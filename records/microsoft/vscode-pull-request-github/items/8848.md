[https://github.com/microsoft/vscode-pull-request-github/issues/8848](https://github.com/microsoft/vscode-pull-request-github/issues/8848)

## Summary

The large-PR slowdown is plausible, but the report does not identify whether time is spent fetching files, constructing the extension tree, or resolving VS Code's multi-diff models. More diagnostics are needed before assigning ownership or consolidating it with the existing VS Code issue.

## Change summary

Loading and previewing a pull request containing more than 1,500 changed files takes an excessive amount of time.

## Best solution

Measure the file-fetch, tree-construction, and editor-opening stages separately. Optimize pagination or node creation in the extension if those dominate; if the delay comes from multi-diff model resolution, consolidate the core work under https://github.com/microsoft/vscode/issues/240181.

## Evidence

- **extension path:** src/github/pullRequestModel.ts:getRawFileChangesInfo paginates the GitHub files endpoint for PRs exceeding 100 files, while src/view/reviewManager.ts:initializePullRequestData creates nodes for every returned change and separately initializes review comments and viewed-file state.
- **existing safeguard:** src/view/reviewManager.ts avoids automatically opening the multi-diff editor once pr.fileChanges.size reaches 400, a safeguard introduced by https://github.com/microsoft/vscode-pull-request-github/pull/7841 for the earlier large-PR performance report https://github.com/microsoft/vscode-pull-request-github/issues/6952.
- **possible core dependency:** https://github.com/microsoft/vscode/issues/240181 remains open and tracks lazy text-model loading for large multi-file diffs, but the issue does not state whether the reported delay occurs in that editor.
- **missing diagnostics:** The report provides current versions and a coarse reproduction, but no timings, GitHub Pull Request output, performance profile, GitHub product, clone configuration, focusedMode value, or exact action that becomes slow.
