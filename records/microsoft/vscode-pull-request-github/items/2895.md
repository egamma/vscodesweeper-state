# Issue #2895 — [feature request]: Allow specific repositories to create issue branch on fork even when you have push access

[https://github.com/microsoft/vscode-pull-request-github/issues/2895](https://github.com/microsoft/vscode-pull-request-github/issues/2895)

## Summary

Thanks for the request. A real gap remains on current main: the issue workflow uses an existing writable fork when configured, but only offers to create a fork when the user lacks upstream push permission. Route this to the issues and git areas for product design.

## Change summary

Allow selected repositories to create issue branches on a fork even when the user can push directly to the upstream repository.

## Best solution

Add an explicit, preferably repository-scoped fork preference for the start-working workflow, then honor it in `FolderRepositoryManager.findUpstreamForItem` and `IssueFeatureRegistrar.doStartWorking` without changing the default behavior for users who want to work directly against upstream.

## Evidence

- **current permission gate:** `src/github/folderRepositoryManager.ts` in `findUpstreamForItem` sets `needsFork` only for READ, TRIAGE, or UNKNOWN permission; WRITE, MAINTAIN, and ADMIN users therefore are not offered fork creation.
- **existing-fork behavior:** `src/github/folderRepositoryManager.ts` detects and selects an already-configured writable fork, while `src/issues/issueFeatureRegistrar.ts` calls `tryOfferToFork` only when `remoteNameResult.needsFork` is true. This partially supports fork workflows but does not cover the requested choice to create or select one despite upstream write access.
- **settings check:** `package.json` exposes issue-branch naming, branch prompting, and base-branch settings, but no setting controls whether issue work should prefer a fork when upstream is writable; `githubIssues.alwaysPromptForNewIssueRepo` applies to creating issues, not starting work on them.
- **canonical search:** Repository issue search for issue-branch, fork, and push-access terms found no separate open canonical owning this request; the closest historical issue, https://github.com/microsoft/vscode-pull-request-github/issues/2805, addressed repeated fork prompts after a fork already existed rather than opting into forks with write access.
