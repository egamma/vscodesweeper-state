# Issue #3663 — Show counter of issues/PRs

[https://github.com/microsoft/vscode-pull-request-github/issues/3663](https://github.com/microsoft/vscode-pull-request-github/issues/3663)

## Summary

The requested issue and PR query counters remain missing; notification badges and coding-agent counts do not cover them. Retain this request as the canonical and route it to the issues and tree-view areas.

## Change summary

Show issue and PR counts on view headers and query groups, optionally allowing a selected count on the activity-bar icon.

## Best solution

Provide clearly defined counts for issue and PR views and their query groups without conflating them with unread notifications. Decide how totals behave with pagination, overlapping queries, and multiple repositories before implementation.

- **Fit:** aligned
- **Reason:** Counters support scanning and managing issues and review queues directly in the editor.
- **Evidence:** The durable themes include trees, queries, and views, plus issues integration; the product promise is to review and manage GitHub pull requests and issues directly in VS Code.

## Plan brief

- **Likely files:** `src/issues/issuesView.ts`, `src/issues/stateManager.ts`, `src/issues/issueFeatureRegistrar.ts`, `src/view/treeNodes/categoryNode.ts`, `src/view/prsTreeModel.ts`, `src/view/prsTreeDataProvider.ts`, `package.json`
- **Validation:** Verify issue and PR query counters against known matching results, including zero results, a query spanning multiple pages, overlapping queries, and multiple repositories. Confirm refresh updates counts and existing notification badges retain their documented meaning.
- **Behavior:**

  > Users should be able to assess issue backlog size and PR review queues without manually counting tree entries. Counts should appear at the agreed view and query-group locations and accurately communicate whether they represent complete matches or loaded items. Acceptance checks should cover empty groups, pagination, overlapping queries, multiple repositories, and refresh. Any activity-bar count selection must remain distinguishable from unread notifications.
- **Trace:**

  > IssuesTreeData.getQueryItem and getIssueGroupItem in src/issues/issuesView.ts render labels without aggregate counts, and src/issues/issueFeatureRegistrar.ts registers the issues view without a badge. CategoryNode._getDescription in src/view/treeNodes/categoryNode.ts only describes coding-agent work counts; PrsTreeDataProvider.updateBadge in src/view/prsTreeDataProvider.ts combines notification counts. The query settings in package.json configure filters but do not expose aggregate counters. src/issues/stateManager.ts:setIssues loads one page per repository, and src/view/prsTreeModel.ts:getPullRequestsForQuery manages PR pagination, so loaded arrays alone do not establish complete totals. Preserve existing filtering, pagination, expansion state, and notification semantics. The maintainer reopened the clarified request, and https://github.com/microsoft/vscode-pull-request-github/issues/6253 has since been consolidated into it. Uncertainty starts at the displayed count contract and optional activity-bar behavior, not whether notification badges already satisfy the request.
- **Open decisions:**
  - Should query counters show complete matching totals, or explicitly marked loaded-item counts when results are paginated?
  - Should a view-header count represent all open items in its repositories or the deduplicated union of configured query matches?
  - Should users be able to replace the activity-bar notification count with a selected issue or PR query count, or should inventory counters remain confined to view headers and groups?
