# Issue #7847 — `Create pull requests` should tell me about uncommitted changes and make it easy to commit them

[https://github.com/microsoft/vscode-pull-request-github/issues/7847](https://github.com/microsoft/vscode-pull-request-github/issues/7847)

## Summary

The creation view still lacks guidance about existing uncommitted changes when its branch comparison is empty. Keep this accepted On Deck request open and route it to the creation UI owner; existing commit prompts cover a different workflow.

## Change summary

Explain uncommitted changes when opening Create Pull Request and provide an easy path to commit them.

## Best solution

Make the empty creation comparison explain that working-tree changes are not yet included, with an accessible path to the existing SCM commit workflow. Preserve committed-branch comparison semantics rather than displaying uncommitted files as PR changes.

- **Reason:** Guiding users from local changes to a pull request supports the native in-editor GitHub workflow.

- **Likely files:** `src/github/createPRViewProvider.ts`, `src/view/compareChangesTreeDataProvider.ts`, `webviews/createPullRequestViewNew/app.tsx`
- **Validation:** In an extension development window, start on a branch identical to its base with staged and unstaged edits, then run pr.create. Repeat with a clean branch and with a different compare branch to ensure no misleading dirty-state message.
- **Behavior:**

  > Opening Create Pull Request on a current branch with uncommitted changes and no committed difference should explain why the PR comparison is empty. Users should have an accessible path to commit those changes through the existing SCM workflow. Uncommitted files must not be represented as committed PR changes. Verify both staged and unstaged edits, the clean-branch case, and refresh after committing.
- **Trace:**

  > CreatePullRequestHelper.create() constructs CreatePullRequestDataModel and CompareChanges without dirty-state guidance. The model compares committed refs; CompareChangesFilesTreeProvider.getGitChildren() displays the no-commits message for an empty diff. CreatePullRequestViewProvider supplies an existing-PR warning, while its submission-time checkForChanges() addresses edits cached by the virtual content providers rather than ordinary local edits. Preserve branch-selection behavior and the separate virtual-file commit workflow. Related https://github.com/microsoft/vscode-pull-request-github/issues/2696 concerns branch suggestions, not this notification. The unresolved product choice is how the creation flow presents guidance and the commit affordance.
- **Open decisions:**
  - Should this empty-comparison guidance be an inline notice with an SCM action, or an entry-time prompt offering to open SCM before continuing?

## Evidence

- **Accepted improvement:** https://github.com/microsoft/vscode-pull-request-github/issues/7847 explicitly says the empty comparison is correct and requests explanatory guidance and easier committing. It carries feature-request and the On Deck milestone, with no comments or linked implementation.
- **Current comparison behavior:** src/view/createPullRequestDataModel.ts: gitCommits() uses a branch commit range and gitFiles() uses diffBetween(base, compare). src/view/compareChangesTreeDataProvider.ts: CompareChangesFilesTreeProvider.getGitChildren() reports no commits when that diff is empty; it does not explain existing working-tree changes.
- **Existing-capability check:** package.json exposes pr.create and creation settings including githubPullRequests.defaultCreateOption and githubPullRequests.showCreatePullRequestCancelConfirmation, but no dirty-working-tree guidance setting. src/view/createPullRequestHelper.ts: create() opens the creation model and views without such guidance. src/github/createPRViewProvider.ts initializes its warning from existingPRMessage(), which concerns an already-existing PR.
- **Commit prompt is not coverage:** src/github/createPRViewProvider.ts: checkForChanges() runs at submission and calls model.filesHaveChanges(). That delegates to ChangesContentProvider.hasChanges() in src/view/gitHubContentProvider.ts, which checks its own edited virtual-file cache, not ordinary existing staged or working-tree edits. GitContentProvider.applyChanges() actually asks users to commit or stash other local changes.
