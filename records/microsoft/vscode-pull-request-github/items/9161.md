# Issue #9161 — Clicking "checkout" on a PR from a branch already in a worktree fails

[https://github.com/microsoft/vscode-pull-request-github/issues/9161](https://github.com/microsoft/vscode-pull-request-github/issues/9161)

## Summary

The supplied main checkout still attempts to reuse a branch occupied by another worktree, without actionable recovery. Route to git and review; the report provides sufficient steps and environment details.

## Change summary

PR checkout fails with a generic error when the PR branch is already checked out in another local worktree.

## Best solution

Make PR checkout handle occupied branches without disturbing the existing worktree, and explain the conflict with an actionable recovery. Decide whether recovery should offer opening the existing worktree, checking out an independent review branch, or both.

- **Likely files:** `src/github/pullRequestGitHelper.ts`, `src/github/folderRepositoryManager.ts`, `src/view/reviewManager.ts`, `src/test/github/pullRequestGitHelper.test.ts`
- **Validation:** Extend the PullRequestGitHelper Mocha tests with equal local/remote commits and a branch occupied by another worktree, including a previously PR-associated branch. Validate the selected recovery, preservation of the occupied branch and its worktree, and unchanged ordinary checkout behavior. Manually repeat the reported main-clone checkout flow with a pushed branch in another worktree and verify an actionable notification rather than a generic Git failure.
- **Behavior:**

  > From a main clone, checking out a PR whose branch is occupied by another worktree currently fails with a generic Git error. The review flow should identify this conflict and provide a usable, maintainer-selected recovery without modifying or removing the existing worktree. Both first-time checkout and checkout of a previously PR-associated branch must handle the conflict. Ordinary unoccupied-branch checkout must retain its existing behavior.
- **Trace:**

  > ReviewManager.switch calls checkoutExistingPullRequestBranch first, then fetchAndCheckout through FolderRepositoryManager. Both helpers in src/github/pullRequestGitHelper.ts can attempt checkout of an occupied branch; fetchAndCheckout only selects a unique branch when local and remote commits differ, and its catch also misclassifies checkout errors as branch absence. FolderRepositoryManager.getWorktreeForBranch already exposes branch-to-worktree lookup, but these checkout paths do not use it. The separate src/github/worktree.ts command creates a worktree rather than opening an existing one, so it is not a demonstrated recovery. Existing tests in src/test/github/pullRequestGitHelper.test.ts cover divergent-commit preservation, not occupancy. Preserve unrelated local work and existing ordinary checkout semantics; do not treat deleting or forcing the occupied worktree as recovery. The supplied snapshot predates the reported versions, so confirm the path against the maintainer's current checkout before implementation.
- **Open decisions:**
  - When a PR branch is occupied by another worktree, should checkout offer opening that worktree, creating an independent review branch in the current clone, or both?
  - If independent review branches are supported, should they be conflict-only recovery or also an opt-in policy for every PR checkout?
