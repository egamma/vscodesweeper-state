# Issue #701 — Add support for reading http.proxy setting

[https://github.com/microsoft/vscode-pull-request-github/issues/701](https://github.com/microsoft/vscode-pull-request-github/issues/701)

## Summary

The request remains necessary on current main: extension network clients support `HTTPS_PROXY`, but they do not read VS Code's `http.proxy` setting. Recent reports were explicitly consolidated into this issue, so it should remain the canonical feature request and be routed to the GitHub integration area.

## Change summary

Make the extension's GitHub API traffic honor VS Code's global `http.proxy` configuration.

## Best solution

Centralize proxy resolution in `src/env/node/net.ts`, using the VS Code `http.proxy` setting when configured while retaining a documented environment-variable fallback, and apply the resulting transport consistently to REST, GraphQL, and GitHub-host detection requests.

## Evidence

- **current source:** `src/env/node/net.ts` constructs the shared HTTPS agent exclusively from `process.env.HTTPS_PROXY`; it does not access `workspace.getConfiguration('http')` or `http.proxy`.
- **network consumers:** `src/authentication/githubServer.ts` and the Octokit setup in `src/github/credentials.ts` use the shared agent, while the GraphQL link in `src/github/credentials.ts` uses `cross-fetch`; proxy behavior should therefore be reviewed across all request paths.
- **existing capability check:** No `http.proxy` or equivalent VS Code proxy-setting integration exists in `src/` or `package.json`; the current `HTTPS_PROXY` support is only a partial workaround and does not satisfy the requested setting behavior.
- **canonical status:** Maintainers closed later reports https://github.com/microsoft/vscode-pull-request-github/issues/7977 and https://github.com/microsoft/vscode-pull-request-github/issues/8099 as duplicates of this issue, including a current-version report from October 2025.
- **enterprise impact:** The maintainer discussion in https://github.com/microsoft/vscode-pull-request-github/issues/4624 explicitly identifies use of `http.proxy` as the known issue tracked here, and this issue includes a GitHub Enterprise user whose corporate network requires proxy access.
