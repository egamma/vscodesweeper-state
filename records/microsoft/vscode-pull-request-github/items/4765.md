# Issue #4765 — Allow copying a github link to the default branch

[https://github.com/microsoft/vscode-pull-request-github/issues/4765](https://github.com/microsoft/vscode-pull-request-github/issues/4765)

## Summary

The requested default-branch link remains unavailable: existing commands use the current branch or a commit, with default-branch fallback only for detached HEAD. Keep this accepted request open and route it to git and ux.

## Change summary

Provide a way to copy a GitHub file link targeting the repository's default branch independently of local HEAD, including upstream-repository sharing for forks.

## Best solution

Offer an explicit default-branch sharing action without changing existing HEAD-link or permalink semantics. Settle which repository it targets in fork and multi-remote setups so the resolved branch and repository consistently match.

## Plan brief

- **Likely files:** `src/issues/util.ts`, `src/issues/issueFeatureRegistrar.ts`, `src/issues/shareProviders.ts`, `package.json`, `package.nls.json`
- **Validation:** In an extension development host, check out an unpublished feature branch and copy a default-branch link for a file that exists on the remote default branch. Verify the URL's repository, branch, encoded path, and selection fragment; repeat with a fork plus upstream remote and detached HEAD. Existing HEAD-link and permalink actions must retain their current behavior.
- **Behavior:**

  > Users can copy a GitHub file link to the chosen repository's default branch while remaining on a different, even unpublished, local branch. The link targets the default branch rather than the local branch name or commit. Fork users must be able to share the upstream version as requested in the discussion. Acceptance checks should cover single-remote and fork configurations, encoded paths, optional selection fragments, and unchanged existing sharing actions.
- **Trace:**

  > src/issues/issueFeatureRegistrar.ts registers issue.copyGithubHeadLink and routes it through copyHeadLink, getHeadLinkWithError, and createGitHubLink. In src/issues/util.ts, createSingleGitHubLink prefers HEAD.name, using repository metadata only for detached HEAD; getSimpleUpstream selects HEAD's tracking remote or the first remote. src/issues/shareProviders.ts independently follows the same branch preference through getHEAD. These paths establish the missing capability without executing the extension. Preserve existing HEAD-link and commit-permalink contracts; automatic unchanged-line fallback in https://github.com/microsoft/vscode-pull-request-github/issues/7983 is separate work. The unresolved product boundary is how the new action chooses its repository when a fork and upstream are both available.
- **Open decisions:**
  - For forks and multiple GitHub remotes, should default-branch sharing target upstream by default, retain the current tracking repository, or ask users to choose the repository?
