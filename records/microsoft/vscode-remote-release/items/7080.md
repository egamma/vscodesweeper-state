# Issue #7080 — Docker not being executed in windows when a \\wsl$\ folder is opened

[https://github.com/microsoft/vscode-remote-release/issues/7080](https://github.com/microsoft/vscode-remote-release/issues/7080)

## Summary

Keep open: the documented execution setting still treats WSL workspace paths specially, rather than providing the requested Windows-only override. The maintainer proposed a three-way setting, and no verified canonical or shipped implementation was found.

## Change summary

Allow Docker commands to execute on Windows when opening a workspace through a \\wsl$ share, even with Docker Desktop's WSL integration disabled.

## Best solution

Dev Containers should provide the proposed Never / For WSL paths / Always execution policy, preserving the current default while allowing Windows Docker for WSL-backed workspaces. Confirm that the Windows-only mode supports this UNC-path workflow before treating the request as delivered.

## Evidence

- **Specific requested capability:** https://github.com/microsoft/vscode-remote-release/issues/7080 supplies steps disabling Docker Desktop WSL integration and setting remote.containers.executeInWSL=false. Reopening a \\wsl$ workspace then reports Docker missing, while a native Windows workspace succeeds.
- **Accepted improvement:** https://github.com/microsoft/vscode-remote-release/issues/7080#issuecomment-1237919146 proposes changing the setting to support Never, For WSL paths (default), and Always. This maintainer-supported direction and the Backlog milestone bar a decline close.
- **Existing-capability check:** https://code.visualstudio.com/remote/advancedcontainers/containers does not document this override; the execution-setting release note at https://github.com/microsoft/vscode-docs/blob/main/remote-release-notes/v1_61.md explicitly says CLI commands still run in WSL for WSL-filesystem workspaces when dev.containers.executeInWSL is disabled. https://code.visualstudio.com/docs/devcontainers/containers documents opening \\wsl$ folders with WSL integration enabled, which does not satisfy the requested integration-disabled workflow.
- **Related reports are not canonicals:** Searches for executeInWSL and Windows/WSL Docker execution found no verified open issue owning this same symptom. https://github.com/microsoft/vscode-remote-release/issues/11005 concerns early initialization with executeInWSL=true; https://github.com/microsoft/vscode-remote-release/issues/11833 concerns local WSL startup for Remote-SSH workspaces, not Windows Docker execution for a WSL UNC workspace. Neither meets the re-review same-symptom duplicate bar.
- **WSL forwarding is distinct:** https://github.com/microsoft/vscode-remote-release/issues/9194#issuecomment-1847422378 distinguishes Docker execution from WSL display and agent forwarding. The forwarding toggle announced at https://github.com/microsoft/vscode-remote-release/issues/9194#issuecomment-1910604239 therefore does not establish that the requested Docker execution override shipped.
