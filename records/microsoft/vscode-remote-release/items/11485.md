# Issue #11485 — upgrading vscode with multiple instances opened to the same linux remote will cause corrupt installation

[https://github.com/microsoft/vscode-remote-release/issues/11485](https://github.com/microsoft/vscode-remote-release/issues/11485)

## Summary

Keep open as a well-supported Remote - SSH installation race: concurrent windows honor the lock but all react to the download trigger, corrupting the server installation and preventing startup.

## Change summary

Ensure that concurrent Remote - SSH windows cannot download and extract the same VS Code Server installation simultaneously during an upgrade.

## Best solution

The SSH installer should let only the lock holder download and extract a given server commit, while waiters re-check the completed installation after the lock is released. Installation should also use an atomic staging path so interrupted or competing attempts cannot expose a partial server.

## Evidence

- **current reproduction:** https://github.com/microsoft/vscode-remote-release/issues/11485 includes logs from three concurrent Remote - SSH 0.122.0 windows on VS Code 1.109.2: one acquires the lock while two wait, but all begin installation after the same download trigger.
- **failure impact:** Both a controlled reproduction and attached logs from an ordinary upgrade show concurrent extraction producing an incomplete server installation, followed by startup failures such as `Cannot find module 'uuid'`.
- **related reports:** https://github.com/microsoft/vscode-remote-release/issues/10133 documents similar upgrade-time missing-module failures but is closed and did not establish this race, while https://github.com/microsoft/vscode-remote-release/issues/11781 concerns a distinct WSL installer path and explicitly cites this issue as the analogous SSH locking defect.
