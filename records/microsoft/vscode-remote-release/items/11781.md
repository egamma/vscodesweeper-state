# Issue #11781 — [WSL] wslDownload.sh nests the server install when the target dir already exists, and the file-count mismatch it detects is non-fatal

[https://github.com/microsoft/vscode-remote-release/issues/11781](https://github.com/microsoft/vscode-remote-release/issues/11781)

## Summary

The current WSL extension can accept a demonstrably malformed server installation as successful, leaving `code .` unusable until manual repair. This is a well-supported WSL installer bug that should remain open and be routed to the server installation path.

## Change summary

Make WSL server installation race-safe and return failure when extraction validation detects a malformed installation.

## Best solution

The WSL installer should install atomically or serialize installations for each commit, avoid moving staging content into an existing destination, and return a nonzero status whenever its file-count or executable validation fails.

## Evidence

- **observed failure:** https://github.com/microsoft/vscode-remote-release/issues/11781 includes current-version logs from WSL 0.104.3 showing the installer report 3603 expected files versus 3604 extracted, then continue to `/bin/remote-cli/code: not found`.
- **filesystem diagnosis:** The reported filesystem contained the intact 3603-entry payload under an extra `$COMMIT-<timestamp>` directory, directly matching the documented `mv` behavior when its destination directory already exists; moving those entries up restored operation.
- **validation defect:** The shipped script excerpt in https://github.com/microsoft/vscode-remote-release/issues/11781 shows that a detected extraction-count mismatch only prints `ERROR:` and does not return failure, allowing callers to execute an installation already known to be malformed.
- **related reports:** https://github.com/microsoft/vscode-remote-release/issues/11485 tracks concurrent installation corruption in Remote - SSH, not this WSL implementation. The older WSL symptom at https://github.com/microsoft/vscode-remote-release/issues/9838 is closed and did not establish this nesting mechanism, so neither is a valid duplicate canonical.
