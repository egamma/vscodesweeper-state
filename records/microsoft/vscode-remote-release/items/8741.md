# Issue #8741 — Unable to start devcontainer when code resides on google drive

[https://github.com/microsoft/vscode-remote-release/issues/8741](https://github.com/microsoft/vscode-remote-release/issues/8741)

## Summary

Keep open as an upstream filesystem-mount compatibility issue. The reporter's follow-up changes the symptom from container startup failure to missing source files; neither a fix nor a canonical covering that Google Drive scenario is established.

## Change summary

Projects on a Google Drive-mapped Windows drive fail to start or expose their source files inside a Docker Compose dev container, while local-drive copies work.

## Best solution

Isolate Docker Desktop's access to the Google Drive bind source using a standalone mount and the container's inspected Mounts. If Docker exposes the files correctly outside Dev Containers, the containers owner should investigate the effective Compose configuration and workspace path; otherwise the fix belongs in the Docker Desktop/host-filesystem integration.

## Evidence

- **Location-dependent failure:** https://github.com/microsoft/vscode-remote-release/issues/8741 supplies Windows 11, Docker Desktop, Dev Containers 0.299.0, Compose bind mounts, and a daemon/runc startup error. The same project works from the native local drive.
- **Unresolved follow-up:** https://github.com/microsoft/vscode-remote-release/issues/8741#issuecomment-2411915053 reports that copying to C: worked, but Google Drive remains problematic: the container now builds and opens while source files are missing. The displayed override contains identification labels, not proof of the effective workspace bind mount.
- **Upstream lead is not a canonical:** The maintainer linked https://github.com/moby/moby/issues/40835 in https://github.com/microsoft/vscode-remote-release/issues/8741#issuecomment-1645789008. That open issue describes intermittent Linux container startup failures with kernel allocation errors, not Google Drive bind mounts or the later missing-files symptom.
- **Mount ownership:** https://docs.docker.com/engine/storage/bind-mounts/ explains that bind sources must be accessible to the daemon and Docker Desktop bridges host paths into its Linux VM. It recommends inspecting the container's Mounts to verify the actual source and destination; this supports investigating host-path access without proving a Google Drive-specific root cause.
- **Existing configuration does not establish resolution:** https://code.visualstudio.com/remote/advancedcontainers/add-local-file-mount documents Docker Compose service volumes for local bind mounts, which the reporter already uses. It does not establish that Google Drive-mapped paths are accessible to Docker Desktop.
- **Canonical search:** Searches for Google Drive, mapped drives, network drives, and virtual drives found no verified open canonical covering this symptom. https://github.com/microsoft/vscode-remote-release/issues/8280 is open but concerns Podman's explicit 'unsupported UNC path' error on a Samba share, not this Docker Desktop/Google Drive failure.
