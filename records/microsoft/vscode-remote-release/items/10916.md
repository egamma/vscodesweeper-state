# Issue #10916 — Port Forwarding Fails to reconnect after disconnect with `useLocalServer` true

[https://github.com/microsoft/vscode-remote-release/issues/10916](https://github.com/microsoft/vscode-remote-release/issues/10916)

## Summary

Keep open for Remote - SSH investigation: the complete report shows the local server timing out and exiting immediately before forwarding fails. It predates newer extension releases, but the supplied steps and logs suffice to retest; neither resolution nor a canonical owning this exact failure is established.

## Change summary

Remote - SSH fails to restore its connection after sleep or network interruption when remote.SSH.useLocalServer is enabled.

## Best solution

The SSH component should investigate why the local server exits during reconnect after successfully discovering the remote listening port, and ensure recovery recreates a live forwarding transport. Compare the shutdown timing with the related sleep-watchdog reports without assuming the separate wrong-SOCKS-port race explains this case.

## Evidence

- **Complete failure log:** The full body at https://github.com/microsoft/vscode-remote-release/issues/10916 includes VS Code 1.99.3, Remote - SSH 0.119.0, macOS arm64, Ubuntu remote details, reproduction steps, and the failure sequence omitted from the supplied excerpt. At 08:31:32.868 the delay-shutdown request fails with EPIPE, the local server prints 'Timed out' and exits, and forwarding then receives ECONNREFUSED on 127.0.0.1:59633.
- **Different forwarding failure:** https://github.com/microsoft/vscode-remote-release/issues/10568 is open and older, but describes application ports remaining broken after the editor reconnects, with useLocalServer=false and recovery by removing and re-adding forwards. Here the connection's own transport fails, and reloading is included among unsuccessful recovery attempts. The author's earlier comment there does not establish that both reports share a root cause.
- **Wrong-port race is not demonstrated:** https://github.com/microsoft/vscode-remote-release/issues/11831 is open and reports forwarding through a different SOCKS port from the one passed to ssh -D. This report consistently uses port 59633 for both; its refusal follows local-server termination, so the newer issue does not demonstrably own its fix.
- **Related shutdown timing:** Open https://github.com/microsoft/vscode-remote-release/issues/11720 describes a sleep-expired local-server shutdown timer, while https://github.com/microsoft/vscode-remote-release/issues/11463 discusses post-wake connection abandonment and timeout experiments. These support investigating shutdown handling, but this report includes network interruption and a timeout after remote-port discovery rather than proving either report's specific mechanism.
- **Documented workaround:** https://github.com/microsoft/vscode-remote-release/wiki/Remote-SSH-troubleshooting documents useLocalServer=true as shared Local Server Mode and false as per-window Terminal Mode. The reporter says false works and changing useExecServer does not help; changing connection mode is a workaround, not proof that reconnect in Local Server Mode is fixed.
