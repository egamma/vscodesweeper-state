Keep open and route to the SSH owner: independent users confirm Codex initialization hangs specifically over Remote-SSH, including on VS Code 1.141.2. The reported settings workaround does not establish a shipped fix or prove that the navigator warning causes the hang.

## Evidence

- **Independent confirmations:** https://github.com/microsoft/vscode-remote-release/issues/11741 contains Fedora-to-Debian confirmation on VS Code 1.137.0 and Windows-to-Ubuntu confirmation on 1.141.2. Both describe Codex renderer readiness failures while the remote backend starts; reinstalling extensions and the remote server did not resolve them.
- **Workaround is not resolution:** The October 14 comment at https://github.com/microsoft/vscode-remote-release/issues/11741 reports recovery after enabling both extensions.supportNodeGlobalNavigator and http.electronFetch. The commenter explicitly cannot identify which setting helped; there is no maintainer-announced fixing release.
- **Documented compatibility setting:** https://code.visualstudio.com/updates/v1_101#_web-environment-detection documents extensions.supportNodeGlobalNavigator and the Node.js navigator migration. This compatibility toggle does not establish that downstream UI startup hangs are intended behavior or universally resolved.
- **Warning does not establish causality:** https://github.com/microsoft/vscode-remote-release/issues/11675#issuecomment-4636789742 and https://github.com/microsoft/vscode-remote-release/issues/11675#issuecomment-4637620385 explain that the migration error is logging and may be a red herring. That issue concerns declared-extension installation after container rebuilds, not Codex UI initialization.
- **Canonical search:** https://github.com/microsoft/vscode-remote-release/issues/11659 is open and reports SSH initialization failures with similar warning stacks, but provides no diagnosis establishing the same cause as this Codex readiness timeout. https://github.com/microsoft/vscode-remote-release/issues/11974 concerns a group-accessible folder missing from Explorer, another distinct symptom; neither is a verified canonical for this report.
- **Core references do not establish full ownership:** https://github.com/microsoft/vscode/issues/312145 is open but concerns Copilot plugin discovery; https://github.com/microsoft/vscode/issues/312110 is closed as a duplicate of https://github.com/microsoft/vscode/issues/252077. The latter remains open, but https://github.com/microsoft/vscode/issues/252077#issuecomment-3007873185 explicitly distinguishes the warning from functional remote failures and directs those failures to this tracker. A shared error string is insufficient for a cross-repository duplicate close.
