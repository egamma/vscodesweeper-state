## Evidence

- **Concrete reproduction:** https://github.com/microsoft/vscode-remote-release/issues/10657 supplies Windows OpenSSH 9.5p1, VS Code 1.96.4, Remote - SSH 0.116.1, a bastion ProxyCommand and ForwardX11 configuration. - **Existing support is not a verified fix:** https://github.com/microsoft/vscode-remote-release/issues/589#issuecomment-783111635 announced X11 support in a Nightly build. A subsequent missing-DISPLAY report prompted the maintainer to request a new issue with logs at https://github.com/microsoft/vscode-remote-release/issues/589#issuecomment-790993892; the closed historical issue is not an open duplicate canonical.
- **Reporter workaround:** https://github.com/microsoft/vscode-remote-release/issues/10657#issuecomment-2955998447 reports that setting local Windows DISPLAY=127.0.0.1:0 enables forwarding, while explicitly asking whether this is the required setup. This is not confirmation of a fixing release or a maintainer determination that the reported behavior is intentional.
- **Mixed independent reports:** https://github.com/microsoft/vscode-remote-release/issues/10657#issuecomment-3070117045 reports xclock failing inside VS Code but working through external ssh -X with XQuartz. However, https://github.com/microsoft/vscode-remote-release/issues/10657#issuecomment-3082489012 retracts another apparent confirmation: VS Code 1.100.3 with Remote - SSH 0.120.0 worked after removing debugging changes, and that user's remaining failure belonged to Cursor.
- **Recent unresolved configuration interaction:** https://github.com/microsoft/vscode-remote-release/issues/10657#issuecomment-5662894727 reports in September 2026 that removing ForwardAgent restores DISPLAY. Versions and a controlled reproduction are absent, so this supports further investigation rather than proving a current-release extension defect or a shared root cause.
- **Troubleshooting boundary:** The complete https://github.com/microsoft/vscode-remote-release/wiki/Remote-SSH-troubleshooting requires comparing the generated SSH command outside VS Code and testing connection modes, including disabling useExecServer. The reporter did not perform the external-command comparison; that comparison would distinguish OpenSSH/environment behavior from extension-specific behavior without discarding the supplied reproduction.
- **Canonical search:** Open-issue searches for X11 and DISPLAY did not establish a canonical owning this SSH-terminal failure. https://github.com/microsoft/vscode-remote-release/issues/11599 was inspected and concerns a Dev Containers extension-host crash when an X11 forwarding target is unreachable, not this report's missing DISPLAY or SSH forwarding failure.
