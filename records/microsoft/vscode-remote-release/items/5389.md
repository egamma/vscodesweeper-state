# Issue #5389 — second wsl2 user causes  /tmp/remote-wsl-loc.txt permission denied

[https://github.com/microsoft/vscode-remote-release/issues/5389](https://github.com/microsoft/vscode-remote-release/issues/5389)

## Summary

Keep open: the public Windows launcher still uses the shared temporary filename implicated by this report. The supplied two-user steps suffice to retest on current releases; the related user-selection request does not establish that this permission failure is covered.

## Change summary

Running `code .` as a second WSL user encounters a permission error because the extension-location temporary file belongs to the first user.

## Best solution

Remove cross-user temporary-file collisions from the Windows CLI's WSL extension-discovery path without requiring permissive file permissions. A maintainer can transfer this to microsoft/vscode, where the launcher lives, while coordinating the separate WSL user-selection behavior with the WSL extension owner.

## Evidence

- **Concrete reproduction:** https://github.com/microsoft/vscode-remote-release/issues/5389 supplies sequential `code .` launches by two Ubuntu WSL2 users, the exact permission error, first-user file ownership, and VS Code 1.58.2. These steps are sufficient for a current-release retest.
- **Public launcher still uses the shared path:** https://github.com/microsoft/vscode/blob/main/resources/win32/bin/code.sh redirects `--locate-extension ms-vscode-remote.remote-wsl` output to `/tmp/remote-wsl-loc.txt`, then reads that same file before invoking the extension's `scripts/wslCode.sh`. This is public core launcher evidence, not closed-source extension evidence, and does not constitute a runtime reproduction.
- **Workarounds are not a shipped fix:** The discussion at https://github.com/microsoft/vscode-remote-release/issues/5389 contains confirmations of launcher edits and permission-changing workarounds, but no maintainer-announced fixing release or reporter-confirmed shipped resolution. The April 2025 reply describes another workaround.

Its full discussion does not establish ownership of this launcher collision, so it does not satisfy the re-reviewed-item duplicate bar.
