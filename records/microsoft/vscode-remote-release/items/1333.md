# Issue #1333 — Support SELinux enabled systems

[https://github.com/microsoft/vscode-remote-release/issues/1333](https://github.com/microsoft/vscode-remote-release/issues/1333)

## Summary

Keep open: the request is for SELinux-compatible workspace mounting without machine-specific project edits, and documented mount overrides remain workarounds rather than automatic support. No verified canonical covers the full Docker-and-Podman scope.

## Change summary

Support opening host workspaces in dev containers on SELinux-enforcing systems without permission failures or machine-specific configuration changes.

## Best solution

The Dev Containers owner should define a host-aware workspace-mounting approach that preserves SELinux isolation and shared project portability, coordinating runtime limitations upstream. Separate SELinux labeling from rootless UID mapping and Docker Desktop file-sharing problems.

## Evidence

- **Existing capability is a workaround:** https://code.visualstudio.com/remote/advancedcontainers/change-default-source-mount documents workspaceMount overrides using Docker --mount syntax; https://containers.dev/implementors/json_reference/ documents runArgs for explicit runtime arguments. In https://github.com/microsoft/vscode-remote-release/issues/1333#issuecomment-898260126 a maintainer suggests clearing workspaceMount and supplying --volume with :Z. These require configuration changes rather than delivering automatic SELinux support.
- **Central request remains distinct:** https://github.com/microsoft/vscode-remote-release/issues/1333#issuecomment-1482447158 explicitly requests out-of-the-box support without patching shared configuration. https://github.com/microsoft/vscode-remote-release/issues/1333#issuecomment-2354339137 confirms moving security-opt into a Podman wrapper works, but that is a local workaround disabling labeling, not a shipped isolation-preserving solution.
- **Runtime limitation and safety:** https://docs.docker.com/engine/storage/bind-mounts/#configure-the-selinux-label states that --mount cannot modify SELinux labels, while :z/:Z modify host labels and can affect host access. Automatically relabeling directories therefore requires an explicit safety decision, not indiscriminate application of :Z.
- **Canonical search:** Open https://github.com/microsoft/vscode-remote-release/issues/6759 includes automatic SELinux handling, but only within Podman improvements; it does not own this report's Docker scope. Open https://github.com/microsoft/vscode-remote-release/issues/11284 reports the same workspace permission symptom on Fedora 43 with Dev Containers 0.427.0 and VS Code 1.105.1, but is younger, has no milestone and no upvotes, so it cannot replace this older re-reviewed request. https://github.com/microsoft/vscode-remote-release/issues/2881 concerns a different Podman mount-format startup failure.
- **Upstream symptoms are not the whole request:** https://github.com/microsoft/vscode-remote-release/issues/1333#issuecomment-1347644927 identifies a Docker Desktop SELinux problem and links https://github.com/docker/desktop-linux/issues/104. That explains one participant's environment, not the broader request for extension-managed SELinux-compatible mounting.
