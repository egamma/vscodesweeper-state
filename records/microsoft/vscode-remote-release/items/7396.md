# Issue #7396 — Devcontainer cloning fails with invalid characters for a local volume name error

[https://github.com/microsoft/vscode-remote-release/issues/7396](https://github.com/microsoft/vscode-remote-release/issues/7396)

## Summary

Keep open: the supplied steps and Docker log suffice to retest invalid generated volume names. A matching report persisted on Dev Containers 0.401.0 in 2025, but there is no current-release reproduction or confirmed fix.

## Change summary

Cloning repositories into container volumes fails when repository-derived volume names start with punctuation or contain unsupported characters.

## Best solution

Dev Containers should generate Docker-valid volume names while preserving deterministic repository identity and avoiding collisions. Retain this older report as the tracking candidate for name sanitization; investigate the Azure DevOps URL-parsing detail separately if it remains reproducible.

## Evidence

- **Actionable reproduction:** https://github.com/microsoft/vscode-remote-release/issues/7396 provides a two-step trigger: create a repository starting with '.' or '_', then run Clone Repository in Container Volume. The extension issues docker volume create with '.git_mgmt-main-81432cc5337c26d3a57b0ddcc532f686', which Docker rejects because the first character must be alphanumeric.
- **Full discussion and workaround limits:** https://github.com/microsoft/vscode-remote-release/issues/7396#issuecomment-1373015891 shows Dev Containers 0.266.1 generating a name containing '%20'. Using the Dev Containers command directly avoids that commenter's Remote Repositories/Azure DevOps URL-parsing problem, but does not establish a fix for punctuation-prefixed repository names. https://github.com/microsoft/vscode-remote-release/issues/7396#issuecomment-1537593340 additionally reports CodeCommit URLs containing '@'.
- **Same symptom, not an eligible canonical:** https://github.com/microsoft/vscode-remote-release/issues/10794 is open and records the same docker volume create rejection for a '.github-private' repository on Dev Containers 0.401.0 and VS Code 1.98.0 in March 2025. It is younger than this issue, has no milestone and zero upvotes, versus this issue's one; it does not satisfy the stronger canonical-ownership bar for this re-review.
- **Other canonical leads differ:** https://github.com/microsoft/vscode-remote-release/issues/5547 and https://github.com/microsoft/vscode-remote-release/issues/11890 concern unresolved configuration variables passed to Docker, not automatic repository-name sanitization. https://github.com/microsoft/vscode-remote-release/issues/7010 concerns decoding '%20' in an existing workspace path and reports 'Workspace does not exist', a different observable failure.
- **Documented alternative does not fix the command:** https://code.visualstudio.com/remote/advancedcontainers/improve-performance documents Clone Repository in Container Volume and a separate manual workflow using workspaceMount with a chosen named volume followed by Git: Clone. That alternative can avoid automatic naming, but does not repair the reported command or prove this defect resolved.
