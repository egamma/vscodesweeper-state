# Issue #7175 — Reconnection attempts after "internal libpod error" when starting a project with Podman

[https://github.com/microsoft/vscode-remote-release/issues/7175](https://github.com/microsoft/vscode-remote-release/issues/7175)

## Summary

The evidence identifies this as an older Podman logging defect rather than a Dev Containers defect. Podman 4.2+ resolves it, while `--log-driver=none` provides a workaround for Podman 3.4.4.

## Change summary

Dev Containers repeatedly reconnects when Podman 3.4.4 times out while recording container output.

## Best solution

Keep this routed as an upstream Podman compatibility issue and document that affected users should upgrade Podman or use the reported `runArgs` workaround when constrained to 3.4.4.

## Evidence

- **upstream diagnosis:** The maintainer connected the exact `timed out waiting for file ... internal libpod error` to https://github.com/containers/podman/issues/13227, whose fix was available in Podman 4.1.0.
- **version confirmations:** The reporter confirmed the failure stopped after upgrading from Podman 3.4.4 to 4.2.1, and another affected user independently confirmed Podman 4.3 resolved the recurring reconnects.
- **root cause and workaround:** https://github.com/containers/podman/issues/13779 tracks the Podman stdout/stderr logging hang; https://github.com/microsoft/vscode-remote-release/issues/7175#issuecomment-1645498699 reports `{"runArgs":["--log-driver=none"]}` as an effective workaround on Podman 3.4.4.
