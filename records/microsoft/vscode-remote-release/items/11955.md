# Issue #11955 — Windows host with OpenSSH 9.8+: `command-shell` launcher leaks on every reconnect

[https://github.com/microsoft/vscode-remote-release/issues/11955](https://github.com/microsoft/vscode-remote-release/issues/11955)

## Summary

Keep open: the report provides concrete reconnect steps and identifies the wrong lifetime-monitoring PID after OpenSSH's session-process split. Those steps suffice to retest; no confirmed fix or canonical covering this launcher leak was established.

## Change summary

Remote-SSH leaves Windows command-shell launchers running after disconnect because their monitored parent PID belongs to the persistent sshd listener rather than the exited session.

## Best solution

The Remote-SSH owner should verify Windows launcher parent selection with OpenSSH 9.8+ and monitor the connection-scoped ancestor so obsolete launchers exit when their session ends, without terminating the shared listener.

## Evidence

- **Actionable report:** https://github.com/microsoft/vscode-remote-release/issues/11955 specifies VS Code 1.145.2, Windows 11, the OpenSSH build and server commit, and a connect–sleep–reconnect trigger. The reporter observes surviving command-shell processes whose --parent-process-id points to the persistent sshd.exe listener after the corresponding sshd-session processes exit. There is no independent reproduction in the thread.
- **Documented process split:** https://www.openssh.org/txt/release-9.8 documents the split into the sshd listener and the per-session sshd-session binary. This corroborates the architectural change behind the report, but does not independently verify Windows launcher behavior.
- **Related lifecycle intent, not a verified duplicate:** https://github.com/microsoft/vscode-remote-release/issues/5699 is open and concerns inability to connect to SSH daemons not named sshd. Its maintainer comment at https://github.com/microsoft/vscode-remote-release/issues/5699#issuecomment-1355904610 explains that monitoring the closest sshd.exe ancestor is intended to shut down the long-running process when the connection ends. That supports the expected cleanup behavior, but does not establish that the nonstandard-daemon connection request owns this OpenSSH launcher leak.
- **Other cleanup and reconnect leads:** https://github.com/microsoft/vscode-remote-release/issues/10931 is closed after the reporter found clean standalone installations worked. https://github.com/microsoft/vscode-remote-release/issues/11403 is open but discusses failed reconnection and Windows extension installation through bash, not selecting the persistent listener as the command-shell parent. Neither establishes a canonical or fix for this report.
