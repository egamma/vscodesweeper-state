# Issue #1996 — [New feature] Abilities to set the remoteUser globally.

[https://github.com/microsoft/vscode-remote-release/issues/1996](https://github.com/microsoft/vscode-remote-release/issues/1996)

## Summary

Keep open: documented image- and container-name configurations support remoteUser, but do not provide the requested global default across containers. No verified canonical or shipped global setting was found.

## Change summary

Allow a user-level remoteUser default for attaching to containers without configuring each project, image, or container separately.

## Best solution

Dev Containers should support an opt-in user-level default applied before initial attachment and server installation, with explicit container configuration taking precedence. Image- and name-specific configurations remain useful overrides, not substitutes for that default.

## Evidence

- **Requested scope:** https://github.com/microsoft/vscode-remote-release/issues/1996 requests a settings.json default across project containers. The 2024 comment adds the need to select the user before the first attachment installs server files; July 2026 comments reaffirm demand.
- **Existing capability is partial:** https://code.visualstudio.com/docs/devcontainers/attach-container documents remoteUser in image- and container-name-level configuration files, including editing existing configurations while detached. These reduce repeated setup within an image or name, but do not establish one user-level default across all containers.
- **Spec boundary:** https://github.com/devcontainers/spec/blob/main/docs/specs/devcontainerjson-reference.md defines remoteUser in devcontainer.json and image metadata, separately from containerUser. Neither documented mechanism supplies the requested VS Code user-level attachment preference.
- **Earlier implementation does not satisfy this request:** https://github.com/microsoft/vscode-remote-release/issues/1155#issuecomment-559139307 announced remoteUser in Remote-Containers 0.86.0. https://github.com/microsoft/vscode-remote-release/issues/1155#issuecomment-564058432 explains configuring the user and reloading to install the server under that user; this is per-configuration support, not a global default.
- **Related discussion is not a canonical:** https://github.com/89luca89/distrobox/issues/514 is closed. Its workaround at https://github.com/89luca89/distrobox/issues/514#issuecomment-2120899296 creates a separate named configuration for each Distrobox container, leaving this report's global-default requirement unmet.
