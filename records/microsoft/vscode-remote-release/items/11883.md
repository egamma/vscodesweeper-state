# Issue #11883 — Dev Containers: .devport file is shared between containers that bind-mount the same ~/.vscode-server, causing "already running" server to be forwarded to the wrong port (WebSocket close 1006)

[https://github.com/microsoft/vscode-remote-release/issues/11883](https://github.com/microsoft/vscode-remote-release/issues/11883)

## Summary

Keep open: the November 22 confirmation on VS Code 1.147.0 demonstrates that shared server installations still require manually isolated runtime state. Retain the accepted feature-request classification; no verified open canonical reports this same wrong-port reconnection symptom.

## Change summary

Allow containers to share installed VS Code Server files while automatically keeping cached endpoints and runtime connection metadata container-local.

## Best solution

Dev Containers should isolate runtime metadata by container instance and validate cached endpoints against the target server before reuse, while preserving shared server binaries. Connecting, reloading, restarting, or recreating one container should not invalidate another container's connection.

## Evidence

- **Specific failure:** https://github.com/microsoft/vscode-remote-release/issues/11883 supplies ordered reproduction steps and logs: container A listens on 34551, container B overwrites the shared .devport file with 39283, and reloading A forwards to 39283, producing ECONNREFUSED and WebSocket close 1006.
- **Recent independent confirmation:** https://github.com/microsoft/vscode-remote-release/issues/11883#issuecomment-7072403325 confirms the same cached-port collision on November 22 with VS Code 1.147.0 and three containers sharing a named server volume. Private per-project data volumes restore connections while retaining shared installation files; automatic isolation remains explicitly requested.
- **Workaround is not implementation:** https://github.com/microsoft/vscode-remote-release/issues/11883#issuecomment-5914802565 independently reports that a private data/Machine mount avoids interference. Both workarounds require changing container mounts rather than fixing endpoint reuse automatically.
- **Existing capability check:** https://code.visualstudio.com/docs/devcontainers/attach-container documents attached-container configuration, including forwardPorts and remoteEnv, but no automatic per-container server-state isolation. https://containers.dev/implementors/json_reference/ documents mounts for manually adding storage; that supports the workaround, not automatic separation when attaching to existing containers.
