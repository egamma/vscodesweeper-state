## Summary

Request a reproducible workspace scenario and process-level diagnostics before deciding ownership. Historical reports mix large-workspace indexing, possible C/C++ extension activity, and WSL load independent of VS Code; none establishes a current reproduction of the original paired CPU spike.

## Change summary

Opening a WSL workspace reportedly causes sustained COM Surrogate and Vmmem CPU usage that stops when the WSL connection is closed.

## Best solution

The WSL component should identify which workload causes the sustained CPU usage using a repeatable workspace example and simultaneous Windows/Linux process captures. Establish whether the remaining defect belongs to remote workspace handling, an installed language extension, or the WSL platform before redirecting it.
