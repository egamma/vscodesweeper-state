[https://github.com/microsoft/vscode-remote-release/issues/11578](https://github.com/microsoft/vscode-remote-release/issues/11578)

## Summary

Keep open for the SSH owner: no verified existing control covers the requested Windows server-readiness timeout. The related download regression does not establish resolution of first-execution delays on pre-deployed servers.

## Change summary

Allow administrators to increase the Windows Remote-SSH server-start wait to accommodate endpoint-protection scanning delays.

Remote - SSH should provide a supported way to tolerate delayed Windows server readiness while preserving bounded waits. Identify whether startup polling or cached exec-server ping validation causes this failure before deciding which timeout to expose.

- **Existing-capability check:** https://github.com/microsoft/vscode-remote-release/wiki/Remote-SSH-Troubleshooting documents remote.SSH.useLocalServer and remote.SSH.useExecServer as connection-mode controls; disabling exec-server mode is a diagnostic workaround, not configurable startup waiting. https://code.visualstudio.com/docs/remote/troubleshooting#_troubleshooting-hanging-or-failing-connections does not document a server-readiness timeout control.
- **Related regression is not a verified canonical:** https://github.com/microsoft/vscode-remote-release/issues/11657 is open and newer, with three upvotes, but concerns first-run downloads in Remote-SSH 0.123.0 rather than AV-delayed execution of a pre-deployed server in 0.122.0. https://github.com/microsoft/vscode-remote-release/issues/11657#issuecomment-4528513420 explicitly reports that downgrading to 0.122.0 resolves that regression; the VS Code 1.122 confirmation at https://github.com/microsoft/vscode-remote-release/issues/11657#issuecomment-4529667568 does not confirm this request is satisfied.
