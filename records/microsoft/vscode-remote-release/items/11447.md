# Issue #11447 — SendEnv does not work

[https://github.com/microsoft/vscode-remote-release/issues/11447](https://github.com/microsoft/vscode-remote-release/issues/11447)

## Summary

The missing session-environment propagation is already tracked by the open request to transfer SSH environment variables into each new remote extension host. This report's log shows reuse of an existing VS Code Server, matching that documented limitation.

## Change summary

Make a locally exported SendEnv variable available in the remote VS Code terminal when connecting over SSH.

## Best solution

Consolidate this report into https://github.com/microsoft/vscode-remote-release/issues/6448, where Remote - SSH owns propagating the current SSH session's environment despite server reuse. Preserve the macOS/zsh SendEnv reproduction and exec-server log as additional evidence.

- **Maintainer-established behavior:** https://github.com/microsoft/vscode-remote-release/issues/6448#issuecomment-1068379024 explains that the shared remote server retains the first SSH session's environment and proposes copying current session variables into each new extension host. This broader capability covers variables supplied through SendEnv.
- **Matching server reuse:** https://github.com/microsoft/vscode-remote-release/issues/11447 supplies concrete macOS-to-Linux steps on VS Code 1.108.1 and Remote - SSH 0.122.0. - **Restart is a workaround, not session propagation:** https://github.com/microsoft/vscode-remote-release/issues/2344#issuecomment-585483918 explains the unchanged server environment, and https://github.com/microsoft/vscode-remote-release/issues/2344#issuecomment-585617991 confirms restarting resolved that older report. The fully read troubleshooting guide at https://github.com/microsoft/vscode-remote-release/wiki/Remote-SSH-troubleshooting documents 'Kill VS Code Server on Host...', but restarting does not deliver automatic environment transfer on subsequent connections.
