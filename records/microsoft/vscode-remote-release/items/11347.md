## Evidence

- **Verified open canonical:** https://github.com/microsoft/vscode-remote-release/issues/10939 is open and predates this report. It tracks successful SSH connections followed by remote CLI startup failure on openSUSE, empty server logs, listeningOn====, and failure to obtain a remote port. Independent reports cover Tumbleweed, Aeon, and Leap, so its scope includes this Slowroll variant.
- **Matching failure stage:** https://github.com/microsoft/vscode-remote-release/issues/11347 shows Remote - SSH 0.120.0 launching the remote CLI, waiting for its log, receiving listeningOn==== with platformDownloadPath==cli-alpine-x64==, and terminating with 'Failed to parse remote port from server output'. This matches the canonical's exec-server bootstrap failure rather than an SSH authentication failure.
- **Alternative client comparison:** https://github.com/microsoft/vscode-remote-release/issues/11347#issuecomment-3599441392 shows VSCodium's server returning a valid listening port on the same remote distribution; https://github.com/microsoft/vscode-remote-release/issues/11347#issuecomment-3604248161 identifies its different SSH extension. This supports retaining the product-path comparison, but does not establish that Microsoft's extension is fixed.
- **Documented diagnostic distinction:** https://github.com/microsoft/vscode-remote-release/wiki/Remote-SSH-troubleshooting distinguishes remote.SSH.useLocalServer from remote.SSH.useExecServer and recommends testing with the latter disabled. The canonical contains successful confirmations of that workaround, including https://github.com/microsoft/vscode-remote-release/issues/10939#issuecomment-2949816330; this reporter tested useLocalServer, not useExecServer.
