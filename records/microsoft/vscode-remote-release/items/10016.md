# Issue #10016 — [Remote-Container Bug] Massive UI performance issues without x11 socket when using Containers in WSL2

[https://github.com/microsoft/vscode-remote-release/issues/10016](https://github.com/microsoft/vscode-remote-release/issues/10016)

## Summary

Keep open for the Dev Containers team's proposed local X11 socket-mounting improvement. The reporter still observed poor performance in February 2026; the manual mount is a workaround, and the related initialization fix does not resolve this request.

## Change summary

Provide performant X11 applications in WSL2 dev containers without requiring a manually configured DISPLAY and direct socket mount.

## Best solution

The containers component should evaluate directly mounting the local X11 socket when the Docker daemon is local, as suggested in the thread, while preserving explicitly configured displays. Use the supplied glxgears comparison to assess whether this eliminates the performance gap.

## Evidence

- **Concrete performance comparison:** https://github.com/microsoft/vscode-remote-release/issues/10016 supplies a Debian Dockerfile and glxgears comparison: approximately 100 FPS without the direct X11 mount versus 1100 FPS with it. The affected applications run inside the container; this is not evidence of editor UI slowness.
- **Maintainer-supported direction:** https://github.com/microsoft/vscode-remote-release/issues/10016#issuecomment-2479040057 explains that detected Wayland sockets are mounted automatically and suggests doing the same for X11 when the Docker daemon runs locally. The feature-request label and Backlog milestone reflect accepted improvement work, not grounds for a decline close.
- **Remaining gap:** https://github.com/microsoft/vscode-remote-release/issues/10016#issuecomment-2476149189 reports that DISPLAY=:0 plus a direct /tmp/.X11-unix/X0 mount restores performance; https://github.com/microsoft/vscode-remote-release/issues/10016#issuecomment-3958444479 reports continued impact on February 25, 2026. Neither comment establishes resolution.
- **Existing-capability check:** https://code.visualstudio.com/remote/advancedcontainers/add-local-file-mount documents explicit bind mounts, and https://code.visualstudio.com/remote/advancedcontainers/environment-variables documents containerEnv and runArgs. These support manual configuration but do not establish automatic, performant X11 socket mounting; the reporter already uses that workaround.
- **Related fix has separate scope:** https://github.com/microsoft/vscode-remote-release/issues/10014#issuecomment-2199540477 explicitly separates this performance issue from the postStartCommand hang. https://github.com/microsoft/vscode-remote-release/issues/10014#issuecomment-2249610484 confirms that Dev Containers 0.378.0 pre-release fixed initialization, not the performance gap.
- **Canonical search:** Searches for X11, Wayland, X11 performance, and glxgears found no verified canonical with the same observable performance symptom. https://github.com/microsoft/vscode-remote-release/issues/8031 concerns disabling automatic forwarding and overwritten DISPLAY values; https://github.com/microsoft/vscode-remote-release/issues/10791 concerns authentication preventing applications from starting. Neither owns this report's remaining work or meets the re-review duplicate bar.
