# Issue #11974 — Remote-SSH: Explorer fails to open a group-accessible directory after VS Code 1.147.0 update; resolved by enabling Node global navigator

[https://github.com/microsoft/vscode-remote-release/issues/11974](https://github.com/microsoft/vscode-remote-release/issues/11974)

## Summary

Keep open: the reported 1.147.0 regression has concrete steps sufficient for a maintainer retest, but no independent confirmation. Enabling navigator support is a workaround, not a shipped fix, and the related reports do not establish the cause of the missing Explorer root.

## Change summary

Opening a group-accessible directory over Remote-SSH leaves Explorer without a workspace root unless Node global navigator support is enabled.

## Best solution

The SSH owner should reproduce the directory-specific failure with navigator support disabled and enabled, then identify the failed workspace-opening operation. Restore normal folder opening under default settings; a maintainer can transfer this to microsoft/vscode if investigation establishes core ownership.

## Evidence

- **Actionable regression report:** https://github.com/microsoft/vscode-remote-release/issues/11974 specifies VS Code 1.147.0, Remote-SSH 0.128.0, Ubuntu client and Linux ARM64 remote, and folder-opening steps. The parent directory fails while subdirectories work; successful listings and server-process supplementary groups support valid filesystem access.
- **Workaround is not resolution:** The reporter confirms that extensions.supportNodeGlobalNavigator=true plus a full restart restores Explorer without permission changes. https://code.visualstudio.com/updates/v1_101#_web-environment-detection documents this setting as controlling navigator compatibility behavior, not as a fix for directory-opening failures.
- **Diagnostic does not establish causality:** In https://github.com/microsoft/vscode/issues/334504#issuecomment-5736809457, a maintainer explains that the compatibility getter in 1.136.1 reports PendingMigrationError and returns undefined rather than throwing into extension initialization. This finding concerns an earlier version, but directly cautions against treating the diagnostic alone as proof of the reported UI failure. That issue was closed for missing information, not a confirmed fix.
- **Related reports are not verified canonicals:** https://github.com/microsoft/vscode-remote-release/issues/11741 remains open and reports Codex initialization failures; https://github.com/microsoft/vscode-remote-release/issues/11659 remains open and reports connection or extension-initialization failures. Neither establishes ownership of this directory-selective missing-Explorer-root behavior, and a shared navigator diagnostic does not prove a shared root cause.
