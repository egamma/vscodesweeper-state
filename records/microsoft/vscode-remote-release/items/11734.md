# Issue #11734 — Remote SSH: server shuts down after reconnect due to hardcoded 5-minute extension host timer triggered by IPC failure

[https://github.com/microsoft/vscode-remote-release/issues/11734](https://github.com/microsoft/vscode-remote-release/issues/11734)

## Summary

Keep open for SSH/server-lifecycle investigation: the supplied steps and timestamped logs suffice to retest the shutdown after reconnection. The July reproductions on VS Code Server 1.127/1.128 lack current-release confirmation, and neither a shipped fix nor a matching canonical has been established.

## Change summary

After a prolonged SSH disconnection, reconnecting is followed by extension-host termination and complete server shutdown instead of a durable recovered session.

## Best solution

The SSH and VS Code Server owners should reproduce the prolonged-disconnection sequence and establish whether failed IPC handoff or stale-session cleanup terminates the newly connected session. Recovery should preserve a healthy active connection or replace an unusable extension host; removing both short timers should not be assumed necessary before confirming that causal chain.

## Evidence

- **Actionable report:** https://github.com/microsoft/vscode-remote-release/issues/11734 specifies Ubuntu client/server environments, VS Code Server 1.127.0 and 1.128.0, and a concrete sequence: work for 30+ minutes, disconnect for 60–90 minutes, then reconnect. The reporter observed the failure six or more times.
- **Observed shutdown versus proposed mechanism:** The July 9 logs in https://github.com/microsoft/vscode-remote-release/issues/11734 show shortened reconnection grace at 17:03:16, extension-host exits at 17:08:16 and 17:08:18, and server shutdown at 17:13:18. These substantiate termination, but the supplied excerpts do not establish that process.send failed during the reconnect or distinguish stale and newly active sessions; the SIGPIPE-to-timer explanation remains the reporter's hypothesis.
- **Reporter-linked issue is not a verified canonical:** https://github.com/microsoft/vscode-remote-release/issues/1257 remains open, but its original failure occurs while opening a large workspace, with repeated reconnects that eventually stabilize. Maintainer discussion at https://github.com/microsoft/vscode-remote-release/issues/1257#issuecomment-531587986 focuses on extension-host responsiveness and file-watcher errors, not the delayed shutdown after a long disconnect documented here.
- **Other reconnection reports have different remaining behavior:** https://github.com/microsoft/vscode-remote-release/issues/11550 is open and concerns a tunnel relay remaining offline while its process stays alive after DNS failure/respawn. https://github.com/microsoft/vscode-remote-release/issues/11805 is open and concerns immediate permanent reconnect failure when a managed socket closes during a brief outage. Neither establishes ownership of this report's delayed SSH server termination.
- **Persistent-session request is distinct:** https://github.com/microsoft/vscode-remote-release/issues/3096 is open and requests indefinite session persistence across days of disconnection. This report instead asks for successful recovery after 60–90 minutes without subsequent termination of the reconnected session.
- **Documented diagnostic path:** https://github.com/microsoft/vscode-remote-release/wiki/Remote-SSH-Troubleshooting calls for full Remote-SSH output and comparison of remote.SSH.useLocalServer and remote.SSH.useExecServer modes. Those diagnostics would help correlate client reconnects with server and extension-host lifetimes; the documented settings do not establish a fix for this failure.
