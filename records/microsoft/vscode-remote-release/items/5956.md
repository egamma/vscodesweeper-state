# Issue #5956 — WSL2 vscode git don't use ssh-agent, but works in integrated terminal

[https://github.com/microsoft/vscode-remote-release/issues/5956](https://github.com/microsoft/vscode-remote-release/issues/5956)

## Summary

The reported launch-dependent behavior matches the documented WSL server environment design: shell startup scripts are not run. The supported server-env-setup script can expose the existing SSH agent to Source Control without launching from an interactive terminal.

## Change summary

Make WSL Source Control Git operations use the SSH agent available in the integrated terminal when VS Code starts from Windows.

## Best solution

Keep the documented WSL startup behavior and configure SSH_AUTH_SOCK in ~/.vscode-server/server-env-setup to point to the reporter's running agent. This supplies the server environment explicitly rather than relying on interactive shell initialization.

- **Proposed comment:**

  > Thanks for the detailed logs. WSL server startup intentionally does not run shell startup scripts, so an SSH_AUTH_SOCK exported only by your interactive shell is not available to Source Control when starting from Windows. This also explains why launching with `code .` works.
  > 
  > The supported configuration is to export `SSH_AUTH_SOCK` in `~/.vscode-server/server-env-setup`, pointing to your existing running agent—for the path in your report, `export SSH_AUTH_SOCK=/home/username/.ssh/agent.sock`. Close all WSL VS Code windows and reconnect after configuring it. See https://code.visualstudio.com/docs/remote/wsl#_advanced-environment-setup-script.

## Evidence

- **Documented intentional behavior and supported configuration:** https://code.visualstudio.com/docs/remote/wsl#_advanced-environment-setup-script explicitly states that WSL server startup does not run shell startup scripts, to avoid problems with shell-specific initialization. It documents ~/.vscode-server/server-env-setup as a Bourne shell script processed before server startup for modifying the environment; exporting the existing SSH_AUTH_SOCK there directly addresses this report.
- **Reporter isolated the launch environment:** https://github.com/microsoft/vscode-remote-release/issues/5956#issuecomment-988496777 reports 'No shell environment set or found for current distro' when starting normally, but confirms everything works with code . from WSL, where the log instead says 'Using shell environment from invoking shell'. The issue body shows an existing loaded agent at /home/username/.ssh/agent.sock.
- **Maintainer diagnosis and later discussion:** https://github.com/microsoft/vscode-remote-release/issues/5956#issuecomment-987687311 points to the server's startup environment. https://github.com/microsoft/vscode-remote-release/issues/5956#issuecomment-1708794310 separately diagnoses the native Linux reports as launcher-versus-interactive-shell environment differences; that Linux configuration is not itself a confirmed WSL fix.
