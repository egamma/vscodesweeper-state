# Issue #10987 — VSCode Remote-SSH drops connection at exactly 20 seconds despite SSH working fine

[https://github.com/microsoft/vscode-remote-release/issues/10987](https://github.com/microsoft/vscode-remote-release/issues/10987)

## Summary

Keep open for the SSH owner: the supplied connection steps and configuration suffice to retest the deterministic disconnect, but current-release reproduction remains unverified. Later reports and mixed workaround results do not establish a fix or a shared root cause.

## Change summary

Remote - SSH disconnects approximately 20 seconds after server startup on Windows-to-Ubuntu connections while comparable standalone SSH sessions remain connected.

## Best solution

The SSH owner should distinguish an SSH transport reset from a remote extension-host acknowledgement timeout by comparing the generated command outside VS Code and correlating SSH and server logs. Preserve this report separately unless that diagnosis establishes shared ownership with an existing issue.

## Evidence

- **Concrete reproduction:** https://github.com/microsoft/vscode-remote-release/issues/10987 supplies VS Code 1.100.2 and 1.101.0-insider, Remote - SSH 0.120.0, Windows OpenSSH 9.5p1, SSH configuration, repeatable connection steps, and a client_loop connection-reset error after server startup. Its successful standalone sleep test also pipes input, so piping alone is not an established cause.
- **Workaround is not resolution:** https://github.com/microsoft/vscode-remote-release/issues/10987#issuecomment-3005246726 reports success with remote.SSH.useExecServer=false, but https://github.com/microsoft/vscode-remote-release/issues/10987#issuecomment-3021571806 explicitly reports continued rapid disconnects with that setting. Neither supplies a current-release reproduction or a maintainer-announced fixing release.
- **Authoritative troubleshooting:** The fully read https://github.com/microsoft/vscode-remote-release/wiki/Remote-SSH-troubleshooting calls for testing the exact generated SSH command externally, testing piped script execution, comparing both useLocalServer values, disabling useExecServer, and examining SSH and server logs. These diagnose different connection paths; successful basic SSH does not exclude a configuration or transport-specific failure.
- **Older candidate has a different demonstrated failure:** https://github.com/microsoft/vscode-remote-release/issues/7497 is open, but https://github.com/microsoft/vscode-remote-release/issues/7497#issuecomment-1329787281 identifies unacknowledged extension-host messages for over 20 seconds. That application-level timeout does not establish the cause of this report's SSH process exiting with Connection reset, including with no workspace opened.
- **Other candidates do not establish a canonical:** https://github.com/microsoft/vscode-remote-release/issues/11570 is open and references this report, but describes a Jetson disconnect after running Python, with minutes between startup and reconnection and standalone SSH subsequently failing until VS Code closes. https://github.com/microsoft/vscode-remote-release/issues/2692 describes an entire EC2 instance becoming unresponsive after hours. Neither demonstrably owns this deterministic 20-second SSH-reset failure.
