# Issue #10939 — Can't connect to Remote SSH server using Exec server

[https://github.com/microsoft/vscode-remote-release/issues/10939](https://github.com/microsoft/vscode-remote-release/issues/10939)

## Summary

Keep open: multiple users confirm exec-server startup fails on SUSE hosts, and newer related reports diagnose a bundled-CLI/OpenSSL configuration incompatibility rather than a shipped fix. The original logs and steps suffice to retest; disabling exec-server mode sacrifices remote-container functionality.

## Change summary

Remote - SSH fails to connect to SUSE hosts with exec-server mode enabled, leaving an empty CLI log and no listening port.

## Best solution

The SSH and CLI owners should resolve the bundled CLI's startup incompatibility with SUSE crypto configuration while preserving Dev Containers over SSH. If confirmed to require a public VS Code CLI fix, a maintainer can transfer this to microsoft/vscode; retain the newer SUSE reports as related diagnostic evidence.

## Evidence

- **Observed failure:** https://github.com/microsoft/vscode-remote-release/issues/10939 records VS Code 1.100.0 / Remote - SSH 0.120.0 successfully authenticating, launching the CLI, then returning listeningOn==== and 'Failed to parse remote port from server output'. The reporter confirms the CLI log exists but is empty: https://github.com/microsoft/vscode-remote-release/issues/10939#issuecomment-2873663689.
- **Independent confirmations:** https://github.com/microsoft/vscode-remote-release/issues/10939#issuecomment-2903708333 compares working and failing SUSE machines following distro updates. https://github.com/microsoft/vscode-remote-release/issues/10939#issuecomment-3421789685 confirms the same failure after upgrading Leap 15.6 to 16.0.
- **Workaround is not resolution:** Disabling remote.SSH.useExecServer restores SSH access per https://github.com/microsoft/vscode-remote-release/issues/10939#issuecomment-2949816330, but prevents remote Dev Containers per https://github.com/microsoft/vscode-remote-release/issues/10939#issuecomment-2952744425. The authoritative https://github.com/microsoft/vscode-remote-release/wiki/Remote-SSH-troubleshooting explains that exec-server bootstrapping enables Dev Containers and WSL over SSH.
- **Newer diagnosis:** The linked solution thread remains open: https://github.com/microsoft/vscode-remote-release/issues/11433. Direct CLI experiments in https://github.com/microsoft/vscode-remote-release/issues/11433#issuecomment-5288977176 report that VS Code 1.131.0's embedded OpenSSL hangs when consuming SUSE's seed=JITTER configuration, while a seed-source override permits startup. https://github.com/microsoft/vscode-remote-release/issues/11433#issuecomment-6225076866 reports the same hang with VS Code 1.141.0 and further isolates its interaction with TLS system defaults. These are compatibility diagnostics and workarounds, not release-fix confirmations.
- **Canonical search:** https://github.com/microsoft/vscode-remote-release/issues/11433 and https://github.com/microsoft/vscode-remote-release/issues/11136 are younger, open, unmilestoned reports with fewer body upvotes than this issue, so neither meets the re-review canonical bar. The older https://github.com/microsoft/vscode-remote-release/issues/10938 concerns an explicit GLIBCXX prerequisite failure; its contributor requested this separate report. https://github.com/microsoft/vscode-remote-release/issues/10918 describes a FIPS-triggered panic with 'library has no ciphers', not this empty-log startup failure.
- **External PR does not fix this issue:** https://github.com/devsy-org/devsy/pull/404 merged a downstream change that disables exec-server mode for Devsy connections. It neither fixes SUSE CLI startup nor delivers working exec-server mode for this reporter.
