Its original log already shows successful authentication, 'Spawned remote CLI', repeated 'Waiting for server log...', and an empty listening port; the final parsing error does not establish a separate failure.
- **Matching direct CLI diagnosis:** https://github.com/microsoft/vscode-remote-release/issues/11433#issuecomment-5288977176 reproduces command-shell hanging without output in a futex wait, identifies embedded OpenSSL 3.1.4 reading the host configuration, and demonstrates startup succeeding after removing or replacing seed=JITTER.
- **This report converges on the same trigger:** https://github.com/microsoft/vscode-remote-release/issues/11721#issuecomment-6180974838 reproduces the same empty-log startup hang on SLES 15 SP7 with VS Code 1.141.2 and Remote-SSH 0.128.0. The same binary starts when the random/JITTER configuration is removed from a private configuration copy.
- **Canonical remains active and covers configuration interaction:** https://github.com/microsoft/vscode-remote-release/issues/11433#issuecomment-6225076866 reports the same hang on MicroOS with VS Code 1.141.0 and isolates an interaction between seed=JITTER and TLS system defaults. This extends the shared diagnosis rather than identifying a separate remaining behavior in this report.
- **Workaround is not resolution:** https://github.com/microsoft/vscode-remote-release/issues/11721#issuecomment-5303116157 confirms disabling remote.SSH.useExecServer bypasses the failing CLI. https://github.com/microsoft/vscode-remote-release/wiki/Remote-SSH-troubleshooting documents this diagnostic fallback and explains that Exec Server enables additional remote functionality; bypassing it is not a shipped fix.
