# Issue #9125 — Dev Container: /workspaces not user writable

[https://github.com/microsoft/vscode-remote-release/issues/9125](https://github.com/microsoft/vscode-remote-release/issues/9125)

## Summary

Keep open for a Dev Containers design decision about creating sibling repositories under /workspaces without misleading users about persistence. The documented parent-folder mount is an opt-in workaround, not a change to the default experience; related permission reports do not own this whole request.

## Change summary

Allow non-root users to clone repositories alongside the mounted workspace under /workspaces.

## Best solution

The containers owner should decide how to support sibling repositories with explicit persistence guarantees, rather than merely making the ephemeral parent directory writable. Separate mounted-workspace ownership failures from this parent-directory usability request.

## Evidence

The linked test https://github.com/microsoft/vscode-remote-release/issues/9123 explicitly exercises git clone from a dev-container terminal.
- **Persistence constraint:** https://github.com/microsoft/vscode-remote-release/issues/9125#issuecomment-1921014511 explains that only the mounted workspace child survives rebuilds. The maintainer cautions against making its parent writable without addressing persistence and offers a parent-folder workspaceMount configuration, rather than declaring the request resolved.
- **Existing capability and limitation:** https://code.visualstudio.com/remote/advancedcontainers/change-default-source-mount documents workspaceMount for replacing the default workspace bind mount. Mounting the local parent at /workspaces supports persistent sibling projects when explicitly configured, but does not provide that behavior in the default configuration.
- **Related ownership reports are distinct:** https://github.com/microsoft/vscode-remote-release/issues/11279 is open and concerns build failures inside a mounted workspace with rootless Docker; https://github.com/microsoft/vscode-remote-release/issues/9931 is open and concerns ownership of additional named volumes. Neither owns the original parent-directory cloning experience.
