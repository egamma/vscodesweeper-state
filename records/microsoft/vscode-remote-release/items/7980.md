# Issue #7980 — Podman Hangs

[https://github.com/microsoft/vscode-remote-release/issues/7980](https://github.com/microsoft/vscode-remote-release/issues/7980)

## Summary

The hang is traced to rootless Podman's journald event backend failing to emit the start event that Dev Containers awaits. Keep this open as an upstream integration issue while considering a bounded fallback when Podman produces no event.

## Change summary

Dev Containers waits indefinitely at “Starting container” when rootless Podman does not emit a container-start event through its journald backend.

## Best solution

Podman should reliably expose rootless container events, while Dev Containers should avoid waiting indefinitely when the configured Podman event backend emits nothing, such as by timing out with a diagnostic or confirming startup through container inspection.

  > Thanks for the investigation and confirmations. The logs indicate that the container starts, but rootless Podman does not deliver the expected start event through its journald backend, leaving Dev Containers waiting. As a workaround, set the following in `containers.conf`:
  > 
  > ```toml
  > [engine]
  > events_logger="file"
  > ```

## Evidence

- **failure point:** The issue log stops after `podman events --format json --filter event=start` and a successful container launch, showing that Dev Containers is waiting for an event rather than for the container process itself.
- **root cause and workaround:** https://github.com/microsoft/vscode-remote-release/issues/7980#issuecomment-2995641998 identifies missing rootless Podman events with `events_logger=journald` and reports that selecting `events_logger="file"` avoids the wait.
- **independent confirmation:** https://github.com/microsoft/vscode-remote-release/issues/7980#issuecomment-3038872350 confirms the file-event workaround on Ubuntu 24.04 with Podman 4.9.3 and Dev Containers 0.417.0.
- **Podman documentation:** https://docs.podman.io/en/latest/markdown/podman-events.1.html documents journald as Podman's default event backend and `events_logger="file"` as the supported alternative.
