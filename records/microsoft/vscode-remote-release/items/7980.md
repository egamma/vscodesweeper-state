# Issue #7980 — Podman Hangs

[https://github.com/microsoft/vscode-remote-release/issues/7980](https://github.com/microsoft/vscode-remote-release/issues/7980)

## Summary

Keep open: the thread points to missing rootless Podman journald events, with a confirmed file-backend workaround rather than a shipped fix. No verified open canonical owns this startup hang.

## Change summary

Starting or rebuilding a rootless Podman dev container stalls until VS Code is reloaded.

## Best solution

Resolve the Podman/journald event-delivery problem and document the confirmed events_logger="file" workaround. The Dev Containers owner should assess whether missing start events can produce a diagnostic instead of an indefinite wait.

## Evidence

- **Concrete startup failure:** https://github.com/microsoft/vscode-remote-release/issues/7980 supplies a rootless Podman configuration and logs stopping after subscribing to start events. https://github.com/microsoft/vscode-remote-release/issues/7980#issuecomment-2417456560 independently reports the same startup stall on Rocky Linux 9.4, Podman 4.9.4 and Dev Containers 0.389.0; its full log prints 'Container started' but connection does not complete until Reload Window.
- **Upstream event-backend diagnosis:** https://github.com/microsoft/vscode-remote-release/issues/7980#issuecomment-2995641998 reports that rootless Podman emits no events with events_logger=journald and recommends [engine] events_logger="file", using Podman 5.4.1 and Dev Containers 0.417.0.
- **Confirmed workaround, not product fix:** https://github.com/microsoft/vscode-remote-release/issues/7980#issuecomment-3038872350 confirms the file backend resolves the problem on Ubuntu 24.04 with Podman 4.9.3 and Dev Containers 0.417.0, while journald works on Debian 12 with Podman 4.3.1 and the same extension version. This supports an environment-dependent event-backend cause, not universal resolution.
- **Documented event mechanism:** https://docs.podman.io/en/latest/markdown/podman-events.1.html documents journald as the default event backend, events_logger="file" as an alternative, and filtering container start events. Changing the backend is a workaround; it does not establish that the extension's indefinite wait has been fixed.
- **Canonical search:** Searches for Podman events, journald and startup hangs found no verified open canonical with the same observable failure. https://github.com/microsoft/vscode-remote-release/issues/11102 hangs during feature-image lookup, https://github.com/microsoft/vscode-remote-release/issues/4536 concerns WSL notebook disconnections, and https://github.com/microsoft/vscode-remote-release/issues/7175 concerns libpod exit-file errors after server connection; none owns this startup-event stall.
- **Closed historical precedent:** https://github.com/microsoft/vscode-remote-release/issues/2890#issuecomment-621632933 identifies missing Podman start events in an older, similar startup hang. That issue is closed following resolution on Podman 1.9.1, so it cannot be a duplicate canonical or prove resolution of this later report.
