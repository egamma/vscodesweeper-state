# Issue #10114 — `Remote SSH: Kill current VS Code server` doesn't work

[https://github.com/microsoft/vscode-remote-release/issues/10114](https://github.com/microsoft/vscode-remote-release/issues/10114)

## Summary

Keep open: the Windows cleanup command targets the legacy bin directory despite an exec-server installation under cli. The report supplies a concrete command, error, and environment sufficient to retest; historical workaround confirmations do not establish resolution on current releases.

## Change summary

Remote-SSH's server-kill command fails to stop and clean up a Windows server installed under .vscode-server\cli.

## Best solution

Remote-SSH should correctly identify and terminate the current server under both legacy and exec-server layouts on Windows, without requiring users to disable exec-server mode. Retest the supplied Windows scenario and distinguish it from the later reports of processes surviving ordinary disconnects.

## Evidence

- **Concrete failure:** https://github.com/microsoft/vscode-remote-release/issues/10114 reports VS Code 1.91.1 on Windows 11 connecting to Windows Server 2019. The emitted PowerShell filters processes under .vscode-server\bin and removes that directory, producing PathNotFound while the reported installation resides under cli.
- **Workaround, not shipped resolution:** https://github.com/microsoft/vscode-remote-release/issues/10114#issuecomment-2487124939 and https://github.com/microsoft/vscode-remote-release/issues/10114#issuecomment-2487279860 confirm disabling remote.SSH.useExecServer helps. Neither identifies a fixing release; the macOS follow-up at https://github.com/microsoft/vscode-remote-release/issues/10114#issuecomment-2986482737 reports remaining processes even with that workaround.
- **Documented server layouts:** https://github.com/microsoft/vscode-remote-release/wiki/Remote-SSH-Troubleshooting documents exec-server logs under ~/.vscode-server[-insiders]/cli/servers/*/log.txt and describes the host-kill command as terminating server processes and removing server files. Disabling useExecServer is a troubleshooting step, not evidence that the cleanup failure is intended.
- **Linked issue is not a canonical:** https://github.com/microsoft/vscode-remote-release/issues/10403 is closed after an unanswered information request. Its Linux environment-refresh scenario with useLocalServer enabled does not establish ownership or resolution of this Windows bin-versus-cli cleanup failure.
- **Open cleanup reports have different triggers:** https://github.com/microsoft/vscode-remote-release/issues/10730 concerns zombie and lingering processes after session drops. https://github.com/microsoft/vscode-remote-release/issues/11151 concerns hard network disconnects and explicitly says Kill VS Code Server on Host successfully tears down its processes. Neither establishes a canonical for the explicit cleanup-command failure here.
