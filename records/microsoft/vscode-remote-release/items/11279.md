# Issue #11279 — Cannot build java project or node project in container, permission denied

[https://github.com/microsoft/vscode-remote-release/issues/11279](https://github.com/microsoft/vscode-remote-release/issues/11279)

## Summary

Keep open for the containers owner to diagnose the rootless Docker/WSL bind-mount permission interaction. The reporter supplied configurations, creation logs, and failing commands, and answered the maintainer's rootless-mode question; no fix or fully verified canonical establishes a close.

## Change summary

Java and Node builds fail as vscode on Windows-backed workspaces mounted through rootless Docker in WSL, while running as container root succeeds.

## Best solution

Establish a supported non-root configuration for Windows-backed bind mounts under rootless Docker, distinguishing namespace ownership from filesystem permission operations. Docker/WSL owns the underlying permission semantics; the containers owner should determine whether configuration guidance suffices or extension-side handling remains necessary.

- **Independent toolchain, same environment:** https://github.com/microsoft/vscode-remote-release/issues/11279#issuecomment-3459341578 reports create-next-app copyfile EPERM and Next.js output-write failures with the analogous Windows-backed mount. - **Documented infrastructure behavior:** https://docs.docker.com/engine/security/rootless/uid-gid-mapping/ documents that the rootless daemon user's host UID maps to container root, explaining root-owned bind-mounted files. https://code.visualstudio.com/remote/advancedcontainers/add-nonroot-user documents remoteUser and UID/GID adjustment, but does not establish that ordinary UID matching resolves rootless namespaces or Windows-backed permission operations.
- **Related issues are not verified canonicals:** https://github.com/microsoft/vscode-remote-release/issues/9125 is open and includes the reporter's matching rootless WSL configuration at https://github.com/microsoft/vscode-remote-release/issues/9125#issuecomment-3426834149. However, its original parent-directory writability problem and proposed parent workspaceMount do not establish coverage of Maven's permission-copy failure inside an already world-writable project. https://github.com/microsoft/vscode-remote-release/issues/9931 is also open but concerns named-volume ownership, rather than this Windows-backed bind mount.
