# Issue #11642 — [Dev Containers] Incompatibility with Podman .in files

[https://github.com/microsoft/vscode-remote-release/issues/11642](https://github.com/microsoft/vscode-remote-release/issues/11642)

## Summary

Keep the accepted Podman compatibility request open: host-side preprocessing is a documented workaround, but native .in handling remains unsupported. The matching CLI request is closed without an implementation and cannot serve as a duplicate canonical.

## Change summary

Support Podman .in Dockerfiles whose included instructions must be expanded before Dev Containers parses and rewrites the build file.

## Best solution

The Dev Containers owner should decide whether to integrate preprocessing before Dockerfile inspection and feature generation, coordinating with devcontainers/cli. Until then, document the initializeCommand workaround without treating it as native support or closing this Backlog request.

## Evidence

- **Two concrete compatibility gaps:** https://github.com/microsoft/vscode-remote-release/issues/11642 supplies Dockerfile examples and dev-containers-cli 0.460.0 logs: an included FROM is rejected before preprocessing, while moving FROM into the input produces Dockerfile-with-features without the .in suffix, leaving included RUN instructions unexpanded.
- **Podman behavior:** https://docs.podman.io/en/latest/markdown/podman-build.1.html#description documents CPP preprocessing for Containerfiles ending in .in, including #include reuse and manual preprocessing for other tools.
- **Existing capabilities and their limits:** https://code.visualstudio.com/remote/advancedcontainers/docker-options documents dev.containers.dockerPath=podman. The metadata reference at https://raw.githubusercontent.com/devcontainers/spec/main/docs/specs/devcontainerjson-reference.md documents initializeCommand for host-side initialization and build.dockerfile for selecting the generated file; these enable explicit preprocessing but do not provide automatic .in recognition.
- **Matching CLI request and workaround:** https://github.com/devcontainers/cli/issues/1223 is closed. Its maintainer comment at https://github.com/devcontainers/cli/issues/1223#issuecomment-4658868108 explicitly declines built-in .in preprocessing for now and recommends initializeCommand="cpp -P Dockerfile.in Dockerfile" with build.dockerfile="Dockerfile". This is a workaround, not a landed fix, and the closed item is not an eligible duplicate canonical.
- **Features discussion:** https://github.com/microsoft/vscode-remote-release/issues/11642#issuecomment-4411276874 suggests Features; the reporter explains their alternative workflow at https://github.com/microsoft/vscode-remote-release/issues/11642#issuecomment-4411307787. https://code.visualstudio.com/docs/devcontainers/create-dev-container documents reusable Features, but replacing the Dockerfile workflow does not implement .in compatibility.

The issue already carries containers, podman, feature-request, and Backlog; no later maintainer decision in this thread overrides that accepted scope.
