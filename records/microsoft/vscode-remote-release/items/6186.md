# Issue #6186 — Run separate VS Code servers per workspace in the same remote to enable different env variables per workspace.

[https://github.com/microsoft/vscode-remote-release/issues/6186](https://github.com/microsoft/vscode-remote-release/issues/6186)

## Summary

Keep this accepted SSH feature request open: documented alternatives do not establish support for simultaneous, independent RemoteCommand environments on the same remote account. It also owns the reload requirement consolidated from the earlier related report.

## Change summary

Allow simultaneous SSH workspaces on one remote account to retain independent environments and refresh their environment without disrupting other sessions.

## Best solution

Remote - SSH should offer opt-in workspace/session isolation that preserves each connection's environment and execution context, including ClearCase views, with independent restart or refresh. Environment-variable transfer alone would cover only part of the request.

## Evidence

- **Accepted scope:** In https://github.com/microsoft/vscode-remote-release/issues/6186, the January 2022 discussion explicitly accepts simultaneous servers as a feature request rather than a bug. The February 2022 bot comment records promotion to Backlog; the issue currently has 18 upvotes. Intended server sharing is not grounds to decline this accepted enhancement.
- **Execution context beyond variables:** The January 2023 confirmation in https://github.com/microsoft/vscode-remote-release/issues/6186 describes different `cleartool setview` RemoteCommands: users cannot work in two ClearCase dynamic views simultaneously. Merely overriding terminal variables does not establish coverage of that requirement.
- **Consolidated reload requirement:** https://github.com/microsoft/vscode-remote-release/issues/6187#issuecomment-1022562252 explicitly closes that report in favor of this issue. https://github.com/microsoft/vscode-remote-release/issues/6187#issuecomment-1022571243 adds proper environment refresh on window reload. The closed report is not a canonical target.
- **Existing SSH settings:** https://github.com/microsoft/vscode-remote-release/wiki/Remote-SSH-Troubleshooting documents `remote.SSH.useLocalServer=false` as providing a separate SSH connection per window, not an independently initialized full remote server environment. `remote.SSH.useExecServer` describes bootstrap behavior, not workspace isolation. Neither description establishes that the central ask is delivered.
- **Container workaround is conditional:** The December 2024 suggestion in https://github.com/microsoft/vscode-remote-release/issues/6186 requires Docker and Dev Containers on the remote. https://code.visualstudio.com/docs/remote/ssh documents Reopen in Container over SSH, and https://containers.dev/implementors/json_reference/#general-properties defines `remoteEnv` for container tooling and subprocesses. This supports project variables inside containers, not independent native SSH/ClearCase sessions.
- **Related issue is narrower:** Canonical searches for RemoteCommand, environment variables, multiple servers, and per-workspace behavior found https://github.com/microsoft/vscode-remote-release/issues/6448, verified open in Backlog. Its proposal transfers SSH environment variables to new extension hosts; https://github.com/microsoft/vscode-remote-release/issues/6448#issuecomment-1068379024 does not establish ownership of separate server execution contexts or independent reload. It therefore does not absorb this issue's full scope.
- **Other older leads:** https://github.com/microsoft/vscode-remote-release/issues/141 requests custom server initialization, https://github.com/microsoft/vscode-remote-release/issues/1722 requests cluster allocation before server startup, and https://github.com/microsoft/vscode-remote-release/issues/690 requests switching users. Their verified bodies do not own simultaneous isolated environments for the same remote account.
