# Issue #8129 — Feature request: devcontainer: add options to avoid applying the feature's `customizations`

[https://github.com/microsoft/vscode-remote-release/issues/8129](https://github.com/microsoft/vscode-remote-release/issues/8129)

## Summary

A project-level customization can override the fish Feature's setting, but no declarative, granular mechanism exists to suppress arbitrary Feature customizations. The remaining gap belongs at the Dev Container spec/CLI layer.

## Change summary

Allow devcontainer users to exclude some or all tool customizations contributed by a referenced Feature.

## Best solution

Track a configuration-level opt-out in https://github.com/devcontainers/spec so all supporting tools can implement consistent suppression semantics; the existing CLI build flag is not a substitute for a per-project or per-Feature option.

- **Proposed comment:**

  > Thanks for the request. For the fish example, the project can currently override the Feature by setting `customizations.vscode.settings.terminal.integrated.defaultProfile.linux` to `bash` in its own `devcontainer.json`. The broader ability to suppress Feature customizations remains a Dev Container specification gap; the CLI's existing hidden build flag only disables all Feature customizations and does not provide per-project or per-Feature control.

## Evidence

- **spec boundary:** The Dev Container specification documents Feature `customizations` and explicitly leaves their merging to supporting tools: https://containers.dev/implementors/spec/#customizations-property.
- **partial CLI capability:** https://github.com/devcontainers/cli/pull/262 added the hidden `--skip-persisting-customizations-from-features` build flag, but it suppresses all Feature customizations during image building and provides no devcontainer.json-level or per-Feature control.
- **current workaround:** For this exact fish-shell scenario, https://github.com/meaningful-ooo/devcontainer-features/issues/70 documents that a project-level `customizations.vscode.settings` value takes precedence over the Feature value. That solves the cited scalar conflict but not the broader request to suppress arbitrary customizations.
- **related proposal:** https://github.com/devcontainers/spec/issues/588 remains open and concerns richer Feature customization configuration, but it does not currently define the requested opt-out and therefore is not a verified duplicate canonical.
