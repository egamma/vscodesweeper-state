# Issue #2353 — uriTransformer.js consume 100% CPU in WSL

[https://github.com/microsoft/vscode-remote-release/issues/2353](https://github.com/microsoft/vscode-remote-release/issues/2353)

## Summary

Keep open: the original report strongly implicates WSL1/glibc compatibility, but the upstream fix does not establish that the later WSL reports are resolved. No verified open canonical covers this issue's symptom and scope.

## Change summary

Opening an empty WSL folder with `code .` causes a remote process whose command line includes uriTransformer.js to consume 100% CPU.

## Best solution

The WSL component owner should retest the supplied empty-folder steps on current Windows, WSL, and VS Code releases, separating the original platform compatibility failure from any remaining remote-server performance defect. The initial platform fix belongs to microsoft/WSL; later reports need independent diagnosis before this issue can be retired.

## Evidence

- **Original trigger and workaround:** https://github.com/microsoft/vscode-remote-release/issues/2353 provides an empty-folder `code .` reproduction on ArchWSL and Windows 10 build 18363. On February 17, 2020, the reporter linked microsoft/WSL's compatibility issue and reported that downgrading glibc to 2.30.3 resolved the CPU problem, revising their initial VS Code regression hypothesis.
- **Upstream diagnosis:** https://github.com/microsoft/WSL/issues/4898 describes ArchWSL failures after glibc 2.30.3 was upgraded to 2.31.1. A WSL maintainer identified missing CLOCK_REALTIME support in WSL1 clock_nanosleep at https://github.com/microsoft/WSL/issues/4898#issuecomment-592196721. That issue is closed, but its platform diagnosis and fix do not independently prove resolution of every CPU report here.
- **Remaining reports:** https://github.com/microsoft/vscode-remote-release/issues/2353 contains subsequent reports through December 2021, including Windows 10 with WSL Ubuntu 21.04. None confirms resolution on a fixing release or establishes that these later occurrences share the original glibc cause.
- **Linked SSH report is not a canonical:** https://github.com/microsoft/vscode-remote-release/issues/3857 is closed and was consolidated into https://github.com/microsoft/vscode-remote-release/issues/2998, also closed. Its maintainers identified a missing GLIBCXX_3.4.22 dependency in an SSH/ARM environment, not this report's WSL1/glibc compatibility failure.
- **Open candidate has a different trigger:** Canonical searches for uriTransformer and WSL CPU reports found https://github.com/microsoft/vscode-remote-release/issues/3161, which remains open in Backlog. It concerns load spikes while saving and rebuilding projects in Docker or WSL2, rather than opening an empty WSL folder; it does not satisfy the same-observable-symptom requirement for this re-reviewed issue.
