# Issue #11803 — Remote-SSH traffic inherits ssh's bulk/scavenger QoS class and gets starved by QoS-aware links — consider `IPQoS=none` (default or setting)

[https://github.com/microsoft/vscode-remote-release/issues/11803](https://github.com/microsoft/vscode-remote-release/issues/11803)

## Summary

Keep open: the measurements implicate OpenSSH packet marking and network QoS treatment, not a demonstrated Remote-SSH defect. Existing configuration provides mitigation, but does not establish that a client-side default change would address the reported server-to-client loss.

## Change summary

Prevent QoS-aware links from starving Remote-SSH traffic through neutral packet marking or documented configuration guidance.

## Best solution

The SSH component should document direction-specific IPQoS troubleshooting and evaluate whether any extension-side policy is warranted. Preserve explicit SSH configuration: the demonstrated mitigation changed sshd, and a client-only IPQoS setting would not change the server's outgoing marking.

## Evidence

- **Measured environment cause:** https://github.com/microsoft/vscode-remote-release/issues/11803 reports Ubuntu 24.04/OpenSSH 9.6 server-to-client flows marked TOS 0x08 with approximately 15–34% retransmission, compared with 0.4% for an interactive SSH flow. Changing server-side IPQoS to none yielded 0.09% retransmission and restored usability; no independent confirmation appears in the supplied thread.
- **Existing capability and remaining ask:** https://code.visualstudio.com/docs/remote/ssh#_remember-hosts-and-advanced-settings documents arbitrary supported SSH configuration directives and remote.SSH.configFile. Host-specific IPQoS none therefore needs no new extension setting for client-side configuration, but does not implement a neutral extension default, document this failure mode, or alter server-side marking.
- **Upstream semantics and changed defaults:** https://man.openbsd.org/ssh_config#IPQoS and https://man.openbsd.org/sshd_config#IPQoS define none as using the operating-system default. The current manuals specify none for non-interactive sessions, unlike the reporter's distro defaults; this is not evidence that their deployed server has changed or that the report is resolved. Operating-system default also does not guarantee universally unmarked or harmless traffic.
- **Independent infrastructure precedent:** https://wiki.osuosl.org/howtos/ssh_ip_qos_fix.html documents frequent dropping of CS1-marked SSH traffic on its network and recommends throughput there. This corroborates network-dependent QoS performance problems, not a universal marking policy.
- **Canonical search:** Tracker searches for IPQoS, QoS, DSCP, scavenger, and slow Starlink found no verified open canonical. https://github.com/microsoft/vscode-remote-release/issues/6086 concerns RemoteCommand/socket connection mode, while https://github.com/microsoft/vscode-remote-release/issues/11780 concerns KnownHostsCommand configuration corruption; neither owns this packet-marking problem.
