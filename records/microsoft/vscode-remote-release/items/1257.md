# Issue #1257 — Repeated SSH disconnects/reconnects that eventually stabilizes (large folder)

[https://github.com/microsoft/vscode-remote-release/issues/1257](https://github.com/microsoft/vscode-remote-release/issues/1257)

## Summary

Keep open: large-workspace disconnects have concrete historical reproductions and a renewed 2026 resource-exhaustion report. Individual extension and environment workarounds do not establish resolution of the original failure, and no verified canonical covers its full scope.

## Change summary

Opening a large remote workspace causes repeated SSH disconnects, sometimes followed by server or extension-host termination and failed recovery.

## Best solution

The SSH and VS Code Server owners should isolate large-workspace resource exhaustion from extension-induced heartbeat stalls, then address the responsible workload and recovery behavior. Capture the latest failing rg command line, process ancestry, server logs, and versions before deciding whether a maintainer can transfer a core-owned portion to microsoft/vscode.

## Evidence

- **Original reproduction:** https://github.com/microsoft/vscode-remote-release/issues/1257 describes opening the Fuchsia checkout over SSH, successful initial connection, and repeated reconnects despite otherwise stable terminal SSH. The reporter supplied client logs and reported persistence after removing remote extensions.
- **Watcher mitigation did not resolve the report:** At https://github.com/microsoft/vscode-remote-release/issues/1257#issuecomment-529650424 the reporter confirmed an increased inotify limit and build-directory watcher exclusions, but continued seeing failures on VS Code 1.38.0 / Remote - SSH 0.46.0. Exclusion workarounds are not proof of a shipped fix.
- **Concrete termination evidence:** https://github.com/microsoft/vscode-remote-release/issues/1257#issuecomment-560504913 records JavaScript heap exhaustion, extension-host SIGABRT, and subsequent failed reconnection on VS Code 1.40.2. Later reports also reproduce disconnects with remote extensions removed.
- **Recent persistence:** https://github.com/microsoft/vscode-remote-release/issues/1257#issuecomment-5230540963 reports in August 2026 that rg consumed about 5.5 GB, the host locked up, the OOM killer terminated processes, and SSH never recovered. Exact current versions and process attribution are not supplied, so this does not establish a single root cause for every report.
- **Related core issue covers only one mechanism:** The maintainer explained heartbeat starvation at https://github.com/microsoft/vscode-remote-release/issues/1257#issuecomment-687070455. The original related issue now lives at https://github.com/microsoft/vscode/issues/135021 and remains open, but specifically tracks extensions keeping the extension host busy; it does not establish ownership of watcher failures, rg memory exhaustion, or extension-free failures here.
- **Canonical search:** Verified open candidates https://github.com/microsoft/vscode-remote-release/issues/11704 and https://github.com/microsoft/vscode-remote-release/issues/11734 concern brief container webview resets and shutdown after a long disconnection respectively. https://github.com/microsoft/vscode-remote-release/issues/11220 and https://github.com/microsoft/vscode-remote-release/issues/11283 concern rg CPU saturation. These younger, unscheduled reports do not meet the re-review canonical bar or establish coverage of this report's complete observable failure. https://github.com/microsoft/vscode-remote-release/issues/3096 requests deliberate session persistence, not prevention of load-induced disconnects.
- **Partial resolutions are not a general fix:** The thread documents separate Python, C++, network, and PATH causes. Increasing MaxSessions helped one user at https://github.com/microsoft/vscode-remote-release/issues/1257#issuecomment-813416704 but failed for another at https://github.com/microsoft/vscode-remote-release/issues/1257#issuecomment-880466944; none establishes a confirmed fixing release for the original report.
