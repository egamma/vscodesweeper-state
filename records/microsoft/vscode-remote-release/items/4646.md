# Issue #4646 — Rootless docker mounts have the wrong permissions

[https://github.com/microsoft/vscode-remote-release/issues/4646](https://github.com/microsoft/vscode-remote-release/issues/4646)

## Summary

This remains a Docker rootless user-namespace limitation rather than a Dev Containers defect. Keep it open as upstream tracking: Docker still lacks the required non-root identity mapping, and the corresponding Moby request remains open.

## Change summary

Allow a non-root container user to write bind-mounted workspace files under rootless Docker without running as container root or changing host ownership.

## Best solution

Docker should provide configurable rootless UID/GID mapping equivalent to Podman's `--userns=keep-id`, tracked at https://github.com/moby/moby/issues/41497. Dev Containers can then adopt that capability through its open CLI; https://github.com/devcontainers/spec/issues/479 tracks the integration need and current workarounds.

  > Thanks for the detailed investigation. Docker's current rootless mapping still maps container UID 0 to the host user and non-root container users into subordinate UID ranges, so `updateRemoteUserUID` cannot make a non-root user own the bind mount. The required mapping capability remains open upstream at https://github.com/moby/moby/issues/41497, with the Dev Containers integration discussion at https://github.com/devcontainers/spec/issues/479. Running as container root or using a managed volume remains a workaround rather than resolving the requested non-root workflow.

## Evidence

- **Docker mapping behavior:** Docker's current documentation states that rootless mode maps container UID 0 to the host user while every non-root UID maps into the subordinate UID range; host-user-owned bind mounts consequently appear as root-owned inside the container: https://docs.docker.com/engine/security/rootless/uid-gid-mapping/
- **open upstream request:** https://github.com/moby/moby/issues/41497 remains open and requests exactly the missing configurable mapping or `--userns=keep-id` equivalent; a 2026 comment confirms it still blocks wider rootless Docker use.
- **Dev Containers tracking:** https://github.com/devcontainers/spec/issues/479 remains open for the same rootless Docker workspace-permission problem. Its 2026 discussion identifies running as container root as a workaround, not a solution.
- **existing capability gap:** Dev Containers documents `updateRemoteUserUID` for ordinary Docker CE/EE bind mounts, but changing the in-container UID cannot override Docker rootless mode's subordinate-ID mapping: https://code.visualstudio.com/remote/advancedcontainers/add-nonroot-user
