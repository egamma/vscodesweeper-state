# Issue #10568 — [Remote-SSH Bug]: Forwarded ports stop working on reconnect

[https://github.com/microsoft/vscode-remote-release/issues/10568](https://github.com/microsoft/vscode-remote-release/issues/10568)

## Summary

Keep open: SSH reconnects successfully, but existing application forwards remain unusable until recreated. The original versions are old, but the supplied steps and reconnection log suffice to retest; neither a confirmed fix nor a canonical covering the full failure has been established.

## Change summary

Restore working manual and automatic port forwards after Remote - SSH reconnects without requiring users to remove and recreate them.

## Best solution

The SSH component should ensure existing application forwards use the restored connection after reconnect. Compare the network-drop reproduction with the older sleep-related report before consolidating; the newer multiwindow report demonstrates a different recovery sequence.

## Evidence

- **Complete reproduction and reconnect log:** https://github.com/microsoft/vscode-remote-release/issues/10568 specifies connecting, forwarding a port, interrupting the connection, and observing localhost requests hang after reconnect until the forward is recreated. Its VS Code 1.96.0 / Remote-SSH 0.117.2024121215 log records successful reconnection with a new internal forwarding endpoint, but does not identify why application forwards remain stale.
- **Thread confirms persistence, not resolution:** https://github.com/microsoft/vscode-remote-release/issues/10568#issuecomment-3380498215 confirms failure after cloudflared drops the connection without laptop sleep. Other commenters report sleep-related failures and window reload as a workaround; none confirms a fixing release.
- **Older candidate has matching symptoms but unverified ownership:** https://github.com/microsoft/vscode-remote-release/issues/10415 is open and predates this issue. It documents stalled application forwards after sleep, recovery by deleting/recreating them, and reports across macOS, ChromeOS and Windows. Its thread does not establish that the broader network-drop/reconnect failure here shares the same underlying defect.
- **Related multiwindow defect is narrower and behaves differently:** https://github.com/microsoft/vscode-remote-release/issues/11965 is open and reproduces shared-forward HTTP timeouts after the creating window reloads on VS Code 1.145.2 / Remote-SSH 0.128.0. Unlike this report, recreating one window's forward does not recover access: all retaining windows must release it. The reporter explicitly states that a shared root cause with this issue is unestablished.
- **Documented workaround does not repair existing forwards:** https://code.visualstudio.com/docs/remote/ssh#_always-forwarding-a-port documents SSH LocalForward, which an affected user reports helps at https://github.com/microsoft/vscode-remote-release/issues/10568#issuecomment-3800380042. This substitutes preconfigured SSH forwards rather than fixing VS Code's manual or automatically created forwards; remote.restoreForwardedPorts is documented as remembering ports, not repairing this failure.
