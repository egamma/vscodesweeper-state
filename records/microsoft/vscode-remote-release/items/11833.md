## Evidence

- **Verified open canonical:** https://github.com/microsoft/vscode-remote-release/issues/11800 is open and was filed on 2026-08-21, before this report. Its Windows-to-Linux Remote-SSH log shows the same sequence: resolved ssh-remote authority immediately followed by local wsl -l -v. Its discussion explicitly identifies unwanted WSL startup and resource consumption.
- **Additional evidence of the same behavior:** https://github.com/microsoft/vscode-remote-release/issues/11833#issuecomment-5497593553 reproduces on a second Windows machine with Dev Containers 0.468.0: approximately 7.5 seconds of distro startup, 1.4 GB of WSL VM memory, and 119 MB of helper installation in an unrelated local distro. These extend the canonical's observed WSL initialization rather than establish a separate defect.
- **Confirmed mitigation, not resolution:** https://github.com/microsoft/vscode-remote-release/issues/11833#issuecomment-5627570620 confirms that setting dev.containers.executeInWSLDistro to a nonexistent distro avoids booting and provisioning the real distro, while remote container connection succeeds. Local wsl invocation still occurs, so the workaround does not deliver the requested behavior.
- **Setting semantics and regression caution:** https://github.com/microsoft/vscode-remote-release/issues/9194#issuecomment-1847422378 explains that executeInWSL controls Docker execution, while WSL connections also support service forwarding; https://github.com/microsoft/vscode-remote-release/issues/9194#issuecomment-1910299605 announces a separate forwarding control. The canonical already shows unwanted probing on 0.466.0, so the separate attach-hang downgrade report here does not establish that this WSL behavior began in 0.467.0.
