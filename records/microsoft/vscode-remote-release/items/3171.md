# Issue #3171 — Remote-WSL: node always running with high CPU usage

[https://github.com/microsoft/vscode-remote-release/issues/3171](https://github.com/microsoft/vscode-remote-release/issues/3171)

## Summary

Keep open: the original code-in-WSL launch steps suffice to retest excessive idle CPU usage, but current-release reproduction is unverified. File-watcher polling changed after the report; its fix and individual workarounds do not establish resolution of the later polling-disabled or tsserver reports.

## Change summary

Opening VS Code through `code .` in WSL causes sustained node CPU usage, battery drain, and, in later reports, slow IntelliSense.

## Best solution

The WSL component owner should isolate the hot server process and distinguish watcher, language-server, and distro-specific failures before tracking their fixes separately. If the remaining defect is in core language services, a maintainer can transfer that specific report to microsoft/vscode.

## Evidence

- **Reported trigger and remaining symptoms:** https://github.com/microsoft/vscode-remote-release/issues/3171 describes sustained >10% CPU after launching `code .` from Ubuntu WSL2, regardless of directory. September 2024 comments report recurrence with polling disabled on WSL1 Ubuntu 22.04.4; the January 2025 comment identifies tsserver at 90% CPU with approximately ten-second IntelliSense delays. These are historical reports, not verified reproductions on current releases.
- **Polling fix covers only part of the thread:** https://github.com/microsoft/vscode-remote-release/issues/4649#issuecomment-800420244 announces disabling Windows-mount polling by default in WSL extension 0.54.5; https://github.com/microsoft/vscode-remote-release/issues/4649#issuecomment-800426392 confirms improvement from roughly 60% to 15% CPU. That issue is closed and concerns a specific /mnt/c watcher case, not every failure reported here.
- **Workarounds are not a general resolution:** In https://github.com/microsoft/vscode-remote-release/issues/3171, some users improved after changing distributions, resetting Ubuntu, disabling built-in JavaScript/TypeScript support, or adjusting file watching. Other users explicitly report different behavior. The September 2024 maintainer request for the hot node processes' command lines remains unresolved: the supplied executable location does not identify which server subprocess is responsible.
- **Documented watcher limitation:** https://code.visualstudio.com/docs/remote/wsl#_known-limitations documents the performance impact of polling large workspaces and the remote.WSL.fileWatcher.pollingInterval and files.watcherExclude controls. These address polling costs, not the reported recurrence with polling disabled or all language-server CPU consumption.
- **Canonical search:** Open-issue searches for WSL CPU and high-CPU titles did not establish a canonical owning the full remaining defect. https://github.com/microsoft/vscode-remote-release/issues/2919 primarily tracks memory growth; https://github.com/microsoft/vscode-remote-release/issues/2353 links its diagnosed case to an Arch glibc compatibility problem; https://github.com/microsoft/vscode-remote-release/issues/3319 tracks a remote extension CPU-capping request with heterogeneous language-server reports. Shared node CPU symptoms alone do not establish shared root cause.
- **Related closure does not resolve this report:** https://github.com/microsoft/vscode-remote-release/issues/4892 is closed after its reporter said an automatic PC update eliminated their problem: https://github.com/microsoft/vscode-remote-release/issues/4892#issuecomment-825459256. That confirmation supplies neither a fixing release nor evidence resolving this issue's later reports.
