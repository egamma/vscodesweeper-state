# Issue #7397 — Fails to init dev container with usernamespaces enabled in docker.json

[https://github.com/microsoft/vscode-remote-release/issues/7397](https://github.com/microsoft/vscode-remote-release/issues/7397)

## Summary

Keep open: the reporter confirmed that --userns=host fixes container startup, but Docker's retained filesystem ownership remapping still prevents server initialization. This reopened report has no confirmed complete fix or verified same-symptom canonical.

## Change summary

Allow a Docker-in-Docker dev container to initialize successfully when the host Docker daemon enables userns-remap.

## Best solution

The containers owner should distinguish Docker's upstream ownership limitation from feasible integration improvements, including clearer diagnostics for incompatible privilege and namespace settings. Preserve the remaining server-installation failure here; do not automatically disable namespace isolation as a purported complete fix.

## Evidence

- **Privilege requirement identified:** https://github.com/microsoft/vscode-remote-release/issues/7397#issuecomment-1298157521 identifies the docker-in-docker feature as the source of --privileged and suggests runArgs: ["--userns=host"]. This is not an unexplained extension-added privilege requirement.
- **Workaround is incomplete:** https://github.com/microsoft/vscode-remote-release/issues/7397#issuecomment-1298292153 confirms startup succeeds with --userns=host, but the full log then fails to create /home/vscode/.vscode-server with Permission denied. https://github.com/microsoft/vscode-remote-release/issues/7397#issuecomment-1301184915 attributes the remaining failure to Docker retaining remapped filesystem UID/GID ownership.
- **Documented upstream limitation:** https://docs.docker.com/engine/security/userns-remap/#disable-namespace-remapping-for-a-container explicitly states that --userns=host disables process remapping but retains remapped filesystem ownership because image layers are shared. Its known-limitations section also documents that --privileged requires --userns=host when daemon remapping is enabled.
- **Related issue is not a verified canonical:** https://github.com/microsoft/vscode-remote-release/issues/9007 is open in Backlog and tracks userns-remap support, but its primary failure is chown: Invalid argument during UID/GID updating at build time, rather than this report's privileged startup followed by server-directory creation failure. Its broader discussion is relevant, but does not establish the same observable symptom required for a re-reviewed duplicate.
- **Rootless Docker is a distinct configuration:** https://github.com/microsoft/vscode-remote-release/issues/4646 is an older open report about bind-mounted workspace permissions under rootless Docker. This issue instead uses a rootful daemon with userns-remap and encounters remapped image-filesystem ownership after --userns=host; the older report does not own the full remaining failure.
- **Unresolved maintainer assessment:** https://github.com/microsoft/vscode-remote-release/issues/7397#issuecomment-1466495686 says the correct fix is uncertain, and https://github.com/microsoft/vscode-remote-release/issues/7397#issuecomment-1513354249 discusses possible upstream or privilege-reduction approaches. Neither confirms resolution after reopening.
