# Issue #7397 — Fails to init dev container with usernamespaces enabled in docker.json

[https://github.com/microsoft/vscode-remote-release/issues/7397](https://github.com/microsoft/vscode-remote-release/issues/7397)

## Summary

The initial startup failure has a documented workaround, but full compatibility remains blocked by Docker's user-namespace handling. The current docker-in-docker feature still requires privileged mode, so this remains valid upstream feature work rather than a Dev Containers extension bug.

## Change summary

Support the docker-in-docker Dev Container feature on Docker hosts using userns-remap without startup or filesystem-permission failures.

## Best solution

The docker-in-docker feature owner in https://github.com/devcontainers/features should determine whether the feature can support userns-remap safely or document the incompatibility and supported alternative; Docker owns the underlying remapped-filesystem behavior.

## Evidence

- **confirmed workaround:** The reporter confirmed that adding `"runArgs": ["--userns=host"]` allows the container to start, but Docker's remapped ownership then prevents creation of `/home/vscode/.vscode-server`.
- **Docker limitation:** https://docs.docker.com/engine/security/userns-remap/ documents that privileged containers require `--userns=host` and warns that shared image-layer ownership remains remapped, potentially breaking programs inside the container.
- **current feature behavior:** The current docker-in-docker feature metadata at https://github.com/devcontainers/features/blob/main/src/docker-in-docker/devcontainer-feature.json still declares `"privileged": true` and offers no user-namespace compatibility option.
- **canonical search:** https://github.com/microsoft/vscode-remote-release/issues/9007 covers UID/GID updating under userns-remap but not this report's broader docker-in-docker privileged-mode incompatibility, so it is not a canonical duplicate.
