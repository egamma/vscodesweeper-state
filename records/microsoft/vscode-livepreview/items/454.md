# Issue #454 — Live preview reloads on editor changes even when not visible

[https://github.com/microsoft/vscode-livepreview/issues/454](https://github.com/microsoft/vscode-livepreview/issues/454)

## Summary

Current source still sends reload notifications to every connected browser without checking whether the bundled preview panel is visible. The Integrated Browser default now sidesteps this path for most users, but the bundled browser remains supported behind `livePreview.useIntegratedBrowser: false`, and this team-authored issue has not been implemented or superseded.

## Change summary

Avoid reloading a bundled Live Preview webview while its editor tab is hidden, then bring it up to date when it becomes visible again.

## Best solution

Track the bundled `WebviewPanel` visibility and suppress or defer reloads for that panel while preserving reloads for visible previews and external browsers; perform one refresh when the panel becomes visible again. Coordinate the client-identification mechanism with https://github.com/microsoft/vscode-livepreview/issues/457, but retain this issue because #457 describes a broader injected-script architecture change rather than owning this specific observable defect.

## Evidence

- **current reload path:** On current main, src/updateListener.ts fires `shouldRefreshPreviews` for qualifying editor changes; src/manager.ts `_refreshBrowsers()` refreshes every server grouping; and src/server/wsServer.ts `refreshBrowsers()` sends a `reload` command to every connected WebSocket client without a visibility check.
- **hidden webview remains active:** src/editorPreview/previewManager.ts creates the bundled preview with `retainContextWhenHidden: true`, while neither that file nor src/editorPreview/browserPreview.ts registers `onDidChangeViewState` or checks `WebviewPanel.visible`; the hidden preview therefore remains connected and receives broadcast reloads.
- **related implementation work:** Open issue https://github.com/microsoft/vscode-livepreview/issues/457 explicitly cites this report and proposes making the injected script aware of whether it belongs to an embedded panel. It is a broader mechanism covering console initialization and client awareness, so landing it would not necessarily implement the required visibility lifecycle unless #454 remains an explicit acceptance condition.
- **current product surface:** package.json now defaults `livePreview.useIntegratedBrowser` to true, but the bundled browser and its hidden-panel behavior remain available when that setting is false; changing the default did not fix this code path.
