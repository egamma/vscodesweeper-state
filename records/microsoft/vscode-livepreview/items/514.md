# Issue #514 — Add custom field for browser path

[https://github.com/microsoft/vscode-livepreview/issues/514](https://github.com/microsoft/vscode-livepreview/issues/514)

## Summary

Keep this accepted request open: current settings cannot select a browser executable by path, and maintainers explicitly consolidated requests for alternate browser editions here. No verified open canonical or implementing PR supersedes it.

## Change summary

Allow external previews to launch a user-specified browser executable, including alternate editions such as Edge Dev.

## Best solution

Support an explicit browser executable path through the extension's external-preview configuration and launch flow, preserving existing named-browser and system-default behavior when unused. Establish how that path interacts with the browser selector; debug-browser selection remains separate work tracked at https://github.com/microsoft/vscode-livepreview/issues/422.

## Vision fit

- **Fit:** aligned
- **Reason:** Choosing a specific external browser extends an established preview workflow without expanding the bundled browser or turning Live Preview into an application server.
- **Evidence:** The durable theme 'Where the preview opens' explicitly includes the custom external browser and external-browser preview.

## Plan brief

- **Likely files:** `package.json`, `package.nls.json`, `src/utils/settingsUtil.ts`, `src/utils/externalBrowserUtils.ts`, `src/editorPreview/previewManager.ts`, `src/editorPreview/browserPreview.ts`, `src/test/suite/common.ts`, `src/test/suite/preview.test.ts`
- **Validation:** Extend the external-preview cases in src/test/suite/preview.test.ts and add launcher-level checks, run through npm test, to verify the selected executable receives the preview URL, paths containing spaces remain intact, and existing named/default browser behavior is unchanged when no path is configured. Manually verify a desktop non-debug preview opens an installed alternate browser edition and reports an invalid executable path clearly.
- **Behavior:**

  > Users should be able to open a non-debug external preview in a specific installed browser by supplying its executable path, including an alternate edition alongside the standard browser. With no path configured, existing Edge, Chrome, Firefox, and system-default choices must retain their behavior. Acceptance checks should cover the preview command and the bundled preview's open-in-browser action, an executable path containing spaces, and an invalid executable path. Changing embedded-browser behavior or debug-browser selection is outside this request.
- **Trace:**

  > package.json exposes only a four-value livePreview.customExternalBrowser enum, mirrored by CustomExternalBrowser and SettingUtil.GetConfig in src/utils/settingsUtil.ts. PreviewManager.launchFileInExternalBrowser in src/editorPreview/previewManager.ts sends non-debug launches to ExternalBrowserUtils.openInBrowser; the bundled preview's action in src/editorPreview/browserPreview.ts also calls that helper. The helper delegates desktop named-browser launches to js-debug-companion.launch with browserType and URL, while default and non-desktop launches use vscode.env.openExternal. This proves the missing extension configuration and argument plumbing, but the delegated launcher's ability to accept a specific executable has not been established. Existing preview tests stub the helper and check named-browser forwarding, so they do not validate executable selection inside the launcher. Preserve debugLink dispatch and non-desktop behavior; https://github.com/microsoft/vscode-livepreview/issues/422 owns the separate debug-selection request. Maintainer confirmation of the intended path field is at https://github.com/microsoft/vscode-livepreview/issues/523#issuecomment-1612264269.
- **Open decisions:**
  - Should a configured executable path override the existing named-browser selection, or should users explicitly select a Custom option to activate it?

## Evidence

- **Existing capability does not cover the request:** package.json restricts livePreview.customExternalBrowser to Edge, Chrome, Firefox, and Default. package.nls.json describes it as desktop-only, non-debug selection. No contributed setting or command accepts an external browser executable path; choosing Default delegates to the system browser rather than selecting an independent installation.
- **Current launch flow:** src/utils/settingsUtil.ts models CustomExternalBrowser as the same four choices. PreviewManager.launchFileInExternalBrowser in src/editorPreview/previewManager.ts passes that selection to ExternalBrowserUtils.openInBrowser; src/utils/externalBrowserUtils.ts delegates named browsers to js-debug-companion.launch with browserType and URL only, with no executable-path argument.
