# Issue #665 — !doctype is case-sensitive

[https://github.com/microsoft/vscode-livepreview/issues/665](https://github.com/microsoft/vscode-livepreview/issues/665)

## Summary

Current source still matches DOCTYPE case-sensitively, allowing the injected script to precede a lowercase declaration and change document rendering when no earlier insertion target matches. Keep this accepted bug open; an existing injection-reliability PR includes a candidate correction but has not merged.

## Change summary

Lowercase and uppercase HTML doctype declarations should produce equivalent rendering after Live Preview injects its reload script.

## Best solution

Preserve the document's standards-mode declaration regardless of its casing in src/server/serverUtils/contentLoader.ts. Review https://github.com/microsoft/vscode-livepreview/pull/746 as a candidate vehicle: its case-insensitive doctype matching addresses this path, but coverage of this report should be verified before landing.

## Evidence

- **Current case-sensitive injection:** src/server/serverUtils/contentLoader.ts:58 lists insertion targets as ['head', 'body', 'html', '!DOCTYPE']; _injectIntoFile at lines 359–392 constructs each regex with only the 'g' flag. When no head/body/html target matches, <!doctype html> is missed and the script is prepended, whereas <!DOCTYPE html> is matched and the script follows it. This establishes the case-dependent defect from source, without executing the preview.
- **Server-owned behavior:** ContentLoader.loadFile reads both open HTML documents and injectable files from disk through _injectIntoFile (src/server/serverUtils/contentLoader.ts:300–336). The changed document reaches whichever browser displays it; switching to the Integrated Browser does not correct the server's insertion ordering.
- **Open implementation candidate:** https://github.com/microsoft/vscode-livepreview/pull/746 is currently open. Its diff replaces the insertion-target loop with a preamble scan containing consume(/<!DOCTYPE\s[^>]*>/iy), explicitly matching the declaration case-insensitively. It references the comment-injection issue rather than this issue and is not a landed fix.
