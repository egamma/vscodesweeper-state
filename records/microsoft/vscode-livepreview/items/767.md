# Issue #767 — livepreview doesn't support proxy when vscode is using socks5h:// as proxy

[https://github.com/microsoft/vscode-livepreview/issues/767](https://github.com/microsoft/vscode-livepreview/issues/767)

## Summary

CDN resources are fetched by VS Code's browser or webview network stack rather than Live Preview's local server, so SOCKS5H proxy compatibility likely belongs to VS Code core. Keep this open until the preview implementation and current-version behavior are confirmed.

## Change summary

Allow pages shown in Live Preview to load CDN scripts when VS Code's `http.proxy` uses a `socks5h://` URL.

## Best solution

Confirm the behavior on current VS Code with both values of `livePreview.useIntegratedBrowser`, then route the networking defect to the corresponding VS Code core browser or webview component. Live Preview should continue serving the local page and should not implement a separate proxy for page subresources.

## Evidence

- **current preview path:** `src/editorPreview/previewManager.ts` hands the local URL directly to VS Code's Integrated Browser when `livePreview.useIntegratedBrowser` is enabled; `package.json` and `src/utils/settingsUtil.ts` show that this setting currently defaults to true.
- **legacy preview path:** `src/editorPreview/webviewComm.ts` loads the served page in an iframe inside a VS Code webview. The extension contains no proxy handling for CDN requests made by that page, so those requests use the webview host's network stack.
- **missing reproduction details:** The report does not provide the Live Preview or VS Code version, OS, `livePreview.useIntegratedBrowser` value, CDN URL, console/network error, or a minimal page demonstrating the failure.
- **related platform behavior:** VS Code previously tracked `socks5h://` support for `http.proxy` in https://github.com/microsoft/vscode/issues/158669; a later comment reports `net::ERR_NO_SUPPORTED_PROXIES`, but that closed issue is not a valid duplicate canonical for this report.
