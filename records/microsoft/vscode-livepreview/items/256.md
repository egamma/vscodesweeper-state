# Issue #256 — Consider changing default time for server to turn off to be instant

[https://github.com/microsoft/vscode-livepreview/issues/256](https://github.com/microsoft/vscode-livepreview/issues/256)

## Summary

The requested immediate-shutdown default remains unimplemented: the setting still defaults to three minutes, and zero explicitly means keep running indefinitely. This team-authored Backlog request needs a lifecycle and compatibility decision, not an as-designed close.

## Change summary

Consider stopping the server immediately when the embedded preview closes instead of retaining it for three minutes by default.

## Best solution

Decide the default server lifetime after closing an embedded preview while preserving an explicit keep-running option and servers still needed by other previews or tasks. Address the extension-owned lifecycle in src/editorPreview/previewManager.ts and src/manager.ts, accounting for the Integrated Browser path, which currently bypasses the bundled preview's disposal timer.

Verify Integrated Browser closure separately if included in scope.
- **Behavior:**

  > Closing an embedded preview currently leaves its server occupying ports, and this request asks whether immediate shutdown should become the default. Zero currently means keep running indefinitely, so setting it to zero does not provide the requested behavior. Acceptance should establish the chosen default, retain a documented way to keep serving, and avoid stopping servers that remain in use. The decision must specify whether the behavior applies to both embedded browser implementations.
- **Trace:**

  > package.json sets livePreview.serverKeepAliveAfterEmbeddedPreviewClose to three minutes; package.nls.json documents zero as indefinite. PreviewManager._startEmbeddedPreview in src/editorPreview/previewManager.ts schedules expiration from the bundled BrowserPreview disposal event only for nonzero values and cancels an existing timer when starting another bundled preview. The expiration callback in src/manager.ts closes all servers only under additional workspace and task conditions. The Integrated Browser branch of launchFileInEmbeddedPreview returns before installing this disposal machinery, so current default-browser closure tracking is an unresolved boundary rather than an implemented capability. https://github.com/microsoft/vscode-livepreview/issues/195 documents reliance on zero retaining the server. Preserve active external-preview and task use cases; file serving, response headers, and reload injection are outside this request.
- **Open decisions:**
  - Should immediate shutdown replace the three-minute default, and how should users select immediate, delayed, and indefinite operation without silently changing existing zero-valued configurations?
  - Should the new default apply to both the Integrated Browser and bundled preview, and which remaining preview or task consumers should prevent automatic shutdown?

## Evidence

- **Existing capability does not cover the request:** package.json contributes.configuration declares livePreview.serverKeepAliveAfterEmbeddedPreviewClose with default 3, minimum 0, and maximum 20. package.nls.json explicitly defines zero as keeping the server running indefinitely. The livePreview.end command provides manual Stop Server, not immediate automatic shutdown on preview closure.
- **Current bundled-preview lifecycle:** src/editorPreview/previewManager.ts:233-246 reads the keep-alive setting on BrowserPreview disposal and schedules _serverExpired only when the value is nonzero, using the configured number of minutes. Changing the default to zero alone would disable expiration rather than implement this request.
- **Shutdown eligibility and browser boundary:** src/manager.ts supplies an expiration callback that additionally requires running servers, no running logging task, an open workspace, and runTaskWithExternalPreview enabled before calling closeAllServers. PreviewManager.launchFileInEmbeddedPreview returns after invoking the Integrated Browser command, before registering the bundled panel's disposal listener; its lifecycle cannot be assumed to match the legacy timer.
