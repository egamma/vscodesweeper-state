## Evidence

- **Confirmed preview failure, not merely command confusion:** In https://github.com/microsoft/vscode-livepreview/issues/561, jtmcdole explicitly confirmed using Show Preview (Internal Browser), reproduced with every other extension disabled, and could load 127.0.0.1:3000 manually. This distinguishes the report from the maintainer's explanation that Start Server Logging alone does not open a preview.
- **Recovery did not resolve all reports:** The original reporter said the problem disappeared on 2023-11-29, but jtmcdole subsequently confirmed the internal-preview failure on Windows 11 with VS Code 1.84.2 and Live Preview 0.4.11. Elrendio reported the same external-working/internal-failing symptom on NixOS on 2025-10-14. These are thread-confirmed reproductions, not a reproduction performed against current main.
- **Task status is not proof that HTTP never started:** src/task/serverTaskTerminal.ts emits "Opening Server..." from ServerTaskTerminal.open(); its later status text comes from serverStarted(). In src/server/serverGrouping.ts, connection.onConnected drives both the task's started notification and pending preview launches. A reachable HTTP server therefore does not by itself establish that the complete readiness and preview-launch sequence finished.
- **Current browser boundary:** src/editorPreview/previewManager.ts: PreviewManager.launchFileInEmbeddedPreview delegates to the Integrated Browser command when SettingUtil.shouldUseIntegratedBrowser() succeeds; otherwise it retains the bundled webview creation path. src/utils/settingsUtil.ts checks both livePreview.useIntegratedBrowser and command availability. This changed default path does not prove that the historical launch failure was fixed.
- **Canonical search:** GitHub searches for "Opening Server" and open reports combining preview/nothing or internal/external found https://github.com/microsoft/vscode-livepreview/issues/731 and https://github.com/microsoft/vscode-livepreview/issues/815. The former is an undiagnosed macOS launch failure; the latter specifically concerns a remote port conflict. Neither establishes the same root cause as this report, where the HTTP server was reachable, so neither is a verified duplicate canonical.
