# Issue #741 — live preview not working

[https://github.com/microsoft/vscode-livepreview/issues/741](https://github.com/microsoft/vscode-livepreview/issues/741)

## Summary

Several reporters receive the same non-loopback bind failure and then lose the Live Preview status-bar control, but the environment and server logs needed to distinguish an unavailable local address from a fallback-startup defect are missing. Because this concerns exposing the server on a non-loopback interface, it should remain open for maintainer review rather than receive a routine needs-info close.

## Change summary

Starting Live Preview with a private-network `livePreview.hostIP` reports that the address cannot host the server, falls back to 127.0.0.1, and leaves no Live Preview status-bar button.

## Best solution

Confirm that the configured address belongs to an active network interface on the host running the extension, then determine from the server log whether the HTTP or WebSocket listener raises `EADDRNOTAVAIL` and whether the retry on 127.0.0.1 succeeds. If fallback succeeds, the status indicator should be shown; otherwise the retry and status-notification path in `src/server/` and `src/server/serverUtils/statusBarNotifier.ts` needs correction, while non-loopback hosting should retain appropriate safety constraints.

## Evidence

- **bind failure path:** `src/server/httpServer.ts` handles `EADDRNOTAVAIL` by calling `Connection.resetHostToDefault()` and retrying `listen` with the default host; `src/server/wsServer.ts` has the corresponding WebSocket fallback.
- **exact warning source:** `src/connectionInfo/connection.ts` emits the reported message only when resetting a non-default host to 127.0.0.1, showing that the configured IPv4 address passed format validation but the operating system rejected it as unavailable.
- **missing status indicator:** `src/server/serverUtils/statusBarNotifier.ts` initially hides the Live Preview status item and shows it only through `setServer`, so the missing indicator suggests that startup did not reach the successful server-connected path after fallback.
- **multiple reports, incomplete environment:** The issue has several independent comments reporting private addresses such as 192.168.1.17 and 192.168.2.109 plus a missing button, but none provides extension/VS Code versions, OS or remote context, confirmation that the address is assigned locally, or server logs.
- **security-sensitive configuration:** `livePreview.hostIP` controls the HTTP and WebSocket bind address; using a non-loopback address can make served workspace content reachable from other machines, so this report requires human review under the security-sensitive keep-open rule.
