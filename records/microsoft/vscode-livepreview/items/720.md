# Issue #720 — LiveServer Serving Old Version of File Despite Changes

[https://github.com/microsoft/vscode-livepreview/issues/720](https://github.com/microsoft/vscode-livepreview/issues/720)

## Summary

The report contains useful cross-client evidence that the server returned stale bytes, but current source does not maintain a persistent file-content cache and the exact trigger remains unclear. A current-version retest with the requested URL, server log, and file-editing state is needed to distinguish a stale open VS Code document from an old server or port still answering requests.

## Change summary

The Live Preview HTTP server sometimes returns an older version of an existing non-HTML file even after that file is changed and the server is restarted.

## Best solution

Determine whether `ContentLoader.getFileStream` is reading stale text from an open VS Code document or whether requests are reaching a previous server after port auto-increment. Once reproduced, add a server regression test that changes a served file and verifies that a subsequent request returns its latest content.

## Evidence

- **cross-client server symptom:** The reporter received the same old content through reqwest, curl with `Cache-Control: no-cache`, Simple Browser, and Firefox, making a single browser cache an unlikely explanation.
- **current serving path:** `src/server/serverUtils/contentLoader.ts` reads each request either from the matching entry in `vscode.workspace.textDocuments` via `getText()` or directly from disk via `fs.createReadStream`; it contains no persistent per-file response cache.
- **possible stale document source:** `ContentLoader.getFileStream` gives an open VS Code text document precedence over the filesystem, so whether the affected files were open or dirty and whether another program modified them is necessary to trace the reported stale bytes.
- **canonical search:** The related open report https://github.com/microsoft/vscode-livepreview/issues/748 specifically attributes stale browser content to a service worker. It does not own this report because service-worker caching would not explain stale responses in curl and reqwest.
