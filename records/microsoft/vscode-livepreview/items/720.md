# Issue #720 — LiveServer Serving Old Version of File Despite Changes

[https://github.com/microsoft/vscode-livepreview/issues/720](https://github.com/microsoft/vscode-livepreview/issues/720)

## Summary

The report provides strong evidence that stale data came from Live Preview's HTTP server rather than a browser cache, but the condition selecting the old content is not reproducible from the available details. Current source can serve an open VS Code document's in-memory text instead of rereading its file, so targeted current-version reproduction information is needed.

## Change summary

Some files that existed when the server first started continue returning old content over HTTP after edits and server restarts, while newer files return their current contents.

## Best solution

Reproduce with current Live Preview while comparing files open and closed in VS Code and edits made inside versus outside the editor. If the stale response follows an open text document, adjust `ContentLoader.getFileStream` in `src/server/serverUtils/contentLoader.ts` so saved filesystem-backed resources cannot remain pinned to stale editor contents, with regression coverage for repeated requests after a file update.

## Evidence

- **server-side symptom:** The reporter received the old bytes through reqwest, curl, Simple Browser, and Firefox, including curl with `Cache-Control: no-cache`; this makes a cache confined to one browser unlikely.
- **current source path:** `src/server/serverUtils/contentLoader.ts` implements `ContentLoader.getFileStream` by first matching the requested path against `vscode.workspace.textDocuments` and serving `TextDocument.getText()`; it calls `fs.createReadStream(readPath)` only when no matching open document is found.
- **no server content cache found:** `src/server/httpServer.ts` calls `getFileStream` for each ordinary file request, and current source contains no response-body cache, ETag handling, or 304 path that directly explains content remaining frozen across a restart.
- **related issue is not canonical:** https://github.com/microsoft/vscode-livepreview/issues/748 specifically attributes stale content to a service worker cache. That mechanism does not fully own this report because the reporter also reproduced the stale response with curl.
- **confirmation lacks diagnostics:** The later commenter says they saw the same problem but provides no extension or VS Code version, file-editing workflow, request URL, settings, logs, or minimal reproduction.
