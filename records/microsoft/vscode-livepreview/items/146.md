# Issue #146 — Changing the port breaks reloading

[https://github.com/microsoft/vscode-livepreview/issues/146](https://github.com/microsoft/vscode-livepreview/issues/146)

## Summary

The WebSocket using port 81 when the configured HTTP port is 80 is intentional, but the reported silent failure when that adjacent port is unavailable is a current server defect already owned by the broader, open https://github.com/microsoft/vscode-livepreview/issues/262.

## Change summary

Changing the HTTP port can leave live reload disconnected when the adjacent WebSocket port cannot be opened, without surfacing a useful error.

## Best solution

Consolidate this reproduction into https://github.com/microsoft/vscode-livepreview/issues/262 and fix the WebSocket startup path there: select an available WebSocket port, attach all connection/error/listening handlers on every retry, and inject the URI of the port that actually started.

- **Proposed comment:**

  > Thanks for the report and the detailed reproduction. The configured `livePreview.portNumber` is the HTTP port, while Live Preview intentionally starts its reload WebSocket on the following port, so port 81 is expected when the page is served on port 80. The real issue is that Live Preview does not correctly handle or report that WebSocket port being unavailable; that broader startup defect is tracked in https://github.com/microsoft/vscode-livepreview/issues/262. This example of changing the HTTP port to 80 and then seeing the injected client fail on 81 should be retained there, so this issue can be closed as a duplicate.

## Evidence

- **canonical issue:** The open https://github.com/microsoft/vscode-livepreview/issues/262 explicitly tracks that the server checks only the HTTP port before assigning the following port to the WebSocket server. Resolving that issue would fully address this report's failed reload connection without separate work.
- **maintainer diagnosis:** The maintainer clarified in https://github.com/microsoft/vscode-livepreview/issues/146#issuecomment-1341830494 that live preview intentionally uses the configured port for HTTP and the following port for WebSocket, while confirming that the failed WebSocket connection and silent server failure remain defects.
- **current source:** In src/server/serverGrouping.ts, ServerGrouping.openServer checks for a free HTTP port and then starts WSServer on freePort + 1. In src/server/wsServer.ts, the EADDRINUSE branch increments connection.wsPort and constructs a replacement server but does not reattach the connection, error, or listening handlers, so startup cannot complete through the normal promise path.
- **injected URI:** src/server/serverUtils/HTMLInjector.ts replaces WS_URL using Connection.resolveExternalWSUri, so port 81 in the injected script is expected for HTTP port 80; the defect is failure to establish and report a working WebSocket endpoint, not failure to copy the HTTP port.
