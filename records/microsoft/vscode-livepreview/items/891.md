# Issue #891 — Feature Request: Open Live Preview as a Native VS Code Editor Tab

[https://github.com/microsoft/vscode-livepreview/issues/891](https://github.com/microsoft/vscode-livepreview/issues/891)

## Summary

Editor-area preview tabs, side-by-side placement, and live refresh already exist, but the requested independent previews are not delivered by the current preview-launch flow. Keep open for that remaining capability rather than closing the entire request as already supported.

## Change summary

Support movable, live-updating editor preview tabs, including multiple pages open independently.

## Best solution

Use VS Code's Integrated Browser for native editor layout and retain the extension's server-backed live refresh. Decide how Live Preview commands should open independent page tabs without unintentionally replacing another preview; the remaining integration work belongs in src/editorPreview/previewManager.ts, not a new bundled browser.

- **Behavior:**

  > The existing embedded preview already provides an editor-area, side-by-side view with live updates. The remaining goal is to keep two different served pages open in independent editor tabs without opening the second replacing the first. Acceptance should cover moving those tabs between editor groups and observing live updates in both. The behavior of repeated preview actions must be explicit so existing users are not surprised by tab replacement or proliferation.
- **Trace:**

  > PreviewManager.launchFileInEmbeddedPreview in src/editorPreview/previewManager.ts selects the Integrated Browser through SettingUtil.shouldUseIntegratedBrowser and invokes workbench.action.browser.open with openToSide: true and a page-independent reuseUrlFilter. The fallback reuses currentPanel and therefore also exposes only one extension-managed preview. package.json has no independent-preview action or setting, while README.md already documents editor preview and live refresh. Native browser tab layout belongs to microsoft/vscode; the remaining extension boundary is how preview commands request opening versus reuse. Do not expand the bundled browser or change serving, path handling, response headers, or reload-script behavior as part of this request. Core command behavior still needs an interactive check before implementation.
- **Open decisions:**
  - Should the existing Show Preview action retain its single-preview reuse behavior with a separate action for independent tabs, or should opening a different page create a separate tab by default?
