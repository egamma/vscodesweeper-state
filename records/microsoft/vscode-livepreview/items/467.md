# Issue #467 — Persistent status bar item to show when server is off also

[https://github.com/microsoft/vscode-livepreview/issues/467](https://github.com/microsoft/vscode-livepreview/issues/467)

## Summary

The optional persistent status-bar indicator accepted by the maintainer remains unimplemented: the current item is hidden whenever all servers are off. Keep this accepted Backlog request open; existing commands and notifications do not supply the requested always-visible entry point.

## Change summary

Offer an opt-in Live Preview status-bar item that remains visible when no server is running and makes server controls discoverable.

## Best solution

Provide the disabled-by-default persistent indicator discussed by the maintainer, while preserving the editor preview button and the minimal default status bar. Settle the indicator's click behavior and initial activation expectations before implementation, including how controls behave with multiple running servers.

- **Evidence:** The public vision identifies beginner approachability and server lifecycle/configuration as durable themes; the maintainer's disabled-by-default proposal preserves the small default surface.

## Plan brief

- **Likely files:** `src/server/serverUtils/statusBarNotifier.ts`, `src/utils/settingsUtil.ts`, `src/manager.ts`, `src/extension.ts`, `package.json`, `package.nls.json`, `src/test/suite/manager.test.ts`, `README.md`
- **Validation:** Add VS Code integration coverage with a stubbed vscode.window.createStatusBarItem to check default-hidden versus opted-in off-state visibility, transitions through one and multiple active servers, and the agreed command behavior; run through the existing npm test harness in an implementation session. In a fresh Extension Development Host window, verify the agreed startup visibility before any Live Preview command and confirm that the editor preview button retains its existing behavior.
- **Behavior:**

  > Users who opt in should have a discoverable Live Preview status-bar entry even when no server is running, with a clear distinction between stopped and running states. The default experience must remain unchanged, with no extra off-state item. Starting servers, stopping the final server, and using a multi-root workspace must leave the indicator accurate. The editor's preview button must remain a preview action, not become a server toggle.
- **Trace:**

  > StatusBarNotifier in src/server/serverUtils/statusBarNotifier.ts hides its item in the constructor through serverOff(), shows it in setServer(), and hides it again when removeServer() removes the final port. Its running-state action currently opens the Live Preview command palette, and src/manager.ts supplies connection and shutdown updates across workspace servers. package.json and package.nls.json expose no setting for persistent visibility; the showStatusBarItem entry in src/utils/settingsUtil.ts is an unused constant, not an existing capability. src/extension.ts creates Manager during extension activation, so visibility immediately after opening a window is a separate lifecycle question from retaining the item after a server stops. The accepted boundary is recorded at https://github.com/microsoft/vscode-livepreview/issues/467#issuecomment-1485375888: persistence is opt-in and the editor preview action is unchanged. No server-serving, browser-rendering, or port-forwarding changes are implicated.
- **Open decisions:**
  - Should the persistent item's click action retain the current command palette, directly start a preview when stopped, or offer explicit server controls, and what should a stop action mean when multiple workspace servers are running?
  - When persistence is enabled, must the item appear immediately in a newly opened VS Code window before any Live Preview command, or only after the extension has otherwise activated?

## Evidence

- **Maintainer-accepted scope:** https://github.com/microsoft/vscode-livepreview/issues/467#issuecomment-1485375888 explicitly accepts a persistent status-bar item disabled by default, while rejecting turning the editor preview button into a server toggle. The feature-request label and Backlog milestone reflect accepted, unscheduled work; a decline close would contradict this direction.
- **Current implementation still hides the off state:** In src/server/serverUtils/statusBarNotifier.ts, StatusBarNotifier's constructor calls serverOff(), serverOff() unconditionally calls _statusBar.hide(), and setServer() shows the item only after a server connects. removeServer() returns to the hidden state when the final server stops. _refreshBar() currently opens the Live Preview command palette rather than toggling a server.
- **Existing-capability check:** package.json contributes.configuration has no persistent-status-bar setting. livePreview.showServerStatusNotifications controls transient information messages, not persistent visibility; livePreview.start, livePreview.end, and livePreview.runServerLoggingTask provide commands rather than an always-visible off-state control. The showStatusBarItem constant in src/utils/settingsUtil.ts is neither contributed in package.json nor read by SettingUtil.GetConfig(), so it does not implement this request.
- **Canonical and implementation search:** GitHub searches for status-bar, status, and Go Live terminology found no verified open canonical owning this request; searching open items for 467 found no linked implementation PR. https://github.com/microsoft/vscode-livepreview/issues/269 is closed and concerns removal of the old visibility setting, not adding an off-state indicator; it cannot support a duplicate close.
- **Activation and multi-server boundary:** package.json declares activation events for restored previews and Live Preview tasks, with command activation also available through contributed commands; src/extension.ts creates Manager only during activation. src/manager.ts creates StatusBarNotifier and updates it through connection and shutdown events, while the notifier aggregates multiple workspace ports. Persistent visibility before the first command and the meaning of a one-click stop action therefore need explicit product expectations.
