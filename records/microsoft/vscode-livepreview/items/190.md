# Issue #190 — Make Live Preview work on the web

[https://github.com/microsoft/vscode-livepreview/issues/190](https://github.com/microsoft/vscode-livepreview/issues/190)

## Summary

Live Preview still cannot run as a web extension: the current manifest exposes only a Node entry point, rejects virtual workspaces, and the implementation depends directly on Node HTTP, filesystem, path, networking, and WebSocket APIs. This team-authored Backlog item remains the canonical product request for a distinct browser-compatible serving architecture.

## Change summary

Support static HTML, CSS, and JavaScript live previewing in vscode.dev and github.dev, potentially by serving files from VS Code's virtual filesystem through a Service Worker.

## Best solution

Keep the desktop Node server intact while prototyping a separate web-extension entry point that reads through `vscode.workspace.fs` and exposes static project resources to the preview through a Service Worker or an appropriate VS Code core browser surface. The prototype should first resolve URL mapping, live-refresh signaling, virtual-workspace support, and the security boundary before maintainers commit to the architecture.

## Vision fit

- **Fit:** aligned
- **Reason:** Browser-hosted static previewing supports the extension's beginner-focused plain HTML/CSS/JS workflow and its durable investment in remote and cloud environments.
- **Evidence:** The public vision describes beginners as a primary audience, identifies Remote and cloud environments as a durable theme, and defines the product promise as hosting a server to preview web projects; the issue deliberately limits its scope to static HTML/CSS/JS rather than turning Live Preview into an application server.

## Evidence

- **current manifest:** `package.json` declares only `main: "./out/extension.js"`, has no browser extension entry point, sets `capabilities.virtualWorkspaces` to `false`, and describes the unsupported capability as a consequence of running a server.
- **desktop-only architecture:** `src/server/httpServer.ts` imports Node's `http`, `fs`, `path`, and `stream`; `src/server/wsServer.ts` uses Node HTTP and the `ws` package; `src/server/serverUtils/contentLoader.ts` reads through Node filesystem and stream APIs. A web implementation therefore remains a substantial, distinct code path rather than an enabled setting.
- **accepted backlog intent:** A maintainer explicitly moved https://github.com/microsoft/vscode-livepreview/issues/190 to Backlog until implementation capacity became available, and another team member documented the education scenario it would enable. The issue is team-authored and contains no factual implementation or duplicate evidence supporting closure.
- **canonical search:** Open repository searches for `vscode.dev`, `github.dev`, `web extension`, and `virtual workspace` found no broader issue that would fully deliver this request. https://github.com/microsoft/vscode-livepreview/issues/560 concerns CORP headers for an already-running server in Codespaces, while https://github.com/microsoft/vscode-livepreview/issues/354 concerns Live Share participants; both require different mechanisms.
- **cross-repository relationship:** https://github.com/microsoft/vscode-edge-devtools/issues/989 tracks the Edge DevTools extension's own web compatibility and merely references Live Preview. Conversely, https://github.com/microsoft/vscode-remote-repositories-github/issues/355 was closed by pointing to https://github.com/microsoft/vscode-livepreview/issues/190, treating this issue as the Live Preview-side canonical.
