# Issue #448 — Allow query parameters in preview path setting

[https://github.com/microsoft/vscode-livepreview/issues/448](https://github.com/microsoft/vscode-livepreview/issues/448)

## Summary

Query-bearing preview targets remain unsupported by the default-path setting and the public string-path command. Keep this accepted feature request open: the maintainer suggested an address-taking command, but that interface has not been implemented and no verified canonical owns the same work.

## Change summary

Allow launching a locally served preview with query parameters through configuration or a command, including a convenient Show Preview workflow.

## Best solution

Provide an extension-owned launch interface that preserves query parameters independently of filesystem paths and uses the extension's resolved server address. Settle whether the proposed address-taking command alone meets the request or whether the default-path setting and Show Preview button also need query support.

## Vision fit

- **Fit:** aligned
- **Reason:** Supporting query-bearing launch targets improves the extension's server-backed preview workflow without adding browser-rendering functionality.
- **Evidence:** The durable themes include serving correctness through livePreview.defaultPreviewPath and configuring where previews open; the product promise combines a local server with an embedded or external preview.

## Plan brief

- **Likely files:** `src/extension.ts`, `src/manager.ts`, `package.json`, `package.nls.json`, `src/test/suite/manager.test.ts`
- **Validation:** Extend src/test/suite/manager.test.ts for the agreed public interface, then run the repository's VS Code integration suite with npm test in a writable implementation environment. Verify that launching page.html?mode=demo&value=a%20b opens the served page with its query intact, ordinary filename inputs retain their behavior, and the agreed embedded/external and Show Preview flows work. No tests were executed in this read-only checkout.
- **Behavior:**

  > A user should be able to launch a page served by Live Preview with query parameters without manually editing the browser address or relying on launch.json. The agreed interface must deliver the query as URL metadata rather than treating it as part of a filename. Acceptance should include multiple parameters, an encoded parameter value, and unchanged behavior for existing filename-only inputs. The maintainer must establish whether this capability also applies to the default preview setting and the Show Preview button.
- **Trace:**

  > src/extension.ts registers livePreview.start.preview.atFileString and forwards its string argument to Manager.openPreviewAtFileString() in src/manager.ts. Manager.openPreview() routes livePreview.defaultPreviewPath through that same method, which constructs file URIs with vscode.Uri.joinPath() or vscode.Uri.file(); it does not parse a query-bearing target. The private Manager._openPreviewAtLink() is not an equivalent public API and currently reconstructs targets from link.path. Existing manager tests in src/test/suite/manager.test.ts cover default-file and string-path launches but not query-bearing targets. The maintainer's proposed address-taking command is recorded at https://github.com/microsoft/vscode-livepreview/issues/448#issuecomment-1426428327. Preserve existing filename semantics, workspace/server-root selection, and served-file access boundaries; this request concerns launch metadata, not changes to what files the server may serve.
- **Open decisions:**
  - Should query-bearing targets be exposed only through a new address-taking command, or also through livePreview.defaultPreviewPath?
  - When Show Preview is invoked for the active file, should configured query parameters apply, and what user-facing configuration supplies them?

## Evidence

- **Maintainer-supported direction:** A maintainer explicitly accepted the use case and suggested a command analogous to livePreview.start.preview.atFileString, named atAddress: https://github.com/microsoft/vscode-livepreview/issues/448#issuecomment-1426428327. The reporter welcomed that alternative at https://github.com/microsoft/vscode-livepreview/issues/448#issuecomment-1426650133. The issue is already classified feature-request and parked in On Deck; a decline close would contradict that accepted direction.
- **Existing-capability check:** Read package.json contributes.configuration and contributes.commands, plus the defaultPreviewPath description in package.nls.json. livePreview.defaultPreviewPath remains documented as a file to open, and the contributed string-input command is livePreview.start.preview.atFileString; no atAddress command or query-parameter setting is present.
- **Current launch path:** In src/manager.ts, Manager.openPreview() passes defaultPreviewPath directly to openPreviewAtFileString(). That method uses vscode.Uri.joinPath() or vscode.Uri.file(), treating the supplied text as a filesystem path rather than separating its query component. In src/extension.ts, livePreview.start.preview.atFileString calls the same method, while the Show Preview command calls openPreviewAtFileUri(). Neither public entry point provides the requested query-bearing string interface.
- **Internal URL handling is not equivalent:** Manager._openPreviewAtLink() in src/manager.ts is a private handler for preview/task events, not a public address-taking command. Its conversion back to a served file uses link.path without carrying link.query, so its existence does not establish coverage of this request.
- **Canonical search:** GitHub searches for query parameters, query string, query, atAddress, and URL parameter found no verified open canonical for the same requested behavior. The maintainer-linked older issue https://github.com/microsoft/vscode-livepreview/issues/388 is closed and concerns accepting absolute or relative filenames as command arguments, not preserving query parameters; it is neither an eligible duplicate target nor coverage of this request.
