# Issue #660 — fragment/anchor in Uri is ignored when preview loose file

[https://github.com/microsoft/vscode-livepreview/issues/660](https://github.com/microsoft/vscode-livepreview/issues/660)

## Summary

The supplied command invocation still loses the URI fragment in current source: preview URL construction uses only file.fsPath for both loose files and workspace files. The Integrated Browser does not resolve this because the extension discards the anchor before handing it the URL.

## Change summary

Preserve a file URI's fragment when opening a preview through livePreview.start.preview.atFile so the page navigates to the requested anchor.

## Best solution

Preserve the requested anchor through URL construction in src/editorPreview/previewManager.ts for loose and workspace files, across Integrated Browser, bundled browser, and external preview launches. Keep filesystem endpoint resolution unchanged and ensure the Integrated Browser's tracking query remains before the fragment.

## Evidence

- **Concrete reproduction supplied:** https://github.com/microsoft/vscode-livepreview/issues/660 supplies a valid file:///home/quan/test.html#section2 URI passed to livePreview.start.preview.atFile; the page opens without navigating to section2. The follow-up also identifies the same loss for a workspace URI constructed with .with({ fragment: 'duration-prop' }).
- **Current source discards the fragment:** src/extension.ts forwards the URI to Manager.openPreviewAtFileUri. src/manager.ts preserves it through _handleOpenFile and _openPreview, and src/server/serverGrouping.ts forwards it to PreviewManager. In src/editorPreview/previewManager.ts, _fileUriToPath passes only file.fsPath to encodeLooseFileEndpoint or getFileRelativeToWorkspace and returns the resulting path without reading file.fragment. Both preview launch methods use that fragment-free result.
- **Default browser change does not fix this path:** PreviewManager.launchFileInEmbeddedPreview calls _fileUriToPath before choosing the Integrated Browser or bundled webview. Its Integrated Browser URL is built as http://host:port/path?vscode-livepreview=true, so the original fragment is already absent before VS Code core receives it. A correction must also preserve the query-before-fragment ordering.
- **Canonical search found related but distinct work:** GitHub searches for fragment, anchor, hash, and atFile found no verified open canonical for this command-input fragment loss. https://github.com/microsoft/vscode-livepreview/issues/587 is closed and concerns the address bar after clicking an in-page anchor. https://github.com/microsoft/vscode-livepreview/issues/658 is closed and concerns literal # characters in filenames. The open https://github.com/microsoft/vscode-livepreview/pull/857 targets filename encoding and references a different issue; its body does not reference this report or address preserving URI fragments.
- **Bounded validation surface:** src/test/suite/preview.test.ts already exercises PreviewManager launches using spies on WebviewComm.goToFile, ExternalBrowserUtils.openInBrowser, and vscode.commands.executeCommand. These provide executable assertions for anchor preservation without changing server endpoint authorization or filesystem path resolution.
