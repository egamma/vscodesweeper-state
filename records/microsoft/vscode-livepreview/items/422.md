# Issue #422 — `Live Preview: Show Debug Preview (External Browser)` doesn't respect `livePreview.customExternalBrowser`

[https://github.com/microsoft/vscode-livepreview/issues/422](https://github.com/microsoft/vscode-livepreview/issues/422)

## Summary

The requested capability remains missing: debug preview passes only the URL to js-debug, while non-debug preview reads livePreview.customExternalBrowser. Keep this accepted, team-authored feature request open; no verified canonical or implementing fix was found.

## Change summary

Make external debug previews honor the browser selected through livePreview.customExternalBrowser.

## Best solution

Extend the external debug-launch integration in src/editorPreview/previewManager.ts to honor browser selection while preserving debugger attachment. Establish the supported-browser and Default behavior with the maintainer, including what users should see when their selected browser cannot support the debug launch.

## Plan brief

- **Likely files:** `src/editorPreview/previewManager.ts`, `src/utils/externalBrowserUtils.ts`, `package.nls.json`, `src/test/suite/preview.test.ts`
- **Validation:** Extend src/test/suite/preview.test.ts to check the agreed debug-launch behavior for each browser selection, preserving URL construction and non-debug selection, and run through npm test in an implementation workspace. Manually verify that supported selected browsers launch with a working breakpoint and that unsupported or missing browsers produce the agreed user-visible outcome.
- **Behavior:**

  > External debug preview currently disregards livePreview.customExternalBrowser even though ordinary external preview follows it. The requested result is browser selection that remains effective when attaching the debugger. Acceptance must cover explicit browser selections and Default, preserve working debugger attachment, and define an honest user-visible outcome when the selected browser cannot be debugged.
- **Trace:**

  > PreviewManager.launchFileInExternalBrowser in src/editorPreview/previewManager.ts constructs the preview URL and splits into debug and non-debug launches. The debug branch calls extension.js-debug.debugLink with the URL alone; the non-debug branch reads customExternalBrowser and delegates to ExternalBrowserUtils.openInBrowser in src/utils/externalBrowserUtils.ts. That helper uses vscode.env.openExternal for Default and js-debug-companion.launch for named desktop browsers, but this is ordinary launch behavior, not evidence of debugger support. package.nls.json explicitly documents the non-debug restriction, and src/test/suite/preview.test.ts asserts both existing branches. Preserve server startup, URL resolution, ordinary external preview and embedded preview behavior. The uncertainty begins at the debugger's supported browser-selection interface and the product contract for Firefox and system-default browsers such as the Arc installation reported at https://github.com/microsoft/vscode-livepreview/issues/422; https://github.com/microsoft/vscode-livepreview/issues/506 is related launch-configuration work, not a canonical for this request.
- **Open decisions:**
  - What should debug preview do when the selected browser, including the system browser under Default, cannot support the debugger integration: stop with an actionable explanation, offer a supported browser, or use an explicitly disclosed fallback?

## Evidence

- **Existing-capability check:** package.json contributes livePreview.customExternalBrowser with Edge, Chrome, Firefox and Default choices, plus livePreview.debugOnExternalPreview and livePreview.start.externalDebugPreview.atFile. package.nls.json explicitly limits customExternalBrowser to normal, non-debug desktop previews; no existing setting or command covers the requested combination.
- **Current launch boundary:** src/editorPreview/previewManager.ts, PreviewManager.launchFileInExternalBrowser, invokes extension.js-debug.debugLink with only the URL when debug is true. Only its non-debug branch passes SettingUtil.GetConfig().customExternalBrowser to ExternalBrowserUtils.openInBrowser. This is an extension-side integration gap, not an Integrated Browser rendering issue.
- **Existing validation contract:** src/test/suite/preview.test.ts already asserts that non-debug preview passes CustomExternalBrowser.edge, while the debug test asserts a URL-only extension.js-debug.debugLink invocation. The tests document the current split rather than the requested browser-selection support.
- **Contemporaneous acknowledgment:** https://github.com/microsoft/vscode/issues/172075 explicitly lists this issue as a known limitation of custom external browser support. Its closed state does not establish that the limitation was fixed.
- **Reporter context:** The discussion on https://github.com/microsoft/vscode-livepreview/issues/422 reports that Default opens normally but debug launch fails to find a browser on macOS 13.5.1 with Arc. That is useful compatibility evidence, but does not establish current debugger support for Arc.

Both are newer and describe different observable problems.
