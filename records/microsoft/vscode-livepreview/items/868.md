# Issue #868 — [Feature Request] Allow Codex CLI to automatically start Live Preview for a specified HTML file

[https://github.com/microsoft/vscode-livepreview/issues/868](https://github.com/microsoft/vscode-livepreview/issues/868)

## Summary

Existing commands already preview a specified file beside the editor, but they do not establish the requested shell-to-VS-Code automation interface. Keep this request open: the earlier CLI discussion does not settle this distinct workflow, and no verified open canonical owns it.

## Change summary

Allow an external CLI to start or focus a side-by-side preview for a specified HTML file without opening its source editor, with clear failure feedback.

## Best solution

Decide whether to support a documented, tool-neutral external invocation interface that reuses the existing preview commands and defines target-window selection and failure reporting. This belongs primarily in the extension's command integration and Manager entry points, not in the Integrated Browser's rendering implementation.

## Evidence

- **Existing command partially covers the request:** package.json contributes livePreview.start.preview.atFileString, and src/extension.ts registers it with a string path argument, explicitly describing use by tasks or other extensions. CHANGELOG.md records its introduction in stable 0.4.5. This is a VS Code command, not a documented shell invocation interface.
- **Side-by-side preview already exists:** src/manager.ts: Manager.openPreviewAtFileString resolves the supplied path and calls openPreviewAtFileUri without requiring its source editor to be opened. src/editorPreview/previewManager.ts: launchFileInEmbeddedPreview passes openToSide: true and reuseUrlFilter to the Integrated Browser; the bundled browser creates or reveals its panel in ViewColumn.Beside.
- **External invocation and failure contract remain incomplete:** src/extension.ts activation registers VS Code commands but no URI handler for an external caller. Manager.openPreviewAtFileString warns when its filesystem lookup fails and then calls _openPreviewWithNoTarget, so the existing command does not establish the requested explicit failure contract for CLI automation. livePreview.defaultPreviewPath selects a startup file but does not provide an external invocation mechanism.
- **Prior task-based capability is not a canonical:** https://github.com/microsoft/vscode-livepreview/issues/388 is closed and documents invoking livePreview.start.preview.atFileString through tasks.json in https://github.com/microsoft/vscode-livepreview/issues/388#issuecomment-1400793551. That supplies an in-VS-Code invocation path, not the requested end-to-end external CLI workflow.
- **CLI precedent does not decline the full request:** https://github.com/microsoft/vscode-livepreview/issues/368 is closed. In https://github.com/microsoft/vscode-livepreview/issues/368#issuecomment-1853006717, a maintainer preferred existing tasks over a standalone executable but explicitly invited other CLI use cases. Its npm-script/server-logging scenario does not settle externally opening a particular file's preview beside the current editor with failure feedback.
- **Canonical search:** Repository searches for CLI, command line, automation, external tool, URI handler, and atFileString found the closed discussions https://github.com/microsoft/vscode-livepreview/issues/172, https://github.com/microsoft/vscode-livepreview/issues/368, and https://github.com/microsoft/vscode-livepreview/issues/388, but no verified open issue owning this request's remaining work.
