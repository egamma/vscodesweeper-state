# Issue #489 — Support Remote Repositories

[https://github.com/microsoft/vscode-livepreview/issues/489](https://github.com/microsoft/vscode-livepreview/issues/489)

## Summary

Remote Repositories remain explicitly unsupported on current main, and the server still assumes native filesystem paths throughout its workspace-content pipeline. This team-authored, On Deck feature request is the established canonical for that missing scenario and should remain open.

## Change summary

Allow Live Preview to serve and refresh HTML projects opened through virtual filesystems such as the GitHub Repositories extension, without requiring a local clone.

## Best solution

Add a URI-based workspace-content abstraction using `vscode.workspace.fs` while retaining native Node filesystem access for extension-owned assets, then remove `fsPath` and native `fs` assumptions from the serving, endpoint, path-resolution, and refresh paths before enabling virtual workspaces in `package.json`. Keep desktop Remote Repositories support scoped separately from the service-worker architecture proposed for browser-hosted VS Code in https://github.com/microsoft/vscode-livepreview/issues/190.

## Vision fit

- **Fit:** aligned
- **Reason:** Supporting virtual repository content extends the extension's core server-and-preview workflow to a remote/cloud environment without turning it into an application server or duplicating browser functionality.
- **Evidence:** The durable themes explicitly include serving correctness and remote/cloud environments, while the README promise is to host a local server for previewing web projects that do not already have a server.

## Evidence

- **explicitly unsupported on main:** `package.json` sets `capabilities.virtualWorkspaces` to `false`, so VS Code disables Live Preview in Remote Repositories and other virtual workspaces.
- **native filesystem dependency:** `src/utils/pathUtil.ts` resolves workspace resources through `Uri.fsPath`, `path.join`, `fs.promises.stat`, and `fs.promises.readFile`; `src/server/serverUtils/contentLoader.ts` additionally uses `fs.createReadStream`, `fs.statSync`, and `fs.readdir` for served workspace content.
- **URI assumptions extend across serving:** `src/manager.ts`, `src/infoManagers/endpointManager.ts`, `src/server/httpServer.ts`, and `src/server/wsServer.ts` represent served resources as native absolute paths, so changing only the final file read to `workspace.fs` would not deliver the requested behavior.
- **confirmed canonical:** A maintainer closed the later concrete Remote Repositories report https://github.com/microsoft/vscode-livepreview/issues/626 in favor of this issue, explicitly stating that support did not exist and progress would be tracked here.
- **related but distinct web work:** https://github.com/microsoft/vscode-livepreview/issues/190 tracks running Live Preview in vscode.dev/github.dev through a browser-compatible service-worker architecture; shipping that work would not necessarily make the existing Node HTTP server consume a Remote Repositories filesystem on desktop.
- **protected product decision:** The issue is authored by a repository member, carries the `feature-request` label, and is assigned to the `On Deck` holding milestone; there is no fixing commit or verified broader canonical that would support a factual close.
