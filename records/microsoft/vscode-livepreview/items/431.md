# Issue #431 — Show progress while external browser is starting

[https://github.com/microsoft/vscode-livepreview/issues/431](https://github.com/microsoft/vscode-livepreview/issues/431)

## Summary

External-browser launch still has no progress feedback while the browser starts loading the page. This team-authored Backlog request remains actionable: no existing setting covers it, and no implementing fix or qualifying canonical was found.

## Change summary

Show progress in VS Code between issuing an external-preview command and the browser reaching the Live Preview server.

## Best solution

Provide external-launch progress through the command and preview lifecycle in src/manager.ts and src/editorPreview/previewManager.ts, using the server's request events as a possible completion signal. Establish the completion and timeout behavior so unrelated requests or a browser that never connects do not produce misleading or indefinite progress.

## Plan brief

- **Likely files:** `src/manager.ts`, `src/editorPreview/previewManager.ts`, `src/utils/externalBrowserUtils.ts`, `src/server/serverGrouping.ts`, `src/test/suite/preview.test.ts`
- **Validation:** Extend the VS Code integration suites with a delayed external-launch scenario: progress is visible before the simulated browser request and ends at the agreed completion signal. Cover an already-running server, unrelated requests, and a browser that never connects; run the new cases through npm test in an implementation workspace.
- **Behavior:**

  > When an external-preview command takes several seconds to bring up a page, VS Code should show that the operation is still in progress rather than appear idle. Feedback should cover both a newly started browser and navigation in an already-running browser. Acceptance checks should exercise delayed arrival, an already-running server, and a launch that never reaches the server, with progress ending according to the agreed contract.
- **Trace:**

  > Manager._openPreview delegates external preview to ServerGrouping.showPreviewInExternalBrowser, and Manager._getServerGroupingFromWorkspace wires the launch event to PreviewManager.launchFileInExternalBrowser. That method dispatches either extension.js-debug.debugLink or ExternalBrowserUtils.openInBrowser; neither path tracks the browser's arrival. HttpServer.onNewReqProcessed is relayed by ServerGrouping.onNewReqProcessed for logging, providing a possible signal but not proof of page readiness or request attribution. The current preview tests in src/test/suite/preview.test.ts cover normal and debug launch dispatch, not progress. Preserve browser selection, debugger behavior, embedded preview, and server access controls; this request requires no changes to file-serving policy, response headers, or injected scripts. The older https://github.com/microsoft/vscode-livepreview/issues/402 concerns invalid-URL feedback and is related but does not own this work.
- **Open decisions:**
  - Should progress end on the next request to the selected server, as suggested in the issue, or only on a request matching the launched page when other clients may already be connected?
  - If no qualifying request arrives, should progress expire quietly after a bounded interval or end with a user-visible launch warning?
