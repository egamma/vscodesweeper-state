# Issue #354 — Feature request: support viewing of shared Live Share servers in the Live Preview embedded browser

[https://github.com/microsoft/vscode-livepreview/issues/354](https://github.com/microsoft/vscode-livepreview/issues/354)

## Summary

Live Share guests still lack the requested integration: current main explicitly disables Live Preview in virtual workspaces, and switching to the Integrated Browser does not remove that restriction. Keep this accepted Backlog request open; no verified older canonical owns the same guest-preview workflow.

## Change summary

Allow Live Share participants to preview the host's shared Live Preview server inside VS Code.

## Best solution

Design a guest preview workflow that uses the host's shared server without requiring guests to serve virtual workspace files themselves, preferably using VS Code's Integrated Browser. Establish how shared server addresses become available to the guest and which preview actions should be supported before changing the virtual-workspace capability declaration.

## Plan brief

- **Likely files:** `package.json`, `package.nls.json`, `src/manager.ts`, `src/editorPreview/previewManager.ts`, `src/connectionInfo/connectionManager.ts`, `src/connectionInfo/connection.ts`, `src/server/serverGrouping.ts`
- **Validation:** Use a two-client Live Share session: start Live Preview on the host, share its server, join as a guest, and open the shared page inside VS Code. Verify host edits refresh the guest preview, the guest does not start a replacement file server, closing the guest preview leaves the host server running, and normal host preview commands retain their behavior.
- **Behavior:**

  > A Live Share participant should be able to view the host's shared Live Preview server inside VS Code rather than being blocked by the guest's virtual workspace. The preview should display the host-served page and receive live refreshes from host edits. Guest preview actions must not require a second server serving the virtual workspace or stop the host's server when the guest closes the preview.
- **Trace:**

  > package.json explicitly declares virtualWorkspaces: false, so the requested guest integration remains unavailable. The existing command surface is file/server oriented: src/manager.ts _openPreviewAtLink resolves links against registered local connections and falls back to a file-path opener for unknown ports. src/server/serverGrouping.ts createOrShowEmbeddedPreview starts its own server if necessary, and src/editorPreview/previewManager.ts launchFileInEmbeddedPreview constructs a URL from that owned Connection before selecting the Integrated Browser or bundled browser. src/connectionInfo/connection.ts uses asExternalUri for its own endpoints, but the inspected code contains no Live Share-specific guest-server discovery. The design boundary is consuming an already shared server, not widening filesystem serving or changing host lifecycle and exposure. Uncertainty begins at the guest activation contract and how the guest obtains the shared server address; the Integrated Browser is a rendering destination, not proof of this integration. Related https://github.com/microsoft/vscode-livepreview/issues/716 describes the virtual-workspace restriction but does not own this feature.
- **Open decisions:**
  - Should guest support provide only an explicit action to open an already shared server, or should previewing a file in the shared workspace automatically select the host's server?
  - Should the guest workflow require the Integrated Browser, or also support the extension's bundled browser when livePreview.useIntegratedBrowser is false?

## Evidence

- **Guest activation remains blocked:** package.json capabilities.virtualWorkspaces is still false. The issue explicitly identifies this restriction as preventing Live Share participants from using the extension; no existing setting overrides the capability declaration.
- **Existing capabilities do not cover the request:** Read package.json contributes.commands and contributes.configuration together with package.nls.json. livePreview.openPreviewTarget and livePreview.useIntegratedBrowser select the preview surface, while the contributed preview commands target files and locally managed servers; none provides a Live Share guest/shared-server workflow.
- **Preview lifecycle assumes an owned server:** src/server/serverGrouping.ts createOrShowEmbeddedPreview calls openServer when its grouping is not running. src/editorPreview/previewManager.ts launchFileInEmbeddedPreview receives a Connection and constructs its Integrated Browser URL from that connection's host, HTTP port, and file path. Changing the browser default therefore does not implement guest access.
- **URL handling is not shared-server adoption:** src/manager.ts _openPreviewAtLink looks up an existing connection by port and, when none exists, falls back to openPreviewAtFileString(link.path, previewType). src/connectionInfo/connection.ts resolves externally reachable addresses for its own connection using vscode.env.asExternalUri; these paths do not establish a Live Share guest connection.
