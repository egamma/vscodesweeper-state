# Issue #354 — Feature request: support viewing of shared Live Share servers in the Live Preview embedded browser

[https://github.com/microsoft/vscode-livepreview/issues/354](https://github.com/microsoft/vscode-livepreview/issues/354)

## Summary

The requested Live Share guest workflow remains unsupported on current main: the extension still disables itself in virtual workspaces, and its preview path assumes that it can start a server and access workspace files through local filesystem paths. No open issue was found that more specifically owns this integration, so this remains a valid feature request.

## Change summary

Allow Live Share participants to view a host's shared Live Preview server inside an embedded preview without running their own local server.

## Best solution

Add a guest-safe preview path that consumes the host's Live Share shared-server URL without attempting to serve the guest's virtual workspace, preferably opening that URL through VS Code's Integrated Browser. The implementation boundary and any required Live Share API integration need maintainer design, while the existing host-side server behavior should remain unchanged.

- **Evidence:** The vision identifies remote and cloud environments as a durable theme and says to build on core platform surfaces, with the server remaining the extension's product while browser rendering increasingly belongs to VS Code.

  > Thanks for the feature request. This is still a real gap on current `main`: Live Preview declares `virtualWorkspaces: false`, and its current preview flow assumes it can access workspace files through local filesystem paths and start its own server. The newer `livePreview.useIntegratedBrowser` setting changes where that locally served URL opens, but it does not let a Live Share guest consume the host's shared-server URL. A suitable implementation would keep the server on the host and add a guest-side path that opens the shared URL through VS Code's Integrated Browser without trying to serve the virtual workspace.

## Evidence

- **capability remains disabled:** Current package.json still declares `capabilities.virtualWorkspaces: false`, so Live Preview is not activated for a Live Share guest's virtual workspace.
- **filesystem-dependent server path:** Current source relies extensively on local filesystem paths: `src/utils/pathUtil.ts` resolves workspaces through `workspace.uri.fsPath` and Node `path`/`fs`, while `src/server/serverUtils/contentLoader.ts#getFileStream` reads content with `fs.createReadStream`, `fs.statSync`, and `PathUtil.FileRead`. Enabling virtual workspaces alone would therefore not implement the requested workflow.
- **preview remains coupled to an owned server:** `src/server/serverGrouping.ts#createOrShowEmbeddedPreview` starts this extension's server before launching a preview, and `src/editorPreview/previewManager.ts#launchFileInEmbeddedPreview` builds the Integrated Browser URL from the extension's own `Connection` host and port. There is no Live Share or shared-server URL integration in the current source.
- **canonical search:** Repository searches found no separate open issue that owns shared Live Share server viewing. https://github.com/microsoft/vscode-livepreview/issues/716 is a later general question about the virtual-workspace warning, not a broader implementation request that would fully satisfy this issue.
- **existing capability check:** `livePreview.useIntegratedBrowser` changes which embedded browser opens after Live Preview starts its own server; it does not let a disabled guest instance consume a host's Live Share shared-server URL, so it is not existing coverage of the central request.
