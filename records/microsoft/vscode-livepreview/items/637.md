# Issue #637 — Problem with "charset=ISO-8859-1"

[https://github.com/microsoft/vscode-livepreview/issues/637](https://github.com/microsoft/vscode-livepreview/issues/637)

## Summary

The Latin-1 corruption remains reproducible from current source: injectable HTML is unconditionally decoded as UTF-8, re-encoded as UTF-8, and served with a UTF-8 response header. This is a confirmed server-side encoding bug and should remain open.

## Change summary

Serve ISO-8859-1 HTML and dynamically loaded fragments without corrupting national characters while still injecting the live-reload script.

## Best solution

Update the content-loading and injection path in `src/server/serverUtils/contentLoader.ts` and `src/utils/pathUtil.ts` so source bytes are decoded using the document's actual charset and the resulting response bytes agree with the advertised `Content-Type`; add coverage for a Latin-1 HTML page and loaded fragment.

- **Proposed comment:**

  > Thanks for the detailed sample and the curl confirmation. This is still present in the current server code: injectable HTML is read explicitly as UTF-8, passed through the reload-script injector, encoded as UTF-8 again, and served with `charset=UTF-8`. That corrupts ISO-8859-1 bytes before the page or a loaded fragment reaches either browser, so this is not limited to the embedded preview. The server should preserve or correctly transcode the document encoding and send a matching response charset. Until that is fixed, converting the participating HTML files and their charset declarations to UTF-8 is the most reliable workaround.

## Evidence

- **forced UTF-8 decoding:** `src/utils/pathUtil.ts` implements `PathUtil.FileRead` with `fs.promises.readFile(file, 'utf-8')`. In `src/server/serverUtils/contentLoader.ts`, `getFileStream` sends injectable files through that method and `_injectIntoFile`, so ISO-8859-1 bytes are irreversibly decoded as UTF-8 before serving.
- **forced UTF-8 response:** `src/server/serverUtils/contentLoader.ts` recreates the injected content with `Buffer.from(injectedFileContents)` and appends `charset=UTF-8` to every `text/*` MIME type; `src/server/httpServer.ts` writes that value directly as the `Content-Type` response header.
- **independent confirmation:** A second reporter used curl and observed both a `Content-Type: text/html; charset=UTF-8` header and conversion of a Latin-1 file's payload to UTF-8, confirming that the server path—not only embedded-browser rendering—is involved.
- **canonical search:** The other open encoding-related report, https://github.com/microsoft/vscode-livepreview/issues/688, concerns the distinct `application/xhtml+xml` MIME-type override and would not resolve Latin-1 decoding or transcoding here.
