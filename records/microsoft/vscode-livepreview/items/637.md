# Issue #637 — Problem with "charset=ISO-8859-1"

[https://github.com/microsoft/vscode-livepreview/issues/637](https://github.com/microsoft/vscode-livepreview/issues/637)

## Summary

Current main still corrupts ISO-8859-1 HTML served from disk: injectable files are decoded as UTF-8, modified as JavaScript strings, re-encoded as UTF-8, and served with an unconditional UTF-8 Content-Type. The reporter's reduced project and the independent curl byte-level confirmation match this source path, so the bug remains necessary and should stay open.

## Change summary

Preserve national characters when serving and injecting live-reload support into HTML files encoded as ISO-8859-1 rather than UTF-8.

## Best solution

Update the serving pipeline in `src/server/serverUtils/contentLoader.ts` and `src/utils/pathUtil.ts` to determine and preserve a document's encoding while injecting the reload script, and emit a Content-Type charset matching the bytes actually returned. Add coverage for an ISO-8859-1 HTML document and an included fragment, ensuring both the original characters and injected reload behavior remain intact.

## Evidence

- **current source reproduces the conversion:** `ContentLoader.getFileStream` in `src/server/serverUtils/contentLoader.ts` sends injectable files through `PathUtil.FileRead`, converts the resulting string back with `Buffer.from`, and then appends `charset=UTF-8` to every `text/*` Content-Type. `PathUtil.FileRead` in `src/utils/pathUtil.ts` explicitly calls `fs.promises.readFile(file, 'utf-8')`, so ISO-8859-1 bytes are decoded under the wrong encoding before serving.
- **independent byte-level confirmation:** Commenter leonbloy reproduced the behavior by fetching an ISO-8859-1 page from `http://127.0.0.1:3000` with curl and inspecting its bytes: the response declared `text/html; charset=UTF-8` and the original content no longer remained ISO-8859-1.
- **concrete reduced reproduction:** The reporter supplied `LivePreviewDemo.zip` with a main HTML file and an `include.html` fragment loaded through `load()`, and showed that the same files display correctly when opened directly in Chrome but not when served by Live Preview.
- **no implementing change found:** A search of the current checkout history and source found no commit referencing issue 637 or adding ISO-8859-1/Latin-1 handling; the unconditional UTF-8 decoding and response header remain on main at commit `ab20860391988468f0fd3b29946c3c9aecf81381`.
