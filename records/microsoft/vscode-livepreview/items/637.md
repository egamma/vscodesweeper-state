# Issue #637 — Problem with "charset=ISO-8859-1"

[https://github.com/microsoft/vscode-livepreview/issues/637](https://github.com/microsoft/vscode-livepreview/issues/637)

## Summary

Keep open: current source still decodes unopened HTML files as UTF-8 regardless of their actual encoding, corrupting Latin1 characters before serving them. The supplied demo, follow-up discussion, and independent HTTP observation establish a server-side problem rather than an embedded-browser-only defect.

## Change summary

Preserve national characters in ISO-8859-1 HTML pages and dynamically loaded HTML fragments, with consistent response bytes and charset declarations.

## Best solution

Resolve encoding handling in src/server/serverUtils/contentLoader.ts and its file-reading path so HTML documents and loaded fragments retain their characters whether or not they are open in the editor. Account for editor-buffer text, disk encoding, and HTTP charset consistency together; changing the bundled browser's wrapper metadata alone cannot repair characters already lost during file reading.

## Evidence

- **Concrete reproduction supplied:** In https://github.com/microsoft/vscode-livepreview/issues/637 the reporter supplied https://github.com/microsoft/vscode-livepreview/files/15231750/LivePreviewDemo.zip and isolated the discrepancy to loading include.html into demo.html with load(). They also confirmed that selecting ISO-8859-1 in the editor did not resolve the loaded fragment.
- **Independent server-side observation:** The final comment on https://github.com/microsoft/vscode-livepreview/issues/637 describes fetching a Latin1 testlatin.html directly with curl and inspecting its bytes with od: the response advertised charset=UTF-8 and the content was converted. This places the problem before browser rendering and does not depend on which embedded browser is selected.
- **Current source loses non-UTF-8 disk characters:** src/utils/utils.ts:50-65 classifies .html as injectable. For an HTML file absent from vscode.workspace.textDocuments, ContentLoader.getFileStream in src/server/serverUtils/contentLoader.ts:327-333 calls PathUtil.FileRead, injects into the returned string, and creates a UTF-8 Buffer. PathUtil.FileRead in src/utils/pathUtil.ts:223-231 explicitly uses fs.promises.readFile(file, 'utf-8'), so Latin1 bytes representing Danish characters are decoded incorrectly before the response is constructed.
- **Editor-open and disk paths differ:** src/server/serverUtils/contentLoader.ts:303-321 obtains open documents through getText() and encodes that Unicode text with Buffer.from, while unopened injectable files use the unconditional UTF-8 disk reader. Lines 340-341 append charset=UTF-8 to text responses in either case. This explains why editor encoding can affect one document without fixing an independently loaded fragment; overriding only the header would not recover lost characters.
- **Earlier browser-wrapper hypothesis is insufficient:** The maintainer identified src/editorPreview/webviewComm.ts as a possible cause in the discussion. Its current line 217 declares UTF-8 for the extension's browser wrapper, but the current server-side decoding path independently corrupts non-UTF-8 HTML before that wrapper can display it.
- **Canonical search:** Repository issue searches for charset, encoding, ISO-8859-1, and latin found no older open report owning this symptom. https://github.com/microsoft/vscode-livepreview/issues/688 is open but newer and concerns XHTML MIME-type replacement and namespace styling, not Latin1 character corruption; it fails both the same-symptom and older-canonical requirements for this re-reviewed item.
