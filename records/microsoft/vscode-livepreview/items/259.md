# Issue #259 — Command for re-opening live preview editor

[https://github.com/microsoft/vscode-livepreview/issues/259](https://github.com/microsoft/vscode-livepreview/issues/259)

## Summary

The supplied steps suffice to retest, and current command visibility still leaves a plausible reopening gap when the server is running without an active HTML editor. The default preview now uses the Integrated Browser, but that change does not establish that this extension-side command-discovery problem is fixed.

## Change summary

Provide a discoverable command to reopen the preview after its editor is closed, without relying on recently closed editor history.

## Best solution

Make reopening an embedded preview discoverable while its server remains running, independently of the active editor's language. Retest the command-palette flow first; the likely boundary is package.json command visibility and src/extension.ts / src/manager.ts command handling, rather than browser rendering in VS Code core.

## Plan brief

- **Likely files:** `package.json`, `package.nls.json`, `src/extension.ts`, `src/manager.ts`, `src/test/suite/manager.test.ts`
- **Validation:** In an Extension Development Host, start an embedded preview, close its tab while leaving the server running, focus a non-HTML editor or close all text editors, then open the Live Preview command palette through both the palette and the server status item. Confirm that a discoverable action opens a working embedded preview without using recently closed editor history. Repeat with livePreview.useIntegratedBrowser true and false, and preserve the existing active-HTML Show Preview workflow.
- **Behavior:**

  > After closing a preview editor while its server remains running, users should be able to reopen an embedded preview through a discoverable Live Preview command without depending on the order of recently closed editors. Reopening must remain available when no HTML editor is active. Verify that the preview loads and that the existing HTML-file preview commands continue to work.
- **Trace:**

  > package.json hides livePreview.start whenever LivePreviewServerOn is true and limits livePreview.start.internalPreview.atFile to an active HTML editor; the generic livePreview.start.preview.atFile command is always hidden from the palette. StatusBarNotifier._refreshBar in src/server/serverUtils/statusBarNotifier.ts opens that same palette, so the status item does not bypass those visibility restrictions. src/extension.ts routes preview commands to Manager.openPreviewAtFileUri in src/manager.ts, which chooses an active file or a no-target fallback. The source establishes a command-discovery lead, but the issue does not identify which editor remained active and there is no current-version runtime confirmation. Start by reproducing the supplied close-and-reopen sequence with different active-editor states; do not treat the Integrated Browser default as a fix or change server serving behavior. Browser rendering and core's recently closed editor history are outside this issue's extension-side scope.

## Evidence

- **Complete reported workflow:** https://github.com/microsoft/vscode-livepreview/issues/259 describes starting the server, closing the preview editor, and being unable to reopen it reliably through recently closed editor history. There are no comments, linked implementation candidates, or confirmed current-version retests.
- **Existing commands only partially cover reopening:** package.json contributes.menus.commandPalette hides livePreview.start while LivePreviewServerOn is true, always hides livePreview.start.preview.atFile, and exposes livePreview.start.internalPreview.atFile only when editorLangId == html && !notebookEditorFocused. package.nls.json names the latter 'Show Preview (Internal Browser)'; it offers a reopening route with an active HTML editor, not an editor-independent reopen action.
- **Extension-owned discovery path:** src/server/serverUtils/statusBarNotifier.ts sets the running server status item's command to workbench.action.quickOpen with '>Live Preview: '. That opens the same filtered command palette rather than directly reopening a preview. src/extension.ts registers the existing preview commands through Manager.openPreviewAtFileUri.
- **Browser migration is not a demonstrated fix:** src/editorPreview/previewManager.ts launchFileInEmbeddedPreview delegates to the Integrated Browser when enabled and otherwise creates or reveals the bundled webview. Both are reached after the extension's command handling; neither establishes that the reported command-discovery gap has been fixed. No runtime reproduction was attempted in the read-only checkout.
- **Canonical search:** Repository issue searches for reopening, restoring, closed previews, and preview commands found no verified older open issue reporting the same symptom. https://github.com/microsoft/vscode-livepreview/issues/499 concerns a command-not-found error, and https://github.com/microsoft/vscode-livepreview/issues/467 requests a status item while the server is off; neither owns this running-server reopening workflow.
- **Existing settings are not a reopen command:** The configuration and command surfaces in package.json include livePreview.defaultPreviewPath, livePreview.openPreviewTarget, and livePreview.serverKeepAliveAfterEmbeddedPreviewClose, but these configure the initial target, browser choice, or server lifetime rather than expose an unconditional command for reopening a closed preview.
