# Issue #815 — Silent failure when default port (3000) is already in use — no error notification or Output channel entry

[https://github.com/microsoft/vscode-livepreview/issues/815](https://github.com/microsoft/vscode-livepreview/issues/815)

## Summary

The reported silent failure is actionable, but current `main` is explicitly designed to find the next free port and the existing integration tests cover concurrent servers choosing different ports. A current Remote - SSH retest with adjacent-port and Developer Tools diagnostics is needed to identify why that recovery path failed.

## Change summary

Starting an internal preview in a Remote - SSH session silently fails when the configured HTTP port is occupied, despite working after manually selecting a free port.

## Best solution

Reproduce the failure on a current extension version in Remote - SSH and determine whether `_findFreePort`, the HTTP retry, or the adjacent WebSocket bind is failing. The server startup path in `src/server/serverGrouping.ts`, `src/server/httpServer.ts`, and `src/server/wsServer.ts` should always clear its pending-start state and surface an actionable notification or log entry when startup cannot recover.

## Evidence

- **current retry behavior:** `src/server/serverGrouping.ts` calls `_findFreePort` before startup; that method probes from the configured port upward, and `openServer` then starts HTTP on the selected port and WebSocket on the following port.
- **additional collision recovery:** `src/server/httpServer.ts` handles `EADDRINUSE` by incrementing `connection.httpPort` and listening again. This means an occupied port 3000 should not, by itself, cause the command to stop.
- **silent terminal-error path:** Unhandled HTTP and WebSocket startup errors are sent only to telemetry and `console.log`, with no `showErrorMessage` or Output-channel entry. In `ServerGrouping.openServer`, rejection also bypasses deletion from `_pendingServerWorkspaces`, so later attempts for that workspace can return immediately without feedback.
- **existing collision coverage:** `src/test/suite/serverGrouping.test.ts` starts servers for two workspaces from the same configured base port and asserts that both HTTP and WebSocket ports differ, but it does not specifically cover an externally occupied port in Remote - SSH.
- **no confirmed canonical:** Repository searches found no other open issue specifically covering an externally occupied configured port. https://github.com/microsoft/vscode-livepreview/issues/561 concerns an internal preview that fails even though the server successfully starts and remains reachable, so it does not own this report.
