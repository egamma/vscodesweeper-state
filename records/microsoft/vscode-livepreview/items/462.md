# Issue #462 — 401 when using remote tunnel

[https://github.com/microsoft/vscode-livepreview/issues/462](https://github.com/microsoft/vscode-livepreview/issues/462)

## Summary

The remote-tunnel failure remains represented in current source: Live Preview returns 401 whenever the forwarded request's Host or Origin differs from the single authority returned by `vscode.env.asExternalUri`. This issue should remain open as the canonical remote/code-server tunnel report, with any change reviewed carefully because these checks protect the server's exposed surface.

## Change summary

Allow Live Preview's HTTP and WebSocket servers to accept the legitimate forwarded address used by VS Code remote tunnels instead of returning 401.

## Best solution

Determine why `vscode.env.asExternalUri` does not consistently produce the authority arriving at the server in vscode.dev and remote-tunnel configurations, then authorize the exact VS Code-provided forwarded HTTP and WebSocket origins without broadly weakening the Host/Origin checks. The implementation likely spans `src/connectionInfo/connection.ts`, `src/server/httpServer.ts`, and the corresponding origin validation in `src/server/wsServer.ts`, potentially requiring clarification or support from VS Code core's port-forwarding API.

## Evidence

- **current rejection path:** `src/server/httpServer.ts` lines 162-172 resolves one external URI and returns 401 when the request Host is neither localhost, the configured host, nor that URI's authority, or when Origin differs from that URI. A forwarded hostname not reflected by `asExternalUri` therefore follows the reported failing path on current main.
- **external-address resolution:** `src/connectionInfo/connection.ts` lines 82-90 constructs the local server URI and relies exclusively on `vscode.env.asExternalUri` for the externally reachable HTTP address; there is no alternate tunnel-host discovery or configurable allowlist.
