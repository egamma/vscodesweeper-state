# Issue #462 — 401 when using remote tunnel

[https://github.com/microsoft/vscode-livepreview/issues/462](https://github.com/microsoft/vscode-livepreview/issues/462)

## Summary

This is the canonical request for accessing Live Preview through remote tunnels: multiple users confirmed that the tunnel authority receives a 401 from the extension's host/origin authorization, and maintainers explicitly consolidated related code-server reports here. The request remains necessary on current main and must stay open because changing which external authorities the server accepts is security-sensitive.

## Change summary

Allow the Live Preview HTTP server to authorize the external address assigned to a VS Code remote tunnel instead of rejecting its Host or Origin header with 401.

## Best solution

Have `src/connectionInfo/` provide the exact active forwarded authority and make `src/server/httpServer.ts` authorize that authority without weakening the existing host/origin boundary; account for tunnel timing or address changes and add focused authorization tests. A user-configured wildcard hostname list should not replace deriving the specific forwarded address where the VS Code API can provide it.

## Evidence

- **current authorization path:** On current main, `src/server/httpServer.ts` calls `Connection.resolveExternalHTTPUri()` and returns 401 unless the request Host is localhost, `connection.host`, or the single resolved external authority, and any Origin must exactly match that resolved URI. A tunnel authority not returned by `vscode.env.asExternalUri` therefore remains rejected.
- **extension-owned integration:** `src/connectionInfo/connection.ts` constructs the local server URI and delegates external-address resolution to `vscode.env.asExternalUri`; the extension then uses that result as its HTTP authorization allowlist, so the failing 401 is produced by extension-owned validation rather than page rendering in the Integrated Browser.
- **confirmed behavior:** The reporter isolated the failure to the Host header and demonstrated that reverse proxies work when they replace it with `127.0.0.1` or `localhost`. Other commenters reproduced tunnel access failures, and one confirmed in March 2025 that making the forwarded port public avoided the 401.
- **canonical tracking issue:** A maintainer closed https://github.com/microsoft/vscode-livepreview/issues/381 specifically so remote-tunnel/code-server support would be tracked by https://github.com/microsoft/vscode-livepreview/issues/462, and likewise directed https://github.com/microsoft/vscode-livepreview/issues/497 here.
- **distinct related report:** https://github.com/microsoft/vscode-livepreview/issues/843 remains open for a narrower corporate MITM certificate scenario and explicitly distinguishes that environment-specific cause from this issue's generic Host-header rejection.
- **security-sensitive boundary:** The requested change affects which external Host and Origin values may reach a server that serves workspace files. Under the review policy, changes that widen server exposure or alter this authorization boundary require human handling and cannot be proposed for automatic closure or repair.
