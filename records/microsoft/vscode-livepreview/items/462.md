# Issue #462 — 401 when using remote tunnel

[https://github.com/microsoft/vscode-livepreview/issues/462](https://github.com/microsoft/vscode-livepreview/issues/462)

## Summary

Keep this as the existing tracking issue for Live Preview access through remote tunnels. Maintainers explicitly consolidated other reports here, and current source does not establish that the reported forwarded-host mismatch is resolved; changes to Host/Origin authorization require human review.

## Change summary

Support accessing Live Preview through a remote tunnel without a 401 response caused by the forwarded request's Host/Origin differing from the address the extension resolves.

## Best solution

Retest the documented vscode.dev-to-Linux tunnel setup and compare the forwarded request authority with Connection.resolveExternalHTTPUri() and HTTPServer's authorization checks. Preserve the server's security boundary while establishing supported tunnel-address handling; involve microsoft/vscode if asExternalUri does not expose the actual forwarded address.

## Evidence

- **Concrete reported scenario:** https://github.com/microsoft/vscode-livepreview/issues/462 documents a vscode.dev frontend connected to a Linux server: the loopback URL works, the devtunnels.ms URL returns 401, and a reverse proxy rewriting the upstream request works. The discussion distinguishes this from merely binding to a loopback interface.
- **Maintainer-designated tracking issue:** A maintainer closed https://github.com/microsoft/vscode-livepreview/issues/381 explicitly in favor of this issue at https://github.com/microsoft/vscode-livepreview/issues/381#issuecomment-1846205081, and likewise directed https://github.com/microsoft/vscode-livepreview/issues/497 here at https://github.com/microsoft/vscode-livepreview/issues/497#issuecomment-1846205822. Neither closed report is a duplicate target.
- **Current extension-side boundary:** src/server/httpServer.ts:162-173 still resolves an expected external URI and returns 401 when Host is neither localhost:<port>, the configured host, nor the resolved authority, or when a supplied Origin differs from the resolved scheme and authority. src/connectionInfo/connection.ts delegates external-address resolution to vscode.env.asExternalUri. This explains a rejection if the authorities differ, but does not prove what today's tunnel environment returns.
- **Existing capabilities do not cover the request:** The commands and configuration in package.json expose no accepted-host or tunnel-authority setting. package.nls.json defines livePreview.hostIP as the local bind address and livePreview.httpHeaders as extra response headers; neither configures accepted incoming Host/Origin values. Current code explicitly accepts localhost:<port>, so the historical localhost observation alone is not proof that the central remote-tunnel request is fixed.
- **Canonical search:** Open-issue searches for 401, tunnel, and host header found no verified older canonical owning this symptom. https://github.com/microsoft/vscode-livepreview/issues/333 concerns live refresh after changing the bind address, not the same remote-tunnel 401. https://github.com/microsoft/vscode-livepreview/issues/843 is newer and alleges a distinct corporate TLS-proxy cause, so it does not satisfy the re-review duplicate bar.
- **Workarounds are not implementation evidence:** Later comments describe public port visibility and LAN-IP access, but neither demonstrates that the original private remote-tunnel Host/Origin scenario is resolved. README.md's Codespaces FAQ documents opening forwarded URLs to complete redirects, not a general solution to a mismatched forwarded authority.
