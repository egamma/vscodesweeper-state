# Issue #1101 — More visibility for workingDirectories setting

[https://github.com/microsoft/vscode-eslint/issues/1101](https://github.com/microsoft/vscode-eslint/issues/1101)

## Summary

Keep open: existing working-directory inference and documentation do not deliver proactive configuration guidance for monorepos. The maintainer accepted that direction while explicitly rejecting a default change; no qualifying older canonical surfaced in the searches.

## Change summary

Make eslint.workingDirectories discoverable by recognizing likely monorepo configuration needs and offering settings guidance before users encounter confusing lint behavior.

## Best solution

Provide lightweight server-side detection with client-side, consent-based guidance for configuring eslint.workingDirectories, preserving existing defaults and explicit settings. Establish which workspace signals warrant a suggestion and what configuration should be offered, accounting for both legacy and flat config.

## Plan brief

- **Likely files:** `server/src/eslint.ts`, `client/src/client.ts`, `$shared/customMessages.ts`, `README.md`
- **Validation:** In a development extension session, open a root workspace containing independently configured nested packages without eslint.workingDirectories and verify that an eligible layout receives actionable guidance. Verify that ignoring or declining it leaves settings and lint behavior unchanged, acceptance applies only the approved workspace configuration, and explicit workingDirectories settings and ordinary single-project layouts are not disrupted.
- **Behavior:**

  > Users opening a monorepo should discover when eslint.workingDirectories may be needed without first diagnosing subtle lint discrepancies or finding the setting in documentation. Offer actionable guidance for eligible layouts without changing the current default or silently rewriting settings. Any configuration write must require user confirmation. Acceptance checks should cover eligible nested projects, explicitly configured workspaces, ordinary single-project workspaces, and both acceptance and dismissal.
- **Trace:**

  > server/src/eslint.ts resolves resource-scoped configuration in ESLint.resolveSettings and computes directories through findWorkingDirectory and projectFolderIndicators. The current detector walks upward from the document and already handles flat-config roots; it does not establish that arbitrary nested configs require a different working directory. client/src/client.ts reads eslint.workingDirectories and contains a separate consent-based settings-migration interaction, but no corresponding monorepo guidance was found. The maintainer's direction is recorded at https://github.com/microsoft/vscode-eslint/issues/1101#issuecomment-720500160: preserve the default and propose settings rather than changing behavior automatically. Preserve explicit directory choices, resource-scoped settings, and editor responsiveness. The unresolved boundary is which layouts genuinely warrant guidance and what user-visible configuration recommendation follows from those signals.
- **Open decisions:**
  - Which workspace layouts should trigger guidance, particularly when nested flat configs are already handled or nested legacy configs intentionally share a root working directory?
  - Should the guidance recommend auto mode or explicit directory/pattern entries, and should it offer to apply the recommendation after confirmation?
  - How often should guidance appear, and should dismissal suppress it for the session or persist for the workspace?
