# Issue #446 — Add option to auto-disable if no `.eslintrc`

[https://github.com/microsoft/vscode-eslint/issues/446](https://github.com/microsoft/vscode-eslint/issues/446)

## Summary

Keep open: current probing reduces missing-library notifications but still starts the ESLint server before checking whether ESLint can validate the project. The requested opt-in startup gate remains missing, and the maintainer explicitly allowed an off-by-default feature.

## Change summary

Add an opt-in option that avoids starting the ESLint server in projects without an applicable ESLint configuration or dependency.

## Best solution

Design an off-by-default activation policy in client/ that avoids starting the server for non-ESLint projects without silently excluding supported configurations. Resolve whether eligibility means an applicable configuration or a declared dependency, including monorepos, inherited configurations, flat config, and later configuration changes.

## Plan brief

- **Likely files:** `package.json`, `client/src/extension.ts`, `client/src/client.ts`
- **Validation:** In an Extension Development Host, enable the proposed option and open a JavaScript file in a project without ESLint configuration or a declared dependency: verify no ESLint server starts and no missing-ESLint notification appears. Repeat with qualifying legacy and flat-config projects, a nested monorepo package, and configuration added after opening the workspace; verify eligible projects begin linting. With the option disabled, verify existing startup and linting behavior remains unchanged.
- **Behavior:**

  > Users who opt in should be able to open non-ESLint projects without starting an unnecessary ESLint server or receiving missing-ESLint notifications. Projects qualifying under the chosen eligibility contract should still lint normally, including supported monorepo and configuration styles. The option must be off by default. Acceptance includes checking both initial startup and the agreed behavior when a project becomes eligible after the workspace opens.
- **Trace:**

  > client/src/extension.ts activate uses Validator.check to decide when to call realActivate, which constructs and starts the language client. Validator.check in client/src/client.ts considers settings and document language, not configuration presence or package dependency declarations. server/src/eslint.ts resolves the library and probes configuration only after startup; its silent probing is partial UX coverage, not a startup gate. The maintainer explicitly confirmed that distinction at https://github.com/microsoft/vscode-eslint/issues/446#issuecomment-581362398 and required an off-by-default flag at https://github.com/microsoft/vscode-eslint/issues/446#issuecomment-679861586. Preserve existing behavior when the option is disabled and do not substitute a root-only .eslintrc check for the project's supported configuration semantics. The uncertainty is the public eligibility contract, not whether the current startup path contains this feature.
- **Open decisions:**
  - Should opt-in eligibility require an applicable ESLint configuration, a declared ESLint dependency, or both, and which inherited, custom, global-install, and monorepo arrangements must qualify?
  - When configuration or dependencies are added after opening a workspace, should the extension automatically reconsider eligibility or require an explicit restart?

## Evidence

- **Current startup path:** client/src/extension.ts:69–95 calls realActivate when Validator.check returns anything other than Validate.off; realActivate starts the client at line 169. client/src/client.ts:39–77 checks settings, language IDs, and previously failed probes, but does not inspect project configuration or dependency declarations before this startup.
- **Existing-capability check:** package.json contributes.configuration provides eslint.enable, eslint.validate, eslint.probe, eslint.workingDirectories, and eslint.useFlatConfig, but no configuration- or dependency-based startup gate. Manual disablement and language selection do not satisfy automatic project eligibility; working-directory inference selects where ESLint runs rather than whether its server starts.
