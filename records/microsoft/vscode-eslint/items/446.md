# Issue #446 — Add option to auto-disable if no `.eslintrc`

[https://github.com/microsoft/vscode-eslint/issues/446](https://github.com/microsoft/vscode-eslint/issues/446)

## Summary

This remains a valid, accepted feature request: current lazy activation avoids starting for unsupported document types, but opening a probed JavaScript or TypeScript document still starts the server without first checking for a workspace ESLint installation or configuration.

## Change summary

Add an opt-in setting that prevents the ESLint server from starting in workspaces that do not appear to use ESLint.

## Best solution

Add a disabled-by-default activation gate in `client/` that recognizes local ESLint usage without breaking monorepos, package.json configuration, or flat config, and expose it as an `eslint.*` setting in `package.json`. The detection contract should be deliberately narrow and documented so the extension does not duplicate all of ESLint's evolving configuration-resolution rules.

## Evidence

- **current activation path:** `client/src/extension.ts` calls `realActivate` when `Validator.check` identifies an opened document for validation; it does not first test for an ESLint dependency or configuration.
- **existing settings do not cover the request:** `package.json` exposes manual `eslint.enable`, language-scoped `eslint.validate` and `eslint.probe`, and working-directory controls, but no setting that gates activation on a workspace ESLint dependency or configuration. `eslint.enable` is also described at runtime as deprecated in `client/src/extension.ts`.
- **server starts before probing completes:** `client/src/client.ts` records `ProbeFailedRequest` only after the language client and server have started, so probe failure can stop syncing a document but cannot fulfill the request to avoid server startup.
