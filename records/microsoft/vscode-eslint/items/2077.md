# Issue #2077 — Server side workingDirectory.mode auto detection is incomplete

[https://github.com/microsoft/vscode-eslint/issues/2077](https://github.com/microsoft/vscode-eslint/issues/2077)

## Summary

Current main still treats every package.json as a project root during automatic working-directory detection, and open PR https://github.com/microsoft/vscode-eslint/pull/2076 directly addresses this request. The issue must remain open while that implementation candidate is under review.

## Change summary

Make eslint.workingDirectories auto mode distinguish nested package manifests from actual project roots by considering lockfiles and related workspace indicators.

## Best solution

Review and refine https://github.com/microsoft/vscode-eslint/pull/2076, preserving legacy-config fallback behavior while preferring meaningful project-root indicators, then land it with focused coverage for nested packages with and without lockfiles.

## Evidence

- **current source:** server/src/eslint.ts lists package.json in projectFolderIndicators with isRoot: true; findWorkingDirectory stops its upward traversal at the first matching root indicator, so a nested package.json currently terminates auto detection.
- **implementation path:** When eslint.workingDirectories uses mode auto, server/src/eslint.ts calls findWorkingDirectory(workspaceFolderPath, filePath) and assigns its result as the document's working directory.
- **open fixing PR:** https://github.com/microsoft/vscode-eslint/pull/2076 is open, contains “Fixes #2077,” modifies server/src/eslint.ts, and proposes lockfile-aware detection plus an uppermost-package.json fallback. It remains review-required and has not merged.
- **maintainer discussion:** Discussion on https://github.com/microsoft/vscode-eslint/pull/2076 confirms the intended direction: a package.json with a lockfile can establish the root, while a package.json alone should allow upward traversal and serve as a fallback when no better match exists.
