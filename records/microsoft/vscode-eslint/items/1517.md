# Issue #1517 — Feature: show rule docs if available in an ESLint config file

[https://github.com/microsoft/vscode-eslint/issues/1517](https://github.com/microsoft/vscode-eslint/issues/1517)

## Summary

Keep this accepted Backlog request open: existing documentation links accompany lint diagnostics, not rule-name entries in ESLint configuration files. The canonical search found no verified issue owning this configuration-editing capability.

## Change summary

Expose rule documentation through clickable rule names or hover tooltips while editing ESLint configuration files.

## Best solution

Add configuration-aware rule documentation navigation to the extension, using the workspace's actual ESLint and plugin metadata. Settle the initial configuration formats and interaction surface before implementation; documentation should remain accessible without requiring a violation of the configured rule.

## Plan brief

- **Likely files:** `client/src/client.ts`, `server/src/eslintServer.ts`, `server/src/eslint.ts`, `package.json`
- **Validation:** In an Extension Development Host, open each agreed configuration format containing core and plugin rule entries, including a configured rule with no current violations. Verify the chosen hover or Ctrl/Cmd-click interaction exposes the correct workspace rule documentation; unrelated strings and rules without documentation must not receive misleading links. Confirm existing diagnostic documentation actions still work.
- **Behavior:**

  > Rule-name entries in supported ESLint configuration files should expose the corresponding rule documentation through the agreed hover or clickable-link interaction. This must work while editing configuration, independently of whether any source file currently reports a violation. Acceptance should cover both core and plugin rules, and ensure unrelated text and rules without documentation do not receive incorrect links.
- **Trace:**

  > The existing documentation path is diagnostic-driven: RuleMetaData.capture in server/src/eslint.ts obtains metadata from lint reports, diagnostic construction sets codeDescription.href, and connection.onCodeAction in server/src/eslintServer.ts builds documentation actions from scoped diagnostic records. Server initialization advertises no hover or document-link provider, and no configuration rule-name provider was found in client or server source. client/src/client.ts already watches configuration files and synchronizes recognized configuration documents. The remaining uncertainty is how to recognize configuration rule entries and obtain the applicable workspace metadata independently of violations, across the formats the maintainer selects. Preserve existing linting, diagnostic documentation, workspace configuration ownership, and ESLint-version compatibility. https://github.com/microsoft/vscode-eslint/issues/2187 is a related but distinct comment-navigation request, not a canonical for this work.
- **Open decisions:**
  - Which configuration formats should the initial supported contract cover: legacy JSON configuration, JavaScript flat configuration, or both?
  - Should the initial user-facing interaction provide hover documentation links, Ctrl/Cmd-click navigation, or both?
