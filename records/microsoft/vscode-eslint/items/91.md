# Issue #91 — How to lint all files in project?

[https://github.com/microsoft/vscode-eslint/issues/91](https://github.com/microsoft/vscode-eslint/issues/91)

## Summary

Keep this accepted feature request open: manually linting the whole workspace is supported, but the discussion's remaining request for automatic project-wide editor diagnostics is not. Current source still disables workspace diagnostics, and the canonical search found no older open issue owning that work.

## Change summary

Show and maintain ESLint problems across the project without requiring users to open each file or manually rerun a lint task.

## Best solution

Define a responsive, opt-in project-diagnostics workflow in client/ and server/, preserving workspace configuration and existing task support. Distinguish extension-side discovery and diagnostic management from ESLint/plugin dependency invalidation, and resolve the automatic refresh contract before implementation.

Check ignored files, multi-root configuration isolation, and responsiveness on a large workspace, while preserving the existing lint task.
- **Behavior:**

  > Users want ESLint problems throughout a project to be visible without opening every file. The existing manual task can scan a workspace and populate Problems, but does not provide the automatically maintained editor workflow requested in the discussion. Acceptance must include unopened files, respect workspace ESLint configuration and ignore rules, and avoid modifying files. The maintainer must settle initial-scan and refresh semantics, including what correctness is promised for cross-file rules, before those checks can be finalized.
- **Trace:**

  > FolderTaskProvider.getTask() in client/src/tasks.ts supplies the existing shell-task workaround with '$eslint-stylish'. The language server in server/src/eslintServer.ts advertises workspaceDiagnostics: false and its document diagnostic handler only validates URIs present in documents; client/src/client.ts configures document-triggered pulls with onTabs: false. These establish an extension-side integration gap, not an incorrect ESLint rule result. Preserve existing task behavior, scoped settings, ignore semantics, and normal open-document validation. The discussion at https://github.com/microsoft/vscode-eslint/issues/91#issuecomment-594429429 identifies dependency-aware invalidation as a separate concern; https://github.com/eslint/eslint/issues/13000 closed without implementing that capability. https://github.com/microsoft/vscode-eslint/issues/1460 and https://github.com/microsoft/vscode/issues/61140 track diagnostic retention, while https://github.com/microsoft/vscode-eslint/issues/1774 tracks cross-file freshness; those related mechanisms do not own workspace discovery. The trace establishes the missing integration, but not a settled background-linting contract or a bounded implementation.
- **Open decisions:**
  - Should the new workflow scan automatically on workspace opening, require an explicit initial scan, or expose both behaviors through an opt-in setting?
  - What freshness guarantee should project diagnostics provide after edits: changed-file updates with documented cross-file limitations, or dependency-consistent results that may require broader rescans or upstream support?
