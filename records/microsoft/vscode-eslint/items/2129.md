# Issue #2129 — ESLint plugin breaks when using `eslint-plugin-react-hooks`

[https://github.com/microsoft/vscode-eslint/issues/2129](https://github.com/microsoft/vscode-eslint/issues/2129)

## Summary

The updated reproduction isolates this to VS Code's task problem-matcher path, not the extension's language server or the React Hooks rules themselves. The broader open VS Code issue https://github.com/microsoft/vscode/issues/9635 already tracks problem matchers failing to represent multiline diagnostics, so this report is a specific duplicate with useful ESLint evidence.

## Change summary

Make the lint-whole-folder task preserve all ESLint diagnostics, rule IDs, and multiline messages emitted by eslint-plugin-react-hooks.

## Best solution

Improve VS Code's task problem-matcher support under https://github.com/microsoft/vscode/issues/9635 so `$eslint-stylish` can consume diagnostics whose messages span multiple physical lines; the extension's task can then continue using the standard matcher without diverging from ESLint's formatter output.

  > Thanks for the detailed reproduction. The updated task-specific steps explain why this differs from normal per-file linting: `lint whole folder` shells out to ESLint and VS Code builds Problems entries by parsing its stdout with `$eslint-stylish`, while open-file validation uses the ESLint language server directly. The React Hooks rules emit multiline messages with source excerpts, and the core matcher expects each diagnostic and rule ID on one physical line. ## Evidence

- **separate execution paths:** client/src/tasks.ts creates the `lint whole folder` operation as a ShellExecution and assigns `$eslint-stylish`; it does not send these results through the ESLint language server. This explains why normal per-file linting works while the task does not.
- **core matcher limitation:** VS Code defines `$eslint-stylish` in https://github.com/microsoft/vscode/blob/main/src/vs/workbench/contrib/tasks/common/problemMatcher.ts with a diagnostic regex that expects the complete severity, message, and optional rule ID on one physical line. The reported React Hooks output contains source excerpts and explanatory text across many lines before the rule ID.
- **confirmed trigger:** The reporter's task output shows multiline messages such as `Cannot create components during render`; normal open-file validation shows all diagnostics, while `yarn eslint .` plus `$eslint-stylish` produces only a small subset in Problems.
- **open broader canonical:** https://github.com/microsoft/vscode/issues/9635 is open and tracks the broader inability of VS Code problem matchers to reliably consume and accumulate multiline diagnostic messages, including discussion of ESLint output.
- **upstream attempt not merged:** https://github.com/react/react/pull/35955 proposed changing React Hooks reports to message IDs but was closed unmerged for inactivity; changing ESLint's internal messageId API would not remove the multiline text that the task matcher must parse.
