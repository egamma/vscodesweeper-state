# Issue #633 — Lint whole folder task ignores workingDirectories setting

[https://github.com/microsoft/vscode-eslint/issues/633](https://github.com/microsoft/vscode-eslint/issues/633)

## Summary

The contributed lint task still ignores eslint.workingDirectories, and both linked implementation attempts were closed without merging. Keep this accepted request open; the remaining work is extension-side task integration, not ESLint configuration semantics.

## Change summary

Make contributed lint tasks run ESLint from the configured working directories rather than always from the workspace-folder root.

## Best solution

Extend client-side task provisioning to support the configured working directories and resolve ESLint in each execution directory. Follow the maintainer's per-directory task direction, settling how users invoke all tasks and how the setting's newer forms map to task execution.

## Plan brief

- **Likely files:** `client/src/tasks.ts`, `client/src/node-utils.ts`, `client/src/client.ts`, `package.json`, `README.md`
- **Validation:** In a separate writable development workspace, open a monorepo containing two subprojects with local ESLint installations and configurations, enable eslint.lintTask.enable, and configure both directories in eslint.workingDirectories. Verify each contributed execution uses its intended directory and ESLint binary, both directories are linted even when the first reports violations, and task diagnostics identify the correct files. Repeat with paths containing spaces, supported command shells, and the agreed setting forms; verify the no-workingDirectories case preserves existing behavior.
- **Behavior:**

  > With explicitly configured working directories, contributed lint tasks should lint each selected project in its own intended execution context rather than using the workspace root for all projects. ESLint discovery, configuration resolution and reported file paths must correspond to that context. Running all selected projects must not skip later projects because an earlier project reports lint violations. Without configured working directories, retain the existing workspace-folder task behavior.
- **Trace:**

  > FolderTaskProvider.getTask() in client/src/tasks.ts creates one shell task using workspaceFolder.uri.fsPath as cwd and findEslint(rootPath) for binary discovery; TaskProvider.getTasks() aggregates those single tasks. Document validation separately interprets string, directory, pattern and mode entries in client/src/client.ts, but the task provider never consumes that setting. findEslint() in client/src/node-utils.ts returns a relative local binary when present, so the binary lookup and execution contexts must remain consistent. The unmerged https://github.com/microsoft/vscode-eslint/pull/1861 attempted chained pushd/ESLint/popd commands; its discussion establishes shell-compatibility and early-termination problems. The maintainer endorsed per-directory tasks and suggested an execute-all command at https://github.com/microsoft/vscode-eslint/pull/1861#issuecomment-2182619359, but the final invocation contract and treatment of modern setting forms remain unsettled. Preserve document-validation semantics, existing lintTask command/options overrides, workspace scoping and ESLint's own rule behavior.
- **Open decisions:**
  - Should users receive only independently runnable per-directory tasks, or also a single execute-all entry point, and should that entry point be a command or a task?
  - How should contributed tasks interpret pattern entries, auto/location modes and !cwd entries in eslint.workingDirectories, which currently describe document-specific validation behavior rather than an explicit task directory list?

## Evidence

- **Current task implementation:** client/src/tasks.ts, FolderTaskProvider.getTask(), always sets ShellExecutionOptions.cwd to the workspace folder, calls findEslint(rootPath), and returns one task. TaskProvider.getTasks() collects one task per workspace folder; neither path reads workingDirectories.
- **Existing capabilities do not cover the request:** package.json exposes eslint.lintTask.enable, eslint.lintTask.command and eslint.lintTask.options, but none provisions executions per working directory. client/src/client.ts:747–818 consumes eslint.workingDirectories for document validation only. client/src/node-utils.ts findEslint() searches the supplied root's node_modules/.bin, making execution-directory-aware binary discovery relevant as well.
