# Issue #1928 — Configuration to use a formatter

[https://github.com/microsoft/vscode-eslint/issues/1928](https://github.com/microsoft/vscode-eslint/issues/1928)

## Summary

Keep this accepted feature request open: current diagnostics still bypass ESLint output formatters, so the reporter's .lint-todo baseline and due-date behavior remain unsupported. Native bulk suppression and CLI tasks are alternatives, not implementations of this integration.

## Change summary

Honor @lint-todo/eslint-formatter-todo's baseline and due-date semantics when displaying live ESLint diagnostics.

## Best solution

Determine a structured integration for .lint-todo filtering and due-date severity changes in server-side validation while preserving diagnostic locations and code actions. Native ESLint suppression is a possible migration alternative, but it does not consume the existing TODO baseline or implement its deadlines.

## Evidence

- **Accepted request and maintainer acknowledgment:** https://github.com/microsoft/vscode-eslint/issues/1928 is labeled feature-request and assigned to Backlog. The supplied maintainer comment explicitly says formatter integration is not currently possible and suggests a periodically triggered CLI task, not a solution for live editor diagnostics.
- **Current diagnostic pipeline:** server/src/eslint.ts:1287–1363, ESLint.validate, calls eslintClass.lintText and converts docReport.messages directly through Diagnostics.create. It does not invoke an output formatter; the ESLintClass interface at lines 259–271 likewise exposes no loadFormatter operation.
- **Existing settings do not cover the request:** package.json defines eslint.format.enable for document formatting, implemented through fix: true and output-to-text-edit conversion in server/src/eslintServer.ts:747–813, not CLI report formatting. eslint.lintTask.options can pass --format to a separate CLI task in client/src/tasks.ts:38–56, but that task does not filter the language server's live diagnostics. eslint.rules.customizations changes severity by rule, not by individual TODO entry or deadline.
- **Native suppression is not equivalent:** package.json:159–177 and server/src/eslint.ts:1306–1358 support ESLint's native suppression file through applySuppressions, suppressionsLocation and suppressedMessages. This uses eslint-suppressions.json rather than .lint-todo. The completed work at https://github.com/microsoft/vscode-eslint/issues/1997 therefore does not establish that this request is implemented, and the closed issue cannot be a duplicate canonical.
- **Third-party baseline semantics:** The README retrieved from https://github.com/lint-todo/eslint-formatter-todo describes storing individual TODO violations in .lint-todo, hiding existing entries, and changing their severity to warning or error according to configured due dates. These are substantive requirements beyond selecting a console presentation format.
- **Canonical search and related precedent:** Repository searches for formatter TODO, lint-todo, custom formatter, baseline and open formatter/suppression titles found no verified open canonical owning this integration. https://github.com/microsoft/vscode-eslint/issues/1355 concerns document-formatter initialization; https://github.com/microsoft/vscode-eslint/issues/1733 concerns enabling document formatting by default; https://github.com/microsoft/vscode-eslint/issues/1739 concerns probing feedback. The closed https://github.com/microsoft/vscode-eslint/issues/1532 discusses custom message presentation and the mismatch between formatter string output and structured diagnostics, but neither owns this TODO-filtering request nor establishes a maintainer decline covering it.
