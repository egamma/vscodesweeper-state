# Issue #1811 — Feature request: bring back enable/disable eslint command

[https://github.com/microsoft/vscode-eslint/issues/1811](https://github.com/microsoft/vscode-eslint/issues/1811)

## Summary

Keep open: restart-free extension disablement addresses the reporter's original inconvenience, but main still lacks the requested command for quickly toggling ESLint. The Backlog assignment and prior maintainer interest support retaining the remaining command-access request rather than declining it.

## Change summary

Restore convenient command-based enablement and disablement of ESLint, potentially as a temporary diagnostic-visibility toggle while writing code.

## Best solution

Decide whether the command should toggle validation through the existing eslint.enable setting or temporarily hide ESLint diagnostics while leaving linting and fixes available. Implement the chosen interaction in the extension client without changing the workspace's ESLint rules or duplicating extension-management UI unnecessarily.

## Plan brief

- **Likely files:** `package.json`, `client/src/extension.ts`, `client/src/client.ts`, `server/src/eslint.ts`, `README.md`
- **Validation:** In a workspace with known ESLint errors and warnings, invoke the chosen command while a linted file is open: ESLint diagnostics should disappear without reloading VS Code and return when toggled back on. Confirm that TypeScript diagnostics remain visible, newly opened files follow the chosen scope, and fix-on-save behaves according to the selected validation-versus-visibility contract.
- **Behavior:**

  > The user wants a command-accessible way to remove ESLint visual noise while writing code and restore it before committing, without restarting the editor. Existing settings and restart-free extension disablement do not supply the requested direct command. Acceptance requires toggling the chosen ESLint behavior in an open editor without disturbing other diagnostic providers. Whether linting and fixes continue while diagnostics are hidden must be explicitly settled before implementation.
- **Trace:**

  > package.json contributes six ESLint commands but none for enablement or diagnostic visibility; their registration lives in client/src/extension.ts. Validator.check in client/src/client.ts consults resource-scoped eslint.enable, and the configuration-change listener resynchronizes documents based on that decision. Separately, server/src/eslint.ts filters diagnostics using rule severity overrides and eslint.quiet, establishing a presentation-only path distinct from disabling validation. The older discussion at https://github.com/microsoft/vscode-eslint/issues/1281 documents demand and maintainer willingness to accept a contribution, but its final update only establishes restoration of the setting. Preserve workspace ESLint configuration, other providers' diagnostics, and existing fixes unless the selected public behavior explicitly changes their availability. The remaining uncertainty is the command's user-visible contract, not an established defect in the current linting implementation.
- **Open decisions:**
  - Should the command disable ESLint validation using the existing enablement setting, or temporarily hide ESLint diagnostics while keeping linting and fixes available?
  - Should toggling persist in resource-scoped settings, or apply only for the current editor session without modifying configuration?
