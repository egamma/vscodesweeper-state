# Issue #2057 — Measure rule performance through VSCode ESLint

[https://github.com/microsoft/vscode-eslint/issues/2057](https://github.com/microsoft/vscode-eslint/issues/2057)

## Summary

This is a valid, accepted feature request: `eslint.options.stats` already enables ESLint's Node API statistics, but the server currently discards the returned `LintResult.stats` data instead of exposing or logging it. No other open issue found in the canonical search owns this work.

## Change summary

Expose rule-level timing statistics from ESLint validation runs in VS Code so users can identify expensive rules without invoking the CLI separately.

## Best solution

Extend the server's validation path to consume `LintResult.stats` when enabled and write a concise, structured report to the ESLint output channel, avoiding a wrapper executable or new protocol message unless a richer client UI is later desired. The implementation should remain opt-in because collecting and logging timing data on editor validation can itself add work.

- **Proposed comment:**

  > Thanks for the detailed request. Setting `eslint.options.stats` should already pass `stats: true` to the workspace ESLint constructor, but the server currently reads diagnostics from the returned lint result and does not consume its `stats` property. Since the extension uses ESLint's Node.js API rather than launching its CLI, an executable wrapper is not the right integration point; `eslint.runtime` controls the Node runtime used for the language server, not an ESLint executable. A focused implementation could read `LintResult.stats` in the server validation path and log an opt-in timing summary to the ESLint output channel without requiring an additional client/server protocol message.

## Evidence

- **constructor option already forwarded:** `package.json` exposes `eslint.options`, and `server/src/eslint.ts` `withClass()` merges `settings.options` into `newOptions`; `newClass()` then passes those options to the workspace's ESLint constructor. Therefore `{ "stats": true }` already reaches ESLint versions that support the option.
- **stats currently discarded:** `server/src/eslint.ts` defines `ESLintDocumentReport` without a `stats` member, and `validate()` consumes only messages, suppressed messages, and related fix metadata from the `lintText()` result. There is no code that logs or forwards rule timings.
- **ESLint API behavior:** ESLint documents at https://eslint.org/docs/latest/extend/stats that constructor option `stats: true` adds a `stats` property to each `LintResult`; the data is directly available to this server through the Node.js API and does not require parsing CLI stdout.
- **wrapper limitation:** `client/src/client.ts` uses `eslint.runtime` as the runtime for the extension's language-server process, while `server/src/eslint.ts` loads and instantiates the workspace ESLint library. It is not an override for an ESLint CLI executable or wrapper.
