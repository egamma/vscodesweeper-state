# Issue #2057 — Measure rule performance through VSCode ESLint

[https://github.com/microsoft/vscode-eslint/issues/2057](https://github.com/microsoft/vscode-eslint/issues/2057)

## Summary

The extension already passes `eslint.options` into ESLint, so `stats: true` can request timing data, but the returned statistics are currently discarded rather than exposed or logged. This remains a valid, accepted feature gap with no separate canonical issue.

## Change summary

Expose ESLint's per-rule execution statistics in VS Code so users can diagnose slow lint configurations without running the CLI separately.

## Best solution

Add server-side handling for the `stats` field returned by `ESLint.lintText` and emit a concise, structured timing report to the existing ESLint output channel when statistics are enabled. The implementation should account for ESLint versions that do not support stats and avoid requiring an executable wrapper or a new protocol message unless an interactive client UI is desired.

  > Thanks for the request. `eslint.options` is passed to the workspace ESLint API, so `"stats": true` can already enable statistics on ESLint versions that support it. The missing part is that the server currently consumes the lint messages but does not capture or log the returned `stats` data. There is no ESLint-executable override for a wrapper—the extension loads ESLint as a library, while `eslint.runtime` controls the Node runtime. A suitable implementation would handle the returned stats in the server and write a structured summary to the existing ESLint output channel.

## Evidence

- **options reach ESLint:** `client/src/client.ts` reads `eslint.options`, and `server/src/eslint.ts` `withClass` copies those options into the constructor options passed to the workspace ESLint API; therefore `{ "stats": true }` can already reach supported ESLint versions.
- **statistics are discarded:** `server/src/eslint.ts` defines `ESLintDocumentReport` without a `stats` field, and `validate` consumes diagnostics, suppressions, fixes, and rule metadata from `lintText` results without logging or otherwise forwarding rule timing data.
- **existing output surface:** The server already writes through `connection.console`, which is surfaced by the client's ESLint output channel and the `eslint.showOutputChannel` command; logging statistics would not inherently require a new LSP notification.
- **no executable-wrapper hook:** The extension loads the workspace ESLint library and invokes its Node.js API. `eslint.runtime` selects the Node runtime for the language server, not an alternate ESLint CLI executable, so the proposed executable-wrapper approach is not an existing capability.
