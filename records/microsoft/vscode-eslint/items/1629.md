# Issue #1629 — Improve the "Error: spawn ...Microsoft VS Code\Code.exe ENOENT" error message to provide more information

[https://github.com/microsoft/vscode-eslint/issues/1629](https://github.com/microsoft/vscode-eslint/issues/1629)

## Summary

The current server still reports uncaught exceptions using only a generic heading and the error stack, so the requested troubleshooting context remains missing. This is a valid, already-triaged feature request in the Backlog rather than a duplicate of the nodePath behavior report.

## Change summary

Include actionable process and configuration context when the ESLint server reports a spawn ENOENT exception.

## Best solution

Enhance the uncaught-exception reporting in `server/src/eslintServer.ts` to preserve useful spawn-error fields such as the executable, arguments, working directory, error code, and relevant runtime settings while avoiding disclosure of unrelated environment data. Add a focused server test covering an ENOENT-shaped error and its rendered output.

## Evidence

- **current exception handling:** `server/src/eslintServer.ts` registers `process.on('uncaughtException')` and prints `Uncaught exception received.` followed preferentially by `error.stack`; because it selects the stack first, additional structured properties on a spawn error are not reported.
- **existing runtime surface:** `client/src/client.ts` passes `eslint.runtime`, `eslint.execArgv`, the server working directory, and environment overrides into the language-server launch options, while `package.json` documents `eslint.runtime` as the Node binary used to run ESLint. That information could make a spawn failure more actionable, but the current exception output does not connect it to the failure.
- **canonical distinction:** The open https://github.com/microsoft/vscode-eslint/issues/1225 concerns how relative `eslint.nodePath` values resolve in multi-root workspaces. This issue requests richer diagnostics for spawn failures generally, so #1225 covers one possible cause rather than owning the requested error-reporting work.
- **existing capability check:** `eslint.showOutputChannel` exposes the server output, but the reported generic stack is already from that output channel; the command therefore does not satisfy the request for additional diagnostic context.
- **triage state:** The issue is assigned to the Backlog milestone and already carries `feature-request` and `help wanted`, consistent with an accepted but unscheduled improvement.
