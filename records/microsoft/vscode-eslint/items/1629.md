# Issue #1629 — Improve the "Error: spawn ...Microsoft VS Code\Code.exe ENOENT" error message to provide more information

[https://github.com/microsoft/vscode-eslint/issues/1629](https://github.com/microsoft/vscode-eslint/issues/1629)

## Summary

Keep this accepted Backlog feature request open: current main still logs only the uncaught exception's stack or message, without the structured process details or configuration context needed to diagnose a spawn failure.

## Change summary

Make ENOENT spawn failures in the ESLint output channel explain which executable and relevant ESLint runtime or module-resolution configuration caused the failure.

## Best solution

Improve the exception reporting around `server/src/eslintServer.ts` to preserve useful child-process error fields such as `code`, `syscall`, `path`, and `spawnargs`, and provide actionable context for `eslint.runtime` versus `eslint.nodePath`. Add focused coverage for formatting an ENOENT spawn error without changing normal server error handling.

## Evidence

- **current exception handling:** `server/src/eslintServer.ts` handles `uncaughtException` by preferring `error.stack`, then `error.message`, and only serializes the complete error when neither exists. A normal Node spawn error has a stack, so additional fields useful for diagnosis are omitted.
- **existing settings:** `package.json` defines `eslint.nodePath` as a path added to `NODE_PATH` for ESLint module resolution and `eslint.runtime` as the Node binary used to run ESLint; the report shows that changing these settings altered or resolved the failure, but the logged error did not distinguish their roles.
- **existing output command:** `eslint.showOutputChannel` in `client/src/extension.ts` only reveals the output already produced by the server; it does not add the missing diagnostic context.
- **canonical search:** https://github.com/microsoft/vscode-eslint/issues/1225 concerns how a relative `eslint.nodePath` is resolved in multi-root workspaces. It is related configuration context but does not own this request to improve generic spawn-error reporting; resolving it would not satisfy this issue.
