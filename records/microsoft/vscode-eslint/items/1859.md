# Issue #1859 — When the user provides eslint.options, remove the requirement for a eslint.config.js file

[https://github.com/microsoft/vscode-eslint/issues/1859](https://github.com/microsoft/vscode-eslint/issues/1859)

## Summary

The requested behavior is already available through ESLint's `overrideConfigFile: true` constructor option, which can be supplied through `eslint.options`; no extension-specific mode or synthetic configuration file is needed.

## Change summary

Allow formatting from configuration supplied entirely through `eslint.options` when no `eslint.config.js` exists.

## Best solution

Keep forwarding `eslint.options` directly to the workspace's ESLint library and configure this scenario with `overrideConfigFile: true` alongside `baseConfig`. The extension should not create an implicit configuration file or independently alter ESLint's configuration-discovery semantics.

## Vision fit

- **Fit:** rejected
- **Reason:** Having the extension synthesize configuration would make it second-guess ESLint's configuration model, while the supported ESLint constructor option already expresses the intended behavior.
- **Evidence:** The vision states that the extension uses the ESLint library installed in the workspace and that the workspace owns its ESLint version and configuration.

- **Proposed comment:**

  > Thanks for the request. `eslint.options` is passed directly to the workspace's ESLint constructor, and ESLint already provides an option for this case. You can disable configuration-file lookup while keeping your in-memory configuration with:
  > 
  > ```json
  > "eslint.options": {
  >   "overrideConfigFile": true,
  >   "baseConfig": {
  >     "rules": {
  >       // rules here
  >     }
  >   }
  > }
  > ```
  > 
  > With `overrideConfigFile: true`, ESLint does not search for `eslint.config.js`, so the extension does not need to create a dummy file or add a separate mode.
