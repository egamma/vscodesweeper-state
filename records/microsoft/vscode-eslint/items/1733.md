# Issue #1733 — Feature Request: enable the "eslint.format.enable" setting by default.

[https://github.com/microsoft/vscode-eslint/issues/1733](https://github.com/microsoft/vscode-eslint/issues/1733)

## Summary

The formatter is intentionally opt-in because enabling it globally would register ESLint alongside formatters users may already prefer and would break existing configurations. The current default is an explicit maintainer design decision, so this can be closed as designed.

## Change summary

Enable ESLint's VS Code formatter by default, or remove the setting and always register the formatter.

## Best solution

Keep `eslint.format.enable` disabled by default and preserve explicit opt-in. Users who want ESLint formatting should enable the setting and select `dbaeumer.vscode-eslint` as the language's `editor.defaultFormatter`, or use `source.fixAll.eslint` on save for more targeted behavior.

## Vision fit

- **Fit:** rejected
- **Reason:** Automatically registering ESLint as a formatter would override or compete with the user's chosen editor formatting pipeline and workspace configuration.
- **Evidence:** The vision says to build on VS Code's core formatting surfaces and treats the workspace configuration as the user's to own rather than something the extension should decide automatically.

  > Thanks for the context. `eslint.format.enable` is intentionally opt-in because VS Code can use different formatters for the same language. Enabling ESLint's formatter for everyone would make it compete with choices such as the TypeScript or Prettier formatter and would be a breaking change for users relying on the current default. If ESLint should format a language, enable `eslint.format.enable` and set `editor.defaultFormatter` for that language to `dbaeumer.vscode-eslint`; for fix-on-save behavior, `editor.codeActionsOnSave` with `source.fixAll.eslint` is the more configurable option. Given those compatibility constraints, the current default is working as designed.
