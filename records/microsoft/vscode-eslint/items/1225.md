# Issue #1225 — eslint.nodePath only works with absolute paths in multi module vscode workspaces

[https://github.com/microsoft/vscode-eslint/issues/1225](https://github.com/microsoft/vscode-eslint/issues/1225)

## Summary

Keep open: resolving eslint.nodePath relative to each workspace folder is intentional, but a portable shared SDK path for mixed-depth multi-root monorepos remains unsupported. The accepted Backlog request needs a backward-compatible configuration decision, not an as-designed close of the existing behavior.

## Change summary

Allow a checked-in multi-root workspace configuration to reference a shared root-level ESLint SDK without developer-specific absolute paths.

## Best solution

Provide an explicit, backward-compatible way to anchor ESLint module resolution to a shared monorepo or workspace-file location while preserving existing folder-relative eslint.nodePath behavior. Decide the public setting or path-reference contract before implementing it in the extension's configuration and module-resolution paths.

## Plan brief

- **Likely files:** `package.json`, `client/src/client.ts`, `$shared/settings.ts`, `server/src/eslint.ts`, `README.md`
- **Validation:** Use a multi-root workspace containing the monorepo root and packages at different depths, with one shared .yarn/sdks ESLint installation. Confirm every package loads that installation through the chosen portable configuration after moving the checkout to another absolute location; separately confirm existing folder-relative and absolute eslint.nodePath configurations retain their current behavior.
- **Behavior:**

  > A monorepo with one root-level Yarn SDK cannot currently use the same .yarn/sdks value across a workspace containing both the root and nested package folders. The desired outcome is a checked-in configuration that locates the shared ESLint SDK without embedding a developer's absolute filesystem path or giving up the multi-root explorer layout. Acceptance requires successful SDK resolution for folders at different depths and after relocating the checkout. Existing relative and absolute eslint.nodePath behavior must remain compatible.
- **Trace:**

  > client/src/client.ts forwards the resource-scoped nodePath string and the document's workspaceFolder through ConfigurationSettings in $shared/settings.ts. server/src/eslint.ts, ESLint.resolveSettings, explicitly joins relative nodePath values to that folder before Files.resolve; the independently computed ESLint working directory does not change this anchor. This confirms the configuration limitation from source, not a runtime reproduction of the historical Yarn environment. The maintainer established the existing semantics as intentional and suggested a separately scoped setting rather than changing them: https://github.com/microsoft/vscode-eslint/issues/1225#issuecomment-881280272. The uncertainty is the new user-facing path-reference contract, not ownership of ESLint rule or plugin behavior. Preserve existing resolution semantics and workspace-trust requirements; general environment injection and better spawn-error reporting are separate work.
- **Open decisions:**
  - Which explicit public configuration contract should identify the shared SDK location: a separately scoped setting anchored to the workspace-file directory, or an opt-in path reference to a named workspace folder?

## Evidence
