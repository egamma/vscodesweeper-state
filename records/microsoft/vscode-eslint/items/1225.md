# Issue #1225 — eslint.nodePath only works with absolute paths in multi module vscode workspaces

[https://github.com/microsoft/vscode-eslint/issues/1225](https://github.com/microsoft/vscode-eslint/issues/1225)

## Summary

This remains a valid feature request: current main intentionally resolves a relative `eslint.nodePath` against each containing workspace folder, which leaves multi-root monorepos without a single portable path to a root-level Yarn SDK. The existing `feature-request` and `help wanted` classification is appropriate.

## Change summary

Allow a checked-in multi-root `.code-workspace` file to reference a shared root-level Yarn SDK through `eslint.nodePath` without using a developer-specific absolute path.

## Best solution

Preserve the existing workspace-folder-relative behavior for compatibility, but add an explicit portable way to resolve `eslint.nodePath` against the common monorepo or `.code-workspace` root, such as a documented variable or a new resolution-base option. The resolution belongs primarily in `server/src/eslint.ts`, with the configuration schema and client/shared settings updated if a new setting is introduced.

## Evidence

- **current source behavior:** `server/src/eslint.ts` in `resolveSettings` derives `workspaceFolderPath` from the document's workspace folder and resolves every non-absolute `settings.nodePath` with `path.join(workspaceFolderPath, nodePath)`. There is no code-workspace-root or common-monorepo-root alternative.
- **setting surface:** `package.json` defines `eslint.nodePath` as a nullable string with machine-overridable scope and describes it only as a path added to `NODE_PATH`; it exposes no resolution-base option.
- **confirmed limitation:** The thread includes a clonable multi-root Yarn reproduction and an independent confirmation that `.yarn/sdks` is resolved separately beneath each workspace folder, while an absolute path works.
- **maintainer classification:** The maintainer confirmed that workspace-file settings are resolved relative to each workspace folder and warned that changing that behavior would be breaking; the issue was subsequently retained in the Backlog with `feature-request` and `help wanted`, indicating that an additive solution remains open.
