# Issue #1845 — Worth using `NODE_COMPILE_CACHE` when detecting node v22+

[https://github.com/microsoft/vscode-eslint/issues/1845](https://github.com/microsoft/vscode-eslint/issues/1845)

## Summary

Keep this accepted performance request open: current main has no dedicated Node compile-cache setting or automatic enablement, and the maintainer acknowledged that eslint.execArgv does not supply the requested environment variable. The related ESLint result-cache work addresses a different capability.

## Change summary

Enable Node's persistent module compile cache for compatible ESLint server runtimes, potentially through an extension setting.

## Best solution

Decide whether compile caching should be opt-in or automatic, then integrate it with the ESLint server startup path while preserving compatibility with older and custom runtimes. Measure cold and warm startup behavior before promising a performance improvement; ESLint result caching is separate work.

## Plan brief

- **Likely files:** `client/src/client.ts`, `server/src/eslintServer.ts`, `package.json`, `README.md`
- **Validation:** In a separate writable development environment, compare first validation and repeated ESLint server restarts with caching enabled and disabled on a compatible Node runtime; verify persistent cache creation and identical diagnostics and fixes. Repeat with an unsupported runtime, a custom eslint.runtime, NODE_DISABLE_COMPILE_CACHE=1, and an unwritable cache location to verify the agreed compatibility and failure behavior.
- **Behavior:**

  > The request is to reuse Node's compiled-module cache across ESLint server runs, not to skip linting through .eslintcache. When enabled on a compatible runtime, repeated server runs should reuse persistent compilation data without changing diagnostics or fixes. Unsupported runtimes must retain working lint integration. Acceptance includes cold-versus-warm timing measurements and the agreed behavior for explicit environment overrides and unavailable cache storage.
- **Trace:**

  > client/src/client.ts:createServerOptions reads eslint.runtime, eslint.execArgv, and eslint.nodeEnv and constructs both run and debug server options; its explicit environment additions are currently DEBUG and NODE_ENV. server/src/eslintServer.ts:loadNodeModule loads the workspace ESLint library through the resolution path in server/src/eslint.ts:resolveSettings. No compile-cache activation was found in those sources or the settings manifest, and the maintainer acknowledged the execArgv/environment distinction at https://github.com/microsoft/vscode-eslint/issues/1845#issuecomment-2098312770. Node documents both environment-variable and programmatic activation, but actual support must be assessed for the server runtime rather than inferred from the editor version. Preserve existing module resolution, ESLint configuration, and lint-result semantics; https://github.com/microsoft/vscode-eslint/issues/1844 and https://github.com/microsoft/vscode-eslint/pull/2120 concern separate result caching. The remaining uncertainty is the intended enablement and storage contract and whether measured startup gains warrant adopting it.
- **Open decisions:**
  - Should compatible ESLint server runtimes enable compile caching automatically, or should users explicitly opt in through a setting?
  - Should the extension manage a cache location or expose a configurable directory, and how should that contract interact with an existing NODE_COMPILE_CACHE environment value?

## Evidence

- **Maintainer acknowledged the capability gap:** At https://github.com/microsoft/vscode-eslint/issues/1845#issuecomment-2095440722 the maintainer suggested eslint.execArgv but noted there was no automatic detection. After the reporter explained that NODE_COMPILE_CACHE is an environment variable, the maintainer explicitly corrected that suggestion at https://github.com/microsoft/vscode-eslint/issues/1845#issuecomment-2098312770.
- **Existing settings do not directly cover the request:** package.json defines eslint.runtime as a Node executable, eslint.execArgv as runtime arguments, eslint.nodeEnv as NODE_ENV, and eslint.nodePath as an ESLint module-resolution path. client/src/client.ts:398-420, createServerOptions(), forwards runtime and execArgv and supplies only DEBUG and NODE_ENV as explicit environment overrides; it does not enable NODE_COMPILE_CACHE. Searches of client/, server/, and $shared/ found no NODE_COMPILE_CACHE or enableCompileCache integration.
- **Extension-owned integration boundary:** client/src/client.ts:createServerOptions controls the ESLint language-server launch. server/src/eslintServer.ts:63-74 loads external modules, and server/src/eslint.ts:982-1046 resolves and loads the workspace ESLint library. Node owns the caching mechanism, but enabling it for this server is extension-side integration rather than an ESLint rule or engine defect.
- **Node capability and performance tradeoff:** https://nodejs.org/docs/latest-v22.x/api/module.html#module-compile-cache documents activation through NODE_COMPILE_CACHE or module.enableCompileCache(). It warns that initial module loading may become slower while subsequent loads can improve, and documents NODE_DISABLE_COMPILE_CACHE and cache-directory behavior. No execution or performance measurement was performed in this read-only review.
- **Canonical search found distinct result-cache work:** Repository searches for compile cache, NODE_COMPILE_CACHE, enableCompileCache, bytecode, cache, and startup found no verified older canonical for this request. https://github.com/microsoft/vscode-eslint/issues/1844 is older and open, but requests .eslintcache result caching on save via lintFiles. Its open implementation candidate, https://github.com/microsoft/vscode-eslint/pull/2120, explicitly fixes that result-cache issue, not Node module compilation; landing it would not satisfy this request.
