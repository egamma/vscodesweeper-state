# Issue #795 — Support specifying the shell to use for Lint task to avoid problems with bash under Windows.

[https://github.com/microsoft/vscode-eslint/issues/795](https://github.com/microsoft/vscode-eslint/issues/795)

## Summary

VS Code's supported task-customization mechanism already lets a workspace select `cmd.exe` for the contributed ESLint task, avoiding the Windows-path interpretation problem without changing the extension's generated command.

## Change summary

Allow the generated whole-workspace lint task to use a Windows-compatible shell when the default integrated shell is Git Bash, Cygwin, or WSL bash.

## Best solution

Keep using `ShellExecution` and rely on the documented `tasks.json` override for shell selection; the ESLint task can be customized with `options.shell.executable` and `options.shell.args` while retaining its contributed task definition.

- **Proposed comment:**

  > Thanks for the report and the follow-up investigation. VS Code supports overriding the shell for a contributed task in `.vscode/tasks.json`, so the generated ESLint task can be kept while selecting `cmd.exe` explicitly:
  > 
  > ```json
  > {
  >   "type": "eslint",
  >   "label": "eslint: lint whole folder",
  >   "options": {
  >     "shell": {
  >       "executable": "cmd.exe",
  >       "args": ["/d", "/c"]
  >     }
  >   }
  > }
  > ```
  > 
  > This is the task system's supported workspace-specific customization mechanism, documented at https://code.visualstudio.com/docs/editor/tasks#_customizing-autodetected-tasks, and it avoids passing the Windows ESLint command through Git Bash without changing the extension's task provider.

## Evidence

- **current implementation:** `client/src/tasks.ts` still contributes the whole-folder task through `vscode.ShellExecution`, with only `cwd` supplied in `ShellExecutionOptions`; `package.json` exposes `eslint.lintTask.command` and `eslint.lintTask.options`, but no separate shell setting.
- **supported customization:** VS Code's task documentation states that contributed tasks can receive workspace-specific configuration in `tasks.json`, and that task `options.shell` overrides the default shell: https://code.visualstudio.com/docs/editor/tasks#_customizing-autodetected-tasks
- **confirmed workaround:** A commenter confirmed that an ESLint task entry with `options.shell.executable` set to `cmd.exe` and arguments `/d`, `/c` resolves this exact problem: https://github.com/microsoft/vscode-eslint/issues/795#issuecomment-1152778571
- **API capability:** The VS Code API used by the current extension defines `ShellExecutionOptions.executable` and `ShellExecutionOptions.shellArgs`, so shell selection is supported by the task platform rather than requiring `ProcessExecution`.
- **canonical search:** The only matching open vscode-eslint issue is this issue itself; https://github.com/microsoft/vscode-eslint/issues/1038 was closed as its duplicate, while the earlier VS Code issue https://github.com/microsoft/vscode/issues/38381 is closed and is not a valid duplicate target.
