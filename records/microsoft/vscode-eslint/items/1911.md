# Issue #1911 — Support for `typescript-eslint` v8's parser `projectService`

[https://github.com/microsoft/vscode-eslint/issues/1911](https://github.com/microsoft/vscode-eslint/issues/1911)

## Summary

The original new-file failure was mitigated in typescript-eslint 8.3.0, but that upstream reload is explicitly a partial workaround and later reports confirm gaps remain. The extension still lacks a watcher or invalidation integration for long-lived typescript-eslint project services, so this TypeScript-specific feature request remains necessary.

## Change summary

Provide an efficient way for a long-lived typescript-eslint project service to learn about relevant file-system changes without requiring an ESLint server restart.

## Best solution

Keep this request open and coordinate an editor-safe watcher or dependency-invalidation API with typescript-eslint and ESLint, then connect it to VS Code file-system events without recreating the entire ESLint instance or indiscriminately re-linting every file. Track the broader cross-file invalidation problem in https://github.com/microsoft/vscode-eslint/issues/1774, while retaining this issue for the distinct newly-created-file/project-service integration.

## Evidence

- **confirmed reproduction:** The maintainer confirmed the supplied repository reproduced the failure in https://github.com/microsoft/vscode-eslint/issues/1911#issuecomment-2271012278 and explained that the extension intentionally keeps the ESLint instance alive because rebuilding type information for each lint is costly.
- **partial upstream mitigation:** typescript-eslint/typescript-eslint#9853 merged as commit https://github.com/typescript-eslint/typescript-eslint/commit/f5ee5eb823f1adafb1be26acc9dd7c3e392340b9 and reloads the project service when a file is not found, but its PR description says it fixes “most -but not all- cases”; the typescript-eslint maintainer likewise described it as a fragile band-aid that does not handle stale file information.
- **current source gap:** client/src/client.ts registers file-system watchers only for ESLint configuration files, .eslintignore, and package.json. server/src/eslintServer.ts clears settings and revalidates in response to those configuration events; current client/, server/, and $shared/ contain no projectService-specific watcher or registration API.
- **existing commands are workarounds:** package.json contributes eslint.restart and eslint.revalidate, and client/src/extension.ts implements revalidation as a diagnostic refresh. Neither provides incremental project-service file registration, matching the reports that restarting the ESLint server is required in remaining cases.
- **related issue is not canonical:** https://github.com/microsoft/vscode-eslint/issues/1774 remains open for the broader problem of recomputing cross-file information after changes. Its proposed re-linting approaches do not by themselves guarantee that a long-lived project service registers a newly created file, so resolving that broader issue would not necessarily leave no work for this request.
- **continued impact:** Comments report persistence with typescript-eslint 8.7.0 and a later folder-creation scenario, showing that the 8.3.0 reload mitigation did not fully cover the requested behavior.
