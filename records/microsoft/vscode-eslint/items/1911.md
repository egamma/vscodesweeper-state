# Issue #1911 — Support for `typescript-eslint` v8's parser `projectService`

[https://github.com/microsoft/vscode-eslint/issues/1911](https://github.com/microsoft/vscode-eslint/issues/1911)

## Summary

Keep open for coordinated projectService integration: typescript-eslint 8.3.0 mitigated new-file discovery, but the discussion explicitly preserves the watcher-support request and later reports describe remaining failures. Current extension settings and commands do not provide that integration.

## Change summary

Support typescript-eslint projectService updates in a long-lived editor session so newly created files and relevant filesystem changes are recognized without restarting ESLint.

## Best solution

Agree on an editor/parser lifecycle and change-notification contract with typescript-eslint/typescript-eslint, then implement the extension-side integration in client/ and server/ while preserving responsiveness. Coordinate with https://github.com/microsoft/vscode-eslint/issues/1774, but retain this issue's distinct new-file discovery and projectService integration requirements.

## Plan brief

- **Likely files:** `client/src/client.ts`, `server/src/eslintServer.ts`, `server/src/eslint.ts`
- **Validation:** In a disposable checkout of https://github.com/tetarchus/project-service, establish behavior with current supported dependencies. With ESLint already active, create and save a TypeScript file in an included directory; also create a new directory, add a file, and reference it from an existing file. Verify projectService recognizes both without eslint.restart, compare typed diagnostics with a fresh CLI run, and check that ordinary linting and CLI termination remain unaffected.
- **Behavior:**

  > Files covered by the workspace's TypeScript configuration should be recognized by projectService when created during an active editor session, without restarting ESLint. Acceptance should include the reported new-directory, new-file, then reference sequence and relevant changes to existing files. Genuine out-of-project configuration errors must remain visible, and ordinary linting must not incur unconditional project-service rebuilds.
- **Trace:**

  > The reported error originates in typescript-eslint's project service; the extension displays the parser result. Current client/src/client.ts createClientOptions watches ESLint configuration and package metadata, while server/src/eslintServer.ts handles those events by clearing extension caches and refreshing diagnostics. server/src/eslint.ts withClass constructs ESLint classes but exposes no project-service watcher or reload contract. The partial upstream mitigation in https://github.com/typescript-eslint/typescript-eslint/pull/9853 does not establish that contract. https://github.com/microsoft/vscode-eslint/issues/1774 is related cross-file freshness work, not a verified duplicate. Begin by separating residual parser behavior from missing extension integration on current versions; preserve workspace configuration ownership and avoid unconditional full-session relinting or server restarts.
- **Open decisions:**
  - Should the editor/parser interoperability contract expose IDE-owned watcher registration and events, or signal a long-lived IDE session so the parser owns its watchers, including lifecycle and disposal responsibilities?
