# Issue #1734 — A change to eslint.debug requires VSCode restart if the ESLint server was already running

[https://github.com/microsoft/vscode-eslint/issues/1734](https://github.com/microsoft/vscode-eslint/issues/1734)

## Summary

Keep open and classify the manual-restart failure as a bug: current client code captures eslint.debug when the language client is created and does not recompute its launch environment during an ordinary server restart. Automatic restart on setting changes is a separate enhancement, not necessary to address the confirmed defect.

## Change summary

Changing eslint.debug after the server starts does not affect debug output even after ESLint: Restart ESLint Server, requiring an editor restart instead.

## Best solution

Make an explicit ESLint server restart honor the current eslint.debug setting without restarting VS Code, within the client-side launch lifecycle. Preserve existing restart and output-channel behavior; investigate the later config-reloading report separately unless its reproduction establishes the same cause.

## Plan brief

- **Likely files:** `client/src/client.ts`, `client/src/extension.ts`
- **Validation:** In an Extension Development Host with a working ESLint formatter, start the server with eslint.debug=false, change it to true, run ESLint: Restart ESLint Server, and format a document. Confirm ESLint debug messages appear without reloading the editor. Then set it to false, restart the server again, and confirm subsequent formatting produces no ESLint debug messages while formatting and ordinary server logging remain functional.
- **Behavior:**

  > After the ESLint server has started, changing eslint.debug and explicitly restarting the ESLint server must apply the new debug setting without restarting VS Code. Verify both enabling and disabling debug output on subsequent formatting operations. Existing formatting, diagnostics, and ordinary restart logging must continue to work. Automatically restarting when settings change is outside this narrowly defined defect.
- **Trace:**

  > ESLintClient.create in client/src/client.ts passes a concrete createServerOptions result to LanguageClient at construction. That helper reads eslint.debug and constructs the child-process DEBUG environment once. The eslint.restart handler in client/src/extension.ts recreates the client only after State.StartFailed; an ordinary running-server restart reuses the client and its captured server options. The maintainer establishes manual restart as the expected behavior at https://github.com/microsoft/vscode-eslint/issues/1734#issuecomment-1818468767. The diagnosis is confirmed by current-source inspection, but the repository's available client tests cover glob conversion rather than restart lifecycle, so validation remains to be established. Do not change runtime-selection defaults, workspace trust behavior, output-pane selection, or assume the later eslint.config.js symptoms share this cause.

## Evidence

- **Current-source root cause:** client/src/client.ts:147 constructs LanguageClient with the result of createServerOptions(context.extensionUri). createServerOptions at lines 398–423 reads eslint.debug once and sets env.DEBUG to eslint:*,-eslint:code-path,eslintrc:* only when that captured setting is true.
- **Restart retains captured options:** client/src/extension.ts:143–163 recreates the client only when its state is StartFailed. For the reporter's already-running server, eslint.restart calls client.restart() on the existing client without calling createServerOptions again. The configuration-change handler in client/src/client.ts:179–193 updates document validation eligibility, not the launch environment.
- **Maintainer-defined expectation:** https://github.com/microsoft/vscode-eslint/issues/1734#issuecomment-1818468767 explicitly says restarting the server should be enough and identifies failure to recompute the debug environment as the likely defect. https://github.com/microsoft/vscode-eslint/issues/1734#issuecomment-1818970625 independently confirms that manual server restart fails whereas restarting the IDE works.
- **Existing capability does not satisfy the report:** package.json:420–425 exposes eslint.debug as a window-scoped boolean, and README.md:373 documents debug output in the ESLint output channel. The existing eslint.restart command does not refresh that setting on the normal restart path, so neither documented surface removes the editor-restart requirement.
- **Canonical search:** Read-only GitHub searches for eslint.debug, debug, and restart found no verified canonical owning this symptom. https://github.com/microsoft/vscode-eslint/issues/91 concerns workspace-wide linting; https://github.com/microsoft/vscode-eslint/issues/1727 concerns runtime selection; https://github.com/microsoft/vscode-eslint/issues/1898 concerns output-pane selection; https://github.com/microsoft/vscode-eslint/issues/2205 concerns automatically showing output. None would resolve the captured debug environment.
- **Later report has a separate evidentiary boundary:** https://github.com/microsoft/vscode-eslint/issues/1734#issuecomment-4949835061 additionally reports config changes and nonfunctional output after restart. The maintainer requested a reproduction for those broader symptoms at https://github.com/microsoft/vscode-eslint/issues/1734#issuecomment-4956595299; that request does not invalidate the original concrete debug-toggle steps or the source-confirmed launch-options defect.
- **Validation limitation:** The checkout was inspected without execution or modification. client/package.json runs compiled Node tests, and the available client test, client/src/tests/glob.test.ts, exercises glob conversion rather than the VS Code client/server restart lifecycle; no existing executable regression check for this surface was identified.
