# Issue #1734 — A change to eslint.debug requires VSCode restart if the ESLint server was already running

[https://github.com/microsoft/vscode-eslint/issues/1734](https://github.com/microsoft/vscode-eslint/issues/1734)

## Summary

Current main confirms that `eslint.debug` is captured when the language client is created and is not recomputed by the normal restart command. This is a localized client lifecycle defect, so the issue should remain open and be classified as a bug rather than a feature request.

## Change summary

Changing `eslint.debug` after activation does not take effect, even after invoking `ESLint: Restart ESLint Server`; reloading VS Code is required.

## Best solution

Update the client restart path so server launch options, including the `DEBUG` environment variable derived from `eslint.debug`, are recomputed before the server starts again. Automatically restarting when this launch-time setting changes can remain a separate product choice; the explicit restart command should at minimum honor the current value.

## Evidence

- **source-traced stale launch options:** In `client/src/client.ts`, `ESLintClient.create` constructs the `LanguageClient` once with `createServerOptions(context.extensionUri)` (around line 147). `createServerOptions` reads `eslint.debug` and conditionally sets `env.DEBUG` (around lines 398-419), so that environment is captured at client construction time.
- **restart reuses the existing client:** In `client/src/extension.ts`, the normal `eslint.restart` path calls `client.restart()` on the existing `LanguageClient` (around lines 143-161). It recreates the client only after `State.StartFailed`, so a successful running client retains the original server options and stale debug environment.
