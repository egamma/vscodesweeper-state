# Issue #1074 — doesn't apply right fix comment in jsx/tsx context

[https://github.com/microsoft/vscode-eslint/issues/1074](https://github.com/microsoft/vscode-eslint/issues/1074)

## Summary

The context-aware JSX/TSX disable-comment capability remains missing on current main, and later reports have been consolidated into this issue as the canonical request. The current implementation selects one comment style for the entire document language and cannot distinguish JavaScript from JSX expression context.

## Change summary

Generate syntactically valid ESLint disable comments based on whether a diagnostic in a JSX/TSX document occurs inside JSX markup or ordinary JavaScript/TypeScript code.

## Best solution

Keep this as the canonical feature request and update the server's disable-rule code-action path to determine the ESTree context at the diagnostic location, using the parser from ESLint's resolved configuration as the maintainer proposed. It should emit JSX-safe `{/* eslint-disable-next-line ... */}` syntax inside JSX while preserving normal line or block comments elsewhere, without depending on VS Code-specific language services.

- **Evidence:** The public architectural goals include “Provide rich code actions (fix all, rule disable, suggestions) and formatting integration” and transparently supporting ESLint parser and API differences.

## Evidence

- **current source gap:** server/src/languageDefaults.ts assigns one line and block comment pair to each language ID; javascriptreact and typescriptreact both use `//` and `/* ... */`, with no representation of JSX expression-container syntax.
- **context-blind edit generation:** server/src/eslintServer.ts:createDisableLineTextEdit chooses only between LanguageDefaults.getLineComment(textDocument.languageId) and getBlockComment(textDocument.languageId), then inserts that comment at the diagnostic line without inspecting the parsed syntax context.
- **existing setting is insufficient:** The shipped `eslint.codeAction.disableRuleComment` setting can select separate-line versus same-line placement and line versus block comment style, but neither option generates the required JSX expression-container wrapper, so it does not cover the central request.
- **maintainer-endorsed direction:** The maintainer proposed resolving the configured ESLint parser, creating an ESTree for JSX/TSX files, and walking parent nodes to determine whether the diagnostic is inside a JSXElement: https://github.com/microsoft/vscode-eslint/issues/1074#issuecomment-1206470902
- **canonical status:** The broader language-context report was manually closed as a duplicate of this issue, confirming that this remains the canonical tracker: https://github.com/microsoft/vscode-eslint/issues/2029#issuecomment-3011955189
- **later fix does not cover JSX context:** https://github.com/microsoft/vscode-eslint/pull/2042 only changed the fallback block marker for unknown language IDs from `/**` to `/*`; it did not add syntax-context detection for JSX/TSX.
