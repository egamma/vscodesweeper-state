# Issue #1074 — doesn't apply right fix comment in jsx/tsx context

[https://github.com/microsoft/vscode-eslint/issues/1074](https://github.com/microsoft/vscode-eslint/issues/1074)

## Summary

Context-aware disable comments remain missing: current main chooses comment delimiters by document language, not by JSX/TSX position. Keep this accepted request open; the related fallback fix and same-line setting do not deliver automatic context detection.

## Change summary

Generate rule-disable comments appropriate to the local JSX/TSX context instead of inserting JavaScript comments into JSX children.

## Best solution

Add context-aware disable-comment generation in the language server while preserving ordinary JavaScript/TypeScript commenting and editor independence. Investigate the maintainer's configured-parser approach across supported ESLint configuration styles before implementing it.

## Plan brief

- **Likely files:** `server/src/eslintServer.ts`, `server/src/eslint.ts`, `server/src/languageDefaults.ts`
- **Validation:** In minimal JSX and TSX workspaces with configured parsers, invoke Disable rule for this line on violations inside JSX children and ordinary JS/TS statements. Verify that generated edits remain syntactically valid, suppress the intended diagnostic after revalidation, and preserve unrelated diagnostics; repeat with flat and legacy configuration and with VS Code's built-in TypeScript extension disabled.
- **Behavior:**

  > Rule-disable quick fixes should emit comments valid at the diagnostic's local JSX/TSX position. A JSX child position requiring an expression-wrapped comment must not receive literal JavaScript comment text, while ordinary JavaScript/TypeScript statements must retain valid conventional comments. Acceptance requires both valid source and suppression of the intended diagnostic without suppressing unrelated violations. The behavior should not depend on an editor-specific smart language service being installed.
- **Trace:**

  > LanguageDefaults in server/src/languageDefaults.ts provides document-wide comment delimiters, including identical JavaScript delimiters for javascriptreact and typescriptreact. createDisableLineTextEdit and createDisableSameLineTextEdit in server/src/eslintServer.ts combine those delimiters with settings and diagnostic positions but obtain no AST context. ESLint configuration resolution in server/src/eslint.ts already calls calculateConfigForFile, although its inspected config type describes legacy parser fields rather than a general parser-context contract. The maintainer's direction at https://github.com/microsoft/vscode-eslint/issues/1074#issuecomment-1206470902 is to investigate the configured parser rather than depend on VS Code or TSServer. Uncertainty starts at acquiring compatible positional context across parser APIs and flat versus legacy configuration, then identifying a syntactically valid directive location. Preserve ordinary commenting, existing rule-disable settings, workspace-owned parser selection, and the server's usefulness to other editors; Markdown defaults and the separate same-line action request are outside this scope.

## Evidence

- **Current source still lacks positional context:** server/src/languageDefaults.ts maps javascriptreact and typescriptreact to // and /* */. server/src/eslintServer.ts:496–529, createDisableLineTextEdit, selects those delimiters using textDocument.languageId and inserts a comment without inspecting JSX ancestry or adding JSX expression braces.
- **Existing-capability check:** package.json:426–460 exposes eslint.codeAction.disableRuleComment.enable, location, and commentStyle. Selecting block produces /* eslint-disable-next-line ... */ without the JSX-required braces; selecting sameLine changes placement, not syntactic context. Neither setting satisfies automatic JSX/TSX-aware commenting.
- **Maintainer accepted an extension-side investigation:** https://github.com/microsoft/vscode-eslint/issues/1074#issuecomment-1206470902 proposes using the workspace-configured parser to obtain an ESTree and locate JSXElement ancestry. The full comment explains why editor language services and syntax tokens are unreliable dependencies. This is accepted enhancement work, not an established out-of-scope decision.
- **Related fallback fix does not implement this request:** https://github.com/microsoft/vscode-eslint/pull/2042 changes the unknown-language block-comment fallback from /** to /*. Its scope does not include position-aware JSX/TSX comments; the current React-language mappings and insertion path still lack that behavior.
- **Canonical-search result:** Open-issue searches for JSX, comment titles, and disable-comment terminology found no older issue owning this request. https://github.com/microsoft/vscode-eslint/issues/2029 is closed and explicitly points to this issue as its canonical. https://github.com/microsoft/vscode-eslint/issues/2224 is open but concerns Markdown delimiters, not mixed JSX/JavaScript context; shipping it would not satisfy this request.
- **Same-line request is distinct:** https://github.com/microsoft/vscode-eslint/issues/2088 remains open. Its reporter explicitly distinguishes always-available same-line disabling from automatic context detection, and the maintainer acknowledges the distinction. It is also newer than this re-reviewed item and cannot serve as its duplicate canonical.
- **Parser integration remains to be designed:** server/src/eslint.ts uses calculateConfigForFile during configuration resolution, but the inspected disable-comment path does not consume a parser or AST. The existing ESLintConfig alias describes legacy parser fields, so the proposed parser-based approach still needs investigation for flat config and parser compatibility.
