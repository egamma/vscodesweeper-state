# Issue #1240 — Reporting errors from node_module and no way to suppress/disable (also ignores .eslintignore)`

[https://github.com/microsoft/vscode-eslint/issues/1240](https://github.com/microsoft/vscode-eslint/issues/1240)

## Summary

The command-line reproduction confirms that legacy ESLint config resolution fails before ESLint consults the ignore rules, so the error originates in ESLint rather than the extension. The upstream issue was declined because eslintrc was frozen, but this issue should remain open with upstream routing rather than be closed against that closed report.

## Change summary

Avoid reporting legacy ESLint configuration-loading errors when an opened file under node_modules should have been ignored.

## Best solution

ESLint's ignore check must succeed before the extension can suppress validation; for legacy eslintrc projects, the practical end state is migration to flat config or an upstream ESLint correction. The extension could separately consider a path-based validation exclusion feature, but `eslint.onIgnoredFiles` and `eslint.validate` do not currently cover that request.

  > Thanks for the report and reproduction. The command-line result confirms that this error comes from legacy ESLint config resolution: ESLint attempts to load the dependency's `eslintConfig` before it can determine that the file is ignored. That behavior was confirmed upstream in https://github.com/eslint/eslint/issues/14686, although ESLint declined to change the frozen eslintrc implementation. The extension delegates both config and ignore resolution to the workspace-installed ESLint, and `eslint.onIgnoredFiles` only controls warnings after ESLint successfully identifies a file as ignored; it cannot suppress this configuration-loading failure.

## Evidence

- **confirmed CLI behavior:** The discussion reproduces the same failure with `yarn eslint node_modules/stylelint/lib/cli.js`, establishing that the extension is not uniquely producing the configuration error.
- **upstream diagnosis:** ESLint maintainers confirmed the legacy eslintrc behavior was most likely a bug but declined to alter the frozen configuration system: https://github.com/eslint/eslint/issues/14686#issuecomment-892878734 and https://github.com/eslint/eslint/issues/14686#issuecomment-946270625.
- **current extension path:** In `server/src/eslint.ts`, `resolveSettings()` calls `eslintClass.isPathIgnored(filePath)` to decide whether validation should run; errors thrown by ESLint during that operation are caught and surfaced. Ignore and config resolution are therefore delegated to the workspace's ESLint library.
- **existing settings gap:** `eslint.onIgnoredFiles` in `package.json` controls warnings for successfully identified ignored files, while `eslint.validate` selects languages rather than filesystem paths; neither suppresses an ESLint configuration error raised while determining ignore status.
