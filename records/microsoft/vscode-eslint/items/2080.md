# Issue #2080 — multithreaded/--concurrency support?

[https://github.com/microsoft/vscode-eslint/issues/2080](https://github.com/microsoft/vscode-eslint/issues/2080)

## Summary

This remains a valid performance feature request, but the current LSP path validates one document at a time with `lintText`, while ESLint's concurrency support is designed to process multiple files. No broader canonical issue or existing LSP capability covers the request.

## Change summary

Investigate whether ESLint's multithreaded concurrency support can improve editor validation, particularly for plugins that inspect an entire project.

## Best solution

Keep the request in Backlog while determining whether the server can safely batch multiple document validations through ESLint without losing unsaved-buffer fidelity or responsiveness. Also clarify that project-wide lint tasks can already receive `--concurrency` through `eslint.lintTask.options`, whereas plugins that scan other files internally may need optimization in the plugin itself.

## Evidence

- **current validation path:** `server/src/eslint.ts` implements `validate()` by reading one open document and calling `eslintClass.lintText(content, { filePath: file, ... })`; it does not enumerate or submit a collection of files that ESLint could distribute among workers.
- **ESLint concurrency semantics:** https://eslint.org/blog/2025/08/multithread-linting/ explains that each worker processes one file and that automatic thread selection happens after file enumeration. That model offers no direct parallelism when the extension submits only the focused document.
- **existing configuration surface:** `package.json` exposes `eslint.options` for ESLint constructor options and `eslint.lintTask.options` for command-line options when linting the whole workspace. Passing a constructor concurrency option does not by itself turn the server's single-file `lintText` calls into a multi-file workload.
- **maintainer assessment:** The maintainer said the request could be investigated but expected limited impact because the extension continuously validates only the currently focused file; the issue is assigned to the Backlog milestone and remains labeled `feature-request`.
- **canonical search:** Repository searches for concurrency, multithreading, and parallel linting found no other open issue owning this work; https://github.com/microsoft/vscode-eslint/issues/2080 is the sole matching open request.
- **plugin-specific limitation:** The graphql-eslint use case may scan project files from inside the plugin while ESLint is linting one document. ESLint's file-level worker pool does not necessarily parallelize that plugin-internal scan, so this scenario needs measurement before selecting an extension-side design.
