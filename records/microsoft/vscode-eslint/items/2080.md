# Issue #2080 — multithreaded/--concurrency support?

[https://github.com/microsoft/vscode-eslint/issues/2080](https://github.com/microsoft/vscode-eslint/issues/2080)

## Summary

This is a valid but unresolved performance feature request. The server currently validates one document at a time through `lintText`, while ESLint's concurrency support distributes multiple files, so merely passing the constructor option would not meaningfully parallelize the existing LSP flow.

## Change summary

Use ESLint 9.34's multithreaded concurrency support to improve interactive validation performance, particularly for plugins that inspect an entire project.

## Best solution

Benchmark the reported graphql-eslint scenario and determine whether the server can safely batch independent pending document validations through an ESLint API that supports multiple targets. Any implementation should preserve single-document responsiveness and remain opt-in where worker startup or plugin initialization would make validation slower.

The server currently validates each document through ESLint's `lintText` API, while ESLint's concurrency feature is designed to distribute multiple target files across workers. `eslint.options` can already pass constructor options through to ESLint, but setting `concurrency` alone would not create a useful multi-file workload in the current validation path. ## Evidence

- **current validation path:** `server/src/eslint.ts` invokes `eslintClass.lintText(content, { filePath, ... })` for document validation, producing one target per call rather than a multi-file workload.
- **existing option pass-through:** `eslint.options` is exposed in `package.json`, and `ESLint.withClass` in `server/src/eslint.ts` merges that object into the options used to construct the workspace's ESLint class. This can pass `concurrency`, but it does not change the single-document `lintText` architecture.
- **ESLint concurrency scope:** ESLint's documentation at https://eslint.org/blog/2025/08/multithread-linting/ describes worker threads processing multiple target files concurrently; the largest gains come from linting many files, whereas this extension currently supplies one document per validation call.
- **maintainer assessment:** The maintainer noted at https://github.com/microsoft/vscode-eslint/issues/2080#issuecomment-3346749848 that the extension continuously validates only the currently focused file and therefore expected limited impact.
- **project-scanning use case:** The follow-up at https://github.com/microsoft/vscode-eslint/issues/2080#issuecomment-3762951387 identifies graphql-eslint duplicate-operation analysis as a concrete project-wide workload worth benchmarking.
