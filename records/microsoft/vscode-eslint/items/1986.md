# Issue #1986 — Issues with PNPM module resolution

[https://github.com/microsoft/vscode-eslint/issues/1986](https://github.com/microsoft/vscode-eslint/issues/1986)

## Summary

The issue should remain open: multiple users reproduced a pnpm 10-specific divergence where the workspace ESLint CLI succeeds but the extension cannot resolve auto-installed peer plugins. The earlier maintainer reproduction used dependencies installed by npm, and the issue was reopened after a clean pnpm installation demonstrated that the failure persisted.

## Change summary

Make ESLint plugin resolution through the extension behave consistently with `pnpm eslint` when pnpm 10 auto-installs a shareable configuration's peer dependencies without publicly hoisting them.

## Best solution

Reproduce from https://github.com/angryermine/vscode-eslint-pnpm by removing any npm-created `node_modules` and installing exclusively with pnpm 10, then determine which pnpm-provided module-resolution context is missing when the server loads ESLint through its Node API. The extension should preserve CLI-equivalent resolution for installed peer plugins, or provide a precise diagnostic if supporting that environment would require invalid phantom-dependency behavior.

## Evidence

- **minimal reproduction:** https://github.com/angryermine/vscode-eslint-pnpm declares ESLint 8.57.1 and eslint-config-airbnb 19.0.4 under pnpm 10.21.0; its lockfile has autoInstallPeers enabled and records eslint-plugin-jsx-a11y and the other Airbnb peer plugins as installed.
- **independent confirmation:** https://github.com/microsoft/vscode-eslint/issues/1986#issuecomment-3630973937 records the same repository failing in vscode-eslint 3.0.20 with pnpm 10.21.0 while the CLI succeeds, including the extension's `Cannot find module 'eslint-plugin-jsx-a11y'` stack.
- **reproduction discrepancy explained:** https://github.com/microsoft/vscode-eslint/issues/1986#issuecomment-3660905000 reports that Codespaces initially installed the reproduction with npm, masking the defect; after removing `node_modules` and reinstalling with pnpm, the extension failed.
- **current loading path:** On current main, server/src/eslint.ts resolves the workspace ESLint entry point with `Files.resolve`, and server/src/eslintServer.ts loads that path directly with `require`. The `eslint.nodePath` setting is used only while resolving the ESLint module; package.json describes it as a path added when resolving that module, so it does not establish general pnpm peer-plugin resolution.
- **pnpm behavior:** https://github.com/pnpm/pnpm/issues/8878#issuecomment-2546442011 documents that pnpm 10 removed the previous default `*eslint*` public-hoist pattern. Adding `public-hoist-pattern[]=*eslint*` is a confirmed workaround, but it changes dependency layout rather than resolving the extension-versus-CLI divergence.
- **no canonical duplicate:** Repository searches for pnpm plugin resolution, pnpm nodePath, and peer-dependency reports found no other open vscode-eslint issue owning this work; the supplied candidate https://github.com/microsoft/vscode-eslint/issues/1355 concerns formatter availability during server initialization and is unrelated.
