# Issue #1986 — Issues with PNPM module resolution

[https://github.com/microsoft/vscode-eslint/issues/1986](https://github.com/microsoft/vscode-eslint/issues/1986)

## Summary

The thread now contains a minimal repository and independent pnpm 10 confirmations showing that the extension's direct ESLint-library invocation resolves legacy-config peers differently from `pnpm eslint`. Keep this open while the maintainer decides whether vscode-eslint should reproduce pnpm's launch environment or document pnpm's explicit ESLint-hoisting requirement.

## Change summary

Make ESLint plugin resolution under pnpm 10 behave consistently between the VS Code extension and the `pnpm eslint` command.

## Best solution

Reproduce from https://github.com/angryermine/vscode-eslint-pnpm after removing any npm-installed `node_modules` and installing exclusively with pnpm 10, then compare the environment and resolution path used by `pnpm eslint` with the direct library load in `server/src/eslint.ts`. Based on that result, either add a narrowly scoped pnpm-compatible resolution mechanism or clearly document `publicHoistPattern: ['*eslint*']` as required for legacy shareable configs whose peers are not otherwise resolvable.
