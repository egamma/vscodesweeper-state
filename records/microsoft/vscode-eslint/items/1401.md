# Issue #1401 — Possible to pass environment variables to eslint server?

[https://github.com/microsoft/vscode-eslint/issues/1401](https://github.com/microsoft/vscode-eslint/issues/1401)

## Summary

Keep this accepted feature request open: the extension still has no dedicated way to configure arbitrary project-specific environment variables for its ESLint server. The existing NODE_ENV setting and shell-launch workaround do not cover the requested API_TOKEN configuration, and no verified open canonical owns that work.

## Change summary

Allow projects to supply arbitrary environment variables to the ESLint server without launching VS Code from a specially configured shell.

## Best solution

Provide a documented project-specific server-environment configuration in client/, preserving inherited environment behavior and existing eslint.nodeEnv support. Decide the configuration source and multi-root scope before implementation; ESLint and the GraphQL plugin should continue consuming the environment normally.

## Vision fit

- **Fit:** aligned
- **Reason:** Making the server environment configurable helps the extension run the workspace's existing ESLint configuration without changing plugin semantics.
- **Evidence:** Layer 1: "The workspace's configuration is the user's to own." Layer 2 identifies the Node runtime story and configuration resolution as durable themes.

## Plan brief

- **Likely files:** `package.json`, `client/src/client.ts`, `client/src/extension.ts`, `README.md`
- **Validation:** In a maintainer implementation session, use a minimal ESLint configuration or test plugin that reports whether process.env.API_TOKEN equals a non-secret sentinel. Check inherited variables, existing eslint.nodeEnv behavior, the selected restart semantics, and the agreed multi-root behavior. Do not log actual credentials.
- **Behavior:**

  > A project whose ESLint plugin reads an arbitrary environment variable should be able to supply that variable to the ESLint server without changing the environment used to launch VS Code. Different projects must receive their intended values, and existing inherited environment behavior and eslint.nodeEnv support must remain intact. Acceptance should use non-secret sentinel values and verify the documented scope and restart behavior.
- **Trace:**

  > client/src/client.ts creates a single LanguageClient in ESLintClient.create(); createServerOptions() constructs the server process options and currently supplies only DEBUG and NODE_ENV overrides. It reads configuration without a resource URI, and getCurrentServerWorkingDirectory() uses the workspace folder only in the single-folder case. client/src/extension.ts owns eslint.restart and client startup, so environment-change lifecycle behavior is relevant there. package.json and README.md expose runtime arguments and NODE_ENV configuration but no arbitrary-variable interface. The remaining uncertainty is the public configuration contract, not ESLint rule behavior; preserve the plugin's normal process.env consumption and do not change lint semantics. https://github.com/microsoft/vscode-eslint/issues/324 and https://github.com/microsoft/vscode-eslint/issues/983 provide historical context but are closed and cannot absorb this request.
- **Open decisions:**
  - Should users supply arbitrary environment values directly through extension settings, through a referenced environment file, or through both supported interfaces?
  - Should the environment configuration apply to the whole workspace/window, or must different folders in a multi-root workspace receive isolated values?
