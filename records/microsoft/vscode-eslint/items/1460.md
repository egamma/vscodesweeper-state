# Issue #1460 — Problems should not dissapear on file close

[https://github.com/microsoft/vscode-eslint/issues/1460](https://github.com/microsoft/vscode-eslint/issues/1460)

## Summary

Keep open: current settings do not provide persistent diagnostics for closed files, and the maintainer identified workspace diagnostics as the required direction while noting performance concerns. The related workspace-linting and core task-restoration issues do not fully own this request.

## Change summary

Retain ESLint problems when a file closes, including problems originally reported by a lint task, without preserving stale results after relevant changes.

## Best solution

Design an optional, performance-conscious persistent diagnostic mode in the extension, consistent with the maintainer's workspace-diagnostic requirement and with explicit invalidation behavior. Coordinate the task-result lifecycle with https://github.com/microsoft/vscode/issues/61140 rather than treating that narrower core issue as ownership of the entire request.

## Plan brief

- **Likely files:** `client/src/client.ts`, `client/src/tasks.ts`, `server/src/eslintServer.ts`, `$shared/settings.ts`, `package.json`
- **Validation:** In a minimal workspace, enable the proposed mode, produce an ESLint problem, close its file, and verify the problem remains. Repeat by running the whole-folder lint task on a closed file, opening the reported problem, and closing the file. Then fix or externally modify the file and verify stale results are refreshed or invalidated. Verify the existing opened-file behavior remains available and assess validation cost on a large workspace.
- **Behavior:**

  > Users should be able to retain known ESLint problems after closing a file, including problems first discovered through a lint task. Closing an unchanged file must not lose the result, while relevant file changes must not leave stale diagnostics presented as current. The existing opened-file workflow should remain available for users who do not want persistent results. Acceptance includes both editor-produced and task-produced diagnostics and a performance assessment.
- **Trace:**

  > The current server advertises workspaceDiagnostics: false in server/src/eslintServer.ts and validates documents held by its TextDocuments collection. client/src/client.ts forwards closure and removes synchronized documents; its diagnostic pulling is document-based. client/src/tasks.ts separately creates a whole-folder shell task with the $eslint-stylish problem matcher, so task-result ownership is a separate lifecycle to investigate. The maintainer's direction is recorded at https://github.com/microsoft/vscode-eslint/issues/1460#issuecomment-1336976022. https://github.com/microsoft/vscode/issues/61140 covers task-result restoration but does not cover the entire extension feature. The uncertainty is how to provide consistent persistent results and invalidation without imposing unconditional workspace-wide linting costs; preserve workspace ESLint configuration and the existing default workflow.

## Evidence

- **Maintainer-defined boundary:** https://github.com/microsoft/vscode-eslint/issues/1460#issuecomment-1336976022 explains that persistent results require a workspace diagnostic provider rather than the current opened-file model. https://github.com/microsoft/vscode-eslint/issues/1460#issuecomment-1338912510 distinguishes workspace lint tasks from extension validation and expresses performance concerns, not a definitive rejection.
- **Current diagnostic architecture:** server/src/eslintServer.ts:215-219 advertises workspaceDiagnostics: false. Its document diagnostic handler obtains the document from documents.get() and returns an empty report when it is unavailable. client/src/client.ts:464-479 configures document-based diagnostic pulling with onTabs: false; its didClose middleware removes the document from syncedDocuments and forwards closure.
- **Existing-capability check:** The configuration and command contributions in package.json contain no closed-file retention setting. eslint.lintTask.enable and eslint.lintTask.options provide a whole-folder task, implemented by FolderTaskProvider.getTask() in client/src/tasks.ts using the $eslint-stylish problem matcher; they do not implement persistent language-server diagnostics. eslint.revalidate explicitly revalidates open files only.
- **Linked core report:** https://github.com/microsoft/vscode/issues/155172 is closed. Its maintainer response at https://github.com/microsoft/vscode/issues/155172#issuecomment-1185293006 identifies extension-managed diagnostics and directs the discussion to this extension; it is neither an open canonical nor evidence of a landed fix.

Its maintainer discussion says coordination with the live-diagnostic extension is needed. It addresses the task-derived example, not retention of all diagnostics produced by this extension.

This accepted Backlog feature has 25 upvotes, repeated requests, and explicit interest in an optional setting; age and existing behavior are not grounds to decline it.
