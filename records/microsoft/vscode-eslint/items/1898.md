# Issue #1898 — Restarting an extension when that extension's output is selected in the "Output" pane should not change which extension is selected in the "Output" pane.

[https://github.com/microsoft/vscode-eslint/issues/1898](https://github.com/microsoft/vscode-eslint/issues/1898)

## Summary

Keep open: the current manual-restart path still disposes and recreates the client-owned ESLint output channel, rather than preserving its selection. The related focus reports are closed, their proposed fix never merged, and no verified older canonical owns this request.

## Change summary

Preserve the selected ESLint output channel when the user runs ESLint: Restart ESLint Server.

## Best solution

Make the ESLint client's output-channel lifecycle preserve an already-selected channel across manual restarts, without requiring users to reopen it or changing whether a hidden panel is revealed. This can be addressed in client/ using the language client's existing external-channel support; coordinate the separate reveal-on-restart request at https://github.com/microsoft/vscode-eslint/issues/2205 without merging their distinct behaviors.

## Plan brief

- **Likely files:** `client/src/client.ts`, `client/src/extension.ts`
- **Validation:** In a VS Code extension-development session with a working ESLint workspace, select ESLint in the visible Output dropdown and invoke ESLint: Restart ESLint Server repeatedly; verify ESLint remains selected and new server logs appear. Repeat with Tasks selected and with the panel hidden to verify restart does not select ESLint or reveal the panel unexpectedly. The existing client tests cover glob behavior, not this workbench surface.
- **Behavior:**

  > A user viewing ESLint output should continue viewing that output after a successful manual server restart, rather than seeing the dropdown fall back to Tasks or another channel. Newly emitted logs should remain available in that channel. Verify repeated restarts preserve selection, while a different selected channel and a hidden Output panel retain their existing state. Automatically revealing output is a separate feature, not part of this request.
- **Trace:**

  > The ordinary eslint.restart handler in client/src/extension.ts delegates to LanguageClient.restart(); ESLintClient.create and createClientOptions in client/src/client.ts leave output-channel ownership to the language client. The exact pinned vscode-languageclient 10.1.0 implementation calls stop() during manual restart, and shutdown disposes its internally owned output channel before start() recreates it. External output-channel ownership is supported by that dependency, so an extension-side solution is plausible without changing ESLint or VS Code core. The State.StartFailed branch separately recreates the entire client and must retain its environment-refresh behavior. https://github.com/microsoft/vscode-eslint/pull/2124 is a closed, unmerged implementation lead, not a shipped fix. No editor-selection reproduction was executed, and the existing client test surface does not validate Output dropdown state; the session should establish that check first. Keep explicit Show Output Channel and error-reporting behavior intact, and treat https://github.com/microsoft/vscode-eslint/issues/2205 as a separate reveal-policy request.
