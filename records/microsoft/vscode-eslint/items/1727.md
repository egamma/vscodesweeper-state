# Issue #1727 — Prefer to use node from environment

[https://github.com/microsoft/vscode-eslint/issues/1727](https://github.com/microsoft/vscode-eslint/issues/1727)

## Summary

This remains a valid runtime-selection feature request: `eslint.runtime: "node"` provides an opt-in, but the extension still defaults to VS Code's runtime. The maintainer has identified a workspace-trust boundary for changing that behavior, so this security-sensitive Backlog item should remain open for an explicit product and compatibility decision.

## Change summary

Prefer a project or environment-selected Node runtime in trusted workspaces, falling back to VS Code's runtime when an environment runtime is unavailable.

## Best solution

Add an explicit runtime-strategy setting in `package.json` and apply it while constructing the language server options in `client/src/client.ts`; the environment strategy should operate only in trusted workspaces, define multi-root and remote behavior, and preserve a safe fallback to VS Code's runtime. Migration must avoid silently changing existing users' execution environment.

## Vision fit

- **Fit:** aligned
- **Reason:** Selecting the workspace's intended Node version in trusted workspaces advances the extension's durable Node-runtime and configuration-resolution themes while respecting its security and compatibility guardrails.
- **Evidence:** The vision identifies `eslint.runtime`, remote environments, and the Node runtime story as durable areas of investment, while also stating that the extension adapts to the opened workspace and that version breadth and editor security have user-facing costs.

## Evidence

- **existing capability is opt-in only:** `package.json` defines `eslint.runtime` with a default of `null`; the README documents `eslint.runtime: "node"` as the way to use the default system Node version. This does not satisfy the request to make environment-based selection the trusted-workspace default.
- **current runtime path:** `client/src/client.ts` reads the nullable `eslint.runtime` setting and passes an undefined runtime to the language client when it is unset, retaining VS Code's runtime. The same code limits workspace-based server cwd selection to trusted, single-folder, file-scheme workspaces.
- **maintainer direction:** In https://github.com/microsoft/vscode-eslint/issues/1727, the maintainer states that changing the default risks breaking existing users and later narrows the viable design to using the `node` command by default only in trusted workspaces because runtime selection is security-sensitive.
- **open implementation lead is incomplete:** https://github.com/microsoft/vscode-eslint/pull/1977 remains open and addresses server cwd so project-aware tools such as Volta can resolve Node, but it does not change the default runtime strategy; the discussion explicitly notes that it does not solve the central request in this issue.
- **related report consolidated here:** https://github.com/microsoft/vscode-eslint/issues/1953 was closed after the maintainer moved its project-local Node-resolution concern into this issue, confirming that #1727 remains the broader runtime-selection tracking item.
