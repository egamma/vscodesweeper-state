# Issue #1727 — Prefer to use node from environment

[https://github.com/microsoft/vscode-eslint/issues/1727](https://github.com/microsoft/vscode-eslint/issues/1727)

## Summary

This remains an accepted runtime-selection feature request: the existing `eslint.runtime` setting provides manual opt-in but does not choose a project or environment Node by default. The maintainer identified executing a workspace-resolved binary as security-sensitive and proposed limiting any new default to trusted workspaces, so this requires an explicit product and trust-boundary design and must remain open.

## Change summary

Prefer the Node runtime selected by the workspace environment, with a safe fallback, instead of using VS Code's bundled Node by default.

## Best solution

Introduce an explicit runtime-selection strategy whose behavior is clearly documented: in trusted workspaces it may resolve `node` from the workspace environment, while untrusted workspaces retain the extension-host runtime. Preserve `eslint.runtime` for explicit paths and migration compatibility, and define deterministic behavior for multi-root and remote workspaces.

## Evidence

- **current setting surface:** `package.json` defines `eslint.runtime` as a machine-overridable string or null, defaults it to null, and describes it as the location of the Node binary used to run ESLint. This enables explicit opt-in but does not implement an environment-first strategy.
- **current launch behavior:** `client/src/client.ts` reads `eslint.runtime` in `createServerOptions()` and passes it directly to the language client's run and debug server options; when unset, no environment-resolved `node` runtime is selected.
- **security-sensitive design:** In the issue discussion, the maintainer states that runtime selection is security-sensitive and proposes using the `node` command as the default only in trusted workspaces. Security-sensitive issues are protected from automated close judgments.
- **existing trust handling:** `client/src/client.ts` already checks `Workspace.isTrusted` when selecting the language-server working directory, providing an existing trust boundary near the runtime launch logic.
- **linked implementation is incomplete:** The open PR https://github.com/microsoft/vscode-eslint/pull/1977 only changes server working-directory selection so an explicitly configured `eslint.runtime: "node"` can resolve from the workspace. It neither changes the default runtime strategy nor closes this issue, and the PR author reports they are no longer actively working on it.
- **distinct related request:** The maintainer consolidated https://github.com/microsoft/vscode-eslint/issues/1953 into this issue because project-local Node resolution is part of the desired outcome; that closed report therefore is not an open duplicate canonical.
