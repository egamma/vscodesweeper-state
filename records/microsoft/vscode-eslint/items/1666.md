# Issue #1666 — Use from CLI?

[https://github.com/microsoft/vscode-eslint/issues/1666](https://github.com/microsoft/vscode-eslint/issues/1666)

## Summary

Keep this accepted feature request open: external pre-commit tools still have no supported way to reuse VS Code's running ESLint server. The existing lint task launches a separate command, and no verified older canonical owns this capability.

## Change summary

Allow lint-staged and other CLI callers to reuse the extension's already-loaded ESLint server instead of paying a fresh initialization cost.

## Best solution

Define whether the extension should support external CLI access to its running server, including workspace selection, input-content semantics, and behavior when VS Code is unavailable. If accepted, provide a documented integration that returns authoritative lint results without compromising editor responsiveness.

## Vision fit

- **Fit:** aligned
- **Reason:** Reusing an initialized ESLint process connects the extension's CLI-parity and performance themes while retaining the workspace's own ESLint configuration.

## Plan brief

- **Likely files:** `client/src/client.ts`, `server/src/eslintServer.ts`, `server/src/eslint.ts`, `$shared/customMessages.ts`, `package.json`
- **Validation:** End-to-end acceptance check: open a trusted sample workspace in VS Code, initialize ESLint, then invoke the proposed CLI integration twice for two or three specified files. Verify that both calls reuse the existing server process, return the expected diagnostics and exit status for the agreed input contents, respect per-resource configuration, and leave editor validation responsive. Repeat with unsaved editor changes and with VS Code closed to verify the chosen contracts.
- **Behavior:**

  > Pre-commit tooling currently starts ESLint again even when VS Code already has the project's ESLint loaded; the reporter observes roughly 25 seconds for a two- or three-file change despite caching. The desired capability is an external CLI invocation that reuses the running extension server and returns useful lint results for the requested files. Acceptance must demonstrate process reuse, correct diagnostics and exit status, and continued editor responsiveness. The treatment of unsaved or staged content and an unavailable editor must be settled before implementation.
- **Trace:**

  > client/src/client.ts:createServerOptions starts the extension's language server over TransportKind.ipc. server/src/eslintServer.ts owns the LSP connection and document managers, while server/src/eslint.ts obtains resource-specific settings from the client and validates document text through lintText. client/src/tasks.ts:FolderTaskProvider.getTask instead launches a separate shell command, so eslint.lintTask.* does not cover this request. $shared/customMessages.ts contains no external batch-lint contract. The trace establishes the missing supported integration, not the cause or size of the reporter's startup delay. Preserve workspace-owned ESLint versions and configuration, existing editor-content validation, and lazy activation. https://github.com/microsoft/vscode-eslint/issues/1844 concerns shared disk-cache output rather than server attachment and does not own this request.
- **Open decisions:**
  - Should the supported CLI integration require an already-running VS Code workspace, or also operate when no editor server is available, and what observable failure or fallback should occur in that case?
  - For pre-commit calls, should authoritative input be on-disk files, staged or explicitly supplied contents, or editor buffers, and how should unsaved differences be handled?
  - How should a CLI caller select the intended workspace and configuration scope when multiple VS Code windows contain the same files?

## Evidence

- **Maintainer confirmation:** In the supplied discussion on https://github.com/microsoft/vscode-eslint/issues/1666, the maintainer explicitly states that there is currently no way to do this. The issue remains classified feature-request in Backlog, with help wanted and two upvotes.
- **Existing capabilities do not cover the request:** package.json exposes eslint.lintTask.enable, eslint.lintTask.command, and eslint.lintTask.options, but client/src/tasks.ts:36-56 implements FolderTaskProvider.getTask using vscode.ShellExecution. This launches an external ESLint command rather than reusing the language server. The contributed commands provide editor actions, not a CLI lint-result interface.
- **Current server boundary:** client/src/client.ts:398-422 creates the server with TransportKind.ipc in both run and debug modes. server/src/eslintServer.ts:34-50 creates its LSP connection, and $shared/customMessages.ts defines editor-facing messages rather than an external batch-lint contract. These surfaces do not provide the requested supported attachment mechanism.
- **Configuration and document semantics:** server/src/eslint.ts:938 obtains resource-scoped configuration through connection.workspace.getConfiguration, and server/src/eslint.ts:1317 validates supplied document content with eslintClass.lintText. External hook callers therefore need an explicit contract for configuration scope and which file contents are authoritative; connecting another process alone would not establish CLI parity.
- **Canonical search:** Read-only searches for CLI/server, lint-staged, pre-commit, daemon, command-line/server, and reuse found no verified older open issue owning external access to the running server. https://github.com/microsoft/vscode-eslint/issues/1844 is open but newer, created 2024-05-02, and requests writing .eslintcache on save. That could improve hook performance but would not deliver server reuse, so it is related rather than a duplicate under the prior-review rules.
