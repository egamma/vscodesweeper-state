# Issue #24850 — API for Alternate Python Language Servers

[https://github.com/microsoft/vscode-python/issues/24850](https://github.com/microsoft/vscode-python/issues/24850)

## Summary

A real API gap remains despite the merged Pyrefly integration: current main special-cases Pyrefly rather than providing a general mechanism for alternate language-server extensions. The accepted `needs proposal` and `needs spike` labels also require this to remain open for design work.

## Change summary

Provide an extension API through which alternate Python language-server extensions can coordinate with vscode-python and suppress its built-in language services.

## Best solution

Design a generic API in vscode-python that lets a language-server extension register or declare itself and coordinate ownership of Python language services without modifying user settings. It should replace product-specific detection such as the current Pyrefly special case while preserving existing Pylance and Jedi behavior.

## Vision fit

- **Fit:** aligned
- **Reason:** A generic integration API advances the project's family-of-extensions architecture and allows community language servers to participate without being absorbed into the core extension.
- **Evidence:** The roadmap's durable extensibility theme calls for access points and APIs for sibling extensions, while the community-tooling guardrail favors integrating ecosystem tools rather than rebuilding them in vscode-python.

- **partial Pyrefly integration:** https://github.com/microsoft/vscode-python/pull/24987 merged support that disables built-in language services when `meta.pyrefly` is installed unless `python.pyrefly.disableLanguageServices` is true, but it did not add the requested generic API.
- **current source gap:** On current main, src/client/common/configSettings.ts explicitly checks `PYREFLY_EXTENSION_ID`, and src/client/common/constants.ts defines that ID as `meta.pyrefly`; this is product-specific coordination rather than an API usable by arbitrary language-server extensions.
- **existing configuration is not coverage:** package.json still limits `python.languageServer` to `Default`, `Jedi`, `Pylance`, and `None`. Selecting `None` can suppress vscode-python's server, but requiring another extension to mutate this user setting does not provide the requested registration or coordination API.
- **related discussion is not a canonical duplicate:** https://github.com/microsoft/vscode-python/issues/24756 primarily requests replacing Jedi with Python-LSP-Server; its maintainer discussion mentions a possible API but explicitly says no final decision was made, so it does not own this concrete API proposal.
