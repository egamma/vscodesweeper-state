# Issue #24850 — API for Alternate Python Language Servers

[https://github.com/microsoft/vscode-python/issues/24850](https://github.com/microsoft/vscode-python/issues/24850)

## Summary

The general alternate-language-server API remains missing: the merged Pyrefly integration handles one extension rather than providing a public registration contract. Preserve the accepted needs-proposal/needs-spike work and route it to the API area.

## Change summary

Provide a supported API for alternate Python language servers to integrate without rewriting users' python.languageServer settings.

## Best solution

Define a public integration contract for third-party language-server extensions, keeping their server implementations outside the core Python extension. Settle selection and coexistence behavior before implementation; the existing Pyrefly-specific integration provides useful precedent but does not fulfill the general request.

## Plan brief

- **Likely files:** `src/client/api/types.ts`, `src/client/api.ts`, `src/client/common/configSettings.ts`, `src/client/languageServer/watcher.ts`, `package.json`
- **Validation:** After agreeing the contract, exercise a minimal third-party language-server extension: integration must not rewrite python.languageServer, must follow the agreed coexistence policy, and must preserve explicit Jedi/Pylance selections and normal behavior when no alternate provider participates.
- **Behavior:**

  > Third-party Python language-server extensions need a supported integration surface instead of changing users' language-server settings. Pyrefly already receives special handling, but other providers cannot participate through a general public contract. Acceptance should demonstrate integration by a non-hardcoded provider without settings mutation, with predictable behavior when providers appear or disappear and when users explicitly select Jedi or Pylance.
- **Trace:**

  > PythonExtension in src/client/api/types.ts has no language-server registration surface, while buildApi in src/client/api.ts exposes only a temporary Pylance-specific client interface. PythonSettings in src/client/common/configSettings.ts special-cases meta.pyrefly when resolving the default server; LanguageServerWatcher.createLanguageServer in src/client/languageServer/watcher.ts handles only Jedi, Pylance, and None. The merged integration at https://github.com/microsoft/vscode-python/pull/24987 establishes coexistence precedent, not a generic API. The proposal should preserve existing explicit selections, environment APIs, and server behavior when no third-party provider participates. Uncertainty begins at the public selection and lifecycle contract, not at whether an API already exists.
- **Open decisions:**
  - Should alternate providers become explicit user-selectable language-server choices, or participate automatically only when python.languageServer is Default?
  - What user-visible selection or conflict behavior should apply when multiple alternate providers are available?
  - Should the public contract let the Python extension manage alternate-server start/stop/restart, or leave lifecycle ownership with each provider extension?

## Evidence

- **Accepted proposal work:** The issue carries needs proposal and needs spike. https://github.com/microsoft/vscode-python/wiki/Issue-Management describes needs proposal as accepted feature work requiring discussion; zero upvotes do not establish a community-feedback close for this issue.
- **Existing capability is partial:** package.json:521-538 restricts python.languageServer to Default, Jedi, Pylance, and None. None disables the built-in service but does not register an alternate provider. The contributed restart command is registered by the existing Jedi and Pylance managers, not a general provider registry.
- **Public API gap:** src/client/api/types.ts defines PythonExtension with ready, debug, and environments, but no language-server registration API. src/client/api.ts exposes a Pylance-specific createClient/start/stop interface explicitly marked temporary and deprecated. src/client/languageServer/watcher.ts:230-265 constructs only Jedi, Pylance, or None managers.
- **Merged PR does not implement the full request:** https://github.com/microsoft/vscode-python/pull/24987 merged as 7fea432ebe694ad4ae5931452d1a435bceacf609 on 2025-04-23. Its diff adds a meta.pyrefly-specific check that selects None for the default language-server setting unless python.pyrefly.disableLanguageServices is true. That behavior remains in src/client/common/configSettings.ts:272-298; it introduces no public registration contract for other servers.
- **Older related issue is not a canonical:** https://github.com/microsoft/vscode-python/issues/24756 is open and older, but requests replacing Jedi with Python-Lsp-Server rather than the general integration API requested here. Its maintainer discussion mentions a possible API and explicitly says no final decision has been made: https://github.com/microsoft/vscode-python/issues/24756#issuecomment-2631348233.
- **Closed related request is not decline precedent:** https://github.com/microsoft/vscode-python/issues/23640 requested alternate-server registration, but its author closed it after finding an independent notebook-support approach. It is neither an open duplicate target nor a maintainer decision rejecting this issue's general API scope.
