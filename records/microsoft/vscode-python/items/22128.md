# Issue #22128 — Adopt to using VS Code API to access terminal output

[https://github.com/microsoft/vscode-python/issues/22128](https://github.com/microsoft/vscode-python/issues/22128)

## Summary

Keep open: current main still prepends PATH and synthesizes PS1 in the legacy activation service, so the remaining adoption work is not complete. The existing needs spike label reflects accepted investigation; low upvotes are not grounds to close it.

## Change summary

Adopt terminal command-output APIs to obtain shell state reliably, improve environment activation and prompt detection, and isolate hidden helper terminals from environment collections.

## Best solution

Finish the investigation into shell-state-aware activation without overwriting user shell initialization changes or duplicating environment prompts. Establish which remaining requirements belong in the legacy service versus Python Environments integration before implementing them.

## Plan brief

- **Likely files:** `src/client/terminals/envCollectionActivation/service.ts`, `src/client/terminals/envCollectionActivation/deactivateService.ts`, `src/client/terminals/envCollectionActivation/indicatorPrompt.ts`, `src/client/terminals/envCollectionActivation/shellIntegrationService.ts`, `src/test/interpreters/activation/terminalEnvVarCollectionService.unit.test.ts`
- **Validation:** For the agreed supported activation paths, open bash and zsh terminals with shell-init PATH modifications and automatic conda activation, select a different Python environment, and verify interpreter resolution, preservation of user PATH entries, a single environment indicator, and correct deactivation. Check that hidden helper terminals exclude environment-collection mutations and that helper commands avoid terminal history where supported; exercise the shell-integration-unavailable fallback.
- **Behavior:**

  > The remaining request concerns obtaining actual shell state so environment activation does not duplicate PATH contributions or environment indicators. Activation must preserve user shell-init changes, resolve the selected interpreter, and show indicator notifications only when appropriate. Hidden helper terminals must not inherit environment-collection activation, and helper commands should avoid terminal history where possible. The already-completed deactivate-prompt removal and shell-integration detection are not sufficient to complete the request.
- **Trace:**

  > TerminalEnvVarCollectionService._applyCollectionImpl in src/client/terminals/envCollectionActivation/service.ts still prepends PATH and PS1; getPS1 calculates a prompt and explicitly references this issue as pending work. TerminalDeactivateService.initializeScriptParams in deactivateService.ts obtains environment data through a hidden terminal and a file, without strictEnv or explicit process.env. ShellIntegrationDetectionService uses terminal data sequences, while the general TerminalService.executeCommandInternal already uses terminal.shellIntegration.executeCommand; this is partial API adoption, not completion of the activation requirements. The legacy activation service and indicator prompt are bypassed when useEnvExtension() is true, which is where the unresolved support boundary starts. Preserve user shell-init PATH changes, disabled-activation behavior, and existing run/REPL behavior. https://github.com/microsoft/vscode-python/issues/22439 covers a completed subset, and https://github.com/microsoft/vscode-python/issues/22879 explicitly retains this issue as a follow-up.
- **Open decisions:**
  - Should the remaining shell-state-aware activation guarantees apply to users who retain the legacy activation mode, or should that mode remain unchanged while the capability is delivered through Python Environments integration?
