# Issue #23529 — Re-use terminal after re-starting VS Code

[https://github.com/microsoft/vscode-python/issues/23529](https://github.com/microsoft/vscode-python/issues/23529)

## Summary

Keep open for the accepted terminal-reuse investigation: the legacy execution path still loses its terminal association across restarts, and the maintainer identified missing terminal-state support rather than an available workaround. The newer Python Environments execution path needs assessment before deciding where the remaining work belongs.

## Change summary

Reuse the restored Python execution terminal after restarting VS Code instead of creating another terminal for the same program.

## Best solution

Allow Python file execution to reuse a restored terminal when its ownership and environment state can be established safely. Assess both execution paths and coordinate with VS Code or Python Environments for any required terminal-state support, without adopting unrelated terminals.

## Plan brief

- **Likely files:** `src/client/common/terminal/factory.ts`, `src/client/common/terminal/service.ts`, `src/client/terminals/codeExecution/terminalCodeExecution.ts`, `src/client/terminals/codeExecution/codeExecutionManager.ts`, `src/client/envExt/api.internal.ts`
- **Validation:** In a maintainer-run VS Code session, run a Python file, close and reopen VS Code with terminal persistence enabled, then run the same file twice. Check terminal identity and count, selected-interpreter execution, and activation correctness with Python Environments both enabled and disabled. Also verify that an unrelated terminal or one running a foreground process is not appropriated.
- **Behavior:**

  > Running a Python file after restarting VS Code should reuse its restored execution terminal when that terminal can be safely identified and its environment state established. Repeated runs should not accumulate unnecessary terminals. Execution must still use the selected interpreter and must not commandeer an unrelated or occupied terminal. Closing the execution terminal should continue to permit creation of a replacement.
- **Trace:**

  > For https://github.com/microsoft/vscode-python/issues/23529, the maintainer identified lost terminal state and a missing VS Code API as the obstacle. TerminalServiceFactory in src/client/common/terminal/factory.ts stores services only in memory, and TerminalService.ensureTerminal in src/client/common/terminal/service.ts creates a terminal when its instance has no terminal reference. TerminalProvider.initialize can activate the current terminal but does not associate it with file execution. CodeExecutionManager.registerCommands in src/client/terminals/codeExecution/codeExecutionManager.ts now delegates file execution to executeUsingExtension when Python Environments is enabled, so that implementation must be assessed separately. The uncertainty starts at reliable restored-terminal identity and environment-state recovery, and whether the newer execution owner already supplies those capabilities. Preserve interpreter selection, activation correctness, occupied-terminal safety, and dedicated-per-file behavior; terminal-name matching alone does not establish safe ownership.

## Evidence

- **Maintainer diagnosis and accepted investigation:** The supplied June 12, 2024 maintainer comment on https://github.com/microsoft/vscode-python/issues/23529 explains that terminal state is not saved and identifies a missing VS Code API for safely reusing terminals after reopening. The issue already carries area-terminal and needs spike; this supports a missing-capability classification rather than a support-question close.
- **Legacy terminal association remains session-local:** src/client/common/terminal/factory.ts initializes TerminalServiceFactory.terminalServices as a fresh in-memory Map. In src/client/common/terminal/service.ts, TerminalService.ensureTerminal returns only when its instance already holds a terminal; otherwise the legacy branch creates and activates a new terminal. Neither path associates a service with a terminal restored from an earlier VS Code session.
- **Existing capabilities do not cover restart reuse:** package.json contributes python.execInTerminal and python.execInDedicatedTerminal and terminal activation settings, but no restart-reuse setting. src/client/providers/terminalProvider.ts applies python.terminal.activateEnvInCurrentTerminal to startup activation only; it does not attach that terminal to TerminalServiceFactory. Dedicated-terminal execution changes the per-file service key, not persistence across restarts.
- **Execution ownership has changed:** src/client/terminals/codeExecution/codeExecutionManager.ts routes file execution through executeUsingExtension when useEnvExtension() is true, bypassing the legacy provider. The legacy source trace therefore establishes a remaining gap in that path, not a conclusive diagnosis of the Python Environments implementation or a fix for all current configurations.
