# Issue #25146 — Kernel picker wrongly displays `Python 2.7.undefined` for a valid `Python 3.12` kernel

[https://github.com/microsoft/vscode-python/issues/25146](https://github.com/microsoft/vscode-python/issues/25146)

## Summary

The defect remains actionable: the Python environment API can initially infer 2.7 for an unversioned Unix executable before later resolving its actual Python 3 version, producing the transient incorrect kernel label. Route this to the environments/API owners rather than closing or redirecting it to Jupyter.

## Change summary

A valid Python 3.12 interpreter at an unversioned `python` path is initially displayed as `Python 2.7.undefined` in the notebook kernel picker.

## Best solution

Stop publishing the legacy PEP 394-based 2.7 guess for an unversioned Unix `python` executable and ensure consumers receive either the resolved interpreter version or an explicitly unknown version until resolution completes. The change belongs in the Python environment discovery/API path, with coverage for a global Python 3 executable named `python` and for the initial-to-resolved update sequence.

## Evidence

- **confirmed API behavior:** A maintainer traced the supplied logs and confirmed that the environment version returned by the Python extension API is initially 2.7 and later changes to 3.x: https://github.com/microsoft/vscode-python/issues/25146#issuecomment-2941666908
- **independent reproduction:** A second maintainer reproduced the same `2.7` kernel label in Codespaces using a public repository change: https://github.com/microsoft/vscode-python/issues/25146#issuecomment-3400070325
- **current source:** src/client/pythonEnvironments/base/info/executable.ts still maps an unversioned non-Windows executable named `python` to version 2.7 based on the legacy PEP 394 assumption.
- **affected resolution path:** src/client/pythonEnvironments/base/locators/composite/resolverUtils.ts uses parseVersionFromExecutable() for non-native globally installed environments, so `/usr/local/bin/python` can be published with the incorrect inferred version before richer resolution data arrives.
- **new environment extension result:** The reporter tested the Python Environments extension and confirmed it did not resolve the issue; it instead failed to finish discovery and no longer exposed the global interpreter: https://github.com/microsoft/vscode-python/issues/25146#issuecomment-3674702939
- **related report:** https://github.com/microsoft/vscode-python/issues/25165 was closed as a duplicate of this issue, making this the canonical open report for the transient undefined-version problem.
