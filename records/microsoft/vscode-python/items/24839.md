## Evidence

- **Reporter diagnosis and maintainer acceptance:** In https://github.com/microsoft/vscode-python/issues/24839, the reporter traced printEnvVariablesToFile.py execution to the unusable /usr/local/bin/python3.5 and a 30-second envVars.txt timeout; removing that installation restored language-server startup. The maintainer explicitly agreed that a bad Python environment should not block extension loading.
- **Relevant current source, not a confirmed full reproduction:** src/client/terminals/envCollectionActivation/deactivateService.ts, TerminalDeactivateService.initializeScriptParams(), still selects the first interpreter without an environment type and runs printEnvVariablesToFile.py without an explicit executable-health check, then waits 30 seconds for its output. However, service.ts launches _applyCollection() without awaiting it and catches initializeScriptParams() failures, so this trace alone does not establish that the timeout blocks current language-server startup.
- **Activation has changed:** src/client/activation/activationManager.ts now bounds waiting for autoSelectInterpreter() before activating services. TerminalEnvVarCollectionService.activate() also bypasses the legacy collection path when useEnvExtension() is enabled. These changes warrant retesting, not an inferred completed close.
- **Sibling report points back here:** https://github.com/microsoft/pylance-release/issues/7011 is closed, repeats the original report, and contains a contributor comment pointing to this Python-extension issue as the investigation home. It is not an open duplicate canonical.
- **Canonical search:** Read-only searches for deactivate initialization failures and invalid-interpreter activation found no verified open canonical for the original symptom. https://github.com/microsoft/vscode-python/issues/26034 instead reports interpreter selection reverting on Windows while Pylance starts; it is newer and does not meet the re-review same-symptom duplicate bar.
- **Later comments describe differing causes:** https://github.com/microsoft/vscode-python/issues/24839#issuecomment-3020376715 records closed-channel errors, while https://github.com/microsoft/vscode-python/issues/24839#issuecomment-3021159940 reports recovery with a reduced extension set without identifying the culprit. Other comments report python.languageServer being None. These do not establish that the original bad-interpreter defect was fixed.
