# Issue #22388 — Switch to using unittest.main and custom runner for unittest design

[https://github.com/microsoft/vscode-python/issues/22388](https://github.com/microsoft/vscode-python/issues/22388)

## Summary

Keep this accepted testing proposal open: current main still manually constructs and runs unittest suites rather than delegating to unittest.main. Django support now exists, but it does not fulfill the broader unittest argument-compatibility request.

## Change summary

Delegate unittest execution and argument handling to unittest.main with an extension-compatible custom runner.

## Best solution

Establish command-line-compatible unittest execution while preserving selected-test execution and VS Code result reporting. Coordinate the argument contract with https://github.com/microsoft/vscode-python/issues/21845 without treating that configuration proposal as a duplicate.

## Plan brief

- **Likely files:** `python_files/unittestadapter/execution.py`, `python_files/unittestadapter/pvsc_utils.py`, `src/client/testing/testController/unittest/testExecutionAdapter.ts`, `python_files/tests/unittestadapter/test_execution.py`, `python_files/tests/unittestadapter/test_discovery.py`
- **Validation:** Add CLI-parity cases for supported execution flags and invalid arguments, then run python -m pytest python_files/tests/unittestadapter/test_execution.py python_files/tests/unittestadapter/test_discovery.py. Acceptance must also cover single-test selection, empty selections, load_tests-generated suites, and unchanged VS Code result payloads.
- **Behavior:**

  > Regular unittest execution should honor applicable unittest command-line arguments rather than silently discard them. Running selected tests must execute only those selections and continue reporting outcomes through the VS Code testing integration. Acceptance should compare argument behavior with python -m unittest and preserve discovery roots, subtest reporting, coverage, and the existing Django path.
- **Trace:**

  > The TypeScript buildExecutionCommand forwards python.testing.unittestArgs to execution.py after --udiscovery. The Python parse_unittest_args helper extracts a fixed subset through parse_known_args, while run_tests manually discovers, filters, and runs a suite using UnittestTestResult. Existing test_execution.py cases cover empty selections, individual tests, and subtests. Django already uses a separate MANAGE_PY_PATH branch and custom runner, so its implementation is not proof that regular unittest delegation landed. The unresolved public-contract boundary is how one shared argument setting interacts with discovery and selected execution; related configuration design is at https://github.com/microsoft/vscode-python/issues/21845.
- **Open decisions:**
  - When configured unittest selectors or name-filter arguments conflict with the Test Explorer selection, should they further restrict that selection or should the explicit Explorer selection take precedence?
  - Should CLI-compatible argument handling ship through the existing shared python.testing.unittestArgs setting, or wait for separate discovery and execution configurations?

## Evidence

- **Remaining execution gap:** python_files/unittestadapter/execution.py::run_tests still constructs unittest.TextTestRunner(resultclass=UnittestTestResult), discovers through TestLoader.discover, filters selected IDs, and calls runner.run(tailor); it does not use unittest.main.
- **Existing setting is partial coverage:** package.json:721-740 declares python.testing.unittestArgs and python.testing.unittestEnabled. src/client/testing/testController/unittest/testExecutionAdapter.ts:309-315 forwards the arguments to execution.py, but python_files/unittestadapter/pvsc_utils.py:287-325 recognizes only selected flags and discards unknown arguments through parse_known_args; the setting does not deliver full unittest CLI semantics.
- **Django does not complete this proposal:** https://github.com/microsoft/vscode-python/issues/22206 is closed and its August 2024 comment announces Django support. Current execution.py branches on MANAGE_PY_PATH to django_execution_runner, whose django_handler.py implementation invokes manage.py with a custom Django runner; regular unittest execution remains separate.
