# Issue #25554 — Conda/Miniforge environments not detected as Jupyter kernels in VSCode (2025.x extension versions)

[https://github.com/microsoft/vscode-python/issues/25554](https://github.com/microsoft/vscode-python/issues/25554)

## Summary

Keep open and route to environment integration: multiple users confirmed missing Conda kernels, with disabling Python Environments restoring discovery. A related adapter fix exists, but this report's trigger has not been connected to that fix.

## Change summary

Valid Conda interpreters disappear from Jupyter's kernel picker when newer Python environment integration is enabled.

## Best solution

Ensure discovered Conda interpreters reliably reach the Python API and Jupyter kernel picker with Python Environments enabled. Retest the reported multi-environment setup against the existing adapter fix before deciding whether additional core integration work or a maintainer transfer to the sibling tracker is needed.

## Plan brief

- **Likely files:** `src/client/pythonEnvironments/index.ts`, `src/client/envExt/api.internal.ts`, `src/client/envExt/envExtApi.ts`, `src/client/environmentApi.ts`, `src/client/jupyter/jupyterIntegration.ts`
- **Validation:** On macOS ARM64 with Miniforge, create two Python environments with ipykernel and open a notebook with current Python, Jupyter, and Python Environments enabled. Verify both interpreters appear and can start kernels without manual paths or disabling extensions; repeat with an additional Conda environment without Python and compare PET discovery, Python API results, and picker entries.
- **Behavior:**

  > The reported setup discovers Conda environments through PET but omits them from Jupyter's Python-environment kernel picker. Valid environments with Python and ipykernel should remain selectable with Python Environments enabled, including when multiple Conda environments exist. Acceptance requires selecting and starting each kernel without downgrading extensions or manually entering interpreter paths. A Conda environment without Python must not suppress valid Python environments.
- **Trace:**

  > src/client/pythonEnvironments/index.ts initialize() chooses the EnvExt, native, or JS discovery implementation; src/client/envExt/api.internal.ts useEnvExtension() gates the EnvExt path. src/client/api.ts buildApi() exposes the discovery-backed environment API implemented in src/client/environmentApi.ts, while src/client/jupyter/jupyterIntegration.ts registers Python services with Jupyter. PET logs in https://github.com/microsoft/vscode-python/issues/25554 locate the missing environments, and several reporters restored picker entries by disabling Python Environments. The original tilde-expansion theory remains unproven. https://github.com/microsoft/vscode-python/commit/e0f1d3c80da21e0246b007990f6513fed9017080 addresses a confirmed no-python batch-conversion failure discussed at https://github.com/microsoft/vscode-python-environments/issues/1671, but this report has not established that trigger. Start by reproducing with the current adapter and identifying where discovered entries stop reaching consumers; preserve valid non-Python Conda environments and existing discovery backends.

## Evidence

- **Python-side isolation:** In https://github.com/microsoft/vscode-python/issues/25554, the reporter confirmed that current Jupyter works with Python 2024.16.0, while upgrading Python alone removes Conda kernels. The apparent resolution after reinstalling Miniforge was explicitly withdrawn when the failure recurred.
- **Discovery succeeds below the picker:** The November 6 discussion identifies PET output locating the requested Miniforge environments, despite their absence from the kernel picker. This supports investigating the discovery-to-consumer handoff rather than assuming Conda installation failure.
- **Independent confirmations and workaround:** July–September 2026 comments confirm continuing failures. A Windows Miniconda reporter and two subsequent commenters report that fully disabling Python Environments restores kernels; changing python.useEnvironmentsExtension alone had not helped.
- **Current integration boundary:** src/client/pythonEnvironments/index.ts initialize() selects createEnvExtApi() when useEnvExtension() is true, otherwise selecting native or JS discovery. src/client/api.ts buildApi() exposes buildEnvironmentApi() to consumers; src/client/environmentApi.ts returns the discovery-backed known collection and resolves interpreters through discoveryApi.resolveEnv().
- **Related fix is not proven coverage:** https://github.com/microsoft/vscode-python/commit/e0f1d3c80da21e0246b007990f6513fed9017080 isolates EnvExt conversion failures and skips no-python Conda placeholders. The related discussion at https://github.com/microsoft/vscode-python-environments/issues/1671 confirms that specific trigger, but this report does not establish that a no-Python environment caused its failure; the shared symptom and disabling workaround alone do not prove completion.
- **Canonical verification:** https://github.com/microsoft/vscode-python/issues/26057 is open but younger, has no milestone or upvotes, and reports interpreter-selection/autoselection failure rather than this notebook symptom. https://github.com/microsoft/vscode-python-environments/issues/1671 is also younger with no milestone or body upvotes. Neither clears the stronger duplicate bar for this re-reviewed issue.
- **Other sibling leads:** https://github.com/microsoft/vscode-python-environments/issues/1013 closed for missing information, not a verified fix or scope decision. https://github.com/microsoft/vscode-python-environments/issues/1932 concerns selecting an already-visible kernel followed by PET timeout recovery, not missing Conda entries, so it is not a canonical for this report.
