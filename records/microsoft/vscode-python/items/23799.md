# Issue #23799 — autoloading `.env` file format does not ignore inline comments.

[https://github.com/microsoft/vscode-python/issues/23799](https://github.com/microsoft/vscode-python/issues/23799)

## Summary

Keep open: the current parser still preserves inline comments, and no verified fix or qualifying duplicate resolves this terminal-loading report. Although currently labeled a bug, inline-comment support changes an explicitly tested behavior and needs a compatibility decision rather than an as-designed close.

## Change summary

Support inline comments in loaded .env files so comment text does not become part of an environment variable's value.

## Best solution

Agree on a quote-aware inline-comment contract for Python environment loading, preserving literal hashes inside quoted values and existing substitution behavior. Coordinate with the Python Environments implementation discussed in https://github.com/microsoft/vscode-python/issues/18307, while retaining this concrete terminal report until its loading path adopts the agreed behavior.

## Plan brief

- **Likely files:** `src/client/common/variables/environment.ts`, `src/client/common/variables/environmentVariablesProvider.ts`, `src/test/common/variables/envVarsService.unit.test.ts`
- **Validation:** Once the parsing contract is agreed, run the parseEnvFile() unit suite with cases for SOME_VAR="900" #inline comments, unquoted trailing comments, quoted literal hashes, full-line comments, and existing variable substitution. Confirm in an enabled terminal env-file loading flow that os.environ['SOME_VAR'] is '900', without retained quotation marks or comment text.
- **Behavior:**

  > Loading a .env assignment such as SOME_VAR="900" #inline comments should make the application receive 900 rather than quotation marks and comment text. Literal hashes inside quoted values must remain data, and existing variable substitution must continue to work. Acceptance should cover both direct parser results and the environment observed by Python in a terminal that loads the file. The compatibility treatment of existing files that rely on retained unquoted hashes needs agreement before changing the default grammar.
- **Trace:**

  > EnvironmentVariablesProvider.getCustomEnvironmentVariables delegates to EnvironmentVariablesService.parseFile, which calls parseEnvFile and its private parseEnvLine in src/client/common/variables/environment.ts. The assignment regex captures everything after the equals sign; outer quotes are removed only when they enclose the entire captured value, so a trailing comment prevents quote removal. The 'Comments are ignored' test in src/test/common/variables/envVarsService.unit.test.ts explicitly preserves an inline hash suffix, confirming an established contract rather than an accidental omission. Preserve ordering-dependent substitution and environment merge behavior; broader multiline and debugger grammar changes are outside this report. https://github.com/microsoft/vscode-python/issues/18307 records broader standardization and a proposed Python Environments implementation, but upstream availability alone would not prove adoption here. The uncertainty is the user-visible compatibility policy for changing existing env-file interpretation, not the parser's current output.
- **Open decisions:**
  - Should inline-comment interpretation become the default for existing python.envFile consumers, changing values that currently include unquoted hash suffixes, or should those consumers retain the legacy grammar until an explicit migration?
