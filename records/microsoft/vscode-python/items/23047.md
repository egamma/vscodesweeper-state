# Issue #23047 — Custom Test Discovery Option

[https://github.com/microsoft/vscode-python/issues/23047](https://github.com/microsoft/vscode-python/issues/23047)

## Summary

Keep open: discovery still uses pytest --collect-only with shared pytest arguments, and existing settings do not provide the requested discovery-specific customization. Related configuration and per-file discovery proposals cover parts of the request, but neither establishes a duplicate covering its full scope.

## Change summary

Allow customized or restricted pytest discovery for very large suites while retaining the normal Test Explorer execution experience.

## Best solution

Design discovery-specific pytest configuration that supports user collection plugins without changing ordinary execution or debugging. Coordinate with the separate-config proposal and per-file discovery work, retaining this report's large-suite and remote-CI use cases as acceptance requirements.

## Vision fit

- **Fit:** aligned
- **Reason:** Improving large-suite discovery through pytest integration advances testing reliability and performance without replacing community tooling.
- **Evidence:** The public Roadmap states "Performance and stability trumps functionality" and "We use tooling provided and loved by the Python community before creating our own"; testing integration is a durable theme.

## Plan brief

- **Likely files:** `package.json`, `src/client/testing/testController/controller.ts`, `src/client/testing/testController/pytest/pytestDiscoveryAdapter.ts`, `src/client/testing/testController/pytest/pytestExecutionAdapter.ts`, `python_files/vscode_pytest/__init__.py`
- **Validation:** Use a fixture with tests in two files and a pytest collection plugin driven by a supplied test-list file. Confirm discovery shows only the listed tests, running and debugging a discovered test use the intended execution configuration, and changing the list then refreshing removes obsolete entries. Repeat with customization disabled to confirm normal pytest collection remains unchanged; measure collection time and editor responsiveness on a representative large suite.
- **Behavior:**

  > Large-suite users need to customize or restrict discovery while keeping tests available through the normal Test Explorer run and debug flows. A second reported use case supplies a changing list of failing tests from remote CI. Acceptance should demonstrate that the selected discovery policy controls the displayed tests without unintentionally applying discovery-only options during execution or debugging. Ordinary projects must retain their existing pytest behavior.
- **Trace:**

  > PytestTestDiscoveryAdapter.discoverTests in src/client/testing/testController/pytest/pytestDiscoveryAdapter.ts always invokes pytest with vscode_pytest and --collect-only, then appends the shared python.testing.pytestArgs. PytestTestExecutionAdapter in src/client/testing/testController/pytest/pytestExecutionAdapter.ts also consumes those arguments. PythonTestController.watchForTestContentChangeOnSave in controller.ts filters refresh triggers, not collection scope; python_files/vscode_pytest/__init__.py builds discovery payloads from pytest session.items. The missing independent configuration surface is confirmed from source, but this review did not execute the reported large-suite slowdown. Preserve pytest plugin compatibility and ordinary execution/debugging semantics; a built-in syntax-scanning replacement conflicts with the maintainer direction in https://github.com/microsoft/vscode-python/issues/21922#issuecomment-1739784125. Related design work is https://github.com/microsoft/vscode-python/issues/21845 and https://github.com/microsoft/vscode-python/issues/4586; uncertainty remains over how much dynamic collection-scope control this feature should provide.
- **Open decisions:**
  - Should this feature provide automatic open-file-only collection as well as discovery-specific pytest configuration, or should dynamic test selection remain entirely the responsibility of user-supplied pytest plugins?
