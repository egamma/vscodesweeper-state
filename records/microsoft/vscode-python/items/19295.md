# Issue #19295 — Add telemetry for which language server is being used on Python notebooks

[https://github.com/microsoft/vscode-python/issues/19295](https://github.com/microsoft/vscode-python/issues/19295)

## Summary

Keep this accepted telemetry request open: current Python language-server events do not establish join-free attribution of notebook usage and errors to the effective server. It is team-authored and reopened, with no verified duplicate or qualifying post-reopen fix identified.

## Change summary

Make the effective Python language server directly identifiable when analyzing notebook usage and error telemetry, without unreliable or expensive session joins.

## Best solution

Establish reliable effective-language-server attribution from the Python extension's activation lifecycle and make it available to the relevant notebook telemetry. Coordinate with Jupyter's telemetry boundary rather than treating the configured python.languageServer value or a separate startup event as sufficient coverage.

Verify that each relevant event identifies the effective server or an explicit unavailable state without a session join, and that telemetry-disabled behavior remains unchanged.
- **Behavior:**

  > Notebook usage and error telemetry must identify the effective Python language server without expensive or unreliable session joins. Configured Pylance must not be reported as successfully active when startup fails or another server is actually serving the workspace. Attribution must remain accurate after server changes and preserve existing telemetry opt-out behavior.
- **Trace:**

  > The discussion at https://github.com/microsoft/vscode-python/issues/19295 establishes Python as the intended origin of server attribution. LanguageServerWatcher.startAndGetLanguageServer in src/client/languageServer/watcher.ts resolves and starts server managers; the Node and Jedi proxies emit separate lifecycle events containing lsVersion. src/client/telemetry/index.ts merges shared properties into this extension's outgoing events, but its shared-property schema has no effective-server field. The trace does not establish a mechanism carrying Python's effective-server state into Jupyter-owned notebook events, so adding another Python-only event cannot yet be assumed to remove joins. Preserve language-server selection, startup behavior and telemetry consent; this is an attribution change, not a request to alter fallback policy.
