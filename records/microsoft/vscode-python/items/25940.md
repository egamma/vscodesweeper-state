## Summary

Keep this team-authored, reopened issue open: the default configure_python_environment path still reaches extension-owned input UI. The optional pythonPath shortcut does not satisfy the requested no-interaction guarantee, and the related strategy and monitoring issues do not replace this concrete report.

Coordinate backend capabilities with Python Environments while keeping this issue as the concrete implementation and acceptance tracker.

## Evidence

- **Current failing path:** src/client/chat/configurePythonEnvTool.ts: ConfigurePythonEnvTool.invokeImpl only bypasses selection UI when pythonPath is supplied or a qualifying selected environment exists. With no such environment and shouldCreateNewVirtualEnv returning false, it invokes selectEnvironment. src/client/chat/selectEnvTool.ts then executes Commands.Set_Interpreter or showCreateAndSelectEnvironmentQuickPick, which calls showQuickPick with ignoreFocusOut: true. This directly preserves the reported extension-owned interaction after tool approval.
- **Partial existing capability:** package.json contributes resourcePath and optional pythonPath for configure_python_environment, but no interactionPolicy. The model description promises prompt avoidance only when pythonPath is supplied; neither the schema nor ConfigurePythonEnvTool enforces a non-interactive default or the requested structured failure categories.
- **Creation and cancellation boundaries:** src/client/chat/createVirtualEnvTool.ts routes creation to python-envs.createAny with quickCreate: true when Python Environments is enabled, or createVirtualEnvironment when disabled. Cancellation races and bounded resolution polling already exist, but selection command calls in src/client/chat/selectEnvTool.ts do not pass the token to their underlying commands, and ConfigurePythonEnvTool catches creation cancellation by invoking selection. Existing cancellation support therefore does not establish the complete no-UI and backend-cancellation contract.
