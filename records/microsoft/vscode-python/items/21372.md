# Issue #21372 — import a library from another vscode extension

[https://github.com/microsoft/vscode-python/issues/21372](https://github.com/microsoft/vscode-python/issues/21372)

## Summary

Keep open for the API proposal the team requested: existing extra-path settings offer a workaround, but the exported Python API still has no library-path contribution surface. The needs proposal label records accepted work, so age and zero upvotes are not grounds for closing.

## Change summary

Allow another extension to contribute SDK-derived Python library paths through a supported API rather than requiring users to configure nested library directories manually.

## Best solution

Agree on a supported library-path contribution contract, including its scope and lifetime, with the Python API and language-server owners. Establish whether it covers analysis only or also Python execution before implementation.

## Plan brief

- **Likely files:** `src/client/api/types.ts`, `src/client/api.ts`, `src/client/proposedApiTypes.ts`, `src/client/proposedApi.ts`, `src/client/activation/jedi/analysisOptions.ts`, `src/client/pylanceApi.ts`
- **Validation:** Use a minimal companion extension that derives a Ren'Py library directory from a configured SDK root. Verify import resolution with the agreed supported language servers, preservation of existing user extra paths, workspace isolation and the agreed removal/reload behavior. If execution is included in the contract, also verify imports in terminal runs and the explicitly supported background processes.
- **Behavior:**

  > An SDK integration extension should be able to contribute a derived Python library directory through a supported API without asking users to configure the SDK root and nested library directory separately. Existing user-configured paths and interpreter selection must remain intact. Acceptance should demonstrate import resolution, workspace isolation and contribution lifetime according to the agreed contract. Whether the contribution also affects runtime imports remains a product decision.
- **Trace:**

  > package.json declares python.autoComplete.extraPaths, and JediLanguageServerAnalysisOptions.getInitializationOptions in src/client/activation/jedi/analysisOptions.ts forwards configured paths to Jedi. PythonExtension in src/client/api/types.ts and buildApi in src/client/api.ts expose no library-path contribution method; the proposed top-level API interface is empty. The Pylance-facing interface in src/client/pylanceApi.ts supplies client lifecycle and telemetry, not search-path contributions. The originating discussion at https://github.com/microsoft/vscode-python/discussions/21284 separates analysis settings from terminal environment changes and explicitly identifies the missing generic API. Maintainer comments at https://github.com/microsoft/vscode-python/issues/21372 request a proposal and identify a second SDK integration use case. Preserve interpreter-selection behavior and existing user settings; do not assume that changing a Jedi initialization option also changes Pylance or execution paths. The uncertainty starts at the public contract, before choosing implementation files or treating the reporter's settings-append sketch as an approved design.
- **Open decisions:**
  - Should contributed library paths affect language analysis only, or also runtime imports in terminal runs and specified background Python processes?
  - Should contributions persist in user/workspace settings, or remain extension-owned registrations that disappear when withdrawn or the contributing extension is disabled?
  - Should each contribution apply to a workspace folder, a selected environment, or the entire extension session?
