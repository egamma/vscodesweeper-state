[https://github.com/microsoft/vscode-python/issues/24135](https://github.com/microsoft/vscode-python/issues/24135)

Windows Python shell integration remains intentionally disabled in the inspected main checkout, even though a Windows sequence branch already omits 633 E. Keep this accepted investigation open: maintainers consolidated the decoration reports here, and the identified CPython pre-execution-hook dependency remains open.

## Plan brief

- **Likely files:** `python_files/pythonrc.py`, `src/client/terminals/pythonStartup.ts`, `python_files/tests/test_shell_integration.py`, `src/test/terminals/shellIntegration/pythonStartup.test.ts`
- **Validation:** On Windows PowerShell in a fresh integrated terminal, enable python.terminal.shellIntegration.enabled and open the terminal Python REPL. Run successful and raising expressions directly and through Shift+Enter, including multiline input; verify stable command boundaries and correctly colored success/failure decorations without visible escape sequences. Check the emitted stream omits 633 E and confirm disabling the setting and existing non-Windows behavior remain unchanged.
- **Behavior:**

  > Windows users should receive Python terminal REPL shell integration even when the 633 E command-line sequence cannot be used. Successful and failing commands should produce correctly positioned and colored decorations for direct input and Shift+Enter execution, including multiline commands. Escape sequences must not appear as literal text, and disabling the setting must retain the ordinary REPL experience.
- **Trace:**

  > package.json exposes python.terminal.shellIntegration.enabled, and registerPythonStartup in src/client/terminals/pythonStartup.ts injects python_files/pythonrc.py through PYTHONSTARTUP while forcing PYTHON_BASIC_REPL=1. PS1.__str__ already has a Windows sequence branch without 633 E, but the final platform guard excludes Windows from installing PS1. Maintainers consolidated https://github.com/microsoft/vscode-python/issues/22675, https://github.com/microsoft/vscode-python/issues/22535 and https://github.com/microsoft/vscode-python/issues/25343 here because marker positioning and decoration status remain part of the acceptance boundary. They identify https://github.com/python/cpython/issues/122622 as crucial; that request remains open and now discusses _pyrepl, which the current startup configuration disables. The unresolved technical question is whether a reliable supported Windows execution boundary exists without that hook; merely enabling the dormant prompt branch does not establish correct command detection. Preserve non-Windows integration and avoid expanding this work into IPython support or the editor-native REPL.

## Evidence

- **Existing capability does not cover Windows:** package.json:643-650 declares python.terminal.shellIntegration.enabled with default true. src/client/terminals/pythonStartup.ts:24-26 injects PYTHONSTARTUP and PYTHON_BASIC_REPL=1, but python_files/pythonrc.py:82-83 assigns sys.ps1 = PS1() only outside Windows and WSL. Thus the enabled setting does not deliver the requested Windows integration.
- **Omitting 633 E is already present but inactive:** python_files/pythonrc.py:65-72 constructs a Windows prompt containing 633 D, A, B and C without E. The platform guard prevents that prompt from being installed; the presence of this branch is not evidence of an implemented feature.
- **This issue owns the consolidated reports:** https://github.com/microsoft/vscode-python/issues/22675#issuecomment-2529515360 closes randomized Windows decorations against this issue. https://github.com/microsoft/vscode-python/issues/22535#issuecomment-2532893035 explicitly requires checking decoration colors when Windows integration is eventually supported. https://github.com/microsoft/vscode-python/issues/25343#issuecomment-3133714499 also consolidates missing Windows integration here.

Current startup code instead forces PYTHON_BASIC_REPL=1, so an upstream PyREPL capability would require explicit adoption here.
