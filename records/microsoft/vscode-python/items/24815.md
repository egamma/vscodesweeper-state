# Issue #24815 — Refresh integrated terminal with .env variables after changing .env file

[https://github.com/microsoft/vscode-python/issues/24815](https://github.com/microsoft/vscode-python/issues/24815)

## Summary

Keep open for the existing terminal-area spike: the reporter clarified that fresh terminals and the relaunch command receive updated values, but wants refresh without restarting the terminal. Existing activation settings do not cover that request, and the hover-link and lost-activation reports need separate investigation.

## Change summary

Provide a way to refresh .env-derived variables in an existing terminal without relaunching it, with clear limits for already-running applications.

## Best solution

Define a safe refresh contract for existing shells and subsequently launched programs, distinguishing it from application-level configuration reload in an already-running server. Coordinate the terminal integration with VS Code and Python Environments, and separately diagnose the reported relaunch failures.

## Plan brief

- **Likely files:** `src/client/common/variables/environmentVariablesProvider.ts`, `src/client/interpreter/activation/service.ts`, `src/client/terminals/envCollectionActivation/service.ts`, `src/client/providers/terminalProvider.ts`
- **Validation:** In a Windows PowerShell 7 workspace with a selected venv, establish an .env variable, open a terminal, then change its value and add another variable. Exercise the agreed refresh behavior and inspect both with Get-ChildItem Env: and a newly launched Python process; verify terminal identity, pending input and venv selection are preserved. Repeat with Python Environments enabled and disabled, and separately compare the hover relaunch link with Terminal: Relaunch Active Terminal.
- **Behavior:**

  > The reporter wants saved .env changes to become usable in an existing integrated terminal without replacing that terminal. Fresh terminals and command-palette relaunch already worked in the reporter's clarified reproduction, so those behaviors must remain intact. Acceptance must distinguish the shell environment and future child processes from an already-running server, whose configuration may require application-level reload. Refresh must not execute pending input, terminate running work or lose the selected virtual environment.
- **Trace:**

  > EnvironmentVariablesProvider in src/client/common/variables/environmentVariablesProvider.ts invalidates its cache and emits a change event on .env edits. EnvironmentActivationService in src/client/interpreter/activation/service.ts clears its activation cache, and TerminalEnvVarCollectionService in src/client/terminals/envCollectionActivation/service.ts republishes scoped environment mutators. That service skips legacy activation when useEnvExtension() is true, so the trace does not establish the current Python Environments implementation or VS Code's handling of collection changes in existing shells. TerminalProvider in src/client/providers/terminalProvider.ts handles terminal creation and initialization-time activation, not a live refresh command. The reporter's clarification at https://github.com/microsoft/vscode-python/issues/24815#issuecomment-2678286920 separates restart-free refresh from a broken hover link; the later activation-loss report is another behavior to diagnose independently. Do not assume collection updates can rewrite an arbitrary running application's environment, and do not inject commands into occupied terminals. Related messaging work at https://github.com/microsoft/vscode-python/issues/23818 does not own this request.
- **Open decisions:**
  - Should .env changes refresh an existing idle shell automatically or only through an explicit user action, and what should users observe while that shell has a foreground application running?
  - Is the supported contract limited to the shell and subsequently launched programs, or does it include an application-cooperative reload workflow for already-running Python servers?
