# Issue #22031 — Fix assumption that macOS filesystem is case sensitive

[https://github.com/microsoft/vscode-python/issues/22031](https://github.com/microsoft/vscode-python/issues/22031)

## Summary

Keep open: current main still treats macOS paths as case-sensitive in both cited normalization helpers and in environment ID generation. The earlier fix addresses duplicate global search directories, not this accepted cross-cutting correction.

## Change summary

Correct Windows-only case normalization assumptions for macOS paths, including environment identity and persisted discovery data.

## Best solution

Make path comparisons and environment identity consistent for the default case-insensitive macOS filesystem, with coherent handling of persisted IDs. Audit shared-helper consumers so filesystem normalization changes do not accidentally make macOS environment-variable names case-insensitive.

- **Behavior:**

  > On the default case-insensitive macOS filesystem, differently cased spellings of the same interpreter or environment path should identify the same environment. Interpreter selection and activation should remain consistent across those spellings and across a reload with existing discovery data. Windows behavior and Linux case-sensitive path behavior must remain unchanged. macOS environment-variable names must retain their existing case-sensitive behavior.
- **Trace:**

  > Both src/client/common/platform/fs-paths.ts and src/client/pythonEnvironments/common/externalDependencies.ts restrict case folding to Windows; tracing getEnvID in src/client/pythonEnvironments/base/info/env.ts conclusively shows different IDs for macOS case variants. PythonEnvInfoCache compares IDs directly, and src/client/pythonEnvironments/index.ts persists environments under the already-existing PYTHON_ENV_INFO_CACHEv2 key. The activation cache in src/client/interpreter/activation/service.ts independently retains Windows-only normalization. The shared normCase helper is also used for environment-variable keys in src/client/common/variables/environment.ts, so extending its behavior indiscriminately would cross a non-filesystem contract boundary. https://github.com/microsoft/vscode-python/pull/22040 fixed only global search-directory deduplication for https://github.com/microsoft/vscode-python/issues/22006; it did not complete this broader correction. The remaining uncertainty is the complete set of identity-dependent consumers and persisted-state transitions, not whether the cited helpers still exhibit the defect.

## Evidence

- **Current source defect:** src/client/pythonEnvironments/common/externalDependencies.ts:98-103 uppercases paths only for OSType.Windows. On macOS, arePathsSame('/Users/example/Envs/project/bin/python', '/Users/example/envs/project/bin/python') therefore returns false even when both identify the same file on the default filesystem.
- **Environment identity:** src/client/pythonEnvironments/base/info/env.ts:getEnvID calls that normCasePath helper. Consequently, case variants produce different environment IDs on macOS; PythonEnvInfoCache in src/client/pythonEnvironments/base/locators/composite/envsCollectionCache.ts compares cached IDs directly.
- **Other affected surfaces:** src/client/common/platform/fs-paths.ts:FileSystemPaths.withDefaults and normCase retain Windows-only case folding. src/client/interpreter/activation/service.ts:getActivatedEnvironmentVariables also lowercases interpreter paths only on Windows when constructing activation-cache keys.

Current getGlobalVirtualEnvDirs deduplicates search directories with uniqBy(venvDirs, toLower) on Windows and macOS, but the shared normalization helpers remain unchanged. https://github.com/microsoft/vscode-python/issues/22006 is closed; its discussion explicitly identifies this issue as the separate general correction.
