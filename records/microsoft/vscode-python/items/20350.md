# Issue #20350 — Add filter based on pytest marks to Test Explorer

[https://github.com/microsoft/vscode-python/issues/20350](https://github.com/microsoft/vscode-python/issues/20350)

## Summary

Keep open: pytest marks still are not exposed as Test Explorer tags on current main. The request has 81 upvotes and accepted-work labels; the proposed implementation was closed without merging after its contributor withdrew.

## Change summary

Allow users to filter pytest tests by their marks directly in Test Explorer.

## Best solution

Deliver pytest-mark filtering through the existing Test Explorer filtering surface, preserving project-based discovery and run/debug behavior. Use the withdrawn proposal as a starting point for maintainer design review, while coordinating filtered execution with the separately tracked exclusion bug.

## Plan brief

- **Likely files:** `python_files/vscode_pytest/__init__.py`, `src/client/testing/testController/common/types.ts`, `src/client/testing/testController/common/utils.ts`, `python_files/tests/pytestadapter/test_discovery.py`, `src/test/testing/testController/utils.unit.test.ts`
- **Validation:** Extend pytest discovery tests and the populateTestTree unit suite to verify the agreed marker metadata and filterable tags. In a workspace containing marked and unmarked tests, check that Test Explorer can select the requested mark without changing pytestArgs, including under project-based discovery; verify filtered execution separately against https://github.com/microsoft/vscode-python/issues/25742.
- **Behavior:**

  > Users should be able to select pytest tests by their marks using Test Explorer's filtering surface without editing test-runner arguments or recollecting a permanently restricted suite. Marked, unmarked and parametrized tests should remain discoverable, and clearing the filter should restore the full view. Acceptance checks should cover multiple marks and the agreed treatment of marks inherited from classes or modules, while preserving existing run/debug capabilities.
- **Trace:**

  > The Python discovery producer create_test_node in python_files/vscode_pytest/__init__.py currently emits no mark metadata. DiscoveredTestItem in src/client/testing/testController/common/types.ts carries only identity, location and runID, and populateTestTree in common/utils.ts assigns only the existing run/debug tags. PythonTestController creates the python-tests controller in controller.ts. The withdrawn https://github.com/microsoft/vscode-python/pull/25740 demonstrated marker-based filtering but never merged; it is a design reference, not current functionality. Preserve project-scoped identifiers, existing run/debug tags, unittest behavior and unfiltered discovery. The remaining product question is marker semantics; filtered execution is separately tracked at https://github.com/microsoft/vscode-python/issues/25742, and configurable suites at https://github.com/microsoft/vscode-python/issues/12075 are outside this request's scope.
- **Open decisions:**
  - Should filterable marks include all effective pytest marks inherited from modules and classes, and should built-in marks such as skip, xfail and parametrize appear alongside user-defined marks?
