# Issue #21998 — Try avoid putting run commands into shell history

[https://github.com/microsoft/vscode-python/issues/21998](https://github.com/microsoft/vscode-python/issues/21998)

## Summary

Keep this accepted request open: current terminal execution and legacy activation paths still send commands without extension-side history suppression. The request has 8 upvotes and needs proposal; neither the existing settings nor the verified related issues cover its full scope.

## Change summary

Avoid recording extension-generated Python run and environment-activation commands in the user's shell history.

## Best solution

Develop a shell-aware proposal for avoiding history pollution in Python-owned run and activation flows while preserving execution and user-entered history. Coordinate debugger-generated commands with VS Code's DAP terminal handling rather than treating that separate responsibility as coverage of this request.

## Plan brief

- **Likely files:** `src/client/common/terminal/helper.ts`, `src/client/common/terminal/service.ts`, `src/client/common/terminal/activator/base.ts`, `src/client/common/terminal/environmentActivationProviders/bash.ts`, `src/client/terminals/codeExecution/terminalCodeExecution.ts`, `src/test/common/terminals/helper.unit.test.ts`, `src/test/common/terminals/service.unit.test.ts`, `src/test/common/terminals/activation.unit.test.ts`
- **Validation:** The proposal should end with shell-specific acceptance checks: run a Python file and trigger command-based venv activation in configured bash, zsh, and fish terminals; verify execution and activation still succeed, generated commands are absent from persistent history under the supported configurations, and manually entered commands remain recorded. Cover both shell-integration execution and the sendText fallback with terminal-service and activation unit tests.
- **Behavior:**

  > Running a Python file or activating its environment should avoid filling the user's persistent shell history with extension-generated commands where suppression is supported. Execution, environment selection, and activation must continue to work, and user-entered commands must retain their normal history behavior. Acceptance must distinguish shell-integration execution from fallback command sending and must state any shell-configuration prerequisites.
- **Trace:**

  > TerminalCodeExecutionProvider.executeFile in src/client/terminals/codeExecution/terminalCodeExecution.ts delegates to TerminalService.sendCommand. TerminalHelper.buildCommandForTerminal in src/client/common/terminal/helper.ts trims the built command; TerminalService.executeCommandInternal in src/client/common/terminal/service.ts forwards it to shellIntegration.executeCommand or sendText. Separately, the Bash activation provider constructs source commands and BaseTerminalActivator sends them directly. These source paths lack extension-side suppression, but actual persistence depends on shell behavior and was not executed in this read-only review. Preserve Python REPL input, command quoting, activation semantics, and user-entered history; a leading space must not be assumed sufficient for every shell. The thread at https://github.com/microsoft/vscode-python/issues/21998 separates debugger DAP handling from Python-owned activation, and https://github.com/microsoft/vscode/issues/192943 covers profile inheritance rather than this capability.
- **Open decisions:**
  - Should the supported contract be best-effort suppression using the user's existing shell-history configuration, or suppression that works without requiring users to configure history-ignore behavior?
