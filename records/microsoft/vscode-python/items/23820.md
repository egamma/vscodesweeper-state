# Issue #23820 — Python extension creates too many zsh processes after update to v2024.10.0

[https://github.com/microsoft/vscode-python/issues/23820](https://github.com/microsoft/vscode-python/issues/23820)

## Summary

Keep open: multiple reporters confirmed runaway shell creation with virtualenv auto-loading plugins, and the implicated deactivation path remains in current main. The Python Environments integration now bypasses that path when enabled, but this does not establish that the legacy activation flow is fixed.

## Change summary

Opening a Python workspace with zsh virtualenv auto-loading causes recursive deactivation processes and exhausts system resources.

## Best solution

Make the core extension's legacy environment-variable activation and deactivation flow coexist safely with shell startup plugins without recursive shell creation. Preserve normal virtualenv activation and deactivation, and verify both the hidden initialization terminal and ordinary terminal paths.

## Plan brief

- **Likely files:** `src/client/terminals/envCollectionActivation/service.ts`, `src/client/terminals/envCollectionActivation/deactivateService.ts`, `python_files/deactivate/zsh/deactivate`
- **Validation:** In an isolated, process-capped zsh fixture, install the reporter's startup hook that calls deactivate outside a .venv directory and exercise legacy environment-variable activation with the Python Environments extension disabled. Cover absent and initialized envVars.txt, hidden snapshot-terminal startup, and ordinary terminal deactivation. Assert that initialization completes, shell descendants remain bounded, and normal activation and deactivation still work; verify separately that the Python Environments-enabled path remains unaffected.
- **Behavior:**

  > Opening a Python workspace must not create an unbounded chain of bash and zsh processes when a shell startup plugin automatically activates or deactivates virtualenvs. Users must not need to disable their plugin globally to prevent resource exhaustion. Hidden activation-initialization terminals must complete without recursive startup, and ordinary virtualenv activation and deactivation must continue to work. Acceptance checks should cover both fresh initialization and an existing environment snapshot under a strict process cap.
- **Trace:**

  > The complete startup hook and process ancestry are recorded at https://github.com/microsoft/vscode-python/issues/23820#issuecomment-2232571840, with independent macOS and Linux confirmations. TerminalEnvVarCollectionService._applyCollectionImpl in src/client/terminals/envCollectionActivation/service.ts puts the deactivation directory on PATH before TerminalDeactivateService.initializeScriptParams creates a hidden shell in that directory. That directory has no project .venv, so the supplied plugin calls deactivate during startup. python_files/deactivate/zsh/deactivate ends by launching zsh, allowing another startup-plugin invocation; without a usable saved PATH, its inherited deactivation lookup remains available. The source identifies the recursive mechanism, but current-main timing and snapshot-state behavior have not been executed, and no dedicated deactivation regression harness was found. The flow is gated by the terminal environment-variable experiment and bypassed when useEnvExtension() is true; preserve that boundary and avoid changing unrelated shell plugins or sibling-extension activation behavior.

## Evidence

- **Reproduction and isolated trigger:** https://github.com/microsoft/vscode-python/issues/23820#issuecomment-2232571840 supplies the complete startup plugin: it calls deactivate when the current directory has no .venv. The reporter identified bash parents executing python_files/deactivate/zsh/deactivate with zsh children loading that plugin; disabling the plugin stops the runaway processes.
- **Independent confirmations:** Several commenters confirmed the same auto-loading configuration and recovery after downgrading to 2024.8.1. https://github.com/microsoft/vscode-python/issues/23820#issuecomment-2547359461 also reports thousands of deactivate shells and memory exhaustion on a Linux SSH host, with the same TERM_PROGRAM workaround.
- **Current activation exposure:** src/client/terminals/envCollectionActivation/service.ts, TerminalEnvVarCollectionService._applyCollectionImpl, prepends the deactivation script directory to PATH at process creation and shell integration, then calls initializeScriptParams. src/client/terminals/envCollectionActivation/deactivateService.ts creates a hidden shell with its working directory set to that script directory and sends the environment snapshot command only after terminal creation.
- **Current recursive-shell mechanism:** python_files/deactivate/zsh/deactivate restores variables from envVars.txt, invokes its local deactivate function, and then launches zsh. The new shell can reload the reporter's startup plugin and invoke the PATH-resolved deactivate executable again. In particular, when envVars.txt is absent or supplies no saved PATH, the script leaves the inherited PATH intact; the snapshot is produced later by python_files/printEnvVariablesToFile.py. There is no recursion guard in the script.
- **Migration is not proof of a fix:** TerminalEnvVarCollectionService.activate and _applyCollectionImpl bypass the legacy collection when useEnvExtension() is true. Otherwise, the experiment-gated deactivation path remains available. No current-main execution was performed, and the checkout is shallow, so local history cannot establish a complete fixing-commit history.
- **Canonical search:** Searches for zsh/deactivate, increasing shell processes, and virtualenv process creation did not establish an older open report with the same observable symptom. https://github.com/microsoft/vscode-python/issues/23305 was read and verified open, but concerns an additional tmux session rather than recursive deactivation and resource exhaustion; it is not a canonical duplicate. No open PR referencing this issue was found.
