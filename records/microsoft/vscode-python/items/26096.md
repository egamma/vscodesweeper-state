# Issue #26096 — Run Selection/Line in Terminal becomes extremely slow and garbled when pyreadline3 is installed in the target interpreter

[https://github.com/microsoft/vscode-python/issues/26096](https://github.com/microsoft/vscode-python/issues/26096)

## Summary

The evidence isolates the slowdown to pyreadline3's Windows console-input handling rather than character-by-character dispatch by the Python extension. Keep this open while the upstream behavior and any extension-side mitigation are investigated.

## Change summary

Run Selection/Line becomes slow and corrupts terminal rendering when the selected Windows interpreter has pyreadline3 installed.

## Best solution

The pyreadline3 input path should handle VS Code terminal writes without per-character delay or screen corruption. The Python extension can retain the native REPL workaround and assess whether it should detect this incompatible classic-REPL configuration or otherwise bypass the affected path.

## Evidence

- **isolated dependency behavior:** The reporter reproduced across multiple VS Code builds, PowerShell versions, clean settings, and disabled extensions; uninstalling only pyreadline3 immediately resolves the delay and rendering corruption.
- **single extension write:** src/client/terminals/codeExecution/terminalCodeExecution.ts passes the normalized selection once to executeCommand, and src/client/common/terminal/service.ts forwards Python REPL code through one Terminal.sendText(commandLine) call rather than iterating over characters.
- **Windows boundary:** python_files/pythonrc.py deliberately excludes win32 from its readline and Python shell-integration hooks, leaving pyreadline3 to own console input processing after the extension writes to the terminal.
- **working bypass:** The reporter confirms that python.REPL.sendToNativeREPL avoids the affected classic terminal REPL path.
- **upstream tracker:** pyreadline3 is the Windows GNU-readline implementation maintained at https://github.com/pyreadline3/pyreadline3; no verified open canonical issue currently covers this exact failure.
