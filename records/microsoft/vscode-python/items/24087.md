# Issue #24087 — Python Test uses incorrect python environment

[https://github.com/microsoft/vscode-python/issues/24087](https://github.com/microsoft/vscode-python/issues/24087)

## Summary

Keep open for the accepted testing investigation: multiple users confirmed discovery selecting Python outside the chosen conda environment. Current environment plumbing has changed, but neither a verified post-reopen fix nor a matching canonical establishes that this report is resolved.

## Change summary

Pytest discovery and execution use a different interpreter from the selected conda environment when native discovery is enabled.

## Best solution

Establish whether the confirmed interpreter mismatch persists through current native environment resolution and pytest subprocess creation, then ensure discovery and execution retain the selected conda interpreter. Investigate the existing core integration before attributing the defect to the native locator or transferring ownership.

- **Behavior:**

  > Refreshing tests must collect them using the selected conda environment, not another Python installation found on PATH. The reported failure rejects coverage arguments or cannot import dependencies installed in the selected environment. Verify discovery and ordinary execution with different packages installed in the selected and system interpreters. Existing interpreter selection and support for other environment managers must remain unchanged.
- **Trace:**

  > The reporter's debug log shows a Python executable incorrectly supplied as the conda prefix, followed by the missing-executable fallback and bare python execution. Current nativeAPI.ts:getLocation distinguishes conda prefixes from executables, and legacyIOC.ts:ComponentAdapter.getCondaEnvironment forwards that location into createCondaEnv. Conda.getInterpreterPathForEnvironment still returns 'python' when the constructed executable is absent, and pythonEnvironment.ts:createDeps replaces stored command arguments for bare interpreter names. Current pytestDiscoveryAdapter.ts additionally has separate environment-extension and execution-factory paths. Historical reproduction is confirmed by multiple commenters, but the unresolved step is reproducing the mismatch on current main and identifying which current producer supplies incorrect environment data. Preserve unrelated pixi handling and do not assume the native locator itself owns the defect. https://github.com/microsoft/vscode-python/pull/24198 predates the reopen and addresses handler ordering rather than proving this report fixed.

## Evidence

- **Confirmed failure and workaround:** The discussion on https://github.com/microsoft/vscode-python/issues/24087 includes independent Windows and macOS confirmations that testing ignores the selected conda interpreter; switching python.locator from native to js restored testing for multiple users. Removing PowerShell profile output did not resolve the reporter's failure.
- **Diagnostic trigger:** https://github.com/microsoft/vscode-python/issues/24087#issuecomment-2344652552 records Refresh Tests passing a conda prefix ending in Autobot\python.exe, followed by 'Executable does not exist within conda env' and bare python execution. The reporter subsequently supplied a traceback under C:\Python311 rather than the selected conda environment.
- **Current source boundary:** src/client/pythonEnvironments/nativeAPI.ts:getLocation now returns the native prefix for conda environments. src/client/pythonEnvironments/legacyIOC.ts:ComponentAdapter.getCondaEnvironment passes env.location to createCondaEnv in src/client/common/process/pythonEnvironment.ts. That path still reaches Conda.getInterpreterPathForEnvironment, whose missing-executable fallback returns 'python'; createDeps can then replace the conda argument vector when the interpreter is a bare command. This explains the logged failure mechanism conditionally, but does not establish that current native resolution still supplies the malformed prefix.
- **Changed testing execution:** src/client/testing/testController/pytest/pytestDiscoveryAdapter.ts now uses getEnvironment/runInBackground when the Python Environments extension is active, otherwise PythonExecutionFactory.createActivatedEnvironment. These distinct current paths require reproduction; source inspection alone cannot establish that the environment-dependent failure is gone.

The issue was reopened on 2024-12-08 after its information-timeout closure, so this earlier PR cannot justify a completed close.
