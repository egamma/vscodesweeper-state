# Issue #24960 — Run Selection/Line in already active python interpreter terminal rather than opening a new terminal

[https://github.com/microsoft/vscode-python/issues/24960](https://github.com/microsoft/vscode-python/issues/24960)

## Summary

Keep open as the canonical request: manually created Python terminals still cannot be targeted by Run Selection/Line, and the maintainer explicitly confirmed that terminal reuse remains valuable after closing the outdated implementation PR.

## Change summary

Allow Run Selection/Line to send code to an already configured Python interpreter terminal instead of creating an extension-managed terminal.

## Best solution

Implement an opt-in or otherwise unambiguous way to select and reuse an existing Python terminal within the current queue-based execution architecture, while retaining creation of an extension-managed REPL as the fallback.

## Evidence

- **current source:** src/client/terminals/codeExecution/terminalCodeExecution.ts obtains an extension-managed terminal from TerminalServiceFactory; initializeRepl only reuses it after this provider's replActive promise has been established, so it does not adopt a manually configured active terminal.
- **no existing setting:** package.json declares python.execSelectionInTerminal and the REPL settings, but provides no setting or command for targeting an existing manually created terminal.
- **implementation attempt:** https://github.com/microsoft/vscode-python/pull/25178 attempted this change but was closed without merging. The closing maintainer comment says the goal remains valuable and that a new implementation must be rewritten for the queue-based terminal execution architecture introduced by https://github.com/microsoft/vscode-python/pull/25669.
- **canonical search:** Searches for open vscode-python issues about reusing an existing terminal found this issue itself and no broader open canonical that owns the same request.
- **workaround limitation:** The discussion confirms reuse currently works only when the terminal was first created through Run Selection/Line; the documented workaround requires restructuring the SLURM workflow and does not provide the requested capability.
