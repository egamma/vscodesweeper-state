# Issue #21845 — Proposal: Enable separate configs per run/discovery/debug/coverage with testing

[https://github.com/microsoft/vscode-python/issues/21845](https://github.com/microsoft/vscode-python/issues/21845)

## Summary

Keep this accepted testing-configuration proposal open: current main still shares arguments across testing actions rather than supporting named, independently configured profiles. The 43 upvotes and ongoing design discussion support completing the proposal, not retiring it.

## Change summary

Support separate, selectable testing configurations with action-specific arguments and environments for discovery, execution, debugging, and coverage.

## Best solution

Finalize the public configuration and profile-selection contract here, coordinated with https://github.com/microsoft/vscode-python/issues/23777, then deliver action-specific configurations without requiring users to edit shared arguments between actions. Preserve automatic discovery and existing testing workflows during migration.

## Plan brief

- **Likely files:** `package.json`, `src/client/testing/testController/controller.ts`, `src/client/testing/testController/pytest/pytestDiscoveryAdapter.ts`, `src/client/testing/testController/pytest/pytestExecutionAdapter.ts`, `src/client/testing/testController/unittest/testDiscoveryAdapter.ts`, `src/client/testing/testController/unittest/testExecutionAdapter.ts`, `src/client/testing/common/debugLauncher.ts`
- **Validation:** Exercise pytest and unittest fixtures with distinct discovery, run, debug, and coverage arguments and environment sentinels; verify each action receives only its selected configuration. Switch between two named execution profiles, check default persistence, and confirm existing settings-only workspaces still discover, run, and debug tests.
- **Behavior:**

  > Users should be able to configure testing actions independently and select among multiple named execution configurations without repeatedly editing shared settings. Discovery must remain automatic rather than requiring a manual debug launch. Acceptance checks should distinguish arguments and environment values received during discovery, run, debug, and coverage, and verify profile selection and existing-workspace compatibility.
- **Trace:**

  > The current manifest exposes shared pytestArgs and unittestArgs, and PythonTestController registers three fixed action profiles. Pytest discovery and execution consume the same pytestArgs; execution additionally filters positional arguments and toggles coverage through an environment variable. Unittest execution similarly consumes shared unittestArgs. DebugLauncher independently selects the first matching debug-test configuration and supports its environment settings, so debugging support is partial rather than a unified profile model. https://github.com/microsoft/vscode-python/issues/23777 records prototype engineering work and unresolved public-contract questions; coordinate with it rather than treating the prototype as shipped. Preserve runner-owned discovery, test identities, result reporting, and existing debug-test behavior; the remaining uncertainty is the configuration contract, profile scope, and discovery-selection semantics.
- **Open decisions:**
  - Is the testing framework selected per named configuration or once for the workspace/project?
  - Can multiple discovery configurations contribute simultaneous test trees, or is only one discovery configuration active at a time?
  - Which configuration scopes are supported—user, workspace, and project—and how are profiles associated with roots in multi-root workspaces?
  - Does the final configuration contract retain independent launch.json debugging settings, as the latest proposal suggests, or allow shared configuration references and overrides?
