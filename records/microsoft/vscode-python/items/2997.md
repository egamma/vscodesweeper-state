# Issue #2997 — Run Selection/Line and Run File produce error when used consecutively

[https://github.com/microsoft/vscode-python/issues/2997](https://github.com/microsoft/vscode-python/issues/2997)

## Summary

Keep this canonical report open: the legacy terminal execution path still reuses a Python REPL for shell commands and retains stale REPL state after exit(). Newer shell-integration and environment-extension paths warrant runtime investigation, but do not establish that both reported failures are fixed.

## Change summary

Alternating Run Selection/Line and Run File sends commands to the wrong interpreter or shell context.

## Best solution

Make terminal execution honor the actual process context so file execution reaches a shell and subsequent selections reach a live Python interpreter. Preserve this issue as the canonical report and verify the behavior with and without the Python Environments extension.

Exit the REPL manually and repeat file → selection. Every operation must print hello in the correct execution context without SyntaxError or shell errors. Repeat with Python Environments enabled and disabled and shell integration enabled and disabled, then pin the established lifecycle behavior with regression tests.
- **Behavior:**

  > Run File and Run Selection/Line must remain usable when alternated in either order. A file invocation must not be interpreted as Python source, and a selection must not be interpreted as a shell command. After the user exits the REPL, the next selection must reach a newly initialized Python interpreter. Validate repeated transitions, not only the first invocation.
- **Trace:**

  > CodeExecutionManager routes legacy file and terminal-selection execution through the same standard TerminalCodeExecutionProvider. TerminalServiceFactory returns a cached terminal for both operations; executeFile() does not account for a running REPL, while initializeRepl() remembers readiness until terminal closure. TerminalService also retains its Python readiness flag after interpreter exit. This conclusively exposes the legacy failure, particularly without shell integration. Modern file execution can instead delegate through runInTerminal() in the Python Environments integration, and its interaction with legacy selection terminals remains unverified. The planning session should establish actual lifecycle events and ownership across these paths before bounding the change. Preserve interpreter selection, launch arguments, working-directory settings, dedicated-file terminals, and unrelated native-REPL and Django behavior. Related reports were consolidated into this issue, including https://github.com/microsoft/vscode-python/issues/14512.

## Evidence

- **Confirmed reproduction:** https://github.com/microsoft/vscode-python/issues/2997#issuecomment-541017984 documents file → selection → file producing SyntaxError inside the REPL, followed by exit() → file → selection sending Python code to cmd.exe. The original report provides Ubuntu/venv steps, so basic reproduction information is not missing.
- **Shared execution context:** src/client/terminals/codeExecution/codeExecutionManager.ts uses the same 'standard' ICodeExecutionService for legacy file and selection execution. TerminalCodeExecutionProvider.executeFile() sends the interpreter-and-file command without checking or exiting an active REPL; execute() initializes the REPL on the same terminal service. src/client/common/terminal/factory.ts caches that service by title/workspace/interpreter, with no distinction between ordinary file execution and selection execution.
- **Stale REPL state:** src/client/terminals/codeExecution/terminalCodeExecution.ts: initializeRepl() returns early when replActive resolves true and resets it only on terminal closure, not interpreter exit. src/client/common/terminal/service.ts similarly retains isReplReady until terminal closure. After exit(), later selections can therefore be sent directly to the underlying shell.
- **Modern integration does not prove resolution:** TerminalService.executeCommandInternal() uses shellIntegration.executeCommand() when available and otherwise sends text, without a process-context guard. python_files/pythonrc.py supplies prompt and execution markers, not shell-command routing or REPL-exit handling. CodeExecutionManager delegates file execution to the Python Environments extension when enabled, while terminal selections retain the standard provider; that combination was not executed in this read-only review.
- **Canonical search:** Live searches for REPL/file execution and terminal/interpreter exit found no older open report with the same observable failures. https://github.com/microsoft/vscode-python/issues/7206 and https://github.com/microsoft/vscode-python/issues/14512 are closed with maintainer comments identifying this issue as their duplicate target. https://github.com/microsoft/vscode-python/issues/21693 and https://github.com/microsoft/vscode-python/issues/22763 likewise point here.
- **Maintainer intent and implementation ownership:** https://github.com/microsoft/vscode-python/issues/2997#issuecomment-2537250447 identifies this as a bug; current labels include needs proposal. The inspected cross-reference timeline contains closed issues, not an open implementation PR.
- **Existing alternatives:** package.json declares python.REPL.sendToNativeREPL, default false, and a separate-terminal execution command. These provide alternative workflows, not automatic correctness for alternating the two reported terminal commands.
