[https://github.com/microsoft/vscode-python/issues/20211](https://github.com/microsoft/vscode-python/issues/20211)

## Summary

Keep open: the core .env parser still leaves ${env:VARIABLE} references unresolved. The debugger-only report is closed, and the open standardization tracker does not establish that restoring this specific behavior is its agreed outcome.

## Change summary

Restore environment-variable substitution for ${env:VARIABLE} references in .env files.

## Best solution

## Evidence

- **Current source defect:** src/client/common/variables/environment.ts: parseEnvFile calls substituteEnvVars for every value. SUBST_REGEX parses ${env:HOME} with substName='env' and bogus=':HOME'; the bogus guard marks it invalid and preserves the literal reference, even when baseVars contains HOME.
- **Core consumer:** src/client/common/variables/environmentVariablesProvider.ts: getCustomEnvironmentVariables and getCustomEnvironmentVariablesSync pass this.process.env to parseFile and parseFileSync. Thus PYTHONPATH=${env:HOME}/external remains literal on this core path, whereas ${HOME} can resolve.
- **Acknowledged expectation:** The issue cites previously documented support. The January 2023 maintainer comment says support was being removed from documentation 'until we fix this'; the author explicitly distinguishes the broader inconsistency from the debugger-only report. Current labels include needs PR.
- **Concrete historical reproduction:** https://github.com/microsoft/vscode-python/issues/19420#issuecomment-1178022954 reports that printing PYTHONPATH yields /Users/${env:USER}/python-test/external rather than an expanded value; subsequent comments supply logs. This corroborates the literal-reference symptom.
- **Rejected duplicate lead:** https://github.com/microsoft/vscode-python-debugger/issues/523 is CLOSED following an unanswered information request, not a verified fix. It covers debugging specifically and cannot serve as an open canonical for this broader report.
- **Related standardization work:** https://github.com/microsoft/vscode-python/issues/18307 is OPEN and older, but is a meta issue spanning dotenv parsing, syntax standardization, recursion, and debugger integration. Its proposed direction may standardize on ${VARIABLE} rather than restore ${env:VARIABLE}; resolving it does not necessarily deliver this report's requested compatibility. https://github.com/microsoft/vscode-python/issues/18307#issuecomment-2539794337 identifies planned work in the Python Environments extension.
- **Other canonical search result:** https://github.com/microsoft/vscode-python/issues/14518 is OPEN but primarily requests VS Code configuration substitution such as ${workspaceFolder}, which a maintainer classified as an enhancement. It is not the same observable environment-variable substitution failure required by the re-review duplicate bar. A focused open-issue search found no additional verified canonical.
- **Existing validation surface:** src/test/common/variables/envVarsService.unit.test.ts contains the 'Parsing Environment Variables Files' → 'parseEnvFile()' → 'variable substitution' suites, including base variables, recursive substitution, escaping, and malformed syntax. These exercise ${VARIABLE}, but do not establish a prefixed-syntax compatibility contract. No tests were executed in the read-only checkout.
