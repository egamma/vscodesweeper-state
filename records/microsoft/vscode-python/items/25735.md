# Issue #25735 — Audit and potentially deprecate `defaultInterpreterPath` updates when Python Environments extension is active

[https://github.com/microsoft/vscode-python/issues/25735](https://github.com/microsoft/vscode-python/issues/25735)

## Summary

Keep this accepted audit open: current main distinguishes setting writes from stored interpreter selections, and some environment-extension guards already exist. The remaining work is to settle setting ownership and explicit-selection API behavior, not to blanket-disable every listed update.

## Change summary

Audit interpreter-update paths and determine whether either extension should modify python.defaultInterpreterPath when Python Environments is active.

## Best solution

Preserve the user-configured fallback while establishing a consistent environment-selection contract across the core extension and Python Environments. Complete the audit of actual configuration writes separately from persistent selection updates before deciding any deprecation.

## Plan brief

- **Likely files:** `src/client/common/interpreterPathService.ts`, `src/client/environmentApi.ts`, `src/client/deprecatedProposedApi.ts`, `src/client/interpreter/interpreterService.ts`, `src/client/interpreter/virtualEnvs/virtualEnvPrompt.ts`, `src/client/interpreter/virtualEnvs/activatedEnvLaunch.ts`, `src/client/pythonEnvironments/creation/createEnvApi.ts`, `src/client/interpreter/configuration/pythonPathUpdaterService.ts`
- **Validation:** With Python Environments enabled and disabled, record the configured fallback and selected environment before and after interpreter selection, new-venv prompting, CLI launch from an activated environment, Create Environment, and both selection APIs. Verify fallback writes and active-selection results against the agreed contract, including no-workspace and multi-root cases; preserve legacy behavior outside the agreed scope.
- **Behavior:**

  > The audit must distinguish changes to the user-configured python.defaultInterpreterPath fallback from changes to the active environment. With Python Environments active, unsolicited core-extension writes must not override that fallback. Explicit user selection and extension API requests must retain a documented, consistent result. Acceptance checks should cover both extension modes, global versus workspace scope, and the prompting, launch, creation, and API scenarios listed in the issue.
- **Trace:**

  > InterpreterPathService.update() in src/client/common/interpreterPathService.ts writes configuration only for Global; other scopes use persistent selection state. Both environmentApi.updateActiveEnvironmentPath() and deprecatedProposedApi.setActiveEnvironment() pass WorkspaceFolder, so the issue body's claim that every listed caller rewrites the setting is too broad. PythonPathUpdaterService and its scope-specific services ultimately reach the same central method. InterpreterService.resolveActiveInterpreter() already bypasses ActivatedEnvironmentLaunch when useEnvExtension() is true, and registerCreateEnvironmentFeatures() delegates the command to python-envs.createAny, although creation API and event paths remain separate. The uncertainty is the intended ownership and selection contract, not proof that all six paths currently conflict. Preserve legacy mode and user-configured fallback reads; related symptom reports https://github.com/microsoft/vscode-python/issues/25629 and https://github.com/microsoft/vscode-python-environments/issues/660 do not replace this broader audit.
- **Open decisions:**
  - Should python.defaultInterpreterPath always remain user-authored, including explicit global interpreter selection, or may an explicit user action update it?
  - When Python Environments is active, should the existing public and deprecated selection APIs change its active selection, retain independent legacy selection state, or be deprecated?
