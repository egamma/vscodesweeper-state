# Issue #22896 — Confusing test screen when working with a monorepo

[https://github.com/microsoft/vscode-python/issues/22896](https://github.com/microsoft/vscode-python/issues/22896)

## Summary

Keep this accepted testing request open: current source still does not consistently honor multi-root workspace display names in test roots and discovery errors. Project-based testing adds project labels, but does not establish that the reporter's workspace aliases are respected across all supported paths.

## Change summary

Distinguish identically named service directories in the Test Explorer and discovery errors using their configured workspace display names.

## Best solution

Make testing roots and discovery-error labels distinguish the reporter's A - api, B - api, and C - api workspaces without changing discovery directories or test identities. Agree on how workspace aliases coexist with the newer Python project labels, then implement consistent display behavior in the testing integration.

Verify distinguishable roots and discovery-error labels for each service, including after refresh and with project-based testing enabled and disabled; executing a selected test must still use the corresponding service directory and interpreter.
- **Behavior:**

  > Three independent services whose directories are all named api must remain distinguishable in the Test Explorer using their configured workspace display names. Discovery-error labels must identify the same service rather than showing three identical api labels. Discovery, execution, interpreter selection and test identities must retain their existing behavior. Acceptance includes discovery refresh and both legacy workspace testing and project-based testing.
- **Trace:**

  > In src/client/testing/testController/common/utils.ts, populateTestTree chooses a supplied project name or the discovery payload's root name, while buildErrorNodeOptions chooses a supplied project name or the filesystem basename. PythonResultResolver forwards optional project names through TestDiscoveryHandler; TestProjectRegistry.createProjectAdapter supplies PythonProject.name, but its fallback resolver does not, and legacy error callers in workspaceTestAdapter.ts and controller.ts also omit a name. These source paths establish that workspace aliases are not consistently used, without executing the extension. Keep filesystem URIs, pytest roots, scoped test IDs and interpreter associations unchanged: this request concerns presentation. The uncertainty is the intended presentation when a named Python project and a custom workspace alias coexist. The maintainer discussion at https://github.com/microsoft/vscode-python/issues/22896 suggests a workspace grouping node, but does not settle that newer project-mode contract.
- **Open decisions:**
  - When project-based testing exposes multiple named projects inside a custom-named workspace, should the Test Explorer add a workspace-alias grouping node while retaining project labels, or incorporate the workspace alias into each project root and discovery-error label?
