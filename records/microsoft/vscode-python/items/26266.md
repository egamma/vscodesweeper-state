# Issue #26266 — Support auto-refreshing Test Coverage from an external report

[https://github.com/microsoft/vscode-python/issues/26266](https://github.com/microsoft/vscode-python/issues/26266)

## Summary

External coverage import remains a genuine capability gap; route this to area-testing for scope approval. The reporter accepts manual import first, with automatic watching deferred.

## Change summary

Render externally generated Cobertura reports in VS Code's Test Coverage view and editor decorations without rerunning tests.

## Best solution

Establish a manual import/refresh workflow for local Cobertura reports, with workspace path mapping and explicit errors. Decide how imported coverage relates to Test Results before adding automatic watching.

## Plan brief

- **Likely files:** `package.json`, `package.nls.json`, `src/client/testing/main.ts`, `src/client/testing/testController/controller.ts`, `src/client/testing/testController/common/testCoverageHandler.ts`, `src/client/testing/testController/common/resultResolver.ts`, `src/client/testing/testController/common/projectTestExecution.ts`
- **Validation:** In an Extension Development Host, import a CLI-generated Cobertura report and verify file totals and covered/missed line decorations without launching pytest. Update the report and manually refresh; check relative paths spanning two workspace roots, missing files, and malformed XML. Confirm ordinary Test Explorer coverage runs retain their behavior.
- **Behavior:**

  > Developers can manually import and refresh a local Cobertura report generated outside Test Explorer without rerunning tests. The Test Coverage view and editor decorations reflect the imported file and line coverage. Workspace file mapping works for the agreed single-root and multi-root scope, and missing or malformed reports produce clear errors. Automatic watching and importing test-result artifacts are outside the initial milestone.
- **Trace:**

  > package.json and src/client/testing/main.ts expose no external coverage import surface. PythonResultResolver.resolveExecution in common/resultResolver.ts receives structured runner coverage payloads and delegates to TestCoverageHandler.processCoverage, which publishes FileCoverage through a TestRun and returns detailed line coverage. PythonTestController.setupCoverageIfNeeded and setupCoverageForProjects attach detail loaders to coverage profiles using resolver maps. This establishes reusable rendering machinery but not a standalone artifact lifecycle or Cobertura parser. Preserve existing execution-backed coverage and do not fabricate test pass/fail outcomes from coverage alone. https://github.com/microsoft/vscode-python/issues/25643 is related multi-root display work, not an external-import canonical. The uncertainty begins at how imported artifacts are represented in Test Results and how relative report paths are assigned to workspace roots.
- **Open decisions:**
  - How should an imported coverage artifact appear in Test Results, and should refreshing it replace the previous imported entry or create a new historical entry?
  - For relative Cobertura paths spanning workspace roots, what resolution contract should apply, and should ambiguous mappings require explicit user configuration?
