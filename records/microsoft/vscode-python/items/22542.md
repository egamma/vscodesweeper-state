## Plan brief

- **Likely files:** `src/client/terminals/codeExecution/terminalCodeExecution.ts`, `src/client/common/utils/localize.ts`, `src/client/terminals/codeExecution/helper.ts`, `python_files/normalizeSelection.py`, `src/test/terminals/codeExecution/smartSend.test.ts`
- **Validation:** After the UX is agreed, check Shift+Enter with Smart Send enabled and no selection in a file containing a syntax error: feedback must identify the blocked execution and provide the agreed recovery without changing the Smart Send setting unless explicitly requested. Check valid-file execution and explicit-selection execution remain unchanged, and pin the selected recovery contract in terminal execution tests.
- **Behavior:**

  > When whole-file parsing prevents Smart Send execution, the user currently receives a detached notification whose only action disables the feature. The goal is feedback connected to the attempted execution, with an understandable way to recover while retaining Smart Send. Acceptance should cover a parse failure, recovery without an unintended setting change, and unchanged valid-file and explicit-selection behavior. The final feedback surface and recovery semantics remain to be agreed.
- **Trace:**

  > python_files/normalizeSelection.py, traverse_file(), catches whole-file parsing failures and returns the 'deprecated' sentinel without structured error-location information. CodeExecutionHelper.normalizeLines() in src/client/terminals/codeExecution/helper.ts propagates that result, and TerminalCodeExecutionProvider.execute() in src/client/terminals/codeExecution/terminalCodeExecution.ts shows a non-modal warning with only Repl.disableSmartSend. Diagnostics.invalidSmartSendMessage in src/client/common/utils/localize.ts already describes explicit selection as a workaround, but the notification does not expose that recovery as an action. Preserve valid Smart Send execution, explicit-selection behavior, and the user's configured setting unless a setting change is expressly chosen. https://github.com/microsoft/vscode-python/issues/22558 provides related wording and contextual-feedback discussion, but it is younger than this report and is not a valid duplicate canonical here.
- **Open decisions:**
  - Should parse-failure feedback appear beside the editor execution context, in the REPL, or in a modal dialog when contextual feedback is unavailable?
  - Should recovery offer one-time execution without Smart Send, guide the user to an explicit selection, or offer both?
