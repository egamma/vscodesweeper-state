# Issue #10645 — Add Profiling (code performance analysis) capability

[https://github.com/microsoft/vscode-python/issues/10645](https://github.com/microsoft/vscode-python/issues/10645)

## Summary

Keep open: general-purpose Python profiling with a searchable, sortable results view remains missing from this extension. The accepted needs-proposal label and 367 upvotes support a scoped design discussion; existing third-party alternatives are not evidence that this request is completed or declined.

## Change summary

Integrate a Python profiler such as cProfile with a user-friendly results table for identifying expensive functions.

## Best solution

Develop a scoped proposal that integrates an existing Python profiler rather than creating a new profiling engine, and explicitly decides whether the experience belongs in this extension or a dedicated companion extension. Preserve this issue as the public request while settling the initial profiler, supported measurements, and results interface.

## Plan brief

- **Likely files:** `package.json`, `src/client/terminals/codeExecution/codeExecutionManager.ts`, `src/client/tensorBoard/tensorboardIntegration.ts`, `src/client/tensorBoard/tensorBoardSession.ts`
- **Validation:** For an agreed cProfile/table first slice, profile a small script containing a deliberately expensive function using the selected interpreter; verify that its results appear in VS Code, sorting by time brings that function to the top, and searching by its name filters the table correctly. Confirm ordinary run/debug behavior remains unchanged.
- **Behavior:**

  > Users want to profile ordinary Python scripts and inspect which functions account for execution time without leaving VS Code. The proposed first slice is an existing profiler such as cProfile paired with a searchable, sortable statistics table. Once the scope is agreed, acceptance should demonstrate that a known expensive function is visible, can be found by name, and can be ranked by its measured cost. Memory profiling and additional visualizations remain product-scope decisions rather than implicit requirements for the first slice.
- **Trace:**

  > package.json declares terminal execution commands and python.terminal.launchArgs but no general profiling command or results view. src/client/terminals/codeExecution/codeExecutionManager.ts::registerCommands connects those commands to existing interpreter-aware execution, including delegation to the environments extension. The profiling-related code found in src/client/tensorBoard/tensorBoardSession.ts handles specialized TensorBoard/PyTorch prerequisites; src/client/tensorBoard/tensorboardIntegration.ts::registerApi demonstrates companion-extension integration, not coverage of the requested general profiling workflow. No implementation boundary for a new viewer is established yet, and ordinary execution, debugging, and TensorBoard integration must retain their behavior. The younger placeholder https://github.com/microsoft/vscode-python-internalbacklog/issues/28 does not replace the public request at https://github.com/microsoft/vscode-python/issues/10645. Planning should begin with the unresolved user-facing scope identified in the maintainer discussion, not assume a new profiling engine or editor-wide API is required.
- **Open decisions:**
  - Should the first supported workflow target cProfile CPU/function timing only, or include other profiler formats or memory measurements?
  - Should the initial results interface be the requested searchable, sortable statistics table alone, or also include flamegraph or source-annotation views?
  - Should users access this capability through the core Python extension or a dedicated companion extension?
