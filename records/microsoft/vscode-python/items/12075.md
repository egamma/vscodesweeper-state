# Issue #12075 — Enable multiple test suites and test configurations in the Test UI

[https://github.com/microsoft/vscode-python/issues/12075](https://github.com/microsoft/vscode-python/issues/12075)

## Summary

Keep this accepted testing request open: current main provides run/debug/coverage modes and project-specific environments, but not selectable named configurations or arbitrary test-suite groupings. Maintainers have explicitly used this issue as the canonical request; the newer configuration proposal is related design work, not a duplicate target.

## Change summary

Allow users to define and select multiple test configurations and custom test groups in Test Explorer without repeatedly editing workspace settings.

## Best solution

Develop the accepted testing configuration design alongside https://github.com/microsoft/vscode-python/issues/21845, explicitly covering multiple configurations within the same run mode and user-defined suites. Preserve this issue as the requirements record until those capabilities are delivered or their scope is explicitly decided.

## Plan brief

- **Likely files:** `package.json`, `src/client/testing/testController/controller.ts`, `src/client/testing/testController/common/testProjectRegistry.ts`, `src/client/testing/testController/common/projectTestExecution.ts`, `src/client/testing/testController/common/testItemUtilities.ts`, `src/client/testing/testController/pytest/pytestDiscoveryAdapter.ts`, `src/client/testing/testController/pytest/pytestExecutionAdapter.ts`, `src/client/testing/testController/unittest/testDiscoveryAdapter.ts`, `src/client/testing/testController/unittest/testExecutionAdapter.ts`, `src/client/testing/testController/common/resultResolver.ts`
- **Validation:** The plan should culminate in controller/adapter tests and a Test Explorer acceptance check using fast and slow marked tests: select two named configurations with distinct arguments and environment variables without editing settings; verify the selected configuration reaches the runner, custom groups expose the intended tests, and an explicitly selected test can run under the designated individual-test configuration. Existing run/debug/coverage and project-environment behavior must remain intact.
- **Behavior:**

  > Users currently must edit test arguments or environment settings to alternate between test workflows within one project. They want selectable named configurations and custom suites based on explicit test membership or criteria such as pytest markers, available through Test Explorer and individual-test actions. Acceptance should demonstrate switching configurations without settings edits, applying each configuration's arguments and environment, and running a selected test under an individual-test configuration regardless of a suite's exclusions. The design must explicitly account for overlapping suites and the requested all/other views rather than treating project roots as equivalent coverage.
- **Trace:**

  > PythonTestController in src/client/testing/testController/controller.ts registers only fixed Run, Debug, and Coverage profiles. package.json exposes one argument array per framework, and PytestTestDiscoveryAdapter/PytestTestExecutionAdapter read that configuration when constructing subprocess arguments. TestProjectRegistry and executeTestsForProjects provide project-specific environments and tree roots, but not multiple named configurations for the same project. removePositionalFoldersAndFiles already removes -k/-m during execution, so preserve that existing individual-selection behavior rather than assuming the historical filtering complaint is unchanged. Test-item tags currently identify run/debug capability, not user-defined marker groups. https://github.com/microsoft/vscode-python/issues/21845 supplies related design discussion, while https://github.com/microsoft/vscode-python/issues/17206 and https://github.com/microsoft/vscode-python/issues/25916 establish this issue as the larger requirements record. The uncertainty begins at the public configuration model, selection precedence, and custom-suite presentation; no bounded implementation has yet been established.
- **Open decisions:**
  - What public configuration model should support multiple named configurations within each execution mode, and how should it coexist with existing python.testing settings and test-debug launch configurations?
  - When a suite default, a currently selected configuration, and an individual-test configuration differ, which applies to each Test Explorer or editor action, and how does the user explicitly choose another?
  - Should the initial delivery include overlapping marker/manual suites with all/other views and external-script runners, or stage those capabilities separately from named configuration selection?
