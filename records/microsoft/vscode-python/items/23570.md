# Issue #23570 — Native REPL should allow for environment configuration

[https://github.com/microsoft/vscode-python/issues/23570](https://github.com/microsoft/vscode-python/issues/23570)

## Summary

Keep open: the native REPL still lacks configurable project initialization, and existing interpreter selection and workspace-directory handling only partially cover the request. The 29 upvotes, community ask label, and explicit maintainer support establish demand; no verified canonical owns the full scope.

## Change summary

Allow native REPL sessions to start with project-specific working directories, environment variables, and initialization code, including Django shell-style setup.

## Best solution

Define a project-scoped startup configuration contract for the core native REPL so users can initialize Django and other project contexts automatically. Decide whether Django shell integration is part of that contract or separate follow-up work, while preserving ordinary interpreter selection and unconfigured sessions.

## Vision fit

- **Fit:** aligned
- **Reason:** Configurable initialization makes the native REPL useful within existing Python projects and integrates community tooling rather than replacing it.
- **Evidence:** The public roadmap goal is Python support that is "fast, stable, and useful to anyone writing Python code for whatever reason"; the supplied durable themes include the REPL and run experience.

## Plan brief

- **Likely files:** `package.json`, `src/client/repl/replCommands.ts`, `src/client/repl/nativeRepl.ts`, `src/client/repl/pythonServer.ts`, `python_files/python_server.py`, `src/test/repl/nativeRepl.test.ts`
- **Validation:** In a sample project, configure a non-root working directory, an environment variable, and startup code defining a sentinel and initializing Django. Launch python.startNativeREPL and verify the first user cell sees the configured directory, variable, sentinel, and usable Django models without manual initialization. Close and reopen the session and verify initialization occurs once for each new session; verify an unconfigured project retains current behavior and configuration does not leak between workspace roots. Extend the REPL - Native REPL suite in src/test/repl/nativeRepl.test.ts to cover the agreed lifecycle.
- **Behavior:**

  > Users need native REPL sessions initialized for their project before executing their first cell, rather than manually repeating environment and framework setup. The requested configuration includes working directory, environment variables, and startup Python code, with Django shell and shell_plus as motivating workflows. Acceptance should demonstrate that configured initialization is available in the first cell and is applied consistently to new sessions. Projects without configuration must retain existing behavior.
- **Trace:**

  > registerStartNativeReplCommand in src/client/repl/replCommands.ts resolves the active interpreter and enters NativeRepl.create in src/client/repl/nativeRepl.ts. setReplDirectory selects a workspace root rather than reading custom REPL configuration, and createPythonServer in src/client/repl/pythonServer.ts launches python_files/python_server.py with cwd only. The Python helper begins its request loop without project initialization, and the contributed REPL settings expose sending and variable-display behavior, not startup configuration. Session recreation also occurs on notebook closure and interpreter changes, so initialization semantics must account for those paths. Preserve interpreter selection, Smart Send, JSON-RPC communication, and unconfigured-session behavior; changes to terminal REPL or Jupyter are outside this request. https://github.com/microsoft/vscode-python/issues/13027 supplies Django context but is closed and narrower; https://github.com/microsoft/vscode-python/issues/21707 lists this as unfinished child work. The uncertainty is the user-facing configuration contract and lifecycle, not whether the current native launch path already supports the full request.
- **Open decisions:**
  - Should native REPL startup use existing python.envFile and standard Python startup conventions, dedicated project-scoped REPL settings, or a combination, and what precedence should users observe?
  - Is automatic project initialization sufficient for the first delivery, or must Django manage.py shell and shell_plus be able to launch or attach to the native REPL directly?
  - When the interpreter changes or startup code fails, should the session rerun initialization before accepting input, remain available with a visible error, or stop until initialization succeeds?

## Evidence

- **Community and maintainer support:** The supplied discussion records maintainer agreement with startup scripts and IPython-style configuration on 2024-06-17, followed by an explicit decision on 2024-09-08 to keep the request open because it exceeded the voting threshold. It now has 29 upvotes and community ask; lack-of-traction closure does not apply.
- **Existing settings do not cover initialization:** package.json declares python.startNativeREPL and the python.REPL.enableREPLSmartSend, python.REPL.sendToNativeREPL, and python.REPL.provideVariables settings, but no native-REPL startup script, environment override, or custom working-directory setting. python.envFile and python.terminal.launchArgs exist, but the native launch path does not consume them.
- **Current native launch path:** src/client/repl/replCommands.ts registerStartNativeReplCommand selects the active interpreter. src/client/repl/nativeRepl.ts NativeRepl.create and setReplDirectory choose a workspace directory, prompting for a workspace in multi-root setups. src/client/repl/pythonServer.ts createPythonServer spawns the selected interpreter with python_files/python_server.py and only a cwd option; it supplies no configured environment or startup hook.
- **Python-side initialization remains absent:** python_files/python_server.py initializes USER_GLOBALS with its input handler and enters the JSON-RPC request loop. It does not load a project startup script or initialize Django before user execution. Manual initialization cells are possible, but do not satisfy automatic setup for every session.
