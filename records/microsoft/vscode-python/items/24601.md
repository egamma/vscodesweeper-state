# Issue #24601 — DocTest unittest discovery adapter

[https://github.com/microsoft/vscode-python/issues/24601](https://github.com/microsoft/vscode-python/issues/24601)

## Summary

Native unittest doctest discovery still lacks correct source locations and grouping. Keep this request open in the testing area; the maintainer welcomed support, but the discussion leaves the presentation of doctests outside the discovery root unresolved.

## Change summary

Display doctests collected through unittest load_tests with accurate source-file grouping, navigation, and editor locations.

## Best solution

Support standard DocTestSuite cases in the unittest adapter without requiring users to rewrite test IDs, while preserving ordinary unittest discovery and execution. Settle how doctests outside the discovery root or without source metadata appear before implementing the discovery mapping.

- **Behavior:**

  > Doctests collected through unittest load_tests should appear without requiring patched names, and known source locations should navigate to the actual file and corresponding doctest location. Module, class, function, and method doctests must not acquire fictitious filenames from their qualified names. Acceptance checks should include src-layout projects and the agreed presentation for sources outside the discovery root or with unavailable location metadata. Ordinary unittest discovery, execution, and result reporting must retain their behavior.
- **Trace:**

  > python_files/unittestadapter/pvsc_utils.py::build_test_tree assumes test IDs end in filename.class.method, skips short DocTestCase IDs, and uses get_source_line on the case method. Current tests explicitly cover unsupported short IDs and a patched-name workaround, rather than native doctest source mapping. src/client/testing/testController/common/utils.ts::populateTestTree consumes path and lineno for TestItem URIs and ranges and uses runID for execution mappings; preserve that discovery-to-execution contract. The maintainer endorsed support at https://github.com/microsoft/vscode-python/issues/24601#issuecomment-2546481566. The unanswered follow-up at https://github.com/microsoft/vscode-python/issues/24601#issuecomment-2573180020 establishes the remaining uncertainty around tree placement outside the discovery root and missing source metadata. - **Open decisions:**
  - How should doctests whose source is outside the unittest discovery root, including outside the workspace, be grouped in Test Explorer while ordinary unittest tests retain their existing organization?
  - When a doctest has no known source filename or line, should it remain visible without navigation, and what grouping should identify that unavailable source?

## Evidence

- **Current capability gap:** python_files/unittestadapter/pvsc_utils.py::build_test_tree skips DocTestCase instances whose IDs have fewer than three components. Longer IDs still undergo the ordinary filename/class/function split, with file paths synthesized from the discovery directory and line numbers obtained from the case method rather than the underlying doctest source. This does not cover the reported module/class doctests or src-layout navigation.
- **Existing surfaces checked:** package.json exposes python.testing.unittestEnabled, python.testing.unittestArgs, and python.testing.cwd, but no doctest source-mapping setting. src/client/testing/testController/controller.ts selects the unittest provider when enabled. The separate pytest doctest path in python_files/vscode_pytest/__init__.py::build_test_tree does not supply the requested unittest integration.
- **Existing tests confirm limited support:** python_files/tests/unittestadapter/test_utils.py::test_doctest_standard_blocked expects an unsupported-doctest error; test_doctest_patched_works only checks that rewritten IDs produce test nodes without doctest errors.
