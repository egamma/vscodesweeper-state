# Issue #21864 — Modify `Python: Create Terminal` to create an activated terminal even when automatic terminal activation is turned off 

[https://github.com/microsoft/vscode-python/issues/21864](https://github.com/microsoft/vscode-python/issues/21864)

## Summary

Keep this accepted request open: explicit Python terminal creation still follows the automatic-activation setting in both the legacy and Python Environments paths. The environment-extension handoff needs a proposal, not a scope or staleness close.

## Change summary

Make Python: Create Terminal activate the selected environment even when automatic activation of ordinary terminals is disabled.

## Best solution

Provide an explicitly activated Python terminal without changing activation of ordinary terminals. Coordinate the command integration here with terminal creation in microsoft/vscode-python-environments; a maintainer can transfer this request there if that is the preferred implementation home.

## Plan brief

- **Likely files:** `src/client/providers/terminalProvider.ts`, `src/client/common/terminal/service.ts`, `src/client/common/terminal/activator/index.ts`, `src/client/envExt/api.legacy.ts`, `src/test/providers/terminal.unit.test.ts`
- **Validation:** In a workspace with a selected venv, disable automatic activation and create an ordinary terminal, then invoke python.createTerminal. Check that the ordinary terminal remains unactivated and the explicitly created Python terminal resolves python to the selected venv. Repeat with Python Environments enabled and python-envs.terminal.autoActivationType set to off, and cover whichever legacy mode the proposal retains.
- **Behavior:**

  > Users working in mixed-language projects need ordinary terminals without automatic Python activation while still being able to request an activated terminal explicitly. Python: Create Terminal should activate the selected environment despite automatic activation being disabled. Acceptance checks must distinguish ordinary terminal creation from explicit Python terminal creation and verify the selected interpreter in the resulting shell. Enabling automatic activation must retain its existing behavior.
- **Trace:**

  > TerminalProvider.onCreateTerminal in src/client/providers/terminalProvider.ts delegates to python-envs.createTerminal when useEnvExtension() is true and then continues through TerminalService. The legacy TerminalService.ensureTerminal path in src/client/common/terminal/service.ts reaches TerminalActivator.activateEnvironmentInTerminalImpl, whose setting gate suppresses activation when python.terminal.activateEnvironment is false. The environment-enabled service path calls ensureTerminalLegacy in src/client/envExt/api.legacy.ts, which calls the sibling API's createTerminal. In the sibling repository, src/features/envCommands.ts:createTerminalCommand also uses TerminalManagerImpl.create; src/features/terminal/terminalManager.ts leaves activation off under ACT_TYPE_OFF. These source paths establish the missing distinction without executing shell behavior. Preserve ordinary-terminal activation preferences and keep the PowerShell PATH defect discussed at https://github.com/microsoft/vscode-python/issues/22047 outside this request. The maintainer's transition comment at https://github.com/microsoft/vscode-python/issues/21864 leaves the supported legacy-versus-sibling scope unresolved.
- **Open decisions:**
  - Should explicitly activated Python terminals be supported in both legacy mode and Python Environments mode, or only with Python Environments enabled?
