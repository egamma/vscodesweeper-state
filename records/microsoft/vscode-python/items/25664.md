# Issue #25664 — Django test coverage

[https://github.com/microsoft/vscode-python/issues/25664](https://github.com/microsoft/vscode-python/issues/25664)

## Summary

Keep open: current main supports in-process Django coverage, but that does not establish coverage for the reporter's --parallel configuration or provide the requested launcher setting. The request has 8 upvotes, and the related parallel-coverage report is newer, so neither the feedback process nor duplicate consolidation justifies closing this re-reviewed item.

## Change summary

Support collecting Django test coverage with the configured test arguments, through built-in integration or a configurable coverage launcher.

## Best solution

Make Django coverage reliable for the reported parallel test workflow while preserving Test Explorer results and coverage reporting. First establish the remaining multiprocessing gap, then decide whether built-in support suffices or a public launcher setting is warranted.

- **Likely files:** `python_files/unittestadapter/execution.py`, `python_files/unittestadapter/django_handler.py`, `python_files/unittestadapter/django_test_runner.py`, `python_files/tests/unittestadapter/test_coverage.py`, `src/client/testing/testController/unittest/testExecutionAdapter.ts`, `package.json`
- **Validation:** Extend the Django coverage fixture to contain multiple test classes that exercise distinct application lines, and run it with --parallel 2 plus the reporter's settings and keepdb arguments. Compare the returned coverage payload against the serial baseline and independently collected multiprocessing-aware coverage; require worker-executed lines to appear and test results to remain correct. Retain test_basic_django_coverage for both manage.py variants.
- **Behavior:**

  > Django tests run successfully through Test Explorer, but the reporter cannot collect useful coverage with their settings, parallel execution, and keepdb arguments. A coverage run should include application lines executed by the selected tests, including worker processes when parallel testing is enabled. Serial coverage, selected-test execution, settings arguments, and test result reporting must retain their existing behavior. The requested launcher setting is a suggested means to this outcome, not proof that replacing python with coverage run alone handles multiprocessing.
- **Trace:**

  > UnittestTestExecutionAdapter.runTestsNew in src/client/testing/testController/unittest/testExecutionAdapter.ts sets COVERAGE_ENABLED for coverage runs and launches the Python execution helper. python_files/unittestadapter/execution.py starts a coverage collector, calls django_execution_runner, and reports the collector's measured data after saving and loading it. django_handler.py executes manage.py in-process, while CustomExecutionTestRunner in django_test_runner.py inherits Django's DiscoverRunner and supplies the extension's result class. The inspected adapter has no explicit multiprocessing coverage initialization or data combination, and test_basic_django_coverage exercises only non-parallel runs; current parallel behavior must therefore be established with multiple test classes and worker-executed lines. https://github.com/microsoft/vscode-python/pull/24927 delivered the in-process serial capability before this report, while https://github.com/microsoft/vscode-python/issues/25597 supplies a newer parallel-coverage report. Preserve discovery, debugging, selected-test identifiers, and the existing result/coverage IPC contracts; arbitrary alternative unittest runners are outside the reported acceptance case.
- **Open decisions:**
  - Should the supported product surface be built-in Django coverage, including parallel workers, or should users also receive a public setting for choosing a unittest coverage launcher?
