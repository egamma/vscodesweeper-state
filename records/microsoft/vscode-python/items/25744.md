# Issue #25744 — Venv activation command leaks into stdin when running tasks on Windows

[https://github.com/microsoft/vscode-python/issues/25744](https://github.com/microsoft/vscode-python/issues/25744)

## Summary

Keep open: the reporter confirmed that migrating to shellStartup eliminates the leak, but this does not establish a fix for legacy command-based activation. Current main delegates activation more broadly to Python Environments, while retaining the sendText path when that extension is absent or explicitly disabled.

## Change summary

Prevent environment activation commands from becoming stdin input to programs launched in fresh VS Code task terminals.

## Best solution

Ensure task startup cannot deliver activation text to the running program while preserving ordinary terminal activation. Use the reporter-confirmed shellStartup configuration as the available mitigation, and establish current behavior under both legacy activation and Python Environments before deciding where the remaining fix belongs.

## Plan brief

- **Likely files:** `src/client/terminals/activation.ts`, `src/client/common/terminal/activator/index.ts`, `src/client/common/terminal/activator/base.ts`, `src/client/envExt/api.internal.ts`, `src/test/terminals/activation.unit.test.ts`
- **Validation:** On Windows PowerShell, run the supplied debug_stdin_leak.py task repeatedly with presentation.panel=new and a selected uv-created venv. Compare legacy activation with Python Environments shellStartup; each task must report no leaked activation characters, an input() prompt must wait for user input, and an ordinary new interactive terminal must retain its configured activation behavior.
- **Behavior:**

  > A program launched by a VS Code task must not receive environment activation commands as stdin. The reported failure occurs in a fresh Windows PowerShell task terminal using a selected venv interpreter; Linux contamination was also reported. Acceptance requires an empty activation-related stdin buffer and interactive prompts that wait for actual user input, without breaking ordinary terminal activation.
- **Trace:**

  > TerminalAutoActivation in src/client/terminals/activation.ts handles terminal-open events and invokes TerminalActivator. The legacy BaseTerminalActivator in src/client/common/terminal/activator/base.ts asynchronously obtains commands and delivers them through terminal.sendText, which can reach the task program instead of the shell. Current shouldEnvExtHandleActivation in src/client/envExt/api.internal.ts suppresses that path when Python Environments owns activation, but preserves it when the sibling extension is absent or explicitly disabled. The reporter confirmed shellStartup as a mitigation at https://github.com/microsoft/vscode-python/issues/25744. The unresolved technical boundary is actual task-startup ordering and how to establish a reliable regression check; existing activation unit tests mock terminal events rather than task execution. Preserve ordinary interactive-terminal activation and explicit ownership settings; do not treat reconnect-related activation or tmux interruption as already proven to be this same defect.

## Evidence

- **Confirmed failure and mitigation:** https://github.com/microsoft/vscode-python/issues/25744 supplies a Windows PowerShell task, a Python stdin-buffer probe, and captured Activate.ps1 input. The February 5 comment corroborates contamination on Linux; the March 13 maintainer comment identifies legacy sendText activation as the cause. On March 24, the reporter confirms that python.useEnvironmentsExtension=true with python-envs.terminal.autoActivationType=shellStartup eliminates the leak.
- **Legacy activation remains in current source:** src/client/terminals/activation.ts: TerminalAutoActivation.register subscribes to onDidOpenTerminal; activateTerminal delegates to the activator after exclusion and ownership checks, without an explicit task-startup synchronization check. src/client/common/terminal/activator/base.ts: BaseTerminalActivator.activateEnvironmentInTerminal awaits activation-command discovery and then calls terminal.sendText(command); its 500 ms wait occurs after sending the command.
- **Current ownership guard is conditional:** src/client/envExt/api.internal.ts: shouldEnvExtHandleActivation returns true when Python Environments is installed and not explicitly disabled, and both automatic activation and TerminalActivator honor this guard. It returns false when the extension is absent or python.useEnvironmentsExtension is explicitly false, leaving legacy command activation available. This guard does not establish task-stdin safety for those configurations.
- **Canonical search:** Open-issue searches for stdin and activation/tasks did not establish a canonical owning this task-specific failure. https://github.com/microsoft/vscode-python/issues/25291 concerns missing activation and documents migration; https://github.com/microsoft/vscode-python/issues/23893 concerns activation into existing terminals after reconnect. https://github.com/microsoft/vscode-python/issues/25885 includes REPL interruption and activation input, but does not establish the same task-startup defect.
- **Closed related reports are not duplicate targets:** https://github.com/microsoft/vscode-python/issues/9374 describes the same fresh-task stdin symptom but was closed in favor of an environment-variable activation initiative, not a verified fix for this report. https://github.com/microsoft/vscode-python-environments/issues/1570 is closed and concerns interruption of tmux workloads; it cannot serve as an open canonical.
- **Validation boundary:** src/test/terminals/activation.unit.test.ts tests ordinary activation, hidden-terminal exclusion, and delegation to Python Environments using mocked terminal events. It does not exercise actual task-process startup or stdin contamination. No execution was performed in the read-only checkout, and no concrete behavior-fixing commit was established.
