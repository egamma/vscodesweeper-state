# Issue #14518 — vscode-variables only expanded in some environment vars from .env file 

[https://github.com/microsoft/vscode-python/issues/14518](https://github.com/microsoft/vscode-python/issues/14518)

## Summary

Keep this accepted, partner-requested enhancement open: current source resolves the python.envFile filename, but does not provide workspaceFolder substitution throughout its contents. The related issues do not establish a valid canonical duplicate or a completed implementation.

## Change summary

Support documented VS Code variable expansion, especially ${workspaceFolder}, consistently in arbitrary environment-variable values loaded from .env files.

## Best solution

Define and document workspace-aware .env substitution shared by Python consumers and sibling extensions, so checked-in configuration can contain workspace-relative absolute paths without depending on process cwd. Coordinate that contract with the environment-variable standardization work and the Python Environments extension rather than implicitly changing ordinary relative-path resolution.

## Plan brief

- **Likely files:** `src/client/common/variables/environment.ts`, `src/client/common/variables/environmentVariablesProvider.ts`, `src/client/common/variables/types.ts`, `src/client/debugger/extension/configuration/resolvers/helper.ts`, `src/test/common/variables/envVarsService.unit.test.ts`, `src/test/common/variables/environmentVariablesProvider.unit.test.ts`
- **Validation:** After agreeing the substitution contract, add parser/provider unit cases for FOOBAR1=${workspaceFolder}/foobar1.asdf and PYTHONPATH=${workspaceFolder}/src, retaining existing environment-reference and escaping cases. Verify in two differently located workspace copies that Python and a local Jupyter kernel receive the appropriate absolute paths, including when execution cwd differs from the workspace root.
- **Behavior:**

  > A shared project .env file cannot currently express the actual workspace root consistently in arbitrary environment variables. The requested outcome is documented workspace-aware substitution that supplies the correct workspace-specific absolute value to Python consumers, including local Jupyter kernels. Acceptance should cover both a custom variable and PYTHONPATH across different workspace locations and execution directories. Existing environment-variable references and literal relative paths must retain their agreed behavior.
- **Trace:**

  > EnvironmentVariablesProvider.getEnvFile in src/client/common/variables/environmentVariablesProvider.ts resolves VS Code variables in the configured filename, not the contents. Its async and sync content paths pass process.env to EnvironmentVariablesService; parseEnvFile/substituteEnvVars in src/client/common/variables/environment.ts consult only local and base environment maps, treating an absent workspaceFolder name as empty. DebugEnvironmentVariablesHelper.getEnvironmentVariables in src/client/debugger/extension/configuration/resolvers/helper.ts separately invokes the same parser with launch env values. Existing parser unit tests pin ordinary environment substitution, recursive references, escaping, and invalid syntax. The unresolved boundary is the public substitution contract and its consistency across consumers, not whether literal ./ should always mean the workspace root. Related design work is https://github.com/microsoft/vscode-python/issues/18307; its environment-extension proposal does not establish adoption here. https://github.com/microsoft/vscode-python/issues/20784 explicitly preserves cwd-dependent relative-path semantics while pointing to this enhancement.
- **Open decisions:**
  - Should .env contents support only explicit workspace-folder references, or a broader documented subset of VS Code configuration variables?
  - When a supported workspace token collides with an environment-variable name or no workspace context exists, which value or observable error behavior should the public contract define?
