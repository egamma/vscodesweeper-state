# Issue #25463 — getPythonEnvironmentInfo tool fails for venv created with uv

[https://github.com/microsoft/vscode-python/issues/25463](https://github.com/microsoft/vscode-python/issues/25463)

## Summary

The compatibility path still falls back to Python's pip module when the Environments extension returns an empty package inventory, explaining the failure for an unseeded uv venv. Route this to the environments area; newer API routing does not eliminate the remaining compatibility defect.

## Change summary

Allow getPythonEnvironmentInfo to inspect a uv-created environment without requiring pip inside that environment.

## Best solution

Return accurate environment information for an empty uv venv without treating a successful empty package inventory as a failed query. Preserve the newer Environments tools API route and distinguish unavailable package information from a valid empty inventory.

- **Current failing compatibility path:** src/client/chat/getPythonEnvTool.ts, GetEnvironmentInfoTool.invokePreviousFlow, initializes packages to an empty string and only populates it when api.getPackages(env) returns a nonempty array. A successful [] therefore enters the !packages fallback. src/client/chat/listPackagesTool.ts, listPipPackages, then executes execModule('pip', ['list']), which requires pip inside the selected environment.

Its current implementation first delegates to api.getEnvironment({ resourcePath: target, includePackages: true }) when the private tools API is available, but explicitly retains invokePreviousFlow for compatibility. alwaysUseUv is not read by the local pip fallback, so that setting does not cover this path.

This pins the problematic branch, but mocks a successful fallback rather than a pip-free environment.
