# Issue #253585 — SCM - Filter Commits in Source Control Graph

[https://github.com/microsoft/vscode/issues/253585](https://github.com/microsoft/vscode/issues/253585)

## Summary

Keep open: existing reference selection and text matching do not provide the requested commit-message exclusions. The older async-filtering issue concerns incomplete search results, not the same observable problem, so it is related rather than a verified duplicate.

## Change summary

Allow message-pattern exclusions in the Source Control Graph to hide repetitive merge and automated-update commits.

## Best solution

Provide optional commit-message exclusion filtering that works across paginated history without misleading graph relationships. Plan the matching contract and representation of hidden ancestry; treat prefix removal and remote-only branch exclusion from the comments as separate enhancements.

- **Likely files:** `src/vs/workbench/contrib/scm/browser/scmHistoryViewPane.ts`, `src/vs/workbench/contrib/scm/browser/scmHistory.ts`, `src/vs/workbench/contrib/scm/common/history.ts`, `extensions/git/src/historyProvider.ts`, `src/vs/workbench/contrib/scm/test/browser/scmHistory.test.ts`
- **Validation:** Use a repository containing ordinary commits interleaved with matching merge and dependency-update commits across multiple history pages. Apply two exclusion patterns and verify matching rows disappear, nonmatching commits remain accessible after loading more history, graph relationships follow the agreed hidden-ancestry representation, and clearing the filter restores the history. Add graph-model coverage in src/vs/workbench/contrib/scm/test/browser/scmHistory.test.ts for that representation.
- **Behavior:**

  > Users can exclude commits by message pattern from the Source Control Graph, including repetitive branch merges and automated dependency updates. Multiple exclusions work together and continue to apply when additional history pages are loaded. Nonmatching history remains accessible, clearing the exclusions restores the normal graph, and the filtered graph does not misrepresent ancestry. Prefix shortening and remote-only branch exclusion are not required to satisfy the original request.
- **Trace:**

  > SCMHistoryViewModel.getHistoryItems in src/vs/workbench/contrib/scm/browser/scmHistoryViewPane.ts fetches history using selected references, limit and a skip derived from accumulated history length; it does not pass message filtering. SCMHistoryTreeKeyboardNavigationLabelProvider provides message and author labels for existing tree matching. ISCMHistoryOptions in src/vs/workbench/contrib/scm/common/history.ts already has filterText, but GitHistoryProvider._searchHistoryItems in extensions/git/src/historyProvider.ts performs positive author/message searches rather than the requested exclusions. toISCMHistoryItemViewModelArray in src/vs/workbench/contrib/scm/browser/scmHistory.ts derives swimlanes from parentIds and preceding rows, so filtered ancestry and paging require deliberate treatment. Preserve unfiltered history, reference-selection behavior and Git data; do not change the team's merge workflow. https://github.com/microsoft/vscode/issues/226835 is related async-search work, not a duplicate. The remaining uncertainty is the user-visible matching contract and how omitted commits are represented in graph connections.
- **Open decisions:**
  - Should exclusion patterns use literal substring matching, glob matching or regular expressions, and how should multiple patterns containing commas be expressed?
  - When hidden commits connect visible history, should the graph contract their ancestry into continuous connections or explicitly indicate omitted history?
