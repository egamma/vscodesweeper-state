# Issue #194806 — [folding] Editor expands when a folding provider comes in with delay

[https://github.com/microsoft/vscode/issues/194806](https://github.com/microsoft/vscode/issues/194806)

## Summary

The folding-state loss is a confirmed core editor bug with a precise timing-dependent cause: restored provider ranges are first reconciled against indentation ranges, then cannot recover their collapsed state when the delayed language provider arrives. The Backlog milestone does not block cleanup, but no evidence shows that the defect was fixed or superseded.

## Change summary

Preserve restored folded regions when a delayed language folding provider replaces temporarily computed indentation ranges of a different size.

## Best solution

Update the folding merge lifecycle so the first delayed provider result can retain or reapply the persisted collapsed state when no intervening user folding interaction occurred, while preserving the current behavior for ranges changed during editing.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/folding/browser/foldingRanges.ts`, `src/vs/editor/contrib/folding/browser/foldingModel.ts`, `src/vs/editor/contrib/folding/test/browser/foldingRanges.test.ts`
- **Validation:** Add a folding test that restores a collapsed provider range, initially receives an overlapping indentation range with a different end line, then receives the original provider range after delayed registration; assert that the final provider range remains collapsed when no user interaction occurred, while existing edited-range merge tests retain their current expectations.
- **Behavior:**

  > When an editor restores a folded region before its language folding provider is registered, a temporary indentation-based range must not cause that fold to become permanently expanded. If the delayed provider later returns the persisted range and the user has not interacted with folding, the final provider range remains collapsed. Folding updates caused by actual document edits or user folding actions must continue to use their established behavior.
- **Trace:**

  > The issue discussion confirms the sequence: persisted ranges are restored, the absence of a registered language provider selects indentation folding, and sanitizeAndMerge in src/vs/editor/contrib/folding/browser/foldingRanges.ts drops collapsed state when the overlapping range has a different size. When the delayed LSP-backed provider arrives with the original range, that state has already been lost. The maintainer identified either initialization/provider-transition-specific merge semantics or reapplication of initial ranges before user interaction as possible directions in https://github.com/microsoft/vscode/issues/194806#issuecomment-1846812765. Keep the boundary in editor folding state reconciliation; do not require language servers to add VS Code-specific initialization behavior, and do not broadly change merge behavior for ranges updated during editing.
- **Open decisions:**
  - When the first language provider arrives without intervening user interaction, should persisted collapse state follow a matching start line despite an interim size mismatch, or should the complete initial persisted ranges be reapplied as a one-time transition?
  - What event ends the initialization grace semantics: the first provider result, the first folding interaction, or the first document edit?

## Evidence

- **confirmed reproduction:** https://github.com/microsoft/vscode/issues/194806#issuecomment-1833334816 summarizes the reproduced conditions: delayed provider registration plus provider ranges at the same location but with a different size from indentation ranges.
- **core diagnosis:** Maintainer comments trace the behavior to restored ranges being merged first with the indentation provider and identify the changed-size collapse handling in src/vs/editor/contrib/folding/browser/foldingRanges.ts as the relevant core path.
- **proposed core approaches:** https://github.com/microsoft/vscode/issues/194806#issuecomment-1846812765 identifies two viable folding-layer approaches: avoid unloading collapsed state for size changes during initialization/provider transitions, or reapply initial folding regions when the first provider arrives before user interaction.
- **not extension-specific:** The reporter supplied an independent JavaScript occurrence and the maintainer noted that VS Code's own language clients register providers with the same delay, so the issue is not attributable solely to Dart-Code.
- **related report:** https://github.com/Dart-Code/Dart-Code/issues/4769 is the originating downstream symptom, but the discussion here establishes a VS Code folding lifecycle defect rather than an extension-owned cause.
