# Issue #76641 — Update detects code.exe instances from other users with seperate install folders

[https://github.com/microsoft/vscode/issues/76641](https://github.com/microsoft/vscode/issues/76641)

## Summary

Keep open while the linked updater fix is reviewed and integrated. Multiple reporters confirm the multi-user update failure, and microsoft/inno-updater#71 remains open with explicit closing references to this issue.

## Change summary

Allow a per-user Windows installation to update without being blocked by Code.exe processes belonging to another installation.

## Best solution

Review and resolve https://github.com/microsoft/inno-updater/pull/71, then establish that VS Code distributes the corrected updater and that separate users' installations update independently. Preserve detection and actionable errors for processes belonging to the installation actually being updated.

## Evidence

Independent confirmations include https://github.com/microsoft/vscode/issues/76641#issuecomment-831052612 and https://github.com/microsoft/vscode/issues/76641#issuecomment-881149171; the latter describes repeated update failures interrupting close and reopen.
- **Exact failure:** https://github.com/microsoft/vscode/issues/76641#issuecomment-1198784145 records the updater error: 'Failed to open process: Access is denied' while attempting to kill running Code.exe processes.
- **Current integration boundary:** build/win32/code.iss:1857-1860 invokes the external inno_updater.exe during background updates and passes the target installation's executable path. build/gulpfile.vscode.win32.ts:146-149 packages build/win32/inno_updater.exe; process matching is implemented in the separate microsoft/inno-updater repository.
- **Open implementation candidate:** Verified https://github.com/microsoft/inno-updater/pull/71 is OPEN and says 'Fixes microsoft/vscode#76641'. It proposes matching launch name and installation directory before waiting or requesting termination rights, using limited-query process access and cross-bitness-safe executable-path queries. An open fix candidate is not evidence of a completed, distributed fix.
- **Earlier upstream attempt:** Verified https://github.com/microsoft/inno-updater/pull/28 is also OPEN and references this report. Its access-denied workaround is explicitly superseded in the description of https://github.com/microsoft/inno-updater/pull/71, which explains that ignoring permission errors alone can still wait on unrelated installations and hide target-process failures.
- **Canonical search and historical workaround:** An open-issue search for updates involving other users returned no canonical candidate. The older matching report, https://github.com/microsoft/vscode/issues/60625, is CLOSED and therefore cannot be a duplicate target; https://github.com/microsoft/vscode/issues/60625#issuecomment-429245429 recommends disabling background updates, not a fix for independent per-user updates.
- **Workarounds do not satisfy the request:** https://github.com/microsoft/vscode/issues/76641#issuecomment-905133445 changes update.mode, and https://github.com/microsoft/vscode/issues/76641#issuecomment-2497574022 supplies a manual PowerShell update workaround. Neither establishes that the normal background-update path correctly excludes other installations.
