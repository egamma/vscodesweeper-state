## Evidence

- **Reported trigger and workaround:** https://github.com/microsoft/vscode/issues/320680 reports that opening a Next.js .tsx file through a workspace omits Use Workspace Version, while opening that project directly works. The reporter's first comment says an explicit typescript.tsdk path restores selection, but its example uses a single parent workspace root (folders: [{path: '.'}]), unlike the two-root reproduction; this distinction may explain discovery differences but does not establish the original configuration.
- **Current discovery path:** extensions/typescript-language-features/src/tsServer/versionProvider.electron.ts: DiskTypeScriptVersionProvider.loadTypeScriptVersionsFromPath iterates every workspace folder and probes node_modules/typescript/lib/tsserver.js directly beneath it. localNodeModulesVersions filters invalid installations, and localVersions exposes all valid candidates. A genuine Next.js workspace root should therefore be discoverable, whereas a nested project under a single parent root is not searched recursively.
- **Picker and selection boundary:** extensions/typescript-language-features/src/tsServer/versionManager.ts: getLocalPickItems maps every localVersions entry to Use Workspace Version. The manager maintains one currentVersion and defaults to defaultVersion unless workspace selection was stored; finding an owning tsconfig does not itself select a project-specific TypeScript server.
- **Existing configuration:** extensions/typescript-language-features/package.json registers js/ts.tsdk.path and the legacy typescript.tsdk as window-scoped settings. package.nls.json documents explicit workspace SDK selection through TypeScript: Select TypeScript Version. These settings provide the reported workaround, not automatic nested-project discovery or independent per-folder SDK selection.
- **Follow-up does not confirm the defect:** The second comment on https://github.com/microsoft/vscode/issues/320680 concerns source-only checkouts without node_modules and resolving types from elsewhere. Selecting a TypeScript compiler SDK does not supply missing project dependencies, so that comment is not an independent reproduction of the missing installed-SDK entry.
- **Canonical search:** Searches for TypeScript multi-root, monorepo, version-selection, and tsdk issues found no verified canonical owning this missing-entry report. https://github.com/microsoft/vscode/issues/320055 concerns rewriting an already-selectable SDK path; https://github.com/microsoft/vscode/issues/263226 concerns incorrect picker attribution; https://github.com/microsoft/vscode/issues/340169 concerns TypeScript native-preview SDK selection. None establishes the same defect.
