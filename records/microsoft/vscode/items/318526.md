# Issue #318526 — Workspace-level Worktree Support

[https://github.com/microsoft/vscode/issues/318526](https://github.com/microsoft/vscode/issues/318526)

## Summary

Keep open: existing workspace duplication and repository-level worktree commands do not provide a replicated multi-root environment backed by corresponding worktrees. The older related requests cover different workflows, not the full capability requested here.

## Change summary

Create an isolated copy of a multi-root workspace with corresponding worktrees for its repositories and optional preservation of workspace configuration.

## Best solution

Define a workspace-level isolation workflow that retains the workspace's folder mapping and selected configuration while placing its repositories in worktrees. Reuse existing workspace duplication and repository isolation capabilities, coordinating the agent-facing requirements with https://github.com/microsoft/vscode/issues/311148 without treating independent per-repository sessions as equivalent.

- **Behavior:**

  > A developer can create a parallel development context from a multi-root workspace without manually creating and assembling each repository's worktree. The resulting context retains the workspace's repository relationships and uses corresponding isolated worktrees. Acceptance must cover two independent repositories, preserved folder names, and the agreed optional configuration copying. Cancellation and partial creation failures must have an explicitly defined user-visible outcome.
- **Trace:**

  > DuplicateWorkspaceInNewWindowAction in src/vs/workbench/browser/actions/workspaceActions.ts copies workspace settings but reuses the original folder URIs. Commands._createWorktree in extensions/git/src/commands.ts and Repository.createWorktree in extensions/git/src/repository.ts provide repository-level creation; git.worktreeIncludeFiles covers selected ignored files. FolderRepositoryManager.initializeMultiRootFolderRepositories in extensions/copilot/src/extension/chatSessions/vscode-node/folderRepositoryManagerImpl.ts already contains batch isolation logic, but the source search found no caller, so its adoption and suitability remain to be established. Preserve existing single-repository commands and trust behavior; this request does not authorize changing those defaults. https://github.com/microsoft/vscode/issues/311148 supplies related agent-workspace requirements, while https://github.com/microsoft/vscode/issues/293884 concerns location configuration rather than workspace replication. The unresolved boundary is the product contract for copied configuration, repository starting state, and partial failures.
- **Open decisions:**
  - Which workspace settings and environment files are preserved by default, and which require explicit opt-in?
  - Should each repository's worktree start from its current HEAD, or should the workflow allow per-repository base branches and transfer of uncommitted changes?
  - If any repository cannot be isolated, should creation fail as a whole or offer an explicitly marked partially isolated workspace?
  - Should the initial capability produce a reusable .code-workspace file, an agent-session-only context, or both?
