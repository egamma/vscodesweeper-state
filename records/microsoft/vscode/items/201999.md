[https://github.com/microsoft/vscode/issues/201999](https://github.com/microsoft/vscode/issues/201999)

## Summary

The reported ARIA role mismatch remains in current source. The related merged PR fixes active-descendant ordering, explicitly not the listbox role; keep this issue open to resolve the shared-list semantics discussed by maintainers.

## Change summary

Expose the selectable Extensions list with appropriate listbox and option semantics rather than a list using aria-activedescendant.

- **Behavior:**

  > The Extensions sidebar currently exposes a selectable, keyboard-navigated widget as a list while publishing aria-activedescendant. It should expose valid listbox and option semantics so assistive technology recognizes selectable-container navigation. Acceptance includes correct container and row roles, selection state, and active-descendant targets before and after scrolling. Existing extension opening, keyboard navigation, and virtualized loading must remain unchanged.
- **Trace:**

  > ExtensionsList in src/vs/workbench/contrib/extensions/browser/extensionsViewer.ts constructs WorkbenchPagedList with accessible labels but no role overrides. PagedAccessibilityProvider in src/vs/base/browser/ui/list/listPaging.ts forwards labels only, so simply adding role methods to the caller's provider would not reach the underlying List. List in src/vs/base/browser/ui/list/listWidget.ts defaults the container to 'list' and makes SelectionTrait behavior depend on whether the role is 'listbox'; ListView in src/vs/base/browser/ui/list/listView.ts separately defaults rows to 'listitem'. The defect is confirmed from these current-source paths, not from a runtime Orca session. https://github.com/microsoft/vscode/pull/330945 addresses rendered active-descendant targets and explicitly excludes this role change; preserve that behavior. The remaining uncertainty is the shared semantic scope raised in https://github.com/microsoft/vscode/issues/201999, not the expected Extensions behavior.
- **Open decisions:**
  - Should selectable listbox semantics become the default for shared List consumers, or should this work retain existing defaults and opt in the Extensions list and other individually assessed selectable lists?
