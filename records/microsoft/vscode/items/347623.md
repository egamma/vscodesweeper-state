## Plan brief

- **Likely files:** `src/vs/workbench/services/files/electron-browser/watcherClient.ts`, `src/vs/workbench/services/files/electron-browser/diskFileSystemProvider.ts`, `src/vs/platform/files/node/watcher/parcel/parcelWatcher.ts`
- **Validation:** On Windows with extensions disabled, publish the affected project, close the publishing terminal, and rename the output directory without reloading. Confirm the rename succeeds and filesystem change notifications continue working; first reproduce the original failure and identify the owning utility process.
- **Behavior:**

  > After publishing a .NET/Avalonia application finishes and its terminal closes, the output directory must remain renamable without reloading VS Code. The reported failure persists on 1.146.0 with extensions disabled, and reload releases the lock. Acceptance requires a Windows reproduction followed by a successful rename without reload, with normal filesystem notifications preserved.
- **Trace:**

  > UniversalWatcherClient in src/vs/workbench/services/files/electron-browser/watcherClient.ts creates a fileWatcher utility worker whose lifetime ends on window reload. DiskFileSystemProvider routes watch requests to that worker, and ParcelWatcher.startWatching in src/vs/platform/files/node/watcher/parcel/parcelWatcher.ts subscribes through the Windows backend with an unsubscribe callback on stop. These facts explain a plausible lifetime relationship, not a confirmed root cause: the reported utility-process arguments do not identify its service or the handle acquisition. Establish that attribution before selecting an implementation boundary; do not assume normal workspace watching should stop when publishing ends. https://github.com/microsoft/vscode/issues/334673 is a diagnostic lead involving an extension-created nested watcher, not a verified duplicate of this extensions-disabled report.

## Evidence

- **Reporter reproduction:** https://github.com/microsoft/vscode/issues/347623 supplies publish, terminal-close, failed-rename, and successful-after-reload steps, plus a Code.exe Node utility-process handle targeting the publish directory. The reporter confirms persistence on 1.146.0 and with extensions disabled.
- **Current process boundary:** src/vs/workbench/services/files/electron-browser/watcherClient.ts creates the fileWatcher utility worker and documents its termination on window reload. diskFileSystemProvider.ts directs all watch requests to the universal watcher process. This matches the reported process lifetime but does not establish causation.
- **Watcher lifecycle:** src/vs/platform/files/node/watcher/parcel/parcelWatcher.ts selects the Windows backend and subscribes in startWatching; its stop callback awaits unsubscribe. Source inspection does not establish which request, if any, watches the publish directory or why its handle would block renaming.
- **Related issue, not verified duplicate:** https://github.com/microsoft/vscode/issues/334673 reports Windows parent-directory rename failures caused by an extension-created RelativePattern watcher. Its reproduction explicitly requires extensions, unlike this report; the evidence does not establish that it owns the same remaining defect.
