# Issue #277852 — Increase visual hierarchy of agent selection

[https://github.com/microsoft/vscode/issues/277852](https://github.com/microsoft/vscode/issues/277852)

## Summary

A real gap remains: current main gives modes distinct icons but renders the selected mode with the same neutral foreground, so it does not provide the requested visual hierarchy. This team-authored request should remain open; neither older related issue reports the same observable symptom required for a duplicate close on re-review.

## Change summary

Make the selected chat mode visually distinct so users are less likely to send prompts using the wrong agent or mode.

## Best solution

Define an accessible, theme-aware semantic treatment for the selected mode in the shared chat mode picker, preserving clear differentiation in compact, light, dark, and high-contrast presentations.

- **Reason:** Making the active interaction mode easier to recognize improves clarity and error prevention in a central AI-assisted workflow.

- **Behavior:**

  > The currently selected chat mode should be immediately distinguishable, reducing accidental submissions to the wrong mode. Agent, non-default built-in modes, and custom agents must remain recognizable in both labeled and compact icon-only layouts. The treatment must remain legible in light, dark, and high-contrast themes and must not rely on color as the only mode identifier. Model, tools, and send controls should retain their existing visual priority.
- **Trace:**

  > ChatMode definitions in src/vs/workbench/contrib/chat/common/chatModes.ts already provide distinct icons for the primary built-in modes. ModePickerActionItem in src/vs/workbench/contrib/chat/browser/widget/input/modePickerActionItem.ts renders the selected icon and label but exposes no mode-specific presentation beyond `chat-mode-picker-item`; src/vs/workbench/contrib/chat/browser/widget/media/chat.css consequently gives every picker the neutral icon foreground. The picker participates in shared responsive and compact layouts, so the trace must enumerate its chat view/editor and other host presentations before settling scope. Keep the boundary to selected-mode identification: do not change model selection, permission state, responsive ordering, or submission behavior. https://github.com/microsoft/vscode/issues/272502 owns broader responsive layout work, while https://github.com/microsoft/vscode/issues/277547 owns agent icon work; neither absorbs this remaining hierarchy request.
- **Open decisions:**
  - Should the semantic selected-mode treatment apply everywhere the shared mode picker is hosted, including session and automation surfaces, or only to the original chat prompt input?

## Evidence

- **current source:** src/vs/workbench/contrib/chat/browser/widget/input/modePickerActionItem.ts renders the current mode's icon and label and adds only the generic `chat-mode-picker-item` class; it does not expose a mode-specific visual state.
- **neutral presentation:** src/vs/workbench/contrib/chat/browser/widget/media/chat.css applies `var(--vscode-icon-foreground)` uniformly to chat input picker controls, including the mode picker, so Agent, built-in non-default modes, and custom agents have no requested foreground hierarchy.
- **partial existing capability:** src/vs/workbench/contrib/chat/common/chatModes.ts assigns distinct icons to Agent, Ask, and Edit, while ModePickerActionItem supplies additional built-in fallbacks; icons improve recognition but do not implement the requested mode-dependent foreground treatment.
