# Issue #330815 — runSubagent still allows empty agentName and bypasses custom agent allow-list (related to #306266)

[https://github.com/microsoft/vscode/issues/330815](https://github.com/microsoft/vscode/issues/330815)

## Summary

Traced this on current main and the gap is real: `runSubagentTool.ts` never validates the resolved agent against the invoking custom agent's `agents:` allow-list, either for an empty/omitted `agentName` (which just falls back to the current agent's own `modeInstructions`) or for an explicit name (`getSubAgentByName` only checks the agent exists and is enabled, not that it's permitted). The earlier fixes for #306266/#306871 addressed a different problem (schema requiring `agentName`, adding the General Purpose agent) and didn't add this enforcement, so this is a genuine, still-open gap rather than a regression of something fixed.

## Change summary

A custom agent's `agents:` allow-list (which subagents it may invoke) is not enforced at runSubagent invocation time, letting an agent that omits `agentName` self-invoke, or invoke any enabled custom agent by name, regardless of its own allow-list.

## Best solution

In src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts, thread the invoking agent's permitted subagent list (currently discarded — `allowedSubagents: undefined` is hardcoded at the `modeInstructions` construction around line 208, and nothing reads `currentModeInstructions?.allowedSubagents` before resolving/self-falling-back) through to both the explicit-name path (`getSubAgentByName`) and the empty/omitted-name self-fallback path, and reject/error when the resolved agent isn't in that list. This needs a maintainer to define exact allow-list semantics (e.g. is self-invocation ever implicitly allowed?), so it's a design/enforcement change, not a one-line guard.

## Evidence

- **no allow-list check on invoke:** src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts:422-425 `getSubAgentByName()` only does `agents.find(agent => agent.name === name && agent.enabled)` — no check against the calling agent's `agents:` config.
- **empty agentName self-fallback unchecked:** Same file, lines 216-217: when `subAgentName` is falsy, `modeInstructions = currentModeInstructions` (the current agent's own instructions) with no allow-list validation at all — matches the reporter's observed `CustomAgent -> CustomAgent` self-invocation.
- **allowedSubagents dropped, never enforced:** Line 208 hardcodes `allowedSubagents: undefined` when building the invoked subagent's modeInstructions; a repo-wide search shows `.allowedSubagents` is only ever read in src/vs/workbench/api/common/extHostTypeConverters.ts (API surface) — nowhere is it used to gate a runSubagent call.
- **only a prompt-level hint, not enforcement:** src/vs/workbench/contrib/chat/common/promptSyntax/computeAutomaticInstructions.ts:513-521 filters which agents are *listed* to the model in the system prompt by `_enabledSubagents`, but that's advisory text for the model, not a runtime check when the tool actually executes.
- **prior fixes addressed a different issue:** https://github.com/microsoft/vscode/issues/306266 and the fixing PR https://github.com/microsoft/vscode/pull/306871 added a 'General Purpose' agent and made agentName required only for that experimental mode — no allow-list enforcement was added.
