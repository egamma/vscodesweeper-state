# Issue #328700 — Extension host crashes on startup in 1.130 and 1.131; createProxyAuthorizationLookup named export not found in @vscode/proxy-agent (works fine on 1.129)

[https://github.com/microsoft/vscode/issues/328700](https://github.com/microsoft/vscode/issues/328700)

## Summary

The crash mechanism is now confirmed: a stale loose copy of `@vscode/proxy-agent` can shadow the version in `node_modules.asar`, and current main still accepts that resolution. This should remain open as the upstream loader-precedence bug rather than staying in the info-needed lane.

## Change summary

Prevent stale packages under the application-level `node_modules` directory from shadowing newer dependencies shipped in `node_modules.asar` and crashing the extension host.

## Best solution

Define and enforce packaged-module precedence so the application's archive is authoritative when it contains the requested package, while preserving built-in extensions' closer bundled dependencies and packages intentionally shipped only as loose files.

## Plan brief

- **Likely files:** `src/bootstrap-esm.ts`
- **Validation:** Exercise a packaged application layout containing `@vscode/proxy-agent` in both `node_modules.asar` and a stale application-level `node_modules`; with `VSCODE_ASAR_TRACE` enabled, resolution must select the archive copy and the extension host must start. Also verify that a built-in extension's own bundled dependency still wins and that packages present only in the loose application directory still resolve.
- **Behavior:**

  > A packaged VS Code installation must not crash when an obsolete package remains in the application-level `node_modules` directory after an update or an overlaid archive extraction. When the current application ships that package in `node_modules.asar`, extension-host startup must use the shipped version. Built-in extensions must retain normal precedence for dependencies they bundle themselves, and packages intentionally shipped only as loose files must continue to resolve.
- **Trace:**

  > `enableASARSupport` in `src/bootstrap-esm.ts` runs default resolution before consulting `node_modules.asar` and accepts any result under the application resources path. That includes `${appRoot}/node_modules`, so an older loose `@vscode/proxy-agent` shadows the current archived package; the named import introduced by https://github.com/microsoft/vscode/commit/ff13883751393d10a253407cdeba4c48ebecfd04 then fails before extension activation. The same path was independently confirmed with `VSCODE_ASAR_TRACE` in https://github.com/posit-dev/positron/issues/16012 and analyzed further in https://github.com/posit-dev/positron/issues/16017. Keep the boundary to packaged ESM resolution: do not change development-mode resolution, extension-local dependency precedence, or proxy behavior itself.
- **Open decisions:**
  - When the same package exists in both the application-level loose `node_modules` directory and `node_modules.asar`, should the archive always be authoritative, or should loose precedence remain available through a narrower packaged-layout rule?

## Evidence

- **current source path:** `src/bootstrap-esm.ts` first performs default ESM resolution and accepts any result whose path starts with the application resources path (`defaultResult`, around lines 151-158). Consequently, a stale `${appRoot}/node_modules/@vscode/proxy-agent` is accepted before the loader consults `node_modules.asar`.
- **triggering change:** https://github.com/microsoft/vscode/commit/ff13883751393d10a253407cdeba4c48ebecfd04 added the `createProxyAuthorizationLookup` import and updated `@vscode/proxy-agent` from 0.43.0 to 0.44.0, making an older shadowing package fail during extension-host startup.
- **independent confirmation:** https://github.com/posit-dev/positron/issues/16012 records the identical crash, confirms that resolution selected a stale `@vscode/proxy-agent` 0.42.0 under `resources/app/node_modules`, and confirms that removing the stale installation state stopped the extension-host crash.
- **related root-cause investigation:** https://github.com/posit-dev/positron/issues/16017 traces the same loader-precedence mechanism and remains open for Positron's Windows update cleanup. It was created after this issue and therefore is not an older canonical duplicate; this VS Code issue remains the appropriate upstream report for the loader behavior.
- **multiple current reports:** The original Ubuntu tarball report and a separate Gentoo tarball report reproduce with extensions disabled, while the related Windows report confirms the same observable crash and resolution path.
