# Issue #138986 — Support opacity in ThemableDecorationAttachmentRenderOptions

[https://github.com/microsoft/vscode/issues/138986](https://github.com/microsoft/vscode/issues/138986)

## Summary

Keep this accepted feature request open: the public attachment API still lacks opacity, and existing global fading controls do not preserve readable attachments while leaving unused code faded. The request has 45 upvotes and a concrete voice-coding use case; a maintainer should settle the attachment-fading contract before implementation.

## Change summary

Allow before/after decoration graphics to remain fully visible when the decorated code is faded as unused.

## Best solution

Provide a supported editor-decoration contract that preserves the readability of extension-provided attachments independently of unused-code fading, without requiring users to disable fading globally. Address the wrapper-opacity interaction as well as any API addition, since setting opacity on a child cannot undo its parent's transparency.

- **Behavior:**

  > Before/after graphics attached to unused code become faded, making Cursorless color annotations difficult to distinguish. The requested outcome is a supported way to keep these attachments fully visible while retaining unused-code fading on the source text. Acceptance must cover both before and after attachments on unused code and preserve ordinary text-decoration behavior. Existing global fading settings are not equivalent to this selective behavior.
- **Trace:**

  > ThemableDecorationAttachmentRenderOptions in src/vscode-dts/vscode.d.ts omits opacity, although getCSSTextForModelDecorationContentClassName in src/vs/editor/browser/services/abstractCodeEditorService.ts already collects that property internally. The discussion identifies parent-span opacity as the underlying obstacle: opacity on a pseudo-element cannot restore opacity lost through its parent. LineDecorationsNormalizer in src/vs/editor/common/viewLayout/lineDecorations.ts combines overlapping classes, and _applyInlineDecorations in src/vs/editor/common/viewLayout/viewLineRenderer.ts transfers them into rendered line parts; codeEditorWidget.ts applies unused-code opacity to the unnecessary-decoration class. These paths were inspected without executing the editor. Preserve unused-code fading, decoration positioning, and unrelated overlapping styles. The remaining uncertainty is the intended public contract and whether independence from diagnostic fading is opt-in or changes the default. https://github.com/microsoft/vscode/issues/170607 supplies a newer concrete example of the same interaction, not a duplicate target for this older request.
- **Open decisions:**
  - Should before/after attachments remain independent of unused-code fading by default, or should extensions explicitly opt into that behavior while existing attachments retain their current appearance?
  - Should the supported public contract expose attachment opacity, provide a dedicated control for independence from diagnostic fading, or intentionally support both?
