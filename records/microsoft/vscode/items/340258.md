# Issue #340258 — Session Sync Silent Error

[https://github.com/microsoft/vscode/issues/340258](https://github.com/microsoft/vscode/issues/340258)

## Summary

Brand-new, well-diagnosed report bundling two session-sync bugs; I confirmed the second one (repository resolution is cached forever even on a failed first attempt) directly in the current source, so this stays open as a real bug with a concrete lead rather than needing more info.

## Change summary

Session Sync silently reports 0 synced sessions with no diagnostics, for two separate reasons: the Copilot harness never uploads (auth token failure in the engine), and the Local harness permanently skips non-GitHub-resolved repos until a window reload.

## Best solution

Fix `_resolveRepository` in remoteSessionExporter.ts so a failed/undefined resolution isn't cached as permanent (only cache a successful repo lookup, or add a bounded retry), and surface the `no_repo`/other disable reasons in the Session Sync status item or output log instead of only telemetry; separately, triage the Rust engine's 'Failed to get authentication token' error against the token being sent to the remote exporter.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/chronicle/vscode-node/remoteSessionExporter.ts`
- **Validation:** A unit/integration test around `_resolveRepository`/`_initializeSession` asserting that a session created after a failed first resolution (e.g. `activeRepository` initially undefined, then available) is still exported, without requiring a window reload; plus a check that the disable reason surfaces somewhere user-visible (status item or output channel), not only telemetry.
- **Behavior:**

  > A new Copilot/chat session in a repo with a resolvable GitHub remote should sync to the cloud even if the very first repository-resolution attempt in a window failed transiently (e.g. git extension/active repository not yet ready). Repos that genuinely have no GitHub remote should keep being skipped, but the skip reason should be visible to the user (status item tooltip or output log), not only telemetry. Acceptance: sessions in a GitHub-backed repo sync without requiring a window reload, and a skipped session's reason is discoverable without Trace-level GDPR telemetry access.
- **Trace:**

  > `_resolveRepository()` in extensions/copilot/src/extension/chronicle/vscode-node/remoteSessionExporter.ts (~1116-1154) sets `this._repositoryResolved = true` unconditionally on first call, before attempting `this._gitService.activeRepository?.get()`; if that's undefined (observed on the first session in a window) or `getGitHubRepoInfoFromContext` returns nothing, the function returns `undefined` and the negative result is cached for the rest of the window's lifetime — the only way out is reloading the window, which matches the reporter's own (unconfirmed) suspicion. The disable path (lines 896-937) only emits a `chronicle.cloudSync`/'sessionDisabled' telemetry event with `reason: 'no_repo'`; nothing is logged to the extension output channel or shown on the status item. Do not change the GitHub REST resolution itself or the consent/policy gating that follows at line ~940 onward — the boundary is just the caching/retry policy around the resolution result and where the disable reason is surfaced. Separate: the 'Failed to get authentication token' error reported for the Copilot harness comes from the Rust `copilot_runtime` engine, not from this TS source tree, so its root cause is undiagnosed here.
- **Open decisions:**
  - Should a failed repository resolution retry on every subsequent session (simple, but repeats work for genuinely non-GitHub repos every time), or use a bounded retry/backoff before falling back to permanent 'no_repo'?
  - Should the skip reason (no_repo, no_consent, policy_blocked, etc.) be surfaced in the status item tooltip, an output log line, or both?
  - Does 'Failed to get authentication token' in the Rust engine refer to the GitHub OAuth token, the Copilot proxy token, or a separate cloud-sync-specific token/scope — this needs engine-side diagnosis before a fix location can be identified.

## Evidence

- **confirmed caching bug:** extensions/copilot/src/extension/chronicle/vscode-node/remoteSessionExporter.ts, `_resolveRepository()` (~line 1116-1154): `this._repositoryResolved = true;` is set unconditionally right after the cache check (line 1120), before the function even tries `this._gitService.activeRepository?.get()`. If that returns undefined on the very first call (e.g. git extension not yet ready), the function returns `undefined` at line 1125 and `_repositoryResolved` stays `true` for the rest of the window — exactly matching the reporter's report that a window reload fixes it.
- **silent skip confirmed:** Lines 908-937: when `_resolveRepository()` returns undefined, the session is added to `_disabledSessions` with reason 'no_repo' and only a telemetry event (`chronicle.cloudSync` / sessionDisabled) is sent — no log line, notification, or status-item update references the reason, matching the reporter's observation that nothing explains a skip.
- **issue 1 not verifiable in this repo:** The 'failed to get authentication token' error is emitted by the Rust Copilot engine (copilot_runtime, outside this TypeScript source tree); I could not trace its root cause from this checkout, so I'm not citing a fix for it.
