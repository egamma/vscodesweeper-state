# Issue #328759 — Transferring dictation targets does not work

[https://github.com/microsoft/vscode/issues/328759](https://github.com/microsoft/vscode/issues/328759)

## Summary

Team-authored bug filed while verifying #328440, and current main confirms it: switching dictation targets is genuinely broken in two ways, so this stays open as a real, still-reproducible defect.

## Change summary

Starting dictation on a new target (chat/editor/terminal) while a dictation session is active elsewhere should end the old session and start the new one; instead it either does nothing or only stops the old session.

## Best solution

Fix in src/vs/workbench/contrib/chat/browser/actions/chatSpeechToTextActions.ts and src/vs/workbench/contrib/codeEditor/browser/dictation/editorDictation.ts: (1) getDictationShortcutOperation()/runDictationShortcut() should key off whether *this* editor is the active dictation target, not the global isDictating(), so invoking the chat mic while the editor is dictating starts chat instead of just stopping the editor; (2) EditorDictationStartAction's precondition `ContextKeyExpr.or(SpeechToTextInProgress.toNegated(), EDITOR_DICTATION_IN_PROGRESS)` disables 'Start Dictation in Editor' entirely whenever another surface is dictating, which should instead allow switching targets (dictationSession.ts's startDictation already handles canceling the previous surface via service.cancel()).

## Evidence

- **global isDictating() drives stop/start decision:** src/vs/workbench/contrib/chat/browser/actions/chatSpeechToTextActions.ts:getDictationShortcutOperation() returns 'stop' whenever isDictating() is true, regardless of which editor is targeted — so invoking the chat mic while the editor session is active calls stopDictation() (ending the editor session) instead of starting a chat session, matching the reporter's exact repro.
- **command precondition blocks cross-surface start:** src/vs/workbench/contrib/codeEditor/browser/dictation/editorDictation.ts:64 gates EditorDictationStartAction on `ContextKeyExpr.or(SpeechToTextInProgress.toNegated(), EDITOR_DICTATION_IN_PROGRESS)`, so the command is disabled/no-ops from the Command Palette whenever dictation is active on a different surface, matching 'running start dictation commands ... seems to do nothing'.
- **underlying switch support exists:** src/vs/workbench/contrib/chat/browser/speechToText/dictationSession.ts:startDictation() already cancels a prior active session via service.cancel() before starting the new surface, so the plumbing for a clean switch exists — the bug is in the callers' guards/preconditions, not the core session logic.
