## Evidence

- **Verified open canonical:** https://github.com/microsoft/vscode/issues/237975 is OPEN and reports negated character classes unexpectedly matching newlines during regex replacement only in longer documents. Its scope covers the size-dependent replacement semantics reported here, rather than only a particular delimiter or file format.
- **Independent confirmation:** https://github.com/microsoft/vscode/issues/237975#issuecomment-2593527274 confirms reproduction on VS Code 1.96.3; https://github.com/microsoft/vscode/issues/237975#issuecomment-2593567173 identifies a match-count-dependent transition. The later workspace-search comment is a separate, unverified theory and is not the basis for this verdict.
- **Current source trigger:** src/vs/editor/contrib/find/browser/findModel.ts defines MATCHES_LIMIT as 19999. FindModelBoundToEditorModel.replaceAll switches whole-document replacement to _largeReplaceAll when the match count reaches that limit; _largeReplaceAll applies the regex to model.getValue(EndOfLinePreference.LF), rather than the individual ranges used by _regularReplaceAll.
- **Exact failing semantics:** In src/vs/editor/common/model/textModelSearch.ts, isMultilineRegexSource does not classify ^([^\t<]+).*$ as multiline, so ordinary find and replacement match it line by line. _largeReplaceAll instead enables multiline anchors and searches the joined document. The negated class can then capture the newline after the final non-tag line, while .* consumes the following </odstavec> tag; replacing with $1 preserves the captured newline but removes the tag. This explains the reporter's cleared line without relying on file size alone.
- **Evidence to preserve:** https://github.com/microsoft/vscode/issues/62651 supplies paired small and large corpus files, Windows 10 reproduction with extensions disabled, and the specific closing-tag deletion pattern. These are additional examples of the canonical defect, not evidence of a separate root cause.
