# Issue #239997 — consider adding a progressive sound for applying edits

[https://github.com/microsoft/vscode/issues/239997](https://github.com/microsoft/vscode/issues/239997)

## Summary

Keep open: current edit rendering exposes percentage progress, but the existing progress sound repeats without conveying that percentage. This team-authored accessibility request remains a real gap; the older notebook sound request is related, not a verified duplicate.

## Change summary

Provide a progressive audio cue conveying how far chat edits have been applied.

## Best solution

Offer configurable, non-disruptive audio feedback tied to edit-application progress, rather than only indicating that work is ongoing. Agree on the audible progression and its behavior for simultaneous edits before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatMarkdownContentPart.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedFileEntry.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedDocumentEntry.ts`, `src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts`, `src/vs/workbench/contrib/accessibility/browser/accessibilityConfiguration.ts`
- **Validation:** Exercise a chat edit stream with several distinct rewriteRatio values and completion; verify that the agreed audio progression distinguishes increasing progress, stops when application ends, and remains silent when disabled. Repeat with simultaneous file edits and a cancelled stream. Add deterministic coverage for the chosen progress-to-audio mapping and playback lifecycle.
- **Behavior:**

  > Users who cannot see the edit progress indicator should be able to perceive advancement through an optional progressive audio cue. The feedback should convey more than an indeterminate waiting sound and stop when edit application ends. Acceptance should cover distinct progress values, completion, cancellation, disabled audio, and simultaneous file edits without excessive or overlapping feedback.
- **Trace:**

  > The edit pill rendering in src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatMarkdownContentPart.ts observes isStreaming and rewriteRatio and currently maps the ratio only to visual progress. ChatEditingModifiedFileEntry exposes the observable, and ChatEditingModifiedDocumentEntry.acceptAgentEdits updates it during application and marks final edits with a ratio of 1. Existing AccessibilityProgressSignalScheduler and AccessibilitySignalService.playSignalLoop repeat a fixed signal and do not accept determinate progress. Source inspection establishes the missing percentage-dependent audio path, not a runtime reproduction. Preserve existing edit application, visual progress, and unrelated indeterminate progress signals. https://github.com/microsoft/vscode/issues/211288 offers related notebook sound-design context but is not a canonical duplicate. The uncertainty starts with the user-facing audio encoding and how progress from multiple edits should be represented.
- **Open decisions:**
  - How should the sound communicate increasing progress: changing pitch, cadence, milestone cues, or another audible progression?
  - When multiple files are being edited, should the cue represent an individual file's displayed progress or an overall editing operation?
