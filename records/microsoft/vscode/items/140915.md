# Issue #140915 — explorer.sortOrder default doesn't work well for hashes

[https://github.com/microsoft/vscode/issues/140915](https://github.com/microsoft/vscode/issues/140915)

## Summary

A real gap remains on current main: Explorer's default comparator still applies numeric collation to hash-like filenames, while the available Unicode option is case-sensitive and disables natural numeric ordering globally. This issue is the established canonical for that behavior and should remain open in Backlog.

## Change summary

Preserve natural numeric sorting for ordinary filenames while sorting hash-like names lexicographically so they can be scanned visually.

## Best solution

Provide a sorting behavior that keeps natural numeric ordering for ordinary filenames but treats hash-like basenames lexicographically without introducing case-sensitive grouping. The area owner should first decide whether this is automatic hash recognition or an explicit sorting option.

## Plan brief

- **Likely files:** `src/vs/base/common/comparers.ts`, `src/vs/base/test/browser/comparers.test.ts`, `src/vs/workbench/contrib/files/common/files.ts`, `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`
- **Validation:** Add comparator tests covering representative 7–32 character hexadecimal basenames, mixed-case names, and ordinary names such as `a2`/`a10`; run `scripts/test.sh --grep 'Comparers'` and verify hash names are lexical while ordinary names retain the selected natural-number behavior.
- **Behavior:**

  > Explorer should order hash-like filenames lexicographically so users can scan them by prefix, while preserving natural numeric sorting for ordinary filenames such as `a2` and `a10`. Uppercase and lowercase hash characters should not be split into Unicode case groups unless the user explicitly selects such ordering. Acceptance should cover hashes with extensions, mixed-case names, and ordinary numeric filenames.
- **Trace:**

  > Explorer sorting flows through FileSorter in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts, which selects comparators from src/vs/base/common/comparers.ts according to `explorer.sortOrderLexicographicOptions`. The default comparator uses an `Intl.Collator` with `numeric: true` for the complete filename; the Unicode comparator is purely code-point based and therefore changes case and numeric behavior globally. Comparator expectations live in src/vs/base/test/browser/comparers.test.ts, while the public option contract is registered in src/vs/workbench/contrib/files/browser/files.contribution.ts and typed in src/vs/workbench/contrib/files/common/files.ts. Keep extension grouping, folder-before-file behavior, reverse sorting, and existing explicit upper/lower/Unicode semantics outside the change. https://github.com/microsoft/vscode/issues/162725 confirms this issue is the canonical report for the observable numeric-prefix symptom.
- **Open decisions:**
  - Should Explorer recognize hash-like basenames automatically within the default mode, or expose a new explicit case-insensitive nonnumeric lexicographic option?
  - If recognition is automatic, what visible filename pattern qualifies: the complete basename excluding its extension, or any hexadecimal run within a name, and what length bounds should apply?

## Evidence

- **current source:** src/vs/base/common/comparers.ts still constructs the default filename collator with `{ numeric: true }`; `compareFileNamesDefault` uses that collator for the entire filename, so digit runs inside hashes continue to be interpreted numerically.
- **Explorer path:** FileSorter in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts selects `compareFileNamesDefault` for the default lexicographic mode and applies it to `statA.name` and `statB.name`.
- **existing capability is incomplete:** src/vs/workbench/contrib/files/browser/files.contribution.ts offers default, upper, lower, and unicode modes only. Unicode gives lexical ordering but is case-sensitive and globally gives up the desired natural-number behavior, matching the limitation discussed in the issue.
- **canonical status:** https://github.com/microsoft/vscode/issues/162725 reported the same numeric-prefix Explorer ordering and was closed specifically as a duplicate of https://github.com/microsoft/vscode/issues/140915, confirming this issue as the canonical report rather than a satellite.
