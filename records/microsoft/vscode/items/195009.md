- **Same observable serializer failure:** https://github.com/microsoft/vscode/issues/70656#issuecomment-474065974 explicitly reports that deserializeWebviewPanel runs on window reload but not extension reload, leaving an existing webview without a way to reconnect. This matches the observable failure here, not merely a related subsystem or inferred root cause.
- **Maintainer direction:** https://github.com/microsoft/vscode/issues/70656#issuecomment-474095992 acknowledges that serialization on extension reload should probably be supported. The canonical discussion therefore encompasses reconnection, despite its original title focusing on closing webviews.
- **Trust transition reaches the same restart path:** src/vs/workbench/contrib/extensions/browser/extensionEnablementWorkspaceTrustTransitionParticipant.ts calls stopExtensionHosts(), updates enablement, and calls startExtensionHosts() for a local trusted-to-untrusted transition; remote workspaces instead reload the window. This explains why the reporter's local trust change differs from Reload Window.
- **Current source retains the restoration gap:** In src/vs/workbench/api/browser/mainThreadWebviewPanels.ts, $registerSerializer invokes $deserializeWebviewPanel only through a registered webview resolver. In src/vs/workbench/contrib/webviewPanel/browser/webviewWorkbenchService.ts, openWebview creates ordinary WebviewInput instances, whereas openRevivedWebview creates lazily resolved inputs; registerResolver processes only the revival pool, not already-open ordinary panels. Re-registering the serializer after an extension-host restart does not reconnect those panels.
- **Distinct reproduction evidence to preserve:** https://github.com/microsoft/vscode/issues/195009 supplies the additional trigger of switching workspace trust to restricted on Ubuntu 23.04 with VS Code 1.83.0, and contrasts the missing callback with successful deserialization after Reload Window.
