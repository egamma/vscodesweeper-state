# Issue #283214 — Disambiguate filenames in read/edit pills

[https://github.com/microsoft/vscode/issues/283214](https://github.com/microsoft/vscode/issues/283214)

## Summary

The disambiguation gap remains on current main: read and edit pills independently display only the basename, making repeated filenames indistinguishable. Keep this team-authored Backlog polish item open for a coordinated UX design across both renderers.

## Change summary

Show folder context in chat read/edit pills when multiple referenced files have the same filename.

## Best solution

Use a consistent, compact folder-qualified label for colliding filenames across read and edit activity, while preserving basename-only labels for unique files and retaining the existing tooltip, icon, activation, and accessibility behavior.

- **Validation:** Extend the chat thinking-content tests to render read and edit activity for two URIs with the same basename in different folders and assert distinguishable visible and accessible labels; also assert that a unique filename remains basename-only.
- **Behavior:**

  > Within agent activity, read and edit pills for different files sharing a basename must be visibly and accessibly distinguishable by folder context. Files whose basenames are unique in the applicable activity scope should retain the compact basename-only presentation. Existing file icons, tool status text, line suffixes, tooltips, and activation behavior must remain unchanged.
- **Trace:**

  > ReadFileTool.prepareInvocation in extensions/copilot/src/extension/tools/node/readFileTool.tsx emits URI-backed markdown through formatUriForFileWidget; because its link text is empty, InlineAnchorWidget in src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatInlineAnchorWidget.ts chooses getUriBasenameLabel. Edit activity follows a separate path: ChatEditPillElement.setUri in src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatEditPillElement.ts also chooses getUriBasenameLabel, although it already retains the relative path as a tooltip. ChatThinkingContentPart coordinates the surrounding activity rows, but the individual widgets currently receive no collision context. The boundary is presentation and accessibility labeling only: do not change tool execution, resource identity, editor opening, diff behavior, or labels for non-colliding files. The original report is https://github.com/microsoft/vscode-copilot/issues/16842 and was transferred to https://github.com/microsoft/vscode/issues/283214.
- **Open decisions:**
  - Should colliding filenames show the shortest unique parent-path suffix or the full workspace-relative parent path?
  - Should collision detection apply within the current visible activity group, the complete response turn, or the entire conversation?
