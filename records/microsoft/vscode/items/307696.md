# Issue #307696 — User confirmation feedback audio is sometimes not heard in terminal

[https://github.com/microsoft/vscode/issues/307696](https://github.com/microsoft/vscode/issues/307696)

## Summary

The intermittent missing signal remains credible and unresolved on current main: another contributor confirmed it for Ask Question, and the signal service still silently absorbs Chromium user-gesture playback failures. This team-authored bug is accepted in Backlog, so it should remain open for diagnosis rather than receive a judgment close.

## Change summary

Confirmation prompts reached after long-running terminal or Ask Question operations sometimes fail to play the user-action-required accessibility sound.

## Best solution

Determine how confirmation sounds can remain reliable after Chromium's recent-user-interaction window expires, while preserving the existing ARIA status announcement as a fallback and avoiding unrestricted media autoplay.

## Plan brief

- **Likely files:** `src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts`, `src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts`, `src/vs/workbench/contrib/chat/browser/accessibility/chatAccessibilityService.ts`
- **Validation:** Run a confirmation flow after a long-running agent task with a screen reader enabled and no recent renderer interaction; verify that the Chat User Action Required sound is heard and the existing status announcement still occurs. The plan should also establish an automated browser-level check that exercises media playback after user activation expires.
- **Behavior:**

  > When a terminal tool, Ask Question tool, or elicitation reaches a pending confirmation after a long-running operation, the configured Chat User Action Required sound must be heard reliably. Screen-reader users must also continue receiving the existing spoken status announcement. Acceptance must cover a delayed confirmation with no recent renderer interaction, not only an immediate prompt following a click or keypress.
- **Trace:**

  > Tool confirmations call AccessibilitySignal.chatUserActionRequired from languageModelToolsService.ts; question carousels and elicitations use the same signal from chatListRenderer.ts and chatAccessibilityService.ts. AccessibilitySignalService.playSignal emits the status announcement before playSound invokes HTMLAudioElement.play(). playSound catches and suppresses the Chromium error stating that playback requires a user gesture, matching the maintainer's likely diagnosis and explaining why speech can succeed while sound is absent. The uncertainty begins at Chromium's media-activation boundary: the solution must not broadly enable arbitrary autoplay or weaken notebook/webview media restrictions. The related notebook autoplay report https://github.com/microsoft/vscode/issues/178642 is closed and concerns notebook-renderer media, so it is precedent about the platform constraint rather than a canonical duplicate.
- **Open decisions:**
  - Should VS Code guarantee audible confirmation signals after user activation expires even if doing so requires a narrowly scoped media-activation mechanism, or treat the spoken status announcement as the supported fallback when Chromium blocks sound?

## Evidence

- **confirmed symptom:** A contributor confirmed the same intermittent missed audio with the Ask Question tool and observed that long-running tasks make it more likely: https://github.com/microsoft/vscode/issues/307696.
- **current signal path:** src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts calls AccessibilitySignal.chatUserActionRequired when a tool confirmation becomes pending; Ask Question and elicitation paths use the same signal in chatListRenderer.ts and chatAccessibilityService.ts.
