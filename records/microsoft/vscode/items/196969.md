# Issue #196969 — Activation `onCommand` sometimes never returns when there are multiple extension hosts

[https://github.com/microsoft/vscode/issues/196969](https://github.com/microsoft/vscode/issues/196969)

## Summary

Keep open: the issue was reopened after the original fix proved insufficient, and current main still has a termination path where a local web-worker host remains registered while activation waits indefinitely on its defunct RPC proxy.

## Change summary

An `onCommand` activation can remain pending forever after one of multiple extension hosts, specifically the local web-worker host, terminates.

## Best solution

Ensure termination of a local web-worker extension host removes or disposes its manager and settles outstanding activation RPCs, then cover the in-flight activation-and-exit sequence in the extension service tests without changing healthy multi-host activation behavior.

- **Behavior:**

  > When one of multiple extension hosts terminates during an `onCommand` activation, the command activation must not remain pending forever. In particular, termination of the local web-worker extension host must settle or remove that host's outstanding activation work so other hosts and commands can continue. Healthy extension hosts must still receive relevant activation events, and the existing filtering for uninterested hosts must remain intact.
- **Trace:**

  > Current main routes command activation from `CommandService.executeCommand` in src/vs/workbench/services/commands/common/commandService.ts through `AbstractExtensionService._activateByEvent`, which waits on every selected manager with `Promise.all`. `ExtensionHostManager._activateByEvent` in src/vs/workbench/services/extensions/common/extensionHostManager.ts caches and awaits the proxy RPC, marking the event resolved only after it returns. `AbstractExtensionService._onExtensionHostCrashed` handles local-process and remote hosts but not `ExtensionHostKind.LocalWebWorker`, matching the reported defunct-manager condition. RPCProtocol disposal settles outstanding replies, so lifecycle cleanup is the relevant boundary; do not weaken normal activation waiting or skip healthy interested hosts. The earlier attempt in https://github.com/microsoft/vscode/pull/197440 only skipped hosts without interested extensions and was shown insufficient by the later reopen.

## Evidence

- **current activation path:** On current main, src/vs/workbench/services/extensions/common/extensionHostManager.ts `_activateByEvent` awaits `proxy.activateByEvent(...)`; the activation is cached and is marked resolved only after that RPC returns.
- **current crash handling:** src/vs/workbench/services/extensions/common/abstractExtensionService.ts `_onExtensionHostCrashed` stops local-process and remote managers but has no corresponding branch for `ExtensionHostKind.LocalWebWorker`, leaving the terminated manager in the collection used by `_activateByEvent`.
- **blocking aggregation:** src/vs/workbench/services/extensions/common/abstractExtensionService.ts `_activateByEvent` waits on `Promise.all` across all selected extension-host managers, while src/vs/workbench/services/commands/common/commandService.ts awaits that aggregate before executing an already registered command.
