# Issue #321290 — Chat session marked empty and hidden while Copilot transcript/edit state remain intact

[https://github.com/microsoft/vscode/issues/321290](https://github.com/microsoft/vscode/issues/321290)

## Summary

Keep open: the detailed persisted artifacts confirm that a non-empty session was replaced by an empty stub and then hidden, and current main still trusts that empty state without reconciliation. This is a team-authored issue, no fixing PR or qualifying duplicate exists, and the precise interruption/write race remains undiagnosed.

## Change summary

Prevent interrupted Copilot Chat sessions from being overwritten and hidden as empty when their persisted transcript or edit state proves they contain work.

## Best solution

Make session persistence refuse to replace previously non-empty history with an empty live model except during an explicit clear/delete operation, then provide a visible recovery path when the core session log and Copilot transcript disagree. Diagnosis should first identify how a titled empty ChatModel acquires an existing session ID with a fresh serializer.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts`, `src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts`, `src/vs/workbench/contrib/chat/common/model/objectMutationLog.ts`, `src/vs/workbench/contrib/chat/test/common/model/chatSessionStore.test.ts`
- **Validation:** Add a focused ChatSessionStore/ChatService regression test that first persists a session with requests, simulates the identified interruption or stale empty-model lifecycle, and verifies that the stored requests and non-empty history entry survive; add a recovery-path test once its UX contract is chosen.
- **Behavior:**

  > A chat session with previously persisted requests must not silently become empty or disappear from history after an interruption, shutdown, or disposal of an incomplete in-memory model. Only an explicit user clear/delete operation may discard persisted requests. When other persisted artifacts prove that a hidden session contains work, VS Code must surface a clear recovery outcome rather than silently omitting it. Existing genuinely empty new chats should remain excluded from history.
- **Trace:**

  > Current history enumeration in src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts drops entries whose stored metadata has `isEmpty`. ChatService.saveState writes index metadata synchronously and session contents asynchronously, while its model-disposal callback stores custom-titled models even when they have no requests. In src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts, metadata considers only the live request count; writeSession installs a fresh ChatSessionOperationLog when none is attached. In src/vs/workbench/contrib/chat/common/model/objectMutationLog.ts, a serializer without previous state replaces the file with an initial snapshot, which is consistent with the reported empty stub, but the source trace does not yet establish how that fresh serializer becomes associated with the existing session ID. Preserve normal explicit deletion, genuinely empty-chat filtering, and append-log compaction behavior. https://github.com/microsoft/vscode/issues/333143 corroborates truncation but is younger; https://github.com/microsoft/vscode/issues/307348 follows a distinct malformed-request hydration path.
- **Open decisions:**
  - When the core chat-session payload is already empty or missing but a Copilot transcript or editing-state artifact remains, should VS Code reconstruct a continuable session, expose a read-only recoverable session, or present an explicit recovery action?

## Evidence

- **confirmed persisted state:** The report documents one session whose index has `isEmpty: true` and whose core JSONL contains an empty initial snapshot, while its matching Copilot transcript contains 557 valid events and its editing-session state remains present.
- **current history filter:** src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:getHistorySessionItems filters out every persisted entry with `entry.isEmpty`, with no transcript or editing-state reconciliation.
- **current empty metadata path:** src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts:getSessionMetadataSync derives `isEmpty` solely from `session.getRequests().length === 0`; ChatService.saveState synchronously flushes that metadata before starting asynchronous session-file writes.
- **destructive empty write path:** ChatService's model-disposal callback preserves and stores a custom-titled model even when it has zero requests. ChatSessionStore.writeSession creates a fresh ChatSessionOperationLog when the model has no serializer, and ObjectMutationLog.write emits a replacing initial snapshot when it has no previous state, matching the reported three-record empty stub shape.
- **related but not duplicate:** https://github.com/microsoft/vscode/issues/307348 is older and concerns an interrupted session remaining visible but failing to hydrate because of an incomplete request. That differs from this report's observable symptom and persisted state: a valid empty replacement marks the session empty and removes it from history.
- **younger corroborating report:** https://github.com/microsoft/vscode/issues/333143 reports the same empty-initial-snapshot truncation after shutdown, but it was created after this re-reviewed issue and therefore cannot be its canonical duplicate.
- **no fixing PR:** A live GitHub search found no open pull request referencing https://github.com/microsoft/vscode/issues/321290.
