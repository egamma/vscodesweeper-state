# Issue #250024 — Significant VSCodeVim performance slowdowns tied to visible size of another extension's static TreeView

[https://github.com/microsoft/vscode/issues/250024](https://github.com/microsoft/vscode/issues/250024)

## Summary

Still reproducible on main: context key changes (frequent during VSCodeVim remapped-key processing) trigger an unthrottled O(n) iteration over all rendered TreeView elements and synchronous rerenders, scaling linearly with the visible tree size. A minor optimization was made (d434e5bb605, hoisting getEntireMenuContexts out of the inner loop) but the fundamental architecture remains.

## Change summary

Holding a remapped VSCodeVim key causes severe lag proportional to how many tree items are visible in another extension's TreeView.

## Best solution

Throttle or debounce the context-key-driven rerender path in TreeRenderer.onDidChangeContext (src/vs/workbench/browser/parts/views/treeView.ts line ~1584). The current code iterates all _renderedElements on every context key change event and synchronously rerenders affected items — batching these rerenders (e.g. via a microtask or requestAnimationFrame) would decouple TreeView cost from high-frequency context key updates. An alternative is to skip the iteration entirely when the TreeView is not focused/active.
