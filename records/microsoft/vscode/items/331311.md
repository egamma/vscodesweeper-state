# Issue #331311 — Add an sound notification for Claude harness permission prompts

[https://github.com/microsoft/vscode/issues/331311](https://github.com/microsoft/vscode/issues/331311)

## Summary

Keep open for Claude permission-notification parity and the ongoing community review. The sound setting already exists, but the inspected Claude confirmation path does not establish equivalent audible notification support.

## Change summary

Play a configurable audible notification when the embedded Claude harness waits for permission, matching Local harness behavior.

## Best solution

Provide consistent permission-request feedback across harnesses using the existing accessibility.signals.chatUserActionRequired control, without changing approval semantics or requiring external audio hooks. First confirm the embedded Claude flow on Linux and identify where its pending confirmations bypass the existing notification path.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/claude/claudeCanUseTool.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts`, `src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts`, `src/vs/workbench/contrib/accessibility/browser/accessibilityConfiguration.ts`
- **Validation:** On Linux, set accessibility.signals.chatUserActionRequired.sound to on and trigger a non-auto-approved tool permission request in both Local and Claude harnesses: each should produce one audible cue. Repeat with sound off and verify silence, unchanged permission controls, and no repeated cue on rerender. The plan should identify a targeted regression test for Claude pending-confirmation signal delivery.
- **Behavior:**

  > The embedded Claude harness should audibly notify the user when a tool operation requires permission, matching Local harness feedback. The existing chat-user-action-required sound setting should enable or disable that feedback. A pending prompt should not produce repeated sounds merely because it rerenders, and automatically approved operations should not produce permission cues. Approval, denial, and cancellation behavior must remain unchanged.
- **Trace:**

  > handleCanUseTool in src/vs/platform/agentHost/node/claude/claudeCanUseTool.ts creates PendingConfirmation state and waits on session.requestPermission. AgentHostSessionHandler._setupServerToolCall translates initial pending states and subsequent confirmation transitions into ChatToolInvocation objects, while _awaitToolConfirmation waits for the answer and forwards it to the host. The inspected bridge does not itself play the permission signal; LanguageModelToolsService.playAccessibilitySignal contains the existing Local-tool signal gating, and accessibilityConfiguration.ts already registers the requested sound control. Elicitation and question-carousel signals are separate paths, not evidence of ordinary permission coverage. The uncertainty is whether another shared observer supplies the signal for these Claude invocations and whether this path matches the reporter's embedded harness; reproduce that exact flow before selecting a change boundary. Preserve permission policy, approval decisions, and existing sound/announcement preferences; do not treat the terminal-only workaround in https://github.com/microsoft/vscode/issues/331311 as embedded-harness validation.
