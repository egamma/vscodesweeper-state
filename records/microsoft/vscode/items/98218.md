Keep this accepted touch-scrolling request open: the discussion identifies a Linux/browser default-input gap, and the reported launch flag is a workaround rather than built-in coverage. No verified fixing commit or older open canonical covering the same symptom was found.

## Change summary

Enable finger-drag scrolling and basic cursor placement in the code editor on Chromebook and Linux touch-enabled devices without special launch flags.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/pointerHandler.ts`, `src/vs/base/browser/touch.ts`
- **Validation:** On a touch-enabled Chromebook/Linux device, open a long source file in a default Code launch and in vscode.dev under Chrome and Firefox. Verify that finger drags scroll the editor and taps place the cursor without --touch-events; compare against the reported flagged launch while recording delivered touch and pointer events. Preserve mouse selection and existing Windows/iOS touch behavior.
- **Behavior:**

  > Users on Chromebook and Linux touch-enabled devices should be able to scroll a source-code editor by dragging a finger and place the cursor by tapping without changing browser or application launch flags. The thread reports that other surfaces scroll while the code editor does not, and that --touch-events restores editor scrolling in some configurations. Acceptance should cover default desktop and web launches on affected hardware while preserving mouse selection and existing touch interactions. Virtual-keyboard support, editor-tab dragging, and general touch-selection enhancements are outside this request.
- **Trace:**

  > PointerHandler in src/vs/editor/browser/controller/pointerHandler.ts chooses PointerEventHandler for iOS/mobile Android, TouchHandler when mainWindow.TouchEvent exists, and otherwise MouseHandler. TouchHandler already maps gesture changes to viewLayout.deltaScrollNow and taps to cursor movement. Gesture in src/vs/base/browser/touch.ts listens for document touch events and uses ontouchstart/maxTouchPoints to detect touch support. These paths establish existing capability, not which events current Linux browsers and Electron deliver on the affected hardware; diagnosis stops at that platform boundary. Compare default and flagged event delivery before deciding whether the remaining work belongs in editor handling or its runtime dependency. https://github.com/microsoft/vscode/issues/104428 reports the same workaround but is younger; https://github.com/microsoft/vscode/issues/340397 concerns a separate virtualization-triggered interruption and must not be treated as proof of this request's root cause.
