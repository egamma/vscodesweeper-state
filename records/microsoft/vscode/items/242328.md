# Issue #242328 — CustomTextEditor does not support the isReadonly flag and icon (small lock)

[https://github.com/microsoft/vscode/issues/242328](https://github.com/microsoft/vscode/issues/242328)

## Summary

Keep open: custom documents still derive read-only state from their provider's editing capability, with no per-document mechanism to change that state after opening. Existing text-editor support does not cover the requested CustomDocument workflow, and no qualifying canonical duplicate or fix was established.

## Change summary

Allow an extension to change a custom document between read-only and editable states while keeping the editor tab's lock indicator synchronized.

## Best solution

Define a per-document read-only API contract for custom editors that supports changing state while the document remains open and updates the standard editor capabilities and lock indicator. Preserve existing provider-level read-only behavior and text-document handling.

## Evidence

- **Public API gap:** src/vscode-dts/vscode.d.ts:10387–10400 defines CustomDocument with only uri and dispose(), without a read-only property or state-change event. CustomReadonlyEditorProvider and CustomEditorProvider distinguish editing capability at the provider level.
- **Current custom-document path:** src/vs/workbench/api/common/extHostCustomEditors.ts:244–263 returns editable from isCustomEditorProviderWithEditingCapability(entry.provider), rather than document state. In src/vs/workbench/api/browser/mainThreadCustomEditors.ts:624–641, this becomes the model's readonly _editable field; lines 729–735 expose onDidChangeReadonly as Event.None and return !_editable.
- **Existing capability is only partial coverage:** src/vs/workbench/contrib/customEditor/common/customTextEditorModel.ts forwards read-only state and changes from its underlying text model. CustomEditorInput.isReadonly() delegates to its resolved model, and its capabilities getter maps that state to EditorInputCapabilities.Readonly. Thus custom text models already have support, but the issue body's CustomDocument unlock workflow remains unsupported.
- **Existing command does not supply the missing API:** workbench.action.files.setActiveEditorReadonlyInSession and its writable/toggle counterparts are registered in src/vs/workbench/contrib/files/browser/fileActions.contribution.ts. BaseSetActiveEditorReadonlyInSession.run in fileActions.ts:1348–1357 updates filesConfigurationService; the resolved MainThreadCustomEditorModel instead returns its fixed provider-derived state.
- **Companion request clarifies the product boundary:** https://github.com/microsoft/vscode/issues/242330 was closed for plain webviews. The response at https://github.com/microsoft/vscode/issues/242330#issuecomment-2845818602 recommends custom editors for read-only behavior and explains that decorators reflect resource state; it does not resolve dynamic per-document read-only state in custom editors.
