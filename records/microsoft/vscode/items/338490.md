# Issue #338490 — Activity indicator appears on the top-level session, not the active chat

[https://github.com/microsoft/vscode/issues/338490](https://github.com/microsoft/vscode/issues/338490)

## Summary

Fresh, credible first-hand report from a collaborator actively testing the new multi-chat session feature (PR #338224), with a screenshot showing the status indicator on the wrong tree row. Real gap likely exists in how the session row derives its aggregate status vs. an expanded/active sub-chat, but I couldn't pin the exact code path with certainty.

## Change summary

When a sub-chat within a session is the one actually processing a request, the busy/activity spinner shows on the top-level session row instead of on the active sub-chat, making it unclear which chat is actually working.

## Best solution

Have someone reproduce interactively in the sessions tree (multi-chat/session-with-sub-chats view) and confirm whether `getSessionRowStatus`'s collapsed/aggregate fallback in src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts is stale or mis-tracking expansion state for this case, then scope the indicator to the chat that is actually in progress.

- **Behavior:**

  > When a user sends a request in a sub-chat (not the session's main chat) within a multi-chat session, the in-progress/activity spinner should render on that specific sub-chat's row, not on the top-level session row (unless the session row also reasonably aggregates 'something in this session is busy' when collapsed). The parent row should not show a spinner that implies the main/session-level chat itself is busy when it isn't.
- **Trace:**

  > getSessionRowStatus in src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:268 returns the session's aggregate status (which can be InProgress due to a sub-chat) when the row is 'collapsed', and the main chat's own status otherwise. Collapse state comes from collapsedSessionIds, computed from tree node collapse in sessionsList.ts:4457-4470. The likely defect is either a stale/incorrect collapse determination for the multi-chat/session-with-visible-sub-chats view, or a separate status source (e.g. chatCompositeBar.ts tab status logic around line 396-414) not being reflected on the parent row consistently. Boundary: do not change status semantics for genuinely collapsed sessions (aggregate rollup there is intentional) — only the case where sub-chats are visible/expanded and the indicator still lands on the parent.
- **Open decisions:**
  - When sub-chats are visible/expanded, should the parent session row show no busy indicator at all, or a distinct 'something in this session is active' indicator separate from the main-chat spinner?
