# Issue #336761 — Agent Host ignores the selected custom agent: picker resets to "Agent" and the agent prompt is never applied

[https://github.com/microsoft/vscode/issues/336761](https://github.com/microsoft/vscode/issues/336761)

## Summary

Thanks for the detailed diagnosis — this reproduces and traces to a real URI-identity mismatch in the Agent Host, so it stays open as a bug rather than closing; the fix needs a design decision on where URI normalization belongs before an agent can implement it.

## Change summary

Selecting a custom agent in the Agent Host picker silently fails to apply the agent's prompt: the picker resets to the default agent and the model answers as the generic assistant instead of the selected custom agent.

## Best solution

Normalize agent URIs to a comparable canonical form before the exact-string match in CopilotAgent._resolveAgentName (and any analogous comparison in the Claude/Codex harnesses), using the existing vscode-agent-host:// unwrap/compare helpers in agentHostUri.ts, so a client-wrapped agent URI resolves against the host's natively-discovered agent URI.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/platform/agentHost/common/customAgents.ts`, `src/vs/platform/agentHost/common/agentHostUri.ts`
- **Validation:** A test selecting a custom agent whose session-published URI is wrapped (vscode-agent-host://...) should still resolve to the matching plugin-discovered agent (raw file:// URI) in _resolveAgentName / resolveAgentHostAgent, and the subsequent turn should carry that agent's prompt.
- **Behavior:**

  > Selecting a custom agent in the Agent Host picker (Agents window or Chat view, especially over Remote-SSH) must keep that agent selected across the next turn and apply its system prompt/instructions to the model. Today the picker silently reverts to the default agent and the reply comes from the generic assistant, with no error surfaced. Acceptance: sending a prompt after selecting a custom agent produces a reply reflecting that agent's prompt, and the picker keeps showing the selected agent.
- **Trace:**

  > CopilotAgent._changeAgentOnce (src/vs/platform/agentHost/node/copilot/copilotAgent.ts:5772) resolves the agent's SDK-facing name via _resolveAgentName (line 2924), which does a strict `a.uri.toString() === agent.uri` compare between the incoming AgentSelection.uri and the host's own plugin.agents entries (populated from raw discovery URIs in copilotPluginConverters.ts:506). When the client's agent URI differs in form from the host's — e.g. the `vscode-agent-host://...` client-facing wrapper documented in agentHostUri.ts versus a raw `file://` discovery URI — the match fails and `entry.setAgent(undefined)` runs with no error, exactly matching the reported symptom. customAgents.ts's resolveAgentHostAgent (line 100/105) has the identical exact-string pattern on the client/picker side. Do not change the picker's effective-agent computation (getEffectiveAgents) or alter working, same-scheme selections — the boundary is specifically the URI-identity comparison used to resolve a selection against the discovered agent list. Where the uncertainty starts: whether the fix normalizes both sides through the existing IAgentHostResourceUriMapper before compare, or compares via a canonicalized key, and whether the same gap exists in the Claude/Codex harnesses (which keep separate agent-selection state per the multi-harness architecture) or is Copilot-specific.
- **Open decisions:**
  - Should URI comparison for agent selection be normalized through a single shared helper (e.g. in agentHostUri.ts) used by every harness, or fixed per-harness where each currently implements its own comparison?
  - Do the Claude and Codex harnesses have an equivalent agent-selection comparison that needs the same fix, or is this isolated to Copilot's _resolveAgentName?
  - Should a failed agent-name resolution surface a visible error/warning to the user instead of silently falling back to the default agent?

## Evidence
