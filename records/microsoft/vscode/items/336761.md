# Issue #336761 — Agent Host ignores the selected custom agent: picker resets to "Agent" and the agent prompt is never applied

[https://github.com/microsoft/vscode/issues/336761](https://github.com/microsoft/vscode/issues/336761)

## Summary

Well-documented report with strong internal evidence (session-state logs showing the custom agent's prompt never enters the system message) and I traced a matching code path in the picker logic: `_initAgent` in agentHostAgentPicker.ts resets the selection to undefined whenever the agent picked doesn't resolve against the provider's current custom-agents list for a no-longer-untitled session — exactly the 'picker flips back to Agent right after send' symptom described.

## Change summary

After manually selecting a custom agent in the Agent Host picker and sending a prompt, the picker resets to 'Agent' and the custom agent's system-message content is never sent to the model — the agent is silently inert.

## Best solution

Diagnose why `resolveAgentHostAgent(agents, selectedAgentUri, storedUri)` fails to resolve a still-valid, already-selected agent once the session transitions off `Untitled` (e.g. a stale/incomplete `getCustomAgents` snapshot for the just-materialized session), and stop `_initAgent`'s reset branch (agentHostAgentPicker.ts ~line 238) from clearing a real selection on that transient failure; separately confirm `resolvedAgentName` correctly threads through to `SessionConfig.agent` in copilotSessionLauncher.ts once the picker keeps the selection.

- **Behavior:**

  > Selecting a custom agent in the Agent Host picker and sending a prompt must keep that agent selected in the picker and must apply the agent's own system prompt to the model for that turn (verified via the probe agent's distinctive reply). Currently the picker silently reverts to the default 'Agent' and the model receives the stock system prompt instead. Acceptance: after send, the picker still shows the selected custom agent, and the system message / SDK `agent` field carries the selected agent's identity for that session.
- **Trace:**

  > `AgentHostAgentPickerContribution._initAgent` (src/vs/sessions/contrib/providers/agentHost/browser/agentHostAgentPicker.ts:212-246) re-runs on session/mode observable changes (autorun at line 115-122) and on send the session goes from Untitled to titled, re-entering this function with `isUntitled=false`. If `resolveAgentHostAgent(agents, selectedAgentUri, storedUri)` (common/customAgents.ts) fails to resolve the currently selected `selectedAgentUri` against `provider.getCustomAgents(session.sessionId)`'s snapshot at that moment, the `else if` branch at line 238 clears the selection via `_setAgent(session, provider, undefined)`. Downstream, `copilotSessionLauncher.ts` correctly force-includes a resolved agent into `customAgents` and sets `SessionConfig.agent` (lines 893, 1027), so the defect most likely sits upstream of that — in the picker's resolve/reset timing, not the SDK config forwarding. The boundary: do not change how a resolved, still-selected agent is threaded into `customAgents`/`SessionConfig.agent`; only the premature-reset condition in `_initAgent` needs scrutiny. Related, narrower issue: https://github.com/microsoft/vscode/issues/317944 (picker pre-selection on session creation), which this report explicitly distinguishes as a possibly-related but distinct regression.
- **Open decisions:**

  - Should `_initAgent`'s reset-on-unresolved branch be removed entirely, gated to only fire when the agent is confirmed genuinely gone (not just not-yet-loaded), or should it retry once the agents list stabilizes?
  - Does the underlying system-message construction (SDK-side, per src/vs/platform/agentHost/node/copilot/prompts/systemMessage.ts / promptRegistry.ts) actually consume `SessionConfig.agent`/`customAgents` correctly once the picker keeps the selection, or is there a second defect there that the picker-reset issue is currently masking?

## Evidence

- **picker reset path:** src/vs/sessions/contrib/providers/agentHost/browser/agentHostAgentPicker.ts:212-246 `_initAgent`: when `selectedAgentUri` is set, `isUntitled` is false, and `resolveAgentHostAgent(agents, selectedAgentUri, storedUri)` returns undefined (agents list present but the URI doesn't resolve), it calls `_setAgent(session, provider, undefined)` — exactly a 'deselection event' as the reporter observed on send.
