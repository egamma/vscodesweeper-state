# Issue #122265 — link parsing should favor on screen urls over offscreen content for huge files

[https://github.com/microsoft/vscode/issues/122265](https://github.com/microsoft/vscode/issues/122265)

## Summary

A real gap remains on current main: link detection processes every line before publishing any results, so links near the viewport are not prioritized in large files. The existing `editor.links` setting only enables or disables the feature, and no open canonical issue was found that owns this narrower scheduling request.

## Change summary

Prioritize link detection around the visible editor range before scanning the remaining content of a large file.

## Best solution

Design range-aware, incremental link computation that publishes visible-region links promptly and completes the rest without regressing extension-provided document links, cancellation, or decoration updates.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/links/browser/links.ts`, `src/vs/editor/contrib/links/browser/getLinks.ts`, `src/vs/editor/browser/services/editorWorkerService.ts`, `src/vs/editor/common/services/editorWebWorker.ts`, `src/vs/editor/common/languages/linkComputer.ts`, `src/vs/editor/common/languages.ts`, `src/vs/editor/test/common/modes/linkComputer.test.ts`
- **Validation:** Add a targeted editor link test using a large synthetic model and a viewport near its end, asserting that links in the visible range become available before completion of the remaining document scan; retain existing link-computer tests for complete-result correctness.
- **Behavior:**

  > After navigating deep into a large file, links in and near the visible range should become clickable without waiting for link detection over all preceding content. Link detection should eventually cover the rest of the document, and ordinary-sized files should retain their current link results and interaction behavior. Acceptance should demonstrate visible-region results arriving before whole-document completion while preserving final link ordering and correctness.
- **Trace:**

  > `EditorLinkDetector.computeLinksNow` in `src/vs/editor/contrib/links/browser/links.ts` awaits `getLinks` and installs decorations only after every registered provider finishes. The built-in provider in `src/vs/editor/browser/services/editorWorkerService.ts` delegates to `EditorWebWorker.$computeLinks`, which calls `LinkComputer.computeLinks`; that function scans line 1 through the end of the model. The existing large-model guard disables the feature only above the synchronization limit and provides no prioritization below it. The uncertainty begins at the provider boundary: `LinkProvider.provideLinks` receives the complete model rather than a requested range, and multiple providers are merged into one `LinksList`. Preserve extension-provider compatibility, cancellation, overlap precedence, complete final results, and behavior for normal-sized documents. The broader https://github.com/microsoft/vscode/issues/167719 does not replace this issue because it concerns very-large-model storage and disabling expensive contributions rather than visible-range-first link computation.
- **Open decisions:**
  - Should viewport prioritization apply only to the built-in link computer, or should the document-link provider contract gain an internal range-aware path?
  - How should partial visible-range results be merged with later background results while preserving provider precedence and avoiding decoration flicker?
  - Which model-size threshold should activate incremental computation, and how should scrolling or edits cancel and reprioritize outstanding work?

## Evidence

- **current controller path:** On current main, `EditorLinkDetector.computeLinksNow` in `src/vs/editor/contrib/links/browser/links.ts` requests one complete `LinksList` and updates decorations only after that promise resolves; it has no visible-range-first path.
- **whole-model scan:** `LinkComputer.computeLinks` in `src/vs/editor/common/languages/linkComputer.ts` loops from line 1 through `model.getLineCount()`, and `EditorWebWorker.$computeLinks` in `src/vs/editor/common/services/editorWebWorker.ts` invokes it for the entire synchronized model.
- **large-file handling:** `src/vs/editor/browser/services/editorWorkerService.ts` and `src/vs/editor/contrib/links/browser/links.ts` disable link computation only when `isTooLargeForSyncing()` is true; files below that threshold still receive a complete scan rather than viewport-prioritized results.
- **existing capability:** `EditorOption.links` is registered as a boolean option in `src/vs/editor/common/config/editorOptions.ts`; disabling links avoids the work but does not satisfy the request for promptly clickable visible links.
- **canonical search:** The broader open large-file exploration at https://github.com/microsoft/vscode/issues/167719 discusses disabling expensive contributions for extremely large models, including link detection, but does not own incremental or viewport-prioritized link parsing for models where links remain enabled.
