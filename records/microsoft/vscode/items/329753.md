# Issue #329753 — Customizations: consolidate the two independent "disabled" stores

[https://github.com/microsoft/vscode/issues/329753](https://github.com/microsoft/vscode/issues/329753)

## Summary

The structural debt remains on current main: customization enablement is still persisted through two contracts, and the agent-host path explicitly combines them. This team-authored issue should remain open while the persistence, precedence, and migration semantics are designed.

## Change summary

Replace the two independent customization-disabled stores with one authoritative enablement contract and consistent persistence semantics.

## Best solution

Choose whether per-harness opt-outs remain an explicit overlay, then expose one shared query and change-notification contract, migrate existing persisted choices, and move every customization UI and agent-host consumer onto it.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/customizationHarnessService.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsService.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentCustomizationSyncProvider.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostLocalCustomizations.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/pluginListWidget.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagement.contribution.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationItemSource.ts`, `src/vs/sessions/contrib/aiCustomizationTreeView/browser/aiCustomizationTreeViewViews.ts`, `src/vs/sessions/AI_CUSTOMIZATIONS.md`
- **Validation:** Add focused storage-migration and enablement tests covering both legacy keys, conflicting legacy values, each supported harness, and consistent list/wire state; run them with `scripts/test.sh --grep "enumerateLocalCustomizationsForHarness|AI Customization Items Model|AgentCustomizationSyncProvider"`.
- **Behavior:**

  > A customization has one authoritative enabled/disabled result for a given harness, and every management surface and agent-host payload reports that same result. Toggling an item updates all affected consumers without requiring each consumer to combine independent stores. Existing users retain a deterministic enablement state after upgrade, including when their legacy stores disagree. Agent-picker visibility and runtime customization enablement remain distinct if the maintainer chooses them as separate concepts.
- **Trace:**

  > IPromptsService persists disabled URIs by prompt type in promptsServiceImpl.ts using PROFILE/USER storage, while AgentCustomizationSyncProvider persists URI strings by session type using PROFILE/MACHINE storage. pluginListWidget.ts writes the latter; aiCustomizationManagement.contribution.ts and promptFilePickers.ts write the former. enumerateLocalCustomizationsForHarness currently joins the states with an OR, while aiCustomizationItemSource.ts and the Sessions tree consume the prompt-service state directly. AgentHostActiveClientService creates and observes one sync provider per session type and separately observes prompt-service change events, so consolidation affects persistence, notification, UI, and wire contracts. Preserve customization discovery, plugin enablement, and single-item explicit actions; the plan should not broaden into unrelated customization filtering or provider discovery. The immediate regression was fixed by https://github.com/microsoft/vscode/pull/329786, but that PR deliberately retained this split.
- **Open decisions:**
  - Should disabling a customization remain per harness and machine, become a single user-synced choice across harnesses, or use a documented global state plus per-harness overlay?
  - Should the agent picker's hidden-agent state remain independent from runtime customization enablement, rather than continuing to share `getDisabledPromptFiles(PromptsType.agent)`?
  - When the two legacy stores disagree during migration, should disabled win, should the more specific per-harness value win, or should one store be ignored for particular customization types?

## Evidence

- **two stores remain:** Current main still defines `chat.disabledPromptFiles.<type>` in src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts with PROFILE/USER storage, while src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentCustomizationSyncProvider.ts defines `customizationSync.disabled.<harnessId>` with PROFILE/MACHINE storage.
- **combined read path:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostLocalCustomizations.ts still computes enablement as `syncProvider.isDisabled(file.uri) || (userToggleable && userDisabled.has(file.uri))`, confirming that neither store is authoritative.
- **split writers:** src/vs/workbench/contrib/chat/browser/aiCustomization/pluginListWidget.ts writes the per-harness sync provider, while src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagement.contribution.ts and promptFilePickers.ts write IPromptsService.
- **different observable scopes:** AgentHostActiveClientService creates one AgentCustomizationSyncProvider per session type, whereas IPromptsService stores one disabled set per prompt type; consolidating them therefore requires a decision about cross-harness and cross-machine behavior.
- **workaround rather than consolidation:** https://github.com/microsoft/vscode/pull/329786 fixed https://github.com/microsoft/vscode/issues/329751 by teaching consumers to honor both stores; its description explicitly lists this issue as the follow-up for removing the split.
- **no competing implementation:** A live GitHub search found no open microsoft/vscode pull request referencing https://github.com/microsoft/vscode/issues/329753, and the canonical search found no open issue owning the same consolidation.
