# Issue #250473 — Retry experience not good

[https://github.com/microsoft/vscode/issues/250473](https://github.com/microsoft/vscode/issues/250473)

## Summary

Keep open for a retry/edit UX decision: inline prompt editing now exists, but Retry still uses the refresh icon and can replace a completed answer without confirmation when no files were edited. The discussion identifies a concrete accidental-click scenario, and the existing settings do not fully address it.

## Change summary

Clarify chat Retry and its relationship to editing a prompt, including protection against accidentally replacing a useful response.

## Best solution

Agree on a coherent retry/edit interaction in the chat message toolbar that makes regeneration intentional and its consequences understandable. Evaluate the icon and placement together with the reported accidental loss of a completed answer, rather than treating an icon swap alone as resolution.

  > The chat retry interaction should communicate its purpose clearly and distinguish intentional regeneration from copying an existing answer. The reported case is a user accidentally activating Retry while trying to copy a satisfactory response and then losing that response. Inline prompt editing already exists, so acceptance must address the remaining separate Retry affordance and its replacement consequences, not merely demonstrate editing. The final interaction must remain usable with keyboard navigation and preserve an intentional recovery path for failed requests.
- **Trace:**

  > RetryChatAction in src/vs/workbench/contrib/chat/browser/actions/chatTitleActions.ts registers workbench.action.chat.retry with Codicon.refresh in the response footer and calls IChatService.resendRequest. Its dialog is conditional on modified files in Edit/Agent mode; text-only answer replacement bypasses that protection. ChatService.resendRequest in src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts removes the original request on its default path before resending. chat.editRequests defaults to inline in chat.shared.contribution.ts, and ChatListRenderer.renderMarkdown wires request-text clicks into editing, so an edit entry point is already present. The existing RetryChatAction test suite provides a bounded action-validation surface. The uncertainty is product behavior, not whether those paths exist: https://github.com/microsoft/vscode/issues/250473 does not settle whether Retry remains separate or how accidental replacement should be handled. Preserve existing file-edit rollback safeguards and distinguish successful-answer regeneration from failure recovery; the latter is separately discussed in https://github.com/microsoft/vscode/issues/295615.
- **Open decisions:**
  - Should successful-response regeneration remain a separate Retry action, or be consolidated into editing and resubmitting the original request?
  - For a completed text-only response, should intentional retry replace the answer immediately, require confirmation, or retain access to the previous answer?
