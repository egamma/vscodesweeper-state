# Issue #343277 — Private marketplace: workbench gallery requests send Electron's User-Agent, so the Marketplace answers 403

[https://github.com/microsoft/vscode/issues/343277](https://github.com/microsoft/vscode/issues/343277)

## Summary

Keep open: current source drops the requested User-Agent before renderer requests reach the configured private marketplace, and the main-process compensation excludes that marketplace. The report provides detailed reproduction steps and request logs, and a maintainer has already requested investigation.

## Change summary

Ensure workbench requests to the configured private extension marketplace carry VS Code's Marketplace User-Agent rather than Electron's browser User-Agent.

## Best solution

Make the existing Marketplace header behavior apply consistently to the configured private gallery in desktop workbench requests. Preserve public-gallery behavior, authentication, telemetry consent, and unrelated requests while accounting for the shared Electron session's interceptor ownership.

## Plan brief

- **Likely files:** `src/vs/platform/windows/electron-main/windowImpl.ts`, `src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryManifestService.ts`, `src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts`, `src/vs/platform/extensionManagement/common/extensionGalleryManifest.ts`
- **Validation:** Using the report's HTTPS relay in an isolated desktop profile, configure extensions.gallery.serviceUrl and extensions.gallery.authProvider=microsoft, sign in, and trigger extension queries by name and ID. Assert that the relay receives User-Agent: VSCode <version> (<nameShort>) and those queries no longer fail with the User agent is blocked response. Repeat with a second window and after changing the configured gallery and performing the requested restart; verify public-gallery requests remain correct and an unrelated HTTPS origin receives no injected Marketplace headers.
- **Behavior:**

  > Workbench extension queries to a configured private marketplace currently carry Electron's browser User-Agent, unlike shared-process queries, causing a forwarding marketplace to receive 403 responses for name and ID lookups. Both paths should present the existing VS Code Marketplace User-Agent. Acceptance checks must inspect the actual received HTTPS headers, not merely request options or trace logs. Existing authentication, public-gallery behavior, telemetry consent, and unrelated-origin requests must remain unchanged.
- **Trace:**

  > NativeRequestService.request delegates to requestImpl.request, whose getRequestHeaders explicitly removes user-agent. CodeWindow's onBeforeSendHeaders handler restores Marketplace headers only for vsassets and the product-defined gallery origin, excluding extensions.gallery.serviceUrl. WorkbenchExtensionGalleryManifestService reads the configured gallery and publishes its resolved state to shared-process and remote-server channels; that inspected path does not publish it to the main process. The report at https://github.com/microsoft/vscode/issues/343277 includes received-header logs and notes that window registrations share a session whose webRequest listener is replaced by later registrations. The remaining trace must establish how the authoritative configured origin reaches the session owner and how multiple windows and configuration restarts interact. Do not remove the generic browser request header restrictions or broaden Marketplace header injection to arbitrary origins.

## Evidence

- **Exact failing path in current source:** src/vs/workbench/services/request/electron-browser/requestService.ts: NativeRequestService.request delegates to src/vs/base/parts/request/common/requestImpl.ts. Its getRequestHeaders explicitly skips user-agent before calling fetcher, so the requested VSCode User-Agent never reaches fetch. This directly explains the reporter's trace showing that header while the HTTPS relay receives Electron's default.
- **Missing main-process compensation:** src/vs/platform/windows/electron-main/windowImpl.ts:953–962 constructs onBeforeSendHeaders filters from https://*.vsassets.io/* and productService.extensionsGallery.serviceUrl only. A separately configured private-gallery origin is not covered, so getMarketplaceHeaders does not restore its User-Agent.
- **Intended header and supported configuration:** src/vs/platform/externalServices/common/marketplace.ts: resolveMarketplaceHeaders defines User-Agent as VSCode <version> (<nameShort>). src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts registers extensions.gallery.serviceUrl with the ExtensionGalleryServiceUrl policy; WorkbenchExtensionGalleryManifestService.doGetExtensionGalleryManifest reads that setting and selects the private marketplace.
- **Concrete reproduction evidence:** https://github.com/microsoft/vscode/issues/343277 supplies an HTTPS relay, configuration steps, and request-by-request results: workbench name/ID queries receive 403 with Electron's User-Agent, while equivalent shared-process queries receive 200 with VSCode's User-Agent. Source inspection confirms the header-loss mechanism; no runtime reproduction or external Marketplace requests were executed.
- **Maintainer direction:** https://github.com/microsoft/vscode/issues/343277#issuecomment-6325674071 acknowledges the workbench User-Agent discrepancy and asks the Private Marketplace owner to investigate. This supports retaining the issue rather than declining the integration.
- **Remaining implementation boundary:** WorkbenchExtensionGalleryManifestService currently publishes the resolved manifest, token, and service-index URL to shared-process and remote-server channels, not the main process. The complete issue also notes that onBeforeSendHeaders registrations replace one another on the shared default session; configuration propagation and interceptor ownership therefore need tracing together.

An unauthenticated GitHub search for private marketplace and User-Agent surfaced this report; no older same-symptom canonical was verified.
