# Issue #65369 — Prevent Find/Replace bar from returning after Next Match (F3)

[https://github.com/microsoft/vscode/issues/65369](https://github.com/microsoft/vscode/issues/65369)

## Summary

Keep open: current source still reopens the Find widget when F3 or Shift+F3 follows Escape, even with editor.find.closeOnResult enabled. This accepted Backlog request has 27 upvotes, and no verified canonical owns the remaining behavior.

## Change summary

Allow next/previous match navigation to reuse the last search without reopening a Find widget dismissed with Escape.

## Best solution

Support hidden next/previous navigation using the retained search text and options in the editor Find controller. Settle whether this is the default or an opt-in behavior while preserving explicit Ctrl+F opening.

## Evidence

- **Exact current-source path:** In src/vs/editor/contrib/find/browser/findController.ts, closeFindWidget() sets isRevealed=false; _onStateChanged() then disposes the find model. On the next F3/Shift+F3, moveToNextMatch()/moveToPrevMatch() returns false without that model, so matchFindAction() calls start(); _start() unconditionally sets isRevealed=true. This matches the reporter's Ctrl+F → search → Escape → F3 trigger.
- **Existing capability does not cover the request:** editor.find.closeOnResult is registered in src/vs/editor/common/config/editorOptions.ts. In matchFindAction(), automatic closing requires wasFindWidgetVisible and isFindInputFocused(); after Escape, wasFindWidgetVisible is false, so this setting does not prevent reopening during either navigation direction. Find Next Selection also starts the widget when its find model is absent and changes the search term to the current selection, so it is not equivalent.
- **Related implementation is a different behavior:** https://github.com/microsoft/vscode/commit/22933cea7b65c18ba29aa7f52937f13b22bd2eb5 added closeOnResult for https://github.com/microsoft/vscode/issues/264818 through https://github.com/microsoft/vscode/pull/299865. Its diff adds closing after successful navigation from a previously visible, focused Find input; it does not change the hidden-widget restart path. The related issue is closed and newer, not a duplicate canonical for this re-reviewed item.
