# Issue #338293 — Agent Host: reconcile filesystem permissions with managed sandbox policies

[https://github.com/microsoft/vscode/issues/338293](https://github.com/microsoft/vscode/issues/338293)

## Summary

Team-authored investigation issue (MEMBER, milestone On Deck) scoping a real, confirmed gap: the Agent Host doesn't reconcile local filesystem sandbox settings with managed policy, and shell-init script registration doesn't verify the read grant was actually applied before treating the script as ready. Nothing bars keep-open here, and the design has open decisions that need maintainer input before implementation.

## Change summary

Define how Agent Host sandbox filesystem permissions should be reconciled when local settings conflict with managed policy, including ensuring shell-init scripts get required read access before being registered.

## Best solution

Design a runtime contract that composes local filesystem grants with managed restrictions (rather than all-or-nothing rejection), and gate shell-init script registration on confirmed (not merely requested) read access — informed by rwoll's concrete Windows PowerShell repro.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/sessionSandbox.ts`, `src/vs/platform/agentHost/node/copilot/sandboxConfigForSdk.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts`
- **Validation:** A test in copilotAgentSession.test.ts (shell init scripts suite) asserting that when a managed-policy conflict rejects a combined sandbox update, the shell init script is not registered as ready until a reconciled/retried grant actually succeeds.
- **Trace:**

  > Confirmed from source: `_updateEffectiveSandboxConfig` in copilotAgentSession.ts applies the whole candidate `SandboxConfig` and on rejection falls back wholesale rather than composing local requested grants with the managed-restricted ones; `_applyEffectiveShellInitScripts` registers the shell-init script path once `_applyEffectiveSandboxConfig` resolves, without distinguishing 'requested' from 'runtime-confirmed' grants. rwoll's Windows PowerShell repro in the thread is a live instance. The boundary: do not duplicate or bypass the runtime's managed-policy parser in VS Code (per the issue body) — any composition must defer to the runtime as source of truth.
- **Open decisions:**
  - What is the runtime-owned contract for composing local filesystem allow/deny lists with managed restrictions — partial grant application, or still all-or-nothing per update?
  - What UX should surface when a required read grant (e.g. shell-init directory) cannot be reconciled with managed policy — generic host-capability failure (as seen today) vs. an actionable message naming the required path?
  - Should operations depending on an unconfirmed grant (shell-init registration, session attachments) be deferred/retried automatically, and for how long, before failing the turn vs. continuing degraded?

## Evidence

- **atomic rejection confirmed:** copilotAgentSession.ts `_updateEffectiveSandboxConfig` (around line 5641) applies `sandboxConfig` as a whole via `applySandboxConfig`; there's no logic composing managed filesystem restrictions with local allow/deny lists — a rejected update just falls back to `{ enabled: false }` or the last applied config, confirming the issue's described gap.
- **shell-init grant not verified:** `_applyEffectiveShellInitScripts` (around line 5673) calls `_applyEffectiveSandboxConfig(true)` before registering the script path, but does not check whether the shell-init directory grant was actually accepted by the runtime versus silently dropped in a rejected/merged config — matching the issue's concern that 'requested' is not proof of 'applied'.
- **related merged PR is partial:** https://github.com/microsoft/vscode/pull/338274 only logs the conflict and continues with the runtime's last applied config; it explicitly does not reconcile filesystem permissions or rewrite local settings, per the issue body and PR discussion https://github.com/microsoft/vscode/pull/338274#discussion_r4117181924.
- **concrete repro added by maintainer:** Comment from rwoll (MEMBER) on 2026-09-30 reproduces a real Windows failure: PowerShell fails under managed sandboxing with 'this Windows host cannot run PowerShell in the sandbox' unless `C:\` is added to read-only access — a live instance of the filesystem/managed-policy reconciliation gap this issue investigates.
- **related closed test issue:** https://github.com/microsoft/vscode/issues/338294 (closed) is a test-plan item for managed sandbox policies, not a canonical covering this reconciliation work.
