# Issue #338293 — Agent Host: reconcile filesystem permissions with managed sandbox policies

[https://github.com/microsoft/vscode/issues/338293](https://github.com/microsoft/vscode/issues/338293)

## Summary

Team-authored investigation issue with a real, non-holding-bin milestone (1.141.0) — the hard keep-open rule applies regardless of other evidence. A maintainer has since confirmed a concrete Windows repro (sandboxed PowerShell fails against managed filesystem policy), but the broader design work (how to reconcile local vs managed filesystem permissions, required host-generated access contract) is still open.

## Change summary

Define how Agent Host sandbox filesystem permissions should reconcile local settings with managed policy, including required read access for VS Code-generated shell-init scripts, and surface actionable errors when reconciliation fails.

## Best solution

Design the runtime contract for distinguishing requested vs. applied filesystem grants (building on the mitigation in PR #338274) and surface an actionable error (naming the required path, e.g. C:\) instead of the generic 'host-capability' failure when managed policy can't satisfy a required grant such as PowerShell's filesystem enumeration need.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/sessionSandbox.ts`, `src/vs/platform/agentHost/node/copilot/sandboxConfigForSdk.ts`, `src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/platform/agentHost/test/node/copilotAgentSession.test.ts`
- **Validation:** A test (or manual check) confirming that under a managed filesystem policy restricting grants, launching a sandboxed PowerShell session either succeeds (grant reconciled) or surfaces an actionable error naming the missing required path, rather than the current generic host-capability failure.
- **Behavior:**

  > When a session's requested filesystem sandbox configuration (including directories needed for shell-init scripts) is rejected due to a managed policy conflict, the system must not silently claim the requested grants were applied. Operations depending on a grant that wasn't actually applied (e.g., registering a shell-init script, or running PowerShell which needs filesystem enumeration) should be deferred/retried or surfaced with an actionable message identifying the specific missing access, instead of continuing silently or failing with only a generic host-capability error.
- **Trace:**

  > PR https://github.com/microsoft/vscode/pull/338274 added logging-and-continue behavior for managed_sandbox_policy_conflict in copilotSessionLauncher.ts/copilotAgentSession.ts, retaining the runtime's last-applied config without confirming which requested grants succeeded. The shell-init dependency (materializing scripts under agentHost/shellInit/<session>/<instance>/init.sh and including that dir in requested read grants) was flagged as unresolved in https://github.com/microsoft/vscode/pull/338274#discussion_r4117181924 — existing tests in copilotAgentSession.test.ts document that unreadable init scripts can be silently skipped. rwoll's comment shows a live instance: sandboxed PowerShell on Windows fails outright unless C:\ is manually granted, meaning the current flow doesn't reconcile the runtime's actual filesystem-enumeration requirement with managed restrictions. Keep the existing managed-policy enforcement and the don't-duplicate-the-runtime's-parser constraint; the open question is the contract for reporting applied-vs-requested grants and the user-facing error for unreconcilable requirements.
- **Open decisions:**
  - Should a managed_sandbox_policy_conflict reject the filesystem update wholesale (current behavior) or allow the runtime to apply partial/per-path grants, and how should callers distinguish requested vs. actually-applied paths?
  - What is the required runtime contract/API for host-generated access needs (shell-init scripts, session attachments) so VS Code can know definitively whether a required grant was applied before depending on it?
  - When a required grant (e.g., PowerShell's filesystem enumeration need) can't be satisfied under managed policy, should VS Code surface a specific actionable message (naming the missing path/capability) instead of the generic host-capability failure, and should it offer a way to defer/retry the dependent operation?
