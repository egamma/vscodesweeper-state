# Issue #338293 — Agent Host: reconcile filesystem permissions with managed sandbox policies

[https://github.com/microsoft/vscode/issues/338293](https://github.com/microsoft/vscode/issues/338293)

## Summary

Fresh (same-day), team-authored investigation issue into reconciling Agent Host sandbox filesystem permissions between local settings and managed policies; the linked PR #338274 only logs/avoids failing on conflict, it does not reconcile permissions, so real design work remains — keep open.

## Change summary

Define how Agent Host sandbox filesystem grants (including shell-init script read access) should be reconciled when local settings conflict with runtime-managed sandbox policies, and ensure rejected grants aren't treated as applied.

## Best solution

Design and implement a runtime-contract for distinguishing requested vs. applied filesystem grants (covering shell-init scripts and session attachments), deferring/retrying dependent operations when grants are rejected, across sessionSandbox.ts / sandboxConfigForSdk.ts / copilotSessionLauncher.ts / copilotAgentSession.ts.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/sessionSandbox.ts`, `src/vs/platform/agentHost/node/copilot/sandboxConfigForSdk.ts`, `src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/platform/agentHost/test/node/copilotAgentSession.test.ts`
- **Validation:** Extend the shell-init scripts test suite in copilotAgentSession.test.ts to cover first use, restored sessions, already-granted paths, rejected updates, and successful retries, asserting dependent operations (e.g. script registration) are deferred/retried rather than treated as ready when a grant was rejected.
- **Behavior:**

  > When a managed filesystem policy conflicts with locally requested sandbox grants (including shell-init script read access), the effective/applied permission set — not the merely-requested one — must be tracked, and any operation depending on a rejected grant must be deferred or retried rather than proceeding as if the grant succeeded, across Windows/macOS/Linux.
- **Trace:**

  > PR https://github.com/microsoft/vscode/pull/338274 (discussion at https://github.com/microsoft/vscode/pull/338274#discussion_r4117181924) added conflict logging and fallback to the runtime's last applied config in copilotSessionLauncher.ts's applySandboxConfig and copilotAgentSession.ts's _applyEffectiveSandboxConfig, but does not compose managed filesystem restrictions with local settings, nor gate shell-init script registration (_applyEffectiveShellInitScripts, _sandboxExtraReadonlyPaths) on confirmed-applied grants. Boundary: preserve runtime-side managed enforcement and do not duplicate the runtime's policy parser in VS Code; do not change managed enablement/bypass/outbound-restriction handling, which is already resolved elsewhere.
- **Open decisions:**
  - What is the runtime-owned contract for combining local filesystem preferences with managed restrictions — does VS Code need a way to query the runtime's effective/applied grant set distinct from the requested one?
  - When a required grant (e.g. for a shell-init script) is rejected, should the dependent session/turn startup be blocked, retried automatically, or proceed in a degraded mode, and how is that surfaced to the user?
  - Should already-materialized shell-init scripts be re-validated against the effective sandbox on every session resume, or only on first creation?
