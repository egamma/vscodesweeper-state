# Issue #12463 — Allow to specify the tsconfig.json filename explicitly 

[https://github.com/microsoft/vscode/issues/12463](https://github.com/microsoft/vscode/issues/12463)

## Summary

Keep open: current VS Code still lacks an explicit language-service project configuration selector, and the documented workarounds require changing the project's configuration files. This is an accepted, well-supported request with 114 upvotes; the related closed reports point here rather than providing a replacement canonical.

## Change summary

Allow users to explicitly choose a differently named or located TypeScript project configuration for editor language features.

## Best solution

Design an explicit project-selection contract for the built-in TypeScript language features, coordinated with tsserver rather than duplicating its configuration parsing in VS Code. Preserve automatic discovery when no override is selected and define how selection affects files shared by multiple projects.

## Plan brief

- **Likely files:** `extensions/typescript-language-features/package.json`, `extensions/typescript-language-features/src/configuration/configuration.ts`, `extensions/typescript-language-features/src/tsServer/bufferSyncSupport.ts`, `extensions/typescript-language-features/src/typescriptService.ts`, `extensions/typescript-language-features/src/tsconfig.ts`
- **Validation:** Create a workspace with tsconfig.client.json and tsconfig.server.json using observably different compiler options and a shared source file. Verify that explicit selection changes editor diagnostics and project configuration attribution, that switching selections updates already-open files, and that clearing the selection restores ordinary discovery. Include a configuration under a config/ subdirectory and verify that build-task configuration remains independent.
- **Behavior:**

  > Users need to choose which existing TypeScript configuration governs editor language features without adding or rewriting a conventionally named tsconfig.json. The chosen configuration may have a custom filename or live outside the source directory. Acceptance should demonstrate that selection changes diagnostics for a shared file, switching updates open documents, and clearing the override restores normal project discovery. Existing compiler-task behavior must remain independent.
- **Trace:**

  > SyncedBuffer.open in extensions/typescript-language-features/src/tsServer/bufferSyncSupport.ts sends document content and a workspace projectRootPath, leaving project association to tsserver; it does not supply a selected configuration. TypeScriptServiceConfiguration in src/configuration/configuration.ts contains no configuration-file override, while openProjectConfigForFile in src/tsconfig.ts only queries and opens the configuration already chosen by the server. Package task definitions support a tsconfig path for compilation, which does not solve language-service selection. The maintainer constraint at https://github.com/microsoft/vscode/issues/12463#issuecomment-255772983 is to avoid reproducing tsserver's config parsing and discovery in the client. https://github.com/microsoft/vscode/issues/18140#issuecomment-271461393 discusses external-project protocol support but leaves the VS Code design unresolved. Current protocol feasibility and project-switch lifecycle still need investigation; do not assume the historical protocol limitation remains unchanged.
- **Open decisions:**
  - Should selecting a configuration establish one preferred project for the workspace folder, or should users be able to select different projects for individual files shared by multiple configurations?
  - When an explicitly selected configuration excludes an opened file, should that file retain normal automatic project discovery or be treated as outside the selected project?

## Evidence

- **Current language-service path:** extensions/typescript-language-features/src/tsServer/bufferSyncSupport.ts:171–190 constructs document-open requests with file, fileContent, projectRootPath, script kind, and plugins, but no user-selected configuration filename. TypeScriptServiceConfiguration in src/configuration/configuration.ts likewise exposes no project-config override.
- **Existing capabilities do not cover selection:** extensions/typescript-language-features/src/tsconfig.ts:openProjectConfigForFile asks tsserver for projectInfo and opens the returned configFileName; it does not select a different project. The package.json task-definition tsconfig property and src/task/taskProvider.ts configure compiler tasks, not editor project membership. Schema associations for tsconfig.*.json provide JSON support, not language-service project selection.
- **Workarounds and product boundary:** The supplied discussion describes tsconfig.json wrappers using extends, separate conventional configs in subdirectories, and build-only ts-node options. These can help particular layouts but do not provide the requested editor-only selection among existing configurations, especially when projects share files.

This establishes a design constraint, not evidence that the request has been implemented.
