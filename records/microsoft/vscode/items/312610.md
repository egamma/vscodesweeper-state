# Issue #312610 — [critical] new GitHub Copilot sessions never appear in list and are irretrievable if Copilot enabled after workspace opened

[https://github.com/microsoft/vscode/issues/312610](https://github.com/microsoft/vscode/issues/312610)

## Summary

Keep open as a high-impact sessions bug: the reporter confirmed a repeatable lifecycle condition where enabling Copilot after workspace startup leaves newly created sessions absent from the Sessions list and makes pending edits irretrievable after navigation or restart.

## Change summary

Refresh chat-session discovery and pending edit-session state when Copilot becomes enabled after an already-open workspace has initialized.

## Best solution

Make the Sessions model react to a post-startup Copilot enablement transition, reload persisted workspace chat sessions, and restore the matching editing-session state so switching sessions or restarting cannot strand a saved conversation or implicitly lose its pending-change workflow.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/chatService.ts`, `src/vs/workbench/contrib/chat/browser/chatSessions.contribution.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingService.ts`
- **Validation:** Add a lifecycle regression test that initializes a workspace with Copilot unavailable, transitions it to enabled without restarting, creates a chat session with pending edits, and verifies the session appears immediately and remains selectable with pending edit state intact after switching sessions and restoring the workspace.
- **Behavior:**

  > When Copilot is enabled for an already-open workspace, newly created chat sessions must immediately appear in the Sessions list without requiring a window restart or global enablement. Switching to another session and back must preserve access to the original session and its pending accept/reject edits. Restarting must restore the same persisted session and pending editing state rather than making edits appear implicitly accepted.
- **Trace:**

  > The reporter confirmed that the session JSONL and matching chatEditingSessions directory are written, so creation and persistence occur while the visible Sessions model remains stale after the enablement transition. The trace should follow the runtime Copilot enablement/entitlement change into session-history initialization and refresh, then verify how the matching chat editing session is attached during navigation and restore. Related https://github.com/microsoft/vscode/issues/311898 explains why workspace enablement may occur after startup but does not own this downstream refresh defect; https://github.com/microsoft/vscode/issues/311981 covers a different archived/view-state desynchronization. Preserve behavior for Copilot-enabled-at-startup workspaces and do not broaden the change into global enablement persistence.

## Evidence

- **confirmed reproduction:** The reporter isolated the trigger on VS Code 1.117: start with GitHub Copilot disabled, enable it for the workspace after startup, create a session, and observe that it never appears under Older or Archived; enabling Copilot globally makes the missing session reappear.
- **persisted data:** The missing session's UUID-backed JSONL remained in workspaceStorage/chatSessions and a matching directory remained in workspaceStorage/chatEditingSessions, showing that persisted session data existed while the visible session model omitted it.
- **impact:** After navigating to another session and restarting, the reporter could no longer return to the hidden session or accept/reject its in-progress edits; the files appeared accepted, creating a concrete pending-state and workflow-loss risk.
- **related but not canonical:** https://github.com/microsoft/vscode/issues/311981 concerns archived/view-state desynchronization and is closed; it does not cover the same post-startup Copilot-enablement symptom required for a duplicate close on this re-reviewed item.
- **related enablement issue:** https://github.com/microsoft/vscode/issues/311898 concerns persistence of per-workspace Copilot enablement and is closed; it can expose this defect repeatedly but does not itself own the missing-session refresh behavior.
