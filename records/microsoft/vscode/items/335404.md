# Issue #335404 — Github Copilot Tool-result truncation splits UTF-16 surrogate pairs → HTTP 400 `invalid_request_body` on OpenAI-family models (Claude models unaffected)

[https://github.com/microsoft/vscode/issues/335404](https://github.com/microsoft/vscode/issues/335404)

## Summary

The exact defect — a truncated tool result leaving a lone UTF-16 surrogate that `JSON.stringify` escapes into a form strict server-side JSON parsers reject with `invalid_request_body` — is already fixed on current main via a dedicated JSON-serialization sanitizer used by every network fetcher, with a test that reproduces this precise scenario.

## Change summary

Tool-result truncation (e.g. grep_search) can split a UTF-16 surrogate pair, and the resulting lone surrogate survives into the request JSON, causing OpenAI-family model requests to fail with HTTP 400 `invalid_request_body` (Claude models tolerate it).

## Best solution

Keep the existing fix: `stringifyJsonBody` in `extensions/copilot/src/platform/networking/common/jsonBody.ts` (used by `nodeFetcher.ts`, `baseFetchFetcher.ts`, and `chatWebSocketManager.ts`) already replaces unpaired surrogates with `\uFFFD` before any request body is sent, which prevents the reported 400 regardless of which tool introduced the lone surrogate. The separate, more cosmetic gap — that `findTextInFilesTool.tsx`'s long-line/grep truncation (`preview.slice(...)` around lines 557–681) isn't surrogate-boundary-aware the way `readFileTool.tsx` already is — is a good small follow-up for polish but is no longer what causes request failures.
