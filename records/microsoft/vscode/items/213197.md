# Issue #213197 — Custom labels: support full file name variable

[https://github.com/microsoft/vscode/issues/213197](https://github.com/microsoft/vscode/issues/213197)

## Summary

The requested full-file-name variable remains absent on current main. Although the reporter confirmed a two-pattern workaround, a maintainer explicitly kept the request open because a dedicated variable would make this scenario easier, and the Backlog milestone supports retaining it.

## Change summary

Add a custom editor-label template variable that returns the complete file name, including all extensions and leading dots.

## Best solution

Provide one documented custom-label variable for the complete basename so `${dirname}` can be combined with an exact file name without extension-sensitive pattern rules, while preserving the existing `${filename}` and `${extname}` semantics.

## Plan brief

- **Likely files:** `src/vs/workbench/services/editor/common/customEditorLabelService.ts`, `src/vs/workbench/browser/workbench.contribution.ts`, `src/vs/workbench/services/editor/test/browser/customEditorLabelService.test.ts`
- **Validation:** Add and run a targeted CustomEditorLabelService unit test showing that the chosen variable returns `Makefile`, `.nvmrc`, `.markdownlint.json`, and `file.tar.gz` unchanged, while existing filename and extname tests remain unchanged.
- **Behavior:**

  > Custom editor-label templates can include the complete file name as one variable. It must preserve leading dots and every extension, returning `Makefile`, `.nvmrc`, `.markdownlint.json`, and `file.tar.gz` exactly as named. Existing `${filename}`, `${extname}`, and `${extname(N)}` behavior must remain unchanged.
- **Trace:**

  > CustomEditorLabelService.applyTemplate in src/vs/workbench/services/editor/common/customEditorLabelService.ts limits recognized variables through `_parsedTemplateExpression`; `${filename}` is derived with `_filenameCaptureExpression`, while extensionless `${extname}` substitutions intentionally remain literal. The configuration documentation in src/vs/workbench/browser/workbench.contribution.ts exposes the same limited set, and src/vs/workbench/services/editor/test/browser/customEditorLabelService.test.ts pins the edge cases reported here. The boundary is the custom-label template contract: do not change existing filename or extension parsing semantics. The reporter's two-pattern workaround is valid but does not remove the requested convenience API.
- **Open decisions:**
  - What stable public token name should represent the complete basename: `${fullFileName}`, `${basename}`, or another documented name?

## Evidence

- **current source:** src/vs/workbench/services/editor/common/customEditorLabelService.ts recognizes only `${dirname}`, `${dirname(N)}`, `${filename}`, `${extname}`, and `${extname(N)}`; no complete-basename variable exists.
- **documented surface:** src/vs/workbench/browser/workbench.contribution.ts documents the same variable set for `workbench.editor.customLabels.patterns`, with `${filename}` explicitly excluding the extension.
- **current behavior:** src/vs/workbench/services/editor/test/browser/customEditorLabelService.test.ts confirms `${filename}.${extname}` leaves `${extname}` literal for extensionless files and dotfiles, while `${filename}` truncates `.markdownlint.json` to `.markdownlint`.
- **maintainer intent:** A maintainer said a `fullFileName` variable could make the scenario easier and deliberately left https://github.com/microsoft/vscode/issues/213197 open; the reporter later confirmed only that the two-pattern workaround covers their cases.
