# Issue #335818 — Unavailable automations warning does not explain the problem or how to fix it

[https://github.com/microsoft/vscode/issues/335818](https://github.com/microsoft/vscode/issues/335818)

## Summary

Confirmed real gap in source: the Automations view's unavailable-provider descriptor (`IAutomationProviderDescriptor` in src/vs/workbench/contrib/chat/common/automations/automationService.ts) only carries `id`/`label`, with no reason field, so when the unavailable-providers list is empty the UI falls back to the fully generic 'Some automations are unavailable' string with no diagnostic detail or recovery action; team-authored and still open, so this stays open regardless.

## Change summary

The Automations view's 'unavailable' warning doesn't say which automations/providers are affected, why, or how to fix it.

## Best solution

Extend the automation provider unavailability model with a reason (disconnected / disabled / unsupported) and a recovery action, then have automationsView.ts / automationCataloguePresentation.ts surface both instead of the generic fallback string — this spans each provider implementation (agentHost, remoteAgentHost, copilotChatSessions) so it needs a short design pass before implementation.

- **Trace:**

  > Root cause: IAutomationProviderDescriptor (src/vs/workbench/contrib/chat/common/automations/automationService.ts:241) has no reason/cause field, so formatUnavailableAutomationsMessage (automationCataloguePresentation.ts:9-17) can only name providers, never explain why they're unavailable, and falls back to the generic string when the provider list itself is empty. automationsView.ts's renderUnavailableState/renderPartialState (lines ~876-934) only ever attach a generic 'create automation' button, never a reason-specific recovery action. Where uncertainty starts: which unavailability reasons exist across providers (agentHost/remoteAgentHost/copilotChatSessions), and what recovery action (reconnect, re-enable extension, sign in) each maps to — that taxonomy and per-provider wiring needs a maintainer decision before implementation. Related: https://github.com/microsoft/vscode/issues/330974 (a narrower, different automation-run-failure case) and the referenced https://github.com/microsoft/vscode/issues/335507.
- **Open decisions:**
  - What unavailability reasons should be modeled (disconnected, disabled, unsupported, auth-expired, etc.) and where do they live — on IAutomationProviderDescriptor or a separate diagnostics API?
  - What recovery action maps to each reason, and does it differ per provider (agentHost vs remoteAgentHost vs copilotChatSessions)?
  - Should the per-provider detail also apply to the full-unavailable state (renderUnavailableState) or only the partial banner (renderPartialState)?

## Evidence

- **generic fallback string:** automationCataloguePresentation.ts:16 returns localize('automationsPartialUnavailable', "Some automations are unavailable.") whenever unavailableProviders.length === 0, matching the screenshot exactly.
- **no reason data:** IAutomationProviderDescriptor (src/vs/workbench/contrib/chat/common/automations/automationService.ts:241-244) only has id/label — there's no field for why a provider is unavailable, so the UI structurally cannot explain the cause today.
- **no recovery action:** renderUnavailableState() and renderPartialState() in automationsView.ts only attach a 'create automation' button (renderStateCreateButton) — no reconnect/enable/reconfigure action tied to the unavailability.
