# Issue #333951 — Chat: allow an inline file reference to display a readable label instead of the raw basename

[https://github.com/microsoft/vscode/issues/333951](https://github.com/microsoft/vscode/issues/333951)

## Summary

Current main still hardcodes the basename for inline file-reference text, while preserving the URI separately. This is a valid, unresolved chat UX request that needs a product decision about how readable labels are chosen and persisted.

## Change summary

Allow inline chat file references to show concise, readable text independently of the referenced file's basename and URI.

## Best solution

Give inline file references a presentation label distinct from their URI and canonical prompt representation, while retaining an unambiguous accessible indication of the actual file. The chat area should first choose whether labels come from document metadata, an editable per-reference alias, or a configurable naming rule.

- **Validation:** Add completion and request-parser tests showing that a file with an unreadable basename can render a chosen readable label while the resulting variable entry retains the original URI and the intended prompt text; manually verify keyboard editing and screen-reader output in the chat input.
- **Behavior:**

  > An inline file reference can display concise, readable text even when the underlying filename is long or machine-generated. Selecting, editing, submitting, restoring, and hovering the reference must continue to identify the original URI without ambiguity. Existing basename-based references remain compatible, and keyboard and screen-reader users can determine both the readable label and the referenced file.
- **Trace:**

  > The built-in completion path in src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts constructs its visible token directly from `getUriBasenameLabel(resource)` and separately records the URI in IDynamicVariable.data. ChatDynamicVariableModel in src/vs/workbench/contrib/chat/browser/attachments/chatDynamicVariables.ts tracks the inserted text by range and removes a reference when that text is edited without a preserved match. IDynamicVariable and ChatRequestDynamicVariablePart already distinguish editor text, optional prompt text, full name, and underlying data in src/vs/workbench/contrib/chat/common/attachments/chatVariables.ts and src/vs/workbench/contrib/chat/common/requestParser/chatParserTypes.ts. The uncertainty starts at the product contract for obtaining, editing, and persisting the presentation label; attachment-chip behavior, URI identity, and ordinary basename references should remain unchanged.
- **Open decisions:**
  - Should the readable label be automatically derived from document metadata, explicitly edited per reference, selected through a setting, or support a defined combination of these behaviors?
  - Should the model-visible prompt contain the readable label, the canonical file token, or both, while the variable data continues to carry the URI?
  - If users can define aliases, are they scoped to one insertion or draft, remembered for the file, or persisted as workspace configuration?
