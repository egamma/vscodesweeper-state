# Issue #297587 — Tool descriptions don't mention any languages

[https://github.com/microsoft/vscode/issues/297587](https://github.com/microsoft/vscode/issues/297587)

## Summary

The reopened defect is present on current main: rename and usages descriptions intentionally omit language names, and the tests enforce that behavior. The pre-reopen fix cannot justify closure, and no newer canonical issue or open fixing PR owns the remaining work.

## Change summary

Make the rename and code-usages tool descriptions communicate which languages are currently supported, including in the tools picker and model-facing request.

## Best solution

Reconcile the requirement to expose supported languages with the newer requirement that model-facing tool definitions remain stable during a request. The likely end state is a dynamically refreshed user-facing description plus an explicitly chosen, stable model-facing representation, with provider-dependent registration behavior settled at the same time.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/tools/renameTool.ts`, `src/vs/workbench/contrib/chat/browser/tools/usagesTool.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatToolPicker.ts`, `src/vs/workbench/contrib/chat/test/browser/tools/renameTool.test.ts`, `src/vs/workbench/contrib/chat/test/browser/tools/usagesTool.test.ts`
- **Validation:** Extend the rename/usages tool unit tests and tools-picker coverage to register providers incrementally and assert the chosen language-list and registration semantics after each change; run the corresponding targeted suites with scripts/test.sh --grep "RenameTool|UsagesTool|ChatToolPicker".
- **Behavior:**

  > The Rename Symbol and List Code Usages tool descriptions identify the languages currently supported wherever the agreed product contract requires that information, including the tools picker. The displayed support information updates when language providers are added or removed. Tool definitions supplied to an active model request remain valid under the chosen stability contract. The behavior when no provider exists is explicit and covered by tests rather than silently drifting between unconditional and provider-dependent registration.
- **Trace:**

  > The current descriptions originate in RenameTool.getToolData in src/vs/workbench/contrib/chat/browser/tools/renameTool.ts and UsagesTool.getToolData in src/vs/workbench/contrib/chat/browser/tools/usagesTool.ts. Both use StaticModelDescription and generic userDescription values; their tests explicitly require descriptions to remain byte-stable and omit language identifiers. The tools picker renders userDescription via createToolTreeItemFromData in src/vs/workbench/contrib/chat/browser/actions/chatToolPicker.ts. PR https://github.com/microsoft/vscode/pull/297684 previously generated language-aware descriptions and provider-dependent registration, but the issue was reopened after its dynamic updates did not reach the picker. The boundary is these two built-in symbol tools and their presentation/registration lifecycle; other language-model tools and unrelated picker behavior should remain unchanged.
- **Open decisions:**
  - Should the current language list be dynamic only in the user-facing tools picker while modelDescription remains stable, or must each model request also receive a language-list snapshot?
  - When no matching provider is registered, should these tools be absent or remain available with a stable description and return an unsupported-language error when invoked?
