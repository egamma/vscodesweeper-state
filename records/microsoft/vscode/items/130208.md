# Issue #130208 — Ctrl+f overwrites X11's Primary selection buffer.

[https://github.com/microsoft/vscode/issues/130208](https://github.com/microsoft/vscode/issues/130208)

## Summary

The behavior remains on current main and originates in Electron/Chromium propagating programmatic input selection to Linux PRIMARY. This older, well-diagnosed report should remain open as the canonical editor-find case.

## Change summary

Opening Find with a seeded term replaces the Linux PRIMARY selection buffer.

## Best solution

Coordinate an upstream Electron/Chromium correction or introduce a VS Code-specific selection mechanism that preserves PRIMARY without removing seeded Find behavior. Consolidate the narrower https://github.com/microsoft/vscode/issues/261170 request here if appropriate.

## Evidence

- **current source:** src/vs/editor/contrib/find/browser/findWidget.ts still calls `_findInput.select()` from `focusFindInput()`, while src/vs/base/browser/ui/inputbox/inputBox.ts implements that through native `HTMLInputElement.select()`.
- **upstream root cause:** https://github.com/electron/electron/issues/26563 documents the same programmatic-selection behavior in Electron; a 2025 comment confirms it remained present with Electron 37.2.3.
- **current confirmation:** https://github.com/microsoft/vscode/issues/261170 reports the same PRIMARY overwrite on VS Code 1.103 under X11 and Wayland and explicitly identifies this issue as covering the behavior.
- **workaround limitation:** `editor.find.seedSearchStringFromSelection` remains registered in src/vs/editor/common/config/editorOptions.ts, but setting it to `never` removes useful search seeding rather than preventing the unintended clipboard side effect.
- **related PR scope:** The open https://github.com/microsoft/vscode/pull/301137 targets ranged selection in quick inputs for https://github.com/microsoft/vscode/issues/167266; it does not change the Find widget's full-input selection path.
