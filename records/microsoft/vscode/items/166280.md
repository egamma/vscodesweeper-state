# Issue #166280 — VS Code regex referring to capture groups in replacement string does not work properly

[https://github.com/microsoft/vscode/issues/166280](https://github.com/microsoft/vscode/issues/166280)

## Summary

Keep open: current workspace replacement code still treats $1123 as literal text when it is the only replacement token. The same parameter-detection gate explains the commenter's named-group failure and why adding $2 makes it work.

## Change summary

Regex replacement fails to expand a numbered capture followed by multiple digits, and named captures expand only when another recognized token enables substitution.

## Best solution

Make workspace replacement consistently apply its existing JavaScript substitution semantics to valid replacement tokens, including numbered captures followed by digits and named references. Preserve existing escaping, case conversion, and literal treatment of unsupported syntax; broader editor named-group support is separate work.

## Evidence

- **Exact source reproduction:** In src/vs/workbench/services/search/common/replace.ts, ReplacePattern.parseReplaceString leaves _hasParameters false when a nonzero dollar reference is followed by three digits. For the reported pattern (Hello world) and replacement $1123, getReplaceString consequently returns the literal replacement instead of invoking String.replace, which would expand capture 1 followed by 123.
- **Named-group confirmation:** The same parser does not recognize $<name>. Thus $<l> $<t> $<r> bypasses substitution, while $<l> $2 $<r> sets _hasParameters through $2 and reaches the native replacement path. This conclusively matches both outcomes in the comment on https://github.com/microsoft/vscode/issues/166280.
- **Affected product path:** src/vs/workbench/contrib/search/browser/searchTreeModel/searchModel.ts constructs the search-service ReplacePattern when replacement text changes. src/vs/workbench/contrib/search/browser/searchTreeModel/match.ts calls getReplaceString for replacement results, establishing that this is the Ctrl+Shift+H path reported.
- **Existing behavior and test boundary:** src/vs/workbench/services/search/test/common/replace.test.ts currently expects hasParameters=false for hello$100 and hello$100a, encoding the faulty detection. In contrast, src/vs/editor/contrib/find/browser/replacePattern.ts consumes at most two reference digits and falls back to an available capture through _substitute. Neither parser implements ${1} syntax; supporting that syntax is not necessary to correct the reported $1123 outcome.
