# Issue #333213 — Source Control - Git - Show submodule diffs properly, or at least not an error

[https://github.com/microsoft/vscode/issues/333213](https://github.com/microsoft/vscode/issues/333213)

## Summary

The historical submodule-diff error remains explainable in current source: graph changes use ordinary file URIs without preserving the parent repository needed to resolve gitlinks. Keep this open and route it to Git; the reporter also confirms it persists on the latest version.

## Change summary

Opening a committed submodule change from the SCM graph or commit diff should display meaningful content rather than an unreadable git-resource error.

## Best solution

Make historical submodule changes readable in the built-in Git diff flow, using the selected parent-repository revisions rather than working-tree state. Rich submodule commit information can remain a separate enhancement; eliminating the erroneous file-read failure is the bounded bug.

- **Historical URI construction:** extensions/git/src/historyProvider.ts:339-355, GitHistoryProvider.provideHistoryItemChanges, passes the parent and selected commit to toMultiFileDiffEditorUris. extensions/git/src/uri.ts:65-88 constructs ordinary git URIs without submoduleOf or another parent-repository identifier. - **Failing repository and content resolution:** extensions/git/src/model.ts:967-1001 resolves git URIs by their filesystem path, preferring nested repositories and excluding a parent repository's submodule paths. Thus a historical submodule URI can resolve to the child repository even though its ref belongs to the parent, or fail repository lookup when the child is not open. extensions/git/src/fileSystemProvider.ts:197-241 then uses the ordinary buffer path and converts failures to FileNotFound; extensions/git/src/git.ts:1586-1610 runs git show --textconv ref:path, which is not a gitlink-aware content representation.

This existing capability does not represent two historical parent-repository revisions and cannot directly satisfy the graph report.
