## Plan brief

- **Likely files:** `extensions/git/src/model.ts`, `extensions/git/src/git.ts`, `extensions/git/src/test/smoke.test.ts`
- **Validation:** Compare baseline and candidate startup on the same Windows multi-repository workspace using Git trace output: record initial-scan duration and rev-parse --show-toplevel call counts. Verify that repositories and a submodule at folder1/moduleA appear without opening files inside them, and add an executable nested-submodule discovery regression in the Git extension test suite.
- **Behavior:**

  > Opening a multi-repository Windows workspace should make Source Control ready without excessive repeated repository-root discovery. Repositories and enabled submodules, including folder1/moduleA, must remain discoverable without manually opening their files. Acceptance requires lower discovery-call counts and improved initial-scan timing on an identical fixture, with the same expected repositories visible. The custom-build feedback must not be mistaken for confirmation that the performance problem was fixed.
- **Trace:**

  > Model.scanWorkspaceFolders in extensions/git/src/model.ts enumerates subfolders and submits each to the sequentialized Model.openRepository. Its initial exact-match check does not eliminate ordinary descendants of an already-open repository, so Model.getRepositoryRoot reaches Git.getRepositoryRoot in extensions/git/src/git.ts and spawns rev-parse --show-toplevel before discovering that the repository is already open. This repeated work is directly visible in current source, but its share of the reporter's total startup delay still needs measurement. https://github.com/microsoft/vscode/pull/313856 attempted to optimize this path and adjust initial submodule discovery, but is closed without merging. The reporter's nested-submodule feedback is at https://github.com/microsoft/vscode/issues/321621#issuecomment-4912944827. Preserve configured scan depth, submodule detection and limits, nested repository discovery, and existing trust and closed-repository behavior; do not broaden the work into unrelated graph or blame performance.
