# Issue #338036 — New Copilot SDK harness ignores chat.permissions.default and starts with Manual permissions

[https://github.com/microsoft/vscode/issues/338036](https://github.com/microsoft/vscode/issues/338036)

## Summary

Team-authored bug, so protected from a judgment close regardless — but the source confirms a real inconsistency: as VS Code migrates panel/editor chat from the local harness to the Agent Host Copilot SDK via `chat.defaultToCopilotHarness`, the classic `chat.permissions.default` setting stops being honored because agent-host new-session config deliberately only reads `chat.defaultConfiguration`.

## Change summary

Sessions created through the new Copilot SDK harness start in Manual permissions even when the user has `chat.permissions.default` set to `autoApprove`.

## Best solution

Decide how `chat.permissions.default` should interact with the newer `chat.defaultConfiguration` object setting for agent-host sessions created via the Copilot SDK harness migration path (fold it in as another precedence input, or explicitly document/migrate it) in `_initialNewSessionConfig` (baseAgentHostSessionsProvider.ts) and `copilotAgent.resolveChatConfig`.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts`
- **Validation:** A test in baseAgentHostSessionsProvider's config-seeding suite asserting `_initialNewSessionConfig` (or its replacement) reflects `chat.permissions.default: 'autoApprove'` for a Copilot-SDK-harness session when no `chat.defaultConfiguration` override is set.
- **Behavior:**

  > When a user sets `chat.permissions.default` to `autoApprove` (or `autopilot`), new chat sessions created through the Agent Host Copilot SDK harness (including sessions started after `chat.defaultToCopilotHarness` migrates panel/editor chat away from the local harness) should start with that permission level instead of defaulting to Manual/`default`. Sessions where the user or an enterprise policy has explicitly set `chat.defaultConfiguration.approvals` should keep that value taking precedence.
- **Trace:**

  > `_initialNewSessionConfig` in src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts seeds the initial `autoApprove` axis purely from `chat.defaultConfiguration` (policy > remembered pick > effective value) and explicitly documents that `chat.permissions.default` is skipped; `copilotAgent.resolveChatConfig` in src/vs/platform/agentHost/node/copilot/copilotAgent.ts then defaults an unset `autoApprove` to `'default'` (Manual). By contrast, the local chat widget (src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts `getDefaultPermissionLevel`) still reads `chat.permissions.default` directly. The migration flag `chat.defaultToCopilotHarness` (src/vs/platform/agentHost/common/agentHostEnablementService.ts) moves users from the local-harness path onto the agent-host path, which is where the setting stops applying. Boundary: do not change the enterprise-policy precedence (`chat.tools.global.autoApprove` clamp) or the remembered-pick behavior; a fix should only add `chat.permissions.default` as an additional, lower-precedence input (or otherwise reconcile the two settings) for agent-host sessions. Related: https://github.com/microsoft/vscode/issues/315381 fixed an analogous gap for the `openNewSessionSidebar` path.
- **Open decisions:**
  - Should `chat.permissions.default` be consulted for Copilot-SDK-harness sessions at all, or is the intended design that `chat.defaultConfiguration` is now the sole source of truth (with `chat.permissions.default` reserved for legacy local chat only, and its description/settings UI updated instead)?
  - If it should be consulted, at what precedence relative to `chat.defaultConfiguration`'s policy/remembered/effective layers?

## Evidence

- **intentional exclusion:** src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts `_initialNewSessionConfig` doc comment states: "The local-only `chat.permissions.default` setting is intentionally NOT consulted here" — only `chat.defaultConfiguration` (mode/approvals) and remembered picks feed the agent-host session's initial `autoApprove` value.
- **local-harness path still uses it:** src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts `getDefaultPermissionLevel()` reads `ChatConfiguration.DefaultPermissionLevel` ('chat.permissions.default') directly for the local chat widget's initial permission level — a different mechanism than agent-host sessions.
- **migration flag:** src/vs/platform/agentHost/common/agentHostEnablementService.ts defines `chat.defaultToCopilotHarness`: "When enabled, new editor and panel chat sessions default to the Agent Host Copilot SDK instead of the local harness" — this is the switch that moves users off the code path that honors `chat.permissions.default`.
- **SDK default fallback:** src/vs/platform/agentHost/node/copilot/copilotAgent.ts `resolveChatConfig` validates config with a hardcoded default of `AutoApprove: 'default'` when no autoApprove value is present in the incoming config, matching the reported 'Manual permissions' symptom.
- **prior related fix:** https://github.com/microsoft/vscode/issues/315381 fixed a similar gap for the `workbench.action.chat.openNewSessionSidebar` path; this report is about a different (Copilot SDK harness) session-creation entry point.
