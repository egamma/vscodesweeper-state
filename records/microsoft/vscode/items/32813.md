# Issue #32813 — [theming] Access theme's colors programmatically 

[https://github.com/microsoft/vscode/issues/32813](https://github.com/microsoft/vscode/issues/32813)

## Summary

This remains a well-supported API request with a real gap: extensions can reference workbench colors and observe theme kind changes, but cannot resolve the active theme's TextMate or semantic token colors programmatically. The `api-proposal` label and Backlog milestone require keeping this tracking issue open.

## Change summary

Expose active theme colors, especially resolved TextMate and semantic token colors, through the extension API.

## Best solution

Design and finalize a read-only theme API that lets extensions query resolved colors by TextMate scope or semantic token classification and react to theme changes, without requiring extensions to parse installed theme files or scrape webview CSS.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostTheming.ts`, `src/vs/workbench/api/browser/mainThreadTheming.ts`, `src/vs/workbench/services/themes/common/workbenchThemeService.ts`
- **Validation:** Add extension API tests that activate themes with inherited TextMate and semantic-token rules, query representative scopes/classifications, switch themes, and verify that returned resolved colors and change notifications match the active editor theme.
- **Behavior:**

  > Extensions need a supported way to obtain colors resolved from the active theme, including TextMate token scopes and semantic token classifications, rather than only opaque `ThemeColor` references or light/dark/high-contrast kind. Results must follow theme inheritance and user customizations and update predictably when the active theme changes. Existing workbench color references and webview CSS variables must remain compatible.
- **Trace:**

  > The current public surface exposes `ThemeColor` as a symbolic workbench-color reference and `window.activeColorTheme.kind`, while webviews receive CSS variables for registered workbench colors; none provides resolved token-scope colors. Theme resolution belongs to the workbench theme service and extension-host theming bridge, with the public contract declared in src/vscode-dts/vscode.d.ts. The thread's file-parsing and vscode-shiki-bridge approaches demonstrate the missing boundary but should not become the API contract. Keep this proposal broader than the closed specialized requests https://github.com/microsoft/vscode/issues/319753 and https://github.com/microsoft/vscode/issues/319754, and do not expose mutable internal theme objects.
- **Open decisions:**
  - Should the public contract expose resolved colors through targeted queries by TextMate scope and semantic token classification, or expose a read-only snapshot of the active resolved theme?
  - Should returned values be concrete color strings, symbolic references that VS Code resolves at render time, or both?
  - Which effective inputs must resolution include: theme inheritance, user token customizations, semantic highlighting rules, and language-specific scope matching?
