# Issue #317607 — Copilot overwriting newer files when switching between nested workspaces

[https://github.com/microsoft/vscode/issues/317607](https://github.com/microsoft/vscode/issues/317607)

## Summary

Still present on current main: restoring a stored chat editing session writes the cached 'current' snapshot back over the file with no check that the file changed on disk in the meantime, so externally saved edits are silently lost. Keeping open; the fix needs a product decision on what should happen when the file is newer than the snapshot.

## Change summary

Reopening a Copilot chat with unaccepted edits overwrites a file that was modified and saved elsewhere (e.g. from a nested workspace window) with the older cached edit state.

## Best solution

Make chat editing session restore detect that a file's on-disk content diverged from the stored snapshot's `current` value and stop silently writing it back — either skip the disk restore and mark the entry as externally changed, or prompt the user — in ChatEditingSession._initEntries / AbstractChatEditingModifiedFileEntry.restoreFromSnapshot.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedDocumentEntry.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingTextModelChangeService.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSessionStorage.ts`
- **Validation:** A test alongside src/vs/workbench/contrib/chat/test/browser/chatEditing/chatEditingSessionStorage.test.ts that stores a session with a Modified entry, changes the underlying file content to something else, then restores the session and asserts the file keeps the newer content (no silent revert to the snapshot's `current`).
- **Behavior:**

  > With pending (unaccepted) chat edits to a file, if that file is changed and saved outside the chat session and the session is later restored (reopening the conversation, another window, or a reload), the newer content must not be silently replaced by the session's cached edit state. The user's saved content is preserved, and the divergence is surfaced rather than resolved destructively. Existing restore behavior for files that did NOT change externally must be unaffected: pending edits still come back with their keep/undo decorations. Acceptance: a store→external-change→restore test keeps the newer content, and the existing chat editing session/storage tests still pass.
- **Trace:**

  > ChatEditingSession._init restores persisted state and calls _initEntries (src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts ≈981–1014), which for each snapshot entry in ModifiedFileEntryState.Modified passes restoreToDisk=true into AbstractChatEditingModifiedFileEntry.restoreFromSnapshot; the document implementation (chatEditingModifiedDocumentEntry.ts:216) calls ChatEditingTextModelChangeService.resetDocumentValues (chatEditingTextModelChangeService.ts:335), which replaces the whole model with the stored `current` text whenever it differs — with auto-save that reaches disk. Confirmed by reading those paths on current main and by `rg` showing no mtime/etag/stale/external-change check anywhere under chatEditing, plus `git log --since=2026-05-01` on the three files showing no related change. The stored snapshot (chatEditingSessionStorage.ts) is the natural place to carry whatever identity is needed to detect divergence. Boundary: do not change how live in-session edits are applied (acceptAgentEdits), the timeline/checkpoint restore semantics, or the notebook entry's own snapshot handling beyond the equivalent guard; the nested-workspace detail in the report is only an amplifier — the fix belongs in the generic restore path, not in workspace resolution. Report and repro video: https://github.com/microsoft/vscode/issues/317607
- **Open decisions:**
  - When a restored snapshot's `current` content differs from what is now on disk, what does the user see — a prompt to choose (as the reporter suggests), a silent skip that marks the entry as externally changed/stale, or the edits dropped entirely?
  - If the restore is skipped, what happens to the session's pending-edit state for that file: is it shown as no longer applicable (keep/undo controls removed) while the conversation's diff stays viewable in chat?
  - Should divergence be detected by comparing content against the snapshot, or by persisting a file identity (etag/mtime/version) in the stored session state — this changes the on-disk session state format for existing sessions?

## Evidence

- **unguarded disk restore:** src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts `_initEntries` (≈lines 981–1014): for every stored snapshot entry it computes `const restoreToDisk = snapshotEntry.state === ModifiedFileEntryState.Modified;` and calls `entry.restoreFromSnapshot(snapshotEntry, restoreToDisk)` — the file's current on-disk content is never compared against the snapshot.
- **write path:** chatEditingModifiedDocumentEntry.ts `restoreFromSnapshot` (line 216) forwards to ChatEditingTextModelChangeService.resetDocumentValues (chatEditingTextModelChangeService.ts line 335), which replaces the full model range with the stored `current` string whenever it differs — with auto-save on, that lands on disk. This is exactly the revert the reporter's video shows.
- **no staleness concept:** `rg` for mtime/stale/outOfDate/externalChange across src/vs/workbench/contrib/chat/browser/chatEditing finds no staleness or external-modification check on the restore path (only an unrelated `mtime: 0` in the notebook FS provider).
- **no fix on main:** `git log --since=2026-05-01` on chatEditingSession.ts, chatEditingSessionStorage.ts and chatEditingModifiedDocumentEntry.ts returns only 95903124 (GitHub authentication notifications), unrelated — the behavior is unchanged since the report.
- **nested workspace is an amplifier, not the cause:** The nested-workspace setup just makes two windows own sessions over the same physical file; the same loss occurs whenever the file is changed outside the session before the session state is restored.
