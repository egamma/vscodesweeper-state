# Issue #335941 — Please provide a more interactive, guided post-update experience when you make breaking changes

[https://github.com/microsoft/vscode/issues/335941](https://github.com/microsoft/vscode/issues/335941)

## Summary

A real gap remains despite the existing post-update tooltip and interactive release-note tryouts: current main can present curated highlights, but it does not identify changed defaults or offer to restore prior behavior. Route this to the update and release-notes owners for product design.

## Change summary

Provide a prominent post-update summary of breaking or default-setting changes, with guided actions to preserve or restore previous behavior.

## Best solution

Build on the existing post-update widget so release authors can prominently identify disruptive default changes and, where safe, offer an explicit action that preserves the user's previous behavior. The design should define which changes qualify and how actions interact with application, profile, workspace, and language-specific settings.

## Plan brief

- **Likely files:** `src/vs/platform/update/common/update.config.contribution.ts`, `src/vs/workbench/contrib/update/browser/postUpdateWidget.ts`, `src/vs/workbench/contrib/update/common/updateInfoParser.ts`, `src/vs/workbench/contrib/update/test/common/updateInfoParser.test.ts`, `src/vs/workbench/contrib/update/test/browser/releaseNotesTryouts.test.ts`
- **Validation:** Add update-contribution tests using versioned update metadata for a changed default, then verify that the post-update experience prominently describes the change, exposes the approved preservation action, and leaves unrelated settings and ordinary release highlights unchanged.
- **Behavior:**

  > After an update containing a designated breaking or default-setting change, VS Code prominently summarizes that change without requiring the user to scan the full release notes. When the release supplies a safe compatibility action, the user can explicitly preserve the previous behavior; declining it keeps the new default. Ordinary updates and users who already configured the affected setting must not receive misleading migration actions.
- **Trace:**

  > Current main registers the opt-in `update.showPostInstallInfo` setting in src/vs/platform/update/common/update.config.contribution.ts. PostUpdateWidgetContribution in src/vs/workbench/contrib/update/browser/postUpdateWidget.ts detects major/minor updates, fetches version-specific content through `getUpdateInfoUrl`, and renders metadata parsed by src/vs/workbench/contrib/update/common/updateInfoParser.ts; that metadata supports highlights and command buttons but has no breaking-change or prior-default semantics. ReleaseNotesTryouts, introduced by https://github.com/microsoft/vscode/commit/9d3c91bf3cbb51ab50c7032cd71c5a8798bd6b0b, supplies guided release-note interactions but does not compare or restore settings. Preserve the existing full release-notes path and avoid rewriting explicitly configured user, profile, workspace, folder, or language-specific values without an affirmative action. Uncertainty starts at the product contract for which changes qualify, whether prominence is automatic or opt-in, and which configuration scopes a compatibility action may affect.
- **Open decisions:**
  - Which release changes qualify for the prominent experience: every changed default, only explicitly designated breaking changes, or a maintainer-curated subset?
  - Should breaking-change notices appear automatically for all users, or only when `update.showPostInstallInfo` is enabled?
  - Should preserving old behavior write only an application-level preference, or may an action alter profile, workspace, folder, or language-specific configuration when those scopes determine the effective value?

## Evidence

- **existing post-update surface:** Current main registers `update.showPostInstallInfo` in src/vs/platform/update/common/update.config.contribution.ts and PostUpdateWidgetContribution in src/vs/workbench/contrib/update/browser/postUpdateWidget.ts. The opt-in widget detects a major/minor version change, fetches version-specific update content, and renders feature highlights and command buttons.
- **existing capability is partial:** The setting defaults to false, and the widget consumes curated remote markdown/metadata; the traced path has no mechanism that compares old and new configuration defaults or restores a user's prior effective behavior.
- **interactive release notes:** Commit https://github.com/microsoft/vscode/commit/9d3c91bf3cbb51ab50c7032cd71c5a8798bd6b0b added guided “Try This” interactions to release notes after this issue was filed, but that path demonstrates features rather than flagging changed defaults or reverting them.
- **related implementation history:** Merged PR https://github.com/microsoft/vscode/pull/311955 established the richer post-update widget and `update.showPostInstallInfo`; its structured feature metadata provides a plausible presentation surface, but does not satisfy the requested migration behavior.
- **canonical search:** No older open issue found in the related-item or keyword searches reports the same observable request for breaking-change summaries plus restoration of prior defaults; the re-reviewed-item duplicate bar is therefore not met.
