# Issue #320828 — [critical] `Codebase` stops GitHub Copilot Restore Checkpoint from working; history corrupted

[https://github.com/microsoft/vscode/issues/320828](https://github.com/microsoft/vscode/issues/320828)

## Summary

The repeated, detailed reproduction remains credible, and current main still has an interaction between checkpoint editing and unresolved authentication confirmations that can retain and later resubmit the original request. This should remain open as a chat-history correctness bug.

## Change summary

Editing or restoring past a request awaiting Codebase repository-access confirmation can duplicate prompts, resume the superseded request, and leave the conversation history in an unusable state.

## Best solution

Restoring or replacing a turn must invalidate its unresolved confirmation and prevent any saved request payload from being submitted later; add regression coverage spanning checkpoint restoration, request editing, and the Codebase authentication confirmation flow.

- **Validation:** Add a regression scenario that creates a Codebase authentication confirmation, restores or edits that request, submits a replacement without Codebase, and asserts that only the replacement remains, the old confirmation is unavailable, and no later confirmation action can enqueue or resume the original request.
- **Behavior:**

  > A request awaiting Codebase repository-access confirmation can be edited or removed with Restore Checkpoint without corrupting the conversation. Submitting the edited request produces exactly one replacement turn, and the superseded Grant/Not Now/Never Ask Again confirmation cannot later resume the original request. Earlier unaffected turns and ordinary authentication confirmations must continue to behave normally.
- **Trace:**

  > The permission prompt originates in extensions/copilot/src/platform/authentication/common/authenticationUpgradeService.ts, where showPermissiveSessionUpgradeInChat embeds the originating ChatRequest into confirmation data; handleConfirmationRequest later derives the resumed prompt from the saved data and chat history. Core renders and dispatches those buttons through ChatConfirmationContentPart, while checkpoint state and transcript removal run through chatEditingActions.ts and ChatWidget.acceptInput. The source establishes the vulnerable lifecycle but not whether the stale state is retained in the response content, checkpoint model, or extension-host history boundary. Keep normal authentication grant/decline semantics, unrelated confirmation widgets, queued requests, and file-edit snapshot restoration out of scope. https://github.com/microsoft/vscode/issues/319225 is related but tracks a different session-switch persistence symptom.

## Evidence

- **confirmed reproduction:** The reporter reproduced the same sequence repeatedly on June 10, August 7, and August 8: invoke Codebase, leave the repository-access confirmation unanswered, edit and resubmit without Codebase, then select Not Now; the original request resumes and duplicate turns remain. See https://github.com/microsoft/vscode/issues/320828.
- **authentication flow:** extensions/copilot/src/platform/authentication/common/authenticationUpgradeService.ts stores the complete originating ChatRequest in confirmation data (`{ authPermissionPrompted: true, ...data, context }`) and handleConfirmationRequest later reconstructs and resumes the previous request from chat history.
- **confirmation dispatch:** src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatConfirmationContentPart.ts keeps confirmation buttons attached to a response and sends a new request carrying the saved accepted/rejected confirmation data when a button is clicked.
- **checkpoint path:** src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingActions.ts restores the editing snapshot after marking a checkpoint, while src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts removes checkpoint-blocked transcript requests during a subsequent submission. The cross-step lifetime of the earlier confirmation needs explicit regression coverage.
- **related issue:** https://github.com/microsoft/vscode/issues/319225 is older and also concerns Restore Checkpoint, but its observable symptom is restored history reappearing after switching sessions rather than an unresolved Codebase confirmation duplicating and resuming a superseded request, so it does not meet the stronger re-review duplicate bar.
