# Issue #339569 — Copilot Inline Chat cannot apply edits to files in a WSL workspace

[https://github.com/microsoft/vscode/issues/339569](https://github.com/microsoft/vscode/issues/339569)

## Summary

Brand-new, well-documented report with clear steps and exact error text; I traced a concrete code mechanism in the Copilot extension's vendored URI/path code that would produce exactly this symptom (backslash-corrupted posix paths for a WSL remote file), but I can't confirm from source alone that this is the actual execution path for this user's setup, so this stays open pending a real WSL repro.

## Change summary

Copilot Inline Chat fails to apply generated edits to a file opened from a WSL remote workspace, with path errors showing the posix path corrupted into backslash form.

## Best solution

Confirm (with an actual Remote-WSL session) where the backslash corruption happens — `PromptPathRepresentationService.getFilePath`/`resolveFilePath` calling `uri.fsPath` for a `vscode-remote` URI while `isWindows()` is true — then make that path handling scheme-aware so WSL/remote posix paths are never run through Windows backslash conversion.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/prompts/common/promptPathRepresentationService.ts`, `extensions/copilot/src/util/vs/base/common/uri.ts`, `extensions/copilot/src/extension/tools/node/toolUtils.ts`

- **Behavior:**

  > When Copilot Inline Chat (Ctrl+I) is used in a window connected to a WSL remote workspace from a Windows host, a generated edit must apply to the correct file in the WSL filesystem. It must not emit or attempt to resolve a backslash-mangled path like `\home\<user>\...\hello.py`, and must not abort with 'Invalid input path' / 'too many failed edit attempts'. Acceptance: editing a WSL-opened file from Inline Chat succeeds end-to-end on a real Remote-WSL session, with no path heal/abort errors in the logs.
- **Trace:**

  > The quoted error text lines up with `uriToFsPath` in extensions/copilot/src/util/vs/base/common/uri.ts (~line 649), which replaces `/` with `\` in the computed fsPath whenever `isWindows` is true, with no guard for non-local (`vscode-remote`) schemes/authorities. `PromptPathRepresentationService.getFilePath` (extensions/copilot/src/platform/prompts/common/promptPathRepresentationService.ts, line 62) calls `uri.fsPath` for both `file` and `vscode-remote` URIs; `resolveFilePath` (line 75) and `resolveToolInputPath` (extensions/copilot/src/extension/tools/node/toolUtils.ts line 142) are the inverse path, and would mis-resolve a corrupted path back to a (wrong) local Windows URI. What's unconfirmed: why `isWindows()` would be true on this code path at all, since extensions/copilot/package.json declares no `extensionKind` and a Node extension defaults to running in the remote (WSL) extension host, where `isWindows` should be false — that routing needs to be checked against an actual Remote-WSL session before concluding this is the exact trigger. Do not change `uriToFsPath`'s behavior for genuine local `file://` URIs on Windows.
- **Open decisions:**
  - Confirm, with a real Remote-WSL session, which process/extension-host actually executes `PromptPathRepresentationService`/`resolveToolInputPath` for this scenario, and whether `isWindows()` is true there.

## Evidence

- **error text matches code:** The reported error 'File not found: \home\<user>\...\hello.py' matches the output of `uriToFsPath` in extensions/copilot/src/util/vs/base/common/uri.ts (lines ~634-652), which unconditionally does `value.replace(/\//g, '\\')` whenever `isWindows` is true, with no check that the URI is actually a local `file://` URI as opposed to a remote `vscode-remote://` (WSL) URI with a posix path.
- **call site:** extensions/copilot/src/platform/prompts/common/promptPathRepresentationService.ts `getFilePath()` (line 62) returns `uri.fsPath` for both `file` and `vscode-remote` schemes; if this executes with `isWindows()===true` the WSL file's posix path gets corrupted before being embedded in the prompt, and `resolveFilePath()`/`resolveToolInputPath` (same file line 75; extensions/copilot/src/extension/tools/node/toolUtils.ts line 142) then mis-resolves the model's response, producing the 'Invalid input path' / 'File not found' errors quoted in the report.
- **unresolved diagnostic question:** extensions/copilot/package.json declares no `extensionKind`, so by VS Code's default host-placement rules a Node extension normally runs in the WSL remote extension host (where `isWindows` would be false) rather than the local Windows UI host — I could not confirm from source alone why this code path would see `isWindows()===true` for this user; that needs an actual Remote-WSL repro to pin down.
