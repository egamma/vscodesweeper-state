# Issue #333013 — [Error] unhandlederror-View already awaiting revival

[https://github.com/microsoft/vscode/issues/333013](https://github.com/microsoft/vscode/issues/333013)

## Summary

This is a real regression with a traced root cause, and a fix is already up for review as an open PR — the issue should stay open until that PR lands, not be closed as a duplicate or completed.

## Change summary

Reopening/reviving a webview view (e.g. after a window reload) can throw 'View already awaiting revival' because a stale pending-revival entry is never cleaned up.

## Best solution

Land https://github.com/microsoft/vscode/pull/333021, which fixes the ordering bug: `WebviewViewPane` registers a `CancellationTokenSource` and a `toDisposable(() => source.cancel())` in the same `DisposableStore` in that order, so on dispose the token's emitter is disposed first and the later `source.cancel()` becomes a silent no-op (MutableToken.dispose() nulls `_emitter`, then cancel() checks `if (this._emitter)` and skips firing). This means `WebviewViewService.resolve`'s `onCancellationRequested` listener never fires, the pending `_awaitingRevival` entry for that viewType is never removed, and the next resolve for the same view type throws.

## Evidence

- **root cause traced:** src/vs/workbench/contrib/webviewView/browser/webviewViewPane.ts: `const source = this._webviewDisposables.add(new CancellationTokenSource()); this._webviewDisposables.add(toDisposable(() => source.cancel()));` — DisposableStore disposes its Set of disposables in insertion order, so `source.dispose()` runs before `source.cancel()`.
- **why cancel() no-ops after dispose:** src/vs/base/common/cancellation.ts MutableToken.dispose() sets `_emitter = null`; MutableToken.cancel() only fires `_emitter.fire()` when `_emitter` is truthy, so calling cancel() after dispose() never notifies listeners.
- **resulting stale state:** src/vs/workbench/contrib/webviewView/browser/webviewViewService.ts:128-160 relies on the cancellation firing to delete the `_awaitingRevival` entry; if it never fires, a later `resolve()` for the same viewType hits `throw new Error('View already awaiting revival')` at line 132.
- **open fix PR:** https://github.com/microsoft/vscode/pull/333021 — 'fix: fire webview view revival cancellation before disposing token (fixes #333013)', not yet merged (no matching commit on current main).
