# Issue #346134 — Reduce cloud sandbox feed connection eagerness

[https://github.com/microsoft/vscode/issues/346134](https://github.com/microsoft/vscode/issues/346134)

## Summary

Keep open for investigation: eligible signed-in accounts start the feed before discovering whether they have sandbox sessions. Existing settings permit disabling the feed, but do not provide demand-based subscription.

## Change summary

Reduce unnecessary cloud sandbox feed connections for accounts without cloud sessions.

## Best solution

Define when an account needs a feed subscription and preserve reliable discovery of its first cloud session, including sessions created elsewhere. Apply the agreed lifecycle consistently through the shared sandbox contribution used by both windows.

- **Trace:**

  > CloudSandboxSessionContribution._doDiscoverAndSeed() starts the optional feed after resolving the account but before listSessions(), without checking whether the account has known sessions. CloudSandboxSessionFeed.start() immediately enters negotiation and then opens a WebSocket when the service supplies credentials. The feed setting offers polling-only operation, and _pollInterval() already treats empty inventory differently, but neither establishes demand-based subscription. The shared contribution serves both windows; preserve account isolation, feature teardown, authoritative task reads, and sandbox host connection ownership. The documented subscribe-before-read ordering currently avoids a discovery/subscription gap, so changing eligibility requires an explicit first-session discovery contract.
- **Open decisions:**
  - What qualifies an account for a feed subscription: existing discovered sessions, prior cloud usage, or explicit interaction with Cloud?
  - For an account without a subscription, what discovery delay is acceptable when its first cloud session is created elsewhere?

## Evidence

- **Current subscription ordering:** src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxSessionContribution.ts:438-476 resolves the account, creates CloudSandboxSessionFeed, and awaits feed.start() before calling listSessions(). There is no known-session requirement at that subscription point.
- **Actual eligibility boundary:** CloudSandboxSessionContribution._isEnabled() requires cloud sandbox enablement and visible AI features; discovery also requires an account. CloudSandboxSessionFeed._doConnect() negotiates through connectSessionFeed() before constructing a WebSocket. The source therefore supports eagerness for eligible accounts, not literally every VS Code user.
- **Existing capability is partial:** remoteAgentHost.contribution.ts registers chat.agentHost.cloudSandbox.sessionFeed.enabled with default true. Setting it false selects polling without feed credentials or a socket; this manual global choice does not automatically avoid subscriptions for empty accounts. cloudSandboxSessionContribution.ts:_pollInterval() already reduces polling for accounts without known environments, but does not gate feed startup.
