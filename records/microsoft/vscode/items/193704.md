# Issue #193704 — Allow to store/resume open editors across Continue On transitions

[https://github.com/microsoft/vscode/issues/193704](https://github.com/microsoft/vscode/issues/193704)

## Summary

Keep open: editor-state transfer is implemented, but current source still leaves file URIs embedded in serialized editor strings outside the URI-conversion path. The original implementation preceded the reopening and does not establish that cross-environment restoration is complete.

## Change summary

Preserve and restore open editors across Continue Working On transitions using the destination workspace's resource URIs.

## Best solution

Complete editor-state portability through the edit-session transfer and editor-serialization paths, so restored tabs open corresponding destination resources rather than retaining source-environment URIs. Preserve existing editor restoration and destination dirty-editor protection.

- **Behavior:**

  > Continuing work on the same repository in another environment preserves open file editors and their group layout. Restored editors resolve to corresponding files in the destination workspace, not resources belonging to the source environment. Acceptance must cover a change of URI scheme or workspace root and preservation of existing dirty destination editors. Ordinary same-environment editor restoration remains unchanged.
- **Trace:**

  > The accepted transfer contract is documented in https://github.com/microsoft/vscode/issues/183449; the post-implementation failure is confirmed in https://github.com/microsoft/vscode/issues/193704#issuecomment-1877110271. EditorPart already exports user-targeted workspace state and applies external memento updates. FileEditorInputSerializer produces a JSON string, and EditorGroupModel stores that string inside the serialized grid state. WorkspaceStateSynchroniser.apply parses the outer storage object, while WorkspaceIdentityService.matches traverses URI objects without interpreting these nested strings; the file resource therefore reaches editor deserialization unchanged. The unresolved technical boundary is how portability interacts with the shared string-based serializer contract across editor types, not whether ordinary file tabs should follow the destination workspace. Preserve existing persisted-state compatibility, non-editor workspace-state consumers, and dirty-editor protection; custom-provider persistence mentioned in the thread is not established as the same defect.
