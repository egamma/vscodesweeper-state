# Issue #340707 — Agent Host high CPU on macOS with repeated catalog reconciliation retries (sourceUnresolvable)

[https://github.com/microsoft/vscode/issues/340707](https://github.com/microsoft/vscode/issues/340707)

## Summary

Thanks for the detailed report. The reporter saw about 35.8k 'sourceUnresolvable' retry logs in roughly 190s, along with sustained agent-host CPU of 140-190%. This was seen in two sessions, but the retries are not yet shown to cause the CPU load, so it stays open for diagnosis.

## Change summary

Agent Host burns high CPU on macOS while catalog reconciliation repeatedly retries unresolvable Claude and Copilot CLI session sources.

## Best solution

Find why reconciliation passes for sources that stay 'sourceUnresolvable' run at about 190/s. Then add backoff or a terminal state for persistently unresolvable sessions in agentHostCatalogReconciliationService.ts. Confirm with a CPU profile that this is the hot path.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentHostCatalogReconciliationService.ts`
- **Validation:** A reconciliation service test where a session source stays unresolvable. It should assert that retries are bounded or backed off rather than re-running continuously across scheduler ticks.
- **Behavior:**

  > With persistently unresolvable session sources, Agent Host must not run reconciliation retries continuously or burn significant CPU. Retries should back off, or stop until a relevant change occurs. Sessions that become resolvable must still be reconciled.
- **Trace:**

  > Retry outcomes are produced in agentHostCatalogReconciliationService.ts (sourceUnresolvable at about lines 402, 495 and 579) and logged in _logOutcomes at line 812. Passes are scheduled by _scheduleNextPass, which uses _minimumPassIntervalMs for follow-ups or _intervalMs for periodic passes. The reported rate of about 190 retries/s exceeds that pacing, so something re-triggers start() or the follow-up request path outside the scheduler. Where the uncertainty starts: which trigger drives it, and whether this loop is the CPU consumer. Do not change reconciliation correctness for resolvable sessions.
- **Open decisions:**
  - For sessions whose source stays unresolvable, should reconciliation back off exponentially or stop until a session-change event arrives?

## Evidence

- **log source:** src/vs/platform/agentHost/node/agentHostCatalogReconciliationService.ts:812 (_logOutcomes) logs every 'retry' outcome at info level. Line ~402 returns retry/sourceUnresolvable. Line ~495 and ~579 also return it from the source-resolution path.
- **scheduling:** _scheduleNextPass uses _minimumPassIntervalMs for follow-ups and _intervalMs otherwise. A rate of about 190 messages/s across 17 sessions does not fit that pacing, so the retry loop is not obviously bounded. I did not trace where it re-triggers.
- **causality not established:** The reporter says CPU and retries were only observed at the same time. Defender was also busy, and no CPU profile was provided.
- **repeat observation:** Comment 1 reports the same symptoms after restart, with 11 Claude and 6 Copilot CLI sessions affected.
