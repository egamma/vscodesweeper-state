# Issue #336998 — Chat Customizations: MCP: Too many different UI elements representing states

[https://github.com/microsoft/vscode/issues/336998](https://github.com/microsoft/vscode/issues/336998)

## Summary

Valid, source-confirmed UX complaint about the MCP page in the new Chat Customizations editor: current main really does layer a status badge, an enablement toggle, a 'forbidden' icon, and a context menu with multiple disable variants — plus uninstall only reachable (and only for some servers) via that menu. This was deliberately extracted from the broader issue https://github.com/microsoft/vscode/issues/335713 (older, item 4) to track the consolidation work on its own, so it stays open as its own tracker rather than being folded back.

## Change summary

The MCP servers page shows server enable/disable/running state through too many separate, inconsistent UI elements (badge, toggle, icon, menu).

## Best solution

Design a single, consolidated status/action representation for MCP server rows (state badge + enable/disable + uninstall) in mcpListWidget.ts, and make uninstall consistently available; this needs a maintainer/design pass before implementation given multiple valid design directions.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts`
- **Validation:** A manual/visual check that a given MCP server row shows a single consistent status+action affordance (no separate badge + toggle + forbidden icon + menu duplicating the same state), and that uninstall is available consistently across server types.
- **Behavior:**

  > On the Chat Customizations MCP page, each server row currently shows up to four separate state cues for essentially two facts (enabled/disabled and running/stopped): a running/stopped/disabled status badge, an enable/disable Switch, a grayed-out + circleSlash icon when disabled, and a context menu offering several more disable variants (profile/workspace/session). The goal is to reduce this to a smaller, coherent set of controls that clearly communicates state without duplication, and to make uninstall consistently reachable regardless of server type. Acceptance: a maintainer-reviewed design lands where each MCP server row conveys enabled/running state through one primary visual language, and uninstall works uniformly.
- **Trace:**

  > getMcpStatusPresentation() in mcpListWidget.ts (around line 634) builds the running/stopped/disabled badge; appendInstalledServerToggle() (~2099) independently renders a Switch for enable/disable; disabled rows also get a '.disabled' class plus Codicon.circleSlash (line 639); getContextMenuActions()/DisableMcpServerForWorkspaceAction/DisableMcpServerGloballyAction (~889-1020) add further disable-scope entries in the overflow menu, and that same menu is the only place uninstall appears, gated by server type. The boundary: this is a rendering/interaction consolidation within mcpListWidget.ts and the AI Customization MCP page only — it should not change the underlying ContributionEnablementState model, MCP connection lifecycle, or the enablement scopes (profile/workspace/session) themselves, only how they are surfaced. Where uncertainty starts: which controls survive the consolidation (e.g., does the badge merge into the toggle, does the menu keep the scope-specific disable options or move them elsewhere) and how/whether uninstall becomes a first-class, always-visible action — those are the open design decisions. Related: https://github.com/microsoft/vscode/issues/335713 (parent tracking issue with other MCP page polish items).
- **Open decisions:**
  - Should the running/stopped badge and the enable/disable toggle be merged into one control, or kept visually distinct but simplified?
  - Should the workspace/profile/session-scoped disable variants stay in the overflow menu, or surface through a different (e.g. dropdown-on-toggle) pattern?
  - Should uninstall become a consistently available, more prominent action for all MCP server types instead of a menu item gated by type?
