# Issue #336998 — Chat Customizations: MCP: Too many different UI elements representing states

[https://github.com/microsoft/vscode/issues/336998](https://github.com/microsoft/vscode/issues/336998)

## Summary

Fresh, concrete UX-consistency observation about the MCP page in Chat Customizations — confirmed in the current source that state is represented redundantly (status badge, switch, forbidden icon + grayout, and a menu), so this is a real design cleanup opportunity, not something to close.

## Change summary

The MCP customization page uses too many overlapping UI elements (badge, slider, forbidden icon, dropdown menu) to represent the same running/disabled state, and only the menu supports uninstall (inconsistently, not for all servers).

## Best solution

Consolidate the MCP list item's state representation in mcpListWidget.ts into fewer, clearer signals, and make uninstall available consistently from one place across all MCP server entries — this is a design call for the AI Customization view owners.

## Plan brief

- **Behavior:**

  > Each MCP server row in the Chat Customizations MCP page should represent its running/disabled/error state with a small, coherent set of indicators instead of stacking a status badge, a switch, a forbidden icon plus grayed-out styling, and a separate menu that duplicates the toggle. Uninstall should be available consistently across all MCP server entries, not only some.
- **Trace:**

  > mcpListWidget.ts builds the list item state from several independent pieces: a status badge (`plugin-list-item-status.mcp-runtime-status-badge`, updated via `updateStatus`/`getMcpStatusPresentation`), a `Switch` control for enable/disable, a `disabled` CSS class that also grays out and applies `Codicon.circleSlash` (getMcpStatusPresentation, ~line 751), and a separate dropdown/context menu that also offers disable and (only for some entries) uninstall. Confirmed via source read, not execution. Boundary: do not change the underlying enablement/connection-state model (McpConnectionState, McpServerStatus, isContributionDisabled) — only the presentation layer that surfaces it. Where uncertainty starts: which of these signals to drop or merge, and how uninstall should be exposed uniformly, are UI/UX decisions the AI Customization owners need to make.
- **Open decisions:**
  - Which single state indicator (badge vs. icon vs. grayout) should remain, and which should be dropped as redundant?
  - Should the enable/disable switch and the menu's disable action be merged into one control?
  - Should uninstall move out of the per-item menu into a location available uniformly for every MCP server type, and why is it currently missing for some?
