# Issue #313211 — Merge Editor is slow or fails to load files

Quick-diff disposal handling has changed since the report; neither that change nor the related SCM regression establishes that this loading failure is resolved.

## Change summary

Opening Resolve in Merge Editor after SCM diffs can leave large files loading indefinitely and prevent subsequent merge files from opening until restart.

## Best solution

Establish whether the blocked merge initialization is downstream of the SCM quick-diff regression or an independent unlimited merge computation, then restore completion and subsequent-file responsiveness. Consolidate with the related SCM issue only if the same cause is established, and coordinate with its existing fix candidate rather than starting competing work.

## Evidence

- **Reported trigger and impact:** https://github.com/microsoft/vscode/issues/313211 describes opening Resolve in Merge Editor after viewing SCM diffs on macOS arm64 in 1.117.0, particularly with files exceeding 10,000 lines. Loading can remain pending for subsequent files even after closing the affected tab; restart usually helps. No representative file or runtime profile was supplied, but the workflow is concrete enough to begin retesting.
- **Discussion and verified related issue:** RedCMD explicitly linked https://github.com/microsoft/vscode/issues/291982 in this issue's discussion. That older issue is currently OPEN and reports large SCM diffs blocking subsequent diffs, including outside SCM, with repeated confirmations and a bisect recorded at https://github.com/microsoft/vscode/issues/291982#issuecomment-4106025238. It is a strong related lead, but this report has not been tied to that bisected cause.
- **Current merge initialization path:** src/vs/workbench/contrib/mergeEditor/browser/mergeEditorInput.ts: MergeEditorInput.resolve awaits model.onInitialized. In browser/model/mergeEditorModel.ts, onInitialized waits for diffComputingState to become upToDate; browser/model/diffComputer.ts: MergeDiffComputer.computeDiff requests maxComputationTimeMs: 0. These dependencies explain how pending computation can leave initialization pending, but do not prove the reporter's files trigger it.
- **Shared worker and distinct possible triggers:** src/vs/editor/browser/services/editorWorkerService.ts: computeDiff routes through _workerWithResources and WorkerManager's reused EditorWorkerClient. Both MergeDiffComputer and src/vs/workbench/contrib/scm/browser/quickDiffModel.ts use this service; QuickDiffModel._diff defaults an unspecified computation limit to Number.MAX_SAFE_INTEGER. Shared infrastructure makes cross-editor blocking plausible, without establishing which computation caused this report.
- **Existing human fix candidate:** https://github.com/microsoft/vscode/pull/318314 remains OPEN and explicitly fixes https://github.com/microsoft/vscode/issues/291982. It changes Git quick-diff provision and main-thread editor diff information. It does not reference this issue, and its ability to fix Merge Editor loading has not been demonstrated.
- **Later change is not a verified fix:** Commit 8fd29eba502d88aaa69fb2b5572188d0f9699c95 adds an early disposed-model guard in QuickDiffModel.diff. Its diff addresses queued work accessing disposed models, not unlimited computation or MergeEditorInput.resolve, and it does not reference this issue; it is not sufficient provenance for a completed close.
- **Canonical-search result:** Also inspected https://github.com/microsoft/vscode/issues/270344, which supplies long-line comparison samples and later reports global diff blocking after removing the computation limit. https://github.com/microsoft/vscode/issues/276318 instead concerns missing Git revision resources. These distinguish plausible computation and resource-resolution failures; neither establishes a canonical owning this report's full underlying defect.
