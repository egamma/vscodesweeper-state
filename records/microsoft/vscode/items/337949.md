# Issue #337949 — Support Markdown Stylesheets in the New Markdown Editor

[https://github.com/microsoft/vscode/issues/337949](https://github.com/microsoft/vscode/issues/337949)

## Summary

Confirmed gap: the new rich-webview Markdown Editor's HTML generation only links its own editor.css and never reads the `markdown.styles` setting, unlike the legacy Markdown Preview which injects it via `#computeCustomStyleSheetIncludes`. Real, unimplemented feature request; not a duplicate of the narrower font-size issue.

## Change summary

The `markdown.styles` setting (custom CSS stylesheets) is applied to the Markdown Preview but not to the new rich webview Markdown Editor.

## Best solution

Port the preview's custom stylesheet injection (`#computeCustomStyleSheetIncludes` / `#getSettingsOverrideStyles` in documentRenderer.ts) into `MarkdownEditorProvider#getHtml`, reading `markdown.styles` from configuration and appending `<link>` tags for each resolved style URI, respecting the same relative-path resolution rules.

## Plan brief

- **Likely files:** `extensions/markdown-language-features/src/preview/markdownEditorProvider.ts`, `extensions/markdown-language-features/src/preview/documentRenderer.ts`, `extensions/markdown-language-features/package.json`
- **Validation:** A test in src/test/markdownEditorProvider.test.ts asserting the generated HTML includes a <link> for each configured markdown.styles entry, resolved the same way the preview resolves them.
- **Behavior:**

  > When `markdown.styles` is configured, the rich Markdown Editor's rendered content should load those stylesheets the same way the Markdown Preview does, so custom CSS shows consistently across both surfaces. Acceptance: opening a markdown file with `markdown.styles` set in the new editor visibly applies the custom CSS, and a test confirms the generated HTML includes a link tag per configured style path/URL.
- **Trace:**

  > MarkdownEditorProvider#getHtml (extensions/markdown-language-features/src/preview/markdownEditorProvider.ts, ~line 1026) builds the webview HTML with a hardcoded single stylesheet link to the bundled editor.css and never reads vscode.workspace.getConfiguration('markdown').get('styles'). The legacy preview's DocumentContentProvider in documentRenderer.ts already has the logic to do this (#computeCustomStyleSheetIncludes, #getSettingsOverrideStyles) and could be reused/ported. Do not change the legacy preview's rendering. Where uncertainty starts: the new editor's CSP (style-src is `${webview.cspSource} 'unsafe-inline'`, no `https:`/external), so remote/http(s) style URLs would need explicit CSP relaxation or resource-provider translation — a maintainer should confirm the intended trust/CSP model for user CSS in this newer, still-evolving editor before implementation.
- **Open decisions:**
  - Should the new editor honor the exact same `markdown.styles` resolution/CSP model as the legacy preview, or does the newer editor's stricter CSP warrant a different (e.g. more restricted) mechanism for custom CSS?

## Evidence

- **new editor has no styles support:** extensions/markdown-language-features/src/preview/markdownEditorProvider.ts #getHtml() only adds `<link rel="stylesheet" href="${styleUri}" />` for the bundled editor.css; no reference to `markdown.styles` config anywhere in the file.
- **preview does support it:** extensions/markdown-language-features/src/preview/documentRenderer.ts has `#computeCustomStyleSheetIncludes` (checks `config.styles` array) and `#getSettingsOverrideStyles`, used to inject user-configured stylesheets into the legacy Markdown Preview only.
- **setting scope:** package.json declares `markdown.styles` with description scoped to "the Markdown preview" only (extensions/markdown-language-features/package.json:1742).
- **second reporter:** irabronson confirmed independently in a comment that markdown.styles doesn't apply to the new editor.
- **related but distinct:** https://github.com/microsoft/vscode/issues/332732 is about a CSS variable (--markdown-font-size) not being wired into the new editor — a narrower, related symptom of the same underlying editor.css limitation, not the same ask as supporting the full markdown.styles list.
