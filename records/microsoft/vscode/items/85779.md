# Issue #85779 — Extension tests improperly activate instance from dist folder

[https://github.com/microsoft/vscode/issues/85779](https://github.com/microsoft/vscode/issues/85779)

## Summary

Keep open: extension activation still honors the manifest entry point independently of the test runner, leaving the reported bundled-versus-unbundled module mismatch unresolved. This is a testing-workflow capability gap, not evidence that VS Code violates its activation contract.

## Change summary

Allow extension tests to exercise the same unbundled module instance that extension activation initializes, without repeatedly editing the production manifest.

## Best solution

Establish a supported testing workflow that keeps activation and test imports on the same compiled module graph while preserving normal manifest-based activation. Decide whether that support belongs in a development-only entry-point override or in sample/build tooling and documentation.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostExtensionService.ts`, `src/vs/workbench/api/node/extHostExtensionService.ts`, `src/vs/platform/environment/node/argv.ts`
- **Validation:** Use the linked activation-bug sample, or an equivalent fixture with main pointing to dist/extension and tests importing out modules. Under the selected supported workflow, verify that '*' activation and test imports observe the same module-local singleton, commands register once, and tests can run without dist when targeting unbundled output. Also verify that ordinary extension launches and tests explicitly targeting the production bundle retain manifest-based activation.
- **Behavior:**

  > An extension with a bundled production entry point and separately compiled tests can currently load two independent copies of its implementation: activation initializes the bundle while tests import unbundled modules. Provide a supported workflow in which tests and activation share the intended module state without repeatedly rewriting the production manifest. Acceptance should cover singleton identity, single command registration, and running against unbundled output without requiring a production bundle. Normal extension activation must retain its existing behavior.
- **Trace:**

  > In src/vs/workbench/api/node/extHostExtensionService.ts, _getEntryPoint returns extensionDescription.main. AbstractExtHostExtensionService._doActivateExtension in src/vs/workbench/api/common/extHostExtensionService.ts loads that manifest entry point, while _handleEagerExtensions activates '*' and _doHandleExtensionTests independently loads extensionTestsLocationURI after eager activation. Consequently, setting extensionTestsPath to out/test does not make activation load out/extension; omitting extensionDevelopmentPath also fails the current test-runner precondition. The current bundling guide continues to describe dist-based activation with out-based tests, and the manifest-rewriting workaround is recorded at https://github.com/microsoft/vscode-docs/issues/3632. https://github.com/microsoft/vscode/issues/106269 was consolidated into this issue. The unresolved boundary is whether VS Code should expose a development-only entry-point contract or establish a tooling-based workflow; do not silently infer an activation entry point from the test runner's directory or disable normal activation.
- **Open decisions:**
  - Should VS Code support an explicit development/test entry-point override, or should sharing the activation and test module graph remain a sample/build-tooling responsibility without a new runtime option?
