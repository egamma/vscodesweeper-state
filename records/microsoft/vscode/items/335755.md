# Issue #335755 — Testing: Agent host dev container sessions cannot run terminal commands with sandboxing enabled

[https://github.com/microsoft/vscode/issues/335755](https://github.com/microsoft/vscode/issues/335755)

## Summary

Reopened, team-authored bug with an independent collaborator confirmation that the problem persists even after manually installing Bubblewrap — no fix commit exists on main, and the sandbox diagnostics code I checked still only reports a generic 'unavailable' reason with no dev-container-specific provisioning or remediation path, so this stays open.

## Change summary

Dev Container Agent Host sessions can't run terminal commands when sandboxing is enabled, because the container lacks Bubblewrap/socat and/or the kernel disallows unprivileged user namespaces, with no clear remediation surfaced.

## Best solution

Design a dev-container-aware sandbox path in agentHost/node/copilot (sessionSandbox.ts, copilotSandboxDiagnostics.ts, agentHostSandboxEngine.ts): either provision/verify the sandbox deps and nested-namespace support during dev container startup, or detect the unsupported configuration and surface an immediate, actionable fallback (e.g. auto-disable sandboxing) instead of leaving the agent with a fully broken shell.

  > Starting a Dev Container Agent Host session with the default sandbox configuration should let the agent run terminal commands (e.g. node, curl, git) without the user having to manually install Bubblewrap/socat or toggle chat.agent.sandbox.enabled off. If the container's kernel can't support nested sandboxing, the user should get an immediate, actionable message rather than a session where file tools work but every shell command silently or confusingly fails.
- **Trace:**

  > CopilotSandboxDiagnostics.update() (src/vs/platform/agentHost/node/copilot/copilotSandboxDiagnostics.ts) only forwards a generic host-support/capability reason from the Copilot SDK's getHostSupport() call; there is no dev-container-specific check for Bubblewrap/socat presence or for unprivileged user namespace availability, and no provisioning step runs during dev container startup. Related: https://github.com/microsoft/vscode/issues/335755 (this issue, reopened) and the earlier https://github.com/microsoft/vscode/issues/335485 referenced in the issue body as the original testing issue. Boundary: do not change the generic SDK-driven diagnostics path for non-container hosts; the fix should be specific to the dev-container startup/detection flow.
- **Open decisions:**
  - Should VS Code provision the sandbox's runtime dependencies (Bubblewrap, socat) and ensure nested user-namespace support in supported dev container images, or should it detect unsupported containers and automatically fall back with a clear message?
  - If falling back, should sandboxing be silently disabled for that session, or should the user be prompted/required to confirm running without sandboxing?
  - Is provisioning dev container images for sandbox support a VS Code core responsibility, or should supported dev container templates (e.g. vscode-remote-try-node) be updated instead?
