# Issue #335755 — Testing: Agent host dev container sessions cannot run terminal commands with sandboxing enabled

[https://github.com/microsoft/vscode/issues/335755](https://github.com/microsoft/vscode/issues/335755)

## Summary

Keep open: a team-authored test found a confirmed Agent Host Dev Container failure, and current main still starts the container without ensuring that its sandbox prerequisites or namespace capabilities are usable. The existing related reports and fixes concern the workbench terminal sandbox or generic Linux restrictions and do not fully cover this Agent Host startup path.

## Change summary

Agent Host sessions created in a supported Dev Container cannot execute any terminal command when sandboxing is enabled because Bubblewrap/Socat are absent or nested namespace creation is unavailable.

## Best solution

Make Dev Container Agent Host startup establish a usable sandbox environment before accepting work, or fail early with actionable remediation while preserving the configured security policy. The design should reuse the shared sandbox capability checks rather than discovering the incompatibility only when the first shell tool runs.

Retain a terminal-tool test proving a sandboxed command executes in the supported nested-container case.
- **Behavior:**

  > A Dev Container Agent Host session with sandboxing enabled must not become apparently ready while all terminal commands are guaranteed to fail. For a supported container, sandboxed terminal commands must execute successfully. If the container cannot support the required sandbox, the failure must be detected before agent work proceeds and present actionable remediation without silently weakening or disabling the configured sandbox.
- **Trace:**

  > DevContainerAgentHostService.connect in src/vs/platform/agentHost/node/devContainerAgentHostService.ts runs `devcontainer up`, performs Git/cache setup, installs the remote CLI, and launches the standalone Agent Host without checking Bubblewrap, Socat, or nested namespace usability. Once a session runs, AgentHostTerminalSandboxHost.checkSandboxDependencies in src/vs/platform/agentHost/node/copilot/agentHostSandboxEngine.ts delegates to the shared sandbox helper, which is too late to prevent the partially functional session described in the report. The older fix in https://github.com/microsoft/vscode/pull/327742 addressed the workbench terminal sandbox and is precedent for shared capability detection, but this startup path needs an explicit lifecycle decision. Preserve fail-closed managed sandbox policy and do not silently reinterpret an enabled sandbox as disabled.
- **Open decisions:**
  - Should a supported Dev Container Agent Host startup provision the required packages and nested-sandbox configuration, or reject the session before it is reported ready with remediation instructions?
  - If nested sandboxing remains impossible after dependency installation, should session creation fail entirely or allow file-only operation with an explicit persistent blocked-terminal state?
