# Issue #269338 — MCP Servers: Change how remote and local configurations work

[https://github.com/microsoft/vscode/issues/269338](https://github.com/microsoft/vscode/issues/269338)

## Summary

A real gap remains: current main distinguishes Global, Remote, and Workspace installation targets, but global MCP configurations still run locally and there is no user-level preference to run them remotely. Maintainers accepted the direction for further design, so this Backlog request should remain open.

## Change summary

Make MCP configuration scope, execution location, naming, and precedence understandable and consistent for users working across local and remote environments.

## Best solution

Define clear global, remote-user, and workspace semantics for MCP servers, including whether a global server may prefer remote execution, then expose those semantics consistently in configuration commands, target pickers, and installed-server provenance.

- **Behavior:**

  > Users configuring MCP servers while connected to WSL, SSH, containers, or another remote can tell where each server is stored and where it will execute. Global, remote-user, and workspace configurations use consistent terminology across commands, add/install pickers, and installed-server views, with precedence visible when names overlap. A global server follows the maintainer-selected local-versus-remote policy without requiring duplicate configurations on every remote. Existing explicitly remote and workspace-scoped servers continue to execute remotely.
- **Trace:**

  > McpAddConfigurationCommand.getInstallTarget in src/vs/workbench/contrib/mcp/browser/mcpCommandsAddConfiguration.ts already separates Global, Remote, and Workspace targets and describes their execution locations. McpWorkbenchService.getUserMcpConfigPath and getRemoteMcpConfigPath in src/vs/workbench/contrib/mcp/browser/mcpWorkbenchService.ts assign distinct USER_LOCAL and USER_REMOTE targets, while IWorkbenchMcpManagementService installation in src/vs/workbench/services/mcp/common/mcpWorkbenchManagementService.ts routes them to separate resources and services. OpenRemoteUserMcpResourceCommand in src/vs/workbench/contrib/mcp/browser/mcpCommands.ts resolves the active remote profile resource, which is part of the reported profile-versus-machine ambiguity. The boundary is MCP configuration targeting and presentation: preserve workspace execution behavior and avoid changing general VS Code settings or remote-extension semantics. https://github.com/microsoft/vscode/issues/255220 is related installation-target work, while https://github.com/microsoft/vscode/issues/269340 tracks the narrower remote configuration command defect.
- **Open decisions:**
  - When a global MCP server is used from a remote workspace, should remote execution be opt-in per server, opt-out by default, or controlled by one user-level policy?
  - Should the remote-user MCP configuration follow the active profile, the remote machine's non-profile user scope, or expose both as distinct destinations?
  - When global, remote-user, and workspace configurations define the same server name, what precedence and provenance should users observe?
