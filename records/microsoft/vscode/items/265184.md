# Issue #265184 — Support for Uploading and Analyzing More File Formats in Copilot Chat Agent (e.g., Excel, PDF)

[https://github.com/microsoft/vscode/issues/265184](https://github.com/microsoft/vscode/issues/265184)

## Summary

Keep open: current main can carry arbitrary file paths into an agent session and has provider-level PDF handling, but it does not provide uniform extraction and analysis for Excel, Word, PDF, and similar binary formats. A maintainer explicitly agreed that the pre-agent attachment restriction should be revisited, and no older canonical or open fixing PR was found.

## Change summary

Allow Copilot Chat agents to attach, extract, and reason over common document and data formats such as XLSX, PDF, DOCX, and CSV.

## Best solution

Define a provider-neutral document attachment contract for agent sessions, including supported formats, size limits, capability signaling, and clear unsupported-format behavior, then connect it to either native model document input or a trusted text-extraction path without regressing ordinary file and image attachments.

- **Validation:** Add targeted attachment-resolution and Copilot prompt/endpoint tests covering at least PDF, XLSX, DOCX, CSV, an unsupported binary format, and an over-limit document; verify each supported attachment reaches the agent in the selected representation and unsupported cases produce an explicit user-facing result.
- **Behavior:**

  > Users can attach the agreed common document and data formats to Copilot Chat agent requests and ask questions about their contents. Supported documents reach the agent in a representation it can analyze, while unsupported formats, unsupported models, and oversized files produce clear feedback rather than being silently omitted. Existing source-file, directory, and image attachment behavior remains unchanged. Acceptance should cover PDF, XLSX, DOCX, CSV, unsupported-format, and size-limit cases.
- **Trace:**

  > The workbench currently turns ordinary resources into URI-based file entries in ChatAttachmentResolveService and accepts external file drops in ChatDragAndDrop. CopilotCLIPromptResolver then forwards those resources to the Copilot CLI SDK as path-based file attachments, without a general document extraction layer. Separately, responsesApi.ts and messagesApi.ts have native application/pdf handling, showing that provider-native document input exists for one format but is not a general contract. The trace therefore reaches a boundary between workbench attachment representation, SDK agent file handling, and model-specific endpoint capabilities; source-file, directory, and image semantics must remain unchanged. The maintainer direction is recorded at https://github.com/microsoft/vscode/issues/265184#issuecomment-3256038671, and the conversion workaround is discussed at https://github.com/microsoft/vscode/issues/265184#issuecomment-3441834948.
- **Open decisions:**
  - Should supported document formats behave uniformly across all chat agents and models through client-side extraction, or should availability and fidelity be advertised per model/provider when native document input is used?
  - Which initial format set and size limits form the supported public behavior, and what feedback should users receive when a selected agent or model cannot analyze an attached format?
