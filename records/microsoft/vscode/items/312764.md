# Issue #312764 — Support all settings via JSON in a Group Policy (GPO)

[https://github.com/microsoft/vscode/issues/312764](https://github.com/microsoft/vscode/issues/312764)

## Summary

Keep this accepted Backlog request open: current policy support does not provide arbitrary JSON settings with separate administrator-default and enforced layers. Older related requests cover portions of the goal, but none verified here owns the full user/computer GPO behavior.

## Change summary

Allow administrators to supply arbitrary settings as JSON through user and computer GPOs, with separate overridable defaults and enforced values.

## Best solution

Design administrator-default and enforced configuration layers that support the requested GPO precedence while preserving existing settings scopes and enterprise enforcement contracts. Coordinate the design with the older JSON-policy and system-default requests without treating their narrower requirements as complete coverage.

## Plan brief

- **Likely files:** `src/vs/platform/configuration/common/configurations.ts`, `src/vs/platform/configuration/common/configurationModels.ts`, `src/vs/platform/configuration/common/configurationRegistry.ts`, `src/vs/platform/policy/node/nativePolicyService.ts`, `src/vs/platform/configuration/test/common/policyConfiguration.test.ts`
- **Validation:** Plan precedence tests using distinct values for the same setting in each requested layer, covering a currently non-policy-backed setting and an extension setting. Verify user-enforced > computer-enforced > workspace > user > user-default > computer-default > built-in default, removal restoring the next applicable value, and unchanged existing dedicated-policy enforcement. Finish with a Windows GPO acceptance check for all four JSON entries.
- **Behavior:**

  > Administrators can distribute arbitrary settings as JSON through separate default and enforced entries in both user and computer GPOs. Defaults remain overridable by user and workspace settings, whereas enforced values take precedence over them. The requested ordering is user-enforced, computer-enforced, workspace, user, user-default, computer-default, then built-in defaults. Acceptance must cover settings that currently lack dedicated policy metadata, extension settings, and removing a managed value without modifying the user's settings file.
- **Trace:**

  > PolicyConfiguration in src/vs/platform/configuration/common/configurations.ts discovers and applies only settings with policy or policyReference metadata; its JSON parsing handles individual mapped values rather than arbitrary configuration payloads. NativePolicyService in src/vs/platform/policy/node/nativePolicyService.ts watches the supplied policy definitions. Configuration.getConsolidatedConfigurationModel() in src/vs/platform/configuration/common/configurationModels.ts applies one policy model above ordinary configuration, and getWorkspaceConsolidatedConfiguration() has no separate administrator-default layers. These source paths establish the gap without executing code. Preserve existing scope, workspace/folder and language-override behavior, and do not silently weaken dedicated policies or runtime-managed controls. Related work is recorded at https://github.com/microsoft/vscode/issues/295044 and https://github.com/microsoft/vscode/issues/27972; neither verified report covers the complete requested GPO contract. The unresolved boundary is how a generic enforced payload interacts with existing dedicated and runtime-managed policy authority.
- **Open decisions:**
  - When a generic enforced JSON value conflicts with an existing dedicated policy or runtime-managed control, which authority wins, and how should the conflict be surfaced to administrators?
