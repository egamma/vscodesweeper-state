# Issue #341192 — Agents Window: moving an already-worktree chat to another new worktree is rejected

[https://github.com/microsoft/vscode/issues/341192](https://github.com/microsoft/vscode/issues/341192)

## Summary

Team-authored TPI failure for #340889. The rejection comes from the explicit guards in sessionWorkspaceConversionService.canIsolateChat, which block moving a chat that shares the session's isolated worktree, so the TPI's peer-isolation and repeated-move scenarios cannot pass as written. Keep open; the guards need relaxing for multi-chat sessions that have multi-root enabled.

## Change summary

A peer chat sharing the session's worktree cannot move to its own new worktree with isolate_session, and a main chat that was converted from a folder cannot move again with set_workspace isolation=true.

## Best solution

Make canIsolateChat and the isolation guards in requestChatIsolation and requestSessionWorkspaceUpdate allow a chat that shares the session worktree to move to a fresh worktree of the same repository. This applies when the session has multiple chats and the provider advertises multipleWorkingDirectories. Per-chat moves must leave sibling chats and the session workspace unchanged, with a test covering peer-then-main sequential moves.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/chatContributions/sessionWorkspaceConversion/sessionWorkspaceConversionService.ts`, `src/vs/platform/agentHost/test/node/sessionWorkspaceConversion.test.ts`
- **Validation:** A sessionWorkspaceConversion test with a session in worktree isolation, two chats sharing the worktree and multipleWorkingDirectories enabled: isolating the peer, then the main chat, each succeeds and leaves the other chat's working directory unchanged. Existing rejection tests for workspaceless, subagent and pending chats must still pass.
- **Behavior:**

  > In a session with multi-root enabled, any chat sharing the session worktree can move alone to a new worktree via isolate_session or set_workspace with isolation=true. The chat keeps its history and continues automatically, and sibling chats stay where they are. A chat moved once can still move again when the target is a new worktree. Acceptance: the TPI peer-isolation and repeated-move scenarios pass, and the three-step sequence peer isolate, then main set_workspace, then each chat's cwd and branch check, behaves as expected.
- **Trace:**

  > canIsolateChat (and requestChatIsolation at line 238 and requestSessionWorkspaceUpdate at line 296) blocks any chat whose directory equals the session's primary worktree when state.config Isolation is 'worktree'. It also blocks _isolatedChats members unless the move is elsewhere and hasSingleUserChat. Neither guard distinguishes a chat that shares a session worktree from one that owns it. Boundary: keep the rejections for workspaceless, subagent, pending, archived and non-local chats, and keep session-level isolation semantics for single-chat sessions. Related: https://github.com/microsoft/vscode/issues/340889.
- **Open decisions:**
  - When one chat of a multi-chat session leaves the shared worktree, does the session-level workspace stay as is and only that chat get a per-chat directory, or should the session workspace change?
  - Should chat isolation be allowed without multi-root enabled, or only when the provider advertises multipleWorkingDirectories?
