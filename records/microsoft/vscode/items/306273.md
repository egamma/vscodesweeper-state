[https://github.com/microsoft/vscode/issues/306273](https://github.com/microsoft/vscode/issues/306273)

## Change summary

Reduce repeated command-approval interruptions when troubleshooting attached chat-session logs on Windows and Linux.

## Best solution

  > Troubleshooting an explicitly attached chat session currently interrupts analysis with repeated approvals for log-processing commands; the report observed at least seven in one turn and also encountered the problem on Linux. The intended improvement is useful session analysis with substantially fewer repetitive interruptions, without requiring blanket command approval. Acceptance should cover native Windows PowerShell and Linux bash and preserve approvals for operations outside the agreed troubleshooting scope.
- **Trace:**

  > The original test instructions at https://github.com/microsoft/vscode/issues/305753 establish the local /troubleshoot flow with an attached session. extensions/copilot/assets/prompts/skills/troubleshoot/SKILL.md still sends analysis through run_in_terminal because logs reside outside the workspace. CommandLineSandboxAnalyzer.analyze provides automatic approval for eligible sandboxed commands, while isTerminalSandboxSupported in src/vs/platform/sandbox/common/settings.ts excludes native Windows for the local terminal harness. The configuration registration distinguishes that local limitation from SDK sandboxing on supported Windows Agent Host sessions. The thread recommends sandboxing or WSL but does not settle the desired native Windows experience. Preserve existing permission enforcement and do not interpret attached logs as authorization for arbitrary shell execution; the remaining uncertainty is the user-visible access model, not a demonstrated parser defect.
- **Open decisions:**
  - Should low-interruption troubleshooting remain dependent on an explicitly enabled, supported sandbox, or should attaching a session offer narrowly scoped access to its diagnostic logs without repeated shell-command approvals?
