# Issue #125306 — iPad: improve browsing experience when no real keyboard is available

[https://github.com/microsoft/vscode/issues/125306](https://github.com/microsoft/vscode/issues/125306)

## Summary

The Command Center now provides keyboard-free access to Quick Open, partially addressing the original pain point. The broader request for touch-friendly command access remains unresolved, and the accepted Backlog item should stay open for a focused design decision.

## Change summary

Provide convenient touch access to frequently used commands on iPad without a physical keyboard or navigation through small nested menus.

## Best solution

Build on the existing Command Center rather than introducing a parallel launcher, and decide whether the remaining need is larger touch targets, a touch-oriented command presentation, or gesture activation. Preserve ordinary menu, keyboard, and touch-scrolling behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/titlebar/commandCenterControl.ts`, `src/vs/workbench/browser/actions/quickAccessActions.ts`, `src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts`, `src/vs/base/browser/touch.ts`
- **Validation:** On an iPad in Safari without a physical keyboard, verify the agreed touch entry point opens command access without traversing nested menus and permits selecting and executing a frequently used command. Check that editor scrolling, long-press context menus, browser/OS gestures, and existing keyboard command access remain unchanged.
- **Behavior:**

  > An iPad user without a physical keyboard should be able to discover and invoke frequently used VS Code commands without navigating small nested menus. Current Command Center access is partial coverage and should be evaluated before adding another surface. The finished experience must provide reliably tappable command access while preserving existing keyboard access and ordinary touch interactions. Acceptance should be checked on an actual iPad in Safari.
- **Trace:**

  > The default-enabled window.commandCenter setting is registered in src/vs/workbench/browser/workbench.contribution.ts. CommandCenterControl in src/vs/workbench/browser/parts/titlebar/commandCenterControl.ts renders the launcher; workbench.action.quickOpenWithModes in src/vs/workbench/browser/actions/quickAccessActions.ts opens Quick Access with provider help supplied by src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts. Gesture in src/vs/base/browser/touch.ts supplies low-level per-touch events rather than the proposed multi-finger command trigger. The uncertainty is which user-visible touch capability remains necessary beyond this launcher and whether Safari/iPadOS makes a chosen gesture available. https://github.com/microsoft/vscode/issues/121202 declined larger menus only; do not treat that as rejecting all touch command access. Keep text selection, scrolling, context-menu semantics, and general keyboard bindings outside the change boundary.
- **Open decisions:**
  - Should the remaining work prioritize touch-friendly presentation through the existing Command Center, gesture activation, or both?
  - If gesture activation is part of the scope, which gesture should users invoke, and what visible alternative should be available when the browser or operating system reserves it?
