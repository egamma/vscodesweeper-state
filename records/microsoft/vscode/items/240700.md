# Issue #240700 — Ability to change Github Sign Ins between profiles

[https://github.com/microsoft/vscode/issues/240700](https://github.com/microsoft/vscode/issues/240700)

## Summary

Keep open: extension account defaults remain application-wide, so profiles cannot independently supply preferred accounts for new workspaces. Maintainers endorsed profile-level preferences, and a later matching report was explicitly consolidated into this issue.

## Change summary

Allow work and personal profiles to retain independent extension account preferences without configuring every workspace separately.

## Best solution

Provide profile-specific extension account defaults while preserving explicit workspace preferences and keeping signed-in accounts and Settings Sync independent of profiles. Settle whether profiles inherit shared defaults optionally or receive independent defaults automatically.

## Plan brief

- **Likely files:** `src/vs/workbench/services/authentication/browser/authenticationExtensionsService.ts`, `src/vs/workbench/contrib/authentication/browser/actions/manageAccountPreferencesForExtensionAction.ts`, `src/vs/platform/userDataProfile/common/userDataProfile.ts`
- **Validation:** Exercise two profiles and two signed-in accounts across fresh workspaces: each profile supplies its chosen default, explicit workspace overrides survive profile changes and reloads, and changing one profile does not alter the other. Add executable authentication-storage tests for the chosen preference precedence and existing-value migration; verify Settings Sync account selection remains unchanged.
- **Behavior:**

  > Users separating personal and work development should be able to retain different extension account defaults in their profiles without reselecting accounts for every new workspace. Explicit workspace preferences should continue to take precedence and survive profile changes. Switching profiles must not sign accounts out or change the Settings Sync account. Acceptance covers two profiles with different defaults, fresh workspaces, explicit workspace overrides, and persistence after reload; the inheritance and migration behavior must first be agreed with the maintainer.
- **Trace:**

  > AuthenticationExtensionsService in src/vs/workbench/services/authentication/browser/authenticationExtensionsService.ts stores extension/provider account labels in WORKSPACE and APPLICATION storage, resolves workspace before application, and removes both scopes. This conclusively explains why fresh workspaces cannot inherit independent profile defaults. The _manageAccountPreferencesForExtension command in src/vs/workbench/contrib/authentication/browser/actions/manageAccountPreferencesForExtensionAction.ts exposes workspace-oriented account selection. Profile resource inheritance is represented by ProfileResourceType and UseDefaultProfileFlags in src/vs/platform/userDataProfile/common/userDataProfile.ts, but there is no dedicated account-preference resource. Maintainers discussed optional inheritance and endorsed profile-scoped preferences in https://github.com/microsoft/vscode/issues/240700#issuecomment-2769993097 and https://github.com/microsoft/vscode/issues/240700#issuecomment-2782511063. Preserve explicit workspace precedence, extension preference inheritance, signed-in session availability, and Settings Sync independence. The separate Agent Host account-switching report at https://github.com/microsoft/vscode/issues/330477 is not evidence that a profile-storage change alone fixes Copilot consuming the wrong account.
- **Open decisions:**
  - Should every profile have independent extension account defaults automatically, or should profiles explicitly choose between shared-default inheritance and profile-specific preferences?
  - When introducing profile-specific defaults, how should existing application-wide preferences populate existing profiles, and should an unset profile continue following subsequent changes to the shared default?
