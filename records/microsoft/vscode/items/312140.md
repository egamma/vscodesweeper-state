# Issue #312140 — Can't tell if agent's latest changes are commit / pushed

[https://github.com/microsoft/vscode/issues/312140](https://github.com/microsoft/vscode/issues/312140)

## Summary

Keep open for Agents Window Git-state UX design: existing commit, sync, and PR affordances provide partial information, but do not establish that the latest agent edits are committed and pushed at a glance. No verified older canonical covers the same symptom, and no issue-linked fixing commit supports closing this team-authored request.

## Change summary

Make the latest agent changes' local commit, remote push, and pull-request state understandable without asking the agent.

## Best solution

Provide clear, repository-backed state for outstanding edits, local-only commits, and synchronization with the PR branch, with discoverable next actions. Coordinate with the related Git UX work without treating action disappearance or an existing PR link as proof that the latest edits were pushed.

Add focused presentation tests alongside src/vs/sessions/contrib/changes/test/browser/changesViewService.test.ts and sessionSyncChanges.test.ts for the agreed contract.
- **Behavior:**

  > After an agent implements a feature or applies review changes, users should be able to determine whether those changes remain uncommitted, are committed only locally, or have reached the remote PR branch without asking the agent. PR existence must be distinguishable from synchronization of the latest edits. The next available action should be understandable even when a previous Commit, Sync, or Create PR action disappears. Acceptance covers subsequent edits after PR creation, folder and worktree sessions, and failure or unavailable-state cases without falsely implying success.
- **Trace:**

  > ChangesViewService in src/vs/sessions/contrib/changes/browser/changesViewService.ts derives repository and PR state, including uncommittedChanges, outgoingChanges, upstreamBranchName, hasPullRequest, and hasGitOperationInProgress. ChangesViewButtonBar in changesView.ts uses outgoing counts and running presentation for supported actions; SessionSyncChangesActionViewItem in sessionSyncChanges.ts shows counts and branch tooltips, while shouldShowSyncChanges limits that affordance to folder sessions with pending incoming or outgoing commits. ChangesHeaderChangesetOperationsActionContribution in changesActions.ts provides Commit in the Changes editor header, demonstrating that action placement already varies by context. This establishes partial capability, not a conclusive current defect or complete coverage of the request. Preserve Git-operation semantics and provider-neutral state ownership; the uncertainty is the user-visible status and navigation contract, not permission to introduce automatic commits or pushes. Coordinate with https://github.com/microsoft/vscode/issues/335316 and https://github.com/microsoft/vscode/issues/336620; neither is a valid older canonical for this re-reviewed report.
- **Open decisions:**
  - Should committed, uncommitted, and remote synchronization state remain visible at rest, including when fully synchronized, or be conveyed through completion feedback and inspectable session details?
  - Should the familiar SCM view be directly available within the Agents Window for this workflow, or should session-specific controls provide the complete state and next-action experience?
