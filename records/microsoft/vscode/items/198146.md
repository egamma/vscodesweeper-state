# Issue #198146 — File explorer performance degrades when the number of files in workspaces is large

[https://github.com/microsoft/vscode/issues/198146](https://github.com/microsoft/vscode/issues/198146)

## Summary

The performance defect remains relevant on current main: Explorer still eagerly enumerates every entry of an expanded directory, and multiple reporters confirm multi-second or multi-minute UI stalls with large generated or cache directories. This member-authored Backlog bug should remain open while the Explorer and file-service owners design bounded or progressive loading.

## Change summary

Opening the Explorer or expanding directories containing tens of thousands to hundreds of thousands of files can block the VS Code window for seconds or minutes.

## Best solution

Keep Explorer responsive by avoiding unbounded synchronous processing of every directory entry, while retaining a discoverable way to access additional entries through progressive loading, an explicit continuation action, or another bounded presentation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/common/explorerModel.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/platform/files/common/fileService.ts`, `src/vs/platform/files/common/files.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Use a generated workspace containing a directory with at least 300,000 small files and record Explorer expansion and view-switch responsiveness before and after; the window must remain interactive, initial results must appear without processing the complete directory, and users must still be able to reach later entries through the selected continuation behavior.
- **Behavior:**

  > Switching to Explorer and expanding a directory with hundreds of thousands of entries must not block the VS Code window for seconds or minutes. Explorer should present a bounded initial result while keeping navigation, collapse, and other workbench interactions responsive. Users must have an explicit, understandable way to access entries beyond the initial result, and ordinary directories must retain their current sorting, nesting, filtering, and reveal behavior.
- **Trace:**

  > ExplorerView in src/vs/workbench/contrib/files/browser/views/explorerView.ts resets tree input whenever the view becomes visible. Expansion flows through ExplorerDataSource.getChildren in explorerViewer.ts to ExplorerItem.fetchChildren in explorerModel.ts, which calls FileService.resolve; FileService.toFileStat in src/vs/platform/files/common/fileService.ts performs `provider.readdir` and materializes every entry before the tree receives children. Current `IResolveFileOptions` has no paging or entry-limit contract, so the uncertainty starts at how partial results are represented across the file-service and async-tree boundary. Preserve normal-directory behavior, `files.exclude`, sorting, file nesting, compact-folder traversal, and explicit single-file reveal. The newer https://github.com/microsoft/vscode/issues/281507 corroborates the same failure mode but is not an older canonical.
- **Open decisions:**
  - Should oversized directories use progressive loading that eventually exposes every entry, or a hard bounded listing with an explicit warning and opt-in continuation?
  - What threshold and continuation interaction should apply consistently to local and remote file-system providers?

## Evidence

- **confirmed impact:** Two independent comments on https://github.com/microsoft/vscode/issues/198146 confirm the same observable problem after the original report: expanding a folder with thousands of files stalls Explorer over SSH, while folders with 319,526 and 353,279 files make the window unresponsive for minutes.
- **current source path:** src/vs/workbench/contrib/files/common/explorerModel.ts (`ExplorerItem.fetchChildren`) resolves an expanded directory through `fileService.resolve` and returns its complete child collection; src/vs/workbench/contrib/files/browser/views/explorerViewer.ts (`ExplorerDataSource.getChildren`) passes that complete array to the async tree without a count limit or continuation mechanism.
- **unbounded enumeration:** src/vs/platform/files/common/fileService.ts (`FileService.toFileStat`) calls `provider.readdir(resource)` and maps every returned entry into an `IFileStat`; `IResolveFileOptions` in src/vs/platform/files/common/files.ts exposes no paging or maximum-entry option.
- **view-switch trigger:** src/vs/workbench/contrib/files/browser/views/explorerView.ts refreshes the tree whenever the Explorer body becomes visible to compensate for missed file events, matching the original report's slow switch back to Explorer.
- **related report:** The newer open report https://github.com/microsoft/vscode/issues/281507 describes the same large-directory expansion freeze and includes a maintainer acknowledgment, but it was created after this re-reviewed issue and therefore cannot serve as its duplicate canonical.
- **historical issue:** The older https://github.com/microsoft/vscode/issues/37075 reported expansion hangs with 10,000+ files but is closed and points to the completed old-tree performance work in https://github.com/microsoft/vscode/issues/18180; neither is an open canonical for the remaining current-tree behavior.
