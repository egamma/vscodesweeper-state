## Change summary

Prevent the VS Code Snap environment from causing GLIBCXX_3.4.29 lookup failures when opening terminals or running host applications and Git commands.

## Best solution

Ensure the Snap's desktop-library environment does not force incompatible libraries into host processes while preserving VS Code's own desktop integration. - **Observable impact:** https://github.com/microsoft/vscode/issues/180629#issuecomment-1628595256 confirms the same libproxy/GIO failure during Git operations on Ubuntu 22.04, including warnings obscuring the actual Git error. Reports of general slowness and application crashes do not establish that VS Code itself crashes or that all performance symptoms share this cause.
- **Current packaging:** resources/linux/snap/snapcraft.yaml still declares confinement: classic and base: core20, with core20 cleanup and crashpad RPATH references. This is a mixed host/Snap library compatibility problem, not evidence that classic confinement universally prevents access to host libraries.
- **Current environment handling:** resources/linux/snap/electron-launch exports GIO_MODULE_DIR as $SNAP_USER_COMMON/.cache/gio-modules and populates it with Snap module symlinks. It saves the original GIO_MODULE_DIR in a *_VSCODE_SNAP_ORIG variable, but src/vs/base/common/processes.ts:sanitizeProcessEnvironment does not restore these saved variables or remove GIO_MODULE_DIR. These paths support the reported mechanism, but native loading was not executed in this read-only review.

Other commenters report persistent performance symptoms with RPM/.deb or after downgrading, so those broader symptoms should not be assumed fixed by a Snap change.

It explicitly references the related Java issue, not this issue; applicability to this exact libproxy failure remains to be verified.
