# Issue #207058 — Inconsistent keyboard shortcut resolution

[https://github.com/microsoft/vscode/issues/207058](https://github.com/microsoft/vscode/issues/207058)

## Summary

Keep open: the supplied Czech-layout steps and event logs suffice to retest, and keyboard.mapAltGrToCtrlAlt does not preserve both shortcuts and AltGr character entry. Later Windows reports describe the same failure, but current behavior on the affected configuration remains unverified; no fixing commit or eligible older canonical was established.

## Change summary

Ctrl+Alt shortcuts on a Windows Czech keyboard lose their modifiers, while enabling the available workaround interferes with AltGr character entry.

## Best solution

Establish where physical Ctrl+Alt becomes an AltGraph-only event on the affected Windows configuration, then restore shortcut recognition without consuming genuine AltGr character input. Determine the VS Code versus Electron/Chromium ownership boundary before choosing a fix.

## Plan brief

- **Likely files:** `src/vs/base/browser/keyboardEvent.ts`, `src/vs/workbench/services/keybinding/browser/keybindingService.ts`, `src/vs/workbench/services/keybinding/common/windowsKeyboardMapper.ts`, `src/vs/workbench/services/keybinding/test/node/windowsKeyboardMapper.test.ts`
- **Validation:** On Windows 11 with the affected Czech layout, enable keyboard troubleshooting and compare physical left Ctrl+left Alt+L against right AltGr+L with keyboard.mapAltGrToCtrlAlt false and true. Acceptance requires the configured Ctrl+Alt+L command to execute while genuine AltGr+L still inserts its character; repeat with an English layout as a control. Capture raw modifier flags and AltGraph state before asserting a source-level fix.
- **Behavior:**

  > On the reported Windows Czech configuration, pressing Ctrl+Alt+L is resolved as unmodified L instead of the configured shortcut. Enabling keyboard.mapAltGrToCtrlAlt restores shortcuts but also captures AltGr combinations needed for typing. The desired outcome is working physical Ctrl+Alt shortcuts alongside unchanged genuine AltGr character entry. First reproduce the reported event stream on Windows; source inspection alone has not confirmed the environment-dependent failure.
- **Trace:**

  > WorkbenchKeybindingService in src/vs/workbench/services/keybinding/browser/keybindingService.ts wraps DOM keydown events in StandardKeyboardEvent and delegates resolution to the keyboard mapper. StandardKeyboardEvent in src/vs/base/browser/keyboardEvent.ts copies the browser modifier flags and AltGraph state; the reporter's raw KeyL event already lacks Ctrl and Alt. WindowsKeyboardMapper.resolveKeyboardEvent in src/vs/workbench/services/keybinding/common/windowsKeyboardMapper.ts only reconstructs those modifiers from AltGraph when keyboard.mapAltGrToCtrlAlt is enabled, which also captures genuine AltGr. The mapper test 'resolveKeyboardEvent mapAltGrToCtrlAlt AltGr+Z' documents that existing behavior. The unresolved boundary is why physical Ctrl+Alt produces the reported browser event and whether enough information survives to distinguish it safely. Preserve genuine character entry, the existing setting's compatibility semantics, and unaffected layouts. Related https://github.com/microsoft/vscode/issues/283735 independently describes the same tradeoff but is newer than this issue.

## Evidence

- **Reported trigger and incomplete workaround:** https://github.com/microsoft/vscode/issues/207058 supplies Windows 11 and Czech-layout reproduction steps: press Ctrl+Alt+L with keyboard troubleshooting enabled. The raw KeyL event already has modifiers: [] and key: Ł. The reporter's December 2024 comment confirms that keyboard.mapAltGrToCtrlAlt restores shortcuts but prevents some AltGr character input.
- **Current event normalization:** src/vs/base/browser/keyboardEvent.ts, StandardKeyboardEvent.constructor, copies ctrlKey, altKey and getModifierState('AltGraph') from the browser event. It does not reconstruct physical Ctrl+Alt from preceding modifier events. This explains propagation of the supplied event, but does not establish why Windows/Chromium emitted it.
- **Existing setting is partial coverage:** src/vs/platform/keyboardLayout/common/keyboardConfig.ts registers keyboard.mapAltGrToCtrlAlt with default false. src/vs/workbench/services/keybinding/common/windowsKeyboardMapper.ts:413-418 maps AltGraph to both Ctrl and Alt when enabled, without distinguishing the physical modifier combination. src/vs/workbench/services/keybinding/test/node/windowsKeyboardMapper.test.ts includes 'resolveKeyboardEvent mapAltGrToCtrlAlt AltGr+Z', confirming that this setting intentionally maps genuine AltGr to shortcuts too.
- **Verified related report, not an eligible canonical:** https://github.com/microsoft/vscode/issues/283735 is open and describes the same Ctrl+Alt versus AltGr tradeoff on Windows. Its discussion includes a maintainer's comparison of the two setting states and independent reports through June 2026. It was created in December 2025, later than this March 2024 issue, so it cannot be the duplicate target under the re-review rules.
- **Older leads do not justify closure:** Canonical searches covered AltGr, Ctrl+Alt and Czech-layout reports. https://github.com/microsoft/vscode/issues/166868 is closed and originally concerns using physical AltGr to invoke shortcuts, rather than physical Ctrl+Alt losing modifiers. https://github.com/microsoft/vscode/issues/41225 is also closed and concerns the inverse symptom, AltGr unexpectedly invoking Ctrl+Alt shortcuts. Neither supplies an open canonical or a demonstrated fix for this report.
