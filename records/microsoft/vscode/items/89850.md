# Issue #89850 — [html] HTML breadcrumbs don't work right when optional end tags omitted

[https://github.com/microsoft/vscode/issues/89850](https://github.com/microsoft/vscode/issues/89850)

## Summary

The central breadcrumb problem remains separately tracked from the resolved formatter symptom: the HTML language service parser does not model HTML optional end-tag closure, so document symbols can retain incorrect nesting. No older canonical with the same breadcrumb symptom is established, so this re-reviewed Backlog request should remain open.

## Change summary

Make HTML breadcrumbs reflect the DOM hierarchy when optional end tags such as those for `p`, `li`, `tr`, and `td` are omitted.

## Best solution

Teach the HTML language service parser to apply the HTML optional end-tag rules when constructing its node tree, then verify that document symbols and breadcrumbs expose the resulting sibling hierarchy without regressing ordinary explicit-tag parsing.

## Plan brief

- **Likely files:** `extensions/html-language-features/server/src/htmlServerMain.ts`
- **Validation:** Add HTML language-service parser/document-symbol tests using consecutive omitted-end-tag `p`, `li`, and table elements, asserting sibling rather than nested symbol ranges; then run the targeted HTML language-feature test suite.
- **Behavior:**

  > In valid HTML that omits optional end tags, breadcrumbs must represent the hierarchy defined by HTML parsing rules rather than treating every start tag as nested until an explicit close tag appears. Consecutive `p` and `li` elements must appear as siblings, with equivalent coverage for representative table elements. Explicitly closed HTML and unrelated document-symbol behavior must remain unchanged.
- **Trace:**

  > Breadcrumbs consume HTML document symbols produced through the built-in HTML language feature, while the issue discussion traces the malformed hierarchy to the parser in the external `microsoft/vscode-html-languageservice` dependency and links https://github.com/microsoft/vscode-html-languageservice/issues/63. The formatter report in https://github.com/microsoft/vscode/issues/94287 had a separate js-beautify root cause and is not evidence that breadcrumbs were fixed. The investigation boundary is optional end-tag tree construction and its document-symbol output; formatting behavior must not be folded into this work. Before implementation, confirm the current parser source and enumerate which optional-end-tag rules are absent, then establish tests in the owning language-service repository.
- **Open decisions:**
  - Should the first change cover the complete HTML standard set of optional end-tag rules, or only the element families demonstrated here before broader conformance work?

## Evidence

- **maintainer diagnosis:** A VS Code maintainer confirmed that the HTML language service was not aware of tags whose end tags may be omitted and later identified the HTML parser as the required implementation area.
- **distinct unresolved symptom:** The js-beautify 1.11.0 update addressed formatting only; commenters explicitly confirmed that it did not fix the breadcrumb hierarchy reported here.
- **related parser issue:** https://github.com/microsoft/vscode-html-languageservice/issues/63 was linked by the maintainer as related parser work, but the supplied record does not establish it as an older open canonical with the same reporter-observable breadcrumb symptom required for a re-reviewed duplicate close.
- **workaround is incomplete:** Changing Breadcrumbs: Symbol Path to `last`, disabling Show Fields, or disabling breadcrumbs hides the incorrect hierarchy but does not make the parsed HTML structure correct.
