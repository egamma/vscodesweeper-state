# Issue #109977 — Git - Expose git.publish as a command through Git API

[https://github.com/microsoft/vscode/issues/109977](https://github.com/microsoft/vscode/issues/109977)

## Summary

Keep open: the Git API still lacks a caller-facing publish operation, and executing git.publish still consumes errors rather than rejecting to the caller. The request is already correctly routed; the notification-waiting side concern is addressed, but the central API gap remains.

## Change summary

Expose the interactive Git publishing flow through the Git extension API so extensions can target a repository and handle failures.

## Best solution

Provide a supported publishing API that retains the existing provider and remote-selection experience while allowing callers to handle failures. Settle the supported options and cancellation contract before implementation, preserving ordinary Git command behavior.

## Plan brief

- **Likely files:** `extensions/git/src/api/git.d.ts`, `extensions/git/src/api/api1.ts`, `extensions/git/src/commands.ts`, `extensions/github/src/publish.ts`
- **Validation:** Exercise the agreed API from a development extension against a selected repository: publish with no remote through a registered publisher, publish a branch with an existing remote, induce a publisher failure and confirm the caller catches it, cancel each selection flow and verify the agreed cancellation result, and leave the GitHub success notification open while confirming the API has already completed. Also verify that ordinary git.publish retains its existing interactive error presentation.
- **Behavior:**

  > Extensions need a supported way to invoke the existing interactive Git publishing experience for a selected repository and handle publishing failures. The existing command is insufficient because its error handler consumes rejections. Acceptance should cover repositories with and without remotes, caller-visible failures, the agreed cancellation semantics, and completion without dismissing a success notification. Existing user-invoked publishing behavior must remain unchanged.
- **Trace:**

  > The public Repository and API interfaces in extensions/git/src/api/git.d.ts have no consumer-facing publishing operation; the similarly named RemoteSourcePublisher method is a provider hook. ApiRepository.push in extensions/git/src/api/api1.ts delegates to pushTo and does not perform publisher selection. Commands.publish in extensions/git/src/commands.ts owns the interactive provider/remote flow, while Commands.createCommand replaces command methods with wrappers that catch failures and display notifications without rethrowing. The GitHub provider in extensions/github/src/publish.ts already does not await the final success notification. The remaining uncertainty is the public options and cancellation contract, not whether the API gap exists. Preserve existing command notifications, provider selection, and branch publishing semantics; organization publishing and empty-repository warning improvements are separate work, including https://github.com/microsoft/vscode/issues/98349 and https://github.com/microsoft/vscode/issues/246562.
- **Open decisions:**
  - Which publishing options should callers be able to supply in addition to the target repository, and which choices must remain interactive?
  - Should user cancellation resolve without a result, return an explicit cancellation outcome, or reject with a distinguishable cancellation error?

## Evidence

- **Existing API does not cover the request:** extensions/git/src/api/git.d.ts exposes Repository.push, API.onDidPublish, and registerRemoteSourcePublisher, but no caller-facing publish method on Repository or API. RemoteSourcePublisher.publishRepository is a provider implementation contract, not an operation consumers can invoke through the Git API. In extensions/git/src/api/api1.ts:313-315, ApiRepository.push delegates to pushTo rather than the interactive publishing flow.
