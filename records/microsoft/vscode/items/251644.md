# Issue #251644 — Chat window is not preserved when cloning a repo

[https://github.com/microsoft/vscode/issues/251644](https://github.com/microsoft/vscode/issues/251644)

## Summary

Keep open for a scoped product decision about continuing an active chat when cloning and opening a repository in the same window. Current secondary-side-bar defaults address part of the request, but they do not carry the conversation over; the maintainer discussion explicitly favors workspace-scoped history outside the existing #new handoff.

## Change summary

Preserve the visible chat and its active conversation when an empty window opens a cloned repository in the same window.

## Best solution

Define whether a chat-driven clone/open transition should explicitly continue its initiating conversation in the destination workspace, while retaining workspace-scoped history for unrelated folder opens. Treat panel visibility separately using the existing secondary-side-bar setting rather than assuming it transfers chat state.

- **Behavior:**

  > Opening a cloned repository in the current window can leave the conversation that initiated the workflow behind. The secondary side bar's default visibility is independently configurable and does not itself preserve that conversation. Establish whether chat-driven cloning should continue the initiating session in the destination, and whether Welcome-driven cloning receives the same treatment. Acceptance must distinguish conversation continuation from globally sharing history, preserve existing destination sessions, and respect explicit layout preferences.
- **Trace:**

  > The clone command's Open choice calls vscode.openFolder in extensions/git/src/commands.ts without an explicit chat handoff. MainThreadChatAgents2.$transferActiveChatSession delegates to ChatService.transferChatSession, which stores a destination-specific transfer for a local Chat-view session. ChatSessionStore maintains separate empty-window and workspace storage roots and also handles onDidEnterWorkspace migrations; that hook is not proof of continuity through the clone/open reload. Current workbench.secondarySideBar.defaultVisibility defaults to visibleInWorkspace, partially addressing visibility but not conversation identity. The maintainer statement at https://github.com/microsoft/vscode/issues/251644#issuecomment-3661611499 favors workspace scoping outside #new, so broader automatic transfer is not an agreed requirement. https://github.com/microsoft/vscode/issues/213378 discusses coupling transfer with workspace opening and is relevant design context, not a duplicate. Preserve unrelated workspace isolation and destination history; first establish the exact same-window reload behavior before designing the approved handoff.
- **Open decisions:**
  - Should a chat-driven clone/open continue its initiating conversation as an additional explicit handoff exception to workspace-scoped history, or should the current scoping remain unchanged?
  - If continuation is approved, should it be automatic or require user consent, and should it also apply when cloning from Welcome rather than from the active chat?
