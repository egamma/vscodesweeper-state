# Issue #235160 — With explorer file search, is it possible to jump to the found file without opening each folder recursively first?

[https://github.com/microsoft/vscode/issues/235160](https://github.com/microsoft/vscode/issues/235160)

## Summary

A real Explorer Find navigation gap remains: Up/Down treats a collapsed ancestor as the navigable match instead of revealing each matching file. This team-authored Backlog request should remain open while the navigation gesture and expansion-restoration semantics are decided.

## Change summary

Provide keyboard navigation through Explorer Find results that reveals matching files without requiring users to expand every containing folder manually.

## Best solution

Define a next/previous-result gesture that reveals each actual matching file and its parent path, with an explicit policy for restoring or retaining folder expansion when navigation or the find session ends.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/tree/asyncDataTree.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/base/test/browser/ui/tree/asyncDataTree.test.ts`, `src/vs/workbench/contrib/files/test/browser/explorerFindProvider.test.ts`
- **Validation:** In a workspace with several matches under different collapsed nested folders, exercise the chosen next/previous-result gesture and verify that each invocation reveals and focuses the actual matching file without manual expansion; ending the find session must follow the selected expansion-restoration policy.
- **Behavior:**

  > Explorer Find should let users navigate through actual matching files even when their parent folders begin collapsed. Each navigation step should reveal and focus the selected result without requiring recursive manual expansion. Existing filtering, fuzzy matching, multi-root behavior, and ordinary Explorer arrow navigation outside an active find session must remain unchanged. Folder state after navigation or after closing Find must follow the maintainer-selected persistence policy.
- **Trace:**

  > ExplorerFindProvider.doHighlightFind in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts deliberately reports a collapsed ancestor with descendant hits as a match. AsyncFindController.shouldFocusWhenNavigating in src/vs/base/browser/ui/tree/asyncDataTree.ts therefore allows focus navigation to stop on that proxy node, and AbstractTree.focusNext/focusPrevious only move focus among visible nodes. Commit https://github.com/microsoft/vscode/commit/8bed1a4734747a62a3713f39e62b0cd4f5ccca10 repaired root-level match accounting for https://github.com/microsoft/vscode/issues/235158 but did not add path expansion or direct navigation to hidden files. The boundary is active Explorer Find navigation: ordinary tree navigation and non-Explorer async-tree consumers must not acquire unexpected expansion behavior.
- **Open decisions:**
  - Should existing Up/Down result navigation reveal hidden matching files automatically, or should this behavior use a separate next/previous-result gesture?
  - After moving away from a revealed result or ending Explorer Find, should automatically expanded folders be restored to their prior state or remain expanded?
