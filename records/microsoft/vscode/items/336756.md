# Issue #336756 — Wrap all lines in diffs after Copilot edits

[https://github.com/microsoft/vscode/issues/336756](https://github.com/microsoft/vscode/issues/336756)

## Summary

Traced the root cause in the checkout: the rejected/original line shown above a Copilot-modified line is rendered as a view zone via `renderLines`/`RenderOptions.fromEditor`, which has no word-wrap support, so it stays on one long unwrapped line while the surrounding unchanged lines wrap normally through the real editor. This is a genuine layout gap, worth keeping open rather than closing.

## Change summary

When word wrap is enabled and Copilot's inline edits are shown for review, the changed/original line renders unwrapped while surrounding unchanged lines wrap, making the diff hard to read.

## Best solution

Extend the view-zone rendering path in chatEditingCodeEditorIntegration.ts (and the shared renderLines/RenderOptions helper it uses) to respect the editor's word-wrap column when laying out the removed/original line content, so it wraps consistently with the rest of the document.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCodeEditorIntegration.ts`, `src/vs/editor/browser/widget/diffEditor/components/diffEditorViewZones/renderLines.ts`
- **Validation:** A manual/visual check: with `editor.wordWrap` enabled and a narrow editor width, trigger a Copilot edit whose original line exceeds the wrap column, and confirm the removed-line view zone wraps to match the modified line and surrounding unchanged lines.
- **Behavior:**

  > When word wrap is enabled, the original (about-to-be-replaced) line shown in the inline Copilot edit review should wrap the same way the rest of the document does, so long changed lines are as easy to read/compare as unchanged ones. Acceptance: with word wrap on and a long original line, the removed-line rendering breaks across multiple visual rows consistent with the wrap column, matching the modified line below it.
- **Trace:**

  > chatEditingCodeEditorIntegration.ts (around lines 352-438) computes `RenderOptions.fromEditor(this._editor)` and calls `renderLines(source, renderOptions, decorations, domNode)` (imported from diffEditor/components/diffEditorViewZones/renderLines.ts) to lay out the removed/original line inside a view zone. `RenderOptions` (renderLines.ts, class at line 103) has no wrappingColumn/word-wrap field, so the produced DOM is always a single unwrapped row. The boundary: don't touch how the modified line itself renders (that's normal editor text and already wraps) — the fix is scoped to how the synthetic removed-line view zone content is laid out. Related shared code: diffEditorViewZones.ts's `hasWrapping`/`wrappingZoneHeights` logic handles vertical spacing for wrapped zones but not content wrapping itself.
- **Open decisions:**
  - Should the removed-line view zone reuse the editor's actual wrapping computation (e.g. via a hidden view model) for pixel-accurate wraps, or is an approximate character-column wrap acceptable given this is synthetic content?
  - Does this change belong in the shared renderLines/RenderOptions helper (affecting other callers) or should chatEditingCodeEditorIntegration.ts get its own wrapping logic to avoid touching the diff editor's rendering path?

## Evidence

- **rendering path:** src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCodeEditorIntegration.ts builds the deleted/original line's view zone via `RenderOptions.fromEditor(this._editor)` and `renderLines(...)` from src/vs/editor/browser/widget/diffEditor/components/diffEditorViewZones/renderLines.ts.
- **no wrap support:** RenderOptions (renderLines.ts, class starting at line 103) exposes no wrappingColumn/word-wrap handling — grep for 'wordWrap'/'wrappingColumn' in that file returns nothing, so the rendered line is always laid out as a single unwrapped line regardless of the editor's word-wrap setting.
- **contrast:** diffEditorViewZones.ts (the full diff editor's equivalent) tracks `hasWrapping`/`wrappingZoneHeights' for spacing compensation, but that's positional bookkeeping, not evidence the rendered zone content itself wraps — the underlying renderLines call is shared and has the same limitation.
