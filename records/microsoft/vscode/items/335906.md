# Issue #335906 — Show migration status badges on the MCP customization page

[https://github.com/microsoft/vscode/issues/335906](https://github.com/microsoft/vscode/issues/335906)

## Summary

Genuine, unimplemented gap: the MCP list currently only shows runtime status badges (Running/Starting/Error/Disabled via getMcpStatusPresentation in mcpListWidget.ts), with no migration-state badge ('Needs migration'/'Unsupported'); no sibling issue in the current batch of migration-UI feedback covers this specific ask, so it stays open as a real, if design-open, feature request.

## Change summary

Add migration-state badges (Needs migration / Unsupported) to entries on the MCP customization page, matching the badge patterns and severity vocabulary used elsewhere in the customization migration UI.

## Best solution

Extend the MCP list's badge rendering (mcpListWidget.ts, alongside getMcpStatusPresentation) to also surface migration eligibility state, sourced from the same compatibility/applicability data already computed for the unified migration dashboard (customizationMigrationDashboard.ts / customizationMigrationCategories.ts) — but the exact badge taxonomy and how it composes with the existing runtime-status badge need a design pass first.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationCategories.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/mcpServerCustomizationMigration.ts`
- **Validation:** A test asserting the MCP list row renders a 'Needs migration' or 'Unsupported' badge for an entry whose migration-compatibility data marks it as such, without disturbing the existing running/disabled status badge.
- **Behavior:**

  > Each MCP entry on the customization page shows a migration-state badge when it needs migration or is unsupported for the target harness, alongside (not replacing) its existing runtime status badge. The wording and visual treatment match the badge/annotation conventions elsewhere in the customization UI and the severity vocabulary used on the unified migration page. Entries with no migration concern show no such badge.
- **Trace:**

  > mcpListWidget.ts renders a single statusBadge per row via getMcpStatusPresentation (lines ~740-770), driven purely by McpConnectionState/McpServerStatus/CustomizationDisabledReason — it has no notion of migration eligibility today. Migration compatibility/applicability data instead lives in mcpServerCustomizationMigration.ts and customizationMigrationCategories.ts, used by the separate migration dashboard (customizationMigrationDashboard.ts). The open design question is how to plumb that migration data into the list row without conflicting with the existing runtime badge, and what exact 'Needs migration'/'Unsupported' presentation to standardize on — no severity/badge convention for this currently exists in the codebase to copy from.
- **Open decisions:**
  - Should the migration badge replace or sit alongside the existing runtime-status badge (Running/Disabled/etc.) on the same row?
  - What exact source of truth (which migration/compatibility check) determines 'Needs migration' vs 'Unsupported' per MCP entry?
  - Should this introduce a new shared badge/severity component reused by the unified migrations page, or a one-off addition to mcpListWidget.ts?
