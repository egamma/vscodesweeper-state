# Issue #102867 — CodeLens messes up page scrolling via cursorPageUp / cursorPageDown

[https://github.com/microsoft/vscode/issues/102867](https://github.com/microsoft/vscode/issues/102867)

## Summary

The gap remains on current main: cursor paging uses a fixed wrapped-line count derived from editor height and does not account for the vertical space occupied by CodeLens view zones. The existing feature-request classification and Backlog milestone remain appropriate.

## Change summary

Make cursorPageUp and cursorPageDown preserve a rendered-page overlap when CodeLens view zones occupy space in the editor.

## Best solution

Define cursor paging in terms of the rendered viewport, including view zones, while preserving cursor movement, selection variants, wrapped-line behavior, and the existing scroll-only commands.

## Plan brief

- **Likely files:** `src/vs/editor/browser/coreCommands.ts`, `src/vs/editor/common/cursorCommon.ts`, `src/vs/editor/common/cursor/cursorMoveCommands.ts`, `src/vs/editor/contrib/codelens/browser/codelensWidget.ts`
- **Validation:** Create an editor test with multiple CodeLens-style view zones and verify that cursorPageDown/cursorPageUp and their selection variants preserve the expected rendered-page overlap in both directions; also verify unchanged behavior without view zones and with wrapped lines.
- **Behavior:**

  > In an editor containing CodeLens rows, PageDown should move the cursor and viewport by one rendered page so the previous bottom text line becomes the new top boundary; PageUp should provide the inverse overlap. Repeated down/up paging should not drift because of CodeLens height. The selection variants must follow the same paging distance, while scrollPageUp and scrollPageDown remain unchanged.
- **Trace:**

  > CursorPageUp and CursorPageDown in src/vs/editor/browser/coreCommands.ts replace PAGE_SIZE_MARKER with viewModel.cursorConfig.pageSize and pass that fixed count to CursorMoveCommands.simpleMove as WrappedLine units. CursorConfiguration in src/vs/editor/common/cursorCommon.ts derives pageSize only from layoutInfo.height and lineHeight. CodeLensWidget in src/vs/editor/contrib/codelens/browser/codelensWidget.ts inserts CodeLensViewZone instances with independent pixel heights, while the later reveal path uses vertical offsets that include those zones; this mismatch explains the asymmetric overlap. The uncertainty starts at finding the editor-level coordinate API and test harness that can map one rendered viewport displacement to the appropriate cursor position without changing ordinary wrapped-line paging, multicursor semantics, or scroll-only commands.

## Evidence

- **current paging calculation:** src/vs/editor/common/cursorCommon.ts computes CursorConfiguration.pageSize as floor(editor layout height / line height) minus two, with no view-zone contribution.
- **cursor command path:** src/vs/editor/browser/coreCommands.ts resolves cursorPageUp and cursorPageDown to that fixed pageSize and moves by WrappedLine units before minimally revealing the resulting cursor.
- **CodeLens layout:** src/vs/editor/contrib/codelens/browser/codelensWidget.ts renders every CodeLens row as a CodeLensViewZone with a pixel height, so it consumes viewport space without reducing the cursor command's wrapped-line count.
