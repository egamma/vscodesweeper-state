# Issue #316870 — VS Code Installer Option Add "Open with Code" action to Windows Explorer directory context menu failed

[https://github.com/microsoft/vscode/issues/316870](https://github.com/microsoft/vscode/issues/316870)

## Summary

Still present on current main: on Windows 11 the `addcontextmenufolders` task is effectively ignored — the legacy folder keys are skipped when the Win11 (appx) menu is used, and the only Win11 menu registration (the `CodeContextMenu` `Title` value) is gated on `addcontextmenufiles`, so a folders-only selection registers no context menu at all while a files-only selection silently also yields folder entries.

## Change summary

The installer's Add "Open with Code" action to Windows Explorer directory context menu option has no effect on Windows 11 when the file context menu option is not also selected.

## Best solution

Make the Windows 11 context-menu registration honor the two installer tasks independently in build/win32/code.iss (and the sparse-package verb gating it relies on), or collapse the two checkboxes into one option on Windows 11 so the wizard no longer offers a choice the installer cannot honor.

## Plan brief

- **Likely files:** `build/win32/code.iss`, `resources/win32/appx/AppxManifest.xml`
- **Validation:** Install the generated user setup on Windows 11 with only "Add 'Open with Code' action to Windows Explorer directory context menu" checked, then right-click a folder and the folder background and confirm the entry appears; repeat with only the file option checked and confirm folders are not affected. Cross-check the installer log line emitted by `LogContextMenuInstallState()`.
- **Behavior:**

  > On Windows 11, checking only "Add 'Open with Code' action to Windows Explorer directory context menu" in the installer must produce an "Open with Code" entry on folders, folder backgrounds and drives; checking only the file option must produce it on files. Today a folders-only selection produces no entry anywhere, and a files-only selection also brings the folder entries along. Acceptance: each of the four task combinations (neither / files / folders / both) yields exactly the matching Explorer entries on Windows 11 and on Windows 10 (and with classic menus forced), and the uninstall path removes whatever was registered.
- **Trace:**

  > In build/win32/code.iss, `ShouldInstallLegacyFolderContextMenu()` (line ~1600) suppresses the legacy `directory\shell`, `directory\background\shell` and `Drive\shell` registrations (lines 1283-1291) whenever `ShouldUseWindows11ContextMenu()` (line ~1568) is true — i.e. on Windows 11 without forced classic menus — leaving the Windows 11 path as the only source of the entry. That path writes a single value, `Software\Classes\{#RegValueName}ContextMenu` `Title` (line 1279), gated on `Tasks: addcontextmenufiles`, while the sparse package (code.iss:112-113, installed for every Windows 11 install regardless of task) declares one verb for `Directory`, `Directory\Background` and `*` in resources/win32/appx/AppxManifest.xml. So the folders task has no effect on Windows 11, and the files task implicitly covers folders. The boundary: do not change the Windows 10 / forced-classic legacy behavior or `ShouldRepairFolderContextMenu()`'s background-update repair, and keep the appx install unconditional for Windows 11 if the verb gating moves into the handler. The shell handler DLL that consumes these values lives outside this repository, so whatever registry contract is chosen must be one it already reads or one the DLL owners agree to add. Related reports of the entry missing after a failed appx registration: https://github.com/microsoft/vscode/issues/303103 and https://github.com/microsoft/vscode/issues/304214.
- **Open decisions:**
  - On Windows 11, should the two installer options remain independently honored (requiring per-item-type gating the sparse-package handler can read), or be collapsed into a single "Open with Code" context-menu option?
  - If they stay independent, what registry contract do the folder and file verbs read — separate per-item-type values alongside the existing `CodeContextMenu` `Title`, and what is the behavior for an existing install that only has `Title`?
  - Should an upgrade from a current install that selected folders-only retroactively register the Windows 11 entry, or only apply on a fresh install or re-run of the installer?

## Evidence

- **folder keys gated off on Win11:** build/win32/code.iss:1600-1602 — `ShouldInstallLegacyFolderContextMenu()` returns `(WizardIsTaskSelected('addcontextmenufolders') and not ShouldUseWindows11ContextMenu()) or ShouldRepairFolderContextMenu()`, and `ShouldUseWindows11ContextMenu()` (line 1568) is true on Windows 11 unless the user forced classic menus, so the `directory\shell`, `directory\background\shell` and `Drive\shell` entries at lines 1283-1291 are never written for a normal Windows 11 install.
- **Win11 registration is keyed to the files task only:** build/win32/code.iss:1279 writes `Software\Classes\{#RegValueName}ContextMenu` `Title` with `Tasks: addcontextmenufiles; Check: ShouldUseWindows11ContextMenu`. There is no equivalent line for `addcontextmenufolders`, so checking only the folders option leaves no Windows 11 registration behind — matching the reporter's observation.
- **sparse package covers all item types with one verb:** resources/win32/appx/AppxManifest.xml declares a single verb for `Directory`, `Directory\Background` and `*`, so the appx (installed whenever `ShouldUseWindows11ContextMenu`, code.iss:112-113) cannot distinguish the two installer tasks; the per-task distinction exists only in the legacy registry path.
- **not a duplicate of the appx-registration reports:** https://github.com/microsoft/vscode/issues/304214 and https://github.com/microsoft/vscode/issues/303103 describe the menu missing after selecting the options (failed appx registration). This report is the distinct case where the folders-only selection is ignored by design of the current gating, so it is related but not the same observable symptom.
- **no fix on main:** The gating described above is present in the checkout at main as of 2026-10-15; this shard's history is squashed, so no fix commit could be identified and none is implied by the current source.
