# Issue #316870 — VS Code Installer Option Add "Open with Code" action to Windows Explorer directory context menu failed

[https://github.com/microsoft/vscode/issues/316870](https://github.com/microsoft/vscode/issues/316870)

## Summary

Keep open: current source confirms that selecting directory integration alone on Windows 11 does not enable the modern context-menu handler. This checkbox-dependent defect is distinct from the related registration-failure and update reports.

## Change summary

Make the installer’s directory context-menu option work when the file context-menu option is unchecked.

## Best solution

Honor the file and directory installer selections independently across modern and classic Windows context menus. Coordinate the installer’s registration state with the packaged Explorer handler rather than enabling both kinds of menu entry as a workaround.

## Plan brief

- **Likely files:** `build/win32/code.iss`, `resources/win32/appx/AppxManifest.xml`, `build/win32/explorer-dll-fetcher.ts`
- **Validation:** On a clean Windows 11 user installation with modern context menus, exercise all four file/directory checkbox combinations, restarting Explorer between cases to clear handler caching. Verify directory-only selection exposes the folder action without enabling file actions, file-only selection does the converse, both enables both, and neither enables neither. Confirm the folder action opens the selected directory, then repeat the selection matrix with forced classic menus and check that reinstall/update preserves the selected behavior.
- **Behavior:**

  > Selecting only the installer’s directory context-menu option must make Open with Code available for directories on Windows 11. Leaving the file option unchecked must not enable file context-menu integration as a side effect. Each checkbox must independently control its advertised integration, including the both-selected and neither-selected cases. Acceptance includes successfully opening the chosen directory and preserving existing classic-menu behavior.
- **Trace:**

  > In build/win32/code.iss, the modern VSCodeContextMenu registry key is controlled exclusively by addcontextmenufiles, while ShouldInstallLegacyFolderContextMenu excludes normal modern-menu installs. The adopted handler from https://github.com/microsoft/vscode-explorer-command/blob/676a2a43194e5821af2642926bc0eef9f6edd13f/src/explorer_command.cc hides its command when that shared key is absent, conclusively explaining the directory-only failure without executing Windows. resources/win32/appx/AppxManifest.xml maps files, directories, and directory backgrounds to the same handler, which currently has a single enablement gate. The uncertainty is the integration needed to represent independent selections across installer and handler, not the expected checkbox behavior. Preserve classic-menu selection, background-update repair, and unrelated AppX registration behavior; merely enabling the shared key would not preserve independent file selection. Related reports https://github.com/microsoft/vscode/issues/304214 and https://github.com/microsoft/vscode/issues/303103 concern different diagnosed triggers and are not verified duplicate targets.

## Evidence

- **Exact trigger:** https://github.com/microsoft/vscode/issues/316870 reports selecting addcontextmenufolders while leaving addcontextmenufiles unchecked in the 1.120.0 user installer on Windows 11 build 26200; the directory action is missing.
- **Current installer registration:** build/win32/code.iss:1275 creates Software\Classes\VSCodeContextMenu only under Tasks: addcontextmenufiles. ShouldInstallLegacyFolderContextMenu at lines 1596–1599 honors addcontextmenufolders only when the modern Windows 11 menu is not used, apart from the background-update repair case. A normal modern-menu directory-only install therefore creates neither the shared modern enablement key nor legacy directory entries.
- **Confirmed visibility gate:** build/win32/explorer-dll-fetcher.ts adopts vscode-explorer-command v8.0.0-398351. Its source at https://github.com/microsoft/vscode-explorer-command/blob/676a2a43194e5821af2642926bc0eef9f6edd13f/src/explorer_command.cc implements IsContextMenuEnabled by checking the VSCodeContextMenu registry key; ExplorerCommandHandler::GetState returns ECS_HIDDEN when that key is absent. This completes the source-only trace of the reported failure.
- **Shared-handler boundary:** resources/win32/appx/AppxManifest.xml:66–76 assigns Directory, Directory\Background, and file entries to the same handler CLSID. The adopted handler uses one shared enablement gate, so enabling that key for directory selection alone would also enable file entries unless selection semantics are addressed.
