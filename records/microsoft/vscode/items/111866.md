## Summary

Keep open: another WSL2 user confirmed the terminal-versus-Source-Control discrepancy, and explicitly selecting the key works around authentication but does not explain the hanging push. Current source identifies the environment boundary to investigate, but neither a verified fix nor a canonical issue covering this case was established.

## Change summary

Source Control push hangs in WSL2 with a non-default SSH key loaded through ssh-add, while terminal push succeeds.

## Best solution

Establish why the WSL extension host's Git process cannot use the agent available to the terminal, and ensure authentication failures terminate or present an actionable prompt instead of leaving push pending. Preserve support for arbitrary key filenames through ordinary SSH configuration and agent discovery.

- **Behavior:**

  > The reported WSL2 workflow can push from the terminal using an SSH key loaded with ssh-add, but Source Control push remains pending unless the key is renamed to id_rsa or explicitly selected through core.sshCommand. Supported agent-based authentication should not require a default key filename. Acceptance requires successful terminal and Source Control pushes with the same non-default key, plus observable failure or prompting when authentication cannot complete. First reproduce this on a current build; historical confirmations do not prove the defect remains today.
- **Trace:**
