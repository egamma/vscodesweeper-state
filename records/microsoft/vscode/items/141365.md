# Issue #141365 — Wrong keybind is used with colemak & russian layout

[https://github.com/microsoft/vscode/issues/141365](https://github.com/microsoft/vscode/issues/141365)

## Summary

The defect remains present on current main: when a non-Latin layout lacks A-Z mappings, VS Code synthesizes QWERTY-position mappings rather than retaining the user's Colemak/Dvorak correspondence. The required fallback semantics need a maintainer decision, so this should remain open in the keyboard-layout backlog.

## Change summary

Switching from Colemak to a non-Latin keyboard layout changes shortcuts to QWERTY equivalents instead of preserving the same physical-key actions.

## Best solution

Define and implement a Linux fallback policy that preserves shortcuts from the user's selected Latin layout while a non-Latin layout is active, without breaking ordinary QWERTY, mixed Latin, or runtime layout-switching behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/services/keybinding/common/macLinuxKeyboardMapper.ts`, `src/vs/workbench/services/keybinding/electron-browser/nativeKeyboardLayoutService.ts`, `src/vs/workbench/services/keybinding/test/node/macLinuxKeyboardMapper.test.ts`
- **Validation:** Add a targeted keyboard-layout test that transitions from a Colemak mapping to a Russian mapping and asserts that Ctrl plus physical KeyG continues resolving as Ctrl+D, while existing QWERTY and non-Latin mapping tests remain unchanged.
- **Behavior:**

  > When a user switches from Colemak or another Latin layout to a non-Latin layout, shortcuts should continue following the same physical-key-to-Latin-key correspondence rather than reverting to QWERTY positions. Switching back must restore the active Latin layout normally. Acceptance should cover Colemak-to-Russian switching, standard QWERTY-to-Russian switching, and both keyboard.dispatch modes without changing text input.
- **Trace:**

  > MacLinuxKeyboardMapper in src/vs/workbench/services/keybinding/common/macLinuxKeyboardMapper.ts builds missingLatinLettersOverride whenever the current mapping lacks A-Z, assigning each Latin letter to its identically named scan code; this conclusively turns Russian ScanCode.KeyG into G regardless of the user's prior Colemak layout. NativeKeyboardLayoutService in src/vs/workbench/services/keybinding/electron-browser/nativeKeyboardLayoutService.ts replaces the stored mapping on every native layout-change event, with no retained Latin reference mapping. The uncertainty begins at the fallback policy: the reference could be the startup layout, the most recently active Latin layout, or an explicit configured layout. The boundary is keyboard shortcut resolution; text production and ordinary native layout detection must not change. https://github.com/microsoft/vscode/issues/23991 is related Linux keymap work but does not cover this cross-layout fallback behavior.
- **Open decisions:**
  - Should a non-Latin layout inherit shortcut positions from the startup Latin layout, the most recently active Latin layout, or an explicitly configured reference layout?
  - Should the reference mapping persist across restarts, or only across layout changes within the current window?
  - How should mixed layouts that provide only some Latin letters combine their native mappings with the reference layout?

## Evidence

- **current source path:** src/vs/workbench/services/keybinding/common/macLinuxKeyboardMapper.ts:429-493 detects layouts missing Latin letters and synthesizes A-Z using matching physical scan codes; for a Russian mapping this forces ScanCode.KeyG to G, losing the preceding Colemak mapping where that physical key produces D.
- **layout switching:** src/vs/workbench/services/keybinding/electron-browser/nativeKeyboardLayoutService.ts:45-54 replaces the active mapping and fires onDidChangeKeyboardLayout whenever the native layout changes, so the mapper is rebuilt from the non-Latin mapping rather than retaining a Latin reference layout.
- **confirmed reports:** The reporter reproduced the regression in Insiders and supplied mappings and keybinding traces; later comments independently confirmed it across Russian, Chinese, and Japanese layouts and described the same QWERTY fallback.
- **existing setting insufficient:** src/vs/platform/keyboardLayout/common/keyboardConfig.ts exposes only keyboard.dispatch values code/keyCode; the issue's traces confirm that both modes resolve the Russian physical KeyG as Ctrl+G rather than the expected Colemak Ctrl+D.
- **canonical check:** https://github.com/microsoft/vscode/issues/23991 remains open but concerns setxkbmap modifier/remapping recognition, including Caps Lock remaps; it does not own this issue's distinct cross-layout Latin fallback semantics.
