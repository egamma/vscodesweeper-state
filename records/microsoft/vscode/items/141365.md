# Issue #141365 — Wrong keybind is used with colemak & russian layout

[https://github.com/microsoft/vscode/issues/141365](https://github.com/microsoft/vscode/issues/141365)

## Summary

Keep open: the current mapper still substitutes QWERTY positions for missing Latin letters, explaining why the same physical shortcut changes commands when switching from Colemak to Russian. The older setxkbmap issue covers a different observable problem and is not a verified duplicate.

## Change summary

Preserve the Colemak shortcut positions when switching to Russian instead of unexpectedly resolving those positions as QWERTY shortcuts.

## Best solution

Provide consistent shortcut resolution for paired non-QWERTY Latin and non-Latin layouts in the native keyboard-layout service and mapper. A maintainer should first settle how the reference Latin layout is selected, without breaking ordinary layout switching or standalone Russian configurations.

- **Behavior:**

  > With Colemak and Russian configured, Ctrl on the physical KeyG position invokes editor.action.addSelectionToNextFindMatch in both layouts rather than switching to workbench.action.gotoLine under Russian. The behavior must remain consistent when switching back to Colemak. Ordinary Russian/QWERTY shortcuts and explicit physical-key user bindings must remain supported. Acceptance includes a paired-layout regression test and a Linux layout-switching check.
- **Trace:**

  > MacLinuxKeyboardMapper in src/vs/workbench/services/keybinding/common/macLinuxKeyboardMapper.ts fills absent Latin characters using fixed QWERTY scan-code positions in missingLatinLettersOverride. NativeKeyboardLayoutService replaces the active mapping on each layout change; KeyboardLayoutService recreates the mapper, and WorkbenchKeybindingService rebuilds resolved command bindings. This explains the supplied Ctrl+[KeyG] logs without attributing the defect solely to Chromium keyCode translation. Existing keyboard.dispatch does not supply a reference Latin layout, and keyboard.layout is web-specific. The thread at https://github.com/microsoft/vscode/issues/141365 suggests either explicit layout association or retaining the startup layout, but neither proposal has been accepted by a maintainer. Preserve normal layout-change handling and existing standalone-layout behavior; the uncertainty is which reference-layout contract should govern mixed-layout shortcuts. The existing keyboardMapper - LINUX ru suite provides a regression-test starting point.
- **Open decisions:**
  - For a non-Latin layout paired with a non-QWERTY Latin layout, should shortcut positions follow an automatically selected Latin layout or an explicitly configured layout association, and what should happen when multiple Latin layouts are available?

## Evidence

- **Reported trigger and independent confirmations:** https://github.com/microsoft/vscode/issues/141365 documents Ctrl+[KeyG] invoking addSelectionToNextFindMatch under Colemak but gotoLine under Russian, including dispatch logs, a 1.61-to-1.62 regression range, and unsuccessful keyCode-dispatch testing. Subsequent commenters confirm persistence and distinguish working Ukrainian/Serbian layouts from failing Russian/Chinese/Japanese layouts.
- **Current source explains the command change:** src/vs/workbench/services/keybinding/common/macLinuxKeyboardMapper.ts constructs missingLatinLettersOverride from the active mapping and explicitly assigns missing G to ScanCode.KeyG and missing D to ScanCode.KeyD. Consequently, Russian mappings without Latin letters resolve G at physical KeyG, whereas Colemak resolves D there; the constructor receives no reference Colemak mapping.
- **Layout switching rebuilds the resolver:** src/vs/workbench/services/keybinding/electron-browser/nativeKeyboardLayoutService.ts replaces its active mapping on layout-change events. KeyboardLayoutService in electron-browser/nativeKeyboardLayout.ts invalidates the cached mapper, and browser/keybindingService.ts:208-212 obtains the replacement mapper and updates the resolver. Default bindings are translated through that mapper in _resolveKeybindingItems, so unchanged physical event codes do not guarantee unchanged commands.
