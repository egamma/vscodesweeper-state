# Issue #338820 — Chat Completions models lose reasoning from earlier user turns (breaks Kimi K3 preserved thinking)

[https://github.com/microsoft/vscode/issues/338820](https://github.com/microsoft/vscode/issues/338820)

## Summary

Well-diagnosed, source-confirmed defect: historical reasoning is only replayed for the Responses API or Messages models with adaptive thinking, so Chat Completions models like Kimi K3 lose reasoning across turns exactly as described, unchanged on main.

## Change summary

For Chat Completions models, assistant-message reasoning from prior user turns is stripped from the prompt, breaking models (like Kimi K3) that expect preserved thinking across turns.

## Best solution

Extend the historical-thinking replay gate in toolCalling.tsx to a per-model opt-in for Chat Completions models that need preserved reasoning, without disturbing the existing protection for models that reject replayed thinking (see #318076).

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/prompts/node/panel/toolCalling.tsx`, `extensions/copilot/src/platform/networking/common/networking.ts`
- **Validation:** A test in toolCalling.spec.ts asserting that historical rounds retain `reasoning_text`/`reasoning_opaque` for a Chat Completions endpoint flagged as supporting preserved reasoning, and continue to drop it for endpoints without that flag.
- **Behavior:**

  > For Chat Completions endpoints whose model is flagged as expecting preserved reasoning across turns (e.g. Kimi K3), historical assistant rounds should retain their reasoning/thinking content in subsequent requests, the same way Responses-API rounds already do. Endpoints not opted in keep today's stripping behavior (needed to avoid 400s per #318076). Acceptance: a new test confirms reasoning survives into turn 2 for an opted-in model and is still stripped for a non-opted-in one.
- **Trace:**

  > In extensions/copilot/src/extension/prompts/node/panel/toolCalling.tsx, `apiSupportsHistoricalThinking` only returns true for apiType 'responses' or ('messages' + modelSupportsHistoricalThinking via IEndpoint.supportsAdaptiveThinking, defined in extensions/copilot/src/platform/networking/common/networking.ts:340). Chat Completions endpoints have no equivalent flag, so `includeThinking` is always false once `isHistorical` is true, stripping `round.thinking` from replay. The boundary: do not change behavior for Responses or adaptive-thinking Messages models, and preserve the existing protection for Messages models that reject replayed blocks (#318076). Uncertainty starts at how the new per-model capability is declared/plumbed (new endpoint flag vs. reusing an existing one) and what the default should be for unknown/custom Chat Completions models.
- **Open decisions:**
  - Should the opt-in be a new endpoint capability flag analogous to supportsAdaptiveThinking, or reuse/extend an existing one, and how is it populated for BYOK/custom Chat Completions endpoints (e.g. Kimi K3)?
  - What is the default for Chat Completions models without an explicit flag — keep stripping (safe) or attempt replay (matches Responses behavior)?

## Evidence

- **code confirms gate:** extensions/copilot/src/extension/prompts/node/panel/toolCalling.tsx: `apiSupportsHistoricalThinking = apiType === 'responses' || (apiType === 'messages' && modelSupportsHistoricalThinking)`, and `includeThinking = sameModelAsEndpoint && (!isHistorical || apiSupportsHistoricalThinking)` — Chat Completions ('openai'-style) apiType never satisfies this, so historical rounds drop `thinking` unconditionally.
- **unchanged on main:** Confirmed the same logic is present on current main; the issue explicitly notes the code is unchanged from 1.139.0-insider.
- **related tension:** The existing guard exists because some Messages models 400 on replayed thinking blocks (referenced issue #318076 in the comment above modelSupportsHistoricalThinking), so a blanket fix for Chat Completions risks the same failure mode for models that reject replay.
