# Issue #36769 — Support envfile for tasks.json

[https://github.com/microsoft/vscode/issues/36769](https://github.com/microsoft/vscode/issues/36769)

## Summary

Keep open: current task configuration and execution still lack native environment-file loading. The 154 upvotes and sustained requests support retaining this accepted Backlog item; Docker-specific support and shell wrappers do not cover ordinary shell and process tasks.

## Change summary

Allow tasks.json to load environment variables from a shared external file instead of duplicating them in inline env objects.

## Best solution

Provide native environment-file support in task options for shell and process tasks, allowing committed task definitions to reference developer-local files also used by debuggers and external scripts. Agree on parsing and environment-precedence semantics before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/tasks/common/jsonSchemaCommon.ts`, `src/vs/workbench/contrib/tasks/common/jsonSchema_v2.ts`, `src/vs/workbench/contrib/tasks/common/tasks.ts`, `src/vs/workbench/contrib/tasks/common/taskConfiguration.ts`, `src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts`, `src/vs/workbench/contrib/tasks/test/common/taskConfiguration.test.ts`
- **Validation:** After agreeing on semantics, add configuration tests and run the taskConfiguration.test.ts suite. Validate end-to-end with shell and process tasks that launch a child program printing non-sensitive fixture variables: file-only values must reach both children, collisions must follow the agreed precedence, edits to the file must be reflected on rerun, and tasks without an environment file must remain unchanged. Include Windows and POSIX execution and a missing-file case.
- **Behavior:**

  > A committed task definition can reference a separate environment file shared with debugger configurations and external scripts. Running either a shell or process task makes the file's variables available to its child process without a shell-specific sourcing command or an additional CLI dependency. Acceptance checks cover file loading, reruns after file edits, agreed precedence against inline and inherited values, and clear handling of unreadable files. Existing tasks without this option retain their current behavior.
- **Trace:**

  > The current schema defines inline env and cwd, with shell added by jsonSchema_v2.ts; CommandOptions and ICommandOptionsConfig carry no environment-file property. CommandOptions.from in taskConfiguration.ts retains only cwd, env and shell, while TerminalTaskSystem._resolveOptions resolves inline values and _createShellLaunchConfig transfers them to the task terminal. This establishes a missing capability rather than a defect in existing env behavior. Docker-specific envFiles and shell/dotenv-cli wrappers in https://github.com/microsoft/vscode/issues/36769 are partial workarounds, not generic support. Keep the scope to task child-process environments; do not assume this also changes global environment state or ${env:NAME} substitution. https://github.com/microsoft/vscode/issues/69233 discusses a broader workspace environment design but is newer and is not a duplicate canonical. Uncertainty begins at the public contract for file syntax and precedence, not at whether the current task path loads files.
- **Open decisions:**
  - Which environment-file syntax is supported, including quoting, export prefixes, multiline values and variable interpolation?
  - When the same variable appears in inherited environment values, global task options, an environment file and task-specific inline env, which value wins?
