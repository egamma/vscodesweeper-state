# Issue #93470 — Event for onWill|DidRename|Create|Delete should indicate what caused the event (explorer vs workspace edit)

[https://github.com/microsoft/vscode/issues/93470](https://github.com/microsoft/vscode/issues/93470)

## Summary

The requested operation-origin metadata is still absent from the public file-event API and its delivery path. Keep this accepted Backlog request open; the related rename-specific request is newer and cannot serve as the canonical for this re-reviewed, broader item.

## Change summary

Expose what initiated file creation, deletion, and rename events so extensions can distinguish Explorer actions from workspace edits.

## Best solution

Define a consistent public origin contract across the six will/did file-operation events, allowing extensions to avoid redundant refactoring for workspace edits. Resolve that contract alongside the related discussion about suppressing events caused by onWill listeners, without treating suppression alone as coverage of the broader request.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostFileSystemEventService.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadFileSystemEventService.ts`, `src/vs/workbench/services/workingCopy/common/workingCopyFileService.ts`
- **Validation:** After the public contract is agreed, add extension-host API checks that create, rename, and delete files through Explorer actions and workspace.applyEdit, asserting the agreed origin on both will and did events. Include a listener-returned WorkspaceEdit case to verify the agreed nested-event behavior and preserve existing waitUntil participation.
- **Behavior:**

  > Extensions currently receive file-operation events without knowing whether the user acted in Explorer or an operation came from a workspace edit. The goal is to distinguish those origins consistently for creation, deletion, and rename, before and after the operation. Acceptance should cover both initiation paths for all three operations and the agreed behavior when an onWill listener contributes another workspace edit. Existing event participation and file payloads must remain compatible.
- **Trace:**

  > The public event interfaces in src/vscode-dts/vscode.d.ts have no origin field. ExtHostFileSystemEventService in src/vs/workbench/api/common/extHostFileSystemEventService.ts constructs payloads containing only file URIs, while the RPC methods in extHost.protocol.ts and their callers in mainThreadFileSystemEventService.ts transmit no initiating origin. WorkingCopyFileEvent and IWorkingCopyFileOperationParticipant in workingCopyFileService.ts likewise have no origin contract; SourceTargetPair.source is a URI, not provenance. The API gap is confirmed, but reliable provenance propagation from initiating callers has not been fully traced. https://github.com/microsoft/vscode/issues/114514 supplies a concrete redundant-refactoring scenario, and https://github.com/microsoft/vscode/issues/114514#issuecomment-762100277 raises suppression of listener-caused events as an alternative. Preserve existing cancellation, waitUntil, and undo behavior unless API owners explicitly choose a contract change; do not expand this into Java-specific refactoring work.
- **Open decisions:**
  - Should origin distinguish only user actions from workspace edits, or specifically identify Explorer initiation and other initiating surfaces?
  - Should file operations contributed by onWill listeners emit events with a distinct origin, or suppress those events as suggested in the related discussion?

## Evidence

- **Existing-capability check:** src/vscode-dts/vscode.d.ts:13554–13748 defines FileWillCreateEvent, FileCreateEvent, FileWillDeleteEvent, FileDeleteEvent, FileWillRenameEvent, and FileRenameEvent without operation-origin metadata. The will events expose files, cancellation, and waitUntil; the did events expose files. These existing contracts do not deliver the central ask.
- **Current delivery path:** src/vs/workbench/api/common/extHostFileSystemEventService.ts constructs will/did event payloads from file URIs only. src/vs/workbench/api/common/extHost.protocol.ts:2657–2658 carries operation and source/target URI pairs, not initiating origin; mainThreadFileSystemEventService.ts:79 and :207 forwards those arguments. SourceTargetPair.source in workingCopyFileService.ts means the original file URI, not the cause of the operation.
- **Motivating extension scenario:** https://github.com/redhat-developer/vscode-java/issues/1222#issuecomment-603750889 explains that moving a Java class between packages requires computing reference updates before the move, and that the onWillRenameFiles listener cannot distinguish Explorer actions from applyEdit. This is a missing VS Code API capability, not grounds to redirect the request to the Java extension.
- **Canonical search:** Searches for file-event origin and onWillRenameFiles found https://github.com/microsoft/vscode/issues/114514, verified open and created on 2021-01-18, after this issue's 2020-03-26 creation. It asks for rename-event source metadata to avoid recomputing an existing rename refactoring; it is narrower and newer, so it does not satisfy the duplicate bar for this re-reviewed item.
- **Related design interest:** https://github.com/microsoft/vscode/issues/114514#issuecomment-762100277 agrees with the problem and offers an alternative: suppress events for edits caused by onWill listeners. That establishes interest but leaves the observable API/event-delivery contract undecided.
- **Related merged PR is not this implementation:** https://github.com/redhat-developer/vscode-java/pull/1372 implements Java class-name and reference updates on file rename. It does not establish implementation of operation-origin metadata in VS Code; the current public declarations and event bridge still lack that metadata.
