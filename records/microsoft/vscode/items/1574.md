# Issue #1574 — Task and/or Extension Command User Arguments On Entry

[https://github.com/microsoft/vscode/issues/1574](https://github.com/microsoft/vscode/issues/1574)

## Summary

Task input prompts now cover runtime argument entry, but entering arguments directly alongside a task or extension command in the Command Palette remains unsupported. Keep this accepted Backlog request open: it has 43 upvotes, and the related open command-contribution issue does not own the same interactive-input capability.

## Change summary

Allow users to supply one-time arguments when invoking tasks or extension commands from the Command Palette.

## Best solution

Retain existing task input prompts and extension input-box APIs, and resolve whether an opt-in inline argument contract should complement them. Any supported design should distinguish command search from argument entry without changing ordinary palette matching.

## Plan brief

- **Likely files:** `src/vs/platform/quickinput/browser/commandsQuickAccess.ts`, `src/vs/workbench/contrib/quickaccess/browser/commandsQuickAccess.ts`, `src/vs/workbench/services/configurationResolver/browser/baseConfigurationResolverService.ts`, `src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts`
- **Validation:** After selecting the product contract, use a test extension whose command displays its received arguments: invoke it with two different one-time values through the agreed palette flow and verify exact delivery, including spaces. Exercise the equivalent task invocation and verify the emitted argument; confirm ordinary command search, cancellation, and existing promptString task inputs retain their behavior.
- **Behavior:**

  > Users want to supply a one-time value while invoking a task or extension command, without editing tasks.json for each run. Existing task prompts satisfy separate runtime input, but not the requested command-and-argument entry in the palette. The plan must establish the supported interaction and argument contract before implementation. Acceptance should verify exact argument delivery on successive invocations and preserve ordinary command search and existing task prompts.
- **Trace:**

  > AbstractCommandsQuickAccessProvider._getPicks in src/vs/platform/quickinput/browser/commandsQuickAccess.ts uses the whole entered string for command matching; command execution forwards predefined commandPick.args rather than a parsed user suffix. CommandsQuickAccessProvider.getGlobalCommandPicks in src/vs/workbench/contrib/quickaccess/browser/commandsQuickAccess.ts creates ordinary contributed-command entries without such arguments. BaseConfigurationResolverService already resolves promptString inputs, and TerminalTaskSystem calls resolveWithInteraction, confirming the task-prompt capability mentioned in https://github.com/microsoft/vscode/issues/64214. The remaining uncertainty is the supported inline-input interaction and public extension contract, not whether task prompts exist. Preserve existing search, task-variable resolution, and extension-provided input boxes. https://github.com/microsoft/vscode/issues/41692 concerns static contributed arguments, while the closed https://github.com/microsoft/vscode/issues/70889 records a previous decline of inline command parameters that the maintainer should consider before reopening that design direction.
- **Open decisions:**
  - Should the supported experience accept command/task names and arguments in one palette entry, or retain separate input prompts as the product boundary?
  - If inline input is supported, what opt-in extension contract distinguishes argument text from command-search text, and does it deliver a raw string or structured arguments?
