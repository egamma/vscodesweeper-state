# Issue #318454 — Upload text without clipboard copy flow

[https://github.com/microsoft/vscode/issues/318454](https://github.com/microsoft/vscode/issues/318454)

## Summary

A real gap remains in the new issue-reporting wizard: oversized issue text still falls back to the clipboard, while the authenticated legacy reporter already supports direct issue creation. The team-authored request should remain open while maintainers settle the wizard's Preview versus Create interaction.

## Change summary

Let authenticated users create an issue with the complete generated body directly, avoiding the error-prone clipboard fallback for oversized reports.

## Best solution

Offer authenticated users both Preview on GitHub and direct Create on GitHub actions in the wizard, with direct creation preserving the full generated body and uploaded attachment links. Retain the current preview-only path when authentication or the selected issue target does not support direct creation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/issue/browser/issueFormService.ts`, `src/vs/workbench/contrib/issue/browser/issueReporterOverlay.ts`, `src/vs/workbench/contrib/issue/browser/githubUploadService.ts`, `src/vs/workbench/contrib/issue/browser/baseIssueReporterService.ts`, `src/vs/workbench/contrib/issue/test/browser/issueReporterOverlay.test.ts`
- **Validation:** Exercise the wizard with an authenticated GitHub session and a body exceeding `MAX_URL_LENGTH`: direct Create must open the newly created issue containing the complete generated text and attachment links without reading from the clipboard, while Preview must continue opening an editable GitHub preview. Add targeted issue-reporter tests for action availability and submitted-body preservation.
- **Behavior:**

  > Authenticated users can choose between previewing an issue on GitHub and creating it directly. Direct creation preserves the complete generated body and uploaded attachment links even when the preview URL would exceed its length limit, without requiring a clipboard copy-and-paste step. Preview remains available for users who want to edit before submission, and unsupported or unauthenticated targets retain their existing behavior.
- **Trace:**

  > The wizard submission path is `IssueReporterOverlay` to `IssueFormService.submitIssue` in src/vs/workbench/contrib/issue/browser/issueFormService.ts. That method uploads media, constructs a preview URL, attempts to shorten oversized bodies through an uploaded issue-data attachment, and finally falls back to `clipboardService.writeText` when the URL still exceeds `MAX_URL_LENGTH`. The Review step in src/vs/workbench/contrib/issue/browser/issueReporterOverlay.ts exposes only `Preview on GitHub`. The legacy `BaseIssueReporterService` already has separate create and preview actions plus an authenticated direct-submit path, so it is useful prior art; preserve preview behavior, external-extension routing, authentication boundaries, attachment upload error handling, and private/internal reporting behavior. The uncertainty begins at the public interaction: the thread proposes both actions but does not settle which should be primary.
- **Open decisions:**
  - For authenticated users, should Preview on GitHub remain the primary action with Create on GitHub in the dropdown, or should direct Create be primary as in the legacy reporter?

## Evidence

- **current wizard UI:** src/vs/workbench/contrib/issue/browser/issueReporterOverlay.ts labels the Review-step submission action `Preview on GitHub` and has no direct-create action or dropdown.
