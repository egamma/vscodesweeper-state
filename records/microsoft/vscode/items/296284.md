# Issue #296284 — Copilot Review appears to do nothing in a Jupyter Notebook

[https://github.com/microsoft/vscode/issues/296284](https://github.com/microsoft/vscode/issues/296284)

## Summary

Keep open: current source still exposes a mismatch between Copilot's document-range review comments and notebook comment rendering, with no Comments-view fallback in the review presentation path. The older related issues do not own this report's specific failure to surface completed Copilot reviews.

## Change summary

Make completed notebook Copilot reviews discoverable instead of leaving their comments hidden and their suggestions inaccessible.

## Best solution

Ensure notebook selection reviews visibly present their results, with a Comments-view fallback when inline presentation is unavailable. Coordinate notebook comment navigation and suggestion support with the existing notebook-commenting work without making basic result discovery depend on that broader API design.

- **Behavior:**

  > Selecting notebook-cell code and invoking Chat: Review currently completes review generation without visibly presenting its findings. Completed reviews with findings must provide a discoverable result surface, at minimum the Comments view when inline notebook presentation is unavailable. The report also identifies ineffective comment navigation and inaccessible suggestions, which must be explicitly accounted for in the agreed scope. Acceptance must distinguish reviews with findings from empty results, cancellation, and errors, while preserving ordinary text-file review behavior.
- **Trace:**

  > The command registration in extensions/copilot/src/extension/inlineChat/vscode-node/inlineChatCommands.ts calls ReviewSession in extensions/copilot/src/extension/review/node/doReview.ts, whose progress callback sends comments to ReviewServiceImpl.addReviewComments. That service creates regular-range comment threads and initiates review.next; navigation calls CommentThread.reveal without a Comments-view fallback. MainThreadCommentController classifies those ranges as document threads, excludes notebook-cell resources from getDocumentComments, and requires non-document threads in getNotebookComments, establishing the notebook rendering mismatch without execution. CellComments consumes that notebook-only path, while the shared revealCommentThread helper handles code-editor comment controllers. The remaining uncertainty is the intended delivery scope for fallback discovery versus full notebook navigation and suggestions, and how explicit view-opening preferences should interact with a user-requested review. Keep review generation, authentication, ordinary text-file presentation, and unrelated notebook editing unchanged. https://github.com/microsoft/vscode/issues/214017 provides related notebook-comment API design context, not a duplicate of this result-discovery defect.
- **Open decisions:**
  - Should this issue deliver the minimum visible Comments-view fallback first, with notebook navigation and actionable suggestions tracked separately, or require all three behaviors together?
  - Should a user-invoked notebook review with findings open and focus Comments when comments.openView is explicitly set to never, or honor that preference and provide another visible result affordance?
