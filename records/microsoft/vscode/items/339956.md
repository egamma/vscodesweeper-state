# Issue #339956 — Same-named MCP servers in different workspace roots overwrite each other, so their enablement is shared

[https://github.com/microsoft/vscode/issues/339956](https://github.com/microsoft/vscode/issues/339956)

## Summary

Credible, concretely-evidenced bug: a multi-root workspace with same-named MCP servers in different folders can have one folder's disable action visibly affect the other's enablement status. The reporter captured the exact storage key and log line, which is a genuine confirmed repro, but my own source trace shows the mechanism is more subtle than the issue's 'likely cause' (the merge in `getEnabledLocalMcpServers` is about execution precedence, not the enablement-status display) — the real interaction likely runs through `McpCollisionEnablementModel`/`getRuntimeStatus`'s fallback to a hardcoded Disabled state for a server that loses a name collision, which looks identical to 'Disabled (Globally)' in the UI even though nothing disabled it.

## Change summary

Disabling one workspace root's MCP server named the same as another root's server also makes the other root's same-named server show as disabled.

## Best solution

Clarify/fix the MCP enablement UI so a server that is merely losing the name-collision (handled intentionally by `McpCollisionEnablementModel`'s collision-disable behavior) is distinguished from one the user actually disabled — likely touching `getRuntimeStatus`/`getEnablementStatus` in mcpWorkbenchService.ts and the collision model in src/vs/workbench/contrib/chat/common/enablement.ts.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/browser/mcpWorkbenchService.ts`, `src/vs/workbench/contrib/chat/common/enablement.ts`, `src/vs/workbench/contrib/mcp/common/mcpService.ts`
- **Validation:** A test asserting that explicitly disabling one workspace root's same-named MCP server leaves `getRuntimeStatus`/enablement for the other root's same-named server unaffected (or correctly reflects 'superseded' rather than 'Disabled (Globally)' if collision-disable intentionally applies).
- **Behavior:**

  > When two workspace roots each define an MCP server with the same name, explicitly disabling one root's server must not change the displayed enablement state of the other root's server unless the product intends collision-disable semantics to apply — in which case the UI should clearly say 'superseded by another server with this name' rather than 'Disabled (Globally)', so the user isn't misled into thinking they disabled something they didn't. Acceptance: toggling one same-named server's enablement in the Customizations UI only changes `mcp.enablement` storage for that server's own id, and the other server's displayed status accurately reflects its own state (enabled, or a collision-specific message if that's the intended design).
- **Trace:**

  > Workspace servers get distinct definition ids like `mcp.config.ws0.<name>` / `mcp.config.ws1.<name>` (confirmed via src/vs/workbench/contrib/mcp/test/browser/mcpWorkbenchService.test.ts lines 946-948), so the base `EnablementModel` keys should not collide. However, `McpCollisionEnablementModel`/`CollisionEnablementModel` (src/vs/workbench/contrib/chat/common/enablement.ts lines 174-236, wired in src/vs/workbench/contrib/mcp/common/mcpService.ts) intentionally auto-disables a lower-priority same-labeled server, and `getRuntimeStatus` in mcpWorkbenchService.ts (~line 1032) falls back to a hardcoded `Disabled` state for any workbench entry missing from `this.mcpService.servers` — the same path a collision-losing duplicate takes — so the UI cannot currently tell the user 'this is disabled because you disabled it' from 'this is disabled because another same-named server won the collision'. Do not change the existing collision-disable mechanism's intent (avoiding duplicate concurrent launches) without a maintainer decision; the boundary is the status/messaging layer plus the enablement-key independence per workspace root, not the overwrite logic in `getEnabledLocalMcpServers` that the reporter's 'likely cause' points at — that function only decides execution precedence for already-resolved local servers.
- **Open decisions:**
  - Should the two same-named servers remain fully independent in the UI (today's collision-disable auto-mutes the lower-priority one), or is collision-disable intended behavior that just needs clearer, distinct messaging ('superseded' vs 'Disabled (Globally)')?
  - If collision-disable stays, should users still be able to independently enable/disable each root's instance, overriding the automatic collision behavior per-root?

## Evidence

- **collision-disable is by design:** src/vs/workbench/contrib/mcp/common/mcpService.ts `McpCollisionEnablementModel` and src/vs/workbench/contrib/chat/common/enablement.ts `CollisionEnablementModel` (lines ~174-236) intentionally auto-disable a lower-priority, same-labeled server when `mcp.serverCollisionBehavior` is 'Disable' (the default) — this is documented as 'mutual-exclusion logic for MCP servers with the same label', not a storage bug.
- **fallback status is ambiguous:** `getRuntimeStatus` in mcpWorkbenchService.ts (around line 1032-1041) returns a hardcoded `{ state: McpServerEnablementState.Disabled }` when a workbench server entry has no matching entry in `this.mcpService.servers` — which is exactly what happens to the collision-losing duplicate — making it visually indistinguishable from an explicit 'Disabled (Globally)' state.
- **distinct storage keys confirmed:** Tests in src/vs/workbench/contrib/mcp/test/browser/mcpWorkbenchService.test.ts (e.g. line 946-948, `mcp.config.ws0.same` / `mcp.config.ws1.same`) show each workspace root does get a distinct definition id, consistent with the reporter's observation that storage only contains one key (`mcp.enablement`'s `mcp.config.ws1.shared=false`) yet both entries show disabled.
- **first-hand reproduction:** Reporter (a contributor who also filed microsoft/vscode#338716) included the exact failing log line ('Overwriting mcp server...') and the actual storage content from a real insiders build (1.141.0-insider), which is concrete first-hand evidence rather than a speculative report.
