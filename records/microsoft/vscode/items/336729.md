# Issue #336729 — Codex Agent Host on Linux: workspace sandbox hides the bundled Codex executable

[https://github.com/microsoft/vscode/issues/336729](https://github.com/microsoft/vscode/issues/336729)

## Summary

Confirmed from source: the Codex Linux sandbox profile denies `:root` filesystem access and only allows `:minimal`/`:tmpdir`/`:slash_tmp`, but the bundled Codex binary lives under the SDK cache in the user's data directory (outside those allowed paths), so bwrap can't exec it — every command fails before the shell starts. A commenter's workaround (adding a read permission for the sdk-cache/codex path in Codex's own config.toml) corroborates the diagnosis.

## Change summary

On Linux, the workspace sandbox permission profile hides the bundled Codex executable under the SDK cache directory, so Codex Agent Host can't run any command.

## Best solution

Extend `codexPermissionProfileOverrides` (or its caller in `buildCodexLaunchConfig`) to grant read access to the Codex SDK cache directory itself, mirroring how `:slash_tmp` read access was added for the sandbox helper — but the exact scope (per-version dir vs. the whole `agent-host/sdk-cache` tree) and how to thread the concrete path in from userData need a maintainer decision.

- **Behavior:**

  > On Linux, a Codex Agent Host session with workspace sandboxing enabled must be able to execute the bundled Codex binary from its SDK cache location. Running `pwd`/`ls` (or any shell command) inside the sandbox must succeed instead of failing with `bwrap: execvp ... No such file or directory`. Acceptance: a test confirms the generated permission profile includes read access to the SDK cache path, and no other sandboxed filesystem access changes.
- **Trace:**

  > codexPermissionProfileOverrides() in src/vs/platform/agentHost/node/codex/codexLaunchConfig.ts (lines 16-36) builds the `vscode-workspace` bwrap profile with `:root = deny` and only `:minimal`/`:tmpdir`/`:slash_tmp` (Linux) allowed as reads/writes. agentSdkDownloader.ts (line 443) stores the downloaded Codex binary under `<userDataPath>/agent-host/sdk-cache/codex/<version>/...`, a path not covered by any of those allowances, so bwrap denies exec. The function currently takes no path argument and is a pure string builder; buildCodexLaunchConfig (same file, ~line 90) is the only caller and doesn't have userDataPath in scope today. Boundary: do not change the `:minimal`/`:tmpdir`/`:slash_tmp` semantics or the Windows/macOS profiles; only add a scoped read for the SDK cache location. Related: https://github.com/microsoft/vscode/pull/335409 (added `:slash_tmp` read), https://github.com/openai/codex/issues/29049 (upstream discussion cited by reporter).
- **Open decisions:**
  - Should the granted read scope be the specific `<sdk-cache>/codex/<version>` directory or the whole `agent-host/sdk-cache` tree?
  - How should the concrete userData path be threaded into codexPermissionProfileOverrides/buildCodexLaunchConfig without breaking its currently-pure signature and existing tests?
  - Should this wait for an upstream Codex SDK fix (per openai/codex#29049) instead of a VS Code-side sandbox profile change?

## Evidence

- **sandbox profile:** src/vs/platform/agentHost/node/codex/codexLaunchConfig.ts lines 16-36 build `permissions.vscode-workspace` with `:root = deny`, `:minimal = read`, `:tmpdir = write`, `:slash_tmp = read (linux only)` — no entry covers the SDK cache path.
- **sdk-cache location:** src/vs/platform/agentHost/node/agentSdkDownloader.ts line 443 places the downloaded Codex binary under `<userDataPath>/agent-host/sdk-cache/codex/<version>/...`, which is outside `:minimal`/`:tmpdir`/`:slash_tmp` and thus denied by `:root = deny`.
- **no existing fix:** git log on codexLaunchConfig.ts shows no commit addressing the sdk-cache path; the most recent related change (referenced in the issue) is PR #335409, which only added `:slash_tmp` read access.
- **user workaround:** Comment by varchasgopalaswamy confirms adding `permissions.vscode-workspace.filesystem."<sdk-cache path>" = "read"` to Codex's config.toml resolves the failure, consistent with the missing-path diagnosis.
