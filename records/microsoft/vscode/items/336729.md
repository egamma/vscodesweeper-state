# Issue #336729 — Codex Agent Host on Linux: workspace sandbox hides the bundled Codex executable

[https://github.com/microsoft/vscode/issues/336729](https://github.com/microsoft/vscode/issues/336729)

## Summary

Confirmed on main: the Codex workspace sandbox permission profile denies filesystem access outside `:minimal`/`:tmpdir`/`:slash_tmp`, but the bundled Codex binary lives under `<userDataPath>/agent-host/sdk-cache/...`, which isn't covered — so bwrap can't even exec the binary. No fix has landed yet; this stays open for a maintainer to plumb the sdk-cache path into the permission profile.

## Change summary

On Linux, the Codex Agent Host's workspace sandbox (bwrap) denies read access to the bundled Codex executable under the user's sdk-cache directory, so every sandboxed command fails before it starts.

## Best solution

Extend codexPermissionProfileOverrides() (or its caller) to grant read access to the actual sdk-cache install path (derived from IEnvironmentService.userDataPath, as used in agentSdkDownloader.ts) rather than relying on the generic `:minimal` profile, and add a regression test pinning the generated TOML.

- **Behavior:**

Running `pwd`/`ls` (or any shell tool call) inside a sandboxed Codex session must succeed instead of failing with `execvp: ... No such file or directory`. Acceptance: a test asserting the generated permission TOML includes read access to the actual sdk-cache path passes, and existing codexLaunchConfig tests still pass.
- **Trace:**

  > codexPermissionProfileOverrides() in src/vs/platform/agentHost/node/codex/codexLaunchConfig.ts (lines ~16-36) builds a TOML permission profile with `:root = deny` and only `:minimal`/`:tmpdir`/`:slash_tmp` allowlisted; it takes only a `platform` parameter today. The Codex binary is installed under `<userDataPath>/agent-host/sdk-cache/<pkg>/<sdkVersion>/<sdkTarget>` per agentSdkDownloader.ts (~line 443), a path outside any of those allowlisted entries. Do not touch the `:tmpdir`/`:slash_tmp` handling (added for the sandbox helper materialization, see PR https://github.com/microsoft/vscode/pull/335409) or the network/read-only profile variants. Where the uncertainty starts: whether to grant read on the whole `agent-host/sdk-cache` tree or scope it to the codex-specific subpath, and whether `buildCodexLaunchConfig`'s call site (~line 119) is the right place to source the userDataPath vs. injecting it as a parameter. Related: https://github.com/openai/codex/issues/29049 (upstream Codex sandbox issue) and https://github.com/microsoft/vscode/pull/335409 (prior /tmp read-access fix in the same profile).
- **Open decisions:**
  - Should the read permission cover the whole agent-host sdk-cache tree, or be scoped to just the codex install path (and would that generalize to Claude's SDK cache too)?
  - Should the userDataPath be passed into codexPermissionProfileOverrides() as a new parameter, or resolved at the buildCodexLaunchConfig call site?

## Evidence

- **permission profile:** src/vs/platform/agentHost/node/codex/codexLaunchConfig.ts lines ~16-36: `codexPermissionProfileOverrides()` sets `:root = deny` and only allowlists `:minimal`, `:tmpdir` (write), and on Linux `:slash_tmp` (read) — the sdk-cache directory under the user's home/userDataPath is not covered.
- **sdk-cache location:** src/vs/platform/agentHost/node/agentSdkDownloader.ts line ~443: downloads/installs land under `<userDataPath>/agent-host/sdk-cache/<pkg>/<sdkVersion>/<sdkTarget>` — outside any allowlisted path in the Codex permission profile.
- **workaround:** Commenter varchasgopalaswamy reports that manually adding `[permissions.vscode-workspace.filesystem] "...sdk-cache/codex" = "read"` to Codex's own config.toml resolves it, corroborating the diagnosis.
- **no fix on main:** `git log` on codexLaunchConfig.ts shows no commit referencing this issue or adding an sdk-cache read permission; latest commit on the file is unrelated (merge 44825207).
