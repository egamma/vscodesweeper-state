## Plan brief

- **Likely files:** `src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditor.ts`, `src/vs/editor/browser/widget/multiDiffEditor/multiDiffEditorWidget.ts`, `src/vs/editor/browser/widget/multiDiffEditor/multiDiffEditorWidgetImpl.ts`, `src/vs/editor/browser/widget/multiDiffEditor/diffEditorItemTemplate.ts`
- **Validation:** The plan should establish targeted checks for pane hide/show reaching embedded editors, including templates created or reused after a visibility change; group resizing honoring the agreed minimum dimensions and constraint-change notifications; and dragging the final embedded diff's sash endpoint coordinating with the adjacent workbench boundary sash. Preserve scoped context behavior, focus, scroll position, and virtualization.
- **Behavior:**

  > The multi diff editor should participate in workbench sizing, visibility, and coordinated sash resizing like other embedded-editor panes. Hiding and revealing the pane must deliver the appropriate visibility lifecycle to its embedded editors, including after virtualized template reuse. Its minimum dimensions and size-change notifications must reflect the agreed layout behavior, and the applicable final diff sash must coordinate with the workbench boundary. Existing scoped context, focus, and view-state behavior must remain intact.
- **Trace:**

  > MultiDiffEditor already exposes its widget's scoped context service, but inherits generic size constraints and lacks visibility and boundary-sash overrides. MultiDiffEditorWidget provides no forwarding surface for those contracts, while DiffEditorItemTemplate.render()/hide() currently change DOM geometry and visibility only. TextDiffEditor and MergeEditor provide concrete forwarding and sizing precedents. MultiDiffEditorWidgetImpl manages virtualized items, so pane-level lifecycle state must be considered alongside template creation and reuse; that interaction has not been fully diagnosed. https://github.com/microsoft/vscode/issues/204076 concerns focus integration rather than these remaining requirements. Preserve virtualization, existing scoped context, focus, and view-state restoration; the uncertainty starts with the intended minimum-size contract and its interaction with responsive diff layout.
- **Open decisions:**
  - Should the multi diff pane retain generic workbench minimum dimensions, or expose layout-dependent minimum dimensions for its side-by-side and inline diff modes?
