# Issue #328305 — new profile that use extensions from default profile  will enable extensions that disabled in default profile

[https://github.com/microsoft/vscode/issues/328305](https://github.com/microsoft/vscode/issues/328305)

## Summary

Real, traceable inconsistency: 'Use Extensions from Default Profile' only shares the installed-extensions resource, not the enablement (disabled) state, because those two things are gated by different flags in the storage layer — keep open and route to the profiles/extensions owners.

## Change summary

A new profile created with 'Use Extensions from Default Profile' re-enables extensions that are disabled in the Default profile, instead of inheriting their disabled state.

## Best solution

Fix the mismatch in src/vs/platform/storage/common/storage.ts's isProfileUsingDefaultStorage (and its call sites) so extension-enablement storage (DISABLED_EXTENSIONS_STORAGE_PATH, written via GlobalExtensionEnablementService at StorageScope.PROFILE) is shared with the Default profile whenever useDefaultFlags.extensions is set, not only when useDefaultFlags.globalState is set — or, if enablement state is meant to stay independent per profile, update ExtensionsResourceInitializer/extensionsResource.ts to actively sync the disabled flags on profile creation.

- **Proposed comment:**

  > Thanks for the report — this reproduces from the source. `useDefaultFlags.extensions` only makes the new profile point at the same *installed-extensions* file as Default (userDataProfile.ts, extensionsResource); the actual enabled/disabled state is tracked separately via `GlobalExtensionEnablementService` in PROFILE-scoped storage, and that storage is only shared with Default when `useDefaultFlags.globalState` is set (`isProfileUsingDefaultStorage` in storage.ts checks `globalState`, not `extensions`). So a profile using 'Extensions from Default Profile' alone gets a fresh, empty disabled-extensions list and everything shows as enabled. This looks like it needs either the storage-sharing check extended to cover the extensions flag, or an explicit sync of disabled state when the profile is created.

## Evidence

- **extensions resource sharing:** src/vs/platform/userDataProfile/common/userDataProfile.ts:202 — `extensionsResource: defaultProfile && options?.useDefaultFlags?.extensions ? defaultProfile.extensionsResource : joinPath(location, 'extensions.json')` — only the installed-extensions list file is shared when the extensions flag is set.
- **enablement state storage:** src/vs/platform/extensionManagement/common/extensionEnablementService.ts getDisabledExtensions()/_setDisabledExtensions() read/write DISABLED_EXTENSIONS_STORAGE_PATH via IStorageService at StorageScope.PROFILE (lines ~48-91).
- **storage sharing gated by a different flag:** src/vs/platform/storage/common/storage.ts:735 `isProfileUsingDefaultStorage(profile) { return profile.isDefault || !!profile.useDefaultFlags?.globalState; }` — PROFILE-scope storage (which holds the disabled-extensions list) is only shared with Default when useDefaultFlags.globalState is true, never when useDefaultFlags.extensions is true. So a profile created with only the extensions flag gets a fresh, empty disabled-extensions list, even though it points at the same installed-extensions file.
- **confirms the mismatch:** isProfileUsingDefaultStorage is consumed in src/vs/workbench/services/storage/browser/storageService.ts:121, src/vs/platform/storage/electron-main/storageMainService.ts:225, and src/vs/workbench/services/userDataProfile/browser/userDataProfileStorageService.ts:46, all keyed off useDefaultFlags.globalState only.
