# Issue #328305 — new profile that use extensions from default profile  will enable extensions that disabled in default profile

[https://github.com/microsoft/vscode/issues/328305](https://github.com/microsoft/vscode/issues/328305)

## Summary

The defect remains source-reproducible on current main: a profile can share the Default profile's extension resource while reading disabled-extension state from its own empty profile storage, causing disabled extensions to appear enabled.

## Change summary

Profiles configured to use extensions from the Default profile do not inherit the Default profile's disabled-extension state.

## Best solution

Make extension enablement semantics consistent with the shared extension resource: a new profile using Default-profile extensions should initially preserve disabled extensions, with the intended ongoing synchronization or override behavior explicitly settled and covered by profile tests.

## Plan brief

- **Likely files:** `src/vs/platform/extensionManagement/common/extensionEnablementService.ts`, `src/vs/platform/userDataProfile/common/userDataProfileStorageService.ts`, `src/vs/platform/storage/common/storage.ts`, `src/vs/workbench/services/userDataProfile/browser/extensionsResource.ts`, `src/vs/workbench/services/userDataProfile/test/browser/extensionsResource.test.ts`
- **Validation:** Add a profile/extension-enablement test that disables an extension in Default, creates a profile with useDefaultFlags.extensions, and asserts the extension remains disabled there; extend it to verify the synchronization or override semantics selected by the maintainer.
- **Behavior:**

  > When a profile is created with “Use Extensions from Default Profile,” extensions disabled in Default must not become enabled merely by switching to the new profile. Enabled extensions and profiles with independent extension resources must retain their existing behavior. Acceptance must cover initial profile creation and the chosen behavior when enablement later changes in either profile.
- **Trace:**

  > toUserDataProfile in src/vs/platform/userDataProfile/common/userDataProfile.ts points extensionsResource at the Default profile when useDefaultFlags.extensions is set. GlobalExtensionEnablementService in src/vs/platform/extensionManagement/common/extensionEnablementService.ts stores disabled identifiers in StorageScope.PROFILE, while isProfileUsingDefaultStorage in src/vs/platform/storage/common/storage.ts shares profile storage only for globalState. Consequently, a profile sharing only extensions sees the same installed-extension resource but an independent, initially empty disabled list. The boundary is extension enablement for profiles using Default extensions; do not change settings, keybindings, general global-state sharing, or profiles with independent extension resources. https://github.com/microsoft/vscode/issues/188612 is broader inheritance work, not a same-symptom canonical.
- **Open decisions:**
  - Should a profile using Default-profile extensions continuously share enablement changes with Default, or copy the Default disabled state only when the profile is created?
  - If enablement is continuously shared, may the derived profile override an individual extension's state without changing the Default profile?

## Evidence

- **shared extension resource:** src/vs/platform/userDataProfile/common/userDataProfile.ts:202 assigns the Default profile's extensionsResource when useDefaultFlags.extensions is true.
- **separate enablement state:** src/vs/platform/extensionManagement/common/extensionEnablementService.ts:51-91 reads and writes disabled extensions in StorageScope.PROFILE rather than in the shared extensions resource.
- **profile storage boundary:** src/vs/platform/storage/common/storage.ts:735-737 treats only the Default profile or profiles sharing globalState as using Default storage. A profile sharing extensions alone therefore receives separate profile storage with no copied disabled-extension list.
