# Issue #325459 — Extensions can pollute process.env inherited by unrelated extensions and child processes

[https://github.com/microsoft/vscode/issues/325459](https://github.com/microsoft/vscode/issues/325459)

## Summary

Well-documented feature request for platform-level environment isolation between extensions sharing an extension host process. The underlying defect is in a third-party extension (openai/codex), but the request for a VS Code platform boundary is a distinct, reasonable ask. An open PR (#325460) from the same author exists. Related prior issues (#319210, #320880) addressed specific Copilot SDK mutations upstream; #152806 tracks a controlled API for extensions to modify environment variables. This issue asks for something different — defensive fencing of `process.env` — and should be routed to the extension-host area for evaluation.

## Change summary

Requests that VS Code fence or isolate `process.env` mutations made by one extension so they do not propagate to unrelated extensions or their child processes in the same extension host.

## Best solution

Route to the extension-host area owner for evaluation. The ask is to snapshot and restore `process.env` around extension activation callbacks (or provide a per-extension env overlay for child-process spawning). An open PR (https://github.com/microsoft/vscode/pull/325460) from the reporter attempts this. The related API discussion at https://github.com/microsoft/vscode/issues/152806 covers the controlled-mutation side; this issue covers the defensive-isolation side. Both should inform the design.
