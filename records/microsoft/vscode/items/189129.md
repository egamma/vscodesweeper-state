# Issue #189129 — [themes] Theme is getting switched on switching profiles

[https://github.com/microsoft/vscode/issues/189129](https://github.com/microsoft/vscode/issues/189129)

## Summary

The bug remains visible in current source: removing a profile-specific theme extension selects the default dark theme with an `auto` target, which persists that fallback and can overwrite an apply-to-all-profiles theme setting. This team-authored Backlog issue should remain open.

## Change summary

Switching profiles can replace a shared color-theme setting with the default dark theme when the previous profile's theme extension becomes unavailable.

## Best solution

Treat theme-extension unavailability during a profile transition as temporary: render an available fallback without persisting it over `workbench.colorTheme`, while preserving the intended behavior for an actual extension uninstall.

## Plan brief

- **Likely files:** `src/vs/workbench/services/themes/browser/workbenchThemeService.ts`, `src/vs/workbench/services/themes/common/themeConfiguration.ts`, `src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts`, `src/vs/workbench/services/themes/test/browser`
- **Validation:** Add a browser service regression test that simulates removal of the active contributed theme during a profile switch and asserts that the rendered fallback becomes available without changing the effective persisted `workbench.colorTheme`; run it with `scripts/test.sh --grep "theme.*profile"`.
- **Behavior:**

  > A theme selected through `workbench.settings.applyToAllProfiles` remains selected when switching between profiles, even if the departing profile removes an extension that supplied its former theme. VS Code may display an available fallback while a configured theme is temporarily unavailable, but that fallback must not overwrite the shared theme setting. Switching back must resolve the configured theme normally, and ordinary theme selection and extension-uninstall behavior must remain consistent.
- **Trace:**

  > `WorkbenchThemeService.installRegistryListeners` in `src/vs/workbench/services/themes/browser/workbenchThemeService.ts` reacts to removal of the active contributed theme by selecting the default dark theme with target `auto`. `ThemeConfiguration.writeConfiguration` in `src/vs/workbench/services/themes/common/themeConfiguration.ts` turns that target into a persistent configuration update, including when the theme disappeared because profile extensions were changing. The extension-management path in `src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts` already tracks whether additions and removals originate from a profile switch, but that distinction is not represented in the theme-registry callback. The boundary is fallback persistence during profile transitions: do not alter explicit user theme selection, apply-to-all configuration semantics, or unrelated extension enablement behavior. https://github.com/microsoft/vscode/issues/319919 is a later report of the same observable symptom, while https://github.com/microsoft/vscode/issues/188794 concerns the distinct settings-tree toggle behavior.

## Evidence

- **current source:** `src/vs/workbench/services/themes/browser/workbenchThemeService.ts` still handles removal of the active contributed theme in `installRegistryListeners` by calling `setColorTheme(defaultTheme, 'auto')`; `ThemeConfiguration.writeConfiguration` in `src/vs/workbench/services/themes/common/themeConfiguration.ts` maps `auto` to `configurationService.updateValue`, so the temporary dark fallback is persisted.
- **profile-switch path:** `src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts` marks extension changes caused by switching profiles with `isProfileSwitch`, while the theme-registry removal handler shown above does not distinguish that transition from an ordinary extension removal.
- **maintainer diagnosis:** The maintainer comment on https://github.com/microsoft/vscode/issues/189129 identifies the same mechanism: the theme component resets the theme when the profile-specific extension is removed.
- **related issue:** https://github.com/microsoft/vscode/issues/188794 was fixed by https://github.com/microsoft/vscode/pull/189130, but that change only corrected the settings-tree apply-to-all toggle and explicitly split this theme-extension behavior into the present issue.
- **later report:** https://github.com/microsoft/vscode/issues/319919 reports the same observable theme-setting loss after profile switching, but it was filed in 2026 and therefore cannot be the canonical duplicate for this re-reviewed 2023 issue.
