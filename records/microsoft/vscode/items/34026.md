# Issue #34026 — Debug console link detection issues

[https://github.com/microsoft/vscode/issues/34026](https://github.com/microsoft/vscode/issues/34026)

## Summary

A real gap remains on current main: Debug Console link detection still relies on a small set of hard-coded patterns and exposes no way for extensions to contribute format-specific links. The issue is correctly parked in the Backlog as debug debt, with no older canonical issue owning its broad scope.

## Change summary

Improve Debug Console link detection and consider an extension-facing mechanism for contributing additional link rules or authoritative targets.

## Best solution

Define the intended boundary between built-in link parsing, structured DAP source locations, and extension-contributed links, then consolidate Debug Console detection around that contract with regression coverage for common URL and stack-trace formats.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/linkDetector.ts`, `src/vs/workbench/contrib/debug/test/browser/linkDetector.test.ts`, `src/vs/workbench/contrib/debug/browser/debugSession.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** Extend the Debug Link Detector unit suite with representative URL, file/line/column, and contributed-format cases; if an extension API is selected, add extension-host/main-thread tests proving registration, precedence, disposal, and navigation behavior.
- **Behavior:**

  > Debug Console output should recognize supported web and source-location formats consistently and navigate to the correct target and line. Debug adapters or extensions must have a documented way to supply authoritative targets when generic parsing cannot understand their output format. Existing structured DAP source locations and currently supported links must retain their behavior. Acceptance includes regression coverage for the formats represented in the issue and lifecycle coverage for any new provider contract.
- **Trace:**

  > Current detection is isolated in LinkDetector.detectLinks in src/vs/workbench/contrib/debug/browser/linkDetector.ts, where an ordered array applies WEB_LINK_REGEX and PATH_LINK_REGEX; the adjacent test suite covers selected built-in formats. DebugSession in src/vs/workbench/contrib/debug/browser/debugSession.ts already converts OutputEvent source, line, and column into a structured REPL source location, which is the existing authoritative single-location path. No Debug Console link-provider registration appears in the extension API or workbench API bridge, although terminal links have a separate provider mechanism. The original implementation in https://github.com/microsoft/vscode/pull/65929 predates the issue's reopen and solved only part of the problem. Preserve existing DAP source handling and avoid folding the separate terminal regression work into this issue; uncertainty begins at the public API boundary and precedence rules.
- **Open decisions:**
  - Should this issue deliver only shared and more consistent built-in parsing, or also introduce a public extension contribution contract for Debug Console links?
  - If extensions can contribute links, what observable precedence should apply among structured DAP source locations, built-in URL/path detection, and extension-provided targets?
  - Should contributed detection be scoped to a debug type or session, or apply globally to Debug Console output?

## Evidence

- **current source:** src/vs/workbench/contrib/debug/browser/linkDetector.ts still detects only hard-coded web and path patterns through WEB_LINK_REGEX, PATH_LINK_REGEX, and the private detectLinks method; there is no provider-registration path for extension-contributed Debug Console links.
- **structured workaround:** src/vs/workbench/contrib/debug/browser/debugSession.ts consumes Debug Adapter Protocol OutputEvent source, line, and column fields, allowing an adapter to attach one authoritative source location, but this does not cover arbitrary or multiple links embedded in output.
