# Issue #342240 — Notebook Markdown: code blocks in cells rendered in the same millisecond lose syntax highlighting (ID collision in requestHighlightCodeBlock)

[https://github.com/microsoft/vscode/issues/342240](https://github.com/microsoft/vscode/issues/342240)

## Summary

The reported collision is present in current main: separate cells can receive identical highlighting request IDs, causing one cell's tokenized content to overwrite another's. Keep this open and route it to the notebook area.

## Change summary

Ensure notebook fenced-code highlighting responses reach their originating blocks when multiple cells render in the same millisecond.

## Best solution

Each pending highlighting request should remain uniquely associated with its originating code block throughout the asynchronous tokenization round trip, including requests from rendered outputs.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/notebook/browser/view/renderers/webviewPreloads.ts`
- **Validation:** Establish a browser-level regression check that issues highlighting requests from two separate roots during the same clock millisecond, then delivers distinct tokenized responses in both arrival orders. Each original block must receive only its own HTML and its shadow root must receive the tokenization stylesheet. Also exercise the shared rendered-output path and multiple blocks within one root. For manual acceptance, open and repeatedly reload the report's Python/JSON two-cell notebook and verify both blocks retain their own content and highlighting.
- **Behavior:**

  > When notebook Markdown cells render close together, every language-tagged fenced code block must receive its own syntax-highlighted content. One cell's response must never replace another cell's code, regardless of response arrival order. The same isolation must hold for rendered outputs using the shared highlighting path. Existing language selection and stylesheet behavior must remain unchanged.
- **Trace:**

  > In src/vs/workbench/contrib/notebook/browser/view/renderers/webviewPreloads.ts, MarkdownCodeBlock.requestHighlightCodeBlock resets its local counter for each root and combines it with Date.now(), while pendingCodeBlocksToHighlight is shared across roots. Equal timestamps and block indices therefore overwrite an outstanding association. BackLayerWebView._handleHighlightCodeBlock in backLayerWebView.ts returns those IDs unchanged, and MarkdownCodeBlock.highlightCodeBlock uses the overwritten mapping to apply both responses to the later element. Markdown cells and rendered outputs both call this helper. Keep the scope to request/response association; do not alter tokenization, language resolution, output rendering, or unrelated pending-map lifecycle behavior. Runtime code must remain self-contained inside the stringified preload function. The remaining uncertainty is how to exercise this private webview path deterministically in the repository's test infrastructure, not the expected product behavior.

## Evidence

- **Collision confirmed in current source:** src/vs/workbench/contrib/notebook/browser/view/renderers/webviewPreloads.ts:2482-2490 resets i to zero for every requestHighlightCodeBlock call and uses `${Date.now()}-${i++}` as the key in a shared static map. Two calls within one millisecond overwrite the first block's mapping.
- **Exact failing response path:** backLayerWebView.ts:1160-1177 tokenizes each request independently and returns its unchanged ID. webviewPreloads.ts:1850-1852 dispatches each response to highlightCodeBlock; lines 2467-2479 resolve only that ID and replace the mapped element's HTML. Both colliding responses therefore target the second block, while the first receives neither highlighted HTML nor its tokenization stylesheet.
- **Shared callers and implementation boundary:** webviewPreloads.ts:2664 invokes requestHighlightCodeBlock for rendered Markdown cells, and line 3050 invokes it for rendered outputs. Its header requires runtime implementation to remain inside the stringified webviewPreloads function and prohibits runtime imports.
