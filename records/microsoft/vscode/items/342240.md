# Issue #342240 — Notebook Markdown: code blocks in cells rendered in the same millisecond lose syntax highlighting (ID collision in requestHighlightCodeBlock)

[https://github.com/microsoft/vscode/issues/342240](https://github.com/microsoft/vscode/issues/342240)

## Summary

The reported collision remains in current main: same-millisecond requests from different cells can overwrite the shared highlight destination. Keep this open as a confirmed notebook rendering bug.

## Change summary

Ensure fenced-code highlighting responses reach the correct notebook cell when multiple cells render within the same millisecond.

## Best solution

Give every notebook code-block highlighting request an unambiguous destination across calls in the same webview, preserving each block's content and language regardless of response order.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/notebook/browser/view/renderers/webviewPreloads.ts`, `src/vs/workbench/contrib/notebook/browser/view/renderers/backLayerWebView.ts`
- **Validation:** Establish a browser-level regression check that requests highlighting for two distinct roots at the same clock value, delivers their differently tokenized responses in both orders, and verifies each block retains its own content and highlighting. Include multiple blocks per root and the shared output caller. Manually verify the reported Python/JSON notebook after opening, reloading, and rerendering an individual cell.
- **Behavior:**

  > Notebook Markdown code blocks must receive highlighting for their own content and language even when multiple cells render within the same millisecond. Neither response order nor another cell's rendering may replace a block's content with another block's HTML. Acceptance should deterministically cover two same-clock requests, multiple blocks within a request, and responses arriving in either order.
- **Trace:**

  > MarkdownCodeBlock in src/vs/workbench/contrib/notebook/browser/view/renderers/webviewPreloads.ts maintains a static pendingCodeBlocksToHighlight map, but requestHighlightCodeBlock restarts its local index on every call and combines it with Date.now(). This conclusively permits different roots to overwrite the same map entry. MarkupCell calls the helper at line 2664, and rendered outputs share it at line 3050. BackLayerWebView._handleHighlightCodeBlock in backLayerWebView.ts tokenizes each request independently and echoes its ID; highlightCodeBlock then writes to the mapped element. Preserve the existing tokenization, language resolution, stylesheet adoption, and message contract; unrelated lifecycle cleanup is outside this report. The remaining uncertainty is how to exercise the webview-local helper deterministically in the repository's test infrastructure, not the expected product behavior.

## Evidence

- **Collision confirmed in current source:** src/vs/workbench/contrib/notebook/browser/view/renderers/webviewPreloads.ts:2482-2490 resets i to zero for every requestHighlightCodeBlock call and constructs IDs with `${Date.now()}-${i++}`. Two first blocks requested in the same millisecond therefore share an ID; the second pendingCodeBlocksToHighlight.set replaces the first destination.
- **Exact rendering and response path:** MarkupCell invokes requestHighlightCodeBlock per cell at webviewPreloads.ts:2664. backLayerWebView.ts:907-914 forwards these requests to _handleHighlightCodeBlock, which returns independently tokenized HTML with the original ID at lines 1160-1176. webviewPreloads.ts:2467-2480 resolves that ID through the overwritten map, so both responses update the second block and the first receives neither highlighted HTML nor the tokenization stylesheet.
- **Shared surface boundary:** webviewPreloads.ts:3050 also calls requestHighlightCodeBlock for rendered outputs. Request identity must remain unique across both markup-cell and output callers, not merely within one cell or one request batch.

The supplied heading-ID and other notebook leads do not establish the same observable highlighting failure; no older canonical was verified.
