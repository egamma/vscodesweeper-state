# Issue #336505 — Allow pausing chat requests

[https://github.com/microsoft/vscode/issues/336505](https://github.com/microsoft/vscode/issues/336505)

## Summary

A real queue-control gap remains on current main: chat can queue, steer, cancel, remove, reorder, or immediately send requests, but users cannot pause automatic queue draining and later resume it without discarding work.

## Change summary

Add a pause/resume control that lets chat requests finish or remain queued without automatically starting the next request.

## Best solution

Provide a clear, keyboard-accessible queue pause state that preserves the active and queued work, visibly communicates that state, and behaves consistently for local and Agent Host chats. A maintainer should first settle its scope and persistence semantics.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/chatService/chatService.ts`, `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatQueueActions.ts`, `src/vs/platform/agentHost/common/state/protocol/channels-chat/actions.ts`, `src/vs/platform/agentHost/node/chatContributions/queueDrain/queueDrainContribution.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatAccessibilityHelp.ts`
- **Validation:** Add targeted chat-service and Agent Host queue-drain tests proving that the current turn follows the chosen pause semantics, queued messages remain pending while paused, resume admits the next message exactly once, and unpaused queues retain existing behavior; verify the control is keyboard-operable and documented in chat accessibility help.
- **Behavior:**

  > Users need to pause automatic chat queue processing without canceling the current response or deleting queued prompts, then resume processing later. The paused state must be visible and operable by keyboard and screen reader. Acceptance must cover the chosen active-turn behavior, queue preservation, exact-once resumption, and consistent behavior for local and Agent Host chats.
- **Trace:**

  > Local queue admission runs through ChatService in src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts: request completion calls processNextPendingRequest, while pauseQueue is only a per-send internal option and is not session state. User queue commands are registered in src/vs/workbench/contrib/chat/browser/actions/chatQueueActions.ts. Agent Host independently drains its server-managed queue through QueueDrainContribution._tryConsumeNextQueuedMessage in src/vs/platform/agentHost/node/chatContributions/queueDrain/queueDrainContribution.ts; its chat protocol currently models pending-message set, removal, and reorder but no paused state. The boundary is queue admission: cancellation, steering semantics, pending-message editing, and unrelated sessions must retain their established behavior. Existing chat accessibility help should describe any new action, and an icon-only control would need a localized accessible label.
- **Open decisions:**
  - Does pausing allow the active request to finish before blocking the queue, or must users also be able to suspend an in-progress request?
  - Is pause state scoped to one chat, one Agent Host session, or all concurrently running sessions?
  - Does paused state survive window reloads, network changes, and application restart, as suggested by the reported use cases?

## Evidence

- **local queue path:** src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts automatically calls processNextPendingRequest after an active response completes. The existing pauseQueue send option only suppresses immediate dispatch for an individual internal enqueue operation; there is no durable user-visible paused state.
- **Agent Host queue path:** src/vs/platform/agentHost/node/chatContributions/queueDrain/queueDrainContribution.ts calls _tryConsumeNextQueuedMessage after successful turns and pending-message updates, with no paused-state guard. The protocol in src/vs/platform/agentHost/common/state/protocol/channels-chat/actions.ts currently exposes set, remove, and reorder operations for pending messages, but no pause/resume operation.
- **current UI surface:** src/vs/workbench/contrib/chat/browser/actions/chatQueueActions.ts registers Add to Queue, Steer with Message, Remove from Queue, Edit, Send Immediately, and Remove All Queued actions; no pause or resume action exists.
- **related issue:** https://github.com/microsoft/vscode/issues/336318 is older and concerns reordering queued requests, not stopping and resuming queue execution, so it does not own the same observable behavior.
- **use cases:** The issue and https://github.com/microsoft/vscode/issues/336505#issuecomment-5709016652 identify concurrent-session scheduling, network changes, application updates, and end-of-day interruption as cases where cancellation loses useful queued work.
