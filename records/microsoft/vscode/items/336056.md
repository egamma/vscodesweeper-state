## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentHostAutomationService.ts`, `src/vs/platform/agentHost/common/state/protocol/channels-automation/state.ts`
- **Validation:** A design decision (and, once made, an integration test) confirming that a registered wake, once fired, queues exactly one continuation turn in the same originating chat — never a new session — with zero inference while pending.
- **Behavior:**

  > An MCP tool call can register a bounded, one-shot 'wake' scoped to the invoking chat and MCP server. While pending, the chat performs no polling inference. When the MCP server later signals the registered event (and the registration/chat are still eligible), VS Code queues exactly one system/event-origin continuation turn in that same chat containing the wake ID and description, delivered at the next safe turn boundary. Registrations are exactly-once, expire, and are invalidated if the chat is cancelled/ended/archived/safety-blocked.
- **Trace:**

  > Today, MCP notifications reach the client but nothing resumes the originating chat with a new turn after registration; the only existing 'resume later' mechanism is Agent Host Automations (src/vs/platform/agentHost/node/agentHostAutomationService.ts), which starts a brand-new session per run rather than continuing the owning chat. The Agent Host protocol already reserves schedule/trigger-definition shapes in src/vs/platform/agentHost/common/state/protocol/channels-automation/state.ts, but the issue reports (and the checkout is consistent with) no event-trigger definitions being advertised or accepted for this yet. Related but distinct: https://github.com/microsoft/vscode/issues/253412 (blocking sleep/wait), https://github.com/microsoft/vscode/issues/323927 (existing background-task completion bug), https://github.com/microsoft/vscode/issues/331521 (child-session completion signals) — none of them cover a same-chat, MCP-authorized wake. The open question is architectural placement and grant/permission model, not the safety-contract details the reporter already proposed.
- **Open decisions:**
  - Should this live as new MCP/chat-integration surface, or be built on top of the existing (currently dormant) Agent Host external-event trigger model in channels-automation?
  - What does the host-issued grant/token look like (scope, expiration, binding to MCP server identity + exact chat + event ID), and who is authorized to mint it?
  - Should the first version be experimental and strictly session-local/non-durable as the reporter suggests, deferring restart persistence to a later decision?
