# Issue #336056 — Allow MCP tools to register one-shot wake events for the current agent chat

[https://github.com/microsoft/vscode/issues/336056](https://github.com/microsoft/vscode/issues/336056)

## Summary

Keep open for design: current main supports MCP notifications and host-authored turns, but has no bounded contract connecting an MCP tool invocation to a one-shot continuation of its owning chat. This team-authored request describes a distinct capability not owned by the related sleep, background-task, or child-session issues.

## Change summary

Allow an MCP tool invocation to register a bounded one-shot event that queues exactly one continuation in the same chat when the server later fires it.

## Best solution

Define an experimental host-owned wake capability that preserves exact-chat and MCP-server identity, uses the standard Agent Host turn-admission path, and enforces expiration, exactly-once consumption, visible event provenance, and safe-boundary queueing. A maintainer should first settle whether this is an MCP-specific contract or a reusable Agent Host event primitive, plus its restart-persistence semantics.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/common/agent.ts`, `src/vs/platform/agentHost/node/agentHostProviderService.ts`, `src/vs/platform/agentHost/node/agentHostTurnService.ts`, `src/vs/platform/agentHost/node/agentService.ts`, `src/vs/workbench/contrib/mcp/common/mcpServerRequestHandler.ts`
- **Validation:** Add targeted Agent Host and MCP tests proving that a registration made during an exact-chat tool invocation causes no polling, one valid notification queues exactly one system-origin continuation after the chat becomes idle, and duplicate, expired, wrong-server, wrong-chat, cancelled-chat, and replayed notifications start no turn.
- **Behavior:**

  > During an MCP tool invocation, the tool can request a bounded one-shot wake tied to that server and exact chat. The tool returns immediately and the pending registration causes no model inference. Firing an eligible registration queues exactly one visibly event-originated continuation in the same chat after the current turn finishes; duplicate, expired, cancelled, or mismatched events do nothing. Newer user input retains priority and the resumed turn receives no implicit tool approval.
- **Trace:**

  > Agent Host already routes MCP requests and notifications by exact chat/server through the optional seams in src/vs/platform/agentHost/common/agent.ts and src/vs/platform/agentHost/node/agentHostProviderService.ts. The workbench MCP handler in src/vs/workbench/contrib/mcp/common/mcpServerRequestHandler.ts consumes only standardized notification kinds and does not re-enter the model loop. src/vs/platform/agentHost/node/agentHostTurnService.ts is the shared admission path for host-authored turns, while src/vs/platform/agentHost/node/agentService.ts contains existing system-origin turn and idle-boundary patterns. Automations are not equivalent: src/vs/platform/agentHost/node/agentHostAutomationService.ts exposes no event definitions, rejects event triggers, and starts fresh sessions. Keep blocking waits, polling, arbitrary prompt injection, cross-chat delivery, and child-session signaling out of scope; https://github.com/microsoft/vscode/issues/331521 remains related but distinct. The uncertainty starts at the public contract boundary: MCP-specific registration versus a reusable Agent Host event capability, and whether registrations are intentionally process-local or durable.
- **Open decisions:**
  - Should the public contract be an MCP tool-invocation capability limited to the invoking server and chat, or a reusable Agent Host event primitive available to other explicitly authorized event sources?
  - Should pending registrations be process/session-local and disappear on restart, or form a durable contract that survives Agent Host or VS Code restart?

## Evidence

- **current MCP notification boundary:** src/vs/workbench/contrib/mcp/common/mcpServerRequestHandler.ts handles a fixed set of MCP notifications, including task status, but none registers or fires a same-chat continuation. Agent Host exposes exact-chat MCP notification routing through src/vs/platform/agentHost/common/agent.ts and src/vs/platform/agentHost/node/agentHostProviderService.ts.
- **available turn primitive:** src/vs/platform/agentHost/node/agentHostTurnService.ts provides startTurnMessage for host-authored turns through normal admission and provider routing, but it requires an immediate idle chat and contains no persistent or queued one-shot wake registration.
- **automation gap:** src/vs/platform/agentHost/node/agentHostAutomationService.ts returns an empty list from listTriggerDefinitions and _validateDefinition rejects every AutomationTriggerKind.Event, while each automation run creates a fresh session rather than resuming the invoking chat.
- **distinct related work:** https://github.com/microsoft/vscode/issues/331521 is open but concerns completion signals from independently scoped child sessions, not an MCP server registering a wake for its invoking chat. https://github.com/microsoft/vscode/issues/253412 requested a blocking sleep/wait command and https://github.com/microsoft/vscode/issues/323927 concerned an existing background-task completion path; both are closed and neither owns this contract.
- **canonical search:** Open-issue searches for “MCP wake chat”, “MCP continuation turn”, and “external event agent chat” found no canonical issue covering this observable behavior.
