# Issue #130486 — Stale semantic tokens across several files

[https://github.com/microsoft/vscode/issues/130486](https://github.com/microsoft/vscode/issues/130486)

## Summary

A real cross-file invalidation gap remains on current main. The global refresh event updates every visible model and can re-request the model already being computed, while providers still cannot identify affected documents or learn which documents need results.

## Change summary

Provide an efficient invalidation contract that keeps semantic tokens and similar pull-based language features current when edits in one file affect other files.

## Best solution

Define a consistent provider/client invalidation contract that refreshes affected visible consumers without duplicating an already-pending request, then align the VS Code API and LSP refresh behavior. The design should apply consistently across semantic tokens, inlay hints, CodeLens, and other pull-based language features rather than adding a semantic-token-only exception.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages.ts`, `src/vs/editor/contrib/semanticTokens/browser/documentSemanticTokens.ts`, `src/vs/editor/contrib/semanticTokens/test/browser/documentSemanticTokens.test.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`
- **Validation:** Extend the document semantic-token tests with multiple models: while one attached model has a content-triggered request pending, fire provider invalidation and assert that the pending model is not requested twice, another affected attached model is refreshed once, and an unattached model is not fetched.
- **Behavior:**

  > When a change in one document can alter language-feature results in other documents, providers can invalidate the relevant results without leaving visible content stale or causing redundant pulls. A document whose current request already incorporates the change must not be immediately requested again solely because of the corresponding refresh. Other affected visible consumers must refresh, while non-visible or unaffected consumers must not incur unnecessary work. The contract should be coherent across semantic tokens and comparable pull-based language features.
- **Trace:**

  > The public semantic-token provider event is payload-free in src/vscode-dts/vscode.d.ts, and the internal provider event is payload-free in src/vs/editor/common/languages.ts. ExtHostLanguageFeatures.registerDocumentSemanticTokensProvider forwards every event through $emitDocumentSemanticTokensEvent without data; MainThreadLanguageFeatures recreates an Event<void>. DocumentSemanticTokensFeature then sends the event to every watcher for that provider. ModelSemanticColoring.handleProviderDidChange sets _providersChangedDuringRequest for a pending request, and the completion path schedules another pull, which conflicts with the 2021 proposal to exclude pending documents and matches the 2025 Dart report. The uncertainty starts at whether VS Code should retain a global event with pending-request suppression, add URI-targeted invalidation, expose consumer interest, or combine those mechanisms; preserve normal content-change refreshes and avoid a semantic-token-only model that other pull providers cannot follow. Related design evidence: https://github.com/microsoft/language-server-protocol/issues/1546 and https://github.com/microsoft/language-server-protocol/issues/1163.
- **Open decisions:**
  - Should provider invalidation remain global with client-side filtering, carry affected URIs, or include both forms?
  - What client interest set should providers or language servers target: visible editors, open documents, or every document with an active consumer?
  - When a refresh races with an in-flight request, under what conditions does that request already satisfy the invalidation and therefore suppress a follow-up pull?
  - Should the contract be designed as a common pattern for semantic tokens, inlay hints, CodeLens, and other pull providers before changing the semantic-token API?
  - Which parts belong in VS Code's extension API versus the Language Server Protocol?

## Evidence

- **current API:** src/vscode-dts/vscode.d.ts declares DocumentSemanticTokensProvider.onDidChangeSemanticTokens as Event<void>, and src/vs/editor/common/languages.ts likewise exposes DocumentSemanticTokensProvider.onDidChange as Event<void>; neither can carry affected URIs.
- **current refresh path:** DocumentSemanticTokensFeature in src/vs/editor/contrib/semanticTokens/browser/documentSemanticTokens.ts broadcasts a provider change to every model watcher. ModelSemanticColoring.handleProviderDidChange marks a pending request as changed and schedules another pull after it completes, rather than excluding that pending document from the refresh.
- **extension-host boundary:** src/vs/workbench/api/common/extHostLanguageFeatures.ts and src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts discard event payloads and transmit only a global semantic-token refresh signal.
- **recent confirmation:** https://github.com/microsoft/vscode/issues/130486#issuecomment-3671249212 reports the same unresolved behavior in Dart: a global refresh causes a duplicate semantic-token request for the visible modified file when a hidden dependent file is open.
- **cross-feature scope:** https://github.com/microsoft/language-server-protocol/issues/1546 remains open and explicitly points back to this issue as the editor-side prerequisite for solving the equivalent inlay-hint problem.
- **canonical search:** https://github.com/microsoft/vscode/issues/102043 is an older but narrower request for file-specific semantic-token events. This issue owns the broader subscription, visibility, pending-request, and cross-provider design, so folding it into that narrower issue would lose scope.
