# Issue #130486 — Stale semantic tokens across several files

[https://github.com/microsoft/vscode/issues/130486](https://github.com/microsoft/vscode/issues/130486)

## Summary

A real API and protocol-design gap remains: cross-file changes can leave semantic tokens stale unless a provider globally invalidates its results, which causes redundant requests. The Backlog item should remain open under discussion because current source and the December 2025 Dart report confirm that neither precise invalidation nor an explicit client-interest contract exists.

## Change summary

Provide an efficient way for language servers to invalidate semantic tokens and similar language features affected by changes in other files.

## Best solution

Define a consistent invalidation contract across language features that lets providers refresh all relevant client-visible results without computing every project URI or causing duplicate requests. Coordinate the VS Code API behavior with the broader LSP design tracked at https://github.com/microsoft/language-server-protocol/issues/1163.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`, `src/vs/editor/contrib/semanticTokens/browser/documentSemanticTokens.ts`, `src/vs/editor/contrib/semanticTokens/test/browser/documentSemanticTokens.test.ts`
- **Validation:** Add semantic-token API and editor tests covering two attached documents: a change-scoped invalidation must refresh the affected dependent document without issuing a redundant request for the changed document; run the targeted semantic-token unit suite with ./scripts/test.sh --grep "DocumentSemanticTokens".
- **Behavior:**

  > When a change in one document can alter semantic tokens in another, a language provider can invalidate the relevant results without globally re-requesting every result from that provider. Visible dependent documents refresh promptly, while the changed document is not redundantly requested after its normal content-change refresh. The contract must remain usable when a server can cheaply identify only an approximate affected set and should be consistent with comparable pull-based language features.
- **Trace:**

  > The public DocumentSemanticTokensProvider event in src/vscode-dts/vscode.d.ts carries no payload. ExtHostLanguageFeatures in src/vs/workbench/api/common/extHostLanguageFeatures.ts discards any emitted value, ExtHostLanguageFeaturesShape in src/vs/workbench/api/common/extHost.protocol.ts has no invalidation data, and MainThreadLanguageFeatures in src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts fires undefined. SemanticColoringFeature in src/vs/editor/contrib/semanticTokens/browser/documentSemanticTokens.ts consequently forwards each provider event to all matching model watchers, while ModelSemanticColoring fetches only when the model is attached to an editor. The uncertainty starts at the public contract: URI-scoped invalidation solves precise cases, while the original report argues that servers also need an efficient way to express broad invalidation over only client-interest documents. Coordinate that decision with https://github.com/microsoft/language-server-protocol/issues/1163 and preserve existing Event<void> providers and normal same-document content refresh behavior.
- **Open decisions:**
  - Should the public invalidation contract carry an optional affected-URI set, or should the client explicitly expose/subcribe the set of documents whose results it currently consumes so servers can issue broad invalidations efficiently?
  - Should the chosen contract be generalized consistently across semantic tokens, code lenses, inlay hints, and other pull-based providers, or introduced first as a semantic-token-specific API?

## Evidence

- **current API gap:** src/vscode-dts/vscode.d.ts declares DocumentSemanticTokensProvider.onDidChangeSemanticTokens as Event<void>, so an extension cannot identify affected documents or otherwise scope an invalidation.
- **global invalidation path:** src/vs/workbench/api/common/extHostLanguageFeatures.ts discards the event value, and src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts forwards an undefined payload; src/vs/editor/contrib/semanticTokens/browser/documentSemanticTokens.ts then notifies every model watcher using that provider.
- **visibility behavior:** ModelSemanticColoring._fetchDocumentSemanticTokensNow in src/vs/editor/contrib/semanticTokens/browser/documentSemanticTokens.ts requests tokens only for models attached to an editor. This avoids hidden-editor fetches but does not prevent the visible changed document from being requested once for its edit and again after a global provider refresh.
- **current confirmation:** The December 2025 comment on https://github.com/microsoft/vscode/issues/130486 reports the same unresolved tradeoff in Dart: global refresh prevents stale dependent files but duplicates requests for the visible changed file.
- **related protocol work:** https://github.com/microsoft/language-server-protocol/issues/1163 remains open and tracks a broader server-to-client invalidation mechanism; its latest discussion also asks for precise provider invalidation.
- **not a duplicate:** https://github.com/microsoft/vscode/issues/102043 is open but only requests file-specific semantic-token events. This issue is broader, covering efficient interest tracking and consistent behavior across semantic tokens, code lenses, inlay hints, and other pull-based features.
