# Issue #139634 — `code` CLI still opens duplicate VSCode instance in the macOS dock

[https://github.com/microsoft/vscode/issues/139634](https://github.com/microsoft/vscode/issues/139634)

## Summary

Keep open: multiple reporters confirmed duplicate Dock icons without extensions, and the attempted fix was reverted after causing disappearing or shrunken icons. Current source still launches a secondary macOS application instance before forwarding arguments; a regression-safe solution remains necessary.

## Change summary

Opening files or projects with the macOS code CLI can display a duplicate Dock icon and reportedly delay opening.

## Best solution

Make CLI invocations deliver files and arguments without a duplicate Dock icon, while preserving the primary application's icon, focus behavior, and CLI semantics. Investigate the reported opening delay separately rather than assuming it shares the icon's root cause.

## Plan brief

- **Likely files:** `resources/darwin/bin/code.sh`, `src/vs/code/node/cli.ts`, `src/vs/code/electron-main/main.ts`
- **Validation:** On macOS with a packaged build, pin Code, open one project using code ., then invoke code . for a second project and code new-file.txt while observing the Dock. Verify that no secondary icon appears and the primary icon remains visible at normal size through repeated invocations and cold launches. Exercise --goto, --new-window, --reuse-window, --wait, and --help; compare warm-opening latency separately against the unchanged baseline.
- **Behavior:**

  > With VS Code already running on macOS, opening another project or a new file through code must not display a duplicate Dock icon. The primary application's icon must remain visible and normally sized, including after repeated invocations and cold starts. Existing argument handling, window targeting, focus, and wait semantics must remain intact. Reported opening delays should be measured independently; suppressing an icon is not evidence that latency improved.
- **Trace:**

  > resources/darwin/bin/code.sh starts the bundled executable in Node mode, and src/vs/code/node/cli.ts launches the macOS application through open -n -g -a with forwarded environment and arguments. CodeMain.claimInstance in src/vs/code/electron-main/main.ts handles the resulting secondary instance by connecting to the existing main IPC endpoint, forwarding the launch request, and terminating. Reporters confirmed the visible symptom without extensions in https://github.com/microsoft/vscode/issues/139634; no GUI reproduction was executed during this read-only review. https://github.com/microsoft/vscode/pull/259883 attempted secondary-instance Dock hiding, but commit 220c355619d00068484b2abc69bd0c162b2719b1 reverted it after the primary-icon regression tracked in https://github.com/microsoft/vscode/issues/274146. The investigation must establish current packaged-build behavior and the native lifecycle behind both symptoms before selecting an implementation. Preserve argument forwarding, startup retry behavior, primary-icon visibility, and established focus semantics; the latency relationship remains unproven.

CodeMain.claimInstance in src/vs/code/electron-main/main.ts:375-480 connects to the existing instance, forwards the request, and terminates the secondary instance.
