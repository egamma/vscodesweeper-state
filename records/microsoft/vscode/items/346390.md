## Evidence

- **Native verifier failure:** https://github.com/microsoft/vscode/issues/346390 reports Code 1.145.0 on Fedora 45 x64: the bundled @vscode/vsce-sign/bin/vsce-sign receives SIGABRT while verifying Ruff 2026.94.0. The stack includes abort and pthread_once with glibc 2.44; it does not establish the precise native root cause.
- **Independent confirmation:** The November 7 discussion at https://github.com/microsoft/vscode/issues/346390 confirms vsce-sign SIGABRT on Fedora 45 ARM64 with Code 1.146.0-insider, commit 29ce94ad8d36c62affc08484e262d5c4fbdd0b3d. The later observation that stable works on another x64 machine explicitly did not exercise extension installation or updates, so it does not demonstrate resolution.
- **Current source boundary:** src/vs/platform/extensionManagement/node/extensionSignatureVerificationService.ts imports @vscode/vsce-sign and calls module.verify. ExtensionDownloader.download in src/vs/platform/extensionManagement/node/extensionDownloader.ts passes the downloaded VSIX and signature archive to that service; ExtensionManagementService.downloadExtension rejects unsuccessful verification in built installations. The reported abort occurs in the dependency executable, not Ruff's extension code.
- **Canonical search:** Public issue search for open Fedora vsce-sign reports found https://github.com/microsoft/vscode/issues/344726, but that report describes ARM64 SIGILL under AppleHV with an SME/SVE-specific runtime hypothesis, not this native Fedora x64/ARM64 SIGABRT. Reviewed signature-failure leads https://github.com/microsoft/vscode/issues/346554, https://github.com/microsoft/vscode/issues/346250 and https://github.com/microsoft/vscode/issues/343594 do not establish the same abort or root cause.
