# Issue #324992 — MCP tool names collide when multiple servers report the same serverInfo.name, producing unstable _2/_3 prefixes

[https://github.com/microsoft/vscode/issues/324992](https://github.com/microsoft/vscode/issues/324992)

## Summary

Confirmed on main: the tool prefix is derived from the backend-announced `serverInfo.name` rather than the unique `mcp.json` key, so multiple servers sharing a `serverInfo.name` get numeric-suffixed prefixes whose server assignment depends on connection order and reshuffles across reloads — matching both the reporter's repro and daxian-dbw's (MEMBER) confirmation on 1.132.0.

## Change summary

Multiple MCP servers reporting the same serverInfo.name get colliding, order-dependent tool-name prefixes (mcp_<name>_2_*, _3_*, …) instead of a stable prefix tied to each server's unique mcp.json key.

## Best solution

In src/vs/workbench/contrib/mcp/common/mcpServer.ts, keep clean announced names for non-colliding servers (preserving the #318638 intent) but make `McpPrefixGenerator`/`preferredName` fall back to the `mcp.json` key deterministically (not order-dependent) whenever two or more servers in the same bucket share a name, so tool prefixes are stable across reloads.

  > MCP tool-name prefixes collide unstably when multiple configured servers report the same `serverInfo.name`. Root cause: in src/vs/workbench/contrib/mcp/common/mcpServer.ts, `preferredName` (around line 649) is `this._serverMetadata.value.read(reader)?.serverName || this.definition.label`, so the announced serverInfo.name always wins when present; `McpPrefixGenerator.take()` (the class right below, using a `_buckets` map keyed on the sanitized name) then assigns the next free numeric index within that name's bucket purely in call order, with no reference to the server's actual mcp.json key. The result: when N servers share a serverInfo.name, they get `mcp_<name>_2_*`, `_3_*`, etc., and which server holds which index depends on connection/registration order, so it reshuffles across window reloads. Fix boundary: preserve the existing clean-name behavior for servers that do NOT collide (this was intentionally added in PR #318638 for registry-style keys like `io.github.upstash/context7` → `Context7`), but when `McpPrefixGenerator` detects that two or more servers in the same bucket share a name, deterministically derive their prefixes from each server's own definition/mcp.json key (`this.definition.label`) instead of blind sequential indices — so the same key always maps to the same prefix regardless of connection order. Do not change the non-colliding path, and do not simply revert to always using the key (that regresses #318638's clean-name goal for solo servers). Validate with a unit test (likely in the existing MCP server/tool test suite) that constructs two servers with distinct keys and an identical announced serverInfo.name, and asserts the resulting prefixes are distinct and stable across different `take()` call orders. ## Evidence

- **root cause in source:** src/vs/workbench/contrib/mcp/common/mcpServer.ts:649 sets `preferredName = this._serverMetadata.value.read(reader)?.serverName || this.definition.label`, i.e. the backend-announced serverInfo.name wins over the mcp.json key when present.
- **unstable index assignment:** McpPrefixGenerator.take() (src/vs/workbench/contrib/mcp/common/mcpServer.ts ~230-260) assigns the lowest free index in a per-name bucket in call order, which depends on server connection/registration order — not on any stable per-key ordering, so the _N→server mapping can change across reloads.
