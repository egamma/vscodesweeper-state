# Issue #201532 — context menu display on another monitor

[https://github.com/microsoft/vscode/issues/201532](https://github.com/microsoft/vscode/issues/201532)

## Summary

Keep open in the existing Electron/native-context-menu area: independent reports confirm wrong-monitor placement through VS Code 1.121.0, and current source still delegates mouse-triggered placement to Electron. No verified fixing commit or eligible older canonical establishes that this report is resolved.

## Change summary

Native context menus on macOS can appear on another monitor, particularly when multiple VS Code windows are open and focus changes between displays.

## Best solution

Resolve native menu placement in Electron's macOS popup/window-selection path, with a minimal multi-window, vertically stacked-display reproduction. Confirm whether explicitly associating the popup with its originating window is necessary in VS Code; switching to custom menus is a workaround, not completion of the native-menu fix.

## Evidence

- **Maintainer diagnosis:** In the supplied January 22, 2024 discussion at https://github.com/microsoft/vscode/issues/201532, bpasero verified that editor right-clicks pass undefined x, y and positioningItem, leaving placement to Electron. The reporter subsequently retracted the apparent 1.85.2 resolution.
- **Independent confirmations:** The discussion at https://github.com/microsoft/vscode/issues/201532 includes confirmations in May 2024, a detailed vertically stacked-display reproduction on 1.94.2 in October 2024, and another confirmation on macOS 15.7.7 / VS Code 1.121.0 in May 2026. Closing the other workspace window or focusing the secondary display changes the outcome; reload and window movement provide only temporary relief.
- **Current source:** src/vs/editor/contrib/contextmenu/browser/contextmenu.ts passes the editor mouse event as the anchor. NativeContextMenuService.showContextMenu in src/vs/workbench/services/contextmenu/electron-browser/contextmenuService.ts leaves x/y undefined for mouse-event anchors. registerContextMenuListener in src/vs/base/parts/contextmenu/electron-main/contextmenu.ts forwards those options to Menu.popup without an explicit BrowserWindow. This preserves the upstream-controlled placement path but does not conclusively reproduce macOS display behavior without execution.
- **Workaround, not coverage:** src/vs/workbench/electron-browser/desktop.contribution.ts registers window.menuStyle with a custom option on macOS. ContextMenuService selects the HTML implementation for that option, bypassing native popup placement; this does not fix the reported native-menu behavior.
- **Related extension report:** https://github.com/brychanrobot/jj-view/issues/150 remains open and links this issue. Its reporter observed a background window's context menu appearing over another window on VS Code 1.112.0; the extension maintainer suspects Electron's last-active-window selection but explicitly could not reproduce on macOS. This is corroborating context, not evidence that an extension causes this report.
- **Canonical search:** Open-issue searches found https://github.com/microsoft/vscode/issues/316665, which reports menus opening over a focused window when right-clicking an unfocused window, including auxiliary windows and both menu styles. It was created in May 2026, later than this December 2023 report, so it cannot be the duplicate canonical under the re-review rule. The older https://github.com/microsoft/vscode/issues/188903 concerns long Explorer folder names and remaining keyboard-anchor offsets, not this wrong-monitor editor symptom.
