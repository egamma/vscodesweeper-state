# Issue #318855 — Chat session observation API for extension-owned evaluation and tooling

[https://github.com/microsoft/vscode/issues/318855](https://github.com/microsoft/vscode/issues/318855)

## Summary

A supported read-only session observation API remains missing: current participant, provider, and debug APIs do not cover arbitrary-session enumeration and structured history retrieval. Keep this request open for API design; the related reports do not establish a qualifying canonical duplicate.

## Change summary

Expose supported session enumeration, structured history retrieval, and lifecycle observation to extensions without private-storage parsing.

## Best solution

Define a read-only extension API over supported chat session services, with explicit access scope, content permissions, and lifecycle semantics. Keep evaluation and dashboard functionality extension-owned, and coordinate overlapping lifecycle requirements with https://github.com/microsoft/vscode/issues/325507.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.chatParticipantPrivate.d.ts`, `src/vscode-dts/vscode.proposed.chatSessionsProvider.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostChatAgents2.ts`, `src/vs/workbench/contrib/chat/common/chatService/chatService.ts`, `src/vs/workbench/contrib/chat/common/chatSessionsService.ts`
- **Validation:** The plan should define extension-host API tests in which an observer enumerates an inactive completed session, retrieves structured turns without reading storage files, and observes creation, turn changes, archive/title changes, and the agreed end condition. Include checks that unauthorized sessions remain inaccessible and that unloading a model does not falsely report conversation completion.
- **Behavior:**

  > Extensions need a supported read-only way to discover chat sessions, retrieve structured conversation history, and observe lifecycle changes without parsing JSONL or SQLite storage. The central acceptance scenario is accessing a completed session that is not the active panel session. Observation must respect the agreed access boundary and must not grant prompt injection, approval, renaming, or other session-control capabilities. Tests should establish both the permitted historical access and the lifecycle semantics selected by the API owners.
- **Trace:**

  > The stable ChatContext.history contract in src/vscode-dts/vscode.d.ts only covers the current participant's history in the current session. The chatSessionsProvider proposal manages extension-provided sessions, while chatParticipantPrivate supplies active-panel and disposal signals; extHost.api.impl.ts exposes those limited surfaces behind proposal gates. The chatDebug proposal adds core debug-event observation but not general historical conversation retrieval. Internal IChatService in src/vs/workbench/contrib/chat/common/chatService/chatService.ts already describes live models, history metadata, loading, and disposal, and IChatSessionsService in src/vs/workbench/contrib/chat/common/chatSessionsService.ts describes provider session items. The trace establishes an extension-boundary gap, not that these internal services already implement the requested cross-workspace contract. Keep private storage formats and provider ownership out of the public contract, and keep session mutation outside this request. Coordinate lifecycle design with https://github.com/microsoft/vscode/issues/325507 without treating its narrower, newer request as a duplicate canonical.
- **Open decisions:**
  - Which sessions may an observer access: only the current workspace, other workspaces in the same profile, or remote/provider-backed sessions as well?
  - What user authorization is required for an extension to read another participant's historical message content, and how does revocation affect subsequent access?
  - Does a session-ended event mean a completed run, model unload, explicit deletion, or another durable conversation lifecycle transition?
  - Must initial enumeration and subsequent events provide a recoverable snapshot/stream contract, or is best-effort notification sufficient?

## Evidence

- **Stable API boundary:** src/vscode-dts/vscode.d.ts:19673-19678 explicitly limits ChatContext.history to the current session and current participant. The stable chat namespace at lines 20118-20127 exposes createChatParticipant, not arbitrary-session enumeration or history retrieval.
- **Proposed APIs provide partial coverage:** src/vscode-dts/vscode.proposed.chatSessionsProvider.d.ts defines controllers and content providers for extension-managed sessions. src/vscode-dts/vscode.proposed.chatParticipantPrivate.d.ts supplies disposal and active-panel-resource events; src/vs/workbench/api/common/extHost.api.impl.ts:1737-1779 gates those surfaces behind their proposals and exposes no general session observation methods.
- **Debug observation is not session history access:** src/vscode-dts/vscode.proposed.chatDebug.d.ts:706-797 allows extensions to supply debug logs and available debug-session resources, plus receive core-originated debug events. It does not let an observer enumerate all existing chat sessions or retrieve their structured conversation histories.
- **Internal services are not an extension contract:** src/vs/workbench/contrib/chat/common/chatService/chatService.ts:2120-2247 exposes internal live models, session loading, history metadata, and creation/disposal events. Its disposal event explicitly distinguishes model unload from deletion, demonstrating that disposal cannot automatically mean the requested session-ended event.
- **Related observer request is newer and narrower:** https://github.com/microsoft/vscode/issues/325507 is open, created on 2026-07-12, and requests lifecycle/status and subagent relationships without message content. It supports demand for observation tooling but neither owns structured historical-content access nor qualifies as an older canonical for this re-reviewed item.
- **Older companion request is related, not equivalent:** https://github.com/microsoft/vscode/issues/316946 is open and describes a first-party mobile companion with steering and approvals. Its API-gap discussion overlaps this request, but that product does not subsume the general extension-owned evaluation, search, and historical observation contract.
- **Timeline references do not resolve this API gap:** https://github.com/microsoft/vscode/issues/328278 was closed as an accidental duplicate of https://github.com/microsoft/vscode/issues/328279. The latter's maintainer comment, https://github.com/microsoft/vscode/issues/328279#issuecomment-5136866152, places session-renaming functionality upstream in the runtime; that decision concerns a mutation tool, not extension session observation.
- **Storage precedent needs qualification:** The retrieved discussion at https://github.com/microsoft/vscode/issues/308381 contains a reporter comment saying it was closed for refiling, not a maintainer decision rejecting an observer API. Its closure therefore does not establish out-of-scope precedent for this request.
