# Issue #337315 — chat timeline view focuses topmost message in view

[https://github.com/microsoft/vscode/issues/337315](https://github.com/microsoft/vscode/issues/337315)

## Summary

Fresh, credible bug report (video attached) from a team member with a plausible root cause traced in promptTimelineModel.ts; keeping open — no fix commit exists yet since this was just filed.

## Change summary

Clicking an entry in the chat prompt timeline (gutter rail) while scrolled up highlights the wrong entry — the one that was topmost in the transcript before the click, not the one clicked.

## Best solution

Ensure the gutter rail's active-highlight state (model.activePromptId) is set synchronously and correctly when reveal() is called, instead of relying entirely on the scroll-driven recompute in _updateActive(), which can run against stale/pre-scroll row positions in the virtualized transcript list.

- **Behavior:**

  > Clicking any entry in the prompt-timeline gutter rail while scrolled away from that message should scroll the transcript to that message AND highlight that same entry in the rail. Currently the highlighted entry can instead remain the one that was topmost before the click. Acceptance: after reveal(requestId), model.activePromptId (and the rendered rail highlight) must equal requestId's owning tick, not the pre-scroll topmost item.
- **Trace:**

  > PromptTimelineGutterRail's highlight is bound to model.activePromptId (promptTimelineWidgetContrib.ts:164). reveal(requestId) in promptTimelineModel.ts (494-504) scrolls via this.widget.reveal() and explicitly re-sets _activeRequestId afterward, but never sets _activePromptId — that value is left to the onDidScroll-driven _updateActive() (line 245, 409-491), which walks widget.getElementTop() over currently rendered rows to infer the active prompt from scroll position. If the virtualized list's rows haven't been re-rendered at the new scroll offset when onDidScroll fires, this recompute uses stale row positions and can pick the previous topmost item instead of the just-revealed one. The boundary: don't touch the ruler rail's activeRequestId path (which reveal() already corrects) or the general scroll-tracking behavior used while the user scrolls manually — only the reveal-triggered path needs to guarantee activePromptId lands on the clicked entry.
