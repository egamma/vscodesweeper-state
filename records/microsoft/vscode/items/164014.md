# Issue #164014 — window.zoomLevel causing blurry canvas

[https://github.com/microsoft/vscode/issues/164014](https://github.com/microsoft/vscode/issues/164014)

## Summary

The requested zoom-factor behavior remains absent on current main, and the Backlog milestone records this as accepted but unscheduled work. Changing the established zoom mapping has compatibility implications, so it should remain open for an owner decision.

## Change summary

Use canvas-friendly discrete window zoom factors instead of fractional factors such as 1.44 that can make extension canvases blurry.

## Best solution

Decide whether `window.zoomLevel` should preserve Electron's exact `1.2 ** level` mapping or map levels to discrete, canvas-friendly factors, then apply the chosen semantics consistently during window creation, startup restoration, and runtime zoom changes.

## Plan brief

- **Likely files:** `src/vs/platform/window/common/window.ts`, `src/vs/platform/window/electron-browser/window.ts`, `src/vs/code/electron-browser/workbench/workbench.ts`, `src/vs/platform/windows/electron-main/windows.ts`
- **Validation:** Launch the Electron workbench at `window.zoomLevel: 2`, render a canvas sized from `window.devicePixelRatio`, and verify that its CSS and backing-store dimensions remain pixel-aligned and visually sharp; also verify zoom commands, reload restoration, and newly opened windows use the same resulting scale.
- **Behavior:**

  > Window zoom should not make correctly scaled extension canvases blurry because of an awkward fractional device-pixel ratio. The configured zoom level, zoom commands, restored windows, and newly opened windows must produce consistent scaling. Existing zoom persistence and multi-window behavior must remain intact. Acceptance includes a canvas comparison at zoom level 2 and consistency checks across startup, reload, and runtime zoom changes.
- **Trace:**

  > Current main preserves Electron's exponential mapping in `zoomLevelToZoomFactor` at src/vs/platform/window/common/window.ts, yielding `1.2 ** 2`, or 1.44. Runtime changes pass the level to `webFrame.setZoomLevel` in `applyZoom` at src/vs/platform/window/electron-browser/window.ts, while early startup restoration does the same in src/vs/code/electron-browser/workbench/workbench.ts. Browser-window construction separately supplies the corresponding exponential `zoomFactor` in src/vs/platform/windows/electron-main/windows.ts. The boundary includes all three lifecycle paths so they cannot disagree; editor-only zoom and integrated-browser per-page zoom are outside this request. The unresolved point begins with the compatibility contract for translating persisted `window.zoomLevel` values into visual scale.
- **Open decisions:**
  - Should existing `window.zoomLevel` values retain Electron's exact `1.2 ** level` visual scale, or should each level map to a discrete canvas-friendly factor even though that changes the rendered size for existing configurations?
  - If factors become discrete, which factor sequence is the supported public mapping for positive, negative, and fractional `window.zoomLevel` values?

## Evidence

- **current implementation:** src/vs/platform/window/common/window.ts defines `zoomLevelToZoomFactor` as `1.2 ** zoomLevel`, so level 2 still produces the reported factor 1.44.
- **runtime path:** src/vs/platform/window/electron-browser/window.ts `applyZoom` still calls Electron `webFrame.setZoomLevel(zoomLevel)`; src/vs/code/electron-browser/workbench/workbench.ts also restores the configured value through `setZoomLevel` during startup.
- **window creation path:** src/vs/platform/windows/electron-main/windows.ts initializes Electron's `zoomFactor` with the same `zoomLevelToZoomFactor` conversion, preserving the exponential mapping for newly created windows.
- **maintainer direction:** The maintainer acknowledged the alternative `setZoomFactor` API but raised concern about changing established zoom behavior: https://github.com/microsoft/vscode/issues/164014#issuecomment-1307209087.
- **canonical search:** Searches for blurry canvas, devicePixelRatio, and setZoomFactor/setZoomLevel issues found no older open issue with the same canvas-blurring symptom; the re-review duplicate bar is not met.
