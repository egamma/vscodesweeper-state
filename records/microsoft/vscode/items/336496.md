# Issue #336496 — Perf: per-row getMenuActions is uncached; tree find widget turns every update into a full list rebuild (20s freeze)

[https://github.com/microsoft/vscode/issues/336496](https://github.com/microsoft/vscode/issues/336496)

## Summary

Confirmed on current main via source tracing: both defects are real. Uncached per-call menu sort in menuService.ts plus a synchronous, un-coalesced tree.refilter() in FindController's onDidChangeModel handler combine to make every tree update a full-viewport re-render when the find widget is open and context menus are large.

## Change summary

Opening a tree's find widget and then updating the model (e.g. deleting an item) causes a 20s UI freeze when the tree has many rows and a large per-row context menu, because the find widget forces a full list rebuild and menu actions are recomputed uncached per row.

## Best solution

Two independent, bounded fixes: (1) cache the sorted/grouped menu structure in MenuInfo/menuService keyed by MenuId, invalidated on MenuRegistry changes rather than rebuilt per getMenuActions call; (2) route FindController's onDidChangeModel refilter() call through the existing refilterDelayer coalescing path (indexTreeModel.ts) instead of calling refilter() synchronously on every splice.

## Plan brief

- **Likely files:** `src/vs/platform/actions/common/menuService.ts`, `src/vs/base/browser/ui/tree/abstractTree.ts`, `src/vs/base/browser/ui/tree/indexTreeModel.ts`
- **Validation:** A tree/find-widget test asserting that a model splice while the find widget is open with a non-empty pattern does not force a full 0..N re-render (targeted splice range preserved), plus a menuService test asserting getMenuActions does not re-sort/re-filter the full menu item list on repeated calls when the registry is unchanged.
- **Behavior:**

  > With the tree find widget open and a non-empty pattern, a model update (e.g. deleting a row) should re-filter/re-render only the affected rows, not the entire viewport, and per-row menu action computation (getResourceActions, getAriaLabel) should not re-sort the full registered menu on every call when nothing in the registry changed. Acceptance: the same update with the find widget closed and open should have comparable renderer cost; a named test should fail before the fix (full-list rebuild / re-sort observed) and pass after.
- **Trace:**

  > Two independent code paths: (1) src/vs/platform/actions/common/menuService.ts createMenuActionGroups() (called via MenuService.getMenuActions) rebuilds and sorts the full menu item list from MenuRegistry.getMenuItems(id) on every call, with sorting bottoming out in MenuInfo.compareMenuItems/_compareTitles (localeCompare) — this is invoked twice per rendered row via TreeMenus.getResourceActions and the accessibility label provider in src/vs/workbench/browser/parts/views/treeView.ts. (2) src/vs/base/browser/ui/tree/abstractTree.ts:1195 FindController.onDidChangeModel calls tree.refilter() synchronously on every onDidChangeModel firing (which fires on every model splice while the widget is open with a pattern), invoking IndexTreeModel.refilter() (indexTreeModel.ts:476) directly rather than through the existing refilterDelayer (indexTreeModel.ts:116, used elsewhere at :324) that coalesces refilters for exactly this reason (see the reporter's reference to #135941). The boundary: do not change filter semantics or menu ordering — only the caching/coalescing layer. Related: reporter cites a companion issue for MenuInfoSnapshot redundancy (referenced in the issue body as #336495, not independently verified here).
- **Open decisions:**
  - Should the menu action cache live in MenuInfo/MenuService keyed by MenuId, or higher up in the tree renderer (memoize per-row menu actions until the registry or context changes)?
  - Should FindController route through the existing refilterDelayer, or does the synchronous-refilter behavior serve some UX requirement (e.g. immediate highlight) that would need preserving via a different coalescing strategy?
  - Should this be split into two separate PRs/issues (menu caching vs. tree find coalescing) given they are independently bounded fixes?

## Evidence

- **uncached menu sort:** src/vs/platform/actions/common/menuService.ts: createMenuActionGroups() calls MenuRegistry.getMenuItems(id).filter(...) then menuItems.sort(MenuInfo.compareMenuItems) on every invocation, with no caching of the sorted/grouped structure across calls.
- **synchronous refilter bypasses coalescing:** src/vs/base/browser/ui/tree/abstractTree.ts:1195 FindController.onDidChangeModel calls this.tree.refilter() synchronously on every model splice when the pattern is non-empty; src/vs/base/browser/ui/tree/indexTreeModel.ts:116/324 shows IndexTreeModel already has a refilterDelayer (MicrotaskDelay) that this path bypasses.
- **no fix present:** git log for src/vs/platform/actions/common/menuService.ts shows no recent change addressing this; the described uncached path and synchronous refilter call are unchanged on current main.
