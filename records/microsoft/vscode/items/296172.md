# Issue #296172 — Tool picker live-syncs to running agent session

[https://github.com/microsoft/vscode/issues/296172](https://github.com/microsoft/vscode/issues/296172)

## Summary

The cross-session path remains present on current main: default-Agent tool choices are global, and returning to a running session can propagate another session's changed selection into its active request. The issue should remain open while maintainers define the intended boundary between persistent defaults and an in-flight session's tool snapshot.

## Change summary

Prevent tool-picker changes made in one chat session from unexpectedly changing the tools available to an agent loop already running in another session.

## Best solution

Preserve each running agent loop's effective tool selection independently from tool-picker changes made in other sessions, while retaining any intended global default for future requests. Maintainers should first settle whether same-session picker changes and newly registered tools may update an in-flight request, and whether custom-agent configuration follows different persistence rules.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/chatSelectedTools.ts`, `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/input/chatSelectedTools.test.ts`
- **Validation:** Add a focused test with two default-Agent sessions sharing a widget: start a request in session A, change the picker in session B, reactivate A, and assert that A's active request does not receive B's tool selection; separately cover the maintainer-approved behavior for newly registered tools and same-session changes.
- **Behavior:**

  > A running agent loop keeps the effective tool selection established for that run when the user changes the picker in another chat session. Switching away from and back to the running session must not import the other session's selection into its active request. Persistent defaults may still govern future requests, and custom-agent or newly registered-tool behavior must follow the scoping decisions recorded during planning.
- **Trace:**

  > The picker writes through ChatSelectedTools.set in src/vs/workbench/contrib/chat/browser/actions/chatToolActions.ts. For the default Agent, ChatSelectedTools in src/vs/workbench/contrib/chat/browser/widget/input/chatSelectedTools.ts falls through to the profile-scoped global state. ChatWidget.getModeRequestOptions in src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts wraps that state in a session/mode-gated derived observable, but it reads the latest global selection again when the captured session is active. The autorun in src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts then forwards changes to the existing request through chatAgentService.setRequestTools. Commit f1eb6bb5f4383a2473c7ebc27d5767023de33b40, from https://github.com/microsoft/vscode/pull/296101, introduced the inactive-session snapshot and fixed https://github.com/microsoft/vscode/issues/293002, but this follow-up concerns the remaining in-flight synchronization boundary. Preserve intentional picker persistence for future requests and do not remove support for dynamically registered MCP or extension tools without an explicit product decision.
- **Open decisions:**
  - Should a default-Agent tool-picker change affect only future requests, the current session's active request, or every active default-Agent request?
  - When a new MCP or extension tool is registered during an agent loop, should it become available to that in-flight request automatically or only to later requests?
  - Should custom-agent tool changes remain tied to the agent definition across sessions while temporary overrides remain session-scoped?
