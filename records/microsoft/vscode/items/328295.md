# Issue #328295 — Detached Agents window does not expose MCP servers from Remote (WSL) extension host

[https://github.com/microsoft/vscode/issues/328295](https://github.com/microsoft/vscode/issues/328295)

## Summary

The remote MCP gap remains valid and is independently corroborated by a later WSL report. Current source still opens the Agents window on a local synthetic workspace and chooses the MCP gateway from that window's extension-host kind, rather than from the handed-off remote workspace.

## Change summary

Make MCP servers from a Remote WSL extension host available to sessions opened in the detached Agents window.

## Best solution

Resolve the MCP gateway against the selected session workspace's remote authority so a WSL-backed Agents session proxies that remote host's MCP registry, while local sessions continue using the local gateway. The design also needs deterministic scoping when the Agents window contains sessions targeting different hosts.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/electron-browser/agentSessions/agentSessionsActions.ts`, `src/vs/platform/windows/electron-main/windowsMainService.ts`, `src/vs/workbench/api/browser/mainThreadMcp.ts`, `src/vs/workbench/contrib/mcp/electron-browser/mcpGatewayService.ts`, `extensions/copilot/src/platform/mcp/vscode/mcpServiceImpl.ts`
- **Validation:** Add a targeted gateway-routing test that hands a WSL remote folder to the Agents window and asserts that starting an MCP gateway enumerates the remote broker's servers rather than the local broker's servers; finish with the issue's WSL steps and verify the same server works in both workspace Chat and the detached Agents session.
- **Behavior:**

  > Opening a WSL workspace in the detached Agents window must expose the same applicable MCP servers and tools available to Chat in that remote workspace. Starting and invoking a remote MCP tool must execute through the WSL extension host, while local Agents sessions must retain their current local MCP behavior. Switching between sessions targeting different hosts must not leak or reuse servers from the wrong host.
- **Trace:**

  > The editor-side handoff in src/vs/workbench/contrib/chat/electron-browser/agentSessions/agentSessionsActions.ts passes the remote folder URI to INativeHostService.openAgentsWindow. WindowsMainService.openAgentsWindow in src/vs/platform/windows/electron-main/windowsMainService.ts nevertheless opens the local synthetic agent-sessions.code-workspace and delivers that URI later as a workspace-selection message. MainThreadMcp.$startMcpGateway in src/vs/workbench/api/browser/mainThreadMcp.ts chooses remote versus local exclusively from the current extension host's ExtensionHostKind, and WorkbenchMcpGatewayService then connects either to IRemoteAgentService or the local main-process channel. This leaves no routing step from the selected Agents session workspace to its WSL MCP broker. Preserve local gateway behavior and avoid coupling one detached window permanently to the editor window that happened to open it. The later matching report is https://github.com/microsoft/vscode/issues/333104; the folder-context problem in https://github.com/microsoft/vscode/issues/330280 may share the remote-resource boundary but is outside this fix's behavior contract.
- **Open decisions:**
  - When one Agents window contains sessions targeting different local or remote hosts, should MCP availability follow each session's selected workspace, the window that initiated the handoff, or an explicit per-session host selection?

## Evidence

- **confirmed reproduction:** The report provides repeatable WSL steps, confirms the same server works in workspace Chat, and states the failure persists after restart on VS Code 1.131.0.
- **independent corroboration:** https://github.com/microsoft/vscode/issues/333104 reports the same observable absence of MCP servers in a WSL-backed Agents window on VS Code 1.135.0. It is newer than this re-reviewed issue, so it cannot serve as the canonical duplicate; this issue is the better consolidation target.
- **window boundary:** src/vs/workbench/contrib/chat/electron-browser/agentSessions/agentSessionsActions.ts passes the invoking remote folder to openAgentsWindow, but src/vs/platform/windows/electron-main/windowsMainService.ts always opens the local synthetic agent-sessions.code-workspace and sends the folder URI afterward through vscode:selectAgentsFolder.
- **gateway routing:** src/vs/workbench/api/browser/mainThreadMcp.ts:$startMcpGateway selects remote routing only when the detached window's own extension host is ExtensionHostKind.Remote; src/vs/workbench/contrib/mcp/electron-browser/mcpGatewayService.ts otherwise creates the gateway through the local main-process channel. That does not represent the handed-off WSL workspace's MCP registry.
- **related but distinct:** https://github.com/microsoft/vscode/issues/330280 concerns remote folder attachments rather than MCP discovery, and https://github.com/microsoft/vscode/issues/325081 concerns authenticated MCP servers generally; neither is the same reporter-observable symptom required for a re-review duplicate close.
