# Issue #332601 — Copilot Not Respecting Disablement on Agent Host

[https://github.com/microsoft/vscode/issues/332601](https://github.com/microsoft/vscode/issues/332601)

## Summary

The reporter supplied the requested enterprise scenario, and current main confirms a real control gap: the existing settings govern defaults or the legacy local harness, while Copilot Agent Host remains registered and visible. Reclassify this as a feature request and route it to the Agent Host/chat owners.

## Change summary

Provide an enforceable enterprise control that permits selected Agent Host harnesses while disabling Copilot Agent Host.

## Best solution

Define an authoritative managed-setting contract for allowed Agent Host providers, enforce it when providers and sessions are exposed or created, and project the effective result into the harness picker. Do not reinterpret `chat.editor.localAgent.enabled`, which explicitly controls the separate legacy local harness.

- **Behavior:**

  > An administrator can permit Claude and Codex Agent Host harnesses while disabling Copilot Agent Host. Governed users do not see Copilot in the new-session harness picker and cannot start it through commands or restored UI state. Unmanaged users retain the current provider availability, and disabling the legacy local harness remains independent.
- **Trace:**

  > Current main registers Copilot unconditionally in src/vs/platform/agentHost/node/agentHostMain.ts and src/vs/platform/agentHost/node/agentHostServerMain.ts. Registered session contributions are exposed by isVisibleEditorChatSessionType in src/vs/workbench/contrib/chat/common/constants.ts and consumed by SessionTargetPickerActionItem. The reported settings only affect default selection or the legacy local harness, as declared in src/vs/platform/agentHost/common/agentHostEnablementService.ts. Existing managed policy in src/vs/platform/policy/common/copilotManagedSettings.ts gates third-party harnesses but provides no inverse control for Copilot. The boundary must include authoritative provider/session enforcement rather than only hiding picker UI; existing default-selection and local-harness semantics must not change.
- **Open decisions:**
  - Should the enterprise contract be an allowlist of permitted Agent Host providers or independent enablement controls for each provider?
  - Should disabling a provider block only creation of new sessions, or also prevent restoring and continuing existing sessions for that provider?
  - Which managed-settings scope is authoritative for provider availability when local and remote Agent Hosts are both available?
