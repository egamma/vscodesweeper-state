# Issue #335477 — Chat Rename Reverting Back

[https://github.com/microsoft/vscode/issues/335477](https://github.com/microsoft/vscode/issues/335477)

## Summary

Traced a concrete, plausible root cause on main: renaming a chat session updates only the in-memory index title, not the persisted index or the full session file, so the rename is lost once the session reloads. A second commenter independently reproduced this on a different platform/build, reinforcing the finding.

## Change summary

Renaming a chat from the history list doesn't stick — the custom title reverts to the auto-generated one after reopening the chat.

## Best solution

Fix `ChatSessionStore.setSessionTitle` (src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts) to flush the index to storage and, when no live `ChatModel` is loaded, persist the title into the full serialized session file as well, so a subsequent load doesn't restore the stale (un-renamed) `customTitle`.

- **Trace:**

  > `ChatSessionStore.setSessionTitle` (chatSessionStore.ts:510-517) only mutates the cached index object and never calls the private `flushIndex()` that every sibling index mutator calls, so the rename is never written to `IStorageService`. Additionally, `ChatService.setChatSessionTitle` (chatServiceImpl.ts:448-461) only updates the live `ChatModel.customTitle` when the session is already loaded in `_sessionModels`; when it isn't, no full session file gets rewritten via `writeSession`/`storeSessions`, so `ChatModel._customTitle` (chatModel.ts:2843, restored from `ISerializableChatData.customTitle`) reverts to the stale value on next load, and the index gets resynced from that stale model (`getSessionMetadataSync`, chatSessionStore.ts:868-869), erasing the rename. The fix must not change the live-model rename path (already correct) or the index/session file formats — only ensure the not-currently-loaded rename path persists both the index and (when needed) the full session file.

## Evidence

- **missing flush:** src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts:510-517 `setSessionTitle` mutates `index.entries[sessionId].title` in the in-memory `indexCache` but never calls `this.flushIndex()`, unlike every sibling mutator in the file (`deleteSession` L493-498, `clearAllSessions` L500-508, the error path in `readSession` L636-648, `migrate` L624-633), which all call `flushIndex()` after mutating the index.
- **no full-session write when unloaded:** chatServiceImpl.ts `setChatSessionTitle` (L448-461) only calls `model.setCustomTitle(title)` when the session is currently a live in-memory model (`this._sessionModels.get(sessionResource)`); when the chat is renamed from the history list without being open, `model` is undefined, so only the volatile index metadata is touched — `writeSession`/`storeSessions` (which serialize the full `ChatModel`, including `customTitle`, to disk) are never invoked for that session.
- **reload restores stale customTitle:** chatModel.ts:2843 restores `_customTitle` from the on-disk `ISerializableChatData.customTitle`; if that file was never rewritten with the new title, reopening the session resets `customTitle` to the old value, and the next index recompute (getSessionMetadataSync, chatSessionStore.ts:868-869, uses `session.customTitle || session.title`) writes the stale title back into the index — reproducing the observed revert.
- **test gap:** The existing test `setSessionTitle updates existing session title` (src/vs/workbench/contrib/chat/test/common/model/chatSessionStore.test.ts:266-275) only asserts against the same in-process `indexCache` via `getIndex()`; it never checks the underlying `storageService` write or the full session file, so it would not catch this bug.
- **independent confirmation:** Comment from mariuszo-at-microsoft-com reproduces on Insiders 1.139.0 (commit 4fa9fcf) via WSL, on a long (~100 turn) session, noting repeated renames don't help — matches the traced pattern of the title never being durably persisted.
