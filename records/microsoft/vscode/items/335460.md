# Issue #335460 — Updating external plugins broken for manual and AutoUpdates

[https://github.com/microsoft/vscode/issues/335460](https://github.com/microsoft/vscode/issues/335460)

## Summary

Traced the reporter's five specific claims against current main and every one holds: the manual/auto update path for git-sourced agent plugins is genuinely broken in several compounding ways. Routing to the chat/plugins area rather than closing.

## Change summary

Manual and automatic 'Update Plugins' fails to update agent plugins whose source is an external Git repository (as opposed to relative-path plugins inside the marketplace repo).

## Best solution

Fix the update path in pluginInstallService.ts/pluginSources.ts/agentPluginRepositoryService.ts so that: force bypasses hasSourceChanged, update() clones when the new ref/sha-derived cache dir doesn't exist yet, and addInstalledPlugin re-keys the installed.json entry to the newly computed install URI instead of reusing the stale one.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/pluginInstallService.ts`, `src/vs/workbench/contrib/chat/browser/pluginSources.ts`, `src/vs/workbench/contrib/chat/browser/agentPluginRepositoryService.ts`, `src/vs/workbench/contrib/chat/common/plugins/pluginMarketplaceService.ts`
- **Validation:** Add/extend tests in src/vs/workbench/contrib/chat/test/browser/plugins/pluginInstallService.test.ts covering: (1) force=true updates a git-sourced plugin even when hasSourceChanged is false due to only a version bump, (2) update() clones into a new ref/sha-derived cache dir when it doesn't yet exist, (3) after a path/ref/sha change, the installed-plugins store is keyed by the newly computed install URI, not the old one.
- **Behavior:**

  > Manually or automatically updating agent plugins whose source is an external Git repository (GitHub or generic Git URL, not a relative-path plugin inside the marketplace repo) should actually pick up: (a) new commits on an unchanged ref/sha, (b) a changed ref/sha even when no local clone exists yet for that revision, and (c) a bumped `version` in the marketplace entry when force-updating. After an update that changes the effective ref/sha/path, the installed-plugins store must reflect the new install location, not the pre-update one.
- **Trace:**

  > Update flow: pluginInstallService.ts `updateAllPlugins` -> per non-relative-path plugin checks `hasSourceChanged(installed, live)` (pluginMarketplaceService.ts:1253) before calling `agentPluginRepositoryService.updatePluginSource` -> `pluginSources.ts` `AbstractGitPluginSource.update()`. Root causes: (1) `options.force` only skips the npm/pip `!desc.version` check (pluginInstallService.ts:459), never the hasSourceChanged gate, so force cannot pull unchanged-source updates; (2) `update()` (pluginSources.ts:111-118) returns false with a log warning when `_getRepoDir` doesn't exist instead of falling through to `_cloneRepository`, and since `_getRepoDir` for GitHub/GitUrl sources appends a ref/sha suffix (pluginSources.ts:278, 322), a ref/sha change always targets a fresh, not-yet-cloned directory; (3) `pluginInstallService.ts:480` calls `addInstalledPlugin(entry.pluginUri, livePlugin)` with the pre-update URI rather than recomputing via `getPluginSourceInstallUri`. Boundary: keep relative-path (in-marketplace) plugin update behavior and the npm/pip package update path unchanged; do not touch marketplace-repo pull logic (`pullRepository`). Open questions for the trace-owner: whether force should fully bypass hasSourceChanged for git sources or only relax specific fields, and how re-keying installed.json entries should be sequenced with cleanup of the old cache dir to avoid orphaned entries mid-update.
- **Open decisions:**
  - Should `force` fully bypass hasSourceChanged for git-sourced plugins, or only relax the version/ref/sha portion of the check?
  - When ref/sha/path changes move a plugin to a new install URI, should the store re-key in place or should the old entry be removed and a new one added (and what happens to the old cache directory)?
  - Should scheduled/automatic plugin-update runs log start/result/skip regardless of the `silent` flag, or only in a verbose/debug mode?

## Evidence

- **hasSourceChanged gate + force not bypassing it:** src/vs/workbench/contrib/chat/browser/pluginInstallService.ts:453 skips independent git plugins entirely when `!hasSourceChanged(...)`; the `options.force` flag (line 459) only bypasses the npm/pip missing-version check, never the hasSourceChanged gate for git sources — matches claim #2.
- **update() refuses to clone a missing cache dir:** src/vs/workbench/contrib/chat/browser/pluginSources.ts:111-118 `AbstractGitPluginSource.update()` checks `repoExists` and returns false with a warning log ('source repository not cloned') if the directory is missing, never falling back to clone — matches claim #3.
- **cache dir is keyed by ref/sha:** GitHubPluginSource._getRepoDir (pluginSources.ts:275-279) and GitUrlPluginSource._getRepoDir (pluginSources.ts:319-323) both append `gitRevisionCacheSuffix(ref, sha)` to the cache path, so changing ref/sha does select a new, not-yet-cloned directory that update() then silently refuses to populate.
- **stale installed-plugin URI key on update:** pluginInstallService.ts:480 calls `this._pluginMarketplaceService.addInstalledPlugin(entry.pluginUri, livePlugin)` reusing the pre-update `entry.pluginUri` rather than the freshly computed install URI, even though `getPluginSourceInstallUri` (agentPluginRepositoryService.ts:393-395) would compute a different URI when path/ref/sha changed — matches claim #4.
