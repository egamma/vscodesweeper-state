# Issue #321480 — Pasting occurs before confirmation

[https://github.com/microsoft/vscode/issues/321480](https://github.com/microsoft/vscode/issues/321480)

## Summary

The defect remains source-reproducible on current main: an Explorer paste can execute through both the keybinding and native DOM-event paths, so the first operation bypasses the confirmation. Route this to the file Explorer area rather than closing it.

## Change summary

Pasting a file between remote windows performs one copy before the confirmation decision and may perform a second copy when confirmed.

## Best solution

Deduplicate the Explorer keybinding and native clipboard-event paths before either performs a file operation, while preserving external OS file paste and ensuring cancellation performs no copy.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/browser/fileActions.ts`, `src/vs/workbench/contrib/files/browser/fileActions.contribution.ts`
- **Validation:** Exercise file paste between two remote windows: Cancel must create no file and Paste must create exactly one. Also copy a file from Finder/Explorer into the VS Code Explorer and verify it still pastes exactly once; add an automated browser test covering both dispatch paths if the Explorer test harness can represent a ClipboardEvent with files.
- **Behavior:**

  > Pasting a copied file into another remote window must not modify the destination before the confirmation is accepted. Cancel leaves the destination unchanged, while Paste creates exactly one copy. Pasting files from the native OS file manager into the Explorer must continue to work exactly once.
- **Trace:**

  > The Explorer currently has two routes for one Cmd/Ctrl+V gesture: the `filesExplorer.paste` keybinding in src/vs/workbench/contrib/files/browser/fileActions.contribution.ts and the window-level DOM paste listener in src/vs/workbench/contrib/files/browser/views/explorerView.ts. The keybinding calls `pasteFileHandler` without a FileList, so src/vs/workbench/contrib/files/browser/fileActions.ts does not request native-paste confirmation and performs the first copy; the DOM path supplies `clipboardData.files` and displays the confirmation. https://github.com/microsoft/vscode/pull/323002 attempted to suppress the DOM path after asynchronously checking clipboard resources, but https://github.com/microsoft/vscode/pull/323885 reverted it because ClipboardEvent DataTransfer data is only valid during synchronous dispatch. Preserve native OS-to-Explorer paste and the event-scoped FileList lifetime; do not remove confirmation or change ordinary in-Explorer copy semantics.

## Evidence

- **current source:** src/vs/workbench/contrib/files/browser/fileActions.contribution.ts registers Cmd/Ctrl+V to invoke `filesExplorer.paste`, while src/vs/workbench/contrib/files/browser/views/explorerView.ts:399-407 independently handles the same DOM paste event and invokes `filesExplorer.paste` with `clipboardData.files`.
- **confirmation ordering:** src/vs/workbench/contrib/files/browser/fileActions.ts:1133-1174 only enables `explorer.confirmPasteNative` when a FileList is supplied. The keybinding invocation has no FileList and can therefore perform the clipboard-resource paste immediately, while the DOM invocation waits for confirmation.
- **reverted fix:** https://github.com/microsoft/vscode/pull/323002 added a clipboard-resource guard specifically to prevent the double paste, but https://github.com/microsoft/vscode/pull/323885 reverted that guard on main because awaiting `hasResources()` invalidated the event-scoped DataTransfer and broke external OS file paste.
- **related report:** https://github.com/microsoft/vscode/issues/323841 reports the same Cancel-pastes-once/Paste-pastes-twice symptom, but it was created after this re-reviewed issue and therefore cannot serve as its duplicate canonical.
- **prior canonical unavailable:** https://github.com/microsoft/vscode/issues/321387 was closed by the subsequently reverted fix in https://github.com/microsoft/vscode/pull/323002, so it is neither an open duplicate target nor evidence that current main is fixed.
