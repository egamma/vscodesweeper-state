# Issue #340829 — Copilot agent can overwrite newer workspace files from a stale chat session

[https://github.com/microsoft/vscode/issues/340829](https://github.com/microsoft/vscode/issues/340829)

## Summary

Keep open: another user confirms destructive overwrites, and current source contains a session-restoration path that replaces live model contents with saved session contents. The exact relationship between that path, stale agent edits, and cross-window acceptance still needs isolation before choosing a fix.

## Change summary

Prevent resumed Copilot sessions from silently replacing newer workspace edits with stale session contents.

## Best solution

Preserve newer workspace and editor contents when restoring or applying changes from an older chat session, with explicit reconciliation for conflicting edits. First distinguish snapshot restoration from stale tool-generated edits and external-save conflicts so the protection covers the actual failure rather than only one symptom.

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedDocumentEntry.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingTextModelChangeService.ts`, `src/vs/workbench/services/textfile/common/textFileEditorModel.ts`, `src/vs/workbench/contrib/chat/test/browser/chatEditing/chatEditingService.test.ts`
- **Validation:** Using disposable sample files, persist a session with pending edits, change the same files to newer contents outside that session, then reopen it, request another edit, and accept. Inspect contents after each stage to identify the first destructive transition; repeat with unsaved editor changes and a second application modifying disk contents. The resulting regression check must preserve unrelated newer edits and require explicit reconciliation before conflicting replacement, while ordinary nonconflicting agent edits and intentional checkpoint restoration continue to work.
- **Behavior:**

  > Resuming an older chat session and requesting edits must not silently erase newer workspace changes. Newer unsaved editor contents and external on-disk changes both need coverage. Acceptance should preserve unrelated newer edits and make conflicting replacement explicit. Ordinary agent edits and deliberately requested checkpoint restoration must remain functional.
- **Trace:**

  > ChatEditingSession._init restores recentSnapshot through _initEntries in src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts. Modified snapshot entries reach ChatEditingModifiedDocumentEntry.restoreFromSnapshot with content restoration enabled, and ChatEditingTextModelChangeService.resetDocumentValues replaces the live model's entire contents without a freshness check at that boundary. Separately, _acceptEdits applies agent-provided edits, while _doAccept saves through TextFileEditorModel, which already has mtime/etag conflict protection. These are distinct mechanisms; neither the report nor the discussion proves which transition caused the original loss. Isolate restoration, edit application, and save acceptance before settling the implementation boundary, and preserve existing save-conflict protection and intentional checkpoint semantics. Related leads https://github.com/microsoft/vscode/issues/317607 and https://github.com/microsoft/vscode/issues/313703 remain unverified rather than established duplicate targets.
