# Issue #134452 — Support global evaluation that requires a file for context

[https://github.com/microsoft/vscode/issues/134452](https://github.com/microsoft/vscode/issues/134452)

## Summary

A real gap remains on current main: global Debug Console evaluations carry neither the active source nor another selectable evaluation context. The existing debug-adapter tracker workaround is Dart-specific and does not provide the standardized DAP behavior discussed in the issue, so the request should remain open under discussion.

## Change summary

Provide file, thread, or adapter-defined context when evaluating Debug Console expressions without a stack frame.

## Best solution

Define a DAP-compatible evaluation-context contract and implement an initial VS Code client experience for global REPL evaluation. A maintainer should first decide whether the initial scope implicitly uses the active editor source or introduces explicit context selection.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/repl.ts`, `src/vs/workbench/contrib/debug/common/replModel.ts`, `src/vs/workbench/contrib/debug/common/debugModel.ts`, `src/vs/workbench/contrib/debug/common/debug.ts`, `src/vs/workbench/contrib/debug/browser/debugSession.ts`, `src/vs/workbench/contrib/debug/common/debugProtocol.d.ts`, `src/vs/workbench/contrib/debug/test/browser/repl.test.ts`
- **Validation:** Extend the debug REPL tests with a global evaluation submitted without a frame and assert that the resulting EvaluateArguments carries the context selected by the approved design; run it with scripts/test.sh --grep "global REPL evaluation".
- **Behavior:**

  > When an expression is submitted in the Debug Console while execution is running and no stack frame is available, a supporting debug adapter receives enough standardized context to evaluate it in the intended file, library, thread, or adapter-defined scope. Evaluations made against an existing stack frame retain their current behavior. The plan must settle how a user chooses or understands the context and what happens when no usable context exists. Acceptance includes inspecting the emitted evaluate request in a Debug Console test and confirming framed evaluations remain unchanged.
- **Trace:**

  > Repl.acceptReplInput in src/vs/workbench/contrib/debug/browser/repl.ts currently sends only the focused stack frame and expression. DebugSession.addReplExpression delegates through ReplModel.addReplExpression, whose call to ExpressionContainer.evaluateExpression supplies no IDebugEvaluatePosition; DebugSession.evaluate therefore emits no source, line, or column when frameId is absent. Hover evaluation already demonstrates location forwarding in src/vs/workbench/contrib/debug/browser/debugHover.ts, but its source/line semantics do not establish a global-context selection contract. The public protocol type in src/vs/workbench/contrib/debug/common/debugProtocol.d.ts has no context-discovery or active-source field, while DebugAdapterTracker offers only a custom extension-side mutation workaround. https://github.com/microsoft/debug-adapter-protocol/issues/57 discusses the broader multiple-global-object problem but not this same reporter-observable file-context behavior. Keep paused frame-scoped evaluations and hover location behavior outside the change.
- **Open decisions:**
  - Should the first supported behavior implicitly use the active editor source, or should users explicitly select from contexts supplied by the debug adapter?
  - Should selectable evaluation contexts be standardized entirely in DAP, exposed through a VS Code extension API, or split between the two?
  - When no active source or selectable context is available, should VS Code preserve the current unscoped evaluation request, prompt the user, or decline the evaluation?
  - Does the initial public contract include thread selection, or does the debug adapter infer a thread until a later context-selection capability is designed?

## Evidence

- **current REPL path:** src/vs/workbench/contrib/debug/browser/repl.ts Repl.acceptReplInput passes only the focused stack frame and expression to IDebugSession.addReplExpression; src/vs/workbench/contrib/debug/common/replModel.ts then calls evaluateExpression without source or location context.
- **request construction:** src/vs/workbench/contrib/debug/common/debugModel.ts forwards an undefined location for global REPL evaluation, and src/vs/workbench/contrib/debug/browser/debugSession.ts only populates EvaluateArguments.source, line, and column from that optional location. Consequently a no-frame REPL request currently contains no file context.
- **protocol gap:** src/vs/workbench/contrib/debug/common/debugProtocol.d.ts has contextual source/line fields for an evaluation location, but no activeSource field, evaluation-context discovery request, or selectable context identifier.
- **existing workaround:** https://github.com/microsoft/vscode/issues/134452#issuecomment-976417546 identifies DebugAdapterTracker message mutation as an extension-specific workaround. src/vscode-dts/vscode.d.ts exposes onWillReceiveMessage, but documents trackers as providing read access; this does not standardize the context for reusable debug adapters or other clients.
- **related protocol request:** https://github.com/microsoft/debug-adapter-protocol/issues/57 is an older open request about selecting among multiple runtime global objects. It is related to context discovery, but it reports a different observable scenario from supplying the active file/library for Dart global evaluation, so it does not meet the stronger duplicate bar for this re-reviewed issue.
- **maintainer discussion:** The discussion converged on passing the active editor source as a pragmatic first step, while leaving explicit thread or adapter-defined context selection unresolved; the reporter reiterated interest in both paths at https://github.com/microsoft/vscode/issues/134452#issuecomment-1628988287.
