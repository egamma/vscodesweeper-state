# Issue #204031 — Don't link the variable viewer to just notebooks

[https://github.com/microsoft/vscode/issues/204031](https://github.com/microsoft/vscode/issues/204031)

## Summary

The central API gap remains: the built-in REPL can use the variable viewer through notebook infrastructure, but independent Julia REPL and test processes cannot supply variables without that coupling. Keep this focused request open for a lifetime and ownership design; the existing notebook API and debug-visualization proposals do not fully cover it.

## Change summary

Allow extensions to expose variables from independent REPL and test processes in the built-in variable viewer, with process-level grouping rather than mandatory notebook ownership.

## Best solution

Establish a concrete lifetime-bearing owner for non-notebook variable sources and define how multiple processes appear in the shared viewer. Preserve notebook integrations while allowing extension-managed processes to participate without manufacturing notebooks or paused debug sessions.

- **Validation:** After agreeing the API contract, use an extension fixture with two independent process-backed variable sources, no notebook documents, and no debug session. Verify that both sources are identifiable, variables can be expanded and refreshed while processes are idle, terminating one source removes only its scope, and existing notebook-backed providers continue working.
- **Behavior:**

  > Extensions should be able to show variables from independently managed REPL processes in the built-in viewer without requiring notebook documents or paused debug sessions. Multiple processes must be distinguishable, and variable updates and source termination must have defined behavior. Acceptance should include two independent sources, nested variables, idle-state refresh, source removal, and unchanged notebook-provider behavior. Test-process support is a requested future use case whose initial scope needs agreement.
- **Trace:**

  > The proposed API in src/vscode-dts/vscode.proposed.notebookVariableProvider.d.ts is owned by NotebookController and uses NotebookDocument for requests and update events. ExtHostNotebookKernels.$provideVariables resolves the notebook before dispatch, while NotebookVariableDataSource obtains variables from the selected notebook kernel. NotebookVariablesView stores one activeNotebook and supplies it as the tree root; its REPL title does not remove those dependencies. Existing notebook-backed REPL support therefore does not resolve the independent-process requirement. The maintainer identified lifetime and applicability as the API boundary at https://github.com/microsoft/vscode/issues/204031#issuecomment-2073618260, and a contributor suggested kernel ownership in the following comment. Preserve notebook providers and ordinary debugging semantics; uncertainty starts at the public ownership/lifetime contract and presentation of multiple sources.
- **Open decisions:**
  - What concrete public owner defines a non-notebook variable source's lifetime and applicability: a kernel/runtime session or a separately registered process source?
  - Should the viewer display all registered process sources as top-level groups, or show only a selected source with an explicit source selector?
  - Should the initial contract support arbitrary extension-managed processes, including test processes, or initially support only REPL sessions?

## Evidence

- **Current API remains notebook-bound:** src/vscode-dts/vscode.proposed.notebookVariableProvider.d.ts attaches variableProvider to NotebookController; both onDidChangeVariables and provideVariables require NotebookDocument. src/vs/workbench/api/common/extHostNotebookKernels.ts:$provideVariables resolves a notebook document before invoking the provider.
- **Current viewer has a single notebook root:** src/vs/workbench/contrib/notebook/browser/contrib/notebookVariables/notebookVariablesView.ts tracks activeNotebook and sets a notebook root as tree input. notebookVariablesDataSource.ts requires NotebookTextModel on root and variable elements and obtains variables through the selected notebook kernel; it does not expose independent process roots.
- **Existing capability is partial:** notebookVariables.ts:handleInitEvent recognizes workbench.editor.repl, but hasVariableProvider still resolves a notebook model and selected kernel. notebookVariablesView.ts changes its title to REPL Variables for composite notebook inputs.
