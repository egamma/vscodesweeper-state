# Issue #258328 — Expose QuickTree in VS Code API

[https://github.com/microsoft/vscode/issues/258328](https://github.com/microsoft/vscode/issues/258328)

## Summary

Keep open: QuickTree exists internally, but extensions still cannot create one. This team-authored API request remains necessary; the related extension-exposure issue was explicitly closed as a duplicate of this one.

## Change summary

Expose a QuickTree creation API so extensions can present hierarchical quick-input pickers.

## Best solution

Define an extension-facing QuickTree contract backed by the existing core widget, then introduce it through the proposed-API process. Resolve the initial selection and tree-data scope with the API owner before implementation, preserving existing QuickPick behavior.

## Plan brief

- **Likely files:** `src/vs/platform/quickinput/common/quickInput.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostQuickOpen.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadQuickOpen.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** The plan should end with an extension-host API test that creates the proposed picker, supplies nested items, observes the agreed selection and acceptance events, and disposes it. Manually verify expansion, filtering, keyboard navigation, and cancellation, and run the relevant existing quick-input tests to establish unchanged QuickPick behavior.
- **Behavior:**

  > Extensions cannot currently present the hierarchical quick-input picker already available to core callers. An extension-facing creation API should let an extension populate and display that picker, observe selection and acceptance, and manage its lifetime without contributing a persistent view. Acceptance checks must exercise nested items and the agreed selection model through an actual extension call. Existing QuickPick and InputBox behavior must remain unchanged.
- **Trace:**

  > IQuickInputService.createQuickTree and IQuickTree in src/vs/platform/quickinput/common/quickInput.ts establish the existing internal widget contract. The extension boundary currently stops at QuickPick and InputBox: extHost.api.impl.ts exports their factories, extHostQuickOpen.ts implements them, extHost.protocol.ts transfers only those two input types, and MainThreadQuickOpen.$createOrUpdate constructs only those controls. Searches of stable and proposed declaration files found no QuickTree API. https://github.com/microsoft/vscode/issues/250638 explicitly separates completed core support from extension exposure, and https://github.com/microsoft/vscode/issues/258762 was closed into this request. The uncertainty starts at which internal capabilities become the initial public contract; single selection and lazy loading have separate discussions at https://github.com/microsoft/vscode/issues/258764 and https://github.com/microsoft/vscode/issues/258655. Preserve existing picker contracts and do not assume those related enhancements must ship with initial API exposure.
- **Open decisions:**
  - Should the initial extension API expose the existing checkbox-based multi-selection behavior only, or also support single-selection trees?
  - Should the initial public data contract accept an eagerly supplied nested item tree, or include lazy child loading?
