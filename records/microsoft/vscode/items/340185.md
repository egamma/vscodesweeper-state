# Issue #340185 — Terminal created from a contributed terminal profile is not focused when the extension host is remote (creation is not awaited before focusing the "last" instance)

[https://github.com/microsoft/vscode/issues/340185](https://github.com/microsoft/vscode/issues/340185)

## Summary

Confirmed from source on main: contributed terminal profiles are focused via a race between the main-thread 'last instance' guess and an unawaited extension-host creation call, which only manifests with remote-extension-host latency. Real, bounded bug, not yet fixed.

## Change summary

A terminal created from a contributed (extension) terminal profile doesn't receive keyboard focus when the extension host is remote (Codespaces/SSH/web), because the main thread focuses 'the last instance' before the new terminal has actually been registered.

## Best solution

Make $createContributedProfileTerminal resolve only after the instance is created (have createExtensionTerminal/createTerminalFromOptions await terminal.create(...)/terminal.createExtensionTerminal(...) and return the new instance id), then have TerminalService.createContributedTerminalProfile focus that specific instance by id instead of 'the last instance by index'.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/terminal/browser/terminalService.ts`, `src/vs/workbench/api/common/extHostTerminalService.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadTerminalService.ts`
- **Validation:** A test (or manual check with an artificial delay injected into the ext-host terminal creation path, simulating remote latency) asserting the newly created contributed-profile terminal is the focused/active instance after createContributedTerminalProfile() resolves, even when other terminal-list mutations race it.
- **Behavior:**

  > After invoking a contributed terminal profile (e.g. from the terminal panel's '+' dropdown), the newly created terminal must receive keyboard focus just like a built-in-profile terminal does today — regardless of extension-host round-trip latency (local or remote). Acceptance: with a remote extension host (or a simulated creation delay), the contributed-profile terminal becomes the active, focused instance; built-in profile and window.createTerminal()+show() behavior are unchanged.
- **Trace:**

  > Root cause: TerminalService.createContributedTerminalProfile() (src/vs/workbench/contrib/terminal/browser/terminalService.ts, ~lines 413-424) focuses 'the last instance' by index immediately after the RPC call resolves, but on the ext-host side $createContributedProfileTerminal (src/vs/workbench/api/common/extHostTerminalService.ts, ~lines 866-903) calls createExtensionTerminal or createTerminalFromOptions without awaiting the underlying terminal.create(...)/terminal.createExtensionTerminal(...) calls, so the RPC resolves before the new instance is registered on the main thread. With a remote extension host the round trip is slow enough that a different terminal (or none) is 'last' when focus is applied. Boundary: do not change the built-in-profile or window.createTerminal() creation paths, which already work correctly; the fix is scoped to the contributed-profile flow. Open question for a maintainer: whether to widen $createContributedProfileTerminal's protocol signature to return the created terminal id (a cross-process contract change in extHost.protocol.ts/mainThreadTerminalService), or to correlate the new instance some other way (e.g. a request/creation token) — this is a public IPC contract choice, not an implementation detail. Refs: https://github.com/microsoft/vscode/issues/340185; workaround precedent at https://github.com/REditorSupport/vscode-R/pull/1839.
- **Open decisions:**
  - Should the ext-host/main-thread terminal-creation protocol be widened to return the created terminal's id synchronously with the await (changing $createContributedProfileTerminal's Promise<void> contract), or should correlation use a different mechanism (e.g. a creation token passed through and matched on the main thread)?

## Evidence

- **race confirmed in main-thread code:** src/vs/workbench/contrib/terminal/browser/terminalService.ts createContributedTerminalProfile() awaits profileProvider.createContributedTerminalProfile(options) and then immediately does this._terminalGroupService.setActiveInstanceByIndex(instances.length - 1) — it assumes the new instance is already the last one in the list.
- **ext-host side is fire-and-forget:** src/vs/workbench/api/common/extHostTerminalService.ts $createContributedProfileTerminal() calls this.createExtensionTerminal(profileOptions, options) or this.createTerminalFromOptions(profileOptions, options) and returns without awaiting either; createExtensionTerminal (line ~521) calls terminal.createExtensionTerminal(...).then(...) without awaiting, and createTerminalFromOptions (line ~1318, remote variant) calls terminal.create(options, ...) without awaiting — both return synchronously before the main-thread instance exists.
- **no related fix on main:** git log on both terminalService.ts and extHostTerminalService.ts shows no recent commit touching this path; the most recent changes are unrelated (e.g. 280a9749, an agentHost E2E storage perf change).
