# Issue #264555 — Agent sessions support for multi-root workspaces

[https://github.com/microsoft/vscode/issues/264555](https://github.com/microsoft/vscode/issues/264555)

## Summary

Keep open for the remaining Agents Window multi-root work. Repository selection and workspace labeling now exist, but current source still limits some multi-root presentation to the primary folder; no verified post-reopen fix referencing this team-authored issue establishes completion.

## Change summary

Make an agent session’s target repositories clear and support multi-root workspaces consistently across agent-session surfaces.

Reconcile the remaining acceptance criteria with the newer multi-root issues without treating their partial implementations as completion of this reopened report.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts`, `src/vs/sessions/services/sessions/common/session.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/agentHostSessionChangesets.ts`
- **Validation:** Plan an acceptance scenario with two repositories containing distinguishable README files: select the intended scope, submit an edit, and confirm the composer, resumed session, and changes presentation identify the actual affected repository or repositories. Include a multi-root session changing both repositories and verify that the agreed presentation does not silently imply primary-folder-only scope.
- **Behavior:**

  > A user with multiple repositories must be able to determine which repository or repositories an agent session will operate in before submitting a task and after reopening the session. Existing background and cloud repository-selection behavior must remain available. For Agents Window sessions spanning multiple roots, the displayed scope and changes must communicate the agreed multi-root behavior without implying that the primary folder is the entire workspace. Acceptance should use distinguishable files in two repositories and cover session creation, edits, and resume.
- **Trace:**

  > The original report concerns an implicit repository choice, while the February maintainer comment explicitly leaves Agents Window multi-root support outstanding: https://github.com/microsoft/vscode/issues/264555#issuecomment-3834342127. Current SessionWorkspacePicker already supports selection, attached folders, and selected-workspace labels, so the trace does not establish that the original missing-picker symptom persists unchanged. The domain contract in src/vs/sessions/SESSIONS.md distinguishes aggregate session scope from effective chat scope. In agentHostSessionChangesets.ts, filterChangesToPrimaryWorkingDirectory still restricts last-turn changes to the first working directory. Related work is documented in https://github.com/microsoft/vscode/issues/311148, https://github.com/microsoft/vscode/issues/321651, and https://github.com/microsoft/vscode/issues/330148; their broader and partially completed scopes need reconciliation before defining this issue’s remaining implementation boundary. Preserve single-root behavior and provider-neutral session contracts.
- **Open decisions:**
  - What observable Agents Window acceptance criteria complete this issue: explicit per-session repository selection and identity, or complete multi-root workspace presentation as well?
  - For a session spanning repositories, should session-level identity present the aggregate workspace while chat-level identity presents the effective repository subset, and how should a primary-folder-only changes view disclose its narrower scope?
