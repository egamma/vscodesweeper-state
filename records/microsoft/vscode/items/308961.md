# Issue #308961 — VSCode MCP Task Compliance - Terrible UX

[https://github.com/microsoft/vscode/issues/308961](https://github.com/microsoft/vscode/issues/308961)

## Summary

Keep open: current source still awaits MCP task completion before returning the tool result, so the central nonblocking task experience remains missing. Existing progress reporting and in-memory reconnection support provide partial coverage, not the requested background lifecycle.

## Change summary

Make long-running MCP tasks visible, cancellable, and nonblocking, with completion delivery and retained task awareness.

## Best solution

Integrate MCP tasks with chat's background-work lifecycle so users can continue chatting while retaining visible task state and receiving completion results. Reconcile the maintainer's backgrounding work with this request, explicitly deciding completion delivery and persistence semantics before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/common/mcpServerRequestHandler.ts`, `src/vs/workbench/contrib/mcp/common/mcpTaskManager.ts`, `src/vs/workbench/contrib/mcp/common/mcpServer.ts`, `src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts`
- **Validation:** Using a controllable Streamable HTTP MCP server with optional task support, return a working task immediately and hold its completion. Verify task identity/status are visible and another chat turn can complete before the task finishes; then verify completion is delivered once, explicit cancellation reaches the server, and reconnection/reload behavior matches the agreed persistence contract. Ordinary non-task tool results and input-required tasks must retain their existing behavior.
- **Behavior:**

  > An MCP tool that returns a working task must not make the conversation unusable until that task finishes. Users should see identifiable task state, be able to continue chatting, and have an explicit cancellation action. Completion must be surfaced without losing the result or duplicating delivery. The plan must define how completion interacts with active turns and what task awareness survives chat reopening or window reload.
- **Trace:**

  > McpToolImplementation.invoke in src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts awaits McpTool.callWithProgress. In mcpServer.ts, _callWithProgress opts into tasks for optional or required task-capable tools and awaits McpServerRequestHandler.callTool; that handler returns McpTask.result rather than exposing a detached task lifecycle. McpTask polls and settles the promise on terminal states, while McpTaskManager retains client tasks only in memory and reattaches handlers on reconnection. Status/progress callbacks already exist, so preserve and account for that partial capability rather than assuming every task is silent. Preserve ordinary tool calls, task input/elicitation flows, and server-side sampling/elicitation tasks; failed-task payload loss is separately tracked at https://github.com/microsoft/vscode/issues/335229. The maintainer's backgrounding lead is recorded at https://github.com/microsoft/vscode/issues/308961#issuecomment-4224836430; no open matching implementation PR was found. The remaining design boundary is how MCP task identity and completion enter chat's background lifecycle, not merely removing an await.
- **Open decisions:**
  - Should task completion only display a result/notification, or also resume the agent automatically, and how should delivery interact with an active user turn?
  - Must task awareness survive a full window reload or process restart in the initial implementation, or only chat reopening and transport reconnection?
