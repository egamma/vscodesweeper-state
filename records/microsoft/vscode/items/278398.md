# Issue #278398 — For local MCP server installation, utilize runtime_hint

[https://github.com/microsoft/vscode/issues/278398](https://github.com/microsoft/vscode/issues/278398)

## Summary

A real gap remains on current main: MCP manifests preserve `runtimeHint`, but local configuration generation still chooses a hardcoded command from the registry type. This team-authored Backlog request should remain open, particularly because a later report was explicitly consolidated into it.

## Change summary

Honor an MCP package's `runtime_hint` when selecting the command used to launch a locally installed server.

## Best solution

Define and implement consistent `runtimeHint` semantics for local MCP packages, using the hinted runtime when supported and retaining a deterministic registry-type fallback when it is absent or unsupported. The design should cover the broader runtime-selection scenario represented by npm versus npx and Docker versus Podman.

## Plan brief

- **Likely files:** `src/vs/platform/mcp/common/mcpManagementService.ts`, `src/vs/platform/mcp/test/common/mcpManagementService.test.ts`
- **Validation:** Add targeted McpManagementService unit cases showing the generated local command for a NODE package with `runtimeHint: 'npm'`, an OCI package with `runtimeHint: 'podman'`, and packages with absent or unsupported hints; existing registry URL and default-runtime cases must remain unchanged.
- **Behavior:**

  > When an MCP registry package supplies a supported runtime hint, installing it locally should generate a configuration that launches through that runtime rather than unconditionally substituting the registry-type default. Private registry arguments and package arguments must remain correctly ordered. Packages without a usable hint must continue to receive a predictable default command.
- **Trace:**

  > Raw MCP gallery data is converted in src/vs/platform/mcp/common/mcpGalleryService.ts, where `runtime_hint` is already preserved as `runtimeHint`; IMcpServerPackage in src/vs/platform/mcp/common/mcpManagement.ts also exposes it. The value stops affecting behavior in AbstractCommonMcpManagementService.getMcpServerConfigurationFromManifest: src/vs/platform/mcp/common/mcpManagementService.ts constructs the local configuration and calls getCommandName, which selects a fixed command solely from RegistryType. Existing tests in src/vs/platform/mcp/test/common/mcpManagementService.test.ts cover default commands and custom registry URLs but contain no runtimeHint case. Preserve remote-server handling, environment/input processing, argument ordering, and current defaults when no acceptable hint is present. https://github.com/microsoft/vscode/issues/291479 establishes that this canonical issue may cover non-NODE runtimes as well, which is where the scope decision begins.
- **Open decisions:**
  - Is `runtimeHint` authoritative whenever present, or may VS Code honor only an explicit allowlist and fall back to the registry-type default for other values?
  - Should this work apply uniformly across all local package registry types, including OCI runtime substitution such as Docker to Podman, or initially cover only the NODE npm-versus-npx scenario?

## Evidence

- **current source gap:** src/vs/platform/mcp/common/mcpGalleryService.ts converts `runtime_hint` into `runtimeHint`, and src/vs/platform/mcp/common/mcpManagement.ts retains it on IMcpServerPackage, but AbstractCommonMcpManagementService.getMcpServerConfigurationFromManifest in src/vs/platform/mcp/common/mcpManagementService.ts never reads it; getCommandName still hardcodes npx, docker, uvx, or dnx from RegistryType.
- **existing capability is partial:** Current main supports `registryBaseUrl` and emits `--registry` for NODE packages, but the generated command remains `npx`; this does not satisfy the requested runtime selection or the broader Podman case.
- **canonical ownership:** https://github.com/microsoft/vscode/issues/291479 requested the same observable behavior for `runtimeHint` with Podman and was closed by a maintainer as a duplicate of this issue, confirming that this issue owns the broader runtime-selection work.
- **maintainer direction:** A maintainer stated at https://github.com/microsoft/vscode/issues/282860#issuecomment-3659704691 that custom registries and runtime hints were not yet supported and linked this issue as the planned runtime-hint work.
- **iteration result:** https://github.com/microsoft/vscode/issues/286040 marked work linked to this issue complete under the narrower description 'Support MCP registry url property'; current source confirms registry URL support landed while runtime-hint command selection remains absent.
