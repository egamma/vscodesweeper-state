# Issue #247136 — UX: Copilot pickers need alignment

[https://github.com/microsoft/vscode/issues/247136](https://github.com/microsoft/vscode/issues/247136)

## Summary

The inconsistency remains structurally present on current main: the model picker uses a bespoke trigger and popup implementation while adjacent chat pickers use the shared picker action item. The original proposal to replace it outright with a simple menu needs revisiting because the model picker now exposes substantially richer functionality.

## Change summary

Align the chat model picker with adjacent chat-input pickers instead of presenting one visibly and behaviorally distinct custom control.

## Best solution

Preserve required model-specific capabilities while converging the trigger, active state, pointer behavior, keyboard navigation, and ordinary menu actions on the shared chat-picker interaction contract. The broader alignment work should remain here, with the concrete behaviors from https://github.com/microsoft/vscode/issues/247137 treated as acceptance criteria.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input/chatInputPickerActionItem.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerActionItem.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerWidget.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerTabbedWidget.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/input/modelPicker/modelPickerItems.test.ts`
- **Validation:** Exercise the mode and model pickers in the chat input and verify matching mouse-open timing, active trigger state, pointer-leave selection behavior, Escape/focus restoration, and keyboard navigation; add browser widget coverage for whichever shared interaction contract the plan selects.
- **Behavior:**

  > The model picker and adjacent chat-input pickers should read as members of one control family and follow the same opening, active-state, pointer, focus, and keyboard conventions. Manage Models should behave as an ordinary menu action rather than a special link. Model-specific capabilities that remain part of the chosen design must continue to work. Acceptance includes the concrete interaction cases documented in https://github.com/microsoft/vscode/issues/247137.
- **Trace:**

  > ModePickerActionItem in src/vs/workbench/contrib/chat/browser/widget/input/modePickerActionItem.ts inherits the shared ChatInputPickerActionViewItem and ActionWidgetDropdownActionViewItem path. ModelPickerActionItem instead wraps ModelPickerWidget, which creates separate anchor elements and owns popup state, focus restoration, and two presentation paths: an IActionWidgetService flat list and TabbedModelPicker. The issue's original simplification argument predates provider tabs, search, pinning, availability states, model cards, and configuration details now implemented in modelPickerWidget.ts and modelPickerTabbedWidget.ts. The uncertainty begins at the product boundary: whether those capabilities justify a specialized model surface or should be relocated so model selection can use the common dropdown. Do not remove model availability, configuration, accessibility, or billing information merely to make the controls visually identical.
- **Open decisions:**
  - Should the provider-tabbed model and details experience remain a specialized popup that adopts the shared picker interaction contract, or should model selection become the common dropdown with those richer capabilities moved elsewhere?
