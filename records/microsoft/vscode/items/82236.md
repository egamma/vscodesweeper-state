# Issue #82236 — Completion should be able to retrigger completions when accepted

[https://github.com/microsoft/vscode/issues/82236](https://github.com/microsoft/vscode/issues/82236)

## Summary

Keep open: completion commands already support retriggering, but current source still lacks the requested dedicated API and user setting. The issue is correctly routed, and no verified older canonical owns this remaining work.

## Change summary

Make retriggering suggestions after accepting a completion an explicit editor/API concept with a user-controlled enable/disable setting.

## Best solution

Define a first-class completion retrigger contract and corresponding editor preference, preserving unrelated completion commands. API owners should settle compatibility with existing command-based retriggering before implementation.

- **Behavior:**

  > Completion providers can explicitly request that accepting an item opens the next set of suggestions, rather than representing this solely as an arbitrary post-accept command. Users can enable or disable this behavior through an editor preference. Acceptance checks must demonstrate chaining when enabled, suppression when disabled, and unchanged insertion and unrelated post-accept command behavior. Compatibility expectations for existing command-based providers must be settled before implementation.
- **Trace:**

  > CompletionItem in src/vscode-dts/vscode.d.ts and src/vs/editor/common/languages.ts currently provides post-accept commands but no dedicated retrigger field. In src/vs/editor/contrib/suggest/browser/suggestController.ts:459–475, the editor special-cases 'editor.action.triggerSuggest' and directly retriggers the model without consulting a preference. The suggest options in src/vs/editor/common/config/editorOptions.ts do not control this path; typed trigger-character settings are a separate mechanism. https://github.com/microsoft/vscode/issues/74054#issuecomment-540500494 endorses an explicit proposal flag, and https://github.com/intersystems-community/sqltools-intersystems-driver/issues/38 supplies a schema-to-table chaining use case. The boundary is accepted-item retriggering, not general quick suggestions, commit-character acceptance, or signature-help behavior. The trace establishes the editor-side gap; extension-host transport and protocol compatibility still need investigation in the planning session.
- **Open decisions:**
  - Should the new preference also suppress existing CompletionItem.command requests for editor.action.triggerSuggest, or apply only to the new explicit retrigger contract?
  - Should accepted-item retriggering remain enabled by default to preserve existing HTML/CSS chaining behavior?

## Evidence
