# Issue #321126 — Session List hover overlay mode

[https://github.com/microsoft/vscode/issues/321126](https://github.com/microsoft/vscode/issues/321126)

## Summary

Keep open: this team-authored polish request has explicit maintainer support, and current main still only provides a persistent grid-level Sessions sidebar toggle. Observable design decisions about symmetric sidebars, the Changes panel, and accessible non-pointer interaction remain open.

## Change summary

Preview the collapsed Sessions list as a temporary overlay on title-bar-toggle hover, then dock it into the layout when the toggle is clicked.

## Best solution

Provide a transient, non-layout-shifting preview of the collapsed Sessions list while preserving the existing click-to-dock behavior and saved layout state. Settle whether the interaction also applies to the right side pane or Changes panel, and provide equivalent keyboard/focus behavior with Escape dismissal.

## Plan brief

- **Likely files:** `src/vs/sessions/browser/layoutActions.ts`, `src/vs/sessions/browser/parts/titlebarPart.ts`, `src/vs/sessions/browser/workbench.ts`, `src/vs/sessions/browser/media/workbench.css`, `src/vs/sessions/test/browser/workbench.test.ts`
- **Validation:** Extend src/vs/sessions/test/browser/workbench.test.ts to prove preview entry/exit leaves persistent sidebar visibility and grid widths unchanged, while activation performs the existing docked transition; validate pointer leave, keyboard focus, Escape dismissal, focus restoration, and high-contrast presentation in an Agents Window UI scenario.
- **Behavior:**

  > When the Sessions list is collapsed, intentional interaction with its title-bar control temporarily reveals the list above the existing workspace without shifting or resizing the chat, editor, or details surfaces. Leaving or dismissing the preview restores the previous composition, while activating the control docks the list using the existing persistent layout behavior. The interaction must be available without a pointer, dismiss with Escape, preserve logical focus, and remain distinguishable in high-contrast themes. Existing Ctrl/Cmd+B toggle behavior and persisted sidebar state must remain unchanged.
- **Trace:**

  > The title-bar action is registered as `ToggleSidebarVisibilityAction` in src/vs/sessions/browser/layoutActions.ts and rendered from `Menus.TitleBarLeftLayout` by `TitlebarPart` in src/vs/sessions/browser/parts/titlebarPart.ts. Activation currently flows directly to `Workbench.setSideBarHidden()` in src/vs/sessions/browser/workbench.ts, which mutates `partVisibility.sidebar`, changes grid visibility, applies width redistribution, persists state, and relayouts. Existing width and visibility invariants are covered in src/vs/sessions/test/browser/workbench.test.ts, and the docked behavior is specified in src/vs/sessions/DESKTOP.md. The boundary is a temporary presentation state: it must not mutate persisted visibility, grid geometry, active pane-composite ownership, or the existing click/keybinding transition. The uncertainty starts with the scope questions raised in https://github.com/microsoft/vscode/issues/321126 and with the equivalent keyboard/focus contract required for a hover-originated interaction.
- **Open decisions:**
  - Is transient preview limited to the left Sessions list, or should the right side pane receive the same interaction for visual and behavioral symmetry?
  - Should the Changes/details panel participate in this preview model, or remain exclusively docked?
  - Which non-pointer gesture opens the preview, and does focus moving into the preview keep it open until Escape or focus leaves the complete control-and-overlay region?

## Evidence

- **protected maintainer item:** https://github.com/microsoft/vscode/issues/321126 was authored by a repository member and already carries `ux` and `polish`; the MEMBER comment endorses the direction and asks design questions rather than declining it.
- **current toggle path:** src/vs/sessions/browser/layoutActions.ts registers `workbench.action.agentToggleSidebarVisibility`; its `run()` only calls `IWorkbenchLayoutService.setPartHidden()` on `Parts.SIDEBAR_PART`, so there is no transient preview state.
- **layout-shifting implementation:** src/vs/sessions/browser/workbench.ts `setSideBarHidden()` changes persistent `partVisibility.sidebar`, calls `workbenchGrid.setViewVisible()`, applies sidebar resizing, saves visibility, and relayouts the grid. That is the docked behavior the requested overlay must leave unchanged until activation.
- **existing layout contract:** src/vs/sessions/DESKTOP.md documents Toggle Sessions List as a persistent collapse/open operation that reallocates width, while src/vs/sessions/test/browser/workbench.test.ts verifies sidebar visibility and width restoration. No temporary desktop overlay mode is documented or tested.
- **canonical search:** The older https://github.com/microsoft/vscode/issues/295788 is a broad UI-refresh tracker and does not report the same hover-preview symptom or explicitly own this work; under the re-review duplicate bar it is related context, not a canonical duplicate.
- **accessibility boundary:** The proposal is currently hover-driven. VS Code accessibility requirements prohibit mouse-only interactions, so keyboard focus, dismissal, and focus restoration are part of the user-observable design rather than optional implementation detail.
