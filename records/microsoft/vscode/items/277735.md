# Issue #277735 — Agent: Prompts should not persist tool/model selection after chat response

[https://github.com/microsoft/vscode/issues/277735](https://github.com/microsoft/vscode/issues/277735)

## Summary

The one-shot semantics remain unimplemented on current main: prompt-file tool and model metadata still changes the widget's session selection, with no restoration after the request. This team-authored, On Deck feature request should remain open for a scoped design and implementation.

## Change summary

Make tool and model selections declared by a prompt file apply only to that prompt's chat turn instead of persisting into later interactions.

## Best solution

Treat prompt-file tool and model metadata as request-scoped overrides while preserving the user's existing session selections for subsequent turns; custom-agent selections should retain their existing multi-turn behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/chatSelectedTools.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/chatWidget.test.ts`
- **Validation:** Add a chat widget browser test that starts with user-selected tools and a model, submits a prompt slash command with different frontmatter values, verifies the sent request uses the prompt values, and verifies the next ordinary turn uses the original selections; run it with `scripts/test.sh --grep "prompt metadata"`.
- **Behavior:**

  > Tool and model values declared by a prompt file affect only the chat request created from that prompt. After that turn, a subsequent ordinary message uses the tool and model selections that were active before the prompt ran. Custom-agent selection remains multi-turn and is not changed by this work. Acceptance should cover prompt success as well as cancellation or rejection so temporary metadata cannot leak into later turns.
- **Trace:**

  > Prompt slash commands are resolved by `ChatWidget._applyPromptFileIfSet` in src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts. `_applyPromptMetadata` then mutates the widget state: tools are written as session state through `ChatSelectedTools.set(..., true)`, and the model is changed through `ChatInputPart.requestModelByQualifiedName`. `ChatWidget._acceptInput` reads those values into `sendRequest`, but its completion path does not restore the prior state, conclusively explaining the reported persistence on current main. Related report https://github.com/microsoft/vscode/issues/290363 confirms the same user-observable symptom and points back to this issue. Keep custom-agent persistence and manually selected session tools/models outside the prompt path unchanged; the uncertainty is how the transient override should appear while a response is active and how queued turns observe it.
- **Open decisions:**
  - While a prompt-generated response is active, should the model and tool pickers visibly show the prompt's temporary overrides, or continue showing the user's persistent selections?
  - If another message is queued while the prompt-generated response is active, should that queued message inherit the prompt overrides or use the user's persistent selections?

## Evidence

- **current source:** In src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts, `_applyPromptMetadata` applies prompt tools through `selectedToolsModel.set(enablementMap, true)` and applies the model through `requestModelByQualifiedName`; the subsequent response-completion path does not restore either prior selection.
- **persistence mechanism:** src/vs/workbench/contrib/chat/browser/widget/input/chatSelectedTools.ts stores `sessionOnly` changes in `_sessionStates`, so the prompt's tool selection remains the active session selection after its request.
