# Issue #337602 — Copilot Chat (1.139.0 / 0.67.0): Prompt prefix cache busted on turns 2+ for third-party prefix-caching models (Grok, DeepSeek)

[https://github.com/microsoft/vscode/issues/337602](https://github.com/microsoft/vscode/issues/337602)

## Summary

Real regression with confirmed comment evidence for at least one sub-case (GPT-5.6 via LiteLLM), but the original reporter's Grok/DeepSeek claim doesn't match that codepath in current source, so the root cause for the titled scenario is still unconfirmed — this needs maintainer/agent investigation, not a close.

## Change summary

Multi-turn Copilot Chat requests to third-party prefix-caching models (Grok, DeepSeek via BYOK/LiteLLM) stopped hitting upstream prompt caches on turn 2+ starting in 1.139.0/0.67.0, inflating token cost.

## Best solution

Investigate whether the newly-default-enabled `github.copilot.chat.responsesApi.promptCacheBreakpoint.enabled` (extensions/copilot/src/platform/configuration/common/configurationService.ts:1093) and its explicit `prompt_cache_breakpoint` mode (responsesApi.ts) are leaking into or interacting badly with BYOK/third-party proxy paths, and separately trace why chat-completions-path Grok/DeepSeek requests (not gated by that setting per `modelSupportCacheBreakPoints`, which is scoped to gpt56/gpt6 only) also regress — likely two distinct bugs sharing one symptom.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/endpoint/node/responsesApi.ts`, `extensions/copilot/src/platform/configuration/common/configurationService.ts`, `extensions/copilot/src/platform/endpoint/common/chatModelCapabilities.ts`, `extensions/copilot/src/extension/intents/node/cacheBreakpoints.ts`, `extensions/copilot/src/extension/intents/node/agentIntent.ts`
- **Validation:** A test that renders two consecutive turns for (a) a gpt-5.6/6-family endpoint behind a BYOK/custom base URL and (b) a non-gpt56/6 BYOK chat-completions model (simulating Grok/DeepSeek), asserting the serialized request body for turn 2 is byte-stable in its shared prefix relative to turn 1 (no new/moved cache-breakpoint markers or metadata that a strict-prefix cache would treat as a diff).
- **Behavior:**

  > For any BYOK/third-party model that relies on exact-prefix KV caching (no explicit cache-control protocol), the portion of the request body corresponding to turn 1's content must be byte-identical when it reappears as history in turn 2 and later turns, so upstream cache hit rates stay high across a session. Explicit cache-breakpoint mechanisms (Responses API `prompt_cache_breakpoint`, or the generic CacheBreakpoint content parts) should only be applied where the model/endpoint is known to understand and benefit from them, never in a way that perturbs the byte-stable prefix for providers that don't.
- **Trace:**

  > Two candidate code paths were found on main: (1) responsesApi.ts:126-146 conditionally sets `prompt_cache_breakpoint`/`prompt_cache_options` when `ConfigKey.ResponsesApiPromptCacheBreakpointEnabled` (default true, configurationService.ts:1093) and `modelSupportCacheBreakPoints()` (chatModelCapabilities.ts:336, scoped to gpt56/gpt6/hidden-model-I) both hold — confirmed by a commenter to break caching for a gpt-5.6 model proxied through LiteLLM. (2) agentIntent.ts:1049-1051 calls `addCacheBreakpoints(result.messages, this.endpoint.apiType)` for any apiType other than 'messages' (Anthropic), inserting CacheBreakpoint content parts (cacheBreakpoints.ts) that get turned into a `copilot_cache_control` field per message (openai.ts:213-215) for chat-completions apiType — this path is NOT gated by `modelSupportCacheBreakPoints` and would apply to Grok/DeepSeek chat-completions requests too, but whether it perturbs a byte-stable prefix (vs. just adding an inert metadata field) was not confirmed from source alone. Do not change unrelated Anthropic ('messages' apiType) cache-breakpoint behavior, which is intentional and unaffected. Related: https://github.com/microsoft/vscode/pull/336967 and commit 70365f14fa615d25b361e9f4a27a249fac347a80 (cited in comments, not independently verifiable in this shallow checkout).
- **Open decisions:**
  - Should `promptCacheBreakpoint.enabled` remain default-true for all gpt56/gpt6-family requests, or be scoped off for custom/BYOK base URLs where the proxy may not implement the Responses API cache-breakpoint contract faithfully?
  - Does the generic chat-completions `addCacheBreakpoints`/`copilot_cache_control` insertion (independent of the Responses API setting) also destabilize the request prefix for non-gpt56/6 BYOK models like Grok/DeepSeek, and if so should it be skipped for non-first-party endpoints?

## Evidence

- **current default:** extensions/copilot/src/platform/configuration/common/configurationService.ts:1093 defines `chat.responsesApi.promptCacheBreakpoint.enabled` defaulting to `true`, only applied when `modelSupportCacheBreakPoints()` (chatModelCapabilities.ts:336) returns true for GPT-5.6/GPT-6/hidden-model-I families — not Grok/DeepSeek.
- **confirmed workaround (sub-case):** Comment by scobely confirms setting `promptCacheBreakpoint.enabled: false` restores cache hits for `gpt-5.6-sol` accessed via LiteLLM proxy, matching the default-true code path found in responsesApi.ts.
- **root cause mismatch for primary report:** Original reporter's models (xai/grok-4.7, xai/grok-4.6) are not gpt56/gpt6 family, so the Responses API explicit cache breakpoint path the reporter blames doesn't gate their requests in current source — a separate mechanism (e.g. the generic `addCacheBreakpoints` in extension/intents/node/cacheBreakpoints.ts, applied for any non-'messages' apiType via agentIntent.ts:1049-1051) is a more plausible candidate but not yet traced to a concrete byte-level diff.
