# Issue #149175 — Problems without column information are always shown as column 1,1

[https://github.com/microsoft/vscode/issues/149175](https://github.com/microsoft/vscode/issues/149175)

## Summary

Whole-line ranges are already supported, but the Problems view still displays column 1 when the task output supplied no column. Keep this accepted On Deck discussion open: the remaining presentation requirement is not covered, and the thread does not settle how to distinguish an unspecified column from an explicit column 1.

## Change summary

Represent line-only task diagnostics without displaying an apparently precise column that the tool never reported.

## Best solution

Agree on a consistent presentation for line-only diagnostics across Problems tree, table, and accessibility text, while preserving valid numeric marker ranges and explicit-column diagnostics. Whole-line highlighting alone does not satisfy the remaining request.

- **Validation:** Run a task with a problem matcher capturing file, line, and message but no column; inspect its diagnostic in Problems tree and table views and its accessibility label. Verify the agreed line-only presentation and whole-line highlighting, then compare with an otherwise identical matcher supplying an explicit column 1 and another supplying a later column. Add targeted matcher and marker-rendering tests for the chosen contract.
- **Behavior:**

  > A task diagnostic whose output supplies a line but no column should not imply that the tool identified column 1. Current whole-line range construction already addresses highlighting, but the Problems views continue to show a column. Acceptance must cover tree, table, and accessibility presentation, and preserve precise locations when a tool explicitly reports a column.
- **Trace:**

  > getLocation and parseLocationInfo in src/vs/workbench/contrib/tasks/common/problemMatcher.ts converge on createLocation, which maps a missing column to a range from column 1 through 2 ** 31 - 1. MarkerService._toMarker in src/vs/platform/markers/common/markerService.ts normalizes absent or nonpositive start columns to 1, so column zero is not currently a retained sentinel. Problems tree and table renderers both pass the numeric start column directly to MARKERS_PANEL_AT_LINE_COL_NUMBER, and messages.ts includes it in ARIA text. The model objection is recorded at https://github.com/microsoft/vscode/issues/149175#issuecomment-1148452951; the task-side willingness to try a large range is at https://github.com/microsoft/vscode/issues/149175#issuecomment-1148545305. Preserve numeric range validity, explicit-column behavior, and existing whole-line ranges; a large end column alone must not be assumed to prove that the producer omitted the start column. The unresolved boundary is how unspecified-column provenance can be represented and presented without contradicting that model contract.
- **Open decisions:**
  - Should line-only diagnostics display only a line number or explicitly identify the column as unspecified, consistently across tree, table, and accessibility text?
  - Should distinguishing an unspecified column from an explicit column 1 become a shared marker contract available to all producers, or remain a task-specific capability while preserving the existing numeric range contract?
