## Evidence

- **Complete reproduction and platform boundary:** https://github.com/microsoft/vscode/issues/302684#issuecomment-4106429144 describes two extensions, expanded-versus-collapsed Explorer startup, persistent missing colors, and Windows user setup specifically. The reporter explicitly says OSS and Extension Development Host do not reproduce; these are sufficient retest steps, not missing basic information.
- **Current core cache behavior:** src/vs/workbench/services/decorations/browser/decorationsService.ts uses a URI-identity-aware TernarySearchTree. getDecoration fetches only when a provider entry is undefined; _keepItem caches an absent result as null. Provider registration announces a global change, and provider events either remove cached entries or fetch again. This explains how an initial empty result can persist, but does not prove that core incorrectly discards a valid result.
- **Provider bridge:** src/vs/workbench/api/browser/mainThreadDecorations.ts batches URI requests in DecorationRequestsQueue. src/vs/workbench/api/common/extHostDecorations.ts revives each URI and calls provideFileDecoration. No source trace established the reported launch-specific failure.
- **Competing extension-side explanation:** https://github.com/jacob-j/vscode-folder-path-color/blob/HEAD/src/extension.ts matches non-glob paths with normalizedUriPath.includes(fullPath), a case-sensitive comparison despite the Windows scenario. That is a plausible URI-spelling sensitivity, not proof that this installed extension caused the report.
