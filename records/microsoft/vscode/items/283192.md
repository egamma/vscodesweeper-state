# Issue #283192 — Can the chat window context support reading PDF and OFFICE format files?

[https://github.com/microsoft/vscode/issues/283192](https://github.com/microsoft/vscode/issues/283192)

## Summary

A real capability gap remains: current chat attachment paths treat ordinary file references as text and reject binary documents, while PDF and Office requirements are common development context. The broader related issue is newer than this re-reviewed item, so it cannot be its duplicate canonical; this older request should remain open.

## Change summary

Allow Copilot Chat to attach and read PDF and Microsoft Office documents as context.

## Best solution

Keep this issue as the older canonical for document attachments and define a format-aware attachment contract spanning the chat UI and Copilot request paths, with explicit behavior for unsupported models, size limits, and content extraction.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentResolveService.ts`, `src/vs/workbench/api/common/extHostTypeConverters.ts`, `src/vscode-dts/vscode.proposed.chatReferenceBinaryData.d.ts`, `extensions/copilot/src/extension/conversation/vscode-node/remoteAgents.ts`, `extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotcliPromptResolver.ts`
- **Validation:** Add targeted attachment tests using representative PDF and DOCX fixtures: attaching each document must produce usable document context without the binary-file rejection, while an agent or model that cannot consume the format must expose the agreed unsupported-format behavior.
- **Behavior:**

  > Users can attach supported PDF and Office documents to chat and ask questions grounded in their contents. The attachment UI must accurately communicate support before submission, and the selected chat implementation must receive usable document context rather than rejecting the file as binary. Existing text and image attachments must remain unchanged. Oversized, encrypted, malformed, or unsupported documents must produce the explicitly chosen user-facing behavior rather than being silently omitted.
- **Trace:**

  > The workbench currently creates URI-backed file entries in src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentResolveService.ts; src/vs/workbench/api/common/extHostTypeConverters.ts emits binary reference data only for images. The traditional Copilot path in extensions/copilot/src/extension/conversation/vscode-node/remoteAgents.ts opens URI references as text documents and catches binary-file failures, while the Copilot CLI path in extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotcliPromptResolver.ts accepts binary reference data only for image MIME types. PDF serialization exists lower down in extensions/copilot/src/extension/conversation/vscode-node/languageModelAccess.ts, but no UI attachment path reaches it. Preserve text/image behavior, content-exclusion checks, and model capability handling. The broader but newer https://github.com/microsoft/vscode/issues/265184 records maintainer support for allowing these attachments; this older issue should remain the canonical request.
- **Open decisions:**
  - Which document formats are part of the supported product contract initially: PDF only, PDF plus DOCX, or the broader PDF/DOCX/XLSX family?
  - Should supported documents be converted locally into text-oriented context, passed to capable providers as native document data, or use a defined hybrid policy?
  - When the selected model or agent cannot consume a document format, should VS Code block attachment, use local extraction, or accept it and show a submission-time warning?

## Evidence

- **current source gap:** src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentResolveService.ts resolves non-image files as URI-backed `file` entries, while src/vs/workbench/api/common/extHostTypeConverters.ts converts only image entries into `ChatReferenceBinaryData`; there is no PDF or Office binary attachment conversion.
- **binary rejection:** extensions/copilot/src/extension/conversation/vscode-node/remoteAgents.ts opens URI references as text documents and returns "Sorry, binary files are not currently supported" when that fails, directly matching the requested gap.
- **agent-host limitation:** extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotcliPromptResolver.ts handles `ChatReferenceBinaryData` only when it is an image and drops other binary data from constructed attachments, so the newer agent path does not provide general document support either.
- **partial infrastructure:** extensions/copilot/src/extension/conversation/vscode-node/languageModelAccess.ts recognizes `application/pdf` `LanguageModelDataPart` values as document content, but the chat attachment pipeline never creates such a value for an attached PDF; this capability therefore does not satisfy the request.
- **related request:** https://github.com/microsoft/vscode/issues/265184 is open and requests the broader set of Excel, CSV, PDF, and DOCX attachments. A maintainer stated that agents should be able to read these files and that attachments should now allow them, but that issue was created after this one and cannot be the canonical duplicate for this re-reviewed item.
- **confirmed behavior:** A maintainer confirmed at https://github.com/microsoft/vscode/issues/276679#issuecomment-3631033647 that PDF files are not currently valid chat attachments.
- **demand:** The issue has four community upvotes, and a separate commenter specifically needs PDF and DOCX business requirements as Copilot context.
