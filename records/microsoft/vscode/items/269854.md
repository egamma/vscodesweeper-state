# Issue #269854 — NES doesn't render when jumping to next problem with F8

[https://github.com/microsoft/vscode/issues/269854](https://github.com/microsoft/vscode/issues/269854)

## Summary

Keep open: current main intentionally suppresses NES whenever a peek widget is visible, and the maintainer discussion confirms that supporting F8 problem navigation still needs a UX decision. This team-authored Backlog request has neither been implemented nor superseded by an older canonical issue.

## Change summary

Allow users navigating diagnostics with F8 to see and act on relevant next edit suggestions without conflicting with the problem peek view.

## Best solution

Design a non-overlapping presentation that preserves awareness of an available NES while the problem peek is open, then gives the user a predictable way to reveal or jump to the full edit.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/inlineCompletions/browser/model/inlineCompletionsModel.ts`, `src/vs/editor/contrib/inlineCompletions/browser/view/inlineEdits/inlineEditsView.ts`, `src/vs/editor/contrib/peekView/browser/peekView.ts`, `src/vs/editor/contrib/inlineCompletions/test/browser/inlineEdits.test.ts`
- **Validation:** Add an editor-level test covering an available inline edit while `openedPeekWidgets` is nonzero, then manually use F8 with a diagnostic and available NES to verify the selected presentation does not overlap the problem peek and that its advertised keyboard action reveals or navigates to the edit.
- **Behavior:**

  > When F8 opens the next problem in a peek view and an NES is available, the user should retain a clear, non-overlapping indication that the edit exists. The chosen keyboard action must predictably reveal or navigate to the edit without leaving both full interfaces visually stacked. Closing the problem peek must continue to restore the normal NES presentation, and ordinary peek views without an available edit must remain unchanged.
- **Trace:**

  > PeekViewWidget in src/vs/editor/contrib/peekView/browser/peekView.ts increments `ObservableCodeEditor.openedPeekWidgets`. InlineCompletionsModel in src/vs/editor/contrib/inlineCompletions/browser/model/inlineCompletionsModel.ts reads that count and drops the entire inline-edit state while it is nonzero; this behavior originated in https://github.com/microsoft/vscode/commit/8f3854f3fb199f0714c4738fc0f58674d598dc77. Consequently InlineEditsView never reaches its collapsed or long-distance-hint rendering paths during the problem peek. Preserve the protection against overlapping the full inline-edit UI with peek content and avoid changing ghost-text behavior, unrelated peek widgets, or normal F8 diagnostic navigation. The uncertainty begins at the presentation contract: the thread has not selected whether NES remains represented beside the peek or whether invoking NES first dismisses or transforms the peek.
- **Open decisions:**
  - While the problem peek remains visible, should an available NES appear as a collapsed/long-distance indicator, or should the peek itself use a presentation that leaves room for the full suggestion?
  - When the user invokes the NES action from that state, should VS Code close the problem peek before revealing the edit, or keep a reduced problem presentation visible?

## Evidence

- **current source:** src/vs/editor/contrib/inlineCompletions/browser/model/inlineCompletionsModel.ts derives `_hasVisiblePeekWidgets` and returns `undefined` for an inline edit whenever `openedPeekWidgets > 0`, so current main still suppresses NES during the F8 problem peek.
- **intentional suppression:** https://github.com/microsoft/vscode/commit/8f3854f3fb199f0714c4738fc0f58674d598dc77 introduced the editor-wide peek-widget counter and deliberately hid inline edits while any peek widget is visible.
- **available presentation primitives:** src/vs/editor/contrib/inlineCompletions/browser/view/inlineEdits/inlineEditsView.ts already supports collapsed and long-distance-hint presentations, but suppression in InlineCompletionsModel prevents those states from being produced while the problem peek is open.
- **maintainer decision remains open:** The issue discussion rejects simultaneous full rendering as visually broken and considers alternatives including a collapsed NES, closing the peek on Tab, a long-distance edit indicator, or changing the peek presentation; no option has been selected.
- **canonical search:** Searches for open NES, peek-widget, view-zone, and F8 interaction issues found no older issue reporting the same observable symptom; the supplied candidate canonicals concern unrelated editor navigation and rendering behavior.
