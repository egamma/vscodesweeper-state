# Issue #269854 — NES doesn't render when jumping to next problem with F8

[https://github.com/microsoft/vscode/issues/269854](https://github.com/microsoft/vscode/issues/269854)

## Summary

Keep open: current source still suppresses next edit suggestions while the problem peek widget exists, and existing presentation settings do not bypass that suppression. Maintainers have accepted the interaction gap but have not settled how suggestions and the peek should coexist.

## Change summary

Make next edit suggestions available during F8 problem navigation without overlapping the problem peek UI.

## Best solution

Provide a non-overlapping NES presentation during problem navigation, with a defined transition from the diagnostic peek to the suggested edit. Choose the observable interaction with the editor/NES owners before implementing it; removing the suppression alone would recreate the overlap documented in the discussion.

- **Behavior:**

  > F8 problem navigation currently makes an available next edit suggestion disappear until the diagnostic peek is closed. The goal is to retain useful access to that suggestion without overlapping or obscuring the diagnostic UI. Acceptance must cover suggestion visibility, activation, keyboard focus, and restoration of ordinary rendering when the peek closes. The exact presentation and transition remain a maintainer decision.
- **Trace:**

  > F8 invokes editor.action.marker.nextInFiles in src/vs/editor/contrib/gotoError/browser/gotoError.ts and displays MarkerNavigationWidget, a PeekViewWidget. PeekViewWidget increments ObservableCodeEditor.openedPeekWidgets during construction and decrements it during disposal. InlineCompletionsModel.state in src/vs/editor/contrib/inlineCompletions/browser/model/inlineCompletionsModel.ts returns undefined for inline edits whenever that count is positive, before the downstream view can select collapsed or long-distance presentation. Existing presentation settings therefore cannot solve this interaction. The discussion at https://github.com/microsoft/vscode/issues/269854 explicitly warns that unrestricted simultaneous rendering overlaps and proposes several alternatives without choosing one. Preserve ordinary NES behavior and do not assume that every other peek widget should receive the same new interaction.
- **Open decisions:**
  - While the problem peek is open, should NES appear as a collapsed indicator, a long-distance-style widget, or a full suggestion alongside a redesigned diagnostic peek?
  - When the user activates the suggestion, should the problem peek close, remain visible, or yield temporarily, and where should keyboard focus move?
  - Should the new coexistence behavior apply only to problem navigation or also to other editor peek widgets?
