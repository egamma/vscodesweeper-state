# Issue #323492 — Extreme lag when VoiceOver is active

[https://github.com/microsoft/vscode/issues/323492](https://github.com/microsoft/vscode/issues/323492)

## Summary

This is a well-isolated accessibility performance regression that remains present on main. The NativeEditContext screen-reader path repeatedly materializes up to 500 untrimmed lines during cursor rendering.

## Change summary

VoiceOver causes multi-second editor lag and high CPU when navigating moderately large files, especially with folding.

## Best solution

Optimize the NativeEditContext screen-reader content path under `src/vs/editor/browser/controller/editContext/native/`, preserving VoiceOver navigation while avoiding full-page DOM replacement on every cursor render. The documented `editor.editContext: false` workaround can remain available until that fix lands.

## Evidence

- **confirmed regression:** The reporter bisected the regression to VS Code 1.123: https://github.com/microsoft/vscode/issues/323492#issuecomment-4843758376. Version 1.122 is unaffected, while cursor movement in a 2,000-line file takes 2–4 seconds and folding raises this to roughly 10 seconds.
- **maintainer diagnosis:** https://github.com/microsoft/vscode/issues/323492#issuecomment-4906152468 identifies the EditContext rollout as the regression boundary and provides `editor.editContext: false` and a smaller `editor.accessibilityPageSize` as diagnostic workarounds.
- **current source:** `src/vs/editor/browser/controller/editContext/native/screenReaderContentSimple.ts` still passes `trimLongText = false` when accessibility support is enabled, while `src/vs/editor/common/config/editorOptions.ts` defaults `accessibilityPageSize` to 500.
- **hot path:** `src/vs/editor/browser/controller/editContext/native/screenReaderSupport.ts` calls `writeScreenReaderContent()` from every `prepareRender`, and `SimpleScreenReaderContent.updateScreenReaderContent()` recomputes and replaces the hidden div text for cursor movement.
