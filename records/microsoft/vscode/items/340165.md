# Issue #340165 — MCP Apps: Agent Host drops structuredContent from tool-result notifications

[https://github.com/microsoft/vscode/issues/340165](https://github.com/microsoft/vscode/issues/340165)

## Summary

Confirmed on current main: the Copilot Agent Host's internal tool-call state shape has no field for `structuredContent`, so it's dropped on the way from the SDK result to the reconstructed `ui/notifications/tool-result` MCP payload sent to the widget — exactly as the reporter traced. No fix has landed yet.

## Change summary

MCP Apps widgets lose `structuredContent` in tool-result notifications when running under the Copilot Agent Host (but not under Local MCP), breaking widgets that depend on it to initialize.

## Best solution

Thread `structuredContent` through the agent-host's internal tool-call representation (sessionState.ts's `ToolResultContent`/`ToolCallCompletedState`), populate it in both the live completion path and the history-replay mapping in copilotAgentSession.ts/mapSessionEvents.ts, and include it when `toMcpCallToolResult()` reconstructs the MCP result for the widget in stateToProgressAdapter.ts.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/common/state/sessionState.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/platform/agentHost/node/copilot/mapSessionEvents.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/stateToProgressAdapter.ts`
- **Validation:** A mapSessionEvents/copilotAgentSession test asserting a tool-complete SDK event carrying structuredContent produces a ToolCallCompletedState that preserves it, plus a test on toMcpCallToolResult (or its caller) asserting the reconstructed CallToolResult includes the original structuredContent object.
- **Behavior:**

  > When an MCP tool invoked through the Copilot Agent Host returns both `content` and `structuredContent`, the widget's `ui/notifications/tool-result` notification should include `params.structuredContent` matching what the server returned (including null-valued properties), matching the behavior already present on the Local MCP path. Acceptance: a widget that validates its opening payload against structuredContent initializes successfully under an Agent Host session, not just Local chat.
- **Trace:**

  > ToolResultContent/ToolCallCompletedState in src/vs/platform/agentHost/common/state/sessionState.ts carries no structuredContent field. copilotAgentSession.ts's handleToolComplete (around line 6920) and mapSessionEvents.ts's history replay (lines 1140-1163) only extract `e.data.result?.content`/`contents` into the abstracted content array — structuredContent is never read off the SDK result at all. stateToProgressAdapter.ts's toMcpCallToolResult() (line 1919) then reconstructs a synthetic MCP.CallToolResult from that abstracted content, so even a perfect passthrough there couldn't recover structuredContent since it was lost upstream. Do not change the Local MCP path (mcpLanguageModelToolContribution.ts) which already works correctly. Related: https://github.com/microsoft/vscode/issues/340232 tracks a separate MCP Apps gap (embedded resources/resource links), not the same defect. Comment from the reporter: https://github.com/microsoft/vscode/issues/340165#issuecomment-1 points at PR https://github.com/microsoft/vscode/pull/321016 as the mapping that omitted this.
- **Open decisions:**
  - Does the Copilot CLI SDK's tool-complete event actually expose structuredContent, and if so under what property — needs confirmation against the SDK before deciding how to wire it through?
  - Should structuredContent live as a new top-level field on ToolCallCompletedState, or be modeled as another ToolResultContent block type, given the same shape is consumed by both the Copilot and Claude agent-host mappings?

## Evidence

- **no structuredContent field:** src/vs/platform/agentHost/common/state/sessionState.ts has no `structuredContent` on `ToolResultContent`/`ToolCallCompletedState` — grep confirms zero matches, so the live completion path (copilotAgentSession.ts) and history replay (mapSessionEvents.ts) have nowhere to carry it even if the SDK event supplies it.
- **reconstruction drops it:** toMcpCallToolResult() in src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/stateToProgressAdapter.ts (around line 1919-1930) returns `{ content, isError }` only — no structuredContent — and chatMcpAppModel.ts forwards that reconstructed object unchanged to the widget.
- **Local MCP path works:** src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts reads `callResult.structuredContent` directly off the original CallToolResult (lines 333/389-391), confirming the Local path retains the field while the agent-host path does not.
- **no fix on main:** HEAD at commit 280a9749 (latest in repo) shows no related change; issue is 0 days old with no maintainer response yet.
- **SDK availability unconfirmed:** Reporter notes the raw Copilot SDK event's own structuredContent field was never captured/confirmed as populated — this checkout has no node_modules to inspect the SDK's event types, so whether the data is even available to thread through is unverified.
