# Issue #328399 — macOS: VS Code 1.131 blocks Local Network access for integrated terminal/Remote-SSH (regression, works on 1.130)

[https://github.com/microsoft/vscode/issues/328399](https://github.com/microsoft/vscode/issues/328399)

## Summary

Well-documented regression: many independent macOS users on 1.131/1.132/1.133 confirm the integrated terminal and its spawned processes (ping, ssh, docker, dotnet, mongo drivers) are denied Local Network traffic that works fine outside VS Code and on 1.130. A collaborator could not reproduce it directly, but the community diagnosis (NECP fingerprint in comment https://github.com/microsoft/vscode/issues/328399#issuecomment-5223... by patrick-loibl) is concrete enough that this should stay open for engineering follow-up, not be closed.

## Change summary

On macOS, VS Code 1.131+ silently loses Local Network (LAN) access for the integrated terminal and Remote-SSH, even though the system Local Network permission toggle appears granted; rolling back to 1.130 restores access.

## Best solution

Needs an engineer with local repro (or Apple's TCC/NECP tooling) to compare the Local Network entitlement/TCC request path across the Electron bump cited in this thread (42.6.0 in 1.130 vs 42.7.0+ in 1.131, current main is 42.8.1) and determine whether Electron's bundle/entitlement handling changed how macOS grants on-link/broadcast/multicast traffic to spawned child processes; the bisect tool (`npx @vscode/vscode-bisect -q insider -g 1.129 -b 1.131`) should be re-run by an affected reporter to pin the exact regressing build.
