# Issue #269179 — `@mcp  @installed ` doesn't show me the extensions I installed through the mcp gallery

[https://github.com/microsoft/vscode/issues/269179](https://github.com/microsoft/vscode/issues/269179)

## Summary

The requested filter remains unsupported on current main: `@mcp @installed` is routed to the MCP view, but `@installed` is treated as gallery search text rather than an installed-only modifier. The accepted Backlog request should remain open under discussion until maintainers choose between supporting the modifier and removing the misleading combination.

## Change summary

Make the Extensions view handle `@installed`, `@enabled`, and `@disabled` coherently when combined with `@mcp`.

## Best solution

Give MCP searches consistent, explicit filter semantics: either make applicable subcommands operate on locally installed MCP servers or prevent unsupported extension subcommands from being offered in the `@mcp` context.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/browser/mcpServersView.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsViewlet.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsViews.ts`, `src/vs/workbench/contrib/extensions/test/electron-browser/extensionsViews.test.ts`
- **Validation:** Run `./scripts/test.sh --grep "ExtensionsViews Tests"` with coverage asserting the chosen `@mcp @installed` routing and filter behavior; manually verify the Extensions search suggestions do not offer any unsupported MCP subcommands.
- **Behavior:**

  > MCP searches must not present extension filter combinations that silently produce unrelated or empty gallery results. If `@installed`, `@enabled`, or `@disabled` is available while `@mcp` is active, it must filter the corresponding local MCP servers; otherwise those modifiers must be unavailable in that context. Ordinary extension searches, plain `@mcp` gallery browsing, and the default installed-MCP view must remain unchanged.
- **Trace:**

  > The Extensions container recognizes any query containing `@mcp` through `SearchMcpServersContext` in `src/vs/workbench/contrib/extensions/browser/extensionsViewlet.ts`. Generic installed-extension routing is excluded for MCP queries by `ExtensionsListView.isInstalledExtensionsQuery()` and `isSearchInstalledExtensionsQuery()` in `extensionsViews.ts`. The resulting MCP view passes every non-empty suffix directly to `IMcpWorkbenchService.queryGallery()` in `src/vs/workbench/contrib/mcp/browser/mcpServersView.ts`; only an empty suffix uses `queryLocal()`, so `@installed` currently has no filter semantics. Keep the boundary to MCP query parsing and search affordances; do not change ordinary extension filtering or MCP installation state.
- **Open decisions:**
  - Should `@installed`, `@enabled`, and `@disabled` become supported local MCP filters, or should unsupported extension subcommands be hidden whenever the `@mcp` context is active?

## Evidence

- **current source:** In `src/vs/workbench/contrib/mcp/browser/mcpServersView.ts`, `McpServersListView.query()` sends every non-empty MCP query to `queryGallery({ text: query.replace('@mcp', '') })`; therefore `@mcp @installed` searches the gallery for `@installed`, while only an empty query calls `queryLocal()`.
- **view routing:** `src/vs/workbench/contrib/extensions/browser/extensionsViews.ts` explicitly excludes queries containing `@mcp` from the generic installed-extension predicates, so current main keeps the MCP view active but supplies no MCP-specific parsing for `@installed`.
- **partial existing capability:** `src/vs/workbench/contrib/mcp/browser/mcpServersView.ts` registers `MCP Servers - Installed` when the Extensions view has its default empty query and installed MCP servers exist. Clearing the search exposes installed servers, but this does not satisfy the requested `@mcp @installed` filter or address the other visible subcommands.
- **maintainer direction:** A maintainer noted at https://github.com/microsoft/vscode/issues/269179#issuecomment-3353773385 that extension-view subcommands do not work with `@mcp` and proposed disabling them in that context if combinations are not intended.
- **canonical search:** No older open issue was found with the same observable `@mcp` subcommand behavior. The later https://github.com/microsoft/vscode/issues/316362 concerns plugin-sourced MCP deduplication and management surfaces, not installed MCP gallery filtering.
