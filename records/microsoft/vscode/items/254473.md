# Issue #254473 — Add scripting interface/batch mode for Copilot Agent Mode?

[https://github.com/microsoft/vscode/issues/254473](https://github.com/microsoft/vscode/issues/254473)

## Summary

Keep open: current source provides simulation runners and programmable Agent Host infrastructure, but that does not establish a supported batch interface that reuses the reporter's VS Code agent configuration. A maintainer explicitly accepted this direction and consolidated the related evaluation request here.

## Change summary

Expose a noninteractive scripting interface for running the VS Code Copilot agent with project prompts, context and MCP tools, bounded execution, persisted edits and completion results.

## Best solution

Provide a documented automation contract for evaluating the VS Code agent with the same project customizations used interactively. First establish how existing simulation and Agent Host interfaces cover that contract, then identify the remaining configuration-parity and execution-lifecycle gaps.

## Plan brief

- **Likely files:** `src/vs/platform/environment/node/argv.ts`, `cli/src/commands/args.rs`, `extensions/copilot/test/simulationMain.ts`, `extensions/copilot/test/base/simulationOptions.ts`, `extensions/copilot/test/simulation/externalScenarios.ts`, `src/vs/platform/agentHost/test/node/e2e/README.md`
- **Validation:** The plan should end with an executable acceptance scenario that runs a prompt noninteractively in a temporary configured project, exercises a project MCP tool and customization, persists an edit without a save dialog, and reports completion or a configured execution limit without fixed sleeps.
- **Behavior:**

  > A caller can run the VS Code Copilot agent noninteractively using a project's prompts, instructions, context and MCP setup rather than maintaining a separate agent configuration. Authorized edits persist without manual Keep or save interactions. A run exposes completion, failure and execution-limit outcomes that an external evaluation suite can consume. Acceptance must distinguish reuse of the VS Code agent configuration from merely invoking a different coding harness.
- **Trace:**

  > The maintainer accepted this direction at https://github.com/microsoft/vscode/issues/254473#issuecomment-3138222149, and the evaluation request at https://github.com/microsoft/vscode/issues/258419 was consolidated here. extensions/copilot/test/base/simulationOptions.ts and test/simulationMain.ts already support external scenarios, while test/simulation/externalScenarios.ts builds simulated workspaces and dispatches edit/agent scenarios through simulatePanelCodeMapper. src/vs/platform/environment/node/argv.ts exposes UI-oriented code chat options; cli/src/commands/args.rs exposes host management, discovery and transport commands, not a prompt-running batch command. Agent Host E2E documentation demonstrates programmable provider execution but deliberately isolates ambient configuration. The unresolved boundary is which supported automation surface preserves the intended VS Code harness and configuration semantics; do not assume a standalone CLI or an internal simulation runner satisfies that parity. Existing interactive behavior and permission enforcement must remain intact.
- **Open decisions:**
  - Must batch execution reproduce the extension-host Agent Mode environment, including editor-provided language context, or is Agent Host execution with a documented configuration-parity boundary sufficient?
  - Which configuration sources must carry over automatically: workspace prompts and MCP definitions only, or also user/profile customizations and editor-provided tools?
  - What supported caller contract should expose authorization, completion, persisted edits and iteration or wall-clock limits?

- **Existing simulation capability:** extensions/copilot/CONTRIBUTING.md documents npm run simulate. extensions/copilot/test/base/simulationOptions.ts exposes --external-scenarios, --sidebar, --n and --output; test/simulationMain.ts loads those scenarios. These are substantive existing evaluation capabilities, but their existence alone does not prove reuse of a user's live workspace MCP and prompt configuration.
- **Simulation boundary:** extensions/copilot/test/simulation/externalScenarios.ts constructs SimulationWorkspace-backed scenarios and routes /edit and /agent conversation scenarios through simulatePanelCodeMapper. That source establishes a developer simulation path, not the full requested supported interface for unattended runs against an ordinary configured project.
- **Current CLI capability check:** src/vs/platform/environment/node/argv.ts registers code chat with mode, context-file and window options. cli/src/commands/args.rs:377-405 registers AgentSubcommand variants Host, Ps, Stop, Kill, Logs, Endpoints and Relay, but no prompt-running batch subcommand. cli/src/commands/agent_relay.rs explicitly implements a raw transport bridge rather than prompt execution and completion handling.
- **Agent Host infrastructure is relevant but not proof of completion:** src/vs/platform/agentHost/test/node/e2e/README.md documents external protocol-driven tests against real provider SDK/CLI subprocesses. Its isolated configuration intentionally excludes ambient MCP servers and session state, so this harness is a useful foundation but does not demonstrate the reporter's requested interactive-to-batch configuration parity.
