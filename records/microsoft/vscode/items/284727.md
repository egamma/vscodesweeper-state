## Evidence

- **Reported impact:** https://github.com/microsoft/vscode/issues/284727 reports approximately 6.1 GB and 1.0 GB in a system monitor on VS Code 1.107.1, with continuing growth and disk activity. The reproduction describes general editing and elapsed time, but supplies no minimal workspace, precise triggering operation, or process-memory time series.
- **Diagnostic values are inflated:** In the checkout, src/vs/base/node/ps.ts:listProcesses converts Unix ps memory percentages into bytes. src/vs/platform/diagnostics/node/diagnosticsService.ts:554-555 then treats those bytes as percentages and multiplies by total system memory again before displaying MB. This explains the impossible multi-billion-MB values in the supplied code --status table, but does not invalidate the independent system-monitor observation.
- **Extensions-disabled evidence needs clarification:** Although the reporter states that code --disable-extensions reproduces the problem, the supplied process tree includes gopls, tailwindServer.js, and eslintServer.js beneath extension-host. That capture does not establish which process grows in the claimed extensions-disabled session; it also does not prove an extension causes the original problem.
- **Discussion corroborates symptoms, not an isolated cause:** The December 23 comment reports similar memory and disk pressure in WSL2; the January 16 comment reports idle CPU usage; the January 21 Fedora KDE comment reports multi-gigabyte growth and a significant reduction when extensions are disabled. These are useful corroborating observations, but none supplies a controlled reproduction identifying the same VS Code core process or root cause.

Its scope does not cover actual memory growth or disk pressure, so it is not a canonical duplicate for this broader report.
