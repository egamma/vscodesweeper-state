# Issue #336883 — Incremental rendering re-animates the full response when main content contains a file reference

[https://github.com/microsoft/vscode/issues/336883](https://github.com/microsoft/vscode/issues/336883)

## Summary

Real, confirmed defect in the new experimental Incremental Rendering feature: adding a new inline file reference mid-stream trips the strict inline-reference equality check, forcing a full non-incremental re-render that replays the entire block-reveal animation instead of animating only the new content.

## Change summary

When incremental rendering is enabled, a new file reference appearing in the main streaming response causes the whole response to re-animate instead of only the newly appended content.

## Best solution

Loosen the inline-reference comparison in ChatMarkdownContentPart so a purely additive change (new keys, all previously-existing keys unchanged) is still eligible for `tryIncrementalUpdate`'s morph path, reserving the full-rebuild fallback for actual metadata changes (e.g. a reference resolving) as intended by the existing test.

## Evidence

- **root cause:** src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatMarkdownContentPart.ts:574 — `tryIncrementalUpdate` bails to `return false` whenever `equalsInlineReferences(newMarkdown.inlineReferences, this.markdown.inlineReferences)` is false, before ever calling `IncrementalDOMMorpher.tryMorph`.
- **over-strict check:** `equalsInlineReferences` (same file, line 646) returns false whenever `Object.keys(a).length !== Object.keys(b).length` — so simply adding one new inline reference (as happens when a file path streams in and becomes a reference) fails equality even though every prior reference is untouched.
- **fallback consequence:** Returning false from `tryIncrementalUpdate` causes the caller to discard the existing `ChatMarkdownContentPart`/DOM and build a fresh one, which re-`seed()`s the `IncrementalDOMMorpher` with `animateInitial: true` (chatMarkdownContentPart.ts:438), re-triggering the entrance animation on every already-rendered child (chatIncrementalRendering.ts:151-179).
- **existing test only covers 'changed' case:** src/vs/workbench/contrib/chat/test/browser/widget/chatContentParts/chatMarkdownContentPart.test.ts, test 'tryIncrementalUpdate requires unchanged inline reference metadata' (~line 733), only exercises an existing key's metadata being *resolved*, not a brand-new key being appended — the additive case this issue reports is untested and unhandled.
