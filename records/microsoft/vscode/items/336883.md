# Issue #336883 — Incremental rendering re-animates the full response when main content contains a file reference

[https://github.com/microsoft/vscode/issues/336883](https://github.com/microsoft/vscode/issues/336883)

## Summary

Well-documented bug in the experimental incremental-rendering feature; tracing the code shows a plausible structural cause (full-content DOM rebuild each frame combined with a top-level-child-count heuristic for what's 'already revealed'), but I can't execute the streaming/timing behavior to nail the exact trigger, so this stays open for a maintainer to confirm and design the fix.

## Change summary

With chat.experimental.incrementalRendering enabled, streaming a response that contains a file path/URL/reference in the main body causes the whole response's entrance animation to restart instead of only newly appended content animating.

## Best solution

Investigate `IncrementalDOMMorpher` in src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatIncrementalRendering/chatIncrementalRendering.ts: it fully re-renders the cumulative markdown via `doRenderMarkdown()` on every frame (see class JSDoc at lines 19-32) and tracks 'already revealed' purely by top-level DOM child count (`_revealedChildCount` in `_animateNewChildren`, lines 274-302). Any content-driven DOM restructuring of earlier, already-rendered text (e.g. a bare path/URL that only gets recognized/linkified once more of the stream resolves it, or gets rewritten by `walkTreeAndAnnotateReferenceLinks` in chatMarkdownDecorationsRenderer.ts) can change the child count/structure for content that was already shown, defeating the count-based 'already revealed' assumption and re-triggering the animation. This likely needs identity-based tracking (e.g. keyed by node/content hash) rather than a raw child index.

- **Behavior:**

  > When `chat.experimental.incrementalRendering.enabled` is true, only newly appended content should receive the incremental-rendering entrance animation as a chat response streams in. Content that was already rendered and revealed must remain visually stable — in particular, a workspace file path/URL/inline file reference being converted into a rendered file/link reference in the main response body must not cause the whole response (or already-revealed portions of it) to re-animate. Acceptance: streaming a response containing a file reference in the main body settles normally, with no visible re-flash/re-blur of previously shown text once the reference resolves.
- **Trace:**

  > `IncrementalDOMMorpher` (chatIncrementalRendering.ts) re-renders the full cumulative markdown via the registered callback (`renderMarkdown()` in chatMarkdownContentPart.ts, which itself calls `renderer.render(...)` into `this.domNode` and then `walkTreeAndAnnotateReferenceLinks` from chatMarkdownDecorationsRenderer.ts) on every rAF-batched frame — not a true DOM diff/morph, despite the class name. `_animateNewChildren` (lines 274-302) decides what to animate purely from `this._domNode.children.length` vs a stored `_revealedChildCount`; it has no signal that content at an already-revealed index changed shape. Do not restructure the buffering/animation strategy pattern (buffers/, animations/) — the boundary is specifically how 'already revealed' is determined across re-renders. Where the uncertainty starts: whether the DOM restructuring on file-reference resolution comes from GFM autolink recognition timing, from `renderFileAnchor`/`richLinkDecorator` replacing anchor elements, or from paragraph-splitting — this needs to be confirmed by actually running the repro steps in the issue.
- **Open decisions:**
  - Should 'already revealed' be tracked by stable node identity/content hash instead of raw child count, and is that change scoped to `IncrementalDOMMorpher` alone or does it also require coordination with the buffer/animation strategies?

## Evidence

- **full re-render architecture:** src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatIncrementalRendering/chatIncrementalRendering.ts lines 19-32 and 233-270: `_flushRender` calls the registered render callback with the (possibly buffered) full markdown, which re-runs `renderMarkdown()`/`doRenderMarkdown()` from scratch on every animation frame rather than diffing the DOM.
- **count-based reveal tracking:** `_animateNewChildren` (lines 274-302) only compares `this._domNode.children.length` to `_revealedChildCount`; it has no way to detect that content at an already-revealed index changed structure (e.g. plain text becoming a linkified/widget-ized file reference) versus genuinely new content.
- **link/file-reference post-processing:** chatMarkdownContentPart.ts line 399 calls `markdownDecorationsRenderer.walkTreeAndAnnotateReferenceLinks(this.markdown, result.element)` after every full markdown render, and chatMarkdownDecorationsRenderer.ts (`renderFileAnchor`, `renderFileWidget`, `richLinkDecorator.decorate`) mutates/replaces anchor elements for file/URL references — this runs again on every re-render pass over the whole cumulative content.
- **related but distinct issue:** https://github.com/microsoft/vscode/issues/319248 reports a similar-looking re-animation symptom for a completed Mermaid block during streaming, but the reporter explicitly distinguishes it as Mermaid-specific, not covering file references or this experimental Incremental Rendering config — not a duplicate target.
