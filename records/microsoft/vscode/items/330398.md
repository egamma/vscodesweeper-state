# Issue #330398 — Dismissing a promo banner in one window should dismiss it in all windows.

[https://github.com/microsoft/vscode/issues/330398](https://github.com/microsoft/vscode/issues/330398)

## Summary

Team-authored (alexr00, MEMBER) and traced conclusively in source: ChatPromoNotificationContribution persists a promo dismissal to StorageScope.APPLICATION but never listens for that storage key changing, so a dismissal in one window doesn't refresh already-open windows. Real, localized gap; routing to the chat area.

## Change summary

Dismissing a promo banner in one VS Code window should also dismiss/remove it from other currently-open windows, not just persist for future sessions.

## Best solution

In src/vs/workbench/contrib/chat/browser/chatPromoNotification.ts, subscribe to IStorageService.onDidChangeValue(StorageScope.APPLICATION, DISMISSED_PROMOS_STORAGE_KEY, ...) and call _update() so other open windows pick up the dismissal immediately, mirroring the existing onDidChangeLanguageModels-triggered refresh.

  > ChatPromoNotificationContribution (src/vs/workbench/contrib/chat/browser/chatPromoNotification.ts) persists dismissed promo ids to StorageScope.APPLICATION/StorageTarget.USER under the key 'chat.dismissedPromoIds' via _persistDismissedPromo, but it only calls _update() in response to _languageModelsService.onDidChangeLanguageModels and the local chatInputNotificationService.onDidDismiss event. It never listens for the storage value itself changing, so if the user dismisses a promo in window A, window B (which has its own instance of this contribution) keeps showing the now-dismissed notification until some unrelated model-list change happens to trigger a refresh. Add a registered listener on _storageService.onDidChangeValue(StorageScope.APPLICATION, DISMISSED_PROMOS_STORAGE_KEY, this._store) (or the appropriate DisposableStore) in the constructor that calls this._update() when the key changes, so all open windows re-derive their notification set from the shared dismissed-ids storage. Do not change the persistence format or the per-harness notification bucketing logic in _update(); only add the additional trigger for refreshing. Validate with a unit test in src/vs/workbench/contrib/chat/test/browser/chatPromoNotification.test.ts asserting that firing the application-scope storage change event for DISMISSED_PROMOS_STORAGE_KEY causes an already-shown notification for a now-dismissed promo id to be deleted, without needing onDidChangeLanguageModels to fire. ## Evidence

- **no cross-window listener:** src/vs/workbench/contrib/chat/browser/chatPromoNotification.ts only calls _update() from onDidChangeLanguageModels and the local widget's onDidDismiss; it never subscribes to IStorageService.onDidChangeValue for DISMISSED_PROMOS_STORAGE_KEY ('chat.dismissedPromoIds'), even though the value is stored at StorageScope.APPLICATION (cross-window scope).
- **storage API supports this:** IStorageService.onDidChangeValue(StorageScope.APPLICATION, key, disposable) exists (src/vs/platform/storage/common/storage.ts:75) and is the standard mechanism for cross-window storage sync in VS Code.
- **related issue:** https://github.com/microsoft/vscode/issues/330327 covers a different aspect (persisting the dismissal so it doesn't reappear later), which this same file already implements via _persistDismissedPromo; the live cross-window sync asked for here is a distinct, unaddressed gap.
