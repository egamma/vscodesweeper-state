# Issue #161753 — TreeView search/filter input & api for customization

[https://github.com/microsoft/vscode/issues/161753](https://github.com/microsoft/vscode/issues/161753)

## Summary

Keep open for extension-controlled filtering through the existing tree find UI: current APIs still do not expose its query to extension data providers. The maintainer accepted this API gap, and the request has 43 upvotes plus a subsequently consolidated duplicate; the separate input field was explicitly declined.

## Change summary

Expose tree-find queries through the extension API so extensions can populate and filter their trees using provider-specific logic.

## Best solution

Provide a designed extension API for provider-controlled search results using the unified Ctrl+F tree interface, including a defined relationship with built-in label filtering. Preserve the maintainer's decision against a separate extension-specific search input.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/browser/parts/views/treeView.ts`, `src/vs/workbench/api/browser/mainThreadTreeViews.ts`, `src/vs/workbench/api/common/extHostTreeViews.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`
- **Validation:** Use a development extension contributing a TreeDataProvider: focus its tree, open Ctrl+F, and enter a query that matches provider metadata but not the displayed label. Verify the extension receives the query and its intended results are visible; clear and close find and verify the original tree returns. Also verify a tree without the new API retains existing find behavior. These are acceptance checks for the eventual implementation, not checks executed during this read-only review.
- **Behavior:**

  > Extension authors should be able to respond to the query entered in the existing tree-find control and supply results using their own data and matching rules. The current interface searches labels without giving the extension that query. Acceptance should demonstrate provider-defined results, including an item whose label does not contain the query, and restoration of normal content after searching ends. Trees that do not opt in must retain their existing behavior, and no separate search-input UX is requested within the accepted scope.
- **Trace:**

  > TreeViewOptions, TreeView, and TreeDataProvider in src/vscode-dts/vscode.d.ts expose no search-query contract. The custom tree construction in src/vs/workbench/browser/parts/views/treeView.ts supplies label-based navigation, and MainThreadTreeViews.registerListeners does not forward find changes across the extension-host boundary. Internal IAsyncFindProvider in src/vs/base/browser/ui/tree/asyncDataTree.ts already models asynchronous queries, cancellation, and sessions, and File Explorer uses it; this is internal infrastructure, not an extension API. The unresolved boundary is how extension-controlled results interact with built-in label filtering and find modes. Preserve the unified Ctrl+F UX and nonparticipating providers. The accepted scope is documented at https://github.com/microsoft/vscode/issues/161753#issuecomment-1259386999; https://github.com/microsoft/vscode/issues/230219 was consolidated into this issue.
- **Open decisions:**
  - Should the public contract only notify extensions of query changes while built-in label filtering remains active, or permit provider-owned matching and visibility so results can match metadata or retain otherwise nonmatching descendants?
  - Should extensions receive queries in both highlight and filter modes, and what result-restoration behavior should the contract guarantee when the query is cleared or the find control closes?

## Evidence

- **Accepted scope:** https://github.com/microsoft/vscode/issues/161753#issuecomment-1259386999 explicitly declines a separate input field because Ctrl+F is the unified tree-search mechanism, but accepts callbacks containing the search contents as a fair feature request. The reporter accepted that distinction.
- **Existing capability does not cover the API gap:** src/vscode-dts/vscode.d.ts:11852-11916, 12144-12306 defines TreeViewOptions, TreeView, and TreeDataProvider without a find-query event or search-provider callback; getChildren receives only an optional parent element. The tree-related proposed declaration files also expose no search/filter contract.
- **Current workbench boundary:** src/vs/workbench/browser/parts/views/treeView.ts:703-758 configures the custom tree's keyboardNavigationLabelProvider from labels or resource names, without an extension findProvider. MainThreadTreeViews.registerListeners in src/vs/workbench/api/browser/mainThreadTreeViews.ts:202-212 forwards expansion, collapse, selection/focus, visibility, and checkbox changes, but no search query.
- **Internal capability is not extension adoption:** src/vs/base/browser/ui/tree/asyncDataTree.ts:225-256 defines IAsyncFindProvider.find(pattern, toggles, token), with session and visibility hooks. src/vs/workbench/contrib/files/browser/views/explorerView.ts:578 supplies a findProvider for File Explorer, but the extension-contributed tree construction does not expose that capability. Internal async search therefore does not complete this request.
- **Settings are only partial coverage:** src/vs/platform/list/browser/listService.ts registers workbench.list.defaultFindMode and workbench.list.defaultFindMatchType. These configure existing tree-find behavior, not delivery of the query to extension code or provider-controlled results.
