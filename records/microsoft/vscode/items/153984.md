# Issue #153984 — Rendered view for DocStrings and Comments in editor

[https://github.com/microsoft/vscode/issues/153984](https://github.com/microsoft/vscode/issues/153984)

## Summary

Keep this accepted, well-supported request open: existing documentation hovers and comment folding do not provide an in-place rendered documentation mode. The discussion clearly distinguishes the requested capability from those workarounds, and no verified canonical issue or completed implementation was found.

## Change summary

Provide toggleable, themed rendering of documentation comments and docstrings inside the source editor, with keyboard controls and automatic return to raw text when editing.

## Best solution

Design an optional editor contribution that presents documentation in place while preserving the underlying source and normal editing behavior. Establish the initial language and documentation-format coverage, then define how rendering integrates with keyboard navigation, accessibility, folding, and language-provided documentation.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/hover/browser/markdownHoverParticipant.ts`, `src/vs/editor/contrib/folding/browser/folding.ts`, `src/vs/editor/browser/editorBrowser.ts`, `src/vs/editor/common/config/editorOptions.ts`
- **Validation:** The plan should end with a runnable editor scenario using representative Python docstrings and JavaScript JSDoc: toggle one block and all supported blocks, verify themed in-place formatting and keyboard collapse/expand, begin editing to restore raw source, and confirm that toggling alone never changes the document. Include keyboard-only and screen-reader checks and retain existing hover and folding behavior.
- **Behavior:**

  > Documentation comments and docstrings can be displayed as formatted content at their location in a source editor rather than only in a hover. Users can toggle the mode globally, for the current editor, and for an individual documentation block, with keyboard controls for toggling and collapse/expand. Rendered content follows the current theme, and attempting to edit a rendered block restores its editable source representation. Presentation changes must not modify the document or disrupt ordinary editing, existing hovers, or accessibility.
- **Trace:**

  > The existing MarkdownHoverParticipant in src/vs/editor/contrib/hover/browser/markdownHoverParticipant.ts queries hover providers at a position and renders their markdown inside a hover; it does not discover documentation blocks or render them in place. FoldAllBlockCommentsAction in src/vs/editor/contrib/folding/browser/folding.ts collapses comment ranges without formatting them. src/vs/editor/browser/editorBrowser.ts exposes view-zone and hidden-area primitives, while editor configuration is registered in src/vs/editor/common/config/editorOptions.ts. These establish relevant infrastructure, not a diagnosed bounded implementation: uncertainty begins with language-specific block discovery and obtaining the appropriate formatted content. Preserve source text, ordinary folding and hover behavior, selection, undo, and keyboard and screen-reader access. The clarification in https://github.com/microsoft/vscode/issues/153984 rules out hover improvements as fulfillment; https://github.com/microsoft/vscode/issues/14165 and https://github.com/microsoft/vscode/issues/3220 are related surfaces, not canonical duplicates.
- **Open decisions:**
  - Which languages and documentation formats must the initial version support, and what should users see for documentation blocks outside that supported scope?
