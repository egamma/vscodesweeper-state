# Issue #170442 — Trusted domain dialog in web doesn't return focus to previously clicked element when canceled.

[https://github.com/microsoft/vscode/issues/170442](https://github.com/microsoft/vscode/issues/170442)

## Summary

Keep open: maintainers confirmed the web focus-restoration defect, and current main still restores only the outer and inner iframe windows without preserving the previously focused webview element. This team-authored, accepted Backlog bug has no cited fixing commit or same-symptom older canonical.

## Change summary

Canceling the trusted-domain dialog in VS Code for the Web can leave keyboard focus at the webview iframe boundary, with the next Tab sometimes entering browser chrome instead of returning to the activated link.

## Best solution

Provide a general webview focus-restoration path so dismissing a workbench dialog returns keyboard navigation to the previously focused webview element, or at minimum makes the next Tab reliably continue inside the webview rather than browser chrome. The behavior should be solved centrally for webviews instead of separately by each extension.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/dialog/dialog.ts`, `src/vs/workbench/contrib/webview/browser/webviewElement.ts`, `src/vs/workbench/contrib/webview/browser/pre/index.html`
- **Validation:** On insiders.vscode.dev, focus an external link inside a webview, open and cancel the trusted-domain dialog repeatedly, and verify every dismissal returns to the link or makes the next Tab continue within the webview; repeat enough times to cover the reported alternating failure and confirm focus never enters browser chrome.
- **Behavior:**

  > In VS Code for the Web, activating an untrusted external link from a webview and canceling the trusted-domain dialog must preserve the user's keyboard position. Focus should return to the previously activated webview element when possible; at minimum, the next Tab must continue through the webview's logical tab order and never jump to browser chrome. Acceptance requires repeated cancel cycles because the confirmed failure alternated between correct and incorrect outcomes. Desktop native-dialog behavior and ordinary webview focus transitions must remain unchanged.
- **Trace:**

  > The dialog records document.activeElement in src/vs/base/browser/ui/dialog/dialog.ts, which is only the outer webview iframe, and restores it during disposal. WebviewElement._doFocus in src/vs/workbench/contrib/webview/browser/webviewElement.ts focuses the iframe contentWindow and sends the generic `focus` message. The preload handler in src/vs/workbench/contrib/webview/browser/pre/index.html forwards that message to the active inner frame's contentWindow without retaining the previously focused descendant. Maintainers confirmed that the iframe regains focus but the next Tab intermittently enters browser chrome; the unresolved point is the browser's cross-origin nested-frame focus state and the webview's placement at the end of the workbench DOM. Keep the investigation general to VS Code webviews rather than coupling it to the GitHub Pull Requests extension, and do not alter trusted-domain decisions or native desktop dialogs.
