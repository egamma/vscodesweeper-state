# Issue #259160 — Cannot use access token for gemini

[https://github.com/microsoft/vscode/issues/259160](https://github.com/microsoft/vscode/issues/259160)

## Summary

A real authentication capability gap remains on current main: Gemini BYOK accepts only an API key. A maintainer invited a contribution, but the supported credential source and ownership of the authentication flow need a product decision first.

## Change summary

Allow Gemini models in Copilot Chat to authenticate with an OAuth access token or Gemini credentials instead of requiring an API key.

## Best solution

Define a supported, refreshable Google authentication contract for the Gemini provider, then expose it through Manage Models without reading another extension's private storage format unless that extension provides a stable integration API.

## Plan brief

- **Likely files:** `extensions/copilot/package.json`, `extensions/copilot/src/extension/byok/vscode-node/geminiNativeProvider.ts`, `extensions/copilot/src/extension/byok/vscode-node/test/geminiNativeProvider.spec.ts`, `extensions/copilot/src/extension/byok/vscode-node/abstractLanguageModelChatProvider.ts`
- **Validation:** Extend the Gemini provider Vitest suite to verify model discovery and chat requests authenticate through the selected non-API-key mechanism, refresh expired credentials as defined by the plan, and preserve the existing API-key path.
- **Behavior:**

  > Users can configure Gemini in Manage Models using the approved Google authentication mechanism without supplying an API key. Model discovery and chat requests use that credential, and expired credentials are refreshed or produce a clear reauthentication path according to the selected contract. Existing API-key configurations continue to work unchanged. Acceptance includes provider tests for discovery, request authentication, expiration behavior, and API-key compatibility.
- **Trace:**

  > The Gemini contribution in extensions/copilot/package.json currently exposes only a required `apiKey`. AbstractLanguageModelChatProvider in extensions/copilot/src/extension/byok/vscode-node/abstractLanguageModelChatProvider.ts propagates that configuration, and GeminiNativeBYOKLMProvider in extensions/copilot/src/extension/byok/vscode-node/geminiNativeProvider.ts constructs `GoogleGenAI` with only `{ apiKey }` for both discovery and requests. The nearby Azure provider demonstrates a separate VS Code authentication-session path, but it does not settle the Google credential contract. The issue specifically mentions `%LOCALAPPDATA%\google-vscode-extension\auth\credentials.json`; that is another extension's private storage and must not become an implicit dependency without an agreed stable ownership boundary. Preserve existing API-key behavior and avoid broad changes to other BYOK providers.
- **Open decisions:**
  - Should the supported public contract use a VS Code authentication session owned by the Gemini extension, Google application credentials, or a user-entered OAuth credential independent of that extension?
  - Must credentials refresh automatically for long-lived model configurations, or should expiration prompt the user to authenticate again?
  - Should Manage Models continue offering API-key authentication alongside OAuth, and how should users choose between those modes?
