# Issue #334613 — Forking Copilot (Agent Host) chat creates orphaned sessions, broken in VSCode

[https://github.com/microsoft/vscode/issues/334613](https://github.com/microsoft/vscode/issues/334613)

## Summary

Detailed, evidenced report (including a `copilot --resume` screenshot proving the forked SDK session exists on disk while VS Code's UI reverts to the original chat) of a real Copilot Agent Host fork defect; source tracing shows a plausible mechanism but not a conclusively pinned fix location, so this needs a maintainer/agent session to diagnose rather than a quick patch.

## Change summary

Forking a Copilot (Agent Host) chat via `/fork` or the Fork button briefly creates a new session, but the title reverts, the source chat is lost from the UI, and the forked chat is unreachable even though it exists on disk.

## Best solution

Trace why the peer-chat resource returned by `_forkSession` in agentHostSessionHandler.ts stops resolving after the initial title update — likely a re-resolution of the session's default/primary chat overwriting the forked fragment during a subsequent state refresh — and fix the chat-widget/session-catalog resolution so a forked chat stays addressable for Copilot the same way it does for other Agent Host providers.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`
- **Validation:** Fork a Copilot Agent Host chat, verify the resulting chat keeps its 'Forked: ...' title and stays selected/reachable via the Back navigation and title dropdown without reverting to the original chat.
- **Behavior:**

  > Forking a Copilot Agent Host chat (via `/fork` or the Fork button) should create a new peer chat that becomes and remains the active chat, keeps a 'Forked: <title>' label, and is reachable afterward from the session's Back navigation and title dropdown alongside the original chat. Currently the title reverts to the un-forked title shortly after creation, the Back/title-dropdown navigation shows only one session, and selecting it opens the original chat — the forked chat (confirmed to exist on disk via `copilot --resume`) becomes permanently unreachable from the UI.
- **Trace:**

  > The backend mints the fork as a genuinely new SDK session via `_forkSdkChat` in src/vs/platform/agentHost/node/copilot/copilotAgent.ts (~line 5003), copying the source chat's database into the new chat's storage scope. The frontend's `_forkSession` in src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts (~line 5610) creates the chat, waits for it to appear in the session's chat catalog, and returns an `IChatSessionItem` addressed by a URI fragment on the same session resource — this initial resolve appears to succeed (the title does briefly flip). The defect is in what happens next: something re-resolves the session back to its default/primary chat, dropping the forked fragment. Do not change the fork-creation semantics (new SDK session + DB copy) — that's intentional; the fix should be in the resolution/catalog path, not the backend mint.
- **Open decisions:**
  - If a forked chat becomes momentarily unreachable (e.g. before the host publishes it), should the UI keep retrying/queuing until it resolves, or immediately surface an error and keep the user on the source chat instead of silently reverting?

## Evidence

- **backend fork mechanism:** src/vs/platform/agentHost/node/copilot/copilotAgent.ts `_mintChatBacking`/`_forkSdkChat` (around lines 4845-5040) forks the source chat's SDK conversation via `client.rpc.sessions.fork(...)`, producing a distinct SDK sessionId and copying its database — this is what shows up as a separate entry in `copilot --resume`.
- **frontend fork wiring:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts `_forkSession` (lines ~5610-5690) creates the new chat via `createChat(...,{fork:...})`, then does `waitForState(...)` on the session's chat catalog to resolve the forked `ChatSummary` before returning an `IChatSessionItem` addressed by a URI fragment (`forkedChatId`) on the *same* session resource.
- **symptom matches a resolution race:** The reporter observes the title briefly flip to 'Forked: ...' (meaning the initial resolve succeeded) before reverting to the original — consistent with something later re-resolving the session's default/primary chat instead of preserving the forked fragment, though this wasn't traced to a single conclusive line.
- **no fix on main:** `git log --oneline --since=2026-09-01 --grep=fork` shows unrelated fork UI polish (tooltip/icon centering, alt-click-to-side) but nothing addressing catalog/resolution correctness for Copilot forks.
