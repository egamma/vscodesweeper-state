# Issue #338920 — Markdown links drop non-line fragments like #page=3 when opening files (PDF links always open on page 1)

[https://github.com/microsoft/vscode/issues/338920](https://github.com/microsoft/vscode/issues/338920)

## Summary

Keep open: the merged fix preserves fragments for preview clicks, but relative-link Ctrl+click in the Markdown source editor remains unresolved. A shared language-service fix is under review and still requires release and adoption by VS Code.

## Change summary

Preserve non-line URI fragments such as #page=3 when opening file links from both Markdown preview and source editors.

## Best solution

Review and land https://github.com/microsoft/vscode-markdown-languageservice/pull/272, then consume the released language-service/server versions in the built-in Markdown extension. Both opening paths should preserve unconsumed fragments without changing existing line, range, or heading navigation.

## Evidence

- **Partial fix, not completion:** https://github.com/microsoft/vscode/pull/332661 is merged, but its description explicitly limits the fix to preview links and leaves source-editor relative links tracked by this issue. Current extensions/markdown-language-features/src/util/openDocumentLink.ts contains the decoded-fragment fallback in MdLinkOpener.openResolvedDocumentLink.
- **Confirmed remaining symptom:** https://github.com/microsoft/vscode/pull/332661#issuecomment-5942174464 reports an actual Code OSS Dev comparison using mathematic.vscode-pdf 0.2.6: patched preview clicks reach page 3, while source-editor Ctrl+click on relative file.pdf#page=3 and file.pdf#page%3D3 still reaches page 1. https://github.com/microsoft/vscode/pull/332661#issuecomment-5942477074 acknowledges that remaining scope.
- **Open upstream implementation:** https://github.com/microsoft/vscode-markdown-languageservice/pull/272 is currently open and explicitly addresses https://github.com/microsoft/vscode/issues/338920. It changes src/languageFeatures/documentLinks.ts to preserve unconsumed fragments through both resolveDocumentLink and resolveLinkTarget; its reported integration validation used unpublished development bundles, not shipped dependencies.
- **Adoption still outstanding:** extensions/markdown-language-features/package.json and package-lock.json still pin vscode-markdown-languageservice and vscode-markdown-languageserver to 0.5.0. src/client/client.ts delegates resolveLinkTarget to the server and forwards vscodeMarkdownLanguageservice.open to vscode.open; the preview-only opener fallback does not cover the source-editor language-server document-link path.
- **Superseded client workaround:** https://github.com/microsoft/vscode/pull/339316 is closed without merging. Its description identifies HTML-entity handling and stale-document-range races in the client middleware approach, names the upstream replacement, and explicitly leaves this issue open until dependency consumption lands.
