# Issue #338632 — Organizing the custom agents in agent picker

[https://github.com/microsoft/vscode/issues/338632](https://github.com/microsoft/vscode/issues/338632)

## Summary

Genuine gap: the agent/mode picker only groups actions into 'builtin' vs 'custom' buckets sorted alphabetically (modePickerActionItem.ts) — there's no user-defined grouping by role and no way to hide agents from the picker. Reasonable request from a power user with many custom agents, but it's brand new (1 day old, 0 upvotes) and no maintainer has weighed in on design.

## Change summary

Let users organize custom agents into role-based groups (e.g. Developer, Tester, PO) in the agent picker, and hide/show groups to declutter the list when many custom agents are defined across a multi-root workspace.

## Best solution

If pursued, extend the mode-picker's category model (src/vs/workbench/contrib/chat/browser/widget/input/modePickerActionItem.ts, which already groups into builtin/custom) to support user- or metadata-defined groups plus a visibility toggle, likely backed by agent frontmatter/metadata (similar to how the Customizations editor already renders group headers via customizationGroupHeaderRenderer.ts) — but the grouping taxonomy and hide/show UX need a maintainer design decision first.

## Vision fit

- **Reason:** It's a workbench/AI-customization UX polish request that could improve usability for heavy custom-agent users, but adding grouping/visibility configuration also risks the 'simple, uniform UI' and 'lean default experience' guardrails for the common case with few agents, so the vision doesn't clearly settle it either way.
- **Evidence:** Values: "Simple, uniform UI and UI interactions" and durable theme: Workbench & core UX (layout flexibility, profiles, settings fidelity) both bear on this without deciding it.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input/modePickerActionItem.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostModePickerPresentation.ts`
- **Validation:** A picker test asserting custom agents render under user-defined groups and that agents in a hidden group are excluded from the rendered action list.
- **Behavior:**

  > Users with many custom agents can assign them to groups (e.g. by role) and choose which groups are visible in the agent/mode picker, so the picker stays short even when dozens of agents are defined across a multi-root workspace. Existing built-in/custom categorization and picker keyboard navigation continue to work unchanged for users who don't define groups.
- **Trace:**

  > The current picker builds its categories in getActionsForCustomAgentTarget/actionProvider.getActions in modePickerActionItem.ts, using only a binary isModeConsideredBuiltIn split via groupBy — there is no concept of an arbitrary group or a visibility flag on IChatMode. The scope should stay inside picker rendering and whatever agent-metadata schema is chosen; do not touch the built-in mode set or the underlying mode-switch command path (ToggleAgentModeActionId).
- **Open decisions:**
  - Where does the group assignment live — agent frontmatter metadata, a new settings map, or a folder-based convention?
  - Is group visibility a per-workspace setting, a per-profile setting, or per-picker-session toggle?
  - Should hidden groups be fully excluded from the picker or just collapsed/deprioritized?
