# Issue #165454 — Context widgets are not aware of Window Controls Overlay (WCO)

[https://github.com/microsoft/vscode/issues/165454](https://github.com/microsoft/vscode/issues/165454)

## Summary

The bug remains source-reproducible on current main: context views are positioned within the full browser viewport without excluding the Window Controls Overlay. The accepted `bug` in the `On Deck` milestone should remain open.

## Change summary

Context menus and other context widgets opened near a Window Controls Overlay can render underneath the native window buttons.

## Best solution

Make context-view placement account for the active window's WCO rectangle when the resulting widget would intersect it, while preserving existing placement everywhere else.

- **Behavior:**

  > A context menu or other context widget opened near native Window Controls Overlay buttons must remain fully visible and must not intersect the overlay rectangle. Acceptance is a context-view regression test demonstrating non-intersection plus the existing positioning tests passing.
- **Trace:**

  > ContextView.doLayout() in src/vs/base/browser/ui/contextview/contextview.ts derives a single rectangular viewport from page offsets and the window's full inner dimensions before calling layout2d. The active window's overlay geometry is already available through getWCOTitlebarAreaRect(targetWindow) in src/vs/base/browser/browser.ts, but context views never consult it, so a top-corner result can occupy pixels reserved for native controls. The same observable context-menu failure was consolidated into this issue from https://github.com/microsoft/vscode/issues/235498. Keep the change bounded to context-view geometry and its tests; do not alter titlebar sizing, native-control rendering, anchors, or ordinary no-WCO placement.
