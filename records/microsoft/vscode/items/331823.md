# Issue #331823 — Copilot `fetch failed` to send `google` apikey and to download `claud SDK`

[https://github.com/microsoft/vscode/issues/331823](https://github.com/microsoft/vscode/issues/331823)

## Summary

Two distinct proxy-related failures bundled in one report. The Claude SDK download half was likely fixed by the proxy-configuration rework in PR #331488 (merged the day before this report, shipped in 1.135.0 — the reporter was on 1.134.0), per the collaborator's own comment, but that's unverified against socks5 specifically. The Gemini BYOK 'fetch failed' half is a real, still-open gap: unlike other BYOK providers, `GeminiNativeBYOKLMProvider` instantiates `@google/genai`'s `GoogleGenAI` client with no fetch/proxy wiring, so it can't honor `http.proxy` (especially non-HTTP proxies like socks5) the way `IFetcherService`-based providers do.

## Change summary

With `http.proxy` set to a socks5 URL, adding a Google Gemini BYOK model fails with `fetch failed` while entering the API key, and the Agent Host also fails to download the Claude SDK tarball; switching to an http:// proxy fixes the Gemini case.

## Best solution

Confirm whether PR #331488 (merged into 1.135.0, touching src/vs/platform/agentHost/node/agentHostProxyResolver.ts and agentHostRequestService.ts) resolves the Claude SDK download under socks5, then separately give `GeminiNativeBYOKLMProvider.getAllModels`/`provideLanguageModelChatResponse` in extensions/copilot/src/extension/byok/vscode-node/geminiNativeProvider.ts a proxy-aware fetch (mirroring how `CustomOAIBYOKModelProvider` uses `IFetcherService`) so it goes through the same proxy resolution as the rest of the extension.
