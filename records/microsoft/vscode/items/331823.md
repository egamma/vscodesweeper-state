# Issue #331823 — Copilot `fetch failed` to send `google` apikey and to download `claud SDK`

[https://github.com/microsoft/vscode/issues/331823](https://github.com/microsoft/vscode/issues/331823)

## Summary

Real, source-confirmed defect: VS Code's `http.proxy` setting explicitly accepts `socks`/`socks4`/`socks5` URLs, but the node-side proxy-agent creation used by the Agent Host's Claude SDK download silently drops any non-http(s) proxy scheme and connects directly, and the fetch path used for provider model listing goes through `@vscode/proxy-agent`'s `undici.ProxyAgent`, which only implements HTTP CONNECT tunneling and has no SOCKS support either — matching the reporter's own diagnosis that socks5 works for some paths (Electron/PAC-aware ones) but not others.

## Change summary

With `http.proxy` set to a `socks5://` URL, adding a Google (Gemini) model via API key fails with `fetch failed`, and the Agent Host's Claude SDK download fails with the same underlying cause; switching to an `http://` proxy fixes at least the Google apikey failure.

## Best solution

Add real SOCKS4/5 proxy support to the node-side proxy agent path in `src/vs/platform/request/node/proxy.ts` (currently `getProxyAgent` only handles `^https?:$` and returns `null` — i.e. no proxy at all — for socks schemes), and check whether the Agent Host's `AgentHostProxyResolver.fetch` (which delegates to `@vscode/proxy-agent`'s `createFetchPatch`/`createProxyAgent`, backed by `new undici.ProxyAgent(...)`, an HTTP-CONNECT-only proxy client) needs the same treatment upstream in `@vscode/proxy-agent`. Short of full support, these paths should at least surface a clear unsupported-proxy-scheme error instead of silently bypassing the proxy.
