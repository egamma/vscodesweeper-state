# Issue #329790 — "command": "revealFileInOS" - doesn't work within devcontainer

[https://github.com/microsoft/vscode/issues/329790](https://github.com/microsoft/vscode/issues/329790)

## Summary

Real, traceable gap: `revealFileInOS`'s local-path mapping only special-cases the WSL remote (added to fix https://github.com/microsoft/vscode/issues/299491), so it silently no-ops for dev container resources, matching exactly the pattern of that earlier bug but for a different remote type.

## Change summary

`revealFileInOS` keybinding/context-menu entry does nothing (and is hidden from the context menu) when the active resource is inside a Dev Container.

## Best solution

Extend `toLocalFileUri` in src/vs/workbench/contrib/files/electron-browser/fileCommands.ts to resolve a host-side path for dev-container remote authorities (mirroring the WSL `\\wsl$\` case added for issue 299491), likely needing cooperation from the remote-containers resolver to supply the host bind-mount path since containers don't have a fixed UNC-style mapping the way WSL does.

## Evidence

- **code path:** src/vs/workbench/contrib/files/electron-browser/fileCommands.ts `toLocalFileUri()` only maps `vscode-remote` authorities when `getRemoteName(resource.authority) === 'wsl'`; any other remote (including dev containers) falls through to `return undefined`, so `revealResourcesInOS` silently does nothing.
- **context menu hidden:** src/vs/workbench/contrib/files/electron-browser/fileActions.contribution.ts gates the 'Reveal in File Explorer' menu item on REVEAL_IN_OS_WHEN_CONTEXT which only matches `file`/`vscode-userdata` schemes, so it's correctly hidden for `vscode-remote` resources today — explaining the reporter's second symptom.
- **precedent:** The reporter's own link, https://github.com/microsoft/vscode/issues/299491, was the exact same symptom for WSL and was fixed/verified in milestone 1.113.0 by adding the wsl-only branch now visible in fileCommands.ts — dev containers were never covered by that fix.
