# Issue #108264 — Add support for vertical tabs

[https://github.com/microsoft/vscode/issues/108264](https://github.com/microsoft/vscode/issues/108264)

## Summary

Keep this accepted Backlog request open: native vertical editor tabs remain missing, and the existing Open Editors view only partially covers the need. With 659 upvotes and concrete accessibility feedback, the next useful step is a maintainer-led layout and interaction design.

## Change summary

Support native vertical file tabs so users can navigate many open editors without repeatedly scrolling a horizontal tab strip.

## Best solution

Provide an optional vertical tab layout that preserves editor-group context and existing tab interactions independently of sidebar navigation. Settle its placement and space-saving behavior before implementation; grouping and archiving need not be prerequisites.

- **Behavior:**

  > Users should be able to choose native vertical file tabs and see more open-file labels without cycling through a horizontal strip. Navigation must retain editor-group context and remain available independently of the active sidebar view. Existing tab selection, focus, ordering, closing, pinned state, and unsaved-state feedback must remain usable, including through keyboard and assistive technology. Acceptance should include many files, repeated basenames, multiple editor groups, and switching sidebar views; the default horizontal layout must remain unchanged.
- **Trace:**

  > EditorTitleControl.createEditorTabsControl in src/vs/workbench/browser/parts/editor/editorTitleControl.ts selects the existing hidden, single, horizontal multiple, and separate-pinned-row controls. MultiEditorTabsControl.createTabsScrollbar in src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts explicitly uses horizontal scrolling and hides the vertical scrollbar. EditorGroupView.layout in src/vs/workbench/browser/parts/editor/editorGroupView.ts reserves title height rather than space for a vertical tab strip. The registrations in src/vs/workbench/browser/workbench.contribution.ts expose visibility and wrapping, not orientation. Open Editors is movable and supports useful list interactions, but it is a cross-group view rather than the requested group-local tab surface. The accessibility requirements at https://github.com/microsoft/vscode/issues/108264#issuecomment-2259375086 explain why that workaround is incomplete. The remaining uncertainty is the product contract for placement, configuration scope, and collapse behavior; preserve existing editor models and horizontal interactions, and do not expand this into the separate grouping request at https://github.com/microsoft/vscode/issues/100335.
- **Open decisions:**
  - Should vertical orientation be selected for the whole window or independently for each editor group?
  - Which placements should the initial vertical mode support: left, right, or both sides of an editor group?
  - Should vertical tabs remain expanded, offer explicit collapse, or automatically collapse and expand on interaction, and how should that behavior preserve accessible navigation?

These settings can hide tabs or expose more rows, but do not provide a vertical tab layout.
- **Current editor tab implementation:** src/vs/workbench/browser/parts/editor/editorTitleControl.ts:63-79 selects NoEditorTabsControl, SingleEditorTabsControl, MultiRowEditorControl, or MultiEditorTabsControl. MultiEditorTabsControl.createTabsScrollbar in src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts:325-340 enables horizontal scrolling, hides vertical scrolling, and maps vertical wheel movement to horizontal scrolling.
- **Layout boundary:** src/vs/workbench/browser/parts/editor/editorGroupView.ts:2233-2253 lays out the title across the group width and subtracts its height from the editor pane. Native vertical tabs would require considering group geometry as well as tab rendering; this is not merely an undiscovered tab-position setting.
