# Issue #141761 — Some default shortcuts don't work with non-english layout: `cmd + .`, etc

[https://github.com/microsoft/vscode/issues/141761](https://github.com/microsoft/vscode/issues/141761)

## Summary

Keep open for improved punctuation-key fallback when switching input layouts. Current source retains character-based defaults and missing-letter fallbacks, while the maintainer explicitly considered punctuation fallbacks; neither the related Colemak report nor the layout-specific keymap proposal establishes a duplicate under the re-review rules.

## Change summary

Keep default punctuation shortcuts usable across input-layout changes without requiring users to rewrite each binding as a scan code.

## Best solution

Define and implement conservative punctuation fallback semantics in the keyboard mapper while preserving intentional character-based shortcuts on German, French, and Dvorak layouts. Use this issue for that behavior, including the terminal-toggle case already consolidated here, rather than replacing every default with US physical-key bindings.

Acceptance must cover both successful fallback and conflicts with existing bindings.
- **Trace:**

  > QuickFixAction in src/vs/editor/contrib/codeAction/browser/codeActionCommands.ts registers a character-based Period binding. MacLinuxKeyboardMapper in src/vs/workbench/services/keybinding/common/macLinuxKeyboardMapper.ts builds layout mappings and synthesizes missing Latin letters, but its missingLatinLettersOverride does not extend to punctuation. keyboard.dispatch already defaults to code; that controls event dispatch rather than making all defaults physical-position bindings. The maintainer proposed punctuation heuristics at https://github.com/microsoft/vscode/issues/141761#issuecomment-1024685783 and consolidated terminal-toggle behavior at https://github.com/microsoft/vscode/issues/151900#issuecomment-1156389988. Preserve layout-native character semantics and explicit user bindings; a global conversion to US scan codes is not an agreed solution. The uncertainty starts at when fallback should activate and how competing bindings should behave.
- **Open decisions:**
  - Should punctuation fallback activate only when the layout cannot produce the character at all, or also when producing it requires additional modifiers that make the default shortcut impractical?
  - When a physical fallback conflicts with a layout-native shortcut or an explicit user binding, which behavior takes precedence?
