# Issue #255498 — Unable to select New Window with Profile when windows are minimized

[https://github.com/microsoft/vscode/issues/255498](https://github.com/microsoft/vscode/issues/255498)

## Summary

The bug remains source-reproducible on current main: macOS rebuilds the native menu with ordinary renderer actions disabled whenever no main window has focus, which includes the all-windows-minimized state. The accepted Backlog bug should remain open.

## Change summary

On macOS, minimizing every VS Code window disables all profile choices under File > New Window with Profile.

## Best solution

Allow profile-opening menu actions to remain enabled and execute through the last active minimized window, while preserving the safeguards that disable renderer actions when focus is absent for other reasons such as a modal dialog.

## Plan brief

- **Likely files:** `src/vs/platform/menubar/electron-main/menubar.ts`, `src/vs/workbench/contrib/userDataProfile/browser/userDataProfile.ts`
- **Validation:** On macOS with at least two profiles, minimize every VS Code window, verify File > New Window with Profile keeps each profile selectable, and confirm choosing one opens a window with that profile; also verify renderer-dependent menu commands remain disabled when focus is absent because a modal dialog is active.
- **Behavior:**

  > When all VS Code windows are minimized on macOS, File > New Window with Profile must continue to list enabled profile choices. Selecting a profile must open a new window using that profile without requiring an existing window to be restored first. Native-menu safeguards for genuinely unavailable renderer commands must remain intact.
- **Trace:**

  > The profile entries are dynamic actions registered in `OpenProfileMenu` by `registerNewWindowAction` in src/vs/workbench/contrib/userDataProfile/browser/userDataProfile.ts. In src/vs/platform/menubar/electron-main/menubar.ts, `onDidChangeWindowFocus` treats the lack of a focused window as `noActiveMainWindow`, and `setMenu` disables all actions without fallback handlers in that state. `runActionInRenderer` already supports dispatching through the last active minimized window, following https://github.com/microsoft/vscode/commit/c15b51130196de80af27aebd34a1cf1646d2f5af, so the observed failure occurs at menu enablement before dispatch. The uncertainty begins at safely distinguishing an all-minimized state from other no-focus states protected for https://github.com/microsoft/vscode/issues/11928 and https://github.com/microsoft/vscode/issues/25907; do not broadly enable commands in every no-focus state.

## Evidence

- **current source:** src/vs/platform/menubar/electron-main/menubar.ts sets `noActiveMainWindow` when `BrowserWindow.getFocusedWindow()` is absent (lines 253-260), then `setMenu` disables every non-fallback action in that state (lines 509-539). Minimizing all macOS windows therefore disables the profile submenu actions before they can be invoked.
- **profile action path:** src/vs/workbench/contrib/userDataProfile/browser/userDataProfile.ts registers each profile as a dynamic action in `OpenProfileMenu` (lines 282-320), and those actions have no main-process fallback handler.
- **existing minimized-window routing:** src/vs/platform/menubar/electron-main/menubar.ts already makes `runActionInRenderer` target the last active window when it is minimized (lines 780-792), but the disabled menu item prevents this routing from being reached.
- **historical precedent:** https://github.com/microsoft/vscode/commit/c15b51130196de80af27aebd34a1cf1646d2f5af fixed https://github.com/microsoft/vscode/issues/63000 by routing native-menu commands to the last active minimized window; the present issue exposes the remaining enablement gap for dynamic profile actions.
- **canonical search:** No open older issue was found with the same reporter-observable symptom; https://github.com/microsoft/vscode/issues/63000 is closed and covered the broader command-dispatch failure rather than this currently disabled profile submenu.
