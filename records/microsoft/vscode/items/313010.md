# Issue #313010 — Profiles: "Use for New Windows" option does not persist on non-default profiles

[https://github.com/microsoft/vscode/issues/313010](https://github.com/microsoft/vscode/issues/313010)

## Summary

The report describes a credible Profiles editor state-sync bug, and the relevant path remains unchanged on current main. Keep it open and route it to user profiles; the persisted setting works, but the checkbox does not reliably reflect it.

## Change summary

The Profiles editor forgets the visible “Use for New Windows” selection for non-default profiles even though new windows continue using the selected profile.

## Best solution

Make the profile editor consistently derive the checkbox state from the persisted application-scoped `window.newWindowProfile` value, without changing the already-correct new-window profile selection behavior, and add regression coverage for reopening the editor.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditorModel.ts`, `src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditor.ts`, `src/vs/workbench/common/configuration.ts`, `src/vs/workbench/services/configuration/test/browser/configurationService.test.ts`
- **Validation:** In a development build, create a non-default profile, enable “Use for New Windows,” close and reopen the Profiles editor, and verify that profile remains checked and a new window uses it; repeat after reload and when viewing Profiles from another active profile.
- **Behavior:**

  > Selecting “Use for New Windows” on a non-default profile must remain visibly selected after closing and reopening the Profiles editor and after reloading VS Code. Newly opened windows must continue using that profile. Selecting another profile must move the checked state to that profile, and the setting's existing active-window fallback behavior must remain unchanged.
- **Trace:**

  > The persisted setting is `window.newWindowProfile`, registered as application-scoped in src/vs/workbench/common/configuration.ts. `UserDataProfileElement` in src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditorModel.ts compares that value with each profile name during construction and configuration changes; `UseAsDefaultProfileRenderer` in src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditor.ts renders the checkbox from `isNewWindowProfile`. The reporter confirms the setting affects new windows, narrowing the defect to editor model or renderer synchronization rather than persistence or window creation. The uncertainty starts at runtime lifecycle ordering: current source reads as though the checkbox should reflect the value, so reproduce while tracing configuration events and model recreation. Do not change new-window selection semantics or fold in the separate fallback-label discussion from https://github.com/microsoft/vscode/issues/255995.

## Evidence

- **reported reproduction:** The reporter reproduced the mismatch on VS Code 1.118.0-insider: selecting a non-default profile affects newly opened windows, but reopening Profiles shows its checkbox unchecked.
- **current source path:** src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditorModel.ts initializes and refreshes `isNewWindowProfile` by comparing `window.newWindowProfile` with `profile.name`, while src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditor.ts renders the checkbox solely from that model property.
- **persistence boundary:** src/vs/workbench/common/configuration.ts registers `window.newWindowProfile` with `ConfigurationScope.APPLICATION`; configuration service tests confirm application-scoped values are stored in and read from the default profile even while a non-default profile is active.
- **no fixing change found:** The only post-report commit touching the profile editor path, https://github.com/microsoft/vscode/commit/acc18a057fe17240b99f53443660dca3d74137c9, only filters internal Agents Window profiles and does not change the setting or checkbox synchronization.
- **related issue:** https://github.com/microsoft/vscode/issues/255995 is older and open, but concerns whether the checkbox may be unchecked and what fallback profile is used; it does not report this persisted-value/display mismatch and is not a valid duplicate canonical.
