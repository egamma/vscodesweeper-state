# Issue #173411 — Make history service work with debounced editor events

[https://github.com/microsoft/vscode/issues/173411](https://github.com/microsoft/vscode/issues/173411)

## Summary

Keep open: current history processing still reads mutable editor state, so the prerequisite for safely restoring deferred processing remains missing. The related emitter fix does not resolve this separate history-service requirement.

## Change summary

Make editor history processing safe for debounced events without reading editor state that may have changed before processing.

## Best solution

Allow history processing to be deferred while preserving the originating editor, selection, event order, and navigation semantics. Establish the event-lifetime boundary before restoring batching, particularly across editor switches, disposal, and history navigation.

## Plan brief

- **Likely files:** `src/vs/workbench/services/history/browser/historyService.ts`, `src/vs/workbench/common/editor.ts`, `src/vs/workbench/browser/parts/editor/textEditor.ts`, `src/vs/workbench/services/history/test/browser/historyService.test.ts`
- **Validation:** Extend the historyService browser tests with deferred selection processing followed by an editor switch or disposal, asserting the originating editor and selection remain correct. Exercise successive Go to Definition actions followed by Go Back in Navigation Locations as described in https://github.com/microsoft/vscode/issues/173109, and verify the starting file remains reachable; compare synchronous keypress history work before and after.
- **Behavior:**

  > History processing should support deferred editor events without attributing an earlier event to a later editor or selection. Rapid selection changes, editor switches, and editor disposal must not lose meaningful navigation locations or corrupt Go Back, Go Forward, and last-edit navigation. Acceptance includes reaching the original file after successive Go to Definition actions and correctly retaining originating selections when processing occurs after an editor switch. The performance benefit must not come at the expense of these existing behaviors.
- **Trace:**

  > HistoryService.registerListeners and onDidActiveEditorChange currently process editor notifications directly in src/vs/workbench/services/history/browser/historyService.ts. EditorNavigationStack.notifyNavigation reads the pane's current input, group, and selection; IEditorPaneSelectionChangeEvent in src/vs/workbench/common/editor.ts carries only a reason, and AbstractTextEditor emits that reason-only payload. This establishes the remaining dependency on mutable pane state, but the trace has not enumerated all selection-aware editor implementations or established safe deferred behavior during stack navigation and disposal. Preserve existing navigation scopes, selection comparisons, and transient-editor exclusions; file-watcher deletion handling is a separate concern. https://github.com/microsoft/vscode/pull/163845 documents the performance motivation, while https://github.com/microsoft/vscode/issues/173109 supplies the regression acceptance case. The emitter defect fixed through https://github.com/microsoft/vscode/pull/173341 does not settle the history-state lifetime problem.
