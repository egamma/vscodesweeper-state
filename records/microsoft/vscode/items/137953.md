# Issue #137953 — Break all processes when one process breaks (mult-target debugging)

[https://github.com/microsoft/vscode/issues/137953](https://github.com/microsoft/vscode/issues/137953)

## Summary

This accepted Backlog feature request remains necessary: users still need compound or multi-target debugging to pause every active debug target when one target stops, and the 26 upvotes plus a recent independent use case show sustained demand.

## Change summary

Allow a compound or multi-target debug session to pause all participating processes when any one process hits a breakpoint or otherwise stops.

## Best solution

Define an opt-in compound-debugging policy that reacts to one session's stopped event by pausing the other active sessions, while preserving today's independent-session behavior by default and accounting for adapters that cannot pause.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/common/debug.ts`, `src/vs/workbench/contrib/debug/common/debugModel.ts`, `src/vs/workbench/contrib/debug/browser/debugService.ts`, `src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts`
- **Validation:** Add debug service tests with two compound child sessions: when the opt-in policy is enabled and one session reports stopped, the other running session receives a pause request; verify the default policy leaves it running and unsupported or already-stopped sessions are handled without disrupting the originating stop.
- **Behavior:**

  > A compound or multi-target debug launch can opt into coordinated suspension. When any participating target stops, every other running participant is asked to pause so their stacks and variables can be inspected near the same point in time. Existing compounds remain independent by default. Acceptance must cover two active targets, default behavior, and a target that cannot be paused.
- **Trace:**

  > The request belongs to workbench debug-session coordination rather than any one debug adapter: one session's stopped event must be associated with its compound peers and translated into pause requests for the running peers. Likely coordination surfaces are DebugService and DebugModel in src/vs/workbench/contrib/debug/browser/debugService.ts and src/vs/workbench/contrib/debug/common/debugModel.ts, with the public configuration contract near src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts and src/vs/workbench/contrib/debug/common/debug.ts. Preserve independent multi-target behavior unless the user opts in, and do not require adapters to fabricate breakpoints or change DAP stepping semantics. https://github.com/microsoft/vscode/issues/207356 is related compound infrastructure but tracks dynamic launch creation, not coordinated suspension.
- **Open decisions:**
  - Should coordinated suspension be configured on a compound, on an individual launch configuration, or as a workspace-wide debugging policy?
  - Which stop reasons should trigger peer suspension: breakpoint stops only, or every DAP stopped event including exceptions, pauses, and entry stops?
  - When a peer adapter does not support pause or a peer fails to pause, should VS Code continue best-effort and surface a notification, or treat coordinated suspension as failed?
