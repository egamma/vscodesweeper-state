# Issue #301692 — After renaming a file from the directory tree, blank lines are continuously inserted in open file

[https://github.com/microsoft/vscode/issues/301692](https://github.com/microsoft/vscode/issues/301692)

## Summary

Keep open as a confirmed, platform-sensitive Explorer rename bug. Multiple extension-disabled reports reproduce continuous Enter input on Fedora/KDE/Wayland, and current main still removes the rename input during the Enter keydown before its keyup arrives.

## Change summary

Confirming an Explorer file rename with Enter can leave Enter repeating into the reopened editor, continuously inserting blank lines.

## Best solution

Ensure the Explorer rename flow consumes the confirmation keystroke and preserves a coherent keyboard lifecycle when replacing the rename input and refocusing the editor. Reproduce on Fedora/KDE/Wayland and add coverage around the inline rename keyboard-event boundary.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** On Fedora KDE Wayland, open a file larger than 500 KiB, rename it from Explorer with F2 and Enter, then focus the editor; repeated runs must never insert blank lines without further input. The plan should also establish an Explorer view test that verifies the Enter confirmation event cannot leak beyond the inline rename control.
- **Behavior:**

  > Confirming an Explorer file rename with Enter must perform exactly one rename and must not carry Enter input into the reopened or refocused editor. Clicking into the editor after the rename must not insert blank lines until the user deliberately types. Acceptance should cover repeated renames of an open large file on Fedora/KDE/Wayland with extensions disabled and preserve mouse-based rename confirmation.
- **Trace:**

  > In src/vs/workbench/contrib/files/browser/views/explorerViewer.ts, the inline rename KEY_DOWN listener calls done() for Enter; done() disposes and removes the focused input immediately, before the registered KEY_UP listener can observe release. The handler does not consume the event, unlike comparable inline editors in the workbench. The resulting onFinish path reaches renameHandler in src/vs/workbench/contrib/files/browser/fileActions.ts, applies the resource move, and clears editable state while focus may return to the open editor. Multiple Fedora/KDE/Wayland users reproduced the symptom with extensions disabled, but one later report became unable to reproduce after an unidentified Fedora or VS Code update. The plan should first determine whether input disposal before keyup, event propagation, or an Electron/Wayland repeat-state interaction is responsible; it must not alter rename validation, mouse-based completion, or general editor Enter handling. The newer same-symptom report https://github.com/microsoft/vscode/issues/305132 is related evidence, not an eligible canonical for this re-reviewed issue.

## Evidence

- **independent reproductions:** The original report used --disable-extensions, and comments independently reproduced the same behavior through VS Code 1.119.0 on Fedora/KDE/Wayland; one commenter found files larger than 500 KiB made it easier to trigger.
- **current source path:** src/vs/workbench/contrib/files/browser/views/explorerViewer.ts:1117-1143 handles Enter on KEY_DOWN by calling done(), which disposes and removes the focused rename input before KEY_UP; unlike comparable inline editors, this handler does not preventDefault() or stopPropagation().
- **rename operation:** src/vs/workbench/contrib/files/browser/fileActions.ts:997-1032 applies the resource rename and clears editable state, causing the open editor and focus context to update while the confirmation key is still active.
- **related report:** https://github.com/microsoft/vscode/issues/305132 reports the same observable symptom, but it was created after this issue. Because this is a re-reviewed item, the newer report cannot serve as its duplicate canonical.
- **resolution remains uncertain:** The latest commenter reported that a recent Fedora or VS Code update appeared to resolve the problem locally, but could not identify which component changed; the unsafe keydown lifecycle remains present on current main.
