# Issue #127674 — Extension bisect does not consider "dependent" extensions when choosing what to disable

[https://github.com/microsoft/vscode/issues/127674](https://github.com/microsoft/vscode/issues/127674)

## Summary

Dependency-aware extension bisect is still missing: current source partitions extension IDs without considering which remaining extensions require them. Keep this accepted Backlog request open; the maintainer discussion identifies an available dependency helper, but the bisect strategy still needs design.

## Change summary

Make extension bisect account for dependencies so disabling one candidate does not silently prevent other candidates from running.

## Best solution

Make bisect trials dependency-aware while retaining reliable culprit identification and restoring the original enablement state when stopped. Establish how shared dependencies affect trial membership and final attribution before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensionManagement/browser/extensionBisect.ts`, `src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts`, `src/vs/platform/extensionManagement/common/extensionManagementUtil.ts`, `src/vs/workbench/services/extensionManagement/test/browser/extensionEnablementService.test.ts`
- **Validation:** Add runnable bisect service tests using B→A and Y→X with ordering [B, Y, A, X], exercising persisted state across successive trials. Verify that retained candidates have their required dependencies available, the initial all-disabled control remains valid, culprit reporting follows the agreed semantics, and stopping restores prior enablement. Include a shared-dependency case and run the targeted extension-management unit tests.
- **Behavior:**

  > Extension bisect currently can disable A and X while nominally retaining B and Y, even though B requires A and Y requires X; the retained candidates consequently cannot run. Dependency-aware trials should preserve the dependencies needed by candidates being tested rather than treating indirectly disabled extensions as active evidence. Acceptance must cover the supplied two-pair example, shared dependencies, completion attribution, and restoration after stopping. Preserve the intentional initial all-disabled control.
- **Trace:**

  > ExtensionBisectService in src/vs/workbench/services/extensionManagement/browser/extensionBisect.ts persists an ordered ID array and low/high/mid indices, then constructs its disabled map solely from the selected interval. The start command supplies currently enabled user extensions, with no dependency ordering or grouping. ExtensionEnablementService._computeEnablementState and _isDisabledByExtensionDependency in src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts propagate bisect disablement to dependents, confirming the reported mismatch between nominal and effective trial membership. getExtensionDependencies in src/vs/platform/extensionManagement/common/extensionManagementUtil.ts supplies transitive dependency information, as the maintainer discussion at https://github.com/microsoft/vscode/issues/127674 already notes. Preserve ordinary dependency enforcement, remote-resolver and environment-enabled exceptions, and users' pre-bisect enablement choices. The unresolved boundary is how dependency-aware trials distinguish a faulty dependency from a faulty dependent when retaining the dependent necessarily retains both.
- **Open decisions:**
  - When a retained candidate requires an extension excluded by the nominal split, should the trial retain that dependency or test the dependency-connected extensions as a group?
  - If a dependency group is isolated but a single culprit cannot yet be distinguished, should bisect report the group or continue dependency-preserving trials until it can attribute one extension?
