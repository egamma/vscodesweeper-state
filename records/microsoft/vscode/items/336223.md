# Issue #336223 — Feature Request: Provide Cursor-like Code Edit Review UI and Extension API

[https://github.com/microsoft/vscode/issues/336223](https://github.com/microsoft/vscode/issues/336223)

## Summary

The native review UI already exists; the missing public extension access is tracked by an older, verified open issue. Consolidate this request there, preserving its general-purpose API requirements and concurrency discussion.

## Change summary

Expose native per-change Keep/Undo, navigation, bulk review actions, and undo/redo integration through a public API for extension-generated edits.

## Best solution

Consolidate public access to the existing edit-review experience under https://github.com/microsoft/vscode/issues/279040. Its API design should cover general extension edits and resolve ownership, overlapping edits, and session lifetime before finalization.

## Evidence

- **Verified older canonical:** https://github.com/microsoft/vscode/issues/279040 is OPEN, created 2025-11-23, before this report. It requests public access to tracked edits with Keep/Undo and is titled "Allow to use `applyEdit` w/ AI-review UI from tools and also refactorings".
- **Same observable gap:** The canonical reports that extension edits cannot use the native Keep/Undo experience. https://github.com/microsoft/vscode/issues/279040#issuecomment-3700150061 explicitly requests native inline review for other coding agents and rejection of individual changes; https://github.com/microsoft/vscode/issues/279040#issuecomment-4061210419 explicitly broadens the wording to extensions using the built-in review UI. This matches the missing capability here, rather than merely sharing an area or root cause.
- **Existing native capability:** src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingEditorActions.ts implements per-hunk Keep/Undo through AcceptRejectHunkAction, registers chatEditor.action.navigateNext and chatEditor.action.navigatePrevious, and provides bulk review actions. chatEditingActions.ts registers chatEditing.acceptAllFiles and chatEditing.discardAllFiles. chatEditingSession.ts implements accept/reject and checkpoint undo/redo. The requested UI does not need to be invented anew.
- **Public API boundary:** src/vscode-dts/vscode.d.ts exposes workspace.applyEdit and WorkspaceEditEntryMetadata.needsConfirmation, but not a general native tracked-edit review session. ChatResponseTextEditPart, ChatResponseStream.textEdit, and externalEdit remain in vscode.proposed.chatParticipantAdditions.d.ts. Existing confirmation metadata and proposed chat-specific APIs do not fully satisfy the requested stable, general-purpose API.
- **Canonical design direction:** https://github.com/microsoft/vscode/issues/279040#issuecomment-3580195354 proposes opting workspace.applyEdit into the native review UI; https://github.com/microsoft/vscode/issues/279040#issuecomment-3581622492 specifies preserving its current default behavior. This is the same extension-access work, not evidence that it has already shipped.
- **Details to preserve:** https://github.com/microsoft/vscode/issues/336223#issuecomment-5676962755 reports a working fork prototype and proposes exclusive review sessions. https://github.com/microsoft/vscode/issues/336223#issuecomment-5676260034 and https://github.com/microsoft/vscode/issues/336223#issuecomment-5685445383 raise edit attribution, overlapping edits, and lock lifetime concerns. These are design inputs to the same public review API, not a separately demonstrated defect.
