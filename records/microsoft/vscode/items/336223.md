[https://github.com/microsoft/vscode/issues/336223](https://github.com/microsoft/vscode/issues/336223)

## Summary

The public edit-review API gap is already tracked by the older, open issue https://github.com/microsoft/vscode/issues/279040. Its discussion explicitly covers third-party agents using native inline Keep/Undo controls, and its scope includes tools and refactorings.

## Change summary

Expose native, granular code-edit review with navigation, bulk acceptance/rejection, and undo/redo integration through a public extension API.

- **Same observable limitation:** https://github.com/microsoft/vscode/issues/279040#issuecomment-3700150061 explicitly requests the native inline Keep/Undo experience for other coding agents, including rejecting individual lines while editing in the normal editor. https://github.com/microsoft/vscode/issues/279040#issuecomment-4061210419 explicitly describes the request as allowing extensions to use the built-in AI edit-review UI. These establish the same user-visible API gap, not merely a related implementation area.
- **Existing capability and remaining gap:** src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingEditorActions.ts implements file-level and per-hunk Keep/Undo actions and change navigation; chatEditingActions.ts contains bulk Keep/Undo actions. However, ChatResponseStream.textEdit() and externalEdit() are declared in src/vscode-dts/vscode.proposed.chatParticipantAdditions.d.ts, not the stable API. The stable workspace.applyEdit() signature and WorkspaceEditMetadata in src/vscode-dts/vscode.d.ts do not expose a general native tracked-review session. Existing internal UI therefore does not satisfy the public API request.
- **Discussion to preserve:** https://github.com/microsoft/vscode/issues/336223#issuecomment-5676962755 reports a working fork prototype and proposes exclusive review sessions. https://github.com/microsoft/vscode/issues/336223#issuecomment-5676260034 and https://github.com/microsoft/vscode/issues/336223#issuecomment-5685445383 raise overlapping-edit attribution and abandoned-session liveness concerns. These are design considerations for the same API, not evidence of a separate capability.
