# Issue #242735 — SCM Graph - Allow branch merge in git graph

[https://github.com/microsoft/vscode/issues/242735](https://github.com/microsoft/vscode/issues/242735)

## Summary

The requested graph-context merge action remains missing, as do the reset and revert actions added in the discussion. Older related requests overlap, but neither establishes a full-scope canonical under the stronger re-review duplicate bar.

## Change summary

Allow merging into the current branch, resetting, and reverting directly from a commit's Source Control Graph context menu.

## Best solution

Support these operations through the built-in Git graph, preserving existing Git safeguards and clearly identifying each operation's target. A maintainer should settle selected-commit versus branch-tip merge semantics and the scope of reset before implementation.

## Plan brief

- **Likely files:** `extensions/git/package.json`, `extensions/git/src/commands.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/git.ts`
- **Validation:** In a disposable Git repository with divergent branches, invoke the proposed graph actions and verify the resulting HEAD, ancestry, working tree, and index. Include selecting a non-tip commit, cancelling each operation, a merge conflict, and each approved reset mode; confirm existing quick-pick merge and graph cherry-pick behavior remain unchanged.
- **Behavior:**

  > Users should be able to initiate a merge into their current branch from another branch's commit in the Source Control Graph, without independently selecting the target again through an unrelated picker. The reporter also requests reset and revert from that context menu. Acceptance should verify that the chosen operation targets exactly the commit or branch described by its UI, cancellation leaves repository state unchanged, and conflicts retain the existing resolution experience. Reset modes and their destructive effects must be explicit.
- **Trace:**

  > extensions/git/package.json defines scm/historyItem/context and scm/historyItemRef/context; neither currently exposes merge, reset, or commit revert. Commands.merge in extensions/git/src/commands.ts obtains references and prompts for a branch or tag, so the existing git.merge capability does not consume the selected graph commit. Repository and Git operation layers are in extensions/git/src/repository.ts and extensions/git/src/git.ts; existing revert-named methods include file-change discard behavior and must not be assumed to implement git revert of a commit. Preserve existing quick-pick merge, graph cherry-pick, and conflict handling. Related https://github.com/microsoft/vscode/issues/217987 owns explicitly requested reset/revert context actions, while https://github.com/microsoft/vscode/issues/225029 contains broader graph-operation feedback. The unresolved product boundary is whether a commit-context merge targets that exact revision or a containing branch's current tip, and which reset modes are exposed.
- **Open decisions:**
  - When a non-tip commit on another branch is selected, should Merge into Current Branch merge that exact revision or the containing branch's current tip?
  - Which reset modes should the graph expose, and what confirmation should precede operations that discard working-tree or index changes?
