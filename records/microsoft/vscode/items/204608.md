- **Likely files:** `src/vs/workbench/contrib/searchEditor/browser/searchEditor.ts`, `src/vs/workbench/contrib/search/common/constants.ts`, `src/vs/workbench/contrib/searchEditor/test/browser/searchEditorModel.test.ts`
- **Validation:** In a workspace containing a known matching string, leave the Search view empty, run search.action.openNewEditorToSide, search for that string, and inspect context keys inside both the Search Editor query widget and results editor: hasSearchResult should be true. Repeat with a query yielding no matches and expect false. Switch between Search Editors and the Search view to verify independent result state. Establish a browser regression test for these context transitions before implementation.
- **Behavior:**

  > A search run directly in a Search Editor can produce matches while hasSearchResult remains false. Result availability should be accurate when inspecting context within that Search Editor, including its query widget and results editor. Matching and nonmatching searches must produce the corresponding true and false values without changing the independent Search view's result state. Existing next/previous-result navigation must remain functional.
- **Trace:**

  > SearchContext.HasSearchResults is declared in src/vs/workbench/contrib/search/common/constants.ts; the inspected binding and updates belong to SearchView in search/browser/searchView.ts. SearchEditor owns a separate SearchModelImpl, and its triggerSearch, doRunSearch and onSearchComplete methods in searchEditor/browser/searchEditor.ts never update that context key. SearchEditor.createEditor already establishes a scoped context for inSearchEditor, while setInput can replace an input without clearInput. HasSearchResults also gates Search-view-specific actions, so preserve their existing model ownership and behavior. The existing searchEditorModel.test.ts does not cover the editor context lifecycle; the planning session should establish a runnable regression check rather than assume model tests exercise this path.

## Evidence

- **Current source confirms the reported trigger:** src/vs/workbench/contrib/search/common/constants.ts declares hasSearchResult with a false default. SearchView binds it in searchView.ts:258 and updates it from its own result file count in updateSearchResultCount at line 2063. A direct Search Editor search instead follows SearchEditor.triggerSearch → doRunSearch → onSearchComplete using a separate SearchModelImpl; that path updates the result text and match ranges but never binds or sets HasSearchResults.
- **Existing navigation does not cover the context contract:** src/vs/workbench/contrib/search/browser/searchActionsNav.ts explicitly enables next/previous-result navigation with hasSearchResult OR inSearchEditor. This supports navigation in Search Editors but does not make hasSearchResult reflect their results. searchActionsTopBar.ts also uses HasSearchResults for Search-view-specific commands, so changing global ownership could affect unrelated commands.
- **Scoped context precedent:** SearchEditor.createEditor in src/vs/workbench/contrib/searchEditor/browser/searchEditor.ts binds inSearchEditor to the editor's scoped context service. https://github.com/microsoft/vscode/issues/120699#issuecomment-832293510 explains the query widget's scoped-context parenting; that closed infrastructure issue does not establish a fix for missing result availability.
