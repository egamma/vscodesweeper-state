# Issue #281575 — SCM: Stashes, branches and tags show multiple times when using worktrees

[https://github.com/microsoft/vscode/issues/281575](https://github.com/microsoft/vscode/issues/281575)

## Summary

Keep open: the repository explorer still presents shared Git artifacts separately under each worktree. This team-authored, accepted UX concern needs a decision about shared artifact presentation and worktree-specific action context; no verified fix or qualifying canonical was found.

## Change summary

Avoid repeating the same branches, tags, and stashes across repository entries when worktrees are open.

## Best solution

Present shared repository artifacts without redundant trees while retaining access to individual worktrees and making the target of stash and checkout actions clear. Settle that interaction model in the SCM repository explorer before implementation.

- **Likely files:** `src/vs/workbench/contrib/scm/browser/scmRepositoriesViewPane.ts`, `extensions/git/src/artifactProvider.ts`, `extensions/git/src/repository.ts`
- **Validation:** In the normal workbench, enable scm.repositories.explorer and single repository selection, open a main repository with two linked worktrees, and create a branch, tag, and stash. Verify the agreed shared-artifact presentation avoids redundant trees, preserves selection of each worktree, and applies stash and checkout actions to the visibly indicated target. Repeat with only a linked worktree open and with two unrelated repositories.
- **Behavior:**

  > With the repository explorer enabled, creating and opening linked worktrees repeats the shared branches, tags, and stashes under separate repository entries. The goal is to remove that redundancy without losing access to individual worktrees or making actions ambiguous. Acceptance must cover a main repository with multiple linked worktrees, a standalone linked-worktree workspace, and unrelated repositories that must remain separate. Stash application and branch checkout must retain an explicit, understandable worktree target.
- **Trace:**

  > RepositoryTreeDataSource.getChildren in src/vs/workbench/contrib/scm/browser/scmRepositoriesViewPane.ts flattens parent and child repositories in explorer mode and obtains artifact groups separately for every repository. extensions/git/src/repository.ts constructs a GitArtifactProvider for each worktree despite recording its parent source control. extensions/git/src/artifactProvider.ts exposes the same artifact categories for all normal-workbench repositories, and branch HEAD indicators remain worktree-specific. This establishes the redundant presentation without executing VS Code, but does not settle how a shared tree should select an action target. Preserve independent worktree changes and selection, keep unrelated repositories separate, and do not extend this work into the Agents window, where artifact groups are already disabled. The original test context is https://github.com/microsoft/vscode/issues/280326; https://github.com/microsoft/vscode/issues/257396 concerns different naming and discovery behavior, not this presentation gap.
- **Open decisions:**
  - Should shared branches, tags, and stashes appear once beneath a repository-family node, or remain attached to a selected worktree with redundant trees suppressed?
  - If artifacts are presented once for a repository family, should stash and checkout actions target the selected worktree or require an explicit worktree choice?
