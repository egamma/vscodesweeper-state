# Issue #241683 — Failure to use code.cmd --install-extension <valid extension id> behind authenticating proxy server

[https://github.com/microsoft/vscode/issues/241683](https://github.com/microsoft/vscode/issues/241683)

## Summary

Keep open: the reporter supplied sufficient steps and a concrete HTTP 407 response to retest authenticated CLI installation. Current source still uses a different network path from the UI, with no automatic Kerberos challenge handling in that request path; the Windows proxy environment was not available to verify current behavior.

## Change summary

Installing extensions from the CLI fails behind a Kerberos-authenticating proxy while installation through the UI works.

## Best solution

Make CLI extension installation work with the supported authenticated-proxy configuration and report authentication failures accurately rather than presenting valid extension IDs as missing. Preserve the documented precedence of an explicit http.proxy setting over environment-variable defaults.

## Evidence

- **Reporter diagnosis:** https://github.com/microsoft/vscode/issues/241683#issuecomment-2710295248 supplies the configured http.proxy, successful UI behavior, the CLI command, and a Marketplace query returning HTTP 407 with NEGOTIATE and NTLM challenges. The report is actionable without another request for basic reproduction details.
- **Current CLI network path:** src/vs/code/node/cliProcessMain.ts constructs the Node RequestService for the CLI. In src/vs/platform/request/node/requestService.ts, request() selects a proxy agent and optionally supplies configured Proxy-Authorization, but does not invoke lookupKerberosAuthorization() or perform a 407 authentication exchange. src/vs/platform/request/node/proxy.ts constructs HttpProxyAgent or HttpsProxyAgent.
- **UI transport differs:** src/vs/platform/request/electron-utility/requestService.ts overrides the raw request implementation with Electron net.request. Successful UI installation therefore does not establish that the standalone Node CLI supports the same authentication behavior.
- **Misleading error path remains:** In src/vs/platform/extensionManagement/common/extensionGalleryService.ts, queryRawGalleryExtensions() converts HTTP 400–499 responses, including 407, into an empty gallery result. src/vs/platform/extensionManagement/common/extensionManagementCLI.ts obtains installation candidates from that gallery service and defines the reported 'Extension ... not found' message.
- **Proxy precedence is documented:** src/vs/platform/request/common/request.ts documents that http_proxy and https_proxy are inherited only when http.proxy is unset. src/vs/platform/request/node/proxy.ts implements options.proxyUrl || getSystemProxyURI(...). The reporter's second claim about environment variables overriding an explicit setting does not match the current contract; it does not invalidate the authentication failure.
- **Older related reports are not verified same-symptom canonicals:** https://github.com/microsoft/vscode/issues/29910 is open and older, but its original symptoms are DNS failure without a configured proxy and installation stalling after successful lookup, not the reported Kerberos 407 lookup failure. https://github.com/microsoft/vscode/issues/239872 concerns UI installation with net::ERR_INVALID_ARGUMENT. https://github.com/microsoft/vscode/issues/12588 requests proxy support for extension-authored network requests. None establishes the same observable symptom required to close this re-reviewed item as a duplicate.
