# Issue #318407 — Device preset should be dropdown?

[https://github.com/microsoft/vscode/issues/318407](https://github.com/microsoft/vscode/issues/318407)

## Summary

Keep open: the device preset control still applies a preset without displaying the current selection. A maintainer explicitly retained this issue for that UX work when closing the related styling report; the control design remains unsettled.

## Change summary

Make the integrated browser's device preset control communicate the selected preset while keeping individual emulation inputs adjustable.

## Best solution

Provide a clearly labeled preset control that reflects the active built-in preset and returns to an unselected/custom state when its settings are edited. Resolve dropdown versus labeled-picker presentation with the browser area owner, keeping custom preset creation and saving separate.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/browserView/electron-browser/features/browserEditorEmulationFeatures.ts`
- **Validation:** In the integrated browser, apply iPhone SE and verify the preset control identifies it; edit width and verify the built-in selection clears while the input remains editable; select Pixel 8 and verify its profile applies and its name is shown. Confirm canceling the picker leaves emulation unchanged and switching browser tabs does not show another tab's selection.
- **Behavior:**

  > The device emulation toolbar should communicate which built-in preset is active rather than exposing only a stateless apply action. Individual emulation inputs remain editable, and modifying a built-in preset returns the control to an unselected/custom state rather than implying that the original preset still matches. Acceptance includes selecting different presets, editing dimensions, canceling selection, and switching browser tabs without stale selection feedback. Custom preset creation, saving, and dirty-state presentation are separate work.
- **Trace:**

  > In src/vs/workbench/contrib/browserView/electron-browser/features/browserEditorEmulationFeatures.ts, PickBrowserDevicePresetAction.run constructs items from DEFAULT_BROWSER_DEVICE_PRESETS and invokes BrowserEditorEmulationSupport.applyPreset, while its BrowserEmulationToolbar menu entry remains a static 'Apply Preset...' action. BrowserEmulationToolbar.refresh updates dimensions, DPR, and scale; BrowserEditorEmulationSupport.onModelAttached invokes it on device changes, but neither path exposes preset identity. This establishes the missing feedback without executing the UI. The reporter settled that inputs remain editable and modified built-in selections clear, but the maintainer left dropdown versus labeled-button presentation open in https://github.com/microsoft/vscode/issues/318404#issuecomment-4733459963. Preserve existing emulation application and scale behavior, and do not expand this work into custom preset persistence tracked by https://github.com/microsoft/vscode/issues/326713.
- **Open decisions:**
  - Should the toolbar expose a persistent preset dropdown, or retain a quick picker behind a labeled control that displays the active preset?
