# Issue #271635 — Workspace trust: sometimes extensions are enabled before a workspace is trusted, then get disabled when I press the trust button

[https://github.com/microsoft/vscode/issues/271635](https://github.com/microsoft/vscode/issues/271635)

## Summary

This should remain open as a confirmed intermittent bug and be routed to extension enablement/configuration owners. The reporter supplied repeated current-version reproductions after the original info request, and a maintainer reproduced the related settings/theme failure.

## Change summary

Granting trust to a fresh local workspace can unload the active theme and leave trust-gated extensions such as built-in Git disabled, sometimes after showing two trust prompts.

## Best solution

Make the trust-grant transition complete consistently across settings persistence and extension-registry updates: trust-gated extensions should become available, the active theme and saved settings should remain intact, and no extension code should activate prematurely.

## Plan brief

- **Likely files:** `src/vs/workbench/services/workspaces/common/workspaceTrust.ts`, `src/vs/workbench/contrib/extensions/browser/extensionEnablementWorkspaceTrustTransitionParticipant.ts`, `src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`
- **Validation:** In a development build, repeatedly open fresh folders under `/tmp` with Synthwave '84 installed and grant trust; over at least 20 iterations, assert that only one trust prompt appears, settings remain saved, the theme remains applied, built-in Git registers a source-control provider after trust, and trust-restricted extension code does not activate before the grant.
- **Behavior:**

  > Opening a fresh untrusted local folder may show the cached theme appearance, but extensions that do not support untrusted workspaces must not activate before trust. After the user grants trust, the active theme and saved settings must remain intact, and trust-gated extensions including built-in Git must become available without reloading. The transition must not produce a second trust prompt or an unsaved settings editor. Validate the behavior across repeated fresh `/tmp` workspaces because the failure is timing-dependent.
- **Trace:**

  > WorkspaceTrustManagementService in src/vs/workbench/services/workspaces/common/workspaceTrust.ts sets the new trust state and awaits registered participants before firing onDidChangeTrust. ExtensionEnablementWorkspaceTrustTransitionParticipant delegates the trusted transition to ExtensionEnablementService.updateExtensionsEnablementsWhenWorkspaceTrustChanges(), which identifies extensions whose states differ between trusted and untrusted workspaces. AbstractExtensionService receives that event, classifies each extension against the new trust state, and invokes its asynchronous _handleDeltaExtensions queue without awaiting completion. The maintainer's reproduction additionally points to a concurrent settings-file write, so the exact failure starts at the boundary between trust transition, configuration persistence, and registry/extension-host delta processing rather than at trust calculation alone. Preserve the existing cached-theme-color behavior before activation and all untrusted-workspace restrictions; do not weaken trust gating. The remote-specific reports https://github.com/microsoft/vscode/issues/128573 and https://github.com/microsoft/vscode/issues/289835 are not the same observable local-workspace failure.

- **expected Git behavior:** extensions/git/package.json declares `capabilities.untrustedWorkspaces.supported` as false, so built-in Git should be absent before trust and added after trust; remaining unavailable after the grant contradicts the intended enablement transition.

Neither is an eligible canonical for this re-reviewed local-workspace symptom.
