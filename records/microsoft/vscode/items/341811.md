# Issue #341811 — Agent host : stale tmp_obj_* files in .git/objects when _stageChangedPaths times out on large untracked files

[https://github.com/microsoft/vscode/issues/341811](https://github.com/microsoft/vscode/issues/341811)

## Summary

Thanks for the detailed report. The source confirms the mechanism: `_stageChangedPaths` runs `git add -A` with the default 5s `_runGit` timeout. On timeout, `_runGit` kills the whole process tree, and git cannot clean up its `tmp_obj_*` files in the real `.git/objects`. The fix has a real design choice (how to bound or isolate the writes), so it needs a maintainer decision first.

## Change summary

A timed-out temp-index `git add -A` in the agent host's git service leaves stale `tmp_obj_*` files in the repo's `.git/objects` when large untracked files are present.

## Best solution

Keep the temp-index staging from leaving partial objects in the user's repo: either write the diff-only staging into a throwaway object directory, or skip or limit very large untracked files and clean up `tmp_obj_*` after a kill. Writes that must persist (checkpoint tree writes) need to keep using the real object store.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentHostGitService.ts`
- **Validation:** A unit test in the agentHostGitService suite that stages a large untracked file with a short timeout and asserts no `tmp_obj_*` files remain under `.git/objects`; it must fail before the change and pass after.
- **Behavior:**

  > Running agent-host diff or checkpoint computation in a repo with a large untracked, non-ignored file must not leave `tmp_obj_*` garbage in `.git/objects`, even when the staging step is cut short. The user's real index and committed state stay untouched, and diff and checkpoint results are unchanged for normal repos.
- **Trace:**

  > `_runWithTempIndex` and `_stageAndWriteTree` both go through `_stageChangedPaths`, which runs `git add -A` with the 5s default and relies on `GIT_INDEX_FILE` only for index isolation. A timeout kills the git process tree via `killTree` in `_runGit`, so git cannot remove its temp object files. Confirmed from source; not executed. Boundary: do not change `_runGit`'s default timeout for other callers, and do not break checkpoint `write-tree` persistence. Uncertainty starts at which mitigation (timeout/size cap vs. object-directory isolation vs. post-kill cleanup) is acceptable.
- **Open decisions:**
  - When a large untracked file makes staging time out, should the diff omit that file, report it as changed without stats, or wait longer?
  - Should there be a size or time cap for untracked files in agent diffs, and what are its default and user-visible behavior?
  - Are checkpoint (write-tree) captures allowed to skip large untracked files, given they must persist objects?

## Evidence

- **no timeout override:** src/vs/platform/agentHost/node/agentHostGitService.ts `_stageChangedPaths` (~L822-836) calls `_runGit(... ['add','-A', '--pathspec-from-file=...'])` with only env set. `_runGit` (~L1371) defaults to `timeoutMs = options?.timeout ?? 5000`.
- **kill path:** `_runGit` timer (~L1418-1423) calls `killTree(child.pid, true)`, a hard kill that lets git do no cleanup. Large untracked files take longer than 5s to hash, so the add is killed mid-write.
- **objects go to the real repo:** `_runWithTempIndex` only sets `GIT_INDEX_FILE` (and `COMMAND_HOOK_LOCK`). Blob writes still go to the repo's `.git/objects`, and `finally` only deletes the temp dir, so stale `tmp_obj_*` files stay behind and the next call retries and leaves more.
- **no existing fix:** No cleanup or larger timeout for this call is present on current main. Reproduction was traced from source only, not executed.
- **other callers:** `_stageAndWriteTree` (checkpoint writes, ~L783) also uses `_stageChangedPaths`, and that path needs its blobs persisted in the real object store, so isolating objects cannot be applied uniformly.
