# Issue #182316 — Git - "fatal: repository not found" exception even when authenticated as repository owner

[https://github.com/microsoft/vscode/issues/182316](https://github.com/microsoft/vscode/issues/182316)

## Summary

Keep open for Git authentication diagnosis: the thread contains independent confirmations and a username-qualified URL workaround, but no verified fix or canonical duplicate. Current source implements automatic GitHub credentials, yet does not establish which credentials Git actually used in the failing environment.

## Change summary

Cloning or pushing to an owned private GitHub repository fails with 'Repository not found' despite being signed into GitHub in VS Code.

## Best solution

Identify whether the failing operation receives credentials from an external Git credential helper or VS Code's built-in GitHub provider, then address the confirmed failing path. Preserve configured credential-helper behavior rather than assuming that adding a username to every clone URL is the correct fix.

## Plan brief

- **Likely files:** `extensions/github/src/remoteSourceProvider.ts`, `extensions/github/src/credentialProvider.ts`, `extensions/github/src/auth.ts`, `extensions/git/src/askpass.ts`, `extensions/git/src/git.ts`
- **Validation:** On a current build, sign into an account owning a private test repository, run Git: Clone > Clone from GitHub, and compare the plain HTTPS URL with the username-qualified URL. Capture redacted Git Trace [Askpass] output and credential-helper configuration; repeat with the helper isolated in a controlled test environment. Acceptance: clone and subsequent fetch/push succeed without embedding a token in the URL, while explicitly configured credential helpers remain respected.
- **Behavior:**

  > The report describes private GitHub clone and push failures despite signing into the repository owner's account, with a username-qualified URL succeeding. Automatic GitHub authentication should supply authorized credentials when Git reaches VS Code's integrated authentication provider. First establish the failure on a current build and distinguish it from an external helper supplying different credentials. Acceptance covers private clone and subsequent fetch/push without token-bearing URLs, while preserving explicitly configured Git authentication.
- **Trace:**

  > GitHub remote selection returns clone_url through GithubRemoteSourceProvider in extensions/github/src/remoteSourceProvider.ts; CloneManager passes it to Git.clone without adding a username. GitHubCredentialProvider obtains a scoped session through getSession and exposes credentials to Askpass, which calls providers on username requests and caches their passwords. Source inspection establishes this intended path but does not establish that it ran in the reported environment, or which credential helper supplied credentials first. The username-qualified workaround is evidence to investigate credential selection, not proof that clone URL construction is defective. https://github.com/microsoft/vscode/issues/158733#issuecomment-1853917507 documents the external-helper boundary. Keep https://github.com/microsoft/vscode/issues/257423's silent-autofetch failure separate unless reproduction proves a shared cause. Do not change helper precedence or silent-fetch prompting as an incidental fix.

## Evidence

- **Confirmed reports:** https://github.com/microsoft/vscode/issues/182316 contains the failing private-repository clone command and a successful username-qualified alternative. Another user confirmed the issue on macOS with VS Code 1.78.0; the original reporter confirmed persistence on December 4, 2023. These establish historical reproduction, not reproduction against today's main.
- **Current clone and authentication paths:** extensions/github/src/remoteSourceProvider.ts selects GitHub's clone_url for HTTPS; extensions/git/src/cloneManager.ts passes that URL to Git.clone in extensions/git/src/git.ts. GitHubCredentialProvider.getCredentials in extensions/github/src/credentialProvider.ts obtains the session from extensions/github/src/auth.ts and returns its account ID and access token. extensions/git/src/askpass.ts invokes credential providers for username requests and caches the corresponding password for the subsequent request.
- **Existing automatic authentication:** extensions/github/package.json registers github.gitAuthentication with default true, and extensions/git/package.json registers git.useIntegratedAskPass with default true. The intended capability already exists; its presence does not prove that the reporter's Git process reached it or received the correct credentials.
- **Suggested related issue is not a verified duplicate:** https://github.com/microsoft/vscode/issues/257423 is open, but its original report explicitly says manual fetch succeeds while autofetch fails. extensions/git/src/askpass-main.ts rejects silent fetch authentication before invoking the provider. That narrower failure does not establish ownership of this report's interactive clone and push failures.
- **Credential-helper precedent:** In https://github.com/microsoft/vscode/issues/158733#issuecomment-1853917507, a maintainer explains that VS Code uses the installed Git executable and participates at the end of its authentication pipeline, after other configured mechanisms such as Git Credential Manager. That related issue was closed awaiting information, not with a demonstrated fix, so it is neither an open canonical nor fix evidence.

The checkout is shallow, and the available file history does not identify a fixing commit. No private-repository operation was executed, and the checkout remained clean.
