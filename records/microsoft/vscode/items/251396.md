# Issue #251396 — Fails to access OS keyring on Windows when signing in, even after clean reinstall and extensive troubleshooting

[https://github.com/microsoft/vscode/issues/251396](https://github.com/microsoft/vscode/issues/251396)

## Summary

Still open and unresolved: on Windows this notification only fires when Electron/Chromium's DPAPI-backed safeStorage reports encryption unavailable, so the root cause sits upstream — but VS Code also leaves Windows users with no fallback, which is worth owning here. Routing to secret-storage rather than closing.

## Change summary

On a clean Windows 11 install with no extensions, signing in fails with "An OS keyring couldn't be identified for storing the encryption related data in your current desktop environment".

## Best solution

Confirm with the reporters' os_crypt logs whether `safeStorage.isEncryptionAvailable()` is returning false (a Chromium/Electron DPAPI failure on those machines) and track it upstream; separately, consider giving Windows users a real escape hatch — today `EncryptionMainService.setUsePlainTextEncryption` throws on Windows and the notification offers only the troubleshooting guide, which documents no Windows configuration issues, so the reporter is left with nothing but `--use-inmemory-secretstorage`.

## Evidence

- **trigger path:** The message comes from NativeSecretStorageService.notifyOfNoEncryption in src/vs/workbench/services/secrets/electron-browser/secretStorageService.ts, reached when the secret storage type is not 'persisted' — i.e. encryption is unavailable. On non-Linux it shows the generic text with only a troubleshooting-guide button.
- **Windows backend is DPAPI:** src/vs/platform/encryption/electron-main/encryptionMainService.ts hardcodes KnownStorageProvider.dplib for Windows and delegates to Electron's `safeStorage`, so the failure is Chromium's OSCrypt/DPAPI on that machine, not VS Code logic.
- **reporter's flag is a no-op here:** `--password-store=wincred` has no effect: the constructor only reacts to the `basic` value, and `setUsePlainTextEncryption()` explicitly throws 'Setting plain text encryption is not supported on Windows.' That explains troubleshooting step 3 and leaves no supported fallback on Windows.
- **no fix on main:** `git log --since=2025-06-01` over src/vs/platform/encryption, src/vs/platform/secrets and src/vs/workbench/services/secrets shows no related change since the report; the code path that produces this notification is unchanged.
- **related, not a canonical:** https://github.com/microsoft/vscode/issues/187338 is the Linux counterpart (labeled upstream/chromium/secret-storage) and does not own the Windows DPAPI case. The only other Windows report, https://github.com/microsoft/vscode/issues/319730, is newer and was closed as info-needed, so it cannot be a canonical.
- **second reporter:** tangturtle confirmed the same blocked sign-in on 2025-07-10 with os_crypt verbose logs attached, so this is not a single-machine anomaly.
