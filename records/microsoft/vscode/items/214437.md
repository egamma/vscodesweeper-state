# Issue #214437 — feature request: open file url without --file-uri flag

[https://github.com/microsoft/vscode/issues/214437](https://github.com/microsoft/vscode/issues/214437)

## Summary

Keep this accepted CLI request open: current source still treats positional arguments as filesystem paths, while URI parsing requires --file-uri. The request has 37 upvotes, and the related issues inspected do not provide an open canonical covering the same behavior.

## Change summary

Allow `code file:///path` to open the referenced file without requiring `--file-uri`.

## Best solution

Support positional file URLs in the desktop CLI while preserving ordinary path handling and explicit URI flags. Establish the cross-platform argument contract first, including Windows launch filtering and interactions with existing CLI modes.

- **Behavior:**

  > A positional file URL such as `code file:///Users/username/file` should open the referenced file rather than a filesystem path containing the literal URL. Explicit --file-uri usage and ordinary absolute or relative paths must continue to work. Acceptance should cover percent-encoded filenames and both initial launch and forwarding to an existing window across desktop platforms. The behavior of directory URLs and combinations with existing CLI modes must be settled before implementation.
- **Trace:**

  > The predecessor https://github.com/microsoft/vscode/issues/213215 establishes the observed literal-path behavior and the maintainer's request for a separate feature issue. In src/vs/code/electron-main/main.ts, validatePaths/doValidatePaths sanitize positional arguments as paths before WindowsMainService.doExtractPathsFromCLI in src/vs/platform/windows/electron-main/windowsMainService.ts distinguishes explicit URI flags from positional paths. The explicit file-URI branch uses cliArgToUri and resolveOpenable, whereas positional inputs use doResolveFilePath or doResolveRemotePath. On Windows, src/vs/code/node/cli.ts invokes combineUriFlags from src/vs/code/node/cliArgs.ts because Chromium filters standalone URL-like tokens before main.js runs. This establishes an earlier transport boundary as well as a path-normalization boundary; no runtime reproduction was attempted. Preserve ordinary path semantics, explicit URI flags, and existing remote-authority behavior; arbitrary URI schemes and OS protocol-handler registration are outside the central request.
- **Open decisions:**
  - Should positional file URLs referencing directories open folders, as ordinary positional paths do, or retain the file-oriented semantics of --file-uri?
  - What is the supported positional file-URL contract for --goto, --diff, --merge, and --remote, including whether remote mode interprets a file URL locally or on the remote authority?
