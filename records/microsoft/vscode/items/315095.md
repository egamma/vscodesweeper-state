[https://github.com/microsoft/vscode/issues/315095](https://github.com/microsoft/vscode/issues/315095)

## Summary

Keep open: telemetry confirmed that expected gallery network failures escape as unhandled rejections during extension auto-update across multiple stable releases and platforms. Current main still contains fire-and-forget auto-update entry points whose promises can reject, but the exact remaining current-main trigger should be reconfirmed before implementation.

## Change summary

Prevent transient extension-gallery fetch failures during background auto-update from reaching global unhandled-error telemetry while retaining diagnostic logging.

## Best solution

Reproduce the current-main rejection through each extension auto-update entry point, then ensure best-effort background update failures are observed and logged without changing `Failed to fetch` into an `OfflineError` or hiding failures from explicit user-initiated installs.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts`, `src/vs/workbench/contrib/extensions/test/electron-browser/extensionsWorkbenchService.test.ts`
- **Validation:** Extend the ExtensionsWorkbenchService unit suite with a rejected gallery/install request triggered through each relevant background auto-update entry point; verify the rejection is observed and logged without producing an unhandled rejection, while an explicit user-initiated installation still reports its failure.
- **Behavior:**

  > A transient gallery request failure during automatic extension updating must not reach the global unhandled-error handler. The failure must remain observable in extension logs, and a later update check must still be able to retry. Explicit user-initiated extension installations must continue to surface their errors rather than being silently swallowed. Acceptance requires regression coverage for the currently failing auto-update entry point and unchanged explicit-install error behavior.
- **Trace:**

  > The reported stack runs from `requestImpl.ts` through `extensionGalleryService.getAsset`, `getManifest`, `installFromGallery`, and `ExtensionsWorkbenchService`. In current main, `autoUpdateBuiltinExtensions()` is invoked without observing its returned promise during web initialization and metered-connection changes, while `autoUpdateExtensions()` is similarly invoked after enabling an extension's auto-update state; both ultimately await `Promises.settled()`, which rethrows the first failed install. The delayed auto-update route separately attaches a rejection handler, so the first planning step is to reproduce the telemetry outcome through the remaining direct entry points and identify the reporter's current path. Keep `requestImpl.ts` behavior and explicit installation failures unchanged; the two rejected PRs at https://github.com/microsoft/vscode/pull/315098 and https://github.com/microsoft/vscode/pull/316296 demonstrate why global `OfflineError` reclassification is outside the boundary.
