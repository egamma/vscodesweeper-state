# Issue #333134 — Allow disabling Copilot harness built-in tools in Chat: Open Customizations

[https://github.com/microsoft/vscode/issues/333134](https://github.com/microsoft/vscode/issues/333134)

## Summary

This is a valid, currently unmet feature request for profile-level control of Copilot runtime tools. Route it to the chat tools and agent-host owners because the UI intentionally presents these tools as read-only and the persisted client-tool enablement state is not forwarded as Copilot runtime exclusions.

## Change summary

Allow users to disable individual Copilot runtime tools from Chat Customizations and optionally require approval before those tools run.

## Best solution

Give Copilot built-in tools enforceable profile-scoped enablement controls in Chat Customizations, with disabled tools omitted at runtime launch or resume. Decide separately whether the first scope also integrates runtime tools into the approval-management surface.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/aiCustomization/toolsListWidget.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostToolSetEnablementService.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostActiveClientService.ts`, `src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts`, `src/vs/workbench/contrib/chat/test/browser/agentSessions/agentHostToolSetEnablementService.test.ts`, `src/vs/platform/agentHost/test/node/copilotSessionLauncher.test.ts`
- **Validation:** Extend the AgentHostToolSetEnablementService tests to cover persisted Copilot built-in decisions and the CopilotSessionLauncher tests to assert that disabling `task` produces an SDK `builtin:task` exclusion; run `./scripts/test.sh --grep "AgentHostToolSetEnablementService|CopilotSessionLauncher"`.
- **Behavior:**

  > Copilot built-in tools shown in Chat Customizations can be enabled or disabled individually, and the selection persists at profile scope. A disabled runtime tool is not advertised to the model and cannot be invoked in affected Copilot sessions, while client and extension tool behavior remains unchanged. The plan must define whether a change applies immediately to an active session or from its next launch or resume. Approval-management integration is a separate acceptance requirement only if maintainers include it in the initial scope.
- **Trace:**

  > ToolsListWidget in src/vs/workbench/contrib/chat/browser/aiCustomization/toolsListWidget.ts synthesizes a static `copilot-cli` tool set and unconditionally marks it read-only, so its rows never call IAgentHostToolSetEnablementService. That service already provides sparse profile-scoped enablement, but AgentHostActiveClientService consumes it solely to filter client-published tools. CopilotSessionLauncher already passes `availableTools` and `excludedTools` to the SDK and supports `builtin:<name>` matching through the experimental model-capability override path. The uncertainty begins at the client-to-host contract needed to convey profile-wide built-in exclusions and at whether live sessions can be updated safely; preserve existing enablement and approval behavior for client tools, extensions, and MCP servers. Related reports https://github.com/microsoft/vscode/issues/300411, https://github.com/microsoft/vscode/issues/309540, and https://github.com/microsoft/vscode/issues/333026 do not own this scope.
- **Open decisions:**
  - Should the initial feature expose only Enabled/Disabled for Copilot built-in tools, or also add an Always Require Confirmation state to Manage Tool Approval?
  - Must changing a built-in tool take effect in an already-running Copilot session, or is applying it on the next session launch or resume acceptable?

## Evidence

- **current UI:** src/vs/workbench/contrib/chat/browser/aiCustomization/toolsListWidget.ts constructs Copilot runtime tools in `_createStaticReadOnlySets`, marks the `copilot-cli` set read-only in `_toViewModel`, hides its checkboxes, and labels its rows “Always Available.”
- **profile persistence boundary:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostToolSetEnablementService.ts already stores tool decisions at profile scope, but src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostActiveClientService.ts applies those decisions only while publishing client-provided `ToolDefinition` entries.
