# Issue #261604 — Debugger not attaching automatically anymore with `Javascript Debug Terminal`

[https://github.com/microsoft/vscode/issues/261604](https://github.com/microsoft/vscode/issues/261604)

## Summary

Keep open: the discussion contains a detailed confirmed reproduction of JavaScript Debug Terminals incorrectly following the ordinary-terminal auto-attach filter, with another confirmation in August 2026. No verified fix or eligible open canonical was established, and the shell-profile workaround does not cover all reported cases.

## Change summary

Restore automatic debugger attachment in explicitly created JavaScript Debug Terminals independently of the ordinary-terminal auto-attach setting.

## Best solution

Preserve the distinction between ordinary terminals and explicitly requested debug terminals: debug terminals should attach without requiring global Always mode, while ordinary terminals continue honoring debug.javascript.autoAttachFilter. Investigate the interaction between global auto-attach environment injection and the bundled JavaScript debugger's dedicated terminal launch path.

## Evidence

- **Confirmed reproduction:** https://github.com/microsoft/vscode/issues/261604#issuecomment-3216366296 supplies a minimal Jest setup, PowerShell 7.5.2 with empty profiles, disabled extensions, explicit commands, NODE_OPTIONS values, and a settings matrix. The commenter reports that dedicated debug terminals behave like ordinary terminals, while a launch.json launch configuration works independently of the filter.
- **Later confirmation:** The August 21, 2026 comment in https://github.com/microsoft/vscode/issues/261604 independently reports that changing auto-attach modes changes dedicated debug-terminal behavior. This supports retaining the report rather than treating the earlier info-needed timeout as resolution.
- **Workaround is not a complete diagnosis:** The thread identifies overwriting NODE_OPTIONS in a shell profile as one cause and preserving its existing value as a workaround. However, the detailed PowerShell reproduction uses empty profiles and already contains bootloader requirements; its author also reports that manually requiring the bootloader does not resolve their case.
- **Current source boundary:** extensions/debug-auto-launch/src/extension.ts refreshes global auto-attach state through extension.js-debug.setAutoAttachVariables and extension.js-debug.clearAutoAttachVariables when filter settings change. product.json identifies ms-vscode.js-debug 1.140.0 as a bundled extension from https://github.com/microsoft/vscode-js-debug. These establish the investigation boundary, not a conclusive reproduction against current main.
- **Debugger implementation lead:** https://github.com/microsoft/vscode-js-debug/blob/main/src/targets/node/terminalNodeLauncher.ts constructs dedicated terminal environments through resolveEnvironment. https://github.com/microsoft/vscode-js-debug/blob/main/src/targets/node/bootloader.ts skips repeated registration and selects attachment behavior using inspector environment options. Their interaction with global auto-attach injection warrants investigation; reading these paths alone does not establish which environment wins in the reported scenario.
- **Canonical search:** Open-issue searches for JavaScript Debug Terminal and autoAttachFilter did not establish an older open issue owning the same symptom. https://github.com/microsoft/vscode/issues/152472 describes the historical symptom but is closed, so it cannot serve as a duplicate canonical.
- **Related reports do not supersede this issue:** https://github.com/microsoft/vscode-js-debug/issues/2296 is open but newer and concerns frozen stepping after a breakpoint, rather than failure to attach. https://github.com/microsoft/vscode/issues/236397 is closed and primarily concerns PowerShell command execution timing. Neither establishes a qualifying duplicate or a fix for this reopened report.
