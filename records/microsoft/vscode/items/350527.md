Its clarification at https://github.com/microsoft/vscode/issues/335037#issuecomment-5660265647 explicitly reports getNotebookSummary failing on virtual notebooks and requests preservation of virtual URIs through VS Code client notebook APIs. This owns the same observable failure and broader cross-provider scope.
- **Current client-tool boundary:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts, _executeClientTool, parses the protocol tool input and passes its parameters to invokeTool without translating notebook filePath values.
- **Notebook URI handling:** extensions/copilot/src/platform/prompts/common/promptPathRepresentationService.ts, resolveFilePath, converts absolute paths to file: by default and preserves explicitly supplied schemes. NotebookSummaryTool.invoke and GetNotebookCellOutputTool.invoke pass the resolved URI to openNotebookDocument, consistent with both logged failure representations.
- **Existing mapping is partial coverage:** src/vs/platform/agentHost/node/copilot/copilotWorkspace.ts already maps virtual SDK paths back to original resources, and src/vs/platform/agentHost/common/agentClientUri.ts provides inverse transport decoding. These capabilities do not establish that native client notebook-tool arguments receive that conversion. No execution was performed; the original invocation arguments remain unavailable.

Neither is a better canonical for virtual notebook URI preservation.
