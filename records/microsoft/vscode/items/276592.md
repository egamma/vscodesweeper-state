## Summary

The built-in tsconfig link resolver still ignores package exports remapping, so the reported navigation gap remains. Keep this correctly routed issue open while the existing fixing PR is reviewed.

## Change summary

Make navigation from tsconfig extends specifiers resolve the same configuration file as TypeScript when package exports remap the path.

## Best solution

Review https://github.com/microsoft/vscode/pull/308156 against the reporter's reproduction and TypeScript's actual configuration-resolution semantics, then land a compatible fix. Preserve existing direct-path behavior without assuming ordinary Node.js module resolution fully matches TypeScript.

## Evidence

- **Current source confirms the failing path:** In extensions/typescript-language-features/src/languageFeatures/tsconfig.ts, _typescript.openExtendsLink calls getTsconfigPath, which delegates bare package specifiers to resolveNodeModulesPath. That function appends the literal subpath to node_modules/<package> and checks existence; it never reads package.json exports. For @scope/example/base/tsconfig.json mapped to ./lib/base/tsconfig.json, it therefore checks the unmapped base/tsconfig.json and cannot discover the exported target.
- **Confirmed reproduction and intended boundary:** https://github.com/microsoft/vscode/issues/276592#issuecomment-3522170337 independently confirms the resolution failure. The reporter provides https://github.com/valler/repro-repo-for-ms-vscode-issue-276592 and explains in https://github.com/microsoft/vscode/issues/276592#issuecomment-3528562809 that navigation must agree with TypeScript rather than restrict configuration filenames or assume ordinary module extension rules.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/308156 is verified OPEN with mergedAt null and explicitly states Fixes #276592. It proposes exports-aware resolution in this document-link provider, so the issue must remain open and a competing agent implementation is inappropriate.
