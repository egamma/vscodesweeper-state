# Issue #334832 — Local history folders are keyed by a 32-bit path hash with no collision handling: Timeline shows another file's entries and Restore overwrites with them

[https://github.com/microsoft/vscode/issues/334832](https://github.com/microsoft/vscode/issues/334832)

## Summary

Confirmed on main by reading the source: WorkingCopyHistoryModel keys history folders by a 32-bit string hash (src/vs/base/common/hash.ts stringHash) and resolveEntriesFromDisk/readEntriesFile never compares the stored `resource` field against the working copy being resolved, so a hash collision serves — and Restore can overwrite — another file's content. Already carries the right area labels, so this just needs a maintainer decision on the fix approach (validate-on-read vs. wider migration).

## Change summary

Local History (and hot-exit backups) key their on-disk folder/file names by a 32-bit hash of the resource path with no collision check, so two colliding filenames share one history store; Timeline shows the wrong file's entries and Restore silently overwrites the open file with the other file's content.

## Best solution

Implement the reporter's minimal fix in WorkingCopyHistoryModel.resolveEntriesFromDisk/readEntriesFile (src/vs/workbench/services/workingCopy/common/workingCopyHistoryService.ts): compare the serialized `resource` against the resolving working copy's resource and treat a mismatch as belonging to a different (disambiguated) folder instead of serving/overwriting with unrelated entries; consider a similar resource-check guard for hashPath collisions in workingCopyBackupService.ts to stop the unsaved-changes loss on hot exit. A stronger/longer digest for the folder key is a larger, migration-requiring follow-up.
