# Issue #334832 — Local history folders are keyed by a 32-bit path hash with no collision handling: Timeline shows another file's entries and Restore overwrites with them

[https://github.com/microsoft/vscode/issues/334832](https://github.com/microsoft/vscode/issues/334832)

## Summary

Verified in the current source: local-history folder keys are a 32-bit path hash with no validation that a resolved folder's stored `resource` matches the working copy being read, and the same unvalidated-hash pattern hits backup `resolve()`. On path collision, Timeline shows another file's entries and Restore/backup-resolve can overwrite the wrong file's content — a real, well-diagnosed data-loss bug worth routing to the area owner.

## Change summary

Local History (and hot-exit backups) key their on-disk folder/file by a 32-bit string hash of the resource path with no collision check, so two files whose paths hash-collide share one history/backup store and can silently overwrite each other's content.

## Best solution

In workingCopyHistoryService.ts's resolveEntriesFromDisk()/doResolveEntries(), compare the `resource` field parsed from entries.json (and the folder's serialized model) against the working copy's own resource before trusting the folder's entries, falling back to a disambiguated folder on mismatch as the reporter suggests; separately, workingCopyBackupService.ts's resolve() should validate the parsed `resourcePreamble` against `identifier.resource` the same way resolveIdentifier() already does, before trusting backup content.

## Evidence

- **hash used as folder key:** src/vs/workbench/services/workingCopy/common/workingCopyHistoryService.ts:118-119 (toHistoryEntriesFolder) uses `hash(workingCopyResource.toString()).toString(16)` — a 32-bit int hash — as the sole folder name, confirmed against src/vs/base/common/hash.ts's stringHash/numberHash (`hashVal*31+ch`, kept int32 via `|0`).
- **no read-side validation:** doResolveEntries()/resolveEntriesFromDisk() (lines 302-362) build entries for whatever is on disk under the hashed folder and always stamp `workingCopy: { resource: workingCopyResource, ... }` (the caller's resource), never comparing it against `entryListing.resource` (the serialized model's `resource: string` field, defined at line 36 and populated at line 513) that names the file the folder was actually written for.
- **backup resolve() omits the same check:** workingCopyBackupService.ts resolve() (~line 431) parses only the meta half of the preamble and never extracts/compares `resourcePreamble` against `identifier.resource`, unlike the sibling resolveIdentifier() a few lines below which does extract `resourcePreamble` — this matches the reporter's addendum exactly.
