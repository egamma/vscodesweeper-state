# Issue #336394 — Hosted Agent: Codex Agent: agent unable to read it's own path, e.g. `~/.codex`, in `Auto-Review` mode

[https://github.com/microsoft/vscode/issues/336394](https://github.com/microsoft/vscode/issues/336394)

## Summary

Real, currently-open Codex Agent Host bug: in Auto-Review mode the sandbox blocks reads outside the narrow permission profile (including Codex's own `~/.codex` state and paths above the workspace root), while Full Access works — corroborated by the closely related issue #336424, which traces the same class of failure to Auto-Review's escalation approval not actually loosening the enforced sandbox.

## Change summary

Codex Agent Host in Auto-Review mode denies filesystem reads (Operation not permitted) for paths outside the workspace/tmp allowlist, including Codex's own `.codex/plugins/cache` and `.codex/skills`, whereas Full Access mode works fine.

## Best solution

Diagnose whether the fix belongs in VS Code's Codex permission wiring (src/vs/platform/agentHost/node/codex/codexLaunchConfig.ts's `codexPermissionProfileOverrides`/`codexPermissionProfile`, which hard-denies `:root` and only grants `:minimal` read plus tmpdir write) or in the bundled Codex app-server's escalation handling referenced by #336424, then extend the Auto-Review filesystem profile (or apply approved escalations) so Codex can read its own state directories without dropping to Full Access.

## Plan brief

- **Behavior:**

  > In Auto-Review permission mode, Codex should be able to read its own working state (e.g. `~/.codex/plugins/cache`, `~/.codex/skills`) and any path an approved escalation covers, without falling back to Full Access. Today those reads fail with 'Operation not permitted' even though the equivalent command succeeds under Full Access.
- **Trace:**

  > The default vscode-workspace Codex permission profile (src/vs/platform/agentHost/node/codex/codexLaunchConfig.ts, `codexPermissionProfileOverrides`) denies `:root` and grants only `:minimal` read plus `:tmpdir` write — it does not special-case Codex's own config/cache directories. Issue https://github.com/microsoft/vscode/issues/336424 additionally shows that even an explicit, accepted escalation request doesn't change the enforced sandbox, suggesting the gap may instead (or also) be in the escalation-to-sandbox wiring around `approvalsReviewer`/`resolveCodexPermissions` in codexAgent.ts. Boundary: do not change Full Access or the default workspace-write network policy; scope is limited to what Auto-Review permits.
- **Open decisions:**
  - Should Codex's own state directories (~/.codex/*) always be readable regardless of permission profile, or should an approved Auto-Review escalation dynamically widen the sandbox for that command only?
