# Issue #130493 — Allow to configure environment variables for extension host

[https://github.com/microsoft/vscode/issues/130493](https://github.com/microsoft/vscode/issues/130493)

## Summary

Long-standing, well-upvoted (44) feature request already parked in Backlog; no equivalent setting exists on current main for the local/non-remote case, so it should stay open and be scoped with a maintainer before implementation.

## Change summary

Let a workspace or user declare environment variables that are applied to the (local) extension host process, similar to `terminal.integrated.env.*` but for the extension host itself.

## Best solution

Design a scoped setting (e.g. workspace-trust-gated `extensions.environmentVariables` or similar) that merges into the local extension host's env, reusing the existing `extensionHostEnv` plumbing in `localProcessExtensionHost.ts`/`remote.contribution.ts` that today is only reachable via `debugExtensionHost.env` or a remote-authority resolver.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/electron-browser/localProcessExtensionHost.ts`, `src/vs/workbench/services/configuration/common/configuration.ts`, `src/vs/workbench/contrib/remote/electron-browser/remote.contribution.ts`
- **Validation:** A test asserting that a configured env var is present in the spawned extension host process's environment.
- **Behavior:**

  > A user or workspace can declare one or more environment variables that are applied to the extension host process on startup, so extensions that shell out to external binaries can locate them without the user having to launch VS Code from a shell with the right PATH/env already exported. Acceptance: setting the new configuration causes the named variable(s) to appear in the extension host's process.env, verified by a new/updated extension-host startup test.
- **Trace:**

  > Today the local extension host's env is built in localProcessExtensionHost.ts (`_resolveAuthority`/env setup around line 225-239) from `objects.mixin(processEnv, shellEnv)`, with `debugExtensionHost.env` merged in only for debug launches (line 235-236). Separately, `remote.contribution.ts` (line 88-89) calls `extensionService.setRemoteEnvironment(resolveResult.options.extensionHostEnv)` when a remote-authority resolver supplies one (type defined in remoteAuthorityResolver.ts:54). Neither path is reachable from a plain user/workspace setting for the local, non-remote, non-debug case — that gap is the remaining work. Do not touch the debug or remote-resolver env paths; this should be an additive merge, and workspace-level values likely need a workspace-trust gate since they let workspace settings inject arbitrary env into a process that runs extension code.
- **Open decisions:**
  - Should this be a user-level setting, a workspace-level setting, or both (and if workspace-level, must it be gated behind workspace trust)?
  - How should a workspace/user-declared variable interact with one supplied by debugExtensionHost.env or a remote-authority resolver's extensionHostEnv (override, merge, or reject conflicts)?
