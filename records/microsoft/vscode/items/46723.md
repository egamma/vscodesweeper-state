# Issue #46723 — VS Code not being able to open a large file

[https://github.com/microsoft/vscode/issues/46723](https://github.com/microsoft/vscode/issues/46723)

## Summary

Keep this accepted large-file request open: current main still constructs an in-memory text buffer, and bypassing the opening confirmation does not provide disk-backed support for a 19 GB SQL file. The related closed report was explicitly consolidated into this issue; no verified older canonical owns the same request.

## Change summary

Support opening multi-gigabyte text files such as a 19 GB SQL dump without requiring the entire document to reside in memory.

## Best solution

Establish a bounded-memory large-file experience in the editor/text-buffer area, with an explicit decision about whether initial support is read-only or includes editing. Preserve this issue as the existing consolidation point rather than treating a confirmation-limit override as a solution.

The plan must define numeric memory and latency acceptance thresholds and check ordinary-file behavior.
- **Behavior:**

  > The reporter cannot open a 19 GB SQL dump, and the maintainer attributes the limitation to loading files into RAM rather than paging from disk. The goal is to make such files usable without memory consumption scaling with the entire document. Acceptance must cover opening, navigation, content fidelity, memory use, and responsiveness while preserving ordinary-file behavior. Whether this experience initially permits viewing only or also editing requires a maintainer decision.
- **Trace:**

  > Current createTextBufferFactoryFromStream in src/vs/editor/common/model/textModel.ts accumulates all stream chunks through PieceTreeTextBufferBuilder before returning a text-buffer factory. In src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeTextBufferBuilder.ts, _acceptChunk2 retains strings and line-start metadata, and PieceTreeTextBufferFactory.create constructs the buffer from those retained chunks. FileEditorInput.doResolve in src/vs/workbench/contrib/files/browser/editors/fileEditorInput.ts passes opening limits supplied by ResourceEditorInput.ensureLimits; these control confirmation, not memory residency. The existing Open Anyway action therefore does not establish support for the reporter's file size. https://github.com/microsoft/vscode/issues/78394 was explicitly closed into https://github.com/microsoft/vscode/issues/46723, while https://github.com/microsoft/vscode/issues/31078 addresses a separate extension-host synchronization boundary. The inspection establishes the current loading architecture, not a complete design or consumer inventory for a disk-backed alternative; do not treat disabling confirmation or increasing synchronization limits as completion.
- **Open decisions:**
  - Should initial multi-gigabyte file support provide read-only inspection, or must it support editing and saving?
  - Which existing editor capabilities must remain available in the large-file experience, and which may be explicitly unavailable to maintain bounded memory?
