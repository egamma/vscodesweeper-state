# Issue #46723 — VS Code not being able to open a large file

[https://github.com/microsoft/vscode/issues/46723](https://github.com/microsoft/vscode/issues/46723)

## Summary

A real architectural gap remains: current main streams file input but retains every decoded chunk and line index in the in-memory text buffer. This is the established canonical request, so it should remain open under discussion.

## Change summary

Support opening and editing multi-gigabyte text files by paging their contents instead of retaining the entire document in memory.

## Best solution

Design a disk-backed or paged text-buffer implementation under `src/vs/editor/common/model/` while preserving the existing piece-tree API and large-file feature reductions. The later crash reports can inform its memory constraints without replacing this canonical request.

## Evidence

- **current implementation:** `src/vs/editor/common/model/textModel.ts` feeds every decoded stream chunk into `PieceTreeTextBufferBuilder`; `src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeTextBufferBuilder.ts` retains those chunks and their line-start arrays.
- **existing optimization:** `editor.largeFileOptimizations` in `src/vs/editor/common/model/textModel.ts` disables costly features such as tokenization, but does not page document contents from disk.
- **current limit:** `src/vs/platform/files/common/files.ts` uses a 1GB local-file confirmation threshold, far below the reported 19GB file; confirmation does not provide disk-backed editing.
- **canonical history:** The related report https://github.com/microsoft/vscode/issues/78394 was closed explicitly as a duplicate of this issue, establishing this as the canonical request.
- **continuing gap:** Newer open reports https://github.com/microsoft/vscode/issues/196510 and https://github.com/microsoft/vscode/issues/197715 document crashes and hangs with substantially smaller large files, reinforcing that the memory architecture remains unresolved.
