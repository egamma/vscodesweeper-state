# Issue #326966 — [Markdown Editor (experimental)] AI plugins cannot recognize active file context

[https://github.com/microsoft/vscode/issues/326966](https://github.com/microsoft/vscode/issues/326966)

## Summary

Current source confirms the gap: the experimental Markdown editor is a custom text editor, while Copilot's active-context path only recognizes ordinary text, notebook, and diff editors. The issue should remain open and be routed to the chat/custom-editor owners.

## Change summary

AI context collection does not recognize the focused Markdown document when it is opened in the experimental custom editor.

## Best solution

Make Copilot's implicit file-context collection recognize the URI and backing text document of an active custom text editor without pretending that it has ordinary TextEditor selection state. Preserve existing behavior for text, notebook, and diff editors; third-party AI extensions can consume the existing TabInputCustom URI independently.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/tabs/common/tabsAndEditorsService.ts`, `extensions/copilot/src/platform/tabs/vscode/tabsAndEditorsServiceImpl.ts`, `extensions/copilot/src/extension/conversation/vscode-node/remoteAgents.ts`, `extensions/markdown-language-features/src/preview/markdownEditorProvider.ts`, `src/vs/workbench/api/browser/mainThreadEditorTabs.ts`, `src/vs/workbench/api/common/extHostEditorTabs.ts`
- **Validation:** Add an extension-level test with an active `TabInputCustom` for `vscode.markdown.editor` and no `window.activeTextEditor`; requesting implicit editor context must include the custom tab's Markdown URI/document, while selection context remains absent and existing ordinary-text-editor context tests continue to pass.
- **Behavior:**

  > When a Markdown file is focused in the experimental Markdown editor, Copilot must recognize that file as the active document and make its contents available as implicit file context. It must not invent a text-editor selection when the custom editor cannot provide one. Ordinary text, notebook, and diff editor context behavior must remain unchanged. Acceptance requires a test where an active custom Markdown tab with no active TextEditor still contributes the correct file URI and document.
- **Trace:**

  > The experimental Markdown surface is registered as a CustomTextEditorProvider in extensions/markdown-language-features/src/extension.shared.ts and is backed by a TextDocument in MarkdownEditorProvider. The workbench already transports a custom editor's resource through CustomEditorInput to CustomEditorTabInput in src/vs/workbench/api/browser/mainThreadEditorTabs.ts and src/vs/workbench/api/common/extHostEditorTabs.ts. The gap begins in extensions/copilot/src/platform/tabs/vscode/tabsAndEditorsServiceImpl.ts: `_asTabInfo` drops TabInputCustom resources, while `activeTextEditor` can only return an actual visible TextEditor. Selection-dependent context in extensions/copilot/src/extension/conversation/vscode-node/remoteAgents.ts is therefore also used as the gate for file context. The plan should enumerate other consumers of ITabsAndEditorsService before defining the boundary between active file context and selection context; it must not change the public meaning of `window.activeTextEditor` or synthesize TextEditor capabilities for a webview-backed custom editor.

## Evidence

- **Markdown editor implementation:** extensions/markdown-language-features/src/extension.shared.ts registers MarkdownEditorProvider as a CustomTextEditorProvider, and extensions/markdown-language-features/src/preview/markdownEditorProvider.ts identifies its view type as `vscode.markdown.editor`.
- **available extension API context:** src/vs/workbench/api/browser/mainThreadEditorTabs.ts exports a CustomEditorInput's resource, and src/vs/workbench/api/common/extHostEditorTabs.ts exposes it as CustomEditorTabInput(uri, viewType), so the active custom tab's file URI is available without treating it as a TextEditor.
- **Copilot context gap:** extensions/copilot/src/platform/tabs/vscode/tabsAndEditorsServiceImpl.ts `_asTabInfo` handles TabInputText, TabInputNotebook, and their diff forms but not TabInputCustom; its `activeTextEditor` fallback also searches only `visibleTextEditors`. Consequently the focused experimental Markdown editor cannot produce an active TextEditor or retained tab URI through this service.
- **affected context path:** extensions/copilot/src/extension/conversation/vscode-node/remoteAgents.ts adds implicit file and selection references only when `tabsAndEditorsService.activeTextEditor` exists, so the custom-editor path is omitted on current main.
- **canonical search:** Repository issue searches for the same custom-editor/active-file AI symptom found no older open canonical issue; the mechanically suggested RTL and workbench-font issues are unrelated.
