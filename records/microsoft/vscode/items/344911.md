# Issue #344911 — MCP: server's notifications/cancelled cancels the editor's own request instead of the server's sampling/elicitation request

[https://github.com/microsoft/vscode/issues/344911](https://github.com/microsoft/vscode/issues/344911)

## Summary

The cancellation-direction defect remains present in current source, including the skipped request ID 0. Keep this open while the two linked implementation candidates are reviewed.

## Change summary

Server cancellation notifications should cancel the matching server-initiated sampling or elicitation request without rejecting unrelated editor requests.

## Best solution

Review and land one of the linked fixes, preserving independent incoming and outgoing request identities. Resolve the candidates' differing treatment of late responses during that review and confirm cancellation reaches sampling and elicitation.

## Evidence

- **Current cancellation routing:** src/vs/workbench/contrib/mcp/common/mcpServerRequestHandler.ts:394-397 checks request.params.requestId for truthiness and calls _rpc.cancelPendingRequest. This skips ID 0 and routes nonzero server cancellation IDs to the editor's outgoing request table.
- **Confirmed protocol defect:** src/vs/base/common/jsonRpcProtocol.ts populates _pendingRequests in sendRequest; cancelPendingRequest cancels that outgoing promise. _handleRequest creates a separate CancellationTokenSource without indexing it by incoming request ID, so a server cancellation cannot reach its handler token. A nonzero ID collision therefore rejects the unrelated outgoing request.
- **Affected handler path:** src/vs/workbench/contrib/mcp/common/mcpServerRequestHandler.ts:305-329 forwards incoming request tokens to ordinary sampling/createMessage and elicitation/create handlers. The missing incoming cancellation route prevents those tokens from being cancelled by notifications/cancelled.
- **Open implementation candidates:** https://github.com/microsoft/vscode/pull/344912 and https://github.com/microsoft/vscode/pull/345027 were verified open and unmerged; both explicitly say Fixes #344911. The former retains responses after cancellation, while the latter proposes suppressing late responses and errors. Neither establishes a landed fix.
- **Complete discussion:** https://github.com/microsoft/vscode/issues/344911#issuecomment-6498779409 identifies direction separation, cancellation reaching the prompt, late-response handling, and a regression case with deliberately colliding request IDs. These are relevant acceptance concerns for reviewing the existing PRs, not grounds for closing the issue.
