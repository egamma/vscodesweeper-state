# Issue #3553 — Get selected file/folder in the explorer view

[https://github.com/microsoft/vscode/issues/3553](https://github.com/microsoft/vscode/issues/3553)

## Summary

Keep open: current main still exposes Explorer selection only to internal workbench code, while extensions cannot query it or observe changes. This is accepted On Deck API work with 126 upvotes and confirmed extension use cases.

## Change summary

Expose the files and folders currently selected or keyboard-focused in the built-in Explorer so extension commands work consistently from context menus, keybindings, and the Command Palette.

## Best solution

Design a proposed extension API that exposes the built-in Explorer's selected resource URIs and a selection-change event, with explicit semantics for keyboard focus, inactive Explorer views, and multiple workspace roots.

- **Reason:** Providing a narrowly scoped Explorer API enables extensions to integrate with a core workbench workflow without adding bundled feature-specific behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/files.ts`, `src/vs/workbench/contrib/files/browser/explorerService.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** Add and run targeted API bridge tests covering single and multiple file/folder selections, keyboard focus changes, an active editor different from the Explorer selection, and the chosen behavior when the Explorer is unfocused.
- **Behavior:**

  > An extension can obtain the URI list corresponding to the user's current selection in the built-in file Explorer and observe when that selection changes. The result must work for files, folders, multiple selections, mouse selection, and keyboard navigation, including when the active editor refers to a different resource. Context-menu command arguments and existing contributed TreeView APIs must remain unchanged.
- **Trace:**

  > The Explorer already retains the required state: ExplorerView.getContext() reads tree focus and selection in src/vs/workbench/contrib/files/browser/views/explorerView.ts, and ExplorerService.getContext() exposes it internally through src/vs/workbench/contrib/files/browser/files.ts. Built-in commands consume that state through getMultiSelectedResources(), including checks for the actively focused Explorer, but the extension-host protocol has no bridge for it. The treeViewActiveItem proposal is limited to extension-created TreeView instances and therefore does not expose the built-in Explorer. https://github.com/microsoft/vscode/pull/117820 confirms that a command-based workaround was rejected in favor of a designed API; https://github.com/microsoft/vscode/issues/316820 records current API-shape options but is newer than this canonical issue. Preserve existing Explorer selection, focus, command-argument, and active-editor fallback behavior outside the new public contract.
- **Open decisions:**
  - Should the public contract be an Explorer object with selection and change event, flat window properties, or a query-only API?
  - When the Explorer is not focused, should the API return its retained selection or an empty result?
  - Should keyboard focus be exposed separately from the multi-selection, and which one should palette and keybinding commands treat as their primary target?
  - Should the contract cover only the built-in file Explorer or generalize across Explorer, Open Editors, and editor tabs?

## Evidence

- **current source gap:** src/vs/workbench/contrib/files/browser/files.ts defines internal IExplorerService.getContext(), and getMultiSelectedResources() reads that context for built-in commands, but no equivalent built-in Explorer selection surface exists in src/vscode-dts/vscode.d.ts.
- **existing proposal does not cover Explorer:** src/vscode-dts/vscode.proposed.treeViewActiveItem.d.ts and src/vs/workbench/api/common/extHostTreeViews.ts expose activeItem only on TreeView<T> instances created by extensions; extensions cannot obtain a TreeView handle for the built-in file Explorer.
- **accepted demand:** The issue is in the On Deck milestone with feature-request, api, and file-explorer labels and has 126 community upvotes. A maintainer explicitly supported the selected-folder use case at https://github.com/microsoft/vscode/issues/3553#issuecomment-904254356.
- **canonical issue:** https://github.com/microsoft/vscode/issues/139313 was closed as a duplicate of this issue for the same selection-query and change-event request. The open https://github.com/microsoft/vscode/issues/316820 is a newer restatement from 2026, so under the re-review rule it cannot replace this 2016 issue as canonical.
- **prior implementation decision:** https://github.com/microsoft/vscode/pull/117820 attempted an explorer.selectedFiles command but was closed without merging; maintainers stated that this should instead be designed as a real extension API through the API discussion process.
