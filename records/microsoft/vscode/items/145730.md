# Issue #145730 — commit message textbox loses focus when scrolled out of view

[https://github.com/microsoft/vscode/issues/145730](https://github.com/microsoft/vscode/issues/145730)

## Summary

Keep open: the SCM input remains a virtualized tree row, so scrolling it outside the viewport removes its focused editor from the DOM. Related sticky-input requests are newer and describe a different observable problem, so they do not qualify as duplicate targets for this re-reviewed issue.

## Change summary

Preserve commit-message keyboard focus when scrolling through a long list of changed files.

## Best solution

Allow users to inspect changes by scrolling without interrupting commit-message typing or requiring another click. Resolve the focused-input lifecycle in the SCM/tree integration, coordinating with the related sticky-input work without making that broader feature a prerequisite.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/scm/browser/scmViewPane.ts`, `src/vs/base/browser/ui/list/listView.ts`, `src/vs/base/browser/ui/list/rowCache.ts`

All markers must appear in the same commit message without refocusing. Also check multiple repositories, deliberate focus changes, and row recycling; the plan should establish browser regression coverage for this lifecycle.
- **Behavior:**

  > Scrolling the Source Control changes list must not interrupt typing into the focused commit-message input. Characters typed while the input is outside the viewport must still reach that repository's message, and typing must continue after scrolling back without another click. Preserve the message and cursor selection, and respect deliberate user focus changes. Making the input permanently visible is an optional broader enhancement, not an acceptance requirement for this bug.
- **Trace:**

  > At main eef761e9628e777317a554114f0202a070e98f0b, SCMViewPane registers InputRenderer as a row renderer in WorkbenchCompressibleAsyncDataTree. ListView.render removes rows outside the render range, removeItemFromDOM releases their templates, and RowCache removes the corresponding DOM nodes; detaching the focused editor accounts for the lost keyboard focus. InputRenderer preserves selections but not focus across this scroll lifecycle, while SCMViewPane.updateChildren restores focus only during tree refreshes. The unresolved technical boundary is how to maintain the active input through viewport virtualization without breaking recycling, scrolling, or other tree consumers; a bounded implementation has not yet been established. Preserve intentional focus transfers and existing multi-repository behavior. Coordinate with https://github.com/microsoft/vscode/issues/244343 and https://github.com/microsoft/vscode/issues/274524, but neither newer sticky-control request replaces this focus-loss report.
