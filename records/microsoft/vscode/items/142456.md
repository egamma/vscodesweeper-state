# Issue #142456 — Inconsistent keyboard shortcuts between Windows and Linux

[https://github.com/microsoft/vscode/issues/142456](https://github.com/microsoft/vscode/issues/142456)

## Summary

Keep open as an actively supported feature request: 40 community upvotes and recent migration feedback show sustained demand for a portable Windows-style keybinding mode on Linux. The existing keybinding customization and third-party extension are workarounds, but they do not provide the requested built-in, synchronized platform-layout choice.

## Change summary

Provide a built-in option to use and synchronize one default keyboard-shortcut layout across Windows and Linux.

## Best solution

Define a product-supported keybinding-profile mechanism that can select Windows defaults on Linux and persist that choice through Settings Sync, while preserving native platform defaults for users who do not opt in.

## Plan brief

- **Likely files:** `src/vs/platform/keybinding/common/keybindingsRegistry.ts`, `src/vs/workbench/services/keybinding/common/keybindingEditing.ts`, `src/vs/platform/userDataSync/common/userDataSync.ts`
- **Validation:** Add keybinding service and Settings Sync tests showing that selecting Windows defaults on Linux changes representative commands such as Format Document and navigation back/forward, survives synchronization and reload, and leaves the native Linux defaults unchanged when no alternate layout is selected.
- **Behavior:**

  > Users who work across Windows and Linux can explicitly select a Windows-compatible default keybinding layout on Linux and have that preference follow them through Settings Sync. The native platform layout remains the default unless the user opts into another layout. User-defined keybindings continue to override whichever default layout is selected, and unsupported or conflicting bindings are surfaced without silently discarding custom mappings.
- **Trace:**

  > The report concerns the platform-specific default keybinding registrations and how an optional layout selection would interact with user overrides and Settings Sync. The existing extension demonstrates that alternate defaults are possible, but the requested core behavior additionally needs stable precedence, conflict handling, and persistence semantics. The boundary is the keybinding/default-profile and sync layers: do not globally replace Linux defaults or alter users who have not selected another layout. Earlier discussions at https://github.com/microsoft/vscode/issues/17550 and https://github.com/microsoft/vscode/issues/38388 explain historical platform differences but do not resolve the broader selectable-layout request documented here.
- **Open decisions:**
  - Should the selected layout replace only platform-specific defaults, or act as a complete emulation profile including chords and reserved-key exceptions?
  - Should the layout choice synchronize globally, per profile, or remain machine-specific to avoid overriding intentional platform-native preferences?
  - How should VS Code report bindings unavailable because the desktop environment or window manager intercepts them?
  - Should alternate layouts be maintained in core or exposed through a first-class keybinding-profile extension API?

## Evidence

- **current classification:** The issue already carries the existing `keybindings` and `under-discussion` labels, matching the unresolved product decision.
- **community demand:** The issue has 40 body upvotes and independent reports spanning 2022 through December 2025 from users moving between or regularly using Windows and Linux.
- **central gap:** Comments identify specific divergent defaults including Format Document, Copy Line Up/Down, and navigation back/forward; the latest request explicitly asks for a selectable keyboard mapping mode that travels through Settings Sync.
- **existing workaround:** Commenters use the third-party `smcpeak.default-keys-windows` extension or manually recreate bindings, but report conflicts with other keybinding layers and reject this as equivalent to a built-in synchronized layout choice.
