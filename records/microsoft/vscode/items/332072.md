# Issue #332072 — Same-name user/workspace MCP collision leaves stopped server inoperable until server ID is renamed

[https://github.com/microsoft/vscode/issues/332072](https://github.com/microsoft/vscode/issues/332072)

## Summary

Well-diagnosed, reproducible bug: reporter gives a clean, deterministic repro (comment 3) showing that after a user/workspace MCP name collision, the workspace server customization stays bound to stale registration state (`Cannot start/stop unknown MCP server customization ...#mcp=<name>`) until a window reload, and reverting the rename reintroduces the stale state. Already correctly labeled `bug`/`agent-host`; no fix found on main and no canonical issue fully covers this.

## Change summary

When a user-scoped and workspace-scoped MCP server share the same ID, the losing/winning server's Agent Host customization can be left bound to stale lifecycle/registration state and become unstartable until the ID is changed and the window reloaded.

## Best solution

Investigate `McpCustomizationController` (src/vs/platform/agentHost/node/shared/mcpCustomizationController.ts) and the per-provider `startMcpServer`/`stopMcpServer` handlers (copilotAgentSession.ts, claudeAgentSession.ts, codexAgent.ts) to ensure that when `getEnabledLocalMcpServers()` in mcpWorkbenchService.ts picks a new collision winner, the customization id -> server-name mapping (and any provider-side registration keyed on the old identity) is invalidated/rebuilt rather than left pointing at a stale entry.
