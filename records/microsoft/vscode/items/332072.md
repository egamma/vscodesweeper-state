# Issue #332072 — Same-name user/workspace MCP collision leaves stopped server inoperable until server ID is renamed

[https://github.com/microsoft/vscode/issues/332072](https://github.com/microsoft/vscode/issues/332072)

## Summary

Real, well-diagnosed bug with an active fix already in flight — https://github.com/microsoft/vscode/pull/334412 directly targets `serverNameForCustomizationId()` in mcpCustomizationController.ts, and a second contributor (kondv) independently reproduced the exact stale-customization-id failure and traced its root cause in a comment. Per policy, an open linked PR keeps the issue open rather than closing it before merge.

## Change summary

When a user-scoped and workspace-scoped MCP server share the same ID, the losing/stale registration leaves the effective server stuck at 'Starting...' or logging 'Cannot start unknown MCP server customization ...#mcp=<id>', inoperable until the ID is renamed and the window reloaded.

## Best solution

Review and land https://github.com/microsoft/vscode/pull/334412, which keeps the live MCP customization lookup first and falls back to an exact ID match in session state instead of rejecting the collision winner's ID as unknown — this is the concrete fix for the stale lifecycle-id binding described here.
