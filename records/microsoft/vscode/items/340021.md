# Issue #340021 — Intermittent incorrect keyboard-layout mapping on X11: Some shortcuts stop working

[https://github.com/microsoft/vscode/issues/340021](https://github.com/microsoft/vscode/issues/340021)

Keep open: the reporter's paired diagnostics demonstrate US-style shortcut mappings despite Spanish layout metadata, and the latest comments confirm persistence in 1.144.0. The evidence supports investigation, but neither a fixing commit nor a same-symptom canonical issue was established.

## Change summary

Prevent intermittent incorrect shortcut resolution on Spanish X11 keyboards while text input continues to work correctly.

## Best solution

- **Validation:** On X11 with Spanish pc105 layout, compare Inspect Key Mappings across startup, additional windows, and focused/unfocused layout switches. Verify Digit7.withShift remains /, Ctrl+Shift+7 toggles line comments, and the terminal shortcut does not outdent; establish a repeatable failing case before choosing automated regression coverage.
- **Behavior:**

  > On a Spanish X11 keyboard, shortcut resolution must agree with the active layout even when text input already works correctly. The reported failure resolves Ctrl+/ through the US Slash position rather than Spanish Shift+Digit7 and can invoke outdent instead of the terminal toggle. Acceptance should cover startup, additional windows, and layout switching without requiring a focus-dependent recovery dance. Normal text input and intentional layout changes must remain unchanged.
- **Trace:**

  > The paired attachments in https://github.com/microsoft/vscode/issues/340021 show identical Spanish layout metadata but different raw mappings, including US-style punctuation in the broken instance. KeyboardLayoutMainService reads native-keymap and caches the result; NativeKeyboardLayoutService transfers that snapshot to the renderer, and KeyboardLayoutService constructs and invalidates a cached mapper on notifications. WorkbenchKeybindingService refreshes its mapper and resolver on the corresponding event. Desktop validateCurrentKeyboardMapping() performs no event-based verification. The trace does not establish whether the wrong snapshot originates in native-keymap, notification timing, or renderer state; diagnose that boundary before selecting a fix. Preserve ordinary layout switching, text input, and existing keyboard.dispatch behavior, and do not assume installed extensions caused the failure.

## Evidence

- **Paired diagnostics confirm incorrect mapping:** Both https://github.com/user-attachments/files/33155196/vscode-key-layout.bad.txt and https://github.com/user-attachments/files/33155195/vscode-key-layout.good.txt report layout es, model pc105, group 0. The bad report maps Ctrl+/ to ctrl+[Slash] and Digit7.withShift to &, whereas the good report maps Ctrl+/ to ctrl+shift+[Digit7] and Digit7.withShift to /. The discrepancy is present in Raw mapping, not merely command selection.

The temporary-profile instance working alongside a broken instance is additional evidence, but does not independently establish extension causation.
- **Current source boundary:** src/vs/platform/keyboardLayout/electron-main/keyboardLayoutMainService.ts reads native-keymap.getKeyMap() and getCurrentKeyboardLayout(), caches their results, and refreshes on native layout-change notifications. src/vs/workbench/services/keybinding/electron-browser/nativeKeyboardLayoutService.ts receives and caches that data; nativeKeyboardLayout.ts caches the resulting mapper and leaves validateCurrentKeyboardMapping() empty. This identifies the acquisition/update path, but does not conclusively locate the intermittent fault.
