# Issue #345646 — MCP local (stdio) servers from ~/.copilot/mcp-config.json fail with spawn ENOENT on Windows client + Remote WSL

[https://github.com/microsoft/vscode/issues/345646](https://github.com/microsoft/vscode/issues/345646)

## Summary

The home-directory discovery adapters still convert the remote home URI into a Windows path before launching on Linux. Keep this open while the existing, explicitly linked fix PR is reviewed and landed.

## Change summary

Make discovered stdio MCP servers start with a valid remote working directory when a Windows client connects to WSL.

## Best solution

Review and land https://github.com/microsoft/vscode/pull/345650 so home-directory discovery preserves the working-directory URI until resolution on the execution host, while retaining existing trust decisions and HTTP behavior.

## Evidence

- **Current source confirms the trigger:** In src/vs/workbench/contrib/mcp/common/discovery/nativeMcpDiscoveryAdapters.ts, ClaudeDesktopMpcDiscoveryAdapter.adaptFile and CopilotMpcDiscoveryAdapter.adaptFile still pass cwd: homedir. claudeConfigToServerDefinition assigns options.cwd.fsPath to stdio launch.cwd; Cursor and Windsurf inherit the Claude adapter behavior.
- **Cross-platform failure path:** src/vs/base/common/uri.ts uriToFsPath replaces forward slashes with backslashes on Windows. src/vs/workbench/api/node/extHostMcpNode.ts:103-124 prioritizes launch.cwd, treats the resulting backslash path as relative on Linux, joins it beneath the home directory, and passes that invalid directory to spawn. This accounts for ENOENT despite an existing absolute executable.
- **Existing implementation candidate:** https://github.com/microsoft/vscode/pull/345650 was verified open with merged_at null and explicitly says Fixes #345646. Its diff switches both adapter entry points to defaultCwd: homedir and adds coverage for all four discovery adapters, unchanged HTTP definitions, and trust nonce preservation. It is not yet a completed fix.
