- **Behavior:**

  > The reporter observes a crash or reload prompt after deleting a committed folder containing 10+ submodules while Source Control is open. The expected behavior is that the parent repository shows staged deletions and deleted submodule repositories are removed from Source Control without disrupting the window. First confirm the failure on a current build and identify whether the renderer, extension host, or another process terminates. Acceptance requires completing the same deletion with no process termination or reload prompt and correct remaining repository state.
- **Trace:**

  > Repository in extensions/git/src/repository.ts watches working-tree deletions and routes them through onFileChange, eventuallyUpdateWhenIdleAndWait, and status. Its run method transitions to RepositoryState.Disposed on NotAGitRepository errors; Model.open in extensions/git/src/model.ts listens for that state and disposes the repository, removes it from openRepositories, and emits onDidCloseRepository. Model.open also scans submodules after status updates. These paths establish where investigation can start, but inspection did not identify a crash-producing branch. Preserve existing submodule detection settings and ordinary status-refresh behavior; do not assume mass deletion requires changing discovery limits. The report at https://github.com/microsoft/vscode/issues/301920 includes multiple installed extensions and low free memory, so distinguish those factors from a built-in Git or Source Control defect before bounding the implementation.
