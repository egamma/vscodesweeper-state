# Issue #340502 — Memory tool's repo-scope storage (/memories/repo/) is placed outside the workspace, so it's lost in devcontainers on "Rebuild Container"

[https://github.com/microsoft/vscode/issues/340502](https://github.com/microsoft/vscode/issues/340502)

## Summary

Confirmed from source: the Copilot Chat memory tool's repo scope writes to extensionContext.storageUri (workspaceStorage) instead of the actual workspace folder, contradicting its own documented 'stored locally in the workspace' description and causing silent data loss on Dev Container rebuild.

## Change summary

Repo-scope memory notes are stored under ~/.vscode-server workspaceStorage rather than inside the workspace folder, so they are wiped when a Dev Container is rebuilt.

## Best solution

Move repo-scope memory storage to a location inside the actual workspace folder (e.g. a git-ignored dotfolder) so it survives container rebuilds, after a maintainer decides the exact directory, gitignore-by-default behavior, and multi-root workspace resolution.

- **Behavior:**

  > Files created via the memory tool's `repo` scope (/memories/repo/...) should persist across a Dev Container rebuild, since only the mounted workspace folder is guaranteed to survive that operation. Currently they are silently lost because they live in ~/.vscode-server workspaceStorage. After the fix, repo memory must live somewhere under the actual workspace folder (e.g. a git-ignored dotfolder), and the tool's documented description ('stored locally in the workspace') must match reality. User and session scopes are unaffected and should keep using extensionContext storage as today.
- **Trace:**

  > MemoryTool (extensions/copilot/src/extension/tools/node/memoryTool.tsx) resolves repo-scope URIs via `this.extensionContext.storageUri` in `_resolveUri`/`_dispatchLocal` (around lines 211-331), which maps to ~/.vscode-server/.../workspaceStorage/<hash>/GitHub.copilot-chat/memory-tool/memories/repo/ — outside the actual workspace. memoryContextPrompt.tsx:206 documents repo memory as 'stored locally in the workspace', which this path contradicts. The boundary: user and session scopes must keep their current storageUri-based paths; only the repo-scope path resolution changes. Open question is where in the workspace tree to place it and whether/how to auto-gitignore and handle multi-root workspaces — that is for the maintainer to decide before implementation, along with whether to migrate/discard existing workspaceStorage-based repo memories.
- **Open decisions:**
  - Which location inside the workspace folder should repo memory live in (e.g. a dedicated dotfolder like `.copilot/memories/` vs. reusing `.vscode/`), and should it be gitignored by default?
  - How should this resolve for multi-root workspaces (one memory store per root, or tied to a single primary root)?
  - Should existing repo-scope memories already stored under workspaceStorage be migrated, or simply left behind / discarded?
