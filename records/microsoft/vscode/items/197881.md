# Issue #197881 — [languages] contribution point `languages` provide the ability to extends

[https://github.com/microsoft/vscode/issues/197881](https://github.com/microsoft/vscode/issues/197881)

## Summary

A real extension API gap remains: a contributed language can define file associations but cannot inherit another language's grammar and language configuration while retaining a distinct language ID. The request is already routed to basic language support and should remain open for API design.

## Change summary

Allow a contributed language ID to reuse an existing language's grammar and language configuration while declaring its own file associations.

## Best solution

Define inheritance semantics for basic language assets so an extension can create a distinct language ID backed by another language's TextMate grammar and configuration, with explicit behavior for overrides, unavailable parents, cycles, and rich-language providers.

## Plan brief

- **Likely files:** `src/vs/workbench/services/language/common/languageService.ts`, `src/vs/editor/common/languages/language.ts`, `src/vs/editor/common/services/languageService.ts`, `src/vs/workbench/contrib/codeEditor/common/languageConfigurationExtensionPoint.ts`, `src/vs/workbench/services/textMate/common/TMGrammars.ts`, `src/vs/workbench/services/textMate/common/TMGrammarFactory.ts`
- **Validation:** Add focused extension-point/service tests with base and derived language contributions: files associated with the derived language retain its distinct ID, while the selected inherited assets behave like the base language; add missing-parent, cycle, and override cases according to the resolved contract.
- **Behavior:**

  > An extension can declare a distinct language ID with its own file associations while reusing designated basic-language behavior from an existing language. Files matching the child contribution remain identified as the child language and receive the agreed inherited grammar and language configuration. Explicit child declarations, unavailable parents, cycles, and activation of rich-language providers follow documented, deterministic rules.
- **Trace:**

  > The `languages` contribution schema and conversion live in src/vs/workbench/services/language/common/languageService.ts, and the resulting model is `ILanguageExtensionPoint` in src/vs/editor/common/languages/language.ts. Configuration loading follows `ILanguageService.getConfigurationFiles` through `LanguageConfigurationFileHandler` in src/vs/workbench/contrib/codeEditor/common/languageConfigurationExtensionPoint.ts. TextMate support is separate: `grammarsExtPoint` requires an extension-relative grammar path in src/vs/workbench/services/textMate/common/TMGrammars.ts, and `TMGrammarFactory` maps each language ID directly to one scope. The boundary is basic language registration, configuration, and tokenization; do not implicitly make providers registered for the parent language apply to the child unless that public behavior is explicitly chosen. The only linked issue, https://github.com/microsoft/vscode/issues/199003, concerns auto-indent and does not cover this API.
- **Open decisions:**
  - Does inheritance cover only TextMate grammar and declarative language configuration, or should rich-language activation and providers registered for the parent language also apply to the child ID?
  - Which child declarations override inherited assets, and are file associations, aliases, MIME types, icons, and configuration defaults intentionally excluded from inheritance?
  - What public behavior should extensions receive when the parent language is unavailable, an inheritance cycle exists, or multiple extensions contribute conflicting definitions?

## Evidence

- **current contribution schema:** src/vs/workbench/services/language/common/languageService.ts defines `IRawLanguageExtensionPoint` and the `languages` JSON schema with associations, aliases, configuration, and icons, but no inheritance or `extend` property.
- **configuration boundary:** WorkbenchLanguageService resolves each contributed `configuration` path relative to the contributing extension, while src/vs/workbench/contrib/codeEditor/common/languageConfigurationExtensionPoint.ts loads configuration files strictly for the requested language ID; there is no parent-language fallback.
- **grammar boundary:** src/vs/workbench/services/textMate/common/TMGrammars.ts requires every grammar contribution to provide its own `scopeName` and extension-relative `path`; src/vs/workbench/services/textMate/common/TMGrammarFactory.ts maps each language ID directly to such a grammar definition.
- **existing partial capability:** `files.associations` in WorkbenchLanguageService can associate a suffix with the existing `shellscript` ID, but it cannot create the distinct `shellscript1` language identity requested here.
- **related comment:** https://github.com/microsoft/vscode/issues/199003 concerns Shell Script auto-indent, was created after this issue, and does not own the requested language-contribution inheritance API.
- **canonical search:** Repository issue searches for language contribution inheritance, grammar reuse, and extending `contributes.languages` found no open canonical issue owning this request.
