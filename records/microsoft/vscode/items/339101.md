# Issue #339101 — [Error] unhandlederror-Tool "selectEnvironment" already has an implementation.

[https://github.com/microsoft/vscode/issues/339101](https://github.com/microsoft/vscode/issues/339101)

## Summary

Real, traceable defect: when an extension calls registerTool twice for the same tool id, ExtHostLanguageModelTools.registerTool has no duplicate guard and fires a second fire-and-forget $registerTool RPC, which the main thread rejects via registerToolImplementation's throw — surfacing as an unhandled error and silently dropping the second registration. The related analysis issue (#339108) argues this is a pre-existing defect re-bucketed by a telemetry-serialization change, not a true regression, so the 'recent-regression' label is likely mislabeled, but the underlying bug is genuine.

## Change summary

Registering a Language Model tool implementation twice for the same id throws across the ExtHost→MainThread RPC boundary and surfaces as an unhandled error instead of failing cleanly or being guarded against.

## Best solution

Add a duplicate-id guard in ExtHostLanguageModelTools.registerTool/registerToolDefinition (src/vs/workbench/api/common/extHostLanguageModelTools.ts) so a second registration for the same id either throws a clear, catchable ExtHost-side error or is handled before crossing the fire-and-forget RPC, rather than letting the main-thread rejection surface as telemetry noise.

The chosen behavior (synchronous throw to the extension author, or silently replacing/ignoring the duplicate) must be well-defined and not depend on a fire-and-forget cross-process RPC rejection.
- **Trace:**

  > ExtHostLanguageModelTools.registerTool/registerToolDefinition (src/vs/workbench/api/common/extHostLanguageModelTools.ts:344-384) unconditionally overwrite `_registeredTools` and re-fire `$proxy.$registerTool(id, ...)` without checking whether `id` is already registered. The main thread's registerToolImplementation (src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts:358-359) throws on a duplicate impl, and because the ExtHost call site never awaits/catches that RPC, the rejection becomes an unhandled error (see stack trace in the issue). Do not change the main-thread throw semantics for other callers of registerToolImplementation/registerToolData; the fix belongs at the ExtHost producer side. Related: https://github.com/microsoft/vscode/issues/339108 (root-cause analysis, no merged fix) and https://github.com/microsoft/vscode/issues/339102 (same code area, different symptom).
- **Open decisions:**
  - Should a second registerTool call with the same id throw synchronously on the extension side (clear API contract violation), or silently replace/ignore the duplicate (more forgiving for activation-timing races)?
