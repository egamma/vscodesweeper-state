## Evidence

- **Missing trigger evidence:** https://github.com/microsoft/vscode/issues/331493 describes intermittent failures and recovery by merging indexes, but provides no actual UNC example, paired workspace.json folder URIs, or opening sequence that establishes whether identical paths produce different hashes. Path aliases and NAS availability are hypotheses; there are no independent reproduction comments.
- **Workspace identity inputs:** src/vs/platform/workspaces/node/workspaces.ts:getSingleFolderWorkspaceIdentifier hashes folderUri.fsPath plus folder creation-time metadata on Windows, using Math.floor(folderStat.birthtimeMs) when available. Identical path and creation-time inputs produce the same identity; different aliases or changed creation-time metadata can produce different identities. The function explicitly warns that existing identifiers must remain stable.
- **Folder-opening path:** src/vs/platform/windows/electron-main/windowsMainService.ts passes URI.file(path) and pathStat to getSingleFolderWorkspaceIdentifier when opening a local directory. The source establishes the inputs, but does not prove which input changed on the reporter's NAS.
- **Chat storage boundary:** src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts selects workspaceStorageHome/<workspaceId>/chatSessions in its constructor. internalGetIndex reads chat.ChatSessionStore.index from StorageScope.WORKSPACE for folder workspaces, so a different workspace ID can hide existing sessions without deleting them. Workspace-transition migration exists, but does not establish recovery across independent reopenings under alternate identities.
- **Related reports are not verified duplicates:** https://github.com/microsoft/vscode/issues/313681 is open and describes deliberate switching between symlink and resolved paths on macOS. https://github.com/microsoft/vscode/issues/324249 is open and describes chat loss following a crash with a WSL UNC folder. Neither establishes the same cause as intermittent NAS identity changes.
- **Network-filesystem precedent:** https://github.com/microsoft/vscode/issues/107429 is closed and traced changing storage hashes to synthetic SSHFS inode values on Linux. https://github.com/microsoft/vscode/issues/107429#issuecomment-699593435 suggests a locally stored multi-root workspace file as a workaround. This supports investigating filesystem identity metadata, not declaring the Windows NAS case fixed, upstream-owned, or a duplicate.
