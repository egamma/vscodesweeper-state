# Issue #339024 — Crash reports on Windows include the full process environment (incl. user env-var secrets); please document this and revisit the default

[https://github.com/microsoft/vscode/issues/339024](https://github.com/microsoft/vscode/issues/339024)

## Summary

Keep open for human security and privacy review: the current startup and configuration paths support the reported crash-reporting guidance gap, and existing controls do not address the disclosure or default-upload requests. The credential-exposure concern independently prohibits a close proposal.

## Change summary

Document Windows crash-dump contents, destination and retention, correct opt-out instructions, and reconsider default minidump uploads.

## Best solution

Have the crash-reporting and privacy owners establish accurate content, destination, retention and opt-out documentation, with documentation work coordinated in microsoft/vscode-docs. They should explicitly decide the minidump consent/default policy while preserving existing telemetry opt-out and enterprise controls; upstream capture ownership does not resolve these VS Code responsibilities.

## Evidence

- **security-sensitive scope:** The complete report at https://github.com/microsoft/vscode/issues/339024 describes environment-variable credentials in locally inspected dumps marked as uploaded, while explicitly withholding secret values and acknowledging that server-side handling is unknown. This requires human review and triggers the hard keep-open rule.
- **current startup ordering:** src/main.ts now delegates to src/mainImpl.ts. In src/mainImpl.ts:85–99,178,419–438, startup reads argv.json and initializes crash reporting before app.ready when enable-crash-reporter is enabled or a crash-reporter-directory is supplied. This substantiates the reported externally edited settings.json scenario when argv.json still contains the old enabled value.
- **generated guidance and subsequent rewrite:** src/vs/code/electron-main/app.ts:1695–1696,1829–1866 calls updateCrashReporterEnablement after window opening, derives enablement from telemetryLevel >= TelemetryLevel.CRASH, generates the comment 'Allows to disable crash reporting.', and rewrites the existing argv value. This updates future startup configuration rather than stopping the reporter already initialized during that launch.
- **existing controls do not cover the full request:** src/vs/platform/telemetry/common/telemetryService.ts:275–360 registers telemetry.telemetryLevel with default all, a restart notice and the TelemetryLevel enterprise policy. src/mainImpl.ts:487–576 controls uploads using development status, destination availability and crash-reporter-directory. These controls do not supply environment-variable disclosure, a retention period, or the requested separate consent for minidump attachments.
- **upstream versus product responsibility:** The issue-linked Crashpad source at https://github.com/chromium/crashpad/blob/ce308a86daa85e65df219ff5fb385095b0a1c467/snapshot/win/process_snapshot_win.cc#L439-L442 explicitly adds process_parameters.Environment to extra memory. VS Code selects the upload URL from product.appCenter in src/mainImpl.ts:487–576. The inspected checkout does not establish the exact shipped endpoint, bundled Crashpad provenance or server retention; these remain owner-verification questions.
- **published documentation gap:** The current https://code.visualstudio.com/docs/configure/telemetry describes crash reports as diagnostic information sent to Microsoft and mentions valid retention policies, but does not disclose Windows environment-block capture or a concrete retention period. Its telemetry-off instructions do not explain the reported startup gap.

Searches for open crash/environment and crash/minidump/telemetry reports did not establish an older canonical covering the same observable problem.
