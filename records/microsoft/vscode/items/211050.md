# Issue #211050 — Diff editor does not render custom label

[https://github.com/microsoft/vscode/issues/211050](https://github.com/microsoft/vscode/issues/211050)

## Summary

The bug remains source-reproducible on current main: Git supplies a preferred diff title, and DiffEditorInput gives that title precedence over the resource inputs' custom labels. This team-authored Backlog issue is the canonical report and should remain open while the intended title-composition contract is decided.

## Change summary

Git diff editor tabs and Open Editors entries ignore workbench.editor.customLabels.patterns because the Git-provided diff title replaces the custom resource label.

## Best solution

Define how custom resource labels compose with an explicit vscode.diff title, then preserve Git's contextual status such as “Working Tree” or “Index” while displaying the configured custom file label in tabs and Open Editors.

## Plan brief

- **Likely files:** `extensions/git/src/repository.ts`, `src/vs/workbench/browser/parts/editor/editorCommands.ts`, `src/vs/workbench/services/textfile/common/textEditorService.ts`, `src/vs/workbench/common/editor/diffEditorInput.ts`, `src/vs/workbench/test/browser/parts/editor/diffEditorInput.test.ts`
- **Validation:** Add a focused editor-input test that opens or constructs a titled diff whose resource inputs have custom labels and asserts the resulting tab name contains the custom file label while retaining the chosen Git context; also verify an explicit vscode.diff title without custom labels remains unchanged.
- **Behavior:**

  > When workbench.editor.customLabels.patterns matches a file opened from Git Changes, the diff tab and Open Editors entry display that custom file label. Git context such as Working Tree, Index, Deleted, Ours, or Theirs remains available according to the composition semantics selected by the maintainer. Diff editors without a matching custom label retain their current titles, and extension-provided vscode.diff titles must follow the selected compatibility contract.
- **Trace:**

  > Git's ResourceCommandResolver.resolveChangeCommand in extensions/git/src/repository.ts passes getTitle(resource) as the vscode.diff title. The command conversion in src/vs/workbench/browser/parts/editor/editorCommands.ts stores it as the untyped input label; TextEditorService.createTextEditor in src/vs/workbench/services/textfile/common/textEditorService.ts then constructs DiffEditorInput with that preferred name. DiffEditorInput.computeLabels in src/vs/workbench/common/editor/diffEditorInput.ts gives preferredName absolute precedence, bypassing the custom names computed by AbstractResourceEditorInput in src/vs/workbench/common/editor/resourceEditorInput.ts. The boundary includes all vscode.diff callers because the title argument is public extension-facing behavior; do not silently discard explicit titles or alter ordinary file-editor custom labels. https://github.com/microsoft/vscode/issues/209931 separated this path into the current issue, while https://github.com/microsoft/vscode/issues/212673 confirms this issue is the canonical report.
- **Open decisions:**
  - When a resource has a custom label and vscode.diff also supplies an explicit title, should the custom label replace only the filename portion while preserving contextual text, or should the explicit title continue to take full precedence?
  - Should the composition behavior apply uniformly to every vscode.diff caller, or only to titles supplied by the built-in Git integration?
