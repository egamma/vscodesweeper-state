# Issue #224338 — Codelens references for properties of object in root module scope

[https://github.com/microsoft/vscode/issues/224338](https://github.com/microsoft/vscode/issues/224338)

## Summary

Keep this accepted feature request open: current TypeScript CodeLens filtering still excludes object-literal properties, and existing settings do not enable them. The request has 28 upvotes and is already correctly routed to the TypeScript backlog; eligibility and default behavior need a product decision.

## Change summary

Allow references CodeLens on properties of selected object literals, particularly module-scope, exported, or const-asserted objects.

## Best solution

Extend the built-in JavaScript/TypeScript references CodeLens capability with an agreed eligibility rule for object-literal properties, preserving the suppression of noisy local and inline object members. Decide whether this is opt-in and whether const assertions independently qualify before implementation.

Assert the agreed property-lens locations and resolved reference counts, including a reference to foo; retain checks that excluded local/inline objects stay lens-free and existing class and enum behavior remains unchanged. If opt-in, cover both enabled and disabled states.
- **Behavior:**

  > Users can obtain reference-count CodeLens on properties of object literals that meet the eligibility policy chosen by the maintainer. Use the issue's rootScopeObj, exportedObj, exportedConstObj, and function-returned const-asserted object as the acceptance matrix, stating explicitly which qualify. Eligible property lenses must resolve references to that property and navigate to them. Object categories excluded by the policy must remain free of property lenses, and existing class, enum, and exported-declaration behavior must remain unchanged.
- **Trace:**

  > TypeScriptBaseCodeLensProvider in extensions/typescript-language-features/src/languageFeatures/codeLens/baseCodeLensProvider.ts requests the tsserver navtree and recursively passes each node and its immediate parent to extractSymbol. TypeScriptReferencesCodeLensProvider.extractSymbol in referencesCodeLens.ts restricts member properties to class/interface/type parents, while accepting enum members separately and exported variable declarations themselves. Its configuration currently exposes only enabled and showOnAllFunctions, so neither enables object-property lenses. The smoke suite explicitly expects no lenses for an ordinary const object literal. https://github.com/microsoft/vscode/issues/86495 documents why indiscriminately enabling literal members would regress editor noise; preserve that boundary outside the agreed categories. The remaining uncertainty is the observable eligibility policy and default, including whether navtree metadata can express the selected const-assertion distinction without additional language-service support.
- **Open decisions:**
  - Which object categories qualify: all module-scope objects, only exported module-scope objects, or some other explicitly defined subset?
  - Does an as const assertion independently qualify an object outside module scope, including the function-returned example?
  - Should qualifying property lenses appear whenever references CodeLens is enabled, or require a separate opt-in control?

## Evidence

- **Current capability gap:** extensions/typescript-language-features/src/languageFeatures/codeLens/referencesCodeLens.ts: TypeScriptReferencesCodeLensProvider.extractSymbol accepts member properties only when their parent is a class, interface, or type. Exported variable declarations can receive a lens, but their object-literal properties do not qualify; enum members have a separate acceptance path.
- **Existing settings do not cover the request:** extensions/typescript-language-features/package.json registers js/ts.referencesCodeLens.enabled and js/ts.referencesCodeLens.showOnAllFunctions. The provider reads only these two controls; showOnAllFunctions affects function symbols, not object-literal properties. There is no property-eligibility setting in this configuration surface.
- **Existing exclusion is deliberate:** extensions/typescript-language-features/src/test/smoke/referencesCodeLens.test.ts contains 'Should not show on const property', expecting zero lenses for a non-exported object literal. The requested expansion therefore changes an established eligibility policy rather than repairing an accidental omission.

Its maintainer confirmation at https://github.com/microsoft/vscode/issues/86495#issuecomment-566140536 reports that regression resolved; it does not settle this request for selectively restoring useful property lenses.

The supplied discussion records promotion after reaching the community threshold, but does not settle which object categories should qualify.
