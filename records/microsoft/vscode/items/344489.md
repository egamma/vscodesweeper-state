# Issue #344489 — Transparently reconcile awesome-copilot and GitHub Feed installs and migrate existing plugins

[https://github.com/microsoft/vscode/issues/344489](https://github.com/microsoft/vscode/issues/344489)

## Summary

Keep open: current source has partial installation matching, but does not establish the requested end-to-end equivalence and migration contract between awesome-copilot and GitHub Feed. The related SDK-ownership migration overlaps with adoption safety, but does not cover compatibility across both installation entry points.

## Change summary

Reconcile equivalent awesome-copilot and GitHub Feed plugins across install links, discovery, installed state, and safe migration of existing installations.

Coordinate ownership migration with https://github.com/microsoft/vscode/issues/343334 while retaining this issue's distinct link-compatibility and canvas-discovery acceptance criteria.

- **Validation:** Extend the existing pluginUrlHandler, customizationMarketplaceInstallService, agentHostCustomizationMarketplaceInstallProvider, and aiCustomizationDiscoveryPage test suites. Cover equivalent installations through each entry point in both orders, unrelated same-name plugins remaining distinct, disabled legacy installations, repeated migration, failed replacement with retry, and consistent Canvases visibility and installed state.
- **Behavior:**

  > Installing an equivalent plugin through an awesome-copilot link or GitHub Feed must recognize an existing installation rather than create duplicate contributions or contradictory installed states. Existing awesome-copilot installations must remain functional during adoption, with applicable enablement decisions preserved. Repeated migration must be safe, and failures must leave a working installation available with a retry path. Corresponding canvases must remain discoverable with consistent installed state, and old and new install links must have defined compatible behavior.
- **Trace:**

  > PluginUrlHandler queries a marketplace and invokes its harness install provider directly. AgentHostCustomizationMarketplaceInstallProvider.install has separate providerCatalog preparation/application and name@marketplace plugin-install paths. CustomizationMarketplaceInstallService.matchesProviderInstallation already supplies partial associations, but explicitly excludes configuredPlugin-to-providerCatalog matching; hiding the default marketplace in PluginCustomizationMarketplaceProvider does not migrate installed content. This source inspection establishes relevant boundaries, not runtime duplication or the SDK's internal reconciliation behavior. Coordinate with https://github.com/microsoft/vscode/issues/343334 for ownership migration, without treating its broader adoption work as proof of source equivalence. Preserve trust prompts, unrelated plugin identities, and compatibility for consumers of legacy installations.
- **Open decisions:**
  - What authoritative identity or catalog mapping establishes that an awesome-copilot plugin and a GitHub Feed entry are equivalent, including when their revisions differ?
  - After verified equivalence, should both old marketplace links and Feed installs converge on one installation ownership model, and what behavior is supported when the Feed or SDK capability is unavailable?

- **Partial identity matching already exists:** src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceInstallService.ts:236-283 implements matchesProviderInstallation and findProviderInstallation. Matching includes compatible versions and external URLs, configured-plugin name/marketplace pairs, and repository/path checks for some installation kinds. In src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationMarketplaceInstallProvider.ts:343-389, providerCatalog installs use prepare/confirmAndApplyCatalogResource, whereas configuredPlugin and providerPlugin installs call installPlugin with name@marketplace. The inspected paths do not establish that equivalent catalog and marketplace installations converge.

This changes discovery visibility, not ownership or cross-source equivalence. customizationMarketplaceConfiguration.ts exposes discovery/feed switches, not an installed-plugin migration or reconciliation setting.
