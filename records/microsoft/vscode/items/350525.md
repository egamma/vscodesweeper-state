# Issue #350525 — Chat pet: declarative pet registry and extension contribution point (contributes.chatPets)

[https://github.com/microsoft/vscode/issues/350525](https://github.com/microsoft/vscode/issues/350525)

## Summary

Keep open for maintainer design review: current customization does not support extension-contributed pet definitions. The existing pet umbrella expresses interest in extensibility, but does not settle this proposal's public contract or implementation split.

## Change summary

Support declarative extension-contributed chat pets with appearance selection and existing pet capabilities in both window types.

## Best solution

Agree on a minimal declarative pet contribution contract that preserves Blobby's behavior and opt-in enablement, then stage internal generalization and extension support around that contract. Coordinate with the existing mini-pet and taught-move PRs without expanding their scope.

## Vision fit

- **Fit:** aligned
- **Reason:** Letting extensions supply optional pet content advances extension extensibility without requiring more bundled pets or always-on UI.
- **Evidence:** Public values: "The power lives in extensions" and "Out of the box, VS Code is a text editor: lightweight and fast."

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chatPetService.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatPetWidget.ts`, `src/vs/workbench/contrib/chat/browser/chatPetAchievementPreview.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatPetJumpGame.ts`, `src/vs/workbench/services/extensions/common/extensionManifestPropertiesService.ts`
- **Validation:** The plan should end with registry/manifest tests for valid and invalid definitions and disable/uninstall fallback, plus a declarative-only sample extension exercised in Editor and Agents windows. Check per-window selection, reduced motion, accessible pet names, accessory/game parity, and recoloring in desktop, web, and remote scenarios while preserving existing Blobby behavior.
- **Behavior:**

  > An extension can contribute a selectable pet without executable renderer code. Selection works independently for Editor and Agents windows, and unavailable contributed pets fall back to Blobby. Supported animations, colors, accessories, previews, and jump-game announcements reflect the selected definition. Existing opt-in enablement, reduced-motion behavior, and Blobby customization remain unchanged; the minimum required capability set needs maintainer agreement.
- **Trace:**

  > ChatPetService currently models window-specific colors and accessories, not pet identity. ChatPetWidget resolves state names and timings to bundled buddy assets; static previews and accessible game text likewise assume Blobby. The sessions-window declarative contribution allowlist does not include chatPets. The open umbrella https://github.com/microsoft/vscode/issues/328270 establishes interest in extension contributions but no schema. The related PRs https://github.com/microsoft/vscode/pull/346367, https://github.com/microsoft/vscode/pull/338664, and https://github.com/microsoft/vscode/pull/338833 concern separate mini-pet and taught-move behavior that must remain compatible. No code was executed; extension placement and canvas-readability guarantees remain unverified.
- **Open decisions:**
  - What minimum states and capabilities must a contributed pet provide, and which may use fallbacks or explicitly opt out?
  - Should the first public contract include both palette-based recoloring and named skins, including how existing color and accessory selections behave when switching pets?

## Evidence

- **Complete proposal:** Read the full body and comment at https://github.com/microsoft/vscode/issues/350525. The previously truncated ending explicitly asks maintainers to approve the contribution direction and decide whether internal generalization and the proposed extension contract should be reviewed separately.
- **Existing capability does not cover the ask:** src/vs/workbench/contrib/chat/browser/chatPetService.ts exposes per-window colors and accessories, but no pet-definition selection. chatPetAchievements.contribution.ts offers Customize Blobby and Change Color actions; these customize the existing pet rather than accept extension-defined pets. Searches across src and extensions found no chatPets, IChatPetDefinition, IChatPetRegistry, or chat.vscodePet.petId registration.
- **Current rendering boundary:** In src/vs/workbench/contrib/chat/browser/widget/chatPetWidget.ts, getChatPetSpriteName selects buddy-* assets and createSpriteSources resolves them from the bundled chatPet media directory. chatPetAchievementPreview.ts also constructs a bundled buddy-idle asset, while chatPetJumpGame.ts contains Blobby-specific accessible labels.
- **Extension eligibility needs design:** src/vs/workbench/services/extensions/common/extensionManifestPropertiesService.ts has a declarative contribution allowlist without chatPets. The proposal's local/web resource-loading and canvas-readability claims require validation; the existing allowlist alone does not establish those guarantees.
- **Related umbrella, not a duplicate canonical:** https://github.com/microsoft/vscode/issues/328270 is open and includes an unchecked 'Extension contributable' item. It collects varied pet requests rather than defining this declarative registry contract, so it supplies design context rather than grounds for closing this focused proposal.
- **Related PRs do different work:** Read the open PRs https://github.com/microsoft/vscode/pull/346367, https://github.com/microsoft/vscode/pull/338664, and https://github.com/microsoft/vscode/pull/338833. They cover subagent mini pets and taught moves/interactions, not extension-contributed pet definitions. An open-PR search for 350525 returned no matches.
