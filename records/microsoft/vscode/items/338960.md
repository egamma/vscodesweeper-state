# Issue #338960 — Agent Host resumes a completed Copilot turn after state divergence, causing assistant-prefill 400

[https://github.com/microsoft/vscode/issues/338960](https://github.com/microsoft/vscode/issues/338960)

## Summary

Fresh, well-diagnosed team-authored bug report; traced the exact code path on current main and it matches the description — no fix has landed, so this stays open (and team-authored items can't be closed on judgment anyway).

## Change summary

After a runtime completes a turn out-of-band (e.g. following an ENOSPC interruption), AHP's locally-persisted turn state can remain `Error`/resumable even though the runtime transcript already ended with a final assistant message; clicking Try Again then dispatches `chat/turnResume` and the provider 400s on an attempted zero-message/assistant-prefill continuation, looping forever.

## Best solution

Before dispatching `chat/turnResume` in `_handleResumedTurn`, reconcile against the runtime's durable completion state (or at least treat a stale/rejected resume as an already-completed result instead of retrying the model) — but the exact mechanism needs a maintainer design call (see open decisions).

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts`
- **Validation:** A test/scenario asserting that resuming a turn whose runtime transcript already ended with a final assistant message does not dispatch chat/turnResume (or gracefully short-circuits to the completed result) instead of hitting the provider's assistant-prefill rejection.
- **Behavior:**

  > When a turn's AHP state is Error/resumable but the underlying runtime session already completed (ended with a final assistant message and sessionEnd reason 'complete'), selecting Try Again must not repeatedly dispatch a resume that the provider rejects with a 400. Instead the UI should surface the already-completed result or a clear non-retryable state. Acceptance: Try Again on such a stale turn no longer produces a repeating prefill-rejection error.
- **Trace:**

  > _handleResumedTurn in agentHostSessionHandler.ts (around line 3321) derives `resumableTurn`/`shouldDispatchResume` solely from the locally persisted AHP turn state, without checking whether the runtime's durable transcript has since completed. The boundary: do not change the normal (non-stale) resume path, where the runtime transcript still legitimately ends with a user turn awaiting continuation — only the stale-completion case needs new reconciliation. Open question is where/how to source 'the runtime already completed' signal (a fresh status query to the backend session, or relying on the existing transcript state already available via `_getSessionState`).
- **Open decisions:**
  - Should VS Code actively reconcile against the runtime's durable completion state before dispatching chat/turnResume (requiring a new or existing query to the backend session), or is it acceptable to let the resume attempt fail and instead gracefully recover from the resulting rejection/400 by treating it as already-completed?
  - Is the runtime completion signal already available locally (e.g. via the transcript already fetched in `_getSessionState`) or does this require a new protocol call to AHP/runtime?
