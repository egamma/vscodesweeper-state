## Plan brief

- **Validation:** On a Windows reproduction machine, run the reported streaming workload in two split terminals with gpuAcceleration=auto and off, recording renderer handle counts, GPU-process memory, and desktop responsiveness. - **Behavior:**

  > Sustained terminal output in two splits must not cause unbounded renderer handle growth or freeze the Windows desktop. The reporter observes the failure on both 1.134.0 and 1.135.0 and reports relief when Claude Code terminal use is disabled. First establish a repeatable baseline with process-specific resource measurements; acceptance requires bounded resources and responsive desktop behavior under the same workload, without dropping terminal output.
- **Trace:**

  > Current renderer selection is controlled by terminal.integrated.gpuAcceleration in src/vs/workbench/contrib/terminal/common/terminalConfiguration.ts and XtermTerminal._shouldLoadWebgl in src/vs/workbench/contrib/terminal/browser/xterm/xtermTerminal.ts. _enableWebglRenderer loads the xterm WebGL addon, handles context loss, and falls back to DOM; _disposeOfWebglRenderer disposes the addon. Inspection did not establish a leaking path, and canvas is not a supported configuration value. The uncertainty starts at identifying the growing handle type and whether equivalent output reproduces independently of the extension. Preserve terminal output correctness and existing renderer-selection semantics. https://github.com/microsoft/vscode/issues/337393 is a comparison lead, not an established canonical, because its GPU-memory symptom is avoided by disabling terminal GPU acceleration.
