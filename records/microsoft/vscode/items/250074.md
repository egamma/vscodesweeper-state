# Issue #250074 — Can't use both env and envFile for MCP server configuration

[https://github.com/microsoft/vscode/issues/250074](https://github.com/microsoft/vscode/issues/250074)

## Summary

Keep open: env and envFile already work together, but envFile contents still do not participate in ${env:NAME} substitution—the expectation clarified by the author. The maintainer acknowledged room for improvement, and this team-authored Backlog item has neither a verified fixing commit nor an eligible duplicate.

## Change summary

Make MCP environment-file values usable or clearly explain their unavailability during configuration-variable substitution.

## Best solution

Settle whether MCP variable resolution should include envFile values or retain the existing process-environment-only contract. Document the chosen resolution order and explicit-env precedence in the MCP configuration guidance and schema descriptions; ordinary merging of env and envFile already works.

## Evidence

- **Clarified request and maintainer response:** The author clarified that ENDPOINT should resolve AZURE_INFERENCE_ENDPOINT from envFile. The maintainer explained that variable substitution precedes reading envFile and acknowledged that behavior or documentation could improve: https://github.com/microsoft/vscode/issues/250074#issuecomment-2921199637 and https://github.com/microsoft/vscode/issues/250074#issuecomment-2922701066.
- **Current resolution order:** src/vs/workbench/contrib/mcp/common/mcpRegistry.ts, _replaceVariablesInLaunch and resolveConnection, resolves configuration variables before launching the server. src/vs/workbench/services/configurationResolver/common/variableResolver.ts resolves missing env references to an empty string; it does not load the MCP envFile.
- **Existing capability and remaining gap:** src/vs/workbench/api/node/extHostMcpNode.ts, startNodeMpc, copies process.env, reads launch.envFile, then overlays launch.env before spawn. Both fields are supported together, but a previously resolved empty env value can overwrite a file value, and mapping a differently named file variable through ${env:NAME} remains unsupported.
- **Configuration guidance:** src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts registers envFile and env together. Their descriptions identify the file and server environment but do not explain substitution timing or override precedence.
- **Related reports are not verified canonicals:** https://github.com/microsoft/vscode/issues/246517 describes the same envFile-substitution expectation in args but is closed, so it cannot serve as a duplicate canonical. Searches found no verified older open issue owning this precise behavior; https://github.com/microsoft/vscode/issues/340161 concerns portable-configuration migration and is newer.
- **Later comment concerns a separate symptom:** https://github.com/microsoft/vscode/issues/250074#issuecomment-3335034416 reports stale process-environment substitution without an envFile. Its linked report, https://github.com/microsoft/vscode/issues/261203, is closed; neither establishes resolution of the original envFile expectation.
