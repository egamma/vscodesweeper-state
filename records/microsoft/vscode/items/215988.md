# Issue #215988 — "Cannot set property activeDebugSession of #<Object> which has only a getter" when trying to change active debug session

[https://github.com/microsoft/vscode/issues/215988](https://github.com/microsoft/vscode/issues/215988)

## Summary

The requested extension API remains missing on current main: extensions can observe the active debug session but cannot select one programmatically. This should remain open for an API design decision, with the existing `debug` area routing.

## Change summary

Allow an extension to make a specific existing debug session active so extension-provided session selectors stay synchronized with VS Code.

## Best solution

Provide an explicit, documented extension API for user-initiated selection of an existing debug session, while preserving VS Code's existing focus behavior and active-session change event.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostDebugService.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadDebugService.ts`, `src/vs/workbench/contrib/debug/test/browser/debugViewModel.test.ts`
- **Validation:** Add extension-host/main-thread API tests that select one of multiple debug sessions, assert that it becomes the focused session and fires `onDidChangeActiveDebugSession`, and assert that an unknown or terminated session is rejected without changing focus.
- **Behavior:**

  > An extension can request that a specific running debug session become VS Code's active session. A successful request updates the same global selection used by VS Code's debug UI and emits `debug.onDidChangeActiveDebugSession`; it does not create, restart, or terminate a session. Invalid or no-longer-running sessions are rejected without changing the current selection. Existing user-driven session selection and observation remain unchanged.
- **Trace:**

  > The public declaration in src/vscode-dts/vscode.d.ts currently uses `export let activeDebugSession`, but src/vs/workbench/api/common/extHost.api.impl.ts implements it as a getter, which explains the reported exception. ExtHostDebugServiceBase in src/vs/workbench/api/common/extHostDebugService.ts only receives `$acceptDebugSessionActiveChanged`, and MainThreadDebugServiceShape in src/vs/workbench/api/common/extHost.protocol.ts has no reverse RPC for selecting a session. Internally, DebugService.focusStackFrame in src/vs/workbench/contrib/debug/browser/debugService.ts and DebugViewModel.setFocus in src/vs/workbench/contrib/debug/common/debugViewModel.ts already own the focused-session transition; src/vs/workbench/api/browser/mainThreadDebugService.ts forwards that transition back to extensions. The existing `workbench.action.debug.selectDebugSession` command only opens a picker and accepts no target session. Keep session lifecycle, stack-frame selection semantics, and the picker UI outside the scope unless the chosen public contract requires otherwise. https://github.com/microsoft/vscode/issues/216555 addresses readonly declaration accuracy only, while https://github.com/Dart-Code/Dart-Code/issues/5146 documents the blocked extension scenario.
- **Open decisions:**
  - Should extensions be allowed to change the globally active debug session, and must that operation be limited by contract to an explicit user action?
  - Should the stable contract be an explicit method or command accepting a `DebugSession`, rather than making `activeDebugSession` writable?

## Evidence

- **current API implementation:** src/vs/workbench/api/common/extHost.api.impl.ts exposes `debug.activeDebugSession` through a getter only; src/vs/workbench/api/common/extHostDebugService.ts likewise has only a getter and receives active-session changes from the main thread.
- **missing RPC:** MainThreadDebugServiceShape in src/vs/workbench/api/common/extHost.protocol.ts supports starting, stopping, and renaming debug sessions but has no operation for selecting the active session.
- **existing internal mechanism:** src/vs/workbench/contrib/debug/common/debugViewModel.ts and src/vs/workbench/contrib/debug/browser/debugService.ts already implement session focus internally through `setFocus` and `focusStackFrame`; mainThreadDebugService.ts forwards resulting focus changes to extensions.
- **picker is not programmatic selection:** The `workbench.action.debug.selectDebugSession` handler in src/vs/workbench/contrib/debug/browser/debugCommands.ts accepts no session argument and only opens `showDebugSessionMenu`, so it does not satisfy the central request.
- **related API cleanup:** https://github.com/microsoft/vscode/issues/216555 remains open and concerns changing misleading `let` declarations to readonly declarations; it does not provide an API for selecting a session and is not a duplicate.
- **downstream use case:** https://github.com/Dart-Code/Dart-Code/issues/5146 remains open and explicitly identifies this issue as blocking synchronization of Dart's sidebar session selection.
- **demand and status:** The request is assigned to the Backlog milestone, has 11 community upvotes, and a VS Code maintainer engaged on the API semantics without rejecting the capability.
