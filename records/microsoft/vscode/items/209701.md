# Issue #209701 — New line support in labels and `workbench.editor.customLabels.patterns` setting

[https://github.com/microsoft/vscode/issues/209701](https://github.com/microsoft/vscode/issues/209701)

## Summary

This remains a distinct, well-supported backlog feature request: 23 community upvotes meet the promotion threshold, and current main still renders custom labels as single-line tab names. The older API issue contains the originating discussion, but a maintainer explicitly requested this focused issue, so it should not be consolidated as a duplicate.

## Change summary

Allow `workbench.editor.customLabels.patterns` to produce two-line editor tab labels, reducing horizontal space for projects with many similarly named files.

## Best solution

Let custom editor-label patterns express a compact primary and secondary tab line while preserving existing single-line behavior by default, accessible naming, and uniform tab-row layout. A maintainer should first settle whether this is literal newline support or an explicit name/description model, and which editor-label surfaces inherit it.

## Plan brief

- **Likely files:** `src/vs/workbench/services/editor/common/customEditorLabelService.ts`, `src/vs/workbench/common/editor/resourceEditorInput.ts`, `src/vs/workbench/browser/workbench.contribution.ts`, `src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts`, `src/vs/workbench/browser/parts/editor/media/editortabscontrol.css`, `src/vs/workbench/browser/parts/editor/media/multieditortabscontrol.css`, `src/vs/workbench/services/editor/test/browser/customEditorLabelService.test.ts`, `src/vs/workbench/test/browser/parts/editor/multiEditorTabsControl.test.ts`
- **Validation:** Add and run targeted custom-label service and multi-editor-tabs tests proving that a configured two-line label renders as two accessible tab lines, ordinary labels remain single-line, and non-tab label surfaces follow the chosen contract.
- **Behavior:**

  > Users can configure a custom editor label with a primary and secondary line so similarly named files remain distinguishable without consuming excessive horizontal tab space. Existing pattern templates and ordinary tabs remain single-line by default. The resulting tab must retain a coherent accessible name, preserve icons and tab actions, and behave correctly with tab wrapping and sizing modes.
- **Trace:**

  > `CustomEditorLabelService.getName` in `src/vs/workbench/services/editor/common/customEditorLabelService.ts` currently returns one string, which `ResourceEditorInput` installs as the editor name. `MultiEditorTabsControl.redrawTabLabel` already receives separate name and description fields, but the custom-label service cannot populate that distinction; the tab CSS also enforces no wrapping and a shared fixed height. The setting schema in `src/vs/workbench/browser/workbench.contribution.ts` documents only scalar string templates, while the same service is consumed by quick access and other non-tab surfaces, so multiline propagation is a public behavior choice. Preserve current single-line templates and unrelated editor descriptions; the uncertainty begins at the representation and surface scope, not at whether horizontal tab identification should improve. Related context: https://github.com/microsoft/vscode/issues/41909.
- **Open decisions:**
  - Should the setting treat `\n` as literal multiline name content, or expose distinct primary-name and secondary-description semantics?
  - Should the second line apply only to editor tabs, or become part of the custom label shown in quick access, editor titles, and other consumers of `CustomEditorLabelService`?
  - Should a multiline label increase the shared tab-row height uniformly, or can matching tabs use a different presentation without disrupting alignment and wrapped-tab layout?
