# Issue #162428 — Make tree view more stable

[https://github.com/microsoft/vscode/issues/162428](https://github.com/microsoft/vscode/issues/162428)

## Summary

A real Explorer polish gap remains: creating a folder still expands, refreshes, and reveals tree elements through several scroll-affecting paths, with no test ensuring that already-visible content keeps a stable position. The older related issue concerns focus replacement after deletion, not this re-reviewed item's observable scroll jump, so it is not a valid duplicate.

## Change summary

Keep the Explorer tree's scroll position stable when creating and revealing a folder unless scrolling is necessary to expose the new item.

## Best solution

Reproduce the reported folder-creation sequence against the current Explorer, identify whether the jump comes from the editable-item reveal, expansion refresh, or post-creation selection, and preserve the viewport anchor while still minimally revealing an off-screen new item.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/fileActions.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`, `src/vs/base/browser/ui/list/listWidget.ts`
- **Validation:** Add an Explorer browser test with a scrolled tree and an expanded visible parent: entering folder-creation edit mode and completing creation must preserve scrollTop when the new row is fully visible, while a new row outside the viewport must be revealed with only the minimum necessary scroll.
- **Behavior:**

  > Creating a folder under a visible Explorer folder should not unexpectedly reposition the surrounding tree rows. Expanding the parent and showing the editable or completed child may scroll only when the child would otherwise be outside the viewport, and that scroll should be minimal. Existing selection, focus, folder expansion, and off-screen reveal behavior must remain intact.
- **Trace:**

  > openExplorerAndCreate in src/vs/workbench/contrib/files/browser/fileActions.ts inserts a NewExplorerItem and calls IExplorerService.setEditable; after successful creation it calls select(resourceToCreate, true). ExplorerView.setEditable in src/vs/workbench/contrib/files/browser/views/explorerView.ts expands and refreshes the parent before calling tree.reveal(stat). ExplorerView.selectResource later checks getRelativeTop and uses tree.reveal(item, 0.5) when the completed folder is not entirely visible. List.reveal in src/vs/base/browser/ui/list/listWidget.ts distinguishes minimal reveal from explicit relative positioning. The uncertainty starts at determining whether the recorded jump is caused by expansion/refresh anchoring, the editable-item reveal, or the post-create centered reveal; preserve unrelated active-editor auto-reveal behavior and generic tree semantics.

## Evidence

- **creation path:** src/vs/workbench/contrib/files/browser/fileActions.ts openExplorerAndCreate adds a temporary NewExplorerItem, enters editable mode, and after folder creation calls explorerService.select(resourceToCreate, true).
- **scroll-affecting paths:** src/vs/workbench/contrib/files/browser/views/explorerView.ts ExplorerView.setEditable expands the parent, refreshes it, and calls tree.reveal(stat); selectResource later centers the created folder with tree.reveal(item, 0.5) when getRelativeTop reports it is not entirely visible.
- **tree behavior:** src/vs/base/browser/ui/list/listWidget.ts List.reveal performs minimal scrolling without relativeTop, while a relativeTop value explicitly repositions the item. The remaining uncertainty is which reveal/refresh transition produces the recorded jump.
- **existing capability:** The explorer.autoReveal focusNoScroll behavior tracked by https://github.com/microsoft/vscode/issues/23902 applies to active-editor auto-reveal; folder creation explicitly requests selection and reveal, so it does not cover this report.
- **related issue:** https://github.com/microsoft/vscode/issues/126964 is older and open, but it tracks keyboard focus moving when a focused tree item disappears. It does not report the same folder-creation scroll jump required for a duplicate close on this re-reviewed item.
- **test gap:** src/vs/workbench/contrib/files/test/browser/explorerView.test.ts exercises Explorer tree interactions but has no folder-creation/editable-item viewport-stability coverage.
