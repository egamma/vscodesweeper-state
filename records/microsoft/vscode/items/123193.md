# Issue #123193 — Support fragment in Uri label formatter

[https://github.com/microsoft/vscode/issues/123193](https://github.com/microsoft/vscode/issues/123193)

## Summary

A real gap remains on current main: resource label formatters can substitute scheme, authority, path, and JSON query fields, but cannot use a URI fragment. The accepted Backlog request should remain open for a small formatter-contract design decision.

## Change summary

Allow URI label formatters to incorporate the fragment used to distinguish notebook cells, metadata, and outputs.

## Best solution

Extend the resource-label formatting contract with fragment substitution semantics consistent with its existing URI tokens, then let notebook resource formatters produce labels that distinguish fragment-addressed resources.

## Plan brief

- **Likely files:** `src/vs/workbench/services/label/common/labelService.ts`, `src/vs/workbench/services/label/test/browser/label.test.ts`, `src/vs/workbench/contrib/notebook/browser/notebook.contribution.ts`
- **Validation:** Add targeted LabelService unit cases for the chosen fragment syntax, covering populated and absent fragments, then verify notebook metadata/output labels can distinguish otherwise-identical URIs whose fragments differ.
- **Behavior:**

  > A resource label formatter can include information from a URI fragment, allowing notebook cell metadata and output resources with the same path but different fragments to receive distinct labels. Existing scheme, authority, path, query, relative-label, and basename behavior remains unchanged. Acceptance should cover both a populated fragment and a URI with no fragment, plus two notebook-style resources differentiated only by fragment.
- **Trace:**

  > LabelService.formatUri in src/vs/workbench/services/label/common/labelService.ts performs all formatter-token substitution and currently never reads URI.fragment. Existing structured query support is tested in src/vs/workbench/services/label/test/browser/label.test.ts, while CellInfoContentProvider in src/vs/workbench/contrib/notebook/browser/notebook.contribution.ts registers the affected notebook metadata/output formatters. The reporter's query-based workaround discussion is at https://github.com/microsoft/vscode/issues/123193#issuecomment-833854082, but it does not expose the fragment already present on these URIs. Keep the boundary to resource-label formatting and its notebook consumer; URI identity and serialization semantics must not change.
- **Open decisions:**
  - Should the formatter contract expose the fragment as one raw `${fragment}` value, or support structured fragment fields analogous to `${query.name}` when the fragment contains encoded JSON?

## Evidence

- **current source gap:** On current main, LabelService.formatUri in src/vs/workbench/services/label/common/labelService.ts handles `scheme`, `authority`, `authoritySuffix`, `path`, and structured `query` substitutions; its default branch returns an empty string for unsupported tokens, and it never reads `resource.fragment`.
- **notebook consumer:** CellInfoContentProvider in src/vs/workbench/contrib/notebook/browser/notebook.contribution.ts registers formatters for notebook cell metadata and output URI schemes using only `${path}`, so fragment-derived cell identity still cannot be represented.
- **existing workaround is incomplete:** The suggestion at https://github.com/microsoft/vscode/issues/123193#issuecomment-833854082 points to JSON query substitution, but the reported notebook resources encode their identity in the URI fragment; moving that identity into the query is not equivalent formatter support.
- **canonical search:** Searches for open issues about URI fragments in resource label formatters or notebook cell label formatters found no older issue owning the same observable request.
