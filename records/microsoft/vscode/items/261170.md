# Issue #261170 — Option to disable search highlighting from updating PRIMARY selection (Linux/X11 & Wayland)

[https://github.com/microsoft/vscode/issues/261170](https://github.com/microsoft/vscode/issues/261170)

## Summary

The search-result path still explicitly writes programmatically selected matches to PRIMARY on Linux. Keep this open: existing settings do not preserve normal mouse selection while suppressing those writes, and the related input-selection reports do not clearly own this separate editor path.

## Change summary

Prevent automatic Find match selection from replacing Linux PRIMARY while retaining explicit selection and middle-click workflows.

## Best solution

Preserve PRIMARY during automatic Find highlighting without disabling ordinary selection copying or changing match navigation. Settle whether this is corrected by default or exposed as an opt-out before implementing the editor-side behavior.

- **Likely files:** `src/vs/editor/contrib/find/browser/findModel.ts`, `src/vs/editor/common/config/editorOptions.ts`, `src/vs/workbench/contrib/codeEditor/electron-browser/selectionClipboard.ts`

Retest the reported sequence on Linux/X11 and Wayland/XWayland with Klipper, including middle-click paste and next/previous match navigation.
- **Behavior:**

  > On Linux, selecting text in another application and then typing a query in VS Code Find must not unexpectedly replace PRIMARY with the automatically selected match under the agreed preservation behavior. Find highlighting and navigation must continue to work, and explicit mouse selections must retain their normal PRIMARY-copy behavior. Acceptance must distinguish preservation of PRIMARY from disabling selection support altogether.
- **Trace:**

  > FindModelBoundToEditorModel.research() in src/vs/editor/contrib/find/browser/findModel.ts advances to a match while typing with the default cursorMoveOnType setting; _setCurrentFindMatch() installs that match as the editor selection. SelectionClipboard in src/vs/workbench/contrib/codeEditor/electron-browser/selectionClipboard.ts observes the selection change and explicitly writes its text to PRIMARY after 100 ms, excluding restoreState but not Find. This confirms an editor-side path independently of native input-selection behavior. Existing editor.selectionClipboard disables the whole workflow, while seedSearchStringFromSelection only changes query seeding. Preserve ordinary selection copying, middle-click paste, and Find navigation; do not expand this work into unrelated programmatic-selection cases. Related input work is tracked at https://github.com/microsoft/vscode/issues/130208 and https://github.com/microsoft/vscode/issues/167266, with an input-only candidate at https://github.com/microsoft/vscode/pull/301137. The remaining uncertainty is whether PRIMARY preservation becomes the default or requires a new Find-specific opt-out.
- **Open decisions:**
  - Should automatic Find match selection preserve PRIMARY by default, or should existing copying remain the default with a Find-specific opt-out setting?

## Evidence

- **Current editor-side reproduction path:** In src/vs/editor/contrib/find/browser/findModel.ts, research() calls _moveToNextMatch() when cursorMoveOnType is enabled; _setCurrentFindMatch(), lines 255–264, calls this._editor.setSelection(match). In src/vs/workbench/contrib/codeEditor/electron-browser/selectionClipboard.ts, SelectionClipboard schedules copying for cursor-selection changes except restoreState, then calls clipboardService.writeText(textToCopy, 'selection') after 100 ms. Ordinary nonempty Find matches therefore reach an explicit PRIMARY write without mouse selection. This was traced from source, not executed on Linux.
- **Existing settings do not cover the requested boundary:** src/vs/editor/common/config/editorOptions.ts registers editor.selectionClipboard as a global Linux PRIMARY-support switch, not a Find-specific control; disabling it also disables normal selection copying and suppresses middle-button paste through LinuxSelectionClipboardPastePreventer. editor.find.cursorMoveOnType disables automatic cursor movement rather than independently preserving PRIMARY. editor.find.seedSearchStringFromSelection controls query seeding, and editor.find.globalFindClipboard is macOS-only.
- **Older related reports verified:** https://github.com/microsoft/vscode/issues/130208 is open and reports PRIMARY being overwritten by prefilled Find-input text; its suggested workaround changes query seeding. https://github.com/microsoft/vscode/issues/197495 is open and describes that input behavior propagating into CLIPBOARD through Klipper synchronization. Neither establishes ownership of the distinct editor-match write traced here. The reporter explicitly linked both, along with https://github.com/microsoft/vscode/issues/86645, whose discussion also mentions search-result overwrites but which is closed and cannot serve as a duplicate canonical.
- **Related open implementation has narrower scope:** https://github.com/microsoft/vscode/issues/167266 is open and concerns PRIMARY overwrites in input controls. Its open implementation candidate, https://github.com/microsoft/vscode/pull/301137, changes InputBox.select() and quick-input tests only; it does not change FindModelBoundToEditorModel or SelectionClipboard and does not reference this issue. It should not be mistaken for a fix of the editor-match copying path.
- **Upstream report is not evidence of resolution:** https://github.com/electron/electron/issues/26563 includes both programmatic input selection and search-result copying, but was closed for missing a standalone reproduction, not because a fix landed. The explicit VS Code clipboard write identified here means the reported match-copying behavior cannot be attributed solely to Electron.
