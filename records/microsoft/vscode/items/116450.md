# Issue #116450 — Find widget focus movement could be improved

[https://github.com/microsoft/vscode/issues/116450](https://github.com/microsoft/vscode/issues/116450)

## Summary

Keep open: current source still gives enabled find-widget buttons individual tab stops and does not provide left/right navigation across the right-side actions. Related Search reports were consolidated into this issue, so it remains the appropriate owner of the remaining keyboard-navigation improvement.

## Change summary

Make find-widget action groups single tab stops with arrow-key navigation while keeping Find in Selection reachable in both directions.

## Best solution

Bring the find widget's option and action groups into the established toolbar keyboard-navigation model, preserving text-input editing and find/replace behavior. Settle the group boundaries and tab sequence before changing the shared FindInput.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/find/browser/findWidget.ts`, `src/vs/base/browser/ui/findinput/findInput.ts`, `src/vs/base/browser/ui/findinput/findInputToggles.ts`, `src/vs/base/test/browser/ui/findinput/findInputToggles.test.ts`
- **Validation:** In a running VS Code window, open a file with multiple matches and a nonempty selection, then open Find. Record forward and backward Tab traversal with Replace collapsed and expanded; each agreed action group must occupy one tab stop, left/right must reach all enabled controls in that group, and Find in Selection must remain reachable. Repeat with no matches and disabled navigation buttons; verify activation, Escape dismissal, and ordinary left/right caret movement in both text inputs.
- **Behavior:**

  > The find widget should use the established toolbar model: Tab enters or leaves an action group, and left/right arrows move between its enabled controls. Find in Selection must remain keyboard reachable during forward and backward traversal. The behavior must work with Replace expanded or collapsed and when match-navigation actions are disabled. Text-input caret movement, action activation, and existing find/replace semantics must remain unchanged.
- **Trace:**

  > FindWidget._buildDomNode in src/vs/editor/contrib/find/browser/findWidget.ts assembles previous/next buttons and Find in Selection directly into find-actions, with Close created separately. SimpleButton sets every enabled button to tabIndex=0 and provides activation handling but no horizontal focus navigation. Shared FindInput already calls navigateToggles from src/vs/base/browser/ui/findinput/findInputToggles.ts, but that navigation is restricted to the inline options. _onFindInputKeyDown, _onReplaceInputKeyDown, and option-specific handlers impose a custom tab sequence, including a Preserve Case handler that can focus Find in Selection. The trace establishes the remaining grouping gap, not a universal inability to focus the selection toggle. Preserve search and replacement semantics and avoid imposing unintended keyboard changes on other consumers of the shared input. Related Search work was consolidated here via https://github.com/microsoft/vscode/issues/116454 and https://github.com/microsoft/vscode/issues/132828; https://github.com/microsoft/vscode/issues/193331 concerns a separate shortcut request.
- **Open decisions:**
  - Should the inline find options and the right-side find actions be separate single-tab groups or one combined group, and where should Close and replacement actions fall in the resulting forward/backward tab sequence?

## Evidence

- **Remaining behavior in current source:** src/vs/editor/contrib/find/browser/findWidget.ts:1091–1135 constructs the right-side controls as separate SimpleButton and Toggle elements, not an ActionBar. SimpleButton at lines 1418 and 1454–1457 assigns each enabled button tabIndex=0; its key handler at lines 1432–1438 handles activation, not left/right navigation. No enclosing arrow-navigation handler appears in FindWidget.
- **Existing capability is partial:** src/vs/base/browser/ui/findinput/findInput.ts installs navigateToggles only within the input's own DOM node. src/vs/base/browser/ui/findinput/findInputToggles.ts provides left/right cycling among those inline toggles, but cannot reach the separate find-actions controls. EditorFind registrations in src/vs/editor/common/config/editorOptions.ts expose no setting for single-tab action groups; editor.tabFocusMode controls editor Tab handling rather than this widget's toolbar navigation.
- **Find in Selection needs a qualified assessment:** The supplied discussion on https://github.com/microsoft/vscode/issues/116450 includes amunger's December 2022 confirmation of Tab reachability and roblourens's report of asymmetric forward/backward traversal. Current findWidget.ts:1188–1201 explicitly focuses Find in Selection from Preserve Case when earlier navigation buttons are disabled. The original blanket claim that it cannot receive keyboard focus is therefore not sufficient grounds to describe all current configurations as broken.
