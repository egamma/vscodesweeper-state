# Issue #210411 — Portable version of VSCode uses absolute path for location entry in data\extensions\extensions.json

[https://github.com/microsoft/vscode/issues/210411](https://github.com/microsoft/vscode/issues/210411)

## Summary

The portable installation already relocates correctly through `relativeLocation`, but current main still writes the obsolete absolute `location` for backward compatibility. A maintainer accepted removing that redundant path as worthwhile cleanup, so the Backlog item remains valid.

## Change summary

Avoid storing machine-specific absolute extension paths in the portable installation's `data/extensions/extensions.json` manifest.

## Best solution

Portable manifests should retain `relativeLocation`, which provides relocatability, while avoiding a stale machine-specific absolute location once the compatibility impact on older clients is resolved.

## Plan brief

- **Likely files:** `src/vs/platform/extensionManagement/common/extensionsProfileScannerService.ts`, `src/vs/platform/extensionManagement/node/extensionsProfileScannerService.ts`, `src/vs/platform/extensionManagement/electron-browser/extensionsProfileScannerService.ts`, `src/vs/platform/extensionManagement/test/common/extensionsProfileScannerService.test.ts`
- **Validation:** Add targeted ExtensionsProfileScannerService tests showing that portable-mode serialization retains `relativeLocation` without a machine-specific absolute path, can scan the manifest after changing the extension root, and preserves the established non-portable compatibility behavior.
- **Behavior:**

  > A portable VS Code installation must continue loading installed extensions after its directory is moved to another path or device. Its extension manifest should not expose the previous machine-specific installation path when a relative location completely identifies the extension. Existing non-portable profile behavior and support for extensions outside the normal extension root must remain intact.
- **Trace:**

  > AbstractExtensionsProfileScannerService in src/vs/platform/extensionManagement/common/extensionsProfileScannerService.ts already prefers `relativeLocation` while scanning, then resolves it against the current `extensionsLocation`. The write path nevertheless emits the absolute URI alongside `relativeLocation`, explicitly to support old clients, and the common scanner tests lock in that dual-field format. Native scanner subclasses receive `INativeEnvironmentService`, but portable-state propagation into this layer is not currently explicit. The boundary is extension-profile persistence and compatibility: do not remove `relativeLocation`, because that is the mechanism that makes relocation work, and do not alter entries whose extension lives outside the configured extension root.
- **Open decisions:**
  - Should omission of the absolute `location` apply only in portable mode, or should every entry with a valid `relativeLocation` use the relative-only format?
  - What backward-compatibility window is required for older clients that depend on the absolute `location` field?
  - Should existing portable manifests be rewritten to remove absolute paths when read, or should the new format apply only on subsequent manifest updates?

## Evidence

- **maintainer direction:** The maintainer comment at https://github.com/microsoft/vscode/issues/210411#issuecomment-2310279521 confirms that `relativeLocation` provides portability and agrees that avoiding the absolute location in portable mode would be cleaner.
