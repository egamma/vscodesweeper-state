# Issue #180442 — Create different visuals on editor for different type of code actions

[https://github.com/microsoft/vscode/issues/180442](https://github.com/microsoft/vscode/issues/180442)

## Summary

A real gap remains on current main: the editor-surface indicator distinguishes preferred quick fixes and AI actions, but still uses the generic lightbulb for refactorings. The request is accepted in the Backlog and should remain open for an icon and mixed-action precedence decision.

## Change summary

Use distinct editor-surface indicators for quick fixes, refactorings, and other code-action kinds.

## Best solution

Extend the editor lightbulb presentation to reflect the available `CodeActionKind`, following the visual vocabulary already used in the code-action menu, while defining a predictable indicator when several kinds are available together.

- **Fit:** aligned
- **Reason:** Clear differentiation between editor actions improves the developer inner loop and reinforces consistent workbench interactions without adding a new always-on surface.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/codeAction/browser/lightBulbWidget.ts`, `src/vs/editor/contrib/codeAction/browser/codeAction.ts`, `src/vs/editor/contrib/codeAction/browser/codeActionMenu.ts`, `src/vs/editor/contrib/codeAction/test/browser`
- **Validation:** Add unit coverage for `computeLightBulbInfo` using quick-fix-only, refactor-only, source-only, AI, and mixed-kind action sets, asserting the selected icon and preserving existing AI/preferred-fix behavior.
- **Behavior:**

  > The editor-surface code-action indicator should communicate whether the available action is a quick fix, refactoring, source action, or AI action instead of presenting ordinary refactorings as the same generic lightbulb. Existing preferred-quick-fix and AI distinctions must remain intact. When multiple action kinds are available, the indicator must follow a documented, deterministic precedence. Acceptance should cover each supported kind and representative mixed sets.
- **Trace:**

  > On current main, `computeLightBulbInfo` in src/vs/editor/contrib/codeAction/browser/lightBulbWidget.ts chooses icons from aggregate AI and preferred-quick-fix flags, then falls back to `Codicon.lightBulb`; it does not inspect each action's `kind`. `ManagedCodeActionSet` in src/vs/editor/contrib/codeAction/browser/codeAction.ts exposes `hasAutoFix`, `hasAIFix`, and `allAIFixes`, but no general kind summary. The menu path in src/vs/editor/contrib/codeAction/browser/codeActionMenu.ts already classifies `CodeActionKind` values and supplies wrench, surround, and source icons. Preserve the existing AI and preferred-fix semantics and avoid changing code-action discovery, ordering, or menu grouping. https://github.com/microsoft/vscode/issues/132109 covers the menu distinction only; https://github.com/microsoft/vscode/issues/211700 concerns notebook entry-point duplication and is not canonical for this request.
- **Open decisions:**
  - Which editor-surface icon should win when quick fixes, refactorings, source actions, and AI actions are available at the same position?
  - Should the editor-surface indicator distinguish every menu category or only the top-level quick-fix, refactor, source, and AI categories?

## Evidence
