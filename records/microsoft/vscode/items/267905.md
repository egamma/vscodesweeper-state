# Issue #267905 — [Source Control]: not able to show diff/staged view of git lfs files

[https://github.com/microsoft/vscode/issues/267905](https://github.com/microsoft/vscode/issues/267905)

## Summary

Keep open: current main explains why Git LFS images cannot be previewed, but still does not display their staged or historical contents. The newer image-preview fixes improve the error presentation without resolving that central problem, and no eligible open canonical was found.

## Change summary

Display Git LFS image contents when opening staged changes and Git diffs in Source Control.

## Best solution

Make locally available LFS image contents previewable for the exact staged or historical revision, without substituting the working-tree image. Coordinate the Git content provider and media preview behavior, retaining the explicit unavailable-content message when the referenced object cannot be resolved.

## Plan brief

- **Likely files:** `extensions/git/src/git.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/fileSystemProvider.ts`, `extensions/media-preview/src/mediaPreview.ts`, `extensions/media-preview/src/imagePreview/index.ts`
- **Validation:** In a disposable test repository with Git LFS installed, commit image A, stage image B, then leave image C unstaged. Open the staged image diff and verify that it shows A and B, not C. Repeat with a non-LFS image and with an unavailable referenced LFS object; ordinary previews must remain unchanged and unavailable content must produce an explicit message.
- **Behavior:**

  > Source Control cannot preview an LFS-managed image when its Git revision contains a pointer, even when the referenced image is available locally. The desired result is a preview of the exact staged or historical image, not the working-tree version. Acceptance must distinguish committed, staged, and unstaged image contents and preserve ordinary non-LFS previews. Missing LFS content must remain clearly identified rather than appearing as a generic image-decoding failure.
- **Trace:**

  > GitFileSystemProvider.readFile in extensions/git/src/fileSystemProvider.ts resolves the ref and calls Repository.buffer, which reaches git show --textconv in extensions/git/src/git.ts. No explicit LFS object resolution occurs on this path. MediaPreview.isGitLfsPointer in extensions/media-preview/src/mediaPreview.ts recognizes the returned pointer; ImagePreview.getResourcePath then suppresses image loading and selects the LFS-unavailable presentation. https://github.com/microsoft/vscode/pull/315424 implements that presentation only, while https://github.com/microsoft/vscode/pull/314581 fixes a separate resource-root problem. The historical workaround is recorded at https://github.com/microsoft/vscode/issues/86611#issuecomment-875894108. The unresolved boundary is whether expanded LFS bytes belong to the shared Git resource contract or only the media-preview flow; other Git-resource consumers and textconv behavior need examination before implementation. Preserve revision identity, existing user-configured conversions, and the explicit unavailable-content fallback.
- **Open decisions:**
  - Should LFS expansion apply to all Git virtual-file consumers, including text views, or only to media previews?

## Evidence

- **Reported trigger:** https://github.com/microsoft/vscode/issues/267905 reports that staging an LFS-managed image and opening it from Source Control produces an image-loading error; the reporter also checked with extensions disabled.
- **Current Git content path:** extensions/git/src/fileSystemProvider.ts:readFile delegates to Repository.buffer after resolving the Git ref. extensions/git/src/repository.ts:buffer delegates to extensions/git/src/git.ts:buffer, which executes git show --textconv <ref>:<path>. This path does not itself resolve LFS pointers into their referenced image objects.
- **Remaining gap confirmed in source:** extensions/media-preview/src/mediaPreview.ts:isGitLfsPointer recognizes small git: resources beginning with the LFS pointer header. extensions/media-preview/src/imagePreview/index.ts:getResourcePath returns null for those resources, and extensions/media-preview/media/imagePreview.js selects the git-lfs message instead of loading an image. Thus an ordinary LFS pointer returned by the Git provider still cannot be previewed; this was traced without executing the application.
- **Partial fix, not completion:** https://github.com/microsoft/vscode/pull/315424, merged as 5ccceabd723a6be55edff4eef00963772b3bcd6f, adds LFS-pointer detection and the message 'The image is stored with Git LFS and is not available for preview.' Its diff changes error handling, not LFS object retrieval. It fixes the narrower presentation issue https://github.com/microsoft/vscode/issues/315423, not the missing preview capability here.
- **Separate non-LFS fix:** https://github.com/microsoft/vscode/pull/314581 strips query and fragment from image-preview resource roots. Its description explicitly excludes LFS files, so it is not evidence that this report is fixed.
- **Older report and workaround:** https://github.com/microsoft/vscode/issues/86611 describes the same LFS image-loading symptom. A commenter reported that git config diff.lfs.textconv cat made both sides work, and a maintainer closed that issue based on the workaround: https://github.com/microsoft/vscode/issues/86611#issuecomment-875894108 and https://github.com/microsoft/vscode/issues/86611#issuecomment-1855697712. It is closed, so it cannot serve as a duplicate canonical; repository-specific configuration is also not automatic coverage of this accepted bug.
