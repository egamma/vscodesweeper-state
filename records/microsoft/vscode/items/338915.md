# Issue #338915 — "This is taking a little longer than usual" shows while a foreground terminal command is running

[https://github.com/microsoft/vscode/issues/338915](https://github.com/microsoft/vscode/issues/338915)

## Summary

Well-diagnosed, reproducible bug: the delayed-progress message ('This is taking a little longer than usual') is still armed on main during an executing foreground terminal invocation because neither `response.model.onDidChange` nor `getPersistentActivityLabel` treat a running foreground tool as activity — confirmed by reading the cited code paths directly.

## Change summary

Under `chat.experimental.persistentProgress`, the 90s 'taking longer than usual' footer message incorrectly appears while a foreground terminal command (or other executing tool) is still actively running.

## Best solution

Extend the activity-detection logic in `getPersistentActivityLabel`/`getPersistentBackgroundActivity` (chatListRenderer.ts) and/or the reset condition in `ChatWorkingProgressContentPart` (chatProgressContentPart.ts) so an executing foreground tool invocation — not just background terminals and blocking read calls — counts as activity and suppresses or resets the delayed message.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatProgressContentPart.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatToolPartUtilities.ts`
- **Validation:** A test (or manual repro per the issue's steps) asserting that during a long-running foreground run_in_terminal invocation, `showDelayedProgressMessage`/the delayed scheduler is suppressed or reset, so the footer never shows 'This is taking a little longer than usual' while the tool is still Executing.
- **Behavior:**

  > While any tool invocation (in particular a foreground terminal command via run_in_terminal) is actively Executing, the chat footer must never show the 90s 'This is taking a little longer than usual' delayed-progress message — that message should only appear when the agent/model has genuinely stopped producing activity. Acceptance: running a >90s foreground terminal command with `chat.experimental.persistentProgress` enabled does not trigger the delayed message while the command is still running; the message still appears correctly when the agent is truly idle.
- **Trace:**

  > `ChatWorkingProgressContentPart` (chatContentParts/chatProgressContentPart.ts:358-468) arms a RunOnceScheduler at 90s and only resets it on `response.model.onDidChange`. `Response` in chatModel.ts only fires that change on tool-invocation state transitions or toolSpecificDataKind changes, not on terminal output/progress updates mid-execution. Separately, `getPersistentActivityLabel` (chatListRenderer.ts:6001-6024) — which drives `showDelayedProgressMessage: !activityLabel` via `getPersistentWorkingProgress` — only produces a label for background terminals (`isActiveBackgroundTerminalToolInvocation`, chatToolPartUtilities.ts:28), active subagents, or pending `read_terminal`/`read_agent` calls; a foreground `run_in_terminal` invocation gets no label and so is treated as idle. The boundary: do not change the background-terminal/subagent label behavior, which is correct as-is; scope the fix to foreground/executing-tool detection. Open question is exactly how broad that detection should be (see openDecisions).
- **Open decisions:**
  - Should the delayed message be suppressed for ANY tool invocation left in the `Executing` state, or only specifically for foreground terminal (`run_in_terminal`) invocations as the issue's narrower proposed fix suggests?
  - Should a visible activity label (e.g. 'Running command') be shown for an executing foreground terminal invocation (consistent with the background-terminal label), or should the delayed message simply be suppressed with no replacement label?
