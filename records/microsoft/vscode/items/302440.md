# Issue #302440 — Expose conversation/session metadata (for example UUID) to custom agents, prompts, and tools

[https://github.com/microsoft/vscode/issues/302440](https://github.com/microsoft/vscode/issues/302440)

## Summary

A real customization API gap remains: current main has stable internal chat, request, and provenance identifiers, but does not expose a documented conversation-chain metadata contract to custom agents, prompt files, or tools. The request should be routed to the chat customization, tools, and subagent owners for API design.

## Change summary

Expose stable opaque conversation, root/parent conversation, turn, active-agent, and entrypoint metadata to custom agents, prompts, and tools.

## Best solution

Define one privacy-scoped metadata contract at the customization execution boundary, derived from the existing chat session resource and origin model, then expose the applicable fields consistently to prompt variables and tool invocations. The contract should specify stability across reload, compaction, forks, handoffs, and subagent creation before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.chatParticipantPrivate.d.ts`, `extensions/copilot/src/extension/prompt/vscode-node/promptVariablesService.ts`, `extensions/copilot/src/extension/tools/node/executionSubagentTool.ts`, `src/vs/platform/agentHost/common/agent.ts`
- **Validation:** Add focused API and prompt-variable tests proving that the conversation identifier remains stable across turns, turn identifiers change per request, and subagent invocations receive distinct local identity plus the correct root/parent provenance.
- **Behavior:**

  > Custom agents, prompt files, and supported tool implementations can obtain a documented opaque identifier for the current conversation. The conversation identifier remains stable across turns, persistence, and compaction, while each request has a distinct turn identifier. Delegated or subagent runs can distinguish their own conversation from their root and direct parent and can identify the active agent and entrypoint. No exposed identifier contains user-identifying information.
- **Trace:**

  > The extension-private ChatRequest contract in src/vscode-dts/vscode.proposed.chatParticipantPrivate.d.ts already carries request, session-resource, and subagent fields. PromptVariablesServiceImpl in extensions/copilot/src/extension/prompt/vscode-node/promptVariablesService.ts receives a sessionId but currently publishes only prompt-folder and debug-log variables. Agent Host already records user, fork, side-chat, and tool-spawned provenance through IAgentChatContext and ChatOrigin in src/vs/platform/agentHost/common/agent.ts and src/vs/platform/agentHost/common/state/protocol/channels-chat/state.ts. The uncertainty begins at the supported public boundary: prompt variables, tool invocation metadata, an extension API, or a shared subset across them. Preserve the distinction between VS Code application session identity, Agent Host session identity, exact chat identity, provider-native conversation identity, and request identity.
- **Open decisions:**
  - Which consumers are part of the supported v1 contract: prompt and agent files, extension language-model tools, MCP tools, or all of them?
  - Should root and parent identity follow the Agent Host session/chat graph, provider-native conversations, or a newly defined opaque logical conversation-chain identity across handoffs and subagents?
  - What lifetime and privacy scope is guaranteed for each identifier across reload, restore, compaction, workspace changes, forks, and exported diagnostics?

## Evidence

- **existing private API:** src/vscode-dts/vscode.proposed.chatParticipantPrivate.d.ts exposes ChatRequest.id, sessionResource, subAgentInvocationId, subAgentName, and parentRequestId internally, but this is a private proposed surface and does not provide the requested documented root/parent conversation contract to customization files.
- **prompt-variable gap:** extensions/copilot/src/extension/prompt/vscode-node/promptVariablesService.ts currently registers only VSCODE_USER_PROMPTS_FOLDER and VSCODE_TARGET_SESSION_LOG; it receives a sessionId but does not expose it or any root, parent, turn, agent, or entrypoint metadata.
- **available provenance:** src/vs/platform/agentHost/common/agent.ts and src/vs/platform/agentHost/common/state/protocol/channels-chat/state.ts already model exact chat resources and ChatOrigin variants for user, fork, side-chat, and tool-spawned chats, including source chat, turn, and tool-call provenance. These facts remain host/provider internals rather than a customization-facing contract.
- **built-in tool mismatch:** extensions/copilot/src/extension/chatSessions/copilotcli/vscode-node/tools/getVscodeInfo.ts returns vscode.env.sessionId, which identifies the VS Code application session rather than the current conversation chain and therefore does not satisfy the request.
