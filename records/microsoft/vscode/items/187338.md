## Summary

Keep open as an upstream keyring-discovery issue: Electron's relevant improvement has merged, but the inspected VS Code encryption path still uses the synchronous APIs rather than the new functionality. Manual backend selection helps many reporters but does not establish that automatic discovery is fixed.

## Change summary

Discover an available Linux keyring on unsupported desktop environments so authentication credentials persist without manual password-store configuration.

## Best solution

Evaluate adoption of Electron's asynchronous safeStorage functionality for automatic keyring discovery, coordinating with the existing detection work in https://github.com/microsoft/vscode/issues/185212. Preserve secure storage and distinguish discovery failures from unavailable or locked keyrings and the reported startup hangs.

- **Original trigger and workaround:** The complete body of https://github.com/microsoft/vscode/issues/187338 reports GitHub authentication failing to persist despite gnome-keyring being installed; safeStorage.encryptString throws 'Encryption is not available'. Explicit --password-store="gnome" reportedly works, identifying automatic backend selection as the original problem.
- **Current VS Code call path:** src/vs/platform/encryption/electron-main/encryptionMainService.ts:37,56,67 calls safeStorage.encryptString, safeStorage.decryptString, and safeStorage.isEncryptionAvailable. getKeyStorageProvider reads getSelectedStorageBackend; this path does not call the new asynchronous APIs. src/vs/workbench/services/secrets/electron-browser/secretStorageService.ts still presents the reported keyring warning when storage is not persisted.
- **Upstream improvement is not adoption:** https://github.com/electron/electron/pull/49054 merged on 2026-02-15 and explicitly closes https://github.com/electron/electron/issues/47436. It introduces isAsyncEncryptionAvailable, encryptStringAsync, and decryptStringAsync for os_crypt_async. That upstream merge does not prove resolution here because the inspected VS Code call site still uses the synchronous APIs.
- **Older related detection issue:** https://github.com/microsoft/vscode/issues/185212 is open and titled 'Allow safestorage api to detect presence of libsecret or kwallet if the desktop environment is unknown'. The maintainer diagnosis at https://github.com/microsoft/vscode/issues/185212#issuecomment-1593271415 attributes backend selection to Chromium/Electron, and https://github.com/microsoft/vscode/issues/185212#issuecomment-1610355074 keeps runtime detection work open.
