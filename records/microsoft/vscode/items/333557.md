# Issue #333557 — Using AI assisted customizations leads to unexpectedly high costs due to chat send

[https://github.com/microsoft/vscode/issues/333557](https://github.com/microsoft/vscode/issues/333557)

## Summary

Team-authored test-plan finding that is still open on main: the AI-assisted customization flow dispatches a chat request on whatever model the picker happens to hold, with no disclosure of model or cost, and the launching surface gives no in-flight progress. The UI has since moved to the welcome-page prompt launcher with a 'Sent to chat ✓' confirmation, which softens the second half but does not address the cost-transparency half, so this should stay open for a design decision.

## Change summary

Generating a customization with AI silently sends a chat request on the user's currently selected (possibly premium) model, with no cost/model disclosure and no progress feedback in the customizations surface.

## Best solution

Make the customization-generation send explicit about what it will do: surface (or pin) the model used before dispatch and keep an in-flight progress affordance in the customizations editor until the chat response starts, rather than firing a hidden agent request on the picker's current model.

Plus a unit test in src/vs/workbench/contrib/chat/test/browser/aiCustomization/ asserting the generation send carries the intended model selection.
- **Behavior:**

  > Generating a customization with AI must not be a silent, open-ended spend: before the request is dispatched the user can see which model will run it (or it runs on a deliberately chosen model), and the customizations surface shows that work is in flight rather than only 'Sent to chat ✓', so the user is not left pressing X and hunting for the chat session. Existing customization creation (name prompt, destination picker, resulting files) is unchanged. Acceptance: the model used is discoverable at send time, and the launching surface reflects in-flight state until the chat response starts.
- **Trace:**

  > Two send paths exist. The reachable one is aiCustomizationWelcomePagePromptLaunchers.ts:193-221, which builds `/init <value>` (or 'Generate agent customizations. …' when `workspaceService.isSessionsWindow`) and hands it to `callbacks.prefillChat(query, { isPartialQuery: false, newChat: true })`; it immediately swaps the submit button for a static 'Sent to chat ✓' label with no progress state. The second, currently uncalled, path is `CustomizationCreatorService.createWithAI` (customizationCreatorService.ts:46-109), which runs `workbench.action.chat.newChat` and then `chatService.sendRequest(...)` with `modeInfo.modeInstructions` and no `userSelectedModelId` — so it inherits the picker's model. Neither path contains any cost or model disclosure (`rg userSelectedModelId` in that folder: no hits). The boundary: do not change general chat model-picker semantics or the customization file layout/instructions; the change belongs to the customization generation entry points. Context: filed while testing https://github.com/microsoft/vscode/issues/333535. Uncertainty starts at whether the right answer is pinning a model for this flow or disclosing the active one.
- **Open decisions:**
  - Should customization generation pin a specific (cheaper) model, or run on the user's selected model with an explicit pre-send disclosure of which model and that it may incur premium cost?
  - What in-flight affordance should the customizations surface show after sending — a progress indicator with a link to the session, or an inline response surface — instead of the current static 'Sent to chat ✓'?
  - Should the now-uncalled CustomizationCreatorService.createWithAI path be revived with the same guarantees, or removed so a single generation entry point carries the behavior?
