## Plan brief

- **Likely files:** `extensions/copilot/src/extension/byok/vscode-node/customEndpointProvider.ts`, `extensions/copilot/src/extension/byok/vscode-node/abstractLanguageModelChatProvider.ts`, `extensions/copilot/src/extension/byok/common/byokProvider.ts`
- **Validation:** A BYOK custom-endpoint test asserting the credential-resolution hook is invoked per request and its output is used as the Authorization header, once the chosen mechanism (apiKeyHelper command vs. templated env/secret) is decided.
- **Behavior:**

  > A custom-endpoint BYOK config can supply a credential that is regenerated per request (or on expiry) rather than only a fixed string, so OAuth-backed gateways (e.g. Databricks AI Gateway) work without manual token pasting or a local proxy. Acceptance depends on which mechanism is chosen by the maintainer.
- **Trace:**

  > CustomEndpointModelConfig and CustomEndpointModelProviderConfig in customEndpointProvider.ts expose only static `apiKey`/`requestHeaders`; the request-building path in AbstractOpenAICompatibleLMProvider consumes these as fixed strings with no refresh/callback concept. Two viable designs: (a) an `apiKeyHelper`-style external command whose stdout supplies the token, or (b) `${env:VAR}`/secret-reference templating resolved at request time. The scope must stay inside the custom-endpoint provider's credential resolution; do not change other BYOK vendors (Azure, OpenAI, etc.).
- **Open decisions:**
  - Should the mechanism be an external-command hook (`apiKeyHelper`) or a templated env/secret reference resolved at request time, or both?
  - How is the helper's output cached/refreshed (per request, on expiry, on 401) and how are helper failures surfaced to the user?
  - Is this scoped to `customendpoint` only or should it generalize to other BYOK vendor configs?
