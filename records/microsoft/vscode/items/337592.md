# Issue #337592 — BYOK custom endpoints: support dynamic/refreshable API key (apiKeyHelper) for OAuth-based gateways

[https://github.com/microsoft/vscode/issues/337592](https://github.com/microsoft/vscode/issues/337592)

## Summary

Keep this accepted Backlog request open: existing secret references and custom auth headers do not acquire or refresh OAuth credentials. It has 23 upvotes, and the older related reports do not own the same token-expiry problem.

## Change summary

Allow BYOK custom endpoints to obtain refreshed short-lived credentials automatically rather than requiring repeated manual token updates.

## Best solution

Provide an explicitly configured credential-acquisition mechanism for custom endpoints that works across token expiry while preserving static-key authentication. A maintainer should settle the supported credential sources, refresh semantics, and local-command execution boundary before implementation.

Manually verify a Databricks CLI-backed OAuth configuration continues working after its initial token expires without editing chatLanguageModels.json.
- **Behavior:**

  > A configured BYOK custom endpoint should continue authenticating to an OAuth-based gateway after the initial access token expires, without manual token pasting or a reverse proxy. The reporter's concrete scenario uses Databricks AI Gateway with credentials obtainable through databricks auth token. Existing static-key configurations must keep working. Acceptance should demonstrate credential renewal across successive requests and explicit handling of acquisition failures without exposing token contents.
- **Trace:**

  > AbstractOpenAICompatibleLMProvider.provideLanguageModelChatResponse in extensions/copilot/src/extension/byok/vscode-node/abstractLanguageModelChatProvider.ts creates an endpoint for the response. CustomEndpointBYOKModelProvider.createOpenAIEndPoint in customEndpointProvider.ts supplies the resolved configuration's apiKey string; OpenAIEndpoint captures it, and CustomEndpointOAIEndpoint.getExtraHeaders emits that value or configured headers. The only header interpolation there is ${apiKey}; LanguageModelsService._resolveConfiguration in src/vs/workbench/contrib/chat/common/languageModels.ts resolves stored top-level secrets when preparing provider configuration, not an OAuth credential source per request. AzureBYOKModelProvider has a separate authentication-session path, but that does not cover arbitrary custom gateways. Preserve existing static credentials, header sanitization, API formats, and non-custom providers; avoid credential acquisition merely for model metadata or token counting. Related https://github.com/microsoft/vscode/issues/320727 and https://github.com/microsoft/vscode/issues/329469 concern header customization/interpolation rather than owning this refresh contract. The unresolved boundary is which credential sources are supported and when they run, including local versus remote execution and refresh/failure behavior.
- **Open decisions:**
  - Should custom endpoints initially support a local command helper, an authentication-provider integration, request-time secret/environment references, or a defined combination?
  - Should credentials be acquired for every outgoing request, cached until an explicit expiry, or refreshed on authentication failure, and should a failed request be retried automatically?
  - If command helpers are supported, which local or remote environment executes them, and what user consent, workspace-trust, and administrator restrictions govern execution?
