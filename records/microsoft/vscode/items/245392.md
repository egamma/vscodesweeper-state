# Issue #245392 — Explorer jumps position when focusing from a seperate window in the same workspace

[https://github.com/microsoft/vscode/issues/245392](https://github.com/microsoft/vscode/issues/245392)

## Summary

The cross-window Explorer jump remains credible on current main: auto-reveal unconditionally follows global active-editor changes, allowing focus returning to the main window to replace the user's Explorer position before their click completes. A newer report confirms the same observable symptom, but cannot be the duplicate canonical for this re-reviewed, older issue.

## Change summary

Prevent Explorer auto-reveal from jumping to the main window's active file when a user returns from an auxiliary window to interact with the Explorer.

## Best solution

Explorer auto-reveal should continue following deliberate editor activation across windows, but focusing or clicking the Explorer itself must preserve its current scroll target until the user opens another file.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/browser/parts/editor/editorParts.ts`, `src/vs/workbench/services/editor/browser/editorService.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Reproduce the steps from https://github.com/microsoft/vscode/issues/300442 with `explorer.autoReveal` enabled: activate a distant file in an auxiliary window, scroll the main-window Explorer, then click a directory in that Explorer. The Explorer must not jump before handling the click, while clicking an editor in either window must still reveal that editor's file.
- **Behavior:**

  > With `explorer.autoReveal` enabled, activating an editor in either the main or an auxiliary window should reveal that editor's file. Returning to the main window specifically to interact with the Explorer must not first scroll or select the file left active in the main editor. The user's first Explorer click must operate on the item under the pointer. Existing single-window auto-reveal behavior must remain unchanged.
- **Trace:**

  > ExplorerView in src/vs/workbench/contrib/files/browser/views/explorerView.ts subscribes to every global `IEditorService.onDidActiveEditorChange` event and immediately runs `selectActiveFile`, which selects and reveals the reported active resource. Cross-window focus updates originate in EditorParts.registerEditorPartListeners in src/vs/workbench/browser/parts/editor/editorParts.ts and flow through EditorService.handleActiveEditorChange in src/vs/workbench/services/editor/browser/editorService.ts. The same sequence is independently documented with exact steps in https://github.com/microsoft/vscode/issues/300442 and confirmed after an upgrade. The plan should first capture the event ordering when focus moves from an auxiliary editor directly to the main-window Explorer, then identify an automated or deterministic manual validation. Preserve auto-reveal for genuine editor activation and keep unrelated editor-group MRU and single-window behavior out of scope.

## Evidence

- **current source path:** On current main, src/vs/workbench/contrib/files/browser/views/explorerView.ts registers `editorService.onDidActiveEditorChange` in `ExplorerView.renderBody` and immediately calls `selectActiveFile`; that method calls `explorerService.select(activeFile, reveal)` whenever `explorer.autoReveal` is enabled, with no distinction between an editor activation and focus returning to the main window for an Explorer interaction.
- **cross-window activation:** src/vs/workbench/browser/parts/editor/editorParts.ts updates the most-recently-active editor part on focus and emits `onDidActiveGroupChange`; src/vs/workbench/services/editor/browser/editorService.ts converts that group change into `onDidActiveEditorChange`, which is the event consumed by Explorer auto-reveal.
- **independent confirmation:** https://github.com/microsoft/vscode/issues/300442 reports the same Explorer jump with detailed multi-window steps, and https://github.com/microsoft/vscode/issues/300442#issuecomment-4031265898 confirms it still occurred after upgrading to VS Code 1.110.1.
- **canonical ordering:** https://github.com/microsoft/vscode/issues/300442 was created on 2026-03-10, after this issue's 2025-04-02 creation date. Under the stronger re-review duplicate rule, that younger report cannot be the canonical for this older issue.
