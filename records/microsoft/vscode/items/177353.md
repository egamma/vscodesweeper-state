# Issue #177353 — Allow revealing path/file in OS from terminal or editor

[https://github.com/microsoft/vscode/issues/177353](https://github.com/microsoft/vscode/issues/177353)

## Summary

Keep open: existing OS-reveal commands target selected resources or the active editor, not paths embedded in terminal output or editor text. This accepted Backlog request has 22 upvotes; the older related terminal request covers the working directory, not the same capability.

## Change summary

Allow paths in terminal output and editor content to be revealed in the desktop OS file manager instead of opened in VS Code.

## Best solution

Provide an explicit desktop OS-reveal interaction for resolvable file and folder links in terminal output and editor content, preserving ordinary link-opening behavior. Agree on the interaction and editor path-recognition scope before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/terminalContrib/links/browser/terminalLinkManager.ts`, `src/vs/workbench/contrib/terminalContrib/links/browser/terminalLinkOpeners.ts`, `src/vs/workbench/contrib/terminalContrib/links/browser/terminalLinkDetectorAdapter.ts`, `src/vs/editor/contrib/links/browser/links.ts`, `src/vs/workbench/contrib/files/electron-browser/fileActions.contribution.ts`, `src/vs/workbench/contrib/files/electron-browser/fileCommands.ts`
- **Validation:** On desktop, print an existing absolute file path and folder path in the terminal, and create a Markdown file containing a relative image link. Verify the agreed reveal interaction targets those resources in Finder/File Explorer rather than the active editor or terminal working directory; verify ordinary link activation remains unchanged and unsupported resources do not reveal an unrelated fallback folder.
- **Behavior:**

  > Users need to reveal a file or folder referenced by terminal output or editor content in the desktop OS file manager without first opening it in VS Code. The target must be the referenced resource, including a relative Markdown image link, rather than the active document or terminal working directory. Ordinary link-opening behavior must remain available and unchanged. The final interaction and which editor-text paths qualify require agreement before implementation.
- **Trace:**

  > The existing revealFileInOS command derives selected resources, while workbench.action.files.revealActiveFileInWindows derives the active editor URI in src/vs/workbench/contrib/files/electron-browser/fileActions.contribution.ts. revealResourcesInOS in fileCommands.ts already bridges supported resource URIs to the native file manager, with local and WSL handling and a workspace-folder fallback when no resources are supplied. TerminalLocalFileLinkOpener and the folder openers in terminalLinkOpeners.ts currently target VS Code; TerminalLinkDetectorAdapter carries optional hover actions into TerminalLinkManager. Editor LinkDetector.openLinkOccurrence resolves document links through IOpenerService rather than offering OS reveal. The discussion at https://github.com/microsoft/vscode/issues/177353 distinguishes embedded paths from active-file reveal and points toward desktop scope; https://github.com/microsoft/vscode/issues/154917 concerns terminal cwd and is related but not a duplicate. Preserve existing link activation, path resolution, and remote-resource boundaries; uncertainty remains about the user interaction and whether editor support includes arbitrary plain-text paths beyond recognized links.
- **Open decisions:**
  - Should OS reveal be exposed through an explicit link hover/context action, an alternate click modifier, or both?
  - Should editor support initially cover recognized document links, including relative Markdown links, or also arbitrary filesystem paths in plain-text content?

## Evidence

- **Clarified scope and acceptance:** In https://github.com/microsoft/vscode/issues/177353, the reporter explicitly distinguishes paths inside terminal output or Markdown/text content from revealing the active file. The discussion identifies desktop Electron as the plausible scope; the request reached the Backlog after sufficient community support and currently has 22 upvotes.
- **Existing commands provide partial coverage:** src/vs/workbench/contrib/files/electron-browser/fileActions.contribution.ts registers revealFileInOS using getMultiSelectedResources, and workbench.action.files.revealActiveFileInWindows using the active editor URI. Neither resolves a path embedded in editor text or terminal output. src/vs/workbench/contrib/files/electron-browser/fileCommands.ts exposes revealResourcesInOS, which delegates supported resources to INativeHostService.showItemInFolder.
- **Terminal link behavior:** src/vs/workbench/contrib/terminalContrib/links/browser/terminalLinkOpeners.ts opens file links through IEditorService.openEditor, workspace folders through revealInExplorer, and outside-workspace folders in another VS Code window. TerminalLinkDetectorAdapter forwards link actions to hover rendering, but inspection of the built-in terminal link sources found no revealFileInOS or showItemInFolder interaction.
- **Editor link behavior:** LinkDetector.openLinkOccurrence in src/vs/editor/contrib/links/browser/links.ts resolves links and invokes IOpenerService.open with openToSide and contributed-opener options. This path does not provide an explicit OS-reveal alternative.

It does not own arbitrary output paths or embedded editor links, so it fails both the full-scope and re-reviewed-item same-symptom duplicate requirements.
