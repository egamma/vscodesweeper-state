# Issue #123139 — Git - Add ability to have ignored repository wildcards

[https://github.com/microsoft/vscode/issues/123139](https://github.com/microsoft/vscode/issues/123139)

## Summary

Keep this accepted Git feature request open: current repository exclusions still require exact paths, so generated Bazel cache names remain unsupported. The request has 27 upvotes and no verified open canonical that absorbs it.

## Change summary

Allow wildcard repository exclusions so dynamically named Bazel and pre-commit cache repositories do not appear in Source Control.

## Best solution

Support documented repository-root patterns in the built-in Git exclusion configuration while preserving existing literal-path exclusions and automatic discovery of unrelated repositories. Settle the pattern syntax and literal-path compatibility contract before implementation.

Also cover existing absolute and workspace-relative literal exclusions, multi-root workspaces, and the agreed behavior for literal glob metacharacters. No tests were executed during this read-only review.
- **Behavior:**

  > Users can exclude dynamically named cache repositories without listing each generated path or disabling automatic repository discovery. Opening files from multiple Bazel cache mirrors covered by the configured pattern must not register those repositories in Source Control. Unmatched repositories must continue to be detected. Existing literal absolute and workspace-relative exclusions must retain their documented behavior under the agreed compatibility contract.
- **Trace:**

  > Model.onDidChangeVisibleTextEditors in extensions/git/src/model.ts feeds file directories to openRepository, which resolves the repository root and calls shouldRepositoryBeIgnored before registration. That exclusion method currently supports normalized exact equality for absolute paths and workspace-relative paths; extensions/git/src/util.ts supplies pathEquals. Workspace traversal exclusions are a separate path and do not cover the reported editor trigger. The Git extension already depends on picomatch and uses it for worktree inclusion rules, but that availability does not establish repository-exclusion semantics. Keep the scope on repository exclusions; do not change files.exclude, global automatic-detection defaults, or unrelated nested-repository discovery. The technical gap is established; uncertainty begins at interpreting glob syntax alongside previously literal configuration entries.
- **Open decisions:**
  - What repository-root pattern syntax and anchoring should be supported, including absolute cache patterns and workspace-relative patterns in multi-root workspaces?
  - How should users distinguish wildcard patterns from literal repository paths containing glob metacharacters, so existing exclusions remain compatible?
