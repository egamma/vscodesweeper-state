# Issue #102857 — Git - Bulk merge conflict resolving issue on large files

[https://github.com/microsoft/vscode/issues/102857](https://github.com/microsoft/vscode/issues/102857)

## Summary

A real gap remains for resolving large generated files without loading, scanning, and editing every conflict marker through the text model. The issue is the established canonical for this work and is assigned to the Backlog, so it should remain open for design.

## Change summary

Allow Accept All Current/Incoming to resolve conflicts efficiently in very large files, with a follow-up request for recursive folder-level resolution.

## Best solution

Provide a scalable SCM conflict-resolution path for taking one complete side of selected large files without requiring full conflict-marker parsing, while preserving clear save and staging semantics. Decide separately whether recursive folder selection belongs in this issue or a narrower follow-up.

## Plan brief

- **Likely files:** `extensions/merge-conflict/src/commandHandler.ts`, `extensions/merge-conflict/src/documentTracker.ts`, `extensions/merge-conflict/src/mergeConflictParser.ts`, `extensions/merge-conflict/package.json`
- **Validation:** Create a repository fixture containing a generated conflicted text file large enough to exercise large-file optimizations, invoke Accept All Incoming and Accept All Current from Source Control, and verify each completes responsively with exactly the selected side retained; also verify ordinary marker-level conflict resolution remains unchanged.
- **Behavior:**

  > Accept All Current and Accept All Incoming must successfully resolve a very large conflicted text file without hanging or silently doing nothing. The resulting file must contain the selected side and no conflict markers. Existing behavior for normal-sized files must remain unchanged, and the final save and staging state must match the semantics selected by the maintainer.
- **Trace:**

  > The SCM context-menu commands are contributed in extensions/merge-conflict/package.json and dispatched by CommandHandler.acceptAllResources in extensions/merge-conflict/src/commandHandler.ts. That path opens every resource as a text document, while DocumentMergeConflictTracker and MergeConflictParser in extensions/merge-conflict/src/documentTracker.ts and extensions/merge-conflict/src/mergeConflictParser.ts copy and scan the full document before constructing one WorkspaceEdit containing all marker replacements. This establishes the scalability boundary but not the intended replacement semantics for taking an entire Git side. Preserve marker-level resolution for ordinary files and do not conflate the central large-file case with the newer multi-selection regression in https://github.com/microsoft/vscode/issues/179872.
- **Open decisions:**
  - For a large-file whole-side operation, should the command leave a dirty resolved editor as it does today, or save and stage the selected file as an SCM operation?
  - Should Accept All Current/Incoming continue resolving individual conflict blocks, or may a large-file path replace the entire file with Git's ours/theirs version when the user invokes it from Source Control?
  - Is recursive folder-level resolution from the 2021 comment part of this issue's accepted scope, or should this issue remain limited to selected files and track folder recursion separately?

## Evidence

- **current source path:** extensions/merge-conflict/src/commandHandler.ts opens every selected resource, asks DocumentMergeConflictTracker for all conflicts, and builds a WorkspaceEdit containing every marker replacement.
- **large-file cost:** extensions/merge-conflict/src/documentTracker.ts and mergeConflictParser.ts call document.getText() and then scan document.lineCount line by line; there is no large-file-specific resolution path or limit handling.
- **existing capability gap:** extensions/merge-conflict/package.json already contributes Accept All Current and Accept All Incoming for SCM merge resources, but the implementation remains text-model based and therefore does not provide the requested scalable whole-side operation.
- **canonical status:** The older https://github.com/microsoft/vscode/issues/66950 was closed by a maintainer as a duplicate of this issue, making this the canonical open item rather than a duplicate candidate.
- **related reports:** Newer reports such as https://github.com/microsoft/vscode/issues/179872 and https://github.com/microsoft/vscode/issues/248533 cover multi-selection, binary-file, save, and staging behavior, but neither predates this re-reviewed issue or reports the same large-text-file performance symptom.
