# Issue #138998 — column number bug with emojis

[https://github.com/microsoft/vscode/issues/138998](https://github.com/microsoft/vscode/issues/138998)

## Summary

The reported behavior remains in current main: the status-bar column counts Unicode code points, so emoji modifiers and ZWJ sequences advance the displayed column multiple times. Keep this open, but settle whether “Col” means grapheme count or rendered cell width before implementation.

## Change summary

Make the status-bar column number handle multi-code-point emoji sequences as a single user-perceived character.

## Best solution

Define the status bar's column semantics for tabs, grapheme clusters, and wide characters, then make `CursorColumns.toStatusbarColumn` and its tests implement that definition consistently. The decision should account for the conflicting display-width expectation tracked in https://github.com/microsoft/vscode/issues/254382.

## Plan brief

- **Likely files:** `src/vs/editor/common/core/cursorColumns.ts`, `src/vs/editor/test/common/core/cursorColumns.test.ts`, `src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts`, `src/vs/workbench/browser/parts/editor/editorStatus.ts`
- **Validation:** Extend the `CursorColumns.toStatusbarColumn` unit test with skin-tone and ZWJ emoji cases, then run `scripts/test.sh --runGlob '**/cursorColumns.test.js'`.
- **Behavior:**

  > For text containing emoji modifiers or ZWJ sequences, the status bar must report columns according to one documented, consistent user-facing definition. The chosen behavior must cover ordinary characters, surrogate pairs, combining sequences, tabs, full-width characters, and multi-code-point emoji. Acceptance requires explicit unit cases for a skin-tone emoji and a ZWJ emoji while preserving existing tab and supplementary-plane cases.
- **Trace:**

  > `EditorStatus.onSelectionChange` in `src/vs/workbench/browser/parts/editor/editorStatus.ts` obtains the displayed value through `ICodeEditor.getStatusbarColumn`. `CodeEditorWidget.getStatusbarColumn` delegates to `CursorColumns.toStatusbarColumn`, whose `CodePointIterator` counts every code point except that tabs advance to a tab stop; it does not group grapheme clusters. The neighboring visible-column functions use `GraphemeIterator`, showing that grapheme-aware infrastructure already exists, but https://github.com/microsoft/vscode/issues/254382 asks for display-cell width instead of grapheme count. Preserve model positions and cursor movement semantics; the decision is limited to the user-facing status-column contract and its conversion.
- **Open decisions:**
  - Should the status bar report Unicode grapheme-cluster positions or rendered cell-width positions?
  - If rendered width is chosen, should emoji and East Asian full-width characters advance by two while combining and ZWJ sequences remain one rendered unit?
  - Should the displayed semantics change globally or be exposed as a separate status-bar value from the model's UTF-16 column?

## Evidence

- **current source:** `src/vs/editor/common/core/cursorColumns.ts` implements `CursorColumns.toStatusbarColumn` with `CodePointIterator`; a skin-tone modifier and each component of a ZWJ emoji therefore increment the displayed column independently.
- **status-bar path:** `src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts` returns `CursorColumns.toStatusbarColumn(...)` from `getStatusbarColumn`, and `src/vs/workbench/browser/parts/editor/editorStatus.ts` uses that value when constructing the displayed selection status.
- **test gap:** `src/vs/editor/test/common/core/cursorColumns.test.ts` verifies surrogate-pair emoji such as 🎈, but has no status-column cases for emoji modifiers or ZWJ grapheme clusters.
- **related but distinct issue:** https://github.com/microsoft/vscode/issues/254382 remains open and requests rendered-width columns, including two columns for full-width characters and emoji. That differs from this report's request to count a multi-code-point emoji as one column, so it is not a safe duplicate canonical without a product decision.
