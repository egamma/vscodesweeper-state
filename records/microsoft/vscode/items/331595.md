# Issue #331595 — Agent host: a replayed client tool from a subagent is handled on the parent chat after a restart

[https://github.com/microsoft/vscode/issues/331595](https://github.com/microsoft/vscode/issues/331595)

## Summary

The reporter's own follow-up comment retracts the reproduction: the mis-routing described here presupposes an admission signal from #330933, which never merged (closed, merged_at null), and the in-process companion #330746 the body cites as already fixed also closed unmerged. Independent source inspection confirms neither mechanism exists on main — the MCP handler still just parks with no signal (see phase10-plan.md's own note: 'the handler just parks on the registry'), so a replayed client tool cannot exhibit the parent-chat mis-grouping this issue describes today.

## Change summary

Design question: after a VS Code restart, a replayed client tool call that originated in a subagent gets executed on the parent chat instead of the owning subagent chat, because the inner-to-parent routing edge does not survive the restart.

## Best solution

Nothing to change on main right now — the routing edge this issue worries about only matters once a client-tool-invoked admission signal exists, and the PR that would have added it (#330933) was declined. If that design is revisited later, the three coordinated changes the reporter outlined (prime the edge from the SDK's subagent store, restore a subagent chat for a dangling Task, populate `_subagentChats`) are a reasonable starting sketch, but they should be filed fresh against whatever admission-signal design actually lands.
