# Issue #163080 — Support nesting threads in the debugger

[https://github.com/microsoft/vscode/issues/163080](https://github.com/microsoft/vscode/issues/163080)

## Summary

The capability remains absent from both the current Debug Adapter Protocol and VS Code's call-stack model. Keep this open while the linked protocol design is resolved, then plan the corresponding hierarchical debugger UI.

## Change summary

Allow debug adapters to describe parent-child thread relationships and display those threads hierarchically in the Call Stack view.

## Best solution

Finalize the thread-parent contract in https://github.com/microsoft/debug-adapter-protocol/issues/339, then preserve that metadata in VS Code's debug model and expose the hierarchy in the Call Stack view without changing adapters that return ordinary flat thread lists.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/common/debugProtocol.d.ts`, `src/vs/workbench/contrib/debug/common/debug.ts`, `src/vs/workbench/contrib/debug/common/debugModel.ts`, `src/vs/workbench/contrib/debug/browser/debugSession.ts`, `src/vs/workbench/contrib/debug/browser/callStackView.ts`, `src/vs/workbench/contrib/debug/test/browser/callStack.test.ts`
- **Validation:** Add targeted debug tests showing that parent metadata produces the expected thread hierarchy, missing metadata preserves the existing flat ordering, and selecting or expanding a nested thread still reveals its stack frames; run the corresponding Call Stack/debug model unit-test suites.
- **Behavior:**

  > When a debug adapter reports parent-child relationships between threads, the Call Stack view can present those threads as a navigable hierarchy so users can trace where concurrent work originated. Adapters without relationship metadata retain the current flat thread list. Nested threads must continue to expose their stack frames and support the existing focus, selection, and thread actions. The plan must settle whether hierarchy display is automatic or controlled by a user setting.
- **Trace:**

  > The linked public-contract proposal is https://github.com/microsoft/debug-adapter-protocol/issues/339; current DAP `Thread` objects still contain only `id` and `name`. In VS Code, DebugSession.rawUpdate in src/vs/workbench/contrib/debug/browser/debugSession.ts converts those objects into Thread instances that have no parent field. CallStackDataSource.getChildren in src/vs/workbench/contrib/debug/browser/callStackView.ts returns session threads flat, and a Thread currently owns only its stack-frame children. The boundary is the debugger thread/model and Call Stack hierarchy: preserve flat behavior for adapters without metadata, and do not alter existing nested debug-session behavior or stack-frame semantics.
- **Open decisions:**
  - What exact parent-thread contract and lifecycle semantics should DAP standardize, including missing parents and relationship changes?
  - Should VS Code display adapter-provided thread hierarchies automatically, make them opt-in, or provide a user-selectable flat/tree mode?

## Evidence

- **open protocol dependency:** https://github.com/microsoft/debug-adapter-protocol/issues/339 remains open; it proposes an optional `Thread.parentId`, and a DAP maintainer said the proposal makes sense.
- **current protocol gap:** The current DAP schema and src/vs/workbench/contrib/debug/common/debugProtocol.d.ts define `Thread` with only `id` and `name`; no parent relationship is available.
- **current model gap:** src/vs/workbench/contrib/debug/browser/debugSession.ts (`rawUpdate`) constructs and updates Thread objects using only the adapter-provided ID and name, while src/vs/workbench/contrib/debug/common/debugModel.ts has no parent-thread field.
- **current UI gap:** src/vs/workbench/contrib/debug/browser/callStackView.ts (`CallStackDataSource.getChildren`) returns all session threads as a flat array and treats a Thread's children exclusively as stack frames.
- **canonical search:** Searches for goroutine nesting, debugger thread hierarchies, and parent-child threads found no separate open microsoft/vscode issue that predates and owns this request.
- **prior exploration:** The DAP proposal was listed for green-thread exploration in https://github.com/microsoft/vscode/issues/220925 and https://github.com/microsoft/vscode/issues/224756, but both checklist entries remained incomplete and the protocol proposal is still open.
