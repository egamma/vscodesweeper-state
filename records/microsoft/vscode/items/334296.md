# Issue #334296 — Remote-SSH: a stale 'code agent host' supervisor keeps serving new windows, so no agent session ever loads

[https://github.com/microsoft/vscode/issues/334296](https://github.com/microsoft/vscode/issues/334296)

## Summary

Keep open: current source still reuses a live supervisor without build compatibility checks, and an incompatible handshake leaves the editor's remote agent-host connection without recovery. The reporter confirmed the diagnosis and recovery; the related older reports do not cover this report's full observable failure.

## Change summary

Prevent incompatible stale supervisors from leaving Remote-SSH agent sessions silently unavailable, and provide an actionable recovery path.

## Best solution

Make remote supervisor selection and lifecycle management avoid incompatible stale hosts, and expose handshake failure with a supported recovery action in the editor. Coordinate the shared supervisor lifecycle with the related stale-build report without losing this issue's negotiation-failure and window-recovery requirements.

- **Behavior:**

  > A new Remote-SSH window must not silently remain empty because discovery selected an incompatible long-lived agent host. Acceptance must cover both the stale-host selection case and recovery of an already-open window, while respecting other clients using the shared supervisor.
- **Trace:**

  > classify_agent_host in cli/src/tunnels/agent_host.rs selects live standalone endpoints without checking their build or protocol compatibility; ensure_supervisor_running in cli/src/commands/agent_host.rs returns that endpoint and ActiveAgentHost.apply_to_bridge wires it into the server bridge. AgentHostEndpointMetadata in cli/src/tunnels/agent_host_registry.rs carries no build commit, and its protocolVersion comes from a constant rather than the running server's negotiated AHP version. AgentHostManager.run_update_loop waits for the running child to exit before downloading an uncached update. AgentHostProtocolClient.connect treats UnsupportedProtocolVersion as terminal Incompatible, while EditorRemoteAgentHostServiceClient keeps _connectStarted set, logs the failure, and provides no restart implementation. The reporter confirmed successful recovery after removing the stale supervisor at https://github.com/microsoft/vscode/issues/334296#issuecomment-5528832932. Coordinate lifecycle work with https://github.com/microsoft/vscode/issues/333175; do not conflate this issue with the cache-eviction defect at https://github.com/microsoft/vscode/issues/338114. Preserve compatible-host behavior and editor-owned endpoint isolation; the unresolved boundary is how new clients select a compatible host without unexpectedly interrupting existing users of the shared supervisor.
- **Open decisions:**
  - Must Remote-SSH use a host matching the client's exact build, as the reporter suggests, or may it reuse a different build when actual protocol compatibility is established?
  - If other clients are using an incompatible shared supervisor, should recovery explicitly restart it with a disruption warning, or provide an isolated compatible host without terminating those clients?
