# Issue #171030 — Allow to use TextMate scope in `notIn` property of `autoClosingPairs`

[https://github.com/microsoft/vscode/issues/171030](https://github.com/microsoft/vscode/issues/171030)

## Summary

Keep open: current language configuration cannot suppress a particular auto-closing pair in arbitrary expression contexts. The reporter accepts a TextMate-independent solution, so the maintainer's concern about TextMate coupling does not settle the broader request.

## Change summary

Allow language authors to suppress angle-bracket auto-closing inside expressions while retaining it elsewhere.

## Best solution

Define a synchronous, tokenizer-independent context contract for conditional auto-closing in the editor's language configuration system. Preserve predictable typing and existing string/comment exclusions rather than making typing depend on asynchronously computed semantic tokens.

## Plan brief

- **Likely files:** `src/vs/editor/common/languages/languageConfiguration.ts`, `src/vs/workbench/contrib/codeEditor/common/languageConfigurationExtensionPoint.ts`
- **Validation:** The plan should end with a runnable editor typing test using a fixture language: typing '<' inside an expression inserts only '<', while typing it in a context where the pair is enabled inserts '<>'. Verify existing string/comment exclusions and repeat the same keystrokes with and without semantic tokens available to ensure identical results.
- **Behavior:**

  > A language author needs to enable the '<', '>' auto-closing pair outside expressions and suppress it inside expressions where '<' is an operator. The capability must not require treating expressions as strings or comments. Existing pair configurations must retain their behavior, and identical typing in identical document states must not depend on semantic-token timing. Acceptance includes expression and non-expression typing cases plus unchanged string/comment exclusions.
- **Trace:**

  > IAutoClosingPairConditional and StandardAutoClosingPairConditional in src/vs/editor/common/languages/languageConfiguration.ts store exclusions as string arrays and evaluate only StandardTokenType categories; ordinary code is always permitted. src/vs/workbench/contrib/codeEditor/common/languageConfigurationExtensionPoint.ts validates and registers that restricted configuration shape. Existing autoCloseBefore and editor.autoClosingBrackets options do not provide expression-context discrimination. The reporter explicitly accepts a TextMate-independent alternative in https://github.com/microsoft/vscode/issues/171030#issuecomment-1378527092, while the maintainer wants language configuration to remain independent of TextMate. The unresolved boundary is the public, synchronous context contract, not a particular helper or patch location. Preserve existing typing semantics and the timing constraint documented in https://github.com/microsoft/vscode/issues/113254#issuecomment-749459222; embedded-language configuration selection in https://github.com/microsoft/vscode/issues/133397 is separate work.
- **Open decisions:**
  - What tokenizer-independent, synchronously available context vocabulary or provider contract should language authors be able to use for pair exclusions, including language-specific expression contexts?
