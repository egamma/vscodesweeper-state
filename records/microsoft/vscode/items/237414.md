# Issue #237414 — Debug sessions become unresponsive after a failed 'restart' request

[https://github.com/microsoft/vscode/issues/237414](https://github.com/microsoft/vscode/issues/237414)

## Summary

The defect remains on current main and is reproducible from the source: a rejected DAP `restart` response is treated as final session termination even though the adapter remains alive, causing the main-thread adapter mapping to be discarded. The issue should remain open for a bounded debug lifecycle fix.

## Change summary

Keep a debug session usable when its adapter rejects a DAP `restart` request.

## Best solution

Only publish final session termination after a failed restart when the adapter actually exited during the restart attempt; a rejected in-place DAP restart must retain the live adapter bridge and allow subsequent requests such as pause, continue, and disconnect.

Run `scripts/test.sh --grep "failed restart"`.
- **Behavior:**

  > When a debug adapter supports the DAP `restart` request but responds with `success: false`, VS Code reports the restart failure without treating the still-running session as terminated. Subsequent session operations, including termination, continue to reach that adapter. Successful in-place restarts and restarts where the adapter really exits retain their existing lifecycle notifications. Acceptance requires a regression test proving that a rejected restart leaves the adapter usable.
- **Trace:**

  > The confirmed path begins in `DebugService.restartSession` and its `doRestart` helper in `src/vs/workbench/contrib/debug/browser/debugService.ts`. `DebugSession.restart` forwards to `RawDebugSession.restart`; `RawDebugSession.send` rejects a response whose `success` field is false without stopping the adapter. Nevertheless, `doRestart` then emits a final non-restart `onDidEndSession`, and `MainThreadDebugService` responds by removing the corresponding adapter handle from `_debugAdapters`; the next adapter message consequently throws `Invalid debug adapter`. The lifecycle bookkeeping must distinguish a failed in-place request from a failed restart after an actual adapter exit. Do not change the semantics for adapters without `supportsRestartRequest`, successful restarts, or genuinely terminated adapters. The same symptom and extension-side workaround are documented at https://github.com/iarsystems/iar-vsc-debug/issues/38.

## Evidence

- **source root cause:** In src/vs/workbench/contrib/debug/browser/debugService.ts, `restartSession` wraps `session.restart()` in `doRestart`; when the request rejects, `didRestart` remains false and the `finally` block unconditionally fires `onDidEndSession({ session, restart: false })`, despite no adapter-exit event having occurred.
- **adapter invalidation:** src/vs/workbench/api/browser/mainThreadDebugService.ts handles every `onDidEndSession` event by deleting the session's entries from `_debugAdapters`. Later messages from the still-running adapter therefore reach `$acceptDAMessage`, whose `getDebugAdapter` call throws `Invalid debug adapter`, matching the reported log exactly.
- **failed response path:** src/vs/workbench/contrib/debug/browser/rawDebugSession.ts sends the supported `restart` request through `send`; a DAP response with `success: false` rejects the promise but does not shut down or clear `debugAdapter`, confirming that the adapter can remain alive when DebugService announces termination.
- **independent confirmation:** https://github.com/iarsystems/iar-vsc-debug/issues/38 records the same observable failure and explicitly identifies this VS Code issue as the underlying bug; extension version 1.42.1 shipped only a workaround that reports failed restarts as successful.
- **current report confirmation:** https://github.com/microsoft/vscode/issues/237414#issuecomment-3571461135 independently reports that the problem still exists.
- **history:** Commit 2d50c20ad2b1739274384e60bb05dca2b15af064 introduced the `doRestart` failure bookkeeping and the adapter-map cleanup behavior involved here; current main still contains both paths, and no open PR referencing this issue was found.
