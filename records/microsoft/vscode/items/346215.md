# Issue #346215 — [Feature Request] Allow Third-Party Extensions to Use VS Code's Built-in Desktop Notifications

[https://github.com/microsoft/vscode/issues/346215](https://github.com/microsoft/vscode/issues/346215)

## Summary

The public extension API still lacks desktop notifications, although reusable internal infrastructure exists. Keep this request open for API design; no verified open canonical owns its full scope.

## Change summary

Expose desktop notifications to extensions, including local delivery from remote extension hosts and click navigation to the originating window.

## Best solution

Design a minimal proposed extension API backed by the existing host toast infrastructure, with explicit user controls, window ownership, and platform capability semantics. Existing chat notification behavior should remain unchanged.

## Vision fit

- **Fit:** aligned
- **Reason:** A shared notification API supports powerful extensions and remote workflows without requiring each extension to implement platform-specific desktop integration.

Manually exercise notification delivery and click-to-focus on macOS, Windows, and Linux, including a remote workspace, denied permissions, and disabled notifications.
- **Behavior:**

  > Extensions should be able to request desktop notifications through a supported VS Code API rather than platform-specific dependencies. A remote extension's notification should appear on the local client desktop, and clicking it should navigate to the originating window and extension context according to the agreed contract. User notification preferences and OS permissions must be respected. Acceptance must cover supported-platform behavior, unavailable capabilities, and unchanged built-in chat notifications.
- **Trace:**

  > The current public message API reaches MainThreadMessageService in src/vs/workbench/api/browser/mainThreadMessageService.ts and uses INotificationService or IDialogService, not the OS notification path. Internal IHostService.showToast in src/vs/workbench/services/host/browser/host.ts reaches NativeHostService.showToast and then NativeHostMainService.showToast, with a browser fallback in src/vs/workbench/services/host/browser/toasts.ts. ChatWindowNotifier in src/vs/workbench/contrib/chat/browser/chatWindowNotifier.ts separately owns configuration checks, target-window selection, focusing, and session navigation. The browser fallback supports clicks but not action buttons, so platform guarantees remain unresolved. Preserve existing message APIs and chat-specific settings rather than assuming they define extension notification policy. Earlier requests at https://github.com/microsoft/vscode/issues/263009 and https://github.com/microsoft/vscode/issues/293062 corroborate demand but are reported closed; no live implementation candidate was identified.
- **Open decisions:**
  - Should extensions receive desktop notifications through a separate API or an opt-in mode of existing message APIs, and which user controls govern delivery?
  - Should clicking always focus the originating window, and should extension navigation use a returned result or a command supplied with the notification?
  - What should the public API promise when native notifications or action buttons are unavailable: reduced functionality, browser fallback, or an explicit unsupported result?

## Evidence

- **Public capability gap:** src/vscode-dts/vscode.d.ts exposes window.showInformationMessage, showWarningMessage, and showErrorMessage. MainThreadMessageService in src/vs/workbench/api/browser/mainThreadMessageService.ts routes these to workbench notifications or modal dialogs, not OS toasts. Searches across src/vscode-dts and src/vs/workbench/api found no desktop notification or showToast bridge.
- **Reusable internal infrastructure:** IHostService.showToast in src/vs/workbench/services/host/browser/host.ts exposes internal toast options and results. NativeHostService.showToast in src/vs/workbench/services/host/electron-browser/nativeHostService.ts calls the native service and falls back to browser notifications. NativeHostMainService.showToast in src/vs/platform/native/electron-main/nativeHostMainService.ts:1539-1590 creates Electron notifications and returns click or action results.
- **Focus is caller-owned:** ChatWindowNotifier._notifyIfNeeded in src/vs/workbench/contrib/chat/browser/chatWindowNotifier.ts checks chat.notifyWindowOnConfirmation, calls IHostService.showToast, and explicitly focuses the target window and opens the session after a click. Reusing the toast service alone would not provide extension-specific focus or command navigation.
- **Platform contract remains unsettled:** src/vs/workbench/services/host/browser/toasts.ts requests browser notification permission and returns click results, but does not implement the actions accepted by IToastOptions. A public API cannot assume uniform action support across native and fallback implementations.
