# Issue #346215 — [Feature Request] Allow Third-Party Extensions to Use VS Code's Built-in Desktop Notifications

[https://github.com/microsoft/vscode/issues/346215](https://github.com/microsoft/vscode/issues/346215)

## Summary

The native notification infrastructure exists, but extensions still lack a public entry point. Keep this request open for API consideration; the earlier requests closed for insufficient votes, not an architectural rejection, and no open canonical covering this API was verified.

## Change summary

Expose desktop notifications to extensions, including local delivery from remote extension hosts and click-to-focus navigation.

## Best solution

Evaluate a minimal extension API backed by the existing host toast service, with explicit user controls, originating-window attribution, and documented platform limitations. Settle the public contract before accepting an implementation.

- **Reason:** A shared notification API would enable extension capabilities while keeping platform-specific integration and consistent interaction behavior in VS Code.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadMessageService.ts`, `src/vs/workbench/services/host/browser/host.ts`, `src/vs/workbench/services/host/electron-browser/nativeHostService.ts`, `src/vs/workbench/services/host/browser/toasts.ts`, `src/vs/platform/native/electron-main/nativeHostMainService.ts`
- **Validation:** After API acceptance, exercise a sample extension locally and over SSH/WSL/Dev Containers: trigger a notification while its VS Code window is unfocused, click it, and verify that the originating window is focused and its command runs once. Verify denied permission, user-disabled notifications, dismissal without command execution, two-window attribution, and the agreed unsupported-platform behavior on macOS, Windows, and Linux.
- **Behavior:**

  > Extensions should be able to request desktop notifications without installing OS-specific notification dependencies. Notifications from remote extension hosts should appear on the user's local desktop. Clicking a notification should focus its originating VS Code window and optionally invoke the extension's navigation command once. User preferences and OS permissions must be respected, and unsupported capabilities must have documented behavior.
- **Trace:**

  > ChatWindowNotifier in src/vs/workbench/contrib/chat/browser/chatWindowNotifier.ts already combines IHostService.showToast with explicit window focus and session navigation. NativeHostService.showToast delegates to the Electron-main implementation, which returns click/action outcomes, with a browser fallback that requests notification permission but lacks equivalent action handling. Public extension messages instead pass through MainThreadMessageService.$showMessage to workbench notifications or dialogs; no OS-toast extension entry point was found in the API declarations or bridge. The existing host implementation establishes reuse potential, not a settled extension-facing contract. Preserve existing chat notification settings, approval behavior, and ordinary extension message semantics. Earlier API requests at https://github.com/microsoft/vscode/issues/263009 and https://github.com/microsoft/vscode/issues/293062 establish recurring demand but not implementation acceptance.
- **Open decisions:**
  - What extension-specific user controls and defaults should govern desktop notifications, independently of chat notification settings?
  - Should the initial API support browser-hosted VS Code and fallback notifications, and what should callers observe when permission or native support is unavailable?
  - Should the initial contract offer only notification-body click navigation, or also action buttons with explicitly platform-dependent support?

## Evidence

- **Existing capability and remaining gap:** src/vs/workbench/contrib/chat/browser/chatWindowNotifier.ts uses IHostService.showToast and explicitly focuses the originating window on a click. These calls are internal chat behavior; chat.notifyWindowOnConfirmation does not provide a general extension notification API.
- **Public API check:** src/vscode-dts/vscode.d.ts exposes showInformationMessage/showWarningMessage/showErrorMessage. src/vs/workbench/api/browser/mainThreadMessageService.ts routes those through INotificationService.notify or modal dialogs, not the OS toast service. Searches of src/vscode-dts and src/vs/workbench/api found no showToast, showSystemNotification, desktopNotification, or systemNotification entry point.
- **Reusable infrastructure and limitations:** src/vs/workbench/services/host/electron-browser/nativeHostService.ts:251-270 delegates to nativeHostService.showToast and falls back to browser notifications. src/vs/platform/native/electron-main/nativeHostMainService.ts:1452-1506 constructs Electron Notification objects and returns click/action results. src/vs/workbench/services/host/browser/toasts.ts requests browser permission and reports clicks, but does not expose native action-button parity; focus and extension command dispatch would need an explicit public contract.
