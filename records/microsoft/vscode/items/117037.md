# Issue #117037 — Files open in wrong window

[https://github.com/microsoft/vscode/issues/117037](https://github.com/microsoft/vscode/issues/117037)

## Summary

This remains an accepted multi-window routing bug with independent Linux reproductions, including a maintainer-confirmed clean-profile reproduction. The current `menus` routing misses the window/editor-group code involved, so it should remain open under the workbench window and editor areas.

## Change summary

Opening a file from one VS Code window can route the file to a different existing or auxiliary window.

## Best solution

File-open requests initiated from a window should retain that originating window through the native dialog, main-process routing, and editor-group selection; auxiliary or locked groups should not redirect the result to another window unless the user explicitly chose that destination.

## Plan brief

- **Likely files:** `src/vs/platform/native/electron-main/nativeHostMainService.ts`, `src/vs/platform/windows/electron-main/windowsMainService.ts`, `src/vs/workbench/services/editor/common/editorGroupFinder.ts`, `src/vs/workbench/browser/parts/editor/editorParts.ts`
- **Validation:** On Linux, open a workspace window and a second empty window, invoke File: Open File from the empty window, and verify the selected file opens there; repeat after moving an editor into an auxiliary window and with locked and unlocked groups, confirming that only the initiating window receives the file.
- **Behavior:**

  > A file chosen through File: Open File must open in the VS Code window from which the command and native dialog were invoked. This must remain true when another application window is maximized, when the initiating window is empty, and when the workspace has auxiliary or locked editor groups. Existing behavior for explicitly opening in a new window and revealing an already-open editor must remain unchanged. Acceptance requires repeating the Linux multi-window scenarios without any file appearing in a non-originating window.
- **Trace:**

  > The native dialog path starts in src/vs/workbench/services/dialogs/electron-browser/fileDialogService.ts and reaches NativeHostMainService.doOpenPicked in src/vs/platform/native/electron-main/nativeHostMainService.ts, which supplies the sender as `contextWindowId`. WindowsMainService.resolveContextWindow in src/vs/platform/windows/electron-main/windowsMainService.ts is intended to preserve that application window. Once the request reaches the renderer, src/vs/workbench/services/editor/common/editorGroupFinder.ts falls back to the globally active or most-recent unlocked group, while src/vs/workbench/browser/parts/editor/editorParts.ts aggregates MRU state across the main and auxiliary editor parts. The original clean-profile reproduction predates auxiliary windows, but the latest report implicates moved auxiliary groups, so the plan must determine whether these are two defects or one surviving focus/routing defect. Do not change `window.openFilesInNewWindow`, explicit new-window commands, or reveal-if-open semantics while isolating the origin-window failure.

## Evidence

- **confirmed reproduction:** A maintainer reproduced the issue in a Fedora 35 VM after the reporter reproduced it with fresh user data and an empty extensions directory: https://github.com/microsoft/vscode/issues/117037#issuecomment-961403308
- **later independent reproduction:** A second reporter reproduced the same observable result on Ubuntu 22.04 with VS Code 1.95.3: a file selected from a newly opened empty window appeared in the existing workspace window instead. https://github.com/microsoft/vscode/issues/117037#issuecomment-2557969630
- **current source routing:** src/vs/platform/native/electron-main/nativeHostMainService.ts passes the initiating `windowId` as `contextWindowId`, and src/vs/platform/windows/electron-main/windowsMainService.ts uses it in `resolveContextWindow`; the remaining editor destination is selected through src/vs/workbench/services/editor/common/editorGroupFinder.ts and the cross-part MRU state in src/vs/workbench/browser/parts/editor/editorParts.ts.
- **multiple current triggers:** The original clean-profile report involved separate application windows, while the latest investigation describes an editor group moved to an auxiliary window and extension-created window state: https://github.com/microsoft/vscode/issues/117037#issuecomment-4983540573. That distinction needs diagnosis rather than a caused-by-extension close.
- **no canonical or fix:** The canonical search found no older open issue with the same reporter-observable symptom, and repository history contains no commit explicitly fixing https://github.com/microsoft/vscode/issues/117037 after it was reopened.
