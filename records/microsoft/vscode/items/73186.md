# Issue #73186 — Regex pattern to clear all problems of a task owner

[https://github.com/microsoft/vscode/issues/73186](https://github.com/microsoft/vscode/issues/73186)

## Summary

The requested output-triggered, owner-scoped clearing capability is still missing. Existing begin/end patterns provide normal build-cycle cleanup, but not the independent clearing and suppression semantics requested here; the related command and documentation issues do not replace this accepted Backlog item.

## Change summary

Allow a task-output regex to clear its problem owner's diagnostics and suspend further collection until task exit or the next background begin pattern.

## Best solution

Provide an explicit problem-matcher clearing capability in the tasks area, with defined interaction with document filtering and shared diagnostic owners. Preserve existing begin/end cleanup behavior for configurations that do not opt in.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/tasks/common/problemMatcher.ts`, `src/vs/workbench/contrib/tasks/common/problemCollectors.ts`, `src/vs/workbench/contrib/tasks/test/common/problemMatcher.test.ts`, `src/vs/workbench/contrib/tasks/test/common/problemCollectors.test.ts`
- **Validation:** Add parser and collector tests for a clear signal with pre-existing owner markers, subsequent matching output, task completion, and a background restart. Assert immediate removal, no reappearance from buffered or replayed output, suppression until the specified resume boundary, and preservation of unrelated owners. Run the focused problemMatcher and problemCollectors suites using scripts/test.sh in an implementation workspace; no tests were run in this read-only review.
- **Behavior:**

  > A task can recognize an output line as an explicit signal to discard diagnostics for its configured problem owner, independently of normal successful or unsuccessful build-cycle messages. For foreground tasks, subsequent output must not repopulate that owner's problems during the same execution. For background tasks, the signal resets the current collection cycle and collection resumes at the next begin signal. Existing configurations and unrelated owners retain their current behavior; acceptance checks must also cover buffered output, model-removal replay, and the agreed document-filtering contract.
- **Trace:**

  > The public schema and ProblemMatcherParser in src/vs/workbench/contrib/tasks/common/problemMatcher.ts expose only normal problem patterns and background begin/end controls. In src/vs/workbench/contrib/tasks/common/problemCollectors.ts, StartStopProblemCollector collects continuously until completion, while WatchingProblemCollector.tryBegin and tryFinish drive resource cleanup and background state. Background marker parsing is not generally gated by _activeBackgroundMatchers, and retained lines can be replayed after model removal, so resetting lifecycle state alone would not establish the requested suppression behavior. Existing removal respects applyTo, whereas the request describes clearing all owner problems; that public semantic needs explicit agreement. Owners may also be shared with language services, as documented at https://github.com/microsoft/vscode/issues/77214#issuecomment-553365352. Keep manual Problems-pane clearing and general task-clearing commands outside this feature's scope.
- **Open decisions:**
  - Should an explicit clear signal remove every diagnostic for the configured owner, including documents excluded by applyTo, or preserve the document filtering used by existing cleanup?

## Evidence

- **Requested behavior and supporting use case:** https://github.com/microsoft/vscode/issues/73186 requests an independent regex-triggered clear operation for both foreground and background tasks. The supplied comment describes Gulp SCSS/JS diagnostics that survive subsequent successful runs, supporting the need for an explicit reset escape hatch.
- **Existing configuration does not cover the request:** src/vs/workbench/contrib/tasks/common/problemMatcher.ts:1250-1403 defines the problem-matcher schema with additionalProperties:false. Its background controls are activeOnStart, beginsPattern, and endsPattern; no clearAllPattern or equivalent is exposed. ProblemMatcherParser.addWatchingMatcher requires both begin and end patterns.
- **Existing cleanup is cycle-dependent:** In src/vs/workbench/contrib/tasks/common/problemCollectors.ts, StartStopProblemCollector records old owner resources for cleanup and AbstractProblemCollector.done reports collected markers before cleaning obsolete ones. WatchingProblemCollector.tryBegin records resources to clean; tryFinish cleans them only when an active background matcher ends. These paths do not implement an independent immediate clear followed by suppression until the next begin.
- **Compatibility boundary:** AbstractProblemCollector._cleanMarkers filters removal through applyToByOwner and open-model state. WatchingProblemCollector also has collector-wide marker caches and retained lines replayed after model removal. An explicit clear needs defined document-filtering semantics and must not restore cleared diagnostics from pending or replayed output.

The latter two also postdate this re-reviewed issue. None establishes an older canonical for the same observable request.
- **Shared-owner constraint and maintainer direction:** https://github.com/microsoft/vscode/issues/77214#issuecomment-553365352 explains that tasks intentionally share owners with language services to avoid duplicate diagnostics. https://github.com/microsoft/vscode/issues/50448#issuecomment-543610065 expresses maintainer interest in a clearing command, but does not settle or implement this issue's output-triggered capability.
