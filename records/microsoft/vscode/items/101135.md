# Issue #101135 — Support FilesDirectories for file systems

[https://github.com/microsoft/vscode/issues/101135](https://github.com/microsoft/vscode/issues/101135)

## Summary

Keep this accepted feature request open: current file-service and Explorer behavior still prevents a resource from exposing both editable contents and children. It has 25 upvotes and reached Backlog through the documented community process; no verified older canonical or implementing fix was found.

## Change summary

Allow extension-provided filesystem entries to have both file contents and directory children, with native Explorer and breadcrumb navigation.

## Best solution

Define a backward-compatible filesystem-provider contract for content-bearing containers, then support expanding their children and explicitly opening their contents in Explorer and breadcrumbs. Settle the public API semantics before implementation rather than treating the existing FileType bitmask as sufficient support.

Add file-service tests for the chosen hybrid entry representation and confirm ordinary files, directories and symbolic links retain their existing behavior.
- **Behavior:**

  > An extension needs a single filesystem resource that has both contents and child resources. Native Explorer and breadcrumb navigation should expose its children, with expansion as the default interaction and an explicit way to open its contents as proposed in the issue. Acceptance should exercise both child navigation and contents access on the same resource, including saving if the chosen contract permits edits. Ordinary files and directories must retain their current interactions.
- **Trace:**

  > The request is https://github.com/microsoft/vscode/issues/101135, accepted into Backlog with 25 upvotes. FileType in src/vscode-dts/vscode.d.ts has no documented hybrid-entry contract, although FileService.toFileStat in src/vs/platform/files/common/fileService.ts independently computes file and directory flags. That is not end-to-end support: validateReadFile and write validation reject entries marked as directories, while the ExplorerView onDidOpen handler in src/vs/workbench/contrib/files/browser/views/explorerView.ts skips directories. FileDataSource.hasChildren in src/vs/workbench/browser/parts/editor/breadcrumbsPicker.ts uses directory status for expansion, and breadcrumbsModel.ts represents path entries as separate file or folder kinds. The trace establishes the missing capability, not a complete inventory of affected filesystem operations. Planning must settle the extension-facing representation and operation semantics while preserving ordinary filesystem behavior; no code was executed or modified during this review.
- **Open decisions:**
  - Should content-bearing containers be represented by a documented FileType.File | FileType.Directory combination, a distinct FileType value, or a separate provider capability/API?
  - Should reading and writing contents use the existing readFile/writeFile contract or distinct operations, and what should rename, copy and delete mean for the resource's contents and children?
