# Issue #182642 — Clipboard APIs do not work inside iframes in webviews

[https://github.com/microsoft/vscode/issues/182642](https://github.com/microsoft/vscode/issues/182642)

## Summary

Keep open: the nested-frame Clipboard API failure has corroborating reproduction evidence, and current source still distinguishes webview-origin permissions from those requested by embedded HTTP pages. No fixing commit or older canonical owning this same API failure was established; the related keyboard-shortcut issues do not replace it.

## Change summary

A user-initiated navigator.clipboard.writeText call fails inside a cross-origin iframe embedded in a webview despite explicit clipboard-write delegation.

## Best solution

Make explicitly delegated, user-initiated clipboard writes work in nested webview frames while preserving restrictions for unrelated content. Diagnose the interaction between webview Permissions Policy and Electron session permission handling before choosing the implementation.

- **Behavior:**

The finished behavior should permit this explicitly delegated, user-initiated write without requiring a parent-message workaround. Existing direct-webview clipboard access must continue working, and frames without delegation must remain restricted.
- **Trace:**

## Evidence

- **Concrete reproduction:** https://github.com/microsoft/vscode/issues/182642 provides a localhost iframe with allow="clipboard-write" and a button calling navigator.clipboard.writeText('inner'); clicking it produces 'Write permission denied'. The reporter states the equivalent cross-origin nesting works outside VS Code.
- **Independent corroboration:** https://github.com/microsoft/vscode/issues/129178#issuecomment-913093082 independently reports that navigator.clipboard is unavailable inside a child webview iframe even with allow="clipboard-read; clipboard-write;". This supports the reported defect, but no current runtime reproduction was performed.
- **Current permission handling:** src/vs/code/electron-main/app.ts:254-298 grants clipboard-read and clipboard-sanitized-write to requesting URLs beginning vscode-webview://. Both session permission handlers reject URLs outside the recognized webview and workbench origins, including the reported http://127.0.0.1:8000/ origin. This is a concrete denial path to investigate; the exact requestingUrl supplied by Electron for the nested call was not observed.
- **Existing frame delegation:** src/vs/workbench/contrib/webview/browser/webviewElement.ts:420-432 and src/vs/workbench/contrib/webview/browser/pre/index.html:1032-1051 already delegate clipboard-read and clipboard-write on VS Code-created frames when supported. Those attributes alone do not establish that a differently originated descendant passes Electron's permission handlers.
- **Related extension closure was a workaround:** https://github.com/Dart-Code/Dart-Code/issues/4540#issuecomment-1549444770 documents the same outer-button-success/inner-button-failure reproduction. Its closure cites https://github.com/Dart-Code/Dart-Code/pull/4814, and later discussion describes forwarding clipboard-write messages to the parent, not a fix to direct nested-frame Clipboard API access in VS Code.
