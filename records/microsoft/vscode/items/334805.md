# Issue #334805 — Tool call's `explanation` is misleading due to truncated arguments

[https://github.com/microsoft/vscode/issues/334805](https://github.com/microsoft/vscode/issues/334805)

## Summary

Confirmed on main: the risk-assessment prompt builder truncates the whole JSON-stringified tool arguments at a fixed byte cutoff, so fields that appear later in the object (like the target issue number) never reach the model, producing a misleading permission explanation — exactly the reporter's scenario.

## Change summary

When a tool call's arguments are long, the risk-assessment explanation shown in the permission prompt is generated from truncated JSON and cites the wrong target (e.g. the wrong issue number).

## Best solution

In serializeParameters() (src/vs/workbench/contrib/chat/browser/tools/chatToolRiskAssessmentService.ts), avoid blind end-truncation of the full JSON string — e.g. truncate only long individual string values before stringifying, or otherwise make sure short, high-signal identifier fields (numbers, ids, paths) aren't dropped just because they sort late in the object.

- **Fix prompt:**

  > In src/vs/workbench/contrib/chat/browser/tools/chatToolRiskAssessmentService.ts, serializeParameters() (around line 187) does `argsJson = JSON.stringify(parameters ?? {})` and, if the result exceeds MAX_PARAM_BYTES (2000, line 51), does a blind `argsJson.slice(0, MAX_PARAM_BYTES) + '...[truncated]'`. Because JSON.stringify preserves object key insertion order, any field that happens to appear after a long preceding field (commonly a long `body`/`explanation`/`description` string) gets silently cut off entirely — even short, high-signal identifier fields like `issue_number`. This is exactly the bug reported in https://github.com/microsoft/vscode/issues/334805: the mini model generating the permission-prompt explanation for `add_issue_comment` saw a truncated JSON missing `issue_number`, so it fell back to referencing the wrong (currently-open) issue in its explanation, nearly causing the user to approve a comment on the wrong issue. Fix the truncation strategy in serializeParameters() (or the parameters object before stringifying) so that long individual field VALUES are truncated/capped (e.g. cap each string value's length before JSON.stringify, so the overall object stays bounded) rather than slicing the serialized JSON string itself — this preserves the object's full key set (including short but critical fields like issue/PR numbers) while still bounding total prompt size. Do not change the rubric/prompt text (buildTerminalPrompt/buildGenericToolPrompt) or the cache-key logic in normalizeRiskCacheParameters — only the serialization step feeding the prompt. Add a unit test asserting that when parameters include a long string field followed by a short numeric/id field, the serialized output passed into the prompt still contains that id field after truncation; the test should fail against the current slice-based implementation and pass once value-level truncation is used.
