# Issue #162191 — Open in Merge Editor button shall always remove the conflict markers

[https://github.com/microsoft/vscode/issues/162191](https://github.com/microsoft/vscode/issues/162191)

## Summary

Keep open: revealing an existing merge editor still does not repeat the marker-removing initialization after the result file is reverted. The maintainer-supported recovery request remains distinct from the related issues, and the issue-referencing commit only changed marker visibility.

## Change summary

Provide recovery when conflict markers return to the result file while its merge editor remains open.

## Best solution

Provide an explicit, discoverable re-merge recovery when markers return, following the maintainer discussion and reusing the existing reset behavior where appropriate. Settle whether invoking Open in Merge Editor should itself reset the result or instead offer recovery without unexpectedly discarding merge edits.

Verify that the agreed recovery is available and produces the initial marker-free auto-merged result with unresolved conflicts still tracked. Repeat using File > Revert, and verify that reopening a marker-free partially resolved result preserves its edits. Add targeted merge-editor regression coverage for the chosen recovery behavior.
- **Behavior:**

  > When conflict markers return to a result file while its merge editor remains open, the user needs a clear way to restart that merge rather than being stranded in the restored marked text. The reported sequence discards changes through the original text editor and then invokes Open in Merge Editor again. Recovery should restore the initial auto-merged result while keeping unresolved conflicts actionable. Reopening a marker-free result must not unexpectedly reset completed merge work; the maintainer must settle whether marker-bearing results reset automatically or require an explicit recovery action.
- **Trace:**

  > WorkspaceMergeEditorModeFactory.createInputModel in src/vs/workbench/contrib/mergeEditor/browser/mergeEditorInputModel.ts detects markers only when constructing the model. MergeEditorInput.resolve in browser/mergeEditorInput.ts retains that model, and OpenMergeEditor in browser/commands/commands.ts opens or reveals the editor without resetting it. The existing mergeEditor.resetResultToBaseAndAutoMerge command calls MergeEditorModel.reset, which recomputes the auto-merged text and conflict states, but has no marker-conditioned recovery contract. The discussion at https://github.com/microsoft/vscode/issues/162191#issuecomment-1263309604 favors an explicit remerge button; earlier comments also consider restarting on external modifications. Commit https://github.com/microsoft/vscode/commit/12637cf568a7bfc4e3357aca5194a7cdcb1b2350 only removes marker-hiding presentation and must not be treated as completion. Preserve ordinary marker-free reopening, text-editor availability, and unrelated save/discard semantics; the uncertainty is the recovery trigger and its treatment of existing edits.
- **Open decisions:**
  - When restored markers are detected, should Open in Merge Editor automatically restart the result, or reveal the existing session with an explicit re-merge recovery action?
  - If the marked result also contains manual merge edits, should recovery require confirmation before replacing the result with the initial auto-merge?
