# Issue #321491 — agents window -- ability to sort `Done` sessions by "most recently marked done"

[https://github.com/microsoft/vscode/issues/321491](https://github.com/microsoft/vscode/issues/321491)

## Summary

Keep open: the Done section still inherits created/updated ordering rather than ordering by when sessions were marked done. This team-authored request identifies a distinct recovery workflow; no verified canonical or implementing fix was found.

## Change summary

Allow Done sessions to be sorted by most recently marked done so mistakenly archived sessions are easy to restore.

## Best solution

Provide archive-recency ordering for the Done section without changing provider activity timestamps or active-session ordering. Settle whether this becomes the section's default or a selectable ordering, and define persistence and fallback behavior for sessions with no recorded archive time.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts`, `src/vs/sessions/contrib/sessions/browser/views/sessionsViewActions.ts`, `src/vs/sessions/services/sessions/browser/sessionsListModelService.ts`, `src/vs/sessions/services/sessions/browser/sessionsManagementService.ts`, `src/vs/sessions/contrib/sessions/test/browser/sessionsList.test.ts`, `src/vs/sessions/services/sessions/test/browser/sessionsListModelService.test.ts`
- **Validation:** Add focused sessionsList tests with creation/activity timestamps deliberately opposed to archive order: the most recently marked-done session must appear first under archive-recency ordering. Cover restore/rearchive, the agreed fallback for unknown archive times, persistence across list recreation if required, and unchanged active-session ordering.
- **Behavior:**

  > A user who mistakenly marks an older session done can find it at the top of Done when using archive-recency ordering, even if other sessions were created or updated more recently. Restoring it removes it from Done; marking it done again gives it the newest archive position. Acceptance must cover the chosen default or selection behavior, unknown archive times, and the agreed reload behavior without changing active-session ordering.
- **Trace:**

  > groupSessionsForList in src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts sorts all sessions before separating archived entries, so Done inherits the global created/updated ordering. sessionsViewActions.ts exposes only those two modes, and SessionsListModelService stores their presentation overrides. SessionsManagementService.archiveSession delegates to the provider and then emits onDidArchiveSession; the shared ISession contract exposes an archive boolean but no archive-recency timestamp. The source establishes the missing capability, but not the intended default, persistence scope, or fallback for previously archived sessions. Preserve provider-neutral list ownership and do not repurpose provider updatedAt as an archive timestamp. The workspace-grouping request at https://github.com/microsoft/vscode/issues/313108 is related but distinct.
- **Open decisions:**
  - Should Done always use archive-recency ordering, or should users explicitly select it while retaining created/updated ordering?
  - Should archive recency survive application restarts only in the current profile, or follow the session across clients?
  - Where should sessions whose archive time is unknown appear relative to sessions with a recorded archive time?
