# Issue #213701 — Multi-select should fire one tabs API event

[https://github.com/microsoft/vscode/issues/213701](https://github.com/microsoft/vscode/issues/213701)

## Summary

The event-coalescing debt remains on current main: bulk editor operations reach the Tabs API as individual editor changes and each operation fires its own extension event. This member-authored Backlog item is protected from judgment closes, and no factual fix or older canonical was found.

## Change summary

Coalesce the tab changes produced by one multi-tab user operation into a single Tabs API event containing all affected tabs.

## Best solution

Define a transaction boundary for multi-tab close and move operations that gives extensions one complete TabChangeEvent while preserving immediately consistent tab model state for subsequent API calls.

## Plan brief

- **Likely files:** `src/vs/workbench/api/browser/mainThreadEditorTabs.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/common/extHostEditorTabs.ts`, `src/vs/workbench/api/test/browser/mainThreadEditorTabs.test.ts`, `src/vs/workbench/api/test/browser/extHostEditorTabs.test.ts`, `src/vs/workbench/browser/parts/editor/editorGroupView.ts`
- **Validation:** Add a Tabs API unit test that performs one modeled bulk multi-tab close or move and asserts exactly one onDidChangeTabs notification containing every affected tab, while an immediate follow-up tabGroups query or close call observes the updated model.
- **Behavior:**

  > One user operation applied to multiple selected editor tabs should produce one vscode.window.tabGroups.onDidChangeTabs notification containing all affected tabs in the appropriate opened, closed, or changed array. Extensions must continue to observe an up-to-date tabGroups model immediately after the operation. Single-tab operations and unrelated changes must retain their existing semantics.
- **Trace:**

  > Bulk close flows through EditorGroupView.doCloseEditors in src/vs/workbench/browser/parts/editor/editorGroupView.ts and closes each selected editor separately. EditorService forwards each group-model event as an individual IEditorsChangeEvent to MainThreadEditorTabs, whose handlers immediately send one TabOperation over the protocol. ExtHostEditorTabs.$acceptTabOperation then fires one singleton TabChangeEvent per operation despite vscode.d.ts allowing arrays. The earlier discussion at https://github.com/microsoft/vscode/issues/146786#issuecomment-1088717605 establishes the important boundary: notification coalescing must not leave the extension-host tab model stale when an extension immediately invokes another Tabs API operation. Do not expose workbench-internal multi-selection state or change single-tab API behavior.
- **Open decisions:**
  - Should one event cover only explicit multi-selected bulk actions, or all tab operations produced by the same user action or event-loop turn?
  - Must the coalesced notification be delivered only after the complete bulk operation while tabGroups state remains synchronously current throughout, or may extensions observe intermediate model states before the single notification?

## Evidence

- **current main:** src/vs/workbench/api/browser/mainThreadEditorTabs.ts registers IEditorService.onDidEditorsChange and handles one IEditorsChangeEvent at a time; each open, close, move, or update immediately invokes $acceptTabOperation.
- **extension-host behavior:** src/vs/workbench/api/common/extHostEditorTabs.ts::$acceptTabOperation fires _onDidChangeTabs once for each individual TabOperation, always placing only one tab in opened, closed, or changed.
- **bulk-operation path:** src/vs/workbench/browser/parts/editor/editorGroupView.ts::doCloseEditors iterates selected editors and closes them individually, producing the granular model events observed by MainThreadEditorTabs.
- **API shape:** src/vscode-dts/vscode.d.ts defines TabChangeEvent.opened, closed, and changed as arrays, so the public shape can represent a coalesced result even though the current implementation emits singleton arrays.
- **known synchronization constraint:** https://github.com/microsoft/vscode/issues/146786#issuecomment-1088717605 explains that earlier event queuing caused model-synchronization problems, including close calls observing a model that had not yet updated. That older issue was closed as expected behavior, but this later member-authored debt explicitly records the desired improvement.
- **no canonical:** Repository issue search found no older open issue with the same observable multi-select Tabs API batching request; the supplied candidate issues concern Explorer selection or mouse shortcuts and do not own this work.
