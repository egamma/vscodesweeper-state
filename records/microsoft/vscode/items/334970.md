# Issue #334970 — MCP client triggers confusing "does not support automatic client registration" OAuth dialog for servers using only static headers (non-OAuth), e.g. on an expired credential

[https://github.com/microsoft/vscode/issues/334970](https://github.com/microsoft/vscode/issues/334970)

## Summary

The current source still routes rejected static credentials into OAuth discovery and potentially an unrelated client-registration prompt. Keep this accepted MCP authentication bug open; the recovery behavior needs a maintainer decision that preserves automatic OAuth discovery for genuine OAuth servers.

## Change summary

Prevent an expired or invalid static MCP credential from producing an unrelated OAuth client-registration dialog.

## Best solution

Provide a clear static-credential authentication failure and recovery path in the MCP HTTP transport, without disabling legitimate automatic OAuth discovery merely because the configuration omits an oauth block. Decide how header-only authentication is distinguished from OAuth-capable configurations before implementing that boundary.

Run the targeted extHostMcp and mainThreadMcp unit suites through scripts/test.sh; manually verify the reporter's valid-token then invalid-token restart scenario.
- **Behavior:**

  > An HTTP MCP server using only a static credential currently presents an OAuth client-registration dialog when that credential is rejected, even when the server has no OAuth discovery endpoints. For a configuration identified as static-auth-only, rejection should produce an actionable authentication failure rather than ask for an unrelated client ID. Genuine OAuth servers must retain automatic discovery without requiring a preconfigured client ID. Acceptance covers invalid Authorization and API-key headers, 401 and 403 responses, missing or custom challenges, and successful OAuth discovery.
- **Trace:**

  > McpHTTPHandle._fetchWithAuthRetry in src/vs/workbench/api/common/extHostMcp.ts starts discovery solely from the response status; createAuthMetadata returns fabricated default OAuth metadata after discovery failures. _addAuthHeader then reaches MainThreadMcp.$getTokenFromServerMetadata and dynamic-provider registration, where ExtHostAuthentication.$registerDynamicAuthProvider prompts after DCR fails. This chain is present on current main and was traced without execution. Existing extHostMcp tests cover automatic discovery after a bare 401 and default-metadata fallback. The oauth schema in src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts supplies OAuth parameters rather than an opt-in flag, while headers may also contain unrelated transport metadata. Preserve genuine OAuth discovery, existing credential handling for OAuth providers, and cross-origin header protections; automatic re-prompting of input variables is an optional recovery improvement, not a prerequisite for resolving the misleading dialog. https://github.com/microsoft/vscode/issues/321834 concerns a distinct already-authorized OAuth recovery case.
- **Open decisions:**
  - Should static-auth-only behavior be explicitly selected by configuration, or inferred from configured credentials and server discovery evidence, and what happens when a server combines static headers with valid OAuth metadata?
