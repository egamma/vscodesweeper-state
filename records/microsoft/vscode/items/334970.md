# Issue #334970 — MCP client triggers confusing "does not support automatic client registration" OAuth dialog for servers using only static headers (non-OAuth), e.g. on an expired credential

[https://github.com/microsoft/vscode/issues/334970](https://github.com/microsoft/vscode/issues/334970)

## Summary

Confirmed in source on current main: `_fetchWithAuthRetry` in extHostMcp.ts triggers OAuth discovery/DCR on any 401/403 regardless of whether the MCP server config has an `oauth` block, so a header-only server with an expired static credential surfaces a confusing 'client registration' dialog. Milestone is Backlog (a holding bin, does not block), no open PR references this, and the fix is bounded — this is agent-ready.

## Change summary

An MCP server configured with only static headers (no oauth block) still triggers VS Code's OAuth Dynamic Client Registration fallback dialog on 401/403, e.g. from an expired static credential.

## Best solution

Guard `_fetchWithAuthRetry`/`_addAuthHeader` in extHostMcp.ts so OAuth discovery is only attempted when the launch config actually has an `oauth` block (or existing auth metadata); for header-only servers, a 401/403 should surface as a plain request failure (ideally re-prompting the `${input:...}` value) instead of falling into `createAuthMetadata`/DCR.

- **Behavior:**

  > When an MCP server's `mcp.json` entry has no `oauth` block (only a static `headers` block, or none), a 401/403 response must not trigger OAuth discovery or the 'does not support automatic client registration' dialog. The failure should surface as a plain request/auth error (ideally re-prompting any `${input:...}` values used in the static headers). Servers that DO have an `oauth` block, or that have already established auth metadata via prior OAuth discovery, are unaffected — their existing discovery/DCR flow must keep working exactly as before.
- **Trace:**

  > `_fetchWithAuthRetry` (src/vs/workbench/api/common/extHostMcp.ts:805) checks only `isAuthStatusCode(res.status)` and the absence of `this._authMetadata` before calling `createAuthMetadata(...)` — it never inspects `this._launch.oauth` to see if OAuth was actually configured for this server. Static headers from `this._launch.headers` are merged into the request headers earlier (e.g. line 638-642), so a header-only server's 401 still falls into this branch. The boundary: do not touch the OAuth flow for servers that DO configure `oauth`, and do not change the WWW-Authenticate parsing/discovery logic itself — only gate whether discovery is attempted at all. Related: https://github.com/microsoft/vscode/issues/279955 (DCR regression for OAuth-configured servers) and https://github.com/microsoft/vscode/issues/321834 (stale-token eviction for completed OAuth flows) are adjacent but do not cover the no-OAuth-configured case per the reporter's own search.
