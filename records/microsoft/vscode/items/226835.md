# Issue #226835 — SCM Graph - add support for async filtering

[https://github.com/microsoft/vscode/issues/226835](https://github.com/microsoft/vscode/issues/226835)

## Summary

Keep open: the SCM Graph still filters only loaded history, despite existing asynchronous tree-search infrastructure. A maintainer accepted the direction, and no verified older canonical owns this specific behavior.

## Change summary

Load additional history while filtering the SCM Graph so matching commits beyond the loaded pages can appear without manually clearing the filter and scrolling.

## Best solution

Make graph filtering discover matching unloaded history while keeping the UI responsive and respecting repository and reference selection. Agree on loading limits and graph-context behavior before adopting the existing asynchronous search capabilities.

- **Behavior:**

  > Filtering the Source Control Graph should discover matching commits beyond the currently loaded history without requiring the user to clear the filter and scroll first. Reproduce with a matching commit beyond the initial page and verify that it becomes visible after filtering. Query changes and clearing the filter must not leave stale results or disrupt normal browsing. The plan must define search limits and whether nonmatching graph-context commits remain visible.
- **Trace:**

  > SCMHistoryViewPane constructs WorkbenchCompressibleAsyncDataTree in src/vs/workbench/contrib/scm/browser/scmHistoryViewPane.ts without a findProvider, so existing asynchronous find infrastructure is not enabled for this surface. SCMHistoryViewModel.getHistoryItems fetches ordinary pages without filterText; SCMHistoryTreeKeyboardNavigationLabelProvider matches loaded messages and authors and excludes the load-more placeholder from matching. IAsyncFindProvider in src/vs/base/browser/ui/tree/asyncDataTree.ts already provides cancellation-aware search hooks. ISCMHistoryOptions supports filterText, and GitHistoryProvider._searchHistoryItems in extensions/git/src/historyProvider.ts searches authors and messages, but that helper clears refNames and therefore is not automatically equivalent to filtering the selected graph history. Preserve repository/reference selection, ordinary unfiltered pagination, graph topology and existing message/author matching expectations. The maintainer accepted asynchronous filtering at https://github.com/microsoft/vscode/issues/226835#issuecomment-2313277881; uncertainty remains around loading bounds and presentation of surrounding history.
- **Open decisions:**
  - Should filtering continue until enough matches fill the viewport or history is exhausted, or stop at a bounded search limit with an explicit continuation control?
  - Should filtered results display only matching commits, or retain nonmatching ancestor/context commits needed to explain graph connections?
