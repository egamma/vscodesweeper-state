# Issue #184047 — Display disabled tasks in Run Build Task... menu

[https://github.com/microsoft/vscode/issues/184047](https://github.com/microsoft/vscode/issues/184047)

## Summary

Keep this accepted feature request open: current task APIs and build-task selection do not expose a visible-but-unavailable state. It reached 20 upvotes and entered Backlog; the linked Swift change is a workaround, not an implementation of the requested core capability.

## Change summary

Allow task providers to display temporarily unavailable build tasks without allowing users to run them.

## Best solution

Provide an explicit task-availability contract that the build-task picker honors, preserving discoverability without requiring executable dummy tasks. Agree on the public API and enforcement scope before implementation, while preserving existing unresolved-task behavior.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTask.ts`, `src/vs/workbench/api/browser/mainThreadTask.ts`, `src/vs/workbench/contrib/tasks/common/tasks.ts`, `src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts`
- **Validation:** Use a test task provider that returns one available and one temporarily unavailable build task. Invoke Tasks: Run Build Task and verify both remain visible, the unavailable task cannot launch by mouse or keyboard, and the available task runs normally. Repeat with the unavailable task as the sole/default build task and with task.quickOpen.skip enabled; restore availability and verify it can run. Verify tasks lacking execution retain their existing resolution behavior.
- **Behavior:**

  > An extension must be able to expose a build task that is temporarily unavailable because another workspace operation conflicts with it. The task remains discoverable in Run Build Task but cannot be launched from that picker, without introducing a runnable dummy task. Available tasks continue to behave normally, and a sole or default unavailable task must not bypass the restriction through automatic selection. Existing missing-execution resolution behavior remains unchanged.
- **Trace:**

  > Task and TaskProvider in src/vscode-dts/vscode.d.ts have no availability contract; missing execution already has documented resolution semantics. TaskDTO.from in src/vs/workbench/api/common/extHostTask.ts transports execution and task metadata without an availability state. In src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts, _runBuildCommand delegates to _runTaskGroupCommand; _createTaskQuickPickEntries constructs ordinary selectable entries, _showQuickPick can skip a sole entry, and the group command can directly execute a single default task. Existing hide and task.autoDetect controls remove discovery rather than preserve a non-actionable row. https://github.com/swiftlang/vscode-swift/pull/548 demonstrates the dummy-task workaround and explicitly identifies this missing core capability. The uncertainty is the public availability contract and its scope beyond the build picker; preserve unresolved-task semantics and normal enabled-task behavior.
- **Open decisions:**
  - Should the task-availability API expose only a disabled state, or also a human-readable reason shown with the unavailable task?
  - Should unavailability prevent execution through every entry point, including tasks.executeTask and dependency execution, or only user-facing task launch controls?

## Evidence

- **Accepted community demand:** https://github.com/microsoft/vscode/issues/184047 has 20 body upvotes and the Backlog milestone. The June 14, 2023 bot comment explicitly confirms promotion after sufficient community support. The fully read triage policy at https://github.com/microsoft/vscode/wiki/Issues-Triaging describes Backlog as accepted, unscheduled work.
- **Public API gap:** src/vscode-dts/vscode.d.ts:9129–9254 declares Task and TaskProvider without a disabled or availability property. TaskProvider.resolveTask documents missing execution as unresolved execution information, not an unavailable state; repurposing it would change an existing contract.
- **Current build-task flow:** src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts:2922–3056 constructs picker entries from task labels, descriptions and details without an availability state. _runBuildCommand delegates to _runTaskGroupCommand, which runs selected tasks and can run a single default task directly. src/vs/workbench/api/common/extHostTask.ts:243–286, TaskDTO.from, transports task execution and metadata but no disabled state.
- **Existing controls do not satisfy the request:** src/vs/workbench/contrib/tasks/browser/task.contribution.ts registers task.autoDetect and task.quickOpen.detail: these control provider discovery and descriptive text, not whether an individual visible task is actionable. src/vs/workbench/contrib/tasks/common/jsonSchema_v2.ts defines hide to remove a task from the picker, which is the opposite of retaining it visibly as unavailable.
- **Linked workaround, not a core fix:** https://github.com/swiftlang/vscode-swift/pull/548 was merged June 4, 2023. Its body explains that conflicting workspace operations suppress build tasks and introduce a runnable dummy task explaining their absence; it explicitly links this request as the missing capability that would eliminate that workaround.
- **Canonical search:** Read-only GitHub searches for disabled, unavailable, enable and availability task requests did not establish an older canonical with the same observable requirement. The verified open https://github.com/microsoft/vscode/issues/73748 concerns disabling task discovery or overriding execution for remote filesystem schemes, not displaying temporarily unavailable provider tasks; it does not absorb this request.
