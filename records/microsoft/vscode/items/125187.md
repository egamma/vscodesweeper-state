# Issue #125187 — Cannot drag and drop normal webviews between windows

[https://github.com/microsoft/vscode/issues/125187](https://github.com/microsoft/vscode/issues/125187)

## Summary

Normal webview panels still lack the transferable editor description required for dragging tabs between independent VS Code windows. The historical change removed misleading drop feedback, not the underlying limitation; this remains appropriately routed.

## Change summary

Allow a normal Markdown preview or other webview-panel tab to open successfully when dragged into another independent VS Code window.

## Best solution

Provide a supported cross-window reopening path for ordinary webview panels, including the normal Markdown preview. Establish how destination-window restoration works for panels with and without a registered serializer, without conflating independent windows with auxiliary editor windows.

Add automated coverage that an eligible ordinary panel produces consumable cross-window drag data and restores its document identity/state. Check the chosen behavior for panels without serializers, and preserve existing custom-editor and same-window drag behavior.
- **Behavior:**

  > Dragging the tab of a normal Markdown preview into another independently opened VS Code window currently does not open the preview there. The destination should display the corresponding preview through a supported restoration path. Acceptance must use independent workbench windows, not only an auxiliary window sharing the original workbench. Unsupported panels must not advertise a successful drop that silently does nothing.
- **Trace:**

  > fillEditorsDragData in src/vs/workbench/browser/dnd.ts relies on EditorInput.toUntyped to construct the cross-window editor payload. WebviewInput inherits the undefined implementation from src/vs/workbench/common/editor/editorInput.ts, while CustomEditorInput provides a resource and override. DynamicMarkdownPreview.create in extensions/markdown-language-features/src/preview/preview.ts still creates an ordinary webview panel. WebviewEditorInputSerializer and WebviewEditorService provide persistence and revival machinery, but the traced drag path does not use that machinery. The mitigation discussed at https://github.com/microsoft/vscode/issues/125187#issuecomment-852810743 only removed misleading feedback. Preserve custom-editor transfer, ordinary within-window movement, and auxiliary-window behavior; uncertainty begins at the contract for restoring a panel in a different workbench and extension-host context.
- **Open decisions:**
  - Should independent-window dragging support only panels with a registered restoration serializer, or should ordinary panels without one also be transferable?

## Evidence

- **Confirmed current transfer gap:** src/vs/workbench/browser/dnd.ts:270-295 calls editor.toUntyped() when building cross-window editor drag data and skips editors returning undefined. WebviewInput in src/vs/workbench/contrib/webviewPanel/browser/webviewEditorInput.ts does not override toUntyped(), so it inherits src/vs/workbench/common/editor/editorInput.ts:352-354, which returns undefined. Consequently no CodeDataTransfers.EDITORS entry is generated for an ordinary webview panel.
- **Reporter trigger still uses ordinary panels:** DynamicMarkdownPreview.create in extensions/markdown-language-features/src/preview/preview.ts:713-732 still uses vscode.window.createWebviewPanel. By contrast, CustomEditorInput.toUntyped in src/vs/workbench/contrib/customEditor/browser/customEditorInput.ts:430-436 supplies a resource and editor override, explaining the distinction in the report.
- **Historical mitigation, not completion:** https://github.com/microsoft/vscode/issues/125187#issuecomment-852810743 explicitly describes removing drop feedback and says further adoption of editor overrides is needed. The inspected diff of https://github.com/microsoft/vscode/commit/e57462fd1f6bd1cb30e35cc69d1127f9c2325a5f filters resource drag formats to file-service-supported resources; it does not introduce ordinary webview transfer.
- **Restoration boundary:** WebviewEditorInputSerializer in src/vs/workbench/contrib/webviewPanel/browser/webviewEditorInputSerializer.ts can serialize eligible panels and restore them through openRevivedWebview, but that persistence mechanism is not connected to the toUntyped-based cross-window drag path. Supporting arbitrary panels therefore needs more than assuming their synthetic resource URI is reopenable.
- **Related report is distinct:** https://github.com/microsoft/vscode/issues/125186 is closed and concerns dropping a file onto a notebook, not transferring a webview tab. Its discussion identifies iframe drag-event bubbling as the cause and points elsewhere; it is not a canonical for this issue.
- **Canonical search:** Read-only searches for webview dragging between windows and Markdown preview window dragging found no verified older canonical with this same symptom. https://github.com/microsoft/vscode/issues/164 is open but concerns native file and clipboard interoperability across applications, not reconstruction of webview editor tabs. Newer reports cannot serve as duplicate targets under the prior-review rule.
