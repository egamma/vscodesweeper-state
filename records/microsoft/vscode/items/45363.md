# Issue #45363 — Settings editor should search known keys in object type settings

[https://github.com/microsoft/vscode/issues/45363](https://github.com/microsoft/vscode/issues/45363)

## Summary

Keep open: current settings search still does not index known object-schema keys, and maintainers explicitly distinguished this request from searching configured values. No verified older canonical or fixing commit was found.

## Change summary

Make object-valued settings discoverable by searching their known nested property names, including color customization keys.

## Best solution

Include known nested schema properties in Settings editor discovery so an unconfigured color key can lead users to workbench.colorCustomizations. Account for referenced schemas, rather than limiting coverage to directly declared object properties.

Manually check that the Settings UI makes the nested match understandable.
- **Behavior:**

  > Users should find an object-valued setting by searching a known nested property even when that property has not been configured. Searching for the active line-number color should discover workbench.colorCustomizations using its current nested key, editorLineNumber.activeForeground. Acceptance must include referenced schemas as well as directly declared properties, without requiring users to seed settings.json first. Existing ordinary settings searches should retain their behavior.
- **Trace:**

  > LocalSearchProvider invokes SettingMatches._doFindMatchesInSetting in src/vs/workbench/contrib/preferences/browser/preferencesSearch.ts, whose matching inputs omit nested schema properties. The same file's TF-IDF document construction uses only top-level identity and description. src/vs/workbench/services/preferences/common/preferencesModels.ts exposes direct object properties, but the original color-customization example is declared through allOf and a schema reference in src/vs/workbench/services/themes/common/themeConfiguration.ts, so direct-property indexing alone would miss it. No execution was performed in the read-only checkout. Preserve configuration serialization, color semantics, and settings.json completion behavior; https://github.com/microsoft/vscode/issues/95260 explicitly routes the discovery idea to this Settings UI issue. The unresolved boundary is how broadly to traverse schema-defined properties and what users see when a nested property matches.
- **Open decisions:**
  - Should nested-property matches display the owning setting with an explanation of the matching property, or expose an individually navigable nested result?
  - Should discovery include only nested property names, or also their descriptions and valid values?
