# Issue #320435 — macOS: Ctrl+F and Ctrl+P intercepted by workbench when typing in webview text input, breaking Cocoa text navigation

[https://github.com/microsoft/vscode/issues/320435](https://github.com/microsoft/vscode/issues/320435)

## Summary

Real, source-reproducible bug: the webview keyboard forwarding mechanism in webviewElement.ts re-dispatches all keydown events (including Ctrl+F/Ctrl+P) from the webview iframe to the workbench window, preventing macOS Cocoa text navigation bindings from reaching the native text input inside the webview. No fix found on current main.

## Change summary

On macOS, Ctrl+F (forward character) and Ctrl+P (previous line) — standard Cocoa text navigation — are silently swallowed when focus is inside a webview text input, because the webview event forwarding mechanism intercepts them.

## Best solution

The webview's handleKeyEvent in src/vs/workbench/contrib/webview/browser/webviewElement.ts unconditionally re-dispatches all key events to the workbench. On macOS, Ctrl+F and Ctrl+P (WinCtrl+F/P) are only bound in editor-context keybindings (EditorContextKeys.textInputFocus), so they match nothing when a webview is focused — but the re-dispatch still consumes them, preventing the Cocoa text system from handling them natively in the webview iframe. The fix should either (a) not forward key events that have no matching workbench keybinding back into the webview, or (b) filter out known macOS Cocoa text navigation keys (Ctrl+A/B/E/F/N/P/K/D) from the forwarding path when the webview has focus. The related issue https://github.com/microsoft/vscode/issues/241801 (double-dispatch) touches the same mechanism and a fix should consider both.

## Evidence

- **keyboard forwarding mechanism:** src/vs/workbench/contrib/webview/browser/webviewElement.ts lines 724–739: handleKeyEvent re-dispatches all keydown events from the webview iframe to the workbench window via an emulated KeyboardEvent, which the keybinding service processes — this prevents Cocoa text bindings from reaching the native text input in the iframe.
- **Ctrl+F binding exists only in editor context:** src/vs/editor/browser/coreCommands.ts line 736: mac secondary for cursor right is WinCtrl|KeyF, gated on EditorContextKeys.textInputFocus — not matched when webview is focused, but the event is still consumed by the forwarding.
- **Ctrl+P binding exists only in editor/quickpick context:** src/vs/editor/browser/coreCommands.ts line 769 and src/vs/workbench/browser/actions/quickAccessActions.ts line 274: WinCtrl|KeyP is bound for cursor up (editor) and select-previous (quick pick) — neither matches in webview focus context.
- **no fix on main:** git log since 2025-06-01 on webviewElement.ts shows no related fix for Cocoa keybinding passthrough; the issue is present on current main.
- **reporter confirmation:** Comment 2 confirms Ctrl+A/E/B/N work fine in the same webview input — only Ctrl+F/P are swallowed, consistent with those specific keys being forwarded and consumed.
- **multiple extensions affected:** Claude Code, Cline, Continue, OpenCode all independently hit this — confirming it is a systemic webview-level issue, not extension-specific.
- **related issue:** https://github.com/microsoft/vscode/issues/241801 — same webview keyboard forwarding mechanism causes double-dispatch; different symptom but same root area.
