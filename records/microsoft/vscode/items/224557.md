# Issue #224557 — `when` condition set to `false` upon configuring keybinding

[https://github.com/microsoft/vscode/issues/224557](https://github.com/microsoft/vscode/issues/224557)

## Summary

The reported condition rewriting remains traceable in current source: reloading a customized binding folds its static context keys, and the editor displays—and can subsequently save—the folded expression instead of the original condition. Keep this open; the existing labels already identify the owning area.

## Change summary

Preserve the original when-clause expression when changing a shortcut through the Keyboard Shortcuts editor.

## Best solution

Keep authored conditions available for display and editing while retaining constant folding for runtime keybinding resolution. Changing Toggle Developer Tools to F12 should not replace its condition with the literal false or silently remove its development-only restriction.

- **Behavior:**

  > Changing only a shortcut must preserve its original when-clause expression in the Keyboard Shortcuts editor and in subsequent saves. In a normal installed window, rebinding Toggle Developer Tools to F12 must retain isDevelopment rather than displaying or persisting false. Reloading and editing the binding again must not destroy that expression. Runtime eligibility must remain unchanged: preserving the expression must not make a false condition active.
- **Trace:**

  > ToggleDevToolsAction registers IsDevelopmentContext, which WorkbenchContextKeysHandler registers as a startup constant. KeybindingIO.readUserKeybindingItem deserializes user conditions through ContextKeyExpr; ContextKeyDefinedExpr.create folds known constants immediately. KeybindingsEditorModel.toKeybindingEntry serializes that normalized expression, and KeybindingsEditor.defineKeybinding passes it to KeybindingsEditingService on a later edit. KeybindingResolver separately substitutes constants to suppress inactive runtime bindings, behavior that must remain intact. The source trace establishes the loss of expression provenance, but does not yet establish the complete consumer boundary for preserving it without changing shared context-expression semantics. The closed shortcut-hint issue https://github.com/microsoft/vscode/issues/174218 explains the intentional runtime restriction and is not a duplicate target.

- **Source-confirmed normalization:** KeybindingIO.readUserKeybindingItem in src/vs/workbench/services/keybinding/common/keybindingIO.ts deserializes the saved when string. ContextKeyDefinedExpr.create in src/vs/platform/contextkey/common/contextkey.ts replaces registered constants with boolean expressions; ContextKeyFalseExpr.serialize returns 'false'. Thus rereading an override with isDevelopment in an ordinary installed window loses the original expression in the parsed representation.
- **Display and subsequent persistence:** KeybindingsEditorModel.toKeybindingEntry in src/vs/workbench/services/preferences/browser/keybindingsEditorModel.ts:283 displays keybindingItem.when.serialize(). KeybindingsEditor.defineKeybinding passes that displayed condition into updateKeybinding, and KeybindingsEditingService writes it to keybindings.json. The initial edit can save the original expression; after reload, a subsequent edit can persist its folded 'false' representation.
- **Runtime boundary:** src/vs/platform/keybinding/common/keybindingResolver.ts separately calls substituteConstants and excludes false conditions from runtime lookup. Preserving editable source must not undo this intentional filtering or enable development-only shortcuts in ordinary windows.
