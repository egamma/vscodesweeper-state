# Issue #335819 — Delete is disabled for an automation with a running session without explanation

[https://github.com/microsoft/vscode/issues/335819](https://github.com/microsoft/vscode/issues/335819)

## Summary

Team-authored, real gap confirmed in source: the Delete context-menu action for an automation is disabled via a plain precondition with no tooltip/message explaining why, or how to proceed while a session is running. No fix exists on main, so this stays open; the reporter's own two proposed remedies (allow-with-confirm-stop vs. explain-and-block) are a genuine design choice for a maintainer.

## Change summary

Delete is silently disabled on an automation's overflow menu while one of its sessions is still running, with no explanation or path forward.

## Best solution

Either let Delete proceed with a confirmation that explains the running session will be stopped, or keep it blocked but surface why (tooltip/message) and point at stopping the run first — a maintainer should pick the direction before implementation.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/sessions/browser/views/automationsView.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/agentHostAutomationStore.ts`
- **Validation:** An automationsView test asserting the Delete action/menu item surfaces an explanatory tooltip or message (or, if the allow-with-stop design is chosen, that confirming delete while running stops the session and then deletes it).
- **Trace:**

  > Root cause traced to DeleteAutomationAction's plain ContextKeyExpr precondition in automationsView.ts, fed by canDeleteAutomation()/_operationAvailable(Remove) in agentHostAutomationStore.ts — there is no code path that attaches a reason string to the disabled menu item today. The boundary: do not change how running-session detection itself works, only how (or whether) deletion is gated and explained. Related: the reporter references issue #335507 in the title as a duplicate test of a related report.
- **Open decisions:**
  - Should Delete be allowed while a session is running, with a confirmation that stops the session first, or should it stay blocked with an explanation?
  - If it stays blocked, what UI mechanism explains it — context-menu tooltip (VS Code menu items often can't show custom tooltips when disabled), an inline card message, or a toast on click attempt?
  - If delete-with-stop is chosen, does stopping the session need its own confirmation step, or is one combined dialog sufficient?

## Evidence

- **disabled precondition, no explanation:** src/vs/sessions/contrib/sessions/browser/views/automationsView.ts: DeleteAutomationAction (id 'sessions.automations.delete') sets precondition ContextKeyExpr.and(ChatAutomationsEnabledContext, AutomationCardCanDeleteContext) with no title/tooltip variant for the disabled case.
- **root of the disabled state:** AutomationCardCanDeleteContext is set from automationService.canDeleteAutomation?.(automation.id), which in src/vs/sessions/contrib/providers/agentHost/browser/agentHostAutomationStore.ts calls this._operationAvailable(automationId, AutomationOperation.Remove) — this is what returns false while a run is active, and nothing surfaces that reason to the user.
- **precedent for explanatory disabled UI elsewhere:** The Run button in the same file (around line 572) does set an aria-label/tooltip ('Running') when disabled — the same pattern isn't applied to the Delete menu item.
