# Issue #332578 — Extension API: Support native dropdown / action menus on StatusBarItem

[https://github.com/microsoft/vscode/issues/332578](https://github.com/microsoft/vscode/issues/332578)

## Summary

This is a distinct API request for an anchored native action menu on a status bar item; the proposed rich-hover work offers related command surfaces but does not provide the requested menu interaction. Because it is in the Backlog Candidates community-voting period, it should remain open under discussion.

## Change summary

Allow extensions to attach a native dropdown or action menu to a StatusBarItem instead of opening a detached Quick Pick.

## Best solution

The API and workbench owners should decide whether status bar items may expose an anchored native menu, including the command contribution model, keyboard/accessibility behavior, and consistency with existing status bar interactions. If accepted, the design should avoid duplicating the proposed rich-hover API while preserving a clear distinction between menus and descriptive hovers.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostStatusBar.ts`, `src/vs/workbench/api/browser/mainThreadStatusBar.ts`, `src/vs/workbench/browser/parts/statusbar/statusbarPart.ts`
- **Validation:** Add extension API tests for menu registration, command dispatch, disposal, and updates, plus a workbench UI test confirming the action menu opens anchored to the status bar item and remains keyboard- and screen-reader-accessible.
- **Behavior:**

  > An extension can associate multiple actions with one status bar item and users can invoke them from a native menu anchored to that item. A status bar item with its existing single command must behave exactly as it does today. The menu must support keyboard navigation, accessible labels and focus handling, command enablement, extension-host updates, and disposal without leaving stale actions.
- **Trace:**

  > The current public StatusBarItem contract exposes a single command, while the extension-host and main-thread status bar bridge carries that item state into the workbench status bar implementation. The issue asks for a distinct anchored menu rather than the rich-hover command surfaces discussed in https://github.com/microsoft/vscode/issues/238297 and https://github.com/microsoft/vscode/issues/234339. The boundary is the status bar API and rendering path: existing command activation and hover behavior must not change. Uncertainty begins at the public API shape and at whether a new anchored-menu interaction is acceptable for status bar consistency and accessibility.
- **Open decisions:**
  - Should the public contract accept a declarative menu contribution identifier, an inline command list, or both?
  - Does clicking an item with both a command and a menu execute the command or open the menu, and how is the alternate action exposed?
  - Should the native menu be a persistent context-menu-style surface or a richer status-bar hover action surface?
