[https://github.com/microsoft/vscode/issues/184357](https://github.com/microsoft/vscode/issues/184357)

## Summary

Keep this accepted accessibility request open. Current main has an opt-in rich screen-reader rendering path that may satisfy the thread's formatting-exposure approach, but the inspected evidence does not establish that screen readers report token colors or provide the requested syntax-dependent speech.

## Change summary

Make syntax distinctions available nonvisually through screen-reader formatting attributes or syntax-dependent speech.

## Best solution

Evaluate the existing rich screen-reader content path against the Python/NVDA formatting example before designing another speech mechanism. Establish whether exposing token formatting is sufficient, and retain this issue for any remaining syntax-to-speech capability.

- **Likely files:** `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/browser/controller/editContext/native/screenReaderSupport.ts`, `src/vs/editor/browser/controller/editContext/native/screenReaderContentRich.ts`

Record whether formatting matches the visible syntax distinctions and whether configured NVDA prosody can distinguish them; also check typing, line reading, and caret navigation remain usable.
- **Behavior:**

  > Screen-reader users should be able to distinguish syntax categories that sighted users distinguish through highlighting. The thread accepts exposing formatting attributes as a possible route to user-configured speech prosody. Acceptance must demonstrate distinct formatting information at representative Python tokens, rather than merely successful reading of plain text. Whether that route completes the request or built-in voice switching is also required remains to be settled.
- **Trace:**

  > EditorOptions registers editor.renderRichScreenReaderContent as an opt-in option dependent on the EditContext path. ScreenReaderSupport selects RichScreenReaderContent, whose _renderLine uses the editor's tokenized line renderer to construct HTML for the focused screen-reader element. This establishes that rich rendering already exists, not that assistive technology exposes its colors or changes speech accordingly. The supporting reproduction is https://github.com/microsoft/vscode/issues/238803, already consolidated into this issue. Related rich-content testing is recorded at https://github.com/microsoft/vscode/issues/257834 and https://github.com/microsoft/vscode/issues/262321. Begin with that existing capability; preserve ordinary editing, selection, caret navigation, and the plain-content fallback, and do not treat unrelated navigation problems as this request.
- **Open decisions:**
  - If rich content exposes syntax formatting reliably and permits screen-reader-configured prosody, does that complete this request, or must VS Code also offer built-in syntax-dependent voice switching?
