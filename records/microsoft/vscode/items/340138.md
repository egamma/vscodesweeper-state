# Issue #340138 — Agent Host BYOK bridge drops provider configurationSchema and statusIcon from the model picker

[https://github.com/microsoft/vscode/issues/340138](https://github.com/microsoft/vscode/issues/340138)

## Summary

Traced the exact drop on current main: the BYOK bridge's wire contract and its renderer/node translation layers genuinely have no fields for the extension's configurationSchema (beyond a synthesized reasoningEffort), statusIcon, tooltip, detail, warningText, or infoText, so the Agent Host-bound picker entry really is built from an impoverished copy — the report is accurate even though the file path it cites doesn't exist in this checkout (the logic lives in a differently-organized but equivalent pipeline).

## Change summary

Extension-published configurationSchema submenus, statusIcon, tooltip, and detail disappear from the model picker once the composer binds to an Agent Host harness with BYOK models enabled.

## Best solution

Extend the IByokLmModelInfo wire contract (agentHostByokLm.ts) to carry the full configurationSchema plus statusIcon/tooltip/detail/warningText/infoText, populate them in AgentHostByokLmHandler.listModels(), and forward them through CopilotAgent._refreshByokModels() into the picker metadata — deciding how they coexist with the host's own notices/thinkingLevel synthesis.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/common/agentHostByokLm.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostByokLmHandler.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostLanguageModelProvider.ts`
- **Validation:** A test on AgentHostByokLmHandler.listModels() (or CopilotAgent._refreshByokModels()) asserting that a BYOK model's full configurationSchema, statusIcon, tooltip, detail, warningText, and infoText survive into the picker-facing metadata, without breaking the existing thinkingLevel/notices tests.
- **Behavior:**

  > When a BYOK extension's LanguageModelChatInformation includes a configurationSchema beyond reasoningEffort, or a statusIcon/tooltip/detail/warningText/infoText, those should still appear in the model picker once the composer is bound to an Agent Host harness. Today the bridged copy loses everything except a synthesized thinkingLevel property; nothing else survives. Acceptance: a BYOK model with a multi-property configurationSchema and a statusIcon shows that schema and icon in the Agent Host-bound picker, with no regression to the host's existing warning/notices icon or thinkingLevel synthesis for models that don't supply their own schema.
- **Trace:**

  > Root cause spans three layers, all confirmed by reading current main (no execution needed). (1) IByokLmModelInfo (src/vs/platform/agentHost/common/agentHostByokLm.ts, ~L149-175) has no fields for configurationSchema/statusIcon/tooltip/detail/warningText/infoText. (2) AgentHostByokLmHandler.listModels() (agentHostByokLmHandler.ts, ~L161-194) reads metadata.configurationSchema only to pull out the reasoningEffort enum, discarding the rest, and never reads metadata.statusIcon/tooltip/detail/warningText/infoText. (3) CopilotAgent._refreshByokModels() (copilotAgent.ts, ~L2517-2557) builds the picker-facing IAgentModelInfo solely from those fields, synthesizing only a thinkingLevel property via _createThinkingLevelConfigSchemaProperty. Downstream, AgentHostLanguageModelProvider._toLanguageModelConfigurationSchema already forwards an arbitrary schema generically, so nothing there needs to change. Boundary: do not touch the host's own notices/warning-icon computation (readAgentModelNoticesMeta) or the existing thinkingLevel synthesis for models with no extension schema.
- **Open decisions:**
  - When both the host's computed notices/warning icon and the extension's own statusIcon are present, which one should win in the picker row?
  - Should the extension's full configurationSchema replace the host-synthesized thinkingLevel property outright, or should the two be merged — and on a key collision, which side wins?
  - Should tooltip/detail/warningText/infoText pass through verbatim, or does the host still want to combine its own pricing-derived detail text (e.g. the Auto discount) with the extension's?

## Evidence

- **wire contract gap:** src/vs/platform/agentHost/common/agentHostByokLm.ts IByokLmModelInfo (~L149-175) has fields only for vendor/id/name/modelIdentifier/token limits/vision/reasoning-effort — no configurationSchema, statusIcon, tooltip, detail, warningText, or infoText.
- **renderer producer drops fields:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostByokLmHandler.ts listModels() (~L161-194) reads metadata.configurationSchema only to extract the reasoningEffort enum into supportedReasoningEfforts/defaultReasoningEffort; it never reads metadata.statusIcon/tooltip/detail/warningText/infoText and discards every other schema property.
- **node consumer confirms the loss:** src/vs/platform/agentHost/node/copilot/copilotAgent.ts _refreshByokModels() (~L2517-2557) builds the picker-facing IAgentModelInfo purely from those impoverished IByokLmModelInfo fields, synthesizing only a thinkingLevel configSchema property — there is no path left for the extension's own schema/icon/tooltip/detail to reach the picker.
- **downstream renderer is not the bottleneck:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostLanguageModelProvider.ts _toLanguageModelConfigurationSchema (~L236-268) forwards whatever configSchema it is given generically (not hardcoded to six keys as the issue's older snippet suggested) — the loss happens upstream of this file, in the BYOK bridge layers above.
