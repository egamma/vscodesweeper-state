# Issue #304147 — Integrated Source Code Management (SCM) - possibility of cancellation, especially during remote push with a huge 3.4 GB file (e.g., due to database export)

[https://github.com/microsoft/vscode/issues/304147](https://github.com/microsoft/vscode/issues/304147)

## Summary

Confirmed gap: VS Code's git extension already supports cancelling long Sync (fetch+pull) operations via the `git.supportCancellation` setting, but that mechanism is not wired up for a standalone Push — there's no way to cancel an in-flight push today, matching the report.

## Change summary

Add the ability to cancel an in-progress SCM push (e.g. for an accidental huge push), plus a progress indicator showing transferred data/file counts.

## Best solution

Extend the existing cancellable-operation infrastructure (used for Sync) to the plain Push path in repository.ts/git.ts, and consider surfacing git's own transfer progress (objects/bytes) in the push progress notification.

## Plan brief

- **Likely files:** `extensions/git/src/repository.ts`, `extensions/git/src/git.ts`, `extensions/git/package.json`, `extensions/git/package.nls.json`
- **Validation:** A test/manual check that invoking Push while `git.supportCancellation` (or a new push-specific setting) is enabled shows a cancellable progress notification, and cancelling it aborts the underlying git process without corrupting the local repository state.
- **Trace:**

  > Sync already demonstrates the pattern: repository.ts wraps fetch/pull in `window.withProgress({cancellable:true}, (_, token) => fn(token))` when `git.supportCancellation` is on, threading a `CancellationToken` into `fetchAll`. Plain push (`repository.push`/`_push`, and `GitAPI.push` in git.ts) has no such token parameter or progress wrapper. The open question is whether to reuse `git.supportCancellation` for push or add a dedicated setting, and whether git's own transfer stats (objects/bytes) can be parsed from push's stderr output to drive a richer progress UI — both are maintainer/product decisions, not implementation details.
- **Open decisions:**
  - Should push reuse the existing `git.supportCancellation` setting, or warrant a separate opt-in (given push cancellation may have different risk characteristics than fetch/pull cancellation)?
  - Should the progress UI parse git's push transfer output (objects/bytes) to show real progress, or just a generic spinner with a cancel button?

## Evidence

- **Sync supports cancellation:** extensions/git/src/repository.ts lines ~2560-2590: when `git.supportCancellation` is enabled, Sync wraps fetch/pull in `window.withProgress({cancellable: true}, (_, token) => fn(token))` and passes a CancellationToken through `fetchAll`/`pull`.
- **Push lacks the same wiring:** repository.ts line 2601 calls `this._push(remoteName, pushBranch, false, followTags)` with no CancellationToken, and `GitAPI.push` in git.ts (line 2565) takes no cancellationToken parameter at all — unlike `fetch` (line 2422) and `log` (line 1455) which do.
- **setting description:** extensions/git/package.nls.json line 281: `git.supportCancellation` is explicitly scoped to "running the Sync action" only, confirming push isn't covered by design today, not as an intentional omission documented elsewhere.
