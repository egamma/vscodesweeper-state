# Issue #335221 — Copilot local chat session disappears from Sessions after Windows restart despite intact JSONL and indexes

[https://github.com/microsoft/vscode/issues/335221](https://github.com/microsoft/vscode/issues/335221)

## Summary

Credible, well-documented bug in the newer Agent Sessions view: the reporter confirms the underlying JSONL, chat.ChatSessionStore.index entry, and agentSessions.model.cache entry all remain intact, yet the session vanishes from the UI and Reindex Sessions doesn't restore it — this looks like a reconciliation bug between the on-disk index and the in-memory/cached session list rather than data loss, but I can't pin the exact code path from source alone.

## Change summary

A local Copilot Chat session disappears from the Sessions view after a Windows restart (or even immediately after sending one message), even though its JSONL file, index entry, and cache entry are all present and non-empty.

## Best solution

Someone with a repro environment should trace why AgentSessionsModel/AgentSessionsCache (agentSessionsModel.ts) fails to surface a session that ChatSessionStore's index (chatSessionStore.ts) still lists as non-empty — likely a stale/partial cache reconciliation on cold start — and add a repro test around the reload path.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentSessionsModel.ts`
- **Validation:** A test that simulates a cold reload (fresh AgentSessionsModel/AgentSessionsCache instantiation) with a pre-existing non-empty ChatSessionStore index entry and asserts the session appears in the resulting session list.
- **Behavior:**

  > A local chat session whose JSONL transcript and ChatSessionStore index entry (isEmpty: false) still exist on disk must appear in the Sessions view after VS Code restarts (whether from a normal close or an unexpected Windows restart), and 'Reindex Sessions' must be able to recover it if it's ever missing. Acceptance: after a simulated cold start with valid persisted index/cache data, the session list includes the session.
- **Trace:**

  > AgentSessionsCache persists 'agentSessions.model.cache' and 'agentSessions.state.cache' at StorageScope.WORKSPACE (agentSessionsModel.ts ~1144-1237), separate from ChatSessionStore's own on-disk 'chat.ChatSessionStore.index' (chatSessionStore.ts ~39, ~490-608) which independently tracks isEmpty per session. The reporter's diagnostics show all three sources intact yet the UI omits the session — the defect is most likely in how these two independently-maintained stores are merged/rehydrated on startup, not in the underlying data. Where the uncertainty starts: I could not trace, without running the app, which merge/read call drops the entry (e.g., a stale in-memory cache overwriting a freshly-read index, or a provider hand-off race) — that diagnosis is the plan's first step. Do not change the persisted file formats or JSONL layout while investigating.
- **Open decisions:**
  - Is the cache-vs-index reconciliation supposed to always trust the on-disk index as source of truth, or does the in-memory cache need to be invalidated/merged differently on cold start? This determines whether the fix belongs in ChatSessionStore's index loader or in AgentSessionsCache's restore path.

## Evidence

- **storage keys involved:** agentSessionsModel.ts defines SESSIONS_STORAGE_KEY ('agentSessions.model.cache') and STATE_STORAGE_KEY ('agentSessions.state.cache') at StorageScope.WORKSPACE/StorageTarget.MACHINE (lines ~1144-1237); chatSessionStore.ts keeps a separate on-disk index under 'chat.ChatSessionStore.index' (line 39) with its own isEmpty/index-merge logic (lines ~490-608). The reporter shows all three data sources have the session, so the bug likely lives in how the model reconciles/rehydrates from these on window start, not in the persisted data itself.
