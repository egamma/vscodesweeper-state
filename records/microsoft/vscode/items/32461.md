# Issue #32461 — Cleanup ExtensionContext.workspaceState when a workspace no longer exists

[https://github.com/microsoft/vscode/issues/32461](https://github.com/microsoft/vscode/issues/32461)

## Summary

Keep open: current cleanup deliberately preserves named-workspace storage, so the maintainer-approved, user-confirmed cleanup capability remains missing. This team-authored request has 63 upvotes and an On Deck milestone; neither existing extension workarounds nor related folder-layout proposals establish a factual close.

## Change summary

Provide a safe way to identify and reclaim obsolete workspace state and extension storage without deleting data for temporarily unavailable workspaces.

## Best solution

Provide a user-controlled workspace-storage inspection and cleanup affordance that identifies large entries and requires explicit selection before deletion. Preserve storage for active workspaces and never equate an unavailable mount or remote location with a deleted workspace.

## Plan brief

- **Likely files:** `src/vs/code/electron-utility/sharedProcess/contrib/storageDataCleaner.ts`, `src/vs/platform/storage/electron-main/storageMain.ts`, `src/vs/platform/workspaces/node/workspaces.ts`, `src/vs/workbench/api/common/extHostStoragePaths.ts`, `src/vs/code/test/electron-utility/sharedProcess/contrib/storageDataCleaner.test.ts`
- **Validation:** The plan should end with an isolated-profile check containing an obsolete local workspace, an active workspace, and a temporarily unavailable mounted or remote workspace: inspect storage entries, cancel without changing data, explicitly select an eligible obsolete entry for cleanup, and verify unrelated and active storage remain intact. Preserve the existing UnusedWorkspaceStorageDataCleaner test expectations and add coverage for the chosen eligibility and confirmation contract.
- **Behavior:**

  > Users can identify workspace storage that consumes disk space and explicitly choose eligible entries to reclaim. A missing workspace path alone must never authorize deletion because mounts, VMs, and remote locations can be temporarily unavailable. Cancelling leaves all storage unchanged, and cleaning a selected entry preserves unrelated and active workspace data. The maintainer-approved direction is a user-confirmed inspection and cleanup affordance, not unconditional background deletion.
- **Trace:**

  > UnusedWorkspaceStorageDataCleaner.cleanUpStorage in src/vs/code/electron-utility/sharedProcess/contrib/storageDataCleaner.ts skips all 32-character identifiers before considering deletion. src/vs/platform/workspaces/node/workspaces.ts generates those identifiers for folder and configured workspaces, and the existing storageDataCleaner.test.ts explicitly preserves such entries. ExtensionStoragePaths in src/vs/workbench/api/common/extHostStoragePaths.ts places extension workspace directories under the workspace identifier; workspace metadata and database paths are handled in src/vs/platform/storage/electron-main/storageMain.ts. The author rejected path-existence-only deletion and endorsed a user-confirmed UI in https://github.com/microsoft/vscode/issues/32461#issuecomment-324727778 and https://github.com/microsoft/vscode/issues/32461#issuecomment-762098971. The trace establishes the existing cleanup boundary, not a completed design for inspecting or deleting named-workspace storage. Preserve existing empty-workspace cleanup, identifier stability, and temporarily unavailable workspace data; relocating storage into project directories is not required by the accepted direction.
- **Open decisions:**
  - Should cleanup remove an entire selected workspace-storage entry, including persisted workbench and extension state, or allow extension-owned storage to be reclaimed separately?
  - Should the initial affordance be explicitly invoked by the user, proactively suggest cleanup when storage is large, or support both?
