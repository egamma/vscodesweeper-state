# Issue #81520 — ctrl + click "go to definition" clashes with ctrl + click "follow link"

[https://github.com/microsoft/vscode/issues/81520](https://github.com/microsoft/vscode/issues/81520)

## Summary

The conflict remains in current source: document links and go-to-definition independently consume the same modifier-click, so both actions run when providers return overlapping results. This should remain open while the editor team chooses the single-action UX and coordination model.

## Change summary

A Ctrl/Cmd-click on text that is both a document link and a definition target opens the link and navigates to the definition.

## Best solution

Coordinate modifier-click handling across editor links and symbol navigation so an overlapping link and definition produce one intentional outcome, such as a defined precedence or a chooser, without changing either feature when it is the only available action.

- **Likely files:** `src/vs/editor/contrib/gotoSymbol/browser/link/clickLinkGesture.ts`, `src/vs/editor/contrib/gotoSymbol/browser/link/goToDefinitionAtPosition.ts`, `src/vs/editor/contrib/links/browser/links.ts`

- **Behavior:**

  > When text is simultaneously a document link and a definition target, one Ctrl/Cmd-click must not both open an external resource and navigate the editor. The product must produce one deliberate outcome according to the UX selected by the maintainer. Link-only and definition-only modifier-click behavior must remain unchanged, including side-by-side modifiers and platform-specific Ctrl/Cmd handling.
- **Trace:**

  > Current main has two independent consumers of ClickLinkGesture: LinkDetector in src/vs/editor/contrib/links/browser/links.ts and GotoDefinitionAtPositionEditorContribution in src/vs/editor/contrib/gotoSymbol/browser/link/goToDefinitionAtPosition.ts. ClickLinkGesture in src/vs/editor/contrib/gotoSymbol/browser/link/clickLinkGesture.ts listens directly to editor mouse events and has no shared consumption mechanism, so both onExecute listeners run for an overlapping range. Commit 65499e56dbb93a16dd173605118ab33065ea7e2b previously collected competing actions, but commit 88c8146de77e3632c3f909e5f5d7ce8fc4fc4c74 reverted it after regressions documented by https://github.com/microsoft/vscode/pull/169667. The boundary is modifier-click coordination: ordinary clicks, keyboard commands, provider contracts, link-only behavior, and definition-only behavior must not change. The uncertainty begins with the intended UX when both targets exist and the coordination mechanism that can provide it without recreating the reverted behavior.
- **Open decisions:**
  - When both targets exist, should VS Code prioritize the document link, prioritize the definition, or present a chooser?
  - Should arbitration live in a shared gesture/controller or in a narrower coordination point between the two existing editor contributions?

## Evidence

- **current source:** src/vs/editor/contrib/links/browser/links.ts constructs its own ClickLinkGesture and opens a matching LinkOccurrence from its onExecute listener, while src/vs/editor/contrib/gotoSymbol/browser/link/goToDefinitionAtPosition.ts constructs a separate ClickLinkGesture and invokes DefinitionAction from its own onExecute listener.
- **shared trigger:** src/vs/editor/contrib/gotoSymbol/browser/link/clickLinkGesture.ts registers each gesture directly on the editor mouse events and fires onExecute after the same modifier mouse-down/up sequence; it provides no consumption or arbitration mechanism between contributions.
- **failed prior approach:** Commit 65499e56dbb93a16dd173605118ab33065ea7e2b introduced a LinkOpener that collected competing actions, but it was fully reverted by 88c8146de77e3632c3f909e5f5d7ce8fc4fc4c74 via https://github.com/microsoft/vscode/pull/169667 after regressions, leaving the independent handlers on main.
- **confirmed scope:** The discussion contains independent examples from Python, Go/gopls, and Swift/SourceKit-LSP where a document link and definition legitimately overlap, confirming this is not limited to the original Jedi behavior.
