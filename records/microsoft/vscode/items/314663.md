# Issue #314663 — Copying symlink, then original file creates symlink

[https://github.com/microsoft/vscode/issues/314663](https://github.com/microsoft/vscode/issues/314663)

## Summary

Keep open: the report supplies sufficient steps to retest a regular-file copy incorrectly becoming a symlink after an earlier copy. Explorer paste handling has changed since the report, but the inspected changes do not establish a fix, and source inspection alone did not confirm the state-dependent failure.

## Change summary

Copying a symlink, deleting the pasted link, and then copying its original file to the same destination unexpectedly creates another symlink until the window is reloaded.

## Best solution

Reproduce the sequence through Explorer in a Windows-to-Linux remote workspace and identify where the selected source or destination state becomes stale. Copying a regular file should produce a regular file independently of earlier symlink operations, while preserving the existing behavior when the selected source actually is a symlink.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/fileActions.ts`, `src/vs/workbench/contrib/files/browser/explorerService.ts`, `src/vs/workbench/services/clipboard/electron-browser/clipboardService.ts`, `src/vs/platform/files/node/diskFileSystemProvider.ts`, `src/vs/base/node/pfs.ts`
- **Validation:** In a Windows client connected to a Linux SSH workspace, run the supplied setup, copy source/file into target using Explorer, delete target/file, then copy original/file into target without reloading. Check with lstat or test -L that the first result is a symlink and the second is a regular file; repeat after reloading as the control. Once the failing layer is identified, add a regression test for this exact sequence.
- **Behavior:**

  > Copying source/file, which is a symlink, into target preserves the link. After deleting that pasted link, copying original/file into target must create a regular file without requiring a window reload. Earlier copy operations must not determine the filesystem type of later copies. Acceptance checks distinguish the resulting filesystem entry type, not merely its Explorer icon or readable contents.
- **Trace:**

  > copyFileHandler in src/vs/workbench/contrib/files/browser/fileActions.ts passes the selected Explorer items to ExplorerService.setToCopy, which writes their resource URIs to the clipboard. NativeClipboardService serializes those URIs, and pasteFileHandler reads them to construct copy ResourceFileEdit entries. DiskFileSystemProvider.copy delegates to Promises.copy; pfs.ts creates a fresh payload and determines symlink status from the current source using lstat. These inspected paths establish the intended behavior but do not confirm where the earlier symlink copy affects the later operation. The first diagnostic step is to reproduce https://github.com/microsoft/vscode/issues/314663 and distinguish an actual on-disk symlink from stale Explorer presentation, then trace the selected source URI and destination deletion. Preserve genuine symlink-copy behavior and do not expand scope into cross-provider symbolic-link APIs tracked by https://github.com/microsoft/vscode/issues/71204.
