# Issue #158387 — Preserve remote kernel connection when using Continue Working On

[https://github.com/microsoft/vscode/issues/158387](https://github.com/microsoft/vscode/issues/158387)

## Summary

A real gap remains: Continue Working On can transfer user-targeted workspace state, but notebook controller bindings remain machine-local, and restoring the underlying authenticated remote connection still needs an extension-aware design.

## Change summary

Preserve and reconnect the selected remote notebook kernel when continuing a workspace in another VS Code environment.

## Best solution

Store portable notebook controller affinity as roamable workspace state using stable controller/server identifiers, then let the providing extension reconnect and handle authentication without transferring credentials through core.

## Evidence

- **current source gap:** src/vs/workbench/contrib/notebook/browser/services/notebookKernelServiceImpl.ts restores `notebook.controller2NotebookBindings` from workspace storage but persists it with `StorageTarget.MACHINE`, so it is not portable between Continue Working On environments.
- **available infrastructure:** src/vs/workbench/contrib/editSessions/common/workspaceStateSync.ts synchronizes only `StorageScope.WORKSPACE` keys targeted at `StorageTarget.USER`; this provides infrastructure that notebook controller affinity has not adopted.
- **related implementation:** https://github.com/microsoft/vscode/pull/179326 introduced a generic edit-session payload contribution model in commit cf7757f85df7443d839fe0c0fd0557dcc5720406, but did not add notebook or remote-kernel adoption.
- **ownership boundary:** https://github.com/microsoft/vscode/issues/158387#issuecomment-1218343775 explains that core remembers controller selection while the Jupyter or third-party provider owns connection lifecycle and authentication, so completing the request requires coordinated portable identity and reconnection behavior.
