# Issue #158387 — Preserve remote kernel connection when using Continue Working On

[https://github.com/microsoft/vscode/issues/158387](https://github.com/microsoft/vscode/issues/158387)

## Summary

Keep open: Cloud Changes can carry kernel-history identifiers, but that does not establish reconnection to the same running remote kernel or authorization at the destination. The linked merged PRs provide state-transfer infrastructure, not the complete requested behavior.

## Change summary

Preserve access to the same running remote notebook kernel across Continue Working On transitions, ideally without repeated authorization.

## Best solution

Define a supported handoff contract between Cloud Changes and notebook connection providers that lets a reachable remote kernel retain its execution state across workspace transitions. Settle the authorization and consent boundary with the notebook and authentication owners before implementing provider-specific support.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/editSessions/common/workspaceStateSync.ts`, `src/vs/workbench/contrib/editSessions/browser/editSessions.contribution.ts`, `src/vs/workbench/contrib/notebook/browser/services/notebookKernelServiceImpl.ts`, `src/vs/workbench/contrib/notebook/browser/services/notebookKernelHistoryServiceImpl.ts`
- **Validation:** Use a remote Jupyter server reachable from both environments, execute a cell that defines a variable, then Continue Working On in the destination and read that variable without rerunning its definition. Confirm the same running kernel is used, observe authorization prompts against the agreed consent contract, and verify that an unreachable server does not silently substitute a new kernel.
- **Behavior:**

  > Continue Working On should allow a notebook to resume against the same reachable running remote kernel, preserving its execution state rather than merely offering a similarly named controller. The report also requests avoiding repeated authorization across VS Code installations, but the supported authorization contract remains undecided. Acceptance should include a variable created before the transition remaining available afterward, plus explicit checks of destination authentication and unavailable-server behavior.
- **Trace:**

  > WorkspaceStateSynchroniser in src/vs/workbench/contrib/editSessions/common/workspaceStateSync.ts transfers USER-target workspace storage. NotebookKernelHistoryService stores controller IDs in that category, while NotebookKernelService stores per-notebook bindings as MACHINE-target state and only auto-binds registered controllers. This provides partial state roaming but does not establish provider connection discovery, authorization, or attachment to a running remote kernel. The inspected diffs of https://github.com/microsoft/vscode/pull/179326 and https://github.com/microsoft/vscode/pull/179479 supply generic contribution infrastructure, not that connection behavior. The discussion at https://github.com/microsoft/vscode/issues/158387#issuecomment-1218343775 places connection lifecycle and authentication with Jupyter or its server providers; their current implementation was not inspected in this checkout. Preserve existing Cloud Changes file-transfer behavior and distinguish kernel-session continuity from controller-history restoration.
- **Open decisions:**
  - Should the initial supported handoff cover only independently reachable unauthenticated servers, or also authenticated and third-party-provider connections?
  - Does signing into VS Code at the destination authorize reuse of a provider's remote-kernel access, or must the destination obtain separate provider consent?

## Evidence

- **Connection ownership:** https://github.com/microsoft/vscode/issues/158387#issuecomment-1218343775 explains that Jupyter connections can use token-bearing server URLs or third-party authentication providers; remembering a controller does not manage its connection lifecycle or authentication.
- **Unsettled authorization contract:** https://github.com/microsoft/vscode/issues/158387#issuecomment-1218282183 asks how remote kernels authenticate. The requested equivalence between signing into VS Code and authorizing an extension in another installation is not settled in the discussion.
- **Existing capability is partial:** src/vs/workbench/contrib/editSessions/common/workspaceStateSync.ts transfers WORKSPACE storage marked StorageTarget.USER. NotebookKernelHistoryService in src/vs/workbench/contrib/notebook/browser/services/notebookKernelHistoryServiceImpl.ts stores notebook.kernelHistory there, but serializes only controller IDs and resolves them against kernels already registered at the destination; it does not serialize a remote server connection or running kernel session.
- **Notebook binding boundary:** src/vs/workbench/contrib/notebook/browser/services/notebookKernelServiceImpl.ts stores notebook.controller2NotebookBindings with StorageTarget.MACHINE. Its _tryAutoBindNotebook requires an existing registered matching kernel, so restoring identifiers alone does not establish the requested remote connection.
- **Settings check:** The configuration registrations in src/vs/workbench/contrib/editSessions/browser/editSessions.contribution.ts expose workbench.experimental.cloudChanges.autoStore, workbench.cloudChanges.autoResume, workbench.cloudChanges.continueOn, and partial matching. None supplies remote-kernel reconnection or cross-installation provider authorization.
- **Merged work is infrastructure:** https://github.com/microsoft/vscode/pull/179326 references this issue and adds generic getStateToStore/resumeState contribution hooks. https://github.com/microsoft/vscode/pull/179479 defers invoking those hooks until changes are applied. Their inspected diffs contain no remote-kernel connection or authorization implementation, so neither establishes completion.

It is newer than this report and does not establish preservation of an authenticated running kernel; it cannot be the duplicate target under the re-review rules.
