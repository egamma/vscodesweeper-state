# Issue #285951 — GitHub Copilot frequently stalls at "Working" after editing previous prompt

[https://github.com/microsoft/vscode/issues/285951](https://github.com/microsoft/vscode/issues/285951)

## Summary

This remains a credible performance bug in the edit-and-resubmit path for large or active chat sessions. A merged optimization addressed measurable edit-mode rendering overhead, but there is no evidence that it resolved the reported multi-minute "Working" stall.

## Change summary

Editing and resubmitting an earlier prompt can leave Copilot at "Working" for minutes, particularly in very large conversations or while a request is active.

## Best solution

Reproduce with a synthetic large conversation while editing an in-progress request, profile the interval from resubmission through request dispatch, and remove or bound the blocking work in the chat widget, model, or request-cancellation path.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts`, `src/vs/workbench/contrib/chat/common/model/chatModel.ts`, `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts`
- **Validation:** Create or load a synthetic chat history comparable to the reported 100,000-plus-line export, start a request, edit and resubmit that request, and verify through timestamps or a focused performance test that dispatch begins promptly and the UI does not remain at "Working" beyond the bounded cancellation interval.
- **Behavior:**

  > Editing and resubmitting an earlier prompt in a very large chat must start the replacement request promptly rather than remaining at "Working" for minutes. This must also hold when the edited prompt's original request is still active. Normal submission, cancellation, checkpoint truncation, and shorter-session behavior must remain unchanged.
- **Trace:**

  > The edit flow begins in ChatWidget.clickedRequest in src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts, which calls ChatModel.setCheckpoint and reconstructs the selected request's input and attachments. Resubmission runs through ChatWidget.acceptInput, awaits IChatService.cancelCurrentRequestForSession for a sent request, tears down editing state, removes checkpointed requests, and dispatches through sendRequest. ChatService.cancelCurrentRequestForSession in src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts now limits its response-completion wait to one second, while commit 86db4eb05dbfd82dc9b4ea022883494257ac3d63 removed an unrelated full-response rerender identified in https://github.com/microsoft/vscode/issues/286660. That optimization explains measurable edit-mode overhead but not the reported multi-minute asynchronous stall, so profiling must identify where progress stops after resubmission. Keep the scope to edit/resubmit behavior; the renderer-wide persistence freeze tracked by https://github.com/microsoft/vscode/issues/285251 and the terminal confirmation loop referenced as https://github.com/microsoft/vscode/issues/297714 are separate.

## Evidence

- **confirmed reproduction:** The reporter states the stall occurred on every edit in a conversation whose Markdown export exceeded 120,000 lines; another user independently reproduced intermittent "Working" stalls after editing an in-progress prompt on VS Code 1.109.0-insider for macOS.
- **distinct from persistence freeze:** A maintainer concluded that https://github.com/microsoft/vscode/issues/285251 was likely a different issue: its renderer freeze happened during the longer wait but did not explain the full multi-minute stall.
- **partial optimization:** https://github.com/microsoft/vscode/pull/286944 and commit 86db4eb05dbfd82dc9b4ea022883494257ac3d63 removed unnecessary response rerendering and code-block model updates when entering edit mode for https://github.com/microsoft/vscode/issues/286660. That investigation measured hundreds of milliseconds of synchronous work, not the multi-minute asynchronous stall reported here, and this issue remained open.
- **current source path:** On current main, ChatWidget.clickedRequest in src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts checkpoints the selected request and prepares its context; ChatWidget.acceptInput then awaits cancelCurrentRequestForSession, removes checkpointed requests, and calls sendRequest. src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts bounds response-completion waiting during cancellation to one second, so the remaining multi-minute delay is not conclusively explained by that wait alone.
- **no canonical duplicate:** The older open https://github.com/microsoft/vscode/issues/253126 tracks "Sorry, no response was returned" failures rather than the same edit-triggered, pre-response "Working" stall, so it does not meet the stronger duplicate bar for this re-reviewed issue.
