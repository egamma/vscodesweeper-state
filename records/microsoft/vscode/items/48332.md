# Issue #48332 — end keyword matching for Ruby, Lua, Julia, Elixir, Crystal and others

[https://github.com/microsoft/vscode/issues/48332](https://github.com/microsoft/vscode/issues/48332)

## Summary

Keep open: current bracket configuration supports simple keyword pairs, but does not fully deliver matchit-style matching across block openers, intermediate clauses, and end keywords. The request has 39 upvotes and maintainer interest; no verified older open canonical owns the same work.

## Change summary

Provide matching and navigation between block keywords in Ruby, Lua, Julia, Elixir, Crystal, and similar languages.

## Best solution

Define how language-aware block matching should integrate with the existing bracket highlighting and navigation commands, including intermediate clauses and context-sensitive keywords. Preserve simple configurable keyword pairs while deciding whether richer matching belongs in language configuration or a language-provided capability.

## Plan brief

- **Likely files:** `src/vs/editor/common/languages/languageConfiguration.ts`, `src/vs/editor/common/languages/supports/languageBracketsConfiguration.ts`, `src/vs/editor/common/model/bracketPairsTextModelPart/bracketPairsTree/parser.ts`, `src/vs/editor/contrib/bracketMatching/browser/bracketMatching.ts`, `extensions/ruby/language-configuration.json`, `extensions/lua/language-configuration.json`
- **Validation:** Establish acceptance fixtures for nested Ruby and Lua blocks, shared end closers, intermediate else/elsif/elseif clauses, and keyword text in comments and strings. Verify highlighting and editor.action.jumpToBracket against those fixtures; extend the bracket-pair model tests under src/vs/editor/test/common/model/bracketPairColorizer and confirm existing punctuation-pair behavior remains unchanged.
- **Behavior:**

  > Users should be able to identify and navigate matching block keywords in languages that use end rather than punctuation to delimit blocks. Nested blocks and different opening keywords sharing end must resolve to the correct block. Intermediate clauses must have explicitly defined matching/navigation behavior, and keyword text outside actual block syntax must not create false matches. Existing punctuation bracket matching must remain unchanged.
- **Trace:**

  > Built-in Ruby and Lua language configurations currently omit keyword brackets, although their indentation rules recognize block syntax. LanguageBracketsConfiguration supports literal opening/closing pairs and shared closing tokens; the bracket-pair Parser builds binary pairs without a clause-chain concept. BracketMatchingController.jumpToBracket consumes that model rather than language-semantic block information. Existing editor.language.brackets and editor.language.colorizedBracketPairs therefore provide simple keyword-pair configuration, not complete language-aware matching. Elixir-specific progress documented at https://github.com/elixir-lsp/vscode-elixir-ls/issues/46#issuecomment-1900362555 shows that grammar scopes can address some context exclusions, but does not settle the cross-language contract. The uncertainty begins at the intended behavior for intermediate clauses and the public mechanism through which language extensions supply richer matching; preserve existing pair configuration, punctuation navigation, and editor performance.
- **Open decisions:**
  - Should navigation cycle through intermediate clauses such as if/elsif/else/end, or match only a block's opening and closing keywords while highlighting intermediate clauses?
  - Should richer block matching be expressible through declarative language configuration, or require a language-provided capability for context-sensitive constructs?
