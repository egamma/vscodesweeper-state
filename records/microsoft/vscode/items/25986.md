# Issue #25986 — [theming] Separate workbench theme and syntax theme

[https://github.com/microsoft/vscode/issues/25986](https://github.com/microsoft/vscode/issues/25986)

## Summary

This remains a well-supported feature request: current customization settings and extension workarounds can approximate the result, but VS Code still lacks a built-in way to independently select workbench and syntax themes. With 194 upvotes and a Backlog milestone, it should remain open.

## Change summary

Allow users to select one color theme for the workbench UI and another for editor syntax highlighting.

## Best solution

Add a first-class syntax-theme selection that composes token colors and semantic token colors from one installed theme with workbench colors from another, while defining compatibility behavior for existing combined themes.

## Plan brief

- **Likely files:** `src/vs/workbench/services/themes/common/colorThemeData.ts`, `src/vs/workbench/services/themes/common/workbenchThemeService.ts`, `src/vs/workbench/contrib/themes/browser/themes.contribution.ts`, `src/vs/editor/common/services/getSemanticTokens.ts`
- **Validation:** Add theme-service tests that select distinct UI and syntax themes and assert that workbench colors remain from the UI theme while TextMate and semantic token colors come from the syntax theme, including reload persistence and fallback behavior.
- **Behavior:**

  > Users can independently choose an installed workbench theme and an installed syntax theme. Changing the syntax theme updates TextMate and semantic token highlighting without replacing sidebar, tab, status bar, or other workbench colors; changing the workbench theme preserves the selected syntax theme. The selections survive reload, and existing users who do not opt into separation retain today's combined-theme behavior.
- **Trace:**

  > The issue's workarounds show that VS Code already exposes separate override settings for workbench colors, TextMate rules, and semantic token rules, but there is no first-class selector that composes these portions from two installed themes. The relevant boundary is the workbench theme service and color-theme contribution flow, with editor semantic-token resolution participating in the resulting syntax colors. Existing combined color themes and their default behavior must remain compatible. Newer reports including https://github.com/microsoft/vscode/issues/210211 and https://github.com/microsoft/vscode/issues/247957 point back to this issue, making this the canonical design discussion rather than a duplicate candidate.
- **Open decisions:**
  - Does the syntax-theme selection supply only TextMate and semantic token colors, or also editor-scoped colors such as editor.background, selection, cursor, and bracket colors?
  - When a selected syntax theme omits semantic-token rules or disables semantic highlighting, should VS Code preserve that theme's semantic-highlighting policy or fall back to the active workbench theme?
  - Should the independent syntax-theme choice be persisted globally, per workspace, or with the same configuration scopes as the existing color-theme setting?
