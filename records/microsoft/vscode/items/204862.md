# Issue #204862 — `window.titleBarStyle` should be `native` by default for SR users

[https://github.com/microsoft/vscode/issues/204862](https://github.com/microsoft/vscode/issues/204862)

## Summary

This team-authored accessibility request remains unimplemented on current main and has no verified canonical duplicate. The startup behavior needs design work because title-bar style is selected before the renderer accessibility service is available.

## Change summary

Use the native title bar by default for screen-reader users while preserving explicit title-bar preferences.

## Best solution

Define a stable startup rule that selects the native title bar for screen-reader users, respects explicit `window.titleBarStyle` choices, and avoids unexpectedly changing window chrome between launches.

## Plan brief

- **Likely files:** `src/vs/workbench/electron-browser/desktop.contribution.ts`, `src/vs/platform/window/common/window.ts`, `src/vs/platform/windows/electron-main/windows.ts`, `src/vs/platform/windows/test/electron-main/windowImpl.test.ts`
- **Validation:** Add startup-focused tests covering explicit native/custom preferences and the chosen screen-reader default, then manually launch on Windows with accessibility detection enabled and disabled to confirm the first window uses the expected title bar without changing explicit user settings.
- **Behavior:**

  > When screen-reader support is active and the user has not explicitly chosen a title-bar style, VS Code should use the agreed accessible title-bar default from the first applicable launch. Explicit `window.titleBarStyle` choices must remain authoritative. Non-screen-reader users must retain the existing default unless maintainers deliberately choose otherwise, and startup behavior must not oscillate unexpectedly between launches.
- **Trace:**

  > The setting is registered with an unconditional `custom` default in src/vs/workbench/electron-browser/desktop.contribution.ts, and getTitleBarStyle in src/vs/platform/window/common/window.ts also falls back to custom. BrowserWindow options are selected in src/vs/platform/windows/electron-main/windows.ts before renderer services exist. Electron's accessibility state is available in the main process and is later copied into the renderer window configuration by src/vs/platform/windows/electron-main/windowsMainService.ts; renderer-side NativeAccessibilityService additionally interprets `editor.accessibilitySupport`. The boundary is title-bar default selection: do not override an explicit title-bar preference or broadly change title-bar behavior for users outside the agreed accessibility/platform scope.
- **Open decisions:**
  - Should the conditional default apply only on Windows, where the reported accelerator-key advantage was confirmed, or on every desktop platform?
  - When Electron detection and an explicit `editor.accessibilitySupport` value disagree, which signal determines the startup title-bar default?
  - If screen-reader detection becomes available only after an earlier launch, should the next launch change the title-bar style automatically or preserve the previously observed default?

## Evidence

- **current default:** src/vs/workbench/electron-browser/desktop.contribution.ts registers `window.titleBarStyle` with the unconditional default `custom`; src/vs/platform/window/common/window.ts#getTitleBarStyle also falls back to `TitlebarStyle.CUSTOM`.
- **startup path:** src/vs/platform/windows/electron-main/windows.ts chooses whether to hide the native title bar while constructing the BrowserWindow, before the renderer-side accessibility service can participate.
- **available detection:** src/vs/platform/windows/electron-main/windowsMainService.ts passes Electron's `app.accessibilitySupportEnabled` into the window configuration, while src/vs/workbench/services/accessibility/electron-browser/accessibilityService.ts combines that signal with `editor.accessibilitySupport` after renderer startup.
- **user evidence:** https://github.com/microsoft/vscode/issues/204862#issuecomment-1940350319 reports that the Windows native context menu exposes accelerator keys that the Electron/custom title-bar context menu does not.
- **canonical search:** Searches for native title-bar and screen-reader accessibility issues found related title-bar reports but no older open issue with the same observable request.
