# Issue #336710 — I archived a chat and then renamed it. The rename didn't work. And, when I closed and reopened the window the chat disappeared

[https://github.com/microsoft/vscode/issues/336710](https://github.com/microsoft/vscode/issues/336710)

## Summary

Fresh report (1 day, no comments) but source tracing turns up a real gap: `ChatSessionStore.setSessionTitle` mutates the in-memory index cache but never calls `flushIndex()`, so a rename can be lost unless a subsequent `saveState()` happens to flush the whole cache while the session is still 'live' in memory — plausible if the archived session's model was unloaded by rename time, matching both symptoms in the report.

## Change summary

Renaming a chat after archiving it silently fails, and after a window reload the chat is gone entirely.

## Best solution

Confirm the exact scenario (is the ChatModel still resident in `_sessionModels` when renaming an archived session?), then make `ChatSessionStore.setSessionTitle` durably persist the index itself instead of relying on a later `saveState()` to flush it incidentally.

- **Behavior:**

  > Renaming an archived chat session should update its title immediately in the UI and keep that title (and the session itself) after the window is closed and reopened. Currently the rename appears to silently fail, and on reload the session is gone. Acceptance: after archive → rename → reload, the session exists with the new title.
- **Trace:**

  > ChatSessionStore.setSessionTitle (src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts:510) mutates the cached index in memory but never calls the private flushIndex() (contrast with deleteSession/clearAllSessions/migrate, which do). chatServiceImpl.setChatSessionTitle (src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:448) calls saveState() right after, which does flush via updateAndFlushIndexSync, but that method only refreshes index entries for sessions still in _sessionModels (chatServiceImpl.ts:389-401) — an archived session whose ChatModel isn't resident wouldn't get its metadata refreshed there, though the mutated title should still ride along in the same cached index object being flushed. The uncertainty starts at whether/why the entry is dropped entirely (not just untitled) after reload — that needs a live repro to pin down (e.g. trimEntries() at chatSessionStore.ts:438 evicting old entries, or a separate per-window store instance never having loaded this session's entry into its cache before saveState() overwrote it). Do not change the archived-state storage in agentSessionsModel.ts (sessionStates ResourceMap) without first confirming it isn't the actual culprit.
- **Open decisions:**
  - Does the disappearance reproduce reliably, and does it require the archived session's ChatModel to have been unloaded from _sessionModels before renaming?
  - Should ChatSessionStore.setSessionTitle flush the index itself (bounded, cheap fix) regardless of the saveState() interaction?
  - Is the session actually removed from the persisted index, or just no longer discoverable due to a separate archived-state (sessionStates) resource-key mismatch?

## Evidence

- **missing flush:** src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts:510-517 `setSessionTitle()` mutates `index.entries[sessionId].title` in the cached index object but, unlike `deleteSession`/`clearAllSessions`/`migrate`, never calls `this.flushIndex()` to persist to `storageService`.
- **existing test gap:** src/vs/workbench/contrib/chat/test/common/model/chatSessionStore.test.ts:266-275 only asserts against `store.getIndex()`, which reads the same in-memory cache (`internalGetIndex()` at line 548-551) rather than a freshly-loaded store — so it would pass even without a flush, masking the persistence bug.
- **mitigating path:** chatServiceImpl.ts:448-460 `setChatSessionTitle` calls `this.saveState()` right after, which does flush the whole index via `updateAndFlushIndexSync` (chatSessionStore.ts:759-773) — but only refreshes entries for sessions still present in `_sessionModels`, so this only rescues the rename if the ChatModel is still resident; an archived session's model dropping out of memory would explain both 'rename didn't stick' and it 'disappearing' after reload.
- **recent code:** chatServiceImpl.ts and chatSessionStore.ts were both last touched by commit d3c24c3c (2026-09-19), part of the same active agent-sessions/archive feature work; no fix for this specific gap exists on main yet.
