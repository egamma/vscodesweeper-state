# Issue #194117 — Cannot undo file deletions from a WorkspaceEdit

[https://github.com/microsoft/vscode/issues/194117](https://github.com/microsoft/vscode/issues/194117)

## Summary

The undo-routing gap remains in current source: WorkspaceEdit deletions register an inverse operation, but ordinary Undo cannot reach it without an editor for the affected resource. Keep this open; the maintainer confirmed the defect, and no verified fix or matching older canonical was found.

## Change summary

Allow users to undo file deletions applied through WorkspaceEdit without needing an open editor for the deleted file.

## Best solution

Make extension-applied file operations reachable through a defined workbench undo interaction, preserving text-editor undo and Explorer operation ordering. Establish which operation Undo should target when an unrelated editor is active before changing the shared command routing.

Repeat with an unrelated edited text document active and with Explorer focused, asserting the agreed precedence and preserving existing editor and Explorer undo behavior.
- **Behavior:**

  > A successful WorkspaceEdit deletion of an ordinary small file must have a discoverable undo interaction that restores its contents without requiring an editor for the deleted resource. Redo must reapply the deletion. Acceptance must cover no open editor, an unrelated editor with pending text changes, and Explorer focus; existing editor and Explorer undo behavior must remain predictable.
- **Trace:**

  > MainThreadBulkEdits.$tryApplyWorkspaceEdit invokes the bulk-edit service without an undo source, whereas ExplorerService.applyBulkEdit supplies its dedicated UNDO_REDO_SOURCE. BulkFileEdits already records an inverse CreateOperation for ordinary deletions. The Explorer Undo implementation selects only its own source, while EditorOrNativeTextInputCommand falls back to an active editor and Undo invokes that model's undo stack; with no editor, the API deletion has no reachable command handler. This source trace agrees with the maintainer's confirmed reproduction at https://github.com/microsoft/vscode/issues/194117. The unresolved boundary is the user-visible selection and precedence of workspace-file undo relative to unrelated editor history, not how to reconstruct deleted contents. Preserve native text-input undo, existing text-edit grouping, and Explorer ordering; recursive-directory restoration and overwrite restoration are separate concerns.
- **Open decisions:**
  - When an extension-applied file operation is pending and an unrelated text editor has undoable changes, should ordinary Undo target the editor or the workspace-file operation, or should workspace-file undo use a separate explicit command?
