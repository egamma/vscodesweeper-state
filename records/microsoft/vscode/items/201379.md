# Issue #201379 — [Feature Request] Distinguish between build vs language service diagnostics

[https://github.com/microsoft/vscode/issues/201379](https://github.com/microsoft/vscode/issues/201379)

## Summary

Keep open: current diagnostic decorations do not visually distinguish build results from language-service results. The older builder/reconciler proposal addresses provenance and diagnostic lifecycle, but does not explicitly cover this request's distinct squiggle presentation.

## Change summary

Provide distinguishable squiggle colors or styles for build diagnostics versus language-service diagnostics.

## Best solution

Define a shared diagnostic-provenance contract that problem matchers and extension diagnostic collections can express, then provide consistent, accessible visual differentiation without conflating provenance with severity. Coordinate with https://github.com/microsoft/vscode/issues/74524 while retaining this issue's presentation requirement.

- **Reason:** Making diagnostic origins understandable improves the developer inner loop and supports uniform editor interactions across diagnostic producers.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/platform/markers/common/markers.ts`, `src/vs/editor/common/services/markerDecorationsService.ts`, `src/vs/platform/theme/common/colors/editorColors.ts`
- **Validation:** After the product contract is agreed, add marker-decoration tests showing distinguishable output for otherwise identical build and language-service errors and warnings, with unchanged legacy diagnostics. Manually compare a task problem-matcher diagnostic and an extension DiagnosticCollection diagnostic in the same file under light, dark, and high-contrast themes.
- **Behavior:**

  > Users should be able to distinguish build-produced diagnostics from language-service diagnostics directly in the editor, including when both have the same severity. The distinction must not imply that a build refreshes language-service diagnostics. Acceptance should compare build and language-service errors and warnings, verify an accessible distinction, and preserve existing behavior for diagnostics without provenance metadata.
- **Trace:**

  > The public DiagnosticSeverity and DiagnosticTag enums in src/vscode-dts/vscode.d.ts contain no build/reconciler classification; Diagnostic.source is only a human-readable producer description. Internal IMarkerData and IMarker in src/vs/platform/markers/common/markers.ts retain severity, source, owner-related identity, and existing tags, but no standardized builder/reconciler category. _createDecorationOption in src/vs/editor/common/services/markerDecorationsService.ts chooses squiggle classes by severity and only recognizes unnecessary/deprecated tags. Theme colors in src/vs/platform/theme/common/colors/editorColors.ts are severity-wide. https://github.com/microsoft/vscode/issues/201379#issuecomment-1880564648 suggests tags; https://github.com/microsoft/vscode/issues/74524 discusses tags versus explicit creator metadata for lifecycle handling. The uncertainty starts at the public provenance and presentation contract, not at whether the current squiggle path already supplies this distinction. Preserve severity meaning and existing diagnostic lifecycle behavior; automatic deduplication or replacement of diagnostics is outside this presentation request unless separately approved.
- **Open decisions:**
  - What provenance contract should diagnostic producers expose, and which build results belong in that category, including full-project builds performed by a language server?
  - Should the distinction be enabled by default, and should it use separate theme colors, non-color squiggle styles, or both?
  - How should diagnostics without explicit provenance be presented to preserve compatibility without incorrectly classifying their origin?
