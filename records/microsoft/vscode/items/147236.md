# Issue #147236 — Bad symlinks  display

[https://github.com/microsoft/vscode/issues/147236](https://github.com/microsoft/vscode/issues/147236)

## Summary

This remains the canonical open bug: current source can retain a cached Explorer symlink decoration after the underlying model refreshes, and maintainers confirmed the same symptom in several newer reports through 2026.

## Change summary

Replacing a symbolic-link folder with a regular folder at the same path leaves the Explorer's symlink badge visible, even after an explicit refresh.

## Best solution

Invalidate and recompute Explorer decorations whenever refreshed file metadata can change a resource's symlink status, while preserving the existing Explorer item and decorations caches for unaffected resources.

- **Behavior:**

  > When a symbolic link is replaced by a regular folder at the same path, refreshing Explorer must remove the symlink badge without restarting VS Code. Replacing a regular folder with a symbolic link must add the badge. Unchanged resources and their decorations must remain unaffected, on both case-sensitive and case-insensitive file systems.
- **Trace:**

  > ExplorerItem.mergeLocalWithDisk in src/vs/workbench/contrib/files/common/explorerModel.ts copies the newly resolved `isSymbolicLink` value, and ExplorerService.refresh in src/vs/workbench/contrib/files/browser/explorerService.ts discards and reloads children. The badge comes from ExplorerDecorationsProvider in src/vs/workbench/contrib/files/browser/views/explorerDecorationsProvider.ts, whose change emitter currently covers workspace-root changes and root errors but not refreshed file metadata. DecorationsService caches provider results by resource and invalidates them through the provider's change event, so reusing the same URI leaves the former badge visible. Newer exact reproductions are https://github.com/microsoft/vscode/issues/233659, https://github.com/microsoft/vscode/issues/259209, https://github.com/microsoft/vscode/issues/262663, and https://github.com/microsoft/vscode/issues/305081. Keep the boundary to Explorer-owned decoration invalidation; do not alter general file watching, SCM decorations, or symlink traversal behavior.
