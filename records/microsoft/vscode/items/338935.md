# Issue #338935 — Inbuilt Browser not picking local system directories 

[https://github.com/microsoft/vscode/issues/338935](https://github.com/microsoft/vscode/issues/338935)

## Summary

Traced to a real defect: the integrated browser's address-bar classifier and its URL-loading normalization disagree about local file paths, so pasting an absolute path (Windows drive-letter or POSIX) doesn't reliably navigate to the file even though it should — the maintainer's `file://` workaround in the thread confirms the gap.

## Change summary

Pasting a local absolute file path (e.g. `C:\Users\...\index.html`) into the integrated browser's address bar doesn't open the file; it's treated as a web search instead.

## Best solution

Treat recognizable absolute local paths (Windows drive-letter and POSIX) as navigable URLs in resolveAddressBarInputType (src/vs/workbench/contrib/browserView/common/browserSearch.ts), and fix BrowserViewModel.loadURL's scheme-detection (src/vs/workbench/contrib/browserView/common/browserView.ts ~line 785) to convert such paths to a proper `file://` URI instead of blindly prepending `http://` when `URL.parse(url)?.protocol` is falsy/misleading.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/browserView/common/browserSearch.ts`, `src/vs/workbench/contrib/browserView/common/browserView.ts`, `src/vs/workbench/contrib/browserView/test/common/browserSearch.test.ts`
- **Validation:** A browserSearch.test.ts case asserting resolveAddressBarInputType('C:\\Users\\x\\index.html') === 'url', and a browserView model test asserting loadURL normalizes a drive-letter/POSIX absolute path into a proper file:// URI rather than prefixing http://.
- **Behavior:**

  > Pasting or typing a recognizable absolute local file path (Windows `C:\...` or POSIX `/...`) into the integrated browser's address bar should navigate directly to that file, the way a conventional desktop browser does, instead of being offered as a web search or silently mis-normalized. Typing an ordinary bare hostname or search query must be unaffected.
- **Trace:**

  > Two places disagree: resolveAddressBarInputType (src/vs/workbench/contrib/browserView/common/browserSearch.ts, the scheme-less/`unknown` branch around lines 298-324) doesn't recognize a single ASCII letter + `:` + `\` or `/` as a Windows path, so it falls through to `unknown`/search-first. Separately, BrowserViewModel.loadURL (src/vs/workbench/contrib/browserView/common/browserView.ts, lines 781-794) only special-cases bare `localhost` and otherwise prepends `http://` whenever `URL.parse(url)?.protocol` is falsy — but `URL.parse` actually parses `C:\...` as having protocol `c:`, and prepends nothing, leaving an unloadable string; POSIX absolute paths (already classified `url`) get `http://` wrongly prepended. Do not touch the existing localhost/IPv4/TLD heuristics in browserSearch.ts, which are deliberately scoped per the file's own header note (treat its test suite as the spec) — this would be additive. Related: https://github.com/microsoft/vscode/issues/338935#issuecomment (workaround confirms the gap).
- **Open decisions:**
  - Which absolute-path shapes should be auto-detected and converted to file:// (Windows drive letters only, or also UNC `\\server\share\...` and POSIX `/...`)?
  - Should navigating to a local file:// path from the address bar carry any additional trust/permission prompt, given the integrated browser's existing permission model (browserPermissionsFeature.ts), or is it safe to treat identically to any other URL since the user typed it?

## Evidence

- **classification gap:** src/vs/workbench/contrib/browserView/common/browserSearch.ts resolveAddressBarInputType: a Windows drive-letter input like `C:\Users\...\index.html` has `candidateScheme === 'c'`, which is not in ALL_KNOWN_SCHEMES and isn't followed by `//`, so it falls into the `unknown` branch (lines 316-324) and the address-bar picker offers Search first (browserNavigationFeatures.ts line 217-226 default case), matching the reporter's 'it just opens the Internet'.
- **normalization bug:** Even when a path IS classified `url` (e.g. POSIX `/Users/x/index.html`, handled at browserSearch.ts line 343-344), BrowserViewModel.loadURL in src/vs/workbench/contrib/browserView/common/browserView.ts (lines 785-791) only special-cases bare `localhost`; anything else without a parseable protocol gets `http://` prepended — `URL.parse('C:\Users\...')?.protocol` actually returns `'c:'` (verified with Node's WHATWG URL.parse), so even an explicit scheme guess is wrong for drive-letter paths, and plain POSIX paths get mangled into `http:///Users/...`.
- **maintainer workaround:** https://github.com/microsoft/vscode/issues/338935#issuecomment (jruales) confirms prefixing with `file://` is required today — i.e. no automatic local-path detection exists, as traced.
