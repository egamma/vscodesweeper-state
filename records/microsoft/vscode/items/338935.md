# Issue #338935 — Inbuilt Browser not picking local system directories 

[https://github.com/microsoft/vscode/issues/338935](https://github.com/microsoft/vscode/issues/338935)

## Summary

Traced in source: pasting a Windows absolute path like `C:\Users\...\index.html` into the integrated browser's address bar is misclassified as an ambiguous/search query rather than a navigable local file, unlike real browsers which fix up drive-letter paths into `file://` URLs. A contributor already gave a `file://` workaround, so this stays a real but low-severity gap, not a close.

## Change summary

Typing/pasting a raw Windows filesystem path (e.g. `C:\Users\Jude\...\index.html`) into the integrated browser's address bar does not navigate to the local file; it falls back to a web search instead.

## Best solution

Teach the address-bar classifier in browserSearch.ts to recognize Windows drive-letter absolute paths as navigable, and have the navigation path (browserNavigationFeatures.ts / BrowserViewModel.loadURL in browserView.ts) convert such paths into a proper `file://` URI (handling backslash-to-slash and percent-encoding) before loading, mirroring how real browsers fix up local file paths.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/browserView/common/browserSearch.ts`, `src/vs/workbench/contrib/browserView/electron-browser/features/browserNavigationFeatures.ts`, `src/vs/workbench/contrib/browserView/common/browserView.ts`
- **Validation:** A new case in browserSearch.test.ts asserting `resolveAddressBarInputType('C:\\Users\\Jude\\Documents\\web\\index.html')` returns `'url'`, plus a test around BrowserViewModel.loadURL (or equivalent) asserting such a path is converted to a `file://` URI before being handed to webContents.
- **Behavior:**

  > Pasting a Windows absolute file path (e.g. `C:\Users\Jude\Documents\web\index.html`) into the integrated browser's address bar and pressing Enter should navigate directly to that local file (as a real file:// URL), the same way typing it in Chrome/Edge does — not fall back to a web search. Existing http(s)/search/localhost behavior must be unchanged. Acceptance: `resolveAddressBarInputType` classifies such drive-letter paths as `'url'`, and the navigation path converts them into a well-formed `file://` URI before calling into webContents.loadURL.
- **Trace:**

  > Root cause has two parts, confirmed by reading (not executing) the code: (1) resolveAddressBarInputType in src/vs/workbench/contrib/browserView/common/browserSearch.ts treats the leading `C:` as an unrecognized scheme operand (not followed by `//`, not digits) and returns `'unknown'` (lines 298-324), causing browserNavigationFeatures.ts (`_resolvePrimaryActions`, lines 193-226) to default to offering a web search first; (2) even when a path is classified as `'url'`, BrowserViewModel.loadURL in common/browserView.ts (lines 781-793) only fixes up bare-host/localhost-style inputs by prepending `http://` — it does not detect or convert filesystem paths into `file://` URIs, and Node's `URL.parse` happily (and wrongly, for this purpose) parses `C:\...` with protocol `'c:'`, so the `!URL.parse(url)?.protocol` guard never catches it. The boundary: do not touch existing http(s)/search/localhost classification or the existing `file://`-prefixed-input path (already works per the contributor's comment) — only add detection/conversion for raw OS absolute paths. Unresolved: whether Unix/macOS absolute paths (already classified as `'url'` via the host-less `/`-prefix rule, line 343-344) also need the same `file://` conversion at loadURL time, and whether UNC paths (`\\server\share`) are in scope.
- **Open decisions:**
  - Should the fix also cover UNC paths (`\\server\share\file.html`), or only single drive-letter absolute paths like `C:\...`?
  - Should the same `file://` conversion also apply to the already-classified-as-'url' Unix/macOS absolute paths (`/Users/.../file.html`), which currently also aren't converted to `file://` at loadURL time, or is that a separate concern?

## Evidence

- **classification gap:** src/vs/workbench/contrib/browserView/common/browserSearch.ts:279 resolveAddressBarInputType: for input like `C:\Users\Jude\Documents\web\index.html`, the leading `C:` is parsed as a single-letter `candidateScheme` not in ALL_KNOWN_SCHEMES, and `afterScheme` (`\Users\...`) doesn't start with `//` or digits, so it falls into the `return 'unknown'` branch (lines 319-324) instead of `'url'`.
- **consumer defaults to search:** browserNavigationFeatures.ts:217-226 `_resolvePrimaryActions` treats `'unknown'` as ambiguous and offers Search first (`[search, goTo]`), matching the reporter's 'it just opens the Internet' symptom.
- **even if classified as url, navigation isn't fixed up:** BrowserEditorInput.navigate (common/browserEditorInput.ts:181) passes the raw string straight to BrowserViewModel.loadURL (common/browserView.ts:781-793), which only prepends `http://` when `URL.parse(url)?.protocol` is falsy — but Node's `URL.parse('C:\\Users\\...')` returns protocol `'c:'` (verified via `node -e`), so the http:// fallback never fires and the path is never turned into a `file://` URI.
- **team acknowledgment:** Contributor @jruales (comment, 2026-09-30) confirmed this is not supported directly and suggested prefixing with `file://`, plus existing entry points (Explorer context menu 'Open in Integrated Browser', editor tab globe icon) as the current way to open local HTML.
