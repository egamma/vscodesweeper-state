# Issue #346819 — Support checkbox toggling to enable/disable workspace Instructions, Prompts, and Skills in LLM context (similar to MCP tools)

[https://github.com/microsoft/vscode/issues/346819](https://github.com/microsoft/vscode/issues/346819)

## Summary

Keep open: existing enablement controls provide partial coverage, not persistent per-file workspace toggles across instructions, prompts, and skills. The related skills requests cover only part of this broader request.

## Change summary

Allow non-destructive, persistent enablement of individual workspace customization files, excluding disabled assets from automatic model context and discovery.

## Best solution

Provide consistent per-item enablement through the shared Customizations surface, with enforcement by each consuming harness. Define persistence and active-conversation semantics explicitly, and distinguish instruction application, skill discovery, and manually invoked prompts.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagement.contribution.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/promptsServiceCustomizationItemProvider.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts`, `src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts`
- **Validation:** After scope decisions, verify that disabling one asset excludes its content and metadata from newly constructed automatic context, preserves its disk contents, survives the chosen persistence boundary, and does not disable a same-named asset in another workspace root. Verify re-enablement and distinguish prompt-picker visibility from automatic context inclusion.
- **Behavior:**

  > Users can disable individual workspace customization assets without moving, editing, or deleting their files. Disabled assets remain available for management but are excluded from the applicable automatic discovery and context paths, including skill metadata. Acceptance includes independent behavior for same-named files in separate workspace roots and persistence at the agreed scope. Prompt controls must describe invocation or visibility accurately rather than promise savings from content that was not automatically included.
- **Trace:**

  > The shared management contribution registers enable/disable commands, but its menu predicates expose them only for Built-in skills. PromptsServiceImpl persists disabled URI sets at profile scope and refreshes agent or skill caches; computeSlashCommandDiscoveryInfo filters skills without equivalently filtering prompt files. PromptsServiceCustomizationItemProvider projects enabled state for several asset kinds, which is presentation evidence, not proof of enforcement by every consumer. Folder-location settings offer partial discovery control and explicitly document harness differences. The related requests https://github.com/microsoft/vscode/issues/290290 and https://github.com/microsoft/vscode/issues/347788 corroborate the skills use case but do not absorb the full request. The remaining uncertainty is the public behavior across persistence boundaries, existing conversations, and deprecated prompt-file support; this was source inspection only, with no execution or checkout changes.
- **Open decisions:**
  - Should enablement persist per workspace, per chat session, or through workspace defaults with session overrides?
  - Should a toggle affect the next turn of an existing conversation or only newly started conversations, given that previously supplied content remains in conversation history?
  - Should legacy prompt files receive dedicated enablement controls, or should that part of the experience follow the existing migration to skills?

## Evidence

- **Existing controls are narrower:** src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagement.contribution.ts:679-774 registers aiCustomizationManagement.disableItem and aiCustomizationManagement.enableItem, but their menu contributions require Built-in storage and the skill type. This does not expose the requested controls for workspace instructions, prompts, and skills.
- **Persistence and consumption are incomplete for this request:** src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts:1005-1037 stores disabled URIs by asset type in StorageScope.PROFILE, rather than workspace/session state. computeSlashCommandDiscoveryInfo filters disabled skills but includes prompt files without that filter; a generic disabled-file store alone does not establish the requested isolation.
- **Settings do not deliver per-file toggles:** src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts registers chat.instructionsFilesLocations, chat.promptFilesLocations, and chat.agentSkillsLocations as discovery-folder settings. These are not individual-asset enablement controls, and their documented harness limitations prevent treating them as coverage for this request.
- **Discussion distinguishes asset semantics:** https://github.com/microsoft/vscode/issues/346819#issuecomment-6724471656 distinguishes instruction injection, skill metadata discovery with lazy body loading, and explicitly invoked prompts. It also identifies multi-root identity and session-prefix implications; its applyTo workaround changes files and therefore does not meet the non-destructive requirement.
- **Related requests are subsets:** https://github.com/microsoft/vscode/issues/347788 requests Agents-window per-skill switches. https://github.com/microsoft/vscode/issues/290290 is verified OPEN and requests individual skill enablement. Neither owns the instructions-and-prompts scope here, so neither is a sufficient duplicate canonical.
- **Prompt lifecycle affects scope:** src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts:2048-2071 deprecates chat.promptFilesLocations and directs migration from prompt files to skills. The design should account for that existing direction rather than assume identical long-term controls for all three asset types.
