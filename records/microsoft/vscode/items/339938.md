# Issue #339938 — Sandboxed Copilot sessions hang during MCP startup when using a localhost proxy

[https://github.com/microsoft/vscode/issues/339938](https://github.com/microsoft/vscode/issues/339938)

## Summary

Real, well-diagnosed bug: a confirmed milestone keeps it open regardless (team-authored, real milestone 1.142.0 is a scheduling decision, not a holding bin), and the reporter's own root-cause analysis checks out against current main — the sandbox config builder never forwards a proxy route even though the SDK-facing type already supports one.

## Change summary

When a sandboxed Copilot session uses a local-process MCP server (e.g. `npx`-launched) and the user has a loopback HTTP/HTTPS proxy configured, MCP startup hangs for minutes and eventually times out, because the sandbox denies localhost access by default and nothing populates the SDK's `userPolicy.network.proxy` route.

## Best solution

Thread VS Code's resolved proxy configuration into `buildSandboxConfigForSdk` so sandboxed MCP/LSP child processes get an explicit `userPolicy.network.proxy` route to a loopback proxy without requiring `allowLocalNetwork` to be enabled wholesale; needs a maintainer decision on how proxy credentials are resolved/forwarded and when the route should be auto-granted.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/sandboxConfigForSdk.ts`, `src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/platform/agentHost/node/copilot/copilotSandboxPolicy.ts`
- **Validation:** A sandboxConfigForSdk unit test asserting that when VS Code's effective proxy is a loopback address (e.g. from http.proxy or HTTPS_PROXY), the built SandboxConfig includes userPolicy.network.proxy.url pointing at it, without requiring allowLocalNetwork to be true.
- **Trace:**

  > buildSandboxConfigForSdk() in src/vs/platform/agentHost/node/copilot/sandboxConfigForSdk.ts builds userPolicy.network from AgentHostSandboxKey values (allowOutbound/allowLocalNetwork/allowedHosts/blockedHosts) but never reads or forwards any proxy configuration, even though SandboxNetworkProxyPolicy (url/username/password) is already defined on the type. Neither call site (copilotAgentSession.ts:5448, copilotSessionLauncher.ts:919) passes a proxy value in. Meanwhile copilotAgent.ts already resolves and forwards HTTP_PROXY/HTTPS_PROXY as process env vars to the SDK client, so the sandboxed child process is told to use a loopback proxy that its own network policy then denies by default. The boundary: do not touch allowOutbound/allowedHosts/blockedHosts behavior, and do not change env-var forwarding to the SDK process — the gap is purely in translating the resolved proxy into the sandbox's own userPolicy.network.proxy route (or an equivalent host-specific allowance).
- **Open decisions:**
  - Should the sandbox automatically grant a route to the configured proxy host:port whenever a proxy is active, or only when the proxy address resolves to the local machine?
  - Which VS Code setting/signal is authoritative for resolving the effective proxy to forward (http.proxy setting vs HTTP_PROXY/HTTPS_PROXY env vars), and how are credentials embedded in a proxy URL handled given SandboxNetworkProxyPolicy exposes separate username/password fields?
  - Does granting this proxy route require allowOutbound to already be true, or should it work independently of the broader outbound/local-network toggles?

## Evidence

- **type exists but unused:** SandboxNetworkPolicy.proxy / SandboxNetworkProxyPolicy are defined in src/vs/platform/agentHost/node/copilot/sandboxConfigForSdk.ts (lines 82-95), but buildSandboxConfigForSdk() (lines 121-194) never populates `network.proxy` — only allowOutbound/allowLocalNetwork/allowedHosts/blockedHosts are forwarded from AgentHostSandboxKey values.
- **no call-site wiring:** Both call sites of buildSandboxConfigForSdk (copilotAgentSession.ts:5448, copilotSessionLauncher.ts:919) pass only (platform, sandbox config, extraReadonlyPaths) — no proxy argument exists anywhere in the signature or its tests (test/node/sandboxConfigForSdk.test.ts).
- **proxy env vars ARE forwarded to the process:** copilotAgent.ts forwards HTTP_PROXY/HTTPS_PROXY (COPILOT_PROXY_ENV_KEYS/COPILOT_PROXY_SET_ENV_KEYS, ~line 187-192, 6099), confirming the reporter's claim that VS Code supplies the proxy env vars to the runtime process while the sandbox's own network policy has no matching allowance.
- **maintainer repro:** Author (MEMBER) reproduced with isolated test showing `connect EPERM 127.0.0.1:<port>` and a 60s MCP lifecycle negotiation timeout, and a second comment shows the session stuck on a 'Reasoning…' loader for several minutes with a screenshot.
