# Issue #30874 — Regex Find can cause VS Code to Freeze

[https://github.com/microsoft/vscode/issues/30874](https://github.com/microsoft/vscode/issues/30874)

## Summary

Keep this established report open: current editor Find still executes JavaScript regular expressions synchronously, without a mechanism in the traced path to interrupt a blocking match. The discussion identifies V8 catastrophic backtracking, and no verified fix or older canonical issue supersedes this report.

## Change summary

Prevent pathological regular expressions, including intermediate patterns entered while editing a search, from freezing the VS Code window.

## Best solution

Retain this report as the canonical tracking point for V8-backed regex-search hangs. Resolve the unbounded execution through upstream engine safeguards or a compatible editor-side containment design that keeps the UI responsive without silently changing supported regex semantics.

## Evidence

- **Confirmed trigger and diagnosis:** The reporter disables extensions and edits the multiline pattern `"""(.*?\n?)+?"""`, causing a frozen window and 100% helper CPU. https://github.com/microsoft/vscode/issues/30874#issuecomment-315861140 confirms catastrophic backtracking against the sample in browsers and explicitly calls for protection against the hang.
- **Current synchronous editor path:** src/vs/editor/contrib/find/browser/findModel.ts:149-177 reacts to search-state changes by calling research directly for ordinary files; research calls _findMatches at line 216. TextModel.findMatches in src/vs/editor/common/model/textModel.ts:1178-1224 synchronously delegates regex searches to TextModelSearch.findMatches.
- **No interruption in the traced match path:** src/vs/editor/common/model/textModelSearch.ts:163-175 selects multiline or line-by-line matching. Multiline matching calls Searcher.next over the concatenated search range; Searcher.next at line 523 executes native RegExp.exec synchronously. Match-count limits and repeated-empty-match guards operate only after exec returns, so they do not bound backtracking within an individual match. This was source inspection, not a runtime reproduction.
- **Partial resolution is not full coverage:** https://github.com/microsoft/vscode/issues/30874#issuecomment-630725619 reports the empty-alternative case resolved in 1.45.1, but https://github.com/microsoft/vscode/issues/30874#issuecomment-640042611 supplies extension-disabled minimal examples that still hang in that same version. The existing empty-match progress guard does not establish resolution of the original backtracking problem.
- **Upstream ownership and product boundary:** https://github.com/microsoft/vscode/issues/30874#issuecomment-724763841 links V8's non-backtracking regexp tracking issue at https://bugs.chromium.org/p/v8/issues/detail?id=10765. https://github.com/microsoft/vscode/issues/30874#issuecomment-315865436 and https://github.com/microsoft/vscode/issues/30874#issuecomment-315914518 identify editor-side matching, including searches of open files, as the affected VS Code path.

Its verified open report describes the same editor-find freezing symptom, and https://github.com/microsoft/vscode/issues/221827#issuecomment-2246436430 acknowledges the absence of blocking-regex protection. It was created in 2024, later than this 2017 report, so it cannot supersede this re-reviewed item under the older-canonical requirement.
