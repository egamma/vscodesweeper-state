# Issue #174900 — Quick Pick: Images in the tooltip confuse the layout

[https://github.com/microsoft/vscode/issues/174900](https://github.com/microsoft/vscode/issues/174900)

## Summary

The layout problem remains traceable on current main: an oversized quick-pick tooltip requested on the right falls back below the item, where it can obscure the list. This team-authored Backlog issue has no verified duplicate or issue-referencing fix commit, so it should remain open while the intended overflow behavior is decided.

## Change summary

Quick-pick tooltips containing large Markdown images reposition in a way that disrupts or obscures the quick-pick layout.

## Best solution

Define a consistent overflow policy for pointer hovers with large asynchronous content, then ensure quick-pick image tooltips stay within the viewport, remain visibly anchored to their item, and avoid unnecessarily covering the list.

## Plan brief

- **Likely files:** `src/vs/platform/quickinput/browser/quickInputList.ts`, `src/vs/platform/hover/browser/hoverWidget.ts`, `src/vs/platform/hover/test/browser/hoverService.test.ts`
- **Validation:** Add a hover service browser test that simulates a right-positioned pointer hover whose content expands to an image-sized width, then asserts the agreed placement remains within the viewport, correctly anchors the pointer, and preserves existing placement behavior for ordinary text tooltips.
- **Behavior:**

  > A quick-pick item tooltip containing an image must remain readable and within the viewport after the image finishes loading. Its pointer must continue to identify the originating item, and the tooltip should not unexpectedly disrupt the quick-pick list. Ordinary text tooltips and keyboard-triggered tooltip interaction must retain their existing behavior.
- **Trace:**

  > QuickInputList.showHover in src/vs/platform/quickinput/browser/quickInputList.ts requests a right-positioned hover with a pointer. Image loading is asynchronous: src/vs/base/browser/markdownRenderer.ts signals the size change, after which HoverWidget in src/vs/platform/hover/browser/hoverWidget.ts lays out again. HoverWidget.adjustHorizontalHoverPosition falls back from RIGHT to BELOW when neither horizontal side has enough room, producing the list-obscuring behavior discussed in https://github.com/microsoft/vscode/issues/174900. The boundary is shared pointer-hover overflow and quick-pick usage; do not alter Markdown sanitization, link behavior, or ordinary tooltip accessibility.
- **Open decisions:**
  - When a pointer tooltip is too wide for either side of its target, should it remain beside the target with constrained or scrollable content, or move above/below even when that covers nearby quick-pick items?
  - Should oversized images be constrained independently within hover content, or should the general hover overflow policy handle all large content uniformly?

## Evidence

- **current quick-pick path:** src/vs/platform/quickinput/browser/quickInputList.ts, QuickInputList.showHover, still requests HoverPosition.RIGHT with showPointer enabled for item tooltips.
- **source reproduction:** src/vs/platform/hover/browser/hoverWidget.ts, HoverWidget.adjustHorizontalHoverPosition, changes a right-positioned hover to BELOW when loaded content fits on neither side; this matches the maintainer discussion that image or sufficiently large text tooltips reposition over list items.
- **asynchronous image behavior:** src/vs/base/browser/markdownRenderer.ts invokes asyncRenderCallback after an image loads, and src/vs/platform/hover/browser/hoverWidget.ts responds by recalculating the hover and requesting ContextView layout. The fallback placement therefore uses the image's expanded dimensions rather than preventing the disruptive fallback.
