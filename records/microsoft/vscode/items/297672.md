# Issue #297672 — Expose terminal enumeration APIs for safe automation gating before kill-all actions

[https://github.com/microsoft/vscode/issues/297672](https://github.com/microsoft/vscode/issues/297672)

## Summary

Extension APIs already enumerate terminals and expose much of the requested metadata, but they do not fully cover an agent-facing inventory with stable identifiers and ownership information. Keep this accepted On Deck request open to define that remaining contract; the maintainer-linked issue covers terminal output access, not enumeration before cleanup.

## Change summary

Expose terminal inventory and identity metadata so automation can inspect terminals before choosing whether and what to close.

## Best solution

Reuse existing terminal enumeration capabilities and define the missing automation-facing inventory contract, including identifier lifetime and ownership semantics. Allow workflows to distinguish their own terminals without treating an unknown process state or ownership as permission to terminate it.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTerminalService.ts`, `src/vs/workbench/api/browser/mainThreadTerminalService.ts`, `src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/terminal.chatAgentTools.contribution.ts`
- **Validation:** After choosing the contract, exercise inventory with no terminals, a user-created terminal, an extension-created terminal, and an agent-created terminal, including panel and editor locations. Verify identifiers follow the chosen lifetime, active-terminal changes are reflected, unavailable metadata remains explicitly unknown, enumeration changes no terminal state, and targeted cleanup preserves terminals outside the workflow's ownership.
- **Behavior:**

  > Automation should inspect terminal inventory before deciding whether cleanup is necessary, rather than invoke kill-all blindly. Extensions already have terminal enumeration and several metadata fields; the remaining request is reliable automation-facing identity and enough state or ownership information to select targets. Acceptance should cover empty and mixed-origin inventories, unavailable metadata, and non-destructive inspection. The intended consumers and identifier/ownership guarantees need to be agreed before implementation.
- **Trace:**

  > vscode.window.terminals and activeTerminal are declared in src/vscode-dts/vscode.d.ts, alongside name, processId, creationOptions, exitStatus, shell state, and shell-integration cwd. MainThreadTerminalService initializes extension-host terminal state from ITerminalService.instances, while ExtHostTerminalService exposes API objects and launch metadata; its internal terminal identifier is not part of the public Terminal interface. The terminal chat-tool contribution registers no general inventory tool, and the current GetTerminalOutputTool requires a previously returned execution UUID. The maintainer-linked https://github.com/microsoft/vscode/issues/288570 and merged https://github.com/microsoft/vscode/pull/308587 address output/input access rather than the full inventory request. Preserve existing extension enumeration, terminal visibility, and explicit disposal behavior; do not broaden kill-all semantics or infer ownership from a terminal name or shell PID. Uncertainty starts at the public contract: which consumers need the additional surface and what identity and ownership guarantees it should provide.
- **Open decisions:**
  - Should the remaining capability be exposed through an agent tool, a command returning inventory, additions to the extension API, or a combination?
  - Should terminal identifiers be stable only for a terminal's lifetime in one window, or also across reload and session restoration?
  - What creator or ownership information should consumers receive, and how should user interaction or restored terminals affect that attribution?
  - Which process-state guarantees are required for cleanup gating, and how should unsupported or indeterminate states appear to consumers?
