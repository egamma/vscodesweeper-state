# Issue #246714 — Search Editor Progress Bar disappears when switching to another editor and back

[https://github.com/microsoft/vscode/issues/246714](https://github.com/microsoft/vscode/issues/246714)

## Summary

Keep open: current source hides editor progress on tab changes but does not restore it when returning to an unfinished Search Editor search. The reporter supplied a recording, a clean-profile reproduction against the OpenJDK repository, and trace logs; another information request is not warranted.

## Change summary

Restore the Search Editor progress indicator when returning to a tab whose search is still running.

## Best solution

Make the visible Search Editor accurately reflect its input's pending search, including after switching tabs, without displaying that search's progress on unrelated editors or retaining progress after completion.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/searchEditor/browser/searchEditor.ts`, `src/vs/workbench/contrib/searchEditor/browser/searchEditorInput.ts`, `src/vs/workbench/services/progress/test/browser/progressIndicator.test.ts`
- **Validation:** Establish a regression check with a controllably pending search: wait until progress appears, switch to an ordinary editor, return before resolving the search, and verify progress is visible again; resolve the search and verify progress disappears. Also check completion while hidden and switching between two Search Editor inputs. Manual acceptance can follow the reported sequence against a large workspace such as OpenJDK.
- **Behavior:**

  > When a Search Editor search remains unfinished, returning to its tab must show that it is still running. Switching to an unrelated editor must not display the hidden search's progress there. Completion must remove the indicator, including when the search finishes while its tab is hidden. Validate the tab-return sequence with a search held pending long enough for the initial progress indicator to appear.
- **Trace:**

  > SearchEditor in src/vs/workbench/contrib/searchEditor/browser/searchEditor.ts starts a LongRunningOperation after query construction and stores its pending promise on SearchEditorInput.ongoingSearchOperation. EditorGroupView supplies the group-level EditorProgressIndicator, whose EDITOR_ACTIVE listener stops and hides progress without replaying it. SearchEditor.setInput restores configuration and attaches completion handling for an ongoing search but does not restore progress; LongRunningOperation's initial timer is one-shot. This conclusively explains the reported switch-away-and-back sequence after progress has appeared. Preserve the intentional suppression of hidden-editor progress documented by https://github.com/microsoft/vscode/issues/138331; do not broaden this into a shared editor-progress redesign. The remaining uncertainty is validation infrastructure: the inspected progress tests cover ScopedProgressIndicator, and the existing Search Editor tests cover its model rather than pane activation.

## Evidence

- **Reporter supplied the requested clarification:** The discussion at https://github.com/microsoft/vscode/issues/246714 includes a recording, clarification that results arrive roughly half a minute after the progress disappears, and a clean portable 1.101.0-insider reproduction searching https://github.com/openjdk/jdk/ with available machine resources and trace output. These details address the maintainer's questions about completion and resource pressure.
- **Current source reproduces the missing-progress lifecycle:** src/vs/workbench/browser/parts/editor/editorGroupView.ts registers EditorProgressIndicator as the group's IEditorProgressService. In src/vs/workbench/services/progress/browser/progressIndicator.ts, EditorProgressIndicator.registerListeners stops and hides the progress bar on EDITOR_ACTIVE and explicitly notes that editor progress is not tracked and replayed.
- **Search Editor does not restore pending progress:** src/vs/workbench/contrib/searchEditor/browser/searchEditor.ts:599-613 starts a LongRunningOperation with a 500 ms delay and retains the pending promise on startInput.ongoingSearchOperation. Returning through setInput at lines 710-749 reattaches completion handling to that promise but never restarts progress. LongRunningOperation.start in src/vs/platform/progress/common/progress.ts shows progress through a one-shot timer, so a search already showing progress before the tab switch has no later show event.
- **Historical behavior is not a fix for this report:** https://github.com/microsoft/vscode/issues/138331 is closed and addressed progress leaking onto another editor. Its concluding discussion confirms hiding progress when changing editors, not restoring progress when returning to an unfinished search. That behavior must remain intact.
- **Canonical search found a distinct related report:** Repository issue searches for Search Editor progress and switching found no verified older canonical with the same disappearing-on-return symptom. The open https://github.com/microsoft/vscode/issues/225315 concerns progress continuing after completion, particularly around invalid regular expressions, rather than disappearing during an unfinished search; it does not meet the re-review duplicate bar.
- **Validation boundary:** The checkout was inspected read-only; no application or tests were executed. src/vs/workbench/contrib/searchEditor/test/browser/searchEditorModel.test.ts covers the model, while src/vs/workbench/services/progress/test/browser/progressIndicator.test.ts exercises ScopedProgressIndicator rather than the Search Editor tab-return lifecycle. An executable regression harness for this exact interaction was not established.
