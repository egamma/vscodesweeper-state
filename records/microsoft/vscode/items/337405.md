# Issue #337405 — Prompt-to-skill migration fails with vague git pathspec error

[https://github.com/microsoft/vscode/issues/337405](https://github.com/microsoft/vscode/issues/337405)

## Summary

Confirmed on main: the worktree commit path unconditionally runs `git add` on the target file even for deletions, so removing a never-committed prompt file during migration fails with the exact pathspec error shown, aborting the batch mid-way.

## Change summary

Converting workspace prompts to skills fails with a raw `git add` pathspec error instead of completing or explaining the failure.

## Best solution

In `github.copilot.cli.sessions.commitToWorktree` (extensions/copilot/src/extension/chatSessions/vscode-node/copilotCLIChatSessions.ts), branch on whether the target file still exists / is tracked before calling `gitService.add`, so a deletion of an untracked file is a no-op instead of surfacing a raw git error; also make the migration loop tolerate a single file's commit failure without leaving the batch in an ambiguous state.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/chatSessions/vscode-node/copilotCLIChatSessions.ts`, `extensions/copilot/src/extension/chatSessions/vscode-node/copilotCLIChatSessionsContribution.ts`, `src/vs/sessions/contrib/chat/browser/aiCustomizationWorkspaceService.ts`
- **Validation:** A test/repro asserting that deleting a never-committed prompt file during migration no longer throws the git pathspec error and the migration completes for the remaining files.
- **Behavior:**

  > Migrating prompt files to skills (or any flow that deletes an ai-customization file from a worktree) must not surface a raw git pathspec error to the user. If the file being removed was never tracked by git, the removal should be treated as already-satisfied (no-op) rather than an error; if it was tracked, the removal should be staged and committed normally. On any unexpected git failure during migration, the user should get an actionable message that clarifies whether other files in the batch were migrated and whether a partial state needs manual cleanup.
- **Trace:**

  > `commitToWorktree` (extensions/copilot/src/extension/chatSessions/vscode-node/copilotCLIChatSessions.ts:1856, mirrored in copilotCLIChatSessionsContribution.ts:2968) always calls `gitService.add(worktreeUri, [fileUri.fsPath])` before `gitService.commit`, regardless of whether the path exists or is tracked. `commitDeletionToRepos` in src/vs/sessions/contrib/chat/browser/aiCustomizationWorkspaceService.ts:231-271 deletes the file from the repository copy and invokes this same command for the worktree copy, where the file may already be gone and untracked — `git add` on such a path fails with exactly the reported pathspec error. The catch block (copilotCLIChatSessionsContribution.ts:1885 area) only special-cases 'nothing to commit'/'NotAGitRepository', so this case falls through to a generic error toast. Do not change the addition path (commitFileToRepos) or the repository-side commit command — only the worktree deletion handling needs the tracked/existence check. Open question is the exact UX contract for the batch-failure case, which is why this is `plan` rather than `implement`.
- **Open decisions:**
  - When the file to delete is untracked and already gone from the worktree, should commitToWorktree silently no-op, or still surface some (non-error) confirmation?
  - When one file in a multi-file migration batch fails to commit, should the migration continue for the remaining files (current apparent behavior) or roll back entirely, and how should that be communicated to the user?
  - Should the UI make explicit whether migration is expected to create an automatic git commit at all (as the reporter asks), independent of this specific error?
