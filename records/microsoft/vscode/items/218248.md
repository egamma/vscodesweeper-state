# Issue #218248 — Dragging text upwards triggers scrolling far too early

[https://github.com/microsoft/vscode/issues/218248](https://github.com/microsoft/vscode/issues/218248)

## Summary

The asymmetric drag scrolling remains plausible on current main: selected-text drag-and-drop bypasses the editor's edge-based drag-scrolling machinery and instead reveals every prospective drop position. Keep this open in the editor drag-and-drop area.

## Change summary

Dragging selected text upward starts scrolling around the middle of the editor instead of only near its top edge.

## Best solution

Make selected-text drag-and-drop use symmetric top and bottom edge activation while preserving its drop indicator and move/copy semantics. The editor team should first decide whether scrolling belongs in the shared mouse operation or the drag-and-drop contribution.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/mouseHandler.ts`, `src/vs/editor/browser/controller/dragScrolling.ts`, `src/vs/editor/contrib/dnd/browser/dnd.ts`
- **Validation:** Exercise selected-text drag-and-drop in a multi-screen editor: moving upward or downward within the central viewport must not scroll, entering the corresponding edge zone must scroll in that direction, and dropping must retain existing move and modifier-copy behavior.
- **Behavior:**

  > Dragging selected text within the editor's central viewport must not change the scroll position. Auto-scroll should begin only at comparable edge zones near the top and bottom, with symmetric behavior in both directions. The drop indicator must continue following the pointer, and normal move, modifier-copy, cancellation, and drop behavior must remain unchanged.
- **Trace:**

  > MouseDownOperation._onMouseDownThenMove in src/vs/editor/browser/controller/mouseHandler.ts separates selected-text drag-and-drop from ordinary selection dragging. Ordinary selection uses TopBottomDragScrolling from src/vs/editor/browser/controller/dragScrolling.ts only for OUTSIDE_EDITOR targets, while drag-and-drop emits onMouseDrag directly. DragAndDropController._onEditorMouseDrag in src/vs/editor/contrib/dnd/browser/dnd.ts then calls showAt(), whose immediate revealPosition call is the only scrolling mechanism on this path. This confirms that drag-and-drop lacks the explicit symmetric edge-scrolling contract used by selection. The boundary is editor text drag-and-drop; external file drops, ordinary text selection, move/copy editing semantics, and horizontal scrolling must not regress.
- **Open decisions:**
  - Should selected-text drag scrolling be owned by MouseDownOperation so it can share the existing edge-scrolling lifecycle, or remain within DragAndDropController?
  - Should activation require the pointer to leave the content viewport, or use an inside-edge zone matching the behavior shown near the bottom?
  - What automated browser-level harness should cover pointer-driven text drag scrolling and drop semantics?
