# Issue #338688 — Expose Modern UI / layout density state to webviews

[https://github.com/microsoft/vscode/issues/338688](https://github.com/microsoft/vscode/issues/338688)

## Summary

Confirmed on main: `ModernUIContribution.applyTo` (src/vs/workbench/contrib/modernUI/browser/modernUI.contribution.ts) toggles `.modern-ui`, `.modern-ui-compact`, `.modern-ui-uppercase-view-headers` only on workbench layout containers, and `WebviewThemeDataProvider` (contrib/webview/browser/themeing.ts) exposes only theme-kind classes and fixed size tokens — webviews genuinely have no way to detect Modern UI/density today. A commenter proposes a competing design (make existing tokens density-aware instead of adding new markers), so this needs a maintainer design decision before implementation.

## Change summary

Webview content has no way to detect Modern UI enablement or layout density (compact vs default), unlike native workbench containers which get dedicated CSS classes.

## Best solution

A maintainer should pick one design: (a) mirror the `.modern-ui`/density classes onto the webview `<body>` as data attributes, or (b) make the existing `--vscode-cornerRadius-*`/`--vscode-spacing-size*`/`--vscode-fontSize-*` tokens themselves vary with density so no new surface is needed (the commenter's preference). Either way the fix lives in `ModernUIContribution` plus `WebviewThemeDataProvider`.

- **Behavior:**

  > Webview content (body or its CSS custom properties) reflects Modern UI enablement and layout density state, kept in sync with the native workbench the same way `ModernUIContribution` applies classes to layout containers, so extensions don't need to duplicate settings-reading logic. Acceptance: toggling `workbench.experimental.modernUI` or `window.density.layout` updates the webview-visible signal without requiring an extension to call `workspace.getConfiguration`.
- **Trace:**

  > ModernUIContribution.applyTo (src/vs/workbench/contrib/modernUI/browser/modernUI.contribution.ts:217) toggles `.modern-ui`/`.modern-ui-compact`/`.modern-ui-uppercase-view-headers` only on `layoutService.containers`; webviews are rendered in separate iframes/processes and never receive these classes. WebviewThemeDataProvider (src/vs/workbench/contrib/webview/browser/themeing.ts) is the existing channel that pushes theme-kind classes and fixed size tokens into webview content — it's the natural place to add whichever signal is chosen. Boundary: do not change how native containers are classed, and do not change theme-kind class behavior for non-Modern-UI webviews. Where uncertainty starts: whether to expose parallel `data-vscode-*` markers, extend the CSS token set to vary by density, or both.
- **Open decisions:**
  - Expose Modern UI/density as new webview body attributes (e.g. data-vscode-modern-ui, data-vscode-layout-density), or make the existing size tokens themselves vary by density (the commenter's preference), or both?

## Evidence

- **class scoping:** modernUI.contribution.ts `applyTo()` only calls `container.classList.toggle(...)` on `this.layoutService.containers` (workbench containers), never on any webview iframe/body.
- **webview token exposure:** contrib/webview/browser/themeing.ts's WebviewThemeDataProvider only reads editor font settings and theme colors; no density-aware size tokens or modern-ui markers are passed through, matching the report.
- **design disagreement:** Comment from lppedd (2026-09-29) proposes updating existing size tokens in place rather than adding new markers/attributes — an open design choice, not settled by the issue alone.
