# Issue #338688 — Expose Modern UI / layout density state to webviews

[https://github.com/microsoft/vscode/issues/338688](https://github.com/microsoft/vscode/issues/338688)

## Summary

Confirmed gap on main: ModernUIContribution only toggles modern-ui classes on workbench containers, and WebviewThemeDataProvider exposes no Modern UI/density signal to webviews. A commenter already contests the proposed design (new markers vs. updating existing size tokens in place), so this needs a maintainer design call before any implementation.

## Change summary

Expose Modern UI / layout-density state to webview content so extension webview views can match native pane chrome.

## Best solution

A maintainer should decide the mechanism — dedicated data-* markers on webview body vs. making the existing --vscode-cornerRadius-*/spacing/font tokens density-aware — then wire ModernUIContribution's state through WebviewThemeDataProvider.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/webview/browser/themeing.ts`, `src/vs/workbench/contrib/modernUI/browser/modernUI.contribution.ts`
- **Validation:** A webview themeing test asserting the emitted webview style/body state reflects the current Modern UI enabled/compact/uppercase-header state and updates when ModernUIContribution's settings change.
- **Behavior:**

  > When Modern UI (and its density/uppercase-header sub-settings) is enabled or changed, webview content can detect the current state the same way the native workbench does, without each extension re-reading configuration and relaying it manually. When Modern UI is off, webviews see the same state they see today. Acceptance: a webview themeing test confirms the exposed state tracks ModernUIContribution's enabled/compact/uppercase flags across changes.
- **Trace:**

  > ModernUIContribution (src/vs/workbench/contrib/modernUI/browser/modernUI.contribution.ts, around lines 210-250) computes `enabled`, `compact`, and `useUppercaseViewHeaders` and toggles MODERN_UI_CLASS/MODERN_UI_COMPACT_CLASS/MODERN_UI_UPPERCASE_VIEW_HEADERS_CLASS only on workbench DOM containers. WebviewThemeDataProvider.getWebviewThemeData() in src/vs/workbench/contrib/webview/browser/themeing.ts is the existing channel that pushes theme-kind classes and CSS custom properties into webview content, but has no density/modern-ui awareness. The boundary: don't change how the size tokens behave for non-Modern-UI users, and don't restructure the webview theming pipeline — this is additive. Where uncertainty starts: whether to add new data-* markers (the issue's proposal) or make the existing tokens density-aware in place (the comment's counter-proposal) — these differ in the public webview CSS contract and extensions' expected API.
- **Open decisions:**
  - Expose Modern UI state as new data-vscode-modern-ui/layout-density markers on webview body, or instead make the existing size tokens (--vscode-cornerRadius-*, spacing, fontSize) vary with density in place?
  - If new markers are added, do they ship as a stable, extension-facing contract immediately, or behind the same experimental gate as workbench.experimental.modernUI?
