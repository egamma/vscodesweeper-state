# Issue #337959 — Chat created with a worktree does not show the "Worktree created" message

[https://github.com/microsoft/vscode/issues/337959](https://github.com/microsoft/vscode/issues/337959)

## Summary

Fresh, plausible report: tracing the code shows the 'workspace transition' confirmation notification infrastructure only fires for mid-session conversions to a worktree, not for a session created with a worktree from the start, which matches the reporter's description of a missing confirmation on a newly-created worktree chat.

## Change summary

Opening a newly created chat that started with a git worktree shows no confirmation that the worktree was created.

## Best solution

Decide (with a maintainer) whether initial worktree-backed session creation should emit the same `AgentSystemNotificationKind.WorkspaceTransition` / 'Now working in {0}' system notification that `sessionWorkspaceConversionService.ts` emits for mid-session conversions, and where in the initial turn stream that record should be inserted so it survives hydration.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/chatContributions/sessionWorkspaceConversion/sessionWorkspaceConversionService.ts`, `src/vs/platform/agentHost/node/shared/worktreeIsolation.ts`, `src/vs/platform/agentHost/node/agentService.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/stateToProgressAdapter.ts`
- **Validation:** A test asserting that a newly-created session whose initial isolation is a worktree hydrates a `systemNotification`/`workspaceTransition`-presentation chat part at (or before) the first turn, similar to the existing conversion-path test coverage for `sessionWorkspaceConversionService`.
- **Behavior:**

  > When a chat/session is created with a git worktree from the start (not converted mid-session), opening it should show a confirmation message ('Now working in {workspace}' or equivalent) at the top of the chat, consistent with what already happens when a session is converted to a worktree mid-session. Acceptance: a fresh worktree-isolated session's turn history contains a workspace-transition system notification the first time it is opened.
- **Trace:**

  > `sessionWorkspaceConversionService.ts` (`_createWorkspaceTransition`, line ~522) is the only place that builds an `AgentSystemNotificationKind.WorkspaceTransition` record ('Now working in {0}') and persists it via `setWorkspaceConversion`/`setTurnWorkspaceTransition`; it is invoked only from the workspace-conversion flow (folder/workspaceless → worktree mid-session), not from initial session/worktree creation in `worktreeIsolation.ts` or `agentService.ts` (verified via `rg` — no matches there). `stateToProgressAdapter.ts:562-575` (`systemNotificationToChatPart`) is the rendering side and needs no change. Do not touch the conversion path's existing behavior or the `sessions_v2`/turn-persistence invariants in agentHost/AGENTS.md (I5, workspace-transition DB markers); where the uncertainty starts is whether an initial-creation notification reuses the same DB/turn-marker mechanism or needs a lighter one-shot at session-creation time.
- **Open decisions:**
  - Should initial worktree-backed session creation persist a real turn-attached WorkspaceTransition record (reusing sessionWorkspaceConversionService's DB mechanism), or is a lighter one-time client-side banner sufficient?
  - Where in the initial turn stream should this notification be inserted so it survives restore/hydration and doesn't duplicate the existing 'Now working in {0}' conversion message if the session is later converted again?

## Evidence

- **conversion path emits the message:** src/vs/platform/agentHost/node/chatContributions/sessionWorkspaceConversion/sessionWorkspaceConversionService.ts:522 `_createWorkspaceTransition` builds a `localize('agentHost.workspaceTransitionLabel', "Now working in {0}", workspaceName)` record with `kind: AgentSystemNotificationKind.WorkspaceTransition`, persisted via `setWorkspaceConversion` and rendered by `systemNotificationToChatPart` in stateToProgressAdapter.ts:562-575.
- **no equivalent on initial creation:** `rg 'WorkspaceTransition' src/vs/platform/agentHost/node/shared/worktreeIsolation.ts src/vs/platform/agentHost/node/agentService.ts` returns no matches — the initial session/worktree creation path does not construct or persist a WorkspaceTransition record, so a session that starts life with a worktree never gets this confirmation.
- **unrelated dispatcher:** src/vs/sessions/contrib/chat/browser/worktreeCreatedTaskDispatcher.ts only dispatches `runOn: 'worktreeCreated'` tasks; it has no UI-message responsibility, ruling it out as the fix location.
