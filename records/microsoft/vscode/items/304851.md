# Issue #304851 — [Feature] Prompt to re-enable disabled MCP servers when agent detects tool reference

[https://github.com/microsoft/vscode/issues/304851](https://github.com/microsoft/vscode/issues/304851)

## Summary

A real MCP workflow gap remains on current main: disabled tools are available to configuration UI code, but tool search has no path to surface their disabled state, request consent, and re-enable the server. This should remain open and be routed to the MCP area as a feature request.

## Change summary

Let an agent recognize a referenced tool from a disabled MCP server, ask permission to enable it, and continue the original request after confirmation.

## Best solution

Expose disabled MCP tool metadata to the tool-search path without making the tools directly invokable, then provide an explicit confirmation flow that enables the appropriate scope and resumes the pending request.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationService.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`
- **Validation:** Add an Agent Host tool-search test where a named MCP tool is disabled: the search must report that it is disabled without invoking it, confirmation must toggle the selected enablement scope, and the original turn must then be able to invoke the tool; declining must leave it disabled.
- **Behavior:**

  > When a request clearly references a tool belonging to a disabled MCP server, the agent can identify the server as disabled and ask whether to enable it. The server remains disabled and its tools remain non-invokable until the user confirms. After confirmation, the original request continues without requiring the user to reopen Configure Tools or repeat the prompt; declining leaves existing enablement unchanged.
- **Trace:**

  > The configuration surface can enumerate disabled tools through ILanguageModelToolsService.getAllToolsIncludingDisabled() in src/vs/workbench/contrib/chat/browser/actions/chatToolPicker.ts, but enabled references are the only entries serialized into the active tool selection. Agent Host tool search in CopilotAgentSession derives candidates from the runtime's available deferred tools, which carry no disabled-server state. AgentHostCustomizationService already dispatches SessionCustomizationToggled, establishing an enablement mutation path, but AgentHostSessionHandler has no confirmation-gated bridge from tool search to that path. Preserve explicit user consent: disabled tools must not become directly invokable or silently enabled, and unrelated MCP servers and tool selections must remain unchanged. The related request at https://github.com/microsoft/vscode/issues/300714 covers configuration UI, not this conversational flow.
- **Open decisions:**
  - Should confirmation enable the MCP server only for the current session, for the workspace, or persist globally?
  - Should the prompt appear only for an explicit disabled server or tool-name reference, or may semantic tool search suggest disabled servers for broader capability requests?

## Evidence

- **current source gap:** src/vs/workbench/contrib/chat/browser/actions/chatToolPicker.ts deliberately uses ILanguageModelToolsService.getAllToolsIncludingDisabled() for configuration, while the active selection is serialized only from enabled entries by src/vs/workbench/contrib/chat/browser/tools/toolSetsContribution.ts.
- **tool-search boundary:** src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts::_toToolSearchCandidates derives candidates only from the runtime's available deferred tools; it carries names and descriptions but no disabled-server state or enable action.
- **enablement API:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationService.ts already exposes setCustomizationEnablement through SessionCustomizationToggled, but that mutation is currently wired to customization UI rather than a model-visible, confirmation-gated tool flow.
- **related issue distinction:** https://github.com/microsoft/vscode/issues/300714 addressed the ability to disable extension-provided MCP servers in the Customizations window; it does not cover conversational discovery and consent-based re-enablement.
