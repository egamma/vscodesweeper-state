# Issue #335673 — Unable to DnD import multiple automations

[https://github.com/microsoft/vscode/issues/335673](https://github.com/microsoft/vscode/issues/335673)

## Summary

Confirmed real gap on main: the Automations drop handler explicitly rejects multiple dropped files (`getAutomationDropData` returns `{kind:'invalid', reason:'multiple'}`), so this is a genuine feature request, not a bug — staying open since it's not covered by any existing setting and needs a small design decision before implementation.

## Change summary

Allow dragging and dropping multiple `.automation.md` blueprint files at once to import several automations in one action, instead of only a single file at a time.

## Best solution

Extend the drop handling in automationsView.ts to accept multiple blueprint files/resources and import each one, deciding how the existing per-import review dialog (`automationDialogService.showAutomationDialog`) behaves for a batch (sequential per-file review vs. bulk import).

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/sessions/browser/views/automationsView.ts`
- **Validation:** A test asserting that dropping N `.automation.md` files/resources results in N automations being created (or N review dialogs being shown, per the chosen design), instead of the current 'Drop one Automation blueprint file at a time.' error.
- **Trace:**

  > getAutomationDropData() in src/vs/sessions/contrib/sessions/browser/views/automationsView.ts (lines 1643-1672) hard-codes `editors.length !== 1` / `files.length !== 1` as invalid with reason 'multiple'; handleDrop() (line 391) surfaces that as an error dialog. importAutomationBlueprint() (line 1674) is written for exactly one blueprint: it parses one file, opens one showAutomationDialog() review, and creates one automation. The boundary is this drop/import path only — do not touch the single-file .automation.md parsing (automationBlueprint.js) or the automation creation service itself. Where uncertainty starts: whether batch drops should show the existing per-item review dialog once per file (safer, matches current single-file UX) or import all dropped blueprints directly without review (faster, but skips the 'review before creating' step the current UI promises).
- **Open decisions:**
  - Should each dropped automation still go through the individual review/edit dialog (showAutomationDialog) before creation, or should multi-file drops import directly without per-file review?
  - If a review dialog is kept per file, should the dialogs be shown sequentially one after another, or should there be a combined batch-review UI?
  - How should partial failures be handled (e.g. one of several dropped files fails to parse) — abort the whole batch or import the valid ones and report the failures?

## Evidence

- **current restriction:** src/vs/sessions/contrib/sessions/browser/views/automationsView.ts: getAutomationDropData() (lines 1643-1672) returns {kind:'invalid', reason:'multiple'} whenever more than one editor/resource or File is dropped, and handleDrop() (line 391) shows the error 'Drop one Automation blueprint file at a time.' for that case.
- **single-file import flow:** importAutomationBlueprint() (line 1674) reads one blueprint, opens a single showAutomationDialog() review dialog, then calls automationService.createAutomation() once — there is no loop for multiple files today.
- **no existing coverage:** No setting or command lets a user batch-import multiple automation blueprints; drag-and-drop is the only import path found alongside this restriction.
