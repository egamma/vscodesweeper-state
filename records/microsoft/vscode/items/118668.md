# Issue #118668 — No way to "deny" a sign in auth request

[https://github.com/microsoft/vscode/issues/118668](https://github.com/microsoft/vscode/issues/118668)

## Summary

Keep open: current authentication code still offers no user-controlled dismissal of a pending sign-in request. Extension-side silent requests mitigate the badge, but do not satisfy this request; a maintainer also consolidated a newer report here in 2025.

## Change summary

Let users decline a pending extension sign-in request and clear its Accounts menu entry and badge contribution without signing in.

## Best solution

Provide a user-controlled dismissal of pending sign-in requests in the core authentication Accounts flow, preserving unrelated requests and existing account grants. Settle whether dismissal is temporary or suppresses subsequent requests before implementing.

- **Fit:** aligned
- **Reason:** Giving users control over persistent authentication indicators improves the built-in workbench experience without requiring them to disable an extension.

## Plan brief

- **Likely files:** `src/vs/workbench/services/authentication/browser/authenticationExtensionsService.ts`, `src/vs/workbench/services/authentication/common/authentication.ts`, `src/vs/workbench/contrib/authentication/browser/authentication.contribution.ts`, `src/vs/workbench/api/browser/mainThreadAuthentication.ts`
- **Validation:** With a test extension issuing a default authentication.getSession request for a provider with no matching session, verify that the user can dismiss the resulting Accounts entry without creating a session or granting access, and that its badge contribution disappears while unrelated requests remain. Repeat the request and reload the window to verify the chosen suppression lifetime. Add targeted authentication tests covering these outcomes and extensions sharing the same provider and request scopes.
- **Behavior:**

  > A default extension authentication request can leave a sign-in entry and numbered badge in Accounts that the user cannot dismiss without signing in. Users should be able to decline that pending request without creating an authentication session, granting account access, or disabling the extension. Dismissal should clear only the relevant entry and badge contribution, leaving other requests intact. Acceptance must also cover repeated requests and window reloads according to the persistence behavior agreed with the maintainer.
- **Trace:**

  > MainThreadAuthentication.doGetSession in src/vs/workbench/api/browser/mainThreadAuthentication.ts routes a default request with no available session to AuthenticationExtensionsService.requestNewSession; silent requests skip this indication. In src/vs/workbench/services/authentication/browser/authenticationExtensionsService.ts, requestNewSession registers a sign-in menu item and command, groups requests by provider and authentication request key, and tracks requesting extension IDs for the badge. completeSignInRequest removes a grouped request after successful session creation or discovery; there is no user dismissal path. Existing grant denial in showGetSessionPrompt concerns an already available account and is a separate flow. Preserve existing session access grants, silent-request behavior, and unrelated pending requests; shared provider/scope groups make per-extension isolation an acceptance concern. https://github.com/microsoft/vscode/issues/268203 was explicitly consolidated here, while https://github.com/microsoft/vscode/issues/158911 concerns modal prompting and https://github.com/microsoft/vscode/issues/309170 adds persistent suppression requirements. The unresolved boundary is how long dismissal lasts and which subsequent requests may surface again.
- **Open decisions:**
  - Does declining a sign-in request dismiss only the current indication, or persist suppression across repeated requests and window reloads?
  - If suppression persists, is it scoped to the extension/provider pair or the specific authentication request, and what user action permits the indication to appear again?

## Evidence
