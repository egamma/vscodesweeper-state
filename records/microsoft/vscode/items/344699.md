# Issue #344699 — Agents window opened from WSL workspace restores an older Windows workspace instead of the active remote context

[https://github.com/microsoft/vscode/issues/344699](https://github.com/microsoft/vscode/issues/344699)

## Summary

The WSL-to-Agents workspace handoff gap is already tracked by the open issue https://github.com/microsoft/vscode/issues/316537. Current source still discards ordinary WSL workspace arguments, supporting consolidation while preserving this report's newer-version and restored-session details.

## Change summary

Opening Agents from a WSL editor should retain the project's WSL environment instead of leaving an unrelated Windows workspace selected.

## Best solution

Consolidate the WSL launch-context work under https://github.com/microsoft/vscode/issues/316537, carrying over the 1.143.1 reproduction and older-Windows-session restoration detail. The completed behavior should resolve the originating WSL distro and Linux workspace through the appropriate agent host, without treating Linux paths as Windows paths.

## Evidence

- **Verified open canonical:** https://github.com/microsoft/vscode/issues/316537 is open. Its reproduction connects a Windows editor to WSL, opens a Linux filesystem project, and invokes Open in Agent; the resulting Agents window remains in a Windows working directory rather than the WSL project. This owns the same launch-context handoff problem.
- **Current source drops WSL context:** src/vs/workbench/contrib/chat/electron-browser/agentSessions/agentSessionsActions.ts passes the invoking workspace URI through OpenWorkspaceInAgentsWindowAction. However, resolveAgentsWindowFolderIntent in src/vs/sessions/contrib/chat/browser/agentsWindowOpenIntent.ts returns folderUri: undefined for vscode-remote://wsl+... arguments: it accepts file URIs and specially handles dev-container authorities, but not ordinary WSL authorities.
- **Restoration symptom follows the same gap:** SelectAgentsFolderContribution.handleOpenIntent in src/vs/sessions/contrib/chat/electron-browser/chat.contribution.ts obtains no resolved folder for an ordinary WSL URI. Without an explicit session, draft, or New Session request, it performs no workspace handoff, leaving restored state untouched. Separately, src/vs/platform/windows/electron-main/agentsWindow.ts deliberately sends no navigation intent when an API invocation merely focuses an existing Agents window. These paths explain why a previous Windows session can remain selected; no Windows/WSL runtime execution was performed.
- **Unique evidence to retain:** https://github.com/microsoft/vscode/issues/344699 supplies a reproduction on 1.143.1 with Ubuntu-24.04, an older Windows Agents session being restored, and a follow-up Windows-style error for a Linux working directory. These extend the canonical's diagnostic evidence without establishing a separate root cause.
- **Related items are not alternate canonicals:** https://github.com/microsoft/vscode/issues/317380 is closed and therefore is not a duplicate target. https://github.com/microsoft/vscode/issues/336869 concerns the reverse Open in Editor direction. The open https://github.com/microsoft/vscode/issues/337026 specifically concerns a Dev Container hosted in WSL, whereas this report and the selected canonical concern an ordinary WSL project.
