# Issue #337279 — Agent Host regression: no per-hunk Accept/Undo or reviewed state for agent changes

[https://github.com/microsoft/vscode/issues/337279](https://github.com/microsoft/vscode/issues/337279)

## Summary

Confirmed on main: the Agent Host / Sessions changes view only tracks review state per file (ChangesetReviewedFilesContext in changesViewService.ts), unlike the older chatEditing flow which had per-hunk Keep/Undo actions (chatEditor.action.acceptHunk / undoHunk). This is a real, verifiable gap in the new architecture, not something already covered elsewhere, so it stays open for design/planning.

## Change summary

Agent Host sessions lack per-hunk Accept/Undo or reviewed-state tracking; only whole-file 'Mark as Reviewed' exists, unlike the previous chat editing workflow.

## Best solution

Extend the sessions changes review model (src/vs/sessions/contrib/changes/browser/changesViewService.ts, changesMultiDiffSourceResolver.ts) with a per-hunk reviewed/accepted state, analogous to the old chatEditing per-hunk actions, while accounting for the fact that Agent Host edits are already applied directly to the working tree (no shadow-copy revert model).

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/changes/browser/changesViewService.ts`, `src/vs/sessions/contrib/changes/browser/changesMultiDiffSourceResolver.ts`, `src/vs/sessions/contrib/changes/common/changesViewService.ts`
- **Validation:** A test/manual check confirming that after marking a single hunk reviewed/accepted, that state persists while navigating files and is cleared when the agent later touches that hunk again.
- **Behavior:**

  > In an Agent Host session with multi-hunk file changes, a user should be able to mark or accept/undo individual diff hunks, not just whole files, and that per-hunk state should persist across navigation and reset if the agent re-edits that hunk.
- **Trace:**

  > Current review tracking lives entirely at file granularity: ChangesetReviewedFilesContext in src/vs/sessions/contrib/changes/browser/changesViewService.ts and the mirrored SessionChangesReviewedFilesContext in changesMultiDiffSourceResolver.ts store reviewed state keyed only by file URI. The older chatEditing flow (src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingEditorActions.ts, chatEditingTextModelChangeService.ts) had hunk-level accept/undo built on a shadow-copy diff model where edits weren't yet committed to disk — Agent Host applies edits directly to the working tree, so a straight port of accept/undo (which implies reverting) may not map cleanly; that mismatch is the open design question, not an implementation detail.
- **Open decisions:**
  - Should per-hunk controls be destructive (Accept/Undo that reverts the hunk in the working tree) like the old chatEditing flow, or purely bookkeeping (Mark Hunk as Reviewed/Unreviewed) given edits are already applied to disk?
  - Where should per-hunk reviewed state be persisted/scoped — per changeset, per session, or per file — and how does it interact with the existing file-level 'Mark as Reviewed'?

## Evidence

- **file-only review state:** src/vs/sessions/contrib/changes/browser/changesViewService.ts defines ChangesetReviewedFilesContext (per-file, keyed by URI string); src/vs/sessions/contrib/changes/browser/changesMultiDiffSourceResolver.ts's SessionChangesReviewedFilesContext/SessionChangesFileResourceContext confirm review tracking is whole-file only.
- **old workflow had per-hunk controls:** src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingEditorActions.ts defines acceptHunkId/undoHunkId ('Keep this Change' / 'Undo this Change') per diff hunk in the classic Chat Edits flow — the capability the reporter says regressed.
- **no existing hunk-level mechanism found:** rg for acceptHunk/undoHunk/reviewedHunk/per-hunk under src/vs/sessions turned up nothing; the gap is real, not a documentation or discovery issue.
