# Issue #276997 — More information in `AuthenticationSessionsChangeEvent` would be helpful

[https://github.com/microsoft/vscode/issues/276997](https://github.com/microsoft/vscode/issues/276997)

## Summary

The consumer authentication event still exposes only the provider, so the requested cache-invalidation information remains missing. Keep this team-authored Backlog request open for API design; the discussion identifies unresolved account-versus-session semantics, not a completed implementation or a scope rejection.

## Change summary

Expose change categories and affected account identities in AuthenticationSessionsChangeEvent so consumers can invalidate authentication caches selectively.

## Best solution

Define a backward-compatible consumer event contract that supplies useful account-change hints without promising scope precision Microsoft authentication cannot reliably provide. Settle how account-preference changes and provider-specific session semantics appear in that contract before implementation.

- **Behavior:**

  > Consumers of authentication.onDidChangeSessions currently receive the provider identity but cannot tell which account-related cache entries need invalidation. The requested outcome is useful change-category and affected-account information without requiring a full cache reset for every notification. Acceptance should cover additions, removals, changes, and provider-specific limitations while preserving existing provider-only consumers. The contract must also explain notifications caused by an extension's account preference changing rather than provider sessions changing.
- **Trace:**

  > AuthenticationSessionsChangeEvent in src/vscode-dts/vscode.d.ts contains only provider, whereas the provider-facing AuthenticationProviderAuthenticationSessionsChangeEvent already contains session delta arrays. MainThreadAuthentication forwards provider identity through $onDidChangeAuthenticationSessions, and ExtHostAuthentication.getExtensionScopedSessionsEvent exposes only that identity after extension filtering. The same RPC also carries account-preference notifications, so not every consumer notification has a provider session delta. MsalAuthProvider in extensions/microsoft-authentication/src/node/authProvider.ts deliberately models these events as account changes, not accurate scope-specific session changes; this matches the concern at https://github.com/microsoft/vscode/issues/276997#issuecomment-3523901830. Preserve existing authentication consent, extension filtering, and provider behavior; this request does not establish a need to expose tokens or redesign token acquisition. The uncertainty is the public meaning of account/session changes and how notifications without granular information are represented.
- **Open decisions:**
  - Should the consumer contract describe account-level changes only, or also expose provider-dependent session or scope detail with explicitly limited guarantees?
  - How should extension account-preference changes and notifications lacking precise deltas be represented so consumers know whether selective or full invalidation is appropriate?
