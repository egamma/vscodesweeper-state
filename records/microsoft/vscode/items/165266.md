# Issue #165266 — [folidng] python ranges unfold when the folding ranges are coming late

[https://github.com/microsoft/vscode/issues/165266](https://github.com/microsoft/vscode/issues/165266)

## Summary

The startup unfolding defect remains in current source: restored collapsed ranges are merged first with indentation ranges, and a same-start range with a different end can lose its collapsed state before the delayed language provider arrives. This older report should remain open; the newer matching report should be consolidated here rather than making this re-reviewed item its duplicate.

## Change summary

Preserve restored folds when a delayed language folding provider replaces temporary indentation-based ranges of a different size.

## Best solution

Preserve the persisted collapsed state across the startup transition from indentation folding to a delayed language provider without preventing intentional unfolding after real document edits. Keep this older issue as the canonical report and consolidate the detailed investigation from https://github.com/microsoft/vscode/issues/194806 into it.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/folding/browser/folding.ts`, `src/vs/editor/contrib/folding/browser/foldingRanges.ts`, `src/vs/editor/contrib/folding/test/browser/foldingRanges.test.ts`
- **Validation:** Add a folding regression test that restores a collapsed provider range, processes a smaller same-start indentation range, then processes the delayed original provider range; the range must remain collapsed throughout, while the selected policy for recalculation after an actual document edit is covered separately.
- **Behavior:**

  > After reopening an editor, a previously collapsed range must remain collapsed while the language folding provider starts. Replacing temporary indentation ranges with delayed language-provider ranges must not visibly unfold the user's restored code merely because the ranges have different end lines. Folding recalculation after an actual edit must continue to follow the explicitly chosen edit behavior.
- **Trace:**

  > FoldingController.restoreViewState in src/vs/editor/contrib/folding/browser/folding.ts reapplies the persisted collapse memento. FoldingController.getRangeProvider initially falls back to IndentRangeProvider and later reruns when a language folding provider registers. FoldingModel.update passes the incoming and currently folded ranges to FoldingRegions.sanitizeAndMerge in src/vs/editor/contrib/folding/browser/foldingRanges.ts; its same-start merge clears collapse when end lines differ and the selection intersects the incoming range. That condition reproduces the maintainer-described Pylance case in current source. The matching investigation at https://github.com/microsoft/vscode/issues/194806 is newer and should feed this older canonical issue. Preserve ordinary user folding controls and avoid globally retaining obsolete folds after edits unless the maintainer explicitly chooses that behavior.
- **Open decisions:**
  - Should a same-start, different-end range preserve collapse only during startup/provider handoff before user interaction, or also during ordinary provider recalculation after document edits?
  - When persisted provider state exists but its provider has not registered yet, should VS Code display indentation folding immediately or defer that fallback to avoid a visible intermediate folding state?

## Evidence

- **current source:** src/vs/editor/contrib/folding/browser/folding.ts restores collapsed regions in FoldingController.restoreViewState, initially selects IndentRangeProvider when no language provider is registered, and later recalculates when foldingRangeProvider.onDidChange fires.
- **defect path:** src/vs/editor/contrib/folding/browser/foldingRanges.ts in FoldingRegions.sanitizeAndMerge preserves a collapsed same-start range only when the end line is unchanged or the selection is outside the incoming range; the different-sized indentation range can therefore clear the restored collapse before the language provider arrives.
- **maintainer diagnosis:** Maintainer comments on https://github.com/microsoft/vscode/issues/165266 identify the transition from smaller indentation ranges to delayed Pylance ranges and state that it is ideally not supposed to unfold.
- **matching newer report:** https://github.com/microsoft/vscode/issues/194806 is open and documents the same observable startup expansion with delayed LSP folding providers and different-sized fallback ranges. It was created after this issue, so it cannot be the canonical duplicate target under the re-review rule.
