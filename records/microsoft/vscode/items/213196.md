# Issue #213196 — workbench.explorer.fileView.toggleVisibility does not work

[https://github.com/microsoft/vscode/issues/213196](https://github.com/microsoft/vscode/issues/213196)

## Summary

The no-op is present on current main: VS Code registers the file-view toggle command while permanently disabling it through the Explorer descriptor. The existing bug classification should stand while maintainers decide whether this command should toggle the Explorer container or cease being exposed as a usable command.

## Change summary

Running `workbench.explorer.fileView.toggleVisibility` silently does nothing even though its generated command metadata promises to toggle the Files view.

## Best solution

Eliminate the silent command-contract mismatch: either give this command meaningful Explorer visibility semantics or stop exposing it as a toggle and direct users to `workbench.action.toggleSidebarVisibility` for hiding the Primary Side Bar.

## Plan brief

- **Likely files:** `src/vs/workbench/services/views/browser/viewDescriptorService.ts`, `src/vs/workbench/contrib/files/browser/explorerViewlet.ts`, `src/vs/workbench/services/views/test/browser/viewDescriptorService.test.ts`
- **Validation:** Add a view-action unit test covering a descriptor with `canToggleVisibility: false`, asserting the chosen command contract and that invoking the exposed command cannot silently leave visibility unchanged.
- **Behavior:**

  > A command presented as toggling the Explorer Files view must not silently do nothing. Its name, availability, and result must agree: either invoking it changes the intended visible surface, or it is not exposed as an actionable toggle. Existing visibility commands for genuinely toggleable views must remain unchanged.
- **Trace:**

  > `ViewDescriptorService.registerViewsVisibilityActionsForContainer` in `src/vs/workbench/services/views/browser/viewDescriptorService.ts` registers a `.toggleVisibility` action for every active local view, while deriving a permanently false precondition for descriptors whose `canToggleVisibility` is false. `ExplorerViewlet.createExplorerViewDescriptor` in `src/vs/workbench/contrib/files/browser/explorerViewlet.ts` gives `workbench.explorer.fileView` exactly that non-toggleable state. The generic action would otherwise call `ViewPaneContainer.toggleViewVisibility`, while the separate `workbench.action.toggleSidebarVisibility` command in `src/vs/workbench/browser/actions/layoutActions.ts` already controls the whole Primary Side Bar. Preserve generic toggling for toggleable views and do not alter Explorer focus-command behavior. The uncertainty begins at the intended public behavior for a fixed primary view: hiding only the Folders view may violate the container invariant, while toggling the whole sidebar changes the command's apparent scope.
- **Open decisions:**
  - Should `workbench.explorer.fileView.toggleVisibility` toggle the whole Explorer/Primary Side Bar, or should non-toggleable views have no exposed `.toggleVisibility` command?

## Evidence

- **source reproduction:** `src/vs/workbench/services/views/browser/viewDescriptorService.ts` registers `${viewDescriptor.id}.toggleVisibility` for every active local view, but its precondition is always false when `canToggleVisibility` is false.
- **Explorer descriptor:** `src/vs/workbench/contrib/files/browser/explorerViewlet.ts` assigns `workbench.explorer.fileView` to the Folders view and explicitly sets `canToggleVisibility: false`, reproducing the reported no-op on current main.
- **existing partial alternative:** `src/vs/workbench/browser/actions/layoutActions.ts` registers `workbench.action.toggleSidebarVisibility` as “Toggle Primary Side Bar Visibility”; it can hide the Explorer container but does not provide the file-view-specific behavior implied by the reported command.
