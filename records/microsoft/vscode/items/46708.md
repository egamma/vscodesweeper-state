# Issue #46708 — [folding] blocked while language server is starting up

[https://github.com/microsoft/vscode/issues/46708](https://github.com/microsoft/vscode/issues/46708)

## Summary

The gap remains on current main: automatic folding waits for a registered language provider to finish, leaving folding unavailable during language-server startup. This team-authored request should stay open while maintainers choose how to provide responsive startup folding without reintroducing fold flicker or lost collapsed state.

## Change summary

Keep folding controls usable while a language server-backed folding provider is still starting or computing ranges.

## Best solution

Define a startup behavior that permits immediate folding while preserving user-created and restored collapsed regions when authoritative syntax ranges arrive. The design should reconcile temporary and syntax ranges without reviving the regressions documented in the linked folding issues.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/folding/browser/folding.ts`, `src/vs/editor/contrib/folding/browser/syntaxRangeProvider.ts`, `src/vs/editor/contrib/folding/test/browser/syntaxFold.test.ts`, `src/vs/editor/contrib/folding/test/browser/foldingModel.test.ts`
- **Validation:** Add an editor folding test with a delayed FoldingRangeProvider: folding must be usable before the provider promise resolves, and resolving it must preserve the user's collapsed state without transiently expanding the region.
- **Behavior:**

  > With automatic folding enabled and a registered folding provider still starting or computing, users can operate available fold controls without waiting for that provider. A fold performed during startup remains folded when authoritative syntax ranges arrive, without unrelated folds expanding or flickering. Providers that answer immediately and the explicit indentation folding strategy retain their existing behavior.
- **Trace:**

  > FoldingController.getRangeProvider in src/vs/editor/contrib/folding/browser/folding.ts selects SyntaxRangeProvider whenever any provider is registered. SyntaxRangeProvider.compute in src/vs/editor/contrib/folding/browser/syntaxRangeProvider.ts waits for Promise.all across provider calls and consults IndentRangeProvider only after every provider returns no ranges, which leaves the model without usable ranges while a language-server request is pending. TypeScriptFoldingProvider in extensions/typescript-language-features/src/languageFeatures/folding.ts demonstrates the startup path by awaiting getOutliningSpans from the TypeScript server. The opposite ordering previously caused collapsed ranges to be replaced or expanded, as documented in https://github.com/microsoft/vscode/issues/44524 and the newer related https://github.com/microsoft/vscode/issues/194806. Preserve explicit editor.foldingStrategy='indentation', syntax-provider result semantics, and persisted folding state; the uncertainty is the observable reconciliation policy between provisional and authoritative ranges.
- **Open decisions:**
  - While an automatic syntax provider is pending, should VS Code expose provisional indentation ranges immediately and reconcile them later, or preserve the current no-replacement behavior until authoritative ranges arrive?
  - When provisional and syntax ranges differ, which user fold actions and restored collapsed states must take precedence so provider arrival never unexpectedly expands content?

## Evidence

- **current source:** In src/vs/editor/contrib/folding/browser/folding.ts, FoldingController.getRangeProvider creates SyntaxRangeProvider whenever a syntax provider is registered, passing IndentRangeProvider only as its fallback.
- **blocking path:** In src/vs/editor/contrib/folding/browser/syntaxRangeProvider.ts, SyntaxRangeProvider.compute waits for collectSyntaxRanges, which uses Promise.all over every registered provider; indentation fallback runs only after all providers finish and collectively return no ranges. A pending provider therefore blocks the initial folding model.
- **language-server path:** extensions/typescript-language-features/src/languageFeatures/folding.ts registers TypeScriptFoldingProvider immediately, while provideFoldingRanges awaits client.execute('getOutliningSpans', ...), so language-server startup can directly delay folding.
- **existing workaround:** The setting editor.foldingStrategy='indentation', registered in src/vs/editor/common/config/editorOptions.ts, avoids language providers entirely. It is only a workaround because it gives up language-specific folding rather than satisfying the requested automatic startup behavior.
- **design history:** https://github.com/microsoft/vscode/issues/44524 records that waiting for syntax folding avoided replacing early indentation ranges and losing collapsed state, but its final comment explicitly identifies the resulting unresponsive collapse button and links this issue.
- **related issue:** https://github.com/microsoft/vscode/issues/194806 remains open and documents the complementary problem where a provider registered later replaces indentation ranges and expands restored folds. It is newer than this re-reviewed issue and reports a different observable symptom, so it is related design evidence rather than a valid duplicate canonical.
