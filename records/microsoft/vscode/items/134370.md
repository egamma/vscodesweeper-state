# Issue #134370 — Git - Merge Conflict - Accept All Incoming/Current - Multiple Repositories

[https://github.com/microsoft/vscode/issues/134370](https://github.com/microsoft/vscode/issues/134370)

## Summary

A real gap remains on current main: the command-palette action is document-scoped and silently returns when no editor is active, so it cannot resolve conflicts for a chosen repository in a multi-repository workspace. The SCM multi-selection path has separate resource handling, but the report indicates that path also needs runtime coverage across repositories.

## Change summary

Accept All Incoming/Current does nothing when invoked for conflicts in a workspace containing multiple Git repositories.

## Best solution

Give the command-palette action an explicit multi-repository behavior rather than silently depending on the active editor, likely by selecting the intended repository and applying the operation to its conflicted resources. Preserve the existing SCM behavior where the action applies only to the resources the user selected.

## Plan brief

- **Likely files:** `extensions/merge-conflict/src/commandHandler.ts`, `extensions/merge-conflict/package.json`
- **Validation:** Using a multi-root fixture with two Git repositories containing conflicted files, invoke Merge Conflict: Accept All Incoming from the command palette with no conflicted file active and verify that the chosen repository's conflicts are resolved; separately multi-select conflicted resources in SCM and verify only those resources are changed.
- **Behavior:**

  > In a workspace containing multiple Git repositories, invoking Accept All Incoming or Accept All Current must not silently do nothing. The command-palette flow must make its target repository or document explicit and apply the selected side consistently. Invoking the action from an SCM multi-selection must affect every selected conflicted resource, including resources in nested repositories, without changing unselected files.
- **Trace:**

  > In extensions/merge-conflict/src/commandHandler.ts, registerTextEditorCommand routes SCM arguments carrying resourceUri to acceptAllResources, but every other invocation falls back to vscode.window.activeTextEditor. With no active editor it returns silently; with an editor, acceptAll scans only that editor.document, so no repository can be inferred or selected. Commit 039a49a5eab688800b0226cf2c4addc797c94a86 added the multi-resource WorkspaceEdit path for https://github.com/microsoft/vscode/issues/63621, but did not address command-palette behavior in multi-repository workspaces. Keep single-document CodeLens behavior and explicitly selected SCM-resource scope unchanged; the uncertainty begins at the command-palette target semantics.
- **Open decisions:**
  - When invoked from the command palette in a multi-repository workspace, should Accept All operate on the active conflicted document or prompt for a repository and resolve all conflicted resources in that repository?

## Evidence

- **current source path:** extensions/merge-conflict/src/commandHandler.ts registers merge-conflict.accept.all-current and merge-conflict.accept.all-incoming through registerTextEditorCommand; without SCM resource arguments it uses only vscode.window.activeTextEditor and silently returns when no editor exists. acceptAll then scans only editor.document, so the command palette has no repository-selection or repository-wide path.
- **maintainer diagnosis:** https://github.com/microsoft/vscode/issues/134370#issuecomment-1351355187 identifies the missing repository quick pick as a bug, while https://github.com/microsoft/vscode/issues/134370#issuecomment-1417080195 confirms that the built-in merge-conflict extension currently operates at document level.
