# Issue #299373 — Source Control fails to track real-time changes on non-system drives (Windows/Linux) since v1.109.5

[https://github.com/microsoft/vscode/issues/299373](https://github.com/microsoft/vscode/issues/299373)

## Summary

Keep open for investigation of Git status updates after saves on secondary drives. The discussion confirms persistence through 1.111.0, but the quoted virtual-file warnings do not establish the cause, and no verified fix or eligible canonical duplicate was found.

## Change summary

Source Control should detect saved modifications and newly created files on secondary drives without requiring a window reload.

## Best solution

Restore automatic working-tree status updates in the built-in Git integration, first distinguishing missing filesystem events from skipped status refreshes or hidden repository selection. Diagnose the reported secondary-drive scenario on a current build before choosing a fix.

## Plan brief

- **Likely files:** `extensions/git/src/repository.ts`, `extensions/git/src/fileSystemProvider.ts`, `extensions/git/src/uri.ts`
- **Validation:** On a current Windows build with extensions disabled and git.autorefresh enabled, open a small repository on D:, modify and save a tracked file, then create and save an untracked file. With the window focused and Git idle, both must appear automatically in Source Control without Reload Window or Git: Refresh. Repeat on C: as a control and on the reported Linux secondary partition; capture Git debug/trace events and status invocations to locate any failure.
- **Behavior:**

  > The reported failure is that saved modifications and new files in a repository on a secondary drive do not update Source Control, although reloading the window discovers them. Automatic refresh should show both modified and untracked files without a reload when git.autorefresh is enabled and the repository is eligible for automatic refresh. Reproduce on a current build using a small repository and compare a system-drive repository. Preserve intentional behavior when automatic refresh is disabled.
- **Trace:**

  > Repository construction in extensions/git/src/repository.ts creates a RelativePattern watcher for the repository root and routes working-tree change/create/delete events into Repository.onFileChange. That method can skip refresh for disabled autorefresh, huge repositories, or active operations; its scheduled status path also waits for window focus. FileEventLogger in the same file exposes working-tree events at debug level, allowing event delivery to be distinguished from status scheduling. The supplied warnings arise in extensions/git/src/fileSystemProvider.ts while reading Git objects, and extensions/git/src/uri.ts retrieves physical paths from the JSON query; those warnings do not establish a drive-mapping defect. The uncertainty starts at whether current builds lose filesystem events, skip status updates, or detect changes that the view does not display. https://github.com/microsoft/vscode/issues/302846 is related but newer and also affects C:, while https://github.com/microsoft/vscode/issues/275281 illustrates a distinct repository-selection cause. Do not change virtual Git content semantics or intentional refresh exclusions without evidence that they cause the reported failure.

## Evidence

- **Reported reproduction and confirmation:** https://github.com/microsoft/vscode/issues/299373 describes saving modified or new files with extensions disabled, seeing no SCM update, and recovering the initial status after Reload Window. The reporter confirmed persistence on 1.110.0, and yibo2023 independently reported persistence on 1.111.0. This establishes discussion-confirmed reproduction, not a current-main execution.
- **Current automatic-refresh path:** extensions/git/src/repository.ts:930-957 creates a filesystem watcher rooted at Uri.file(repository.root), merges change/create/delete events, and connects working-tree events to Repository.onFileChange. At lines 3334-3385, refresh depends on git.autorefresh, repository size, operation state, and window focus before status() runs. This identifies the investigation path but does not conclusively expose a secondary-drive defect.
- **Warnings do not prove URI mapping failure:** extensions/git/src/uri.ts preserves the physical fsPath in the JSON query and fromGitUri parses that query. GitFileSystemProvider.stat and readFile in extensions/git/src/fileSystemProvider.ts read Git objects; their File not found branches explicitly include untracked or ignored files. Consequently, the supplied git:/d%3A/... warnings alone do not prove broken physical-drive mapping or explain missing watcher events.
- **Existing refresh controls:** extensions/git/package.json registers git.refresh and sets git.autorefresh to true by default. Manual refresh is an investigative comparison, not a replacement for the requested automatic updates.
