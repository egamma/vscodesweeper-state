# Issue #340170 — New "Agent Harness" spins up research sub-agents with unexpected models

[https://github.com/microsoft/vscode/issues/340170](https://github.com/microsoft/vscode/issues/340170)

## Summary

Traced a real architectural gap that matches the report: the new agent harness's search/execution subagents resolve their model via a separate, independently-configured setting (ConfigKey.Advanced.SearchSubagentModel / ExecutionSubagentModel) rather than the model the user picked in the dropdown, and unlike the utility-model path, this subagent resolution path has no BYOK-awareness check — so a BYOK/OpenRouter user's subagents can end up calling a different provider/model than they selected. Keeping open pending maintainer product decision; not closing since the exact OpenRouter-specific chain (why Anthropic specifically) isn't fully nailed down from source alone.

## Change summary

User's OpenRouter billing shows unexpected, more expensive Anthropic model calls after VS Code switched them to the new Agent Harness, which they attribute to 'research' subagents silently using different models than the one selected in the model picker.

## Best solution

Either make execution/search subagent model resolution BYOK-aware (mirroring the `_mainAgentBYOKModel` check already done for utility models in `endpointProviderImpl.ts`'s `_resolveUtilityFamily`, but missing from `_resolveFamily`), or surface this behavior and the resolved subagent model clearly to BYOK users so there are no billing surprises; a maintainer should decide which.

## Evidence

- **subagents use separately configured models:** extensions/copilot/src/extension/prompt/node/searchSubagentToolCallingLoop.ts:109-165 and executionSubagentToolCallingLoop.ts:124-160 resolve the subagent's model from ConfigKey.Advanced.SearchSubagentModel / ExecutionSubagentModel (experiment-based config, default '' / 'gemini-3-flash' respectively in platform/configuration/common/configurationService.ts:787,803), independent of the model the user selected in the chat dropdown.
- **no BYOK-awareness in subagent model resolution:** endpointProviderImpl.ts's _resolveFamily (line 175) — used by subagent model-name/family lookups — calls this._modelFetcher.getChatModelFromCapiFamily(family) unconditionally, with no check of this._mainAgentBYOKModel. Contrast with _resolveUtilityFamily (line 198), which explicitly branches on `this._mainAgentBYOKModel` and a BYOKUtilityModelDefault policy before falling back to a CAPI family. This asymmetry is consistent with BYOK users getting an unexpected, non-user-selected model/provider for subagent calls.
- **fallback to main-request model exists but may use stale request:** On any resolution failure, both loops fall back to `this.endpointProvider.getChatEndpoint(this.options.request)` — the model attached to the subagent-invoking request object, not necessarily the live dropdown selection at invocation time.
- **existing debug logging partially answers reporter's second question:** extension/chat/vscode-node/chatDebugFileLoggerService.ts and the OTel trace/export tooling (extension/trajectory/vscode-node/otelSpanToChatDebugEvent.ts, docs/monitoring/agent_monitoring.md) already attach modelName per subagent call and can be exported via the prompt-log export command, which is relevant context for a maintainer reply but doesn't address the core surprise.
