# Issue #105247 — [theme] allow variables in the color theme definition file

[https://github.com/microsoft/vscode/issues/105247](https://github.com/microsoft/vscode/issues/105247)

## Summary

The capability remains a valid, unimplemented theme-authoring request. A maintainer explicitly welcomed a contribution and sketched the parser entry point, but the public color-reference syntax and whether settings should share it still require design agreement.

## Change summary

Allow color theme files to define reusable palette variables and reference them from workbench, token, and semantic-token color rules.

## Best solution

Design one validated palette/reference format for theme JSON, resolve references while loading themes in `colorThemeData.ts`, and preserve existing literal color behavior and diagnostics. Decide explicitly whether the initial contract is theme-file-only or shared with user color customizations.

## Plan brief

- **Likely files:** `src/vs/workbench/services/themes/common/colorThemeData.ts`
- **Validation:** Add theme service tests that load a fixture with palette references across `colors`, `tokenColors`, and semantic-token colors, assert the resolved colors, and verify literal-color themes and invalid-reference diagnostics remain unchanged.
- **Behavior:**

  > A color theme can declare named colors once and reference them from its workbench, TextMate token, and semantic-token color definitions. References resolve consistently, while themes containing only literal colors behave exactly as before. Undefined references, cycles, and invalid color results must produce clear validation behavior rather than silently yielding an incorrect theme. Acceptance includes fixture-based theme loading tests for valid references and malformed palettes.
- **Trace:**

  > Theme JSON is loaded through `src/vs/workbench/services/themes/common/colorThemeData.ts`, the entry point identified by the area maintainer in https://github.com/microsoft/vscode/issues/105247#issuecomment-1245050823. The same maintainer favored a parser constructed from the palette and `$variable` or `${variable}` references in https://github.com/microsoft/vscode/issues/105247#issuecomment-1246409229, but the final public syntax was never settled. https://github.com/microsoft/vscode/pull/199091 is a closed, unmerged implementation attempt and must be treated as design evidence, not as a fix. Preserve backward compatibility for existing theme JSON and keep runtime theme consumers outside the parsing contract unchanged. The related settings request at https://github.com/microsoft/vscode/issues/56855 raises a scope choice but does not subsume this theme-file request.
- **Open decisions:**
  - What public palette declaration and reference syntax should theme authors rely on: `$name`, `${name}`, or another explicitly versioned form?
  - Should the first contract apply only to contributed color-theme files, or also define shared behavior for user color customization settings?
  - What user-visible behavior should invalid references and reference cycles have: reject the theme, ignore the affected value with diagnostics, or use a documented fallback?
