# Issue #337336 — MCP: show effective enablement state and scope

[https://github.com/microsoft/vscode/issues/337336](https://github.com/microsoft/vscode/issues/337336)

## Summary

Fresh, team-authored feature request describing a real UX gap in the MCP servers UI — the enablement model already distinguishes global/profile/workspace overrides in code, but the UI collapses them into a generic disabled/greyed style with no scope labeling. No maintainer decision on the exact labeling scheme yet, so this stays open.

## Change summary

MCP UI doesn't show the effective enablement state and scope (e.g. globally disabled but workspace-enabled), just a generic disabled/greyed control.

## Best solution

Design and implement scope-aware enablement labels (e.g. 'Enabled (Workspace)') in the MCP servers view, driven by the existing McpServerEnablementState (Disabled/DisabledByAccess/DisabledProfile/DisabledWorkspace/Enabled) in src/vs/workbench/contrib/mcp/common/mcpTypes.ts, replacing the current binary 'disabled' class toggle in mcpServersView.ts.

## Plan brief

- **Behavior:**

  > When an MCP server's effective enablement differs across scopes (e.g. globally disabled but enabled for the current workspace), the UI shows a clear label describing the effective state and its source, such as 'Enabled (Workspace)' or 'Disabled (Global)', instead of only greying out the control. The greyed/disabled style should only be used when a control is genuinely unavailable, not to represent every 'off' state. Acceptance: server list items and session-level indicators reflect scope-aware state text that matches McpServerEnablementState.
- **Trace:**

  > McpServerEnablementState (src/vs/workbench/contrib/mcp/common/mcpTypes.ts:971) already models Disabled, DisabledByAccess, DisabledProfile, DisabledWorkspace, and Enabled, but the browser UI in mcpServersView.ts:502 only checks `runtimeStatus.state !== McpServerEnablementState.Enabled` to toggle a single 'disabled' CSS class — no distinct copy or styling per state. The fix must map each enablement-state value to a distinguishing label without breaking the existing 'disabled' visual for cases where the server is truly unavailable (e.g. DisabledByAccess). Where uncertainty starts: what exact label copy/format to use across the different UI surfaces (list view item, session/chat view badge), and whether all four disabled substates need distinct visible text or only workspace-vs-global distinction as the issue's repro emphasizes.
- **Open decisions:**

  - Should DisabledByAccess and DisabledProfile get their own distinct visible labels, or just be grouped as 'Disabled' with workspace/global being the only distinction called out?
