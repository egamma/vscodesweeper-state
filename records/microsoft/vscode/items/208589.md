# Issue #208589 — Switching to profile on an empty folder leaves the Explorer loading

## Change summary

Switching profiles while an empty folder is open can leave the Explorer indefinitely showing a loading state instead of the empty folder.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/browser/explorerService.ts`, `src/vs/workbench/services/userDataProfile/browser/userDataProfileManagement.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Open an empty folder, switch to another profile, and verify that the Explorer finishes loading and renders the empty-folder state; repeat while the Explorer is both visible and initially hidden, and confirm a second profile switch also settles.
- **Behavior:**

  > With an empty folder open, switching to another profile must leave the Explorer usable and showing the normal empty-folder state. The Explorer progress indicator must finish, and later refreshes or profile switches must not wait indefinitely. Non-empty folders and ordinary workspace-root changes must retain their existing behavior.
- **Trace:**

  > Profile switching runs through `UserDataProfileManagementService.changeCurrentProfile` in src/vs/workbench/services/userDataProfile/browser/userDataProfileManagement.ts, which stops extension hosts, updates the profile, and restarts the hosts. Explorer input and progress are coordinated by `ExplorerView.setTreeInput` in src/vs/workbench/contrib/files/browser/views/explorerView.ts; it stores the `tree.setInput` operation in `setTreeInputPromise`, exposes that promise as Explorer progress, and makes later input and selection work await it. ExplorerService in src/vs/workbench/contrib/files/browser/explorerService.ts requests new tree input for root and filesystem-provider changes, but neither it nor ExplorerView directly observes current-profile changes. The issue's video and maintainer-applied `confirmed` label establish the behavior, but source inspection alone does not identify which event or unresolved tree operation creates the persistent loading state. Keep the investigation bounded to profile switching and Explorer input/progress lifecycle; do not alter general extension-host restart semantics or unrelated tree refresh behavior.

## Evidence

- **confirmed report:** The issue contains a video reproduction and was explicitly labeled `confirmed` and `bug` by a maintainer on 2024-12-16; it remains open in the Backlog milestone.
