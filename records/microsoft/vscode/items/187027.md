# Issue #187027 — [wsl] support undo after deleting directory

[https://github.com/microsoft/vscode/issues/187027](https://github.com/microsoft/vscode/issues/187027)

## Summary

Keep open: current Explorer undo does not preserve a deleted directory's contents. The older remote-trash request is related, but restoring from trash does not necessarily deliver the Ctrl+Z recovery requested here.

## Change summary

Support restoring a deleted WSL directory and its contents through Explorer undo.

## Best solution

Provide a supported directory-recovery contract for Explorer undo on WSL, coordinated with remote-trash work. Establish recovery limits and failure behavior before extending the shared bulk-file undo infrastructure.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/fileActions.ts`, `src/vs/workbench/contrib/bulkEdit/browser/bulkFileEdits.ts`, `src/vs/workbench/services/workingCopy/common/workingCopyFileService.ts`
- **Validation:** In a disposable WSL workspace, create a directory containing nested directories and text/binary files, delete it through Explorer, and invoke Ctrl+Z with Explorer focused. Verify restoration of the tree and byte-identical contents, then verify redo and the chosen oversized-directory/failure behavior; existing individual-file undo must remain unchanged.
- **Behavior:**

  > Deleting a populated directory in a WSL workspace currently leaves its contents unavailable to Explorer undo, unlike supported individual-file deletions. The requested outcome is Ctrl+Z restoration of the directory tree and its file contents. Acceptance must cover nested directories, empty directories, binary contents, and redo. Recovery limits and the user-visible outcome when recovery cannot be guaranteed need an explicit product contract.
- **Trace:**

  > Explorer deleteFiles in src/vs/workbench/contrib/files/browser/fileActions.ts sends one recursive ResourceFileEdit per selected directory with folder: true and a 5 MB file-undo limit. DeleteOperation.perform in src/vs/workbench/contrib/bulkEdit/browser/bulkFileEdits.ts captures contents only for non-folder edits; its inverse CreateEdit retains no descendant tree. CreateOperation.perform consequently recreates the directory alone through IWorkingCopyFileService.createFolder. This was traced read-only, not executed. Preserve individual-file undo, existing confirmation behavior, and other bulk-file consumers unless the approved recovery contract requires a change. https://github.com/microsoft/vscode/issues/108731 concerns remote trash and contains corroborating folder-recovery reports, but manual trash recovery alone does not settle this Ctrl+Z requirement. The unresolved boundary is the supported recursive recovery contract, including limits and failures, rather than a particular helper or patch location.
- **Open decisions:**
  - What directory size or entry-count limits, if any, should apply to recursive undo, and what should users see before deleting a directory outside those limits?
  - If complete recovery cannot be guaranteed before deletion, should deletion proceed with an explicit irreversible-operation warning or be refused?
