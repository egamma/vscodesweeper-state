## Summary

The folder-versus-multi-root difference exposes the same spurious Yarn detection already tracked by an open canonical issue. Its discussion explicitly covers npm workspaces opened below the repository root and identifies the same detection heuristic.

## Change summary

Running the same npm workspace script selects npm or Yarn depending on which directory VS Code treats as the workspace folder.

## Evidence

- **Verified open canonical:** https://github.com/microsoft/vscode/issues/170101 is OPEN. Its comment https://github.com/microsoft/vscode/issues/170101#issuecomment-1411643321 reports npm workspaces incorrectly running scripts through Yarn when VS Code is opened below the monorepo root.
- **Same diagnosed root cause:** https://github.com/microsoft/vscode/issues/170101#issuecomment-1437978598 identifies find-yarn-workspace-root treating the shared package.json workspaces field as Yarn evidence. This matches the present report, including the absence of Yarn-specific project metadata.
- **Current source trace:** extensions/npm/src/tasks.ts:createScriptRunnerTask computes cwd from packageJsonUri but passes folder.uri to getRunScriptCommand. getScriptRunner auto-detects through findPreferredPM; extensions/npm/src/preferred-pm.ts checks package-lock.json only locally, while isYarnPreferred accepts an ancestor workspace returned by find-yarn-workspace-root. Consequently, changing the workspace folder to packages/cli removes local npm lockfile evidence while retaining the Yarn heuristic.
- **Existing implementation candidate:** https://github.com/microsoft/vscode/pull/243250 is OPEN and explicitly fixes https://github.com/microsoft/vscode/issues/170101 by removing the inference that a workspaces field implies Yarn. Its description specifically addresses multi-workspace packages without yarn.lock; it has not established a completed fix.
- **Related reports and workaround:** https://github.com/microsoft/vscode/issues/261630 concerns detection using the wrong directory, but the canonical above also owns this report's false Yarn inference. Current getScriptRunner reads npm.scriptRunner independently of npm.packageManager; setting npm.scriptRunner to npm is a workaround, not a correction of automatic detection.
