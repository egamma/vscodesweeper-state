[https://github.com/microsoft/vscode/issues/345640](https://github.com/microsoft/vscode/issues/345640)

## Summary

The older, open canonical already includes npm workspace scripts incorrectly switching to yarn when opened below the repository root. This report provides a useful multi-root reproduction of that same behavior.

## Change summary

Npm workspace scripts unexpectedly run through yarn when their package becomes a separate VS Code workspace folder.

## Evidence

- **Verified canonical:** https://github.com/microsoft/vscode/issues/170101 is currently open and was created on 2022-12-27. Its discussion explicitly reports npm workspaces executing package.json tasks through yarn when VS Code is opened below the monorepo root: https://github.com/microsoft/vscode/issues/170101#issuecomment-1411643321. This establishes the same reporter-observable symptom, not merely a related detection problem.
- **Current source trace:** extensions/npm/src/tasks.ts:createScriptRunnerTask computes the execution cwd from packageJsonUri but passes folder.uri to getRunScriptCommand. getScriptRunner delegates auto detection to findPreferredPM. In extensions/npm/src/preferred-pm.ts, isNPMPreferred checks only the local package-lock.json, while isYarnPreferred accepts an ancestor workspace returned by find-yarn-workspace-root without requiring a yarn.lock.
- **Reproduction boundary:** The supplied https://github.com/Praynia/vscode-npm-scripts-yarn-repro contains a root package.json with workspaces and a repro.code-workspace listing both '.' and 'packages/cli'. Consequently the nested package's workspace-folder detection base changes between opening modes while its script cwd remains unchanged. This exposes the same ancestor-workspaces yarn heuristic diagnosed at https://github.com/microsoft/vscode/issues/170101#issuecomment-1437978598. No code was executed.
- **Existing fix candidate:** https://github.com/microsoft/vscode/pull/243250 is open and explicitly fixes the canonical issue by removing yarn detection based solely on the shared workspaces field. It is not a landed fix and does not justify a completed close.
- **Workaround distinction:** extensions/npm/src/tasks.ts:getScriptRunner reads npm.scriptRunner independently of getPackageManager. Setting npm.scriptRunner to npm controls script execution; npm.packageManager alone does not. This report's clarification should accompany consolidation.
