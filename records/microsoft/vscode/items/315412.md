## Change summary

Copilot Chat reportedly remains unusable after transient network failures during Windows host resume, requiring a window reload.

Confirm recovery after Windows/WSL resume in Copilot's authentication and model-discovery paths, distinguishing temporary network failure from remote extension-host disconnection. Coordinate with the existing retry PR and ensure restored connectivity makes Chat usable without reloading, rather than assuming pool replacement alone solves the problem.

## Evidence

- **Concrete reported scenario:** https://github.com/microsoft/vscode/issues/315412 identifies Windows 10 with WSL2 Ubuntu, host sleep/resume, per-window failure, reload-based recovery, and EAI_AGAIN/ECONNRESET/token-fetch signatures. These support retesting, but aggregate request failures do not independently establish permanently stuck UI state or the proposed undici root cause.
- **Current token failure handling:** extensions/copilot/src/platform/authentication/node/copilotTokenManager.ts: BaseCopilotTokenManager.doAuthFromGitHubTokenOrDevDeviceId converts thrown fetch errors into RequestFailed. extensions/copilot/src/platform/authentication/vscode-node/copilotTokenManager.ts: VSCodeCopilotTokenManager.getCopilotToken clears its cached token and rethrows on failure, allowing a later call to fetch again. This supports investigating recovery scheduling, not asserting permanent token-manager lockout.
- **Current model-discovery behavior:** extensions/copilot/src/platform/endpoint/node/modelMetadataFetcher.ts: _fetchModels records token-acquisition failures in _lastFetchError and sets _lastFetchTime to the current time; model-request failures instead reset _lastFetchTime to zero. _shouldRefreshModels applies an active-window and ten-minute refresh condition. These are relevant recovery paths, but inspection alone does not prove the reported indefinite failure.
- **Existing fallback is not delayed recovery:** extensions/copilot/src/platform/networking/node/fetcherFallback.ts: fetchWithFallbacks tries available backends when retryFallbacks is enabled and throws the first error if all fail. Disconnect-and-retry handling targets network-process crashes; the inspected path does not establish delayed recovery from a WSL DNS outage affecting every backend.
- **Related open implementation:** https://github.com/microsoft/vscode-copilot-chat/pull/4594 is currently OPEN and unmerged. It addresses graceful HTTP/2 GOAWAY and transient Electron-network retries, partially overlapping this report but not establishing recovery of silent authentication/model discovery after EAI_AGAIN. Its closingIssuesReferences list is empty; it is a related candidate, not a landed fix.
- **Later authentication changes are not proof of this fix:** Commit https://github.com/microsoft/vscode/commit/88d87414a09ebd952b1ee37c6410fc2adafb5dea changes rate-limit handling and shared fetched-value caching. Its inspected diff does not demonstrate that the report's suspend-triggered, permanent Chat failure is resolved.
- **Canonical search:** Searches for Copilot sleep, EAI_AGAIN, token refresh, reconnect, and network recovery found no verified canonical owning this exact failure. https://github.com/microsoft/vscode/issues/332379 concerns invalid-token recovery rather than transient DNS failure; https://github.com/microsoft/vscode/issues/253137 and https://github.com/microsoft/vscode/issues/253136 are broad error meta issues without an established matching root cause. The reporter's historical reference https://github.com/microsoft/vscode-copilot-release/issues/5644 describes similar token-fetch failures but does not establish a current canonical or fix.
