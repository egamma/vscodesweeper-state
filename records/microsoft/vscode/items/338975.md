# Issue #338975 — Delegate Copilot plugin installation to the Copilot SDK

[https://github.com/microsoft/vscode/issues/338975](https://github.com/microsoft/vscode/issues/338975)

## Summary

Fresh, well-diagnosed architecture proposal (0 days old) from a frequent contributor, confirmed from source: the Chat Customizations UI (customizationMarketplaceInstallService.ts) still uses IPluginInstallService while Agent Host /plugin commands (merged in PR #338982) go through the Copilot SDK's session.rpc.plugins — two independent install/enablement stores as described. This is a real, unaddressed split worth planning, not a quick patch.

## Change summary

Make the Copilot SDK the single source of truth for Copilot plugin install/enable state, replacing the Chat Customizations UI's separate IPluginInstallService-backed inventory.

## Best solution

Design and land a provider-facing plugin-management boundary that lets the customization UI delegate install/uninstall/update/enable/disable to the SDK (acquiring the right session/account/policy context), retiring the parallel agent-plugins/installed.json state in favor of the SDK's inventory, with a migration path for existing installs.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceInstallService.ts`, `src/vs/workbench/contrib/chat/common/plugins/pluginInstallService.ts`, `src/vs/platform/agentHost/common/agentPluginManager.ts`, `src/vs/platform/agentHost/node/agentPluginManager.ts`
- **Validation:** A test asserting that installing a plugin via the customization UI's install path causes it to appear in the SDK's plugin inventory (e.g. reflected in a /plugin list equivalent query), and that a subsequent /plugin uninstall succeeds without a 'not installed' error.
- **Trace:**

  > Root cause: the Chat Customizations UI installs/uninstalls Copilot plugins via IPluginInstallService (used from customizationMarketplaceInstallService.ts), persisting to VS Code's own agent-plugins/installed.json, while Agent Host's /plugin commands call the Copilot SDK's session.rpc.plugins API (backed by agentPluginManager.ts and the generated Plugin*Params/Response protocol types under src/vs/platform/agentHost/node/codex/protocol/generated/v2/). These are two independent persistent stores with no sync, confirmed by reading both call paths; the issue also shows enable/disable state diverges the same way. Boundary: UI should keep catalog browsing/confirmation/progress/accessibility; the SDK should become canonical for install/uninstall/update/enable/disable mutations.
- **Open decisions:**
  - How does the UI (which can run without an active Agent Host session) acquire the right SDK/session context — on demand, via a background session, or another mechanism — while preserving account/policy/profile/remote context?
  - What migration path moves existing VS Code-installed Copilot plugins (agent-plugins/installed.json) into the SDK's authoritative inventory, and is it automatic or user-initiated?
  - How and when do active Agent Host sessions get refreshed after a UI-driven plugin mutation (immediately, lazily, via an event) and what is the UI's contract for reflecting SDK-driven changes (e.g. /plugin disable) without a reload?
