# Issue #347019 — allow users to save & recall window layouts & arrangements

[https://github.com/microsoft/vscode/issues/347019](https://github.com/microsoft/vscode/issues/347019)

## Summary

Existing layout controls and workspace restoration do not provide switchable, named snapshots of the whole workbench. Keep this request open for scope assessment; the verified related requests cover only portions of it.

## Change summary

Add named, recallable workbench arrangements covering views, sidebars, panels, editor groups and optionally floating windows.

## Best solution

Define a coherent saved-layout contract covering scope, automatic saving and reconciliation of open editors, while preserving today's default restoration behavior. Treat event-driven switching and extension APIs as separate follow-up scope.

## Evidence

- **Existing customization is partial:** src/vs/workbench/browser/actions/layoutActions.ts:1428 onward registers workbench.action.customizeLayout for adjusting the current layout, rather than managing named saved arrangements.
- **Editor layout commands are narrower:** src/vs/workbench/browser/parts/editor/editorCommands.ts:365-430 registers vscode.setEditorLayout and vscode.getEditorLayout for editor-group geometry. These do not capture sidebar/panel arrangements, editor membership or the requested recall policies.
- **Restoration is not named layout switching:** src/vs/workbench/browser/parts/editor/editorPart.ts:1629-1671 saves a single workspace editor UI state and exposes createState/applyState. This supports restoration infrastructure, not a user-facing collection of named whole-workbench snapshots.
- **Profiles are incomplete coverage:** src/vs/workbench/services/userDataProfile/browser/globalStateResource.ts exports profile-scoped, user-target storage. EditorPart separately persists the editor grid in workspace storage, so profile export does not supply the requested complete arrangement.
