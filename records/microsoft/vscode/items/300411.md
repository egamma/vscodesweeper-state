# Issue #300411 — runSubagent - more parameters, e.g. for model and tools

[https://github.com/microsoft/vscode/issues/300411](https://github.com/microsoft/vscode/issues/300411)

## Summary

The model parameter has since landed, but invocation-time tool selection remains a real gap with unresolved permission semantics. This team-authored issue is the canonical place to design that remaining work and should be routed to the subagents area.

## Change summary

Allow `runSubagent` callers to choose the subagent model and tool set without maintaining separate custom-agent definitions.

## Best solution

Keep the shipped `model` parameter and add a bounded tool-selection contract that always permits narrowing the parent's enabled tools, while requiring an explicit, well-defined approval flow before any invocation can expand them.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts`, `src/vs/workbench/contrib/chat/test/common/tools/builtinTools/runSubagentTool.test.ts`
- **Validation:** Extend the RunSubagentTool unit suite to verify the chosen schema and matching syntax, that requested subsets reach `IChatAgentRequest.userSelectedTools`, that omitted tools preserve current inheritance, and that attempted expansion follows the maintainer-selected approval or rejection behavior.
- **Behavior:**

  > `runSubagent` callers can select tools for one invocation without creating another custom agent. Omitting the parameter preserves current inherited or agent-defined tools, and selecting a strict subset cannot enable anything unavailable to the parent. Requests that would expand permissions must follow the explicit user-facing policy chosen by the maintainer. Existing model selection, nested-subagent depth restrictions, and forced disabling of todo/question tools remain unchanged.
- **Trace:**

  > `RunSubagentTool.getToolData()` in `src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts` currently advertises prompt, description, agentName, and model. During `invoke()`, `modeTools` starts from `invocation.userSelectedTools`; a named agent can replace it through `subagent.tools` and `toToolAndToolSetEnablementMap()`, after which runSubagent nesting and selected built-ins are further restricted before assigning `IChatAgentRequest.userSelectedTools`. The model half landed in b947d0b27f2e9157bef16de0cf664c48eaf9f3f8, so it is outside the remaining scope. The uncertainty starts at the public syntax for selecting tools and whether/how a requested superset may obtain approval; do not weaken existing parent restrictions or nesting controls.
- **Open decisions:**
  - Must invocation-time tool selection always be a subset of the parent's enabled tools, or may the caller request additional tools after explicit user approval?
  - If expansion is allowed, is approval scoped to that invocation, the current chat session, or a persistent user choice?
  - Should the public parameter accept exact tool and tool-set identifiers only, or also support regular-expression matching as requested?
