# Issue #348953 — Agents window: Progress accessibility sound loops when opening certain idle chats

[https://github.com/microsoft/vscode/issues/348953](https://github.com/microsoft/vscode/issues/348953)

## Summary

Keep open: the report provides sufficient steps to retest idle-session switching, but the affected session state has not been reproduced. Current source includes progress-signal cleanup on completion and disposal; that does not establish that reopening these chats is fixed.

## Change summary

Opening certain idle Agents-window chats starts an indefinite Progress accessibility sound loop without submitting a prompt.

## Best solution

Ensure restored idle chats remain silent while genuine operations retain progress feedback. First identify whether the sound comes from chat-request tracking or a separate progress bar, then validate the affected session-switching lifecycle.

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts`, `src/vs/workbench/contrib/chat/browser/accessibility/chatAccessibilityService.ts`, `src/vs/workbench/contrib/chat/common/model/chatModel.ts`, `src/vs/workbench/contrib/chat/test/browser/accessibility/chatAccessibilityService.test.ts`, `src/vs/base/browser/ui/progressbar/progressbar.ts`
- **Validation:** On Windows with accessibility.signals.progress.sound enabled, open an affected idle chat without sending a message, wait through multiple signal intervals, switch to an unaffected chat, and reopen the affected chat; idle chats must remain silent. Confirm a genuine long-running request still produces progress feedback and stops on completion. Once the producer is identified, add a failing regression for that lifecycle and run the targeted suite; for chat-request tracking, use scripts/test.sh --grep ChatAccessibilityService.
- **Behavior:**

  > Selecting an existing idle chat must not start repeating Progress sounds without a submitted request or another genuinely active operation. Switching away and back, reloading, and restarting must not revive stale progress feedback. A completed new reply must leave the chat silent. Genuine in-progress requests must retain their configured progress signals and stop them when work ends.
- **Trace:**

  > ChatWidget's viewModel setter in src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts calls ChatAccessibilityService.acceptRequest when the bound model reports requestInProgress. ChatModel derives that state from the last response, making restored response state a relevant diagnostic boundary. ChatAccessibilityService starts a delayed loop and observes later request-state transitions and disposal; its existing tests cover several termination paths but not this report's affected restored chats. ProgressBar.show in src/vs/base/browser/ui/progressbar/progressbar.ts independently creates the same signal, so hearing the Progress sound does not establish a chat-scheduler defect. The uncertainty starts at identifying the active producer and the state of the affected model during selection; no runtime reproduction was performed. Preserve genuine progress feedback, rerun handling, and waiting-for-input behavior rather than disabling the signal globally. https://github.com/microsoft/vscode/issues/296342 and https://github.com/microsoft/vscode/issues/250402 have different triggers and are not established duplicates.
