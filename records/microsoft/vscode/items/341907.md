# Issue #341907 — Agent Host (Claude): replies to Claude Code cross-session messages aren't shown in the chat (they're in the SDK transcript)

[https://github.com/microsoft/vscode/issues/341907](https://github.com/microsoft/vscode/issues/341907)

## Summary

Thanks for the detailed report. The Claude agent-host code drops SDK messages that arrive when no turn is active, which matches what you see for peer-initiated activity. The permission auto-deny is plausible but not fully traced. Keeping open as a real gap that needs a design decision.

## Change summary

Messages, tool calls and replies triggered by a Claude Code peer (cross-session) message are not rendered in the Agents-window chat, and any permission request they raise is silently denied as 'User declined'.

## Best solution

Treat unsolicited SDK activity (peer-origin user entries and the assistant output that follows) as an implicit turn, or surface it in the chat. Route its permission requests to the user, or report an automatic denial distinctly from a user decision.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/claude/claudeSdkMessageRouter.ts`, `src/vs/platform/agentHost/node/claude/claudeAgentSession.ts`, `src/vs/platform/agentHost/node/claude/claudeCanUseTool.ts`, `src/vs/platform/agentHost/node/claude/claudeSdkPipeline.ts`
- **Validation:** A unit test that feeds the router or pipeline a peer-origin user message plus assistant output with no active turn, and asserts that chat signals are emitted and that permission requests are not auto-denied as 'User declined'.
- **Behavior:**

  > When a Claude Code peer session sends a message to an Agents-window Claude chat, the chat shows the inbound message (or a row for it), the tool calls, and the reply. Permission-requiring tools raise a normal prompt. If a request is denied automatically, it is not reported as a user decision. Prompts typed in the chat behave as before.
- **Trace:**

  > ClaudeSdkMessageRouter.handle in claudeSdkMessageRouter.ts returns early when turnId is undefined, so messages outside a user-initiated turn never reach mapSDKMessageToAgentSignals. Permission requests go through claudeCanUseTool.ts to ClaudeAgentSession.requestPermission, which returns false immediately when the pipeline is missing or aborted. I did not trace the pipeline's turn-tracking code in claudeSdkPipeline.ts or why the denial took 15 ms. The boundary is typed-prompt turn handling, which must not change. The uncertainty starts at how to represent a turn that no client started.
- **Open decisions:**
  - Should peer-initiated activity render as a synthetic turn in the chat, or as a distinct 'external message' row?
  - Should permission prompts for peer-triggered tools be shown to the user, or auto-denied with an explicit 'denied automatically' message?

## Evidence

- **turnless messages dropped:** src/vs/platform/agentHost/node/claude/claudeSdkMessageRouter.ts, ClaudeSdkMessageRouter.handle(): `if (turnId === undefined) { return; }` runs before mapSDKMessageToAgentSignals. Anything the SDK emits outside a user-initiated turn is therefore never mapped to chat signals.
- **permission path:** claudeCanUseTool.ts denies with CLAUDE_USER_DECLINED_MESSAGE ('User declined') when session.requestPermission resolves false. claudeAgentSession.ts requestPermission returns false immediately when the pipeline is missing or aborted, and otherwise waits for a UI response. I did not trace whether the pending_confirmation signal is also dropped when no turn is active, so the 15 ms denial is not confirmed from source.
