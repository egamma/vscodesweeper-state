# Issue #324147 — Remote Tunnel Access fails after a while

[https://github.com/microsoft/vscode/issues/324147](https://github.com/microsoft/vscode/issues/324147)

## Summary

Keep open: the logs show a healthy tunnel becoming permanently unavailable after a WebSocket reset because host-token refresh repeatedly returns 401, and current main still retries that failure indefinitely. This is also a team-authored issue, so no judgment-based close is available.

## Change summary

Remote Tunnel Access stops recovering after a connection reset when host-token refresh begins returning persistent 401 responses.

## Best solution

Make the tunnel lifecycle recover from stale host authorization after a relay disconnect, or terminate with an actionable authentication state instead of remaining in an endless retry loop. The newer recurrence at https://github.com/microsoft/vscode/issues/333100 should be consolidated into this better-diagnosed report rather than replacing it as the canonical issue.

## Plan brief

- **Likely files:** `cli/src/tunnels/dev_tunnels.rs`
- **Validation:** Add a Rust tunnel test with an injected access-token provider that succeeds initially, returns an authorization failure after a simulated relay disconnect, and verifies the maintainer-selected recovery or terminal authentication behavior without unbounded retries.
- **Behavior:**

  > A Remote Tunnel service that loses its relay connection must either reconnect automatically with valid refreshed authorization or enter a clear authentication-failed state that can be recovered without manually restarting VS Code. It must not remain unavailable while silently retrying the same rejected host-token lookup forever. Acceptance should cover a relay reset followed by host-token authorization failure and verify bounded, observable recovery behavior.
- **Trace:**

  > The issue log shows the tunnel operating normally until a WebSocket connection reset, after which host-token lookup repeatedly returns HTTP 401. ActiveTunnel::spawn_tunnel in cli/src/tunnels/dev_tunnels.rs obtains a token through AccessTokenProvider::refresh_token; its failure branch records the error, waits using Backoff, and continues indefinitely. The keep-alive branch can terminate when credentials become invalid, but persistent refresh failures never reach an equivalent authentication transition. The newer same-author recurrence is https://github.com/microsoft/vscode/issues/333100. Preserve reconnection for transient relay and token-service failures; the uncertainty begins at how persistent 401 responses should refresh identity, recreate authorization, or surface reauthentication.
- **Open decisions:**
  - Should a persistent host-token 401 trigger identity-token refresh, tunnel recreation, or an explicit reauthentication-required state?
  - Which authorization failures are transient and should retain backoff retries, and which should terminate retries?
  - How should a service-mode tunnel expose the terminal authentication state so recovery does not require restarting VS Code?
