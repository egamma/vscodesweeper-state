# Issue #115354 — No way to ensure an extension is prioritized as a rename provider in a language

[https://github.com/microsoft/vscode/issues/115354](https://github.com/microsoft/vscode/issues/115354)

## Summary

Keep open for a rename-provider selection decision. Current main deprioritizes built-in providers at equal scores, addressing the original Angular-versus-TypeScript ordering case, but still offers no supported preference among competing non-built-in providers; this issue already serves as the consolidation target.

## Change summary

Provide predictable, supported selection of a rename provider when multiple extensions support the same document.

## Best solution

Define a user-controlled rename-provider preference or selection contract that does not depend on extension registration timing. Preserve sequential fallback and the stated boundary against allowing one extension to mute another.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/rename/browser/rename.ts`, `src/vs/editor/common/languageFeatureRegistry.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** With two test extensions registering equal-score rename providers for the same language, reverse registration order and verify that the chosen preference or selection produces the same intended provider. Verify preparation and edits remain consistent, fallback works when the preferred provider cannot rename a symbol, and documents without a preference retain existing behavior.
- **Behavior:**

  > Multiple extensions can provide valid but different rename results for the same document, yet users cannot select which result should take precedence independently of activation timing. Provide a supported way to express that choice without disabling an entire extension. Acceptance should cover reversed registration order, consistent rename preparation and edits, and fallback when the selected provider cannot handle a symbol. Existing behavior should remain unchanged when no choice is expressed.
- **Trace:**

  > RenameSkeleton in src/vs/editor/contrib/rename/browser/rename.ts obtains providers from LanguageFeatureRegistry.ordered and accepts the first successful result. LanguageFeatureRegistry._compareByScoreAndTime in src/vs/editor/common/languageFeatureRegistry.ts already favors non-built-in providers over built-ins at equal scores, so the original Angular-versus-TypeScript ordering example is partially superseded; competing non-built-in providers still use registration time. ExtHostLanguageFeatures.registerRenameProvider in src/vs/workbench/api/common/extHostLanguageFeatures.ts forwards selectors and preparation support without a preference contract, matching the public registration API in src/vscode-dts/vscode.d.ts. The unresolved boundary is the user-facing selection mechanism and its persistence, not a missing sorting guard. Preserve fallback and do not permit one extension to mute another, as stated at https://github.com/microsoft/vscode/issues/115354#issuecomment-769656039. The later conflict report was consolidated here at https://github.com/microsoft/vscode/issues/183075#issuecomment-2548837526; provider-result composition from the discussion is not automatically part of a selection feature.
- **Open decisions:**
  - Should users choose a persistent default rename provider, select a provider for an individual rename operation, or have both options?
  - If a persistent preference is offered, should its scope be per language or per workspace and language?

## Evidence

- **Current selection behavior:** src/vs/editor/common/languageFeatureRegistry.ts, LanguageFeatureRegistry._compareByScoreAndTime, sorts by selector score, then deprioritizes built-in providers, then favors later registrations. src/vs/workbench/api/common/extHostTypeConverters.ts, DocumentSelector._doTransformDocumentSelector, propagates extension.isBuiltin.
