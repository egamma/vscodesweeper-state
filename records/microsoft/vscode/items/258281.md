# Issue #258281 — *Destructive* shortcut keys override standard text file operations (Ctrl+N rejects changes)

[https://github.com/microsoft/vscode/issues/258281](https://github.com/microsoft/vscode/issues/258281)

## Summary

The cursor-in-hunk mitigation reduced accidental activation but did not resolve the destructive collision: multiple users confirm on newer builds that Ctrl+N/Ctrl+Shift+N still discards chat edits when they intend standard New File/New Window actions. This remains an active, maintainer-confirmed UX defect under discussion.

## Change summary

Chat edit review keybindings override standard New File and New Window shortcuts and can silently discard agent-generated edits.

## Best solution

Remove the default collisions with New File/New Window, or require an explicit, visibly indicated review mode before destructive accept/reject shortcuts take precedence; rejected edits must also have an obvious recovery path.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCodeEditorIntegration.ts`
- **Validation:** Add or extend chat-editing keybinding tests, then manually verify on Windows/Linux and macOS that New File/New Window retain their standard behavior unless an explicitly selected review interaction is active, while intentional keyboard-driven hunk accept/reject and recovery remain available.
- **Behavior:**

  > Using the standard New File or New Window shortcut must not unexpectedly reject or accept chat edits. Keyboard-driven hunk review must remain discoverable and intentional, with a visible indication whenever its bindings take precedence. If an edit is rejected, the user must have a clear way to restore it with review state and diff highlighting intact. Acceptance must cover Ctrl/Cmd+N, Ctrl/Cmd+Shift+N, and the keep/redo collision across supported desktop platforms.
- **Trace:**

  > The conflicting hunk actions are registered through the chat editing editor integration in src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCodeEditorIntegration.ts. https://github.com/microsoft/vscode/pull/274361 narrowed activation to the current edit hunk, but comments after that merge confirm the same user-observable loss when the cursor happens to be inside a hunk. The issue thread leaves the intended product model unsettled: maintainers considered no default binding, safer bindings, persistent keybinding labels, and an explicit review mode. Preserve intentional keyboard-based hunk review and ordinary editor undo/redo behavior; do not treat cursor scoping alone as resolution.
- **Open decisions:**
  - Should hunk accept/reject have default shortcuts that never overlap New File/New Window, or should those commands be unbound until the user assigns shortcuts?
  - Should destructive hunk shortcuts work contextually whenever the cursor is in a hunk, or only after the user explicitly enters a visibly indicated review mode?
  - What recovery contract should follow an accidental reject: must ordinary undo restore both the content and the review diff state?

## Evidence

- **confirmed impact:** Maintainers sbatten and ulugbekna independently reported being surprised by the binding and losing agent edits; the reporter and several other users describe the same observable Ctrl/Cmd+N or Ctrl/Cmd+Shift+N collision.
- **mitigation insufficient:** https://github.com/microsoft/vscode/pull/274361 restricted undo/keep keybindings to hunks under the cursor, but a later report on Insiders 1.108 confirms Ctrl+Shift+N still discarded edits while the cursor was in a green edit hunk.
- **current confirmations:** Comments from February, April, May, and August 2026 continue to report lost work from the same shortcuts, including Ctrl+Shift+N overriding New Window.
- **maintainer direction:** Maintainers explicitly agreed there is user confusion and discussed removing defaults, choosing safer bindings, displaying active bindings, or introducing an explicit review mode; no settled design is recorded.
- **related reports:** Later closed reports https://github.com/microsoft/vscode/issues/274170, https://github.com/microsoft/vscode/issues/275250, https://github.com/microsoft/vscode/issues/273808, and https://github.com/microsoft/vscode/issues/284845 point back to the same shortcut behavior, while no older open canonical with the same observable symptom is identified.
