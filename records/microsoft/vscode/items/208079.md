# Issue #208079 — Allow extensions to contribute contexts to explorer tree nodes so that context menu commands can be conditional

[https://github.com/microsoft/vscode/issues/208079](https://github.com/microsoft/vscode/issues/208079)

## Summary

This remains a valid, accepted API request: current main exposes fixed Explorer resource context keys but no extension-provided per-resource context values. With 26 upvotes and a Backlog milestone, it should remain open for API design.

## Change summary

Allow extensions to provide resource-specific context values that conditionally control commands in the File Explorer context menu.

## Best solution

Design a proposed, invalidatable extension API that supplies namespaced context data for Explorer resources before their menus are resolved, while avoiding extension-host calls when a context menu opens. The API should support refreshing affected resources so mutually exclusive commands accurately follow changing extension state.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.fileDecorationContext.d.ts`, `src/vs/workbench/api/common/extHostDecorations.ts`, `src/vs/workbench/api/browser/mainThreadDecorations.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/api/test/browser/extHostDecorations.test.ts`
- **Validation:** Add extension API and workbench tests in which a provider assigns different context data to two Explorer resources, ExplorerContext menu when-clauses expose the corresponding mutually exclusive commands, and a provider change event updates the command selection without reopening or rebuilding the Explorer.
- **Behavior:**

  > Extensions can associate context data with individual File Explorer resources so menu `when` clauses show only commands applicable to the selected node. Context data is available when the menu is resolved without synchronously querying the extension host during menu opening. When an extension reports that a resource's data changed, the next menu resolution reflects the new state. Existing Explorer context keys, menus, and file decorations remain compatible.
- **Trace:**

  > ExplorerView.setContextKeys in src/vs/workbench/contrib/files/browser/views/explorerView.ts currently populates only built-in resource context keys, and ExplorerView.onContextMenu resolves MenuId.ExplorerContext against the tree context-key service. FileDecorationProvider is the closest existing resource-scoped provider: its public contract is in src/vscode-dts/vscode.d.ts, with batching and invalidation crossing ExtHostDecorations, MainThreadDecorations, and extHost.protocol.ts, but its payload contains decoration fields only. This establishes the likely cross-layer path but not whether context data belongs on FileDecorationProvider or a distinct proposed provider. Preserve existing global `setContext` behavior and custom TreeItem.contextValue semantics; this issue concerns file-system nodes in the built-in Explorer. https://github.com/microsoft/vscode/issues/10471 is related context-key API work but does not own this resource-specific behavior.
- **Open decisions:**
  - Should the public contract expose one namespaced context value per resource, a bounded set of boolean/string keys, or a distinct provider model, and how may extensions reference those values in menu `when` clauses?
  - Are contributed contexts evaluated only for the focused resource or for every selected resource, and what should a `when` clause observe for a mixed multi-selection?
  - What invalidation and caching guarantees should the API expose so menu state remains current without querying the extension host while the context menu opens?
