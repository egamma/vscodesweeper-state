# Issue #293258 — `@cloud Start implementation` triggered a Cloud Agent session on the wrong repo!

[https://github.com/microsoft/vscode/issues/293258](https://github.com/microsoft/vscode/issues/293258)

## Summary

Real bug: in multi-root workspaces, the plan agent's 'Start Implementation' handoff to the cloud agent does not pass the target repository from the plan context, so the cloud agent falls back to the first repo returned by `getRepoId()`, which may be wrong.

## Change summary

Triggering '@cloud Start implementation' from plan mode in a multi-root workspace sends the task to the wrong repository.

## Best solution

When the plan agent hands off to the cloud agent via the 'Start Implementation' handoff, the session's `sessionRepositoryMap` should be populated based on the repository context established during planning (e.g., from workspace files referenced in the plan). The fallback logic in `invokeRemoteAgent` that uses `repoIds?.[0]` is the proximate cause — it should either require an explicit selection or infer the correct repo from the plan's file references.

## Evidence

- **fallback to first repo:** In `extensions/copilot/src/extension/chatSessions/vscode-node/copilotCloudSessionsProvider.ts` line 3146, when `selectedRepository` is unset, the code falls back to `repoIds?.[0]` — the first repo returned by `getRepoId()`, which has no guaranteed order in multi-root workspaces.
- **handoff has no repo context:** The plan agent handoff in `extensions/copilot/src/extension/agents/vscode-node/planAgentProvider.ts` (line 225) only specifies `agent: 'agent'` and `prompt: 'Start implementation'` — no mechanism to pass the identified target repository.
- **getRepoId ordering:** `extensions/copilot/src/extension/chatSessions/vscode/copilotCodingAgentUtils.ts` line 78-86: for multi-root, returns repos in `gitService.repositories` order (workspace folder order), not by relevance to current context.
