# Issue #325381 — Copilot agent regex search returns zero results for files outside workspace root

[https://github.com/microsoft/vscode/issues/325381](https://github.com/microsoft/vscode/issues/325381)

## Summary

The failure remains visible in current main: an absolute include path outside the working directory is passed to the workspace search API in a form that cannot select that external file. This team-authored issue should stay open while the external-read permission behavior is designed.

## Change summary

Make the Copilot text-search tool return matches from an explicitly requested file outside the workspace instead of silently reporting zero results.

## Best solution

Support an explicitly targeted external file through the same read-access policy used by other Copilot file tools, then scope the text-search query to that external resource without changing ordinary workspace search behavior.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/tools/node/findTextInFilesTool.tsx`, `extensions/copilot/src/extension/tools/node/toolUtils.ts`, `extensions/copilot/src/extension/tools/node/test/findTextInFilesTool.spec.tsx`, `extensions/copilot/src/extension/tools/node/test/toolUtils.spec.ts`
- **Validation:** Add a targeted Copilot tool test that searches an explicitly permitted external fixture and asserts the same matches are returned whether or not the file is open, while retaining the existing in-workspace and working-directory cases.
- **Behavior:**

  > When the agent is explicitly asked to run text or regex search against an absolute file path outside the workspace, the tool must not silently treat that path as a workspace-relative glob and return zero results. After the applicable external-read authorization, a closed external file must produce the same matches as an equivalent in-workspace or open file. Existing workspace-relative, multi-root, ignore-file, and maximum-result behavior must remain unchanged.
- **Trace:**

  > FindTextInFilesTool resolves includePattern through inputGlobToPattern and then forwards the result to workspace.findTextInFiles2. In extensions/copilot/src/extension/tools/node/toolUtils.ts, absolute paths are converted to RelativePattern only when WorkingDirectory.getFolder accepts them; external paths remain plain strings or become patterns based at the unrelated working directory. The ext-host search implementation in src/vs/workbench/api/common/extHostWorkspace.ts searches an explicit folder only when the include is a RelativePattern, which explains the empty result for a closed sibling file. Opening the file can mask the defect through open-editor search participation, matching the report. Keep the scope to explicitly targeted external files and do not broaden unrestricted recursive search outside the workspace; preserve the existing workspace and multi-root behavior. External file tools already centralize read authorization through isFileExternalAndNeedsConfirmation, but text search does not currently participate in that flow.
- **Open decisions:**
  - Should an explicit external search require the standard one-time external-read confirmation, or be permitted only when the path is already covered by the session working directory or github.copilot.chat.additionalReadAccessPaths?
