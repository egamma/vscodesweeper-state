# Issue #350331 — RequestService ignores cancellation after response headers arrive

[https://github.com/microsoft/vscode/issues/350331](https://github.com/microsoft/vscode/issues/350331)

## Summary

The cancellation gap remains directly visible in current main: receiving headers removes the listener while the response body can still be downloading. Keep this open for a request-lifecycle fix covering both Node and Electron transports.

## Change summary

Ensure cancellation after response headers stops the underlying transfer rather than leaving abandoned downloads running.

## Best solution

Make the existing request cancellation token effective throughout response-body consumption in both transports, with terminal-event cleanup and regression coverage. Preserve existing request-context consumers and unrelated stream behavior.

## Evidence

- **Exact failing path:** In src/vs/platform/request/node/requestService.ts, nodeRequestAttempt resolves IRequestContext from the response callback, but req.on('response', () => cancellationListener.dispose()) removes the only token listener that calls req.abort(). Cancelling after headers therefore cannot abort a still-running body transfer.
- **Wrapper destruction does not propagate:** src/vs/base/common/buffer.ts:407 delegates streamToBufferReadableStream to streams.transform. In src/vs/base/common/stream.ts:712, transform creates a separate writable stream and forwards data/error/end; its destroy implementation at line 451 clears only that wrapper's buffers and listeners, without destroying the source.
- **Electron shares the defect:** src/vs/platform/request/electron-utility/requestService.ts supplies Electron net.request and isChromiumNetwork: true to the same Node RequestService implementation. The premature cancellation-listener disposal therefore applies to the shared-process transport too.
