# Issue #279938 — Copying a chat response includes tool calls

[https://github.com/microsoft/vscode/issues/279938](https://github.com/microsoft/vscode/issues/279938)

## Summary

The defect remains source-reproducible on current main: copying uses `Response.toString()`, which deliberately includes tool invocations and inserts Markdown-backed invocation messages without converting them to plain text. The merged related PR only worked around the problem for agent-session descriptions.

## Change summary

Copying or otherwise stringifying a chat response exposes tool-call text containing raw Markdown links and internal file details.

## Best solution

Establish a consistent user-facing text representation for chat responses: tool-call messages included in that representation must be converted to readable plain text, with a maintainer decision on whether ordinary copy should include those tool summaries at all.

- **Behavior:**

  > Copying a chat response must never expose raw Markdown link syntax or internal file URIs from tool invocation messages. Assistant-authored response content must remain readable and complete. The plan must settle whether copy omits tool calls entirely or retains concise plaintext summaries, then apply that contract consistently without degrading voice or accessibility output.
- **Trace:**

  > `AbstractResponse.partsToRepr()` in `src/vs/workbench/contrib/chat/common/model/chatModel.ts` explicitly routes tool invocations through `getToolInvocationText()`. That method extracts `.value` from Markdown-backed invocation messages without rendering it as plaintext; `stringifyItem()` in `src/vs/workbench/contrib/chat/browser/actions/chatActions.ts` then returns the representation directly for copying. Several other consumers also use `toString()`, although voice and accessibility apply separate plaintext conversion afterward. Commit https://github.com/microsoft/vscode/commit/f59e9a53494b32a3265f4db7e5f2a938bcaa7e0d handles only local agent-session descriptions and must not be treated as the underlying fix. Preserve structured response parts, visual tool rendering, persistence, and terminal-command sanitization behavior.
- **Open decisions:**
  - Should copying a full chat response omit tool invocation summaries entirely, or retain them after converting their Markdown to concise plain text?
  - Should `Response.toString()` itself define the sanitized user-facing contract for every consumer, or should copy use a separate representation while accessibility and voice retain their existing tool-status semantics?
