# Issue #326371 — Record video when reporting issue doesn't work

[https://github.com/microsoft/vscode/issues/326371](https://github.com/microsoft/vscode/issues/326371)

## Summary

Team-authored bug report on the brand-new 'Record video' feature in the issue reporter; the described macOS permission-dialog loop followed by a silent no-op recording click is plausible given how screen-capture permission and source selection are wired, so this should stay open and be routed to the issue-reporter area for investigation.

## Change summary

On macOS, clicking 'Record video' in Chat: Report Issue triggers repeated permission dialogs, and after granting/restarting, clicking record again flashes but starts no recording.

## Best solution

Have the issue-reporter feature owner trace the macOS flow end-to-end: NativeRecordingService.startRecording() only pre-checks getScreenCapturePermissionStatus() for 'denied'/'restricted' and otherwise calls navigator.mediaDevices.getDisplayMedia(), which resolves via session.defaultSession.setDisplayMediaRequestHandler() in src/vs/code/electron-main/app.ts — that handler silently calls back({}) (no video) when desktopCapturer.getSources() finds no matching/cached screen source, which would manifest exactly as 'flashes but nothing happens' with no error surfaced to the renderer.

## Evidence

- **permission check:** src/vs/workbench/contrib/issue/electron-browser/issueReporterEditorPane.ts:262-286 only blocks recording on getScreenCapturePermissionStatus() === 'denied'|'restricted'; other states (e.g. transient 'not-determined' after a fresh grant) fall through to startRecording().
- **silent no-source path:** src/vs/code/electron-main/app.ts:304-346 setDisplayMediaRequestHandler calls callback({}) with no video whenever desktopCapturer.getSources() finds no matching screen (denied permission or stale cachedScreenSources), which would make getDisplayMedia produce no stream without a clear error — matching the reported 'flashes but nothing happens'.
- **stale cache risk:** cachedScreenSources in app.ts is process-lifetime cached; if the first getSources() call raced OS permission propagation, subsequent recordings in the same session could keep using an empty/incomplete cache.
