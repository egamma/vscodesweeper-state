# Issue #335218 — Composite view containers should not silently inherit the first view's title and icon

[https://github.com/microsoft/vscode/issues/335218](https://github.com/microsoft/vscode/issues/335218)

## Summary

Traced the exact behavior on main: `ViewContainerModel.updateContainerInfo()` in viewContainerModel.ts falls back to `visibleViewDescriptors[0]`'s title/icon whenever the container isn't a 'default' one for those views — which is exactly the case for a user-dragged composite container with 2+ views. The report is accurate and still unaddressed; no canonical issue owns it and a real design decision (generic fallback copy/icon, and whether a rename/icon-pick affordance is in scope) remains for a maintainer.

## Change summary

When 2+ views are grouped into a user-created container, the container silently takes the title/icon of whichever view is first, with no visual cue it's a composite group.

## Best solution

In ViewContainerModel.updateContainerInfo() (src/vs/workbench/services/views/common/viewContainerModel.ts), special-case containers with multiple visible view descriptors to use a generic 'group of views' title/icon instead of the first view's, and decide separately whether to add a rename/icon-pick affordance for these containers (mirroring editor groups/profiles).

## Plan brief

- **Behavior:**

  > A user-created view container holding 2+ views should present a generic, container-level title/icon signalling a group of views, instead of adopting the first view's own title/icon. A container holding a single view keeps today's merge behavior. Acceptance: dragging Explorer + Search into one panel container shows a generic label/icon, not 'Explorer'.
- **Trace:**

  > updateContainerInfo() in src/vs/workbench/services/views/common/viewContainerModel.ts computes `useDefaultContainerInfo` and, when false, always takes `visibleViewDescriptors[0]`'s title/containerIcon regardless of how many views are visible — traced directly in the source, confirmed by the placeholder-title comment in viewDescriptorService.ts's registerGeneratedViewContainer(). The boundary: do not change the existing single-view merge path (isViewMergedWithContainer() in viewPaneContainer.ts) or default (non-generated) containers, which correctly use their own registered title/icon.
- **Open decisions:**
  - What is the generic fallback title/icon for a composite container (localized copy, icon choice), and does it apply universally or only to generated/custom containers?
  - Is a rename/icon-pick affordance (like editor groups/profiles) in scope for this change, or is the generic-fallback-only version the accepted minimum?
