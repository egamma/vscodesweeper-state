# Issue #335218 — Composite view containers should not silently inherit the first view's title and icon

[https://github.com/microsoft/vscode/issues/335218](https://github.com/microsoft/vscode/issues/335218)

## Summary

Current main explicitly derives a generated container's identity from its first visible view, and reordering therefore changes the displayed title and icon. The request remains a valid, unrouted workbench UX design question rather than an already-implemented capability.

## Change summary

Give generated containers holding multiple views a recognizable composite identity, ideally with optional user-defined title and icon.

## Best solution

Define a stable identity model for generated multi-view containers in the workbench views service: preserve the existing single-view identity, but give composite containers an identity that does not change with view ordering, with maintainers deciding whether user customization belongs in the initial scope.

## Plan brief

- **Likely files:** `src/vs/workbench/services/views/common/viewContainerModel.ts`, `src/vs/workbench/services/views/browser/viewDescriptorService.ts`, `src/vs/workbench/services/views/test/browser/viewContainerModel.test.ts`, `src/vs/workbench/browser/parts/paneCompositeBar.ts`
- **Validation:** Add view-container model tests covering a generated container with one view and with two reordered views: the singleton retains its view identity, while the composite retains the agreed title and icon across reordering; if customization is selected, also verify its chosen persistence scope and reset behavior.
- **Behavior:**

  > A generated container containing two or more views must be recognizable as a composite and must not silently change identity when its views are reordered. A generated container containing one view should retain the existing view-derived identity. If custom naming and icon selection are included, those choices must override the fallback consistently and survive according to the agreed persistence scope.
- **Trace:**

  > ViewContainerModel.updateContainerInfo in src/vs/workbench/services/views/common/viewContainerModel.ts deliberately derives the title and icon of a generated container from `visibleViewDescriptors[0]` whenever none of its visible views belongs there by default. View moves and ordering changes call updateState, which recomputes that identity; PaneCompositeBar consumes the resulting model fields and immediately updates the displayed composite action. ViewDescriptorService.registerGeneratedViewContainer in src/vs/workbench/services/views/browser/viewDescriptorService.ts supplies only a placeholder identity, while IViewsCustomizations persists no custom title or icon. The boundary is generated user-arranged containers: do not alter contributed/default container identities or the existing singleton behavior. No older canonical issue or existing rename/icon capability was found.
- **Open decisions:**
  - What generic title and icon should identify a generated container with multiple views?
  - Should composite status be based on every view assigned to the container or only currently visible/active views?
  - Should the initial feature include user-defined names and icons, and if so should that identity persist per profile or per workspace?
