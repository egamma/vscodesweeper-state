# Issue #305798 — Sessions: Git branch not found despite existing

[https://github.com/microsoft/vscode/issues/305798](https://github.com/microsoft/vscode/issues/305798)

## Summary

Remote-branch discovery remains a real gap: current branch completions intentionally enumerate local branches, with only selected upstream/default remote branches added separately. Keep this team-authored report open; neither a qualifying fix referencing it nor an older canonical with the same symptom was found.

## Change summary

Allow the Sessions branch picker to discover and select existing remote branches without first creating a local branch.

## Best solution

Extend the Agents Window branch-selection experience to discover remote branches and make fetching understandable, while preserving the distinction between folder checkout and isolated worktree creation. A maintainer should first settle whether discovery uses cached remote refs or contacts the remote, and how users refresh stale results.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/shared/worktreeIsolation.ts`, `src/vs/platform/agentHost/node/agentHostGitService.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/agentHostSessionConfigPicker.ts`, `src/vs/platform/agentHost/test/node/shared/worktreeIsolation.test.ts`
- **Validation:** Add focused branch-completion and picker checks using a repository with a remote feature branch and no corresponding local branch. Verify discovery and selection under the agreed refresh policy, distinguish cached remote refs from branches created remotely after the last fetch, and preserve existing local-branch ordering and folder-isolation behavior.
- **Behavior:**

  > An existing remote branch should be discoverable for a new isolated session without first checking it out or creating a local branch. The experience must distinguish unavailable or stale remote information from an absent branch. Acceptance should cover both a cached remote-tracking branch and a branch created on the remote since the last fetch. Existing local branch choices and folder-isolation checkout behavior remain unchanged unless explicitly included in the agreed scope.
- **Trace:**

  > AgentService delegates branch completion to WorktreeIsolation.branchCompletions in src/vs/platform/agentHost/node/shared/worktreeIsolation.ts, which explicitly enumerates refs/heads only. AgentHostSessionConfigPicker in src/vs/sessions/contrib/providers/agentHost/browser/agentHostSessionConfigPicker.ts adds only the current upstream and default remote branch as pinned worktree choices; it does not discover arbitrary remote branches. AgentHostGitService.getRefs reads locally stored refs via for-each-ref. Worktree creation can fetch an already selected RemoteHead, but that occurs after discovery and cannot populate the picker. The existing tests in src/vs/platform/agentHost/test/node/shared/worktreeIsolation.test.ts cover completion ordering and explicit remote worktree start points. Preserve local selection semantics and do not expand this into cloud/local conversation handoff, which is separately discussed at https://github.com/microsoft/vscode/issues/266476. Uncertainty starts at the remote discovery and refresh contract, not at whether the local-only enumeration exists.
- **Open decisions:**
  - Should opening the branch picker contact the remote automatically, or show cached remote-tracking branches with an explicit refresh action?
  - Should remote-only branch selection be supported only for isolated worktrees, or also create and check out a local tracking branch in folder isolation?
