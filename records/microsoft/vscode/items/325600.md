# Issue #325600 — Third-party extensions cannot configure TLS CA verification — structural disparity with BYOK

[https://github.com/microsoft/vscode/issues/325600](https://github.com/microsoft/vscode/issues/325600)

## Summary

The core disparity the reporter describes is real, but VS Code already ships an opt-in `http.electronFetch` setting (defaults to `false`) that routes extension-host `globalThis.fetch()` through Electron's fetch — which uses the OS TLS stack (SChannel/Secure Transport) and resolves the incomplete-chain scenario. The reporter may not be aware of this setting. The remaining ask is either to default it to `true`, improve its discoverability, or offer a more granular API — all valid but incremental feature requests.

## Change summary

Third-party extensions using `globalThis.fetch()` in the extension host cannot leverage OS CA stores for TLS verification, unlike first-party features that use Electron's network stack.

## Best solution

Point the reporter to the existing `http.electronFetch` setting, which already provides the transport parity they request. If there is appetite to default it to `true` or improve discoverability, that decision belongs to the proxy/networking area owner. A dedicated extension API for TLS CA configuration would be a larger feature tracked separately. Related: https://github.com/microsoft/vscode/issues/248170 covers a similar TLS/certificate gap for MCP SSE connections.
