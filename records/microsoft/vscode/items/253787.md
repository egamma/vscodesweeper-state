# Issue #253787 — Auto confirm for MCP tool call in extension using 'vscode.lm.tools' APIs

[https://github.com/microsoft/vscode/issues/253787](https://github.com/microsoft/vscode/issues/253787)

## Summary

Keep open: non-chat tool calls still use a per-invocation modal without session approval or rejection controls. Existing global and saved approvals provide partial coverage, but do not deliver the requested session-scoped experience; the team-authored request needs an explicit product decision.

## Change summary

Allow users to approve or reject repeated MCP tool invocations within an extension-driven session without answering a modal for each call.

## Best solution

Define a user-controlled approval scope and lifetime for non-chat lm.invokeTool callers, then expose the corresponding choices in the confirmation experience while preserving enterprise restrictions. Explain confirmation differences using tool metadata rather than HTTP/OAuth versus npx transport.

- **Validation:** After defining the scope, add targeted tests in the languageModelToolsService and languageModelToolsConfirmationService suites covering repeated no-chat-context invocations, scope expiration and isolation, rejection, and enterprise restrictions. Manually invoke a confirmation-requiring MCP tool twice from a non-chat extension and verify that the chosen session behavior applies without changing ordinary one-shot confirmation.
- **Behavior:**

  > An extension invoking MCP tools outside a VS Code chat request should have a user-controlled way to avoid repeated confirmation dialogs within a defined session. Approval or rejection must apply only to the scope the user selected and expire at its documented boundary. Existing one-shot confirmation, cancellation, saved approvals, and enterprise restrictions must retain their behavior. Acceptance checks must cover repeated calls, scope isolation, expiration, and both approval and rejection.
- **Trace:**

  > ExtHostLanguageModelTools.invokeTool forwards options.toolInvocationToken as context; the public API documents undefined for non-chat calls and supplies no separate session identity on this path. LanguageModelToolsService.invokeTool uses a no-context branch that resolves existing approvals before showing dialogService.confirm with only message and detail. shouldAutoConfirm already supports saved approvals and the global setting, but session approval depends on a chatSessionResource that this caller does not supply. MCP confirmation preparation depends on sandbox status and tool annotations, not directly on transport or OAuth. The unresolved boundary is how a non-chat session is identified and what consent persists within it; do not treat global auto-approval as a session-scoped solution or let extensions silently bypass user consent. Related https://github.com/microsoft/vscode/issues/258778 records the same missing modal choices but is closed and newer.
- **Open decisions:**
  - What defines a non-chat extension session and its lifetime, and should remembered consent be scoped by extension, MCP server, individual tool, or a combination?
  - Should this surface support both remembered approval and remembered rejection, and how should users inspect or revoke either decision?
