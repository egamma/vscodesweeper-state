# Issue #243469 — Test Peek Output Window and Test Results Tab don't support file links.

[https://github.com/microsoft/vscode/issues/243469](https://github.com/microsoft/vscode/issues/243469)

## Summary

Keep open: current source exposes a concrete remote-file resolution defect matching the Windows/WSL environment reported here. Test output enables built-in link detection but supplies neither the remote authority nor the remote OS, so remote paths are interpreted and checked as local files.

## Change summary

Make workspace file paths clickable in test peek output and the Test Results output pane, including Windows clients connected to WSL.

## Best solution

Ensure both test-output surfaces resolve built-in file links in the environment that owns the test files, preserving remote authority and path semantics. Keep extension-provided custom-scheme links as separate work.

## Evidence

- **Reported scenario:** https://github.com/microsoft/vscode/issues/243469 reports non-clickable full file paths in both test-output surfaces on VS Code 1.97.2, with a Windows frontend connected to Ubuntu through WSL. The only supplied comment requests an upgrade; it does not confirm resolution.
- **Current test-output construction:** src/vs/workbench/contrib/testing/browser/testResultsView/testResultsOutput.ts: TerminalMessagePeek.makeTerminal constructs DetachedProcessInfo with only initialCwd. updateCwd retains the workspace URI's fsPath but not its scheme or authority. src/vs/workbench/contrib/terminal/browser/detachedTerminal.ts leaves remoteAuthority and os undefined unless explicitly supplied.
- **Failing resolution path:** src/vs/workbench/contrib/terminalContrib/links/browser/terminalLinkContribution.ts installs TerminalLinkManager for detached terminals. terminalLocalLinkDetector.ts uses processManager.os || OS, and terminalLinkResolver.ts constructs vscode-remote URIs only when remoteAuthority is present; otherwise it calls URI.file and checks that local resource with IFileService.stat. A file existing only inside the WSL workspace therefore cannot be validated as the correct remote file through this path.
