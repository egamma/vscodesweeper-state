## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `extensions/extension-editing/src/extensionLinter.ts`, `extensions/extension-editing/package.json`, `src/vs/workbench/contrib/customEditor/common/extensionPoint.ts`
- **Validation:** The plan should define an executable extension-author fixture check: a custom-editor identifier and configuration declaration stay consistent between TypeScript and package.json after renaming; an inconsistent registration or stale generated manifest makes the check exit nonzero. Also verify repeat generation is unchanged and ordinary string-based extensions remain supported.
- **Behavior:**

  > Extension authors can avoid independently maintaining matching identifiers in manifest contributions and implementation code. A custom-editor identifier rename must not silently leave its provider registration inconsistent, and typed configuration access should agree with its declaration. The selected tooling must expose inconsistencies before publishing and keep generated manifest content reliably synchronized. Existing extensions that use ordinary package.json declarations and string-based APIs must remain supported.
- **Trace:**

  > The stable API in src/vscode-dts/vscode.d.ts accepts string viewTypes and configuration sections, while ExtHostCustomEditors.registerCustomEditorProvider stores and forwards the supplied identifier without linking it to manifest declarations. Built-in authoring support in extensions/extension-editing validates JSON and activation metadata, not TypeScript-to-manifest correspondence. Implicit activation in src/vs/workbench/contrib/customEditor/common/extensionPoint.ts already eliminates explicit onCustomEditor duplication, so that is not the remaining work. The maintainer proposal at https://github.com/microsoft/vscode/issues/97399#issuecomment-872418125 favors opt-in typed-contributions tooling; the js-debug generator cited earlier is prior art. The trace establishes the missing contract, not the architecture of a new package. Preserve runtime extension loading, existing string-based API compatibility, and bundler independence while deciding how author tooling represents identifiers and synchronizes manifests.
- **Open decisions:**
  - Should typed identifiers be exposed through optional augmentation of the vscode API declarations, or through a separate typed facade that leaves those declarations unchanged?
  - What is the supported manifest-authoring contract: the proposed $fileRef in-place augmentation, or a separate typed manifest source, and which fields may generation overwrite?
  - Should the initial supported contract cover custom-editor identifiers and configuration keys only, or also other contribution/registration pairs such as commands and views?
