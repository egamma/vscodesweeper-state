# Issue #244273 — A single slow Code Action provider can affect all others

[https://github.com/microsoft/vscode/issues/244273](https://github.com/microsoft/vscode/issues/244273)

## Summary

The blocking behavior remains in current source: all providers must finish before either the lightbulb or invoked action list receives results. Keep this correctly routed backlog issue open; partial-result presentation needs a product decision before implementation.

## Change summary

Prevent one slow Code Action provider from delaying usable actions returned by other providers.

## Best solution

Make ready actions available independently of slow providers in the editor Code Action flow, while preserving stable selection and safe auto-apply behavior. Decide the initial wait policy and late-result presentation before changing the shared aggregation contract.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/codeAction/browser/codeAction.ts`, `src/vs/editor/contrib/codeAction/browser/codeActionModel.ts`, `src/vs/editor/contrib/codeAction/browser/codeActionController.ts`, `src/vs/editor/contrib/codeAction/common/types.ts`, `src/vs/editor/contrib/codeAction/test/browser/codeAction.test.ts`, `src/vs/editor/contrib/codeAction/test/browser/codeActionModel.test.ts`
- **Validation:** Add controlled fast and deferred providers to the CodeAction and CodeActionModel tests. Verify that ready actions become available under the agreed timing policy before the deferred provider completes, late arrivals preserve the selected action, and cancellation disposes results without publishing stale actions. Cover First/IfSingle auto-apply semantics and preserve existing complete-result behavior for noninteractive consumers. Manually verify automatic lightbulb and explicit Quick Fix presentation with the same two-provider setup.
- **Behavior:**

  > When multiple Code Action providers match a document, a slow provider currently prevents actions from responsive providers from appearing. Ready actions should become usable without waiting for the slowest provider, for both automatic lightbulb discovery and explicit invocation. Late results must not shift an existing action underneath the user's pointer or keyboard selection. Acceptance must also cover cancellation, stale results, and auto-apply commands under the agreed partial-result policy.
- **Trace:**

  > getCodeActions in src/vs/editor/contrib/codeAction/browser/codeAction.ts starts provider calls concurrently and then blocks result construction on Promise.all. CodeActionsState.Triggered in codeActionModel.ts exposes one result promise, and CodeActionController.update awaits it before publishing lightbulb information or showing the menu. The controller currently declines to update an already visible widget for automatic results, and First/IfSingle auto-application depends on the final action set. The shared getCodeActions function also serves _executeCodeActionProvider, so editor presentation changes must not silently turn complete-result consumers into partial-result consumers. Existing provider-kind filtering does not help when both providers legitimately match. The source establishes the barrier conclusively; uncertainty begins at the intended timing, late-result, and auto-apply contracts, not at whether the barrier exists.
- **Open decisions:**
  - For explicit invocation, should ready actions appear immediately or after a bounded initial wait, and what wait should users experience?
  - Should an already open menu append late actions with a loading indication, or retain a fixed snapshot until the next invocation?
  - Should First and IfSingle auto-apply commands continue waiting for all providers, or adopt a defined partial-result policy?

## Evidence

- **Current aggregation barrier:** src/vs/editor/contrib/codeAction/browser/codeAction.ts:125-164 invokes providers concurrently but awaits Promise.all(promises) before constructing any CodeActionSet. With one completed provider and one pending provider, the completed provider's actions remain unavailable. The 1250 ms timer at line 126 only reports progress; it does not release partial results.
- **Both editor triggers are affected:** src/vs/editor/contrib/codeAction/browser/codeActionModel.ts represents results as a single Promise<CodeActionSet> and awaits getCodeActions for automatic and explicit triggers. src/vs/editor/contrib/codeAction/browser/codeActionController.ts:215 awaits newState.actions before updating the lightbulb or opening the action list.
- **Presentation and contract boundaries:** CodeActionController.update currently discards automatic results when the action widget is already visible, with an explicit TODO about updating the menu. Its tryGetValidActionToApply uses the completed set to implement First and IfSingle auto-application. Incremental delivery therefore needs observable policy decisions, not merely replacement of Promise.all.

The settings registered in codeActionContributions.ts cover headers, nearby quick fixes, and focus-change triggering, not partial-result delivery.
