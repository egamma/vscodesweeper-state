# Issue #244273 — A single slow Code Action provider can affect all others

[https://github.com/microsoft/vscode/issues/244273](https://github.com/microsoft/vscode/issues/244273)

## Summary

The defect remains on current main: code actions from every matching provider are joined with `Promise.all`, so one slow provider delays the light bulb and manually invoked results from all other providers. This accepted Backlog bug should stay open for a design and implementation that supports partial results without destabilizing the menu.

## Change summary

Prevent one slow Code Action provider from withholding actions already returned by other providers.

## Best solution

Let the editor expose available code actions while slower providers remain pending, preserving existing items and focus when late results arrive. The editor team should first settle the observable timeout and loading-state behavior for invoked actions.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/codeAction/browser/codeAction.ts`, `src/vs/editor/contrib/codeAction/browser/codeActionModel.ts`, `src/vs/editor/contrib/codeAction/browser/codeActionController.ts`, `src/vs/editor/contrib/codeAction/common/types.ts`, `src/vs/editor/contrib/codeAction/test/browser/codeAction.test.ts`, `src/vs/editor/contrib/codeAction/test/browser/codeActionModel.test.ts`
- **Validation:** Add CodeAction and CodeActionModel tests with one immediate provider and one deferred provider, then run `scripts/test.sh --grep "CodeAction"`; the immediate action must become available before the deferred provider resolves, late actions must append without moving the focused item, and cancellation must dispose every provider result exactly once.
- **Behavior:**

  > When multiple Code Action providers match, actions returned by responsive providers become available without waiting for the slowest provider. Automatic requests can show the light bulb from the first usable result, and an already-open action menu retains its existing ordering and focused item as later actions arrive. Cancellation or a newer request must prevent stale late results from appearing. Acceptance includes tests with immediate and deferred providers covering partial availability, stable menu updates, and disposal.
- **Trace:**

  > `getCodeActions` in `src/vs/editor/contrib/codeAction/browser/codeAction.ts` starts providers concurrently but joins them with `Promise.all`, then creates one immutable `ManagedCodeActionSet`. `CodeActionsState.Triggered` in `codeActionModel.ts` exposes only a final `Promise<CodeActionSet>`, and `CodeActionController.update` waits for it before updating the light bulb or list. The action-widget service already exposes `updateItems`, including focus and scroll preservation, so the uncertainty begins at the code-action result lifecycle and product semantics rather than the generic list widget. Preserve provider filtering, cancellation on registry/model changes, sorting of the initial batch, auto-apply behavior, and exactly-once disposal; save-participant behavior addressed by https://github.com/microsoft/vscode/issues/209789 is outside this issue's boundary.
- **Open decisions:**
  - For manually invoked actions, after what user-visible threshold should the menu open with partial results, and should it remain visibly loading until every provider completes?
  - Should an invoked request continue accepting late provider results indefinitely, or stop and cancel outstanding providers after a defined timeout?
  - Should pending providers be represented by named placeholders in the menu, or only by a generic progress state?

## Evidence

- **current source:** `src/vs/editor/contrib/codeAction/browser/codeAction.ts` maps every matching provider to a promise and awaits `Promise.all(promises)` before constructing and returning the `ManagedCodeActionSet`; this conclusively preserves the reported all-provider blocking behavior on current main.
- **consumer path:** `src/vs/editor/contrib/codeAction/browser/codeActionModel.ts` represents triggered actions as a single `Promise<CodeActionSet>`, and `src/vs/editor/contrib/codeAction/browser/codeActionController.ts` awaits that promise before updating the light bulb or opening the action list.
- **incremental UI capability:** `IActionWidgetService.updateItems` in `src/vs/platform/actionWidget/browser/actionWidget.ts` can refresh an open action list while preserving focus, but the code-action controller currently calls only `show` and has no stream of provider completions to feed into it.
- **related reports:** https://github.com/microsoft/vscode/issues/89745 and https://github.com/microsoft/vscode/issues/204648 concern save-time code actions and are closed, so neither is an open canonical for this broader light-bulb and invocation aggregation defect.
- **canonical search:** A search for open reports about slow Code Action providers, all-provider waiting, and incremental Code Actions found no older open issue with the same reporter-observable symptom; https://github.com/microsoft/vscode/issues/244273 remains the appropriate owner.
