# Issue #339207 — Timestamp colliding with edited chat input

[https://github.com/microsoft/vscode/issues/339207](https://github.com/microsoft/vscode/issues/339207)

## Summary

Team-authored visual bug report (screenshot only, no text) that traces cleanly to a CSS gap: the request timestamp overlay only gets its collision-avoidance offset for the `.editing` state, not `.editing-input` (used when `chat.editRequests` is set to `input`), so the timestamp sits on top of the edited text in that mode.

## Change summary

When editing a chat request with `chat.editRequests: input`, the request timestamp overlaps/collides with the edited input text instead of being offset out of the way.

## Best solution

Extend the `.interactive-item-container.interactive-request.editing .chat-request-timestamp-container` positioning rules (src/vs/workbench/contrib/chat/browser/widget/media/chat.css, around lines 531-545) to also cover `.editing-input`, mirroring the same margin/pointer-events treatment already applied for `.editing`.

Acceptance: manually toggling the setting and editing a request shows the timestamp cleanly positioned, not overlapping the text, in both editing modes.
- **Trace:**

  > src/vs/workbench/contrib/chat/browser/widget/media/chat.css: the `.chat-request-timestamp-container` is shown for both `.editing` and `.editing-input` row states (line 519), but only `.interactive-item-container.interactive-request.editing .chat-request-timestamp-container` (lines 531-545) gets the `margin-top: -22px` / `pointer-events: none` / inline-end padding that pulls the timestamp out of the text flow. `.editing-input` falls through with no equivalent rule. The two classes are set exclusively in chatListRenderer.ts (lines 1868-1869) based on whether `chat.editRequests` is `'input'`. Do not change the `.editing` (non-input) styling, which already works correctly; scope any fix to the `.editing-input` selector.
- **Open decisions:**
  - Should `.editing-input` mode receive the exact same timestamp offset as `.editing`, or does its different editing UX (inline text edit vs. separate editor) call for a different placement/behavior?

## Evidence

- **selector asymmetry:** chat.css line 519 shows the timestamp container for both `.editing` and `.editing-input` (`:not(.editing):not(.editing-input)` hides it otherwise), but the compensating layout rules at lines 531-545 (`height: 22px; margin-top: -22px; pointer-events: none` and the inline-end padding) are scoped only to `.interactive-item-container.interactive-request.editing`, with no equivalent for `.editing-input`.
- **class toggle source:** chatListRenderer.ts line 1868-1869 toggles `editing` only when `editing && !isInput`, and `editing-input` when `editing && isInput`, where `isInput` comes from the `chat.editRequests` setting being `'input'` — so the two classes are mutually exclusive and only one path gets the offset fix.
