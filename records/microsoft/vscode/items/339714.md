# Issue #339714 — Expect no welcome message when mode set to `replace` with empty list

[https://github.com/microsoft/vscode/issues/339714](https://github.com/microsoft/vscode/issues/339714)

## Summary

Team-authored report (testing a related PR), and it's a hard keep-open regardless — but it's also a real, confirmed gap: `getNewSessionWelcomePhrases` falls back to default phrases when `mode: 'replace'` resolves to an empty custom list, which conflicts with the reporter's expectation of no welcome message.

## Change summary

With `sessions.chat.experimental.welcomeMessages` set to `{mode: 'replace', phrases: []}`, the new-session composer still shows a default welcome message instead of none.

## Best solution

Decide and implement the intended contract for `mode: 'replace'` with an effectively-empty phrase list in src/vs/sessions/contrib/chat/common/welcomePhrases.ts (`getNewSessionWelcomePhrases`), then update the existing test in welcomePhrases.test.ts that currently codifies the opposite (fallback-to-defaults) behavior.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/chat/common/welcomePhrases.ts`, `src/vs/sessions/contrib/chat/test/common/welcomePhrases.test.ts`
- **Validation:** A test asserting getNewSessionWelcomePhrases({ mode: 'replace', phrases: [] }, undefined) (and/or an all-empty-after-trim phrases array) returns an empty array rather than the defaults, matching whatever semantics the maintainer settles on.
- **Behavior:**

  > When `sessions.chat.experimental.welcomeMessages` is configured with `mode: 'replace'` and an empty (or effectively empty, post-trim) `phrases` list, the new-session composer should show no welcome message at all — not fall back to the built-in default phrases. Non-empty replace/append configurations are unaffected. Acceptance: `getNewSessionWelcomePhrases` returns `[]` for this configuration, and `NewChatWidget`'s `_updateWelcomeMessage` (which already no-ops on an empty phrases array) renders nothing.
- **Trace:**

  > Root cause is in `getNewSessionWelcomePhrases` (src/vs/sessions/contrib/chat/common/welcomePhrases.ts, lines 70-79): the branch `if (configuration?.mode === 'replace' && customPhrases.length > 0) return customPhrases;` means an empty-after-filtering custom list under `mode: 'replace'` falls through to the default-phrases return. This is not an untested oversight — src/vs/sessions/contrib/chat/test/common/welcomePhrases.test.ts's `replacedWithoutPhrases` case deliberately asserts the fallback-to-defaults outcome for `mode: 'replace', phrases: ['  ']`. The open question is whether that deliberate contract should change (and for which case — an explicitly empty `phrases: []` vs. phrases that merely trim/resolve to empty), since this new issue argues the opposite of what the test currently encodes. Do not touch `resolveWelcomePhraseTemplate` or the `append` mode path; `NewChatWidget._updateWelcomeMessage` (browser/newChatWidget.ts) already correctly suppresses rendering when given an empty phrases array, so the fix is confined to `getNewSessionWelcomePhrases`'s fallback logic.
- **Open decisions:**
  - Should `mode: 'replace'` with an effectively empty phrase list suppress the welcome message entirely (returning []), reversing the behavior the existing test currently asserts?
  - If so, does this apply uniformly to any list that resolves to empty after filtering (e.g. all-whitespace entries), or only to a literally empty `phrases: []` as in this report — i.e. should whitespace-only entries still be treated as 'no real phrases given, fall back to defaults'?

## Evidence

- **source trace:** src/vs/sessions/contrib/chat/common/welcomePhrases.ts lines 70-79: `getNewSessionWelcomePhrases` only returns `customPhrases` when `mode === 'replace' && customPhrases.length > 0`; otherwise it falls through to `[...getDefaultWelcomePhrases(accountName), ...customPhrases]`, so `phrases: []` under `mode: 'replace'` yields the default phrases, not an empty list.
- **conflicting existing test:** src/vs/sessions/contrib/chat/test/common/welcomePhrases.test.ts, test 'appends, replaces, and falls back to the default phrases', case `replacedWithoutPhrases = getNewSessionWelcomePhrases({ mode: 'replace', phrases: ['  '] }, undefined)` explicitly asserts the result equals `defaults` — i.e. the current fallback-to-defaults behavior was a deliberate, tested design choice that this new issue now disputes.
