# Issue #332917 — BYOK OpenRouter: hover shows Max context 1M instead of 256K for ":free" variants (discovery prefers top-level context_length over top_provider.context_length)

[https://github.com/microsoft/vscode/issues/332917](https://github.com/microsoft/vscode/issues/332917)

## Summary

Confirmed on current main: `resolveModelCapabilities` in the OpenRouter BYOK provider unconditionally prefers `context_length` over `top_provider.context_length`, which surfaces the parent model's inflated window for `:free` route variants — but the naive fix isn't trivial because that same preference was deliberately added to fix a different regression (issue #324671), and simply flipping to `min()` would break that case.

## Change summary

OpenRouter BYOK hover/context-window computation shows the parent model's larger context window (e.g. 1M) instead of the correct, smaller window for `:free` route variants (e.g. 256K), risking truncation/failures above the true limit.

## Best solution

In extensions/copilot/src/extension/byok/vscode-node/openRouterProvider.ts (resolveModelCapabilities), reconcile this with the existing #324671 fix and its test suite (test/openRouterProvider.spec.ts) — a plain `min(context_length, top_provider.context_length)` regresses the `xiaomi/mimo-v2.5` case that test explicitly protects, so the fix needs a way to distinguish 'top_provider window is smaller because it's stale/parent data' (this issue) from 'top_provider window is smaller because it's genuinely the binding constraint' (#324671's case) — e.g. keying off the `:free` suffix, per-route pricing, or querying the unfiltered `/models` endpoint for confirmation — before landing a change.
