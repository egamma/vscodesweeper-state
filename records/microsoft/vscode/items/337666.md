# Issue #337666 — 1.139 can not see Use Dev Container menu for remote host

[https://github.com/microsoft/vscode/issues/337666](https://github.com/microsoft/vscode/issues/337666)

## Summary

Team-authored bug in the experimental Agents-window Dev Container feature (`chat.agentHost.devContainer.enabled`); I traced the gating logic that likely causes this but found no fix commit, so it stays open per the team-authored keep-open rule.

## Change summary

With chat.agentHost.devContainer.enabled on, the 'Use Dev Container' submenu appears for a local workspace but not for the equivalent SSH remote-host workspace, even though the same repo and devcontainer config are used.

## Best solution

Diagnose in src/vs/sessions/contrib/providers/remoteAgentHost/browser/remoteAgentHostSessionsProvider.ts (`supportsDevContainerWorkspace`) and devContainerAgentHostConnector.contribution.ts (`DevContainerAgentHostConnector.isAvailable`) whether the remote connection's capability negotiation (`supportsAgentHostDevContainers(connection.initializeResult.get())`) or `connection.devContainerService` is the blocker for SSH-backed remote hosts, and either fix the capability check or document this as a current limitation.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/providers/remoteAgentHost/browser/remoteAgentHostSessionsProvider.ts`, `src/vs/sessions/contrib/providers/remoteAgentHost/electron-browser/devContainerAgentHostConnector.contribution.ts`, `src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts`
- **Validation:** A test confirming that an SSH-backed remote agent-host connection with a valid devcontainer.json and matching capability reports `isDevContainerWorkspaceAvailable` as true (or an explicit as-designed answer if capability is genuinely absent for SSH hosts).
- **Trace:**

  > The Dev Container submenu in sessionWorkspacePicker.ts is gated by provider.isDevContainerWorkspaceAvailable, which for remote sessions delegates to RemoteAgentHostSessionsProvider.supportsDevContainerWorkspace (scheme/authority/hostGroup checks) and then DevContainerAgentHostConnector.isAvailable, which additionally requires the connection to report supportsAgentHostDevContainers() and expose connection.devContainerService. The open question is whether SSH-backed connections are expected to advertise this capability today; nothing on the record (issue, code comments, or related issues) settles that.
- **Open decisions:**
  - Should SSH remote-host connections advertise devcontainer capability (supportsAgentHostDevContainers) the same way local/tunnel connections do, or is Dev Container support intentionally unavailable for plain SSH hosts today?
  - If capability negotiation is the blocker, does the fix belong in the remote agent-host protocol/connector, or is this still a work-in-progress feature gap that should just be documented?

## Evidence

- **menu gating:** src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts `createWorkspaceModeActions` only renders the Use Dev Container/Use Remote Host toggle when `_isDevContainerWorkspaceAvailable(folderUri, providerId)` returns true (line ~1631).
- **remote provider gate:** src/vs/sessions/contrib/providers/remoteAgentHost/browser/remoteAgentHostSessionsProvider.ts:746-751 `supportsDevContainerWorkspace` requires the workspace URI scheme to be AGENT_HOST_SCHEME with a matching connection authority and no hostGroup/worktree scope — any mismatch silently hides the menu.
- **capability check:** src/vs/sessions/contrib/providers/remoteAgentHost/electron-browser/devContainerAgentHostConnector.contribution.ts:321-331 `isAvailable` for non-local URIs requires `supportsAgentHostDevContainers(connection.initializeResult.get())` and a present `connection.devContainerService`; if the SSH-backed connection doesn't advertise this capability, the menu never appears even with a valid devcontainer.json.
- **no fix found:** git log on both files shows no recent commit referencing issue #337666 or clearly addressing this gap; most recent related commit (280a9749) is an unrelated perf change.
