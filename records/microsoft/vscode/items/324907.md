# Issue #324907 — Copilot Agent built-in list_dir returns unbounded output for large directories and freezes/poisons the chat session

[https://github.com/microsoft/vscode/issues/324907](https://github.com/microsoft/vscode/issues/324907)

## Summary

The reporter confirmed the freeze on then-current stable after upgrading, and the related Remote-SSH report is newer, so it cannot be the canonical duplicate under the re-review rules. Keep this issue open as the original report of unbounded `list_dir` output poisoning chat history.

## Change summary

Bound built-in `list_dir` results for very large directories so oversized tool output cannot freeze the workbench or contaminate subsequent chat turns.

## Best solution

Limit and explicitly truncate directory-listing tool results before they enter chat history, while returning enough metadata for the agent to narrow or paginate its request; also ensure rendering and context assembly remain responsive when historical tool results are unusually large.

## Plan brief

- **Likely files:** `extensions/copilot/src`, `src/vs/workbench/contrib/chat`
- **Validation:** Create a controlled directory with roughly 100,000 entries, invoke the built-in directory-listing tool through Agent mode, and verify that the returned/stored result is bounded with an explicit truncation indication, the chat remains interactive, and reopening or continuing that conversation does not resend or render an unbounded listing.
- **Behavior:**

  > When Agent mode inspects a directory containing tens of thousands of entries, the built-in directory-listing result must be bounded and clearly indicate that additional entries were omitted. The workbench and chat must remain responsive during and after the tool call, including when the conversation is continued or restored. Small directory listings must retain their existing useful behavior.
- **Trace:**

  > The reporter observed a built-in `list_dir` call returning all 87,348 filenames, after which the same chat became persistently slow while a new chat remained responsive; reproduction was confirmed on VS Code 1.128.0. Investigation should trace the directory-listing implementation in `extensions/copilot/src`, the serialization/persistence of tool results, and historical tool-result rendering/context assembly under `src/vs/workbench/contrib/chat`. The boundary is all filesystem and text-search tool outputs that can become unbounded, but ordinary small results and remote filesystem semantics must not change. The newer related report https://github.com/microsoft/vscode/issues/334726 may provide additional Remote-SSH evidence but cannot replace this issue as canonical.
- **Open decisions:**
  - What user-observable truncation contract should the built-in directory-listing tool expose: a fixed entry/byte limit only, or a continuation mechanism that lets the agent request additional pages?
  - Should oversized historical tool results already stored in conversations be truncated when restored or rendered, or should bounding apply only when new results are produced?

## Evidence

- **confirmed reproduction:** The reporter reproduced on VS Code 1.128.0 after the automated upgrade request, using a Remote Tunnel workspace and a directory containing 87,348 entries; a new uncontaminated chat remained responsive.
