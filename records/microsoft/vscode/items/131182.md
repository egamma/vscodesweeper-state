# Issue #131182 — [api] memento onDidChange api

[https://github.com/microsoft/vscode/issues/131182](https://github.com/microsoft/vscode/issues/131182)

## Summary

The requested extension-state notification API is still missing: current code refreshes globalState internally without exposing a change event to extensions. Keep this accepted Backlog request open for API design; the existing area labels are appropriate.

## Change summary

Expose notifications when an extension's persisted Memento values change in another VS Code window.

## Best solution

Provide an extension-scoped state-change API so extensions can react to cross-window globalState updates without using secret storage as a broadcast channel. API owners should settle event payload, notification semantics, and whether workspaceState is included before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostMemento.ts`, `src/vs/workbench/api/common/extHostStorage.ts`, `src/vs/workbench/api/browser/mainThreadStorage.ts`
- **Validation:** Use a test extension in two windows sharing a profile: update, replace, and delete its globalState keys in one window, and verify the other receives the agreed notifications and reads the updated state in its callback. Check local-write behavior against the chosen contract, verify another extension's state produces no notification, and confirm subscription disposal stops callbacks.
- **Behavior:**

  > Extensions currently cannot subscribe to changes in their Memento values made by another window, despite globalState being refreshed internally. The desired outcome is a supported state-change notification API that avoids fake secret writes or an external broadcast service. Acceptance should cover additions, replacements, and deletions across two windows sharing a profile, with the new value readable when notification arrives. Notifications must remain scoped to the owning extension; local-write semantics and workspaceState coverage require an explicit API contract.
- **Trace:**

  > MainThreadStorage in src/vs/workbench/api/browser/mainThreadStorage.ts watches StorageScope.PROFILE changes for initialized shared extension storage and forwards the serialized state through $acceptValue(). ExtHostStorage in src/vs/workbench/api/common/extHostStorage.ts parses that state and emits onDidChangeStorage, which ExtensionMemento in src/vs/workbench/api/common/extHostMemento.ts consumes to replace _value without exposing an extension-facing event. The stable Memento declaration in src/vscode-dts/vscode.d.ts contains no event, and no matching proposed declaration was found. The existing main-thread listener handles shared/profile state, so equivalent workspaceState notification behavior is not established by this trace. Preserve existing persistence, update batching, JSON serialization, and setKeysForSync semantics; this request is not an atomic-write or general inter-extension messaging API. The discussion at https://github.com/microsoft/vscode/issues/131182 establishes cross-window demand but does not settle the public event contract.
- **Open decisions:**
  - Should notifications cover only globalState, or also workspaceState changes across windows sharing a workspace?
  - Should the event identify each changed Memento key, or signal that the extension's state snapshot changed?
  - Should the event fire for writes made in the subscribing window as well as external writes, and should updates that leave the stored value unchanged produce a notification?
