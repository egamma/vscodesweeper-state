# Issue #73780 — Add more flexible Decorations or editor overlays for extensions

[https://github.com/microsoft/vscode/issues/73780](https://github.com/microsoft/vscode/issues/73780)

## Summary

Keep open: current guide settings do not expose extension-defined semantic guides or editor overlays, and the public decoration API still leaves a meaningful gap. With 523 upvotes and an accepted Backlog milestone, this warrants an extension-API design discussion rather than a staleness close.

## Change summary

Provide extensions with reliable, layout-neutral editor drawing capabilities for semantic guides and other custom visualizations.

## Best solution

Agree on a supported extension API for editor-anchored visualizations, using Flutter parent/child guides as the initial acceptance case. Keep language-specific semantics in extensions while defining the rendering, positioning, and update contract in VS Code.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/browser/mainThreadEditors.ts`, `src/vs/editor/browser/editorBrowser.ts`, `src/vs/editor/browser/viewParts/indentGuides/indentGuides.ts`
- **Validation:** The plan should define an executable extension-host/rendering check plus a manual Flutter-guide scenario: draw multiple parent/child guides across blank lines, vary fonts and line height, edit and scroll the document, and verify correct anchoring without changes to text layout. Preserve existing decoration and built-in guide behavior.
- **Behavior:**

  > Extensions need to draw editor-anchored visualizations without altering code layout or relying on box-drawing glyphs. The initial acceptance case is Flutter parent/child guides with continuous vertical segments and correctly anchored horizontal connections, including across blank lines and under different fonts and line heights. Guides should remain aligned through edits and scrolling. The broader discussion also requests custom live visualizations, so the supported scope must be explicitly agreed rather than assumed to be satisfied by bracket guides.
- **Trace:**

  > The stable DecorationRenderOptions and TextEditor contracts in src/vscode-dts/vscode.d.ts provide styled ranges and text/image attachments, not overlay drawing or pixel geometry access. MainThreadEditors.$registerTextEditorDecorationType in src/vs/workbench/api/browser/mainThreadEditors.ts forwards those options to the code editor service. Internally, src/vs/editor/browser/editorBrowser.ts offers overlay widgets and visible-position geometry, and src/vs/editor/browser/viewParts/indentGuides/indentGuides.ts renders guides from internal view-model data. This confirms an extension-access boundary, not a diagnosed defect requiring a small patch. Preserve existing decoration semantics, built-in guide settings, and editor responsiveness; Flutter-specific relationship discovery belongs in the extension. https://github.com/microsoft/vscode/issues/54147 concerns edit tracking and https://github.com/microsoft/vscode/issues/237095 concerns decoration offsets, so neither replaces this request. Uncertainty begins at the public contract: constrained semantic drawing versus general custom visual content.
- **Open decisions:**
  - Should the initial API support only declarative editor-anchored guides and drawing primitives, or also arbitrary custom visual content such as the live widgets requested in the discussion?
  - Should extensions supply document anchors that VS Code positions and updates, or receive pixel geometry and viewport updates to manage their own drawing surface?
  - Is the initial visualization surface non-interactive, or must it support focusable and interactive content with a corresponding accessibility contract?
