# Issue #336472 — Separate agent task completion from long-running background processes

[https://github.com/microsoft/vscode/issues/336472](https://github.com/microsoft/vscode/issues/336472)

## Summary

Reasonable architectural request for the Agents window/agent-host: separate a session's task-completion state from the lifetime of an intentionally-left-running background process. It's already routed to the right areas (agents-window, agent-host); a possibly-related report (#336348, narrower symptom) exists but I can't verify scope overlap or ordering with confidence, so I'm not proposing a duplicate close.

## Change summary

Let an agent session report task completion (and send its completion notification) even while a background process it started (e.g. an emulator) keeps running, instead of showing 'Thinking...'/'Analyzing...' indefinitely.

## Best solution

A maintainer should decide the ownership model (e.g. a dedicated sub-session owning the long-running process vs. a status flag on the same session) and the resulting Agents window state semantics before implementation begins; the request is coherent but the design has multiple viable shapes.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost`, `src/vs/workbench/contrib/chat/browser/agentSessions`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatThinkingContentPart.ts`
- **Validation:** A test asserting that once the agent's response/task stream ends, the session/Agents-window state transitions to a distinct 'complete, background process running' status rather than remaining in an active/thinking state while a spawned long-running process (e.g. an attached async shell) is still alive.
- **Behavior:**

  > When an agent intentionally leaves a long-running process (e.g., an emulator or attached background shell) running after finishing the requested task, the session should report task completion (including the normal completion notification) instead of continuing to show 'Thinking...'/'Analyzing...'. The Agents window should be able to show a distinct state (e.g. 'Task complete · background process running') that clearly separates finished agent work from the still-active background process.
- **Trace:**

  > No current code path models this distinction: session/task 'done' state appears tied to the underlying process/session still being alive, and the Agents window progress/status rendering (e.g. stateToProgressAdapter, chatThinkingContentPart) has no notion of a completed-but-still-hosting-a-background-process state. A related, narrower symptom report exists at https://github.com/microsoft/vscode/issues/336348. The open question is architectural: whether the background process should be owned by a separate child/sub-session (as the reporter suggests) or tracked via a status flag on the same session, and what the exact Agents window state string/semantics should be.
- **Open decisions:**
  - Should a long-running background process be moved to a dedicated child/sub-session that other sessions can interact with, or should the same session just gain a 'complete but has active background process' status flag?
  - What exact UI state/label should the Agents window show for this case, and should it differ from the normal 'complete' state in the completion notification itself?
  - Should the completion notification fire as soon as the agent's response stream ends regardless of any spawned process, or only for processes explicitly marked as 'intentionally left running'?
