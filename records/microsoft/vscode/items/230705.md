# Issue #230705 — Can't create Breakpoint with custom mode from extension

[https://github.com/microsoft/vscode/issues/230705](https://github.com/microsoft/vscode/issues/230705)

## Summary

The extension API still lacks supported breakpoint-mode creation, and the current serialization path drops the label needed by the Breakpoints view. Keep this accepted Backlog request open; a newer report independently describes the same gap but cannot serve as the canonical for this re-reviewed item.

## Change summary

Allow extensions to create source breakpoints with custom DAP modes whose labels appear correctly in the Breakpoints view.

## Best solution

Define a supported extension API contract for breakpoint modes and ensure extension-created breakpoints display the corresponding adapter-provided label. Coordinate the overlapping API request at https://github.com/microsoft/vscode/issues/304764 while retaining this older report.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTypes.ts`, `src/vs/workbench/api/common/extHostDebugService.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadDebugService.ts`, `src/vs/workbench/contrib/debug/common/debugModel.ts`, `src/vs/workbench/contrib/debug/browser/breakpointsView.ts`
- **Validation:** Using a debug adapter advertising source breakpoint mode foo with label Foo, create a source breakpoint through the agreed extension API. Verify that the adapter receives mode foo and the Breakpoints view displays Foo without opening Edit Mode; repeat with no mode and confirm existing behavior is unchanged.
- **Behavior:**

  > An extension must be able to create a source breakpoint with an adapter-advertised mode through a supported API. The adapter must receive the selected mode, and the Breakpoints view must show its corresponding human-readable label without requiring a manual edit. Ordinary breakpoints without a mode must retain their existing behavior.
- **Trace:**

  > The report injects mode and modeLabel into a SourceBreakpoint because neither is exposed by src/vscode-dts/vscode.d.ts. ExtHostDebugService.addBreakpoints serializes mode but drops modeLabel; ISourceMultiBreakpointDto and MainThreadDebugService.$registerBreakpoints also omit the label. DebugModel.addBreakpoints preserves rawBp.modeLabel rather than resolving it, and BreakpointsRenderer.renderBreakpointCommon requires that label to display the mode. The existing debug.editBreakpointMode action supplies both values after a manual picker selection, which does not cover extension-driven creation. Current source establishes this boundary without executing code. The newer overlapping request https://github.com/microsoft/vscode/issues/304764 should inform API design; exception-breakpoint DAP transmission in https://github.com/microsoft/vscode/issues/272410 is separate. Uncertainty starts at the public API contract and ownership of label resolution, not at whether the current serialization omits the label.
- **Open decisions:**
  - Should extensions specify only an adapter mode identifier, with VS Code resolving its display label, or should the public API also accept a display label for creation before adapter capabilities are available?

## Evidence
