# Issue #337688 — Agent host crash-loops with V8 OOM when a large Claude session (GB-sized subagent transcripts) is restored, taking down all sessions

[https://github.com/microsoft/vscode/issues/337688](https://github.com/microsoft/vscode/issues/337688)

## Summary

Real, well-diagnosed bug: the Claude agent host loads a session's full JSONL transcript into memory with no streaming/paging cap, and because all sessions for a provider share one agent host process, one oversized transcript OOMs the whole process and, after 5 restarts, takes down every other session too.

## Change summary

Restoring one GB-scale Claude session OOMs the shared agent host process and, after it exhausts its restart budget, breaks every other open session.

## Best solution

Cap or stream what's loaded per session (avoid materializing the entire JSONL transcript / all subagent transcripts as in-memory arrays), and make a single session's failure isolated rather than exhausting a shared process's restart budget for every other session.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentHostService.ts`, `src/vs/platform/agentHost/node/claude/claudeSubagentResolver.ts`, `src/vs/platform/agentHost/node/claude/claudeReplayMapper.ts`
- **Validation:** A regression/integration test asserting that restoring or listing an oversized session (large transcript/many subagent transcripts) does not exhaust the shared process's restart budget and does not prevent other sessions from opening.
- **Behavior:**

  > Opening or restoring a single very large agent session (GB-scale main transcript and/or thousands of subagent transcripts) must not crash the shared agent host process, and even if that one session fails to load, every other session must remain usable. Acceptance: a synthetic oversized session fails gracefully (or loads with truncated/paged history) without triggering repeated V8 OOM restarts, and unrelated sessions continue to open normally in the same window.
- **Trace:**

  > `fetchParentTurns` (src/vs/platform/agentHost/node/claude/claudeSubagentResolver.ts) and the live replay path call `IClaudeAgentSdkService.getSessionMessages(...)`, which returns the full on-disk JSONL transcript as an in-memory `SessionMessage[]` with no size cap; `mapSessionMessagesToTurns` (claudeReplayMapper.ts) then builds the full `Turn[]` structure from it. Separately, `AgentHostProcessManager._handleProcessExit` (agentHostService.ts) tracks `_restartCount` against `Constants.MaxRestarts` per process, not per session — once exhausted, `_restartLimitReached` blocks all further starts, which is why the reporter sees every other session fail after the large one crash-loops. The boundary: do not change the SDK message shape or the turn-building logic itself; the intended fix scope is (a) bounding/streaming what gets loaded per session and (b) isolating one session's failure from the shared process's restart budget. Related but not duplicative: https://github.com/microsoft/vscode/issues/336200 (renderer OOM), https://github.com/microsoft/vscode/issues/335232 (tunnel-specific Agent Host OOM).
- **Open decisions:**
  - Should oversized sessions be truncated/paged (partial history shown) or refused outright with a clear error, rather than attempting a full load?
  - Should the restart-and-give-up policy become per-session rather than per-process, so one bad session can't block others from ever opening?
  - Is there a size/turn-count threshold above which a session is treated as 'too large to restore' at all, and where is that surfaced to the user?

## Evidence

- **unbounded transcript load:** src/vs/platform/agentHost/node/claude/claudeSubagentResolver.ts:fetchParentTurns calls `sdk.getSessionMessages(ctx.parentSessionId, { includeSystemMessages: true })` and feeds the full result into `mapSessionMessagesToTurns` — no size/streaming guard; reporter confirmed the crash reproduces even with only the 268MB main transcript (subagents renamed away).
- **shared-process blast radius:** src/vs/platform/agentHost/node/agentHostService.ts `_handleProcessExit` restarts the single shared agent host process up to `Constants.MaxRestarts` times and then sets `_restartLimitReached`, logging 'giving up after N restarts' — this is a per-process (not per-session) limit, matching the reporter's observation that all sessions fail once the limit is hit.
- **reporter's own confirmation:** Comment from 2026-09-24 isolates the main transcript alone (268MB) as sufficient to crash-loop, and notes the crash point (~3.2GB) sits close to Electron's pointer-compressed V8 heap cap, so raising heap limits isn't a workaround.
- **related but distinct reports:** https://github.com/microsoft/vscode/issues/336200 is a renderer-side OOM from large chat history, and https://github.com/microsoft/vscode/issues/335232 is an Agent Host OOM specific to tunneled sessions — neither is the same reporter-observable symptom (agent-host-process-wide crash-loop from local session restore) as this issue, so this stays open rather than closing as a duplicate of either.
