# Issue #337688 — Agent host crash-loops with V8 OOM when a large Claude session (GB-sized subagent transcripts) is restored, taking down all sessions

[https://github.com/microsoft/vscode/issues/337688](https://github.com/microsoft/vscode/issues/337688)

## Summary

Well-diagnosed report: the reporter isolated the crash with a controlled before/after test (renaming the subagents/ folder), and the codebase confirms the architecture that makes it severe — a single agent host process serves every session, so one session's OOM kills all of them. Real gap, but the exact fix location (host-side mitigation vs. upstream SDK behavior) isn't settled from the checkout alone, so this needs routing/planning rather than a blind agent implementation.

## Change summary

Opening/restoring one very large Claude session (GB-scale subagent transcripts) OOMs the shared agent host process, crash-looping it and taking every other session down with it.

## Best solution

Agent host session load/restore should be resilient to one oversized session: fail that session's load without crashing the shared host process (or run risky loads with a memory/time budget), and separately investigate whether `@anthropic-ai/claude-agent-sdk`'s `getSessionMessages`/session load path is itself reading more of the subagents directory than the host's own lazy-load design (documented in claude/CONTEXT.md) accounts for.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/claude/claudeAgent.ts`, `src/vs/platform/agentHost/node/claude/claudeAgentSdkService.ts`, `src/vs/platform/agentHost/node/nodeAgentHostStarter.ts`
- **Validation:** A reproduction (even synthetic, e.g. a large generated subagents/ directory) that previously OOM'd the agent host process should instead fail only the affected session with a clear error, leaving other sessions and the shared process alive.
- **Behavior:**

  > Restoring/opening a Claude session whose subagent transcripts are very large (GB-scale) must not crash the shared agent host process. The affected session may fail to open with a clear error, but every other open session and the process itself must remain usable. Acceptance: simulate a session with an oversized subagents/ directory and confirm the host survives and other sessions keep working.
- **Trace:**

  > claudeAgent.ts's `_openTurns`/replay path calls `this._sdkService.getSessionMessages(sdkSessionId, ...)` (a thin pass-through to the third-party `@anthropic-ai/claude-agent-sdk`, see claudeAgentSdkService.ts) once per session open; per claude/CONTEXT.md, subagent transcripts are documented as lazily fetched only when a subagent marker is clicked, and `primeFromTranscript` only scans the already-loaded parent turns. Despite that documented design, the reporter's isolation test (renaming subagents/) stops the OOM, suggesting the SDK's own session-load internals may read more of the session directory than the host code above assumes. The single agent host process backs every session (see agentHostProcessTelemetry.ts's restartCount/willRestart), so any OOM there brings down all sessions after 5 restarts. Do not touch the subagent lazy-load contract described in CONTEXT.md without first confirming where the excess read is actually happening — that's the open question a plan phase should resolve before any code change.
- **Open decisions:**
  - Should a single session's oversized load fail gracefully (session-scoped error) rather than crash the shared host process, and if so, via a memory/size guard, a timeout, or a separate process per session?
  - Is the excess memory usage actually inside the third-party Claude SDK's session-load implementation (requiring an upstream report/fix) or somewhere in this repo's host code not yet identified?
  - Should the host expose a configurable heap size / cap on transcript size it will attempt to load automatically?

## Evidence

- **single shared process:** src/vs/platform/agentHost/common/agentHostProcessTelemetry.ts tracks restartCount/willRestart for the agent host process as a whole — one process backs all sessions, matching the reporter's observation that one huge session's crash takes down every other session's availability.
- **documented lazy design:** src/vs/platform/agentHost/node/claude/CONTEXT.md states subagent transcripts are 'fetched lazily, never eagerly' and that opening a parent session only calls the SDK's getSessionMessages for the parent transcript (claudeAgent.ts lines ~1108/1676/2010), with subagent correlation (`primeFromTranscript`) scanning only the already-loaded parent turns, not the subagents/ directory — so per VS Code's own code, the 9.4GB subagents folder should not need to be read merely to restore the session. This means the excess memory usage most plausibly originates inside the third-party `@anthropic-ai/claude-agent-sdk`'s own session-load implementation (a dependency this repo doesn't own), not something visibly traceable in this checkout.
- **reporter's controlled repro:** Reporter's own evidence table shows repeated OOM crashes only on launches that touch the large session (16-57 log-line matches per crash) vs. zero crashes across 4 launches that didn't touch it, and confirms renaming the session's subagents/ folder away stops the crash while the main transcript still restores — a genuine, methodical reproduction even though I could not execute it myself against the actual multi-GB fixture.
