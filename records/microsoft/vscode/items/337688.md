# Issue #337688 — Agent host crash-loops with V8 OOM when a large Claude session (GB-sized subagent transcripts) is restored, taking down all sessions

[https://github.com/microsoft/vscode/issues/337688](https://github.com/microsoft/vscode/issues/337688)

## Summary

Still a real, unaddressed gap: the Claude session restore path loads full transcripts/subagent history in-process with no cap or streaming, and AgentHostProcessManager's crash-recovery logic (giving up after 5 restarts) takes the whole agent host down for all sessions once one session's restore OOMs — exactly as reported, with no fix commit found.

## Change summary

Restoring one Claude session with a GB-scale transcript/subagent history OOMs the agent host process, which then exhausts its 5 restart attempts and takes every other session down with it.

## Best solution

Cap or stream what's loaded per session during Claude transcript/subagent restoration, and make a single session's repeated failure isolate to that session (e.g. mark it unrestorable) instead of exhausting the shared MaxRestarts budget in AgentHostProcessManager and killing unrelated sessions.

- **Trace:**

  > Root structural issue traced to src/vs/platform/agentHost/node/agentHostService.ts's AgentHostProcessManager: `_handleProcessExit` increments a single shared `_restartCount` across all sessions and, after `Constants.MaxRestarts` (5), sets `_restartLimitReached`, after which every session fails to start — there is no per-session isolation. Separately, no cap/streaming for Claude transcript or subagent-transcript loading was found under src/vs/platform/agentHost/node/claude/. Where uncertainty starts: whether the fix belongs in the Claude SDK bridge (stream/cap history) or in the process manager (isolate repeated-crash sessions, e.g. skip restoring a session that OOM'd N times), and whether a size/age cap on subagent history is itself the right product behavior.
- **Open decisions:**
  - Should the agent host cap or stream subagent/main transcript loading at restore time, and if so what's the cap (size, turn count, age)?
  - When a specific session repeatedly OOMs the process, should it be marked as unrestorable/skipped rather than consuming the shared restart budget that currently takes down every other session?
  - Should list/discovery (listSessions) even attempt to read huge subagent folders, or should those be lazily loaded only on explicit open?

## Evidence

- **crash-recovery structure:** src/vs/platform/agentHost/node/agentHostService.ts: `_handleProcessExit` restarts up to `Constants.MaxRestarts` (5) on any unexpected exit, then sets `_restartLimitReached = true` and all future `_ensureStarted()` calls reject with 'Agent Host process stopped after 5 restarts' — this is process-wide, not per-session, matching the reporter's observation that every other session fails once the large one crash-loops.
- **no streaming/cap found:** No code under src/vs/platform/agentHost/node/claude/ (claudeAgentSession.ts, claudeSessionMetadataStore.ts) implements streaming, pagination, or a size cap for subagent transcripts; restore appears to rely on the Claude SDK loading full history into memory.
- **reproduction detail:** Reporter isolated the defect to the main transcript alone (268MB) reproducing the same OOM after removing the 9.4GB subagents folder, and confirmed a second ~1GB-transcript session is equally at risk — a credible, detailed repro even though we did not execute it.
