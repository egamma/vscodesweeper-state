# Issue #50952 — onEnterRules should be multi-line aware

[https://github.com/microsoft/vscode/issues/50952](https://github.com/microsoft/vscode/issues/50952)

## Summary

Current onEnterRules can inspect the immediately preceding line, but cannot match arbitrary multiline context or derive indentation from the beginning of a multiline expression. That leaves a meaningful gap beyond the reportedly resolved C++ comment-continuation example; no verified canonical absorbs the full request.

## Change summary

Allow language-defined Enter rules to use multiline context when deciding comment continuation and expression-relative indentation.

## Best solution

Define a bounded, declarative multiline-context contract for language Enter rules, preserving responsive typing and compatibility with existing rules. Agree on context and indentation-anchor semantics before implementing the editor and extension-facing changes.

## Plan brief

- **Likely files:** `src/vs/editor/common/languages/languageConfiguration.ts`, `src/vs/editor/common/languages/supports/onEnter.ts`, `src/vs/editor/common/languages/supports/indentationLineProcessor.ts`, `src/vs/editor/common/languages/enterAction.ts`, `src/vs/workbench/contrib/codeEditor/common/languageConfigurationExtensionPoint.ts`, `src/vscode-dts/vscode.d.ts`, `src/vs/editor/test/common/modes/supports/onEnter.test.ts`
- **Validation:** After agreeing on the contract, add focused editor tests for context spanning more than one preceding line, multiline function-header indentation, and comment-versus-multiplication distinction. Run the targeted OnEnterSupport suite through scripts/test.sh and the corresponding Enter-action tests; existing single-line and previousLineText behavior must remain unchanged.
- **Behavior:**

  > Language authors need Enter behavior that can distinguish multiline syntactic context rather than relying only on the current and immediately preceding lines. The supplied examples require avoiding comment leaders in ordinary multiplication and starting a function body one indent inside the function declaration rather than inside its aligned parameter continuation. Acceptance must include constructs spanning more than two lines and preserve existing rule behavior. The session must establish which of these outcomes the new contract guarantees rather than assuming additional context alone provides expression-relative indentation.
- **Trace:**

  > OnEnterRule in src/vs/editor/common/languages/languageConfiguration.ts exposes separate beforeText, afterText, and previousLineText expressions. OnEnterSupport.onEnter evaluates those expressions independently; IndentationContextProcessor in src/vs/editor/common/languages/supports/indentationLineProcessor.ts supplies only the immediately preceding line. getEnterAction in src/vs/editor/common/languages/enterAction.ts computes the initial indentation at the cursor, so wider matching and expression-relative indentation are separate concerns. Preserve embedded-language boundaries, existing rule semantics, and responsive synchronous Enter handling. https://github.com/microsoft/vscode/issues/66235 records related alignment requirements and renderer-process constraints, but is newer and not a duplicate canonical. Source inspection establishes the capability boundary, not a runtime reproduction of either C++ example; the design uncertainty begins with the amount of exposed context and the indentation anchor available to actions.
- **Open decisions:**
  - Should multiline rules receive a bounded preceding-text window or a syntactically delimited expression/block, and what context boundary is guaranteed to extension authors?
  - Does this request include anchoring indentation to the beginning of a matched multiline construct, or only exposing additional text for rule matching?
