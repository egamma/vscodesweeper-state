# Issue #763 — Hide empty folders after apply file exclusions (user settings)

[https://github.com/microsoft/vscode/issues/763](https://github.com/microsoft/vscode/issues/763)

## Summary

This remains an accepted Explorer feature request with 33 community upvotes and an explicit maintainer signal welcoming a setting-based implementation. Current main supports compact folders but still does not hide directories whose descendants are all removed by exclusion filters.

## Change summary

Optionally hide Explorer folders that become empty after applying `files.exclude` or equivalent Explorer exclusions.

## Best solution

Design an opt-in Explorer setting that removes folders with no visible descendants while preserving lazy filesystem loading and acceptable performance on deep directory trees.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Add Explorer data-source/filter tests covering an excluded-only directory, a deep chain ending in an excluded file, and a directory containing at least one visible descendant; verify the chosen setting hides only the intended folders and leaves existing behavior unchanged when disabled.
- **Behavior:**

  > Users can opt in to hiding Explorer folders that have no visible descendants after file exclusions are applied. A folder containing any visible descendant remains visible, and disabling the option preserves current Explorer behavior. The accepted behavior must be defined for descendants that have not yet been loaded, and must avoid making ordinary Explorer navigation unacceptably slower.
- **Trace:**

  > `FilesFilter.isVisible` in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts evaluates exclusions one item at a time. `ExplorerDataSource.getChildren` obtains children lazily through `ExplorerItem.fetchChildren`, and `hasChildren` only filters the children currently represented by the model, so current source cannot establish recursive post-filter emptiness without additional traversal semantics. `explorer.compactFolders` in src/vs/workbench/contrib/files/browser/files.contribution.ts only compresses single-child chains and is not coverage for this request. Keep exclusion matching semantics and visible-editor exceptions unchanged; the design boundary is how directory visibility interacts with lazy resolution and performance. https://github.com/microsoft/vscode/issues/19032 is a newer duplicate pointing to this canonical issue.
- **Open decisions:**
  - Should the option hide a folder only after its loaded children establish that it is empty, allowing visibility to change as folders are resolved, or recursively inspect unresolved descendants so empty-after-exclusion folders are hidden immediately?

## Evidence

- **current source gap:** `FilesFilter.isVisible` in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts filters each item from `files.exclude` and ignore rules, but does not determine whether a directory has any visible descendants.
- **lazy-loading constraint:** `ExplorerDataSource.getChildren` calls `ExplorerItem.fetchChildren`, while `hasChildren` considers only available children through the current filter. Hiding recursively empty folders would therefore require a deliberate policy for unresolved descendants rather than an existing-capability toggle.
- **partial existing capability:** `explorer.compactFolders` is registered in src/vs/workbench/contrib/files/browser/files.contribution.ts and only compresses single-child folder chains; it does not hide folders emptied by exclusions.
- **maintainer direction:** The discussion at https://github.com/microsoft/vscode/issues/763 records maintainer openness to an opt-in setting if compact folders did not sufficiently improve the experience.
- **canonical search:** https://github.com/microsoft/vscode/issues/19032 reported the same observable request and was closed as a duplicate pointing back to this issue, supporting #763 as the canonical tracker. The other open keyword candidate, https://github.com/microsoft/vscode/issues/45177, concerns adding individual files to workspaces and does not own this behavior.
