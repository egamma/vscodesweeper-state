# Issue #184027 — Add (trace) logging to help extension author trouble shoot notebook code actions

[https://github.com/microsoft/vscode/issues/184027](https://github.com/microsoft/vscode/issues/184027)

## Summary

The requested diagnostic gap remains: notebook code-action save participants report progress and selected failures, but do not trace action selection or application. Keep this accepted Backlog request open; no verified canonical or fixing commit was found.

## Change summary

Add renderer-side trace logging that helps extension authors understand when and how notebook code actions are selected and applied.

## Best solution

Provide opt-in diagnostic traces for notebook code-action save participation, including notebook-versus-cell dispatch, provider selection, filtering, and application outcomes, while preserving existing behavior and avoiding notebook content in logs.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/notebook/browser/contrib/saveParticipants/saveParticipants.ts`, `src/vs/workbench/contrib/notebook/browser/services/notebookLoggingServiceImpl.ts`, `src/vs/editor/contrib/codeAction/browser/codeAction.ts`
- **Validation:** With trace logging enabled, save a notebook whose first cell is markdown and whose notebook action provider matches only code cells; diagnostics should explain the selected cell and absence of a matching provider. Move a matching code cell first and save again; diagnostics should identify action selection and application. Verify cell-scoped actions remain cell-scoped, existing save results are unchanged, trace messages are absent at normal log levels, and notebook contents are not logged.
- **Behavior:**

  > Extension authors should be able to enable renderer-side diagnostics and understand why configured notebook code actions did or did not run on save. Diagnostics should distinguish notebook-level and cell-level execution and explain relevant selection and application outcomes. Acceptance includes the markdown-first-cell selector mismatch from the motivating discussion and a successful application after a matching code cell becomes first. Normal logging levels and notebook save behavior must remain unchanged.
- **Trace:**

  > CodeActionOnSaveParticipant.participate in src/vs/workbench/contrib/notebook/browser/contrib/saveParticipants/saveParticipants.ts reads notebook.codeActionsOnSave, separates notebook and cell action kinds, and uses the first cell for notebook-level requests. CodeActionParticipantUtils.getActionsToRun delegates to getCodeActions in src/vs/editor/contrib/codeAction/browser/codeAction.ts, where model matching and advertised action kinds determine eligible providers; returned actions are filtered again. Existing progress messages and error/warning logs do not explain that selection path. NotebookLoggingService already supplies a trace-capable Notebook logger. The motivating selector mismatch is explained at https://github.com/microsoft/vscode/issues/183855#issuecomment-1571049948. Preserve first-cell dispatch, action filtering, cross-resource restrictions, cancellation, and save semantics; uncertainty concerns the diagnostic coverage and discoverable output surface, not whether those behaviors should change.
- **Open decisions:**
  - Should the diagnostics cover only notebook save-participant decisions, or also explain provider exclusion and action filtering in the shared code-action pipeline?
  - Should authors find these diagnostics in the existing Notebook output channel or the renderer Window log?

## Evidence

- **Motivating troubleshooting:** https://github.com/microsoft/vscode/issues/183855#issuecomment-1570262727 describes a notebook action provider not being called on save. https://github.com/microsoft/vscode/issues/183855#issuecomment-1571049948 identifies first-cell selection and a markdown-cell document-selector mismatch as the explanation, demonstrating the diagnostic need.
- **Current dispatch lacks trace diagnostics:** In src/vs/workbench/contrib/notebook/browser/contrib/saveParticipants/saveParticipants.ts, CodeActionOnSaveParticipant.participate filters notebook.codeActionsOnSave, dispatches notebook actions against notebookModel.cells[0], and dispatches cell actions across cells. These decisions have no trace logging; existing logging covers selected errors.
- **Existing capabilities are partial:** CodeActionParticipantUtils.applyOnSaveGenericCodeActions reports provider names and application titles through progress, warns about cross-resource cell edits, and silently catches application failures. src/vs/editor/contrib/codeAction/browser/codeAction.ts filters providers and returned actions without diagnostic trace logging. Progress and warnings do not provide the requested persistent explanation of selection and application.
- **Logging infrastructure already exists:** src/vs/workbench/contrib/notebook/browser/services/notebookLoggingServiceImpl.ts implements trace logging through the Notebook output logger, registered in notebook.contribution.ts. That infrastructure is not used by the inspected notebook code-action save-participant path.

Searches for notebook code-action logging and trace requests did not establish an older open canonical owning this request.
