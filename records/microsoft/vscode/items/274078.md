# Issue #274078 — Consider adding variablesReference to VSCodeDebugProtocol.EvaluateArguments

[https://github.com/microsoft/vscode/issues/274078](https://github.com/microsoft/vscode/issues/274078)

## Summary

The reporter answered the maintainer's question with a concrete gap: copying a watch result cannot identify the previously evaluated object, potentially requiring another evaluation with side effects. Current source still lacks that identity channel; keep this open for a debug-protocol design decision rather than treating evaluateName as complete coverage.

## Change summary

Allow clipboard evaluation requests to identify an existing evaluated result and its originating context instead of relying solely on expression text.

## Best solution

Agree on a backward-compatible DAP contract for copying an already evaluated result without executing the original expression again, including how scope identity and scalar results are handled. Coordinate that contract with VS Code's Copy Value implementation rather than adding an undocumented protocol field locally.

## Evidence

- **Reporter supplied the missing use case:** https://github.com/microsoft/vscode/issues/274078#issuecomment-3528201338 explains that evaluateName works for variables but EvaluateResponse cannot supply an equivalent cached-result expression. Copying the top-level watch expression some_function() sends that expression again, potentially repeating side effects; the reporter also explains the missing originating-scope information.
- **Existing capability is only partial coverage:** src/vs/workbench/contrib/debug/browser/variablesView.ts:683-731 implements workbench.debug.viewlet.action.copyValue. It uses Variable.evaluateName when available, but uses Expression.name for a top-level watch expression, then calls session.evaluate with the expression, frame ID, and clipboard context. The selected result's reference is not forwarded.
- **Current protocol boundary:** src/vs/workbench/contrib/debug/common/debugProtocol.d.ts:1395-1463 defines EvaluateArguments without variablesReference and EvaluateResponse with variablesReference but without evaluateName. src/vs/workbench/contrib/debug/browser/debugSession.ts:712-717 forwards expression, frameId, context, and optional source location, not result identity.
- **Cached identity exists in the model:** src/vs/workbench/contrib/debug/common/debugModel.ts, ExpressionContainer.evaluateExpression, retains response.body.variablesReference as this.reference. Thus the request concerns exposing retained result identity through clipboard evaluation, not merely adding the already-supported clipboard context.
- **Canonical search did not establish a duplicate:** Read and compared https://github.com/microsoft/vscode/issues/94937, which remains open but concerns truncated debug-console output, and https://github.com/microsoft/vscode/issues/54853, which is closed and concerns evaluateName handling for watch children. Neither owns this report's top-level cached-result identity and scope-provenance request, so neither satisfies the stronger duplicate bar for this re-reviewed item.
