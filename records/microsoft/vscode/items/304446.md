# Issue #304446 — Agent mode: run_in_terminal with multi-line git commit -m gets stuck in zsh dquote> mode

[https://github.com/microsoft/vscode/issues/304446](https://github.com/microsoft/vscode/issues/304446)

## Summary

Keep open: current main requests bracketed paste for macOS terminal-tool commands and provides idle-silence recovery, but neither establishes that this multiline commit failure is resolved. The supplied workflow and environment suffice to retest against the changed execution path.

## Change summary

Multiline git commit messages sent through run_in_terminal leave macOS zsh at a dquote> continuation prompt instead of completing the commit.

## Best solution

Verify that valid multiline commit commands reach zsh intact and complete with the intended message, distinguishing transport corruption from model-generated quoting errors. Preserve recovery from stalled commands without treating recovery alone as a fix for incorrect command delivery.

- **Validation:** In a disposable Git repository on macOS with standard zsh, stage a file and invoke a known-valid multiline git commit -m command through Agent mode's run_in_terminal. Repeat with safely quoted literal backticks and an em dash, and with messages below and above 1024 bytes. Compare the captured tool argument with git log -1 --format=%B, verify the shell returns to its normal prompt, and verify a subsequent terminal-tool command completes. Separately check that malformed quoting returns control through existing recovery rather than hanging the agent indefinitely.
- **Behavior:**

  > A syntactically valid multiline git commit command issued through Agent mode should complete and preserve the intended commit message, including safely quoted punctuation. It should not leave zsh waiting at dquote> because command text was altered during delivery. Acceptance should compare the resulting Git message with the intended text and confirm that a subsequent command executes normally. Malformed model-generated commands are a separate case and must not be confused with transport corruption.
- **Trace:**

  > Current RichExecuteStrategy, BasicExecuteStrategy and NoneExecuteStrategy request bracketed paste for macOS or multiline commands. TerminalInstance.sendText only inserts the delimiters if xterm reports bracketed-paste mode, then converts newlines to carriage returns and forwards the text; TerminalProcess.input currently writes directly to node-pty. RunInTerminalTool also has idle-silence promotion, introduced by https://github.com/microsoft/vscode/pull/315885, which restores model control but does not correct the submitted command. The older transport report https://github.com/microsoft/vscode/issues/296955 establishes a plausible macOS failure mode, while https://github.com/microsoft/vscode/issues/304928 supplies related commit-message symptoms without proving the same cause. The uncertainty starts at whether a valid command still becomes corrupted on this current path or the model supplied invalid quoting. Preserve normal shell interpretation, existing command approval and recovery behavior; do not introduce a Git-specific workaround as a substitute for diagnosing command delivery.

TerminalInstance.sendText in src/vs/workbench/contrib/terminal/browser/terminalInstance.ts:1397-1418 actually adds paste delimiters only when the terminal advertises bracketed-paste mode, normalizes newlines to carriage returns, and writes the text to the process.

Its diff adds an idleSilence race that moves a silent synchronous command into the background and returns control without killing it; it does not repair quoting or preserve a corrupted commit message. Current runInTerminalTool.ts retains this behavior around lines 2201-2207 and 2250-2262.
