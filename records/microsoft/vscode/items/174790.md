# Issue #174790 — Git - Support `git diftool -d`, AKA Git directory diff

[https://github.com/microsoft/vscode/issues/174790](https://github.com/microsoft/vscode/issues/174790)

## Summary

The requested Git directory-diff CLI workflow remains unsupported, despite existing multi-file comparison UI. Keep this accepted Backlog request open; the cited predecessors are closed, and no verified older open canonical was found.

## Change summary

Support Git's `git difftool --dir-diff` by comparing its two temporary directory trees in one navigable VS Code diff view.

## Best solution

Provide a directory-aware CLI comparison that presents changed files together and permits side-by-side review, using the existing multi-diff infrastructure where appropriate. Agree on rename presentation and preserve Git's temporary-file lifetime and existing file-diff behavior.

## Plan brief

- **Likely files:** `src/vs/platform/windows/electron-main/windowsMainService.ts`, `src/vs/platform/window/common/window.ts`, `src/vs/workbench/electron-browser/window.ts`, `src/vs/workbench/common/editor.ts`, `src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts`
- **Validation:** In a disposable Git repository outside the shared checkout, create two commits containing a nested modification, addition, deletion, and rename. Configure the difftool command as `code --wait --diff "$LOCAL" "$REMOTE"`, then run `git difftool --no-prompt --dir-diff HEAD~1 HEAD`. Verify that one navigable comparison contains every changed path, with the agreed rename presentation, and that Git remains waiting until review is finished. Repeat against the working tree and verify edits persist; confirm ordinary two-file `code --wait --diff` still works.
- **Behavior:**

  > Invoking `git difftool --dir-diff` with VS Code configured as the difftool should open a single navigable comparison of the supplied directory trees rather than ordinary folder workspaces. Users should be able to inspect nested changed files side by side, including additions and deletions. Comparing against the working tree should permit edits where Git exposes editable working-tree files. Git's wait-and-cleanup lifecycle and ordinary two-file diff behavior must remain intact; rename presentation requires agreement.
- **Trace:**

  > WindowsMainService in src/vs/platform/windows/electron-main/windowsMainService.ts classifies directory arguments as workspaces before selecting files for diff mode. NativeWindow.onOpenFiles and openResources in src/vs/workbench/electron-browser/window.ts handle file comparisons, while pathsToEditors in src/vs/workbench/common/editor.ts rejects directories. Existing repository-ref comparison in extensions/git/src/commands.ts demonstrates multi-diff presentation but does not bridge the shell-supplied directory inputs. NativeWindow's filesToWait handling currently follows editor resources, making temporary-directory lifetime part of the design boundary. The trace establishes the missing integration without executing code; uncertainty begins at directory comparison semantics and carrying its lifecycle through the native open request. Preserve normal folder opening, existing two-file comparisons, and Git working-tree editing behavior. Related diagnosis: https://github.com/microsoft/vscode/issues/48437#issuecomment-383965277.
- **Open decisions:**
  - Should the initial directory-diff experience identify and pair renamed files, or is presenting them as a deletion and addition an acceptable supported behavior?

## Evidence

- **Current CLI boundary:** src/vs/platform/environment/node/argv.ts:104 documents `--diff` as comparing two files. In src/vs/platform/windows/electron-main/windowsMainService.ts:1217-1223, directories become workspace inputs; lines 389-393 activate diff mode only for file inputs. Git's two directory arguments therefore do not become a directory comparison.
- **Renderer boundary:** src/vs/workbench/common/editor.ts:1684-1686 rejects directory editor inputs. src/vs/workbench/electron-browser/window.ts:1030-1094 resolves file inputs and constructs a single IResourceDiffEditorInput, without directory enumeration or multi-diff construction. This also shows why changing only the renderer location suggested in the discussion would not cover normal CLI directory routing.
- **Existing capability is partial:** extensions/git/src/commands.ts:3226-3286 implements `git.graph.compareRef` and `_openChangesBetweenRefs`, which obtains repository changes and opens `_workbench.openMultiDiffEditor`. This supports interactive comparison between Git references, but does not accept the temporary directory pair supplied by `git difftool --dir-diff`.
- **Discussion and demand:** https://github.com/microsoft/vscode/issues/174790 has 17 body upvotes and several comments supporting shell-driven multi-file review. The May and August 2024 comments suggest the multi-diff editor as a possible implementation, but contain no maintainer acceptance of the proposed design or linked implementation PR.
- **Related closed reports and precedent:** https://github.com/microsoft/vscode/issues/6898, https://github.com/microsoft/vscode/issues/48437, and https://github.com/microsoft/vscode/issues/63548 are all closed, so none is a valid duplicate canonical. The older extension-oriented position at https://github.com/microsoft/vscode/issues/6898#issuecomment-297044092 does not justify declining this subsequently accepted Backlog item. https://github.com/microsoft/vscode/issues/48437#issuecomment-383965277 independently diagnoses Git's two temporary directories being treated as folders.
- **Workaround does not cover CLI integration:** https://github.com/microsoft/vscode/issues/63548#issuecomment-1398881816 suggests the Git Tree Compare extension. The response at https://github.com/microsoft/vscode/issues/63548#issuecomment-1418352494 explicitly distinguishes interactive comparison from invoking `git difftool --dir-diff` in the shell, the central requirement here.

Local history is shallow, so absence of a matching local commit is not proof that no historical work occurred; current source nevertheless establishes the remaining capability gap.
