# Issue #243625 — Extensions should be able to open new documents wich are not dirty

[https://github.com/microsoft/vscode/issues/243625](https://github.com/microsoft/vscode/issues/243625)

## Summary

Keep this accepted API request open: current untitled-document creation still marks supplied content or an associated filename dirty, with no creation option to suppress that state. The request has 27 upvotes and reached Backlog; no verified canonical or landed implementation was identified.

## Change summary

Allow extensions to open a named, initially populated document without a temporary file or an initial dirty state.

## Best solution

Design an opt-in document-creation API that supports initial content and a filename without immediately requiring a save. Settle its editing, save, and close semantics while preserving existing untitled-document defaults.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostDocuments.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadDocuments.ts`, `src/vs/workbench/services/untitled/common/untitledTextEditorService.ts`, `src/vs/workbench/services/untitled/common/untitledTextEditorModel.ts`, `src/vs/workbench/services/untitled/test/browser/untitledTextEditor.integrationTest.ts`
- **Validation:** An extension-host acceptance scenario should create a document with nonempty content and a supplied filename without writing a temporary file, assert TextDocument.isDirty is false, and verify that opening it does not change that state. Check close, subsequent editing, and explicit Save against the agreed contract, and verify existing openTextDocument creation calls retain their dirty-state behavior.
- **Behavior:**

  > An extension can open a new document containing supplied text and a specified filename without first writing a temporary file. Its initial state is clean rather than immediately requiring a save. Acceptance must cover the displayed filename, TextDocument.isDirty, and closing before any user edit. Subsequent edits and explicit Save must follow an agreed public contract, while existing creation calls retain their current behavior.
- **Trace:**

  > workspace.openTextDocument creation options in src/vscode-dts/vscode.d.ts expose language, content, and encoding only; the extension-host creation path crosses ExtHostDocuments.createDocumentData and MainThreadDocuments.$tryCreateDocument. MainThreadDocuments._doCreateUntitled forwards content to the untitled service and explicitly reports a dirty state to the extension host. UntitledTextEditorModel initializes and resolves documents as dirty when initial content or an associated path exists, so this is an established default rather than a demonstrated bug. TextDocumentContentProvider supplies readonly virtual documents, and FileSystemProvider supplies extension-managed resources; neither adds the requested creation contract. Preserve current untitled defaults and existing provider behavior. The unresolved boundary is how a clean generated document behaves after edits, when closed, and when explicitly saved; no execution was performed in the read-only checkout.
- **Open decisions:**
  - Should the new clean document remain editable like an untitled text document, or is a readonly generated-document surface the intended contract?
  - For an editable document, does returning to the supplied initial content restore the clean state, and should closing untouched generated content discard it without a save prompt?
  - Does the supplied filename identify a future save destination or only a display name, and what should explicit Save do before any edits?
