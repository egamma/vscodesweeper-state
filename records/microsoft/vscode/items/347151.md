# Issue #347151 — Session inline action appears on every peer chat

[https://github.com/microsoft/vscode/issues/347151](https://github.com/microsoft/vscode/issues/347151)

## Summary

Keep open as Sessions-list polish. Nested-row actions are explicitly supported today, so reducing repetition needs a presentation decision that preserves access to genuinely chat-specific actions.

## Change summary

Reduce redundant inline actions across a parent session and its peer-chat rows.

## Best solution

Agree on when repeated actions should appear only on the parent, while retaining access to actions for peers with distinct feedback or workspaces. Apply that presentation rule within the Sessions list without changing background execution or chat targeting.

- **Likely files:** `src/vs/workbench/contrib/sessions/browser/views/sessionsList.ts`, `src/vs/workbench/contrib/sessions/browser/views/sessionInlineActions.ts`, `src/vs/sessions/contrib/sessions/test/browser/sessionsList.test.ts`, `src/vs/sessions/contrib/chat/browser/sessionsChatAccessibilityHelp.ts`

- **Behavior:**

  > With inline actions enabled, expanding a session with peer chats should avoid unnecessary repetition of the same actionable work. The presentation must distinguish redundant actions from actions that belong to a different chat. Acceptance should cover shared and distinct feedback, preserve the intended target when activating a remaining control, and leave the disabled-setting behavior unchanged.
- **Trace:**

  > SessionsList supplies the same renderInlineActions factory to session and chat renderers in src/vs/workbench/contrib/sessions/browser/views/sessionsList.ts. SessionInlineActions selects the supplied chat or the session main chat, creates a chat-targeted SessionInputBannerModel, and submits through sendRequestInBackground. Existing tests in src/vs/sessions/contrib/sessions/test/browser/sessionsList.test.ts intentionally assert peer-specific targeting. The original feature description at https://github.com/microsoft/vscode/issues/346647 explicitly includes nested rows, so blanket suppression would change that contract. The unresolved boundary is whether identical-looking actions represent redundant work or distinct chat contexts; preserve eligibility, permissions, background execution, and multi-selection isolation.
- **Open decisions:**
  - Should all peer-row inline actions disappear, or should only actions representing the same underlying work be suppressed while distinct peer actions remain accessible?

## Evidence

- **Reporter context:** https://github.com/microsoft/vscode/issues/347151 reports repeated inline actions on peer chats while testing https://github.com/microsoft/vscode/issues/346647 and suggests parent-only placement.
- **Existing feature contract:** https://github.com/microsoft/vscode/issues/346647 explicitly requests nested-chat support: session rows target their main chat, while nested rows target their represented chat. This makes the report a presentation refinement rather than proof of broken targeting.
- **Current rendering path:** src/vs/workbench/contrib/sessions/browser/views/sessionsList.ts:4938-4942 constructs SessionInlineActions with the represented peer chat for nested rows; the callback is supplied to both session and chat renderers. sessionInlineActions.ts independently builds a SessionInputBannerModel for each target chat.
- **Existing capability check:** src/vs/sessions/contrib/sessions/browser/sessions.contribution.ts registers sessions.list.inlineActions as an experimental boolean defaulting to false. Disabling it hides all inline actions, not merely redundant peer actions, so it does not satisfy the parent-only request.

The current accessibility help also documents distinct session/main-chat and nested-chat targets.
