# Issue #52875 — Dragging files and folders onto an empty explorer ignores the files

[https://github.com/microsoft/vscode/issues/52875](https://github.com/microsoft/vscode/issues/52875)

## Summary

The accepted Backlog bug remains source-reproducible on current main: a mixed drop containing a folder or workspace opens that workspace resource and returns before opening the ordinary files. The shared handler needs a decision about where those files open and which drop surfaces adopt the behavior.

## Change summary

Dropping a mixture of files and folders or workspace files onto an empty Explorer opens the workspace resource but silently ignores the files.

## Best solution

Preserve every resource in a mixed drop: open the folder or workspace as intended, then open the accompanying files in the appropriate resulting window. Scope that behavior explicitly for each consumer of ResourcesDropHandler so editor-tab and editor-group drops retain their intended semantics.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/dnd.ts`, `src/vs/workbench/contrib/files/browser/views/emptyView.ts`, `src/vs/workbench/browser/parts/editor/editorDropTarget.ts`
- **Validation:** Add automated ResourcesDropHandler coverage for a mixed file-plus-folder drop and a file-plus-workspace-file drop, asserting that the workspace resource is opened and every ordinary file is subsequently opened exactly once in the selected target window.
- **Behavior:**

  > Dropping a folder together with one or more files onto an empty Explorer must not discard the files. The folder should retain the existing workspace-opening behavior, and every accompanying file should open exactly once in the maintainer-selected target window. The same guarantee must cover a workspace-file-plus-file drop. Folder-only, workspace-only, and file-only drops, as well as consumers configured not to open workspaces, must remain unchanged.
- **Trace:**

  > The empty Explorer creates ResourcesDropHandler with allowWorkspaceOpen enabled in src/vs/workbench/contrib/files/browser/views/emptyView.ts. Native entries are all marked allowWorkspaceOpen in extractEditorsDropData in src/vs/platform/dnd/browser/dnd.ts. ResourcesDropHandler.handleDrop in src/vs/workbench/browser/dnd.ts passes those resources to handleWorkspaceDrop and returns as soon as that method recognizes any folder or workspace, bypassing editorService.openEditors for the remaining files. The handler is shared with editor-group drop targets, while tabs and Open Editors instantiate it with workspace opening disabled. The issue discussion at https://github.com/microsoft/vscode/issues/52875#issuecomment-400706539 confirms that configurability across these consumers is part of the boundary; do not alter folder-only or ordinary editor-drop behavior.
- **Open decisions:**
  - When a mixed drop opens or replaces a workspace, should accompanying files open in that resulting workspace window or remain in the original window when it is not reused?
  - Should mixed workspace-and-file handling be enabled for every ResourcesDropHandler consumer that allows workspace opening, or only for the empty Explorer?

## Evidence

- **current source path:** src/vs/workbench/contrib/files/browser/views/emptyView.ts creates ResourcesDropHandler with allowWorkspaceOpen enabled and passes the complete external drop to handleDrop.
- **source reproduction:** In src/vs/workbench/browser/dnd.ts, ResourcesDropHandler.handleDrop filters all workspace-eligible dropped resources, calls handleWorkspaceDrop, and returns immediately when any folder or workspace is opened. The later editorService.openEditors call therefore never receives the accompanying ordinary files.
- **mixed-resource trigger:** src/vs/platform/dnd/browser/dnd.ts marks every native dropped file-system entry allowWorkspaceOpen: true. For a file-plus-folder drop, handleWorkspaceDrop identifies the folder, returns true, and causes the ordinary file to be skipped; the same early-return path applies to a workspace-file-plus-file drop.
- **maintainer direction:** https://github.com/microsoft/vscode/issues/52875#issuecomment-400706539 explicitly permits changing the shared drop logic but asks that behavior be configurable for its different consumers.
- **canonical search:** Searches for mixed file/folder drops and empty-Explorer drops found no older open issue with the same observable symptom. The timeline reference https://github.com/microsoft/vscode/issues/128834 concerns Explorer sorting and is unrelated.
