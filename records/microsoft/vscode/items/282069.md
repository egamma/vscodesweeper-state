# Issue #282069 — GitHub Copilot checkpoint behavior for added and deleted files is neither expected nor well documented

[https://github.com/microsoft/vscode/issues/282069](https://github.com/microsoft/vscode/issues/282069)

## Summary

The gap remains on current main: checkpoints can restore explicitly recorded create/delete operations, but they are not filesystem snapshots and terminal-driven changes are recoverable only when the affected resources are reported through the external-edit path. The accepted bug should remain open while the restore contract and added/deleted/moved-file behavior are defined and covered end to end.

## Change summary

Restoring a Copilot checkpoint failed to recover newly created files deleted by a later terminal command, while Keep/Undo behavior for renamed and deleted files was ambiguous.

## Best solution

Define one user-visible checkpoint contract for created, deleted, moved, and modified files, then ensure every agent editing path records enough content and file-operation metadata to honor it. The checkpoint documentation and Keep/Undo UI should state any unavoidable boundary, especially for external command effects.

- **Validation:** Add an end-to-end chat-editing test that creates an untracked file in one request, removes or renames it through the external-command path in the next request, restores the preceding checkpoint, and asserts exact file existence/content plus unambiguous Keep/Undo outcomes.
- **Behavior:**

  > A checkpoint must have a documented, consistent contract for modified, newly created, deleted, and moved files. Restoring to the point before an agent-driven deletion or move must either recover the exact prior content and path or warn before the operation that this effect is outside checkpoint coverage. Keep and Undo must clearly distinguish accepting edits from accepting a deletion, and accepting a rename must not resurrect the old path. Acceptance is an end-to-end test covering creation in one request followed by deletion and rename in a later request.
- **Trace:**

  > ChatEditingCheckpointTimelineImpl records and replays Create, Delete, Rename, and content-edit operations; Delete carries finalContent, so captured deletions are reconstructible. ChatEditingSession.startDeletion records structured deletions, while startExternalEdits/stopExternalEdits can snapshot only resources supplied by the caller. The proposed ChatResponseStream.externalEdit API exposes that explicit-resource boundary, and ExternalEditTracker currently applies it in Copilot CLI permission flows rather than providing a general workspace snapshot around arbitrary terminal commands. The existing timeline test covers already-recorded operations, not the reported cross-request terminal rm/mv path. Preserve ordinary text-edit checkpoint behavior and do not broaden rollback to unrelated user or process changes without an explicit product decision.
- **Open decisions:**
  - Does the checkpoint guarantee include every agent-authorized filesystem mutation made through terminal commands, or only structured and explicitly bracketed edits; if the latter, what warning must appear before an uncovered destructive command runs?
  - For a moved file with pending edits, should Keep/Undo operate on the rename as one atomic change, and what should accepting or rejecting the deleted-source entry do?
