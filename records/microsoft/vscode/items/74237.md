# Issue #74237 — Add "type" to textDocument/references results (icon, filtering)

[https://github.com/microsoft/vscode/issues/74237](https://github.com/microsoft/vscode/issues/74237)

## Summary

Keep open: the shared reference-provider API still lacks reference categories, and a later request from another language extension was explicitly consolidated here. The C++ workaround does not satisfy the cross-language API and UI request; this team-authored Backlog item has no verified factual basis for closure.

## Change summary

Allow reference providers to supply reference categories that the built-in references UI can distinguish and filter.

## Best solution

Define a backward-compatible reference-category contract and corresponding shared references presentation, coordinated with the separate LSP proposal. Keep rename filtering outside this issue, and explicitly settle whether changing confirmation states belongs in the initial contract.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/editor/common/languages.ts`, `src/vs/editor/contrib/gotoSymbol/browser/referencesModel.ts`, `src/vs/editor/contrib/gotoSymbol/browser/peek/referencesTree.ts`, `extensions/references-view/package.json`
- **Validation:** After agreeing the contract, exercise a test reference provider returning confirmed, comment, string, and uncertain results: the built-in references presentation must distinguish categories and filter them without losing location navigation. Run corresponding API transport and references UI tests, and verify that existing Location[] providers retain their current behavior.
- **Behavior:**

  > Extensions need to return reference categories that users can distinguish and filter in the shared references experience. The request includes semantic references, comment/string occurrences, inactive-code occurrences, and uncertain or rejected candidates. Acceptance should cover category presentation, filtering, correct navigation, and unchanged behavior for providers returning plain locations. Rename filtering is a separate request.
- **Trace:**

  > ReferenceProvider.provideReferences in src/vscode-dts/vscode.d.ts returns Location[], whose entries expose only uri and range. ReferenceAdapter.provideReferences in src/vs/workbench/api/common/extHostLanguageFeatures.ts converts those results into editor locations; OneReference in src/vs/editor/contrib/gotoSymbol/browser/referencesModel.ts and OneReferenceTemplate in browser/peek/referencesTree.ts provide no reference-category presentation. The built-in references-view registration offers placement and manual removal rather than category filtering. The C++ custom-view workaround is documented at https://github.com/microsoft/vscode/issues/74237#issuecomment-525958416, but another language's grouped-reference request was subsequently consolidated here at https://github.com/microsoft/vscode/issues/144699#issuecomment-1062621497. Coordinate the public contract with https://github.com/microsoft/language-server-protocol/issues/763 without treating that separate proposal as a replacement for the VS Code work. Preserve existing plain-location providers and keep rename outside scope; uncertainty starts at the category vocabulary and whether results can change confirmation state after delivery.
- **Open decisions:**
  - Should reference categories be a standardized vocabulary, provider-defined categories, or standardized categories with provider-defined extensions?
  - Should the initial contract describe only completed reference results, or also support confirmation-state updates while the references view remains open?
