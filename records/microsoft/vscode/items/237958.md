# Issue #237958 — Dragging does not work in a VSCode extension WebView

[https://github.com/microsoft/vscode/issues/237958](https://github.com/microsoft/vscode/issues/237958)

## Summary

This is a feature request rather than a bug: VS Code's webview infrastructure intentionally intercepts drag events and either opens files in editors (explorer drags) or swallows the drop (OS drags). There is no existing API for extensions to receive drop data in webview panel content. Reclassifying as feature-request and keeping open.

## Change summary

Allow extension webview panels to receive drag-and-drop events (files from VS Code explorer or OS file manager) instead of VS Code intercepting them.

## Best solution

Add an opt-in mechanism (e.g. a `WebviewOptions` flag or extension API) that lets webview panels receive drop events with file data. The webview preload script in `src/vs/workbench/contrib/webview/browser/pre/index.html` currently swallows drops unconditionally at line 820-822 and disables pointer events during drags at line 753-758 — both would need to be conditional on the opt-in. The related `handleInnerDragStartEvent` already respects `e.defaultPrevented` from extension code (line 783), but `handleInnerDropEvent` does not, which is an inconsistency worth fixing as part of this work.

## Evidence

- **drop swallowed in preload:** src/vs/workbench/contrib/webview/browser/pre/index.html line 820-822: `handleInnerDropEvent` calls `e.preventDefault()` unconditionally and does nothing else — extension content JS never receives the drop.
- **pointer events disabled during drags:** src/vs/workbench/contrib/webview/browser/webviewElement.ts line 753-758: `windowDidDragStart` disables pointer events on the webview iframe during drags, preventing any drag events from reaching the webview content when dragging from VS Code's own explorer.
- **inconsistent defaultPrevented check:** The dragenter handler (`handleInnerDragStartEvent`, line 783) checks `e.defaultPrevented` to let extension code opt out, but the drop handler does not — so even if extension code prevents the dragenter, the drop is still swallowed.
- **no extension API for webview drops:** Neither WebviewOptions nor WebviewContentOptions in src/vs/workbench/contrib/webview/browser/webview.ts includes any drop-related option. No proposed API exists in src/vscode-dts/vscode.proposed.*.d.ts for webview drop handling.
- **referenced issues were custom-editor specific:** Issues #182449 and #218626 (both closed/fixed) addressed drop behavior for custom editors specifically, not general webview panels.
