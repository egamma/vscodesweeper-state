# Issue #237958 — Dragging does not work in a VSCode extension WebView

[https://github.com/microsoft/vscode/issues/237958](https://github.com/microsoft/vscode/issues/237958)

## Summary

Keep open: the supplied extension and Windows reproduction steps suffice to retest, but source inspection does not establish why holding Shift still fails. Current main includes the earlier drag/drop fixes, which predate this report; neither those fixes nor the related open issues establish that this report is resolved.

## Change summary

Dropping files from VS Code Explorer or Windows Explorer opens an editor instead of delivering drag/drop events to an extension webview, reportedly even while holding Shift.

## Best solution

Establish whether Shift-dragging into the supplied webview fails in VS Code's event routing or whether its body-only event handlers miss the actual drop target. Preserve normal file-opening behavior without Shift, and correct the responsible path if Shift does not deliver events to a valid webview drop target.

- **Behavior:**

  > The reporter cannot receive file drag/drop events in an extension webview on Windows, including when holding Shift; files open instead. Ordinary file drops should retain the established workbench file-opening behavior, while Shift allows dropping into webview content. Reproduce using both VS Code Explorer and Windows Explorer and distinguish a core routing failure from events missing the sample's body-only target.
- **Trace:**

  > WebviewWindowDragMonitor in src/vs/workbench/contrib/webview/browser/webviewWindowDragMonitor.ts toggles webview pointer-event blocking according to drag modifier state through WebviewElement.windowDidDragStart/windowDidDragEnd. src/vs/workbench/contrib/webview/browser/pre/index.html handles iframe drag events and forwards file drag state to the host. The supplied extension installs handlers only on an initially empty body without an explicit height, leaving a hit-testing explanation unresolved. The fixes discussed in https://github.com/microsoft/vscode/issues/182449 and https://github.com/microsoft/vscode/issues/218626 predate this report and are not proof of resolution. Do not broaden this investigation into removing Shift requirements for non-resource tree data: that separate behavior is being addressed by https://github.com/microsoft/vscode/pull/321275. The uncertainty is the actual native event target and modifier delivery on Windows, not a settled source-level defect.

## Evidence

- **Complete reproduction:** https://github.com/microsoft/vscode/issues/237958 provides a runnable extension, F5 launch steps, Windows 11 and VS Code 1.96.3 details, and failures with both VS Code Explorer and Windows Explorer, including an attempted Shift modifier. No execution was performed during this read-only review.
- **Reproducer event target:** https://github.com/wchengk09/vscode-webview-dragging-does-not-work/blob/cf50ffe05fc5a898caddc9f50dea4de65044ff11/extension.js enables scripts and installs drag/drop handlers only on document.body. That body initially contains only a script and has no explicit height or visible drop target. Current src/vs/workbench/contrib/webview/browser/pre/index.html default body styles also do not establish a minimum height; hit-testing must be checked before attributing missing events conclusively to VS Code.
- **Current routing:** src/vs/workbench/contrib/webview/browser/webviewWindowDragMonitor.ts restores webview pointer events when drag or dragover carries shiftKey. In webviewElement.ts, windowDidDragStart disables pointer events and windowDidDragEnd restores them. In pre/index.html, handleInnerDragStartEvent skips Shift drags, while handleInnerDragEvent forwards file drag state and handleInnerDropEvent prevents default navigation. These paths express the intended Shift behavior but do not prove the reported native Windows interaction succeeds.
- **Earlier issues are closed, not duplicate targets:** https://github.com/microsoft/vscode/issues/182449 is closed; its discussion explicitly describes Shift as switching from opening an editor to dropping into the webview. https://github.com/microsoft/vscode/issues/218626 is also closed. Its fix, https://github.com/microsoft/vscode/commit/d00533a1df0778ab3a3fe8200b18cd59e3d1b722, added preventDefault handling and file-item filtering in pre/index.html on 2024-08-01, before this January 2025 report, so it is not evidence of a subsequent fix.
- **Older candidate has a different symptom:** https://github.com/microsoft/vscode/issues/193558 is open and older, but concerns internal drag/drop in cross-origin nested iframes on macOS, explicitly contrasting working Windows behavior. It does not establish ownership of this Windows Explorer-to-webview failure and does not satisfy the stronger duplicate bar for a re-reviewed item.
- **Newer related work does not absorb this report:** https://github.com/microsoft/vscode/issues/256444 is open but newer and concerns extension tree data and unnecessary Shift requirements. Its open implementation candidate, https://github.com/microsoft/vscode/pull/321275, explicitly preserves existing behavior for dragged resource URIs and changes delegation for non-resource data; it neither references nor establishes a fix for this report's file drops.
