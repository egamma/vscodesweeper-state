# Issue #337331 — Sandbox cannot start commands when firewall mode requires missing slirp4netns

[https://github.com/microsoft/vscode/issues/337331](https://github.com/microsoft/vscode/issues/337331)

## Summary

The current Dev Container Agent Host path can enable the Copilot SDK firewall sandbox without checking or provisioning its `slirp4netns` prerequisite, so commands fail before execution. This remains open and should be routed to the Agent Host, agent sandbox, and container owners.

## Change summary

Make sandboxed commands work predictably in Dev Container Agent Host sessions when firewall enforcement requires `slirp4netns`.

## Best solution

Preflight the Copilot SDK sandbox dependencies inside the Dev Container before dispatching commands, then either provision `slirp4netns` through an approved container setup path or present an actionable remediation while keeping firewall enforcement fail-closed.

## Plan brief

- **Validation:** Add focused tests simulating a Linux Dev Container with bubblewrap and socat present but `slirp4netns` absent, asserting that no command reaches the firewall sandbox and that the selected remediation is returned; run them with `scripts/test.sh --grep "Dev Container Agent Host Main Service|SandboxHelperService"`.
- **Behavior:**

  > A Dev Container Agent Host session with sandboxing enabled must not dispatch a command into firewall enforcement when `slirp4netns` is unavailable. The user must receive an actionable, fail-closed outcome before execution, or the dependency must be installed through an explicitly supported container setup path. Containers with all prerequisites must continue executing sandboxed commands normally, and disabling sandboxing must remain unaffected.
- **Trace:**

  > DevContainerAgentHostService in src/vs/platform/agentHost/node/devContainerAgentHostService.ts launches the pinned CLI and standalone Agent Host inside the selected container without inspecting sandbox-specific dependencies. CopilotAgentSession applies the Linux policy produced by buildSandboxConfigForSdk in src/vs/platform/agentHost/node/copilot/sandboxConfigForSdk.ts, which enables restricted networking but has no prerequisite handshake. The shared SandboxHelperService currently detects only bubblewrap and socat, so it cannot report `slirp4netns` as missing, and the SDK-backed shell path does not use the shared terminal sandbox prerequisite flow. Keep firewall behavior fail-closed and do not silently grant unrestricted networking. The uncertainty begins at ownership of remediation: modifying an arbitrary user container, surfacing a repair action through Agent Host, or changing the SDK runtime dependency contract have different user-visible and architectural consequences.
- **Open decisions:**
  - Should the new Dev Container feature install `slirp4netns` into the container automatically, or leave the container unchanged and stop with an explicit remediation action?

## Evidence

- **Dev Container launch path:** src/vs/platform/agentHost/node/devContainerAgentHostService.ts starts the Dev Container, installs the VS Code CLI, and launches the Agent Host, but contains no `slirp4netns` capability check or provisioning step.
- **SDK sandbox configuration:** src/vs/platform/agentHost/node/copilot/sandboxConfigForSdk.ts enables the Linux Copilot SDK sandbox with `allowOutbound: false`; this path does not preflight the runtime dependency required by firewall enforcement.
- **incomplete dependency model:** src/vs/platform/sandbox/node/sandboxHelper.ts and src/vs/platform/sandbox/common/sandboxHelperService.ts check only bubblewrap and socat. The shared dependency status cannot currently represent a missing `slirp4netns` binary.
