# Issue #339735 — Banner flickers when clicking retry

[https://github.com/microsoft/vscode/issues/339735](https://github.com/microsoft/vscode/issues/339735)

## Summary

Freshly filed (same-day) internal test note with a video repro, and the code path matches: clicking Retry on the chat-input notification churns through transient notification states that fully tear down and rebuild the banner's DOM, briefly dropping its severity CSS class and flashing the border back to its default color before the red error state resettles.

## Change summary

Clicking Retry on the agent-session chat-input error banner makes its red outline flash to normal and back.

## Best solution

Stop the notification widget from fully tearing down and rebuilding its DOM (and stripping/re-adding the severity class) on every transient state during a retry — either update content in place or smooth over the brief 'checking' state so the border doesn't visibly flash.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input/chatInputNotificationWidget.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostChatInputState.ts`
- **Validation:** Manually: open a conversation in the blocked/error state, click Retry, and confirm the banner's border does not visibly flash away from red before settling back; repeat for both a fast-resolving and slow-resolving retry.
- **Behavior:**

  > Clicking Retry on the agent-session chat input error banner should not cause the banner's red outline/border to visibly flash to a neutral color and back. The banner may still update its message/icon as it moves through checking/retry states, but the visual frame should stay stable rather than flicker.
- **Trace:**

  > AgentHostChatInputState._updateNotification() (src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostChatInputState.ts, lines 81-113) re-publishes the notification on every retrying/state/retryError change, all at Error severity but with different message/icon. ChatInputNotificationWidget._render() (src/vs/workbench/contrib/chat/browser/widget/input/chatInputNotificationWidget.ts, ~line 183) responds to each publish by clearing the DOM node and stripping/re-adding severity-* classes; the severity-error class (src/vs/workbench/contrib/chat/browser/widget/input/media/chatInputNotice.css lines ~101-119) is what colors the border red, so its removal during rebuild is the likely flash source. Do not change the notification data model or the retry command itself — the fix should be scoped to how the widget renders/transitions between states for the same logical notification.
- **Open decisions:**
  - Should the transient 'Checking Conversation' state be suppressed/debounced for fast retries, or is a brief visible checking step intended by design?

## Evidence

- **retry state churn:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostChatInputState.ts _updateNotification() (lines 81-113) is re-invoked via autorun on every change to state/retrying/retryError; clicking Retry walks through 'Checking Conversation' then back to the blocked/error message, each with severity ChatInputNotificationSeverity.Error but different icon/text.
- **full DOM rebuild per render:** src/vs/workbench/contrib/chat/browser/widget/input/chatInputNotificationWidget.ts _render() (around line 183) calls dom.clearNode(this.domNode) and this.domNode.classList.remove(...Object.values(severityToClass)) on every notification change, then rebuilds and re-adds the class — this runs again for each transient state during a retry.
- **severity drives border color:** src/vs/workbench/contrib/chat/browser/widget/input/media/chatInputNotice.css lines ~101-119: .severity-error sets --chat-input-notice-severity to var(--vscode-editorError-foreground) which colors the border; the brief absence of the severity class during teardown restores the default (non-error) border, producing the reported red→normal→red flash.
