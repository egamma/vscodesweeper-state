# Issue #187863 — Support input validation in quick pick

[https://github.com/microsoft/vscode/issues/187863](https://github.com/microsoft/vscode/issues/187863)

## Summary

Core quick picks already support inline validation, but the maintainer-preferred popover presentation and extension-facing validation remain incomplete. Keep this team-authored request open: the floating implementation never merged, and the older related issues do not own its full remaining scope.

## Change summary

Provide consistent quick-pick input validation feedback, including the preferred floating presentation and extension API support.

## Best solution

Finish the agreed popover presentation without breaking neutral prompts or ordinary input boxes, and coordinate extension-facing validation with https://github.com/microsoft/vscode/issues/121205. Existing prompt text should remain instructional rather than substitute for severity-aware validation.

## Plan brief

- **Likely files:** `src/vs/platform/quickinput/browser/quickInput.ts`, `src/vs/platform/quickinput/browser/media/quickInput.css`, `src/vs/platform/quickinput/common/quickInput.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** The plan should end with a runnable quick-pick scenario covering invalid arbitrary input, valid input, selection changes, clearing validation, multiline messages, and Severity.Ignore. Verify that decorated feedback follows the approved popover behavior, neutral prompts remain usable, keyboard selection and acceptance still work, and ordinary InputBox validation is unchanged; include light, dark, high-contrast, and screen-reader checks.
- **Behavior:**

  > Quick picks that combine arbitrary input with suggested choices should communicate invalid input before users repeatedly restart the interaction. Maintainers preferred floating validation feedback over pushing the item list down; core inline validation already exists. Acceptance should distinguish error, warning, informational, and neutral instructional content, preserve keyboard interaction, and leave ordinary input-box behavior intact. Extension callers also need a validation contract rather than relying solely on instructional prompt text.
- **Trace:**

  > QuickInput.validationMessage and severity in src/vs/platform/quickinput/browser/quickInput.ts feed QuickInput.update and showMessageDecoration; QuickPick.update controls message visibility. The current .quick-input-message rule in src/vs/platform/quickinput/browser/media/quickInput.css remains in normal flow. QuickInput is shared with InputBox, and its fallback prompt is rendered even when Severity.Ignore clears all decoration, so globally changing message presentation could affect unrelated instructional and input-box content. https://github.com/microsoft/vscode/pull/187864 attempted the preferred floating variant but never merged and left the Ignore case unresolved. Stable QuickPick.prompt in src/vscode-dts/vscode.d.ts offers neutral context, not InputBox-style validationMessage. Coordinate the API portion with https://github.com/microsoft/vscode/issues/121205 and consult https://github.com/microsoft/vscode/issues/145672 for prompt-obscuring overlay concerns; neither was verified to absorb this issue's full scope.
- **Open decisions:**
  - In a quick pick with floating validation feedback, should neutral Severity.Ignore text remain visible as inline instructional content while decorated validation floats, or should neutral validation text be suppressed?
  - Should extension-facing quick-pick validation use an InputBox-style severity/message contract, and should error severity prevent acceptance or leave acceptance control entirely with the extension?
