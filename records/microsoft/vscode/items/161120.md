# Issue #161120 — Define ordering when multiple outlines are present

[https://github.com/microsoft/vscode/issues/161120](https://github.com/microsoft/vscode/issues/161120)

## Summary

Still a real gap on current main: when several document symbol providers match a document, the outline/breadcrumb order is decided purely by selector score and registration time with no extension- or user-facing control, so this backlog item should stay open; a maintainer needs to decide what the ordering contract should be.

## Change summary

Requests a defined, controllable ordering when multiple extensions contribute document symbols (outline groups and breadcrumbs) for the same document.

## Best solution

Define an explicit ordering contract for document symbol providers — either a provider-side priority/metadata field surfaced through the DocumentSymbolProvider registration, or a user-facing setting that ranks outline groups — and honor it in OutlineModel.create / LanguageFeatureRegistry.ordered so both the Outline view and breadcrumbs follow it.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/documentSymbols/browser/outlineModel.ts`, `src/vs/editor/common/languageFeatureRegistry.ts`, `src/vs/workbench/contrib/codeEditor/browser/outline/documentSymbolsOutline.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`
- **Validation:** An outlineModel test that registers two document symbol providers for the same model and asserts the resulting OutlineGroup order follows the chosen ordering mechanism rather than registration time, plus a breadcrumbs check that the same group wins.
- **Behavior:**

  > When more than one extension contributes document symbols for a document, the order of the resulting outline groups — and which one breadcrumbs follow — must be predictable and influenceable, instead of falling out of selector score and extension activation order. Expected end state: a user or extension can state that provider A's outline comes before provider B's, and both the Outline view and the breadcrumb bar honor that consistently across reloads. Single-provider documents must be completely unchanged, including the existing `_compact()` behavior that flattens a lone group into the root.
- **Trace:**

  > OutlineModel.create (src/vs/editor/contrib/documentSymbols/browser/outlineModel.ts:199-221) maps `registry.ordered(textModel)` to one OutlineGroup per provider, passing the array index as the group's order; LanguageFeatureRegistry.ordered sorts via `_compareByScoreAndTime` (src/vs/editor/common/languageFeatureRegistry.ts:199), i.e. selector score, then registration time — so the winning outline depends on which extension registered first. No ordering configuration is registered for the outline anywhere in the documentSymbols contrib or the workbench outline contribution (verified by grep). Breadcrumbs consume the same OutlineModel via documentSymbolsOutline.ts, so a single ordering source fixes both. Boundaries: do not change `LanguageFeatureRegistry` scoring for other feature kinds, and do not alter the single-provider flattening path. The uncertainty starts at where the ordering signal comes from — the extension API surface (vscode.d.ts / extHostLanguageFeatures) or a workbench setting keyed by extension id.
- **Open decisions:**
  - Should ordering be declared by extensions (a priority/rank on DocumentSymbolProvider registration, i.e. a public API addition) or configured by users (a setting ranking outline contributors by extension id)?
  - Does the chosen order also decide which single outline breadcrumbs follow, or should breadcrumbs keep their own selection rule?
  - If the mechanism is a user setting, what is its scope and shape (global list of extension ids vs. per-language map), and what happens to providers not listed?

## Evidence
