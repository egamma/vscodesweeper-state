# Issue #132767 — Support `dependsOn` programmatically in the vscode.Task API

[https://github.com/microsoft/vscode/issues/132767](https://github.com/microsoft/vscode/issues/132767)

## Summary

Keep this accepted API request open: current Task declarations and extension-host transport still lack dependency configuration. The request has 31 upvotes, and the related reports do not provide an eligible canonical duplicate.

## Change summary

Allow extensions to configure dependsOn and dependsOrder on programmatically created vscode.Task objects.

## Best solution

Expose a supported task-dependency API that uses the existing task scheduler and preserves dependency ordering across the extension-host boundary. API owners should settle dependency identity and workspace-scoping semantics before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTypes.ts`, `src/vs/workbench/api/common/shared/tasks.ts`, `src/vs/workbench/api/common/extHostTask.ts`, `src/vs/workbench/api/browser/mainThreadTask.ts`, `src/vs/workbench/contrib/tasks/common/tasks.ts`, `src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts`
- **Validation:** In an extension-host integration scenario, construct applyWorkload, someOtherTask, and portForward programmatically, assign dependencies through the agreed API, and execute portForward. Record task start/end events to verify sequence ordering, the agreed parallel behavior, and that the dependent task waits for prerequisites; include a background prerequisite with a readiness matcher and confirm existing tasks.json dependencies remain unchanged.
- **Behavior:**

  > Extensions can configure dependencies and dependency ordering on tasks created with new vscode.Task(), without generating tasks.json. Executing the dependent task uses the same ordering and prerequisite-readiness semantics as equivalent configured tasks. Acceptance includes the report's ordered applyWorkload/someOtherTask prerequisites before portForward, unchanged behavior for tasks without dependencies, and preservation of existing configured-task execution.
- **Trace:**

  > The current public Task declaration in src/vscode-dts/vscode.d.ts lacks both properties, and ITaskDTO in src/vs/workbench/api/common/shared/tasks.ts cannot carry them. The TaskDTO conversions in extHostTask.ts and mainThreadTask.ts omit dependency configuration; mainThreadTask.ts constructs a ContributedTask without those configuration properties. Internal task configuration already exposes dependsOn and dependsOrder in src/vs/workbench/contrib/tasks/common/tasks.ts, and terminalTaskSystem.ts executes dependencies using that configuration. Executing an unchanged fetched task can preserve configured dependencies, as confirmed at https://github.com/microsoft/vscode/issues/299946, but does not cover creating a dependency graph through the API. Preserve the existing scheduler, tasks.json semantics, and original fetched-task execution behavior. The unresolved boundary is the public representation and resolution of dependency references, especially across workspace folders; no runtime validation was performed.
- **Open decisions:**
  - Should API dependencies reference Task objects, configured-task names/identifiers, or both?
  - How should dependency references identify their workspace scope and resolve ambiguous names across multiple folders?
