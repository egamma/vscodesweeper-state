# Issue #337742 — Agent Host: auto-restored chat registers no BYOK models when restored before the BYOK bridge is wired, so every message fails with modelSelectionFailed

[https://github.com/microsoft/vscode/issues/337742](https://github.com/microsoft/vscode/issues/337742)

## Summary

Confirmed still-open startup race on current main: independently reproduced by two reporters (custom-endpoint and third-party LM providers) and matches the code exactly — a chat auto-restored before the BYOK bridge is wired gets a permanently-empty BYOK provider/model config, and nothing rebuilds it once the bridge becomes ready, so every later `switchTo` for that chat fails.

## Change summary

An Agent Host chat auto-restored at startup before the BYOK/third-party model bridge is ready never gets its BYOK models registered, so every subsequent message in that chat fails with modelSelectionFailed.

## Best solution

Either delay/gate the affected chat's `resumeSession` until the BYOK bridge has reported its model set at least once, or make `_refreshByokModels`/`onDidChangeModels` also rebuild the provider/model config of already-launched sessions that resumed with an empty BYOK snapshot (and retry the failed switchTo) — a maintainer should pick the approach given the startup-latency vs. correctness trade-off.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/platform/agentHost/node/byokLmBridgeRegistry.ts`
- **Validation:** A restored session whose selected model is a BYOK/third-party model, when messaged before the bridge first reports its models, must not fail `switchTo` — e.g. an agentHost test that resumes a session with an initially-empty bridge registry, fires `onDidChangeModels` after resume, and asserts a subsequent `changeModel`/send for the previously-unregistered model succeeds.
- **Behavior:**

  > A chat auto-restored at window startup, whose remembered model is a BYOK custom-endpoint or third-party-provider model, must be able to send a message successfully even if the message is sent within the first few seconds after the window opens — before the BYOK bridge has reported any models to the host. Currently every send in that chat fails permanently with `(modelSelectionFailed) ... Provider model '...' is not registered`, while newly created chats (which launch after the bridge is ready) work fine. Acceptance: sending in an early-restored BYOK chat succeeds (either by waiting briefly for the bridge before resuming, or by re-registering/retrying once the bridge becomes ready), without needing the documented workaround (switch to Auto and back).
- **Trace:**

  > `resolveByokSessionConfig` (copilotSessionLauncher.ts:550-609) does a synchronous, one-time read of `bridgeRegistry.getModels()` and bakes the result into the `resumeSession`/`createSession` config (used at copilotSessionLauncher.ts:919); when the bridge hasn't reported yet, this returns `{}` and the session is permanently launched with no BYOK providers/models. `_refreshByokModels` (copilotAgent.ts:2407-2436), invoked from the `onDidChangeModels` handler (copilotAgent.ts:1077-1080) once the bridge later becomes ready, only refreshes the model *picker* catalog (`this._byokModels` / `_publishModels()`) — it does not touch any already-launched `CopilotAgentSession`. `setModel` (copilotAgentSession.ts:4198) only calls the SDK's `session.setModel` RPC to switch among models the SDK already knows about; there is no seam here to add a model to a live session after launch. The boundary: do not change the model-switch RPC semantics or the picker/catalog publication path — the gap is specifically that a resumed session's SDK-side provider/model config is never revisited after the bridge becomes ready. Confirmed independently by brunogsystem's reproduction (comment, 2026-09-26) tracing the same three files/functions on Windows Stable 1.139.1.
- **Open decisions:**
  - Should `resumeSession` for an affected chat wait (with what bound) for the BYOK bridge's first model report before launching, trading startup latency for correctness, or should the fix instead rebuild/retry the already-launched session's config once the bridge becomes ready?
  - If retrying/rebuilding a live session, should the host automatically re-issue the pending model switch, or just make the provider/model set available so the user's next explicit switch succeeds?

## Evidence

- **resolveByokSessionConfig snapshots once:** src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:550-609 `resolveByokSessionConfig` calls `bridgeRegistry.getModels()` synchronously and returns `{}` when empty; this snapshot is baked into the `resumeSession`/`createSession` config passed to the SDK (called via `_resolveByokSessionConfig` at line 871 and used at line 919) and is never revisited for that session afterward.
- **refresh only updates the picker, not live sessions:** src/vs/platform/agentHost/node/copilot/copilotAgent.ts:2407-2436 `_refreshByokModels` (triggered by `onDidChangeModels` at line 1077, logged as 'BYOK bridge changed; refreshing models') only rebuilds `this._byokModels` and calls `_publishModels()` (the model catalog/picker) — it never touches already-launched `CopilotAgentSession`s' SDK-side provider/model config.
- **no dynamic model registration RPC on a live session:** copilotAgentSession.ts exposes `setModel()` (line 4198) which only calls the SDK's `session.setModel` RPC to switch among already-registered models; there is no RPC path found to add a new provider/model to an already-launched session, confirming the resumed session is stuck with its empty snapshot.
- **second independent reproduction:** Comment by brunogsystem (2026-09-26) reproduces the same race on Windows Stable 1.139.1 with both a `customendpoint` model and a third-party `registerLanguageModelChatProvider` model, in an isolated profile, citing the identical code path (`resolveByokSessionConfig`, `onDidChangeModels`, `byokLmBridgeRegistry.getModels()`) as this review found on current main.
