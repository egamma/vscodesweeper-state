# Issue #337742 — Agent Host: auto-restored chat registers no BYOK models when restored before the BYOK bridge is wired, so every message fails with modelSelectionFailed

[https://github.com/microsoft/vscode/issues/337742](https://github.com/microsoft/vscode/issues/337742)

## Summary

Well-diagnosed startup race, confirmed against current main: a chat auto-restored before the BYOK bridge connects is resumed with an empty provider/model list, and nothing re-syncs that list to the live SDK session afterward, so any later switch to the remembered BYOK model is permanently rejected.

## Change summary

An Agent Host chat auto-restored at startup, before the BYOK bridge wires up, can never successfully select its previously-used BYOK/custom-endpoint model — every message fails with modelSelectionFailed.

## Best solution

When the BYOK bridge registry's model set changes after a session already resumed with an empty/stale BYOK provider list, either re-resolve and push the current BYOK provider/model config to that live session (if the Copilot SDK exposes a mid-session provider update) before honoring `setModel`, or retry the resume with the refreshed BYOK config instead of leaving the session stuck; the fix belongs in copilotSessionLauncher.ts / copilotAgent.ts.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/platform/agentHost/node/byokLmBridgeRegistry.ts`
- **Validation:** A test that resumes a session while the BYOK bridge registry reports zero models, then simulates the registry gaining models and asserts a subsequent `setModel` to a BYOK model id succeeds instead of surfacing 'is not registered'.
- **Behavior:**

  > A chat auto-restored at VS Code startup, whose remembered model is a BYOK/custom-endpoint model, should be able to switch to (or resume on) that model even if the BYOK bridge connected after the session was resumed. Acceptance: sending a message in such a restored chat succeeds instead of repeatedly failing with `modelSelectionFailed` / 'Provider model ... is not registered'; sessions created after the bridge is ready are unaffected.
- **Trace:**

  > `resolveByokSessionConfig` (copilotSessionLauncher.ts:530-590) is invoked once per resume/create via `_buildSessionConfig` (copilotSessionLauncher.ts:843-849) and snapshots `IByokLmBridgeRegistry.getModels()` at that instant; if empty, the SDK session is given no BYOK providers. `_refreshByokModels()` (copilotAgent.ts:2332), fired from `_byokBridgeRegistry.onDidChangeModels` (copilotAgent.ts:1096-1099), only republishes the model-picker catalog via `_publishModels()` and has no effect on already-resumed sessions. `setModel` (copilotAgentSession.ts:3903) calls straight into `session.setModel` with no provider re-sync. Where the uncertainty starts: whether the Copilot SDK (`@github/copilot-sdk`, not vendored in this checkout) exposes any API to add/update providers on a live session, versus the fix needing to defer/retry the resume itself when the bridge isn't ready yet — that decides the whole shape of the change. Boundary: do not change the newly-created-session path, which already works correctly per the reporter's logs.
- **Open decisions:**
  - Does the Copilot SDK support registering additional providers/models on an already-resumed session, or must the fix retry/re-issue resumeSession with the refreshed BYOK config?
  - Should the host delay marking an auto-restored chat as ready until the BYOK bridge has reported its models at least once, to close the race outright, or should it stay eager and instead recover after the fact when the bridge connects later?

## Evidence

- **one-shot BYOK resolution:** src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:530-590 `resolveByokSessionConfig` reads `bridgeRegistry.getModels()` once, synchronously, at session build time (`_buildSessionConfig`, called from `resumeSession`/`createSession` at copilotSessionLauncher.ts:849); if the registry is empty at that instant the session gets no BYOK providers.
- **catalog-only refresh:** src/vs/platform/agentHost/node/copilot/copilotAgent.ts:2332 `_refreshByokModels()` (triggered by `_byokBridgeRegistry.onDidChangeModels`, line ~1096-1099) only rebuilds `this._byokModels` and calls `_publishModels()` — the picker catalog — with no path back into an already-created session's provider config.
- **setModel does not re-sync providers:** src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:3903 `setModel` calls `this._wrapper.session.setModel(model, ...)` directly against the SDK session with no re-application of BYOK provider/model config, so a session created without the BYOK provider stays unable to select it.
- **documented asymmetry:** copilotSessionLauncher.ts:885 comment notes some launch-time config is 'Re-applied on every launch and resume, but NOT on a mid-session model change' — consistent with BYOK config also only applying at (re)launch time.
