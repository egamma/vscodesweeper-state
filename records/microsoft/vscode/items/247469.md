# Issue #247469 — Starting VS code turns off Bluetooth

[https://github.com/microsoft/vscode/issues/247469](https://github.com/microsoft/vscode/issues/247469)

Keep open for investigation of the Linux desktop-launch path: a second reporter confirms Bluetooth switches off and identifies a launcher-specific workaround. Current source preserves the launch-path difference, but neither a fixing commit nor a verified duplicate explains the Bluetooth shutdown.

## Change summary

Starting VS Code from a Linux dock disables Bluetooth, while starting it through the command-line launcher does not.

## Best solution

Compare the packaged desktop entry, CLI launcher, and runtime behavior before deciding whether the fix belongs in VS Code packaging or upstream.

## Plan brief

- **Likely files:** `resources/linux/code.desktop`, `resources/linux/bin/code.sh`, `build/gulpfile.vscode.linux.ts`, `src/vs/code/node/cli.ts`
- **Validation:** On an affected Linux system with current VS Code, fully exit VS Code between trials, enable Bluetooth, and compare dock startup, `/usr/bin/code`, and direct `/usr/share/code/code` startup. Record `rfkill list`, `bluetoothctl show`, and Bluetooth service/kernel journal output before and after each trial. Acceptance: desktop startup leaves Bluetooth powered and connected, as CLI startup does, while ordinary file opening and new-window actions remain functional.
- **Behavior:**

  > On affected Ubuntu and Linux Mint systems, opening VS Code from the desktop launcher reportedly switches Bluetooth off; launching through `code` does not. Opening the editor must preserve the existing Bluetooth power state and connections regardless of launch method. First establish the behavior on a current build, then verify equivalent Bluetooth behavior for desktop and CLI startup without regressing desktop file opening.
- **Trace:**

  > The Debian packaging path in build/gulpfile.vscode.linux.ts substitutes the direct application executable into resources/linux/code.desktop. resources/linux/bin/code.sh instead enters the Node-mode CLI, and src/vs/code/node/cli.ts subsequently spawns the GUI executable with a prepared environment. The second reporter explicitly identifies this distinction and a wrapper-based workaround at https://github.com/microsoft/vscode/issues/247469#issuecomment-3049396773. The inspected source confirms different startup paths, not the mechanism that powers Bluetooth off. https://github.com/microsoft/vscode/issues/134461 documents runtime BlueZ activation, but its relationship to this shutdown remains unproven. Begin with controlled fresh launches on an affected system; preserve normal launcher arguments, file handling, and unrelated Bluetooth/browser capabilities.

## Evidence

- **Reporter isolates desktop startup:** https://github.com/microsoft/vscode/issues/247469#issuecomment-2831956701 confirms that both `code` and `code --disable-extensions` preserve Bluetooth, whereas clicking the dock icon switches it off. This does not establish extension causation.
- **Independent confirmation and workaround:** https://github.com/microsoft/vscode/issues/247469#issuecomment-3049396773 reports the same problem on Linux Mint 22 with XFCE. Changing the desktop entry from `/usr/share/code/code` to `/usr/bin/code` reportedly prevents it. This supports a credible reported reproduction, not a reproduction executed against current main.
- **Current packaging preserves the distinction:** resources/linux/code.desktop uses `Exec=@@EXEC@@ %F`; build/gulpfile.vscode.linux.ts:56 substitutes `/usr/share/${product.applicationName}/${product.applicationName}` for Debian packages. Desktop startup therefore directly launches the executable rather than the CLI shell wrapper.
- **CLI startup follows a different path:** resources/linux/bin/code.sh invokes the executable with `ELECTRON_RUN_AS_NODE=1` and resources/app/out/cli.js. src/vs/code/node/cli.ts:224-229 prepares the environment and removes ELECTRON_RUN_AS_NODE; lines 480-502 spawn the GUI executable. These differences support investigating startup context but do not conclusively explain Bluetooth power changes.
- **Canonical search:** Repository issue searches for Bluetooth, Linux, and Bluetooth switching off found https://github.com/microsoft/vscode/issues/134461, verified open. Its report concerns startup requesting the BlueZ service, with runtime ownership identified at https://github.com/microsoft/vscode/issues/134461#issuecomment-941023602. It does not establish that Bluetooth is switched off or that both reports share a root cause, so it is related evidence rather than a verified duplicate.
- **Fix verification limits:** The checkout is shallow, and the inspected history yielded no concrete fixing commit. Source inspection cannot observe Linux Bluetooth state; no application launch, build, installation, or artifact-producing test was performed.
