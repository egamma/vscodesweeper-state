# Issue #349469 — Support static imports of npm packages in browser and worker code

[https://github.com/microsoft/vscode/issues/349469](https://github.com/microsoft/vscode/issues/349469)

## Summary

Keep open: current build and development pipelines do not provide the requested cross-environment static package imports. The related diff migration tracks a consumer of this capability, not a replacement for this engineering request.

## Change summary

Support ordinary static npm imports consistently in browser and worker code across development, production, tests, and Monaco.

## Best solution

Establish consistent package resolution across the development transpiler, production bundler, and Monaco extraction pipeline, without per-consumer runtime URL imports or conditional import paths. Preserve asynchronous initialization for wasm where required.

Run the extended suites with node --test build/next/test/transpile.test.ts build/next/test/bundle.test.ts; retain separate acceptance checks for asynchronous wasm initialization.
- **Behavior:**

  > Browser and worker sources can use ordinary static imports from supported npm packages without environment-specific import statements. The same source works in unbundled development output, production builds, tests, and a Monaco consumer bundle. JavaScript package APIs are available when the importing module evaluates; wasm initialization may remain asynchronous. Acceptance must include a module worker, not only a window using an import map.
- **Trace:**

  > build/next/transpile.ts:transpileFile transforms individual files without resolving packages, while build/next/bundle.ts:getBundleOptions externalizes packages. The web development import map in src/vs/code/browser/workbench/workbench-dev.html only maps CSS URLs. externalLinesDiffComputer.ts:loadExternalModule illustrates the runtime URL loader and separate MONACO import path that remain today. Monaco extraction in build/gulpfile.editor.ts is a separate pipeline using applyMonacoConditionals and vendored resources. https://github.com/microsoft/vscode/issues/348904 identifies this infrastructure as a dependency of diff adoption, rather than owning the general capability. The trace establishes these boundaries but not a complete resolution design across every target; preserve Node dependency handling, existing package compatibility, source maps, and asynchronous wasm initialization.

## Evidence

- **Production resolution:** build/next/bundle.ts:getBundleOptions sets packages: 'external' for both neutral and Node bundles; ordinary package imports are not generally bundled into browser consumers.
- **Development resolution:** build/next/transpile.ts:transpileFile uses esbuild.transform without package resolution. Its adjustEsmUrl helper only changes .ts?esm suffixes, not bare package specifiers.
- **Existing import map is insufficient:** src/vs/code/browser/workbench/workbench-dev.html constructs an import map for CSS-module URLs. This does not provide general npm resolution or satisfy worker imports.
- **Concrete remaining workaround:** src/vs/editor/common/diff/externalLinesDiffComputer.ts:loadExternalModule still computes resolveAmdNodeModulePath('@vscode/diff', 'dist/index.js') and dynamically imports that URL. Its MONACO conditional instead uses a static @vscode/diff/core import, demonstrating the environment-specific split.
- **Standalone pipeline:** build/gulpfile.editor.ts extracts editor sources with applyMonacoConditionals and explicitly copies vendored marked and dompurify files. That existing mechanism does not supply the general static npm import capability requested here.

Its diff-specific scope does not absorb package loading for other browser and worker consumers.
