# Issue #63813 — terminal stays open after process exit

[https://github.com/microsoft/vscode/issues/63813](https://github.com/microsoft/vscode/issues/63813)

## Summary

The requested control over external debug-terminal lifetime is still missing: current code deliberately pauses after execution, with no corresponding setting. Keep this accepted request open; the linked implementation proposal was closed without merging, and the newer related report does not supersede it.

## Change summary

Allow external debugging terminals to close after program exit instead of always waiting for a keypress and accumulating across runs.

## Best solution

Provide an explicit, backward-compatible way to opt out of keeping external debug terminals open, while retaining access to output for users who want the pause. Settle whether this is a user setting or a debug-adapter opt-in contract before implementation; do not terminate unrelated terminals or assume debug-session termination means every launched command has finished.

## Plan brief

- **Likely files:** `src/vs/platform/externalTerminal/common/externalTerminal.ts`, `src/vs/platform/externalTerminal/node/externalTerminalService.ts`, `src/vs/workbench/api/node/extHostDebugService.ts`, `src/vs/workbench/contrib/externalTerminal/electron-browser/externalTerminal.contribution.ts`, `src/vs/platform/externalTerminal/test/node/externalTerminalService.test.ts`
- **Validation:** Extend the externalTerminalService unit suite to check command construction for the chosen wait/no-wait contract. Manually debug a short-lived console program repeatedly in supported external terminals: opting out must remove the keypress wait and avoid accumulating finished terminals; the existing default must retain output, and concurrent live or unrelated terminals must remain untouched.
- **Behavior:**

  > Repeated external-terminal debugging currently leaves finished terminal windows waiting for a keypress, requiring manual cleanup. Users need a supported way to avoid that pause while users who depend on inspecting output retain existing behavior by default. Acceptance must cover normal program completion, nonzero exits, repeated runs, and protection of concurrent live terminals. Integrated-terminal accumulation is separate from the original request.
- **Trace:**

  > ExtHostDebugService.$runInTerminal dispatches external requests through runInExternalTerminal in src/vs/workbench/api/node/extHostDebugService.ts to the platform services in src/vs/platform/externalTerminal/node/externalTerminalService.ts. The Linux path appends an unconditional read prompt, Windows appends pause, and Ghostty is launched with wait-after-command enabled. IExternalTerminalSettings and the external-terminal configuration registrations expose executable selection but no wait control. The thread at https://github.com/microsoft/vscode/issues/63813 explains why output retention is intentional and why debug-session end is not a safe universal signal for terminating launched processes. The proposed Linux control in https://github.com/microsoft/vscode/pull/72080 was closed without merging; https://github.com/microsoft/vscode/issues/255629 supplies a newer C#/Konsole example of the same gap. The trace establishes the missing capability, but not the public contract for controlling it; preserve output-retaining defaults and do not expand this into integrated-terminal cleanup.
- **Open decisions:**
  - Should external-terminal waiting be controlled directly by a user setting, by an optional debug-adapter runInTerminal contract, or by both with defined precedence?
  - When waiting is disabled, should terminals close after every program exit or remain open for nonzero exits to preserve runtime-error output?

No final setting or contract is settled.
