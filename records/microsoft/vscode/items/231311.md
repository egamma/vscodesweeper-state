# Issue #231311 — Closing a view while dragging border makes the editor view unresponsive to mouse interaction

[https://github.com/microsoft/vscode/issues/231311](https://github.com/microsoft/vscode/issues/231311)

## Summary

The defect remains source-reproducible on current main: closing a split while its sash is being dragged disposes the sash before the drag-end handler can restore pointer interaction on the remaining editor views.

## Change summary

Closing an editor group with Ctrl+W while dragging its border leaves the remaining editor groups unable to receive mouse input.

## Best solution

Ensure an interrupted split-view sash drag performs the same interaction cleanup as a completed drag, including restoring pointer events on every surviving view when the dragged sash is removed.

## Evidence

- **source reproduction:** In src/vs/base/browser/ui/splitview/splitview.ts, SplitView.onSashStart sets every ViewItem.enabled to false; the setter applies `pointer-events: none` to each view container. Only onSashEnd restores enabled=true.
- **interrupted cleanup:** SplitView.removeView disposes the adjacent sash and its onDidEnd subscription while a drag may still be active. Releasing the pointer afterward cannot invoke SplitView.onSashEnd, so surviving view containers retain `pointer-events: none`.
- **sash lifecycle:** src/vs/base/browser/ui/sash/sash.ts keeps drag listeners in a method-local DisposableStore and Sash.dispose only removes the sash element; disposal does not complete or cancel the active drag lifecycle.
