# Issue #339795 — Markdown preview opened via a #fragment link always jumps back to that fragment when the tab is re-shown

[https://github.com/microsoft/vscode/issues/339795](https://github.com/microsoft/vscode/issues/339795)

## Summary

Traced to source: the host-side Markdown preview never clears the one-time fragment scroll target after the first render, so every subsequent full-page reload (which happens whenever the webview is hidden when an update fires, since the panel isn't created with retainContextWhenHidden) re-sends the original fragment and the webview's own 'ignore saved scrollProgress if a fragment is set' logic jumps back to it, discarding the user's real scroll position.

## Change summary

A Markdown preview opened via a `#heading` link keeps re-jumping to that heading on every tab re-show instead of restoring the scroll position the user left it at.

## Best solution

Clear the preview's one-shot fragment target after its first use (mirroring what the webview-side script already does for its own `state.fragment`), so later reloads fall back to the persisted `scrollProgress` instead of re-including the original fragment in every re-rendered page.

- **Behavior:**

  > A Markdown preview opened via a link containing a `#heading` fragment should scroll to that heading once, on first open. After the user scrolls elsewhere in that same preview tab, switching away and back to the tab (or any other action that causes the preview page to fully reload) must restore the user's last scroll position, not jump back to the original heading. The fragment-based initial scroll should behave as one-time, exactly like the webview's own persisted `state.fragment` already does.
- **Trace:**

  > `MarkdownPreview` in extensions/markdown-language-features/src/preview/preview.ts stores the opening fragment in `#scrollToFragment` (set once in the constructor, declared `readonly`) and surfaces it forever via the `state` getter. Whenever `#updatePreview()` decides `shouldReloadPage` is true (forced update, document switch, or — notably — `!this.#webviewPanel.visible`, i.e. a reload that happens to fire while the tab is hidden), it calls `renderDocument(..., this.state, ...)` again, which re-sends the stale fragment through `documentRenderer.ts`'s `initialData.fragment`. On the webview side, preview-src/index.ts line 109 refuses to use the persisted `scrollProgress` whenever `settings.settings.fragment` is truthy, so the stale fragment wins every time. The boundary: don't touch the webview-side one-shot handling (preview-src/index.ts lines 121-150), which is already correct — the missing reset belongs on the host side, mirroring the webview's own `state.fragment = undefined` pattern. No related open PR or prior fix found (`git log` on preview.ts shows no related change).

## Evidence

- **host never clears fragment:** extensions/markdown-language-features/src/preview/preview.ts: `#scrollToFragment` is set once in the constructor (readonly) from the `fragment` StartingScrollLocation and is included unconditionally in the `state` getter (`fragment: this.#scrollToFragment`); nothing ever resets it.
- **state re-used on every full reload:** preview.ts `#updatePreview()` recomputes `shouldReloadPage = forceUpdate || !this.#currentVersion || ... || !this.#webviewPanel.visible` and, when true, calls `renderDocument(..., this.state, ...)` again — so any reload that happens while the panel is hidden re-sends the original fragment.
- **fragment always wins over saved scroll position:** extensions/markdown-language-features/src/preview/documentRenderer.ts line 88 sets `initialData.fragment = state?.fragment || ...` from that same stale state; preview-src/index.ts line 109 explicitly checks `!settings.settings.fragment` before honoring the persisted `scrollProgress`, so a persistently-set fragment always overrides the saved scroll position on every reload.
- **webview already treats its own copy as one-shot:** preview-src/index.ts line 131 does `state.fragment = undefined; vscode.setState(state);` after first using the fragment, showing the intended design was for the fragment to be a one-time scroll — the host-side mirror of that reset is missing.
