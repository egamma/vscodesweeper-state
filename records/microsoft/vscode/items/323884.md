# Issue #323884 — Recent Opens in New Window

[https://github.com/microsoft/vscode/issues/323884](https://github.com/microsoft/vscode/issues/323884)

## Summary

A real discoverability gap remains on the Welcome page: modifier-click already opens a recent workspace in a new window, but no visible control communicates or directly exposes that behavior. The Backlog milestone records this as accepted work, so a judgment close would contradict existing triage.

## Change summary

Provide a visible option on Welcome-page Recent entries for opening a workspace or folder in a new window.

## Best solution

Expose an accessible per-entry Open in New Window action while preserving ordinary click, Ctrl/Cmd-click, remote-authority handling, and removal behavior. Decide whether that affordance belongs only on the Welcome page or should be consistent across Open Recent surfaces.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/welcomeGettingStarted/browser/gettingStarted.ts`, `src/vs/workbench/contrib/welcomeGettingStarted/browser/media/gettingStarted.css`
- **Validation:** Manually verify on the Welcome page that the chosen affordance opens local and remote Recent entries in a separate window, is keyboard and screen-reader accessible, and leaves ordinary click, Ctrl/Cmd-click, and Remove from Recently Opened behavior unchanged.
- **Behavior:**

  > A user can discover and invoke Open in New Window directly from a Recent entry on the Welcome page. Ordinary activation still opens using the existing default behavior, and Ctrl/Cmd-click remains supported. The action must be keyboard accessible and have an appropriate accessible label. Local folders, workspaces, and remote entries must retain their existing routing behavior.
- **Trace:**

  > The Welcome-page list is built by `buildRecentlyOpenedList` in src/vs/workbench/contrib/welcomeGettingStarted/browser/gettingStarted.ts. Its entry click handler passes `forceNewWindow: e.ctrlKey || e.metaKey` to `IHostService.openWindow`, so the capability already exists behind an undisclosed modifier. The same renderer creates a hover/focus-visible removal action, styled in src/vs/workbench/contrib/welcomeGettingStarted/browser/media/gettingStarted.css, but no new-window action. The Open Recent picker in src/vs/workbench/browser/actions/windowActions.ts explicitly describes the modifier, showing that no host-service change is required. Preserve `remoteAuthority`, ordinary activation, modifier-click, and removal semantics; the uncertainty begins with the visible interaction and which Recent surfaces should share it. Related context: https://github.com/microsoft/vscode/issues/320413.
- **Open decisions:**
  - Should the choice be a per-entry inline action, a configurable default, or another visible interaction?
  - Should the affordance apply only to the Welcome-page Recent list or consistently across other Open Recent surfaces?
