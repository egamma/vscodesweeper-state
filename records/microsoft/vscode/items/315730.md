# Issue #315730 — Should configuring tools close after closing agent.md

[https://github.com/microsoft/vscode/issues/315730](https://github.com/microsoft/vscode/issues/315730)

## Summary

The lifecycle gap remains on current main: closing the custom-agent editor does not cancel its Configure Tools picker. The issue should stay open, with a maintainer deciding which editor/model lifecycle signal should own cancellation.

## Change summary

Close the Configure Tools quick picker when the originating `*.agent.md` editor is closed.

## Best solution

Bind the code-lens picker to the originating agent editor's lifetime so closing that editor dismisses the picker without applying changes, while preserving normal picker behavior in chat and other editors.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/promptSyntax/promptToolsCodeLensProvider.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatToolPicker.ts`
- **Validation:** Open an `*.agent.md` file with a `tools` attribute, invoke its Configure Tools code lens, close that editor tab using its close button, and verify the quick picker closes without rewriting the file; also verify accepting the picker while the editor remains open still updates the tools attribute.
- **Behavior:**

  > The Configure Tools picker opened from an `*.agent.md` code lens is contextual to that editor. Closing the originating editor must dismiss the picker without applying a selection. Keeping the editor open and accepting a selection must continue to rewrite the tools attribute normally, and chat-input Configure Tools behavior must remain unchanged.
- **Trace:**

  > `PromptToolsCodeLensProvider.updateTools` in `src/vs/workbench/contrib/chat/browser/promptSyntax/promptToolsCodeLensProvider.ts` awaits `showToolsPicker` while retaining the text model but passes no cancellation token. `showToolsPicker` in `src/vs/workbench/contrib/chat/browser/actions/chatToolPicker.ts` already hides itself when its optional token is cancelled. The chat-input caller in `chatToolActions.ts` uses that contract for mode changes, whereas the prompt-file code-lens caller has no corresponding editor-lifetime signal. The uncertainty begins at choosing whether model disposal reliably represents closing the originating tab or whether the workbench editor-close event must be correlated by resource. The boundary is the agent-file code-lens flow; do not alter ordinary quick-picker dismissal or chat tool selection semantics.
- **Open decisions:**
  - Should cancellation follow `ITextModel.onWillDispose`, or must it track `IEditorService.onDidCloseEditor` so closing the tab is handled even while the model remains retained by the pending command?
  - Should the same lifecycle behavior also cover the analogous `.toolsets.jsonc` Configure Tools code lens, or remain scoped to `*.agent.md` for this issue?
  - Which browser/unit harness can assert quick-tree dismissal from an editor-close event without relying only on manual verification?
