# Issue #188716 — Find/Replace indicates the tooltip "enter" is for both "next item" and "replace".  Actual behavior depends on which textbox has focus.

[https://github.com/microsoft/vscode/issues/188716](https://github.com/microsoft/vscode/issues/188716)

## Summary

Keep open for a focused tooltip-design decision: current source still builds static shortcut hints without explaining their focus requirements. This issue already owns a confirmed duplicate, and the existing keyboard shortcuts do not resolve the discoverability problem.

## Change summary

Make the editor Find/Replace shortcut tooltips distinguish broadly available navigation and replacement shortcuts from focus-dependent Enter bindings.

## Best solution

Make the Find/Replace button hints accurately communicate how to navigate and replace without changing established Enter behavior. Decide whether to advertise the broader shortcuts or explicitly qualify focus-dependent shortcuts, while respecting customized keybindings.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/find/browser/findWidget.ts`, `src/vs/editor/contrib/find/browser/findController.ts`, `src/vs/editor/contrib/find/test/browser/findController.test.ts`
- **Validation:** With default Windows keybindings, open Ctrl+H in a document containing several matches and inspect Next Match and Replace hints while switching focus between the Find and Replace inputs. Confirm the agreed hints accurately communicate their scope, F3 advances without replacing, Ctrl+Shift+1 replaces one occurrence, and Enter retains its input-dependent behavior. Repeat with customized navigation/replacement shortcuts and check the button ARIA labels.
- **Behavior:**

  > The Find/Replace widget currently advertises Enter for different actions without explaining that its meaning depends on input focus. Users should be able to discover how to skip a match and replace another without inferring that focus dependency. The finished hints must follow the agreed presentation policy and respect customized keybindings. Existing Find-input Enter navigation, Replace-input Enter replacement, and direct button activation must remain unchanged.
- **Trace:**

  > FindWidget._keybindingLabelFor in src/vs/editor/contrib/find/browser/findWidget.ts delegates to appendKeybinding without an explicit context; Next Match and Replace consume that label when their SimpleButton instances are constructed. SimpleButton uses the label for both hover content and its initial ARIA label. In src/vs/editor/contrib/find/browser/findController.ts, both commands have broader editor-focused shortcuts plus separately registered input-focused Enter shortcuts. AbstractKeybindingService and KeybindingResolver perform reverse lookup using a default context and can fall back to the last registered binding; they do not promise to select the least focus-specific shortcut. The boundary is Find/Replace hint clarity, not a change to dispatch semantics or a global redesign of keybinding lookup. https://github.com/microsoft/vscode/issues/199880 independently reports the same symptom and was closed as a duplicate of this issue. The remaining uncertainty is the intended user-visible hint policy, not whether keyboard navigation and replacement already exist.
- **Open decisions:**
  - Should Find/Replace hints prefer the broader editor-focused shortcuts, or retain input-dependent shortcuts with an explicit explanation of their focus requirements?

## Evidence

- **Current tooltip construction:** src/vs/editor/contrib/find/browser/findWidget.ts:980–982, 1082–1089 and 1205–1218 construct Next Match and Replace labels using appendKeybinding('', actionId), without supplying the editor/input context or explaining focus requirements. SimpleButton at lines 1421–1425 uses the resulting static label for both its ARIA label and hover content.
- **Existing shortcuts do not cover the central ask:** src/vs/editor/contrib/find/browser/findController.ts:777–791 registers Find Next with F3 on Windows/Linux and a separate find-input-focused Enter binding; lines 1153–1173 register Replace One with Ctrl+Shift+1 and a separate replace-input-focused Enter binding. These already permit skipping and replacing by keyboard, but their existence does not make the tooltips explain the distinction. The editor.find configuration in src/vs/editor/common/config/editorOptions.ts does not expose a shortcut-hint presentation setting.
- **Lookup explanation from the discussion:** https://github.com/microsoft/vscode/issues/40389#issuecomment-352404326 explains reverse keybinding lookup, and https://github.com/microsoft/vscode/issues/40389#issuecomment-944372273 says the later improvement selects a binding matching the global context—not necessarily the least context-specific binding. Current AbstractKeybindingService.lookupKeybinding uses its default context when none is supplied; KeybindingResolver.lookupPrimaryKeybinding at src/vs/platform/keybinding/common/keybindingResolver.ts:291–311 falls back to the last binding if no context matches. This explains why the linked menu fix does not establish resolution of this tooltip request.
