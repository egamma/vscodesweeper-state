# Issue #195960 — Add "resourceWebviewId" context key for webviews in `editor/title/context` contribution point

[https://github.com/microsoft/vscode/issues/195960](https://github.com/microsoft/vscode/issues/195960)

## Summary

Keep open: current source still lacks a dedicated context key identifying the right-clicked webview tab independently of the active editor. The older related request concerns title-bar contributions, not the same inactive-tab context-menu limitation.

## Change summary

Expose the target webview's extension-provided view type to editor/title/context when clauses, including for inactive tabs.

## Best solution

Provide a supported target-specific webview identity context for editor tab menus while preserving activeWebviewPanelId's existing active-editor semantics. Extensions should not need to infer identity from generated resource URI paths.

## Evidence

- **Target tab context:** src/vs/workbench/browser/parts/editor/editorTabsControl.ts, EditorTabsControl.onTabContextMenu, updates resource and editor-state context keys from the clicked EditorInput before opening MenuId.EditorTitleContext, but supplies no target-specific webview identity.
- **Existing active identity is insufficient:** src/vs/workbench/contrib/webviewPanel/browser/webviewWorkbenchService.ts registers CONTEXT_ACTIVE_WEBVIEW_PANEL_ID using getWebviewId(group.activeEditor), which returns the active input's webview.providedViewType. Right-clicking another tab does not make that value identify the clicked webview.
- **Existing capability check:** src/vs/workbench/contrib/webview/browser/webviewElement.ts supplies webviewId only in the overlay for MenuId.WebviewContext, not EditorTitleContext. WebviewInput.resource in src/vs/workbench/contrib/webviewPanel/browser/webviewEditorInput.ts embeds providerId in a generated URI path, making resourcePath matching a possible workaround rather than a dedicated view-type context contract.
