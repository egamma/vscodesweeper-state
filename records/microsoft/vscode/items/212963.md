# Issue #212963 — Add support for running command when clicking on a progress status item

[https://github.com/microsoft/vscode/issues/212963](https://github.com/microsoft/vscode/issues/212963)

## Summary

Keep open: the workbench supports clickable window progress internally, but the extension API still cannot supply its command. This accepted Backlog request has 63 upvotes, and no verified canonical or landed API implementation was found.

## Change summary

Allow extensions to associate a command with window progress so clicking updated build progress can reveal the running task.

## Best solution

Expose a supported click-command contract for extension-created window progress, using the existing workbench capability while preserving behavior for callers that omit it. API owners should settle the command type and supported progress locations before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostProgress.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadProgress.ts`, `src/vs/workbench/services/progress/browser/progressService.ts`, `src/vs/workbench/services/progress/test/browser/progressService.test.ts`
- **Validation:** After the API contract is approved, add bridge and progress-service tests demonstrating command propagation and invocation. Manually run an extension using window.withProgress at ProgressLocation.Window, update its build message to Building [45/120], and activate the status entry with mouse and keyboard: the registered command must reveal the intended task. Verify that progress disappears on completion and callers without a command retain their existing behavior.
- **Behavior:**

  > An extension can report changing window progress, such as Building [45/120], while retaining an action that reveals the associated build task when the progress entry is activated. Updating the message must not lose the action, and completing the operation must remove the progress entry. Existing callers without a command must retain their current behavior. Acceptance includes mouse and keyboard activation of the specified command and unchanged progress reporting.
- **Trace:**

  > The public ProgressOptions declaration in src/vscode-dts/vscode.d.ts has no command, and ExtHostProgress.withProgress in src/vs/workbench/api/common/extHostProgress.ts serializes only the existing options. IProgressOptionsDto in src/vs/workbench/api/common/extHost.protocol.ts is the bridge contract consumed by MainThreadProgress.$startProgress in src/vs/workbench/api/browser/mainThreadProgress.ts. Internally, IProgressWindowOptions already accepts a string command; ProgressService.withProgress selects direct status-bar progress when it is present, and updateWindowProgress assigns it to the status entry. This establishes a missing public contract rather than a missing renderer capability. Preserve the no-command silent-notification path and existing cancellation semantics; do not redesign task execution or unrelated progress locations. https://github.com/swiftlang/vscode-swift/pull/794 is related extension-side work, not a core API fix.
- **Open decisions:**
  - Should the public command accept only a command ID string, as requested and supported internally, or also a vscode.Command with arguments, as StatusBarItem does?
  - Should command be supported only for ProgressLocation.Window, and what documented behavior should callers receive if they supply it for another progress location?

## Evidence

In src/vs/workbench/services/progress/browser/progressService.ts:95-105, window progress with a command uses the status-bar path; without one it uses a silent notification. updateWindowProgress passes options.command into the status entry at lines 158 and 190.
