# Issue #201555 — Moving outline view out of explorer makes command name weird

[https://github.com/microsoft/vscode/issues/201555](https://github.com/microsoft/vscode/issues/201555)

## Summary

Still present on current main: when a view is dragged out of its container, it lands in a generated container whose title is the placeholder "User View Container", and the focus command's category is taken from that static title — so the palette shows a nonsensical prefix for "Focus on Outline View". Team-authored issue with no fix commit, so it stays open; the remaining question is what the category should become for generated/merged containers.

## Change summary

Moving the Outline view into its own activity bar (or secondary side bar) container makes the "Focus on Outline View" command show a weird/placeholder category prefix.

## Best solution

In ViewsService.onViewDescriptorsAdded, stop using the raw ViewContainer.title as the focus-action category for generated containers — derive it from the view container model's resolved title (which merges to the view name for single-view containers) or drop the category entirely — and re-register when the container title changes.

## Plan brief

- **Likely files:** `src/vs/workbench/services/views/browser/viewsService.ts`, `src/vs/workbench/services/views/browser/viewDescriptorService.ts`
- **Validation:** A views service test that moves a view into a generated container and asserts the registered `<viewId>.focus` command's title/category no longer contains the "User View Container" placeholder; plus a manual check in the command palette after dragging Outline to the activity bar and to the secondary side bar.
- **Behavior:**

  > After dragging a view (e.g. Outline) out of its default container into the activity bar or the secondary side bar, the command palette entry for focusing it must read sensibly — no "User View Container" placeholder prefix and no redundant doubling of the view name. Views still in their original containers keep their current category (e.g. "Explorer: Focus on Outline View"). Acceptance: drag Outline to the activity bar, open the palette, type "Focus on Outline" and see a clean label; repeat for the secondary side bar; existing focus-command IDs and keybindings are unchanged.
- **Trace:**

  > ViewsService.onViewDescriptorsAdded (src/vs/workbench/services/views/browser/viewsService.ts:169) passes `container.title` as the `category` of the focus action created in registerFocusViewAction (same file, ~line 557). When a view is moved out, ViewDescriptorService.registerGeneratedViewContainer (src/vs/workbench/services/views/browser/viewDescriptorService.ts:554) creates the container with the placeholder title "User View Container", explicitly commented as never meant to be displayed — so the palette shows that placeholder. The resolved, user-visible title lives on the view container model (merged with the view name when `mergeViewWithContainerWhenSingleView` is set), not on the static ViewContainer descriptor. Boundary: do not change command IDs, keybindings, the `<viewId>.active` context keys, or the behavior of focus actions for views in their default containers; the generated-container placeholder itself is used elsewhere as a sentinel. Related: the secondary side bar report in https://github.com/microsoft/vscode/issues/201555#issuecomment-1870968558.
- **Open decisions:**
  - For a view moved into its own generated container, what should the focus command's category be — the view's own name, a generic "View", or no category at all?
  - Should the category update live when the container's resolved title changes (e.g. a second view is moved into the same generated container), or is a registration-time value acceptable?
