# Issue #159356 — Notebook API: Support Language Providers for Notebook Output Cells

[https://github.com/microsoft/vscode/issues/159356](https://github.com/microsoft/vscode/issues/159356)

## Summary

Keep this accepted feature request open: current JSON output rendering provides syntax tokenization, not the notebook-scoped semantic tokens and document links requested here. The request has 43 upvotes, and no verified canonical or completed implementation was found.

## Change summary

Support notebook-scoped semantic token and document link providers in rendered JSON notebook outputs.

## Best solution

Define a supported contract for applying language providers to notebook output content, preserving notebook identity and interactive link navigation. Resolve the output-document and renderer boundary before implementation rather than treating HTML presentation or opening output in a separate editor as equivalent coverage.

## Plan brief

- **Likely files:** `extensions/markdown-language-features/notebook/index.ts`, `src/vs/workbench/contrib/notebook/browser/view/renderers/backLayerWebView.ts`, `src/vs/workbench/contrib/notebook/browser/view/renderers/webviewPreloads.ts`, `src/vs/workbench/contrib/notebook/browser/notebook.contribution.ts`, `src/vs/editor/common/languageSelector.ts`
- **Validation:** Use an xbook notebook test extension registering JSON semantic-token and document-link providers with notebookType: 'xbook'. Execute a cell producing JSON with an XPath location; verify provider-derived highlighting and Ctrl-click navigation to the corresponding XML node inside the rendered output. Replace the output and verify tokens and links update without affecting notebook inputs or ordinary JSON editors.
- **Behavior:**

  > The reporter's xbook notebook emits JSON containing XPath locations, but the rendered output no longer displays provider-specific highlighting or responds to Ctrl-click on those locations. The requested outcome is supported semantic-token and document-link behavior within JSON notebook outputs, using notebook-scoped language providers. Acceptance should exercise both highlighting and navigation, including output replacement, while leaving notebook input cells and ordinary JSON documents unchanged. HTML presentation and opening output in a separate editor are not equivalent outcomes.
- **Trace:**

  > The built-in markdown notebook renderer registers application/json in extensions/markdown-language-features/package.json. Its renderOutputItem in extensions/markdown-language-features/notebook/index.ts converts JSON into fenced-code HTML, and BackLayerWebView._handleHighlightCodeBlock in src/vs/workbench/contrib/notebook/browser/view/renderers/backLayerWebView.ts delegates to tokenizeToString, which uses TokenizationRegistry rather than semantic-token or document-link providers. notebook.contribution.ts separately exposes output text models, but that does not make the inline HTML output a language-provider client. The notebookType selector is matched against candidate notebook identity in src/vs/editor/common/languageSelector.ts. The unresolved boundary is what output document and notebook identity providers would receive, and whether existing provider registrations acquire output applicability. Preserve existing input-cell behavior and output trust restrictions; the later HTML-link complaint in https://github.com/DeltaXML/vscode-xpath-notebook/issues/10 is not proof of the same remaining defect.
- **Open decisions:**
  - Should existing notebookType-scoped language-provider registrations automatically apply to matching output content, or should output applicability require an explicit opt-in contract?
  - What document URI, content, and notebook association should providers observe for an individual output item, including when that output is replaced?
