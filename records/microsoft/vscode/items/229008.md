# Issue #229008 — Adopt new call stack widget for exceptions

[https://github.com/microsoft/vscode/issues/229008](https://github.com/microsoft/vscode/issues/229008)

## Summary

A real gap remains on current main: debug exceptions still render a linkified plain-text stack trace instead of the reusable call-stack widget already used by testing. A debug maintainer explicitly adopted this issue as the tracker, and no open fixing PR or older same-symptom canonical was found.

## Change summary

Render debug exception stack traces with the reusable call-stack widget so source frames and offending lines are visible at a glance.

## Best solution

Use the shared CallStackWidget in the debug exception zone, backed by the paused thread's structured call stack, while preserving the exception summary, copy action, accessibility, and a sensible fallback when structured source frames are unavailable.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/exceptionWidget.ts`, `src/vs/workbench/contrib/debug/browser/debugEditorContribution.ts`, `src/vs/workbench/contrib/debug/browser/callStackWidget.ts`, `src/vs/workbench/contrib/debug/browser/media/exceptionWidget.css`, `src/vs/workbench/contrib/debug/test/browser/exceptionWidget.test.ts`
- **Validation:** Add targeted debug browser tests covering structured frames and the no-structured-frames fallback, runnable with `scripts/test.sh --grep "ExceptionWidget"`; manually stop on an exception and verify source snippets, frame navigation, collapse behavior, copy output, keyboard focus, screen-reader labeling, and zone relayout.
- **Behavior:**

  > When debugging stops on an exception, the inline exception surface presents available stack frames with source context and navigable locations rather than only a plain-text trace. The exception type, description, copy and close actions, keyboard accessibility, and screen-reader information remain available. Adapters that provide no usable structured source frames still show their textual exception details without losing information. The widget remains correctly sized and positioned as frames expand, collapse, or load.
- **Trace:**

  > ExceptionWidget in src/vs/workbench/contrib/debug/browser/exceptionWidget.ts currently renders `DebugProtocol.ExceptionDetails.stackTrace` through LinkDetector. DebugEditorContribution.toggleExceptionWidget in src/vs/workbench/contrib/debug/browser/debugEditorContribution.ts already retrieves the stopped thread's call stack, identifies the exception frame, and then discards that structured stack when constructing ExceptionWidget. CallStackWidget in src/vs/workbench/contrib/debug/browser/callStackWidget.ts provides source-backed frame rendering, accessibility labels, collapse behavior, asynchronous skipped-frame loading, and content-height events; TestResultsViewContent demonstrates its integration and layout lifecycle. The plan should determine the narrow data and lifecycle boundary needed to embed that widget in the editor zone while preserving raw-text fallback and existing exception actions. Do not change the Debug Adapter Protocol, the Call Stack view, or general debugger frame-loading semantics. Related tracker: https://github.com/microsoft/vscode/issues/229008

## Evidence

- **current exception rendering:** src/vs/workbench/contrib/debug/browser/exceptionWidget.ts still reads `exceptionInfo.details.stackTrace` as a string and renders it through `LinkDetector.linkify`, with no CallStackWidget integration.
- **shared widget exists:** src/vs/workbench/contrib/debug/browser/callStackWidget.ts defines the reusable CallStackWidget and structured CallStackFrame model; its documentation says it is intended for both debug exceptions and testing, but current debug exception code does not instantiate it.
- **working adoption pattern:** src/vs/workbench/contrib/testing/browser/testResultsView/testResultsViewContent.ts creates CallStackWidget, supplies structured frames with `setFrames`, responds to content-height changes, and lays it out within the containing editor.
- **available debug data:** src/vs/workbench/contrib/debug/browser/debugEditorContribution.ts already obtains the stopped thread's structured call stack before opening ExceptionWidget, but passes only exceptionInfo, the session, and positioning data into the widget.
- **maintainer intent:** A debug maintainer explicitly said this issue should track adoption of testing's stack-trace widget for debug exceptions: https://github.com/microsoft/vscode/issues/229008#issuecomment-2555975847
