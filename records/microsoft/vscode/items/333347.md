# Issue #333347 — Highlighting text appears to unhighlighted when tooltip/pop up appear

[https://github.com/microsoft/vscode/issues/333347](https://github.com/microsoft/vscode/issues/333347)

## Summary

Genuine, well-documented visual bug: text selection visibly fades to near-background color the instant a hover/tooltip appears while drag-selecting, confirmed with a clear gif across two VS Code versions with extensions disabled — routing to the editor/hover area since the exact trigger needs an owner's confirmation.

## Change summary

While drag-selecting text, if a hover popup appears, the current text selection immediately loses its highlighted appearance (dims almost to editor background color).

## Best solution

Have the editor/hover team investigate why showing the content hover widget correlates with the editor view losing its `.focused` state (which drives `--vscode-editor-selectionBackground` vs. the much dimmer `--vscode-editor-inactiveSelectionBackground` in src/vs/editor/browser/viewParts/selections/selections.css) during an active drag-select, and either prevent that focus/class flip during dragging or decouple selection-dimming from hover visibility.

## Evidence

- **selection dimming mechanism:** src/vs/editor/browser/viewParts/selections/selections.css:14-20 renders selected text with `--vscode-editor-selectionBackground` only while `.monaco-editor` has the `.focused` class, otherwise it uses the much dimmer `--vscode-editor-inactiveSelectionBackground`; the class is toggled in src/vs/editor/browser/view/viewOverlays.ts:87,125 from `ViewFocusChangedEvent`, which originates from `viewModelImpl.ts:244-247 setHasFocus()` (DOM text-input focus).
- **hover focus-stealing is conditional:** src/vs/editor/contrib/hover/browser/contentHoverWidget.ts:348-349 only calls `.focus()` on the hover container when `renderedHover.shouldFocus` is true (keyboard-triggered hover), so a plain mouse hover during drag-select should not, in principle, steal DOM focus from the editor — meaning the exact trigger for the observed focus/CSS flip during a drag needs to be confirmed by someone who can run the editor.
- **existing mousedown suppression:** src/vs/editor/contrib/hover/browser/contentHoverController.ts:137-146,223-232 already hides the hover on mousedown and suppresses new hover computations while `_isMouseDown` is true, so if a hover is still appearing mid-drag there may be a race (e.g. an in-flight scheduled hover operation started just before mousedown) not covered by this guard.
- **reporter evidence:** Screenshots and a clear gif in the issue body show the JS function `log()` losing its selection highlight the instant a popup appears; reproduced with extensions disabled on both VS Code 1.135.0 and 1.113.0.
