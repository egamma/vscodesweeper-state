# Issue #198883 — Apparent lifecycle discrepancy between `ManagementPersistentConnection` and  `ExtensionHostPersistentConnection`

[https://github.com/microsoft/vscode/issues/198883](https://github.com/microsoft/vscode/issues/198883)

## Summary

The configurable grace period addressed only part of the report; current source still treats extension-host and management-connection failures differently, and a recent current-version report confirms that users can still lose the extension host while the remote window remains usable.

## Change summary

Recover the remote extension host, or require a window reload, when its persistent connection expires while the management connection remains alive.

## Best solution

Make extension-host permanent reconnection failure converge on a reliable user-visible recovery state: either start a fresh remote extension host with a new token or consistently prompt for reload. The remote area should also verify when the five-minute shortened grace period may override a configured long grace period.

## Plan brief

- **Likely files:** `src/vs/platform/remote/common/remoteAgentConnection.ts`, `src/vs/server/node/remoteExtensionHostAgentServer.ts`, `src/vs/server/node/extensionHostConnection.ts`, `src/vs/workbench/api/node/extensionHostProcess.ts`, `src/vs/workbench/services/extensions/common/remoteExtensionHost.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/contrib/remote/browser/remote.ts`
- **Validation:** Add a focused remote-connection lifecycle test that expires an extension-host token while keeping the management connection alive, then assert that the workbench either establishes a fresh extension-host connection or presents the reload action; separately verify the configured and shortened grace-time cases.
- **Behavior:**

  > After a remote extension-host connection exceeds its applicable reconnection grace period, the workbench must not remain apparently connected with extensions silently unavailable. It must either recreate and initialize a fresh remote extension host or clearly require a window reload. A configured long grace period must have documented, testable behavior when another connection triggers the short-grace mechanism.
- **Trace:**

  > The extension host schedules long and short disconnect timers in src/vs/workbench/api/node/extensionHostProcess.ts. The server can trigger the short timer from RemoteExtensionHostAgentServer when another connection arrives, and later rejects an expired extension-host token as previously seen. ExtensionHostPersistentConnection converts that rejection into a nonfatal permanent failure and disposes its protocol, while RemoteAgentConnectionStatusListener observes only management-connection state. RemoteExtensionHost and AbstractExtensionService contain a separate exit/restart path, but the report and current-version confirmation show that it does not reliably restore the user-visible extension-host state. Preserve management-connection reconnection behavior and normal extension-host crash handling while resolving this lifecycle boundary.
- **Open decisions:**
  - Should an expired extension-host reconnection token automatically create a fresh remote extension host, or should the workbench require a full reload?
  - Should a new connection continue reducing other disconnected extension hosts to the five-minute short grace period when an explicit longer `reconnection-grace-time` is configured?
  - Which layer should own the user notification when only the extension-host connection reaches permanent failure?

## Evidence

- **partial implementation:** https://github.com/microsoft/vscode/commit/6cc2564bf9dfdb55cf62eebf7746cad0279819bd added configurable reconnection grace time, but https://github.com/microsoft/vscode/pull/274910 describes only plumbing the timeout through the server and remote client; it does not address recovery after an extension-host permanent failure.
- **current failure handling:** src/vs/platform/remote/common/remoteAgentConnection.ts constructs ExtensionHostPersistentConnection with reconnectionFailureIsFatal=false, so an unknown old token disposes only that protocol, while ManagementPersistentConnection failures use the global fatal path.
- **server behavior:** src/vs/server/node/remoteExtensionHostAgentServer.ts still rejects a reconnecting extension-host token whose prior connection has expired as `Unknown reconnection token (seen before)`.
- **notification gap:** RemoteAgentConnectionStatusListener in src/vs/workbench/contrib/remote/browser/remote.ts subscribes to remoteAgentService.getConnection(), whose state events come from the management connection in src/vs/workbench/services/remote/common/abstractRemoteAgentService.ts; it does not directly observe ExtensionHostPersistentConnection permanent failures.
- **current confirmation:** https://github.com/microsoft/vscode/issues/198883#issuecomment-3978653984 reports the same `renderer disconnected for too long` termination on VS Code 1.109.5 even with `reconnection-grace-time` set to 86400 seconds.
- **short-grace interaction:** src/vs/server/node/remoteExtensionHostAgentServer.ts shortens disconnected extension-host grace periods when any new connection arrives; src/vs/workbench/api/node/extensionHostProcess.ts then schedules a second timer capped by ProtocolConstants.ReconnectionShortGraceTime, currently five minutes.
