# Issue #115672 — Twisties appear only after the view has loaded for the view

[https://github.com/microsoft/vscode/issues/115672](https://github.com/microsoft/vscode/issues/115672)

## Summary

The delayed twistie remains source-reproducible on current main: tree rows immediately use a codicon glyph, while the codicon font intentionally blocks glyph rendering until the font loads. The fixed-width twistie container now prevents most label movement, but it does not address the delayed icon appearance.

## Change summary

Explorer tree twisties appear after the surrounding view content has rendered, producing visible startup flicker and previously shifting labels.

## Best solution

Ensure the standard tree twistie is available for the first tree paint without weakening product-icon theming or causing fallback-glyph flashes elsewhere. This needs a focused design pass across tree rendering and shared codicon loading because the underlying font behavior affects more than the Explorer.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/tree/abstractTree.ts`, `src/vs/base/browser/ui/tree/media/tree.css`, `src/vs/base/browser/ui/codicons/codicon/codicon.css`, `src/vs/platform/theme/browser/iconsStyleSheet.ts`, `src/vs/workbench/services/themes/browser/workbenchThemeService.ts`
- **Validation:** Launch Code OSS with an uncached or throttled codicon font and capture the Explorer's first rendered frame; collapsible rows must show their twisties immediately, labels must remain stationary, and product-icon theme loading must not display fallback glyphs.
- **Behavior:**

  > On a cold workbench load, collapsible Explorer rows display their twisties in the first frame in which their labels are visible. Labels do not move when icon fonts finish loading. Product-icon themes and non-tree codicons retain their existing appearance, and collapsed versus expanded state remains visually correct.
- **Trace:**

  > TreeRenderer in src/vs/base/browser/ui/tree/abstractTree.ts creates the twistie element and applies Codicon.treeItemExpanded during the initial row render. The glyph comes from the webfont declared with `font-display: block` in src/vs/base/browser/ui/codicons/codicon/codicon.css; themed icon fonts generated by src/vs/platform/theme/browser/iconsStyleSheet.ts use the same policy, and WorkbenchThemeService installs their generated stylesheet asynchronously. The fixed width in src/vs/base/browser/ui/tree/media/tree.css protects layout but cannot make the blocked glyph visible. The uncertainty starts at the shared-font boundary: the plan must determine whether first-paint readiness belongs in workbench font loading or can be isolated to standard tree twisties without changing product-icon theme semantics. Do not alter tree expansion behavior, indentation, extension tree APIs, or fallback behavior for unrelated codicons.
- **Open decisions:**
  - Should first-paint availability be guaranteed for the shared codicon font across the workbench, or only for the standard tree twistie while product-icon themes continue loading asynchronously?
  - When a product-icon theme replaces the default twistie glyph, should the first frame show the default codicon and swap later, or withhold the themed tree until its font is ready?

## Evidence

- **current source path:** src/vs/base/browser/ui/tree/abstractTree.ts creates `.monaco-tl-twistie` synchronously and applies `Codicon.treeItemExpanded` for collapsible nodes, so the twistie depends on the codicon glyph at initial render.
- **font loading behavior:** src/vs/base/browser/ui/codicons/codicon/codicon.css declares the codicon webfont with `font-display: block`; src/vs/platform/theme/browser/iconsStyleSheet.ts uses the same blocking behavior for product-icon fonts. Glyphs can therefore remain invisible while their font loads.
- **layout mitigation only:** src/vs/base/browser/ui/tree/media/tree.css now gives `.monaco-tl-twistie` a fixed 16px width and `flex-shrink: 0`, which reserves its layout space but does not make the glyph visible before the font is ready.
- **confirmed original diagnosis:** The discussion at https://github.com/microsoft/vscode/issues/115672 and https://github.com/microsoft/vscode/issues/115585#issuecomment-772316923 identifies delayed codicon loading; later confirmation at https://github.com/microsoft/vscode/issues/115585#issuecomment-773464358 says the twistie delay remained after the separate debug-view flicker was fixed.
