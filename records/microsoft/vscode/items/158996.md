# Issue #158996 — "Follow link" hover is not linkified on markdown links

[https://github.com/microsoft/vscode/issues/158996](https://github.com/microsoft/vscode/issues/158996)

## Summary

The defect remains source-reproducible on current main: link decorations build their hover synchronously before a lazy DocumentLink has been resolved, so "Follow link" is rendered as plain text. This team-authored On Deck issue should remain open in the existing workbench-link area.

## Change summary

Make the editor's "Follow link" hover clickable when a DocumentLink provider supplies its target lazily through resolveLink.

## Best solution

Support lazy DocumentLink resolution when producing or displaying the editor link hover, while preserving deferred resolution, cancellation, command-link safety, and existing click behavior. The implementation should live in the core editor link contribution because the Markdown provider cannot work around the missing target without disabling resolveLink.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/links/browser/links.ts`, `src/vs/editor/contrib/links/browser/getLinks.ts`
- **Validation:** Add an editor link test with a LinkProvider that returns a DocumentLink without url and supplies it from resolveLink; hovering must expose a clickable "Follow link" target, resolve only when needed, and retain existing open-link behavior.
- **Behavior:**

  > A DocumentLink whose target is supplied lazily must show the same clickable "Follow link" hover as a link whose target is returned eagerly. Hovering should resolve the target without requiring a keyboard-modified click, and unresolved or failed targets must remain safely non-clickable. Existing eager links, command links, modifier labels, and link-opening behavior must remain unchanged.
- **Trace:**

  > LinkOccurrence._getOptions in src/vs/editor/contrib/links/browser/links.ts synchronously derives hoverMessage through getHoverMessage. That helper emits a clickable Markdown link only when Link.url is already populated; otherwise it emits plain text. Link.resolve in src/vs/editor/contrib/links/browser/getLinks.ts can populate a missing target through LinkProvider.resolveLink, but the editor invokes it from the open path rather than the hover-construction path. Maintainers documented this diagnosis at https://github.com/microsoft/vscode/issues/158996#issuecomment-1239637644, and the Markdown provider workaround was ruled out at https://github.com/microsoft/vscode/issues/158996#issuecomment-1242508505. The boundary is generic DocumentLink hover handling: do not eagerly resolve every document link or alter click/open semantics.
- **Open decisions:**
  - Should lazy resolution begin when the pointer requests the hover, or earlier with a cancellable decoration refresh?
  - How should stale resolution results be discarded when links are recomputed, the model changes, or the hover closes?
  - Which editor hover test harness should cover asynchronous DocumentLink resolution without coupling the core test to Markdown?

## Evidence

- **current source:** In src/vs/editor/contrib/links/browser/links.ts, LinkOccurrence._getOptions synchronously calls getHoverMessage; getHoverMessage only uses MarkdownString.appendLink when link.url is already present and otherwise appends plain text.
- **lazy resolution path:** src/vs/editor/contrib/links/browser/getLinks.ts exposes Link.resolve, which invokes the provider's resolveLink when url is absent, but src/vs/editor/contrib/links/browser/links.ts currently calls it only while opening the occurrence, not while constructing its hover.
- **maintainer diagnosis:** Comments at https://github.com/microsoft/vscode/issues/158996#issuecomment-1232200314 and https://github.com/microsoft/vscode/issues/158996#issuecomment-1239637644 identify the same lazy-target path and state that resolution is needed for hover as well as open.
- **provider workaround ruled out:** https://github.com/microsoft/vscode/issues/158996#issuecomment-1242508505 explains that supplying a fake target from the Markdown language server prevents resolveLink from being called, leaving the core link contribution as the appropriate boundary.
- **canonical status:** https://github.com/microsoft/vscode/issues/173875 and https://github.com/microsoft/vscode/issues/196572 were both closed explicitly as duplicates of this issue, confirming that this remains the canonical report.
