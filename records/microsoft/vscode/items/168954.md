# Issue #168954 — Jupyter: move cell up/down buttons

[https://github.com/microsoft/vscode/issues/168954](https://github.com/microsoft/vscode/issues/168954)

## Summary

Keep open: existing move commands and conditional overflow-menu entries do not provide the requested toolbar buttons. Maintainers have supported optional buttons, and this issue already owns the work consolidated from the earlier discoverability report.

## Change summary

Provide mouse-accessible notebook cell move-up/down buttons, with an additional request for a toolbar action that executes a cell and advances to the next.

## Best solution

Provide optional move-up/down controls through core notebook toolbar customization without crowding the default toolbar or disabling drag-and-drop. Decide separately whether the execute-and-advance action should also be available in the notebook's main toolbar.

## Plan brief

- **Validation:** In a notebook containing several code and Markdown cells with tall outputs, enable the agreed optional controls and click move up/down repeatedly; verify the intended cell moves one position per click, retains its contents and outputs, supports undo, and respects document boundaries and read-only notebooks. Verify drag-and-drop remains usable and the default toolbar is unchanged. If execute-and-advance is included, three clicks must execute three successive cells.
- **Behavior:**

  > Users should be able to opt into directly clickable move-up/down notebook controls rather than relying on dragging tall cells or invoking keyboard commands. Reordering should preserve cell contents, outputs, selection, and undo behavior, with sensible handling at notebook boundaries. The default toolbar should remain uncluttered. The report also requests a main-toolbar action whose repeated clicks execute successive cells; its inclusion needs a scope decision.
- **Trace:**

  > The local CellTitleToolbarPart builds its actions from NotebookCellTitle, and getCellToolbarActions in src/vs/workbench/contrib/notebook/browser/view/cellParts/cellToolbars.ts puts only inline groups in the primary toolbar. Current upstream cellCommands.ts registers notebook.cell.moveUp/down in an overflow group and only when notebook.dragAndDropEnabled is false; both delegate to moveCellRange in controller/cellOperations.ts. The existing toolbar placement/visibility settings do not expose arbitrary command selection. ExecuteCellSelectBelow in controller/executeActions.ts already provides execute-and-advance behavior but has no toolbar menu contribution. The earlier discoverability issue was explicitly consolidated into this request: https://github.com/microsoft/vscode/issues/127524#issuecomment-1347777160. Preserve existing movement, keyboard, execution, and drag-and-drop semantics; the remaining uncertainty is the user-facing customization contract and the additional main-toolbar scope.
- **Open decisions:**
  - Should optional move buttons be exposed through general notebook toolbar command customization or a dedicated notebook option?
  - Should this work also include the requested main-toolbar execute-and-advance button, or should that interaction be tracked separately?

## Evidence

- **Existing capability and remaining gap:** Current upstream src/vs/workbench/contrib/notebook/browser/contrib/cellCommands/cellCommands.ts registers notebook.cell.moveUp and notebook.cell.moveDown in MenuId.NotebookCellTitle only when config.notebook.dragAndDropEnabled is false, using CellOverflowToolbarGroups.Edit. The local src/vs/workbench/contrib/notebook/browser/view/cellParts/cellToolbars.ts:272-274 treats only groups beginning with inline as primary toolbar actions. These conditional overflow entries are not the requested directly clickable toolbar buttons.
