# Issue #77215 — Git - Support for gitdir

[https://github.com/microsoft/vscode/issues/77215](https://github.com/microsoft/vscode/issues/77215)

## Summary

Keep open: current Git discovery and repository identity do not support independently selecting multiple Git directories for the same working folder. The request has 33 upvotes, and neither ordinary worktree support nor the linked untracked-files request covers its central ask.

## Change summary

Support workspace-configured nonstandard Git directories, including multiple independent repositories sharing one working folder, with correct SCM paths and reload behavior.

## Best solution

Provide explicit repository selection scoped to the workspace without requiring process-wide Git environment overrides. First settle how overlapping repositories participate in file-based commands and gutter decorations, then preserve repository identity across discovery, SCM operations, and reloads.

## Plan brief

- **Likely files:** `extensions/git/package.json`, `extensions/git/src/model.ts`, `extensions/git/src/git.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/decorationProvider.ts`
- **Validation:** In a disposable fixture outside the read-only checkout, create two independent Git directories sharing one working folder, with different tracked-file sets. Verify that both SCM providers survive reload, each shows its own status, changed-file clicks resolve to the actual working folder, and staging through either provider affects only its index. Check file-based commands and gutters against the chosen overlap policy, and confirm ordinary repositories and linked worktrees remain unchanged.
- **Behavior:**

  > A workspace can select a nonstandard Git directory without changing the Git environment inherited by unrelated repositories or terminals. The reported workflow also requires two independent repositories over the same working folder to appear separately in Source Control and remain available after reload. Each provider must show changes and open files relative to its actual working tree, and explicit provider actions must operate on the selected repository. Acceptance includes a file tracked only by the secondary repository and a file tracked by both; gutter and file-command behavior for those cases must follow a maintainer-approved policy.
- **Trace:**

  > Git.getRepositoryRoot in extensions/git/src/git.ts discovers a working root using rev-parse --show-toplevel. Model.openRepository and getRepositoryExact in extensions/git/src/model.ts deduplicate by that root or its real path, so two Git directories over one working folder cannot retain separate identities through the current opening path. Repository.exec runs commands from repositoryRoot, while Git.spawn inherits process-level Git variables rather than selecting a configured repository per operation. Model.getOpenRepository resolves file URIs by folder containment, and Git decoration lookup relies on that resolution. Existing git.scanRepositories and git.detectWorktrees handle discovery, not independent Git-directory selection. Preserve ordinary repository and linked-worktree behavior and avoid promising compatibility changes in third-party extensions. The uncertainty is the public configuration contract and the user-visible policy for files belonging to overlapping repositories; https://github.com/microsoft/vscode/issues/249351 is a separate untracked-files request, not the implementation target.
- **Open decisions:**
  - What workspace configuration contract should select Git directories and associate them with working trees, including multiple repositories sharing one working folder?
  - When a file belongs to multiple configured repositories, which repository should file-based commands and gutter decorations use, and how should users select or distinguish that context?
