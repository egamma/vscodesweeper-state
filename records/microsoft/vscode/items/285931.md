# Issue #285931 — Workbench hover appears when focused after quick pick closes

[https://github.com/microsoft/vscode/issues/285931](https://github.com/microsoft/vscode/issues/285931)

## Summary

The lifecycle defect remains on current main: QuickInput restores focus to the invoking status bar item, and the managed-hover focus listener interprets that programmatic focus as a reason to show its tooltip. The issue should remain open because the related fix attempt was closed without merging and current source still contains the failing path.

## Change summary

Closing a QuickPick restores focus to its invoking status bar item and unintentionally opens that item's workbench hover.

## Best solution

Preserve QuickInput's accessible focus restoration while preventing that programmatic restoration from triggering managed hovers; genuine keyboard focus must continue to show hovers for accessibility.

## Plan brief

- **Likely files:** `src/vs/platform/quickinput/browser/quickInputController.ts`, `src/vs/platform/hover/browser/hoverService.ts`, `src/vs/platform/hover/test/browser/hoverService.test.ts`, `src/vs/platform/quickinput/test/browser/quickinput.test.ts`
- **Validation:** Add a browser unit regression that focuses a managed-hover target, opens and closes QuickInput, and verifies that focus returns without a hover appearing after the configured delay; also verify that ordinary keyboard focus still shows the hover.
- **Behavior:**

  > After a status bar item opens a QuickPick, completing or dismissing the QuickPick returns focus to the invoking item without opening its tooltip. Keyboard navigation that deliberately focuses the item must continue to expose its hover for accessibility. The same distinction should hold for other managed-hover targets, including the Debug view's Start Debugging item.
- **Trace:**

  > QuickInputController in src/vs/platform/quickinput/browser/quickInputController.ts stores previousFocusElement when focus enters QuickInput and restores it with HTMLElement.focus() after onHide fires. HoverService.setupManagedHover in src/vs/platform/hover/browser/hoverService.ts captures the resulting focus event and schedules a hover because the QuickInput element is a normal non-null relatedTarget. StatusbarEntryItem in src/vs/workbench/browser/parts/statusbar/statusbarItem.ts attaches that managed hover to the status bar container. The closed attempt at https://github.com/microsoft/vscode/pull/285953 suppressed all workbench hovers only while QuickInput was visible, which is both broader than the reported case and ends before focus restoration. Preserve QuickInput focus restoration and keyboard-triggered hover behavior; do not globally disable hovers during QuickInput interactions.

## Evidence

- **source trace:** On current main, QuickInputController records the previously focused element and, after firing onHide, calls currentElement.focus() in src/vs/platform/quickinput/browser/quickInputController.ts. HoverService.setupManagedHover in src/vs/platform/hover/browser/hoverService.ts listens for that focus event and schedules a hover whenever relatedTarget is neither null nor inside .monaco-hover.
- **status bar path:** src/vs/workbench/browser/parts/statusbar/statusbarItem.ts installs a managed hover on the status bar entry container, so restored focus on its label is captured by the container's managed-hover listener.
- **maintainer confirmation:** https://github.com/microsoft/vscode/issues/285931#issuecomment-3711201156 confirms that focus is intentionally restored for accessibility and that the restored focus triggers the hover; it also notes the same symptom in the Debug view.
- **closed fix attempt:** https://github.com/microsoft/vscode/pull/285953 proposed globally suppressing workbench hovers while QuickInput was visible but was closed without merging. Its approach also tracked onHide before QuickInputController restores focus, so the suppression flag would already be cleared when the problematic focus event occurs.
- **no later fix:** Current WorkbenchHoverDelegate in src/vs/platform/hover/browser/hover.ts has no QuickInput-aware suppression, and the later hover lifecycle guards only exclude focus returning from .monaco-hover or window reactivation, not focus restored from QuickInput.
