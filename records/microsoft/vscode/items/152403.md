# Issue #152403 — Open source translations of third-party vs code OSS extensions

[https://github.com/microsoft/vscode/issues/152403](https://github.com/microsoft/vscode/issues/152403)

## Summary

Keep open: public localization tooling and VS Code language packs do not establish that translations for separately built OSS extensions such as Python are available for source builds. The localization owner explicitly welcomed this request; no verified fix or matching canonical issue was found.

## Change summary

Make the localization pipeline or translation files publicly available so OSS extensions can be built from source with translations enabled.

## Best solution

Provide a documented, publicly accessible and appropriately licensed source of version-matched translation resources for the affected OSS extensions. Publishing those resources could satisfy the request without opening the shared localization service or exposing resources for closed-source extensions.

## Plan brief

- **Likely files:** `build/lib/i18n.ts`, `build/npm/update-localization-extension.ts`
- **Validation:** The plan should end with an executable clean-source packaging check for an affected OSS extension such as Python: obtain translations exclusively from documented public inputs, build its VSIX with localization enabled, and verify a supported non-English locale displays translated manifest and runtime strings without missing-bundle errors.
- **Behavior:**

  > Developers building an affected OSS extension from source can include its translations using documented public inputs, without access to an internal localization service. Turning translations off is not acceptance. Validate that an agreed extension version can be packaged with matching translation resources and displays translated manifest and runtime strings in a supported non-English locale. Resources belonging to closed-source extensions are outside this request.
- **Trace:**

  > The linked discussion establishes that Python translation files were injected by an internal build stage rather than supplied by a normal source checkout; the localization owner explicitly welcomed this request at https://github.com/microsoft/vscode-python/issues/19280#issuecomment-1158181199. Current build/lib/i18n.ts provides public translation conversion, including prepareI18nPackFiles, and build/npm/update-localization-extension.ts consumes externally supplied translation directories. Public microsoft/vscode-loc resources inspected here cover built-in extensions and JavaScript debugging, not the ms-python.python translation inputs central to the report. This establishes a distinction between available processing tooling and available translated resources, but does not trace the current Python packaging pipeline end to end. The planning session must establish the publication and version-matching contract with the localization owner; keep closed-source resources and changes to translation-disabled build behavior outside the boundary.
- **Open decisions:**
  - What public artifact contract will support localized source builds: version-matched translation snapshots, resources published alongside extension releases, or a publicly reproducible pipeline, and which OSS extensions and locales will that contract cover?

## Evidence

- **Requested scope:** https://github.com/microsoft/vscode/issues/152403 requests either an open localization pipeline or the necessary translation files, specifically so source-built OSS extensions retain translations. Disabling translations does not satisfy that requirement.
- **Maintainer interest and correct ownership:** In https://github.com/microsoft/vscode-python/issues/19280#issuecomment-1158181199, the extension localization pipeline owner invited an issue in microsoft/vscode, expressed openness to publishing translations for OSS extensions, and explained that the shared pipeline also contains closed-source extensions. This is a platform publication request, not a Python-specific issue to transfer.
- **Historical workaround is incomplete:** https://github.com/microsoft/vscode-python/issues/19280#issuecomment-1154220637 recommends DISABLE_TRANSLATIONS for source builds, and https://github.com/microsoft/vscode-python/issues/19280#issuecomment-1154243861 confirms it works. That avoids missing-bundle errors by removing localization rather than making translated builds possible.
- **Existing public capability:** Current build/lib/i18n.ts exposes XLIFF conversion through prepareI18nPackFiles and uses @vscode/l10n-dev. build/npm/update-localization-extension.ts imports supplied XLIFF files through location and externalExtensionsLocation. These are public processing tools, but they require translation inputs; they do not themselves publish the requested extension resources.

Its inspected German extension-resource directory contains built-in vscode.python.i18n.json and ms-vscode.js-debug.i18n.json, but not ms-python.python resources. The built-in Python language contribution is not the separately distributed Python extension named in this request.
