# Issue #163457 — Add workspace folder path to context keys.

[https://github.com/microsoft/vscode/issues/163457](https://github.com/microsoft/vscode/issues/163457)

## Summary

Keep this accepted feature request open: current resource context keys do not expose the containing workspace folder for a right-clicked root or descendant. It has 34 upvotes, and the canonical search found no verified older open issue owning this request.

## Change summary

Expose the containing workspace folder's identity in context keys so extensions can conditionally show Explorer commands for supported projects and their descendants.

## Best solution

Provide a resource-scoped workspace-folder context usable with an extension's setContext collection and the in operator. Settle its path-versus-URI contract, including remote and virtual workspaces, before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/common/contextkeys.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/platform/workspace/common/workspace.ts`
- **Validation:** In a two-root workspace, contribute an explorer/context command using the agreed workspace-folder key in a setContext collection containing only one root. Verify visibility on that root and its nested folders/files, absence on the other root and its descendants, and correct updates after workspace-folder changes. Add focused automated context tests for those membership cases and the agreed remote/virtual identity representation.
- **Behavior:**

  > An extension can identify supported workspace folders and show an Explorer context-menu command on those roots and every contained folder or file. The same command remains hidden for unsupported workspace folders and their descendants. Acceptance must cover multiple roots and nested resources without requiring the extension to enumerate every descendant. The exposed identity must have a documented representation suitable for setContext collection membership.
- **Trace:**

  > AbstractResourceContextKey in src/vs/workbench/common/contextkeys.ts exposes the selected resource's path, immediate parent path and URI, but not its containing workspace folder. ExplorerView.setContextKeys and onContextMenu in src/vs/workbench/contrib/files/browser/views/explorerView.ts update resource contexts before showing MenuId.ExplorerContext; explorerResourceIsRoot supplies only a boolean. IWorkspaceContextService.getWorkspaceFolder(resource) in src/vs/platform/workspace/common/workspace.ts already provides the relevant lookup. Preserve existing resource-key semantics and keep project detection in the extension; the requested boundary is Explorer menu visibility, not new project classification machinery. The unresolved contract is the folder identity representation, especially for remote and virtual resources. Related https://github.com/microsoft/vscode/issues/249352 confirms additional demand but was closed through the community process rather than fixed.
- **Open decisions:**
  - Should the exposed workspace-folder identity use resourcePath-style paths or full URI strings including scheme and authority, and what representation should remote and virtual folders use?
