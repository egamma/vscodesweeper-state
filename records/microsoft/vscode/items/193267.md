# Issue #193267 — Aux window: allow detaching views and panels

[https://github.com/microsoft/vscode/issues/193267](https://github.com/microsoft/vscode/issues/193267)

## Summary

Keep this accepted, well-supported request open: current auxiliary windows support editor-backed terminals and Chat, but not general view or panel detachment. The existing multi-monitor workaround only partially covers the request, and this issue already serves as the canonical destination for detached-panel reports.

## Change summary

Allow views and bottom-panel contents to detach into auxiliary windows on another monitor while remaining connected to the originating workbench.

## Best solution

Provide supported auxiliary-window hosting for ordinary workbench views or panel containers, preserving their workspace connection and predictable file-opening behavior. Establish the detachment unit and editor-navigation contract before extending the shared view and window infrastructure.

## Plan brief

- **Likely files:** `src/vs/workbench/common/views.ts`, `src/vs/workbench/services/views/browser/viewsService.ts`, `src/vs/workbench/browser/parts/views/viewPaneContainer.ts`, `src/vs/workbench/browser/parts/panel/panelPart.ts`, `src/vs/workbench/browser/parts/editor/auxiliaryEditorPart.ts`, `src/vs/workbench/services/auxiliaryWindow/browser/auxiliaryWindowService.ts`
- **Validation:** The plan should define a runnable two-monitor acceptance scenario: detach Problems and another ordinary panel view without opening a second workspace, interact with both, activate a file link and confirm the agreed editor destination, then redock or close the auxiliary window without losing view state or terminating an unrelated terminal. Confirm existing terminal and Chat new-window commands remain functional.
- **Behavior:**

  > Users want panel contents on a secondary monitor while retaining the originating workspace and their code-editing window. Terminal-specific editor windows and moving the editors instead are partial alternatives, not support for general panel detachment. Acceptance must include an ordinary view such as Problems, continued interaction with the original workspace, and file navigation to the agreed editing destination. Detachment granularity and auxiliary-window close behavior must be established before implementation.
- **Trace:**

  > ViewContainerLocation in src/vs/workbench/common/views.ts models only Sidebar, Panel, and AuxiliaryBar; AuxiliaryBar is an in-workbench location, not an OS window. AuxiliaryEditorPart.create in src/vs/workbench/browser/parts/editor/auxiliaryEditorPart.ts hosts editors with a scoped IEditorService and window chrome. TerminalService.moveIntoNewEditor uses AUX_WINDOW_GROUP, and chatMoveActions.ts similarly opens ChatEditorInput sessions rather than rehosting arbitrary views. General views run through viewsService.ts and viewPaneContainer.ts, with panel hosting in panelPart.ts; the trace establishes the missing general host but does not enumerate all lifecycle, persistence, and extension-view consumers. Preserve existing editor, terminal, and Chat window behavior and do not turn this into the standalone-terminal request at https://github.com/microsoft/vscode/issues/34442. https://github.com/microsoft/vscode/issues/231357 already consolidates detached-panel demand here.
- **Open decisions:**
  - Should the initial supported unit of detachment be an individual view, a view container, the entire bottom panel, or more than one of these?
  - Should file links activated in a detached view target the originating main-window editor or the last active editor group across the connected windows?
  - When an auxiliary view window closes, should its contents automatically redock, or remain hidden until explicitly reopened?
