# Issue #336775 — Terminal auto-approve ignored for operators inside a colon-attached quoted arg

[https://github.com/microsoft/vscode/issues/336775](https://github.com/microsoft/vscode/issues/336775)

## Summary

Well-documented, plausible PowerShell tree-sitter parsing gap: the existing pwsh grammar workaround in this exact file only masks `-flag=value`/`--flag=value` forms, not the `/Flag:"value"` colon-attached style the reporter hit, so this is a real, currently-unhandled edge case rather than something to close.

## Change summary

For PowerShell commands, a shell operator (e.g. `|`) inside a colon-attached quoted argument like `/Filter:"a|b"` is not recognized as safely quoted, so matching `matchCommandLine` auto-approve rules are ignored even though the same operator inside a space-separated quoted arg (`"a|b"`) auto-approves fine.

## Best solution

Extend (or generalize) the existing `pwshFlagEqualsRegex`/`maskPwshFlagEquals` workaround in treeSitterCommandParser.ts to also mask colon-attached value syntax (`/Flag:"..."`, `-Flag:"..."`) before the tree-sitter PowerShell grammar parses it, mirroring the fix already applied for the equals-attached case (see the linked #294010 precedent) — or track it for an upstream tree-sitter-powershell grammar fix if that's preferred over adding another masking regex.

- **Behavior:**

  > For PowerShell command lines, a shell operator character (`|`, `&`, `;`, parens, `&&`, `||`, braces) that appears inside a quoted value attached directly after a colon (e.g. `/Filter:"a|b"`, `-Property:"x&y"`) must be treated the same as when it appears inside a space-separated quoted argument (e.g. `"a|b"`): the auto-approve command-line matcher should see one command, not a split at the operator. Acceptance: `chat.tools.terminal.autoApprove` rules with `matchCommandLine: true` auto-approve commands containing colon-attached quoted operators exactly as they already do for space-separated quoted operators.
- **Trace:**

  > CommandLineAutoApproveAnalyzer.analyze() (src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/tools/commandLineAnalyzer/commandLineAutoApproveAnalyzer.ts) relies on TreeSitterCommandParser.extractAutoApprovalSubCommands() (src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/treeSitterCommandParser.ts, line 75) to split the command line into `(command)` nodes via the tree-sitter PowerShell grammar; if the grammar mis-splits at the operator, either subCommands ends up wrong or hasUnanalyzableSyntax forces isAutoApproved=false regardless of the matchCommandLine rule. The file already works around one instance of this grammar limitation for `-flag=value` forms via pwshFlagEqualsRegex/maskPwshFlagEquals (lines 28-45, citing https://github.com/microsoft/vscode/issues/294010), but that regex only matches `-`/`--`-prefixed, equals-terminated flags — it does not cover the reporter's colon-attached `/Flag:"..."` form. The boundary: do not touch the bash grammar path or the equals-masking behavior for existing `-flag=value` cases; only extend (or add a parallel) masking path for colon-attached quoted values, or otherwise avoid the grammar's premature operator recognition inside that quoted span.
- **Open decisions:**
  - Extend the existing equals-masking regex to also cover colon-attached forms (`/Flag:"..."`, `-Flag:"..."`), or wait for/pursue an upstream tree-sitter-powershell grammar fix as the TODO comment in the file suggests?
  - How to scope a colon-masking regex narrowly enough to avoid false positives on legitimate PowerShell colon usages (drive letters like `C:\`, scope-qualified variables like `$env:PATH`, ternary/hashtable colons) that must keep parsing normally?
  - Should masking apply only when the colon is immediately followed by a quote character (minimizing risk), or more broadly to any colon-attached flag value?

## Evidence

- **existing precedent workaround:** src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/treeSitterCommandParser.ts lines 28-45 already document and mask an almost identical tree-sitter-powershell grammar limitation for POSIX-style `--flag=value` args (comment references https://github.com/microsoft/vscode/issues/294010), confirming this class of colon/equals-attached-value parsing bug is real and previously hit core auto-approve.
- **gap in current mask:** pwshFlagEqualsRegex = /(^|\s)(-{1,2}[\w-]+)=/g only matches `-`/`--`-prefixed flags ending in `=`; it does not match `/Flag:` (single-slash prefix, colon separator) as used in the reporter's `Write-Output /Filter:"a|b"` example, so the exact scenario reported is not covered by the existing mitigation.
- **no test coverage:** No test in src/vs/workbench/contrib/terminalContrib/chatAgentTools/test/electron-browser/treeSitterCommandParser.test.ts exercises colon-attached quoted args (`/Filter:"..."`), so this gap is not currently guarded against by the test suite.
