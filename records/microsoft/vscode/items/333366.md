# Issue #333366 — macOS system Pinyin English candidate moves the caret and corrupts adjacent text

[https://github.com/microsoft/vscode/issues/333366](https://github.com/microsoft/vscode/issues/333366)

## Summary

Real, still-open bug: macOS Pinyin English-candidate insertion corrupts adjacent text via the native EditContext path. A fix was proposed in PR #333365 (author reports it resolves the repro with tests) but was closed unmerged for reviewer bandwidth, not rejected on correctness — and a second, independent reporter reconfirmed the same symptom with a different trigger word on 2026-09-21.

## Change summary

Selecting an English candidate from macOS's built-in Pinyin IME moves the caret over adjacent existing text and, on commit, deletes/corrupts that text instead of inserting the candidate at the original caret position.

## Best solution

Revive and review the closed PR https://github.com/microsoft/vscode/pull/333365 (or a similar fix) that keeps the native EditContext's cached text synchronized before the model content listener runs and ignores composition-only selection excursions during a pending candidate, in src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts.

- **Behavior:**

  > While a macOS Pinyin English candidate is pending (e.g. typing `revie`+`w` or `active` with the caret initially before existing text like `1234`), the editor caret must visually appear to move for the candidate preview, but the underlying model caret and adjacent text must not be altered until the candidate is actually committed. Committing the candidate (Return) must insert the candidate text at the original caret position and leave all adjacent text intact (`review1234`, not `revieww234`).
- **Trace:**

  > nativeEditContext.ts's 'textupdate' listener (around lines 197-220) and the 'compositionend'/'_updateEditContext' path do not distinguish a composition-only temporary selection excursion (sent by the OS while an English candidate is highlighted) from a real model caret move; per PR #333365's root-cause analysis, Chromium updates the native EditContext state before dispatching 'textupdate', and the editor's own model content listener then writes back using stale cached EditContext text, duplicating trailing content and causing the final commit to consume/reinsert adjacent characters. The fix boundary is this synchronization + composition-selection handling inside nativeEditContext.ts; it must not change non-IME typing or paste paths. Where the uncertainty starts: whether the specific synchronization strategy in the closed PR (resync cached EditContext text before listeners run, ignore composition-only selection excursions) is the correct fix or needs redesign — no maintainer reviewed it before the PR was closed for bandwidth, not on correctness grounds. See https://github.com/microsoft/vscode/pull/333365 for the proposed diff and manual before/after recordings.
- **Open decisions:**
  - Is the synchronization approach in the closed PR #333365 (resync EditContext text before model listeners run; ignore composition-only selection excursions) the right fix, or does it need a different strategy to avoid regressing other EditContext/IME flows (e.g. Japanese/Korean IMEs, other browsers)?
