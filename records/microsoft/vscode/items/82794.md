# Issue #82794 — Provision trusted domains for enterprise setup

[https://github.com/microsoft/vscode/issues/82794](https://github.com/microsoft/vscode/issues/82794)

## Summary

A supported enterprise provisioning path is still missing on current main. The issue is accepted in the Backlog, has recent enterprise demand, and needs a policy design that preserves link protection rather than a cleanup close.

## Change summary

Allow enterprise administrators to preconfigure trusted link domains so users do not repeatedly approve the same organizational domains.

## Best solution

Provide a supported managed configuration for trusted domains that the trusted-domain service consumes alongside user choices, with explicit semantics for whether administrators supply additive defaults or enforce the complete list.

- **Fit:** aligned
- **Reason:** Managed trusted domains improve settings fidelity for enterprise deployments while preserving the security boundary around external-link prompts.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/url/browser/url.contribution.ts`, `src/vs/workbench/contrib/url/browser/trustedDomains.ts`, `src/vs/workbench/contrib/url/browser/trustedDomainService.ts`, `src/vs/workbench/contrib/url/test/browser/trustedDomains.test.ts`
- **Validation:** Add trusted-domain service tests showing that administrator-provisioned domains are trusted without prompting and that non-provisioned domains still prompt; run the targeted Trusted Domains unit-test suite.
- **Behavior:**

  > Enterprise administrators can provision trusted domains through a supported managed configuration, and links matching those domains open without repeated trust prompts. Domains outside the provisioned and user-approved sets remain protected. The selected policy semantics must behave consistently across restarts and disposable remote environments.
- **Trace:**

  > The link-validation path reaches TrustedDomainService in src/vs/workbench/contrib/url/browser/trustedDomainService.ts, which obtains its list through readStaticTrustedDomains in src/vs/workbench/contrib/url/browser/trustedDomains.ts. That function currently combines product metadata, browser embedder options, and user application storage; no managed configuration source is consulted. url.contribution.ts registers only workbench.trustedDomains.promptInTrustedWorkspace, not a domain-list policy. Ordinary user settings were rejected in https://github.com/microsoft/vscode/issues/81841 because extensions can modify them, while a maintainer later proposed the group-policy direction in https://github.com/microsoft/vscode/issues/82794#issuecomment-1139897136. Preserve the existing user-managed Trusted Domains editor and prompting behavior for domains not covered by policy.
- **Open decisions:**
  - Should the managed domain list be additive, allowing users to trust further domains, or should administrators be able to enforce the complete trusted-domain set?
  - Which supported enterprise deployment contract must expose the list: configuration policy alone, or policy plus a non-interactive command-line provisioning surface?

## Evidence

- **current source gap:** src/vs/workbench/contrib/url/browser/trustedDomains.ts readStaticTrustedDomains reads productService.linkProtectionTrustedDomains, browser embedder options.additionalTrustedDomains, and per-user application storage, but it does not read a managed configuration or enterprise policy.
- **existing capabilities are incomplete:** src/vs/base/common/product.ts exposes linkProtectionTrustedDomains as product metadata, while src/vs/workbench/browser/web.api.ts exposes additionalTrustedDomains to web embedders; neither is a supported administrator-facing provisioning mechanism for standard desktop deployments.
- **maintainer direction:** A maintainer explicitly suggested making the list configurable through group policy in https://github.com/microsoft/vscode/issues/82794#issuecomment-1139897136.
- **continuing demand:** The enterprise remote-development scenario and repeated prompts were described in https://github.com/microsoft/vscode/issues/82794#issuecomment-3114339900, showing that the original gap remains relevant.
- **related decision:** https://github.com/microsoft/vscode/issues/81841 rejected ordinary settings because extensions could modify them; that does not settle this issue's distinct request for an administrator-controlled policy.
- **canonical search:** The open trusted-domain search found no older issue with the same enterprise-provisioning request; https://github.com/microsoft/vscode/issues/80595 is closed and explicitly directed this remaining scenario to the issue under review.
