# Issue #169821 — VS Code is still adding `/d /c` to task commands

[https://github.com/microsoft/vscode/issues/169821](https://github.com/microsoft/vscode/issues/169821)

## Summary

Keep open: current main still appends cmd-specific arguments to unrecognized Windows automation shells, including the latest reported extensionless `pwsh` configuration. Nushell support addressed one case, but the broader fix was reverted and the remaining defect is directly traceable in source.

## Change summary

Windows tasks add inappropriate `/d /c` arguments to custom automation shells, breaking execution unless each task overrides its shell configuration.

## Best solution

Make task launch arguments appropriate for the selected automation shell without requiring shared tasks.json overrides. Settle how explicit automation-profile arguments interact with inferred execution flags, while preserving existing task-shell overrides, command quoting, and empty-command terminal tasks.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts`, `src/vs/workbench/contrib/terminal/browser/terminalProfileResolverService.ts`
- **Validation:** On Windows, run the supplied `mvn -v` shell task with automationProfile.windows set to `path: "pwsh", args: []`; it must execute without `/d /c`. Exercise an MSYS2 launcher with its configured initialization arguments and a simple echo task, plus Nushell with `args: ["-c"]`. Check generated launch arguments and successful execution. Preserve explicit task-shell overrides, the prequoted cmd.exe command scenario from https://github.com/microsoft/vscode/issues/260534, and the empty-command PowerShell startup scenario from https://github.com/microsoft/vscode/issues/261459. The plan should establish automated launch-configuration coverage for these cases.
- **Behavior:**

  > A Windows shell task should execute using the user's automation profile without injecting arguments belonging to a different shell. The latest concrete failure is an automation profile with `path: "pwsh", args: []`, where an ordinary `mvn -v` task receives `/d /c`; MSYS2 launcher configurations expose the same inappropriate fallback. Users must not need task-level shell overrides to make their personal automation shell usable. Existing explicit task-shell configurations, correctly working Nushell tasks, command quoting, and empty-command terminal startup must remain compatible.
- **Trace:**

  > BaseTerminalProfileResolverService.getDefaultProfile in src/vs/workbench/contrib/terminal/browser/terminalProfileResolverService.ts returns the configured automation executable and arguments; its resolution does not normalize `pwsh` to `pwsh.exe`. TerminalTaskSystem._createShellLaunchConfig in src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts copies that profile, but shellSpecified tracks only a task-level executable override. Its Windows dispatch recognizes a small set of `.exe` basenames and otherwise appends `/d /c`, conclusively explaining both extensionless PowerShell and MSYS2-wrapper failures. _addAllArgument merges configured and inferred flags, while _buildShellCommandLine independently handles quoting and preserves raw string commands. https://github.com/microsoft/vscode/pull/238440 covers only Nushell; https://github.com/microsoft/vscode/pull/261565 reverted the broader attempt because of the quoting and empty-command regressions documented in https://github.com/microsoft/vscode/issues/260534 and https://github.com/microsoft/vscode/issues/261459. The unresolved boundary is the observable argument-inference contract for explicit automation profiles, not whether non-cmd shells should receive cmd-specific flags.
- **Open decisions:**
  - When automationProfile.args is explicitly provided, including an empty array, does it define the complete shell argument list before the task command, or should VS Code still infer a missing execution flag for recognized shells? What should an unrecognized wrapper receive when args is omitted?

## Evidence

- **Current source confirms the latest reproduction:** src/vs/workbench/contrib/terminal/browser/terminalProfileResolverService.ts:getDefaultProfile, _getUnresolvedAutomationShellProfile, and _resolveProfile preserve the configured `pwsh` executable name without adding `.exe`. In src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts:1228–1327, the automation profile supplies executable and args, but shellSpecified becomes true only for a task-level shell executable. Windows recognition checks `pwsh.exe`, not `pwsh`; the fallback therefore appends `/d /c` to the supplied `path: "pwsh", args: []` before the task command.
- **Wrapper-shell reports remain covered by the same faulty fallback:** The March and April 2023 comments describe MSYS2 launcher failures with `/d /c` injected after their configured arguments. Current _createShellLaunchConfig likewise sends `msys2_shell.cmd` through the unrecognized-shell fallback. The task-level options.shell workaround bypasses that inference, but requires editing shared tasks and does not deliver the requested user-level automation configuration.
- **Partial fix is not completion:** https://github.com/microsoft/vscode/pull/238440 explicitly describes a Nushell-specific fix. Current terminalTaskSystem.ts:1294–1297 recognizes `nu.exe` and supplies `-c`, but this does not address MSYS2 wrappers or extensionless `pwsh`.
- **Broader fix was reverted:** https://github.com/microsoft/vscode/pull/251201 changed argument defaults and MSYS2 handling, but https://github.com/microsoft/vscode/pull/261565 reverted commit c758ad40aa76933d0cc44d3bac241db8430f5093 and explicitly returned to this issue. The revert cites https://github.com/microsoft/vscode/issues/260534 for double-wrapped command quotes and https://github.com/microsoft/vscode/issues/261459 for empty-command PowerShell startup failures; these are compatibility boundaries for another attempt.
- **Reopened issue and subsequent confirmation:** https://github.com/microsoft/vscode/issues/169821 is reopened. The supplied July 30, 2026 comment reports the failure in 1.130.0 with complete settings.json and tasks.json examples, and current source corroborates that specific path. Earlier merged attempts https://github.com/microsoft/vscode/pull/181760 and https://github.com/microsoft/vscode/pull/236058 do not establish completion.
- **Canonical and active-fix search:** https://github.com/microsoft/vscode/issues/93437 is closed and originally concerns local-to-remote Windows tasks, so it cannot serve as an open duplicate canonical. Searches for automation-profile task arguments and shell-argument reports did not identify an older open issue owning this same symptom. https://github.com/microsoft/vscode/pull/251239 is closed, and an open-PR search for 169821 returned no active implementation candidate.
