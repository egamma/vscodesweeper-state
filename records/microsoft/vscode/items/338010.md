# Issue #338010 — New Session from Pull Request cannot find draft pull requests

[https://github.com/microsoft/vscode/issues/338010](https://github.com/microsoft/vscode/issues/338010)

## Summary

Traced a real gap in the New Session from Pull Request picker: pasting a full github.com PR URL never matches any pull request (draft or not), because the search matcher only checks `#number title author`, not URL parsing — this plausibly explains the reported symptom even though it isn't actually draft-specific.

## Change summary

Pasting a draft pull request's URL into 'New Session from Pull Request' doesn't find/list it, so a session can't be created from it.

## Best solution

Make `pullRequestMatchesQuery` in pullRequestPicker.ts recognize a pasted canonical PR URL (via the existing `parseGitHubPullRequestUrl` helper in common/utils.ts) and match by extracted number, so both draft and ready PRs are found the same way whether searched by number, title, or pasted URL.

- **Behavior:**

  > Pasting a canonical github.com pull request URL (e.g. https://github.com/microsoft/vscode/pull/337791) into the 'New Session from Pull Request' search box should surface that pull request in the list, the same way searching by number or title already does — for both draft and ready-for-review PRs. Non-URL queries (number/title/author substrings) keep working exactly as today.
- **Trace:**

  > pullRequestMatchesQuery in src/vs/sessions/contrib/github/browser/pullRequestPicker.ts builds the haystack as `#{number} {title} {author}`.toLowerCase() and does a plain substring check — a full URL query is never a substring of that, so createSessionFromPullRequestAction.ts's loadUntilMatch() keeps paging without ever matching, producing the reported 'not found' result regardless of draft state (the fetch/filter pipeline itself does not exclude drafts — see githubPullRequestsFetcher.ts's `states: OPEN` query and pullRequestPicker.ts's isPullRequestAvailable, neither of which checks isDraft). common/utils.ts already exports parseGitHubPullRequestUrl(url) for parsing `https://github.com/<owner>/<repo>/pull/<number>`. Boundary: keep existing number/title/author substring matching intact; only add a branch that, when the query parses as a GitHub PR URL, matches by the parsed number (optionally checking owner/repo against the resolved repository). Do not touch the fetch/pagination logic or the draft-icon rendering, which already work correctly.

## Evidence

- **no draft-specific filter:** src/vs/sessions/contrib/github/browser/fetchers/githubPullRequestsFetcher.ts queries `states: OPEN` (drafts included) and never filters on `isDraft`; pullRequestPicker.ts's isPullRequestAvailable() only excludes cross-repo/existing PRs, not drafts; toQuickPickItem() explicitly renders a draft icon, so drafts are meant to be listed.
- **confirmed PR is same-repo, draft, open:** GET https://api.github.com/repos/microsoft/vscode/pulls/337791 returns draft: true, state: open, head.repo.fork: false — not a cross-repository PR, so the isCrossRepository filter doesn't explain the miss.
- **URL matching gap:** pullRequestMatchesQuery() in src/vs/sessions/contrib/github/browser/pullRequestPicker.ts (line ~130) only tests `#{number} {title} {author}`.toLowerCase().includes(query); a pasted URL like https://github.com/microsoft/vscode/pull/337791 will never be a substring of that, so loadUntilMatch() in createSessionFromPullRequestAction.ts paginates forever without a match.
- **existing unused utility:** src/vs/sessions/contrib/github/common/utils.ts already exports parseGitHubPullRequestUrl(url) for exactly this parsing, used elsewhere (sessionGitHubReferences.ts) but not wired into pullRequestPicker.ts's matcher.
- **test coverage gap:** src/vs/sessions/contrib/github/test/browser/pullRequestPicker.test.ts only tests number/title/author substrings for pullRequestMatchesQuery, no URL case.
