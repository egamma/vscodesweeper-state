# Issue #335445 — Agents Window: Allow file references to open in the associated Editor window

[https://github.com/microsoft/vscode/issues/335445](https://github.com/microsoft/vscode/issues/335445)

## Summary

A real Agents Window workflow gap remains: file-reference clicks are handled by the window-local opener, with no setting to route them to a regular Editor window. Route this to the Agents Window area for a window-targeting design decision.

## Change summary

Allow file references clicked in the Agents Window to open in a corresponding regular Editor window, while preserving the current behavior as a configurable option.

## Best solution

Add an Agents Window preference that preserves local opening by default but can route file references, including line selections and editor associations, to an appropriate regular Editor window for the same workspace. Define deterministic behavior for multiple matching windows and for cases where no regular Editor window exists.

- **Behavior:**

  > By default, clicking a file reference in an Agents Window continues to open it inside that window. When the new preference is enabled, clicking a file reference opens or reveals the same resource and line selection in an appropriate regular Editor window associated with the session workspace. Existing editor associations, image handling, keyboard activation, and ordinary Editor-window chat links remain unchanged. Acceptance includes deterministic behavior when several or no suitable Editor windows exist.
- **Trace:**

  > InlineAnchorWidget in src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatInlineAnchorWidget.ts currently resolves every file-reference click through the local IOpenerService. The Sessions ChatWidget is created in src/vs/sessions/contrib/chat/browser/chatView.ts with isSessionsWindow set, but IChatWidgetViewOptions/IChatListItemRendererOptions expose no host-specific resource opener. Sessions already owns regular-window actions in src/vs/sessions/electron-browser/actions/vscodeActions.ts, while main-process workspace matching exists in src/vs/platform/windows/electron-main/windowsMainService.ts and windowsFinder.ts. The boundary is Agents Window file-reference routing: do not change link behavior in ordinary Editor windows, lose selections or editor overrides, or bypass IEditorService for local opening. No older canonical issue or open fixing PR was identified.
- **Open decisions:**
  - When several regular Editor windows can open the resource, should routing select the workspace-matching window, the most recently active matching window, or an explicitly paired window?
  - When no suitable regular Editor window exists, should configured routing fall back to the Agents Window or create a regular Editor window?
