# Issue #334574 — Agent shell tool sandbox fails with "bwrap: setting up uid map: Permission denied"

[https://github.com/microsoft/vscode/issues/334574](https://github.com/microsoft/vscode/issues/334574)

## Summary

Team-authored testing report (TylerLeonhardt, from testing PR #334389) of a real gap in the sandbox dependency check: the code only detects the Ubuntu-style AppArmor restriction on unprivileged user namespaces, not the Debian/RHEL/Arch-style `kernel.unprivileged_userns_clone=0` sysctl a commenter identified as the likely cause here — no fix has landed yet, so this stays open.

## Change summary

Enabling agent shell sandboxing on Linux can fail with `bwrap: setting up uid map: Permission denied` because the current unprivileged-userns detection/repair flow doesn't cover all the kernel hardening variants that block it.

## Best solution

Extend SandboxHelperService._resolveAppArmorRestriction (src/vs/platform/sandbox/node/sandboxHelper.ts) to also read /proc/sys/kernel/unprivileged_userns_clone, and decide with a maintainer what remediation (if any) to offer on distros where that sysctl — not AppArmor — is the blocker, since the existing auto-repair path already discourages SUID-bit-based fixes for security reasons.

## Plan brief

- **Likely files:** `src/vs/platform/sandbox/node/sandboxHelper.ts`, `src/vs/platform/sandbox/common/terminalSandboxEngine.ts`, `src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/tools/runInTerminalTool.ts`
- **Validation:** A sandboxHelper.test.ts case asserting checkSandboxDependencies reports the restriction when /proc/sys/kernel/unprivileged_userns_clone is 0, mirroring the existing AppArmor test.
- **Behavior:**

  > When bwrap fails to start because unprivileged user namespaces are blocked by kernel policy (AppArmor on Ubuntu, or the unprivileged_userns_clone sysctl elsewhere), the sandbox dependency check should detect the actual cause and either offer an appropriate repair path or surface a clear, actionable error instead of the raw bwrap uid-map failure.
- **Trace:**

  > SandboxHelperService.checkSandboxDependenciesWith (src/vs/platform/sandbox/node/sandboxHelper.ts) only probes /proc/sys/kernel/apparmor_restrict_unprivileged_userns via _resolveAppArmorRestriction; it has no equivalent check for kernel.unprivileged_userns_clone, which is the Debian/RHEL/Arch mechanism for the same restriction (per the issue comment). The consuming repair/remediation flow lives in terminalSandboxEngine.ts (~line 340) and runInTerminalTool.ts's repair messaging. Do not change the SUID-based repair path — it is intentionally avoided for security reasons — and do not adopt Landlock or any new sandbox backend as part of this fix; that's a separate, larger design question.
- **Open decisions:**
  - Should VS Code detect and surface the unprivileged_userns_clone sysctl restriction the same way it does AppArmor, or just improve the generic bwrap failure message?
  - If detected, should any automated repair be offered (e.g. guidance to run a sysctl command) given it requires root and is a kernel security policy change, or should this remain informational only?
