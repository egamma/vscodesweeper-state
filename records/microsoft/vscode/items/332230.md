# Issue #332230 — Subprocess environment breaks GDK apps that do not support Wayland

[https://github.com/microsoft/vscode/issues/332230](https://github.com/microsoft/vscode/issues/332230)

## Summary

Plausible, well-diagnosed report: VS Code's source contains no code that sets GDK_BACKEND (only an unrelated snap-packaging script, which doesn't apply to this reporter's RPM install), so the value must come from Electron/Chromium's Wayland/Ozone integration and is then inherited unmodified into terminal/task subprocesses, breaking GDK apps without Wayland support — worth routing to the terminal/platform owners rather than closing on a single fresh report.

## Change summary

Integrated terminal subprocesses inherit a GDK_BACKEND=wayland environment variable (apparently set by Electron/Chromium's own Wayland handling) with no x11 fallback, causing non-Wayland-aware GTK apps launched from the terminal to fail to open a display.

## Best solution

Confirm with the terminal/platform owners whether VS Code should filter or append a fallback (`,x11`) to GDK_BACKEND when building the subprocess environment for terminal/task processes, similar to how removeDangerousEnvVariables strips ELECTRON_RUN_AS_NODE for forked processes (src/vs/base/common/processes.ts), rather than passing the Electron-set value straight through.

## Evidence

- **no core setter found:** `rg GDK_BACKEND src/vs` only matches resources/linux/snap/electron-launch (a snap-packaging launcher script), which is irrelevant to the reporter's RPM-installed build — VS Code's own TypeScript source never sets GDK_BACKEND.
- **env passthrough:** Terminal process environment construction (src/vs/workbench/contrib/terminal/common/terminalEnvironment.ts, src/vs/platform/terminal/node/terminalProcess.ts) merges from process.env without any GDK_BACKEND-specific handling, unlike the explicit ELECTRON_RUN_AS_NODE stripping done via removeDangerousEnvVariables (src/vs/base/common/processes.ts) for forked/utility processes.
- **known upstream behavior:** Electron/Chromium's GTK/Ozone Wayland integration is documented (in Electron/Chromium community discussions) to set GDK_BACKEND for its own GTK dialog rendering, which then leaks into any child process that inherits process.env.
