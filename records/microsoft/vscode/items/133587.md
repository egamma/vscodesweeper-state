# Issue #133587 — Allow pinning hover popovers (datatips)

[https://github.com/microsoft/vscode/issues/133587](https://github.com/microsoft/vscode/issues/133587)

## Summary

Keep this accepted, community-supported request open: current hover settings and focus commands do not preserve documentation while the user continues editing. The verified related pinning request is newer, and an earlier documentation-pinning report was closed as a duplicate of this issue.

## Change summary

Allow users to pin documentation hovers for persistent reference beside their code.

## Best solution

Provide an explicitly retained documentation surface that remains readable while editing, with deliberate dismissal. Decide whether that surface is an anchored popover or a dedicated view before implementation; ordinary transient hovers should retain their existing behavior.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/hover/browser/contentHoverController.ts`, `src/vs/editor/contrib/hover/browser/contentHoverWidget.ts`, `src/vs/editor/contrib/hover/browser/contentHoverWidgetWrapper.ts`, `src/vs/editor/contrib/hover/browser/hoverActions.ts`, `src/vs/editor/contrib/hover/browser/hoverActionIds.ts`
- **Validation:** After choosing the retention model, open a symbol documentation hover, retain it, then move the pointer away, click elsewhere, type, and scroll. Verify the retained documentation remains available according to the chosen lifecycle, can be explicitly dismissed using the keyboard, and does not change dismissal behavior for ordinary unpinned hovers.
- **Behavior:**

  > Users need to retain a symbol's documentation for reference while continuing to work in the editor. Existing hover focus and pointer-stickiness do not satisfy that workflow. Acceptance should cover retaining the content during editing, deliberate keyboard-accessible dismissal, and unchanged behavior for ordinary unpinned hovers. The retained surface's placement and lifetime require a product decision.
- **Trace:**

  > EditorHover in src/vs/editor/common/config/editorOptions.ts exposes pointer stickiness, hiding delay, and above/below preference, but no pinning option. ShowOrFocusHoverAction in src/vs/editor/contrib/hover/browser/hoverActions.ts operates on the transient hover through ContentHoverController. That controller owns one ContentHoverWidgetWrapper and dismisses the hover on editor clicks, scrolling, and ordinary key input; ContentHoverWidget already supports resizing. These source paths establish the remaining gap without executing the UI. Preserve existing unpinned hover semantics and do not assume the discussion's debugging examples require a debugger implementation in the same change. https://github.com/microsoft/vscode/issues/147492 was consolidated here; https://github.com/microsoft/vscode/issues/332901 is a newer related selection-focused request, not an older canonical. The trace does not establish a dedicated-view architecture or an extension API contract.
- **Open decisions:**
  - Should retained documentation remain in an anchored popover, appear in a dedicated view, or support both?
  - Should retention capture a fixed documentation snapshot or update when the cursor or underlying symbol changes?
  - Can users retain multiple documentation items, and what should happen to retained content when its source editor is closed?
