# Issue #44711 — Provide activation reason to extensions in activate call

[https://github.com/microsoft/vscode/issues/44711](https://github.com/microsoft/vscode/issues/44711)

## Summary

The requested activation context is still missing from the extension-facing API, although VS Code already tracks activation reasons internally. Keep this accepted Backlog request open: 21 upvotes and multiple concrete extension-author use cases support an API design discussion.

## Change summary

Expose activation context during an extension's activate call so it can tailor initialization and diagnostics to the triggering command or event.

## Best solution

Define a forward-compatible activation-context API that supports command-specific diagnostics and selective initialization without implying an exhaustive set of activation causes. Settle its semantics for dependency activation, concurrent triggers, and reactivation before implementation.

- **Behavior:**

  > An extension activated by flutter.createProject with no workspace open should have enough activation context during activate to choose Flutter-specific missing-SDK diagnostics without a timer. Extensions handling several languages should be able to identify a triggering language event when the agreed contract makes it available. Existing extensions that do not inspect activation context must behave unchanged. Acceptance checks should cover direct command activation and the agreed behavior for indirect, concurrent, and restart activation.
- **Trace:**

  > ExtensionActivationReason in src/vs/workbench/services/extensions/common/extensions.ts already carries startup, extensionId, and activationEvent internally. ExtensionsActivator.activateByEvent in src/vs/workbench/api/common/extHostExtensionActivator.ts constructs it, while _handleActivationRequest propagates the originating reason through dependencies and reuses an existing activation operation. AbstractExtHostExtensionService._doActivateExtension in src/vs/workbench/api/common/extHostExtensionService.ts receives the reason, but _loadExtensionContext does not, and _callActivateOptional passes only the resulting context to activate. The stable ExtensionContext in src/vscode-dts/vscode.d.ts and its proposed augmentations expose no corresponding information. The uncertainty begins at the public contract: internally propagated root-cause metadata is not necessarily the reason an extension author would expect for dependency activation or competing triggers. Preserve activation scheduling, dependency ordering, and existing activate-call compatibility; changes to eager debugger activation tracked by https://github.com/microsoft/vscode/issues/88617 are outside this request. The compatibility concern is documented at https://github.com/microsoft/vscode/issues/44711#issuecomment-369183434.
- **Open decisions:**
  - Should the public API expose an open-ended activation-event string, structured activation causes, or both, and what should extensions receive when a cause is unavailable?
  - For dependency or imperative activation, should the context describe the extension's immediate activation cause, the originating extension and event, or both?
  - When several events race to activate an extension, should the contract report only the winning trigger or represent multiple triggers?
  - After an extension-host restart, should activation context identify reactivation explicitly or preserve the original triggering context?
  - Does the initial API include matching workspaceContains resource paths requested in the discussion, or only activation-event metadata?
