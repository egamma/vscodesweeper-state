# Issue #224682 — Feature Request: Persistent Undo/Redo Across Sessions

[https://github.com/microsoft/vscode/issues/224682](https://github.com/microsoft/vscode/issues/224682)

## Summary

Keep open for the clarified request: persistent, granular undo history that also preserves alternative branches. Existing capabilities provide only partial coverage, and the verified older issues separately cover persistence and branching rather than the complete requested behavior.

## Change summary

Preserve granular, branching undo/redo history across editor closure, VS Code restarts, crashes, and computer reboots.

## Best solution

Design durable editor undo history together with the existing persistence and undo-branch discussions, preserving familiar undo/redo behavior. Settle retention, crash-recovery guarantees, and branch navigation before implementation; save-based Timeline snapshots are not an equivalent solution.

## Plan brief

- **Likely files:** `src/vs/editor/common/services/modelService.ts`, `src/vs/platform/undoRedo/common/undoRedoService.ts`
- **Validation:** After agreeing on the persistence and navigation contract, edit a file through several undo stops, undo and create an alternative edit, then close/reopen the editor and restart VS Code. Verify granular undo/redo and both branches remain recoverable; repeat after forced termination and verify recovery to the agreed durability boundary. Check ordinary undo/redo and files.restoreUndoStack behavior remain compatible.
- **Behavior:**

  > The requested history survives editor closure and subsequent VS Code sessions, rather than preserving only saved snapshots. Undoing and then making a different edit must not permanently discard the alternative history. Users must be able to recover and navigate retained states through a keyboard-accessible interaction. Acceptance includes normal restart and recovery after unexpected termination, with durability and retention limits explicitly agreed beforehand.
- **Trace:**

  > ModelService in src/vs/editor/common/services/modelService.ts caches disposed-model metadata in memory and reattaches retained undo elements when a matching resource is reopened. ResourceEditStack in src/vs/platform/undoRedo/common/undoRedoService.ts has linear past/future arrays, and pushElement discards the future on a new edit. Local History stores saved-content snapshots and can merge nearby entries, so it does not satisfy the clarified requirement. Persistence is discussed in https://github.com/microsoft/vscode/issues/15135 and https://github.com/microsoft/vscode/issues/43555, serialization in https://github.com/microsoft/vscode/issues/7536, and branching in https://github.com/microsoft/vscode/issues/20889. The trace establishes the missing capabilities, but not a complete storage lifecycle or all shared undo-service consumers. Preserve familiar undo/redo interactions and existing saved-state recovery; the session must first settle the public persistence and branch-navigation contract.
- **Open decisions:**
  - Should durable history be enabled by default or opt-in, and what retention limits are exposed to users?
  - What history is guaranteed recoverable after an unexpected termination: every completed undo stop or history through a documented checkpoint boundary?
  - How should users select alternative branches while ordinary undo/redo shortcuts retain their familiar behavior?
