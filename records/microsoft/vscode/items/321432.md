# Issue #321432 — Agent turn hangs indefinitely when a streaming response stalls (no idle timeout in messagesApi/responsesApi SSE read loop)

[https://github.com/microsoft/vscode/issues/321432](https://github.com/microsoft/vscode/issues/321432)

## Summary

Keep open: both current SSE processors can still wait indefinitely on a body that neither produces data nor closes. The merged telemetry PR explicitly did not mitigate the hang, and the maintainer's timeout and migration concerns require a product decision before implementation.

## Change summary

Prevent stalled Messages and Responses API streams from leaving agent turns pending indefinitely.

## Best solution

Establish a finite, provider-appropriate termination policy for stalled model streams on the supported request paths, with explicit failure and reliable cancellation. Resolve the maintainer's migration and timeout concerns before changing behavior; observation-only telemetry does not complete this work.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/endpoint/node/messagesApi.ts`, `extensions/copilot/src/platform/endpoint/node/responsesApi.ts`, `extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts`, `extensions/copilot/src/platform/endpoint/test/node/messagesApi.spec.ts`, `extensions/copilot/src/platform/endpoint/node/test/responsesApi.spec.ts`
- **Validation:** Use the existing endpoint Vitest suites with controlled ReadableStream bodies and fake timers: HTTP 200 followed by no bytes, a stall after partial SSE data, and a stream ending without its terminal event must settle according to the approved policy. Check that healthy long-running streams remain valid, cancellation settles a pending read, and timers/resources are cleaned up. Run equivalent cases for both Messages and Responses APIs.
- **Behavior:**

  > An agent turn must not remain pending indefinitely because its model response returns HTTP 200 but then stops producing data without closing. Both Messages and Responses API paths need a documented finite outcome for a stalled response, without treating legitimate long model processing as an immediate failure. Acceptance must cover stalls before the first byte and after partial output, premature stream termination, normal completion, and cancellation. Timeout tolerance and treatment of non-progress keep-alive traffic remain maintainer decisions.
- **Trace:**

  > processResponseFromMessagesEndpoint in extensions/copilot/src/platform/endpoint/node/messagesApi.ts and processResponseFromChatEndpoint in extensions/copilot/src/platform/endpoint/node/responsesApi.ts feed SSE parsers inside unguarded response.body loops. DestroyableStream in extensions/copilot/src/platform/networking/common/fetcherService.ts waits on reader.read() without a deadline, confirming the pending-read boundary from current source. ChatEndpoint selects these processors, but does not pass its cancellation token; transport-level abort wiring already exists and must not be mistaken for absent cancellation everywhere. https://github.com/microsoft/vscode/pull/321671 deliberately observed stalls without terminating them, so it is not a fixing PR. The maintainer questioned a 120-second threshold and preferred deferral until migration in https://github.com/microsoft/vscode/issues/321432#issuecomment-4712356311. Planning must establish which supported post-migration flows still use these processors and settle the user-visible termination policy; preserve healthy streaming, normal completion, and existing transport cancellation rather than redesigning unrelated agent-host lifecycle behavior.
- **Open decisions:**
  - Should the remaining supported legacy SSE paths receive mitigation now, or should this work remain deferred pending verification that the AHP+CLI migration replaces them?
  - What first-byte and subsequent inactivity limits should apply, given the reported legitimate multi-minute model responses and the maintainer's objection to a 120-second limit?
  - Should periodic keep-alive bytes permit an indefinitely pending turn, or must a separate progress or total-turn deadline terminate it?
