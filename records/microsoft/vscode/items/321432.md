# Issue #321432 — Agent turn hangs indefinitely when a streaming response stalls (no idle timeout in messagesApi/responsesApi SSE read loop)

[https://github.com/microsoft/vscode/issues/321432](https://github.com/microsoft/vscode/issues/321432)

## Summary

Keep open: both current streaming processors still await body chunks without a local inactivity deadline, and the linked merged PR explicitly added observation rather than mitigation. The maintainer's concerns about timeout duration and the AHP/CLI migration require a product decision before changing request behavior.

## Change summary

Prevent a stalled Messages or Responses API stream from leaving an agent turn pending indefinitely.

## Best solution

Establish the supported endpoint paths after migration and agree on a stall-recovery policy that bounds genuinely stuck turns without rejecting legitimate long model pauses. Validate that policy against both streaming processors and preserve existing request cancellation and healthy-stream behavior.

- **Validation:** Add deterministic Vitest cases in the existing Messages and Responses endpoint suites using a controllable response body that remains open without producing bytes. Under the agreed policy, assert that a pending completion settles within the allowed interval, healthy chunks reset inactivity accounting, cancellation remains effective, and normal terminal events retain existing behavior; also test continuing keep-alive traffic if a total deadline is selected.
- **Behavior:**

  > An agent turn must not remain pending indefinitely because an HTTP 200 streaming response stops delivering data without closing. Recovery must follow a maintainer-approved timeout policy and preserve legitimate long-running model responses. Acceptance checks cover a stall before the first byte, a stall after partial output, normal streaming completion, and cancellation. A total-duration limit for streams that continue sending keep-alives is a separate observable policy choice, not an assumed requirement.
- **Trace:**

  > processResponseFromMessagesEndpoint in extensions/copilot/src/platform/endpoint/node/messagesApi.ts and processResponseFromChatEndpoint in extensions/copilot/src/platform/endpoint/node/responsesApi.ts both directly await response.body chunks with no local inactivity escape. ChatEndpoint.processResponseFromChatEndpoint in extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts routes to these processors without forwarding its cancellation token, although networking.ts separately supports request-level abort signals; preserve that distinction. The source confirms the non-terminating-body case without executing it, and the reporter supplies corroborating proxy/client logs at https://github.com/microsoft/vscode/issues/321432#issuecomment-4709793611. The merged https://github.com/microsoft/vscode/pull/321671 was explicitly observation-only, not mitigation. At https://github.com/microsoft/vscode/issues/321432#issuecomment-4712356311 a maintainer questions the proposed threshold and prefers waiting for migration, so the session must first settle supported-path scope and observable recovery policy. Do not conflate this defect with terminal tool execution, upstream service remediation, or every abandoned agent-host turn.
- **Open decisions:**
  - Should mitigation be added to the retained Messages and Responses endpoint paths now, or should this work remain deferred pending confirmation of the AHP/CLI migration's coverage?
  - What inactivity threshold and recovery behavior should distinguish a stuck stream from a legitimate long model pause?
  - Should streams that keep sending keep-alive bytes also have a total request deadline, and if so what duration and termination behavior should users observe?
