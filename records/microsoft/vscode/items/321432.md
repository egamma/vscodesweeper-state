# Issue #321432 — Agent turn hangs indefinitely when a streaming response stalls (no idle timeout in messagesApi/responsesApi SSE read loop)

[https://github.com/microsoft/vscode/issues/321432](https://github.com/microsoft/vscode/issues/321432)

## Summary

Keep open: both current HTTP SSE processors still await body chunks without a processor-level inactivity deadline, so a body that neither produces data nor terminates can leave the turn pending. The linked telemetry PR explicitly did not mitigate the hang; timeout tolerance and the intended post-migration scope need a maintainer decision.

## Change summary

Ensure stalled Anthropic Messages and OpenAI Responses HTTP streams cannot leave an agent turn pending indefinitely.

## Best solution

Establish a bounded, explicit failure outcome for stalled streams on the endpoint paths that remain supported after migration, while preserving legitimate long reasoning pauses and cancellation. Choose the timeout policy using the recorded latency evidence rather than adopting the proposed 120-second threshold without review.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/endpoint/node/messagesApi.ts`, `extensions/copilot/src/platform/endpoint/node/responsesApi.ts`, `extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts`, `extensions/copilot/src/platform/endpoint/test/node/messagesApi.spec.ts`, `extensions/copilot/src/platform/endpoint/node/test/responsesApi.spec.ts`
- **Validation:** Add deterministic Vitest cases in the Messages and Responses endpoint suites using an HTTP-200 Response with a controlled ReadableStream that never closes. Advance fake time through the agreed deadline and assert explicit failure instead of a pending turn; also cover resumed chunks, legitimate pauses below the threshold, cancellation, and healthy terminal SSE events.
- **Behavior:**

  > An agent turn must not remain pending indefinitely when a supported HTTP streaming endpoint returns headers but its body stops making progress without closing or reporting an error. Under the agreed timeout policy, the turn must reach an explicit failure or cancellation outcome rather than consume an outer harness cap. Healthy streams and legitimate reasoning pauses within the supported tolerance must continue normally. Acceptance checks should cover both Messages and Responses streams, including stalls before the first chunk and after partial output.
- **Trace:**

  > processResponseFromMessagesEndpoint in extensions/copilot/src/platform/endpoint/node/messagesApi.ts and processResponseFromChatEndpoint in extensions/copilot/src/platform/endpoint/node/responsesApi.ts directly iterate response.body with no processor-level inactivity deadline. A controlled non-terminating body therefore leaves the AsyncIterableObject producer pending; the reporter's proxy/client logs corroborate that outcome in https://github.com/microsoft/vscode/issues/321432. ChatEndpoint dispatches to both functions without forwarding its cancellation token, although networking.ts separately attaches cancellation to the HTTP abort signal. Response.body uses DestroyableStream in extensions/copilot/src/platform/networking/common/fetcherService.ts; destroy() cancels through the reader and does not accept an error argument, so cancellation alone must not be assumed to produce the proposed rejection semantics. https://github.com/microsoft/vscode/pull/321671 was observation-only, not a behavioral fix. Preserve healthy completion processing and existing transport cancellation, and do not expand this work into terminal-tool failures or unrelated agent-host lifecycle defects. The uncertainty is the acceptable timeout behavior and which endpoint paths the maintainer intends to retain after migration.
- **Open decisions:**
  - What first-byte and subsequent inactivity limits should supported streams use, given the maintainer's concern that a 120-second limit can interrupt legitimate model pauses?
  - Should these existing HTTP endpoint paths receive mitigation now, or is their replacement by AHP+CLI the intended resolution—and which supported paths must remain protected afterward?
  - Should a stream that continues sending keep-alives without completing have a separate maximum duration, and what duration preserves supported long-running reasoning?

## Evidence

- **Confirmed report:** https://github.com/microsoft/vscode/issues/321432#issuecomment-4709793611 documents a fourth /v1/messages request returning HTTP 200 headers without a corresponding client completion, error, or retry before the harness cap. https://github.com/microsoft/vscode/issues/321432#issuecomment-4709832243 establishes that the preceding tools had already returned.
- **Current Messages path:** extensions/copilot/src/platform/endpoint/node/messagesApi.ts:678–752 constructs the streaming AsyncIterableObject and directly awaits response.body at lines 746–748. A body that never yields, ends, or errors keeps that producer pending; no inactivity timer or deadline is present in this function.
- **Current Responses path:** extensions/copilot/src/platform/endpoint/node/responsesApi.ts:1012–1047 contains the same direct body iteration at lines 1041–1043, with completion emission driven by parsed SSE events and no processor-level inactivity deadline.
- **Cancellation boundary:** extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts passes the cancellation token to ChatEndpoint.processResponseFromChatEndpoint, but extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts:536–555 does not forward it to the Messages or Responses processors. Cancellation is nevertheless wired to an HTTP abort signal in extensions/copilot/src/platform/networking/common/networking.ts, so the report does not establish that all current user cancellation is broken.
- **Merged PR is not a mitigation:** https://github.com/microsoft/vscode/pull/321671 is merged, but its description and diff explicitly add only an observe-only five-minute watchdog: no abort, rejection, or request-behavior change. Current messagesApi.ts no longer contains that watchdog. https://github.com/microsoft/vscode/pull/321640 changes terminal-output handling, not stalled SSE reads. Neither establishes completion of this issue; local history is shallow.
- **Unsettled product policy:** https://github.com/microsoft/vscode/issues/321432#issuecomment-4712356311 questions whether 120 seconds tolerates legitimate pauses and favors waiting for AHP+CLI migration. https://github.com/microsoft/vscode/issues/321432#issuecomment-4712386795 reports zero occurrences in the plain CLI control, distinguishing the affected integration.
