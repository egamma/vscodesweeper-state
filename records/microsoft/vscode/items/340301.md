# Issue #340301 — Agents window: new session sometimes starts on a different model than the last used one

[https://github.com/microsoft/vscode/issues/340301](https://github.com/microsoft/vscode/issues/340301)

## Summary

Team-authored bug report (so protected from judgment closes regardless) describing an intermittent model-selection mismatch when starting a new Agents window session; the area already has dedicated diagnostics instrumentation for exactly this symptom, but I found no fix on main and the report itself has no confirmed repro trace yet.

## Change summary

A new Agents window session sometimes preselects a different model than the one last used in the previous session, instead of always carrying it forward.

## Best solution

Use the existing ChatModelSelectionDiagnostics logging (src/vs/workbench/contrib/chat/browser/widget/input/chatModelSelectionDiagnostics.ts) to capture a real occurrence, then check whether the mismatch comes from model storage being scoped per `modelTarget` (src/vs/sessions/contrib/chat/browser/sessionModelSelection.ts, getSelectedModelStorageKey) while new-session initialization picks a different modelTarget/provider before settling on the previous one.

- **Trace:**

  > sessionModelSelection.ts stores and reads the selected model per `modelTarget` via getSelectedModelStorageKey(ChatAgentLocation.Chat, modelTarget); `_modelTarget` is set from the active session/provider's snapshot during `_refresh`/`selectModel`. If a new Agents window session briefly resolves to a different provider/session-type (hence modelTarget) during startup before the final one is bound, it would read that other target's stored model — plausibly explaining the intermittent mismatch. Not yet confirmed from source alone; needs a captured occurrence via the existing ChatModelSelectionDiagnostics logging.
- **Open decisions:**
  - Is 'last used model' meant to persist per modelTarget (provider/session-type) or as one global last-used value across all Agents window sessions?
  - What is the actual sequence during new-session startup that produces a transient wrong modelTarget — is it a provider/session-type resolution race, or a storage event ordering issue?

## Evidence
