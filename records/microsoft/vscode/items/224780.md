# Issue #224780 — Make dropdown control looks more consistent with other parts

## Change summary

Bring the custom select dropdown's scrolling, spacing, elevation, and separators into visual alignment with other VS Code menus.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/selectBox/selectBox.ts`, `src/vs/base/browser/ui/selectBox/selectBoxCustom.ts`, `src/vs/base/browser/ui/selectBox/selectBoxCustom.css`, `src/vs/base/test/browser/ui/selectBox/selectBox.test.ts`
- **Validation:** Add focused SelectBoxList DOM tests for separator rendering and navigation, run the select-box unit suite, then manually compare a long Output-channel dropdown on Windows/Linux and macOS with `window.menuStyle: custom`, including keyboard navigation, scrolling, high-contrast themes, and reduced-motion behavior.
- **Behavior:**

  > Custom select dropdowns should feel consistent with VS Code's other floating menus: the overlay uses the shared elevation treatment, option spacing is coherent, and separators read as compact dividers rather than disabled full-height options. Long dropdowns should scroll according to the agreed smooth-scrolling contract without disrupting keyboard selection. Mouse, keyboard, screen-reader, high-contrast, and reduced-motion behavior must remain usable.
- **Trace:**

  > The shared implementation is SelectBoxList in src/vs/base/browser/ui/selectBox/selectBoxCustom.ts, with presentation in selectBoxCustom.css and the separator contract in selectBox.ts. Main already includes a large-radius overlay, shared shadow token, and a full-width `option-separator::after` rule. The remaining separator-height issue comes from `getHeight` returning the constant `SELECT_OPTION_HEIGHT` for all elements; scrolling is created through `List` in `createSelectList` without an explicit smooth-scrolling policy. Existing coverage in src/vs/base/test/browser/ui/selectBox/selectBox.test.ts exercises dropdown DOM behavior but not these presentation and interaction requirements. Preserve native-select mirroring, disabled-option navigation, ARIA roles and labels, and option-description behavior. Related design detail is tracked in https://github.com/microsoft/vscode/issues/277746, but that newer issue cannot replace this older report as canonical during re-review.
- **Open decisions:**
  - Should a separator occupy a compact dedicated row, or be rendered between adjacent option rows without consuming a selectable row?
  - Should custom select dropdowns honor the workbench smooth-scrolling preference, or use one fixed scrolling behavior independent of other lists?
