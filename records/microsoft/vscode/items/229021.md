# Issue #229021 — Zero-width non-joiner renders differently in different file types

[https://github.com/microsoft/vscode/issues/229021](https://github.com/microsoft/vscode/issues/229021)

## Summary

Still a valid open bug — the inconsistent rendering of ZWNJ (U+200C) across file types is rooted in language-specific tokenization boundaries and has not been specifically fixed on main, despite significant RTL rendering work since the report. No commit references this issue.

## Change summary

Zero-width non-joiner (ZWNJ / half-space) in Persian text renders correctly in Markdown/HTML/Python but incorrectly in JS/TS/Go, because different language tokenizers split tokens at different boundaries around the ZWNJ character.

## Best solution

The fix likely belongs in the view-line renderer's token-merging logic (src/vs/editor/common/viewLayout/viewLineRenderer.ts): adjacent tokens containing RTL text separated only by ZWNJ should be merged or the ZWNJ should not break the bidi run. This is a specific case of the broader RTL rendering effort tracked by https://github.com/microsoft/vscode/issues/86667 and https://github.com/microsoft/vscode/issues/65648, but this report adds a concrete, actionable reproduction that those broader issues don't cover — keep it open as a distinct bug.

- **RTL work since filing:** Significant RTL work has landed — PR #255455 (decoration-based RTL), PR #279474 (dir="auto" on RTL tokens), and bidi text fixes — but these address line-level direction and token-level dir attributes, not ZWNJ-at-token-boundary splitting.
- **root cause in tokenization:** The viewLineRenderer splits containsRTL per token (line 557–561) and applies dir attributes per span. If a language tokenizer (e.g. JS/TS/Go) splits a Persian word at the ZWNJ boundary into separate tokens, each token's RTL rendering may invert the visual order. Markdown/HTML/Python likely keep the text in a single token.
