# Issue #229021 — Zero-width non-joiner renders differently in different file types

[https://github.com/microsoft/vscode/issues/229021](https://github.com/microsoft/vscode/issues/229021)

## Summary

The language-dependent rendering remains explainable on current main: RTL isolation is applied independently to syntax-token-derived line parts, so token boundaries around U+200C can change the visual ordering. The issue already has the appropriate editor rendering and RTL routing labels.

## Change summary

Persian identifiers containing U+200C render in a different, unreadable order in JavaScript, TypeScript, and Go compared with plain text, HTML, and Markdown.

## Best solution

Make a contiguous RTL identifier render consistently regardless of syntax-token boundaries while preserving syntax coloring, Unicode highlighting, and editor character-to-DOM mapping.

## Plan brief

- **Likely files:** `src/vs/editor/common/viewLayout/viewLineRenderer.ts`, `src/vs/editor/test/common/viewLayout/viewLineRenderer.test.ts`
- **Validation:** Add a view-line renderer case containing `اب‌الو` with line-part boundaries around U+200C, then verify in a browser-backed editor scenario that its visual order matches an unsplit token across JavaScript, TypeScript, Go, plain text, HTML, and Markdown while existing RTL renderer tests remain unchanged.
- **Behavior:**

  > A Persian identifier containing U+200C must retain the same readable visual order in every language mode. Syntax highlighting or invisible-character decoration must not split or reverse the identifier. Acceptance requires matching visual order in JavaScript, TypeScript, Go, plain text, HTML, and Markdown, with cursor positioning and selection still corresponding to the original character offsets.
- **Trace:**

  > The editor converts language tokens into LinePart entries in transformAndRemoveOverflowing within src/vs/editor/common/viewLayout/viewLineRenderer.ts. Each part is tested independently with strings.containsRTL, and _renderLine emits a separate `unicode-bidi:isolate` span for every RTL-containing part; the enclosing view line is explicitly LTR for mixed content in src/vs/editor/browser/viewParts/viewLines/viewLine.ts. This makes bidi behavior depend on language-token boundaries around the neutral U+200C character. Existing tests in src/vs/editor/test/common/viewLayout/viewLineRenderer.test.ts cover mixed RTL tokens and isolation but not a ZWNJ-separated identifier split across parts. Preserve syntax styling, Unicode-security highlighting, whitespace rendering, and CharacterMapping behavior; uncertainty begins with the isolation strategy needed to preserve one bidi run across differently styled spans.
- **Open decisions:**
  - Should contiguous RTL text separated by U+200C participate in one bidi run across token boundaries, or should the span-level CSS bidi strategy change more generally?
  - How should Unicode invisible-character highlighting interact with the bidi run without hiding U+200C or changing cursor and selection mapping?
  - Which browser-backed regression test can assert visual ordering rather than only snapshotting generated markup?

## Evidence

- **current source path:** src/vs/editor/common/viewLayout/viewLineRenderer.ts derives each LinePart from language token boundaries in transformAndRemoveOverflowing, computes containsRTL separately for each substring, and emits `unicode-bidi:isolate` independently for every RTL-containing part in _renderLine.
- **tokenization-dependent behavior:** Because U+200C is not itself an R/AL character, a token or decoration boundary at the character can leave the surrounding Persian fragments in separate isolated spans inside the line's LTR container; different language tokenization therefore changes bidi layout without changing the source text.
