# Issue #261048 — Impossible to select text and code from a chat message

[https://github.com/microsoft/vscode/issues/261048](https://github.com/microsoft/vscode/issues/261048)

## Summary

The selection gap remains on current main: request prose is native DOM text while fenced code is rendered in a separate Monaco editor, so a selection cannot span both surfaces. A maintainer proposed reconsidering Markdown rendering rather than bridging the two selection models, leaving a concrete product choice that should remain open.

## Change summary

Allow users to select and copy a contiguous range containing both prose and fenced code from a chat request.

## Best solution

Give chat requests one coherent selection experience, likely by rendering their displayed content in a single selectable surface while retaining an explicit full-message copy action. Preserve useful code readability without making users discover separate selection and copy mechanisms.

- **Behavior:**

  > A chat request containing prose and fenced code must offer a coherent way to select and copy a contiguous range across both kinds of content. Copying the selected range must preserve every line once and in display order. Standalone code selection and the full-message Copy action must remain available and understandable.
- **Trace:**

  > Request rendering starts in src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts, which sends the request Markdown through ChatMarkdownContentPart. In src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatMarkdownContentPart.ts, fenced blocks are replaced with CodeBlockPart, and src/vs/workbench/contrib/chat/browser/widget/chatContentParts/codeBlockPart.ts hosts each block in a read-only CodeEditorWidget; prose stays in the surrounding native DOM. That DOM/editor boundary explains the reported split selection on current main. The maintainer discussion at https://github.com/microsoft/vscode/issues/261048 rejects coordinating both selection systems and raises request rendering as the alternative; the uncertainty begins at the user-visible tradeoff between Markdown/code-editor presentation and one continuous native selection surface. Do not broaden this into response auto-scroll, which is separately discussed in https://github.com/microsoft/vscode/issues/263717 and https://github.com/microsoft/vscode/issues/307939.
- **Open decisions:**
  - Should user requests retain Markdown-rendered Monaco code blocks, or use a single native selectable presentation so mouse selection can span prose and code?

## Evidence

These are independent selection models.

That proposed product change rules out a decline close while its tradeoff remains undecided.
