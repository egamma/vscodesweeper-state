- **Proposed comment:**

  > Thanks for the report. The command expects the range and language as separate arguments: `await vscode.commands.executeCommand('notebook.cell.changeLanguage', { start: 1, end: 2 }, 'javascript');`. With an active notebook editor, this targets cell index 1 and takes the direct language-change path without opening the picker; the same argument handling was present in 1.86.2. This command currently targets the first cell in the supplied range, rather than every cell in it.

## Evidence

- **Existing command contract:** src/vs/workbench/contrib/notebook/browser/controller/editActions.ts:398–461 registers notebook.cell.changeLanguage with two arguments: range {start, end} and language string. ChangeCellLanguageAction.getCellContextFromArgs reads start/end directly from the first argument and the language from additionalArgs[0]; runWithContext bypasses the picker when that language is supplied.
- **Argument forwarding and mutation:** src/vs/workbench/contrib/notebook/browser/controller/coreActions.ts:262–278 forwards additional arguments into getCellContextFromArgs. editActions.ts:596–613 applies a CellLanguage edit for an existing code cell. Thus executeCommand('notebook.cell.changeLanguage', {start: 1, end: 2}, 'javascript') reaches the noninteractive single-cell path; a nested {range, language} argument fails parsing and falls back to the active-cell picker.
- **Capability predates the report:** Read the same command implementation at the reporter's VS Code 1.86.2 commit, https://github.com/microsoft/vscode/commit/903b1e9d8990623e3d7da1df3d33db3e42d80eda. It already parses the positional range and language and bypasses the picker. This is existing capability, not evidence of a subsequently landed fix.
