## Plan brief

- **Likely files:** _(none given)_
- **Validation:** The plan should end with a Windows integration scenario that opens a host-backed workspace through a Windows Sandbox target, executes a PowerShell script inside the sandbox, verifies host edits persist after sandbox disposal, and confirms sandbox-installed state does not persist.
- **Behavior:**

  > VS Code should support Windows Sandbox as an isolated development target while keeping the user's working copy on the host. A user can open or attach to a configured sandbox, edit the host-backed workspace, and run scripts or binaries inside the sandbox without manual copying. Host file changes must persist after the sandbox is closed, while guest-installed state remains disposable. The plan must define whether contextual one-shot execution and a configuration GUI are part of the initial capability or follow-up work.
- **Trace:**

  > The issue is a Backlog Remote Development feature request with 45 upvotes and no verified canonical duplicate. The report references external Windows Sandbox tooling as design evidence, not an implementation already present in VS Code. The uncertainty begins at the product boundary: full workspace attachment, one-shot contextual execution, and GUI configuration are separable public experiences. Keep host-workspace persistence and disposable guest state as invariants; do not collapse the request into merely launching a `.wsb` file or an external process.
- **Open decisions:**
  - Is the initial supported experience a persistent Remote Development target for an entire workspace, one-shot execution of selected files in Windows Sandbox, or both?
  - Should VS Code own a Windows Sandbox configuration GUI in the initial scope, or consume existing `.wsb` configuration files and leave authoring UI as follow-up or extension territory?
  - Which host-to-sandbox sharing and trust model is exposed to users by default, particularly for writable workspace mounts and command execution?
