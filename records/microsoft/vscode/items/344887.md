# Issue #344887 — Let dictation reach chat inputs contributed by extensions (webviews), including over Remote Tunnels

[https://github.com/microsoft/vscode/issues/344887](https://github.com/microsoft/vscode/issues/344887)

## Summary

The requested third-party dictation integration is already tracked by the open Speech API request, which explicitly asks for speech events or integration into extension-contributed text inputs. Consolidate there while preserving this report's Remote Tunnels requirements and concrete extension examples.

## Change summary

Allow extension-contributed webview inputs to receive client-side dictation, either through focused-input integration or a consumer speech API.

## Best solution

Resolve extension-consumable dictation through https://github.com/microsoft/vscode/issues/242428, including client-side recognition for remote workspaces and partial/final transcript events. This report supplies concrete acceptance scenarios for that existing request rather than a separate defect.

Its body requests speech interfaces for third-party extensions, integration into text-entry components, and events enabling behavior like Copilot Chat. This encompasses both alternatives offered by the present report, not merely provider registration.
- **Established community demand:** https://github.com/microsoft/vscode/issues/242428#issuecomment-2705391289 records promotion after sufficient community upvotes. The subsequent discussion continues to request usable speech APIs for shipping extensions.
- **Existing commands do not cover the request:** src/vs/workbench/contrib/chat/browser/actions/chatSpeechToTextActions.ts resolves workbench.action.chat.toggleSpeechToText through IChatWidgetService and widget.inputEditor. src/vs/workbench/contrib/codeEditor/browser/dictation/editorDictation.ts implements workbench.action.editorDictation.start as an EditorAction2 over ICodeEditor, while terminalVoiceActions.ts targets terminal instances. These are not a generic focused-webview dictation surface.
- **Consumer API remains absent:** src/vscode-dts/vscode.proposed.speech.d.ts exposes registerSpeechProvider and registerVoiceLiveSessionProvider, but no consumer operation to request a recognition session. src/vs/workbench/api/common/extHost.api.impl.ts gates both registrations behind the speech proposal. Finalizing provider registration alone would not satisfy either this report or the canonical's requested consumer integration.
- **Distinctive scenario to retain:** https://github.com/microsoft/vscode/issues/344887 identifies anthropic.claude-code and openai.chatgpt webviews, Windows-to-Windows Remote Tunnels, client-side microphone capture, partial/final transcription, and an existing UI-recorder/workspace-relay workaround. These refine the canonical request's acceptance scenarios without establishing a separate root cause.
