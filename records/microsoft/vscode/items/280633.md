# Issue #280633 — Update chat message when a user reaches their chat limit

[https://github.com/microsoft/vscode/issues/280633](https://github.com/microsoft/vscode/issues/280633)

## Summary

The requested reset date is still missing from the non-usage-based quota message on current main. This team-authored feature request is accepted in the Backlog and should remain open while the reset timestamp semantics are clarified.

## Change summary

Include the applicable allowance-reset date in the chat response shown when a user exhausts their Copilot chat quota.

## Best solution

Make quota-exceeded responses show the same applicable reset timestamp as the chat status surface, while retaining the existing fallback copy when no valid reset time is available. Keep the extension and corresponding core Agent Host formatter behavior consistent.

- **Behavior:**

  > When Copilot rejects a chat request because the user's allowance is exhausted and a valid reset timestamp is known, the response tells the user when that allowance resets. When no valid reset timestamp is available, the existing undated guidance remains. Usage-based billing, plan-specific upgrade guidance, and unrelated error messages retain their current behavior. Acceptance checks cover both dated and undated non-usage-based quota responses in the extension and mirrored core formatter.
- **Trace:**

  > The quota-exceeded request path in extensions/copilot/src/extension/conversation/vscode-node/languageModelAccess.ts already supplies `copilotToken.quotaInfo.quota_reset_date` to `getErrorDetailsFromChatFetchError`. In extensions/copilot/src/platform/chat/common/commonTypes.ts, `getQuotaMessageForPlan` formats that value but uses it only inside the usage-based-billing branch; the ordinary free-plan branch therefore reproduces the reported omission in current source. src/vs/workbench/contrib/chat/common/chatErrorMessages.ts mirrors this formatter and has the same gap for Agent Host-backed paths. The status surface can prefer quota-snapshot reset data through `getQuotaReset`, so uncertainty starts where the response formatter must choose between snapshot-specific and account-level reset timestamps. Keep changes bounded to quota-exceeded messaging and its tests; do not alter quota accounting, entitlement refresh, billing behavior, or other error classifications.
- **Open decisions:**
  - When account-level `quota_reset_date` and a quota snapshot's reset timestamp differ, which timestamp should the non-usage-based chat-limit response display so that it remains consistent with the status surface?
