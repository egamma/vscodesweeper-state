- **Behavior:**

  > Codex Agent Host sessions should accept every attachment type explicitly approved from the checklist in https://github.com/microsoft/vscode/issues/315193 and provide the model with the same user-selected content represented by other supported harnesses. Attachment entries that Codex cannot faithfully consume must not appear to work while silently losing context. Existing file, selection, unsaved-text, and image attachment behavior must remain intact. Acceptance requires provider-level tests for the approved matrix and an end-to-end Codex scenario covering representative text and image context.
- **Trace:**

  > The send path in src/vs/platform/agentHost/node/codex/codexAgent.ts passes protocol MessageAttachment values to resolveCodexInput in src/vs/platform/agentHost/node/codex/codexPromptResolver.ts. That resolver currently handles Resource, EmbeddedResource, and Simple variants: files become path mentions, selections retain line metadata, images become localImage inputs, textual embedded resources are inlined, and Simple values contribute modelRepresentation. Unsupported non-text binaries are dropped, and the file documents deferred skill/app mention support. Unit coverage exists in src/vs/platform/agentHost/test/node/codex/codexPromptResolver.test.ts, but it does not establish parity with the broader checklist in https://github.com/microsoft/vscode/issues/315193. Preserve the existing provider-neutral MessageAttachment seam and current supported behavior; the uncertainty begins at the product-visible matrix of additional picker entries Codex should expose and how unsupported entries should behave.
- **Open decisions:**
  - Which attachment entries from the checklist in https://github.com/microsoft/vscode/issues/315193 are required for Codex parity in this issue, versus intentionally deferred?
  - For attachment kinds Codex cannot faithfully represent, should the picker hide them for Codex sessions or expose them with an explicit unsupported-state message?
