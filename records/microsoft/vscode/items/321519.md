# Issue #321519 — Feature Request: Let extensions add custom options to the main "Session Target" dropdown menu

[https://github.com/microsoft/vscode/issues/321519](https://github.com/microsoft/vscode/issues/321519)

## Summary

Keep open: current source supports extension-contributed session targets and provider-owned request handlers, but these APIs remain proposed rather than a generally supported extension integration. Related requests confirm demand, but no verified older issue covers this same Agents Window integration requirement.

## Change summary

Allow extensions to contribute top-level session targets that send prompts directly to independent local agent runtimes without an intervening Copilot model invocation.

## Best solution

Provide a supported third-party session-provider contract that exposes independent local harnesses in the Agents Window and preserves their session identity and history without a parent-model invocation. Build on the existing session-provider and Agent Host infrastructure rather than introducing an unrelated dropdown-only command hook.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.chatSessionsProvider.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostChatSessions.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/sessionTargetPickerActionItem.ts`
- **Validation:** Use a minimal third-party extension and instrumented local CLI: select its top-level target, submit a distinctive prompt, and verify the CLI receives it without a parent-model request. Verify follow-up messages retain the same provider session identity and that session history can be reopened in the Agents Window. The plan must establish the supported installation path and lifecycle acceptance checks.
- **Behavior:**

  > An extension-owned local coding harness can be selected as a top-level target in the Agents Window. Submitting a prompt reaches that harness without first asking another model to interpret or launch it. Follow-up prompts retain the harness session identity, and the native session UI retains usable history. Existing built-in targets continue to behave unchanged.
- **Trace:**

  > SessionTypePickerActionItem in src/vs/workbench/contrib/chat/browser/widget/input/sessionTargetPickerActionItem.ts already builds entries for extension-contributed session types. The proposed chatSessionsProvider declarations expose session controllers, prompt-bearing new-session callbacks, and provider-owned request handlers; ExtHostChatSessions invokes those handlers directly. extHost.api.impl.ts still gates registration on the proposed API. This establishes partial infrastructure, not a complete supported local-harness integration in the Agents Window; that integration and its lifecycle remain the design boundary. Preserve existing built-in routing and avoid treating a raw CLI command hook as equivalent to a session-provider contract. Related design and distribution evidence is in https://github.com/microsoft/vscode/issues/325827 and https://github.com/microsoft/vscode/issues/340045; neither is an eligible older duplicate canonical.
- **Open decisions:**
  - Should the supported extension contract expose independent local harnesses through the chat-session provider API, an Agent Host provider API, or both?
  - What session lifetime and cross-window reconnect guarantees should a third-party local target provide when its originating window closes?
