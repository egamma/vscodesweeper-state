# Issue #292383 — Race with afterDelay save on editor close, especially with git commit

[https://github.com/microsoft/vscode/issues/292383](https://github.com/microsoft/vscode/issues/292383)

## Summary

The built-in Git editor still releases Git on tab closure without waiting for the commit message to reach disk. Keep this open: the earlier CLI fix protects a different completion path, and the broader ordinary-editor close behavior needs a scope decision.

## Change summary

Prevent accepting a Git commit message before pending short-delay autosave has persisted its latest edits, and assess the equivalent race on ordinary editor closure.

## Best solution

Make completion of the built-in Git commit editor reliably imply that the accepted message has been persisted, including explicit acceptance and tab closure. Separately decide whether ordinary editor closure should flush pending autosave or retain its existing asynchronous behavior; combining autosave modes is not necessary to resolve the Git defect.

- **Validation:** Exercise the built-in Git editor with files.autoSave=afterDelay and delays of 100ms and 1000ms: change a saved commit message, then immediately invoke git.commitMessageAccept or close its tab. Git must receive the complete latest message only after persistence. Repeat with a deliberately delayed or failed save to verify completion ordering and failure handling. Preserve explicit discard and autosave-off confirmation behavior; use 1001ms and onFocusChange as comparison cases. Add automated coverage for the Git IPC completion ordering; no existing GitEditor or commitMessageAccept test was found in extensions/git/src/test.
- **Behavior:**

  > With short-delay autosave enabled, accepting or closing the built-in Git commit-message editor can let Git read the previous on-disk message. Successful completion must instead deliver all accepted edits, regardless of whether the autosave deadline has elapsed. Save failures must not be reported as successful message completion, and explicit discard must retain its existing meaning. The report additionally asks whether ordinary editor closure should guarantee immediate disk persistence; that broader behavior must be settled before changing shared close semantics.
- **Trace:**

  > GitEditor.handle in extensions/git/src/gitEditor.ts opens the message and resolves the Git IPC request directly from the matching tab-closed event. Commands.commitMessageAccept in extensions/git/src/commands.ts closes the tab without saving, whereas commitMessageDiscard saves first. FileEditorInput.isSaving treats short-delay autosave as saving, and EditorGroupView.shouldConfirmClose consequently allows closure without a persistence barrier. The 1000ms cutoff is explicit in FilesConfigurationService.computeAutoSaveConfiguration. The CLI path already waits for clean working copies through whenEditorClosed in src/vs/workbench/browser/editor.ts, explaining why https://github.com/microsoft/vscode/issues/72573 does not establish a fix for the built-in Git IPC path. Preserve CLI waiting, explicit discard, long-delay confirmation, and dirty-indicator behavior unless the maintainer explicitly includes a shared close-policy change. The Wayland hang comment is not established as part of this root cause.
- **Open decisions:**
  - Should this work guarantee persistence only when completing a Git commit-message edit, or should closing any file editor with short-delay autosave also wait for persistence before reporting closure?

## Evidence

- **Current Git acceptance path:** extensions/git/src/commands.ts:2659–2666 implements git.commitMessageAccept by calling _closeEditorTab without saving. _closeEditorTab at lines 2699–2703 closes matching tabs. By contrast, commitMessageDiscard explicitly awaits commitMsgDocument.save() before closing.
- **Premature external completion:** extensions/git/src/gitEditor.ts, GitEditor.handle, resolves its IPC response immediately when window.tabGroups.onDidChangeTabs reports the commit-message tab closed. It neither saves the document nor waits for pending persistence, so accepting or closing before the autosave deadline can return stale on-disk content to Git.
- **Exact autosave threshold and close bypass:** src/vs/workbench/services/filesConfiguration/common/filesConfigurationService.ts:363–366 classifies delays of 1000ms or less as short. src/vs/workbench/contrib/files/browser/editors/fileEditorInput.ts:313–327 reports isSaving() for that configuration even before a save is pending. src/vs/workbench/browser/parts/editor/editorGroupView.ts:1738–1741 and 1885–1894 therefore bypass close confirmation without awaiting persistence. This explains the reporter's 1000ms versus 1001ms distinction.
