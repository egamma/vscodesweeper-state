# Issue #172574 — Switch back to previous application after "code --wait"

[https://github.com/microsoft/vscode/issues/172574](https://github.com/microsoft/vscode/issues/172574)

## Summary

Keep open: the current CLI waits for editor closure but does not restore the originating application's focus. Maintainer interest and a confirmed duplicate support planning this capability; cross-platform support and activation semantics remain unresolved.

## Change summary

Allow code --wait to return focus to the application from which it was invoked after the requested files are closed.

## Best solution

Provide a supported CLI focus-return capability for external-editor workflows, with an explicit activation policy and supported-platform contract. Preserve existing wait completion semantics and keep external-application activation distinct from integrated-terminal focus.

## Plan brief

- **Likely files:** `src/vs/code/node/cli.ts`, `src/vs/platform/environment/node/argv.ts`, `src/vs/platform/environment/common/argv.ts`
- **Validation:** On each supported platform, invoke code --wait <file> from an external terminal while another VS Code window remains open, edit and close the requested file, and verify that the selected policy returns OS focus to the originating application only when waiting completes. Repeat with multiple files, an existing VS Code window, and switching to a third application before closing; verify ordinary CLI invocations and disabled focus-return behavior remain unchanged.
- **Behavior:**

  > An external-terminal user should be able to finish a code --wait editing session and resume typing in the originating application without manually switching applications. Returning focus must follow an explicitly agreed activation policy and occur only after the requested editing session completes. Acceptance must cover multiple waited files and other VS Code windows remaining open, rather than relying on closing the whole application. The behavior when the user has switched to a third application must be settled before implementation.
- **Trace:**

  > src/vs/code/node/cli.ts handles args.wait by creating a marker file and registering a process callback that awaits marker deletion, child error, or applicable child exit; afterward the CLI completes its callbacks and exits. The macOS launch uses open -n -g to avoid initial launch focus problems, but the inspected completion path contains no originating-application reactivation. src/vs/platform/environment/node/argv.ts exposes wait/-w without a focus-return option, and src/vs/platform/environment/common/argv.ts contains the CLI argument contract. The reporter's macOS wrapper demonstrates the intended workflow, not a verified portable implementation; uncertainty begins at identifying and activating the originating application across platforms. Preserve existing wait-marker semantics and distinguish external OS focus from the integrated-terminal work in https://github.com/microsoft/vscode/issues/153499. https://github.com/microsoft/vscode/issues/197556 is already consolidated into this issue; https://github.com/microsoft/vscode/issues/68579 records the older platform/API obstacle.
- **Open decisions:**
  - Should focus restoration be opt-in through a CLI option, or the default for --wait with an opt-out?
  - Must the capability support macOS, Windows, and Linux initially, or is explicitly documented platform-specific support acceptable?
  - If the user switches to another application during the editing session, should completion still reactivate the original application or avoid taking focus from the user's newer activity?

## Evidence

- **Existing capability does not cover the request:** src/vs/platform/environment/node/argv.ts registers wait/-w as waiting for files to close, and new-window/-n and reuse-window/-r control window selection; these do not provide originating-application focus restoration. src/vs/code/node/cli.ts creates a wait marker and awaits its deletion or child failure, then completes its callbacks and exits without a focus-return step.
- **macOS launch behavior is not focus restoration:** src/vs/code/node/cli.ts launches through open -n -g on macOS. Its comments explain that background launch avoids transient-instance focusing problems; this concerns initial launch, not reactivating Terminal.app after the waited editor closes.
