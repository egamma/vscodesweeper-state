# Issue #347811 — Preserve the collaborative, in-editor experience: feedback on Local vs. Copilot harness

[https://github.com/microsoft/vscode/issues/347811](https://github.com/microsoft/vscode/issues/347811)

## Summary

Keep open for a product decision about preserving collaborative in-editor workflows. Current Agent Host terminal integration provides partial coverage, but read-only command output and a Windows-excluded experimental terminal override do not satisfy the shared, reusable terminal request.

## Change summary

Preserve human-agent collaboration inside the editor, including shared interactive terminals and session continuity as the Copilot harness evolves.

## Best solution

Define a supported collaborative experience in the editor independently of retaining the Local implementation. Establish which session-owned terminal interactions and cross-window continuity the Copilot harness should provide, then track concrete gaps against that contract.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts`, `src/vs/platform/agentHost/node/copilot/copilotNonPtyShellTerminals.ts`, `src/vs/workbench/contrib/terminal/browser/agentHostOutputChannel.ts`, `src/vs/workbench/contrib/terminal/browser/agentHostPty.ts`
- **Validation:** After agreeing the contract, exercise a Copilot sidebar session running a background service: reveal and scroll its output, interact with or reuse its terminal, and switch or reopen editor windows to verify the agreed process and terminal continuity, including Windows.
- **Behavior:**

  > Users want to collaborate with Copilot in the editor while continuing their own work, rather than only receiving completed task results. The concrete gap is an agent command surface they can reveal, inspect, interact with, and reuse, including background services. Acceptance should cover the supported platforms and explicitly agreed continuity when editor windows change. Retaining Local is one proposed means, not the only acceptable outcome.
- **Trace:**

  > chat.shared.contribution.ts registers chat.agentHost.customTerminalTool.enabled as an experimental opt-in that excludes Windows. NonPtyShellTerminalStreams publishes SDK command output through createOutputTerminal, while AgentHostOutputChannel explicitly remains read-only and creates no ITerminalInstance. AgentHostPty separately supports interactive protocol terminals and attachment with output replay. These paths demonstrate partial infrastructure but do not establish end-to-end shared SDK shell interaction or the requested cross-window lifecycle. The uncertainty is the supported product contract, not merely which helper to use; unrelated terminal-profile or command-output reports do not absorb the full request.
- **Open decisions:**
  - Should the supported collaborative experience be delivered entirely through the Copilot harness, or should a Local-style alternative remain available?
  - Must users be able to type into and reuse the exact shell running agent commands, and what happens when user input overlaps active agent execution?
  - Which terminal processes, output history, and interactive state must remain available when users switch or close editor windows?
