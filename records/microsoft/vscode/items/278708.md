# Issue #278708 — Parallel MCP tools execution triggers multiple oauth logins

[https://github.com/microsoft/vscode/issues/278708](https://github.com/microsoft/vscode/issues/278708)

## Summary

Keep open: startup serialization does not establish that parallel requests share subsequent OAuth or step-up authentication. The maintainers identified this distinction and discussed improvements; current source still exposes separate interactive authentication paths without establishing that the requested coordination is covered.

## Change summary

Coordinate authentication for parallel MCP tool calls so requests needing the same authorization share one login flow.

## Best solution

Provide coordinated, cancellable authentication for concurrent MCP requests requiring equivalent authorization, while retaining parallel tool execution. Settle how cancellation and additional scope challenges affect waiting requests before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostMcp.ts`, `src/vs/workbench/api/browser/mainThreadMcp.ts`, `src/vs/workbench/api/test/common/extHostMcp.test.ts`, `src/vs/workbench/api/test/browser/mainThreadMcp.test.ts`
- **Validation:** Use a controlled OAuth MCP server to exercise concurrent tool calls with fresh authentication and post-start 401 challenges; count interactive authorization starts and verify that equivalent requests resume using one completed authorization. Add focused regression tests in the extHostMcp/mainThreadMcp suites, including cancellation, failed authorization, and differing scope challenges; verify ordinary tool calls remain parallel.
- **Behavior:**

  > Parallel MCP tool calls requiring the same authorization should not make the user complete repeated equivalent OAuth logins. Successful authorization should allow all eligible waiting calls to continue without serializing normal tool execution. Validate both fresh authentication and authorization challenges after the server has started. Waiting requests must have a defined outcome when authorization is cancelled or abandoned, and requests needing different permissions must not silently receive insufficient authorization.
- **Trace:**

  > McpHTTPHandle.send in src/vs/workbench/api/common/extHostMcp.ts queues sends only during Unknown transport mode; established transports send concurrently. _fetchWithAuthRetry handles challenges and calls _addAuthHeader, which reaches MainThreadMcp.$getTokenFromServerMetadata and _getSessionForProvider in src/vs/workbench/api/browser/mainThreadMcp.ts. The latter reads sessions before prompting and creating one, with no shared in-flight operation in that method; AuthenticationService.createSession delegates to the provider, so provider behavior remains a reproduction dependency. The maintainer distinguished startup from step-up authentication at https://github.com/microsoft/vscode/issues/278708#issuecomment-3648518375. Preserve parallel tools, server-specific consent, account selection, resource boundaries, and scope correctness. Existing agent-host authentication UI does not by itself prove this transport path is covered. Begin with a controlled fresh-login and post-start challenge reproduction rather than treating existing-account selection as equivalent.
- **Open decisions:**
  - When a shared login is cancelled or abandoned, should all waiting tool calls fail together, or remain pending behind an explicit retry action?
  - If concurrent calls challenge for different additional scopes, should the user authorize their combined permissions once, or complete separate permission-specific flows?
