# Issue #278708 — Parallel MCP tools execution triggers multiple oauth logins

[https://github.com/microsoft/vscode/issues/278708](https://github.com/microsoft/vscode/issues/278708)

## Summary

Keep open: startup serialization and provider-operation queues do not establish that parallel tool requests share one interactive OAuth login. Maintainers have accepted investigating this improvement, and cancellation behavior still needs a product decision.

## Change summary

Coordinate parallel MCP tool authentication so equivalent requests share one OAuth login and reuse its resulting token.

## Best solution

Equivalent authentication requests for the same MCP server should share one cancellable sign-in while ordinary tool execution remains parallel. Define how waiting calls recover from cancellation and how differing scope requirements are presented before implementing the coordination.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostMcp.ts`, `src/vs/workbench/api/browser/mainThreadMcp.ts`, `src/vs/workbench/api/common/extHostAuthentication.ts`, `src/vs/workbench/api/test/common/extHostMcp.test.ts`, `src/vs/workbench/api/test/browser/mainThreadMcp.test.ts`
- **Validation:** Add focused MCP transport/authentication tests issuing simultaneous calls against an established connection with no usable session or a scope-step-up challenge. For equivalent authentication requirements, assert one interactive login and successful completion of every waiting call using the resulting session; verify cancellation releases callers without unsolicited repeat logins and authenticated tool calls remain concurrent. Run the relevant suites with ./scripts/test.sh --run src/vs/workbench/api/test/common/extHostMcp.test.ts --run src/vs/workbench/api/test/browser/mainThreadMcp.test.ts. Also exercise fresh OAuth against a controlled server rather than an already signed-in account.
- **Behavior:**

  > Parallel MCP tool calls requiring equivalent authentication should present one OAuth login, not a succession of logins, and waiting calls should continue using the resulting session. Already authenticated calls must remain parallel. Acceptance must cover both missing usable credentials and authentication requested by an established server, including scope step-up. Cancellation must leave the workflow recoverable without trapping waiting calls; behavior for differing scope requirements and automatic retries needs maintainer agreement.
- **Trace:**

  > McpServer.start in src/vs/workbench/contrib/mcp/common/mcpServer.ts serializes startup, but McpHTTPHandle.send in src/vs/workbench/api/common/extHostMcp.ts bypasses its request sequencer once the transport mode is established. Each request traverses _addAuthHeader and _fetchWithAuthRetry, which can request credentials again for changed scopes or failed authorization. MainThreadMcp._getSessionForProvider in src/vs/workbench/api/browser/mainThreadMcp.ts reads available sessions before interactive consent and session creation. ExtHostAuthentication.$createSession serializes provider calls in src/vs/workbench/api/common/extHostAuthentication.ts, but DynamicAuthProvider.createSession still initiates a new flow for each creation request; serialization alone is not result sharing. Preserve provider/account/resource isolation, scope consent, and ordinary parallel tool execution. The source establishes a coordination gap worth investigating, not a runtime reproduction of every reported trigger. The maintainer discussion at https://github.com/microsoft/vscode/issues/278708#issuecomment-3648519994 and https://github.com/microsoft/vscode/issues/278708#issuecomment-3648529532 leaves cancellation and interaction presentation unresolved.
- **Open decisions:**
  - When the shared sign-in is cancelled or abandoned, should all waiting tool calls fail together and require an explicit retry, or should they return to individually actionable chat confirmations?
  - When parallel tools require different additional scopes, should the user authorize their combined requirements in one interaction or receive separate scope-specific confirmations?
