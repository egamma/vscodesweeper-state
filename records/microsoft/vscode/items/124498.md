# Issue #124498 — Components that offer to open an editor should specify the `override` that makes most sense

[https://github.com/microsoft/vscode/issues/124498](https://github.com/microsoft/vscode/issues/124498)

## Summary

The underlying editor-opening policy remains unresolved: notebook Outline now preserves its editor type, but Search and Problems still pass a resource and selection without an explicit override. A maintainer-requested UX decision is still needed before auditing and aligning the affected components.

## Change summary

Require UI components that open resources to deliberately choose the appropriate editor override instead of accidentally inheriting the user's default editor.

## Best solution

Define a consistent policy for location-based navigation, then audit Outline, Search, Problems, and similar components so each deliberately preserves the originating editor or chooses an editor capable of honoring the requested location. Do not restore the global CodeEditorService override suppression that caused the `vscode.open` regression.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/notebook/browser/contrib/outline/notebookOutline.ts`, `src/vs/workbench/contrib/codeEditor/browser/outline/documentSymbolsOutline.ts`, `src/vs/workbench/contrib/search/browser/searchView.ts`, `src/vs/workbench/contrib/markers/browser/markersView.ts`, `src/vs/workbench/services/editor/browser/codeEditorService.ts`
- **Validation:** Add focused component tests using a resource whose configured default is a custom editor: notebook Outline must retain its notebook editor, and Search/Problems must exhibit the maintainer-selected behavior while preserving the requested selection whenever the target editor supports it; also retain coverage that `vscode.open` resolves the configured default editor.
- **Behavior:**

  > Editor-opening workbench components must select an editor intentionally rather than inheriting resolver behavior accidentally. Notebook Outline must continue revealing entries in the originating notebook editor. For Search, Problems, and other location-based navigation, the chosen editor must follow one consistent maintainer-approved policy and handle the requested location as far as its contract permits. `vscode.open` must continue resolving the user's configured default editor.
- **Trace:**

  > NotebookOutline.reveal in src/vs/workbench/contrib/notebook/browser/contrib/outline/notebookOutline.ts already passes the active input's `editorId`. DocumentSymbolsOutline.reveal delegates to CodeEditorService, while SearchView.open and MarkersView.openFileAtElement pass resource-plus-selection inputs without overrides. CodeEditorService currently forwards these requests to EditorService; globally forcing a text override there previously caused the regression documented at https://github.com/microsoft/vscode/issues/128756, so that behavior must not be reintroduced. The newer reports https://github.com/microsoft/vscode/issues/336059 and https://github.com/microsoft/vscode/issues/289785 confirm remaining Search/custom-editor consequences but are narrower than this policy audit.
- **Open decisions:**
  - When Search or Problems opens a text location whose configured default is a custom editor, should navigation force the default text editor so the range is revealed, or honor the custom editor even when it cannot consume the location?
  - Should location-based components apply one uniform policy, or may specific surfaces such as Search deliberately differ from Outline and Problems based on their user intent?

## Evidence

- **partial adoption on main:** src/vs/workbench/contrib/notebook/browser/contrib/outline/notebookOutline.ts:739-750 explicitly passes `override: this._editor.input?.editorId`, preserving the active notebook editor when revealing an outline entry.
- **remaining source gap:** src/vs/workbench/contrib/search/browser/searchView.ts:2240-2256 and src/vs/workbench/contrib/markers/browser/markersView.ts:300-318 open a resource with a target selection but no `override`, so editor resolution still follows the configured default editor.
- **centralized fix remains unsafe:** src/vs/workbench/services/editor/browser/codeEditorService.ts:90-126 forwards its input to IEditorService without forcing an override. https://github.com/microsoft/vscode/issues/128756 documents that globally disabling overrides there broke `vscode.open`, and the attempted change was reverted.
- **current observable symptom:** https://github.com/microsoft/vscode/issues/336059 reports on current VS Code that clicking a Search match opens the default Markdown Preview without revealing the match, confirming that a concrete instance of this policy gap remains.
- **related API limitation:** https://github.com/microsoft/vscode/issues/289785 tracks the narrower custom-editor selection/range API gap. It is newer than this re-reviewed issue and does not absorb the broader component-policy work, so it is related rather than a valid duplicate canonical.
- **maintainer direction:** The issue discussion explicitly calls for a UX decision, and a maintainer later suggested using per-editor `editorId` while noting that CodeEditorService cannot serve as the centralized enforcement point.
