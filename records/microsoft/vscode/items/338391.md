# Issue #338391 — Agents window: automation target silently reverts from "Use Dev Container" to "Use Remote Host"

[https://github.com/microsoft/vscode/issues/338391](https://github.com/microsoft/vscode/issues/338391)

## Summary

Confirmed structural gap from source: `AutomationTarget` has no slot for a dev-container relay, so a dev container selection silently degrades to the plain WSL/remote folder target with no warning — exactly as the reporter's own analysis traced it. This needs a maintainer decision on whether to build persistence support or fail loudly in the picker, so keep-open with a plan brief rather than an immediate fix.

## Change summary

Selecting 'Use Dev Container' as an Automation's target silently reverts to 'Use Remote Host' on save, with no persisted dev-container state and no warning.

## Best solution

Either extend AutomationTarget/AutomationWorkspaceIsolation to name a dev-container relay so AgentHostAutomationStore can invoke devcontainer up/exec at trigger time, or — more cheaply — make the automation target picker/validation (automationDialog.ts, sessionsManagementService.isNewSessionTargetAvailable) recognize and reject/hide dev-container selections instead of silently discarding them.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/automations/automation.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/agentHostAutomationStore.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/devContainerAgentHostSessionsProvider.ts`, `src/vs/sessions/contrib/automations/browser/automationDialog.ts`
- **Validation:** An automation-store test asserting that saving an automation with a dev-container-selected target either round-trips the dev-container intent (if supported) or is rejected/blocked at save time with a surfaced validation error (if not supported) — never silently substitutes a different target.
- **Behavior:**

  > Creating or editing an Automation whose target is 'Use Dev Container' must not silently change to 'Use Remote Host'. Either (a) the dev-container selection is persisted and honored on every scheduled run — the run resolves/starts the dev container the same way a manual session would — or (b) the target picker disables/hides the dev-container option for automations, or the save path surfaces an explicit validation error explaining it isn't supported yet. Reopening the automation's configuration must show exactly what was chosen, and re-saving must not silently drop it.
- **Trace:**

  > AutomationTarget (src/vs/workbench/contrib/chat/common/automations/automation.ts, lines ~39-52) only models {providerId, folderUri, isolation, sessionTypeId} — there is no field representing a dev-container relay. AgentHostAutomationStore._projectTarget (src/vs/sessions/contrib/providers/agentHost/browser/agentHostAutomationStore.ts) constructs the persisted target purely from providerId+folderUri, so any dev-container selection collapses to the plain remote folder target. Dev-container enablement itself is tracked only per live session id (_devContainerDrafts/_enableDevContainer/isDevContainerEnabled in devContainerAgentHostSessionsProvider.ts) — there is no static identity to serialize today. The open question — extend the target schema and the AgentHost's automation runner to invoke devcontainer exec at trigger time, versus reject/hide the option in automationDialog.ts's target picker and isNewSessionTargetAvailable validation — is a product/design call, not an implementation detail; do not guess at a schema shape without maintainer sign-off given the cross-cutting relay lifecycle (5-minute idle timeout, ephemeral spawn) the reporter documented.
- **Open decisions:**
  - Should Automations support dev-container targets at all (persist a relay identity and have the owning agent host invoke devcontainer up/exec at trigger time), or should the picker simply disallow/hide the dev-container option for automations for now?
  - If unsupported for now, should the target picker hide 'Use Dev Container' entirely for automations, or allow the selection but block save with an explicit validation error?
  - If supported, what does the persisted target schema look like given the relay is ephemeral and lacks a durable provider identity today?

## Evidence

- **AutomationTarget has no dev-container field:** src/vs/workbench/contrib/chat/common/automations/automation.ts lines 39-52 define AutomationTarget as {kind:'workspace', folderUri, providerId?, sessionTypeId?, isolation} | {kind:'quickChat', providerId, sessionTypeId} — no dev-container/relay concept anywhere in the persisted shape.
- **dev-container-ness is per-session, not persistable:** src/vs/sessions/contrib/providers/agentHost/browser/devContainerAgentHostSessionsProvider.ts tracks enablement via in-memory _devContainerDrafts/_enableDevContainer(sessionId)/isDevContainerEnabled(sessionId) keyed by live session id, confirming there is no static target representation the automation store could serialize.
- **automation projection only round-trips providerId/folderUri:** src/vs/sessions/contrib/providers/agentHost/browser/agentHostAutomationStore.ts _projectTarget() builds AutomationTarget purely from providerId + folderUri + isolation, matching the reporter's observation that the persisted target regresses to a plain file: folder under the WSL authority.
