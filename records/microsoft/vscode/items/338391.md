# Issue #338391 — Agents window: automation target silently reverts from "Use Dev Container" to "Use Remote Host"

[https://github.com/microsoft/vscode/issues/338391](https://github.com/microsoft/vscode/issues/338391)

## Summary

The automation dialog still exposes the shared Dev Container selection without carrying that choice into its saved execution target. Keep this open: the source confirms the silent-loss path, and no verified canonical or landed fix was found.

## Change summary

Prevent an automation's Dev Container selection from silently becoming a remote-host execution target after saving.

## Best solution

Make the automation target picker truthful: either preserve and execute a supported container target or explicitly prevent unsupported container selection. Decide that product boundary before extending persistence and host execution; ordinary manually created container sessions must remain supported.

- **Behavior:**

  > Selecting Use Dev Container for an automation must never silently save a plain remote-host target. If supported, reopening must retain the selection and scheduled runs must execute inside the intended container, including after an earlier relay has exited. If unsupported, the automation UI must clearly communicate that limitation before a misleading save is possible. Ordinary remote-host automations and manually created Dev Container sessions must retain their existing behavior.
- **Trace:**

  > The shared SessionWorkspacePicker exposes container-mode actions and emits onDidSelectWorkspaceMode, whereas automationDialog.ts consumes only onDidSelectWorkspace and builds its target from folder, provider, session type, and isolation. Its inherited submenu therefore offers a choice that the automation target construction does not encode. DevContainerAgentHostSessionsProvider stores ordinary draft selection in transient sets and performs container handoff during prepareNewSession; BaseAgentHostSessionsProvider.getAutomationSessionConfiguration does not capture that state. This confirms the selection-loss boundary without executing the application. The remaining uncertainty is whether automation container execution should become a durable supported capability or remain explicitly unavailable. Keep manual session handoff and provider-neutral routing intact; do not treat an ephemeral relay as a durable scheduler. Related open PR https://github.com/microsoft/vscode/pull/335595 explicitly leaves transient container handoff outside its template changes.
- **Open decisions:**
  - Should automations support durable Dev Container execution now, including container startup at trigger time, or explicitly disallow container targets while retaining ordinary remote-host scheduling?
