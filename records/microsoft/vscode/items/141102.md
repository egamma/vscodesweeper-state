# Issue #141102 — problemMatcher is too complicated and should be modernised

[https://github.com/microsoft/vscode/issues/141102](https://github.com/microsoft/vscode/issues/141102)

## Summary

Keep this accepted tasks request open: current source still couples background readiness to problem matchers and requires both begin and end patterns. The older related issue covers task-level watching configuration, but does not clearly own this request's additional completion-only watch semantics.

## Change summary

Allow task-level background monitoring without a diagnostic problem matcher, and allow completion-only output when activeOnStart is true.

## Best solution

Provide an independent, backward-compatible task readiness configuration for watchers that do not produce diagnostics or begin messages. Coordinate the task-level configuration with the older related issue, while explicitly defining what completion-only monitoring means for subsequent rebuilds.

- **Behavior:**

  > A watcher should be configurable for readiness without pretending to match diagnostic output or inheriting an unrelated TypeScript matcher. When activeOnStart is true, a watcher that emits only a completion message should not require a begin pattern to release the initial preLaunchTask wait. Existing problemMatcher-based configurations must remain compatible. Acceptance must cover initial readiness, subsequent completion messages under the agreed contract, and unchanged behavior for watchers with explicit begin/end output.
- **Trace:**

  > The task schema in src/vs/workbench/contrib/tasks/common/jsonSchema_v2.ts exposes isBackground but leaves readiness patterns inside problemMatcher; taskConfiguration.ts parses task configuration. ProblemMatcherParser.addWatchingMatcher in common/problemMatcher.ts rejects end-only monitoring regardless of activeOnStart. WatchingProblemCollector in common/problemCollectors.ts activates on startup or begin matches and deactivates on end matches, so subsequent silent rebuilds have no observable activation signal. DebugTaskRunner in src/vs/workbench/contrib/debug/browser/debugTaskRunner.ts waits for an inactive task event before launching. The older https://github.com/microsoft/vscode/issues/6209 establishes maintainer interest in task-level patterns but does not settle completion-only cycles. Preserve diagnostic matching, legacy background/watching configuration and existing debugger readiness guarantees; do not expand this into the separate completely silent fire-and-forget task request.
- **Open decisions:**
  - Without a begin signal, should completion-only monitoring describe initial readiness only, or also publish subsequent rebuild completions; if the latter, what busy/readiness state should dependent launches observe between completion messages?
  - If a task supplies both independent task-level monitoring and legacy problemMatcher.background monitoring, which configuration governs readiness, or should that combination be rejected?

## Evidence

- **Existing capability does not cover the request:** src/vs/workbench/contrib/tasks/common/jsonSchema_v2.ts exposes isBackground and problemMatcher as task properties, but no independent background monitoring object. src/vs/workbench/contrib/tasks/common/problemMatcher.ts registers background under the problem matcher; isBackground alone does not supply readiness detection.
- **Begin pattern remains required:** ProblemMatcherParser.addWatchingMatcher in src/vs/workbench/contrib/tasks/common/problemMatcher.ts constructs internal.watching only when both beginsPattern and endsPattern parse successfully. Supplying an end pattern alone reports 'A problem matcher must define both a begin pattern and an end pattern for watching', even with activeOnStart: true.
- **Repeated-cycle semantics need a decision:** WatchingProblemCollector.aboutToStart, tryBegin and tryFinish in src/vs/workbench/contrib/tasks/common/problemCollectors.ts track active matchers. activeOnStart activates the initial cycle; tryFinish removes that active state, and subsequent activation depends on a begin match. Merely accepting an omitted beginsPattern would not establish when later silent rebuilds become busy.
- **Debugger integration:** src/vs/workbench/contrib/debug/browser/debugTaskRunner.ts waits for TaskEventKind.Inactive for background preLaunchTask readiness. A running background process is not equivalent to a completed initial build, so modernization must preserve that distinction.
- **Older related issue is partial overlap:** https://github.com/microsoft/vscode/issues/6209 is currently open. Maintainer comments https://github.com/microsoft/vscode/issues/6209#issuecomment-289412206 and https://github.com/microsoft/vscode/issues/6209#issuecomment-350994475 explicitly support task-level watching patterns, but retain begin/end regular expressions. Its verified scope does not clearly absorb the additional request to omit beginsPattern for completion-only watchers.
