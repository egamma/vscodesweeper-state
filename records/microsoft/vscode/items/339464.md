# Issue #339464 — Agent Host: pluggable session isolation (non-Git VCS and custom worktree providers)

[https://github.com/microsoft/vscode/issues/339464](https://github.com/microsoft/vscode/issues/339464)

## Summary

Fresh, well-reasoned architecture proposal (0 days old, no traction yet) to make Agent Host session isolation pluggable beyond Git worktrees; the gap is real in the current code, but this is a design decision for the Agent Host owners, not something to triage-close or auto-implement yet.

## Change summary

Agent Host 'worktree' isolation mode is hard-coded to Git; add a pluggable isolation provider model (settings-based commands and/or an extension API) so non-Git VCS and custom isolation mechanisms can participate.

## Best solution

Agent Host maintainers should decide the extension point shape (settings-based external command vs. an SCM-style extension API) before any implementation; in the meantime this stays open as a design proposal, possibly consolidated with related session-isolation requests (#334727, #337350, #321685) once a direction is picked.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/shared/worktreeIsolation.ts`, `src/vs/platform/agentHost/common/sessionConfigKeys.ts`, `src/vs/platform/agentHost/common/agentHostGitService.ts`
- **Validation:** A new isolation provider (e.g. a trivial no-op or filesystem-copy provider) can be registered and selected for session creation, and sessions created through it support create/remove without going through git worktree add/remove.
- **Behavior:**

  > Session isolation 'worktree' mode should not be exclusively Git-based: a pluggable provider contract (create/remove, optional status/changes) should let non-Git VCS or custom isolation mechanisms supply a session working directory, selectable alongside Folder and Worktree in the isolation picker and via create_remote_session's workspace.isolation.
- **Trace:**

  > Current isolation is a closed SessionConfigKey.Isolation enum ('folder' | 'worktree'); worktree creation/removal in worktreeIsolation.ts calls IAgentHostGitService directly (git worktree add/remove, branch naming via agentBranchNameGenerator.ts). The boundary: whatever design is chosen should keep the existing Git worktree path working as the built-in default and not regress folder-mode behavior. Where uncertainty starts: whether the extension point is a settings-driven external command (works uniformly across local/remote/SSH/WSL hosts) or an SCM-extension-style API (richer but extension-host-only), and what the create/remove/status contract looks like.
- **Open decisions:**
  - Settings-based external command provider, an extension API, or both?
  - What is the exact create/remove/status JSON contract and how are errors surfaced to the session UI?
  - Should custom providers be usable from remote Agent Hosts (SSH/tunnels/WSL) from day one, or is that a follow-up?
