# Issue #134455 — Consider a "test-adapter-protocol" that maps onto the new testing APIs

[https://github.com/microsoft/vscode/issues/134455](https://github.com/microsoft/vscode/issues/134455)

## Summary

Keep open: the current testing API and internal extension-host RPC do not provide the requested editor-independent test adapter protocol. A maintainer explicitly supported pursuing this direction, and no verified canonical issue or implementing fix was found.

## Change summary

Define a reusable testing protocol so language tools can implement discovery and execution outside a TypeScript extension and share that integration across editors.

## Best solution

Design a public, editor-independent protocol mapped to the testing API, with an initial client and an external adapter demonstrating interoperability. Settle the initial protocol scope and its relationship to DAP before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTesting.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`
- **Validation:** The plan should specify an interoperability check using an external test adapter and a VS Code client: discover a test hierarchy, request a selected test run, report outcomes, and verify cancellation. Establish executable protocol conformance checks for the agreed initial contract.
- **Behavior:**

  > Language tooling should be able to provide testing integration from another process through a documented, editor-independent protocol rather than implementing VS Code API translation separately in every extension. The resulting VS Code experience should retain test discovery, selected execution and result reporting. Acceptance should demonstrate an external adapter serving these operations through a reusable client, with cancellation and identity semantics explicitly covered.
- **Trace:**

  > The public testing entry point is tests.createTestController in src/vscode-dts/vscode.d.ts. ExtHostTesting.createTestController in src/vs/workbench/api/common/extHostTesting.ts constructs extension-owned objects and forwards changes to VS Code through internal RPC; ExtHostTestingShape in src/vs/workbench/api/common/extHost.protocol.ts describes the reverse execution and discovery calls. That RPC models useful operations but is not evidence of a supported public adapter protocol. The reporter's Dart integration forwards custom runner events through DAP and translates them in the extension, which remains a workaround rather than the requested shared contract. Maintainer support is recorded at https://github.com/microsoft/vscode/issues/134455#issuecomment-936515816. Preserve existing extension APIs and integrations; uncertainty begins at the public protocol's initial scope, compatibility guarantees and relationship to DAP.
- **Open decisions:**
  - Should the public testing contract be independent of DAP, with optional forwarding through it, or explicitly extend DAP?
  - Which testing operations are required in the initial interoperable contract, and which are negotiated optional capabilities?
  - What compatibility and version-negotiation guarantees should independent editor clients and language-tool adapters receive?
