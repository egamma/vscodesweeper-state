# Issue #336200 — Renderer OOM in JSON.stringify / serializeRequestArguments when invoking agent with large chat history

[https://github.com/microsoft/vscode/issues/336200](https://github.com/microsoft/vscode/issues/336200)

## Summary

Well-documented renderer OOM with a crash dump whose V8 stack (serializeRequestArguments/_remoteCall/invokeAgent) matches real code in chatServiceImpl.ts; no bound exists today on the result/metadata forwarded into agent-invocation history, and no fix has landed on main. Related issue #337688 is a newer report (higher issue number filed after this one), so the re-reviewed duplicate bar isn't met — this stays open as the earlier report.

## Change summary

A renderer OOMs during JSON.stringify of RPC arguments when invoking a chat agent with a very large (hundreds-of-MB) restored chat history, because unbounded prior tool-result metadata is forwarded into the invocation history.

## Best solution

Bound or externalize the `result` metadata forwarded per history entry in ChatServiceImpl.getHistoryEntriesFromModel (chatServiceImpl.ts) and/or truncate large tool-result payloads before they are retained in session history, so a single agent invocation's RPC argument size cannot approach the renderer's heap limit.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts`, `src/vs/workbench/services/extensions/common/rpcProtocol.ts`
- **Validation:** A test that builds a chat session with an oversized tool-result payload in `result.metadata`, invokes an agent, and asserts the serialized invocation history stays under an agreed size bound instead of forwarding the full payload.
- **Behavior:**

  > Restoring and continuing a very large chat session (hundreds of MB, many tool calls with multi-megabyte results) must not let a single agent invocation's serialized RPC arguments grow unbounded to the point of renderer OOM. Either the retained history is capped/streamed/externalized, or an oversized invocation fails with a recoverable error instead of taking down the whole renderer. Acceptance: a history-size test (see validation) passes, and normal small-history invocations are unaffected.
- **Trace:**

  > ChatServiceImpl.getHistoryEntriesFromModel (src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:2264) builds each IChatAgentHistoryEntry with `result: request.response.result ?? {}`, with no size check; this array is passed to `$invokeAgent(handle, request, { history, ... })`, which the extension-host RPC layer (src/vs/workbench/services/extensions/common/rpcProtocol.ts) serializes via JSON.stringify — matching the reporter's crash stack (serializeRequestArguments/_remoteCall/invokeAgent). Do not touch the response-content filtering (toChatHistoryContent) which already excludes tool-invocation display entries; the gap is specifically in forwarded `result` metadata. Related: https://github.com/microsoft/vscode/issues/311225 (chat memory growth), https://github.com/microsoft/vscode/issues/332725 (concurrent-session OOM), https://github.com/microsoft/vscode/issues/337688 (newer, similar agent-host OOM).
- **Open decisions:**
  - Should oversized result metadata be truncated/summarized when forwarded into history, streamed/externalized out of the RPC payload, or should the invocation instead fail with a recoverable error above some size threshold?
  - Where should the size limit live — per-entry, per-invocation total, or per-field (e.g. only `result.metadata`) — and what is an acceptable default cap?
  - Does bounding history change extension-facing behavior (agents seeing truncated context) in a way that needs to be documented or made configurable?
