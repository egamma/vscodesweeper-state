# Issue #336200 — Renderer OOM in JSON.stringify / serializeRequestArguments when invoking agent with large chat history

[https://github.com/microsoft/vscode/issues/336200](https://github.com/microsoft/vscode/issues/336200)

## Summary

A well-diagnosed but unconfirmed-reproducible crash: the reporter's crash-dump stack (serializeRequestArguments → JSON.stringify) matches current main's RPC serialization path in rpcProtocol.ts, and getHistoryEntriesFromModel in chatServiceImpl.ts confirms the whole chat history (including prior tool-result metadata) is forwarded unbounded on every agent invocation. This is a real, still-open gap, not something already fixed; keeping open pending a bounding/streaming design.

## Change summary

Renderer OOMs during JSON.stringify of RPC arguments when invoking a chat agent with a very large accumulated chat history (hundreds of MB across many requests/tool results).

## Best solution

Bound or externalize large retained chat history/tool-result metadata before it is forwarded through RPCProtocol.serializeRequestArguments — e.g. truncating/streaming oversized tool results or capping history size sent per invocation — likely spanning src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts (getHistoryEntriesFromModel) and src/vs/workbench/services/extensions/common/rpcProtocol.ts.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts`, `src/vs/workbench/services/extensions/common/rpcProtocol.ts`
- **Validation:** A regression test that builds a chat history entry list far exceeding a chosen size threshold and asserts the forwarded/serialized history stays under a bound (or is rejected gracefully) rather than growing unbounded.
- **Behavior:**

  > When accumulated chat history (including retained tool-result text/metadata) is very large, invoking an agent must not risk an unbounded JSON.stringify allocation that can OOM the renderer. Large history should be bounded, truncated, or streamed, or the invocation should fail with a recoverable error instead of terminating the renderer. Acceptance: a history far exceeding the chosen size bound no longer produces an unbounded serialization payload in tests.
- **Trace:**

  > getHistoryEntriesFromModel (src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:2218) builds an IChatAgentHistoryEntry per prior request/response with no size cap, including forwarded result metadata; this history is passed into $invokeAgent and ultimately serialized whole via RPCProtocol.serializeRequestArguments → JSON.stringify (src/vs/workbench/services/extensions/common/rpcProtocol.ts:475,731), matching the reported crash stack. Do not change the response-history filtering that already excludes toolInvocation/toolInvocationSerialized display entries, and do not alter unrelated RPC argument types (VSBuffer/SerializableObjectWithBuffers) paths. Where the uncertainty starts: whether bounding happens by capping/truncating history entries, dropping/summarizing oversized tool-result metadata, or chunking/streaming the RPC payload — each has different user-visible effects on what the agent sees as history. Related: https://github.com/microsoft/vscode/issues/311225 and https://github.com/microsoft/vscode/issues/332725 report similar chat memory/OOM symptoms but without this specific RPC-serialization stack confirmed.
- **Open decisions:**
  - Should the fix truncate/drop older or oversized history entries (changing what the agent can see), or instead stream/chunk the RPC payload so full history is preserved but never fully materialized at once?
  - If a size bound is hit, should the invocation proceed with reduced history, or fail with a recoverable error surfaced to the user?
