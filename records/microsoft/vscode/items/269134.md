# Issue #269134 — Tool references in prompts: support `extensionId/*`

[https://github.com/microsoft/vscode/issues/269134](https://github.com/microsoft/vscode/issues/269134)

## Summary

A real gap remains on current main: extension tool sets are not serialized with the requested `extensionId/*` form, and the synthesized extension-wide set is omitted when an extension contributes explicit tool sets. This team-authored Backlog request should remain open while those public reference semantics are decided.

## Change summary

Represent all tools contributed by an extension with an `extensionId/*` reference in prompt and mode tool selections, matching MCP wildcard references.

## Best solution

Provide a stable extension-wide aggregate reference whose canonical prompt serialization is `extensionId/*`, while preserving individual tool and explicitly contributed tool-set references and defining compatibility for the currently accepted bare extension identifier.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/tools/languageModelToolsContribution.ts`, `src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts`, `src/vs/workbench/contrib/chat/test/browser/tools/languageModelToolsService.test.ts`
- **Validation:** Extend the language-model tools service tests to assert that an extension-wide set resolves and round-trips as `extensionId/*`, includes every tool contributed by that extension, and does not alter individual or explicit tool-set references.
- **Behavior:**

  > Prompt and mode tool selections can represent every tool contributed by an extension with `extensionId/*`, matching the wildcard form used for MCP servers. The reference resolves back to the extension-wide collection and round-trips through selection serialization. Individual extension tool references and explicitly contributed tool-set references continue to work. Acceptance must cover extensions both with and without explicit `languageModelToolSets` contributions.
- **Trace:**

  > Tool registration is handled by LanguageModelToolsExtensionPointHandler in src/vs/workbench/contrib/chat/common/tools/languageModelToolsContribution.ts. It currently creates a synthetic per-extension ToolSet only when the extension contributes no explicit tool sets, using the extension identifier as the bare reference name. LanguageModelToolsService in src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts computes full reference names, and getToolSetFullReferenceName currently reserves the `/*` suffix for MCP sources. Selection serialization already delegates to getFullReferenceName, so its behavior follows that naming decision. Keep individual qualified tool names and explicit tool-set behavior intact; do not broaden the change into tool invocation or picker redesign. https://github.com/microsoft/vscode/issues/271086 is a newer, closed related request that explicitly points back to this issue.
- **Open decisions:**
  - Should `extensionId/*` aggregate every tool from the extension even when the extension also contributes one or more explicit `languageModelToolSets`, or only tools not covered by those sets?
  - Should the currently recognized bare extension identifier remain as a compatibility alias after `extensionId/*` becomes the canonical serialized reference?
