# Issue #153478 — Starting to debug should be snappier

[https://github.com/microsoft/vscode/issues/153478](https://github.com/microsoft/vscode/issues/153478)

## Summary

The startup feedback remains staggered on current main: debug enters an initializing state immediately, but the Debug view and status-bar styling still wait until after configuration resolution and the pre-launch task. No older canonical issue or active fixing PR was found, so this remains useful debug-startup polish.

## Change summary

Make the debug toolbar, selected-target control, Debug view, and debug status styling appear together immediately after F5, including while a pre-launch task is running.

## Best solution

Give debug startup one coherent optimistic visual transition when initialization begins, while preserving explicit run-without-debugging and UI-suppression behavior. The debug area should first settle those boundary semantics and add coverage for initialization before changing the sequencing.

- **Behavior:**

  > After the user starts debugging, all approved debug-start visual feedback appears as one coherent transition without waiting for a slow pre-launch task. The feedback remains visible while initialization is pending and returns cleanly to the inactive state if startup fails. Explicit run-without-debugging and suppression options continue to produce the behavior selected by the maintainer.
- **Trace:**

  > DebugService.startDebugging in src/vs/workbench/contrib/debug/browser/debugService.ts enters State.Initializing before extension activation and the preLaunchTask. DebugToolBar already reacts to that state, while doCreateSession opens the Debug view only after runTaskAndCheckErrors and StatusBarColorProvider explicitly excludes State.Initializing. The existing status-bar assertion is in src/vs/workbench/contrib/debug/test/browser/baseDebugView.test.ts. Keep adapter launch, task execution, error handling, and established suppression settings outside the behavioral change; the uncertainty is limited to which optimistic visuals apply before the resolved session configuration is available.
- **Open decisions:**
  - Should the orange debug status styling represent an attempted debug startup during State.Initializing, or only a successfully created debug session?
  - When the resolved configuration later specifies noDebug, suppressDebugView, or suppressDebugStatusbar, should optimistic startup feedback be withheld, shown briefly and withdrawn, or limited to signals known before configuration resolution?
