# Issue #153478 — Starting to debug should be snappier

[https://github.com/microsoft/vscode/issues/153478](https://github.com/microsoft/vscode/issues/153478)

## Summary

Keep open: current debug startup still separates initialization feedback from session-dependent UI updates, leaving the reported staggered transition unresolved. Existing settings control visibility and placement, not a coordinated startup transition.

## Change summary

Make debug startup feedback appear promptly and coherently instead of revealing the toolbar, Debug view, session selector, and status color in separate stages.

## Best solution

Provide coherent startup feedback while pre-launch work runs, without waiting for successful adapter startup. Preserve configured visibility, suppressed UI, and run-without-debug behavior, and restore the appropriate state when startup fails or is cancelled.

- **Behavior:**

  > Starting debugging should give prompt, coherent feedback rather than a sequence of visibly separated UI changes while pre-launch dependencies run. The report specifically includes toolbar appearance, Debug view opening, multi-target selector appearance, and status coloring. Acceptance should cover delayed pre-launch work, multi-target launches, failure, and cancellation while honoring explicit visibility settings and run-without-debug behavior.
- **Trace:**

  > DebugService.startDebugging enters initialization early, but createSession awaits preLaunchTask before doCreateSession registers a session and opens the Debug view. Multi-session view is enabled after launchOrAttachToSession, the toolbar selector depends on CONTEXT_MULTI_SESSION_DEBUG, and isStatusbarInDebugMode explicitly rejects State.Initializing. DebugToolBar independently schedules updates and checks actual sessions for toolbar suppression. This establishes separate milestones, not measured runtime latency. The remaining design work is to determine how pending launch information can support coherent feedback before actual sessions exist, including asynchronously resolved configurations and compound launches. Preserve trust checks, task execution, adapter sequencing, existing visibility policies, and session suppression; do not treat faster pre-launch task execution as satisfying the UI request.
