# Issue #306090 — Copilot CLI: Allow tool confirmations for specific arguments

[https://github.com/microsoft/vscode/issues/306090](https://github.com/microsoft/vscode/issues/306090)

## Summary

Keep open: argument-specific approval infrastructure exists in ordinary Chat, but Copilot CLI's host-side confirmation flow still remembers tool names rather than tool-and-argument combinations. This team-authored Backlog item tracks adoption, not another copy of the underlying API proposal.

## Change summary

Allow Copilot CLI users to remember approval for a specific tool-and-argument combination without approving every invocation of that tool.

## Best solution

Deliver argument-scoped approval in Copilot CLI sessions, using the existing combination-approval semantics where applicable and preserving runtime-managed restrictions. First establish which CLI tool categories participate and how approval scope maps onto host-backed sessions.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/sessionPermissions.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/stateToProgressAdapter.ts`, `src/vs/workbench/contrib/chat/browser/tools/languageModelToolsConfirmationService.ts`
- **Validation:** Add targeted approval tests demonstrating that remembering tool T with arguments A permits a later matching invocation, while T with different arguments B and another tool with arguments A still require confirmation. Exercise the selected approval lifetime, revocation, and managed-approval restrictions, then manually verify the combination choice in a Copilot CLI session.
- **Behavior:**

  > Copilot CLI users should be able to remember approval for a particular tool-and-argument combination rather than granting permission to every use of the tool. Matching subsequent invocations should honor that approval within its selected scope; different arguments must remain subject to confirmation unless independently approved. The UI must identify what combination and scope are being approved. Managed restrictions must remain authoritative, and existing one-time and whole-tool choices must retain their behavior.
- **Trace:**

  > The request adopts the behavior described in https://github.com/microsoft/vscode/issues/302393, whose API implementation is represented by https://github.com/microsoft/vscode/pull/302395. Ordinary Chat exposes approveCombination in languageModelToolsService.ts and stores keyed approvals in LanguageModelToolsConfirmationService. CopilotAgentSession._handlePermissionRequest emits host-side pending confirmations, while SessionPermissionManager remembers ordinary session allowances by tool name and stateToProgressAdapter.toolCallConfirmationMessages projects host options without combination metadata. Client-provided tools can instead pass through AgentHostSessionHandler's ordinary tools-service invocation, so coverage differs by execution path. The uncertainty starts at which tool categories should expose combination approval and whether its lifetime should match ordinary Chat's session/workspace/profile choices. Preserve runtime policy enforcement and compatibility with hosts lacking optional capabilities; do not broaden unrelated terminal or sandbox grants.
- **Open decisions:**
  - Should combination approval cover only VS Code-provided tools exposing approval metadata, or also SDK-native and MCP tools?
  - Should host-backed CLI combination approvals offer session-only scope or the same session, workspace, and profile scopes as ordinary Chat?
