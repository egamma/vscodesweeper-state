# Issue #98618 — Bulb menu should open immediately after clicking on the info icon in the problems view

[https://github.com/microsoft/vscode/issues/98618](https://github.com/microsoft/vscode/issues/98618)

## Summary

Keep open: current source still requires quick-fix discovery before enabling the Problems lightbulb, so the requested click-before-discovery workflow remains missing. The request reached 20 upvotes and was accepted into Backlog; related requests do not own the same work.

## Change summary

Let users request quick fixes directly from a Problems row's icon without first waiting for an enabled lightbulb.

## Best solution

Provide an actionable Problems-row affordance before quick-fix discovery completes, with deliberate loading and no-fix feedback. Agree on that interaction with the Problems and code-actions owners before implementation, without requiring a diagnostic API change.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/markers/browser/markersTreeViewer.ts`, `src/vs/workbench/contrib/markers/browser/markersTable.ts`, `src/vs/workbench/contrib/markers/browser/markersViewActions.ts`, `src/vs/workbench/contrib/markers/browser/markersView.ts`, `src/vs/workbench/contrib/markers/browser/media/markers.css`
- **Validation:** Use a code-action provider with a deliberately delayed response. In both Problems tree and table modes, activate the agreed row affordance before discovery completes and verify that one activation leads to the returned fix choices without another lightbulb click; repeat with no fixes, changing rows during the delay, and keyboard activation.
- **Behavior:**

  > A user working through Problems should be able to initiate quick fixes without waiting for the lightbulb to become available and then clicking again. Provider latency may remain, but the user's initial activation must carry through to the resulting choices. Validate with delayed and empty provider responses in both tree and table views, preserving the diagnostic's severity information and existing keyboard workflow. The pending and empty-result presentation require product agreement.
- **Trace:**

  > MarkersView.createWidget starts discovery on selection and focus changes; MarkersViewModel also starts it on hover. MarkerViewModel.showLightBulb and setQuickFixes in src/vs/workbench/contrib/markers/browser/markersTreeViewer.ts await model availability and code-action providers. QuickFixAction in markersViewActions.ts stays disabled until populated, and QuickFixActionViewItem.showQuickFixes only opens cached, nonempty actions. Tree and table renderers switch between severity information and the enabled quick-fix affordance; current CSS reinforces that gate. Preserve provider contracts, preferred-fix semantics, diagnostic severity, and unrelated navigation behavior. https://github.com/microsoft/vscode/issues/161438 concerns menu-widget adoption rather than this discovery gate; https://github.com/microsoft/vscode/issues/209212 concerns navigation after applying a fix. The uncertainty is the owner-approved interaction while availability is unknown, not whether this code path still gates activation.
- **Open decisions:**
  - Should the existing severity icon become actionable before discovery, or should a separate persistent quick-fix affordance provide that interaction?
  - What should users see while a requested quick-fix lookup is pending and when it returns no fixes, given the maintainer's concern about delayed menu appearance?
