# Issue #333298 — Support pagination for automations run history

[https://github.com/microsoft/vscode/issues/333298](https://github.com/microsoft/vscode/issues/333298)

## Summary

Team-authored feature request in an active area (sessions/automations); no fix has landed and no duplicate exists, so it stays open. The automations run history currently holds all runs in a single in-memory observable with no server-side pagination, unlike the cursor-based fetching pattern already used for the sessions list and GitHub PR pickers.

## Change summary

Add pagination to the automations run history so not every run row needs to be fetched/rendered at once, mirroring the session list's existing pagination.

## Best solution

Extend the automation run data-loading path (IAutomationService.runs / the underlying store in src/vs/sessions/contrib/providers/agentHost/browser/agentHostAutomationStore.ts) to support cursor-based paging, and have AutomationHistorySection in automationsView.ts request additional pages on scroll/load-more, following the same cursor pattern used by githubPullRequestsFetcher.ts for session pickers.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/automations/automationService.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/agentHostAutomationStore.ts`, `src/vs/sessions/contrib/sessions/browser/views/automationsView.ts`
- **Validation:** A test asserting the history section requests only an initial page of runs and fetches an additional page when scrolled to the end / a 'load more' action is triggered.
- **Behavior:**

  > The automations run history view should not need to hold or fetch every run for an automation up front; older runs load incrementally (e.g. as the user scrolls or invokes 'load more'), similar to how the sessions list already pages its data. Acceptance: opening the history for an automation with many runs only fetches an initial page, and additional runs load on demand without re-fetching everything already shown.
- **Trace:**

  > automationService.runs (src/vs/workbench/contrib/chat/common/automations/automationService.ts) exposes the full run set as one observable array, consumed wholesale by AutomationHistorySection.render() in src/vs/sessions/contrib/sessions/browser/views/automationsView.ts, which groups it by date and hands runs to SessionsFlatList (an already-virtualized WorkbenchObjectTree) for rendering — so the DOM cost is not the bottleneck, the data-loading path is. The sessions list and GitHub PR picker (src/vs/sessions/contrib/github/browser/fetchers/githubPullRequestsFetcher.ts) already implement a cursor/hasNextPage pattern that a maintainer may want mirrored here. Boundary: do not change the SessionsFlatList virtualization itself, only how run history is sourced/paged; where the uncertainty starts is which store(s) (agentHostAutomationStore, reconnectableAgentHostAutomationStore, provider-specific implementations) need a paged fetch API and what page size/trigger to use.
- **Open decisions:**
  - Should paging be cursor-based (mirroring the GitHub PR fetcher) or offset/limit-based, and does the underlying automation provider protocol already support this?
  - Should additional pages load on scroll-to-end, an explicit 'load more' action, or both?
  - Does this apply per-automation history only, or also to the aggregate cross-automation history view?

## Evidence

- **current implementation:** automationService.runs (src/vs/workbench/contrib/chat/common/automations/automationService.ts:176) is a single IObservable<readonly IAutomationRun[]> covering 'All recorded runs across all automations'; AutomationHistorySection.render() in automationsView.ts receives and groups the full allRuns array with no fetch limit or cursor.
- **existing pagination pattern elsewhere:** src/vs/sessions/contrib/github/browser/fetchers/githubPullRequestsFetcher.ts and createSessionFromPullRequestAction.ts already implement cursor/hasNextPage paging that this request could mirror.
- **no fix on main:** git log on automationsView.ts shows no pagination-related commit; the rendering still relies on the already-virtualized SessionsFlatList (WorkbenchObjectTree), so the gap is data loading, not DOM rendering.
