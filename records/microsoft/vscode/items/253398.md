## Plan brief

- **Likely files:** `src/vs/workbench/contrib/preferences/browser/keybindingsEditor.ts`, `src/vs/workbench/services/keybinding/browser/keybindingService.ts`
- **Validation:** On macOS with Caps Lock configured to switch input sources, open Keyboard Shortcuts, focus chat, type text, and press Caps Lock. Verify the input source switches, chat retains focus, and subsequent text remains in chat; repeat with a selected shortcuts row. Also verify shortcut labels refresh after a layout change and explicit shortcuts search/table navigation still works.
- **Behavior:**

  > With Keyboard Shortcuts open and chat focused, switching input sources must not transfer focus to the shortcuts search or table. Subsequent typing must remain in chat and use the selected input source. Shortcut labels must continue to reflect layout changes, and explicit focus commands inside Keyboard Shortcuts must retain their existing behavior.
- **Trace:**

  > WorkbenchKeybindingService in src/vs/workbench/services/keybinding/browser/keybindingService.ts turns keyboard-layout changes into onDidUpdateKeybindings events. KeybindingsEditor in src/vs/workbench/contrib/preferences/browser/keybindingsEditor.ts handles that event by calling render with preservation determined only by the keybinding-row focus context. renderKeybindingsEntries can then call focus when Keyboard Shortcuts is the active editor pane, even if chat currently owns DOM focus; focus selects the search input when there is no active row. This is a plausible explanation for https://github.com/microsoft/vscode/issues/253398, not a confirmed current-macOS reproduction. First establish whether the Caps Lock input-source switch produces that event and which refresh branch moves focus. Preserve label refresh, intentional editor activation, search navigation, and key-recording behavior; do not change OS input-method handling without evidence that it is responsible.
