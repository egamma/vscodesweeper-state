# Issue #306243 — Rate limit chat UI could use improvement

[https://github.com/microsoft/vscode/issues/306243](https://github.com/microsoft/vscode/issues/306243)

## Summary

A real gap remains on current main: rate-limit errors now identify several limit types and show a wait duration, but the rendered duration is static and session/weekly usage is not exposed in the status dashboard. Maintainer feedback accepted the concern while leaving the desired time presentation open.

## Change summary

Make chat rate-limit UI identify the applicable limit, expose usage and reset information, and keep the displayed wait state current.

## Best solution

Give rate-limit responses a time-aware presentation that remains accurate until reset, and expose session and weekly limit consumption through the existing chat status experience so users can understand the limit before and after reaching it.

- **Behavior:**

  > When chat is rate-limited, the UI identifies which limit was reached and gives reset information that does not become stale while the response remains visible. Users can determine whether they may retry without repeatedly submitting requests. The existing distinctions among session, weekly, model, agent-mode, and service-demand limits remain intact. If persistent usage visibility is selected, session and weekly consumption and reset information are discoverable from the chat status surface.
- **Trace:**

  > Rate-limit payloads reach getRateLimitMessage in src/vs/workbench/contrib/chat/common/chatErrorMessages.ts, where `retryAfter` is immediately converted to text. IChatResponseErrorDetails in src/vs/workbench/contrib/chat/common/chatService/chatService.ts retains only the resulting message and an `isRateLimited` flag, and ChatErrorContentPart renders that message statically. Separately, ChatQuotaNotificationContribution in src/vs/workbench/contrib/chat/browser/chatQuotaNotification.ts consumes session and weekly snapshots for threshold notifications, while ChatStatusDashboard does not render those snapshots as persistent indicators. Preserve existing quota, anonymous-user, and Auto-model behavior; this issue does not call for changing server limit policy. Related reports are https://github.com/microsoft/vscode/issues/302742 and https://github.com/microsoft/vscode/issues/325598.
- **Open decisions:**
  - Should a rate-limit response show a continuously updating relative countdown, a fixed local reset timestamp, or both?
  - Should session and weekly rate-limit consumption be persistently visible in the chat status dashboard, or only surfaced in warnings and the terminal rate-limit response?
