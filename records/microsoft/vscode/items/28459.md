# Issue #28459 — [css] Use CSS custom properties imported via @import

[https://github.com/microsoft/vscode/issues/28459](https://github.com/microsoft/vscode/issues/28459)

## Summary

This remains a well-supported Backlog feature request: current VS Code completion still operates on the active stylesheet and does not collect custom properties through CSS imports. No eligible duplicate exists under the stronger re-review rule, and 156 community upvotes strongly support retaining the request.

## Change summary

Provide IntelliSense for CSS custom properties declared in local stylesheets referenced through `@import`.

## Best solution

Add import-aware custom-property completion to the CSS language service using its filesystem abstraction, initially following statically resolvable local imports rather than indexing every stylesheet in the workspace. VS Code should then consume the language-service implementation while preserving fast single-file completion.

## Plan brief

- **Likely files:** `extensions/css-language-features/server/src/cssServer.ts`, `extensions/css-language-features/server/src/test/completion.test.ts`, `extensions/css-language-features/server/package.json`
- **Validation:** Add a CSS language-service completion test with `main.css` importing `variables.css`, asserting that `var(--...)` offers the imported custom property while unrelated workspace stylesheets do not contribute suggestions; run the CSS language-feature server test suite.
- **Behavior:**

  > In a CSS document, custom-property completion should include declarations from statically resolvable local stylesheets imported by that document. Suggestions should respect the document's import scope rather than collecting unrelated variables from the entire workspace. Existing same-file custom-property completion and `@import` path completion must remain unchanged. The accepted behavior should be covered with imported, unrelated, missing, and cyclic stylesheet fixtures.
- **Trace:**

  > The VS Code server in `extensions/css-language-features/server/src/cssServer.ts` parses only the active document and calls `vscode-css-languageservice` through `doComplete2`; the filesystem-backed document context currently supports path resolution but not a stylesheet dependency graph. `extensions/css-language-features/server/src/test/completion.test.ts` confirms that `@import` paths can be resolved, but it does not test symbols from imported content. The maintainer diagnosis at https://github.com/microsoft/vscode/issues/100217#issuecomment-644633466 places the core implementation in https://github.com/microsoft/vscode-css-languageservice, followed by dependency consumption and integration coverage here. Preserve the existing single-file behavior and avoid an unconditional workspace-wide scan; the plan must bound cache invalidation, cycles, missing files, and completion latency.
- **Open decisions:**
  - Should the completion scope follow the transitive graph of statically resolvable local `@import` rules, or only direct imports; and should remote or conditional imports be excluded from IntelliSense?

## Evidence

- **current source:** `extensions/css-language-features/server/src/cssServer.ts` parses the active document into the stylesheet cache and passes only that stylesheet to `LanguageService.doComplete2`; it has no imported-document graph or workspace symbol index.
- **current tests:** `extensions/css-language-features/server/src/test/completion.test.ts` tests filesystem-backed path completion for `@import`, but contains no completion test that reads declarations from an imported stylesheet.
