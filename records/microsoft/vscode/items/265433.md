# Issue #265433 — Be smarter about errors from edits

[https://github.com/microsoft/vscode/issues/265433](https://github.com/microsoft/vscode/issues/265433)

## Summary

Keep open: edit feedback still filters diagnostics against the immediately preceding edit, so an unresolved error introduced earlier can disappear from subsequent feedback. Neither the existing autoFix setting nor get_errors automatically provides the requested persistent reminder.

## Change summary

Keep unresolved diagnostics visible to the agent across successive edits rather than reporting only newly introduced errors.

## Best solution

Define when outstanding edit-related diagnostics should be repeated and whether feedback should include unrelated preexisting errors, then apply that contract consistently across edit tools. Coordinate with the related diagnostics-timing discussion without treating it as a duplicate.

- **Validation:** Add a targeted edit-feedback test covering two successive edits: the first introduces an error, the second leaves it unchanged, and the outstanding error remains available at the agreed feedback point; after a third edit fixes it, it is absent. Also check the chosen treatment of preexisting errors and preserve behavior when automatic diagnostic feedback is disabled.
- **Behavior:**

  > An agent can introduce an error in one edit and receive no reminder about it after another edit leaves that error untouched. Outstanding errors should remain available in subsequent diagnostic feedback until resolved, according to an agreed scope and repetition policy. Acceptance must cover introduction, persistence across a subsequent edit, and removal after resolution, while distinguishing unresolved errors from newly introduced ones.
- **Trace:**

  > EditFileResult.getNewDiagnostics in extensions/copilot/src/extension/tools/node/editFileToolResult.tsx compares current diagnostics with IEditedFile.existingDiagnostics using message and exact range equality. AbstractReplaceStringTool uses an invocation-local existingDiagnosticMap, while insertEditTool.tsx and applyPatchTool.tsx capture current diagnostics for each invocation; this explains why an earlier unresolved error becomes part of the next baseline and is filtered out. The github.copilot.chat.agent.autoFix setting gates this feedback, and GetErrorsTool supplies an explicit query rather than a persistent reminder. Preserve the existing disabled-feedback behavior and do not conflate diagnostic feedback with failed edit application. The related timing discussion at https://github.com/microsoft/vscode/issues/271669 highlights the tradeoff between useful reminders and interrupting intermediate refactor steps; the issue does not settle which feedback cadence or diagnostic scope should apply.
- **Open decisions:**
  - Should repeated feedback include only diagnostics introduced during the session, or also errors that predated the agent's edits, explicitly identified as preexisting?
  - Should outstanding diagnostics be repeated after each edit, or at a later checkpoint such as the transition away from editing?
