# Issue #344869 — Worktrees that were created and deleted from VSCode don't show up after being recreated unless you restart VSCode

[https://github.com/microsoft/vscode/issues/344869](https://github.com/microsoft/vscode/issues/344869)

## Summary

The current Git extension has a lifecycle mismatch that explains the missing recreated worktree: deletion disposes the repository without removing its entry from the model, so discovery subsequently treats it as already open. Route this to Git; the related Agents Window umbrella does not own this specific defect.

## Change summary

A worktree deleted and recreated through VS Code should reappear without restarting the window when git.detectWorktrees is enabled.

## Best solution

Keep the Git model's open-repository registry synchronized with worktree deletion so recreating the same path registers a fresh, visible source control provider. Preserve deliberate Close Repository behavior and existing worktree detection settings.

## Evidence

- **Reporter trigger:** https://github.com/microsoft/vscode/issues/344869 describes creating, deleting, and recreating a worktree through VS Code; restarting restores visibility. The reporter additionally confirms git.detectWorktrees=true, with Windows hosting a WSL Debian workspace.
- **Deletion leaves a stale model entry:** extensions/git/src/repository.ts:2268-2275, Repository.deleteWorktree(), calls worktree?.dispose() after deleting the directory. Repository.dispose() at lines 3656-3658 only disposes its resources. In extensions/git/src/model.ts, Model.open() removes the openRepositories entry through its local dispose callback, triggered by RepositoryState.Disposed or sourceControl.onDidDisposeParent; direct Repository.dispose() triggers neither.
- **Recreation is rejected as already open:** extensions/git/src/model.ts:808-827 detects worktrees and queues discovery. Model.openRepository() at lines 600-606 returns immediately when getRepositoryExact() finds an entry; getRepositoryExact() at lines 934-941 matches the stale entry by root path without checking whether its source control provider was disposed. This prevents registering a new provider for the recreated path.
- **Source control disposal distinction:** src/vs/workbench/api/common/extHostSCM.ts:854 defines onDidDisposeParent from the parent's disposal event, not the provider's own event. ExtHostSourceControl.dispose() at lines 954-968 unregisters the provider and fires its own onDidDispose, explaining why the worktree vanishes from the UI while its Git model entry survives.
