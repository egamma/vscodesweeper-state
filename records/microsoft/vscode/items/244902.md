# Issue #244902 — // MARK text in minimap is strechted when "Render Characters" option is checked

[https://github.com/microsoft/vscode/issues/244902](https://github.com/microsoft/vscode/issues/244902)

## Summary

The minimap rendering path that produces the reported high-DPI, line-count-dependent distortion remains on current main. A proposed fix was closed without merging, and the issue was subsequently classified as an editor-minimap bug, so it should remain open for a corrected diagnosis and fix.

## Change summary

Minimap section-header text such as `// MARK` becomes horizontally distorted when Render Characters is enabled for files around the minimap sampling threshold.

## Best solution

Diagnose the coordinate-space transition between minimap layout, sampling, and the canvas backing store, then keep section-header and character rendering proportions stable when `editor.minimap.renderCharacters` changes. The earlier one-line width adjustment should not be reused without validating decorations, section headers, standard-DPI displays, and fill/fit layouts.

- **Behavior:**

  > With the minimap visible, `// MARK` section-header labels must retain the same readable horizontal proportions when `editor.minimap.renderCharacters` is toggled. This must hold at high DPI and on both sides of the file-length threshold where minimap sampling begins. Existing minimap scale, fill/fit behavior, ordinary character rendering, and section-header truncation must remain intact.
- **Trace:**

  > Current main computes minimap layout in `EditorLayoutInfoComputer.computeMinimapLayout` in src/vs/editor/common/config/editorOptions.ts: `renderCharacters` changes `baseCharHeight`, which can alter sampling, scale, and backing dimensions around the reported line count. `MinimapOptions` and `InnerMinimap._applyLayout` in src/vs/editor/browser/viewParts/minimap/minimap.ts then bridge CSS dimensions and device-pixel canvas dimensions, while `_renderSectionHeaders` draws MARK labels directly onto the decorations canvas. The closed, unmerged https://github.com/microsoft/vscode/pull/254135 attributed the problem to `minimapCharWidth`, but that value also controls ordinary glyph placement and its proposed change did not include a repository test. The investigation boundary is therefore the layout-to-canvas coordinate conversion; unrelated minimap navigation and section-header discovery must not change.
- **Open decisions:**
  - Is the distortion caused by the canvas backing-store/CSS-size ratio, the sampling transition, or the section-header drawing scale rather than the shared character-width calculation changed by the closed PR?
  - Should regression coverage be expressed as deterministic layout geometry assertions, a browser canvas rendering test, or both?
