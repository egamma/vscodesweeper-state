# Issue #111669 — Extension bisect unable to find 2 bad extensions

[https://github.com/microsoft/vscode/issues/111669](https://github.com/microsoft/vscode/issues/111669)

## Summary

Extension Bisect can still incorrectly blame VS Code when multiple extensions independently reproduce the problem. Keep this older report open; an open PR addresses the underlying failure, but has not landed.

## Change summary

Make Extension Bisect identify a faulty extension reliably when several extensions independently cause problems, with a way to continue finding additional culprits.

## Best solution

Review https://github.com/microsoft/vscode/pull/316792 against this report's multiple-culprit scenario and land an appropriate fix before closing. Reliably identifying one culprit per run satisfies the author's explicitly stated minimum; automatically collecting every culprit remains a separate product decision.

## Evidence

- **Current source reproduces the failure:** In src/vs/workbench/services/extensionManagement/browser/extensionBisect.ts, ExtensionBisectService constructs its disabled map with `i >= mid && i < high`. After next(true) reduces high, extensions outside that range become enabled again, including other faulty extensions. With four extensions and independent culprits at indices 0 and 3, the states (low, high, mid) progress from (0,4,0) with all disabled to (0,4,2), (0,2,1), and (0,1,0). Culprit 3 is enabled during the latter states, so truthful 'I can reproduce' answers produce `{id: extensions[0], bad: true}`; the continuation action displays 'no extension has been identified' and suggests a VS Code problem. This is a source trace, not an executed reproduction.
- **Author's minimum accepted direction:** https://github.com/microsoft/vscode/issues/111669#issuecomment-737544035 explicitly distinguishes finding every culprit from the minimum requirement: identify one faulty extension despite multiple culprits, allowing repeated runs. https://github.com/microsoft/vscode/issues/111669#issuecomment-743464546 separately discusses interacting extensions and preserving prerequisite extensions.
- **Existing capability does not cover the failure:** The `extension.bisect.start` and `extension.bisect.next` commands implement a single-candidate search. The success dialog can keep an identified extension disabled, enabling repeated runs, but the traced failure prevents reaching that successful identification. There is no multi-culprit collection state in BisectState.
- **Related issue is newer, not a valid canonical for this re-review:** https://github.com/microsoft/vscode/issues/237092 is open, was created on 2024-12-30, and explicitly describes this report's multiple-culprit failure. It is newer than this issue's 2020-12-01 creation date, so it cannot be the duplicate target under the re-review rules. The focused open-issue search found no older canonical owning the same symptom.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/316792 is OPEN and declares `Fixes #237092`. Its description addresses this exact failure by retaining disabled extensions eliminated after 'still bad' answers, identifying one culprit per run, and suggesting subsequent runs. This is an implementation candidate, not evidence of a completed fix.
