# Issue #166741 — Sticky scroll messes up accurate markdown scroll sync

[https://github.com/microsoft/vscode/issues/166741](https://github.com/microsoft/vscode/issues/166741)

## Summary

The issue remains a valid interaction bug between editor sticky scroll and Markdown preview synchronization. A maintainer confirmed that the Markdown extension uses the editor API correctly and identified the editor's occlusion-unaware visible ranges as the underlying problem; no resolution is documented.

## Change summary

Keep Markdown preview and editor scrolling synchronized when sticky scroll obscures lines at the top of the editor viewport.

## Best solution

Define an editor-level way for scroll synchronization consumers to distinguish the effective unobscured viewport from lines covered by sticky scroll, then update Markdown's topmost-line synchronization to use that contract without changing ordinary visible-range semantics unexpectedly.

## Plan brief

- **Likely files:** `src/vs/editor/browser/viewParts/lines/viewLines.ts`, `extensions/markdown-language-features/src/preview/topmostLineMonitor.ts`
- **Validation:** Add or extend scroll-sync coverage using a Markdown document with seven headings and sticky scroll enabled: slowly scroll the side preview to the bottom, verify the editor tracks the corresponding source position, then scroll the editor and verify the preview does not jump backward.
- **Behavior:**

  > With sticky scroll enabled and Markdown preview open to the side, scrolling either pane must keep the other pane aligned to the same document region. Scrolling the preview through a short sequence of headings to the bottom must advance the editor instead of leaving its effective viewport near line 2. Switching to editor-driven scrolling afterward must not make the preview jump backward. Behavior with sticky scroll disabled must remain unchanged.
- **Trace:**

  > Markdown preview synchronization observes editor visible ranges in extensions/markdown-language-features/src/preview/topmostLineMonitor.ts. Sticky scroll is rendered as an editor contribution over the line view; the issue points to src/vs/editor/browser/viewParts/lines/viewLines.ts, and alexdima confirms that editor core therefore reports occluded lines as visible. The uncertainty starts at the contract boundary: whether core visible-range semantics should change, a separate effective-viewport API should be exposed, or Markdown should consume sticky-scroll state. Avoid coupling Markdown to the editor.stickyScroll.maxLineCount setting alone, because configured capacity does not necessarily describe the currently rendered sticky lines.
- **Open decisions:**
  - Should editor visible ranges exclude lines occluded by sticky scroll, or should a separate effective/unobscured viewport API be introduced?
  - Should Markdown scroll synchronization consume an editor-level occlusion contract, or is a narrowly scoped sticky-scroll integration acceptable?
  - Which existing visible-range consumers could be affected if the core event semantics change?

## Evidence

- **confirmed root cause:** In the issue discussion, editor maintainer alexdima confirms that sticky scroll is implemented as an editor contribution, so editor core reports visible ranges containing lines that are actually occluded by sticky content.
- **confirmed extension behavior:** The maintainer explicitly states that the Markdown implementation is doing the correct thing; its synchronization path is extensions/markdown-language-features/src/preview/topmostLineMonitor.ts.
- **reproduction:** The supplied seven-heading Markdown example demonstrates the mismatch: preview-driven scrolling reaches the bottom while the editor's reported top remains near line 2, and subsequent editor scrolling makes the preview jump backward.
