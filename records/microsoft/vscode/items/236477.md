# Issue #236477 — Debug: Search inside collapsed nodes

[https://github.com/microsoft/vscode/issues/236477](https://github.com/microsoft/vscode/issues/236477)

## Summary

Keep this accepted request open: current Variables tree search matches names and values of loaded entries but does not recursively discover data beneath unexpanded nodes. The request has 26 upvotes, and the related issues inspected do not own the same capability.

## Change summary

Support searching variable names and values inside collapsed nested objects and collections in the debugger's Variables view.

## Best solution

Provide an explicit deep-search capability in the Variables view that discovers matching descendants and exposes their ancestry without requiring console serialization. Establish traversal limits and treatment of expensive or lazily evaluated variables before implementation so searching large debuggee objects remains responsive.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/variablesView.ts`, `src/vs/workbench/contrib/debug/browser/baseDebugView.ts`, `src/vs/workbench/contrib/debug/common/debugModel.ts`
- **Validation:** Use a debug session exposing a nested dictionary and an indexed collection whose only matching key or value is beneath an initially unexpanded node. Verify deep search discovers both matches and reveals their ancestry without console export; clearing the search restores ordinary browsing. Add deterministic mock-adapter tests covering traversal limits, cancellation, paged collections, and the agreed lazy-variable policy.
- **Behavior:**

  > Users should be able to search names and values within nested debugger variables even when the containing nodes have never been expanded. Matching descendants must be locatable with enough ancestor context to identify their location, without serializing the value in the console. Acceptance includes a nested dictionary and an array of dictionaries, with matches found separately by key and by value. Searching large or expensive structures must remain controllable and must communicate when results are incomplete.
- **Trace:**

  > VariablesView.renderBody in src/vs/workbench/contrib/debug/browser/variablesView.ts creates an asynchronous tree with ordinary label matching and no asynchronous findProvider. expressionAndScopeLabelProvider in src/vs/workbench/contrib/debug/browser/baseDebugView.ts already includes both names and displayed values, so name-only matching is not the missing piece. VariablesDataSource delegates child discovery to the debug model; ExpressionContainer in src/vs/workbench/contrib/debug/common/debugModel.ts caches debug-adapter variable responses and chunks large indexed collections. AsyncDataTree.refreshNode in src/vs/base/browser/ui/tree/asyncDataTree.ts does not fetch children of collapsed non-root nodes, leaving never-expanded descendants unavailable to ordinary matching. Preserve normal lazy browsing and existing adapter paging behavior; do not make ordinary tree search eagerly evaluate every object. The unresolved boundary is how an explicit deep search limits traversal and handles expensive or lazy evaluation. https://github.com/microsoft/vscode/issues/205821 concerns scope expansion, while https://github.com/microsoft/vscode/issues/279795 concerns hover filtering; neither subsumes this request.
- **Open decisions:**
  - What traversal scope and user-visible limits should deep search use for large, cyclic, or remotely fetched object graphs, and how should it indicate incomplete results?
  - Should deep search evaluate expensive scopes or lazy variables such as getters, require explicit consent, or skip them with an indication that they were not searched?
