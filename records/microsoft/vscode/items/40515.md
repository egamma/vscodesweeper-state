# Issue #40515 — Tasks with target = TaskScope.Global as the scope do not show up in task picker UI

[https://github.com/microsoft/vscode/issues/40515](https://github.com/microsoft/vscode/issues/40515)

## Summary

Keep open: current main explicitly documents TaskScope.Global as unsupported and still excludes folderless provider tasks from task discovery. The maintainer-supported request remains unimplemented; existing user tasks do not cover dynamically contributed global tasks.

## Change summary

Support extension-provided TaskScope.Global tasks in the task picker without associating them with a workspace folder.

## Best solution

Make globally scoped provider tasks discoverable and runnable while keeping them separate from workspace tasks.json customization. Preserve workspace-dependent variable expressions literally, as agreed in the discussion, and design the remaining execution and picker behavior with the tasks maintainer.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/browser/mainThreadTask.ts`, `src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts`, `src/vs/workbench/contrib/tasks/browser/taskQuickPick.ts`, `src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts`, `src/vs/workbench/contrib/tasks/common/tasks.ts`
- **Validation:** Use a test extension whose TaskProvider returns both folder-scoped tasks and a TaskScope.Global task with an explicit executable and working directory. In a multi-root workspace, verify that Run Task lists and executes the global task once, Configure Task does not offer to persist it into workspace tasks.json, and workspace-dependent variable expressions remain literal. Retest existing folder-scoped task discovery, execution, and customization; agree empty-window and implicit-working-directory expectations during planning.
- **Behavior:**

  > An extension can contribute a task applicable across a multi-root workspace using TaskScope.Global, and users can discover and run it without assigning it to a folder. Global provider tasks must not be offered for workspace tasks.json customization. Workspace-dependent variable expressions retain their literal text, as established by the maintainer discussion. Acceptance includes a provider returning both global and folder tasks, with the global task listed once and existing folder-task behavior unchanged.
- **Trace:**

  > TaskSourceDTO.to in src/vs/workbench/api/browser/mainThreadTask.ts preserves Global without a workspaceFolder, but AbstractTaskService._getGroupedTasks in src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts drops contributed tasks without a folder in both normal collection and fallback. The public enum in src/vscode-dts/vscode.d.ts still documents Global as unsupported. The Open User Tasks command opens user configuration and does not satisfy this provider API request. _canCustomize already excludes folderless contributed tasks, while TerminalTaskSystem._executeCommand falls back to the first workspace folder, creating a separate execution-context concern. Preserve existing folder-scoped and user-configured task semantics; do not treat user tasks as interchangeable with global provider tasks. The accepted discovery, customization, and literal-variable requirements are recorded in https://github.com/microsoft/vscode/issues/40515; uncertainty remains around implicit execution context and empty-window support.
- **Open decisions:**
  - When a global shell or process task omits an explicit working directory, what directory should execution use without implicitly binding the task to the first workspace folder?
  - Should global provider tasks be discoverable and runnable in an empty window as well as in single-folder and multi-root workspaces?
