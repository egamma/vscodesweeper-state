# Issue #310714 — When updating VSC if one window has an ongoing copilot session only that window is re-opened when VSC restarts after update

[https://github.com/microsoft/vscode/issues/310714](https://github.com/microsoft/vscode/issues/310714)

## Summary

Keep open: this team-authored report describes a specific multi-window update-restoration failure, and current source still runs shutdown confirmation independently in each window. The checkout shows the intended all-window restoration path but does not conclusively explain or disprove the Windows/WSL failure without exercising an actual update.

## Change summary

Restart to Update restores only the window that contained an active Copilot session instead of every previously open local and WSL window.

## Best solution

Reproduce the update shutdown with multiple local/WSL windows and one delayed chat-session confirmation, then preserve the complete pre-update window set through shutdown and relaunch without changing ordinary close/quit session protection.

## Plan brief

- **Likely files:** `src/vs/platform/lifecycle/electron-main/lifecycleMainService.ts`, `src/vs/platform/windows/electron-main/windowsStateHandler.ts`, `src/vs/platform/windows/electron-main/windowsMainService.ts`, `src/vs/platform/update/electron-main/abstractUpdateService.ts`, `src/vs/workbench/contrib/chat/electron-browser/chat.contribution.ts`
- **Validation:** On Windows, open at least two VS Code windows including a WSL window, start an in-progress local Copilot session in one, select Restart to Update, confirm shutdown, and verify every pre-update window reopens with its original workspace. End the plan with a focused lifecycle/window-state regression test that delays one renderer's shutdown acknowledgement and asserts the complete window set remains available for restart restoration.
- **Behavior:**

  > Restart to Update must reopen every VS Code window that was open when the update began, including mixed local and WSL windows, even when one window pauses shutdown to confirm termination of an active Copilot session. Confirming the session shutdown must not reduce the restored set to that final window. Ordinary window-close, workspace-change, reload, and quit protections for active sessions must remain unchanged.
- **Trace:**

  > The update starts in AbstractUpdateService.quitAndInstall in src/vs/platform/update/electron-main/abstractUpdateService.ts and reaches LifecycleMainService.quit(true) in src/vs/platform/lifecycle/electron-main/lifecycleMainService.ts. Electron then unloads windows independently; ChatLifecycleHandler in src/vs/workbench/contrib/chat/electron-browser/chat.contribution.ts can delay one renderer while it awaits confirmSessionShutdown. WindowsStateHandler.onBeforeShutdown in src/vs/platform/windows/electron-main/windowsStateHandler.ts is intended to serialize all open windows before closure, and WindowsMainService.getRestoreWindowsSetting in src/vs/platform/windows/electron-main/windowsMainService.ts forces an update restart to restore all of them. Source inspection does not establish whether the loss occurs while persisting that snapshot, during installer relaunch, or while resolving mixed local/remote paths; reproduction with state and lifecycle logging must locate that boundary. Keep https://github.com/microsoft/vscode/issues/335731 separate: it concerns repeated confirmation UX, not the missing-window restoration result.
- **Open decisions:**
  - Should update restart restoration preserve the exact mixed local/remote window set captured when Restart to Update begins even if some windows finish shutdown substantially earlier than a window awaiting session confirmation?
