# Issue #179015 — 'Define keybinding' widget doesn't accept `shift shift` keybinding

[https://github.com/microsoft/vscode/issues/179015](https://github.com/microsoft/vscode/issues/179015)

## Summary

The recording limitation remains explicit in current source; manual keybindings.json editing supports the shortcut but does not satisfy the widget request. Keep this team-authored Backlog item open: an earlier intentional restriction explains the behavior, but does not justify declining the subsequently accepted report.

## Change summary

Allow the Define Keybinding widget to record modifier-only sequences such as shift shift.

## Best solution

Support recording double-modifier shortcuts without making ordinary modifier combinations accidentally become multi-part bindings. Reconcile that interaction with the earlier maintainer concern before changing the shared keybinding recorder.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/preferences/browser/keybindingWidgets.ts`, `src/vs/platform/keybinding/common/abstractKeybindingService.ts`
- **Validation:** The plan should establish browser-level recording checks: opening Define Keybinding, pressing and releasing Shift twice, and accepting must produce shift shift; ordinary Ctrl+/ and Ctrl+K Ctrl+C recording must remain unchanged. Include the previously cited release-Ctrl-then-press-Ctrl+/ sequence and verify its maintainer-approved outcome, plus the shared keyboard-shortcut search recording behavior.
- **Behavior:**

  > The Define Keybinding widget cannot record shift shift even though the resulting binding works when entered manually in keybindings.json. Users should be able to define supported double-modifier shortcuts through the UI while ordinary modifier combinations and normal multi-part shortcuts remain reliable. Acceptance must cover two distinct Shift presses, ordinary shortcut recording, and the agreed behavior when a modifier is pressed and released before a conventional shortcut.
- **Trace:**

  > In src/vs/workbench/contrib/preferences/browser/keybindingWidgets.ts, DefineKeybindingWidget uses KeybindingsSearchWidget, whose recorder receives keydown events and replaces any preceding chord with null normal dispatch. Modifier presses have null normal dispatch, so the second Shift replaces the first; an explicit TODO describes this exact case. Modifier-only runtime dispatch exists separately in src/vs/platform/keybinding/common/abstractKeybindingService.ts. The recorder is also used by keyboard-shortcut search, so changing its interpretation can affect both surfaces. Preserve existing keybindings.json syntax and runtime dispatch semantics. https://github.com/microsoft/vscode/issues/142465#issuecomment-1342596043 documents why modifier-only recording was previously declined: a released Ctrl followed by Ctrl+/ could become an unintended ctrl ctrl+/ binding. The remaining uncertainty is the user-facing recording interaction that avoids that ambiguity, not whether the limitation exists.
- **Open decisions:**
  - Should ordinary recording automatically recognize repeated standalone modifiers, or should users explicitly enter a modifier-only recording mode so a released modifier before a conventional shortcut remains ignored?

## Evidence

- **Current recording path:** In src/vs/workbench/contrib/preferences/browser/keybindingWidgets.ts, KeybindingsSearchWidget.startRecordingKeys listens for keydown but not keyup. printKeybinding treats a last chord with getDispatchChords()[0] === null as incomplete and replaces it with the next keypress, so two separate Shift presses never accumulate as shift shift. The adjacent TODO explicitly documents this exact limitation.
- **Modifier dispatch distinction:** src/vs/platform/keybinding/common/usLayoutResolvedKeybinding.ts returns null from getDispatchStr for modifier keys, while _getSingleModifierChordDispatch recognizes a standalone Shift as 'shift'. src/vs/platform/keybinding/common/abstractKeybindingService.ts separately supports double-modifier dispatch; runtime support therefore does not imply recording support.
- **Existing workaround is partial:** DefineKeybindingWidget constructs KeybindingsSearchWidget and starts recording immediately; its accepted value comes from the recorded chord array. Defining shift shift manually in keybindings.json bypasses this recorder, rather than delivering the requested widget behavior.
