# Issue #215722 — editor.action.nextMatchFindAction won't scroll to target when followed by closeFindWidget

[https://github.com/microsoft/vscode/issues/215722](https://github.com/microsoft/vscode/issues/215722)

## Summary

Traced a plausible, still-present root cause in source: closing the find widget right after a find-next move cancels the in-flight smooth scroll to the match. The prior review's fix commit was refuted, and I found no new fix commit referencing this issue, so this stays open pending a real fix.

## Change summary

When a keybinding chains `editor.action.nextMatchFindAction` and `closeFindWidget`, the editor never scrolls to the newly found match if it's off-screen.

## Best solution

Fix FindWidget._removeViewZone (src/vs/editor/contrib/find/browser/findWidget.ts) so it doesn't clobber an in-flight smooth-scroll-to-match with an immediate setScrollTop computed from the stale current scrollTop.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/find/browser/findWidget.ts`, `src/vs/editor/contrib/find/browser/findModel.ts`
- **Validation:** A test that calls FindModel.moveToNextMatch() (or triggers nextMatchFindAction) immediately followed by closeFindWidget(), for a match outside the viewport, and asserts the final/target scrollTop reveals the match rather than reverting to the pre-move position.
- **Behavior:**

  > When a single keybinding runs `editor.action.nextMatchFindAction` immediately followed by `closeFindWidget`, the editor should still scroll to reveal the newly found match, just as it does when nextMatchFindAction runs alone. Today, if the match is off-screen, closing the find widget in the same tick leaves the viewport near its previous position instead. Acceptance: running both commands back-to-back ends with the match visible (consistent with the CenterIfOutsideViewport reveal nextMatchFindAction alone produces); closing the find widget in the ordinary case (no pending match-reveal) is unaffected.
- **Trace:**

  > FindModel._setCurrentFindMatch (src/vs/editor/contrib/find/browser/findModel.ts, ~line 264) requests an animated reveal via `revealRangeInCenterIfOutsideViewport(match, ScrollType.Smooth)`. closeFindWidget (src/vs/editor/contrib/find/browser/findController.ts, ~line 246) sets `isRevealed:false`, which FindWidget._onStateChanged routes to `_hide(true)` -> `_removeViewZone()` (findWidget.ts lines 726-736). `_removeViewZone` calls `this._codeEditor.setScrollTop(this._codeEditor.getScrollTop() - this._viewZone.heightInPx)` using the default `ScrollType.Immediate` (see the signature at codeEditorWidget.ts line 1015) — since this runs synchronously right after the smooth-scroll request, `getScrollTop()` reads the pre-animation position and the immediate set overrides/cancels the pending reveal. Confirmed by reading source only, not executed. The prior review's cited fix commit (22933cea7b65c18ba29aa7f52937f13b22bd2eb5) was independently refuted and is not re-cited. Boundary: the normal case (closing find with no pending match-reveal) must keep collapsing the view zone and adjusting scroll exactly as today; `addExtraSpaceOnTop` layout semantics must not change.
- **Open decisions:**
  - Should _removeViewZone preserve/compose with an in-flight smooth-scroll target instead of reading the instantaneous getScrollTop(), or should its own scroll adjustment use ScrollType.Smooth so it merges with any pending reveal?
  - Is there (or should there be) an API to query the scrollable's pending/target scrollTop rather than its current value, and would that generalize to other callers that adjust scroll around changeViewZones?
