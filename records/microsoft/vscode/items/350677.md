## Evidence

- **Unconditional forwarding on main:** src/vs/workbench/api/browser/mainThreadTerminalShellIntegration.ts:82-90 subscribes to onData for every executed command with Event.accumulate(..., 50, true, ...), joins every batch, and calls $shellExecutionData without checking whether an extension reads the execution.
- **Continuous-output buffering confirmed:** src/vs/base/common/event.ts:270-355 shows debounce clearing and restarting its timer on every event, while accumulate appends chunks to an array without a size or maximum-wait bound. The reported continuous yes output therefore retains chunks until a pause or listener removal; command completion disposes the listener and flushes the accumulated output.
- **Unread output discarded:** src/vs/workbench/api/common/extHostTerminalShellIntegration.ts:381-413 creates _dataStream only through execution.read(); InternalTerminalShellExecution.emitData uses optional forwarding to that stream. With no reader, the transmitted output is discarded.
- **Complete reproduction and measured impact:** https://github.com/microsoft/vscode/issues/350677 supplies the bash command, Linux Insiders build, shell-integration-disabled control, and macOS confirmation. The reporter measured a 195.5 MB message and renderer heap growth from 170 MB to 987 MB. This review confirmed the mechanism from source without executing the reproduction.
- **Open fixing PR:** https://github.com/microsoft/vscode/pull/350714 was verified OPEN with mergedAt null and explicitly says Fixes #350677. Its proposal covers reader-aware forwarding, 50 ms and size-triggered flushing, command identity races, and execution ordering. It is an active implementation candidate, not a landed fix.
- **Distinct scope:** The complete issue body distinguishes the earlier extension-host stream leak at https://github.com/microsoft/vscode/issues/338243 from this renderer-side accumulation, and explicitly excludes the separate $acceptTerminalProcessData forwarding path.
