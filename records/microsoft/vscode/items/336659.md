# Issue #336659 — Allow copying individual links from chat context menus

[https://github.com/microsoft/vscode/issues/336659](https://github.com/microsoft/vscode/issues/336659)

## Summary

Genuine gap: chat's custom context menu (MenuId.ChatContext) replaces the browser's native 'Copy Link Address', and no chat-side copy-link action exists on main. The fix follows an established pattern already in the codebase (the KaTeX math-source copy action), so this is a well-scoped, implementable request.

## Change summary

Add a context-menu action to copy just the link address when right-clicking a link inside a chat response, instead of copying the whole response.

## Best solution

Add a context key (e.g. `chatIsLinkElement`) computed in `getChatContextMenuTargetContext` in chatListWidget.ts, and register a 'Copy Link Address' action in chatCopyActions.ts gated on it, mirroring `CopyKatexMathSourceAction`/`isKatexMathElement`.

## Vision fit

- **Fit:** aligned
- **Reason:** A small, uniform context-menu affordance for a common developer-inner-loop surface (chat) fits the workbench/core-UX theme without adding always-on UI or performance cost.
- **Evidence:** Durable theme: Workbench & core UX — layout flexibility, profiles, settings fidelity, first-run experience, notifications hygiene.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatListWidget.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatCopyActions.ts`, `src/vs/workbench/contrib/chat/common/actions/chatContextKeys.ts`
- **Validation:** A chatListWidget test (mirroring the existing getChatContextMenuTargetContext tests in chatListWidget.test.ts) asserting the new link context key is set/unset correctly for anchor vs. non-anchor targets, plus a manual check that right-clicking a chat link and choosing the new action copies only the href.
- **Behavior:**

  > Right-clicking a link inside a chat response shows a context-menu action (e.g. 'Copy Link Address') that copies only the link's target URL to the clipboard, without disturbing the existing 'Copy'/'Copy All' behavior for the rest of the response. Right-clicking non-link content is unaffected.
- **Trace:**

  > The custom chat context menu is built in ChatListWidget.handleContextMenu() (src/vs/workbench/contrib/chat/browser/widget/chatListWidget.ts, ~line 831), which calls preventDefault()/stopPropagation() on the native contextmenu event and opens MenuId.ChatContext via contextMenuService, so the browser's built-in 'Copy Link Address' never appears. getChatContextMenuTargetContext() (line 148) already inspects e.browserEvent.target to derive isKatexElement/isBackground flags that get merged into a scoped context-key overlay; CopyKatexMathSourceAction in chatCopyActions.ts consumes ChatContextKeys.isKatexMathElement the same way. Do not change the native browser context-menu suppression or the existing Copy/Copy All/Copy Final Response semantics — this only adds a new target-scoped action alongside them. Related: no linked PR or duplicate found.
- **Open decisions:**
  - Should the action target the whole anchor's href, or respect chat's inline anchor widget (chatInlineAnchorWidget.ts) which may render richer link chips differently from plain markdown `<a>` links?
  - Where should 'Copy Link Address' sit in the menu — its own group, or alongside 'copy' group items — and should it require the click to land exactly on the anchor vs. anywhere in a still-selected link?

## Evidence

- **no existing action:** src/vs/workbench/contrib/chat/browser/actions/chatCopyActions.ts registers CopyAllAction, CopyItemAction, CopyFinalResponseAction, and CopyKatexMathSourceAction into MenuId.ChatContext, but nothing for links.
- **existing pattern for element-scoped copy:** chatListWidget.ts's getChatContextMenuTargetContext() (line 148) computes isKatexElement/isBackground from the click target and feeds them into a scoped context-key overlay (handleContextMenu, ~line 843), which CopyKatexMathSourceAction already consumes via ChatContextKeys.isKatexMathElement — the same shape would work for a link target.
- **custom menu confirmed:** handleContextMenu() calls e.browserEvent.preventDefault()/stopPropagation() and shows contextMenuService's own MenuId.ChatContext menu, so the browser's native 'Copy Link Address' item is indeed suppressed, matching the report.
