# Issue #295755 — Feature Request: Support Branch Selection for Organization‑Level Copilot Agents

[https://github.com/microsoft/vscode/issues/295755](https://github.com/microsoft/vscode/issues/295755)

## Summary

This remains a valid, well-supported backlog request: 40 community upvotes demonstrate demand, and current main exposes no way to select a branch when synchronizing organization-level agents. The user-visible configuration and the Copilot service contract need a maintainer design decision before implementation.

## Change summary

Allow organization-level Copilot agents to be sourced from a selected non-default branch for pilot and staged rollouts.

## Best solution

Define a supported branch-selection contract for organization agents, including who controls it and whether local overrides are permitted, then carry that selection through agent discovery and detail retrieval while retaining the repository default branch when no selection is configured.

## Plan brief

- **Likely files:** `extensions/copilot/package.json`, `extensions/copilot/src/extension/agents/vscode-node/githubOrgCustomAgentProvider.ts`, `extensions/copilot/src/extension/agents/vscode-node/test/githubOrgCustomAgentProvider.spec.ts`, `extensions/copilot/src/platform/github/common/githubService.ts`, `extensions/copilot/src/platform/github/common/octoKitServiceImpl.ts`
- **Validation:** Extend the organization custom-agent provider unit tests to verify that a selected branch is used for discovery and detail retrieval, that an absent selection preserves default-branch behavior, and that the agreed policy/override precedence is honored.
- **Behavior:**

  > Organization administrators or approved users can select a non-default repository branch for organization-level custom agents using the authority and scope chosen by maintainers. Agent discovery and content retrieval use the selected branch consistently, allowing pilot users to receive preview definitions without affecting default-branch users. With no branch selection, synchronization retains its existing default-branch behavior. Invalid, inaccessible, or deleted branch selections produce the agreed visible/logged failure behavior rather than silently mixing definitions from different refs.
- **Trace:**

  > Organization-agent polling starts in `GitHubOrgCustomAgentProvider.pollAgents` in extensions/copilot/src/extension/agents/vscode-node/githubOrgCustomAgentProvider.ts. It calls `IOctoKitService.getCustomAgents` with source filters but no ref, then passes each API-returned `agent.version` to `getCustomAgentDetails`; `CustomAgentListOptions` in extensions/copilot/src/platform/github/common/githubService.ts has no branch field. `OctoKitServiceImpl` sends the list request through the Copilot custom-agents endpoint without a branch parameter, while the detail endpoint receives only the discovered version. extensions/copilot/package.json exposes an enablement setting but no branch selector. The boundary is organization-level agent synchronization: repository and user agents, agent precedence, cache layout, and normal default-branch behavior must remain unchanged. The uncertainty begins at the public control model and whether the Copilot service can enumerate an organization source at an arbitrary branch.
- **Open decisions:**
  - Who selects the branch: an organization policy, an individual user or machine setting, or both with a defined precedence?
  - May users override an organization-selected branch, and if so, how is that permission represented and enforced?
  - When the selected branch is missing or inaccessible, should VS Code retain the last successfully synchronized agents, fall back to the repository default branch, or expose no organization agents until the selection is corrected?
  - Does the Copilot custom-agents service support branch-scoped organization discovery, or must its API contract be extended before the VS Code client can implement this behavior?
