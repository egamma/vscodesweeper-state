# Issue #251857 — Support arbitrary URI schemes in `workbench.action.chat.attachFile`

[https://github.com/microsoft/vscode/issues/251857](https://github.com/microsoft/vscode/issues/251857)

## Summary

A real gap remains on current main: the command still discards extension-backed URI schemes before adding them to chat, while the attachment layer can represent them. Keep this Backlog request open while maintainers decide whether extensions may attach context directly or should use a user-mediated/tool-based flow.

## Change summary

Allow `workbench.action.chat.attachFile` to attach files supplied by registered virtual file-system providers instead of accepting only a fixed URI-scheme allowlist.

## Best solution

Define the intended consent and extension contract first, then make file attachment consistently accept supported registered file-system resources without broadening folder attachment or menu visibility unintentionally.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/actions/chatContextActions.ts`, `src/vs/workbench/contrib/chat/common/constants.ts`, `src/vs/workbench/contrib/chat/test/browser/actions/chatContextActions.test.ts`
- **Validation:** Add a targeted chat action test that invokes `workbench.action.chat.attachFile` with a URI from a registered virtual file-system provider and verifies exactly one file attachment is added; also verify an always-unsupported scheme is rejected and the folder action's behavior remains unchanged.
- **Behavior:**

  > When an extension invokes `workbench.action.chat.attachFile` with a file URI backed by a supported registered file-system provider, that resource can be added to the active chat as file context. Schemes explicitly unsupported by chat remain rejected. Existing local, remote, and untitled attachment behavior remains unchanged, and the chosen user-consent boundary must be explicit.
- **Trace:**

  > `AttachFileToChatAction.runWithWidget` obtains resources through `AttachResourceAction._getResources` in src/vs/workbench/contrib/chat/browser/actions/chatContextActions.ts; that shared helper hard-codes three schemes and silently drops `memfs:` and other extension-backed URIs. `ChatAttachmentModel.addFile` already represents arbitrary URI-backed file entries, while `isSupportedChatFileScheme` in src/vs/workbench/contrib/chat/common/constants.ts provides the newer denylist-based chat policy used by the context picker. Because `_getResources` is shared with `AttachFolderToChatAction` and menu registrations have separate scheme conditions, the plan must keep folder and UI expansion out of scope unless explicitly selected. https://github.com/microsoft/vscode/issues/277970 concerns indexing and should remain separate.
- **Open decisions:**
  - Should extensions be allowed to attach a supported URI immediately by executing this command, or must attachment require an explicit user action or a contributed tool?
  - Should arbitrary registered schemes be accepted only for URI arguments passed to `workbench.action.chat.attachFile`, or also become eligible through editor/explorer menus?
  - Should this request remain file-only, leaving `workbench.action.chat.attachFolder` and its shared resource-filtering path unchanged?

## Evidence

- **current source gap:** `AttachResourceAction._getResources` in src/vs/workbench/contrib/chat/browser/actions/chatContextActions.ts still accepts only `file`, `vscode-remote`, and `untitled`, so `AttachFileToChatAction.runWithWidget` silently receives no resource for a `memfs:` URI.
- **attachment support:** `ChatAttachmentModel.addFile` in src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentModel.ts creates a normal file attachment for schemes other than its special image and browser-resource cases; it does not impose the command's fixed allowlist.
- **existing scheme policy:** `isSupportedChatFileScheme` in src/vs/workbench/contrib/chat/common/constants.ts uses a targeted denylist and otherwise supports schemes, and the chat context picker already applies that helper in src/vs/workbench/contrib/chat/browser/actions/chatContextActions.ts.
- **maintainer discussion:** A maintainer asked whether extensions should forcibly attach context or instead contribute a tool or let the user select context, leaving a user-consent and API-boundary decision unresolved: https://github.com/microsoft/vscode/issues/251857#issuecomment-3659340708
- **related but not duplicate:** https://github.com/microsoft/vscode/issues/277970 is newer and concerns workspace/codebase indexing of virtual file systems, not the same observable failure of `workbench.action.chat.attachFile`; it does not satisfy the stronger duplicate bar for this re-reviewed issue.
