# Issue #123605 — Applying multiple valid workspace edits and then awaiting after can fail unexpectedly.

[https://github.com/microsoft/vscode/issues/123605](https://github.com/microsoft/vscode/issues/123605)

## Summary

Keep open as a workspace-edit API design discussion. Current source still captures document versions before dispatching each call, and the thread leaves automatic serialization versus extension-managed sequencing unresolved.

## Change summary

Allow successive workspace.applyEdit calls issued without intermediate awaits to apply reliably in sequence.

## Best solution

Establish an explicit concurrency contract for workspace.applyEdit that addresses dependent edit sequences without silently applying stale ranges. Decide whether sequencing remains extension-owned or becomes an API-supported behavior, and document and test that contract.

- **Behavior:**

  > Two workspace edits targeting an open document are issued consecutively, with both promises awaited afterward; the reporter expects both applications to succeed, but the second can return false. Explicitly awaiting the first application before issuing the second avoids the reported conflict. The finished design must specify whether separate calls are automatically sequenced and how intervening document changes affect success. Acceptance checks must assert both application results and resulting document content, not merely promise completion.
- **Trace:**

  > ExtHostBulkEdits.applyWorkspaceEdit in src/vs/workbench/api/common/extHostBulkEdits.ts synchronously serializes each edit through WorkspaceEdit.from before dispatching its RPC. The converter in src/vs/workbench/api/common/extHostTypeConverters.ts attaches the extension host's current document version, so immediately consecutive calls can capture the same version. BulkTextEdits and ModelEditTask.validate in src/vs/workbench/contrib/bulkEdit/browser/bulkTextEdits.ts reject mismatched versions; MainThreadBulkEdits returns false for application errors. Existing extHostBulkEdits tests explicitly verify version attachment. The discussion at https://github.com/microsoft/vscode/issues/123605 leaves automatic extension-host queuing versus caller sequencing undecided, while https://github.com/microsoft/vscode/issues/54773 records why version checks must remain effective. The uncertainty is the public concurrency contract, not the location of a guard; do not equate unconditional stale-edit acceptance with safe serialization.
- **Open decisions:**
  - Should workspace.applyEdit retain caller-managed sequencing, automatically serialize calls, or expose an explicit opt-in sequencing contract?
  - If sequencing is supported, should later edit ranges be interpreted against the document state at invocation or after preceding applications, and what intervening changes must still cause rejection?
