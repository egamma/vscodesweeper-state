# Issue #162555 — Support relative paths in file picker that extend up past the open workspace folder

[https://github.com/microsoft/vscode/issues/162555](https://github.com/microsoft/vscode/issues/162555)

## Summary

Keep this accepted Backlog request open: Quick Open still resolves relative paths against workspace folders, not an enclosing repository root. The older related reports cover different path-resolution cases and do not establish a duplicate.

## Change summary

Allow Quick Open to find an in-workspace file from a pasted repository-relative path when only a nested repository folder is open.

## Best solution

Support repository-relative paths for files inside the open workspace without requiring users to remove ancestor directory segments. First settle whether this is repository-aware resolution or more general ancestor-prefix matching, while preserving existing exact-path behavior and workspace search boundaries.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts`, `src/vs/workbench/services/search/common/search.ts`, `src/vs/workbench/services/search/node/fileSearch.ts`
- **Validation:** Create a repository containing packages/package_1/my_folder/foo.ts, open only packages/package_1, invoke Cmd+P/Ctrl+P, and paste packages/package_1/my_folder/foo.ts: the intended in-workspace file must be offered and open. Repeat with my_folder/foo.ts and an absolute path to preserve existing behavior; check ambiguous multi-root matches and confirm ordinary search does not expand into sibling packages.
- **Behavior:**

  > When only a nested package folder is open, a repository-relative path copied from GitHub should locate the corresponding file inside that workspace without manually removing ancestor segments. The example packages/package_1/my_folder/foo.ts must find my_folder/foo.ts under the opened package_1 folder. Existing workspace-relative and absolute-path navigation must continue to work. Normal file search must not broaden to unrelated files outside the workspace.
- **Trace:**

  > AnythingQuickAccessProvider.doFileSearch in src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts combines workspace file search with getRelativePathFileResults. The former forwards the original query to the search service; the latter resolves it against workspace folders using folder.toResource(query.original), so the reporter's repository prefix is appended beneath the already-open package folder. getAbsolutePathFileResult handles absolute and home-relative paths but does not infer a repository root. FileWalker.getSearchPath in src/vs/workbench/services/search/node/fileSearch.ts supplies only a workspace-relative path and optional workspace folder name to matching. The unresolved boundary is whether ancestor-qualified matching requires an enclosing Git repository or should work with arbitrary ancestor directory prefixes. Preserve existing exact-path handling, ranking expectations, remote URI handling, and workspace search scope. The older https://github.com/microsoft/vscode/issues/133438 and https://github.com/microsoft/vscode/issues/139845 concern active-editor-relative navigation and dot-segment normalization, respectively, rather than this exact request.
- **Open decisions:**
  - Should ancestor-qualified paths be recognized only relative to an enclosing Git repository root, or should matching also accept arbitrary ancestor directory prefixes in non-Git workspaces?
