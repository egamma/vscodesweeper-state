# Issue #318839 — REGRESSION: new default dark theme is absolute crap for syntax highlight

[https://github.com/microsoft/vscode/issues/318839](https://github.com/microsoft/vscode/issues/318839)

## Summary

Keep open as actionable theme-readability feedback: current Dark 2026 still assigns pale grey to ordinary variables and red to keywords and storage tokens. Dark Modern remains available, but switching themes does not address the requested quality of the default PHP palette; no verified older canonical covers the full report.

## Change summary

Improve default PHP syntax-color differentiation and the experience of moving existing users to Dark 2026.

## Best solution

Have the theme owners evaluate PHP variable visibility and the distinction between routine syntax and diagnostic emphasis, then agree on palette acceptance criteria. Retain Dark Modern and the existing migration opt-out rather than treating their availability as resolution of the default-theme feedback.

## Plan brief

- **Likely files:** `extensions/theme-defaults/themes/2026-dark.json`, `extensions/php/syntaxes/php.tmLanguage.json`, `src/vs/workbench/services/themes/browser/workbenchThemeService.ts`
- **Validation:** In a development build with third-party extensions disabled, compare the same PHP sample under Dark 2026 and Dark Modern, including mutable variables, parameters, keywords, storage modifiers, strings, and an actual diagnostic. Inspect token scopes with Developer: Inspect Editor Tokens and Scopes, and visually verify the agreed distinctions. Separately check the existing default-theme notification and No Thanks behavior without changing explicit theme selections.
- **Behavior:**

  > The reporter finds PHP difficult to scan after an update changes the unset default from Dark Modern to Dark 2026: routine syntax is heavily red and ordinary variables resemble unhighlighted text. The intended improvement is a default palette whose meaningful token categories remain distinguishable without competing with diagnostics. Acceptance requires an agreed visual comparison using representative PHP code, not merely confirming that tokens receive colors. Dark Modern must remain selectable, and explicitly chosen themes must remain respected.
- **Trace:**

  > Dark 2026 is registered in extensions/theme-defaults/package.json and inherits dark_modern.json while overriding tokenColors in extensions/theme-defaults/themes/2026-dark.json. Its variable.other rule is pale grey, and keyword/storage rules are red; the bundled PHP grammar in extensions/php/syntaxes/php.tmLanguage.json emits matching variable scopes. These are intentional palette definitions rather than proof of a tokenizer defect. WorkbenchThemeService.showNewDefaultThemeNotification already provides an eligible-user opt-out from the new default, so do not assume that transition protection is absent. Related maintainer discussion at https://github.com/microsoft/vscode/issues/299387#issuecomment-4024055722 supports revisiting grey-token meaning, while https://github.com/microsoft/vscode/issues/331473 provides newer evidence about variable visibility. The unresolved boundary is the desired observable palette, especially whether changes should apply globally or only to PHP; preserve other languages and existing theme-selection semantics unless the maintainer explicitly expands scope.
- **Open decisions:**
  - Which variable and routine syntax categories should be visually distinct from plain text and diagnostic emphasis in the default dark palette?
  - Should the agreed readability changes apply across Dark 2026 languages, or be limited to PHP-specific token scopes?
