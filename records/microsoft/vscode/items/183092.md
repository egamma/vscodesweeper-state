# Issue #183092 — Support 'textEdit.newText' in 'resolveSupport' of 'CompletionClientCapabilities'

[https://github.com/microsoft/vscode/issues/183092](https://github.com/microsoft/vscode/issues/183092)

## Summary

Keep open: current source still tolerates resolved insertion-text changes while explicitly declaring them unsupported, so the requested supported contract remains missing. This team-authored request needs an API and acceptance-semantics decision, not a decline close based on today's restrictions.

## Change summary

Support lazily resolving completion text while keeping the initial edit range fixed and providing usable fallback text.

## Best solution

Agree on a supported completion contract that permits expensive text computation without making acceptance unpredictably dependent on resolve timing. Settle the editor/API semantics before advertising textEdit.newText through the LSP client's resolveSupport.

- **Behavior:**

  > Language servers want to show usable completion candidates before computing expensive parameter names or context-specific snippet text. The initial range and fallback text are available immediately, while resolution may supply richer insertion text. Acceptance checks must cover resolution before acceptance, acceptance before resolution, mouse selection, keyboard selection, and subsequent typing. The supported outcome for each timing case must be explicit, including snippet placeholders and cursor behavior.
- **Trace:**

  > CompletionsAdapter.resolveCompletionItem in src/vs/workbench/api/common/extHostLanguageFeatures.ts currently forwards changed insertion text but reports it as unsupported API use. CompletionItemProvider documentation in src/vscode-dts/vscode.d.ts prohibits that mutation, and additionalTextEdits cannot overlap the main edit. In src/vs/editor/contrib/suggest/browser/suggestController.ts, primary snippet insertion is synchronous while unresolved additional edits are handled later on a best-effort basis. https://github.com/microsoft/vscode/pull/183426 preserved compatibility rather than defining a supported contract. The thread at https://github.com/microsoft/vscode/issues/183092 establishes the performance motivation but leaves acceptance timing and snippet semantics unresolved. Preserve existing completion sorting, filtering, fixed ranges, and ordinary additional-edit behavior; LSP capability advertisement must follow an agreed editor/API contract.
- **Open decisions:**
  - Should supported lazy primary-text resolution explicitly permit acceptance to insert fallback text when resolve has not finished, or must acceptance guarantee the resolved text?
  - Should the supported capability include changing snippet placeholders during resolve, or be restricted to plain-text refinement?
