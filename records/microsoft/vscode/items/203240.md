# Issue #203240 — Allow Extensions to contribute to DebugHoverContext/DebugWatchContext

[https://github.com/microsoft/vscode/issues/203240](https://github.com/microsoft/vscode/issues/203240)

## Summary

Watch-menu contributions are now supported, but the debug hover context menu still lacks an extension contribution point. Keep this team-authored Backlog request open for the remaining hover capability; no eligible older canonical was established.

## Change summary

Allow extensions to contribute commands to the debug hover and Watch context menus.

## Best solution

Support extension-contributed commands in the debug hover context menu with an agreed command-context contract, preserving the existing Watch contribution point. Resolve the remaining hover requirement without expanding this into the broader debug-visualization API.

## Plan brief

- **Likely files:** `src/vs/workbench/services/actions/common/menusExtensionPoint.ts`, `src/vs/workbench/contrib/debug/browser/debugHover.ts`, `src/vs/workbench/contrib/debug/browser/variablesView.ts`, `src/vs/workbench/contrib/debug/browser/watchExpressionsView.ts`
- **Validation:** Use a development extension contributing a command to the agreed hover menu key. Pause debugging with a nonempty object variable, expand the debug hover, invoke the contributed command from a variable row, and verify its arguments identify that row and session. Verify when-clause filtering, built-in hover actions, and existing debug/watch/context contributions remain functional.
- **Behavior:**

  > Extensions can already contribute commands to the Watch context menu, but cannot contribute to the debug hover context menu. The remaining goal is to make extension commands available on appropriate variable rows in that existing hover menu and provide usable invocation context. Acceptance should verify command visibility, when-clause filtering, and the identity of the selected variable and debug session. Existing Watch contributions and built-in debugger actions must remain unchanged.
- **Trace:**

  > The apiMenus registry in src/vs/workbench/services/actions/common/menusExtensionPoint.ts exposes debug/watch/context but no menu mapped to DebugHoverContext; the contribution handler ignores unrecognized menu keys. DebugHoverWidget's context-menu path in src/vs/workbench/contrib/debug/browser/debugHover.ts already calls openContextMenuForVariableTreeElement in variablesView.ts with MenuId.DebugHoverContext. That shared helper constructs variable context and obtains menu actions, whereas Watch uses its own expression argument path in watchExpressionsView.ts. The source establishes the missing registration surface, but not an agreed public argument contract for exposing the hover path. Keep the scope to hover menu extensibility, not replacement trees or visualization providers. Related discussion is at https://github.com/microsoft/vscode/issues/274072 and https://github.com/microsoft/vscode/issues/200880#issuecomment-2201090551; the latter explicitly identifies extension-facing context types as a design concern.
- **Open decisions:**
  - What supported command-argument contract should hover contributions receive: the existing Variables-menu context shape or a separately defined public context?
