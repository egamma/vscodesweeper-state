# Issue #340294 — Unify Agent capabilities across Chat and Agents window: tool control, local harnesses, and MCP management

[https://github.com/microsoft/vscode/issues/340294](https://github.com/microsoft/vscode/issues/340294)

## Summary

Keep open as a cross-surface capability-parity request. Existing tool controls, shared customization management, and individual MCP fixes cover parts of the request, but no verified canonical or implementation covers its full scope.

## Change summary

Provide consistent tool selection, compatible local models and session continuation, and MCP discovery, configuration, and lifecycle management across Chat and the Agents window.

## Best solution

Define a capability-based parity contract across supported harnesses, with explicit unsupported states and predictable configuration ownership. Coordinate the existing focused issues against that contract rather than treating individual fixes as completion of this broader request.

- **Likely files:** `src/vs/sessions/contrib/chat/browser/customizationHarnessService.ts`, `src/vs/workbench/contrib/chat/common/customizationHarnessService.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatToolPicker.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostToolSetEnablementService.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostActiveClientService.ts`
- **Validation:** Establish a capability matrix and manually check Chat and Agents-window sessions with Local and supported Agent Host harnesses: tool inventory and references, selection persistence, custom endpoints, scoped MCP lifecycle, and compatible continuation. Supported capabilities must remain consistent; unsupported capabilities must be explicitly explained. Repeat workspace-scoped checks in a multi-root Windows/WSL workspace.
- **Behavior:**

  > Users should encounter consistent model, tool, and MCP controls when switching between compatible Chat and Agents-window experiences. Supported tool references and selections must have predictable scope and persistence, and incompatible capabilities must be explained rather than silently omitted. Acceptance must distinguish already-supported functionality from remaining gaps and verify configuration provenance, server isolation, and compatible session continuation.
- **Trace:**

  > SessionsCustomizationHarnessService in src/vs/sessions/contrib/chat/browser/customizationHarnessService.ts receives provider-backed descriptors rather than automatically inheriting the workbench Local harness. Shared customization contracts live in src/vs/workbench/contrib/chat/common/customizationHarnessService.ts, with harness-specific compatibility and migration ownership documented in src/vs/sessions/AI_CUSTOMIZATIONS.md. AgentHostToolSetEnablementService persists tool and group overrides per session type in application storage; AgentHostActiveClientService consumes that state when publishing client tools. Tool selection and references have focused tracking at https://github.com/microsoft/vscode/issues/340041, while native Local integration and continuation are tracked at https://github.com/microsoft/vscode/issues/318358. The trace establishes partial shared infrastructure, not a complete cross-runtime parity diagnosis. Preserve provider-neutral Sessions boundaries, runtime authorization, scoped identities, and secret-storage boundaries; do not assume different runtimes can share executable session state.
- **Open decisions:**
  - Should tool selections default to harness-wide preferences, session-specific state, or per-prompt overrides, and how should those scopes interact?
  - Which compatible Chat sessions should support live continuation in the Agents window, and which should expose only import or reference capabilities?
  - Which MCP configuration source is authoritative across compatible harnesses, and what precedence and migration behavior should users observe when definitions overlap?
