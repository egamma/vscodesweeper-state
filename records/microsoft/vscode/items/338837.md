# Issue #338837 — Agent Host: prune old Claude/Codex SDK versions from sdk-cache

[https://github.com/microsoft/vscode/issues/338837](https://github.com/microsoft/vscode/issues/338837)

## Summary

Confirmed on main: AgentSdkDownloader writes each SDK version into its own cache directory (sdk-cache/<version>) but never removes older versions, so the cache grows unbounded across updates. Worth keeping open; the retention policy (immediate cleanup vs. keep-N-versions vs. age-based) is a product decision a maintainer should make before implementation.

## Change summary

Agent Host's sdk-cache directory accumulates old Claude/Codex SDK version folders indefinitely with no pruning/eviction policy.

## Best solution

Add a post-install cleanup step in agentSdkDownloader.ts that removes SDK version directories outside a chosen retention policy (e.g. keep the current + previous version) once the new version's sentinel file is written, guarding against removing a version another running Agent Host process may still be using.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentSdkDownloader.ts`
- **Validation:** A test in agentSdkDownloader.test.ts asserting that after a successful download of a new version, only the retained set of version directories remain under sdk-cache for that package/target.
- **Behavior:**

  > After Agent Host successfully downloads and installs a new SDK version, older cached versions for the same package/target that fall outside the retention policy should be removed from sdk-cache, without ever removing the version that was just successfully installed or (if kept for rollback) the immediately preceding version. A failed download/install must leave the existing cache untouched. Acceptance: a new test simulates two sequential version downloads and asserts stale version directories are pruned while the retained ones remain.
- **Trace:**

  > In src/vs/platform/agentHost/node/agentSdkDownloader.ts, _cacheDir() (~line 436) computes a per-version path under 'sdk-cache', and _download() (~line 453) extracts into a tmp dir then moves it into that versioned cacheDir once the tarball is fetched and the sentinel `.complete` file is written (~line 407, 493-509) — no code afterward enumerates or removes sibling version directories. The boundary: do not touch the download/extraction/sentinel-write path itself, only add cleanup after a successful install; avoid deleting a version directory that lacks a load or lock indicating it's in use by another running Agent Host process, per the issue's own caution.
- **Open decisions:**
  - Should cleanup delete all older versions immediately, or keep one previous version for rollback safety (or an N-version/age-based policy)?
  - Should cleanup account for another concurrently running Agent Host process that might still be using an older version, and if so how (lock file, timestamp, etc.)?
