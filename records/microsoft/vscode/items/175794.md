# Issue #175794 — Find in files: Inconsistent search results when using regex and whole word matching

[https://github.com/microsoft/vscode/issues/175794](https://github.com/microsoft/vscode/issues/175794)

## Summary

Keep open: current source still applies different whole-word rules to open-editor and disk searches, explaining both the original example and the confirmed alternation reproducer. The related older issue covers only part of this report, not a verified canonical for its full scope.

## Change summary

Make regex whole-word search results independent of whether matching files are open in an editor.

## Best solution

Make disk-search matching consistent with editor matching for the supplied Python and alternation examples. Preserve existing editor word-separator behavior and establish cross-engine acceptance tests before extending the change to broader regex semantics.

## Plan brief

- **Likely files:** `src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts`, `src/vs/base/common/strings.ts`, `src/vs/workbench/services/search/common/searchService.ts`, `src/vs/editor/common/model/textModelSearch.ts`, `src/vs/workbench/services/search/test/node/ripgrepTextSearchEngineUtils.test.ts`, `src/vs/workbench/services/search/test/node/textSearch.integrationTest.ts`
- **Validation:** Add regression cases for Foo|Bar and Bar|Foo over the supplied six-line sample, expecting only standalone Foo and Bar, and for target\([^)] over target(), target(arg=1), target(arg=2), and target(a), expecting only target(a). Compare match ranges from disk search and open-editor search, rerun after opening or closing the file, and retain the existing punctuation-and-spaces whole-word cases.
- **Behavior:**

  > With Use Regular Expression and Match Whole Word enabled, Find in Files must return the same matching ranges whether a saved candidate file is open or closed. In the supplied Foo/Bar sample, either alternation order matches only the standalone words, not their prefixed or suffixed variants. For the original Python pattern, a partial match ending inside arg must not appear only because the file is closed. Acceptance must cover both examples and preserve existing literal whole-word, punctuation, and editor word-separator behavior.
- **Trace:**

  > SearchService.getOpenEditorResults in src/vs/workbench/services/search/common/searchService.ts uses model.findMatches with word separators. TextModelSearch and Searcher in src/vs/editor/common/model/textModelSearch.ts validate boundaries against actual matched text. By contrast, getRgArgs in src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts calls createRegExp in src/vs/base/common/strings.ts, which decides boundary insertion from regex-source endpoint characters and does not group alternatives. Source inspection therefore confirms both the alternation precedence error and the missing trailing check for the original Python pattern. The uncertainty is how to achieve compatible disk-search semantics without changing editor behavior or unrelated consumers of the shared regex helper; a grouping-only correction does not complete this issue. Existing argument-generation and disk-search tests provide validation entry points. Related https://github.com/microsoft/vscode/issues/170529 covers one boundary case, while closed https://github.com/microsoft/vscode/issues/112401 concerns additional post-filtering semantics that should not be silently redesigned here.
