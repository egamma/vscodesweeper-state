# Issue #327454 — Environment variables from the first VS Code launch carry over to later windows

[https://github.com/microsoft/vscode/issues/327454](https://github.com/microsoft/vscode/issues/327454)

## Summary

Current source preserves first-launch environment variables when later launch environments omit them. Keep this open for human review because the report explicitly concerns credentials reaching unrelated windows; the security-sensitive keep-open rule overrides duplicate consolidation.

## Change summary

Prevent environment variables supplied to the first CLI launch from unexpectedly appearing in unrelated later windows and their integrated terminals.

## Best solution

Have the window/environment owners review per-launch inheritance and credential isolation, preserving intentional environment overrides without retaining omitted project secrets. Coordinate with the older matching report at https://github.com/microsoft/vscode/issues/314381, while retaining this credential-exposure report for human handling.

## Evidence

- **Current source preserves omitted variables:** src/vs/platform/windows/electron-main/windowsMainService.ts:1569 constructs each window's userEnv as { ...this.initialUserEnv, ...options.userEnv }. In the reported sequence, clearing MY_API_KEY in the second cmd.exe removes that property from its environment; its absence cannot overwrite the first-launch value.
- **Propagation into integrated terminals:** src/vs/base/parts/sandbox/electron-browser/preload.ts:83-88 merges process.env, shellEnv and userEnv. ShellEnvironmentService.getShellEnv() delegates to process.shellEnv(); LocalTerminalBackend.getShellEnvironment() consumes it. TerminalProcessManager._resolveEnvironment() passes the resulting base environment to createTerminalEnvironment(), which copies its non-null entries in src/vs/workbench/contrib/terminal/common/terminalEnvironment.ts:259. This source trace supports the reported carryover without executing VS Code.
- **Existing workaround and discussion:** The supplied discussion links https://code.visualstudio.com/docs/configure/command-line#_isolating-vs-code-instances. The reporter acknowledges --user-data-dir but explains that isolating settings, extensions and UI state is too heavy, and describes bootstrapping a clean initial window before loading project variables. Neither workaround provides ordinary per-window isolation.
- **Verified older matching report:** https://github.com/microsoft/vscode/issues/314381 is open, created 2026-05-05, and reports the same observable symptom: variables from repository A survive in integrated terminals of a later repository B window launched with code from an external terminal. Its macOS/fish/direnv scenario is a strong consolidation lead, but this item's explicit credential-exposure concern requires human handling rather than a proposed close.
- **Other related reports differ:** https://github.com/microsoft/vscode/issues/47816 remains open and asks for fresh Windows environment blocks after external environment changes. https://github.com/microsoft/vscode/issues/194736 is closed and concerns missing macOS PATH expansion in subsequent subprocesses. https://github.com/microsoft/vscode/issues/303788 concerns first-launch Visual Studio PATH replacement, not a secret omitted from a later launch.
- **Protected scope:** The issue explicitly describes an LLM API key unexpectedly appearing in unrelated windows. This meets the credential/data-exposure keep-open rule regardless of whether shared-process inheritance is documented or a matching older issue exists.
