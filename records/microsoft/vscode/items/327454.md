# Issue #327454 — Environment variables from the first VS Code launch carry over to later windows

[https://github.com/microsoft/vscode/issues/327454](https://github.com/microsoft/vscode/issues/327454)

## Summary

This describes credential/data exposure (an env var like an API key leaking into an unrelated later window's terminal), which is a hard security-sensitive keep-open case regardless of how the evidence otherwise reads — keeping open for a maintainer decision rather than proposing any close.

## Change summary

On Windows, environment variables present when the first VS Code window/main process starts are inherited by the integrated terminals of later windows opened from a separate shell with different variables set, since all windows share one main process.

## Best solution

Traced the mechanism: shell-env resolution (src/vs/platform/shell/node/shellEnv.ts, getResolvedShellEnv) explicitly skips on Windows, and app.ts resolves/caches shell env once per main-process lifetime (electron-main/app.ts afterWindowOpen -> resolveShellEnvironment), so terminals in later windows inherit the single long-lived main process's process.env rather than the env of the shell that invoked `code` for that window. A real fix would need either per-window env capture at the OS process boundary (hard given Electron's single-instance model) or clearer first-class guidance/warning about sensitive env vars and single-instance reuse; absent a maintainer decision this stays a documented architectural limitation, not a quick patch.

## Evidence

- **shellEnv skip on Windows:** src/vs/platform/shell/node/shellEnv.ts getResolvedShellEnv() returns {} immediately when isWindows is true — the shell-env resolution/caching mechanism that this label covers is a no-op on Windows, so it isn't the direct cause; the carryover instead comes from all windows sharing one long-lived Electron main process whose process.env was captured at first launch.
- **single main process:** src/vs/code/electron-main/app.ts afterWindowOpen() calls this.resolveShellEnvironment(...) once per app lifetime (line ~1614), and terminals/extension hosts spawned for any later window inherit that same main process environment.
- **maintainer-adjacent pointer:** Contributor gjsjohnmurray (CONTRIBUTOR) linked https://code.visualstudio.com/docs/configure/command-line#_isolating-vs-code-instances, which documents --user-data-dir isolation but doesn't explicitly call out this specific env-carryover-via-shared-instance case, so it's a lead, not a confirmed as-designed statement from the team.
- **related but distinct:** https://github.com/microsoft/vscode/issues/47816 is an open feature-request about terminals not picking up *new* env vars while VS Code stays running (different ask); https://github.com/microsoft/vscode/issues/194736 is closed/fixed and macOS-specific (PATH expansion), so neither is a canonical duplicate that fully owns this Windows carryover-of-secrets report.
