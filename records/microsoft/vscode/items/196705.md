# Issue #196705 — Support Monaco editor in webviews

[https://github.com/microsoft/vscode/issues/196705](https://github.com/microsoft/vscode/issues/196705)

## Summary

Keep open: the current webview API still does not provide a supported way to embed a VS Code-integrated editor. This team-authored Backlog request has concrete extension-author demand, and neither an applicable fixing commit nor a verified older duplicate was established.

## Change summary

Allow extensions to embed an editor in webviews that uses VS Code's configured shortcuts, completions, hovers, and link behavior.

## Best solution

Design a supported editor-embedding API for webviews that connects to VS Code's document and editor services rather than requiring extensions to recreate those integrations around standalone Monaco. Start with the PR comment-input scenario and establish the document identity, provider participation, and lifecycle contract before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/browser/mainThreadWebviews.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`
- **Validation:** Use an extension-development sample with a webview comment input and a normal editor for the same language. Verify configured editing shortcuts, a sample completion provider, hover provider, and link behavior in the embedded input; then close and recreate the webview to check the agreed document lifecycle and absence of stale editor instances.
- **Behavior:**

  > An extension can place a VS Code-integrated editor within a webview, such as a PR comment box, without rebuilding editor-service integration around a separate Monaco distribution. The embedded input should honor the user's applicable shortcuts and provide the completions, hovers, and link behavior available for its document and language. Acceptance should compare the embedded input with a normal editor using deterministic sample providers and verify disposal and recreation of the webview.
- **Trace:**

  > The public Webview and WebviewOptions contracts in src/vscode-dts/vscode.d.ts expose HTML, resource loading, and messaging but no editor embedding. MainThreadWebviews in src/vs/workbench/api/browser/mainThreadWebviews.ts bridges those operations without an embedded-editor endpoint. The existing proposed editorInsets API and MainThreadEditorInsets implement the opposite direction: webviews inside editor view zones, as tracked by https://github.com/microsoft/vscode/issues/85682. This establishes an API gap, not a broken existing implementation. Preserve existing webview isolation and behavior; the unresolved design starts at how an embedded editor participates in VS Code's document, provider, and lifecycle contracts. Demand and the motivating workflow are recorded in https://github.com/microsoft/vscode/issues/196705.
- **Open decisions:**
  - What TextDocument identity and lifecycle should an embedded editor expose to extensions: may it attach to an existing document, create a webview-owned document, or support both, and when is that document closed?

- **Existing-capability check:** src/vscode-dts/vscode.d.ts:9900–10055 defines WebviewOptions and Webview around HTML, script permissions, resource URIs, and message passing; it exposes no embedded TextEditor or editor-component API. window.showTextDocument opens a text document in the workbench, which does not satisfy editing inside the webview.

Its exposed bridge does not create a VS Code editor inside webview content. Standalone Monaco plus extension-authored messaging remains a workaround, not the requested shared editor integration.

That does not provide an editor inside a webview and is not a canonical duplicate.
