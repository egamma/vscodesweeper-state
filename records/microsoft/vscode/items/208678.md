# Issue #208678 — Download Code from Currently Opened Folder in VSCode Workspace

[https://github.com/microsoft/vscode/issues/208678](https://github.com/microsoft/vscode/issues/208678)

## Summary

Keep open: this team-authored Backlog request was explicitly accepted as expanding `explorer.download` to take specified URIs, and current main still ignores command arguments. The hard keep-open rule applies, and no open canonical issue owns the request.

## Change summary

Allow extensions to invoke the workspace download functionality for an explicit set of files or folders instead of relying on the Explorer selection.

## Best solution

Give `explorer.download` a documented argument contract for explicit workspace resource URIs while preserving its current no-argument behavior of downloading the Explorer selection or workspace roots.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/fileActions.ts`, `src/vs/workbench/contrib/files/browser/fileImportExport.ts`, `src/vs/workbench/contrib/files/test/browser/fileActions.test.ts`
- **Validation:** Add targeted `Files - Download` unit tests covering explicit resource arguments and the unchanged no-argument Explorer-selection/workspace-root fallback, then run `scripts/test.sh --grep "Files - Download"`.
- **Behavior:**

  > An extension can execute `explorer.download` with explicitly identified workspace files or folders and receive the existing browser/native download experience for exactly those resources. Calling the command without resource arguments continues to download the current Explorer selection, or all workspace roots when there is no selection. Acceptance includes multiple files and folders and preservation of the existing fallback behavior.
- **Trace:**

  > `DOWNLOAD_COMMAND_ID` is registered in `src/vs/workbench/contrib/files/browser/fileActions.ts`; its `downloadFileHandler` currently accepts only `ServicesAccessor`, reads `IExplorerService.getContext(true)`, and never inspects command arguments. It passes the resulting `ExplorerItem[]` to `FileDownload.download` in `src/vs/workbench/contrib/files/browser/fileImportExport.ts`, whose source contract already supports multiple resources. Generic resource-selection helpers in `src/vs/workbench/contrib/files/browser/files.ts` demonstrate nearby command-argument handling, but this command needs a deliberate public argument contract rather than selection inference. Preserve no-argument behavior and the existing destination picker, progress, cancellation, and browser/native download paths.
- **Open decisions:**
  - Should the documented command contract accept one URI, an array of URIs, or both forms for extension callers?

## Evidence

- **current source:** On current main, `downloadFileHandler` in `src/vs/workbench/contrib/files/browser/fileActions.ts` accepts no command argument and derives sources solely from `explorerService.getContext(true)`, falling back to `explorerService.roots`; `explorer.download` therefore cannot receive the requested URI list.
- **existing implementation boundary:** `FileDownload.download` in `src/vs/workbench/contrib/files/browser/fileImportExport.ts` already processes an array of download sources, so the missing capability is primarily command argument handling and source resolution rather than a new download pipeline.
