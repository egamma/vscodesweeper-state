# Issue #223416 — Find/Replace field does not scroll to cursor position when typing a newline

[https://github.com/microsoft/vscode/issues/223416](https://github.com/microsoft/vscode/issues/223416)

## Summary

The defect remains traceable on current main: Ctrl+Enter inserts and selects the newline programmatically without revealing the new caret position. The issue is correctly routed and should remain open as a bug.

## Change summary

Make multiline Find and Replace inputs scroll to reveal the caret after Ctrl+Enter inserts a newline.

## Best solution

Update `InputBox.insertAtCursor` to reveal the resulting selection within a flexible-width textarea, covering both editor Find/Replace and workspace Search inputs without changing ordinary value assignment behavior.

## Evidence

- **current source path:** `src/vs/editor/contrib/find/browser/findWidget.ts` lines 893–940 handles Ctrl+Enter by calling `InputBox.insertAtCursor('\n')` for both Find and Replace.
- **defect on main:** `src/vs/base/browser/ui/inputbox/inputBox.ts` lines 637–647 replaces the value, calls `setSelectionRange`, and lays out the control, but performs no caret-reveal or internal scroll adjustment. This differs from native paste behavior.
- **shared impact:** `src/vs/workbench/contrib/search/browser/searchWidget.ts` uses the same insertion helper, so the underlying correction should remain in `InputBox` rather than be duplicated in the editor Find widget.
- **related issue:** https://github.com/microsoft/vscode/issues/248209 concerns replacement-match navigation after inserting a newline, not failure to reveal the input caret, so it is not a canonical duplicate.
