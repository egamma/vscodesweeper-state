# Issue #140684 — Web: Allow non-repository, non-filesystem temporary folders

[https://github.com/microsoft/vscode/issues/140684](https://github.com/microsoft/vscode/issues/140684)

## Summary

Keep this accepted request open: current web filesystem infrastructure does not provide the requested standalone temporary-folder workflow or browser-independent archive export. It has 21 upvotes, appropriate area labels, and no verified older canonical issue was found.

## Change summary

Allow vscode.dev users to create or import a temporary folder without a repository or local filesystem access, export it as an archive, and optionally publish it to GitHub.

## Best solution

Provide an explicit browser-backed scratch-folder workflow with Explorer editing and archive import/export independent of File System Access APIs. Settle reload/lifetime semantics and the GitHub publication boundary before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/web.main.ts`, `src/vs/workbench/contrib/files/browser/fileActions.ts`, `src/vs/workbench/contrib/files/browser/fileActions.contribution.ts`, `src/vs/workbench/contrib/files/browser/fileImportExport.ts`, `src/vs/workbench/services/dialogs/browser/fileDialogService.ts`, `extensions/github/package.json`
- **Validation:** In Firefox or a browser without File System Access APIs, create a temporary root from an empty vscode.dev window, create and edit nested files, import an archive, and export/reimport the folder archive with paths and contents preserved. Verify reload behavior against the agreed lifetime contract, confirm existing local/remote folder workflows are unchanged, and validate GitHub publication separately if included.
- **Behavior:**

  > A user can begin a multi-file project in vscode.dev without first creating a remote repository or granting local directory access. An empty temporary folder or an imported archive appears as an editable Explorer root, and its contents can be exported together as an archive in browsers without File System Access APIs. The request also includes publishing that folder to GitHub. Acceptance must explicitly cover folder lifetime across reloads and whichever publication scope the maintainer approves.
- **Trace:**

  > web.main.ts registers an in-memory Schemas.tmp provider, but its temporary-workspace startup handling recreates workspace configuration with an empty folders array; neither establishes a user-facing scratch-folder workflow. explorer.newFolder is registered in fileActions.ts and exposed in fileActions.contribution.ts only for an existing workspace folder, with openExplorerAndCreate operating beneath an existing Explorer root. FileDownload.doDownloadBrowser in fileImportExport.ts requires browser directory-picker support for directory downloads and otherwise handles individual files, leaving archive export uncovered. FileDialogService in services/dialogs/browser/fileDialogService.ts routes unsupported-browser operations to warnings or individual-file alternatives. The existing github.publish registration is publication prior art, not proof of browser-backed folder support. Preserve existing local-folder permissions, remote-repository opening, and individual-file upload/download behavior. The remaining uncertainty is the scratch-folder lifecycle and publication contract, not whether a memory filesystem primitive exists; the request and empty-repository motivation are recorded at https://github.com/microsoft/vscode/issues/140684.
- **Open decisions:**
  - Should temporary folder contents survive page reloads or browser restarts, or be session-only with an explicit loss warning?
  - Must the initial feature include publishing the temporary folder to GitHub, and does publication replace the temporary workspace with the remote repository or retain a separate scratch copy?
