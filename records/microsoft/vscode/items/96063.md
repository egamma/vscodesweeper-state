# Issue #96063 — Auto-hide Activity Bar exactly like Windows taskbar

[https://github.com/microsoft/vscode/issues/96063](https://github.com/microsoft/vscode/issues/96063)

## Summary

Keep this accepted Backlog request open: current auto-hide settings do not provide taskbar-style edge-hover reveal of the Activity Bar. The request has 30 upvotes, and the related sidebar issue does not satisfy the same-observable-behavior duplicate bar for this re-reviewed item.

## Change summary

Allow the Activity Bar to hide automatically and reappear when the pointer reaches its edge, independently of the sidebar.

## Best solution

Design an opt-in Activity Bar auto-hide interaction in the workbench layout, preserving independent sidebar visibility and keyboard access. Decide whether the revealed bar overlays content or temporarily reserves layout space before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/workbench.contribution.ts`, `src/vs/workbench/browser/layout.ts`, `src/vs/workbench/browser/parts/activitybar/activitybarPart.ts`, `src/vs/workbench/services/layout/browser/layoutService.ts`
- **Validation:** Manually verify the chosen opt-in mode with the sidebar both open and closed: the Activity Bar hides while idle, appears when the pointer reaches its edge, stays usable while interacting, and hides after leaving. Verify keyboard access and that disabling the mode preserves existing location, manual visibility, and count-based auto-hide behavior.
- **Behavior:**

  > Provide an optional taskbar-style auto-hide mode for the Activity Bar, not for the entire sidebar. Users can reveal the hidden bar by moving the pointer to its edge and interact with its controls before it hides again. Sidebar visibility remains independent, and Activity Bar controls remain accessible by keyboard. Existing behavior is unchanged when the mode is disabled.
- **Trace:**

  > The configuration surface in src/vs/workbench/browser/workbench.contribution.ts offers Activity Bar positioning, permanent hiding, and count-based auto-hide for top/bottom placement. LayoutSettings in src/vs/workbench/services/layout/browser/layoutService.ts defines those settings; SidebarPart.shouldShowCompositeBar() in src/vs/workbench/browser/parts/sidebar/sidebarPart.ts confirms that autoHide depends on visible container count rather than pointer position. The vertical ActivitybarPart lives in src/vs/workbench/browser/parts/activitybar/activitybarPart.ts, while persistent visibility is coordinated by src/vs/workbench/browser/layout.ts. No execution was performed; the source establishes the capability mismatch, not a completed interaction design. Keep sidebar auto-hide outside this request and preserve existing visibility and keyboard behavior. https://github.com/microsoft/vscode/issues/3742 is related sidebar work, not a same-symptom canonical. The unresolved boundary is how transient reveal affects layout and keyboard focus.
- **Open decisions:**
  - Should the temporarily revealed Activity Bar overlay adjacent content or reserve space and reflow the layout?
  - When keyboard navigation targets an auto-hidden Activity Bar, should it reveal and remain visible until focus leaves?
