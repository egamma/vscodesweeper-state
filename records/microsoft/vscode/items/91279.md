# Issue #91279 — Use VS Code's syntax highlighting in Markdown preview

[https://github.com/microsoft/vscode/issues/91279](https://github.com/microsoft/vscode/issues/91279)

## Summary

Keep open: the Markdown preview still uses highlight.js and separate token colors rather than the editor's highlighting. The request has 46 upvotes and explicit maintainer acceptance; newer highlighting support in the rich Markdown editor does not complete this preview request.

## Change summary

Make Markdown preview code blocks use VS Code's installed language highlighting and active theme, including the requested semantic-highlighting parity.

## Best solution

Bring the built-in Markdown preview's code-block highlighting into alignment with the editor's language grammars and active theme. Plan semantic-token support explicitly, since the existing proposed TextMate highlighting API does not provide the semantic parity requested in the original report.

## Plan brief

- **Likely files:** `extensions/markdown-language-features/src/markdownEngine.ts`, `extensions/markdown-language-features/media/highlight.css`, `extensions/markdown-language-features/package.json`, `extensions/markdown-language-features/src/preview/markdownEditorProvider.ts`, `src/vscode-dts/vscode.proposed.documentSyntaxHighlighting.d.ts`
- **Validation:** Compare identical TypeScript snippets in the editor and Markdown preview with semantic highlighting enabled; repeat after changing the active theme and with an extension-contributed language. Verify theme updates, grammar availability, safe rendering, and the agreed semantic-highlighting behavior without regressing existing Markdown rendering or plugin contributions.
- **Behavior:**

  > Markdown preview code blocks currently differ from the editor in token colors and supported languages, with the original report specifically highlighting the difference when TypeScript semantic highlighting is enabled. The desired outcome is preview highlighting consistent with the active editor theme and installed language support. Acceptance must cover theme switching and extension-contributed languages, and must distinguish TextMate parity from semantic-token parity rather than claiming one delivers the other.
- **Trace:**

  > The traditional preview creates its MarkdownIt engine in extensions/markdown-language-features/src/markdownEngine.ts; getMarkdownOptions supplies a synchronous highlight.js callback and escapes languages highlight.js does not recognize. Preview styles include media/highlight.css, which contains separate token colors. The rich Markdown editor already calls vscode.languages.computeFullSyntaxHighlighting in src/preview/markdownEditorProvider.ts, but the proposed contract in src/vscode-dts/vscode.proposed.documentSyntaxHighlighting.d.ts guarantees TextMate grammar and theme support only. https://github.com/microsoft/vscode/issues/56356 tracks the related general API, while https://github.com/microsoft/vscode/issues/91375 addressed access to semantic tokens. The unresolved boundary is how preview snippets obtain meaningful semantic context and whether delivery is staged; preserve Markdown plugin contributions, escaping, and existing preview behavior outside highlighting.
- **Open decisions:**
  - Should this request be delivered in stages with editor TextMate/theme parity first and semantic highlighting tracked explicitly as remaining work, or should completion require semantic parity?
  - What semantic context should a fenced snippet use when its highlighting depends on imports, project types, or declarations outside the block?

## Evidence

- **Current preview implementation:** extensions/markdown-language-features/src/markdownEngine.ts:398–415 imports highlight.js and calls hljs.highlight for recognized languages, otherwise escaping the source. This path does not use the editor's grammars, theme token map, or semantic tokens.
- **Existing-capability check:** extensions/markdown-language-features/package.json registers markdown.styles and bundles media/highlight.css as a preview stylesheet. That stylesheet defines separate .hljs token colors; custom CSS can restyle these classes but does not supply editor grammar or semantic-token parity.
