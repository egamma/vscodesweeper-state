# Issue #245108 — Edits: undo/redo does not restore decoration for the edit

[https://github.com/microsoft/vscode/issues/245108](https://github.com/microsoft/vscode/issues/245108)

## Summary

Keep open: editor undo/redo still does not restore Copilot review decisions and their decorations. The discussion establishes that restoration should also work after undoing subsequent manual edits; existing checkpoint commands do not cover that editor-history behavior.

## Change summary

Make accepting or rejecting a Copilot edit undoable and redoable, restoring its undecided review decorations and controls when the decision is undone.

## Best solution

Integrate Copilot review decisions with editor undo history so undo restores both the appropriate text and the pending review state, including after intervening manual edits. Plan the baseline and review-state restoration contract before implementation rather than treating this as a decoration-only change.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedFileEntry.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedDocumentEntry.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingTextModelChangeService.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCodeEditorIntegration.ts`
- **Validation:** In an existing text file, obtain Copilot changes and test accepting and rejecting both an individual hunk and the whole file. Editor Undo must restore the pending review decorations and controls, including when accepting changed no text; Redo must reapply the decision. Repeat after two manual edits: undo those edits first, then undo the review decision, and verify text, unrelated hunks, and review state remain consistent.
- **Behavior:**

  > Accepting or rejecting a Copilot suggestion should be reversible through normal editor undo/redo, not merely through chat checkpoint restoration. Undoing the decision should restore the suggestion's undecided decorations and accept/discard controls, even when acceptance made no textual change. Subsequent manual edits should undo in chronological order before the review decision is restored. Redo should reapply the decision without losing manual edits or altering unrelated pending suggestions.
- **Trace:**

  > ChatEditingModifiedFileEntry.acceptDeferred() and rejectDeferred() settle entry state independently of editor text history. ChatEditingModifiedDocumentEntry._createUndoRedoElement() records streaming text edits, while _doAccept() calls keep() and _doReject() calls undo() on ChatEditingTextModelChangeService. That service replaces or clears the review baseline, treats later editor changes through _mirrorEdits(), and suppresses diff computation for settled entries; hunk acceptance modifies the original model rather than the editor's modified model. ChatEditingCodeEditorIntegration renders the resulting differences, so restoring decorations alone would not restore a valid decision state. The requested chronological behavior is already stated in https://github.com/microsoft/vscode/issues/245108#issuecomment-2765656536; uncertainty begins at preserving and restoring baseline, hunk, and entry metadata coherently with shared editor undo infrastructure. Preserve ordinary manual-edit ordering and keep request/checkpoint undo distinct; notebook, created-file, and bulk-action consumers need boundary assessment before choosing an implementation scope.
