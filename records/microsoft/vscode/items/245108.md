# Issue #245108 — Edits: undo/redo does not restore decoration for the edit

[https://github.com/microsoft/vscode/issues/245108](https://github.com/microsoft/vscode/issues/245108)

## Summary

A real UX gap remains on current main, but restoring accepted or rejected edit state through editor undo requires a product decision about undo semantics. Keep it open under discussion.

## Change summary

Make editor undo and redo restore the pending Copilot edit state, including decorations and Keep/Undo controls.

## Best solution

Represent Keep/Undo decisions as undo-redo elements that restore both document snapshots and `ModifiedFileEntryState`, with defined behavior after intervening manual edits. Implement this consistently across text and notebook chat-editing entries.

## Evidence

- **current source:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedFileEntry.ts` changes the entry state directly in `acceptDeferred` and `rejectDeferred`; those state transitions are not added to the editor undo stack.
- **undo boundary:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedDocumentEntry.ts` creates a `SingleModelEditStackElement` when agent edits begin, while `_doAccept` and `_doReject` subsequently mutate the baseline or document without an undo element that restores the pending decision state.
- **decoration behavior:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingTextModelChangeService.ts` clears diff state after Keep/Undo and suppresses diff computation whenever the entry state is no longer `Modified`, so ordinary text undo cannot restore the decorations.
- **open design question:** The discussion at https://github.com/microsoft/vscode/issues/245108#issuecomment-2765500238 identifies an unresolved choice between immediate reversal and restoration after intervening manual edits; https://github.com/microsoft/vscode/issues/245108#issuecomment-2765656536 favors putting the decision itself on the undo stack.
