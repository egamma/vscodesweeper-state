# Issue #123934 — Git - panel incorrectly shows case-sensitive renames on case-insensitive FS

[https://github.com/microsoft/vscode/issues/123934](https://github.com/microsoft/vscode/issues/123934)

## Summary

The current decoration cache still merges case-distinct Git paths on case-insensitive filesystems, allowing the deleted path's badge to overwrite the added path's badge. Keep this open; the older related gutter issue reports a different observable symptom and is not a duplicate canonical.

## Change summary

After a case-only rename and staged content replacement, Source Control shows both paths as deleted instead of distinguishing the added and deleted files.

## Best solution

Preserve Git's case-distinct status decorations in the Source Control view without changing filesystem URI identity. The shared decoration cache needs a solution that also preserves other providers' caching, invalidation, and parent-decoration behavior.

## Evidence

- **Reporter trigger and maintainer lead:** https://github.com/microsoft/vscode/issues/123934 documents git mv makefile Makefile followed by replacing and staging its contents: Git reports added Makefile and deleted makefile, while Source Control displays D for both. The discussion points specifically to the decoration service.
- **Git retains distinct statuses:** extensions/git/src/repository.ts maps staged A and D entries to INDEX_ADDED and INDEX_DELETED, with status letters A and D. extensions/git/src/decorationProvider.ts stores and retrieves their decorations by exact URI strings, so the Git provider itself keeps these two paths distinct.
- **Current source collision:** src/vs/workbench/services/decorations/browser/decorationsService.ts constructs _data with TernarySearchTree.forUris(key => uriIdentityService.extUri.ignorePathCasing(key)). On a case-insensitive provider, _ensureEntry returns the same DecorationEntry for Makefile and makefile; selective change processing fetches both into that entry, and _keepItem overwrites the same provider slot. Both subsequent getDecoration calls therefore return the same status decoration.
- **Filesystem casing contract:** src/vs/platform/uriIdentity/common/uriIdentityService.ts sets ignorePathCasing when a filesystem provider lacks PathCaseSensitive. This connects the cache collision to the reporter's case-insensitive filesystem rather than to incorrect Git rename detection.
- **Default rendering and workaround:** extensions/git/package.json defaults git.decorations.enabled to true. Under that setting, repository.ts does not supply per-resource status icons, and ResourceRenderer.renderIcon in src/vs/workbench/contrib/scm/browser/scmViewPane.ts enables file-decoration badges. Disabling git.decorations.enabled selects per-resource icons instead, but bypasses rather than fixes the shared-cache defect.
