# Issue #167065 — Allow multiple extensions to contribute to the same remote explorer view

[https://github.com/microsoft/vscode/issues/167065](https://github.com/microsoft/vscode/issues/167065)

## Summary

Keep open: current core still rejects duplicate view IDs and supports only one tree data provider per view, so the requested independent contributions remain unsupported. This team-authored, accepted backlog request needs a shared-view contract before implementation.

## Change summary

Allow SSH and Tunnels to independently contribute content to the same Remote Explorer view without a coordinating extension calling their commands.

## Best solution

Provide core-supported composition for independently owned Remote Explorer contributions, preserving the unified destination without requiring the Remote Explorer extension to broker provider commands. Settle contribution ordering and ownership of shared view controls before coordinating adoption by the remote extensions.

## Plan brief

- **Likely files:** `src/vs/workbench/api/browser/viewsExtensionPoint.ts`, `src/vs/workbench/api/browser/mainThreadTreeViews.ts`, `src/vs/workbench/api/common/extHostTreeViews.ts`, `src/vs/workbench/contrib/remote/browser/remote.ts`, `src/vs/workbench/contrib/remote/browser/explorerViewItems.ts`, `src/vs/workbench/api/test/browser/mainThreadTreeViews.test.ts`, `src/vs/workbench/api/test/browser/extHostTreeViews.test.ts`, `src/vs/workbench/api/test/browser/extHostTreeViewDisposal.test.ts`
- **Validation:** Add focused tree-view tests with two independently owned contributions targeting the agreed Remote Explorer view: both must appear, refresh and item actions must reach the correct provider, and disposing either contribution must leave the other functional. Run the relevant mainThreadTreeViews, extHostTreeViews, and extHostTreeViewDisposal suites; manually verify SSH and Tunnels remain independently usable when either extension is disabled.
- **Behavior:**

  > SSH and Tunnels should independently supply their own content to the same Remote Explorer destination without a coordinating extension invoking provider commands. Both contributions must coexist, update independently, and dispatch item actions to their owner. Disabling or disposing one contributor must not remove or break the other. Existing single-provider views must retain their behavior.
- **Trace:**

  > ViewsExtensionHandler.addViews in src/vs/workbench/api/browser/viewsExtensionPoint.ts rejects duplicate IDs even for remote contributions. MainThreadTreeViews.$registerTreeViewDataProvider and ExtHostTreeViews._createExtHostTreeView key provider state by view ID, while the main-thread viewer has one dataProvider, establishing that removing contribution validation alone would not implement composition. RemoteViewPaneContainer in src/vs/workbench/contrib/remote/browser/remote.ts and SwitchRemoteViewItem in explorerViewItems.ts already handle remote-specific filtering and authority grouping, but not shared provider ownership. The maintainer explicitly requested core support before extension adoption at https://github.com/microsoft/vscode/issues/167065#issuecomment-1331030108. Keep the scope on Remote Explorer composition and preserve ordinary views' uniqueness and single-provider semantics unless a broader API is explicitly approved. The unresolved boundary is the user-visible composition contract and the extension adoption work outside this checkout.
- **Open decisions:**
  - How should independently contributed SSH and Tunnels content be presented and ordered within the shared view: distinct provider sections or a combined root list?
  - Which contributor, or core, owns shared view-level title, message, badge, and toolbar behavior when contributors supply conflicting values?

## Evidence

- **Current contribution restriction:** src/vs/workbench/api/browser/viewsExtensionPoint.ts:179–207 describes remote view IDs as globally unique. ViewsExtensionHandler.addViews at lines 471–480 rejects both repeated IDs within the contribution batch and IDs already registered, without a Remote Explorer exception.
- **Single-provider runtime:** src/vs/workbench/api/browser/mainThreadTreeViews.ts:MainThreadTreeViews.$registerTreeViewDataProvider stores providers under treeViewId and assigns viewer.dataProvider to one provider. src/vs/workbench/api/common/extHostTreeViews.ts:_createExtHostTreeView likewise stores one ExtHostTreeView per ID; neither path composes independently owned contributions.

These mechanisms do not merge multiple providers into the same view ID, so they do not satisfy the central request.
