# Issue #13953 — Feature Request: Show all errors and warnings in project for all JavaScript and TypeScript files, not just opened ones

[https://github.com/microsoft/vscode/issues/13953](https://github.com/microsoft/vscode/issues/13953)

## Summary

Keep open: the experimental setting provides partial project-wide diagnostics, but maintainers explicitly identify this issue as tracking its replacement. Current source still depends on open buffers and requests diagnostics for one selected file's project, rather than establishing complete workspace coverage.

## Change summary

Show and maintain JavaScript and TypeScript errors and warnings across project files, including files that have never been opened.

## Best solution

Deliver reliable project-wide diagnostics through the built-in JavaScript/TypeScript language support, with complete project coverage and updates that do not depend on keeping affected files open. Evaluate the native TypeScript direction identified by the maintainer rather than treating the existing experimental switch as the finished solution.

## Plan brief

- **Likely files:** `extensions/typescript-language-features/package.json`, `extensions/typescript-language-features/src/tsServer/bufferSyncSupport.ts`, `extensions/typescript-language-features/src/typescriptServiceClient.ts`, `extensions/typescript-language-features/src/languageFeatures/diagnostics.ts`
- **Validation:** In a configured TypeScript project, open only an exported function's file and change its signature so an unopened consumer becomes invalid; verify Problems reports the consumer and clears it when the signature is restored. Open and close the consumer without fixing it and verify its diagnostics remain accurate. Repeat with multiple configured projects, project references, and JavaScript with checking enabled; assess responsiveness on a large workspace. These are acceptance scenarios for the planning session, not checks executed during this read-only review.
- **Behavior:**

  > Users should be able to see JavaScript and TypeScript project errors and warnings in Problems without opening every affected file. Changing an exported signature must expose errors in unopened consumers, and correcting it must clear those errors. Closing a file must not make a still-valid project diagnostic disappear. Coverage must respect project configuration and remain responsive on large projects.
- **Trace:**

  > The experimental option is registered in extensions/typescript-language-features/package.json as js/ts.tsserver.experimental.enableProjectDiagnostics. GetErrRequest in src/tsServer/bufferSyncSupport.ts switches to geterrForProject for the first selected file, while BufferSyncSupport builds requests from synced buffers rather than enumerating workspace projects. closeResource fires onDelete, and src/typescriptServiceClient.ts deletes that resource's diagnostics through DiagnosticsManager in src/languageFeatures/diagnostics.ts. This establishes partial coverage but does not settle how every configured project is discovered, refreshed, or supported by the selected TypeScript server. Maintainer comments at https://github.com/microsoft/vscode/issues/168410#issuecomment-1347604841 and https://github.com/microsoft/vscode/issues/252117#issuecomment-3138176302 reject further investment in the current experimental approach and identify native TypeScript work as a possible replacement. Planning should establish the supported server path and performance envelope; preserve existing validation settings and avoid expanding this TypeScript/JavaScript request into a universal analyzer for unrelated languages.
