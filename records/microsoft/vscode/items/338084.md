# Issue #338084 — Webview can stay on its old content when its HTML is replaced while that content is still loading

[https://github.com/microsoft/vscode/issues/338084](https://github.com/microsoft/vscode/issues/338084)

## Summary

The reported race remains in the current source: an old frame's delayed load event can cancel the replacement frame's activation fallback and strand messages. Keep this open while the explicitly linked fixing PR is reviewed and landed.

## Change summary

Prevent replacing still-loading webview HTML from leaving the replacement frame permanently pending and host-to-webview messages undelivered.

## Evidence

- **Current source confirms timer ownership race:** src/vs/workbench/contrib/webview/browser/pre/index.html declares the shared loadTimeout at line 433. In hookupOnLoadHandlers, lines 1172–1191, each new frame replaces that timer, while every frame's load listener clears whichever timer is currently stored. Thus A's delayed load can clear B's fallback; B's later load sees an undefined timer and skips activation.
- **Activation and message delivery consequences:** In the same file, onLoad at lines 1115–1167 activates a frame and drains pendingMessages only when its document matches the current pending frame. A's late callback cannot activate B. The hostMessaging 'message' handler at lines 1264–1275 queues messages whenever a pending frame exists, explaining both the stale visible content and undelivered messages.
- **Complete reproduction evidence:** https://github.com/microsoft/vscode/issues/338084 supplies a controlled sequence using held nested documents to fire A's load during B's fallback window. The reporter records failure in all five stock-host runs and successful delivery in all five control runs; the later comment confirms testing on 1.139.1.
