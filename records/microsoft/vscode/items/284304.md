# Issue #284304 — Subagent spawned by subagent inherits root tools by default, not the spawner's tools

[https://github.com/microsoft/vscode/issues/284304](https://github.com/microsoft/vscode/issues/284304)

## Summary

Keep open: this team-authored bug has a concrete reproduction and independent confirmation that nested subagents receive the root agent's tools instead of the spawning custom agent's declared tools.

## Change summary

Nested subagents should run with the spawning custom agent's identity or effective tool set rather than inheriting the root agent's tools.

## Best solution

Define and implement nested-subagent identity and tool inheritance so an unnamed nested invocation runs as the spawning custom agent, or require an explicit agent name with model guidance that preserves that identity and its declared permissions.

## Plan brief

- **Likely files:** _(none given)_
- **Validation:** Add an agent-host or chat subagent test with root, orchestrator, and implementer agents that asserts a nested invocation exposes the intended custom agent's declared tools and cannot access undeclared agents or root-only tools.
- **Behavior:**

  > When a custom agent spawns another subagent, the nested subagent must not silently receive the root agent's tools. Its effective identity and tool permissions must follow one documented rule: either an omitted agent name means the spawning custom agent, or the invocation is rejected until that agent is named explicitly. Acceptance should cover a three-level root → orchestrator → implementer flow and verify that only the selected custom agent's declared tools and accessible agents are available.
- **Trace:**

  > The issue and confirmed reproduction establish that nested agent invocation loses the spawning custom-agent context and falls back to the root tool set. The affected boundary is the chat/agent-host subagent invocation path that resolves an omitted or selected agent identity into effective tools and accessible agents. Preserve explicit invocation of a different permitted custom agent and do not broaden an agent's declared permissions. https://github.com/microsoft/vscode/issues/333369 is related to omitted agent identity but is newer and reports a different observable policy bypass, so it should inform the design rather than absorb this issue.
- **Open decisions:**
  - Should an unnamed nested subagent invocation inherit the spawning custom agent's identity, or should the agent name become mandatory for nested invocations?
  - When a custom agent explicitly invokes another permitted custom agent, should the callee use its own declared tools exclusively or an intersection with the caller's permissions?

## Evidence

- **confirmed reproduction:** A commenter reproduced the behavior on VS Code 1.109.5 with separate Orchestrator and Implementer agent files: the invoked Implementer received the Orchestrator tool set instead of its own declared edit and terminal tools.
- **maintainer diagnosis:** The team-authored issue identifies the intended direction: the third subagent should run as the named custom agent, either by default or by requiring the nested invocation to name that agent.
- **distinct related issue:** https://github.com/microsoft/vscode/issues/333369 concerns omitted agent names bypassing disable-model-invocation; it is newer than this re-reviewed issue and does not establish the same reporter-observable tool-inheritance symptom, so it is not a valid canonical duplicate.
- **additional impact:** A later comment reports that the same boundary may let subagents call agents outside the accessible-agent list, reinforcing that effective subagent permissions are not scoped as declared.
