# Issue #119002 — Use a content hash for dirty write protection instead of checking only the size (risk of data loss)

[https://github.com/microsoft/vscode/issues/119002](https://github.com/microsoft/vscode/issues/119002)

## Summary

Keep open: current source still permits overwriting an external edit that changes content without changing file size. The newer content-comparison machinery does not cover this case, and maintainers have explicitly retained this request while discussing its performance tradeoffs.

## Change summary

Detect same-size external content changes during saving instead of treating unchanged size as sufficient evidence that overwriting is safe.

## Best solution

Provide content-aware save-conflict detection in the shared file-writing path, preserving normal saves when only metadata changes and retaining explicit overwrite behavior. Settle the protection-versus-performance policy for providers that repeatedly advance modification times without changing contents.

## Plan brief

- **Likely files:** `src/vs/platform/files/common/fileService.ts`, `src/vs/platform/files/common/files.ts`, `src/vs/workbench/services/textfile/common/textFileEditorModel.ts`, `src/vs/workbench/services/workingCopy/common/storedFileWorkingCopy.ts`, `src/vs/platform/files/test/node/diskFileService.integrationTest.ts`
- **Validation:** Add targeted file-service coverage using the actual original mtime and etag: externally replace content with different bytes of the same length, advance mtime, and attempt to save divergent editor contents; expect FILE_MODIFIED_SINCE and unchanged external bytes. Also cover metadata-only changes, identical outgoing/disk content, explicit overwrite, and buffered/streamed writes. Manually repeat the issue's six steps with autosave disabled.
- **Behavior:**

  > Saving a dirty editor must detect an external content change even when the external edit preserves the original byte length. The save should enter the existing conflict-resolution flow rather than silently overwrite the external edit. Metadata-only timestamp changes must not create false conflicts, and writing content already identical to disk must remain allowed. Explicit overwrite behavior must remain available. Acceptance includes the original six-step scenario and coverage for valid original metadata, not merely an arbitrary mismatched etag.
- **Trace:**

  > FileService.validateWriteFile in src/vs/platform/files/common/fileService.ts gates conflict detection on advanced mtime and an etag comparison using the original mtime plus current disk size. The etag helper in src/vs/platform/files/common/files.ts contains no content identity, so an unchanged size bypasses the entire content-comparison branch. TextFileEditorModel passes its last resolved metadata during save; StoredFileWorkingCopy has an analogous metadata-based save path. The current content comparison checks outgoing bytes against disk, not the original loaded content, and only runs after a metadata conflict. https://github.com/microsoft/vscode/issues/241381#issuecomment-2676031356 confirms that this machinery does not complete the request. Preserve metadata-only false-positive avoidance, identical-content saves, and explicit overwrite semantics across providers. The unresolved boundary is how much protection remains when a provider repeatedly changes timestamps without changing contents; no heuristic fallback policy has been accepted.
- **Open decisions:**
  - When a provider repeatedly advances modification times without changing contents, should content-aware protection remain active on subsequent saves, or may it automatically fall back to weaker detection that can miss same-size external edits?
