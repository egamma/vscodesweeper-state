# Issue #119002 — Use a content hash for dirty write protection instead of checking only the size (risk of data loss)

[https://github.com/microsoft/vscode/issues/119002](https://github.com/microsoft/vscode/issues/119002)

## Summary

The data-loss gap remains on current main: dirty-write validation still ignores externally changed files when their size is unchanged. This accepted Backlog feature request is already correctly routed to file I/O and should remain open.

## Change summary

Strengthen dirty-write protection so an external same-length edit cannot be overwritten without a save-conflict warning.

## Best solution

Extend `FileService.validateWriteFile` to detect newer, same-size disk contents without imposing an unconditional read or hash cost, likely using a stored content identity or adaptive per-provider heuristic. Add integration coverage for an external same-length edit followed by saving a dirty editor.
