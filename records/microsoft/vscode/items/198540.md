# Issue #198540 — "View: Show GitHub" keyboard shortcut focuses wrong activity view

[https://github.com/microsoft/vscode/issues/198540](https://github.com/microsoft/vscode/issues/198540)

## Summary

The issue remains valid: a maintainer reproduced the wrong-focus behavior, and current main still binds registered-container commands to the original container while per-view focus commands follow moved views. The expected handling of a stale container shortcut remains under discussion.

## Change summary

After GitHub views are moved into a custom container, a keybinding for the original "View: Show GitHub" command focuses an unrelated view instead of the moved GitHub views.

## Best solution

Ensure a command for an emptied or obsolete registered view container never focuses an unrelated view. Prefer disabling it with clear feedback directing users to the location-independent "Focus on … View" commands, unless the workbench owners choose to make the old command follow the moved views.

## Plan brief

- **Likely files:** `src/vs/workbench/services/views/browser/viewsService.ts`, `src/vs/workbench/common/views.ts`
- **Validation:** Move all views out of a registered sidebar container, invoke a user keybinding for its original "View: Show …" command, and verify that no unrelated view is focused; then verify each per-view "Focus on … View" command opens the view in its current custom container.
- **Behavior:**

  > When all views have been moved out of a registered view container, invoking a retained keybinding for that container must not focus Explorer or any other unrelated view. The command should either follow the moved view content or decline with clear feedback, according to the maintainer's chosen contract. Location-independent per-view focus commands and the `view ` quick-access picker must continue to open moved views correctly.
- **Trace:**

  > ViewsService.registerOpenViewContainerAction in src/vs/workbench/services/views/browser/viewsService.ts captures the registered ViewContainer and invokes openViewContainer with its original ID. In the same file, registerFocusViewAction invokes openView with the view descriptor ID, allowing IViewDescriptorService to resolve the view's current custom container. The maintainer reproduction and current implementation therefore preserve the stale-container-command path described in https://github.com/microsoft/vscode/issues/198540. Keep the scope to commands whose registered container has lost its views; do not change normal container toggling or per-view focus behavior.
- **Open decisions:**
  - After every view leaves a registered container, should its existing "View: Show …" command become unavailable with user-visible feedback, or should it follow the moved view or views into their current container?

## Evidence
