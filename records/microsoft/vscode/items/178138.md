# Issue #178138 — Not clear how to share attribute definitions between "attach" and "launch" configurations

[https://github.com/microsoft/vscode/issues/178138](https://github.com/microsoft/vscode/issues/178138)

## Summary

This remains a valid, accepted debug extensibility gap: a maintainer confirmed that shared launch/attach attribute definitions were not implemented and said VS Code could support them. The Backlog milestone and existing debug routing support keeping it open.

## Change summary

Allow debugger extensions to share custom launch configuration property schemas between `launch` and `attach`, or document the required duplication if sharing remains unsupported.

## Best solution

Define and document a supported schema-reuse mechanism for `contributes.debuggers.configurationAttributes`, ideally using JSON Schema references or a shared schema definition that both `launch` and `attach` can consume.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/common/debugSchemas.ts`, `src/vs/workbench/contrib/debug/common/debug.ts`
- **Validation:** Add an extension-point/schema test using one shared custom property definition for both `launch` and `attach`, then verify that both generated launch configuration schemas expose and validate that property.
- **Behavior:**

  > A debugger extension can define a custom launch configuration property once and reuse it for both `launch` and `attach`, with validation and IntelliSense behaving identically in each configuration type. The supported package.json shape is documented with a working example. Existing debugger contributions that duplicate property definitions continue to work unchanged.
- **Trace:**

  > The issue concerns the `contributes.debuggers.configurationAttributes` extension contract and the launch configuration schemas assembled by the debug contribution path. The discussion establishes that no supported reuse mechanism was known in 2023, and a maintainer explicitly said the earlier request was not implemented but could be supported. The uncertainty begins at the public schema contract: whether standard `$defs`/`$ref` should resolve within contributed attributes or whether VS Code should expose another shared-definition shape. Preserve compatibility with existing debugger manifests and avoid changing launch/attach runtime semantics.
- **Open decisions:**
  - Should the public contribution contract support standard JSON Schema `$defs`/`$ref`, or introduce a VS Code-specific shared-definition mechanism?
  - Must shared definitions be scoped to one debugger contribution, or may references target definitions elsewhere in the extension manifest?
