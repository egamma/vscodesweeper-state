# Issue #206582 — Allow changing the font color of an editor widget

[https://github.com/microsoft/vscode/issues/206582](https://github.com/microsoft/vscode/issues/206582)

## Summary

Keep open: the cited CSS workaround remains in current source, and existing theme customization does not provide the requested per-CodeEditorWidget foreground control. This team-authored Backlog request has neither a verified fixing commit nor a same-scope canonical duplicate.

## Change summary

Provide a supported way for individual CodeEditorWidget instances to use a different text foreground, such as input.foreground, without targeting generated token CSS classes.

## Best solution

Provide an editor-owned, instance-scoped foreground mechanism for embedded input editors, preserving ordinary editor theming and syntax coloring. The editor/theming owners should establish its contract before implementation.

SuggestEnabledInput.style() in suggestEnabledInput.ts:310-313 sets the container foreground from inputForeground or its style override; this remains a consumer-specific CSS solution, not a general widget contract.
- **Existing capability does not cover the ask:** workbench.colorCustomizations is registered in src/vs/workbench/services/themes/common/themeConfiguration.ts; editor.foreground supplies the theme-level editor foreground. src/vs/editor/common/config/editorOptions.ts exposes no per-instance text foreground option, and CodeEditorWidget.updateOptions() in src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts:446-447 forwards IEditorOptions to its configuration. Global theme customization does not let an embedded input independently follow input.foreground.
- **Token styling boundary:** src/vs/editor/common/languages/supports/tokenization.ts:413-419 generates explicit .mtkN color rules from the token color map. This explains why setting a container foreground alone is insufficient and why the existing consumer overrides .mtk1.
