# Issue #336470 — Let virtual documents inherit source-editor visibility for push diagnostics

[https://github.com/microsoft/vscode/issues/336470](https://github.com/microsoft/vscode/issues/336470)

## Summary

Current main confirms a real extension-API gap: virtual documents can be opened and updated, but cannot declare that an open source editor represents them for push-diagnostic scheduling. This team-authored API request has no verified canonical and should be routed to the API, TypeScript, and notebook owners for contract design.

## Change summary

Allow an extension-managed virtual language document to inherit the visibility and lifecycle of its open source document or notebook cell so language extensions can schedule push diagnostics without showing another editor.

## Best solution

Define a proposed, disposable API contract for associating a virtual document with its represented source resource, with language providers explicitly opting into syntax-diagnostic scheduling. Preserve existing validation settings and keep semantic diagnostics gated on provider-specific project-context support.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostDocumentContentProviders.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/test/browser/extHostDocumentContentProvider.test.ts`, `extensions/typescript-language-features/src/tsServer/bufferSyncSupport.ts`
- **Validation:** Add extension-host tests covering association registration, disposal, and source visibility changes, plus a TypeScript language-features test showing that a syntax-invalid virtual document is scheduled only while its represented source is open and that existing validation settings still suppress diagnostics.
- **Behavior:**

  > An extension can associate a virtual language document with the source document or notebook cell visible to the user, and dispose that association. A participating language extension treats the virtual document as visible for syntax-diagnostic scheduling without opening an implementation-detail editor tab. Closing the source or disposing the association stops that inherited visibility; validation settings and virtual-content updates continue to govern diagnostics, while semantic diagnostics remain unavailable unless the language provider explicitly supports the required project context.
- **Trace:**

  > TextDocumentContentProvider and workspace.openTextDocument in src/vscode-dts/vscode.d.ts create and update virtual documents but expose no represented-source metadata. ExtHostDocumentContentProvider in src/vs/workbench/api/common/extHostDocumentContentProviders.ts forwards provider registration and content changes only. In extensions/typescript-language-features/src/tsServer/bufferSyncSupport.ts, TabResourceTracker derives visibility exclusively from tabs, with a built-in notebook-cell-to-notebook special case, and shouldValidate rejects other hidden virtual resources when project diagnostics are disabled. Semantic diagnostics are independently constrained by configuration/fileSchemes.ts and languageProvider.ts, so that boundary must not be weakened as part of syntax scheduling. The closed requests https://github.com/microsoft/vscode/issues/159911 and https://github.com/microsoft/vscode/issues/59650 concern different contracts and are not canonical duplicates.
- **Open decisions:**
  - Should the public contract expose a general represented-source relationship observable by participating language extensions, or a diagnostics-specific capability negotiated with individual providers?
  - Can one virtual document be represented by multiple simultaneously open source resources, and what visibility and lifetime semantics should that public contract guarantee?
