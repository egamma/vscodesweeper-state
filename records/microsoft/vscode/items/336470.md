# Issue #336470 — Let virtual documents inherit source-editor visibility for push diagnostics

[https://github.com/microsoft/vscode/issues/336470](https://github.com/microsoft/vscode/issues/336470)

## Summary

Well-researched API proposal from a contributor with deep source tracing (TabResourceTracker, BufferSyncSupport, getSemanticSupportedSchemes) showing there's genuinely no existing supported way to associate a virtual document with its visible source editor for push diagnostics; no maintainer has weighed in on API shape yet, so this stays open pending that discussion.

## Change summary

Add a supported extension API letting a virtual document declare it represents a visible source editor/notebook cell, so embedded-language extensions can push syntax diagnostics onto it without opening a separate tab.

## Best solution

A vscode.languages (or similar) API for registering a visibility/lifecycle association between a virtual TextDocument and its source editor/cell, which built-in language services (and third-party ones) can consult for diagnostic scheduling — needs an API owner to scope and design, likely starting as a proposed API.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/vscode.proposed.*.d.ts`, `extensions/typescript-language-features/src/tsServer/bufferSyncSupport.ts`
- **Validation:** Once an API shape is agreed, a test asserting a registered virtual-document association causes the built-in TS/JS extension (or a sample embedded-language extension) to schedule syntax diagnostics for the virtual document while its source editor is visible.
- **Behavior:**

  > An extension should be able to declare that a virtual TextDocument (created e.g. via TextDocumentContentProvider) represents content embedded in a currently-visible source editor or notebook cell, without opening a separate tab for the virtual document. Language services (built-in and third-party) should be able to use that declared relationship to decide whether to compute and push diagnostics for the virtual document, honoring normal validation settings and document-update lifecycle.
- **Trace:**

  > Traced in extensions/typescript-language-features/src/tsServer/bufferSyncSupport.ts, TabResourceTracker/shouldValidate today only recognizes native notebook-cell URIs via the tab tracker, with no equivalent for extension-created virtual URIs; extensions/typescript-language-features/src/configuration/fileSchemes.ts's getSemanticSupportedSchemes further restricts semantic diagnostics by scheme. No generic vscode API surface for this relationship currently exists. Scope boundary: syntax-only push diagnostics tied to visibility, not a general pull-diagnostics API (declined at https://github.com/microsoft/vscode/issues/159911) and not full virtual-workspace semantic parity (https://github.com/microsoft/vscode/issues/59650). Where uncertainty starts: what the API surface looks like and whether/how the built-in TS extension should be updated to honor it.
- **Open decisions:**
  - Should this be a new public vscode API (e.g. a document-association registration) or an extension of an existing mechanism, and should it launch as a proposed API first?
  - Should the association be scoped generically to any TextDocument/editor, or specifically to notebook cells as in the motivating Pylance use case?
  - Should the built-in TypeScript/JavaScript extension be updated to consume this relationship as a reference implementation, or is this purely a platform API for third parties?

## Evidence

- **no existing API found:** Author traced extensions/typescript-language-features/src/tsServer/bufferSyncSupport.ts (TabResourceTracker/shouldValidate) and fileSchemes.ts (getSemanticSupportedSchemes) on current main and found no mechanism for an extension-created virtual URI to inherit its source editor's visibility.
- **scoped distinctly from prior asks:** Author explicitly distinguishes this from the declined generic pull-diagnostics request (https://github.com/microsoft/vscode/issues/159911) and from broader virtual-workspace TS support (https://github.com/microsoft/vscode/issues/59650) — this is narrower (visibility/lifecycle relationship for push diagnostics only).
- **concrete downstream motivation:** Public Pylance discussion https://github.com/microsoft/pylance-release/issues/4969 describes the notebook-cell-magic request-forwarding use case this would unblock.
