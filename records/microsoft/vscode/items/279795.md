# Issue #279795 — Debug Hover: Node filter for objects

[https://github.com/microsoft/vscode/issues/279795](https://github.com/microsoft/vscode/issues/279795)

## Summary

Keep open: the debug hover inherits a tree Find/filter capability, but that does not establish the requested reusable filter for object hovers. The issue is already correctly routed to debug and accepted into Backlog; neither its age nor its four upvotes warrants closing it.

## Change summary

Allow a reusable object-property filter in debug hovers so Laravel users can consistently focus on the attributes node.

## Best solution

Build on the existing workbench tree filtering experience rather than introduce a separate PHP-specific control. First settle how a chosen filter applies across object hovers and how long it is retained, while keeping hidden properties readily recoverable.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugHover.ts`, `src/vs/workbench/contrib/debug/browser/debugEditorContribution.ts`, `src/vs/platform/list/browser/listService.ts`, `src/vs/workbench/contrib/debug/test/browser/debugHover.test.ts`
- **Validation:** In a PHP/Laravel debug session, focus an object hover and exercise list.find in filter mode with attributes. Check filtering, clearing, moving between objects in the same editor and another editor, stepping, and restarting debugging against the chosen retention contract; verify ordinary unfiltered hovers remain unchanged.
- **Behavior:**

  > The reporter wants object hovers to keep showing a chosen property node, such as attributes, until the filter is changed or removed. A user must be able to discover the active filter and recover the full object without modifying the debuggee. Acceptance should cover successive object hovers, changing or clearing the filter, and the agreed retention boundary. Existing unfiltered inspection should remain available.
- **Trace:**

  > DebugHoverWidget.create() in src/vs/workbench/contrib/debug/browser/debugHover.ts constructs a WorkbenchAsyncDataTree with property-name keyboard navigation. The shared workbench tree setup in src/vs/platform/list/browser/listService.ts already supplies Find and the workbench.list.defaultFindMode setting; list.find is registered in src/vs/workbench/browser/actions/listCommands.ts. DebugHoverWidget retains its tree when hidden and replaces its input in beforeRender(), so same-widget filtering may already cover part of the workflow, but no saved object-hover filter preference is restored when a widget is created. The PHP debugger discussion at https://github.com/xdebug/vscode-php-debug/issues/1079 places the generic hover UI request in core. Planning should first exercise the existing Find/filter behavior and establish what remains missing, without changing DAP variable fetching or unrelated tree consumers.
- **Open decisions:**
  - Should the selected filter apply to every object hover, or only a narrower context such as the current editor, debug session, or object type?
  - Should the filter survive only successive hovers, or also debug-session restarts and window reloads?

## Evidence
