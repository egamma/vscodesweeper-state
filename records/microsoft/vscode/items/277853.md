# Issue #277853 — Customize Key Binding for default Agent

[https://github.com/microsoft/vscode/issues/277853](https://github.com/microsoft/vscode/issues/277853)

## Summary

Keep open: individual custom-agent commands partially reduce the picker friction, but current main still lacks a stable keybinding command whose target is a user-selected default agent. This is also a team-authored feature request, and no issue-referencing completion commit or true duplicate was found.

## Change summary

Allow a stable chat keybinding to open or switch to a user-selected default built-in or custom agent instead of always targeting the built-in Agent mode.

## Best solution

Provide a stable default-agent command whose target can be selected and persisted, while retaining the existing commands for opening specific agents. A maintainer should first settle whether this default is an explicit preference or derived from the last-used agent, its persistence scope, and its fallback behavior when unavailable.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/actions/chatActions.ts`, `src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts`, `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts`
- **Validation:** Add a targeted chat action test showing that a stable default-agent command selects the configured default across a new chat or mode switch, survives the chosen persistence boundary, falls back according to the decided policy when unavailable, and leaves existing per-agent commands unchanged.
- **Behavior:**

  > Users can assign one durable keybinding to their preferred default chat agent, including a custom agent, without binding directly to that agent's generated command. Invoking it opens or switches chat to the selected default according to clearly defined persistence and fallback semantics. Existing keybindings for specific built-in and custom agents continue to work. Acceptance covers selection, persistence, unavailable-agent behavior, and compatibility with the existing command surface.
- **Trace:**

  > In src/vs/workbench/contrib/chat/browser/actions/chatActions.ts, `ModeOpenChatGlobalAction` binds commands directly to an `IChatMode`; built-in Agent receives its own fixed command and keybinding, while `PrimaryOpenChatGlobalAction` opens chat without representing a selected default agent. In src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts, `ChatAgentActionsContribution` dynamically registers a separate action for every uniquely named custom agent. Current session restoration in src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts can recover a stored custom-agent mode, but that session-state behavior does not define a user-selected global default command. Preserve the direct per-agent commands and avoid coupling the new semantics accidentally to whichever widget happened to be focused. The responsive-layout issue https://github.com/microsoft/vscode/issues/272502 is related UX work but does not own this behavior.
- **Open decisions:**
  - Should the keybinding target an explicitly selected default agent, or should the default follow the most recently used agent?
  - Is the selected default persisted per user/profile, per workspace, or only for the current session?
  - When the selected custom agent is unavailable or renamed, should the command fall back to built-in Agent, retain an unresolved preference, or ask the user to choose another default?
