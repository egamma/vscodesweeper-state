# Issue #32088 — Provide an API to show hover-like tooltip

[https://github.com/microsoft/vscode/issues/32088](https://github.com/microsoft/vscode/issues/32088)

## Summary

Keep open: keyboard hover commands address much of the discussion, but they do not provide an extension-controlled tooltip that updates to a larger expression on repeated invocation. This accepted Backlog request has 34 upvotes, and no verified older canonical owns the remaining API requirement.

## Change summary

Allow extensions to show custom expression information in a hover-like tooltip and expand the expression scope on repeated shortcut presses.

## Best solution

Define a supported extension contract for showing and updating expression hovers without moving the caret or requiring dismissal between invocations. Decide whether this belongs in the existing hover-provider model or a separately controlled tooltip API, preserving normal hover and accessibility behavior.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vscode-dts/vscode.proposed.editorHoverVerbosityLevel.d.ts`, `src/vs/editor/contrib/hover/browser/hoverActions.ts`, `src/vs/editor/contrib/hover/browser/contentHoverWidgetWrapper.ts`, `src/vs/editor/contrib/hover/browser/markdownHoverParticipant.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`
- **Validation:** Use a test language extension on a nested expression: the first shortcut invocation shows its type, and subsequent invocations at the unchanged caret show types for successively enclosing expressions without requiring Escape. Verify editor focus remains available in ordinary keyboard mode, explicit dismissal works, and mouse hovers and screen-reader focus behavior remain unchanged.
- **Behavior:**

  > A language extension can display expression information in an editor hover-like tooltip from a keyboard command. Repeating that command at the same caret can replace the information with the type of a successively larger enclosing expression without dismissing the tooltip first. The interaction must not require moving the caret or unnecessarily taking editor focus. Acceptance includes unchanged ordinary mouse hover behavior, explicit dismissal, and preserved accessible interaction.
- **Trace:**

  > ShowOrFocusHoverAction in src/vs/editor/contrib/hover/browser/hoverActions.ts immediately shows the existing provider-backed hover at the caret and exposes focus controls, not custom content. ContentHoverWidgetWrapper._startShowingOrUpdateHover and _startHoverOperationIfNecessary in src/vs/editor/contrib/hover/browser/contentHoverWidgetWrapper.ts skip recomputation for an unchanged anchor, so invoking that command repeatedly is not a general content-update contract. MarkdownHoverParticipant obtains content through hover providers; the stable HoverProvider contract exposes neither an update event nor invocation context. The proposed editorHoverVerbosityLevel contract adds previousHover and verbosityDelta, making it relevant to investigate, but it is not stable and its finalization is separately requested at https://github.com/microsoft/vscode/issues/333269. The uncertainty is the extension-facing ownership and update contract, not whether keyboard hover commands exist. Preserve existing provider aggregation, ordinary hover dismissal, and accessibility-specific focus behavior.
- **Open decisions:**
  - Should extensions supply independently controlled, command-only tooltip content, or should this capability remain provider-backed and participate in normal hover aggregation?
  - Should repeated invocation expand the expression through an explicit extension-controlled update contract, or through the expandable-hover verbosity contract?

## Evidence

- **Original requirement and discussion:** https://github.com/microsoft/vscode/issues/32088 requests custom tooltip content and progressively larger expression scopes on repeated shortcut presses. The 2020-11-09 comment reports improvements to keyboard hover behavior, but does not establish that the original extension API requirement was implemented.
- **Existing keyboard capabilities:** src/vs/editor/contrib/hover/browser/hoverActions.ts implements editor.action.showHover using HoverStartMode.Immediate and supports focus: 'noAutoFocus'; editor.action.hideHover provides explicit dismissal, and ShowDefinitionPreviewHoverAction addresses keyboard definition preview. These cover several secondary concerns in the comments, but showHover accepts focus options rather than extension-supplied content or an expression range.
- **Remaining update limitation:** In src/vs/editor/contrib/hover/browser/contentHoverWidgetWrapper.ts, _startShowingOrUpdateHover returns without recomputing when the new anchor equals the visible hover's anchor. _startHoverOperationIfNecessary also skips an unchanged anchor. Repeating showHover at the same caret therefore does not itself refresh provider content for a larger expression.
