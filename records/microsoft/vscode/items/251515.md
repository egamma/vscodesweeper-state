# Issue #251515 — Support Storing Toolset Files Directly Within the Workspace

[https://github.com/microsoft/vscode/issues/251515](https://github.com/microsoft/vscode/issues/251515)

## Summary

This accepted Backlog request remains necessary: current main loads `.toolsets.jsonc` files only from the active user profile, not from workspace folders. It has 45 community upvotes and explicit maintainer support, while the later workspace-scoped report is younger and should not replace this re-reviewed issue as the canonical tracker.

## Change summary

Allow repositories to version and share reusable toolset definitions that workspace agents can reference instead of duplicating tool lists.

## Best solution

Make this the canonical workspace-toolsets issue and design a bounded first phase that discovers trusted workspace toolset files, exposes their named sets to workspace agents, reports unresolved references, and preserves the existing user-profile toolset format. Decide separately whether file-path references, deny semantics, organization-level policy, and resolved-tool introspection belong in that first phase.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/tools/toolSetsContribution.ts`, `src/vs/workbench/contrib/chat/test/browser/tools/toolSetsContribution.test.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/promptFileParser.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/languageProviders/promptValidator.ts`
- **Validation:** Add targeted toolset contribution tests showing that a toolset file in the selected workspace location is discovered and removed on file deletion, remains isolated between multi-root folders, and can be referenced by a workspace agent; add parser/validator tests for whichever reference syntax is selected and for missing or invalid references.
- **Behavior:**

  > A repository can commit reusable toolset definitions in a documented workspace location, and agents in that workspace can reference those definitions without copying each tool list. User-profile toolsets and the existing `tools: []` agent syntax continue to work. Workspace definitions are resolved with deterministic multi-root behavior, and invalid files or unresolved references produce actionable diagnostics rather than being ignored. Acceptance must cover discovery, updates and deletion, agent resolution, multi-root isolation, and backward compatibility.
- **Trace:**

  > `UserToolSetsContributions._initToolSets` in `src/vs/workbench/contrib/chat/browser/tools/toolSetsContribution.ts` currently observes only `currentProfile.promptsHome`, lists its immediate children, and creates user-sourced toolsets from matching `.toolsets.jsonc` files. The workspace customization location machinery in `src/vs/workbench/contrib/chat/common/promptSyntax/config/promptFileLocations.ts` already distinguishes workspace and user sources for agents, prompts, instructions, and skills, but has no toolset location entry. Agent metadata remains list-only through `promptFileParser.ts`, `promptsService.ts`, and `promptValidator.ts`. Preserve user-profile discovery and simple string-list agent files; do not fold organization policy or mandatory security enforcement into the first implementation unless the maintainer explicitly selects that scope. https://github.com/microsoft/vscode/issues/259183 is a younger report of the same gap, while https://github.com/microsoft/vscode/issues/312724 is a later closed umbrella proposal without a fixing PR.
- **Open decisions:**
  - Which workspace location is the supported public contract: a single `.vscode/toolsets.jsonc`, files under a dedicated `.github/toolsets` directory, or configurable source folders consistent with other chat customizations?
  - Should agents reference workspace toolsets through the existing string entries in `tools`, through explicit file paths, or through the proposed object-form `tools.extends` contract?
  - Is the first phase limited to reusable named allow-lists, or must it also define deny precedence and composition semantics?
  - Are organization-level toolsets and policy-enforced restrictions part of this feature's initial scope, or a separate enterprise-policy design?

## Evidence

- **current source gap:** `UserToolSetsContributions._initToolSets` in `src/vs/workbench/contrib/chat/browser/tools/toolSetsContribution.ts` derives its only discovery folder from `IUserDataProfileService.currentProfile.promptsHome`, watches that folder, and loads matching `.toolsets.jsonc` files; it does not enumerate workspace folders.
- **agent schema limitation:** `src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsService.ts` and `promptFileParser.ts` model agent `tools` as `readonly string[]` / `string[]`; `promptValidator.ts` accepts only an array or comma-separated string, so the proposed object-form inheritance and file references are not implemented.
