# Issue #268190 — VSCode crashes when opening files if GLib >= 2.83

[https://github.com/microsoft/vscode/issues/268190](https://github.com/microsoft/vscode/issues/268190)

## Summary

The GLib-dependent native-dialog crash needs confirmation on a current build and a diagnostic crash stack. Source inspection identifies the native-dialog boundary but does not establish a fix or a verified duplicate.

## Change summary

Opening a file or folder through the File menu crashes VS Code when locally installed GLib is 2.83 or newer.

## Best solution

Native file and folder dialogs should work with the affected GLib installation without terminating VS Code. Obtain current-build diagnostics to determine whether the correction belongs in VS Code's integration or Electron/GTK/GLib; the simple file dialog is an interim workaround, not resolution.

## Evidence

- **Reported version-dependent crash:** https://github.com/microsoft/vscode/issues/268190 reports a crash with extensions disabled in VS Code 1.104.1 / Electron 37.3.1 after installing GLib 2.83–2.86 under /usr/local, while GLib 2.80–2.82 works. There are no confirming comments or current-build results; the supplied Crashpad messages do not identify the crashing function.
- **Current native-dialog boundary:** src/vs/platform/dialogs/electron-main/dialogMainService.ts: doPick constructs the reported Open Folder properties, and showOpenDialog acquires the logged file-dialog lock before calling electron.dialog.showOpenDialog. This traces the trigger to native dialog invocation, but cannot establish an environment-dependent native crash or its root cause without execution and a crash stack.
- **Existing workaround:** src/vs/workbench/contrib/files/browser/files.contribution.ts registers files.simpleDialog.enable. In src/vs/workbench/services/dialogs/electron-browser/fileDialogService.ts, shouldUseSimplified causes pickFileAndOpen and pickFolderAndOpen to use the built-in simplified picker instead of the native host. This bypasses the implicated native-dialog path but does not repair it.
- **Canonical search:** GitHub searches for GLib crashes, GLib dialogs, and version 2.83 did not establish an older open issue owning this report. The older similar report https://github.com/microsoft/vscode/issues/207345 is closed and points to https://github.com/microsoft/vscode/issues/230454, also closed.
- **Related crash has a different established cause:** https://github.com/microsoft/vscode/issues/230454#issuecomment-2418352959 attributes the older Snap crash to shared-mime-info 2.4 and bundled GLib 2.64, with a workaround in newer GLib. That does not establish coverage of this report's regression specifically with GLib 2.83 or newer; neither a duplicate close nor reuse of that fix is justified.
- **Inspection limits:** The checkout is shallow, so local git history cannot establish a historical fixing commit. No build, installation, or runtime reproduction was performed, and the checkout remained unchanged.
