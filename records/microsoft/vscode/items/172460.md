# Issue #172460 — Setting trim_trailing_whitespace = true breaks undo history

[https://github.com/microsoft/vscode/issues/172460](https://github.com/microsoft/vscode/issues/172460)

## Summary

The bug remains source-reproducible on current main: trimming whitespace after an undo pushes a new edit, and the undo/redo service explicitly destroys the redo stack when a new element is pushed. The issue should remain open while the intended handling of save-time edits is designed.

## Change summary

Saving with `files.trimTrailingWhitespace` enabled clears redo history when whitespace is trimmed after an undo.

## Best solution

Preserve valid redo operations across save-time whitespace cleanup while keeping the model, editor selections, document-change notifications, and on-disk content synchronized. The undo/redo representation may need to rebase or otherwise incorporate the cleanup rather than treating it as an ordinary divergent edit.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/codeEditor/browser/saveParticipants.ts`, `src/vs/workbench/contrib/codeEditor/test/browser/saveParticipant.test.ts`, `src/vs/editor/common/model/editStack.ts`, `src/vs/platform/undoRedo/common/undoRedo.ts`
- **Validation:** Add a save-participant test that creates trailing indentation, types and undoes text, runs `TrimWhitespaceParticipant` for an explicit save, then asserts that redo restores the text while the whitespace remains trimmed; also verify that the trim emits the expected model-content change.
- **Behavior:**

  > With `files.trimTrailingWhitespace` enabled, saving after an undo must trim eligible whitespace without discarding a still-valid redo operation. Invoking redo must restore the previously undone text, and the editor model must remain synchronized with the saved content. The save-time trim must continue to emit normal document-change notifications and preserve selections.
- **Trace:**

  > TrimWhitespaceParticipant in src/vs/workbench/contrib/codeEditor/browser/saveParticipants.ts computes the cleanup and calls `ITextModel.pushEditOperations`. That reaches EditStack.pushEditOperation in src/vs/editor/common/model/editStack.ts; after an undo there is no appendable last element, so it pushes a new element through IUndoRedoService. The service contract in src/vs/platform/undoRedo/common/undoRedo.ts states that pushing an element destroys the redo stack, directly explaining the report. The boundary is save-time whitespace cleanup and its interaction with existing future edits; ordinary user edits must retain their current branch-invalidating behavior, and model change events must not be bypassed.
- **Open decisions:**
  - Should save-time cleanup be represented inside the existing future edit, rebased across future edits, or supported by a distinct undo/redo operation that does not invalidate the future stack?
  - How should redo operations whose ranges overlap or shift because of trimmed whitespace be transformed or invalidated?
  - Should the same preservation semantics apply to other content-changing save participants such as final-newline insertion, final-newline trimming, and formatting?
