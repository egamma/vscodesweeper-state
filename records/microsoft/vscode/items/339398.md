# Issue #339398 — Local harness: parent agent PreToolUse deny propagates to child subagents

[https://github.com/microsoft/vscode/issues/339398](https://github.com/microsoft/vscode/issues/339398)

## Summary

Traced the described delegation flow in current main's runSubagentTool.ts: when a coordinator delegates to a named child agent, the code explicitly discards the caller's own agent-scoped hooks and uses only the named subagent's frontmatter hooks (plus global workspace hook files). This matches the documented design ('scoped to this agent only') and directly contradicts the reported propagation.

## Change summary

A parent custom agent's agent-scoped PreToolUse deny hook was reported to override a delegated child agent's own allow hook for the same tool, blocking commands the child should be permitted to run.

## Best solution

If this still reproduces on the latest Insiders build, it would need a fresh repro with logs/output-channel traces showing which hook object actually fired, since the current delegation code path (runSubagentTool.ts) does not thread the caller's frontmatter hooks into a named child invocation.

- **top-level coordinator hooks are not threaded into the running-subagent map:** The `_runningSubagents` map (and thus `callingSubagent`) is populated only inside RunSubagentTool invocations (line 416), not for the top-level agent's own chat request, so a top-level coordinator's frontmatter hooks (merged into the request in chatServiceImpl.ts:1718-1728) are never available to be inherited by a delegated named child in the first place.
- **documented design:** extensions/copilot/assets/prompts/skills/agent-customization/references/agents.md:133 — 'Custom agents support inline `hooks` in frontmatter. These hooks execute shell commands at agent lifecycle points and are scoped to this agent only.' — matching the code's behavior, not the reported propagation.
- **per-request hook source:** extensions/copilot/src/extension/prompts/node/panel/toolCalling.tsx:300 executes the PreToolUse hook using `promptContext.request?.hooks`, i.e. the specific (sub)agent request's own hooks object, not a session-wide/global state that could carry over a parent's hook.
