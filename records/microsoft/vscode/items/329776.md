# Issue #329776 — Support awaited cleanup before agent-created worktrees are removed

[https://github.com/microsoft/vscode/issues/329776](https://github.com/microsoft/vscode/issues/329776)

## Summary

Keep open: current source supports worktree-created setup tasks, but the inspected archive and deletion paths do not provide awaited user-defined cleanup before removal. The related Git/worktree umbrella explicitly preserves this narrower request rather than replacing it.

## Change summary

Expose an awaited cleanup lifecycle while an agent-created worktree still exists, covering archive and permanent session deletion.

## Best solution

Provide a host-coordinated pre-removal lifecycle that workspace tooling can participate in, preserving access to worktree-local metadata until cleanup settles. Decide the supported task/API surface and failure, timeout, and explicit override semantics before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/shared/worktreeIsolation.ts`, `src/vs/platform/agentHost/node/agentSideEffects.ts`, `src/vs/platform/agentHost/node/agentService.ts`, `src/vs/sessions/contrib/chat/browser/worktreeCreatedTaskDispatcher.ts`, `src/vs/workbench/contrib/tasks/common/tasks.ts`, `src/vs/workbench/contrib/tasks/common/jsonSchema_v2.ts`
- **Validation:** After agreeing on the contract, add lifecycle tests using a deferred cleanup participant and a recording Git service: archive and permanent deletion must not call removeWorktree until cleanup settles, and the worktree must remain accessible during cleanup. Cover rejection, timeout, explicit remove-anyway behavior, and sessions without configured cleanup; run the targeted worktreeIsolation and agentSideEffects unit suites.
- **Behavior:**

  > Workspace tooling can finish cleanup of resources provisioned for an isolated agent session before VS Code removes its managed worktree. Cleanup runs with access to the existing worktree and applies to both Mark as Done/archive and permanent deletion. Acceptance checks must demonstrate ordering with deliberately delayed cleanup and the agreed failure, timeout, and explicit override behavior. Sessions without cleanup retain their existing lifecycle behavior; crash reconciliation is outside this request.
- **Trace:**

  > The task run-mode enum and schema support worktreeCreated but no removal lifecycle. WorktreeCreatedTaskDispatcher manages setup-task process handles on archive/removal, which is not an awaited external-resource cleanup contract. AgentSideEffects handles SessionIsArchivedChanged through the shared worktree controller; _cleanupWorktreeOnArchive performs Git preservation checks and directly removes the worktree. AgentService's permanent deletion path deletes session data and invokes removeSessionWorktree, whose implementation also directly calls Git removal. The remaining uncertainty is how workspace tooling participates across the host/client boundary and which public failure contract applies, not whether the existing setup mode supplies cleanup. Preserve branch protection, commit-failure retention, ordinary task behavior, and provider-neutral lifecycle ownership. https://github.com/microsoft/vscode/issues/336620 supplies broader design context but explicitly retains this narrower issue.
- **Open decisions:**
  - Should the supported participation surface be a worktreeRemoving task mode, an awaited extension API, or both?
  - On cleanup failure or timeout, should removal remain blocked until an explicit override, and what should happen for unattended automatic cleanup?
  - Which removal-reason and stable session/worktree identity fields should be guaranteed to cleanup participants?
