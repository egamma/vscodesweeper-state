# Issue #235898 — Git - add a delay before showing git blame information

[https://github.com/microsoft/vscode/issues/235898](https://github.com/microsoft/vscode/issues/235898)

## Summary

Keep open: built-in Git blame still has no display delay, and disabling or restyling the decoration does not satisfy the request. The older selection-dragging report covers a narrower interaction, not the same requested behavior.

## Change summary

Delay inline Git blame decoration rendering briefly to reduce visual noise during editor interaction.

## Best solution

Support a short quiet period before inline blame appears in the built-in Git extension, with the timing and default behavior agreed by the area maintainer. Preserve the independent status-bar blame experience.

## Plan brief

- **Likely files:** `extensions/git/src/blame.ts`, `extensions/git/package.json`, `extensions/git/package.nls.json`
- **Validation:** With inline blame enabled in a committed file, navigate rapidly between lines and verify the agreed quiet period before the final line's annotation appears. Switch editors or disable inline blame during that period and verify no stale annotation appears; confirm status-bar blame retains its existing behavior.
- **Behavior:**

  > The reporter finds immediate inline blame updates noisy and requests a short delay, suggesting approximately one second. The finished behavior should let users navigate without rendering each transient line's annotation, then show blame for the settled selection after the agreed interval. Acceptance should cover rapid navigation, editor switching, disabling inline blame while an update is pending, and preservation of status-bar blame behavior.
- **Trace:**

  > In extensions/git/src/blame.ts, GitBlameController responds to editor selection changes through _updateTextEditorBlameInformation and publishes information consumed independently by GitBlameEditorDecoration and GitBlameStatusBarItem. GitBlameEditorDecoration._onDidChangeBlameInformation renders through setDecorations without a timer. The @throttle helper in extensions/git/src/decorators.ts controls concurrent asynchronous updates, not elapsed display time. Configuration in extensions/git/package.json offers visibility, templates, and hover controls but no display-delay option. Keep the scope on inline presentation rather than changing blame computation, line mapping, or status-bar timing. https://github.com/microsoft/vscode/issues/235173 concerns the distinct selection-dragging interaction and is related, not a duplicate canonical. The uncertainty starts at the user-visible timing contract and whether existing users receive a changed default.
- **Open decisions:**
  - Should the delay apply by default when inline blame is enabled, or be an opt-in configurable interval that preserves immediate rendering by default?
  - Should every selection change restart the quiet period and immediately hide the previous annotation until the new selection settles?

## Evidence

- **Current rendering path:** In extensions/git/src/blame.ts, GitBlameController registers selection changes directly with _updateTextEditorBlameInformation, and GitBlameEditorDecoration._onDidChangeBlameInformation calls textEditor.setDecorations without a timed delay. The @throttle implementation in extensions/git/src/decorators.ts serializes concurrent work; it does not wait for a quiet period.
- **Existing capabilities do not cover the ask:** extensions/git/package.json registers git.blame.editorDecoration.enabled, template, and disableHover, plus git.blame.toggleEditorDecoration. extensions/git/package.nls.json documents visibility, formatting, and hover controls, but none provides delayed decoration rendering. Disabling inline blame or using git.blame.statusBarItem.enabled is an alternative presentation, not the requested delay.

It does not own the broader request for a short delay before rendering during ordinary navigation; the re-reviewed-item same-symptom and scope requirements are not met.
