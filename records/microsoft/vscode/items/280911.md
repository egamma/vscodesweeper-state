# Issue #280911 — Command Palette closes unexpectedly with VoiceOver enabled on VS Code Web

[https://github.com/microsoft/vscode/issues/280911](https://github.com/microsoft/vscode/issues/280911)

## Summary

Keep open: a maintainer confirmed the web picker losing focus while typing, and the report was reopened after additional Windows evidence. Quick Input ARIA behavior has since changed, but neither a verified fix nor an older canonical covering the same symptom was established; the supplied steps suffice for retesting.

## Change summary

Typing into VS Code Web Quick Open with VoiceOver closes the picker, while Narrator reportedly prevents text entry.

## Best solution

Ensure typing and filtering remain usable with VoiceOver and Narrator in the web Quick Input widget, while preserving intentional dismissal when focus genuinely moves elsewhere. Retest the reported scenarios against current ARIA behavior and identify the focus-transfer trigger before selecting a fix.

## Plan brief

- **Likely files:** `src/vs/platform/quickinput/browser/quickInputController.ts`, `src/vs/platform/quickinput/browser/quickInputBox.ts`, `src/vs/workbench/services/quickinput/browser/quickInputService.ts`, `src/vs/base/browser/dom.ts`, `src/vs/platform/quickinput/test/browser/quickinput.test.ts`
- **Validation:** On current VS Code Web, enable macOS VoiceOver, open Quick Open with Cmd+P, and type a filename; repeat with Windows Narrator and Ctrl+P. Verify characters appear, filtering works, the picker stays open, and keyboard navigation and Escape remain usable. Record browser versions and activeElement transitions; also check genuine external focus changes still obey workbench.quickOpen.closeOnFocusLost.
- **Behavior:**

  > With a screen reader enabled, typing into VS Code Web Quick Open must enter text and filter results without unexpectedly dismissing the picker. The confirmed macOS failure moves document focus to body and closes the widget; the Windows report leaves it open but prevents typing. Acceptance includes usable result navigation and normal Escape dismissal on both platforms. Genuine focus changes outside the picker must continue to respect the existing focus-loss setting.
- **Trace:**

  > The maintainer confirmed the web failure and body becoming document.activeElement in https://github.com/microsoft/vscode/issues/280911#issuecomment-3607842028 and https://github.com/microsoft/vscode/issues/280911#issuecomment-3607848356. QuickInputController in src/vs/platform/quickinput/browser/quickInputController.ts subscribes to dom.trackFocus(container) and hides on blur; FocusTracker in src/vs/base/browser/dom.ts defers blur emission. The workbench QuickInputService supplies the workbench.quickOpen.closeOnFocusLost policy. QuickInputBox.setListFocusMode and the controller's keydown and list-focus handlers now dynamically change ARIA popup attributes following https://github.com/microsoft/vscode/commit/424ef28d9b759ea0f8485cc7e84a81f8b77f8dcc, so current browser and screen-reader behavior needs retesting. The investigation has not established which event or attribute change initiates focus loss, nor whether the Windows symptom shares that cause. Preserve intentional blur dismissal and other Quick Input consumers; the existing QuickInput test setup uses ignoreFocusOut returning true and therefore does not exercise default blur dismissal.
