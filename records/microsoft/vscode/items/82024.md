# Issue #82024 — Implement token-based language service

[https://github.com/microsoft/vscode/issues/82024](https://github.com/microsoft/vscode/issues/82024)

## Summary

Keep open: current navigation still depends on language providers, and existing text search and Anycode do not establish coverage of the requested general-purpose fallback. Maintainers have retained this as the canonical request; a planning session should settle how approximate results coexist with semantic navigation.

## Change summary

Provide optional text- or token-based definition and reference navigation when semantic language services cannot supply complete results.

## Best solution

Provide an explicitly approximate, opt-in navigation experience that complements semantic providers without presenting textual matches as authoritative definitions or references. Decide whether this belongs in a generic extension or built-in fallback, taking the Anycode exploration and unsupported-language coverage into account.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/gotoSymbol/browser/goToSymbol.ts`, `src/vs/editor/contrib/gotoSymbol/browser/goToCommands.ts`, `src/vs/editor/common/config/editorConfigurationSchema.ts`, `src/vs/workbench/contrib/search/browser/searchActionsFind.ts`
- **Validation:** The plan should define a runnable navigation check using a workspace with repeated identifiers and missing semantic results: verify the chosen approximate mode returns eligible matches, communicates uncertainty, honors its language/file scope, and leaves existing semantic navigation unchanged when disabled.
- **Behavior:**

  > Users should be able to navigate to potential definitions and references when semantic language services return no result or miss occurrences. The reporter asks for an optional approximate mode, not a guarantee that textual matches are semantically correct. Acceptance should cover unsupported languages, incomplete semantic results, clear indication of uncertainty, and unchanged existing navigation when the mode is disabled.
- **Trace:**

  > In src/vs/editor/contrib/gotoSymbol/browser/goToSymbol.ts, getLocationLinks aggregates registered language-provider results; getDefinitionsAtPosition and getReferencesAtPosition do not perform generic workspace search. src/vs/editor/contrib/gotoSymbol/browser/goToCommands.ts builds navigation models from these results, while Find in Files remains a separate operation in src/vs/workbench/contrib/search/browser/searchActionsFind.ts. editor.wordBasedSuggestions in src/vs/editor/common/config/editorConfigurationSchema.ts supplies lexical completions only. Maintainer exploration points to https://github.com/microsoft/vscode-anycode, but the discussion at https://github.com/microsoft/vscode/issues/82024#issuecomment-1287893097 leaves generic coverage and coexistence unresolved. Preserve semantic-provider accuracy and existing default behavior; do not treat the original Intelephense example as a diagnosed VS Code defect. The uncertainty begins at the product contract for approximate results and who owns their implementation.
- **Open decisions:**
  - Should approximate navigation be a built-in opt-in capability or a generic extension using the existing provider APIs?
  - Should approximate matches supplement nonempty semantic results, appear only when providers return nothing, or be available through a separate explicit action?
  - How should approximate matches be distinguished from authoritative definitions and references, and should their scope default to the same language or the whole workspace?

## Evidence

- **Current navigation boundary:** src/vs/editor/contrib/gotoSymbol/browser/goToSymbol.ts:getLocationLinks collects results exclusively from registry.ordered(model, recursive). getDefinitionsAtPosition and getReferencesAtPosition invoke registered providers; this path contains no generic workspace text/token fallback. goToCommands.ts consumes those results and defines the empty-result messages.
- **Existing capabilities are partial:** src/vs/editor/common/config/editorConfigurationSchema.ts:66–76 registers editor.wordBasedSuggestions for completions, including words from other open documents, not definition/reference navigation. src/vs/workbench/contrib/search/browser/searchActionsFind.ts provides Find in Files as a separate workspace-search operation, rather than an integrated approximate navigation provider.
