# Issue #327021 — Copilot Chat re-walks the entire CLI session store on every refresh — extension host stalls for minutes with a large store

[https://github.com/microsoft/vscode/issues/327021](https://github.com/microsoft/vscode/issues/327021)

## Summary

Confirmed on main: `CopilotCLISessionService._getAllSessions()` (extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotcliSessionService.ts) unconditionally lists and maps every on-disk session via `sessionManager.listSessions()` with no cache/pagination, so a full `refreshSessions()` in copilotCLIChatSessions.ts is O(N) against the whole store — real for very large stores. However, the reporter's specific '5s poll while active' trigger doesn't match this code path: that `setInterval`/`updateActiveSessionsOnly` (5s) belongs to the unrelated `CopilotCloudSessionsProvider` (cloud/PR-backed sessions), and CLI per-session change events (`onDidChangeSession`/`onDidCreateSession`) already call the targeted `refreshSession({sessionId})`, not a full re-walk. Already correctly labeled bug/agents-window, so this stays open for the owning team to decide on caching/pagination/retention.

## Change summary

With a very large Copilot CLI session store (thousands of sessions, GBs of data), listing sessions for the Agent Sessions view does an unconditional full-store enumeration that can take seconds to minutes and stall the extension host.

## Best solution

In `copilotcliSessionService.ts`'s `_getAllSessions()`, add either an incremental/cached listing (reuse `_cachedSessionItems` and only diff changed sessions) or a cap/pagination on `sessionManager.listSessions()` results, plus consider a session-store retention/prune command; also correct the root-cause framing since the described 5s poll is actually in the separate cloud-sessions provider, not the CLI path.
