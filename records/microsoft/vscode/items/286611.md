# Issue #286611 — Slow chat switching- keep ChatModel in memory for a bit

[https://github.com/microsoft/vscode/issues/286611](https://github.com/microsoft/vscode/issues/286611)

## Summary

The repeated-load path remains on current main: switching sessions releases the old model, and an idle model without pending edits is disposed rather than retained for quick reopening. This team-authored Backlog performance issue still represents unfinished work and should remain open.

## Change summary

Retain recently closed chat models briefly so switching back to a large session does not immediately deserialize and reconstruct it again.

## Best solution

Introduce a bounded retention policy for recently inactive chat models, reusing the live model when reopened and evicting it after a maintainer-selected timeout or cache limit so the speedup does not create unbounded memory growth.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/model/chatModelStore.ts`, `src/vs/workbench/contrib/chat/common/model/chatModel.ts`, `src/vs/workbench/contrib/chat/test/common/model/chatModelStore.test.ts`
- **Validation:** Extend the ChatModelStore unit suite to release the last reference, reacquire the same session within the chosen retention window, and assert that the original model is reused; then advance beyond the window and assert that the model is persisted, disposed, and recreated on the next acquisition.
- **Behavior:**

  > When a user switches away from an idle chat and returns within the retention window, VS Code reuses the existing ChatModel instead of reading and reconstructing the session. Once the retention window expires, the model is disposed and normal persisted-session restoration still works. Active requests, sessions awaiting input, and sessions with pending edits retain their existing keep-alive behavior. Retention must be bounded so cycling through many chats cannot keep every model alive indefinitely.
- **Trace:**

  > ChatViewPane.showModel in src/vs/workbench/contrib/chat/browser/widgetHosts/viewPane/chatViewPane.ts releases the previous IChatModelReference before binding another session. ChatModelStore.destroyReferencedObject in src/vs/workbench/contrib/chat/common/model/chatModelStore.ts immediately begins disposal when the reference count reaches zero; ChatService.acquireOrRestoreLocalSession in src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts must consequently read persisted data and create a new model on return. ChatModel in src/vs/workbench/contrib/chat/common/model/chatModel.ts already self-retains while a request is running or needs input and contains a TODO describing a roughly five-minute post-use keep-alive. Preserve those active-work and pending-edit semantics, persistence correctness, explicit deletion, and disableBackgroundKeepAlive behavior; the uncertainty starts at the bounded idle-retention policy.
- **Open decisions:**
  - How long should an otherwise idle ChatModel remain reusable after its last external reference is released?
  - Should retention be bounded only by time, or also by a maximum count or memory-oriented eviction policy when many sessions are opened?
