# Issue #338948 — Modern UI - Connected Tabs hover background alignment discrepancy

[https://github.com/microsoft/vscode/issues/338948](https://github.com/microsoft/vscode/issues/338948)

## Summary

Freshly filed, detailed visual bug in the new Modern UI 'Connected' tab style; the likely cause traces to a pre-flattened (opaque) close-button background color that doesn't match the live semi-transparent tab hover paint in connected mode, but I couldn't render the UI to confirm visually.

## Change summary

With a semi-transparent modernTab.hoverBackground color and 'Connected' editor tab style, hovering an inactive tab shows a visibly misaligned background rectangle around the close button.

## Best solution

Reconcile the pre-flattened modernEditorTab.hoverActionBackground (opaque(MODERN_EDITOR_TAB_HOVER_BACKGROUND, editorBackground) in theme.ts) with whatever backdrop actually sits behind the tab-actions area in Connected tab style, so a semi-transparent hover color composites identically across the whole tab including the close button.

## Plan brief

- **Likely files:** `src/vs/workbench/common/theme.ts`, `src/vs/workbench/contrib/modernUI/browser/media/tabs.css`
- **Validation:** Manually verify the reporter's repro steps (workbench.colorCustomizations modernTab.hoverBackground: #0002, Light 2026 theme, Connected tab style, two tabs, hover the inactive tab) and confirm the close-button area blends seamlessly with the rest of the hovered tab with no visible rectangle.
- **Behavior:**

  > With a semi-transparent modern tab hover background configured, hovering an inactive tab in 'Connected' editor tab style should show one uniform semi-transparent overlay across the entire tab, including the close-button area — no visible rectangle or color seam around the close button. Acceptance: following the reporter's exact repro steps, the tab-actions region is visually indistinguishable in tone from the rest of the hovered tab.
- **Trace:**

  > The live tab background uses --modern-ui-editor-tab-hover-background (semi-transparent, painted at render time) directly in tabs.css's `.tab:hover` rule. The close-button container (`.tab-actions`) instead uses --modern-ui-editor-tab-action-hover-background, which resolves to MODERN_EDITOR_TAB_HOVER_ACTION_BACKGROUND = opaque(MODERN_EDITOR_TAB_HOVER_BACKGROUND, editorBackground) (src/vs/workbench/common/theme.ts:729) — an opaque color pre-computed by compositing the semi-transparent hover color against editorBackground at color-registration time, not against whatever is actually behind the tab on screen. A gradient `::before` blend (tabs.css:404-437) smooths one edge of this boundary but doesn't change the flattened interior. If the real backdrop behind tabs in 'Connected' style (e.g. the editor-group title/tabs-and-actions-container, especially over empty tab-bar space) differs from plain editorBackground, the pre-flattened action color won't match the live-painted tab color, producing the reported seam. No connected-mode-specific override for this action background was found outside the hc-black/hc-light block. Boundary: avoid changing the separate (non-connected) tab style's behavior or the gradient blend mechanism itself unless the chosen fix requires it; the open question is which base color the opaque() flattening should target in connected mode.
- **Open decisions:**
  - What backdrop base color should modernEditorTab.hoverActionBackground (and its active/unfocused variants) be flattened against in 'Connected' tab style so the opaque, pre-composited close-button background matches the live semi-transparent tab hover paint exactly — editorBackground, the editor-group title background, or a new connected-mode-specific token?

## Evidence

- **live vs. pre-flattened color:** tabs.css applies --modern-ui-editor-tab-hover-background directly as a live (semi-transparent) background-color on .tab:hover, but .tab-actions instead uses --modern-ui-editor-tab-action-hover-background, which maps to MODERN_EDITOR_TAB_HOVER_ACTION_BACKGROUND = opaque(MODERN_EDITOR_TAB_HOVER_BACKGROUND, editorBackground) in src/vs/workbench/common/theme.ts:729 — a pre-composited opaque color computed against editorBackground, not the real on-screen backdrop.
- **edge blend exists but may not cover full action area:** tabs.css:404-437 adds a gradient ::before pseudo-element blending the two backgrounds at the boundary, which smooths one edge but does not change the flattened interior of .tab-actions, consistent with a 'misaligned background' seam rather than a hard color-stop.
- **no connected-mode override found:** grep for `.modern-ui-connected-editor-tabs` combined with `.tab-actions` in tabs.css shows no connected-specific override for the action background outside the hc-black/hc-light block, so the same flattened color is used in both separate and connected styles even though the real backdrop likely differs between them.
