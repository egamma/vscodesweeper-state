# Issue #75726 — [folding] folding indicators missing for folded code

[https://github.com/microsoft/vscode/issues/75726](https://github.com/microsoft/vscode/issues/75726)

## Summary

The core failure mode remains possible on current main: one folding range provider that never settles leaves the editor's folding-model promise pending, which also blocks every fold/unfold command. Multiple reports tying recovery to disabling Go or Jupyter extensions support this provider-related path, but the resilience behavior needs a maintainer decision.

## Change summary

Folding indicators and commands can stop working until the window is restarted, leaving collapsed code inaccessible.

## Best solution

Make editor folding resilient to a nonresponsive folding range provider so existing or fallback ranges remain usable and fold/unfold commands cannot remain pending indefinitely.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/folding/browser/syntaxRangeProvider.ts`, `src/vs/editor/contrib/folding/browser/folding.ts`, `src/vs/editor/contrib/folding/test/browser/syntaxFold.test.ts`
- **Validation:** Add a targeted folding test with one provider that never settles and verify that folding computation and fold/unfold operations still become usable without reloading the editor.
- **Behavior:**

  > A delayed or nonresponsive language folding provider must not leave folding indicators and commands unusable indefinitely. Users must remain able to unfold already-collapsed regions without restarting the window. Responsive providers should continue contributing syntax ranges normally, and provider cancellation must remain supported.
- **Trace:**

  > SyntaxRangeProvider.collectSyntaxRanges in src/vs/editor/contrib/folding/browser/syntaxRangeProvider.ts waits on Promise.all for every registered FoldingRangeProvider. FoldingController.triggerFoldingModelChanged stores that computation as foldingModelPromise, while FoldingAction.runEditorCommand in src/vs/editor/contrib/folding/browser/folding.ts waits for the same promise before invoking any folding operation. A provider that never resolves therefore blocks the shared command path indefinitely; the current syntax-folding tests do not exercise this case. Reports that disabling Go or Jupyter restores folding corroborate this path, while https://github.com/microsoft/vscode/issues/75632, https://github.com/microsoft/vscode/issues/85739, https://github.com/microsoft/vscode/issues/93033, and https://github.com/microsoft/vscode/issues/154295 establish this issue as the canonical report. Preserve normal syntax-provider precedence and do not change folding persistence or unrelated decoration behavior.
- **Open decisions:**
  - When one of several folding providers fails to settle, should VS Code retain the last-known ranges, use results from providers that completed, or switch to indentation-based ranges?
  - What user-visible delay should be allowed before the editor stops waiting for a folding provider?

## Evidence

- **current source path:** src/vs/editor/contrib/folding/browser/syntaxRangeProvider.ts collects all provider results with Promise.all; a provider whose provideFoldingRanges promise never settles prevents compute from completing, with no timeout or partial-result path.
- **commands blocked:** FoldingController.triggerFoldingModelChanged in src/vs/editor/contrib/folding/browser/folding.ts assigns that computation to foldingModelPromise, and FoldingAction.runEditorCommand awaits getFoldingModel before invoking fold or unfold. A pending provider therefore reproduces the reported combination of unavailable indicators and nonworking commands.
- **extension correlation:** Comments report that disabling vscode-go or Jupyter restores folding, while other confirmations involve Python, JavaScript, Vue, and remote sessions. This is consistent with the shared core controller being held by a language folding provider rather than one language's indentation rules.
- **canonical status:** https://github.com/microsoft/vscode/issues/75632, https://github.com/microsoft/vscode/issues/85739, https://github.com/microsoft/vscode/issues/93033, and https://github.com/microsoft/vscode/issues/154295 were closed by maintainers as duplicates of this still-open issue, making this the established canonical report.
- **test gap:** src/vs/editor/contrib/folding/test/browser/syntaxFold.test.ts covers successful synchronous folding providers and range limits, but not a provider that never resolves.
