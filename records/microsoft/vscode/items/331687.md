# Issue #331687 — revealFileInOS may ignore the passed URI or pick additional URIs from Explorer selection depending on UI state

[https://github.com/microsoft/vscode/issues/331687](https://github.com/microsoft/vscode/issues/331687)

## Summary

Traced and confirmed in source: getMultiSelectedResources in files.ts returns the Explorer selection unconditionally (ignoring the passed URI) whenever the Explorer tree is the last-focused, active list — unlike the adjacent 'open editors' branch, which does check the passed URI against the selection first. An open PR (#331755) already proposes a dedicated revealUriInOS command to fix this, so per policy the issue stays open pending that PR landing rather than being closed or auto-fixed.

## Change summary

revealFileInOS (and several extension/core consumers relying on it with an explicit URI) can silently reveal an unrelated Explorer-selected resource instead of the URI actually passed in.

## Best solution

Land (or iterate on) the open PR https://github.com/microsoft/vscode/pull/331755, which adds a revealUriInOS command that operates strictly on the passed URI and migrates the listed core/extension consumers off the selection-aware revealFileInOS.

## Evidence

- **contrast with editors branch:** The very next branch (open editors, files.ts:131-151) does check `mainUriStr` against `commandArg` before trusting the selection — the Explorer branch above it lacks that same guard, which is exactly the asymmetry the reporter describes.
