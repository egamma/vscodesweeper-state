# Issue #266105 — MCP server configurations should be an options map

[https://github.com/microsoft/vscode/issues/266105](https://github.com/microsoft/vscode/issues/266105)

## Summary

This accepted, team-authored On Deck request remains unimplemented: current main still expands registry parameters into command-line arguments and generated inputs rather than persisting a named options map. It should stay open for design and implementation.

## Change summary

Persist MCP gallery configuration as named user options so server command-line changes can be applied safely across version updates.

## Best solution

Define a stable named-options contract between gallery manifests and installed MCP configurations, retaining user-selected values while regenerating runtime command arguments from the current manifest. Secret parameters should continue using password inputs, with explicit migration and update semantics for existing installations.

## Plan brief

- **Likely files:** `src/vs/platform/mcp/common/mcpManagement.ts`, `src/vs/platform/mcp/common/mcpManagementService.ts`, `src/vs/platform/mcp/common/mcpPlatformTypes.ts`, `src/vs/platform/mcp/node/mcpManagementService.ts`, `src/vs/platform/mcp/test/common/mcpManagementService.test.ts`
- **Validation:** Add MCP management tests that install a manifest with named non-secret and secret parameters, retain a changed non-secret value across a manifest version whose command syntax differs, regenerate the new runtime arguments, and keep the secret represented as a password input.
- **Behavior:**

  > An MCP server installed from the gallery stores user-provided non-secret settings by stable parameter name rather than embedding them irreversibly into command arguments. Updating the server can regenerate its command from the new manifest while retaining compatible user values. Secret parameters remain password inputs, and ordinary VS Code ${...} substitutions remain usable in shared configuration. Acceptance should cover installation, a manifest update that changes argument syntax, retained values, and secret handling.
- **Trace:**

  > The registry model in src/vs/platform/mcp/common/mcpManagement.ts already gives package arguments structured names, defaults, descriptions, and secret metadata. AbstractCommonMcpManagementService.getMcpServerConfigurationFromManifest in src/vs/platform/mcp/common/mcpManagementService.ts currently flattens those structures through processArguments into config.args and generated inputs. IMcpServerConfiguration in src/vs/platform/mcp/common/mcpPlatformTypes.ts has no persisted named-options field, and src/vs/platform/mcp/node/mcpManagementService.ts installs the flattened result with gallery/version metadata. Existing direct command/args configurations must continue to launch unchanged; the scope is gallery-backed configuration and its update path, not arbitrary local MCP definitions.
- **Open decisions:**
  - Should existing gallery-backed command/args installations migrate automatically to named options, or should the new persisted contract apply only to fresh installations?
  - When a newer manifest removes or renames a parameter, should its stored user value be retained as an unknown option, removed, or surfaced for explicit user resolution?

## Evidence
