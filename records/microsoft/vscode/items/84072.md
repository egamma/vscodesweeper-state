# Issue #84072 — Allow viewing and editing commands with 'args' in the keybindings editor

[https://github.com/microsoft/vscode/issues/84072](https://github.com/microsoft/vscode/issues/84072)

## Summary

Keep open: the Keyboard Shortcuts editor still lacks argument display and editing, and JSON editing does not cover the requested discoverability. Maintainers have explicitly consolidated related reports here; no verified older canonical supersedes it.

## Change summary

Allow users to view, create, and edit command arguments in the graphical Keyboard Shortcuts editor.

## Best solution

Provide an accessible argument-aware workflow in the Keyboard Shortcuts editor that distinguishes bindings for the same command and round-trips their arguments correctly. Agree on the argument-editing UX before implementation, retaining JSON editing for advanced use.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/preferences/browser/keybindingsEditor.ts`, `src/vs/workbench/services/preferences/browser/keybindingsEditorModel.ts`, `src/vs/workbench/services/keybinding/common/keybindingEditing.ts`, `src/vs/workbench/services/keybinding/test/browser/keybindingEditing.test.ts`, `src/vs/workbench/services/preferences/test/browser/keybindingsEditorModel.test.ts`
- **Validation:** After the UX decision, manually create, inspect, edit, reload, and invoke a graphical-editor binding for editor.action.codeAction with {"kind":"refactor.extract","preferred":true}; verify distinct arguments for the same command remain distinguishable and independently editable. Add targeted model/editing tests for argument round-tripping and selection of the intended binding, retaining existing key/when editing behavior.
- **Behavior:**

  > Users cannot currently inspect or author command arguments in the graphical Keyboard Shortcuts editor, making parameterized shortcuts and code actions difficult to discover and configure. The completed experience should expose argument values and allow creating and editing bindings with arguments without requiring manual navigation through keybindings.json. Bindings sharing a command but carrying different arguments must remain distinguishable and independently editable. Acceptance includes persistence across reload, correct command invocation, keyboard and screen-reader access, and unchanged behavior for bindings without arguments.
- **Trace:**

  > KeybindingsEditor.createTable in src/vs/workbench/contrib/preferences/browser/keybindingsEditor.ts has no argument surface, and CommandColumnRenderer renders only command labels and IDs. defineKeybinding/updateKeybinding accept key and when changes but no argument input. KeybindingsEditorModel in src/vs/workbench/services/preferences/browser/keybindingsEditorModel.ts retains the underlying ResolvedKeybindingItem, but its text filtering has no argument matching branch. In src/vs/workbench/services/keybinding/common/keybindingEditing.ts, existing-entry edits preserve other JSON fields, while asObject omits arguments for newly constructed entries and findUserKeybindingEntryIndex matches command and when rather than arguments. JSON authoring and command-schema support already exist and must remain compatible. Maintainers consolidated related reports here through https://github.com/microsoft/vscode/issues/114935#issuecomment-768365065 and https://github.com/microsoft/vscode/issues/174125#issuecomment-1440398273. The unresolved boundary is the graphical argument-authoring experience; the Java action-identity question in https://github.com/microsoft/vscode/issues/84072#issuecomment-1313276270 should not silently expand this into a new code-action API.
- **Open decisions:**
  - Should the graphical editor expose arguments as editable JSON, schema-driven fields, or a combination, including when a command provides no argument schema?
  - Should this iteration expose arguments only for existing command entries, or also discover and present named code-action variants before any binding exists?
