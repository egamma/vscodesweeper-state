# Issue #301143 — Title: onDidRequestToolApproval event for Chat/Language Model extensions

[https://github.com/microsoft/vscode/issues/301143](https://github.com/microsoft/vscode/issues/301143)

## Summary

A real extension-API gap remains: extensions can implement tools but cannot observe when the chat UI is waiting for tool approval. The request is concrete and aligned with accessibility and extension-ecosystem goals, but the public event's privacy, scope, and lifecycle semantics need API-owner design.

## Change summary

Expose a read-only Chat/Language Model API signal when a tool invocation is awaiting user approval.

## Best solution

Design a minimal proposed Chat API that lets extensions detect an actionable approval state without exposing prompt contents or granting control over the approval decision, with semantics covering concurrent sessions, cancellation, and prompt dismissal.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.chatParticipantPrivate.d.ts`, `src/vs/workbench/api/common/extHostChatAgents2.ts`, `src/vs/workbench/api/browser/mainThreadChatAgents2.ts`, `src/vs/workbench/contrib/chat/common/chatService.ts`
- **Validation:** Add API tests proving that an extension receives one notification when an approval prompt becomes actionable, receives the corresponding resolved/cancelled transition, and cannot observe approval details outside the selected visibility boundary.
- **Behavior:**

  > Extensions need a supported read-only signal when a chat tool invocation is waiting for user approval so accessibility or notification extensions can alert the user. The contract must identify enough context to correlate the waiting state without exposing chat or argument content unnecessarily. Acceptance should cover prompt presentation, approval, denial, dismissal or cancellation, and overlapping chat sessions.
- **Trace:**

  > The public Language Model API lets extensions register and invoke tools, but the issue identifies no observer surface for the workbench-owned approval UI. The likely path crosses the chat tool-approval state in src/vs/workbench/contrib/chat/common/chatService.ts and the extension-host bridge in src/vs/workbench/api/browser/mainThreadChatAgents2.ts and src/vs/workbench/api/common/extHostChatAgents2.ts, with a proposed declaration under src/vscode-dts. Keep the boundary read-only: extensions must not approve, deny, inspect tool arguments, or alter trust decisions. The uncertainty starts at the public contract—whether extensions observe all approval prompts or only prompts connected to their own participant or tools, and whether the API emits transitions or exposes current state.
- **Open decisions:**
  - May an extension observe every chat approval prompt, or only approvals associated with its own participant or registered tools?
  - Should the public contract be a request-only event or a state lifecycle that also reports approval, denial, dismissal, and cancellation?
  - Which tool and participant identifiers may be exposed without leaking private extension or chat context?

## Evidence

- **specific API gap:** The report identifies a concrete observer gap: vscode.lm.registerTool lets extensions provide tools, while no public Chat/Language Model event reports that the UI is awaiting tool approval.
- **bounded user need:** The requested signal supports notification and accessibility extensions when agent execution is blocked for user action; terminal execution events cover only terminal-backed activity and do not cover arbitrary tool approvals.
- **no existing owner:** The issue has no comments, labels, linked canonical issue, fixing PR, or related timeline item establishing that the request is already implemented, duplicated, or declined.
- **design-sensitive contract:** The proposed event exposes tool identity and participant information globally; API owners need to decide visibility boundaries, concurrent-session behavior, and whether the contract represents a request event or a durable waiting state.
