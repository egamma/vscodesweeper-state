# Issue #344328 — Agents window: dev container agent host doesn't receive the GitHub Enterprise endpoint (asks for api.github.com, 'Authentication is required to start a session')

[https://github.com/microsoft/vscode/issues/344328](https://github.com/microsoft/vscode/issues/344328)

## Summary

Keep open: current source forwards the enterprise endpoint only to the local agent host, leaving a freshly created container host advertising github.com resources. The report identifies a concrete configuration-propagation gap, distinct from the related authentication and settings-editor reports.

## Change summary

Ensure a freshly created dev-container agent host receives the selected GitHub Enterprise endpoint before resolving authentication.

## Best solution

Make enterprise authentication work on first connection and after container rebuilds without requiring manual host configuration. Preserve explicitly configured remote endpoints and third-party host interoperability; establish the endpoint-inheritance boundary before extending remote initialization.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostTerminalContribution.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostRootConfigForwarder.ts`, `src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostAuthenticationResolver.ts`, `src/vs/platform/agentHost/browser/remoteAgentHostServiceImpl.ts`
- **Validation:** Add remote-connection boundary coverage for a fresh host with no enterprise configuration: a selected enterprise account must result in enterprise protected resources before credential resolution. Cover reconnect/container rebuild, an explicitly configured remote endpoint, and a conforming host without the optional configuration capability. Manually repeat the supplied fresh-container steps and confirm chat starts without github.com sign-in.
- **Behavior:**

  > A user signed in to GitHub Enterprise can start an Agents-window chat on a freshly rebuilt dev container without manually editing agent-host-config.json. Authentication targets the enterprise instance rather than api.github.com. Reconnection and subsequent rebuilds retain this behavior. Explicit remote endpoint settings and independently administered hosts must follow an agreed precedence contract.
- **Trace:**

  > AgentHostTerminalContribution computes GithubEnterpriseUri from the initialized default account, but AgentHostRootConfigForwarder dispatches only through IAgentHostService and explicitly excludes remote connections. AgentHostGitHubEndpointService reads only host root configuration, so a fresh container without this value advertises github.com resources. RemoteAgentHostAuthenticationResolver._resolve then resolves the advertised resources without first supplying enterprise configuration. This source path accounts for the missing configuration and wrong-resource authentication in https://github.com/microsoft/vscode/issues/344328; the intermittent WSL delay is not independently diagnosed. The uncertainty is the intended inheritance contract for client-managed versus independently administered remote hosts. Do not forward machine-specific settings indiscriminately or reinterpret third-party advertised resources. The malformed settings-editor workaround is separately tracked at https://github.com/microsoft/vscode/issues/344331.
- **Open decisions:**
  - Should client enterprise-endpoint inheritance apply only to client-managed dev-container hosts, or also to other VS Code remote agent hosts?
  - When the client account and an explicitly configured remote enterprise endpoint differ, should the host retain its endpoint and request matching credentials, or follow the connected client's selected account?
