# Issue #247926 — Pass LanguageModelChat to tools

[https://github.com/microsoft/vscode/issues/247926](https://github.com/microsoft/vscode/issues/247926)

## Summary

Keep open: this team-authored Backlog item tracks an unresolved API-finalization decision. The proposed API is available for testing, but the discussion explicitly identifies a required split between invocation options supplied by callers and resolved options received by tools.

## Change summary

Finalize an extension API that passes the active LanguageModelChat to an invoked language-model tool.

## Best solution

Finalize the tool invocation contract with distinct caller-supplied and tool-received option types, exposing the resolved model only to the invoked tool while preserving the existing toolInvocationToken lookup behavior.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.lmTools.ts`, `src/vs/workbench/api/common/extHostLanguageModels.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadLanguageModels.ts`
- **Validation:** Run the targeted extension API tests covering language-model tool invocation and verify that tools receive the selected model for token-associated chat requests while extension callers cannot provide that resolved model field.
- **Behavior:**

  > When a language-model tool is invoked from a chat request through a toolInvocationToken, the tool receives the LanguageModelChat selected for that request. Extension callers cannot spoof or directly supply that resolved model. The finalized API must be usable by published extensions while preserving invocations that have no associated chat model.
- **Trace:**

  > The issue records that the model ID is stored on ChatRequest and resolved for the associated tool invocation. PR https://github.com/microsoft/vscode/pull/244323 introduced the proposed surface, but the API sync discussion identified that the existing LanguageModelToolInvocationOptions combines caller-provided and tool-received data and therefore needs a public-contract split. MCP is explicitly outside this path and must not be folded into the change. The uncertainty starts at the stable names and exact separation of the input and resolved invocation option interfaces.
- **Open decisions:**
  - What stable public names should distinguish options supplied by an extension caller from resolved options delivered to LanguageModelTool.invoke?
  - Should the resolved model remain optional for invocations without a toolInvocationToken or associated chat request, and how should that absence be represented in the stable contract?
