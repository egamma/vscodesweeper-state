# Issue #158603 — Sidebar defaultWidth, View-Specific Sidebar widths, & View-Specific Sidebar defaultWidths

[https://github.com/microsoft/vscode/issues/158603](https://github.com/microsoft/vscode/issues/158603)

## Summary

Keep open: current layout storage preserves a shared sidebar width, but does not deliver configurable defaults and independent widths for each Activity Bar view. The request has substantial community support, and an open fork PR addresses only the universal default-width portion.

## Change summary

Support configurable sidebar default widths and independently remembered or configured widths for built-in and extension-provided view containers.

## Best solution

Provide consistent per-view-container sidebar sizing with defined persistence and default-setting precedence. Review the universal default-width proposal at https://github.com/M-Jeremy/vscode/pull/1 as a partial implementation candidate, while retaining this issue for the per-view behavior.

## Evidence

- **Existing persistence is partial coverage:** src/vs/workbench/browser/layout.ts saves the sidebar grid width on storageService.onWillSaveState into LayoutStateKeys.SIDEBAR_SIZE. That key is a single profile-scoped sideBar.size value, not a width keyed by the active view container. Ordinary saved-width restoration already exists, but does not fulfill independent Explorer, Search, SCM, and extension-view widths.
- **Default-width capability remains missing:** LayoutStateModel in src/vs/workbench/browser/layout.ts assigns SIDEBAR_SIZE.defaultValue using Math.min(300, mainContainerDimension.width / 4). Inspection of src/vs/workbench/browser/workbench.contribution.ts found secondary-sidebar visibility and maximization settings, but no workbench.sideBar.defaultWidth or workbench.secondarySideBar.defaultWidth registration.
- **Workarounds do not satisfy the request:** src/vs/workbench/browser/actions/layoutActions.ts registers workbench.action.increaseViewSize and workbench.action.decreaseViewSize. These are manual resizing commands, as commenters describe, rather than configured or automatically restored per-view widths. SidebarPart.preferredWidth in src/vs/workbench/browser/parts/sidebar/sidebarPart.ts derives an optimal content width, not a user-configured per-view default; moving views to the secondary sidebar likewise does not cover all requested views.
- **Open partial implementation:** https://github.com/M-Jeremy/vscode/pull/1 was verified OPEN. Its body explicitly references this upstream issue and limits its scope to universal primary and secondary sidebar default-width settings, accepting pixels or percentages and preserving previously saved widths. It is a fork PR, not a merged upstream fix, and does not implement per-view widths.
- **Canonical search:** Verified https://github.com/microsoft/vscode/issues/75017 is OPEN and older, but its original observable problem is restoring different widths across workspaces, rather than resizing when switching Activity Bar views. Its later discussion overlaps this request without establishing full-scope canonical ownership. Searches for sidebar width and viewlet width found no verified older canonical satisfying the stronger duplicate bar for this re-reviewed item.
- **Demand and accepted scope:** https://github.com/microsoft/vscode/issues/158603 has 409 community upvotes, carries feature-request and layout, and is assigned to Backlog. The thread repeatedly requests independent widths; secondary-sidebar and keyboard-resizing suggestions are explicitly treated as workarounds, not completion.
