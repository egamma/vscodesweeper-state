# Issue #133229 — Webview editors are not registered editors?

[https://github.com/microsoft/vscode/issues/133229](https://github.com/microsoft/vscode/issues/133229)

## Summary

The underlying registration gap remains on current main: auto-lock configuration still relies on a hard-coded list for webview editors. The accepted Backlog debt should stay open while the webview and editor owners decide the discovery contract.

## Change summary

Provide a lightweight way to discover extension-provided webview editor types and labels without treating resource-less webviews as normal editor-resolver registrations.

## Best solution

Expose webview editor metadata through a lightweight discovery contract so dynamic editor settings can enumerate contributed view types without weakening the resource-based semantics of IEditorResolverService.

- **Fit:** aligned
- **Reason:** Removing hard-coded editor metadata improves settings fidelity and extension integration while preserving the editor resolver's existing architectural boundary.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/editor/editorConfiguration.ts`, `src/vs/workbench/api/browser/mainThreadWebviewPanels.ts`, `src/vs/workbench/contrib/webviewPanel/browser/webviewWorkbenchService.ts`
- **Validation:** Add a targeted test proving that a discovered extension webview type and label appear in the workbench.editor.autoLockGroups configuration schema without a hard-coded AUTO_LOCK_EXTRA_EDITORS entry, then verify opening that editor first in a multi-group window locks the group when enabled.
- **Behavior:**

  > Extension-provided webview editor types that can participate in workbench.editor.autoLockGroups should be discoverable with a stable identifier and human-readable label. The setting schema should offer those editors without requiring a hard-coded core entry, and enabling one should preserve the existing group auto-lock behavior. Resource-backed editor resolution and editor selection behavior must remain unchanged.
- **Trace:**

  > DynamicEditorConfigurations in src/vs/workbench/browser/parts/editor/editorConfiguration.ts builds the auto-lock schema from IEditorResolverService.getEditors() plus AUTO_LOCK_EXTRA_EDITORS; the latter still hard-codes selected webviews. MainThreadWebviewPanels in src/vs/workbench/api/browser/mainThreadWebviewPanels.ts creates runtime IDs by prefixing extension view types, and WebviewInput.editorId returns that view type, so editorGroupView.ts can already apply locking once the user knows the ID. IWebviewWorkbenchService currently manages opening and resolving webviews but exposes no registry of their types and labels. Preserve the editor resolver's resource-based responsibility and do not make webview editors user-selectable file associations. The related extension-API proposal is https://github.com/microsoft/vscode/issues/185674; it is newer and narrower, so it should inform the design rather than absorb this issue.
- **Open decisions:**
  - Must a webview editor type be visible in settings before it has ever been opened, requiring declarative extension metadata, or may discovery occur on first use with persisted metadata?
  - Should extensions explicitly provide the stable display label and any default auto-lock recommendation as a public contribution contract, or should VS Code derive and cache metadata from runtime webview creation?

## Evidence

- **current source:** src/vs/workbench/browser/parts/editor/editorConfiguration.ts still declares AUTO_LOCK_EXTRA_EDITORS with hard-coded entries for mainThreadWebview-markdown.preview, mainThreadWebview-simpleBrowser.view, and mainThreadWebview-browserPreview, explicitly describing them as editor identifiers not registered through the resolver infrastructure.
- **webview identity path:** src/vs/workbench/api/browser/mainThreadWebviewPanels.ts constructs extension webview editor IDs at runtime with WebviewViewTypeTransformer('mainThreadWebview-'), while src/vs/workbench/contrib/webviewPanel/browser/webviewEditorInput.ts exposes the resulting viewType as editorId.
- **consumer behavior:** src/vs/workbench/browser/parts/editor/editorGroupView.ts checks openedEditor.editorId against workbench.editor.autoLockGroups, confirming that runtime webview IDs can participate in locking even though their metadata is absent from the dynamic configuration schema.
- **related issue:** https://github.com/microsoft/vscode/issues/185674 is a newer, still-open request for an extension contribution point for the same auto-lock discovery surface. It is related but cannot be the canonical duplicate for this re-reviewed 2021 architectural debt, and it covers one proposed API design rather than the full registration question.
