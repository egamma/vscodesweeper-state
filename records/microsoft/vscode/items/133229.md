# Issue #133229 — Webview editors are not registered editors?

[https://github.com/microsoft/vscode/issues/133229](https://github.com/microsoft/vscode/issues/133229)

## Summary

The registration gap remains: auto-lock configuration still combines resolver registrations with a hard-coded list of webview editor types. Keep this debt item open; the closely related contribution-point request is newer and cannot replace this re-reviewed report.

## Change summary

Provide discoverable webview editor identities and names for auto-lock configuration without maintaining a hard-coded list or making arbitrary panels selectable as file editors.

## Best solution

Give auto-lock configuration a supported source of webview type metadata while preserving the distinction between panel discovery and resource-based editor resolution. Coordinate its discovery and naming contract with https://github.com/microsoft/vscode/issues/185674.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/editor/editorConfiguration.ts`, `src/vs/workbench/api/browser/mainThreadWebviewPanels.ts`, `src/vs/workbench/contrib/webviewPanel/browser/webviewWorkbenchService.ts`, `src/vs/workbench/contrib/webviewPanel/browser/webviewEditorInput.ts`, `src/vs/workbench/services/editor/common/editorResolverService.ts`
- **Validation:** After choosing the discovery contract, use an extension-created panel with a previously unknown view type and verify that auto-lock settings expose its stable identity and intended display name at the agreed discovery point. With another editor group present, enabling its entry must lock a group when that panel is its first editor. Verify that the panel type does not become an unrelated file-editor choice and that existing built-in auto-lock defaults remain unchanged.
- **Behavior:**

  > Auto-lock settings currently expose selected known webview panel types through a hard-coded list, rather than discovering arbitrary extension-provided panel types. The goal is a supported way to enumerate panel identities and meaningful names for configuration without making those panels ordinary file-editor choices. Acceptance should cover a previously unknown extension panel type, its appearance at the agreed discovery point, and effective auto-locking when enabled. Existing built-in auto-lock defaults must remain unchanged.
- **Trace:**

  > DynamicEditorConfigurations in src/vs/workbench/browser/parts/editor/editorConfiguration.ts builds the auto-lock schema from resolver registrations plus AUTO_LOCK_EXTRA_EDITORS, confirming the original workaround is still present. MainThreadWebviewPanels.$createWebviewPanel() passes a prefixed type to WebviewEditorService.openWebview(), which constructs and opens a typed WebviewInput without registering type metadata for settings discovery. WebviewInput now has a generated webview-panel resource and returns viewType as editorId, so the original no-resource explanation needs updating rather than repeating. The boundary is metadata discovery for locking, not a change to panel restoration, file associations, or editor-picker eligibility. The original discussion considers first-use registration and caching; https://github.com/microsoft/vscode/issues/185674 adds the alternative of declarative extension metadata. The unresolved point is the observable discovery and naming contract, not which helper or class should implement it.
- **Open decisions:**
  - Should panel types appear in auto-lock settings only after first use, or be discoverable before opening through extension-declared metadata?
  - What stable display-name contract should identify a panel type in settings, independently of individual panel titles?
  - If discovery occurs at runtime, should discovered types remain available across window reloads before the extension creates another panel?

## Evidence

- **Current configuration still contains the workaround:** src/vs/workbench/browser/parts/editor/editorConfiguration.ts: DynamicEditorConfigurations.AUTO_LOCK_EXTRA_EDITORS explicitly includes mainThreadWebview-markdown.preview, mainThreadWebview-simpleBrowser.view, and mainThreadWebview-browserPreview. updateDynamicEditorConfigurations() combines this list with IEditorResolverService.getEditors(); the workbench.editor.autoLockGroups schema sets additionalProperties to false. Known panels are covered, but arbitrary extension panel types are not discovered by this path.
- **Panel creation does not supply editor metadata registration:** src/vs/workbench/api/browser/mainThreadWebviewPanels.ts: $createWebviewPanel() passes the prefixed view type to IWebviewWorkbenchService.openWebview(). In src/vs/workbench/contrib/webviewPanel/browser/webviewWorkbenchService.ts, WebviewEditorService.openWebview() creates a WebviewInput and opens it through IEditorService; it does not register the type with the editor resolver.
- **Historical resource limitation has changed, but discovery remains missing:** src/vs/workbench/contrib/webviewPanel/browser/webviewEditorInput.ts: WebviewInput.editorId returns viewType, and resource now returns a generated Schemas.webviewPanel URI. Consequently, the thread's historical statement that panels lack resources is no longer literally true, but a per-instance URI does not provide the missing catalog of panel type identities and display names.
