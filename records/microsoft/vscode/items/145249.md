# Issue #145249 — Feedback should be accountless

[https://github.com/microsoft/vscode/issues/145249](https://github.com/microsoft/vscode/issues/145249)

## Summary

Keep open: the inspected issue reporter still hands submission to an external tracker rather than providing accountless feedback. A maintainer supported exploring email delivery, and explicitly identified this issue as the tracking item; its Backlog placement should not be overridden by a scope decline.

## Change summary

Allow users to submit bugs or feedback without creating a GitHub or Twitter account, potentially using email.

## Best solution

Define an accountless submission path that preserves the team's centralized issue workflow, while distinguishing extension-provided email destinations from VS Code's own intake. Decide whether general positive feedback belongs in that same path before implementing it.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/issue/browser/issueFormService.ts`, `src/vs/workbench/contrib/issue/electron-browser/issueReporterEditorPane.ts`, `src/vs/workbench/contrib/issue/electron-browser/nativeIssueFormService.ts`
- **Validation:** The plan should end with an explicit manual acceptance flow: with no GitHub or Twitter account or active session, compose feedback in VS Code and deliver it through the approved destination, preserving its contents. Existing GitHub issue submission and extension-specific destinations must remain usable.
- **Behavior:**

  > Users without GitHub or Twitter accounts should have a supported way to submit feedback, with email acceptable to the reporter. Current submission opens an external issue tracker rather than completing accountless delivery. Acceptance should demonstrate delivery without those accounts and preservation of the composed report. The discussion also raises positive feedback, whose inclusion needs an explicit scope decision.
- **Trace:**

  > IssueFormService.submitIssue in src/vs/workbench/contrib/issue/browser/issueFormService.ts resolves a destination through getIssueTarget and opens it externally. GitHub targets are normalized to the new-issue form by getIssueUrlWithTitle; anonymous access in searchGitHubIssues is discovery only. Extension-supplied destinations already have a separate path through getExtensionIssueUrl, which must remain functional. The native editor delegates submission to this service. https://github.com/microsoft/vscode/issues/145249#issuecomment-1069861091 distinguishes optional extension email delivery from changing the team's own intake process; the uncertainty starts at that product boundary, not at a diagnosed code defect.
- **Open decisions:**
  - Should accountless submission cover VS Code's own feedback intake, extension destinations that opt in, or both?
  - Should accountless delivery use the user's email client or an intake service that preserves centralized tracking?
  - Should the supported path accept general positive feedback as well as actionable bugs and feature requests?

## Evidence
