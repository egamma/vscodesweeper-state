# Issue #242304 — "Reveal in File Explorer" does not work as intended

[https://github.com/microsoft/vscode/issues/242304](https://github.com/microsoft/vscode/issues/242304)

## Summary

The defect remains on current main: VS Code invokes the single-item OS reveal API once for every selected resource, producing the reported repeated selection and window reopening. Keep it open while a maintainer decides whether to pursue platform-specific multi-selection or use a deterministic single-call fallback.

## Change summary

Revealing multiple Explorer selections repeatedly scrolls and changes the operating-system file manager selection instead of revealing the selection as a group.

## Best solution

Use native multi-item selection where it can be supported reliably; otherwise make one deterministic reveal operation for the shared parent or one selected item, avoiding repeated window activation. The fallback semantics need a maintainer decision because the reporter and later commenter prefer different outcomes.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/electron-browser/fileCommands.ts`, `src/vs/platform/native/common/native.ts`, `src/vs/platform/native/electron-main/nativeHostMainService.ts`
- **Validation:** Add a focused test around `revealResourcesInOS` for multiple same-folder resources, then manually verify on Windows and macOS that one command no longer causes repeated scrolling, selection changes, or reopening; the accepted selection or fallback behavior must match the maintainer's decision.
- **Behavior:**

  > Invoking Reveal in File Explorer/Finder on multiple files must not repeatedly activate, scroll, or reopen the OS file manager. Ideally all selected sibling files are revealed together. If the platform cannot support that, one documented deterministic fallback must occur, while single-file reveal remains unchanged.
- **Trace:**

  > The Explorer command obtains all selected resources in src/vs/workbench/contrib/files/electron-browser/fileActions.contribution.ts and passes them to `revealResourcesInOS`. In src/vs/workbench/contrib/files/electron-browser/fileCommands.ts, that function sequences one `showItemInFolder` call per resource. The native service contract in src/vs/platform/native/common/native.ts accepts one path, and NativeHostMainService forwards it directly to Electron's single-path `shell.showItemInFolder`. This conclusively explains the reported behavior on current main. Historical reports https://github.com/microsoft/vscode/issues/42576 and https://github.com/microsoft/vscode/issues/162486 identify the same Electron limitation but are closed; preserve single-resource behavior and remote-to-local URI handling while investigating the multi-resource path.
- **Open decisions:**
  - Should VS Code add platform-specific multi-item selection where available, even if behavior differs between operating systems, or keep one uniform cross-platform fallback?
  - When native multi-item selection is unavailable, should revealing a same-folder multi-selection open the parent with nothing selected or select one deterministic item?
