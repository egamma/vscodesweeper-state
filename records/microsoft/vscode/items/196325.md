# Issue #196325 — Git - Stage/unstage file, then immediately click it, no diff shown

[https://github.com/microsoft/vscode/issues/196325](https://github.com/microsoft/vscode/issues/196325)

## Summary

The wrong-diff path remains in current source: optimistic staging and unstaging change the resource group but retain the old status used to construct the diff. Keep this accepted, team-authored bug open; the related reports do not provide a canonical duplicate or a verified fix.

## Change summary

Immediately opening a file after staging or unstaging can show an empty diff with the previous group's title and comparison endpoints.

## Best solution

Make diff opening during optimistic Git transitions agree with the destination group's comparison and eventual repository state, without requiring users to close and reopen the editor. Resolve the thread's outstanding immediate-open versus refresh behavior before implementing in the Git extension.

- **Validation:** In a disposable Git repository with git.optimisticUpdate enabled, change a tracked file, stage it and immediately open its Staged Changes row; verify the resulting diff shows HEAD versus index with the Index title. - **Behavior:**

  > Opening a changed file immediately after staging or unstaging currently can show an empty comparison labeled for its previous group. The resulting editor must represent the destination group's changes and reach the correct contents without requiring close-and-reopen. Staged modified files compare HEAD with index; unstaged modified files compare index with the working file. Acceptance must exercise both transitions while the optimistic resource list is visible, as well as ordinary opening with optimistic updates disabled.
- **Trace:**

  > Repository.add and Repository.revert in extensions/git/src/repository.ts move resources between groups through Resource.clone, which preserves the previous Status. ResourceCommandResolver derives ordinary-file comparison URIs and titles from that Status rather than the destination resourceGroupType, conclusively explaining both reported directions. Repository.run currently completes the Git operation before _updateModelState publishes the optimistic groups; the stale cloned resources remain visible while metadata and authoritative status are fetched. Resource.openChange and resolveChangeCommand immediately construct the comparison from that resource. Preserve settled diff semantics and the purpose of optimistic updates; added, deleted, renamed and partially staged resources need their existing semantics retained rather than assuming every transition is a modified-file case. The discussion at https://github.com/microsoft/vscode/issues/196325 leaves uncertainty about whether opening should be immediate with later reconciliation or wait for authoritative state.
- **Open decisions:**
  - During an optimistic staging or unstaging transition, should a requested diff open immediately and reconcile as repository state settles, or wait for authoritative resource state before opening?
