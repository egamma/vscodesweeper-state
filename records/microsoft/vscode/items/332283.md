# Issue #332283 — using different set of memory file connecting via remote ssh

[https://github.com/microsoft/vscode/issues/332283](https://github.com/microsoft/vscode/issues/332283)

## Summary

A real repository-memory continuity gap remains: current source keys `/memories/repo` to extension-host-specific workspace storage, so local and Remote-SSH windows can use separate memories for the same project. This should be routed to the chat tools and remote areas for a persistence-contract decision.

## Change summary

Share repository-scoped Copilot memory for the same project regardless of whether it is opened locally or through Remote-SSH.

## Best solution

Define a stable repository-memory identity and backing store that works across local and Remote-SSH extension hosts while preserving workspace isolation and explicit privacy semantics. The design should also align with the broader cross-device repository-memory request at https://github.com/microsoft/vscode/issues/308964.

- **Likely files:** `extensions/copilot/src/extension/tools/node/memoryTool.tsx`, `extensions/copilot/src/extension/tools/node/resolveMemoryFileUriTool.tsx`, `extensions/copilot/src/extension/tools/node/memoryContextPrompt.tsx`, `extensions/copilot/src/extension/tools/vscode-node/tools.ts`, `extensions/copilot/src/extension/tools/node/test/memoryTool.spec.tsx`
- **Validation:** Add tests modeling local and remote extension contexts for the same canonical workspace: a repository memory created through one context must be visible through the other, while a different workspace remains isolated.
- **Behavior:**

  > Repository-scoped Copilot memory for a project remains available when that same project is opened locally or through Remote-SSH. Memories from unrelated projects remain isolated. The chosen behavior must make persistence, visibility, and reset semantics clear and must not expose repository memories through source control or broader synchronization unless that is an explicit product decision.
- **Trace:**

  > `MemoryTool._resolveUri` in extensions/copilot/src/extension/tools/node/memoryTool.tsx maps repository memory to `extensionContext.storageUri/memory-tool/memories/repo`; local and remote extension hosts therefore use different backing roots. The show-memory command in extensions/copilot/src/extension/tools/vscode-node/tools.ts, URI resolver in extensions/copilot/src/extension/tools/node/resolveMemoryFileUriTool.tsx, and prompt discovery in extensions/copilot/src/extension/tools/node/memoryContextPrompt.tsx follow that same location and must remain consistent. Existing session-memory and user-memory scope semantics are outside this request and must not change. https://github.com/microsoft/vscode/issues/308964 is related broader work, but this issue specifically establishes the local-versus-Remote-SSH continuity requirement.
- **Open decisions:**
  - Should repository memory be workspace-visible project data, account-synchronized data, or private editor data addressed by a stable repository identity across extension hosts?
  - When the same checkout has existing but divergent local and Remote-SSH memories, should they be merged, migrated from one source, or kept separate until the user chooses?
  - Should sharing apply only to the same physical checkout or to any checkout recognized as the same repository?
