# Issue #339865 — Moving chat in the grid behavior is inconsistent

[https://github.com/microsoft/vscode/issues/339865](https://github.com/microsoft/vscode/issues/339865)

## Summary

Freshly filed (same-day) report testing a WIP feature; the grid's move-in-direction logic genuinely produces inconsistent placement, confirmed by tracing the code, so this stays open as a real bug in the agents-window area.

## Change summary

"Move Session Above/Below" sometimes lands the session in the row above as a new column, and sometimes creates a brand-new split row, with no consistent rule.

## Best solution

Change the move-in-direction placement logic (sessionsService.moveSessionInDirection / SessionGridLayout) to explicitly check whether a row already exists in the requested direction and, if so, insert into that row as a new column instead of relying on the nearest geometric neighbor to decide the split.

## Plan brief

- **Likely files:** `src/vs/sessions/services/sessions/browser/sessionsService.ts`, `src/vs/sessions/browser/parts/sessionGridLayout.ts`, `src/vs/sessions/services/sessions/browser/visibleSessions.ts`
- **Validation:** A test exercising moveSessionInDirection/insertAt where a 2-column row exists above the focused session's row, asserting the moved session ends up in that row as a new column rather than in a newly created split row; and the inverse case (no row above) asserting a new row is created.
- **Behavior:**

  > Invoking 'Move Session Above' (or 'Move Session Below') should consistently place the focused session into the existing row above (or below) as an additional column when such a row exists, and only create a brand-new row via split when no row exists in that direction. Today the outcome is inconsistent — sometimes it lands in the existing row, sometimes it forces a new split row — even though the only thing that changed is the geometry of the existing grid, not any user intent difference.
- **Trace:**

  > moveSessionInDirection (src/vs/sessions/services/sessions/browser/sessionsService.ts:1248) finds a 'neighbor' via SessionGridLayout.neighbor() (src/vs/sessions/browser/parts/sessionGridLayout.ts:174), which just asks the base Grid for the nearest spatial leaf in that direction with no notion of 'the row above'. It then calls insertAt(session, neighbor.sessionId, 'up'/'down') (src/vs/sessions/services/sessions/browser/visibleSessions.ts:524), which always positions the moved view relative to that single neighbor leaf via Grid.moveView (src/vs/base/browser/ui/grid/grid.ts:480) — whether this merges into the neighbor's existing row or creates a new split branch depends on the internal tree shape, which is exactly the observed inconsistency. The fix needs a row-aware lookup (distinct from the geometric 'neighbor' used for focus navigation) before calling insertAt; do not change focusSessionInDirection's neighbor-finding, which should keep its current (correct) geometric behavior for arrow-key focus movement — only the move-session path's targeting needs to change. Referenced: issue screenshots and the linked in-progress PR https://github.com/microsoft/vscode/pull/339183.
- **Open decisions:**
  - When a row above exists with more than one existing column, which column position should the moved session land in — appended at the end, inserted nearest the session's current column, or always leftmost?
  - Should 'Move Session Above' ever still create a split within the row above (e.g., splitting an existing column) rather than always adding a new column slot?

## Evidence

- **move implementation:** src/vs/sessions/services/sessions/browser/sessionsService.ts:1248 moveSessionInDirection() calls sessionsPartService.getNeighborSession() for the nearest geometric neighbor, then always calls insertAt(session, neighbor.sessionId, 'up'/'down') — the destination is whatever view happens to be geometrically nearest, not an explicit 'row above' lookup.
- **neighbor is geometric, not row-aware:** src/vs/sessions/browser/parts/sessionGridLayout.ts:174 neighbor() delegates to the base Grid.getNeighborViews(), which returns the nearest spatial leaf in that direction — it has no concept of VS Code sessions-grid 'rows', so the same move can resolve to a leaf inside an existing row or to a leaf whose branch forces a brand-new split, depending on tree shape.
- **insertAt always splits relative to reference:** src/vs/sessions/services/sessions/browser/visibleSessions.ts:524 insertAt() sets placement {reference, direction} and src/vs/base/browser/ui/grid/grid.ts:480 moveView() moves the view next to that single reference leaf — whether that merges into an existing row or creates a new branch depends on the reference leaf's parent orientation, which is exactly the inconsistency reported.
- **issue context:** Reporter (houghj16) is testing a specific referenced PR (#339183) and filed same-day; already labeled bug + agents-window by the team, consistent with a known rough edge in the in-flight feature rather than settled, closeable behavior.
