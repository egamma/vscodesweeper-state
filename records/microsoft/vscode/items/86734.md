# Issue #86734 — Disambiguate quickSuggestion from editor.action.triggerSuggest

[https://github.com/microsoft/vscode/issues/86734](https://github.com/microsoft/vscode/issues/86734)

## Summary

The provider-facing distinction is still missing: automatic word suggestions and explicit invocation both produce CompletionTriggerKind.Invoke. Keep this open for the API and UX decision raised in the discussion; existing settings do not provide equivalent provider-specific control.

## Change summary

Allow completion providers to distinguish automatic quick suggestions from explicit invocation so embedded-language or expensive completions can be offered only on demand.

## Best solution

Define a backward-compatible completion-context contract that lets providers recognize explicit requests without changing existing providers' behavior. Resolve the thread's concern about different automatic and manual results before implementing the API across the editor and extension-host boundary.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages.ts`, `src/vs/editor/contrib/suggest/browser/suggestModel.ts`, `src/vs/workbench/api/common/extHostTypes.ts`, `src/vs/workbench/api/common/extHostTypeConverters.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`
- **Validation:** After the contract is agreed, exercise a completion provider in an embedded SQL string through automatic word suggestions and editor.action.triggerSuggest; assert that its received contexts distinguish those cases. Cover trigger-character and incomplete-list retriggers, and verify that providers using only the existing context fields retain their behavior.
- **Behavior:**

  > A completion-list provider currently cannot tell whether ordinary word completion was requested automatically or explicitly. The requested outcome is that an embedded-language provider can withhold low-confidence or expensive results during automatic typing while offering them on explicit invocation. Acceptance should demonstrate distinguishable provider contexts for those two entry points and backward-compatible behavior for existing providers.
- **Trace:**

  > SuggestModel's quick-suggestion path in src/vs/editor/contrib/suggest/browser/suggestModel.ts calls trigger with auto: true, whereas SuggestController.triggerSuggest in src/vs/editor/contrib/suggest/browser/suggestController.ts defaults auto to false. SuggestModel.trigger constructs CompletionContext without this distinction, assigning Invoke to both ordinary paths. The extension-host adapter in src/vs/workbench/api/common/extHostLanguageFeatures.ts converts that context through extHostTypeConverters.ts before calling the provider; the public contract in src/vscode-dts/vscode.d.ts exposes no corresponding distinction. Token-category quickSuggestions settings and the separate inline-completion API do not satisfy this provider-specific request. Preserve existing completion-provider behavior and existing trigger-character semantics. The unresolved boundary is the public invocation contract and whether differing result sets are acceptable, as discussed at https://github.com/microsoft/vscode/issues/86734.
- **Open decisions:**
  - Should completion-list providers be allowed to return additional results only on explicit invocation, accepting the automatic-versus-manual UX difference raised in the thread?
  - What backward-compatible public context contract should expose invocation intent, and what should it report for incomplete-list retriggers and programmatic completion requests?

## Evidence

- **Current API:** src/vscode-dts/vscode.d.ts:5141–5175 defines only Invoke, TriggerCharacter, and TriggerForIncompleteCompletions; CompletionContext contains triggerKind and triggerCharacter, with no automatic-versus-explicit field.
- **Current invocation paths:** src/vs/editor/contrib/suggest/browser/suggestModel.ts:452 starts automatic word suggestions with trigger({ auto: true }); suggestController.ts:598–604 starts manual suggestions with auto defaulting to false. SuggestModel.trigger at suggestModel.ts:552–559 does not include auto in the provider context, and both paths default to CompletionTriggerKind.Invoke.
- **Extension boundary:** src/vs/workbench/api/common/extHostLanguageFeatures.ts:1166–1178 passes the context through typeConvert.CompletionContext.to to the extension provider; extHostTypeConverters.ts:1122 onward maps the existing completion-context fields. The internal auto distinction is not exposed to CompletionItemProvider.
- **Existing-capability check:** EditorQuickSuggestions in src/vs/editor/common/config/editorOptions.ts provides token-category controls for other text, comments, and strings. These can suppress automatic suggestions for an entire category, but cannot let a particular embedded-language provider distinguish automatic calls from Ctrl+Space while preserving other providers. The separate InlineCompletionTriggerKind API applies to inline completions, not this completion-list provider contract.
- **Discussion and product decision:** The discussion at https://github.com/microsoft/vscode/issues/86734 supplies the concrete SQL-inside-JavaScript scenario. The December 16, 2019 response recognizes its relevance to fast and slow completion sources but explicitly leaves the user-confusion concern unresolved.
