# Issue #129818 — Git - Git changes panel shows mid-checkout changes (is not atomic)

[https://github.com/microsoft/vscode/issues/129818](https://github.com/microsoft/vscode/issues/129818)

## Summary

Keep open: current source suppresses refreshes during extension-managed writes, but a checkout launched in the terminal remains outside that operation tracking. The maintainer's proposed direction addresses part of the problem; preventing intermediate terminal-checkout results still needs investigation.

## Change summary

Prevent Source Control from displaying incomplete working-tree changes while a large terminal-driven branch checkout is still running.

## Best solution

Make the built-in Git extension defer publishing intermediate checkout status and refresh promptly after completion, including terminal-driven checkouts. Establish reliable external-operation detection without installing global Git hooks or weakening ordinary file-change refreshes.

## Plan brief

- **Likely files:** `extensions/git/src/repository.ts`, `extensions/git/src/operation.ts`, `extensions/git/src/terminal.ts`, `extensions/git/src/git.ts`
- **Validation:** With Source Control visible and autorefresh enabled, switch between branches with a large changeset using terminal git checkout. Correlate Git trace logs with command completion: intermediate working-tree changes must not be published, and the final status must appear afterward. Repeat with ordinary file edits and VS Code's checkout command to ensure existing refresh behavior remains intact; the planning session should establish deterministic regression coverage for the external-operation timing.
- **Behavior:**

  > A long-running branch checkout launched from the terminal can cause Source Control to show changes that exist only while Git is updating the working tree. Source Control should retain the last settled changes until checkout completes, then display the resulting repository state. Normal file edits must continue to refresh automatically, and extension-managed checkout behavior must remain intact. Acceptance requires observing the refresh timeline during a large checkout, not merely checking that the final state eventually becomes correct.
- **Trace:**

  > Working-tree events reach Repository.onFileChange in extensions/git/src/repository.ts and schedule updateWhenIdleAndWait after a one-second debounce. Its idle check uses OperationManager in extensions/git/src/operation.ts, populated by Repository.run, whereas terminal-launched checkout does not enter that wrapper. TerminalShellExecutionManager in extensions/git/src/terminal.ts requests status only after command completion and provides no running-operation barrier. Git status in extensions/git/src/git.ts uses GIT_OPTIONAL_LOCKS=0, and Repository._updateModelState publishes resource groups without an external-operation completion check. The maintainer's direction is recorded at https://github.com/microsoft/vscode/issues/129818#issuecomment-2535784836. The uncertainty begins at reliably detecting external write lifetimes and validating races, including terminals without usable shell integration; global hooks are only a reporter suggestion, not an agreed requirement. Keep huge-repository recovery from https://github.com/microsoft/vscode/issues/322337 outside this issue's acceptance scope.

## Evidence

- **Exact trigger and remaining source path:** The reporter runs git checkout in the terminal while Source Control is visible. In extensions/git/src/repository.ts:933–952, working-tree watcher events reach onFileChange; at 3334–3389, refresh scheduling checks only the extension's OperationManager, debounces for one second, and then calls status. An external checkout does not enter Repository.run, so a sufficiently long checkout with a pause in delivered events can trigger status before completion.
- **Existing suppression is limited to tracked operations:** extensions/git/src/repository.ts:2859–2897 registers and ends operations around extension-owned commands and refreshes after writes. OperationManager.isIdle in extensions/git/src/operation.ts considers only operations registered in its in-memory map; this does not establish that an independently launched Git process has finished.
- **No external-checkout publication barrier:** DotGitWatcher in extensions/git/src/repository.ts excludes index.lock events. extensions/git/src/git.ts:2794–2820 executes git status with GIT_OPTIONAL_LOCKS=0, and repository.ts:3074–3096 publishes the resulting resource groups without checking an external checkout's lifetime. This source trace establishes the race, not its timing or frequency on a particular machine.
- **Terminal completion handling is not atomicity:** TerminalShellExecutionManager in extensions/git/src/terminal.ts listens only to onDidEndTerminalShellExecution and calls repository.status after a recognized successful git checkout or other write command. It does not mark the command as running or suppress watcher-triggered refreshes before completion.
- **Maintainer direction:** https://github.com/microsoft/vscode/issues/129818#issuecomment-2535784836 proposes discarding filesystem events during write operations and refreshing afterward. Current source has that guard for extension-managed operations, but the report's terminal trigger remains outside it; a decline close would also contradict this accepted investigation direction.

It was created in 2026, later than this 2021 issue, and its persistent stale-state symptom differs from displaying intermediate checkout changes, so it cannot satisfy the stronger duplicate bar for this re-reviewed item.
