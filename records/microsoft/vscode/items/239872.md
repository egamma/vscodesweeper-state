# Issue #239872 — Error when installing extensions when using HTTP proxy

[https://github.com/microsoft/vscode/issues/239872](https://github.com/microsoft/vscode/issues/239872)

## Summary

The failure remains traceable on current main: a configured `http.proxyAuthorization` string is copied verbatim into Electron fetch requests, so values such as `username:password` can make extension installation fail with the opaque `net::ERR_INVALID_ARGUMENT`. The older related reports do not qualify as duplicate canonicals for this re-reviewed issue.

## Change summary

Prevent or clearly diagnose extension-install failures caused by an invalid `http.proxyAuthorization` value.

## Best solution

Define the supported `http.proxyAuthorization` contract, then validate or retire the setting so malformed values cannot surface as an unexplained Electron networking error. Preserve normal proxy authentication, including Electron's credential lookup when the setting is unset.

## Plan brief

- **Likely files:** `src/vs/platform/request/common/request.ts`, `src/vs/workbench/services/request/electron-browser/requestService.ts`, `src/vs/base/parts/request/common/requestImpl.ts`
- **Validation:** Add focused request-service tests covering an unset authorization value, a valid scheme-qualified Proxy-Authorization value, and the maintainer-selected behavior for plain `username:password`; verify extension gallery requests no longer reach Electron fetch with a malformed header.
- **Behavior:**

  > Installing an extension through the Extensions view must not fail with `net::ERR_INVALID_ARGUMENT` merely because `http.proxyAuthorization` contains plain credentials. Unsetting the setting must continue to allow Electron's normal proxy authentication flow, and valid supported authorization values must continue to work. Invalid values must produce the maintainer-selected actionable behavior rather than an opaque networking failure.
- **Trace:**

  > `NativeRequestService.request` in `src/vs/workbench/services/request/electron-browser/requestService.ts` copies the user-local `http.proxyAuthorization` value into `IRequestOptions`. `getRequestHeaders` in `src/vs/base/parts/request/common/requestImpl.ts` forwards it verbatim as `Proxy-Authorization`, while the schema in `src/vs/platform/request/common/request.ts` permits any string. Extension gallery downloads use `IRequestService`, so a value such as `username:password` reaches Electron fetch and corresponds to the reported `ERR_INVALID_ARGUMENT`; removing the setting bypasses that path and lets normal proxy credential lookup operate. Do not change CLI proxy support tracked separately by https://github.com/microsoft/vscode/issues/241683 or the broader extension proxy API work in https://github.com/microsoft/vscode/issues/12588.
- **Open decisions:**
  - Should `http.proxyAuthorization` continue accepting only a complete scheme-qualified header value, accept plain username/password credentials as shorthand, or be deprecated in favor of Electron's credential lookup?
  - When the configured value is unsupported, should VS Code reject it with an actionable configuration error or ignore it and fall back to normal proxy authentication?

## Evidence

- **current source path:** `src/vs/workbench/services/request/electron-browser/requestService.ts` reads the user-local `http.proxyAuthorization` value and assigns it directly to every native request; `src/vs/base/parts/request/common/requestImpl.ts` then sets that value verbatim as the `Proxy-Authorization` header before calling Electron fetch.
- **configuration contract:** `src/vs/platform/request/common/request.ts` accepts any string for `http.proxyAuthorization` and describes it only as the value sent as the header; it does not validate an authentication scheme or explain that plain `username:password` is not a complete Proxy-Authorization header value.
- **confirmed workaround:** The reporter confirmed that removing `http.proxyAuthorization` fixes extension installation and Copilot sign-in: https://github.com/microsoft/vscode/issues/239872#issuecomment-2784432734 and https://github.com/microsoft/vscode/issues/239872#issuecomment-2784755099.
- **current confirmation:** A later RHEL 9 report on VS Code 1.108.2 shows the same `net::ERR_INVALID_ARGUMENT` while `http.proxyAuthorization` contains plain credentials, even though Electron and Node proxy tests succeed: https://github.com/microsoft/vscode/issues/239872#issuecomment-3793787018.
- **canonical check:** https://github.com/microsoft/vscode/issues/176609 has the same workaround but is closed as info-needed; https://github.com/microsoft/vscode/issues/12588 is an older open extension proxy API request rather than the same reporter-observable configuration failure. The younger https://github.com/microsoft/vscode/issues/241683 concerns CLI authentication returning HTTP 407, so none satisfies the stronger duplicate bar.
