# Issue #192189 — Ability to disable diagnostics etc. from certain sources

[https://github.com/microsoft/vscode/issues/192189](https://github.com/microsoft/vscode/issues/192189)

## Summary

Keep open under discussion: current source filtering and TypeScript validation settings provide partial workarounds, but neither delivers configurable diagnostic-source priority in editor hovers. The discussion raises a performance concern rather than establishing a decision to decline the request.

## Change summary

Allow users to suppress redundant diagnostic sources or prioritize their preferred source when several diagnostics describe the same problem.

## Best solution

Resolve whether editor diagnostics should support source prioritization, taking the reporter's ordering alternative and the diagnostic-computation cost into account. Existing Problems-panel filtering should remain distinct from any editor-wide suppression or hover-ordering capability.

## Evidence

- **Discussion and revised request:** In https://github.com/microsoft/vscode/issues/192189, jrieken explains that hiding pushed diagnostics still wastes computation and recommends producer-side controls. The reporter then proposes ordering sources so Pretty TypeScript Errors appears first, and notes that some diagnostic entries lack a source.
- **Existing Problems-panel filtering:** src/vs/workbench/contrib/markers/browser/markersFilterOptions.ts parses @source:ts and !@source:eslint and implements matchesSourceFilters; markersTreeViewer.ts and markersTable.ts apply it to Problems rows. This filters that panel, not diagnostic production or editor-hover ordering, and cannot identify an unnamed source for selective exclusion.
- **Existing TypeScript validation control:** extensions/typescript-language-features/package.json registers js/ts.validate.enabled, described in package.nls.json as enabling or disabling JavaScript and TypeScript validation. The older typescript.validate.enable and javascript.validate.enable settings are also declared, with deprecation guidance toward the unified setting. Thus disabling validation does not require disabling the entire built-in extension, but this is not a general source-priority facility.
- **Remaining editor capability gap:** src/vs/editor/contrib/hover/browser/markerHoverParticipant.ts computes marker hover parts from line decorations and renders the supplied parts in sequence; its severity sort selects the status-bar marker rather than a user-preferred diagnostic source. src/vs/workbench/contrib/markers/browser/markers.contribution.ts exposes problems.sortOrder with severity and position choices, not source priority.
