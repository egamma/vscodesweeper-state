# Issue #339079 — WebViews in sidebar that use iframes frequently fail to load in v1.140

[https://github.com/microsoft/vscode/issues/339079](https://github.com/microsoft/vscode/issues/339079)

## Summary

Fresh, well-corroborated regression: multiple independent reporters (including the contributor author, across two different extensions) confirm iframe-based sidebar webviews intermittently fail to render after the v1.139.1 -> v1.140.0 upgrade, and it still reproduces on 1.141.0-insider, so this stays open and should be routed to the webview area owners; the root cause (timing/lifecycle vs. the bundled Electron/Chromium bump) isn't yet pinned down.

## Change summary

Sidebar webviews that load content via an embedded iframe frequently render a grey/blank box instead of loading, starting in v1.140.

## Best solution

Webview area owners should trace the iframe creation/attach path in the webview contribution (webviewElement.ts / the pre/index.html iframe host) across 1.139->1.140 to find what changed in iframe lifecycle or sandboxing, given the reporter's finding that forcing a reflow (setting/removing `srcdoc`) makes the frame load correctly.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/webview/browser/webviewElement.ts`, `src/vs/workbench/contrib/webview/browser/pre/index.html`
- **Validation:** A manual repro across several VS Code restarts confirming a sidebar iframe-based webview (e.g. the vscode-api-tests webview fixture with an embedded iframe) consistently loads without the grey-box failure.
- **Behavior:**

  > A webview view in the sidebar that injects an iframe and sets its `src` should reliably render that iframe's content. Since v1.140, it intermittently renders a grey/blank box instead, even though the injected script still runs and sets the iframe src, and the iframe is present in the DOM/console but not visible. Acceptance: repeated reloads/restarts of a sidebar webview using an iframe (e.g. Dart-Code's embedded DevTools) load successfully at a rate comparable to 1.139.1 (effectively every time), not ~20% of the time.
- **Trace:**

  > Symptom is isolated to the iframe-hosting path inside the webview's internal iframe (the webview content frame created by the webview contribution, likely src/vs/workbench/contrib/webview/browser/webviewElement.ts and its pre/index.html harness) — the outer webview and the injected script both run fine, but the inner iframe fails to paint. The reporter's finding that toggling `srcdoc` on the failed iframe forces it to load suggests a paint/attach timing issue rather than a network or script failure. No root-cause commit could be identified here because this checkout is shallow (1 commit only); diagnosis needs to happen against the real 1.139.1 vs 1.140.0 history, ideally also checking whether the bundled Electron/Chromium version changed between those VS Code releases. Do not conflate with https://github.com/microsoft/vscode/issues/125993, which DanTup only speculates may be related.
- **Open decisions:**
  - Is the regression caused by VS Code's own webview iframe lifecycle code, or by the Electron/Chromium version bundled in 1.140 (e.g. changed iframe sandboxing or cross-origin isolation behavior)?

## Evidence

- **reproduction rate:** Author tested 10 portable installs each: 1.139.1 loaded correctly 10/10, 1.140.0 only 2/10 (8/10 showed the grey box).
- **still broken on insiders:** Comment from DanTup on 1.141.0-insider (commit ec2e580674cdb512aa9b2a9596ab35d8a9590f1e) shows the bug still reproduces, ruling out an already-landed fix.
- **multiple independent confirmations:** digitalprobr confirms the same grey-box failure for a different extension's webview ("Property Editor"), and also had to downgrade to 1.139.1 to work around it.
- **shallow checkout limitation:** This checkout has only 1 commit of history (`5f22c683`), so I could not bisect the webview contribution source between 1.139 and 1.140 to pinpoint the change myself.
- **diagnostic lead:** DanTup found the iframe exists (visible via console picker, sensible width/height) but doesn't paint, and forcing `srcdoc` set/remove on the iframe makes it load — pointing at an iframe attach/paint timing issue rather than the webview process itself; possibly related to the Chromium bump to 150.0.7871.250 noted in the insiders build info.
