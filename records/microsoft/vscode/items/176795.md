# Issue #176795 — Variables within a configuration snippet defined in package.json file are not being allowed

[https://github.com/microsoft/vscode/issues/176795](https://github.com/microsoft/vscode/issues/176795)

## Summary

The bug was independently confirmed on multiple VS Code releases, and the available caret-based package.json encoding is undocumented and poorly understood. The issue should remain open until configuration snippets can preserve debug variables through a supported, documented syntax.

## Change summary

Debug configuration snippets contributed through package.json incorrectly transform `${command:...}` values instead of inserting them literally into launch.json.

## Best solution

Define and document a supported escaping contract for literal debug variables in contributed configuration snippets, then ensure snippet conversion preserves `${command:debugger.getPaths}` without relying on the caret workaround.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/common/debug.ts`, `src/vs/editor/contrib/snippet/browser/snippetParser.ts`
- **Validation:** Add a debug contribution test that loads a `configurationSnippets` body containing `${command:debugger.getPaths}` and asserts the generated launch configuration preserves that exact string without an undocumented caret prefix.
- **Behavior:**

  > An extension can contribute a debug `configurationSnippets` body containing a command variable such as `${command:debugger.getPaths}`. Selecting that snippet must insert the command variable literally into the generated debug configuration rather than transforming it into `debugger.debugger.getPaths`. Existing snippet placeholders and ordinary literal values must retain their current behavior. Acceptance requires an automated contribution-to-launch-configuration test covering the literal command variable.
- **Trace:**

  > The issue is independently reproduced through VS Code 1.79.2. The reported package.json contribution enters through the debug configuration-snippet contribution path and is ultimately interpreted with snippet syntax; commenters identified `src/vs/editor/contrib/snippet/browser/snippetParser.ts`, but also established that the parser may receive an already transformed value. The caret-and-escaped-quote workaround preserves the desired text, indicating another conversion stage likely participates. Trace the registration and normalization of `configurationSnippets` from `src/vs/workbench/contrib/debug/common/debug.ts` through snippet insertion before deciding ownership. Preserve normal snippet tab stops, variables, and existing debug-variable resolution semantics; do not generalize the change to unrelated snippets without evidence. Related closed report: https://github.com/microsoft/vscode/issues/186618.
- **Open decisions:**
  - Should contributed debug configuration snippets formally support literal `${command:...}` text directly, or require and document a distinct escaping syntax that is compatible with TextMate snippet variables?

## Evidence

- **confirmed reproduction:** The reporter reconfirmed the behavior after upgrading, and another user independently confirmed it in VS Code 1.78.2 and again documented it in 1.79.2.
- **observable failure:** A contributed `program` value of `${command:debugger.getPaths}` is inserted as `debugger.debugger.getPaths`, so the generated debug configuration no longer contains a resolvable command variable.
- **unsupported workaround:** The thread records that `^"\${command:pickRemoteProcess}"` produces the desired literal value, but neither the reporter nor commenters could establish this as a supported escaping contract.
- **related report:** https://github.com/microsoft/vscode/issues/186618 covers command variables in extension debug snippets but is closed and therefore cannot serve as a duplicate canonical for this open issue.
