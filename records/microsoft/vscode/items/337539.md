# Issue #337539 — Agent Host: apply the network filter to web fetches

[https://github.com/microsoft/vscode/issues/337539](https://github.com/microsoft/vscode/issues/337539)

## Summary

Confirmed security-relevant gap: IAgentNetworkFilterService (src/vs/platform/networkFilter/common/networkFilterService.ts) enforces the domain allow/deny filter for the local fetch tool, but the Agent Host's runtime-native `web_fetch` tool (src/vs/platform/agentHost/node/copilot/copilotToolDisplay.ts) isn't wired through it, so unlisted domains are fetched without the filter applying. This describes a security/sandboxing control bypass, so it stays open regardless of author or freshness.

## Change summary

Agent Host's built-in `web_fetch` tool bypasses the configured network filter that the local fetch/browser tools already enforce.

## Best solution

Route Agent Host web fetches through IAgentNetworkFilterService — either by substituting VS Code's own filtered fetch tool for the runtime's native web_fetch, or by checking each request host-side before it executes — with tests for allowlist/denylist/empty-list cases, per the issue's own checklist.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotToolDisplay.ts`, `src/vs/platform/networkFilter/common/networkFilterService.ts`
- **Validation:** Tests covering allowlist, denylist, and empty-list cases for an Agent Host web_fetch call, asserting blocked domains fail without a prompt when the network filter is enabled (per the issue's checklist).
- **Behavior:**

  > When `chat.agent.networkFilter` is enabled with a configured allow/deny domain list, an Agent Host web fetch to a disallowed domain must fail the same way the local fetch tool does today: no prompt, no silent fetch, even under 'Allow All' or assisted-approval modes. Fetches to allowed domains continue to work normally. Acceptance: new tests for allowlist, denylist, and empty-list configurations pass against the Agent Host's web_fetch path.
- **Trace:**

  > IAgentNetworkFilterService.isUriAllowed() (src/vs/platform/networkFilter/common/networkFilterService.ts) is the existing enforcement point used by the local fetch/browser tools. The Agent Host's runtime-native `web_fetch` tool (referenced in src/vs/platform/agentHost/node/copilot/copilotToolDisplay.ts as a distinct SDK-provided tool, and exercised in the e2e prompt snapshots under src/vs/platform/agentHost/test/node/e2e/) has no reference to this service, so filtering doesn't apply there. Two fix shapes are proposed in the issue: (1) expose VS Code's already-filtered fetch tool to the Agent Host instead of the SDK's native web_fetch, or (2) intercept/check outgoing web_fetch requests host-side against the same service. The boundary is scoped to how Agent Host resolves/executes the web_fetch tool call — do not change the filter's allow/deny matching logic itself (domainMatcher.ts) or the local (non-Agent-Host) fetch tool's behavior.
- **Open decisions:**
  - Should Agent Host stop advertising the SDK's native web_fetch tool and instead expose VS Code's own filtered fetch tool, or keep web_fetch but intercept/check requests host-side?
  - How should a blocked fetch be surfaced to the model/user under Agent Host (silent tool error vs. a prompt), to match 'no prompt' behavior for denied domains while still working under assisted approval for allowed ones?
