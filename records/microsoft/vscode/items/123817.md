# Issue #123817 — Clear secrets when extension is uninstalled

[https://github.com/microsoft/vscode/issues/123817](https://github.com/microsoft/vscode/issues/123817)

## Summary

Keep open: extension-scoped key enumeration now exists, but it does not deliver automatic secret cleanup on uninstall or a user-controlled reset independent of the extension. A maintainer explicitly supported uninstall cleanup, and no verified canonical or completed implementation was found.

## Change summary

Clear an extension's stored secrets when it is uninstalled and provide a way for users to reset them without extension cooperation.

## Best solution

Provide a VS Code-owned secret cleanup lifecycle and an extension-scoped user reset, preserving other extensions' secrets and persistence across ordinary sessions. Define profile and local/remote uninstall semantics before introducing deletion of application-wide credentials.

## Plan brief

- **Likely files:** `src/vs/platform/secrets/common/secrets.ts`, `src/vs/workbench/api/browser/mainThreadSecretState.ts`, `src/vs/workbench/services/extensionManagement/common/extensionManagement.ts`, `src/vs/workbench/services/extensionManagement/common/extensionManagementService.ts`, `src/vs/workbench/services/secrets/browser/secretStorageService.ts`
- **Validation:** After choosing lifecycle semantics, add targeted secret-storage/uninstall tests that store secrets for extensions A and B, successfully uninstall A, reload and reinstall A, and verify A's secrets are absent while B's remain. Cover failed uninstall, ordinary reload, and uninstall from only one profile or server while another installation remains; manually verify any user reset without extension cooperation.
- **Behavior:**

  > Secrets currently survive an extension's uninstall, reload, and reinstall. The requested outcome is removal of that extension's retained secrets on the agreed uninstall boundary, while ordinary sessions continue to preserve secrets and other extensions remain unaffected. Users also need a way to reset an extension's secrets when it exposes no cleanup command. Acceptance must cover successful versus failed uninstall and retention when the extension remains installed in another profile or server.
- **Trace:**

  > MainThreadSecretState in src/vs/workbench/api/browser/mainThreadSecretState.ts namespaces secrets using JSON containing extensionId and key; doGetKeys already enumerates only the calling extension's keys. BaseSecretStorageService in src/vs/platform/secrets/common/secrets.ts persists secrets at application scope, with selected credentials in application-shared scope. Workbench extension management exposes profile-aware and server-specific uninstall events in src/vs/workbench/services/extensionManagement/common/extensionManagement.ts and extensionManagementService.ts, so an uninstall event does not by itself establish that all consumers of an extension's credentials are gone. Inspected paths contain no integration that automatically purges those credentials. https://github.com/microsoft/vscode/issues/196616 covers enumeration, not the lifecycle gap. Preserve extension isolation and ordinary-session persistence; uncertainty starts at the user-visible deletion boundary and the scope of the reset surface.
- **Open decisions:**
  - Should uninstall delete application-wide secrets immediately when an extension is removed from one profile or server, or only when no relevant installation remains?
  - Should this work include an independent user-facing reset for an installed extension, or should that additional capability be tracked separately?
