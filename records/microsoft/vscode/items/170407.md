# Issue #170407 — Two extensions with conflicting custom semantic tokens cause vscode to crash

[https://github.com/microsoft/vscode/issues/170407](https://github.com/microsoft/vscode/issues/170407)

## Summary

The crash remains source-reproducible on current main: conflicting semantic-token contributions can create a cyclic super-type graph, and hierarchy resolution traverses it without cycle detection. This should remain open for a defensive core fix.

## Change summary

Prevent conflicting extension-defined semantic token types from creating a cyclic hierarchy that crashes VS Code.

## Best solution

Ensure semantic-token contribution processing detects or safely contains cyclic and conflicting type definitions, reports the invalid contribution to the responsible extension, and always terminates hierarchy resolution without disrupting valid token inheritance.

## Plan brief

- **Likely files:** `src/vs/platform/theme/common/tokenClassificationRegistry.ts`, `src/vs/workbench/services/themes/common/tokenClassificationExtensionPoint.ts`, `src/vs/workbench/services/themes/test/node/tokenStyleResolving.test.ts`
- **Validation:** Add a regression test beside the existing `super type` test that registers the reported operator/punctuation cycle, verifies token-style resolution terminates, and verifies valid acyclic inheritance remains unchanged; run the targeted token-style resolving test suite.
- **Behavior:**

  > Loading extensions whose semantic-token contributions form a cyclic super-type relationship must not hang or crash VS Code. Invalid conflicting contributions should be diagnosed without preventing unrelated extensions and valid semantic-token hierarchies from loading. Acceptance covers the reported two-extension cycle, a self-cycle, and the existing valid multi-level inheritance behavior.
- **Trace:**

  > TokenClassificationExtensionPoints in src/vs/workbench/services/themes/common/tokenClassificationExtensionPoint.ts validates contribution shape and then forwards every valid-looking type to the global registry. TokenClassificationRegistry.registerTokenType in src/vs/platform/theme/common/tokenClassificationRegistry.ts replaces entries with matching IDs, including the built-in `operator` type, allowing the reported registrations to produce `operator -> punctuation -> operator`. TokenClassificationRegistry.getTypeHierarchy then follows that graph without recording visited IDs, making the cycle non-terminating when a token selector is matched. Existing coverage in src/vs/workbench/services/themes/test/node/tokenStyleResolving.test.ts exercises only acyclic super types. Preserve valid inheritance and avoid changing semantic-token styling results for non-conflicting contributions.
- **Open decisions:**
  - Should duplicate semantic-token type IDs be rejected outright, or may extensions intentionally augment or replace prior definitions?
  - Should cycle validation happen while processing extension contributions, during registry registration, during hierarchy traversal, or through layered defenses?
  - Which conflicting extension contribution should receive the diagnostic when a cycle spans multiple extensions?

## Evidence

- **source reproduction:** In src/vs/platform/theme/common/tokenClassificationRegistry.ts:357-371, registerTokenType overwrites an existing entry by ID without checking for conflicts or cycles. The reported registrations therefore leave `operator.superType === punctuation` and `punctuation.superType === operator`.
- **unbounded traversal:** In src/vs/platform/theme/common/tokenClassificationRegistry.ts:462-470, getTypeHierarchy follows `superType` in a while loop without a visited set or cycle guard, so the reported two-node hierarchy never terminates.
- **extension validation gap:** src/vs/workbench/services/themes/common/tokenClassificationExtensionPoint.ts validates only the syntax of IDs and super-type IDs before registering them; it does not reject duplicate built-in IDs, conflicting definitions, or cyclic inheritance.
- **existing test surface:** src/vs/workbench/services/themes/test/node/tokenStyleResolving.test.ts contains the existing `super type` hierarchy test but no cyclic or conflicting-registration coverage.
- **canonical search:** Repository issue searches for semanticTokenTypes crashes and cyclic/infinite semantic-token hierarchies found no separate open canonical issue owning this defect.
