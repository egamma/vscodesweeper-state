# Issue #281465 — Undoing a next rename suggestion proposes the same rename refactoring

[https://github.com/microsoft/vscode/issues/281465](https://github.com/microsoft/vscode/issues/281465)

## Summary

The confirmed NES bug remains open: current source does not prevent an accepted rename suggestion from being proposed again after undo, and the only linked workaround PR was closed without merging. As a team-authored Backlog issue with no verified fix or duplicate, it should remain open.

## Change summary

Prevent Next Edit Suggestions from proposing the same rename refactoring again after the user accepts and then undoes it.

## Best solution

Track accepted rename edits in the NES cache and suppress an equivalent cached or regenerated suggestion after its effects are undone, while preserving legitimate later rename suggestions. Start with a focused cache-level reproduction because the issue author explicitly identifies that layer as the proper fix.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/inlineEdits/node/nextEditCache.ts`, `extensions/copilot/src/extension/inlineEdits/node/nextEditProvider.ts`, `extensions/copilot/src/extension/inlineEdits/test/node/nextEditProviderCaching.spec.ts`, `src/vs/editor/contrib/inlineCompletions/browser/model/renameSymbolProcessor.ts`
- **Validation:** Add a focused NES caching test that accepts a rename suggestion, applies the inverse edit representing Undo, and verifies that requesting the next edit does not return the same rename; verify that a distinct later rename remains eligible.
- **Behavior:**

  > After a user accepts an NES rename refactoring and undoes it, NES must not immediately offer the same rename refactoring again. Different rename proposals and a deliberately repeated rename after the suppression lifetime must remain possible. Acceptance requires a deterministic cache-level test covering accept, undo, and the subsequent NES request.
- **Trace:**

  > The editor path in src/vs/editor/contrib/inlineCompletions/browser/model/renameSymbolProcessor.ts converts an eligible inline edit into a rename action but retains no history after applying it. The NES cache in extensions/copilot/src/extension/inlineEdits/node/nextEditCache.ts tracks cached and rejected edits, while NextEditProvider in extensions/copilot/src/extension/inlineEdits/node/nextEditProvider.ts owns cache use and user-action handling. The reporter explicitly identifies this cache layer as the proper fix; https://github.com/microsoft/vscode/pull/281467 instead attempted a local LRU workaround in RenameSymbolProcessor and was closed unmerged. The plan should first trace how acceptance and the inverse undo edit mutate or rebase the cached entry, then define a bounded suppression lifetime. Do not broadly suppress equivalent renames across unrelated documents or indefinitely block a rename the user intentionally requests later.
- **Open decisions:**
  - For how long should an accepted-and-undone rename remain suppressed before an identical rename becomes eligible again?
