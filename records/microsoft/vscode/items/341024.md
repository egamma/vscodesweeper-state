# Issue #341024 — Feature request for `sessions.experimental.layoutScope`: Add option to remember bottom pane state as well, not just visibility

[https://github.com/microsoft/vscode/issues/341024](https://github.com/microsoft/vscode/issues/341024)

## Summary

Keep open: chat-scoped layout remembers the selected panel view, but not the selected terminal within it. Current source explicitly preserves that boundary, and the maintainer's Insiders check confirms the requested capability remains missing.

## Change summary

Remember and restore the selected bottom-pane terminal separately for each chat.

## Best solution

Provide opt-in per-chat terminal selection restoration in the Sessions terminal contribution, coordinated with layout ownership without changing terminal creation, task reuse, or process lifetime. Decide whether this extends the existing chat layout mode or uses a separate control.

- **Behavior:**

  > With per-chat terminal selection enabled, returning to chat A restores the terminal last selected in A, while returning to chat B restores B's selection, including when both chats share a working directory. Remembering the Terminal panel view alone does not satisfy this request. Acceptance should cover repeated switching and switching after commands run in another terminal, without creating or killing terminals as a side effect.
- **Trace:**

  > The layout registration in src/vs/sessions/contrib/layout/browser/sessions.layout.contribution.ts deliberately excludes terminal behavior from layoutScope. ChatLayoutContext in src/vs/sessions/common/chatLayout.ts exposes session/chat ownership, while SessionsTerminalContribution in src/vs/sessions/contrib/terminal/browser/sessionsTerminalContribution.ts tracks session ID, cwd, and backend. _onActiveSessionChanged short-circuits when that scope is unchanged; _updateTerminalVisibility otherwise prefers the terminal with the latest command. Existing sibling-chat tests preserve session terminal behavior in all layout modes. The remaining uncertainty is the public opt-in and persistence contract, not whether the selection gap exists. Preserve provider/backend matching, task reuse, visibility policy, cleanup safeguards, and process lifetime. Related https://github.com/microsoft/vscode/issues/335133 and https://github.com/microsoft/vscode/issues/335252 describe distinct projection and split-layout problems.
- **Open decisions:**
  - Should per-chat terminal selection extend sessions.experimental.layoutScope: chat, apply to both chat-owned modes, or require a separate opt-in control?
  - Should remembered terminal selection survive window reload when the corresponding terminal reconnects, or remain limited to the current window lifetime?
