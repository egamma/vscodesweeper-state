# Issue #227238 — Zoom : The left commonly used section tree view content gets disappear when viewing the page at 200% browser zoom and a 1280-pixel viewport width. 

[https://github.com/microsoft/vscode/issues/227238](https://github.com/microsoft/vscode/issues/227238)

## Summary

The reported disappearance remains source-reproducible: the Settings editor explicitly hides category navigation below its narrow-layout threshold. Keep this accepted accessibility bug open; restoring access at enlarged zoom requires a narrow-layout interaction decision, not merely changing the breakpoint.

## Change summary

Preserve access to Settings categories, including Commonly Used, at 200% zoom in a 1280-pixel viewport.

## Best solution

Provide discoverable, keyboard-operable category navigation in the Settings editor's narrow layout without sacrificing readable settings controls. Agree on the compact navigation interaction before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/preferences/browser/settingsEditor2.ts`, `src/vs/workbench/contrib/preferences/browser/media/settingsEditor2.css`, `src/vs/workbench/contrib/preferences/browser/preferences.contribution.ts`
- **Validation:** At a 1280-pixel browser viewport and 200% zoom, open Settings with an empty search and verify that Commonly Used and other categories can be discovered, reached by keyboard, and selected without reducing zoom. Resize across the current 700 CSS-pixel threshold and verify usable focus, readable settings controls, and unchanged wide-layout and search-ToC behavior.
- **Behavior:**

  > At 200% zoom in a 1280-pixel viewport, the Settings editor removes its category tree, preventing direct use of Commonly Used and other categories. Category navigation must remain discoverable and keyboard-operable at that zoom without requiring users to shrink text. Acceptance includes navigating to a category, retaining usable focus when resizing, and preserving readable settings controls and existing wide-layout behavior.
- **Trace:**

  > SettingsEditor2 defines NARROW_TOTAL_WIDTH as TOC_RESET_WIDTH plus EDITOR_MIN_WIDTH, currently 700 CSS pixels. Its layout() sets narrow-width, layoutSplitView() hides split-view index 0, and settingsEditor2.css independently hides the ToC container under that class. The settingsSearchTocBehavior setting only controls search-time visibility, and focusTOC() does not reveal the hidden navigation. https://github.com/microsoft/vscode/issues/145243#issuecomment-1074307423 confirms that small-width hiding was deliberate historically, while this later report is accepted as an accessibility bug. The remaining uncertainty is the user-facing compact navigation interaction; preserve wide-layout resizing, settings readability, and existing search behavior.
- **Open decisions:**
  - At narrow widths, should category navigation remain inline in a reflowed layout, or become an explicitly opened compact navigation surface?

## Evidence

- **Current source reproduces hiding:** src/vs/workbench/contrib/preferences/browser/settingsEditor2.ts:128-132 defines a 700 CSS-pixel narrow-layout threshold from a 200-pixel ToC plus a 500-pixel editor minimum. layout():637-651 applies narrow-width below that threshold; layoutSplitView():2254-2284 also calls setViewVisible(0, false) when the available body width falls below it. A 1280-pixel viewport at 200% zoom falls below this threshold.
- **Navigation is removed rather than reflowed:** src/vs/workbench/contrib/preferences/browser/media/settingsEditor2.css:299-301 applies display: none to .settings-toc-container in narrow-width mode. This directly explains the missing left-hand category tree; it is not evidence of a Chromium rendering failure.
