# Issue #350736 — P2 Emmet re-parses the entire HTML document on every completion request while typing (~2–2.5 s extension host CPU per 15 keystrokes, +0.2–0.8 s completion latency on a 30k-line HTML file)

[https://github.com/microsoft/vscode/issues/350736](https://github.com/microsoft/vscode/issues/350736)

## Summary

Keep open: current source confirms that HTML location detection reparses the complete document after edits invalidate the version cache. The report supplies a reproducible workload and A/B measurements; the historical cache fix does not eliminate this remaining typing cost.

## Change summary

Avoid repeated whole-document HTML parsing for Emmet completions while typing in large files.

## Best solution

Provide cheaper HTML completion-context detection while preserving embedded-language selection and valid abbreviation behavior. Diagnose and benchmark the context-preserving approach before implementation; disabling Emmet suggestions is a workaround, not a fix.

## Plan brief

- **Likely files:** `extensions/emmet/src/defaultCompletionProvider.ts`, `extensions/emmet/src/parseDocument.ts`, `extensions/emmet/src/util.ts`, `extensions/emmet/src/test/completion.test.ts`
- **Validation:** Repeat the issue's generated HTML typing and Ctrl+Space workload with extension-host profiling, recording parse frequency, CPU time, and suggestion latency before and after. Verify that the reported full-parse-per-edit pattern is eliminated without suppressing valid suggestions, then run scripts/test-integration.sh --suite emmet with regression cases for successive edits and embedded HTML/CSS/script contexts.
- **Behavior:**

  > Typing HTML abbreviations in the supplied large document should not repeatedly incur complete HTML-tree reconstruction for completion-context detection. Valid suggestions and their expansions must remain available after successive edits. Embedded CSS, script MIME-type handling, and template content must retain their existing behavior. Acceptance combines the same before/after profiling workload with completion correctness checks; disabling suggestions does not satisfy the goal.
- **Trace:**

  > DefaultCompletionItemProvider.provideCompletionItemsInternal in extensions/emmet/src/defaultCompletionProvider.ts obtains an HTML root before abbreviation extraction when validateLocation remains true. getRootNode in extensions/emmet/src/parseDocument.ts caches by URI and document.version, then parses all document text on a version mismatch; edits invalidate reuse. Incomplete-completion requests can bypass this work when lastCompletionType is known, so profiling must distinguish trigger kinds. util.ts:getHtmlFlatNode resolves ordinary nodes, template-script subtrees, and CDATA, while the provider uses that context to select HTML or CSS and suppress inappropriate script suggestions. The shared root parser also serves structural editing commands whose behavior must remain unchanged. The unresolved technical boundary is how to obtain correct completion context cheaply across edits without losing surrounding-document context; no bounded implementation has yet been established. https://github.com/microsoft/vscode/pull/78207 introduced the historical caching fix but does not resolve version churn.

## Evidence

- **Current source confirms the expensive path:** At checkout commit 6737a1ccd2c3ceebe67eb57d3c14b2c9e1c2589c, extensions/emmet/src/defaultCompletionProvider.ts:75–93 calls getRootNode(document, true) for HTML location detection before abbreviation extraction. extensions/emmet/src/parseDocument.ts:20–35 only reuses a tree when document.version matches, otherwise synchronously parses document.getText(). Successive edits therefore invalidate that cache.
- **Important trigger qualification:** defaultCompletionProvider.ts:77–89 skips location detection for TriggerForIncompleteCompletions when lastCompletionType is HTML or CSS. The defect is repeated full parsing on requests that still require context detection, not an unconditional parse on every possible completion request.
- **Reporter workload and impact:** https://github.com/microsoft/vscode/issues/350736 supplies a 30,002-line HTML generator, typing and Ctrl+Space steps, and an emmet.showExpandedAbbreviation: never comparison. Its profiles attribute substantial synchronous extension-host work to Emmet parsing. Source inspection confirms the mechanism; runtime timings were not independently measured.
- **Existing optimization does not cover HTML:** defaultCompletionProvider.ts:135–139 uses parsePartialStylesheet only for stylesheet documents above 1,000 lines. The HTML path has no corresponding optimization. Setting emmet.showExpandedAbbreviation to never exits the provider early but removes the requested suggestions.
- **Historical fix is insufficient:** https://github.com/microsoft/vscode/issues/70371 is closed and identifies merged https://github.com/microsoft/vscode/pull/78207 as its fix. The current version-keyed cache still reparses after edits, so that historical resolution does not establish completion of this report.
- **Canonical and PR search:** Open Emmet issue and PR searches found no verified canonical or implementation candidate for this parsing cost. https://github.com/microsoft/vscode/issues/31078 concerns activeTextEditor being undefined for documents with very long lines; https://github.com/microsoft/vscode/issues/27378 requests general zero-latency typing. Neither establishes ownership of this specific Emmet completion defect.
- **Correctness boundary:** defaultCompletionProvider.ts:94–123 distinguishes script MIME types, style elements, and inline style attributes. util.ts:getHtmlFlatNode also handles template scripts and CDATA. getRootNode is shared with structural editing commands, so changing its tree semantics could affect unrelated Emmet operations.
