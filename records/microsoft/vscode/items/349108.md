# Issue #349108 — Match native inline comment borders and styling to the VS Code workbench

[https://github.com/microsoft/vscode/issues/349108](https://github.com/microsoft/vscode/issues/349108)

## Summary

Keep open as native comments UI polish: current inline styling still distinguishes the square idle reply field from the rounded composer. The experimental floating presentation improves these treatments but does not satisfy the request for consistency within the inline layout.

## Change summary

Align native inline comment threads, reply states, and action presentation with comparable workbench controls while preserving accessibility and compactness.

## Best solution

Bring the inline comments surface onto the workbench's shared radius and theme conventions without changing its in-code placement. Agree on the secondary action hierarchy before changing action placement, preserving extension contributions and keyboard behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/comments/browser/media/review.css`, `src/vs/workbench/contrib/comments/browser/commentReply.ts`, `src/vs/workbench/contrib/comments/browser/commentThreadZoneWidget.ts`, `src/vs/workbench/contrib/comments/browser/commentFormActions.ts`
- **Validation:** Using a synthetic public Comments API provider, compare a published inline thread with its idle reply field, keyboard-focused reply field, expanded composer, and edit state in dark, light, and high-contrast themes. Verify consistent corner treatment, visible focus, unclipped content at narrow widths, unchanged compactness, and working Tab/Shift+Tab navigation, submission, and extension-contributed actions; also check that floating threads remain unaffected.
- **Behavior:**

  > Native inline comment threads should feel consistent with comparable workbench surfaces across published, idle-reply, composing, and editing states. Preserve compact dimensions, high-contrast focus visibility, keyboard navigation, screen-reader semantics, and extension-contributed commands. The secondary goal is a clearer relationship between the reply editor, its submit action, and thread-level actions, without adding formatting controls.
- **Trace:**

  > review.css assigns square corners to the collapsed reply button and a separate rounded treatment to the embedded editor. CommentReply.initialize selects between these states according to whether the thread already contains comments. ReviewZoneWidget in commentThreadZoneWidget.ts owns the inline ZoneWidget presentation. The floating variant has separate tokenized styling in review.css, but its placement and interaction model differ from the requested inline surface. CommentFormActions already uses shared workbench buttons and primary/secondary styles, so preserve those controls and extension action contracts. Source inspection establishes the styling split; rendered appearance was not executed in this read-only review.
- **Open decisions:**
  - What visible grouping and primary/secondary ordering should distinguish reply submission from thread-level actions, while preserving all extension-contributed commands?

## Evidence

- **Existing inline styling:** src/vs/workbench/contrib/comments/browser/media/review.css explicitly sets .review-thread-reply-button to border-radius: 0, while the reply/edit Monaco editor receives border-radius: 3px. These distinct rules substantiate the reported state inconsistency.
- **State transition:** CommentReply.initialize in src/vs/workbench/contrib/comments/browser/commentReply.ts creates the collapsed reply button for existing comments and expands the editor for an empty thread. The two screenshot states correspond to separate production rendering paths.
- **Existing-capability check:** comments.thread.experimental.style is registered in src/vs/workbench/contrib/comments/browser/comments.contribution.ts with default 'inline' and alternative 'floating'. review.css gives floating threads tokenized outer corners, control-tier reply corners, and revised spacing, but those rules are scoped to .comment-thread-floating-widget; changing placement is not equivalent to improving the inline surface.
- **Shared controls already used:** CommentFormActions.setActions in src/vs/workbench/contrib/comments/browser/commentFormActions.ts already renders Button/ButtonWithDropdown with defaultButtonStyles and primary/secondary treatment. The remaining request concerns composition and consistency, not replacing extension-provided actions with custom controls.
