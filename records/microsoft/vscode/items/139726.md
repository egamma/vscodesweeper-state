# Issue #139726 — Configure unicode highlight limit

[https://github.com/microsoft/vscode/issues/139726](https://github.com/microsoft/vscode/issues/139726)

## Summary

Keep open: current main still has a hard-coded Unicode highlighting limit and no setting to retain highlighting above it. A maintainer supported an opt-in control, and the related banner request is newer, so it cannot absorb this re-reviewed item as a duplicate.

## Change summary

Allow Unicode highlighting to remain useful in documents with thousands of special characters, with configurable limits and less repetitive banner behavior.

## Best solution

Provide an opt-in way to inspect non-breaking spaces in Unicode-heavy translation files while preserving default performance safeguards. Settle the limit and overflow-warning behavior with the editor owner, coordinating the overlapping banner request.

- **Likely files:** `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/common/services/unicodeTextModelHighlighter.ts`, `src/vs/editor/contrib/unicodeHighlighter/browser/unicodeHighlighter.ts`, `src/vs/editor/test/common/services/unicodeTextModelHighlighter.test.ts`
- **Validation:** Extend the UnicodeTextModelHighlighter suite with documents containing 1000, 1001 and 5337 qualifying non-breaking spaces, asserting ranges and hasMore under the selected default and opt-in policy. Run the targeted suite through scripts/test.sh. In an editor, verify the chosen highlighting and banner behavior when opening, switching away from, and returning to the 5337-character translation file; exercise both worker-backed and viewport fallback paths.
- **Behavior:**

  > A translation-file author needs to distinguish normal spaces from non-breaking spaces even when the document contains thousands of qualifying characters. An explicit user opt-in should make that inspection possible without disabling invisible-character detection or excluding non-breaking spaces. The default must retain performance safeguards, and the UI must not imply that a scan is complete when qualifying characters remain unhighlighted. Acceptance covers documents below and above the current 1000-character threshold, the reporter's approximately 5337-character case, and banner behavior across file switches.
- **Trace:**

  > UnicodeTextModelHighlighter.computeUnicodeHighlights in src/vs/editor/common/services/unicodeTextModelHighlighter.ts returns at most 1000 ranges and sets hasMore on the next qualifying character. DocumentUnicodeHighlighter._update and ViewportUnicodeHighlighter._update in src/vs/editor/contrib/unicodeHighlighter/browser/unicodeHighlighter.ts suppress all decorations when their result hasMore; UnicodeHighlighter._updateState then shows a category-specific warning, with dismissal reset on model changes. The options registered in src/vs/editor/common/config/editorOptions.ts contain no limit or overflow override. The existing test suite in src/vs/editor/test/common/services/unicodeTextModelHighlighter.test.ts demonstrates non-breaking-space detection but does not cover overflow. Preserve character classification, locale exemptions and trust-sensitive defaults; this request does not concern selection-occurrence highlighting. The maintainer proposed an opt-in overflow-highlighting control in https://github.com/microsoft/vscode/issues/139726 and later supported a configurable limit in https://github.com/microsoft/vscode/issues/147888#issuecomment-1109553992; neither record settles their combined behavior.
- **Open decisions:**
  - Should the opt-in provide a configurable finite highlight limit, highlighting despite overflow, or both, and what user-visible guarantee should it make about complete coverage?
  - When the opt-in is enabled, should the banner disappear only after all qualifying characters are highlighted, or remain in a less intrusive form whenever highlighting is incomplete?
