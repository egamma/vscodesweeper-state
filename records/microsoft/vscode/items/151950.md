# Issue #151950 — Workbench decorations for files with comments

[https://github.com/microsoft/vscode/issues/151950](https://github.com/microsoft/vscode/issues/151950)

## Summary

Keep open: existing comment indicators do not cover files in the Explorer tree, which the reporter explicitly requested. This accepted Backlog request has 36 upvotes, and inspection found neither a covering implementation nor a verified canonical duplicate.

## Change summary

Indicate in the Explorer file tree which files contain review comments, without requiring users to open each file or switch to the pull-request view.

## Best solution

Provide a consistent file-level comment indicator through the workbench decoration infrastructure, using comment data already available to the comments service. Settle which comment states qualify and how the indicator coexists with existing file decorations before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/comments/browser/comments.contribution.ts`, `src/vs/workbench/contrib/comments/browser/commentService.ts`, `src/vs/workbench/contrib/comments/browser/commentsModel.ts`, `src/vs/workbench/services/decorations/common/decorations.ts`
- **Validation:** Exercise Explorer with a comment provider: a file with qualifying comments gains an indicator without being opened; adding or removing threads and unregistering the provider updates it; unrelated files stay unchanged. Check the chosen resolved-thread behavior, coexistence with SCM/problem decorations, and explorer.decorations.badges=false. Add focused automated coverage for resource decoration results and lifecycle invalidation.
- **Behavior:**

  > Users can identify files containing review comments directly in the Explorer file tree, without opening each file or navigating to Changes in Pull Request. Indicators track available comment data as threads are added or removed and providers disappear. Acceptance must cover the agreed handling of resolved comments and coexistence with existing Explorer decorations. Existing editor comments and the Comments view retain their behavior.
- **Trace:**

  > The clarified request at https://github.com/microsoft/vscode/issues/151950 concerns the core Explorer surface, not the pull-request extension's own tree. In src/vs/workbench/contrib/comments/browser/comments.contribution.ts, UnresolvedCommentsBadge aggregates unresolved threads into Comments-view activity only; the comments contribution does not register a resource decorations provider. CommentService in browser/commentService.ts exposes thread/provider lifecycle events and CommentsModel in browser/commentsModel.ts maintains per-resource, per-owner thread data. The resource-decoration contract is in src/vs/workbench/services/decorations/common/decorations.ts, and Explorer already exposes badge/color visibility settings. Inspection establishes the missing integration but does not settle which thread states should qualify or how comment indicators should interact with competing file decorations. Keep the work scoped to already available comment data; changing GitHub fetching, editor thread rendering or pull-request navigation is not established as necessary.
- **Open decisions:**
  - Should the Explorer indicator represent every nonempty comment thread, including resolved threads, or only unresolved threads?
  - When a file already has SCM or problem decorations, should its comment indicator remain independently visible or participate in the existing decoration-priority behavior?
