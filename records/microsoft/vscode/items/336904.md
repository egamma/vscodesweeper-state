# Issue #336904 — Agents Web: Expose ChatGPT/Codex providers from remote Agent Host

[https://github.com/microsoft/vscode/issues/336904](https://github.com/microsoft/vscode/issues/336904)

## Summary

Real, independently confirmed gap (three separate reporters, tunnel and SSH) where the remote Agents web client's model picker doesn't surface non-Copilot providers (ChatGPT/Codex, Claude) that are configured on the desktop Agent Host — this is a genuine parity gap in the remote Agent Host architecture, not something to close, but the fix requires a maintainer design decision on cross-provider auth forwarding, not a bounded patch.

## Change summary

The remote Agents window (via vscode.dev/agents tunnel or SSH) only lists GitHub/Copilot models, not other providers (ChatGPT/Codex, Claude) that are authenticated on the connected desktop/remote Agent Host.

## Best solution

Design how provider/model availability and authentication (e.g. ChatGPT/Codex, Claude sessions) is forwarded to remote/web Agent Host clients so the remote model picker mirrors what's available on the host; likely touches remoteAgentHostChatContribution.ts, agentHostLanguageModelProvider.ts, and the auth-forwarding helpers in agentHostAuth.ts.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostChatContribution.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostLanguageModelProvider.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts`
- **Validation:** A test/manual check confirming that once a desktop Agent Host has an authenticated ChatGPT/Codex (or Claude) provider, connecting via a remote tunnel/SSH shows that provider in the remote model picker.
- **Trace:**

  > remoteAgentHostChatContribution.ts iterates `rootState.agents` (from the connected Agent Host's protocol state) and registers a language model provider per `agent.provider`, so the registration path itself isn't hardcoded to Copilot — the gap likely lies in whether/how non-Copilot provider auth state (ChatGPT/Codex, Claude) is included in `rootState` for remote connections, or how `agentHostLanguageModelProvider.ts` / `agentHostAuth.ts` handle auth session forwarding to a web/remote client versus a local one. This was not traced to a specific missing line — it needs investigation of the rootState population and auth propagation path before any implementation.
- **Open decisions:**
  - Should remote/web Agent Host clients receive full parity with the desktop host's configured providers, or is there a deliberate security boundary limiting which provider credentials can be exposed to a remote/browser client?
  - For providers requiring interactive OAuth (ChatGPT/Codex, Claude), should authentication be proxied through the already-authenticated host, or does the remote/web client need its own re-auth flow?
  - Does this apply uniformly to both the vscode.dev tunnel scenario and the Remote-SSH scenario, or do they need different solutions given different connection/auth models?
