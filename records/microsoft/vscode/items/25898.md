# Issue #25898 — [html] provide translations of tag documentation

[https://github.com/microsoft/vscode/issues/25898](https://github.com/microsoft/vscode/issues/25898)

## Summary

A real gap remains: current VS Code localizes the HTML language server UI but still sources tag documentation from English-only generated data. With 48 upvotes and a Backlog milestone, this should remain open for design and implementation rather than stale-feature cleanup.

## Change summary

Localize built-in HTML tag documentation, including hover and IntelliSense text, according to VS Code's display language.

## Best solution

Provide locale-aware built-in HTML documentation through the HTML language service or its web-custom-data source, with reliable English fallback for untranslated entries, then consume it through VS Code's existing language-server localization setup.

- **Reason:** Making web-language documentation usable in the configured display language advances VS Code's durable language-support and accessibility direction.
- **Evidence:** Durable themes: “Accessibility” and “Languages & protocols,” including first-class web-language experiences.

## Plan brief

- **Likely files:** `extensions/html-language-features/server/src/modes/languageModes.ts`, `extensions/html-language-features/server/src/node/htmlServerNodeMain.ts`, `extensions/html-language-features/server/src/browser/htmlServerWorkerMain.ts`, `extensions/html-language-features/server/src/test/hover.test.ts`
- **Validation:** Add an HTML language-server hover test using a Korean localization bundle and localized HTML data, asserting that a known tag description is Korean while an untranslated entry falls back to English; run the targeted html-language-features server test suite.
- **Behavior:**

  > When VS Code uses Korean or another supported display language, built-in HTML tag hover and IntelliSense documentation appears in that language where a translation exists. Missing entries fall back to the existing English documentation rather than becoming empty or suppressing completion details. Custom HTML data providers and English installations retain their current behavior. Acceptance includes a localized hover assertion and an untranslated-entry fallback assertion.
- **Trace:**

  > The client already forwards VSCODE_L10N_BUNDLE_LOCATION in extensions/html-language-features/client/src/node/htmlClientMain.ts, and the node and browser server entry points configure @vscode/l10n. However, getLanguageModes in extensions/html-language-features/server/src/modes/languageModes.ts creates vscode-html-languageservice with its default provider, whose documentation is generated as English text in vscode-html-languageservice/src/languageFacts/data/webCustomData.ts from @vscode/web-custom-data. vscode-html-languageservice/src/services/htmlHover.ts returns those provider descriptions directly, so message-bundle localization cannot translate them. The plan must coordinate the data and locale contract with https://github.com/microsoft/vscode-html-languageservice/issues/137 and determine the generated translation source; it must not regress custom data providers, English fallback, or non-documentation HTML language features.
- **Open decisions:**
  - Should the first supported scope localize only tag descriptions requested here, or all built-in HTML documentation exposed for tags, attributes, values, and compatibility annotations?
  - When only part of an entry is translated, should fallback occur per documentation field or for the entire entry?
  - Which display languages must be supported for the initial rollout, and what translation-completeness threshold is required before enabling each locale?

## Evidence

- **current source gap:** extensions/html-language-features/server/src/modes/languageModes.ts constructs vscode-html-languageservice without a locale-specific data provider; its default documentation therefore remains the package's built-in data.
- **localization plumbing:** extensions/html-language-features/client/src/node/htmlClientMain.ts passes VSCODE_L10N_BUNDLE_LOCATION, and extensions/html-language-features/server/src/node/htmlServerNodeMain.ts configures @vscode/l10n, but this localizes message strings rather than the generated HTML documentation dataset.
- **English-only data source:** The current vscode-html-languageservice generates src/languageFacts/data/webCustomData.ts from @vscode/web-custom-data/data/browsers.html-data.json; entries such as the html element description are embedded in English and htmlHover.ts returns those descriptions directly.
- **related issue:** https://github.com/microsoft/vscode-html-languageservice/issues/137 is open and requests the same translatable documentation capability, but it was created in 2022, five years after this issue; under the stronger re-review rule it cannot be the canonical duplicate for this older report.
- **community demand:** The issue has 48 community upvotes, exceeding the 20-upvote Backlog threshold, and a maintainer explicitly asked users to vote while leaving the request in Backlog.
- **data coordination:** https://github.com/mdn/data/issues/199 remains open and records discussion of sourcing editor documentation and translations from MDN, including an explicit reference to this issue, but it does not provide a completed localized data path.
