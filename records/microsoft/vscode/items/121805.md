# Issue #121805 — "Reopen folder using..." should use a more dedicated ux solution, not notifications

[https://github.com/microsoft/vscode/issues/121805](https://github.com/microsoft/vscode/issues/121805)

## Summary

The central UX gap remains on current main: discovering a `.code-workspace` file still produces a notification, while the broader replacement surface for workspace and Dev Container reopen actions remains undecided. The existing `under-discussion`, `ux`, and `remote` routing is appropriate.

## Change summary

Replace startup notifications for reopening a folder as a workspace or Dev Container with a less disruptive, dedicated discovery surface.

## Best solution

Define one discoverable, non-toast UX pattern for reopen recommendations that preserves first-use discoverability across core workspaces and Dev Containers. Implement the core side in the workspaces contribution and coordinate the matching Dev Containers behavior with https://github.com/microsoft/vscode-remote-release.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/workspaces/browser/workspaces.contribution.ts`
- **Validation:** Manually open a previously unseen folder containing a `.code-workspace` file and a project containing Dev Container configuration; verify each reopen action is discoverable through the chosen dedicated surface without an unsolicited startup toast, remains available after dismissal, and opens the intended workspace or container.
- **Behavior:**

  > When VS Code detects that the opened folder can be reopened as a `.code-workspace` or Dev Container, the option should be discoverable without adding an unsolicited startup notification. The chosen surface should clearly identify the available reopen action, preserve access after the initial discovery moment, and avoid presenting duplicate prompts. Invoking the action must reopen the correct workspace or container, while folders without either configuration remain unchanged.
- **Trace:**

  > On current main, WorkspacesFinderContribution in src/vs/workbench/contrib/workspaces/browser/workspaces.contribution.ts scans the root of a single-folder workspace and calls notificationService.prompt for discovered `.code-workspace` files. Commit 4f3f43190820d687786df37c9bb9b64c735c338b made repeat openings silent, and the current first-open notification is OPTIONAL, so notification pressure was reduced but the central request remains. The core contribution also exposes `workbench.action.openWorkspaceFromEditor`, but only while a workspace file is itself open. The Dev Containers implementation is owned outside this checkout in https://github.com/microsoft/vscode-remote-release, so the plan must establish a shared product pattern before coordinating both implementations. Preserve the existing reopen commands and workspace selection behavior; this issue concerns discovery and presentation, not changing what reopening does.
- **Open decisions:**
  - Which persistent surface should expose reopen recommendations: an Explorer action, the remote indicator, activity/action badges, or another shared workbench surface?
  - Should a first-use notification remain as a fallback, or should the dedicated surface fully replace startup notifications?
  - Must workspace-file and Dev Container detection use one identical interaction pattern, or may they use different placements while following the same notification-free policy?

## Evidence

- **current source:** src/vs/workbench/contrib/workspaces/browser/workspaces.contribution.ts still has WorkspacesFinderContribution call notificationService.prompt when a folder contains one or more `.code-workspace` files; the first-open prompt uses NotificationPriority.OPTIONAL and subsequent openings use NotificationPriority.SILENT.
- **partial mitigation:** Commit 4f3f43190820d687786df37c9bb9b64c735c338b addressed https://github.com/microsoft/vscode/issues/125315 by making the workspace notification silent after the first opening, but it did not replace the initial notification with the dedicated UX requested here.
- **existing alternate action:** The same source file registers `workbench.action.openWorkspaceFromEditor`, but that action appears only when a `.code-workspace` file is opened and therefore does not provide equivalent proactive discovery.
- **unsettled product decision:** The discussion explicitly leaves the replacement surface unresolved among the Explorer, welcome content, remote indicator, and activity/action badges, while maintainers noted that removing the toast could reduce discoverability.
- **related policy issue:** https://github.com/microsoft/vscode/issues/119463 established general notification guidance and closed after documenting it; it does not own or resolve this specific reopen UX.
