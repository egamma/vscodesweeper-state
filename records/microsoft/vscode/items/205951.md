# Issue #205951 — File drop should insert file paths, take 3

[https://github.com/microsoft/vscode/issues/205951](https://github.com/microsoft/vscode/issues/205951)

## Summary

This remains an accepted, confirmed Windows bug in the Backlog. Current main still advertises both a filesystem path and a `file:` URI during external drags, allowing affected external terminals to select the unusable URI representation.

## Change summary

Dragging a file or editor tab from VS Code into some external Windows terminals inserts a `file:` URI instead of a usable filesystem path.

## Best solution

External Windows terminals should receive a filesystem path while URI-aware applications such as browsers continue receiving a file URI, without regressing internal, cross-window, or multi-resource drag and drop.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/dnd.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/browser/parts/editor/editorTabsControl.ts`
- **Validation:** On Windows, drag a local file from both Explorer and an editor tab into Command Prompt, PowerShell, and Git Bash and verify each receives a usable filesystem path; then verify dragging into Chrome still produces a working file URI and existing internal/cross-window drag scenarios remain functional.
- **Behavior:**

  > Dragging a local file or editor tab from VS Code into an external Windows terminal must insert a filesystem path that the shell can use, not a `file:` URI. URI-aware external targets such as browser address bars must retain their working file-URI behavior. Explorer-originated and editor-tab-originated drags must behave consistently, and internal or cross-window drag and drop must remain unchanged.
- **Trace:**

  > Both reported drag sources converge on `fillEditorsDragData` in src/vs/workbench/browser/dnd.ts: Explorer uses it from `FileDragAndDrop.onDragStart` in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts, and editor tabs use it from `EditorTabsControl.doFillResourceDataTransfers` in src/vs/workbench/browser/parts/editor/editorTabsControl.ts. The helper publishes a filesystem path as `text/plain` but also publishes `file:` URI representations through `DownloadURL` and `text/uri-list`; affected Windows terminals select the latter. The URI-list behavior was introduced by commit 63f0154cf5df3e1d35edf808c91aa526af19338b for https://github.com/microsoft/vscode/issues/181373, where Chrome specifically needed a URI, so globally removing or replacing that representation is outside the safe boundary. The plan must determine how VS Code or its Electron/Chromium host can expose the appropriate native Windows file/path flavor while preserving URI-aware targets and existing VS Code-internal transfer types.
