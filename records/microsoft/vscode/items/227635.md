## Evidence

- **Verified open canonical:** https://github.com/microsoft/vscode/issues/150910 is OPEN and reports the same observable symptom: a block cursor over an inline debug glyph changes the glyph into an unexpected character. Its reproduction uses editor.cursorStyle="block", a Node.js breakpoint, and cursor movement over the debug symbol; it also reproduces without installed extensions.
- **Maintainer-confirmed reproduction:** https://github.com/microsoft/vscode/issues/150910#issuecomment-1251292526 explicitly confirms that moving the cursor left and right over the debug symbol readily reproduces the problem and identifies callStackEditorContribution.ts as the decoration source.
- **Corroborating macOS report:** https://github.com/microsoft/vscode/issues/164409 is also OPEN and describes a codicon incorrectly displayed under a block cursor on Darwin arm64. https://github.com/microsoft/vscode/issues/164409#issuecomment-1289354126 confirms the symptom, and https://github.com/microsoft/vscode/issues/164409#issuecomment-1292775592 clarifies that it requires a block cursor without a selection.
- **Current source boundary:** src/vs/workbench/contrib/debug/browser/callStackEditorContribution.ts:64-71 injects the execution glyph U+EB8B with the debug-top-stack-frame-column class. src/vs/workbench/contrib/debug/browser/media/debug.contribution.css:44-56 gives that class the codicon font. In src/vs/editor/browser/viewParts/viewCursors/viewCursor.ts, ViewCursor._prepareRender copies the next grapheme into a block cursor, while _getTokenClassName supplies token classes and render applies the cursor classes rather than the injected glyph's decoration class. This supports the same rendering boundary identified in the canonical discussion; no runtime reproduction was attempted.
- **Scope and close eligibility:** https://github.com/microsoft/vscode/issues/227635 adds VS Code 1.92.2 on Darwin arm64 with an Apple M2, but describes no distinct behavior beyond the canonical debug-glyph defect.
