# Issue #209427 — Explorer range selection (shift + arrow) doesn't include focused item

[https://github.com/microsoft/vscode/issues/209427](https://github.com/microsoft/vscode/issues/209427)

## Summary

The inconsistent range-selection behavior remains on current main, but it is an intentional consequence of VS Code's disjoint focus and selection model rather than a broken implementation. Keep the existing under-discussion issue open because matching conventional keyboard selection requires a cross-cutting UX decision.

## Change summary

Make Shift+Arrow range selection include the initially focused but unselected Explorer item.

## Best solution

Define consistent range-selection semantics for the shared list/tree widgets so the first Shift+Arrow includes the prior focused item when focus and selection are disjoint. Decide whether this applies across workbench lists or only Explorer, and preserve intentional multi-selection behavior elsewhere.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/actions/listCommands.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`
- **Validation:** In a development build, focus an unselected Explorer item and press Shift+Down or Shift+Up repeatedly; verify the original focus and every traversed sibling are selected, then repeat in another multi-select workbench tree to confirm the chosen scope and verify shrinking an existing range remains correct.
- **Behavior:**

  > When an Explorer item has keyboard focus but is not selected, the first Shift+Arrow operation should select both that original item and the newly focused sibling. Repeated Shift+Arrow presses should extend or shrink a contiguous range using the original item as its anchor. Existing Ctrl/Cmd multi-selection and ordinary unmodified arrow navigation must remain intact.
- **Trace:**

  > Explorer enables shared multiple-selection behavior in src/vs/workbench/contrib/files/browser/views/explorerView.ts. The Shift+Arrow commands are registered in src/vs/workbench/browser/actions/listCommands.ts as `list.expandSelectionDown` and `list.expandSelectionUp`; each moves focus before `expandMultiSelection` updates selection, and that helper adds only the destination when the original focus was unselected. This directly produces the reported omission on current main. A maintainer confirmed the focus/selection split is intentional and described broader reunification as substantial in https://github.com/microsoft/vscode/issues/209427#issuecomment-2034631974. Preserve ordinary arrow navigation, Ctrl/Cmd selection, and range shrinking; uncertainty begins at whether the corrected anchor behavior should be shared by every workbench list/tree or scoped to Explorer.
- **Open decisions:**
  - Should an unselected focused item become the range anchor in every multi-select workbench list/tree, or only in the Explorer?
  - When another disjoint selection already exists, should the first Shift+Arrow preserve those selected items while adding the focused range, or replace them with the new contiguous range?

## Evidence

- **current source:** src/vs/workbench/browser/actions/listCommands.ts still implements `list.expandSelectionDown` and `list.expandSelectionUp` by moving focus first and then calling `expandMultiSelection`; when the destination is unselected, that helper appends only the new focus to the selection, omitting the previous focused item.
- **Explorer integration:** src/vs/workbench/contrib/files/browser/views/explorerView.ts enables `multipleSelectionSupport: true`, so Explorer uses the shared list/tree selection commands rather than an Explorer-specific range-selection implementation.
- **maintainer assessment:** A maintainer explains that focus and selection are intentionally disjoint and that re-unifying them is a large undertaking: https://github.com/microsoft/vscode/issues/209427#issuecomment-2034631974.
- **canonical search:** No older open issue with the same reporter-observable Shift+Arrow symptom was found. https://github.com/microsoft/vscode/issues/162788 is related to disjoint focus and selection after deletion, but reports a different interaction and does not satisfy the stronger duplicate bar for this re-reviewed item.
