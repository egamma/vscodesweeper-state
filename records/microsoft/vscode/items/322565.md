Keep open pending confirmation of both startup status and persistence after reboot. Tunnel startup has been substantially rewritten since the report, but the supplied steps and logs suffice to retest; the linked change does not establish that the entire report is resolved.

## Change summary

Compare Remote Tunnel output with `code tunnel status` and `code tunnel service log` before and after reboot.
- **Behavior:**

  > Selecting Install as service for Remote Tunnel Access should finish the startup notification once the tunnel is connected. The installed service should restore remote availability after host reboot without requiring another manual enablement. Validate both behaviors independently, because the original logs show a working tunnel despite incorrect UI status. Preserve the existing in-session fallback and its warning when service installation genuinely fails.
- **Trace:**

  > RemoteTunnelWorkbenchContribution.startTunnel waits for connected or disconnected status before completing its progress notification. RemoteTunnelService now derives that status from machine-readable coordinator events and accepts service mode; its existing test explicitly covers service-mode connection reporting. The maintainer-linked change at https://github.com/microsoft/vscode/pull/330480 replaced obsolete output matching, but its original handler excluded service mode, so that commit alone cannot prove this service-backed report fixed. Persistence involves RemoteTunnelService._storeMode/_restoreMode, authentication reacquisition in RemoteTunnelWorkbenchContribution.initialize, and service installation plus attachment in TunnelProcessCoordinator._reconcile. The unresolved boundary is actual OS-service behavior across reboot, which was not executed during this read-only review. https://github.com/microsoft/vscode/issues/331546 documents a related ownership race, but the reporter's logs do not establish that race as this issue's cause.
