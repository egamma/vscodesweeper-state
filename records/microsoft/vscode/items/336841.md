# Issue #336841 — MCP: initialized notification is not ordered before the first request, breaking stateful Streamable HTTP servers intermittently

[https://github.com/microsoft/vscode/issues/336841](https://github.com/microsoft/vscode/issues/336841)

## Summary

The initialization race is present on current main and can make stateful Streamable HTTP servers fail indefinitely. Keep the issue open while the linked fixing PR is reviewed and corrected.

## Change summary

Ensure the MCP initialized notification is delivered before the first post-handshake request to a stateful Streamable HTTP server.

## Best solution

Review and land a corrected version of https://github.com/microsoft/vscode/pull/336843 that orders the initialized POST before later requests without blocking behind a potentially long-lived initialize SSE response.

## Evidence

- **source trace:** On current main, src/vs/workbench/contrib/mcp/common/mcpServerRequestHandler.ts sends `notifications/initialized` through a void `sendNotification`/`send` path immediately before returning the initialized handler; IMcpMessageTransport.send is also void in src/vs/workbench/contrib/mcp/common/mcpRegistryTypes.ts.
- **race on main:** src/vs/workbench/api/common/extHostMcp.ts serializes McpHTTPHandle.send only while HttpMode.Unknown. The initialize response sets HttpMode.Http and its session ID before later sends, allowing the initialized notification and first real request to execute as concurrent POSTs, each with an asynchronous authentication-header step.
- **confirmed trigger:** The reporter observed stateful servers return HTTP 400 with `Session not initialized` when the first request arrives before `notifications/initialized`, while the same calls always succeed when issued sequentially across macOS and Windows.
- **open fixing PR:** https://github.com/microsoft/vscode/pull/336843 is open, contains `Fixes #336841`, and changes the implicated McpHTTPHandle sequencing path. Its review identifies a remaining deadlock risk when the initialize response is a long-lived SSE stream, so it should be revised and reviewed rather than treating the issue as completed.
