# Issue #336715 — Copilot Agent Host not respecting workspace chat.tools.terminal.autoApprove

[https://github.com/microsoft/vscode/issues/336715](https://github.com/microsoft/vscode/issues/336715)

## Summary

Credible, reporter-confirmed discrepancy: the same workspace-scoped `chat.tools.terminal.autoApprove` rule is honored by the in-editor Chat view's Copilot harness but not by a Copilot session run from the Agents Window, even on the latest 1.138.0 build — worth keeping open for a maintainer to pin down which config-forwarding path the Agents Window session actually goes through.

## Change summary

A workspace-level `chat.tools.terminal.autoApprove` rule in `.vscode/settings.json` auto-approves the matching terminal command from the normal Chat view's Copilot harness, but the same rule is ignored (prompts for permission) when the identical command is run from a session opened in the Agents Window.

## Best solution

Confirm exactly how a Agents-Window-opened session's `AgentHostProtocolClient`/`IConfigurationService` resolves `chat.tools.terminal.autoApprove` (and its `configService.getRootValue(platformRootSchema, AgentHostTerminalAutoApproveRulesConfigKey)` read in `src/vs/platform/agentHost/node/sessionPermissions.ts`) — whether that session's client lacks the workspace-folder resource context that the normal Chat view's client has — and fix the resolution/forwarding path so root config always reflects the workspace-scoped rule regardless of which surface opened the session.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/browser/agentHostProtocolClient.ts`, `src/vs/platform/agentHost/common/agentHostSchema.ts`, `src/vs/platform/agentHost/node/sessionPermissions.ts`, `src/vs/sessions/contrib/providers/remoteAgentHost`
- **Validation:** Manual check: set a `chat.tools.terminal.autoApprove` rule in workspace `.vscode/settings.json`, run the matching command from (a) the normal Chat view Copilot harness and (b) a session opened via the Agents Window against the same workspace — both should auto-approve without a permission prompt.
- **Behavior:**

  > A `chat.tools.terminal.autoApprove` rule defined in a workspace's `.vscode/settings.json` should auto-approve the matching terminal command identically regardless of whether the Copilot session is driven from the in-editor Chat view or from a session opened in the Agents Window. Currently only the Chat view honors it; the Agents Window session still prompts for permission for the same command against the same workspace. Acceptance: running the same auto-approved command from both surfaces against the same workspace produces the same (auto-approved) outcome.
- **Trace:**

  > The browser-side `AgentHostProtocolClient` computes `chat.tools.terminal.autoApprove` via the workspace-aware `getAgentHostTerminalAutoApproveRulesConfig(this._configurationService)` (src/vs/platform/agentHost/common/agentHostSchema.ts:629) and pushes it into the agent host's root config with a `RootConfigChanged` action (src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:2228-2230, fired on connect and on `onDidChangeConfiguration`). The node-side `SessionPermissionManager` only ever reads the already-pushed value via `_configService.getRootValue(platformRootSchema, AgentHostTerminalAutoApproveRulesConfigKey)` (src/vs/platform/agentHost/node/sessionPermissions.ts:405-411, :561) — there's no independent workspace-folder read there, so the whole path hinges on the specific client connection (and its `IConfigurationService`'s resolved resource/workspace context) that backs the Agents-Window-opened session having actually resolved and forwarded the correct workspace-scoped value. The boundary to preserve: do not change the terminal-approval evaluation logic in `commandAutoApprover.ts` itself, and do not alter the existing root-config-forwarding contract for other (non-terminal) keys. Where the uncertainty starts: which concrete `AgentHostProtocolClient` instance/connection backs an Agents-Window-opened session, and whether its `IConfigurationService` resource context differs from the Chat view's — that determination is the first step of the plan.
- **Open decisions:**
  - Does a session opened from the Agents Window connect through a distinct AgentHostProtocolClient/configuration-resource context than the normal Chat view, and if so, why does that context not resolve the workspace-folder-scoped `chat.tools.terminal.autoApprove` value?
  - Is this specific to sessions backed by a remote agent host connector (Dev Containers/SSH/WSL/tunnel), or does it also reproduce with a purely local agent host session opened from the Agents Window?
  - Should the fix live in how the Agents Window resolves/attaches its workspace resource before connecting, or in a gap in the root-config-forwarding logic itself?

## Evidence

- **workspace-aware forwarding path:** src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:2218-2230 explicitly documents `_updateTerminalAutoApproveEnabled`/`_updateTerminalAutoApproveRules` as 'deliberately on the manual, workspace-aware path' reading `chat.tools.terminal.autoApprove` via `configurationService.getValue(...)` (no resource) and pushing it into the agent host's root config via a `RootConfigChanged` action, fired on connect (line 1153-1154) and on `onDidChangeConfiguration` (lines 468-503).
- **node-side consumption is root-only:** src/vs/platform/agentHost/node/sessionPermissions.ts:405-411 and :561 read the rule set only via `_configService.getRootValue(platformRootSchema, AgentHostTerminalAutoApproveRulesConfigKey)` — the value that was pushed by the client above; there is no separate per-session/workspace-folder lookup on the node side, so everything depends on the browser-side client having correctly resolved and forwarded the workspace value for *that* session's connection.
- **reporter re-confirmed on latest build:** Comment from JakopK (2026-09-18T08:10) retested on 1.138.0 and narrowed it precisely: same command auto-approves from the normal Chat view (both 'Local' and 'Copilot' harness) but prompts when run from a session opened in the Agents Window, suggesting the Agents-Window-opened session's client/connection isn't picking up the same workspace-scoped configuration.
