# Issue #336715 — Copilot Agent Host not respecting workspace chat.tools.terminal.autoApprove

[https://github.com/microsoft/vscode/issues/336715](https://github.com/microsoft/vscode/issues/336715)

## Summary

Thanks for the detailed report and follow-up. Two independent reporters on different recent builds (1.138.0 and 1.140.0) confirm that the Agents Window's Copilot harness doesn't honor workspace-level `chat.tools.terminal.autoApprove` the way the classic chat view's Copilot harness does, while user-level settings do work — this is a real, reproducible gap that stays open pending root-cause diagnosis.

## Change summary

Workspace-scoped `chat.tools.terminal.autoApprove` rules are ignored by the Agents Window's Copilot/Agent Host harness even though they are honored by the classic chat view and by user-level settings.

## Best solution

Diagnose why the Agent Host protocol client's `_updateTerminalAutoApproveRules`/`getAgentHostTerminalAutoApproveRulesConfig` (src/vs/platform/agentHost/browser/agentHostProtocolClient.ts, src/vs/platform/agentHost/common/agentHostSchema.ts) resolves a different effective value in the Agents Window context than in the classic chat view, and ensure the forwarded root config reflects the correct workspace/folder-scoped configuration resource for that session.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/browser/agentHostProtocolClient.ts`, `src/vs/platform/agentHost/common/agentHostSchema.ts`, `src/vs/platform/agentHost/node/sessionPermissions.ts`
- **Validation:** A test (or manual check) confirming that `getAgentHostTerminalAutoApproveRulesConfig`/`_updateTerminalAutoApproveRules` forwards the same effective rules for an Agents Window session as `IConfigurationService.getValue` resolves for the corresponding workspace folder in the classic chat view, for a workspace-only (non-user) `chat.tools.terminal.autoApprove` entry.
- **Behavior:**

  > When a workspace's `.vscode/settings.json` sets `chat.tools.terminal.autoApprove` for a command, running that command via the Agents Window's Copilot/Agent Host harness should auto-approve it exactly as the classic chat view does, and exactly as it already does when the same rule is placed in user settings instead. Currently the Agents Window still prompts for permission even though the workspace setting is present. Acceptance: toggling only the workspace-level setting (not user settings) changes Agents Window approval behavior the same way it changes classic chat view behavior.
- **Trace:**

  > The Agent Host forwards terminal auto-approve rules to the host process via `_updateTerminalAutoApproveRules` in src/vs/platform/agentHost/browser/agentHostProtocolClient.ts (line ~2472), which calls `getAgentHostTerminalAutoApproveRulesConfig(this._configurationService)` (src/vs/platform/agentHost/common/agentHostSchema.ts:652) — this calls `configurationService.getValue(...)` with no resource argument. The sibling `_updateTerminalAutoApproveEnabled` just above it carries an explicit comment that this setting is workspace-scoped and 'restricted', and that resolving only the global value would be wrong — strongly suggesting the same class of resource-scoping sensitivity applies to the rules getter. The host side (src/vs/platform/agentHost/node/sessionPermissions.ts:409,557) just reads back whatever root config value it was given, so it is not the place to fix. What's unconfirmed from source alone: whether the Agents Window's underlying `IConfigurationService` instance/resource context differs from the classic chat view's (e.g., no workspace folder resource bound, or bound to the wrong folder for a worktree-backed session) — that's the open diagnostic step. Do not change the host-side consumption path or the schema's declared setting scope; the suspected gap is in what gets computed and forwarded on the client side.

## Evidence

- **config forwarding path:** src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:2472-2474 calls `getAgentHostTerminalAutoApproveRulesConfig(this._configurationService)` with no resource/scope argument, and the sibling `_updateTerminalAutoApproveEnabled` has a comment (lines 2462-2469) explicitly noting the setting is 'restricted and settable per workspace' and that resolving only the global value 'would let a workspace that turned auto-approval off still have it applied' — i.e. this forwarding path is known to be workspace-scope sensitive.
- **host-side consumption:** src/vs/platform/agentHost/node/sessionPermissions.ts:409,557 reads the forwarded value via `this._configService.getRootValue(platformRootSchema, AgentHostTerminalAutoApproveRulesConfigKey)` — purely a readback of whatever the client forwarded, so the defect (if any) is upstream in what gets computed/sent, not in host-side consumption.
- **independent confirmations:** Comment by JakopK (2026-09-18, re-tested on 1.138.0) and comment by pkcakeout (2026-10-06, on 1.140.0) both independently reproduce: 'Local' mode respects workspace autoApprove, 'Copilot'/Agents Window mode does not.
