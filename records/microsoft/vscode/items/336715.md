# Issue #336715 — Copilot Agent Host not respecting workspace chat.tools.terminal.autoApprove

[https://github.com/microsoft/vscode/issues/336715](https://github.com/microsoft/vscode/issues/336715)

## Summary

Thanks for the report. The behavior is consistent across several reporters: the workspace-level `chat.tools.terminal.autoApprove` is honored by the Local harness but not by the Copilot agent host, so commands are prompted for when they shouldn't be. The source suggests why, but I did not confirm it end to end. The report has clear steps and is still open, so it stays open.

## Change summary

Workspace-scoped `chat.tools.terminal.autoApprove` rules are ignored by the Copilot agent host harness (notably in the Agents window), while user-scoped rules work.

## Best solution

Make the agent host's terminal auto-approve rules resolve workspace and folder-scoped settings for the session's working directory, not only the window's own configuration, and re-push them when the session folder or workspace settings change.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/browser/agentHostProtocolClient.ts`, `src/vs/platform/agentHost/common/agentHostSchema.ts`, `src/vs/platform/agentHost/node/sessionPermissions.ts`
- **Validation:** A test in src/vs/platform/agentHost/test/node/sessionPermissions.test.ts: with the rule defined only at workspace or folder scope, a matching terminal command is auto-approved for a session whose working directory is that folder.
- **Behavior:**

  > A `chat.tools.terminal.autoApprove` rule defined in a workspace or folder `.vscode/settings.json` auto-approves matching terminal commands for Copilot agent host sessions working in that folder, as it does for the Local harness. Rules in user settings keep working. Acceptance: with the rule only in the workspace settings, `npm run myNewCommand` runs without a prompt in the Agents window using the Copilot harness.
- **Trace:**

  > The client forwards one effective rules object from its own configuration service (`getAgentHostTerminalAutoApproveRulesConfig`, `agentHostProtocolClient.ts`). It stores it under the root key `terminalAutoApproveRules` (`AgentHostTerminalAutoApproveRulesConfigKey`). The host reads that single root value in `sessionPermissions.ts` for all sessions. Workspace-scoped values for a session's folder are likely not reflected in it, especially in the Agents window where the window workspace is not the session folder. This is not confirmed, so reproduce first. Do not change the managed-policy denial rules (`agentHostManagedSettings.ts`) or the default-rule handling in `normalizeAgentHostTerminalAutoApproveRulesConfig`.
- **Open decisions:**
  - Should the host resolve these rules per session folder, or should the client send a per-session override? This decides whether remote hosts and multi-root sessions honor workspace rules.
  - Should workspace rules from an untrusted workspace be honored for auto-approve? This is a security-relevant default.

## Evidence

- **forwarding path:** src/vs/platform/agentHost/browser/agentHostProtocolClient.ts (around lines 559 and 2659) pushes `getAgentHostTerminalAutoApproveRulesConfig(this._configurationService)` as a single root-level config value, `terminalAutoApproveRules`. This value comes from the client's own configuration service, not from the session's working-directory scope.
- **host consumption:** src/vs/platform/agentHost/node/sessionPermissions.ts (lines 418 and 616) reads that root value for every session. Nothing re-resolves it per session folder, so a folder or workspace `.vscode/settings.json` that the window does not apply would be missed.
- **reporter observations:** On 1.138.0, the chat view works with both the Local and Copilot harness. The Agents window prompts. A user-scoped rule works. A second reporter on 1.140.0 sees the same behavior. This fits a scope-resolution gap, but I did not execute it.
