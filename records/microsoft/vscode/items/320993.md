# Issue #320993 — Agents Window: Custom agents disappear from dropdown after sending a message

[https://github.com/microsoft/vscode/issues/320993](https://github.com/microsoft/vscode/issues/320993)

## Summary

Multiple users, including a team member, confirmed that sending or running an Agents Window session can drop custom agents and other workspace customizations. Current main has substantially revised picker scoping, but no cited change conclusively covers the first-message session transition, so the issue should remain open pending a current-build reproduction.

## Change summary

Keep workspace custom agents available and preserve the selected custom agent when the first Agents Window prompt starts the session.

## Best solution

Reproduce the first-message draft-to-running-session transition on current main and ensure the session resource, workspace context, discovered modes, and selected agent survive that handoff. Add regression coverage that starts with a workspace custom agent selected, commits the first request, and verifies that the same agent remains selected and listed.

- **Behavior:**

  > A workspace custom agent selected before the first Agents Window request remains selected when the draft becomes a running session. The custom agent remains present in the dropdown, and workspace customizations continue to resolve from the selected workspace rather than an `unknown:/` or unrelated context. Default-agent sessions and explicit later agent changes remain unchanged.
- **Trace:**

  > The original and follow-up reports place the failure at or after the first-send session transition, with one team-member observation tying it to loss of folder context and all customization categories. ModePickerModel in src/vs/sessions/contrib/providers/copilotChatSessions/browser/modePicker.ts discovers modes using the current session resource, while CopilotChatSessionsProvider in copilotChatSessionsProvider.ts replaces or commits draft session state during request creation. Commit https://github.com/microsoft/vscode/commit/19b53d232c272d3dbe881eaa66f159a5537ccada later made picker models session-scoped and retained them across toolbar rebuilds, but its tests do not exercise first-send draft replacement. First determine whether current main still loses the resource, workspace, mode observable, or customization discovery during that transition; preserve behavior for explicit agent changes and independent concurrent sessions.

## Evidence

- **confirmed symptom:** The issue provides deterministic first-prompt steps, and https://github.com/microsoft/vscode/issues/320993#issuecomment-4614783467 independently reports that agents, skills, and MCP servers disappear while the session context appears to switch to an invalid folder.
- **additional confirmations:** Later comments report the selected agent reverting on Enter or background-session creation and custom agents becoming unavailable during active sessions, showing that this is not limited to the original reporter's agent files.
- **related report:** https://github.com/microsoft/vscode/issues/324402 reports the same first-prompt loss with logs showing the workspace becoming `unknown:/`, but it was created after this re-reviewed issue and therefore cannot serve as its duplicate canonical.
- **different older issue:** https://github.com/microsoft/vscode/issues/315144 is older, but its observable symptom is opening a second session interrupting the first session's MCP servers and selections, not losing custom agents after the first prompt in the same session.
- **current source:** src/vs/sessions/contrib/providers/copilotChatSessions/browser/modePicker.ts now binds discovered modes to the scoped session resource through ModePickerModel and ScopedModePickerModelCache; src/vs/sessions/contrib/providers/copilotChatSessions/browser/copilotChatSessionsActions.ts consumes that scoped model.
- **later related change:** Commit https://github.com/microsoft/vscode/commit/19b53d232c272d3dbe881eaa66f159a5537ccada added session-scoped picker models and toolbar-rebuild retention tests, but its pull request addresses Automation configuration and does not reference this issue or test the first-message session handoff, so it is insufficient provenance for an implemented-on-main close.
