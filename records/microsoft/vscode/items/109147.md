# Issue #109147 — Dispatching KeyboardEvent on Webview fails to work only on Windows.

[https://github.com/microsoft/vscode/issues/109147](https://github.com/microsoft/vscode/issues/109147)

## Summary

Keep open: forwarded synthetic events without keyCode still reach Windows keybinding resolution without a usable key identity. The 2024 confirmation supplies a working keyCode workaround, not evidence of a core fix; no verified canonical supersedes this report.

## Change summary

Synthetic keyboard events forwarded from nested webview iframes fail to invoke Windows shortcuts when they provide key and code but omit keyCode.

## Best solution

Make the supported webview forwarding path resolve the reported Windows shortcuts from the supplied key identity without requiring extension authors to populate deprecated keyCode. Preserve existing keyboard-layout behavior, explicit keyCode handling, focus requirements, and untrusted-event forwarding controls.

- **Likely files:** `src/vs/workbench/contrib/webview/browser/pre/index.html`, `src/vs/workbench/contrib/webview/browser/webviewElement.ts`, `src/vs/base/browser/keyboardEvent.ts`, `src/vs/workbench/services/keybinding/common/windowsKeyboardMapper.ts`, `src/vs/workbench/contrib/webview/test/browser/webviewElement.test.ts`, `src/vs/workbench/services/keybinding/test/node/windowsKeyboardMapper.test.ts`
- **Validation:** On Windows, run the supplied extension sample and verify that its synthetic Ctrl+N opens an untitled document without keyCode; compare with keyCode: 78. Also verify forwarded Ctrl+S saves a dirty custom editor. Add targeted regression coverage for missing versus explicit keyCode and conflicting key/code under a non-US layout, and retain existing forwarding-control tests.
- **Behavior:**

  > An extension forwards keyboard input from a nested iframe by dispatching a synthetic event containing key, code, and modifiers. On Windows, the report's Ctrl+N does not open a document unless deprecated keyCode is supplied; the thread independently confirms the same dependency for Ctrl+S. The supported forwarding behavior should be consistent across platforms without regressing explicit keyCode events or keyboard-layout handling. Acceptance must cover the original sample, saving, and the agreed fallback semantics on non-US layouts.
- **Trace:**

  > reviveWebviewContentOptions in src/vs/workbench/api/browser/mainThreadWebviews.ts enables synthetic-event forwarding for extensions. forwardKeyEvent in src/vs/workbench/contrib/webview/browser/pre/index.html serializes the event fields, and WebviewElement.handleKeyEvent in src/vs/workbench/contrib/webview/browser/webviewElement.ts redispatches them unchanged after its existing checks. StandardKeyboardEvent derives its logical key from keyCode, and WindowsKeyboardMapper.resolveKeyboardEvent consumes that logical key rather than code; an omitted keyCode therefore becomes Unknown. The July 2024 workaround on https://github.com/microsoft/vscode/issues/109147 matches this source path. The uncertainty is the observable fallback contract when keyCode is absent and key differs from code on non-US layouts. Do not weaken existing forwarding controls, change unrelated iframe clipboard behavior, or conflate this report with https://github.com/microsoft/vscode/issues/129178.
- **Open decisions:**
  - When a forwarded synthetic event omits keyCode and key differs from code because of the keyboard layout, should Windows shortcut resolution follow the logical key or the physical code?

## Evidence

The follow-up reports success after preserving keyCode. The original runnable extension sample likewise omits keyCode.
