# Issue #315964 — VS Code Agents App: Add back the ability to thumbs down or thumbs up prompt responses

[https://github.com/microsoft/vscode/issues/315964](https://github.com/microsoft/vscode/issues/315964)

## Summary

The requested feedback controls remain absent from coding-agent responses on current main, and a maintainer identified them as potentially useful metrics. This accepted Backlog request should remain open while the supported Agents Window providers and feedback destination are defined.

## Change summary

Expose Helpful and Unhelpful response actions in the Agents Window, matching the normal VS Code chat experience.

## Best solution

Reuse the existing chat response-footer actions in the Agents Window for the agreed set of providers, preserving their accessible labels and selected state, and route each vote through the appropriate feedback or telemetry path.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/actions/chatTitleActions.ts`, `src/vs/workbench/contrib/chat/common/chatService/chatServiceTelemetry.ts`, `src/vs/sessions/contrib/chat/browser/chatView.ts`, `src/vs/sessions/contrib/chat/test/browser/chatView.fixture.ts`
- **Validation:** Add a focused menu/action test proving that eligible Agents Window responses expose keyboard-accessible Helpful and Unhelpful actions, selecting either action updates its toggled state, and ineligible providers or responses remain unchanged; also validate the Agents Window chat fixture renders both footer controls.
- **Behavior:**

  > Completed, eligible assistant responses in the Agents Window show Helpful and Unhelpful actions with the same labels, keyboard access, and selected-state feedback as normal VS Code chat. Activating either action records the corresponding vote without disrupting the response or composer. Error, filtered, survey-owned, or otherwise ineligible responses retain their existing behavior. Acceptance should cover visibility, keyboard activation, toggled state, and vote reporting.
- **Trace:**

  > The Agents Window creates the shared ChatWidget in src/vs/sessions/contrib/chat/browser/chatView.ts and does not suppress its footer. The missing controls originate in src/vs/workbench/contrib/chat/browser/actions/chatTitleActions.ts: both ChatMessageFooter contributions require `lockedToCodingAgent.negate()`, while ChatWidget sets that context key for coding-agent sessions. The action implementations already update `IChatResponseViewModel.vote` and call `IChatService.notifyUserAction`; src/vs/workbench/contrib/chat/common/chatService/chatServiceTelemetry.ts already classifies Agent Host votes. Preserve the existing telemetry-feedback setting, error/feedback-survey exclusions, accessible action labels, and behavior in ordinary chat. The uncertainty begins at provider eligibility: the Agents Window can host multiple harnesses, and the issue does not settle whether every harness should receive these controls.
- **Open decisions:**
  - Should Helpful and Unhelpful appear for every interactive Agents Window harness, or only for Copilot-backed and other explicitly feedback-capable providers?

## Evidence

- **current source gap:** src/vs/sessions/contrib/chat/browser/chatView.ts constructs the standard ChatWidget with its response footer enabled, but src/vs/workbench/contrib/chat/browser/actions/chatTitleActions.ts gates both Helpful and Unhelpful with `ChatContextKeys.lockedToCodingAgent.negate()`. ChatWidget sets `lockedToCodingAgent` for coding-agent sessions, so these actions remain hidden in the Agents Window on current main.
- **existing infrastructure:** The existing actions already call `IChatService.notifyUserAction` and update the response vote state. src/vs/workbench/contrib/chat/common/chatService/chatServiceTelemetry.ts records vote direction and distinguishes Agent Host-backed sessions with `isAgentHostSession`, so this is not a request to invent a new response-control system.
