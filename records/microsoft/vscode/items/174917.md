# Issue #174917 — Notebook cells should be resizable

[https://github.com/microsoft/vscode/issues/174917](https://github.com/microsoft/vscode/issues/174917)

## Summary

Keep open: current output settings control truncation and scrolling, but do not provide the requested drag-to-resize interaction. Maintainers have explicitly directed related output-sizing reports here, and the verified related open issues do not replace this request.

## Change summary

Allow users to resize individual notebook cells by dragging their edges rather than adjusting output line-limit settings.

## Best solution

Design a per-cell resizing interaction in the notebook editor that preserves existing scrolling and automatic layout behavior for untouched cells. First settle whether resizing applies to output regions alone or also to cell input editors, and whether chosen sizes persist.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/notebook/browser/notebookEditorWidget.ts`, `src/vs/workbench/contrib/notebook/browser/view/renderers/backLayerWebView.ts`, `src/vs/workbench/contrib/notebook/browser/view/renderers/webviewPreloads.ts`, `src/vs/workbench/contrib/notebook/browser/viewModel/codeCellViewModel.ts`, `extensions/notebook-renderers/src/index.ts`
- **Validation:** After agreeing the scope, open a notebook containing two cells with long outputs, resize one by dragging its boundary, and verify only that cell changes size without changing notebook.output.textLineLimit. Check scrolling, streamed output updates, and scrolling the resized cell out of and back into the viewport; reload and rerun behavior must match the agreed persistence contract. Include a keyboard-accessible equivalent in the acceptance checks.
- **Behavior:**

  > Users should be able to adjust an individual notebook cell's displayed size through direct manipulation instead of changing a global output line limit. Resizing one cell must not resize unrelated cells or alter their output settings. Existing output content, scrolling, and execution behavior should remain usable after resizing. Acceptance must cover long outputs, output updates, viewport recycling, and an accessible alternative to dragging; the exact input/output scope and persistence semantics remain to be agreed.
- **Trace:**

  > The existing output renderer derives scrollability from output metadata or notebook.output.scrolling in extensions/notebook-renderers/src/index.ts, while BackLayerWebView computes the scrollable maximum height from configured line count and line height. Output dimension reports pass through BackLayerWebView to the notebook editor, and CodeCellViewModel.updateOutputHeight participates in cell layout. These paths establish the relevant sizing boundary but do not establish an existing user-controlled resize interaction. Preserve settings-driven defaults and automatic sizing for cells the user has not resized. Maintainers explicitly identify this issue as the output-resizing tracker in https://github.com/microsoft/vscode-jupyter/issues/13308#issuecomment-1856395352. The report says cells generally, while its motivation and related reports focus on outputs; uncertainty starts at that user-visible scope and at whether sizes survive reruns or reloads.
- **Open decisions:**
  - Should dragging resize only the output region, or should notebook cell input editors also support independent resizing?
  - Should a manually selected size survive output replacement, cell re-execution, and notebook reload, or remain temporary view state?
