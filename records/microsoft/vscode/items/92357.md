# Issue #92357 — Settings Sync : Allow for custom backend service end points

[https://github.com/microsoft/vscode/issues/92357](https://github.com/microsoft/vscode/issues/92357)

## Summary

Keep open: Settings Sync still obtains backend endpoints from product configuration rather than a supported user or extension selection mechanism. The request has 76 upvotes and explicit maintainer acceptance; it merits a design session on the custom-provider contract.

## Change summary

Allow built-in Settings Sync to use custom backend services, including self-hosted or alternative storage providers.

## Best solution

Define a supported custom-backend contract and a way to select and authenticate compatible services without modifying product.json. Resolve whether direct Git/Gist storage is part of that contract or requires a provider adapter, while preserving the existing hosted-service experience.

- **Reason:** An extensible Settings Sync backend advances settings fidelity and extension integration without requiring additional storage providers to be bundled.
- **Evidence:** Durable themes: Workbench & core UX includes settings fidelity; Extension ecosystem includes API hygiene. Public value: “The power lives in extensions.”

## Plan brief

- **Likely files:** `src/vs/platform/userDataSync/common/userDataSyncStoreService.ts`, `src/vs/platform/userDataSync/common/userDataSync.ts`, `src/vs/workbench/contrib/userDataSync/browser/userDataSync.ts`, `src/vs/base/common/product.ts`
- **Validation:** The plan should end with an integration check using a compatible local sync server: select it through the supported mechanism without editing product.json, authenticate, sync a setting between two isolated profiles, and verify that the existing hosted-service selection still works.
- **Behavior:**

  > Users need to synchronize through a custom backend without modifying the installed product configuration. The discussion includes compatible self-hosted services as well as Git/Gist storage, which are not necessarily the same capability. Acceptance should demonstrate selection, authentication, and a settings round trip between isolated profiles against a custom service, while preserving the default hosted-service workflow. The supported storage-provider boundary must be agreed before implementation.
- **Trace:**

  > AbstractUserDataSyncStoreManagementService.updateUserDataSyncStore in src/vs/platform/userDataSync/common/userDataSyncStoreService.ts obtains endpoints and authentication providers from productService['configurationSync.store']. UserDataSyncStoreType and the management service's switch contract in src/vs/platform/userDataSync/common/userDataSync.ts support only stable and insiders; selectSettingsSyncService in src/vs/workbench/contrib/userDataSync/browser/userDataSync.ts presents those two choices. UserDataSyncStoreClient speaks a versioned HTTP sync protocol, not Git. This confirms that product-level configurability is not the requested supported customization surface. The discussion at https://github.com/microsoft/vscode/issues/92357 distinguishes backend extensibility from authentication and provides a compatible-server use case; https://github.com/microsoft/vscode/issues/84332 does not resolve that boundary. Preserve existing hosted-service behavior and sync semantics; uncertainty begins at the public provider contract and how users select it.
- **Open decisions:**
  - Should custom backends be selected through a user-configurable compatible-service endpoint, an extension-contributed provider API, or both?
  - Does the supported contract cover only services implementing the existing sync protocol, or also direct Git/Gist storage through provider adapters?
