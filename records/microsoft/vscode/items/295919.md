## Plan brief

- **Likely files:** `src/vs/workbench/contrib/editSessions/browser/editSessionsStorageService.ts`
- **Validation:** With at least two available authentication accounts, enable Cloud Changes with one account and verify that the chosen account is visibly identified after sign-in; restart VS Code and confirm the displayed account still matches the persisted Cloud Changes session preference.
- **Behavior:**

  > After Cloud Changes is enabled, users can determine which account it is using without disabling and re-enabling the feature. The displayed identity must match the persisted Cloud Changes authentication session, including after restart and when multiple accounts are signed in. Settings Sync account presentation and Cloud Changes storage behavior must remain unchanged.
- **Trace:**

  > EditSessionsWorkbenchService in src/vs/workbench/contrib/editSessions/browser/editSessionsStorageService.ts persists CACHED_SESSION_STORAGE_KEY through existingSessionId. getAuthenticationSession resolves that ID to a session, while getAccountPreference/createQuickpickItems expose session.account.label only during initial account selection. Once signed in, registerResetAuthenticationAction contributes only “Turn off Cloud Changes...” to MenuId.AccountsContext, so the selected account label is no longer visible. The maintainer discussion at https://github.com/microsoft/vscode/issues/295919 settles the feature scope as active-account visibility; uncertainty starts at the presentation and interaction contract. Keep the boundary within Cloud Changes and do not alter Settings Sync or global authentication-selection semantics.
- **Open decisions:**
  - Should the active Cloud Changes account be passive identity information, or should the same surface also allow users to switch the account?
