# Issue #326160 — Dead key used as a shortcut or first key of a chord leaves dead-key composition active

[https://github.com/microsoft/vscode/issues/326160](https://github.com/microsoft/vscode/issues/326160)

## Summary

This is a distinct, well-supported keybinding/IME defect that remains relevant on main: the command is consumed successfully, but the native dead-key composition is not cleared. Existing dead-key issues concern shortcuts that fail to dispatch, so none is a canonical duplicate for this behavior.

## Change summary

Using a dead key as a shortcut or the first key of a chord executes the command but leaves composition active, causing the following key to insert composed or extra text.

## Best solution

Ensure a consumed dead-key shortcut cancels its pending native composition for both single-key bindings and chord prefixes without suppressing ordinary dead-key typing or active IME input. The keybinding and editor-input owners should first validate the current Windows behavior and choose the safest boundary for that cancellation.

## Plan brief

- **Likely files:** `src/vs/workbench/services/keybinding/browser/keybindingService.ts`, `src/vs/platform/keybinding/common/abstractKeybindingService.ts`, `src/vs/editor/browser/controller/editContext/textArea/textAreaEditContext.ts`, `src/vs/platform/keybinding/test/common/abstractKeybindingService.test.ts`
- **Validation:** On Windows with the Finnish layout, bind `[BracketRight]` and `[BracketRight] d`: each command must execute without inserting text or affecting the next keypress; unbound `¨ e` must still produce `ë`, and ordinary IME composition must remain functional.
- **Behavior:**

  > A dead key consumed as a complete shortcut or chord prefix must not remain active after the command or chord completes. The shortcut command executes without inserting text, and the next unrelated keypress behaves normally. Unbound dead keys must continue composing characters, and established non-dead-key chord behavior must remain unchanged.
- **Trace:**

  > The report's troubleshooting log reaches `workbench.action.showCommands`, isolating the failure from keybinding resolution. On main, `AbstractKeybindingService._doDispatch` consumes matching key events, while `_expectAnotherChord` calls `IME.disable()` only for chord prefixes. `IMEImpl` in src/vs/base/common/ime.ts has no native cancellation operation; `TextAreaEditContext._ensureReadOnlyAttribute` merely toggles `readonly`, leaving uncertainty about how Windows/Chromium's pending dead-key state should be cleared. The later IME guard in fa6217ecb59b750bf9fbf2644cc006b327f84e7b addresses dispatch during active composition, not this consumed-dead-key transition. Preserve normal dead-key typing, active IME ownership, and terminal/editor keybinding consistency.
- **Open decisions:**
  - Should native dead-key cancellation be owned by the window keybinding listener or by the focused editor input implementation?
  - What browser-safe operation clears pending dead-key state on Windows without blur/focus side effects or disruption to ordinary IME composition?
  - Should cancellation occur immediately when a dead-key chord prefix is consumed, or only when the chord completes or is abandoned?

## Evidence

- **confirmed behavior:** The report provides exact Finnish-layout steps, extension-disabled confirmation, and troubleshooting logs showing that `[BracketRight] d` resolves and invokes `workbench.action.showCommands` while a literal `d` is subsequently inserted without another logged keydown.
- **current source path:** On main, src/vs/platform/keybinding/common/abstractKeybindingService.ts `_doDispatch` prevents the consumed event and invokes the command, but has no dead-key-state cancellation. `_expectAnotherChord` only disables VS Code's IME abstraction; single-key bindings do not enter that path.
- **IME boundary:** src/vs/base/common/ime.ts only tracks an enabled boolean, while src/vs/editor/browser/controller/editContext/textArea/textAreaEditContext.ts responds by toggling the textarea `readonly` attribute. Neither path explicitly clears an already-pending native dead-key composition.
- **no applicable later fix:** Commit fa6217ecb59b750bf9fbf2644cc006b327f84e7b, merged after this report for https://github.com/microsoft/vscode/issues/318977, suppresses keybinding dispatch during an in-flight IME composition but does not cancel dead-key state after a consumed shortcut and does not reference this issue.
- **distinct related reports:** https://github.com/microsoft/vscode/issues/282752 and https://github.com/microsoft/vscode/issues/307895 concern dead-key shortcuts that do not dispatch at all. This report's command dispatches successfully and leaves composition active, so those issues do not absorb its remaining work.
