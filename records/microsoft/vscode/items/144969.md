# Issue #144969 — Linux: Ship RPM packages for EL8/EL9 alongside EL7

[https://github.com/microsoft/vscode/issues/144969](https://github.com/microsoft/vscode/issues/144969)

## Summary

The only candidate fix (merge commit 74ef67b4abbdd8c55ba612f690b832e7ba4598e5) is already on the table as refuted by a prior independent review, and I confirmed why: it only renames the release-tag suffix from `.el7` to `.el8` in resources/linux/rpm/code.spec.template — it does not add any EL8/EL9-specific build or separate repo-indexed packages. No different fix commit exists, so this stays open per the re-citation rule.

## Change summary

Ship real EL8/EL9-targeted RPM builds (or at minimum stop mislabeling packages as `.el7`) instead of a single universal RPM tagged for one RHEL major version.

## Best solution

Current main already dropped the misleading `.el7` tag (now `.el8`, since PR https://github.com/microsoft/vscode/pull/203770 / commit 74ef67b4abbdd8c55ba612f690b832e7ba4598e5), but the deeper ask — genuinely separate, correctly labeled EL8 and EL9 RPM builds/repo paths — remains undone; that requires a maintainer decision on whether to invest in a multi-target RPM build matrix in build/gulpfile.vscode.linux.ts and the Azure release pipeline, which is a release-engineering tradeoff, not a quick code change.

## Plan brief

- **Likely files:** `build/gulpfile.vscode.linux.ts`, `resources/linux/rpm/code.spec.template`, `build/azure-pipelines/linux/steps/product-build-linux-package.yml`
- **Validation:** A rebuilt RPM for each targeted RHEL major version that installs cleanly and reports the correct release tag via `rpm -qi`.
- **Behavior:**

  > Users should be able to install an RPM whose release tag accurately reflects (and is tested against) the RHEL major version they're running, rather than one universal RPM carrying a single hardcoded `.el8` suffix regardless of whether the host is EL8 or EL9.
- **Trace:**

  > The RPM release suffix is a static string in resources/linux/rpm/code.spec.template, substituted via gulp `replace('@@RELEASE@@', linuxPackageRevision.toString())` in build/gulpfile.vscode.linux.ts (line ~202); there is one RPM build target, not a matrix per RHEL version, and the Azure pipeline (build/azure-pipelines/linux/steps/product-build-linux-package.yml) doesn't branch on target distro either. Where uncertainty starts: whether the project wants to invest in actually building/signing separate EL8 and EL9 artifacts (extra CI time/storage) or is content with a single forward-compatible build just relabeled accurately — that tradeoff hasn't been decided by a maintainer.
- **Open decisions:**
  - Is a true multi-target RPM build (separate EL8 and EL9 artifacts, possibly different glibc baselines) worth the added CI/release complexity, or does the project prefer to keep one universal RPM with an accurate-enough label?
  - If separate artifacts are built, should they be published to separately indexed repo paths as the reporter requested, or kept in the same yum repo?

## Evidence

- **current state:** resources/linux/rpm/code.spec.template on main (git HEAD 3a7c8e01) reads `Release: @@RELEASE@@.el8` — confirmed via raw.githubusercontent.com across tags 1.85.0 (`.el7`) through 1.86.0+ (`.el8`), so the rename already landed.
- **fix commit is cosmetic only:** `git show 74ef67b4abbdd8c55ba612f690b832e7ba4598e5` / PR https://github.com/microsoft/vscode/pull/203770 changes exactly one line, `.el7` -> `.el8`, in code.spec.template; no change to the build matrix, CI pipeline, or repo indexing. build/gulpfile.vscode.linux.ts still produces a single universal RPM (`linuxPackageRevision` stamped into one `@@RELEASE@@` value) with no el8/el9 branching.
