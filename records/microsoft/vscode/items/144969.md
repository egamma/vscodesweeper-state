# Issue #144969 — Linux: Ship RPM packages for EL8/EL9 alongside EL7

[https://github.com/microsoft/vscode/issues/144969](https://github.com/microsoft/vscode/issues/144969)

## Summary

The EL7-only naming problem was partly addressed: current RPMs use an .el8 release suffix. Keep this open because that change does not establish the requested shared EL8/EL9 naming or separately indexed distribution packages, and no verified open canonical absorbs the remaining work.

## Change summary

Provide clearly identified RPM support for EL8 and EL9, either through a shared package without the misleading EL7 suffix or through separately indexed distribution-specific packages.

## Best solution

Settle and document the shared RPM's supported Enterprise Linux versions and naming contract. If one package serves EL8 and EL9, make that coverage clear rather than introducing separate builds solely to change filenames; otherwise define the necessary distribution-specific publishing.

- **Validation:** The plan should end with RPM artifact inspection and clean-install/upgrade checks on the supported EL8 and EL9 environments, confirming the agreed release suffix, dependency compatibility, repository selection, and upgrade ordering from existing .el8 packages.
- **Behavior:**

  > Users on supported EL8 and EL9 systems should be able to identify and install the appropriate official RPM without interpreting an obsolete distribution suffix as lack of support. The request accepts either clearly shared packaging or distribution-specific packages with independent repository selection. Acceptance must cover both installation and upgrades from the currently published package naming.
- **Trace:**

  > resources/linux/rpm/code.spec.template declares an `.el8` release suffix. prepareRpmPackage and buildRpmPackage in build/gulpfile.vscode.linux.ts consume one spec template and build per architecture, not per Enterprise Linux version. Commit https://github.com/microsoft/vscode/commit/74ef67b4abbdd8c55ba612f690b832e7ba4598e5 replaced `.el7` with `.el8` to reflect increased glibc requirements, but did not establish neutral naming or separate EL9 packaging. The neutral-name proposal at https://github.com/microsoft/vscode/pull/154453 was closed unmerged. The thread confirms historical cross-version installation, but current EL8/EL9 installation was not executed in this read-only review. Preserve supported dependency baselines and package upgrade ordering; restoring EL7 support is outside this request's remaining scope.
- **Open decisions:**
  - Should supported EL8 and EL9 installations share one RPM with explicitly documented compatibility and agreed naming, or require distribution-specific packages and independently selectable repository indexes?

## Evidence

- **Current packaging capability:** resources/linux/rpm/code.spec.template:3 currently declares `Release: @@RELEASE@@.el8`. In build/gulpfile.vscode.linux.ts, prepareRpmPackage substitutes the package revision into this single template, and buildRpmPackage invokes rpmbuild per architecture; the inspected path has no EL8/EL9 distribution selector.
- **Partial implementation, not a full fix:** https://github.com/microsoft/vscode/commit/74ef67b4abbdd8c55ba612f690b832e7ba4598e5 changed the spec's Release line from `.el7` to `.el8`. Its merged PR, https://github.com/microsoft/vscode/pull/203770, explains that this reflects the raised glibc requirements for version 1.86; it does not implement neutral naming, an EL9 variant, or separate repository indexes.
- **Earlier fix proposal did not land:** https://github.com/microsoft/vscode/pull/154453 explicitly proposed removing `.el7` to represent compatibility with RHEL 7, 8 and 9. GitHub confirms it was closed without merging, so its proposed neutral naming cannot be treated as shipped.
- **Discussion establishes compatibility workaround and demand:** The issue's August 2023 comment reports successful installation of the EL7-labelled package on EL8, and the February 2024 reply reports that package working on RHEL9. These establish a shared-package workaround, not the requested packaging contract. The request has 11 upvotes.
- **Canonical search:** A maintainer consolidated https://github.com/microsoft/vscode/issues/162853 into this issue at https://github.com/microsoft/vscode/issues/162853#issuecomment-1348593614. Searches for open RHEL/RPM, EL7, and RPM-title reports found no verified older canonical for the same request; https://github.com/microsoft/vscode/issues/82425 concerns FIPS digest verification instead.
- **Published installation surface:** https://code.visualstudio.com/docs/setup/linux documents one yum repository for RHEL, Fedora and CentOS-based distributions. This provides an existing shared installation route, but does not itself settle EL8/EL9 package naming or the requested independent indexing.
