# Issue #206864 — Moving cursor on the same word when hovering on package.json dependencies reloads hover

[https://github.com/microsoft/vscode/issues/206864](https://github.com/microsoft/vscode/issues/206864)

## Summary

Keep open: current source still recomputes provider hovers when the mouse moves between positions inside the returned range. A maintainer accepted caching as follow-up work, and the older hover-jumping report was explicitly closed in favor of this issue.

## Change summary

Avoid repeatedly reloading package.json dependency hovers and launching npm lookups while the pointer moves within the same dependency.

## Best solution

Keep dependency hovers stable during movement within their applicable range without repeating expensive metadata lookups. Establish the compatibility and invalidation rules for editor-level reuse before changing behavior for all hover providers.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/hover/browser/contentHoverWidgetWrapper.ts`, `src/vs/editor/contrib/hover/browser/markdownHoverParticipant.ts`, `src/vs/editor/contrib/hover/browser/getHover.ts`, `src/vs/editor/contrib/hover/test/browser/contentHover.test.ts`, `extensions/npm/src/features/jsonContributions.ts`, `extensions/npm/src/features/packageJSONContribution.ts`
- **Validation:** Add a browser hover regression using a delayed counting provider that returns one dependency-sized range; simulate movement across positions inside that range and assert stable displayed content with no redundant provider calls under the agreed reuse contract. Verify that movement outside the range and document edits obtain fresh results. Manually repeat the package.json scenario while observing npm process launches.
- **Behavior:**

  > Moving the pointer slightly within a package.json dependency should not repeatedly reload the same hover or repeat expensive metadata lookups. Moving to a different dependency must still show its correct information, and editing the document must not leave stale results. Acceptance should measure provider invocation counts as well as visible stability, because retaining old content while recomputing does not address the resource cost.
- **Trace:**

  > ContentHoverWidgetWrapper creates mouse-target anchors and starts another operation when their exact ranges differ, even after filtering existing hover parts to retain those applicable at the new position. MarkdownHoverParticipant then reaches getHoverProviderResultsAsAsyncIterable, which invokes providers again; JSONHoverProvider returns a string-literal range but performs its contribution lookup on each call. The desktop npm contribution currently reaches both npm view and npm ls through fetchPackageInfo. The source confirms repeated computation remains possible, but this review did not execute the UI. Keep unrelated hover participants, explicit refresh behavior, and npm registry/configuration semantics outside the initial scope. The older report was consolidated here at https://github.com/microsoft/vscode/issues/168106#issuecomment-3050132935; its preceding discussion identifies compatibility concerns for position-dependent providers. The uncertainty is whether returned ranges can universally authorize result reuse or whether existing position-sensitive providers require a narrower contract.
- **Open decisions:**
  - Should a provider-returned hover range guarantee reusable content across positions while the document is unchanged, or must position-dependent providers retain recomputation within that range?
