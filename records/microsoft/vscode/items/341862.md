# Issue #341862 — [AgentPluginManager] Failed to sync plugin (WSL)

[https://github.com/microsoft/vscode/issues/341862](https://github.com/microsoft/vscode/issues/341862)

## Summary

Keep open: independent WSL and Remote Tunnel reports confirm that host-resident plugins fail to load, including on 1.143.0. Current source retains the implicated client-copy path; neither a fixing commit nor a canonical duplicate was established.

## Change summary

Remote Copilot sessions fail to load host-resident plugins with an access-denied error, repeatedly retry synchronization, and reportedly delay prompts by approximately four minutes.

## Best solution

Preserve plugin filesystem ownership through remote customization discovery and synchronization so host-resident plugins load successfully while client-resident plugins continue to synchronize normally. Investigate retry amplification and measure prompt latency separately rather than assuming the synchronization error explains the entire delay.

## Evidence

- **Confirmed reproduction with minimal plugin:** https://github.com/microsoft/vscode/issues/341862#issuecomment-6276192262 supplies a minimal plugin.json, skills/hello/SKILL.md, and remote chat.pluginLocations configuration. On Windows-to-Linux Remote Tunnels, the skill is missing and synchronization logs repeat Access to file:///home/... is not granted; 7,250 errors were recorded in 31 minutes.
- **Independent cross-platform confirmation:** https://github.com/microsoft/vscode/issues/341862#issuecomment-6255447165 confirms the same failure on macOS-to-Linux arm64 Remote Tunnels. CLI-installed plugins never populate their sync directories, reinstalling does not help, and client-resident plugins synchronize successfully.
- **Persists on newer release:** https://github.com/microsoft/vscode/issues/341862#issuecomment-6320089349 confirms the failure on VS Code 1.143.0 with Windows-to-WSL. All 11 affected sync directories remain empty; client-side customizations work, but host-resident plugin skills, agents, and instructions are absent. The commenter explains why granting a Linux file URI on the Windows client would not provide a valid workaround.
- **Current source supports the routing diagnosis:** At checkout cf19b1ceff2cc6e55b02e2f9bc2ed8dfb779344e, src/vs/platform/agentHost/node/agentPluginManager.ts, AgentPluginManager._syncPlugin, bypasses copying only for AGENT_HOST_FILE_SCHEME. Other URIs, including ordinary file URIs, pass through toAgentClientUri and IFileService.copy. src/vs/platform/agentHost/common/agentClientUri.ts explicitly encodes these as client-side resources. This corroborates the reported failure mechanism but does not establish where remote plugin provenance is first lost.
