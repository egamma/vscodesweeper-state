# Issue #150983 — Table: Support sorting

[https://github.com/microsoft/vscode/issues/150983](https://github.com/microsoft/vscode/issues/150983)

## Summary

The sortable-header capability remains absent from the shared table widget on current main. The request is explicitly accepted for future work and parked in Backlog, with no verified canonical issue owning the widget-level change.

## Change summary

Allow users to sort table rows by clicking column headers, initially motivated by grouping similar entries in the Problems table.

## Best solution

Define sorting as a shared table-widget capability with consistent direction indicators, keyboard and screen-reader interaction, and consumer-provided comparison semantics; then adopt it in the Problems table without changing filtering behavior.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/table/table.ts`, `src/vs/base/browser/ui/table/tableWidget.ts`, `src/vs/base/browser/ui/table/table.css`, `src/vs/workbench/contrib/markers/browser/markersTable.ts`
- **Validation:** Exercise a table with sortable and non-sortable columns: pointer and keyboard activation must cycle through the approved sort states, update the visible and accessible direction indicator, reorder rows stably, and preserve filtering and selection behavior.
- **Behavior:**

  > Sortable table columns should expose a clear header affordance and reorder rows when activated by pointer or keyboard. The current direction must be visible and announced accessibly, while non-sortable columns remain inert. In the Problems table, sorting must coexist with filtering and must not lose the selected problem.
- **Trace:**

  > ITableColumn in src/vs/base/browser/ui/table/table.ts currently describes presentation and row projection but no ordering semantics. ColumnHeader and Table in src/vs/base/browser/ui/table/tableWidget.ts render static header text and expose no header activation or sort-state event. MarkersTable in src/vs/workbench/contrib/markers/browser/markersTable.ts is the motivating consumer and supplies Code, Message, File, and Source columns. No related sorting change appears in the widget history, and the issue has no linked implementation PR. Keep generic sorting policy in the shared widget contract while leaving each consumer responsible for domain-specific comparison values; filtering and column resizing must remain unchanged.
- **Open decisions:**
  - Should activating a sortable header cycle ascending and descending only, or also return to the consumer's original unsorted order?
  - Should the shared widget reorder its row collection itself, or expose sort state for each consumer to apply to its backing model?

## Evidence

- **current source:** src/vs/base/browser/ui/table/table.ts defines ITableColumn with labels, sizing, rendering, and projection only; it has no sortable/comparator contract.
- **header behavior:** ColumnHeader in src/vs/base/browser/ui/table/tableWidget.ts creates a plain .monaco-table-th label and exposes only layout events; no click, keyboard, sort-state, or direction-indicator behavior exists.
- **affected consumer:** src/vs/workbench/contrib/markers/browser/markersTable.ts constructs Code, Message, File, and Source columns through WorkbenchTable, but cannot declare sorting behavior for those headers.
- **maintainer intent:** A maintainer confirmed that the widget did not support clicking a column to sort and said it would be added in the future: https://github.com/microsoft/vscode/issues/150983#issuecomment-1144703704.
- **canonical search:** The older keybindings-specific request https://github.com/microsoft/vscode/issues/22748 is closed and scoped to the keybindings editor, while https://github.com/microsoft/vscode/issues/184399 concerned static extension-contribution tables; neither is an open canonical for shared table-widget sorting.
