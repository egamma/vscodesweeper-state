# Issue #224581 — [json] colorize string literals based on language information coming from schemas

[https://github.com/microsoft/vscode/issues/224581](https://github.com/microsoft/vscode/issues/224581)

## Summary

This accepted Backlog request remains unimplemented and has strong community demand. Current JSON language support has no schema-driven embedded-language or semantic-token path, and the older tokenization overhaul does not own this specific user-visible capability.

## Change summary

Allow JSON schemas to identify string values as embedded languages so values such as package.json scripts receive appropriate syntax coloring.

## Best solution

Define a stable schema annotation contract and a semantic-highlighting path in the built-in JSON language extension, initially validating the design against shell syntax in package.json scripts while preserving ordinary JSON highlighting and avoiding dependencies between built-in extensions.

## Plan brief

- **Likely files:** `extensions/json-language-features/server/src/jsonServer.ts`, `extensions/json-language-features/client/src/jsonClient.ts`, `extensions/json-language-features/server/package.json`, `extensions/json-language-features/server/src/test/semanticTokens.test.ts`
- **Validation:** Add a server-level semantic-token test that applies a schema language annotation to package.json script values and verifies shell tokens are returned only for matching strings, while unannotated strings and unknown language identifiers retain normal JSON highlighting.
- **Behavior:**

  > A supported JSON-schema annotation can identify a string-valued node as containing an embedded language. For package.json scripts, recognized shell constructs receive shell-appropriate coloring while JSON punctuation, quoting, and escaping remain correct. Strings without the annotation, and annotations naming unsupported languages, retain existing JSON highlighting without errors. Token results update after document edits or a relevant schema change.
- **Trace:**

  > The JSON server in extensions/json-language-features/server/src/jsonServer.ts already parses documents and resolves schemas through vscode-json-languageservice, but its initialization capabilities and request handlers contain no semantic-token path. The client in extensions/json-language-features/client/src/jsonClient.ts likewise registers no semantic-token provider; extensions/html-language-features/client/src/htmlClient.ts and extensions/html-language-features/server/src/htmlServer.ts provide nearby prior art for transporting embedded-language semantic tokens, but are reference-only. The built-in shell grammar is declared in extensions/shellscript/package.json, yet the maintainer discussion at https://github.com/microsoft/vscode/issues/224581 explains that TextMate grammars cannot be injected dynamically from runtime schema matches. The boundary is the built-in JSON language feature: preserve ordinary JSON tokenization, avoid a dependency on the shellscript extension, and do not turn this into the broad tokenization overhaul tracked by https://github.com/microsoft/vscode/issues/77140. Uncertainty begins at the public schema keyword, supported language identifier contract, and whether the first deliverable is generic or deliberately limited to package.json scripts.
- **Open decisions:**
  - Should the public schema contract consume the existing x-intellij-language-injection keyword and its language names, define x-vscode-language-injection with VS Code language identifiers, or support both?
  - Should the first supported behavior be generic for annotated JSON string schemas, or intentionally limited to package.json script values until a reusable embedded-language mechanism is proven?
  - What observable fallback should apply when a schema names an installed but unsupported language versus an unknown language identifier?
