# Issue #339559 — Extension host crash-loops on every startup after Microsoft account sign-in (fixed only by clearing microsoft-authentication session state)

[https://github.com/microsoft/vscode/issues/339559](https://github.com/microsoft/vscode/issues/339559)

## Summary

Rigorous, well-evidenced report of a real defect: a corrupted/incompatible persisted MSAL token cache for the built-in `vscode.microsoft-authentication` extension silently kills the extension host on every startup, and the code path that reads that cache has no guard against a bad deserialize. Keeping open for investigation; a maintainer session should confirm the exact MSAL call that throws before fixing.

## Change summary

Extension host crash-loops on every VS Code startup once a Microsoft account session is signed in, and only clearing the microsoft-authentication secret-storage entries (an undocumented SQLite edit) restores stability.

## Best solution

Guard the MSAL token-cache read path in extensions/microsoft-authentication so a corrupted/unparseable cache entry is caught, discarded, and the account re-prompted for sign-in instead of propagating an exception that kills the extension host.

## Plan brief

- **Likely files:** `extensions/microsoft-authentication/src/common/cachePlugin.ts`, `extensions/microsoft-authentication/src/node/cachedPublicClientApplication.ts`, `extensions/microsoft-authentication/src/node/publicClientCache.ts`
- **Validation:** A unit/integration test in the microsoft-authentication extension's test suite that seeds secret storage with intentionally corrupted MSAL cache data, then asserts `CachedPublicClientApplication.create`/`getOrCreate` resolves (or rejects gracefully) without an uncaught exception, and that the account list is reset rather than the process dying.
- **Behavior:**

  > When the persisted MSAL token cache (secret storage key `publicClients-<cloud>` / the per-client `pca:<clientId>` cache blob) is corrupted or fails to parse, the microsoft-authentication extension should recover gracefully — discard the bad cache entry and require re-authentication — instead of throwing an exception that terminates the extension host on every startup. Acceptance: with a deliberately corrupted cache entry, the extension host stays alive, the account is dropped (or a recoverable error is surfaced), and the user is not stuck in a permanent crash-loop without manually editing `state.vscdb`.
- **Trace:**

  > Traced via extensions/microsoft-authentication/src/common/cachePlugin.ts `beforeCacheAccess` → `tokenCacheContext.tokenCache.deserialize(data)` (line 39) with no try/catch around a raw secret-storage value; this is invoked from MSAL's `getAllAccounts()`, called unguarded in `CachedPublicClientApplication._update()` (cachedPublicClientApplication.ts lines 352-362), itself invoked from `publicClientCache.ts` `getOrCreate()` (line 123) outside any try/catch (unlike the manager's own `initialize()` path at lines 69-87, which does catch and delete corrupted data). The actual MSAL-internal throw site lives in `@azure/msal-node`, which isn't in this checkout, so the precise exception type is unconfirmed — a maintainer session should reproduce with a synthetically corrupted cache blob to pin this down before fixing. Boundary: do not change the broker/account-access flows (`accountAccess.ts`) or the migration logic in `publicClientCache.ts`'s `initialize()`, which already has its own corruption-recovery path.
- **Open decisions:**
  - When cache deserialization fails, should the extension silently discard the corrupted entry and re-prompt sign-in, or surface a recoverable error/notification to the user?
  - Should the fix be a defensive try/catch at the cache-read boundary (cachePlugin.ts), or should a deeper validation/versioning scheme be added when writing the cache to prevent corruption in portable/relocated installs in the first place?

## Evidence

- **reporter's controlled experiment:** Table shows exthost crashes 2-3x per launch with the Microsoft session present (both normal and --disable-extensions), and 0 crashes after deleting the `publicClients-AzureCloud` / `accounts-AzureCloud` secret-storage keys — isolates the trigger to the persisted MSAL cache, not any third-party extension.
- **last-logged activity:** exthost.log ends immediately after `ExtensionService#_doActivateExtension vscode.microsoft-authentication ... activationEvent: 'onAuthenticationRequest:microsoft'` with no error, consistent with an unhandled exception terminating the process during cache load.
- **unguarded cache read:** extensions/microsoft-authentication/src/common/cachePlugin.ts `beforeCacheAccess` (lines 35-41) calls `tokenCacheContext.tokenCache.deserialize(data)` on raw secret-storage data with no try/catch; this runs during `CachedPublicClientApplication._update()` -> `this._pca.getAllAccounts()`, which is invoked unguarded from `publicClientCache.ts` `getOrCreate()` (line 123) outside the try/catch that only covers the manager's own `initialize()` path.
- **unhandled-rejection handling:** src/vs/workbench/api/node/extensionHostProcess.ts (line 403) logs unhandled promise rejections rather than crashing, so the exact failure mode (sync throw vs. something else) still needs confirmation from a maintainer session or a corrupted-cache repro, hence keep-open with `plan`, not `implement`.
