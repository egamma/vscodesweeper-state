- **Behavior:**

  > A Windows portable installation reportedly enters an extension-host crash loop whenever its persisted Microsoft session is restored, even with third-party extensions disabled. Startup must remain stable with that state present; unusable authentication state should produce a recoverable authentication failure rather than repeatedly terminating the process. Valid sessions must continue to restore normally. Acceptance requires reproducing the original failure on the affected environment and showing stable repeated launches with the same triggering state afterward.
- **Trace:**

  > Activation in extensions/microsoft-authentication/src/extension.ts awaits MsalAuthProvider.create, which first creates CachedPublicClientApplicationManager in src/node/authProvider.ts. The manager restores the persisted publicClients-AzureCloud client-ID list and creates CachedPublicClientApplication instances in src/node/publicClientCache.ts. Their constructor enables NativeBrokerPlugin unless the existing msal-no-broker setting is selected, and initialization invokes _update/getAllAccounts in src/node/cachedPublicClientApplication.ts; token-cache deserialization lives in src/common/cachePlugin.ts. The manager already handles some JavaScript restoration failures, and source inspection did not establish which operation silently terminates the process. The checkout predates the report, so the session must first reproduce on a current Windows build and distinguish cache restoration from native-broker or other native failures. https://github.com/microsoft/vscode/issues/309056 supplies a broker-isolation diagnostic, not a proven duplicate. Keep recovery confined to affected VS Code-owned authentication state, preserve valid sessions, and never publish the reporter's token-bearing database.

## Evidence

- **Controlled reproduction evidence:** https://github.com/microsoft/vscode/issues/339559 reports 2–3 startup crashes with persisted Microsoft session state, three crashes with --disable-extensions and no third-party activations, and stable startup after removing VS Code-owned authentication state. The initial sign-in was observed once; the report explicitly distinguishes that from the repeated state-dependent experiments.
- **Restoration path:** extensions/microsoft-authentication/src/extension.ts activate calls MsalAuthProvider.create; src/node/authProvider.ts creates CachedPublicClientApplicationManager before registering the authentication provider. src/node/publicClientCache.ts initialize reads persisted client IDs and recreates their public-client applications.
- **Cache interpretation and diagnostic boundary:** In extensions/microsoft-authentication/src/node/publicClientCache.ts, publicClients-AzureCloud stores a JSON list of client IDs, not the token cache itself. src/node/cachedPublicClientApplication.ts uses pca:<clientId> for token-cache storage, constructs NativeBrokerPlugin by default, and initializes accounts through _update/getAllAccounts. src/common/cachePlugin.ts deserializes persisted token-cache data. These paths explain why clearing restoration metadata could avoid activation-time work, but do not prove corrupted tokens or a native-broker defect.
- **Existing error handling:** extensions/microsoft-authentication/src/node/publicClientCache.ts initialize catches failure reading the client list and logs rejected PCA initialization through Promise.allSettled. A silent native process termination would not be explained or recovered by those JavaScript handlers; no conclusive fatal path was established from the inspected source.
