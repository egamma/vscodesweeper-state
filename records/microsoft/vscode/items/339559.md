# Issue #339559 — Extension host crash-loops on every startup after Microsoft account sign-in (fixed only by clearing microsoft-authentication session state)

[https://github.com/microsoft/vscode/issues/339559](https://github.com/microsoft/vscode/issues/339559)

## Summary

Fresh, very thorough single report (0 days old, no maintainer or independent confirmation yet) of the extension host silently crash-looping every startup once a Microsoft account session is persisted; the reporter's controlled A/B experiments (session present vs. deleted, with `--disable-extensions`) are a credible confirmed repro, but the exact failure point (native broker addon vs. unguarded MSAL cache deserialize) hasn't been independently traced, so this stays open for routing/diagnosis rather than closing.

## Change summary

A persisted Microsoft account session in the MSAL token cache silently crashes (not just errors) the extension host on every VS Code startup, with no recoverable error path.

## Best solution

Harden the built-in microsoft-authentication extension's cache restore path (SecretStorageCachePlugin.beforeCacheAccess / NativeBrokerPlugin init in cachedPublicClientApplication.ts) so a corrupted or broker-incompatible persisted session is caught and discarded with a re-auth prompt instead of silently killing the extension host process.

## Plan brief

- **Likely files:** `extensions/microsoft-authentication/src/common/cachePlugin.ts`, `extensions/microsoft-authentication/src/node/cachedPublicClientApplication.ts`, `extensions/microsoft-authentication/src/node/publicClientCache.ts`
- **Validation:** Reproduce with a corrupted/incompatible persisted MSAL cache blob (or the native broker enabled on Windows with a stale session) and confirm the extension host no longer terminates — instead the auth provider logs a recoverable error and discards the bad cache entry.
- **Behavior:**

  > A corrupted or broker-incompatible persisted Microsoft account session must never crash the extension host. On startup, if the cached MSAL token data can't be restored, the auth extension should log the failure, discard the bad cache entry, and let the user re-authenticate — the extension host must keep running in every case.
- **Trace:**

  > Reporter traces every crash to the activation of `vscode.microsoft-authentication` (`onAuthenticationRequest:microsoft`), with the exthost log ending abruptly right after that line and no JS error, OOM, or WER event — consistent with either an unguarded exception during `SecretStorageCachePlugin.beforeCacheAccess`'s `tokenCache.deserialize(data)` (extensions/microsoft-authentication/src/common/cachePlugin.ts, no try/catch) or a native crash in `NativeBrokerPlugin` from @azure/msal-node-extensions~5.3.2, constructed in `getNativeBrokerOptions`/`CachedPublicClientApplication` constructor (extensions/microsoft-authentication/src/node/cachedPublicClientApplication.ts) whenever the broker is enabled on Windows. Deleting the two `vscode.microsoft-authentication` secret-storage keys (the MSAL cache) reliably stops the crash loop. Where the uncertainty starts: which of the two failure points is the actual crash site, and whether it reproduces outside this reporter's portable/Scoop + C# Dev Kit setup — neither has been confirmed from source or in a live session.
- **Open decisions:**
  - Is the crash in the JS cache-deserialize path or in the native broker addon, and does it reproduce with a generic (non-Scoop, non-C#-Dev-Kit) Microsoft sign-in on Windows?
  - When a persisted session can't be restored, should the extension silently discard it and re-prompt for sign-in, or surface a notification to the user first?

## Evidence

- **no guard on cache deserialize:** extensions/microsoft-authentication/src/common/cachePlugin.ts `beforeCacheAccess` calls `tokenCacheContext.tokenCache.deserialize(data)` directly with no try/catch around a value read straight from secret storage — a malformed/corrupted cache blob is not defended against.
- **native broker is in the activation path:** extensions/microsoft-authentication/src/node/cachedPublicClientApplication.ts constructs `NativeBrokerPlugin()` from @azure/msal-node-extensions (~5.3.2) on every CachedPublicClientApplication creation during `onAuthenticationRequest:microsoft` activation on Windows unless the user set `microsoft-authentication.implementation` to `msal-no-broker` — a native-addon fault there would explain a silent process death with zero JS stack trace, matching the reporter's logs.
- **reporter's controlled experiments:** Issue body: 2–3 crashes per launch with the Microsoft session present (reproduces even under `code --disable-extensions`, with the built-in auth extension still enabled and zero third-party activations logged), 0 crashes after deleting the `vscode.microsoft-authentication` secret-storage keys — a credible, repeatable reproduction even without a second commenter confirming it.
