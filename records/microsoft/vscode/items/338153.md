# Issue #338153 — Fix and re-enable flaky Windows Codex session changeset aggregation E2E test

[https://github.com/microsoft/vscode/issues/338153](https://github.com/microsoft/vscode/issues/338153)

## Summary

Legitimate, well-evidenced flake-tracking issue: 6 CI failures across 6 unrelated branches, all Windows/Codex, with a quarantine already merged (commit 682c0f7d) and an owner assigned. The underlying race in changeset aggregation is not yet diagnosed, so this correctly stays open until fixed and re-enabled.

## Change summary

On Windows, the Codex Agent Host E2E test asserting that session-level changesets aggregate edits from both the default chat and a peer chat sometimes fails because the peer chat's edit hasn't been aggregated within the retry window (100 retries x 100ms).

## Best solution

Diagnose why session changeset aggregation is slower/racier for Codex on Windows (likely file-watcher or aggregation-timing skew in src/vs/platform/agentHost/node/agentHostChangesetCoordinator.ts / agentHostChangesetFileMonitorCoordinator.ts), then either fix the missing synchronization or extend the retry budget, and flip providerChangesetAggregationEnabled back on in changesetSuite.ts once several clean Windows runs confirm it.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentHostChangesetCoordinator.ts`, `src/vs/platform/agentHost/node/agentHostChangesetFileMonitorCoordinator.ts`, `src/vs/platform/agentHost/test/node/e2e/suites/changesetSuite.ts`
- **Validation:** Re-enable the quarantined 'session changeset aggregates provider edits from default and peer chats' test on Windows/Codex (flip providerChangesetAggregationEnabled) and run it repeatedly via scripts\test-integration.bat with strict replay until confirmed stable, per the issue's reproduction steps.
- **Behavior:**

  > On Windows with the Codex provider, after a peer chat completes a file-creating turn, the session-level changeset (subscribed via buildSessionChangesetUri) should aggregate both the default chat's and the peer chat's file edits within a bounded time. Currently this sometimes fails to include the peer chat's edit before the test's retry budget (100 x 100ms) is exhausted, even though a same-run retry of the identical test passes. The fix should make the aggregation observably converge reliably within the existing retry budget (or the coordinator should be sped up/synchronized so it does), without changing behavior on other platforms/providers.
- **Trace:**

  > The failing assertion is in src/vs/platform/agentHost/test/node/e2e/suites/changesetSuite.ts around lines 1678-1691, which polls changesetState(sessionChangeset) expecting both 'default-provider.txt' and 'peer-provider.txt' to appear. The quarantine gate at lines 1642-1647 (added in commit 682c0f7d) disables this specifically for provider==='codex' && isWindows, citing this issue. The likely root cause lives in the session changeset aggregation path — src/vs/platform/agentHost/node/agentHostChangesetCoordinator.ts (aggregate-counts/changes computation) and agentHostChangesetFileMonitorCoordinator.ts (file-monitor-driven updates) — where Windows filesystem-event timing or an extra coordination step for the Codex provider likely introduces a race not present on other OS/provider combinations. No fix has landed yet; do not change other providers' or macOS/Linux's aggregation behavior, and do not simply widen the test's retry budget without understanding why aggregation is slow on this path.
