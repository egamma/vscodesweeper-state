# Issue #275616 — Keystrokes for GitHub Copilot "Continue to iterate" prompt Continue/Pause options.

[https://github.com/microsoft/vscode/issues/275616](https://github.com/microsoft/vscode/issues/275616)

## Summary

The keyboard-accessibility gap remains on current main: the iteration-limit prompt is a generic confirmation with clickable buttons but no scoped accelerator commands. A maintainer explicitly confirmed that the existing confirmation keybindings should work here, and the On Deck milestone preserves the request despite limited community reactions.

## Change summary

Provide discoverable keyboard shortcuts for the Continue and Pause choices in Copilot's "Continue to iterate?" prompt.

## Best solution

Make pending generic chat confirmations expose configurable primary and secondary actions, with the iteration-limit prompt using the established confirmation shortcuts and showing their resolved bindings in tooltips and chat accessibility help. The scoped shortcuts must take precedence over unrelated chat actions such as accepting all edits.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatConfirmationContentPart.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatToolActions.ts`, `src/vs/workbench/contrib/chat/common/actions/chatContextKeys.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatAccessibilityHelp.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/chatListRenderer.test.ts`
- **Validation:** Add a targeted chat widget/action test that renders an unused generic confirmation, invokes the configured primary and secondary commands, and verifies accepted versus rejected confirmation data; also verify the resolved shortcuts appear in button tooltips and accessibility help.
- **Behavior:**

  > While the "Continue to iterate?" confirmation is pending, users can select Continue and Pause without moving focus from the chat input. Ctrl/Cmd+Enter performs Continue, and the corresponding configurable secondary confirmation shortcut performs Pause; both buttons expose their resolved shortcuts for discovery. These shortcuts are active only while the relevant confirmation is pending, and Ctrl/Cmd+Enter must not accept all edited files in that state.
- **Trace:**

  > The Copilot tool loop emits this UI as a generic `stream.confirmation` in extensions/copilot/src/extension/intents/node/toolCallingLoop.ts. Core renders that response in `ChatConfirmationContentPart`, where primary and secondary button clicks send accepted or rejected confirmation data, but no pending-generic-confirmation context key or command reaches that path. The existing actions in chatToolActions.ts are scoped to `chatHasToolConfirmation` and operate only on tool invocations, while chatAccessibilityHelp.ts documents only those tool actions. Preserve the existing accepted/rejected request semantics and unrelated edit-accept behavior; the unresolved boundary is whether generic confirmations extend the existing tool-command contract or receive separate commands. Related discussion: https://github.com/microsoft/vscode/issues/273315.
- **Open decisions:**
  - Should the existing Accept/Skip Tool Confirmation command IDs and user keybindings be broadened to all generic chat confirmations, or should generic primary/secondary confirmations expose separate configurable commands?
  - Should the accelerators apply to every pending generic confirmation's primary and secondary choices, or only to the agent iteration-limit prompt?

## Evidence

- **missing accelerator path:** src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatConfirmationContentPart.ts maps generic confirmation buttons only to widget click callbacks and does not bind a confirmation context key or command. src/vs/workbench/contrib/chat/common/actions/chatContextKeys.ts defines `chatHasToolConfirmation` but no equivalent pending-generic-confirmation key.
