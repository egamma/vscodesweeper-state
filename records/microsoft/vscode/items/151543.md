# Issue #151543 — Read-only --extensions-dir break remote extension installation

[https://github.com/microsoft/vscode/issues/151543](https://github.com/microsoft/vscode/issues/151543)

## Summary

The bug remains present on current main: local extension files are archived with their read-only modes and extracted with those same modes on the remote, leaving the remote installation unable to modify its own files. The issue was deliberately reopened and classified as a low-hanging bug after renewed community interest.

## Change summary

Installing a local extension from a read-only `--extensions-dir` onto a remote host preserves read-only permissions and can fail when VS Code updates the remote copy.

## Best solution

Make locally packaged extensions writable by their owner after transfer to a writable remote extension directory while preserving required executable bits. Cover the archive/extraction behavior with a permission-focused unit test so ordinary VSIX handling remains unchanged.

- **Behavior:**

  > When VS Code transfers a locally installed extension to a remote extension directory, read-only permissions inherited from the local package manager must not prevent VS Code or the extension from updating the remote copy. Required executable permissions must remain intact. Acceptance requires a read-only source file to extract as owner-writable on the remote side, while existing archive and extraction behavior for ordinary callers remains unchanged.
- **Trace:**

  > ExtensionManagementService.zip in src/vs/platform/extensionManagement/node/extensionManagementService.ts gathers files through collectFiles and sends their local paths to the generic zip helper. In src/vs/base/node/zip.ts, zip uses yazl.addFile without a mode override; extraction then reads externalFileAttributes through modeFromEntry and creates the destination with that mode in extractEntry. This conclusively carries a Nix store file's read-only mode into the writable remote extension tree. The closed https://github.com/microsoft/vscode/pull/242256 is an implementation lead, not an active competing PR. Keep the boundary to extension-transfer archives: do not globally discard executable bits or change extraction semantics for unrelated archives.

## Evidence

- **current source path:** In src/vs/platform/extensionManagement/node/extensionManagementService.ts, ExtensionManagementService.zip calls collectFiles; collectFiles returns each source file as an IFile with its localPath but no mode override. In src/vs/base/node/zip.ts, zip passes that local path to yazl's addFile, so the source mode is recorded in the archive.
- **permission restoration:** src/vs/base/node/zip.ts derives each extracted file's mode from entry.externalFileAttributes in modeFromEntry and passes it to createWriteStream in extractEntry. A read-only local file therefore becomes a read-only remote file.
- **confirmed reproduction:** https://github.com/microsoft/vscode/issues/151543#issuecomment-2676076948 reports a 2025 reproduction using Nix-managed read-only extensions and provides a non-Nix chmod/symlink reproduction path.
- **maintainer direction:** The timeline shows that on 2026-01-06 the prior under-discussion/wont-fix disposition was removed, the issue was relabeled bug and team-low-hanging, restored to Backlog, and reopened; https://github.com/microsoft/vscode/issues/151543#issuecomment-3715093540 cites community interest.
- **closed implementation lead:** https://github.com/microsoft/vscode/pull/242256 proposed carrying an explicit writable mode through IFile and zip creation, but it was closed without merging while the issue was still under discussion. Current main does not contain that mode override.
