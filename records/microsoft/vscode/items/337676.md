# Issue #337676 — Setting or memory for the default agent harness in the main window (Welcome page / chat panel always start on Copilot)

[https://github.com/microsoft/vscode/issues/337676](https://github.com/microsoft/vscode/issues/337676)

## Summary

Genuine gap: the main window chat (Welcome page / chat panel) has no equivalent to the Agents window's last-used-harness persistence, so users on a non-default harness (e.g. Claude) get reset to Copilot every new chat/restart. Worth keeping open as a feature request; needs a maintainer decision on the mechanism (setting vs. remembered state) before implementation.

## Change summary

Let users choose or have VS Code remember which agent harness (Copilot, Claude, Codex, etc.) new chats start with in the main window, instead of always defaulting to Copilot.

## Best solution

Add main-window persistence analogous to `sessions.quickChat.lastUsedSessionType` (or a `chat.defaultHarness` setting) so the chat panel/Welcome page remembers the last harness used, mirroring `SessionsManagementService._defaultQuickChatSessionType` in src/vs/sessions/services/sessions/browser/sessionsManagementService.ts.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/customizationHarnessService.ts`, `src/vs/workbench/contrib/chat/common/constants.ts`, `src/vs/sessions/services/sessions/browser/sessionsManagementService.ts`
- **Validation:** A test asserting that creating a new main-window chat after switching harness and restarting picks the previously used harness (or the configured default), mirroring the existing quick-chat persistence test pattern.
- **Behavior:**

  > New chats opened from the Welcome page, chat panel, or chat editor in the main window should start on the harness the user last used (or an explicitly configured default), not always reset to Copilot after a restart or new window. Switching harness via the Local picker should persist across sessions the same way `sessions.quickChat.lastUsedSessionType` persists for the Agents window's quick chats.
- **Trace:**

  > The active harness for a chat session is derived in customizationHarnessService.ts (`_activeHarness = derived(..., getChatSessionType(this._activeSessionResource.read(reader)))`), which reads off the session resource URI rather than any persisted preference. The Agents window has a working precedent: SessionsManagementService in src/vs/sessions/services/sessions/browser/sessionsManagementService.ts stores the last-used session type under `sessions.quickChat.lastUsedSessionType` (StorageScope.PROFILE) and falls back to the first available session type. The main workbench chat (src/vs/workbench/contrib/chat/...) has no equivalent read/write of a persisted default harness — `chat.defaultToCopilotHarness` only distinguishes local vs. agent-host Copilot, not an arbitrary harness choice. Boundary: do not change the Agents window's existing quick-chat persistence or the agent-host enablement logic; the new mechanism is scoped to how the main window picks a harness for a brand-new session.
- **Open decisions:**
  - Should this be an explicit setting (`chat.defaultHarness` with fixed values) or remembered last-used state (like the Agents window), or both?
  - Should users be able to hide/remove Copilot entirely from the harness picker, as the second reporter requests, or only reorder the default?
  - Does the persisted/default harness apply uniformly to Welcome page, chat panel, and chat editor, or can they differ?

## Evidence

- **no main-window persistence:** src/vs/sessions/services/sessions/browser/sessionsManagementService.ts defines LAST_USED_QUICK_CHAT_SESSION_TYPE_STORAGE_KEY ('sessions.quickChat.lastUsedSessionType') and `_defaultQuickChatSessionType()`, which remembers the last harness for Agents-window quick chats — no analogous storage/service exists for the main workbench chat panel or Welcome page.
- **existing setting scope:** src/vs/workbench/contrib/chat/common/constants.ts defines `DefaultToCopilotHarness = 'chat.defaultToCopilotHarness'`, which only toggles between the local harness and the Copilot SDK agent-host harness — it does not pick among arbitrary harnesses (Claude, Codex, etc.) as requested.
- **corroborating report:** A second reporter (aseiger) independently describes the same symptom in the main window and asks for persistence or the ability to hide Copilot from the picker.
