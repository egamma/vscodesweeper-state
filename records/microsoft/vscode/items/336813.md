# Issue #336813 — Need Language Model API available in vscode.dev

[https://github.com/microsoft/vscode/issues/336813](https://github.com/microsoft/vscode/issues/336813)

## Summary

A real web-extension capability gap remains: the Language Model API bridge exists in the web workbench, but the built-in Copilot provider is registered only by the Node extension-host contribution. This team-authored request should remain open while the supported web model and authentication contract is designed.

## Change summary

Make language models available to extensions running in vscode.dev, or establish and document the supported alternative.

## Best solution

Expose a supported `vscode.lm.selectChatModels` experience to web extensions by making an authenticated model provider available in the web extension host, with clearly defined model availability and embedding scope. If service or security constraints require a smaller web contract, document that contract and the supported alternative for extension authors.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/extension/vscode-worker/contributions.ts`, `extensions/copilot/src/extension/extension/vscode-worker/services.ts`, `extensions/copilot/src/extension/conversation/vscode-node/languageModelAccess.ts`, `src/vs/workbench/api/browser/mainThreadLanguageModels.ts`
- **Validation:** Exercise a web extension-host scenario in vscode.dev where an authenticated test extension calls `vscode.lm.selectChatModels({ vendor: 'copilot' })`, receives the intended model inventory, sends a request, and consumes its streamed response; also confirm the existing desktop flow remains unchanged.
- **Behavior:**

  > An eligible extension running in vscode.dev can use the stable Language Model API to discover an intended set of models and send a streaming request after the required authentication or consent flow. Empty results and unavailable entitlements remain graceful and documented. Desktop model discovery and request behavior must remain unchanged.
- **Trace:**

  > The web workbench already loads MainThreadLanguageModels through src/vs/workbench/api/browser/extensionHost.contribution.ts, so calls from a web extension can reach ILanguageModelsService. The missing provider is downstream: LanguageModelAccess registers the `copilot` provider from extensions/copilot/src/extension/extension/vscode-node/contributions.ts, but the web-worker contribution list in extensions/copilot/src/extension/extension/vscode-worker/contributions.ts does not include an equivalent. The current provider and its dependencies live under vscode-node, while vscode-worker/services.ts registers only common services, so the trace becomes cross-runtime at provider authentication and endpoint access. Keep the stable desktop API behavior and third-party extension authorization semantics unchanged. Related issue: https://github.com/microsoft/vscode/issues/336813.
- **Open decisions:**
  - Should vscode.dev expose the same Copilot model inventory and authorization behavior as desktop, or an explicitly limited web-compatible subset?
  - Is the supported contract intended for vscode.dev only, or for every embedding that hosts VS Code's web extension host?
