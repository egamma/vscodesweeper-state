# Issue #52844 — Safe File Delete

[https://github.com/microsoft/vscode/issues/52844](https://github.com/microsoft/vscode/issues/52844)

## Summary

Keep open: current deletion confirmations do not check file usages, and the existing Find File References command does not provide the requested pre-deletion warning. This accepted Backlog request has 28 upvotes; the related reference-provider proposal is supporting infrastructure, not a duplicate.

## Change summary

Offer an optional usage check, including comments, strings, or text occurrences, that warns before deleting a referenced file.

## Best solution

Provide an opt-in, usage-aware file deletion workflow that presents discovered references before committing the deletion. Coordinate with the file-reference API proposal while settling the user-facing activation and search-coverage contract.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/fileActions.ts`, `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `src/vs/workbench/api/browser/mainThreadFileSystemEventService.ts`, `src/vscode-dts/vscode.d.ts`, `extensions/typescript-language-features/src/languageFeatures/fileReferences.ts`
- **Validation:** After agreeing the interaction contract, exercise a workspace containing a target file, an importing file, and comments/string literals mentioning the target. Invoke the safe-delete workflow with each supported search option, verify matching usages produce a warning before deletion, verify cancelling preserves the target, and verify explicitly proceeding deletes it. Check an unreferenced target and ensure ordinary deletion retains its existing behavior when the feature is not enabled.
- **Behavior:**

  > Users can request a usage check before deleting a file, with control over the requested comments/string and text-occurrence search modes. Found usages must be presented before deletion, with an opportunity to cancel and leave the file intact. Existing confirmation and recovery mechanisms do not satisfy this requirement because they do not inspect usages. Acceptance must cover referenced and unreferenced files, cancelling and proceeding, and the agreed behavior when language-aware reference discovery is unavailable.
- **Trace:**

  > deleteFiles in src/vs/workbench/contrib/files/browser/fileActions.ts performs dirty/read-only checks and ordinary confirmation before applying ResourceFileEdit deletions; no usage-discovery step exists there. explorer.confirmDelete in files.contribution.ts controls only the ordinary confirmation. FileReferencesCommand in extensions/typescript-language-features/src/languageFeatures/fileReferences.ts already exposes JS/TS file references, but only as a standalone command. FileWillDeleteEvent and the participant implementation in mainThreadFileSystemEventService.ts support additional edits, not an established usage-warning approval contract. https://github.com/microsoft/vscode/issues/134405 proposes shared file-reference discovery and names this request as a consumer; https://github.com/microsoft/vscode/issues/66162 concerns discovery rather than deletion. Preserve existing ordinary deletion, trash, undo, dirty-file protection, and additional-edit semantics unless the maintainer explicitly approves a behavior change. The uncertainty starts at how users activate safe deletion and what coverage is promised across languages and textual matches.
- **Open decisions:**
  - Should safe deletion be a separate opt-in action, or an optional mode of the existing Delete action?
  - What usage coverage must the initial feature guarantee: language-provider references, configurable textual matches, or both, and what should users see when language-aware discovery is unavailable?

## Evidence

- **Existing deletion behavior:** src/vs/workbench/contrib/files/browser/fileActions.ts, deleteFiles, checks unsaved changes and read-only protection, presents trash/permanent-deletion confirmation, then applies ResourceFileEdit operations. That path does not search usages or offer comments/strings/text-occurrence checks.
- **Existing setting is not coverage:** src/vs/workbench/contrib/files/browser/files.contribution.ts registers explorer.confirmDelete as a boolean controlling ordinary deletion confirmation. It does not make confirmation dependent on discovered references; explorer.enableUndo provides recovery rather than usage analysis.
- **Existing reference command is a partial workaround:** extensions/typescript-language-features/src/languageFeatures/fileReferences.ts implements typescript.findAllFileReferences by requesting tsserver fileReferences and displaying locations through editor.action.showReferences. It requires a supported JS/TS document and is not connected to deletion or configurable text-occurrence checking. The related https://github.com/microsoft/TypeScript/issues/39489 is closed, but its file-reference capability does not complete this request.
- **Deletion participants are not safe-delete approval:** src/vscode-dts/vscode.d.ts exposes workspace.onWillDeleteFiles and FileWillDeleteEvent.waitUntil. In src/vs/workbench/api/browser/mainThreadFileSystemEventService.ts, file-operation participants supply additional edits; declining their prompt skips those changes rather than providing the requested reference-aware cancellation of deletion.
