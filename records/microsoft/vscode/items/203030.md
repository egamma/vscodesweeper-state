# Issue #203030 — Tree Sticky Scroll: Support mouse interaction with compressed nodes

[https://github.com/microsoft/vscode/issues/203030](https://github.com/microsoft/vscode/issues/203030)

## Summary

A real interaction gap remains on current main: compressed sticky-scroll rows render individual folder labels, but the generic sticky-scroll mouse path still acts on the backing tree row rather than the clicked intermediate folder. This team-authored Backlog request should remain open for the tree-sticky-scroll area.

## Change summary

Allow mouse actions on each intermediate folder represented inside a compressed tree sticky-scroll row.

## Best solution

Make each folder segment in a compressed sticky row target the corresponding tree element for selection and context-menu actions, while retaining equivalent keyboard navigation and accessible state.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/tree/abstractTree.ts`, `src/vs/base/browser/ui/tree/objectTree.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`, `src/vs/base/test/browser/ui/tree/objectTree.test.ts`
- **Validation:** Add browser unit coverage for a compressed sticky row with at least three folder segments: clicking and right-clicking the middle segment must resolve that folder, while keyboard navigation and ordinary non-sticky compressed rows retain their existing behavior.
- **Behavior:**

  > Each visually distinct folder segment in a compressed sticky-scroll row should be an independently usable target. Clicking or opening the context menu on an intermediate segment must act on that folder rather than the compressed row's terminal or backing element. Hover highlighting, focus, selection, context-menu anchoring, keyboard navigation, and screen-reader state should describe the same active segment. Ordinary compressed rows and uncompressed sticky rows must remain unchanged.
- **Trace:**

  > CompressibleStickyScrollDelegate.compressStickyNodes in src/vs/base/browser/ui/tree/objectTree.ts synthesizes one sticky node from several ancestors and associates it with an ICompressedTreeNode for rendering. FilesRenderer.renderCompressedElements in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts creates a separate CompressedNavigationController for every rendered copy and identifies label segments on mousedown. TreeNodeListMouseController.handleStickyScrollMouseEvent in src/vs/base/browser/ui/tree/abstractTree.ts nevertheless focuses and selects the single backing list node, while ExplorerView.onContextMenu in src/vs/workbench/contrib/files/browser/views/explorerView.ts resolves through the first controller registered for that backing item. The boundary is compressed sticky-row targeting: preserve normal compact-folder behavior, generic tree selection semantics, drag-and-drop behavior unless explicitly included, and existing keyboard accessibility.
- **Open decisions:**
  - Which mouse operations must target an intermediate sticky segment: primary-click selection/navigation and context menu only, or also double-click, twistie, and drag-and-drop behavior?
  - When an intermediate folder has no independent visible list row, should clicking it change the tree's public selection/focus to that folder, or only use it as the action and context-menu target while the compressed row remains selected?

## Evidence

- **current source:** src/vs/base/browser/ui/tree/objectTree.ts:164-240 combines multiple sticky ancestors into one synthetic compressed node, while src/vs/base/browser/ui/tree/abstractTree.ts:2601-2617 handles a sticky pointer event through the backing list node and its single list index rather than resolving the clicked compressed segment.
- **Explorer interaction:** src/vs/workbench/contrib/files/browser/views/explorerViewer.ts:930-966 renders separate `.label-name` segments and updates a per-render CompressedNavigationController on mousedown, but src/vs/workbench/contrib/files/browser/views/explorerView.ts:708-733 resolves context-menu state through `controllers[0]`; it does not identify which normal or sticky controller contains the clicked label.
