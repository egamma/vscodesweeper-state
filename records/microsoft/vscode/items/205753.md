# Issue #205753 — Show loading icon on processing data

[https://github.com/microsoft/vscode/issues/205753](https://github.com/microsoft/vscode/issues/205753)

## Summary

The direct extension-command path still has no way for VS Code to show progress while the extension prepares issue data, because the workbench learns about the request only after `workbench.action.openIssueReporter` is invoked. This team-authored, accepted Backlog bug should remain open while the progress contract is designed.

## Change summary

Show visible pending feedback while an extension prepares data before opening the Issue Reporter.

## Best solution

Define an issue-reporter contribution contract that lets VS Code open or signal progress before awaiting extension-provided data, while preserving the existing immediate-data command path and accessible status feedback.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/issue/common/issue.contribution.ts`, `src/vs/workbench/contrib/issue/browser/issueFormService.ts`, `src/vs/workbench/contrib/issue/browser/issueReporterOverlay.ts`, `src/vs/workbench/contrib/issue/test/browser/issueReporterOverlay.test.ts`
- **Validation:** Add an Issue Reporter test with delayed extension-provided data that verifies pending feedback is exposed before resolution, submission cannot race the pending operation, and the completed data is applied afterward.
- **Behavior:**

  > When a user starts an extension-provided Issue Reporter flow whose data takes time to prepare, VS Code visibly and accessibly reports that the request is processing. The pending state begins promptly, prevents premature submission, and clears when data resolves or fails. Existing immediate-data calls continue to open without an unnecessary delay.
- **Trace:**

  > The direct command handler in src/vs/workbench/contrib/issue/common/issue.contribution.ts receives resolved arguments and calls `IWorkbenchIssueService.openReporter`; work performed by the extension before that call is outside VS Code's observable lifecycle. The in-reporter path already has a partial model: `IssueReporterOverlay.updateSelectedExtension` sets a localized loading status while awaiting `resolveExtensionIssueData`, and the legacy reporter renders a spinner around `sendReporterMenu`. The uncertainty begins at the extension contract: core cannot own the pending state unless invocation occurs before data preparation or a provider/promise lifecycle is exposed. Preserve immediate command calls, cancellation/race handling when extension selection changes, and accessible status communication; do not broaden this into a general command-progress redesign. The reporter confirmed the affected direct-entry flow at https://github.com/microsoft/vscode/issues/205753#issuecomment-1955135003.
- **Open decisions:**
  - Should extension-initiated reporting open the Issue Reporter immediately and resolve data through a provider-style asynchronous contract, or should the invoking extension remain responsible for progress until it calls `workbench.action.openIssueReporter`?
  - If VS Code owns the pending state, should users be able to edit the report while data loads, or should the form remain blocked until the extension data settles?

## Evidence

- **direct command path:** src/vs/workbench/contrib/issue/common/issue.contribution.ts registers `workbench.action.openIssueReporter` with already-resolved arguments and only then calls `IWorkbenchIssueService.openReporter`; VS Code cannot display progress during extension work performed before that invocation.
- **existing partial coverage:** src/vs/workbench/contrib/issue/browser/issueReporterOverlay.ts:965-968 displays “Loading extension issue data...” while `resolveExtensionIssueData` runs after an extension is selected inside the reporter, but this does not cover the reporter-direct command flow confirmed in https://github.com/microsoft/vscode/issues/205753#issuecomment-1955135003.
