# Issue #160373 — completion on breakpoint remove all items

[https://github.com/microsoft/vscode/issues/160373](https://github.com/microsoft/vscode/issues/160373)

## Summary

The contextual-completion gap remains on current main: breakpoint conditions are filtered using the widget text, but completion providers receive only the underlying source model at the start of the breakpoint line. This is established behavior rather than a regression, and the unresolved completion-model/API design warrants keeping the Backlog request open under discussion.

## Change summary

Make breakpoint-condition completions account for the complete expression being entered, including text after logical operators and member-access context.

## Best solution

Define a supported way to request language completions for an embedded debug expression with its surrounding source context, then use it in the breakpoint widget without transiently modifying the user's document.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/breakpointWidget.ts`, `src/vs/editor/contrib/suggest/browser/suggest.ts`
- **Validation:** Using a TypeScript or JavaScript breakpoint condition, verify that completion after a logical operator and member access (for example `enabled && object.`) returns context-appropriate members, while ordinary editor completions and breakpoint suggestions at the start of an expression remain unchanged; the plan should identify or add an automated debug-widget completion test where feasible.
- **Behavior:**

  > Breakpoint-condition completions must use the entire expression entered up to the cursor, so logical operators and member access do not discard relevant suggestions. Completions must still be evaluated in the lexical scope of the breakpoint's source location. Accepting a suggestion must replace only the intended expression segment, and normal source-editor completion behavior must remain unchanged.
- **Trace:**

  > In src/vs/workbench/contrib/debug/browser/breakpointWidget.ts, `createBreakpointInput` registers the debug-scheme completion provider. Its `provideCompletionItems` implementation calls `provideSuggestionItems` on the underlying source model at the first column of the breakpoint line, then rewrites returned ranges against the widget model; it never presents the widget expression to the language provider. Maintainers confirmed this limitation in https://github.com/microsoft/vscode/issues/160373#issuecomment-1244866572 and noted the lack of an LSP mechanism in https://github.com/microsoft/vscode/issues/160373#issuecomment-1247921410. The plan must trace how a contextual or virtual document would interact with extension-host and LSP completion providers before bounding the files. It must not transiently edit the user's source document, alter ordinary editor completion semantics, or broaden the work to the distinct Watch-input request at https://github.com/microsoft/vscode/issues/48810.

## Evidence
