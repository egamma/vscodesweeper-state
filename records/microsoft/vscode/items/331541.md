# Issue #331541 — Allow creator sessions to answer child input requests

[https://github.com/microsoft/vscode/issues/331541](https://github.com/microsoft/vscode/issues/331541)

## Summary

Keep open: current session tools still cannot submit a typed answer to another chat's pending input request. The orchestration model has changed since filing, so this team-authored follow-up needs planning against today's chat/session boundaries and authorization contract.

## Change summary

Let a creator conversation inspect and answer delegated work's active input request by exact target and request ID without starting a separate turn or bypassing user confirmation.

## Best solution

Provide a provider-neutral, request-addressed response capability with structured question context, answer validation, and stale-request rejection. First settle its eligibility rules under the current provenance-only relationship model, while retaining explicit user confirmation for approvals and sensitive actions.

- **Behavior:**

  > A creator conversation can obtain the structured context of an eligible delegated conversation's pending input request and submit an answer to that exact request. Submission must resume the existing request rather than create or steer an unrelated turn. Invalid answers and stale, completed, mismatched, or ineligible requests must be rejected without side effects. Approvals and sensitive actions retain explicit user confirmation, and supported providers expose equivalent behavior.
- **Trace:**

  > The current tool inventory in src/vs/platform/agentHost/common/serverToolNames.ts and node/shared/sessionServerTools.ts has no typed input-response operation. applySendMessageTool only starts, queues, or steers messages, and serializeSessionContext omits InputRequest response parts. The protocol already represents structured ChatInputRequest questions and answers, while AgentSideEffects handles ChatInputCompleted through the owning provider's respondToUserInputRequest seam. https://github.com/microsoft/vscode/pull/331518 and https://github.com/microsoft/vscode/pull/331544 explicitly leave this capability to https://github.com/microsoft/vscode/issues/331541; https://github.com/microsoft/vscode/issues/331521 is related orchestration context, not an equivalent report. The uncertainty starts at authorization and target scope: current create_session defaults to peer chats, independent sessions retain only creation provenance, and coordinateWithCreator is absent. Preserve ordinary messaging semantics, exact advertised identities, provider ownership, and existing permission/confirmation enforcement; creation provenance alone must not be assumed to grant authority.
- **Open decisions:**
  - Which delegated targets may a creator answer under the current model: same-session peer chats, independently created sessions, or both, and what explicit consent or coordination policy establishes that eligibility?
