# Issue #271012 — Copy and paste does not work between projects opened in dev containers

[https://github.com/microsoft/vscode/issues/271012](https://github.com/microsoft/vscode/issues/271012)

## Summary

The cross-container failure remains present on current main and belongs with the VS Code-owned Remote Development tracker. An older open report there covers the same cross-window ENOENT symptom, so this issue should be moved rather than closed or sent back to the reporter.

## Change summary

Copying an Explorer file between VS Code windows connected to different dev containers fails because the destination window cannot resolve the source container's remote URI.

## Best solution

Move this thread to https://github.com/microsoft/vscode-remote-release and consolidate it with https://github.com/microsoft/vscode-remote-release/issues/11149. The eventual implementation should transfer the current file contents between distinct remote authorities without resolving the source URI through the destination window's file-system provider.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/explorerService.ts`, `src/vs/workbench/contrib/files/browser/fileActions.ts`, `src/vs/workbench/services/clipboard/electron-browser/clipboardService.ts`, `src/vs/workbench/browser/dnd.ts`, `src/vs/platform/files`
- **Validation:** Open two VS Code windows attached to different dev containers, modify a source file, copy it from the first Explorer, and paste it into the second; verify the current bytes are transferred without ENOENT. Repeat remote-to-local, local-to-remote, same-remote, cut/paste, and drag-and-drop flows to guard against the regressions that caused the earlier revert.
- **Behavior:**

  > Explorer copy and paste between VS Code windows attached to different dev containers must copy the selected file's current contents into the destination. It must not report ENOENT merely because the destination window cannot directly resolve the source container's URI, and it must never transfer a stale version. Existing local, same-remote, cut/paste, and drag-and-drop behavior must remain unchanged.
- **Trace:**

  > ExplorerService.setToCopy in src/vs/workbench/contrib/files/browser/explorerService.ts puts the source resource URI on IClipboardService. NativeClipboardService in src/vs/workbench/services/clipboard/electron-browser/clipboardService.ts serializes that URI into the system clipboard, and pasteFileHandler in src/vs/workbench/contrib/files/browser/fileActions.ts asks the destination window's IFileService to stat and copy it. That destination service cannot resolve a URI owned by another remote authority, matching the ENOENT in this report and https://github.com/microsoft/vscode-remote-release/issues/11149. A broader proxy implementation landed in https://github.com/microsoft/vscode/pull/320685 but was reverted by https://github.com/microsoft/vscode/pull/321516 and https://github.com/microsoft/vscode/pull/323490 after regressions. The plan must preserve local and same-remote clipboard semantics and account for copy, cut, and drag-and-drop without reintroducing those regressions.

## Evidence

- **source trace:** src/vs/workbench/contrib/files/browser/explorerService.ts writes the selected remote URI through IClipboardService; src/vs/workbench/services/clipboard/electron-browser/clipboardService.ts serializes only that URI; src/vs/workbench/contrib/files/browser/fileActions.ts then calls fileService.stat on it in the destination window. A window attached to container B has no provider capable of resolving container A's authority, producing the reported ENOENT.
- **older canonical:** https://github.com/microsoft/vscode-remote-release/issues/11149 was opened before this issue and reports the same reporter-observable behavior: copying between two remote VS Code windows fails with the same ENOENT message. Its scope is broader and fully includes two dev-container windows.
- **related confirmed scenario:** https://github.com/microsoft/vscode-remote-release/issues/6204 is an older open Remote Development report where maintainers confirmed that transferring files between different remote authorities, including WSL and a dev container, fails.
- **implementation history:** https://github.com/microsoft/vscode/pull/320685 added a cross-process remote file-system proxy across ten core files for remote copy/paste and drag-and-drop, but it was reverted by https://github.com/microsoft/vscode/pull/321516 after regressions and again by https://github.com/microsoft/vscode/pull/323490. Current main therefore retains the failing URI-only path.
