# Issue #237095 — Support Line decoration editor offset retrieval

[https://github.com/microsoft/vscode/issues/237095](https://github.com/microsoft/vscode/issues/237095)

## Summary

Keep this accepted Backlog request open: current editor geometry methods expose column positions and whole-line widths, but not the requested class-filtered decoration endpoint. No verified canonical duplicate or concrete implementation was found.

## Change summary

Expose the rendered horizontal endpoint of matching inline decorations so editor overlay widgets can avoid covering their text.

## Best solution

Provide an editor-level geometry query for the requested decoration endpoint without changing existing column-position semantics. Settle the query's behavior for wrapped or bidirectional text and unavailable geometry before implementation.

## Plan brief

- **Likely files:** `src/vs/editor/browser/editorBrowser.ts`, `src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts`, `src/vs/editor/browser/view.ts`, `src/vs/editor/browser/viewParts/viewLines/viewLines.ts`, `src/vs/editor/browser/viewParts/viewLines/viewLine.ts`
- **Validation:** Use a rendered-editor browser check with multiple text decorations at one column, including matching and nonmatching classes: compare the returned endpoint with the rendered matching decoration bounds and verify an overlay placed there does not cover matching text. Repeat after scrolling and decoration updates, and cover the agreed wrapping, bidirectional-text, and unavailable-geometry contract.
- **Behavior:**

  > Core editor contributions need to place overlays beyond text-bearing decorations rather than only beyond document text. Given a column and decoration class, the query should expose the horizontal endpoint of the last matching decoration described by the request. Acceptance should demonstrate correct placement with multiple decorations and after scrolling or decoration changes, while preserving existing column-offset behavior.
- **Trace:**

  > ICodeEditor in src/vs/editor/browser/editorBrowser.ts exposes decoration enumeration separately from column and whole-line geometry. CodeEditorWidget delegates getOffsetForColumn to View.getOffsetForColumn in src/vs/editor/browser/view.ts, which converts a model position to a view position and asks the rendered lines for its visible range. ViewLine in src/vs/editor/browser/viewParts/viewLines/viewLine.ts measures whole-line widths and column ranges, but the inspected interfaces do not expose the requested class-filtered decoration endpoint. Whole-line width is not equivalent when unrelated decorations or subsequent content are present. Preserve existing offset APIs and keep this scoped to editor geometry rather than changing suggestion rendering or selection hit testing. The remaining uncertainty is the observable geometry contract for wrapped or bidirectional content and cases without a rendered match.
- **Open decisions:**
  - For wrapped or bidirectional content, does 'last/rightmost' mean the final matching decoration in logical order or the greatest visual right edge, and which rendered line does the result describe?
  - What result should callers receive when no matching decoration exists or the relevant line is outside the rendered viewport?
