# Issue #237095 — Support Line decoration editor offset retrieval

[https://github.com/microsoft/vscode/issues/237095](https://github.com/microsoft/vscode/issues/237095)

## Summary

A real editor API gap remains on current main: core contributions can retrieve geometry for a model column or an entire line, but not the horizontal bounds of a particular injected-text decoration. Keep this open under discussion because the API semantics and renderer compatibility need a maintainer decision.

## Change summary

Expose the horizontal offset of matching inline or injected-text decorations so overlay widgets can avoid covering rendered decoration content.

## Best solution

Provide a renderer-neutral internal editor API for retrieving the horizontal bounds of injected decoration content, with defined behavior for multiple decorations, wrapping, RTL text, and off-viewport lines. Prefer stable decoration identity or range semantics over coupling callers solely to a CSS class name.

## Plan brief

- **Likely files:** `src/vs/editor/browser/editorBrowser.ts`, `src/vs/editor/browser/view.ts`, `src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts`, `src/vs/editor/browser/viewParts/viewLines/viewLines.ts`, `src/vs/editor/browser/viewParts/viewLinesGpu/viewLinesGpu.ts`
- **Validation:** Add an editor browser test that renders multiple injected-text decorations at one model column and verifies the resulting geometry identifies the intended rightmost decoration without changing getOffsetForColumn behavior; cover wrapping and RTL, and exercise both supported rendering paths where the harness permits.
- **Behavior:**

  > Core editor contributions need a supported way to determine where selected inline decoration text ends so an overlay widget does not cover that text. The result must be accurate when multiple decorations share a column and must define behavior for wrapping, RTL text, invisible lines, and decorations that disappear between renders. Existing column-offset behavior must remain unchanged.
- **Trace:**

  > ICodeEditor in src/vs/editor/browser/editorBrowser.ts currently exposes only getOffsetForColumn and getWidthOfLine. CodeEditorWidget delegates column geometry through src/vs/editor/browser/view.ts, which maps the model position to a view position and calls ViewLines.visibleRangeForPosition; src/vs/editor/browser/viewParts/viewLines/viewLines.ts consequently returns a position edge rather than the bounds of any particular injected decoration. The GPU renderer exposes the same position-oriented operation in src/vs/editor/browser/viewParts/viewLinesGpu/viewLinesGpu.ts. The uncertainty begins at the public contract: CSS class matching, decoration identity, and range-based lookup have different stability and ambiguity characteristics. Preserve existing column geometry and do not make overlay callers inspect renderer DOM.
- **Open decisions:**
  - Should callers identify the target by decoration ID, injected-text options, range, CSS class name, or another stable handle?
  - When several matching decorations start at the same column, should the API return one bound, the rightmost bound, or all horizontal ranges?
  - What should the result mean for wrapped or RTL content and for lines outside the rendered viewport?
  - Must the initial contract support both DOM and GPU editor renderers before it is exposed to core contributions?

## Evidence

- **current editor API:** src/vs/editor/browser/editorBrowser.ts exposes getOffsetForColumn(lineNumber, column) and getWidthOfLine(lineNumber), but no decoration-specific geometry method.
- **source trace:** src/vs/editor/browser/view.ts converts a model position to a view position and asks ViewLines.visibleRangeForPosition for a zero-width position; src/vs/editor/browser/viewParts/viewLines/viewLines.ts returns only that position's left edge, without selecting or measuring a particular decoration.
- **renderer boundary:** The geometry path has both DOM handling in src/vs/editor/browser/viewParts/viewLines/viewLines.ts and GPU handling through visibleRangeForPosition in src/vs/editor/browser/viewParts/viewLinesGpu/viewLinesGpu.ts, so the contract must be defined consistently across renderers.
