# Issue #325081 — Agents Window: MCP Server with Authentication are not available in Agents Window

[https://github.com/microsoft/vscode/issues/325081](https://github.com/microsoft/vscode/issues/325081)

## Summary

Authenticated MCP servers remain unusable in the Agents Window despite working in editor Chat, with several independent confirmations across Balsamiq, Azure DevOps, Sentry, and Atlassian. Current main contains the intended authentication bridge, but the migration and runtime paths still have compatibility boundaries, so the issue remains necessary while the precise failing path is diagnosed.

## Change summary

Make OAuth-authenticated MCP servers configured through VS Code remain visible, authenticate successfully, and expose their tools in the Agents Window.

## Best solution

Authenticated MCP servers should survive transfer from VS Code configuration into Agent Host, complete authentication through the existing bridge, and remain visible and usable in the session. Unsupported configurations or failed authentication must remain visible with an actionable status instead of disappearing from Customizations.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationService.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/mcpServerCustomizationMigration.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`
- **Validation:** Add and run a targeted Agent Host customization/authentication test that starts with an authenticated remote server from a workspace MCP configuration, observes AuthRequired, completes authentication, and asserts the server transitions to Ready and its tools remain published; also retain a case that reports unsupported explicit OAuth configuration without silently removing the server.
- **Behavior:**

  > An MCP server configured in VS Code that requires OAuth must remain visible in the Agents Window, provide a working authentication flow, and expose its tools after authentication. Authentication state must not cause the server to disappear from Customizations. If the configuration cannot be transferred to Agent Host, the server must remain visible with a durable explanation and recovery or migration action. Editor Chat behavior and unauthenticated MCP servers must remain unchanged.
- **Trace:**

  > The issue starts with `.vscode/mcp.json`: editor Chat starts and authenticates the server, while the Agents Window initially lists it and then loses both the customization and its tools. Current main has interactive and silent authentication entry points in `agentHostCustomizationService.ts` and `agentHostSessionHandler.ts`, forwarding tokens through the session provider into Agent Host; Copilot session launch also installs `onMcpAuthRequest` with in-memory OAuth token storage. Separately, `mcpServerCustomizationMigration.ts` rejects explicit `oauth` configuration as non-representable. The uncertainty begins at the boundary between migration/discovery and runtime authentication: the affected server may never be adopted by Agent Host, may lose its published customization during an auth-state transition, or may receive a token without successfully republishing tools. Keep the investigation bounded to authenticated MCP discovery, state publication, and token handoff; do not redesign general customization enablement or unrelated Chat MCP behavior. Related tracking: https://github.com/microsoft/vscode/issues/332083 and https://github.com/microsoft/vscode/issues/334271.

## Evidence

- **independent reproductions:** https://github.com/microsoft/vscode/issues/325081 contains three additional confirmations involving Sentry and Atlassian MCP servers; reporters consistently observe that authenticated servers work in normal Chat but are absent or non-functional in the Agents Window.
- **active migration tracker:** https://github.com/microsoft/vscode/issues/332083 remains open and explicitly lists https://github.com/microsoft/vscode/issues/325081 under MCP reliability, describing authentication and invocation validation as remaining work rather than completed behavior.
- **current authentication path:** Current main routes interactive authentication through `authenticateMcpServer` in `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationService.ts` and silent token reuse through `_autoAuthenticateMcpServer` in `agentHostSessionHandler.ts`; both forward credentials to the Agent Host connection.
- **configuration compatibility boundary:** `isConfigurationRepresentable` in `src/vs/workbench/contrib/chat/browser/aiCustomization/mcpServerCustomizationMigration.ts` rejects remote configurations with an explicit `oauth` property, while `.vscode/mcp.json` requires migration for the Copilot Agent Host harness. This can explain some missing servers but does not account for all independently reported server-discovered OAuth cases.
- **related current reproduction:** https://github.com/microsoft/vscode/issues/334271 is open with the `bug` and `agent-host` labels and reports the same observable OAuth failure—tools absent in agent sessions while the identical configuration works in editor Chat—along with additional interactive-activation cases.
