# Issue #339964 — VS Code 1.101+ cannot find its own files on Omnissa App Volumes writable volumes (libuv `GetFileInformationByName` fast path, same cause as #251448 / libuv#4844)

[https://github.com/microsoft/vscode/issues/339964](https://github.com/microsoft/vscode/issues/339964)

## Summary

Keep open as an upstream Windows filesystem compatibility issue. The reporter's standalone reproduction isolates the failure below VS Code, and the previous FSLogix-specific workaround does not establish a fix for App Volumes.

## Change summary

Restore startup and file metadata lookups when Windows' by-name information API incorrectly reports existing App Volumes files as missing.

## Best solution

Resolve the App Volumes filter-driver incompatibility or agree on a safe fallback in libuv/Electron, then verify that VS Code's bundled runtime can resolve its CLI entry point and launch from the affected writable volume without modifying signed binaries.

## Evidence

- **Isolated reproduction:** https://github.com/microsoft/vscode/issues/339964 reports that direct GetFileInformationByName calls fail with errors 2 or 3 for existing writable-volume paths while ordinary existence checks succeed. Disabling that function lookup in an experimental executable restores metadata operations and startup; this is reporter evidence, not a reproduction performed during this review.
- **Current upstream error path:** https://github.com/libuv/libuv/blob/v1.x/src/win/fs.c, fs__stat_path, returns FS__STAT_PATH_ERROR for ERROR_FILE_NOT_FOUND and ERROR_PATH_NOT_FOUND rather than FS__STAT_PATH_TRY_SLOW. This matches the reported mechanism, but does not independently establish the exact libuv code bundled in the affected official build.
- **VS Code runtime boundary:** resources/win32/bin/code.cmd sets ELECTRON_RUN_AS_NODE=1 and passes resources/app/out/cli.js to Code.exe. The reported inability to resolve that existing entry point occurs before src/cli.ts can execute. build/lib/electron.ts packages a prebuilt Electron runtime; .npmrc currently selects Electron 43.7.7.
- **Previous fix is narrower:** https://github.com/microsoft/vscode/issues/251448 is closed. The workaround documented at https://github.com/microsoft/vscode/issues/251448#issuecomment-3105859398 retries only when HKLM\SOFTWARE\FSLogix exists. https://github.com/libuv/libuv/issues/4844 is also closed, with its discussion documenting a temporary Electron patch and a subsequent FSLogix driver fix, not an App Volumes fix.
- **Older related report:** https://github.com/microsoft/vscode/issues/259597 is open and older. https://github.com/microsoft/vscode/issues/259597#issuecomment-3325310276 confirms App Volumes launch failures on 1.104.1, but the detailed reproduction concerns profile-directory stat/mkdir failures rather than failure to resolve VS Code's own cli.js. It is strong related evidence, but does not establish the identical observable failure required for a duplicate close of this re-reviewed item.
