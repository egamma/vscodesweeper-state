# Issue #334541 — Plan is not shown when using Codex via Agent Host

[https://github.com/microsoft/vscode/issues/334541](https://github.com/microsoft/vscode/issues/334541)

## Summary

Traced in source: the live Codex event mapper never handles the `plan` `ThreadItem` type, so a completed Plan-mode plan is silently dropped instead of rendered in chat — a real, unrouted gap rather than something to close.

## Change summary

When using Codex via Agent Host in Plan mode, the generated plan is never shown in chat once the steps finish.

## Best solution

In src/vs/platform/agentHost/node/codex/codexMapAppServerEvents.ts, add explicit handling for `item.type === 'plan'` in both mapItemStarted and mapItemCompleted (it currently falls through the 'every remaining item type is a tool call' path and is dropped since no itemToToolCall entry exists), deciding whether to surface it as a markdown response part or a dedicated plan UI element; codexReplayMapper.ts also needs the same for restored sessions.

  > Thanks for the report — I traced this in the code. Codex's Agent Host protocol has a dedicated `plan` thread-item type, but the live event mapper (`codexMapAppServerEvents.ts`) only handles `agentMessage`/`reasoning` explicitly and treats every other item type as a tool call; since no tool-call entry is ever registered for `plan`, the plan text is silently dropped on completion. The same gap exists in the session replay mapper for restored sessions. This looks like it needs an explicit `plan` handling path (and a decision on how to render it) rather than a one-line fix.

## Evidence

- **live mapper gap:** src/vs/platform/agentHost/node/codex/codexMapAppServerEvents.ts only special-cases 'agentMessage'/'reasoning' in mapItemCompleted; for any other item type (including 'plan') it looks up state.itemToToolCall — which was never populated for 'plan' in mapItemStarted — finds nothing, and returns `[]`, so the plan text is silently dropped.
- **replay mapper gap:** src/vs/platform/agentHost/node/codex/codexReplayMapper.ts explicitly documents 'plan' as 'currently dropped' when reconstructing turns from `thread/read`, confirming the same gap applies to restored sessions.
