## Summary

Keep open: current source still rejects headerless or BOM-prefixed session logs without recovery, and the discussion confirms recurrence after the failed-write fix. An open persistence-hardening PR references this issue but does not establish that the full problem is resolved.

## Change summary

Previously saved Copilot Chat sessions become inaccessible when their JSONL log lacks the initial snapshot or contains a leading BOM.

## Best solution

Review the existing persistence-hardening PR, investigate the remaining path that creates headerless logs, and establish safe handling of already-corrupted sessions without silently inventing lost conversation state. Treat BOM handling separately, since the reporter encountered it during manual repair.

## Evidence

- **Current source confirms restoration failure:** src/vs/workbench/contrib/chat/common/model/objectMutationLog.ts:345–380 parses each line directly with JSON.parse and throws 'Log file is missing an initial entry' when a Set or Push precedes the initial snapshot. This conclusively preserves the reported failure for headerless and BOM-prefixed input; it does not establish how fresh corruption is created.
- **Corrupted files remain inaccessible:** src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts:653–711 passes an existing JSONL file to log.read(), reports malformedSession on failure, and returns undefined. The flat-file fallback only runs when JSONL content was not read, not when that content fails to parse.
- **Earlier prevention fix is not full resolution:** https://github.com/microsoft/vscode/pull/309292 merged on 2026-04-13 as 5e9baab3da463ac203611b9607d4b6df1af18675 and introduced write confirmation after successful persistence. Current ChatSessionStore.writeSession uses confirmWrite(), but the issue's 2026-07-20 comment independently reports recurrence on 1.129.1 and describes closing a chat immediately before quitting. That comment also offers a third-party repair tool, not evidence of a built-in fix.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/309286 is OPEN and explicitly references this issue. It proposes falling back to a full snapshot after incremental serialization failure and explicitly limits its claim to one durability failure path. The issue must remain open while this candidate is reviewed, and agent readiness must remain none.
- **Canonical search distinguishes missing files from malformed files:** https://github.com/microsoft/vscode/issues/299231 is older and OPEN, but its diagnostic discussion concerns nonexistent JSONL/JSON backing files after workspace transitions, not existing headerless logs. https://github.com/microsoft/vscode/issues/301098 is CLOSED as a duplicate of that missing-file report. Neither establishes a verified canonical for this corruption-specific report.

It supports the corruption diagnosis, but cannot be the duplicate target for this older, previously reviewed issue.
- **BOM provenance:** https://github.com/microsoft/vscode/issues/308730 states that the BOM parse error appeared after attempted manual repair. This supports parser intolerance of that input, not a conclusion that VS Code originally wrote the BOM.
