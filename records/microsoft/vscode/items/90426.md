# Issue #90426 — Add ability for before decorations to indent (stretch across) word wrapped lines

[https://github.com/microsoft/vscode/issues/90426](https://github.com/microsoft/vscode/issues/90426)

## Summary

This remains a valid editor API gap: GitLens cannot keep its inline blame annotation visually aligned across wrapped view lines, and a VS Code maintainer explicitly indicated that a purpose-built editor API is needed. The Backlog milestone and low reaction count do not establish that the request has been implemented or superseded.

## Change summary

Provide an editor rendering API that lets line annotations occupy a consistent leading area across every visual line produced by word wrapping.

## Best solution

Design a dedicated editor annotation surface rather than extending inline before-decoration behavior ad hoc, with wrapping, selection, hit testing, accessibility, and extension-host API semantics defined together.

## Plan brief

- **Likely files:** `src/vs/editor/common/model/textModel.ts`, `src/vs/editor/browser/viewParts/lines/viewLine.ts`, `src/vs/workbench/api/common/extHostTypes.ts`, `src/vs/workbench/api/browser/mainThreadEditors.ts`
- **Validation:** Add editor rendering tests covering an annotation on a logical line that wraps into multiple view lines, plus extension API tests confirming the annotation's configured wrapping behavior.
- **Behavior:**

  > Extensions need a supported way to render a line annotation such as blame text in a leading visual area that remains consistent across all wrapped segments of the same logical line. The annotation must not cause continuation text to begin underneath annotation content or disrupt indent guides. Existing inline and before-decoration behavior must remain compatible unless an API migration is explicitly chosen.
- **Trace:**

  > The report demonstrates that GitLens currently models gutter blame through inline before decorations, whose content belongs to one rendered position rather than a stable annotation column shared by every wrapped view line. In https://github.com/microsoft/vscode/issues/90426, alexdima identifies the intended direction as a new editor API and moving blame annotations off inline decorations. The uncertainty begins at the API boundary: whether this should be a general line-annotation primitive, a decoration option controlling wrapped continuation layout, or another editor-owned rendering surface. The implementation must preserve existing decoration and word-wrapping semantics for extensions that do not opt in.
- **Open decisions:**
  - Should the capability be a dedicated line-annotation API or an opt-in wrapping behavior on editor decorations?
  - Should wrapped continuation lines reserve the annotation width, repeat annotation content, or expose those behaviors separately?
  - What interaction, accessibility, and hit-testing semantics should annotation content support?
