# Issue #321878 — Agents: Need a way to heal broken worktree paths

[https://github.com/microsoft/vscode/issues/321878](https://github.com/microsoft/vscode/issues/321878)

## Summary

This team-authored feature request describes a real recovery gap: current main retains the session's old working-directory metadata after its worktree is moved, and the Agents Window exposes no relocation flow. No verified canonical issue or complete existing capability makes this unnecessary.

## Change summary

Allow an active Agents Window session to reconnect to its worktree after the repository and worktree paths move.

## Best solution

Provide a safe recovery flow that detects an unavailable session worktree, lets the user identify its new location, validates that it is the expected repository/worktree, and atomically updates the Agent Host session so chat, terminal, changes, permissions, and future turns use the repaired path.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/localAgentHostSessionsProvider.ts`, `src/vs/sessions/contrib/sessions/browser/sessionsActions.ts`, `src/vs/sessions/contrib/providers/agentHost/test/browser/localAgentHostSessionsProvider.test.ts`
- **Validation:** Add focused provider/action tests that start with a session whose primary worktree URI is unavailable, accept a validated replacement URI, and assert that the session workspace and subsequent Agent Host state use the replacement while unrelated working directories remain unchanged.
- **Behavior:**

  > When an active session's recorded worktree no longer exists because its containing folders moved, the Agents Window offers a recoverable path instead of leaving the session unusable. The user can identify the relocated worktree, and VS Code verifies that it is compatible with the session before adopting it. After recovery, reopening the chat, terminals, changes, and subsequent agent operations consistently use the new location. Cancellation or a mismatched directory must leave the persisted session unchanged.
- **Trace:**

  > The session facade in src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts derives its workspace from authoritative `project` and `workingDirectories` metadata through src/vs/sessions/common/agentHostSessionWorkspace.ts. SessionsService opens that facade and trusts its recorded working directories; there is no Sessions-owned relocation action. The AHP state model already defines a client-dispatchable `SessionWorkingDirectoryReplacedAction`, including compare-and-swap semantics and capability-gated primary replacement, but no code under src/vs/sessions dispatches it. Preserve provider ownership of persisted workspace metadata and do not implement recovery as a UI-only URI override. Keep deleted archived-worktree restoration from https://github.com/microsoft/vscode/issues/324248 and the broader UX work in https://github.com/microsoft/vscode/issues/336620 outside this issue's narrow moved-path contract.
- **Open decisions:**
  - Should recovery offer only an explicitly chosen replacement directory, or also suggest a uniquely inferred relocated path when the repository and worktree moved together?
  - What repository/worktree identity must match before VS Code accepts a replacement path and resumes agent operations?
  - When both the parent repository URI and primary worktree URI moved, should one recovery operation relocate both identities or require separate confirmation?

## Evidence

- **current source gap:** src/vs/sessions/common/agentHostSessionWorkspace.ts builds the visible session workspace directly from persisted `project` and `workingDirectories`; src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts refreshes that workspace only when authoritative metadata changes. No Agents Window action currently dispatches a replacement for a moved path.
- **protocol foundation:** src/vs/platform/agentHost/common/state/protocol/channels-session/actions.ts defines the client-dispatchable `SessionWorkingDirectoryReplacedAction`, and reducer.ts atomically replaces the matching directory. Replacing the primary directory is capability-gated, so the remaining work includes product UX, capability handling, validation, and provider integration rather than merely changing display metadata.
- **related issue distinction:** https://github.com/microsoft/vscode/issues/324248 concerns restoring an archived session whose managed worktree was deleted and is expected to be recreated; this report concerns reconnecting an active session to an existing worktree moved to a new path.
- **canonical search:** https://github.com/microsoft/vscode/issues/336620 is a broader Git/worktree UX overview that explicitly preserves narrower reports and does not establish relocation semantics; it is related context, not a canonical duplicate owning this concrete recovery flow.
