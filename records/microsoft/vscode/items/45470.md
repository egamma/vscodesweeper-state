# Issue #45470 — Add a setting to not promote workspace folders to top level if they are children of another top level folder

[https://github.com/microsoft/vscode/issues/45470](https://github.com/microsoft/vscode/issues/45470)

## Summary

The requested hierarchy remains absent on current main, while 107 community upvotes and repeated monorepo examples show sustained demand. The Backlog milestone and established feature-request classification also rule out a judgment close.

## Change summary

Add an opt-in Explorer mode that displays nested workspace folders at their filesystem position instead of duplicating each one as a top-level root.

## Best solution

Provide an opt-in Explorer hierarchy for workspace folders related by filesystem ancestry, preserving each nested folder's workspace identity and settings while eliminating its duplicate top-level presentation. Keep unrelated workspace roots and existing default behavior unchanged.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/common/explorerModel.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `src/vs/workbench/contrib/files/test/browser/explorerService.test.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Add Explorer model/view tests for a workspace containing one root nested beneath another: with the option enabled, the child appears once at its filesystem position and retains workspace-root identity; with it disabled, both folders remain separate top-level roots. Also cover unrelated roots and multiple nested children.
- **Behavior:**

  > An opt-in setting presents workspace folders nested beneath another workspace folder at their actual filesystem position rather than duplicating them at the Explorer's top level. The nested folder must remain a real workspace folder for resource-scoped settings and extension APIs, and it should be visually distinguishable as such. Unrelated roots and the setting's disabled state retain today's flattened multi-root behavior. Acceptance includes parent-child, sibling nested-project, and unrelated-root workspace layouts.
- **Trace:**

  > ExplorerModel in src/vs/workbench/contrib/files/common/explorerModel.ts currently maps every workspace folder to a parentless ExplorerItem, which conclusively explains the flattened duplicate presentation. ExplorerDataSource in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts resolves children from each filesystem-backed ExplorerItem, and ExplorerView in explorerView.ts renders the resulting roots through the async tree. The Explorer configuration in files.contribution.ts has no overlapping-root option; `explorer.compactFolders` addresses a different kind of compression. Preserve workspace-folder identity, resource-scoped configuration, selection/reveal behavior, and the default top-level layout. Arbitrary synthetic grouping through slash-delimited workspace names, proposed later in the thread, is outside the issue's filesystem-ancestry scope unless a maintainer deliberately expands it. Related issue https://github.com/microsoft/vscode/issues/32693 concerns nested settings rather than this Explorer symptom.
- **Open decisions:**
  - Should a nested workspace folder be shown as the ordinary filesystem node with a workspace-root decoration, or as a visually distinct workspace-root node inserted at the same hierarchy position?

## Evidence

- **current source gap:** In src/vs/workbench/contrib/files/common/explorerModel.ts, ExplorerModel constructs `_roots` by mapping every entry from `contextService.getWorkspace().folders` directly to a parentless ExplorerItem. Therefore an overlapping child workspace folder is still always presented as a separate top-level Explorer root.
- **no existing setting:** The Explorer configuration registered in src/vs/workbench/contrib/files/browser/files.contribution.ts has no option for nesting or suppressing overlapping workspace roots. `explorer.compactFolders` only compresses ordinary single-child folder chains and does not cover this request.
- **tree path:** ExplorerDataSource in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts obtains children through each ExplorerItem's filesystem-backed `fetchChildren`, while ExplorerView consumes the model roots directly. Representing a workspace root inside another root must preserve resource identity across both the model and tree behavior.
- **community demand:** The issue has 107 body upvotes, and comments provide concrete nested Flutter, package, and monorepo layouts where flattened roots create indistinguishable duplicate entries.
- **workaround is incomplete:** The thread's `files.exclude` workaround hides nested projects from the parent root rather than representing workspace folders hierarchically; later comments report Explorer jumping and extension incompatibilities, so it does not satisfy the central request.
- **canonical search:** https://github.com/microsoft/vscode/issues/32693 predates this issue but requests subtree-specific settings discovery, not the same reporter-observable Explorer duplication. It does not satisfy the stronger duplicate bar for this re-reviewed item, and no open canonical owning the same hierarchy request was found.
