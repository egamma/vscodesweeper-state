# Issue #350212 — Crash recovery dialogs must be dismissed in reverse order when multiple windows exit on Linux/X11

[https://github.com/microsoft/vscode/issues/350212](https://github.com/microsoft/vscode/issues/350212)

## Summary

Keep open: the detailed reproduction and current native-dialog path point to Electron/GTK modal-grab behavior, not an extension problem. No verified fix or matching canonical was found.

## Change summary

Make recovery dialogs for different crashed windows independently usable, or clearly present serialized recovery.

## Best solution

Correct cross-window modality in Electron's GTK message-box implementation so one window's recovery dialog does not silently block another's. Assess a VS Code recovery-dialog workaround only after confirming the native cause; recovery must remain available when renderers are dead.

Reversing renderer termination order reverses the required dialog dismissal order; the main process survives and recovery succeeds in stack order.
- **Current VS Code path:** src/vs/platform/windows/electron-main/windowImpl.ts:1180-1196 passes this._win to the recovery message box. src/vs/platform/dialogs/electron-main/dialogMainService.ts:139-176 queues independently by window ID and delegates to electron.dialog.showMessageBox(window, options), allowing different windows' native dialogs to coexist.
- **Native modality evidence:** https://github.com/electron/electron/blob/v43.8.9/shell/browser/ui/message_box_gtk.cc constructs GtkMessageBox instances, disables each parent and calls gtk_window_set_modal(..., TRUE), without assigning a separate GtkWindowGroup in this implementation. https://github.com/GNOME/gtk/blob/3.24.52/gtk/gtkwindowgroup.c documents default-group membership and prepends new grabs, returning the head as the current grab. This supports the reported last-in-first-out behavior; the graphical reproduction was not independently executed.
