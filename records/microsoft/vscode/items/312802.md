## Summary

Keep open: recent stable telemetry confirms the Microsoft-provider timeout still interrupts Cloud Changes resume, and the failing path remains on main. The authentication owner rejected the user-error interpretation; the registration failure needs diagnosis before choosing a fix.

## Change summary

Microsoft authentication provider registration times out during Cloud Changes resume and escapes as an unhandled error.

## Best solution

Establish why activation completes without an available Microsoft provider, then make provider readiness reliable while preserving progress when another extension host is blocked. Cloud Changes must distinguish authentication failure from an empty session list and handle that failure explicitly.

- **Behavior:**

  > Cloud Changes automatic resume can fail with an unhandled Microsoft-provider registration timeout despite a previously selected authentication session. When the provider becomes available, resume should use the existing session normally; an authentication failure must remain distinguishable from having no cloud changes and must not escape as an unhandled background rejection. Acceptance includes a deterministic reproduction of the diagnosed registration condition, successful normal resume, explicit handling of genuine provider failure, and continued authentication progress when an unrelated extension host is blocked.
- **Trace:**

  > AuthenticationService.tryActivateProvider in src/vs/workbench/services/authentication/browser/authenticationService.ts races activateByEvent against provider registration and starts its 5000ms fallback only after activation completes without a provider. Microsoft activate in extensions/microsoft-authentication/src/extension.ts awaits MsalAuthProvider.create before registration, while ExtHostAuthentication.registerAuthenticationProvider queues and internally awaits the main-thread registration RPC independently of extension activation. AbstractExtensionService aggregates activation across applicable hosts; the exact reason registration is missing at timeout is not established. EditSessionsStorageService.getAllSessions propagates the failure through getExistingSession and initialize, and EditSessionsContribution launches automatic resume without a rejection handler. Stable telemetry and the owner discussion confirm the failure, but not the earlier automated MSAL-delay explanation; https://github.com/microsoft/vscode-engineering/pull/2691 specifically critiques that explanation. Preserve the blocked-host behavior introduced by https://github.com/microsoft/vscode/pull/316386 and covered by the authentication-service test referencing https://github.com/microsoft/vscode/issues/315841. Do not treat a larger timeout or an empty-session fallback as proof of a root-cause fix; diagnosis must establish the failing activation/registration ordering first.
