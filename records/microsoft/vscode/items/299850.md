# Issue #299850 — Allow workspace extensions to use proposed API

[https://github.com/microsoft/vscode/issues/299850](https://github.com/microsoft/vscode/issues/299850)

## Summary

The requested capability remains absent on current main: workspace-scoped extensions lose their proposed API declarations because runtime extension descriptions do not preserve workspace scope. This team-authored Backlog feature request should remain open for the extensions area.

## Change summary

Allow trusted workspace-local extensions to use explicitly declared proposed APIs in built VS Code distributions such as Insiders.

## Best solution

Carry workspace-scoped identity into the runtime extension description and define a deliberate access policy that permits these development extensions to retain declared proposals without weakening the restrictions for ordinary user-installed extensions.

## Plan brief

- **Likely files:** `src/vs/platform/extensions/common/extensions.ts`, `src/vs/workbench/services/extensions/common/extensions.ts`, `src/vs/workbench/services/extensions/common/extensionsProposedApi.ts`, `src/vs/workbench/services/extensions/test/common/extensions.test.ts`
- **Validation:** Add targeted extension-service tests showing that a workspace-scoped extension retains its explicitly declared proposed APIs in a built Insiders-like environment while an equivalent ordinary user extension still has them removed.
- **Behavior:**

  > A workspace-scoped extension installed from the workspace can use the proposed APIs it explicitly declares when running in an eligible built VS Code distribution. Ordinary marketplace or user-installed extensions remain subject to the existing product and command-line allowlists. Invalid or undeclared proposals remain rejected. Acceptance requires tests distinguishing workspace-scoped and ordinary user extensions under the same built-environment configuration.
- **Trace:**

  > ILocalExtension carries isWorkspaceScoped in src/vs/platform/extensionManagement/common/extensionManagement.ts. CachedExtensionScanner converts those extensions through toExtensionDescription in src/vs/workbench/services/extensions/common/extensions.ts, but IRelaxedExtensionDescription in src/vs/platform/extensions/common/extensions.ts has no workspace-scope field, so that identity is lost. ExtensionsProposedApi.doUpdateEnabledApiProposals in src/vs/workbench/services/extensions/common/extensionsProposedApi.ts consequently reaches its non-builtin guard and clears enabledApiProposals. Preserve the product allowlist, command-line opt-in, extension-development behavior, proposal validation, and restrictions for ordinary user extensions; the uncertainty is limited to the intended trust/access policy for workspace-scoped extensions.
- **Open decisions:**
  - Should every workspace-scoped extension automatically retain declared proposed APIs, or should access additionally require a trusted-workspace or explicit opt-in condition?
