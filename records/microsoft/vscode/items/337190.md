# Issue #337190 — Forked chat accepts a new name but does not retain it, including after Reload Window

[https://github.com/microsoft/vscode/issues/337190](https://github.com/microsoft/vscode/issues/337190)

## Summary

Traced this on main: `ChatSessionStore.setSessionTitle` (src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts:510) only patches the in-memory index entry's title and never writes the underlying per-session log/flat file, so if the ChatModel for the renamed session isn't currently loaded in `_sessionModels`, the rename never reaches durable storage and is silently overwritten on next load — matching both the forked-chat report and the second commenter's plain rename report.

## Change summary

Renaming a chat (forked or ordinary) via Rename/F2 either doesn't stick, or reverts to the old title after switching away and back / reloading the window.

## Best solution

Make ChatSessionStore.setSessionTitle also update the persisted session content (append a customTitle Set entry via ChatSessionOperationLog, or rewrite the flat file) when the session model isn't already resident in memory, so the durable file and the index agree; alternatively have ChatService.setChatSessionTitle force-load the model before calling setCustomTitle so storeSessions() always captures the change.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts`, `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts`, `src/vs/workbench/contrib/chat/common/model/chatSessionOperationLog.ts`
- **Validation:** A ChatSessionStore/ChatService test that renames a session without first loading its ChatModel into memory, then reloads/reconstructs the model from the persisted store and asserts the new title is reflected (not the stale one), covering the exact gap the current 'setSessionTitle updates existing session title' test misses.
- **Behavior:**

  > Renaming a chat session (via Rename, F2, or the rename quick-input) must persist durably: the new title must survive switching to another chat and back, and must survive Reload Window / restarting VS Code, whether or not the session's chat editor happens to be open at the moment of the rename. Acceptance: rename a session that is NOT currently open, reload/reconstruct its ChatModel from storage, and confirm the new title (not the old one) comes back.
- **Trace:**

  > ChatSessionStore.setSessionTitle (chatSessionStore.ts:510) only mutates the in-memory index (`index.entries[sessionId].title`), never the per-session persisted content; ChatSessionStore.readSession (chatSessionStore.ts:635) and ChatModel's constructor (chatModel.ts:2983) reconstruct `_customTitle` purely from that persisted content, ignoring the index. ChatService.setChatSessionTitle (chatServiceImpl.ts:426) only calls `model.setCustomTitle(...)` when the model is already resident in `_sessionModels`, so an unopened session's rename never reaches the file. Do not change how a resident model's rename is persisted today (that path, via storeSessions()/ChatSessionOperationLog, already works) — the gap is specifically the not-currently-loaded-session path. Related: microsoft/vscode#337190 (this issue) and the corroborating comment from mmateas on the same thread.
- **Open decisions:**
  - Should the fix patch the persisted log/flat file directly for a title-only change on an unloaded session, or should the service force-load the ChatModel (via getOrRestoreSession) before calling setCustomTitle so the existing storeSessions() write path handles it uniformly?

## Evidence

- **index-only write:** ChatSessionStore.setSessionTitle (chatSessionStore.ts:510-517) only does `index.entries[sessionId].title = title` inside storeQueue.queue — no call to writeSession/fileService, so the actual session log/flat file content (which carries the authoritative `customTitle`) is never touched.
- **restore path ignores index:** ChatSessionStore.readSession (chatSessionStore.ts:635) reads the persisted log/flat file to reconstruct the ChatModel; ChatModel deserialization sets `_customTitle` from that file's `customTitle` field (chatModel.ts:2983), not from the index — so a title only updated in the index is discarded when the model is (re)created.
- **caller only conditionally updates the model:** ChatService.setChatSessionTitle (chatServiceImpl.ts:426-439) calls `model.setCustomTitle(title)` only `if (model)` is already in `_sessionModels`; when the session isn't currently loaded (e.g. renamed from the sessions list/picker without the chat open), only the index-only setSessionTitle path runs, so nothing durable changes.
- **test coverage gap:** The only existing test, 'setSessionTitle updates existing session title' (test/common/model/chatSessionStore.test.ts:265), asserts only `index['session-1'].title`, never checking the actual persisted file content, which is consistent with this being a long-standing, untested gap (chatSessionStore.ts has existed with this exact setSessionTitle body since at least commit fb25c9348).
- **second report corroborates:** Comment from mmateas describes the identical symptom for an ordinary, non-forked chat on macOS, inspecting the JSONL directly and confirming no customTitle patch is written — independent confirmation of the same code path.
