# Issue #338156 — Terminal throughput is limited by the flow control window and 5 ms output batching

[https://github.com/microsoft/vscode/issues/338156](https://github.com/microsoft/vscode/issues/338156)

## Summary

New, well-researched performance investigation into pty-host output batching and flow control; the reporter's code references and behavior description check out against current main, but this is a deliberate design (with an explicit comment warning about remote/shared-connection tradeoffs), so it needs a maintainer decision rather than an automated fix.

## Change summary

Local terminal output throughput is capped by TerminalDataBufferer's fixed 5ms batching delay and the 100,000-char HighWatermarkChars flow-control window; reporter proposes a leading-edge flush and/or raising the watermark (possibly only for local terminals).

## Best solution

Have a maintainer weigh in on whether a leading-edge flush (no message-count regression per the reporter's own measurements) and/or a local-only watermark increase are acceptable, given the existing code comment's concern about the watermark affecting shared remote connections.

## Plan brief

- **Likely files:** `src/vs/platform/terminal/common/terminalDataBuffering.ts`, `src/vs/platform/terminal/common/terminal.ts`
- **Validation:** A benchmark or terminal flow-control test comparing round-trip latency and message count before/after, similar to the reporter's vtebench methodology.
- **Behavior:**

  > As far as established: local terminal bulk output should not be artificially capped by a fixed 5ms batch delay when the pty and renderer are otherwise idle, and the flow-control watermark should allow more throughput per round trip without harming Ctrl+C responsiveness or (for remote) fairness on the shared connection.
- **Trace:**

  > Root cause traced to two independent mechanisms: TerminalDataBufferer.startBuffering (src/vs/platform/terminal/common/terminalDataBuffering.ts:38-49) always waits `throttleBy` (default 5ms) before the first flush even when the pty is idle, and FlowControlConstants.HighWatermarkChars (src/vs/platform/terminal/common/terminal.ts, ~line 881) fixes the unacknowledged-chars window at 100,000 regardless of local vs. remote connections. The existing comment on LowWatermarkChars explicitly flags that the window size matters because the connection is shared with other core functionality for remote scenarios — this is the boundary that must not be casually widened without further remote testing. Where uncertainty starts: reporter tested only local terminals; remote impact of either change is unverified.
- **Open decisions:**
  - Should the flush behavior become leading-edge (send immediately, batch only within the following throttle window) for all terminals, or only local ones?
  - Should HighWatermarkChars be raised globally or only for local (non-remote) terminals, given the shared-connection concern noted in the existing code comment?

## Evidence

- **5ms batching confirmed:** src/vs/platform/terminal/common/terminalDataBuffering.ts:38 sets `throttleBy: number = 5` and schedules a `setTimeout(() => this.flushBuffer(id), throttleBy)` on the first chunk before any data is sent, matching the report.
- **watermark constants confirmed:** src/vs/platform/terminal/common/terminal.ts defines `FlowControlConstants.HighWatermarkChars = 100000` with a comment on `LowWatermarkChars` explicitly noting 'not flooding the connection is the important thing as it's shared with other core functionality' — i.e. the current window size is an intentional remote-sharing tradeoff, not an oversight.
- **no existing fix:** git log on both files shows no recent related change; these mechanisms are unmodified as the reporter states.
