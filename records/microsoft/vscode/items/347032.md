# Issue #347032 — Stopping port forwarding leaves concurrent tunnel connections open

[https://github.com/microsoft/vscode/issues/347032](https://github.com/microsoft/vscode/issues/347032)

## Summary

The concurrent-connection cleanup defect remains in current main. Keep this open while the existing fixing PR is reviewed and landed.

## Change summary

Stopping a built-in Node tunnel fails to close every established connection because disposal callbacks collide on the listener's shared local address.

## Best solution

Review and land https://github.com/microsoft/vscode/pull/347033 so stopping forwarding closes all established connections, including when another client disconnected earlier.

## Evidence

- **Confirmed callback collision:** src/vs/platform/tunnel/node/tunnelService.ts:53,150-156 declares a Map<string, () => void> and registers each connection using localSocket.localAddress. Two established sockets accepted on the same local address overwrite the same entry.
- **Both reported failure paths remain:** NodeRemoteTunnel.dispose() at src/vs/platform/tunnel/node/tunnelService.ts:75-85 invokes only callbacks remaining in that map. The end/error handlers at lines 126-138 delete by the same shared address, so disconnecting one client can remove the remaining client's disposal callback.
- **Public service path:** src/vs/platform/tunnel/common/tunnel.ts:424-454 traces closeTunnel through tryDisposeTunnel to the underlying tunnel.dispose(true), reaching the faulty NodeRemoteTunnel cleanup. This confirms the reported established-connection path from source without executing code.

Its description addresses socket-identity tracking and reports regression cases for two concurrent clients and an earlier client disconnect; those reported checks were not independently executed during this read-only review.
