# Issue #129482 — Imported modules not idenfied in subsequent Notebook Cells

[https://github.com/microsoft/vscode/issues/129482](https://github.com/microsoft/vscode/issues/129482)

## Summary

Keep open: cross-cell visibility of imported TypeScript bindings remains an unresolved notebook language-support capability. Current code suppresses notebook semantic errors but still sends cells as separate documents; this accepted, team-authored request has 21 upvotes and already serves as the consolidation target for related reports.

## Change summary

Make TypeScript bindings imported in one notebook cell available to IntelliSense in subsequent cells.

## Best solution

Define notebook-wide TypeScript binding visibility and redeclaration semantics, then provide cross-cell IntelliSense through the built-in TypeScript language support. Preserve notebook workflows that reevaluate or redeclare variables rather than treating simple document concatenation as sufficient.

## Plan brief

- **Likely files:** `extensions/typescript-language-features/src/tsServer/bufferSyncSupport.ts`, `extensions/typescript-language-features/src/typescriptServiceClient.ts`, `extensions/typescript-language-features/src/languageProvider.ts`
- **Validation:** In a TypeScript notebook, put import * as fs from 'fs' in the first cell and request completions for fs. in the second; verify filesystem members and their types are available. Exercise repeated const declarations in separate cells according to the agreed semantics, and confirm normal TypeScript files retain module isolation.
- **Behavior:**

  > An import in an earlier TypeScript notebook cell should supply useful typed IntelliSense in subsequent cells, matching the notebook's shared execution workflow. Suppressing an undefined-name diagnostic alone does not satisfy the request. Acceptance includes completions and type information for fs in a later cell after importing it in the first, plus explicit checks for the chosen behavior of repeated declarations and exports. Ordinary TypeScript files must retain their existing module semantics.
- **Trace:**

  > SyncedBuffer.open in extensions/typescript-language-features/src/tsServer/bufferSyncSupport.ts sends each document's text under its own filepath; BufferSyncSupport.openTextDocument creates those buffers independently. This matches the discussion's diagnosis that an import makes a cell a module and isolates its declarations. extensions/typescript-language-features/src/languageProvider.ts currently suppresses notebook semantic diagnostics, which addresses visible errors but not cross-cell symbol availability. The thread rejects treating concatenation as an automatic answer because duplicate declarations across cells can then produce errors. Related project-resolution work was consolidated here at https://github.com/microsoft/vscode/issues/213740#issuecomment-2260989967; avoid assuming that resolving relative paths alone supplies cross-cell bindings. The uncertainty starts at the notebook's intended visibility and redeclaration contract, not at the choice of implementation helper.
- **Open decisions:**
  - Should subsequent cells inherit all top-level bindings, including imported names and non-exported declarations, or only explicitly exported bindings?
  - When separate cells redeclare the same name, should later cells see the latest preceding declaration without a duplicate-declaration error, or should notebook-wide TypeScript diagnostics report a conflict?
