# Issue #268511 — Images attachments behavior has changed

[https://github.com/microsoft/vscode/issues/268511](https://github.com/microsoft/vscode/issues/268511)

## Summary

The capability gap remains on current main: user-attached images are uploaded and represented to the model by a private URL, while MCP tool invocation receives only model-generated JSON parameters. A maintainer explicitly accepted investigating a base64-visible path, so this should remain open under discussion.

## Change summary

Allow an MCP tool to access a user-attached image when chat sends the model a private uploaded URL instead of inline base64 data.

## Best solution

Define a secure, bounded attachment handoff that lets an invoked MCP tool retrieve the original image without restoring large base64 payloads to every model turn. The contract should cover representation, authorization, lifetime, and whether attachment access is automatic or explicitly selected in tool input.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/prompts/node/panel/image.tsx`, `extensions/copilot/src/extension/prompts/node/panel/toolCalling.tsx`, `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostLanguageModelTools.ts`, `src/vs/workbench/contrib/chat/common/tools/languageModelToolsService.ts`
- **Validation:** Add an integration test that submits a known image attachment, invokes a test MCP tool, and verifies that the tool can retrieve byte-identical image data while the outbound model request continues to use an uploaded URL rather than inline base64.
- **Behavior:**

  > When a chat request includes an image and the model invokes an MCP tool that needs it, the tool can access the selected attachment through a supported contract. The attachment remains usable for the invocation even when the model-facing prompt uses an uploaded URL, and unauthorized or unrelated tools cannot retrieve it. The existing URL-based model payload and context-size protection remain intact.
- **Trace:**

  > Image.render in extensions/copilot/src/extension/prompts/node/panel/image.tsx receives the original Uint8Array, then uploadChatImageAttachment replaces the model-facing source with a URL when supported. Tool invocations cross the VS Code API boundary as JSON parameters through LanguageModelToolInvocationOptions and extHostLanguageModelTools; no parallel attachment payload is currently carried. MCP and prompt code already handle binary images in the opposite direction, from tool results to the model, in src/vs/platform/mcp/common/modelContextProtocol.ts and extensions/copilot/src/extension/prompts/node/panel/toolCalling.tsx. Preserve URL-based prompt-size optimization and existing tool-result image handling; the unresolved boundary is the secure user-attachment-to-tool contract. Related https://github.com/microsoft/vscode/issues/287801 concerns MCP prompt argument encoding and should not absorb this issue.
- **Open decisions:**
  - Should an MCP tool receive attachment bytes/base64 directly, an authenticated short-lived URL, or a VS Code resource identifier it can read through a defined API?
  - Is attachment access passed automatically with every invocation, or must the model explicitly bind a selected attachment to a declared tool input?

## Evidence

- **tool boundary:** src/vscode-dts/vscode.d.ts and src/vs/workbench/api/common/extHostLanguageModelTools.ts expose tool invocation through LanguageModelToolInvocationOptions.input / dto.parameters; the current invocation contract has no separate user-attachment data channel.

- **maintainer direction:** The maintainer comment at https://github.com/microsoft/vscode/issues/268511#issuecomment-3341938977 explains that URL upload was introduced for image/context-size limits and proposes investigating a way to expose the base64 result while retaining the URL for the model.
