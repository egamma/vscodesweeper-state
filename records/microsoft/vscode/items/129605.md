# Issue #129605 — Required fields aren't being validated

[https://github.com/microsoft/vscode/issues/129605](https://github.com/microsoft/vscode/issues/129605)

## Summary

Required object properties still escape validation in the Settings editor: the current validator checks only keys that are present, while the display merges in defaults. Keep this accepted, team-authored bug open; no qualifying fix or older canonical was identified.

## Change summary

Make the Settings editor report missing required object properties, including when displayed defaults conceal their absence from settings.json.

## Best solution

Bring object-setting validation into agreement with the JSON editor without removing normal default-value rendering. Preserve the author's stated persistence rule: required defaults belong in an explicitly configured object when saved, but ordinary defaults must not be written indiscriminately.

- **Confirmed missing-required validation:** src/vs/workbench/services/preferences/common/preferencesValidation.ts:340–405: getObjectValidator reads properties, patternProperties, additionalProperties and propertyNames, but never required. It validates only Object.keys(value), so an object containing B but omitting required A passes when B is otherwise valid.
- **Exact reported display path:** src/vs/workbench/contrib/preferences/browser/settingsTree.ts:168–256: getObjectDisplayValue merges elementDefaultValue with elementScopeValue for configured settings. Thus missing A appears when supplied by the default object, and is absent from the rows when neither object supplies it. Neither case introduces a missing-required warning.
- **Validator is wired but lacks the constraint:** src/vs/workbench/services/preferences/common/preferencesModels.ts assigns validator: createValidator(prop). SettingsTreeSettingElement.update in src/vs/workbench/contrib/preferences/browser/settingsTreeModels.ts retains the configured target value, and the object renderer passes dataElement.value to renderArrayValidations. The missing required-key check is therefore on the actual GUI validation path, not merely an unused helper.
