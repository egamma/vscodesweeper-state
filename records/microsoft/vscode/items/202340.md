# Issue #202340 — Feature: Debug console filters in settings.json

[https://github.com/microsoft/vscode/issues/202340](https://github.com/microsoft/vscode/issues/202340)

## Summary

Keep this accepted Backlog request open: it exceeded the 20-upvote threshold, and current main only remembers one user's filter in machine-local workspace storage rather than providing a team-shareable workspace setting.

## Change summary

Allow projects to define default Debug Console filter terms in workspace settings so every contributor receives the same filtering rules.

## Best solution

Provide a workspace-overridable Debug Console filter setting that initializes or composes with the interactive filter while preserving the existing per-user editing and persistence experience. A maintainer should first settle the setting shape and whether configured filters are defaults or enforced alongside user-entered filters.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`, `src/vs/workbench/contrib/debug/browser/repl.ts`, `src/vs/workbench/contrib/debug/test/browser/repl.test.ts`
- **Validation:** Add a targeted Debug Console test covering workspace-configured filter initialization and the chosen interaction with user-entered filter text, then run `scripts/test.sh --grep "Debug Console filter setting"`.
- **Behavior:**

  > A workspace can declare Debug Console filtering rules that apply when contributors open that workspace, without each contributor re-entering them. Matching and exclusion semantics remain consistent with the existing filter box. Changing the workspace configuration updates the effective filter according to the chosen precedence model, while workspaces without the setting retain today's persisted-filter behavior.
- **Trace:**

  > The Debug Console view is implemented by `Repl` in src/vs/workbench/contrib/debug/browser/repl.ts. Its constructor initializes `FilterViewPane` and `ReplFilter` from `debug.repl.filterValue`; `saveState()` persists that value with workspace scope but machine target, and `registerListeners()` currently reacts only to unrelated `debug.console.*` settings. Debug settings are registered in src/vs/workbench/contrib/debug/browser/debug.contribution.ts, where no filter property exists. `FilterWidget.setFilterText()` in src/vs/workbench/browser/parts/views/viewFilter.ts can update the visible input, and existing filter-expression coverage is in src/vs/workbench/contrib/debug/test/browser/repl.test.ts. Preserve existing matching syntax and manual filtering; the uncertainty begins at the public setting contract and its precedence relative to persisted user input. Related precedent: https://github.com/microsoft/vscode/issues/140315.
- **Open decisions:**
  - Should the workspace setting be a single string matching the Debug Console input syntax, or an array of independently authored filter terms as proposed in the issue?
  - Does the configured value act as an editable initial default that users can replace, or as a workspace baseline that remains composed with user-entered filter text?
