# Issue #302333 — Let CLI know about IME composition started

[https://github.com/microsoft/vscode/issues/302333](https://github.com/microsoft/vscode/issues/302333)

## Summary

Keep open: notifying a CLI before IME text is committed remains a distinct capability request, explicitly supported by a maintainer in the linked discussion. The ConPTY workaround fixes composition positioning, not the CLI-owned placeholder overlap that motivated this issue.

## Change summary

Let terminal applications detect the start of IME composition so they can hide their ghost text before committed input arrives.

## Best solution

Define a composition-notification contract usable by cooperating terminal applications, with matching CLI handling that hides placeholders during composition. Preserve ordinary terminal input semantics and establish compatibility and composition-completion behavior before implementation.

Commit and cancel compositions separately, verify the agreed completion behavior and exactly-once delivery of committed input, and confirm a nonparticipating shell receives no unsolicited composition bytes.
- **Behavior:**

  > A cooperating terminal application can learn that IME composition has started before committed characters arrive, allowing it to hide its own placeholder or ghost text. The requested improvement is distinct from composition positioning and clipping. Acceptance must cover starting, committing, and canceling composition, while preserving committed text delivery and behavior for applications that do not participate. The precise notification and completion contract remains to be agreed.
- **Trace:**

  > TerminalInstance in src/vs/workbench/contrib/terminal/browser/terminalInstance.ts forwards xterm onData and onBinary to process handling; XtermTerminal in src/vs/workbench/contrib/terminal/browser/xterm/xtermTerminal.ts wraps the renderer and explicitly leaves backing-process interaction outside its scope. Searches found no composition-start contract in these surfaces, terminal configuration, or terminal extension API declarations. The diagnosis in https://github.com/microsoft/vscode/issues/301609#issuecomment-4072207503 establishes the boundary: xterm holds the in-progress composition while the CLI owns and renders its placeholder. The follow-up at https://github.com/microsoft/vscode/issues/301609#issuecomment-4072217464 says matching CLI changes are required. An extension event alone would not establish delivery to the running CLI; the uncertainty starts at the transport and participation contract. Preserve ordinary input delivery and do not conflate this work with ConPTY positioning fixes. The listed API bridge files are relevant only if the chosen contract includes extension-host participation.
- **Open decisions:**
  - Should composition notification be a negotiated terminal protocol available to cooperating CLIs generally, or a VS Code extension-mediated integration contract?
  - Does the public contract expose only composition start, or also end and cancellation so participating applications can reliably restore their placeholders?
