# Issue #250388 — Should clicking on the element pill direct the user to the actual span element in the developer tools?

[https://github.com/microsoft/vscode/issues/250388](https://github.com/microsoft/vscode/issues/250388)

## Summary

The navigation gap remains on current main: activating an element attachment opens its serialized context in a text editor rather than revealing the selected DOM node. This team-authored polish request should remain open while the activation behavior and stale-element fallback are decided.

## Change summary

Let users navigate from an attached HTML-element pill to the corresponding element in browser Developer Tools, potentially through an additional action.

## Best solution

Define a consistent activation contract for browser-element attachments: provide a DevTools reveal action while retaining access to serialized context, with a clear fallback when the originating browser session or DOM node no longer exists.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/attachments/chatVariableEntries.ts`, `src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentWidgets.ts`, `src/vs/workbench/contrib/browserView/electron-browser/features/browserEditorChatFeatures.ts`, `src/vs/workbench/contrib/browserView/common/browserView.ts`, `src/vs/platform/browserView/electron-main/browserViewInspector.ts`
- **Validation:** In an Integrated Browser page, attach a DOM element to chat and verify the chosen pill action opens Developer Tools with that exact live node revealed; then navigate or close the originating browser and verify the agreed stale-element fallback without breaking access to serialized context.
- **Behavior:**

  > An element attachment offers predictable navigation back to the selected DOM element when its originating browser session and node are still available. Users must retain a way to inspect the serialized HTML/CSS context. If the browser or node has become unavailable, activation follows an explicit, non-failing fallback. Acceptance covers a live element, a removed element, navigation, and a closed browser editor.
- **Trace:**

  > ElementChatAttachmentWidget in src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentWidgets.ts routes activation to openElementAttachment, which opens attachment.value as a pinned text editor. IElementVariableEntry in src/vs/workbench/contrib/chat/common/attachments/chatVariableEntries.ts carries serialized HTML, styles, dimensions, and image data but no browser-view identity or live element reference. BrowserEditorChatIntegration._attachElementDataToChat in src/vs/workbench/contrib/browserView/electron-browser/features/browserEditorChatFeatures.ts receives both the browser model and elementData.elementId but omits that provenance from the attachment. IBrowserViewModel can toggle Developer Tools, and BrowserViewFrameInspector owns transient handles and highlighting, so the uncertainty begins at the product contract and lifetime boundary rather than basic browser capability. Preserve ordinary element attachments from providers that cannot supply live browser provenance, and do not change generic file/image attachment activation.
- **Open decisions:**
  - Should primary activation of a live element pill reveal it in Developer Tools, or should the existing serialized-context editor remain primary with a separate DevTools action?
  - When the originating browser session or DOM node is stale, should activation fall back automatically to serialized context or present the unavailable state before offering that fallback?
  - Is live navigation limited to Integrated Browser attachments, or must the attachment contract support extension-provided browser surfaces such as the original Live Preview workflow?
