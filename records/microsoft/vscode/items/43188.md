# Issue #43188 — Allow to open multiple workspaces in the same window

[https://github.com/microsoft/vscode/issues/43188](https://github.com/microsoft/vscode/issues/43188)

## Summary

Keep open: current workspace handling and macOS native tabs do not fully deliver multiple independent workspaces inside one cross-platform editor window. With 944 upvotes and continued concrete demand, this remains a substantial design request rather than a stale item or a duplicate of the newer proposals.

## Change summary

Allow multiple independent, potentially multi-root workspaces to remain accessible in one window, with identifiable workspace names and access to their configuration.

## Best solution

Design a cross-platform workspace container that preserves separate project settings, search scope, and working state while avoiding OS-window clutter. Establish its isolation and lifecycle contracts before implementation; combining windows must not be assumed to eliminate extension-host memory usage.

## Plan brief

- **Likely files:** `src/vs/platform/workspace/common/workspace.ts`, `src/vs/workbench/services/workspaces/electron-browser/workspaceEditingService.ts`, `src/vs/workbench/browser/actions/workspaceActions.ts`, `src/vs/workbench/electron-browser/desktop.contribution.ts`
- **Validation:** The plan should end with a runnable acceptance scenario opening two independently configured multi-root workspaces in one window, navigating between them, and verifying retained editor and terminal state, isolated settings and search results, configuration-file access, and the agreed close/reopen behavior. Compare resource usage with two separate windows rather than assuming a memory reduction.
- **Behavior:**

  > Users want multiple independent workspaces accessible inside one editor window without closing existing work or merging all folders into one workspace. Each workspace should remain identifiable and retain its project-specific context, including settings and search scope. Existing macOS native tabs and workspace-switching extensions are partial alternatives, not cross-platform coverage. Acceptance should demonstrate two independently configured multi-root workspaces with retained working state and access to each workspace's configuration; presentation and persistence semantics need agreement first.
- **Trace:**

  > IWorkspaceContextService and IWorkspace in src/vs/platform/workspace/common/workspace.ts describe one workspace with a folder array and one configuration URI. NativeWorkspaceEditingService.enterWorkspace() in src/vs/workbench/services/workspaces/electron-browser/workspaceEditingService.ts changes extension-host, storage and backup context rather than retaining parallel workspaces. window.nativeTabs in src/vs/workbench/electron-browser/desktop.contribution.ts is macOS-only, while workbench.action.openWorkspaceConfigFile in src/vs/workbench/browser/actions/workspaceActions.ts addresses the current workspace. These source paths establish the existing boundary but do not settle how several independent contexts should coexist. Preserve existing single-workspace and multi-root behavior; do not assume extension hosts can share state safely or that a single visible window implies lower memory use. https://github.com/microsoft/vscode/issues/324309 supplies a newer sidebar-based design proposal, and https://github.com/microsoft/vscode/issues/76904 addresses folder hierarchy rather than independent workspace lifecycles.
- **Open decisions:**
  - Should independent workspaces appear as whole-workbench tabs or sessions, as simultaneous Explorer groups, or support both presentations?
  - Which inactive-workspace state must remain live, particularly terminals and debug sessions, and what resource-saving suspension behavior is acceptable?
  - Must the initial capability support workspaces with different remote authorities in the same window, or can it initially be limited to compatible connection contexts?
  - Should the collection of open workspaces and their working state be restored together after closing and reopening the window?

## Evidence

- **Current workspace boundary:** src/vs/platform/workspace/common/workspace.ts exposes IWorkspaceContextService.getWorkspace() as one IWorkspace; IWorkspace contains a folder array and a single configuration URI. Multi-root folders therefore do not represent several independently configured workspaces.
- **Workspace transition lifecycle:** src/vs/workbench/services/workspaces/electron-browser/workspaceEditingService.ts:178-219, NativeWorkspaceEditingService.enterWorkspace(), stops extension hosts, enters the replacement workspace, switches storage and backup location, then restarts extension hosts or reloads for a remote authority. This is a workspace transition, not retention of several live workspace contexts.
- **Existing capabilities provide partial coverage:** src/vs/workbench/electron-browser/desktop.contribution.ts:299-305 registers window.nativeTabs only on macOS. src/vs/workbench/browser/actions/workspaceActions.ts:188-212 implements workbench.action.openWorkspaceConfigFile for the current workspace. These cover native window grouping and configuration-file access, not the central cross-platform multi-workspace request.
- **Discussion distinguishes workarounds from the request:** The supplied discussion explicitly rejects Project Manager and workspace-switcher extensions as substitutes because switching or opening separate windows does not retain independent workspaces together. Other comments distinguish multi-root folders from independent settings, search and indexing scopes; the macOS tabs workaround is acknowledged as platform-specific.
- **Canonical search:** Read-only GitHub searches for workspace tabs and multiple workspaces found no verified older issue owning this full request. https://github.com/microsoft/vscode/issues/31308 is older and open, but asks for folder and editor-tab colors, not independent workspace contexts.
- **Related proposals are not canonical duplicates:** https://github.com/microsoft/vscode/issues/76904 is open and proposes nested folder layout within one workspace. https://github.com/microsoft/vscode/issues/324309 is open and proposes full editing-context switching via a session sidebar, but was created in 2026, later than this 2018 report; it cannot replace this re-reviewed item as a duplicate canonical.
- **Demand and performance caveat:** The issue has 944 body upvotes and a Backlog milestone. The July 2026 comment reports six windows consuming substantial memory and an OOM incident, but does not establish that one-window presentation would safely remove duplicated extension hosts or their memory footprint.
