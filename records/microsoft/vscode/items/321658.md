## Evidence

- **Verified older canonical:** https://github.com/microsoft/vscode/issues/2809 is open and was created on 2016-02-09, before this report. Its original reproduction configures `typescript.tsdk` with a variable and receives an invalid-tsserver-path error because the variable remains literal. It requests variable evaluation for that setting and other path settings, covering the same observable failure on the same setting surface rather than merely related infrastructure.
- **Current and legacy settings share behavior:** extensions/typescript-language-features/src/configuration/configuration.electron.ts: readGlobalTsdk and readLocalTsdk read `js/ts.tsdk.path`, falling back to `typescript.tsdk`. Both pass through fixPathPrefixes, which expands only a leading home-directory prefix, not `${workspaceFolder}`.
- **Literal variable reaches filesystem lookup:** extensions/typescript-language-features/src/tsServer/versionProvider.electron.ts: loadVersionsFromSetting treats the supplied value as an absolute or relative path. RelativeWorkspacePathResolver.asAbsoluteWorkspacePath in extensions/typescript-language-features/src/utils/relativePathResolver.ts recognizes workspace-folder-name prefixes, not variable expressions; the fallback joins the literal expression beneath each workspace root.
- **Existing capability is a workaround, not expansion:** extensions/typescript-language-features/package.nls.json documents `./node_modules/typescript/lib` for `js/ts.tsdk.path`. This can select the workspace installation without `${workspaceFolder}`, but does not implement the requested variable substitution.
- **Related prior classification:** https://github.com/microsoft/vscode/issues/182545 explicitly reported workspace-variable expansion missing from `typescript.tsdk` and was classified as a feature request. It closed through the community-upvote process, not through a fix or a substantive as-designed decision, so it is neither a duplicate target nor grounds for declining this request.
