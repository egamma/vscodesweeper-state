# Issue #170369 — 3+ elements for "editor.language.colorizedBracketPairs"

[https://github.com/microsoft/vscode/issues/170369](https://github.com/microsoft/vscode/issues/170369)

## Summary

The existing setting still supports opening/closing pairs, not intermediate keywords colored at the same nesting level. Keep this accepted Backlog request open; neither the HTML-tag request nor the closed C/C++ request owns its full scope.

## Change summary

Support colorizing three or more related block keywords, such as Lua if/then/else/end, at the same nesting level.

## Best solution

Extend the editor's bracket-colorization model to represent intermediate block keywords without treating them as additional nested openings or terminating the enclosing block. Settle whether the configuration expresses ordered keyword sequences or opening/closing pairs with associated interior keywords before implementation.

- **Behavior:**

  > Users should be able to colorize intermediate keywords together with the opening and closing keywords of their enclosing block. Lua if/then/else/end and C/C++ #if/#else/#endif illustrate the goal: interior keywords should not introduce extra nesting or prematurely end the block. Existing two-element pair configurations must remain compatible. Acceptance cases must cover nested blocks and the agreed behavior for omitted or repeated intermediate keywords.
- **Trace:**

  > The setting schema in src/vs/editor/common/config/editorConfigurationSchema.ts exposes pairs, and validateBracketPairs in src/vs/editor/common/languages/languageConfigurationRegistry.ts rejects arrays longer than two. LanguageBracketsConfiguration constructs opening/closing relationships, while Parser.parseChild builds binary PairAstNode structures; no intermediate role is represented. The thread offers both ordered arrays and a bracketPair/colorizedToo object contract, without settling their different matching semantics. Preserve existing pair behavior and incremental parsing performance; changing language defaults or adding HTML-specific parsing is outside this request. https://github.com/microsoft/vscode/issues/159586 documents the #else limitation but is closed and is not a canonical; https://github.com/microsoft/vscode/issues/137504 concerns a different HTML-tag capability. Source inspection establishes the gap, but implementation and executable validation were not performed in this read-only review.
- **Open decisions:**
  - Should a multi-keyword configuration require an ordered sequence, or associate optional and potentially repeated interior keywords with an opening/closing pair?
  - Should the new configuration contract apply only to colorization, or should intermediate keywords also participate in bracket matching, navigation, and guides?
