# Issue #81782 — [json] allow $ref in confiuguration schemas

[https://github.com/microsoft/vscode/issues/81782](https://github.com/microsoft/vscode/issues/81782)

## Summary

The accepted Backlog request remains necessary: current main supports whole schema documents and references within schemas, but still has no path for a `json.schemas` association to select a subschema by JSON Pointer fragment.

## Change summary

Allow settings-based JSON schema associations to target a subschema through a `$ref` or URL fragment instead of requiring a whole schema document.

## Best solution

Define and implement fragment-aware schema associations so a relative or absolute `json.schemas[].url` such as `types.json#/definitions/items` loads the base document and applies the selected subschema, without changing existing whole-document associations.

## Plan brief

- **Likely files:** `extensions/json-language-features/client/src/jsonClient.ts`, `extensions/json-language-features/server/src/jsonServer.ts`, `extensions/json-language-features/client/src/test/schemaRequests.test.ts`, `extensions/json-language-features/server/package.json`, `extensions/json-language-features/server/package-lock.json`
- **Validation:** Add JSON language-feature integration coverage configuring a local `json.schemas[].url` ending in `#/definitions/items`; assert that validation and completion use only that subschema, then run `scripts/test-integration.sh --grep "subschema"` and retain a whole-file URL control.
- **Behavior:**

  > A workspace or folder setting may associate JSON files with a subschema selected by a JSON Pointer fragment, including a relative URL such as `./schemas/types.json#/definitions/items`. VS Code loads the base schema document and validates or completes against the selected subschema. Existing whole-document associations and references inside schema files continue to behave unchanged, and errors identify the base schema resource rather than treating the fragment as part of its file path.
- **Trace:**

  > Settings are collected in extensions/json-language-features/client/src/jsonClient.ts:getSettings and normalized by getSchemaId; relative URLs currently pass through `Uri.joinPath` as one string. extensions/json-language-features/server/src/jsonServer.ts:updateConfiguration forwards that URL to vscode-json-languageservice as the external schema URI. The language service registers and loads that URI as the schema root, while its existing fragment machinery primarily resolves references encountered inside loaded schema content. Upstream `$id` support landed through https://github.com/microsoft/vscode-json-languageservice/pull/107, but it did not add fragment selection for settings-based associations. Preserve whole-file URL behavior, trust checks, cache identities, and ordinary internal `$ref` resolution; the uncertainty starts at the intended public scope and ownership of fragment selection across the client/server boundary.
- **Open decisions:**
  - Should this public configuration contract cover only fragments in `json.schemas[].url`, or also relative external `$ref` values inside inline `json.schemas[].schema` objects and extension-contributed configuration schemas?

## Evidence

- **maintainer classification:** The maintainer confirmed that referring to subschemas from settings.json was unsupported, then classified this as a feature request in https://github.com/microsoft/vscode/issues/81782#issuecomment-537395299.
- **current source:** extensions/json-language-features/client/src/jsonClient.ts:getSchemaId resolves a relative `json.schemas[].url` by passing the complete string to `Uri.joinPath`; extensions/json-language-features/server/src/jsonServer.ts:updateConfiguration then forwards that URI as the registered schema root. Neither path separates or selects a JSON Pointer fragment.
- **language-service boundary:** The current vscode-json-languageservice implementation registers the normalized configuration URI as a SchemaHandle and loads that URI as the schema document; its registration path does not interpret the association URI as a request to expose only a selected subschema: https://github.com/microsoft/vscode-json-languageservice/blob/main/src/services/jsonSchemaService.ts.
- **partial prerequisite:** General `$id` reference support was implemented by https://github.com/microsoft/vscode-json-languageservice/pull/107 and closed https://github.com/microsoft/vscode/issues/92042, but that supports references inside schema content rather than selecting the root subschema of a `json.schemas` association.
- **canonical status:** The younger reports https://github.com/microsoft/vscode/issues/97662 and https://github.com/microsoft/vscode/issues/108875 were closed in favor of this issue. They therefore reinforce this issue as the canonical open request rather than providing an older duplicate target.
