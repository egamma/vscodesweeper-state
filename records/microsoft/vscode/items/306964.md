# Issue #306964 — Sessions App: Tiny window cuts off app

[https://github.com/microsoft/vscode/issues/306964](https://github.com/microsoft/vscode/issues/306964)

## Summary

Keep open for a broader responsive-layout design. Current main has partial narrow-window handling, but desktop windows still retain the desktop composition at tiny widths, and the team-authored issue remains the appropriate place to define the intended adaptation.

## Change summary

Make the Agents Window progressively hide or adapt workbench parts as the window shrinks instead of clipping the application below their combined minimum sizes.

## Best solution

Define a responsive desktop policy that preserves each part's minimum usable size by collapsing lower-priority surfaces in a deliberate order, then restores only automatically hidden surfaces when space returns while preserving explicit user visibility choices.

## Plan brief

- **Likely files:** `src/vs/sessions/browser/layoutPolicy.ts`, `src/vs/sessions/browser/workbench.ts`, `src/vs/sessions/contrib/layout/browser/desktopSessionLayoutController.ts`, `src/vs/sessions/contrib/layout/test/browser/desktopSessionLayoutController.test.ts`
- **Validation:** Extend the desktop layout-controller tests with constrained-width transitions that verify the selected parts collapse in the agreed order, explicit user-hidden state is preserved, and automatically hidden parts return when space becomes available; validate the final composition at the issue's approximately 452x185 viewport.
- **Behavior:**

  > When the Agents Window becomes narrower or shorter than the combined usable dimensions of its visible parts, it must adapt rather than clip or squeeze those parts below their minimum sizes. Lower-priority surfaces should disappear in a predictable order, the primary session surface must remain usable, and automatically hidden surfaces should return as space becomes available. Explicit user visibility choices and multi-session behavior must remain intact.
- **Trace:**

  > The desktop grid is assembled in src/vs/sessions/browser/workbench.ts from independently constrained parts. src/vs/sessions/browser/layoutPolicy.ts reserves phone composition for mobile platforms, so an arbitrarily narrow Electron window remains in desktop mode. LayoutController._registerResponsiveSidebar in src/vs/sessions/contrib/layout/browser/desktopSessionLayoutController.ts handles only the case where sidebar, editor, and auxiliary bar compete below 1800px; commit https://github.com/microsoft/vscode/commit/adc7ecf823aa5a7de0effea1c742ee73ef1a3dad and its D7 tests establish that partial behavior. Planning should preserve D7's manual-toggle and restoration semantics, avoid changing session/provider state, and determine where broader responsive composition begins.
- **Open decisions:**
  - At constrained desktop widths, which visible surfaces should collapse first, and what minimum usable composition must remain?
  - Should an extremely narrow desktop window transition to the phone-style single-surface composition, or use a distinct progressive desktop layout?
  - Should height constraints independently collapse the panel or other vertical surfaces, and in what order?

## Evidence

- **maintainer intent:** The team-authored report explicitly proposes responsive hiding and showing while honoring part minimum widths, and the maintainer response at https://github.com/microsoft/vscode/issues/306964#issuecomment-4166191301 supports exploring responsive and mobile Sessions layouts.
- **partial implementation:** Commit https://github.com/microsoft/vscode/commit/adc7ecf823aa5a7de0effea1c742ee73ef1a3dad added experimental responsive sidebar collapse, but it does not reference this issue and only hides the sidebar when the editor and auxiliary bar are both visible.
- **remaining gap:** src/vs/sessions/browser/layoutPolicy.ts deliberately classifies Electron and desktop web as `desktop` regardless of width, while src/vs/sessions/contrib/layout/browser/desktopSessionLayoutController.ts uses a single 1800px threshold for one sidebar scenario. Tiny desktop widths therefore have no general policy for progressively adapting all competing parts.
- **minimum-size constraints:** The current parts independently enforce minimum widths, including 300px for SessionsPart, 300px for CustomViewGridPart, 200px for session/chat views, and the editor and sidebar minimums in src/vs/sessions/browser/parts; the desktop grid in src/vs/sessions/browser/workbench.ts composes these surfaces without a complete small-viewport fallback.
