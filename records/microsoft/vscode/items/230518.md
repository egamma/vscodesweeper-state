# Issue #230518 — Allow grouping of `package.nls*.json` files in a custom folder

[https://github.com/microsoft/vscode/issues/230518](https://github.com/microsoft/vscode/issues/230518)

## Summary

Keep open: configurable manifest-translation placement remains unsupported, and a maintainer supports the change pending web and Marketplace coordination. The suggested older duplicate is closed, leaving this issue as the remaining tracking item.

## Change summary

Allow extension authors to place package.nls.json and its locale variants in a configurable subdirectory.

## Best solution

Provide a backward-compatible manifest localization-location contract shared by desktop, web, and Marketplace, following the maintainer's preference for separate package and bundle paths under l10n. Establish Marketplace compatibility before committing to a rollout.

- **Behavior:**

  > Extension authors should be able to group default and locale-specific manifest translations in a configured subdirectory without displaying unresolved %translation.keys%. Desktop and web installations must resolve those translations consistently, including fallback text. Existing root-level package.nls files and string-valued l10n bundle configurations must continue to work. The published extension's Marketplace metadata must remain localized under the agreed compatibility contract.
- **Trace:**

  > ExtensionsScanner.getLocalizedMessages and findMessageBundles in src/vs/platform/extensionManagement/common/extensionsScannerService.ts resolve manifest translation files directly under extensionLocation. The web scanner in src/vs/workbench/services/extensionManagement/browser/webExtensionsScannerService.ts obtains translation resources from gallery listings and uses a root-level fallback for other discovery paths. IExtensionManifest in src/vs/platform/extensions/common/extensions.ts and the manifest schema in src/vs/workbench/services/extensions/common/extensionsRegistry.ts currently expose l10n only as a bundle-directory string. The maintainer prefers package and bundle paths under an l10n object, accepted by the reporter, but identifies Marketplace compatibility as unresolved: https://github.com/microsoft/vscode/issues/230518#issuecomment-2394167886. Preserve existing manifest localization, locale fallback, and runtime bundle behavior; this is a new location contract, not a defect in the existing root-layout contract. The older same-request issue, https://github.com/microsoft/vscode/issues/169150, is closed and does not replace this tracking item. Source inspection establishes the missing capability, but does not establish Marketplace's current support or the final rollout contract.
- **Open decisions:**
  - Must custom manifest-translation directories wait for native Marketplace support, or may an initial publishing contract retain a root-level compatibility copy while source translations live in the configured directory?
