# Issue #320389 — VSCode seems it does not respect my profiles when starting some extensions

[https://github.com/microsoft/vscode/issues/320389](https://github.com/microsoft/vscode/issues/320389)

## Summary

Keep open: current main can still replace the initiating window's profile with a stored workspace profile while opening a remote window, matching the reported switch to Default and the workspace-level exception.

## Change summary

Opening a WSL target from Remote Explorer can switch from the active profile to Default before resolving the remote authority, leaving the required WSL extension unavailable.

## Best solution

Define and test profile precedence for extension-initiated remote opens so the profile containing the remote resolver remains active through connection establishment, without unintentionally breaking deliberate workspace-profile associations.

## Plan brief

- **Likely files:** `src/vs/platform/windows/electron-main/windowsMainService.ts`, `src/vs/platform/userDataProfile/electron-main/userDataProfile.ts`, `src/vs/platform/userDataProfile/test/electron-main/userDataProfileMainService.test.ts`
- **Validation:** Add coverage for opening a remote workspace from a non-Default profile when that workspace is unassociated and when it is already associated with Default, then manually verify the supplied WSL Remote Explorer steps keep the resolver extension available through connection establishment.
- **Behavior:**

  > Starting a WSL connection from a profile where WSL is installed must not switch to Default before the remote authority is resolved. The initiating profile's extensions must remain available during connection establishment, and closing the remote connection must not unexpectedly leave the local window on Default. Existing, deliberate workspace-profile associations need a documented precedence rule and corresponding coverage.
- **Trace:**

  > The extension host reports the terminal error from src/vs/workbench/api/common/extHostExtensionService.ts when the selected profile has no extension capable of resolving the WSL authority. In src/vs/platform/windows/electron-main/windowsMainService.ts, openInBrowserWindow computes the initiating/last-active profile as defaultProfile, but resolveProfileForBrowserWindow prefers userDataProfilesMainService.getProfileForWorkspace(workspace), which can replace it with Default. The reporter's observation that behavior changes after opening the remote folder under another profile corroborates that association path. The uncertainty begins at the intended precedence between an explicitly active initiating profile and an existing workspace association; preserve normal local workspace restoration and explicit --profile behavior.
- **Open decisions:**
  - When a remote connection is initiated from one profile but the target workspace is associated with another, which profile should own authority resolution and the resulting remote window?

## Evidence

- **current source:** In src/vs/platform/windows/electron-main/windowsMainService.ts, openInBrowserWindow derives a fallback from the last active window's profile, but resolveProfileForBrowserWindow returns getProfileForWorkspace(workspace) before that fallback. An existing Default-profile association can therefore override the profile initiating the remote open.
- **reported exception:** The reporter says reopening begins to work after the remote folder has been opened and associated with the non-Default profile. That directly matches the workspace-association precedence in resolveProfileForBrowserWindow.
- **failure point:** src/vs/workbench/api/common/extHostExtensionService.ts emits “No remote extension installed to resolve …” when no extension in the selected profile registers the remote authority resolver; selecting Default without WSL reaches this path.
- **reported-build comparison:** The reported commit 6a44c352bd24569c417e530095901b649960f9f8 contains the same last-active-profile fallback and workspace-profile precedence, so current source has not clearly eliminated the implicated behavior.
