# Issue #232941 — Ability to Temporarily Lock Folders in Workspace

[https://github.com/microsoft/vscode/issues/232941](https://github.com/microsoft/vscode/issues/232941)

## Summary

Keep this accepted request open: read-only settings provide edit protection, but current Explorer menus still lack the requested folder-level toggle. It has 25 upvotes and a Backlog milestone; no verified older canonical was found.

## Change summary

Provide an Explorer folder-menu option to temporarily protect inactive project folders from accidental edits, with feedback when protection is encountered.

## Best solution

Expose reversible folder-level protection through the existing read-only machinery in the file Explorer. Settle whether this means edit protection or blocking access, and whether protection lasts only for the session, before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/fileActions.ts`, `src/vs/workbench/contrib/files/browser/fileActions.contribution.ts`, `src/vs/workbench/services/filesConfiguration/common/filesConfigurationService.ts`, `src/vs/workbench/services/filesConfiguration/test/browser/filesConfigurationService.test.ts`
- **Validation:** After agreeing on semantics, test folder protection against existing and newly created descendants, sibling folders, pre-existing read-only rules, and unlock/reset. Manually exercise the Explorer folder action in a two-root workspace, including an already-open descendant editor, the chosen notification behavior, and reload lifetime; run the targeted FilesConfigurationService unit suite.
- **Behavior:**

  > Users can reversibly protect an inactive project folder from its Explorer context menu without manually editing settings. Protection must cover descendants, including files already open and files created after protection is enabled, while leaving unrelated folders unchanged. Removing temporary protection must preserve any pre-existing read-only restrictions. Acceptance must specify whether protected files remain readable, when feedback appears, and whether the protection survives reload.
- **Trace:**

  > files.contribution.ts registers files.readonlyInclude and files.readonlyExclude, providing existing glob-based edit protection. fileActions.ts exposes session read-only commands through BaseSetActiveEditorReadonlyInSession, but the commands target only the active editor resource. fileActions.contribution.ts has no corresponding folder action in its ExplorerContext registrations. FilesConfigurationService.isReadonly consults an exact-resource sessionReadonlyOverrides map before configured glob matching, so a folder override alone does not imply descendant protection. The discussion at https://github.com/microsoft/vscode/issues/232941 establishes Explorer discoverability as a remaining gap, while the original body also requests feedback on access. Preserve existing provider read-only restrictions and unrelated configuration; this is accidental-edit protection, not an OS permission or security boundary. Uncertainty begins with the intended access behavior and lifetime, not with whether existing settings already satisfy the menu request.
- **Open decisions:**
  - Should folder protection allow browsing and reading while preventing edits, or require an explicit override before accessing protected contents; when should feedback appear?
  - Should temporary folder protection end when the window session ends, or persist across reload until explicitly unlocked?
