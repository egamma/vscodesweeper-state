# Issue #197811 — Allow to recover backups from extension provided file systems if extension uninstalled

[https://github.com/microsoft/vscode/issues/197811](https://github.com/microsoft/vscode/issues/197811)

## Summary

Keep open: current source still ties normal backup restoration to an available file-system provider, leaving the clarified recovery request unresolved. The maintainer accepted this direction, and no verified canonical or completed fix was found.

## Change summary

Allow users to recover locally stored hot-exit contents when the extension providing the original file-system scheme is unavailable.

## Best solution

Provide a discoverable, provider-independent way to inspect and save recoverable text backup contents without recreating the original URI. Preserve existing hot-exit behavior and distinguish recovery from successfully reconnecting to the original file system.

## Plan brief

- **Likely files:** `src/vs/workbench/services/workingCopy/common/workingCopyBackupTracker.ts`, `src/vs/workbench/contrib/files/browser/editors/fileEditorHandler.ts`, `src/vs/workbench/contrib/files/browser/editors/fileEditorInput.ts`, `src/vs/workbench/services/textmodelResolver/common/textModelResolverService.ts`, `src/vs/workbench/services/textfile/common/textFileEditorModel.ts`, `src/vs/workbench/contrib/files/browser/fileActions.ts`
- **Validation:** In a normal desktop window, install a minimal MemFS extension, edit a virtual file without saving, exit with hot exit enabled, make the extension unavailable, and reopen the same window. Verify the chosen recovery interaction exposes the exact unsaved text and permits saving it to a local file; verify declining recovery preserves the backup and restoring the provider still permits normal recovery. Do not use an extension-development window, where the thread notes hot exit is disabled.
- **Behavior:**

  > Users must be able to recover unsaved text retained by hot exit even when the extension providing the original file-system scheme has been uninstalled or no longer registers that scheme. Recovery must not require the original external session or URI to become usable again. The recovered contents must be inspectable and savable elsewhere without implying that saving to the original resource succeeded. Existing recovery with a registered provider, including unavailable original files, must remain unchanged.
- **Trace:**

  > The remaining scope is established by https://github.com/microsoft/vscode/issues/197811#issuecomment-1809713724, not the initial request to disable hot exit for virtual files. FileEditorWorkingCopyEditorHandler.handles delegates to FileService.canHandleResource, which requires a registered provider after activation; WorkingCopyBackupTracker.restoreBackups skips unhandled backups. TextFileEditorModel.doResolve can load backup contents before reading the original file, but FileEditorInput.doResolveAsText subsequently obtains a model reference, and ResourceModelCollection.doCreateReferencedObject in textModelResolverService.ts rejects a scheme without a provider. These paths establish the normal-restoration boundary; no provider-independent recovery action was found in the inspected file commands. Preserve backup retention, provider activation, and ordinary save semantics rather than globally disabling hot exit or treating extension uninstallation as grounds to discard edits. The maintainer proposed raw-content recovery at https://github.com/microsoft/vscode/issues/197811#issuecomment-1804030372; the unresolved part is its user-facing recovery and consumption contract. Notebook backup formats are related precedent, not automatically part of this text-file request.
- **Open decisions:**
  - Should provider-independent recovery be an explicit action on the failed editor, or should the backed-up text automatically open in a separate recovery editor?
  - Should recovery leave the original backup available until explicitly discarded, or consume it after the user successfully saves the recovered contents elsewhere?

## Evidence
