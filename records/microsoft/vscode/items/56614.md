# Issue #56614 — Allow extensions to be installed for all users

[https://github.com/microsoft/vscode/issues/56614](https://github.com/microsoft/vscode/issues/56614)

## Summary

Keep open: Windows extension bootstrapping now addresses first-launch provisioning, but it installs per-user copies rather than providing a supported shared installation for all users. The thread also establishes Linux lab requirements and centralized-management needs that this capability does not cover.

## Change summary

Provide a supported way for administrators to install extensions once and make them available to every user of a machine.

## Best solution

Define a supported machine-wide extension deployment model that coexists with personal extensions and specifies administrator updates and user overrides. Build on the existing Windows bootstrap experience without treating per-user provisioning or installation into the built-in extension directory as full coverage.

- **Trace:**

  > DefaultExtensionsInitializer in src/vs/code/electron-utility/sharedProcess/contrib/defaultExtensionsInitializer.ts processes bootstrap/extensions only on Windows and installs VSIX files through the existing extension management service, with completion tracked in application storage. NativeEnvironmentService in src/vs/platform/environment/common/environmentService.ts exposes a built-in location and one configurable user-extension root; ExtensionsScannerService in src/vs/platform/extensionManagement/node/extensionsScannerService.ts passes both to the scanner. The CLI registrations in src/vs/platform/environment/node/argv.ts expose --extensions-dir and --install-extension but no all-users mode. Comments confirm that placing extensions in resources/app/extensions makes them available as built-ins, with different listing and uninstall behavior. https://github.com/microsoft/vscode/issues/158801 records maintainer concern about the wider effects of multiple extension roots, but is closed and does not absorb this issue. Preserve ordinary per-user installation and existing Windows bootstrap semantics; uncertainty begins at the product contract for shared storage, precedence, and lifecycle management.
- **Open decisions:**
  - Should all-users deployment provide one administrator-owned shared installation alongside personal extensions, or provision independent per-user copies?
  - How should administrator-installed extensions interact with user-installed versions, disabling, and uninstalling?
  - Should the supported deployment contract cover Windows and Linux together, or explicitly stage platform support?

## Evidence

- **Existing supported capability:** https://code.visualstudio.com/docs/enterprise/extensions#_preinstall-extensions documents Windows-only provisioning from bootstrap\extensions. VSIX files are installed silently on each user's first launch; users can uninstall them without automatic reinstallation. This covers provisioning but not a single shared installation or Linux deployment.
- **Current bootstrap implementation:** src/vs/code/electron-utility/sharedProcess/contrib/defaultExtensionsInitializer.ts gates initialization on isWindows and application storage, discovers bootstrap/extensions, and invokes extensionManagementService.install for each VSIX. src/vs/code/electron-utility/sharedProcess/sharedProcessMain.ts instantiates DefaultExtensionsInitializer. This is an adopted capability, but not a machine-wide installation mode.
- **Current extension locations and CLI:** src/vs/platform/environment/node/argv.ts registers --extensions-dir and --install-extension, but no all-users installation flag. src/vs/platform/environment/common/environmentService.ts resolves extensionsPath from --extensions-dir, VSCODE_EXTENSIONS, portable storage, or the user's home; builtinExtensionsPath is separate. src/vs/platform/extensionManagement/node/extensionsScannerService.ts supplies those system and user locations to the scanner. Selecting a shared user-extension root replaces the personal root rather than introducing an independently managed shared layer.
- **Discussion establishes partial workarounds:** The Ubuntu lab report describes network home directories and avoiding hundreds of duplicate installations. https://github.com/microsoft/vscode/issues/56614#issuecomment-2396645710 confirms code.cmd installation into resources/app/extensions but reports built-in uninstall restrictions and missing --list-extensions results. https://github.com/microsoft/vscode/issues/56614#issuecomment-2879109132 confirms offline VSIX deployment on 1.100.0, with extensions classified as built-in rather than ordinary installed extensions. These are meaningful workarounds, not equivalent lifecycle support.
- **Related issue is not a canonical:** https://github.com/microsoft/vscode/issues/158801 is closed and requests multiple extension directories or --static-extensions-dir. https://github.com/microsoft/vscode/issues/158801#issuecomment-1232571895 says the concept requires thorough discussion because it affects other features.
