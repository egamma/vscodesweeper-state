# Issue #155874 — File Decorations for Search Folders 

[https://github.com/microsoft/vscode/issues/155874](https://github.com/microsoft/vscode/issues/155874)

## Summary

Search folders still lack decorations scoped to their search-result descendants; the existing decoration settings cover individual file results only. Keep this accepted, team-authored request open, with the author's question about combining different child decorations requiring a product decision.

## Change summary

Show search-folder decorations derived only from files represented in the search results, rather than all files under the directory.

## Best solution

Define how folders summarize different decorations among their search-result descendants, then provide that result-scoped summary consistently for ordinary and compressed folder rows without changing Explorer decoration behavior.

## Vision fit

- **Fit:** aligned
- **Reason:** Result-scoped folder indicators would make the search hierarchy more informative and consistent with its decorated file rows.
- **Evidence:** Public values: "Simple, uniform UI and UI interactions"; durable themes: Workbench & core UX and Developer inner loop.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/search/browser/searchResultsView.ts`, `src/vs/workbench/contrib/search/browser/searchTreeModel/folderMatch.ts`, `src/vs/workbench/browser/labels.ts`, `src/vs/workbench/services/decorations/browser/decorationsService.ts`
- **Validation:** After choosing aggregation semantics, exercise ordinary, workspace-root, and compressed search-folder rows with differently decorated matching descendants and a decorated nonmatching sibling. Verify that only result members influence the folder summary, removing a result updates it, search.decoration settings remain respected, and Explorer decorations remain unchanged.
- **Behavior:**

  > Search-folder indicators should summarize decorations belonging to files represented in that folder's search results, excluding nonmatching files elsewhere under the directory. The same policy should apply to workspace-root folders and compressed folder rows. Acceptance should cover differently decorated descendants, a decorated nonmatching sibling, result removal, and the existing search.decorations.colors and search.decorations.badges settings. The presentation for mixed child decorations requires maintainer agreement.
- **Trace:**

  > FolderMatchRenderer.renderElement and renderCompressedElements in src/vs/workbench/contrib/search/browser/searchResultsView.ts currently render folder labels without fileDecorations, while FileMatchRenderer enables decorations using the search settings. ResourceLabel rendering in src/vs/workbench/browser/labels.ts requests descendant bubbling for folders; DecorationsService.getDecoration in src/vs/workbench/services/decorations/browser/decorationsService.ts aggregates cached bubbling descendants without knowing search membership. FolderMatchImpl.allDownstreamFileMatches in src/vs/workbench/contrib/search/browser/searchTreeModel/folderMatch.ts identifies the relevant result files. Preserve individual-file decoration behavior and generic Explorer semantics. The author explicitly left mixed-decoration presentation open in https://github.com/microsoft/vscode/issues/155874; the merged https://github.com/microsoft/vscode/pull/155549 covers file rows rather than this remaining behavior.
- **Open decisions:**
  - When result descendants have different decoration colors or badges, what single folder indicator should users see: a precedence-selected decoration, a neutral mixed-state indicator, or another defined summary?

## Evidence

- **Current capability and remaining gap:** src/vs/workbench/contrib/search/browser/search.contribution.ts registers search.decorations.colors and search.decorations.badges, both enabled by default. FileMatchRenderer.renderElement in searchResultsView.ts passes these settings through fileDecorations, but FolderMatchRenderer.renderElement and renderCompressedElements do not enable decorations or compute a result-scoped summary.
- **Why enabling folder decorations alone is insufficient:** src/vs/workbench/browser/labels.ts obtains folder decorations through decorationsService.getDecoration(resource, true). In src/vs/workbench/services/decorations/browser/decorationsService.ts, getDecoration collects bubbling decorations from cached descendants beneath the URI without a search-result membership filter, matching the limitation described by the author.
- **Maintainer intent and unresolved behavior:** https://github.com/microsoft/vscode/issues/155874 was filed by a MEMBER and is accepted in Backlog. In the supplied December 4, 2023 comment, the author explicitly asks to discuss the correct folder decoration when children have multiple different decorations; the record does not settle that behavior.
- **Referenced implementation is narrower:** https://github.com/microsoft/vscode/pull/155549 is merged and added decorations to search file results, fixing https://github.com/microsoft/vscode/issues/115741. It does not establish implementation of this issue's result-scoped folder aggregation.
- **Canonical search:** Read-only open-issue searches using search/folder/directory/decoration terminology found no verified older canonical for this request. https://github.com/microsoft/vscode/issues/187756 concerns extension-versus-Git decoration precedence, and https://github.com/microsoft/vscode/issues/162283 concerns badge-setting terminology; neither owns result-scoped folder summaries, and both are newer than this re-reviewed issue.
- **Result membership boundary:** src/vs/workbench/contrib/search/browser/searchTreeModel/folderMatch.ts exposes FolderMatchImpl.allDownstreamFileMatches(), providing the search-model descendant set relevant to this request. The unresolved part is the observable aggregation policy, not whether generic directory decoration bubbling already satisfies the request.
