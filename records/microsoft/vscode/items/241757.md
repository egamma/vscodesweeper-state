# Issue #241757 — Allow me to drag and drop a diff editor into chat/edits

[https://github.com/microsoft/vscode/issues/241757](https://github.com/microsoft/vscode/issues/241757)

## Summary

This remains a real gap on current main: editor-tab drag data preserves both sides of a diff, but chat attachment resolution rejects the resource-less composite input. The Backlog milestone and existing area labels support keeping it open while the desired attachment semantics are decided.

## Change summary

Allow dropping a diff editor into chat so a Git diff contributes its changed content and an arbitrary comparison contributes both files.

## Best solution

Preserve the diff editor's structure when it is dropped into chat, representing Git-backed comparisons as useful change context and arbitrary comparisons as two clearly identified file attachments. A maintainer should first settle whether Git diffs attach the modified file, a patch, or both.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/dnd.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatDragAndDrop.ts`, `src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentResolveService.ts`, `src/vs/workbench/contrib/chat/test/browser/chatAttachmentResolveService.test.ts`
- **Validation:** Add targeted chat attachment tests that pass transferred resource diff inputs through the drop-resolution path and assert the approved attachment representation for both a Git-backed diff and two arbitrary files.
- **Behavior:**

  > Dragging a diff editor tab onto the chat input must produce usable context instead of silently attaching nothing. For a comparison between arbitrary files, both sides must remain identifiable. For a Git-backed comparison, the resulting context must follow the maintainer-approved representation while preserving the changed content. Ordinary file, directory, image, browser, and untitled-editor drops must remain unchanged.
- **Trace:**

  > Editor tabs call `fillEditorsDragData` in src/vs/workbench/browser/parts/editor/editorTabsControl.ts. `DiffEditorInput.toUntyped` in src/vs/workbench/common/editor/diffEditorInput.ts retains `original` and `modified`, but `fillEditorsDragData` in src/vs/workbench/browser/dnd.ts assigns a top-level canonical resource that is undefined for composite diff inputs. `extractEditorsDropData` preserves that payload, and `ChatDragAndDrop.resolveAttachmentsFromDragEvent` forwards it to `ChatAttachmentResolveService.resolveEditorAttachContext`, which exits when `editor.resource` is absent without inspecting either diff side. The boundary is diff-editor attachment handling; do not alter normal editor drag behavior or collapse arbitrary comparisons to only one side.
- **Open decisions:**
  - For a Git-backed diff, should chat receive only the modified file, a patch representing the diff, or both forms of context?
  - Should the two sides of an arbitrary diff appear as separate file attachments or as one structured comparison attachment?

## Evidence

- **current source gap:** src/vs/workbench/common/editor/diffEditorInput.ts exposes `modified` and `original` from `DiffEditorInput.toUntyped`, while src/vs/workbench/common/editor.ts makes `EditorResourceAccessor.getCanonicalUri` return undefined for a diff unless side-by-side handling is explicitly requested.
- **drop path:** src/vs/workbench/browser/dnd.ts serializes the complete untyped editor but assigns that undefined canonical `resource`; src/vs/workbench/contrib/chat/browser/widget/chatDragAndDrop.ts then passes the transferred editor to `resolveEditorAttachContext`.
- **attachment rejection:** src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentResolveService.ts returns undefined whenever a transferred editor has no top-level `resource`, so the preserved `original` and `modified` inputs are not attached.
