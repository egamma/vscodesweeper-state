# Issue #97643 — Make editor.action.marker.nextInFiles prioritize severe issues

[https://github.com/microsoft/vscode/issues/97643](https://github.com/microsoft/vscode/issues/97643)

## Summary

Keep open: current commands support file-local navigation and cursor-based positioning, but still cycle into warnings while errors remain. The related request for explicit severity selection does not fully cover this request's automatic highest-severity-only behavior.

## Change summary

Allow problem navigation to cycle only through the highest severity present in the current file, falling back to lower severities only after higher-severity problems are resolved.

## Best solution

Provide an opt-in highest-severity-only navigation mode in the editor marker-navigation area, preserving existing navigation defaults. Reuse existing file-local commands and position ordering rather than introducing redundant commands for capabilities already available.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/gotoError/browser/markerNavigationService.ts`, `src/vs/editor/contrib/gotoError/browser/gotoError.ts`, `src/vs/workbench/contrib/markers/browser/markers.contribution.ts`
- **Validation:** With the proposed mode enabled, create a file containing two errors, a warning, and an information diagnostic. Repeated file-local next/previous navigation must cycle only among errors; removing all errors must switch to warnings, and removing all warnings must switch to information diagnostics. Verify cursor-relative navigation under position ordering, isolation from diagnostics in another file, and unchanged behavior with the mode disabled.
- **Behavior:**

  > The requested opt-in behavior navigates only among the highest-severity problems remaining in the current file. While any errors remain, repeated next/previous navigation wraps among errors and never selects a warning or information diagnostic. Once errors are resolved, navigation falls back to warnings, then information diagnostics. Existing file-local commands and cursor-relative position ordering remain available, and users who do not opt in retain current behavior.
- **Trace:**

  > MarkerController.navigate in src/vs/editor/contrib/gotoError/browser/gotoError.ts already distinguishes file-local from workspace-wide commands and initializes navigation using the editor position. MarkerList in src/vs/editor/contrib/gotoError/browser/markerNavigationService.ts collects all error, warning, and information markers, sorts them according to problems.sortOrder, and cycles through the entire list. That confirms the missing capability is severity-exclusive cycling with automatic fallback, not file-local scope or ordinary severity sorting. The existing setting is registered in src/vs/workbench/contrib/markers/browser/markers.contribution.ts. Preserve existing defaults and do not alter diagnostic production or Problems-view filtering. https://github.com/microsoft/vscode/issues/105795 concerns explicit severity selection and is related, but does not settle the opt-in contract for this automatic behavior. The remaining uncertainty is how users select the mode and whether its contract also extends to workspace-wide commands.
- **Open decisions:**
  - Should highest-severity-only navigation be selected through a setting affecting existing commands or through separate opt-in commands?
  - Should the opt-in behavior apply only to file-local navigation, as clarified by the reporter, or also to workspace-wide navigation using the highest severity across the workspace?

## Evidence

- **Clarified requirement:** The reporter's clarification on https://github.com/microsoft/vscode/issues/97643 asks for file-local navigation that wraps among errors while any errors remain, then among warnings when errors are exhausted. The maintainer's earlier explanation establishes severity ordering, not this severity-exclusive cycling behavior.
- **Existing file-local capability:** src/vs/editor/contrib/gotoError/browser/gotoError.ts registers editor.action.marker.next and editor.action.marker.prev with multiFile=false. MarkerController.navigate consequently requests a MarkerList restricted to the current model URI; nextInFiles and prevInFiles intentionally use the workspace-wide list.
- **Remaining source-level gap:** In src/vs/editor/contrib/gotoError/browser/markerNavigationService.ts, MarkerList reads Error | Warning | Info together. Its severity comparator orders markers but does not exclude lower severities, and move advances modulo the entire marker list. Repeated navigation therefore reaches warnings even when errors remain in the file.
- **Cursor and ordering capabilities:** MarkerController resets the navigation index when the cursor leaves the selected marker; MarkerList._initIdx initializes navigation from the cursor position. src/vs/workbench/contrib/markers/browser/markers.contribution.ts registers problems.sortOrder with severity and position options. Position ordering addresses the supplementary cursor-relative request, but neither option provides highest-severity-only cycling. https://github.com/microsoft/vscode/issues/135249 is closed and documents the position-ordering capability, not a fix for the remaining requirement here.
- **Canonical search:** Verified https://github.com/microsoft/vscode/issues/105795 is open and requests separate error/warning/info navigation groups. Its comment https://github.com/microsoft/vscode/issues/105795#issuecomment-1264500714 explicitly links this issue for automatic severity prioritization. Explicit severity selection and automatic fallback are different observable behaviors, so that issue does not establish full duplicate coverage. Searches for next-error and severity-navigation requests found no other verified canonical covering the complete ask.
- **Existing workaround:** https://github.com/microsoft/vscode/issues/105795#issuecomment-1130836242 recommends the yy0931.go-to-next-error extension. The later comment at https://github.com/microsoft/vscode/issues/105795#issuecomment-1264500714 notes that it requires multiple bindings rather than the requested single-command automatic fallback; extension availability does not establish a maintainer decision to exclude this capability from core.
