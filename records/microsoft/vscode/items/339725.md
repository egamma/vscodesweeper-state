# Issue #339725 — Different rendering of /plugin commands

[https://github.com/microsoft/vscode/issues/339725](https://github.com/microsoft/vscode/issues/339725)

## Summary

Screenshots show a real rendering inconsistency between manually-typed and completion-accepted `/plugin` slash commands, but the root cause isn't pinned down from source alone — this needs a live debugging session (checking whether it's the custom slash-command decoration, Monaco's own selection/typeahead rendering after a completion commit, or a race in the throttled decoration update) rather than a static fix.

## Change summary

Typing a `/plugin <subcommand>` slash command manually renders differently (no highlight) than accepting it via IntelliSense suggestions (blue background highlight), and a third, partially-highlighted state was seen once but isn't reliably reproducible.

## Best solution

Trace live in a dev build whether InputEditorDecorations (src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputEditorContrib.ts, slashCommandTextDecorationType) is actually being applied consistently after a completion commit vs. manual typing, or whether the highlight in the screenshots is really Monaco's post-completion selection/typeahead rendering bleeding through; fix the decoration update path (or the completion's insertText/range) once the mechanism is confirmed.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputEditorContrib.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts`
- **Validation:** After the diagnosis, a manual check: type a `/plugin <subcommand>` fully by hand vs. accept it via the suggestion list, and confirm both render identically with the slash-command highlight; add an editor decoration test if a concrete throttling/race bug is found.
- **Behavior:**

  > A `/plugin <subcommand>` entry in the chat input box should render identically (same highlight/background) regardless of whether the user typed every character or accepted it from the IntelliSense suggestion list. Currently the manually-typed version shows as plain text while the suggestion-accepted version shows the blue slash-command highlight, and an intermittent partially-highlighted state has also been observed once.
- **Trace:**

  > The custom highlight comes from InputEditorDecorations.updateAsyncInputEditorDecorations in src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputEditorContrib.ts, which is throttled 200ms behind onDidChangeModelContent and depends on this.widget.parsedInput.parts recognizing the agent/slash-command part. Completions for `/plugin` are inserted in src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts. It is not established from source whether the blue highlight seen after accepting a completion is this decoration applying earlier/more reliably than for manual typing, or is unrelated Monaco selection/typeahead rendering left over from the completion commit — that distinction is where the uncertainty starts, and determining it requires watching the live editor/decoration state, not just reading the code. Do not assume the fix lives in the decoration throttle without confirming the mechanism first.
- **Open decisions:**
  - Is the highlighted background in the 'accepted suggestion' screenshots our custom chatSlashCommandBackground decoration, or Monaco's own post-completion selection/typeahead styling?
  - If it is our decoration, why does it apply reliably after a completion commit but not after manual typing of the same resulting text — is parsedInput failing to recognize the slash command part in the manual-typing case, or is the decoration simply not yet applied within the 200ms throttle window at the time of the screenshot?

## Evidence

- **symptom confirmed visually:** Fetched and viewed all three attached screenshots: typed '/plugin update' renders as plain text with an argument-value suggestion list (dap-cli, github-inbox, ...); accepting the suggestion for 'disable' renders '/plugin disable' fully highlighted with a blue background; the third screenshot shows only the substring 'upda' of 'update' highlighted mid-edit, a partial/inconsistent state the reporter couldn't reliably reproduce again.
- **decoration code path:** src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputEditorContrib.ts: InputEditorDecorations applies slashCommandTextDecorationType (chatSlashCommandBackground) in updateAsyncInputEditorDecorations(), which runs on a 200ms ThrottledDelayer after onDidChangeModelContent — a plausible but unconfirmed source of timing-dependent inconsistency between typed and completion-driven edits; I could not conclusively trace the defect without running the editor.
- **completion insertion:** src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts inserts slash-command completions (e.g. `${withSlash} `, `${label} `) via standard Monaco completion items; whether the highlighted blue background in the screenshots is our custom decoration or Monaco's own post-completion selection/typeahead rendering is unresolved from static source review.
