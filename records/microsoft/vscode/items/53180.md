# Issue #53180 — Show 'Source' actions in file explorer context menu

[https://github.com/microsoft/vscode/issues/53180](https://github.com/microsoft/vscode/issues/53180)

## Summary

A real capability gap remains: source code actions are still bound to an active code editor and are not generically exposed for a file selected in the Explorer. The Backlog and help-wanted classifications already accept the work, but the activation and presentation contract needs design before implementation.

## Change summary

Expose applicable source code actions, such as Organize Imports, from a file's Explorer context menu.

## Best solution

Provide a resource-oriented source-action flow that activates relevant language extensions, queries actions for the selected Explorer file rather than the active editor, and presents applicable actions without requiring every language extension to duplicate the plumbing.

- **Reason:** Making language actions consistently available from the Explorer improves the developer inner loop and provides reusable infrastructure for the extension ecosystem.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/codeAction/browser/codeActionCommands.ts`, `src/vs/editor/contrib/codeAction/browser/codeAction.ts`, `src/vs/workbench/contrib/files/browser/fileActions.contribution.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Add an Explorer context-menu test using a registered source code-action provider: selecting a supported file must expose and run the action against that file rather than an unrelated active editor, while unsupported files must show no source actions.
- **Behavior:**

  > When a user opens the context menu for a file in the Explorer, applicable source actions for that file can be discovered and invoked without first opening or focusing it in an editor. The action must target the selected Explorer resource, not whichever editor happens to be active. Unsupported files show no source-action entry, and existing editor source actions continue to behave unchanged.
- **Trace:**

  > SourceAction and OrganizeImportsAction in src/vs/editor/contrib/codeAction/browser/codeActionCommands.ts are EditorAction implementations and query the current ICodeEditor model and selection. The underlying getCodeActions/applyCodeAction functions in src/vs/editor/contrib/codeAction/browser/codeAction.ts operate on a text model, but there is no Explorer-facing resource flow that resolves a selected URI and presents those results. MenuId.ExplorerContext is available, and language extensions already contribute static resource commands there; TypeScript's organize-imports provider remains document-based and its command path delegates back to editor.action.sourceAction. The boundary is generic source actions for a selected file: do not change editor invocation behavior, make actions depend on an unrelated active editor, or add TypeScript-only behavior. The unresolved point begins at how selecting a resource activates providers and how dynamically discovered actions are represented in the Explorer menu.
- **Open decisions:**
  - Should the Explorer show a generic dynamic Source Actions submenu, or should extensions explicitly opt individual source-action kinds into the Explorer menu?
  - May invoking or opening the menu silently resolve the selected file and activate its language extensions, or should activation occur only after the user chooses a generic Source Actions entry?
  - Should the first version support exactly one selected file, or define behavior for multi-selection and folders as part of the public interaction contract?

## Evidence

- **current source-action path:** src/vs/editor/contrib/codeAction/browser/codeActionCommands.ts:183-250 implements Source Action and Organize Imports as EditorAction commands; both receive an ICodeEditor and trigger actions against its current model and selection.
- **Explorer surface:** MenuId.ExplorerContext exists in src/vs/platform/actions/common/actions.ts, and extensions/typescript-language-features/package.json contributes file-reference commands there, but it does not expose source actions or Organize Imports for the selected resource.
- **provider capability:** extensions/typescript-language-features/src/languageFeatures/organizeImports.ts provides source.organizeImports through a document-based CodeActionProvider, while its command aliases invoke editor.action.sourceAction and therefore still depend on the active editor.
- **remaining design:** https://github.com/microsoft/vscode/issues/53180#issuecomment-474092849 identifies unresolved extension activation and menu presentation semantics. Generic submenu infrastructure now exists, but the resource-oriented code-action and activation contract remains absent.
- **canonical search:** Repository issue searches for source actions and Organize Imports in the Explorer found no older open issue reporting the same observable request; the supplied cross-references concern extension implementations that depended on the active editor, not a canonical VS Code issue.
