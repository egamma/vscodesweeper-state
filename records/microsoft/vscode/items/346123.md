# Issue #346123 — Support CLI-first AI tooling with developer-controlled terminal execution

[https://github.com/microsoft/vscode/issues/346123](https://github.com/microsoft/vscode/issues/346123)

Keep open for product design: existing terminal visibility and shell-profile controls cover parts of the request, but not its full execution-mode and inspectable-record contract. The linked terminal reports cover narrower problems and do not absorb this broader proposal.

## Change summary

Provide developer-selected agent execution contexts, interactive terminal sessions, and authoritative execution records for reusable CLI workflows.

Verify that sensitive human input is excluded from model-visible records and that existing background execution remains available.
- **Behavior:**

  > Developers should be able to choose an appropriate execution environment for agent-invoked repository CLIs and inspect what actually ran. Interactive execution must support live observation, human input, interruption, and deliberate session reuse without removing background execution. Execution evidence must identify the invocation, actual context, completion state, output availability, and truncation. Sensitive human input must not enter model context or ordinary execution logs.
- **Trace:**

  > The built-in RunInTerminalTool already reveals real terminals through _handleTerminalVisibility and reuses foreground terminals through _initTerminal; TerminalProfileFetcher resolves the configured agent shell profile. The configuration registrations expose outputLocation and per-OS terminalProfile settings. Separately, AgentHostTerminalManager models output-only non-PTY channels, and Copilot mapSessionEvents maps shell_exit metadata into those terminal results. These paths establish partial capabilities, not a unified contract covering the full proposal. https://github.com/microsoft/vscode/issues/341462 owns the narrower SDK interactive-authentication request and should inform planning without replacing this broader issue. Preserve existing background execution and distinguish output presentation from interactive process ownership; the remaining uncertainty is the supported configuration scope and durable record contract.
- **Open decisions:**
  - Which execution modes and configuration scopes should the initial supported contract expose, and how should user choices take precedence over repository or Skill guidance?
  - Should independently inspectable execution records persist across reloads, and what retention and export contract should users receive?
  - Should the initial capability apply equally to built-in terminal tools and Copilot SDK sessions, or explicitly support a narrower first surface?
