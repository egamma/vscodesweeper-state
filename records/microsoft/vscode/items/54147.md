# Issue #54147 — Provide an API to track a position in a document across edits

[https://github.com/microsoft/vscode/issues/54147](https://github.com/microsoft/vscode/issues/54147)

## Summary

Keep open: current extension APIs still lack general-purpose position tracking across edits, and a maintainer explicitly chose this issue as the canonical request. Internal test-location tracking and extension-side workarounds do not cover the requested public API.

## Change summary

Expose an API that lets extensions register document positions and retrieve their updated locations after edits.

## Best solution

Design an explicit, opt-in tracked-position or tracked-range API with defined edit-boundary, deletion, and lifetime semantics. Preserve editor performance without synchronizing every decoration to the extension host on each keystroke.

- **Reason:** A missing editor API would enable multiple extensions to maintain reliable navigation and annotations, provided its design preserves typing performance.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/model/textModel.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`
- **Validation:** After agreeing the API contract, exercise an extension-host integration scenario that registers multiple locations, inserts and deletes text before and at those locations, and queries their updated positions. Include undo/redo, deletion of a tracked span, document closure, and handle disposal; verify the agreed semantics and assess typing cost with many tracked locations.
- **Behavior:**

  > An extension can retain independently registered document locations and resolve their current positions after intervening edits, so editing an earlier test does not invalidate navigation to later tests. Tracking must not require rendering decorations or maintaining a separate edit-mapping algorithm in each extension. Acceptance must cover multiple locations, edits before and at a location, undo/redo, and the agreed deletion and lifetime behavior. Existing immutable Position and Range values must retain their current contracts.
- **Trace:**

  > TextDocument and TextEditor in src/vscode-dts/vscode.d.ts provide coordinate conversion and decoration setters, but no general tracking handle or current-decoration getter. TextModel._setTrackedRange and _getTrackedRange in src/vs/editor/common/model/textModel.ts demonstrate internal tracking backed by decorations, while MainThreadTextEditorsShape in src/vs/workbench/api/common/extHost.protocol.ts lacks a public tracking bridge. TestingDecorations.getDecoratedTestPosition already reads model decoration positions internally, but this is not an extension-accessible general API. A maintainer selected this issue as the canonical in https://github.com/microsoft/vscode/issues/48364#issuecomment-423199363 and identified per-keystroke decoration synchronization as a performance concern in https://github.com/microsoft/vscode/issues/48364#issuecomment-383483874. The remaining uncertainty is the public contract, including edit affinity, deletion, document lifetime, and observation semantics; no implementation was executed or changed.
- **Open decisions:**
  - Should the public contract track individual positions, ranges, or both, and what insertion-at-boundary affinity should it expose?
  - When an edit deletes a tracked location or span, should the handle collapse to a surviving position or become invalid, and should extensions receive a removal event?
  - Should handles survive document closure and reopening, and should updated positions be available through queries, change events, or both?
