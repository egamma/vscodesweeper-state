# Issue #345163 — "Reply immediately" after the agent has finished its reply cancels its running background subagents

[https://github.com/microsoft/vscode/issues/345163](https://github.com/microsoft/vscode/issues/345163)

## Summary

Keep open: an independent reporter confirms that Send Immediately actually aborts running background subagents after the main response finishes. Current source retains the destructive cancellation path; the related steering issues do not own this distinct symptom.

## Change summary

Sending an immediate follow-up after the main response finishes cancels background subagents instead of preserving their work.

## Best solution

Allow immediate follow-up messages after foreground work finishes without aborting background subagents, and make the reported idle-parent Stop behavior consistent with that boundary. Establish how foreground completion is represented across the workbench, Agent Host, and Copilot runtime before changing shared cancellation behavior.

- **Behavior:**

  > After the main agent finishes its response while a background subagent remains running, an immediate follow-up must reach the main agent without cancelling that subagent. The reported idle-parent Stop case must not destroy background work. Ordinary foreground cancellation and unrelated queued messages must retain their intended behavior.
- **Trace:**

  > Immediate-send entry points reach cancellation through ChatService.sendPendingRequestImmediately or ChatWidget.acceptInput, and AgentHostSessionHandler dispatches ChatTurnCancelled. AgentSideEffects then cancels child sessions and invokes the provider abort seam; CopilotAgentSession.abort completes active child turns and aborts the SDK session. The independent reproduction at https://github.com/microsoft/vscode/issues/345163#issuecomment-6560939009 demonstrates actual runtime cancellation rather than the presentation-only failure in https://github.com/microsoft/vscode/issues/342375. Investigation has not established which runtime signal reliably distinguishes finished foreground work from a session remaining busy with children: assistant.message is handled as a model-call boundary, not definitive session completion. The planning session must resolve that execution-state boundary and the available non-destructive runtime interaction before selecting a bounded implementation. Preserve unrelated providers, explicit background-work cancellation, queue ordering, and exactly-once message delivery.
