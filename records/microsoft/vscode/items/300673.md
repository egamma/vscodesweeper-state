# Issue #300673 — Claude models existed on Windows, but disappeared on WSL Ubuntu 20.04 

[https://github.com/microsoft/vscode/issues/300673](https://github.com/microsoft/vscode/issues/300673)

## Summary

Keep open as a Copilot model-availability bug: the reporter and independent commenters showed that the same account receives different model lists locally and in WSL/Linux. The current evidence points toward remote authentication, model-metadata, or extension-version divergence, but does not establish which one is responsible.

## Change summary

Claude models available in local Windows Copilot Chat disappear when the same account is used from a WSL Ubuntu workspace.

## Best solution

Make Copilot resolve the same authenticated account and entitled server-provided model set across local and WSL extension hosts, while surfacing model-fetch failures rather than silently presenting a reduced picker. First reproduce on a current build while recording the local and remote extension versions, selected account, diagnostics, and model-metadata responses.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/authentication/vscode-node/session.ts`, `extensions/copilot/src/platform/authentication/vscode-node/copilotTokenManager.ts`, `extensions/copilot/src/platform/endpoint/node/modelMetadataFetcher.ts`, `extensions/copilot/src/extension/conversation/vscode-node/languageModelAccess.ts`
- **Validation:** Using one Copilot account on a current build, compare a local Windows window with a WSL window after confirming identical Copilot extension versions: diagnostics must identify the same account, model metadata must contain the same entitled user-selectable models, and both model pickers must show the same Claude entries. Repeat after reload and account switching to ensure stale remote state does not return.
- **Behavior:**

  > With the same Copilot account, entitlement configuration, and Copilot extension version, opening a WSL workspace must not remove Claude models that are available locally. The model picker should expose the same entitled user-selectable model set in both windows. If remote authentication or model retrieval fails, the failure must be diagnosable rather than appearing as an unexplained reduced list. Acceptance requires a local-versus-WSL check on a current build, including reload and account-switch scenarios.
- **Trace:**

  > The issue and two independent comments establish a local/remote model-list discrepancy, but their screenshots also expose different Copilot extension versions. Model publication currently flows from AuthenticationService/CopilotTokenManager through ModelMetadataFetcher._fetchModels in extensions/copilot/src/platform/endpoint/node/modelMetadataFetcher.ts, then through LanguageModelAccess._provideLanguageModelChatInfo in extensions/copilot/src/extension/conversation/vscode-node/languageModelAccess.ts, which keeps only endpoints marked for the picker. A newer related report, https://github.com/microsoft/vscode/issues/324396, found stale or wrong account context in remote sessions and recovered by signing out and back in, but it concerns the newer Agents Window and cannot serve as this older issue's canonical duplicate. The uncertainty starts at whether current WSL reproduces with identical extension versions and whether the local and remote extension hosts receive different accounts, tokens, server model lists, or experiment flags. Preserve entitlement and organization policy filtering; do not force models into the picker when the server legitimately marks them unavailable.
- **Open decisions:**
  - When local and remote extension hosts resolve different signed-in Copilot accounts, should the remote window automatically follow the locally selected account or explicitly prompt the user to choose the remote account?

## Evidence

- **independent reproduction:** https://github.com/microsoft/vscode/issues/300673#issuecomment-4234169124 independently reports the same account showing Claude models on Windows but not Ubuntu, with screenshots from VS Code 1.115.
- **version divergence:** https://github.com/microsoft/vscode/issues/300673#issuecomment-4125296104 and https://github.com/microsoft/vscode/issues/300673#issuecomment-4234169124 show the Linux/WSL extension lagging behind the Windows extension, so extension-version skew is a concrete lead that must be separated from account and network behavior.
- **current model path:** extensions/copilot/src/platform/endpoint/node/modelMetadataFetcher.ts::_fetchModels obtains a Copilot token, fetches the server model list, and applies the server/experiment model-picker flag; extensions/copilot/src/extension/conversation/vscode-node/languageModelAccess.ts::_provideLanguageModelChatInfo publishes only endpoints marked for the picker.
- **related remote account evidence:** The newer related report https://github.com/microsoft/vscode/issues/324396 describes reduced model availability in WSL/SSH and reports that signing out of all accounts and signing back into only the intended Business account restored the models, supporting remote account-context divergence as a lead. It is newer and concerns the Agents Window, so it is not a canonical duplicate.
- **no verified fix:** No concrete fixing commit or open canonical issue was found for the original Copilot Chat picker symptom, and source inspection cannot verify account-, entitlement-, proxy-, or service-dependent behavior without current diagnostics.
