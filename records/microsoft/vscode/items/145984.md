# Issue #145984 — Timeline API has no way to signal an entry should be removed

[https://github.com/microsoft/vscode/issues/145984](https://github.com/microsoft/vscode/issues/145984)

## Summary

The granular-removal gap remains on current main: timeline providers can request an additive refresh or reset the entire timeline, but cannot identify entries that should be removed. The accepted Backlog request should remain open for API design.

## Change summary

Allow a timeline provider to remove individual timeline entries without resetting and re-querying the entire timeline.

## Best solution

Define a granular timeline-change contract that can identify removed entries, carry it across the extension-host protocol, and update the cached aggregate without resetting selection, scroll position, or unrelated entries.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.timeline.d.ts`, `src/vs/workbench/contrib/timeline/common/timeline.ts`, `src/vs/workbench/contrib/timeline/browser/timelinePane.ts`, `src/vs/workbench/api/common/extHostTimeline.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadTimeline.ts`
- **Validation:** Add a timeline test that loads multiple identified entries, emits a granular removal change, and verifies that only the named entry disappears while the remaining aggregate and non-reset view state are preserved.
- **Behavior:**

  > A timeline provider can signal that one or more previously returned entries no longer exist without requesting a full timeline reset. The Timeline view removes only those entries and preserves unrelated items and existing view state. Providers that continue using ordinary change events or `reset: true` retain their current behavior.
- **Trace:**

  > TimelineChangeEvent currently carries only `uri` and `reset` in src/vscode-dts/vscode.proposed.timeline.d.ts and src/vs/workbench/contrib/timeline/common/timeline.ts. ExtHostTimeline forwards that shape through extHost.protocol.ts and MainThreadTimeline into TimelineService; TimelinePane.updateTimeline then either asks for newer entries or discards and reloads the whole TimelineAggregate. TimelineAggregate.add can replace duplicate IDs but has no removal operation. The motivating local-history case is documented at https://github.com/microsoft/vscode/issues/145721#issuecomment-1077718457. Preserve current paging, reset behavior, provider isolation, and view state; the uncertainty begins at the public removal and identity contract.
- **Open decisions:**
  - Should the public TimelineChangeEvent identify removed entries by TimelineItem IDs, carry removed item objects, or expose a separate removal event?
  - Must TimelineItem.id become mandatory for granular removal, or should entries without IDs have defined timestamp-based removal semantics?
  - Should one removal event be scoped to a single resource URI only, or support provider-wide removals in the same way an undefined change currently covers all resources?

## Evidence

- **current API:** src/vscode-dts/vscode.proposed.timeline.d.ts defines TimelineChangeEvent with only `uri` and optional `reset`; TimelineItem has an optional unique `id`, but the event has no removed-item field.
- **current implementation:** src/vs/workbench/contrib/timeline/common/timeline.ts likewise exposes only `uri` and `reset`. In src/vs/workbench/contrib/timeline/browser/timelinePane.ts, TimelineAggregate.add only merges or replaces duplicate returned items, while updateTimeline either fetches newer entries or deletes the whole source aggregate and reloads it.
- **extension-host path:** src/vs/workbench/api/common/extHostTimeline.ts forwards provider changes as `{ uri, reset, id }`; there is no granular removal information carried to the main thread.
- **original use case:** https://github.com/microsoft/vscode/issues/145721#issuecomment-1077718457 explains that local history must use `reset: true` to remove expired visible entries, causing a full re-render and potentially disturbing view state.
- **existing workaround:** The existing `reset` capability covers correctness through a full refresh, but does not satisfy the central request for removing entries while preserving the existing timeline view state.
- **canonical search:** Searches for open timeline-provider removal issues found no older issue with the same observable API gap; the mechanical candidate list contains unrelated items.
