# Issue #270160 — Add support for full-match patterns relative to workspace root for Copilot Instructions `applyTo` pattern

[https://github.com/microsoft/vscode/issues/270160](https://github.com/microsoft/vscode/issues/270160)

## Summary

Keep open in the Backlog: a maintainer confirmed that VS Code intentionally prepends `**/` when matching instruction paths and that no workspace-root full-match syntax currently exists. The request has 25 upvotes and remains a concrete customization gap.

## Change summary

Allow Copilot instruction `applyTo` globs to match complete paths relative to the workspace root instead of always behaving as though prefixed with `**/`.

## Best solution

Define an explicit, backward-compatible workspace-root anchoring syntax for instruction `applyTo` patterns, then apply it consistently in automatic instruction matching and document the distinction from the existing basename/partial-match behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/promptSyntax/computeAutomaticInstructions.ts`, `src/vs/workbench/contrib/chat/test/common/promptSyntax/computeAutomaticInstructions.test.ts`
- **Validation:** Add instruction-matching tests showing that the chosen anchored form matches `src/testA.component.ts` but not `app/src/testB.component.ts`, while existing unanchored `src/**/*.ts` behavior and `**/*.ts` matching remain backward compatible.
- **Behavior:**

  > Copilot instruction authors can express a full-path `applyTo` pattern anchored to the workspace root. The anchored form must match `src/testA.component.ts` and exclude `app/src/testB.component.ts`; ordinary existing patterns must retain their current matching behavior. The behavior must work consistently with normalized path separators.
- **Trace:**

  > Automatic instruction applicability is computed in src/vs/workbench/contrib/chat/common/promptSyntax/computeAutomaticInstructions.ts. The maintainer trace in https://github.com/microsoft/vscode/issues/270160#issuecomment-3420670918 identifies the current basename/partial-match behavior: `src/**/*.ts` effectively receives a leading `**/`, so it also matches `app/src/testB.component.ts`. The boundary is Copilot instruction `applyTo` path matching; the separate PromptHeader `tools` glob request at https://github.com/microsoft/vscode/issues/300943 does not settle this path contract. Existing unanchored patterns must not silently change semantics.
- **Open decisions:**
  - What public syntax denotes a workspace-root-anchored `applyTo` glob without changing existing patterns: a leading slash, an explicit prefix, or another documented form?
  - In a multi-root workspace, should the anchor resolve independently against each workspace folder root or against a single workspace-level path namespace?
