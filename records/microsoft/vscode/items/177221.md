# Issue #177221 — Differentiate breakpoint types more clearly

[https://github.com/microsoft/vscode/issues/177221](https://github.com/microsoft/vscode/issues/177221)

## Summary

A real accessibility polish gap remains: current main uses separate conditional and data breakpoint glyphs, but their similar circular silhouettes remain difficult to distinguish for users with limited vision. This issue is already the canonical report for that broader problem and carries the correct debug, UX, and accessibility routing.

## Change summary

Make breakpoint types distinguishable through clearer, non-color-only icon shapes, particularly for conditional and data breakpoints.

## Best solution

Adopt a coherent set of clearly distinct silhouettes for regular, conditional, data, function, and log breakpoints while preserving recognizable disabled and unverified variants. The exact shapes should be selected with design and accessibility review before updating the Codicons asset.

## Plan brief

- **Likely files:** `package.json`, `src/vs/base/common/codiconsLibrary.ts`, `src/vs/workbench/contrib/debug/browser/debugIcons.ts`
- **Validation:** Create regular, conditional, data, function, and log breakpoints and visually compare their gutter and Breakpoints-view icons at default zoom, including disabled and unverified states; each type must remain identifiable without relying on color.
- **Behavior:**

  > Regular, conditional, data, function, and log breakpoints must be distinguishable by silhouette rather than color alone in both the editor gutter and Breakpoints view. Conditional and data breakpoints must remain recognizable at default zoom for users with reduced visual acuity. Disabled and unverified variants must preserve both breakpoint type and state, and existing breakpoint interactions must remain unchanged.
- **Trace:**

  > Breakpoint types are mapped in src/vs/workbench/contrib/debug/browser/debugIcons.ts to dedicated Codicon IDs, including conditional and data regular, disabled, and unverified variants. Those IDs map to generated glyph entries in src/vs/base/common/codiconsLibrary.ts; the font is supplied by the `@vscode/codicons` dependency declared in package.json, so the underlying artwork is owned upstream by microsoft/vscode-codicons. Current main retains the reported glyph family. https://github.com/microsoft/vscode/issues/129543 is related design context for instruction breakpoints but has a different observable symptom and must not absorb this issue. Preserve breakpoint semantics, colors, state handling, and interactions; the scope is visual differentiation.
- **Open decisions:**
  - Which silhouettes should represent conditional and data breakpoints so they remain distinct from regular, function, and log breakpoints at small sizes?
  - Should the icon-system review cover instruction breakpoints from https://github.com/microsoft/vscode/issues/129543 at the same time, or keep that type as separate follow-up work?

## Evidence

- **current implementation:** src/vs/workbench/contrib/debug/browser/debugIcons.ts still registers the existing `debug-breakpoint-conditional` and `debug-breakpoint-data` Codicons for their regular, disabled, and unverified states.
- **asset ownership:** src/vs/base/common/codiconsLibrary.ts identifies its breakpoint glyph mappings as generated by microsoft/vscode-codicons, while src/vs/base/browser/ui/codicons/codicon/README.md states that codicon.ttf comes from the `@vscode/codicons` package.
- **canonical status:** A maintainer closed https://github.com/microsoft/vscode/issues/189527 by explicitly merging its small-breakpoint visibility concern into this issue: https://github.com/microsoft/vscode/issues/189527#issuecomment-1856450366.
- **related but distinct:** https://github.com/microsoft/vscode/issues/129543 is older and open, but concerns instruction breakpoints using exactly the same icon as regular breakpoints; it does not own this report's observable problem with conditional and data breakpoint silhouettes.
