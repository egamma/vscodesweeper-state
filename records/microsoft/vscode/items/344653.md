- **Trace:**

## Evidence

- **Actionable report:** https://github.com/microsoft/vscode/issues/344653 supplies the affected versions, macOS environment, authorization-server metadata characteristics, registered redirect URIs, first-login steps, and discovery/cancellation logs. A manually supplied ****** works, which narrows the investigation to token acquisition but does not establish that the confidential-client exchange is configured correctly.
- **Manual registration is supported:** src/vs/workbench/api/common/extHostAuthentication.ts, $registerDynamicAuthProvider, prompts for a client ID and secret when dynamic registration is unavailable and passes those credentials to the dynamic provider. The reported no-DCR configuration is an existing core authentication path, not an unsupported third-party extension workflow.
- **Browser hand-off is not the token-delivery mechanism:** src/vs/workbench/api/node/loopbackServer.ts completes its OAuth result promise after receiving a code and matching state on '/'. NodeDynamicAuthProvider._createWithLoopbackServer in src/vs/workbench/api/node/extHostAuthentication.ts awaits that result and calls exchangeCodeForToken independently of the app URI hand-off. Its finally block schedules loopback-server shutdown after either success or failure, so the closed port alone does not prove a successful token exchange.
- **Client-authentication distinction:** DynamicAuthProvider.exchangeCodeForToken in src/vs/workbench/api/common/extHostAuthentication.ts sends an available client_secret in the form body, without a Basic Authorization header. https://github.com/microsoft/vscode/issues/257277 remains open for client_secret_basic/client_secret_post support, but this report says no token request occurs and advertises support for client_secret_post; the shared root cause needed for a duplicate close is not established.
- **Cancellation explains the final symptom, not its origin:** McpHTTPHandle._addAuthHeader in src/vs/workbench/api/common/extHostMcp.ts awaits $getTokenFromServerMetadata, adds Authorization only when a token is returned, and logs caught authentication errors. This accounts for a cancellation followed by an unauthenticated failure, but does not identify which authentication stage canceled.
- **Related reports do not establish duplication:** https://github.com/microsoft/vscode/issues/277659 concerns expired-secret diagnostics; https://github.com/microsoft/vscode/issues/343436 concerns parallel reauthentication after refresh-token rejection, with a follow-up about abandoned browser flows; https://github.com/microsoft/vscode/issues/343316 concerns extension-host replacement after successful authentication. None establishes the same initial-login failure described here.
