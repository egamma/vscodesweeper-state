# Issue #344653 — MCP OAuth (pre-registered confidential client): browser login succeeds but token never reaches MCP client, stuck on 'Waiting for server to respond to initialize'

[https://github.com/microsoft/vscode/issues/344653](https://github.com/microsoft/vscode/issues/344653)

## Summary

Keep open: the report provides sufficient steps to retest the confidential-client login failure, but the source trace does not establish its cause or a fix. Authentication plumbing has evolved since the reported builds; none of the verified related issues establishes the same callback-stage failure.

## Change summary

MCP initialization fails without a Bearer token after browser authorization completes for a manually registered confidential OAuth client.

## Best solution

Establish where this initial-login flow fails between loopback callback receipt, token exchange, session storage, and the authenticated initialize retry. Successful authorization should connect the server; a failed exchange should surface its actual error rather than leave initialization waiting.

- **Behavior:**

  > A manually registered confidential OAuth client should connect an HTTP MCP server after successful browser authorization. The accepted callback should lead to token exchange, session availability, and an authenticated initialize retry. A failed exchange should report its failure rather than indefinitely display initialization waiting. First reproduce the supplied PingOne/AgentCore scenario on current VS Code; browser login success alone is not proof of token exchange success.
- **Trace:**

  > LoopbackAuthServer in src/vs/workbench/api/node/loopbackServer.ts resolves the OAuth response before serving the application hand-off page. NodeDynamicAuthProvider._createWithLoopbackServer awaits that response and immediately invokes DynamicAuthProvider.exchangeCodeForToken; createSession subsequently stores the token. MainThreadMcp obtains the provider session, and McpHTTPHandle._addAuthHeader applies its access token or logs an exception and proceeds without it. The supplied MCP logs do not identify which earlier stage failed, so the root cause is unconfirmed. Preserve callback state validation, existing public-client/DCR behavior, and unrelated lifecycle semantics. https://github.com/microsoft/vscode/issues/257277 concerns authentication methods; https://github.com/microsoft/vscode/issues/345860 concerns cross-window registration removal, not this established trigger.
