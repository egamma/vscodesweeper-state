# Issue #27905 — Have ctrl+click work the same way as in Visual Studio

[https://github.com/microsoft/vscode/issues/27905](https://github.com/microsoft/vscode/issues/27905)

## Summary

The requested Ctrl-based word-selection gestures remain missing from the built-in editor. Keep this accepted Backlog request open: it has 26 upvotes, existing settings do not cover it, and the related issues do not establish an eligible canonical for this re-reviewed item.

## Change summary

Support Ctrl+click word selection, Ctrl+Shift+click word-aligned range extension, and Ctrl+drag selection of whole words, as in Visual Studio.

## Best solution

Provide an opt-in way to use all three word-selection gestures while preserving existing navigation and multicursor behavior for users who do not opt in. Decide the user-facing configuration contract alongside the broader mouse-shortcut customization work.

## Plan brief

- **Likely files:** `src/vs/editor/browser/view/viewController.ts`, `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/contrib/gotoSymbol/browser/link/clickLinkGesture.ts`, `src/vs/editor/browser/coreCommands.ts`, `src/vs/editor/test/browser/view/viewController.test.ts`
- **Validation:** Add targeted ViewController mouse-dispatch tests for the agreed opt-in behavior: Ctrl+click selects a whole word, Ctrl+Shift+click extends to the target word boundary, and Ctrl+drag includes the entire endpoint word in both directions. Run scripts/test.sh --run src/vs/editor/test/browser/view/viewController.test.ts and manually verify that default Go to Definition, link opening, double-click selection, and multicursor gestures remain unchanged.
- **Behavior:**

  > Users want Visual Studio-style word selection without double-clicking: Ctrl+click selects one word, Ctrl+Shift+click extends the selected range through another whole word, and holding Ctrl while dragging selects complete words even when the pointer stops inside a word. Acceptance must cover forward and backward selections and all three gestures, not only the initial click. The default editor interactions should remain unchanged unless the user opts into the agreed behavior.
- **Trace:**

  > ViewController.dispatchMouse in src/vs/editor/browser/view/viewController.ts routes double-clicks to _wordSelect or _wordSelectDrag, but routes single-click modifier gestures to movement, column selection, or multicursor operations. WordSelect and WordSelectDrag already exist in src/vs/editor/browser/coreCommands.ts. editor.multiCursorModifier in src/vs/editor/common/config/editorOptions.ts only chooses the cursor-addition modifier; ClickLinkGesture.createOptions in src/vs/editor/contrib/gotoSymbol/browser/link/clickLinkGesture.ts adapts navigation to its opposite, so that setting is not word-selection coverage. The existing ViewController test suite provides a mouse-dispatch harness. General mouse customization is tracked at https://github.com/microsoft/vscode/issues/3130; the younger overlapping report is https://github.com/microsoft/vscode/issues/34354. The uncertainty is the user-facing opt-in contract and its modifier precedence, not whether the current source provides the requested gestures. Preserve default navigation, link opening, double-click selection, and multicursor semantics.
- **Open decisions:**
  - Should users enable a dedicated Visual Studio-style selection mode, or configure these gestures through a general mouse-shortcut customization surface?
  - When word-selection gestures are enabled, what happens to Ctrl-based Go to Definition and link opening, and how should the mode interact with editor.multiCursorModifier set to ctrlCmd?

## Evidence
