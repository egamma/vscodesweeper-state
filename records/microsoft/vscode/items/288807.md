# Issue #288807 — How to push changes to remote after creating PRs for background session

[https://github.com/microsoft/vscode/issues/288807](https://github.com/microsoft/vscode/issues/288807)

## Summary

Confirmed real gap on main: the 'Sync Changes' toolbar action that pushes commits is explicitly gated to folder-kind sessions and skipped for worktree-kind sessions, which is exactly the background-session-after-PR scenario the report describes — but how push should work for worktree sessions (auto vs. explicit, where the affordance lives) is an open design question, so this needs planning rather than a quick fix.

## Change summary

After a background (worktree) session's branch is used to open a PR, there is no discoverable way to push further changes made in that session to the remote/PR branch.

## Best solution

Extend push/sync support to worktree-kind sessions (or add an equivalent affordance) in the sessions UI so changes made after PR creation can be pushed without leaving the session — likely in src/vs/sessions/contrib/changes/browser/sessionSyncChanges.ts and the agent host changeset/PR creation code, after a maintainer decides the intended interaction model.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/changes/browser/sessionSyncChanges.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/agentHostSessionChangesets.ts`, `src/vs/platform/agentHost/common/agentHostChangesetOperationService.ts`
- **Validation:** A test asserting that a worktree-kind session with outgoing commits after PR creation exposes a push/sync action (analogous to the existing sessionSyncChanges tests for folder sessions).
- **Behavior:**

  > After a background (worktree-kind) session's branch has been used to open a PR, and the session makes further changes, the user should have a clear, discoverable way to push those new commits to the PR's remote branch from within the sessions UI. Acceptance: a worktree-kind session with outgoing commits exposes an equivalent of the existing 'Sync Changes' push action (or a dedicated push affordance), and invoking it pushes to the correct upstream/PR branch.
- **Trace:**

  > src/vs/sessions/contrib/changes/browser/sessionSyncChanges.ts defines `shouldShowSyncChanges` and `isFolderSession`, which gate the Sync Changes action (via `AGENT_HOST_SYNC_CHANGESET_OPERATION_ID = 'sync'`) to `SessionWorkspaceKind.Folder` only; `getSessionWorkspaceKind` in src/vs/sessions/services/sessions/common/session.ts classifies any session with a git worktree (`workTreeUri` set) as `Worktree`, not `Folder`, so the push UI never appears for worktree/background sessions. The boundary: do not change folder-session sync behavior or the underlying `sync` operation semantics — the gap is specifically in UI/availability for worktree-kind sessions, and the open question (below) is what the right interaction model is before any code change.
- **Open decisions:**
  - Should pushing new commits for a worktree-based background session after PR creation be automatic, or require an explicit user action?
  - If explicit, should it reuse the existing 'Sync Changes' action (extended to worktree-kind sessions) or a new, PR-specific push affordance?
  - Does pushing update the existing PR's branch directly, or does it need to account for the PR having since changed base/target?

## Evidence

- **gate in source:** src/vs/sessions/contrib/changes/browser/sessionSyncChanges.ts `shouldShowSyncChanges`/`isFolderSession` only shows the Sync Changes (push/pull) action when `getSessionWorkspaceKind(...) === SessionWorkspaceKind.Folder`; worktree-kind sessions are excluded from this UI entirely.
- **kind classification:** src/vs/sessions/services/sessions/common/session.ts `getSessionWorkspaceKind` returns `Worktree` for any session whose git repository has a `workTreeUri`, which is how background/Copilot CLI agent sessions are represented — matching the report's 'worktree branch' scenario.
