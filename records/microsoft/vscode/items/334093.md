[https://github.com/microsoft/vscode/issues/334093](https://github.com/microsoft/vscode/issues/334093)

## Summary

The failure path remains on current main: a 422 from the embeddings endpoint leaves extension tools without embeddings, so tool search can omit even an explicitly named tool. The issue already has the correct chat-tools routing and should remain open while the endpoint rejection and graceful fallback are resolved.

## Change summary

Copilot tool search cannot discover explicitly named extension tools when computing their embeddings returns HTTP 422.

## Best solution

Determine why the Dotcom embeddings request rejects these tool descriptions, then make tool search degrade gracefully so an exact tool-name query remains usable when embeddings are unavailable.

- **Validation:** Extend the tool-search unit tests with an embeddings service that rejects with HTTP 422; verify the agreed fallback still returns an explicitly named available extension tool while unrelated tools are not incorrectly selected.
- **Behavior:**

  > When tool-embedding computation is unavailable, searching with an available extension tool's explicit name must still return that tool. The chat request must not fail solely because the embeddings endpoint returned 422. Normal semantic ranking must remain unchanged when embeddings are available, and unavailable or disabled tools must not become callable.
- **Trace:**

  > RemoteEmbeddingsComputer.computeEmbeddings in extensions/copilot/src/platform/embeddings/common/remoteEmbeddingsComputer.ts throws for the reported non-OK response. ToolEmbeddingsComputer.computeMissingEmbeddings catches that rejection and removes the affected entries, while searchToolsByQuery has no non-embedding path. ToolSearchTool.invoke in extensions/copilot/src/extension/tools/node/toolSearchTool.ts returns only those embedding-ranked names, which explains why selected extension tools disappear. A nearby test already models `Error fetching embeddings: 422` in extensions/copilot/src/extension/tools/test/node/virtualTools/virtualToolGrouperUnhandledRejection.spec.ts, but it verifies only promise handling, not discoverability. The plan must first identify whether malformed or oversized request content causes the 422, then define the smallest fallback without changing successful semantic search or tool enablement boundaries.
- **Open decisions:**
  - When embeddings are unavailable, should tool search match only exact tool names, or provide broader lexical name-and-description matching?
  - Should a failed embeddings request produce a degraded successful tool-search result, or also expose a user-visible diagnostic while preserving the chat request?
