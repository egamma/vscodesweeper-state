# Issue #336422 — Nested subagent invocation fails with "Requested agent is not allowed by the current agent" despite nested subagents being enabled

[https://github.com/microsoft/vscode/issues/336422](https://github.com/microsoft/vscode/issues/336422)

## Summary

This is the same underlying defect already tracked by the open issue https://github.com/microsoft/vscode/issues/335257 — nested runSubagent calls are rejected against the wrong agent's allow-list when nesting more than one level deep, even with allowInvocationsFromSubagents enabled.

## Change summary

Enabling chat.subagents.allowInvocationsFromSubagents doesn't let a subagent (agent-b) invoke its own allow-listed subagent (agent-c); the call fails with 'not allowed by the current agent'.

## Best solution

Consolidate on https://github.com/microsoft/vscode/issues/335257 and fix RunSubagentTool.validateSubagentAllowed / invoke() in src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts so each nested invocation checks the allow-list of the *immediately calling* subagent's modeInstructions, not the top-level request's stale modeInfo.

## Evidence

- **canonical duplicate:** https://github.com/microsoft/vscode/issues/335257 is open and describes the identical scenario: nested runSubagent calls rejected several levels deep even when the target is in the calling agent's allow-list.
- **traced root cause:** src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts:169-199 reads `model.getRequests().at(-1)!.modeInfo?.modeInstructions` on every invoke() call. Because invokeAgent() (called at line 395) does not append a new request to the model, this always resolves to the top-level (agent-a) request's modeInfo — never the dynamically-computed `modeInstructions` for the intermediate subagent (agent-b, built at line 232-239 and only passed into `agentRequest`, not stored back on the model). So when agent-b tries to invoke agent-c, validateSubagentAllowed() (line 686-691) checks agent-c against agent-a's `agents:` allow-list instead of agent-b's, and rejects it.
- **same file, same mechanism:** The nesting-depth counter (`this._sessionDepth`, keyed per session) correctly increments across levels, but the allow-list check has no equivalent per-level tracking, confirming the depth feature and the allow-list check are on separate, inconsistent code paths.
