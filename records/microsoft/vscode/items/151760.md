# Issue #151760 — Expose the hostname (server name on which VSCode is running on)

[https://github.com/microsoft/vscode/issues/151760](https://github.com/microsoft/vscode/issues/151760)

## Summary

Keep this accepted API request open: stable vscode.env.remoteName identifies the remote provider, not the connected host, while vscode.env.remoteAuthority remains proposal-gated. The older remote-authority proposal is relevant, but its empty-window discovery scenario does not establish equivalent coverage of this report's host/container identification requirement.

## Change summary

Expose connected remote-host identity to extensions so they can filter host-specific data and actions.

## Best solution

Define a supported extension API contract for the remote identity needed by host-aware extensions, coordinating with the existing remoteAuthority proposal. Establish whether resolver-defined authority is sufficient or whether identifying the server behind a container requires additional semantics.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vscode-dts/vscode.proposed.resolvers.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/platform/remote/common/remoteHosts.ts`
- **Validation:** Exercise a normal extension without the resolvers proposal enabled in local, Remote-SSH, and container-connected windows, including an empty remote window. Verify the agreed identity contract lets it select the correct host-specific data, has documented absence semantics locally, and leaves vscode.env.remoteName unchanged.
- **Behavior:**

  > Extensions need supported access to the identity of the remote connection so they can filter mount/container lists and enable actions for the correct host. Stable remoteName currently supplies the provider category rather than the host. Acceptance must cover ordinary extensions without proposed-API enablement and distinguish SSH connections from container connections according to an explicitly agreed identity contract.
- **Trace:**

  > In src/vs/workbench/api/common/extHost.api.impl.ts, env.remoteName calls getRemoteName(initData.remote.authority), while env.remoteAuthority returns the full authority only after checking the resolvers proposal. getRemoteName in src/vs/platform/remote/common/remoteHosts.ts strips the suffix after '+'. The full authority is declared in src/vscode-dts/vscode.proposed.resolvers.d.ts, not stable vscode.d.ts, and is defined by the resolver rather than guaranteed to be a normalized server hostname. https://github.com/microsoft/vscode/issues/111371 tracks related authority discovery and eventual finalization; coordinate with that API work without assuming it resolves physical-host identification behind containers. Preserve existing provider-name semantics and resolver compatibility. The uncertainty is the public identity guarantee, not where to place a getter.
- **Open decisions:**
  - Is a resolver-defined remote authority sufficient for this contract, or must the API identify the underlying server when the active remote extension host runs inside a container?
