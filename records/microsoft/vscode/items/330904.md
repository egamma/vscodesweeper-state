# Issue #330904 — BYOK support for embedding-based AI features

[https://github.com/microsoft/vscode/issues/330904](https://github.com/microsoft/vscode/issues/330904)

## Summary

Keep open for the community feature-request process: current embedding consumers still use GitHub/Copilot services, and the existing model preference does not enable local or BYOK embedding providers. The request has 9 upvotes in Backlog Candidates; neither the related API work nor inline-completion request owns this product integration.

## Change summary

Allow embedding-based AI features to use user-configured embedding providers, including local Ollama models, independently of GitHub/Copilot embedding services.

## Best solution

Define a supported BYOK embedding-provider contract and the built-in features that consume it, including model compatibility and index persistence semantics. Coordinate with the embeddings API work without folding this end-user integration request into API finalization or inline-completion support.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/embeddings/common/embeddingsComputer.ts`, `extensions/copilot/src/platform/embeddings/common/remoteEmbeddingsComputer.ts`, `extensions/copilot/src/platform/workspaceChunkSearch/common/githubAvailableEmbeddingTypes.ts`, `extensions/copilot/src/platform/workspaceChunkSearch/node/workspaceChunkSearchService.ts`, `extensions/copilot/src/extension/prompt/vscode-node/endpointProviderImpl.ts`, `extensions/copilot/src/extension/extension/vscode/services.ts`, `extensions/copilot/package.json`
- **Validation:** After agreeing on the supported feature scope, configure a local embedding provider with no GitHub session and verify that an approved built-in embedding consumer computes document and query vectors through that provider without GitHub/Copilot embedding requests. Verify model changes cannot reuse incompatible indexed vectors, and that the existing Copilot path remains unchanged when no BYOK provider is selected.
- **Behavior:**

  > Users want built-in embedding-based AI features to work with their own embedding services, including local Ollama models, rather than requiring GitHub/Copilot embedding services. Successful support must cover the agreed built-in consumers, not merely register a provider that those consumers never use. Acceptance should demonstrate provider-backed document and query embeddings without a GitHub session, compatible vector comparisons, and unchanged behavior for existing Copilot users. Inline code completions are a separate request.
- **Trace:**

  > The production service registration binds IEmbeddingsComputer to RemoteEmbeddingsComputer, whose requests use GitHub/Copilot authentication and endpoints. ProductionEndpointProvider.getEmbeddingsEndpoint resolves Copilot embedding metadata, while the workspace preferredEmbeddingsModel setting only selects among GitHub-advertised embedding types. WorkspaceChunkSearchService.computeEmbeddings delegates document and query computation to IEmbeddingsComputer; EmbeddingType and distance encode a same-model compatibility boundary. The root API infrastructure exposes embeddings providers, but the traced built-in consumer uses its own service rather than that provider registry. The related API tracker is https://github.com/microsoft/vscode/issues/212083; search modernization is recorded in https://github.com/microsoft/vscode/issues/292972. Uncertainty begins at which current built-in consumers should support arbitrary local models and what provider-selection and index compatibility contract they should expose; do not expand the work into inline completions or assume a local provider can query GitHub-built indexes.
- **Open decisions:**
  - Which built-in embedding-based features should support BYOK initially, and which service-backed features remain unavailable with only a local embedding provider?
  - Should users select one embedding provider globally or separately for each supported feature?
  - When the selected embedding model changes, should incompatible indexes be rebuilt automatically or require explicit user action?
