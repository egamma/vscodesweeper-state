# Issue #227936 — Closing a terminal that was reopen in a new window doesn't dispose the terminal object

[https://github.com/microsoft/vscode/issues/227936](https://github.com/microsoft/vscode/issues/227936)

## Summary

The missing terminal-close notification after moving a terminal editor is already tracked by the open issue https://github.com/microsoft/vscode/issues/206735. The auxiliary-window round trip exercises the same broken lifecycle tracking, so consolidate this report there while preserving its reproduction details.

## Change summary

Closing an API-created terminal after moving it through an auxiliary window leaves its extension-host Terminal object registered without an exit status.

## Best solution

Resolve terminal-editor lifecycle tracking under https://github.com/microsoft/vscode/issues/206735 so moving an editor preserves disposal notifications and its eventual closure updates the extension API. Preserve the existing behavior that returns confirming terminal editors to the main window when an auxiliary window closes.

## Evidence

- **Verified open canonical:** https://github.com/microsoft/vscode/issues/206735 is open and predates this report. Its discussion identifies moving a terminal editor before closing it as the trigger for missing window.onDidCloseTerminal notifications, rather than a WSL-only problem.
- **Independent confirmation:** https://github.com/microsoft/vscode/issues/206735#issuecomment-1988859123 reports the missing close event after moving an API-created terminal to another pane. https://github.com/microsoft/vscode/issues/206735#issuecomment-3888950878 independently confirms the moved-editor symptom on macOS in February 2026.
- **Current-source defect:** At main snapshot 8571e6fd2f04a40dc0341c05897b93ff132b06f8, src/vs/workbench/browser/parts/editor/editorGroupView.ts::doMoveOrCopyEditorAcrossGroups opens the same input in the destination and closes it in the source with EditorCloseContext.MOVE. src/vs/workbench/contrib/terminal/browser/terminalEditorService.ts handles that close by calling _removeInstance, which disposes the instance.onDisposed forwarding listener even though the input survives in another group. Its visible-editor rediscovery path restores the input and instance directly without restoring those listeners.
- **API consequence:** src/vs/workbench/api/browser/mainThreadTerminalService.ts::_onTerminalDisposed sends $acceptTerminalClosed only through TerminalService.onDidDisposeInstance. src/vs/workbench/api/common/extHostTerminalService.ts::$acceptTerminalClosed removes the Terminal from _terminals, sets exitStatus, and fires onDidCloseTerminal. Losing the editor-service disposal forwarding therefore explains both this report's stale Terminal object and the canonical issue's missing close event.
- **Auxiliary-window scope:** src/vs/workbench/browser/parts/editor/auxiliaryEditorPart.ts::doClose deliberately merges confirming editors back into the main part. The report's subsequent terminal closure, not the window-to-main return itself, exposes the same moved-editor disposal-notification defect tracked by the canonical.
- **Related extension change:** https://github.com/espressif/vscode-esp-idf-extension/pull/1289 merged an extension-side monitor-terminal reuse change. Its diff changes terminal creation and close-event handling in the extension; it does not repair VS Code's moved-editor lifecycle forwarding and is not evidence that this core issue was fixed.
