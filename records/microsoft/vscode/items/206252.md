# Issue #206252 — Stop stealing focus from other applications

[https://github.com/microsoft/vscode/issues/206252](https://github.com/microsoft/vscode/issues/206252)

## Summary

Keep this accepted focus-preservation request open: it has 24 upvotes, and neither the related view-focus fix nor the newer command-line request establishes that background initialization no longer interrupts another application.

## Change summary

Preserve the user's active application and virtual desktop when a VS Code window finishes initializing in the background.

## Best solution

Ensure background startup and restoration do not reactivate VS Code after the user switches away, while preserving explicit user-requested activation and floating-window navigation. Reproduce the Windows startup scenario first and distinguish core initialization from Remote-SSH dialog activation.

Also verify explicit activation and floating-window focus navigation still work.
- **Behavior:**

  > After launching a VS Code window, a user can switch to another application or virtual desktop while initialization continues. Finishing initialization must not redirect keyboard input to VS Code or switch the user's desktop back. Explicitly returning to VS Code must continue to work. Acceptance checks should cover ordinary startup and slower Remote-SSH initialization, with dialog-triggered activation recorded separately.
- **Trace:**

  > Current src/vs/workbench/browser/window.ts guards element-driven window activation with hasAppFocus(), so that path already contains focus-preservation logic. The readiness flow runs from src/vs/workbench/electron-browser/window.ts through NativeHostMainService.notifyReady to CodeWindow.setReady; setReady itself does not directly activate the window, but invokes waiting callbacks. src/vs/workbench/browser/layout.ts also focuses parts during restoration, and native focus calls reach NativeHostMainService.focusWindow and CodeWindow.doFocusWindow. The trace has not identified which caller produces the reported Windows activation, so runtime diagnosis is needed before defining a bounded implementation. Preserve explicit activation and floating-window navigation; do not assume the view-focus fix in https://github.com/microsoft/vscode/issues/205766 covers startup or that the narrower CLI request at https://github.com/microsoft/vscode/issues/340297 replaces this issue.
