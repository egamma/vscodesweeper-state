# Issue #307922 — UI corruption when opening extension "Open to the Side" from Profiles → Contents → Extensions

[https://github.com/microsoft/vscode/issues/307922](https://github.com/microsoft/vscode/issues/307922)

## Summary

Keep open as a confirmed visual-layout bug: an independent commenter reproduced the same editor overlap, and current main still routes the Profiles extension action through the side-by-side extension-editor path. No older canonical or concrete fixing commit was found.

## Change summary

Opening an extension beside Profiles → Contents → Extensions causes extension content to overlap and visually corrupt the Profiles editor.

## Best solution

Ensure that an extension editor opened from Profiles is confined to its adjacent editor group and that the Profiles editor relayouts cleanly after the split, without duplicated or overlaid content.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditorModel.ts`, `src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditor.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts`
- **Validation:** On Windows, open Profiles → active profile → Contents → Extensions, invoke Open to the Side on an extension, and verify that two correctly bounded editor groups render with no duplicated, ghosted, or overlapping content; repeat after resizing both groups.
- **Behavior:**

  > Opening an extension from Profiles → Contents → Extensions with Open to the Side must create a normal adjacent editor group. The extension details must remain inside that group, while the Profiles editor remains correctly laid out and fully repainted. There must be no duplicated text, ghosted imagery, or overlap before or after resizing the split.
- **Trace:**

  > The profile resource action is created in `AbstractUserDataProfileElement.toUserDataProfileResourceChildElement` in src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditorModel.ts; for extension children it executes `extension.open` with `preserveFocus` and `sideByside` enabled. That command reaches `ExtensionsWorkbenchService.open` in src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts, which opens an `ExtensionsInput` in `SIDE_GROUP`. `UserDataProfilesEditor.layout` and its nested horizontal `SplitView` in src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditor.ts are the adjacent relayout boundary. The discussion at https://github.com/microsoft/vscode/issues/307922 confirms the visible overlap, but the available source inspection does not settle whether the stale layer originates in Profiles layout, editor-group layout, or extension-editor rendering; preserve ordinary side-opening behavior elsewhere.

## Evidence

- **confirmed reproduction:** The report at https://github.com/microsoft/vscode/issues/307922 provides deterministic steps and a screenshot, and a second user independently confirmed that opening an extension from the Profiles/settings surface places extension imagery above that surface.
- **current source path:** src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditorModel.ts constructs the extension child action by executing `extension.open` with both `preserveFocus` and `sideByside` set to true.
- **side-group routing:** src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts opens ExtensionsInput in `SIDE_GROUP` when `options.sideByside` is true; this is the reported transition from the Profiles editor into the corrupted split layout.
- **canonical search:** Repository issue searches found no older open issue describing the same Profiles → Contents → Extensions side-opening overlap symptom; the mechanically suggested candidates concern unrelated behavior.
