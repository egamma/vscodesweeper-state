# Issue #244590 — Git - Bad git diff handling for UTF-16 LE file

[https://github.com/microsoft/vscode/issues/244590](https://github.com/microsoft/vscode/issues/244590)

## Summary

Consolidate this report into the older, open encoding issue: both report false change highlighting on unchanged files whose working-tree encoding differs from Git's stored content. The Windows driver sample supplies a concrete UTF-16LE reproduction of that same defect.

## Change summary

Opening an unchanged UTF-16LE driver INF file produces false Git change decorations and garbled diff content.

## Best solution

Resolve the working-tree-encoding mismatch tracked by https://github.com/microsoft/vscode/issues/127441, preserving this report's Windows driver sample as a UTF-16LE reproduction alongside the existing Windows-1251 and CP1252 cases.

## Evidence

- **Verified older canonical:** https://github.com/microsoft/vscode/issues/127441 is open and was created on 2021-06-29, before this report. Its original report describes falsely highlighted changed lines despite a clean git status, with working-tree-encoding matching the editor encoding. This is the same reporter-observable false-change symptom, not merely another issue in the Git area.
- **Reported repository encoding:** The Windows-driver-samples .gitattributes at the latest attributes commit preceding this report, https://github.com/microsoft/Windows-driver-samples/commit/d5569c08aa2818c6240744bb47a00f67f20fdb54, specifies '*.inf text diff working-tree-encoding=UTF-16LE-BOM eol=crlf'. Thus scanner.inf is checked out as UTF-16LE with BOM while Git stores its normalized content as UTF-8.
- **Current source trace:** extensions/git/src/fileSystemProvider.ts readFile delegates to repository.buffer; extensions/git/src/git.ts:1586-1588 retrieves the original with 'git show --textconv', without working-tree encoding conversion. src/vs/workbench/contrib/scm/browser/quickDiffModel.ts:400-404 then decodes the original model using the working file's encoding. For this INF file, that interprets UTF-8 original bytes as UTF-16LE, producing garbage and false differences. This is source inspection, not an executed reproduction.
- **Reporter confirmation:** https://github.com/microsoft/vscode/issues/244590#issuecomment-2752659126 confirms the same behavior in 1.99.0 Insiders after the request to retest.
- **Independent corroboration:** The newer https://github.com/microsoft/vscode/issues/334092 describes garbled original content and false whole-file changes with working-tree-encoding. https://github.com/microsoft/vscode/issues/334092#issuecomment-5619426672 reports that retrieving filtered content resolved the equivalent CP932 case; https://github.com/microsoft/vscode/issues/334092#issuecomment-5791157361 identifies the older canonical. The newer report is supporting evidence, not the duplicate target.
