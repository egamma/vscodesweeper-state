# Issue #117556 — Onboard shared process to --prof-start

[https://github.com/microsoft/vscode/issues/117556](https://github.com/microsoft/vscode/issues/117556)

## Summary

The shared process still is not included in --prof-startup, despite maintainer agreement that its startup performance should be observable. Its architecture has changed from a renderer to a utility process, so the request remains useful but needs profiling-lifecycle planning.

## Change summary

Include shared-process startup CPU profiling in the existing --prof-startup workflow.

## Best solution

Have --prof-startup collect and report a shared-process CPU profile alongside the existing main, renderer, and extension-host profiles, with an explicit policy for its delayed startup and profiling cutoff.

## Evidence

- **Existing capability does not cover the request:** src/vs/code/node/cli.ts allocates profiler ports only for main, renderer, and extension host, starts Profiler sessions named main, extHost, and renderer, and stops only those three when the marker file is deleted. There is no shared-process session in this workflow.
- **Manual inspection is only partial coverage:** src/vs/platform/environment/node/environmentService.ts exposes parseSharedProcessDebugPort through inspect-sharedprocess and inspect-brk-sharedprocess. src/vs/platform/sharedProcess/electron-main/sharedProcess.ts passes the resulting inspector arguments to UtilityProcess.start, but --prof-startup does not enable or collect that inspector automatically.
