# Issue #197939 — Let extensions configure the "Start Discussion" for new comments

[https://github.com/microsoft/vscode/issues/197939](https://github.com/microsoft/vscode/issues/197939)

## Summary

The requested API capability is still missing: controller options customize the comment input, but not the initial “Start discussion” heading. Keep this accepted, team-authored request open; the later duplicate and extension-author feedback reinforce the need.

## Change summary

Allow extensions to configure the heading shown when users create a new comment thread from the gutter.

## Best solution

Expose a controller-wide default heading for new comment threads through the comments API, preserving explicit per-thread labels and the existing localized fallback. Review the public API contract with the comments owner before implementation.

- **Validation:** Using a comments sample extension, configure a provider-wide heading and create a thread through the gutter: its first rendered heading and accessible label must match the configured text. Repeat without the option to verify the localized default, and verify that explicit per-thread labels and existing input prompt/placeholder behavior remain unchanged.
- **Behavior:**

  > An extension can configure one default heading for new comment threads created by users through the gutter. The configured heading is present when the thread first appears, including its accessible label. Providers that do not configure it retain the localized “Start discussion” heading, and explicit per-thread labels continue to take precedence. A provider-wide value satisfies the extension-author use case recorded in the discussion.
- **Trace:**

  > CommentOptions in src/vscode-dts/vscode.d.ts and src/vs/editor/common/languages.ts exposes only input prompt and placeholder customization. ExtHostCommentController.options forwards options through the main-thread bridge, while $createCommentThreadTemplate() creates empty threads internally without an extension customization callback. CommentThreadHeader.createThreadLabel() in src/vs/workbench/contrib/comments/browser/commentThreadHeader.ts uses the thread label or the hardcoded localized fallback; CommentThreadWidget separately passes controller options to CommentReply. These source paths establish that input customization is not heading customization. Preserve explicit thread-label behavior, accessibility labeling, and existing comment creation semantics; unrelated Comments view behavior is outside scope. https://github.com/microsoft/vscode/issues/275375 is already consolidated here, and the remaining planning question is the public default-heading contract.
- **Open decisions:**
  - Should the controller-wide default heading be exposed as CommentOptions.threadLabel or CommentOptions.defaultThreadLabel?
