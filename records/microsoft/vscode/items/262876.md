# Issue #262876 — [prompts] One-Click install of Copilot Instructions / Prompts from private Github repos

[https://github.com/microsoft/vscode/issues/262876](https://github.com/microsoft/vscode/issues/262876)

## Summary

A real gap remains: current main supports one-click prompt and instruction installation from public URLs, but that path sends no authentication and therefore cannot read private GitHub content. The accepted Backlog request should remain open while maintainers choose the installation and authorization contract.

## Change summary

Allow one-click installation of prompts, instructions, and custom agents stored in private GitHub repositories without requiring users to manage personal access tokens.

## Best solution

Define a GitHub-specific private-content path for customization install URLs that requests explicit repository authorization and retrieves content through a CORS-compatible GitHub API, while preserving unauthenticated fetching for public and non-GitHub URLs. Repository-packaged customizations can already use agent plugins, but that does not replace installing an individual prompt or instruction.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/promptSyntax/promptUrlHandler.ts`, `src/vs/workbench/contrib/chat/browser/githubRepoFetcher.ts`, `src/vs/workbench/contrib/chat/browser/pluginGitCommandService.ts`, `src/vs/workbench/contrib/chat/test/browser`
- **Validation:** Add focused PromptUrlHandler tests with mocked request and authentication services: private GitHub content should request an authorized session and create the selected customization file; public URLs should retain the unauthenticated path; denied authorization and non-success responses should create no file and surface an error.
- **Behavior:**

  > A user can activate a one-click install URL for a prompt, instruction, or custom agent stored in a private GitHub repository and explicitly authorize VS Code to access that repository. After authorization, VS Code retrieves the requested content, asks for the destination and filename as it does today, creates the file, and opens it. Public URLs continue to work without requiring sign-in, and declined or insufficient authorization must not create a file or expose a token.
- **Trace:**

  > PromptUrlHandler in src/vs/workbench/contrib/chat/browser/promptSyntax/promptUrlHandler.ts recognizes the customization install routes, confirms the external request, and then performs an unauthenticated GET through IRequestService; there is no branch for private GitHub content. BrowserPluginGitCommandService in src/vs/workbench/contrib/chat/browser/pluginGitCommandService.ts demonstrates repository-scoped GitHub session acquisition, and githubRepoFetcher.ts demonstrates authenticated retrieval through api.github.com rather than raw.githubusercontent.com. PluginUrlHandler provides a separate repository-plugin distribution path, but it requires plugin packaging and does not satisfy individual-file install URLs. Preserve the existing confirmation, destination selection, naming, and unauthenticated behavior; do not broaden authentication to arbitrary hosts or silently attach credentials.
- **Open decisions:**
  - Should the public install contract continue accepting a private GitHub file URL and authorize its retrieval, or should private installs use a distinct GitHub repository/ref/path representation?
  - Should individual private-file installation be supported directly, or should private repositories be supported only as agent plugins with manifests?
  - Which GitHub URL forms are in scope for the first authenticated phase: raw content URLs, github.com blob URLs, gists, or all three?
