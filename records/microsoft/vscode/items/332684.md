# Issue #332684 — Synchronous terminal tool returns incomplete output after clearing pending input in Copilot-managed terminal

[https://github.com/microsoft/vscode/issues/332684](https://github.com/microsoft/vscode/issues/332684)

## Summary

Real race condition traceable in current main: when the rich-shell-integration execute strategy clears non-empty pending prompt input before running the requested command, the resulting spurious 'command finished' event for the cleared input isn't filtered out the way an actually-executing prior command is, so it can be mistaken for the result of the real command.

## Change summary

In a Copilot-managed terminal with unsubmitted pending prompt text, the synchronous terminal tool sometimes returns only the auto Ctrl+C cleanup output instead of the actual requested command's output.

## Best solution

In src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/richExecuteStrategy.ts, extend the stale-command filtering (currently keyed only off `executingCommandObject`) to also guard against the ETX sent by `ITerminalInstance.runCommand` (src/vs/workbench/contrib/terminal/browser/terminalInstance.ts:1042-1049) whenever the prompt has non-empty pending input but no command is yet executing, so a spurious onCommandFinished for the cleared input can't be mistaken for the real command's result.

## Evidence

- **ETX sent for any pending prompt text:** src/vs/workbench/contrib/terminal/browser/terminalInstance.ts:1042-1049 — `runCommand()` sends `\x03` (Ctrl+C) whenever `commandDetection.promptInputModel.value.length > 0`, not only when a command is confirmed still executing.
- **stale-command filter only covers an already-executing command:** src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/richExecuteStrategy.ts:106-124 — `staleMarker` is derived from `executingCommandObject?.marker`, which is undefined for merely-typed, unsubmitted input (e.g. `foo` with no Enter), so the filter is a no-op in exactly this scenario; the code's own comment (lines 106-113) documents that clearing stale input via ETX can produce a spurious `onCommandFinished` with exit code 130, but only accounts for the 'previous command still executing' case.
- **basic strategy avoids this by design:** src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/basicExecuteStrategy.ts:193-210 explicitly sends Ctrl+U instead of Ctrl+C for idle-prompt pending input specifically to avoid a spurious 130 exit; RichExecuteStrategy relies on the shared `runCommand()` helper which does not make this same distinction.
- **symptom match:** Reporter's captured tool output `> foo^C` matches exactly what a spurious finished-command event for the ETX-cleared `foo` input (rather than the real `pwd` command) would look like.
