# Issue #309028 — Allow clearing the undo/redo stack of a custom editor

[https://github.com/microsoft/vscode/issues/309028](https://github.com/microsoft/vscode/issues/309028)

## Summary

Keep this accepted API request open: current custom editors cannot explicitly invalidate retained undo/redo history while continuing to support subsequent undoable edits. It has 23 upvotes and reached the Backlog; the canonical search found no open issue owning the same request.

## Change summary

Allow a CustomEditorProvider to clear a custom document's undo/redo history when its retained edit callbacks can no longer be executed.

## Best solution

Design an explicit, document-scoped history-reset API for editable custom documents, preserving ordinary undo-across-save behavior unless the provider opts in. Settle its dirty-state and save-ordering semantics before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostCustomEditors.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadCustomEditors.ts`
- **Validation:** Use a minimal CustomEditorProvider that emits undoable edits: edit and save, request a history reset, and invoke Undo/Redo to verify pre-reset callbacks are never called. Emit another edit and verify its undo/redo works; verify save without reset still preserves history, another document is unaffected, and dirty-state behavior matches the agreed API contract.
- **Behavior:**

  > An editable custom document needs an explicit history boundary when previously emitted undo/redo callbacks are no longer valid, including after a save that discards provider-side state. After that boundary, standard Undo and Redo must not invoke invalidated callbacks, while subsequent edits remain undoable. Providers that do not request a reset must retain existing undo-across-save behavior, and resetting one document must not affect another. The API must define how resetting history interacts with unsaved changes and an in-progress save.
- **Trace:**

  > CustomEditorProvider.onDidChangeCustomDocument in src/vscode-dts/vscode.d.ts offers edit events or content-change events, but no reset signal. ExtHostCustomEditors.registerCustomEditorProvider in src/vs/workbench/api/common/extHostCustomEditors.ts caches edit callbacks in CustomDocumentStoreEntry and forwards edit IDs through src/vs/workbench/api/common/extHost.protocol.ts. MainThreadCustomEditorModel in src/vs/workbench/api/browser/mainThreadCustomEditors.ts maintains edit IDs, the current index, the save point, and resource undo elements; saveCustomEditor advances the save point without releasing history. Existing cleanup occurs during model disposal and redo-tail removal, not at a provider-selected boundary. The scope is editable CustomDocument providers, not general TextDocument or filesystem undo-stack manipulation; preserve default save semantics. The original request at https://github.com/microsoft/vscode/issues/296528 is closed without demonstrated implementation, and https://github.com/microsoft/vscode/issues/104693 concerns a different text-document contract. No linked open implementation PR appeared in the inspected timeline.
- **Open decisions:**
  - Should reset be permitted while the document is dirty, preserving its dirty state, or only at a clean/save boundary?
  - Should providers be able to request a reset at any time, including during saveCustomDocument, or should the API apply resets only after a successful save?

## Evidence

- **Existing API does not cover the request:** src/vscode-dts/vscode.d.ts:10407–10438 defines CustomDocumentEditEvent with document, undo, redo, and label only. CustomEditorProvider.onDidChangeCustomDocument at approximately lines 10578–10591 requires providers to consistently use edit events or content-change events; the latter gives up standard undo/redo rather than allowing a reset boundary. Inspection of stable and proposed API declarations found no custom-document history-reset capability.
- **Save retains history on current main:** MainThreadCustomEditorModel.saveCustomEditor in src/vs/workbench/api/browser/mainThreadCustomEditors.ts:875–890 records _savePoint = _currentEditIndex and clears dirty flags without clearing _edits or removing undo elements. Its undo and redo methods still dispatch retained edit IDs to the extension host.
- **Internal cleanup is not a provider capability:** MainThreadCustomEditorModel.dispose removes resource undo elements when the model is disposed. spliceEdits discards the redo tail and calls $disposeEdits, while CustomDocumentStoreEntry in src/vs/workbench/api/common/extHostCustomEditors.ts caches callbacks. Neither path exposes an extension-triggered reset of an open custom document.
- **Original report is closed, not a canonical:** https://github.com/microsoft/vscode/issues/296528 is closed and requests the same capability, initially on save. Its author repeatedly questioned the closure, including https://github.com/microsoft/vscode/issues/296528#issuecomment-3993640216; the inspected discussion supplies no implementation evidence. It cannot serve as an open duplicate target.
- **Canonical search and distinct precedent:** Repository searches for custom-editor undo and clearing undo history found no open canonical for this capability. https://github.com/microsoft/vscode/issues/103645 concerns intermittent save cancellation and concurrent undo operations, not provider-controlled history invalidation. The declined https://github.com/microsoft/vscode/issues/104693 concerns filesystem-backed text documents and cross-resource edits; that precedent does not establish a decision on this custom-document API request.
