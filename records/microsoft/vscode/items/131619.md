# Issue #131619 — Editor resolver: untyped `editorGroupFinder#findGroup` causes issues

[https://github.com/microsoft/vscode/issues/131619](https://github.com/microsoft/vscode/issues/131619)

## Summary

The architectural debt remains on current main: EditorResolverService still chooses a group from the untyped input before creating the typed editor, so type-specific matching can select the wrong group. The existing Backlog/debt classification remains appropriate.

## Change summary

Stop selecting an editor group from an untyped input before the resolver has created the typed editor needed for accurate matching.

## Best solution

Make group selection operate on the resolved typed editor while preserving custom-editor and webview lifecycle behavior that currently depends on knowing the target group during input creation.

## Plan brief

- **Likely files:** `src/vs/workbench/services/editor/browser/editorResolverService.ts`, `src/vs/workbench/services/editor/common/editorGroupFinder.ts`, `src/vs/workbench/services/editor/common/editorResolverService.ts`, `src/vs/workbench/contrib/customEditor/browser/customEditors.ts`, `src/vs/workbench/contrib/webviewPanel/browser/webviewPanel.contribution.ts`, `src/vs/workbench/services/editor/test/browser/editorResolverService.test.ts`
- **Validation:** Add an EditorResolverService regression test with two groups and multiple editor types for one resource, asserting that opening an untyped input reveals the group containing the resolved typed editor; run scripts/test.sh --grep 'EditorResolverService'.
- **Behavior:**

  > Opening an untyped resource that resolves to a custom or otherwise non-default editor must select the group based on the resolved typed editor's matching semantics. If that typed editor is already open in another group, VS Code must reveal or reuse the correct group rather than create or choose a group based only on the resource-shaped input. Existing explicit-group, side-group, locked-group, modal-editor, and live webview movement behavior must remain unchanged.
- **Trace:**

  > EditorResolverService.resolveEditor currently calls resolveUntypedInputAndGroup in src/vs/workbench/services/editor/browser/editorResolverService.ts before selecting and creating the registered typed editor. That helper invokes findGroup with IUntypedEditorInput, and editorGroupFinder.ts subsequently asks each existing typed EditorInput to match that incomplete input. The chosen group is then passed into doResolveEditor and into registered editor factories; CustomEditors uses group.id while constructing CustomEditorInput, explaining why the order cannot be swapped without tracing group-bound inputs. The open symptom report https://github.com/microsoft/vscode/issues/133761 confirms that mismatched notebook-cell and notebook resources can choose the wrong group. Keep the scope to editor resolution/group selection and preserve explicit preferred-group semantics and live custom-editor/webview transfer behavior.

## Evidence

- **current source:** src/vs/workbench/services/editor/browser/editorResolverService.ts:117-126 still implements resolveUntypedInputAndGroup by passing the untyped editor directly to findGroup before editor resolution.
- **incorrect matching boundary:** src/vs/workbench/services/editor/common/editorGroupFinder.ts:153-186 searches groups before fallback, while lines 253-268 call EditorInput.matches with the untyped input; the selected typed editor and its override are not yet available.
- **architectural blocker:** src/vs/workbench/services/editor/browser/editorResolverService.ts:786-830 passes the preselected IEditorGroup into registered editor factories, and src/vs/workbench/contrib/customEditor/browser/customEditors.ts:188-198 uses group.id when constructing CustomEditorInput. This makes changing the ordering a cross-component lifecycle design rather than a local cleanup.
- **remaining consequence:** The younger open issue https://github.com/microsoft/vscode/issues/133761 documents a concrete wrong-group symptom caused by untyped matching and explicitly identifies https://github.com/microsoft/vscode/issues/131619 as the broader blocker. - **prior blocker discussion:** https://github.com/microsoft/vscode/issues/121322 is older but closed and narrower: its discussion explains that webview inputs need group information to transfer a live webview without rerendering, so it cannot serve as an open duplicate target.
