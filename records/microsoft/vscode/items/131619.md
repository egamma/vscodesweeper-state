# Issue #131619 — Editor resolver: untyped `editorGroupFinder#findGroup` causes issues

[https://github.com/microsoft/vscode/issues/131619](https://github.com/microsoft/vscode/issues/131619)

## Summary

The underlying debt remains: the resolver selects a group before resolving the editor type, and editor factories still require that group. Keep this issue as the broader cleanup rather than consolidating it into a narrower notebook symptom or treating a historical workaround as completion.

## Change summary

Remove editor-group selection's dependence on unresolved editor inputs so matching and group creation respect the resolved editor's identity.

## Best solution

Make target-group selection reliable for resolved editor identities without breaking webview ownership and movement. First establish how group-dependent editor factories can support that ordering, then validate same-resource editors and notebook-cell navigation across groups.

- **Behavior:**

  > Opening an editor must select its target group using the identity of the editor that will actually open, rather than an ambiguous unresolved resource. Existing editors should be revealed in the appropriate group when requested, and provisional selection must not leave unintended extra groups. Same-resource editors of different types must remain distinguishable. Explicit group requests, locked-group behavior, and webview movement must retain their intended semantics.
- **Trace:**

  > EditorResolverService.resolveUntypedInputAndGroup in src/vs/workbench/services/editor/browser/editorResolverService.ts invokes findGroup before resolveEditor selects an editor registration or constructs a typed input. The finder in src/vs/workbench/services/editor/common/editorGroupFinder.ts performs matches checks and can create groups at that stage. Factory types in src/vs/workbench/services/editor/common/editorResolverService.ts still require IEditorGroup, and the resolver supplies the early-selected group to their creation methods. The historical webview constraint is documented in https://github.com/microsoft/vscode/issues/121322; WebviewInput.updateGroup remains present in src/vs/workbench/contrib/webviewPanel/browser/webviewEditorInput.ts. The remaining design trace must enumerate group-dependent factory consumers and establish their ownership and movement requirements before choosing a resolution lifecycle. Preserve explicit placement, reveal options, locked groups, and webview content continuity; do not broaden this into the separate options.override API redesign at https://github.com/microsoft/vscode/issues/126997.

## Evidence

- **Current resolver ordering:** src/vs/workbench/services/editor/browser/editorResolverService.ts: resolveUntypedInputAndGroup invokes findGroup with the untyped input. resolveEditor calls this before getEditor selects the registration, before options.override is populated from that registration, and before doResolveEditor constructs the typed input.
- **Matching and side effects remain coupled:** src/vs/workbench/services/editor/common/editorGroupFinder.ts still accepts IUntypedEditorInput. isActive and isOpened call typed editors' matches methods with that input; doFindGroup can create groups for SIDE_GROUP or locked-group fallback before editor resolution.
