# Issue #198997 — Aux window: support to navigate between parts between windows

[https://github.com/microsoft/vscode/issues/198997](https://github.com/microsoft/vscode/issues/198997)

## Summary

Floating windows already support local Focus Next/Previous Part navigation, but directional part navigation still uses the main-window layout and there is no cross-window part traversal in the inspected path. Keep this accepted Backlog request open to define the remaining cross-window behavior.

## Change summary

Support navigating between workbench parts when floating editor windows are involved.

## Best solution

Define consistent keyboard navigation semantics for floating windows, including whether part traversal stays within the active window or crosses to the main window. Preserve existing local focus cycling and handle editor-history and Go to Definition concerns separately unless they prove to share the same missing behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/actions/navigationActions.ts`, `src/vs/workbench/browser/layout.ts`, `src/vs/workbench/services/layout/browser/layoutService.ts`
- **Validation:** With a main window containing visible sidebar and panel parts and a floating window containing split editor groups, invoke workbench.action.focusNextPart, workbench.action.focusPreviousPart and all four workbench.action.navigate* commands from each window. Verify the agreed window-transition behavior, preserve intra-window editor-group navigation, and repeat with the floating-window status bar hidden.
- **Behavior:**

  > Keyboard part navigation should behave consistently when the workspace includes floating editor windows. Current Focus Next/Previous Part commands already cycle locally in an auxiliary window, while directional navigation relies on the main-window part layout. Acceptance must specify when focus remains in the active window and when it crosses windows, then verify both directions without regressing main-window navigation or split-editor navigation.
- **Trace:**

  > BaseFocusAction.findVisibleNeighbour in src/vs/workbench/browser/actions/navigationActions.ts branches on isAuxiliaryWindow(getActiveWindow()) and cycles between editor and status bar; focusNextOrPreviousPart passes the active window to layoutService.focusPart. BaseNavigationAction.run attempts editor-group movement before querying layoutService.getVisibleNeighborPart. That method in src/vs/workbench/browser/layout.ts reads the main workbenchGrid and uses mainWindow visibility, establishing the remaining window-layout boundary without executing code. Preserve the existing local F6/Shift+F6 behavior unless the maintainer explicitly chooses otherwise, and preserve editor-group movement precedence. The comment at https://github.com/microsoft/vscode/issues/198997 raises history and definition navigation as additional concerns, not a confirmed shared root cause. https://github.com/microsoft/vscode/issues/193267 concerns detachable panels rather than the same navigation contract.
- **Open decisions:**
  - Should Focus Next/Previous Part remain local to each window, or include parts in other windows; if cross-window, what traversal order should users observe?
  - At a floating editor group's directional boundary, should Navigate Left/Right/Up/Down stop, enter a main-window part, or select another window according to screen position?

## Evidence
