# Issue #326591 — Feature Request: Support external browser password autofill in integrated browser

[https://github.com/microsoft/vscode/issues/326591](https://github.com/microsoft/vscode/issues/326591)

## Summary

Keep this accepted feature request open: persistent browser sessions do not provide autofill from external password stores, and no verified canonical issue covers that gap. The request received 21 upvotes and was explicitly promoted to Backlog.

## Change summary

Allow integrated-browser login forms to use credentials saved in an external browser or OS password manager.

## Best solution

Define a supported, user-authorized credential-provider integration for integrated-browser login forms, preserving session isolation and explicit control over agent access. This needs a feasibility and product-design pass rather than assuming that sharing an external browser profile is supported.

## Plan brief

- **Likely files:** `src/vs/platform/browserView/electron-main/browserSession.ts`, `src/vs/platform/browserView/electron-main/browserView.ts`, `src/vs/platform/browserView/common/browserView.ts`, `src/vs/workbench/contrib/browserView/electron-browser/features/browserDataStorageFeatures.ts`
- **Validation:** Using a test account in the chosen supported external credential provider, save credentials, open the matching login page in the integrated browser, authorize autofill, and verify successful sign-in without manual copying. Also verify that a different origin cannot receive those credentials and that denying provider access leaves manual sign-in working.
- **Behavior:**

  > Users currently cannot fill integrated-browser website login forms using credentials already saved in an external browser or OS password manager. The goal is a supported, user-authorized way to reuse those credentials without manual copying. Acceptance must demonstrate matching-origin autofill and successful sign-in with a test account, while rejecting unrelated origins and retaining manual sign-in when access is denied. Remembering cookies or adding an independent local password store alone does not satisfy the external-store request.
- **Trace:**

  > BrowserSession in src/vs/platform/browserView/electron-main/browserSession.ts creates VS Code-owned Electron sessions using a persistent partition, workspace-local storage, or in-memory partitions. workbench.browser.dataStorage in src/vs/workbench/contrib/browserView/electron-browser/features/browserDataStorageFeatures.ts controls persistence and sharing, not external credential access; its agent scope explicitly permits agent access to session data. The login handler in src/vs/platform/browserView/electron-main/browserView.ts supplies tunnel-proxy credentials, not website-form autofill. The boundary is integration between an external credential provider and the embedded page; preserve existing session isolation, trust restrictions, and agent-sharing gates. https://github.com/microsoft/vscode/issues/300149 concerns HTTP Basic Authentication and is separate. The trace does not establish a usable provider API or cross-platform adoption path, so feasibility and user-visible authorization semantics remain unresolved.
- **Open decisions:**
  - Which external credential providers and operating systems should the initial supported contract cover?
  - What explicit user authorization is required before a provider may fill credentials for an origin?
  - Should external-store autofill be available in agent-shared sessions, and what additional consent or restrictions should apply there?

## Evidence

- **Accepted community demand:** https://github.com/microsoft/vscode/issues/326591 has 21 body upvotes, the Backlog milestone, and a September 14 bot comment confirming promotion after reaching the community threshold. The September 5 comment also requests remembering and autofilling passwords, but local password saving alone would not fulfill the original external-store request.
- **Existing capability does not cover the request:** src/vs/workbench/contrib/browserView/electron-browser/features/browserDataStorageFeatures.ts registers workbench.browser.dataStorage for cookies, cache, and storage across global, workspace, ephemeral, and agent scopes. In src/vs/platform/browserView/electron-main/browserSession.ts, getOrCreateGlobal uses persist:vscode-browser and getOrCreateWorkspace uses workspace-local browserStorage; neither factory connects to an external browser profile or credential provider. Searches of the browserView implementation found no password-autofill integration.
- **Documented session persistence:** https://code.visualstudio.com/docs/debugtest/integrated-browser documents persistent global/workspace session storage and external-browser opening. Retaining an authenticated session can reduce repeated sign-ins, but neither capability fills a login form using credentials saved in Edge or an OS password manager.
- **Related issue is not a duplicate:** https://github.com/microsoft/vscode/issues/300149 is open and requests an HTTP Basic Authentication prompt for pages returning unauthorized responses. Its discussion concerns inline Basic Auth credentials, not saved-password autofill into website forms, so it does not own this request's scope.
