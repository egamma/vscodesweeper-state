# Issue #332493 — Feature Request: Expose settings.json configuration for integrated browser proxy

[https://github.com/microsoft/vscode/issues/332493](https://github.com/microsoft/vscode/issues/332493)

## Summary

Keep open: current browser configuration does not expose a local debugging proxy or bypass list, and remote-workspace proxying does not cover this request. The issue remains within its Backlog Candidates community-review period; neither a verified duplicate nor a landed implementation was found.

## Change summary

Allow integrated-browser traffic to use a configurable local proxy and bypass list without changing the system-wide proxy.

## Best solution

Provide an explicit settings-based proxy configuration for local integrated-browser sessions while preserving existing remote-tunnel behavior and leaving unrelated VS Code traffic unchanged. Settle whether this uses dedicated browser settings or opt-in reuse of the existing HTTP settings before implementation.

- **Behavior:**

  > A developer can configure integrated-browser traffic to use a local debugging proxy without changing the system-wide proxy. Browser requests should observe the proxy's rewrites and mocks, including when the same page is shared with an agent. A configured bypass list should exclude selected destinations, and unconfigured users should retain their existing behavior. Acceptance includes a locally proxied rewritten response, bypass behavior, and preservation of existing remote-workspace networking.
- **Trace:**

  > BrowserViewWorkbenchService in src/vs/workbench/contrib/browserView/electron-browser/browserViewWorkbenchService.ts forwards browser configuration to main, but its exposed proxy setting only enables remote-workspace routing. The corresponding registration is in features/browserRemoteFeatures.ts; the shared window contract and main-process application path are in src/vs/platform/browserView/common/browserView.ts and electron-main/browserViewMainService.ts. BrowserSession owns Electron storage identities, and BrowserSessionRemote applies tunnel proxy information through Electron session.setProxy(); shared sessions mean settings scope cannot be treated as independent per-tab state. Source inspection establishes the missing configuration surface, not a runtime networking failure. Preserve existing remote-tunnel credentials, certificate handling, agent sharing controls, and unrelated HTTP traffic. The contributor discussion at https://github.com/microsoft/vscode/issues/332493 leaves the configuration contract unresolved; https://github.com/microsoft/vscode/issues/331926 concerns a different remote-host capability.
- **Open decisions:**

  - Should proxy configuration be user-wide or workspace-specific, and what behavior should users see when windows with different configurations share a global browser session?
  - When explicit browser proxy configuration and remote-workspace proxying are both enabled, which routing behavior should take precedence?
