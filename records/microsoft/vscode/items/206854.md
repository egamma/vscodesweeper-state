# Issue #206854 — Debug console is very slow with a single long line

[https://github.com/microsoft/vscode/issues/206854](https://github.com/microsoft/vscode/issues/206854)

## Summary

Keep open: a maintainer reproduced the freeze and traced current debug-console hot paths for a continuously growing line, while a later report confirms a similar high-throughput hang. No older issue with the same observable symptom is established as the canonical owner.

## Change summary

Sustained debug-adapter output, especially carriage-return output that accumulates into one very long Debug Console line, progressively slows and can freeze VS Code.

## Best solution

Bound or compact accumulated REPL output without breaking output ordering, grouping, ANSI handling, or normal multiline output, and avoid serially queueing every adapter output event when safe batching can preserve semantics.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/common/replModel.ts`, `src/vs/workbench/contrib/debug/browser/debugSession.ts`, `src/vs/workbench/contrib/debug/test/common/replModel.test.ts`
- **Validation:** Add a debug REPL performance regression test that feeds a large sequence of carriage-return updates and asserts bounded completion time and retained responsiveness, plus a throughput test for many newline-delimited output events; existing REPL ordering and grouping tests must continue to pass.
- **Behavior:**

  > The Debug Console must remain responsive while a debug adapter emits sustained output. Carriage-return progress updates must not create an ever-growing line whose processing eventually freezes the window, and high-throughput newline output must not prevent pausing or interacting with the debugger. Output ordering and ordinary multiline display must remain correct. Acceptance requires regression coverage for both repeated carriage-return updates and a large burst of newline-delimited output.
- **Trace:**

  > The reporter's script prints flushed progress updates ending in `\r`; maintainer roblourens reproduced the freeze and found that changing `\r` to `\n` avoids it. Profiling pointed to REPL output merging in src/vs/workbench/contrib/debug/common/replModel.ts and raised serialized output processing in src/vs/workbench/contrib/debug/browser/debugSession.ts as a second bottleneck. A later commenter supplied independent C++ and JavaScript high-throughput cases where Debug Console output stops and the window hangs. The investigation must distinguish the unbounded-single-line cost from general event-backlog pressure before choosing the product behavior. Preserve output order, grouping, ANSI semantics, and normal multiline output; do not treat clearing the entire console at session start as a fix. The newer closed https://github.com/microsoft/vscode/issues/238441 is related evidence, not a canonical duplicate for this re-reviewed issue.
- **Open decisions:**
  - For carriage-return progress output, should the Debug Console replace the current logical line to mirror terminal-style progress, or retain history with a bounded truncation policy?
  - If retained Debug Console output must be bounded, what user-observable limit and truncation indication should apply?
