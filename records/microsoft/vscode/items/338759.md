# Issue #338759 — Opening file with Cmd+O on macOS sometimes destroys existing workspace

[https://github.com/microsoft/vscode/issues/338759](https://github.com/microsoft/vscode/issues/338759)

## Summary

Credible, recently-emerged report of the macOS native Open dialog (triggered by Cmd+O / workbench.action.files.openFileFolder) auto-deselecting the chosen file so that clicking Open instead opens its parent folder, replacing the current workspace. The reporter confirmed it still reproduces on the latest stable (1.139.1) with a video; I could not pin the root cause from source since the behavior lives in the native NSOpenPanel/Electron dialog interaction, not in a VS Code code path I can trace or fix from the checkout alone.

## Change summary

On macOS, opening a file via Cmd+O sometimes has the selected file spontaneously deselect right after picking it, so clicking Open opens the containing folder (destroying the current workspace) instead of the intended file.

## Best solution

Needs investigation on an actual macOS 26 (Tahoe) machine to determine whether this is a native NSOpenPanel/Electron regression (likely, given the reporter says it started 'in the past month or so' and runs Darwin 25.6.0) or something VS Code's dialog result handling in fileDialogService.ts/dialogMainService.ts can work around (e.g. debouncing the dialog's selection-changed/Open-click race). If it's confirmed to be an Electron/macOS panel bug, it should be tracked as upstream and possibly reported to Electron.
