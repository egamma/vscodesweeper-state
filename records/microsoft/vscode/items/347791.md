# Issue #347791 — Need terminal profile support for Copilot harness

[https://github.com/microsoft/vscode/issues/347791](https://github.com/microsoft/vscode/issues/347791)

## Summary

Keep open: current shell-selection and initialization settings only partially cover repository-configured terminal profiles. The Windows initialization requirements consolidated into this issue remain a meaningful gap.

## Change summary

Support repository-specific shell executables, initialization arguments, and environment settings in Copilot harness command execution.

## Best solution

Provide supported, deterministic workspace-scoped shell initialization for Copilot commands, including Windows launcher-based environments, and document which terminal settings each harness honors. Preserve command lifecycle behavior and existing authorization controls.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostTerminalContribution.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostShellInitSynchronizer.ts`, `src/vs/workbench/contrib/terminal/browser/terminalProfileResolverService.ts`, `src/vs/platform/agentHost/node/copilot/copilotShellTools.ts`, `src/vs/platform/agentHost/node/agentHostTerminalManager.ts`, `src/vs/platform/agentHost/common/copilotCliConfig.ts`
- **Validation:** In a trusted Windows workspace, configure a repository launcher that sets EXAMPLE_DEV_ENV_READY=1 and adds a tool directory to PATH. Compare manual terminal execution with Copilot root and delegated shell commands: verify the variable and tool resolve before commands run, initialization failure is reported, and exit status and cancellation remain correct. Add corresponding automated coverage once the execution contract is selected.
- **Behavior:**

  > Copilot shell commands should run in the repository-configured development environment without asking the model to remember bootstrap commands. Executable discovery, initialization arguments, environment variables, and command language must be honored consistently, including delegated execution. Acceptance includes the Windows launcher reproduction preserved in https://github.com/microsoft/vscode/issues/348088, successful initialization before command execution, and explicit initialization failures. Existing approvals, cancellation, output capture, and exit status must remain intact.
- **Trace:**

  > TerminalProfileResolverService resolves terminal.integrated.agentHostProfile.<os>, but AgentHostTerminalContribution forwards only the resolved executable path. Host-managed ShellManager terminals use that executable without the configured profile arguments; the custom terminal override is unsupported on Windows. AgentHostShellInitSynchronizer separately supplies standard Bash/PowerShell startup and Python activation, which is not arbitrary repository-profile initialization. These existing capabilities provide partial coverage but do not establish a completed fix. The remaining uncertainty is the supported workspace execution contract and how it applies to SDK-owned Windows commands and delegated work. Keep shared existing-terminal interaction and the broader observability requests in https://github.com/microsoft/vscode/issues/343575 and https://github.com/microsoft/vscode/issues/346123 outside this feature's essential scope.
- **Open decisions:**
  - Should Copilot honor existing terminal-profile configuration directly, or expose a distinct workspace execution contract with documented precedence?
  - Must configured initialization provide a persistent shell environment, or is deterministic initialization of fresh command processes sufficient?
