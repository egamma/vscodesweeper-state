# Issue #285427 — Reference folder task in multi-root workspace

[https://github.com/microsoft/vscode/issues/285427](https://github.com/microsoft/vscode/issues/285427)

## Summary

Keep this accepted feature request open: current task configuration still cannot reference folder-scoped tasks from a workspace-level dependency list. It has 22 upvotes and was promoted to Backlog; the earlier requests are closed, and no verified open canonical absorbs this work.

## Change summary

Allow tasks defined in a .code-workspace file to depend on existing tasks in explicitly selected workspace folders.

## Best solution

Provide an unambiguous, documented workspace-to-folder task reference that supports both configured and extension-provided folder tasks while preserving existing dependency ordering and folder-local resolution. Settle the public reference syntax before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/tasks/common/taskConfiguration.ts`, `src/vs/workbench/contrib/tasks/common/jsonSchema_v2.ts`, `src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts`, `src/vs/workbench/contrib/tasks/test/common/taskConfiguration.test.ts`
- **Validation:** Add parser coverage in taskConfiguration.test.ts for the agreed workspace-to-folder reference contract. Manually run a workspace-level aggregate over two folders containing identically labeled tasks, verifying explicit folder selection, sequential and parallel execution, an extension-provided folder task, and a clear diagnostic for an unresolved reference; existing local dependsOn references must remain unchanged.
- **Behavior:**

  > A task authored in a .code-workspace file should be able to invoke existing tasks from selected folders in that multi-root workspace without copying their definitions. Folder selection must remain unambiguous when different folders use the same task label. Both configured tasks and extension-provided folder tasks should be addressable, including the reporter's Java buildArtifact example. Acceptance checks should cover dependency ordering, unresolved references, and unchanged behavior for existing folder-local and workspace-local dependencies.
- **Trace:**

  > TaskDependency.from and uriFromSource in src/vs/workbench/contrib/tasks/common/taskConfiguration.ts derive every dependency URI from the source configuration rather than an explicitly selected folder. AbstractTaskService._createResolver in browser/abstractTaskService.ts resolves within URI-keyed task groups, and TerminalTaskSystem._executeTask in browser/terminalTaskSystem.ts already consumes URI-qualified dependency objects. _createRunnableTask demonstrates internal cross-folder aggregation, but current JSON configuration does not expose that capability. The source trace establishes the missing authored reference contract; it does not settle its syntax or folder identity semantics. Preserve existing unqualified dependency resolution, ordering, and provider resolution, and do not expand this request into arbitrary folder-to-folder references or direct extension task definitions in workspace files. The latter is separately tracked at https://github.com/microsoft/vscode/issues/93149; earlier matching requests at https://github.com/microsoft/vscode/issues/185084 and https://github.com/microsoft/vscode/issues/84800 closed for insufficient upvotes.
- **Open decisions:**
  - What public dependsOn syntax identifies a folder task, and should the folder selector use the workspace folder's configured name or its workspace-relative path?

## Evidence

- **Current configuration boundary:** src/vs/workbench/contrib/tasks/common/taskConfiguration.ts:1324–1344, TaskDependency.uriFromSource/from, assigns dependencies the URI of their configuration source. Dependencies authored in a workspace file receive the workspace configuration URI; neither string references nor task-identifier objects select a different workspace folder.
- **Resolver and execution path:** src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts:1962–2050, _createResolver, resolves labels and task identifiers within the supplied URI's task group. src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts:535–580 passes dependency.uri and dependency.task to that resolver. Consequently, exposing folder tasks in the picker does not make them addressable from workspace-level dependsOn.
- **Existing-capability check:** src/vs/workbench/contrib/tasks/common/jsonSchema_v2.ts:65–98 supports dependsOn strings and task-identifier objects, but no folder-selection contract. The task settings in browser/task.contribution.ts contain no setting that changes this scope. workbench.action.tasks.runTask provides interactive execution, not declarative workspace-to-folder composition. _createRunnableTask can internally construct URI-qualified dependencies, but this is not an authored workspace-task capability.
- **Previously requested, not implemented:** https://github.com/microsoft/vscode/issues/185084 and https://github.com/microsoft/vscode/issues/84800 describe the same workspace-to-folder dependency capability. Both are closed after failing the community-upvote threshold, not because a fix landed or a maintainer rejected the capability on technical grounds; neither is an eligible duplicate canonical.

Its maintainer comment, https://github.com/microsoft/vscode/issues/93149#issuecomment-602477170, discusses determining the folder for those definitions. Referencing already-existing folder tasks is a different observable capability, so this older issue does not establish a duplicate.
