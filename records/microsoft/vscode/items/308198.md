# Issue #308198 — Feature Request: Add a setting to configure the default agent (Agent/Plan/Ask) for new chat sessions

[https://github.com/microsoft/vscode/issues/308198](https://github.com/microsoft/vscode/issues/308198)

## Summary

This remains a valid, community-promoted Backlog request: 45 upvotes demonstrate demand for choosing the initial built-in chat agent, and no verified older canonical owns the same request.

## Change summary

Allow users or workspaces to configure which built-in or custom agent is selected when a new chat session starts.

## Best solution

Define a chat setting for the initial agent used by genuinely new sessions, while preserving the existing agent for restored sessions and handling unavailable custom-agent identifiers predictably.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/chatConfiguration.ts`, `src/vs/workbench/contrib/chat/browser/chatWidget.ts`, `src/vs/workbench/contrib/chat/browser/chatWidgetService.ts`
- **Validation:** Add targeted chat tests that create a new session under each configured default, verify the selected agent, verify restored sessions retain their recorded agent, and verify the agreed fallback for an unavailable custom-agent identifier.
- **Behavior:**

  > Users can configure the agent initially selected for a new Copilot Chat session, including at workspace scope if that is the chosen contract. Starting a genuinely new session uses that configured default without manual picker interaction. Restoring an existing session does not overwrite its recorded agent. Invalid or unavailable custom-agent identifiers follow a documented fallback rather than leaving the picker in an inconsistent state.
- **Trace:**

  > The report distinguishes new-session initialization from explicit URL invocation and restored sessions. The relevant boundary is chat configuration plus the browser-side session/widget initialization path; existing picker changes and persisted session restoration must remain unchanged. No older canonical with the same observable request was verified, and the Backlog promotion with 45 upvotes establishes enough demand for a maintainer-led design session. The uncertainty starts at the public setting contract: whether custom identifiers are supported, which configuration scopes apply, and how unavailable configured agents fall back.
- **Open decisions:**
  - Should the setting accept only the built-in Agent, Plan, and Ask identifiers, or also custom-agent identifiers?
  - Should the default be configurable at user, profile, remote, and workspace scopes, or should team-controlled workspace configuration be excluded?
  - When the configured agent is unavailable, should a new session fall back to Agent or retain the most recently available selection?
