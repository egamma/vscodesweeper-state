# Issue #241338 — Allow extension to modify "Debug Console" contents

[https://github.com/microsoft/vscode/issues/241338](https://github.com/microsoft/vscode/issues/241338)

## Summary

This is an accepted Backlog feature request with 26 community upvotes, and the broad extension API for transforming and enriching Debug Console content remains a real gap. It should stay open for API and product design rather than be closed for age.

## Change summary

Expose extensibility for transforming, filtering, grouping, annotating, exporting, pausing, and otherwise inspecting Debug Console output.

## Best solution

Define a narrowly scoped Debug Console extension API that preserves debugger ordering, source mapping, ANSI styling, accessibility, and performance while enabling extensions to observe and present structured output. The maintainer design should first decide whether extensions may mutate the canonical REPL model or instead contribute derived views and actions.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.d.ts`, `src/vs/workbench/api/common/extHostDebugService.ts`, `src/vs/workbench/api/browser/mainThreadDebugService.ts`, `src/vs/workbench/contrib/debug/common/debugModel.ts`, `src/vs/workbench/contrib/debug/browser/repl.ts`
- **Validation:** End the plan with extension-host API tests and Debug Console model/UI tests demonstrating the selected extensibility model on interleaved adapter output while preserving ordering, source links, ANSI styling, and existing console filtering.
- **Behavior:**

  > Extensions should be able to build useful Debug Console enhancements without forcing users to repeatedly copy output into an editor. The supported contract must define which output can be observed or transformed and how filtering, grouping, annotations, export, and interaction compose with live adapter output. Existing debugger output ordering, source navigation, ANSI presentation, keyboard interaction, and accessibility must remain intact for users without participating extensions.
- **Trace:**

  > The request belongs to the debug REPL path: extension-host debug integration is exposed through `src/vs/workbench/api/common/extHostDebugService.ts` and `src/vs/workbench/api/browser/mainThreadDebugService.ts`, while Debug Console entries and presentation are centered in `src/vs/workbench/contrib/debug/common/debugModel.ts` and `src/vs/workbench/contrib/debug/browser/repl.ts`. Any public contract would begin as a proposed API in `src/vscode-dts/vscode.proposed.d.ts`. The uncertainty starts at ownership: allowing mutation of canonical REPL elements affects ordering, identity, source links, persistence, and other extensions, while a derived-view or contribution model has different observable capabilities. Keep adapter protocol behavior and the default console unchanged; the plan should not attempt to implement every listed analytics feature in core.
- **Open decisions:**
  - May an extension replace or reorder canonical Debug Console entries, or may it only observe them and contribute a derived presentation?
  - Is the API scoped per debug session, per console, or globally across all active debug sessions?
  - Can multiple extensions transform the same output, and if so what user-observable ordering and conflict semantics apply?
  - Which metadata and interaction contributions are public: structured fields, decorations and annotations, filtering/grouping providers, commands, or a separate custom view?
