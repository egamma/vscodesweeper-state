## Evidence

- **Complete reproduction:** https://github.com/microsoft/vscode/issues/326572 supplies five reproduction steps, Windows 11, VS Code 1.129.1, Speech 0.16.0, ja-JP, and a useful short-versus-long response comparison. Both the stop button and Escape reset the controls while audio continues; restarting produces overlapping playback. There are no independent confirmations.
- **Current core cancellation path:** In src/vs/workbench/contrib/chat/electron-browser/actions/voiceChatActions.ts, ChatSynthesizerSessions.stop() calls activeSession.dispose(true). MainThreadSpeech in src/vs/workbench/api/browser/mainThreadSpeech.ts forwards token cancellation to $cancelTextToSpeechSession; src/vs/workbench/api/common/extHostSpeech.ts cancels the provider token and removes the synthesizer reference. This establishes cancellation propagation, not successful native playback termination.
- **Long-response boundary:** ChatSynthesizerSessions.parseNextChatResponseChunk in src/vs/workbench/contrib/chat/electron-browser/actions/voiceChatActions.ts sends the remaining complete response as one chunk. SpeechService.createTextToSpeechSession in src/vs/workbench/contrib/speech/browser/speechService.ts resets its active state on cancellation independently of audio termination, so restored controls alone do not prove playback stopped.
- **Provider investigation lead:** https://github.com/microsoft/vscode-speech/blob/main/src/extension.ts connects provider cancellation to AbortController.abort(), then Synthesizer.synthesize's abort handler calls the native synthesizer.stop(). Lines 203–208 also document an existing workaround for synthesis failing to stop, referencing https://github.com/Azure-Samples/cognitive-services-speech-sdk/issues/2367 and https://github.com/Azure-Samples/cognitive-services-speech-sdk/issues/2350. These are leads, not proof of this report's root cause or a fix.
