# Issue #326572 — VS Code Speech cannot stop playback for long GitHub Copilot Chat responses

[https://github.com/microsoft/vscode/issues/326572](https://github.com/microsoft/vscode/issues/326572)

## Summary

Keep open: the supplied Windows 11 and Japanese-language steps suffice to retest the long-response cancellation failure, but source inspection does not confirm its cause or resolution. Current main still exposes provider-backed read-aloud cancellation; newer built-in dictation does not establish that this playback defect is fixed.

## Change summary

Stopping a long Copilot read-aloud response resets the controls without stopping audio, allowing subsequent playback to overlap.

## Best solution

Reproduce the long-response failure and establish whether cancellation is lost in the core speech bridge or honored incorrectly by VS Code Speech. Restore reliable playback termination at the responsible boundary; if the defect is provider-owned, transfer the issue to microsoft/vscode-speech rather than closing it or asking the reporter to re-file.

## Evidence

- **Complete reproduction report:** https://github.com/microsoft/vscode/issues/326572 specifies Windows 11, VS Code 1.129.1, VS Code Speech 0.16.0, Japanese ja-JP, and a start-stop-restart sequence. Long responses continue speaking and overlap; short responses remain stoppable. Disabling Claude Code and starting a new conversation did not resolve it.
- **Core stop path:** In src/vs/workbench/contrib/chat/electron-browser/actions/voiceChatActions.ts, StopReadAloud and StopReadChatItemAloud both invoke ChatSynthesizerSessions.stop(), which calls activeSession.dispose(true). Cancellation also disposes the scoped progress context, so an icon reset alone does not demonstrate that audible playback has stopped.
- **Provider boundary remains unresolved:** src/vs/workbench/contrib/speech/browser/speechService.ts passes the session cancellation token to the speech provider. src/vs/workbench/api/browser/mainThreadSpeech.ts forwards cancellation through $cancelTextToSpeechSession; src/vs/workbench/api/common/extHostSpeech.ts cancels the token supplied to provideTextToSpeechSession and removes the synthesizer. This establishes the intended cancellation chain, not whether VS Code Speech actually stops long Japanese audio.
- **Long-response path:** ChatSynthesizerSessions.parseNextChatResponseChunk() sends the remaining completed response as one synthesis chunk, while start() awaits synthesis through raceCancellation. This is a relevant distinction between long and short responses, but does not conclusively identify a length-dependent defect.
- **Related reports are not open canonicals:** https://github.com/microsoft/vscode/issues/214878 describes the same icon-reset and overlapping-voices symptom, including a report that reinstalling only temporarily helped. https://github.com/microsoft/vscode/issues/244448 also reports unstoppable playback. Both are currently closed, so neither qualifies as a duplicate target; neither inspected discussion supplies a concrete fixing commit.
- **Newer report does not prove resolution:** https://github.com/microsoft/vscode/issues/330473 is newer and closed after a maintainer suggested built-in dictation. Its discussion does not establish that long-response text-to-speech cancellation was repaired, and it cannot serve as an older open canonical for this re-reviewed item.
- **Inspection limits and ownership:** Read-only searches found no qualifying open canonical or open microsoft/vscode PR referencing this issue. The checkout is shallow, limiting commit provenance, and no playback was executed. Copilot is in scope and VS Code Speech is team-owned; extension involvement alone does not justify a caused-by-extension close.
