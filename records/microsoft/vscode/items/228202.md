# Issue #228202 — Azure DevOps - Enable seamless Azure DevOps repository cloning in VSCode similar to GitHub

[https://github.com/microsoft/vscode/issues/228202](https://github.com/microsoft/vscode/issues/228202)

## Summary

Keep this accepted feature request open: the built-in GitHub credential integration does not cover Azure DevOps cloning, including the reported Remote-SSH workflow. It has 21 upvotes and was promoted to Backlog; the related requests do not provide a valid duplicate target.

## Change summary

Provide reusable Azure DevOps OAuth authentication when cloning repositories into a full local or Remote-SSH workspace, comparable to GitHub.

## Best solution

Integrate Azure DevOps authentication with ordinary Git cloning so users can reuse a Microsoft sign-in without manually configuring a separate credential tool or switching to a virtual repository. Plan the account, authorization, and remote-host behavior with the Git and Microsoft authentication owners, preserving existing credential-helper workflows.

## Plan brief

- **Likely files:** `extensions/git/src/askpass.ts`, `extensions/git/src/api/git.d.ts`, `extensions/github/src/credentialProvider.ts`, `extensions/github/src/auth.ts`, `extensions/microsoft-authentication/src/extension.ts`, `extensions/microsoft-authentication/src/node/authProvider.ts`
- **Validation:** In a Remote-SSH Linux workspace with no configured Azure credential helper, clone a private Azure DevOps repository through Git: complete the initial Microsoft sign-in, verify a real filesystem checkout with terminal and debugging access, then clone another authorized repository and fetch without repeating sign-in while the session remains valid. Repeat locally and verify existing GitHub authentication and configured Git credential helpers remain functional.
- **Behavior:**

  > Cloning a private Azure DevOps repository into a Remote-SSH Linux workspace should offer integrated OAuth sign-in comparable to GitHub, rather than require manual credential-manager setup. Subsequent authorized Git operations should reuse a valid authentication session. The result must be a normal filesystem-backed repository with terminal and debugging access, not a virtual Azure Repos browsing workspace. Acceptance should cover initial sign-in, session reuse, cancellation or authorization failure, and preservation of existing GitHub and credential-helper workflows.
- **Trace:**

  > The current Git authentication entry point is Askpass.handleAskpass in extensions/git/src/askpass.ts, which queries registered CredentialsProvider implementations before falling back to input prompts. GitHubCredentialProvider in extensions/github/src/credentialProvider.ts accepts only github.com and calls getSession in extensions/github/src/auth.ts; this is the concrete built-in precedent, not Azure coverage. extensions/microsoft-authentication/src/extension.ts exposes Microsoft authentication sessions, but the inspected extensions do not connect those sessions to Azure DevOps Git credentials. The trace establishes the missing integration; it does not establish a complete remote-host, account-selection, or authorization design. Preserve ordinary Git clone destinations and existing helper behavior rather than substituting a virtual repository. https://github.com/microsoft/vscode/issues/201679 is a related granular-scope constraint, while https://github.com/microsoft/vscode/issues/243479 concerns repository discovery and should not be treated as completing the credential requirement.
- **Open decisions:**
  - For multiple signed-in Microsoft accounts or Azure DevOps tenants, when should Git reuse an existing account and when should the user be asked to select one?
  - Should the initial supported scope cover only Azure DevOps Services HTTPS repositories, or also Azure DevOps Server and sovereign-cloud deployments?
