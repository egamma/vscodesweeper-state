# Issue #167890 — Allow extensions to change { ... } completion to { ... };

[https://github.com/microsoft/vscode/issues/167890](https://github.com/microsoft/vscode/issues/167890)

## Summary

Keep this accepted backlog request open: current autoclosing configuration cannot distinguish a C/C++ type definition from a control-flow block. Format-on-type provides a possible extension workaround, but does not establish that the requested context-sensitive autoclosing capability is available.

## Change summary

Allow language extensions to insert `};` when opening a class, struct, enum, or union definition without adding semicolons to ordinary blocks.

## Best solution

Keep language-specific syntax analysis in extensions while determining whether the existing format-on-type contract can reliably deliver the requested typing experience or a dedicated autoclosing extension contract is needed. Preserve language-agnostic bracket insertion for other constructs and languages.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages/languageConfiguration.ts`, `src/vs/editor/common/languages/supports/characterPair.ts`, `src/vs/editor/common/cursor/cursorTypeEditOperations.ts`, `src/vs/editor/contrib/format/browser/formatActions.ts`
- **Validation:** In an extension-enabled development window, type `struct A {`, `class A {`, `enum A {`, and `union A {` and verify the resulting definitions end in `};` with the caret inside. Type `if (1) {` and a function body and verify they end in `}` without an added semicolon. Check the chosen contract's behavior with format-on-type disabled, undo, and multiple cursors.
- **Behavior:**

  > A language extension can recognize a C/C++ type definition when its opening brace is typed and provide the closing brace followed by the required semicolon, leaving the caret inside the definition. Control-flow and function blocks must retain ordinary brace autoclosing without a semicolon. The accepted design must specify whether this experience depends on format-on-type and which typing interactions it supports.
- **Trace:**

  > CharacterPairSupport builds static autoclosing pairs from LanguageConfiguration. AutoClosingOpenCharTypeOperation.getAutoClosingPair in src/vs/editor/common/cursor/cursorTypeEditOperations.ts selects literal pairs and applies bracket-balance and token-category checks; it has no declaration-aware extension callback on this path. The public AutoClosingPair contract in src/vscode-dts/vscode.d.ts exposes fixed strings and token exclusions. FormatOnType in src/vs/editor/contrib/format/browser/formatActions.ts offers a separate extension-provider path gated by editor.formatOnType and skips multiple selections. The discussion at https://github.com/microsoft/vscode/issues/167890 identifies that workaround and welcomes the feature, but does not settle the public contract. Preserve the core editor's language-agnostic behavior and avoid unconditional semicolon insertion.
- **Open decisions:**
  - Should context-sensitive semicolon insertion remain an opt-in format-on-type behavior, or should extensions receive a dedicated autoclosing contract that also works when format-on-type is disabled?
