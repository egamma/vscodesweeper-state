# Issue #210759 — Find bar resize issue

[https://github.com/microsoft/vscode/issues/210759](https://github.com/microsoft/vscode/issues/210759)

## Summary

Keep open as editor-find polish: the editor Find widget still uses a narrow, fixed-size resize target that the global sash-size setting does not enlarge. No verified open canonical or landed fix covers this usability concern; an intermittent drag-event failure remains unconfirmed.

## Change summary

Make the editor Find widget's left resize handle easier to discover and reliably acquire with the mouse.

## Best solution

Provide a discoverable, easier-to-acquire resize affordance in the editor Find widget while preserving its existing width limits and standard resize feedback. Distinguish missed targeting from an actual drag-event failure before treating the latter as a separate bug.

## Evidence

- **Reporter follow-up:** https://github.com/microsoft/vscode/issues/210759 describes difficulty initiating a drag on the editor Find widget's left edge, requests a larger and clearer handle, and confirms persistence on 1.89.0 after the initial 1.88.0 report. The issue is already classified as polish and editor-find.
- **Current resize target:** src/vs/editor/contrib/find/browser/findWidget.ts:1271 constructs the vertical Sash with size: 2. src/vs/editor/contrib/find/browser/findWidget.css:243-246 forces it to the left edge and supplies a themed background. This confirms the narrow affordance, not an intermittent event-handling defect.
- **Existing capability does not cover the ask:** workbench.sash.size is registered in src/vs/workbench/contrib/sash/browser/sash.contribution.ts, but src/vs/base/browser/ui/sash/sash.ts:472-486 applies an explicit size as an inline width instead of subscribing to global size changes. The Find widget's explicit size therefore bypasses that enlargement setting. sash.css already supplies an ew-resize cursor, so resize feedback exists but does not address the small acquisition target.
- **Resize constraints:** src/vs/editor/contrib/find/browser/findWidget.ts:1279-1291 ignores requested widths below FIND_WIDGET_INITIAL_WIDTH or above the computed maximum. Those intentional limits can also produce a drag with no width change; the report does not establish that mouse events themselves are lost.
- **Canonical search:** Read-only GitHub searches for find resize and find handle found no verified open canonical with the same symptom. https://github.com/microsoft/vscode/issues/159174 concerns positioning, zoom and tree-find persistence; https://github.com/microsoft/vscode/issues/33349 concerns localization-driven input narrowing. Neither owns this resize-target complaint.
- **Related narrow-handle reports:** https://github.com/microsoft/vscode/issues/27505 was completed in 2017 and cannot serve as an open canonical or proof of a post-report fix. https://github.com/microsoft/vscode/issues/225366 requests a wider handle but is newer and was automatically closed for missing information, not declined on product grounds.
- **Related patch did not land:** https://github.com/microsoft/vscode/pull/225367 is closed and unmerged. Its sole changed file was src/vs/workbench/contrib/codeEditor/browser/find/simpleFindWidget.css, not the editor FindWidget's explicit Sash sizing; it does not establish resolution of this issue.
