# Issue #111616 — [theme icons] Include color class in ThemeIcon.asClassName()

[https://github.com/microsoft/vscode/issues/111616](https://github.com/microsoft/vscode/issues/111616)

## Summary

The requested capability remains absent on current main: `ThemeIcon.asClassName()` ignores `ThemeIcon.color`, leaving consumers to implement color handling independently. The older related issue is broader and explicitly depends on this issue, so it does not meet the stronger duplicate bar for this re-reviewed item.

## Change summary

Include sufficient color-class information when converting a colored `ThemeIcon` to CSS class names.

## Best solution

Provide a shared, theme-aware color-class mechanism for `ThemeIcon` while preserving the established ability of consumers to decide whether icon colors should be honored. A maintainer should first settle whether the existing `asClassName()` contract changes globally or color support remains opt-in.

## Plan brief

- **Likely files:** `src/vs/base/common/themables.ts`, `src/vs/platform/theme/common/colorUtils.ts`
- **Validation:** Add focused tests asserting the chosen class contract for colored and uncolored ThemeIcons, plus a browser-level theming test showing that the generated color class follows the active theme after a theme change.
- **Behavior:**

  > A ThemeIcon carrying a ThemeColor can be rendered through CSS classes with the color defined by the active theme, without each participating caller resolving that color independently. Icons without a color retain their existing class output and appearance. The rendered color updates when the active theme changes, and invalid icon IDs retain the existing error-icon fallback behavior.
- **Trace:**

  > `ThemeIcon.asClassNameArray()` and `ThemeIcon.asClassName()` in `src/vs/base/common/themables.ts` currently discard the optional `color` property. Colored-icon consumers therefore apply colors independently through `IThemeService` or `asCssVariable`, including treeView.ts, timelinePane.ts, and actionList.ts. Registered theme colors are enumerable through `ColorRegistry` in `src/vs/platform/theme/common/colorUtils.ts`, but no shared class-to-color rules exist for ThemeIcon. The boundary is colored ThemeIcon class generation and its theme CSS integration; icon IDs, modifiers, uncolored output, and unrelated consumer rendering must remain unchanged. The uncertainty starts at compatibility: the helper has hundreds of callers, while the originating discussion states that consumers should retain control over whether colors are supported.
- **Open decisions:**
  - Should `ThemeIcon.asClassName()` automatically include and activate color styling for every existing caller, or should color-class generation be an explicit opt-in so consumers retain control over whether ThemeIcon colors affect their surface?

## Evidence

- **current source:** `src/vs/base/common/themables.ts` defines `ThemeIcon.color`, but `asClassNameArray()` emits only `codicon`, the icon ID, and an optional modifier; `asClassName()` merely joins those classes.
- **consumer inconsistency:** Current consumers handle color separately: `src/vs/workbench/browser/parts/views/treeView.ts`, `src/vs/workbench/contrib/timeline/browser/timelinePane.ts`, and `src/vs/platform/actionWidget/browser/actionList.ts` each apply `icon.color` through inline theme values or CSS variables.
- **theme registry:** `src/vs/platform/theme/common/colorUtils.ts` maintains the registered color contributions through `ColorRegistry.getColors()`, but no general ThemeIcon color-class rules connect that registry to `ThemeIcon.asClassName()`.
- **related issue:** https://github.com/microsoft/vscode/issues/109460 is older and tracks the broader goal of supporting colored theme icons across API surfaces, but its discussion says it "Depends on #111616," establishing this helper work as a distinct dependency rather than the broader issue owning the same observable request.
- **design constraint:** The originating maintainer discussion at https://github.com/microsoft/vscode/issues/109460#issuecomment-736322301 says each ThemeIcon consumer decides whether it supports colors, which must be reconciled with changing a helper used by hundreds of existing call sites.
