# Issue #313942 — New Window places title bar and status bar outside the visible work area (regression from #262266)

[https://github.com/microsoft/vscode/issues/313942](https://github.com/microsoft/vscode/issues/313942)

## Summary

Keep open: current source retains the oversized default-window placement and unbounded cascading described in the report. The linked fixing PR is still open, and a maintainer has consolidated the Agents-window symptom into this issue.

## Change summary

New workspace windows can open outside the display work area, leaving their title bar or status bar inaccessible on small or scaled displays.

## Best solution

Review and land https://github.com/microsoft/vscode/pull/313944 after confirming that default placement and overlap offsets keep windows inside the target display's work area, including the shared Agents-window path.

## Evidence

- **Current-source placement defect:** src/vs/platform/windows/electron-main/windowsStateHandler.ts, doGetNewWindowState(), centers default windows on displayToUse.bounds without first constraining their dimensions to workArea. src/vs/platform/window/electron-main/window.ts:146-153 selects the workspace size unchanged; src/vs/platform/window/common/window.ts:578 defines it as 1440x900. For the reported workspace-window case with logical display bounds 1536x864, the computed y is -18 and the bottom is 882, outside a work area ending at 816. This is source inspection, not an executed desktop reproduction.
- **Current-source cascading defect:** src/vs/platform/windows/electron-main/windowsStateHandler.ts:413-430, ensureNoOverlap(), compares coordinates against all existing windows using x equality OR y equality and repeatedly adds 30 to both coordinates. It receives no target work area, and doGetNewWindowState() returns the resulting state without a subsequent work-area clamp, supporting the reported side-by-side-display overflow mechanism.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/313944 was verified OPEN with mergedAt null and contains Fixes #313942. Its description proposes work-area-based placement and size constraints and reports successful testing on a 1920x1080 display at 125% scaling. The issue's August follow-up says the PR now also addresses overlap offsets; an open fix attempt is not a completed fix.
- **Maintainer-confirmed canonical ownership:** https://github.com/microsoft/vscode/issues/317762#issuecomment-5439892138 identifies the Agents-window report as the same underlying defect, points to the linked PR, and closes that satellite with /duplicate of #313942. This issue remains the canonical report, not a duplicate of the closed Agents-window issue.
- **Older-canonical search:** Open-issue searches for window work-area and off-screen symptoms found https://github.com/microsoft/vscode/issues/248443 and https://github.com/microsoft/vscode/issues/266242. Reading their bodies showed different triggers: returning after monitor wake/display changes, and dragging an existing window between monitors with corruption and freezing. Neither establishes the same new-default-window symptom required to supersede this re-reviewed issue.
