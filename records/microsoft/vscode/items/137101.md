# Issue #137101 — Cursor Follow Outline

[https://github.com/microsoft/vscode/issues/137101](https://github.com/microsoft/vscode/issues/137101)

## Summary

Keep open: navigating through Outline entries without activating each one still does not move the editor cursor. This accepted Backlog request has 22 upvotes, and the existing Follow Cursor command implements the opposite direction.

## Change summary

Allow browsing Outline entries to reveal their definitions in the editor without pressing Enter on each entry.

## Best solution

Provide an intentional Outline-to-editor browsing mode that preserves focus in Outline while revealing the browsed symbol. Settle whether browsing means keyboard focus changes or literal scrolling before implementing it, while preserving ordinary scrolling and the existing Follow Cursor behavior.

Verify that the editor reveals each corresponding definition while Outline retains keyboard focus; verify that disabled-mode browsing, explicit activation, and existing Follow Cursor behavior remain unchanged.
- **Behavior:**

  > Users should be able to inspect successive symbol definitions by browsing Outline without activating every entry. The editor should reveal the corresponding definition while keyboard focus remains in Outline so browsing can continue. Acceptance must specify whether the trigger is keyboard navigation, pointer scrolling, or both, and verify that ordinary Outline use and the existing editor-to-Outline Follow Cursor mode remain intact.
- **Trace:**

  > OutlinePane in src/vs/workbench/contrib/outline/browser/outlinePane.ts creates a WorkbenchDataTree and invokes newOutline.reveal only through onDidOpen. Its followCursor handler instead derives Outline focus and selection from the editor's active symbol. DocumentSymbolsOutline in src/vs/workbench/contrib/codeEditor/browser/outline/documentSymbolsOutline.ts supplies reveal, preview, and captureViewState capabilities, but its tree options do not enable selectionNavigation. Shared arrow-navigation handling in src/vs/workbench/browser/actions/listCommands.ts distinguishes focus movement from selection-driven opening. Source inspection identifies the relevant boundary but the report's use of 'scrolling' does not settle the intended input trigger. Preserve shared list defaults and explicit symbol activation; consider interaction with Follow Cursor so editor updates do not redirect ongoing Outline browsing. The related Settings request https://github.com/microsoft/vscode/issues/173935 concerns the opposite synchronization direction and is not a duplicate.
- **Open decisions:**
  - Should editor following react to keyboard-focused Outline entries, literal mouse-wheel/viewport scrolling, or both?
  - Should activation-free browsing be an opt-in Outline mode or become the default navigation behavior?
