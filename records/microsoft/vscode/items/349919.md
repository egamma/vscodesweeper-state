# Issue #349919 — Investigate surfacing connectors in chat when MCP sign-in issues block a task

[https://github.com/microsoft/vscode/issues/349919](https://github.com/microsoft/vscode/issues/349919)

## Summary

Keep this investigation open. Chat already has MCP authentication controls, but those do not establish that connector-specific recovery and the requested failure-state distinctions are fully covered.

## Change summary

Investigate contextual connector recovery when MCP authentication blocks the user's current chat task.

## Best solution

Document the authoritative authentication signals and connector mapping, then identify gaps in the existing chat authentication surfaces before proposing additional UI. Preserve explicit user consent and distinguish authentication requirements from unrelated failures.

## Evidence

- **Existing inline capability:** src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatToolAuthenticationSubPart.ts already renders a server-named authentication confirmation for WaitingForAuthentication, with Authenticate, Cancel, and conditional Disable for This Session actions.
- **Existing session recovery:** src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatMcpAuthenticationContentPart.ts filters live enabled servers by McpServerStatus.AuthRequired, uses connector-aware display labels, offers Authenticate, and retains an authenticating progress state. This partially covers the request, but does not itself document or distinguish every requested recovery case.
- **Available connector metadata:** src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts exposes connector MCP inventory, connectionStatusDetail, and explicit authorization/connection operations. src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationService.ts already reads connector identity during MCP authentication; the investigation should establish which signals are authoritative for each failure case.
