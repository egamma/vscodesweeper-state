# Issue #321385 — VS Code does not reload modified .ipynb files when stored on external drives and edited on another machine

[https://github.com/microsoft/vscode/issues/321385](https://github.com/microsoft/vscode/issues/321385)

## Summary

Real behavioral gap: notebook hot-exit backup restoration does not compare the backup's stored mtime against the file's current mtime on disk, so externally-modified .ipynb files are overridden by stale in-memory state on reopen. Closely related to #238746 (closed info-needed) but not identical — this one focuses on cross-machine editing rather than WSL-specific restore.

## Change summary

When a .ipynb file is modified externally (e.g. on another PC via an external SSD) and VS Code reopens, hot-exit restores the old notebook backup instead of detecting the newer file on disk.

## Best solution

The stored-file working copy's `resolveFromBackup()` path (src/vs/workbench/services/workingCopy/common/storedFileWorkingCopy.ts ~line 535) should stat the file and compare the current mtime/etag against the backup metadata before blindly restoring — if the file is newer, it should resolve from disk (or prompt). This would fix both this issue and the related #238746 scenario. The notebook area team should determine whether to add an mtime guard in the generic working copy layer or specifically for notebooks.
