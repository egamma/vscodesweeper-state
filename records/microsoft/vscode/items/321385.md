# Issue #321385 — VS Code does not reload modified .ipynb files when stored on external drives and edited on another machine

[https://github.com/microsoft/vscode/issues/321385](https://github.com/microsoft/vscode/issues/321385)

## Summary

Keep open: the two-machine steps suffice to retest, but the external-drive restart failure remains unverified. Current source supports disk loading and external-change reloads, with backup restoration taking a separate path; neither a matching fix nor a verified canonical was established.

## Change summary

Reopening a saved notebook after another machine modifies it on an external SSD displays the previous contents instead of the updated file.

## Best solution

Ensure a clean, saved notebook reopened after an offline disk change displays the current disk contents without disabling session restoration. Diagnose notebook working-copy restoration first, preserving recovery of genuinely unsaved edits rather than introducing an unconditional disk-wins option.

## Evidence

- **Report and workaround:** https://github.com/microsoft/vscode/issues/321385 supplies a concrete sequence: save and close on PC1, modify the same external-SSD notebook on PC2, then reopen VS Code on PC1. Disabling hot exit and window restoration reportedly avoids stale contents; there are no independent confirmations or linked fix PRs in the supplied discussion.
- **Current notebook loading:** src/vs/workbench/contrib/notebook/common/notebookEditorModel.ts, SimpleNotebookEditorModel.load(), delegates file-backed notebooks to the file working-copy manager and requests reloads for existing models. src/vs/workbench/contrib/notebook/common/notebookEditorInput.ts, NotebookEditorInput.resolve(), resolves the notebook model and also has a separate legacy _backupId restoration path. These paths do not establish which restoration mechanism the reporter encountered.
- **Backup versus disk boundary:** src/vs/workbench/services/workingCopy/common/storedFileWorkingCopy.ts, doResolve(), tries a backup before reading the file on initial resolution. doResolveFromBackup() restores it as dirty; resolve() avoids overwriting dirty or saving working copies. Without a backup, resolveFromFile() reads disk. This identifies a diagnostic boundary, not proof that a clean saved notebook incorrectly retains a backup.
- **External reload support:** src/vs/workbench/services/workingCopy/common/storedFileWorkingCopyManager.ts, onDidFilesChange() and queueWorkingCopyReloads(), reload clean working copies on UPDATED or ADDED file events and skip dirty copies. Existing reload support therefore does not prove the restart-specific report is resolved.

Its reproduction concerns running Black externally while the notebook remains open, not closing VS Code and moving an SSD between machines. No shared root cause or identical restart symptom was established, so it does not meet the stronger duplicate bar for this re-reviewed item.
