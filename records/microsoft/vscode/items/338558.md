# Issue #338558 — WT confusing behavior with create_session

[https://github.com/microsoft/vscode/issues/338558](https://github.com/microsoft/vscode/issues/338558)

## Summary

Team-authored (MEMBER) report, so no judgment close applies regardless of how strongly the design reads as intentional; the source traces exactly the two-step behavior described, but whether it's the intended UX or needs tightening is a maintainer call, not a mechanical fix.

## Change summary

Using the create_session tool to target an untrusted folder creates the session without a trust prompt, but the trust prompt then appears when the session is opened and a message is sent — the reporter isn't sure which half is the bug.

## Best solution

A maintainer should confirm whether this defense-in-depth split (eager backend creation is skipped silently for untrusted folders per baseAgentHostSessionsProvider.ts, with the interactive trust prompt deferred to the first Send in agentHostSessionHandler.ts) is the intended UX, or whether create_session should surface the trust requirement up front instead of appearing to succeed silently.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts`
- **Validation:** Once the intended UX is decided, a test asserting the session view surfaces trust status/prompt at the decided point (creation vs. first send) for an untrusted target folder.
- **Behavior:**

  > When create_session targets a folder that isn't workspace-trusted, the user currently sees the session get created without any trust indication, and only encounters the trust prompt later when they send their first message in that session. The goal is to make this behavior unambiguous to the user — either the session creation itself should reflect the untrusted state, or the current two-step flow should be confirmed as intended and clarified in the UI.
- **Trace:**

  > _startNewSessionBackend in baseAgentHostSessionsProvider.ts (~4402-4433) deliberately skips eager backend creation for untrusted folders per its own comment, treating the folder-pick-time prompt (newChatWidget) and the first-Send backstop (agentHostSessionHandler.ts _ensureFoldersTrusted, ~6413-6445, invoked at ~1877-1902) as the two normal trust checkpoints. The reporter's flow (creating a session by name via chat tool rather than the folder picker) hits neither checkpoint until Send, producing the 'created fine, then prompted later' sequence. Boundary: do not alter the whole-workspace vs. per-resource trust semantics or the Send-time gating logic — the open question is only whether/how create_session-driven session creation should reflect trust state earlier.
- **Open decisions:**
  - Should create_session surface the target folder's trust status (e.g., a warning or blocked state) at creation time, rather than only prompting on first Send?
  - Is silently creating the session record while deferring the actual trust prompt to first Send the intended, documented behavior, or should it be tightened?
