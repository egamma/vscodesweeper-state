# Issue #258314 — Can't test an extension in vscode.dev with an API proposal

[https://github.com/microsoft/vscode/issues/258314](https://github.com/microsoft/vscode/issues/258314)

## Summary

Keep open: core supports host-configured proposed API access, but the inspected web-extension installation flow does not expose an opt-in for extension developers on vscode.dev. No verified canonical or issue-referencing fix was found; this team-authored, accepted request needs a product decision rather than a decline close.

## Change summary

Provide a way to test locally hosted web extensions that use proposed APIs in vscode.dev.

## Best solution

Provide an explicit developer opt-in for testing declared API proposals in the hosted web workbench, while preserving restrictions for ordinary installed extensions. Decide the supported build channel and authorization lifetime before implementing the user-facing flow.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts`, `src/vs/workbench/services/environment/browser/environmentService.ts`, `src/vs/workbench/services/extensions/common/extensionsProposedApi.ts`, `src/vs/workbench/browser/web.api.ts`, `src/vs/workbench/services/environment/test/browser/environmentService.test.ts`
- **Validation:** On the agreed hosted-web channel, serve a web extension declaring an API proposal still present in that build, install it through Developer: Install Extension from Location, and invoke its proposed-API command before and after explicit authorization. Verify that the authorized command succeeds and an unrelated unauthorized extension remains blocked; exercise the agreed reload/revocation behavior and retain the existing production-payload restriction tests.
- **Behavior:**

  > A developer should be able to test a locally hosted web extension using a declared proposed API in the supported vscode.dev development workflow. Installing the extension alone currently does not provide a way to authorize that access. Acceptance must demonstrate successful invocation after an explicit supported opt-in, continued rejection for unrelated unauthorized extensions, and the agreed behavior when the session reloads or authorization ends.
- **Trace:**

  > The URL-install action workbench.extensions.action.installExtensionFromLocation in src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts delegates to extension management without proposal authorization. ExtensionsProposedApi in src/vs/workbench/services/extensions/common/extensionsProposedApi.ts subsequently restricts non-built-in extensions unless product, environment, or development conditions authorize them. BrowserWorkbenchEnvironmentService in src/vs/workbench/services/environment/browser/environmentService.ts already consumes host-supplied enabledExtensionProposedApi, exposed in src/vs/workbench/browser/web.api.ts, but production builds deliberately ignore privileged workspace payload options. Existing environment tests assert that boundary. https://github.com/microsoft/vscode-dev/issues/1300#issuecomment-3129017331 confirms that this gap blocked real API verification. The remaining uncertainty is the supported developer-facing authorization contract and hosted application integration; preserve default proposal restrictions and do not enable arbitrary privileged production payloads.
- **Open decisions:**
  - Should the supported proposed-API testing workflow be available on stable vscode.dev, only its Insiders channel, or a dedicated development session?
  - Should authorization be limited to a named extension for the current session, or persist across reloads, and what user-visible action revokes it?

## Evidence

- **Existing capability is host-facing:** src/vs/workbench/browser/web.api.ts exposes IWorkbenchConstructionOptions.enabledExtensionProposedApi, including extension-specific authorization and an empty-array enable-all mode. BrowserWorkbenchEnvironmentService.extensionEnabledProposedApi consumes this option, but it is supplied by the embedding application, not by the reporter's install-from-URL workflow.
- **Installation does not authorize proposals:** src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts registers workbench.extensions.action.installExtensionFromLocation and passes the entered URL to installFromLocation. src/vs/workbench/services/extensionManagement/common/webExtensionManagementService.ts delegates that operation to install(location, { profileLocation }); neither inspected entry point provides a proposed API opt-in.
