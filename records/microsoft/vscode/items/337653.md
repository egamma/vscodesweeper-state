# Issue #337653 — Claude agent host: model picker shows the first native model (Fable) after restart, while turns still run on the saved model

[https://github.com/microsoft/vscode/issues/337653](https://github.com/microsoft/vscode/issues/337653)

## Summary

Well-documented, actively-investigated bug: two independent reporters give detailed session-log evidence of a startup race in the Claude agent host's native model catalog loading — sometimes only the picker label is stale, but a follow-up comment shows the actual SDK model can also silently fall back to the first native entry. No fix found on main; keep open.

## Change summary

After restarting VS Code and reopening a Claude agent-host session, the model picker (and sometimes the actual routed model) reverts to the first native model instead of the previously saved selection, because the native model list loads asynchronously after the saved selection is resolved.

## Best solution

Diagnose the exact race in the Claude agent host's model-catalog/session-restore path (claudeAgent.ts's async `supportedModels()` fetch vs. session/model restore) and ensure the restored selection is either held pending the native catalog or re-resolved once it arrives, for both the picker label and the actual SDK model id used for routing.

- **Behavior:**

  > After restarting VS Code and reopening an existing Claude agent-host session, the model picker must show the previously selected model (e.g. Opus) as soon as the native model catalog is available, and every subsequent turn must route to that same model — never silently falling back to the first native catalog entry (e.g. Fable) in either the label or the actual routed model id.
- **Trace:**

  > claudeAgent.ts merges the proxy and native model catalogs asynchronously (mergeClaudeModelCatalogs after Promise.all([query.accountInfo(), query.supportedModels()]), ~line 960-1030); the reporter's diagnosis and mmontagnana's session-log timestamps point to session/model restoration reading or defaulting before this async catalog settles. No related commit found in git log for claudeAgent.ts or claudeModelSelection.ts. Where the uncertainty starts: whether the stale state is confined to display (picker label) or also reaches session routing — comment evidence shows both have occurred across different SDK pins (0.3.239, 0.3.258), so the exact code path causing the SDK-level fallback (not just the label) is not yet pinned down.
- **Open decisions:**
  - Should the restore path block/delay presenting the model picker until the native catalog resolves, or optimistically show the saved id and reconcile once the catalog arrives?
  - Is there a genuine SDK-level fallback to the first native model when the saved model id isn't yet in the resolved catalog, separate from the UI label issue, and if so where does that fallback happen?

## Evidence

- **reporter diagnosis:** Issue body traces session_metadata.claude.model / defaultChatProviderData / chatModelConfigurationStore in the profile all showing Opus while the picker shows Fable, and turn_usage confirms turns still ran on claude-opus-5 — a UI-only staleness at first.
- **escalating comment:** mmontagnana's comments (2026-09-26) give timestamped evidence from ~/.claude/projects/*/*.jsonl across 9 sessions/SDK versions (0.3.239, 0.3.258) where the assistant message model itself switched to claude-fable-5 after an overnight restart, only reverting when the user re-picks Opus — i.e. the fallback sometimes reaches the SDK, not just the label.
- **code location (unverified fix):** src/vs/platform/agentHost/node/claude/claudeAgent.ts (~L960-1030) merges proxy/native model catalogs via mergeClaudeModelCatalogs after an async Promise.all([query.accountInfo(), query.supportedModels()]); no commit in git log for this file since the report addresses a startup-restore race.
