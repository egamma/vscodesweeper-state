# Issue #337653 — Claude agent host: model picker shows the first native model (Fable) after restart, while turns still run on the saved model

[https://github.com/microsoft/vscode/issues/337653](https://github.com/microsoft/vscode/issues/337653)

## Summary

Real, well-documented bug in the Claude agent host's native model catalog/session-restore race, but reproduction status is genuinely unclear from source alone (the thread itself shows the symptom flipping between label-only and actual-model-switch across SDK/VS Code versions) and it is not written by a reporter-thin issue, so keep-open with info-needed-adjacent evidence rather than a hard needs-info — the existing detailed logs already substitute for a reporter ask.

## Change summary

After restarting VS Code, the Claude agent host model picker shows the first native model (Fable) instead of the previously-saved model (Opus), apparently because the restored session resolves the saved model id before the async native `supportedModels()` catalog has published, and in some reports this fallback is also persisted and/or actually executed by the SDK rather than being a pure UI label bug.

## Best solution

Trace the startup ordering between ClaudeAgent._refreshModels()/_fetchNativeModels() (src/vs/platform/agentHost/node/claude/claudeAgent.ts) and the session-restore path in SessionModelSelection/BaseAgentHostSessionsProvider (src/vs/sessions/contrib/chat/browser/sessionModelSelection.ts, src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts) to confirm whether `isModelAbsenceConclusive`/`resolveModelIdentifier` ever classifies a not-yet-loaded native model as 'unavailable' instead of 'pending', and whether the persisted `session_metadata.claude.model` can be overwritten by a stand-in before the real catalog lands — this needs a maintainer session with live repro, not a pure source read.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/claude/claudeAgent.ts`, `src/vs/sessions/contrib/chat/browser/sessionModelSelection.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/chatInputModelSelectionController.ts`
- **Validation:** A repeatable manual check: restore a Claude native session whose model is Opus right after VS Code startup (before the native catalog refresh completes) and confirm the picker shows Opus throughout, with no persisted overwrite of session_metadata.claude.model and no turn executed on the fallback model.
- **Behavior:**

  > After restarting VS Code and reopening a Claude agent host session whose saved model is e.g. Opus, the model picker must continue to show Opus (not the first native model, Fable) even if the native model catalog has not finished its async refresh yet, and no turn should run on a model other than the one the picker displays. The persisted selection (session_metadata.claude.model) must never be silently overwritten by a startup stand-in.
- **Trace:**

  > ClaudeAgent._refreshModels()/_fetchNativeModels() in src/vs/platform/agentHost/node/claude/claudeAgent.ts publish the native model catalog only after an async SDK query (supportedModels()/accountInfo()) resolves, confirming the race window the reporter describes. On the restore side, sessionModelSelection.ts and chatInputModelSelectionController.ts already distinguish a 'pending' (catalog not yet loaded) from 'unavailable' (genuinely absent) resolution via isModelAbsenceConclusive/resolveModelIdentifier, which is designed to show a stand-in without persisting over the real selection — but reporter comments (2026-09-26 to 2026-09-30) show cases where the fallback was both label-only and, at other times, a real persisted overwrite with turns actually executed on the wrong model. The boundary: do not touch the proxy (GitHub/Copilot) model catalog path or the unrelated alias-resolution issues (#334750, #338986); scope is strictly the native Claude catalog publish timing vs. session restore.
- **Open decisions:**
  - Should the agent-host Claude session block/disable sending until the native catalog has loaded at least once after startup, or is a label-only stand-in acceptable as long as persistence and execution never follow the stand-in?
  - Is the observed persisted overwrite of session_metadata.claude.model a distinct, worse-severity bug from the pure UI race, warranting separate tracking/fix sequencing?

## Evidence

- **race design exists:** chatInputModelSelectionController.ts and sessionModelSelection.ts already implement a deliberate 'pending vs unavailable' distinction (resolveModelIdentifier, isModelAbsenceConclusive) specifically meant to avoid showing a stand-in model that overwrites the real selection — the bug report implies this safeguard is not fully closing the gap for the agent-host Claude provider.
- **async native catalog load:** ClaudeAgent._fetchNativeModels() in src/vs/platform/agentHost/node/claude/claudeAgent.ts opens a throwaway SDK query and awaits `Query.supportedModels()`/`accountInfo()` before publishing the native catalog via `this._models.set(...)`, confirming the native list really does arrive asynchronously after startup, as the reporter theorizes.
- **evolving/conflicting symptom:** Comments from mmontagnana (2026-09-26 to 2026-09-30) show the bug alternating between a pure UI label glitch and an actual persisted overwrite of session_metadata.claude.model plus real execution on the wrong model (claude-fable-5), which makes this harder to pin down as a single deterministic code path without live tracing.
- **related but distinct issues:** https://github.com/microsoft/vscode/issues/334750 (toSdkModelId truncates claude-fable-5-1[1m] to claude-fable-5) and https://github.com/microsoft/vscode/issues/338986 (native picker alias resolution) are plausibly entangled but describe different observable symptoms, so neither is a canonical duplicate of this startup-race report.
