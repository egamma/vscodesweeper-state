# Issue #337653 — Claude agent host: model picker shows the first native model (Fable) after restart, while turns still run on the saved model

[https://github.com/microsoft/vscode/issues/337653](https://github.com/microsoft/vscode/issues/337653)

## Summary

Real, actively-corroborated bug in the Claude agent host's native model list/session restore path; a second reporter has since documented that on some runs the fallback also overwrites the persisted selection and desyncs the executed model from the displayed label — this stays open and keeps growing in severity, not staling out.

## Change summary

After restarting VS Code, the Claude agent host model picker falls back to displaying the first native model (Fable) instead of the saved selection, and in some runs the fallback actually reaches the SDK and even overwrites the persisted selection.

## Best solution

Fix the startup race in the native model list resolution (claudeModelSelection.ts / the agent host's model source in src/vs/platform/agentHost/node/claude) so the saved ModelSelection is resolved against the async supportedModels() list once it arrives, rather than falling back to the first entry and (in the worst case) persisting that fallback back to session_metadata.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/claude/claudeModelSelection.ts`, `src/vs/platform/agentHost/node/claude/claudeAgentSdkService.ts`, `src/vs/platform/agentHost/node/sessionDatabase.ts`
- **Validation:** A test that restores a session whose saved ModelSelection is Opus while supportedModels() has not yet resolved, then resolves it after the list arrives, asserting the picker converges on Opus (not the first native entry) and that session_metadata.claude.model is never overwritten by the transient fallback.
- **Behavior:**

  > On reopening VS Code and an existing Claude agent-host session, the model picker should display the session's saved model (e.g. Opus) once the native model list is available, not permanently fall back to the first native model (Fable). Turns must run on the saved model, and the persisted selection (session_metadata.claude.model) must never be overwritten by a transient startup fallback.
- **Trace:**

  > The reporter traces this to a startup race: session restore resolves the saved ModelSelection id before the agent host's async supportedModels() call has published the native model list, so the UI falls back to the first entry and never re-resolves the label once the list arrives. A later comment (2026-09-30) shows this fallback can also be persisted back into session_metadata, and that the per-message model indicator is re-derived at render time from current picker state rather than stored per turn, which retroactively rewrites which model appears to have answered. Relevant seams: claudeModelSelection.ts (parseClaudeModelSelection/toSdkModelId) and claudeAgentSdkService.ts (supportedModels()); the persistence layer is sessionDatabase.ts's session_metadata table. Uncertainty starts at exactly where in session restore the saved selection is matched/fallen-back against the model list, and why that fallback is sometimes (not always) written back to storage — this needs tracing before a fix can be scoped, and is possibly entangled with https://github.com/microsoft/vscode/issues/334750's id-normalization bug.
- **Open decisions:**
  - Should model resolution during restore block/wait on the native model list before rendering the picker, or render immediately and reconcile once the list arrives — and if reconciling, should partial-turn history run under the interim state or be held?
  - Should the fallback-to-first-model ever be persisted back to session_metadata, or must the on-disk selection only ever be written by explicit user action?
