# Issue #169921 — Add API to reopen document with specific CustomTextEditor

[https://github.com/microsoft/vscode/issues/169921](https://github.com/microsoft/vscode/issues/169921)

## Summary

Current main has substantially better editor switching, including an internal command that selects a specific editor and avoids save prompts for shared dirty text documents. Keep this open for the remaining supported API contract; the existing fix does not establish that the full request is completed.

## Change summary

Provide an extension API to switch an existing document to a specific custom text editor while preserving dirty state, undo history, and tab continuity.

## Best solution

Establish a supported programmatic reopen contract using the existing editor-replacement behavior, rather than requiring extensions to close and reopen tabs. Verify document history and tab continuity in both directions before considering this request satisfied.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostApiCommands.ts`, `src/vs/workbench/browser/parts/editor/editorCommands.ts`, `extensions/markdown-language-features/src/commands/reopenAsPreview.ts`
- **Validation:** Use a minimal CustomTextEditorProvider to switch a saved Markdown document with unsaved edits from text to custom editor and back through the agreed public entry point. Verify no save prompt, unchanged content and dirty state, functional undo/redo, and preserved tab position and editor group; repeat for a clean document and observe tab/title continuity.
- **Behavior:**

  > An extension can select a specific custom text editor for the current document without explicitly closing its tab first. Switching between text-backed editors preserves unsaved content, dirty state, undo/redo history, and the originating tab's group and position. The transition should not produce the close/open tab-title disappearance reported here. Acceptance must exercise both switching directions with a minimal custom text editor.
- **Trace:**

  > reopenActiveEditorWith in src/vs/workbench/browser/parts/editor/editorCommands.ts accepts an editor override and delegates to reopenEditorWith, which resolves command context and performs group.replaceEditors. The built-in Markdown extension already invokes it in extensions/markdown-language-features/src/commands/reopenAsPreview.ts. Commit https://github.com/microsoft/vscode/commit/fdf2e9ad7f425101b787fff7438defb10b0a4e69 supplies dirty shared-text working-copy protection, but the public vscode.openWith registration in src/vs/workbench/api/common/extHostApiCommands.ts remains a resource-opening contract. The uncertainty is whether to support the existing targeted reopen command publicly or expose another documented API, and which preservation guarantees that contract makes. Preserve save protection for independently owned custom documents; do not broaden this into the distinct untitled ownership work in https://github.com/microsoft/vscode/issues/340054.
- **Open decisions:**
  - Should targeted reopening become a supported public command contract based on reopenActiveEditorWith, or be exposed through another documented API?
  - Should the supported operation target only the active editor, or allow an explicitly identified tab and editor group?
