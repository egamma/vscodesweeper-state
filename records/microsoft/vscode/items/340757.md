# Issue #340757 — Agents window: restored session stays unread after opening an already-read chat

[https://github.com/microsoft/vscode/issues/340757](https://github.com/microsoft/vscode/issues/340757)

## Summary

Thanks for the detailed log analysis. The repair gap is visible in current main: a mark-read on a chat that is already read can never clear an unread session. How the mismatch first arises is still unknown, and the issue is a day old and team-authored, so it stays open.

## Change summary

After restoring an old Agents window session, the session shows unread while its chat is already read, and mark-read requests do not clear it.

## Best solution

Reconcile session and chat read state, either at restore or when a chat read action arrives, so an already-read chat can repair a stale unread parent session. Keep the intentional session-level Mark as Unread behavior. Find which restore or persistence step first produces the mismatch.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentHostStateManager.ts`
- **Validation:** An agentHostStateManager test: restore a session with status unread and all aggregate chats read, dispatch ChatIsReadChanged(true), and assert the session becomes read. An explicit session Mark as Unread must still hold.
- **Behavior:**

  > A session whose aggregate chats are all read must not stay unread after restore or after the user opens it. Clicking an already-read session clears its unread indicator. Intentional session-level Mark as Unread keeps working.
- **Trace:**

  > In agentHostStateManager.ts, the ChatIsReadChanged handler promotes the session only on a chat unread->read transition (`!chatWasRead`), so an already-read chat cannot repair a stale unread session. Restore (~L1202, registration of restored chat/session status) is the likely place the mismatch is introduced, but it is not traced. Do not change the demotion path (chat unread -> session unread) or the Mark as Unread semantics. Related: https://github.com/microsoft/vscode/issues/340103.
- **Open decisions:**
  - Should the host reconcile at restore (derive session read from chats), or on any ChatIsReadChanged(true), or both?
  - How should an intentional session-level Mark as Unread be distinguished from a stale mismatch when all chats are read?

## Evidence

- **repair gap in source:** src/vs/platform/agentHost/node/agentHostStateManager.ts (~L2062-2075): on ChatIsReadChanged the session is promoted to read only when `chatIsRead && !chatWasRead && !sessionIsRead && all chats read`. A repeated mark-read on an already-read chat has chatWasRead true, so no session sync happens. That matches the logs: the host acknowledges the request but sends no session read update.
- **root cause unconfirmed:** The reporter says the logs do not show which restore or persistence step creates the mismatch. It was seen once and cleared when the session scrolled out of view, which suggests a client-side or restore-time component. I did not trace the restore path.
- **related:** The body cites #340103 as related. I did not verify it as a canonical, and the report adds a remote-host reproduction.
