# Issue #328610 — GitHub Copilot constantly freezes for several seconds in long chats.

[https://github.com/microsoft/vscode/issues/328610](https://github.com/microsoft/vscode/issues/328610)

## Summary

This is a detailed recurrence of a confirmed long-chat performance defect: very large conversations cause periodic whole-window typing freezes and batched response rendering. The earlier persistence fix remains on main, but the post-fix reports show that a significant bottleneck remains and should be routed to Chat performance.

## Change summary

Keep typing and streamed Copilot responses responsive when a chat transcript grows to roughly 60,000 exported Markdown lines.

## Best solution

Profile a representative long session during both typing and response streaming, then eliminate the main-thread work that scales with transcript length in Chat persistence or list rendering. Preserve long-chat history and normal incremental-rendering behavior rather than requiring users to abandon sessions.

- **Behavior:**

  > A long-running Copilot chat must remain responsive as its transcript grows. Typing should appear without periodic multi-second whole-window freezes, and model reasoning or response text should advance continuously rather than arriving in one-second batches. Starting a new conversation must not be the required workaround. Acceptance requires profiling a representative approximately 60,000-line exported transcript during both typing and streaming and confirming that the long-session behavior remains comparable to a short-chat baseline.
- **Trace:**

  > The same observable defect was previously diagnosed in https://github.com/microsoft/vscode/issues/285251 and addressed by the append-log work in https://github.com/microsoft/vscode/pull/286644, but this report reproduces after that change. Current persistence runs through ChatSessionStore.writeSession in src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts, which serializes operation-log deltas and appends them to .jsonl storage. Streaming updates propagate from ChatResponseViewModel through ChatViewModel.onDidChange in src/vs/workbench/contrib/chat/common/model/chatViewModel.ts to ChatWidget in src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts; the list refresh and progressive rendering paths are in chatListWidget.ts and chatListRenderer.ts. The uncertainty starts at which of these paths dominates the current main-thread stalls, so capture a profile before choosing the implementation boundary. Do not alter transcript retention, discard old turns, or conflate the separate service stalls in https://github.com/microsoft/vscode/issues/327906 and extension-host crashes in https://github.com/microsoft/vscode/issues/285598.

## Evidence

- **repeated reproduction:** The report and follow-up comments at https://github.com/microsoft/vscode/issues/328610 describe the same trigger across VS Code 1.131.0 and 1.134.0: after the exported transcript reaches about 60,000 Markdown lines, typing periodically freezes the whole window for several seconds and streamed output advances in one-second batches; starting a new conversation temporarily restores responsiveness.
- **previous confirmed defect:** https://github.com/microsoft/vscode/issues/285251 documented the same stop-the-world typing and streaming symptom, including an independent performance profile that identified chat-session encoding. It was closed by https://github.com/microsoft/vscode/pull/286644, whose commit a177750050de1642a9a7c9ea8038de7e1b703f3f replaced full JSON rewrites with an append-only operation log; this report occurred months after that fix.
- **current persistence path:** Current main still uses the append-log implementation in src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts: ChatSessionStore.writeSession calls ChatSessionOperationLog.write and appends the resulting delta to the .jsonl session file. This rules out closing the recurrence merely because the earlier full-file rewrite was fixed, but does not identify the remaining bottleneck.
- **current rendering path:** In current main, response model updates propagate through ChatResponseViewModel and ChatViewModel.onDidChange in src/vs/workbench/contrib/chat/common/model/chatViewModel.ts; ChatWidget subscribes in src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts and refreshes the transcript, while src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts performs incremental or progressive response rendering. These are concrete profiling boundaries for the once-per-second streamed-output stalls.
- **no duplicate canonical:** The older exact-symptom issues https://github.com/microsoft/vscode/issues/285251 and https://github.com/microsoft/vscode/issues/257729 are closed, so neither can be a duplicate canonical. The reporter explicitly distinguishes the service/network stalls in open issue https://github.com/microsoft/vscode/issues/327906, while https://github.com/microsoft/vscode/issues/285598 concerns extension-host termination and lost debug history rather than the same observable freeze.
