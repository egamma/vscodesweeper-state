# Issue #337936 — Clicking "disable AI features" on github copilot chat incorrectly does not set "disable AI features" setting to true, causing a soft-lock

[https://github.com/microsoft/vscode/issues/337936](https://github.com/microsoft/vscode/issues/337936)

## Summary

Thanks for the detailed report — this reproduces as described and the underlying mechanism is traceable in the current source, but the exact trigger (an async race between the AI-disable listeners) needs live debugging before a fix can be written, so this stays open rather than closed.

## Change summary

Clicking 'Disable AI Features' in the Copilot Chat extension view disables the extension but leaves `chat.disableAIFeatures` unchecked, and toggling the setting doesn't restore chat until the user manually checks then unchecks it.

## Best solution

Fix the event-handling race in ChatSetupContribution (src/vs/workbench/contrib/chat/browser/chat/chatSetup/chatSetupContributions.ts) so that disabling the extension via `DisableAIFeaturesGloballyAction` doesn't get immediately undone by the extension-enablement 'onChange' listener resetting `chat.disableAIFeatures` back to its default.

- **Behavior:**

  > After a user clicks 'Disable AI Features' (globally or in-workspace) from the Copilot Chat extension view, the `chat.disableAIFeatures` setting must end up (and stay) checked/true in the corresponding scope, and the chat extension must show as disabled. Re-enabling should be possible via the normal Enable AI Features action or by toggling the setting once — not require an uncheck/recheck workaround.
- **Trace:**

  > DisableAIFeaturesGloballyAction.run() (extensionsActions.ts:1926-1928) sets `chat.disableAIFeatures` to true via configurationService.updateValue with no explicit target, landing at ConfigurationTarget.USER per deriveConfigurationTargets. ChatSetupContribution.handleChatDisabled() (chatSetupContributions.ts ~806-816) reacts to that change by disabling the chat extension. A second listener in the same class's registerListeners() (~829-846) watches extensionsWorkbenchService.onChange for the chat extension and, when it reads the extension as still enabled, calls updateValue(ChatAIDisabledSettingId, false) to resync the setting — this is meant for the re-enable-via-marketplace path but could fire on a stale/transitional read during the disable sequence, undoing the just-applied true value. The reporter's workaround (uncheck/recheck the setting) forces the extension state and setting back into agreement. Boundary: do not change the semantics of enabling AI features when the extension is manually re-enabled from the Extensions view (chatSetupContributions.ts ~836-845) — only the race/ordering during the disable path needs fixing.
- **Open decisions:**
