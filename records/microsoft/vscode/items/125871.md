# Issue #125871 — Resolve file with same name as folder as index

[https://github.com/microsoft/vscode/issues/125871](https://github.com/microsoft/vscode/issues/125871)

## Summary

The tab and Open Editors portions now have a configurable solution, but the central contextual-filename problem remains in Quick Open and Search results. The older related issue covers only Quick Open, so it does not absorb this re-reviewed issue's broader observable scope.

## Change summary

Present generic filenames such as `index.tsx` and `__init__.py` using their parent-directory context across tabs, Open Editors, Quick Open, Search results, and relevant debugging surfaces.

## Best solution

Use one contextual-label model across workbench file surfaces, building on `workbench.editor.customLabels.patterns`; Quick Open should also match and rank the contextual parent-directory name without losing ordinary filename and path matching. Maintainers should first settle whether this behavior is automatic for generic filenames or explicitly configured, and whether debugger source labels belong in the same scope.

## Plan brief

- **Likely files:** `src/vs/workbench/services/editor/common/customEditorLabelService.ts`, `src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts`, `src/vs/workbench/contrib/search/browser/searchResultsView.ts`, `src/vs/workbench/services/editor/test/browser/customEditorLabelService.test.ts`, `src/vs/workbench/contrib/search/test/browser/searchViewlet.test.ts`
- **Validation:** Add targeted tests proving a configured contextual name for `Component/index.tsx` is rendered in Search results and can be matched and appropriately ranked by `Component` in Quick Open, while ordinary basename and relative-path queries retain their existing order; retain the `Custom Editor Label Service` unit coverage.
- **Behavior:**

  > Files with generic names such as `index.tsx` or `__init__.py` should remain distinguishable using directory context across the workbench surfaces included in the final scope. Quick Open must find the file when the user types the meaningful directory name, and Search results must expose that same context without requiring an excessively wide view. Existing filename and path searches, nonmatching files, and explicit custom-label patterns must continue to behave predictably.
- **Trace:**

  > `CustomEditorLabelService` in `src/vs/workbench/services/editor/common/customEditorLabelService.ts` already computes pattern-based names using directory and filename variables. `ResourceEditorInput.getName()` applies those names, and `OpenEditorRenderer` renders that name, so tabs and Open Editors have partial coverage. Quick Open's file path in `src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts` instead searches resources and creates picks without consulting the contextual-label service; Search's `FileMatchRenderer` in `src/vs/workbench/contrib/search/browser/searchResultsView.ts` similarly renders the resource directly. The boundary should preserve actual resource identity, ordinary basename/path matching, and unrelated file labels. https://github.com/microsoft/vscode/issues/72514 owns the narrower Quick Open ranking case and should inform this design, but does not absorb all remaining surfaces.
- **Open decisions:**
  - Should parent-directory naming activate automatically for recognized generic filenames, or only through explicit `workbench.editor.customLabels.patterns` configuration?
  - Should Quick Open search and ranking treat the contextual label as an additional searchable value, and if so, how should exact contextual matches rank relative to exact basenames and paths?
  - Should the accepted scope include VS Code debugger source and console labels, or remain limited to workbench navigation and search surfaces?

## Evidence

- **existing partial capability:** `workbench.editor.customLabels.patterns` is registered in `src/vs/workbench/browser/workbench.contribution.ts`; `CustomEditorLabelService` in `src/vs/workbench/services/editor/common/customEditorLabelService.ts` supports `${dirname}`, `${filename}`, and `${extname}` templates. `ResourceEditorInput.getName()` consumes that service, and `OpenEditorRenderer` in `src/vs/workbench/contrib/files/browser/views/openEditorsView.ts` renders `editor.getName()`, covering configured editor tabs and Open Editors.
- **remaining Quick Open gap:** `src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts` obtains file-search URIs and passes them to `createAnythingPick`; the contextual editor-label service is not consulted by this file-search and ranking path.
- **remaining Search results gap:** `FileMatchRenderer.renderElement` in `src/vs/workbench/contrib/search/browser/searchResultsView.ts` calls `ResourceLabels.setFile(fileMatch.resource, ...)` directly and does not supply the custom contextual editor name.

- **related but narrower canonical:** https://github.com/microsoft/vscode/issues/72514 is older, open, in the Backlog, and has 74 upvotes, but its owned request is Quick Open matching/ranking for a directory's `index` file. It does not cover this issue's Search results, Open Editors, tabs, and debugger-label scope, so it fails the stronger duplicate bar for this re-reviewed item.
