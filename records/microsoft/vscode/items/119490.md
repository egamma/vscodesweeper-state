# Issue #119490 — Debug: inline breakpoints are not stable

[https://github.com/microsoft/vscode/issues/119490](https://github.com/microsoft/vscode/issues/119490)

## Summary

The requested polish remains relevant: outside an active debug session, removing an inline breakpoint also removes the column hint, causing source text to shift and making the same breakpoint awkward to restore. The discussion establishes the intended behavior, while the latest maintainer comment identifies a real adapter-data constraint rather than resolving the request.

## Change summary

Keep inline breakpoint positions visually stable and readily restorable after removing a column breakpoint, including outside active debug sessions.

## Best solution

Preserve known inline-breakpoint hints for lines that still have breakpoints, without inventing unverified candidate locations when no debug adapter can provide them. The debug owners should decide whether cached adapter locations can safely support this outside an active session.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugEditorContribution.ts`, `src/vs/workbench/contrib/debug/common/debugModel.ts`
- **Validation:** Add or extend debug editor contribution coverage to verify that removing and restoring an inline breakpoint does not change the rendered source-text position, including the chosen behavior after the debug session ends.
- **Behavior:**

  > Inline breakpoint interactions should not make source text shift horizontally as breakpoint hints appear or disappear. When a user removes an inline breakpoint from a line that still has breakpoint context, the previously known position should remain discoverable enough to restore without relying only on Shift+F9. Acceptance must cover both an active debug session and the chosen behavior after that session ends, while avoiding hints at locations that were never validated by a debug adapter.
- **Trace:**

  > The issue discussion distinguishes active-session behavior, where the debug adapter supplies candidate breakpoint locations, from inactive-session behavior, where those candidates are unavailable. The latest maintainer comment identifies the unresolved boundary: build/source mapping can make inferred positions invalid. Trace the inline-breakpoint decoration lifecycle in src/vs/workbench/contrib/debug/browser/debugEditorContribution.ts and the breakpoint/session state in src/vs/workbench/contrib/debug/common/debugModel.ts. Keep ordinary line breakpoints, adapter validation, and Shift+F9 semantics unchanged. No supplied candidate canonical reports the same decoration-shift symptom.
- **Open decisions:**
  - After a debug session ends, should VS Code keep the last adapter-validated inline breakpoint hints visible, despite the possibility that a rebuild makes those cached locations stale, or hide them until another adapter session validates them?
