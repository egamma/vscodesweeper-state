# Issue #264052 — Pressing 'return' with file explorer context menu open starts renaming file

[https://github.com/microsoft/vscode/issues/264052](https://github.com/microsoft/vscode/issues/264052)

## Summary

The macOS Explorer context-menu bug remains present on current main: keyboard activation closes the menu and restores Explorer focus while Return is also the Explorer rename key. A prior fixing PR was closed without merging, so this still needs diagnosis and a validated fix.

## Change summary

Selecting an Explorer context-menu command with Return can put the selected folder into rename mode instead of only running the chosen command.

## Best solution

Ensure a context-menu activation keystroke cannot trigger a command on the element that regains focus when the menu closes, while preserving normal keyboard activation, focus restoration, and Explorer rename behavior.

## Plan brief

- **Likely files:** `src/vs/platform/contextview/browser/contextMenuHandler.ts`, `src/vs/base/browser/ui/menu/menu.ts`, `src/vs/workbench/contrib/files/browser/fileActions.contribution.ts`
- **Validation:** On macOS, open an Explorer folder context menu, keyboard-navigate to Find in Folder, and press Return: Find in Folder must run without entering rename mode. Repeat with other Enter-activated context-menu commands, mouse activation, Escape dismissal, and the normal Explorer Enter-to-rename binding.
- **Behavior:**

  > Activating Find in Folder or another Explorer context-menu command with Return must execute only that command. Closing the menu may restore focus to the Explorer, but the same activation keystroke must not start rename or invoke another Explorer command. Mouse activation, Escape cancellation, and pressing Return directly in the focused Explorer must retain their current behavior.
- **Trace:**

  > Menu construction in src/vs/base/browser/ui/menu/menu.ts configures Enter activation on keydown. ContextMenuHandler.onActionRun in src/vs/platform/contextview/browser/contextMenuHandler.ts immediately hides the context view, and its onHide callback restores focus to the previously focused Explorer element. On macOS, src/vs/workbench/contrib/files/browser/fileActions.contribution.ts binds Enter to renameFile under FilesExplorerFocusCondition, creating the reported conflicting path. The prior attempt at https://github.com/microsoft/vscode/pull/288498 targeted shared context-menu event handling but was closed unmerged; validate the precise native event sequence before choosing the containment point. Keep the boundary to activation-event isolation: do not remove or alter the normal macOS Explorer rename binding, and do not change mouse-triggered menu behavior.
