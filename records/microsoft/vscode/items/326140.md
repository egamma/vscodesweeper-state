# Issue #326140 — Package.json dependency metadata lookup; slow with PNPM

[https://github.com/microsoft/vscode/issues/326140](https://github.com/microsoft/vscode/issues/326140)

## Summary

The current hover path waits for an `npm ls --depth=0` subprocess, whose project-wide dependency inspection explains the PNPM-dependent delay. This is a supported core hover path and should remain open as an npm performance bug.

## Change summary

Package dependency hovers take up to eight seconds in large projects using PNPM's default node_modules layout.

## Best solution

Avoid running a full `npm ls` for every dependency hover while preserving installed-version reporting, likely by using a cheaper package lookup or caching in `extensions/npm/src/features/packageJSONContribution.ts`.

## Evidence

- **current source path:** `extensions/npm/src/features/packageJSONContribution.ts` lines 276-295 makes every dependency hover await both registry metadata and the installed-version lookup through `Promise.all`.
- **expensive command:** `npmListInstalledVersion` at `extensions/npm/src/features/packageJSONContribution.ts` lines 367-379 executes `npm ls --json --depth=0 -- <package>` in the package.json directory, so hover completion is coupled to npm traversing the PNPM-managed installation.
- **configuration boundary:** `npm.packageManager` is consumed by the npm task-running code in `extensions/npm/src/tasks.ts`; the metadata hover receives an npm executable and does not select PNPM from that setting, matching the reporter's observation.
- **report evidence:** The reporter provides a repeatable dependency-count correlation and reports that PNPM's hoisted node linker reduces the delay from about eight seconds to under one second.
- **maintainer context:** The maintainer comment confirms that the built-in feature invokes npm for hover metadata; watcher and search exclusions therefore do not bypass this subprocess path.
