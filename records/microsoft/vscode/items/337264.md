# Issue #337264 — Agent Customization: Unable to migrate instructions

[https://github.com/microsoft/vscode/issues/337264](https://github.com/microsoft/vscode/issues/337264)

## Summary

Fresh report (filed same day, no comments yet) about the still-experimental Configured Locations migration. Tracing the source confirms the mismatch the reporter describes: migration only copies customization files to supported locations, it never clears the underlying `chat.*.locations` settings, so settings.json keeps showing the deprecation warning even after the editor reports everything migrated.

## Change summary

After running 'Migrate Location Settings' in the Agents Customization editor, the deprecated chat.instructions/agents/mode location settings still show deprecation warnings in settings.json even though the editor reports the migration as complete.

## Best solution

Either have the configured-locations migration also clear/reset the migrated location settings once their files have all moved (so the deprecation warning disappears), or make the migration UI explicitly instruct the user to remove the setting keys themselves — a maintainer should decide which UX is intended for this experimental flow.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationServiceImpl.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationCategories.ts`, `src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts`
- **Validation:** A migration flow test confirming that after 'Migrate Location Settings' completes with no remaining candidates, the corresponding location setting no longer differs from its default (or, if manual removal is the intended design, that the UI clearly surfaces a follow-up action to remove it).
- **Trace:**

  > The Configured Locations migration (customizationMigrationServiceImpl.ts) copies agent/instructions/skill files out of deprecated locations but never calls configurationService.updateValue on PromptsConfig.INSTRUCTIONS_LOCATION_KEY/AGENTS_LOCATION_KEY/MODE_LOCATION_KEY/SKILLS_LOCATION_KEY. The settings.json deprecation warning (chat.shared.contribution.ts:1949-2067) fires purely because those settings still hold non-default values, independent of whether their files were migrated. getModifiedSettingIds (customizationMigrationCategories.ts:445-450) already detects this mismatch for banner purposes but takes no corrective action.
- **Open decisions:**
  - Should the migration automatically clear/reset the location setting once all of its files have been migrated, or should users be expected to remove the setting manually?
  - If manual removal is intended, should the 'migration complete' messaging in the Agents Customization editor explicitly tell the user to delete the setting from settings.json?

## Evidence

- **settings deprecation is value-based:** src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts:1949-1982 shows PromptsConfig.INSTRUCTIONS_LOCATION_KEY (and the sibling agents/mode/prompt location keys) carry a markdownDeprecationMessage pointing users to the Agent Customizations editor; the warning is driven purely by the setting's JSON schema/value, not by any migration-completed state.
- **migration never touches the setting value:** customizationMigrationServiceImpl.ts's migration flow (computeMigration/createFileMigration, lines ~57-100) only lists and copies prompt/instructions/agent files via IPromptsService; there is no configurationService.updateValue call anywhere in this file for PromptsConfig.*_LOCATION_KEY.
- **getModifiedSettingIds only detects non-default values:** customizationMigrationCategories.ts:445-450 computes which settings are 'modified' (non-default) purely to show a banner ('The setting {0} is no longer read by {1}...') — it never clears them, so the setting stays non-default (and thus deprecated) after migration finishes.
