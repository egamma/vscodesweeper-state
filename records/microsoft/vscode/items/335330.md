# Issue #335330 — Agent cannot access files within folder when using remote ssh

[https://github.com/microsoft/vscode/issues/335330](https://github.com/microsoft/vscode/issues/335330)

## Summary

The exact wording in the report ("X links to Y, which is outside the current folder") matches the message built in extensions/copilot/src/extension/tools/node/readFileTool.tsx when getWorkspaceFileExternalConfirmation() in toolUtils.ts finds the file's realpath is not inside the workspace folder's realpath — this is consistent with an NFS automounter resolving the same directory to two different canonical paths, but confirming the exact divergence needs the reporter's mount topology, and any fix touches a security-relevant safety check, so this should stay open for a maintainer-guided plan rather than closing or auto-fixing.

## Change summary

On Remote-SSH into an NFS-mounted folder, the agent's external-file safety check treats files inside the opened workspace as "external" and demands confirmation, because the file's resolved realpath diverges from the workspace folder's resolved realpath.

## Best solution

Have a maintainer decide how the external-file check in getWorkspaceFileExternalConfirmation (extensions/copilot/src/extension/tools/node/toolUtils.ts) should tolerate automounter/bind-mount realpath divergence — e.g. comparing device+inode or caching a canonicalized workspace root once — without weakening the safety guarantee that flags genuinely external files.

- **Behavior:**

  > When a workspace folder is opened over Remote-SSH from an NFS-mounted path, files that are genuinely inside that folder must not trigger the "outside the current folder" external-file confirmation, even if the underlying filesystem's realpath resolution for the folder and for the file take different (but equivalent) canonical routes (e.g. via an NFS automounter symlink). Files that are actually outside the workspace must still be flagged.
- **Trace:**

  > getWorkspaceFileExternalConfirmation in extensions/copilot/src/extension/tools/node/toolUtils.ts (around line 287) calls Node's fs/promises `realpath` separately on the target file and on the workspace folder, then does a string-based extUriBiasedIgnorePathCase.isEqualOrParent comparison; readFileTool.tsx:279-285 renders the exact "links to ... outside the current folder" message from this result. The boundary: do not weaken the security intent of flagging files truly outside the workspace — any fix must still catch real external files/symlinks, just tolerate automounter-style equivalent-path divergence for the workspace root itself.
