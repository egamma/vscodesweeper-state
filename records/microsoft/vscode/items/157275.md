# Issue #157275 — Unable to connect to VS Code server: Error in request - ENOENT /run/user/1000/vscode-ipc-*.sock

[https://github.com/microsoft/vscode/issues/157275](https://github.com/microsoft/vscode/issues/157275)

## Summary

The stale IPC failure remains possible on current main and was confirmed again on VS Code 1.125.1. This should remain open for a lifecycle-aware fix covering persistent remote terminals across server or window reconnections.

## Change summary

Running `code` in a remote integrated terminal fails when its inherited `VSCODE_IPC_HOOK_CLI` points to a socket removed during a reconnect or server restart.

## Best solution

Preserve valid CLI routing when a remote terminal survives a reconnect, ensuring commands from that terminal reach its current VS Code window without selecting an unrelated live socket.

## Plan brief

- **Likely files:** `src/vs/server/node/server.cli.ts`, `src/vs/server/node/remoteTerminalChannel.ts`, `src/vs/workbench/api/node/extHostCLIServer.ts`
- **Validation:** Add an automated remote-terminal lifecycle test that creates a terminal, invalidates its original CLI socket, simulates reattachment or revival, and verifies that `code -r <file>` reaches the owning reconnected window; also verify normal newly-created terminal routing remains unchanged.
- **Behavior:**

  > A `code` command launched from a persistent remote integrated terminal continues to reach its owning VS Code window after the remote server or window reconnects and the terminal's original IPC socket disappears. It must not fail with ENOENT merely because the inherited socket path is stale. A newly created terminal must retain its existing CLI behavior, and recovery must not route commands to an unrelated VS Code window.
- **Trace:**

  > In src/vs/server/node/server.cli.ts, `cliPipe` is captured from `VSCODE_IPC_HOOK_CLI` and every remote CLI request uses that path without stale-path recovery. In src/vs/server/node/remoteTerminalChannel.ts, `_createProcess` creates both the socket path and CLIServerBase, but `AttachToProcess` and revived-terminal paths only reconnect to the pty host. CLIServerBase in src/vs/workbench/api/node/extHostCLIServer.ts owns and removes its socket independently of the shell process that retains the environment variable. The plan must trace remote-agent/channel disposal and persistent-terminal revival far enough to preserve ownership of the original logical window; selecting an arbitrary `vscode-ipc-*` socket is outside the acceptable boundary because it can target another window. https://github.com/microsoft/vscode/issues/336161 concerns an unavailable socket directory before listening and should remain separate.

## Evidence

- **current source:** On current main at 832cf23c588, src/vs/server/node/server.cli.ts reads `VSCODE_IPC_HOOK_CLI` once into `cliPipe` and passes it directly to `http.request` as `socketPath`; the request error handler exits without validating, refreshing, or retrying a stale path.
- **lifecycle gap:** src/vs/server/node/remoteTerminalChannel.ts creates a unique IPC handle and CLIServerBase only in `_createProcess`; `AttachToProcess` and revived-terminal requests delegate directly to the pty host without establishing updated CLI routing for an already-running terminal.
- **socket lifetime:** src/vs/workbench/api/node/extHostCLIServer.ts shows that CLIServerBase owns the HTTP socket and removes it on disposal, while the shell process retains the original environment value.
- **current confirmation:** A June 2026 comment on https://github.com/microsoft/vscode/issues/157275 reports the same stale-socket ENOENT behavior on VS Code 1.125.1, now using `/tmp/vscode-ipc-*.sock`.
- **canonical search:** https://github.com/microsoft/vscode-remote-release/issues/6997 was explicitly closed by a maintainer in favor of this issue. The open https://github.com/microsoft/vscode/issues/336161 is newer and describes failure to create an agent-host socket when XDG_RUNTIME_DIR is unavailable, not this stale CLI socket symptom.
- **impact:** The issue has 28 community upvotes and independent reports across Remote SSH, WSL, Codespaces, and Dev Containers; several users confirm that replacing the stale environment value or starting a fresh terminal restores operation.
