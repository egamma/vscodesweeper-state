# Issue #279149 — Prevent same version update with new update flow

[https://github.com/microsoft/vscode/issues/279149](https://github.com/microsoft/vscode/issues/279149)

## Summary

Keep open: the current developer update command still accepts the running build's installer without checking its identity. The older same-version fix does not cover current main, and the related product-target repair addresses a different defect.

## Change summary

Embed build identity in Windows setup executables and prevent Developer: Apply Update from File from applying the currently running build.

## Best solution

Make the file-based Windows update flow identify the selected installer's build and reject an identical running build before installation begins, while preserving updates between distinct Insiders commits and direct installer reinstalls.

## Plan brief

- **Likely files:** `build/gulpfile.vscode.win32.ts`, `build/win32/code.iss`, `src/vs/platform/update/electron-main/updateService.win32.ts`, `src/vs/workbench/contrib/update/browser/update.contribution.ts`, `src/vs/platform/update/common/update.ts`, `src/vs/platform/update/common/updateIpc.ts`
- **Validation:** On Windows, use _update.applyupdate to select the running build's setup executable: it must reject the selection before setup starts or an update becomes pending. Select a different Insiders commit sharing the same numeric version: it must remain eligible. Check user background and system foreground flows, and confirm launching the matching setup directly still permits reinstallation. Establish automated coverage for installer identity and same-build rejection during planning.
- **Behavior:**

  > The developer file-based update command currently accepts an installer for the running build and starts or queues a redundant update. It should identify that build from the selected executable and reject an identical build before installation begins. Different Insiders commits must not be rejected merely because they share a numeric version. Direct installer reinstallation and normal update-feed behavior must remain unchanged.
- **Trace:**

  > DeveloperApplyUpdateAction in src/vs/workbench/contrib/update/browser/update.contribution.ts passes only the selected executable path through updateIpc.ts. Win32UpdateService._applySpecificUpdate checks Idle state but does not inspect the package identity or compare it with productService.commit; its background and foreground branches subsequently spawn the selected package. build/gulpfile.vscode.win32.ts supplies numeric version and commit definitions to build/win32/code.iss, which currently exposes numeric VersionInfoVersion. The earlier manually entered commit guard cited by https://github.com/microsoft/vscode/issues/253311 is absent on current main and is not a solution to automatic executable identification. The trace establishes the missing rejection, but has not established a reusable executable-metadata reader or an automated Windows packaging/service harness. Keep pending-update recovery, normal feed updates, direct reinstalls, and the distinct product-target repair in https://github.com/microsoft/vscode/issues/327904 outside the behavioral change.
