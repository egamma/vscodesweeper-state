# Issue #99159 — Partial cross-file undo if a file is changed in the meantime

[https://github.com/microsoft/vscode/issues/99159](https://github.com/microsoft/vscode/issues/99159)

## Summary

A real gap remains on current main: when one resource blocks a cross-file undo, VS Code automatically falls back to undoing only the focused file rather than offering the requested safe partial undo. The team-authored Backlog request should remain open, and the maintainer discussion explicitly reserved it for this behavior.

## Change summary

Offer a partial cross-file undo when intervening changes prevent safely undoing the complete workspace edit.

## Best solution

Provide a clear choice to undo the workspace edit in every still-safe file or cancel, while identifying files that cannot participate and preserving the existing fail-safe behavior for operations that cannot be split safely.

## Plan brief

- **Likely files:** `src/vs/platform/undoRedo/common/undoRedoService.ts`, `src/vs/platform/undoRedo/test/common/undoRedoService.test.ts`
- **Validation:** Run `scripts/test.sh --grep "UndoRedoService"` with coverage for a three-resource workspace element where one resource has a newer edit, verifying partial undo affects only safe resources, cancel changes nothing, and existing complete and local undo behavior remains intact.
- **Behavior:**

  > After a workspace edit affects several files and one file receives a later edit, invoking undo from another affected file must not silently undo only that focused file. The user must be able to apply the original undo to all resources where it remains safe or cancel without changing any resource. The UI must identify or account for resources excluded from the partial operation, while ordinary complete cross-file undo remains unchanged.
- **Trace:**

  > Workspace undo validation is implemented in `UndoRedoService._checkWorkspaceUndo` in src/vs/platform/undoRedo/common/undoRedoService.ts. When any affected stack has a newer element, it calls `_tryToSplitAndUndo`; that method invokes `_splitPastWorkspaceElement` and then `_undo(strResource, 0, true)`, producing the current focused-file-only fallback. `_confirmAndExecuteWorkspaceUndo` has an all/current/cancel prompt for otherwise valid splittable elements, but the conflict path returns before reaching it. The related https://github.com/microsoft/vscode/issues/99295 owns random-access undo rather than this partial-safe-subset choice. Preserve atomic complete undo when every resource is valid, grouped undo ordering, redo invariants, and the defensive behavior for non-splittable workspace elements.
- **Open decisions:**
  - Should the conflict prompt offer partial undo and cancel only, or also retain an explicit focused-file-only option?
  - How should the prompt identify excluded resources without overwhelming users when a workspace edit spans many files?
  - What redo semantics should follow a partial undo so the affected and excluded resource stacks remain predictable?

## Evidence

- **maintainer direction:** The concluding maintainer comment at https://github.com/microsoft/vscode/issues/99159#issuecomment-637990725 explicitly says to keep this issue for implementing partial undo with a prompt; the separate random-access concept was moved to https://github.com/microsoft/vscode/issues/99295.
- **current source gap:** In src/vs/platform/undoRedo/common/undoRedoService.ts, `_checkWorkspaceUndo` detects affected resources whose workspace element is no longer at the top, then `_tryToSplitAndUndo` splits the element and recursively undoes only `strResource`. There is no partial/all/cancel choice for this conflict path.
- **existing prompt is insufficient:** The `_confirmAndExecuteWorkspaceUndo` prompt in src/vs/platform/undoRedo/common/undoRedoService.ts offers all files, the current file, or cancel only before a conflict is detected; once validation finds an intervening change, the fallback bypasses that prompt.
- **behavior origin:** Commit https://github.com/microsoft/vscode/commit/dc43bc617b16b015d05d1a9bf6e02a2b8d4eabd6 introduced the local-file fallback before this request was filed; current history contains no commit implementing the requested partial-safe-files behavior.
- **canonical search:** Searches for open partial and cross-file undo issues returned this issue itself. https://github.com/microsoft/vscode/issues/99295 is narrower and concerns random-access undo, so it does not absorb this request.
