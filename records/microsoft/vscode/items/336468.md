# Issue #336468 — Agents Window layout should be restored per session

[https://github.com/microsoft/vscode/issues/336468](https://github.com/microsoft/vscode/issues/336468)

## Summary

This is a real, accepted feature gap: editor tabs are restored per session, but the single-pane layout intentionally shares Editor/Details visibility and side-pane geometry, allowing a chat-only session to inherit another session's open pane. Keep it open for a maintainer-led design of the per-session restoration boundary.

## Change summary

Restore each Agents Window session's resource-pane arrangement so chat-only sessions remain full-width while sessions using editors, diffs, terminals, or browsers retain their layout.

## Best solution

Give each session an appropriate restorable workbench-layout snapshot, at minimum covering side-pane visibility and Editor/Details composition, so activating an editorless chat-only session closes inherited empty space and returning restores the prior session's resources. Keep terminal-internal split restoration tracked separately by https://github.com/microsoft/vscode/issues/335252 unless the design deliberately unifies those state models.

## Plan brief

- **Likely files:** `src/vs/sessions/LAYOUT_CONTROLLER.md`, `src/vs/sessions/SINGLE_PANE_SCENARIOS.md`, `src/vs/sessions/contrib/layout/browser/baseSessionLayoutController.ts`, `src/vs/sessions/contrib/layout/browser/singlePaneLayoutController.ts`, `src/vs/sessions/contrib/layout/browser/singlePane/singlePaneExistingSessionStrategy.ts`, `src/vs/sessions/contrib/layout/browser/singlePane/singlePaneDraftSessionStrategy.ts`, `src/vs/sessions/contrib/layout/browser/singlePane/singlePaneVisibilityProfileStore.ts`, `src/vs/sessions/contrib/layout/test/browser/desktopSessionLayoutController.test.ts`, `src/vs/sessions/contrib/layout/test/browser/singlePaneStrategies.test.ts`
- **Validation:** Add a focused single-pane layout-controller test that opens the editor/detail side pane in a workspace session, switches to an editorless no-workspace chat session and asserts the pane is closed, then switches back and asserts the original visibility, active editors, and selected detail are restored.
- **Behavior:**

  > Each Agents Window session should recover the resource layout associated with that session. Switching from a workspace session with an editor, diff, browser, or detail pane to an editorless chat-only session must leave the chat full-width rather than showing inherited empty space. Switching back must restore the first session's resources and agreed visibility/geometry state. Existing multi-session and explicit user-toggle behavior must remain consistent with the selected persistence policy.
- **Trace:**

  > BaseLayoutController in src/vs/sessions/contrib/layout/browser/baseSessionLayoutController.ts already stores per-session editor working sets, but SinglePaneLayoutController overrides `_isEditorPartVisibilityPerSession` and `_isViewStatePerSession` to return false. SinglePaneExistingSessionStrategy then captures and reapplies one shared `SessionVisibilityProfile.Existing`; the test `[single-pane] carries an open side pane to the next session instead of restoring stale session state` confirms that this is deliberate current behavior. SINGLE_PANE_SCENARIOS.md also makes side-pane width global across switches, so changing visibility alone versus visibility plus geometry is a product contract choice. Preserve per-session editor working sets and do not absorb terminal-internal split restoration from https://github.com/microsoft/vscode/issues/335252 unless maintainers explicitly choose a unified scope.
- **Open decisions:**
  - Should per-session restoration cover only part visibility and Editor/Details composition, or also side-pane and panel dimensions?
  - Should bottom-panel visibility and its selected view become fully per session in single-pane mode, or remain workbench-level while only editor/detail state is session-scoped?
  - When several sessions are visible simultaneously, should the shared effective layout be captured back to individual sessions, discarded as today, or restored only after returning to a single visible session?

## Evidence

- **current contract:** src/vs/sessions/LAYOUT_CONTROLLER.md states that editor working sets are per session, but single-pane uses a shared Editor/Details profile for Existing Sessions and workbench-level panel visibility.
- **intentional shared state:** src/vs/sessions/SINGLE_PANE_SCENARIOS.md explicitly says Existing Sessions share one Editor/Details visibility profile and side-pane sizes remain workbench-level across session switches.
- **source path:** src/vs/sessions/contrib/layout/browser/singlePaneLayoutController.ts disables per-session editor-part and auxiliary-view state through `_isEditorPartVisibilityPerSession` and `_isViewStatePerSession`, while SinglePaneExistingSessionStrategy reapplies `SessionVisibilityProfile.Existing` after a session change.
- **behavior locked by test:** src/vs/sessions/contrib/layout/test/browser/desktopSessionLayoutController.test.ts contains `[single-pane] carries an open side pane to the next session instead of restoring stale session state`, directly encoding the inheritance described by this report.
- **prior implementation:** https://github.com/microsoft/vscode/issues/315698 and merged https://github.com/microsoft/vscode/pull/315696 introduced per-session working sets and classic layout state, but they do not provide the requested single-pane per-session composition.
- **related issue:** https://github.com/microsoft/vscode/issues/335252 is older and tracks loss of terminal-internal split geometry, not the same observable symptom or the broader workbench-pane restoration requested here, so it is not a canonical duplicate.
