- **Behavior:**

  > The reporter wants the user and Copilot to collaborate in an existing integrated terminal, observing output and intervening without replacing the execution environment. Long-running server workflows should not strand an agent tool call or unexpectedly lose the usable shell after interruption. Agent execution should expose enough progress to recognize repeated work, and corrections should reach a running turn without requiring cancellation. Acceptance must distinguish existing capabilities from remaining gaps in the Windows/Git Bash Copilot session.
- **Trace:**

  > ShellManager in copilotShellTools.ts owns a private shell registry; the inspected workbench output/input tools instead resolve RunInTerminalTool execution IDs, neither of which establishes arbitrary user-terminal attachment. AgentHostActiveClientService forwards enabled client tools, so tool availability and the selected execution path must be checked rather than assuming all terminal tools disappeared. CopilotAgentSession already handles steering and reasoning/tool events, and chat.requestQueuing.defaultAction exposes steering in the workbench. RunTaskTool awaits output collection after its startup race, leaving server-return semantics to investigate. The supplied matcher omits captures required by ProblemPatternParser, while inline background monitors are supported. Preserve existing task completion/readiness semantics and terminal isolation until the collaboration contract is understood; do not infer measured latency from the IPC architecture alone. Related https://github.com/microsoft/vscode/issues/348170 provides terminal-intervention evidence but does not absorb this report's complete scope.

These inspected paths do not deliver the requested attachment to an existing user shell.
- **Existing steering:** src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts registers chat.requestQueuing.defaultAction with queue/steer choices and defaults to steer. src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts implements sendSteering, and agentHostSessionHandler.ts synchronizes steering messages. Therefore the blanket claim that current main offers only cancellation is not established; availability and behavior in the reporter's Stable session still need checking.
- **Existing progress plumbing:** src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts subscribes to reasoning deltas and maps tool execution events. Source-level event support does not prove that the reporter's loader-only presentation is resolved, nor that an always-visible execution stream or loop indicator exists.
- **Task requirements need separate validation:** RunTaskTool in src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/tools/task/runTaskTool.ts races task startup against a three-second timeout, then awaits collectTerminalResults. Its input schema contains workspaceFolder and id, with no explicit non-blocking option. The startup timeout alone does not establish that the complete tool invocation returns for a server.

ProblemPatternParser.validateProblemPattern requires file and message captures, plus line/location unless kind is file.
