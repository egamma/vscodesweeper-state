# Issue #171238 — Regression: debugger cannot attach to a child process

[https://github.com/microsoft/vscode/issues/171238](https://github.com/microsoft/vscode/issues/171238)

## Summary

Keep open: a VS Code debugger maintainer reproduced the regression and traced it to a race introduced by PR 166137 between parent-session termination and the child's `startDebugging` request. The discussion raises an unresolved product-contract question about whether VS Code must support launching or retaining child debug sessions after their parent session has ended.

## Change summary

Attaching debugpy to a process that replaces itself with `os.execv()` fails to launch the replacement process as a child debug session starting with VS Code 1.74.

## Best solution

Define the debug-session lifecycle contract for this race, then either allow a pending child-session launch to survive parent termination in VS Code's debug service or establish the adapter-side sequencing required to keep the parent alive until the child is registered.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugService.ts`, `src/vs/workbench/contrib/debug/common/debugModel.ts`
- **Validation:** Add or extend a debug service test that holds a child `startDebugging` request pending while the parent terminates, then verifies the behavior selected by the maintainer without regressing ordinary disconnect sequencing.
- **Behavior:**

  > When an attached debug target replaces itself and the adapter requests a child session while the parent session is terminating, VS Code must follow a defined lifecycle rather than losing the child request with "Failed to launch debugger for child process." Acceptance should cover the parent-disconnect/child-start race and preserve normal disconnect behavior for sessions with no pending child launch.
- **Trace:**

  > The reporter bisected the regression to https://github.com/microsoft/vscode/pull/166137, and a debugger maintainer reproduced it. The established sequence is: a `debugpyAttach` request is pending; the parent session terminates; VS Code awaits the disconnect response and stops the parent; the Python extension then calls `startDebugging`; core rejects the child because its parent is dead. The relevant boundary is the debug-session lifecycle and parent-child registration path, likely in `src/vs/workbench/contrib/debug/browser/debugService.ts` and the session model in `src/vs/workbench/contrib/debug/common/debugModel.ts`; ordinary parent disconnect ordering must not regress. Debugpy's asynchronous process-replacement behavior is also discussed at https://github.com/microsoft/debugpy/issues/43, so the plan must separate adapter sequencing from the core contract before choosing an implementation.
- **Open decisions:**
  - Should VS Code accept a child `startDebugging` request that was initiated while its parent was alive but arrives after that parent has terminated, or is the adapter contract that the parent must remain alive until child registration completes?
  - If child sessions may outlive their parent, how should the debug tree represent and manage those surviving sessions?

## Evidence

- **confirmed reproduction:** A VS Code debugger maintainer stated "I can repro" after the reporter supplied an MCVE, recording, version range, and a bisect to https://github.com/microsoft/vscode/pull/166137.
- **traced race:** The maintainer traced the observable failure: `debugpyAttach` is pending, the parent terminates, VS Code awaits disconnect and stops it, and the later `startDebugging` call is rejected because its parent session is already dead.
- **upstream context:** https://github.com/microsoft/debugpy/issues/43 documents debugger-side asynchrony, but the VS Code thread also identifies a core lifecycle/UI question about live child sessions whose parent has gone away.
