# Issue #271138 — Link MCP servers with Marketplace extensions

[https://github.com/microsoft/vscode/issues/271138](https://github.com/microsoft/vscode/issues/271138)

## Summary

This accepted, team-authored Backlog request remains necessary: current main keeps extension-provided MCP collections separate from Marketplace-managed servers and has no contract for linking equivalent entries. The desired deduplication is clear, but source precedence and extension control over the link need a maintainer design decision.

## Change summary

Associate equivalent Marketplace and extension-provided MCP servers so VS Code enables only one source without losing source-specific configuration.

## Best solution

Define an explicit, stable association between an extension contribution and its Marketplace MCP entry, then present and enable only the selected source while preserving its complete launch configuration. Avoid inferring equivalence solely from commands or server names because extensions can supply dynamic SDK paths, arguments, and tool exclusions.

## Plan brief

- **Likely files:** `src/vs/platform/extensions/common/extensions.ts`, `src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts`, `src/vs/workbench/contrib/mcp/common/discovery/extensionMcpDiscovery.ts`, `src/vs/workbench/contrib/mcp/common/mcpRegistry.ts`, `src/vs/workbench/contrib/mcp/browser/mcpWorkbenchService.ts`, `src/vs/workbench/contrib/mcp/test/common/mcpRegistry.test.ts`, `src/vs/workbench/contrib/mcp/test/browser/mcpWorkbenchService.test.ts`
- **Validation:** Add targeted MCP discovery/management tests showing that explicitly linked extension and Marketplace entries result in one enabled runtime server, preserve the selected source's full launch configuration, and do not merge unlinked servers merely because their names or commands match.
- **Behavior:**

  > When the same MCP server is intentionally linked between a Marketplace entry and a VS Code extension, users should see and enable one effective server rather than duplicate tools or competing installations. The chosen source must retain its complete launch configuration, including dynamic arguments and tool exclusions. Servers that only happen to share a name or executable must remain distinct unless the agreed linkage contract identifies them as equivalent.
- **Trace:**

  > Current main has two independent paths. ExtensionMcpDiscovery in src/vs/workbench/contrib/mcp/common/discovery/extensionMcpDiscovery.ts creates extension-prefixed collections from mcpServerDefinitionProviders, whose contract in src/vs/platform/extensions/common/extensions.ts and schema in src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts contain no Marketplace identity. McpWorkbenchService in src/vs/workbench/contrib/mcp/browser/mcpWorkbenchService.ts links locally installed MCP resources to gallery metadata by name/gallery ID, but it does not inspect extension collections. McpRegistry.registerCollection in src/vs/workbench/contrib/mcp/common/mcpRegistry.ts only resolves exact collection-ID replacement, not cross-source equivalence. The Dart case at https://github.com/microsoft/vscode/issues/271138#issuecomment-4125630652 establishes the boundary: do not infer equivalence from command text because extension launch details can intentionally differ. The broader https://github.com/microsoft/vscode/issues/278301 is related but does not settle this issue's linkage or precedence contract.
- **Open decisions:**
  - Should linking require an explicit Marketplace server identifier in the extension contribution contract, or may VS Code infer links from another stable identity?
  - When linked sources differ, should the extension-provided server always take precedence, should the user choose the active source, or should Marketplace configuration win by default?
  - How should the management UI represent a linked pair and expose source selection without presenting duplicate enabled servers?
