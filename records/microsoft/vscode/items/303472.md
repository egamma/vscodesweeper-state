# Issue #303472 — Title bar becomes hard to read when the window is inactive

[https://github.com/microsoft/vscode/issues/303472](https://github.com/microsoft/vscode/issues/303472)

## Summary

The maintainer's increase to 0.6 mitigates the original dimming, but current main still applies opacity on top of titleBar.inactiveForeground. Keep this open for a decision on theme-controlled inactive appearance and consistency with Windows caption buttons; the existing tests explicitly preserve the current dimming behavior.

## Change summary

Make inactive title-bar content readable and let its configured foreground color determine its appearance without additional, inconsistent opacity.

## Best solution

Define a consistent inactive-title-bar appearance contract for theme authors and Windows caption buttons. Prefer theme-token-controlled dimming rather than independently attenuating rendered title-bar content, while retaining a clear active/inactive distinction in default themes.

- **Behavior:**

  > Inactive title-bar content should remain readable, and theme authors should be able to predict its appearance from the documented foreground tokens. The report asks to avoid extra opacity that changes a configured color and makes web-rendered content differ from native Windows caption buttons. Acceptance should cover opaque custom foregrounds, default themes, and focus transitions, including keyboard focus in the menubar. The maintainer's increase from 0.3 to 0.6 is a mitigation, not a resolution of the theme-control request.
- **Trace:**

  > BrowserTitlebarPart.updateStyles selects titleBar.inactiveForeground and toggles the inactive class; titlebarpart.css then applies 0.6 opacity to child containers. The default inactive foreground itself is transparent in dark and light themes, so the two attenuation mechanisms compose. NativeTitlebarPart.updateStyles sends the uncomposited foreground to nativeHostService.updateWindowControls, leaving Windows overlay controls outside the CSS dimming path. The titlebarPart.test.ts menubar-focus test explicitly locks in 0.6/1 opacity behavior, so the uncertainty is the intended appearance contract, not whether the rule exists. Preserve keyboard menubar visibility, unrelated command-center token semantics, and native-title-bar behavior. The later matching report https://github.com/microsoft/vscode/issues/336929 is supporting evidence, not an eligible canonical.
- **Open decisions:**
  - Should titleBar.inactiveForeground fully determine inactive content appearance, with default dimming expressed through theme colors, or should VS Code retain additional container opacity and provide a supported way for themes or users to bypass it?
  - Should Windows native caption buttons and web-rendered title-bar content have matching effective foreground appearance when configured with the same opaque inactive foreground?
