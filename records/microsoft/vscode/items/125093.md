# Issue #125093 — Trust: dialogs should listen to changes

[https://github.com/microsoft/vscode/issues/125093](https://github.com/microsoft/vscode/issues/125093)

## Summary

The accepted bug remains in current main: trust changes propagate between windows, but an already-open startup trust dialog remains actionable and can restore stale untrusted indicators after another window trusts the parent folder.

## Change summary

Workspace Trust dialogs should react to trust changes made in another VS Code window and must not apply a stale choice.

## Best solution

When shared storage changes make the current workspace trusted, dismiss or otherwise invalidate both startup and immediate Workspace Trust prompts so their stale actions cannot override the current trust UI.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/workspace/browser/workspace.contribution.ts`, `src/vs/platform/dialogs/common/dialogs.ts`, `src/vs/workbench/services/dialogs/common/dialogService.ts`, `src/vs/workbench/common/dialogs.ts`
- **Validation:** Open the same Desktop child folder in two windows with both startup trust dialogs visible; trust the parent folder in one window and verify the other prompt closes or becomes non-actionable, the second window remains trusted, and restricted-mode indicators do not return. Also verify ordinary single-window Trust and Don't Trust actions retain their current behavior.
- **Behavior:**

  > A Workspace Trust prompt must not remain actionable after another window changes shared trust so that the prompt's workspace is already trusted. Trusting a parent folder in one window should cause the corresponding prompt in another window to close or become harmless, and the second window must remain trusted. Existing single-window Trust, Don't Trust, Manage, and Cancel behavior must remain unchanged.
- **Trace:**

  > WorkspaceTrustManagementService.registerListeners() in src/vs/workbench/services/workspaces/common/workspaceTrust.ts observes APPLICATION_SHARED storage changes, reloads trust information, and reaches updateWorkspaceTrust(), which fires onDidChangeTrust. WorkspaceTrustUXHandler in src/vs/workbench/contrib/workspace/browser/workspace.contribution.ts receives that event but only updates indicators; doShowModal() remains pending, and its untrusted action can subsequently force those indicators back to false. WorkspaceTrustRequestHandler has a separate immediate prompt path that should be checked against the same invalidation contract. IDialogService.prompt() does not expose a public cancellation handle even though DialogsModel internally owns close-capable items, so the uncertainty begins at the dialog lifecycle boundary. Do not change trust persistence semantics or broaden the work to unrelated modal dialogs.

## Evidence

- **cross-window propagation:** src/vs/workbench/services/workspaces/common/workspaceTrust.ts listens for APPLICATION_SHARED storage changes in registerListeners(), reloads trusted folders, and calls updateWorkspaceTrust(); updateWorkspaceTrust() then fires onDidChangeTrust when the effective state changes.
- **stale startup dialog:** WorkspaceTrustUXHandler in src/vs/workbench/contrib/workspace/browser/workspace.contribution.ts listens to onDidChangeTrust only to update workbench indicators. Its doShowModal() prompt remains open, and the untrusted button subsequently calls updateWorkbenchIndicators(false), recreating the stale restricted-mode UI described by the reporter.
- **dialog lifecycle gap:** IDialogService.prompt() in src/vs/platform/dialogs/common/dialogs.ts returns only the eventual prompt result and exposes no cancellation handle, while DialogsModel in src/vs/workbench/common/dialogs.ts has an internal close-capable dialog item. Resolving this safely may therefore involve shared dialog infrastructure rather than only Workspace Trust code.
