# Issue #232232 — Views drag and drop: allow to drop into the entire bar instead of splitting

[https://github.com/microsoft/vscode/issues/232232](https://github.com/microsoft/vscode/issues/232232)

## Summary

The requested drag-and-drop behavior remains absent on current main, and several workbench maintainers support exploring a more intuitive default. The interaction details remain under discussion, so the existing Backlog feature request should stay open.

## Change summary

Make dropping a view or view container over the main body of a sidebar or panel move it as a separate container by default instead of merging it into the target container.

## Best solution

Align view-container drag-and-drop with the editor-grid model: use the large central target for moving the container into the destination bar and reserve merging or splitting for smaller edge targets or an explicit modifier. Apply the resulting interaction consistently across the Primary Sidebar, Secondary Sidebar, and Panel.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/views/viewPaneContainer.ts`, `src/vs/workbench/browser/parts/editor/editorDropTarget.ts`
- **Validation:** Manually drag a single-view container and a multi-view container between the Primary Sidebar, Secondary Sidebar, and Panel, targeting both the center and edges with and without Shift; verify each accepted interaction matches the chosen move-versus-merge semantics and that reordering within the original container remains unchanged.
- **Behavior:**

  > Dragging a view or view container between workbench locations should offer a large, predictable target for moving it as a separate container rather than unexpectedly merging its views into another container. Splitting or merging must remain available through a clearly distinguishable target or modifier. The behavior should be consistent across the Primary Sidebar, Secondary Sidebar, and Panel, while ordinary reordering inside one container remains unchanged.
- **Trace:**

  > ViewPaneContainer in src/vs/workbench/browser/parts/views/viewPaneContainer.ts installs separate targets for the unused container area and each pane body. ViewPaneDropOverlay.positionOverlay currently divides a pane body into equal directional halves, and the pane onDrop handler always calls IViewDescriptorService.moveViewsToContainer before directional reordering, which produces the reported merge/split behavior. The editor precedent is in src/vs/workbench/browser/parts/editor/editorDropTarget.ts, where modifier-aware drop semantics already exist. Preserve same-container view reordering and non-movable/rejectAddedViews guards. https://github.com/microsoft/vscode/issues/173835 is related evidence about the consequences of merging containers, but it tracks the distinct hidden-view visibility defect.
- **Open decisions:**
  - When dragging a view from another container, should the unmodified central drop create a separate custom container while Shift merges it into the target container?
  - When dragging an entire view container from another location, should unmodified drop always move the container to the destination bar while Shift merges its views?
  - For a view container dragged onto another container in the same location, should the default operation remain a merge, become a no-op, or reorder the containers?

## Evidence

- **current source behavior:** src/vs/workbench/browser/parts/views/viewPaneContainer.ts registers each pane body as a drop target; ViewPaneDropOverlay.positionOverlay divides that entire target into two equal halves and records UP/DOWN or LEFT/RIGHT, after which onDrop moves the dragged views into the target container and reorders them.
- **missing requested interaction:** The view drop path in src/vs/workbench/browser/parts/views/viewPaneContainer.ts does not inspect a Shift modifier or provide a central drop zone that preserves the dragged item as a separate view container. By contrast, src/vs/workbench/browser/parts/editor/editorDropTarget.ts explicitly recognizes Shift-modified drag behavior.
- **maintainer direction:** Multiple maintainer comments support exploring the change across the Primary Sidebar, Secondary Sidebar, and Panel, while leaving the exact default-versus-Shift behavior unsettled.
- **related issue is distinct:** https://github.com/microsoft/vscode/issues/173835 is older and related, but reports hidden views becoming visible after a container merge. It references this issue as a prospective improvement, so it does not report the same observable symptom required for a re-reviewed duplicate close.
- **canonical search:** Repository issue searches for view-container drag/drop, splitting, and sidebar/panel merging found no older open issue that owns this same requested interaction.
