# Issue #227924 — Persisted files associated with a test run

[https://github.com/microsoft/vscode/issues/227924](https://github.com/microsoft/vscode/issues/227924)

## Summary

Keep open: current testing APIs still lack managed, run-associated file storage that survives reloads and is cleaned up when restored results are discarded. The testing maintainer endorsed this direction, and the existing testing label already routes the request correctly.

## Change summary

Allow extensions to retain profiling and other artifact files for a persisted test result's lifetime, including across VS Code restarts.

## Best solution

Provide a VS Code-managed storage URI associated with a test result, following the maintainer's suggested direction, with defined retention and cleanup semantics across reloads. Keep incremental coverage aggregation outside this request, as the reporter explicitly requested.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTesting.ts`, `src/vs/workbench/api/browser/mainThreadTesting.ts`, `src/vs/workbench/contrib/testing/common/testResultStorage.ts`, `src/vs/workbench/contrib/testing/common/testResultService.ts`, `src/vs/workbench/contrib/testing/test/common/testResultStorage.test.ts`
- **Validation:** Add focused testing storage/API checks that write an artifact for a persisted result, recreate the result storage to simulate reload, verify the artifact remains readable, then discard the restored result and verify its files are deleted without affecting another retained result. Include multiple unnamed runs and ordinary result-retention eviction.
- **Behavior:**

  > Extensions can retain files such as CPU and memory profiles with the test result that produced them. Those files remain available after a window reload while the corresponding result is retained, and VS Code owns their cleanup when that result is discarded. Multiple unnamed runs must remain distinguishable for artifact ownership. Acceptance checks cover reload persistence, explicit result removal, retention eviction, and isolation between results; incremental coverage aggregation is outside scope.
- **Trace:**

  > TestRun in src/vscode-dts/vscode.d.ts exposes isPersisted and onDidDispose but no managed artifact storage. MainThreadTesting in src/vs/workbench/api/browser/mainThreadTesting.ts forwards removal notifications only for LiveTestResult, and ExtHostTesting delegates disposal to its current-session run tracker. TestResultStorage in src/vs/workbench/contrib/testing/common/testResultStorage.ts already owns workspace-local result JSON/output retention and orphan cleanup; TestResultService.clear() removes completed results and schedules persistence. This establishes the existing lifecycle boundary but not an extension-facing file contract. The maintainer endorsed result-associated managed storage in https://github.com/microsoft/vscode/issues/227924; the public API and behavior for non-persisted runs remain unspecified. Preserve existing result ordering and persistence behavior, and do not expand this work into profile viewers or coverage merging.
- **Open decisions:**
  - What public API lets an extension obtain a result-owned storage URI and reconnect retained artifact files to their result after a reload?
  - Is managed artifact storage available for non-persisted runs, and what observable lifetime does it have in that case?
  - Do artifact files follow existing test-result retention limits regardless of their size, or does artifact storage introduce an additional documented retention limit?
