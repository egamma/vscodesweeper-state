# Issue #282076 — NES rendering for minor changes (i.e. missing letter or parenthesis)

[https://github.com/microsoft/vscode/issues/282076](https://github.com/microsoft/vscode/issues/282076)

## Summary

This team-authored Backlog request remains necessary: current main distinguishes inserted NES text with inline diff styling, but has no presentation specifically designed to keep one-character insertions from looking like committed source. The appropriate visual treatment is still a product decision, so it should remain open for UX discussion.

## Change summary

Make very small next-edit suggestions, such as a missing letter or closing delimiter, visually distinguishable from text already present in the file.

## Best solution

Define a theme-aware, accessible presentation for tiny NES insertions that clearly distinguishes pending text without making routine editing disruptive, then apply it through the inline-edit view-selection and rendering path.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/inlineCompletions/browser/view/inlineEdits/inlineEditsView.ts`, `src/vs/editor/contrib/inlineCompletions/browser/view/inlineEdits/inlineEditsViews/originalEditorInlineDiffView.ts`, `src/vs/editor/contrib/inlineCompletions/browser/view/inlineEdits/view.css`, `src/vs/editor/contrib/inlineCompletions/browser/view/inlineEdits/theme.ts`, `src/vs/workbench/test/browser/componentFixtures/editor/inlineCompletions/views.fixture.ts`
- **Validation:** Add component screenshot fixtures for a missing letter and a missing closing parenthesis, then verify that pending text remains unmistakable under light, dark, high-contrast, and the reported #d0d0c0 editor background while existing multi-character inline-edit fixtures remain unchanged.
- **Behavior:**

  > When NES proposes inserting only a letter, brace, parenthesis, or similarly small token, the user must be able to distinguish the proposed character from text already present in the file at a glance. The treatment should remain clear across built-in high-contrast themes and a custom #d0d0c0 editor background without making larger suggestions more intrusive. Acceptance should cover missing-letter and missing-delimiter examples and confirm that accepting or dismissing the suggestion retains existing behavior.
- **Trace:**

  > InlineEditsView._determineView in src/vs/editor/contrib/inlineCompletions/browser/view/inlineEdits/inlineEditsView.ts classifies a single-line insertion after the cursor as InsertionInline. That state flows through OriginalEditorInlineDiffView in src/vs/editor/contrib/inlineCompletions/browser/view/inlineEdits/inlineEditsViews/originalEditorInlineDiffView.ts, which injects the proposed text with inlineCompletions-char-insert and single-line-inline classes styled in view.css. The classification and styling do not distinguish one-character edits from longer inline insertions. editor.inlineSuggest.edits.showCollapsed is a global alternative and does not solve the visible-minor-edit case. Preserve acceptance, dismissal, cursor stability, larger-edit presentation, and the existing accessible-view path; the uncertainty begins at the desired user-visible cue for tiny edits.
- **Open decisions:**
  - Should tiny insertions remain inline with a stronger persistent visual boundary, use a separate callout-style presentation, or collapse to an indicator until the user navigates to them?
