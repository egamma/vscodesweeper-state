# Issue #347663 — Agents window “Open in Editor” opens a new folder window instead of the existing workspace window

[https://github.com/microsoft/vscode/issues/347663](https://github.com/microsoft/vscode/issues/347663)

## Summary

The current source still loses workspace-file identity during this round trip: Open in Agents passes a folder, and Open in Editor requests that folder rather than the existing workspace. Keep this open; the reported steps are sufficient and the related reports do not establish a duplicate.

## Change summary

Preserve the originating Remote SSH workspace-file context when returning from Agents to the editor.

## Best solution

Return to the matching originating editor window without replacing its .code-workspace context, while retaining current behavior when opening a different session working directory or worktree. Establish how that identity survives the cross-window handoff before implementing.

Verify the original editor window gains focus, its workspace-file identity remains unchanged, and no additional editor window appears. Add focused regression coverage for workspace-file reuse and preserve existing folder, worktree, remote-authority, and session-handoff cases.
- **Behavior:**

  > Returning from Agents to an already-open Remote SSH editor for the same project must preserve that editor's .code-workspace context instead of opening the project as a separate folder window. Acceptance is the reported three-step round trip with no additional editor window and the original workspace still active. Opening a session whose working directory differs from the original project must continue to target that session's directory.
- **Trace:**

  > OpenWorkspaceInAgentsWindowAction passes only the selected folder URI, although NativeHostMainService.openAgentsWindow also receives the invoking window ID as contextWindowId. The return action openSessionInVSCode constructs folder openables from the selected chat's working directories. WindowsMainService checks those against findWindowOnWorkspaceOrFolder, whose workspace-file branch matches configPath rather than workspace membership, conclusively explaining the identity mismatch. The unresolved technical boundary is how originating window/workspace identity can remain available through Agents open intents and subsequent session selection without becoming stale. Do not globally equate a folder with every workspace containing it, or redirect unrelated worktree sessions to the originating editor. Existing action coverage is in src/vs/sessions/test/electron-browser/vscodeActions.test.ts; related but distinct requests are https://github.com/microsoft/vscode/issues/311148 and https://github.com/microsoft/vscode/issues/318087.

## Evidence

- **Reported trigger:** https://github.com/microsoft/vscode/issues/347663 provides a concrete Remote SSH round trip from a single-folder .code-workspace through Open in Agents and back through Open in Editor; the result is a separate folder window.
- **Workspace identity discarded on entry:** In src/vs/workbench/contrib/chat/electron-browser/agentSessions/agentSessionsActions.ts, getInvokingWorkspaceFolder returns the sole folder URI, and OpenWorkspaceInAgentsWindowAction.run passes it as folderUri. IOpenAgentsWindowOptions in src/vs/platform/native/common/native.ts has no originating workspace-file field.
- **Folder-only return path:** In src/vs/sessions/electron-browser/actions/vscodeActions.ts, openSessionInVSCode builds IFolderToOpen entries from chat workspace workingDirectory values and calls nativeHostService.openWindow with forceNewWindow: true. It does not request the originating workspace file or identify its editor window.
- **Why the existing workspace is not reused:** src/vs/platform/windows/electron-main/windowsMainService.ts:702-728 looks for an existing window matching the requested folder. findWindowOnWorkspaceOrFolder in src/vs/platform/windows/electron-main/windowsFinder.ts:44-59 compares a workspace-file window against its configPath, not its contained folders. The project-folder URI therefore does not match the already-open .code-workspace window; forceNewWindow alone is not the complete explanation.
- **Related reports have different scopes:** Read https://github.com/microsoft/vscode/issues/318087, which reports opening the incorrect root path on Windows, and https://github.com/microsoft/vscode/issues/311148, which requests multi-root Agents support, repository selection, and cross-repository changes. Neither establishes ownership of this specific single-folder workspace return defect.
- **Search and inspection limits:** An open-issue search for Open in Editor with code-workspace returned this report alone; an open-PR search referencing 347663 returned no matches. The checkout is shallow, so local history cannot establish an older fix. No code was executed or modified.
