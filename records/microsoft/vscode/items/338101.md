# Issue #338101 — Toggling the Secondary Sidebar sometime reveal "Copilot Chat" even if it's hidden

[https://github.com/microsoft/vscode/issues/338101](https://github.com/microsoft/vscode/issues/338101)

## Summary

Traced a plausible root cause in core layout code: the auxiliary-bar restore logic falls back to any view container with 'active' views without checking whether the user explicitly hid it, and does so synchronously before giving a late-registering extension's view container a chance to report its views — so a just-unpinned built-in container (Chat) can win the fallback race against a still-activating extension's container (Claude Code).

## Change summary

Toggling the Secondary Sidebar sometimes reopens the hidden/unpinned "Chat" (Copilot) view container instead of the last-active one from another extension.

## Best solution

In src/vs/workbench/browser/layout.ts, make the auxiliary-bar (and panel) restore fallback respect the user's hidden/unpinned state for view containers (not just activeViewDescriptors.length>=1), and/or avoid substituting a different container before the real last-active one has had a chance to register its views during extension activation.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/layout.ts`
- **Validation:** A test asserting that reopening the Secondary Side Bar never substitutes a different, currently-hidden/unpinned view container for the last-active one, even when the last-active container's views are not yet registered (simulated late view registration).
- **Trace:**

  > setAuxiliaryBarHidden's restore path (src/vs/workbench/browser/layout.ts ~2313-2327) picks the last active auxiliary-bar view container, but if hasViews() (line 1983, using viewContainerModel.activeViewDescriptors) reports no views, it falls back to the first container anywhere in that location satisfying hasViews — with no check against the container's user-visible/pinned state (viewContainerModel.visibleViewDescriptors). A container the user just hid via the tab context menu can still pass hasViews() and so win the fallback race, especially if the real last-active container (contributed by a slower-activating extension) hasn't registered its views yet at the moment of this synchronous check — unlike paneCompositePart.openPaneComposite, which explicitly awaits extensionService.whenInstalledExtensionsRegistered() before giving up. Boundary: do not change the general restore flow for Sidebar/Panel beyond mirroring whatever fix is chosen here (setPanelHidden has the same fallback pattern at ~lines 2138-2141). Open question for a maintainer: should the fix filter the fallback by visibility (visibleViewDescriptors) alone, or also delay the decision until extensions finish registering, matching openPaneComposite's existing pattern?
- **Open decisions:**
  - Should the hasViews() fallback check filter by the container's user-visible/pinned state (visibleViewDescriptors) instead of/in addition to activeViewDescriptors?
  - Should setAuxiliaryBarHidden/setPanelHidden await extension registration (like openPaneComposite already does) before deciding the last-active container has no views, to avoid the race with slow-activating extensions?

## Evidence

- **fallback logic:** setAuxiliaryBarHidden in src/vs/workbench/browser/layout.ts (~lines 2313-2327) calls getLastActivePaneCompositeId(AuxiliaryBar); if !hasViews(viewletToOpen) it falls back to viewDescriptorService.getViewContainersByLocation(AuxiliaryBar).find(hasViews) — the first container satisfying hasViews, with no check for user-hidden/unpinned state.
- **hasViews semantics:** hasViews() (layout.ts ~line 1983) checks viewContainerModel.activeViewDescriptors.length >= 1; activeViewDescriptors (src/vs/workbench/services/views/common/viewContainerModel.ts:311) filters only by item.state.active, NOT by isViewDescriptorVisible (viewContainerModel.ts:316 visibleViewDescriptors) — so an explicitly user-hidden container like Chat can still satisfy hasViews() and win the fallback.
- **race acknowledged elsewhere:** doOpenPaneComposite in src/vs/workbench/browser/parts/paneCompositePart.ts (~lines 504-516) explicitly awaits extensionService.whenInstalledExtensionsRegistered() before giving up on an id, but the synchronous hasViews() pre-check in setAuxiliaryBarHidden has no equivalent wait, so a late-activating extension's container can momentarily look view-less and get bypassed in favor of an always-registered built-in container.
- **no existing test harness:** workbenchTestServices.ts stubs setAuxiliaryBarHidden as a no-op; no layout.test.ts covers this restore path, so there's no existing executable check to pin the fix against.
