# Issue #254931 — Enable/disable MCP server via UI/config per user/workspace

[https://github.com/microsoft/vscode/issues/254931](https://github.com/microsoft/vscode/issues/254931)

## Summary

Current main now provides global and workspace MCP enablement controls, including extension-provided servers, but it persists those decisions in machine-local storage rather than reflecting workspace policy in mcp.json. This team-authored Backlog request therefore retains a meaningful declarative-configuration gap, and the implementing PR does not explicitly reference this issue as required for a factual close.

## Change summary

Let users and workspace maintainers enable or disable individual MCP servers through the UI and declarative configuration, including extension-provided servers.

## Best solution

Retain the scoped controls in the Customizations UI and define a declarative mcp.json contract through which a repository can select its MCP servers and tools without unexpectedly overriding a developer's personal safety choices. The contract should specify precedence between checked-in policy and user, workspace, and session decisions across both local and Agent Host harnesses.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts`, `src/vs/workbench/contrib/mcp/browser/mcpServerActions.ts`, `src/vs/workbench/contrib/chat/common/enablement.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts`, `src/vs/platform/agentHost/node/agentHostCustomizationEnablementService.ts`
- **Validation:** Extend the MCP configuration, Customizations widget, and AgentHostCustomizationEnablementService unit suites to show that a declarative per-server workspace decision survives reload, is displayed consistently, and produces the same effective enablement in local and Agent Host harnesses while respecting the chosen precedence rules.
- **Behavior:**

  > Users can enable or disable each MCP server globally or for a workspace, including servers contributed by extensions, without uninstalling the server or extension. Workspace maintainers can record the intended server/tool selection declaratively so shared repositories have a reproducible baseline. The UI displays the effective state and scope, and manually disabled servers cannot be reactivated by modes or prompts. Acceptance requires equivalent effective behavior in local and Agent Host harnesses across reloads.
- **Trace:**

  > Current main already exposes scoped actions in src/vs/workbench/contrib/mcp/browser/mcpServerActions.ts and src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts. Local decisions are machine-local ObservableMemento entries in src/vs/workbench/contrib/chat/common/enablement.ts; Agent Host decisions are separately persisted and resolved by src/vs/platform/agentHost/node/agentHostCustomizationEnablementService.ts. The mcp.json schema in src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts does not represent the requested enabled state, so checked-in repository policy remains the missing boundary. https://github.com/microsoft/vscode/pull/330566 supplies the scoped storage foundation but does not settle declarative configuration or reference this issue. Preserve existing per-user and per-session controls, extension-provided-server support, and the session > workspace > global precedence unless the product contract explicitly changes them.
- **Open decisions:**
  - Should checked-in mcp.json enablement be an enforceable workspace policy or a repository-provided default that each user may override?
  - When declarative mcp.json state conflicts with existing profile, workspace-storage, or session decisions, which scope is authoritative and how should the UI explain that effective state?
