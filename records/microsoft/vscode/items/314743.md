# Issue #314743 — "Light 2026" theme does not have shadows, but VS Code shell does have shadows

[https://github.com/microsoft/vscode/issues/314743](https://github.com/microsoft/vscode/issues/314743)

## Summary

Valid UI consistency feedback for the 2026 Light theme/webview token surface, not enough for a close. Current main still sets the webview-exposed widget shadow token transparent while separate Modern UI workbench shadows are handled by style overrides, so this should be routed to the theme/webview owners for a design decision.

## Change summary

Make shadow behavior consistent between Light 2026 webviews and the surrounding VS Code workbench shell.

## Best solution

Have the 2026 theme/design owners decide whether Light 2026 should expose a non-transparent `widget.shadow` to webviews or continue suppressing widget shadows while aligning the remaining workbench shell shadows accordingly.

## Evidence

- **theme token on main:** `extensions/theme-defaults/themes/2026-light.json` still defines `widget.shadow`, `scrollbar.shadow`, `editorStickyScroll.shadow`, `sideBarStickyScroll.shadow`, `panelStickyScroll.shadow`, and `listFilterWidget.shadow` as transparent colors for Light 2026.
- **webview-facing usage:** `src/vs/workbench/contrib/webview/browser/pre/index.html` uses `var(--vscode-widget-shadow)`, so Light 2026 webviews receive the transparent widget shadow token described in the issue.
- **workbench shadow handling:** `src/vs/workbench/contrib/styleOverrides/browser/media/shadows.css` suppresses Modern UI part-level shadows but explicitly preserves floating-modal shadows such as hovers, dropdowns, dialogs, and notifications.
- **theme umbrella:** https://github.com/microsoft/vscode/issues/293405 is open for the 2026 default-theme refresh and asks users to open issues for bugs or suggestions with the `2026-themes` label; it is a broad feedback umbrella rather than a duplicate owner for this specific polish item.
