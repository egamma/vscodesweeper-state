# Issue #329209 — Support cron-like scheduling syntax for automations

[https://github.com/microsoft/vscode/issues/329209](https://github.com/microsoft/vscode/issues/329209)

## Summary

Keep open: the Agent Host already evaluates timezone-aware cron expressions, but automation authoring, agent tools, and portable imports still restrict users to preset schedules. This team-authored request remains broader than the newer related cron-UI request, which cannot replace it under the re-review rules.

## Change summary

Allow expressive cron-like automation schedules with timezone selection, validation, and next-run previews while preserving existing scheduling options.

## Best solution

Expose the existing host scheduling capability through a provider-aware schedule contract shared by automation authoring, tools, and portable definitions. Settle the supported expression dialect and timezone behavior first, coordinating the overlapping UI work with https://github.com/microsoft/vscode/issues/339781 and explicitly scoping optional context reuse and jitter/backoff.

- **Behavior:**

  > Users and agents should be able to define schedules beyond the existing hourly, daily, weekday, and weekly presets, including weekdays at 18:00 and the first day of each month. Accepted expressions should retain their intended timezone and recurrence through save, reload, editing, and any supported import/export path. Invalid expressions should produce helpful feedback, and next-run previews should agree with execution. Existing preset schedules must remain compatible; optional context reuse and jitter/backoff require explicit scope decisions.
- **Trace:**

  > The host already validates and evaluates five-field cron expressions through validateAutomationCron and nextAutomationCronOccurrence in src/vs/platform/agentHost/node/automationCron.ts, called by AgentHostAutomationService. The gap starts at IAutomationSchedule in src/vs/workbench/contrib/chat/common/automations/automation.ts and continues through the dialog, tool schema, blueprint parser, and AgentHostAutomationStore projection. projectSchedule classifies complex expressions as custom, and custom definitions are not editable through the current store; blueprint parsing rejects monthly expressions and non-local zones. Preserve provider-owned execution authority and unsupported-provider behavior rather than introducing renderer scheduling or silently changing recurrence semantics. Coordinate with https://github.com/microsoft/vscode/issues/339781 and https://github.com/microsoft/vscode/issues/329621; both are newer related requests, not duplicate targets for this item.
- **Open decisions:**
  - Which expression dialect is supported publicly: the existing five-field host dialect, or an expanded dialect including seconds or ordinal weekdays such as the first Monday?
  - Should schedules default to UTC as requested, or retain local-time defaults, and which per-schedule timezone choices should authoring and portable definitions expose?
  - Are jitter/backoff and cross-run context reuse part of this delivery, or separately tracked follow-ups?
