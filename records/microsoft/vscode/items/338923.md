# Issue #338923 — VS Code Stopped Rendering Mermaid Blocks in Jupyter Notebook (VS Code `1.140.0`)

[https://github.com/microsoft/vscode/issues/338923](https://github.com/microsoft/vscode/issues/338923)

## Summary

Fresh, well-diagnosed report; I traced the exact failure path in the bundled fastdom UMD wrapper and confirmed current main has no mitigation, so this is a real gap worth fixing in the mermaid extension's bundling, not a close.

## Change summary

Mermaid diagrams in Jupyter notebook Markdown cells fail to render (`.extend is not a function`) because the bundled fastdom dependency takes its AMD branch instead of its CommonJS branch.

## Best solution

Harden the mermaid-markdown-features webview bundle against an ambient global `define` (e.g. via esbuild's `define: { define: 'undefined' }` substitution) so bundled UMD dependencies like fastdom always resolve to their CJS/global export regardless of what else shares the notebook webview's global scope.

## Plan brief

- **Likely files:** `extensions/mermaid-markdown-features/esbuild.webview.mts`, `extensions/esbuild-webview-common.mts`
- **Validation:** Manually verify: open a Jupyter notebook, add a Markdown cell with a mermaid code fence, render it, and confirm the diagram renders with no `TypeError` in the notebook webview devtools console; ideally also simulate an ambient global `define`/`define.amd` in a local repro page loading the bundled notebook-out/index.js to confirm fastdom resolves correctly either way.
- **Behavior:**

  > Rendering a Mermaid diagram in a Jupyter notebook Markdown cell should always produce the diagram, regardless of what other scripts (e.g. widget/kernel-related RequireJS loaders) have run in that notebook's webview and left global state behind. No `TypeError` referencing fastdom/`.extend` should appear in the webview console. Non-notebook Mermaid rendering (Markdown preview, chat) must be unaffected.
- **Trace:**

  > The bundled fastdom 1.0.12 dependency (pulled in transitively via `mermaid` in extensions/mermaid-markdown-features/package.json) uses a UMD footer that prefers `typeof define == 'function'` over the CommonJS `module.exports` branch. esbuild (`extensions/esbuild-webview-common.mts`, used by extensions/mermaid-markdown-features/esbuild.webview.mts for the `notebook-out` bundle) does not rewrite or disable this runtime check, so if the hosting notebook webview iframe happens to already have a global `define`/`define.amd` (reporter's console shows `define.amd` as an object — the RequireJS pattern, not VS Code's own `src/vs/amdX.ts` which uses a boolean `define.amd = true`), fastdom resolves incorrectly and the bundled mermaid code calls `.extend()` on the wrong export. Boundary: do not change mermaid/dompurify/other dependency versions or restructure the extension's rendering pipeline — the fix should be a build-time shim scoped to how this extension's webview bundles are produced. Unconfirmed: the exact script/extension setting the global `define` in a notebook with no running kernel, and whether a mermaid-local fix alone is sufficient or whether the shared esbuild-webview-common.mts should also be hardened for other built-in webview extensions.
- **Open decisions:**
  - Should the `define`-shimming fix be applied narrowly to mermaid-markdown-features' esbuild config only, or added to the shared extensions/esbuild-webview-common.mts so other built-in webview extensions get the same defensive hardening?
  - Is it worth identifying and coordinating with whatever extension (likely Jupyter/ipywidgets) is leaving a RequireJS-style global `define` in the notebook webview, or is a purely defensive fix in mermaid sufficient?

## Evidence

- **root cause confirmed upstream:** fastdom 1.0.12's UMD footer is `if ((typeof define) == 'function') define(...); else if ((typeof module) == 'object') module.exports = exports;` (https://raw.githubusercontent.com/wilsonpage/fastdom/master/fastdom.js). If a global `define` function exists in the webview, fastdom calls `define(factory)` instead of assigning `module.exports`, so the bundled export esbuild captures is not the FastDom singleton — exactly matching the reported `Ge.default.extend is not a function`.
- **no existing mitigation on main:** extensions/mermaid-markdown-features/esbuild.webview.mts and the shared extensions/esbuild-webview-common.mts bundle with plain esbuild `bundle: true` and no `define`/banner shim; `git log` shows no related change to either file.
- **origin of global `define` is not VS Code's own AMD loader:** src/vs/amdX.ts sets `globalThis.define.amd = true` (a boolean), but the reporter's console shows `typeof define.amd -> "object"` (the classic RequireJS signature), suggesting another script sharing the notebook webview's global scope — most likely something in the Jupyter extension's ipywidgets support — sets it, not VS Code core.
