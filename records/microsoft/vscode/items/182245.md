# Issue #182245 — Complete app for android 

[https://github.com/microsoft/vscode/issues/182245](https://github.com/microsoft/vscode/issues/182245)

## Summary

Keep this accepted Android-app request open: 45 upvotes and the Backlog promotion establish demand, while the existing web/PWA experience does not deliver the requested native filesystem and local-terminal integration. No verified older canonical owns this Android-specific scope.

## Change summary

Provide an officially supported Android app with desktop-like editing, local file access, preview, and terminal capabilities.

## Best solution

Assess a supported Android host for the existing web workbench, with an explicit decision about local filesystem and execution capabilities. Preserve this issue as the Android-app request rather than treating browser installation or third-party ports as equivalent coverage.

## Plan brief

- **Likely files:** `build/gulpfile.vscode.ts`, `resources/server/manifest.json`, `src/vs/platform/files/browser/webFileSystemAccess.ts`, `src/vs/workbench/contrib/terminal/browser/terminalService.ts`
- **Validation:** The plan should define a runnable Android-device acceptance scenario: install the supported app, open and edit a local project, save and reopen it after restarting the app, and exercise the agreed terminal and preview capabilities with a hardware keyboard in tablet or desktop mode. Separately verify that existing web and desktop behavior remains unchanged.
- **Behavior:**

  > Users want an officially supported Android application, not merely a browser shortcut or an unofficial port. The central requested capabilities are editing local projects with reliable saving, preview, and terminal integration on tablets and desktop-mode devices. Acceptance must distinguish native Android capabilities from those available only through a remote development connection. The supported capability set needs agreement before implementation.
- **Trace:**

  > build/gulpfile.vscode.ts lists Windows, macOS, and Linux desktop targets, with no Android packaging target in that matrix. resources/server/manifest.json already supplies standalone PWA presentation, but WebFileSystemAccess.supported in src/vs/platform/files/browser/webFileSystemAccess.ts relies on browser filesystem APIs. TerminalService in src/vs/workbench/contrib/terminal/browser/terminalService.ts initially gates process support on a non-web environment or remote connection. These establish the existing web boundary, not an identified Android implementation path. https://github.com/microsoft/vscode-remote-release/issues/11558 was closed as a duplicate of this request; https://github.com/microsoft/vscode/issues/70764 concerns iPad support. Preserve existing desktop and browser contracts, and do not assume an Electron replacement: https://github.com/microsoft/vscode/issues/292049#issuecomment-5541355900 explicitly declines that rewrite. Uncertainty begins at the Android host's supported filesystem, execution, and extension contracts.
- **Open decisions:**
  - Should the supported Android app provide local terminal and preview execution, or initially support those capabilities only through remote development?
  - Which local-project access and permission-persistence guarantees should the Android app offer beyond the existing browser/PWA experience?
  - Should Android support include locally running extensions, or retain the web and remote extension execution contracts?
