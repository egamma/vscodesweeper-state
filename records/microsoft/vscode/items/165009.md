# Issue #165009 — Feature: identify Inlay Hints text (e.g. info in tooltip)

[https://github.com/microsoft/vscode/issues/165009](https://github.com/microsoft/vscode/issues/165009)

## Summary

Keep open: current inlay-hint hovers still lack a built-in explanation that the text is not document content or guidance to its settings. Existing appearance and visibility settings help users who already know the feature's name, but do not satisfy the requested discovery experience.

## Change summary

Make inlay hints identifiable in place and expose guidance for controlling their visibility.

## Best solution

Provide a quiet, discoverable explanation through the core inlay-hint interaction surface, identifying the text as an inlay hint and pointing to editor.inlayHints.enabled. Settle the presentation and provider-attribution scope before implementation, while preserving existing provider documentation and hint interactions.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/inlayHints/browser/inlayHintsHover.ts`, `src/vs/editor/contrib/inlayHints/browser/inlayHintsLocations.ts`, `src/vs/editor/contrib/inlayHints/browser/inlayHintsController.ts`
- **Validation:** Using an inlay-hint provider, check hints with and without provider tooltips, locations, commands, and insertion edits. The chosen interaction must identify the annotation as non-document text and expose the visibility setting even when provider tooltip content is absent; existing documentation, navigation, command execution, and insertion behavior must remain available. Include keyboard and screen-reader acceptance checks for the chosen surface.
- **Behavior:**

  > A user encountering unfamiliar inline annotations can discover that they are inlay hints rather than text stored in the document, and can find how to control their visibility without already knowing the feature's name. This must work when the provider supplies no tooltip. Existing provider documentation and interactive hint behavior remain available, and the explanation must not add distracting always-on editor content.
- **Trace:**

  > InlayHintsHover.suggestHoverAnchor in src/vs/editor/contrib/inlayHints/browser/inlayHintsHover.ts recognizes injected text carrying RenderedInlayHintLabelPart. Its computeAsync path supplies only optional provider content and interaction guidance, leaving the generic explanation absent. showGoToContextMenu in src/vs/editor/contrib/inlayHints/browser/inlayHintsLocations.ts supplies navigation and optional command actions, not identification or settings guidance. editor.inlayHints.enabled and appearance settings already exist in src/vs/editor/common/config/editorOptions.ts, so the remaining gap is discovery rather than a missing visibility control. The controller and location code access item.provider.displayName, but whether and how that metadata should be presented remains unestablished. Preserve hint visibility defaults, provider content, and existing click gestures; changing rust-analyzer defaults is outside this request. https://github.com/microsoft/vscode/pull/161859 addresses contrast, not this interaction.
- **Open decisions:**
  - Should identification and settings guidance appear directly in every inlay-hint hover, or behind a discoverable help action within the hover?
  - Should the initial experience identify only the generic inlay-hint feature and its global visibility setting, or also identify the supplying provider when metadata is available?

## Evidence

- **Current hover capability:** src/vs/editor/contrib/inlayHints/browser/inlayHintsHover.ts: InlayHintsHover.computeAsync emits provider hint and label-part tooltips, double-click insertion guidance, command/navigation guidance, and location documentation. It adds no generic inlay-hint identification, provider attribution, or visibility-settings guidance; hints without these optional contents can produce no explanatory hover.
- **Existing settings are partial coverage:** src/vs/editor/common/config/editorOptions.ts registers editor.inlayHints.enabled with on, off, onUnlessPressed, and offUnlessPressed, plus editor.inlayHints.padding, fontSize, and fontFamily. These control visibility and appearance but do not explain an unfamiliar annotation at the point of interaction.
- **Context menu does not fill the gap:** src/vs/editor/contrib/inlayHints/browser/inlayHintsLocations.ts: showGoToContextMenu requires a label-part location and constructs symbol-navigation actions and an optional provider command. It does not add generic identification or inlay-hint settings actions.
- **Contrast change is not the requested feature:** https://github.com/microsoft/vscode/pull/161859 merged on 2022-09-26 and changes inlay-hint contrast. The discussion at https://github.com/microsoft/vscode/issues/165009 explicitly distinguishes improved contrast from the remaining need for a discoverable explanation; the reporter reiterated that distinction after the maintainer suggested padding and contrast.
- **Related discussion supports the discovery problem:** https://github.com/rust-lang/rust-analyzer/issues/13495 is closed, but its discussion explicitly redirects the hover-identification proposal to this issue and includes independent accounts of mistaking parameter hints for Rust syntax. Its original request concerned extension defaults, so it is neither a duplicate canonical nor evidence that the core discovery request was completed.
