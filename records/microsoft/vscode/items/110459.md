# Issue #110459 — Make API commands simpler to consume

[https://github.com/microsoft/vscode/issues/110459](https://github.com/microsoft/vscode/issues/110459)

## Summary

The requested command-specific typing is still missing from the public API. Keep this open under API discussion: current declarations remain generic, and the maintainer's suggestion to check package.json command bindings leaves a public tooling-scope decision to resolve.

## Change summary

Provide command-specific argument checking and return-type inference for known API commands, including commands embedded in Command objects.

## Best solution

Define a backward-compatible public typing contract for known API commands that also supports Command objects while retaining arbitrary extension commands. Decide whether package.json command-binding validation belongs in the same effort or a separate tooling proposal.

Include negative cases showing whether malformed known-command arguments are rejected under the agreed compatibility contract.
- **Behavior:**

  > Extension authors should receive command-specific argument assistance and result inference for known API commands rather than relying solely on prose documentation. Commands embedded in Command objects should retain the relationship between the identifier and its arguments. Arbitrary extension commands must remain supported. Acceptance checks should cover direct calls, object construction, optional arguments, inferred results, and the agreed treatment of invalid known-command calls.
- **Trace:**

  > src/vscode-dts/vscode.d.ts exposes only a string identifier and any[] arguments for both Command and commands.executeCommand; the return generic is supplied independently of the command identifier. Internal command descriptions live in src/vs/workbench/api/common/extHostApiCommands.ts, while ExtHostCommands.registerApiCommand in extHostCommands.ts performs runtime validation and conversion. These internal checks do not close the public authoring gap. Preserve runtime dispatch and arbitrary extension-command support. The issue's broad string fallback may accept malformed calls that a specialized overload rejects, so the public compatibility and checking guarantees need explicit agreement. The maintainer comment at https://github.com/microsoft/vscode/issues/110459#issuecomment-726205635 additionally raises package.json binding validation, whose inclusion remains undecided.
- **Open decisions:**
  - Should malformed calls to known command identifiers become compile-time errors, or must the existing permissive string overload continue accepting them?
  - Should the initial public contract cover TypeScript calls and Command objects only, or also validate command bindings contributed through package.json?
