# Issue #174355 — Gathering feedback from Diagnostics

[https://github.com/microsoft/vscode/issues/174355](https://github.com/microsoft/vscode/issues/174355)

## Summary

Keep this accepted feature request open: current diagnostic hovers do not provide per-diagnostic usefulness feedback, and no verified canonical or landed implementation was found. Its 23 upvotes and explicit Backlog promotion support a maintainer-led design session.

## Change summary

Allow users to submit explicit helpful or unhelpful feedback for individual diagnostics directly from their hover.

## Best solution

Define a provider-aware diagnostic feedback contract and an unobtrusive, accessible per-diagnostic hover interaction that works without quick fixes and remembers submitted feedback. Decide the feedback destination and reporting behavior before implementation; automatic diagnostic suppression and provider disabling are optional follow-up scope.

- **Likely files:** `src/vs/editor/contrib/hover/browser/markerHoverParticipant.ts`, `src/vs/platform/markers/common/markers.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** Exercise a diagnostic hover containing two diagnostics from different providers, including one with no quick fix. Verify that keyboard and pointer feedback target the selected diagnostic, reopening the hover retains its submitted state, and moving that diagnostic within the same file preserves the agreed identity. Confirm feedback reaches only the agreed recipient, existing quick-fix and navigation behavior remains unchanged, and screen readers identify each feedback control and its state.
- **Behavior:**

  > Users should be able to explicitly mark an individual diagnostic helpful or unhelpful from its hover, even when no quick fix exists. Multiple diagnostics in one hover must have independently attributable feedback, and subsequent hovers should show feedback already submitted according to the workspace-persistence requirement. Feedback alone must not silently hide diagnostics or disable providers; those are optional extensions of the request rather than prerequisites. Acceptance includes keyboard and screen-reader access, correct provider attribution, retained feedback state, and unchanged existing diagnostic actions.
- **Trace:**

  > MarkerHoverParticipant.renderHoverParts in src/vs/editor/contrib/hover/browser/markerHoverParticipant.ts renders individual diagnostic rows through _renderMarkerHover, but its shared status bar selects a single marker and offers navigation, quick fixes, and menu actions rather than per-row usefulness feedback. IMarker and IMarkerData in src/vs/platform/markers/common/markers.ts carry owner/source/code/message information, while IMarkerService has no feedback delivery contract. The inspected diagnostic API in src/vscode-dts/vscode.d.ts likewise supplies no diagnostic feedback event; existing chat feedback is not diagnostic feedback. The feature therefore remains missing, but the trace does not establish who should receive feedback or how a negative-feedback reporting action selects its destination. Preserve existing diagnostic publication, quick fixes, navigation, and visibility. The request and its accepted Backlog status are recorded at https://github.com/microsoft/vscode/issues/174355.
- **Open decisions:**
  - Should diagnostic feedback be delivered to the originating diagnostic provider through an extension API, collected centrally by VS Code, or both, and what diagnostic information may each recipient receive?
  - Should an unhelpful vote offer a core VS Code issue-reporting action as requested, a provider-specific reporting action, or no reporting action when an appropriate destination is unavailable?
