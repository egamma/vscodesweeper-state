# Issue #332725 — Renderer and extension host OOM when running multiple concurrent Copilot chat/agent sessions (Windows)

[https://github.com/microsoft/vscode/issues/332725](https://github.com/microsoft/vscode/issues/332725)

## Summary

Well-diagnosed report: growing 'potential listener LEAK detected' warnings tied to the chat code-block editor pool and chat editing modified-file-entry creation, correlating with renderer/extension host OOM crashes during long, multi-window Copilot agent sessions. Already labeled 'chat'; no fix found on main, so this stays open for investigation.

## Change summary

Running 2+ concurrent long Copilot agent chat sessions on Windows leads to escalating listener leaks and eventual renderer OOM / extension host crashes.

## Best solution

Investigate why CodeBlockPart/EditorPool references (src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatContentCodePools.ts, chatCollections.ts) or chatEditingSession._createModifiedFileEntry's model references (chatEditingSession.ts) aren't consistently released/disposed during long streaming sessions, causing listeners to accumulate; the ResourcePool trimming logic itself looks correct, so the leak likely lies in a caller failing to release a pooled item or a modified-file-entry reference.

## Evidence

- **pool implementation:** src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatContentCodePools.ts EditorPool.get() returns an IDisposableReference whose dispose() calls _pool.release(); if a caller in the render path fails to dispose this reference during streaming re-renders, CodeBlockPart instances (and their internal listeners, matching the reported leak stack through xw.renderCodeBlock/new xw) would accumulate indefinitely.
- **pool trimming looks correct:** src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatCollections.ts ResourcePool trims idle items via a debounced timer, so the leak is more likely items stuck in `_inUse` (never released) rather than a broken trim mechanism.
- **second leak stack:** chatEditingSession.ts `_createModifiedFileEntry` acquires a text model reference via `_textModelService.createModelReference(resource)` (line ~1203) whose disposal path would need to be verified for every code path (including early returns/errors) to avoid leaking the `onDidChangeFilesAssociation` listener reported in the second stack.
- **reporter confirmation:** Reporter reproduced the same crash pattern (ptyHost heartbeat loss, listener-leak counts scaling with session duration, OOM code -536870904) across two separate days/sessions in the issue body and the follow-up comment, with per-process working-set growth on a machine with ample free RAM, ruling out system-wide memory pressure.
- **related but unverified:** https://github.com/microsoft/vscode/issues/331901 reports a similarly-themed renderer memory growth / OOM during long Copilot Agent sessions (on Linux); could not fetch its body to verify it documents the same leak stacks, so treating as an unverified lead rather than a confirmed duplicate.
