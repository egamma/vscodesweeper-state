# Issue #70824 — Ability to vary completion item insertion (based on chosen commit character?)

[https://github.com/microsoft/vscode/issues/70824](https://github.com/microsoft/vscode/issues/70824)

## Summary

Keep open: current completion APIs cannot vary insertion text or additional edits by how an item is accepted. Insert/replace support changes only the replacement range, and the older commit-character suppression issue explicitly treats conditional edits as separate work.

## Change summary

Allow users to choose different insertion text and additional edits when accepting the same completion item, without duplicating completion entries or changing settings.

## Best solution

Define an opt-in completion API and interaction for alternative insertion behavior, covering auto-import versus qualified-name insertion. Coordinate with the separate commit-character suppression work without treating suppression alone as satisfying this request.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages.ts`, `src/vs/editor/contrib/suggest/browser/suggestCommitCharacters.ts`, `src/vs/editor/contrib/suggest/browser/suggestController.ts`
- **Validation:** After choosing the contract, add completion acceptance tests showing that one displayed item can either insert an unqualified name plus an import or insert a qualified name without an import. Verify existing acceptance and insert/replace behavior remains unchanged; test the zero-argument parentheses case if commit-character-dependent behavior is included.
- **Behavior:**

  > A language extension should be able to offer alternative insertion outcomes for one completion entry. The Haxe example requires choosing between an unqualified type name with an import edit and a fully qualified name without that edit, at acceptance time and without changing settings. The interaction must remain understandable and keyboard-accessible. Existing completion providers must retain their current behavior unless they opt in.
- **Trace:**

  > CompletionItem in src/vscode-dts/vscode.d.ts and the internal completion contract in src/vs/editor/common/languages.ts expose a single insertion and additional-edit payload. CommitCharacterController in src/vs/editor/contrib/suggest/browser/suggestCommitCharacters.ts recognizes the typed character but forwards only the selected item; SuggestController._insertSuggestion applies that item's existing payload. The existing acceptAlternativeSelectedSuggestion command changes overwrite ranges through getOverwriteInfo, not text or additional edits. https://github.com/microsoft/vscode/issues/42544 tracks suppression separately, as explicitly stated at https://github.com/microsoft/vscode/issues/42544#issuecomment-773110768. Source inspection establishes the missing contract, but not the intended interaction or its extension-host and protocol transport design. Preserve current provider behavior and insert/replace semantics; do not assume character suppression alone resolves this request.
- **Open decisions:**
  - Should alternative insertion be selected through acceptance keys and commit characters, an explicit completion-item action menu, or both?
  - What opt-in public completion contract should expose alternative insertion text and additional edits, and which acceptance inputs should that contract distinguish?

## Evidence

- **Current API gap:** src/vscode-dts/vscode.d.ts:5036–5091 exposes one insertText value, one additionalTextEdits array, and commitCharacters as string[]. resolveCompletionItem at line 5223 receives an item and cancellation token, not the acceptance key or commit character.
- **Acceptance path:** src/vs/editor/contrib/suggest/browser/suggestCommitCharacters.ts invokes accept(this._active.item) without passing the typed character. suggestController.ts:169 forwards that item to _insertSuggestion; lines 354–370 apply its additionalTextEdits and lines 435–453 insert its insertText.
- **Existing capability is partial:** editor.suggest.insertMode and acceptAlternativeSelectedSuggestion already support alternate insert/replace acceptance. However, suggestController.ts:574–589 changes overwrite ranges, not insertion text or import edits; the alternative command at lines 880–890 therefore cannot implement the Haxe example.
- **Related issue is not a canonical:** https://github.com/microsoft/vscode/issues/42544 is verified open and older, but primarily requests suppression of the typed commit character. https://github.com/microsoft/vscode/issues/42544#issuecomment-773110768 explicitly distinguishes suppression from choosing a different text edit and recommends keeping them separate. It covers the parentheses subcase, not the full auto-import versus qualified-name request.
- **Related protocol work does not complete this request:** https://github.com/microsoft/language-server-protocol/issues/793 concerns append versus replace ranges and was reported implemented in LSP 3.16 at https://github.com/microsoft/language-server-protocol/issues/793#issuecomment-721376939. That capability does not select different insertion text or additional edits.
- **Canonical search:** Open-issue searches for completion commit characters, alternative completion behavior, and additionalTextEdits found no verified canonical owning the full request. https://github.com/microsoft/vscode/issues/183092 concerns lazy resolution of textEdit.newText for performance, not selection based on acceptance input.
