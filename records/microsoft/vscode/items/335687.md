# Issue #335687 — Agent Host downloads Claude SDK 0.3.239 / Claude Code 2.1.239, but Fable 5.1 requires >= 2.1.251

[https://github.com/microsoft/vscode/issues/335687](https://github.com/microsoft/vscode/issues/335687)

## Summary

This is a recurring structural gap, not a one-off bug that's been fixed: the Claude Agent SDK version is pinned in package.json/product.json and only bumped on VS Code release cadence, so newly released Claude models (Fable 5.1, and now Opus 5.5 per later comments) routinely outpace the bundled runtime's minimum-version requirement. Main currently pins 0.3.258 (up from 0.3.239 in 1.136.2), but comments from 2026-09-24 show the same failure mode recurring with newer models, so the underlying gap remains.

## Change summary

Agent Host downloads a pinned Claude Agent SDK build whose bundled Claude Code binary is too old for models already exposed in the model picker, and the resulting error doesn't clarify that Agent Host's own managed runtime (not the user's system Claude Code) needs updating.

## Best solution

Either decouple the Agent Host SDK-cache download from the fixed package.json pin (e.g. fetch/verify against a minimum-compatible version per model, or allow faster out-of-band updates) so new models aren't blocked by release cadence, or at minimum surface a clearer error naming the Agent Host-managed runtime (not system Claude Code/extension) as what needs updating, and hide/disable a model in the picker until the managed SDK satisfies its minimum version.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentSdkDownloader.ts`, `src/vs/platform/agentHost/common/claudeModelConfig.ts`, `package.json`
- **Validation:** A maintainer-approved design would end with either a test asserting Agent Host refuses/hides a model whose minimum Claude Code version exceeds the cached SDK's bundled version, or a mechanism test that the SDK cache updates independent of the VS Code release train.
- **Behavior:**

  > Selecting a model in the picker (e.g. Fable 5.1, Opus 5.5) should never silently fail because Agent Host's own managed SDK cache is running an incompatible bundled Claude Code build. Either the managed runtime is compatible before the model is offered, or the failure clearly states that VS Code's Agent Host runtime (not system Claude Code or the extension) needs updating.
- **Trace:**

  > The Claude Agent SDK version is a static pin in package.json (currently 0.3.258 on main) consumed by agentSdkDownloader.ts, which downloads exactly that version into %APPDATA%/Code/agent-host/sdk-cache regardless of which models are exposed in the picker. There is no code path that checks a model's minimum Claude Code version against the cached SDK version before offering/using the model. The boundary: do not change the SDK download/caching pipeline wholesale — the fix is either a compatibility gate before model use, better error messaging naming the Agent Host runtime, or a faster/decoupled update mechanism for the SDK pin. Related: https://github.com/microsoft/vscode/issues/325721 (agent-host version mismatch over SSH) touches similar version-skew territory but is a distinct SSH-provisioning symptom, not the same root report.
- **Open decisions:**
  - Should the SDK cache be updateable independent of VS Code's release cadence (e.g. auto-fetch newer compatible builds), or should the fix instead be gating/hiding incompatible models in the picker until a release ships a sufficient SDK pin?
  - If gating models, what UX communicates that the block is the Agent Host-managed runtime and not the user's own Claude Code/extension installation?

## Evidence

- **current pin:** package.json:171 pins "@anthropic-ai/claude-agent-sdk": "0.3.258" on current main — already bumped once from 0.3.239, but comments (2026-09-24) report the same class of failure with newer models like Opus 5.5.
- **download mechanism:** src/vs/platform/agentHost/node/agentSdkDownloader.ts fetches the SDK tarball per the version baked into product.json at build time; there is no per-model minimum-version check or dynamic update path in that module.
- **workaround reported:** Comment by masterbugs describes manually copying a newer claude binary into the agent-host sdk-cache directory to work around the pin — confirming the root cause is the fixed dependency version, not a code defect elsewhere.
