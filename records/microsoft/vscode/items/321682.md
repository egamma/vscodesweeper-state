# Issue #321682 — It says files are ignored when they are not.

[https://github.com/microsoft/vscode/issues/321682](https://github.com/microsoft/vscode/issues/321682)

## Summary

The original confusion was org-level content exclusion (not a defect), but two actionable things remain: there is no way to see which rule or source excluded a file, and the later comment's report of one repo's exclusions silently excluding a whole multi-root workspace is confirmed in current main — RemoteContentExclusion matches every file against a flattened, repo-unscoped glob list.

## Change summary

Copilot tools report files as "configured to be ignored" with no indication of which exclusion rule or source caused it, and exclusions from one repository appear to apply to every repository in a multi-root workspace.

## Best solution

Scope glob content-exclusion rules to the file's own repository (plus the unscoped org/non-git rule set) the way the regex rules already are, in extensions/copilot/src/platform/ignore/node/remoteContentExclusion.ts, and surface the matching rule's source (the already-parsed ContentExclusionRule.source) in the user-visible/ log message so reporters can tell where the rule comes from.

- **Behavior:**

Rules that genuinely apply workspace-wide (the unscoped organization rule set) must keep applying to every file, including files outside any git repository. Acceptance: a repo-b file stays readable by Copilot tools while repo-a is excluded by `**`; existing exclusion behavior for single-repo workspaces, non-git files, and the regex (ifAnyMatch/ifNoneMatch) rules is unchanged. Secondary ask from the reporter, to be decided as part of the plan: when a tool read is refused, the user should be able to tell which rule and which source (organization or repository, by name) caused it.
- **Trace:**

  > RemoteContentExclusion.isIgnored (extensions/copilot/src/platform/ignore/node/remoteContentExclusion.ts) resolves the file's repo and computes `fileName` relative to that repo root, then matches it against `this._compiledGlobs` — a list rebuildCompiledRules() flattens from `patterns` across every entry of `_contentExclusionCache`, i.e. every repo fetched in the session. Nothing restricts the glob match to the file's own `repoMetadata.fetchUrls`, so one repo's `**` rule excludes the whole workspace; the regex branch a few lines below is already scoped via `regexRuleSources` (fetch urls + NON_GIT_FILE_KEY) and folds the scope into its cache key, which is the shape the glob path is missing. Note that `_ignoreGlobResultCache` memoises verdicts per URI and is only retired by `invalidateVerdicts()` on a rule-generation bump, so any scoping change must keep generation/expiry handling intact. The boundary: do not change the fetch/batching/backoff machinery, the NON_GIT_FILE_KEY semantics for files outside a repo, or the regex rule path; the diagnosability ask (ContentExclusionRule.source is parsed but never used, and CopilotIgnoreInfoFileContentProvider in extensions/copilot/src/platform/ignore/vscode/ignoreInfoFileContentProvider.ts is unregistered) is a separate change to decide on, not a prerequisite. - **Open decisions:**

## Evidence

- **root cause of the original report:** The reporter resolved it themselves in https://github.com/microsoft/vscode/issues/321682#issuecomment — the rules came from their organization's Copilot content exclusions. What remains is their explicit ask: "There should still be a way to determine where the rules are coming from… Is there a way to list the rules and their source?"
- **source is parsed but never surfaced:** extensions/copilot/src/platform/ignore/node/remoteContentExclusion.ts declares `ContentExclusionRule.source: { name: string; type: 'Repository' | 'Organization' }`, but `source` is never read anywhere in the file; the only trace is a debug-level `File ... is ignored by content exclusion rule ${glob.pattern}` log. The user-facing text (extensions/copilot/src/platform/ignore/common/ignoreService.ts, HAS_IGNORED_FILES_MESSAGE) only links to the docs, and CopilotIgnoreInfoFileContentProvider in extensions/copilot/src/platform/ignore/vscode/ignoreInfoFileContentProvider.ts has no registration anywhere in the tree.
- **cross-repo leakage confirmed on main:** In RemoteContentExclusion.isIgnored, the glob loop walks `this._compiledGlobs`, which rebuildCompiledRules() builds by flattening `patterns` from *every* entry of `_contentExclusionCache` (i.e. every repo fetched so far), and matches them against a `fileName` computed relative to the file's *own* repo root. A `**` rule fetched for repo A therefore excludes files in repos B and C. The regex path immediately below is explicitly scoped (`regexRuleSources` = this file's fetch urls + NON_GIT_FILE_KEY, with the rule set folded into the cache key, commented "Regex rules are per repository"), so the glob path's lack of scoping looks like an oversight rather than a design choice.
- **matches the later report:** https://github.com/microsoft/vscode/issues/321682#issuecomment by kapouer (2026-09-28): adding a repository whose exclusions contain `**` to an existing multi-root workspace caused Copilot to exclude all files from all repositories; removing it restored the expected list. That is exactly what the flattened glob list produces.
- **no canonical found:** The pre-search candidates are about .gitignore/file-watcher/search scope (https://github.com/microsoft/vscode/issues/62725, https://github.com/microsoft/vscode/issues/308995, https://github.com/microsoft/vscode/issues/48674) and own different work; none covers Copilot content-exclusion scoping or diagnosability.
