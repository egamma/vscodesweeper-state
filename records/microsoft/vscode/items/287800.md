# Issue #287800 — ⛔ 100% CPU on Windows when a watched file is deleted

[https://github.com/microsoft/vscode/issues/287800](https://github.com/microsoft/vscode/issues/287800)

## Summary

Keep open as upstream tracking: the Windows watcher loop has confirmed reproductions, and the original fix was reverted. A newer mitigation on main directly addresses the reported event loop, but runtime resolution and adoption of the native fix have not been established.

## Change summary

Prevent permanently deleting or replacing a watched Windows directory from leaving a file-watcher process consuming an entire CPU core indefinitely.

## Best solution

Confirm that the August watcher mitigation stops the original deletion/recreation trigger and the installer-triggered PATH case on Windows, while tracking delivery of the libuv correction through VS Code's runtime. Keep terminal completion recovery requirements distinct from the native CPU loop.

## Evidence

- **Confirmed upstream root cause:** The maintainer confirmed reproduction at https://github.com/microsoft/vscode/issues/287800#issuecomment-3753559548 and reproduced it with bare Node.js at https://github.com/microsoft/vscode/issues/287800#issuecomment-3758735453. https://github.com/nodejs/node/issues/61398 remains open; its investigation attributes the loop to libuv retaining a handle to a permanently deleted NTFS directory.
- **Original fix is not completion evidence:** https://github.com/microsoft/vscode/pull/288003 merged in January, but commit 66a451a86cc9fdfad0f4111256773c9ac3183cc2 reverted it. The issue was explicitly reopened on April 27 at https://github.com/microsoft/vscode/issues/287800#issuecomment-4328330954, followed by independently measured CPU loops in July and August.
- **New mitigation on current main:** https://github.com/microsoft/vscode/commit/31a2160bbe836d263a187e63da66a5f6859be335 merged August 25 via https://github.com/microsoft/vscode/pull/332535, after reopening. In src/vs/platform/files/node/watcher/nodejs/nodejsWatcherLib.ts:300-339, the rename handler recognizes the absolute watched-root filename, prevents repeated events from postponing the deletion check, closes the stale watcher with activeWatch.clear(), and reattaches if the path exists. This directly addresses the reported delete/recreate trigger rather than merely suppressing error callbacks.
- **Mitigation validation limits:** src/vs/platform/files/test/node/nodejsWatcher.test.ts:621-660 contains a Windows regression exercising three permanent delete/recreate cycles, stable raw-event counts after reattachment, and subsequent file events. The PR reports three focused regressions passing, but the enclosing suite is marked suite.skip. No execution was performed during this read-only review, and shipping status was not established.
- **Native correction:** https://github.com/libuv/libuv/pull/5013 merged commit 44125af62afa285af6fe581dfa2daa3ca85a7983. Its src/win/fs-event.c diff detects handles under \$Extend\$Deleted\, reports UV_ENOENT, and returns instead of rearming ReadDirectoryChangesW. Adoption of this correction in VS Code's bundled runtime was not verified; an upstream merge alone does not establish delivery.
