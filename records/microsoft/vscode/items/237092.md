# Issue #237092 — Extension Bisect should not re-enable most extensions throughout the process

[https://github.com/microsoft/vscode/issues/237092](https://github.com/microsoft/vscode/issues/237092)

## Summary

The requested improvement remains missing on current main, and an open PR explicitly targets this issue. Keep it open pending review of that implementation rather than proposing completion or starting a competing agent fix.

## Change summary

Keep eliminated, potentially faulty extensions disabled during Extension Bisect so multiple independently problematic extensions do not prevent identifying one culprit.

## Best solution

Review the existing implementation candidate at https://github.com/microsoft/vscode/pull/316792, ensuring it can identify one independently faulty extension per run while preserving single-fault behavior and accurate disabled counts. Coordinate its outcome with the older overlapping report at https://github.com/microsoft/vscode/issues/111669.

## Evidence

- **Current capability and remaining gap:** In src/vs/workbench/services/extensionManagement/browser/extensionBisect.ts, ExtensionBisectService constructs its disabled map using `i >= mid && i < high`. After next(true) narrows high to the previous mid, extensions at or beyond the new high become enabled again on reload. The existing extension.bisect.start/next/stop commands do not provide a mode that keeps those eliminated extensions disabled.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/316792 is verified OPEN with mergedAt null and a closingIssuesReferences entry for https://github.com/microsoft/vscode/issues/237092. Its proposal keeps the eliminated upper range disabled, updates disabled counts and completion messaging, and includes a new extensionBisect.test.ts. The open-linked-PR rule requires keeping this issue open and agentReadiness none.
- **Older overlapping report:** https://github.com/microsoft/vscode/issues/111669 is verified OPEN, created 2020-12-01, and reports the same observable failure: two faulty extensions cause bisect to conclude the problem is in core. Its discussion explicitly considers finding one faulty extension in the presence of several and repeating bisect; this issue's author also describes retaining disabled extensions there. It is a verified consolidation lead, but this issue now has an explicitly linked open implementation PR, so the pending-PR keep-open rule applies.
- **Accepted community demand:** The issue has 22 community upvotes and the Backlog milestone. The supplied 2025-02-04 engineering-bot comment confirms that it reached the community threshold and was accepted into the backlog; inactivity is not a reason to decline it.
- **Concrete use case:** The supplied 2024-12-30 author comment describes approximately three extensions independently performing recursive workspace searches in a large home-folder workspace. Disabling those extensions removed the CPU spike, but bisect could not identify a single culprit.
