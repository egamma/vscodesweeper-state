# Issue #149478 — Some keyboard shortcuts ignored in Safari/vscode.dev

[https://github.com/microsoft/vscode/issues/149478](https://github.com/microsoft/vscode/issues/149478)

## Summary

Keep this canonical web-keybinding issue open: current main still advertises the affected shortcuts without browser-specific handling, and maintainers have not settled whether to rebind them or suppress unavailable shortcut hints. The team-authored issue has no referenced fixing commit or verified older duplicate that would permit a factual close.

## Change summary

Avoid advertising default VS Code shortcuts on vscode.dev when Safari or Edge consumes those shortcuts before the corresponding command can run.

## Best solution

Define a consistent web policy for browser-reserved shortcuts, then ensure Safari and Edge users are shown only shortcuts that can reach VS Code while preserving desktop behavior and user-defined keybindings.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/preferences/browser/preferences.contribution.ts`, `src/vs/workbench/contrib/themes/browser/themes.contribution.ts`, `src/vs/workbench/services/keybinding/browser/keybindingService.ts`, `src/vs/platform/actions/browser/menuEntryActionViewItem.ts`
- **Validation:** Exercise vscode.dev in current Safari and Edge: verify Settings and Color Theme do not advertise unusable shortcuts and that any displayed replacement invokes the command; verify the existing desktop shortcuts and user-defined web keybindings remain unchanged.
- **Behavior:**

  > In vscode.dev, command surfaces must not advertise a default keyboard shortcut that the active browser consumes instead of delivering to VS Code. Settings in Safari and Color Theme in Edge must either have a working web shortcut or appear without an unavailable shortcut hint. Desktop defaults and user-defined keybindings must remain unchanged. Acceptance requires checking the affected commands in current Safari and Edge as well as the corresponding desktop behavior.
- **Trace:**

  > The Settings action unconditionally registers Ctrl/Cmd+, in src/vs/workbench/contrib/preferences/browser/preferences.contribution.ts, while the Color Theme action unconditionally registers Ctrl/Cmd+K Ctrl/Cmd+T in src/vs/workbench/contrib/themes/browser/themes.contribution.ts. Menu shortcut text is derived from IKeybindingService.lookupKeybinding, including in src/vs/platform/actions/browser/menuEntryActionViewItem.ts, so the same registration is advertised even when a browser reserves it. src/vs/workbench/services/keybinding/browser/keybindingService.ts can prevent a browser default only after receiving the keydown event; the issue records cases where the browser retains control. Preserve desktop registrations and custom user mappings; the uncertainty begins at the web product policy for unavailable browser-reserved defaults. Related reports https://github.com/microsoft/vscode/issues/170149 and https://github.com/microsoft/vscode/issues/181565 point back to this issue as the canonical discussion.
- **Open decisions:**
  - For browser-reserved defaults on the web, should VS Code assign browser-specific alternate shortcuts, or retain the command without displaying an unavailable shortcut hint?
  - Should availability be modeled per supported browser and operating system, or should the web product use one conservative default set across browsers?
