# Issue #166696 — Explorer should show which folders are gitignored when multiple folders are collapsed into one item

[https://github.com/microsoft/vscode/issues/166696](https://github.com/microsoft/vscode/issues/166696)

## Summary

The gap remains on current main: a compact Explorer path is rendered using only the deepest folder's resource decoration, so every path segment receives the same ignored color. The accepted Backlog request should remain open for a design that supports segment-level decorations.

## Change summary

Show the gitignored state of each individual folder segment when the Explorer compacts a single-child folder chain into one row.

## Best solution

Let compressed Explorer labels associate each visible path segment with its own resource decoration, while preserving the current single icon and compact navigation behavior. A maintainer should first decide whether this applies to all file decorations or only color decorations such as Git ignored state.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/browser/labels.ts`, `src/vs/base/browser/ui/iconLabel/iconLabel.ts`, `src/vs/base/browser/ui/iconLabel/iconlabel.css`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`, `src/vs/base/test/browser/ui/iconLabel/iconLabel.test.ts`
- **Validation:** Add a browser unit test rendering a compressed folder chain whose resources have mixed ignored decorations and assert that only the corresponding `.label-name` segments receive the ignored color, while existing single-resource and compact-navigation tests continue to pass.
- **Behavior:**

  > A compact Explorer row must preserve the decoration state of every folder represented in its path. In a chain containing both tracked and gitignored folders, tracked segments retain the normal foreground and only ignored segments use the ignored-resource foreground. Disabling compact folders and ordinary single-resource labels remain unchanged, and compact-path keyboard and pointer navigation continue to address the correct segment.
- **Trace:**

  > FilesRenderer.renderCompressedElements in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts keeps all segment names but passes only the final ExplorerItem to renderStat. ResourceLabelWidget in src/vs/workbench/browser/labels.ts consequently subscribes to and renders one resource decoration, whose class is applied to the whole IconLabel. LabelWithHighlights in src/vs/base/browser/ui/iconLabel/iconLabel.ts already creates a distinct `.label-name` element for each array entry, but its options are shared across the array. GitIgnoreDecorationProvider in extensions/git/src/decorationProvider.ts can decorate each URI independently, so Git ignore calculation itself is outside the change boundary. Preserve icon selection, decoration behavior for non-compressed labels, and CompressedNavigationController semantics. The uncertainty begins at whether the shared label contract should support every per-resource decoration attribute or whether compressed paths should expose only per-segment foreground colors.
- **Open decisions:**
  - Should each compact-path segment expose the full decoration contract, including badges, strikethrough, and tooltip text, or only its resource-specific foreground color while badges and other row-level decoration remain attached to the deepest folder?

## Evidence

- **current render path:** src/vs/workbench/contrib/files/browser/views/explorerViewer.ts: FilesRenderer.renderCompressedElements selects the final ExplorerItem as `stat`, collects only the names of all compressed elements, and calls renderStat with that final item's resource.
- **single decoration source:** src/vs/workbench/browser/labels.ts: ResourceLabelWidget stores one resource, requests one decoration from IDecorationsService, and applies its color class to the outer icon label; it does not associate decorations with individual entries in a string-array name.
- **segment DOM:** src/vs/base/browser/ui/iconLabel/iconLabel.ts: LabelWithHighlights renders array labels as separate `.label-name` elements, but accepts one shared IIconLabelValueOptions object and has no per-segment decoration input.
- **Git ignored provider:** extensions/git/src/decorationProvider.ts: GitIgnoreDecorationProvider can resolve ignored state independently for each URI, so the missing behavior is in compact-label resource/decorations plumbing rather than Git ignore detection.
