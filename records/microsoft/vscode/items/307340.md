# Issue #307340 — [microsoft-authentication] Sovereign cloud (ChinaCloud) tokens not persisted in msal-no-broker mode — shared PCA cache between microsoft and microsoft-sovereign-cloud providers

[https://github.com/microsoft/vscode/issues/307340](https://github.com/microsoft/vscode/issues/307340)

## Summary

Keep open: current source supports the reported cross-provider account visibility and coupled sign-out. The older sovereign authentication issue covers the silent-token failure, but does not establish coverage of this additional provider-isolation defect.

## Change summary

ChinaCloud authentication without a broker fails to supply scoped sessions and exposes the same account through both authentication providers, with coupled sign-out.

## Best solution

Ensure global and sovereign providers expose and remove only their own cloud accounts while preserving working broker authentication. Investigate the silent-token failure alongside the older MSAL issue rather than assuming shared storage or an omitted constructor authority explains it.

## Plan brief

- **Likely files:** `extensions/microsoft-authentication/src/extension.ts`, `extensions/microsoft-authentication/src/node/authProvider.ts`, `extensions/microsoft-authentication/src/node/publicClientCache.ts`, `extensions/microsoft-authentication/src/node/cachedPublicClientApplication.ts`, `extensions/microsoft-authentication/src/common/cachePlugin.ts`
- **Validation:** With a ChinaCloud test account and msal-no-broker, complete interactive sign-in and immediately request the same ARM scopes through vscode.authentication.getSession('microsoft-sovereign-cloud', scopes). Verify a usable session is returned, Azure Resources loads subscriptions, and the account is not listed under the global provider. With separate global and sovereign accounts signed in, verify signing out one provider preserves the other provider's session; repeat after reload and check broker-mode behavior separately.
- **Behavior:**

  > In msal-no-broker mode, successful ChinaCloud interactive authentication should yield usable subsequent sessions for the same ARM scopes. A ChinaCloud-only account should not appear under the global Microsoft provider, and signing out a sovereign account should not remove an unrelated global session. Validate immediate token retrieval, account-menu visibility, sign-out isolation, and reload behavior without regressing broker authentication.
- **Trace:**

  > Both providers are initialized using the same ExtensionContext in extensions/microsoft-authentication/src/extension.ts. CachedPublicClientApplicationManager has cloud-qualified client-list storage, but CachedPublicClientApplication uses a client-ID-only token-cache key; its non-broker _update returns all cached accounts, and MsalAuthProvider.getSessions(undefined) does not filter by cloud. Non-broker removeAccount operates on that shared cache, explaining the account-menu and sign-out coupling from source. Silent requests already carry an environment-specific authority in getAllSessionsForPca, so an omitted request authority is not the established cause. The token failure is independently confirmed in https://github.com/microsoft/vscode/issues/285993, where a maintainer identifies an MSAL library bug. The uncertainty starts at whether cache sharing contributes to token failure or is an independent account-isolation problem; preserve broker behavior and existing global authentication while diagnosing that boundary.

## Evidence

- **Current-source provider isolation defect:** extensions/microsoft-authentication/src/extension.ts creates both providers with the same ExtensionContext. node/cachedPublicClientApplication.ts constructs SecretStorageCachePlugin with `pca:${clientId}`; node/publicClientCache.ts passes the same SecretStorage without cloud qualification. CachedPublicClientApplication._update loads all cached accounts without cloud filtering in non-broker mode, and MsalAuthProvider.getSessions(undefined) returns them without cloud filtering. removeAccount removes the account from that shared token cache. This supports duplicate account visibility and coupled sign-out independently of whether silent acquisition is fixed upstream.
- **Reporter diagnosis is only partially supported:** extensions/microsoft-authentication/src/node/authProvider.ts:getAllSessionsForPca explicitly constructs authority from this._env.activeDirectoryEndpointUrl and passes it to acquireTokenSilent. CachedPublicClientApplication.acquireTokenSilent forwards that request unchanged. Therefore, the report's claim that silent requests omit the sovereign authority is not supported by current source; token destruction or overwrite was not established through read-only inspection.
- **Older related issue verified:** https://github.com/microsoft/vscode/issues/285993 is OPEN and was created on 2025-12-14, before this report. Its discussion confirms the same ChinaCloud browser-login success followed by no_tokens_found and an empty Azure Resources view. However, its body and comments do not document the duplicate global/sovereign account entries or coupled sign-out, which remain a separate observable behavior here.
- **Maintainer-confirmed upstream token failure:** https://github.com/microsoft/vscode/issues/285993#issuecomment-3711805584 confirms reproduction with msal-no-broker. https://github.com/microsoft/vscode/issues/285993#issuecomment-3721094068 states that MSAL confirmed a library bug. This is strong evidence for the token-failure investigation, not proof that the additional provider-isolation behavior is caused by that same defect.
- **Related extension report:** https://github.com/microsoft/vscode-azureresourcegroups/issues/1425 reports browser sign-in succeeding while ChinaCloud resources remain unavailable. Its reporter links https://github.com/microsoft/vscode/issues/307340 as the suspected underlying cause; this does not establish that Azure Resources owns the shared-cache behavior.
- **Maintainer guidance and validation limits:** The supplied 2026-04-03 maintainer comment recommends broker mode but explicitly retains msal-no-broker for environments where brokering fails; it does not decline fixing that fallback. Inspection was read-only, no authentication flow was executed, and no concrete behavior-fixing commit was identified. The checkout remained clean.
