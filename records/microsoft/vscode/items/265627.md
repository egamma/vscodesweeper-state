# Issue #265627 — extensions.allowed setting should support an indirection

[https://github.com/microsoft/vscode/issues/265627](https://github.com/microsoft/vscode/issues/265627)

## Summary

A real gap remains on current main: `extensions.allowed` accepts only an inline object, while multiple enterprises need a centrally managed source that can change without redeploying group policy. The request is accepted in the Backlog and has maintainer interest, but source trust, refresh, and failure semantics need design before implementation.

## Change summary

Allow the enterprise-managed `extensions.allowed` policy to reference a local or remote JSON allowlist instead of embedding the full list in group policy.

## Best solution

Provide a secure, cross-platform policy reference for an externally maintained extension allowlist, with explicit source restrictions, refresh behavior, validation, and deterministic handling of unavailable or malformed data while preserving the existing inline-object format.

## Plan brief

- **Likely files:** `src/vs/platform/extensionManagement/common/extensionManagement.ts`, `src/vs/platform/extensionManagement/common/allowedExtensionsService.ts`, `src/vs/platform/extensionManagement/test/common/allowedExtensionsService.test.ts`, `src/vs/platform/policy/common/filePolicyService.ts`
- **Validation:** Run `scripts/test.sh --grep "AllowedExtensionsService"` with coverage for the retained inline-object format, each selected external source, source updates, malformed content, and unavailable-source behavior.
- **Behavior:**

  > Enterprise administrators can configure `extensions.allowed` through an approved external JSON source and update that source without redeploying the group policy value. VS Code detects updates according to the selected refresh contract and applies the same extension, publisher, version, and platform rules as an inline allowlist. Existing object-valued configurations remain compatible. Tests must cover updates and the maintainer-selected behavior for malformed or unavailable sources.
- **Trace:**

  > The setting is registered as object-only in src/vs/platform/extensionManagement/common/extensionManagement.ts under `AllowedExtensionsConfigKey`. `AllowedExtensionsService.getAllowedExtensionsValue` in src/vs/platform/extensionManagement/common/allowedExtensionsService.ts reads only the configuration value, rejects non-objects, and refreshes only when that configuration key changes. `FilePolicyService` already demonstrates watched local JSON policy loading, but it operates on the whole policy source and does not provide URL loading or per-setting indirection. Preserve the existing allowlist matching and enforcement semantics; the unresolved boundary is how an external source is trusted, refreshed, and handled on failure. The remote-server enforcement request at https://github.com/microsoft/vscode/issues/314414 is related but distinct.
- **Open decisions:**
  - Which source forms are supported: a fixed local-file scheme, HTTPS, or both, and what authentication or trust restrictions apply to remote sources?
  - What is the observable refresh contract for local and remote sources, including polling or watch frequency and whether a restart is ever required?
  - When the source is unavailable, malformed, or fails validation, should enforcement fail closed, retain the last known-good list, or follow another explicit policy?
  - Should the public policy contract make `AllowedExtensions` polymorphic between an object and a reference string, or introduce a separate reference policy while retaining the existing object policy?

## Evidence

- **current configuration contract:** src/vs/platform/extensionManagement/common/extensionManagement.ts:730-748 registers `extensions.allowed` as an object-valued `AllowedExtensions` policy; there is no string or URI form.
- **current runtime behavior:** src/vs/platform/extensionManagement/common/allowedExtensionsService.ts:55-59 reads the value synchronously and discards every non-object value, so a file path or URL cannot currently provide the allowlist.
- **existing capability does not cover the request:** src/vs/platform/policy/common/filePolicyService.ts watches and reloads a whole local policy file, and src/vs/code/electron-main/main.ts:225-231 uses that path on Linux; this does not provide per-setting indirection or a remotely hosted allowlist for Windows/macOS group policy.
- **documented enterprise demand:** https://github.com/microsoft/vscode/issues/265627#issuecomment-3529604115 identifies four enterprises needing faster, cross-platform allowlist updates, and https://github.com/microsoft/vscode/issues/265627#issuecomment-4014821380 records another customer request.
