# Issue #167294 — Remote loading state for Explorer view

[https://github.com/microsoft/vscode/issues/167294](https://github.com/microsoft/vscode/issues/167294)

## Summary

A real gap remains: current main still shows only generic Explorer progress while remote files load. This team-authored feature request is accepted in the Backlog and has no verified older canonical with the same observable request, so it should remain open.

## Change summary

Show meaningful remote connection and file-loading details in the otherwise-empty Explorer while a remote workspace is loading.

## Best solution

Give the Explorer a staged, remote-aware loading presentation that identifies the current connection or file-enumeration state and disappears as soon as the tree is ready. A maintainer should first define which stages are useful and which service owns their user-facing status.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/services/remote/common/remoteAgentService.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Add an Explorer view test with delayed remote tree resolution that verifies staged loading content is visible while pending, updates when the stage changes, and is removed when files render; retain coverage for ordinary local loading.
- **Behavior:**

  > While a remote workspace is connecting or its files are being enumerated, an otherwise-empty Explorer should show a meaningful loading state rather than only a minimal spinner. The presentation should distinguish the agreed user-relevant stages without exposing implementation jargon. It must disappear when the tree becomes available, show failures through the existing error experience, and leave local Explorer loading behavior unchanged unless deliberately generalized.
- **Trace:**

  > ExplorerView.setTreeInput in src/vs/workbench/contrib/files/browser/views/explorerView.ts awaits WorkbenchCompressibleAsyncDataTree.setInput and sends the promise to ProgressLocation.Explorer without reporting any message. ExplorerDataSource.getChildren in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts does the same around ExplorerItem.fetchChildren. ProgressService maps that location to generic pane-composite progress in src/vs/workbench/services/progress/browser/progressService.ts. Remote connection state is available through IRemoteAgentConnection events in src/vs/workbench/services/remote/common/remoteAgentService.ts, but the trace did not find an existing contract that combines connection stages with Explorer file enumeration. The boundary is the empty, pending remote Explorer state: do not replace normal tree rendering, alter local file enumeration semantics, or duplicate established remote error notifications.
- **Open decisions:**
  - Which user-visible stages should the Explorer distinguish: remote connection, remote environment initialization, workspace resolution, and file enumeration, or a smaller stable subset?
  - Should detailed status appear only before the first Explorer contents render, or also when a later remote refresh temporarily leaves the view empty?

## Evidence

- **current Explorer behavior:** On current main, ExplorerView.setTreeInput in src/vs/workbench/contrib/files/browser/views/explorerView.ts:835-906 wraps tree.setInput in ProgressLocation.Explorer but never reports a message or stage; the empty tree therefore receives only generic pane progress.
- **child loading behavior:** ExplorerDataSource.getChildren in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts:116-168 similarly wraps asynchronous fetchChildren work in generic Explorer progress without exposing remote connection or enumeration details.
