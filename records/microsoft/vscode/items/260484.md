# Issue #260484 — JAWS/NVDA is not announcing the real time content. It is reading some extra content along with the generated response:A11y_Visual Studio Code_Github_Copilot_Screen reader

[https://github.com/microsoft/vscode/issues/260484](https://github.com/microsoft/vscode/issues/260484)

## Summary

The current source still announces the response only after generation completes and builds that announcement from a representation that can include tool activity and other non-response content. This team-authored accessibility bug should remain open; no explicit fixing commit or same-symptom canonical issue was found.

## Change summary

Make Copilot Chat announce generated response content promptly to JAWS and NVDA without mixing in unrelated response metadata.

## Best solution

Define and implement a screen-reader streaming policy for chat responses that announces newly generated user-facing content in coherent batches while excluding tool, progress, command, and system metadata unless separately requested by accessibility verbosity settings.

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts`, `src/vs/workbench/contrib/chat/browser/accessibility/chatAccessibilityService.ts`, `src/vs/workbench/contrib/chat/common/model/chatModel.ts`, `src/vs/workbench/contrib/chat/test/browser/accessibility/chatAccessibilityService.test.ts`
- **Validation:** Add targeted ChatAccessibilityService tests that simulate incremental response updates and assert each generated text segment is announced once while tool/progress metadata is excluded; then manually verify a long response with current NVDA and JAWS on Windows.
- **Behavior:**

  > While Copilot generates a long response, JAWS and NVDA should receive the newly generated user-facing response in coherent, timely announcements rather than waiting for completion. Tool activity, progress messages, commands, system notifications, and edit summaries must not be mixed into the generated-text announcement unless an explicitly chosen accessibility policy calls for them. Each response segment should be spoken once, and the final completion path must not repeat the full response.
- **Trace:**

  > ChatWidget in src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts calls ChatAccessibilityService.acceptResponse only from `responseCompletePromise`. ChatAccessibilityService in src/vs/workbench/contrib/chat/browser/accessibility/chatAccessibilityService.ts converts `response.response.toString()` to plain text and sends it through `status()`. AbstractResponse.partsToRepr in src/vs/workbench/contrib/chat/common/model/chatModel.ts includes several non-markdown response-part categories, explaining the reported extra content. The boundary is chat response accessibility announcements: preserve visual rendering, response serialization/copy behavior, tool-confirmation alerts, and accessibility signals. https://github.com/microsoft/vscode/issues/247522 is related only at the screen-reader level and does not own this chat-streaming symptom.
- **Open decisions:**
  - Should streaming announcements be batched by sentence, paragraph, or a time-based cadence so they remain timely without repeatedly interrupting screen-reader speech?
  - Which non-markdown response parts, if any, should be announced separately when verbose chat progress updates are enabled?
