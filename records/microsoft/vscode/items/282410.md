# Issue #282410 — Request for a low-resource default configuration for VS Code Remote-SSH in shared environments

[https://github.com/microsoft/vscode/issues/282410](https://github.com/microsoft/vscode/issues/282410)

## Summary

Keep this accepted feature request open: existing profiles and individual resource settings provide partial mitigations, but do not establish the requested operator-supported conservative default for shared remote hosts. It has 22 upvotes, and the linked CPU-limiting request is closed and narrower, not a duplicate canonical.

## Change summary

Provide a supported low-resource configuration for shared Remote-SSH hosts that reduces background activity without relying on each user to configure individual mitigations.

## Best solution

Define a supported shared-host configuration spanning remote server behavior and relevant extension settings, coordinating with the Remote-SSH owners in microsoft/vscode-remote-release. Specify whether it is an optional preset or an operator-applied default, and distinguish reduced background activity from enforceable resource limits.

## Plan brief

- **Likely files:** `src/vs/workbench/services/userDataProfile/browser/userDataProfileManagement.ts`, `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `src/vs/server/node/serverEnvironmentService.ts`, `extensions/typescript-language-features/package.json`, `extensions/typescript-language-features/src/configuration/configuration.ts`
- **Validation:** The plan should define a repeatable Remote-SSH workload on an isolated Linux host with a fixed workspace and extension set, comparing startup and idle CPU, aggregate process memory, and background activity with and without the configuration. Agree on measurable acceptance thresholds and verify ordinary editing, explicit search, language assistance, and reconnection under the chosen feature tradeoffs; no resource ceiling should be claimed without testing its enforcement.
- **Behavior:**

  > Operators of shared Remote-SSH login nodes need a supported way to reduce background resource consumption without depending on every user to discover and apply separate settings. The configuration should state which background activities are reduced and which editing capabilities are affected. Acceptance requires a repeatable comparison against the ordinary configuration and an explicit distinction between resource-saving defaults and guaranteed resource limits. Ordinary remote sessions outside the selected scope should retain their existing behavior.
- **Trace:**

  > files.watcherExclude in src/vs/workbench/contrib/files/browser/files.contribution.ts already supplies targeted exclusions, but the reporter explicitly says watcher exclusions and disabling extensions are insufficient. UserDataProfileManagementService in src/vs/workbench/services/userDataProfile/browser/userDataProfileManagement.ts manages profiles and reloads remote windows on relevant profile changes; its built-in template list comes from an external product URL whose contents were not inspected. src/vs/server/node/serverEnvironmentService.ts defines server startup options, while the TypeScript extension exposes language-specific memory and acquisition controls. These are separate configuration boundaries, and the investigation did not identify a coordinated operator-facing mode or establish the cause of the reported hundred-gigabyte incident. https://github.com/microsoft/vscode/issues/233842 concerns extension-host startup CPU caps and is closed, so it does not absorb this request. Coordinate Remote-SSH-specific connection or deployment work with microsoft/vscode-remote-release; do not assume the SSH extension alone controls core watchers or arbitrary language servers.
- **Open decisions:**
  - Should the supported configuration be a user-selected preset, an operator-applied remote-host default, or an enforceable administrator control, and may users override it?
  - Which background capabilities may be disabled or deferred, and which editing and language-service behaviors must remain available?
  - Does the supported contract promise reduced typical resource consumption only, or actual CPU and memory ceilings, and does it cover arbitrary installed extensions?
