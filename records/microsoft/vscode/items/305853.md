# Issue #305853 — Expose `chatSessionResource` to `LanguageModelChatProvider.provideLanguageModelChatResponse()`

[https://github.com/microsoft/vscode/issues/305853](https://github.com/microsoft/vscode/issues/305853)

## Summary

Keep open: providers still lack a documented request-owning chatSessionResource contract. Current Copilot plumbing forwards an internal conversation ID, but that does not satisfy the requested public API; the related session-header and turn-ID requests are newer and do not replace this report.

## Change summary

Expose optional, request-specific chat session identity to language model providers without associating standalone requests with a chat.

## Best solution

Define a supported provider API for opaque request-owning session identity, including its absence outside chat contexts, and carry that identity through chat-originated model calls. Preserve standalone language model requests and treat turn identity as separate work.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.chatProvider.d.ts`, `src/vs/workbench/api/common/extHostLanguageModels.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadLanguageModels.ts`, `src/vs/workbench/contrib/chat/common/languageModels.ts`, `extensions/copilot/src/platform/endpoint/vscode-node/extChatEndpoint.ts`
- **Validation:** End with provider/API tests proving that successive turns in one chat carry the same owning identity, two concurrent chats carry distinct identities despite focus changes, and standalone sendRequest calls have no inferred chat identity. Include an explicit manual check with a recording provider across two chat panels and a direct language model API call.
- **Behavior:**

  > Language model providers need a supported way to correlate each chat-originated request with its owning conversation, without inspecting prompts or the currently focused panel. The identity must remain consistent across turns and distinguish concurrent chats even when focus changes. Requests outside a chat must remain valid without an inferred session identity. Acceptance should cover repeated turns, background/concurrent requests, and standalone language model API calls; per-turn identity is separate scope.
- **Trace:**

  > ProvideLanguageModelChatResponseOptions in src/vscode-dts/vscode.d.ts and vscode.proposed.chatProvider.d.ts has no chatSessionResource field. MainThreadLanguageModels forwards request options, and ExtHostLanguageModels.$startChatRequest spreads them into provider options; the generic sendRequest path does not establish chat ownership. Copilot's ExtChatEndpoint.makeChatRequest already forwards an internal modelOptions._conversationId, which is useful precedent but is not the requested supported session URI contract. The trace has not established an authoritative session-resource source across every chat-originated model call, so the plan must resolve that boundary rather than assume the three IPC files alone suffice. Preserve direct sendRequest behavior and do not infer ownership from active-chat focus, prompt markers, or message hashes. https://github.com/microsoft/vscode/issues/332597 tracks distinct turn identity, while https://github.com/microsoft/vscode/issues/316794 concerns downstream header use cases.
- **Open decisions:**
  - Should the provider contract expose the opaque chat-session URI as proposed, or a separate opaque conversation identifier, and what identity continuity should it guarantee when a chat is restored or forked?
  - Should chat ownership be supplied only by VS Code-owned chat flows, or should chat participants have a supported way to associate their own sendRequest calls with the current ChatRequest?
