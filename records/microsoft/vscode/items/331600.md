# Issue #331600 — Notebook Webview scroll distance is improperly reduced

[https://github.com/microsoft/vscode/issues/331600](https://github.com/microsoft/vscode/issues/331600)

## Summary

The reported wheel-distance mismatch remains directly traceable in current main: notebook webviews divide Chrome wheel deltas by devicePixelRatio even though the host limits that workaround to Chrome 122 and earlier. Keep this open; the report provides sufficient reproduction details and identifies a core notebook defect.

## Change summary

Make outer-notebook wheel scrolling consistent over code cells, rendered Markdown, and non-scrollable inline outputs on high-DPI displays.

## Best solution

Notebook webview wheel forwarding should preserve the same effective scroll distance as native notebook-list wheel handling, while retaining compatibility for older Chrome runtimes and existing nested-output scrolling behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/notebook/browser/view/renderers/webviewPreloads.ts`, `src/vs/workbench/contrib/notebook/browser/view/renderers/backLayerWebView.ts`, `src/vs/workbench/contrib/notebook/test/browser/notebookCellList.test.ts`
- **Validation:** Establish a regression check comparing effective host wheel deltas for identical native and webview-forwarded input at DPR 1 and 2 on Chrome >=123, with older-Chrome compatibility checked separately. Manually repeat the supplied notebook steps on a high-DPI display and measure outer scroll-position changes over code, rendered Markdown, and non-scrollable text output; also verify nested scrollable outputs retain their existing behavior.
- **Behavior:**

  > Identical physical mouse-wheel input should move the outer notebook by the same distance over a code cell, rendered Markdown, or a non-scrollable inline output. On modern Chrome at DPR greater than 1, Markdown and output scrolling must not receive an extra inverse-DPR multiplier. Acceptance should compare actual scroll-position changes from the same starting position, away from scroll boundaries, and cover DPR 1 and 2. Nested scrollable outputs and older-runtime compatibility must retain their existing behavior.
- **Trace:**

  > In src/vs/workbench/contrib/notebook/browser/view/renderers/webviewPreloads.ts, handleWheel forwards deprecated wheelDelta fields after unconditionally dividing them by DPR whenever isChrome is true. BackLayerWebView forwards that payload unchanged to the notebook list, which ultimately constructs StandardWheelEvent in src/vs/base/browser/ui/scrollbar/scrollableElement.ts. StandardWheelEvent in src/vs/base/browser/mouseEvent.ts limits its own historical DPR workaround to Chrome <=122, conclusively exposing the modern-Chrome scale mismatch. The boundary is notebook outer-scroll forwarding: preserve eventTargetShouldHandleScroll, defaultPrevented handling, native code-cell scrolling, and existing sensitivity settings. The report is https://github.com/microsoft/vscode/issues/331600. No existing preload-wheel regression harness was identified in the notebook browser tests; the planning session should establish a runnable validation path before implementation.

## Evidence

- **Current-source mismatch:** src/vs/workbench/contrib/notebook/browser/view/renderers/webviewPreloads.ts:100-101 detects Chrome without a version gate. Its handleWheel function at lines 677-695 divides wheelDelta, wheelDeltaX, and wheelDeltaY by window.devicePixelRatio for every Chrome runtime; the listener is registered at line 1123.
- **Host normalization:** src/vs/base/browser/mouseEvent.ts, StandardWheelEvent, applies DPR normalization only for Chrome major versions <=122. For Chrome 148 and DPR 2, an incoming wheelDeltaY of 120 becomes 60 through notebook forwarding and then 0.5 in StandardWheelEvent, versus 1 through native host handling.
- **Forwarded event reaches the notebook list:** src/vs/workbench/contrib/notebook/browser/view/renderers/backLayerWebView.ts:732-738 passes did-scroll-wheel payloads to notebookEditor.triggerScroll without restoring their scale. notebookEditorWidget.ts:1451 delegates to NotebookCellList.triggerScrollFromMouseWheelEvent; notebookCellList.ts:1202-1204 forwards to the list view, and src/vs/base/browser/ui/scrollbar/scrollableElement.ts:402-403 constructs StandardWheelEvent.
- **Reported trigger and boundary:** https://github.com/microsoft/vscode/issues/331600 supplies a minimal notebook, physical-wheel comparison steps, Ubuntu/X11 display scaling, window zoom, and ordinary inline-output and Markdown cases. webviewPreloads.ts:eventTargetShouldHandleScroll distinguishes nested scrolling from outer-notebook forwarding, matching the report's non-scrollable-output boundary.

Searches for open PRs mentioning 331600 or notebook wheel found no implementation candidate. https://github.com/microsoft/vscode/issues/146403 is closed and concerns historically faster editor scrolling, not this pointer-target-dependent notebook mismatch.
