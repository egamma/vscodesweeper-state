# Issue #286259 — Worktrees should highlight the currently active worktree

[https://github.com/microsoft/vscode/issues/286259](https://github.com/microsoft/vscode/issues/286259)

## Summary

Keep open: the Worktrees list still does not distinguish the current worktree, and its opening actions remain unconditional. This team-authored request has no verified fixing commit or older canonical duplicate.

## Change summary

Identify the current worktree in the Source Control Repositories list and make its opening actions reflect that state.

## Best solution

Provide a clear, accessible current-worktree indicator in the existing SCM artifact list, with opening actions consistent with the chosen meaning of current worktree. Settle that meaning for multi-root workspaces and whether opening the same worktree in another window remains available.

## Plan brief

- **Likely files:** `extensions/git/src/artifactProvider.ts`, `extensions/git/package.json`, `src/vs/workbench/contrib/scm/browser/scmRepositoriesViewPane.ts`, `src/vs/workbench/contrib/scm/browser/menus.ts`
- **Validation:** Create two linked worktrees, open one in VS Code, enable scm.repositories.explorer and single repository selection, and expand Worktrees. Verify the agreed current-state indicator and opening-action behavior; switch worktrees and confirm the indicator follows. Repeat with a multi-root workspace, keyboard navigation, a screen reader, and high-contrast themes.
- **Behavior:**

  > Users looking at the Worktrees list can identify which worktree corresponds to their current working context without inferring it from branch names or paths. That state remains distinguishable from ordinary tree focus and selection, and is available without relying solely on color. Opening actions reflect the agreed current-state semantics. Acceptance covers switching between linked worktrees and the chosen multi-root behavior.
- **Trace:**

  > GitArtifactProvider.provideArtifacts in extensions/git/src/artifactProvider.ts emits worktree entries without a current-state distinction; Repository.getWorktreeDetails only enriches their commit metadata. ArtifactRenderer in src/vs/workbench/contrib/scm/browser/scmRepositoriesViewPane.ts renders that metadata directly. Opening commands in extensions/git/package.json are enabled for every worktree artifact, while RepositoryMenus.getArtifactMenu in src/vs/workbench/contrib/scm/browser/menus.ts has no worktree-current context. The source establishes the missing capability, but does not settle whether current means workspace membership or the selected SCM repository. Keep worktree discovery, branch metadata, and unrelated artifact groups unchanged. https://github.com/microsoft/vscode/issues/288242 supplies related community feedback and screenshot concepts, but is younger than this report.
- **Open decisions:**
  - In a multi-root workspace, should the indicator identify every worktree open in the window or only the worktree belonging to the selected SCM repository?
  - For a current worktree, should Open be hidden or disabled, and should Open in New Window remain available for intentionally opening a second window?
