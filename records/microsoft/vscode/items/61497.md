# Issue #61497 — Task Manager: provide the ability to reuse custom problem matchers

[https://github.com/microsoft/vscode/issues/61497](https://github.com/microsoft/vscode/issues/61497)

## Summary

Keep open as the established tracking issue for supported, reusable custom problem matchers in tasks.json. Current source contains a local declaration mechanism, but it is absent from the configuration schema; 58 upvotes and explicit maintainer acceptance support finishing the public configuration surface.

## Change summary

Allow users to define a custom problem matcher once in tasks.json and reference it by name from multiple tasks.

## Best solution

Provide a supported, discoverable tasks.json declaration and reference contract, building on the existing local matcher parser where appropriate. Settle its public syntax and name-resolution semantics without requiring users to publish an extension.

- **Likely files:** `src/vs/workbench/contrib/tasks/common/taskConfiguration.ts`, `src/vs/workbench/contrib/tasks/common/jsonSchemaCommon.ts`, `src/vs/workbench/contrib/tasks/common/jsonSchema_v2.ts`, `src/vs/workbench/contrib/tasks/common/problemMatcher.ts`, `src/vs/workbench/contrib/tasks/test/common/taskConfiguration.test.ts`
- **Validation:** Add task-configuration tests showing two tasks resolve one locally declared matcher through $name, distinct declarations remain independently selectable, and existing extension references and global defaults remain unchanged. Verify the agreed syntax and references produce no schema diagnostics in tasks.json; run the targeted taskConfiguration.test.ts suite with scripts/test.sh.
- **Behavior:**

  > Users can define a custom output matcher once in tasks.json and select it by name from multiple tasks without installing or publishing an extension. The supported syntax is discoverable and accepted by configuration validation. Tasks can select different named matchers, and existing inline definitions, extension-contributed references, and global defaults continue working. Acceptance includes two tasks sharing one declaration and deterministic handling of name collisions.
- **Trace:**

  > In src/vs/workbench/contrib/tasks/common/taskConfiguration.ts, ProblemMatcherConverter.namedFrom reads fileConfig.declares, and ConfigurationParser.createTaskRunnerConfiguration installs the resulting local map before parsing tasks. resolveProblemMatcher already resolves $name from that map after checking ProblemMatcherRegistry; ProblemMatcherParser in common/problemMatcher.ts preserves declared names. The shared and v2 schemas do not expose declares, and jsonSchema_v2.ts:updateProblemMatchers advertises only registry names. Global matcher inheritance is a separate defaulting mechanism and must retain its existing semantics. Source inspection establishes partial runtime support, but the supported declaration syntax and collision contract remain unsettled. This issue is the maintainer-designated tracker, as recorded in https://github.com/microsoft/vscode/issues/81901 and https://github.com/microsoft/vscode/issues/24865; extension Task API expansion is outside this request.
- **Open decisions:**
  - Should the supported tasks.json contract expose the existing declares array, or use a dedicated named-matcher property?
  - When a local declaration and an extension-contributed matcher share a name, should extension-first resolution remain the public contract, or should local declarations take precedence?
