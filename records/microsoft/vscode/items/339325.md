# Issue #339325 — ChatApprovedAccountOrganizations (chat.approvedAccountOrganizations) policy never recognized via macOS managed preferences, confirmed on 1.137.0-1.140.0

[https://github.com/microsoft/vscode/issues/339325](https://github.com/microsoft/vscode/issues/339325)

## Summary

Traced the exact failing path in source: array-typed policies (only `chat.approvedAccountOrganizations`/ChatApprovedAccountOrganizations today) are silently degraded to the 'string' policy type because the native `@vscode/policy-watcher` dependency only understands string/number/boolean, and its macOS `StringPolicy::read()` rejects any CFPreferences value that isn't literally a CFString — exactly what happens when an admin delivers a native plist `<array>` via a .mobileconfig instead of a JSON-stringified string. This matches the reporter's isolation (control string/boolean fields work, the array field silently reads as unset) and isn't limited to one MDM vendor.

## Change summary

The ChatApprovedAccountOrganizations managed-preferences policy is never recognized on macOS even when correctly delivered via MDM as a native plist array.

## Best solution

Either extend the native policy-watcher dependency (microsoft/vscode-policy-watcher) with real array/CFArray support on macOS (and Linux/Windows parity), or — as a smaller near-term fix — clearly document in the policy description and Policy Diagnostics output that array-type policies must be delivered as a JSON-stringified string value, not a native plist array, so admins aren't silently broken.

- **Trace:**

  > configurations.ts#toPolicyDefinitionType (src/vs/platform/configuration/common/configurations.ts, ~line 147) degrades any non-number/boolean config type — including 'array' — to the runtime policy type 'string', because @vscode/policy-watcher's native CreateWatcher (main.cc) throws for any type other than string/number/boolean. On macOS, StringPolicy::read() (vendored dependency, microsoft/vscode-policy-watcher src/macos/StringPolicy.cc) does `CFPreferencesCopyAppValue` then rejects the value via `CFGetTypeID(pref) != CFStringGetTypeID()` — exactly triggered when the delivered preference is a CFArray rather than a CFString. accountPolicyService.ts#parseApprovedOrganizations (~line 375) confirms the intended contract is a JSON-stringified array string. The underlying array-type gap lives in the @vscode/policy-watcher native addon (separate repo), which has BooleanPolicy/NumberPolicy/StringPolicy classes but no ArrayPolicy on any platform. Do not change the JSON-string parsing contract in accountPolicyService.ts without also fixing/documenting the delivery side, or existing Windows/Linux JSON-string deployments would break.
- **Open decisions:**
  - Should macOS (and Linux/Windows for parity) gain real native array/CFArray support in @vscode/policy-watcher, so admins can deliver array policies using the platform-natural list representation?
  - If staying with the JSON-stringified-string contract instead, where should that requirement be surfaced to admins (policy description text, ADMX/profile authoring docs, Policy Diagnostics output) so this doesn't fail silently again for the next array-type policy?
