# Issue #339325 — ChatApprovedAccountOrganizations (chat.approvedAccountOrganizations) policy never recognized via macOS managed preferences, confirmed on 1.137.0-1.140.0

[https://github.com/microsoft/vscode/issues/339325](https://github.com/microsoft/vscode/issues/339325)

## Summary

Thanks for the detailed report. The report is complete and the control policies show the managed-preferences path works. The likely cause is that array policies are declared to the native watcher as strings (JSON-encoded), so a real plist array is probably not read. I could not confirm this without the native watcher source or a macOS run.

## Change summary

A ChatApprovedAccountOrganizations value delivered as an array in a macOS managed-preferences plist is not recognized, so the Account Policy Gate stays inactive.

## Best solution

Decide the supported macOS delivery format for array policies. Either have the native layer accept plist arrays and serialize them to JSON, or document and publish a JSON-string form. Then confirm and fix it in the policy-watcher path. Coordinate with the related Windows REG_SZ/REG_MULTI_SZ mismatch issue.

## Evidence

- **policy definition:** src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts registers chat.approvedAccountOrganizations as type 'array' with policy ChatApprovedAccountOrganizations.
- **native policy types:** src/vs/platform/policy/common/policy.ts defines PolicyDefinition.type as only 'string' | 'number' | 'boolean', and PolicyValue as string | number | boolean. src/vs/platform/policy/node/nativePolicyService.ts passes definitions straight to @vscode/policy-watcher and stores whatever value it returns. A plist array therefore probably yields no value.
- **consumer:** src/vs/workbench/services/policies/common/accountPolicyService.ts parseApprovedOrganizations only accepts a JSON string or an array; an undefined value makes the gate Inactive, which matches the report.
- **related:** https://github.com/microsoft/vscode/issues/341503 reports the same array/string mismatch on Windows (ADMX multiText vs REG_SZ JSON). It is newer than this issue, so not a duplicate target.
