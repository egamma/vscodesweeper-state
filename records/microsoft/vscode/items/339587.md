# Issue #339587 — Incorrect handling of completions in the Debug REPL

[https://github.com/microsoft/vscode/issues/339587](https://github.com/microsoft/vscode/issues/339587)

## Summary

Both replacement defects remain evident in current main: adapter completions ignore their explicit start when constructing edits, and multiline history suggestions replace only the current line. Keep this report open; the protocol discussions do not subsume these VS Code defects.

## Change summary

Correct Debug REPL completion replacement ranges, prevent multiline history duplication, and resolve the documented DAP compatibility discrepancies.

## Best solution

Make Debug REPL suggestions replace their intended text without duplicating preceding lines. Settle the adapter-compatibility contract for omitted starts and unsupported multiline ranges before changing externally observable completion semantics.

- **Trace:**

  > Repl.onDidFocusSession in src/vs/workbench/contrib/debug/browser/repl.ts registers the completion provider. Its computeRange helper always ends at the cursor and begins on the same line; adapter items use only item.length for that range, and history items insert their entire stored text through the same helper. Position.delta clamps negative columns rather than traversing lines, conclusively explaining the duplicated preceding line. DebugSession.completions forwards editor coordinates and the complete input text, while the session advertises one-based columns; no intermediate response conversion accounts for item.start. The editor's CompletionItem contract requires single-line ranges containing the request position, so arbitrary multiline replacement cannot be assumed to work. Preserve snippet-selection behavior and unrelated REPL output/history navigation. https://github.com/microsoft/debug-adapter-protocol/issues/138 records unresolved compatibility concerns; https://github.com/microsoft/debug-adapter-protocol/issues/285 documents the indexing and UTF-16 clarification. The remaining uncertainty is the intended compatibility policy, not whether the two replacement defects exist.
- **Open decisions:**
  - Should omitted-start completions retain VS Code's existing replace-before-cursor behavior for adapter compatibility, or adopt the documented DAP cursor-start behavior?
  - For multiline history suggestions unsupported by the editor's primary completion range, should VS Code complete the whole command without duplication or withhold the suggestion?
  - Should completion indexing discrepancies be corrected to the advertised one-based DAP contract now, or retained pending a coordinated compatibility clarification?
