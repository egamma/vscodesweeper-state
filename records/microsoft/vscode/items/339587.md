# Issue #339587 — Incorrect handling of completions in the Debug REPL

[https://github.com/microsoft/vscode/issues/339587](https://github.com/microsoft/vscode/issues/339587)

## Summary

Confirmed in source: the Debug REPL completion range computation ignores DAP `item.start`, and multiline history suggestions duplicate preceding lines because the replacement range is clamped to the current line while the inserted text spans multiple lines. The issue also raises a design clarification (0- vs 1-based indexing, default start-position semantics) that needs maintainer input before any spec-level fix.

## Change summary

Debug console (REPL) completion replacement ranges deviate from the DAP spec: `item.start` is ignored for the edit range, and multiline history-suggestion ranges duplicate preceding lines.

## Best solution

Fix the two concrete bugs in src/vs/workbench/contrib/debug/browser/repl.ts: honor `item.start` when computing the completion range, and either restrict history suggestions to single-line entries or correctly compute a multiline replacement range. The indexing/semantics clarification (point 3) is a separate product/spec decision for a maintainer, ideally tracked alongside or split into its own discussion with the DAP maintainers.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/repl.ts`
- **Validation:** A debug REPL completion test asserting that a completion item with `item.start` before the cursor produces an edit range starting at `item.start` (not just filtering), and a history-suggestion test asserting a multiline history entry does not duplicate preceding lines when accepted.
- **Behavior:**

  > Debug console completions whose DAP response specifies `item.start` should replace text starting at that position (not just the `length` characters immediately before the cursor), so adapters can overwrite text ahead of the cursor as DAP allows. Separately, accepting a multiline debug-console history suggestion should insert the historical command once, without duplicating any preceding line content. Acceptance: completion and history-suggestion tests covering both scenarios pass.
- **Trace:**

  > In src/vs/workbench/contrib/debug/browser/repl.ts, `computeRange(length)` builds the edit range as `position.delta(0, -length)` to `position`, ignoring `item.start` entirely for the edit (only used in `filterText`). The same helper is reused for history suggestions with `h.length` (the full, possibly multiline, history string); `Position.delta` (src/vs/editor/common/core/position.ts:58) clamps the column to a minimum of 1 on the same line instead of moving up lines, so the computed range covers only the current line while the inserted text spans multiple lines, producing duplicated content. Do not change the internal single-line completion range representation (src/vs/editor/common/languages.ts around line 615) — multiline ranges must be filtered out or explicitly handled, not silently mishandled. The indexing/semantics clarification in the issue's point 3 (0- vs 1-based `start`, default-to-cursor when `start` is omitted) is out of scope for a direct code fix and needs a maintainer/DAP-level decision.
- **Open decisions:**
  - Should VS Code's debug-console completion handling be changed to match the DAP's 1-based `columnsStartAt1` semantics for `item.start`, or should the DAP spec/docs be clarified instead?
  - When `item.start` is omitted, should VS Code default to the cursor position (per the DAP) instead of replacing `length` characters before the cursor, and would that break existing adapters that rely on the current behavior?

## Evidence

- **bug 1 traced:** src/vs/workbench/contrib/debug/browser/repl.ts line ~300: `range: computeRange(item.length || 0)` always computes the range as `length` characters before the cursor via `position.delta(0, -length)`, never using `item.start` for the edit itself — only for `filterText`.
- **bug 2 traced:** History suggestions use the same `computeRange(h.length)` helper (repl.ts ~line 319); `Position.delta` (src/vs/editor/common/core/position.ts:58) clamps the column to a minimum of 1 on the SAME line rather than moving to a prior line, so a multiline history entry's range collapses to the current line while the full multiline text is inserted — reproducing the reported duplication.
