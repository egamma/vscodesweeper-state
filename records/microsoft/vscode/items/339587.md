# Issue #339587 — Incorrect handling of completions in the Debug REPL

[https://github.com/microsoft/vscode/issues/339587](https://github.com/microsoft/vscode/issues/339587)

## Summary

Well-diagnosed, source-confirmed bug in the Debug REPL's completion/history replacement-range logic, with no fix landed on main yet; reporter has a draft fix and offers a PR, so this is a good agent/maintainer candidate but needs a product decision on the multi-line and DAP-deviation questions first.

## Change summary

Debug REPL completions ignore DAP `item.start` for the edit range, and multiline history suggestions duplicate preceding lines; several other DAP range-handling deviations are flagged for clarification.

## Best solution

Fix the two confirmed bugs in repl.ts (use item.start for the edit range; bound history-suggestion insertion to avoid duplicating lines), and separately decide/document the DAP range-semantics deviations (0- vs 1-based start, default-to-cursor, multi-line handling) — likely via a PR from the reporter plus maintainer sign-off on the DAP-deviation points.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/repl.ts`
- **Validation:** A debug REPL completion test asserting the edit range starts at item.start (not just `length` chars before cursor) when item.start is provided, and a history-suggestion test asserting a multi-line history entry inserted via completion does not duplicate preceding lines.
- **Behavior:**

  > Debug REPL completion items from a DAP adapter that specify `item.start` should have their edit range begin at `item.start` (not always `length` characters immediately before the cursor), matching DAP semantics. Accepting a multiline history suggestion in the REPL should insert the full command without duplicating any already-present line. Acceptance: completions with explicit `start` correctly overwrite text behind the cursor per the DAP; accepting a multi-line history suggestion produces exactly the suggested text with no repeated lines.
- **Trace:**

  > In src/vs/workbench/contrib/debug/browser/repl.ts, `provideCompletionItems`'s `computeRange(length)` helper always computes `Range.fromPositions(position.delta(0, -length), position)`, ignoring `item.start` entirely — it's used only for `filterText`. The same helper is reused for history suggestions (`computeRange(h.length)`), which stays within the current line while `insertText: h` can be a full multi-line history entry, producing duplicated lines. Boundary: this fix should stay inside the completion-provider construction in repl.ts and should not touch the internal single-line CompletionItem range representation (src/vs/editor/common/languages.ts) — the issue separately flags that multi-line ranges aren't supported there, which is a larger, undecided question. Related: reporter's draft fix at https://github.com/ManuelHentschel/vscode/blob/621f9ec3b8f0c6342dedf7091647476e20e31ee8/src/vs/workbench/contrib/debug/browser/repl.ts#L301-L305; DAP discussions at https://github.com/microsoft/debug-adapter-protocol/issues/138 and https://github.com/microsoft/debug-adapter-protocol/issues/285.
- **Open decisions:**
  - For multi-line completion/history ranges, should VS Code filter them out early (ignore the suggestion) or implement correct multi-line range handling, given the internal CompletionItem range model is documented as single-line-only?
  - Should VS Code's 0-based interpretation of DAP `item.start` be changed to 1-based (matching `columnsStartAt1: true`), or should this be treated purely as a documentation/DAP-spec clarification rather than a behavior change that could break existing debug adapters?
  - When `item.start` is omitted, should VS Code change its current behavior (replace `length` chars before cursor) to match the DAP's stated default (insert at cursor position), risking a behavior change for existing adapters that rely on the current interpretation?

## Evidence

- **bug 1 confirmed in source:** src/vs/workbench/contrib/debug/browser/repl.ts: `range: computeRange(item.length || 0)` ignores `item.start` entirely for the edit range — `computeRange` only uses `position.delta(0, -length)`, confirming the reporter's claim that item.start is used for filterText but not for the actual edit range.
- **bug 2 confirmed in source:** Same file: history suggestions use `range: computeRange(h.length)` where `h` can be a multi-line history entry; `computeRange` shifts only within the current line (`position.delta(0, -length)`), while `insertText: h` inserts the full multi-line text — matching the reported line-duplication repro.
- **no recent fix:** `git log --oneline -- src/vs/workbench/contrib/debug/browser/repl.ts` shows the latest commit (3d5764c1) is unrelated to completions/history; no fix for either bug is present on main.
- **reporter has a draft fix:** Reporter links their own branch (ManuelHentschel/vscode@621f9ec, repl.ts#L301-L305) implementing the item.start-based range and offers to submit a PR.
