# Issue #278428 — On smaller screens vertical space is impacted when you have a lot of context

[https://github.com/microsoft/vscode/issues/278428](https://github.com/microsoft/vscode/issues/278428)

## Summary

The vertical-space problem remains on current main: the chat input renders every attached-context pill, and the container wraps them into unlimited rows at narrow widths. This team-authored, accepted bug should remain open while the compact overflow behavior is designed.

## Change summary

Prevent numerous chat context attachments from consuming excessive vertical space on smaller screens.

## Best solution

Bound the attached-context presentation in narrow chat inputs and provide an accessible summary or expansion affordance that preserves access to every attachment and its remove/open actions.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts`, `src/vs/workbench/contrib/chat/browser/widget/media/chat.css`
- **Validation:** Add automated coverage for the chosen collapsed/expanded attachment behavior, then resize a chat input to a narrow width with enough attachments to wrap and verify that its context area remains bounded while every attachment remains keyboard-accessible and removable.
- **Behavior:**

  > A narrow chat input containing many explicit context attachments must retain useful vertical room for the conversation and prompt editor rather than growing one row per wrapped group of attachments. Users must still be able to discover, open, navigate, and remove every attachment using mouse and keyboard. A small attachment set and wider chat inputs should retain the normal concise presentation.
- **Trace:**

  > ChatInputPart.renderAttachedContext in src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts enumerates getRenderableAttachments() and creates one attachment widget for every entry. The associated rules in src/vs/workbench/contrib/chat/browser/widget/media/chat.css use wrapping flex containers without a height or row bound, directly producing the reported vertical growth at narrow widths. ChatAttachmentsContentPart has related 'more' behavior for historical request attachments, but it is a separate rendering path and does not solve the active composer. Keep attachment model contents, request serialization, deletion behavior, implicit-context semantics, and wide-layout behavior intact; uncertainty begins at the responsive presentation and expansion contract.
- **Open decisions:**
  - Should compaction be based on a fixed visible attachment count, a maximum number of rendered rows, or the available composer width and height?
  - When compacted, should activation temporarily expand the pills in place or open a separate attachment list, and how should that state collapse again?
  - Should implicit context share the same overflow treatment as explicit attachments or remain independently visible?
