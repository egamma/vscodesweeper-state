# Issue #278428 — On smaller screens vertical space is impacted when you have a lot of context

[https://github.com/microsoft/vscode/issues/278428](https://github.com/microsoft/vscode/issues/278428)

## Summary

The compact-screen problem remains in current source: every input attachment is rendered and the container wraps without a height limit or collapsed state. This team-authored UX issue should remain open while the compact presentation and activation threshold are finalized.

## Change summary

Prevent numerous chat context attachments from consuming excessive vertical space on smaller screens.

## Best solution

Give the chat input attachment area a compact, accessible collapsed presentation on constrained layouts, while preserving access to every attachment and its remove/open actions.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts`, `src/vs/workbench/contrib/chat/browser/widget/media/chat.css`, `src/vs/workbench/contrib/chat/test/browser/widget/chatWidget.test.ts`
- **Validation:** Exercise a chat input at a narrow width with enough attachments to exceed one row: verify the composer remains height-bounded, all attachments remain keyboard-accessible through the compact interaction, expanding reveals every attachment, and removing an attachment updates both states correctly.
- **Behavior:**

  > On a constrained chat surface, adding many context attachments must not let attachment rows consume most of the conversation viewport. The compact presentation must still disclose the number of hidden items and provide mouse and keyboard access to every attachment, including its existing open and remove actions. Wider layouts and inputs with only a few attachments should retain the normal pill presentation.
- **Trace:**

  > ChatInputPart.renderAttachedContext in src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts renders the complete attachment model directly into attachedContextContainer. The corresponding rules in src/vs/workbench/contrib/chat/browser/widget/media/chat.css use wrapping flex containers without a height cap or responsive collapsed state, which conclusively preserves the reported growth on current main. ChatAttachmentsContentPart has a nearby limited-list and accessible show-more pattern for historical request attachments, but the editable input has different removal, focus, and navigation requirements. Keep the work within chat input attachment presentation; do not change attachment selection, implicit-context discovery, request serialization, or model context behavior.
- **Open decisions:**
  - Should compaction activate from available input height or width, or from a fixed number of visible attachment rows?
  - When compacted, should expanding the attachments persist until the user collapses them, or automatically return to the compact state as attachments or layout dimensions change?
