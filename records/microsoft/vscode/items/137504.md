# Issue #137504 — Bracket Pair Colorization for HTML tags

[https://github.com/microsoft/vscode/issues/137504](https://github.com/microsoft/vscode/issues/137504)

## Summary

Keep open: native colorization by HTML element nesting remains missing, and the discussed settings do not reliably provide it. With 79 upvotes and an accepted Backlog milestone, this warrants design work rather than a staleness close.

## Change summary

Color HTML/XML tag delimiters by element nesting depth while preserving ordinary tag-name highlighting.

## Best solution

Provide syntax-aware tag-delimiter colorization that handles HTML void elements and embedded markup without treating comparisons or arrows as tags. Establish the language-support boundary and parsing contract before implementation; changing literal bracket pairs alone does not satisfy the request.

Manually check that paired tag delimiters share the element-depth color while tag names retain syntax highlighting, including unindented markup; verify comparisons and arrows remain unchanged in supported embedded-language cases. Preserve the existing Bracket Pair Colorizer - Brackets suite and assess incremental-edit performance. These checks were not run during this read-only review.
- **Behavior:**

  > Opening and closing tag delimiters should share a color based on element nesting, while tag names retain ordinary syntax highlighting. HTML void elements and self-closing elements must not corrupt subsequent nesting colors, and coloring must not depend on indentation. Comparisons, arrow functions, and delimiters inside quoted attributes must not be mistaken for structural tags. Acceptance should include nested markup, mixed void/self-closing elements, and the embedded markup languages selected by the design.
- **Trace:**

  > extensions/html/language-configuration.json currently disables colorized bracket pairs explicitly. LanguageBracketsConfiguration creates literal delimiter relationships, and NonPeekableTextBufferTokenizer.read searches eligible language-token text with the corresponding bracket regular expression; neither inspected path identifies HTML element names or void elements. ColorizedBracketPairsDecorationProvider applies nesting colors to the bracket ranges emitted by that pipeline. The discussion at https://github.com/microsoft/vscode/issues/137504 demonstrates why literal angle-bracket settings and indentation-guide coloring are insufficient. Existing bracket behavior, tag-name highlighting, and incremental editor performance must remain intact. The trace does not establish how syntax-aware tag structure should enter the shared pipeline or which embedded-language providers can supply it; this is not a bounded configuration-only change.
- **Open decisions:**
  - Which markup and template languages must the initial feature support beyond standalone HTML/XML, and what should users see in unsupported embedded markup?
  - For HTML with legally omitted end tags, should nesting colors follow the implied HTML element structure or only explicitly paired tags?
