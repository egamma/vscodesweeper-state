# Issue #146921 — Add inline suggestion API commands

[https://github.com/microsoft/vscode/issues/146921](https://github.com/microsoft/vscode/issues/146921)

## Summary

The requested provider-execution API remains missing: existing inline-suggestion commands operate on editor UI state rather than returning aggregated provider data. Keep this accepted Backlog request open for API design; no verified canonical or fixing commit was found.

## Change summary

Expose an API command that returns inline-completion data aggregated across providers for Live Share and other extensions.

## Best solution

Provide a documented language-feature execution command analogous to vscode.executeCompletionItemProvider, usable without displaying inline suggestions. Establish its public request and result contract while preserving existing editor behavior and provider lifecycle guarantees.

Include no-result, provider-failure, and disposal cases, and preserve existing completion-command tests.
- **Behavior:**

  > Extensions should be able to request inline suggestions for a document and position through a language-feature API command and receive aggregated provider data rather than editor UI state. The request must not require displaying, accepting, or cycling inline suggestions. Acceptance should exercise two providers without an active editor and verify the agreed public data shape, empty results, and unchanged editor-trigger behavior.
- **Trace:**

  > src/vs/workbench/api/common/extHostApiCommands.ts provides the existing ApiCommand pattern through vscode.executeCompletionItemProvider, including argument validation and conversion to extension-facing types; no inline-completion equivalent was found. TriggerInlineSuggestionAction in src/vs/editor/contrib/inlineCompletions/browser/controller/commands.ts returns void and depends on InlineCompletionsController, so it does not satisfy the requested data API. provideInlineCompletions in src/vs/editor/contrib/inlineCompletions/browser/model/provideInlineCompletions.ts queries providers and manages streamed lists, yield-to behavior, internal transformations, and disposal. The uncertainty starts at the public command contract: the issue establishes data rather than UI output, but does not specify invocation context or how provider yield-to relationships affect aggregation. Preserve existing editor commands, rendering, and provider lifecycle behavior. https://github.com/microsoft/vscode/issues/169336 concerns hover actions, not this missing execution API.
- **Open decisions:**
  - What inline-completion request context does the public command accept, and what trigger kind applies when the caller supplies none?
  - Does the returned aggregation include every matching provider's data regardless of yield-to relationships, or honor the provider precedence used by interactive inline suggestions?

## Evidence

- **Requested contract:** https://github.com/microsoft/vscode/issues/146921 explicitly requests a data-model result merged across providers, not the UI model, and identifies Live Share and other extensions as consumers. It remains accepted in Backlog with feature-request, api, and inline-completions labels.
- **Existing API does not cover inline completions:** src/vs/workbench/api/common/extHostApiCommands.ts registers vscode.executeCompletionItemProvider with URI, position, optional trigger character and resolution count, returning a converted CompletionList. Inspection found no corresponding inline-completion execution command; vscode.executeInlineValueProvider concerns debugger inline values, not inline suggestions.
- **UI command is not equivalent:** src/vs/editor/contrib/inlineCompletions/browser/controller/commands.ts: TriggerInlineSuggestionAction registers editor.action.inlineSuggest.trigger. Its run method returns Promise<void> and triggers InlineCompletionsController's editor model; it does not return provider data to the caller.
- **Provider aggregation boundary:** src/vs/editor/contrib/inlineCompletions/browser/model/provideInlineCompletions.ts:38-148 queries providers, applies yield-to relationships, converts results into internal InlineSuggestData, streams provider lists, and manages cancellation/disposal. This machinery exists internally but is not exposed through the inspected API-command registry.

Its discussion confirms UI cycling through merged suggestions, but does not establish an API command returning that data. It is also newer than this re-reviewed item.
