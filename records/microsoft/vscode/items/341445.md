# Issue #341445 — Windows background update: hung CodeSetup .tmp installer accumulates win32k sent-message backlog and makes the whole system's input laggy over time

[https://github.com/microsoft/vscode/issues/341445](https://github.com/microsoft/vscode/issues/341445)

## Summary

Thanks for the detailed measurements. The background-update path in build/win32/code.iss blocks the installer's UI thread in a Sleep(1000) loop while waiting for the app mutex, with no message pumping, which matches the hung-window behavior described. The system-wide input lag attributed to the Ussm backlog is the reporter's own inference, so keep this open for a maintainer to look at.

## Change summary

The Windows background-update installer waits for VS Code to exit on a non-pumping UI thread, leaving hung windows that accumulate sent messages and slow system-wide input.

## Best solution

Make the background-update wait loop in build/win32/code.iss pump messages (or wait on a non-UI thread). Alternatively, have the installer exit and retry on the next launch, rather than sleeping on the UI thread for hours.

## Plan brief

- **Likely files:** `build/win32/code.iss`
- **Validation:** On Windows, start a background update with VS Code kept open. Confirm the CodeSetup tmp windows are not reported by IsHungAppWindow after an hour, and that Ussm pool usage does not grow.
- **Behavior:**

  > While waiting for VS Code to exit, the background installer must not leave windows that stop processing messages. The update must still apply once the app exits, and cancel-file and session-end handling must be unchanged.
- **Trace:**

  > In build/win32/code.iss, the background-update branch of CurStepChanged polls CheckForMutexes('{#AppMutex}') with Sleep(1000) on the UI thread and checks CancelFileExists. Inno Setup Pascal script has no built-in message pump. Do not change the mutex protocol ({#AppMutex}-ready and -updating) or the inno_updater invocation. Related reports: https://github.com/microsoft/vscode/issues/154879 and https://github.com/microsoft/vscode/issues/105205.
- **Open decisions:**
  - Should the installer keep waiting with a message-pumping loop, or exit and let VS Code retry on next launch?
  - Is it acceptable for VS Code to relaunch the installer after the user kills it, as the reporter observed?

## Evidence

- **wait loop:** build/win32/code.iss (~lines 1829-1846): `while (CheckForMutexes('{#AppMutex}')) do ... Sleep(1000)` runs on the installer's main thread during a background update, with no message pumping.
- **measurements:** The reporter measured Ussm growing to 221 MB and hook latency p90 of ~150 ms. Both returned to normal about 4 s after the CodeSetup tmp processes were killed.
- **not verified:** The causal link between the Ussm backlog and system-wide lag is the reporter's inference. I could not run the installer to confirm it.
