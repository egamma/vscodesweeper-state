# Issue #322584 — Extension host frozen ~14s by synchronous require() of undici llhttp on Copilot's first HTTPS request (starves other extensions / language clients at startup)

[https://github.com/microsoft/vscode/issues/322584](https://github.com/microsoft/vscode/issues/322584)

## Summary

Keep open: the reported startup starvation has concrete profiling evidence, and the currently pinned undici version retains synchronous first-connection parser initialization. No verified fix or qualifying older duplicate was established; this team-authored report warrants continued investigation.

## Change summary

Copilot's first HTTPS connection reportedly blocks the shared extension host for approximately 14 seconds while undici synchronously loads its llhttp parser.

## Best solution

Resolve the blocking parser initialization in undici and verify its adoption on Copilot's actual request path. Establish which module causes the packaged Windows synchronous read before choosing a VS Code-side mitigation; wrapping initialization in import() or moving it earlier does not by itself make CommonJS loading or WebAssembly compilation nonblocking.

## Evidence

- **Reported trigger and measured impact:** https://github.com/microsoft/vscode/issues/322584 reports a first HTTPS connection at workspace startup on Windows with VS Code 1.125.1. Its profile analysis identifies a contiguous 13.9-second readFileSync/readFileUtf8 interval, with all 8,315 samples attributed to Copilot's require → lazyllhttp → connectH1 path. Defender amplification is the reporter's hypothesis, not independently established.
- **Upstream initialization remains synchronous:** extensions/copilot/package-lock.json pins undici 7.29.1. In https://github.com/nodejs/undici/blob/v7.29.1/lib/dispatcher/client-h1.js, connectH1 at lines 821–826 calls lazyllhttp synchronously on the first connection. lazyllhttp synchronously requires llhttp_simd-wasm.js or llhttp-wasm.js and constructs WebAssembly.Module and WebAssembly.Instance.
- **Current Copilot request path:** extensions/copilot/src/platform/networking/node/nodeFetchFetcher.ts imports undici, creates a lazy undici.Agent({ allowH2: true }), and passes that dispatcher to the host-patched or global fetch implementation. HTTP/1 connections can therefore reach undici's parser initialization; this source inspection does not establish the reported Windows delay on current main.
- **Packaging uncertainty:** extensions/copilot/.esbuild.mts enables bundling and does not list undici among its Node build externals. The upstream require statements alone therefore do not prove that today's packaged extension performs the same disk read.
