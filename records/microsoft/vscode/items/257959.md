# Issue #257959 — git.openChange stopped to work in changed files

[https://github.com/microsoft/vscode/issues/257959](https://github.com/microsoft/vscode/issues/257959)

## Summary

The reported no-op remains explainable conclusively from current source: the shortcut resolves an active editor resource, not the selected SCM file. Keep this accepted Git bug open; supporting selection-aware keyboard invocation requires planning across the SCM and extension command boundary.

## Change summary

A custom git.openChange shortcut should open changes for the selected SCM file even when double-click opening is enabled and no editor is open.

## Best solution

Make keyboard invocation of Open Changes honor the focused SCM resource without requiring an editor to be opened first, while preserving editor-based invocation outside SCM. Account for the independently reported Open File symptom when defining the selection-aware command contract.

## Plan brief

- **Likely files:** `extensions/git/src/commands.ts`, `src/vs/workbench/contrib/scm/browser/scmViewPane.ts`, `src/vs/workbench/api/browser/mainThreadCommands.ts`, `src/vs/workbench/api/common/extHostSCM.ts`, `extensions/git/src/test/smoke.test.ts`
- **Validation:** In a disposable Git workspace, modify two tracked files, enable workbench.list.openMode=doubleClick, close all editors, single-select a changed SCM file, and invoke the reporter's argument-free shortcut. Verify that its diff opens; repeat with a different file active to ensure the selected SCM file wins. Check context-menu invocation and editor-focused invocation remain unchanged, and exercise the independently reported git.openFile shortcut. The plan should establish an automated UI regression check for actual keybinding dispatch, not merely executeCommand with an explicit URI.
- **Behavior:**

  > With double-click opening enabled, selecting a changed file in SCM and pressing a custom git.openChange shortcut must open that file's changes without first opening an editor. An unrelated active editor must not substitute its resource for the focused SCM selection. Context-menu invocation and editor-based invocation outside SCM must continue to work. Acceptance must exercise the argument-free keyboard path with no editors open and with an unrelated editor open.
- **Trace:**

  > CommandCenter.openChange in extensions/git/src/commands.ts falls back to getSCMResource(), which resolves active editor resources rather than SCM tree selection; an empty editor state reaches its early return. AbstractKeybindingService dispatches the reporter's binding without arguments, and MainThreadCommands forwards those arguments unchanged. In contrast, RepositoryPaneActionRunner in src/vs/workbench/contrib/scm/browser/scmViewPane.ts supplies selected resources to menu actions, which ExtHostSCM can resolve from marshalled handles. CommandCenter.openFile shares the fallback, matching the independent confirmation in https://github.com/microsoft/vscode/issues/257959. The existing Git smoke test supplies a URI and cannot establish keyboard-selection behavior. The trace establishes the failure but not a bounded selection-delivery implementation or the complete set of extension command consumers; planning must establish that boundary without globally changing unrelated keybindings or breaking explicit-resource and editor-focused calls.
- **Open decisions:**
  - Should selection-aware keyboard invocation be limited to the Git file-opening commands, or become an explicit shared contract for SCM resource commands contributed by extensions?
  - For multiple selected SCM files, should keyboard Open Changes operate on all selected files as the context-menu action does, or only the focused file?

## Evidence

- **Exact failing path:** The reporter selects a changed SCM file with workbench.list.openMode=doubleClick and invokes an argument-free git.openChange binding. src/vs/platform/keybinding/common/abstractKeybindingService.ts:393-396 executes such bindings without arguments; src/vs/workbench/api/browser/mainThreadCommands.ts forwards only the supplied arguments.
- **Current source defect:** extensions/git/src/commands.ts:1420-1446, CommandCenter.openChange, calls getSCMResource() when no Resource or Uri argument is supplied and returns without opening anything when resolution fails. getSCMResource at approximately line 5710 consults active notebook/text editors and an active notebook-diff tab, but never the SCM tree selection. With no editor open, the selected changed file therefore cannot be resolved.
- **Context-menu distinction:** src/vs/workbench/contrib/scm/browser/scmViewPane.ts:467-489, RepositoryPaneActionRunner.runAction, explicitly collects selected SCM resources and passes them to menu actions. src/vs/workbench/api/common/extHostSCM.ts:992 onward resolves supplied marshalled SCM resource arguments. This explains why context-menu invocation works while the shortcut does not.
