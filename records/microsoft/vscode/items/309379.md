# Issue #309379 — `remote.extensionKind` ignored from workspace/.vscode/settings.json and devcontainer Machine settings (only works from user settings)

[https://github.com/microsoft/vscode/issues/309379](https://github.com/microsoft/vscode/issues/309379)

## Summary

The detailed Dev Container logs and current source support a real configuration-initialization race: extension placement can read and permanently cache `remote.extensionKind` before remote Machine and workspace configuration is available. The issue remains necessary and should be routed to the remote area.

## Change summary

Honor `remote.extensionKind` from workspace and remote Machine settings when selecting extension host locations in a Dev Container.

## Best solution

Ensure extension-kind resolution uses the fully initialized effective configuration before running locations are assigned, while preserving existing local-user overrides and extension-host startup behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts`, `src/vs/workbench/services/extensions/common/extensionManifestPropertiesService.ts`, `src/vs/workbench/services/extensions/test/common/extensionManifestPropertiesService.test.ts`
- **Validation:** Using the issue's Dev Container, remove the local user override, configure `remote.extensionKind` separately through `.vscode/settings.json` and remote Machine settings, reload the remote window, and verify with `Developer: Show Running Extensions` that the named extensions run locally in both cases; also verify an ordinary user-level override remains effective.
- **Behavior:**

  > In a remote Dev Container window, `remote.extensionKind` must influence extension placement from every source allowed by its WINDOW configuration scope, including workspace and remote Machine settings. With only either of those sources configured, `Developer: Show Running Extensions` must show the selected extension on the requested local UI or remote workspace side. Existing user-setting behavior and placement of extensions without an override must remain unchanged.
- **Trace:**

  > Extension host assignment flows from NativeExtensionService._doResolveExtensions in src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts through AbstractExtensionService._resolveAndProcessExtensions to ExtensionRunningLocationTracker.initializeRunningLocation. The tracker obtains kinds from ExtensionManifestPropertiesService.getExtensionKind; getUserConfiguredExtensionKind snapshots `configurationService.getValue('remote.extensionKind')` into `_configuredExtensionKindsMap` on first access and does not invalidate it. The native resolution path does not await `IConfigurationService.whenRemoteConfigurationLoaded()` before running-location initialization, while src/vs/workbench/services/configuration/browser/configurationService.ts exposes that barrier specifically for remote configuration. The reporter's logs confirm the remote Machine file exists but its override is absent from the placement decision. Keep the boundary to initial extension placement and configuration readiness; do not alter default manifest-kind deduction or unrelated remote extension scanning.

## Evidence

- **confirmed reproduction:** The report and https://github.com/microsoft/vscode/issues/309379#issuecomment-4234494340 provide repeatable Dev Container steps and logs showing the populated remote Machine settings file while Copilot still starts in the Remote Extension Host; moving the same value to local user settings changes the placement.
- **configuration contract:** src/vs/workbench/contrib/remote/common/remote.contribution.ts registers `remote.extensionKind` without an explicit scope, so it uses the WINDOW scope that permits user and workspace configuration.
- **current source path:** src/vs/workbench/services/extensions/common/abstractExtensionService.ts assigns running locations immediately after extension resolution. src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts resolves and scans the remote before starting the local host but does not await `IConfigurationService.whenRemoteConfigurationLoaded()` before that assignment.
- **stale cached value:** src/vs/workbench/services/extensions/common/extensionManifestPropertiesService.ts:getUserConfiguredExtensionKind reads `configurationService.getValue('remote.extensionKind')` only while `_configuredExtensionKindsMap` is null, then retains that first snapshot without a configuration-change invalidation path.
