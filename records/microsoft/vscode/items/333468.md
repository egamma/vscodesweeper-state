# Issue #333468 — Chat history is missing from the VS Code UI although local chat session files still exist

[https://github.com/microsoft/vscode/issues/333468](https://github.com/microsoft/vscode/issues/333468)

## Summary

Current main still loses discoverability when the chat-session index is absent or invalid even though valid local session files remain. The independently confirmed report should stay open as a source-confirmed recovery bug.

## Change summary

Restore locally persisted Copilot Chat sessions to the sessions UI when their storage index becomes detached or empty.

## Best solution

Make the local chat-session store recover index metadata from valid `.jsonl` or legacy `.json` session files when the persisted index is missing or corrupt, while isolating malformed files and preserving normal session filtering.

- **Validation:** Run `scripts/test.sh --grep "ChatSessionStore"` with a new test that places a valid session file in the workspace chat storage while leaving the persisted index empty, then asserts that the recovered index exposes the session; also cover malformed files without losing valid entries.
- **Behavior:**

  > When valid persisted chat-session files exist but their index is missing or invalid, those sessions reappear in the Chat sessions UI and can be reopened after reload. Recovery supports the current `.jsonl` format and retained legacy `.json` sessions. A malformed individual file does not prevent other valid sessions from appearing. Normal indexed sessions, filtering, deletion, and empty-session behavior remain unchanged.
- **Trace:**

  > `ChatSessionStore.internalGetIndex()` in `src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts` converts a missing, malformed, or invalid `chat.ChatSessionStore.index` value directly into `{ version: 1, entries: {} }`; `getIndex()` performs no filesystem reconciliation. `ChatService.getHistorySessionItems()` in `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts` derives local history exclusively from that index, and `LocalAgentSessionsController` consumes that result for the sessions UI. The store already knows how to deserialize `.jsonl` and `.json` content through `readSessionFromLocation`, and the existing `ChatSessionStore` test suite uses an in-memory file service suitable for a fail-before/pass-after recovery test. Keep the boundary to local persisted sessions: do not alter synchronized/cloud-provider enumeration, session filtering, or transcript storage owned by the Copilot extension.

## Evidence

- **source-confirmed index gap:** On current main, `src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts` reads `chat.ChatSessionStore.index`; a missing or invalid value becomes an empty index, and `getIndex()` returns it without examining the existing files under the `chatSessions` storage root.
- **UI dependency:** `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts` implements `getHistorySessionItems()` solely from `ChatSessionStore.getIndex()`, and `src/vs/workbench/contrib/chat/browser/agentSessions/localAgentSessionsController.ts` uses those items to populate the local sessions UI. Therefore an empty index hides otherwise readable session files.
- **existing read support:** `src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts` already reads both append-log `.jsonl` sessions through `ChatSessionOperationLog` and legacy flat `.json` sessions, so the persisted content needed for recovery is supported by current main.
- **independent confirmation:** A second user confirmed the same issue in https://github.com/microsoft/vscode/issues/333468#issuecomment-3255867868.
- **distinct prior issue:** The earlier cluster at https://github.com/microsoft/vscode/issues/298507 was closed after provider-resolution changes in https://github.com/microsoft/vscode/pull/300592 and https://github.com/microsoft/vscode/pull/302160. This report postdates those fixes and specifically identifies an empty index alongside surviving local files, so the closed issue is not a valid duplicate target.
