# Issue #284849 — Support for Custom Attributes in `.prompt.md` YAML Front Matter

[https://github.com/microsoft/vscode/issues/284849](https://github.com/microsoft/vscode/issues/284849)

## Summary

A real capability gap remains on current main: prompt front matter accepts only a fixed schema and marks every other top-level attribute as unnecessary. The request is already correctly routed and assigned to the Backlog, so it should remain open pending a decision on the metadata contract.

## Change summary

Allow `.prompt.md` files to carry organization-specific YAML metadata without producing unsupported-attribute diagnostics.

## Best solution

Provide a documented custom-metadata escape hatch for prompt files—preferably a namespaced mapping unless compatibility requires arbitrary top-level keys—while retaining diagnostics for misspelled functional attributes.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/promptSyntax/languageProviders/promptFileAttributes.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/languageProviders/promptValidator.ts`, `src/vs/workbench/contrib/chat/test/browser/promptSyntax/languageProviders/promptValidator.test.ts`
- **Validation:** Run `scripts/test.sh --grep PromptValidator` with coverage showing that supported custom metadata produces no diagnostic while misspelled built-in prompt attributes remain detectable.
- **Behavior:**

  > A `.prompt.md` file can contain documented custom organizational metadata without an unsupported-attribute diagnostic. VS Code continues to interpret its functional prompt attributes exactly as before, and custom metadata does not alter prompt execution. Misspellings of reserved functional attributes must remain diagnosable. Acceptance should cover scalar, sequence, and nested-map metadata values.
- **Trace:**

  > PromptHeader in src/vs/workbench/contrib/chat/common/promptSyntax/promptFileParser.ts already retains arbitrary YAML properties as `IHeaderAttribute` values. The diagnostic comes from `PromptValidator.checkForInvalidArguments`, which compares each key with the fixed prompt list from `promptFileAttributes.ts`; the same file already models a `metadata` map for skills but not prompts. The existing PromptValidator suite is the bounded validation surface. Preserve validation, completion, and runtime semantics for the existing prompt attributes; do not broadly disable unknown-attribute diagnostics for agents, instructions, or skills. The uncertainty starts at the public prompt-file schema: arbitrary top-level extension keys maximize compatibility, while a reserved metadata container preserves typo detection and namespace control.
- **Open decisions:**
  - Should the supported contract allow arbitrary top-level custom attributes, require a reserved `metadata` mapping, or recognize a documented extension-key prefix?
  - Are custom values intentionally opaque to VS Code and retained only for external tools, or should VS Code expose them to prompt consumers through a supported API?
