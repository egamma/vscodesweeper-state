## Evidence

- **Confirmed reproduction and root cause:** The thread contains a maintainer reproduction using code-insiders serve-web followed by Configure Display Language to a non-English language. In https://github.com/microsoft/vscode/issues/299425#issuecomment-4143740925, another maintainer measured 17,234 bundled server-web messages versus 17,056 localized CDN messages for the same commit; the failing message had index 17,063 in server-web but 16,885 in standalone web.
- **Current build path:** build/next/index.ts creates a fresh NLS collector inside bundle() for each target, selects target-specific entry points, and finalizes that collector into its output and shared out-build metadata. build/next/nls-plugin.ts collects entries through esbuild onLoad and assigns indices by sorting only those collected entries. Deterministic sorting within a target does not establish identical indices across different target dependency graphs.
- **Current runtime path:** src/vs/server/node/webClientServer.ts:430-447 selects localization from the display-language cookie or Accept-Language and constructs a CDN URL using commit, version, and locale without a target identity. src/vs/nls.ts lookupMessage() indexes that global message array; an absent entry with no English fallback throws NLS MISSING, while a mismatched existing entry returns the wrong string.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/336476 is currently OPEN and explicitly says Fixes #299425. It proposes a source-wide shared NLS catalog and reports reproducing the original 1.110.0 NLS MISSING: 16444 failure. Its reported validation is PR-author evidence, not an independently executed check in this review; the unmerged PR is not a completed fix.
- **Merged packaging change does not fix this issue:** https://github.com/microsoft/vscode/pull/336093 merged as 035ea03daa564007602c813e2db7a968aac0cacf. Its description explicitly states that the browser/CDN table mismatch tracked by this issue is not fixed or changed by that PR.
