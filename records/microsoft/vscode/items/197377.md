# Issue #197377 — workspaceFolder variable substitution in launch.json or tasks.json should use URI for virtual filesystems

[https://github.com/microsoft/vscode/issues/197377](https://github.com/microsoft/vscode/issues/197377)

## Summary

The virtual-workspace URI gap remains in the current debug substitution path. The earlier fix was incomplete and explicitly reverted after breaking extensions; keep this open for a compatibility-preserving solution consistent with the maintainer's proposed new variable.

## Change summary

Allow launch.json and tasks.json substitutions to retain a virtual workspace folder's URI scheme and authority instead of reducing it to a filesystem path.

## Best solution

Provide an explicit URI-valued workspace-folder substitution consistently across renderer and extension-host resolution, while preserving existing path-valued variables for extension compatibility. Agree on its public syntax and URI serialization contract before implementation.

- **Validation:** Extend the Configuration Resolver Service tests to cover the agreed URI-valued substitution with virtual and file workspace folders, named multi-root selection, and URI escaping; retain assertions for unchanged legacy path substitutions. Run scripts/test.sh --run src/vs/workbench/services/configurationResolver/test/electron-browser/configurationResolverService.test.ts. Also verify a launch.json pathMappings value against a virtual workspace through extension-host resolution, rather than relying solely on the renderer-backed test fixture.
- **Behavior:**

  > A configuration must be able to obtain a virtual workspace folder's complete URI, including its scheme and authority, so a debug adapter can map remote source paths to editor resources. The reporter's SSHFS launch.json example currently receives a filesystem path instead. The finished behavior must work consistently in launch.json and tasks.json without breaking extensions that depend on existing path-valued substitutions. Acceptance includes virtual folders, ordinary file folders, named multi-root selection, and unchanged legacy substitutions.
- **Trace:**

  > ExtHostDebugService.$substituteVariables delegates to ExtHostVariableResolverService and then AbstractVariableResolverService.resolveAsync. The shared workspaceFolder branch calls fsPath(), and the extension-host instance supplies no label service, so URI.fsPath discards scheme and authority. Renderer resolution instead supplies ILabelService, explaining the reporter's different task result. The merged attempt in https://github.com/microsoft/vscode/pull/235954 only changed active-file-related callbacks and was explicitly reverted by https://github.com/microsoft/vscode/commit/a1d56fd8a25e54907c142e92b0bfc60f0b209485. Preserve existing path-valued substitutions and their relative-path behavior; the maintainer's direction is a separate variable, not another unconditional semantic replacement. Current registration and evaluation expose no dedicated workspace-folder URI variable. The remaining uncertainty is the public syntax and serialization contract, not the location of a guard or helper.
- **Open decisions:**
  - What public variable syntax should expose the workspace-folder URI while preserving the existing ${workspaceFolder:folderName} named-folder contract?
  - Should the new substitution return a percent-encoded URI string, and what exact serialization behavior should users and debug adapters rely on for spaces and reserved characters?
