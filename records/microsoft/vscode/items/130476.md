# Issue #130476 — VS code not preventing MacOS sleep

[https://github.com/microsoft/vscode/issues/130476](https://github.com/microsoft/vscode/issues/130476)

## Summary

Keep this accepted, well-supported request open: current power blockers cover Copilot requests and remote tunnel access, but not the broader execution/debugging lifecycle requested here. The linked Copilot implementation does not establish protection against automatic macOS restarts.

## Change summary

Prevent automatic macOS sleep or restart from interrupting running code, and restore normal power behavior when execution finishes or debugging pauses.

## Best solution

Design activity-scoped host sleep protection for supported execution and debugging workflows, allowing the display to sleep and releasing protection when work stops. Treat automatic update/restart protection as a separate platform feasibility and product decision rather than assuming a sleep blocker provides it.

## Plan brief

- **Likely files:** `src/vs/workbench/services/power/common/powerService.ts`, `src/vs/workbench/services/power/electron-browser/powerService.ts`, `src/vs/workbench/contrib/debug/browser/debugService.ts`, `src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts`, `src/vs/platform/native/electron-main/nativeHostMainService.ts`
- **Validation:** On macOS with a short idle sleep timeout, run a long task and a debug session, leave input idle, and inspect pmset -g assertions: supported active work should retain system activity while allowing display sleep. Verify protection is released after completion or the agreed debugger pause behavior, remains while another qualifying operation is active, and is cleaned up on cancellation/window close. Validate restart handling separately against the product contract selected during planning.
- **Behavior:**

  > Long-running code should not be interrupted by automatic idle system sleep while VS Code knows qualifying work is executing. The display should still be allowed to sleep, and ordinary system sleep should resume when no qualifying work remains; the reporter also requests release when debugging pauses. The original report additionally requests protection against automatic macOS update restarts, which must be evaluated separately from idle sleep. Acceptance must cover overlapping operations, completion, cancellation, and the agreed paused-debugger behavior.
- **Trace:**

  > Current desktop infrastructure exposes IPowerService.startPowerSaveBlocker in src/vs/workbench/services/power/common/powerService.ts and delegates through the desktop service to Electron in src/vs/platform/native/electron-main/nativeHostMainService.ts. Copilot already uses prevent-app-suspension through extensions/copilot/src/extension/power/vscode-node/powerService.ts, acquired by chatMLFetcher.ts, but that path does not track ordinary task or debug execution. DebugService exposes session and state lifecycle events in src/vs/workbench/contrib/debug/browser/debugService.ts; AbstractTaskService exposes task state changes in src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts. Searches found no power-blocker integration in debug, tasks, or terminal contributions, but this review did not enumerate every execution surface or execute macOS behavior. Preserve existing Copilot and remote-tunnel protection, and do not equate display sleep, idle system sleep, explicit sleep, and OS restart. The narrower completed work is documented at https://github.com/microsoft/vscode/issues/276546; the original discussion and host/container workarounds remain at https://github.com/microsoft/vscode/issues/130476.
- **Open decisions:**
  - Should execution-scoped sleep protection be enabled by default, or require explicit user opt-in?
  - Which activities qualify: debug sessions and registered tasks only, or also test runs, notebook execution, and commands in integrated terminals?
  - Does debugging paused at a breakpoint release protection, as suggested by the reporter, or retain it to preserve the session?
  - For container and remote execution, when should work keep the local desktop host awake, and is protection of a separate remote host part of the supported contract?
  - Is preventing automatic macOS update restarts part of this feature's supported behavior, or should the initial scope explicitly cover idle sleep only?
