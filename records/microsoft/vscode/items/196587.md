# Issue #196587 — Git - Allow users to still force push, or drive them to the new force push settings

[https://github.com/microsoft/vscode/issues/196587](https://github.com/microsoft/vscode/issues/196587)

## Summary

Keep open: current force-push errors distinguish the safety rejection, but still recommend Pull without explaining the controlling settings or offering a one-operation override. The existing settings only provide persistent workarounds, and the older related issue concerns a different user-visible workflow.

## Change summary

Explain force-push safety rejections and provide an appropriate recovery path without requiring users to permanently disable protective settings.

## Best solution

Make the built-in Git rejection dialog explain the active safety protection and provide a deliberate recovery path. A maintainer should decide whether that means settings guidance alone or an explicitly confirmed, operation-scoped override that leaves future pushes protected.

- **Behavior:**

  > When a force push is rejected by an enabled safety protection, the dialog explains why that explicitly requested operation was blocked and provides a useful recovery path rather than only recommending Pull. The existing protection remains the default. A maintainer must choose whether recovery is settings guidance or a deliberately confirmed exception for this operation. - **Trace:**

  > CommandCenter._push in extensions/git/src/commands.ts derives the force mode from git.useForcePushWithLease and git.useForcePushIfIncludes, then invokes the repository push path. Repository.push in extensions/git/src/git.ts emits the corresponding flags and classifies safety rejections; the workbench-facing Repository._push is in extensions/git/src/repository.ts. CommandCenter.createCommand already distinguishes force rejection wording from ordinary PushRejected, but combines the two force rejection codes and offers only log/output actions alongside Pull guidance. The persistent settings in extensions/git/package.json partially cover manual recovery, not the requested rejection-time experience. The uncertainty is the public recovery contract, not whether Git should reject the protected operation.
- **Open decisions:**
