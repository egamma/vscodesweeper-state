# Issue #153164 — Allow registerTextEditorCommand callbacks to return a value

[https://github.com/microsoft/vscode/issues/153164](https://github.com/microsoft/vscode/issues/153164)

## Summary

The requested capability is still missing: text editor command callbacks have a void contract, and their return values are discarded. Keep this accepted Backlog request open; the existing registerCommand workaround does not provide the same editor and edit-builder integration.

## Change summary

Allow values returned by registerTextEditorCommand callbacks to reach callers of executeCommand.

## Best solution

Provide a documented return-value contract for text editor commands while preserving the synchronous edit-builder lifetime and existing edit-completion ordering. API owners should settle promise-return and edit-failure semantics before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `extensions/vscode-api-tests/src/singlefolder-tests/commands.test.ts`
- **Validation:** Extend the vscode API - commands integration suite to register a text editor command returning 42, invoke it through executeCommand with an active editor, and assert that the result is 42 and its synchronous edits have completed. Cover no active editor, void callbacks, and the chosen promise-return and edit-failure contracts; no tests were executed during this read-only review.
- **Behavior:**

  > Extension authors should be able to obtain a text editor command callback's result through executeCommand without replacing the registration with registerCommand. A callback returning 42 with an active editor should produce 42 after the command's synchronous edits finish. Existing callbacks returning nothing and commands invoked without an active editor should retain their current behavior. The edit builder must remain valid only during synchronous callback execution; promise-return and failed-edit outcomes need an explicit API contract.
- **Trace:**

  > The public signature in src/vscode-dts/vscode.d.ts declares a void callback. In src/vs/workbench/api/common/extHost.api.impl.ts, commands.registerTextEditorCommand wraps callback.apply in activeTextEditor.edit, discards the callback result, and resolves its completion handler without a value. Ordinary registerCommand directly registers the handler and therefore provides the reporter's partial workaround. ExtHostTextEditor.edit and _applyEdit in src/vs/workbench/api/common/extHostTextEditor.ts establish the synchronous builder lifetime; preserve that boundary and the existing completion ordering. https://github.com/microsoft/vscode/issues/178931#issuecomment-1496317688 explains why asynchronous builder usage is unsupported, but does not decide synchronous return-value support. extensions/vscode-api-tests/src/singlefolder-tests/commands.test.ts already exercises editor-command arguments and is the relevant integration-test surface. The remaining uncertainty is the observable contract for thenable results and unsuccessful edit application, not where to retain the callback result.
- **Open decisions:**
  - Should the API support only synchronous callback results, or also await returned thenables while keeping the edit builder strictly synchronous?
  - Should executeCommand expose the callback result when applying its edits fails, or retain the existing undefined outcome for that case?
