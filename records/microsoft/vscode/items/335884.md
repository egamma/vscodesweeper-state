# Issue #335884 — MCP migration blocks same-name servers in different workspace roots

[https://github.com/microsoft/vscode/issues/335884](https://github.com/microsoft/vscode/issues/335884)

## Summary

Team-authored, source-confirmed bug: the cross-root migration guard in mcpServerCustomizationMigration.ts rejects any name collision across workspace roots even when destinations differ, but a real fix must also reconcile with sessionMcpDiscovery's first-root-wins name merge, so this needs a maintainer's design call before implementation.

## Change summary

MCP config migration blocks migrating same-named servers that live in separate workspace roots' .mcp.json files, even though they wouldn't overwrite each other.

## Best solution

Relax findCrossRootConflicts to only block when migrating would actually overwrite a differing entry at the same destination, while explicitly deciding how to handle (or surface) the runtime precedence change in sessionMcpDiscovery's `_mergeRootDefinitions`, which still picks the first root's definition by name.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/aiCustomization/mcpServerCustomizationMigration.ts`, `src/vs/platform/agentHost/node/shared/sessionMcpDiscovery.ts`
- **Validation:** Extend the existing migration tests (mcpServerCustomizationMigration test suite) to assert that identically-named servers in two different workspace roots each migrate independently into their own root's .mcp.json, without a cross-root conflict failure.
- **Behavior:**

  > Migrating MCP server entries from .vscode/mcp.json to per-root .mcp.json should not fail just because another workspace root happens to define a server with the same name; each root's entry should migrate into its own .mcp.json unless doing so would actually overwrite a different, unmigrated entry at that same destination. Acceptance: two roots with an identical 'same' server both migrate successfully in the scenario from the issue, and genuinely conflicting overwrites are still rejected.
- **Trace:**

  > The rejection happens in findCrossRootConflicts (src/vs/workbench/contrib/chat/browser/aiCustomization/mcpServerCustomizationMigration.ts, ~lines 264-296): for every other root it checks whether any source or target document has a server of the same name and, if so, records it as a conflict, with no comparison of contents or whether the destination is actually different. Do not touch this in isolation, though: _mergeRootDefinitions (src/vs/platform/agentHost/node/shared/sessionMcpDiscovery.ts, lines 178-190) resolves same-named servers across roots at runtime by keeping the first root's definition and dropping the rest, so loosening the migration guard changes which config ends up winning at session-start time. Related: https://github.com/microsoft/vscode/issues/335820 (where this was found) and https://github.com/microsoft/vscode/issues/335860 (a related refresh-loop fix that does not touch this restriction). Where the uncertainty starts: whether migration should just permit identical-content duplicates, or must also change/warn about the runtime precedence semantics when the migrated configs differ.
- **Open decisions:**
  - Should migration allow same-name servers across roots only when contents are identical, or in general (accepting that runtime precedence still picks one)?
  - Does the fix need to also change or surface sessionMcpDiscovery's first-root-wins merge behavior, or is silently keeping current precedence acceptable?
  - Should the UI warn the user when migrating a same-named server that will not be the one used at runtime due to another root's precedence?

## Evidence

- **guard code:** findCrossRootConflicts in src/vs/workbench/contrib/chat/browser/aiCustomization/mcpServerCustomizationMigration.ts (around lines 264-296) flags a conflict whenever any other root's source or target document has a server with the same name, regardless of whether contents match or destinations differ.
- **runtime merge:** _mergeRootDefinitions in src/vs/platform/agentHost/node/shared/sessionMcpDiscovery.ts (lines 178-190) merges same-named servers across roots by taking the first root's definition, so removing the migration guard without addressing this could silently change which server config wins at runtime.
- **author:** Reported by vritant24 (MEMBER), who traced this from source and existing migration tests while investigating https://github.com/microsoft/vscode/issues/335820; explicitly flags the runtime-precedence tradeoff as unresolved.
- **no fix on main:** git log on mcpServerCustomizationMigration.ts shows no commit addressing this since the issue was filed.
