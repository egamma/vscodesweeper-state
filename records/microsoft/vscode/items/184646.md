# Issue #184646 — .vscode\cli\ ignores portable mode

[https://github.com/microsoft/vscode/issues/184646](https://github.com/microsoft/vscode/issues/184646)

## Summary

Keep open: current CLI initialization still defaults to the home-directory CLI folder without consulting VSCODE_PORTABLE. Explicit CLI-directory overrides are workarounds, not automatic portable-mode support, and this issue already serves as the canonical report for several duplicates.

## Change summary

Make the CLI automatically keep its data inside the portable data directory instead of creating ~/.vscode/cli.

## Best solution

Support portable-aware CLI data placement while preserving explicit CLI-directory overrides and existing nonportable behavior. Settle how existing home-directory CLI state should be handled when portable mode is enabled.

## Plan brief

- **Likely files:** `cli/src/state.rs`, `cli/src/bin/code/main.rs`, `cli/src/commands/args.rs`
- **Validation:** In an isolated Windows or Linux environment, launch the portable application and its CLI with a clean temporary home and portable data directory; verify no home-directory .vscode/cli is created and CLI metadata stays under portable data/cli. Check explicit --cli-data-dir and VSCODE_CLI_DATA_DIR overrides, unchanged nonportable defaults, and the agreed behavior when legacy home-directory CLI state already exists.
- **Behavior:**

  > Starting portable VS Code currently creates a CLI data folder in the user's home directory even though a portable data directory is configured. Automatic CLI data placement should follow the portable installation without requiring a second environment variable or flag. Explicit CLI-directory overrides and nonportable operation must retain their existing behavior. Acceptance includes portable desktop startup and CLI invocation on Windows and Linux, with no default CLI folder created in the temporary home directory.
- **Trace:**

  > cli/src/bin/code/main.rs initializes LauncherPaths before dispatch using only GlobalOptions.cli_data_dir. cli/src/commands/args.rs obtains that option from --cli-data-dir or VSCODE_CLI_DATA_DIR; without it, LauncherPaths::migrate in cli/src/state.rs selects the home-directory default, optionally migrates ~/.vscode-cli, and creates the resulting directory. src/bootstrap-node.ts configurePortable already detects portable data and exports VSCODE_PORTABLE, but LauncherPaths does not consume it. The portable-aware resolver in cli/src/tunnels/user_data_path.rs serves a different purpose and does not resolve this CLI-root gap. Preserve ordinary CLI paths and explicit overrides; general XDG restructuring and ~/.copilot placement are outside this report. Related https://github.com/microsoft/vscode/issues/3884 concerns broader folder organization, while https://github.com/microsoft/vscode/issues/323325 concerns a separate data directory. The remaining product question is how portable initialization should interact with pre-existing home-directory CLI state.
- **Open decisions:**
  - When portable mode is enabled and home-directory CLI state already exists, should the portable installation start with independent state or migrate existing state into its portable data directory?

## Evidence

- **Current CLI initialization:** cli/src/bin/code/main.rs calls LauncherPaths::migrate(core.global_options.cli_data_dir.clone()) before command dispatch. In cli/src/state.rs, migrate(None) chooses the home directory plus DEFAULT_DATA_PARENT_DIR/cli, and new_for_path creates that directory; neither migrate nor new consults VSCODE_PORTABLE.
- **Existing capability does not cover the request:** cli/src/commands/args.rs:775–778 exposes --cli-data-dir and VSCODE_CLI_DATA_DIR. These explicitly redirect CLI metadata, matching the workarounds reported in comments 4 and 5, but require separate configuration and do not automatically follow portable mode. --user-data-dir is a separate desktop option.
