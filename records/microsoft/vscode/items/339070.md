# Issue #339070 — "Install specific version" on extension takes 30s to show the version selector

[https://github.com/microsoft/vscode/issues/339070](https://github.com/microsoft/vscode/issues/339070)

## Summary

Traced in source: the version picker validates engine compatibility for every gallery version, and when the marketplace response omits the engine property for a version, VS Code falls back to fetching that version's manifest individually — exactly matching the per-extension-request pattern the reporter saw in the network tab. A design decision (skip/lazily defer the per-version check vs. batch it) is needed before implementing, so this is a plan, not a same-day fix.

## Change summary

"Install Specific Version" takes ~30s to populate the version list because VS Code issues a separate manifest request per gallery version lacking cached engine metadata.

## Best solution

Avoid eagerly validating engine compatibility for every historical version when just populating the picker — either trust the marketplace-provided engine property and skip the manifest fallback for older versions, or defer the compatibility check to install time instead of list time, in extensionGalleryService.ts's getVersions/isValidVersion/isEngineValid path.

## Plan brief

- **Likely files:** `src/vs/platform/extensionManagement/common/extensionGalleryService.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsActions.ts`
- **Validation:** A test/manual check that opening "Install Specific Version" for an extension with many older versions lacking cached engine metadata no longer issues one manifest HTTP request per version (e.g. assert request count scales with a small constant, not with version count).
- **Behavior:**

  > Opening "Install Specific Version..." on an extension should populate the version picker quickly (not ~30s) even when the extension has many published versions. The marketplace manifest should not be fetched individually for every historical version just to show the list; compatibility/engine checks for rarely-installed old versions can be deferred or relaxed. Acceptance: network activity when opening the picker does not scale linearly with the extension's total version count.
- **Trace:**

  > InstallAnotherVersionAction.run (src/vs/workbench/contrib/extensions/browser/extensionsActions.ts:1610) calls IExtensionGalleryService.getAllCompatibleVersions, which calls the private getVersions (src/vs/platform/extensionManagement/common/extensionGalleryService.ts:1785). getVersions runs isValidVersion (line 997) over every version returned by the gallery query via Promise.all (line 1813). When `compatible` is true, isValidVersion calls isEngineValid (line 1046), which calls getEngine (line 1064) to fetch that version's manifest over the network whenever the version's gallery-provided `engine` property (the module-level getEngine(version) helper at line 346) is empty — common for older/legacy versions. This produces one HTTP request per such version, which is what the reporter observed in the network tab. The boundary: do not change how compatibility is computed for versions that already carry gallery engine metadata, and do not change the install path itself — only how/when the fallback per-version manifest fetch is triggered for the picker list.
- **Open decisions:**
  - Should the version picker skip eager engine-compatibility validation for older versions entirely (showing them, and only checking compatibility at actual install time), or should it still validate eagerly but batch/limit the fallback manifest fetches (e.g. cap how many legacy versions get the expensive fallback)?
  - If validation is deferred, what should the picker show for a version whose compatibility is unknown until install is attempted?
