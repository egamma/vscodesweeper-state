# Issue #184829 — JSX Linked Editing not working with Vim extension

[https://github.com/microsoft/vscode/issues/184829](https://github.com/microsoft/vscode/issues/184829)

## Summary

This remains a confirmed core linked-editing defect rather than a Vim-extension problem: deleting the complete opening-tag name and typing its replacement can leave the closing tag unsynchronized. The older related issue reports broader desynchronization during rapid edits, but not the same specific observable sequence required for a duplicate close on re-review.

## Change summary

Replacing an entire multiline JSX opening-tag name through Vim-style word editing fails to propagate the replacement to the closing tag.

## Best solution

Keep this older, specific report open and fix the core linked-editing lifecycle so a linked range remains active across complete deletion and subsequent replacement, with a regression test covering the delete-then-type sequence on separate lines.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/linkedEditing/browser/linkedEditing.ts`, `src/vs/editor/contrib/linkedEditing/test/browser/linkedEditing.test.ts`
- **Validation:** Extend the linked editing editor-contribution tests with a multiline case that deletes the complete reference tag name, types a replacement, and asserts both linked ranges contain the replacement; run scripts/test.sh --grep "linked editing".
- **Behavior:**

  > When linked editing is active, deleting the complete opening-tag name and immediately typing a replacement keeps the opening and closing names synchronized, including when they are on separate lines. The behavior must work for the equivalent core edit sequence without requiring Vim or another extension. Partial replacements, ordinary typing, breakout characters, and undo/redo behavior must remain unchanged.
- **Trace:**

  > LinkedEditingContribution in src/vs/editor/contrib/linkedEditing/browser/linkedEditing.ts handles content changes by choosing between _syncRanges and a debounced updateRanges call; updateRanges may clear decorations when the current reference range no longer contains the cursor. The current suite in src/vs/editor/contrib/linkedEditing/test/browser/linkedEditing.test.ts verifies complete word deletion only through the intermediate '<></>' state and never types the replacement, leaving the reported transition uncovered. https://github.com/microsoft/vscode/pull/242993 addressed a related desynchronization path, but a maintainer subsequently confirmed the complete-tag behavior still reproduces at https://github.com/microsoft/vscode/issues/208276#issuecomment-3246989361. Diagnose whether the failure comes from decoration tracking, cursor movement, provider refresh, or event ordering before choosing the implementation boundary; do not alter linked-editing breakout semantics or extension command handling.

## Evidence

- **core reproduction:** https://github.com/microsoft/vscode/issues/184829#issuecomment-2092498009 reports the same complete-tag deletion and retyping failure with Vim disabled, so this is not attributable solely to the third-party extension.
- **continued confirmation:** https://github.com/microsoft/vscode/issues/208276#issuecomment-3246989361 is a VS Code team confirmation that the complete-tag replacement behavior still reproduced after https://github.com/microsoft/vscode/pull/242993 merged.
- **current source:** src/vs/editor/contrib/linkedEditing/browser/linkedEditing.ts routes model changes between _syncRanges and updateRanges; updateRanges can clear the active decorations when the cursor is no longer contained by the reference range, making the deletion-to-empty transition a sensitive lifecycle boundary.
- **test gap:** src/vs/editor/contrib/linkedEditing/test/browser/linkedEditing.test.ts covers deleting the whole linked word and expects '<></>', but does not type a replacement afterward or cover the multiline JSX-style sequence from this report.
- **related older issue:** https://github.com/microsoft/vscode/issues/180156 is older and tracks linked editing stopping during rapid edits, but its reporter-observable sequence is broader than this report's complete deletion followed by replacement, so it does not meet the stronger duplicate bar for this re-reviewed item.
