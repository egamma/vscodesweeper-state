# Issue #307430 — Allow subagents to use higher-cost models than the parent session

[https://github.com/microsoft/vscode/issues/307430](https://github.com/microsoft/vscode/issues/307430)

## Summary

This is a valid, still-unimplemented subagent feature request and the oldest report in a cluster of requests for higher-cost specialist models. It should be classified and routed to the subagent area for a product decision on authorization and charging semantics.

## Change summary

Allow an orchestrating agent to invoke a subagent whose configured model has a higher cost multiplier than the parent model.

## Best solution

Define an explicit consent policy for higher-cost subagents, then let `RunSubagentTool` honor an authorized model from `.agent.md` or its model parameter while retaining the current cost-tier protection by default.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts`, `src/vs/workbench/contrib/chat/test/common/tools/builtinTools/runSubagentTool.test.ts`
- **Validation:** Extend the RunSubagentTool unit suite and run `scripts/test.sh --grep 'RunSubagentTool'`; acceptance should cover rejection without authorization and successful resolution of a higher-multiplier configured model with authorization.
- **Behavior:**

  > A user can explicitly authorize a subagent to use its configured model even when that model costs more than the parent session's model. Without that authorization, the existing cost-tier protection remains in effect and the invocation does not silently consume the higher tier. The selected and displayed subagent model must match the authorized model from the custom-agent configuration or explicit invocation parameter.
- **Trace:**

  > `RunSubagentTool.resolveSubagentModel` in `src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts` resolves the explicit `model` parameter first and custom-agent `model` frontmatter second. It then applies `checkMultiplierConstraint` to every non-Auto result and throws whenever the selected model's `multiplierNumeric` exceeds the parent model's multiplier. The corresponding test suite explicitly asserts this rejection. Keep model availability checks, agent allowlists, Auto-model behavior, and rejection for unauthorized higher-cost requests unchanged. Related demand appears in https://github.com/microsoft/vscode/issues/309540, https://github.com/microsoft/vscode/issues/309543, and https://github.com/microsoft/vscode/issues/314121.
- **Open decisions:**
  - Should authorization be requested per invocation, stored as a persistent setting, or support both with deny as the default?
  - Should the authorization cover both models declared in custom-agent frontmatter and models supplied through the `runSubagent` model parameter, or only user-authored agent configurations?
  - What should happen in unattended or autopilot sessions where an interactive approval cannot be obtained?
