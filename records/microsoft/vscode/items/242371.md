These details extend the canonical's existing SSH reproduction rather than establish a separate requested behavior.
- **Current-source remote failure:** At checkout HEAD 8571e6fd2f04a40dc0341c05897b93ff132b06f8, terminalLinkManager.ts passes OSC 8 targets as URI.parse(text) directly to TerminalUrlLinkOpener. terminalLinkOpeners.ts:302-352 stats the unchanged file:// URI and falls back to external opening on failure. Unlike terminalLinkResolver.ts:28-33, that path does not convert file:// targets to vscode-remote:// with the terminal's remote authority, so a remote-only target is looked up in the wrong filesystem.
- **Local support versus hover issue:** Current TerminalUrlLinkOpener already delegates existing local file:// targets to VS Code file/folder openers. https://github.com/microsoft/vscode/issues/241646#issuecomment-3526101526 distinguishes successful direct activation from its remaining blue-hover-link failure; that narrower hover behavior is not the basis for this duplicate proposal.
