# Issue #224516 — LogOutputChannel does not clear all characters of Log Message

[https://github.com/microsoft/vscode/issues/224516](https://github.com/microsoft/vscode/issues/224516)

## Summary

The defect remains source-reproducible on current main: LogOutputChannel tracks unformatted message bytes, but clear uses that value as an offset into a file containing additional timestamp, level, and newline bytes. This issue should remain open as the canonical report for the resulting partial stale output.

## Change summary

LogOutputChannel.clear() leaves characters from earlier formatted log entries visible when another entry is written.

## Best solution

Ensure clearing a LogOutputChannel advances its displayed-content boundary through the complete formatted log data written before clear(), while preserving the intended on-disk log retention and existing behavior of ordinary OutputChannels.

## Evidence

- **source reproduction:** In src/vs/workbench/api/common/extHostOutput.ts, ExtHostOutputChannel.log increments offset using only VSBuffer.fromString(message).byteLength, and clear() sends that raw-message offset through OutputChannelUpdateMode.Clear.
- **formatted file mismatch:** src/vs/platform/log/common/fileLog.ts writes each normal logger entry as a timestamp, level marker, message, and trailing newline. The actual file position is therefore beyond the raw-message offset tracked by ExtHostOutputChannel.
- **observable trigger:** src/vs/workbench/contrib/output/common/outputChannelModel.ts resets FileContentProvider to the supplied offset and subsequently reads from that byte position. For the reporter's info('my first log message') -> clear() -> info('my second log message') sequence, this starts reading inside the first formatted entry and exposes its remaining characters.
