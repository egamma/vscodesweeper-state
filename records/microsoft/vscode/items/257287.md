# Issue #257287 — Git - prune branches when deleting a worktree

[https://github.com/microsoft/vscode/issues/257287](https://github.com/microsoft/vscode/issues/257287)

## Summary

Keep open: deleting a worktree still offers no associated branch-cleanup option. Existing fetch pruning only partially addresses the discussion, and no verified canonical owns the complete request; this is accepted, team-authored Backlog work.

## Change summary

Offer optional cleanup of associated local and/or remote branches when deleting a Git worktree.

## Best solution

Provide an explicit, opt-in branch-cleanup choice in the built-in Git worktree deletion flow, clearly distinguishing local branch deletion, remote branch deletion, and stale remote-tracking reference pruning. Settle the cleanup scope and destructive-operation semantics before implementation.

## Plan brief

- **Likely files:** `extensions/git/src/commands.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/git.ts`
- **Validation:** In a disposable repository with a local bare remote, create and push a branch, attach a worktree, and exercise each approved cleanup choice through Git: Delete Worktree. Verify worktree presence with git worktree list, local branch presence with git show-ref, and remote branch presence with git ls-remote. Declining or cancelling cleanup must preserve branches; ordinary worktree deletion must retain its existing behavior. Also check detached HEAD, an unmerged branch, and dirty-worktree deletion refusal.
- **Behavior:**

  > Deleting a worktree currently leaves its associated branches behind, requiring separate cleanup. Users should be able to explicitly choose the approved associated-branch cleanup operations without changing the default behavior of worktree deletion. Acceptance must distinguish deletion of a local branch, deletion of a branch on the remote, and pruning a stale remote-tracking reference. Cancellation or refusal to delete the worktree must not unexpectedly remove branches.
- **Trace:**

  > WorktreeDeleteItem.run and Commands.deleteWorktree in extensions/git/src/commands.ts lead to Repository.deleteWorktree in extensions/git/src/repository.ts, which invokes the low-level git worktree remove operation in extensions/git/src/git.ts. WorktreeDeleteItem already has the worktree ref and detached-state information, but the removal path does not use it for branch cleanup. Separate local and remote branch deletion paths exist, including an unmerged-local-branch confirmation in Commands._deleteBranch. Repository.fetchPrune and git.pruneOnFetch operate at fetch time and do not implement associated local or remote branch deletion. Preserve existing dirty-worktree and unmerged-branch safeguards, and do not silently extend cleanup to agent-session callers or the reverse branch-deletion workflow. https://github.com/microsoft/vscode/issues/183906 owns bulk local cleanup after upstream disappearance, not this lifecycle integration. The uncertainty begins at the user-visible cleanup choices and whether the reverse operation requested in the final comment belongs in this scope.
- **Open decisions:**
  - Which operations should the worktree-deletion choice expose: associated local branch deletion, deletion of its remote upstream, stale remote-tracking pruning, or a combination?
  - Should branch deletion automatically offer removal of its corresponding worktree as part of this feature, or should that reverse lifecycle request remain separate?
