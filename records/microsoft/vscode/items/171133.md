# Issue #171133 — Support case sensitive matching during completion

[https://github.com/microsoft/vscode/issues/171133](https://github.com/microsoft/vscode/issues/171133)

## Summary

Keep open: current completion filtering still accepts case-insensitive matches, and no existing setting provides the requested case-matching modes. This team-authored Backlog request has supporting discussion and no verified canonical that absorbs its full scope.

## Change summary

Allow users to configure case sensitivity when filtering the completion list.

## Best solution

Provide a consistent editor-level completion matching policy while preserving today's behavior by default. Settle which case-sensitive modes to expose and their interaction with fuzzy matching before implementation.

## Plan brief

- **Likely files:** `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/contrib/suggest/browser/completionModel.ts`, `src/vs/editor/contrib/suggest/test/browser/completionModel.test.ts`, `src/vs/base/common/filters.ts`
- **Validation:** Extend the CompletionModel unit suite with mixed-case labels and filterText values, checking the agreed modes, unchanged default behavior, and incremental refiltering. Run that targeted suite and manually compare completion eligibility for timelineFilters/TimeStamp and g/G under each mode.
- **Behavior:**

  > Users can choose how character case affects eligibility in the completion list. The selected policy applies consistently across language providers and remains effective as the user types additional characters. Existing behavior remains the default. Acceptance checks must distinguish excluding case-mismatched candidates from merely ranking exact-case candidates higher, and cover both labels and provider-supplied filterText.
- **Trace:**

  > CompletionModel._createCachedState in src/vs/editor/contrib/suggest/browser/completionModel.ts supplies lowercase patterns and candidate text to the shared fuzzy scorers for both label and filterText paths. _doScore in src/vs/base/common/filters.ts gives exact-case characters a scoring bonus but permits case-insensitive matches. ISuggestOptions and EditorSuggest in src/vs/editor/common/config/editorOptions.ts contain no case-matching policy; existing typo, word-boundary, and selection-history settings do not provide it. The CompletionModel suite in src/vs/editor/contrib/suggest/test/browser/completionModel.test.ts already constructs mixed-case foo/Foo candidates and offers a focused validation surface. Preserve default completion behavior and unrelated consumers of the shared fuzzy scorer. The unresolved product boundary is which matching modes the editor should expose and how those modes interact with fuzzy matching; the C# report at https://github.com/dotnet/vscode-csharp/issues/6170 supplies related selection evidence but does not settle that contract.
- **Open decisions:**
  - Should the user-facing policy offer insensitive and fully sensitive matching only, or also a first-character-sensitive mode?
  - In case-sensitive modes, should case constraints apply to every character matched by the existing fuzzy matcher, or should eligibility require a case-sensitive contiguous prefix?

## Evidence

- **Current filtering path:** src/vs/editor/contrib/suggest/browser/completionModel.ts, CompletionModel._createCachedState, lowercases the typed word and passes lowercase label/filterText values to fuzzyScore or fuzzyScoreGracefulAggressive. Both label-based and filterText-based filtering remain case-insensitive.
- **Case preference is not case filtering:** src/vs/base/common/filters.ts:847-872, _doScore, rejects characters based on lowercase comparisons and awards a higher score for exact-case matches. This influences ranking but does not exclude differently cased candidates.
