# Issue #290466 — Restoring a sync state is failing

[https://github.com/microsoft/vscode/issues/290466](https://github.com/microsoft/vscode/issues/290466)

## Summary

The restore failure remains source-reproducible on current main: the restore path writes with the synthetic ref `0`, and unlike normal synchronization it does not recover from the resulting 412 by refreshing the remote ref and retrying. Multiple users have independently confirmed the same repeatable failure.

## Change summary

Restoring a historical Settings Sync resource fails with HTTP 412 when newer remote data exists.

## Best solution

Make historical-resource restore tolerate a changed remote revision while preserving the explicitly selected historical content, with a regression test covering a 412 between selecting and applying the restore.

- **Behavior:**

  > Restoring a selected historical Settings Sync resource must replace the current synced resource even if another client has created a newer remote revision since the history was displayed. The explicitly selected historical content must remain the restore source; conflict recovery must not merge away or substitute that selection. Acceptance requires a test in which the first restore write encounters HTTP 412 and the operation still completes with the selected content. Ordinary synchronization and restoration without a concurrent update must remain unchanged.
- **Trace:**

  > The Restore action in `src/vs/workbench/contrib/userDataSync/browser/userDataSyncViews.ts` passes the historical handle to `UserDataSyncService.replace` in `src/vs/platform/userDataSync/common/userDataSyncService.ts`. That service resolves the selected content and calls `AbstractSynchroniser.replace` in `src/vs/platform/userDataSync/common/abstractSynchronizer.ts`. `replace` obtains `getLatestRemoteUserData(null)`, which produces ref `NON_EXISTING_RESOURCE_REF` (`0`), then calls `applyResult` with `force: false`; resource synchronizers therefore send `If-Match: 0` through `UserDataSyncStoreService.writeResource`, and an existing/newer resource produces the reported 412. Normal `performSync` already refreshes remote data and retries `PreconditionFailed`, but the direct restore path bypasses that recovery. Keep the boundary to restoring the selected resource: do not alter normal merge behavior or silently replace the selected historical payload with current remote content. ## Evidence

- **source trace:** `src/vs/workbench/contrib/userDataSync/browser/userDataSyncViews.ts` registers the Restore command and passes the selected historical handle to `IUserDataSyncService.replace`; `src/vs/platform/userDataSync/common/userDataSyncService.ts` resolves that content and calls `AbstractSynchroniser.replace`.
- **failing precondition path:** In `src/vs/platform/userDataSync/common/abstractSynchronizer.ts`, `replace` calls `getLatestRemoteUserData(null)`, which returns `{ ref: NON_EXISTING_RESOURCE_REF, syncData: null }`; `NON_EXISTING_RESOURCE_REF` is `0`. The selected historical content is then applied with `force: false`, so resource synchronizers pass ref `0` to `writeResource`, which emits it as `If-Match` in `src/vs/platform/userDataSync/common/userDataSyncStoreService.ts` and surfaces HTTP 412 as `PreconditionFailed`.
- **missing recovery:** `AbstractSynchroniser.performSync` explicitly catches `Conflict` and `PreconditionFailed`, reloads the current remote data without cache, and retries. `AbstractSynchroniser.replace` calls `applyResult` directly and has no corresponding recovery, matching the reported command error when newer remote data exists.
