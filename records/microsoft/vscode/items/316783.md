# Issue #316783 — vscode_listCodeUsages reports 0 usages to Copilot if a user invoked find all references is invoked

[https://github.com/microsoft/vscode/issues/316783](https://github.com/microsoft/vscode/issues/316783)

## Summary

A real API and tool-result gap remains on current main: reference providers cannot distinguish agent-initiated requests from interactive Find All References requests, and an internally cancelled provider request can therefore reach the usages tool as a valid empty result. This team-authored issue should remain open for an API-design decision.

## Change summary

Allow reference providers and the usages tool to distinguish agent-initiated, user-initiated, cancelled, and incomplete reference requests.

## Best solution

Define reference-request context and cancellation semantics that let providers distinguish interactive UI requests from agent/tool requests without coupling extensions directly to Copilot. The usages tool should report cancellation or incomplete results distinctly rather than telling the model that zero usages exist.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages.ts`, `src/vs/editor/contrib/gotoSymbol/browser/goToSymbol.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`, `src/vs/workbench/contrib/chat/browser/tools/usagesTool.ts`, `src/vs/workbench/api/test/browser/extHostLanguageFeatures.test.ts`, `src/vs/workbench/contrib/chat/test/browser/tools/usagesTool.test.ts`
- **Validation:** Extend the reference-provider API tests to assert the observable request context for interactive and agent callers, and extend the UsagesTool tests to assert that cancellation or incompleteness is not rendered as `No usages found`; run the targeted ExtHostLanguageFeatures and UsagesTool unit-test suites.
- **Behavior:**

  > Reference providers can distinguish a reference request initiated by an interactive user action from one initiated by an agent tool. Concurrent user and agent requests do not become indistinguishable solely because an extension coordinates or cancels expensive reference work. A cancelled or incomplete agent request is not reported to the model as a successful zero-usage result. Existing reference providers that only use `includeDeclaration` remain compatible.
- **Trace:**

  > UsagesTool.invoke in src/vs/workbench/contrib/chat/browser/tools/usagesTool.ts calls getReferencesAtPosition and treats an empty array as authoritative absence. getReferencesAtPosition in src/vs/editor/contrib/gotoSymbol/browser/goToSymbol.ts invokes ReferenceProvider.provideReferences with a ReferenceContext containing only `includeDeclaration`; that contract is mirrored through src/vs/editor/common/languages.ts, src/vscode-dts/vscode.d.ts, and the main-thread/ext-host language-feature bridge. Consequently, the C/C++ extension cannot distinguish the UI and agent requests described in https://github.com/microsoft/vscode/issues/316783. The closed, unmerged workaround at https://github.com/microsoft/vscode-cpptools/pull/14457 shows that merely retaining all concurrent requests has undesirable UI behavior. Preserve compatibility for existing providers and avoid making the public API Copilot-specific; the uncertainty begins at the observable origin vocabulary and cancellation-result contract.
- **Open decisions:**
  - Should the extension-facing ReferenceContext expose a general invocation origin such as interactive UI versus programmatic/tool invocation, and which origins must be stable public values?
  - When a provider abandons a request because another reference request supersedes it, should cancellation propagate as an error/cancellation signal or as structured incomplete-result metadata rather than an empty array?
  - Should agent-originated reference requests suppress or isolate interactive progress and references UI, or is caller identity alone the intended contract for extensions to implement that behavior?
