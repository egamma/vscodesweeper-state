# Issue #43671 — "Download Now" button should respect the used installation method on Linux

[https://github.com/microsoft/vscode/issues/43671](https://github.com/microsoft/vscode/issues/43671)

## Summary

Keep open: current Linux update handling still does not distinguish deb, rpm, and tarball installations. The generic website fallback improves on the original tarball download, but does not deliver the accepted, community-supported installation-aware behavior.

## Change summary

Make Linux update notifications and download actions respect the running installation's packaging method.

## Best solution

Provide installation-aware update guidance for deb and rpm installations while retaining the archive download path for tarball users and existing Snap handling. Settle whether package-managed installations should receive actionable package-manager guidance or defer update notifications entirely to the package manager.

## Plan brief

- **Likely files:** `src/vs/platform/update/electron-main/updateService.linux.ts`, `src/vs/workbench/contrib/update/browser/update.contribution.ts`, `src/vs/code/electron-main/app.ts`
- **Validation:** On Linux, compare outdated deb, rpm, and extracted tarball installations: trigger an update check and invoke the offered action, verifying the agreed package-manager guidance or notification suppression for deb/rpm and the archive download behavior for tarballs. Include simultaneous package and tarball installations to verify attribution follows the running instance, and confirm existing Snap behavior remains unchanged.
- **Behavior:**

  > Linux update actions should reflect how the running VS Code instance was installed instead of treating all non-Snap installations alike. Package-managed deb/rpm installations should follow the maintainer-approved package-manager experience, while tarball installations retain an appropriate archive download action. Acceptance must cover simultaneous installations so an installed system package does not misclassify a separately running tarball. Automatic in-place tarball updates are outside this request.
- **Trace:**

  > DownloadUpdateAction in src/vs/workbench/contrib/update/browser/update.contribution.ts calls IUpdateService.downloadUpdate(true), which delegates through AbstractUpdateService to LinuxUpdateService.doDownloadUpdate. In src/vs/platform/update/electron-main/updateService.linux.ts that method explicitly does not detect package type and opens a generic product download URL, falling back to the update feed URL. src/vs/code/electron-main/app.ts already separates SnapUpdateService from the ordinary Linux service; preserve that behavior. update.mode can suppress checks but does not fulfill installation-aware guidance. The discussion on https://github.com/microsoft/vscode/issues/43671 supports this work but offers different observable outcomes for package-managed installations; diagnosis is sufficient to locate the gap, not to choose among those outcomes. https://github.com/microsoft/vscode/issues/158111 concerns automatic in-place updates and must not broaden this work.
- **Open decisions:**
  - For a running deb/rpm installation, should VS Code retain its update notification with package-manager instructions, or suppress its own notification and defer entirely to the package manager?
  - If notifications remain, should availability follow the VS Code release feed or wait until the installed package manager's configured repository offers the update?

## Evidence
