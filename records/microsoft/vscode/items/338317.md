# Issue #338317 — [Source control][Merge changes] Focus jumps to "Staged Changes" instead of the next conflicted file

[https://github.com/microsoft/vscode/issues/338317](https://github.com/microsoft/vscode/issues/338317)

## Summary

Freshly filed but the mechanism checks out in source: SCM resource identity encodes the owning group id, so moving a resource between groups (e.g. Merge Changes → Staged Changes on conflict resolution, or any stage/unstage) makes the tree treat it as a deleted+unrelated node, dropping semantic focus without restoring it to a sensible sibling; updateChildren() only special-cases the SCM input widget's focus, not tree focus/selection.

## Change summary

After resolving a merge conflict, keyboard focus jumps away from the Merge Changes list instead of moving to the next conflicted file.

## Best solution

In SCMViewPane.updateChildren() (src/vs/workbench/contrib/scm/browser/scmViewPane.ts), when the previously focused/selected element is removed from the tree due to a group change, explicitly restore focus/selection to the next remaining sibling in the same original group (falling back to the group header) instead of leaving focus wherever the AsyncDataTree's identity diffing happens to land it.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/scm/browser/scmViewPane.ts`
- **Validation:** A test (new or added to a new scm view test suite) that simulates a resource moving from one resource group to another while focused, then asserts the tree's focus/selection lands on the next sibling in the original group rather than being silently dropped.
- **Behavior:**

  > When a resource that is currently tree-focused/selected moves out of its resource group (most commonly: a merge-conflict file becomes staged after resolution, but this also applies to ordinary staging/unstaging), the SCM view should move focus/selection to the next remaining resource in the group the item left, instead of leaving focus in an arbitrary or unrelated location. If no sibling remains, fall back to the group header or nearest available element.
- **Trace:**

  > SCM resource identity (getSCMResourceId in scmViewPane.ts) embeds the owning resourceGroup.id, so a resource that changes group is a structurally different tree node to the identity-based diffing in AbstractTree (see onDidModelSplice in src/vs/base/browser/ui/tree/abstractTree.ts, which drops a focused node when no inserted node shares its id). SCMViewPane.updateChildren() calls tree.updateChildren() and only re-applies focus to the SCM input widget, never to tree elements, so nothing corrects the lost focus afterward. The fix should stay scoped to updateChildren()/the SCM view's own state tracking — do not change the identity provider (group scoping is needed elsewhere) or the generic AbstractTree splice/focus semantics, which are shared by many other trees.
- **Open decisions:**
  - Should the refocus behavior be scoped to conflict resolution specifically, or generalized to any resource moving between any two resource groups (e.g. plain stage/unstage)?
  - What should happen in Tree (folder) view mode versus List view mode, where 'next sibling' may mean different things?
  - If the group becomes empty, should focus move to the next group's first item, the group header, or be left cleared?

## Evidence

- **resource identity includes group id:** getSCMResourceId() in scmViewPane.ts (line ~849-852) returns `resource:${provider.id}/${group.id}/${uri}` — moving a resource to a different resource group (e.g. merge → index) changes its tree identity entirely.
- **focus dropped on identity mismatch:** src/vs/base/browser/ui/tree/abstractTree.ts onDidModelSplice() (~line 2468-2500): when a focused node's id is in deletedNodesIdSet and no insertedNode with the same id exists (true here, since group id differs), the node is simply omitted from the new focus set — semantic focus is lost, not intentionally reassigned.
- **no focus-restore handling in view:** SCMViewPane.updateChildren() (scmViewPane.ts ~1980-2000) explicitly restores focus for the SCM input widget after a tree refresh but has no equivalent logic for tree element focus/selection, so whatever ends up visually focused after the splice is incidental.
