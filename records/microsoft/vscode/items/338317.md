# Issue #338317 — [Source control][Merge changes] Focus jumps to "Staged Changes" instead of the next conflicted file

[https://github.com/microsoft/vscode/issues/338317](https://github.com/microsoft/vscode/issues/338317)

## Summary

Thanks for the report — this is a real gap: the SCM tree has no explicit logic to keep focus on the next conflicted file when a resource moves out of the Merge Changes group, so the generic tree's index-based focus preservation lands focus somewhere in Staged Changes instead. No maintainer signal or duplicate found yet, so keeping it open as a UX polish item rather than closing.

## Change summary

Resolving a merge conflict in the Source Control view moves focus into the Staged Changes group instead of to the next remaining conflicted file.

## Best solution

Add explicit focus-restoration logic in SCMViewPane's updateChildren path (src/vs/workbench/contrib/scm/browser/scmViewPane.ts) that, when the previously focused resource was in the Merge Changes group and has left it, re-focuses the next remaining resource in that same group rather than relying on the tree's default index-based focus trait.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/scm/browser/scmViewPane.ts`
- **Validation:** Manual check: with several files in Merge Changes, resolve/stage the first one and confirm focus lands on the next remaining item in Merge Changes (not Staged Changes); repeat until the group is empty.
- **Behavior:**

  > When a file is focused in the SCM view's Merge Changes group and the user resolves (stages) it, causing it to move to another group, focus should move to the next remaining file in the Merge Changes group rather than wherever the tree's default focus preservation happens to land. When Merge Changes becomes empty, some reasonable fallback (e.g. first item in Staged Changes, or the group header) should be chosen explicitly rather than incidentally.
- **Trace:**

  > SCMViewPane.updateChildren() (src/vs/workbench/contrib/scm/browser/scmViewPane.ts, ~line 1980) calls this.tree.updateChildren(), which triggers the generic ObjectTree/IndexTreeModel splice and its index/trait-based focus preservation in src/vs/base/browser/ui/tree/abstractTree.ts. There is no SCM-specific code capturing 'which group was the focused resource in' before the splice and re-targeting focus afterward — only the SCM input widget's focus is explicitly preserved (inputRenderer.getFocusedInput() check). Do not touch the generic abstractTree splice/focus-trait mechanism; the fix should stay scoped to SCMViewPane, capturing the focused element's group+position before refresh and restoring intent after. Related code: focusResourceGroup/focusNextResourceGroup (lines ~2095-2127) show the existing pattern for group-aware navigation that could be reused.
- **Open decisions:**
  - If the resolved file was the last one in Merge Changes, should focus move to the first item in Staged Changes, stay on the (now collapsed) group header, or do something else?
  - Should this new focus-restoration apply generally to any resource that changes group (e.g. staging/unstaging any file), or only specifically within the merge-conflict workflow?
  - Does this need to respect user-configured sort order within the group when picking the 'next' item?

## Evidence

- **no dedicated focus logic:** src/vs/workbench/contrib/scm/browser/scmViewPane.ts updateChildren() only preserves the focused SCM *input* widget (inputRenderer.getFocusedInput()); there is no logic that tracks or restores tree-node focus by resource group when the tree's children are spliced.
- **generic trait-based focus:** src/vs/base/browser/ui/tree/abstractTree.ts's list/tree splice logic preserves focus via index/trait remapping (see setFocus/focusTrait around lines 2200-2722), which naturally lands on whatever element now occupies a nearby index rather than a semantically 'next conflicted file' target — matching the reported jump into Staged Changes.
