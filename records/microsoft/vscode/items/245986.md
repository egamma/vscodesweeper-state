# Issue #245986 — Invalid extensions detected

[https://github.com/microsoft/vscode/issues/245986](https://github.com/microsoft/vscode/issues/245986)

## Summary

Keep open: a later report provides concrete evidence that VS Code deleted extension payloads still referenced by custom profiles, and current main retains the cleanup path capable of producing that outcome. This is also a team-authored, accepted Backlog bug, with no factual fix or verified duplicate supporting closure.

## Change summary

VS Code can mark and physically delete installed extensions that remain referenced by custom profiles, leaving those profiles with invalid extension entries.

## Best solution

Ensure extension cleanup never marks or deletes a payload while any profile associated with the extension store still references it, including when separate processes or user-data directories share that store. The ownership and isolation semantics of `--user-data-dir` versus the default extension directory should be settled before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/extensionManagement/node/extensionsWatcher.ts`, `src/vs/platform/extensionManagement/node/extensionManagementService.ts`, `src/vs/platform/environment/common/environmentService.ts`, `src/vs/platform/extensionManagement/test/node/extensionsScannerService.test.ts`
- **Validation:** Create an isolated regression scenario with user-data directories A and B sharing extension directory E: install an extension only in A's custom profile, initialize extension management under B, then restart A and assert that the payload is neither added to `E/.obsolete` nor deleted and remains loadable from A's profile.
- **Behavior:**

  > An extension payload referenced by any profile must remain installed and readable; starting another VS Code process must not invalidate that profile merely because the second process cannot see its profile registry. Validate with two isolated user-data directories sharing one extension directory: an extension referenced only by a custom profile in A must survive startup and cleanup activity from B. Existing uninstall behavior must continue deleting payloads once they are genuinely unreferenced.
- **Trace:**

  > The confirmed report at https://github.com/microsoft/vscode/issues/245986#issuecomment-5091706983 correlates physical deletion logs with persisted profile references. `ExtensionsWatcher.initialize()` in `src/vs/platform/extensionManagement/node/extensionsWatcher.ts` populates `allExtensions` from the current process's `IUserDataProfilesService.profiles`, scans the shared physical store, and marks everything outside that process-local union for deletion. `deleteExtensionsMarkedForRemoval()` in `src/vs/platform/extensionManagement/node/extensionManagementService.ts` later trusts the shared `.obsolete` ledger without revalidating profile references. `src/vs/platform/environment/common/environmentService.ts` resolves user-data and extension roots independently, so separate profile registries can address the same extension store. Preserve intentional extension uninstall and stale-version cleanup; the boundary is preventing one profile universe from deleting payloads owned by another.
- **Open decisions:**
  - Should an alternate `--user-data-dir` automatically receive an isolated extension root, or is sharing the default extension root an intentionally supported CLI contract?
  - If extension stores may be shared, what persisted ownership or reference contract must authorize physical deletion across user-data/profile registries?

## Evidence

- **confirmed impact:** https://github.com/microsoft/vscode/issues/245986#issuecomment-5091706983 reports 43 logged physical deletions and shows that every deleted payload remained referenced by at least one persisted custom-profile manifest; all 202 custom-profile-only payload directories were missing.
- **current source path:** On current main, `ExtensionsWatcher.initialize()` in `src/vs/platform/extensionManagement/node/extensionsWatcher.ts:47-51` builds its reference set only from `IUserDataProfilesService.profiles` and then calls `deleteExtensionsNotInProfiles`; lines 192-201 mark every physically installed extension absent from that process-local set for deletion.
- **deletion lacks profile revalidation:** `deleteExtensionsMarkedForRemoval()` in `src/vs/platform/extensionManagement/node/extensionManagementService.ts:961-997` reads the shared `.obsolete` ledger and deletes matching installed payloads without re-reading profile manifests or validating which user-data universe created the entry.
- **CLI namespace split:** `src/vs/platform/environment/common/environmentService.ts` resolves `--user-data-dir` and `--extensions-dir` independently, supporting the reported hypothesis that two user-data universes can operate against one physical extension store.
