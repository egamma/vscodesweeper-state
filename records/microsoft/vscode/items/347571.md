Confirm that retained memory does not grow with historical reload volume and that the renderer remains responsive without OOM.
- **Behavior:**

  > Opening an actively appended log file should display external updates without accumulating memory proportional to every historical reload. The reporter observes approximately 100 MB/s renderer growth followed by an OOM crash while the file is approximately 10 MB. First reproduce this on current main, measuring file size alongside retained renderer memory. Acceptance should distinguish necessary growth from the expanding file from retained obsolete content, while preserving reload correctness and responsiveness.
- **Trace:**

  > TextFileEditorModelManager.onDidFilesChange sends clean-model updates through queueModelReload, whose per-resource queue is already bounded. TextFileEditorModel.resolveFromFile reads content and resolveFromContent reaches doUpdateTextModel; TextEditorModel.updateTextEditorModel then calls ModelService.updateModel, which computes and pushes undoable edits. Source inspection confirms this route, not a retaining object or the reported growth rate. Preserve dirty-file protection and normal reload/undo behavior during diagnosis. Compare local and remote workloads before assigning the defect to transport or an extension. https://github.com/microsoft/vscode/issues/326812 is a related undo-retention lead with a materially different reproduction, not a verified canonical.
