## Evidence

- **Verified canonical:** https://github.com/microsoft/vscode/issues/344869 is open and reports that creating, deleting, and recreating a worktree through VS Code prevents it from reappearing until restart. Its reporter confirms git.detectWorktrees=true in https://github.com/microsoft/vscode/issues/344869#issuecomment-6483479187.
- **Shared lifecycle defect:** extensions/git/src/repository.ts:2268-2275 calls worktree.dispose() after successful deletion, while dispose() at lines 3656-3658 only disposes resources. Model.open in extensions/git/src/model.ts:764-766 listens for RepositoryState.Disposed; its cleanup at lines 865-876 removes the model entry and emits onDidCloseRepository. Direct repository disposal bypasses that cleanup.
- **Canonical symptom explained:** extensions/git/src/model.ts:600-606 returns without opening a repository when getRepositoryExact finds an existing entry. getRepositoryExact at lines 934-940 searches openRepositories without checking disposal. The stale entry left by deletion therefore also blocks discovery of a recreated worktree, connecting both reports to the same defect.
- **Unique evidence to retain:** This report supplies a Windows 1.145.0 reproduction involving Git: Fetch and Git: Create Branch, plus missing API close notifications. Model.pickRepository reads the stale collection at extensions/git/src/model.ts:898-905; commands.ts:3880-3884 can return before executing Git, whereas repository.ts:2889-2890 transitions to Disposed after NotAGitRepository.
- **Other candidates differ:** https://github.com/microsoft/vscode/issues/346024 concerns external deletion and persisted SCM visibility corruption; https://github.com/microsoft/vscode/issues/340112 concerns failed-spawn process-group termination. Neither is needed to explain the direct-disposal defect traced here.
