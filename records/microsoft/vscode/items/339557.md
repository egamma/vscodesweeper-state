# Issue #339557 — Copilot Chat `copilot_sessionStoreSql` tool blocks read-only queries whose string literals contain SQL keywords, with a misleading error message

[https://github.com/microsoft/vscode/issues/339557](https://github.com/microsoft/vscode/issues/339557)

## Summary

Confirmed from current main: the mutating-statement blocklist in sessionStoreSqlTool.ts tests the raw SQL string, so keywords inside quoted string literals (e.g. an ILIKE search term containing 'create') false-positive, and the shared error text falsely claims the query isn't a SELECT/WITH. This stays open — it's a real, well-diagnosed bug needing a design call on how to fix the false positive safely.

## Change summary

The copilot_sessionStoreSql tool blocks valid read-only SELECT/WITH queries whenever a string literal (e.g. an ILIKE search term) contains a blocklisted SQL keyword, and reports a misleading 'not a SELECT/WITH' error.

## Best solution

At minimum, give the blocklist check in extensions/copilot/src/extension/tools/node/sessionStoreSqlTool.ts its own error message (mirroring the existing blocked_mutating_sql vs blocked_not_select_or_with telemetry split) naming the matched keyword category; then decide, with a maintainer, whether to fix the literal false-positive via fail-closed literal stripping or parser-based classification so a regex can't be tricked into masking a real DROP/CREATE.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/tools/node/sessionStoreSqlTool.ts`, `extensions/copilot/src/extension/tools/node/test/sessionStoreSqlTool.spec.ts`
- **Validation:** A test asserting a query like `SELECT ... WHERE user_message ILIKE '%memory create%'` is NOT blocked, plus a test confirming an actual mutating statement (e.g. `DROP TABLE x`) is still blocked after the fix.
- **Behavior:**

  > A read-only SELECT/WITH query must not be rejected merely because a quoted string literal (e.g. an ILIKE search pattern) contains a word like 'create', 'drop', 'insert', etc. If a query IS rejected, the error message must correctly state the real reason (distinguishing 'contains a mutating keyword' from 'is not a SELECT/WITH statement') rather than always claiming the latter. Genuinely mutating statements (DROP TABLE, INSERT INTO, etc.) must remain blocked regardless of the fix.
- **Trace:**

  > In extensions/copilot/src/extension/tools/node/sessionStoreSqlTool.ts, `_invokeQuery` runs `BLOCKED_PATTERNS` (lines 28-39) against the raw `sql` string at lines 113-120, before the allowlist check at lines 124-131 — both branches return the identical error text. The allowlist check already has a precedent for literal-independent parsing via `stripLeadingCommentsAndWhitespace` (lines 42-51), but that only strips leading comments, not interior string literals. The boundary: do not relax detection of genuinely mutating statements outside string literals, and do not change the allowlist (SELECT/WITH-only) or multi-statement (`;`) checks. Where the uncertainty starts: whether to (a) ship distinct error messages only (trivial, doesn't fix the false positive), or (b) also strip/ignore quoted-string content before applying BLOCKED_PATTERNS, which requires getting '' doubling, backslash escapes, and DuckDB dollar-quoting right in both SQLite and cloud DuckDB dialects — an incorrect over-strip could let a real DROP/INSERT slip past the check, so the issue author explicitly recommends a maintainer-level call between a fail-closed stripper and parser/engine-based enforcement (SQLite already has setAuthorizer; cloud DuckDB enforcement would need a server-side read-only guarantee).
- **Open decisions:**
  - Should the false-positive fix ship now (distinguish mutating-keyword literals from real mutating statements), or only the error-message clarity fix, deferring the literal-parsing fix to a follow-up?
  - If fixing the false positive: fail-closed literal-stripping regex (reject on any ambiguity) or parser/engine-based classification (e.g. SQLite setAuthorizer locally, server-side read-only enforcement for cloud DuckDB)?
  - Is the local SQLite engine-level enforcement (setAuthorizer) already sufficient as the real boundary, making the client-side regex blocklist purely a UX/early-feedback layer whose false positives can be tolerated if messaging is clear?
