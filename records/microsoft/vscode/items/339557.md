# Issue #339557 — Copilot Chat `copilot_sessionStoreSql` tool blocks read-only queries whose string literals contain SQL keywords, with a misleading error message

[https://github.com/microsoft/vscode/issues/339557](https://github.com/microsoft/vscode/issues/339557)

## Summary

Confirmed on main: the blocklist in sessionStoreSqlTool.ts tests the raw SQL string (including quoted literals), so a read-only SELECT with a keyword like `create`/`drop`/`alter` inside an `ILIKE`/string literal is rejected, and both the blocklist and allowlist rejections emit the identical misleading 'Only SELECT or WITH' message even though telemetry already distinguishes the two cases.

## Change summary

The copilot_sessionStoreSql tool blocks valid read-only SELECT/WITH queries whose string literals happen to contain blocklisted SQL keywords, and reports a misleading 'not a SELECT/WITH' error either way.

## Best solution

Split the blocked-keyword and not-select-or-with error messages (cheap, safe, matches existing telemetry discriminators 'blocked_mutating_sql' vs 'blocked_not_select_or_with'); separately decide, with a maintainer, whether/how to stop scanning quoted string literals without weakening the security boundary (parser-based classification vs. fail-closed literal stripping).

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/tools/node/sessionStoreSqlTool.ts`, `extensions/copilot/src/extension/tools/node/test/sessionStoreSqlTool.spec.ts`
- **Validation:** A test in sessionStoreSqlTool.spec.ts asserting that a SELECT query with a blocklisted keyword inside a quoted string literal (e.g. `SELECT ... WHERE user_message ILIKE '%create%'`) is not blocked, while a true mutating statement (bare `DROP TABLE ...`) is still blocked and reports blocked_mutating_sql distinctly from a genuinely non-SELECT statement.
- **Behavior:**

  > A read-only SELECT/WITH query whose string literals (e.g. an ILIKE search pattern) merely contain a word like 'create', 'drop', or 'alter' must execute normally, not be rejected. A query that is genuinely mutating (e.g. actual `DROP TABLE`) must still be blocked, with an error message that correctly identifies it as a blocked keyword rather than falsely claiming the query isn't a SELECT/WITH. A query that truly isn't a SELECT/WITH gets its own distinct, accurate error message.
- **Trace:**

  > BLOCKED_PATTERNS (sessionStoreSqlTool.ts lines 28-41) and the check at lines 114-121 run regex tests against the full raw `sql` string, not a literal-stripped version, so keywords inside quoted string literals false-positive. Lines 116-119 and 126-130 return the exact same error text for two already-distinguished telemetry outcomes ('blocked_mutating_sql' vs 'blocked_not_select_or_with'), which the reporter traced as the direct cause of a multi-retry loop. The boundary: do not weaken the mutating-statement blocklist itself (it is a defense-in-depth layer on top of engine-level read-only enforcement per the issue's own analysis) — any literal-stripping must agree with the query engine's own escaping/quoting rules (`''` doubling, backslash escapes, DuckDB dollar-quoting) or fail closed (treat ambiguous input as still blocked), never silently let a real mutating statement through. Where the uncertainty starts: whether to ship only the trivial distinct-message fix first, or also implement literal-aware classification in the same pass, and how conservative the literal-stripping must be to avoid becoming a bypass vector.
- **Open decisions:**
  - Should the distinct-error-message fix ship on its own first, or bundled with the literal-awareness fix for the false positive?
  - For literal-aware classification, is parser-based tokenization required, or is a carefully fail-closed regex-based literal stripper acceptable given this is a defense-in-depth layer over engine-level read-only enforcement?
  - How much detail should the improved error message expose (e.g. which keyword/category) without helping a would-be adversary probe the filter's edges?

## Evidence

- **blocklist tests raw SQL:** extensions/copilot/src/extension/tools/node/sessionStoreSqlTool.ts lines 28-41 (BLOCKED_PATTERNS) and the loop at lines 114-121 call `pattern.test(sql)` against the full raw query string, with no literal-stripping, so `SELECT ... WHERE user_message ILIKE '%memory create%'` matches `/\b(INSERT|UPDATE|DELETE|DROP|CREATE|ALTER|TRUNCATE|REPLACE)\b/i` via the literal's `create`.
- **identical error message:** Lines 116-119 (blocked_mutating_sql) and 126-130 (blocked_not_select_or_with) both return the literal string 'Error: Blocked SQL statement. Only SELECT or WITH queries are allowed.' even though they are distinct telemetry outcomes, confirming the reporter's claim that the message is misleading for a query that IS a SELECT.
- **related but distinct issues:** Reporter cites https://github.com/microsoft/vscode/issues/317358 (error-rate tracking, not this false-positive class) and the closed https://github.com/microsoft/vscode/issues/317355 (schema hallucination, a different failure mode) — neither is a duplicate of this report.
