# Issue #335200 — Co-author Profile Picture Not  Displaying in Source Control Panel

[https://github.com/microsoft/vscode/issues/335200](https://github.com/microsoft/vscode/issues/335200)

## Summary

Confirmed from source: the Git hover only renders an avatar image for the primary commit author; co-authors are always shown with a generic `$(account)` icon, with no avatar lookup attempted for them at all.

## Change summary

When hovering a commit with a `Co-authored-by` trailer in the Source Control panel, the co-author's GitHub profile picture never appears, only a placeholder account icon.

## Best solution

Extend the avatar-resolution pipeline (currently keyed per commit hash in extensions/github's provideAvatar) to also resolve co-author emails, and thread that avatar into hover.ts's co-author rendering branch instead of always using the `$(account)` icon.

## Plan brief

- **Likely files:** `extensions/git/src/hover.ts`, `extensions/git/src/git.ts`, `extensions/github/src/historyItemDetailsProvider.ts`
- **Validation:** A hover.ts unit test asserting a co-author with a resolved avatar renders an image markdown instead of `$(account)`, once the avatar plumbing exists.
- **Behavior:**

  > Hovering a commit that has one or more `Co-authored-by` trailers should show each co-author's GitHub avatar image (same size/style as the primary author's), when it can be resolved, instead of the generic `$(account)` icon. Primary-author avatar rendering is unaffected. Acceptance: a commit with a known co-author email shows an avatar image in the hover; an unresolvable co-author email falls back to the current `$(account)` icon.
- **Trace:**

  > extensions/git/src/hover.ts's appendContent() only accepts a single `authorAvatar` string and never receives per-co-author avatar data; CoAuthor (extensions/git/src/git.ts:770) has no avatar field. extensions/github/src/historyItemDetailsProvider.ts's provideAvatar() resolves exactly one avatar per commit hash from the primary author's email/name (line ~147) via a GraphQL/REST lookup and a repositoryStore.users cache — it has no notion of resolving multiple emails per commit. The boundary: do not change the primary-author avatar path or the existing per-hash avatar cache keying; any extension needs a new lookup keyed by (hash, co-author email) or similar, and must consider added API calls for repos with many co-authored commits.
- **Open decisions:**
  - Should co-author avatars be resolved via the same GitHub API path as the primary author (with the added API-call cost), and should that be gated by the existing 'showAvatar' setting?
  - How should resolution results be keyed/cached when a commit has multiple co-authors (one avatar map entry per hash today)?
