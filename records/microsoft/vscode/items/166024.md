# Issue #166024 — Cursor selection scroll down not working when status bar is hidden and in full screen mode

[https://github.com/microsoft/vscode/issues/166024](https://github.com/microsoft/vscode/issues/166024)

## Summary

The fullscreen edge case remains present on current main: vertical drag scrolling starts only after the pointer moves beyond the editor, which is impossible at the bottom display boundary when the status bar is hidden. No open canonical issue or fixing commit was found.

## Change summary

Dragging a text selection downward cannot auto-scroll when a fullscreen editor with a hidden status bar reaches the physical bottom of the macOS display.

## Best solution

Define an editor-edge activation rule that permits downward selection auto-scroll when the pointer cannot move beyond the viewport, while avoiding unwanted scrolling during ordinary selection of the last visible line.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/mouseHandler.ts`, `src/vs/editor/browser/controller/dragScrolling.ts`
- **Validation:** Launch the Electron workbench on macOS, hide the status bar, enter native fullscreen, and drag a selection against the bottom display edge; verify that the editor scrolls and extends the selection while ordinary selection at the last visible line does not begin scrolling prematurely.
- **Behavior:**

  > In native macOS fullscreen with the status bar hidden, holding a downward text-selection drag at the physical bottom of the display must continue scrolling the editor and extending the selection. Selection behavior away from the constrained display edge must remain unchanged, including selecting text on the last visible line without unintended scrolling. Validate both the reported fullscreen configuration and a normal window with space below the editor.
- **Trace:**

  > MouseDownOperation._onMouseDownThenMove in src/vs/editor/browser/controller/mouseHandler.ts starts TopBottomDragScrolling only when _findMousePosition returns an OUTSIDE_EDITOR target. _getPositionOutsideEditor creates the lower outside target only when `e.posy` is greater than the editor's bottom coordinate; with the editor flush against the physical screen bottom, the pointer cannot enter that region. TopBottomDragScrollingOperation in src/vs/editor/browser/controller/dragScrolling.ts handles continuous scrolling once activated, so the uncertainty begins at how the bottom-edge gesture should be classified without changing ordinary in-editor selection. Commit 69b857be534f26586c9290374c90be9026d3898a addresses a different end-of-document edge case and does not remove this activation constraint.
- **Open decisions:**
  - Should downward auto-scroll activate on the editor's final pixel row, within a small edge zone, or only when the editor is known to be flush with the display boundary?
  - How should the activation rule distinguish an intentional scroll hold from ordinary selection on the last visible line?

## Evidence

- **confirmed report:** The reporter supplied a fullscreen reproduction video in https://github.com/microsoft/vscode/issues/166024#issuecomment-1328001778 after the initial non-fullscreen attempt did not reproduce.
- **current source:** In src/vs/editor/browser/controller/mouseHandler.ts, MouseDownOperation._getPositionOutsideEditor recognizes the lower boundary only when `e.posy > editorContent.y + editorContent.height`; _onMouseDownThenMove starts TopBottomDragScrolling only for the resulting OUTSIDE_EDITOR target. At a physical screen boundary the pointer cannot cross that threshold.
- **drag-scroll path:** src/vs/editor/browser/controller/dragScrolling.ts still requires an outside-editor target to create TopBottomDragScrollingOperation; the later commit 69b857be534f26586c9290374c90be9026d3898a fixes selection behavior after scrolling reaches the document boundary, not activation at the display boundary.
- **canonical search:** Keyword and semantic searches across open and closed microsoft/vscode issues found no issue that owns this fullscreen, hidden-status-bar selection-scroll edge case.
