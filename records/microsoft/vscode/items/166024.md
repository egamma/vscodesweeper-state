# Issue #166024 — Cursor selection scroll down not working when status bar is hidden and in full screen mode

[https://github.com/microsoft/vscode/issues/166024](https://github.com/microsoft/vscode/issues/166024)

## Summary

The full-screen reproduction remains valid on current main: downward selection auto-scroll starts only after the pointer is classified outside the editor, which cannot happen when the editor reaches the physical bottom of the display. The issue was explicitly accepted as a bug after the reporter clarified the full-screen condition and should remain open in editor-core.

## Change summary

Dragging a text selection downward does not auto-scroll when macOS full-screen mode and a hidden status bar place the editor at the bottom edge of the display.

## Best solution

Make editor selection auto-scroll engage at the lower viewport boundary even when the pointer cannot physically move outside the window, while preserving existing speed and behavior when dragging beyond an ordinary editor boundary.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/mouseHandler.ts`, `src/vs/editor/browser/controller/dragScrolling.ts`, `src/vs/editor/browser/controller/mouseTarget.ts`
- **Validation:** On macOS, launch Code OSS with a long text file, enter full-screen mode, hide the status bar, and drag a selection downward against the physical bottom edge; the document must continue scrolling and extending the selection. Repeat with the status bar visible and with upward dragging to confirm existing behavior is unchanged.
- **Behavior:**

  > In a full-screen editor whose content reaches the physical bottom of the display, holding a downward mouse drag at the viewport edge must continue scrolling the document and extending the text selection. The behavior should match selection dragging beyond an editor edge when window geometry leaves room for the pointer to move outside. Existing upward selection scrolling and ordinary non-full-screen dragging must remain unchanged.
- **Trace:**

  > The reporter's full-screen video at https://github.com/microsoft/vscode/issues/166024#issuecomment-1328001778 established the condition, after which a maintainer classified the issue as a bug. On current main, `MouseDownOperation._onMouseDownThenMove` in src/vs/editor/browser/controller/mouseHandler.ts starts `TopBottomDragScrolling` only for `MouseTargetType.OUTSIDE_EDITOR`. `TopBottomDragScrollingOperation._execute` in src/vs/editor/browser/controller/dragScrolling.ts performs the repeated scrolling only after that transition. When the editor is flush with the physical screen bottom, the pointer cannot move below the editor, leaving the operation unstarted. Preserve normal outside-editor scrolling speed, horizontal drag scrolling, and upward selection behavior; the validation gap is how best to exercise this geometry-dependent pointer path reliably.

## Evidence

- **confirmed reproduction:** The reporter supplied a full-screen video in https://github.com/microsoft/vscode/issues/166024#issuecomment-1328001778 after the initial non-reproduction; the editor maintainer then removed `info-needed`, applied `bug`, and scheduled the issue before it eventually moved to On Deck.
- **current source path:** In src/vs/editor/browser/controller/mouseHandler.ts, `MouseDownOperation._onMouseDownThenMove` starts `TopBottomDragScrolling` only when the target type is `MouseTargetType.OUTSIDE_EDITOR` and its position is above or below. An editor flush with the physical screen bottom cannot receive a pointer position below that boundary, so this path never starts.
- **scroll implementation:** src/vs/editor/browser/controller/dragScrolling.ts implements continued downward movement in `TopBottomDragScrollingOperation._execute`, but that operation is constructed only after the outside-editor transition; there is no current near-edge trigger covering the reported full-screen case.
- **later corroboration:** https://github.com/microsoft/vscode/issues/238295 independently reported the same behavior on macOS and Windows in 2025. It was closed only through the low-upvote feature-request lifecycle, not by a fix, and therefore is neither a canonical open duplicate nor evidence that this accepted bug was resolved.
