# Issue #208400 — Inconsistent behavior of Explorer when copying/moving file into folder with filename already present

[https://github.com/microsoft/vscode/issues/208400](https://github.com/microsoft/vscode/issues/208400)

## Summary

Still valid on current main: the four Explorer conflict paths (DnD move, DnD copy, cut+paste, copy+paste) are implemented in two different places with different conflict strategies, so the inconsistency the reporter and a maintainer confirmed persists; keep open and let an owner decide the intended unified behavior.

## Change summary

Explorer handles a name collision differently for drag-and-drop move (replace prompt), drag-and-drop/keyboard copy (silent " copy" suffix), and cut+paste (a hard error notification).

## Best solution

Unify conflict handling for Explorer move/copy across the drag-and-drop handler (explorerViewer.ts) and the paste command (fileActions.ts) — at minimum give cut+paste the same overwrite-confirmation flow that doHandleExplorerDropOnMove already has, and decide whether cross-folder copy should prompt instead of silently incrementing the name.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/fileActions.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`
- **Validation:** A files-contrib test (or explicit manual steps covering all four paths) asserting that move-with-collision via cut+paste produces the same overwrite confirmation as drag-and-drop move rather than a FILE_MOVE_CONFLICT error notification.
- **Behavior:**

  > Moving or copying a file in the Explorer onto a folder that already contains a file of that name should behave the same whether the user drags, uses Ctrl+X/Ctrl+V, Ctrl+C/Ctrl+V, or the context menu. Today drag-move prompts 'replace?', cut+paste fails with an error toast, and both copy paths silently create a '<name> copy.ext' file. Acceptance: the four flows produce one agreed outcome for a cross-folder collision, the existing `explorer.incrementalNaming` setting values ('simple' | 'smart' | 'disabled') keep working, and same-folder copy still produces the incremented name.
- **Trace:**

  > Two independent implementations diverge. Drag-and-drop lives in FileDragAndDrop in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts: `doHandleExplorerDropOnMove` catches FileOperationResult.FILE_MOVE_CONFLICT and re-applies the bulk edit with `overwrite: true` after getMultipleFilesOverwriteConfirm, while `doHandleExplorerDropOnCopy` routes through `findValidPasteFileTarget`. The paste command in src/vs/workbench/contrib/files/browser/fileActions.ts also calls `findValidPasteFileTarget`, whose loop (`while (true && !fileToPaste.allowOverwrite)`) appends `incrementFileName` suffixes for copies; for a cut it sets `allowOverwrite: pasteShouldMove`, skipping the loop, and builds a ResourceFileEdit with `overwrite: incrementalNaming === 'disabled'`, so fileService.ts:944 throws and the catch block merely calls notificationService.error — there is no conflict-confirmation path on the paste side. Boundary: do not change the `explorer.incrementalNaming` setting contract or same-folder copy naming, and do not alter FileService move/copy semantics. Maintainer confirmation on 1.96: https://github.com/microsoft/vscode/issues/208400#issuecomment-2547261398
- **Open decisions:**
  - For a cross-folder collision, should all four flows prompt 'replace?' (the drag-move behavior), or should move prompt while copy keeps auto-incrementing?
  - Should the " copy" suffix remain the default when source and target folders differ, given it silently produces a file whose contents differ from the existing one?
  - If cut+paste gains a prompt, does `explorer.incrementalNaming: 'disabled'` still mean 'ask to overwrite', and how do the setting's three values map onto the unified behavior?

## Evidence

- **DnD move prompts:** src/vs/workbench/contrib/files/browser/views/explorerViewer.ts `doHandleExplorerDropOnMove` catches FileOperationResult.FILE_MOVE_CONFLICT and shows getMultipleFilesOverwriteConfirm before retrying with `overwrite: true`.
- **copy increments silently:** Both DnD copy (`doHandleExplorerDropOnCopy`, explorerViewer.ts ~line 1953) and paste (fileActions.ts ~line 1204/1244) call `findValidPasteFileTarget`, whose while-loop calls `incrementFileName` to append " copy" whenever the candidate exists (fileActions.ts lines 321-353), regardless of whether source and target folder differ.
- **cut+paste errors:** In the paste handler, `allowOverwrite: pasteShouldMove || incrementalNaming === 'disabled'` skips the increment loop for a cut, and the move edit is created with `overwrite: incrementalNaming === 'disabled'` — so fileService throws 'Unable to move/copy ... already exists at destination.' (src/vs/platform/files/common/fileService.ts:944) and it is surfaced via notificationService.error with no overwrite prompt.
