# Issue #202324 — scroll behavior in editor is different compared to native scrolling on macOS or other websites on chrome

[https://github.com/microsoft/vscode/issues/202324](https://github.com/microsoft/vscode/issues/202324)

## Summary

Keep open: multiple users report that editor trackpad scrolling on macOS has a different acceleration/deceleration curve from native scrolling, including a detailed 120 Hz investigation. The team-authored issue remains a valid investigation, and the recent Electron overscroll support addresses bounce behavior rather than conclusively fixing delta calculation or acceleration.

## Change summary

Make editor trackpad scrolling on macOS match the precision, acceleration, and deceleration characteristics of native macOS and Chrome scrolling.

## Best solution

Measure raw wheel-event deltas and the editor scroll pipeline on current Electron across 60 Hz and 120 Hz macOS displays, separate Chromium event-generation defects from VS Code delta processing, and either correct the editor path or track the confirmed Chromium/Electron defect upstream.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/scrollbar/scrollableElement.ts`, `src/vs/base/common/scrollable.ts`, `src/vs/editor/browser/config/editorOptions.ts`
- **Validation:** On current macOS hardware, record identical slow precision gestures and fast trackpad throws in a native Chromium scroll container and the VS Code editor at both 60 Hz and 120 Hz; compare raw wheel deltas, resulting scroll distance, monotonic deceleration, and stopping behavior.
- **Behavior:**

  > Trackpad scrolling in the editor on macOS should preserve pixel-level control during slow gestures while retaining native-style acceleration for fast throws. Deceleration should feel continuous and should not continue gliding after the corresponding native scroll has effectively stopped. Acceptance requires side-by-side recorded measurements against a native Chromium scroll container on current Electron, covering both 60 Hz and 120 Hz displays.
- **Trace:**

  > The report distinguishes the editor's acceleration curve from a simple delta multiplier: changing the multiplier trades precision against long-distance movement and cannot match both ends of native behavior. A later independent report supplies 120 Hz measurements, while the newest comment points to Electron's `webPreferences.scrollBounce`; bounce/elasticity is a related but separate observable behavior from wheel delta acceleration and deceleration. Trace wheel input through `src/vs/base/browser/ui/scrollbar/scrollableElement.ts` and `src/vs/base/common/scrollable.ts`, including editor scroll settings in `src/vs/editor/browser/config/editorOptions.ts`, then compare the raw browser events with the resulting editor movement. Do not broaden the work to notebook restoration or general input latency, and do not treat enabling elastic overscroll as proof that the acceleration defect is resolved.
- **Open decisions:**
  - Should matching native macOS behavior include elastic overscroll, or should this issue remain limited to acceleration, precision, deceleration, and stopping distance?
  - If native acceleration cannot be reproduced consistently across Chromium and Safari, which browser-native behavior is the compatibility target for the editor?
