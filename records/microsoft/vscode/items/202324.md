The report remains open and has independent confirmation that macOS trackpad scrolling diverges from native acceleration behavior, especially on 120 Hz displays and in Safari. As a team-authored issue with no verified fixing commit or canonical duplicate, it should remain open for editor scrolling investigation.

## Change summary

Make editor trackpad scrolling on macOS match native acceleration, precision, and deceleration behavior more closely.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/scrollbar/scrollableElement.ts`, `src/vs/base/common/scrollable.ts`, `src/vs/editor/browser/viewParts/scrollDecoration/scrollDecoration.ts`
- **Validation:** Capture identical slow precision gestures and high-velocity trackpad throws on a 120 Hz macOS device in VS Code, Chrome, and Safari; compare wheel delta sequences and resulting editor displacement, and verify that any change improves acceleration and stopping behavior without regressing mouse-wheel scrolling or non-macOS input.
- **Behavior:**

  > On macOS, editor scrolling from a trackpad should preserve both pixel-level control during slow gestures and native-like acceleration during fast gestures, without requiring users to trade one for the other through a fixed multiplier. Momentum should decelerate predictably rather than jiggle or continue after the gesture feels complete. Acceptance requires comparison against native/browser behavior using captured event and displacement data on a 120 Hz MacBook, while confirming ordinary mouse-wheel behavior remains unchanged.
- **Trace:**

  > The issue concerns the path from browser wheel events through VS Code's scrollable element and scroll model, with likely entry points in src/vs/base/browser/ui/scrollbar/scrollableElement.ts and src/vs/base/common/scrollable.ts. The original report describes an acceleration-curve mismatch rather than only a constant speed difference; a later commenter independently reports deltaY jiggle on a 120 Hz MacBook and Safari. Chromium/Electron event generation is a plausible boundary, and the 2026 comment identifies newer native overscroll support, but overscroll elasticity is not itself proof that acceleration and deceleration are fixed. The investigation must preserve non-trackpad and non-macOS scrolling semantics and distinguish raw upstream event behavior from transformations performed by VS Code.
- **Open decisions:**
  - Do captured raw wheel events already contain the non-native acceleration and non-monotonic deceleration, making this an Electron/Chromium-owned defect, or does VS Code's normalization introduce it?
  - Should native overscroll elasticity be evaluated as part of this issue, or tracked separately from the acceleration-curve mismatch?
  - If VS Code compensation is needed, should it apply only to macOS precision-trackpad input or to browser-hosted scrolling more broadly?
