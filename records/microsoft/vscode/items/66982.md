# Issue #66982 — Clear all problems in the 'Problems' pane with a button

[https://github.com/microsoft/vscode/issues/66982](https://github.com/microsoft/vscode/issues/66982)

## Summary

Keep open: current Problems controls filter or collapse entries but do not provide the requested cross-provider clear action. This accepted Backlog request has substantial demand, and the related task-only issue does not absorb its broader scope.

## Change summary

Provide a Problems-pane action to clear accumulated diagnostics from tasks and language or extension providers without restarting VS Code.

## Best solution

Design a user-triggered clearing action in the Problems view with explicit diagnostic-provider synchronization and republishing semantics. Coordinate task-generated diagnostics with the related task-only request without silently desynchronizing extension-owned diagnostic collections.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/markers/browser/markers.contribution.ts`, `src/vs/workbench/contrib/markers/browser/markersView.ts`, `src/vs/platform/markers/common/markerService.ts`, `src/vs/workbench/api/browser/mainThreadDiagnostics.ts`, `src/vs/workbench/api/common/extHostDiagnostics.ts`, `src/vs/workbench/contrib/tasks/common/problemCollectors.ts`
- **Validation:** After choosing the contract, validate with a diagnostic-producing extension that retains a collection and publishes incremental updates, alongside a task with a problemMatcher: populate Problems, invoke the clearing action without restarting or rerunning either producer, then publish changed and new diagnostics. Verify the agreed dismissal/republishing behavior, consistency between the Problems view and diagnostic APIs, and unchanged normal provider-driven cleanup.
- **Behavior:**

  > Users want a Problems-pane action that removes accumulated entries without reloading the window, restarting the Extension Host, or rerunning builds. The request includes both task problemMatcher diagnostics and language or extension diagnostics; source filtering is not equivalent. Acceptance must cover clearing existing entries and the behavior of subsequent diagnostic updates, including incremental updates from providers. The product contract must first settle whether clearing dismisses the current display or resets diagnostic state, and when unchanged diagnostics may reappear.
- **Trace:**

  > Problems actions are registered in src/vs/workbench/contrib/markers/browser/markers.contribution.ts; the existing clear command clears filter text only. MarkerService.remove in src/vs/platform/markers/common/markerService.ts removes owner/resource entries, while DiagnosticCollection in src/vs/workbench/api/common/extHostDiagnostics.ts keeps independent producer-side state and synchronizes through MainThreadDiagnostics. Task collectors in src/vs/workbench/contrib/tasks/common/problemCollectors.ts also retain marker and cleanup bookkeeping. https://github.com/microsoft/vscode/issues/50448#issuecomment-456745547 documents the incremental-update synchronization concern, and https://github.com/microsoft/vscode/issues/50448#issuecomment-504309962 identifies this issue as the general clearing tracker. https://github.com/microsoft/vscode/issues/77214 owns the narrower task-only request, not this full capability. Preserve normal provider-driven diagnostics, inter-file reporting and task cleanup; unrelated stale-diagnostic producer bugs are not evidence that a global clear action already exists.
- **Open decisions:**
  - Should Clear All dismiss the currently displayed diagnostics while retaining provider state, or reset diagnostic state across the workbench and originating providers?
  - When a producer next updates diagnostics, should unchanged dismissed entries reappear immediately, only after explicit refresh, or only when their diagnostic content changes?
  - Must the initial action cover every producer, or may unsupported providers remain uncleared with an explicit explanation?
