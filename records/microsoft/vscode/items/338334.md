# Issue #338334 — Failed Automation session cannot be reopened after restart

[https://github.com/microsoft/vscode/issues/338334](https://github.com/microsoft/vscode/issues/338334)

## Summary

Fresh, well-diagnosed bug report — the described restore-miss path and exact error message match current main precisely — reporting a session-list zombie state after a specific first-turn-failure race. No fix exists yet, so this stays open for design and implementation.

## Change summary

A failed Automation session whose first turn fails right after chat materialization but before SDK metadata persistence becomes permanently listed but unopenable once Agent Host restarts.

## Best solution

A maintainer should choose between the two proposed directions (keep the session provisional until provider backing is durable, vs. let persisted Agent Host metadata restore a registered failed session when SDK metadata is absent) before an agent implements the fix in copilotAgent.ts / agentService.ts's restore path.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/platform/agentHost/node/agentService.ts`, `src/vs/platform/agentHost/node/agentSideEffects.ts`
- **Validation:** A restore-path test that materializes a chat, simulates a first-turn failure before SDK metadata is written, restarts/reopens the session, and asserts it either shows its recorded error or is removed rather than throwing the transient-provider error indefinitely.
- **Behavior:**

  > When an Automation session's first turn fails after chat materialization but before the SDK persists restorable session metadata, reopening that session after an Agent Host restart must not permanently fail with a 'provider not ready' error. Instead it should either reopen showing the recorded failure, or be removed from the session list if no durable session was ever created. Acceptance: a restore attempt against such a session no longer throws JSON_RPC_INTERNAL_ERROR indefinitely, and the session list does not retain an unopenable entry forever.
- **Trace:**

  > Root cause per reporter and confirmed against src/vs/platform/agentHost/node/agentService.ts: CopilotAgent's onDidMaterializeChat fires before first-turn preflight completes; _onDidMaterializeChat (~line 5519) then clears the provisional marker and marks the session ready. If the first turn then fails before the SDK writes durable session metadata, a later restore's _restoreSessionState (~lines 7833-7865) finds getChatMetadata() returns undefined for a session no longer marked provisional and not readable from the provider, so it throws the transient 'provider not ready' error forever — while orphan reconciliation correctly refuses to discard the session because it holds a local failed turn. The boundary: do not change orphan reconciliation's refusal to discard sessions containing turns, and do not weaken the general provisional/materialize sequencing for the successful case. Related: https://github.com/microsoft/vscode/issues/335928 (cited by reporter as the current trigger).
- **Open decisions:**
  - Should a session in this state reopen and display its recorded failure (keep it listed, degrade gracefully), or should it be silently removed from the list when no durable backend session was ever created?
  - Should materialization only clear the provisional marker once the SDK has confirmed durable metadata exists (delaying 'ready' status), or should restore instead be taught to reconstruct a minimal state purely from locally persisted Agent Host metadata when SDK metadata is absent?

## Evidence

- **restore-miss path confirmed:** src/vs/platform/agentHost/node/agentService.ts:7838-7864 (_restoreSessionState) throws the exact reported error 'Provider ... is not ready to open ...; it may still be starting, so try again shortly' via a ProtocolError(JSON_RPC_INTERNAL_ERROR) when getChatMetadata misses but the session is known to the registry — matching the reporter's trace precisely.
- **materialize-before-persist ordering:** _onDidMaterializeChat (agentService.ts:5519) clears the provisional marker (_clearSessionProvisional) and marks the session persisted/ready as soon as the provider fires onDidMaterializeChat, independent of whether the SDK has actually written restorable metadata yet — consistent with the reported root cause.
- **related trigger:** Reporter cites https://github.com/microsoft/vscode/issues/335928 as the current trigger for the permission-mode race; not verified as fixed/open here.
