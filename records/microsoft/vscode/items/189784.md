# Issue #189784 — [Accessibility] problems.decorations.enabled setting must equally benefit screen reader users

[https://github.com/microsoft/vscode/issues/189784](https://github.com/microsoft/vscode/issues/189784)

## Summary

The Explorer still gives its accessible tree rows only the file name, while problem decorations update a child label that does not supply the row's accessible name. Keep this reopened issue open: the original merged PR predates the reopen and does not resolve that remaining path.

## Change summary

Make Explorer error and warning decorations available to screen reader users, including changes to diagnostic state.

## Best solution

Expose current problem information through the Explorer's actual accessible row and compact-folder navigation targets without requiring a full tree refresh. Establish the folder announcement and optional audio-signal behavior before extending shared decoration infrastructure.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/browser/labels.ts`, `src/vs/workbench/contrib/markers/browser/markersFileDecorations.ts`, `src/vs/workbench/services/decorations/browser/decorationsService.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Add browser regression tests asserting the actual Explorer treeitem accessible name contains the agreed problem information on initial render and after diagnostics are added, changed and cleared, without creating or deleting files. Cover compact folders and bubbled folder decorations. Manually navigate those cases with NVDA or JAWS and verify the agreed announcements and any approved signals.
- **Behavior:**

  > With problems.decorations.enabled enabled, screen reader users navigating Explorer must receive the problem information represented by file and folder decorations. That information must remain accurate when diagnostics change, without requiring filesystem changes or an Explorer refresh. Ordinary file names, tree levels, selection and compact-folder navigation must remain intact. Acceptance includes accessible-name assertions for initial and changing diagnostics, plus screen-reader navigation through files and folders.
- **Trace:**

  > ExplorerView supplies FilesRenderer as its accessibility provider, whose getAriaLabel currently returns only element.name; AccessibiltyRenderer in listWidget.ts applies that string to the accessible row. ResourceLabels independently handles decoration changes and updates the child IconLabel's title and aria-label, leaving the parent row unchanged. Compact-folder navigation assigns separate name-only labels in CompressedNavigationController.updateLabels. MarkersDecorationsProvider provides counts and severity-dependent colors, while DecorationsService replaces bubbled folder tooltips with generic text, so forwarding existing tooltip text alone does not establish severity/count parity everywhere. The thread explicitly identifies other decoration-consuming trees; preserve their existing behavior and avoid full-tree rerenders. The insufficient original attempt is https://github.com/microsoft/vscode/pull/189856, merged before the issue reopened; no runtime validation was performed during this read-only review.
- **Open decisions:**
  - For folders containing problems, should the spoken decoration identify descendant problems generically or report their error/warning severities and aggregate counts?
  - Should navigating decorated Explorer items also play error/warning accessibility signals, or should this change provide spoken problem information without additional sounds?
