# Issue #295305 — Source Control Graph fails to refresh when git.autorefresh is false

[https://github.com/microsoft/vscode/issues/295305](https://github.com/microsoft/vscode/issues/295305)

## Summary

Keep open: current source confirms that the Graph refresh action can reuse stale commit revisions when git.autorefresh is disabled. The separate report that Git: Refresh also fails is not explained by the normal source path and needs targeted investigation.

## Change summary

Ensure manual Source Control Graph refresh reflects external commits, branch switches, and fetched refs while git.autorefresh is false.

## Best solution

Make explicit Graph refresh obtain current history references and render the latest repository state without re-enabling automatic refresh. Investigate the reported Git: Refresh failure separately, since that command already updates repository state and notifies the history provider.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/scm/browser/scmHistoryViewPane.ts`, `src/vs/workbench/contrib/scm/common/history.ts`, `extensions/git/src/historyProvider.ts`, `extensions/git/src/repository.ts`
- **Validation:** In a disposable repository with git.autorefresh:false and the Graph's automatic ref filter, create a commit externally and click Graph Refresh without first running Git: Refresh; the new commit must appear. Repeat with an external branch checkout and a fetch that advances the tracked remote ref, checking current-branch and incoming/outgoing indicators. Repeat each case using Git: Refresh separately. Establish an automated regression check for stale cached revisions, and verify automatic filesystem refresh remains disabled.
- **Behavior:**

  > Disabling git.autorefresh must not prevent an explicit Source Control Graph refresh from displaying current repository history. After an external commit, branch switch, or fetch, manual refresh must show the relevant latest commits and accurate current-reference indicators. Git: Refresh should also leave the graph consistent with refreshed repository state. Automatic filesystem-driven refresh must remain disabled.
- **Trace:**

  > SCMHistoryViewPane._refresh clears graph state but does not refresh the history provider's current-reference state. Under the automatic filter, _resolveHistoryItemFilter reads cached current refs, and getHistoryItems passes their revision SHAs to GitHistoryProvider.provideHistoryItems; its read-only log operation cannot update those refs. Repository.onFileChange skips status updates when autorefresh is false, making an external commit followed only by Graph Refresh a conclusive stale-revision path. In contrast, Commands.refresh -> Repository.refresh -> Operation.Refresh updates HEAD/refs and emits a write-operation event consumed by GitHistoryProvider, so the reported failure after Git: Refresh still requires runtime diagnosis. The plan must establish regression coverage across this boundary; ISCMHistoryProvider currently exposes no explicit refresh method. Preserve existing filtering, background-fetch notification behavior, and the user's disabled automatic-refresh setting. The related selection-preservation request at https://github.com/microsoft/vscode/issues/226754 is separate work.

- **Why cached revisions remain stale:** extensions/git/src/repository.ts:3336-3340 skips filesystem-triggered status updates when git.autorefresh is false. Clicking Graph refresh therefore does not itself advance those cached refs.

GitHistoryProvider then emits history-ref changes, and scmHistoryViewPane.ts:1788-1803 refreshes the graph. This normal path does not explain the reporter's intermittent failure after Git: Refresh.
