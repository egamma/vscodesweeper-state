# Issue #107360 — append option for vscode.workspace.fs.writeFile

[https://github.com/microsoft/vscode/issues/107360](https://github.com/microsoft/vscode/issues/107360)

## Summary

The append option remains missing from workspace.fs, although the internal file service supports append operations. Keep this accepted Backlog request open; exposing the capability requires an API decision about contributed file-system providers.

## Change summary

Allow extensions to append bytes through vscode.workspace.fs.writeFile without reading and rewriting the existing contents.

## Best solution

Provide an explicit append operation through the extension-facing file-system API while preserving overwrite behavior by default. Define support and failure semantics for contributed providers before exposing the internal append capability.

- **Behavior:**

  > Extensions currently cannot request append through workspace.fs.writeFile; they must read, concatenate, and replace the complete file. The requested capability preserves existing bytes and adds the supplied bytes at the end without changing ordinary writeFile overwrite behavior. Acceptance checks must cover built-in and contributed file systems, including providers without native append support and writes to missing files. The public guarantee about native append versus read/modify/write fallback needs agreement before implementation.
- **Trace:**

  > FileSystem.writeFile in src/vscode-dts/vscode.d.ts has no options argument. ExtHostConsumerFileSystem in src/vs/workbench/api/common/extHostFileSystemConsumer.ts either invokes the contributed provider with overwrite:true or forwards content through the options-free MainThreadFileSystemShape.$writeFile RPC; MainThreadFileSystem then invokes IFileService.writeFile without options. Internal append support exists in src/vs/platform/files/common/files.ts and fileService.ts, but validateWriteFile requires FileAppend, and ExtHostFileSystem.registerFileSystemProvider does not advertise that capability for contributed providers. Preserve ordinary overwrite semantics and compatibility with existing providers; this is an API-contract gap, not evidence of a broken write implementation. Source inspection establishes the missing surface, but does not settle unsupported-provider semantics or concurrent-write guarantees.
- **Open decisions:**
