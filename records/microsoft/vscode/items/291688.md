# Issue #291688 — Feature Request: Public API to access Local History entries

[https://github.com/microsoft/vscode/issues/291688](https://github.com/microsoft/vscode/issues/291688)

## Summary

Keep this accepted API request open: current main exposes Local History internally, but neither the public extension API nor the proposed Timeline API provides the requested enumeration. The 25 upvotes and additional extension use case support API-owner design work, particularly distinguishing unflushed history metadata from unsaved editor contents.

## Change summary

Expose supported extension access to a file's Local History entries and snapshot contents without parsing internal storage.

## Best solution

Provide a supported, read-only Local History API that returns current entry metadata and readable snapshot references while respecting existing retention and configuration behavior. API owners should settle unsaved-buffer scope and entry-lifetime guarantees before implementation; Git reconstruction and project checkpoints should remain extension functionality.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vscode-dts/vscode.proposed.timeline.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/services/workingCopy/common/workingCopyHistory.ts`, `src/vs/workbench/services/workingCopy/common/workingCopyHistoryService.ts`
- **Validation:** An extension-host integration check should create a saved Local History entry with metadata flushing deferred, enumerate it through the agreed API, and read its snapshot contents without accessing entries.json. Verify metadata and content after reload, existing retention/merge behavior, and local versus remote resources. Explicitly test the chosen dirty-buffer and entry-lifetime contracts.
- **Behavior:**

  > Extensions need supported access to a file's Local History metadata and snapshot contents, including entries whose metadata has not yet been flushed to entries.json. Enumeration must not require parsing internal storage or interacting with a picker. Existing history configuration and retention behavior must remain respected. Acceptance should demonstrate fresh saved-entry enumeration and snapshot reads before metadata flush, then after reload, with documented behavior for unsaved edits and expired or replaced entries.
- **Trace:**

  > IWorkingCopyHistoryService.getEntries in src/vs/workbench/services/workingCopy/common/workingCopyHistory.ts already exposes the relevant internal metadata. WorkingCopyHistoryModel.getEntries and doResolveEntries in workingCopyHistoryService.ts merge disk and in-memory metadata, while NativeWorkingCopyHistoryService delays local metadata persistence for five minutes. Snapshot contents are cloned from files; WorkingCopyHistoryTracker.onDidChangeContent only tracks versions, whereas onDidSave schedules entry creation. Existing entries can be replaced during the merge period, so identifiers and locations are not automatically immutable checkpoint references. src/vscode-dts/vscode.proposed.timeline.d.ts and MainThreadTimeline expose provider contribution, not built-in history enumeration; https://github.com/microsoft/vscode/issues/84297 is related design context, not a verified duplicate. Preserve existing persistence, retention, and save-triggered capture semantics unless API owners explicitly choose otherwise; Git operations and project-wide checkpoint orchestration remain outside this core API request.
- **Open decisions:**
  - Should the initial API enumerate existing saved Local History entries only, or also expose current unsaved document contents as a distinct snapshot concept?
  - Are returned IDs and snapshot URIs best-effort references subject to existing replacement and retention, or must extensions be able to retain immutable checkpoint contents?
