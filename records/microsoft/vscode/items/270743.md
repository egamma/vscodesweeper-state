# Issue #270743 — Ensure version compatibility of simultaneous VSCode instances

[https://github.com/microsoft/vscode/issues/270743](https://github.com/microsoft/vscode/issues/270743)

## Summary

Keep open: current startup handling does not fully enforce compatibility between versions sharing a user-data directory or protect eagerly executed CLI commands. This is team-authored, accepted Backlog work; the related updater fix does not establish completion of these requirements.

## Change summary

Prevent incompatible VS Code versions from sharing startup IPC or concurrently using the same user-data directory, and reject mismatched CLI execution during updates.

## Best solution

Establish a consistent compatibility boundary across desktop instance acquisition and early CLI execution, with actionable errors for incompatible launches. Preserve normal same-version window forwarding and independent instances using separate user-data directories.

## Plan brief

- **Likely files:** `src/vs/base/parts/ipc/node/ipc.net.ts`, `src/vs/platform/environment/electron-main/environmentMainService.ts`, `src/vs/code/electron-main/main.ts`, `src/cli.ts`, `src/vs/code/node/cli.ts`, `src/vs/code/node/cliProcessMain.ts`
- **Validation:** The plan should define executable checks using two builds: incompatible versions targeting the same user-data directory must not forward IPC or both proceed; the rejected desktop launch must show an actionable error; same-version launches must still forward normally; separate user-data directories must remain independent. Exercise an early extension-management CLI command across an update transition and verify a detected mismatch exits unsuccessfully before performing the command.
- **Behavior:**

  > Launching an incompatible VS Code version must not communicate through the running version's startup IPC or start another desktop instance against its user-data directory. The rejected launch must provide an actionable user-facing error. CLI commands started during an update must abort when their executable/resources are mismatched, before executing the operation. Normal same-version forwarding and independent instances using different user-data directories must remain supported.
- **Trace:**

  > EnvironmentMainService.mainIPCHandle derives the endpoint from the user-data directory and product version; createStaticIPCHandle keeps the full version on Windows but only four characters on macOS/Linux. CodeMain.claimInstance treats successful binding as ownership and forwards through the launch channel on EADDRINUSE without checking the peer's version; code.lock is written afterward rather than used here as a shared-directory exclusion mechanism. checkInnoSetupMutex covers only Windows versioned Inno Setup startup, while src/cli.ts and cli.ts can dispatch extension-management operations directly into CliMain. These observations establish incomplete coverage, not a runtime reproduction. The uncertainty is the compatibility identity and synchronization contract across desktop startup, CLI bootstrap, and updates; preserve existing same-version forwarding and separate-directory isolation. The fixed originating report at https://github.com/microsoft/vscode/issues/264558 concerns updater process killing, and the newer Linux symptom at https://github.com/microsoft/vscode/issues/337691 is related rather than a canonical.
- **Open decisions:**
  - What defines an incompatible instance or CLI/resource pair: a product-version difference, a commit/build difference, or another explicit compatibility identity?
