# Issue #83424 — Add custom QuickPick highlighting

[https://github.com/microsoft/vscode/issues/83424](https://github.com/microsoft/vscode/issues/83424)

## Summary

Keep open: extensions still cannot supply QuickPick highlight ranges, and the documented filtering workaround does not cover regex or flag-bearing search queries. Maintainers have accepted the use case and expressed willingness to review an API proposal.

## Change summary

Allow extensions to supply custom highlights for QuickPick labels, descriptions, and details instead of relying on built-in fuzzy highlighting.

## Best solution

Provide a backward-compatible QuickPick highlighting API consistent with TreeItemLabel range conventions, preserving existing behavior for ordinary string items. Settle how explicit ranges interact with automatic filtering and highlighting before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostQuickOpen.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadQuickOpen.ts`, `src/vs/platform/quickinput/common/quickInput.ts`, `src/vs/platform/quickinput/browser/quickInputList.ts`
- **Validation:** Use an Extension Development Host with a createQuickPick sample that searches text using a regex and an inline file-scope flag, supplies detail-only match ranges, and updates results through onDidChangeValue. Verify the supplied detail ranges remain visible after typing and item updates, label and description stay unhighlighted when explicitly suppressed, and ordinary string-only items retain existing fuzzy filtering and highlighting.
- **Behavior:**

  > An extension implementing regex or flag-bearing search should be able to highlight the actual matched text in QuickPick results, even when the full input is not a fuzzy match. Custom highlighting should support label, description, and detail, including explicitly leaving individual fields unhighlighted. Ordinary string-only QuickPick items must retain their existing behavior. Acceptance should exercise both initial items and updates while the user types.
- **Trace:**

  > QuickPickItem in src/vscode-dts/vscode.d.ts exposes strings only, while the internal IQuickPickItemHighlights in src/vs/platform/quickinput/common/quickInput.ts already represents ranges for all three fields. ExtHostQuickPick.items in src/vs/workbench/api/common/extHostQuickOpen.ts serializes items through TransferQuickPickItem in src/vs/workbench/api/common/extHost.protocol.ts without highlight metadata. QuickInputList.filter in src/vs/platform/quickinput/browser/quickInputList.ts recomputes or clears ranges from the full query, so exposing metadata alone would not establish the intended behavior. TreeItemLabel provides the existing inclusive-start, exclusive-end tuple convention, and the maintainer requested consistency with that API at https://github.com/microsoft/vscode/issues/83424#issuecomment-949057495. Preserve existing string-item behavior and do not absorb the separate sorting work from https://github.com/microsoft/vscode/issues/73904. The uncertainty is the public contract for explicit highlights and whether supplying them also overrides automatic matching.
- **Open decisions:**
  - Should QuickPick expose highlighted text objects on label, description, and detail, or separate range metadata while keeping those properties string-valued?
  - Does supplying explicit highlight ranges disable automatic filtering for that item, as the reporter proposes, or should filtering remain independently controlled?
  - For fields without supplied ranges, should automatic highlighting continue or should an item using custom highlighting suppress automatic highlights across all fields?
