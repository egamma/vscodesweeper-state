# Issue #334271 — Agent sessions: MCP servers requiring promptString inputs or OAuth fail silently — tools absent with no surfaced error or support documentation

[https://github.com/microsoft/vscode/issues/334271](https://github.com/microsoft/vscode/issues/334271)

## Summary

A real gap remains on current main: Agent Host discovers and launches MCP servers through a separate path that neither matches editor-chat configuration discovery nor resolves `${input:...}` variables. The newer related issue concerns persistent health UI and cannot absorb this re-reviewed report.

## Change summary

Agent sessions silently omit MCP servers that require input or authentication, and may omit configured servers generally, despite the same configuration working in editor chat.

## Best solution

Give Agent Host sessions configuration parity with editor chat for supported MCP sources, establish a safe client/host contract for resolving interactive inputs and OAuth, and publish a durable unavailable or authentication-required state instead of silently dropping tools.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/shared/sessionMcpDiscovery.ts`, `src/vs/platform/agentHost/node/copilot/copilotPluginConverters.ts`, `src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationService.ts`, `src/vs/platform/agentHost/test/node/shared/sessionMcpDiscovery.test.ts`
- **Validation:** Add focused tests proving an MCP server from the supported workspace configuration surface reaches an Agent Host session, an unresolved `${input:...}` server is represented as requiring input rather than silently omitted, and completing that input makes its tools available without regressing static stdio or HTTP servers.
- **Behavior:**

  > Agent sessions should recognize the same supported workspace MCP server configurations as editor chat. A server requiring `${input:...}` or OAuth must remain visible with an actionable blocked state rather than disappearing from the toolset without explanation. After the required interaction succeeds, the server and its tools should become available to the session; static stdio and HTTP configurations must continue to start without interaction.
- **Trace:**

  > Current Agent Host workspace discovery is RootMcpDiscovery in src/vs/platform/agentHost/node/shared/sessionMcpDiscovery.ts, which reads only `<root>/.mcp.json` and normalizes definitions independently of the workbench MCP registry. CopilotPluginConverters.toSdkMcpServer forwards configuration values directly to the SDK without resolving `${input:...}` placeholders. CopilotSessionLauncher supplies `onMcpAuthRequest`, and CopilotAgentSession already projects SDK MCP lifecycle state, so OAuth/status plumbing partially exists; the uncertainty begins at how editor-owned interactive input and secrets should cross into the Agent Host. Keep persistent primary-UI health work associated with https://github.com/microsoft/vscode/issues/335528 rather than broadening this fix into that separate presentation request.
- **Open decisions:**
  - Should `${input:...}` values be resolved by the connected VS Code client before MCP configuration is published, or should Agent Host expose a blocked-input request that the client answers on demand?
  - Which MCP configuration sources are part of the supported Agent Sessions contract: the editor's complete effective MCP registry or a documented subset with explicit unsupported-state reporting?

## Evidence

- **configuration discovery gap:** src/vs/platform/agentHost/node/shared/sessionMcpDiscovery.ts scans only `<workspace>/.mcp.json` through RootMcpDiscovery; it does not consume the editor MCP registry or scan `.vscode/mcp.json`, one of the sources named in the report.
- **unresolved interactive inputs:** SessionMcpDiscovery normalizes raw definitions and src/vs/platform/agentHost/node/copilot/copilotPluginConverters.ts forwards command, args, env, URL, and headers directly into the SDK configuration. This path has no `${input:...}` resolver or client interaction boundary, so promptString placeholders remain unresolved.
- **partial current support:** src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts now passes discovered MCP servers and `onMcpAuthRequest` to the Copilot SDK, while copilotAgentSession.ts projects SDK lifecycle events into MCP customization state. This addresses parts of the reporting gap but does not establish editor-config or promptString parity.
- **distinct newer issue:** https://github.com/microsoft/vscode/issues/335528 was created after this issue and specifically requests persistent proactive authentication-health UI. Under the re-review rule it cannot be the canonical duplicate for this older activation/configuration report.
- **related older reports:** https://github.com/microsoft/vscode/issues/327640 covers a no-op authentication action and silent sign-in feedback, while https://github.com/microsoft/vscode/issues/330837 covers failed GitHub credential handoff and recovery. Neither fully owns promptString activation or general workspace MCP configuration parity.
