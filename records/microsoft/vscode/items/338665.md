# Issue #338665 — Remote agent host over SSH keeps reconnecting while a large message is still downloading

[https://github.com/microsoft/vscode/issues/338665](https://github.com/microsoft/vscode/issues/338665)

## Summary

Well-diagnosed, team-authored report; traced the defect in current main — the liveness watchdog only resets on a fully-parsed message, not on inbound bytes, so a large in-flight message can starve it and trigger a spurious reconnect loop exactly as described.

## Change summary

The agent-host protocol client's 25s liveness watchdog (5s ping + 20s timeout) drops and reconnects a connection that is still actively receiving a large (multi-MB) message, causing repeated redundant re-downloads instead of recognizing the connection as alive.

## Best solution

Give the client visibility into raw inbound activity (not just completed messages) so the liveness watchdog treats a connection that is actively streaming a large message as alive — likely by having transports surface a raw-data/progress signal that `agentHostProtocolClient.ts` folds into `_lastReadTime`/`_resetLivenessTimers`.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/browser/agentHostProtocolClient.ts`, `src/vs/platform/agentHost/common/state/sessionTransport.ts`, `src/vs/platform/agentHost/node/webSocketTransport.ts`, `src/vs/platform/agentHost/browser/webSocketClientTransport.ts`, `src/vs/platform/agentHost/browser/webPubSubRelayTransport.ts`, `src/vs/platform/agentHost/browser/agentHostIpcChannelTransport.ts`, `src/vs/platform/agentHost/common/reconnectingTransport.ts`
- **Validation:** A protocol-client test that simulates a transport receiving raw chunks of a single large message spanning more than LIVENESS_TIMEOUT_MS without completing it, asserting the client does not force-close/reconnect while chunks keep arriving, and still force-closes on genuine silence.
- **Behavior:**

  > A connection that is actively receiving data — even mid-way through a single large message — must not be treated as dead by the liveness watchdog. Today, receiving continuous partial data for a message larger than ~20s of transfer time still triggers a forced close and reconnect (repeating indefinitely on very large/slow transfers). After the fix, the watchdog should only fire when there is genuine silence (no bytes at all) for the timeout window; a connection streaming a large payload should be recognized as alive throughout. Acceptance: a new/updated protocol-client test proves a partially-received large message no longer forces a reconnect, while true silence still does.
- **Trace:**

  > `_lastReadTime` in agentHostProtocolClient.ts is only updated when `transport.onMessage` fires (a fully parsed JSON-RPC message) or right after a reconnect attempt — never on raw bytes arriving mid-message. `IProtocolTransport` (sessionTransport.ts) exposes no such raw-activity event, so nothing today can distinguish 'no bytes for 25s' from 'megabytes streaming in but the message hasn't finished'. `_keepAliveTimeoutCheck`/`_onCloseTimer` (~line 2538 onward) force-close based purely on `_lastReadTime`. The boundary: do not touch the general remote `PersistentProtocol` in ipc.net.ts (base/parts/ipc/common/ipc.net.ts) — that protocol already updates `lastReadTime` per raw chunk via `ProtocolReader.acceptChunk` and is unaffected; this is specific to the agent-host protocol client's own watchdog and its transport abstraction.
- **Open decisions:**
  - Should raw-byte arrival fully reset the liveness timer, or only extend it by a bounded grace period while a message is in flight (to avoid masking a truly half-dead connection that dribbles garbage bytes)?
  - Is the raw-activity signal added to the shared `IProtocolTransport` interface (implemented by every transport), or handled per-transport with a narrower opt-in capability?
  - Should the server also chunk/paginate very large state-snapshot messages instead of (or in addition to) the client-side watchdog fix, to bound worst-case download time after reconnect?

## Evidence

- **watchdog constants:** src/vs/platform/agentHost/browser/agentHostProtocolClient.ts: PING_INTERVAL_MS=5_000, LIVENESS_TIMEOUT_MS=20_000 (lines 78, 89) sum to the exact 25s the reporter measured before a forced close (`_onCloseTimer`, line ~2556).
- **only resets on complete message:** `_lastReadTime` is set only in `_attemptReconnect` (lines 911, 965) and `_handleMessage` (line 1972), which fires from `transport.onMessage` — an event that only emits once a whole JSON-RPC message has been assembled. There is no lower-level 'bytes received' hook wired into the watchdog.
- **transport interface has no raw-data event:** src/vs/platform/agentHost/common/state/sessionTransport.ts:IProtocolTransport only exposes `onMessage` (complete messages) and `onClose`; multiple concrete transports implement it (webSocketTransport.ts, webSocketClientTransport.ts, webPubSubRelayTransport.ts, agentHostIpcChannelTransport.ts, reconnectingTransport.ts), so a fix touches several transport implementations, not one bounded file.
