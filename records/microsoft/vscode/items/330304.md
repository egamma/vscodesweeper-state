# Issue #330304 — Change default 'Enter' behavior in Copilot prompt window when writing lists

[https://github.com/microsoft/vscode/issues/330304](https://github.com/microsoft/vscode/issues/330304)

## Summary

A real chat-input UX gap remains: current main always binds plain Enter to Send and has no context-sensitive handling for Markdown lists. The request should stay open and be routed to the chat-input area for a product decision.

## Change summary

Make Enter insert and optionally continue a Markdown list item in chat prompts, submitting only when the user ends the list.

## Best solution

Provide predictable multiline list entry in chat while preserving an unambiguous way to submit, with the chat-input owners deciding whether the behavior is automatic or opt-in and whether list markers are continued automatically.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/actions/chatExecuteActions.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/chatWidget.test.ts`
- **Validation:** Add chat-input keyhandling coverage showing the chosen Enter behavior for numbered and bulleted list lines, list termination, ordinary text, Shift+Enter, and customized submit keybindings.
- **Behavior:**

  > Users composing a numbered or bulleted response in chat should be able to press Enter between list items without prematurely sending the prompt. Ending the list must provide a predictable transition back to submission, while ordinary prompts and explicit newline or submit keybindings retain their established behavior. Acceptance coverage should include numbered lists, bullets, termination on an empty continuation, non-list text, and customized keybindings.
- **Trace:**

  > ChatSubmitAction in src/vs/workbench/contrib/chat/browser/actions/chatExecuteActions.ts binds plain Enter whenever the chat input context is active. ChatInputPart in src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts separately prevents the editor's default newline whenever that plain-Enter submit binding is present; neither path inspects Markdown structure. Existing keybinding customization documented in https://github.com/microsoft/vscode/issues/246513 can globally change Enter, but cannot switch behavior only inside lists. Preserve custom keybindings, Shift+Enter newline behavior, and non-list submission semantics; the uncertainty begins at whether smart list handling should be default behavior and whether it should synthesize subsequent list markers.
- **Open decisions:**
  - Should list-aware Enter behavior be enabled by default for every chat input, or exposed as an opt-in setting?
  - Should Enter only insert a newline after a recognized list item, or also generate the next numbered or bulleted marker?
  - Should an empty generated list item submit immediately, or first remove the marker and require a second Enter to submit?

## Evidence

- **current keybinding:** src/vs/workbench/contrib/chat/browser/actions/chatExecuteActions.ts registers `workbench.action.chat.submit` on plain Enter whenever `inChatInput` is active; there is no list-sensitive context condition.
- **current input handling:** src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts prevents plain Enter from creating a newline whenever the submit command remains bound to Enter, without inspecting the current line or Markdown list syntax.
- **existing workaround is partial:** https://github.com/microsoft/vscode/issues/246513 documents that users can remap `workbench.action.chat.submit`, but that global keybinding customization does not provide the requested context-sensitive behavior where Enter changes meaning only while composing a list.
- **no canonical duplicate:** The older Enter-mode requests concern globally swapping or remapping Enter and submission. None found reports the same observable request to detect list items, continue multiline entry, and submit after a terminating blank item.
