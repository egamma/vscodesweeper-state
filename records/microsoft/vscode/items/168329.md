# Issue #168329 — Filter completion client-side even if the LSP returns incomplete results

[https://github.com/microsoft/vscode/issues/168329](https://github.com/microsoft/vscode/issues/168329)

## Summary

The requested immediate filtering remains absent from the incomplete-completion refresh path. The older related issue concerns accepting delayed server responses, whereas this request explicitly asks to filter already available results without waiting for any response.

## Change summary

Immediately filter existing incomplete completion results while requesting updated server results, with a loading indication during the refresh.

## Best solution

Make incomplete completion refreshes responsive by filtering available candidates against current input while the provider computes replacements. Coordinate with the related cancellation discussion without treating acceptance of delayed responses as a substitute for local filtering.

- **Validation:** Add a delayed completion-provider case to suggestModel.test.ts: after an initial incomplete list, type another matching character while holding the replacement response unresolved; verify an interim onDidSuggest contains locally filtered candidates, then resolve the response and verify replacement results appear. Cover successive keystrokes and mixed complete/incomplete providers. Manually verify that the visible list remains usable with a refresh indication during the delay.
- **Behavior:**

  > When an incomplete completion list is visible, additional typing should immediately filter the candidates already available rather than leave the previous list unchanged until the server responds. Updated server results should subsequently replace the provisional results for the current input. A loading indication should communicate that further candidates may arrive. Acceptance must distinguish an update before the pending response resolves from the final update after it resolves, and preserve normal complete-list behavior.
- **Trace:**

  > SuggestModel._onNewContext in src/vs/editor/contrib/suggest/browser/suggestModel.ts separates incomplete-provider retriggering from the branch that updates CompletionModel.lineContext and emits onDidSuggest. trigger cancels the current model before requesting new results, while CompletionModel in src/vs/editor/contrib/suggest/browser/completionModel.ts already supports local refiltering. SuggestController forwards trigger and suggestion events to SuggestWidget, whose showTriggered method ignores an already-visible widget. The unresolved design work is how provisional results, request cancellation, replacement results, and loading presentation coexist across successive keystrokes; those interactions were not executed in this read-only review. Preserve complete-provider reuse, completion acceptance semantics, and cancellation on context changes. https://github.com/microsoft/vscode/issues/147830 concerns a related but distinct delayed-response policy and should remain coordinated rather than assumed solved by this work.
- **Open decisions:**
  - What loading presentation should accompany an already-visible, provisionally filtered completion list while replacement results are pending?
