# Issue #167863 — Column number is incorrect when using tabs.

[https://github.com/microsoft/vscode/issues/167863](https://github.com/microsoft/vscode/issues/167863)

## Summary

This remains a valid, accepted Backlog feature request: current main intentionally reports a tab-expanded visible column, while the requested character-based position is still unavailable. The existing behavior should not be redefined without a product decision because users rely on both coordinate systems.

## Change summary

Provide a way for the editor status bar to report the cursor's character-based column instead of only its tab-expanded visible column.

## Best solution

Expose character-based position as an explicit status-bar mode while preserving a clear visual-column option and consistent terminology. The chosen behavior should also remain coherent with cursor-position accessibility announcements and Go to Line/Column.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/editor/editorStatus.ts`, `src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts`, `src/vs/editor/common/core/cursorColumns.ts`, `src/vs/editor/test/common/core/cursorColumns.test.ts`, `src/vs/workbench/contrib/codeEditor/browser/accessibility/accessibility.ts`
- **Validation:** Add targeted tests covering a line beginning with two tabs at tab size 4: the existing visual mode reports column 9 at `H`, the character-based mode reports column 3, and changing modes updates the status entry without affecting ordinary space-only lines.
- **Behavior:**

  > For text containing tabs, users need an unambiguous way to obtain the cursor's character-based column for coordinates supplied by stack traces and other external tools. At the `H` in `\t\tHello`, character position is 3 while visible position is 9 with tab size 4; the finished behavior must distinguish those meanings rather than silently redefining one as the other. Space-only lines and existing selection counts must remain unchanged, and the accessible cursor-position announcement must use clearly consistent semantics.
- **Trace:**

  > The single-selection status entry is assembled by EditorStatus.onSelectionChange in src/vs/workbench/browser/parts/editor/editorStatus.ts, which substitutes editorWidget.getStatusbarColumn() for the model selection column. CodeEditorWidget.getStatusbarColumn in src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts calls CursorColumns.toStatusbarColumn in src/vs/editor/common/core/cursorColumns.ts; that helper advances tabs to render tab stops, and its unit tests encode that behavior. AnnounceCursorPosition in src/vs/workbench/contrib/codeEditor/browser/accessibility/accessibility.ts separately computes the same visible-column concept to match the status bar. https://github.com/microsoft/vscode/pull/284668 aligned Go to Line/Column with visible columns but did not resolve this request. The boundary is cursor-coordinate presentation: selection ranges, model positions, tab rendering, and Go to Offset semantics must not change accidentally.
- **Open decisions:**
  - Should users select visual versus character columns through a setting, a status-bar interaction, or a display that exposes both?
  - Should the existing visible-column behavior remain the default for compatibility, and what labels distinguish the two coordinate systems clearly?
  - Should Announce Cursor Position follow the selected status-bar mode or announce both coordinates when they differ?

## Evidence

- **current source:** src/vs/workbench/browser/parts/editor/editorStatus.ts calls editorWidget.getStatusbarColumn() for the single-selection status entry; src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts delegates that calculation to CursorColumns.toStatusbarColumn().
- **tab expansion:** src/vs/editor/common/core/cursorColumns.ts explicitly expands tabs to render tab stops in toStatusbarColumn(); src/vs/editor/test/common/core/cursorColumns.test.ts asserts that the position after one tab with tab size 4 is reported as column 5.
- **accepted demand:** A VS Code team comment recorded that the request received sufficient community support and moved it to the Backlog milestone; it remains labeled feature-request and workbench-status.
- **related fix is distinct:** https://github.com/microsoft/vscode/issues/280540 and merged https://github.com/microsoft/vscode/pull/284668 changed Go to Line/Column to use visible columns. The PR only modifies quick-access code and does not add the requested character-based status-bar mode.
- **accessibility boundary:** src/vs/workbench/contrib/codeEditor/browser/accessibility/accessibility.ts intentionally announces a visible column to match the status bar, so any selectable status-bar coordinate system needs an explicit decision about announcement consistency.
