# Issue #290750 — Drop target too small when using integrated browser

[https://github.com/microsoft/vscode/issues/290750](https://github.com/microsoft/vscode/issues/290750)

## Summary

Keep open: the existing steps suffice to retest, and current source still suggests a gap between native browser content and workbench drop handling. Browser presentation has since moved into WebContentsViewHost; source inspection alone cannot confirm current native drag-event behavior.

## Change summary

Dragging an Explorer file over an editor containing only the integrated browser exposes a usable drop target only near the top.

## Best solution

Make ordinary editor file drops available throughout the browser editor area, preserving normal open/split behavior. First reproduce with a loaded page and establish how native browser content intercepts the workbench drag sequence.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/browserView/electron-browser/webContentsViewHost.ts`, `src/vs/workbench/contrib/browserView/electron-browser/overlayManager.ts`, `src/vs/workbench/browser/parts/editor/editorDropTarget.ts`
- **Validation:** In desktop VS Code, leave the integrated browser as the sole editor and load a valid page. Drag an Explorer file directly over the page center without first crossing the browser toolbar; verify the normal editor drop target appears and dropping opens the file. Repeat at an editor split edge and cancel a drag, checking that normal split behavior and browser visibility resume correctly.
- **Behavior:**

  > With the integrated browser as the only open editor, dragging an Explorer file over the page should offer the normal editor drop interaction throughout the editor content area, not only at the top. Dropping should open the file according to existing editor open/split conventions. Cancelling or completing a drag must leave the browser usable and correctly visible.
- **Trace:**

  > WebContentsViewRendererFeature delegates native presentation to WebContentsViewHost, whose visibility depends on editor visibility, page state, and BrowserOverlayManager overlap detection. BrowserOverlayManager's tracked overlay definitions omit the editor drop overlay, and the host has no explicit drag handling. EditorDropTarget creates its overlay only after a DOM drag-enter reaches its container and identifies a target group, while BrowserView owns a separate native Electron WebContentsView above the workbench. This suggests an event-delivery and presentation boundary rather than merely a target-size constant; runtime reproduction is needed before asserting the root cause. Preserve ordinary editor drop semantics and webpage interaction outside workbench file drags. The originating behavior contract is documented in https://github.com/microsoft/vscode/issues/290615.

## Evidence

- **Actionable report:** https://github.com/microsoft/vscode/issues/290750 specifies opening only the integrated browser and dragging an Explorer file over its area; the reported limitation is that only the top accepts the drop. No additional reporter information is needed to attempt this scenario.
- **Intended overlay behavior:** The originating test plan, https://github.com/microsoft/vscode/issues/290615, explicitly requires workbench content not to be hidden behind the native browser and describes temporarily pausing the browser to expose overlapping UI.
- **Current presentation path:** src/vs/workbench/contrib/browserView/electron-browser/features/webContentsViewRendererFeature.ts delegates presentation to WebContentsViewHost. In webContentsViewHost.ts, _shouldShowPage and _refreshOverlayObscured govern native-view visibility through detected overlays; neither this host nor overlayManager.ts provides explicit drag handling, and OVERLAY_DEFINITIONS does not include the editor drop overlay.
- **Drop-event boundary:** src/vs/workbench/browser/parts/editor/editorDropTarget.ts registers DOM DRAG_ENTER listeners on the editor container and constructs DropOverlay from the event target's editor group. src/vs/platform/browserView/electron-main/browserView.ts creates a separate Electron WebContentsView and attaches it with contentView.addChildView. These paths identify a plausible native/DOM interception boundary, but do not prove the runtime outcome.
