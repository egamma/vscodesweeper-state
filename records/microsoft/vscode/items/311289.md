# Issue #311289 — API: Allow access to the notebook editor scroll state

[https://github.com/microsoft/vscode/issues/311289](https://github.com/microsoft/vscode/issues/311289)

## Summary

Keep open for notebook API design: current extension APIs still lack pixel-level notebook scroll observation and navigation. The request earned Backlog promotion with 31 upvotes, and the related native-minimap issue does not own this broader API contract.

## Change summary

Expose notebook scroll position, viewport and content dimensions, layout information, and sub-cell navigation to extensions.

## Best solution

Have notebook API owners settle a minimal proposed scroll API that supports extension-built notebook navigation without exposing unstable layout assumptions or imposing unnecessary scroll-time overhead. Evaluate the reporter's reference implementation against that contract before implementation proceeds.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/browser/mainThreadNotebookEditors.ts`, `src/vs/workbench/api/common/extHostNotebookEditor.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/contrib/notebook/browser/notebookBrowser.ts`, `src/vs/workbench/contrib/notebook/browser/notebookEditorWidget.ts`, `src/vs/workbench/contrib/notebook/browser/view/notebookCellList.ts`, `extensions/vscode-api-tests/src/singlefolder-tests/notebook.editor.test.ts`
- **Validation:** After agreeing the proposed contract, add notebook extension-API integration coverage using a tall single-cell output: scrolling within unchanged visible cell ranges must update pixel state; programmatic navigation must reach the requested clamped offset; resize and output-height changes must produce consistent geometry. Verify initialization, event ordering, and unchanged existing cell-range navigation.
- **Behavior:**

  > Extensions cannot currently observe progress through a tall notebook cell or navigate to a position inside its output using notebook-level APIs. The desired capability is continuous notebook scroll observation and sub-cell navigation, sufficient for extension-built minimaps and synchronized reading positions. Acceptance should include scrolling within a single tall cell without a visibleRanges transition, accurate viewport/content measurements, and navigation to an offset within the available scroll extent. Existing cell-range APIs must retain their behavior.
- **Trace:**

  > NotebookEditor in src/vscode-dts/vscode.d.ts exposes cell-index visibleRanges and revealRange only; no equivalent notebook scroll proposal was found among current declarations. MainThreadNotebookEditors.handleEditorsAdded forwards visible-range and selection changes, while ExtHostNotebookEditor.apiEditor exposes no pixel-scroll state or setter. Internal onDidScroll and setScrollTop are declared in notebookBrowser.ts, with measurements available in notebookEditorWidget.ts and view/notebookCellList.ts. The gap is the extension API contract and its renderer-to-extension-host synchronization, not absence of an internal scrolling mechanism. https://github.com/microsoft/vscode/issues/311289 contains a reference implementation and suggested validation, but API-owner acceptance of its shape is not established. https://github.com/microsoft/vscode/issues/115266 tracks a related end-user minimap rather than this API; do not expand this work into a built-in minimap or alter existing revealRange semantics.
- **Open decisions:**
  - Should the initial public proposal expose per-cell pixel geometry as well as aggregate scroll metrics and navigation, or leave per-cell layout outside the contract?
  - What initialization and update guarantees should consumers receive: optional metrics before layout, and cached omission-based cell geometry versus self-contained state snapshots?

## Evidence
