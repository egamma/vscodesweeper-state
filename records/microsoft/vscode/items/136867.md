# Issue #136867 — ICodeEditor.setHiddenAreas optimizes away valid update

[https://github.com/microsoft/vscode/issues/136867](https://github.com/microsoft/vscode/issues/136867)

## Summary

Keep open: current source still allows hidden-line projections to diverge from their tracking decorations, causing a valid setHiddenAreas update to be skipped. The related folding report depends on this core defect being fixed; it does not replace the broader API-level issue.

## Change summary

Reapplying the correct hidden ranges after inserting a line must reveal any newly inserted line outside those ranges.

## Best solution

Make hidden-area change detection reflect actual line visibility after model edits, while preserving valid no-op optimization and existing folding behavior. Cover the reported boundary insertion in the view-model tests rather than relying on another folding-provider workaround.

## Evidence

- **Current source defect:** src/vs/editor/common/viewModel/viewModelLines.ts:351–385 marks inserted lines hidden when the preceding projection is hidden. For the reported insertion at line 3, the hidden line-2 projection therefore makes the new line hidden. However, setHiddenAreas at lines 178–199 compares only decoration ranges and returns false when those still equal the requested line-2 range, before reconciling projection visibility.
- **Decoration boundary mismatch:** normalizeLineRanges in src/vs/editor/common/viewModel/viewModelLines.ts:1035–1060 constructs ranges with both endpoints at column 1. setHiddenAreas stores them using ModelDecorationOptions.EMPTY. This matches the maintainers' diagnosis in https://github.com/microsoft/vscode/issues/136867: a newline inserted after the content of the final hidden line does not extend its tracking decoration, although onModelLinesInserted extends hidden projection visibility.
- **Folding refresh does not resolve the core mismatch:** src/vs/editor/contrib/folding/browser/hiddenRangeModel.ts:35–41 and 77–79 detect line changes and emit updated hidden ranges even when their line numbers remain unchanged. The lower-level decoration-only equality check still exists; the forceUpdate parameter in viewModelImpl.ts:595–609 bypasses only its outer cache, not that check.
