# Issue #197634 — Search: Support tree type navigation and find widget

[https://github.com/microsoft/vscode/issues/197634](https://github.com/microsoft/vscode/issues/197634)

## Summary

The Search results tree still lacks the navigation-label provider needed for type navigation and the tree find widget. Keep this open: the maintainer explicitly retained it for the full widget, while the older filtering request covers only part of that scope.

## Change summary

Support type navigation and the standard tree find widget within Search results without filtering away the result children of matching files.

## Best solution

Give the Search results tree the standard navigation and find experience while retaining useful match previews beneath matching files. Settle which row types and labels participate before implementing the Search-specific integration.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/search/browser/searchView.ts`, `src/vs/workbench/contrib/search/browser/searchResultsView.ts`, `src/vs/workbench/contrib/search/test/browser/searchViewlet.test.ts`, `src/vs/base/browser/ui/tree/abstractTree.ts`
- **Validation:** Add focused Search-tree coverage for type-navigation targets and tree-find highlight/filter behavior. Manually search a workspace with multiple files and nested folders, focus the results tree, exercise type navigation and the standard find command, and verify that matching file rows retain their result children, clearing find restores the results, and the underlying workspace search query and counts remain unchanged.
- **Behavior:**

  > Users with many Search results should be able to navigate by typing and open the standard tree find widget within those results. Finding or filtering a matching file must not leave that file without its useful result children. Acceptance must cover highlight and filter modes, clearing the find text, and preservation of the underlying workspace search query and results. Which row types and labels participate remains a product decision.
- **Trace:**

  > SearchView.createSearchResultsView in src/vs/workbench/contrib/search/browser/searchView.ts constructs the results tree without keyboardNavigationLabelProvider. The generic find controller in src/vs/base/browser/ui/tree/abstractTree.ts and type-navigation controller in src/vs/base/browser/ui/list/listWidget.ts require that provider, so generic workbench list settings alone cannot enable the requested experience. FindFilter.filter already handles undefined labels without filtering those rows, but Search-specific matching and rendering semantics have not been established. FileMatchRenderer, FolderMatchRenderer, and MatchRenderer live in src/vs/workbench/contrib/search/browser/searchResultsView.ts. Keep the boundary at navigation and finding within existing Search results; do not alter workspace text-search execution or replacement behavior. https://github.com/microsoft/vscode/issues/67397 records the narrower filtering concern; this issue's maintainer explicitly retained the broader widget request separately.
- **Open decisions:**
  - Should tree find match only file and folder labels, preserving textual result rows as context, or should textual result previews also be independently searchable?
  - Should file and folder matching include displayed path descriptions as well as names, and should type navigation use the same label scope?
