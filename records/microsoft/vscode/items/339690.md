# Issue #339690 — During Dev Container session creation some empty sessions show in the session list

[https://github.com/microsoft/vscode/issues/339690](https://github.com/microsoft/vscode/issues/339690)

## Summary

Fresh, credible report (video attached) of a transient UI glitch during Dev Container sample session creation: empty placeholder sessions appear under the sample's generic group (e.g. 'Rust Sample') before the real session resolves into its actual repo group, and the stale empty entries linger until a reload or eventually self-clear.

## Change summary

Creating a session from a Dev Container sample briefly shows duplicate/empty session entries in the wrong group before the real session appears.

## Best solution

Trace the session skeleton→committed-session handoff in baseAgentHostSessionsProvider.ts together with the sample-vs-resolved-workspace grouping key in devContainerAgentHostService.ts (findDevContainerSample / devContainerWorktreeScope) so the UI list doesn't show a transient empty group tied to the sample identity before the real workspace/group resolves.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/sessions/contrib/providers/remoteAgentHost/browser/devContainerAgentHostService.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/devContainerAgentHostSessionsProvider.ts`
- **Validation:** A test or manual check creating a session from a Dev Container sample confirms no empty/placeholder group entry remains visible in the session list once the real session's workspace resolves, without requiring a window reload.
- **Behavior:**

  > When creating a new Dev Container sample session, the session list should never show an empty/stray session entry grouped under the sample's generic name (e.g. 'Rust Sample') once the real session has been created — either the skeleton session should appear directly under the final group, or the stale group should be removed as soon as the real session is committed, without needing a window reload. Acceptance: starting a sample session shows at most the eventual committed session's group; no leftover empty group lingers after creation settles.
- **Trace:**

  > The create-session flow seeds a 'skeleton' pending session (baseAgentHostSessionsProvider.ts, _pendingSessions.set + _onDidChangeSessions.fire around lines 6960-6965) and later swaps it for the committed session via _onDidReplaceSession once _waitForNewSession resolves (~line 6992). Separately, devContainerAgentHostService.ts computes devContainerWorktreeScope based on whether the workspace URI currently matches a known sample (findDevContainerSample, line 419) — which likely differs before and after the workspace resolves to the cloned repo folder, and the session list's grouping may pick up the sample-derived key for the skeleton and the repo-derived key for the committed session, producing a dangling empty group entry. Boundary: do not change the sample picker, the overall dev container provisioning flow, or the GC-based cleanup noted in the code comments at line ~7009 — the fix should only affect how/when the UI groups the skeleton vs. committed session.

## Evidence

- **reporter repro:** Issue includes a screenshot and a screen recording showing empty sessions under 'Rust Sample' that later disappear once real sessions land under 'vscode-remote-try-rust', on insiders build 1.141.0 (commit ae1080a).
- **skeleton/commit mechanism:** src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts (~lines 6960-7010) creates a 'skeleton' pending session fired via _onDidChangeSessions, later swapped for the committed session via _onDidReplaceSession — a plausible source of transient duplicate/empty entries if the group key differs between skeleton and committed session.
- **sample vs resolved grouping key:** src/vs/sessions/contrib/providers/remoteAgentHost/browser/devContainerAgentHostService.ts line 419 computes devContainerWorktreeScope differently depending on findDevContainerSample(workspaceUri), suggesting the sample-derived group label and the eventual repo-derived group label are computed from different inputs during the async resolve.
