# Issue #179742 — Provide a global context menu to auto expand lazy variables

[https://github.com/microsoft/vscode/issues/179742](https://github.com/microsoft/vscode/issues/179742)

## Summary

The discoverability gap remains on current main: VS Code supports automatic lazy-variable expansion through a setting, but provides no corresponding Variables context-menu action. This team-authored Backlog request has an unresolved product decision about contextual behavior and persistence, so it should remain open.

## Change summary

Expose a global Variables context-menu control that immediately changes lazy-variable expansion and preserves the selected behavior.

## Best solution

Resolve whether the Variables menu should offer a persisted expansion-mode toggle or a one-shot contextual action, without unexpectedly writing workspace settings. If a toggle is chosen, it should use the current `auto | on | off` setting contract and immediately update the visible variable tree.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`, `src/vs/workbench/contrib/debug/browser/variablesView.ts`, `src/vs/workbench/contrib/debug/test/browser/variablesView.test.ts`
- **Validation:** Add a targeted debug Variables view test that invokes the chosen menu action and verifies both the immediate lazy-variable display change and the selected persistence semantics.
- **Behavior:**

  > Users should be able to discover and control lazy-variable expansion from the debug Variables context menu. Activating the control must update the relevant visible variables immediately and follow an explicitly chosen persistence scope. Existing `debug.autoExpandLazyVariables` behavior, including its screen-reader-aware `auto` mode, must remain coherent and no obsolete boolean value may be written.
- **Trace:**

  > Current automatic expansion is driven by `debug.autoExpandLazyVariables`, registered as `auto | on | off` in `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`; `DebugSession.autoExpandLazyVariables` in `src/vs/workbench/contrib/debug/browser/debugSession.ts` interprets it, and `ExpressionContainer.fetchVariables` in `src/vs/workbench/contrib/debug/common/debugModel.ts` evaluates lazy children when enabled. The Variables context menu is also registered in `debug.contribution.ts`, with handlers in `variablesView.ts`, but no core expansion action exists. The uncertainty begins at the public behavior: maintainers disagreed between a one-shot contextual reveal and a persisted toggle, and the latest concern was avoiding unexpected workspace-settings writes. Preserve the enum setting and accessibility-aware `auto` behavior; the Java extension's obsolete boolean-writing action reported at https://github.com/microsoft/vscode/issues/227770 is not a model to copy.
- **Open decisions:**
  - Should the menu perform a one-shot recursive reveal for the selected variable, or toggle the persistent automatic-expansion mode for the Variables view?
  - If the choice persists, should it be stored at user, workspace, or session/view scope without unexpectedly modifying the workspace settings file?
  - Should the action affect only the selected variable subtree or immediately refresh all currently visible lazy variables?

## Evidence

- **existing capability:** `src/vs/workbench/contrib/debug/browser/debug.contribution.ts` registers `debug.autoExpandLazyVariables` with `auto`, `on`, and `off` values, while `src/vs/workbench/contrib/debug/browser/debugSession.ts` applies that configuration to debug sessions.
- **remaining gap:** The `MenuId.DebugVariablesContext` registrations in `src/vs/workbench/contrib/debug/browser/debug.contribution.ts` contain no lazy-variable expansion or reveal-all action, and the corresponding command handlers in `src/vs/workbench/contrib/debug/browser/variablesView.ts` do not implement one.
- **open product decision:** Maintainers discussed two observably different designs: a contextual “Reveal All Children” action at https://github.com/microsoft/vscode/issues/179742#issuecomment-1505897435 and a persisted view toggle at https://github.com/microsoft/vscode/issues/179742#issuecomment-1509258766. A later concern at https://github.com/microsoft/vscode/issues/179742#issuecomment-1624439494 notes that a workspace-scoped toggle should not unexpectedly write the workspace settings file.
- **related issue:** https://github.com/microsoft/vscode/issues/227770 concerned the Java extension's action writing the obsolete boolean setting after core migrated the setting to an enum; it was closed as extension-caused and does not implement or canonically track this core request.
