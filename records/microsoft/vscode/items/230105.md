## Evidence

- **Reporter trigger and maintainer diagnosis:** https://github.com/microsoft/vscode/issues/230105 reports that accepting the first conflict works but accepting the second fails, with undo and retry restoring operation, on Windows with VS Code 1.93.1 and extensions disabled. The maintainer's body edit identifies rapid successive acceptance while the first edit remains pending.
- **Verified older canonical and matching symptom:** https://github.com/microsoft/vscode/issues/107821 was created on 2020-09-30 and is currently OPEN. Its body reports acceptance doing nothing before repeated clicks, and https://github.com/microsoft/vscode/issues/107821#issuecomment-723339494 describes subsequent Accept Current actions failing to clear the intended conflict. https://github.com/microsoft/vscode/issues/107821#issuecomment-723346504 identifies clicking the next acceptance action before the previous conflict's gutter text disappears as the trigger. This matches the observable successive-acceptance failure, not merely the feature area, satisfying the stronger duplicate bar for a re-reviewed item.
- **Canonical scope includes current and incoming acceptance:** Despite its Accept Both title, https://github.com/microsoft/vscode/issues/107821#issuecomment-1294205706 explicitly covers accepting incoming/current changes before the preceding CodeLens disappears. It records waiting for CodeLens refresh or disabling merge-conflict.codeLens.enabled and using keybindings as workarounds. The canonical therefore owns the full reported timing problem.
- **Current source confirms overlapping-edit failure:** extensions/merge-conflict/src/codelensProvider.ts embeds conflict objects in 'known-conflict' command arguments. CommandHandler.accept in extensions/merge-conflict/src/commandHandler.ts calls conflict.commitEdit without awaiting or inspecting its result, allowing another acceptance while the first edit is pending. DocumentMergeConflict.commitEdit delegates to editor.edit; src/vs/workbench/api/common/extHostTextEditor.ts captures the document version and sends it to $tryApplyEdits. MainThreadTextEditor.applyEdits in src/vs/workbench/api/browser/mainThreadEditor.ts:479-483 returns false when that version no longer matches. Two requests constructed before the first edit updates the document can therefore silently reject the second acceptance. This was traced without executing or modifying the checkout.
