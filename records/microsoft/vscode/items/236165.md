# Issue #236165 — Customize shortcut to show the context menu for the highlighted File/Folder in the Files Explorer

[https://github.com/microsoft/vscode/issues/236165](https://github.com/microsoft/vscode/issues/236165)

## Summary

A real customization gap remains: Explorer lists recognize Shift+F10 directly in the list widget, but there is no assignable command equivalent to `editor.action.showContextMenu`. The issue is already correctly routed and should remain open under discussion.

## Change summary

Expose a customizable keyboard command that opens the context menu for the focused file or folder in the Explorer.

## Best solution

Provide an assignable command for the focused list or Explorer item while preserving Shift+F10, the Context Menu key, VoiceOver access, mouse behavior, focused-item anchoring, and multi-selection semantics. A maintainer should first decide whether this is an Explorer-only command or a uniform command for all workbench lists.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/list/listWidget.ts`, `src/vs/workbench/browser/actions/listCommands.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Add a targeted Explorer/list test that invokes the new command with a focused item and asserts the context menu targets that item, preserves an existing multi-selection when appropriate, and remains customizable independently of `editor.action.showContextMenu`.
- **Behavior:**

  > Users can assign any keybinding to open the context menu for the focused Explorer file or folder. Invoking it targets the focused item and preserves the same selection and compressed-folder behavior as Shift+F10. Existing Shift+F10, Context Menu key, VoiceOver, right-click, and editor-context-menu behavior remain unchanged. Acceptance includes command invocation for a single focused item and an item within an existing multi-selection.
- **Trace:**

  > The list widget in src/vs/base/browser/ui/list/listWidget.ts synthesizes context-menu events only from hard-coded DOM keyboard gestures and mouse events. ExplorerView in src/vs/workbench/contrib/files/browser/views/explorerView.ts consumes those events and performs the Explorer-specific target, selection, compressed-folder, and menu-context work. `editor.action.showContextMenu` is an EditorAction in src/vs/editor/contrib/contextmenu/browser/contextmenu.ts and cannot act on the Explorer. Generic focused-list commands already use IListService.lastFocusedList in src/vs/workbench/browser/actions/listCommands.ts, but the current list API exposes no command-oriented context-menu trigger. Preserve all existing accessibility gestures and Explorer selection semantics; do not redirect the editor command or alter mouse handling. The older same-request issue https://github.com/microsoft/vscode/issues/159745 was closed only by the feature-request upvote lifecycle and provides no implementation decision.
- **Open decisions:**
  - Should the assignable public command open the context menu for any focused workbench list, providing uniform behavior across Explorer and other trees, or be intentionally limited to the Files Explorer?

## Evidence
