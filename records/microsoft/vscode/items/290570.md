# Issue #290570 — Allow support for different editor types of the same file in GoTo/LocationLink

[https://github.com/microsoft/vscode/issues/290570](https://github.com/microsoft/vscode/issues/290570)

## Summary

Keep this accepted feature request open: current LocationLink navigation cannot specify a target editor type, and the existing openWith command does not cover provider-driven Ctrl+Click navigation. The request has 24 upvotes and was promoted to Backlog; the older related issues do not describe the same requested capability.

## Change summary

Allow Go To navigation links to select a particular editor representation of a file instead of relying on its default editor.

## Best solution

Provide an extension-facing navigation contract that can distinguish textual, tabular, and diagrammatic destinations for the same URI while preserving existing links' behavior. API owners should settle how non-text destinations interact with selection ranges and Peek before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTypeConverters.ts`, `src/vs/editor/common/languages.ts`, `src/vs/editor/contrib/gotoSymbol/browser/referencesModel.ts`, `src/vs/editor/contrib/gotoSymbol/browser/goToCommands.ts`, `src/vs/workbench/services/editor/browser/codeEditorService.ts`
- **Validation:** Use a development extension registering textual, tabular, and diagrammatic editors for one resource and a definition provider returning representation-specific destinations. Verify Ctrl+Click opens each requested representation, same-URI destinations remain distinguishable, and links without editor metadata retain their current behavior. Cover the agreed contract in extHostTypeConverters.test.ts and referencesModel.test.ts, and manually verify the chosen Peek behavior.
- **Behavior:**

  > An extension offers multiple editor representations of one file and needs built-in Go To navigation to address those representations separately. Navigating a representation-specific destination should open the requested editor without changing the file's default association. Destinations for the same URI must remain distinguishable when they target different representations. Existing links without an editor choice must behave as before; selection and Peek behavior for non-text targets must follow the agreed API contract.
- **Trace:**

  > The public LocationLink in src/vscode-dts/vscode.d.ts contains only URI and range metadata, and DefinitionLink.from/to in src/vs/workbench/api/common/extHostTypeConverters.ts preserves only those fields. SymbolNavigationAction in src/vs/editor/contrib/gotoSymbol/browser/goToCommands.ts opens through ICodeEditorService with a URI and selection; CodeEditorService.doOpenCodeEditor delegates to the workbench editor service and expects a code-editor control. ReferencesModel in src/vs/editor/contrib/gotoSymbol/browser/referencesModel.ts groups and deduplicates location results, so distinguishing representations is not solely an opening concern. vscode.openWith already exposes explicit editor selection through a command, but definition-provider links cannot express it. Preserve existing default associations and text-navigation behavior. The uncertainty starts at the public contract for non-text selections and Peek, not at whether the metadata gap exists. Related https://github.com/microsoft/vscode/issues/124498 discusses component-specific overrides but does not settle this API request.
- **Open decisions:**
  - What should targetRange and targetSelectionRange mean when a navigation destination opens a diagrammatic or tabular editor that does not expose a text selection?
  - When a destination specifies a non-text editor, should Peek show a textual preview, open the requested representation directly, or provide a representation-aware preview?

- **Existing capability is only partial:** src/vs/workbench/api/common/extHostApiCommands.ts:443-453 registers vscode.openWith(resource, viewId, options), and src/vs/workbench/browser/parts/editor/editorCommands.ts:544-551 passes that ID as options.override. This supports explicit command-driven opening, not an editor choice carried by a returned LocationLink.
- **Same-file destination identity:** The ReferencesModel constructor in src/vs/editor/contrib/gotoSymbol/browser/referencesModel.ts groups links by URI and deduplicates using _compareReferences. Supporting separate representations requires examining result identity as well as the final editor-opening call.

Both are open but neither establishes provider-selected editor destinations for the same file, so neither meets this re-reviewed item's duplicate bar.
