# Issue #292620 — Contextual Onboarding Nudges (Non-Sequential Tour)

[https://github.com/microsoft/vscode/issues/292620](https://github.com/microsoft/vscode/issues/292620)

## Summary

Keep open: the shared onboarding engine now provides contextual eligibility and shown-state tracking, but the browser-specific nudges remain unwired. The maintainer discussion supports experimenting with actionable guidance rather than generic welcome messages; neither the existing welcome placeholder nor the related issues completes that request.

## Change summary

Provide lightweight, dismissible browser guidance triggered independently by relevant user actions and milestones.

## Best solution

Define a small browser-specific experiment around actionable next-feature guidance, using the existing onboarding infrastructure rather than introducing another engine. Settle the initial triggers and dismissal behavior before implementing browser scenarios.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/browserView/electron-browser/browserView.contribution.ts`, `src/vs/workbench/contrib/browserView/electron-browser/features/browserWelcomeFeature.ts`, `src/vs/workbench/contrib/onboarding/common/onboardingScenario.ts`, `src/vs/workbench/contrib/onboarding/browser/onboardingService.ts`, `src/vs/workbench/contrib/onboarding/test/browser/onboardingService.test.ts`
- **Validation:** After selecting the initial scenario, exercise its qualifying browser action in an isolated profile: only eligible guidance appears, competing scenarios do not overlap, and dismissal/reload behavior matches the agreed contract. Add targeted scenario tests alongside onboardingService.test.ts covering eligibility and persisted suppression; confirm onboarding.enabled=false prevents automatic presentation.
- **Behavior:**

  > Browser guidance should appear independently when a user's current action makes a specific next feature useful, without requiring completion of a sequential tour. Guidance must remain lightweight and non-blocking, with defined temporary and permanent dismissal behavior. Acceptance should cover a qualifying action, an unrelated action that produces no nudge, competing eligible nudges, dismissal across reloads, and disabling automatic onboarding. The initial experiment should follow the maintainer's preference for actionable suggestions rather than a generic welcome.
- **Trace:**

  > The browser currently provides static empty-page guidance through BrowserWelcomeFeature in src/vs/workbench/contrib/browserView/electron-browser/features/browserWelcomeFeature.ts, registered by browserView.contribution.ts; visibility depends only on whether a URL exists. The shared onboarding engine already models context and observable triggers, priority, seen keys, experiments, and outcomes in src/vs/workbench/contrib/onboarding/common/onboardingScenario.ts, with evaluation and persistence in browser/onboardingService.ts. No browser scenario integration was found in these contributions. Preserve existing navigation, agent sharing boundaries, and ordinary empty-page behavior; the remaining work is contextual discovery, not a browser architecture change. The native browser surface also requires any overlaid guidance to participate in existing overlay handling. https://github.com/microsoft/vscode/issues/291056 is related command discoverability work, not a replacement for this request. The unresolved boundary is which actionable browser moments enter the first experiment and how temporary dismissal differs from permanent suppression.
- **Open decisions:**
  - Which actionable browser moments should the initial experiment cover: manual opening, agent opening, local navigation, or a development milestone?
  - When temporarily dismissed, what event makes a nudge eligible again, and should permanent suppression apply to one nudge or all browser guidance?
