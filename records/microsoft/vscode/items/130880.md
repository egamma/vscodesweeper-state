# Issue #130880 — Allow key bindings to work on tree view items

[https://github.com/microsoft/vscode/issues/130880](https://github.com/microsoft/vscode/issues/130880)

## Summary

Keep open: keybinding dispatch still does not supply tree-item context automatically, and the discussion calls for a generalizable, opt-in contract. Existing selection access offers partial workarounds, but no verified older canonical owns the same request.

## Change summary

Allow extension commands invoked by keyboard shortcuts to act on the appropriate tree items without first opening a context menu.

## Best solution

Define an explicit, opt-in way for tree-aware commands to obtain their invocation target, covering the Test Explorer without exposing arbitrary core tree internals. Keep when-clauses declarative and preserve existing command argument behavior for commands that do not opt in.

## Plan brief

- **Likely files:** `src/vs/platform/keybinding/common/abstractKeybindingService.ts`, `src/vs/workbench/contrib/testing/browser/testingExplorerView.ts`, `src/vs/workbench/contrib/testing/browser/testExplorerActions.ts`, `src/vs/workbench/api/common/extHostTesting.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** Use a test extension contributing a testing/item/context command and an Alt+F10 keybinding. Focus a test and invoke the shortcut without opening its context menu; verify the target matches the agreed contract. Repeat after moving focus independently of selection and with multiple selected tests. Verify context-menu invocation and ordinary keybindings with explicit arguments retain their existing behavior.
- **Behavior:**

  > A keyboard-invoked extension command should be able to identify the appropriate tree-item target without the user first opening a context menu. The original case is a testing/item/context command invoked with Alt+F10 in the Test Explorer. Acceptance must cover focus versus selection, multiple selected items, and invocation without prior context-menu interaction. Existing non-contextual commands and explicit keybinding arguments must remain compatible.
- **Trace:**

  > AbstractKeybindingService currently forwards only configured keybinding arguments, whereas TestingExplorerView.onContextMenu explicitly supplies its element to an action runner. ExtHostTesting's argument processor resolves supplied TestItemContext objects, but cannot manufacture missing invocation context. ExtHostTesting also exposes testing.getExplorerSelection as a partial testing-specific workaround; stable custom TreeView.selection similarly provides selection access without a general invocation contract. The original discussion requests an opt-in mechanism and rejects making when-clauses perform argument injection. Related focused-view and focused-item work is tracked at https://github.com/microsoft/vscode/issues/315186 and https://github.com/microsoft/vscode/issues/170248, respectively; neither establishes the full requested behavior. The unresolved boundary is the public targeting and opt-in contract, not a local missing guard.
- **Open decisions:**
  - Should opted-in commands receive contextual tree arguments directly, or should extensions obtain the invocation target through an explicit API?
  - For keyboard invocation, should the target be the focused item, the selected items, or the selection only when it contains the focused item?
  - Which trees may expose contextual targets, and how is ownership enforced so extensions cannot inspect unrelated core or extension tree internals?

## Evidence

- **Maintainer direction:** The supplied discussion on https://github.com/microsoft/vscode/issues/130880 explicitly treats this as new contextual-command capability: connor4312 requests a generalizable, opt-in design, while jrieken rejects using when-clauses to change callback behavior. This is not a confirmed regression in an established argument-passing contract.
- **Current keybinding dispatch:** src/vs/platform/keybinding/common/abstractKeybindingService.ts:393-396 invokes executeCommand(commandId) when no configured arguments exist, or passes resolveResult.commandArgs otherwise. This path does not derive arguments from the focused tree or its selection.
- **Context-menu path differs:** src/vs/workbench/contrib/testing/browser/testingExplorerView.ts:1077-1089 explicitly supplies the clicked element through getActionsContext and its action runner. src/vs/workbench/api/common/extHostTesting.ts:81-89 converts a supplied MarshalledId.TestItemContext into the extension's TestItem; that conversion cannot supply context absent from a keyboard invocation.
- **Existing-capability check:** FocusedViewContext in src/vs/workbench/common/contextkeys.ts:199 provides focusedView for declarative conditions, not command arguments. Stable TreeView.selection and onDidChangeSelection in src/vscode-dts/vscode.d.ts:12159-12164 allow extensions to inspect their own custom-tree selection, but do not provide the built-in Test Explorer's invocation target.
- **Testing-specific partial workaround:** src/vs/workbench/api/common/extHostTesting.ts:104-120 registers testing.getExplorerSelection, returning include/exclude objects resolved against the calling extension's controllers. This is a testing-specific pull mechanism, not automatic tree-item argument delivery or a general tree-command contract.
