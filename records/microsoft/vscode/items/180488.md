# Issue #180488 — DAP error response handling is confusing and inconsistent

[https://github.com/microsoft/vscode/issues/180488](https://github.com/microsoft/vscode/issues/180488)

## Summary

The issue remains necessary: a maintainer confirmed that `showUser` is intended to be independent of `url`, reproduced additional inconsistencies based on how a debug request is triggered, and classified the URL behavior as a bug. The broader notification policy still needs a maintainer decision before implementation.

## Change summary

Make DAP error responses honor `showUser` consistently and define predictable dialog, notification, and contextual error behavior across request types and invocation paths.

## Best solution

First make `showUser` authoritative regardless of whether the DAP error includes a URL, then establish one consistent policy for critical versus contextual request failures and document that client behavior in the Debug Adapter Protocol.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/rawDebugSession.ts`, `src/vs/workbench/contrib/debug/browser/debugService.ts`, `src/vs/platform/keybinding/common/abstractKeybindingService.ts`
- **Validation:** Add focused debug unit tests covering DAP error responses with `showUser` true, false, and omitted, both with and without `url`, and verify equivalent user-facing behavior when the same failing request originates from a keybinding and from a direct UI action.
- **Behavior:**

  > DAP error responses must honor `showUser` consistently whether or not an error URL is present. Equivalent failures should not produce contradictory or duplicate notifications merely because the request originated from a keybinding rather than a click. Error responses without displayable text must not create an empty dialog. Acceptance must cover `showUser` true, false, and omitted, with and without a URL, for both critical startup requests and contextual requests.
- **Trace:**

  > The primary behavior is in `src/vs/workbench/contrib/debug/browser/rawDebugSession.ts`, where response errors are converted into dialogs or notifications and the URL branch bypasses the expected `showUser` interpretation. `src/vs/workbench/contrib/debug/browser/debugService.ts` has another interpretation of absent `showUser`; errors from command-triggered requests may also bubble into `src/vs/platform/keybinding/common/abstractKeybindingService.ts`, creating invocation-dependent behavior. A maintainer reproduced this split with `setBreakpoints` and traced the intended `showUser` behavior through commits fe9bc04a75e92c4630cd1917320b8d8827e4548b and b7e8092b8df23b5017269335ed4a0968870a1269. Preserve contextual presentation in the debug console and watch UI, and avoid changing generic keybinding error handling for unrelated commands. The DAP ambiguity is discussed at https://github.com/microsoft/debug-adapter-protocol/issues/387.
- **Open decisions:**
  - Which failed DAP requests are critical enough to require a modal dialog rather than a notification or contextual error?
  - When `showUser` is omitted, should the client treat it as false everywhere or preserve a distinct default behavior?
  - Should `showUser=true` request an additional global notification, or only guarantee that the error is visible in the request's existing UI context?
  - When a URL is provided, should it appear as an action on the chosen notification/dialog only when `showUser=true`?
