# Issue #294263 — VoiceOver on MacOS stops reading the code editor after jumping to the end of a long code file

[https://github.com/microsoft/vscode/issues/294263](https://github.com/microsoft/vscode/issues/294263)

## Summary

Keep open: multiple reporters confirm that reaching the document end silences VoiceOver, and disabling EditContext restores speech. The workaround isolates a relevant input path but does not establish a fix or the precise root cause.

## Change summary

VoiceOver stops announcing editor navigation after reaching the end of a long file, with later reports also describing delays when restoring editor focus.

## Best solution

Restore continuous VoiceOver announcements through document-end navigation on the default editor input path. Diagnose the native EditContext screen-reader interaction on macOS before deciding whether the correction belongs in editor content synchronization or the platform accessibility implementation.

- **Behavior:**

Users must not need to open and dismiss the Command Palette to restore speech. Returning focus from Explorer must preserve usable speech and responsiveness. Acceptance should cover the default EditContext path and the existing textarea fallback on an affected macOS environment.
- **Trace:**

  > The discussion at https://github.com/microsoft/vscode/issues/294263 independently confirms the failure and confirms editor.editContext false as mitigation. In src/vs/editor/browser/view.ts, _instantiateEditContext switches between NativeEditContext and TextAreaEditContext; the effective option currently has no screen-reader exclusion. NativeEditContext forwards focus and rendering to ScreenReaderSupport, which invokes SimpleScreenReaderContent by default. That implementation replaces changed hidden-div text and synchronizes document selection with setBaseAndExtent; the shared SimplePagedScreenReaderStrategy supplies paged content. These paths explain what the workaround bypasses, but do not conclusively identify the VoiceOver failure mechanism. Start with an affected macOS reproduction and distinguish editor synchronization from platform accessibility behavior; preserve IME, clipboard, other screen readers, and textarea fallback semantics. Related reports https://github.com/microsoft/vscode/issues/323492 and https://github.com/microsoft/vscode/issues/338956 offer diagnostic context, not a verified canonical or fix.

## Evidence

- **Confirmed reproduction:** https://github.com/microsoft/vscode/issues/294263 provides explicit steps using a file of approximately 100 or more lines and Command+Down. adincebic independently confirmed the issue on VS Code 1.119.1 on May 13; the reporter confirmed continued problems on October 3.
- **Confirmed workaround:** In the October 10 discussion at https://github.com/microsoft/vscode/issues/294263, adincebic proposed setting editor.editContext to false, and Ghorthalon confirmed that this resolves both speech loss and the later focus-delay symptom. This is mitigation, not evidence that the default behavior is fixed.
- **Current input-path boundary:** src/vs/editor/common/config/editorOptions.ts registers editContext with default true; EffectiveEditContextEnabled.compute checks API support and that setting without excluding screen readers. src/vs/editor/browser/view.ts::_instantiateEditContext selects NativeEditContext when enabled and TextAreaEditContext otherwise, matching the confirmed workaround.
- **Relevant screen-reader synchronization:** NativeEditContext delegates focus and rendering to ScreenReaderSupport in src/vs/editor/browser/controller/editContext/native/. ScreenReaderSupport.prepareRender writes screen-reader content; the default SimpleScreenReaderContent updates the hidden div textContent and document selection using setBaseAndExtent. This identifies the investigation path, but source inspection alone does not prove why macOS VoiceOver stops speaking.
