# Issue #331746 — Markdown previews do not support path drag-and-drop

[https://github.com/microsoft/vscode/issues/331746](https://github.com/microsoft/vscode/issues/331746)

## Summary

Traced the underlying gap in core: the Markdown preview tab is a plain `WebviewInput` (registered via `vscode.window.registerWebviewPanelSerializer`), which never overrides `toUntyped()`, so `fillEditorsDragData` in dnd.ts skips it entirely — no path/uri-list data is ever placed on the drag event for that tab, unlike custom text editors.

## Change summary

Dragging a Markdown preview tab into the terminal (for path insertion) does nothing, while dragging the underlying markdown source tab works.

## Best solution

Give the Markdown preview's webview editor input (or `WebviewInput` generically, for webviews backed by a real document) a `toUntyped()` override that returns the source document's resource, mirroring `CustomEditorInput.toUntyped()` in src/vs/workbench/contrib/customEditor/browser/customEditorInput.ts, so `fillEditorsDragData` in src/vs/workbench/browser/dnd.ts picks up a real resource for drag/uri-list purposes.

## Evidence

- **no resource exposed:** src/vs/workbench/contrib/webviewPanel/browser/webviewEditorInput.ts: WebviewInput.resource is a synthetic `webviewPanel` scheme URI (path `webview-panel/webview-...`), and the class has no `toUntyped()` override, so it inherits the base `EditorInput.toUntyped()` which returns `undefined` (src/vs/workbench/common/editor/editorInput.ts:352-354).
- **dnd skips unresolved editors:** src/vs/workbench/browser/dnd.ts:278-297: fillEditorsDragData calls `resourceOrEditor.editor.toUntyped(...)`; when that returns undefined, `editor` stays undefined and the loop does `continue`, so no CodeDataTransfers.EDITORS entry and no text/uri-list entry (built at line 354-382) is ever produced for that tab.
- **existing pattern for the fix:** src/vs/workbench/contrib/customEditor/browser/customEditorInput.ts:396 shows `CustomEditorInput.toUntyped()` already returns a real `IResourceEditorInput` with the backing resource — the mechanism markdown preview's plain WebviewInput lacks.
- **extension confirms a real document uri exists:** extensions/markdown-language-features/src/preview/preview.ts:225/658/819 shows the preview always tracks `this.resource = document.uri`, so the underlying file path is known to the extension even though it never reaches the core drag machinery.
