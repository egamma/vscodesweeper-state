# Issue #183354 — Support `when` clause for `terminal.profiles` contribution point

[https://github.com/microsoft/vscode/issues/183354](https://github.com/microsoft/vscode/issues/183354)

## Summary

Keep this accepted Backlog request open: current source still lacks context-dependent visibility for contributed terminal profiles. The use case is clear, but the interaction with configured default profiles needs a maintainer decision before implementation.

## Change summary

Allow extensions to hide contributed terminal profiles using a when clause when prerequisites such as a remote server connection are unavailable.

## Best solution

Support context-dependent visibility in terminal profile selection surfaces while preserving configured profile identity and existing terminals. Settle what happens when a conditionally hidden profile is the configured default, including settings validation and launch behavior.

- **Reason:** This fills a core contribution-point gap that lets extensions present usable terminal choices consistently with other context-aware menus.

## Plan brief

- **Likely files:** `src/vs/platform/terminal/common/terminal.ts`, `src/vs/workbench/contrib/terminal/common/terminal.ts`, `src/vs/workbench/contrib/terminal/common/terminalExtensionPoints.ts`, `src/vs/workbench/contrib/terminal/browser/terminalProfileService.ts`, `src/vs/workbench/contrib/terminal/browser/terminalMenus.ts`, `src/vs/workbench/contrib/terminal/browser/terminalProfileQuickpick.ts`, `src/vs/workbench/contrib/terminal/test/browser/terminalProfileService.integrationTest.ts`
- **Validation:** Extend the terminal profile service tests to cover absent, true and false conditions and context-key transitions, preserving existing null exclusions and name overrides. Manually verify that a contributed profile follows a custom connection context key in the terminal dropdown and profile picker without reloading, then verify the agreed configured-default behavior when that key becomes false.
- **Behavior:**

  > An extension can declare a condition controlling whether its contributed terminal profile is offered for selection. A connection-dependent profile is absent when its connection context is false and appears when it becomes true, without a window reload. Profiles without a condition retain existing behavior, and changing a condition does not terminate existing terminals. Acceptance must also cover the agreed behavior when the hidden profile is configured as the default.
- **Trace:**

  > The terminal contribution schema in src/vs/workbench/contrib/terminal/common/terminal.ts and ITerminalProfileContribution in src/vs/platform/terminal/common/terminal.ts have no when field. TerminalContributionService in src/vs/workbench/contrib/terminal/common/terminalExtensionPoints.ts collects manifest profiles, while TerminalProfileService._updateContributedProfiles filters only explicit null settings and its contributedProfiles getter handles name overrides. getTerminalActionBarArgs in src/vs/workbench/contrib/terminal/browser/terminalMenus.ts builds menu actions from that list without context evaluation. The same service passes contributed profiles into default-profile configuration registration, which explains the default-profile concern in https://github.com/microsoft/vscode/issues/183354. Preserve existing terminal sessions, unconditional profiles, user exclusions and overrides; the uncertainty is the public meaning of a false condition for an explicitly configured default, not which helper or filtering layer to use. The closed predecessor https://github.com/microsoft/vscode/issues/144135 offers a launch-time workaround but does not satisfy selection visibility.
- **Open decisions:**
  - When a profile's condition is false, does the condition only hide selection entries while retaining explicit default-profile launches and settings validity, or does it make the profile unavailable for launch? If unavailable, what fallback or error should a configured default produce?

## Evidence

- **Missing contribution capability:** src/vs/workbench/contrib/terminal/common/terminal.ts:666-725 registers terminal.profiles with id, title, icon and titleTemplate, but no when property. ITerminalProfileContribution in src/vs/platform/terminal/common/terminal.ts:984-990 likewise has no condition field.
- **Existing behavior does not cover the request:** TerminalProfileService._updateContributedProfiles in src/vs/workbench/contrib/terminal/browser/terminalProfileService.ts:171-186 excludes profiles whose terminal.integrated.profiles.<platform> entry is null; contributedProfiles also handles user-defined name overrides. Neither evaluates extension context keys. Static user exclusion does not provide dynamic connection-dependent visibility, and disposing a registered provider does not remove its manifest contribution.
- **Selection and default-profile coupling:** getTerminalActionBarArgs in src/vs/workbench/contrib/terminal/browser/terminalMenus.ts:820-877 constructs actions for the supplied contributed profiles without context-condition evaluation. TerminalProfileService._refreshPlatformConfig passes its contributed profile list to registerTerminalDefaultProfileConfiguration, so filtering the shared list could also change default-profile settings validation.
