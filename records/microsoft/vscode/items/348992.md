## Evidence

- **Missing layout on main:** src/vs/workbench/services/keybinding/browser/keyboardLayouts/layout.contribution.win.ts imports 22 Windows layouts but no Japanese layout. The only Windows occurrence of 00000411 is a secondaryLayouts entry in en.win.ts, whose mapping remains US.
- **Failing selection and mapping path:** BrowserKeyboardMapperFactoryBase.keyboardLayouts exposes primary layouts only, and setKeyboardLayout() in src/vs/workbench/services/keybinding/browser/keyboardLayoutService.ts matches only keymapInfo.layout. Consequently keyboard.layout=00000411 cannot select a built-in Japanese mapping. getMatchedKeymapInfo() scores registered mappings, and _createKeyboardMapper() constructs WindowsKeyboardMapper from the selected mapping; no registered Windows JIS mapping supplies the reported @/VK_OEM_3 relationship.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/348995 is verified open and unmerged, explicitly says Fixes #348992, and proposes jp.win.ts plus registration and loader tests. Its author reports real Chrome 158 testing on Windows with a JIS keyboard: US detection and Ctrl+` labels before the change, Japanese detection and Ctrl+@ afterward. This is contributor-reported validation, not a locally executed check.
