# Issue #308703 — Electron Build Process Holding app.asar File

[https://github.com/microsoft/vscode/issues/308703](https://github.com/microsoft/vscode/issues/308703)

## Summary

Keep open: the discussion contains a concrete archive-lock reproduction and a workaround, but neither a verified fix nor an open canonical issue was found. The next useful step is to distinguish an Electron archive-handle issue from a VS Code filesystem caller on current Windows builds.

## Change summary

Electron build output archives remain locked after a build finishes, preventing subsequent builds until the editor exits.

## Best solution

Workspace observation and file access should not leave build-output archives locked against replacement. Reproduce the copy-only case in current VS Code on Windows, identify the holding process and operation, and determine whether the remaining fix belongs in VS Code or Electron; retain watcher exclusion as a temporary workaround.

## Evidence

- **Confirmed symptom and isolated trigger:** The October 8 comment on https://github.com/microsoft/vscode/issues/308703 reports Windows Restart Manager identifying Cursor's main process as the sole holder of default_app.asar. Copying a valid archive into a watched workspace reproduces the lock without running a build, and excluding the output folder prevents it. This is credible reproduction evidence, although it was obtained in Cursor rather than current VS Code.
- **Related extension attribution is inconclusive:** https://github.com/microsoft/vscode-cmake-tools/issues/4905 is closed, not an open duplicate target. Its maintainers reproduced the failure after opening app.asar with CMake Tools both enabled and disabled; the reporter later said it resolved without identifying a fixing change. See https://github.com/microsoft/vscode-cmake-tools/issues/4905#issuecomment-4805969119 and https://github.com/microsoft/vscode-cmake-tools/issues/4905#issuecomment-4844609962. This does not establish extension ownership of the present report.
- **Historical upstream lead:** https://github.com/microsoft/vscode/issues/66440 describes the same Windows Electron-build archive-lock symptom, including reproduction with extensions disabled and watcher exclusions as a workaround. A maintainer classified it as upstream in https://github.com/microsoft/vscode/issues/66440#issuecomment-540472598, but named no specific component or fixing commit. That is an investigation lead, not proof that the current report is fixed or exclusively upstream.
- **Current source does not establish the failing caller:** src/bootstrap-esm.ts maps ESM imports of 'fs' to Electron's ASAR-unaware original-fs. The filesystem provider and watcher implementations import 'fs'. Also, src/vs/platform/files/electron-main/diskFileSystemProviderServer.ts explicitly rejects recursive watches in the main process. Consequently, the reported main-process holder cannot conclusively be attributed to the recursive watcher from these sources alone.
- **Workaround is not resolution:** src/vs/workbench/contrib/files/browser/files.contribution.ts:294-310 registers files.watcherExclude for excluding paths from observation. This supports the reported output-folder workaround but does not provide normal watched-folder behavior without archive locks. Current defaults in that registration do not exclude node_modules, unlike the Cursor configuration described in the comment.
- **Canonical and fix search:** GitHub searches for open archive-lock reports did not identify another issue owning this specific symptom. Historical matching reports are closed. The checkout exposes only a single snapshot commit in the inspected history, so no concrete fixing commit could be established; no code was executed or modified.
