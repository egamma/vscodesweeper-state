# Issue #154988 — List widget - add api for a list item to specify not to receive focus

[https://github.com/microsoft/vscode/issues/154988](https://github.com/microsoft/vscode/issues/154988)

## Summary

The capability remains absent on current main: list pointer handling still focuses every row, while Source Control explicitly clears tree focus after transferring focus to its commit input or action button. This team-authored Backlog request should remain open for a shared list-widget design.

## Change summary

Allow a list or tree item containing an interactive control to opt out of receiving row focus.

## Best solution

Define consistent list/tree semantics for rows that delegate focus to embedded controls, then adopt them for the Source Control commit input and action-button rows without changing ordinary row selection or focus behavior.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/list/list.ts`, `src/vs/base/browser/ui/list/listWidget.ts`, `src/vs/base/browser/ui/tree/abstractTree.ts`, `src/vs/base/test/browser/ui/list/listWidget.test.ts`, `src/vs/workbench/contrib/scm/browser/scmViewPane.ts`
- **Validation:** Extend the ListWidget unit suite and run scripts/test.sh --grep "ListWidget"; verify pointer and arrow-key navigation skip an opted-out row or transfer focus according to the chosen contract, while ordinary rows retain existing focus and selection behavior.
- **Behavior:**

  > A list or tree row containing an interactive control can declare that the row itself must not receive focus. Pointer and keyboard interaction must follow one consistent rule for reaching or skipping that embedded control, and the list must not retain an active row focus marker for it. Ordinary rows, selection behavior, and assistive-technology focus reporting remain unchanged. In Source Control, the commit input and action button use this behavior without relying on clearing tree focus after opening.
- **Trace:**

  > List pointer handling in src/vs/base/browser/ui/list/listWidget.ts currently assigns focus to every handled row through MouseController.onViewPointer. Sequential navigation can accept transient filters, but src/vs/base/browser/ui/list/list.ts exposes no durable per-element focus eligibility contract, and AbstractTree's focusNavigationFilter in src/vs/base/browser/ui/tree/abstractTree.ts is reserved for find navigation. Source Control therefore transfers DOM focus to SCMInputWidget or SCMActionButton and immediately clears tree focus in SCMViewPane.open. Commit 428c8e29bd6b18729e4ba3c6af971f8db9eb8694 introduced that workaround. Preserve normal selection, context-menu, type-navigation, and accessibility behavior for all other rows; the unresolved boundary is how keyboard traversal should treat an opted-out row containing a focusable child.
- **Open decisions:**
  - When keyboard navigation reaches a non-row-focusable item, should focus move directly into its designated embedded control, or should list navigation skip the entire item?

## Evidence

- **current list behavior:** src/vs/base/browser/ui/list/listWidget.ts MouseController.onViewPointer still calls List.setFocus([focus]) for every row that reaches the pointer handler; IListOptions and IIdentityProvider expose no per-element focusability contract.
- **existing SCM workaround:** src/vs/workbench/contrib/scm/browser/scmViewPane.ts open() focuses SCMInputWidget or SCMActionButton and then explicitly calls this.tree.setFocus([]), preserving the workaround described by the issue.
- **partial navigation mechanism:** List.focusNext/focusPrevious accept call-scoped filters, and AbstractTree uses an internal focusNavigationFilter for find behavior, but SCM cannot declare that its input and action-button elements must never receive row focus across pointer, keyboard, and programmatic paths.
