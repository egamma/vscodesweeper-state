# Issue #229860 — [VSCode Extension API] Allow extensions to define custom disabled messages when a command is disabled

[https://github.com/microsoft/vscode/issues/229860](https://github.com/microsoft/vscode/issues/229860)

## Summary

Keep this accepted feature request open: contributed commands still cannot provide context-dependent explanations for disabled menu actions. It has 25 upvotes and a Backlog milestone; existing title customization and code-action disabled reasons do not cover the requested extension contribution API.

## Change summary

Allow extensions to supply explanatory tooltips when contributed commands are disabled by their enablement conditions.

## Best solution

Provide a supported command-contribution contract for localized disabled explanations in editor and explorer menu actions, preserving normal command titles and existing enablement semantics. Agree on whether explanations are declared against conditions or supplied dynamically before implementing the API.

## Plan brief

- **Likely files:** `src/vs/workbench/services/actions/common/menusExtensionPoint.ts`, `src/vs/platform/action/common/action.ts`, `src/vs/platform/actions/common/actions.ts`, `src/vs/platform/actions/common/menuService.ts`, `src/vs/platform/actions/browser/menuEntryActionViewItem.ts`, `src/vs/platform/actions/test/common/menuService.test.ts`, `src/vs/platform/actions/test/browser/menuEntryActionViewItem.test.ts`
- **Validation:** Add focused menu-service and menu-entry action-view-item tests for an extension-contributed command transitioning between enabled and disabled contexts: the selected explanation must appear while disabled, update when its relevant context changes, and restore the normal tooltip when enabled. Manually verify editor and explorer actions with a sample extension, including localized text and keyboard-accessible hover behavior; commands without explanation metadata must retain their existing behavior.
- **Behavior:**

  > Extensions currently cannot explain why a contributed editor or explorer command is disabled without changing its command title. The desired capability displays a localized explanation appropriate to the current disabling condition while keeping the command's normal identity and enabled-state presentation intact. Acceptance should cover context transitions, commands with more than one disabling condition, and unchanged behavior for existing contributions. The precise contribution contract and selection behavior need agreement before implementation.
- **Trace:**

  > In src/vs/workbench/services/actions/common/menusExtensionPoint.ts, IUserFriendlyCommand and the command contribution schema expose enablement but no explanatory tooltip contract; handleCommand registers tooltip: title and an independent precondition. MenuItemAction in src/vs/platform/actions/common/actions.ts computes the tooltip and enabled state separately, and MenuEntryActionViewItem.getTooltip in src/vs/platform/actions/browser/menuEntryActionViewItem.ts uses that tooltip with keybinding decoration. The internal ICommandAction interface already accepts static tooltip text, but that does not expose condition-dependent explanations to extensions. CodeAction.disabled.reason is a separate API and does not solve this contribution-path gap. Preserve existing command titles, menu visibility, enablement, and programmatic execution semantics; this request is not an execution-permission change. https://github.com/microsoft/vscode/issues/131205 documents title modification as a workaround, not an implementation of the requested API. Uncertainty begins at the public metadata contract and how multiple or changing disabled reasons are selected.
- **Open decisions:**
  - Should extensions declare localized explanations against context conditions, supply a dynamically updated explanation through a supported contract, or have both capabilities?
  - When multiple disabling conditions apply, should the UI display one explanation using a defined precedence or combine the applicable explanations?
