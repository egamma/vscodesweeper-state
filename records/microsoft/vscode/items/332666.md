# Issue #332666 — `read_file` does not report whether a line-range read reached EOF

[https://github.com/microsoft/vscode/issues/332666](https://github.com/microsoft/vscode/issues/332666)

## Summary

The capability remains missing on current main: successful text reads clamp the requested range to the file length but do not consistently tell the model that EOF was reached. This is a concrete, bounded enhancement to the core Copilot read tool and should remain open for an output-contract decision.

## Change summary

Expose an explicit end-of-file signal or equivalent length metadata when `read_file` reaches the end of a text file.

## Best solution

Give every ranged text read an unambiguous, token-efficient indication of the actual returned range and whether it reached EOF, across both supported parameter versions. Preserve the existing truncation distinction and the binary path's existing byte-range metadata.

## Plan brief

- **Likely files:** `extensions/copilot/package.json`, `extensions/copilot/src/extension/tools/node/readFileTool.tsx`, `extensions/copilot/src/extension/tools/node/test/readFile.spec.tsx`
- **Validation:** Run `cd extensions/copilot && npm run test:unit -- src/extension/tools/node/test/readFile.spec.tsx`; add assertions distinguishing a range that reaches EOF from one that stops before EOF for both V1 and V2 inputs, while retaining truncation and binary-range coverage.
- **Behavior:**

  > A successful ranged text-file read explicitly tells the calling model whether the returned range reached the end of the file. Reads that stop before EOF remain distinguishable from reads that reach or exceed EOF, and tool-imposed output truncation remains distinguishable from EOF. The behavior applies consistently to both V1 `startLine`/`endLine` and V2 `offset`/`limit` inputs; existing binary byte-range metadata remains intact.
- **Trace:**

  > `getParamRanges` in extensions/copilot/src/extension/tools/node/readFileTool.tsx already clamps requested text ranges against `snapshot.lineCount`, so it has the information needed to identify EOF. `ReadFileResult.render` receives the clamped range and snapshot but conditionally emits line-count context only for partial code-fenced reads or truncation, leaving ordinary EOF reads as bare content. The adjacent test suite at extensions/copilot/src/extension/tools/node/test/readFile.spec.tsx already exercises both parameter versions and is the bounded validation surface. Binary reads flow through `BinaryFileHexdump` and already expose byte bounds, total size, and truncation; keep that path unchanged. The uncertainty starts at the model-visible representation and token cost of the text metadata, not at the range calculation.
- **Open decisions:**
  - Should successful text reads expose EOF through structured/tagged metadata, or through a concise textual marker in the prompt result?
  - Should every ranged result include total line count and returned bounds, or should the contract expose only the minimal EOF boolean except when truncation requires more detail?
