# Issue #265406 — Chat: support `chat` subcommand in remote environments

[https://github.com/microsoft/vscode/issues/265406](https://github.com/microsoft/vscode/issues/265406)

## Summary

Remote CLI chat support remains missing in current source, and the maintainer explicitly endorsed implementing it. Keep this accepted Backlog request open; no verified older canonical or open fixing PR was found.

## Change summary

Support initiating VS Code chat with `code chat "hello world"` from WSL and other remote CLI environments.

Provide remote CLI parity with the existing desktop chat subcommand, preserving prompts and remote workspace context across both integrated-terminal IPC and external WSL forwarding. Plan the transport and remote file-context handling before implementation.

- **Validation:** In a trusted WSL workspace, run `code chat "hello world"` from both the integrated terminal and an external WSL shell: each must initiate chat with that exact prompt rather than open files named after the arguments. Repeat through a Remote-SSH integrated terminal, then check chat help, mode selection, remote file attachments, piped context, and unchanged native desktop invocation.
- **Behavior:**

  > Users can initiate VS Code chat from WSL and remote integrated terminals using the same `code chat` syntax available on the desktop. The prompt reaches chat intact and is not interpreted as a file path. The invocation retains the relevant remote workspace context, and supported file or stdin context must refer to remote content rather than unrelated local paths. Acceptance covers both external WSL forwarding and integrated remote-terminal invocation while preserving existing desktop behavior.
- **Trace:**

  > src/vs/server/node/server.cli.ts implements two transports: VSCODE_IPC_HOOK_CLI for remote integrated terminals and VSCODE_CLIENT_COMMAND for external WSL shells. isSupportedForPipe removes chat before parsing; the pipe path subsequently translates positional arguments into open requests. The external command path retains the shared chat registration but serializes its nested parsed object as a flat option. PipeCommand and CLIServerBase in src/vs/workbench/api/node/extHostCLIServer.ts have no chat operation, and src/vs/workbench/api/browser/mainThreadCLICommands.ts has no corresponding remote chat command. Desktop delivery uses WindowsMainService.handleChatRequest and ChatCommandLineHandler in src/vs/workbench/contrib/chat/electron-browser/chat.contribution.ts; the latter resolves attachments as local file URIs. These source paths establish the missing capability, but remote attachment delivery and window targeting have not been traced end-to-end. Preserve existing trust checks, native CLI behavior, and ordinary remote file-opening commands; unattended batch execution requested by https://github.com/microsoft/vscode/issues/254473 is outside this issue.

- **Remote IPC gap:** In src/vs/server/node/server.cli.ts, isSupportedForPipe excludes `chat`, so main removes its subcommand registration before parsing integrated remote-terminal arguments. Remaining positional inputs are translated into file paths and sent as an `open` request. src/vs/workbench/api/node/extHostCLIServer.ts defines and dispatches only open, openExternal, status, and extensionManagement requests; it has no chat request.
- **External WSL forwarding gap:** The VSCODE_CLIENT_COMMAND branch of src/vs/server/node/server.cli.ts retains the shared chat option, but reconstructs parsed arguments as flat `--key=value` strings. A nested parsed chat object becomes `--chat=[object Object]`, rather than preserving the `chat` subcommand and its prompt. The source therefore also lacks a functioning external WSL forwarding path.
