# Issue #335069 — First agent handoff blocked by process-wide message limit

[https://github.com/microsoft/vscode/issues/335069](https://github.com/microsoft/vscode/issues/335069)

## Summary

Traced conclusively in source: the `send_message` server tool's 50-message cap is a single closure-scoped counter created once per Agent Host process (not per session or per spawn chain), so once any 50 `send_message` calls have fired anywhere in that process's lifetime, every subsequent session — including a brand-new task session's very first handoff — is permanently refused with a bare error and no recovery path. This is a real, still-open design flaw, so it stays open pending a fix.

## Change summary

A task/subagent session's first `send_message` call to its coordinator is rejected because a process-wide send-message counter (shared across all unrelated sessions for the process's whole lifetime) has already hit 50.

## Best solution

Rescope the fan-out guard in `src/vs/platform/agentHost/node/shared/sessionServerTools.ts` (`maxSentMessages` / `sentMessageCount`, lines ~38, 1512, 1576-1581) so it bounds a single spawn chain or session rather than the whole process's lifetime, and make the thrown error explain the limit, current usage, and how to recover, rather than throwing a bare unactionable string.

## Evidence

- **the guard:** src/vs/platform/agentHost/node/shared/sessionServerTools.ts:38 `const maxSentMessages = 50;` documented as a 'Process-wide backstop against runaway send_message fan-out', and lines 1576-1581 throw `Refusing to send more than ${maxSentMessages} messages...` once `sentMessageCount >= maxSentMessages`, exactly matching the reporter's error text.
- **counter scope:** `sentMessageCount` is declared at line 1512 inside `createSessionServerToolGroup`, which is invoked exactly once via `buildServerToolGroups` in src/vs/platform/agentHost/node/agentServiceComposition.ts:165, which is itself called exactly once at Agent Host process startup in src/vs/platform/agentHost/node/agentHostBootstrap.ts:184-194 — so the counter is shared and never reset across every session/chat handled by that process for its entire runtime.
- **comment corroboration:** A second commenter (MominRaza) independently confirms: 'the limit is I think tied to the entire agent copilot host not a individual limit for each session... in this session that was first send_message call only,' matching the process-lifetime scoping found in source.
