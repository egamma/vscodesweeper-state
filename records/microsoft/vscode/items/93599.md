# Issue #93599 — Can't drag files from a remote vscode window to a local window

[https://github.com/microsoft/vscode/issues/93599](https://github.com/microsoft/vscode/issues/93599)

## Summary

The requested remote-to-local VS Code window transfer remains missing on current main. This team-authored, On Deck feature request has 40 upvotes and is the canonical issue for several later reports, so it should remain open while the reverted cross-window transfer design is revisited.

## Change summary

Allow files dragged from a remote VS Code Explorer to be copied into the Explorer of a local VS Code window.

## Best solution

Provide a reliable remote-to-local cross-window Explorer transfer that lets the receiving local window read files and directories from the source remote window, reports unavailable sources clearly, and preserves existing local-to-local and local-to-remote behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/dnd.ts`, `src/vs/platform/dnd/browser/dnd.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/browser/fileImportExport.ts`, `src/vs/code/electron-main/app.ts`, `src/vs/workbench/electron-browser/desktop.main.ts`
- **Validation:** Add and run targeted tests for routing read-only remote resources between windows, then manually drag a file and a directory from a Remote-SSH Explorer into a local VS Code Explorer and verify byte-identical copies; also verify local-to-local and local-to-remote drag-and-drop remain unchanged.
- **Behavior:**

  > Dragging a file or directory from the Explorer of a remote VS Code window into the Explorer of a local VS Code window copies the resource to the selected local destination. Transfers preserve names and contents, provide progress for large resources, and report a clear failure if the source remote window disconnects. Existing local-to-local and local-to-remote drag-and-drop behavior must remain unchanged.
- **Trace:**

  > FileDragAndDrop.onDragStart in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts delegates to fillEditorsDragData in src/vs/workbench/browser/dnd.ts. That function places vscode-remote URIs in DataTransfers.RESOURCES but only places file:// paths in CodeDataTransfers.FILES; extractEditorsAndFilesDropData in src/vs/platform/dnd/browser/dnd.ts revives the remote URI in the receiving window. ExternalFileImport in src/vs/workbench/contrib/files/browser/fileImportExport.ts activates the URI scheme and then filters out resources without a provider, which excludes a remote URI in an unrelated local window. https://github.com/microsoft/vscode/pull/320685 previously introduced an Electron-main-mediated remote file-system proxy across these layers, but https://github.com/microsoft/vscode/pull/323490 reverted it after the regressions documented in https://github.com/microsoft/vscode/issues/321354. The uncertainty is therefore in designing and validating a regression-safe cross-window transport, not in the requested product behavior. Keep remote-to-native OS drag-and-drop and the separate vscode.dev null-error report outside this issue's acceptance boundary.

## Evidence

- **current source gap:** src/vs/workbench/browser/dnd.ts serializes file-system resources, including remote URIs, into DataTransfers.RESOURCES, while FileDragAndDrop.onDragStart in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts adds CodeDataTransfers.FILES only for file:// resources. ExternalFileImport in src/vs/workbench/contrib/files/browser/fileImportExport.ts then discards candidates for which the receiving window has no file-system provider, so a local window cannot import the source vscode-remote URI.
- **reverted implementation:** https://github.com/microsoft/vscode/pull/320685 added a cross-window remote file-system proxy and merged on 2026-06-11, but testing found multiple regressions and https://github.com/microsoft/vscode/pull/323490 reverted it on 2026-06-29. The proxy files are absent and the original source path remains on current main.
