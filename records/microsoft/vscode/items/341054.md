# Issue #341054 — Copilot Chat: rendering a chat response blocks on tree-sitter symbol resolution of every inline-code span (multi-second freeze / ParserWorkerTimeoutError)

[https://github.com/microsoft/vscode/issues/341054](https://github.com/microsoft/vscode/issues/341054)

## Summary

Thanks for the detailed report. The code path is confirmed on current main: the inline-code linkifier awaits symbol resolution for every unique span, and each resolution parses the whole referenced document with tree-sitter under a 3s worker timeout.

## Change summary

Rendering a chat response blocks on tree-sitter symbol resolution for each inline-code span, causing multi-second freezes and worker timeouts.

## Best solution

Make inline-code linkification non-blocking: render the response immediately and apply symbol links asynchronously. Also bound the parse cost with a document size cap or a cached AST per document, and avoid restarting the worker on every timeout.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/linkify/vscode-node/inlineCodeSymbolLinkifier.ts`, `extensions/copilot/src/extension/linkify/vscode-node/findWord.ts`, `extensions/copilot/src/platform/parser/node/parserServiceImpl.ts`
- **Validation:** Run a linkify test with a large referenced document and several distinct inline-code spans, and assert that linkify returns without waiting for symbol resolution (or within a bounded time).
- **Behavior:**

  > A chat response with inline-code spans renders immediately and is never blocked by symbol resolution. Links may appear shortly afterwards, and documents above a size limit are skipped. Acceptance: with a large active document and several distinct spans, rendering is not delayed and no ParserWorkerTimeoutError appears in the logs.
- **Trace:**

  > InlineCodeSymbolLinkifier.linkify awaits Promise.all over the unique spans. Each span goes through ReferencesSymbolResolver in findWord.ts, which parses doc.getText() through IParserService. In parserServiceImpl.ts, a call past 3s restarts the worker and throws ParserWorkerTimeoutError, and arguments are deep-cloned with JSON per call. Do not change the linkification output format for non-tree-sitter languages. The uncertainty is which mitigation to use, since async linkification affects how the progressive-render pipeline handles late links.
- **Open decisions:**
  - Should links appear asynchronously after the response renders, or should linkification be skipped when it exceeds a time budget?
  - Should there be a document size limit above which symbol linking is skipped, and should it be configurable?
