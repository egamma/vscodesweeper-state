# Issue #330327 — Dismissing a promo banner should disable it from showing again

[https://github.com/microsoft/vscode/issues/330327](https://github.com/microsoft/vscode/issues/330327)

## Summary

Team-authored report; traced the likely mechanism in `ChatPromoNotificationContribution` — dismissal is persisted per `promo.id` (`chat.dismissedPromoIds`, APPLICATION scope), so a *different* rotating promo (a new id) will legitimately reappear even after the user dismissed a prior one, which reads to the user as "it keeps showing up" — this is the most plausible source given it's the only promo-banner feature in the tree, though the report doesn't confirm which banner or promo id(s) were involved.

## Change summary

Requests that dismissing a promo banner suppress it (or promo banners generally) from reappearing, rather than only suppressing that specific promo instance.

## Best solution

Clarify (or change) the intended semantics in src/vs/workbench/contrib/chat/browser/chatPromoNotification.ts: either surface the existing `mute` (bell-slash, "stop showing this entirely") affordance more prominently as the answer to this request, or decide product-side whether the plain dismiss (X) should also suppress future distinct promo ids rather than only the one just shown.

## Evidence

- **dismissal keyed by promo id:** src/vs/workbench/contrib/chat/browser/chatPromoNotification.ts:106-118 persists dismissed promo ids in `chat.dismissedPromoIds` (StorageScope.APPLICATION), and `_update()` (line 54) only skips a promo whose exact id is in that set — a different promo id is never suppressed by a prior dismissal.
- **existing mute affordance:** src/vs/workbench/contrib/chat/browser/widget/input/chatInputNotificationService.ts:53-59 defines an `IChatInputNotificationMuteAction` explicitly described as "a 'stop showing this entirely' action that is distinct from a one-off dismissal", suggesting the maintainers already anticipated this exact gap but the promo notification doesn't currently wire it up (no `mute` field is set in chatPromoNotification.ts's `setNotification` call, lines 80-94).
- **in-memory dismiss state per session:** src/vs/workbench/contrib/chat/browser/widget/input/chatInputNotificationService.ts:160-205 — the service's own `_dismissed` set is in-memory only per window/session and is not itself persisted; persistence for promos specifically relies on the contribution re-deriving `dismissed` from storage on each `_update()`, so the reappearance the reporter describes is more likely a distinct promo id than a persistence bug.
- **not yet a duplicate:** Candidate canonical https://github.com/microsoft/vscode/issues/330398 is about dismiss not syncing across windows for the same promo — a narrower, different symptom than 'the banner should stop showing at all', so it does not clearly own this report's full scope.
