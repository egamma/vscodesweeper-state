# Issue #180958 — Git - Use gitattributes encoding when opening a file

[https://github.com/microsoft/vscode/issues/180958](https://github.com/microsoft/vscode/issues/180958)

## Summary

Keep this accepted, 39-upvote feature request open: current encoding selection does not consult .gitattributes. The related Git diff reports do not cover automatically choosing an encoding when opening working-tree files.

## Change summary

Use per-file encoding declarations in .gitattributes when opening files.

## Best solution

Provide repository-aware encoding selection for working-tree files without requiring users to duplicate attribute rules in VS Code settings. First settle which attributes are supported and their precedence against explicit encoding choices, detected encodings, and files.encoding.

## Plan brief

- **Likely files:** `src/vs/workbench/services/textfile/browser/textFileService.ts`, `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `extensions/git/src/git.ts`, `extensions/git/src/repository.ts`
- **Validation:** In a temporary Git repository, declare *.html encoding=utf-8 and *.c encoding=cp1252 and create matching non-ASCII files. Open them without per-language encoding overrides and verify readable content and the selected encoding against the agreed attribute contract. Cover explicit Reopen with Encoding precedence, files without matching attributes, and any agreed working-tree-encoding support; preserve existing settings/workspace-file encoding overrides.
- **Behavior:**

  > The request is to open repository files using their applicable .gitattributes encoding declarations instead of requiring duplicated VS Code configuration. The examples assign UTF-8 to HTML files and CP1252 to C files. Acceptance should verify non-ASCII content and the selected encoding for both patterns, plus the agreed behavior when an explicit user choice or another encoding signal conflicts. Files without applicable attributes should retain existing behavior.
- **Trace:**

  > EncodingOracle in src/vs/workbench/services/textfile/browser/textFileService.ts owns the inspected read-encoding selection: built-in resource overrides, explicit or detected encodings, configured files.encoding, and UTF-8 fallback. src/vs/workbench/contrib/files/browser/files.contribution.ts exposes configured defaults and guessing, neither of which reads attribute patterns. The Git command and repository wrappers live in extensions/git/src/git.ts and extensions/git/src/repository.ts; the bridge from repository attribute lookup to ordinary file decoding remains to be designed. Preserve protected settings/workspace-file overrides and avoid treating this as only a Git diff fix. https://github.com/microsoft/vscode/issues/127441 and https://github.com/microsoft/vscode/issues/334092 concern baseline-versus-working-tree decoding, a related but distinct requirement. This report explicitly uses encoding, whereas those reports use working-tree-encoding; the record does not settle whether this feature should support one or both.
- **Open decisions:**
  - Should file-opening selection honor the reported encoding attribute, working-tree-encoding, or both, and which wins when both are present?
  - Where should an applicable attribute sit relative to an explicit Reopen with Encoding choice, BOM/content detection, and language- or workspace-configured files.encoding?
