# Issue #193143 — Git - After Rebase, recommend Push (Force)

[https://github.com/microsoft/vscode/issues/193143](https://github.com/microsoft/vscode/issues/193143)

## Summary

Keep open: current source still offers Sync after a completed rebase, without surfacing an appropriate force-push alternative. Existing commands provide a workaround, but neither verified related issue owns this specific post-rebase guidance request.

## Change summary

Provide appropriate push guidance after rebasing a published branch instead of leading users toward pulling rewritten history through Sync.

## Best solution

Make the built-in Git action button and rebase warning offer a clear, explicitly authorized way to publish rewritten history while preserving force-push safeguards. Decide when rebase detection warrants changing the primary action, rather than treating every diverged branch as safe to force-push.

Cover the agreed behavior in Git extension tests.
- **Behavior:**

  > After intentionally rebasing a published branch onto its parent, users should receive clear guidance for publishing rewritten history instead of being led toward pulling the old commits back through Sync. The appropriate publishing action should be discoverable from the SCM workflow without navigating a hidden menu. Existing force-push permissions, configured safety modes, and confirmation must remain effective. Acceptance must distinguish intentional local rewriting from genuine remote changes and must avoid contradictory pull advice when the user declines the post-rebase pull.
- **Trace:**

  > ActionButton.getSyncChangesActionButton() in extensions/git/src/actionButton.ts bases its recommendation on ahead/behind counts and whether a rebase is currently active; it has no completed-rebase state. Repository.checkIfMaybeRebased() in extensions/git/src/repository.ts already provides a patch-equivalence heuristic, but only inside pull/sync execution, where its false result skips pulling without preventing the subsequent ordinary push. PushRejected handling in extensions/git/src/commands.ts then advises Pull, matching the reported follow-up. The explicit git.pushForce command already applies permission, force-mode, and confirmation settings; these safeguards and ordinary non-rebased Sync behavior are boundaries to preserve. Divergence or patch equivalence alone does not establish that replacing remote history is appropriate. Related design discussions are https://github.com/microsoft/vscode/issues/174198 and https://github.com/microsoft/vscode/issues/267911, neither a verified duplicate of this request.
- **Open decisions:**
  - What evidence of an intentional completed rebase is sufficient to promote force-push to the primary SCM action, and when should it remain an explicit alternative accompanied by a warning?
