# Issue #239416 — Git - submodule displayed with a file icon in the source control panel

[https://github.com/microsoft/vscode/issues/239416](https://github.com/microsoft/vscode/issues/239416)

## Summary

Keep open: current source still assigns file icons to submodule change entries. The fixes discussed in the thread concern status decorations and opening diffs, not the reporter's clarified folder-icon problem.

## Change summary

Display a changed submodule directory with a folder icon rather than a file icon in the parent repository's Source Control changes.

## Best solution

Make Source Control represent submodule directory entries with the appropriate folder icon in both list and tree views, while preserving their modified status, actions, and submodule diff behavior.

## Plan brief

- **Likely files:** `extensions/git/src/repository.ts`, `src/vs/workbench/contrib/scm/common/scm.ts`, `src/vs/workbench/contrib/scm/browser/scmViewPane.ts`
- **Validation:** Establish a renderer regression check that distinguishes a modified submodule directory from an ordinary modified file. Manually confirm with the built-in Seti icon theme: create a parent repository with a committed submodule, switch the submodule to a branch with a different HEAD, and inspect the parent Changes entry in both list and tree modes. The submodule must receive a folder icon, ordinary files must retain file icons, and staging and opening the submodule diff must remain functional.
- **Behavior:**

  > Changing a submodule to a different commit correctly produces a modified entry in the parent repository, but that directory currently receives a file icon. The entry should use the icon theme's folder representation in both Source Control list and tree views. Ordinary changed files must retain their file icons. Modified status, staging actions, and submodule diff opening must remain unchanged.
- **Trace:**

  > extensions/git/src/repository.ts constructs modified entries as Resource objects; their contextValue describes the owning repository kind, not whether the individual path is a submodule directory. ISCMResource in src/vs/workbench/contrib/scm/common/scm.ts carries no file-kind metadata. In src/vs/workbench/contrib/scm/browser/scmViewPane.ts, the data source returns direct resources in list mode and unwraps childless resource-tree nodes in tree mode. ResourceRenderer.renderElement assigns FileKind.FILE to those direct resources, and renderIcon passes it to the label. This establishes the classification defect without executing VS Code. Preserve parent-repository gitlink status and existing diff behavior; the thread's earlier fixes address different symptoms. The remaining planning work is to establish a focused renderer validation harness and determine the bounded metadata path without assuming that repository context identifies the changed resource itself.
