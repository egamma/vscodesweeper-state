# Issue #239416 — Git - submodule displayed with a file icon in the source control panel

[https://github.com/microsoft/vscode/issues/239416](https://github.com/microsoft/vscode/issues/239416)

## Summary

Still reproduces on current main: the Source Control resource renderer hardcodes FileKind.FILE for every resource state, so a submodule folder listed as a change gets a file icon; there is no channel today for the git extension to tell the SCM UI that a resource is a directory.

## Change summary

A modified git submodule is listed in the Source Control panel with a file icon instead of a folder icon.

## Best solution

Give SCM resource states a way to declare their file kind (folder/submodule) and have the git extension set it for submodule resources, so ResourceRenderer in src/vs/workbench/contrib/scm/browser/scmViewPane.ts renders a folder icon instead of the hardcoded FileKind.FILE.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/scm/browser/scmViewPane.ts`, `src/vs/workbench/contrib/scm/common/scm.ts`, `src/vs/workbench/api/common/extHostSCM.ts`, `src/vs/workbench/api/browser/mainThreadSCM.ts`, `extensions/git/src/repository.ts`
- **Validation:** With a repository containing a submodule on a different branch, the submodule entry in the Source Control view renders with a folder icon (both list and tree view modes, with and without a file icon theme), while ordinary file changes are unchanged.
- **Behavior:**

  > A modified git submodule listed in the Source Control view should render with a folder icon, matching what it is on disk, instead of the generic file icon it gets today. Ordinary file resource states must keep their current file icons, and tree-view folder nodes must keep rendering as folders. Acceptance: in a workspace with a submodule checked out to a different branch, the submodule row in Source Control shows a folder icon in both list and tree view modes; existing SCM view tests still pass.
- **Trace:**

  > ResourceRenderer.renderElement in src/vs/workbench/contrib/scm/browser/scmViewPane.ts (line ~535) computes `fileKind` as FileKind.FOLDER only for ResourceTree nodes and FileKind.FILE for every leaf ISCMResource, then passes it to the file label — so a submodule resource state can never render as a folder. ISCMResource/ISCMResourceDecorations in src/vs/workbench/contrib/scm/common/scm.ts carry no kind information, and `decorations.icon` drives the separate right-hand decoration badge in ResourceRenderer.renderIcon, not the label icon, so it is not a usable substitute. The git extension already identifies submodule resources by comparing fsPath against `this.repository.submodules` (extensions/git/src/repository.ts:581), so the missing piece is plumbing that fact through extHostSCM/mainThreadSCM to the renderer. Boundary: do not change the decoration-badge path, the tree-node folder rendering, or the existing 'M' status decorations a maintainer already fixed for 1.97. Note the checkout here is shallow (single commit), so history could not be searched; the source state above is current main. Related, different symptoms: https://github.com/microsoft/vscode/issues/205125 and https://github.com/microsoft/vscode/issues/333950.
- **Open decisions:**
  - Should SourceControlResourceState gain a public (initially proposed) way to declare its kind — e.g. a folder/submodule hint on the resource state or its decorations — or should core infer directory-ness another way?
  - If a hint is added, is it a generic file-kind/folder flag usable by any SCM provider, or a git-specific submodule concept?
  - Should a submodule row get a plain folder icon, or a distinct submodule affordance (e.g. a root-folder/repository icon) to distinguish it from an ordinary directory?

## Evidence

- **root cause on main:** src/vs/workbench/contrib/scm/browser/scmViewPane.ts:535 — `const fileKind = ResourceTree.isResourceNode(resourceOrFolder) ? FileKind.FOLDER : FileKind.FILE;`. A leaf SCM resource state is always rendered as a file, so a submodule directory shown as a change gets a file icon regardless of icon theme.
- **no API channel:** ISCMResource / ISCMResourceDecorations in src/vs/workbench/contrib/scm/common/scm.ts expose only icon/iconDark/tooltip/strikeThrough/faded — the decoration icon is the separate right-hand badge (ResourceRenderer.renderIcon), not the label icon — so the git extension cannot currently signal that a resource is a folder.
- **git extension knows it is a submodule:** extensions/git/src/repository.ts:581-584 already matches a resource's fsPath against `this.repository.submodules` when opening it, so the information exists extension-side.
- **maintainer thread:** In https://github.com/microsoft/vscode/issues/239416 a maintainer confirmed the separate 'M' decoration bug was fixed for 1.97 and that listing the submodule folder is expected; the reporter then clarified the remaining ask is the icon, which was reproduced with all extensions disabled. That icon part is what remains open.
- **candidate canonicals checked:** https://github.com/microsoft/vscode/issues/205125 (stage/discard don't work for submodules) and https://github.com/microsoft/vscode/issues/333950 (submodules arbitrarily hidden) are both about different observable symptoms, not the icon; neither owns this work.
