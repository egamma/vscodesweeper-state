# Issue #331572 — chat sessions are gone

[https://github.com/microsoft/vscode/issues/331572](https://github.com/microsoft/vscode/issues/331572)

## Summary

Traced a real, current-main defect: when a workspace transitions (e.g. single folder promoted to an untitled multi-root workspace), ChatSessionStore.migrateSessionsToNewWorkspace copies the .jsonl transcript files but never migrates or rebuilds the chat.ChatSessionStore.index entries for the new workspace's storage scope, so migrated sessions vanish from the Chat view even though the underlying files are intact on disk.

## Change summary

Two days of chat sessions disappeared from the Chat view after a workspace transition, even though nothing was deliberately deleted.

## Best solution

In src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts, handleWorkspaceTransition/migrateSessionsToNewWorkspace should not just clear indexCache and flush a near-empty index for the new StorageScope.WORKSPACE bucket — it needs to populate index entries for the copied session files (either by reading the old workspace's index alongside the transcripts, or by reconciling the index against the chatSessions/ directory), so migrated sessions remain visible after the transition.

## Auto-fix candidate

- **Auto-fixable:** no
- **Rationale:** The defect is clearly localized to migrateSessionsToNewWorkspace, but a correct fix needs either reading the old workspace's storage index (which IStorageService only exposes for the *current* workspace, not an arbitrary prior one) or parsing/deserializing each copied session file to rebuild metadata — both require deeper knowledge of the session load/storage architecture than a safe automatic patch, so this needs a maintainer-directed fix rather than an automated one.

## Evidence

- **migration copies files but not index:** src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts lines 100-183: handleWorkspaceTransition computes oldStorageRoot/newStorageRoot from workspace IDs, then migrateSessionsToNewWorkspace copies *.json/*.jsonl files (line 151-168) and logs 'Copied N chat session files ... (originals preserved at old location)' (line 170) — matching the reporter's log excerpt exactly.
- **index cleared, not rebuilt:** Lines 172-178: after copying files, indexCache is simply set to undefined and flushIndex() is called, which just persists whatever internalGetIndex() currently holds (empty or the new workspace's pre-existing, unrelated index) to StorageScope.WORKSPACE (line 422-436) — no code path reads the old index or rebuilds entries from the copied files.
- **storage is scoped per-workspace:** getIndexStorageScope() (line 432-436) returns StorageScope.WORKSPACE for non-empty windows, meaning the index lives in that workspace's own state.vscdb — a new workspace ID after transition means a fresh, unrelated index bucket, exactly as the reporter's 'opus findings' describe.
- **no reconciliation on startup:** No code in chatSessionStore.ts scans storageRoot/chatSessions to rebuild missing index entries from files present on disk; grep for reconcile/rebuildIndex/readdir in the file returns nothing.
- **related but distinct request:** https://github.com/microsoft/vscode/issues/305818 tracks the broader, separate scenario of orphaned sessions from moved/renamed/deleted workspace folders; this issue's root cause (index not migrated during an in-app workspace-type transition) is a different, more specific code path, so it is not a clean duplicate of that broader feature request.
