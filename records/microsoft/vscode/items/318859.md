# Issue #318859 — Don’t collapse 3rd-party stack frames (or at least not as aggressively)

[https://github.com/microsoft/vscode/issues/318859](https://github.com/microsoft/vscode/issues/318859)

## Summary

Current main still automatically groups consecutive `subtle` or deemphasized stack frames, and expansion is remembered only for the current frame objects. This remains a valid debugger UX request, but the preferred user-facing behavior needs a debug-area decision.

## Change summary

Make automatic collapsing of third-party debug stack frames less aggressive, configurable, or persistent across stops in a debug session.

## Best solution

Let users inspect subtle frames without repeatedly expanding them, while retaining compact call stacks for users who prefer the current behavior. The debug owners should choose between an opt-out setting, session-level expansion persistence, or narrower collapse conditions before implementation.

- **Behavior:**

  > Users who need third-party frames should not have to re-expand the same logical stack-frame group after every stop in one debug session, or they should be able to disable automatic collapsing explicitly. The default behavior should remain compact unless the maintainer chooses to change that default. Normal frames and adapters that do not mark frames as subtle must remain unaffected. Acceptance should cover consecutive subtle frames, a subsequent call-stack refresh, and the selected default or configuration semantics.
- **Trace:**

  > CallStackDataSource.getThreadChildren in src/vs/workbench/contrib/debug/browser/callStackView.ts groups consecutive frames accepted by `isFrameDeemphasized`. Clicking the generated group adds the current `IStackFrame` objects to `deemphasizedStackFramesToShow`, but that WeakSet cannot carry the choice to newly created frames after execution resumes. `isFrameDeemphasized` in src/vs/workbench/contrib/debug/common/debug.ts deliberately treats DAP `subtle` and source `deemphasize` alike, following https://github.com/microsoft/vscode/pull/209078. The boundary is call-stack presentation: do not change DAP semantics, adapter stepping behavior, or `justMyCode`; preserve current grouping for users who have not selected the new behavior. The uncertainty begins at the public UX contract: configuration, session-persistent expansion, and conditional collapsing provide materially different controls.
- **Open decisions:**
  - Should VS Code expose a setting that disables automatic grouping of subtle/deemphasized frames, remember manual expansion for the remainder of the debug session, or provide both behaviors?
  - If expansion is remembered, what stable logical identity should it follow across stops: all subtle frames in the session, a contiguous group, or matching frame/source identities?
  - Should collapse eligibility change when the stopped breakpoint frame is subtle or when the call stack contains no normal user-code frame?
