# Issue #337349 — Diff editor toolbar can split Previous/Next Change actions when space is limited

[https://github.com/microsoft/vscode/issues/337349](https://github.com/microsoft/vscode/issues/337349)

## Summary

Real, code-confirmed UX papercut: the responsive toolbar's overflow algorithm hides one non-separator action at a time from the end, with no concept of 'paired' or 'atomic' actions, so adjacent Previous/Next Change items can split. Fixing it well requires deciding how (or whether) to expose a generic grouping/atomicity concept in the shared toolbar component, so this belongs with a maintainer before implementation.

## Change summary

Diff editor's Previous Change and Next Change toolbar buttons can end up split — one visible, one pushed into the overflow menu — when horizontal space is limited.

## Best solution

Design a small opt-in 'keep together' / atomic-group concept for WorkbenchToolBar's responsive overflow (or a diff-editor-specific menu grouping) so logically paired navigation actions move to overflow as a unit; land it in toolbar.ts and apply it to the Previous/Next Change menu items in editor.contribution.ts.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/toolbar/toolbar.ts`, `src/vs/workbench/browser/parts/editor/editor.contribution.ts`
- **Validation:** Once a grouping mechanism is designed, add a toolbar test asserting that when only one of two 'grouped' actions fits, both are moved into the overflow menu together (and both restored together as space returns).
- **Trace:**

  > getActionsToHide() in src/vs/base/browser/ui/toolbar/toolbar.ts picks one non-separator action (from the end, or start depending on overflowFromStart) to hide, and only widens the hidden range across contiguous Separator instances — never across two adjacent regular actions. The Previous Change (order 10) and Next Change (order 11) menu items registered in src/vs/workbench/browser/parts/editor/editor.contribution.ts are two ordinary, independent actions in the same 'navigation' group, so nothing currently marks them as a unit; that's the entire root cause. Where uncertainty starts: whether 'grouping' should be a new first-class WorkbenchToolBar/responsiveBehavior option (reusable by any menu) or a narrower, diff-editor-only workaround, and how the overflow menu should render a hidden pair (as two entries or one combined entry).
- **Open decisions:**
  - Should 'keep these actions together in overflow' be a new generic, reusable option on WorkbenchToolBar/responsiveBehavior, or a one-off special case just for the diff editor's Previous/Next Change actions?
  - When a paired group is hidden, should the overflow menu show the two actions as separate entries (as today) or as one combined entry?
