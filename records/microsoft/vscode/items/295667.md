# Issue #295667 — Network disruptions cause subagents to hang forever

[https://github.com/microsoft/vscode/issues/295667](https://github.com/microsoft/vscode/issues/295667)

## Summary

A real resilience gap: the networking layer retries on certain network errors (ECONNRESET, ETIMEDOUT, ERR_NETWORK_CHANGED, etc.) but only once, and the subagent tool calling loop has no independent network-health timeout — so a mid-flight network disruption that doesn't surface one of the recognized error codes can leave the subagent's fetch promise hanging indefinitely. The reporter's workaround (sending a new prompt) confirms recovery is possible, suggesting the agent state itself isn't corrupted, just stuck on an unresolved network promise.

## Change summary

When the network connection is disrupted mid-request during a subagent's tool calling loop, the subagent hangs indefinitely instead of timing out and retrying or surfacing an error.

## Best solution

Add a network-level or loop-level timeout to subagent fetch requests so that a stalled connection is detected and either retried or surfaced as an error. The relevant code paths are in `extensions/copilot/src/platform/networking/common/networking.ts` (the `networkRequest` function and `canRetryOnceNetworkError`), `extensions/copilot/src/extension/intents/node/toolCallingLoop.ts` (the `shouldAutoRetry` retry logic), and `extensions/copilot/src/extension/prompt/node/executionSubagentToolCallingLoop.ts`. A request-level AbortController timeout or a keepalive/idle timeout on the fetch would address the hang without architectural changes.

## Evidence

- **networking retry layer:** `canRetryOnceNetworkError` in `extensions/copilot/src/platform/networking/common/networking.ts` retries on ECONNRESET/ETIMEDOUT/ERR_NETWORK_CHANGED etc., but only once and only when the error code is recognized — a full connection drop mid-stream may not raise one of these.
- **no cancellation in subagent loop:** grep for cancel/abort/token in `extensions/copilot/src/extension/prompt/node/executionSubagentToolCallingLoop.ts` returns zero matches — the subagent loop does not independently watch for network health or enforce a per-request timeout.
- **tool calling loop auto-retry:** `shouldAutoRetry` in `extensions/copilot/src/extension/intents/node/toolCallingLoop.ts` (line ~684) retries failed fetches in autopilot mode, but only if the fetch actually completes with a non-success `ChatFetchResponseType` — a hanging promise never triggers this path.
- **reporter workaround:** Sending 'Continue' unblocks the agent, confirming the agent state isn't corrupted — only the in-flight fetch is stuck.
