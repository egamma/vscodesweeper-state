# Issue #20530 — Search: target particular set of files

[https://github.com/microsoft/vscode/issues/20530](https://github.com/microsoft/vscode/issues/20530)

## Summary

Keep open for the remaining file-set search capabilities. Current main supports open-editor and source-control-changed-file scopes, but those do not cover staged-only, recently modified, or custom file sets; this issue remains the established consolidation point.

## Change summary

Provide convenient search scopes for particular file sets without requiring users to manually enumerate paths.

## Best solution

Retain the existing open-editor and changed-file scopes, and define the remaining supported file sets and their interaction with include/exclude filters. Resolve the broader request through an agreed scope-selection contract rather than treating the implemented subsets as full completion.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/search/browser/patternInputWidget.ts`, `src/vs/workbench/contrib/search/browser/searchView.ts`, `src/vs/workbench/contrib/search/browser/searchActionsFind.ts`, `src/vs/workbench/contrib/search/browser/searchActionsBase.ts`, `src/vs/workbench/services/search/common/queryBuilder.ts`
- **Validation:** For each approved scope, search a fixture workspace containing staged-only, unstaged-only, unchanged, and recently committed files; verify that results and replacements affect exactly the selected file set. Repeat with include/exclude filters, multiple repositories, and no matching files, while preserving existing open-editor and changed-file behavior.
- **Behavior:**

  > Users should be able to target an agreed set of files without manually entering every path or opening every file. Open-editor and source-control-changed-file search already exist, so acceptance must distinguish the remaining capabilities from those delivered subsets. The selected scope must constrain both search results and replacements, and its interaction with include/exclude filters must be explicit. Preserve current-file find and the existing search scopes.
- **Trace:**

  > PatternInputWidget in src/vs/workbench/contrib/search/browser/patternInputWidget.ts exposes open-editor and changed-file toggles. SearchView in src/vs/workbench/contrib/search/browser/searchView.ts gathers every SCM resource group into changedFileUris, and QueryBuilder in src/vs/workbench/services/search/common/queryBuilder.ts filters those resources through the query before constructing a file-list search. FindInFilesAction and findInFilesCommand support configured path arguments and variable resolution, but not a general selectable scope contract. https://github.com/microsoft/vscode/issues/227363#issuecomment-2327038086 identifies this issue as the home for additional file-set infrastructure and possible API support. The uncertainty is which remaining sets should be first-class and whether extensions can supply them; do not turn this into a redesign of single-file find or unrelated whitespace matching.
- **Open decisions:**
  - Which remaining scopes should be first-class: staged-only files, SCM-selected files, recently modified files, reusable custom sets, or some subset?
  - Should a selected file set be an exclusive search universe narrowed by include/exclude filters, or should users be able to combine multiple sets?
  - Should extensions be able to contribute named file sets, and if so, what public selection and refresh behavior should that contract expose?
