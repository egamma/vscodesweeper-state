# Issue #110067 — Implement Debugger Modules View

[https://github.com/microsoft/vscode/issues/110067](https://github.com/microsoft/vscode/issues/110067)

## Summary

Keep open: current source still lacks a built-in debugger Modules view, and Loaded Scripts does not cover module metadata. The related reports point back here rather than providing an older canonical or a landed implementation.

## Change summary

Expose modules reported by debug adapters in a built-in debugger view, including their associated metadata.

## Best solution

Provide a capability-gated Modules view backed by DAP modules requests and module lifecycle events. Settle the tabular presentation and supported metadata before implementation, preserving Loaded Scripts as a separate source-file browsing feature.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`, `src/vs/workbench/contrib/debug/browser/rawDebugSession.ts`, `src/vs/workbench/contrib/debug/browser/debugSession.ts`, `src/vs/workbench/contrib/debug/common/debug.ts`, `src/vs/workbench/contrib/debug/common/debugProtocol.d.ts`
- **Validation:** Use a test debug adapter advertising supportsModulesRequest and returning two modules with distinct metadata. Verify that opening the agreed Modules surface displays them, module new/changed/removed events update the correct rows, switching sessions shows the correct modules, and adapters without the capability retain existing behavior. Cover the agreed lifecycle with targeted debug tests and verify keyboard and screen-reader access manually.
- **Behavior:**

  > Users debugging through an adapter that supports DAP modules can inspect loaded modules and their metadata in a built-in VS Code surface. The displayed collection remains accurate as modules are added, changed or removed and when the user switches debug sessions. Existing Loaded Scripts behavior remains unchanged, and adapters without modules support are unaffected. Acceptance includes accurate module identity and updates, the agreed metadata presentation, and accessible keyboard navigation.
- **Trace:**

  > The debug view registrations in src/vs/workbench/contrib/debug/browser/debug.contribution.ts contain no Modules view. DebugSession.getLoadedSources() in src/vs/workbench/contrib/debug/browser/debugSession.ts uses loadedSources and returns Source objects, so Loaded Scripts is not an existing implementation of this request. RawDebugSession in src/vs/workbench/contrib/debug/browser/rawDebugSession.ts has an empty dedicated module-event case; the protocol declarations in src/vs/workbench/contrib/debug/common/debugProtocol.d.ts already describe modules requests, module attributes and column descriptors. The remaining uncertainty is the product presentation and initial metadata scope, particularly the thread's tree-versus-table concern. Preserve source browsing and unrelated debugger behavior; adapter-specific symbol-loading commands are not established requirements. Additional demand was directed here in https://github.com/microsoft/vscode/issues/200842#issuecomment-1856371010.
- **Open decisions:**
  - Should the initial Modules surface be a debugger sidebar table or a dedicated editor-style table for inspecting module metadata?
  - Should the initial view expose a fixed set of standard DAP Module fields, or also honor adapter-provided additionalModuleColumns?

## Evidence

- **Existing-capability check:** src/vs/workbench/contrib/debug/browser/debug.contribution.ts:470-475 registers Variables, Watch, Call Stack, Breakpoints, Welcome and Loaded Scripts views, but no Modules view. Debug-area searches found modules request support only in protocol declarations, not an implemented view or request wrapper.
- **Loaded Scripts is not equivalent:** src/vs/workbench/contrib/debug/browser/debugSession.ts:860-871 implements getLoadedSources() through raw.loadedSources({}) and returns Source objects. src/vs/workbench/contrib/debug/browser/loadedScriptsView.ts:414-490 renders a source tree; it does not expose loaded binary/module metadata.
- **Missing module integration:** src/vs/workbench/contrib/debug/browser/rawDebugSession.ts:165-166 explicitly leaves the module event without dedicated handling. src/vs/workbench/contrib/debug/common/debugProtocol.d.ts:1890-1940 defines Module fields such as version, symbolStatus and addressRange, and ColumnDescriptor for tabular metadata; protocol declarations alone do not deliver the requested UI.

The discussion leaves the presentation contract unsettled, not the existence of the requested capability.

It is a closed clarification issue, not an upstream defect or implementation.
