# Issue #20652 — [themes] different themes for different filetypes

[https://github.com/microsoft/vscode/issues/20652](https://github.com/microsoft/vscode/issues/20652)

## Summary

This remains a well-supported feature request with 302 community upvotes and an assigned Backlog milestone. The documented workarounds do not satisfy the central requirement of displaying simultaneous editors with independent file- or language-specific syntax themes.

## Change summary

Allow editor color themes or syntax-color schemes to vary by file type or language without changing the entire workbench or other open editors.

## Best solution

Decouple editor syntax theming from the global workbench theme, then support language- or resource-specific editor theme selection with a global theme fallback. The design must define behavior for embedded languages, notebooks, previews, and multiple differently themed editors shown simultaneously.

## Plan brief

- **Likely files:** `src/vs/workbench/services/themes/common/workbenchThemeService.ts`, `src/vs/workbench/services/themes/browser/workbenchThemeService.ts`, `src/vs/editor/common/services/themeService.ts`
- **Validation:** Add theme-service and editor tests covering two simultaneous editors with different language/resource mappings, fallback to the global theme, and deterministic handling of embedded-language tokens; manually verify split editors, notebooks, and Markdown preview.
- **Behavior:**

  > Users can associate an editor syntax/color theme with a language or file pattern while retaining a separate global workbench theme. Two editors displayed side by side can use different configured editor themes without either changing the workbench or the other editor. Files without a mapping use the global theme, and switching focus must not repaint unrelated editors. Acceptance must cover ordinary text editors, an agreed notebook/preview behavior, and the agreed treatment of embedded languages.
- **Trace:**

  > The issue's central gap is editor-local theme selection rather than the existing global theme switch. The Theme by Language extension cited in the thread changes the entire application theme, and language-specific editor configuration only addresses settings such as font family and size; neither supports simultaneous independently themed editors. Theme ownership likely crosses src/vs/workbench/services/themes/common/workbenchThemeService.ts, src/vs/workbench/services/themes/browser/workbenchThemeService.ts, and editor theme consumption under src/vs/editor/common/services/themeService.ts. https://github.com/microsoft/vscode/issues/25986 is related because separating workbench and syntax themes may provide the necessary boundary, but it is newer and broader rather than a valid duplicate canonical for this re-reviewed item. Preserve the existing single global theme behavior as the fallback and avoid changing unrelated workbench theming.
- **Open decisions:**
  - Should mappings select a full editor theme, syntax token colors only, or token colors plus editor background and foreground?
  - Should selection keys be language identifiers, file glob patterns, or both, and which takes precedence when both match?
  - For embedded languages, should the containing editor use one mapped theme or should each embedded token region use its language's mapped theme?
  - Should notebook cells and preview editors inherit the resource mapping, use mappings by cell language, or remain on the global theme?
