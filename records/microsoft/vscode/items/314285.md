# Issue #314285 — FindFIles2 can stall forever with virtual file system with no search provider

[https://github.com/microsoft/vscode/issues/314285](https://github.com/microsoft/vscode/issues/314285)

## Summary

The indefinite wait remains in current main: searching a virtual-only workspace without a search provider awaits a promise that only provider registration can resolve. Both linked fix attempts closed without merging, so this issue still tracks necessary work.

## Change summary

Prevent workspace.findFiles2 from waiting indefinitely when a virtual workspace has no file-search provider.

## Best solution

Make provider absence terminate promptly without losing results from providers still registering through a remote extension host. Resolve the activation/registration lifecycle boundary in the shared search service rather than substituting a long timeout.

## Plan brief

- **Likely files:** `src/vs/workbench/services/search/common/searchService.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/api/browser/mainThreadWorkspace.ts`, `src/vs/workbench/api/common/extHostWorkspace.ts`
- **Validation:** Add focused SearchService tests showing that a virtual-only file search with no provider settles promptly after activation completes, an asynchronously registering remote provider still supplies results, and cancellation remains effective. Manually repeat the issue's Memfs setup/create-files steps and call workspace.findFiles2 with a matching non-empty glob and no cancellation token.
- **Behavior:**

  > In a workspace containing only a virtual filesystem without a search provider, workspace.findFiles2 must settle instead of waiting forever. The caller must not have to supply cancellation to escape the wait, and a 30-second stall is not acceptable. Searches begun while a remote extension host is connecting must still return results when its provider becomes available. Existing searches with registered providers and explicit cancellation must retain their behavior.
- **Trace:**

  > ExtHostWorkspace.findFiles2 delegates through _findFilesImpl and _findFilesBase to MainThreadWorkspace.$startFileSearch, which calls SearchService.fileSearch. SearchService.doSearch awaits search activation and installed-extension registration, but searchWithProviders subsequently calls waitForProvider when none of the queried schemes has a provider. That DeferredPromise is completed only by registerSearchResultProvider, so a virtual scheme that never supplies a provider leaves the operation pending. The provider-wait machinery is shared by file, text, and AI-text searches; avoid changing their existing semantics incidentally. The unresolved technical boundary is distinguishing permanent provider absence from legitimate delayed registration during remote extension-host startup. Both https://github.com/microsoft/vscode/pull/314288 and https://github.com/microsoft/vscode/pull/314329 closed unmerged; their discussion establishes the remote-result compatibility requirement and rejects a long timeout. No existing shared SearchService orchestration test suite was found in the inspected search tests, so the plan should establish focused coverage of that lifecycle.
