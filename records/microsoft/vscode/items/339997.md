# Issue #339997 — Remote agent host: large chat history exceeds tunnel gateway frame limit and causes terminal timeout

[https://github.com/microsoft/vscode/issues/339997](https://github.com/microsoft/vscode/issues/339997)

## Summary

Keep open: the gateway still uses default WebSocket limits while the client accepts 100 MiB, matching the independently confirmed large-history rejection and terminal timeout. The discussion also establishes that turn pagination alone cannot address oversized individual turns or shared-connection blocking.

## Change summary

Large agent-host chat snapshots exceed the tunnel gateway's frame limit, disconnecting the shared transport and surfacing misleading terminal timeouts.

## Best solution

Make large-history delivery reliable across the CLI gateway and AHP transport, with consistent bounded limits and actionable failure reporting. Address payload growth within individual turns as well as across turns, without breaking other clients or blocking unrelated session traffic.

## Plan brief

- **Likely files:** `cli/src/tunnels/agent_host.rs`, `src/vs/platform/agentHost/common/webSocketOverDuplex.ts`, `src/vs/platform/agentHost/node/protocolServerHandler.ts`
- **Validation:** Extend the Rust gateway tests alongside gateway_session_selects_existing_endpoint_and_proxies_frames and run cargo test --manifest-path cli/Cargo.toml gateway_. Cover target-to-client snapshots above 16 MiB over TCP and socket targets, both message directions, explicit rejection beyond the chosen bound, and connection-close diagnostics. End-to-end acceptance should open a large multi-turn history and a single oversized turn through a tunnel while checking that unrelated session actions and terminal requests remain responsive.
- **Behavior:**

  > Opening a long-running chat through a remote tunnel must not repeatedly disconnect the shared connection merely because its snapshot exceeds the gateway's current 16 MiB frame default. Supported large histories must remain readable, including histories dominated by a single turn; transport rejections must identify the actual failure rather than appearing only as terminal launch timeouts. Acceptance must cover both TCP and socket-backed agent hosts and unrelated session traffic on the same connection. Third-party AHP clients must retain interoperable access.
- **Trace:**

  > In cli/src/tunnels/agent_host.rs, handle_gateway_select_request creates an unconfigured client-facing WebSocket, and dial_gateway_target uses unconfigured TCP and socket handshake helpers. proxy_gateway_frames logs a target read failure and returns without explicitly forwarding the cause; the supplied gateway logs and direct-WebSocket comparison independently isolate this path. The client in src/vs/platform/agentHost/common/webSocketOverDuplex.ts already accepts payloads up to 100 MiB by default. protocolServerHandler.ts ignores subscription views and fetchTurns emits an empty page, so existing pagination fields do not currently bound the initial snapshot. The latest maintainer evidence in https://github.com/microsoft/vscode/issues/339997 establishes that a single turn can dominate the payload and delay unrelated traffic. The uncertainty is the user-visible delivery and failure contract beyond correcting the immediate mismatch; preserve finite resource bounds, existing session identities, and interoperability rather than assuming only VS Code clients.
- **Open decisions:**
  - Should the initial resolution support whole snapshots up to the client's existing 100 MiB bound, or must bounded history/content delivery be part of the same acceptance scope?
  - For histories dominated by one turn, what content is initially visible and what is loaded on demand, while preserving access to complete tool inputs, outputs, and response parts?
