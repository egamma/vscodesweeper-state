# Issue #339997 — Remote agent host: large chat history exceeds tunnel gateway frame limit and causes terminal timeout

[https://github.com/microsoft/vscode/issues/339997](https://github.com/microsoft/vscode/issues/339997)

## Summary

Well-diagnosed, reproducible bug confirmed against current main: the CLI gateway's target connections use tungstenite's default 16 MiB frame limit while the client tunnel allows 100 MiB, so a large Agent Host chat snapshot gets rejected and the failure surfaces as a generic terminal timeout instead of a clear error. Keeping open; the fix involves a design choice (raise/align limits vs. propagate the real error vs. chunk large payloads) best left to a maintainer.

## Change summary

Opening a remote Agent Host session whose default chat history exceeds 16 MiB fails because the CLI gateway's WebSocket target connections use tungstenite's default frame-size limit, well below the client's 100 MiB limit, and the resulting connection drop is reported as an opaque terminal timeout.

## Best solution

Set an explicit WebSocketConfig (max_frame_size/max_message_size) on the gateway's target-dial calls in cli/src/tunnels/agent_host.rs to match the client's 100 MiB limit, and propagate the real frame-size-rejection reason to the client instead of letting it surface as a generic terminal connection timeout.

## Plan brief

- **Likely files:** `cli/src/tunnels/agent_host.rs`, `src/vs/platform/agentHost/common/webSocketOverDuplex.ts`
- **Validation:** A CLI integration test that proxies a >16 MiB single-frame payload through the gateway target connection and asserts it is forwarded (or, if chunking is chosen, reassembled) without a Capacity(MessageTooLong) rejection.
- **Behavior:**

  > Opening a remote Agent Host session whose default chat snapshot exceeds 16 MiB must not silently kill the tunnel connection or report a generic 25-second terminal timeout. Either the full snapshot should be delivered successfully, or, if it is rejected, the client should surface a specific, actionable error about the session/history size rather than a terminal launch failure.
- **Trace:**

  > The gateway's target WebSocket connections (`dial_gateway_target` in cli/src/tunnels/agent_host.rs, used by `proxy_gateway_frames`) are opened via `tokio_tungstenite::connect_async`/`client_async` with no `WebSocketConfig`, so they inherit tungstenite's default 16 MiB max frame size. The client's tunnel socket (src/vs/platform/agentHost/common/webSocketOverDuplex.ts) advertises a 100 MiB `defaultMaxPayloadLength`. When the AHP chat-subscription response for a large session (observed: 18,774,427 bytes / 52 turns) is sent as one frame, the gateway rejects it with `Capacity(MessageTooLong)`, logs it, and closes the target connection; the client only observes silence on an unrelated in-flight terminal request and reports a 25s connection-timeout instead of the real cause. Do not change the legacy per-request proxy path or the client's existing 100 MiB limit; the fix is scoped to the gateway's target dial path and/or how its error is surfaced. Related, unverified: https://github.com/microsoft/vscode/issues/335232.
- **Open decisions:**
  - Should the gateway's target connection limit be raised to match the client's 100 MiB (simple, but just raises the ceiling), or should very large chat snapshots instead be chunked/streamed so there's no practical frame-size ceiling at all?
  - When a frame-size rejection does occur, should it surface as a dedicated Agent Host/session error in the UI, or is it acceptable for it to still interact with the terminal's connection-health reporting?
