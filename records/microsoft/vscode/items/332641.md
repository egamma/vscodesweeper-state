# Issue #332641 — Delete permanently doesn't ask for confirmation, but also doesn't delete permanently

[https://github.com/microsoft/vscode/issues/332641](https://github.com/microsoft/vscode/issues/332641)

## Summary

Team-authored report; I traced the mechanism in bulkFileEdits.ts and it looks like as-designed undo behavior rather than a real 'permanent delete failed' defect, but the hard keep-open rule protects team-authored (MEMBER) issues from judgment closes like *as-designed, so this stays open for a maintainer to confirm and decide.

## Change summary

Reporter says 'Delete Permanently' on a remote/Docker workspace didn't show a confirmation and the file wasn't actually permanently deleted, since Ctrl+Z restored it.

## Best solution

A maintainer (roblourens is already engaged) should confirm this is as-designed: src/vs/workbench/contrib/bulkEdit/browser/bulkFileEdits.ts `DeleteOperation.perform()` reads the file's content before deletion and always pushes a `CreateEdit` for undo (independent of `useTrash`/`skipTrashBin`), so Ctrl+Z recreating the file after a 'permanent' delete is VS Code's own undo history, not a failure to actually delete from disk/trash. If confirmed, this can be closed as *as-designed by a human — I can't propose that close myself since the reporter is a team member.

## Evidence

- **undo always captures content:** src/vs/workbench/contrib/bulkEdit/browser/bulkFileEdits.ts, DeleteOperation.perform(): reads `fileContent = await this._fileService.readFile(edit.oldUri)` and pushes `new CreateEdit(...)` for undo whenever the file isn't too large, regardless of whether useTrash/skipTrashBin was set.
- **useTrash only affects disk deletion, not undo:** The `useTrash` flag (line ~252 of the same file) only controls whether IFileService.del() moves to OS trash vs. permanently deletes; it does not gate whether an undo CreateEdit is recorded.
