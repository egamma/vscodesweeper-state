# Issue #175652 — Provide option to disable drag and drop in Editor

[https://github.com/microsoft/vscode/issues/175652](https://github.com/microsoft/vscode/issues/175652)

## Summary

Keep this accepted, community-supported request open: existing settings do not disable opening files dropped onto the editor. The Codespaces teaching scenario establishes a concrete remaining need, and no verified canonical issue owns this opt-out.

## Change summary

Provide an option to prevent files from being opened by dragging and dropping them onto the editor.

## Best solution

Provide a supported editor drop opt-out that prevents accidental file opening while retaining today's behavior by default. Settle whether it also disables internal editor rearrangement and Shift-drop content insertion before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/workbench.contribution.ts`, `src/vs/workbench/browser/parts/editor/editor.ts`, `src/vs/workbench/browser/parts/editor/editorDropTarget.ts`, `src/vs/workbench/browser/parts/editor/editorTabsControl.ts`, `src/vs/workbench/test/browser/parts/editor/editor.test.ts`
- **Validation:** In browser-hosted VS Code or Codespaces, disable the agreed option and drag a local text file onto both an occupied editor and an empty editor group: neither should open the file. Re-enable it and verify existing opening and local-save behavior. Check internal tab/group movement and Shift-drop insertion against the agreed scope, and add browser tests for the resulting drop-acceptance contract.
- **Behavior:**

  > Users can prevent accidental opening of files dropped onto the editor, including local Downloads files dropped into browser-hosted Codespaces. With the opt-out active, the drop must not create an editor for the file; with the default behavior retained, file opening and local-file save semantics remain unchanged. Acceptance must cover occupied and empty editor groups. Whether internal editor movement and Shift-drop insertion are disabled by the same option requires an explicit scope decision.
- **Trace:**

  > EditorDropTarget.onDragEnter in src/vs/workbench/browser/parts/editor/editorDropTarget.ts accepts resource transfers, checks the internal allowDropIntoGroup option, and creates a DropOverlay. DropOverlay.handleDrop delegates external resources to ResourcesDropHandler.handleDrop in src/vs/workbench/browser/dnd.ts, which calls IEditorService.openEditors; browser file transfers are extracted in src/vs/platform/dnd/browser/dnd.ts. The existing editor.dragAndDrop and editor.dropIntoEditor.enabled settings govern different interactions, while workbench.editor.splitOnDragAndDrop changes splitting rather than acceptance. The internal allowDropIntoGroup capability is present, but no registered user setting exposes the requested opt-out. Preserve the local-file editing contract explained at https://github.com/microsoft/vscode/issues/175267#issuecomment-1442854532; this request is not an upload feature or a change to save destinations. Uncertainty starts at the opt-out's scope across external file drops, internal tab/group transfers, and Shift-drop insertion.
- **Open decisions:**
  - Should the opt-out reject all file/resource drops onto editors, or only external local-file drops while preserving internal editor and group rearrangement?
  - Should Shift-drop content insertion remain available when ordinary file-opening drops are disabled?
