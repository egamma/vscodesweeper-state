# Issue #137938 — [html] "Auto Closing Tags" adds unnecessary tags in some cases with prettier-vscode 

[https://github.com/microsoft/vscode/issues/137938](https://github.com/microsoft/vscode/issues/137938)

## Summary

The defect remains source-reproducible on current main: formatting edits can insert a single-line change ending in `>`, and HTML auto-insertion treats that programmatic edit like typing and adds an unwanted closing tag.

## Change summary

Prevent HTML auto-closing tags from reacting to formatter-generated document changes.

## Best solution

Formatter-originated edits should bypass HTML auto-insertion while ordinary typed `>` and `/` characters continue to request closing tags. The implementation should use a supported edit-origin signal rather than formatter-specific content heuristics.

## Plan brief

- **Likely files:** `extensions/html-language-features/client/src/autoInsertion.ts`, `extensions/html-language-features/package.json`, `src/vscode-dts/vscode.proposed.textDocumentChangeReason.d.ts`, `src/vs/workbench/api/common/extHostDocuments.ts`
- **Validation:** Using the issue's HTML fixture with html.autoClosingTags enabled, run Format Document with Prettier and verify no extra closing tag is inserted; then type an opening HTML tag ending in `>` and verify normal auto-closing still occurs.
- **Behavior:**

  > Formatting an HTML document must not trigger HTML auto-closing or add tags beyond the formatter's returned edits. The behavior must hold with html.autoClosingTags enabled and with formatters such as Prettier that rewrite a wrapped opening tag into a line ending in `>`. Directly typing an opening tag must continue to insert its closing tag. Undo and redo behavior must remain unchanged.
- **Trace:**

  > HTML auto-insertion is activated by activateAutoInsertion in extensions/html-language-features/client/src/autoInsertion.ts. Its document-change listener cannot distinguish typing from formatting through the stable TextDocumentChangeEvent.reason, so a formatter insertion ending in `>` reaches doAutoInsert. FormattingEdit.execute in src/vs/editor/contrib/format/browser/formattingEdit.ts labels edits with `formatEditsCommand`; current main transports detailed edit metadata through ExtHostDocuments only for extensions using the proposed textDocumentChangeReason API. The HTML extension has not enabled that proposal, and there is no client-side autoInsertion test suite. Keep the boundary to suppressing non-user formatter changes; do not alter HTML completion results, formatter output, or typed-tag auto-closing.
- **Open decisions:**
  - Should formatter-originated changes become identifiable through a stable TextDocumentChangeEvent contract, or should the built-in HTML extension consume the proposed detailedReason metadata for this behavior?

## Evidence

- **current source path:** extensions/html-language-features/client/src/autoInsertion.ts listens to workspace.onDidChangeTextDocument and invokes autoClose whenever the last change is a single-line insertion ending in `>` or `/`; it excludes only undo and redo and does not distinguish formatter edits.
- **formatter edit source:** src/vs/editor/contrib/format/browser/formattingEdit.ts applies formatting through editor.executeEdits('formatEditsCommand', ...), producing the same document-change notification consumed by HTML auto-insertion.
- **event metadata boundary:** src/vs/workbench/api/common/extHostDocuments.ts exposes only Undo/Redo through the stable TextDocumentChangeEvent.reason. Current main has a proposed detailedReason path in src/vscode-dts/vscode.proposed.textDocumentChangeReason.d.ts, but extensions/html-language-features/package.json does not enable that proposal.
- **confirmed reproduction:** A VS Code maintainer confirmed the supplied Prettier formatting example still reproduced in https://github.com/microsoft/vscode/issues/137938#issuecomment-1352012448.
- **cross-extension confirmation:** https://github.com/sveltejs/language-tools/issues/2167#issuecomment-1733309365 independently traces the same observable symptom to formatting edits triggering html.autoClosingTags; disabling that setting prevents it.
