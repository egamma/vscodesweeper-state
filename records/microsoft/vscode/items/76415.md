# Issue #76415 — Allow for configuration files in .devcontainer

[https://github.com/microsoft/vscode/issues/76415](https://github.com/microsoft/vscode/issues/76415)

## Summary

Inline container settings already support launch and task definitions, but do not fully cover separate configuration files or container-specific overrides of workspace settings. Keep this accepted Backlog request open for a configuration-design decision; no verified canonical owns its full scope.

## Change summary

Support container-specific settings, tasks, and launch configurations without applying them when the same project is opened locally.

## Best solution

Provide a supported container-only configuration surface, with explicit precedence relative to shared workspace configuration. Coordinate core configuration, debug, and tasks behavior with Dev Containers rather than treating inline remote-user settings as equivalent to container workspace overrides.

## Plan brief

- **Likely files:** `src/vs/workbench/services/configuration/common/configuration.ts`, `src/vs/workbench/services/configuration/browser/configuration.ts`, `src/vs/workbench/services/configuration/browser/configurationService.ts`, `src/vs/platform/configuration/common/configurationModels.ts`, `src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts`, `src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts`
- **Validation:** In a fixture project with conflicting local and container settings plus distinct tasks and launch configurations, compare opening locally versus reopening in a Dev Container. Verify container configuration is inactive locally, active remotely, follows the agreed precedence, and updates according to the agreed reload lifecycle; exercise a container launch configuration referencing a container task.
- **Behavior:**

  > The same project should support distinct local and container settings, tasks, and launch configurations without editing shared configuration whenever the environment changes. The thread also requests container-specific values that can override local workspace toolchain paths. Acceptance must cover local/container isolation, the agreed precedence, task-to-launch references, and the lifecycle for changes to container configuration. Existing inline devcontainer settings provide partial coverage but do not settle these requirements.
- **Trace:**

  > UserLaunch.getConfig() in src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts reads launch from userValue, and AbstractTaskService._computeUserTasks() plus _getConfiguration() in src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts consume userValue for tasks. Configuration.getWorkspaceConsolidatedConfiguration() and getFolderConsolidatedConfiguration() in src/vs/platform/configuration/common/configurationModels.ts place workspace/folder settings above user settings. Workspace configuration paths in src/vs/workbench/services/configuration/common/configuration.ts remain under .vscode. The complete discussion at https://github.com/microsoft/vscode/issues/76415 supplies both the inline workaround and a concrete precedence gap; https://github.com/microsoft/vscode/issues/169375#issuecomment-1355556844 explains its build-time copying lifecycle. Dev Containers integration is outside this checkout, so planning must establish the ownership boundary with microsoft/vscode-remote-release. Preserve existing local configuration behavior and ordinary remote-user settings semantics unless the maintainer explicitly chooses otherwise.
- **Open decisions:**
  - Should container configuration remain remote-user defaults, or introduce a container-specific workspace layer that overrides shared .vscode settings?
  - Should the supported surface include separate settings.json, tasks.json, and launch.json files under .devcontainer, or remain inline in devcontainer.json?
  - Should edits to container configuration take effect while the container is running, after a window reload, or only after rebuilding the container?

## Evidence

- **Existing capability:** https://github.com/microsoft/vscode/issues/76415#issuecomment-1232813388 provides a complete working example using settings.launch and settings.tasks in devcontainer.json. Current src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts:764-792 reads launch through UserLaunch.getConfig() from inspect('launch').userValue; src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts:2714-2731 and 2823-2847 parse tasks from inspect('tasks').userValue.
- **Remaining precedence requirement:** https://github.com/microsoft/vscode/issues/76415#issuecomment-583023473 describes local Go toolchain paths in .vscode/settings.json overriding container defaults, and a bind-mount workaround. In src/vs/platform/configuration/common/configurationModels.ts:1065-1083, workspace configuration is merged after user configuration and folder configuration is merged afterward; inline remote-user settings therefore do not provide the requested higher-precedence container workspace layer.
- **Separate files remain distinct:** src/vs/workbench/services/configuration/common/configuration.ts:14-16 and 41-42 identify .vscode/settings.json, .vscode/tasks.json, and .vscode/launch.json as the workspace configuration paths. The inspected core configuration surface does not establish equivalent automatic discovery under .devcontainer.
- **Workaround lifecycle:** https://github.com/microsoft/vscode/issues/169375#issuecomment-1355556844 explains that devcontainer.json launch settings are copied into Remote settings when the container is built, rather than reread as workspace configuration files. Its closed serverReadyAction report and https://github.com/microsoft/vscode/issues/166569 concern a narrower debugging symptom, not completion of this request.
- **Canonical search:** Open-issue searches for container tasks/settings, container configuration overrides, and devcontainer launch.json found no verified full-scope canonical. https://github.com/microsoft/vscode/issues/15909 concerns configuration inheritance, https://github.com/microsoft/vscode/issues/40233 concerns private user-specific workspace settings, and https://github.com/microsoft/vscode/issues/5595 concerns platform-specific settings; their verified bodies do not own container-specific settings, tasks, and launch configuration together.
- **Accepted work and maintainer interest:** The issue is assigned to Backlog and already labeled feature-request, debug, and tasks. https://github.com/microsoft/vscode/issues/76415#issuecomment-508704584 raises the design fit, while https://github.com/microsoft/vscode/issues/76415#issuecomment-508800378 identifies machine-level launch/task support. Existing partial support is not grounds for declining the remaining accepted work.
