# Issue #315842 — Testing: Open VS Code window + keybinding "broken" when multiple instances are open

[https://github.com/microsoft/vscode/issues/315842](https://github.com/microsoft/vscode/issues/315842)

## Summary

The gap remains on current main: Open VS Code Window selects the first non-Agents window in creation order rather than the most recently focused editor window. This team-authored Backlog request has explicit maintainer support for recency-based selection and should remain open.

## Change summary

Make the Agents window command and keybinding focus the most recently used VS Code editor window when several are open.

## Best solution

The command should consistently return to the most recently focused regular VS Code window, while preserving the existing behavior of opening a new editor window when none exists.

## Plan brief

- **Likely files:** `src/vs/sessions/electron-browser/actions/vscodeActions.ts`, `src/vs/sessions/test/electron-browser/vscodeActions.test.ts`, `src/vs/platform/native/common/native.ts`, `src/vs/platform/native/electron-main/nativeHostMainService.ts`
- **Validation:** Add and run the VS Code Actions unit tests with multiple editor windows, asserting that the most recently focused non-Agents window is selected and that an editor window is opened when no eligible window exists.
- **Behavior:**

  > From the Agents window, Open VS Code Window and Cmd/Ctrl+Shift+A should focus the most recently focused regular VS Code window when multiple editor windows exist. Repeated invocation must follow changes in editor-window focus rather than always selecting the same instance. When no regular editor window exists, the command must continue opening one.
- **Trace:**

  > OpenVSCodeWindowAction in src/vs/sessions/electron-browser/actions/vscodeActions.ts obtains `IOpenedMainWindow[]` and chooses the first entry whose ID differs from the Agents window. NativeHostMainService constructs that array from WindowsMainService's insertion-ordered window Map, so the selected editor does not change with focus. The main process already records `lastFocusTime` and uses `getLastFocused` for `getLastActiveWindow`, but the current native-host contract cannot request the most recent window while excluding the focused Agents window. Preserve auxiliary-window exclusion, the no-editor fallback, and unrelated callers of `getWindows()` and `getActiveWindowId()`.

## Evidence

- **current source:** src/vs/sessions/electron-browser/actions/vscodeActions.ts:112-117 calls `getWindows()` and focuses `windows.find(w => w.id !== currentWindowId)`, so it does not consider focus recency.
- **window ordering:** src/vs/platform/native/electron-main/nativeHostMainService.ts:226-246 preserves `windowsMainService.getWindows()` order, while src/vs/platform/windows/electron-main/windowsMainService.ts:1819-1821 returns the window Map's insertion order. This explains why the same window is repeatedly selected.
- **available main-process state:** src/vs/platform/windows/electron-main/windows.ts:272-285 already selects windows by `lastFocusTime`, but that recency is not included in `IOpenedMainWindow` or otherwise exposed to the Sessions action.
- **maintainer direction:** A maintainer explicitly preferred focusing the most recently focused instance: https://github.com/microsoft/vscode/issues/315842#issuecomment-4429402617
- **canonical search:** Searches for Open VS Code Window, Agents window multi-instance focus, and most-recently-focused behavior found no older open issue with the same observable symptom.
