# Issue #266397 — Support tool calling responses for @github requests via platform agent in VSCode

[https://github.com/microsoft/vscode/issues/266397](https://github.com/microsoft/vscode/issues/266397)

## Summary

A real compatibility gap remains in the `@github` platform-agent path: current main parses modern tool-call responses generically but the participant handles only the deprecated function-call field. The Backlog request should remain open while maintainers define the migration contract.

## Change summary

Allow `@github` platform-agent requests to consume modern tool-call responses instead of depending on legacy function calling.

## Best solution

Make the `@github` response adapter recognize tool calls emitted by the existing endpoint parser and preserve the current progress and final-response experience across Sonnet and GPT-5-family models. Decide whether legacy function-call responses remain as a transition fallback, then cover both the selected contract and modern tool-call flow with focused tests.

- **Behavior:**

  > An `@github` request using a model that returns standard tool calls completes without relying on messages with the deprecated `function` role. Internal GitHub-agent tools remain server-executed, while VS Code presents their progress and final response consistently with the existing flow. Sonnet and GPT-5-family requests must not fail merely because legacy function calling is unsupported. The accepted legacy fallback behavior must be covered explicitly.
- **Trace:**

  > `RemoteAgentContribution.registerAgent` in `extensions/copilot/src/extension/conversation/vscode-node/remoteAgents.ts` creates a `RemoteAgentChatEndpoint` whose metadata already advertises the selected model's tool-call capability. `SSEProcessor` in `extensions/copilot/src/platform/networking/node/stream.ts` converts streamed `tool_calls` into `delta.copilotToolCalls`, while the remote-agent callback reacts only to `delta._deprecatedCopilotFunctionCalls`. The generic endpoint therefore already parses the modern wire shape; uncertainty begins at how the participant should expose or retain those calls. Keep tool execution inside the platform agent and avoid expanding this into client-side tool execution or unrelated chat-agent behavior. The referenced service issue is https://github.com/github/copilot-experiences/issues/7475.
- **Open decisions:**
  - Should modern platform-agent tool calls be used only to reproduce the existing search-progress UI, or must they also be retained in the conversation history passed back on subsequent `@github` turns?
  - Must VS Code continue accepting legacy `function_call` responses during a migration period, or may the platform-agent contract switch atomically to `tool_calls`?

## Evidence

- **modern parsing exists:** `extensions/copilot/src/platform/networking/node/stream.ts` parses streaming `tool_calls` and emits them as `IResponseDelta.copilotToolCalls`; `extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts` also normalizes non-streaming `tool_calls`.
- **platform-agent gap:** `extensions/copilot/src/extension/conversation/vscode-node/remoteAgents.ts` advertises `tool_calls: selectedEndpoint.supportsToolCalls`, but its response callback handles only `delta._deprecatedCopilotFunctionCalls` for `bing-search` and `codesearch` and does not consume `delta.copilotToolCalls`.
- **history boundary:** `prepareRemoteAgentHistory` in `extensions/copilot/src/extension/conversation/vscode-node/remoteAgents.ts` reconstructs only user text, assistant text, and references; it does not preserve tool-call messages, leaving the requested meaning of passing tool responses through unresolved.
