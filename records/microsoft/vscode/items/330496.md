# Issue #330496 — ChatApprovedAccountOrganizations causes toolset bootstrap deadlock

[https://github.com/microsoft/vscode/issues/330496](https://github.com/microsoft/vscode/issues/330496)

## Summary

Well-diagnosed bug: `getToolByName()` resolves via `getAllToolsIncludingDisabled()`, which — despite its name — still filters by `isPermitted()` (the enterprise-policy/agent-mode gate). Toolset membership for built-in sets like `read` is computed once via `getToolByName()` when the extension's `languageModelToolSets` contribution point runs, so tools that are transiently un-permitted during `ChatApprovedAccountOrganizations` policy verification never get added to the toolset, and the retry-on-`onDidChangeTools` path in `languageModelToolsContribution.ts` doesn't reliably backfill them in this window-reload scenario.

## Change summary

In a new window, while an enterprise `ChatApprovedAccountOrganizations` sign-in policy is still verifying, the 'read' toolset permanently ends up missing several core read tools (readFile, problems, viewImage, etc.) even after the policy resolves, until the Copilot extension is manually disabled/re-enabled.

## Best solution

Fix `getToolByName()` in src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts to look up tools directly in `_tools` (as the reporter's diff proposes), decoupling structural tool lookup/toolset-membership construction from the runtime `isPermitted` gate, which should already be enforced separately in `getTools()`/`observeTools()`/`isPermitted()` for actual tool availability.
