# Issue #295547 — Do not scroll chat too much such that my full message is not visible

[https://github.com/microsoft/vscode/issues/295547](https://github.com/microsoft/vscode/issues/295547)

## Summary

The gap remains on current main: adding a request explicitly scrolls the transcript to its end, which can move the top of a long user message out of view. Existing sticky-prompt behavior improves navigation but does not replace this submission-time scroll policy.

## Change summary

Keep a newly submitted long chat message fully visible when possible, preferably revealing its top instead of immediately scrolling past it.

## Best solution

Define a submission-time anchoring policy that reveals the start of the new request when the request fits, handles requests taller than the viewport predictably, and transitions to response-following without a disorienting jump. This belongs in the chat widget's add-request and list reveal behavior while preserving explicit Scroll to Bottom behavior.

- **Behavior:**

  > After a user submits a multi-line chat request, the transcript should keep that request comprehensible rather than immediately scrolling its beginning out of view. When the complete request fits in the viewport, its full body should remain visible. Requests taller than the viewport and the transition into streaming response-following need one consistent policy. Explicit Scroll to Bottom and ordinary response auto-follow behavior must remain available.
- **Trace:**

  > The add-request listener in src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts calls `ChatListWidget.scrollToEnd()` after refreshing the view model. In src/vs/workbench/contrib/chat/browser/widget/chatListWidget.ts, `scrollToEnd()` reveals the final tree item at its bottom edge and applies bottom padding, which explains why the beginning of a long request can leave the viewport. Current sticky-prompt support is enabled separately and capped in height, so it does not settle submission-time positioning. Preserve explicit bottom navigation, user-controlled scrolling, sticky-prompt navigation, and configured response-follow behavior; the scope is the initial add-request anchor and its transition into streaming.
- **Open decisions:**
  - For a request taller than the viewport, should submission align its beginning to the viewport top, or align its end so the first response content can appear immediately?
  - When should response auto-follow be allowed to move away from the newly submitted request: as soon as response content arrives, only after the request has been visible for the initial frame, or only after an explicit user action?

## Evidence

- **current source path:** In src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts, the view-model change listener calls `listWidget.scrollToEnd()` whenever an `addRequest` event arrives (around lines 2924-2948), so submission deliberately uses bottom alignment rather than revealing the request top.
- **scroll behavior:** In src/vs/workbench/contrib/chat/browser/widget/chatListWidget.ts, `scrollToEnd()` delegates to `revealLastItem()`, which reveals the final item with a very large relative offset and then consumes effective bottom padding (around lines 1254-1270). For a long request or an immediately-created response row, this can place the request's beginning above the viewport.
- **existing capability check:** Current main enables chat prompt sticky scroll through `chat.stickyScroll.enabled`, but the tree configuration caps the sticky node at 150 pixels and the add-request listener still calls `scrollToEnd()`. Sticky navigation therefore does not guarantee that the full newly submitted message remains visible.
