# Issue #131084 — Search files by name is very slow even for cases that could be optimised

[https://github.com/microsoft/vscode/issues/131084](https://github.com/microsoft/vscode/issues/131084)

## Summary

Keep open: current Quick Open checks workspace-relative paths, but still waits for the full file search before returning those matches, and does not resolve paths relative to the active file. The closely matching newer report cannot replace this older, previously reviewed issue.

## Change summary

Make exact workspace-relative and active-file-relative paths available in Quick Open without waiting for a workspace-wide file search.

## Best solution

Provide promptly selectable exact relative-path matches in AnythingQuickAccessProvider, retaining normal search when no exact file exists. Settle how multiple exact matches and subsequent fuzzy results should be presented before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts`
- **Validation:** Use a regression test with a deferred workspace file-search response and an immediately successful exact-path stat: the exact match must become selectable before the deferred search resolves. Cover workspace-relative and active-file-relative inputs, missing files, multiple exact matches, and cancellation. Manually verify Cmd/Ctrl+P with a previously unopened exact relative path in a large workspace.
- **Behavior:**

  > Pasting an existing workspace-relative or active-file-relative file path into Quick Open should make the exact target selectable without waiting for the workspace-wide fuzzy search. Missing exact targets should retain normal file-search behavior. Acceptance must distinguish exact-match availability from overall search completion and cover ambiguous paths across workspace roots or the active file's directory.
- **Trace:**

  > In src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts, getFilePicks short-circuits an existing absolute path, while doFileSearch joins getFileSearchResults and getRelativePathFileResults with Promise.all. getRelativePathFileResults already stats candidates under workspace folders, but has no active-file-relative lookup; its successful results remain blocked by the other promise. getAdditionalPicks adds another file/symbol aggregation step before sorting and presentation. Preserve ordinary fuzzy matching, remote URI handling, filename casing, cancellation, and existing excluded-file exact lookup behavior. The remaining uncertainty is user-visible presentation when exact matches exist, particularly when several roots or the active directory resolve the same input. Related https://github.com/microsoft/vscode/issues/325607 independently describes the workspace-relative delay but is newer than this report.
- **Open decisions:**
  - When exact relative-path matches exist, should Quick Open show only those matches, or show them immediately and append fuzzy results later?
  - When workspace roots and the active file's directory resolve the same input to different files, should all exact candidates have equal standing or should one location take precedence?
