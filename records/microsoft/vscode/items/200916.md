# Issue #200916 — SCM - Sorting Changes by FileSystem's "Modified Date"

[https://github.com/microsoft/vscode/issues/200916](https://github.com/microsoft/vscode/issues/200916)

## Summary

Keep this accepted request open: current SCM sorting still lacks filesystem modification-time ordering, and the issue has 41 upvotes. The related newer report was closed as a duplicate of this issue, so this remains the appropriate tracking item.

## Change summary

Add filesystem modification-time sorting to the Source Control changes list.

## Best solution

Extend the existing SCM list sorting surface with modification-time ordering, without introducing arbitrary filesystem filters or changing tree ordering. Settle timestamp availability and refresh behavior for deleted, virtual, and remote resources before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/scm/browser/scmViewPane.ts`, `src/vs/workbench/contrib/scm/browser/scm.contribution.ts`, `src/vs/workbench/contrib/scm/common/scm.ts`
- **Validation:** Create changed files whose names and paths sort differently from their known filesystem modification times. In SCM list mode, select modification-time sorting and verify chronological ordering; modify an already-listed file and verify the agreed refresh behavior. Check equal timestamps, deleted files, unsupported virtual resources, and a remote repository. Verify existing name/path/status sorting, selection, staging, reload persistence, and tree ordering remain unchanged.
- **Behavior:**

  > Users need to order the SCM changes list by filesystem modification time rather than filename, path, or Git status. The option should make recently edited files discoverable while preserving existing resource groups and staging behavior. Acceptance should use files with deliberately different name, path, and timestamp orders, including edits to files already listed as modified. Existing sorting modes and tree behavior must remain unchanged, and unavailable timestamps must have a defined, predictable outcome.
- **Trace:**

  > The configuration registration in src/vs/workbench/contrib/scm/browser/scm.contribution.ts and ViewSortKey, SetSortKeyAction, and getViewSortKey in src/vs/workbench/contrib/scm/browser/scmViewPane.ts currently support only name, path, and status. SCMTreeSorter.compare is synchronous and reads resource names, status tooltips, and paths; no timestamp acquisition is present in that sorting path. ISCMResource in src/vs/workbench/contrib/scm/common/scm.ts has sourceUri but no modification-time field, and SCMViewPane updates children on resource-group changes. The remaining investigation is how filesystem metadata becomes available and stays current without slowing default SCM behavior, especially for remote, deleted, and virtual resources. Keep scope to modification-time list sorting, not arbitrary filesystem criteria, commit chronology, filtering, or tree reordering. https://github.com/microsoft/vscode/issues/204283 is already consolidated here; https://github.com/microsoft/vscode/issues/101116 documents the existing sorting contract.
- **Open decisions:**
  - Should modification-time sorting show newest files first only, or expose both chronological directions?
  - What ordering should users see for deleted or virtual resources whose filesystem modification time is unavailable?
  - Should timestamp ordering update while a file remains in the changes list, or only when SCM refreshes its resource groups?
