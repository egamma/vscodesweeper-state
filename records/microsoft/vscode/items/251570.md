## Plan brief

- **Likely files:** `src/vs/platform/userDataProfile/common/userDataProfile.ts`, `src/vs/platform/userDataProfile/node/userDataProfile.ts`, `src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts`, `src/vs/platform/storage/electron-main/storageMain.ts`, `src/vs/workbench/services/workingCopy/common/workingCopyHistoryService.ts`, `src/vs/workbench/services/workingCopy/common/workingCopyHistoryTracker.ts`, `src/vs/workbench/browser/workbench.contribution.ts`
- **Validation:** Create a workspace with a selected non-default profile, a workspace-disabled extension, and multiple saved revisions of a file. Close VS Code, rename and move the workspace outside VS Code, and reopen it; verify the selected profile, extension enablement, and timeline revisions remain available. Repeat for the agreed folder and multi-root scope, and verify workspaces not using the mechanism retain existing storage behavior.
- **Behavior:**

  > The reporter wants workspace-specific profile selection, extension enablement preferences, and local file history to accompany the workspace folder rather than remain associated only with its old location in application storage. After closing VS Code and externally moving or renaming that folder, reopening it should retain all three kinds of state. Acceptance must check actual profile selection, extension enablement, and access to prior timeline revisions, not merely the presence of files in a storage directory. The intended activation model and supported workspace types still require a product decision.
- **Trace:**

  > Profile associations are stored as workspace-URI-to-profile-ID mappings in src/vs/platform/userDataProfile/common/userDataProfile.ts and persisted through the application state service by src/vs/platform/userDataProfile/node/userDataProfile.ts. ExtensionEnablementService stores workspace enabled/disabled identifiers through StorageScope.WORKSPACE, while WorkspaceStorageMain locates storage under workspaceStorageHome using the workspace ID. WorkingCopyHistoryService selects environment-provided localHistoryHome and keys history directories by resource-URI hashes; WorkingCopyHistoryTracker handles file-service moves, which is narrower than portable state accompanying an externally relocated workspace. Existing local-history settings do not select a storage location, and --profile or --user-data-dir does not satisfy the combined automatic portability requirement. Related work is tracked at https://github.com/microsoft/vscode/issues/193970 and https://github.com/microsoft/vscode/issues/40239, but neither subsumes this request. The design boundary includes existing workspaces that should retain their current behavior and historical state; no persistence or migration change was executed during this read-only review.
- **Open decisions:**
  - Should folder-local portable state be explicitly enabled per workspace, or become the default for supported workspaces?
  - Does portability include only moves and renames on the same installation, or also copying the workspace to another installation where its selected profile may not exist?
  - For multi-root workspaces, which location owns the portable state, and what should happen when one root is moved independently?
