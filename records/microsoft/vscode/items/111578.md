# Issue #111578 — Progress: cannot cancel

[https://github.com/microsoft/vscode/issues/111578](https://github.com/microsoft/vscode/issues/111578)

## Summary

A real cancellation gap remains for Explorer transfers on current main, especially single native remote downloads and uploads. The accepted Backlog request should remain open for a transfer-cancellation design spanning the Explorer and file-service paths.

## Change summary

Allow users to cancel Explorer download and upload operations, including a single transfer involving a remote workspace.

## Best solution

Explorer downloads and uploads should expose cancellation for single and multi-file transfers, stop scheduling remaining files immediately, and interrupt the active transfer when the underlying provider supports it. Move and delete behavior should remain outside this request.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/fileImportExport.ts`, `src/vs/workbench/contrib/files/browser/explorerService.ts`, `src/vs/workbench/contrib/bulkEdit/browser/bulkFileEdits.ts`, `src/vs/workbench/services/workingCopy/common/workingCopyFileService.ts`, `src/vs/workbench/contrib/bulkEdit/test/browser/bulkFileEdits.test.ts`
- **Validation:** Add a targeted cancellation test covering a single copy in the bulk-file-edit/working-copy path, then manually verify in a remote workspace that cancelling one large Explorer download or upload stops further transfer work without reloading the window.
- **Behavior:**

  > A single or multi-file download or upload started from the Explorer presents a working cancel action. Cancelling stops scheduling remaining files and aborts the active transfer when its provider supports cancellation; otherwise it stops at the next safe per-file boundary. The operation must settle without requiring a window reload, while completed files remain valid. Move and delete operations are not part of this request.
- **Trace:**

  > FileDownload.download in src/vs/workbench/contrib/files/browser/fileImportExport.ts marks progress cancellable only for web, while doDownloadNative delegates a single ResourceFileEdit to ExplorerService.applyBulkEdit. ExplorerService in src/vs/workbench/contrib/files/browser/explorerService.ts exposes cancellation only when `edit.length > 1`, which excludes the reported single-transfer case. BulkFileEdits forwards a token into WorkingCopyFileService.copy, but WorkingCopyFileService.doMoveOrCopy in src/vs/workbench/services/workingCopy/common/workingCopyFileService.ts invokes FileService.copy without cancellation and does not stop an active copy. Browser download and upload already contain token-aware loops, so preserve those behaviors and avoid expanding the scope to generic move/delete cancellation. Related progress work is tracked by https://github.com/microsoft/vscode/issues/111580, but this issue remains the established cancellation tracker.

## Evidence

- **current native path:** src/vs/workbench/contrib/files/browser/fileImportExport.ts:618-636 makes FileDownload progress cancellable only when `isWeb`; `doDownloadNative` performs one ResourceFileEdit through ExplorerService, so desktop connections to remote workspaces still lack a cancel action.
- **single-operation restriction:** src/vs/workbench/contrib/files/browser/explorerService.ts:207-235 sets `cancellable: edit.length > 1`. A single download or upload edit therefore cannot be cancelled even though a CancellationToken is supplied to BulkEditService.
- **token propagation gap:** src/vs/workbench/contrib/bulkEdit/browser/bulkFileEdits.ts passes the token into WorkingCopyFileService.copy, but src/vs/workbench/services/workingCopy/common/workingCopyFileService.ts:398-446 calls `fileService.copy(source, target, overwrite)` without the token and does not check cancellation around each active copy.
- **canonical status:** https://github.com/microsoft/vscode/issues/181992 was closed as a duplicate of this issue, confirming https://github.com/microsoft/vscode/issues/111578 as the established cancellation tracker.
- **related but not canonical:** https://github.com/microsoft/vscode/issues/111580 is open and discusses transfer progress plus cancellation, but it was created after this re-reviewed issue and has the broader observable goal of aligning desktop and web progress, so it does not meet the stronger duplicate bar.
- **maintainer direction:** The discussion on https://github.com/microsoft/vscode/issues/111578 explicitly accepts offering cancellation for download and upload on at least a per-file basis, while leaving move and delete outside the proposed scope.
