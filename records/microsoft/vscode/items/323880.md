# Issue #323880 — Allow vscode:// (file / folder open) URL to specify non-destructive window re-use options

[https://github.com/microsoft/vscode/issues/323880](https://github.com/microsoft/vscode/issues/323880)

## Summary

Keep open: the current URL handler lacks a per-link policy that preserves matching-window reuse while preventing unrelated workspace replacement. Existing settings provide a user-level workaround, but neither verified related issue owns the full request.

## Change summary

Allow vscode:// file and folder links to request matching-workspace reuse without replacing an unrelated active workspace.

## Best solution

Define an opt-in URL contract for safe matching-window reuse, with an explicit non-destructive fallback when no workspace matches. Preserve existing link behavior unless the new option is supplied.

## Plan brief

- **Likely files:** `src/vs/code/electron-main/app.ts`, `src/vs/platform/windows/electron-main/windowsMainService.ts`, `src/vs/platform/windows/electron-main/windowsFinder.ts`
- **Validation:** After the contract is agreed, exercise actual vscode:// links with an unrelated active workspace and a separate matching workspace: matching targets reuse the matching window, unmatched targets follow the chosen non-destructive fallback, and the unrelated workspace and terminals remain intact. Repeat for file and folder targets, single-folder and multi-root workspaces, existing windowId=_blank links, and links without the new option.
- **Behavior:**

  > External documentation tools need to emit vscode:// links without knowing which workspaces are already open. An opt-in link policy should reuse an eligible matching workspace without replacing an unrelated active workspace; when no match exists, it should use an explicitly agreed non-destructive fallback. Acceptance covers both file and folder links, preserves the unrelated workspace's terminals and editor context, and leaves existing links unchanged. The exact matching scope and fallback behavior remain product decisions.
- **Trace:**

  > CodeApplication.handleProtocolUrl in src/vs/code/electron-main/app.ts extracts windowId=_blank and forwards forceNewWindow into WindowsMainService.open. In src/vs/platform/windows/electron-main/windowsMainService.ts, file opening consults findWindowOnFile unless forced new, then falls back to the last active window; folder opening first checks findWindowOnWorkspaceOrFolder and otherwise follows shouldOpenNewWindow. The two matchers in src/vs/platform/windows/electron-main/windowsFinder.ts differ: file matching understands resolved multi-root containment, while folder matching checks exact single-folder or workspace-configuration identity. window.openFoldersInNewWindow is a global workaround, not a per-link contract. Preserve existing CLI behavior, existing URL defaults, authority separation, and windowId=_blank semantics outside the agreed scope. https://github.com/microsoft/vscode/issues/336105 tracks related multi-root integration work, and https://github.com/microsoft/vscode/issues/209188 tracks remote URL replacement; neither is a verified canonical for this request. Source inspection establishes the missing policy, but startup handling and runtime acceptance remain to be examined during planning.
- **Open decisions:**
  - Should the initial public URL contract provide one safe reuse-or-new mode, or also expose warning and explicit replacement modes?
  - For folder links, does a matching workspace mean an exact open folder only, or also a folder contained within an open single-folder or multi-root workspace?
  - When no workspace matches, should the opt-in policy always open a new window or ask before proceeding, and how should that policy interact with window.openFoldersInNewWindow?

## Evidence

It does not expose a conditional matching-workspace reuse policy or the proposed noReplaceActive/windowReuseLogic options.
- **Existing setting is partial coverage:** src/vs/workbench/browser/workbench.contribution.ts:978–988 registers window.openFoldersInNewWindow with on/off/default. WindowsMainService.shouldOpenNewWindow consumes it at src/vs/platform/windows/electron-main/windowsMainService.ts:1363–1373. Setting it to on prevents unmatched folder replacement while exact already-open folders can still be reused, but this is application-wide user configuration, not intent expressible by a link emitter.
- **Matching boundary:** src/vs/platform/windows/electron-main/windowsFinder.ts:11–59 distinguishes findWindowOnFile, which resolves multi-root workspace folders and checks containment, from findWindowOnWorkspaceOrFolder, which checks only workspace configuration URI or exact single-folder URI. WindowsMainService.open uses the latter for folder requests at windowsMainService.ts:670–708. Forced-new file requests skip matching at lines 589–596; unmatched files otherwise fall back to the last active window, so the report's unmatched-file observation is not a universal guarantee.
