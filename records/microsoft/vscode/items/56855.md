# Issue #56855 — [themes] Allow custom variables and references in workbench color customizations section

[https://github.com/microsoft/vscode/issues/56855](https://github.com/microsoft/vscode/issues/56855)

## Summary

The request remains necessary on current main: workbench color customizations accept literal colors or `default`, but cannot define variables or reference other registered colors. This issue is the established canonical for settings-based variables and references, while the unresolved expression syntax and transformation scope warrant `under-discussion` rather than closure.

## Change summary

Allow reusable custom variables, existing color references, and potentially derived colors in `workbench.colorCustomizations`.

## Best solution

Define one bounded color-expression contract for user color customizations that supports reusable palette entries and registered-color references while preserving existing literal and theme-scoped overrides. A maintainer should first settle whether transformations and the editor token customization settings belong in the same contract.

## Plan brief

- **Likely files:** `src/vs/platform/theme/common/colorUtils.ts`, `src/vs/workbench/services/themes/common/themeConfiguration.ts`, `src/vs/workbench/services/themes/common/colorThemeData.ts`, `src/vs/workbench/services/themes/test`
- **Validation:** End the plan with theme-service unit tests that load literal colors, palette variables, registered-color references, undefined references, theme-scoped overrides, and any approved transformations; run the new suite with `scripts/test.sh --grep "Themes - Color Customizations"`.
- **Behavior:**

  > Users can define reusable colors in workbench color customizations and use them for multiple registered workbench color IDs. Approved references remain adaptive when the active theme changes, while existing hexadecimal colors, `default`, and theme-specific override blocks continue to behave unchanged. Invalid, missing, or cyclic references produce an explicitly chosen and testable outcome rather than being silently interpreted as colors. Acceptance must cover literals, variables, registered-color references, theme-scoped customizations, and any approved transformation syntax.
- **Trace:**

  > The setting schema in src/vs/workbench/services/themes/common/themeConfiguration.ts references the workbench color schema built by ColorRegistry in src/vs/platform/theme/common/colorUtils.ts. That schema currently permits only hexadecimal strings or `default`, and ColorThemeData.overwriteCustomColors in src/vs/workbench/services/themes/common/colorThemeData.ts parses every other customization string with `Color.fromHex`. Internal registered-color defaults already have reference and transform machinery through `resolveColorValue`, but user customization values do not enter that path. https://github.com/microsoft/vscode/issues/105247 covers theme-definition files rather than settings, and the unmerged https://github.com/microsoft/vscode/pull/199091 deliberately excluded settings after exposing schema-complexity concerns. Preserve current literal/default handling and theme-specific precedence; do not broaden into arbitrary configuration-variable substitution tracked by https://github.com/microsoft/vscode/issues/2809.
- **Open decisions:**
  - Should the public contract expose only named palette variables, only references to registered workbench color IDs, or both?
  - Are relative-color transformations part of the initial contract, and if so which bounded operations and failure behavior are supported?
  - Does the contract apply only to `workbench.colorCustomizations`, or consistently to `editor.tokenColorCustomizations` and `editor.semanticTokenColorCustomizations` as well?
  - What user-visible result should undefined and cyclic references produce: validation-only rejection, fallback to `default`, or an explicit diagnostic color?

## Evidence

- **current source:** src/vs/platform/theme/common/colorUtils.ts:143-157 defines each workbench customization value as a hexadecimal color string or the literal `default`; custom palette properties and color references are not represented by the settings schema.
- **resolution path:** src/vs/workbench/services/themes/common/colorThemeData.ts:406-428 sends customization strings directly through `Color.fromHex`, so registered color identifiers and user-defined variables are not resolved on current main.
