# Issue #327755 — setting workbench.editorAssociations does not applyToAllProfiles

[https://github.com/microsoft/vscode/issues/327755](https://github.com/microsoft/vscode/issues/327755)

## Summary

The bug remains source-reproducible on current main: editor association resolution manually reads the user configuration layer but omits the application layer where settings listed in `workbench.settings.applyToAllProfiles` are stored for non-default profiles.

## Change summary

Editor associations marked to apply to all profiles are ignored after switching from the default profile to another profile.

## Best solution

Editor resolution should include application-level editor associations while preserving the existing precedence among workspace, default, and profile-specific associations.

## Evidence

- **source reproduction:** In src/vs/workbench/services/configuration/browser/configuration.ts, `ApplicationConfiguration.loadConfiguration()` includes keys listed by `workbench.settings.applyToAllProfiles`, placing the default-profile value of `workbench.editorAssociations` in the application configuration layer.
- **root cause:** In src/vs/workbench/services/editor/browser/editorResolverService.ts, `getAllUserAssociationsForSetting()` merges `defaultValue`, `workspaceValue`, and `userValue` from `IConfigurationService.inspect()`, but never reads `applicationValue`. src/vs/platform/configuration/common/configurationModels.ts shows that `userValue` is derived only from local and remote user configuration, separately from `applicationValue`.
- **reported trigger:** After `workbench.editorAssociations` is added to `workbench.settings.applyToAllProfiles`, switching to a non-default profile moves the shared association into the application layer; Ctrl+clicking a JPG then misses the `*.jpg: default` association and selects the preview editor.
