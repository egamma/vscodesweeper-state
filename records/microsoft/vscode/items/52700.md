# Issue #52700 — Git - Support submodule management

[https://github.com/microsoft/vscode/issues/52700](https://github.com/microsoft/vscode/issues/52700)

## Summary

Keep open: built-in Git support detects existing submodules but still lacks general submodule-management commands. This accepted Backlog request has 24 upvotes, and a maintainer has since expressed interest in adding submodule actions to the Repositories view.

## Change summary

Provide built-in commands and UI actions for Git submodule management, especially add, initialize, and update.

## Best solution

Provide explicit submodule-management actions in the built-in Git experience, following the maintainer's stated Repositories-view direction. Retain this older request as the central record and coordinate the overlapping newer request without losing its broader add/init/update scope.

## Plan brief

- **Likely files:** `extensions/git/package.json`, `extensions/git/package.nls.json`, `extensions/git/src/commands.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/git.ts`, `extensions/git/src/model.ts`, `extensions/git/src/test/smoke.test.ts`
- **Validation:** In disposable local parent and child Git repositories, verify the agreed UI actions can add a submodule, initialize one in a nonrecursive clone, and update it to the parent-recorded commit after that commit changes. Check .gitmodules, the gitlink, child HEAD, and repository visibility; verify failures are surfaced and dirty child work is not silently discarded. Include Git extension smoke coverage for the agreed command semantics.
- **Behavior:**

  > Users can manage submodules in an existing repository through VS Code rather than needing the terminal for every operation. The original request prioritizes add, initialize, and update; later comments also request removal, update-all, and integration with pulls or branch switches. Acceptance should verify the agreed operations against real local Git repositories and ensure existing detection, recursive cloning, and ordinary repository operations remain unchanged. The distinction between explicit update actions and automatic updates needs to be settled before implementation.
- **Trace:**

  > extensions/git/package.json and extensions/git/src/commands.ts expose git.cloneRecursive but no general submodule-management commands. Model.checkForSubmodules in extensions/git/src/model.ts scans existing submodule paths; it does not initialize or add them. Repository.updateSubmodules in extensions/git/src/git.ts executes git submodule update for supplied paths, and its existing caller in extensions/git/src/repository.ts is the discard-changes flow. These are partial capabilities, not coverage of the central request. The maintainer's comment at https://github.com/microsoft/vscode/issues/283999#issuecomment-3664711099 establishes a Repositories-view direction, but does not settle operation scope or automatic-update behavior. Preserve existing clone, detection, and discard semantics; coordinate with https://github.com/microsoft/vscode/issues/283999 and the pull scenario consolidated from https://github.com/microsoft/vscode/issues/125842.
- **Open decisions:**
  - Should the first supported management surface cover add/init/update only, or also remove/deinit, summary, and update-all?
  - Should updates remain explicit user actions, or should pulls and branch switches optionally update submodules automatically?
  - Should the update action only check out the parent-recorded submodule commit, or also expose a distinct update-to-remote operation?
