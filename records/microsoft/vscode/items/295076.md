# Issue #295076 — Allow extensions to handle agent hooks execution

[https://github.com/microsoft/vscode/issues/295076](https://github.com/microsoft/vscode/issues/295076)

## Summary

Keep open: extensions can provide hook configuration files, but the inspected API does not let them register extension-host execution callbacks. This team-authored request remains the designated tracking issue; the related extensibility request is newer and is not a valid duplicate target for this re-review.

## Change summary

Allow extensions to dynamically register agent hooks whose execution happens inside the contributing extension rather than through shell scripts.

## Best solution

Define an extension-host hook execution contract that gives extensions access to their state and VS Code APIs while preserving existing shell-hook behavior. Agree on registration scope, lifecycle coverage, and execution semantics before implementing the API and its agent integration.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.chatHooks.d.ts`, `src/vs/workbench/api/common/extHostChatAgents2.ts`, `src/vs/workbench/api/browser/mainThreadChatAgents2.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `extensions/copilot/src/extension/chat/vscode-node/chatHookService.ts`
- **Validation:** After the API contract is agreed, add an extension-host integration check that registers a hook callback, triggers the corresponding agent lifecycle event, observes extension-held state and current in-memory document content, and verifies disposal prevents subsequent invocation. Cover the agreed result, cancellation, and ordering semantics alongside existing shell-hook behavior.
- **Behavior:**

  > An extension can dynamically contribute an agent lifecycle hook and execute its handler inside the extension host, with access to extension-held state and VS Code APIs. The handler must not require a shell-script bridge. Acceptance should demonstrate invocation at an agreed lifecycle event, access to current in-memory document content, and removal of the contribution when its registration is disposed. Existing shell hooks must retain their behavior.
- **Trace:**

  > ChatHookProvider in src/vscode-dts/vscode.proposed.chatPromptFiles.d.ts supplies configuration-file resources, and extHost.api.impl.ts routes its registration through ExtHostChatAgents2.registerPromptFileProvider. The separate chatHooks proposal represents executable hooks as shell commands; ChatHookService.executeHook in extensions/copilot/src/extension/chat/vscode-node/chatHookService.ts sends those commands to _hookExecutor.executeCommand. This establishes the distinction between donating hook files and owning execution, but does not settle a callback API or its integration across agent runtimes. Preserve existing resource-provider and shell-hook contracts. https://github.com/microsoft/vscode/issues/293808 explicitly consolidated here; https://github.com/microsoft/vscode/issues/306375 is a newer related request, and https://github.com/microsoft/vscode/issues/315926#issuecomment-4444251786 supplies the in-memory-state use case.
- **Open decisions:**
  - Are extension-executed hooks registered globally, per workspace, or per agent session, and which agent runtimes must honor them?
  - Which lifecycle events and hook results are part of the initial extension API, including whether handlers can block operations or stop a turn?
  - What ordering, cancellation, timeout, and failure behavior should users observe when extension handlers and shell hooks participate in the same event?
