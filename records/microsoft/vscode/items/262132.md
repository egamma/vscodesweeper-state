# Issue #262132 — ObservableMap/Set API should be improved

[https://github.com/microsoft/vscode/issues/262132](https://github.com/microsoft/vscode/issues/262132)

## Summary

Keep open: current ObservableMap/Set APIs still expose ordinary collection reads that bypass dependency tracking. The linked PR fixed one missed subscription, not the API ergonomics raised by this team-authored issue.

## Change summary

Make ObservableMap/Set reads less prone to accidentally omitting reactive dependency tracking.

## Best solution

Establish an internal collection API contract that clearly distinguishes tracked reads from deliberate untracked access, then migrate consumers while preserving mutation and transaction semantics. A maintainer should settle the compatibility boundary before implementation.

- **Behavior:**

Deliberate untracked reads must remain possible under an agreed contract. Acceptance should cover map lookup, set membership, collection size and iteration, plus recomputation after mutations and existing transaction batching. The issue requests safer API ergonomics, not merely another repair of the already-fixed chat call site.
- **Trace:**

  > ObservableMap in src/vs/base/common/observableInternal/map.ts implements Map and ObservableSet in set.ts implements Set; their ordinary read methods delegate directly to _data. Each exposes a separate observable whose read(reader) subscribes the computation, as documented in observableInternal/base.ts. https://github.com/microsoft/vscode/pull/261793 demonstrates the failure mode by adding that subscription at one chat lookup. Current ChatModelStore consumers intentionally use ordinary reads, while common/tools/languageModelToolsService.ts explicitly tracks ObservableSet reads. Preserve mutation behavior, collection ordering and transaction batching, and do not treat the linked chat fix as completion of this API request.
- **Open decisions:**
  - Should ObservableMap/Set retain ordinary Map/Set read compatibility, or require an explicitly tracked or untracked collection view before reading data?

## Evidence

- **Current API gap:** src/vs/base/common/observableInternal/map.ts exposes get, has, size, iteration and forEach directly over _data; set.ts does likewise for Set reads. None of these read paths accepts a reader or subscribes it. Tracking is available separately through collection.observable.read(reader), so the omission described in the issue remains possible.
- **Existing tracking capability:** src/vs/base/common/observableInternal/base.ts documents IObservableWithChange.read(reader) as subscribing the reader. This provides a working opt-in mechanism, but does not make direct ObservableMap/Set access tracking-safe.
- **Linked concrete example:** https://github.com/microsoft/vscode/pull/261793 merged on 2025-08-19. Its sole change replaced this._sessionStates.get(currentMode.id) with this._sessionStates.observable.read(r).get(currentMode.id) in chatSelectedTools.ts. That corrects the specific missed read without changing either collection API.
- **Compatibility boundary:** src/vs/workbench/contrib/chat/common/model/chatModelStore.ts uses ObservableMap.get, has and values directly while exposing _models.observable separately. src/vs/workbench/contrib/chat/common/tools/languageModelToolsService.ts uses ObservableSet.observable.read(r) in reactive computations. These consumers demonstrate both deliberate untracked access and tracked access that an API redesign must accommodate.
