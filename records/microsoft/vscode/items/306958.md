## Evidence

- **canonical issue:** https://github.com/microsoft/vscode/issues/280486 is open, predates this report, carries the accepted bug/chat labels, and describes the same observable behavior: after an image exceeds the 8000-pixel limit, every later request in that chat fails because the image remains in history.
- **source-confirmed resize gap:** src/vs/workbench/contrib/chat/browser/chatImageUtils.ts returns the original image when either width or height is at most 768 (`width <= 768 || height <= 768`). Consequently, an extreme image such as 9000x500 bypasses the later longest-side scaling and can reach the service above its 8000-pixel cap.
- **request path:** The Copilot image service invokes the `_chat.resizeImage` command registered in src/vs/workbench/contrib/chat/browser/chatImageUtils.ts; chat attachment restoration also routes non-pasted image data through this helper in src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts.
- **corroborating report:** https://github.com/microsoft/vscode/issues/306383 independently reports the same unrecoverable image-dimension loop, and a maintainer identified improper image resizing as the likely cause.
- **distinct comment symptom:** The later `thinking_0` comment reports a separate cross-model request-serialization error, not the oversized-image root cause. Current main's extensions/copilot/src/platform/endpoint/node/responsesApi.ts filters reasoning by its originating API and excludes non-Responses `thinking_0` data.
