# Issue #57370 — Settings decoration: Modified in Folder

[https://github.com/microsoft/vscode/issues/57370](https://github.com/microsoft/vscode/issues/57370)

## Summary

Keep open: the settings editor still does not enumerate folder-specific modifications in its scope indicators. This team-authored, accepted request remains the older tracking item; the newer matching report is supporting evidence, not a duplicate target.

## Change summary

Show which workspace folders modify a setting in the settings editor's modification indicators, including when viewing workspace settings.

## Best solution

Extend the existing settings modification indicators to identify affected workspace folders while preserving settings-editor responsiveness. Retain this issue as the canonical request and associate the newer matching report with it.

- **Fit:** aligned
- **Reason:** Making configuration scope visible improves settings fidelity and lets the existing interface explain why a setting behaves differently across folders.

## Plan brief

- **Validation:** In a multi-root workspace, modify a resource-scoped setting in two folders but not a third. Verify user and workspace settings identify exactly the two modified folders, then remove one override and verify the indication updates. Cover model enumeration and indicator rendering in the preferences tests, verify any folder links select the correct folder, and compare settings-editor rendering responsiveness with many folders before and after.
- **Behavior:**

  > When a setting is modified in workspace folders, the settings editor identifies those folders from both user and workspace settings. Multiple affected folders must be distinguishable, and folders without an override must not appear. Adding or removing a folder override updates the indication. Existing user, remote, workspace, language, and managed-setting indicators retain their behavior, and the additional inspection must not materially degrade settings-editor responsiveness.
- **Trace:**

  > SettingsTreeSettingElement.update in src/vs/workbench/contrib/preferences/browser/settingsTreeModels.ts constructs overriddenScopeList without folder entries. inspectSetting supplies a resource only for a selected folder target, so user and workspace views never collect per-folder modifications. SettingsTreeIndicatorsLabel.updateScopeOverrides in src/vs/workbench/contrib/preferences/browser/settingsEditorSettingIndicators.ts renders that list, and its ScopeString contract cannot identify a folder. The override-click handler in src/vs/workbench/contrib/preferences/browser/settingsEditor2.ts also has no folder destination. Folder-settings opening commands already exist in preferences.contribution.ts, but are manual inspection rather than coverage of this request. Maintainers accepted resource-specific inspection and explicitly called for performance measurement, potentially using lazy row rendering. Preserve existing scope and language behavior; establish the folder presentation/navigation contract and performance acceptance before implementation. https://github.com/microsoft/vscode/issues/301462 supplies a newer matching scenario, while https://github.com/microsoft/vscode/issues/50516 was already consolidated into this issue.
- **Open decisions:**
  - Should each named folder in the modification indicator navigate directly to that folder's settings, matching existing scope links, or should the initial feature provide informational folder names only?
