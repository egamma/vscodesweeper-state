# Issue #244064 — Enhance scoping for MCP severs

[https://github.com/microsoft/vscode/issues/244064](https://github.com/microsoft/vscode/issues/244064)

## Summary

Keep open: workspace-folder MCP configuration does not provide automatic, file-context-based server selection across several folders. The merged folder-support PR explicitly left this broader capability for this issue; the remaining work needs product decisions about context matching and tool availability during a request.

## Change summary

Allow MCP servers and their tools to be scoped automatically to relevant files or multiple folders, potentially through glob patterns in a shared configuration.

## Best solution

Define scenario-driven MCP applicability rules for monorepos, including which files determine relevance and when the available tool set changes. Preserve existing folder-level configuration and manual enablement while designing automatic selection for the three-language-family scenario described in the discussion.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts`, `src/vs/workbench/contrib/mcp/common/discovery/installedMcpServersDiscovery.ts`, `src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts`
- **Validation:** After the applicability contract is agreed, exercise three MCP servers mapped to distinct language-family subfolders: a request concerning one family should expose the applicable tools, a request spanning families should follow the agreed combination rule, and unrelated servers should remain excluded. Verify the chosen behavior when context changes between turns and verify that servers without applicability rules retain their existing behavior.
- **Behavior:**

  > A monorepo user should not need to switch MCP servers manually for each prompt when different servers apply to different language-family subfolders. A shared configuration should be able to express applicability across multiple paths without duplicating configuration into each folder. Acceptance must cover single-family context, context spanning several families, and changes of context during a conversation. Servers without applicability rules must retain their existing behavior.
- **Trace:**

  > The initial folder-level implementation in https://github.com/microsoft/vscode/pull/244066 explicitly reserves this work for https://github.com/microsoft/vscode/issues/244064. Current server schemas in src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts have no file-applicability selector; development watch globs and sandbox rules have different semantics. InstalledMcpServersDiscovery assigns configuration-folder roots, while McpLanguageModelToolContribution registers enabled servers' model-visible tools without matching the conversation's files. The trace establishes a missing applicability capability, not a broken existing behavior. Uncertainty starts at the definition of relevant conversation context and the timing of tool-set changes; the downstream request lifecycle would need further tracing after those choices. Preserve existing discovery, manual enablement, and unscoped server behavior, and do not treat applicability filtering as a filesystem security boundary.
- **Open decisions:**
  - Which context determines server applicability: the active editor, explicit chat attachments, files referenced or accessed during the conversation, or a defined combination?
  - When context spans several matching paths or has no matching file, which server tool sets should be available?
  - Should applicability be fixed for an entire user request or reevaluated between model turns as the working files change?
