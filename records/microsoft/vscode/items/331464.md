# Issue #331464 — Agent Host issue - keeps asking to sign in to Github although signed in

[https://github.com/microsoft/vscode/issues/331464](https://github.com/microsoft/vscode/issues/331464)

## Summary

Traced a plausible root cause in source: the Agent Host's protected-resource auth flow requires an exact/glob match between the resource's advertised `authorization_servers` and the provider's declared `authorizationServers`, but the built-in GHES provider only declares `<ghesUri>/login/oauth` — if the GHES instance's OAuth/OIDC issuer differs (e.g. bare host), the match always fails, causing repeated 'No token resolved' and re-prompts even with a valid session.

## Change summary

Agent Host repeatedly fails to resolve a token for a GitHub Enterprise Server resource and re-prompts sign-in on every launch, even though a valid GHES session already exists.

## Best solution

Confirm what `authorization_servers` value the reporter's GHES protected-resource metadata actually returns, then either broaden the matching in `matchesProvider`/`getOrActivateProviderIdForServer` (src/vs/workbench/services/authentication/browser/authenticationService.ts) or have the GHES provider registration in extensions/github-authentication/src/github.ts declare a matching `supportedAuthorizationServers` set (or normalize URL comparisons) so Agent Host's `resolveTokenForResource` in agentHostAuth.ts finds the existing session instead of re-authenticating every launch.

## Evidence

- **strict matching:** src/vs/workbench/services/authentication/browser/authenticationService.ts:417-436 `matchesProvider` requires `provider.authorizationServers` to equal or glob-match the requested authorization server string; the pre-activation filter only uses the declared `authorizationServerGlobs` (which is `"*"` for github-enterprise), so activation happens but the post-activation exact match can still fail.
- **GHES provider declaration:** extensions/github-authentication/src/github.ts:176-179 sets `supportedAuthorizationServers = [vscode.Uri.joinPath(ghesUri, '/login/oauth')]` for the GHES provider — if the enterprise server's real OAuth/OIDC issuer (as returned in the resource's protected-resource metadata) doesn't equal this exact URL, the match in `matchesProvider` fails on every attempt, which would produce exactly the repeated failure/re-auth loop described.
- **package.json globs:** extensions/github-authentication/package.json declares `authorizationServerGlobs: ["*"]` for `github-enterprise`, so the provider is always considered a candidate and activated, but that alone doesn't guarantee the post-activation `authorizationServers` match succeeds.
