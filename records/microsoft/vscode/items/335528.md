# Issue #335528 — Surface MCP authentication problems persistently in the primary UI

[https://github.com/microsoft/vscode/issues/335528](https://github.com/microsoft/vscode/issues/335528)

## Summary

Real, well-scoped gap confirmed in source: today's Customizations UI only shows per-server status badges inline (mcpListWidget.ts) and aggregate section counts are plain item totals (aiCustomizationManagementEditor.ts), with no persistent unhealthy/auth-required indicator at the section or Overview level — the request is legitimate and already correctly labeled `mcp`/`agents-window`.

## Change summary

Add a persistent, proactive health signal (badge/count + durable Authenticate/Reconnect action) for MCP servers needing authentication, visible in Customizations Overview and the MCP Servers row, instead of only a brief post-send toast.

## Best solution

Extend the McpServers section count/badge machinery in aiCustomizationManagementEditor.ts (and mcpListWidget.ts's existing AuthRequired handling) to surface an aggregate unhealthy/auth-required indicator at the section and Overview level that persists until resolved, reusing the already-implemented per-row status/auth action as the recovery entry point.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagementEditor.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts`
- **Validation:** A test/manual check that an MCP server left in AuthRequired state produces a persistent unhealthy indicator on the McpServers section (and/or Overview) that remains until the server authenticates or is disabled, and that triggering Authenticate/Reconnect from that indicator clears it.
- **Behavior:**

  > When one or more configured MCP servers require authentication or are otherwise unhealthy, the Customizations UI shows a persistent indicator (badge/count) on the MCP Servers section and/or Overview — visible before any request is sent — that remains until the server authenticates successfully or is disabled. A reliable Authenticate/Reconnect action is reachable from that indicator. Optionally, sending a request that depends on an unavailable server surfaces a pre-send warning rather than silently continuing.
- **Trace:**

  > mcpListWidget.ts already computes per-row `McpServerStatus.AuthRequired` and exposes a per-row authenticate action (`authenticateMcpServer`, ~line 505-517) and a status badge (`updateStatus`, ~line 452). aiCustomizationManagementEditor.ts's `updateSectionCount` (~line 3025) and the `onDidChangeItemCount` wiring (~line 1408-1411) only track plain total counts, not health state — that's the boundary to extend, without altering the existing per-row status/auth flow. Related but distinct: https://github.com/microsoft/vscode/issues/327640, https://github.com/microsoft/vscode/issues/330837, https://github.com/microsoft/vscode/issues/334271 (broken auth affordance / silent tool loss, not this issue's persistent-visibility ask).
- **Open decisions:**
  - Should the unhealthy signal live on the McpServers section row, the Overview screen, or both?
  - Does an unhealthy count reuse the existing item-count UI element or need a distinct badge treatment (e.g. warning color)?
  - Should a pre-send warning be added when a session's expected tools are unavailable, and if so, should it block or just warn?

## Evidence
