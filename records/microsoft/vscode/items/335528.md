# Issue #335528 — Surface MCP authentication problems persistently in the primary UI

[https://github.com/microsoft/vscode/issues/335528](https://github.com/microsoft/vscode/issues/335528)

## Summary

Keep open: current source provides persistent per-server sign-in actions, but the primary Customizations overview still lacks an aggregate MCP health signal. This team-authored request is broader than the related authentication defects, and no verified fixing commit or eligible canonical covers it.

## Change summary

Make MCP authentication and connection problems persistently discoverable before submission, with affected-server identification and durable recovery actions.

## Best solution

Expose session-relevant MCP health in the Customizations overview and section entry points, leading to named servers and their existing recovery controls. Decide separately whether unavailable expected tools warrant a pre-send warning, without treating intentionally disabled or unstarted servers as authentication failures.

Add focused browser coverage for these state transitions alongside the existing mcpListWidget tests; separately validate any agreed pre-send behavior.
- **Behavior:**

  > Users must be able to discover known MCP authentication and connection problems from the primary Customizations UI without submitting a request or catching a transient notification. The indication identifies affected servers and provides a durable route to authentication or connection recovery. It remains while the enabled server needs attention and clears when recovery succeeds or the server is disabled. Healthy servers must not acquire warning treatment, and status must correspond to the relevant session. Whether to actively discover expired credentials before first use or warn during submission remains a maintainer decision.
- **Trace:**

  > AICustomizationOverviewView in src/vs/sessions/contrib/aiCustomizationTreeView/browser/aiCustomizationOverviewView.ts renders counts and reads the local MCP server array without consuming runtime health. The shared AICustomizationWelcomePage delegates the legacy Overview to PromptLaunchersAICustomizationWelcomePage, whose MCP card is navigation rather than a health summary. McpListWidget already renders persistent AuthRequired sign-in actions and error controls, while AgentHostCustomizationService.getMcpServers exposes session-scoped status and authenticateMcpServer handles known authentication challenges. Source inspection therefore establishes partial recovery UI and missing overview aggregation, but not advance discovery of credential expiry. Preserve existing authentication consent, enablement, harness/session scoping, and tool invocation semantics; do not turn this into a repair of every OAuth failure. https://github.com/microsoft/vscode/issues/337792 covers prompt identification, and https://github.com/microsoft/vscode/issues/339960 covers native authentication failures rather than this complete presentation requirement. Uncertainty starts at proactive discovery and the optional pre-send experience, not at the availability of status for already-reported failures.
- **Open decisions:**
  - Should proactive visibility reflect only known runtime failures, or should opening Customizations initiate connection/authentication checks that can discover expired credentials before first tool use?
  - When expected MCP tools are unavailable, should submission remain unchanged, show a nonblocking warning, or require acknowledgment before proceeding?
