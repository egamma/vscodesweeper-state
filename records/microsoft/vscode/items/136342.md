# Issue #136342 — Support structured "browser" property in package.json

[https://github.com/microsoft/vscode/issues/136342](https://github.com/microsoft/vscode/issues/136342)

## Summary

The requested manifest capability is still missing: current validation rejects object-valued browser fields, and the worker extension host expects a string entry point. Keep this accepted Backlog request open; no verified canonical issue owns the same work.

## Change summary

Allow an extension manifest to combine browser-specific module substitutions with a web-worker entry point through a structured browser field.

## Best solution

Define a compatible manifest contract for structured browser fields, including how the web entry point is distinguished from bundler substitution mappings. Preserve existing string-valued entry points and make validation, host selection, and worker loading agree on the new contract.

## Plan brief

- **Likely files:** `src/vs/platform/extensions/common/extensions.ts`, `src/vs/platform/extensions/common/extensionValidator.ts`, `src/vs/workbench/services/extensions/common/extensionManifestPropertiesService.ts`, `src/vs/workbench/api/worker/extHostExtensionService.ts`
- **Validation:** After agreeing on the manifest contract, add targeted validation and extension-kind tests for string entry points, structured entry points with substitution mappings, and substitution-only objects. Manually load a sample web extension using the agreed structured form and confirm activation succeeds without the browser-type validation error; confirm an existing string-valued web extension still activates.
- **Behavior:**

  > An extension author wants browser-specific dependency substitutions and a web-worker entry point to coexist in the published package.json without build-time manifest rewriting. The proposed form is an object-valued browser field with a main sub-property identifying the entry point. Acceptance must cover successful validation and activation of that form, unchanged handling of existing string-valued browser fields, and explicitly defined behavior for substitution-only objects.
- **Trace:**

  > Current extensionValidator.ts rejects object-valued browser fields, while IExtensionManifest in extensions.ts permits only browser?: string. The worker ExtHostExtensionService._getEntryPoint returns browser directly, and ExtensionManifestPropertiesService.deduceExtensionKind treats its presence as evidence of web capability. These paths establish that the requested capability is absent, but do not settle the public semantics of objects without an entry point or the interaction of a main key with bundler mappings. Preserve string-valued manifests and existing host-selection behavior for those manifests; implementing bundler module substitution inside the extension host is outside the request. The discussion at https://github.com/microsoft/vscode/issues/136342 supplies build-manifest workarounds, not an agreed compatibility contract.
- **Open decisions:**
  - Should the web entry point be identified by browser.main as proposed, or by another manifest representation that avoids ambiguity with bundler substitution keys?
  - Should a substitution-only browser object be accepted without making the extension web-capable, or must every structured browser field include an explicit web entry point?

## Evidence

- **Current validation rejects the requested form:** src/vs/platform/extensions/common/extensionValidator.ts:304–307 explicitly rejects any defined browser field whose type is not string. An object containing module substitutions and a main sub-property therefore still reaches the reported validation error.
- **Entry-point contract remains string-only:** src/vs/platform/extensions/common/extensions.ts:353 declares browser?: string. src/vs/workbench/api/worker/extHostExtensionService.ts:55–57 returns extensionDescription.browser directly from _getEntryPoint; there is no structured-field entry-point extraction.
- **Host selection also depends on browser:** src/vs/workbench/services/extensions/common/extensionManifestPropertiesService.ts:267–277, deduceExtensionKind, uses the truthiness of manifest.browser to classify web-capable extensions. Supporting substitution-only objects requires an explicit contract rather than merely relaxing validation.
- **Discussion and workaround:** In https://github.com/microsoft/vscode/issues/136342, alexdima discusses the conflicting package.json conventions and suggests a separate build manifest or rewriting browser before publishing. These workarounds do not provide the requested single-manifest capability; weinand also notes that webpack supported the structured form before their use of esbuild.
- **Canonical search:** Repository-scoped searches for structured browser and browser-field titles found this request and https://github.com/microsoft/vscode/issues/165162. The latter is closed and concerns acquireWebNodePaths during development builds, not extension-manifest validation or web-worker entry-point selection; it is not a canonical duplicate.
