# Issue #259262 — Show a more prominent call to action for adding a failed command to chat

[https://github.com/microsoft/vscode/issues/259262](https://github.com/microsoft/vscode/issues/259262)

## Summary

Keep open: command-specific attachment is available, but the inspected terminal UI still exposes it through menus rather than a prominent failed-command action. Both listed prerequisites are closed; the remaining work needs a discoverability design that preserves a quiet terminal experience.

## Change summary

Make attaching a failed terminal command and its output to chat easier to discover.

## Best solution

Provide a discoverable, command-specific attachment affordance in the terminal without automatically submitting a prompt or running a fix. Decide its placement and visibility with the terminal/chat owners, preserving existing menus and avoiding distracting chrome around every command.

- **Behavior:**

  > Users should be able to discover how to attach a failed terminal command and its output to chat without first finding a context-menu entry. Invoking the affordance should attach the specific command the user selected, leaving prompt submission and any subsequent execution under user control. Existing attachment menus must remain usable, and the new AI surface must not appear when AI features are disabled. Acceptance includes command identity across multiple terminals, keyboard accessibility, and a terminal presentation that does not obscure output.
- **Trace:**

  > DecorationAddon in src/vs/workbench/contrib/terminal/browser/xterm/decorationAddon.ts renders command-status decorations and opens action menus through _createContextMenu and _getCommandActions. Its _createAttachToChatAction already constructs a command-specific TerminalContext from the terminal resource and command.id, then adds an attachment to the chat widget. TerminalQuickFixContribution in src/vs/workbench/contrib/terminalContrib/quickFix/browser/terminal.quickFix.contribution.ts registers quick-fix actions into the same decoration menu; this is neighboring UX, not proof of a prominent attachment action. Both explicit prerequisites, https://github.com/microsoft/vscode/issues/259260 and https://github.com/microsoft/vscode/issues/259261, are closed. The remaining uncertainty is the new affordance's placement and visibility, not whether command-specific attachment plumbing exists. Preserve existing attachment semantics and do not expand this work into automatic corrections, agent-mode handoff, or continuous terminal-context access.
- **Open decisions:**

  - Should it remain visible after failure or be revealed on hover and keyboard focus, balancing discoverability against terminal clutter?
