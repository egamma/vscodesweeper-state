# Issue #230337 — Support for search engines

[https://github.com/microsoft/vscode/issues/230337](https://github.com/microsoft/vscode/issues/230337)

## Summary

Keep open: extension-defined search modes in both workspace Search and editor Find remain a distinct capability gap. The maintainer explicitly accepted this distinction after reopening, and the request has 35 upvotes and an accepted Backlog milestone.

## Change summary

Allow extensions to add selectable search engines, such as clang AST matching, to workspace Search and editor Find without replacing ordinary text or regex search.

## Best solution

Design a shared extension contract for additional search modes in both built-in search surfaces, leaving language-specific engines in extensions and preserving existing text/regex behavior. Coordinate with the search-provider API work, but retain this issue for mode selection, engine-specific options, and editor Find integration.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.textSearchProvider2.d.ts`, `src/vs/workbench/api/common/extHostSearch.ts`, `src/vs/workbench/contrib/search/browser/searchWidget.ts`, `src/vs/editor/contrib/find/browser/findWidget.ts`, `src/vs/editor/contrib/find/browser/findModel.ts`
- **Validation:** End the plan with a runnable fixture-extension scenario: register a deterministic AST-like engine alongside normal search, select it in workspace Search and editor Find, and verify engine-specific matches in each scope. Verify Ctrl+Shift+F and Ctrl+F focus the corresponding search input without resetting the selected mode, and switching back preserves ordinary text/regex behavior.
- **Behavior:**

  > Extensions should be able to offer an additional search mode in both workspace Search and editor Find, without requiring a separate view or replacing normal text and regex search. The motivating engine accepts clang AST matcher expressions rather than literal text. Ctrl+F and Ctrl+Shift+F should focus the relevant input while retaining its selected engine. Acceptance must demonstrate correct matches in both scopes, switching back to existing search, and a defined way to supply engine-specific options; richer query editing is an optional extension of that goal.
- **Trace:**

  > The current TextSearchProvider2 proposal describes text queries and registers providers by URI scheme; ExtHostSearch.registerTextSearchProvider rejects a second registration for the same scheme. SearchWidget in src/vs/workbench/contrib/search/browser/searchWidget.ts constructs standard find toggles plus notebook-specific filters, while the editor FindWidget and FindModelBoundToEditorModel live in a separate editor contribution. The AITextSearchProvider proposal adds workspace AI results but not a general mode contract covering editor Find. The maintainer accepted the UI-extension distinction at https://github.com/microsoft/vscode/issues/230337#issuecomment-2391738851 after the original duplicate close. Related provider-selection work appears in https://github.com/microsoft/vscode/issues/210692, but does not settle this request's two-surface contract. Preserve ordinary text/regex search and keep clang-specific implementation outside core. Uncertainty starts at the public engine-registration, option, and selection-state contracts; this trace is not a complete implementation design.
- **Open decisions:**
  - Should engine selection be shared between workspace Search and editor Find, or independently retained by each surface, and should it persist across reloads?
  - What engine-specific options and query-editing capabilities should the initial public contract expose: bounded controls in the existing inputs, or also a richer extension-provided query editor?
  - How should an engine's availability be scoped when the active document language or workspace content changes, particularly when an engine supports only one search scope?
