# Issue #343871 — Abandoned extension extraction directories are not recovered by subsequent cleanup

[https://github.com/microsoft/vscode/issues/343871](https://github.com/microsoft/vscode/issues/343871)

## Summary

Keep open: current source confirms that interrupted extraction can leave hidden UUID directories that subsequent extension cleanup never considers. Recovery should reclaim abandoned installation data without interfering with concurrent installations.

## Change summary

Recover abandoned extension extraction directories during subsequent cleanup after an installation process terminates unexpectedly.

## Best solution

Extend native extension-management recovery to reclaim demonstrably abandoned extraction directories on desktop and server installations, while preserving active extractions, installed extensions, and unrelated hidden entries.

Also verify that a concurrent active extraction, installed/profile-referenced extensions, and unrelated hidden entries survive, while existing .vsctmp cleanup still works; repeat the reported isolated desktop and server recovery scenarios.
- **Behavior:**

  > An installation terminated after extraction can leave a hidden UUID directory that survives a later successful installation and repeated cleanup. Subsequent cleanup should eventually reclaim abandoned installation data without requiring manual deletion. Acceptance must cover recovery on desktop and server, preservation of concurrent active extractions and installed extensions, and unchanged handling of unrelated hidden entries.
- **Trace:**

  > In src/vs/platform/extensionManagement/node/extensionManagementService.ts, ExtensionsScanner.extractUserExtension creates .<UUID> directories and removes them on handled errors, but process termination bypasses that cleanup. ExtensionsScanner.cleanUp only recovers temporary deletion directories ending in .vsctmp, while scanExtensionsFromLocation in src/vs/platform/extensionManagement/common/extensionsScannerService.ts deliberately excludes dot-prefixed user-extension directories. This conclusively explains the retention described at https://github.com/microsoft/vscode/issues/343871 without executing the program. The existing tests in src/vs/platform/extensionManagement/test/node/extensionsScannerService.test.ts provide scanner/file-service fixtures, but do not establish recovery behavior for the management-side ExtensionsScanner. The unresolved technical boundary is how abandonment can be established across independent CLI, desktop, and server processes sharing an extensions directory; an in-process activity check alone would not cover that boundary. Preserve normal installation, profile ownership, hidden-directory scanning exclusions, and existing temporary-deletion cleanup.

## Evidence

- **Reported trigger and recovery checks:** https://github.com/microsoft/vscode/issues/343871 describes terminating the installation process immediately after extraction and before metadata writing or rename. The visible follow-up reports retained 131,388-byte directories on Windows Stable/Insiders and WSL Stable/Insiders Server, including after aging the temporary entry by 30 days.
- **Extraction lifetime:** src/vs/platform/extensionManagement/node/extensionManagementService.ts:620-704, ExtensionsScanner.extractUserExtension, creates a fresh .<UUID> directory for each extraction. Its error handler removes that directory only while the process can execute the handler; process termination bypasses it, and a later successful installation uses a different UUID.
- **Cleanup excludes extraction directories:** src/vs/platform/extensionManagement/node/extensionManagementService.ts:562-569 invokes temporary-deletion recovery, stale built-in removal, marked-extension deletion, and size initialization. removeTemporarilyDeletedFolders at lines 1000-1037 only deletes directories ending in .vsctmp; abandoned .<UUID> extraction directories do not match.
- **Extension scanning does not recover them:** src/vs/platform/extensionManagement/common/extensionsScannerService.ts:613-633, scanExtensionsFromLocation, explicitly skips dot-prefixed user-extension directories. Consequently, the extension-scanning cleanup paths do not rediscover these extraction leftovers as installed extensions.
