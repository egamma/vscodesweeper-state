# Issue #109083 — vscode.debug.startDebugging should support named automatic (dynamic) and global (user settings) debug configurations

[https://github.com/microsoft/vscode/issues/109083](https://github.com/microsoft/vscode/issues/109083)

## Summary

A real API gap remains on current main: `vscode.debug.startDebugging` cannot resolve named user, workspace, or dynamic configurations. The issue should remain open under discussion because the public API semantics and dynamic-provider activation model still require design.

## Change summary

Allow extensions to programmatically start named debug configurations from user settings, workspace configuration, and dynamic configuration providers.

## Best solution

Provide a scoped API that can resolve user/workspace configurations and request a named dynamic configuration from an identified debug type without activating unrelated debug extensions. Preserve the existing folder-scoped and direct-configuration behavior.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostDebugService.ts`, `src/vs/workbench/api/browser/mainThreadDebugService.ts`, `src/vs/workbench/contrib/debug/browser/debugService.ts`, `src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts`, `extensions/vscode-api-tests/src/singlefolder-tests/debug.test.ts`
- **Validation:** Extend the debug extension API integration tests to cover starting a named user configuration, a named workspace configuration, and a named dynamic configuration from a selected debug type while verifying unrelated dynamic providers are not activated; run `./scripts/test-integration.sh --grep "vscode.debug.startDebugging"`.
- **Behavior:**

  > An extension can programmatically start a named debug configuration that the user defined in user settings or workspace configuration, not only one in a folder's `.vscode/launch.json`. It can also request a named dynamic configuration through a scope that identifies the relevant debug provider without activating unrelated providers. Ambiguous or missing names produce deterministic errors. Existing folder-scoped lookup and directly supplied `DebugConfiguration` objects remain compatible.
- **Trace:**

  > The extension host forwards only a folder URI and name/configuration through `ExtHostDebugService.startDebugging` to `MainThreadDebugService.$startDebugging`. The main thread calls `ConfigurationManager.getLaunch(folderUri)`, whose implementation returns only folder-backed launches and returns undefined for the user and workspace launch entries created by `initLaunches`; `DebugService.startDebugging` then resolves string names only when that launch exists. Dynamic configurations use the separate internal `ConfigurationManager.getDynamicConfigurationsByType` UI path, which activates one selected debug type and queries its provider, but that scope is absent from the public API. Preserve direct configuration objects, folder-relative variable resolution, and selective extension activation; do not introduce enumeration that eagerly activates every dynamic debug provider. The related https://github.com/microsoft/vscode/issues/77782 is closed and narrower, so it does not absorb this work.
- **Open decisions:**
  - When the folder argument is undefined, should a named lookup search user settings, workspace configuration, or both, and what precedence or ambiguity error should apply when names collide?
  - What public identifier should select a dynamic provider and its context: a debug type, a provider identifier, or another explicit scope?
  - Should the API expose only scoped start-by-name behavior, or also expose scoped configuration discovery comparable to the Run quick pick?

## Evidence

- **current API path:** src/vs/workbench/api/browser/mainThreadDebugService.ts resolves the supplied folder through `ConfigurationManager.getLaunch` and passes that single launch to `DebugService.startDebugging`; an undefined folder therefore produces no launch.
- **static configuration gap:** src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts creates `WorkspaceLaunch` and `UserLaunch` entries, but `getLaunch` only matches launches with a workspace-folder URI. src/vs/workbench/contrib/debug/browser/debugService.ts only resolves a string name when a launch was supplied, so `startDebugging(undefined, name)` cannot reach those entries.
- **dynamic configuration gap:** ConfigurationManager.getDynamicConfigurationsByType in src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts selectively activates and queries a dynamic provider for the UI, but no corresponding extension-host API exposes this path and `startDebugging` does not invoke it for a name.
- **public contract:** src/vscode-dts/vscode.d.ts still documents named lookup specifically against `.vscode/launch.json` in the supplied folder.
- **maintainer direction:** https://github.com/microsoft/vscode/issues/109083#issuecomment-722267045 explicitly says the issue should remain open for global and workspace launch configurations; the discussion also records unresolved performance and provider-selection questions for dynamic configurations.
- **canonical search:** The older https://github.com/microsoft/vscode/issues/77782 is closed and concerns compound configuration behavior rather than the same full API request. Searches found no other open issue owning this work; the younger https://github.com/microsoft/vscode/issues/185408 concerns dynamically created compounds and is also closed.
