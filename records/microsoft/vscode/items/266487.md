# Issue #266487 — Running task terminal left open after extension host reload

[https://github.com/microsoft/vscode/issues/266487](https://github.com/microsoft/vscode/issues/266487)

## Summary

Keep open: current source disposes an extension-host-backed terminal's process proxy without signaling process exit, leaving the task registered as active after its execution disappears. The supplied sample and restart steps are sufficient, and the related closed report does not cover cleanup of interrupted CustomExecution tasks.

## Change summary

Interrupted CustomExecution tasks should stop appearing active after an extension host restart and allow a fresh execution without manual termination.

## Best solution

Complete the lifecycle of CustomExecution tasks whose owning extension host stops, clearing their running state so the next invocation starts normally. Preserve ordinary shell/process tasks that can survive an extension host restart and existing completed-terminal presentation settings.

- **Behavior:**

  > Restarting an extension host while its CustomExecution task runs interrupts that execution, but must not leave the task marked as running. After the extension reactivates, invoking the task once should start a fresh execution without first terminating an orphaned instance. The previous terminal may retain output according to existing presentation settings, but must no longer display active task status. Ordinary shell/process tasks that survive an extension host restart must remain unaffected.
- **Trace:**

  > CustomExecution launch configuration in src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts constructs TerminalProcessExtHostProxy. MainThreadTerminalService._onRequestStartExtensionTerminal owns that proxy through _terminalProcessProxies and a DisposableStore. ExtensionHostManager.dispose disposes the main-thread service when the host stops, which disposes the proxy's emitters without firing onProcessExit; only TerminalProcessExtHostProxy.emitExit currently sends that notification. Consequently the terminal.onExit completion path in TerminalTaskSystem never clears the active task, while the replacement ExtHostTask starts with an empty execution map. AbstractTaskService._handleInstancePolicy then sees the stale workbench entry and offers termination. Keep the boundary to lifecycle completion of terminals backed by the stopped host: do not add execution restoration, alter native task persistence, or change instance-limit policy. The existing MainThreadTerminalService tests already create extension-backed terminals and exercise process readiness, explicit exit, and disposal. The related decision at https://github.com/microsoft/vscode/issues/248736 concerns persistent process tracking, not this cleanup contract.
