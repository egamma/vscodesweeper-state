# Issue #158797 — Merge Editor: Use existing merge conflict theme colors

[https://github.com/microsoft/vscode/issues/158797](https://github.com/microsoft/vscode/issues/158797)

## Summary

Keep this open for a merge-editor design decision: current source partially reuses inline incoming/current colors, but only through optional simplified input decorations, not the ordinary diff or result presentation. The earlier fixing PR predates the explicit reopening, and no verified older canonical owns the remaining work.

## Change summary

Reuse familiar inline incoming/current conflict colors in the merge editor while keeping unresolved and handled states distinguishable.

## Best solution

Agree on consistent color semantics across inline conflicts, merge inputs, and the result, then complete the merge-editor presentation accordingly. Resolve whether result colors communicate accepted-side provenance or only unresolved status, preserving readable word diffs and theme control.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mergeEditor/browser/view/colors.ts`, `src/vs/workbench/contrib/mergeEditor/browser/view/editors/codeEditorView.ts`, `src/vs/workbench/contrib/mergeEditor/browser/view/editors/inputCodeEditorView.ts`, `src/vs/workbench/contrib/mergeEditor/browser/view/editors/resultCodeEditorView.ts`, `src/vs/workbench/contrib/mergeEditor/browser/view/media/mergeEditor.css`
- **Validation:** After agreeing on semantics, open the same conflict inline and in the merge editor with visibly distinct current/incoming theme colors. Check unresolved, accept-current, accept-incoming, accept-both, and manually edited result states in light, dark, and high-contrast themes; repeat with simplified decorations enabled and with an input compared against base. Confirm the agreed color meanings, readable word diffs, and independently identifiable unresolved status.
- **Behavior:**

  > The merge editor should make the transition from inline conflict resolution easier by preserving recognizable current/incoming color meanings. Unresolved status must remain distinguishable from input identity and accepted resolution. Acceptance should cover both input panes and the result before and after accepting either or both sides, including theme customizations and high-contrast themes. The thread has not settled whether handled result content retains source-side colors or loses conflict coloring.
- **Trace:**

  > colors.ts already derives mergeEditor.conflict.input1.background and mergeEditor.conflict.input2.background from inline header colors. CodeEditorView reads mergeEditor.useSimplifiedDecorations with a false fallback, and InputCodeEditorView uses those backgrounds only for simplified unhandled blocks outside base-comparison mode. Ordinary input diffs and ResultCodeEditorView share generic line/word background classes in mergeEditor.css; result decorations do not identify an accepted input. The optional input-color implementation is https://github.com/microsoft/vscode/commit/981234442060152423e9f360b6d9f7953ec79478, which references a separate issue and does not settle this request. Preserve merge-resolution logic, focus/handled indicators, and word-diff readability; the uncertainty is the intended visual meaning and default scope, not the underlying merge algorithm. The maintainer's custom-theme-only background direction is recorded at https://github.com/microsoft/vscode/issues/158797#issuecomment-1385072323.
- **Open decisions:**
  - Should incoming/current identity colors appear in the normal merge-editor presentation by default, or remain confined to an optional simplified presentation?
  - After handling a conflict, should result coloring disappear or communicate accepted-side provenance, and what should users see for accept-both and manually edited resolutions?
