# Issue #244166 — MCP: support server sessions connections per-edit session

[https://github.com/microsoft/vscode/issues/244166](https://github.com/microsoft/vscode/issues/244166)

## Summary

Keep open: the local-chat MCP path still shares a server connection across conversations. Conversation metadata supports correlation, but does not deliver the requested separate connection and execution sandbox for each chat.

## Change summary

Support distinct MCP server connections per chat session so stateful servers can allocate a separate execution sandbox to each conversation.

## Best solution

Provide chat-scoped MCP connection ownership and lifecycle for the local-chat path, allowing concurrent conversations to use independent server sessions. Preserve existing discovery, trust, and configuration behavior while defining how connections survive chat switching and restoration.

Exercise switching between chats and verify the agreed restoration and disposal behavior; cover the ownership contract in the MCP service tests.
- **Behavior:**

  > A stateful MCP server should be able to treat each chat as an independent MCP session and allocate a separate execution sandbox. Calls within one chat must remain associated with that chat's session, while concurrent chats must not share its connection or sandbox state. Acceptance should use a stateful server reporting instance identifiers and verify both within-chat continuity and cross-chat separation. Connection lifetime across chat switching and restoration needs an explicit product contract.
- **Trace:**

  > McpService.updateCollectedServers in src/vs/workbench/contrib/mcp/common/mcpService.ts creates and retains McpServer objects by collection and server-definition identity, not chat identity. McpServer in src/vs/workbench/contrib/mcp/common/mcpServer.ts owns a single _connection, and start reuses it; McpTool._callWithProgress obtains the handler through that server and supplies conversation identity only as request metadata. This establishes the remaining gap in the local-chat path without executing the application. The maintainer explicitly described one stdio connection per chat at https://github.com/microsoft/vscode-copilot-issues/issues/179#issuecomment-3186763708. Preserve discovery, trust, configuration, and conversation metadata; do not mistake agent-host session-specific configuration for coverage of the local-chat path. The trace has not enumerated all prompt, resource, sampling, and connection-management consumers, so the lifecycle change is not yet bounded for implementation.
- **Open decisions:**
  - When a chat is closed and later restored, should it reconnect to its previous server-side session and sandbox where supported, or start a fresh one?
