# Issue #193970 — Adjust save location of local history

[https://github.com/microsoft/vscode/issues/193970](https://github.com/microsoft/vscode/issues/193970)

## Summary

Keep this accepted Backlog request open: current source still selects a fixed remote history directory, and no local-history-specific location setting covers persistence across devcontainer rebuilds. The related open workspace-storage request is newer and does not meet the duplicate bar for this re-reviewed item.

## Change summary

Allow configuring the built-in Local History storage location so history can survive devcontainer rebuilds or live alongside a workspace.

## Best solution

Provide an opt-in history location that can reside on persistent workspace storage while preserving the existing remote-local default. Settle path resolution and existing-history migration semantics before implementation; shared multi-user history should not be assumed to follow automatically.

## Plan brief

- **Likely files:** `src/vs/workbench/services/workingCopy/common/workingCopyHistoryService.ts`, `src/vs/workbench/browser/workbench.contribution.ts`, `src/vs/workbench/services/workingCopy/test/electron-browser/workingCopyHistoryService.test.ts`
- **Validation:** Extend the WorkingCopyHistoryService suite to verify default storage remains unchanged, configured storage receives entries, and a newly created service can read retained entries. Manually save several revisions in a devcontainer with the chosen history directory on a persistent mount, rebuild the container, and verify Timeline can list and restore those revisions.
- **Behavior:**

  > Built-in Local History currently disappears when its storage is discarded during a devcontainer rebuild. Users should be able to select persistent storage, including a workspace-adjacent location, and recover saved revisions after reconnecting to the rebuilt container. Without an override, existing local and remote storage behavior must remain unchanged. Acceptance must cover retained history after service recreation and an actual container rebuild; concurrent shared history is a separate requirement unless explicitly accepted.
- **Trace:**

  > WorkingCopyHistoryService.resolveLocalHistoryHome() in src/vs/workbench/services/workingCopy/common/workingCopyHistoryService.ts resolves one history root from the remote environment, falling back to the local environment. AbstractNativeEnvironmentService.localHistoryHome in src/vs/platform/environment/common/environmentService.ts derives that root from appSettingsHome/History. The local-history settings in src/vs/workbench/browser/workbench.contribution.ts control retention and inclusion, not location; server-wide data relocation exists but is not an independent history override. The existing WorkingCopyHistoryService test suite provides entry persistence and retrieval coverage to extend after the product contract is settled. Preserve default remote-local storage and avoid adding automatic transfers or multi-user guarantees without approval. https://github.com/microsoft/vscode/issues/146716#issuecomment-1088283798 records remote-path and transfer-cost concerns; https://github.com/microsoft/vscode/issues/251570 is related workspace-portability work, not a duplicate target for this older report.
- **Open decisions:**
  - Should an override always resolve on the edited file's host, with relative paths anchored to each workspace folder, or also allow client-local storage for remote files?
  - When the storage location changes, should existing history be migrated or remain accessible in its original location while new entries use the new location?
