# Issue #218102 — Profile/metadata feedback on testing

[https://github.com/microsoft/vscode/issues/218102](https://github.com/microsoft/vscode/issues/218102)

## Summary

Keep open: profiles address test applicability, but current request reconstruction still cannot preserve arbitrary per-run launch context. This team-authored discussion has no verified fixing commit or qualifying older canonical; the newer custom-session rerun request reinforces the remaining gap.

## Change summary

Allow custom test sessions to retain the execution context needed for faithful reruns and debug restarts, without requiring an impractical profile workflow.

## Best solution

Settle a supported testing API contract for replaying extension-created runs with their original execution parameters, accounting for persisted results and existing profile behavior. Coordinate with https://github.com/microsoft/vscode/issues/297962 while preserving this older discussion's profile UX requirements.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTesting.ts`, `src/vs/workbench/contrib/testing/browser/testExplorerActions.ts`, `src/vs/workbench/contrib/debug/browser/debugService.ts`
- **Validation:** Use a test extension that starts a custom session with a non-default launch argument and a runtime test filter. Verify that Rerun Last Run and correlated debug Restart preserve both parameters and record results in a new run, without broadening execution to all tests. Verify ordinary profile runs remain unchanged, and test reload behavior against the persistence contract chosen during planning.
- **Behavior:**

  > Extension-created test sessions can depend on launch arguments or runtime filters not represented by their discovered TestItems. Replaying such a session must retain its execution meaning rather than silently using default parameters or running all tests. Acceptance should cover both Rerun Last Run and correlated debug Restart, including result recording and unchanged ordinary profile behavior. Behavior after window reload must follow an explicitly agreed persistence contract.
- **Trace:**

  > TestRunRequest in src/vscode-dts/vscode.d.ts has no custom replay payload. TestRunCoordinator.createTestRun in src/vs/workbench/api/common/extHostTesting.ts serializes recognized fields, and ExtHostTesting.runControllerTestRequest constructs a new request before invoking the selected profile. RunOrDebugLastRun.run in src/vs/workbench/contrib/testing/browser/testExplorerActions.ts and DebugService.restartSession in src/vs/workbench/contrib/debug/browser/debugService.ts replay stored test requests rather than the extension's original launch operation. Existing profile tags and defaults solve applicability and selection, not arbitrary per-run context. The uncertainty is the public replay contract, not an identified implementation defect in those existing contracts. Preserve current behavior for normal profiles and debug sessions without testRun. Coordinate the overlapping demand in https://github.com/microsoft/vscode/issues/297962 and the persistence concerns documented in https://github.com/microsoft/vscode/issues/144169#issuecomment-1058247499.
- **Open decisions:**
  - Should custom-session replay be represented through profiles alone, or should the testing API support per-run execution context for sessions that cannot reasonably be modeled as profiles?
  - If per-run context is supported, must it survive window reload, and what should rerun actions do when the original context cannot be restored?
