# Issue #114047 — Unexpected editor.selection in onDidChangeActiveTextEditor callback

[https://github.com/microsoft/vscode/issues/114047](https://github.com/microsoft/vscode/issues/114047)

## Summary

The confirmed API timing gap remains worth tracking: extensions receive `onDidChangeActiveTextEditor` before the workbench restores the editor selection, so the callback can observe transient state. The Backlog milestone does not block reassessment, but there is no evidence of a fix, canonical open duplicate, or established reason to close.

## Change summary

Ensure restored selection and visible-range state is available when `onDidChangeActiveTextEditor` fires after switching between previously opened files.

## Best solution

Define and implement consistent activation semantics across editor-core and the extension-host editor bridge so the active-editor notification exposes restored view state, while preserving subsequent selection and visible-range events for genuine changes.

## Plan brief

- **Likely files:** `src/vs/workbench/api/browser/mainThreadEditors.ts`, `src/vs/workbench/api/common/extHostTextEditors.ts`, `src/vs/workbench/browser/parts/editor/textEditor.ts`, `src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts`
- **Validation:** Add an extension-host API integration test that switches back to a previously opened text editor with a nonzero saved selection and asserts that the first `onDidChangeActiveTextEditor` callback observes that restored selection; include the top-of-file visible-range case described in the thread.
- **Behavior:**

  > When an extension receives `window.onDidChangeActiveTextEditor` after the user returns to a previously opened file, that editor's selection and visible ranges should already represent the restored view state. The callback must not expose a transient 0:0 selection that changes immediately afterward solely because restoration completed. Opening a genuinely new file at 0:0 and later genuine selection or scrolling changes must retain their existing event behavior.
- **Trace:**

  > The confirmed ordering described in https://github.com/microsoft/vscode/issues/114047 is that a reused editor instance first changes model, synchronizes a new API editor, and only then restores selection in the following statement. The relevant boundary spans workbench text-editor model/view-state restoration and the main-thread/ext-host editor synchronization path, likely involving src/vs/workbench/browser/parts/editor/textEditor.ts, src/vs/workbench/api/browser/mainThreadEditors.ts, and src/vs/workbench/api/common/extHostTextEditors.ts. The visible-range report shows that relying on a later property-specific event is insufficient when restored state equals the temporary/default state and no event is emitted. Do not suppress genuine selection or visible-range changes, and do not alter the behavior for newly opened files whose correct initial position is 0:0.
- **Open decisions:**
  - Should active-editor publication be delayed until all restored view state is applied, or should editor-core provide an atomic model-and-view-state operation?
  - Which properties are guaranteed coherent at `onDidChangeActiveTextEditor` time: selection only, or selection and visible ranges together?
  - How should event ordering and compatibility be preserved for extensions that currently observe the transient selection event?

## Evidence

- **confirmed reproduction:** A VS Code contributor confirmed the report in https://github.com/microsoft/vscode/issues/114047#issuecomment-757678181 and identified the ordering: the shared editor receives a new model, the API synchronizes before a selection exists, and selection restoration occurs in the next statement.
- **distinct API gap:** The report demonstrates that switching tabs yields selection 0:0 during `onDidChangeActiveTextEditor`, followed immediately by the restored selection and a selection event; switching between already-visible split editors exposes the restored selection immediately.
- **additional affected state:** A later comment reports the same activation-order problem for `visibleRanges`, including a case where no visible-range event follows because the restored range remains at the top of the file.
