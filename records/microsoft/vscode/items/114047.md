# Issue #114047 — Unexpected editor.selection in onDidChangeActiveTextEditor callback

[https://github.com/microsoft/vscode/issues/114047](https://github.com/microsoft/vscode/issues/114047)

## Summary

The extension API still exposes the newly active editor before its saved selection and view state are restored. This remains the canonical, correctly routed Backlog request for a coherent active-editor event snapshot.

## Change summary

Make `onDidChangeActiveTextEditor` expose the restored selection immediately when switching back to a previously opened file.

## Best solution

Ensure that an extension observing `onDidChangeActiveTextEditor` receives a coherent editor snapshot containing the restored selection, without relying on a timeout or an optional later selection event. The editor and extension-API owners should also settle whether the same guarantee covers restored visible ranges.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/editor/textResourceEditor.ts`, `src/vs/workbench/api/browser/mainThreadDocumentsAndEditors.ts`, `src/vs/workbench/api/browser/mainThreadEditor.ts`, `src/vs/workbench/api/test/browser/mainThreadDocumentsAndEditors.test.ts`
- **Validation:** Add an extension-API integration test that switches back to an editor with a saved nonzero selection and asserts that the selection observed synchronously inside `onDidChangeActiveTextEditor` is already restored and remains unchanged after the event turn.
- **Behavior:**

  > When a user switches to a previously opened text editor, `onDidChangeActiveTextEditor` must expose that editor's restored selection immediately. The value observed synchronously in the callback must match the value after restoration completes, without an extension using a timeout. Opening a genuinely new file at the start of the document must continue to report `(0,0)`, and later user-driven selection changes must continue producing selection-change events.
- **Trace:**

  > The issue was reproduced by a VS Code contributor at https://github.com/microsoft/vscode/issues/114047#issuecomment-757695664. On current main, `AbstractTextResourceEditor.setInput` in src/vs/workbench/browser/parts/editor/textResourceEditor.ts sets the model before restoring view state and applying editor options. `MainThreadDocumentAndEditorStateComputer` in src/vs/workbench/api/browser/mainThreadDocumentsAndEditors.ts listens synchronously to `onDidChangeModel`, publishes the replacement API editor, and the extension host fires the active-editor event from that delta. Selection changes are synchronized separately by `MainThreadTextEditor` in src/vs/workbench/api/browser/mainThreadEditor.ts. Preserve ordinary model-change, focus, and user-selection event behavior; the uncertainty starts at whether atomic activation should include visible ranges as well as selection.
- **Open decisions:**
  - Should the active-editor event guarantee that both restored selection and restored visible ranges are current, or is the public guarantee limited to selection?
  - When restoration changes the cursor from the model's initial position, should extensions still receive a subsequent `onDidChangeTextEditorSelection` event after the coherent active-editor event?

## Evidence

- **confirmed behavior:** A VS Code contributor reproduced the ordering problem and explained that changing the editor model synchronizes a new API editor before the selection is restored: https://github.com/microsoft/vscode/issues/114047#issuecomment-757695664
