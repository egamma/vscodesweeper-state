# Issue #316266 — MCP stdio servers pointing to a batch file on Windows cause two issues

[https://github.com/microsoft/vscode/issues/316266](https://github.com/microsoft/vscode/issues/316266)

## Summary

Both concerns remain actionable: current main launches Windows batch-based MCP servers without windowsHide, and disposing their shutdown handler cancels pending termination without cleaning up the process tree. The reporter's proposed fix is not present in the inspected source, and the linked external workaround does not resolve VS Code's lifecycle gap.

## Change summary

Prevent visible console windows and surviving descendant processes when Windows batch-based MCP stdio servers start and stop.

## Best solution

Make the extension-host MCP launcher start batch servers without a visible console and ensure their owned process trees are cleaned up during stop and disposal. Validate Windows wrapper-exit behavior before settling the lifecycle design, while preserving graceful MCP shutdown and command escaping.

- **Behavior:**

  > Starting a Windows stdio MCP server through a batch launcher must not display a separate console window. Stopping or disposing its connection must not leave server descendants accumulating across repeated starts and stops, including when the wrapper exits before the server. Normal stop must preserve the existing opportunity for graceful MCP shutdown. Acceptance requires Windows checks covering console visibility and descendant PIDs, plus regression coverage for disposal and early wrapper exit.
- **Trace:**

  > NodeExtHostMpcService.startNodeMpc in src/vs/workbench/api/node/extHostMcpNode.ts uses formatSubprocessArguments to select shell: true for resolved Windows batch scripts, but its spawn options omit windowsHide. McpStdioStateHandler in src/vs/workbench/contrib/mcp/node/mcpStdioStateHandler.ts already escalates to killTree, whose Windows implementation in src/vs/base/node/processes.ts uses taskkill /T /F. The direct-child exit callback deletes and disposes the handler, and dispose cancels escalation without terminating descendants. The unresolved technical boundary is how to retain reliable ownership of descendants when the wrapper exits before tree termination; taskkill against a departed wrapper cannot be assumed sufficient. Preserve existing command escaping and graceful shutdown, and avoid unrelated changes to other killTree consumers. The proposed commit https://github.com/microsoft/vscode/commit/2101a6af66b16196e513e8910ec95dece0ca6f37 is a lead, not a verified solution; https://github.com/conda-incubator/conda-meta-mcp/pull/217 is server-specific mitigation only.

## Evidence

- **Current launch path:** In src/vs/workbench/api/node/extHostMcpNode.ts, formatSubprocessArguments resolves .bat/.cmd commands and returns shell: true on Windows. NodeExtHostMpcService.startNodeMpc passes stdio, cwd, env and shell to spawn, but no windowsHide option. This matches the reported batch-launch trigger; the visible-window outcome was independently confirmed in the supplied discussion, not executed during this review.
- **Current cleanup defect:** src/vs/workbench/contrib/mcp/node/mcpStdioStateHandler.ts schedules termination after stdin closure, skips polite tree termination on Windows, and eventually calls killTree(pid, true). However, dispose() only cancels the timer. In extHostMcpNode.ts, the direct child's exit invokes nodeServers.deleteAndDispose(id), so a wrapper exiting before escalation cancels descendant cleanup; extension-host service disposal likewise disposes handlers without initiating termination.
- **Existing tree termination is partial coverage:** src/vs/base/node/processes.ts implements Windows killTree through taskkill.exe /T, adding /F for forceful termination. Thus the report's claim that shutdown always kills only the direct child is too broad: forceful escalation already targets the tree, but disposal and early wrapper exit can bypass it.
- **Confirmed report and unlanded candidate:** The supplied first comment confirms reproduction on Windows with a .bat-based MCP server. The reporter's https://github.com/microsoft/vscode/commit/2101a6af66b16196e513e8910ec95dece0ca6f37 proposes windowsHide and lifecycle changes and references this issue, but those changes are absent from current main. The commit-to-PR lookup returned no associated PR, and an open-PR search for 316266 returned none.
- **Neighboring fix does not cover this report:** https://github.com/microsoft/vscode/commit/e4a4712e4277b8d8420ce6fb7401fcfd686c383a changes Windows shell argument quoting in formatSubprocessArguments and adds escaping tests. Its diff changes neither console visibility nor process-tree shutdown, so it is not a fixing commit for this issue.
- **External mitigation only:** https://github.com/conda-incubator/conda-meta-mcp/pull/217 merged a server-side parent-death watchdog and explicitly describes it as a defensive workaround for host/proxy lifecycle gaps. It protects that server, not arbitrary batch-based MCP servers launched by VS Code.
