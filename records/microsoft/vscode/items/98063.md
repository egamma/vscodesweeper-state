# Issue #98063 — Add an option to save files atomically

[https://github.com/microsoft/vscode/issues/98063](https://github.com/microsoft/vscode/issues/98063)

## Summary

Keep open: atomic-write infrastructure exists, but ordinary editor saves still do not request it and no user-facing atomic-save option covers this request. The maintainer's reconsideration and subsequent reports support retaining this accepted Backlog work.

## Change summary

Provide an atomic-save option that writes replacement content to a temporary file before replacing the destination, avoiding exposure of truncated or partially written files.

## Best solution

Define and deliver an opt-in atomic-save contract for ordinary editor files using the existing file-service capabilities. Settle provider coverage and compatibility with links, permissions, file watchers, and large remote writes before implementation; copying temporary content back into the original file does not satisfy atomic replacement.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `src/vs/workbench/services/textfile/common/textFileEditorModel.ts`, `src/vs/workbench/services/textfile/browser/textFileService.ts`, `src/vs/platform/files/common/fileService.ts`, `src/vs/platform/files/common/files.ts`, `src/vs/platform/files/node/diskFileSystemProvider.ts`
- **Validation:** Extend src/vs/platform/files/test/node/diskFileService.integrationTest.ts and the text-file save tests to verify the chosen option reaches ordinary saves, failed temporary writes leave original bytes intact, successful replacement exposes complete new content, and disabled behavior remains unchanged. Include large-file saves and explicit checks for the agreed symlink, hard-link, permissions, and unsupported-provider behavior.
- **Behavior:**

  > Users can opt into saving ordinary editor files without exposing an empty or partially written destination during replacement. A failure before replacement leaves the existing file intact and reports the save failure. Successful saves expose the complete replacement content; writing temporary content back into the existing inode does not fulfill this requirement. Acceptance must cover explicit and automatic saves, large files, and the agreed compatibility behavior for links and providers. Atomic replacement must not be described as a guarantee against every power-loss scenario.
- **Trace:**

  > TextFileEditorModel passes a snapshot and save metadata to TextFileService.write without an atomic option; that method forwards to FileService.writeFile. FileService already supports requested or provider-enforced atomic writes, and DiskFileSystemProvider.doWriteFileAtomic writes a temporary sibling then renames it over the destination. FileUserDataProvider enables this for selected profile resources, but ordinary files have no equivalent user-facing option. DiskFileSystemProvider.canWriteFileAtomic currently declines symbolic links and falls back to direct writing, while FileService forces atomic writes through the unbuffered provider path, making large-file memory behavior relevant. https://github.com/microsoft/vscode/issues/98063 records both remote-write concerns and the requirement to preserve the old inode for running scripts; https://github.com/microsoft/vscode/issues/195539 illustrates user-data link compatibility concerns. The unresolved boundary is the promised behavior across links, unsupported providers, and large remote saves; preserve encoding, conflict detection, and existing save semantics outside the chosen atomic mode.
- **Open decisions:**
  - Should the option cover every eligible ordinary file save, or only large streamed saves as discussed by the maintainer?
  - When atomic replacement is unavailable or incompatible with a symbolic link, hard link, or required file metadata, should saving fail explicitly or fall back to an in-place write?
  - Should the initial atomic-save contract include remote file providers, or be explicitly limited to supported local filesystems?
