# Issue #231446 — Allow terminal links to be opened in a web browser

[https://github.com/microsoft/vscode/issues/231446](https://github.com/microsoft/vscode/issues/231446)

## Summary

Keep open: current terminal link handling still opens existing HTML files in the editor, with no browser-opening alternative. The maintainer's preferred direction is an explicit link action rather than a file-extension mapping setting.

## Change summary

Allow users to open terminal file links, including generated HTML reports and file:// URLs, in a web browser instead of the editor.

## Best solution

Provide an explicit browser-opening action for eligible terminal file links, following the maintainer's preference for a link-specific context menu. Preserve ordinary editor-opening behavior and establish what the action supports in remote terminals.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/terminalContrib/links/browser/terminalLinkManager.ts`, `src/vs/workbench/contrib/terminalContrib/links/browser/terminalLinkOpeners.ts`, `src/vs/workbench/contrib/terminalContrib/links/browser/terminal.links.contribution.ts`, `src/vs/workbench/contrib/terminalContrib/links/test/browser/terminalLinkManager.test.ts`, `src/vs/workbench/contrib/terminalContrib/links/test/browser/terminalLinkOpeners.test.ts`
- **Validation:** Extend terminal link manager/opener tests to exercise the chosen explicit browser action for an existing local index.html, while confirming ordinary file activation still opens the editor. Manually verify both a relative HTML path and its file:// URL in terminal output, including the agreed remote-terminal behavior.
- **Behavior:**

  > Users need an explicit way to open an existing generated HTML file linked in terminal output in a browser, without copying its path or changing the producing program. Cover both detected filesystem paths and file:// URLs. Ordinary file activation should continue opening the editor. Acceptance should verify the alternate action, unchanged default activation, and the agreed behavior for remote files.
- **Trace:**

  > TerminalUriLinkDetector resolves file:// links and classifies them with getTerminalLinkType; TerminalLinkManager dispatches LocalFile links to TerminalLocalFileLinkOpener.open, which opens an editor. OSC 8 hyperlinks also reach TerminalUrlLinkOpener._openFileSchemeLink, which delegates existing files to the same file opener, so the historical hyperlink workaround does not satisfy the current request. The inspected commands and terminal settings expose no alternate browser-opening choice. The maintainer prefers a link-specific context-menu action; https://github.com/microsoft/vscode/issues/216853 tracks related copy-link interaction work but is not a duplicate. https://github.com/microsoft/vscode/issues/301517 was explicitly consolidated into this report. Preserve existing editor selections, folder opening, and normal URL handling; uncertainty remains around the supported browser destination and remote-file scope.
- **Open decisions:**
  - Should the explicit action guarantee opening in the external system browser, or may it use VS Code's integrated browser?
  - Should browser opening initially be available only for local files, or also for remote terminal files, and what user-visible behavior should remote files receive?

## Evidence

- **Current file-link behavior:** src/vs/workbench/contrib/terminalContrib/links/browser/terminalUriLinkDetector.ts classifies resolved file:// URLs through getTerminalLinkType. TerminalLinkManager maps LocalFile to TerminalLocalFileLinkOpener, whose open method calls IEditorService.openEditor. Thus the reported existing index.html file still takes the editor path.
- **Existing capabilities do not cover the request:** The terminal link commands in src/vs/workbench/contrib/terminalContrib/links/common/terminal.links.ts provide detected, word, file and web link opening, not an alternate browser action. terminal.integrated.enableFileLinks controls detection and terminal.integrated.allowedLinkSchemes controls scheme permission; neither selects a browser for file links.
- **Hyperlink workaround is insufficient:** The December 2024 comment describes OSC 8 file:// hyperlinks opening externally. Current TerminalLinkManager sends those hyperlinks to TerminalUrlLinkOpener, whose _openFileSchemeLink now delegates existing files to the local file opener. External opening is a fallback when file resolution fails, not a browser choice for an existing generated HTML file.
- **Maintainer direction and related context-menu issue:** Tyriar's December 11, 2024 comment on https://github.com/microsoft/vscode/issues/231446 prefers an open-in-browser option in a link-specific context menu over an extension-to-opener mapping setting. https://github.com/microsoft/vscode/issues/216853 is verified open and older, but requests copying hyperlinks; it does not own the same reporter-observable capability and is not a duplicate canonical.
- **Recent duplicate confirms ownership:** https://github.com/microsoft/vscode/issues/301517 reports the same file:// HTML-report behavior and was closed as a duplicate of this issue by a maintainer on October 8, 2026: https://github.com/microsoft/vscode/issues/301517#issuecomment-6067241885. This issue remains the canonical report.
- **Canonical search:** Open-issue searches for terminal browser opening and terminal link context menus found no older issue owning the same request. https://github.com/microsoft/vscode/issues/109277 is open but concerns extension-provided URL openers, not a browser alternative for terminal file links.
