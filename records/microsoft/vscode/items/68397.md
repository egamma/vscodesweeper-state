# Issue #68397 — More flexible input variables: Multiple values & labels

[https://github.com/microsoft/vscode/issues/68397](https://github.com/microsoft/vscode/issues/68397)

## Summary

Labels are supported today, but a single selection still cannot supply multiple named values as requested. Keep this accepted Backlog request open; the remaining work needs a compatible variable-reference contract, not another label-display change.

## Change summary

Allow one labeled task input selection to provide several named values, such as an image tag and build context.

## Best solution

Support coordinated named string values from one input selection in the shared configuration resolver, preserving existing scalar inputs and literal input IDs. Settle the property-reference syntax and compatibility behavior before implementation.

- **Behavior:**

  > One labeled input selection should supply multiple named string values to the same task, allowing the Docker example to obtain both its image tag and build context without independent choices. Selecting a different option should change both outputs consistently, and the user should be prompted once for the shared selection. Existing string options and labeled scalar options must continue working. Acceptance includes successful resolution of both outputs, preserved cancellation semantics, and compatibility with existing input IDs.
- **Trace:**

  > PickStringInputInfo and inputsSchema currently restrict each option value to a string; showUserInput in browser/baseConfigurationResolverService.ts also enforces that restriction at runtime. resolveWithInteraction passes the full input argument to showUserInput, whose exact ID lookup treats image.tag and image.context as independent IDs rather than fields of image. parseConfigurationVariable in src/vs/platform/configuration/common/configurationVariables.ts does not interpret dots, and ConfigurationResolverExpression stores string-valued resolutions keyed by complete variable references. The trace establishes the missing capability, but the public syntax and precedence for literal dotted IDs remain unsettled. Preserve existing scalar input behavior and the shared resolver's other consumers; variable substitution inside input definitions, tracked at https://github.com/microsoft/vscode/issues/64358, is separate work.
- **Open decisions:**
  - Should named outputs use the proposed `${input:image.tag}` syntax, and if so what takes precedence when a literal input ID named `image.tag` also exists, or should property references use a distinct syntax?

## Evidence

- **Existing capability covers labels only:** src/vs/workbench/services/configurationResolver/common/configurationResolverSchema.ts permits pickString options as strings or objects with a string value and optional label. In browser/baseConfigurationResolverService.ts:306–314, showUserInput displays labeled options as `${label}: ${value}`; object-valued bundles remain unsupported.
- **Remaining multi-value gap:** src/vs/workbench/services/configurationResolver/common/configurationResolver.ts defines PickStringInputInfo.options with scalar string values. browser/baseConfigurationResolverService.ts:293–296 rejects non-string option values, and :262 matches the entire variable argument against an input ID. Thus the report's `${input:image.tag}` does not access the tag property of input image.
