# Issue #153657 — Treat numpad-enter and enter keys as different

[https://github.com/microsoft/vscode/issues/153657](https://github.com/microsoft/vscode/issues/153657)

## Summary

Independent bindings for numpad Enter and main Enter remain unsupported in the current keyboard mappers. Keep this accepted Backlog request open; the older modifier-key request discusses numpad Enter, but its primary scope does not establish ownership of this separate non-modifier capability.

## Change summary

Allow numpad Enter and main Enter to invoke different commands through VS Code keybindings.

## Best solution

Support independently assignable Enter keys across supported platforms while preserving existing Enter behavior for users who have not configured distinct bindings. Settle compatibility and binding semantics before changing the platform keyboard mappers.

- **Validation:** Add targeted keyboard-mapper tests for Enter and NumpadEnter events with independently configured commands, including modifier combinations and existing ordinary Enter bindings. Verify on Windows, macOS, and Linux that numpad Enter can execute a notebook cell without main Enter invoking that command, and that uncustomized Enter behavior remains unchanged.
- **Behavior:**

  > Users cannot currently assign different commands to numpad Enter and main Enter. The goal is to make those keys independently bindable across supported platforms, including modified combinations. A representative acceptance check binds notebook execution to numpad Enter while main Enter retains ordinary editing behavior. Existing configurations without distinct bindings must retain their current behavior; the interaction between generic Enter bindings and explicit physical-key bindings requires a defined contract.
- **Trace:**

  > KeybindingParser in src/vs/base/common/keybindingParser.ts already recognizes bracketed scan codes, so syntax recognition alone does not deliver this request. MacLinuxKeyboardMapper.resolveKeyboardEvent explicitly normalizes NumpadEnter to Enter, and keyCodeChordToScanCodeChord deliberately avoids double Enter bindings. WindowsKeyboardMapper resolves events and scan-code chords through KeyCode.Enter, whose shared mapping is defined in src/vs/base/common/keyCodes.ts; FallbackKeyboardMapper likewise uses key codes. The existing macOS/Linux mapper test for https://github.com/microsoft/vscode/issues/23393 pins the shared Ctrl+Enter behavior. Preserve uncustomized Enter behavior, NumLock handling, and remote-desktop navigation-key workarounds; left/right modifier support discussed at https://github.com/microsoft/vscode/issues/44697 is outside this request. Source inspection confirms the gap, but no runtime checks were performed in the read-only checkout.
- **Open decisions:**
  - When generic enter and explicit physical-key bindings coexist, should generic enter remain a fallback for both keys, or should an explicit physical-key configuration make the keys exclusive within its applicable context?
