# Issue #314317 — Proposal: Stable Preview channel + first-class feature gates for progressive rollout

[https://github.com/microsoft/vscode/issues/314317](https://github.com/microsoft/vscode/issues/314317)

## Summary

A real cross-cutting product and release-engineering proposal remains, but it needs maintainer design decisions rather than implementation as written. Current experiment infrastructure covers part of the feature-gate ask, while neither it nor the existing update-frequency issue fully covers the proposed offline gates, expiration policy, and additional distribution channel.

## Change summary

Introduce a lower-risk opt-in release channel and a unified feature-gate system with deterministic cohorts, telemetry, overrides, and mandatory expiration.

## Best solution

Plan the rollout mechanism around the existing assignment and experimental-setting services rather than creating an overlapping system, then separately decide whether release-risk concerns should produce a new product channel or extend the update-frequency work in https://github.com/microsoft/vscode/issues/308615. The design should settle channel timing, offline versus service-backed assignment, user and policy overrides, gate visibility, expiration enforcement, and any extension-facing contract before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/services/assignment/common/assignmentService.ts`, `src/vs/platform/configuration/common/configurationRegistry.ts`, `src/vs/workbench/services/configuration/browser/configurationService.ts`, `src/vs/platform/update/common/update.config.contribution.ts`, `build/azure-pipelines/product-build.yml`
- **Validation:** End the plan with assignment/configuration tests covering stable cohort membership across restarts, explicit user or policy overrides, telemetry attribution, and gate expiration, plus a product-pipeline validation that any approved channel has distinct product metadata and update routing.
- **Behavior:**

  > VS Code should reduce rollout risk without making feature exposure unpredictable or opaque. Users and administrators must have clearly defined release-channel and feature-gate behavior, with stable cohort membership, telemetry respecting existing telemetry controls, explicit override semantics, and an enforceable end to temporary gates. The plan must define whether the new channel precedes Stable or deliberately delays Stable releases, and its acceptance checks must cover both gate behavior and product update routing.
- **Trace:**

  > Current rollout behavior is centered on WorkbenchAssignmentService in src/vs/workbench/services/assignment/common/assignmentService.ts, which obtains online TAS treatments, stores assignment context for telemetry, and permits experiments.override values. IConfigurationPropertySchema.experiment in src/vs/platform/configuration/common/configurationRegistry.ts and ConfigurationDefaultOverridesContribution in src/vs/workbench/services/configuration/browser/configurationService.ts connect treatments to setting defaults; IExperimentalSettingsService tracks whether settings have real assignments. The product pipeline in build/azure-pipelines/product-build.yml currently recognizes exploration, insider, and stable qualities, while src/vs/platform/update/common/update.config.contribution.ts has no active channel selector beyond update behavior. Preserve the established assignment, telemetry-consent, configuration-precedence, and stable/insider update behavior unless the maintainer explicitly chooses a replacement contract. https://github.com/microsoft/vscode/issues/134684 documents the implemented setting-default mechanism; https://github.com/microsoft/vscode/issues/308615 is related update-frequency work but does not absorb the complete proposal.
- **Open decisions:**
  - Is Stable Preview a pre-Stable release-candidate channel, or a delayed channel that receives already-published Stable builds after an additional validation period?
  - Should gate assignment remain service-backed through the existing assignment system, become deterministic and offline from a shipped manifest, or define a user-visible fallback contract combining both?
  - Can users and managed environments override individual gates, and which gates, if any, may be mandatory for security or recovery releases?
  - Should extensions receive a public gate-query API, or should gates remain an internal VS Code contract so extensions cannot depend on temporary rollout state?

## Evidence
