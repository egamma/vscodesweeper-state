# Issue #345069 — Debug Console hangs when scroling far away from a text selection in large output

[https://github.com/microsoft/vscode/issues/345069](https://github.com/microsoft/vscode/issues/345069)

## Summary

Keep open: current source retains every row between the selection and the viewport, explaining why scrolling progressively slows down. The reporter also confirmed the problem on 1.144.0 with extensions disabled; no verified canonical absorbs this specific defect.

## Change summary

Scrolling far from selected Debug Console text progressively degrades performance and can reportedly crash the window.

## Best solution

Keep Debug Console scrolling responsive independently of the distance from a retained selection, while preserving selected text, copying, and shift-click extension. Address the selection-aware virtualization path rather than replacing the entire Debug Console.

- **Likely files:** `src/vs/base/browser/ui/list/listView.ts`, `src/vs/base/test/browser/ui/list/listView.test.ts`, `src/vs/workbench/contrib/debug/browser/repl.ts`

Run scripts/test.sh --run src/vs/base/test/browser/ui/list/listView.test.ts, retaining the existing shift-click selection test. Manually repeat the issue's Node.js Debug Console scenario and verify responsiveness, selection preservation, and copying. No tests were executed during this read-only review.
- **Behavior:**

  > Selecting a small amount of Debug Console text must not make scrolling progressively slower as the viewport moves away from that selection. With 10,000 completed output lines, scrolling should remain comparable to the unselected case. Existing selected text, copy behavior, and shift-click selection extension must remain intact.
- **Trace:**

  > DebugRepl in src/vs/workbench/contrib/debug/browser/repl.ts enables ListView's userSelection path. ListView.onPotentialSelectionStart records persistent currentSelectionBounds, and getRenderRange expands the viewport into one contiguous interval spanning those bounds. ListView.render then creates all intervening rows, directly explaining the reported distance-dependent degradation. The existing listView.test.ts shift-click test requires offscreen selection preservation, so clearing selection is not an acceptable shortcut. The unresolved technical scope is how to preserve that contract without the contiguous render interval, including interactions with row recycling and dynamic-height rendering; this trace does not establish a bounded implementation across those operations. https://github.com/microsoft/vscode/issues/11462 is architectural context, not a duplicate target.

## Evidence

The reporter's follow-up confirms reproduction and a crash on Linux with 1.144.0, in addition to the Windows report; extensions were disabled.
- **Selection enables the problematic path:** src/vs/workbench/contrib/debug/browser/repl.ts:666-691 constructs the DebugRepl tree with userSelection: true. In src/vs/base/browser/ui/list/listView.ts:1294-1342, onPotentialSelectionStart retains currentSelectionBounds after mouseup while the native selection remains noncollapsed.
- **Source-confirmed loss of virtualization:** src/vs/base/browser/ui/list/listView.ts:1621-1628 expands a single contiguous render range to include both the viewport and currentSelectionBounds. With a selection in row zero and the viewport near row 10,000, that range includes all intervening rows. render at lines 948-996 materializes those rows, so rendered content grows with scrolling distance rather than remaining viewport-bounded. This confirms the performance mechanism, not the reported crash.
- **Existing selection contract:** src/vs/base/test/browser/ui/list/listView.test.ts:1022-1071 explicitly tests preservation of offscreen rows when extending a selection with shift-click. Removing selection retention without preserving this behavior would regress an existing contract.
