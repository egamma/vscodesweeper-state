# Issue #295256 — Power save block on active chat session should have an indicator

[https://github.com/microsoft/vscode/issues/295256](https://github.com/microsoft/vscode/issues/295256)

## Summary

The power-save blocker remains invisible on current main, so users cannot identify which VS Code window is keeping the system awake. This team-authored UI-discoverability request should remain open for a product decision and implementation.

## Change summary

Show an indicator in the VS Code window whose active chat request is blocking system sleep.

## Best solution

Expose per-window power-save-blocker activity to the workbench and present a calm, accessible indicator in the responsible window without changing blocker lifetime or sleep semantics.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/power/vscode-node/powerService.ts`, `src/vs/workbench/services/power/common/powerService.ts`, `src/vs/workbench/services/power/electron-browser/powerService.ts`, `src/vs/platform/native/electron-main/nativeHostMainService.ts`
- **Validation:** Manual desktop integration check: start a long chat request in one of two VS Code windows, verify only the responsible window exposes an accessible indicator while system sleep is blocked, then verify the indicator disappears after the existing release delay without preventing display sleep.
- **Behavior:**

  > While a chat request causes VS Code to prevent system suspension, the responsible VS Code window visibly and accessibly indicates that state. With multiple windows open, users can identify the owning window, and the indicator disappears when that window no longer holds the blocker. Existing blocker timing and the ability for the display to sleep remain unchanged.
- **Trace:**

  > Chat acquires the blocker in extensions/copilot/src/extension/power/vscode-node/powerService.ts through the proposed environment power API. MainThreadPower and NativePowerService forward start/stop operations, while src/vs/platform/native/electron-main/nativeHostMainService.ts receives but discards the caller windowId before invoking Electron's process-wide blocker. IPowerService has no blocker-state event or aggregate activity model for UI consumers, which is where the trace reaches a cross-layer design boundary. Preserve the existing two-minute release grace period and prevent-app-suspension semantics; https://github.com/microsoft/vscode/issues/332518 concerns provider coverage and is outside this indicator's scope.
- **Open decisions:**
  - Should the owning-window indication live in the title bar, status bar, or another existing global activity surface?
  - Should the indicator be passive, or should activating it reveal the active chat session or offer any control over the blocker?

## Evidence

- **current implementation:** https://github.com/microsoft/vscode/commit/de441dc178462184fb8772bfff47d325f752bf3e added the blocker used by chat requests; extensions/copilot/src/extension/power/vscode-node/powerService.ts acquires it and logs its identifier but contributes no user-visible state.
- **missing workbench state:** src/vs/workbench/services/power/common/powerService.ts exposes start, stop, and per-ID status methods but no event or aggregate state through which workbench UI could observe active blockers.
- **window attribution gap:** src/vs/platform/native/electron-main/nativeHostMainService.ts receives a windowId for startPowerSaveBlocker but currently ignores it and directly calls Electron's process-wide powerSaveBlocker.start(type), so current main does not retain the owning-window information needed by an indicator.
- **related issue:** https://github.com/microsoft/vscode/issues/332518 is newer than this re-reviewed issue and reports a different observable problem—missing blocker coverage for custom model providers—so it is not an eligible duplicate canonical.
- **original implementation:** The referenced https://github.com/microsoft/vscode-copilot-chat/pull/3483 implemented power-save blocking, not an indicator for identifying the responsible window.
