- **Behavior:**

  > The reporter sees the application-icon system menu positioned too high and partly beneath window controls on Windows 11 with the Activity Bar at the top and compact mode enabled. The expected outcome is a fully visible system menu with no obscured entries or interference from window controls. Start by reproducing those exact steps on the current build and compare the same flow with compact mode disabled and the Activity Bar in its default location. Preserve system-menu functionality and normal minimize, maximize, and close behavior.
- **Trace:**

  > BrowserTitlebarPart creates the application icon and supplies title bar height; NativeTitlebarPart.onUpdateAppIconDragBehavior controls whether the icon is draggable, and NativeTitlebarPart.layout sends native overlay height updates. In windowImpl.ts, the system-context-menu handler intercepts and forwards events only on Linux, leaving native Windows handling intact on this path. This inspection identifies the boundary but does not prove where the reported overlap originates. Current workbench.contribution.ts documentation says compact mode applies only to the default Activity Bar location, so test the claimed setting dependency rather than assuming it changes title bar geometry. The related reports https://github.com/microsoft/vscode/issues/240722 and https://github.com/microsoft/vscode/issues/224515 describe different symptoms and are not verified duplicates. Keep diagnosis scoped to application-icon system-menu placement and layering; do not redesign Activity Bar layout or alter unrelated context-menu behavior.

## Evidence

- **Complete reproduction report:** https://github.com/microsoft/vscode/issues/321504 specifies Windows 11 24H2, VS Code 1.124.2, both settings, reload, and right-clicking the top-left application icon. It reports visual overlap without functional impairment and says extensions are disabled; there are no confirming comments.
- **Current Windows menu boundary:** src/vs/platform/windows/electron-main/windowImpl.ts:241-259 handles Electron's system-context-menu event but only prevents its default behavior and forwards coordinates inside an isLinux branch. The Windows application-icon flow therefore retains native handling here; this does not conclusively demonstrate a positioning defect or an upstream root cause.
- **Title bar integration:** src/vs/workbench/electron-browser/parts/titlebar/titlebarPart.ts sets the application icon's draggable behavior in onUpdateAppIconDragBehavior and updates native overlay height in layout. src/vs/workbench/browser/parts/titlebar/titlebarPart.ts creates the icon and computes title bar minimumHeight. These are relevant integration points, but their source alone does not establish the reported Windows rendering outcome.
- **Configuration distinction:** src/vs/workbench/browser/workbench.contribution.ts:693-697 documents workbench.activityBar.compact as applying only when workbench.activityBar.location is default. The report uses top; this weakens the claimed compact-mode dependency without invalidating its concrete reproduction steps.
- **Canonical search:** Read-only searches for system-menu positioning, application-icon menus, and titlebar overlap found no verified canonical for this symptom. https://github.com/microsoft/vscode/issues/240722 is open but concerns Alt+Space opening the wrong menu depending on cursor location; https://github.com/microsoft/vscode/issues/224515 concerns menu sizing and padding. Neither establishes ownership of this application-icon overlap.
- **Different later overlap report:** https://github.com/microsoft/vscode/issues/332131 is closed and describes Linux KDE left-side native controls overlapping the application icon and menu bar after Electron 43. Its platform, trigger, and affected surface differ from this Windows system-menu report, so it is not evidence that this issue was fixed.
