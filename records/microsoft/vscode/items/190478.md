# Issue #190478 — Document symbols: details are not rendered

[https://github.com/microsoft/vscode/issues/190478](https://github.com/microsoft/vscode/issues/190478)

## Summary

Keep open: current source preserves document-symbol details but does not display or search them in Go to Symbol in Editor. This accepted Backlog request has 27 upvotes and maintainer support; no verified canonical or completed implementation was found.

## Change summary

Display document-symbol details in the in-file symbol picker so overloaded functions can be distinguished and found by their signatures.

## Best solution

Expose provider-supplied DocumentSymbol.detail in Go to Symbol in Editor and support finding overloads by signature information without requiring providers to put signatures in symbol names. Keep workspace-symbol changes separate, as the maintainer requested.

- **Likely files:** `src/vs/editor/contrib/quickAccess/browser/gotoSymbolQuickAccess.ts`, `src/vs/workbench/contrib/codeEditor/browser/quickaccess/gotoSymbolQuickAccess.ts`
- **Validation:** Add focused browser tests for doGetSymbolPicks using same-name document symbols with different detail strings: verify distinguishable displayed signatures, the agreed signature-query behavior, correct navigation ranges, and unchanged behavior for empty details and existing container queries. Manually check Ctrl+Shift+O and @ with a provider supplying names and details separately; do not execute these checks during this read-only review.
- **Behavior:**

  > Go to Symbol in Editor currently presents identical names for overloads even when the document-symbol provider supplies distinct signatures in detail. Users should be able to distinguish those overloads without providers embedding signatures in name, and the original request also asks to find an overload using name plus type information. Acceptance should cover distinct details, absent details, correct navigation, and existing container-qualified searches. Workspace-symbol capabilities are outside this issue's maintainer-established scope.
- **Trace:**

  > OutlineModel._flattenDocumentSymbols in src/vs/editor/contrib/documentSymbols/browser/outlineModel.ts preserves detail, and AbstractGotoSymbolQuickAccessProvider.getDocumentSymbols consumes that flattened list. Its doGetSymbolPicks in src/vs/editor/contrib/quickAccess/browser/gotoSymbolQuickAccess.ts only presents and scores names and container labels; multiword queries currently split into a symbol query and container query. The workbench provider in src/vs/workbench/contrib/codeEditor/browser/quickaccess/gotoSymbolQuickAccess.ts delegates text-editor picks to this shared implementation. Source inspection establishes the missing capability, but the discussion does not settle presentation defaults or how signature matching coexists with container matching. Preserve provider names, navigation ranges, category grouping, and workspace-symbol behavior. https://github.com/microsoft/vscode/issues/139485 concerns a separate workspace-picker truncation problem and is not a canonical for this request.
- **Open decisions:**
  - Should nonempty document-symbol details appear by default, or only when a user enables an option?
  - How should name-plus-signature queries coexist with the current multiword name-plus-container search behavior?
