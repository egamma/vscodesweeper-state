# Issue #244880 — Bug with auto-indent rule: "onEnterRules" + "indentOutdent" + "AppendText" do not insert indentation and string at the END as expected.

[https://github.com/microsoft/vscode/issues/244880](https://github.com/microsoft/vscode/issues/244880)

## Summary

The current source still reproduces the reported missing indentation and placement of `end` on the cursor line rather than the closing line. Keep this older report open: the newer related issue proposes an API extension for the same workflow, but cannot be its duplicate target under the re-review rules.

## Change summary

Make Enter-based block completion produce an indented cursor line followed by an outdented closing keyword without losing indentation.

## Best solution

Resolve the indentation defect and establish a backward-compatible contract for inserting closing-line text in language configuration rules. Coordinate with the proposal at https://github.com/microsoft/vscode/issues/338700 while preserving existing comment-continuation behavior.

- **Behavior:**

  > With the supplied rule, Enter currently inserts 'end' on the first generated line without increasing indentation and leaves the following line empty. The desired block-completion workflow leaves the cursor on an indented empty line and places 'end' on the following line at the opener's indentation. Acceptance must cover the agreed language-configuration contract, cursor placement, tabs and spaces, and unchanged existing comment-continuation behavior.
- **Trace:**

  > getEnterAction in src/vs/editor/common/languages/enterAction.ts supplies automatic indentation differently for empty and nonempty appendText when IndentOutdent is selected. EnterOperation._enter in src/vs/editor/common/cursor/cursorTypeEditOperations.ts then places appendText exclusively on the first generated line. EnterAction in languageConfiguration.ts and the schema in languageConfigurationExtensionPoint.ts expose no separate closing-line text property. Existing JSDoc rules intentionally use appendText on the cursor line, so the reporter's desired placement cannot safely be inferred for every existing rule. The maintainer proposal at https://github.com/microsoft/vscode/issues/338700#issuecomment-5956540599 describes an additive contract, but it is not implemented in the inspected source. The reported Tab behavior should also be checked because the Tab path in cursorTypeEditOperations.ts derives indentation from getEnterAction; it is not independently confirmed here.
- **Open decisions:**
  - Should closing-line text use the optional appendTextNextLine contract proposed in the related issue, preserving appendText's existing first-line behavior, or another explicitly approved public contract?

## Evidence

- **Current source confirms missing indentation:** In src/vs/editor/common/languages/enterAction.ts:40-52, an empty appendText receives a tab for both Indent and IndentOutdent, but a nonempty appendText receives a tab only for Indent. The supplied IndentOutdent/appendText:'end' rule therefore returns 'end' without the additional indentation.
- **Current source confirms wrong closing-line placement:** src/vs/editor/common/cursor/cursorTypeEditOperations.ts:608-620 constructs the IndentOutdent insertion as newline + normalized(indentation + appendText) + newline + original indentation. At an unindented block opener, this produces a first generated line containing 'end' and an empty second generated line, with the cursor on the first.
- **Discussion independently diagnoses indentation defect:** https://github.com/microsoft/vscode/issues/244880#issuecomment-2764275384 identifies the missing IndentOutdent handling in getEnterAction and explains the mismatch with the documented indentation contract. That conditional remains unchanged in the inspected source.

Its maintainer proposal at https://github.com/microsoft/vscode/issues/338700#issuecomment-5956540599 explicitly reproduces this behavior and recommends an optional appendTextNextLine property; this is a proposal, not a landed fix or linked implementation PR.
- **Older search result has a different symptom:** https://github.com/microsoft/vscode/issues/50952 is open but concerns recognizing multiline context and unwanted comment continuation after multiplication expressions. It does not own this report's missing indentation and closing-keyword insertion behavior.
- **Existing workaround does not cover requested workflow:** https://github.com/microsoft/vscode/issues/244880#issuecomment-2759943002 explains that bracket auto-closing inserts the closing keyword before the opening statement is finished. The later autoClosingPairs workaround improves that experience but does not provide the requested insertion triggered by Enter.
- **Compatibility boundary:** src/vs/editor/test/common/modes/supports/onEnterRules.ts:8-14 uses IndentOutdent with appendText:' * ' for JSDoc continuation on the first generated line. Moving all existing appendText values to the outdented line would change established behavior. EnterAction and the configuration schema currently expose appendText but no appendTextNextLine.
