# Issue #336191 — Splitting a reconnected terminal editor reuses its PTY; closing the copy terminates the original

[https://github.com/microsoft/vscode/issues/336191](https://github.com/microsoft/vscode/issues/336191)

## Summary

The code trace supports the report: TerminalEditor.setInput() passes the live instance's full shellLaunchConfig (including attachPersistentProcess when the terminal was reconnected) into setCopyLaunchConfig, and TerminalEditorInput.copy() then constructs the split's instance from that same config, causing terminalProcessManager to attachToProcess() with the original's persistent-process id instead of creating a new process — this plausibly explains the shared PID and the original dying when the split is closed.

## Change summary

Splitting a reconnected (persisted) terminal editor makes the split share the original's PTY instead of getting its own, so closing the split kills the original terminal's process.

## Best solution

In terminalEditor.ts's setInput (or TerminalEditorInput.setCopyLaunchConfig), clone the shellLaunchConfig and strip attachPersistentProcess before storing it as the copy config, so EditorInput.copy() always resolves a fresh profile/process for the split while leaving the source terminal's process untouched; needs care to still resolve profile/cwd/shell path correctly, as the reporter notes.

## Evidence

- **copy config carries attachPersistentProcess:** src/vs/workbench/contrib/terminal/browser/terminalEditor.ts:90 calls `this._editorInput.setCopyLaunchConfig(this._editorInput.terminalInstance.shellLaunchConfig)` — this passes the instance's live shellLaunchConfig object as-is, without stripping attachPersistentProcess.
- **copy() reuses that config verbatim:** src/vs/workbench/contrib/terminal/browser/terminalEditorInput.ts:74-79 `copy()` calls `this._terminalInstanceService.createInstance(this._copyLaunchConfig || {}, TerminalLocation.Editor)` with no sanitization of attachPersistentProcess.
- **attach reuses the same PTY:** src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts:339-343 (local case) calls `backend.attachToProcess(shellLaunchConfig.attachPersistentProcess.id)` whenever attachPersistentProcess is present, which reattaches to the existing persistent process rather than spawning a new one — matching the observed shared PID.
- **no existing guard found:** git log on terminalEditorInput.ts/terminalEditor.ts shows no recent change addressing this; the only nearby `delete shellLaunchConfig.attachPersistentProcess` guard is in an unrelated `relaunch()` path (terminalInstance.ts:1936-1941), not in the copy/split path.
