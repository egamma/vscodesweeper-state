## Change summary

Opening a Ruby project after updating VS Code causes rebornix.ruby 0.28.1's language server to fail loading tree-sitter.wasm.

## Best solution

Replace the deprecated rebornix.ruby extension with Shopify's Ruby LSP. Compatibility fixes for the old extension belong to its external project, not VS Code core.

## Evidence

- **Core boundary:** Current extensions/ruby/package.json declares the separate vscode.ruby built-in extension with language configuration and grammar contributions, but no language-server entry point. The reported dist/server/tree-sitter.wasm belongs to the installed rebornix extension.
- **Maintainer assessment:** https://github.com/microsoft/vscode/issues/195159#issuecomment-1767984045 states that this is not VS Code's general WASM support and identifies the Ruby language server's tree-sitter loading.
- **Diagnosis and workaround:** https://github.com/microsoft/vscode/issues/195159#issuecomment-1778475845 attributes the failure to the extension's older Emscripten loader using Node's newly available fetch API for a filesystem path. It reports NODE_OPTIONS="--no-experimental-fetch" as a workaround, while warning that disabling fetch can break other extensions.
- **External dependency corroboration:** https://github.com/emscripten-core/emscripten/issues/16913 documents the same filesystem-path URL parsing failure with Node 18's fetch API. This corroborates the extension-bundled loader diagnosis, rather than establishing a current VS Code dependency defect.
- **Deprecation and alternative:** https://github.com/rubyide/vscode-ruby is archived, and its README explicitly deprecates the extension in favor of Shopify's Ruby LSP. https://github.com/microsoft/vscode/issues/195159#issuecomment-2346704070 independently reports that the replacement does not exhibit this failure.
