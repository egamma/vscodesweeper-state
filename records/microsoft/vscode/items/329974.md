# Issue #329974 — Image attachments should expose the file path to the agent, not just pixel data

[https://github.com/microsoft/vscode/issues/329974](https://github.com/microsoft/vscode/issues/329974)

## Summary

The gap remains on current main: VS Code retains the originating URI for a file-backed image, but the Agent Host conversion sends only an embedded image whenever pixel data is present. This should stay open for an agent-facing attachment contract that preserves both representations without assigning paths to pasted or captured images.

## Change summary

File-backed image attachments provide pixels to the agent but omit the local source path needed for file operations.

## Best solution

Preserve a usable source resource URI alongside the image bytes for file-backed images across the chat-to-agent boundary, while screenshots, clipboard images, and URL images remain binary-only unless they have a genuine local resource.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts`, `src/vs/workbench/contrib/chat/test/browser/agentSessions/agentHostChatContribution.test.ts`, `src/vs/platform/agentHost/common/state/protocol/channels-chat/state.ts`
- **Validation:** Add an Agent Host chat contribution test that attaches a local image and verifies the outgoing message exposes both its image bytes and usable source resource, plus a companion case proving a screenshot or pasted image has no fabricated source path.
- **Behavior:**

  > When a user attaches an image originating from a local file, the agent receives both the image pixels and a usable reference to that source file. The agent can use the reference for file operations without asking the user to provide the path again. Screenshots, clipboard images, and other images without a local source continue to expose only their binary image content. Existing image preview and vision behavior must remain unchanged.
- **Trace:**

  > ChatAttachmentResolveService in src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentResolveService.ts preserves a file-backed image's URI in `references` and its path in `fullName`. AgentHostSessionHandler._toImageAttachment in src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts selects an embedded-resource attachment whenever bytes exist and therefore omits that URI; the URI fallback runs only when bytes are absent. The extension-host converter in src/vs/workbench/api/common/extHostTypeConverters.ts already carries the URI on ChatReferenceBinaryData, so that path should not regress. The uncertainty begins at the Agent Host message contract, where embedded binary and URI resources are currently distinct variants. Do not assign local paths to pasted, captured, URL-only, or generated images that lack a real local source.
- **Open decisions:**
  - Should the Agent Host contract represent a file-backed image as one embedded attachment with an optional source URI, or as coordinated embedded-image and resource attachments, while ensuring the model does not perceive duplicate user attachments?

## Evidence

- **source path retained:** src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentResolveService.ts:246-258 records the local image path in `fullName` and the source URI in `references` while also storing resized pixel data.
- **source path dropped:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:6862-6886 converts any image with bytes into `MessageAttachmentKind.EmbeddedResource` containing only label, base64 data, MIME type, and optional metadata; it consults the resource URI only when no bytes are available.
- **protocol boundary:** src/vs/platform/agentHost/common/state/protocol/channels-chat/state.ts defines embedded-resource and URI-resource attachments as separate variants; the embedded-resource variant has no source-URI field, so preserving both requires an explicit protocol or message-representation decision.
- **existing extension-host behavior:** src/vs/workbench/api/common/extHostTypeConverters.ts:3645-3654 constructs `ChatReferenceBinaryData` with the originating URI when one exists, showing that VS Code already distinguishes file-backed images from pasted binary images on the extension-host path.
- **related issue is distinct:** https://github.com/microsoft/vscode/issues/328244 concerns subagents being unable to read attachment paths they already receive; it does not own this report's symptom, where the source path is never exposed to the agent.
