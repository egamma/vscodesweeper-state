# Issue #237533 — Keybindings different behavior in Windows and macOS with Czech localized keyboard layout

[https://github.com/microsoft/vscode/issues/237533](https://github.com/microsoft/vscode/issues/237533)

## Summary

Keep open for keyboard-layout investigation: current source still uses different Windows and macOS resolution paths, but the exact Czech-layout failure has not been confirmed on current main. The report already provides sufficient steps and dispatch logs to retest; the subsequent Neovim workaround does not establish a core fix.

## Change summary

Investigate why the same contributed ctrl+[ binding works on the physical BracketLeft key with Czech layout on Windows but disappears on macOS.

## Best solution

Establish the intended cross-platform contract for contributed punctuation bindings and verify this Czech-layout case in the native keyboard mappers. Preserve explicit scan-code bindings as the supported physical-key mechanism without broadly changing layout-aware shortcuts.

- **Behavior:**

  > A contributed ctrl+[ binding activates from the physical key right of P on Windows with Czech layout, but the equivalent binding is unavailable on macOS in the reported version. Explicit ctrl+[BracketLeft] works on both platforms. Establish whether this discrepancy persists on current builds and which cross-platform behavior is intended before changing defaults. Acceptance must compare both binding forms on US and Czech layouts while preserving unrelated layout-aware shortcuts.
- **Trace:**

  > KeyboardLayoutService in src/vs/workbench/services/keybinding/electron-browser/nativeKeyboardLayout.ts selects distinct Windows and macOS mappers. WindowsKeyboardMapper.resolveKeyboardEvent uses keyCode, while MacLinuxKeyboardMapper.resolveKeyboardEvent uses code and resolves declared character chords through layout-derived mappings; explicit ScanCodeChord bindings bypass that translation. This explains the observed dispatch formats but does not conclusively reproduce the Czech mapping failure on current main. https://github.com/vscode-neovim/vscode-neovim/pull/2390 supplies an extension-level workaround, not a core fix. Preserve established character-aware behavior discussed at https://github.com/microsoft/vscode/issues/141761#issuecomment-1024680855; do not generalize physical-key fallback to all shortcuts without a product decision.
- **Open decisions:**
  - For Ctrl+[ on Czech macOS, should the character-form declaration preserve Windows's physical-key activation, or should that guarantee require an explicit ctrl+[BracketLeft] declaration?
