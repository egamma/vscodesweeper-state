# Issue #2809 — Support variables when resolving values in settings

[https://github.com/microsoft/vscode/issues/2809](https://github.com/microsoft/vscode/issues/2809)

## Summary

Keep open: general variable resolution in settings remains missing, and an open implementation PR explicitly targets this request. The existing setting-specific support does not cover the central ask; review that PR rather than start competing work.

## Change summary

Support environment and workspace variables in path-valued settings so teams can share configuration across machines.

## Best solution

Provide a consistent, compatibility-conscious variable-resolution contract for supported core and extension settings. Review https://github.com/microsoft/vscode/pull/319156 for whether its opt-in API actually reaches setting consumers and addresses extension-host access before treating this request as completed.

## Evidence

- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/319156 is verified OPEN with mergedAt null and explicitly says Fixes #2809. Its proposal adds opt-in supportsVariableSubstitution and getResolvedValue APIs; it is not a landed fix and must not trigger a completed close.
- **Existing capability does not cover general settings:** src/vs/workbench/api/common/extHostConfiguration.ts, ConfigurationProvider.getConfiguration(), reads configuration values and returns strings without variable substitution. src/vs/workbench/services/configurationResolver/common/configurationResolver.ts exposes an internal resolver, while terminal consumers explicitly invoke it in terminalActions.ts and terminalProfileResolverService.ts. These selected consumers do not provide transparent resolution for arbitrary extension settings.
- **Original setting still has only partial path handling:** extensions/typescript-language-features/src/configuration/configuration.electron.ts, ElectronServiceConfigurationProvider.readGlobalTsdk() and readLocalTsdk(), read typescript.tsdk or the newer js/ts.tsdk.path through inspect(). Their fixPathPrefixes() expands a leading tilde followed by the platform separator, but does not expand %APPDATA% or ${env:APPDATA}. Home-prefix handling therefore does not satisfy the requested general environment-variable support.
- **Canonical search:** A repository issue search for variable substitution in settings found related API requests https://github.com/microsoft/vscode/issues/46471 and https://github.com/microsoft/vscode/issues/140056. Both are verified open, concern extension access to resolution, and were created in 2018 and 2022 respectively, later than this 2016 report. Neither qualifies as an older same-symptom canonical under the re-review rule.
- **Discussion and demand:** https://github.com/microsoft/vscode/issues/2809 has 741 community upvotes and is accepted into Backlog. The supplied discussion documents ESLint, JAVA_HOME, multi-root workspaces, home-directory paths and cross-platform synchronization; the workspace-substitution extension offered in comment 1 is a workaround, not built-in coverage. Comments 12–19 also identify unsettled compatibility expectations around automatic versus opt-in expansion.
- **Scope distinction:** The latest supplied comment distinguishes reading environment variables in setting values from defining environment variables for processes. This review concerns the former; the latter is not evidence that the requested setting-resolution capability exists.
