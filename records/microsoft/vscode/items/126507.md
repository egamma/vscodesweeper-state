# Issue #126507 — [scss] map value override => identifier expected

[https://github.com/microsoft/vscode/issues/126507](https://github.com/microsoft/vscode/issues/126507)

## Summary

Still reproduces on main: the SCSS parser in vscode-css-languageservice does not handle namespaced variable declarations (e.g. `test.$var: value;`), producing a false 'identifier expected' diagnostic. The upstream parser is unchanged.

## Change summary

VS Code's built-in SCSS language service incorrectly flags valid namespaced variable assignments (`namespace.$variable: value;`) as syntax errors.

## Best solution

Fix `_parseVariableDeclaration` (or add a sibling method) in the upstream `microsoft/vscode-css-languageservice` SCSS parser to recognize module-namespaced variable declarations (`ident . $variable : expr`), then bump the dependency in `extensions/css-language-features/server/package.json`. The `_parseModuleMember` method already handles namespaced variable *reads* — the declaration side needs the same treatment.

## Evidence

- **source trace:** In the installed vscode-css-languageservice (6.3.4) and current upstream main (SHA 6b31dbb), `_parseVariableDeclaration` at scssParser.ts:62 exits immediately if the current token is not `VariableName` (starts with `$`). A line like `test.$test: (...)` starts with an identifier, so the variable declaration parser is never entered.
- **upstream unchanged:** The latest `src/parser/scssParser.ts` on microsoft/vscode-css-languageservice main still has the same `if (!this.peek(scssScanner.VariableName)) { return null; }` guard — the bug is not fixed upstream.
- **_parseModuleMember reads only:** `_parseModuleMember()` at scssParser.ts:137 correctly parses `namespace.$var` as a value expression, but there is no corresponding path for namespaced variable *declarations* (assignments with `:`).
- **valid Sass syntax:** The reporter confirmed `sass test2.scss` (Dart Sass 1.35.1) compiles the namespaced variable override without error; this is valid Sass module syntax per the @use spec.
- **ongoing user impact:** Comments from 2023, Feb 2025, and Dec 2025 confirm the issue persists across VS Code versions, with 6 upvotes on the issue body.
