# Issue #203315 — SCM Graph - Support reordering outgoing commits

[https://github.com/microsoft/vscode/issues/203315](https://github.com/microsoft/vscode/issues/203315)

## Summary

Outgoing-commit reordering remains missing from the SCM Graph. Keep this accepted Backlog request open for design; the related interactive-rebase requests do not establish the same graph-specific interaction required by the prior-review duplicate bar.

## Change summary

Allow users to reorder outgoing commits by dragging a commit between other commits in the SCM Graph.

## Best solution

Provide a deliberate SCM Graph interaction that rewrites the order of outgoing commits, backed by Git operations and a defined conflict/cancellation experience. Coordinate with the interactive-rebase work without treating a general rebase editor as coverage of graph drag-and-drop.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/scm/browser/scmHistoryViewPane.ts`, `extensions/git/src/historyProvider.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/git.ts`
- **Validation:** In a disposable Git repository with a configured upstream and three independent outgoing commits, drag one between the others in the SCM Graph and verify the resulting order with git log and the refreshed graph. Confirm the upstream ref and final file contents remain unchanged. Exercise overlapping commits to verify the agreed conflict/cancellation behavior, and confirm ineligible drop targets leave repository history unchanged.
- **Behavior:**

  > Users should be able to reorder outgoing commits directly in the SCM Graph by dropping one between other commits. The operation must change repository history, not merely the graph's display order, and the refreshed graph must reflect that history. Acceptance includes moving an independent commit earlier and later while preserving the final file contents and leaving the upstream ref unchanged. Eligibility and the user-visible handling of conflicts must be agreed before implementation.
- **Trace:**

  > SCMHistoryTreeDragAndDrop in src/vs/workbench/contrib/scm/browser/scmHistoryViewPane.ts exports history-item transfer data but rejects all drop targets and has an empty drop method. Between-item list/tree support exists according to https://github.com/microsoft/vscode/issues/200745, but this graph has not adopted it for history rewriting. The built-in git.rebase command selects a branch, and Repository.rebase in extensions/git/src/git.ts accepts a branch plus onto/rebaseMerges options rather than a requested commit sequence. The relevant integration boundary is the generic SCM graph and the Git provider/repository operations, with extensions/git/src/historyProvider.ts as a provider-side starting point. Preserve existing drag exports and ordinary branch-rebase behavior; this request is not graph date sorting or arbitrary rewriting of published history. https://github.com/microsoft/vscode/issues/31153 is related design context, not a verified duplicate of this graph interaction. The trace establishes missing capability, not an existing bounded rewrite implementation; provider integration and conflict behavior require planning.
- **Open decisions:**
  - Should the initial interaction support only linear outgoing history, or also outgoing merge commits with preserved merge topology?
  - If reordering produces conflicts, should the operation enter a resumable rebase workflow or cancel and restore the original history?

## Evidence

- **Current graph capability:** src/vs/workbench/contrib/scm/browser/scmHistoryViewPane.ts:1024–1056 implements SCMHistoryTreeDragAndDrop, but onDragOver always returns false and drop is empty. Dragging history items exports transfer data; dropping them into the graph cannot reorder commits.
- **Existing commands do not cover the request:** extensions/git/src/commands.ts:3412 onward implements git.rebase as selection of a branch to rebase onto. extensions/git/src/git.ts:2539–2552 supports branch rebasing with onto/rebaseMerges options, not a chosen commit order. The scm/historyItem/context registrations in extensions/git/package.json contain checkout, branch, tag, cherry-pick and comparison actions, but no reorder action.
