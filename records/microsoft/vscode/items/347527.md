# Issue #347527 — Proposal: check PRs against their merged result, not just the PR head

[https://github.com/microsoft/vscode/issues/347527](https://github.com/microsoft/vscode/issues/347527)

## Summary

The existing PR workflow already checks GitHub's synthetic merge result, including client type checking, rather than only the PR head. The central capability proposed here is already present.

## Change summary

Add an optional CI check that detects integration failures by testing a PR merged with its base branch.

## Best solution

Keep the existing merge-result CI rather than add a second action for the same check. Treat guaranteed revalidation after subsequent base-branch changes as a separate question about merge freshness, not head-only testing.

- **Client type checking already included:** .github/workflows/pr.yml:367-370 runs core-ci-pr in the Compile step. build/gulpfile.vscode.ts:65-79 defines core-ci-pr through coreCIOutBuildTask, including tsgo-typecheck against src/tsconfig.json with noEmit, covering merged-result TypeScript errors such as the reported missing export.
- **Proposal and demonstrations:** https://github.com/microsoft/vscode/issues/347527 offers an optional merge-guard action and explicitly allows closure if the existing flow covers it. The linked fork demonstrations contrast merge-guard with a plain head check; they do not establish that VS Code's existing Code OSS workflow tests only the head.
- **Freshness boundary:** The workflow's default pull_request trigger does not by itself establish revalidation whenever the base branch advances. Repository branch-protection and merge-queue settings were not verified, so this review does not claim that a passing check always covers the latest base tip at merge time.
