# Issue #211983 — Cycle windows backward and forward by last used 

[https://github.com/microsoft/vscode/issues/211983](https://github.com/microsoft/vscode/issues/211983)

## Summary

Keep this accepted, 24-upvote request open: the built-in window pickers do not provide most-recently-used ordering. Related reports cover native macOS ordering and repeated picker navigation, but neither clearly owns the full Alt-Tab-style behavior requested here.

## Change summary

Provide forward and backward cycling through VS Code windows in most-recently-used order, including convenient switching between the two last-used windows.

## Best solution

Offer MRU window navigation with predictable forward/backward cycling and two-window toggling while preserving access to existing window-order behavior. Decide whether this is exposed through separate commands or an opt-in change to existing switching, and define how auxiliary windows participate.

## Plan brief

- **Likely files:** `src/vs/workbench/electron-browser/actions/windowActions.ts`, `src/vs/platform/native/common/native.ts`, `src/vs/platform/native/electron-main/nativeHostMainService.ts`, `src/vs/platform/windows/electron-main/windowsMainService.ts`, `src/vs/platform/windows/electron-main/windowImpl.ts`
- **Validation:** On macOS, open four distinguishable windows and focus them in an order different from creation order. Verify that the agreed MRU command switches to the previously used window, repeated separate invocations toggle the last two windows, and forward/backward traversal visits the remaining windows in the agreed order without focus updates scrambling an active cycle. Verify existing ordering remains available and repeat with an auxiliary window according to the chosen scope.
- **Behavior:**

  > With many VS Code windows open, users should be able to navigate by recent use rather than creation order. The reporter explicitly wants Alt-Tab-style behavior, including returning between the last two windows, and mentions recency ordering for the macOS Ctrl+W window picker as a follow-up. Acceptance should cover forward and backward traversal, two-window toggling, and preservation of existing ordering for users who prefer it. The record does not settle which shortcuts or commands should expose this behavior or how auxiliary windows participate.
- **Trace:**

  > BaseSwitchWindow.run in src/vs/workbench/electron-browser/actions/windowActions.ts underlies both Switch Window and Quick Switch Window; it preserves main-window enumeration order, groups auxiliary windows, and selects the next item after the current window. NativeHostMainService.getWindows in src/vs/platform/native/electron-main/nativeHostMainService.ts obtains that order from WindowsMainService.getWindows and returns no focus-recency metadata. Main-window lastFocusTime is tracked in src/vs/platform/windows/electron-main/windowImpl.ts, but that alone does not define a stable MRU navigation session or auxiliary-window ordering. Preserve existing picker close controls, dirty-window indications, and non-MRU navigation behavior. https://github.com/microsoft/vscode/issues/195442 concerns native macOS explicit-foreground ordering, while https://github.com/microsoft/vscode/issues/204337 concerns repeated key navigation; neither proves this request is implemented or fully duplicated. Native shortcut handling remains a separate uncertainty if changing Cmd+backtick is chosen instead of adding workbench commands.
- **Open decisions:**
  - Should MRU navigation use separate bindable commands, or be an opt-in mode for existing window-switching commands and native macOS shortcuts?
  - Should the Ctrl+W picker share MRU ordering, and should auxiliary windows be independently ordered or remain grouped under their parent?
