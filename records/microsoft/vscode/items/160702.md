## Summary

Keep open: multiple independent reports confirm editor-caret drift on ChromeOS, particularly after fractional DPR changes, and a maintainer consolidated a later report here. Current source has DPR-aware font measurement and monospace validation, but the ChromeOS-specific failure has neither a cited fix nor a verified current-main resolution.

## Change summary

Changing display scaling on ChromeOS can make the editor caret drift several characters away from the text insertion position.

## Plan brief

- **Likely files:** `src/vs/base/browser/pixelRatio.ts`, `src/vs/editor/browser/config/editorConfiguration.ts`, `src/vs/editor/browser/config/fontMeasurements.ts`, `src/vs/editor/browser/viewParts/viewLines/viewLine.ts`, `src/vs/editor/test/browser/config/fontMeasurements.test.ts`
- **Validation:** On current vscode.dev or Insiders running on ChromeOS, change display scaling so the effective DPR becomes 1.375, refresh, and edit near the end of a long monospace line with editor.disableMonospaceOptimizations left false; the caret, diagnostics, and inserted text must remain aligned at default browser zoom and after 90%/110% zoom transitions.
- **Behavior:**

  > After ChromeOS display scaling or browser zoom changes the effective device-pixel ratio, the editor caret must remain aligned with the character and insertion position throughout a long line. Diagnostics and other column-positioned decorations must remain aligned as well. The result must hold with monospace optimizations enabled; the existing hidden setting may remain a fallback but must not be required. Acceptance requires exercising DPR 1.375 and 1.25 transitions on current ChromeOS without accumulating horizontal drift.
- **Trace:**

  > PixelRatioMonitorImpl in src/vs/base/browser/pixelRatio.ts watches devicePixelRatio through a resolution media query, and EditorConfiguration in src/vs/editor/browser/config/editorConfiguration.ts recomputes options when that event fires. FontMeasurementsImpl in src/vs/editor/browser/config/fontMeasurements.ts measures character widths through DOM offsetWidth and caches them under BareFontInfo, whose ID includes pixelRatio. ViewLineOptions and RenderedViewLine in src/vs/editor/browser/viewParts/viewLines use those measurements for optimized column offsets and contain the monospace-assumption fallback introduced by https://github.com/microsoft/vscode/pull/92291. The unresolved boundary is whether ChromeOS exposes the new DPR after stale measurements have been reused, produces fractional measurements that pass the existing validation, or has an upstream rendering behavior that cannot be modeled by the current browser tests. Preserve optimized rendering and behavior on other platforms; do not treat the separate Wayland mouse-pointer issue https://github.com/microsoft/vscode/issues/136390 as the same defect.

## Evidence

- **confirmed reproduction:** The reporter reproduced with extensions disabled on ChromeOS, isolated the trigger to changing display scaling/DPR, observed drift at DPR 1.375 and 1.25, and reproduced in vscode.dev; https://github.com/microsoft/vscode/issues/160702 documents the exact scaling and browser-zoom observations.
- **independent confirmation:** A second reporter reproduced the offset with default settings, while https://github.com/microsoft/vscode/issues/180223 was closed by a maintainer specifically to consolidate another ChromeOS caret-offset report into this issue.
- **current source path:** src/vs/base/browser/pixelRatio.ts monitors devicePixelRatio changes, src/vs/editor/browser/config/editorConfiguration.ts recomputes editor options when it changes, and src/vs/editor/browser/config/fontMeasurements.ts caches DOM-measured character widths using a BareFontInfo key that includes pixelRatio. This identifies the relevant path but does not establish that ChromeOS reports the transition early enough for fresh measurements.
- **optimization path:** src/vs/editor/browser/viewParts/viewLines/viewLineOptions.ts enables monospace positioning from cached font metrics, while viewLine.ts validates assumptions against DOM width and falls back when they differ. The reported workaround, editor.disableMonospaceOptimizations, bypasses this path and strongly localizes the symptom without proving the underlying cause.
- **prior fix is insufficient evidence:** https://github.com/microsoft/vscode/pull/92291 fixed the older ChromeOS cursor issue https://github.com/microsoft/vscode/issues/77817 by validating monospace assumptions, but this report and its confirmations occurred years after that merge, so the old commit cannot support an implemented-on-main close.
- **not the candidate canonical:** https://github.com/microsoft/vscode/issues/136390 remains open but tracks an oversized and inaccurate OS mouse pointer under Wayland/Electron; this issue concerns the text caret drifting from glyph and insertion positions after ChromeOS DPR changes, so the candidate does not clearly own the same defect.
