# Issue #339255 — [Copilot Agent] Tool execution fails with 400 INVALID_ARGUMENT: Function call missing thought_signature

[https://github.com/microsoft/vscode/issues/339255](https://github.com/microsoft/vscode/issues/339255)

## Summary

A brand-new report (0 comments, no maintainer engagement yet) against the BYOK Gemini native provider; the code shows a plausible concrete mechanism for exactly this symptom (second tool call in a turn losing its thought signature), so this stays open for investigation rather than needs-info.

## Change summary

Using a BYOK Gemini (Gemini 3) model in Agent mode, tool execution fails with a 400 INVALID_ARGUMENT because a functionCall part sent back to the API is missing a required thought_signature.

## Best solution

In the BYOK Gemini native provider, ensure every outgoing functionCall part always carries a thoughtSignature when a model turn contains more than one tool call (propagate the last known signature, or insert Gemini's documented placeholder for calls that arrived without one), then add test coverage for multi-call turns.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/byok/common/geminiMessageConverter.ts`, `extensions/copilot/src/extension/byok/vscode-node/geminiNativeProvider.ts`
- **Validation:** A vitest case in geminiMessageConverter.spec.ts with two LanguageModelToolCallParts in one assistant message where only the first is preceded by a LanguageModelThinkingPart(signature) should assert the second outgoing functionCall part also carries a thoughtSignature once the decision below is made.
- **Behavior:**

  > When a BYOK Gemini (Gemini 3) model issues more than one tool/function call within a single turn, the next outgoing request must include a thoughtSignature on every functionCall part being echoed back, even ones whose original streamed response part carried no signature — otherwise Gemini rejects the request with 400 INVALID_ARGUMENT 'Function call is missing a thought_signature'. Expected: agent tool execution with multiple tool calls per turn succeeds without this validation error.
- **Trace:**

  > `pendingThinkingSignature` in geminiNativeProvider.ts's `_makeRequest` streaming loop (~lines 452-506) is set only when the currently-iterated API part itself has `thoughtSignature`, and is cleared as soon as it's attached to a functionCall part; a subsequent functionCall part in the same turn with no own `thoughtSignature` gets no preceding LanguageModelThinkingPart. On the next turn, `apiContentToGeminiContent` in geminiMessageConverter.ts (lines 11-40) mirrors this with a single `pendingSignature` local that is likewise cleared after one use, so that second tool call is serialized without a `thoughtSignature`. Boundary: the existing single-tool-call path is covered by the 'should attach a thought signature to the following function call' test and must keep passing unchanged. Where the uncertainty starts: whether Gemini expects the same signature to cover all function calls in a turn (propagate) or expects a specific placeholder for calls without a real one — that determines the actual fix.
- **Open decisions:**
  - Should a function call lacking its own thoughtSignature in a multi-call turn reuse/propagate the last signature seen in that turn, or should a Gemini-documented placeholder value be inserted instead?
  - Is the missing signature only a capture bug in geminiNativeProvider.ts (Gemini actually sent one we failed to parse), or does Gemini genuinely omit signatures on non-first parallel calls, requiring a synthesized value?

## Evidence

- **single mutable signature slot:** extensions/copilot/src/extension/byok/common/geminiMessageConverter.ts lines 11-40: apiContentToGeminiContent tracks one `pendingSignature` variable that is cleared immediately after being attached to the first LanguageModelToolCallPart it sees; a later tool call in the same message with no preceding LanguageModelThinkingPart gets no thoughtSignature at all.
- **capture logic in the streaming reader:** extensions/copilot/src/extension/byok/vscode-node/geminiNativeProvider.ts lines 452-506 (_makeRequest): `pendingThinkingSignature` is only set when the *current* streamed part itself carries `thoughtSignature`, and is consumed/cleared the moment any functionCall part is seen; a second functionCall part in the same turn whose own stream part lacks `thoughtSignature` is emitted with no thinking part before it.
- **no test coverage for multi-call turns:** extensions/copilot/src/extension/byok/common/test/geminiMessageConverter.spec.ts only has a single-call test ('should attach a thought signature to the following function call'); there is no test exercising two sequential tool calls in one assistant turn, which is the scenario the reporter's error ('position 2') describes.
