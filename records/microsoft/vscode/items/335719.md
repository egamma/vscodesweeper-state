# Issue #335719 — Multi-diff editor retains disposed row DOM across input changes

[https://github.com/microsoft/vscode/issues/335719](https://github.com/microsoft/vscode/issues/335719)

## Summary

Real, source-confirmed lifecycle bug: DiffEditorItemTemplate appends its root DOM node but never removes it on disposal, unlike the equivalent DiffEditorWidget pattern which does. This is a genuine DOM/memory leak in multi-diff editor row virtualization, still open and unfixed on main, so it should stay open for a fix.

## Change summary

Repeatedly replacing the multi-diff editor's input leaves disposed row DOM elements attached instead of being removed, causing DOM to grow unbounded across input changes.

## Best solution

Register `this._elements.root.remove()` with the template's own disposal lifetime in diffEditorItemTemplate.ts (mirroring diffEditorWidget.ts line 204's `this._register(toDisposable(() => this.elements.root.remove()))`), not with unbind, since pooled templates are reused across bindings; add a regression test asserting `.multiDiffEntry` DOM count stays bounded after repeated setViewModel/dispose cycles and pool eviction.

- **Fix prompt:**

  > In src/vs/editor/browser/widget/multiDiffEditor/diffEditorItemTemplate.ts, DiffEditorItemTemplate's constructor calls `this._container.appendChild(this._elements.root)` (around line 287) but never registers removal of that root element when the template itself is disposed. Compare with the analogous src/vs/editor/browser/widget/diffEditor/diffEditorWidget.ts line 204, which does `this._register(toDisposable(() => this.elements.root.remove()));`. Because DiffEditorItemTemplate is pooled and reused across many bindings/unbindings by VirtualizedTemplatePool (in virtualizedItemManager.ts), the removal must be registered against the *template's* own Disposable lifetime (i.e., in the constructor via `this._register(toDisposable(() => this._elements.root.remove()))`), NOT against bind/unbind — unbinding a pooled-but-reused template must NOT remove its DOM, since it may still be attached and about to be rebound. Only when the pool actually disposes an excess template (VirtualizedTemplatePool.acquire()'s returned dispose callback, which calls `template.dispose()` once `_unused.size >= 5`) should the root be detached — and that will now happen automatically via the template's own disposal. Do not change binding/unbinding logic, the pool's eviction threshold, or DiffEditorWidget's existing correct pattern. Add a regression test that creates a MultiDiffEditorWidget, feeds it several successive large inputs (repeated setViewModel/dispose cycles like the report's 90-file, 3-cycle scenario), and asserts the number of `.multiDiffEntry` elements remaining in the container stays bounded at the pool's cache size (5) instead of growing by roughly the collapsed-row count each cycle. Related: https://github.com/microsoft/vscode/issues/335719, https://github.com/microsoft/vscode/issues/206959 (a related but distinct bounded-listener-count issue, not the same defect).
