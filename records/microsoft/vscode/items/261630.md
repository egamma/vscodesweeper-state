# Issue #261630 — `npm.scriptRunner` auto-detection fails in subdirectories; defaults to npm instead of pnpm/yarn/bun

[https://github.com/microsoft/vscode/issues/261630](https://github.com/microsoft/vscode/issues/261630)

## Summary

The subdirectory detection defect remains in current main: script and installation tasks execute in the package directory but detect the package manager from the workspace root. The linked implementation candidate remains open and does not address that caller mismatch.

## Change summary

Automatically select the correct package manager for scripts and dependency installation in nested packages instead of falling back to npm.

## Best solution

Make automatic detection reflect the target package across manually defined npm tasks, the NPM Scripts view, and package.json actions while preserving explicit configuration overrides. Review https://github.com/microsoft/vscode/pull/302916 against this subdirectory scenario; its detector changes alone do not cover the reported failure.

## Evidence

- **Source-confirmed trigger:** For the reported root/client layout with package-manager metadata only under client, extensions/npm/src/tasks.ts:createScriptRunnerTask computes cwd from packageJsonUri but calls getRunScriptCommand with folder.uri, the workspace root. createInstallationTask similarly passes folder.uri to getInstallDependenciesCommand. NpmTaskProvider.resolveTask resolves the supplied path to client/package.json but reaches these same constructors.
- **Detection fallback:** extensions/npm/src/tasks.ts:detectPackageManager passes that root fsPath to findPreferredPM. In extensions/npm/src/preferred-pm.ts, lockfile checks operate at the supplied directory, pnpm's findUp searches ancestors rather than child packages, and the final fallback is npm. The detector does not read the packageManager field.
- **Built-in ownership and shared entry points:** The discussion explicitly corrected the initial third-party-extension attribution and reopened the issue. Current extensions/npm/src/npmView.ts executes generated script tasks and calls createInstallationTask for installation; extensions/npm/src/tasks.ts:runScript also calls createScriptRunnerTask for package.json actions. These built-in paths share the confirmed mismatch.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/302916 is currently OPEN with mergedAt null, as referenced in the final issue comment. Its diff changes only extensions/npm/src/preferred-pm.ts, adding packageManager-field detection and ancestor lockfile lookup; it does not change the workspace-root arguments in tasks.ts. https://github.com/microsoft/vscode/pull/302354 is CLOSED without merging, so neither establishes a landed fix.
- **Related issue is narrower:** https://github.com/microsoft/vscode/issues/172865 is verified OPEN, but reports an npm task's options.cwd being ignored; its discussion diagnoses task-provider configuration exposure. This report additionally supplies definition.path and covers generated explorer tasks, direct package.json execution, and installation, where the package URI is already available. The older issue therefore does not demonstrably own the full scope.
- **Workaround is not a fix:** https://github.com/microsoft/vscode/issues/279150 is CLOSED after the reporter confirmed that explicitly setting npm.scriptRunner resolved their unwanted Yarn invocation. That workaround matches this report's existing workaround but does not provide automatic per-package detection for mixed-package-manager repositories.
