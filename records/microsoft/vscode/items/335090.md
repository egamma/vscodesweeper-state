# Issue #335090 — Change flow when viewing .code-workspace file contents

[https://github.com/microsoft/vscode/issues/335090](https://github.com/microsoft/vscode/issues/335090)

## Summary

A real workspace-opening UX gap remains: the editor's Open Workspace button follows the normal folder/window reuse policy even when the current window contains unrelated or dirty editors. No older open issue found in the canonical search reports this same observable behavior.

## Change summary

Open a .code-workspace file in a new window when the current window contains other editors, preserving the current ad hoc window and its unsaved contents.

## Best solution

Make the Open Workspace editor action preserve a populated current window by opening the selected workspace separately, while retaining the lightweight current-window flow when the .code-workspace file is effectively the window's only content. The workspace owner should decide how this contextual safeguard interacts with an explicit `window.openFoldersInNewWindow: off` preference.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/workspaces/browser/workspaces.contribution.ts`, `src/vs/workbench/browser/workbench.contribution.ts`
- **Validation:** Exercise the Open Workspace editor button in two scenarios: with the .code-workspace file as the only editor, and with an additional dirty editor. Confirm the latter opens a separate workspace window without prompting or changing the original editor, then repeat with `window.openFoldersInNewWindow` set explicitly to `off` and verify the behavior chosen by the maintainer.
- **Behavior:**

  > Opening a .code-workspace file through its editor button must not unexpectedly replace a window that contains other working editors. When another editor, including a dirty editor, is present, the workspace should open separately and the original window and edits must remain intact. The existing lightweight behavior when the workspace file is the only editor should remain available. Acceptance must cover both default settings and the chosen semantics for an explicit `window.openFoldersInNewWindow: off` preference.
- **Trace:**

  > The button is `workbench.action.openWorkspaceFromEditor` in src/vs/workbench/contrib/workspaces/browser/workspaces.contribution.ts. Its `run` method checks only whether the same workspace is already open and then calls `IHostService.openWindow` without window-placement options or editor-state awareness. Desktop placement is consequently decided by `WindowsMainService.shouldOpenNewWindow` in src/vs/platform/windows/electron-main/windowsMainService.ts; web uses the analogous `BrowserHostService.shouldReuse` path. Both consult `window.openFoldersInNewWindow`, whose default permits an in-application workspace open to reuse the current window. The boundary is this editor-button flow: ordinary File > Open Workspace, CLI opening, explicit new-window commands, save-prompt wording, and the meaning of Don't Save should not change.
- **Open decisions:**
  - When other editors are present, should the editor-button safeguard override an explicit `window.openFoldersInNewWindow: off` preference, or should that explicit reuse choice remain authoritative?

## Evidence

- **current action path:** src/vs/workbench/contrib/workspaces/browser/workspaces.contribution.ts registers `workbench.action.openWorkspaceFromEditor`; its `run` method calls `hostService.openWindow([{ workspaceUri: uri }])` without `forceNewWindow` or `preferNewWindow` and without considering other open editors.
- **current window policy:** src/vs/platform/windows/electron-main/windowsMainService.ts (`shouldOpenNewWindow`) and src/vs/workbench/services/host/browser/browserHostService.ts (`shouldReuse`) resolve workspace opens through `window.openFoldersInNewWindow`; the default in src/vs/workbench/browser/workbench.contribution.ts allows in-application workspace opens to replace the current window.
- **partial existing capability:** Setting `window.openFoldersInNewWindow` to `on` globally opens folders and workspaces in new windows, and `workbench.action.openWorkspaceInNewWindow` exists in src/vs/workbench/browser/actions/workspaceCommands.ts. Neither provides the requested contextual behavior for the Open Workspace button based on whether other editors are present.
