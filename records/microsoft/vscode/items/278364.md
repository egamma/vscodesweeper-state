# Issue #278364 — Monaco editor hijacks all input context menus

[https://github.com/microsoft/vscode/issues/278364](https://github.com/microsoft/vscode/issues/278364)

## Summary

The reported interception remains reproducible from current source when an embedding application supplies document.body as its workbench container. Keep this accepted bug open; the supported boundary between workbench inputs and host-application inputs needs clarification before implementation.

## Change summary

Preserve host-application input context menus when Monaco and workbench components share a document with unrelated inputs.

## Best solution

Provide a supported way for embedded workbench applications to preserve unrelated inputs' context menus while retaining workbench menus, including the Problems panel. Establish the ownership boundary first, without changing ordinary VS Code input menus.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/actions/textInputActions.ts`, `src/vs/platform/layout/browser/layoutService.ts`, `src/vs/workbench/browser/layout.ts`
- **Validation:** End the plan with a browser regression test that mounts workbench and host inputs under a shared container, dispatches cancelable bubbling contextmenu events, and verifies that host-input events remain unprevented and do not invoke IContextMenuService while workbench-input events retain their menu. Manually verify that the Problems panel context menu still works in the embedding application.
- **Behavior:**

  > An application embedding Monaco and workbench components alongside unrelated inputs must be able to retain those inputs' native or host-provided context menus. Workbench input menus and the Problems panel menu must continue to function. Acceptance should cover a shared document.body container, ordinary dedicated workbench containers, and both input and textarea elements.
- **Trace:**

  > TextInputActionsProvider.registerListeners in src/vs/workbench/browser/actions/textInputActions.ts attaches to every layout-service container. Its onContextMenu handler distinguishes inputs and textareas from other targets, but does not distinguish host inputs from workbench inputs before preventing the event and invoking IContextMenuService. This conclusively explains the trigger described in https://github.com/microsoft/vscode/issues/278364 when mainContainer is document.body. The layout-service interface describes an application container, whereas the standard workbench creates a dedicated div in src/vs/workbench/browser/layout.ts. The unresolved boundary is how an embedding application identifies host-owned inputs when it deliberately shares that container; its wrapper implementation is not present in the evidence. Preserve standard workbench behavior, auxiliary-container handling, existing defaultPrevented handling, and non-input context menus.
- **Open decisions:**
  - Should embedded applications explicitly designate inputs or regions that retain host context menus, or should workbench input-menu handling be restricted to designated workbench-owned regions when the layout container is shared?

## Evidence

- **Current interception path:** src/vs/workbench/browser/actions/textInputActions.ts:76-104 registers a bubbling contextmenu listener on layoutService.mainContainer and subsequently added containers. For any input or textarea whose event is not already defaultPrevented, onContextMenu calls EventHelper.stop(e, true) and shows the workbench menu. With document.body supplied as the container, an unrelated input follows this exact path.
- **Existing escape hatch is insufficient:** TextInputActionsProvider.onContextMenu skips events already marked defaultPrevented, but that is not a way to preserve the browser's native context menu: preventing the event also suppresses that menu. The provider has no configuration dependency or host-input ownership check.
- **Embedding boundary:** src/vs/platform/layout/browser/layoutService.ts documents mainContainer as the application's main container. Standard VS Code instead creates a dedicated div in src/vs/workbench/browser/layout.ts:205. The reporter's body-based container is therefore an embedding-specific condition, not the standard workbench layout; the wrapper's claimed document.body default was not independently verified.
