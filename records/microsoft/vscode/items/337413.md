# Issue #337413 — Agent Host: verify OTLP trace endpoint routing and governed identity

[https://github.com/microsoft/vscode/issues/337413](https://github.com/microsoft/vscode/issues/337413)

## Summary

Team-authored follow-up to the just-merged governed-identity PR (#336814); tracing the source confirms the reported defect: the traces signal endpoint is built inconsistently with the logs/metrics endpoints, so a bare base URL supplied for OTLP traces is posted verbatim instead of getting `/v1/traces` appended. Real, unfixed work — stays open.

## Change summary

Verify and correct base-vs-signal OTLP trace endpoint routing, and independently validate governed identity capture (denial/re-enable/restart) against a real OpenTelemetry Collector.

## Best solution

Apply the same base-vs-signal URL resolution already used for logs/metrics (`resolveSignalEndpoint` in claudeSdkOptions.ts/codexLaunchConfig.ts, `resolveCopilotOtlpMetricsEndpoint` in copilotAgent.ts, and the DB-mode `${receiver.baseUrl}/v1/traces` construction in agentHostOTelService.ts) to the traces endpoint in the external/passthrough path too, so all three harnesses treat a bare base URL the same way for traces as they already do for logs and metrics; then separately validate governed identity capture end-to-end against a live collector.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/otel/agentHostOTelService.ts`, `src/vs/platform/agentHost/node/claude/claudeSdkOptions.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/platform/agentHost/node/codex/codexLaunchConfig.ts`, `src/vs/platform/otel/node/otlp/outboundForwarder.ts`
- **Validation:** A unit test (alongside the existing claudeSdkOptions.test.ts / agentHostOTelService.integrationTest.ts) asserting that a bare base `OTLP` endpoint, when routed to the traces env var/exporter config for each harness, resolves to `.../v1/traces` the same way logs/metrics already resolve to `.../v1/logs` and `.../v1/metrics`; ideally cross-checked once against a real OpenTelemetry Collector as the issue requests.
- **Behavior:**

  > When a user configures a bare base OTLP endpoint (e.g. `http://localhost:4318`) for OTel export, the traces signal should reach the collector at `.../v1/traces`, exactly as logs and metrics already reach `.../v1/logs` and `.../v1/metrics` today. Explicit/custom full URLs, policy precedence, authentication headers, and existing DB-mode (loopback receiver) trace routing must be unaffected. Acceptance: a test collector receiving traces posted through the non-DB (external/passthrough) native config path sees requests at `/v1/traces`, not `/`.
- **Trace:**

  > Root cause: agentHostOTelService.ts's getNativeSdkTelemetryConfig() only builds a full `/v1/traces` URL when the local loopback receiver (DB mode) is active; in the external/passthrough branch it returns the user's raw `otlpEndpoint` for `traces` unmodified. Each harness (claudeSdkOptions.ts, copilotAgent.ts, codexLaunchConfig.ts) then writes that raw value straight into the signal-specific traces env var/exporter config, while all three already run the exact same class of endpoint through a base-vs-signal resolver (`resolveSignalEndpoint` / `resolveCopilotOtlpMetricsEndpoint`) for logs and metrics — so the inconsistency is isolated to the traces signal only. `src/vs/platform/otel/node/otlp/outboundForwarder.ts:resolveOtlpTracesEndpoint()` is an existing, already-tested implementation of the exact correction needed. Do not touch DB-mode trace routing (already correct) or the logs/metrics resolution paths (already correct); do not rewrite explicit/custom full-path URLs, which the existing helpers already leave verbatim. Related: https://github.com/microsoft/vscode/pull/336814 (merged, governed identity capture — keep separate per the issue's own instruction).
- **Open decisions:**
  - Should the traces-endpoint fix land as one shared helper reused by all three harnesses (mirroring resolveOtlpTracesEndpoint), or should each harness keep its own local resolver as logs/metrics do today?
  - Is the governed-identity validation (denial, re-enable, restart) part of the same change, or a separate follow-up issue/PR, given it needs a live OTel Collector and is largely a test/verification task rather than a code fix?

## Evidence

- **DB-mode builds full path:** src/vs/platform/agentHost/node/otel/agentHostOTelService.ts getNativeSdkTelemetryConfig() (lines ~307-332): when the loopback receiver is active it explicitly returns `traces: { endpoint: `${this._receiver.baseUrl}/v1/traces`, ... }`, but when dbSpanExporter is off it falls back to `external` = `{ endpoint: this._config.otlpEndpoint, ... }` — the raw, unmodified user-configured base endpoint, with no signal path appended.
- **Claude harness sets it verbatim:** src/vs/platform/agentHost/node/claude/claudeSdkOptions.ts line 343 sets `env.OTEL_EXPORTER_OTLP_TRACES_ENDPOINT = config.traces.endpoint` verbatim, while the file's own `resolveSignalEndpoint()` helper (used only for logs/metrics, lines 369-378) already knows how to append `/v1/{signal}` to a bare base URL.
- **Copilot harness same pattern:** src/vs/platform/agentHost/node/copilot/copilotAgent.ts lines 2444-2447 sets `env['OTEL_EXPORTER_OTLP_TRACES_ENDPOINT'] = nativeTelemetry.traces.endpoint` raw, while `resolveCopilotOtlpMetricsEndpoint()` (lines 616-628) performs the equivalent bare-base-URL correction for metrics only.
- **Codex harness same pattern:** src/vs/platform/agentHost/node/codex/codexLaunchConfig.ts line 154 passes `config.traces` straight into `codexExporter()` unmodified, while lines 155-156 wrap logs/metrics endpoints through `resolveSignalEndpoint()` (lines 175-188).
- **existing precedent for the fix:** src/vs/platform/otel/node/otlp/outboundForwarder.ts `resolveOtlpTracesEndpoint()` (lines 54-73) already implements exactly this base-vs-signal correction for the DB-mode forwarder, so the fix pattern for the native/passthrough traces path already exists in the codebase.
