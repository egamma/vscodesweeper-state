# Issue #133961 — Sparse top level menu when no window is opened

[https://github.com/microsoft/vscode/issues/133961](https://github.com/microsoft/vscode/issues/133961)

## Summary

The accepted Backlog request remains unimplemented on current main: after the last macOS window closes, VS Code deliberately retains only the application, File, Window, and Help menus. The remaining top-level entries are still omitted rather than preserved in a disabled state.

## Change summary

Keep the full macOS top-level menu visible when no VS Code window is open, with unavailable commands disabled.

## Best solution

Preserve the normal macOS menu topology after the last window closes while disabling commands that require a workbench window and retaining the existing safe fallback actions such as opening a new window or folder.

## Plan brief

- **Likely files:** `src/vs/platform/menubar/electron-main/menubar.ts`
- **Validation:** On macOS, open VS Code, close its final window without quitting, and verify that every normal top-level menu remains visible; commands requiring a workbench window are disabled, existing no-window fallback commands remain usable, and reopening a window restores normal enablement.
- **Behavior:**

  > After the final VS Code window closes on macOS, the application menu retains the same top-level entry points shown while a window is open. Commands that require a workbench window are disabled, while established no-window actions such as creating a window or opening a file or folder remain available. Reopening a window restores the normal enabled menu state without duplicate or stale entries.
- **Trace:**

  > The native application menu is assembled by Menubar.install in src/vs/platform/menubar/electron-main/menubar.ts. Menubar.onDidChangeWindowsCount marks `closedLastWindow` and schedules a rebuild; Menubar.shouldDrawMenu then retains File, Help, and Window in that state but excludes Edit, Selection, View, Go, Run, and Terminal through its default window-count check. Menubar.setMenu already has a no-window fallback path that disables ordinary actions and preserves registered fallback handlers. The boundary is the macOS zero-main-window state: native menus on other platforms, auxiliary-window menu behavior, and the existing fallback actions must remain unchanged.

## Evidence

- **current source:** In src/vs/platform/menubar/electron-main/menubar.ts, Menubar.shouldDrawMenu permits File, Help, and Window when `getWindowCount() === 0 && closedLastWindow`, while its default branch requires a window count greater than zero; Edit, Selection, View, Go, Run, and Terminal therefore remain absent.
- **existing no-window behavior:** Menubar.setMenu in src/vs/platform/menubar/electron-main/menubar.ts already disables ordinary actions in the no-window fallback state and preserves selected fallback handlers, but this logic is reached only for top-level menus that shouldDrawMenu includes.
