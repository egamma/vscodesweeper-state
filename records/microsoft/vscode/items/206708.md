# Issue #206708 — javascript and typescript: "conditions" configuration setting for conditional export resolution in package.json

[https://github.com/microsoft/vscode/issues/206708](https://github.com/microsoft/vscode/issues/206708)

## Summary

Keep this accepted, community-supported request open: TypeScript's customConditions provides project-level resolution, but current VS Code has no equivalent editor setting. The remaining request is editor-specific conditions without changing build configuration, not conditional-export support generally.

## Change summary

Allow JavaScript and TypeScript language features to select configurable package.json export/import conditions independently of build configuration.

## Best solution

Define an opt-in conditions setting in the built-in TypeScript language-features extension that supports source navigation and IntelliSense without changing runtime or build resolution. Settle its interaction with explicit tsconfig.json/jsconfig.json conditions before implementation.

## Plan brief

- **Likely files:** `extensions/typescript-language-features/package.json`, `extensions/typescript-language-features/package.nls.json`, `extensions/typescript-language-features/src/configuration/configuration.ts`, `extensions/typescript-language-features/src/tsconfig.ts`, `extensions/typescript-language-features/src/typescriptServiceClient.ts`
- **Validation:** Use a workspace package whose exports and #imports map a development condition to source and the normal import condition to dist. With editor conditions enabled, verify completions and Go to Definition resolve source both with dist absent and with stale dist present; disable the setting and verify ordinary resolution returns. Verify tsconfig/jsconfig and command-line build behavior remain unchanged, and exercise explicit customConditions according to the agreed precedence.
- **Behavior:**

  > Developers need JavaScript and TypeScript IntelliSense and navigation to follow selected development conditions in package.json exports and imports without generating dist files or source maps. The requested editor configuration should remain effective when stale dist files exist and should not alter command-line build or runtime conditions. Acceptance checks should cover source navigation, completions, exports, imports, and restoring ordinary resolution when the setting is disabled. Its interaction with project-defined customConditions must be explicit.
- **Trace:**

  > The built-in extension's package.json and ImplicitProjectConfiguration in extensions/typescript-language-features/src/configuration/configuration.ts expose no customConditions setting. inferredProjectCompilerOptions in src/tsconfig.ts builds inferred-project compiler options; TypeScriptServiceClient.setCompilerOptionsForInferredProjects in src/typescriptServiceClient.ts sends those through compilerOptionsForInferredProjects, while serviceStarted separately sends configure preferences. These paths establish the current inferred-project boundary but do not establish how editor-only conditions could affect configured projects. TypeScript already supports project-level customConditions, as documented in https://www.typescriptlang.org/tsconfig/customConditions.html and discussed at https://github.com/microsoft/vscode/issues/206708#issuecomment-2530143239. The unresolved technical question is how to apply the agreed editor behavior to configured projects, potentially requiring TypeScript language-service cooperation. Preserve package export ordering and normal runtime/build semantics; this is not a request to change extension-host module loading.
- **Open decisions:**
  - Should the editor setting apply to configured projects as well as inferred projects? Inferred-project-only support would not cover the reported monorepo workflow.
  - For configured projects, should editor-selected conditions augment or replace compilerOptions.customConditions, and how should conflicts be resolved?

## Evidence
