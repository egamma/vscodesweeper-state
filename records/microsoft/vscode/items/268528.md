# Issue #268528 — Copilot agent fails to execute commands in ssh - impossible to work with remotely accessed shells

[https://github.com/microsoft/vscode/issues/268528](https://github.com/microsoft/vscode/issues/268528)

## Summary

Keep open as the established tracking issue for agent execution inside SSH-like subshells. Current interactive-input tools and manual shell-integration workarounds provide partial coverage, but do not establish automatic support for the reported workflow.

## Change summary

Allow Copilot to execute commands in an existing SSH session, interactive container shell, or cmd terminal rather than switching to a new PowerShell terminal.

## Best solution

Provide an explicit, reliable terminal-agent contract for targeting an existing interactive shell and reporting command completion when inner-shell integration is absent. Preserve this issue as the canonical discussion, and settle automatic detection versus explicit targeting before implementation.

- **Behavior:**

  > The reporter requests continued agent execution in the shell they are actually using after entering SSH, an interactive container, or cmd. The current workflow can instead select another PowerShell terminal or treat the inner session as a continuing outer-shell command. Acceptance should demonstrate correct shell targeting, usable output retrieval, and truthful completion reporting without requiring users to disable integration globally. The plan must first retest the supplied Windows workflow against today's interactive-input tools.
- **Trace:**

  > The maintainer diagnosis in https://github.com/microsoft/vscode/issues/268528#issuecomment-3418797884 identifies the missing inner-shell integration boundary. RunInTerminalTool._initTerminal in src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/tools/runInTerminalTool.ts works with session-associated terminals and otherwise creates a Copilot-profile terminal. ToolTerminalCreator.refreshShellIntegrationQuality only upgrades detected quality, and RunInTerminalTool._createStrategy chooses none/basic/rich execution from that quality. SendToTerminalTool in browser/tools/sendToTerminalTool.ts can send input and wait for idle output, but only for an execution registered with RunInTerminalTool, so its existence does not prove coverage of a manually entered session. The uncertainty starts at how users identify the intended inner shell and what completion guarantee is possible without its integration. Preserve ordinary shell execution, parallel background terminals, and existing command confirmations; this concerns SSH inside a terminal, not an extension-owned Remote-SSH defect.
- **Open decisions:**
  - Should agents automatically recognize and continue inside a manually entered subshell, or require the user to explicitly select that terminal for agent interaction?
  - When inner-shell integration is unavailable, should execution return clearly marked idle-output snapshots with completion unknown, or require integration before offering command-level completion guarantees?
