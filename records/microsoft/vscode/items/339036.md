# Issue #339036 — Regression - VS Code Secondary Sidebar Plugin Drop-down

[https://github.com/microsoft/vscode/issues/339036](https://github.com/microsoft/vscode/issues/339036)

## Summary

Milestone 1.142.0 is assigned, which is itself a hard keep-open rule, and the evidence independently confirms this is an upstream Electron regression, not something to close — drag-and-drop into webviews broke after the Electron 43.6.0 → 43.7.3 bump (PR #336697), traced by a collaborator to electron/electron#53750's restored SiteInstanceGroup drag-target check, and corroborated by multiple independent reporters across macOS and Windows.

## Change summary

Drag-and-drop from the Explorer into extension webviews (e.g. chat panels) stopped working after upgrading to VS Code 1.140.0.

## Best solution

Track and pull in the upstream Electron fix (or add a VS Code-side workaround in WebviewWindowDragMonitor/WebviewElement) once the interaction between the new Electron drag-target check and VS Code's shiftKey-based drag gating is understood; this is primarily an Electron-side regression that VS Code may need to work around.

## Evidence

- **upstream root cause:** The collaborator traces the behavior change to electron/electron#53750 (commit d7f36584d79, shipped in Electron 43.7.0), which restores a SiteInstanceGroup drag-target check Chromium previously bypassed via VS Code's webview_cross_drag.patch.
- **current source unchanged:** src/vs/workbench/contrib/webview/browser/webviewWindowDragMonitor.ts (HEAD 4c8b9b7a) still gates drag-through on event.shiftKey during DRAG/DRAG_OVER exactly as before; no fix for this interaction exists on main.
- **multiple reporters:** Confirmed independently on macOS and Windows by tetyos, JohanManders, and technokolya, with technokolya reproducing on 1.141.0 (Electron 43.7.7) and testing partial workarounds.
