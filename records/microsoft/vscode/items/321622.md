# Issue #321622 — agents window

[https://github.com/microsoft/vscode/issues/321622](https://github.com/microsoft/vscode/issues/321622)

## Summary

Keep open: proposed chat-session registration APIs exist, but they do not provide a stable, general extension integration with the Agents window. Related requests cover API finalization and executable agent providers; neither establishes that this session-registration request is fully covered.

## Change summary

Expose an extension API for registering extension-owned agent sessions in the Agents window.

## Best solution

Define a supported extension contract for discovering and opening extension-owned sessions in the Agents window. Coordinate with the existing session API and Agent Host extensibility work, explicitly deciding whether session presentation requires registering an executable agent runtime.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.chatSessionsProvider.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/sessions/contrib/providers/copilotChatSessions/browser/copilotChatSessions.contribution.ts`, `src/vs/sessions/contrib/providers/copilotChatSessions/browser/copilotChatSessionsProvider.ts`
- **Validation:** After the contract is agreed, use a minimal extension with a non-Copilot session type to register a session, verify it appears in the dedicated Agents window, and open it to its provider-owned conversation. For a stable API, verify this works without proposed-API runtime flags; existing Copilot Cloud sessions must remain available.
- **Behavior:**

  > Extensions should have a supported way to register their own agent sessions for the dedicated Agents window. A contributed session should be discoverable and openable there without masquerading as a Copilot session. Acceptance should use a minimal third-party session provider and preserve existing built-in session behavior. The report does not request execution-runtime registration or specify whether experimental proposed-API access is sufficient.
- **Trace:**

  > The proposed chatSessionsProvider declarations already expose session item controllers and content providers, and extHost.api.impl.ts enforces proposal access. The dedicated Agents window registers CopilotChatSessionsProvider through DefaultSessionsProviderContribution; that provider exposes fixed Copilot session types and skips non-Cloud sessions during enumeration. This establishes a presentation boundary beyond simply making a registration function available. https://github.com/microsoft/vscode/issues/340045 concerns API stabilization, while https://github.com/microsoft/vscode/issues/325827 concerns executable Agent Host providers; neither was verified to own this narrower window-integration contract. Preserve built-in provider behavior and do not assume that presenting extension-owned sessions requires adopting their execution runtimes.
- **Open decisions:**
  - Should extensions be able to contribute sessions to the Agents window independently of registering an executable Agent Host provider?
  - Should the supported session-registration contract be public and stable for Marketplace extensions, or initially available only as a proposed API?

## Evidence

- **Existing proposed capability:** src/vscode-dts/vscode.proposed.chatSessionsProvider.d.ts declares chat.createChatSessionItemController, chat.registerChatSessionItemProvider, and chat.registerChatSessionContentProvider. These are proposed APIs rather than a stable extension contract; src/vs/workbench/api/common/extHost.api.impl.ts gates each with checkProposedApiEnabled(extension, 'chatSessionsProvider').
- **Agents window integration boundary:** src/vs/sessions/contrib/providers/copilotChatSessions/browser/copilotChatSessions.contribution.ts registers a specific CopilotChatSessionsProvider. In copilotChatSessionsProvider.ts, sessionTypes exposes only Copilot Cloud or sandbox types, and the session enumeration explicitly skips sessions whose providerType is not AgentSessionProviders.Cloud. Existing chat-session registration therefore does not automatically project arbitrary extension sessions into this window.
- **Related API finalization request:** https://github.com/microsoft/vscode/issues/340045 was verified open and requests stable chatSessionsProvider access for Marketplace extensions. It establishes the proposed-versus-public API gap, but does not establish general integration with the dedicated Agents window.
- **Related runtime registration request:** https://github.com/microsoft/vscode/issues/325827 was verified open and requests complete executable Agent Host providers with SDK and lifecycle integration. Its discussion explicitly distinguishes session-provider APIs from runtime registration; this report asks only for agent-session registration, so equivalence is not established.
- **Related architectural debt:** https://github.com/microsoft/vscode/issues/290605 remains open and concerns hardcoded agent-session details. The maintainer agreement at https://github.com/microsoft/vscode/issues/290605#issuecomment-3804063799 supports contribution-driven extensibility, but removing hardcoded details alone does not deliver a public session-registration API.
