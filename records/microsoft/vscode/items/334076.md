# Issue #334076 — Chat Sessions panel loses all history except current run after tunnel restart — no state.vscdb/chat.ChatSessionStore.index fallback for agent-host storage backend

[https://github.com/microsoft/vscode/issues/334076](https://github.com/microsoft/vscode/issues/334076)

## Summary

Well-documented, code-verified gap: the chat Sessions index is workspace-storage-scoped with no fallback that rebuilds it from on-disk transcript files, so any process that gets a new workspace-storage hash (tunnel restart, CLI update) shows an empty history even though the `.jsonl` files are intact. Routing to the chat area rather than closing, since the reporter's cited related issues are unverified leads, not a confirmed canonical.

## Change summary

After a Remote Tunnel restart/reconnect changes the workspace-storage hash, the Chat Sessions panel shows only the current run's sessions; prior sessions' transcript files remain on disk but are not indexed, and there is no fallback (state.vscdb-based or agent-host-db-based) to recover them.

## Best solution

In src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts, `internalGetIndex()` returns an empty index whenever `IStorageService.get(ChatIndexStorageKey, ...)` is empty, with no directory scan of the `chatSessions`/transcripts folder to rebuild entries; consider either correlating storage roots across hash-drifted workspace-storage folders (extending `handleWorkspaceTransition`/`migrateSessionsToNewWorkspace`, which already migrates files but does not rebuild index metadata from them) or adding an index-rebuild-from-disk fallback when the stored index is empty but session files exist.

## Evidence

- **index storage is workspace-scoped:** src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts:39,432-435 — ChatIndexStorageKey is stored via IStorageService at StorageScope.WORKSPACE (or APPLICATION for empty windows); a new workspace-storage folder (new hash) starts with no data for this key.
- **no rebuild-from-disk fallback:** internalGetIndex() (lines 547-583) returns `{version:1, entries:{}}` whenever storageService.get() is empty/absent — there is no directory scan of the chatSessions/transcripts folder to reconstruct entries from existing .jsonl files; grep for rebuildIndex/scanDirectory/readdir in the file returns nothing.
- **existing migration path doesn't cover this case:** handleWorkspaceTransition/migrateSessionsToNewWorkspace (lines 99-181) only fires on an in-process workspace identity change (e.g. saving Untitled Workspace as .code-workspace, matching https://github.com/microsoft/vscode/issues/301793) and even there only copies files and flushes the (still-empty) indexCache without rebuilding index metadata from the copied files — it would not help across separate process restarts with a drifted hash anyway.
- **reporter's own related-issue leads (unverified):** Issue body cites #297247, #285059, #305818, and microsoft/vscode-remote-release#11207 as prior reports of the same workspaceStorage hash-drift pattern; without gh auth I could not confirm their current state or exact scope, so I'm not proposing a duplicate close on an unverified lead.
