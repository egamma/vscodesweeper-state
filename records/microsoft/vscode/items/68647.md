# Issue #68647 — Allow dynamic location of textmate grammar

[https://github.com/microsoft/vscode/issues/68647](https://github.com/microsoft/vscode/issues/68647)

## Summary

Keep open: current grammar contributions still use static extension-relative paths, and semantic-token APIs do not provide dynamic TextMate grammar registration. The existing api routing is appropriate; the supported extension use cases warrant an API design discussion rather than a staleness close.

## Change summary

Allow extensions to supply configuration-dependent syntax grammars without rewriting their installed extension files.

## Best solution

Provide an extension-facing contract for configuration-dependent grammar content or registration, with explicit activation, fallback, and update semantics. Preserve bundled highlighting before activation and avoid requiring mutable files inside installed extensions.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/services/textMate/common/TMGrammars.ts`, `src/vs/workbench/services/textMate/browser/textMateTokenizationFeatureImpl.ts`, `src/vs/workbench/services/textMate/common/TMGrammarFactory.ts`, `src/vs/workbench/services/textMate/browser/backgroundTokenization/threadedBackgroundTokenizerFactory.ts`
- **Validation:** Use a sample extension with a bundled Vue grammar and configurable custom-block language. Verify the agreed fallback before activation, configuration-dependent highlighting after registration, the agreed live-update or reload behavior, and restoration after disposal or reload, without modifying the installed extension directory; check equivalent behavior with background tokenization enabled.
- **Behavior:**

  > Extensions need to provide configuration-dependent syntax highlighting without overwriting installed extension assets. A Vue custom block such as <docs> must be highlightable as the language selected by the user's configuration, and generated grammars must support cases that cannot be covered by a finite set of bundled variants. Acceptance must establish what users see before activation, when configuration changes, and when the supplying extension is disposed or the window reloads.
- **Trace:**

  > TMGrammars.ts defines static contributes.grammars entries with required scopeName and path. TextMateTokenizationFeatureImpl._handleGrammarsExtPoint recreates tokenization registrations from those entries, while _validateGrammarDefinition resolves paths against the extension location. TMGrammarFactory loads and parses the resulting resources; grammar definitions also feed ThreadedBackgroundTokenizerFactory. The public semantic-token registration APIs provide token classifications, not dynamic TextMate grammar replacement. The unresolved boundary is the public registration, activation, and persistence contract, not a missing guard in one loader. Preserve existing static contributions and ordinary highlighting; do not require extensions to mutate their installation. Related semantic embedded-language work at https://github.com/microsoft/vscode/issues/81558 is not a duplicate of this request.
- **Open decisions:**
  - Should the public contract expose TextMate-specific grammar registration, or a more general dynamic syntax-highlighting capability?
  - Should configuration-dependent grammars apply immediately to already-open documents, or is an explicit window reload an acceptable contract?
  - Should generated grammar selection persist across reloads and apply before extension activation, or should bundled highlighting remain the fallback until each activation?
