# Issue #163593 — Custom URLs for non-theme extensions

[https://github.com/microsoft/vscode/issues/163593](https://github.com/microsoft/vscode/issues/163593)

## Summary

Keep this accepted request open: existing theme-preview URLs and extension URI infrastructure do not establish a general vscode.dev onboarding URL for non-theme extensions. The maintainer explicitly parked this issue to gauge interest, and no verified older open canonical or concrete implementation was found.

## Change summary

Allow extension authors to share vscode.dev URLs that launch a playground with their non-theme web extension available.

## Best solution

Define a supported, consent-aware vscode.dev URL contract for non-theme extension onboarding, including whether it can open a target repository and invoke an extension entry point. Reuse the existing installation and URI-dispatch infrastructure rather than treating theme previews as sufficient coverage.

## Plan brief

- **Likely files:** `src/vs/workbench/services/url/browser/urlService.ts`, `src/vs/workbench/services/extensions/browser/extensionUrlHandler.ts`, `src/vs/workbench/browser/web.api.ts`
- **Validation:** After choosing the public URL contract, open a generated link in a fresh browser profile for a compatible non-theme extension and sample repository; verify the agreed consent, extension availability, and repository-opening behavior, including cancellation and an unavailable or web-incompatible extension.
- **Behavior:**

  > Extension authors want a shareable vscode.dev link that lets a new user try a non-theme web extension with a representative playground, without separately locating and installing it. Existing theme-preview links do not cover executable extensions. Acceptance should exercise a fresh browser profile, the agreed user confirmation flow, successful onboarding, and cancellation without unintended installation.
- **Trace:**

  > The request inherits its concrete onboarding scenario from https://github.com/microsoft/vscode/issues/139839, and the maintainer retained https://github.com/microsoft/vscode/issues/163593 to gauge interest. ExtensionUrlHandler.handleURL and handleUnhandledURL in src/vs/workbench/services/extensions/browser/extensionUrlHandler.ts already support extension lookup, installation justification, and URI activation. BrowserURLService in src/vs/workbench/services/url/browser/urlService.ts depends on an embedding-provided callback provider, while src/vs/workbench/browser/web.api.ts exposes host-controlled extension provisioning options. The trace does not establish a public vscode.dev route or where its deployment-side routing would be implemented. Existing theme previews, normal URI handling, and ordinary extension installation should remain unchanged. The younger related request https://github.com/microsoft/vscode/issues/228421 adds explicit extension-entry-point expectations and is useful design context, not an eligible duplicate target.
- **Open decisions:**
  - Should the public link provide a temporary extension trial or a persistent installation in the user's browser profile?
  - Should the supported URL only make an extension available, or also select a playground repository and invoke an extension-defined entry point?
  - What confirmation must a new user see before a shared URL installs or activates a non-theme extension?
