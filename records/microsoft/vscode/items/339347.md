# Issue #339347 — Automations can't switch between remote and local folders

[https://github.com/microsoft/vscode/issues/339347](https://github.com/microsoft/vscode/issues/339347)

## Summary

Team-authored bug report (protected from judgment closes) describing a UX issue in the Automations dialog: switching a remote-folder automation to a local folder trips the 'cannot use this workspace' validation error, while switching to 'No workspace' does not. I traced a plausible cause in the session-type availability check but could not confirm the exact root cause without running the UI, so this stays open pending diagnosis.

## Change summary

Editing an automation with a remote folder selected and switching the folder to a local one triggers an incorrect/unhelpful 'cannot use this workspace' validation error.

## Best solution

Likely needs either auto-resetting/re-resolving the session type (providerId/sessionTypeId) when the folder target changes in the automation dialog, or a clearer validation message distinguishing 'stale session type needs reselecting' from a true incompatibility — the right fix should be decided by whoever owns src/vs/sessions/contrib/automations/browser/automationDialog.ts.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/automations/browser/automationDialog.ts`, `src/vs/sessions/services/sessions/browser/sessionsManagementService.ts`
- **Validation:** A test (or manual repro) that creates/edits an automation with a remote folder and a remote-specific session type selected, switches the folder to a local path, and asserts the dialog either auto-selects a valid session type or surfaces a clear, actionable message instead of the current generic 'cannot use this workspace' error.
- **Trace:**

  > Validation in automationDialog.ts (~line 1811) calls sessionsManagementService.isNewSessionTargetAvailable(folderUri, { providerId, sessionTypeId }), which (sessionsManagementService.ts:384-397) fails when the currently-selected provider/session type isn't offered for the new folder. Switching to 'No workspace' instead routes through isQuickChatTargetAvailable, which has no such providerId/sessionTypeId constraint, which may explain the asymmetry. Not yet confirmed by actually running the dialog or stepping through folder-switch state transitions in isolationModel.
- **Open decisions:**
  - Should switching the automation's folder auto-reset/re-resolve the provider and session type to one valid for the new workspace, or should the user be required to manually reselect?
  - If reselection is required, should the error message explicitly say the current session type is unavailable for this workspace and prompt the user to pick a new one, rather than the generic 'cannot use this workspace' text?

## Evidence

- **availability check:** src/vs/sessions/services/sessions/browser/sessionsManagementService.ts:384-397 isNewSessionTargetAvailable/_isTargetAvailable returns false if the currently selected providerId/sessionTypeId isn't among the session types available for the new folder (e.g. a remote-only provider staying selected after switching to a local folder) — plausible root cause, but not confirmed by execution.
