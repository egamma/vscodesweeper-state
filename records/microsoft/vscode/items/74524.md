# Issue #74524 — Add support to distinguish between diagnostics created by a reconciler and a builder

[https://github.com/microsoft/vscode/issues/74524](https://github.com/microsoft/vscode/issues/74524)

## Summary

Keep open: current diagnostic APIs still lack a builder-versus-reconciler distinction, and the task restoration workaround does not provide it. This team-authored, accepted API request remains distinct from the older problem-restoration report that prompted it.

## Change summary

Distinguish build diagnostics from live reconciler diagnostics sharing an owner so their lifecycles can be coordinated without stale, missing, or duplicate problems.

## Best solution

Agree on an explicit diagnostic provenance contract and its precedence/restoration semantics across the extension API, marker service, and task collectors. Preserve existing behavior for producers that do not supply the new metadata.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/platform/markers/common/markers.ts`, `src/vs/workbench/contrib/tasks/common/problemCollectors.ts`, `src/vs/workbench/contrib/tasks/common/problemMatcher.ts`
- **Validation:** The plan should end with automated marker/task tests covering build and reconciler diagnostics for the same owner and resource: opening a file, receiving live updates, closing the file, and preserving legacy producers without provenance metadata. Verify the agreed precedence and restoration behavior without relying on timing-dependent replay.
- **Behavior:**

  > Build diagnostics and live reconciler diagnostics sharing an owner must be distinguishable so one producer cannot accidentally erase or leave stale results from the other. The recorded maintainer direction is for live diagnostics to take precedence while a file is open and remembered build diagnostics to become applicable when it closes. Acceptance must cover both producer types on the same resource and compatibility with existing producers that provide no provenance metadata.
- **Trace:**

  > Diagnostic and DiagnosticTag in src/vscode-dts/vscode.d.ts expose no builder/reconciler discriminator; the internal IMarkerData and MarkerTag contracts in src/vs/platform/markers/common/markers.ts likewise do not express that distinction. ProblemMatcher.owner and applyTo in src/vs/workbench/contrib/tasks/common/problemMatcher.ts select ownership and document applicability, not producer lifecycle. WatchingProblemCollector in src/vs/workbench/contrib/tasks/common/problemCollectors.ts currently handles part of file-close restoration using cached output and a timed marker-change listener. https://github.com/microsoft/vscode/issues/61140#issuecomment-496217510 records the intended lifecycle direction, while https://github.com/microsoft/vscode/issues/74524 leaves the public metadata representation unsettled. The trace establishes the capability gap but not a complete transport and storage design; enumerate those consumers during planning. Preserve legacy diagnostics and keep edit-tracking changes from https://github.com/microsoft/vscode/issues/102724 outside this request.
- **Open decisions:**
  - Should extension authors identify builder/reconciler provenance through DiagnosticTag values or a dedicated diagnostic property, and what values form that public contract?
