# Issue #334437 — Copilot Chat cannot resolve installed custom skills

[https://github.com/microsoft/vscode/issues/334437](https://github.com/microsoft/vscode/issues/334437)

## Summary

Traced the root cause in the extensions/copilot source: when a workspace has enough custom skills that their descriptions exceed a 15,000-character prompt budget, the remaining skills are only listed by name in free text and never get an XML `<skill><file>` entry in the customizations index, so the skill tool's resolver — which only looks up names against that index — genuinely can't find them, exactly matching the reported error.

## Change summary

Copilot's `skill` tool throws "Skill not found" for custom skills beyond roughly the first 15, even though they are listed as invocable by name in the prompt.

## Best solution

Have the truncation logic in automaticInstructionsCollector.ts still emit a minimal `<skill><name>/<file>` entry (without the full description) for every skill that gets named in the "Additional skills available" overflow list, so resolveSkillUri in skillTool.ts can find them regardless of the description char budget; a maintainer should weigh the token-cost tradeoff of always including all skill file paths versus a resolver fallback that scans skill folders directly.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/promptFiles/node/automaticInstructionsCollector.ts`, `extensions/copilot/src/extension/tools/node/skillTool.ts`, `extensions/copilot/src/platform/customInstructions/common/customInstructionsService.ts`
- **Validation:** A test invoking the `skill` tool for a skill name that falls past the description char budget (e.g. the 20th of 20 skills with long descriptions) should resolve and load successfully instead of throwing "Skill not found".
- **Behavior:**

  > Any custom skill that is discovered and listed as an available skill to the model — whether shown with a full description or only named in the "Additional skills available" overflow text — must be resolvable and loadable via the `skill` tool by name. Today, skills pushed past the internal character budget are named but not resolvable, producing a "Skill \"X\" not found" tool error even though the skill is installed and valid. Acceptance: invoking any skill named anywhere in the generated skills section of the prompt (full or overflow) succeeds; skills genuinely absent from the workspace still correctly error.
- **Trace:**

  > automaticInstructionsCollector.ts (extensions/copilot/src/platform/promptFiles/node/automaticInstructionsCollector.ts, ~lines 500-538) builds the `<skills>` XML block fed into the customizations index; once accumulated skill entries exceed SKILL_DESCRIPTION_CHAR_BUDGET (15000 chars) it stops emitting `<skill><file>` blocks and instead appends a plain-text list of remaining skill names with no file path. customInstructionsService.ts's InstructionIndexFile.skills getter (~line 552) only extracts URIs from `<skill><file>` entries, so those overflow names are absent from the parsed index. skillTool.ts's resolveSkillUri (~line 226) searches only that index and throws when a name isn't present — this is the exact failure path and error text reported. Do not touch the skill-discovery (`getSkills`) or SKILL.md parsing logic — those already find all installed skills correctly; the gap is purely in the index truncation vs. resolver lookup.
- **Open decisions:**
  - Should every discovered skill always get a minimal `<file>` index entry (guaranteeing resolvability) even when its description is omitted from the prompt for budget reasons, accepting the added prompt/token cost at scale?
  - Alternatively, should the skill tool's resolver fall back to scanning skill folders on disk directly when a name isn't in the truncated index, and if so how should name collisions across storages (workspace/personal/extension) be resolved?

## Evidence

- **truncation logic:** extensions/copilot/src/platform/promptFiles/node/automaticInstructionsCollector.ts:500-538 stops emitting full `<skill>...<file>...</file></skill>` blocks once SKILL_DESCRIPTION_CHAR_BUDGET (15000 chars) is exceeded, and instead pushes a plain-text line `Additional skills available (invoke by name): name1, name2...` for the rest — these names never get a `<file>` tag.
- **index parsing:** extensions/copilot/src/platform/customInstructions/common/customInstructionsService.ts:552-556 — the `skills` getter on InstructionIndexFile only extracts skill URIs via getValuesInIndexFile('skills','skill','file'), i.e. only from `<skill><file>` blocks; a name mentioned only in the overflow text is invisible to it.
- **resolver:** extensions/copilot/src/extension/tools/node/skillTool.ts:226-250 resolveSkillUri iterates `indexFile.skills` (the URIs from the index) looking for a name match, and throws `Skill "X" not found. Available skills: ...` when it isn't present — this is the exact error string and available-skills format in the report.
- **reporter data:** Reporter observed roughly the first ~15 skills work and the rest fail across multiple machines/OSes/models, consistent with a shared char-budget cutoff rather than a machine-specific issue.
