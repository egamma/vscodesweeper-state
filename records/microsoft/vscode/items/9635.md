# Issue #9635 — Problem matchers for error messages that span multiple lines

[https://github.com/microsoft/vscode/issues/9635](https://github.com/microsoft/vscode/issues/9635)

## Summary

Keep open: fixed-length patterns already concatenate message captures, but variable-length message blocks still cannot be accumulated into one diagnostic declaratively. The reopened discussion explicitly distinguishes this requirement from programmatic problem matching, and the request has 28 community upvotes.

## Change summary

Allow declarative task problem matchers to collect variable-length, multiline error messages into a single diagnostic.

## Best solution

Extend declarative problem matching to accumulate a variable number of continuation lines into one diagnostic while preserving existing loop behavior. Establish termination and location-capture semantics with the tasks maintainer before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/tasks/common/problemMatcher.ts`, `src/vs/workbench/contrib/tasks/common/problemCollectors.ts`, `src/vs/workbench/contrib/tasks/test/common/problemMatcher.test.ts`, `src/vs/workbench/contrib/tasks/test/common/problemCollectors.test.ts`
- **Validation:** Add matcher and collector tests feeding consecutive diagnostic blocks with differing continuation counts and assert exactly one marker per block containing every captured message line. Cover terminator handling, task completion, and existing loop behavior; run the targeted ProblemPatternParser, ProblemMatcher, and ProblemCollectors suites after implementation.
- **Behavior:**

  > A tasks.json problem matcher can collect a variable-length error message into one diagnostic without an extension or a fixed number of repeated patterns. Each captured continuation appears once, in order, with line breaks preserved, and adjacent diagnostics remain separate. Acceptance should cover the CMake-style location-first example and establish whether NUnit-style location-after-message blocks are supported. Existing fixed-length patterns and loops that intentionally produce multiple diagnostics must remain compatible.
- **Trace:**

  > AbstractLineMatcher.fillProblemData and appendProperty in src/vs/workbench/contrib/tasks/common/problemMatcher.ts already concatenate captures across fixed patterns. MultiLineMatcher.handle requires a buffer equal to patterns.length, while its final-pattern loop and next method clone prefix data and return independent markers for each continuation. AbstractProblemCollector.tryFindMarker and tryMatchers in src/vs/workbench/contrib/tasks/common/problemCollectors.ts consume those markers immediately; accumulating a pending diagnostic therefore crosses the matcher/collector contract. The schema currently exposes only message and loop for this behavior. The remaining uncertainty is the public configuration and lifecycle semantics, not whether fixed-length concatenation exists. Preserve established loop behavior and keep reused-terminal matching defects separate, as tracked in https://github.com/microsoft/vscode/issues/183262. The programmatic alternative at https://github.com/microsoft/vscode/issues/59337 does not replace this repository-local declarative requirement.
- **Open decisions:**
  - Should accumulation support a variable-length message before a later file/location pattern, as in NUnit output, or initially support only continuations after the location is known?
  - What configuration expresses accumulation, and what should happen to a pending diagnostic when continuation matching stops or the task ends, including treatment of blank lines and the first nonmatching line?
