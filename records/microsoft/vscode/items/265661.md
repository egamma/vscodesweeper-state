# Issue #265661 — Support for FoldingRangeProviders that don't disable indentation based folding

[https://github.com/microsoft/vscode/issues/265661](https://github.com/microsoft/vscode/issues/265661)

## Summary

Keep open: a maintainer accepted the capability and invited a contribution, and the request remains a real extension API gap under the Backlog milestone. The provider contract and precedence semantics still need a maintainer decision before implementation.

## Change summary

Allow supplemental folding range providers to contribute ranges without disabling indentation-based folding when no primary provider exists.

## Best solution

Define a secondary/supplemental folding-provider contract in the extension API, then have the editor folding orchestration combine those ranges with the selected primary provider or indentation fallback while preserving existing providers' behavior by default.

## Plan brief

- **Likely files:** `src/vs/editor/common/languages.ts`, `src/vs/editor/contrib/folding/browser/syntaxRangeProvider.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** Add folding tests covering indentation plus one secondary provider, a primary plus a secondary provider, and mixed provider registrations; verify legacy providers still replace indentation while supplemental ranges are merged without conflicting starts.
- **Behavior:**

  > Extensions can register a supplemental folding range provider whose ranges augment, rather than replace, the language's normal folding source. When no primary syntax provider exists, indentation folding remains available alongside supplemental ranges. Existing providers retain today's replacement behavior by default, and precedence is deterministic when primary and supplemental providers coexist.
- **Trace:**

  > The editor currently chooses provider-backed folding through src/vs/editor/contrib/folding/browser/syntaxRangeProvider.ts, while the public FoldingRangeProvider contract is declared in src/vscode-dts/vscode.d.ts and crosses the extension-host language-feature bridge. The issue demonstrates that merely registering a specialized provider changes unrelated base folding depending on whether another extension supplies a provider. A maintainer accepted the gap and suggested distinguishing a secondary provider in https://github.com/microsoft/vscode/issues/265661. Preserve legacy provider behavior and avoid changing indentation folding itself; uncertainty begins at the public contract and conflict/precedence semantics.
- **Open decisions:**
  - Should supplemental status be a property of `FoldingRangeProvider` or registration options exposed by `registerFoldingRangeProvider`?
  - When several providers are registered, does any primary provider suppress indentation, or can supplemental providers explicitly retain indentation alongside a primary provider?
  - How should conflicting ranges from indentation, primary providers, and supplemental providers be prioritized in the observable folding result?
