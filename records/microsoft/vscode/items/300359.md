# Issue #300359 — Add option to order models by multiplier instead of alphabetically

[https://github.com/microsoft/vscode/issues/300359](https://github.com/microsoft/vscode/issues/300359)

## Summary

Keep open: the current picker offers pinning and curated sections, but not a remembered cost-based ordering option. The older sorting requests concern different surfaces or provider-controlled ranking, so neither establishes a duplicate.

## Change summary

Let users sort the model selector by ascending request multiplier or cost and remember their selection.

## Best solution

Provide an optional, persistent cost-based ordering in the model picker while retaining the existing default presentation. Define the cost metric for credit-priced models and how the ordering interacts with pinned and suggested sections before implementation.

Manually select cost ordering, close and reopen the picker, then reload the window to confirm the preference persists and inexpensive models remain easy to find.
- **Behavior:**

  > Users should be able to choose an ordering that makes inexpensive models easy to find in the model selector, including models with a zero request multiplier. The chosen ordering should survive subsequent picker openings and window reloads. Alphabetical/default presentation should remain available. Acceptance must cover the agreed treatment of pinned sections, missing pricing and credit-priced models.
- **Trace:**

  > buildModelPickerSections in src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerTabs.ts currently uses name-based comparators with promotion and retirement precedence; no sort preference enters its options. modelPickerTabbedWidget.ts renders the resulting pinned, suggested and other sections. languageModels.ts supplies multiplierNumeric and profile-persisted pin state, while modelPickerDetails.ts exposes several distinct token-cost metrics. Pinning improves visibility but does not satisfy automatic cost ranking. Preserve provider boundaries, selectable-model gating and existing default behavior. The unresolved boundary is which pricing metric users sort by and whether sorting preserves or supersedes curated sections. Related management-view work at https://github.com/microsoft/vscode/issues/292921 and pricing discussion at https://github.com/microsoft/vscode/issues/315790 should inform consistency, not replace this selector request.
- **Open decisions:**
  - For credit-priced models, should cost ordering use a price category or a user-selected input/output metric, and how should models with unavailable or incomparable pricing appear?
  - Should cost ordering apply independently within pinned, suggested and other sections, or present a single cost-ranked list?
