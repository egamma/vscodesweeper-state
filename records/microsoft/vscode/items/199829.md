# Issue #199829 — Handle markdown links better

[https://github.com/microsoft/vscode/issues/199829](https://github.com/microsoft/vscode/issues/199829)

## Summary

Keep this localization automation request open: explicit locking comments remain supported, but the inspected core export path does not generate protection for markdown links automatically. The closed example addressed one translated notification, not this broader request.

## Change summary

Automatically protect markdown link syntax during localization instead of requiring locking comments on every message.

## Best solution

Establish automatic markdown-link protection across core and extension localization exports while keeping link labels translatable and preserving existing explicit locks. A maintainer-led plan should settle detection and protection semantics and confirm the extension tooling's behavior.

## Plan brief

- **Likely files:** `build/lib/i18n.ts`, `build/lib/test/i18n.test.ts`
- **Validation:** Extend XLF export tests with unannotated markdown links, placeholder destinations, multiple links, explicit locking comments and ordinary non-markdown strings. Verify automatic protection preserves the ]( boundary without freezing translated link labels, and confirm equivalent output through the extension export path; finish with a translation round-trip that retains a renderable link.
- **Behavior:**

  > Localized markdown links should retain valid link syntax without developers manually adding locking comments to every message. Translators must still be able to translate visible link labels. Acceptance should cover literal and placeholder destinations, multiple links and existing explicit locks across core and extension messages. Ordinary text and non-link localization behavior must remain unchanged.
- **Trace:**

  > In build/lib/i18n.ts, XLF.addFile obtains notes only from explicitly supplied LocalizeInfo.comment values, and addStringItem writes those notes into XLIFF; the inspected core path does not infer markdown protection from message contents. createXlfFilesForExtensions collects package, NLS metadata and l10n bundle inputs and delegates XLIFF generation to @vscode/l10n-dev.getL10nXlf, whose behavior remains to be traced. build/lib/test/i18n.test.ts already exercises keys/messages-to-XLF conversion. The motivating French notification and maintainer request for automation are recorded at https://github.com/microsoft/vscode/issues/199715. Keep translated labels, message identity and existing explicit lock behavior intact; this is localization protection, not a change to runtime markdown parsing. The unresolved boundary is which markdown forms receive automatic protection and whether literal markdown-like text needs an escape mechanism.
- **Open decisions:**
  - Should automatic protection apply to every localization string containing recognizable markdown links, or only messages explicitly identified as markdown, with a way to leave literal markdown-like text unprotected?

## Evidence

- **Existing capability and remaining gap:** build/lib/i18n.ts, XLF.addFile and addStringItem: translator notes are taken from explicit LocalizeInfo.comment values; plain string keys receive no comment, and messages are entity-encoded without automatic markdown-link locking. Explicit locks therefore do not cover the central request to eliminate per-message annotations.
- **Extension export boundary:** build/lib/i18n.ts, createXlfFilesForExtensions: package.nls.json, nls.metadata.json and bundle.l10n.json are collected and passed to @vscode/l10n-dev's getL10nXlf.
