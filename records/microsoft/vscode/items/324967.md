# Issue #324967 — Browser: Open Integrated Browser needs an allow list

[https://github.com/microsoft/vscode/issues/324967](https://github.com/microsoft/vscode/issues/324967)

## Summary

Keep this accepted feature request open: supported host allowlisting for Integrated Windows Authentication remains missing from the inspected browser configuration and session setup. It reached 21 upvotes and was explicitly promoted to Backlog; the related authentication issues do not own the same work.

## Change summary

Provide a supported way to authorize NTLM/Kerberos authentication to approved internal websites in the integrated browser without custom startup commands.

## Best solution

Provide a documented, administrator-governable authentication allowlist for integrated-browser sessions, with explicit host-matching, session-scope, and update semantics. Preserve existing authentication restrictions for hosts that have not been approved.

Include negative host-matching cases and administrator-policy enforcement checks.
- **Behavior:**

  > An approved internal Windows-authenticated website should load in the integrated browser without maintaining a custom VS Code launch command. Users or administrators need a supported, documented way to approve hosts while leaving unapproved hosts restricted. Acceptance must cover a fresh application process and reused browser sessions, with any restart requirement explicitly documented.
- **Trace:**

  > BrowserSession in src/vs/platform/browserView/electron-main/browserSession.ts owns Electron sessions for global, workspace, ephemeral, and agent storage scopes; its current configuration contains no integrated-authentication allowlist. The login handler in src/vs/platform/browserView/electron-main/browserView.ts supplies only tunnel-proxy credentials, and http.proxyKerberosServicePrincipal is a separate proxy concern. The reporter demonstrates a startup-flag workaround at https://github.com/microsoft/vscode/issues/324967#issuecomment-4916749887, but runtime behavior was not executed in this read-only review. The existing configuration registrations expose no equivalent supported browser setting. Preserve unrelated proxy, certificate, permission, and network-filter behavior; uncertainty starts at the public configuration contract and which browser session identities may use ambient Windows credentials.
- **Open decisions:**
  - Should the supported contract be a machine/user allowlist, inherited enterprise authentication policy, or documented startup configuration, and what restart requirement is acceptable?
  - Should approval apply to every integrated-browser session, including agent-controlled sessions, or should those sessions require separate authorization?
