# Issue #175202 — Debug with f5 never starts and caused extraneous extension activation 

[https://github.com/microsoft/vscode/issues/175202](https://github.com/microsoft/vscode/issues/175202)

## Summary

Keep open: current source still activates unrelated task providers when an explicitly named preLaunchTask requires task discovery. The reporter confirmed this after reopening; activation now has a timeout, but that does not resolve the unwanted activation or establish that every debug-start stall is fixed.

## Change summary

Starting extension debugging with a named npm preLaunchTask activates unrelated extensions and can leave debugging waiting without useful feedback.

## Best solution

Resolve and run the requested prelaunch task without unnecessarily activating unrelated providers, while preserving arbitrary task labels and existing configured-task resolution. Separately establish whether the original indefinite debug-start wait remains possible and ensure any remaining wait is diagnosable.

- **Trace:**

AbstractTaskService.getTask in src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts resolves configured tasks first, but an unmatched label falls through to _getGroupedTasks with an undefined type, causing _getActivationEvents to activate every registered task type. The reporter does not observe it with ${defaultBuildTask}; this is concrete reproduction information, not a missing-info report.
- **Current source path:** src/vs/workbench/contrib/debug/browser/debugTaskRunner.ts:202 calls taskService.getTask(root, taskId) without a task type. In src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts:953-999, getTask first checks configured workspace tasks, then calls _getGroupedTasks({ type }) when no match exists. With the omitted type, _getGroupedTasks at lines 2303-2308 activates all providers; _getActivationEvents at lines 741-753 emits onTaskType events for every registered task definition. This directly explains unrelated activation for a discovered npm task.
- **Partial protection, not full resolution:** src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts:756-771 bounds provider activation with a 5000 ms raceTimeout and logs a warning. That limits this particular activation wait but still sends all activation events; source inspection alone does not confirm the original indefinite debugging stall on current main.
- **Workaround boundary:** src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts:368-383 resolves ${defaultBuildTask} through configured default tasks before falling back to all-provider discovery. Likewise, getTask can resolve a configured task through tryResolveTask using its known type. These selective paths do not cover every explicitly named, auto-detected prelaunch task.

This report already has an extensionHost launch configuration and identifies onTaskType:docker-build during prelaunch-task lookup, so the older issue does not satisfy the re-reviewed duplicate bar.

It was created on 2026-09-14, later than this report, and concerns a different observable entry point; it is related work, not a valid duplicate target for this re-reviewed issue.
