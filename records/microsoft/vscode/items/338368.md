# Issue #338368 — Repository-scoped Copilot content exclusions affect unrelated files in multi-repository workspaces

[https://github.com/microsoft/vscode/issues/338368](https://github.com/microsoft/vscode/issues/338368)

## Summary

Confirmed in the current source: RemoteContentExclusion flattens every fetched repo's glob patterns into one shared list and checks every file against all of them, so a nested repo's `**/*` rule silently blocks Copilot from files in an unrelated sibling repo in the same workspace.

## Change summary

A repository-scoped Copilot content-exclusion rule (e.g. `**/*` for a nested vendor repo) is applied to unrelated files in other repositories of the same multi-repo workspace.

## Best solution

Scope glob matching by repo the same way regex (ifAnyMatch/ifNoneMatch) rules already are — restrict `isIgnored`'s glob check to the patterns keyed under the file's own repo (plus any genuinely org-wide rules), instead of walking the fully flattened `_compiledGlobs` list built in `rebuildCompiledRules()`.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/ignore/node/remoteContentExclusion.ts`, `extensions/copilot/src/platform/ignore/node/test/remoteContentExclusion.spec.ts`
- **Validation:** A remoteContentExclusion.spec.ts test seeding two repos (an outer and a nested one) where only the nested repo has a `**/*` rule, asserting isIgnored() returns false for a file in the outer repo and true for a file in the nested repo.
- **Behavior:**

  > A content-exclusion rule fetched for one repository must only ignore files inside that repository. In a multi-root/nested-repo workspace, a `**/*` (or any path) exclusion configured for repo B must not cause Copilot to treat files in unrelated repo A as excluded. Organization-wide rules (if any) may still need to apply across all repos in that org — that scope should be preserved, just made explicit rather than implicit. Acceptance: a new/updated test in remoteContentExclusion.spec.ts covering a two-repo workspace where only the nested repo carries a rule passes, and existing content-exclusion tests continue to pass.
- **Trace:**

  > In extensions/copilot/src/platform/ignore/node/remoteContentExclusion.ts, `_contentExclusionCache` (a Map keyed by repo fetch URL) correctly stores each repo's own `patterns`/`ifAnyMatch`/`ifNoneMatch` separately. `rebuildCompiledRules()` then discards that per-repo keying by pushing all `patterns` into one shared `_compiledGlobs: Minimatch[]` array. `isIgnored()` resolves the file's own repo (`resolvedRepo`/`repoMetadata`) correctly, but then checks the file's relative path against the ENTIRE flattened `_compiledGlobs`, not just the globs belonging to `repoMetadata.fetchUrls`. The regex path a few lines later (`regexRuleSources`, lines ~226-234) does exactly the scoping that's missing for globs: it looks up `this._contentExclusionCache.get(fetchUrl)` per relevant fetch URL. The boundary: don't touch the regex (ifAnyMatch/ifNoneMatch) matching path, which is already correct, and don't change the per-repo fetch/caching/batching logic — only how `isIgnored` selects which compiled globs to test a given file against. Where the uncertainty starts: the `source.type` field ('Repository' | 'Organization') is parsed but never consulted, so it's unclear whether the fix should key strictly per-repo (fetchUrl) as regex rules do, or needs a separate org-wide bucket for `type: 'Organization'` rules that should apply beyond the repo they were fetched alongside.
- **Open decisions:**
  - Should Repository-type exclusion patterns be scoped strictly to the repo whose fetch URL produced them (mirroring the existing regex-rule scoping), with no cross-repo leakage at all?
  - Do Organization-type rules (source.type === 'Organization') need to apply across every repo in the same GitHub org within the workspace, requiring the org identity to be tracked per rule/repo — or is per-repo fetch-URL scoping (as suggested in the issue) sufficient for the reported case?

## Evidence

- **flattening bug:** extensions/copilot/src/platform/ignore/node/remoteContentExclusion.ts rebuildCompiledRules() (~lines 533-554) iterates `this._contentExclusionCache.values()` — patterns cached per-repo — and pushes every pattern into a single flat `this._compiledGlobs` array with no repo tag retained.
- **unscoped check:** isIgnored() (~lines 216-222) loops over the entire flattened `this._compiledGlobs` for every file regardless of which repo the file belongs to, so any repo's exclusion pattern (e.g. a nested repo's `**/*`) matches files anywhere in the workspace.
- **contrast with regex rules:** Regex rules (ifAnyMatch/ifNoneMatch) ARE scoped correctly via `repoMetadata.fetchUrls` (lines 226-234) — only the glob path is unscoped, confirming this is an oversight rather than intended global-rule behavior.
- **unused source.type:** ContentExclusionRule.source.type ('Repository' | 'Organization', line 33) is parsed from the API response but never read anywhere else in the file, so the code has no mechanism at all to distinguish org-wide vs repo-specific rules — it always treats patterns as if flattened for the whole workspace.
