# Issue #339267 — ChatApprovedAccountOrganizations policy enabled prevents GHE sign-in

[https://github.com/microsoft/vscode/issues/339267](https://github.com/microsoft/vscode/issues/339267)

## Summary

Confirmed from source: when the ChatApprovedAccountOrganizations policy gate is active (restricted/unsatisfied), the chat sign-in entry points that offer a GHE/enterprise provider picker are hidden, and the only remaining 'Sign In' affordance (the account-policy notification and the accounts-menu generic sign-in) calls the raw account sign-in path that always targets github.com with no enterprise option — exactly contradicting the policy's own documented GHE-deployment use case.

## Change summary

With the ChatApprovedAccountOrganizations policy enabled, the only available Sign In action skips the GitHub Enterprise instance picker, so GHE users have no way to sign in via the title-bar/toast flow.

## Best solution

Route the account-policy gate notification's 'Sign In' button (and any other sign-in affordance left visible while the gate is active) through the same chat setup flow used by the title-bar sign-in button (workbench.action.chat.triggerSetup), which prompts for GitHub vs. GHE, instead of calling DEFAULT_ACCOUNT_SIGN_IN_COMMAND directly.

- **Trace:**

  > The gate notification's Sign In button (accountPolicyGateContribution.ts) calls commandService.executeCommand(DEFAULT_ACCOUNT_SIGN_IN_COMMAND), which resolves to defaultAccountService.signIn() in defaultAccount.ts — this creates a session directly against getDefaultAccountAuthenticationProvider() with no provider choice. The enterprise picker only exists in chatSetupController.ts's setup flow (triggered via CHAT_SETUP_ACTION_ID = 'workbench.action.chat.triggerSetup'), and the title-bar button that normally invokes it is hidden while chatEntitlementService.setForceHidden(true) is in effect (driven by the same gate). Do not change the gate's restriction semantics (org/account checks in computeGateInfo) — only the sign-in call site(s) need to route through (or gain access to) the enterprise-aware flow. The managed-settings-blocked dialog's 'Sign In' button shares the same DEFAULT_ACCOUNT_SIGN_IN_COMMAND call and may need the same treatment — that's part of the scope decision.
- **Open decisions:**
  - Should the account-policy gate notification's 'Sign In' button invoke the full chat setup flow (workbench.action.chat.triggerSetup) instead of the raw account sign-in command?
