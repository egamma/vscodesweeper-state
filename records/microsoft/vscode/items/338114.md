# Issue #338114 — CLI agent host supervisor evicts the running Remote-SSH server from the shared server cache; on an NFS home this leaves a broken install (ServerNotExecutable)

[https://github.com/microsoft/vscode/issues/338114](https://github.com/microsoft/vscode/issues/338114)

## Summary

Thanks for the exceptionally thorough report — confirmed on current main: the CLI's LRU cache eviction (`DownloadCache::touch`) does not check whether an entry is a running server before deleting it, unlike the sibling `prune_stopped_servers`, and the agent host supervisor shares the editor's server cache directory, so its background updates can evict the editor's own running install. On NFS the partial delete then leaves a broken folder the CLI can't self-heal from.

## Change summary

The CLI agent host supervisor's periodic server downloads can evict the editor's currently-running Remote-SSH server from the shared LRU cache, and on NFS a partial delete of that running server's files leaves a broken install reporting ServerNotExecutable with no automatic recovery.

## Best solution

Make the shared download-cache LRU eviction running-aware (mirroring `prune_stopped_servers`'s `get_running_pid()` filter) so it never removes a server folder that's still in use, and add recovery for a partially-deleted (NFS `.nfs*`) cache entry so the CLI can reinstall instead of surfacing `ServerNotExecutable` forever — but the exact mechanism (generic cache API change vs. giving the agent host supervisor its own cache directory) needs a design call since `DownloadCache` is shared generic infrastructure (also backs `cli_cache` and web server storage).

## Plan brief

- **Likely files:** `cli/src/download_cache.rs`, `cli/src/tunnels/agent_host.rs`, `cli/src/tunnels/paths.rs`, `cli/src/tunnels/code_server.rs`
- **Validation:** A `download_cache.rs` unit test asserting `touch()` never removes an entry whose server is currently running (mirroring the `get_running_pid()` check `prune_stopped_servers` already uses), plus a scenario check that a partially-deleted (leftover `.nfs*`) cache entry is detected and triggers reinstall rather than a persistent `ServerNotExecutable`.
- **Behavior:**

  > The agent host supervisor's periodic background server downloads (and any other LRU cache traffic) must never delete the folder of a server that is currently running, whether or not the delete completes cleanly. If a cache entry is left partially deleted (e.g. an NFS `.nfs*` remnant of `bin/code-server`), the next connection attempt must detect the corrupt install and reinstall automatically instead of failing with `ServerNotExecutable` indefinitely. Acceptance: a running editor server survives supervisor cache churn, and a corrupted/partial cache entry self-heals on the next `serve`.
- **Trace:**

  > `DownloadCache::touch` in cli/src/download_cache.rs (~line 222) pops the oldest of `KEEP_LRU` (5) LRU entries and unconditionally `remove_dir_all`s it; it has no concept of 'is this server running', unlike `prune_stopped_servers` in cli/src/tunnels/paths.rs which filters via `ServerPaths::get_running_pid()` before deleting. The agent host supervisor (cli/src/commands/agent_host.rs ~line 289, cli/src/tunnels/agent_host.rs ~line 546-575) shares the same `DownloadCache` (`ctx.paths.server_cache`) as the editor's installed server (cli/src/tunnels/code_server.rs ~line 470), and refreshes its own entry via `exists()` (which calls `touch`) every 6 hours, while the editor's entry is only touched on first install (`create()` returns early without touching if the dir already exists), so the editor's entry drifts to the LRU tail over time. On NFS, deleting a running server's directory leaves open-file remnants (`.nfs*`) that block `remove_dir_all`, corrupting the folder without removing the state-file (`lru.json`) entry cleanly, per the reporter's step 5-6 analysis. The boundary: don't change `create`/`exists`/`delete`'s existing correctness for non-running entries, and `DownloadCache` is also used generically for `cli_cache` (state.rs) and web server storage (serve_web.rs) — any running-check must not regress those callers, which have no notion of a 'running process' at all.
- **Open decisions:**
  - Should the generic `DownloadCache` gain a running-process-aware guard in `touch()` (parameterized by a caller-supplied predicate), or should the agent host supervisor instead use a cache directory entirely separate from the editor's server cache so their LRUs never interact?
  - When a cache entry is found partially deleted (leftover `.nfs*` files, missing `bin/code-server`), should the CLI treat it as absent and reinstall automatically, or surface a clearer error asking the user to remove the folder?
  - Should the editor's own server entry be touched on ordinary use (e.g. via `get_running`), not just on first install, so it naturally stays at the front of the LRU instead of relying on eviction becoming running-aware?

## Evidence

- **unguarded eviction:** cli/src/download_cache.rs `touch()` (~line 222-240) pops the LRU-oldest entry and calls `std::fs::remove_dir_all` with no check for whether that server is running, unlike `prune_stopped_servers` in cli/src/tunnels/paths.rs (~line 118-127) which filters on `s.get_running_pid().is_none()` before deleting.
- **shared cache:** The agent host supervisor is constructed with `ctx.paths.server_cache.clone()` in cli/src/commands/agent_host.rs (~line 289) — the same `DownloadCache` the editor's own server is installed into via cli/src/tunnels/code_server.rs (~line 470-473).
- **only fresh-install touches:** `DownloadCache::create` (cli/src/download_cache.rs) returns early without calling `touch` when the target directory already exists, so a long-running editor server's cache entry never gets refreshed by ordinary use and drifts toward LRU eviction, while the supervisor's own entry is kept fresh via `exists()` (called in cli/src/tunnels/agent_host.rs ~line 552), which does call `touch`.
- **generic cache reuse:** `DownloadCache::new` is also used for `cli_cache` (cli/src/state.rs ~line 196) and web server storage (cli/src/commands/serve_web.rs ~line 609), so any running-process awareness needs to be plumbed in without breaking those other, process-agnostic uses.
