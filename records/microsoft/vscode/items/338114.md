# Issue #338114 — CLI agent host supervisor evicts the running Remote-SSH server from the shared server cache; on an NFS home this leaves a broken install (ServerNotExecutable)

[https://github.com/microsoft/vscode/issues/338114](https://github.com/microsoft/vscode/issues/338114)

## Summary

Confirmed from source on current main (same code paths, unchanged logic): the CLI's shared server download cache evicts and deletes the LRU entry's folder without checking whether that server is actually running, and the editor-installed server's cache entry is only recorded on first install, not on subsequent re-use — so a long-lived agent-host supervisor process can silently delete the active, in-use server install. Previously reviewed and kept open; no fix has landed since, so it stays open.

## Change summary

The CLI agent-host supervisor's periodic server downloads can evict and physically delete the cache entry for a currently-running Remote-SSH server, leaving a broken install (ServerNotExecutable) especially on NFS-backed $HOME where permission-repair races make it worse.

## Best solution

Fix the cross-process LRU eviction in cli/src/download_cache.rs (`touch`) to check the server's running state (via the same PID-liveness check `get_running`/`get_running_pid` already use in cli/src/tunnels/code_server.rs) before deleting a cache folder, and/or have `DownloadCache::create`'s early-return path call `touch` as well so the editor's entry is kept fresh in the LRU. This likely needs a maintainer decision on the exact approach (liveness check vs. separate cache namespace for supervisor vs. editor servers vs. locking changes to `lru.json`).

## Plan brief

- **Likely files:** `cli/src/download_cache.rs`, `cli/src/tunnels/code_server.rs`, `cli/src/tunnels/agent_host.rs`, `cli/src/state.rs`
- **Validation:** A test asserting that `DownloadCache::touch`/eviction never removes a cache folder whose server process (per `get_running_pid`) is currently alive, even when it is the LRU tail; plus a test that re-using an already-downloaded entry via `create()`'s early-return path moves it to the front of the LRU.
- **Behavior:**

  > The CLI's shared download cache for installed servers must never delete the on-disk folder of a server that is currently running (checked via the existing PID-liveness mechanism in `get_running`/`get_running_pid`), regardless of its LRU recency. Re-using an already-installed server (the `create()` early-return path) must also refresh its LRU position like the supervisor's own downloads do, so an actively-used editor server isn't the oldest entry simply because nothing ever touched it again.
- **Trace:**

  > cli/src/download_cache.rs: `create()` returns `Ok(target_dir)` at its first existence check without calling `touch`, so an editor server's cache entry is set only once, at install time (evidenced by the early-return before `remove_orphaned_staging_directories`). `touch()` (same file) evicts `l.last()` and calls `std::fs::remove_dir_all` on it with no check of whether that server is alive; `get_running`/`get_running_pid` in cli/src/tunnels/code_server.rs (around lines 401-419) already implement the liveness check the eviction path lacks, but nothing in download_cache.rs calls it. Each CLI process (supervisor vs. command-shell) holds its own in-memory copy of `lru.json` via `PersistedStateContainer` (cli/src/state.rs), so writes from one process can clobber what another just wrote — this cross-process state sharing/locking question is part of the ambiguity, not something to silently restructure. Do not change the on-disk `lru.json` format or remove the 5-entry LRU cap outright; the fix should add a liveness guard (or equivalent) to eviction, not abandon LRU bounding altogether.
- **Open decisions:**
  - Should eviction simply skip (and try the next-oldest entry) when the LRU tail is a running server, or should running servers be excluded from the LRU/eviction pool entirely?
  - Should the agent-host supervisor's own server downloads live in a separate cache/directory from the editor's server installs, to avoid contention over the same LRU pool altogether?
  - Does fixing `create()`'s missing `touch()` on the early-return path risk masking the real problem (that the supervisor still shares the same bounded cache), or is cache separation the more durable fix?

## Evidence

- **touch() has no liveness check:** cli/src/download_cache.rs `fn touch` (lines ~219-230 on main at commit 280a9749) pops the last LRU entry and calls `remove_dir_all` on its folder unconditionally — no check against `get_running_pid`/`get_running` in cli/src/tunnels/code_server.rs (line 401, 409).
- **create() early-return skips touch:** cli/src/download_cache.rs `create()` returns `Ok(target_dir)` immediately when `target_dir.exists()` at the top of the function (before `remove_orphaned_staging_directories`), with no `self.touch(...)` call on that path — matching the issue's claim that the editor's own cache entry is only touched on first install.
- **no recent fix:** git log on cli/src/download_cache.rs, cli/src/tunnels/agent_host.rs, cli/src/state.rs shows only commit 280a9749 ('[Perf] agentHost: isolate E2E storage on tmpfs'), unrelated to eviction/locking logic — the reported code paths are unchanged.
