# Issue #338114 — CLI agent host supervisor evicts the running Remote-SSH server from the shared server cache; on an NFS home this leaves a broken install (ServerNotExecutable)

[https://github.com/microsoft/vscode/issues/338114](https://github.com/microsoft/vscode/issues/338114)

## Summary

Well-diagnosed, still-reproducing bug: on current main, DownloadCache::create's early-return path (target_dir already exists, before the lock) skips touch(), while touch() itself evicts the LRU-last cache entry by deleting its directory without checking whether a server there is currently running — exactly what the report traces through download_cache.rs, agent_host.rs, and state.rs. This only carries `triage-needed`, so routing to the CLI/remote area is the right move rather than a close.

## Change summary

The CLI agent host supervisor shares the same server download cache as the editor's Remote-SSH server; its periodic downloads can evict and delete the currently-running editor server's cache entry (worse on NFS homes / multi-process lru.json races), leaving a broken ServerNotExecutable install.

## Best solution

In cli/src/download_cache.rs, make cache eviction (touch()) refuse to delete an entry that is currently in use by a running server process, and make the early-return branch of create() call touch() too so actively-used entries stay at the front of the LRU list; likely also needs a look at the single-read/last-write race on lru.json described in state.rs.

## Plan brief

- **Likely files:** `cli/src/download_cache.rs`, `cli/src/tunnels/agent_host.rs`, `cli/src/state.rs`
- **Validation:** A download_cache.rs unit test that pins an entry as "in use", pushes the LRU list past KEEP_LRU, and asserts the pinned entry's directory and lru.json record survive touch()'s eviction.
- **Behavior:**

  > The agent host supervisor's periodic server downloads must never delete the on-disk cache entry for a server version that is actively serving a Remote-SSH connection, even when the supervisor and the editor's command-shell run as separate CLI processes and race on lru.json. Acceptance: repeatedly cycling the supervisor's download/update loop past the 5-entry LRU cap never removes a currently-running server's folder or its lru.json record.
- **Trace:**

  > In cli/src/download_cache.rs, `create()`'s pre-lock branch (`if target_dir.exists() { return Ok(target_dir); }`) returns without calling `touch`, so a server that's merely opened (not freshly created) doesn't get its LRU position refreshed; `touch()` then evicts whatever is `l.last()` by unconditionally calling `remove_dir_all` on it, with no notion of "in use". Compounding this, cli/src/state.rs's `PersistedStateContainer` reads lru.json once per process and last-writer-wins on `update`, so the supervisor process and the command-shell process can each hold a stale in-memory copy of the LRU list. The fix boundary is this cache/eviction logic and its cross-process persistence — do not change the download/lock/rename mechanics that already work (staging directories, file lock acquisition), and do not change the supervisor's decision to auto-start (issue explicitly separates that as tracked by microsoft/vscode#328397).
- **Open decisions:**
  - How should a cache entry be marked/detected as "currently in use by a running server process" so touch() can skip evicting it — a lock file held by the running server, a liveness check against the process, or something else?
  - Should the pre-lock early-return branch in create() also call touch(), and if so does that risk contending with the lock unnecessarily?
  - Should the lru.json read-once/last-writer-wins persistence model in state.rs be changed to something that tolerates concurrent CLI processes, or is a targeted eviction-safety check in touch() sufficient on its own?

## Evidence

- **early-return skips touch:** cli/src/download_cache.rs `create()`: `let target_dir = self.path.join(name); if target_dir.exists() { return Ok(target_dir); }` returns before acquiring the lock and without calling `touch`, matching the issue's point 3 (only the post-lock branches call `touch`).
- **unconditional eviction on touch:** cli/src/download_cache.rs `touch()`: when the LRU list exceeds `KEEP_LRU` (5), it takes `l.last()` and calls `std::fs::remove_dir_all(f)` on that cache folder with no check for whether a server process is running out of it — matches the issue's point 5.
- **shared cache + periodic downloads:** cli/src/tunnels/agent_host.rs and cli/src/commands/agent_host.rs use `ctx.paths.server_cache`, the same `DownloadCache` the editor's `code-server` is installed into (cli/src/state.rs), and the supervisor's update loop calls into the cache on its own 6-hour schedule, independent of whether the editor's server is in use.
- **line-number drift, same code path:** The issue's links are pinned to commit 520fb30b (1.136.0); this checkout is a single squashed commit at 101c86fe with no history to diff against, but the described logic (early-return-without-touch, unconditional last-entry deletion) is present verbatim in current main's download_cache.rs.
