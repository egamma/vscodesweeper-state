# Issue #210393 — Wrong text decoration locations on vscode 1.88.1

[https://github.com/microsoft/vscode/issues/210393](https://github.com/microsoft/vscode/issues/210393)

## Summary

The positioning regression remains explainable in current source: an absolutely positioned line-content span changes the containing block used by the supplied decoration. Keep the accepted bug open while the editor owner decides the compatibility boundary for CSS injected through textDecoration.

## Change summary

Since VS Code 1.88, absolutely positioned decoration attachments are anchored to line content instead of their previous full-width positioning context.

## Best solution

Resolve the editor-rendering compatibility issue without undoing the line-height improvements. Establish whether the previous positioning behavior should be preserved or whether editor-relative attachments need an explicitly supported contract.

## Evidence

- **Supplied reproduction:** The reporter supplied a minimal extension in https://github.com/microsoft/vscode/issues/210393#issuecomment-2076281359. Its source, https://github.com/changchanghwang/vscode_decoration_debug/blob/main/src/extension.ts, attaches an empty after decoration to the first visible position and injects position:absolute, right:5vw and top:50% through textDecoration; typing and visible-range changes recreate it.
- **Introducing layout change:** https://github.com/microsoft/vscode/commit/a9ab31da9cfa2d45bac4bda59a980cc701d497e5 added bottom:0 and position:absolute to .view-line > span in src/vs/editor/browser/viewParts/lines/viewLines.css. This adds a nearer positioned ancestor for the decoration attachment. The rule is absent in 1.87.2 and present, with top:0 and a narrower selector, in 1.88.1.
- **Current source path:** src/vs/editor/browser/viewParts/viewLines/viewLines.css still absolutely positions .lines-content > .view-lines > .view-line > span. src/vs/editor/browser/services/abstractCodeEditorService.ts, getCSSTextForModelDecorationContentClassName and collectCSSText, still interpolate the supplied textDecoration string into CSS. Consequently the reproduction's right and top offsets resolve against the line-content span rather than the previous ancestor. This is a source trace, not an executed rendering check.
- **Public-contract boundary:** src/vscode-dts/vscode.d.ts, ThemableDecorationAttachmentRenderOptions, documents textDecoration as a CSS styling property and before/after as content attachments; it exposes no position, top or right option and promises no editor-relative containing block. The sample depends on additional CSS declarations injected into that string, so preserving this positioning requires an owner decision rather than assuming it is a documented API guarantee.
- **Independent reports and partial workaround:** https://github.com/hoovercj/vscode-power-mode/issues/112 contains multiple independent confirmations of the meter moving or shifting after the update, including on macOS. https://github.com/JunbaeJs/junbae-mode/issues/21 reports the same 1.88.1 positioning change. The open extension-side workaround https://github.com/hoovercj/vscode-power-mode/pull/114 replaces right:5% with left:calc(100vw - 25rem); it is not a landed VS Code fix or a general resolution for the supplied reproduction.
