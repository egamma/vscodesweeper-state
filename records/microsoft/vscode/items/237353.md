# Issue #237353 — Ability to close and folders to reduce resource consumption in multi-root workspaces

[https://github.com/microsoft/vscode/issues/237353](https://github.com/microsoft/vscode/issues/237353)

## Summary

Keep this accepted Backlog request open: persistent, reversible deactivation of workspace roots remains distinct from removing folders or applying exclusion settings. It has 34 upvotes, and no verified open canonical was found.

## Change summary

Allow users to deactivate and reactivate multi-root workspace folders while retaining their identities and reducing workspace processing and clutter across sessions.

## Best solution

Provide a persistent inactive-root state with an easy reactivation action, coordinated with search, file watching, SCM, and extension workspace membership. Define the extension-facing and editor behavior before implementation; deactivation should not make files disappear from external programs.

## Plan brief

- **Likely files:** `src/vs/platform/workspace/common/workspace.ts`, `src/vs/platform/workspaces/common/workspaces.ts`, `src/vs/workbench/browser/actions/workspaceActions.ts`, `src/vs/workbench/services/workspaces/browser/abstractWorkspaceEditingService.ts`, `src/vs/workbench/services/configuration/browser/configurationService.ts`, `src/vs/workbench/contrib/files/browser/workspaceWatcher.ts`, `src/vs/workbench/api/browser/mainThreadWorkspace.ts`
- **Validation:** The plan should define automated workspace persistence and membership checks plus a manual two-root scenario: deactivate one root, confirm default search and Go to File omit it, verify the agreed watcher/SCM/extension behavior, reload and confirm the state persists, then reactivate without browsing for the folder. Files must remain accessible to external programs, and the other root must remain unaffected.
- **Behavior:**

  > Users want to temporarily deactivate a workspace root without losing its saved identity or having to locate it again. The state should persist across VS Code sessions, offer easy reactivation, and reduce irrelevant search results and background project processing. Acceptance must cover deactivation, reload, and reactivation in a two-root workspace, including the agreed SCM and language-extension behavior. The comment asking for external Node.js reads to fail is a broader filesystem-isolation request, not an established requirement of workspace deactivation.
- **Trace:**

  > RemoveRootFolderAction in src/vs/workbench/browser/actions/workspaceActions.ts currently invokes removeFolders in AbstractWorkspaceEditingService, which delegates actual workspace membership removal. Stored root types in src/vs/platform/workspace/common/workspace.ts and src/vs/platform/workspaces/common/workspaces.ts have no inactive-state contract. Existing exclusion settings cover individual Explorer, search, and watcher concerns rather than coordinated deactivation. WorkspaceWatcher consumes workspace membership and folder-change events; MainThreadWorkspace propagates workspace changes toward extensions. The uncertainty starts at whether inactive roots remain in the public workspaceFolders collection and how editor access interacts with suspension of language/project processing. Preserve files on disk, normal remove-folder behavior, and unaffected active roots. The predecessor https://github.com/microsoft/vscode/issues/63963 is closed and supplies historical demand and workarounds, not an implementation or open canonical.
- **Open decisions:**
  - Should inactive roots be absent from the extension API's workspaceFolders collection, with ordinary remove/add events on deactivation/reactivation, or remain present under a new explicit inactive-root contract?
  - What happens to already-open editors in a deactivated root, and does explicitly opening one of its files reactivate the root or leave workspace-level processing suspended?

## Evidence

The January 31, 2025 bot comment explicitly records promotion after reaching the community threshold; subsequent comments request persistence and coordinated exclusion from search, Go to File, and SCM.
- **Existing capability does not cover the request:** src/vs/workbench/browser/actions/workspaceActions.ts registers workbench.action.removeRootFolder through RemoveRootFolderAction, which calls IWorkspaceEditingService.removeFolders. src/vs/workbench/services/workspaces/browser/abstractWorkspaceEditingService.ts delegates removal to the workspace service rather than retaining an inactive root. IRawFileWorkspaceFolder and IRawUriWorkspaceFolder in src/vs/platform/workspace/common/workspace.ts contain path/uri and optional name, with no inactive-state field.
- **Exclusions are partial workarounds:** files.watcherExclude in src/vs/workbench/contrib/files/browser/files.contribution.ts excludes paths from file watching; files.exclude is consumed by the Explorer filter in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts, and search.exclude participates in search filtering in src/vs/workbench/services/search/common/search.ts. These controls do not provide a retained, reactivatable root or a coordinated extension-project shutdown contract.
