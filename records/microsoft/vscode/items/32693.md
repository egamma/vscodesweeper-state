# Issue #32693 — Monolithic structure, multiple project settings

[https://github.com/microsoft/vscode/issues/32693](https://github.com/microsoft/vscode/issues/32693)

## Summary

This remains the accepted canonical request for resource-scoped settings within monorepos. Current main still loads one .vscode configuration per workspace folder, and the Backlog placement, 608 upvotes, and maintainer description of this as a major design item all support keeping it open.

## Change summary

Apply settings from nested .vscode/settings.json files to files in their corresponding project subtrees.

## Best solution

Design a resource-aware configuration hierarchy that lets nested projects contribute settings without requiring each project to be added as a multi-root workspace folder, while preserving existing workspace-folder behavior and defining discovery, precedence, and standalone-configuration scope.

## Plan brief

- **Likely files:** `src/vs/workbench/services/configuration/browser/configuration.ts`, `src/vs/workbench/services/configuration/browser/configurationService.ts`, `src/vs/platform/configuration/common/configurationModels.ts`, `src/vs/workbench/services/configuration/test/browser/configurationService.test.ts`
- **Validation:** Extend the WorkspaceConfigurationService folder and multiroot unit suites to open resources under nested projects and verify that the expected root and nested values merge by resource, while existing single-folder and multi-root precedence tests remain unchanged.
- **Behavior:**

  > Files inside a nested project should receive settings declared by that project's .vscode/settings.json, while files outside that subtree should not. Settings inherited from the enclosing workspace and user scopes must continue to apply, with a deterministic precedence rule when nested configuration files overlap. Existing single-folder and explicitly configured multi-root workspaces must retain their current behavior.
- **Trace:**

  > FolderConfiguration in src/vs/workbench/services/configuration/browser/configuration.ts currently binds one configuration directory to each IWorkspaceFolder. WorkspaceService.loadFolderConfigurations in src/vs/workbench/services/configuration/browser/configurationService.ts creates models only for workspace.folders, and Configuration.getFolderConfigurationModelForResource in src/vs/platform/configuration/common/configurationModels.ts selects only the model belonging to workspace.getFolder(resource). This conclusively leaves no representation for nested project configuration on current main. Multi-root workspaces are an existing workaround, but the duplicate history confirms that requiring every nested project to become an explicit root does not satisfy the requested workflow. Keep ordinary workspace-folder precedence, trust filtering, and extension configuration APIs stable; the uncertainty begins at how nested configurations are discovered and represented.
- **Open decisions:**
  - Should nested .vscode directories be discovered automatically, enabled by an explicit workspace option or glob, or declared as workspace project roots?
  - When root and multiple nested settings files apply to one resource, what is the observable precedence and inheritance contract?
  - Does the feature initially apply only to settings.json, or also expose nested tasks.json, launch.json, and other .vscode resources?

## Evidence

- **current source gap:** In src/vs/workbench/services/configuration/browser/configuration.ts, FolderConfiguration.createFileServiceBasedConfiguration constructs settings, tasks, and launch resources only beneath the single configurationFolder derived from workspaceFolder.uri. It does not discover nested .vscode directories.
- **resource resolution:** src/vs/workbench/services/configuration/browser/configurationService.ts loadFolderConfigurations creates exactly one FolderConfiguration for each entry in workspace.folders, while src/vs/platform/configuration/common/configurationModels.ts getFolderConfigurationModelForResource resolves a resource back to that workspace root's single configuration model.
