# Issue #331790 — Copilot edit tools report success even when the underlying FileSystemProvider.writeFile fails

[https://github.com/microsoft/vscode/issues/331790](https://github.com/microsoft/vscode/issues/331790)

## Summary

Well-diagnosed report with source tracing that matches current main: the edit tools decide 'success' before the underlying FileSystemProvider.writeFile even runs, so a save rejection from a custom provider never reaches the tool result. Routing to the chat/tools area for a maintainer design call rather than closing.

## Change summary

Copilot edit tools (replace_string_in_file, apply_patch, insert_edit_into_file) report edits as successfully applied even when the target FileSystemProvider.writeFile ultimately throws, because the tool never observes the save outcome.

## Best solution

A maintainer needs to design how (or whether) the edit tools can observe the eventual save outcome of a streamed textEdit — e.g. wire a completion/error signal from the chat editing session's apply/save path back into the tool result in extensions/copilot/src/extension/tools/node/abstractReplaceStringTool.tsx and editFileToolResult.tsx — while weighing the latency/streaming UX tradeoff of awaiting saves.
