# Issue #298928 — Copilot Fix ignores extension-provided code.target and code actions, generating incorrect fixes

[https://github.com/microsoft/vscode/issues/298928](https://github.com/microsoft/vscode/issues/298928)

## Summary

A real gap remains on current main: inline Copilot Fix now includes diagnostic related information, but it still does not expose `code.target` or extension-provided quick fixes to the fix prompt. This team-authored request should remain open while the desired action and URL handling semantics are designed.

## Change summary

Let Copilot Fix use structured extension guidance attached to diagnostics, including target URLs, related information, code actions, and referenced snippets.

## Best solution

Define a safe structured context contract for Copilot Fix that carries diagnostic target links and relevant non-Copilot quick-fix guidance without automatically executing arbitrary extension commands. Preserve the existing related-information handling and bound the added context by relevance and prompt size.

- **Validation:** Add targeted prompt/provider tests using a diagnostic with object-valued `code.target`, `relatedInformation`, and a non-Copilot quick fix; assert the rendered fix context includes the approved structured guidance, excludes the Copilot action itself, and leaves ordinary message-only diagnostics unchanged.
- **Behavior:**

  > Invoking Copilot Fix for a diagnostic should make the extension's relevant structured guidance available to the model instead of reducing the request to the diagnostic message. Existing `relatedInformation` context must continue to work, while a diagnostic target and applicable extension quick-fix guidance should be represented according to the agreed trust and execution policy. Copilot's own fix action and unrelated actions must not be fed back as guidance. Message-only diagnostics must retain their current behavior.
- **Trace:**

  > QuickFixesProvider in extensions/copilot/src/extension/inlineChat/vscode-node/inlineChatCodeActions.ts constructs `/fix` from `Diagnostic.message` only. InlineFix3Prompt later reacquires matching diagnostics through `findDiagnosticForSelectionAndPrompt` and renders `Diagnostics`, whose DiagnosticRelatedInfo component already opens and includes bounded source from `relatedInformation`. That renderer does not consume `Diagnostic.code.target`, while `fixCookbookService.ts` deliberately reduces an object-valued code to its value. The code-action provider receives diagnostics but not results from sibling providers; the public `vscode.executeCodeActionProvider` command can query actions, although doing so from this path requires defining how self-actions, unresolved actions, workspace edits, and commands are treated. Keep the existing message-only and related-information paths unchanged; the uncertainty starts at whether links are fetched and whether extension actions are represented, resolved, or executed.
- **Open decisions:**
  - Should an extension-provided quick fix be supplied only as model context, or may Copilot apply its workspace edit automatically before or during the generated fix?
  - Should `Diagnostic.code.target` contribute only its URL/reference, or may Copilot retrieve remote documentation content, and under which trust or consent boundary?
  - Which sibling actions are eligible: only preferred non-AI quick fixes tied to the selected diagnostic, all matching quick fixes, or actions containing workspace edits but not commands?
