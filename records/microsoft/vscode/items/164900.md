# Issue #164900 — Solve merge conflict in git submodule update using new 3 way merge editor

[https://github.com/microsoft/vscode/issues/164900](https://github.com/microsoft/vscode/issues/164900)

## Summary

Keep open: conflicting submodule commit pointers still lack a working resolution flow, with repeated confirmations through June 2026 and a relevant mismatch in current source. The issue already has the appropriate merge-editor label; no verified older canonical or fixing commit supports closing it.

## Change summary

Allow users to resolve conflicting Git submodule commit pointers from Source Control instead of encountering an unusable merge editor.

## Best solution

Provide a submodule-aware resolution experience in the built-in Git extension that selects the intended commit pointer and clears the parent repository's conflict. Establish how that selection affects the checked-out submodule and protects local changes before implementation.

## Plan brief

- **Likely files:** `extensions/git/src/repository.ts`, `extensions/git/src/commands.ts`, `extensions/git/src/git.ts`, `extensions/git/src/uri.ts`, `extensions/git/src/fileSystemProvider.ts`
- **Validation:** In a separate disposable fixture, create a parent repository whose two branches point the same submodule at divergent commits, then merge to produce an unmerged gitlink. Resolve each side through Source Control in separate runs and verify git ls-files --stage reports one stage-0 entry with mode 160000 and the selected SHA, while git ls-files --unmerged reports no entry for that path. Check the agreed submodule checkout behavior, preservation of local edits, and unchanged ordinary text-conflict resolution.
- **Behavior:**

  > A parent-repository merge that conflicts on a submodule commit pointer must offer a usable way to select the current or incoming pointer. Completing that selection must remove the submodule from Merge Changes and record the selected commit in the parent index. Ordinary text-file merge behavior must remain unchanged. Acceptance checks must verify the resulting gitlink SHA, conflict clearance, and preservation of local submodule edits.
- **Trace:**

  > ResourceCommandResolver.getResources in extensions/git/src/repository.ts exposes submodules as synthetic git: diff documents; resolveChangeCommand can pass those resources to git.openMergeEditor. CommandCenter.openMergeEditor in extensions/git/src/commands.ts treats the resource as a text merge, while toMergeUris in extensions/git/src/uri.ts does not preserve its submodule metadata. GitFileSystemProvider.readFile returns submodule diff text, not an editable commit-pointer model. This establishes a relevant integration mismatch, but no runtime fixture was executed. Keep the boundary focused on parent-repository gitlink conflicts, not merges of files inside the submodule or the separate rebase-metadata problem at https://github.com/microsoft/vscode/issues/167414. The younger same-symptom report https://github.com/microsoft/vscode/issues/184519 supplies additional confirmation. Planning must settle the observable checkout semantics and validate the actual resolution path before defining a bounded implementation.
- **Open decisions:**
  - Should accepting a submodule pointer change only the parent repository's index, or also check out that commit inside the submodule; if checkout is part of acceptance, what should the user see when local submodule changes prevent it?
