# Issue #164900 — Solve merge conflict in git submodule update using new 3 way merge editor

[https://github.com/microsoft/vscode/issues/164900](https://github.com/microsoft/vscode/issues/164900)

## Summary

Still unresolved on current main: a conflicted submodule (a gitlink, not a blob) is routed into the 3-way merge editor like any other `UU` path, so no conflict regions and no accept actions appear and the merge cannot be completed in VS Code; keep open and route to the git/merge-editor owners.

## Change summary

A merge conflict on a git submodule (conflicting subproject commits) cannot be resolved from the Source Control view — the merge editor opens with no Accept Current / Accept Incoming affordances.

## Best solution

Give conflicted submodule entries their own resolution path in the git extension instead of the text merge editor — e.g. detect the gitlink in `ResourceCommandResolver.resolveChangeCommand` and offer 'Accept Current'/'Accept Incoming' actions that run `git checkout --ours/--theirs -- <path>` followed by `git add <path>` — so the merge can be completed without dropping to the command line.

## Plan brief

- **Likely files:** `extensions/git/src/repository.ts`, `extensions/git/src/commands.ts`, `extensions/git/src/fileSystemProvider.ts`, `extensions/git/package.json`
- **Validation:** With a repo containing a submodule in a conflicted merge, the Source Control 'Merge Changes' entry for the submodule offers working accept actions; after invoking one, `git status` reports the submodule staged and the merge can be committed — no command-line step needed.
- **Behavior:**

  > When a merge leaves a git submodule conflicted (both sides point at different subproject commits), clicking that entry under Source Control > Merge Changes must lead to an outcome the user can complete in VS Code: a way to take the current (ours) or incoming (theirs) subproject commit, after which the submodule is staged and the merge can be committed. Today a 3-way merge editor opens with no conflict regions and no Accept Current / Accept Incoming actions, so the merge is deadlocked and the user must run `git reset HEAD <submodule>` or `git checkout --ours/--theirs` in a terminal. Acceptance: the submodule conflict is resolvable end-to-end from the UI; conflicts on ordinary files keep their existing merge-editor behavior unchanged.
- **Trace:**

  > A conflicted submodule is parsed as `UU` and pushed into the merge group as `Status.BOTH_MODIFIED` (extensions/git/src/repository.ts, status parsing ~line 3231). `ResourceCommandResolver.resolveChangeCommand` (same file, ~line 540) then routes every BOTH_MODIFIED/BOTH_ADDED resource with a `rightUri` to `git.openMergeEditor` when `git.mergeEditor` is enabled, with no check for whether the path is a gitlink. `openMergeEditor` in extensions/git/src/commands.ts constructs base/ours/theirs `git:` URIs that GitFileSystemProvider (extensions/git/src/fileSystemProvider.ts) resolves through `getObjectDetails`/`buffer`; a gitlink index entry has no blob content, so all three inputs are empty, the merge editor finds no conflicting regions and renders no accept affordances — matching the reporter's screenshot and ten independent confirmations. `rg -i 'gitlink|160000|Subproject'` over extensions/git/src shows no submodule-conflict handling exists anywhere on main. Boundary: do not change merge-editor behavior for ordinary text conflicts, and do not alter the existing status parsing for non-gitlink paths; the change belongs in the git extension's resource routing/resolution, not in src/vs/workbench/contrib/mergeEditor. Ref: https://github.com/microsoft/vscode/issues/164900.
- **Open decisions:**
  - Should a conflicted submodule open the 3-way merge editor at all, or should it instead surface dedicated 'Accept Current' / 'Accept Incoming' commands (context-menu and/or quick pick) on the Merge Changes entry?
  - Which resolutions are offered: ours/theirs only, or also 'open the submodule repository' so the user can pick an arbitrary subproject commit?
  - After accepting a side, should the submodule be staged automatically (`git add <path>`), and should the working tree be updated with `git submodule update` — or is staging the index entry alone the expected behavior?

## Evidence

- **no gitlink handling on main:** `rg -i 'gitlink|160000|Subproject'` over extensions/git/src returns nothing — the extension has no special handling for conflicted submodule entries anywhere.
- **routing path:** extensions/git/src/repository.ts (~line 540, `ResourceCommandResolver.resolveChangeCommand`) sends any `Status.BOTH_MODIFIED`/`BOTH_ADDED` resource with a `rightUri` to `git.openMergeEditor` when `git.mergeEditor` is on; a conflicted submodule is reported as `UU` (repository.ts ~3231) and takes that same branch.
- **merge editor inputs are empty for a gitlink:** extensions/git/src/commands.ts `openMergeEditor` builds base/ours/theirs as `git:` URIs resolved by fileSystemProvider.ts via `getObjectDetails`/`buffer`; for a gitlink path there is no blob content, so the merge editor has no conflicting regions and therefore shows no accept actions — exactly the screenshot in the report.
- **sustained confirmations:** Independent reports through 2023, 2024, 2025 and 2026-06-18 (https://github.com/microsoft/vscode/issues/164900), 11 upvotes; commenters note the only way out is `git reset HEAD <submodule>` on the command line.
