Keep open as an upstream filesystem compatibility issue. Current VS Code has a targeted workaround, but the upstream history does not establish a complete fix for Windows Store execution aliases or this report's missing directory entries.

## Evidence

- **Confirmed upstream diagnosis:** https://github.com/microsoft/vscode/issues/95828#issuecomment-618326465 documents both stat and lstat failing on a WindowsApps execution alias. The discussion distinguishes these AppExecLink reparse points from ordinary junctions, so successful enumeration of Documents and Settings does not refute the report.
- **Current enumeration path:** src/vs/workbench/api/browser/mainThreadFileSystem.ts:76-85 obtains directory children through the file service. In src/vs/platform/files/node/diskFileSystemProvider.ts:115-141, readdir resolves symbolic-link targets through stat and omits individual entries when that operation throws.
- **Existing mitigation, not proven completion:** src/vs/base/node/pfs.ts:264-311 implements SymlinkSupport.stat, including an explicit Windows EACCES workaround referencing https://github.com/nodejs/node/issues/36790: stat(readlink(path)). That fallback can still throw. The separate safeReaddirWithFileTypes fallback retains entries whose lstat fails, but neither path proves complete enumeration of AppExecLinks on the reporter's Windows configuration. No Windows execution was performed.
- **Earlier upstream fix was incomplete:** https://github.com/nodejs/node/issues/33024#issuecomment-621156469 describes the libuv change as fixing lstat while warning that stat can still fail. The original reporter subsequently states that the latest release still reproduces the issue at https://github.com/nodejs/node/issues/33024#issuecomment-763097001.
- **Upstream closure was inactivity, not resolution:** https://github.com/nodejs/node/issues/36790 was automatically closed for inactivity on 2026-07-28, not by a verified fix. Its discussion also cautions that readlink may expose the launcher rather than the requested application's metadata: https://github.com/nodejs/node/issues/36790#issuecomment-791607422.
- **Active upstream implementation candidate:** https://github.com/libuv/libuv/pull/4986 remains open and proposes treating AppExecLinks as regular files instead of resolving them as symbolic links. It is an upstream lead, not a merged or adopted fix.
