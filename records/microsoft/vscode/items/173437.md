# Issue #173437 — Git - Changes are not staged if multiple parts are selected separately

[https://github.com/microsoft/vscode/issues/173437](https://github.com/microsoft/vscode/issues/173437)

## Summary

Keep open: the discussion confirms that staging a second range can discard the first staged range. Current source still relies on a cached index document; a related open PR is an implementation candidate, not a landed fix.

## Change summary

Successive Stage Selected Range operations should preserve previously staged changes even when the diff view has not refreshed.

## Best solution

Evaluate the fresh-index-read approach in https://github.com/microsoft/vscode/pull/326397 against this report's two-stage, no-intervening-commit reproduction. The finished behavior must preserve both selected ranges without requiring a tab switch or functioning filesystem watchers.

## Evidence

- **Confirmed reproduction:** https://github.com/microsoft/vscode/issues/173437#issuecomment-1425086024 supplies a fresh-repository reproduction: commit 1\n2\n3\n, insert 0\n and append 4\n, stage the two additions separately, and observe only 4\n in the index. No intervening commit is involved.
- **Current staging path:** extensions/git/src/commands.ts:1777-1809 selects changes from editor diff information; _stageChanges at lines 1940-1953 obtains the index base through workspace.openTextDocument(toGitUri(modifiedUri, '~')) and applies only the selected changes. extensions/git/src/git.ts:2005-2044 writes the resulting whole-file blob using update-index --cacheinfo. A stale base can therefore replace earlier staged content rather than accumulate selections.
- **Refresh qualification:** extensions/git/src/repository.ts:1323-1330 explicitly emits an original-resource change after staging, and extensions/git/src/fileSystemProvider.ts:67-80 immediately emits changes for the index-backed documents. General repository invalidation remains debounced by 1100 ms. Immediate notification is present, so the historical watcher explanation alone does not conclusively establish the exact current timing failure.
- **Workarounds and environment:** https://github.com/microsoft/vscode/issues/173437#issuecomment-1423940198 reports that opening the index view triggers a refresh. https://github.com/microsoft/vscode/issues/173437#issuecomment-1833761279 independently reports the problem in a large Remote-SSH workspace, with improvement after increasing Linux watcher limits and a tab-switch workaround. These are mitigation evidence, not proof that the Git staging defect is extension-owned.
