# Issue #199367 — Tree Sticky Scroll - ability to programatically define nodes that should be sticky

[https://github.com/microsoft/vscode/issues/199367](https://github.com/microsoft/vscode/issues/199367)

## Summary

A real gap remains: current tree sticky scroll only selects nodes from the visible element's ancestor chain, while the SCM input and action button are sibling leaves. A newer customization API can adjust or suppress an ancestor's sticky range, but it cannot nominate these arbitrary SCM nodes, so this team-authored Backlog request should remain open.

## Change summary

Allow tree consumers to programmatically designate nodes such as SCM input controls, action buttons, and Incoming/Outgoing headers as sticky.

## Best solution

Define sticky-node selection semantics that can retain designated non-ancestor nodes, then use them in the Source Control tree for its input, action button, and relevant resource-group headers without disturbing ordinary ancestor-based sticky scroll.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/tree/abstractTree.ts`, `src/vs/base/browser/ui/tree/asyncDataTree.ts`, `src/vs/base/test/browser/ui/tree/objectTree.test.ts`, `src/vs/workbench/contrib/scm/browser/scmViewPane.ts`
- **Validation:** Create a long Source Control resource list and verify that the chosen input/action controls and Incoming/Outgoing header remain visible while their content scrolls, including single- and multi-repository layouts; add a tree browser test showing designated non-ancestor nodes follow the agreed sticky lifetime while existing ancestor sticky-scroll tests remain unchanged.
- **Behavior:**

  > Tree consumers can designate nodes whose controls or section context remain visible while related descendants or sibling content scroll. In Source Control, the commit input and action control remain usable as agreed, and Incoming/Outgoing headers identify the currently visible section. Ordinary tree sticky scroll, maximum-item limits, keyboard interaction, and trees without custom designation retain their existing behavior. Acceptance must cover both single- and multi-repository Source Control layouts.
- **Trace:**

  > StickyScrollController in src/vs/base/browser/ui/tree/abstractTree.ts derives candidates with getAncestorUnderPrevious, restricting sticky rows to the first visible node's ancestor chain. Commit https://github.com/microsoft/vscode/commit/34a41e00d4609f76a472da3a7feb0a0090430d1c added stickyScrollNodeSourceRangeProvider, but that API only changes the source range of an already selected ancestor or suppresses it. SCMTreeDataSource.getChildren in src/vs/workbench/contrib/scm/browser/scmViewPane.ts emits the input, action button, and resource groups as repository-child siblings, so scrolling inside a resource group cannot retain the preceding leaf controls. The boundary is custom selection and SCM adoption: preserve default ancestor-based behavior for every consumer that does not opt in, along with existing sticky-scroll height and item-count constraints.
- **Open decisions:**
  - Should the SCM input and action button remain pinned throughout the entire repository, or only while scrolling the repository's first resource section?
  - In a multi-repository layout, should sticky controls be shown only for the repository containing the visible resources, and should they be replaced when scrolling into the next repository?

## Evidence

- **current sticky algorithm:** src/vs/base/browser/ui/tree/abstractTree.ts selects each candidate through StickyScrollController.getAncestorUnderPrevious, so sticky candidates must belong to the first visible node's ancestor path.
- **SCM hierarchy:** SCMTreeDataSource.getChildren in src/vs/workbench/contrib/scm/browser/scmViewPane.ts places the SCM input, action button, and resource groups beside one another as children of the repository; the input and action button therefore cannot remain sticky while scrolling through a resource-group subtree.
- **partial later capability:** Commit https://github.com/microsoft/vscode/commit/34a41e00d4609f76a472da3a7feb0a0090430d1c added stickyScrollNodeSourceRangeProvider. The callback can adjust or suppress a candidate ancestor, but it does not nominate arbitrary sibling nodes and the SCM tree does not configure it.
