# Issue #340148 — Snap: system-wide font in /usr/share/fonts not used, falls back to DejaVu Sans Mono

[https://github.com/microsoft/vscode/issues/340148](https://github.com/microsoft/vscode/issues/340148)

## Summary

Thanks for the very thorough write-up. This is a fresh, well-diagnosed report that looks like a distinct variant of the Snap font-loading problems already seen in this repo (#232578, #233333, #46581), but it's specifically about system-wide `/usr/share/fonts` fonts rather than per-user fonts, no maintainer has looked at it yet, and we can't confirm the root cause (snap confinement/mount visibility vs. Chromium font matching) from source alone.

## Change summary

On the Snap build, a system-wide font installed under /usr/share/fonts is resolved correctly by fontconfig but is never actually opened/read by the renderer, so the editor silently falls back to DejaVu Sans Mono.

## Best solution

A maintainer with snap-build access should reproduce this against current main's electron-launch/fontconfig setup and determine whether the gap is in VS Code's snap packaging (resources/linux/snap/electron-launch, resources/linux/snap/snapcraft.yaml) or in Chromium's font-matching layer for classic-confinement snaps; if it's upstream, it should be filed against Electron/Chromium instead.

## Plan brief

- **Likely files:** `resources/linux/snap/electron-launch`, `resources/linux/snap/snapcraft.yaml`
- **Validation:** Reproduce on a real Snap build (classic confinement) with a system-wide-only font and confirm via `/proc/<pid>/maps` whether the ttf file is opened after any proposed change; no existing automated test covers Snap font loading.
- **Behavior:**

  > On the Snap package, a font installed system-wide under /usr/share/fonts and set via editor.fontFamily should actually render in the editor, matching what `fc-match` and the GTK font chooser already report on the host. Currently it falls back to DejaVu Sans Mono even though fontconfig's own cache (under FONTCONFIG_FILE=/etc/fonts/fonts.conf) correctly lists the font family and the computed CSS font-family includes it.
- **Trace:**

  > resources/linux/snap/electron-launch sets FONTCONFIG_PATH=/etc/fonts and FONTCONFIG_FILE=/etc/fonts/fonts.conf (the host's config), and resources/linux/snap/snapcraft.yaml deliberately excludes `-usr/share/fonts` from the snap's own prime so the snap relies solely on classic confinement's host filesystem access. The reporter verified fontconfig's cache correctly enumerates the font files under /usr/share/fonts/truetype/jetbrains-mono, yet none of those files ever appear in the process's /proc/<pid>/maps, meaning fontconfig resolves the match but something downstream (likely Chromium's Skia/FontConfig bridge, or a confinement/mount-visibility quirk for nested font subdirectories) never opens the file. This repo's own config doesn't filter or restrict that directory, so the boundary for any fix here is electron-launch/snapcraft.yaml; if the gap is in Chromium itself, the next step is filing upstream. Related, but not the same symptom: https://github.com/microsoft/vscode/issues/232578, https://github.com/microsoft/vscode/issues/233333, https://github.com/microsoft/vscode/issues/46581.
- **Open decisions:**
  - Does this belong to VS Code's snap packaging (electron-launch/snapcraft.yaml) or is it an upstream Chromium/Electron font-loading limitation that should be filed against Electron instead?
  - Is the defect specific to nested font subdirectories (e.g. /usr/share/fonts/truetype/jetbrains-mono) versus flat system font directories, which would narrow the investigation?
