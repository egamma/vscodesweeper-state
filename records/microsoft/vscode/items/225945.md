# Issue #225945 — Error: `No view is registered with id` might be caused by a race condition

[https://github.com/microsoft/vscode/issues/225945](https://github.com/microsoft/vscode/issues/225945)

## Summary

Keep open: two extension authors reproduced stale view registrations after Update and Restart Extensions, and the reporter confirmed the problem remained in VS Code 1.95.3 after a maintainer mentioned a possible fix. The prior review's proposed fix commit was independently refuted, so there is no verified completed fix.

## Change summary

Restarting extension hosts after an extension update can retain or resolve stale contributed view IDs before the updated extension has registered its views, producing “No view is registered with id” errors.

## Best solution

Trace and correct the extension-restart/view-registration lifecycle so updated view contributions are reconciled before restored or newly contributed views are resolved, without requiring extensions to call `createTreeView` synchronously before asynchronous activation work.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/common/extensions.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsActions.ts`, `src/vs/workbench/browser/parts/views/viewsService.ts`

- **Behavior:**

  > Updating an installed extension and choosing Restart Extensions must not produce “No view is registered with id” for views contributed by either the old or updated extension manifest. Extensions with asynchronous activation must be able to register tree views during normal activation without a synchronous `createTreeView` workaround. Acceptance should cover an update that adds view IDs, an extension-host restart, absence of the error notification, and successful availability of the new views.
- **Trace:**

  > The reported trigger is specifically Update followed by Restart Extensions; installing an older GitLens version and restarting without an update does not fail, while updating and restarting does. A second author reports that only two newly added view IDs fail after restart, which points to stale contribution/view restoration state rather than a generic activation failure. The reporter's synchronous `createTreeView` workaround narrows the uncertainty to ordering between extension activation and view resolution, but the source path and exact owner of the race are not yet conclusive. Trace the restart action through the extension service and the workbench view registration/restoration path; preserve ordinary startup, extension disable/uninstall behavior, and lazy activation semantics. The related https://github.com/microsoft/vscode/issues/224590 is closed and concerns view name/ID guidance, so it does not currently provide an open canonical for this restart race.
