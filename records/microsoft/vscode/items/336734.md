# Issue #336734 — vscode-automation-mcp not offered for migration

[https://github.com/microsoft/vscode/issues/336734](https://github.com/microsoft/vscode/issues/336734)

## Summary

Real gap in the AI Customization MCP migration flow: a server using `${workspaceFolder}` in `cwd` is excluded from the migration offer, and the merged workaround PR only hand-migrated this one repo's server rather than fixing the underlying eligibility check.

## Change summary

The chat customization migration page doesn't offer `vscode-automation-mcp` (from `.vscode/mcp.json`) for migration to `.mcp.json`, apparently because its `cwd` contains an unresolved `${workspaceFolder}` variable.

## Best solution

Either resolve `${workspaceFolder}`/other supported variables against the source folder before the eligibility check in `mcpServerCustomizationMigration.ts`/`agentHostMcpServerSupport.ts`, or (per the reporter's own suggestion) let the agent perform the migration interactively with a guiding prompt/FAQ instead of trying to hardcode every substitution case — a maintainer should pick the direction.

- **Behavior:**

  > A `.vscode/mcp.json` server whose configuration (e.g. `cwd`) references `${workspaceFolder}` should be offered for migration to `.mcp.json` on the AI Customization page, the same as servers without variables. Acceptance: the migration plan includes such a server as a candidate, and the actual migrated `.mcp.json` entry has the variable correctly substituted or preserved in a form the agent host can still resolve.
- **Trace:**

  > `McpServerCustomizationMigrator.createPlan` (mcpServerCustomizationMigration.ts) only includes servers passing `isMcpServerMigrationDeliverable`, which requires `compatibility.kind === 'supported'`. Compatibility comes from `resolveInstalledMcpServerCompatibility`-family logic in agentHostMcpServerSupport.ts, which resolves variables via `resolveMcpConfigurationForSync(configurationResolverService, definition.variableReplacement?.folder, projectedConfiguration)` — if `${workspaceFolder}` doesn't resolve there, the reason becomes `UnresolvedConfiguration` and the server is excluded with `NoLongerEligible`. The reporter confirmed this by hand-migrating with npm's `--prefix` in PR #336751 (merged, commit 53e9983), which only touched this repo's `.mcp.json`, not the general logic. Boundary: do not change the actual MCP server launch/runtime resolution (`mcpRegistry.ts` `_replaceVariablesInLaunch`), which already works correctly at runtime — only the migration-eligibility path is affected. Where uncertainty starts: whether `.vscode/mcp.json`-sourced definitions populate `variableReplacement.folder` correctly in all discovery code paths, and which of the two design directions (hardcode resolution vs. agent-guided migration) the maintainers prefer.
- **Open decisions:**
  - Should the migration planner resolve common variables like `${workspaceFolder}` itself before the eligibility check, or should unmigratable servers instead be handed to the agent with a guiding prompt/FAQ to do the migration interactively?
  - If resolving variables directly, which variable set is safe to hardcode (workspaceFolder only, or the full configuration-resolver variable set), and does that risk producing an `.mcp.json` that's no longer portable across machines?
