# Issue #143667 — Layout picker isn't accessible

[https://github.com/microsoft/vscode/issues/143667](https://github.com/microsoft/vscode/issues/143667)

## Summary

Keep open: Customize Layout still exposes layout choices without semantic checked states or accessible option groups. The linked fix attempt was closed without merging, and the source confirms the gap remains.

## Change summary

Make the active Side Bar Position and Panel Alignment options, and their grouping, accessible to screen readers.

## Best solution

Expose layout option groups and their current selection through appropriate accessibility semantics in the quick-input infrastructure, preserving existing layout actions and ordinary quick-pick behavior. Validate the resulting announcements with VoiceOver and NVDA.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/actions/layoutActions.ts`, `src/vs/platform/quickinput/common/quickInput.ts`, `src/vs/platform/quickinput/browser/quickInputList.ts`, `src/vs/platform/quickinput/test/browser/quickinput.test.ts`
- **Validation:** Extend the QuickInput browser tests with grouped, single-selection layout options and assert accessible group labels and active-state semantics before and after selection changes. Manually enable screen reader mode, run workbench.action.customizeLayout, navigate Side Bar Position and Panel Alignment, and verify VoiceOver and NVDA announce the group and current selection correctly. Check ordinary single-select and multi-select quick picks retain their behavior.
- **Behavior:**

  > In Customize Layout, screen reader users must be able to identify the active Side Bar Position and Panel Alignment choices and understand which group each choice belongs to. Changing an option must update the accessible state to match the visible layout. Keyboard navigation, activation, focus retention, and independent visibility toggles must remain functional. Acceptance requires semantic accessibility assertions and successful VoiceOver and NVDA checks, not merely an '(Active)' label string.
- **Trace:**

  > CustomizeLayoutAction.getItems in src/vs/workbench/browser/actions/layoutActions.ts evaluates layout context keys but expresses active state only through icons and ariaLabel text. QuickInputAccessibilityProvider in src/vs/platform/quickinput/browser/quickInputList.ts assigns ordinary options and supplies checked state only for checkbox items; setElements omits buttonless separators as standalone group elements. The internal item and separator interfaces in src/vs/platform/quickinput/common/quickInput.ts do not express the requested semantics. This establishes the source-level gap, but platform-specific speech has not been tested. https://github.com/microsoft/vscode/pull/275954 is an unmerged prior approach, not a shipped solution. The boundary is accessibility for layout choices and reusable quick-pick support: preserve ordinary picker selection, filtering, focus, and independent toggle behavior. The unresolved design is the accessible interaction contract for mixed option groups inside the existing listbox.
- **Open decisions:**
  - Should mutually exclusive layout choices be exposed as radio groups, or through grouped listbox options with explicit selection semantics, while preserving the existing single-list keyboard interaction?
  - Should client-defined accessibility roles and state be a general internal quick-pick capability, as requested in the discussion, or a narrower contract for grouped choices?
