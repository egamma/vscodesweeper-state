# Issue #184288 — Allow separate `when` clauses for each command in a keybinding with multiple commands

[https://github.com/microsoft/vscode/issues/184288](https://github.com/microsoft/vscode/issues/184288)

## Summary

Per-command conditions remain unsupported in the current runCommands implementation. Keep this accepted On Deck request open: the existing keybinding-level condition does not cover it, and the related reports do not provide a qualifying canonical or landed implementation.

## Change summary

Allow individual commands within a runCommands sequence to have independent when clauses while preserving sequential execution.

## Best solution

Provide declarative per-step conditions in runCommands without changing existing unconditional sequences or outer keybinding conditions. Settle which context scope conditions use when earlier commands move focus, then validate conditional execution against changing context.

Include an earlier command that changes context and a focus-changing sequence to verify the agreed scope semantics. Manually exercise SCM navigation over files and collapsible nodes.
- **Behavior:**

  > A runCommands sequence can condition each command independently using a when expression. Matching commands execute in their original order, nonmatching commands are skipped, and entries without conditions retain existing behavior. The outer keybinding condition continues to gate the entire sequence. Acceptance checks cover mixed conditions, argument forwarding, context changes caused by earlier commands, and the agreed behavior when focus moves.
- **Trace:**

  > RunCommands in src/vs/workbench/contrib/commands/common/commands.contribution.ts currently awaits every entry and forwards only its command and args; the schema provides no explicit per-step when support. AbstractKeybindingService in src/vs/platform/keybinding/common/abstractKeybindingService.ts evaluates the outer keybinding using the keyboard event target's scoped context, whereas CommandService invokes handlers without carrying that target as a conditional-execution contract. The SCM example in the thread needs a later command to respond to state after navigation; it is not satisfied by another outer keybinding condition. The unresolved boundary is which scoped context a later step observes after focus changes, including invocation outside a keybinding. Preserve existing sequencing, arguments, error handling, and unconditional command execution; do not turn conditions into waits or expose a general context-reading API. Related evidence: https://github.com/microsoft/vscode/issues/189980 and https://github.com/microsoft/vscode/issues/249741.
- **Open decisions:**
  - When an earlier step moves focus, should subsequent when clauses use the original invocation target's context or the newly focused target's context, and what context should apply when runCommands is invoked programmatically?

## Evidence

- **Current capability gap:** In src/vs/workbench/contrib/commands/common/commands.contribution.ts, RunnableCommand contains only a command and arguments; RunCommands.run awaits every entry, and _runCommand extracts only command and args before calling ICommandService.executeCommand. No per-entry when expression is evaluated.
- **Existing conditions are not equivalent:** src/vs/platform/keybinding/common/abstractKeybindingService.ts resolves the outer keybinding against getContext(target). src/vs/workbench/services/commands/common/commandService.ts then invokes registered command handlers without evaluating per-step conditions.
