# Issue #337240 — Scrollbars on Terminal, Debug Output, etc. panels need buttons for precision scrolling

[https://github.com/microsoft/vscode/issues/337240](https://github.com/microsoft/vscode/issues/337240)

## Summary

Accessibility-motivated feature request with a genuine, unaddressed gap: the base scrollbar component already supports arrow buttons (verticalHasArrows/horizontalHasArrows) but every consumer explicitly disables them, and no setting exposes this to users; keeping open pending maintainer interest and a design for which surfaces to cover.

## Change summary

Add clickable up/down (and left/right) scrollbar arrow buttons to output-style panels (Terminal, Debug Console, etc.) so users who can't rely on mouse-wheel/gesture scrolling can navigate precisely.

## Best solution

A maintainer should scope this: for tree/list-based panels like the Debug Console (WorkbenchAsyncDataTree over the base ScrollableElement), a setting could flip verticalHasArrows on; the integrated Terminal renders via xterm.js and doesn't use this component at all, so that half of the request may need a different (or upstream xterm) solution or could be descoped.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/scrollbar/scrollableElementOptions.ts`, `src/vs/workbench/contrib/debug/browser/repl.ts`, `src/vs/workbench/contrib/terminal/browser/xterm/xtermTerminal.ts`
- **Validation:** A test (or manual check) confirming a new setting renders visible up/down arrow buttons on the target panel's scrollbar and that clicking them scrolls by one line.
- **Trace:**

  > The base ScrollableElement stack (src/vs/base/browser/ui/scrollbar/*.ts) already implements arrow buttons behind verticalHasArrows/horizontalHasArrows, but every current consumer disables them and no setting exposes them. The Debug Console (src/vs/workbench/contrib/debug/browser/repl.ts) uses a WorkbenchAsyncDataTree that could plausibly surface this option, while the integrated Terminal is rendered by the external xterm.js library (src/vs/workbench/contrib/terminal/browser/xterm/xtermTerminal.ts) and does not go through this component at all — that's where the uncertainty starts: whether/how to expose arrows for xterm's own scrollbar, and whether a single setting should cover both panels or the scope should be split per-surface.
- **Open decisions:**
  - Should this be a single global setting enabling arrow buttons on all applicable scrollbars, or a per-panel/per-feature toggle?
  - Is the integrated Terminal (xterm.js-rendered) in scope at all, or should this be limited to core tree/list/editor scrollbars where the existing arrow infra already applies?
  - If in scope for Terminal, does that require an xterm.js addon/upstream capability, or can core wrap its own overlay scrollbar?

## Evidence

- **arrow infra exists but unused:** src/vs/base/browser/ui/scrollbar/scrollableElementOptions.ts defines verticalHasArrows/horizontalHasArrows/arrowSize, implemented in verticalScrollbar.ts and horizontalScrollbar.ts, but every call site found (editor, peek widgets, notebook output/cell editors, comments editor, scm quickDiffWidget, callHierarchy/typeHierarchy peeks) explicitly passes verticalHasArrows: false / horizontalHasArrows: false — no consumer enables it and no user setting toggles it.
- **terminal is out of this component's reach:** The integrated Terminal renders via xterm.js (src/vs/workbench/contrib/terminal/browser/xterm/xtermTerminal.ts imports @xterm/xterm) which manages its own scrollbar, so enabling core's arrow option would not cover the Terminal case the reporter leads with — a distinct implementation path (or upstream xterm capability) would be needed there.
- **debug console is tree-based:** src/vs/workbench/contrib/debug/browser/repl.ts renders output via WorkbenchAsyncDataTree, which is built on the base list/scrollbar stack where arrow support could plausibly be surfaced.
- **no true duplicate found:** Candidate canonicals (scrollbar width #30191, visibility setting #66000, opaque scrollbar #48153, drag scrollbars #124895, focus-follow-mouse #93772, chat scrollbar size #292800, umbrella #334285) all address different scrollbar concerns, not arrow-button precision scrolling; the reporter also explicitly distinguishes this from #22636 and #142590.
