# Issue #337240 — Scrollbars on Terminal, Debug Output, etc. panels need buttons for precision scrolling

[https://github.com/microsoft/vscode/issues/337240](https://github.com/microsoft/vscode/issues/337240)

## Summary

Fresh, unrouted accessibility-motivated feature request asking for scroll-arrow buttons on the Terminal/Debug Console scrollbars; VS Code's base ScrollableElement already supports arrow rendering (`verticalHasArrows`/`horizontalHasArrows`) but it's unused everywhere in the product today, so no existing setting covers this — routing to the relevant areas rather than closing.

## Change summary

Add clickable up/down (and left/right) arrow buttons on the scrollbars of output-style panels (Terminal, Debug Console) for precision, non-gesture scrolling.

## Best solution

Have the terminal/debug/accessibility area owners weigh in on scope: the underlying `ScrollableElement` in src/vs/base/browser/ui/scrollbar already implements arrow rendering but it's disabled by default everywhere, so exposing it (likely first for the Monaco-based Debug Console) is more tractable than for the xterm.js-rendered Terminal panel, which has no such hook.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/scrollbar/scrollableElementOptions.ts`, `src/vs/editor/common/config/editorOptions.ts`, `src/vs/workbench/contrib/terminal/browser`
- **Validation:** A setting that enables scrollbar arrows should show clickable up/down buttons in the Debug Console; clicking one scrolls by a single line/unit. No concrete test exists yet — the plan should define one.
- **Trace:**

  > The base `ScrollableElement` (src/vs/base/browser/ui/scrollbar) already implements `verticalHasArrows`/`horizontalHasArrows` rendering, but no consumer in the editor, workbench, or terminal currently turns it on — confirmed by finding zero non-test call sites setting it to true. The Terminal panel is rendered by xterm.js, which does not use this widget at all, so any terminal-side fix is a separate implementation from an editor/Debug-Console-side one.
- **Open decisions:**
  - Should this ship as an opt-in setting or become default-on, given the 'simple, uniform UI' guardrail against added chrome?
  - Should the first iteration cover just Monaco-editor-based panels (Debug Console, output channels) where the existing `hasArrows` option can be wired up, or also the xterm.js-rendered Terminal panel, which needs new plumbing?
  - Should the setting apply globally to all scrollable widgets or be scoped to specific views?

## Evidence

- **latent capability:** src/vs/base/browser/ui/scrollbar/scrollableElementOptions.ts defines `verticalHasArrows`/`horizontalHasArrows` options for ScrollableElement, but a repo-wide search found this only set to true in a single layout unit test (src/vs/editor/test/browser/config/editorLayoutProvider.test.ts) — it is not wired up as a real setting anywhere in the editor, terminal, or debug console.
- **terminal rendering:** The integrated terminal (src/vs/workbench/contrib/terminal) renders via xterm.js canvas/DOM rather than the base ScrollableElement, so enabling arrows there would need separate work beyond flipping the existing option.
- **no existing setting:** terminalConfiguration.ts only exposes scroll-speed multipliers (FastScrollSensitivity, MouseWheelScrollSensitivity), not a scrollbar-arrow toggle.
