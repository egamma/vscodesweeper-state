# Issue #30795 — Can the VSCode gutter be made smaller, i.e., decreased size/width?

[https://github.com/microsoft/vscode/issues/30795](https://github.com/microsoft/vscode/issues/30795)

## Summary

Keep open: current settings can reduce the gutter, including hiding folding controls without disabling keyboard folding, but fine-grained width controls remain undocumented. This accepted, well-supported request is already the maintainer-designated tracking issue; the newer related requests do not supersede its scope.

## Change summary

Allow users to reduce the editor gutter's width without unnecessarily sacrificing useful editor features.

## Best solution

Provide a supported, discoverable way to compact the gutter while retaining the user's chosen line-number and folding functionality. Decide whether this means exposing existing width controls or changing the default spacing, and coordinate the overlapping configuration work with https://github.com/microsoft/vscode/issues/93887.

- **Validation:** After choosing the configuration contract, add targeted configuration-schema and EditorLayoutInfoComputer tests demonstrating reduced contentLeft for a short file while retaining visible line numbers and enabled keyboard folding. Manually verify the selected settings in the Settings UI and confirm folding commands still work; no tests or builds were run during this read-only review.
- **Behavior:**

  > Users want a narrower editor gutter, especially for short files and side-by-side editing. Existing visibility settings reduce its width, but removing line numbers or disabling folding is not an adequate substitute for compact spacing. The selected solution should be discoverable and preserve the editor features the user chooses to retain. Acceptance should demonstrate a narrower gutter with line numbers visible and keyboard folding functional, and document whether default layouts change.
- **Trace:**

  > EditorLayoutInfoComputer.computeLayout in src/vs/editor/common/config/editorOptions.ts sums glyph-margin width, line-number width, and decoration width into contentLeft. Line-number width uses the greater of the actual digit count and lineNumbersMinChars; folding adds 16 pixels unless showFoldingControls is 'never'. Existing lineDecorationsWidth and lineNumbersMinChars controls have no schemas, so src/vs/editor/common/config/editorConfigurationSchema.ts omits them from registered settings. The existing layout test suite in src/vs/editor/test/browser/config/editorLayoutProvider.test.ts exercises these width components, though its helper currently disables folding. Keep clickable content padding, right-side line numbers, and unrelated gutter APIs outside this scope. Coordinate with https://github.com/microsoft/vscode/issues/93887; the maintainer explicitly consolidated gutter-related work here in https://github.com/microsoft/vscode/issues/103389#issuecomment-686768421. The uncertainty is the supported user-facing configuration and whether the default spacing should change, not the width calculation itself.
- **Open decisions:**
  - Should compact gutter spacing remain opt-in through supported width settings, or should the default gutter become narrower?
  - Should users configure the existing line-number and decoration widths separately, or receive a single compact-gutter setting?
