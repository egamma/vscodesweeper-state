# Issue #340305 — Terminal link detection runs `wsl.exe -e wslpath` without `-d`, starting the default WSL distro

[https://github.com/microsoft/vscode/issues/340305](https://github.com/microsoft/vscode/issues/340305)

## Summary

Traced in current main: `getWslPath` in src/vs/platform/terminal/node/ptyService.ts spawns `wsl.exe -e wslpath [-w] <path>` with no `-d <distro>` argument, so link resolution always targets the default WSL distro regardless of which distro the terminal is actually running in — a real, confirmed defect worth fixing, not a design choice.

## Change summary

Terminal file-link resolution calls `wsl.exe -e wslpath` without specifying the terminal's own WSL distro, which starts the unrelated default distro (and anything it autostarts) whenever a `/mnt/...` path is printed.

## Best solution

Thread the terminal's actual WSL distro (not just the default) through to `getWslPath` so it calls `wsl.exe -d <distro> -e wslpath ...`; this needs a decision on how the running distro is determined for a given terminal, since VS Code doesn't currently track it end-to-end.

## Plan brief

- **Likely files:** `src/vs/platform/terminal/node/ptyService.ts`, `src/vs/platform/terminal/common/terminal.ts`, `src/vs/platform/terminal/node/ptyHostService.ts`, `src/vs/workbench/contrib/terminalContrib/links/browser/terminalLinkResolver.ts`
- **Validation:** A test asserting `getWslPath`/the underlying spawn passes `-d <distro>` to `wsl.exe` when a distro is known for the terminal, and existing behavior is preserved when it isn't.
- **Behavior:**

  > Resolving a `/mnt/<drive>/...` terminal link (or the reverse direction) must not start or wake any WSL distro other than the one the terminal is actually running in. When the terminal's distro is known, `wsl.exe` should be invoked with `-d <that distro>`; the unrelated default distro should never be launched as a side effect of link resolution. Acceptance: a new/updated test confirms the spawned command includes the correct `-d` argument when distro info is available.
- **Trace:**

  > The defect is in `getWslPath` in src/vs/platform/terminal/node/ptyService.ts (around lines 509-549): both the win-to-unix and unix-to-win branches call `execFile(wslExecutable, ['-e', 'wslpath', ...], ...)` with no `-d` argument, so `wsl.exe` always resolves against the default distro. The call originates from `terminalLinkResolver.ts:78` (`processManager.backend.getWslPath(linkUrl, 'unix-to-win')`), and nothing in that chain currently carries which WSL distro the terminal process belongs to — `terminalProfiles.ts:380` shows VS Code already knows how to pass `-d <distroName>` for WSL *profile launches*, but that value isn't persisted onto the terminal process/backend for later use by link resolution. The boundary: don't change WSL profile creation or the general local-link detection flow; only the distro-targeting of the `wslpath` invocation. Where uncertainty starts: whether the right distro comes from the shell launch config's `-d` arg, from the running shell's `WSL_DISTRO_NAME` env var, or needs a new explicit tracking mechanism — none of these is settled by the issue or current code.
- **Open decisions:**
  - How should VS Code determine the WSL distro a given terminal is actually running in — from the shell launch config's `-d` argument, from an environment variable of the running shell, or some other signal?
  - What should happen when the distro can't be determined (e.g. terminal was launched with a plain shell and the user manually ran `wsl -d B`) — fall back to current default-distro behavior, or skip link conversion entirely?

## Evidence

- **confirmed on main:** src/vs/platform/terminal/node/ptyService.ts lines ~509-549: `getWslPath` builds `execFile(wslExecutable, ['-e', 'wslpath', original], ...)` and `['-e', 'wslpath', '-w', original]` with no `-d` argument in either direction.
- **call path:** src/vs/workbench/contrib/terminalContrib/links/browser/terminalLinkResolver.ts:78 calls `processManager.backend.getWslPath(linkUrl, 'unix-to-win')` for `/mnt/...` links; no distro context is passed anywhere in this chain.
- **distro info exists elsewhere but isn't threaded through:** src/vs/platform/terminal/node/terminalProfiles.ts:380 builds WSL profiles with explicit `args: ['-d', distroName]`, showing VS Code already models per-distro launch args for profiles, but that data isn't propagated to the link-resolution path.
- **related but distinct issues:** https://github.com/microsoft/vscode/issues/326576 (visible console window for `wsl -l -q`) and https://github.com/microsoft/vscode/issues/326670 (synchronous CreateProcessW blocking) touch nearby WSL code but describe different symptoms/root causes; neither covers this missing `-d` argument.
