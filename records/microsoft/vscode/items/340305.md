# Issue #340305 — Terminal link detection runs `wsl.exe -e wslpath` without `-d`, starting the default WSL distro

[https://github.com/microsoft/vscode/issues/340305](https://github.com/microsoft/vscode/issues/340305)

## Summary

The reported command is still present on current main: terminal link resolution invokes wslpath without identifying the terminal's distro. Route this to the terminal area; the supplied related issues concern different triggers and do not justify a duplicate close.

## Change summary

Resolving /mnt/<drive>/ terminal links starts the default WSL distro even when the terminal is running in another distro.

## Best solution

Preserve clickable WSL drive-mount links without starting an unrelated distro. Establish how conversion obtains the correct terminal context, including a safe outcome when that context is unavailable, while preserving existing remote and UNC link behavior.

- **Validation:** On Windows with stopped default distro A and running distro B, open a local terminal using wsl.exe -d B with file links enabled, print the report's existing /mnt/c/... file path, and monitor process creation and wsl --list --running through repeated link detection. Acceptance: A remains stopped and the link opens the correct Windows file. Extend the Windows terminalLocalLinkDetector suite to cover the chosen conversion contract and retain existing /mnt/, UNC, suffix, and remote-link coverage.
- **Behavior:**

  > In a local Windows workspace, detecting a /mnt/<drive>/ file link in a terminal running distro B must not start unrelated default distro A. Existing drive-mount file links should remain clickable and open the correct file without requiring users to disable file links or change their WSL default. Acceptance includes repeated detection after cache expiry, with A remaining stopped. Existing Windows, WSL UNC, and remote link behavior must remain unchanged.
- **Trace:**

  > TerminalLinkResolver.resolveLink in src/vs/workbench/contrib/terminalContrib/links/browser/terminalLinkResolver.ts recognizes /mnt/[a-z] on Windows frontends and calls backend.getWslPath before checking file existence. LocalTerminalBackend and PtyHostService forward only path and direction, and PtyService.getWslPath in src/vs/platform/terminal/node/ptyService.ts executes wsl.exe with ['-e', 'wslpath', '-w', original], conclusively confirming the missing distro selector. Resolver caches are partitioned by remote authority rather than distro and expire after ten seconds, so repeated conversion remains possible. TerminalProcessManager retains shell launch configuration privately, but this review has not established a reliable identity source for the active distro, especially when WSL is entered from an existing shell. Existing Windows detector tests mock conversion and cannot detect an unintended distro launch. The boundary includes shared win-to-unix conversion consumers and remote backends; those must not change incidentally. The full reproduction and process measurements are recorded at https://github.com/microsoft/vscode/issues/340305.
