# Issue #325592 — Agents window welcome sign in experience is not working with GH enterprise

[https://github.com/microsoft/vscode/issues/325592](https://github.com/microsoft/vscode/issues/325592)

## Summary

Keep open: a maintainer reproduced the GitHub Enterprise instance-entry failure during the Agents window test plan, and no eligible factual close was found. The item is team-authored and already accepted as a bug, while neither an explicitly linked fix nor an older canonical with the same observable symptom exists.

## Change summary

Selecting GitHub Enterprise from the Agents window welcome sign-in flow opens an instance dialog that does not allow the GHE.com hostname to be entered.

## Best solution

Make the Agents window welcome flow collect and accept the GitHub Enterprise hostname before starting authentication, while preserving the existing GitHub.com path. First confirm the current desktop behavior and trace the handoff between Sessions setup and the GitHub Enterprise authentication provider.

## Plan brief

- **Likely files:** `src/vs/sessions/browser/sessionsSetUpService.ts`, `extensions/github-authentication/src/githubEnterprise.ts`, `extensions/github-authentication/src/extension.ts`
- **Validation:** Launch an isolated desktop Agents window with `code-insiders --transient --agents`, select GitHub Enterprise, enter a valid GHE.com hostname, and verify submission advances into authentication; repeat the GitHub.com selection to confirm it remains unchanged.
- **Behavior:**

  > From a fresh Agents window, selecting GitHub Enterprise must present an editable enterprise-instance field. Entering a valid GHE.com hostname and submitting it must continue the authentication flow rather than leave the user blocked. GitHub.com sign-in must continue to work without requiring an enterprise hostname.
- **Trace:**

  > The initial desktop flow starts in `SessionsSetUpService._showWelcome` and `_showWelcomeDialog` in src/vs/sessions/browser/sessionsSetUpService.ts. The built-in provider in extensions/github-authentication/src/githubEnterprise.ts cannot create a session until an enterprise URI has been configured, while extensions/github-authentication/src/extension.ts reads that URI from `github-enterprise.uri`. The current uncertainty is the UI handoff that should collect and persist the hostname after the welcome dialog selects GitHub Enterprise; reproduce that handoff before choosing the owning layer. Do not conflate this with https://github.com/microsoft/vscode/issues/316511, which fails later during model discovery, or the Android-specific submission problem in https://github.com/microsoft/vscode/issues/332163.
