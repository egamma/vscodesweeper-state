# Issue #50692 — QuickPick API is no longer type safe

[https://github.com/microsoft/vscode/issues/50692](https://github.com/microsoft/vscode/issues/50692)

## Summary

The public API remains unsound when a multi-select options object is explicitly typed as `QuickPickOptions`: TypeScript selects the single-item overload while the runtime returns an array. This is the canonical report for the gap and should remain open for a backward-compatible API design.

## Change summary

Make `window.showQuickPick` return typing accurately reflect `canPickMany` when callers pass an explicitly typed `QuickPickOptions` value.

## Best solution

Define a backward-compatible public typing contract that returns an array for statically known multi-select options and a safe union when `canPickMany` is not known at compile time, while preserving existing literal-object inference.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostQuickOpen.ts`
- **Validation:** Compile TypeScript declaration fixtures covering omitted options, literal `false`, literal `true`, an explicitly typed `QuickPickOptions` with `canPickMany: true`, and a runtime boolean; assert that each inferred return type matches the selected behavior contract without breaking existing extension sources.
- **Behavior:**

  > Calling `window.showQuickPick` must expose a return type consistent with whether multiple selection can occur. Literal `canPickMany: true` must infer an array, single-select calls must retain their single-item type, and an explicitly typed or dynamically valued `QuickPickOptions` must not claim that an array is impossible when runtime behavior permits one. Existing source-compatible QuickPick usage must continue compiling.
- **Trace:**

  > The public overloads in src/vscode-dts/vscode.d.ts discriminate only on the intersection `QuickPickOptions & { canPickMany: true }`. A value declared as `QuickPickOptions` cannot satisfy that literal intersection, so overload resolution selects the single-item signature even when its runtime property is true. The implementation in src/vs/workbench/api/common/extHostQuickOpen.ts already models and returns `Item | Item[] | undefined`, so the gap is in the public declaration contract rather than widget behavior. The linked https://github.com/microsoft/vscode/issues/64014 is a younger duplicate and does not replace this canonical issue. Preserve literal-object inference and runtime behavior; the uncertainty begins at the public return type for options whose `canPickMany` value is not statically known.
- **Open decisions:**
  - When the static type of `canPickMany` is `boolean` or otherwise unknown, should the public return type become `T | T[] | undefined`, or should the API introduce a distinct options contract that requires callers to state the selection mode?
  - Can explicitly typed `QuickPickOptions` values with `canPickMany: true` gain an array result without a breaking change, or must soundness take precedence by widening their result to a union?

## Evidence

- **current declaration:** src/vscode-dts/vscode.d.ts:11421 and :11441 return arrays only for `QuickPickOptions & { canPickMany: true }`; the fallback overloads at :11431 and :11451 accept a general `QuickPickOptions` but return only one item.
- **runtime mismatch:** src/vs/workbench/api/common/extHostQuickOpen.ts forwards `options.canPickMany` to the quick-pick widget and its implementation return type is `Promise<Item | Item[] | undefined>`, confirming that a general `QuickPickOptions` value can produce an array at runtime.
- **maintainer confirmation:** https://github.com/microsoft/vscode/issues/50692#issuecomment-393063596 confirms that explicitly typing the options as `QuickPickOptions` prevents the multi-select signature from matching.
- **unresolved API decision:** https://github.com/microsoft/vscode/issues/50692#issuecomment-393483605 records the backward-compatibility constraint and the unresolved behavior for options whose `canPickMany` value is not statically known.
- **canonical status:** The same observable problem in the newer https://github.com/microsoft/vscode/issues/64014 was closed as a duplicate of this issue, so it is evidence that this report owns the remaining work rather than a canonical to close against.
