# Issue #349813 — Sandbox Profiles: Readonly view is inconsistent with settings and profiles UI

[https://github.com/microsoft/vscode/issues/349813](https://github.com/microsoft/vscode/issues/349813)

## Summary

Keep open: current source explicitly requires Edit Profile and Save, confirming the interaction inconsistency. This team-authored feedback calls for a UX change, not a judgment close.

## Change summary

Make editing existing sandbox profiles consistent with other customization surfaces, without a separate read-only mode or explicit Save step.

## Best solution

Allow direct editing of existing sandbox profiles with validated automatic persistence. Establish when those edits propagate to connected hosts, while preserving validation and managed restrictions.

Manually open a saved profile, edit without Edit/Save, switch profiles, and reopen to verify persistence and keyboard focus.
- **Behavior:**

  > Existing sandbox profiles should be directly editable without entering a separate edit mode or pressing Save. Valid changes should persist automatically at the agreed commit boundary. Invalid names or JSON must remain visibly invalid without being persisted or forwarded, and changes must retain the existing assigned-host scope.
- **Trace:**

  > SandboxProfilesInput.select() deliberately opens saved profiles with editing=false, and SandboxProfilesEditor._render() uses that state to disable the controls. Control changes currently update only the draft; the explicit Save action invokes save(), which writes local storage, updates assigned connected hosts, and returns to read-only mode. The sandboxProfiles.test.ts suite asserts this existing contract. UserDataProfilesEditorModel provides a validated scheduled-save comparison. The uncertainty is the user-visible timing of automatic persistence and remote propagation; runtime enforcement, profile assignment, and managed restrictions are outside this UI change.
- **Open decisions:**
  - Should text-field edits persist and update assigned connected hosts after a typing pause, or only when the user commits or leaves the field?

## Evidence

- **Current interaction:** src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/sandboxProfilesInput.ts: select() sets editing=false for saved profiles; edit() explicitly enables editing. SandboxProfilesEditor._render() disables controls when editing=false and provides a Save button that calls input.save().
- **Intentional behavior, not a malfunction:** src/vs/workbench/contrib/terminalContrib/chatAgentTools/test/browser/sandboxProfiles.test.ts explicitly tests 'opens new profiles with a unique default name and saved profiles read-only'. The report requests refinement of that designed interaction.
- **Reporter's additional requirement:** https://github.com/microsoft/vscode/issues/349813#issuecomment-7103388177 explicitly identifies the Save action as inconsistent too; removing only the read-only mode would not address the complete feedback.
- **Existing capability comparison:** The sandbox editor's Edit Profile action enables manual editing but does not provide automatic persistence. By contrast, src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditorModel.ts uses a 500 ms saveScheduler and validates before updating an existing profile.
- **Persistence has remote effects:** SandboxProfilesInput.save() writes the local library and calls assignHostSandboxProfile() for connected hosts using the profile. Automatic saving therefore changes when remote host defaults update, not merely when local UI state is stored.
- **Related items and implementation ownership:** https://github.com/microsoft/vscode/issues/349740 explicitly prescribes the current read-only/Edit/Save workflow. https://github.com/microsoft/vscode/issues/349201 proposes per-host profiles but does not specifically own this interaction feedback; neither establishes a duplicate.
