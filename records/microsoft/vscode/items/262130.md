# Issue #262130 — Cannot `Tab` out of a focused chat request

[https://github.com/microsoft/vscode/issues/262130](https://github.com/microsoft/vscode/issues/262130)

## Summary

The shared chat transcript still has two adjacent focus stops—the tree root and the request content—so pressing Tab from the visually focused request can appear to do nothing. A later fix removes the redundant root stop only in the Agents Window and explicitly leaves other chat hosts unchanged, so this accepted accessibility bug remains open.

## Change summary

Make Tab and Shift+Tab move predictably out of a focused chat request instead of landing on an indistinguishable nested focus target.

## Best solution

Define one consistent sequential focus model for request rows across chat hosts: arrow keys should continue navigating transcript rows, while Tab and Shift+Tab should advance to the next or previous logical control without an invisible duplicate stop.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chat.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatListWidget.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/chatListWidget.test.ts`
- **Validation:** Extend the ChatListWidget browser test coverage to verify the chosen Tab and Shift+Tab traversal while preserving arrow-key row navigation and programmatic transcript focus; also manually verify the sequence in the Chat panel with Screen Reader Optimized mode enabled.
- **Behavior:**

  > When focus is visibly on a chat request, pressing Tab once moves to the next logical focus target and Shift+Tab moves to the previous one; neither key should land on an indistinguishable second focus representation of the same request. Up and Down continue navigating transcript rows. Programmatic transcript focus, request actions, and screen-reader access remain available across the Chat panel and other affected chat hosts.
- **Trace:**

  > ChatListWidget in src/vs/workbench/contrib/chat/browser/widget/chatListWidget.ts creates a focusable Monaco tree root, while ChatListItemRenderer in src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts also makes request markdown focusable. The maintainer confirmed this row-versus-bubble focus mismatch at https://github.com/microsoft/vscode/issues/262130#issuecomment-3198082078. Commit ec5408d8eb06853e264fcf35a877ddb1ac353c60 and https://github.com/microsoft/vscode/pull/335459 demonstrate that excluding the tree root preserves request and programmatic focus, but they enable that behavior only for src/vs/sessions/contrib/chat/browser/chatView.ts and explicitly leave other hosts unchanged. Preserve arrow-key transcript navigation and do not remove request controls from the tab order; the uncertainty begins at whether the shared root should leave sequential navigation globally or remain available through explicit focus handling.
- **Open decisions:**
  - Should the transcript tree root be removed from sequential keyboard navigation for every chat host, or should non-Agents chat hosts retain it and explicitly route Tab and Shift+Tab around the duplicate request focus stop?

## Evidence

- **confirmed focus model:** The maintainer explanation at https://github.com/microsoft/vscode/issues/262130#issuecomment-3198082078 confirms that the apparent request focus is actually on the Monaco list row and that its tab-index behavior needs correction.
- **current source:** src/vs/workbench/contrib/chat/browser/widget/chatListWidget.ts leaves the transcript tree root at its default sequential tab index unless a host supplies `options.tabIndex`; src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts separately assigns `tabIndex = 0` to request markdown content. These adjacent stops can represent the same request visually.
- **partial later fix:** https://github.com/microsoft/vscode/commit/ec5408d8eb06853e264fcf35a877ddb1ac353c60 adds `transcriptTabIndex: -1` only to src/vs/sessions/contrib/chat/browser/chatView.ts. Its merged PR, https://github.com/microsoft/vscode/pull/335459, says other chat hosts deliberately retain their previous focus behavior and fixes a different issue.
- **existing regression coverage:** src/vs/workbench/contrib/chat/test/browser/widget/chatListWidget.test.ts verifies that request content remains tabbable when the transcript root is excluded, but current production configuration applies that model only to the Agents Window.
