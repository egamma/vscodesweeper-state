# Issue #341484 — Agent Host (Copilot CLI): OAuth MCP server token never re-acquired after mid-session 401 — tools silently unavailable until new session

[https://github.com/microsoft/vscode/issues/341484](https://github.com/microsoft/vscode/issues/341484)

## Summary

Thanks for the detailed report. It is complete (steps, logs from both the host and the CLI runtime) but I could not confirm it without running it. Current source shows OAuth tokens are delivered only through the needs-auth challenge path, and the stale-catalog retry comes from the bundled Copilot CLI runtime, so the fix may belong partly in the SDK. Keep open; the steps suffice to retest on the latest build.

## Change summary

An Agent Host (Copilot CLI) session never re-requests an OAuth MCP token from VS Code's auth provider after a mid-session 401, so the server's tools stay unavailable.

## Best solution

When the runtime reports a 401 or OAuth challenge mid-session, the agent host should re-request a token from the host auth provider (silent first). If that fails, it should surface needs-auth instead of retrying with the stale token. This likely needs a coordinated change with the Copilot CLI SDK.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/platform/agentHost/node/copilot/copilotSessionWrapper.ts`
- **Validation:** A copilotAgentSession test simulating a mid-session 401 or OAuth challenge on a connected MCP server, asserting the host re-requests a token or transitions to needs-auth.
- **Behavior:**

  > After an OAuth MCP server's token expires mid-session, the agent host re-acquires a token from VS Code's auth provider (silently when possible) and the server's tools recover. If silent refresh fails, the server shows needs-auth rather than staying stale. Acceptance: a mid-session 401 test passes, and the existing initial needs-auth flow is unchanged.
- **Trace:**

  > Token delivery currently happens through the needs-auth / OAuth-requested path in copilotAgentSession.ts (the _handleMcpOAuthCompleted and status-translation code). The runtime (tool_catalog) retries tools/list with the stale token and does not escalate to needs-auth. Where the uncertainty starts: whether the runtime emits a signal the host can act on (and whether rpc.mcp.oauth.authenticationStateChanged can be used to re-trigger auth), or whether an SDK change is required first. Do not change the initial connect flow.
- **Open decisions:**
  - Is the fix host-side, by reacting to a runtime signal, or does it require a Copilot SDK/runtime change first?
  - If silent refresh fails, does the user see needs-auth immediately, or only on the next tool call?
