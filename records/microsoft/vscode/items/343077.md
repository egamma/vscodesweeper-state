# Issue #343077 — Large Codex chat restore stalls in JSON-RPC buffering and accessibility Markdown block counting

[https://github.com/microsoft/vscode/issues/343077](https://github.com/microsoft/vscode/issues/343077)

## Summary

Keep open: current source retains both reported expensive paths, and an independent Windows confirmation reproduces the buffering stall with the bundled runtime. The follow-up also establishes that fragment buffering alone is insufficient for oversized history responses.

## Change summary

Keep large Codex history restoration responsive without repeated partial-message scanning, unnecessary Markdown inline parsing, or indefinitely loading oversized responses.

## Best solution

Make transport processing and accessibility block counting scale with their inputs while preserving existing semantics. Address oversized history responses across pagination and resume as well; treat the separately observed queued-message disappearance as an unresolved recovery concern, not something these optimizations demonstrably fix.

## Evidence

- **Current transport defect:** At checkout 9019233f1961ea6208a69eceebc2776bbea65acc, src/vs/platform/agentHost/node/codex/codexAppServerClient.ts::_listenToStdout appends every chunk to _buf and searches from its beginning. A newline-free fragmented response therefore repeatedly scans the accumulated prefix; concatenation and allocation failures occur outside the JSON.parse catch.
- **Current accessibility hotspot:** src/vs/workbench/contrib/chat/browser/accessibility/chatAccessibilityProvider.ts::_getLabelWithInfo calls marked.lexer(responseText) solely to count top-level table and code tokens. src/vs/base/common/marked/marked.js performs block lexing followed by processing its inlineQueue, confirming unnecessary inline parsing on this counting path.
- **Independent bundled-runtime reproduction:** https://github.com/microsoft/vscode/issues/343077#issuecomment-6509077974 confirms the buffering stall on Windows with VS Code 1.144.0 and bundled Codex 0.163.0: 4,592 ms of a roughly six-second CPU sample was attributed to the stdout callback, with delayed updates across sessions. Its synthetic fragmented-message reproducer removes dependence on the original private transcript and SDK override.
- **Complete follow-up changes the required scope:** The October 30 follow-up at https://github.com/microsoft/vscode/issues/343077 reports RangeError: Invalid string length after locally introducing fragments. Smaller full-history pages plus metadata-only resume allowed the affected panes to load; the commenter explicitly warns that one turn can still exceed the string limit and separately reports unisolated queued-message disappearance.
- **Oversized responses remain possible:** src/vs/platform/agentHost/node/codex/codexAgent.ts uses CODEX_THREAD_TURNS_PAGE_SIZE = 100 with itemsView: 'full'; codexSavedThreadReader.ts independently requests 100 full turns. codexLaunchConfig.ts::buildCodexResumeParams does not set excludeTurns, although protocol/generated/v2/ThreadResumeParams.ts documents that option for metadata-only resume followed by paginated history.
