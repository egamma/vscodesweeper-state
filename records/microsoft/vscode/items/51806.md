# Issue #51806 — Add DecorationRangeBehavior.Word

[https://github.com/microsoft/vscode/issues/51806](https://github.com/microsoft/vscode/issues/51806)

## Summary

A real API gap remains on current main: decorations support only fixed edge-stickiness modes, not word-sensitive growth. The issue was deliberately assigned to the editor text-buffer area and placed On Deck, so it should remain open for API semantics and implementation planning despite limited community reactions.

## Change summary

Add a decoration range behavior that grows when edits extend the decorated word but stops at non-word characters.

## Best solution

Define stable word-boundary semantics for decorations, then expose a corresponding DecorationRangeBehavior through the extension API and editor text model while preserving all four existing stickiness modes.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTypes.ts`, `src/vs/workbench/api/common/extHostTypeConverters.ts`, `src/vs/editor/common/model.ts`, `src/vs/editor/common/standalone/standaloneEnums.ts`, `src/vs/editor/common/model/intervalTree.ts`, `src/vs/editor/test/common/model/modelDecorations.test.ts`
- **Validation:** Extend the model decoration tests to verify that inserting a word character at either applicable edge expands a word-sensitive decoration, inserting whitespace or punctuation does not, and all four existing stickiness modes retain their current results.
- **Behavior:**

  > Extensions need a decoration range behavior that follows the decorated word as users type at its edges. Inserting a word character that extends the word should expand the decoration, while inserting a separator such as a space should not. Existing OpenOpen, ClosedClosed, OpenClosed, and ClosedOpen behavior must remain unchanged. Acceptance includes model tests covering both edges, word characters, separators, and the existing modes.
- **Trace:**

  > DecorationRangeBehavior is declared in src/vscode-dts/vscode.d.ts and mirrored in src/vs/workbench/api/common/extHostTypes.ts, with conversion in extHostTypeConverters.ts to TrackedRangeStickiness. The resulting stickiness reaches editor decorations through abstractCodeEditorService.ts and is processed by nodeAcceptEdit in src/vs/editor/common/model/intervalTree.ts. That function currently receives offsets and inserted text length but not the inserted characters, and the internal enum has only four fixed edge modes. Existing insertion expectations are centralized in src/vs/editor/test/common/model/modelDecorations.test.ts. Preserve the numeric values and behavior of the existing public enum members; the unresolved boundary is which established word definition should control this new public behavior.
- **Open decisions:**
  - Should “word character” follow the document language's word definition, the editor's configured word separators, or a language-independent definition?
  - Should word-sensitive growth apply symmetrically at both edges, or should the public API also support independently open and closed word-aware edges?

## Evidence

- **current public API:** src/vscode-dts/vscode.d.ts defines only OpenOpen, ClosedClosed, OpenClosed, and ClosedOpen in DecorationRangeBehavior; no word-sensitive behavior exists.
- **current model behavior:** src/vs/editor/common/model/intervalTree.ts implements nodeAcceptEdit using only four TrackedRangeStickiness modes and receives the inserted text length, not its characters, so it cannot currently distinguish a word character from a space.
- **API path:** The behavior flows through src/vs/workbench/api/common/extHostTypes.ts, src/vs/workbench/api/common/extHostTypeConverters.ts, src/vs/editor/browser/services/abstractCodeEditorService.ts, and the editor model stickiness enum.
- **existing tests:** src/vs/editor/test/common/model/modelDecorations.test.ts exercises insertion behavior for all four existing stickiness modes and provides the appropriate validation surface for word-sensitive edge edits.
- **maintainer routing:** The issue timeline shows assignment by an editor maintainer, placement in Backlog and later On Deck, and addition of the existing api and editor-textbuffer labels.
- **originating discussion:** https://github.com/microsoft/vscode/issues/50779 identifies GrowWhenTypingWord as the desired behavior; that broader issue was later closed for lack of interest, but this separately routed API request remains open.
