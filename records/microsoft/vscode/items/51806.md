# Issue #51806 — Add DecorationRangeBehavior.Word

[https://github.com/microsoft/vscode/issues/51806](https://github.com/microsoft/vscode/issues/51806)

## Summary

The requested word-sensitive decoration behavior remains absent from current main. Keep the API request open under discussion because defining a word and carrying inserted text into the decoration-tracking layer require explicit API and editor-model design decisions.

## Change summary

Add a decoration range behavior that grows at its edges for inserted word characters but not for separators such as spaces.

## Best solution

Define stable, language-aware semantics for word-sensitive decoration growth, then expose them consistently through the extension API and editor text-buffer tracking. The design must specify whose word definition applies and how replacements, multi-character edits, and language-configuration changes behave.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTypes.ts`, `src/vs/workbench/api/common/extHostTypeConverters.ts`, `src/vs/editor/common/model.ts`, `src/vs/editor/common/model/intervalTree.ts`, `src/vs/editor/common/model/textModel.ts`, `src/vs/editor/test/common/model/modelDecorations.test.ts`, `src/vs/editor/test/common/model/intervalTree.test.ts`
- **Validation:** Extend the editor model decoration tests with edge insertions showing that configured word characters grow the range while whitespace and punctuation do not, including start/end insertions and replacement edits; run the targeted model decoration and interval-tree unit suites.
- **Behavior:**

  > Extensions can select a decoration range behavior that follows the decorated word as users extend it at either edge. Inserting a character considered part of that word expands the decoration, while inserting whitespace or another separator does not. Existing four DecorationRangeBehavior modes retain their current semantics. Acceptance must cover both range edges, multi-character input, and replacement edits.
- **Trace:**

  > The public enum in src/vscode-dts/vscode.d.ts is mirrored by src/vs/workbench/api/common/extHostTypes.ts and converted to TrackedRangeStickiness in src/vs/workbench/api/common/extHostTypeConverters.ts. The internal enum is in src/vs/editor/common/model.ts, while edit tracking flows from TextModel into IntervalTree.acceptReplace and nodeAcceptEdit in src/vs/editor/common/model/intervalTree.ts. That path currently receives only offsets and inserted text length, so it cannot distinguish a word character from a separator. Existing behavior is exercised by src/vs/editor/test/common/model/modelDecorations.test.ts and src/vs/editor/test/common/model/intervalTree.test.ts. The boundary is decoration range tracking: existing stickiness values and unrelated cursor word-navigation behavior must remain unchanged. The originating discussion is https://github.com/microsoft/vscode/issues/50779.
- **Open decisions:**
  - Should "word" use the active language's word definition, the editor's word-separator configuration, or fixed identifier-character semantics?
  - Should the behavior apply only to typed insertions, or also to paste, snippets, replacements, and programmatic edits?
  - Can word-sensitive decisions be made before IntervalTree.acceptReplace, or should the decoration-tracking interface be extended to receive edit content and word context?
  - How should the behavior respond when a decoration spans multiple words or crosses a line boundary?

## Evidence

- **current API gap:** Current main still defines only OpenOpen, ClosedClosed, OpenClosed, and ClosedOpen in src/vscode-dts/vscode.d.ts and src/vs/workbench/api/common/extHostTypes.ts; no word-sensitive behavior exists.
- **conversion boundary:** src/vs/workbench/api/common/extHostTypeConverters.ts maps the four public DecorationRangeBehavior values directly to the four TrackedRangeStickiness values.
- **model constraint:** IntervalTree.acceptReplace and nodeAcceptEdit in src/vs/editor/common/model/intervalTree.ts receive edit offsets and inserted text length, but not the inserted text or a language-specific word definition, so the requested semantics cannot be added as another numeric stickiness case without a broader design.
- **existing coverage:** src/vs/editor/test/common/model/modelDecorations.test.ts tests all four current edge-stickiness modes, providing a likely validation surface but no coverage for word-sensitive growth.
- **triage history:** The issue was deliberately moved from Backlog to On Deck and labeled editor-textbuffer in 2020. Its originating discussion at https://github.com/microsoft/vscode/issues/50779 identified GrowWhenTypingWord as the missing behavior, but that broader issue was later closed for lack of user interest rather than because this API was implemented.
- **canonical search:** A repository issue search for DecorationRangeBehavior found no other open issue that owns this specific word-sensitive range behavior.
