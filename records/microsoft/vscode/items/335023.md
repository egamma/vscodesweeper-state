# Issue #335023 — Agent feedback sent to parent session instead of fork

[https://github.com/microsoft/vscode/issues/335023](https://github.com/microsoft/vscode/issues/335023)

## Summary

Traced the exact code path on main: feedback file-to-session mapping and the active feedback scope are keyed to the session's base resource, never to the currently active chat, so feedback attribution silently points at the parent chat whenever the active chat is a fork (peer chat) instead of the main chat.

## Change summary

When a user adds inline feedback in a forked chat and submits it, the `/act-on-feedback` request is sent to the parent session's chat instead of the forked chat.

## Best solution

In src/vs/sessions/contrib/agentFeedback/browser/agentFeedbackService.ts, make the feedback scope follow the active *chat* (activeSession.activeChat.get().resource) rather than the session's base resource — at minimum in `_trackVisibleEditorResources` (line 523, `this._fileToSession.set(candidate, activeSession.resource)`) and in the `activeFeedbackSessionResource` derived observable (line 378), plus `_resolveSession`'s active-session fast path (line 538) — so `getFeedbackSessionResource`/`submitFeedback` resolve to the fork's chat widget instead of the parent's.

## Evidence

- **file-to-session mapping ignores active chat:** src/vs/sessions/contrib/agentFeedback/browser/agentFeedbackService.ts:519-524 `_trackVisibleEditorResources()` maps every visible editor resource to `activeSession.resource` (the session's base/parent resource), never consulting `activeSession.activeChat`.
- **scope observable uses session resource:** agentFeedbackService.ts:373-378 `activeFeedbackSessionResource` is derived purely from `activeSession.resource`, so `getFeedbackSessionResource()` (line 578, `getSessionForFile(resourceUri)?.resource`) returns the parent session's resource even while a fork is the active chat.
- **downstream widget resolution:** agentFeedbackService.ts:969-979 `submitFeedback(sessionResource)` calls `whenChatWidgetForSession(this._chatWidgetService, sessionResource)`, which resolves the chat widget by exact resource match — so if `sessionResource` is the parent's resource, the `/act-on-feedback` request lands on the parent chat's widget, matching the reported symptom exactly.
- **fork model confirms distinct chat resource:** src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:4888-4929 `forkChat` creates a new peer chat with its own resource (fragment) within the same session — session.resource and the fork's chat.resource are different, which is what the mapping above collapses back together.
