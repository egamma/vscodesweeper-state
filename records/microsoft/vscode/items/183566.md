# Issue #183566 — Add tagged template literal support for `localize` calls

[https://github.com/microsoft/vscode/issues/183566](https://github.com/microsoft/vscode/issues/183566)

## Summary

Keep open: core localize still lacks tagged-template support, and the older extension-API proposal explicitly treats this issue as separate prerequisite work. The remaining design question is how keyless templates participate in core localization metadata.

## Change summary

Allow core strings to use localize as a template tag, with interpolated expressions becoming localization replacements.

## Best solution

Define tagged-template message identity and extraction semantics for core localization, then support the syntax consistently in development and packaged builds while preserving existing keyed calls and translator comments.

## Plan brief

- **Likely files:** `src/vs/nls.ts`, `build/lib/nls-analysis.ts`, `build/lib/nls.ts`, `build/next/nls-plugin.ts`, `build/next/test/nls-sourcemap.test.ts`
- **Validation:** Add executable extraction and runtime checks for localize`Hello ${name}!`: extraction produces the agreed stable key and placeholder message, packaged execution substitutes a translated message correctly, and development execution formats the English message. Cover zero and multiple substitutions, repeated messages, existing keyed/commented calls, and source-map preservation in the NLS build tests.
- **Behavior:**

  > Core developers should be able to use localize as a template tag without manually numbering interpolation placeholders. Template text must be extractable for translation, and interpolated values must remain runtime replacements rather than becoming part of translation identity. Development and packaged builds should produce equivalent formatted results for their selected language. Existing keyed calls, including calls with translator comments, must remain supported.
- **Trace:**

  > src/vs/nls.ts currently requires a key or ILocalizeInfo plus a separate message; its localize implementation formats that message or looks it up by a build-generated numeric index. build/lib/nls-analysis.ts recognizes ordinary call expressions only and extracts separate key/message argument spans. Both build/lib/nls.ts and build/next/nls-plugin.ts depend on that representation for extraction and rewriting; the latter also emits module-scoped key metadata. This establishes the missing capability without executing code, but does not settle how a keyless template should be identified in translation catalogs. Preserve existing keyed-call identities, translator comments, substitution behavior and source-map correctness; extension API changes remain separate work under https://github.com/microsoft/vscode/issues/181555.
- **Open decisions:**
  - What translation-key identity should keyless tagged templates expose, including how identical templates within a module share identity and how editing template text affects existing translations?

## Evidence

- **Existing capability check:** src/vs/nls.ts exposes localize overloads accepting an ILocalizeInfo or string key followed by a message and replacement arguments. Neither overload accepts TemplateStringsArray; the implementation formats the separate message argument. Existing placeholder-based calls do not deliver the requested tagged-template syntax.
- **Extraction boundary:** build/lib/nls-analysis.ts collects SyntaxKind.CallExpression nodes and extracts arguments[0] as the key and arguments[1] as the message. TaggedTemplateExpression nodes are not recognized. Both build/lib/nls.ts and build/next/nls-plugin.ts consume this analyzer, so a runtime overload alone would not provide localized packaged output.
- **Message identity contract:** build/next/nls-plugin.ts stores module IDs, explicit keys and messages, sorts entries by module and key, and emits nls.keys.json and nls.metadata.json. The proposed keyless syntax leaves its translation-key identity unspecified.
- **Verified related proposal, not a duplicate:** https://github.com/microsoft/vscode/issues/181555 is open and predates this issue, but requests vscode.l10n.t support for extension authors rather than core localize support. https://github.com/microsoft/vscode/issues/181555#issuecomment-1564686519 explicitly says the extension proposal was backlogged to try the capability in core first and points to this core issue.
