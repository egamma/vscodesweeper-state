- **Validation:** Add an integration-level regression check that starts with an extension manifest lacking a test setting, updates it to a manifest contributing that setting, restarts extension hosts without reloading the window, and asserts that the configuration registry and an open Settings editor can immediately find the new setting.
- **Behavior:**

  > After an installed extension is updated and the user chooses Restart Extensions, newly added configuration properties from the updated manifest must be available immediately in the current window. Opening the setting directly and searching for its full identifier must find it without a window reload. Existing settings removed or changed by the update must likewise reflect the new manifest.
- **Trace:**

  > The reported failure followed a Copilot Chat update that introduced github.copilot.chat.agentDebugLog.enabled; restarting extensions left the Settings editor on the old contribution set until the window reloaded. AbstractExtensionService._deltaExtensions in src/vs/workbench/services/extensions/common/abstractExtensionService.ts models updates as removal plus addition and invokes extension-point handlers. configurationExtensionPoint.ts forwards those deltas to IConfigurationRegistry, while Settings2EditorModel and SettingsEditor2 listen for schema/group changes. All of that wiring existed at the reported commit, so the uncertainty begins at runtime ordering and whether the updated manifest or a stale extension description reaches the delta. The original setting was later removed by https://github.com/microsoft/vscode/commit/39767fdcf6220e2913489c3ede13dd7f77535237; reproduce with a controlled test setting rather than restoring that deprecated surface. Do not change the requirement that settings whose activation semantics demand a reload may still require one after their value changes—the defect concerns discovering the contributed setting itself.
