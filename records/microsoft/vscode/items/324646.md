# Issue #324646 — Skills: nested skill directory discovery (organizational subfolders + nested project subdirectories)

[https://github.com/microsoft/vscode/issues/324646](https://github.com/microsoft/vscode/issues/324646)

## Summary

Keep open: current standalone skill discovery still lacks recursive organizational folders and automatic directory-scoped monorepo skills. Explicit locations are only a workaround, and neither related closed issue owns the full remaining request.

## Change summary

Discover skills beneath organizational subfolders and nested project roots, with directory scoping and narrower-scope name precedence.

## Best solution

Support grouped skills within configured roots and project-local skills whose availability and collision precedence follow their directory scope. Settle automatic versus opt-in project discovery and the meaning of file context before implementation, with cached discovery and watcher-driven invalidation.

- **Behavior:**

  > Skills under organizational folders within a configured skills root should be discoverable using the name of the folder directly containing SKILL.md. Nested project skill roots should make their skills available only for work within that project, while repository-root skills remain available throughout the repository. When eligible scopes contain the same skill name, the narrower scope should win. Acceptance checks should cover the two layouts in the report, unrelated sibling projects, name collisions, and skill additions/removals without repeated full-tree scans.
- **Trace:**

  > PromptFilesLocator.findAgentSkillsInFolder in src/vs/workbench/contrib/chat/common/promptSyntax/utils/promptFilesLocator.ts only checks immediate child directories; toAbsoluteLocations resolves explicit roots and rejects skill globs, while getWorkspaceFolderRoots optionally walks upward rather than finding descendant roots. PromptsService.computeSkillDiscoveryInfo in src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts already derives canonical identity from the containing folder but deduplicates the inventory before project-context selection. The model-visible filter in src/vs/workbench/contrib/chat/common/promptSyntax/computeAutomaticInstructions.ts has no directory-scope eligibility check. Existing locator and prompts-service tests provide a validation foundation, but this review has not enumerated every slash-command and harness consumer that would need consistent scoping. Preserve existing explicit-location behavior, invocation flags, source precedence outside the new nested-scope case, and the exclusion of AHP workspace roots from filesystem scanning. https://github.com/microsoft/vscode/issues/293277 documents the performance concern; https://github.com/microsoft/vscode/issues/328927 concerns a separate plugin-view surface. The unresolved boundary is the discovery default and which file context determines project-local availability.
- **Open decisions:**

  - What determines directory scope when a chat has no file context, or references files from multiple projects, and should explicit slash invocation follow the same eligibility rules?
