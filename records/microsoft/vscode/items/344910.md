- **Behavior:**

  > After clicking inside an Integrated Browser page, clicking a focusable workbench component outside that page should transfer focus normally. The supplied Windows reproduction uses about:blank and does not require extensions or page scripts. Acceptance includes mouse focus transfer to Explorer, a code editor, and the Chat input in both active and side editor-group arrangements. Keyboard shortcuts and the working separate-window behavior must remain intact.
- **Trace:**

  > WebContentsViewRendererFeature delegates presentation and focus to WebContentsViewHost. BrowserEditor reacts to model.onDidChangeFocus by calling ensureBrowserFocus(), which updates the browser container's DOM active state; WebContentsViewHost.tryFocus() can then schedule model.focus() while that container remains active. In the main process, BrowserView forwards Electron focus/blur events, focuses the native webContents on request, and returns focus to the owning window when hiding a focused view. Inspection identifies this renderer/native boundary but does not establish which event or native transition fails on Windows; diagnosis must begin with the reported click sequence. Preserve keyboard forwarding, legitimate browser focus, and separate-window behavior. https://github.com/microsoft/vscode/issues/288173 describes a different reload-triggered focus problem and is not a duplicate target.
