## Evidence

- **Complete original reproduction:** https://github.com/microsoft/vscode/issues/344910 provides Windows build details and explicit about:blank steps, with extensions disabled and GPU acceleration disabled; keyboard focus switching and a separate browser window work.
- **Confirmed related reproduction:** In the November 19 comment on https://github.com/microsoft/vscode/issues/344910, mpcallahan confirms that focusing the browser, clicking outside VS Code, then clicking an extension webview input causes its caret to disappear and typing to miss the input. The contributor explicitly has not confirmed coverage of every original scenario.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/349193 is currently open and references this issue. It proposes distinguishing restored container focus from explicit focus requests; an open fix candidate is not evidence of completion.
- **Current focus bridge:** src/vs/workbench/contrib/browserView/electron-browser/webContentsViewHost.ts registers container focus to call tryFocus(), which schedules model.focus() when the document is focused and the container remains active. src/vs/platform/browserView/electron-main/browserView.ts ultimately calls native webContents.focus(). This identifies the relevant bridge without conclusively reproducing every reported mouse transition.
- **Related issue is not a verified canonical:** https://github.com/microsoft/vscode/issues/288173 describes automatic page refresh stealing focus from an HTML editor on macOS. That differs from mouse-based focus switching on Windows with about:blank, so it does not satisfy the same-observable-symptom duplicate bar for this re-reviewed item.
