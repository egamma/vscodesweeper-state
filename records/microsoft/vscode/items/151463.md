# Issue #151463 — Strange behavior of files.exclude in workspace with deep nested folders

[https://github.com/microsoft/vscode/issues/151463](https://github.com/microsoft/vscode/issues/151463)

## Summary

The deep-nesting variant remains source-reproducible on main: opening a file from a nested workspace root can make its excluded ancestor appear under the outer root. The existing fix for directly nested roots does not cover an intermediate excluded directory.

## Change summary

Keep an excluded ancestor such as `packages` hidden in an outer workspace root when files are opened through workspace roots nested beneath it.

## Best solution

Preserve `files.exclude` for the outer root while allowing `Module-A` and `Module-B` to remain independent workspace roots; revealing an editor through a nested root must not expose excluded ancestors in another root.

- **Behavior:**

  > In a multi-root workspace containing Root plus `packages/module-a` and `packages/module-b`, `files.exclude: { "packages": true }` keeps `packages` hidden under Root. Opening and closing files through either module root must not make `packages` appear under Root, while the module workspace roots and their files remain normally usable. Existing behavior that reveals an excluded file opened solely through its own workspace root must remain intact.
- **Trace:**

  > `FilesFilter.isVisible` in `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts` first marks `packages` excluded, then applies the visible-editor exception using `findClosestRoot(stat.resource)`. `ExplorerService.findClosestRoot` in `src/vs/workbench/contrib/files/browser/explorerService.ts` receives the ancestor `/packages`, for which Root is the closest containing workspace root; it therefore cannot see that the matching editor belongs to the deeper `/packages/module-a` root, and the exception exposes the ancestor. Commit `0dcf9300ddfed92106c54cbb843f9a827c324754` from https://github.com/microsoft/vscode/pull/118777 established the intended direct nested-root behavior but did not cover this intermediate-directory topology. Keep the boundary to visible-editor filtering in the explorer: do not change general `files.exclude` glob semantics, workspace-folder visibility, or auto-reveal for files that have no closer workspace-root representation.

## Evidence

- **current source:** `FilesFilter.isVisible` in `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts` makes an excluded item visible when an open editor is below it and `stat.root === explorerService.findClosestRoot(stat.resource)`. For the excluded `/packages` ancestor, `findClosestRoot(/packages)` is still the outer Root, so opening `/packages/module-a/test1.txt` satisfies this exception and exposes `packages`.
- **root selection:** `ExplorerService.findClosestRoot` in `src/vs/workbench/contrib/files/browser/explorerService.ts` selects the deepest workspace root containing the resource passed to it. Because the filter passes the excluded ancestor's resource rather than the editor resource, deeper roots below that ancestor do not participate in the decision.
- **prior related fix:** https://github.com/microsoft/vscode/pull/118777 fixed https://github.com/microsoft/vscode/issues/118557 by restricting visible-editor reveal to the closest root. Its commit `0dcf9300ddfed92106c54cbb843f9a827c324754` covers a workspace root that is itself the excluded item, but the present report adds an intermediate excluded `packages` ancestor and exposes the remaining case.
- **canonical search:** The directly related https://github.com/microsoft/vscode/issues/118557 is closed as fixed, while https://github.com/microsoft/vscode/issues/150764 is a closed feature request for per-workspace-folder exclude configuration. Neither is an open canonical owning this still-broken deep-nesting behavior.
