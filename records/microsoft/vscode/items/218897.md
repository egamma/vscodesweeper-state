# Issue #218897 — Option to automatically change the debug toolbar's selected active session when launching a new debug session

[https://github.com/microsoft/vscode/issues/218897](https://github.com/microsoft/vscode/issues/218897)

## Summary

This remains a valid debug UX request: a maintainer agreed with the behavior in principle while identifying an intentional distinction between explicitly user-launched sessions and child or automatically started sessions. No verified canonical duplicate or evidence of existing coverage supports closing it.

## Change summary

Optionally select a newly launched, user-initiated debug session in the debug toolbar so its pause, restart, and stop controls are immediately available.

## Best solution

Define and implement focus behavior that selects a newly started top-level session only when its launch was explicitly initiated by the user, while preserving the current selection for child and automatically started sessions.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugService.ts`
- **Validation:** Add or extend debug service tests to start session A, explicitly launch top-level session B, and assert B becomes focused; also assert that child and automatically started sessions do not replace the selected session.
- **Behavior:**

  > When a user explicitly launches a new top-level debug session while another session is active, VS Code should make the new session available as the selected session in the debug toolbar so its controls act on it immediately. Child sessions and sessions started automatically must not steal the toolbar selection. Existing focus changes caused by stopping, pausing, or switching sessions must remain intact. Acceptance should cover explicit top-level launch, child launch, and automatic launch cases.
- **Trace:**

  > The issue thread identifies the session-focusing logic in src/vs/workbench/contrib/debug/browser/debugService.ts as the relevant path and notes that it is shared by several session lifecycle cases. The maintainer and reporter agree on the important boundary: directly user-started top-level sessions should be distinguished from child and automatic sessions. The supplied related issues cover different observable symptoms and are not canonical duplicates. The trace does not establish whether this should be unconditional behavior or a user option, which affects the public configuration surface and must be decided before implementation.
- **Open decisions:**
  - Should selecting a newly user-launched top-level session be the default behavior, or should it be controlled by a new setting as requested?
  - If configurable, should the setting apply globally to all debug types or be expressible per launch configuration?
