# Issue #145204 — Introduce Sound Theme, similar like Product Icon Themes

[https://github.com/microsoft/vscode/issues/145204](https://github.com/microsoft/vscode/issues/145204)

## Summary

Keep this accepted accessibility request open: current sound controls do not support replacing audio assets or selecting extension-contributed sound themes. This issue already serves as the canonical customization request; the remaining product decision is how packaged themes and individual overrides should coexist.

## Change summary

Let extensions contribute selectable sound themes that replace VS Code's built-in accessibility signal sounds.

## Best solution

Provide an opt-in sound customization contract that lets extensions package alternative sounds while preserving built-in defaults. Decide whether users can override individual sounds independently of the selected theme before defining the contribution and selection interfaces.

## Plan brief

- **Likely files:** `src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts`, `src/vs/workbench/contrib/accessibility/browser/accessibilityConfiguration.ts`, `src/vs/workbench/contrib/accessibilitySignals/browser/commands.ts`, `src/vs/workbench/services/themes/common/themeExtensionPoints.ts`
- **Validation:** In a development build, install a sample sound-theme extension, select it, and trigger debugger-break and task-completion signals to confirm the selected assets play. Return to built-in sounds and verify default playback, existing enablement, volume, and announcements remain unchanged; exercise individual overrides if included in the agreed contract.
- **Behavior:**

  > Users cannot currently replace accessibility signal sounds through supported settings or extension-contributed themes. The requested outcome is an opt-in way to install and select a packaged sound theme, without changing sounds for users who retain the defaults. Acceptance should demonstrate that selected replacement assets play for existing signals and that returning to defaults restores built-in playback. Existing signal enablement, volume controls, and announcements must retain their behavior. Whether individual local-file overrides are included remains a maintainer decision.
- **Trace:**

  > AccessibilitySignalService.playSignal and playSignals in src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts resolve statically registered Sound objects, and playSound constructs URLs under the bundled media directory. The current configuration in src/vs/workbench/contrib/accessibility/browser/accessibilityConfiguration.ts controls enablement, announcements, volume, and delays, not asset selection. ShowSignalSoundHelp in src/vs/workbench/contrib/accessibilitySignals/browser/commands.ts previews bundled sounds and updates enablement settings. src/vs/workbench/services/themes/common/themeExtensionPoints.ts provides the existing theme-contribution precedent but no sound-theme contract. Maintainers consolidated replacement requests from https://github.com/microsoft/vscode/issues/170971 and https://github.com/microsoft/vscode/issues/232853 into this issue. The uncertainty begins at the user-facing contract for packaged themes versus individual overrides; preserve default sound assets and existing signal triggering and announcement semantics.
- **Open decisions:**
  - Should the first supported customization surface provide packaged sound themes only, individual local-file overrides first, or both?
  - If both are supported, should individual overrides take precedence and persist when the selected sound theme changes?
