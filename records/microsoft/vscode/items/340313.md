# Issue #340313 — Copilot Chat: Delete archives first filtered session instead of editing the session filter

[https://github.com/microsoft/vscode/issues/340313](https://github.com/microsoft/vscode/issues/340313)

## Summary

Credible bug: the global Delete keybinding for archiving a session (ARCHIVE_SESSION_COMMAND_ID) appears to fire even while the tree's find/filter input has focus, consuming forward-Delete keystrokes that should just edit the filter text.

## Change summary

Pressing Delete while the sessions list filter input is focused archives the first filtered session instead of deleting a character in the filter field.

## Best solution

Tighten the `when` clause (or the underlying focus-tracking) on the Delete keybinding for ARCHIVE_SESSION_COMMAND_ID in sessionsViewActions.ts so it never fires while the tree's FindInput (filter box) has keyboard focus.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/sessions/browser/views/sessionsViewActions.ts`, `src/vs/sessions/contrib/sessions/browser/views/sessionsView.ts`, `src/vs/base/browser/ui/tree/abstractTree.ts`
- **Validation:** A test or manual check confirming that with the sessions filter/find input focused and containing text, pressing Delete edits the input text (or does nothing when cursor is at end) and never invokes ARCHIVE_SESSION_COMMAND_ID.
- **Behavior:**

  > When the Copilot Chat sessions view's filter/find input has keyboard focus, pressing Delete must only affect the input's text content (deleting the character after the cursor, or doing nothing if the cursor is at the end) and must never archive a session. This should hold regardless of cursor position or which session is currently the first filtered match. Acceptance: with the filter input focused, pressing Delete at the end of the filter text does not change session archive state; pressing Delete mid-text deletes forward as expected.
- **Trace:**

  > The Delete key is globally bound to ARCHIVE_SESSION_COMMAND_ID in src/vs/sessions/contrib/sessions/browser/views/sessionsViewActions.ts (~line 1055), gated by WorkbenchListFocusContextKey, which is defined in src/vs/platform/list/browser/listService.ts:119 as requiring NOT InputFocusedContextKey. InputFocusedContextKey is set globally based on document.activeElement being an editable element (src/vs/platform/contextkey/browser/contextKeyService.ts). The sessions list's find/filter widget (src/vs/base/browser/ui/tree/abstractTree.ts FindWidget, using FindInput) renders a genuine <input>, and its container is mounted in src/vs/sessions/contrib/sessions/browser/views/sessionsView.ts (findWidgetContainer, ~lines 285-307) as a sibling of the list, not inside it — it is currently unclear whether this detached placement, or some other timing interaction between the tree's render/refilter cycle and DOM focus, is causing InputFocusedContextKey (or the list's own RawWorkbenchListFocusContextKey) to be evaluated incorrectly when the command dispatches. Do not change the mac binding (Cmd+Backspace) or the general archive behavior for list-focused Delete presses — only the guard for filter-input focus needs tightening.
- **Open decisions:**
  - Is the correct fix an explicit additional `when` guard (e.g. excluding a 'find widget focused' context key) on the keybinding, or a fix to the underlying focus/context-key tracking so WorkbenchListFocusContextKey already behaves correctly for this detached find-widget container?

## Evidence

- **keybinding:** src/vs/sessions/contrib/sessions/browser/views/sessionsViewActions.ts:1055-1065 binds ARCHIVE_SESSION_COMMAND_ID to plain KeyCode.Delete, gated only by IsSessionsWindowContext, FocusedViewContext.isEqualTo(SessionsViewId), and WorkbenchListFocusContextKey.
- **expected guard:** WorkbenchListFocusContextKey = RawWorkbenchListFocusContextKey AND NOT InputFocusedContextKey (src/vs/platform/list/browser/listService.ts:119), and InputFocusedContextKey is set globally whenever the active element is an <input>/<textarea> (src/vs/platform/contextkey/browser/contextKeyService.ts ~line 389-420). The filter/find widget's FindInput renders a real <input> (src/vs/base/browser/ui/tree/abstractTree.ts FindWidget, ~line 881), so this guard should normally block the Delete keybinding while typing in the filter.
- **symptom consistency:** Reporter says Backspace edits text correctly but Delete does nothing to the text and instead archives — consistent with the cursor sitting at the end of the filter text (native forward-Delete is a no-op there) while the bubbling Delete keydown still matches the global keybinding and gets preventDefault'd/executed, implying the WorkbenchListFocusContextKey guard is not actually false while the filter input in src/vs/sessions/contrib/sessions/browser/views/sessionsView.ts (findWidgetContainer, line ~285-307) has focus.
