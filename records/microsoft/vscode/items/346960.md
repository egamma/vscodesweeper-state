Keep open to investigate the reported accumulation of unwanted empty windows. The attachments provide sufficient steps to retest; current source explains restoring recorded windows, but does not establish why windows the reporter never opened entered that state.

## Change summary

They describe Windows 11, VS Code 1.145.2, relaunching without arguments, 16 saved empty-window entries, corresponding startup window logs, and relief after clearing state and selecting window.restoreWindows=folders. The underlying state files and logs are described rather than supplied.
- **Existing restoration policy:** src/vs/workbench/electron-browser/desktop.contribution.ts:182–194 registers window.restoreWindows with default 'all' and a 'folders' option. In src/vs/platform/windows/electron-main/windowsMainService.ts:1039–1109, doGetPathsFromLastSession restores saved empty-window backup paths except in folders mode; getRestoreWindowsSetting forces 'all' following a restart. This explains replaying existing records, not their unexpected origin.
- **Independent backup recovery:** src/vs/platform/windows/electron-main/windowsMainService.ts:407–415 additionally restores empty windows with backups on initial startup. src/vs/platform/backup/electron-main/backupMainService.ts:230–257 filters backup records through doHasBackups and removes stale directories. Empty backup directories alone therefore do not establish a defect in backup recovery; saved window-state restoration is a separate path.
- **Persistence boundary:** WindowsStateHandler.saveWindowsState in src/vs/platform/windows/electron-main/windowsStateHandler.ts records current application windows for multi-window restoration. Source inspection did not establish a path that turns the reporter's single window into 16 distinct records, so the alleged defect remains unconfirmed rather than source-reproduced.
