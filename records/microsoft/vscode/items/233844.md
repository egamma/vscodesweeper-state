# Issue #233844 — Tab With Problems - Improve Accessibility for Colorblind People

[https://github.com/microsoft/vscode/issues/233844](https://github.com/microsoft/vscode/issues/233844)

## Summary

Keep open: maintainers agreed that tabs should use an icon rather than color alone to distinguish files with errors, and the Backlog milestone indicates the request is accepted but unscheduled.

## Change summary

Add a non-color visual indicator, preferably an icon beside the tab filename, for files containing errors.

## Best solution

Add a compact error indicator to editor tabs without replacing the file-type icon, preserving tab recognizability while making error state perceivable without color. The interaction should remain legible across built-in, high-contrast, and color-vision-deficiency-friendly themes.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/editor/tabsTitleControl.ts`, `src/vs/workbench/browser/parts/editor/media/tabsTitleControl.css`
- **Validation:** Add or update editor-tab rendering tests for an error-bearing editor, then verify the indicator remains distinguishable from dirty state in default dark, default light, and high-contrast themes without relying on color.
- **Behavior:**

  > An editor tab for a file with error diagnostics must expose a visible non-color indicator next to its filename, so users do not need to distinguish diagnostic and dirty-state text colors. Tabs without errors remain unchanged, warning-only files must follow the chosen diagnostic-severity policy, and dirty plus error states must remain independently understandable. Acceptance includes keyboard and screen-reader semantics where applicable and visual checks in light, dark, and high-contrast themes.
- **Trace:**

  > The issue is already routed to the accessibility and workbench-tabs areas, and maintainers explicitly agreed on an icon next to the tab filename. The likely rendering boundary is the editor tabs title control and its tab styling under src/vs/workbench/browser/parts/editor; preserve existing file-type icons, dirty-state behavior, tab sizing, and diagnostics behavior outside tabs. The existing color treatment is insufficient for the reporter because dirty and problem states are not reliably distinguishable by color. The uncertainty begins at the public UX contract: whether the new indicator supplements or replaces existing tab decorations, and which diagnostic severities activate it.
- **Open decisions:**
  - Should the diagnostic indicator appear only for errors, or represent warnings and errors with distinct observable states?
  - Should the indicator supplement the file-type icon or replace it while diagnostics are present?
  - When a tab is both dirty and has diagnostics, which non-color indicators must remain visible simultaneously?
