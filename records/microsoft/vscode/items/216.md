# Issue #216 — [grammars] provide alternative to TextMate grammars

[https://github.com/microsoft/vscode/issues/216](https://github.com/microsoft/vscode/issues/216)

## Summary

This remains a valid, well-supported API request: current main has an internal Tree-sitter tokenization path, but extensions still cannot contribute alternative syntax tokenizers or Tree-sitter grammars. The newer Tree-sitter issues are related rather than valid duplicate canonicals for this re-reviewed 2015 request.

## Change summary

Allow language extensions to provide a syntax tokenizer or grammar format other than TextMate.

## Best solution

Define a stable extension contribution contract for alternative tokenizers, initially leveraging the existing Tree-sitter backend while preserving TextMate fallback, theme compatibility, extension isolation, and parser ABI compatibility.

- **Reason:** A stable tokenizer contribution API strengthens language support and lets extensions provide richer language experiences without moving language-specific parsers into core.

## Plan brief

- **Likely files:** `src/vs/workbench/services/treeSitter/browser/treeSitterLibraryService.ts`, `src/vs/workbench/services/treeSitter/browser/treeSitter.contribution.ts`, `src/vs/editor/common/services/treeSitter/treeSitterLibraryService.ts`, `src/vs/workbench/test/electron-browser/treeSitterTokenizationFeature.test.ts`
- **Validation:** Add an extension integration test using a fixture language whose extension contributes an alternative grammar: opening and editing the fixture must select the contributed tokenizer, produce the expected themed token ranges, and fall back to TextMate when the contribution is unavailable or rejected.
- **Behavior:**

  > A language extension can contribute a supported non-TextMate syntax tokenizer without relying on private `src/vs/languages` APIs. VS Code validates and loads the contribution in desktop and web-compatible environments, applies normal theme token styling, and updates tokens after edits. Existing TextMate grammars continue to work unchanged and provide a deterministic fallback when an alternative contribution cannot load. Competing contributions are resolved by a documented, stable rule.
- **Trace:**

  > The current Tree-sitter implementation is internal: TreeSitterLibraryService in src/vs/workbench/services/treeSitter/browser/treeSitterLibraryService.ts constructs paths for bundled WASM grammars and built-in `.scm` queries, while its editor-layer interface in src/vs/editor/common/services/treeSitter/treeSitterLibraryService.ts exposes no extension provenance or registration lifecycle. The only grammar extension point is `grammarsExtPoint` in src/vs/workbench/services/textMate/common/TMGrammars.ts, consumed by TextMateTokenizationFeature. The closed prototype https://github.com/microsoft/vscode/pull/147648 established that a declarative Tree-sitter contribution is plausible but left parser ABI compatibility unresolved. The broader internal Tree-sitter work is tracked by https://github.com/microsoft/vscode/issues/210475; preserve its current bundled-language behavior and the existing TextMate and semantic-token pipelines while deciding the public contribution boundary.
- **Open decisions:**
  - Should the first public contract be a declarative Tree-sitter grammar contribution containing packaged WASM and query resources, or a general tokenizer-provider API that permits extension-host code to produce syntax tokens?
  - What parser ABI compatibility guarantee will VS Code expose to extensions, including how incompatible or obsolete contributed grammars are detected and reported?
  - When TextMate and alternative grammar contributions both target a language, which one wins, how can users choose, and under which failures must VS Code fall back automatically?

## Evidence

- **current source gap:** src/vs/workbench/services/treeSitter/browser/treeSitterLibraryService.ts loads bundled `@vscode/tree-sitter-wasm` grammars by fixed language ID and gates only css, typescript, ini, and regex through experimental settings; it does not consume extension contributions.
- **existing contribution boundary:** src/vs/workbench/services/textMate/common/TMGrammars.ts registers only the `grammars` extension point for TextMate tokenizers, while the Tree-sitter services under src/vs/workbench/services/treeSitter expose no corresponding extension point or public API.
