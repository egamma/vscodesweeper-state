# Issue #77492 — If pasting over text containing TextEditorDecorations, they are retained

[https://github.com/microsoft/vscode/issues/77492](https://github.com/microsoft/vscode/issues/77492)

## Summary

The extension API gap remains on current main: VS Code supports collapsing internal decorations when their range is replaced, but `TextEditorDecorationType` cannot request that behavior. This maintainer-authored feature request should remain open for an API decision.

## Change summary

Allow extension-provided text editor decorations to stop covering replacement text when their decorated range is overwritten.

## Best solution

Expose an opt-in replacement behavior for `DecorationRenderOptions` and carry it through the extension-host converter to the existing model-level `collapseOnReplaceEdit` support, preserving current decoration behavior by default.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTypeConverters.ts`, `src/vs/workbench/api/test/common/extHostTypeConverters.test.ts`
- **Validation:** Add an extension-host type-converter test proving the selected replacement behavior is forwarded to the model decoration options, then run `scripts/test.sh --grep "DecorationRenderOptions"`.
- **Behavior:**

  > An extension can opt into decorations being collapsed when an edit replaces their complete range, so pasted replacement text is not decorated as though it were the original content. Existing extensions retain their current range-tracking behavior unless they select the new behavior. Partial edits and the four existing edge-growth modes remain unchanged.
- **Trace:**

  > Extension decoration options originate in `DecorationRenderOptions` in src/vscode-dts/vscode.d.ts and are converted by `DecorationRenderOptions.from` in src/vs/workbench/api/common/extHostTypeConverters.ts before registration. The editor model already supports `IModelDecorationOptions.collapseOnReplaceEdit` in src/vs/editor/common/model.ts, with replacement behavior covered by the `issue #41492` test in src/vs/editor/test/common/model/modelDecorations.test.ts. The uncertainty begins at the public API boundary: the current API exposes `DecorationRangeBehavior` only for edits at range edges, while replacement collapse remains internal. Preserve existing defaults and do not change replacement semantics globally.
- **Open decisions:**
  - Should replacement collapse be a separate boolean option or an additional decoration range-behavior mode?
  - Should the behavior apply only when the entire decoration range is replaced, matching the existing model option, or also define truncation for partial overlap?
