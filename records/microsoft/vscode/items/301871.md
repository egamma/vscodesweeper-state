# Issue #301871 — Quick Open % symbol search preview closes picker when resolving a Custom Editor (Webview focus theft)

[https://github.com/microsoft/vscode/issues/301871](https://github.com/microsoft/vscode/issues/301871)

## Summary

Keep open: the report provides sufficient steps to retest premature picker dismissal, and the reporter confirmed persistence in 1.111.0. Current source has custom-editor navigation support and webview focus guards, but neither establishes that this preview-resolution case is fixed.

## Change summary

Keep the Quick Open % search picker focused and open when navigating results previews a file associated with a custom editor.

## Best solution

Preserve the active search session throughout background custom-editor resolution while retaining normal explicit editor focus and picker dismissal. First isolate whether focus originates in core webview initialization or the provider's content; the existing report is sufficient to begin that investigation.

Verify the picker stays visible, its input retains focus and query, and navigation continues. Compare a provider without autofocus against the reported extension; verify Enter still focuses the chosen editor and Escape and deliberate outside clicks retain normal dismissal behavior.
- **Behavior:**

  > Arrow-key navigation through % Quick Text Search results must not terminate the search when a matching file opens as a transient custom-editor preview. The picker must retain its query and keyboard focus while the preview resolves. Explicit result acceptance must still open and focus the selected editor, and deliberate dismissal must continue working. Acceptance requires exercising newly resolved webviews, not only already-open custom editors.
- **Trace:**

  > The % prefix belongs to TextSearchQuickAccessProvider in src/vs/workbench/contrib/search/browser/quickTextSearch/textSearchQuickAccess.ts, despite the issue's symbol-search wording. Its active-item handler queues openTransientEditor with preserveFocus: true. WebviewEditor.setInput() resolves the input and claims its webview; QuickInputController hides the picker on blur. WebviewElement._doFocus() contains both immediate iframe focus and a delayed, guarded focus message, but the inspected source does not prove which operation causes this report. CustomEditorInput.applyOptions() now propagates preserveFocus to supported custom-editor navigation. Start by reproducing with a minimal provider and the reported provider, tracing focus across resolution; preserve explicit editor focus, ordinary blur dismissal, and text-editor previews. The closed breadcrumb report https://github.com/microsoft/vscode/issues/338120 offers a timing-related lead but has a different initiating path.

## Evidence

- **Complete reproduction and version follow-up:** https://github.com/microsoft/vscode/issues/301871 specifies macOS, a CustomTextEditorProvider associated with Markdown, a % query, and arrow-key navigation into a Markdown result. The reporter subsequently confirmed the same dismissal on 1.111.0. Requiring a custom-editor extension does not by itself establish extension fault.
- **Correct search surface:** src/vs/workbench/contrib/search/browser/quickTextSearch/textSearchQuickAccess.ts defines TEXT_SEARCH_QUICK_ACCESS_PREFIX as '%'; this is Quick Text Search, not workspace symbol search. Its provide() active-item handler calls PickerEditorState.openTransientEditor with preserveFocus: true, revealIfOpened: true, and the match selection.
- **Resolution and dismissal paths:** src/vs/workbench/contrib/webviewPanel/browser/webviewEditor.ts setInput() awaits input.resolve() and claims the webview. src/vs/platform/quickinput/browser/quickInputController.ts closes the picker with QuickInputHideReason.Blur when focus leaves and ignoreFocusOut is false. These establish the relevant interaction, but do not conclusively identify what initiates focus transfer in the reported case.
- **Existing focus protection is not proof of coverage:** src/vs/workbench/contrib/webview/browser/webviewElement.ts _doFocus() immediately calls contentWindow.focus(), then schedules a guarded focus message. The delayed guard explicitly addresses picker dismissal, but source inspection alone does not establish whether preview resolution invokes this path or whether provider HTML initiates focus. CustomEditorInput.applyOptions() also forwards preserveFocus to supported navigation providers.
- **Canonical search:** Repository issue searches for custom-editor/Quick Open and webview/picker focus found no verified older canonical with the same observable symptom. https://github.com/microsoft/vscode/issues/341449 and https://github.com/microsoft/vscode/issues/341467 are newer reports about restoration after Escape, not dismissal while previewing a custom editor. They do not meet the re-review duplicate bar.
- **Related webview race:** https://github.com/microsoft/vscode/issues/338120 is closed and describes delayed webview focus dismissing a breadcrumb picker in the Agents window. Its investigated trigger explicitly focuses the editor before opening breadcrumbs, unlike this background-preview trigger; it is a diagnostic lead, not a duplicate target or proof that this issue is fixed.
