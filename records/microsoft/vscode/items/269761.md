# Issue #269761 — Too many buttons in explorer for empty workspace

[https://github.com/microsoft/vscode/issues/269761](https://github.com/microsoft/vscode/issues/269761)

## Summary

The empty Explorer still renders all matching welcome contributions as a vertical stack, so the requested improvement remains relevant. Related discussions address button emphasis or hiding contributions, but neither establishes an older canonical covering this request for a less crowded layout.

## Change summary

Improve the empty Explorer UI when multiple extensions contribute welcome sections and buttons.

## Best solution

Agree on a compact, discoverable presentation for multiple Explorer welcome contributions that preserves access to extension actions and keeps opening a folder prominent. Coordinate with the existing button-hierarchy discussion without treating styling alone as a solution to excessive sections.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/views/viewPane.ts`, `src/vs/workbench/contrib/welcomeViews/common/viewsWelcomeContribution.ts`, `src/vs/workbench/contrib/welcomeViews/common/viewsWelcomeExtensionPoint.ts`
- **Validation:** In an empty window, compare Explorer with zero, one, and several extensions contributing welcome paragraphs and command buttons. Verify the agreed compact presentation, keyboard and screen-reader access to every retained action, command enablement, and unchanged behavior after opening a folder.
- **Behavior:**

  > When no folder is open, multiple extension welcome contributions can produce a long stack of sections and buttons in Explorer. The desired outcome is a calmer presentation with a clear primary action while keeping extension actions discoverable and accessible. Acceptance should cover zero, one, and several contributions, including explanatory text and disabled actions. The precise presentation requires maintainer agreement.
- **Trace:**

  > ViewWelcomeController in src/vs/workbench/browser/parts/views/viewPane.ts filters descriptors by context and renders every visible contribution sequentially; standalone links become buttons. ViewsWelcomeContribution maps extension contributions to view descriptors, and viewsWelcomeExtensionPoint.ts defines their existing text, conditions, grouping, and enablement contract. Secondary button styling changes emphasis but does not consolidate sections. Preserve contributed command behavior and do not silently discard explanatory text or alter other welcome views without an explicit scope decision. Related design discussion is at https://github.com/microsoft/vscode/issues/158530; the newer opt-out request at https://github.com/microsoft/vscode/issues/320342 is related but distinct.
- **Open decisions:**
  - Should additional contributions remain visible in compact sections, collapse behind an expandable area, or move into an action chooser?
  - Should the new presentation apply only to empty Explorer or uniformly to other welcome views?
  - If actions are consolidated, how should extension-provided explanatory text remain discoverable?
