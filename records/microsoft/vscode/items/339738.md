# Issue #339738 — Clicking on pill of peer chat could take to relevant request in peer chat

[https://github.com/microsoft/vscode/issues/339738](https://github.com/microsoft/vscode/issues/339738)

## Summary

Brand-new (same-day), reasonable UX suggestion on the just-built multi-chat/peer-chat pill feature; no traction yet and the author themselves frames it tentatively ("Maybe..."), so this stays open as a feature request rather than anything decisive.

## Change summary

Clicking the chat-reference pill that links a main chat to a peer chat opens the peer chat, but doesn't scroll to or focus the specific request the pill refers to.

## Best solution

Wire the attachment's `endTurn` through to the open-session link's existing `turn` query param (already plumbed in src/vs/platform/agentHost/common/openSessionLink.ts via buildOpenSessionLinkUri/parseOpenSessionLinkTurnId) and have the chat widget reveal/scroll to that turn when resolving the link, rather than just opening the peer chat at its default scroll position.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentWidgets.ts`, `src/vs/platform/agentHost/common/openSessionLink.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/openSessionLinkOpener.contribution.ts`
- **Validation:** A test that builds a chat-reference link from an attachment with an `endTurn`, opens it, and asserts the resolved chat widget reveals/scrolls to that specific turn rather than just the chat's default position.
- **Trace:**

  > Trace so far: ChatReferenceAttachmentWidget._openReferencedChat (chatAttachmentWidgets.ts) builds the open-session link via buildOpenSessionLinkForChatResource, which only forwards session+chat id, not the entry's endTurn. The turn-id round trip already exists (buildOpenSessionLinkUri/parseOpenSessionLinkTurnId in openSessionLink.ts) but no consumer currently uses it to reveal/scroll a request in an already-resolved chat widget — only to format an external link in an error path. Where uncertainty starts: whether a "reveal specific request" API exists anywhere on the chat widget/session handler, and what the desired UX is (scroll-only vs. scroll+highlight, behavior when the peer chat isn't yet open).
- **Open decisions:**
  - Should opening the pill scroll to the request, or also visually highlight/select it?
  - Does this need a new reveal API on the chat widget, or does something equivalent already exist elsewhere that could be reused?

## Evidence

- **pill click handler:** src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentWidgets.ts ChatReferenceAttachmentWidget._openReferencedChat() calls buildOpenSessionLinkForChatResource(chatResource) and opens it — it only carries the session/chat id, not a turn.
- **existing turn-id plumbing, unused here:** src/vs/platform/agentHost/common/openSessionLink.ts already supports a `turnId` param (buildOpenSessionLinkUri, parseOpenSessionLinkTurnId), and the entry being restored (IChatRequestChatReferenceVariableEntry) already carries `endTurn` (src/vs/workbench/contrib/chat/common/attachments/chatVariableEntries.ts), but buildOpenSessionLinkForChatResource() does not pass it through, and the opener (openSessionLinkOpener.contribution.ts) does not use parseOpenSessionLinkTurnId to reveal/scroll to a specific request — it's only read elsewhere (chat.contribution.ts) to rebuild an external link for an error notification.
