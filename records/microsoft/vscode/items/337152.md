# Issue #337152 — Agent Host sandboxing uses a separate setting on Windows

[https://github.com/microsoft/vscode/issues/337152](https://github.com/microsoft/vscode/issues/337152)

## Summary

Team-authored (MEMBER), confirmed on current main: `chat.agent.sandbox.enabledWindows` is still a separate setting from `chat.agent.sandbox.enabled` on Windows. The recently merged PR #337181 fixed a related Linux forwarding bug but explicitly deferred this exact OS-split issue as a follow-up, so it stays open.

## Change summary

On Windows, `chat.agent.sandbox.enabled` doesn't enable Agent Host sandboxing; only the separate `chat.agent.sandbox.enabledWindows` setting does.

## Best solution

Unify the enablement setting across platforms (or make `chat.agent.sandbox.enabled` the single source of truth with `enabledWindows` reserved only for Windows-specific overrides) in src/vs/platform/sandbox/common/settings.ts and src/vs/workbench/contrib/terminalContrib/chatAgentTools/common/sandboxSettingsReader.ts — the design choice (unify vs. document as intentional per-OS split) needs a maintainer decision given backward-compatibility implications.

## Plan brief

- **Likely files:** `src/vs/platform/sandbox/common/settings.ts`, `src/vs/workbench/contrib/terminalContrib/chatAgentTools/common/sandboxSettingsReader.ts`, `src/vs/platform/agentHost/common/sandboxConfigSchema.ts`, `src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts`
- **Validation:** A sandboxSettingsReader test asserting that on a simulated Windows environment, `chat.agent.sandbox.enabled: true` alone (without `enabledWindows`) yields the sandbox forwarded as enabled.
- **Behavior:**

  > Setting `chat.agent.sandbox.enabled` to `on` should enable Agent Host sandboxing on all supported platforms, including Windows, without requiring the separate `chat.agent.sandbox.enabledWindows` setting. Existing users who have `enabledWindows` explicitly set should have their choice respected (back-compat). Acceptance: on Windows, only `chat.agent.sandbox.enabled` set to on results in the permissions picker showing sandboxing enabled.
- **Trace:**

  > AgentSandboxSettingId in src/vs/platform/sandbox/common/settings.ts declares `AgentSandboxEnabled` and `AgentSandboxWindowsEnabled` as separate setting IDs; sandboxSettingsReader.ts normalizes each independently with no OS-aware fallback between them (both keys forwarded verbatim per settingId, see normalizeSandboxSettingValue). Related PR https://github.com/microsoft/vscode/pull/337181 fixed a similar SDK-settings-vs-standard-settings split for Linux (#337113) but explicitly left the OS split (this issue) unresolved. Do not touch the SDK-sandbox deprecation work already merged in that PR; scope is limited to how `enabled` vs `enabledWindows` resolve on Windows.
- **Open decisions:**
  - Should `chat.agent.sandbox.enabled` become the single cross-platform setting (deprecating `enabledWindows`), or should Windows continue to support an OS-specific override layered on top of the common setting?
  - For users who already have `enabledWindows` explicitly configured, does the new behavior preserve their existing override, or does `enabled` now take precedence unconditionally?

## Evidence

- **still split on main:** src/vs/platform/sandbox/common/settings.ts still defines both `AgentSandboxEnabled = 'chat.agent.sandbox.enabled'` and `AgentSandboxWindowsEnabled = 'chat.agent.sandbox.enabledWindows'` as distinct setting IDs.
- **reader treats them as separate:** src/vs/workbench/contrib/terminalContrib/chatAgentTools/common/sandboxSettingsReader.ts normalizes both settingIds independently (line 61) and both are listed in SANDBOX_SETTING_KEYS, confirming no unification/fallback logic exists on Windows.
- **related PR explicitly deferred this:** PR https://github.com/microsoft/vscode/pull/337181 (merged, commit b99f5fa) fixed the Linux forwarding bug (#337113) but its description states: 'This PR removes the SDK-specific settings split, but does not eliminate the OS-specific split... Making chat.agent.sandbox.enabled enable sandboxing on Windows as well remains a follow-up; that issue remains open for follow-up.'
