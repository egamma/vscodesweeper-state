# Issue #337152 — Agent Host sandboxing uses a separate setting on Windows

[https://github.com/microsoft/vscode/issues/337152](https://github.com/microsoft/vscode/issues/337152)

## Summary

Team-authored bug report, confirmed still present on main: `chat.agent.sandbox.enabled` is silently ignored on Windows, where only the separate `chat.agent.sandbox.enabledWindows` setting controls sandboxing. No fix commit references this issue yet, so this stays open per the team-authored keep-open rule.

## Change summary

On Windows, `chat.agent.sandbox.enabled` does not enable Agent Host sandboxing — only the separate `chat.agent.sandbox.enabledWindows` setting does, contrary to the expectation that the primary setting should work on all platforms.

## Best solution

Decide how the two settings should relate (e.g. have `enabledWindows` fall back to `enabled` when unset, or explicitly document/deprecate the split) in src/vs/platform/sandbox/common/terminalSandboxEngine.ts (`_isSandboxConfiguredEnabled`/`_getSandboxConfiguredWindowsEnabledValue`), then update the setting docs and permission-picker setting-id resolution accordingly.

## Plan brief

- **Likely files:** `src/vs/platform/sandbox/common/terminalSandboxEngine.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/permissionPickerActionItem.ts`, `src/vs/workbench/contrib/terminalContrib/chatAgentTools/common/terminalChatAgentToolsConfiguration.ts`
- **Validation:** A terminalSandboxEngine test asserting that with `chat.agent.sandbox.enabled` = on and `chat.agent.sandbox.enabledWindows` unset, sandboxing resolves to enabled on a simulated Windows OS.
- **Behavior:**

  > Setting `chat.agent.sandbox.enabled` to on should enable Agent Host sandboxing on Windows just as it does on macOS/Linux, without requiring the user to also set `chat.agent.sandbox.enabledWindows`. Setting only `enabledWindows` should continue to work as a Windows-specific override. Acceptance: a new engine test confirms sandboxing is considered enabled on Windows when only the top-level setting is set.
- **Trace:**

  > `_isSandboxConfiguredEnabled()` in src/vs/platform/sandbox/common/terminalSandboxEngine.ts unconditionally uses `_getSandboxConfiguredWindowsEnabledValue()` (reads only `AgentSandboxWindowsEnabled`, default Off) when `this._os === OperatingSystem.Windows`, ignoring `AgentSandboxEnabled` entirely on that platform; the same pattern is mirrored in permissionPickerActionItem.ts's `getLocalSandboxEnabledSettingId()`. Do not change the non-Windows path or other sandbox settings (fileSystem, allowNetwork, etc.) — the fix is scoped to how the Windows-enabled value is resolved relative to the top-level enabled setting.
- **Open decisions:**
  - Should `enabledWindows` fall back to the value of `enabled` when the user hasn't explicitly set it, or should the two remain fully independent settings?
  - Given `enabledWindows` is tagged 'experimental' while `enabled` is 'preview', is unifying them premature, or should the tags/maturity gating be reconciled first?

## Evidence

- **reproduced on main:** src/vs/platform/sandbox/common/terminalSandboxEngine.ts `_isSandboxConfiguredEnabled()` branches on `this._os === OperatingSystem.Windows` and, when true, only reads `AgentSandboxWindowsEnabled` (default Off) via `_getSandboxConfiguredWindowsEnabledValue()` — it never consults `AgentSandboxEnabled` on Windows.
- **same split elsewhere:** src/vs/workbench/contrib/chat/browser/widget/input/permissionPickerActionItem.ts `getLocalSandboxEnabledSettingId()` also picks `AgentSandboxWindowsEnabled` when `isWindows`, confirming the split is consistent (intentional design) rather than a stray bug, but not addressing the reporter's ask that a single setting suffice.
- **setting tags differ:** terminalChatAgentToolsConfiguration.ts tags `chat.agent.sandbox.enabled` as `preview` and `chat.agent.sandbox.enabledWindows` as `experimental`, suggesting the split may be deliberate due to Windows sandboxing maturity — a design question for the team, not settled by the issue text alone.
- **related merged PRs don't cover this:** The linked merged PRs (https://github.com/microsoft/vscode/pull/337181, /337183, /337187) fixed SDK sandbox setting forwarding/deprecation, but current main still shows the unaddressed Windows/enabled split traced above — none of them reference issue #337152.
