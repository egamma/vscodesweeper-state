# Issue #189109 — Polyglot Notebooks get code cells that are not editable

[https://github.com/microsoft/vscode/issues/189109](https://github.com/microsoft/vscode/issues/189109)

## Summary

Keep open: the malformed auto-closing-pair path still reaches an unchecked editor dereference on current main, and a maintainer explicitly requested defensive handling. Polyglot's workaround does not establish a VS Code fix; neither related report qualifies as a duplicate canonical.

## Change summary

Prevent malformed language configuration supplied by an extension from leaving notebook code cells unusable.

## Best solution

Contain invalid auto-closing-pair configuration at the extension API boundary so it cannot break editor initialization. The language-feature owner should settle whether invalid registrations are rejected with a clear diagnostic or supported through normalization, preserving valid configurations.

- **Behavior:**

  > A malformed autoClosingPairs registration must not leave notebook code cells collapsed and unusable. The reported input mixes array-form pairs from language-configuration JSON with object-form pairs before registering the configuration through the extension API. Acceptance must demonstrate containment of this input, continued notebook-cell editability, and unchanged behavior for valid configurations. Whether the malformed registration is rejected or normalized remains an extension-facing contract decision.
- **Trace:**

  > ExtHostLanguageFeatures._serializeAutoClosingPair reads object properties from every entry without checking its runtime shape. MainThreadLanguageFeatures.$setLanguageConfiguration forwards the resulting undefined open/close values; CharacterPairSupport and StandardAutoClosingPairConditional preserve them, and AutoClosingPairs dereferences open.charAt. This matches the exception diagnosed in https://github.com/microsoft/vscode/issues/189109#issuecomment-1663115862. The maintainer requested an assertion or graceful handling, but did not choose between them. https://github.com/dotnet/interactive/issues/3109 records an extension workaround, not removal of the core failure path. Keep notebook layout redesign and unrelated language-configuration behavior outside this work; valid API configurations must remain compatible.
- **Open decisions:**
  - Should array-form auto-closing pairs passed through the extension API be rejected with a clear diagnostic, or normalized and accepted despite the API's object-form contract?
