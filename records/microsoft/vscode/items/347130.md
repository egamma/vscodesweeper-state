# Issue #347130 — Worktree cleanup duplicates worktrees with multiple sessions

[https://github.com/microsoft/vscode/issues/347130](https://github.com/microsoft/vscode/issues/347130)

## Summary

Current source confirms that shared worktrees are represented and counted separately for each session. Keep this team-authored report open; worktree identity and latest activity need to be aggregated across sessions.

## Change summary

Show each distinct worktree once in Worktree Cleanup, with accurate counts and the latest activity across its sessions.

## Best solution

Make cleanup inventory, storage totals, and activity reflect distinct worktrees rather than individual sessions. Settle how a worktree-level cleanup action affects its linked sessions while preserving existing in-use protections.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/sessions/browser/sessionInputBanners/sessionWorktreeCleanupService.ts`, `src/vs/sessions/contrib/sessionInputBanners/browser/sessionWorktreeCleanupEditor.ts`, `src/vs/workbench/contrib/sessions/test/browser/sessionInputBanners/sessionWorktreeCleanupService.test.ts`, `src/vs/sessions/contrib/sessionInputBanners/test/browser/sessionWorktreeCleanupEditor.test.ts`
- **Validation:** Add service and editor regressions with several sessions sharing one worktree and different activity timestamps: assert one row, one counted checkout, nonduplicated storage, and the latest linked activity. Cover protection when a linked session is active, running, or pinned, plus the agreed archive behavior. Run scripts/test.sh --grep 'SessionWorktreeCleanup' after implementation.
- **Behavior:**

  > Worktree Cleanup currently repeats a long-lived checkout once per associated session and reports session counts as worktree counts. Each distinct checkout should appear once, and its last activity should reflect the most recently active associated session. Counts and estimated storage must not multiply when additional sessions reuse that checkout. Cleanup must retain existing protections for worktrees still in use.
- **Trace:**

  > SessionWorktreeCleanupService._measureWorktrees creates one entry per session, while _countWorktrees deduplicates only within that session. getWorktreeCleanupId uses sessionId, so SessionWorktreeCleanupEditor.getDisplayWorktrees preserves duplicates; filtering, sorting, and activity display read the individual session's updatedAt. Managed inventory already deduplicates unlinked paths but leaves linked-session entries unchanged. Cleanup operations and archive requests are also session-keyed, so merely hiding duplicate rows would leave inconsistent scheduling and totals. Existing service and editor test suites provide validation harnesses. The remaining product uncertainty is what cleaning one shared worktree means for all associated sessions; preserve local-only scope, branch eligibility, and in-use protections.
- **Open decisions:**
  - When cleaning a worktree associated with several sessions, should the action mark every associated session as done, or preserve their individual archive states and expose cleanup only when those states permit removal?

- **Existing deduplication does not cover the report:** _refreshManagedWorktrees deduplicates unlinked inventory by provider and normalized worktree URI and excludes paths already linked to sessions. Replacing duplicate rows with worktree-level entries therefore affects observable cleanup and session-archive behavior, not only rendering.
