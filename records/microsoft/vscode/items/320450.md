# Issue #320450 — Background send should pop up an information dialog that allows me to navigate directly to the generated chat

[https://github.com/microsoft/vscode/issues/320450](https://github.com/microsoft/vscode/issues/320450)

## Summary

This team-authored, On Deck request remains necessary: current main resets the composer and adds the background session to the list but provides no actionable confirmation for opening it. No older issue with the same observable request was found, and the protected accepted-work rules require keeping it open.

## Change summary

Show an informational notification after a background send with an action that opens the generated session directly.

## Best solution

After a background send commits, show concise confirmation with an Open action targeting that exact session, while preserving the defining background-send behavior of leaving the new-session composer active.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/chat/browser/newChatWidget.ts`, `src/vs/sessions/contrib/chat/test/browser/newChatWidget.test.ts`
- **Validation:** Add a focused NewChatWidget test that completes a background send, invokes the notification's Open action, and verifies the exact committed session is opened while the replacement composer remains active; also cover two rapidly completed sends according to the chosen notification policy.
- **Behavior:**

  > A successful background send provides visible confirmation with an Open action that navigates to the session created by that specific send. Until Open is selected, the user remains in the replacement new-session composer and can continue composing. Foreground sends and failed or cancelled background sends retain their existing behavior. Multiple rapid background sends must follow an explicitly chosen, predictable notification policy without opening the wrong session.
- **Trace:**

  > NewChatWidget._send in src/vs/sessions/contrib/chat/browser/newChatWidget.ts already correlates each background send through the exact ISendRequestOptions object and listens for ISessionsManagementService.onDidSendRequest. The resulting event carries the committed session, and ISessionsService.openSession in src/vs/sessions/services/sessions/browser/sessionsService.ts is the existing navigation surface. The current listener only clears feedback, restores the selected workspace, and disposes its pending entry; no success notification is emitted. Keep the fire-and-forget composer reset, foreground navigation, failure notification, and per-send correlation unchanged. The originating feature and test-plan context are https://github.com/microsoft/vscode/issues/319598 and https://github.com/microsoft/vscode/issues/319600.
- **Open decisions:**
  - When several background sends commit in quick succession, should each retain its own actionable notification, or should the UI consolidate them into one notification with different navigation behavior?

## Evidence

- **current behavior:** src/vs/sessions/contrib/chat/browser/newChatWidget.ts::_send registers a per-send onDidSendRequest listener only to clear feedback and restore the workspace; its success path does not create an informational notification.
- **navigation capability:** src/vs/sessions/services/sessions/browser/sessionsService.ts exposes ISessionsService.openSession(sessionResource), so current main can navigate directly to the committed session once its identity is available.
- **send lifecycle:** src/vs/sessions/services/sessions/browser/sessionsManagementService.ts::_sendNewChatRequestInBackground fires onDidStartSession and onDidSendRequest with the committed session after the provider send succeeds, while deliberately leaving the visible composer unchanged.
