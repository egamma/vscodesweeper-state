# Issue #340090 — Copilot Chat: background commands running counter only increases after commands finish

[https://github.com/microsoft/vscode/issues/340090](https://github.com/microsoft/vscode/issues/340090)

## Summary

Thanks for the report. A second user confirms the stale count persists across window and machine restarts. The count is derived purely from persisted tool-call state, so background terminals that end without a recorded exit code can stay counted indefinitely. This stays open for a chat owner.

## Change summary

The 'N background commands running' chat indicator keeps counting background terminal tool calls that have finished or been stopped.

## Best solution

Base the count on live terminal or command state, and do not count restored or serialized tool calls whose terminal no longer exists. Terminals that were stopped, killed or disposed without an exit code should also drop out of the count.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatToolPartUtilities.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts`
- **Validation:** A unit test on getPersistentBackgroundActivity / isActiveBackgroundTerminalToolInvocation: a background terminal tool call that was stopped or restored without an exit code is not counted.
- **Behavior:**

  > The background commands indicator counts only background terminal commands that are actually still running. Commands that finished, failed, were cancelled, or were stopped via the terminal tools are not counted. After a window reload or session restore, tool calls whose terminals no longer exist are not counted. A session with no live background commands shows no count.
- **Trace:**

  > The count comes from getPersistentBackgroundActivity in chatListRenderer.ts, which uses isActiveBackgroundTerminalToolInvocation in chatToolPartUtilities.ts. That check treats exitCode === undefined plus isBackground or didContinueInBackground as active. It does not consult the terminal or command lifecycle, and the same check applies to serialized tool calls. Still to be traced: which terminal tool flows (kill terminal, terminal disposal, session restore) leave exitCode unset, and whether backgroundShellCount (passed to getPersistentActivityLabel) is a live source that should replace the derived count. The boundary is that subagent counting and the other persistent-progress labels must not change.
- **Open decisions:**
  - Should stopped or killed background commands, and restored sessions whose terminals are gone, be dropped from the count automatically, or should the indicator expose entries so users can clear stale ones?

## Evidence

- **count derivation:** getPersistentBackgroundActivity (src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts ~L5994) counts each tool call where isActiveBackgroundTerminalToolInvocation is true. That function (chatContentParts/toolInvocationParts/chatToolPartUtilities.ts L66) requires terminalCommandState.exitCode === undefined and isBackground or didContinueInBackground. It never checks whether the terminal still exists.
- **persistence:** The same check runs for toolInvocationSerialized parts, so a tool call that never recorded an exit code (stopped, killed or disposed terminal) is counted again after reload. This matches the comment from gabaedu: 11 background commands still shown after a machine reboot.
- **not fully traced:** I did not trace which terminal tool paths leave exitCode unset. Explicit stop via the kill tool and terminals closed by the user are the likely cases.
- **related issues:** The reporter's related issues https://github.com/microsoft/vscode/issues/339187 and https://github.com/microsoft/vscode/issues/337684 cover different symptoms (end-of-turn behavior and a running attached server), so neither is a verified duplicate.
