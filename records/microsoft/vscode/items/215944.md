# Issue #215944 — Breakpoint classes have no property for triggered breakpoints

[https://github.com/microsoft/vscode/issues/215944](https://github.com/microsoft/vscode/issues/215944)

## Summary

The extension API still omits triggered-breakpoint dependencies, although the debug model supports them internally. Keep this accepted API request open; the existing debugger behavior does not cover the reporter's extension-API integration.

## Change summary

Expose a breakpoint's triggering dependency to extensions through breakpoint objects and debug.onDidChangeBreakpoints events.

## Best solution

Define a public API contract for identifying the prerequisite breakpoint and expose it consistently in breakpoint snapshots and change events. Preserve the existing workbench-managed triggering behavior for DAP-based debugging.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTypes.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadDebugService.ts`, `src/vs/workbench/api/common/extHostDebugService.ts`
- **Validation:** Use an extension that records vscode.debug.breakpoints and debug.onDidChangeBreakpoints. Create two source breakpoints, make one wait for the other, change its prerequisite, and remove the dependency; verify the agreed public representation reflects each state while ordinary breakpoints retain their existing properties. Also confirm a normal DAP session still activates the dependent breakpoint only after its prerequisite is hit.
- **Behavior:**

  > An extension consuming breakpoint objects must be able to distinguish an ordinary source breakpoint from one configured to wait for another breakpoint, and identify that prerequisite. Initial breakpoint snapshots and subsequent change events must agree when a dependency is created, changed, or removed. Existing conditional, hit-count, and logpoint properties must remain unchanged. The finished API must support the reporter's terminal-based debugger integration without requiring it to implement a DAP session.
- **Trace:**

  > The internal Breakpoint model in src/vs/workbench/contrib/debug/common/debugModel.ts already stores triggeredBy, and DebugService.sendBreakpoints in src/vs/workbench/contrib/debug/browser/debugService.ts uses it to defer sending dependent breakpoints. The dependency is absent from MainThreadDebugService.convertToDto, the breakpoint DTO contracts in extHost.protocol.ts, ExtHostDebugService.$acceptBreakpointsDelta, and the public/runtime breakpoint classes. This establishes an API exposure gap rather than missing triggering behavior in the built-in debugger. Preserve existing DAP triggering semantics and unrelated breakpoint properties. The record at https://github.com/microsoft/vscode/issues/215944 establishes the need but does not settle the public representation or whether the first API should permit creating dependencies as well as observing them.
- **Open decisions:**
  - Should the public dependency identify the prerequisite by breakpoint ID, source location, or a breakpoint reference, including its behavior when the prerequisite is removed?
  - Should the initial API only expose dependencies configured in the workbench, or also let extensions create and modify them?

## Evidence

- **Internal capability is not API coverage:** src/vs/workbench/contrib/debug/common/debugModel.ts:1004,1018,1162–1164 stores and updates triggeredBy. src/vs/workbench/contrib/debug/browser/debugService.ts:1291 filters pending triggered breakpoints before sending them to a debug session.
