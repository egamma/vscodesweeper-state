# Issue #215944 — Breakpoint classes have no property for triggered breakpoints

[https://github.com/microsoft/vscode/issues/215944](https://github.com/microsoft/vscode/issues/215944)

## Summary

The extension API gap remains on current main: VS Code internally records a source breakpoint's trigger relationship, but drops it when constructing the public `Breakpoint` objects delivered to extensions. The accepted Backlog request should remain open, with the public API shape decided before implementation.

## Change summary

Expose the trigger relationship of a triggered breakpoint through the VS Code extension API and breakpoint change events.

## Best solution

Add a public, read-only trigger relationship for source breakpoints and preserve it through the main-thread DTO and extension-host conversion paths, so `debug.breakpoints` and `debug.onDidChangeBreakpoints` identify triggered breakpoints consistently. First decide whether the contract exposes an ID, location, or breakpoint object and whether extensions may also create such breakpoints.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTypes.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadDebugService.ts`, `src/vs/workbench/api/common/extHostDebugService.ts`, `extensions/vscode-api-tests/src/singlefolder-tests/debug.test.ts`
- **Validation:** Extend the debug extension API test to create or obtain a triggered source breakpoint and assert that both `debug.breakpoints` and `debug.onDidChangeBreakpoints` expose the selected trigger relationship while ordinary breakpoints expose no relationship.
- **Behavior:**

  > Extensions can distinguish an ordinary source breakpoint from a triggered source breakpoint through the public breakpoint API. For a triggered breakpoint, the API identifies the breakpoint that must be hit first; ordinary breakpoints have no trigger relationship. The same information is available from `debug.breakpoints` and from added or changed breakpoints delivered by `debug.onDidChangeBreakpoints`, including when the trigger relationship is changed or removed.
- **Trace:**

  > The source breakpoint model already stores the relationship as `IBreakpoint.triggeredBy` in `src/vs/workbench/contrib/debug/common/debug.ts`. `MainThreadDebugService.convertToDto` in `src/vs/workbench/api/browser/mainThreadDebugService.ts` omits it, `IBreakpointDto` in `src/vs/workbench/api/common/extHost.protocol.ts` cannot carry it, and `ExtHostDebugService.$acceptBreakpointsDelta` in `src/vs/workbench/api/common/extHostDebugService.ts` constructs and updates public breakpoint objects without it. The public declarations and runtime class are in `src/vscode-dts/vscode.d.ts` and `src/vs/workbench/api/common/extHostTypes.ts`; nearby API coverage exists in `extensions/vscode-api-tests/src/singlefolder-tests/debug.test.ts`. Keep the scope to source-breakpoint extension API visibility and transport; do not alter internal trigger execution, DAP behavior, or unrelated breakpoint types unless the chosen public contract explicitly requires it.
- **Open decisions:**
  - Should the public trigger relationship be represented as the triggering breakpoint's ID, its source location, or a `SourceBreakpoint` reference?
  - Is the new contract read-only for observing UI-created triggered breakpoints, or should `SourceBreakpoint` construction and `debug.addBreakpoints` also support creating them?
  - Should the property live only on `SourceBreakpoint`, matching the current internal capability, or on the base `Breakpoint` API for possible future breakpoint types?

## Evidence

- **internal model:** `src/vs/workbench/contrib/debug/common/debug.ts` declares `IBreakpoint.triggeredBy` as the ID of the breakpoint that triggers a source breakpoint, and current debug behavior uses that relationship.
- **DTO gap:** `src/vs/workbench/api/browser/mainThreadDebugService.ts` `convertToDto` serializes source breakpoint condition, hit condition, log message, URI, and position but omits `triggeredBy`; `IBreakpointDto` in `src/vs/workbench/api/common/extHost.protocol.ts` has no corresponding field.
- **public API gap:** `src/vscode-dts/vscode.d.ts` and `src/vs/workbench/api/common/extHostTypes.ts` expose condition, hit condition, and log message on `Breakpoint`, but no trigger relationship. `$acceptBreakpointsDelta` therefore cannot expose it through `debug.breakpoints` or `debug.onDidChangeBreakpoints`.
- **maintainer confirmation:** A maintainer confirmed that triggered breakpoints had not reached the extension API: https://github.com/microsoft/vscode/issues/215944#issuecomment-2177252907.
- **canonical search:** Repository searches for open triggered-breakpoint extension API requests found no older issue owning the same observable request; the supplied candidate https://github.com/microsoft/vscode/issues/232009 concerns unrelated editor token-color behavior.
