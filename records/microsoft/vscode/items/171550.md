# Issue #171550 — Focused item in tree is never unfocused

[https://github.com/microsoft/vscode/issues/171550](https://github.com/microsoft/vscode/issues/171550)

## Summary

Keep open: current source drops empty-focus changes, so clearing a tree's focus leaves the previous item in extension command arguments. This remains the canonical report for that symptom; the related extension PR implements a workaround, not a core fix.

## Change summary

Clear stale focused-item command arguments when an extension-contributed tree no longer has a focused item.

## Best solution

Make extension command context accurately represent an explicitly cleared tree focus through the tree-view and extension-host bridge. Preserve keyboard navigation state where appropriate, and have the tree-view owner settle how ordinary DOM blur interacts with the proposed TreeView.activeItem API.

## Evidence

- **Exact Escape trigger:** src/vs/workbench/browser/actions/listCommands.ts:792-821 registers Escape as list.clear. With one selected item, its handler calls setSelection([]) followed by setFocus([]), providing the explicit focus-clear path described in the report.
- **Empty focus is discarded:** src/vs/workbench/browser/parts/views/treeView.ts:773-784 retains lastActive when getFocus()[0] is absent and only processes onDidChangeFocus when e.elements.length is nonzero. Consequently, the empty-focus event from list.clear never clears the previously published item. The DOM blur listener at line 686 only changes this.focused.
- **Stale value reaches command arguments:** TreeViewPane.getActionsContext in src/vs/workbench/browser/parts/views/treeView.ts:165-166 requests $focusedTreeItem. src/vs/workbench/api/browser/mainThreadTreeViews.ts:205 forwards items.focus.handle, and src/vs/workbench/api/common/extHostTreeViews.ts:311-312 resolves that argument to treeView.focusedElement. Its stored _focusedHandle therefore remains the previous item after Escape.
