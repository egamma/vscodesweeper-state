# Issue #236600 — Support collapsing/expanding notebook cell comments

[https://github.com/microsoft/vscode/issues/236600](https://github.com/microsoft/vscode/issues/236600)

## Summary

Notebook cell comments still have a no-op collapse handler on current main, so the requested capability remains missing. The older notebook-commenting issues concern broader exploration and comment-location mapping, not the same collapse-button symptom, and do not justify a duplicate close.

## Change summary

Support collapsing notebook cell comment threads and reopening them through a discoverable control.

## Best solution

Complete collapse/expand support in the notebook cell-comment surface, with an accessible way to restore collapsed threads. Agree on the collapsed-thread presentation before implementation; keep source-mapping and broader notebook-comment API work separate.

- **Behavior:**

  > Pressing Collapse on a notebook cell comment should visibly collapse that thread rather than do nothing. A collapsed thread must remain discoverable and reopenable by mouse and keyboard. Collapsing one thread must not hide other threads or discard pending replies. Acceptance includes correct notebook layout after collapse and expansion and unchanged text-editor commenting behavior.
- **Trace:**

  > CellComments._createCommentTheadWidget in src/vs/workbench/contrib/notebook/browser/view/cellParts/cellComments.ts constructs the shared CommentThreadWidget with a collapse delegate that immediately returns true without changing anything. CommentThreadHeader invokes this delegate through the shared widget, whose collapse() method otherwise only handles text-editor selection restoration. CellComments._updateHeight sums the retained widgets, and the class has no collapsed-thread presentation or reopening path. This confirms the missing notebook implementation without running code. The boundary is notebook thread presentation and layout, not notebook serialization, comment-location mapping, or existing text-editor behavior. https://github.com/microsoft/vscode/issues/214017 and https://github.com/microsoft/vscode/issues/144850 provide related context but do not own the same reported symptom. The uncertainty starts at the product choice of how collapsed threads are represented and reopened.
- **Open decisions:**
  - Should a collapsed thread retain a compact header at its current location, or be represented by a cell-level comment indicator, and how should that surface distinguish and reopen multiple collapsed threads?
