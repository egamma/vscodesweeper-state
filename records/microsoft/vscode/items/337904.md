# Issue #337904 — Claude agent host: steering messages sent mid-turn are never shown in the conversation

[https://github.com/microsoft/vscode/issues/337904](https://github.com/microsoft/vscode/issues/337904)

## Summary

Confirmed gap in the Claude agent host: a steered mid-turn message is injected into the SDK and its pending bubble is removed on `steering_consumed`, but nothing promotes the steered text into a visible chat action, unlike the Copilot path which has an explicit mechanism for this. Keeping open — real work remains and there's a design choice for how Claude's steered text should surface.

## Change summary

Steering messages sent mid-turn via the Claude agent host disappear from the input and never appear anywhere in the transcript, before or after the turn completes.

## Best solution

Give the Claude pipeline a Copilot-style mechanism: either promote the steered SDK echo into its own ChatTurnStarted/user message (mirroring copilotAgentSession.ts's `_beginProviderInitiatedTurn`/`_takeMatchingPendingSteering`), or render the steered text inline in the running turn as the narrower request in the issue asks — a maintainer should pick the surfacing model before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/claude/claudeAgentSession.ts`, `src/vs/platform/agentHost/node/claude/claudeSdkPipeline.ts`, `src/vs/platform/agentHost/node/claude/claudeSdkMessageRouter.ts`, `src/vs/platform/agentHost/node/agentSideEffects.ts`
- **Validation:** An agent-host test (alongside the existing claudeAgent.test.ts steering_consumed tests around line 8183) asserting that after a steering message is consumed mid-turn, a chat action reflecting the steered user text is dispatched (either inline in the running turn or as its own ChatTurnStarted), not just ChatPendingMessageRemoved.
- **Behavior:**

  > When a user sends a steering message to a running Claude turn (`chat.requestQueuing.defaultAction: 'steer'`), the steered text must become visible in the conversation transcript — either inline in the currently running turn or as its own turn — both while the turn is still running and after it completes. Today the pending bubble simply vanishes with no trace. Acceptance: a test confirms a chat action carrying the steered text is emitted when steering is consumed, and the transcript (live and on reload) shows the steered message.
- **Trace:**

  > `ClaudeAgentSession.injectSteering` (claudeAgentSession.ts:1259) builds an `SDKUserMessage` and hands it to `ClaudeSdkPipeline.injectSteering` (claudeSdkPipeline.ts:462), which enqueues it and fires `steering_consumed` the moment the iterable yields it to the SDK (claudeSdkPipeline.ts:259-270) — well before any SDK echo arrives. `AgentSideEffects._handleAgentSignal` (agentSideEffects.ts:698) handles `steering_consumed` solely by dispatching `ChatPendingMessageRemoved`; no code path turns the steered text into a `ChatTurnStarted` or an in-turn message action. Contrast with Copilot's `CopilotAgentSession._beginProviderInitiatedTurn`/`_takeMatchingPendingSteering` (copilotAgentSession.ts:1693-1750), which matches a provider-echoed `user.message` to the buffered steering entry and promotes it into a visible `ChatTurnStarted` with `origin: { kind: MessageKind.User }`. The boundary: do not touch the existing `steering_consumed` removal of the pending bubble (it's still needed to clear the input-side pending indicator) or Copilot's working mechanism — only add the missing Claude-side promotion/render step. Where the uncertainty starts: whether Claude's SDK reliably echoes the injected `user` message back through `ClaudeSdkMessageRouter.handle` (claudeSdkMessageRouter.ts:73, `message.type === 'user'`) the way Copilot's SDK does, which determines whether the same echo-matching pattern is reusable or a different signal is needed. Related, non-duplicate issues: https://github.com/microsoft/vscode/issues/336305, https://github.com/microsoft/vscode/issues/339309, https://github.com/microsoft/vscode/issues/333174 (steering-to-own-turn, explicitly marked unsupported for external harnesses).
- **Open decisions:**
  - Should the steered text render inline inside the currently running turn (the issue's explicit, narrower ask) or be promoted into its own turn like the Copilot path does?
  - Does the Claude SDK actually echo the injected steering message back as a `user` SDK message the router observes, or does the fix need a different signal/hook to recover the steered text for display?

## Evidence

- **steering_consumed only removes the pending bubble:** src/vs/platform/agentHost/node/agentSideEffects.ts:698-704 handles `signal.kind === 'steering_consumed'` by dispatching only `ActionType.ChatPendingMessageRemoved` — no chat action records the steered text anywhere.
- **fired the moment the SDK accepts the message, not after an echo:** src/vs/platform/agentHost/node/claude/claudeSdkPipeline.ts:259-270 fires `steering_consumed` from the queue callback the instant the iterable yields the steering entry to the SDK — before any SDK echo of the user message is observed, so no downstream code has a hook to convert it into a visible turn.
- **Claude session builds the SDK message but never tracks it for a later promotion:** src/vs/platform/agentHost/node/claude/claudeAgentSession.ts:1259-1281 `injectSteering()` constructs the `SDKUserMessage` and hands it to the pipeline with no bookkeeping comparable to Copilot's pending-steering map.
- **Copilot has the exact missing mechanism:** src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:1693-1714 `_beginProviderInitiatedTurn()` and the neighboring `_takeMatchingPendingSteering()` convert a provider-echoed `user.message` into a `ChatTurnStarted` action with `origin: { kind: MessageKind.User }` — this is the pattern the issue says Claude is missing.
- **related open issues, not duplicates:** https://github.com/microsoft/vscode/issues/336305 (steering starts a new turn instead of steering the active one) and https://github.com/microsoft/vscode/issues/339309 (resume rebuild drops subagent replies) are adjacent Claude steering/turn issues but address different observable symptoms (wrong turn attribution, dropped replies on rebuild) rather than this issue's 'never rendered at all' gap.
