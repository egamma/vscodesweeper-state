# Issue #337904 — Claude agent host: steering messages sent mid-turn are never shown in the conversation

[https://github.com/microsoft/vscode/issues/337904](https://github.com/microsoft/vscode/issues/337904)

## Summary

Real, distinct bug in the Claude agent host's steering path: the general chat pending-request architecture removes a steering message from the pending queue once consumed, but nothing converts it into a persisted transcript entry for the Claude/SDK harness, so the steered text vanishes even though the log shows it was delivered and acted on.

## Change summary

When steering an in-progress Claude agent turn, the steering message is delivered to the model but never appears anywhere in the chat transcript, before or after the turn completes.

## Best solution

In the agent host session handler / Claude session, persist the steering text as part of the turn record (or a distinct history entry) when the steering pending request is consumed, instead of only calling `removePendingRequest` with no transcript trace — likely touching `agentHostSessionHandler.ts`'s steering-id-change handling and how `claudeAgentSession.ts`/`claudeMapSessionEvents.ts` build turn history from SDK output.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts`, `src/vs/platform/agentHost/node/claude/claudeAgentSession.ts`, `src/vs/platform/agentHost/node/claude/claudeMapSessionEvents.ts`
- **Validation:** A confirmed reproduction: start a Claude turn, steer mid-turn, and assert the steered text is visible in the chat transcript both while the turn runs and after reload from persisted session history.
- **Behavior:**

  > When a user steers an in-progress Claude agent turn, the steering text should be visible in the conversation — while the turn is running, and afterward when the session/log is reviewed — the same way it works for the Copilot harness today. It should not look like the model's reply was answering the original prompt when it was actually answering the steer.
- **Trace:**

  > The shared chat model (chatModel.ts, chatViewModel.ts) has generic support for rendering a pending 'steering' divider, and agentHostSessionHandler.ts removes that pending request as soon as the protocol state's steeringMessage id changes (around line 2549) — but nothing then writes the steered text into the persisted turn/transcript for the Claude harness. claudeAgent.ts's setPendingMessages comment confirms queued/steering content isn't surfaced back from the harness boundary into transcript state. Related but distinct: https://github.com/microsoft/vscode/issues/336305 (steering spawns a new turn instead of steering the active one) and https://github.com/microsoft/vscode/issues/333174 (promoting steering into its own turn, called out as unsupported for external harnesses) — this report is narrower, asking only that the steered text render inline in the running turn. Do not change how the pending queue itself is consumed/dequeued; the gap is purely in what happens to the text after it's consumed.
- **Open decisions:**
  - Should the steered text be rendered as an inline addition to the currently-running turn, or as its own lightweight history marker (per #333174's broader 'promote to its own turn' idea)?
  - Does this apply uniformly across all external (non-Copilot) harnesses, or is a Claude-specific fix acceptable for now?

## Evidence

- **generic steering UI exists:** chatModel.ts addPendingRequest/removePendingRequest and chatViewModel.ts render a 'steering' pending divider generically, so the plumbing to show a steering message exists in the shared chat layer.
- **removal without persistence:** agentHostSessionHandler.ts (~line 2549-2552) calls `this._chatService.removePendingRequest(sessionResource, previousSteeringId)` as soon as the protocol state's steeringMessage id changes, with no code path that folds the consumed text into the turn history for the Claude harness.
- **queued messages explicitly a no-op at the harness boundary:** claudeAgent.ts `setPendingMessages` comment: 'Queued messages are intentionally a no-op ... the agent boundary always receives an empty queue', confirming the harness does not surface steering content back into transcript state itself.
- **distinct from #336305:** https://github.com/microsoft/vscode/issues/336305 (older, created 2026-09-15) reports steering starting a brand-new turn instead of steering the active one, with delivery:idle in the SDK — a different observable symptom (extra turn vs. missing transcript entry), so not the same defect and not a valid duplicate canonical.
- **reporter follow-up:** Comment links the interaction with #336305, noting the hidden steer makes that bug look worse (the model's reply appears to answer the original prompt instead of the steer).
