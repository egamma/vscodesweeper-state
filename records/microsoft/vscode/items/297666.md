# Issue #297666 — Add Computer Use / Desktop Automation Support to GitHub Copilot

[https://github.com/microsoft/vscode/issues/297666](https://github.com/microsoft/vscode/issues/297666)

## Summary

This remains a valid, strongly supported backlog request: current main can automate pages in VS Code's integrated browser, but it does not provide general desktop or native-application control. With 71 community upvotes and no verified canonical issue or fixing PR, it should stay open for product and security design.

## Change summary

Enable Copilot agents to inspect and interact with desktop applications and operating-system UI beyond the integrated browser.

## Best solution

Define a permissioned, auditable computer-use capability with explicit scope, platform support, confirmation semantics, and remote-session behavior before choosing an OS automation backend. It should complement the existing integrated-browser tools without broadening their page-scoped access implicitly.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/browserView/electron-browser/tools/browserTools.contribution.ts`, `src/vs/platform/browserView/common/playwrightService.ts`, `extensions/copilot/src/extension/tools/common/toolNames.ts`
- **Validation:** The plan should end with an injectable automation-backend integration test covering screen inspection and an approved click/type action, denial or cancellation producing no OS interaction, and regression coverage showing that existing integrated-browser tools remain page-scoped; define a supported-platform smoke-test matrix as part of the platform decision.
- **Behavior:**

  > Copilot can inspect and interact with the explicitly authorized desktop surface needed for a development workflow, including identifying visible controls and performing approved pointer or keyboard actions. Users receive clear control over what application or screen is shared and which actions may run, and declining or revoking access prevents further interaction. Existing integrated-browser automation continues to operate with its current page-scoped sharing model. The supported operating systems and behavior in local, remote, and web sessions must be stated explicitly.
- **Trace:**

  > Current automation is confined to the integrated browser: BrowserChatAgentToolsContribution in src/vs/workbench/contrib/browserView/electron-browser/tools/browserTools.contribution.ts registers page-oriented tools, while IPlaywrightService in src/vs/platform/browserView/common/playwrightService.ts routes every operation through a session ID and browser page ID. OpenBrowserTool and ClickBrowserTool likewise describe and enforce integrated-browser page access; extensions/copilot/src/extension/tools/common/toolNames.ts exposes those browser tools to Copilot but has no desktop equivalent. The boundary is broader than adding another Playwright command because native applications have no DOM/page abstraction and introduce OS permissions, sensitive-screen capture, input injection, platform differences, and local-versus-remote execution semantics. Existing browser sharing, network filtering, and page automation must remain unchanged. https://github.com/microsoft/copilot-intellij/issues/12308 investigated provider-header support but did not establish a VS Code implementation.
- **Open decisions:**
  - Is the supported surface limited to VS Code and development-related applications, or may the agent control any user-authorized desktop application?
  - Which actions require per-action confirmation, which may be approved for a session, and how does the user revoke screen or application access?
  - Which desktop operating systems are supported initially, and what visible behavior is provided on unsupported platforms or vscode.dev?
  - In Remote-SSH, containers, and other remote workspaces, does computer use control the local desktop, the remote environment when one exists, or remain unavailable?
