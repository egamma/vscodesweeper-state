# Issue #45963 — [icon themes] Expose API to provide a dynamic icon theme.

[https://github.com/microsoft/vscode/issues/45963](https://github.com/microsoft/vscode/issues/45963)

## Summary

The dynamic file-icon-theme provider API remains unimplemented. The merged watcher is explicitly an unsupported workaround, while the maintainer discussion identifies a programmatic provider as the intended long-term solution.

## Change summary

Expose an extension API for providing and updating file icon themes dynamically without rewriting extension files or reloading VS Code.

## Best solution

Design a public file icon theme provider API that lets extensions supply icon associations programmatically and notify VS Code when they change, while preserving the existing static `contributes.iconThemes` path and avoiding per-resource extension-host calls during rendering.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/services/themes/common/themeExtensionPoints.ts`, `src/vs/workbench/services/themes/browser/fileIconThemeData.ts`, `src/vs/workbench/services/themes/browser/workbenchThemeService.ts`, `src/vs/workbench/services/themes/test/browser/fileIconThemeData.test.ts`
- **Validation:** Add extension-API and theme-service coverage proving that a registered dynamic file icon theme is applied, a provider change refreshes the active theme without a window reload, disposal removes the provider, and existing static `contributes.iconThemes` behavior remains unchanged.
- **Behavior:**

  > An extension can register a dynamically generated file icon theme without rewriting files in its installed extension directory. When the extension reports that its theme changed, the active theme refreshes without reloading the VS Code window. Existing static file icon themes continue to load from `contributes.iconThemes`, and provider disposal is handled predictably. The API must avoid introducing extension-host round trips for every file rendered in the workbench.
- **Trace:**

  > File icon themes currently enter through the static `iconThemes` extension point in `src/vs/workbench/services/themes/common/themeExtensionPoints.ts`; `FileIconThemeData.fromExtensionTheme` in `src/vs/workbench/services/themes/browser/fileIconThemeData.ts` records the manifest location, and `WorkbenchThemeService` loads and applies it. Commit c5963831ebcdeaf054f990b8234f16d6382f593d added an internal `_watch` path, but `_watch` remains explicitly unsupported and there is no extension-host provider API. The maintainer discussion at https://github.com/microsoft/vscode/pull/66115#issuecomment-456114402 identifies a provider as the intended solution and warns that the current workaround relies on mutating extension content. Planning should remain scoped to file icon themes unless maintainers deliberately choose a shared color/product-icon contract; static contribution behavior and icon-rendering performance must not regress.
- **Open decisions:**
  - Should the public provider return a complete generated icon-theme definition, or resolve icon associations through another bounded contract?
  - What change-event and caching semantics should extensions use to refresh an active dynamic theme without causing per-file extension-host calls?
  - Should the first API cover only file icon themes as requested, or define one shared provider model for file icon, product icon, and color themes?
  - How should dynamically registered themes participate in theme selection, persisted settings, extension disablement, and provider disposal?

## Evidence

- **maintainer direction:** In https://github.com/microsoft/vscode/pull/66115#issuecomment-456114402, the theme maintainer states that watching mutable extension content is the wrong approach and that the proper solution is an icon/color theme provider API.
- **remaining API gap:** Current `src/vs/workbench/services/themes/common/themeExtensionPoints.ts` still defines `contributes.iconThemes` solely through static `id`, `label`, and `path` properties; no programmatic provider or change event is exposed.
- **unsupported workaround:** `src/vs/workbench/services/themes/common/workbenchThemeService.ts` declares `_watch` as an unsupported option, while `src/vs/workbench/services/themes/browser/fileIconThemeData.ts` copies it into internal theme state.
- **current load path:** `src/vs/workbench/services/themes/browser/workbenchThemeService.ts` obtains file icon themes from the static extension-point registry and reloads the active theme through `FileIconThemeLoader`; there is no extension-host provider path on current main.
- **partial implementation:** Merged https://github.com/microsoft/vscode/pull/66115 in commit c5963831ebcdeaf054f990b8234f16d6382f593d added file watching and reload behavior, but its maintainer discussion explicitly says this only unblocks extensions temporarily and does not settle the requested API.
- **canonical search:** No older open issue was found that owns the same dynamic file-icon-theme provider request; https://github.com/microsoft/vscode/issues/32813 concerns reading theme colors programmatically and does not cover this observable capability.
