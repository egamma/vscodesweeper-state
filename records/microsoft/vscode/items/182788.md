- **Likely files:** `.vscode/extensions/vscode-selfhost-test-provider/src/sourceUtils.ts`, `.vscode/extensions/vscode-selfhost-test-provider/src/testTree.ts`, `.vscode/extensions/vscode-selfhost-test-provider/src/vscodeTestRunner.ts`, `.vscode/extensions/vscode-selfhost-test-provider/src/testOutputScanner.ts`, `.vscode/extensions/vscode-selfhost-test-provider/src/extension.ts`
- **Validation:** In a maintainer implementation session, use the reported two-value forEach suite and an equivalent parameterized-test fixture. Verify both generated names appear distinctly, selecting one runs only that case or suite, and results attach to the correct items; repeat with ordinary static tests to preserve existing behavior.
- **Behavior:**

  > The repository-specific VS Code Tests provider does not recognize suites whose names are computed by the reported true/false forEach example. Supported data-driven declarations should expose distinct generated cases or suites that can be selected and whose execution results are attributed correctly. Acceptance must cover both generated variants, individual execution, and unchanged discovery and execution of ordinary static tests. This request does not cover unrelated third-party testing extensions.
- **Trace:**

  > In .vscode/extensions/vscode-selfhost-test-provider/src/sourceUtils.ts, extractTestFromNode rejects names that are not ts.isStringLiteralLike, which excludes the report's interpolated template expression. TestFile.updateFromContents in testTree.ts traverses the AST without evaluating loop iterations, so accepting template syntax alone would not produce the two actual suite names. TestConstruct.fullName feeds VSCodeTestRunner.prepareArguments in vscodeTestRunner.ts, making runtime-name accuracy relevant to individual execution as well as discovery. extension.ts connects static file discovery to test runs through scanTestOutput; result reconciliation must be examined during planning. The source establishes the gap, but not the intended breadth of supported dynamic declarations or whether discovery may execute test modules. Preserve existing static-test identity and filtering behavior, and keep the work scoped to this repository's provider. Scope clarification: https://github.com/microsoft/vscode/issues/182788#issuecomment-1936285493.
- **Open decisions:**
  - Should support cover arbitrary runtime-generated Mocha tests and suites, or only a documented subset of statically discoverable data-driven declarations?
  - Must generated cases be available before any test-module execution, or may discovery load test modules to obtain their runtime names?
