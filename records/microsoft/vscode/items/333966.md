# Issue #333966 — Side chat cannot be created from selected text in a subagent chat

[https://github.com/microsoft/vscode/issues/333966](https://github.com/microsoft/vscode/issues/333966)

## Summary

Traced this conclusively in the checkout: creating a side chat from a subagent chat's selected text sends a malformed chat URI to the host because the client builds the source URI with the wrong helper for subagent chats, so the host correctly rejects it as belonging to a different session.

## Change summary

Asking a question about selected text inside a subagent chat fails to create a side chat, showing 'The side chat could not be created.'

## Best solution

In `_resolveBackendSourceChatUri` (src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts), detect a compound subagent fragment (`subagent/<toolCallId>`) and build the source URI with `buildSubagentChatUri(sessionUri, toolCallId)` instead of feeding the whole fragment into `buildChatUri`, which mis-splits it into `ahp-chat://subagent/<toolCallId>/<encodedSession>`.

## Evidence

- **malformed URI reproduced:** `_resolveBackendSourceChatUri` (baseAgentHostSessionsProvider.ts:4587-4593) does `if (sourceChat.fragment) return URI.parse(buildChatUri(sessionUri, sourceChat.fragment));`. For a subagent chat, `sourceChat.fragment` is the compound id `subagent/<toolCallId>` (see agentHostSessionHandler.ts:383 and openSubagentChat.ts:31, both building/matching the fragment as `subagent/${toolCallId}`). `buildChatUri` (sessionState.ts:1122) does `${AHP_CHAT_SCHEME}://${chatId}/${encoded}`, so passing the compound fragment yields `ahp-chat://subagent/<toolCallId>/<encodedSession>` — the toolCallId lands where the encoded session should be, and the real encoded session lands where the toolCallId should be.
- **matches the reported stack exactly:** Decoding the second path segment of the reported URI (`Y29waWxvdGNsaTo...`) as base64 yields `copilotcli:/ddf0e208-e4c0-47a2-98f9-e338ccfda78f`, the same session named in the error; the first segment (`call_KVfLCgAQ3Cf68qCciryYqymH`) is not valid base64, confirming it is the toolCallId misplaced in the session-encoding slot.
- **backend rejection:** agentService.ts:3246-3255 `_resolveSideChatOrigin`/`_resolveSessionSourceChat` decodes the URI per the `buildSubagentChatUri` convention (base64 session first, then toolCallId) and throws `... does not belong to session ...` when the parsed session doesn't match — exactly the error in the report, because the client sent the segments swapped.
- **correct helper exists but unused here:** `buildSubagentChatUri(sessionUri, toolCallId)` (sessionState.ts:1148-1152) already produces the correctly-ordered URI and is used elsewhere (agentSideEffects.ts:787,972; agentService.ts:7173), but `_resolveBackendSourceChatUri` never calls it.
