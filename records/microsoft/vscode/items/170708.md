# Issue #170708 — Cannot paste full file paths after copying file from file explorer on Linux

[https://github.com/microsoft/vscode/issues/170708](https://github.com/microsoft/vscode/issues/170708)

## Summary

The Linux clipboard defect remains current and is now well diagnosed: external file managers publish full paths as `text/uri-list`, but VS Code's native resource reader only checks its private `code/file-list` format. Keep this issue as the canonical report and route it to the editor clipboard area.

## Change summary

Copying a file in a Linux file manager and pasting into VS Code inserts only its filename, `/`, or a transformed relative path instead of the available absolute path.

## Best solution

On Linux, have the native clipboard resource path consume valid file URIs from `text/uri-list` when the private VS Code file-list format is absent, while preserving existing behavior for VS Code-originated copies and non-file clipboard data.

- **Trace:**

  > The current paste path is `CopyPasteController.handlePaste` through `mergeInDataFromCopy` in src/vs/editor/contrib/dropOrPasteInto/browser/copyPasteController.ts. When the browser paste event omits `text/uri-list`, it calls `IClipboardService.readResources()`, but `NativeClipboardService.readResources()` in src/vs/workbench/services/clipboard/electron-browser/clipboardService.ts reads only VS Code's private `code/file-list` format. External Linux file managers instead expose file paths through `text/uri-list`, as verified in https://github.com/microsoft/vscode/issues/320375. Once resource URIs reach the data transfer, `PathProvider` in src/vs/editor/contrib/dropOrPasteInto/browser/defaultProviders.ts already converts file URIs to absolute filesystem paths, so that provider and paste-selection behavior are outside the change boundary. Preserve the private format as the preferred path and do not reinterpret arbitrary `text/plain` content.

## Evidence

- **current reproduction:** https://github.com/microsoft/vscode/issues/320375 documents the same behavior through VS Code 1.135 and includes multiple Linux confirmations. Its reporter verified that Nautilus exposes the complete file URI through `text/uri-list` while `text/plain` contains only the filename.
- **source trace:** src/vs/editor/contrib/dropOrPasteInto/browser/copyPasteController.ts calls `IClipboardService.readResources()` when the paste event lacks `text/uri-list`; src/vs/workbench/services/clipboard/electron-browser/clipboardService.ts implements that call by reading only the private `code/file-list` clipboard format, so resources copied by external Linux file managers are not recovered.
- **existing path behavior:** src/vs/editor/contrib/dropOrPasteInto/browser/defaultProviders.ts already has `PathProvider`, which parses `text/uri-list` and converts `file:` URIs to `uri.fsPath`; the missing behavior is obtaining the external URI-list data, not formatting paths.
- **canonical cluster:** https://github.com/microsoft/vscode/issues/320375 is a newer, more detailed report of the same defect and should consolidate into this older issue rather than replace it. https://github.com/microsoft/vscode/issues/164 concerns broader cross-application file transfer and does not specifically own editor insertion of copied absolute paths.
- **prior confirmation:** In https://github.com/microsoft/vscode/issues/148499, a maintainer confirmed that Linux file-manager copies produced full paths in the integrated terminal but only filenames in the editor; that issue was later closed after temporary reports of recovery, while newer reports show the defect persists.
