# Issue #174488 — Annoying warnings in launch.json for configs that don't apply to current platform. 

[https://github.com/microsoft/vscode/issues/174488](https://github.com/microsoft/vscode/issues/174488)

## Summary

The bug remains relevant: launch configurations intentionally scoped to another platform still produce Problems diagnostics, and a second reporter confirmed the same observable behavior on macOS in 2025. The Backlog milestone does not block triage, but there is no evidence of a fix or an older canonical issue owning this work.

## Change summary

Avoid reporting actionable Problems errors for launch configurations that are valid only on a different operating system.

## Best solution

Keep validating all launch configurations, but downgrade unsupported-platform diagnostics for inactive platform-specific entries to non-error warnings or informational markers in the debug configuration validation path.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts`, `src/vs/workbench/contrib/debug/common/debug.ts`
- **Validation:** Add or identify a debug configuration validation test with Linux/macOS and Windows-only launch entries, asserting that the current-platform entry retains normal validation while an unsupported-platform entry does not create an error-level Problems diagnostic.
- **Behavior:**

  > A workspace may contain launch configurations for multiple operating systems. On the current OS, configurations intended for another OS must not create error-level Problems entries merely because their debug type is unsupported in the current environment. The applicable configuration must continue to receive normal validation, and genuinely malformed configurations must still be reported.
- **Trace:**

  > The issue is in the core debug configuration-validation experience rather than the C/C++ adapter's execution path: the warning says the contributed debug type is installed but unsupported in the current environment, and the debug maintainer explicitly suggested retaining a marker without treating it as a real error. The same symptom was reported on Linux and later macOS, so the first implementation step is to trace diagnostic severity from debug-type availability through DebugConfigurationManager and the launch.json schema/marker path. Preserve validation for malformed configurations and current-platform targets; the boundary is diagnostics caused only by a configuration intentionally targeting another platform.
- **Open decisions:**
  - Should an inactive platform-specific launch configuration be shown as a warning, informational marker, or only as an editor hint while remaining absent from the Problems list?

## Evidence

- **maintainer assessment:** A debug maintainer stated that these entries could be marked without making them real errors, similar to unrecognized settings, confirming that the current Problems severity is not the desired experience.
- **current user confirmation:** A second reporter reproduced the same platform-mismatch diagnostic on macOS in 2025: a Windows-only `cppvsdbg` configuration is warned about while the selected macOS target uses `cppdbg`.
- **reopen evidence:** The original reporter upgraded as requested and confirmed the problem remained; the issue was reopened because that persistence invalidated the earlier closure.
- **canonical search:** The supplied candidate https://github.com/microsoft/vscode/issues/2809 concerns variable resolution in settings, not launch.json diagnostics for configurations targeting another platform, so it does not own the same observable symptom.
