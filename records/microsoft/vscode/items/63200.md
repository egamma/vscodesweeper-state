## Plan brief

- **Likely files:** `extensions/css-language-features/server/src/cssServerMain.ts`, `extensions/css-language-features/package.json`
- **Validation:** Add language-service hover tests for nested SCSS/CSS selectors, including `#id { div {} }`, `.block { &__element {} }`, and `.foo { .bar& {} }`, asserting specificity and composed selector output before updating VS Code's bundled dependency.
- **Behavior:**

  > Hover specificity for nested SCSS/CSS selectors must account for the complete resolved selector, including all parent and ancestor selectors. Nesting operators must compose in their actual position: `.foo { .bar& {} }` represents `.bar.foo`, while BEM-style `&__element` must include the parent's specificity. Flat-selector specificity behavior must remain unchanged.
- **Trace:**

  > The issue is in the built-in CSS/SCSS language feature's language-service-backed hover path. A prior attempted fix, https://github.com/microsoft/vscode-css-languageservice/pull/139, proposed calculating specificity from the root selector node but was closed without merging; recent issue comments confirm the gap remains. https://github.com/microsoft/vscode/issues/72608 is related but newer than this re-reviewed item, so it cannot absorb this report as a duplicate. Investigation should begin in microsoft/vscode-css-languageservice's selector specificity and hover generation, then identify the dependency update surface under extensions/css-language-features; do not alter unrelated selector parsing or flat CSS specificity.
- **Open decisions:**
  - Should hover show specificity for the fully expanded selector when nesting creates multiple resolved selector combinations, or present each resolved combination separately?
