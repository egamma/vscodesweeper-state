# Issue #185814 — Adopt `GlyphMarginWidget`s

[https://github.com/microsoft/vscode/issues/185814](https://github.com/microsoft/vscode/issues/185814)

## Summary

The two remaining migrations are not implemented on current main, and the concern about widgets failing to track model edits remains visible in the current API. Keep this open under discussion until maintainers decide whether to extend the widget-position contract and complete the testing/debug adoption.

## Change summary

Adopt glyph margin widgets for testing and breakpoint decorations so each visible glyph owns its click behavior without interfering with overlapping decorations.

## Best solution

Define tracked positioning semantics for glyph margin widgets, then migrate testing and breakpoint glyphs from line-wide mouse handlers to widget-owned handlers while preserving their existing actions and model-edit tracking.

## Plan brief

- **Likely files:** `src/vs/editor/browser/editorBrowser.ts`, `src/vs/editor/browser/viewParts/glyphMargin/glyphMargin.ts`, `src/vs/workbench/contrib/testing/browser/testingDecorations.ts`, `src/vs/workbench/contrib/debug/browser/breakpointEditorContribution.ts`
- **Validation:** Add browser unit coverage proving a glyph widget follows its anchored line after model insertion, plus testing/debug click-dispatch coverage proving that clicking one of two colocated glyphs invokes only that glyph's action; run the resulting suites through scripts/test.sh with their targeted --grep selectors.
- **Behavior:**

  > Testing and breakpoint glyphs must respond only when their own rendered glyph is activated; clicking a colocated breakpoint must not run a test, and clicking a test glyph must not toggle a breakpoint. Their positions must continue following the associated source line as text is inserted or deleted, matching the behavior currently obtained from model decorations. Existing primary, alternate, context-menu, and breakpoint-edit actions must remain unchanged.
- **Trace:**

  > Testing glyphs are produced as model decorations in src/vs/workbench/contrib/testing/browser/testingDecorations.ts and dispatched by TestingDecorations.onMouseDown across every decoration on the clicked line. Breakpoints follow the same model-decoration pattern in src/vs/workbench/contrib/debug/browser/breakpointEditorContribution.ts, where marginFreeFromNonDebugDecorations uses CSS-class heuristics to avoid collisions. GlyphMarginWidgets in src/vs/editor/browser/viewParts/glyphMargin/glyphMargin.ts renders widget.preference.range directly, and IGlyphMarginWidgetPosition in src/vs/editor/browser/editorBrowser.ts provides no tracked-position contract or introspection. The current adoption is limited to the diff revert button. Preserve extension-contributed decoration behavior, inline breakpoint widgets, and the existing diff revert widget; the scope is the shared tracking contract and the two unchecked adopters. Related symptoms are documented at https://github.com/microsoft/vscode/issues/196138 and https://github.com/microsoft/vscode/issues/95992.
- **Open decisions:**
  - Should all IGlyphMarginWidget ranges automatically follow model edits, including defined edge-stickiness semantics, or should tracked positioning be an opt-in part of the public widget contract?
  - Should this backlog item deliver the shared tracking support and both testing/debug migrations together, or stage the shared contract before separate adopter changes?

## Evidence

- **remaining testing adoption:** src/vs/workbench/contrib/testing/browser/testingDecorations.ts still represents test glyphs as model decorations and handles clicks through TestingDecorations.editor.onMouseDown, scanning all decorations on the clicked line; RunTestDecoration.click checks only the center glyph lane rather than ownership of the clicked DOM element.
- **remaining breakpoint adoption:** src/vs/workbench/contrib/debug/browser/breakpointEditorContribution.ts still creates breakpoint model decorations and routes gutter clicks through a contribution-wide onMouseDown listener guarded by marginFreeFromNonDebugDecorations, including a class-name heuristic for competing glyphs.
- **tracking blocker:** IGlyphMarginWidgetPosition in src/vs/editor/browser/editorBrowser.ts exposes a raw IRange, while GlyphMarginWidgets in src/vs/editor/browser/viewParts/glyphMargin/glyphMargin.ts stores that range in widget.preference and changes it only through an explicit layoutGlyphMarginWidget call. It has no equivalent to model.getDecorationRange for automatically tracked positions.
- **limited current adoption:** The only core feature currently calling addGlyphMarginWidget is src/vs/editor/browser/widget/diffEditor/features/revertButtonsFeature.ts; testing and debug have not adopted the API.
- **confirmed interaction failures:** https://github.com/microsoft/vscode/issues/196138 documents a test action firing when a colocated breakpoint is clicked, while https://github.com/microsoft/vscode/issues/95992 remains open for inability to set a breakpoint over another gutter decoration.
- **not a re-review duplicate:** https://github.com/microsoft/vscode/issues/95992 is older but covers only the breakpoint-over-decoration symptom; it does not own the broader testing and breakpoint widget migrations or the widget range-tracking prerequisite, so it cannot absorb this re-reviewed item.
