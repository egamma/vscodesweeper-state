# Issue #327927 — broker implementation setting does not persist across profiles

[https://github.com/microsoft/vscode/issues/327927](https://github.com/microsoft/vscode/issues/327927)

## Summary

The broker implementation preference remains profile-specific in current source, so switching profiles can undo the user's broker choice. Keep this accepted, team-authored issue open; the remaining scope decision is whether sharing should also make the preference machine-specific.

## Change summary

Preserve the Microsoft authentication broker implementation choice across profile switches.

## Best solution

Make the broker preference consistent across profiles without requiring users to configure sharing manually. Settle its Settings Sync and remote-machine semantics before changing the contributed setting's scope.

## Evidence

- **Current setting registration:** extensions/microsoft-authentication/package.json declares microsoft-authentication.implementation with default msal and no scope. src/vs/workbench/api/common/configurationExtensionPoint.ts:345 assigns such extension settings ConfigurationScope.WINDOW, which is included in PROFILE_SCOPES in src/vs/workbench/services/configuration/common/configuration.ts:29.
- **Reporter trigger and broker outcome:** For independently configured profiles, setting msal-no-broker in one profile does not populate another profile's settings. extensions/microsoft-authentication/src/extension.ts reads the effective configuration on activation, and src/node/cachedPublicClientApplication.ts:17-28 disables the native broker only when that effective value is msal-no-broker. A profile without the override therefore permits the native broker again.
- **Existing capability is an opt-in workaround:** src/vs/workbench/services/configuration/browser/configurationService.ts:504-510 recognizes settings listed in workbench.settings.applyToAllProfiles as shared. This can share microsoft-authentication.implementation manually, but does not deliver the requested automatic cross-profile scope.
- **Scope boundary:** ConfigurationScope.MACHINE remains in PROFILE_SCOPES, so machine scope alone would not fix profile isolation. APPLICATION_MACHINE has the relevant cross-profile and remote-machine semantics internally, but parseScope in src/vs/platform/configuration/common/configurationRegistry.ts:1215-1230 does not accept application-machine for extension manifests. APPLICATION is supported but represents a different contract.
- **Existing validation infrastructure:** src/vs/workbench/services/configuration/test/browser/configurationService.test.ts contains the WorkspaceConfigurationService - Profiles suite, including update application machine setting and switch to non default profile. These establish how shared application settings differ from ordinary profile settings; they were inspected, not executed.
