# Issue #347483 — Automations: let an automation decide when to notify

[https://github.com/microsoft/vscode/issues/347483](https://github.com/microsoft/vscode/issues/347483)

## Summary

Keep open: existing notification settings control when notifications appear, not whether an automation's findings merit one. The related warning-card and attention-badge requests do not cover this distinct, team-authored request.

## Change summary

Allow an automation to decide per run whether its findings warrant notifying the user.

## Best solution

Define a per-run notification decision that reaches the session notification consumers while respecting user notification preferences. Coordinate with warning-card work without equating an actionable finding with execution failure.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/automations/automation.ts`, `src/vs/sessions/contrib/automations/browser/automationTools.ts`, `src/vs/sessions/contrib/sessions/browser/sessionsWindowNotifier.ts`, `src/vs/sessions/contrib/sessions/test/browser/sessionsWindowNotifier.test.ts`
- **Validation:** Extend sessionsWindowNotifier.test.ts with automation runs that finish quietly versus report actionable findings under identical enabled notification settings. Verify quiet runs emit no toast, actionable runs notify once, and existing off, focus, and deduplication behavior remains intact; run the focused suite through scripts/test.sh.
- **Behavior:**

  > An automation can decide from its findings whether a run merits notifying the user. A run finding nothing new can finish without an interruption, while a run discovering a failure can request attention even if execution itself succeeded. Acceptance must cover both outcomes under the same user notification preferences and preserve ordinary session notifications. The behavior when no decision is supplied, and the treatment of execution errors or approval requests, require agreement before implementation.
- **Trace:**

  > SessionsWindowNotifier in src/vs/sessions/contrib/sessions/browser/sessionsWindowNotifier.ts observes session or chat status and sends completion, error, or input-needed notifications subject to configuration, focus, and deduplication. Sessions covered by a live chat model or widget defer to the chat notifier, so changing only this consumer would not establish complete coverage. IAutomationRun in src/vs/workbench/contrib/chat/common/automations/automation.ts has lifecycle and descriptive fields but no explicit notification decision; automationTools.ts exposes management tools only. The trace establishes those boundaries, not a complete host-to-client transport design. Preserve provider-neutral ownership, user notification controls, and the distinction between discovered failures and failed execution. https://github.com/microsoft/vscode/issues/343087 concerns card warnings and is related rather than a duplicate.
- **Open decisions:**
  - When an automation supplies no notification decision, should it retain today's completion notification behavior or default to quiet completion?
  - Does the per-run decision affect only completion interruptions, or also unread and attention indicators in the Automations UI?
  - May an automation suppress execution-error or input-needed notifications, or must those remain independently governed by user settings?
