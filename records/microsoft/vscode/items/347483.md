# Issue #347483 — Automations: let an automation decide when to notify

[https://github.com/microsoft/vscode/issues/347483](https://github.com/microsoft/vscode/issues/347483)

## Summary

Keep open for the assigned 1.148.0 milestone. Existing notification controls do not let an automation decide whether its findings warrant an alert.

## Change summary

Allow each automation run to choose whether to notify the user based on its findings.

## Best solution

Define a per-run notification intent that the session notification paths can honor without overriding user notification preferences. Keep this distinct from automation-card warning state.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/sessions/browser/sessionsWindowNotifier.ts`, `src/vs/sessions/contrib/sessions/test/browser/sessionsWindowNotifier.test.ts`, `src/vs/workbench/contrib/chat/common/automations/automation.ts`, `src/vs/sessions/contrib/automations/browser/automationTools.ts`
- **Validation:** Extend notification tests to distinguish uneventful and noteworthy automation runs under the same user notification settings; verify notification-off preferences remain authoritative and ordinary session notifications remain unchanged.
- **Behavior:**

  > An automation can decide from a run's findings whether the user should be notified. A run finding nothing new can complete quietly, while a run finding a failure can request notification. User notification preferences remain authoritative, and ordinary interactive sessions retain their existing behavior.
- **Trace:**

  > SessionsWindowNotifier in src/vs/sessions/contrib/sessions/browser/sessionsWindowNotifier.ts derives notifications from session or chat status and global chat notification settings. It delegates cases already covered by live chat notification paths through _isCoveredByChatNotifier, so changing only this notifier would not establish consistent behavior. The automation tools in src/vs/sessions/contrib/automations/browser/automationTools.ts manage definitions and dispatch, rather than reporting notification intent from a running automation. src/vs/sessions/AUTOMATIONS.md assigns execution and lifecycle authority to providers and the Agent Host, with the Agents Window observing state. The trace establishes the missing explicit intent on these inspected surfaces, but not a complete cross-provider design. The warning-card request at https://github.com/microsoft/vscode/issues/343087 is related but has a different observable outcome.
- **Open decisions:**
  - When a run supplies no notification decision, should completion retain existing notification behavior or default to silence?
  - Should an automation's quiet decision suppress only completion notifications, or also failure and input-required notifications?

## Evidence

- **Scheduling protection:** https://github.com/microsoft/vscode/issues/347483 is team-authored and assigned to release milestone 1.148.0; the milestone independently requires keeping it open.
- **Existing capability check:** src/vs/sessions/contrib/sessions/browser/sessionsWindowNotifier.ts schedules notifications from Completed, NeedsInput, and Error status transitions. Its _notify method consults ChatConfiguration.NotifyWindowOnResponseReceived or NotifyWindowOnConfirmation and window focus, not whether an automation found something noteworthy. These user-level controls do not satisfy the per-run decision requested here.
- **Automation surface:** src/vs/sessions/contrib/automations/browser/automationTools.ts exposes list, configure, run, and delete tools; its automation output contract has no explicit per-run notification intent. src/vs/sessions/AUTOMATIONS.md separates host-owned run lifecycle from client observation, making this a contract-design task rather than a notification-setting adjustment.
- **Related but distinct request:** https://github.com/microsoft/vscode/issues/343087 requests an agent tool to flag an automation card with a warning and possibly disable it. That does not cover deciding whether an individual run should notify, so it is not established as a duplicate canonical.
