# Issue #347483 — Automations: let an automation decide when to notify

[https://github.com/microsoft/vscode/issues/347483](https://github.com/microsoft/vscode/issues/347483)

## Summary

Keep open: existing notification controls do not let an automation choose whether a particular run merits attention. The assigned 1.147.0 milestone also requires retaining this scheduled work.

## Change summary

Allow automations to decide whether to notify the user based on each run's findings.

## Best solution

Define a per-run notification-intent contract that reaches the session notification paths while respecting user notification preferences. Keep this distinct from adding warning indicators to automation cards.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/automations/automation.ts`, `src/vs/sessions/contrib/sessions/browser/sessionsWindowNotifier.ts`, `src/vs/workbench/contrib/chat/browser/chatWindowNotifier.ts`, `src/vs/sessions/contrib/sessions/test/browser/sessionsWindowNotifier.test.ts`, `src/vs/workbench/contrib/chat/test/browser/chatWindowNotifier.test.ts`
- **Validation:** Extend the SessionsWindowNotifier and ChatWindowNotifier suites to cover a quiet no-change automation run, a notification-worthy finding, existing user notification preferences, and unchanged ordinary-session behavior; run both suites through scripts/test.sh with targeted --run selectors.
- **Behavior:**

  > An automation can decide from a run's findings whether that run merits notifying the user. A run finding nothing new can remain quiet, while a run finding a failure can request attention. Acceptance must cover both outcomes and establish how they interact with existing notification preferences, execution failures, and requests for user input.
- **Trace:**

  > SessionsWindowNotifier observes session status changes and delegates to ChatWindowNotifier when an existing chat model covers the session. Both inspected notification paths gate delivery on user settings and focus, without consulting an automation outcome-specific decision. IAutomationRun currently exposes lifecycle and attention-related state but no explicit notification intent. The architecture assigns execution authority to providers rather than the Agents Window, so the trace still needs to establish how a run's decision reaches both notification paths. Preserve ordinary-session notification behavior and existing cross-window deduplication. https://github.com/microsoft/vscode/issues/343087 concerns warning indicators on automation cards, not this notification decision.
- **Open decisions:**
  - Does a quiet decision suppress only normal completion notifications, or also execution-failure and user-input notifications?
  - When a run supplies no notification decision, should existing completion behavior remain the default or should automation runs remain quiet?
  - Does notification intent affect only OS notifications and window badges, or also unread and inbox attention indicators?
