# Issue #168677 — Scroll position changes randomly on Release Notes page when switching tabs

[https://github.com/microsoft/vscode/issues/168677](https://github.com/microsoft/vscode/issues/168677)

## Summary

The scroll drift is likely still present on main — the webview uses percentage-based scroll restoration which is inherently imprecise when page height changes between tab switches (e.g., lazy-loaded images). The prior canonical issue #120322 was closed as *out-of-scope, but this report specifically focuses on the Release Notes page. Keeping open as a low-priority papercut in the Backlog.

## Change summary

Switching tabs causes the Release Notes page scroll position to shift slightly up or down because the webview restores scroll by percentage rather than absolute pixel offset.

## Best solution

Fix the webview scroll restoration to use a more stable anchor (e.g., nearest visible element or absolute pixel offset after content settles) rather than the current percentage-based approach in `src/vs/workbench/contrib/webview/browser/pre/index.html` and `overlayWebview.ts`. Alternatively, ensure Release Notes images are sized before scroll restoration fires. This is a minor papercut that affects all webview-based editors, not just Release Notes.

## Evidence

- **scroll restoration mechanism:** src/vs/workbench/contrib/webview/browser/pre/index.html restores scroll via `window.scroll(0, body.clientHeight * initData.initialScrollProgress)` — a percentage-based approach that drifts when page height changes between save and restore (e.g., images loading).
- **overlayWebview tracking:** src/vs/workbench/contrib/webview/browser/overlayWebview.ts stores `_initialScrollProgress` as a float percentage and replays it on webview re-creation, compounding any height mismatch.
- **prior canonical:** https://github.com/microsoft/vscode/issues/120322 was closed as *out-of-scope on 2022-12-05, just days before this issue was filed. A commenter (gjsjohnmurray) noted this issue could reopen that concern.
- **workaround:** Comment #3 notes opening release notes in a split editor or new window avoids the issue, and suggests image caching would fix it — consistent with the percentage-based scroll restoration root cause.
