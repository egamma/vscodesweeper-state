# Issue #176666 — Split View: Allow Snap To Content Size

[https://github.com/microsoft/vscode/issues/176666](https://github.com/microsoft/vscode/issues/176666)

## Summary

A real SplitView capability gap remains on current main: views can request a preferred size, but a sash cannot enter a persistent content-bound state and leave it when dragged away. This team-authored Backlog request should remain open for design and implementation.

## Change summary

Allow a split-view pane to snap to its content size, track later content-size changes, and clear that binding when the user moves the sash away.

## Best solution

Add a generic, opt-in SplitView contract for a dynamic content snap size and preserve that size while the sash is bound, without changing existing minimum/maximum sizing or collapse snapping. Debug views such as Variables and Call Stack can then expose content-size changes through that contract.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/splitview/splitview.ts`, `src/vs/base/browser/ui/splitview/paneview.ts`, `src/vs/base/test/browser/ui/splitview/splitview.test.ts`, `src/vs/workbench/browser/parts/views/viewPaneContainer.ts`, `src/vs/workbench/contrib/debug/browser/variablesView.ts`, `src/vs/workbench/contrib/debug/browser/callStackView.ts`
- **Validation:** Extend src/vs/base/test/browser/ui/splitview/splitview.test.ts to verify that dragging a sash to a view's content snap size binds it, subsequent content-size events resize that view within available constraints, and dragging away clears the binding while existing minimum-size collapse snapping remains unchanged.
- **Behavior:**

  > An opted-in pane exposes its current content size as a sash snap point. Dragging the adjacent sash onto that point binds the pane to its content, so later content growth or shrinkage updates the pane size while the layout respects available space and neighboring constraints. Dragging the sash away clears the binding. Existing panes and existing collapse-to-minimum snapping remain unchanged.
- **Trace:**

  > IView in src/vs/base/browser/ui/splitview/splitview.ts currently exposes minimumSize, maximumSize, and a boolean snap whose drag handling only collapses or reveals a view around minimumSize. IView.onDidChange may emit a preferred size, and SplitView.onViewChange immediately applies it, but SplitView does not track whether a sash was deliberately bound to that size. Pane in src/vs/base/browser/ui/splitview/paneview.ts forwards constraint changes, while ViewPaneContainer persists ordinary sash sizes. BreakpointsView implements a separate content-fit behavior by setting minimumBodySize and maximumBodySize from tree.contentHeight; that behavior must not be generalized by conflating content snap size with hard constraints. The plan should enumerate SplitView and PaneView consumers before changing the shared contract and preserve collapse snapping, proportional layout, persisted manual sizes, and non-opted-in views.

## Evidence

- **current SplitView contract:** src/vs/base/browser/ui/splitview/splitview.ts defines only minimumSize, maximumSize, priority, proportionalLayout, and collapse-oriented snap on IView. onViewChange accepts an emitted preferred size immediately, but records no sash-bound content-size state.
- **existing snap semantics:** The drag logic in src/vs/base/browser/ui/splitview/splitview.ts uses IView.snap to hide or reveal a view around its minimum size; it does not snap to an independently changing content size.
- **debug-specific partial behavior:** src/vs/workbench/contrib/debug/browser/breakpointsView.ts:updateSize derives minimumBodySize and maximumBodySize from tree.contentHeight. As the discussion notes, this constraint-based Breakpoints behavior does not provide the requested user-controlled binding for Variables, Call Stack, or generic panes.
- **maintainer discussion:** https://github.com/microsoft/vscode/issues/176666#issuecomment-1462801400 confirms that the requested behavior needs a third size concept which the sash locks to and the layout algorithm attempts to preserve; https://github.com/microsoft/vscode/issues/176666#issuecomment-1463550117 confirms that this is the intended request.
- **canonical search:** Searches for split-view snapping, fit-to-content panes, and debug-view automatic resizing found no older open issue with the same reporter-observable behavior; the only exact fit-to-content result was https://github.com/microsoft/vscode/issues/176666 itself.
