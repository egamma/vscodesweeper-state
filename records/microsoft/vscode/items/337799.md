# Issue #337799 — Copilot 

[https://github.com/microsoft/vscode/issues/337799](https://github.com/microsoft/vscode/issues/337799)

## Summary

The reporter repeatedly reproduced a current-release regression where an inaccessible historical image prevents both resuming and forking a conversation. Current main recognizes this server error but only reports it and suppresses retries; it does not make the conversation usable again.

## Change summary

Resuming or forking conversations containing an expired image attachment fails every subsequent request with `vision_attachment_not_accessible`.

## Best solution

Allow affected conversations to continue without replaying an inaccessible historical image, or rehydrate the attachment when possible. Forking must produce an independently usable conversation rather than preserving the poisoned attachment state.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/actions/chatForkActions.ts`, `extensions/copilot/src/extension/prompt/node/chatParticipantRequestHandler.ts`, `extensions/copilot/src/platform/chat/common/commonTypes.ts`, `extensions/copilot/src/extension/intents/node/toolCallingLoop.ts`
- **Validation:** Add a chat history/fork regression test containing a historical image reference that becomes inaccessible, then assert that the next request or fork can proceed without resending that reference and that unaffected historical attachments remain available.
- **Behavior:**

  > A conversation must remain usable when an image attached to an earlier turn has expired or become inaccessible. Resuming it and sending a new text request must not repeatedly fail because of that historical image, and forking from a checkpoint must create a usable branch. The user should be informed if historical image context is omitted, while accessible attachments and ordinary conversation history remain unchanged.
- **Trace:**

  > The reporter received repeated `vision_attachment_not_accessible` responses on VS Code 1.139.0, including after forking. The core fork path in src/vs/workbench/contrib/chat/browser/actions/chatForkActions.ts clones serialized requests and preserves `variableData`. Copilot reconstructs those historical references in `createTurnFromVSCodeChatHistoryTurns` in extensions/copilot/src/extension/prompt/node/chatParticipantRequestHandler.ts. Current error handling in extensions/copilot/src/platform/chat/common/commonTypes.ts identifies the condition, and `ToolCallingLoop.shouldAutoRetry` in extensions/copilot/src/extension/intents/node/toolCallingLoop.ts suppresses retries, but neither provides recovery. The uncertainty starts at whether attachment accessibility can be determined or refreshed before sending, or only after the service rejects the request; preserve normal replay of accessible images and do not broadly discard historical context.
- **Open decisions:**
  - When a historical image is inaccessible, should VS Code automatically omit it and continue with a warning, or require an explicit user action before resending the conversation?
  - Should a fork retain accessible historical images while dropping only the rejected attachment, or intentionally start with text-only history to guarantee independence from expiring attachment state?
