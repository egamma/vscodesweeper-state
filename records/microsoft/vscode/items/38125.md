# Issue #38125 — [Extensions] Bind package.config's activation onLanguage to configuration

[https://github.com/microsoft/vscode/issues/38125](https://github.com/microsoft/vscode/issues/38125)

## Summary

Configuration-bound language activation remains a real API gap. Existing broad activation events support the maintainer's lightweight-loader workaround, but do not provide selective activation from user-configured languages; later extension-author discussion confirms the distinction.

## Change summary

Allow an extension's language activation conditions to follow user-configured language identifiers rather than only static manifest entries.

## Best solution

Define a configuration-aware activation contract in the extension infrastructure that preserves lazy loading for selected languages. Retain the lightweight-loader workaround while maintainers decide the declarative contract and configuration-change semantics.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/common/extensionsRegistry.ts`, `src/vs/platform/extensionManagement/common/implicitActivationEvents.ts`, `src/vs/workbench/services/extensions/common/extensionDescriptionRegistry.ts`, `src/vs/workbench/services/language/common/languageService.ts`
- **Validation:** Use a minimal test extension with a static Markdown activation event and a configured additional plaintext language. In a fresh extension host, opening only a plaintext document must activate it when plaintext is selected, while opening an unselected language must not. Repeat after a configuration change under the agreed update semantics, and verify existing static activation events remain unchanged.
- **Behavior:**

  > An extension should activate when a document uses a language selected through its supported configuration, without first opening a document in a hardcoded language. Unselected languages should not trigger this selective activation. Acceptance must cover a fresh extension host, the configured additional language, an unselected language, and the agreed behavior when configuration changes.
- **Trace:**

  > ImplicitActivationEventsImpl in src/vs/platform/extensionManagement/common/implicitActivationEvents.ts computes and caches activation strings from extension manifests and static contribution generators. ExtensionDescriptionRegistry in src/vs/workbench/services/extensions/common/extensionDescriptionRegistry.ts indexes those strings, while WorkbenchLanguageService in src/vs/workbench/services/language/common/languageService.ts emits specific and generic language events. These paths do not resolve an extension's user-configured language list. The maintainer's existing workaround is a minimal broadly activated entry point that performs its own filtering; it does not meet selective declarative activation. Independent demand and the same limitation are documented at https://github.com/DavidAnson/vscode-markdownlint/issues/228; https://github.com/DavidAnson/vscode-markdownlint/pull/368 was not merged and explicitly retained the activation limitation. Preserve existing static events and ordinary provider registration semantics. Uncertainty starts at the public declaration contract, configuration scope, and how settings changes affect previously inactive extensions.
- **Open decisions:**
  - What public manifest contract should declare a binding between language activation and an extension's configuration setting?
  - Which configuration scope determines the selected languages in multi-root workspaces?
  - Should adding a language to configuration activate an inactive extension immediately when a matching document is already open, or only on a subsequent language activation event?
