# Issue #339278 — Shift+drag from the Explorer no longer delivers drag/drop events to a webview (regression)

[https://github.com/microsoft/vscode/issues/339278](https://github.com/microsoft/vscode/issues/339278)

## Summary

Detailed, well-isolated regression report (extension-bisected, exact version/commit, Win+WSL) about shift+drag from the Explorer no longer reaching webviews, while OS-level shift+drag still works — plausible and corroborated by an independent report in another repo, but I couldn't confirm the root cause from source alone or execute Electron drag/drop here, so this needs a maintainer/agent repro before further action.

## Change summary

Shift+drag of a file/folder from the VS Code Explorer onto a webview no longer re-enables the webview (removes pointer-events:none) or delivers dragover/drop, while the same shift+drag from the OS file explorer still works.

## Best solution

A maintainer or agent session should reproduce with a minimal sample webview extension and instrument src/vs/workbench/contrib/webview/browser/webviewWindowDragMonitor.ts (the 'drag'/'dragover' window listeners that toggle pointer-events) and src/vs/workbench/browser/parts/editor/editorDropTarget.ts (isDragIntoEditorEvent/onDragEnter) to see whether an internal HTML5 drag started from the Explorer list actually dispatches 'drag'/'dragover' events to the window the same way an OS-level drag does, or whether something now intercepts/stops it earlier in the chain (e.g. list view's own dragover handling in src/vs/base/browser/ui/list/listView.ts).

## Evidence

- **editor-side shift handling:** src/vs/workbench/browser/parts/editor/editorDropTarget.ts's isDragIntoEditorEvent()/onDragEnter() also special-case shiftKey to skip creating the drop overlay, but this only applies to editor-tab webviews, not the sidebar WebviewView the reporter also says is affected.
- **external corroboration:** https://github.com/Kilo-Org/kilocode/issues/14737 reports the identical regression (shift+drag into a chat webview stopped working after a VS Code 1.140 update), suggesting this is a real, broader regression rather than reporter-specific.
