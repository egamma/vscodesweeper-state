# Issue #214277 — Disable notebook chat hint permanently when the user has triggered ctrl+i

[https://github.com/microsoft/vscode/issues/214277](https://github.com/microsoft/vscode/issues/214277)

## Summary

The requested persistence remains unimplemented: starting inline chat dismisses the current notebook hint, but current source records no durable state when Ctrl+I is used. Keep this accepted On Deck request open for a product decision about notebook-only versus shared empty-editor hint behavior.

## Change summary

Permanently stop showing the notebook chat discovery hint after the user has invoked inline chat with Ctrl+I.

## Best solution

Remember that the user has discovered notebook inline chat and suppress future notebook-cell hints, while preserving an explicit way to re-enable them. Decide whether that state applies only to notebook cells or to the shared empty-editor hint across notebooks and untitled editors.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/codeEditor/browser/emptyTextEditorHint/emptyTextEditorHint.ts`, `src/vs/workbench/contrib/notebook/browser/contrib/editorHint/emptyCellEditorHint.ts`
- **Validation:** Exercise an empty notebook cell before and after invoking Ctrl+I, reload the window, and verify the hint remains suppressed at the chosen scope while the explicit re-enable path restores it.
- **Behavior:**

  > An empty notebook cell may show the inline-chat discovery hint until the user invokes notebook inline chat with Ctrl+I. After that discovery action, future eligible notebook cells remain free of the hint across cell changes and window reloads. The user retains an explicit way to restore hints. Acceptance must also verify the chosen behavior for ordinary untitled editors, since the current hint implementation is shared.
- **Trace:**

  > Notebook hints derive from EmptyTextEditorHintContribution through src/vs/workbench/contrib/notebook/browser/contrib/editorHint/emptyCellEditorHint.ts. In src/vs/workbench/contrib/codeEditor/browser/emptyTextEditorHint/emptyTextEditorHint.ts, onWillStartSession only disposes the current widget; durable suppression occurs solely when workbench.editor.empty.hint is explicitly changed to hidden. The precedent in https://github.com/microsoft/vscode/issues/213820 stored application-scoped user state when terminal Ctrl+I ran, and its discussion explicitly called for notebooks to follow. Preserve normal inline-chat startup and non-empty-editor behavior; the uncertainty begins at whether discovery state should be notebook-specific or shared with the unified empty-editor hint.
- **Open decisions:**
  - Should invoking Ctrl+I suppress only notebook-cell hints, or the shared empty-editor hint in both notebook cells and untitled editors?
  - Should the existing workbench.editor.empty.hint control reset the automatic suppression state when the user re-enables hints?

## Evidence

- **current source gap:** src/vs/workbench/contrib/codeEditor/browser/emptyTextEditorHint/emptyTextEditorHint.ts listens to IInlineChatSessionService.onWillStartSession and only calls disposeHint(); it persists the hidden state only when the user explicitly activates “don't show,” through workbench.editor.empty.hint.
- **notebook code path:** src/vs/workbench/contrib/notebook/browser/contrib/editorHint/emptyCellEditorHint.ts derives the notebook-cell hint from EmptyTextEditorHintContribution, so notebook Ctrl+I currently has no notebook-specific durable discovery state.
- **accepted direction:** In https://github.com/microsoft/vscode/issues/213820#issuecomment-2145516536, a maintainer agreed that notebooks should follow the terminal behavior; that terminal issue was implemented by storing an application-scoped user flag when its Ctrl+I command runs.
- **existing capability is partial:** The workbench.editor.empty.hint setting can hide the shared hint manually, but it does not automatically react to Ctrl+I and affects the broader empty-editor surface rather than expressing notebook discovery state.
- **canonical search:** The exact notebook-hint search found no other open issue. https://github.com/microsoft/vscode/issues/213820 is closed and terminal-specific, so it is precedent rather than a valid duplicate canonical.
