# Issue #326166 — Plugins hooks on devcontainers can't call upon plugin location

[https://github.com/microsoft/vscode/issues/326166](https://github.com/microsoft/vscode/issues/326166)

## Summary

Keep open: two commenters independently confirm that plugin-backed hooks fail in WSL/devcontainers when their commands reference host-side plugin files. Current source still exposes a host-path/execution-environment mismatch, and neither a verified fixing commit nor an older canonical covering this exact symptom was established.

## Change summary

Make plugin hooks resolve bundled scripts and resources in the environment where the hooks execute, rather than passing inaccessible Windows installation paths into a container shell.

## Best solution

Ensure plugin discovery, hook command selection, and bundled-resource availability agree with the hook execution environment. Diagnose the Windows-to-WSL-to-container boundary before choosing a fix; quoting a Windows path alone cannot make its files accessible inside a container.

- **Behavior:**

  > A plugin hook that invokes its bundled script or reads its bundled resources must work when a Windows user opens a devcontainer inside WSL. The command and plugin-root environment value must refer to files accessible to the executing hook process, and command selection must match that environment. Acceptance covers successful bundled-resource access in the container, with direct WSL and local execution remaining functional.
- **Trace:**

  > AgentPluginRepositoryService obtains the installation root from the current profile, and plugin discovery passes the plugin URI into the format-specific hook parser. In src/vs/platform/agentPlugins/common/pluginParsers.ts, interpolateHookCommandRoot substitutes pluginUri.fsPath into commands and environment values and selects quoting using field names and local isWindows. NodeHookExecutor._spawn in extensions/copilot/src/platform/chat/node/hookExecutor.ts executes the resulting string with the executor process's shell. The report and two confirmations demonstrate the mismatch, but this review did not finish tracing host selection or establish how local plugin files should become accessible inside arbitrary containers. Preserve workspace-hook cwd semantics and existing local hook behavior; do not assume Windows-drive translation alone solves container file availability. Related reports are https://github.com/microsoft/vscode/issues/313201 and https://github.com/microsoft/vscode/issues/307478.
