# Issue #94303 — Timeline providers that don't need URI's should be able to render on empty workbench

[https://github.com/microsoft/vscode/issues/94303](https://github.com/microsoft/vscode/issues/94303)

## Summary

The workspace-level Timeline provider capability remains missing on current main: the API, service, protocol, and pane all require a resource URI. The request is accepted in the On Deck milestone and needs an API/UX design decision rather than closure.

## Change summary

Allow Timeline providers to contribute workspace-level events when there is no active editor or resource URI.

## Best solution

Extend the proposed Timeline API and view model to distinguish workspace timelines from resource timelines, then provide an explicit Timeline view mode that can display workspace entries even while an editor is open.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.timeline.d.ts`, `src/vs/workbench/contrib/timeline/common/timeline.ts`, `src/vs/workbench/contrib/timeline/common/timelineService.ts`, `src/vs/workbench/contrib/timeline/browser/timelinePane.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/common/extHostTimeline.ts`, `src/vs/workbench/api/browser/mainThreadTimeline.ts`
- **Validation:** Use a proposed-API test extension that registers one workspace-capable provider and one resource-only provider: with no active editor, the Timeline view must request and render only workspace entries; after opening a file and switching modes, resource and workspace entries must follow the selected semantics without regressing pin/follow behavior.
- **Behavior:**

  > Extensions can contribute Timeline entries whose scope is the workspace rather than a file. Those entries remain available when no editor is active, and users can intentionally view them while an editor is open. Resource-only providers continue receiving resource requests and are excluded when no applicable resource exists. Acceptance must cover empty-workbench rendering, switching between workspace and editor timelines, provider filtering, and existing pin/follow behavior.
- **Trace:**

  > The proposed API in src/vscode-dts/vscode.proposed.timeline.d.ts requires `provideTimeline(uri: Uri, ...)`; that requirement continues through `$getTimeline` in src/vs/workbench/api/common/extHost.protocol.ts, ExtHostTimeline, MainThreadTimeline, and TimelineService. TimelinePane.loadTimeline in src/vs/workbench/contrib/timeline/browser/timelinePane.ts returns before querying providers when `this.uri` is undefined. Provider applicability also currently depends on matching the URI scheme in TimelineService.getTimeline. The existing pin command only freezes a resource timeline and does not select a workspace mode. Preserve existing resource-provider behavior, paging, source filtering, cache isolation, and pin/follow semantics; the uncertainty begins at the public distinction between resource and workspace requests and how users select that scope.
- **Open decisions:**
  - Should workspace scope be represented by an optional URI on the existing provider callback, or by an explicit request scope/provider capability that distinguishes workspace and resource timelines?
  - When an editor is active, should workspace entries be merged with resource entries or shown through a separately selected Timeline mode?
  - How should provider registration and source filtering express applicability when a workspace request has no URI scheme?

## Evidence

- **current API gap:** src/vscode-dts/vscode.proposed.timeline.d.ts still declares `provideTimeline(uri: Uri, ...)`, and src/vs/workbench/api/common/extHost.protocol.ts declares `$getTimeline(..., uri: UriComponents, ...)`; neither supports a workspace request without a URI.
- **current view behavior:** src/vs/workbench/contrib/timeline/browser/timelinePane.ts `loadTimeline` clears and returns when `this.uri === undefined`, so providers are never queried on an empty workbench.
- **service boundary:** src/vs/workbench/contrib/timeline/common/timelineService.ts `getTimeline` requires a `URI` and uses its scheme to select providers, while src/vs/workbench/api/common/extHostTimeline.ts revives and passes that required URI to the extension provider.
- **maintainer direction:** https://github.com/microsoft/vscode/issues/94303#issuecomment-607970330 supports making the URI optional and identifies a UX mode for showing workspace timelines while editors remain open; https://github.com/microsoft/vscode/issues/94303#issuecomment-1091912892 records consideration of separate editor and workspace timelines.
- **related items:** https://github.com/microsoft/vscode/issues/95332 is newer and limited to Git history for folders, so it cannot absorb this re-reviewed provider-API request. https://github.com/microsoft/vscode/issues/213935 was closed based on the Source Control Graph, which covers Git repository history but not arbitrary workspace Timeline providers.
- **umbrella distinction:** https://github.com/microsoft/vscode/issues/84297 is the older proposed-API tracking issue, but its stated model is explicitly file-based and follows the active document; it does not report the same empty-workbench/workspace-provider behavior required for a re-review duplicate close.
