# Issue #339187 — Agent turn should not end while background commands are still running

[https://github.com/microsoft/vscode/issues/339187](https://github.com/microsoft/vscode/issues/339187)

## Summary

Thoughtful, well-written proposal about agent turns ending while background shells are still running, with no exact existing feature-request match found. It's distinct from the two open 'turn stuck Working' issues (opposite symptom), bundles several possible designs, and has zero community corroboration yet (filed today) — keep open for maintainer triage rather than close or consolidate.

## Change summary

Make end-of-turn handling for agent-mode background/async shell commands honest: don't let a turn read as 'done' while background commands are still live, surface their state to the agent at finalization, and make the UI indicator per-session and actionable (stop, inspect, cleanup).

## Best solution

A maintainer should decide the end-of-turn contract for background shells (block/evaluate/allow-detached) and whether the agent gets a structured inventory API at turn finalization; implementation would extend the existing Background Shells pill/control (src/vs/workbench/contrib/chat/browser/sessionBackgroundShellsControl.ts, src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostBackgroundShells.ts) and the Agent Host turn-completion logic.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/sessionBackgroundShellsControl.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostBackgroundShells.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/stateToProgressAdapter.ts`
- **Validation:** A test asserting a chat turn is not reported complete (or the agent receives a structured pending-session list) while a tracked background shell for that turn is still running.
- **Behavior:**

  > When an agent-mode turn ends with one or more background/async shell commands it started still running, the turn's completion must either (a) wait for them, or (b) have the agent explicitly acknowledge each pending session (state, and what happens to it) in its final reply. The chat's 'Waiting for x background commands' indicator must never appear under a reply that already reads as done. Acceptance: a turn that starts a background shell and finishes before that shell exits either blocks completion or includes an explicit per-session disposition in the final message.
- **Trace:**

  > Existing background-shell tracking lives in src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostBackgroundShells.ts and is surfaced to the user via sessionBackgroundShellsControl.ts (pill + picker with elapsed time, detached flag, command, shellId); turn completion/finalization logic lives in the Agent Host protocol adapters such as stateToProgressAdapter.ts. None of these currently feed background-session state back to the model before it finalizes a turn, which is the gap the reporter describes. Do not conflate with https://github.com/microsoft/vscode/issues/337684 / https://github.com/microsoft/vscode/issues/336348, which are about the turn staying open indefinitely — the opposite symptom.
- **Open decisions:**
  - Should a pending background session block turn completion by default, or is 'agent must explicitly evaluate and report' sufficient?
  - Should the agent get a single machine-readable inventory call, and if so what's its contract/shape?
  - Is a configurable end-of-turn behavior (wait/evaluate/allow-detached) worth the added setting surface, or should one default policy be chosen for everyone?

## Evidence

- **existing partial surface:** src/vs/workbench/contrib/chat/browser/sessionBackgroundShellsControl.ts already implements a 'Background Shells' pill/picker showing per-shell command, elapsed time, detached state, and details — but this is a user-facing UI, not an agent-facing end-of-turn contract, so the core ask (agent awareness/evaluation at finalization) is not yet covered.
- **related but distinct issues:** https://github.com/microsoft/vscode/issues/337684 and https://github.com/microsoft/vscode/issues/336348 report the opposite symptom (turn never completes while a background shell runs); this issue is about turns completing too early without accounting for background work, so it is not a duplicate of either.
