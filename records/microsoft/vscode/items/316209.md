# Issue #316209 — No port forwarding for "code serve-web" when accessed from another machine

[https://github.com/microsoft/vscode/issues/316209](https://github.com/microsoft/vscode/issues/316209)

## Summary

Valid, current bug in the serve-web remote-extension path: localhost URIs passed to `vscode.env.asExternalUri()` are not mapped to a browser-reachable address when the web client connects from another machine. The report has a concrete reproduction and a downstream confirmation, with no verified older canonical or fixing change.

## Change summary

Make `vscode.env.asExternalUri()` return a usable forwarded or externally mapped URI for localhost services exposed by extensions running under `code serve-web`.

## Best solution

Define and implement serve-web authority/port-mapping semantics so localhost URIs from the remote extension host resolve through the server address used by the browser, while preserving existing desktop, web, and remote-authority behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostTunnelService.ts`, `src/vs/workbench/api/browser/mainThreadTunnelService.ts`, `src/vs/server/node/webClientServer.ts`
- **Validation:** Add an integration test that models a web client using a non-loopback server authority, calls `vscode.env.asExternalUri()` for a remote localhost port, and asserts the returned URI is browser-reachable and no longer points at the browser machine's loopback interface.
- **Behavior:**

  > When VS Code is served with `code serve-web` and opened from another machine, an extension calling `vscode.env.asExternalUri()` for a localhost service on the server must receive a URI reachable from the browser machine. The returned URI must preserve the requested resource path and must not resolve to the browser machine's 127.0.0.1. Existing behavior for local desktop windows and established remote authorities must remain unchanged.
- **Trace:**

  > The affected flow begins at the extension-host implementation of `vscode.env.asExternalUri()` in `src/vs/workbench/api/common/extHost.api.impl.ts` and crosses the tunnel/URI resolution path in `src/vs/workbench/api/common/extHostTunnelService.ts` and `src/vs/workbench/api/browser/mainThreadTunnelService.ts`. The serve-web endpoint and browser-facing authority are established by `src/vs/server/node/webClientServer.ts`. The report and https://github.com/flutter/devtools/issues/9827 confirm the browser-visible symptom, but the record does not settle whether serve-web should create a true tunnel, expose a proxy route, or only rewrite to an explicitly configured public authority. Keep ordinary desktop and other remote-authority URI handling outside the change boundary.
- **Open decisions:**
  - Should serve-web proxy remote localhost ports through its own HTTP origin, or return direct server-host URLs for ports that are already externally reachable?
  - Must this behavior be enabled explicitly by a CLI option, or should `asExternalUri()` provide it by default for serve-web sessions?

## Evidence

- **reproduction:** The report gives a concrete two-machine flow: run `code serve-web --host 0.0.0.0 --port 9000`, connect from another machine, and call `vscode.env.asExternalUri()` with a localhost URI; the resulting webview URL still targets the client machine's localhost.
- **independent confirmation:** https://github.com/flutter/devtools/issues/9827 is an open downstream report of the same observable failure: Dart DevTools cannot connect under vscode-serve-web because the browser receives a 127.0.0.1 endpoint.
