# Issue #344012 — Windows: extension child processes are respawned during shutdown, causing "unable to start correctly (0xc0000142)" popups

[https://github.com/microsoft/vscode/issues/344012](https://github.com/microsoft/vscode/issues/344012)

## Summary

Keep open for Windows shutdown investigation: the report provides sufficient steps and event-log evidence to retest, but neither process respawning nor its owner is confirmed. Current source has orderly extension-host termination guards and automatic crash recovery; their ordering during Windows session teardown needs verification.

## Change summary

Prevent shutdown-time process launches from producing application-initialization error dialogs when Windows restarts with VS Code open.

## Best solution

Establish which process launches powershell.exe and lemminx-win32.exe during session teardown, then ensure the responsible lifecycle or recovery path stops launching processes once shutdown is committed. Preserve ordinary crash recovery outside shutdown; extension involvement alone does not establish an extension-caused defect.

## Plan brief

- **Likely files:** `src/vs/platform/lifecycle/electron-main/lifecycleMainService.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/services/extensions/electron-browser/localProcessExtensionHost.ts`, `src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts`
- **Validation:** On a disposable Windows ARM64 environment matching the report, activate XML and PowerShell with the specified extensions and restart Windows with VS Code open. Correlate process creation and parent identity with session-ending events and VS Code logs; acceptance is no shutdown-triggered recovery launches or 0xc0000142 popups across repeated restarts, while ordinary extension-host crash recovery still works outside shutdown.
- **Behavior:**

  > Restarting Windows with VS Code open and the reported XML and PowerShell processes active produces application-error dialogs during teardown. Once session shutdown is committed, recovery must not launch replacement processes that cannot initialize. Verify repeated Windows restarts without these dialogs and preserve normal recovery when Windows is not shutting down.
- **Trace:**

  > The report at https://github.com/microsoft/vscode/issues/344012 provides reproduction steps and event-log timing, but its respawn explanation is a hypothesis. LifecycleMainService.registerListeners in src/vs/platform/lifecycle/electron-main/lifecycleMainService.ts drives normal shutdown from Electron application events. AbstractExtensionService registers onWillShutdown to stop extension hosts, while LocalProcessExtensionHost.disconnect sets _terminating and _onExtHostProcessExit suppresses expected exits. NativeExtensionService._onExtensionHostCrashed can restart a crashed local extension host. The unresolved boundary is whether Windows session-ending notification precedes these paths and whether the new executables originate from host recovery, extension-owned recovery, or terminal activity. Attribute the launches before selecting an owning component; do not disable ordinary crash recovery or assume all extension child processes are directly managed by VS Code.

This is a candidate path only: the report does not establish that the extension host itself exits, rather than an extension-owned child process.
