# Issue #273325 — Subagents: Limit read/write access to specific file globs

[https://github.com/microsoft/vscode/issues/273325](https://github.com/microsoft/vscode/issues/273325)

## Summary

The requested file-level access controls remain absent on current main, and the existing custom-agent tool allowlist cannot limit writes to particular paths. This team-authored Backlog request should remain open for an access-policy design.

## Change summary

Allow runSubagent callers to constrain subagent reads and writes to approved file globs, including a no-write mode.

## Best solution

Define a subagent access-policy contract with independently configurable read and write scopes, then enforce it across every workspace-writing path rather than only the built-in edit tool. The design must settle glob semantics and whether terminal, MCP, and extension tools are included before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts`, `src/vs/workbench/contrib/chat/common/participants/chatAgents.ts`, `src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts`, `src/vs/workbench/contrib/chat/test/common/tools/builtinTools/runSubagentTool.test.ts`
- **Validation:** Add targeted RunSubagentTool and LanguageModelToolsService tests covering an allowed write, an out-of-scope denied write, and a no-write invocation; run them with scripts/test.sh using a grep that selects the RunSubagentTool and LanguageModelToolsService suites.
- **Behavior:**

  > A runSubagent invocation can independently constrain which workspace files the child may read and write. A write-only allowlist supports the reported case where the child reads the workspace but writes only beneath a research directory, while an empty write scope makes the child read-only. Attempts outside the effective scope are rejected explicitly, and the parent agent's permissions remain unchanged. Acceptance must cover allowed and denied paths and demonstrate that no supported subagent write path bypasses the policy.
- **Trace:**

  > RunSubagentTool in src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts currently exposes only prompt, description, agentName, and model, then creates an IChatAgentRequest carrying tool selection and subAgentInvocationId. IChatAgentRequest in src/vs/workbench/contrib/chat/common/participants/chatAgents.ts has no file-access policy. LanguageModelToolsService in src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts receives the subagent identity and generic tool parameters, but path interpretation is tool-specific; custom-agent tools can remove write tools wholesale but cannot scope them by path. The uncertainty starts at the enforcement contract: terminal commands and arbitrary MCP or extension tools may write without presenting a standardized file path. Keep the parent request's permissions and ordinary non-subagent tool behavior unchanged. https://github.com/microsoft/vscode/issues/300411 overlaps on call-time tool selection but is newer and does not own this path-scoping requirement.
- **Open decisions:**
  - Is the access policy supplied per runSubagent invocation, declared by the selected custom agent, or supported in both places with a defined narrowing rule?
  - Must write scoping cover terminal commands and arbitrary MCP or extension tools, or only tools that expose standardized file-operation metadata?
  - What are the glob roots and matching semantics for multi-root workspaces, paths outside the workspace, symbolic links, case sensitivity, and newly created files?
  - Does the public contract support independent read and write allowlists, and what do omitted versus empty lists mean?
