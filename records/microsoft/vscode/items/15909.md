# Issue #15909 — Add ability to extend from other settings files

[https://github.com/microsoft/vscode/issues/15909](https://github.com/microsoft/vscode/issues/15909)

## Summary

This remains a valid, highly demanded Backlog feature request. Current main still loads each settings resource directly without inheritance, and this issue is the established canonical for reusable or modular settings files.

## Change summary

Allow a settings file to inherit shared settings from another file while letting the primary file override inherited values.

## Best solution

Define a supported inheritance contract for folder settings with deterministic precedence, cycle and error handling, safe access to the parent or shared files required by the original scenario, and live reload when inherited files change. The design should also settle how inherited values appear and are edited in the Settings UI.

## Plan brief

- **Likely files:** `src/vs/workbench/services/configuration/browser/configuration.ts`, `src/vs/platform/configuration/common/configurationModels.ts`, `src/vs/workbench/services/configuration/test/browser/configurationService.test.ts`, `src/vs/workbench/services/configuration/test/common/configurationModels.test.ts`
- **Validation:** Add targeted configuration-service tests for inherited-value loading, primary-file override precedence, recursive chains, cycles or missing files, permitted parent/shared paths, and change propagation; run `./scripts/test.sh --grep "settings extends"`.
- **Behavior:**

  > A folder `.vscode/settings.json` can reference a shared settings file, including the parent-relative layout in the issue, and settings in the primary file override inherited values. Recursive inheritance must terminate safely, malformed, missing, or cyclic references must produce actionable diagnostics, and changes to inherited files must refresh effective configuration. Existing settings files without inheritance and normal Settings UI writes must retain their behavior.
- **Trace:**

  > Current main loads folder configuration through FileServiceBasedConfiguration in src/vs/workbench/services/configuration/browser/configuration.ts. Its `allResources`, `resolveContents`, `loadConfiguration`, and file-change handlers know only the primary settings file plus predefined standalone resources, while ConfigurationModelParser in src/vs/platform/configuration/common/configurationModels.ts only parses the supplied JSON object. The closed attempt at https://github.com/microsoft/vscode/pull/299164 identified the relevant loading and watching path, but its containment rule rejected the original parent-relative use case and it never merged. The younger `.code-workspace.local` work at https://github.com/microsoft/vscode/pull/282854 addresses only a fixed local override convention, not reusable settings inheritance. Preserve existing configuration-scope filtering, restricted-setting handling, precedence between user/workspace/folder scopes, and behavior for files without inheritance.
- **Open decisions:**
  - What workspace-trust and filesystem boundary should govern inherited paths while still supporting the original parent-relative shared-file scenario?
  - Should the first public contract apply only to folder `.vscode/settings.json`, or also to user/profile settings and the `settings` section of `.code-workspace` files?
  - When a value originates in an inherited file, should Settings UI edits create an override in the primary file or edit the originating file?

## Evidence

- **current source gap:** In src/vs/workbench/services/configuration/browser/configuration.ts, FileServiceBasedConfiguration constructs `allResources` only from the primary settings resource and predefined standalone resources, `resolveContents` reads only that fixed list, and `loadConfiguration` parses the primary content directly. There is no inherited-resource resolution or watching path on current main.
- **parser behavior:** src/vs/platform/configuration/common/configurationModels.ts:317-454 parses the JSON object as configuration keys and contains no special handling for `extends` or included settings files.
- **canonical ownership:** https://github.com/microsoft/vscode/issues/191380 was closed by a maintainer as a duplicate of this issue for the same multiple-settings-files capability, confirming https://github.com/microsoft/vscode/issues/15909 as the canonical request.
- **unmerged implementation attempt:** https://github.com/microsoft/vscode/pull/299164 attempted inheritance and inherited-file watching but was closed without merging. Its directory-boundary restriction also excluded the original `../../.vscode/my-company-settings.json` scenario, as documented in https://github.com/microsoft/vscode/pull/299164#issuecomment-4478348825.
- **narrow related work:** https://github.com/microsoft/vscode/issues/282806 and its open PR https://github.com/microsoft/vscode/pull/282854 cover an automatically discovered `.code-workspace.local` override file. That younger, narrower design does not provide arbitrary reusable inheritance for `.vscode/settings.json` and therefore does not absorb this issue.
