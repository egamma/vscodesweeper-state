# Issue #315314 — Hydrating large chat session items block renderer during startup

[https://github.com/microsoft/vscode/issues/315314](https://github.com/microsoft/vscode/issues/315314)

## Summary

The original startup stall was credibly reproduced and diagnosed as large chat-session item hydration, but current main has since stopped eagerly sending cached per-file change arrays. There is not enough evidence that this fully addressed the reported long task, so a current Insiders confirmation and profile are needed rather than closing it as fixed.

## Change summary

Prevent large built-in Copilot chat-session items from synchronously blocking the renderer during startup.

## Best solution

Confirm whether the lazy session-change handling from https://github.com/microsoft/vscode/pull/329505 removed the startup long task. If it persists, profile the `$updateChatSessionItems` RPC path and keep large or binary session data out of eagerly hydrated startup DTOs.

## Evidence

- **maintainer diagnosis:** A maintainer attributed the stall to large chat-session items, probably involving binary content, at https://github.com/microsoft/vscode/issues/315314#issuecomment-4422118393 rather than to the MCP registry requests initially suspected.
- **current RPC path:** src/vs/workbench/api/common/extHostChatSessions.ts converts every changed item to a DTO and sends it through `$updateChatSessionItems`; src/vs/workbench/api/browser/mainThreadChatSessions.ts accepts and constructs each `MainThreadChatSessionItem` on the renderer side.
- **likely mitigation:** Commit b65471b484a261aee58c5573f08cec09db95b230 from https://github.com/microsoft/vscode/pull/329505 stopped eagerly attaching cached full changed-file arrays during lazy session listing and retained only aggregate summaries, directly reducing startup item payloads. The PR addressed renderer retention, however, and neither the reporter nor a maintainer confirmed that it removed this issue's startup long task.
