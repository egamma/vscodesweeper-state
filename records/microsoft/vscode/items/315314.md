# Issue #315314 — Hydrating large chat session items block renderer during startup

[https://github.com/microsoft/vscode/issues/315314](https://github.com/microsoft/vscode/issues/315314)

## Summary

This remains a valid startup performance bug: a maintainer traced the stalls to hydrating large chat-session items, and current main still eagerly converts, transfers, and processes the full item collection. The two MCP-focused fix PRs were closed without merging and do not establish that the actual hydration bottleneck was fixed.

## Change summary

Large persisted chat-session items cause long renderer tasks and visible UI freezes while VS Code starts.

## Best solution

Profile the chat-session item DTO boundary and keep large or binary session details out of the eager startup payload, while preserving the lightweight metadata needed to display the session list and resolving heavier details on demand.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostChatSessions.ts`, `src/vs/workbench/api/common/extHostTypeConverters.ts`, `src/vs/workbench/api/browser/mainThreadChatSessions.ts`, `src/vs/workbench/api/test/browser/mainThreadChatSessions.test.ts`
- **Validation:** Create a representative large chat-session collection containing the suspected large/binary fields, profile startup hydration before and after the change, and verify that no renderer long task attributable to `$updateChatSessionItems` exceeds 500 ms while session-list metadata and lazily resolved details remain correct.
- **Behavior:**

  > Starting VS Code while signed into GitHub with large persisted chat sessions must not freeze the renderer while the session list is populated. Lightweight session metadata must remain available at startup, and opening or expanding a session must still expose its complete details. Acceptance requires reproducing the existing long task with representative large session data and showing that the same startup no longer produces the hydration-related renderer stall.
- **Trace:**

  > The issue initially attributed the stalls to MCP registry requests, but the maintainer traced the profile to large chat-session items at https://github.com/microsoft/vscode/issues/315314#issuecomment-4422118393. ChatSessionItemCollectionImpl.replace in src/vs/workbench/api/common/extHostChatSessions.ts converts the complete changed collection through convertChatSessionDeltaToDto; ChatSessionItem.from in src/vs/workbench/api/common/extHostTypeConverters.ts includes `changes` and arbitrary `metadata`. The RPC arrives at `$updateChatSessionItems` and MainThreadChatSessionItemController.acceptChange in src/vs/workbench/api/browser/mainThreadChatSessions.ts, where every item is processed and `dto.changes` is eagerly revived. Current main retains this path. The investigation must identify whether conversion, RPC serialization, revival, metadata lookup, or their combination dominates before bounding the change; unrelated MCP account-policy fetching and ordinary chat-session rendering are outside scope.

## Evidence

- **maintainer diagnosis:** A VS Code maintainer identified large chat-session item hydration, likely involving binary content, as the actual source of the long task: https://github.com/microsoft/vscode/issues/315314#issuecomment-4422118393.
- **current source path:** On current main, src/vs/workbench/api/common/extHostChatSessions.ts still synchronously converts every changed item in convertChatSessionDeltaToDto, including `changes` and arbitrary `metadata`, before sending the collection over RPC.
- **renderer processing:** src/vs/workbench/api/browser/mainThreadChatSessions.ts still sends every received item through MainThreadChatSessionItemController.acceptChange/addOrUpdateItem; MainThreadChatSessionItem eagerly revives `dto.changes` on the renderer side.
- **unmerged fix attempts:** https://github.com/microsoft/vscode/pull/315421 and https://github.com/microsoft/vscode/pull/321992 both targeted MCP registry fetching in defaultAccount.ts, but both were closed without merging after the issue discussion identified chat-session hydration as the underlying bottleneck.
- **reported reproduction:** The report includes repeated approximately 500 ms renderer long-task warnings and an attached CPU profile; signing out removes the startup slowdown because the affected chat-session data is no longer loaded.
