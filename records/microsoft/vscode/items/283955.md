# Issue #283955 — Allow exporting flattened view for LLM's text response and toolcall results

[https://github.com/microsoft/vscode/issues/283955](https://github.com/microsoft/vscode/issues/283955)

## Summary

A real gap remains: current chat JSON and ZIP exports preserve Prompt-TSX tool results as structured metadata rather than exposing flattened text. The request belongs in the existing chat backlog, but the exported schema and scope need a maintainer decision before implementation.

## Change summary

Expose a flattened, programmatically consumable view of assistant text and tool-call results in exported chat sessions.

## Best solution

Define a backward-compatible export contract that makes the rendered text available to benchmark and analysis consumers while retaining enough structured data for normal chat import. Decide whether this belongs only in the evaluation-oriented ZIP export or in every exported chat JSON file.

- **Likely files:** `src/vs/workbench/contrib/chat/electron-browser/actions/chatExportZip.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatImportExport.ts`, `src/vs/workbench/contrib/chat/common/model/chatModel.ts`, `extensions/copilot/src/extension/prompt/vscode-node/requestLoggerToolResult.tsx`
- **Validation:** Add a targeted export test using a response whose `toolCallResults` contains a LanguageModelPromptTsxPart; verify the agreed flattened text appears in chat.json, structured data is preserved if required by the chosen contract, and the exported session still imports successfully.
- **Behavior:**

  > An exported benchmark chat session exposes the readable text represented by assistant responses and Prompt-TSX tool-call results without requiring consumers to interpret Prompt-TSX JSON. Existing session-import behavior and ordinary response content remain intact. Acceptance must cover a Prompt-TSX text result and define the observable representation of non-text content.
- **Trace:**

  > Both export commands currently serialize `ChatModel.toExport()` directly: src/vs/workbench/contrib/chat/electron-browser/actions/chatExportZip.ts writes it into ZIP chat.json, and src/vs/workbench/contrib/chat/browser/actions/chatImportExport.ts writes the standalone JSON file. ChatModel.toExport in src/vs/workbench/contrib/chat/common/model/chatModel.ts carries `IChatAgentResult.metadata` through without interpreting extension-owned values such as `toolCallResults`. The Copilot extension already has rendering semantics in extensions/copilot/src/extension/prompt/vscode-node/requestLoggerToolResult.tsx, used by request logging rather than export. The boundary must preserve import compatibility and avoid making core depend directly on extension implementation code. The uncertainty starts at the exported contract: whether flattening supplements or replaces structured results, which export command owns it, and how non-text parts are represented.
- **Open decisions:**
  - Should flattened text be an additive field alongside structured `toolCallResults`, or should the evaluation export replace those structured values?
  - Should the flattened representation appear only in the evaluation-oriented ZIP export, or also in the ordinary `workbench.action.chat.export` JSON contract?
  - What observable representation should exported image and binary/data parts use when a Prompt-TSX result is flattened?
