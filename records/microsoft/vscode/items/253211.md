# Issue #253211 — Support Instruction Breakpoints in the VS Code API

[https://github.com/microsoft/vscode/issues/253211](https://github.com/microsoft/vscode/issues/253211)

## Summary

Keep open: instruction breakpoints exist internally, but the extension API still cannot represent or manage them. A maintainer has explicitly consolidated earlier reports into this issue, and the related data-breakpoint work does not cover it.

## Change summary

Expose instruction breakpoints through the VS Code extension API so debugger extensions can synchronize CLI-managed breakpoints with the workbench.

## Best solution

Define an instruction-breakpoint API contract and support creation, removal, enumeration, and change notifications across the extension-host boundary. Settle instruction-reference lifetime and session ownership before implementation, while preserving existing source/function breakpoint behavior.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTypes.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/common/extHostDebugService.ts`, `src/vs/workbench/api/browser/mainThreadDebugService.ts`, `src/vs/workbench/contrib/debug/common/debugModel.ts`, `src/vs/workbench/api/test/browser/mainThreadDebugService.test.ts`
- **Validation:** Add extension-host/main-thread round-trip tests for instruction-breakpoint addition, removal, initial enumeration, and change notifications, including stable identity and instruction-reference/offset preservation. Exercise the agreed session-lifetime contract with an instruction-breakpoint-capable debug adapter and verify that CLI/API changes and disassembly UI changes remain synchronized without changing source/function breakpoint behavior.
- **Behavior:**

  > A debugger extension can represent, add, and remove instruction breakpoints through the VS Code API and observe corresponding workbench changes. API-managed and disassembly-managed breakpoints expose consistent identities and instruction locations so an extension can synchronize its debugger CLI. Acceptance covers initial enumeration, add/remove notifications, and the agreed behavior when debug sessions end or multiple sessions exist. Source and function breakpoint behavior remains unchanged.
- **Trace:**

  > The current public declarations have no InstructionBreakpoint type, and ExtHostDebugService.addBreakpoints serializes only source and function instances. MainThreadDebugService registration/removal DTOs have no instruction variant, convertToDto drops instruction instances, and initial enumeration excludes them. Internally, DebugService already adds/removes instruction breakpoints and sends them through debug sessions; DebugModel.InstructionBreakpoint contains instructionReference, offset, address, and canPersist, while additions emit sessionOnly events that the API bridge ignores. The unresolved boundary is how those internal session-sensitive locations become a public API contract, not whether disassembly supports breakpoints. Preserve existing breakpoint kinds and keep DAP removed-event handling in https://github.com/microsoft/vscode/issues/252294 separate. The data-breakpoint PR at https://github.com/microsoft/vscode/pull/226735 is related prior art, not an implementation of this request.
- **Open decisions:**
  - Are API-created instruction breakpoints explicitly owned by a debug session, or globally represented, and what should extensions observe when the owning session ends or another session starts?
  - Does the public location contract expose only the adapter's instructionReference and offset, or also a resolved address and persistence semantics?
