# Issue #270778 — When automatic type capture is disabled, the web type file system loads the file automatically incrementing the vscode-node-modules schema

[https://github.com/microsoft/vscode/issues/270778](https://github.com/microsoft/vscode/issues/270778)

## Summary

The reported unconditional URI remapping remains in the current web server host: virtual node_modules paths are rewritten even when acquisition is disabled. Keep this open; the existing javascript and web labels already route it appropriately.

## Change summary

Prevent web TypeScript module resolution from making existing virtual node_modules files inaccessible through unconditional vscode-node-modules URI remapping.

## Best solution

Ensure the web TypeScript server can resolve dependencies supplied by a virtual workspace filesystem without requiring automatic package acquisition. Preserve acquired-package resolution when enabled, and clarify the relationship between automatic typings acquisition and web package acquisition settings.

## Plan brief

- **Likely files:** `extensions/typescript-language-features/web/src/serverHost.ts`, `extensions/typescript-language-features/web/src/pathMapper.ts`, `extensions/typescript-language-features/src/tsServer/serverProcess.browser.ts`, `extensions/typescript-language-features/src/configuration/configuration.ts`
- **Validation:** In a web extension-host fixture, provide a virtual workspace containing a TypeScript file importing a package whose package.json and index.d.ts already exist under virtual node_modules. Disable automatic typings acquisition, restart the TypeScript server, and verify definition navigation and imported types resolve through the original provider. Repeat with web package acquisition disabled; also verify acquisition-enabled resolution still works when the package is absent locally.
- **Behavior:**

  > A web workspace with dependencies already supplied by its virtual filesystem must retain working imports and definition navigation when automatic acquisition is disabled. Resolution must not depend on successfully reading an acquisition-only URI for a file available from the original provider. Acceptance should cover both acquisition controls independently and preserve resolution of genuinely acquired packages when web package acquisition is enabled.
- **Trace:**

  > The report at https://github.com/microsoft/vscode/issues/270778 points to the realpath implementation still present in extensions/typescript-language-features/web/src/serverHost.ts. Its isNm branch maps non-file node_modules paths to vscode-node-modules regardless of acquisition flags; PathMapper subsequently reconstructs resources using that mapped scheme. The readFile path cannot recover the original virtual provider after this canonicalization. Configuration distinguishes automatic typings acquisition from web package acquisition, and WorkerServerProcessFactory passes their flags independently. The source establishes the unconditional mapping, but no runtime fixture was executed and no existing focused serverHost test was found. Preserve local file-scheme behavior, global typings handling, and enabled acquisition semantics; the remaining product question is which acquisition control should govern virtual package remapping.
- **Open decisions:**
  - Should disabling automatic typings acquisition also disable web package acquisition and its URI remapping, or should those remain independent controls while existing virtual dependencies always remain readable?

## Evidence

- **Current source confirms remapping:** At checkout 922ce6a45a81f7da9c6f9d18b0a08c2fca57934d, extensions/typescript-language-features/web/src/serverHost.ts:357–399 defines realpath(). For non-file, non-global-typings paths containing /node_modules, it calls mapUri(uri, 'vscode-node-modules') without checking enabledExperimentalTypeAcquisition or --disableAutomaticTypingAcquisition. For example, /memfs/workspace/project/node_modules/pkg/index.d.ts becomes /vscode-node-modules/workspace/memfs/workspace/project/node_modules/pkg/index.d.ts.
- **Failing read path:** extensions/typescript-language-features/web/src/pathMapper.ts preserves the remapped scheme when converting that result back to a resource. serverHost.ts:123–161 then reads that resource, not the original virtual workspace resource; its fallback also targets vscode-node-modules. Thus the original provider's accessible file does not rescue a failed read after realpath remapping. This was traced statically, not executed.
- **Separate acquisition controls do not remove the defect:** src/configuration/configuration.ts:229–235 maps typescript.disableAutomaticTypeAcquisition and its replacement js/ts.tsserver.automaticTypeAcquisition.enabled to the typings-installer flag. src/tsServer/serverProcess.browser.ts:49–54 independently selects --experimentalTypeAcquisition using webTypeAcquisitionEnabled. The separate js/ts.tsserver.web.typeAcquisition.enabled setting controls web package acquisition, but realpath() ignores even that control; disabling it is not source-level coverage of the requested behavior.

It does not report existing virtual node_modules becoming unreadable with acquisition disabled, so it does not satisfy the same-observable-symptom duplicate bar for this re-reviewed issue.

The checkout is shallow, so its available git history cannot establish a complete historical fix search. The implicated unconditional mapping is nevertheless present in current source.
