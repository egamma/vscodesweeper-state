# Issue #278325 — Unexpected extension activation after switching to empty profile

[https://github.com/microsoft/vscode/issues/278325](https://github.com/microsoft/vscode/issues/278325)

## Summary

Keep open: current source contains a profile-switch path that can register and activate an extension without first filtering it through the target profile's enablement state. This is also a maintainer-authored bug parked in On Deck, so no judgment close is permitted.

## Change summary

Switching to an empty profile can activate an extension that was disabled before the profile transition.

## Best solution

Make extension deltas from a profile switch honor the target profile's enablement state before an extension is registered or activation events are replayed, with a regression test covering a disabled extension during the transition.

## Evidence

- **profile-switch path:** src/vs/workbench/services/extensions/common/abstractExtensionService.ts handles IWorkbenchExtensionManagementService.onDidChangeProfile by forwarding every added extension directly to _handleDeltaExtensions, unlike its install handler, which filters additions through _safeInvokeIsEnabled.
- **activation path:** After a profile-switch addition, AbstractExtensionService._deltaExtensions calls _activateAddedExtensionIfNeeded; that method immediately activates extensions for previously requested activation events, '*' and 'onStartupFinished', explaining how a disabled extension can visibly activate during the transition.
- **profile-scoped state:** src/vs/platform/extensionManagement/common/extensionEnablementService.ts stores disabled extension identifiers in StorageScope.PROFILE and emits enablement changes when profile storage changes, so ordering between the target profile's disabled state and its extension delta is material.
