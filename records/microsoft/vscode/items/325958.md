# Issue #325958 — Extension Development Host fails with EADDRINUSE in WSL when using mirrored networking in WSL 2.9, works in 2.7

[https://github.com/microsoft/vscode/issues/325958](https://github.com/microsoft/vscode/issues/325958)

## Summary

Symptom is a debug-session EADDRINUSE when VS Code probes for a free extension-host debug port, but the reporter's own findings (only under WSL2 mirrored networking, resolved by downgrading WSL or switching to NAT, or by restarting the Windows HNS service) point to a WSL2 mirrored-networking loopback bug rather than a defect in VS Code's port-finding code.

## Change summary

Extension Development Host fails to launch with EADDRINUSE on random ports when WSL2 is configured with mirrored networking (regression from WSL 2.7 to 2.9).

## Best solution

Route to the WSL/extension-host area for awareness, but the actual fix belongs in WSL's mirrored-networking TCP/loopback stack; link this to the open microsoft/WSL#41102 report of 127.0.0.1 TCP handshakes never completing under mirrored networking, which plausibly explains why VS Code's connect-based free-port probe in src/vs/base/node/ports.ts (findFreePort, used by src/vs/workbench/services/extensions/electron-browser/localProcessExtensionHost.ts) misjudges port availability on affected machines.

## Evidence

- **port-check code:** src/vs/base/node/ports.ts findFreePort() considers a port free when a TCP connect() to it returns ECONNREFUSED; localProcessExtensionHost.ts calls this to pick the extension host debug port. If WSL2 mirrored networking mishandles loopback TCP (SYN never gets a SYN-ACK/RST), this probe can misreport availability, matching the reporter's random-port EADDRINUSE.
- **related upstream report:** https://github.com/microsoft/WSL/issues/41102 (open) describes 127.0.0.1 TCP connections never completing under WSL2 mirrored networking, with NAT mode unaffected — same networking-mode dependency as this issue.
- **reporter's own diagnosis:** Downgrading WSL to 2.7.10, or switching networkingMode from mirrored to nat, both eliminate the problem; a second commenter reports the same EADDRINUSE symptom fixed by restarting the Windows HNS service — all pointing outside VS Code's own code.
- **not machine-universal:** Reporter notes colleagues on the same mirrored-networking config do not reproduce it, consistent with an intermittent host-networking-stack bug rather than a deterministic VS Code logic error.
