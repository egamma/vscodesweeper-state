# Issue #214274 — `baseUri` of `exclude` in `findTextInFiles` and `findFiles2` is ignored

[https://github.com/microsoft/vscode/issues/214274](https://github.com/microsoft/vscode/issues/214274)

## Summary

The exclusion-scoping defect remains visible in current source: findTextInFiles discards baseUri, while findFiles2 preserves it initially but query construction also promotes its pattern to an unscoped exclusion. Keep this correctly routed issue open; the related report confirms the observable failure.

## Change summary

Honor the baseUri of RelativePattern exclusions in extension file and text searches without excluding matching files outside that base.

## Best solution

Preserve each exclusion's association with its base URI through API conversion, query construction, and search execution. Verify both file and text searches against nested-folder exclusions, retaining matching files elsewhere and preserving ordinary string-exclusion behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostWorkspace.ts`, `src/vs/workbench/services/search/common/queryBuilder.ts`, `src/vs/workbench/services/search/common/fileSearchManager.ts`, `src/vs/workbench/api/test/browser/extHostWorkspace.test.ts`, `src/vs/workbench/services/search/test/browser/queryBuilder.test.ts`
- **Validation:** Add and run targeted API-conversion and query-builder regressions, plus a search-level check using root/foo.txt, nested1/foo.txt, and nested2/foo.txt. Excluding RelativePattern(nested1, '*.txt') must retain root/foo.txt and nested2/foo.txt and omit nested1/foo.txt for file search and text matches; repeat with multiple exclusion bases and confirm ordinary string exclusions remain unchanged.
- **Behavior:**

  > A RelativePattern exclusion must apply relative to its baseUri, not to the workspace root or unrelated folders. With matching files at the workspace root and in two nested folders, excluding '*.txt' relative to the first nested folder must remove only that folder's matching files. File and text searches must agree on this behavior. Existing string exclusions and configured exclude/ignore settings must retain their established semantics.
- **Trace:**

  > In src/vs/workbench/api/common/extHostWorkspace.ts, findTextInFiles explicitly discards the exclusion base URI, whereas findFiles2 uses globsToISearchPatternBuilder to preserve it. In src/vs/workbench/services/search/common/queryBuilder.ts, commonQuery flattens exclusion builders into an unscoped global expression, and getFolderQueryForRoot handles roots separately without preserving each original pattern association. FileSearchManager consumes both global and folder exclusions, so repairing only the API conversion would not establish correct end-to-end behavior. The related sample and maintainer diagnosis are at https://github.com/microsoft/vscode/issues/226862. Existing API tests check pattern strings but do not establish scoped exclusion semantics. The remaining diagnosis is to enumerate the file/text and native/provider consumers of these query structures and identify the bounded execution changes and regression coverage; preserve legacy findFiles behavior and unrelated ignore-setting semantics.
