# Issue #196854 — [Accessibility] word-by-word keyboard navigation does not work in Output View

[https://github.com/microsoft/vscode/issues/196854](https://github.com/microsoft/vscode/issues/196854)

## Summary

Keep open: a maintainer confirmed that Windows screen-reader mode prevents word navigation in Output, and the relevant keybinding exclusions remain in current source. The editor input implementation has evolved, so the supplied steps should be retested with NVDA and JAWS before choosing a fix.

## Change summary

Restore Ctrl+LeftArrow and Ctrl+RightArrow word navigation and screen-reader announcements in the Windows Output view.

## Best solution

Make the read-only Output editor support word navigation with Windows screen readers while preserving its non-editable content and the editor's screen-reader-compatible word boundaries. First establish whether the failure persists in the current editor input backend, then address the confirmed navigation path without globally undoing the accessibility keybinding exclusions.

## Plan brief

- **Validation:** On Windows with NVDA and then JAWS, enable screen-reader mode, open Output with Ctrl+Shift+U, select the Window log channel containing multiword text, focus its text, and press Ctrl+LeftArrow and Ctrl+RightArrow. Verify that the caret moves between words and the corresponding words are spoken. Compare with an ordinary editor, confirm Output remains non-editable, and check that regular-editor screen-reader word navigation is unchanged.
- **Behavior:**

  > With Windows screen-reader mode enabled, Ctrl+LeftArrow and Ctrl+RightArrow in the Output text should move the caret between words and produce the corresponding screen-reader announcements. A maintainer confirmed that neither movement nor announcements occurred in the reported build, while disabling screen-reader mode restored movement. Acceptance requires checking both NVDA and JAWS on the current build, preserving read-only Output content and existing regular-editor word navigation.
- **Trace:**

  > OutputEditor.getConfigurationOverrides in src/vs/workbench/contrib/output/browser/outputView.ts sets readOnly and domReadOnly. The textarea backend maps that combination to a native readonly attribute in TextAreaEditContext._ensureReadOnlyAttribute. CursorWordLeft and CursorWordEndRight in src/vs/editor/contrib/wordOperations/browser/wordOperations.ts exclude Windows accessibility mode, matching the maintainer diagnosis at https://github.com/microsoft/vscode/issues/196854#issuecomment-1804298356. That exclusion addresses the word-boundary problem discussed in https://github.com/microsoft/vscode/issues/90578 and must not be indiscriminately removed. Current source also has a native EditContext backend and separate screen-reader content implementations; the unresolved diagnosis is which backend handles Output on the affected current configuration and where native navigation stops. Preserve Output's non-editable behavior, other platforms, and the regular editor's screen-reader-compatible navigation.
