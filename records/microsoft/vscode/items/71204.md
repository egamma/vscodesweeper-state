# Issue #71204 — File Provider: support symbolic link operations

[https://github.com/microsoft/vscode/issues/71204](https://github.com/microsoft/vscode/issues/71204)

## Summary

Keep this accepted Backlog request open: current providers can preserve symlinks during native copies, but the cross-provider path still lacks link creation and target inspection. Related discussions establish this issue as the owner of that missing capability; no verified replacement canonical was found.

## Change summary

Support inspecting and recreating symbolic links through file-system providers so cross-provider copies and moves can preserve self-contained links.

## Best solution

Define a provider-level symbolic-link contract and cross-provider preservation semantics, retaining native same-provider operations. Preserve self-contained links as requested, and settle the public API and unsupported-provider behavior with the file-service and API owners before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/files/common/files.ts`, `src/vs/platform/files/common/fileService.ts`, `src/vs/platform/files/node/diskFileSystemProvider.ts`, `src/vscode-dts/vscode.d.ts`, `src/vs/platform/files/test/browser/fileService.test.ts`
- **Validation:** After agreeing the contract, add file-service tests using distinct source and target providers: copying a tree with a relative link to an included file or directory must preserve the link and its destination; moving must preserve it before removing the source. Cover external targets and unsupported providers according to the agreed semantics, and verify native same-provider copy/rename behavior remains unchanged. No tests were executed in this read-only review.
- **Behavior:**

  > Cross-provider copy and move currently lack a way to recreate symbolic links even when their targets are included in the transferred tree. The requested outcome is to preserve those self-contained links rather than materializing their contents. Acceptance must cover links to both files and directories and verify the recreated links resolve within the destination tree. Same-provider native operations must retain their existing behavior; external-target and unsupported-provider outcomes need an explicit contract.
- **Trace:**

  > IFileSystemProvider in src/vs/platform/files/common/files.ts has no link-creation or readlink contract, while FileRealpath provides only canonical-path resolution. FileService.doMoveCopy in src/vs/platform/files/common/fileService.ts delegates native copy only for the same provider; otherwise doCopyFolder and doCopyFile create directories or transfer bytes, and cross-provider move then deletes the source. DiskFileSystemProvider.copy in src/vs/platform/files/node/diskFileSystemProvider.ts already preserves symlinks on its native path, so that behavior is not the missing feature. The public FileSystemProvider in src/vscode-dts/vscode.d.ts also lacks the required operations. https://github.com/microsoft/vscode/issues/71158#issuecomment-477057542 records the self-contained-link boundary, while https://github.com/microsoft/vscode/issues/84514 brings related link-inspection API demand. The review establishes the gap but does not settle API exposure, provider capability semantics, or enumerate every transport and provider consumer affected by a new contract.
- **Open decisions:**
  - Should symbolic-link inspection and creation be exposed to extensions through FileSystemProvider and workspace.fs as well as the internal provider contract, and what target representation should that public contract use?
  - When a provider cannot preserve a self-contained link, should cross-provider copy or move retain today's content-copy fallback or fail explicitly rather than change the item's type?

## Evidence

- **Current provider contract:** src/vs/platform/files/common/files.ts:678–705 defines IFileSystemProvider without symlink creation or readlink operations. FileRealpath and IFileSystemProviderWithFileRealpathCapability at lines 737–743 provide canonical-path resolution, not a contract for reading and recreating a symbolic link.
- **Cross-provider gap:** src/vs/platform/files/common/fileService.ts:819–917 routes cross-provider copies through doCopyFolder/doCopyFile and cross-provider moves through copy followed by deletion. These paths create directories or transfer file contents; they do not branch on isSymbolicLink or recreate links.
- **Existing capability is partial:** src/vs/platform/files/node/diskFileSystemProvider.ts:724–738 uses Promises.copy with preserveSymlinks: true. FileService uses that native copy only when sourceProvider === targetProvider, so it does not satisfy the cross-provider request. Configuration-registration searches found search.followSymlinks and watcher-related options, neither of which provides link-preserving copy operations.
- **Public API boundary:** src/vscode-dts/vscode.d.ts:9603–9771 exposes FileSystemProvider operations without link creation or target inspection. Its stat documentation explicitly returns the target's metadata with the SymbolicLink type flag; identifying a link is not enough to reconstruct it.
- **Confirmed ownership and scope:** https://github.com/microsoft/vscode/issues/71158#issuecomment-477057542 explicitly says cross-provider symlink restoration depends on this issue and advocates copying raw data for targets outside the moved data. The later closure at https://github.com/microsoft/vscode/issues/71158#issuecomment-539175635 was backlog cleanup, not evidence that this capability shipped.
- **Related API demand:** https://github.com/microsoft/vscode/issues/84514 requests inspecting symbolic links themselves for the Python extension. https://github.com/microsoft/vscode/issues/84514#issuecomment-552793521 closes that request as a duplicate of this issue, establishing related extension demand rather than a replacement canonical.
