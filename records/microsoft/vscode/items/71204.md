# Issue #71204 — File Provider: support symbolic link operations

[https://github.com/microsoft/vscode/issues/71204](https://github.com/microsoft/vscode/issues/71204)

## Summary

A real API gap remains on current main: providers can identify symlinks but cannot read their targets or create new links. This issue is the canonical request and should remain open for API design discussion.

## Change summary

Add file-provider operations for reading and creating symbolic links so cross-provider copies can preserve them.

## Best solution

Design provider capabilities equivalent to `readlink` and `symlink`, expose them through the extension-host protocol, and update cross-provider copy handling in `FileService` to preserve links according to an explicitly documented policy.

## Evidence

- **current provider API:** `src/vs/platform/files/common/files.ts` defines `IFileSystemProvider` operations through `cloneFile`, plus optional `realpath`, but no operation for reading a link's stored target or creating a symbolic link.
- **public extension API:** `src/vscode-dts/vscode.d.ts` documents that `FileSystemProvider.stat` reports target metadata with `FileType.SymbolicLink`, while the provider interface exposes neither `readlink` nor `symlink`.
- **remaining copy gap:** `src/vs/platform/files/common/fileService.ts` implements cross-provider copies by resolving folders and copying file bytes in `doCopyFolder`/`doCopyFile`; it has no branch that recreates symbolic links.
- **canonical ownership:** https://github.com/microsoft/vscode/issues/84514 was explicitly closed as a duplicate of this issue for the overlapping ability to inspect symbolic links; no separate open canonical issue was found.
