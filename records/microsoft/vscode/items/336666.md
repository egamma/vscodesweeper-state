# Issue #336666 — Agent session context transfer truncates delegated results without a lossless handoff

[https://github.com/microsoft/vscode/issues/336666](https://github.com/microsoft/vscode/issues/336666)

## Summary

Confirmed from source: `get_session_context` caps per-turn assistant text (140/800/2000 chars by detail level) with no continuation cursor, so a long delegated response is silently clipped with no way to fetch the rest — a real, unaddressed gap in multi-chat delegation, but a design/feature gap rather than a bug in existing intended behavior.

## Change summary

Peer/session-context handoff (`get_session_context`) truncates a completed delegated agent's response with no way to retrieve the omitted remainder.

## Best solution

Add a message-level continuation mechanism to `get_session_context` — either an offset/cursor for retrieving the remainder of a truncated assistant turn, or route large completed responses through the existing session-artifact channel (`sessionArtifacts.ts`) instead of inlining them, so delegated work isn't lossy by default.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/shared/sessionServerTools.ts`, `src/vs/platform/agentHost/node/shared/sessionArtifacts.ts`
- **Validation:** A server-tools test (alongside sessionServerTools.test.ts) asserting that a delegated turn longer than the per-detail cap can be fully retrieved via whichever continuation/handoff mechanism is chosen, without needing a re-run of the delegated agent.
- **Behavior:**

  > When a delegated (peer) chat completes a response longer than the `get_session_context` per-detail truncation cap, the requesting chat must be able to retrieve the full content — via a continuation cursor, an artifact/attachment reference, or another explicit full-result channel — without re-running the delegated work. Short responses within the cap are unaffected. Acceptance: a test seeding a completed turn whose assistant text exceeds the 'full' cap (2000 chars) can retrieve the complete text through the new mechanism.
- **Trace:**

  > `serializeSessionContext` in src/vs/platform/agentHost/node/shared/sessionServerTools.ts (lines 1285-1340) truncates each turn's assistant text via `trunc()`/`truncateText()` against `contextCaps[detail].assistant` (140/800/2000 chars) and sets `truncated: true`, but `hasMoreHistory` only reflects whether more *turns* exist (`snapshot.hasMoreHistory`, from `agentService.ts:1526`), not whether the current turn's text was clipped. `getSessionContextArgs` (lines 1211-1235) has no offset/cursor field to request the remainder of a clipped turn. The boundary: do not change the existing caps or default behavior for chats that fit within them; any new mechanism must be additive (a new optional argument or a separate read path), and must not weaken the deliberate size caps that keep tool payloads bounded for the calling model.
- **Open decisions:**
  - Add a per-turn text offset/cursor argument to `get_session_context` itself, or redirect oversized completed responses through the existing session-artifact channel (`sessionArtifacts.ts`) as an attachment?
  - If artifact-based, should this be automatic (host writes an artifact once a turn's text exceeds the cap) or opt-in via a tool argument?
  - Does this apply uniformly across `summary`/`digest`/`full` detail levels, or only to `full`?

## Evidence

- **truncation caps:** src/vs/platform/agentHost/node/shared/sessionServerTools.ts:1190-1196 defines `contextCaps` — assistant text is capped at 140 ('summary'), 800 ('digest'), or 2000 ('full') characters per turn — with `truncateText()` (line 1237) appending an ellipsis and setting `truncated: true` (line 1281) when a field is shortened.
- **no continuation param:** `ISessionContextArgs`/`getSessionContextArgs` (lines 1198-1235) only accept `session`, `detail`, and `transcriptLimit` (bounding the number of turns, max 50) — there is no offset/cursor argument to retrieve a truncated turn's remaining text, matching the reporter's observation that `hasMoreHistory: false` with `truncated: true` leaves no retrieval path.
- **adjacent infra:** src/vs/platform/agentHost/node/shared/sessionArtifacts.ts exposes a session-scoped artifact collection (read/mutate/remove), which is closer to the 'artifact handoff' the reporter suggests, but it's currently used for reference/metadata artifacts, not as an automatic overflow channel for oversized turn text.
