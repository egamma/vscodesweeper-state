# Issue #337024 — Clarification on wording of sandboxing prompt

[https://github.com/microsoft/vscode/issues/337024](https://github.com/microsoft/vscode/issues/337024)

## Summary

Legitimate, self-filed wording/behavior clarification for the agent-host sandbox read-permission prompt — the code shows two distinct code paths ('outside of workspace' vs 'outside the sandbox') whose semantics may not line up cleanly with what 'Allow in this Session' actually persists, and settling that needs a maintainer decision plus verification of the external Copilot SDK's runtime request shape.

## Change summary

Clarify (and possibly correct) the wording of the 'Allow reading file outside of workspace?' sandbox confirmation prompt, since 'Allow in this Session' may be understood as scoping to one file when it can actually disable sandboxing more broadly.

## Best solution

Have a maintainer confirm, against the actual `@github/copilot-sdk` runtime behavior, whether the unauthorized-path-gate read request (title: 'Allow reading file outside of workspace?' in src/vs/platform/agentHost/node/copilot/copilotToolDisplay.ts) can ever carry `requestSandboxBypass` in production; if so, the title should say 'outside the sandbox' (matching the existing bypass title) and/or the copy should make clear that 'Allow in this Session' disables sandboxing rather than granting access to a single file, per the reporter's suggestion of 'outside the workspace' wording too.

## Evidence

- **title logic:** src/vs/platform/agentHost/node/copilot/copilotToolDisplay.ts `readConfirmationTitle()` shows 'Allow reading file outside of workspace?' for the unauthorized-path-gate case and a distinct 'Read file outside the sandbox?' title only when `requestSandboxBypass` is true — the two prompts read as separate scenarios in code.
- **session-approval behavior:** src/vs/platform/agentHost/node/sessionPermissions.ts `handleToolCallConfirmed()` only disables the whole sandbox (`SessionConfigKey.SandboxEnabled: 'off'`) when the tool call's `_meta[SANDBOX_BYPASS_META_KEY]` was set, which `createToolReadyAction()` only sets when `e.requestSandboxBypass` is true — so whether 'Allow in this Session' scopes to one file or disables sandboxing depends on a flag not directly visible in the title text.
- **test coverage gap:** src/vs/platform/agentHost/test/node/copilotToolDisplay.test.ts's 'pathGate' case is synthesized without `requestSandboxBypass`, so it doesn't establish what the real Copilot SDK sends for genuinely out-of-workspace reads; confirming that requires runtime behavior from the external `@github/copilot-sdk`, not just this repo's source.
