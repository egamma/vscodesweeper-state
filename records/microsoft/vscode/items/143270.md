# Issue #143270 — Improve Performance Of Unicode Highlighting / Link Detection

[https://github.com/microsoft/vscode/issues/143270](https://github.com/microsoft/vscode/issues/143270)

## Summary

The incremental-computation and worker-result-delta capabilities remain missing on current main. Keep this maintainer-authored, accepted Backlog request open; the related performance report was explicitly consolidated into this issue.

## Change summary

Reduce repeated full-document scanning and full-result updates for Unicode highlighting and built-in link detection after edits.

## Best solution

Develop an incremental computation and result-update lifecycle for the built-in editor detectors, preserving their existing results and extension-provider contracts. Establish current large-document costs and measurable acceptance targets before committing to shared infrastructure.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/unicodeHighlighter/browser/unicodeHighlighter.ts`, `src/vs/editor/contrib/links/browser/links.ts`, `src/vs/editor/browser/services/editorWorkerService.ts`, `src/vs/editor/common/services/editorWebWorker.ts`, `src/vs/editor/common/services/editorWorker.ts`, `src/vs/editor/common/services/unicodeTextModelHighlighter.ts`, `src/vs/editor/common/languages/linkComputer.ts`, `src/vs/editor/test/common/services/unicodeTextModelHighlighter.test.ts`, `src/vs/editor/test/common/modes/linkComputer.test.ts`
- **Validation:** Extend the existing Unicode-highlighter and link-computer unit suites with edit sequences covering insertions, deletions, line splits/joins, and changes before existing matches; compare incremental results with fresh full recomputation after every edit. Add instrumentation-based checks for examined text and transferred result entries on single-line edits in large documents, and benchmark worker computation, transfer, and main-thread decoration updates against the baseline. The plan should establish explicit performance targets before implementation; none were measured during this read-only review.
- **Behavior:**

  > Editing a large document currently triggers a fresh document-wide computation for built-in links and document Unicode highlights, followed by complete result updates. The goal is to make routine small edits require work and result transfer proportional to the affected text and matches, while preserving the same highlighted characters and clickable links. Acceptance requires equivalence to full recomputation across edit sequences, correct relocation of unaffected matches, and measurable reductions in computation and transfer on large documents. Existing settings, Unicode limits and banner behavior, and contributed link-provider behavior must remain intact.
- **Trace:**

  > DocumentUnicodeHighlighter in src/vs/editor/contrib/unicodeHighlighter/browser/unicodeHighlighter.ts schedules content-change updates without supplying an affected range. EditorWorkerService and EditorWebWorker forward each request to UnicodeTextModelHighlighter.computeUnicodeHighlights, which starts a fresh scan and result. LinkDetector in src/vs/editor/contrib/links/browser/links.ts requests complete provider results; the default worker-backed provider reaches LinkComputer.computeLinks, which traverses all lines, and LinkDetector rebuilds its occurrence map. Both worker methods return complete results rather than retained-result deltas. The maintainer endorsement at https://github.com/microsoft/vscode/issues/143270#issuecomment-1042822221 distinguishes computation locality from transport savings; neither is delivered by the existing debounce or decoration API alone. Unicode decisions use word context, and link parsing includes contextual delimiters, so the proposed whitespace-independent abstraction must not be assumed correct without equivalence checks. The uncertainty starts at shared result ownership, invalidation, and performance targets, not at whether the requested capability already exists; preserve third-party provider contracts and all current detection semantics.
