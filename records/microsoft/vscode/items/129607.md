# Issue #129607 — Automatic classification: more aggressive debounce and perf considerations

[https://github.com/microsoft/vscode/issues/129607](https://github.com/microsoft/vscode/issues/129607)

## Summary

Keep open: worker execution, 600 ms debounce, and bounded text sampling are implemented, but retry backoff after unsuccessful classifications and reduced detection after success remain absent. The maintainer explicitly deferred that remaining work to the backlog.

## Change summary

Reduce unnecessary automatic language classifications while typing, especially after repeated unsuccessful attempts or an already successful detection.

## Best solution

Add an adaptive classification policy in the untitled editor model path that reduces repeated work without preventing detection after meaningful content changes. Agree on retry and reclassification thresholds before implementation, preserving explicit language choices and continuous-typing debounce.

## Plan brief

- **Likely files:** `src/vs/workbench/common/editor/textEditorModel.ts`, `src/vs/workbench/services/untitled/common/untitledTextEditorModel.ts`, `src/vs/workbench/services/untitled/test/browser/untitledTextEditor.test.ts`
- **Validation:** Add deterministic tests to the untitled editor suite using a counting language-detection service and controlled time. Verify continuous edits postpone detection, repeated unsuccessful results and successful classifications reduce calls under the agreed policy, meaningful content changes resume detection, and explicitly selected languages remain unchanged. Run the targeted suite with scripts/test.sh --run src/vs/workbench/services/untitled/test/browser/untitledTextEditor.test.ts.
- **Behavior:**

  > Automatic language classification should avoid repeatedly performing equivalent work while a user edits an untitled document. After repeated unsuccessful classifications, and after successful classification, small edits should trigger less work according to an agreed policy. Meaningful content changes must still allow the language to be detected or corrected. Acceptance checks should measure detection-call counts across small edits, larger replacements, failed guesses, and successful guesses, while preserving continuous-typing debounce and explicit language selections.
- **Trace:**

  > UntitledTextEditorModel.onModelContentChanged in src/vs/workbench/services/untitled/common/untitledTextEditorModel.ts schedules detection for every content event without using its change information to adjust classification frequency. BaseTextEditorModel.autoDetectLanguage and doAutoDetectLanguage in src/vs/workbench/common/editor/textEditorModel.ts use a fixed 600 ms ThrottledDelayer and gate only explicit language selection, resource availability, and configuration enablement. Successful automatic detection deliberately does not count as an explicit language selection; neither unsuccessful attempts nor successful classification introduce backoff. LanguageDetectionWorkerClient already runs inference in a synchronized worker, and LanguageDetectionWorker.getTextForDetection samples at most 10000 characters, so those completed optimizations are not the remaining work. Preserve worker execution, bounded sampling, configuration overrides, and explicit-language behavior; shared BaseTextEditorModel behavior outside untitled documents must not change unintentionally. https://github.com/microsoft/vscode/pull/130006 is merged and partial, while https://github.com/microsoft/vscode/issues/170343 requests a related but narrower detect-once policy. The unresolved boundary is the user-visible definition of when small edits may defer classification and when a content change must resume it.
- **Open decisions:**
  - After how many unsuccessful classifications should backoff begin, and what content change should permit another attempt?
  - After a successful classification, what size or kind of edit should permit reclassification, including replacement of the document with another language?
