# Issue #339707 — Sessions marked as done appear again after a bit

[https://github.com/microsoft/vscode/issues/339707](https://github.com/microsoft/vscode/issues/339707)

## Summary

Fresh, actively-reproduced regression in the new dev container Sessions feature: marking a dev container session done briefly hides it before it reappears, and the confetti animation doesn't fire for that path. A maintainer (cwebster-99) confirmed hitting it the same day, and the client code shows a plausible mechanism for the 'comes back after a few seconds' symptom.

## Change summary

Marking a dev container session as done is not sticking — the session disappears briefly then reappears, and no confetti animation plays (unlike normal sessions).

## Best solution

Trace why the dev container archive confirmation handshake in remoteAgentHostSessionsProvider.ts isn't completing (or is timing out) before the 5s DEV_CONTAINER_ARCHIVE_CONFIRMATION_TIMEOUT_MS window, causing `_setSessionArchivedLocally` to revert the optimistic archive; align the mark-as-done confetti trigger path to also cover dev container sessions.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/providers/remoteAgentHost/browser/remoteAgentHostSessionsProvider.ts`, `src/vs/sessions/browser/sessionActionViewItem.ts`, `src/vs/platform/agentHost/node/agentService.ts`
- **Validation:** A test or manual repro confirming a dev container session stays archived after `archiveSession` without reverting within the confirmation window, plus confetti firing on that path.
- **Behavior:**

  > Marking a dev container session as done should keep it archived/hidden from the active list (same as non-dev-container sessions) and should trigger the same mark-as-done confetti animation. Currently the session disappears briefly then reappears, and no confetti plays.
- **Trace:**

  > `archiveSession`/`_setDevContainerSessionArchived` in remoteAgentHostSessionsProvider.ts optimistically archives locally, then races a `SessionIsArchivedChanged` confirmation action against a 5s timeout; on timeout or a rejection it calls `_setSessionArchivedLocally(sessionId, !archived)`, undoing the archive. It's not yet confirmed from source why the backend confirmation fails to arrive/match in time for dev container sessions specifically, or why the confetti trigger (sessionActionViewItem.ts / sessionsPart.ts) doesn't fire on this path — that's the open diagnosis step. Do not change the confirmation handshake for non-dev-container (detached worktree) archiving, which uses a different, working path (`_setSessionArchived` directly).
- **Open decisions:**
  - Is the fix to make the backend confirm faster/reliably for dev container sessions, or to stop reverting the local archive optimistically on timeout (and instead surface an error without undoing the UI state)?

## Evidence

- **optimistic-revert code path:** src/vs/sessions/contrib/providers/remoteAgentHost/browser/remoteAgentHostSessionsProvider.ts `_setDevContainerSessionArchived` optimistically sets archived state via `_setSessionArchived`, then waits up to `DEV_CONTAINER_ARCHIVE_CONFIRMATION_TIMEOUT_MS = 5000`ms for a `SessionIsArchivedChanged` confirmation action from the backend; on timeout or rejection it calls `_setSessionArchivedLocally(sessionId, !archived)`, reverting the session back to unarchived — matching the reporter's 'removed for a few seconds then comes back' symptom.
- **member confirmation:** cwebster-99 (MEMBER) commented 'Running into this as well' the same day, corroborating the repro independent of the original reporter.
- **confetti gap:** Confetti is triggered via src/vs/sessions/browser/parts/sessionsPart.ts `triggerConfettiAnimation`/`ClickAnimation.Confetti` in sessionActionViewItem.ts on a successful mark-as-done action, which appears tied to the normal archive success path, not surviving the dev container revert — consistent with the reporter's note that confetti never shows for dev container sessions.
- **feature freshness:** Issue references 'Testing #339581', a very recently landed/active dev container sessions feature; no fix commit references this issue or touches the revert logic yet.
