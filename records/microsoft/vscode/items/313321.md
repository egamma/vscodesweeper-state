# Issue #313321 — Add estimated token cost for customization files

[https://github.com/microsoft/vscode/issues/313321](https://github.com/microsoft/vscode/issues/313321)

## Summary

Keep open: current customization rows do not expose per-file token estimates, and existing session-usage displays do not cover this request. This team-authored Backlog item needs a decision on what the estimate represents before implementation.

## Change summary

Show estimated token consumption beside customization files in the customizations management surface.

## Best solution

Provide clearly labeled per-file token estimates in the shared customizations UI, distinguishing potential context contribution from actual usage or billed cost. Agree on estimation semantics for conditionally loaded customizations and different models before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationListWidget.ts`, `src/vs/workbench/contrib/chat/common/customizationHarnessService.ts`
- **Validation:** Use the customizations editor with short and long instruction files, a conditionally applied instruction, and an on-demand skill. Check that estimates follow the agreed counting semantics, update after edits, remain distinguishable from actual usage and billed cost, and are understandable through keyboard and screen-reader navigation; pin the agreed behavior in focused tests.
- **Behavior:**

  > Users should be able to understand the potential token overhead of individual customization files from the customizations management surface before using them. Estimates must be identified as estimates rather than actual usage or charges. Acceptance should cover files of different lengths, edited content, and conditional or on-demand loading, with unavailable estimates distinguishable from zero. The management surface should remain unobtrusive and accessible.
- **Trace:**

  > AICustomizationItemRenderer.renderElement in src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationListWidget.ts renders customization metadata without any token-estimation path. ICustomizationItem in src/vs/workbench/contrib/chat/common/customizationHarnessService.ts has no estimate metadata, and the architecture specification describes shared management across harnesses. ChatContextUsageDetails in src/vs/workbench/contrib/chat/browser/widgetHosts/viewPane/chatContextUsageDetails.ts already shows actual session usage and supplied category percentages, which is distinct from prospective file estimates. The related request https://github.com/microsoft/vscode/issues/313320 concerns that session widget and should not absorb this different surface. The uncertainty begins at the counting contract: file contents, model-dependent tokenization, and conditional loading can produce different user-visible meanings. Preserve existing customization discovery, enablement, and actual-usage reporting; this request does not establish a billing calculation contract.
- **Open decisions:**
  - Should each estimate describe the file's full-content token size, or its expected contribution when loaded, including the distinction between skill metadata and on-demand bodies?
  - Should estimates use the active model's tokenizer, with an unavailable state when no tokenizer exists, or a model-independent approximation clearly labeled as such?
