# Issue #70283 —  errors in dependsOn background tasks do not prevent subsequent tasks from executing

[https://github.com/microsoft/vscode/issues/70283](https://github.com/microsoft/vscode/issues/70283)

## Summary

Background-task sequencing now exists, but the explicitly retained request—preventing dependent tasks from starting when a background dependency reports errors—remains unsupported in current source. Keep this accepted, well-supported tasks request open; no verified canonical issue absorbs the remaining work.

## Change summary

Prevent subsequent tasks from starting when a background dependency finishes a watch cycle with problem-matcher errors.

## Best solution

Make background dependency readiness account for problem-matcher errors, not only the end of a watch cycle. Settle whether an unsuccessful cycle fails the dependent invocation or leaves it waiting for a successful rebuild, while preserving successful sequencing and foreground exit-code handling.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts`, `src/vs/workbench/contrib/tasks/common/jsonSchema_v2.ts`, `src/vs/workbench/contrib/tasks/test/common/problemCollectors.test.ts`
- **Validation:** Use a background shell task that emits a problem-matcher error followed by its endsPattern and remains alive, with a dependent task that prints a distinct sentinel. Verify the sentinel is absent after the unsuccessful cycle, appears after an error-free cycle under the chosen recovery policy, and still appears normally for successful fresh and already-running dependencies. Add executable regression coverage for these dependency outcomes and preserve foreground nonzero-exit blocking.
- **Behavior:**

  > A background dependency that completes a watch cycle with problem-matcher errors must not allow its dependent command or later sequential tasks to start as if that cycle succeeded. Successful background cycles must continue to release dependent tasks without terminating the watcher. Acceptance checks must cover newly started and already-running dependencies, error versus warning diagnostics, and an unsuccessful cycle followed by a successful rebuild. Whether that rebuild resumes the original dependent invocation or requires a new invocation remains a maintainer decision.
- **Trace:**

  > The retained scope is established by https://github.com/microsoft/vscode/issues/70283#issuecomment-663467256, not by the original background sequencing hang. In src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts, _executeTask gates execution on dependency summary exit codes, while _createInactiveDependencyPromise and _getDependencyPromise report success on background inactivity without consulting diagnostics. _executeInTerminal emits Inactive before recording watch-cycle errors, so existing _taskErrors tracking does not prevent dependency release. Preserve foreground exit-code semantics, successful watcher readiness, and parallel scheduling; already-started parallel siblings are outside the successor-blocking guarantee. The source identifies the gap, but does not settle failed-cycle recovery semantics or demonstrate a dedicated terminal-task-system test harness.
- **Open decisions:**
  - When a background dependency finishes a cycle with errors, should the dependent invocation fail immediately or remain pending until that watcher completes a successful cycle?
