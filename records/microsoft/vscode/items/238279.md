# Issue #238279 — Hovering over an expression with a `!` (like `foo!.bar`) while debugging does not evaluate the expression

[https://github.com/microsoft/vscode/issues/238279](https://github.com/microsoft/vscode/issues/238279)

## Summary

The defect remains source-reproducible on current main: the generic debug-hover heuristic splits expressions at `!`, so hovering `a!.length` evaluates only `.length`. The older related issue reports a different parenthesized-expression symptom, and the attempted fixing PR was closed without merging.

## Change summary

Debug hovers should recognize postfix non-null assertions and evaluate the complete member expression in TypeScript and Dart.

## Best solution

Provide language-aware evaluatable expressions that preserve the source hover range while sending a runtime-valid expression to the debugger, such as `a.length` rather than `.length` or TypeScript-invalid `a!.length`. A maintainer should first decide whether this belongs in the generic fallback, a TypeScript provider plus corresponding language support, or a standardized LSP capability.

- **Behavior:**

  > While paused in TypeScript or another supported language, hovering the member in `a!.length` evaluates the complete intended member expression and displays its value. The expression sent to the debug adapter must be valid for that runtime rather than the current `.length` fragment or an unsupported source-only assertion. Unary negation, optional chaining, spread syntax, and ordinary member-expression hovers must remain unchanged. Acceptance requires focused tests covering the expression and range passed through the debug-hover path.
- **Trace:**

  > The fallback path in getExactExpressionStartAndEnd at src/vs/workbench/contrib/debug/common/debugUtils.ts excludes `!`, splitting `a!.length` into `a` and `.length`; getEvaluatableExpressionAtPosition then sends the latter substring to the debug adapter. An EvaluatableExpressionProvider takes precedence and can return a source range plus a different expression, but the built-in TypeScript extension does not currently register one. https://github.com/microsoft/vscode/pull/252116 only changed the generic regex and was closed unmerged; retaining `a!.length` does not address the TypeScript runtime-expression requirement. https://github.com/microsoft/vscode/issues/235168 exercises the same heuristic through parentheses but is a distinct observable defect. Keep unary `!`, optional chaining, spread handling, and other languages' fallback parsing outside the regression surface; uncertainty begins at whether postfix assertion handling should be generic or language-owned, and whether cross-language support requires the LSP work tracked at https://github.com/microsoft/language-server-protocol/issues/1596.
- **Open decisions:**
