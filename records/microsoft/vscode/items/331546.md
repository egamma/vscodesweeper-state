# Issue #331546 — Remote tunnel service status client can take over tunnel ownership

[https://github.com/microsoft/vscode/issues/331546](https://github.com/microsoft/vscode/issues/331546)

## Summary

Traced and confirmed on current main: the desktop's status-child tunnel process can win the singleton lock via `acquire_singleton()` in the retry loop, and an open PR from the same author already fixes it — this should stay open until that PR lands.

## Change summary

The desktop shared-process tunnel status client (used to relay logs/status for a service-mode tunnel) can, during a service restart race, win the singleton lock and become the tunnel owner instead of staying a passive client.

## Best solution

Review and land https://github.com/microsoft/vscode/pull/331547, which adds a hidden `--attach-to-existing` CLI mode that only ever calls `connect_as_client()` (never `acquire_singleton()`), omits hosting-only args for the status child, and updates the UI status from the tunnel name the singleton actually reports.
