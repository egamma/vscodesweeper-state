# Issue #335879 — Avoid repeated expensive work when evaluating automatic session cleanup

[https://github.com/microsoft/vscode/issues/335879](https://github.com/microsoft/vscode/issues/335879)

## Summary

Keep open: this is a team-authored engineering debt item with an explicit unresolved design space for reducing repeated automatic-cleanup work. No factual duplicate or issue-referencing implementation was established, so the team-authored protection applies.

## Change summary

Make automatic session cleanup avoid repeatedly restoring unchanged, non-actionable sessions and duplicating GitHub or provider work while retaining authoritative pre-action validation.

## Best solution

Design cleanup eligibility around cheap authoritative metadata, shared pull-request resolution, and invalidation or backoff for unchanged blocked sessions; preserve immediate validation before archive/delete and fail-closed behavior.

## Plan brief

- **Likely files:** `src/vs/sessions`
- **Validation:** Add focused lifecycle tests that run cleanup repeatedly over unchanged sessions and sessions sharing an open pull request, asserting expensive restoration and remote resolution are not repeated while archive/delete still revalidate immediately and failures prevent action.
- **Behavior:**

  > Automatic cleanup should not repeatedly perform expensive eligibility work for an unchanged session that remains blocked, including sessions tied to an open pull request or a retained worktree. Multiple sessions referring to the same pull request should not duplicate equivalent remote work within an evaluation cycle. Before archive or deletion, cleanup must refresh the authoritative state, and any validation failure must prevent the action. Acceptance should cover startup plus a later lifecycle pass, state invalidation, shared pull-request references, and fail-closed archive/delete behavior.
- **Trace:**

  > The report identifies automatic session cleanup under src/vs/sessions as repeatedly reconsidering unchanged sessions at startup and hourly lifecycle passes. Its expensive path can reach restoreSession, materializing provider chat, reading the session database, reconstructing full message history, and potentially warming the provider session catalog when direct metadata resolution fails. Related https://github.com/microsoft/vscode/issues/336620 is newer and broader, so it is context rather than a duplicate canonical. Preserve the boundary between cheap background eligibility evaluation and authoritative validation immediately before mutation; do not weaken archive/delete safety or convert provider/GitHub failures into eligibility.
- **Open decisions:**
  - Which state changes invalidate a prior non-actionable result and make a session eligible for reevaluation?
  - How long may background cleanup reuse a non-actionable result before authoritative reevaluation?
  - Should pull-request resolution be shared only within one lifecycle pass or across passes, and what freshness contract should that expose?
