# Issue #221620 — Problem comparing files

[https://github.com/microsoft/vscode/issues/221620](https://github.com/microsoft/vscode/issues/221620)

## Summary

Keep open: current source still allows an expensive diff to continue after its editor is closed, blocking subsequent worker requests. The cancellation defect is confirmed from source; the supplied CSV files' computation time has not been measured.

## Change summary

Comparing large CSV files takes excessively long and continues consuming CPU after the comparison is closed, with subsequent small comparisons also delayed.

## Best solution

Ensure closing a comparison stops its outstanding computation without disrupting other editor-worker consumers, and investigate the supplied CSV pair's performance under both diff algorithms. A finite computation timeout is a mitigation, not a replacement for cancellation.

## Plan brief

- **Likely files:** `src/vs/editor/browser/widget/diffEditor/diffEditorViewModel.ts`, `src/vs/editor/browser/widget/diffEditor/diffProviderFactoryService.ts`, `src/vs/editor/browser/services/editorWorkerService.ts`, `src/vs/editor/common/services/editorWorker.ts`, `src/vs/editor/common/services/editorWebWorker.ts`, `src/vs/editor/common/diff/defaultLinesDiffComputer/defaultLinesDiffComputer.ts`, `src/vs/editor/common/diff/legacyLinesDiffComputer.ts`, `src/vs/editor/test/browser/widget/diffEditorWidget.test.ts`, `src/vs/editor/test/common/services/editorWebWorker.test.ts`
- **Validation:** Compare the attached CSV pair with extensions disabled and maxComputationTime=0, separately using advanced and legacy. Keep another text model open, close the expensive comparison while it is computing, and immediately compare a small known pair: obsolete computation must stop and the small comparison must complete without restarting VS Code. Establish a measured cancellation-latency threshold and automated worker/lifecycle regression coverage; also check finite-timeout behavior and unrelated worker requests.
- **Behavior:**

  > An expensive file comparison must not continue consuming resources or delay subsequent comparisons after the user closes it. This applies to both advanced and legacy algorithms, including when computation time is unlimited. Unclosed comparisons must retain their existing timeout and result semantics, and cancelling one comparison must not break other editor-worker operations. Use the supplied CSV files to investigate computation performance separately from the confirmed cancellation defect.
- **Trace:**

  > DiffEditorViewModel cancels its token on disposal, but WorkerBasedDocumentDiffProvider only checks cancellation after editorWorkerService.computeDiff resolves. EditorWorkerService sends a token-free $computeDiff request to the shared worker, whose EditorWorker.computeDiff invokes the selected algorithm synchronously; advanced computation uses InfiniteTimeout for a zero time limit. This conclusively explains why closing a comparison does not interrupt work already underway, but does not establish which algorithm phase dominates the attached CSV pair. WorkerManager also serves other editor operations, so interrupting one request must preserve their availability and correct completion. The same worker constraint is acknowledged at https://github.com/microsoft/vscode/issues/287693#issuecomment-3748879548; that younger report is related, not a canonical for this re-reviewed item. Planning should establish the cross-layer interruption boundary and executable validation without treating worker termination versus cooperative scheduling as an unresolved product decision.

## Evidence

- **Concrete reproduction material and follow-up:** https://github.com/microsoft/vscode/issues/221620 includes two downloadable CSV files. The reporter describes both advanced and legacy algorithms failing to finish promptly, subsequent small comparisons remaining blocked until restart, testing with extensions disabled, and continued problems on VS Code 1.94.0 under Manjaro. Lowering the timeout eventually produced a comparison, but did not establish that the underlying problem was fixed.
- **Cancellation stops result publication, not computation:** src/vs/editor/browser/widget/diffEditor/diffEditorViewModel.ts cancels its CancellationTokenSource on disposal. In WorkerBasedDocumentDiffProvider.computeDiff, src/vs/editor/browser/widget/diffEditor/diffProviderFactoryService.ts, that token is not passed to editorWorkerService.computeDiff; it is checked only after awaiting the completed worker result. Closing the editor therefore cannot interrupt an already-running built-in diff.
- **Synchronous computation on a shared worker:** EditorWorkerService.computeDiff in src/vs/editor/browser/services/editorWorkerService.ts sends $computeDiff without a cancellation argument. In src/vs/editor/common/services/editorWebWorker.ts, EditorWorker.computeDiff invokes the selected algorithm synchronously. DefaultLinesDiffComputer uses InfiniteTimeout when maxComputationTimeMs is zero. WorkerManager is shared and stops on global model exhaustion or its idle timer, not on disposal of an individual comparison; queued small comparisons can remain behind the expensive computation.
- **Maintainer corroboration and younger related report:** https://github.com/microsoft/vscode/issues/287693 is open and reports continued diff computation after closing the editor with diffEditor.maxComputationTime set to zero. A maintainer explains the synchronous worker's inability to receive cancellation messages at https://github.com/microsoft/vscode/issues/287693#issuecomment-3748879548. It was created in January 2026, after this July 2024 report, so it cannot be this re-reviewed item's duplicate canonical.
- **Older candidate does not clearly absorb the full report:** https://github.com/microsoft/vscode/issues/206769 is open and older. It reports advanced-algorithm hangs on CSV/YAML while explicitly saying legacy works; a later comment also describes computation continuing after closing a tab. It is related, but does not clearly own this report's failures under both algorithms. https://github.com/microsoft/vscode/issues/199704 instead concerns listener warnings and inability to revert through SCM, not the same observable defect.
