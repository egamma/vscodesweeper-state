## Plan brief

- **Likely files:** `build/win32/code.iss`, `src/vs/platform/update/electron-main/updateService.win32.ts`
- **Validation:** On a policy-managed Windows 11 machine, launch VS Code elevated and initiate an update with extensions disabled; record installation target, installer logs, child-process activity, and whether the update window can be moved and repainted during preparation. Compare the equivalent non-elevated flow where permitted, and verify that any eventual fix eliminates the prolonged unresponsive interval without bypassing policy or changing elevated User Setup update disablement.
- **Behavior:**

  > The reporter observes an update window that cannot be moved for minutes when updating an elevated VS Code installation on a corporate Windows 11 laptop. The same symptom was reported for Stable and Insiders with extensions disabled, while the personal PC does not exhibit it. First confirm the affected window and preparation stage on current builds; the finished behavior should keep the update UI responsive while preparation proceeds and preserve enterprise restrictions and existing update eligibility.
- **Trace:**

  > Win32UpdateService.initialize in src/vs/platform/update/electron-main/updateService.win32.ts disables elevated User Setup updates, whereas doQuitAndInstall can launch a separate silent installer using RunAsInvoker. In build/win32/code.iss, PrepareToInstall invokes StopTunnelServiceIfNeeded and StopTunnelOtherProcesses for non-background installations; both contain synchronous waits for child processes. This identifies a preparation-stage lead, not a confirmed root cause: the reporter's installation target and actual blocked process remain unverified. The related PowerShell-profile freeze at https://github.com/microsoft/vscode/issues/196344 was addressed by https://github.com/microsoft/vscode/pull/282201 before this report, and the current process-enumeration command already suppresses profiles and interactive prompts. Do not assume that earlier fix covers this issue, bypass corporate restrictions, or broaden the work into enabling elevated User Setup updates. The plan should begin with Windows reproduction and log/process correlation rather than a prescribed source change.

## Evidence

- **Reported trigger and environment:** https://github.com/microsoft/vscode/issues/308674 reports Windows 11 Enterprise 10.0.26200.0, VS Code 1.116.0-insider at a4f5119796984330f866b3dd6b2ce0694ff5c814, and an update window that cannot be moved, with extensions disabled. The author's follow-ups report the same symptom on Stable, delays exceeding 15 minutes, and occurrence on the corporate elevated installation but not the personal PC; the proposed elevation-policy cause remains a hypothesis.
- **Installer preparation lead:** build/win32/code.iss:1451-1515 defines StopTunnelOtherProcesses, StopTunnelServiceIfNeeded, and PrepareToInstall. Non-background installation waits for hidden PowerShell and tunnel-service commands using ewWaitUntilTerminated before installation proceeds. These are plausible blocking points, but source inspection cannot establish which operation stalls on the reporter's machine.
- **Elevation and process boundary:** src/vs/platform/update/electron-main/updateService.win32.ts:139-143 disables updates for elevated User Setup installations. Its doQuitAndInstall path at lines 614-643 launches a separate installer with /silent, /log, and __COMPAT_LAYER=RunAsInvoker. A frozen installer therefore does not establish that the VS Code renderer is blocked, and the installation target matters to diagnosis.
- **Related closed report is not a canonical:** https://github.com/microsoft/vscode/issues/196344 describes a preparation-stage installer freeze relieved by terminating a PowerShell child. Maintainer comment https://github.com/microsoft/vscode/issues/196344#issuecomment-3720707374 points to https://github.com/microsoft/vscode/pull/282201, merged on 2025-12-09, before this report. Current StopTunnelOtherProcesses already uses -NoProfile and -NonInteractive; that earlier fix does not prove this later elevated corporate-machine report resolved.
- **Canonical search:** Searches for update/elevation freezes and frozen installers found no verified open canonical. https://github.com/microsoft/vscode/issues/298494 concerns updates being disabled for User Setup with UAC off, while https://github.com/microsoft/vscode/issues/203207 includes startup GPU failures; neither establishes ownership of this preparation-stage update-window freeze.
