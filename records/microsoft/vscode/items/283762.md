# Issue #283762 — VSCode loses connection with remote after "Developer: Restart Extension Host"

[https://github.com/microsoft/vscode/issues/283762](https://github.com/microsoft/vscode/issues/283762)

## Summary

The defect remains on current main: Restart Extension Host unconditionally stops every extension host in a remote window, including the local host responsible for resolving the remote authority. The issue already has the correct remote-connection routing and should stay open while maintainers choose between reloading remote windows or supporting a narrower restart.

## Change summary

Running Developer: Restart Extension Host in a remote window terminates the remote connection and immediately requires a window reload.

## Best solution

Make the command produce a recoverable, intentional result in remote windows—either perform the full reload flow with an accurate user-facing expectation or introduce a restart scope that preserves the host managing the remote connection.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/services/extensions/test/browser/extensionService.test.ts`
- **Validation:** Add and run a workbench action test for workbench.action.restartExtensionHost in both local and remote environments: local execution must retain stop/start behavior, while remote execution must complete through the selected recovery flow without entering ReconnectionPermanentFailure.
- **Behavior:**

  > In a local window, Developer: Restart Extension Host continues to restart extension hosts without reloading the window. In a remote window, invoking it must not leave the connection in the permanent-failure state or require a second manual recovery action. The resulting behavior and command wording must accurately communicate whether the whole window is being reloaded.
- **Trace:**

  > RestartExtensionHostAction in src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts calls stopExtensionHosts and startExtensionHosts without considering a remote authority. AbstractExtensionService._doStopExtensionHosts in src/vs/workbench/services/extensions/common/abstractExtensionService.ts stops every extension-host manager, while the issue discussion confirms that the local extension host manages remote authority resolution. The disconnected path reaches ReconnectionPermanentFailure in src/vs/workbench/contrib/remote/browser/remote.ts and offers Reload Window. Preserve the existing lightweight restart semantics for local windows and do not conflate this deterministic command behavior with unrelated spontaneous WSL, container, or out-of-memory crashes.
- **Open decisions:**
  - Should Restart Extension Host become Reload Window whenever a remote authority is active, or should the extension service support restarting only hosts that do not own the remote connection?
  - If remote execution reloads the window, should the command label, confirmation, or notification make the broader impact explicit?

## Evidence

- **current source:** src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts registers workbench.action.restartExtensionHost and still calls IExtensionService.stopExtensionHosts followed by startExtensionHosts without checking environmentService.remoteAuthority.
- **root cause:** src/vs/workbench/services/extensions/common/abstractExtensionService.ts implements _doStopExtensionHosts with _extensionHostManagers.stopAllInReverse(), confirming that the command stops all managed hosts rather than preserving the local host responsible for the remote authority.
- **failure path:** src/vs/workbench/contrib/remote/browser/remote.ts handles ReconnectionPermanentFailure by showing "Cannot reconnect. Please reload the window" and invoking workbench.action.reloadWindow when accepted.
- **confirmed reproduction:** The reporter reproduced with external extensions disabled, another user confirmed the same Windows 11/WSL behavior, and the maintainer explained that the local extension host manages the remote connection: https://github.com/microsoft/vscode/issues/283762#issuecomment-3442603256
- **related report:** The linked https://github.com/microsoft/vscode-remote-release/issues/11091 contains a video reproducing the command-triggered disconnect with the implicated third-party extension disabled; it was closed only after requesting a separate core report, which became this issue.
- **canonical search:** Searches for Restart Extension Host plus remote reconnect failures found no other open microsoft/vscode issue that owns this exact command behavior; https://github.com/microsoft/vscode/issues/212410 concerns unexpected remote extension-host crashes and is not a canonical duplicate.
