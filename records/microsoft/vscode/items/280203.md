# Issue #280203 — agent doesn't try re-calling failed MCP

[https://github.com/microsoft/vscode/issues/280203](https://github.com/microsoft/vscode/issues/280203)

## Summary

Keep open: current MCP invocation code has limited retry paths, but does not cover general recovery of safe tool calls after a server failure or manual restart. The maintainer endorsed retries restricted to read-only or idempotent tools, and the linked implementation proposal was closed without merging.

## Change summary

Allow the agent to recover a failed MCP invocation by retrying tools marked read-only or idempotent instead of ending the conversation.

## Best solution

Provide bounded recovery for safe MCP tool calls while preserving genuine user cancellation and avoiding automatic replay of potentially non-idempotent operations. Coordinate with the separate connection-failure cancellation issue so recovery does not depend on treating a disconnect as a user pressing Stop.

- **Behavior:**

  > A transient MCP failure should not require a new conversation turn to recover an invocation that is safe to repeat. Recovery is eligible only when the tool explicitly advertises readOnlyHint or idempotentHint, as required by the maintainer. Acceptance must cover recovery after server availability returns, bounded failure when it does not, no replay of unannotated operations, and immediate respect for genuine user cancellation. The recovery window and relationship to manual server restart remain to be agreed.
- **Trace:**

  > McpToolImplementation.invoke in src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts delegates to callWithProgress. McpTool._callWithProgress in src/vs/workbench/contrib/mcp/common/mcpServer.ts currently has special retries for URL elicitation and Error states carrying shouldRetry, but no general retry eligibility check using the tool annotations. The source establishes the missing capability, not an executed reproduction of the original stalled server. The closed, unmerged proposal https://github.com/microsoft/vscode/pull/280215 is prior implementation context rather than a fix. Related https://github.com/microsoft/vscode/issues/336192 owns the narrower distinction between connection failure and user cancellation; coordinate with it without absorbing its separate scope. Preserve existing elicitation behavior and do not expand recovery into arbitrary tool replay or billing changes.
- **Open decisions:**
  - Should recovery wait for a manual server restart within the same turn, automatically attempt reconnection, or support both?
  - What retry limit and recovery window should users observe before the invocation reports a terminal failure?
