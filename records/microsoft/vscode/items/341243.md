# Issue #341243 — [macOS] Ctrl+A, Ctrl+E and the other Ctrl text-editing keys do nothing in an integrated-browser page

[https://github.com/microsoft/vscode/issues/341243](https://github.com/microsoft/vscode/issues/341243)

## Summary

Thanks for the detailed report. The source confirms it: on macOS the preload only allowlists Cmd chords, so Ctrl+letter keys are preventDefault'ed and forwarded to the workbench instead of reaching the page's text fields.

## Change summary

On macOS, Ctrl+A/E/K/F/B/N/P/D/H do nothing in text inputs inside the integrated browser because the preload swallows them.

## Best solution

In the browserView preload, let macOS Ctrl+letter keys (without Cmd/Alt) through to the page when an editable element is focused, so Cocoa text navigation works, while still forwarding them to the workbench otherwise.

## Plan brief

- **Likely files:** `src/vs/platform/browserView/electron-browser/preload-browserView.ts`, `src/vs/workbench/contrib/browserView/electron-browser/webContentsViewHost.ts`
- **Validation:** Manual: on macOS, open a page with <input value="hello world"> in the integrated browser, click mid-text, then press Ctrl+A and Ctrl+E. The cursor should jump to the start and then the end. Workbench shortcuts over non-editable content should still work.
- **Behavior:**

  > On macOS, with an editable element focused in an integrated browser page, Ctrl+letter keys without Cmd or Alt (at minimum A, E, K, F, B, N, P, D, H) reach the page and behave like native Cocoa text editing. Cmd shortcuts and the existing allowlist are unchanged, and workbench keybindings still work when no editable element is focused.
- **Trace:**

  > The keydown handler in preload-browserView.ts builds ctrlCmd from metaKey on Mac, so Ctrl chords miss the nativeCtrlCmdKeybindings allowlist. The handler then calls preventDefault and forwards the event to the workbench (webContentsViewHost.ts handles it). Do not change Windows/Linux behavior or the Cmd allowlist. The uncertainty is the exact key set and how 'editable element focused' is detected.
- **Open decisions:**
  - Pass through only the Cocoa text-system keys (A, E, K, F, B, N, P, D, H), or all Ctrl+letter chords, when an editable element is focused?
  - If a workbench keybinding is bound to one of these chords, should the page's text field take priority?

## Evidence

- **preload:** src/vs/platform/browserView/electron-browser/preload-browserView.ts: on Mac, ctrlCmd is event.metaKey only, so Ctrl+A/E are never in the native allowlist. They fall through to event.preventDefault() and are sent over 'vscode:browserView:keydown'. Traced in current main.
- **related, not duplicate:** https://github.com/microsoft/vscode/issues/320435 covers Ctrl+F/P in a webview, a different surface (webview, not integrated browser). Its open/closed state could not be checked because gh is unauthenticated, so it is cited only as a related issue.
