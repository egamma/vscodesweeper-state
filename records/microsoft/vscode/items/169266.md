# Issue #169266 — Context for compressed Explorer folders always points to child

[https://github.com/microsoft/vscode/issues/169266](https://github.com/microsoft/vscode/issues/169266)

## Summary

The bug remains in current main: a context menu on an individual segment of a compressed Explorer path forwards that segment to commands, but evaluates resource context keys against the compressed node's last child. The issue should remain open as the canonical report and is bounded enough for implementation.

## Change summary

Explorer context-menu when clauses receive the child resource instead of the specific folder segment clicked within a compressed folder path.

## Best solution

Make the Explorer's resource context keys, command target, and compressed-navigation target consistently represent the folder segment the user clicked, while preserving current multi-selection behavior. Cover both parent and child segments with an Explorer context-menu regression test.

## Evidence

- **source reproduction:** In src/vs/workbench/contrib/files/browser/views/explorerView.ts, onContextMenu updates the compressed navigation controller from the clicked label and derives menuActionOptions.arg from compressedControllers[0].current.resource, but calls setContextKeys(stat); stat is the compressed tree element rather than the controller's current clicked segment.
- **inconsistent resource contexts:** setContextKeys in src/vs/workbench/contrib/files/browser/views/explorerView.ts passes stat.resource to ResourceContextKey, so resource, resourcePath, resourceFilename, and related when-clause keys continue to describe the child even when the compressed controller points at the parent.
- **test gap:** The existing context-menu test 'keeps the compressed-folder navigation target when replacing the selection' in src/vs/workbench/contrib/files/test/browser/explorerView.test.ts verifies commandTargets and menuTarget for the parent segment, but does not assert the ResourceContextKey values used to evaluate menu when clauses.
- **canonical status:** https://github.com/microsoft/vscode/issues/187792 was closed by a maintainer as a duplicate of this issue after reproducing the compressed-folder rename symptom on 1.81 Insiders. https://github.com/microsoft/vscode/issues/188571 is a younger related report and was also closed after being linked back here, so neither can replace this older canonical issue.
