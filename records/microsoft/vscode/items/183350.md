# Issue #183350 — Show outputs below cells during interactive sessions

[https://github.com/microsoft/vscode/issues/183350](https://github.com/microsoft/vscode/issues/183350)

## Summary

Keep this accepted feature request open: current interactive-window settings do not place execution results beneath cells in a Python source editor. The request has 23 upvotes, and the older editor-widget/API issues address enabling infrastructure rather than delivering this complete workflow.

## Change summary

Optionally display Jupyter execution outputs beneath their originating cells in a .py editor instead of requiring a separate Interactive Window.

## Best solution

Define an opt-in source-editor output experience with the Jupyter and editor owners, preserving the existing Interactive Window workflow. Establish the supported rendering contract and output lifecycle before implementation; a generic editor-inset API alone does not deliver the requested integration.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/interactive/browser/interactive.contribution.ts`, `src/vs/workbench/contrib/interactive/browser/interactiveEditor.ts`, `src/vscode-dts/vscode.proposed.editorInsets.d.ts`
- **Validation:** The plan should end with an executable UI scenario using a .py file containing two # %% cells producing text and a plot: execute both, rerun the first, and verify that inline-mode results remain attached to their source cells without switching to a separate editor. Verify that disabling the mode preserves the existing Interactive Window workflow; include an explicit acceptance check for the chosen source-edit lifecycle.
- **Behavior:**

  > Users working in a .py file can opt into seeing Jupyter cell results beneath the originating source cells, without converting the file to .ipynb. Running another cell must not sever the visible association between earlier results and their source. The experience must accommodate text and rich results, and preserve the existing Interactive Window workflow when the mode is disabled. Acceptance checks must cover multiple cells, reexecution, and the maintainer-selected behavior when source cells are edited or removed.
- **Trace:**

  > InteractiveEditor in src/vs/workbench/contrib/interactive/browser/interactiveEditor.ts builds a separate notebook-backed execution surface. The registrations in src/vs/workbench/contrib/interactive/browser/interactive.contribution.ts configure that surface rather than inserting output into the originating text editor. src/vscode-dts/vscode.proposed.editorInsets.d.ts contains createWebviewTextEditorInset, but this is proposed rendering infrastructure, not Jupyter execution/output integration. https://github.com/microsoft/vscode/issues/3220 and https://github.com/microsoft/vscode/issues/85682 are relevant infrastructure discussions; neither should be assumed to deliver this product behavior. The trace stops at the source-editor rendering and Jupyter integration boundary: execution ownership, supported API use, and source-to-output lifecycle remain to be designed. Keep notebook-file behavior and the default Interactive Window experience unchanged.
- **Open decisions:**
  - When inline output is enabled, does it replace Interactive Window output for that execution, or mirror output in both surfaces?
  - When a source cell is edited, moved, or deleted, should its existing output follow it, remain marked as stale, or be cleared?
  - Is the initial supported contract a Jupyter-specific source-editor mode, or a general extension-facing rich-output capability that Jupyter adopts?
