# Issue #275727 — Make it easier for Playwright to write to a Monaco editor

[https://github.com/microsoft/vscode/issues/275727](https://github.com/microsoft/vscode/issues/275727)

## Summary

Team-authored, maintainer-discussed request for a Monaco-level affordance that lets Playwright/LLM-driven DOM automation write into (and read from) the editor; nothing on current main provides it, so it stays open — the remaining question is which surface (exposed `type` command, edit-context hook, or a DOM-level affordance) the editor should offer.

## Change summary

Make it possible for Playwright-style DOM automation to reliably type into a Monaco editor without per-area workarounds.

## Best solution

Add a deliberate automation affordance at the editor layer (src/vs/editor/browser/controller) — e.g. a discoverable DOM-visible input target or a documented `type`-style entry point — so generic Playwright/MCP automation works against any Monaco instance instead of needing a bespoke MCP tool per surface.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/editContext/editContext.ts`, `src/vs/editor/browser/controller/editContext/native`, `src/vs/editor/browser/controller/editContext/textArea`, `test/mcp/src/automationTools/editor.ts`
- **Validation:** A Playwright-driven check that types a string into a plain Monaco editor using only the generic automation affordance (no editor-specific MCP tool) and asserts the model content matches, plus the same against a non-editor Monaco surface such as the Settings search or chat input.
- **Behavior:**

  > Generic DOM automation (Playwright, Playwright MCP, an LLM driving the DOM) can write text into any Monaco instance in VS Code — editors, Settings search, Extensions search, chat input — and ideally read its content back, without bespoke per-surface tooling or heavy prompt instructions. The obvious target an automation tool discovers in the DOM should either accept the text correctly or lead it to the supported path. Acceptance: a Playwright script that targets the editor the way a naive automation tool would, types a multi-line string, and sees it land in the editor model; existing typing, IME, screen-reader and EditContext behavior for real users is unchanged.
- **Trace:**

  > Editor input today goes through the controllers in src/vs/editor/browser/controller/editContext (`native` EditContext path and the `textArea` fallback); `rg -i 'playwright|automation' src/vs/editor` shows no automation-facing affordance at all, which is why automation that writes to the inner textarea fails or behaves inconsistently. The current mitigation is per-area MCP tooling — test/mcp/src/automationTools/editor.ts (`vscode_automation_editor_type_text`, annotated "Playwright had trouble typing in monaco") and notebook.ts — which does not generalize to Monaco instances without a dedicated tool. In the thread, alexdima proposes exposing commands (`executeCommand('type', …)`) and hediet asks whether EditContext makes this easier or harder; the author notes a JS-only entry point is not discoverable for an LLM. Boundary: do not regress real input handling — IME composition, screen-reader/accessibility behavior, clipboard, and the EditContext/textarea split must keep working, and any affordance must not become a security or input-spoofing surface in normal use. Related: https://github.com/microsoft/vscode/issues/265592 and https://github.com/microsoft/vscode-engineering/issues/1612. Uncertainty starts at which surface is offered and whether it is always on.
- **Open decisions:**
  - Which automation surface does Monaco expose: a documented command entry point (`type`), an EditContext/DOM element that generic automation naturally finds and writes to correctly, or both?
  - Is the affordance always present in the shipped product, or gated behind a flag/test build — i.e. is this a supported public contract for third-party automation of Monaco, or VS Code-internal test infrastructure only?
  - Does the scope include reading editor content back through the same affordance, or is writing the only requirement for now?

## Evidence
