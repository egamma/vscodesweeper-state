# Issue #275727 — Make it easier for Playwright to write to a Monaco editor

[https://github.com/microsoft/vscode/issues/275727](https://github.com/microsoft/vscode/issues/275727)

## Summary

This remains a real Monaco automation gap: current main still uses a dedicated test-driver path because ordinary Playwright typing is unreliable, and that path does not provide the general, discoverable Monaco-layer contract requested here. The team-authored Backlog request should remain open while editor and engineering maintainers choose that contract.

## Change summary

Provide a reliable and discoverable way for Playwright automation to read from and write to Monaco editors and Monaco-backed input controls.

## Best solution

Define a supported Monaco automation contract that works across code editors and Monaco-backed inputs, including EditContext, selection, reading, and multiline writing, without requiring an agent to infer private DOM details or surface-specific MCP tools.

## Plan brief

- **Likely files:** `src/vs/workbench/services/driver/browser/driver.ts`, `src/vs/workbench/services/driver/common/driver.ts`, `src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts`, `test/automation/src/editor.ts`, `test/mcp/src/automationTools/editor.ts`, `test/mcp/src/automationTools/windows.ts`
- **Validation:** Add an automation scenario that uses the chosen public Playwright-facing contract to enter and read multiline text in both a normal code editor and a Monaco-backed workbench input with EditContext enabled, without invoking a surface-specific editor MCP tool.
- **Behavior:**

  > Playwright automation can identify a Monaco editing surface and reliably read and write its contents without knowing whether it uses a textarea or EditContext. The behavior works for both full code editors and Monaco-backed workbench inputs, supports multiline text and selection, and is discoverable enough for an agent using ordinary automation tools. Existing keyboard input, IME/EditContext behavior, and user-facing editor semantics remain unchanged.
- **Trace:**

  > Current automation splits generic Playwright typing in test/mcp/src/automationTools/windows.ts from Monaco-specific typing in test/mcp/src/automationTools/editor.ts. The latter calls `Editor.waitForTypeInEditor` in test/automation/src/editor.ts, which selects the internal edit-context element and delegates to `Driver.typeInEditor` in src/vs/workbench/services/driver/browser/driver.ts. That driver synthesizes `TextUpdateEvent` for EditContext or mutates a textarea directly, and the higher-level helper rejects multiline input. This confirms a working private test workaround but not the general Monaco-layer automation surface requested by https://github.com/microsoft/vscode/issues/275727. The boundary is automation support: normal editor input, accessibility, IME, and clipboard semantics must not be changed merely to accommodate Playwright.
- **Open decisions:**
  - Should the supported automation contract be exposed through DOM/EditContext semantics, Monaco commands, or a dedicated test-driver API?
  - Which operations must be first-class beyond writing: reading model text, selection, replacement, multiline input, and submission?
  - Should every Monaco-backed workbench input expose the same contract automatically, or should consumers opt in?

## Evidence

- **current workaround:** test/mcp/src/automationTools/editor.ts exposes the surface-specific `vscode_automation_editor_type_text` tool and explicitly says it is critical because Playwright has trouble typing in Monaco; it targets an editor by filename rather than establishing a general Monaco DOM contract.
- **specialized driver path:** src/vs/workbench/services/driver/browser/driver.ts implements `typeInEditor` by directly dispatching a `TextUpdateEvent` to an EditContext or mutating a textarea and dispatching `input`; test/automation/src/editor.ts routes editor typing through that private driver path and rejects multiline text.
