# Issue #75017 — Save Side Bar layouts per Workspace

[https://github.com/microsoft/vscode/issues/75017](https://github.com/microsoft/vscode/issues/75017)

## Summary

Keep open: current main remembers the primary sidebar width per profile, not per workspace, so the requested independent widths remain unsupported. The request has 42 upvotes, and no verified older canonical owns the same workspace-switching behavior.

## Change summary

Remember and restore a distinct Explorer sidebar width for each workspace when switching between projects.

## Best solution

Support workspace-specific primary sidebar width restoration in the workbench layout persistence path. Decide whether this replaces profile-wide persistence by default or is opt-in; independent widths for individual viewlets and automatic filename-based sizing are separate enhancements.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/layout.ts`, `src/vs/workbench/browser/workbench.contribution.ts`
- **Validation:** In one profile, open existing workspaces A and B in the same window. Resize the primary sidebar to two clearly different widths, switch repeatedly between A and B, and reload each workspace; verify that each restores its own width within normal layout constraints. Repeat with the sidebar hidden before leaving a workspace and with left/right placement. If opt-in, verify that disabling the option preserves existing profile-wide behavior.
- **Behavior:**

  > Users switching between workspaces with different filename lengths should not have to repeatedly resize the Explorer sidebar. Each participating workspace should retain its last chosen primary sidebar width and restore it when reopened, including after a window reload. Hidden-sidebar state should not discard the last visible width, and normal minimum-size and window-size constraints still apply. Acceptance is that two workspaces sharing one profile restore distinct widths without one overwriting the other's preference.
- **Trace:**

  > In src/vs/workbench/browser/layout.ts, LayoutStateKeys.SIDEBAR_SIZE declares profile-scoped persistence, while Layout's onWillSaveState handler captures the current or cached visible width. LayoutStateModel.load/loadKeyFromStorage restores that profile-scoped value, and Layout.createGridDescriptor uses it for the primary sidebar node. This establishes that width persistence already exists but its scope does not provide the requested workspace independence; no execution was performed. Preserve sidebar visibility, left/right placement, existing layout constraints, and unrelated panel/secondary-sidebar sizing. The per-viewlet-width request at https://github.com/microsoft/vscode/issues/158603 is related but distinct and newer. The unresolved product boundary is whether workspace-specific persistence becomes the default or an opt-in; shareable settings-file serialization is not required by the central request.
- **Open decisions:**
  - Should workspace-specific primary sidebar width persistence replace the current profile-wide behavior by default, or be an opt-in that preserves the existing default?

## Evidence

The issue has 42 community upvotes and is accepted into Backlog.
- **Current persistence scope:** src/vs/workbench/browser/layout.ts:2879 declares LayoutStateKeys.SIDEBAR_SIZE as 'sideBar.size' with StorageScope.PROFILE. These paths do not retain independent widths for workspaces sharing a profile.
