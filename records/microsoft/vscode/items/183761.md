# Issue #183761 — can't define keybinding for "prtsc"

[https://github.com/microsoft/vscode/issues/183761](https://github.com/microsoft/vscode/issues/183761)

## Summary

Keep open: current recording and dispatch paths still do not handle the keyup-only PrintScreen event identified by the maintainer. The older matching report is closed without a fix, so it is not a valid duplicate target.

## Change summary

PrintScreen cannot be recorded or used as a VS Code keybinding on the reported Windows configuration.

## Best solution

Support recording, resolving, and invoking PrintScreen bindings consistently when Windows delivers only a keyup event, without changing ordinary key dispatch or intercepting an unbound system screenshot shortcut. Investigate the elevated-window Snipping Tool observation separately before treating it as the same defect.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/preferences/browser/keybindingWidgets.ts`, `src/vs/workbench/services/keybinding/browser/keybindingService.ts`, `src/vs/base/common/keyCodes.ts`, `src/vs/workbench/services/keybinding/common/windowsKeyboardMapper.ts`
- **Validation:** On Windows, record PrintScreen in Keyboard Shortcuts, save a binding to a harmless command, and verify that one press invokes it exactly once. Repeat with a synthetic keyup-only event in focused recording/dispatch tests; verify ordinary keydown bindings and modifier-only chords remain unchanged. Separately compare unbound Snipping Tool activation with normal and elevated VS Code windows.
- **Behavior:**

  > On the reported Windows configuration, pressing PrintScreen does not appear in the shortcut recorder or keyboard troubleshooting output. A delivered keyup-only PrintScreen press should be recordable and usable as a binding, and a configured command should run exactly once per press. Ordinary shortcuts and modifier-only chords must retain their behavior. An unbound PrintScreen key must not acquire new suppression of the operating system screenshot action.
- **Trace:**

  > The maintainer identified keyup-only PrintScreen delivery in https://github.com/microsoft/vscode/issues/183761#issuecomment-1568200589. KeybindingsSearchWidget.startRecordingKeys() in src/vs/workbench/contrib/preferences/browser/keybindingWidgets.ts listens only for KEY_DOWN; _registerKeyListeners() in src/vs/workbench/services/keybinding/browser/keybindingService.ts reserves KEY_UP for hold-mode reset and single-modifier dispatch. src/vs/base/common/keyCodes.ts also represents PrintScreen as KeyCode.Unknown, so this is not established as a recorder-only change. The remaining investigation is how native Windows events resolve through WindowsKeyboardMapper and how support can remain consistent across recording and invocation without broad keyup dispatch changes. The elevated-window observation at https://github.com/microsoft/vscode/issues/183761#issuecomment-2187445194 concerns an OS shortcut and must not be assumed to have the same cause.

## Evidence

- **Maintainer diagnosis and accepted work:** https://github.com/microsoft/vscode/issues/183761#issuecomment-1568200589 acknowledges the problem, promises to address it, and identifies that PrintScreen sends only a keyup event. The reporter also confirmed that upgrading did not resolve it: https://github.com/microsoft/vscode/issues/183761#issuecomment-1567964358.
- **Recording path still excludes keyup:** src/vs/workbench/contrib/preferences/browser/keybindingWidgets.ts:73-80, KeybindingsSearchWidget.startRecordingKeys(), registers keyboard recording only for KEY_DOWN. A PrintScreen press delivering only KEY_UP therefore cannot reach _onKeyDown() or printKeybinding().
- **Dispatch and troubleshooting match the symptom:** src/vs/workbench/services/keybinding/browser/keybindingService.ts:274-305, _registerKeyListeners(), logs received keyboard events and dispatches standard bindings in the KEY_DOWN listener. KEY_UP only resets hold mode and calls _singleModifierDispatch(), explaining why the diagnosed PrintScreen event is neither logged there nor dispatched as an ordinary binding.
- **Key representation also needs investigation:** src/vs/base/common/keyCodes.ts:573 maps ScanCode.PrintScreen to KeyCode.Unknown with an empty label and no native virtual-key mapping. Recording alone is therefore not enough to establish usable Windows PrintScreen bindings.
- **Canonical search:** GitHub searches for PrintScreen, "Print Screen", and prtsc found the older same-symptom report https://github.com/microsoft/vscode/issues/133273. It is closed after an unanswered information request, not a landed fix; its closure comment is https://github.com/microsoft/vscode/issues/133273#issuecomment-957351926. No qualifying older open canonical was identified.
- **Different observation in later discussion:** https://github.com/microsoft/vscode/issues/183761#issuecomment-2187445194 reports Windows Snipping Tool failing only while VS Code runs as administrator, explicitly without trying to define a VS Code binding. This is useful environment evidence, but does not establish that system-shortcut suppression and keybinding recording share a cause.
