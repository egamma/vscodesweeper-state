# Issue #336588 — Session-in-progress quit dialog should identify and link to the active session

[https://github.com/microsoft/vscode/issues/336588](https://github.com/microsoft/vscode/issues/336588)

## Summary

Verified against current main: the shutdown confirmation in chatLifecycle.ts is a generic message with no session identity or reveal action, and the veto is issued per-window with no cross-window consolidation, matching the report exactly.

## Change summary

The 'session in progress' quit/reload confirmation dialog should name the active session and offer a way to open it, and ideally consolidate to one prompt across windows.

## Best solution

Extend confirmSessionShutdown (src/vs/workbench/contrib/chat/electron-browser/chatLifecycle.ts) to accept the in-progress session(s) already available in chat.contribution.ts's shouldVetoShutdown, surface the session title/workspace in the dialog detail, and wire a dialog action to open/reveal that session; the multi-window single-prompt consolidation is a separate, more architectural piece a maintainer should scope explicitly.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/electron-browser/chatLifecycle.ts`, `src/vs/workbench/contrib/chat/electron-browser/chat.contribution.ts`, `src/vs/sessions/contrib/providers/agentHost/electron-browser/localAgentHostLifecycle.contribution.ts`
- **Validation:** A unit test in chatLifecycle.test.ts asserting confirmSessionShutdown's dialog detail includes a session's title/workspace when passed a session, and (if implemented) that a dialog action opens/reveals that session.
- **Behavior:**

  > When a shutdown/reload/close is about to discard an in-progress session, the confirmation dialog should name the specific session(s) at risk (title and workspace/repository) and offer an action to open or reveal it, instead of a generic 'A session is in progress' message. If multiple windows would each prompt, ideally the user sees one consolidated confirmation. Acceptance: existing shouldWarnForSessionShutdown/confirmSessionShutdown tests still pass, plus a new test confirming the dialog surfaces session identity.
- **Trace:**

  > confirmSessionShutdown (src/vs/workbench/contrib/chat/electron-browser/chatLifecycle.ts:20) builds message/detail purely from ShutdownReason; the caller in chat.contribution.ts:182-211 already has the specific IAgentSession objects from agentSessionsService.model.sessions (used in shouldWarnForSessionShutdown) but discards that context before calling confirmSessionShutdown. The boundary: do not change the veto/shutdown control flow itself (onBeforeShutdown, getEffectiveSessionShutdownReason) — only the message content and, optionally, a dialog custom action wired through IDialogService's action support. The multi-window consolidation is a separate, more cross-cutting concern (spans per-window lifecycle contributions in both chat.contribution.ts and sessions/contrib/providers/agentHost/electron-browser/localAgentHostLifecycle.contribution.ts) and should be scoped by a maintainer before deciding if it's in scope for this change.
- **Open decisions:**
  - Should the dialog list all in-progress sessions when there are several, or only the first/most-relevant one?
  - What does 'link to the session' resolve to when the session lives in a different window (Agents window vs. an editor window) — reveal the widget, focus another window, or open a specific chat session view?
  - Is consolidating to a single cross-window confirmation in scope for this change, or a separate follow-up given its architectural reach?
