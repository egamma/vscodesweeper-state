# Issue #225410 — Custom text editors do not handle extension host restarts or crashes which can lead to data loss

[https://github.com/microsoft/vscode/issues/225410](https://github.com/microsoft/vscode/issues/225410)

## Summary

Keep open: planned extension-host restarts now warn for custom text editors, but that partial mitigation does not establish recovery after a crash or an overridden restart. The installed-sample steps suffice to retest the remaining failure, and an open linked PR already proposes part of the recovery.

## Change summary

Prevent custom editors from silently remaining interactive but disconnected and unable to save after their extension host restarts or crashes.

## Best solution

Review the recovery candidate at https://github.com/microsoft/vscode/pull/226069 and ensure the eventual solution also handles dirty documents safely, rather than only reconnecting clean editors. Disconnected editors should either recover their provider connection and unsaved state or clearly prevent unsupported editing while preserving a recovery path.

- **Merged change is explicitly partial:** https://github.com/microsoft/vscode/pull/225985 merged commit https://github.com/microsoft/vscode/commit/2386e2f750564550111d01ecd88f5c5d455ced58. Its diff adds an onWillStop veto to CustomTextEditorModel and changes the custom-document handler to veto restarts rather than attempt saving; it does not reconnect orphaned editors. The PR description explicitly states that editors remain orphaned after restarting.
- **Current source retains the mitigation:** src/vs/workbench/contrib/customEditor/common/customTextEditorModel.ts registers extensionService.onWillStop and vetoes a planned stop. src/vs/workbench/api/browser/mainThreadCustomEditors.ts:664-666 does the same for editable custom documents. These handlers support a restart warning, not proof of recovery from a forcibly terminated host; text-document backing also differs from extension-owned custom-document state.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/226069 is verified OPEN and explicitly references this issue. It proposes reconnecting orphaned, non-dirty webviews when their provider registers again, while leaving dirty-editor recovery for later consideration. The issue should not be treated as completed, and a competing agent implementation is not appropriate.
- **Older related report and prior-review duplicate check:** The reporter suggested https://github.com/microsoft/vscode/issues/184142 in https://github.com/microsoft/vscode/issues/225410#issuecomment-2296878447. That issue is verified OPEN and older, and describes continued editing without working save after extension-host restart. It is closely related, but its original reproduction does not establish coverage of this report's explicit custom-text-editor versus custom-document distinction and forced-crash scenario; no duplicate close is proposed while the directly linked recovery PR remains open.
