# Issue #240243 — Do you trust the authors of the files in this folder? prompt blocks cmd-w from closing window

[https://github.com/microsoft/vscode/issues/240243](https://github.com/microsoft/vscode/issues/240243)

## Summary

Keep open: current source intentionally blocks both command keybindings and Escape while the startup trust prompt is active, leaving no keyboard-only dismissal path. The later Backlog milestone and under-discussion label protect this accepted polish from an as-designed close, while the duplicate report adds accessibility evidence.

## Change summary

Make the startup Workspace Trust prompt keyboard-dismissible or allow the normal macOS window-close shortcut without accidentally granting trust.

## Best solution

Preserve the trust prompt's security boundary while providing a predictable keyboard-only exit, either by closing the window or declining/dismissing into Restricted Mode according to an explicit maintainer decision. The interaction should follow macOS modal conventions and remain consistent with other VS Code dialogs.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/workspace/browser/workspace.contribution.ts`, `src/vs/workbench/browser/parts/dialogs/dialogHandler.ts`, `src/vs/workbench/browser/parts/dialogs/dialog.ts`, `src/vs/base/browser/ui/dialog/dialog.ts`, `src/vs/base/test/browser/ui/dialog/dialog.test.ts`
- **Validation:** Add targeted dialog/workspace-trust coverage for the selected Escape and close-keybinding semantics, run `scripts/test.sh --grep 'Dialog'`, and manually open an untrusted folder on macOS to verify the approved keyboard path without granting trust.
- **Behavior:**

  > When the startup Workspace Trust prompt has focus, a keyboard-only user must be able to leave the blocked state without granting trust. Cmd+W or Cmd+Shift+W and Escape must follow the maintainer-selected modal behavior consistently, while the explicit trust action remains the only path that grants trust. Acceptance includes opening an untrusted folder on macOS, exercising each approved shortcut, and confirming that no dismissal persists trust accidentally.
- **Trace:**

  > WorkspaceTrustUXHandler.doShowModal in src/vs/workbench/contrib/workspace/browser/workspace.contribution.ts creates the startup prompt with `disableCloseAction: true`. Dialog in src/vs/base/browser/ui/dialog/dialog.ts consequently ignores Escape and omits its close action, while BrowserDialogHandler and createWorkbenchDialogOptions in src/vs/workbench/browser/parts/dialogs block close commands outside the modal allowlist. This conclusively explains the reported keyboard trap on current main. The boundary is the startup trust decision: do not weaken explicit trust granting or silently persist trust, and do not change every modal's close semantics unless that broader behavior is deliberately selected. https://github.com/microsoft/vscode/issues/281757 is a later duplicate confirming the same observable behavior with extensions disabled.
- **Open decisions:**
  - Should the normal macOS close shortcut close the entire VS Code window while the Workspace Trust prompt is active, or should this modal continue intercepting it?
  - Should Escape mean continuing in Restricted Mode, abandoning the folder by closing the window, or remain unavailable once another keyboard close path exists?
