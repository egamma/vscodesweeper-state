# Issue #256277 — Allow extensions to de-dupe identical MCP servers

[https://github.com/microsoft/vscode/issues/256277](https://github.com/microsoft/vscode/issues/256277)

## Summary

Keep open: current main partially handles same-name MCP collisions, but it still lacks a cross-source identity model for recognizing identical servers and a complete management UX. This is also a team-authored Backlog item whose maintainers explicitly chose a platform-owned solution.

## Change summary

Let VS Code recognize identical MCP servers contributed through different sources so duplicate instances can be suppressed or managed.

## Best solution

Give MCP definitions a platform-level identity that survives different contribution sources, group genuinely identical servers in the MCP management surface, and let the user see their origins and select or disable the active copy without conflating distinct same-name servers.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/common/mcpTypes.ts`, `src/vs/workbench/contrib/mcp/common/mcpService.ts`, `src/vs/workbench/contrib/mcp/browser/mcpCommands.ts`, `src/vs/workbench/contrib/mcp/browser/mcpServersView.ts`, `src/vs/workbench/contrib/mcp/test/common/mcpRegistry.test.ts`, `src/vscode-dts/vscode.proposed.mcpServerDefinitions.d.ts`
- **Validation:** Extend the MCP registry collision tests with two differently sourced definitions representing the same stable server identity and two distinct servers sharing a label; run scripts/test.sh --grep "Server Label Collision Enablement" and verify only the identical pair is grouped while the same-label distinct pair remains independently usable.
- **Behavior:**

  > When the same MCP server is contributed by an extension and another installation source, VS Code recognizes the duplicate, runs only the selected copy, and shows every origin in the MCP management experience. The user can inspect and change which copy is enabled. Distinct server instances that happen to share a display label remain independently usable. Existing tool-name collision handling remains unchanged.
- **Trace:**

  > Extension-provided definitions flow through ExtHostMcpService.registerMcpConfigurationProvider in src/vs/workbench/api/common/extHostMcp.ts, where IDs are source-scoped as extension ID plus label. McpCollisionEnablementModel in src/vs/workbench/contrib/mcp/common/mcpService.ts currently groups definitions solely by lower-cased label and uses collection order to choose the enabled entry. The proposed lm.mcpServerDefinitions API publishes all definitions, but McpServerDefinition has no stable cross-source identity or provenance contract. MCP list and action UI lives primarily in src/vs/workbench/contrib/mcp/browser/mcpCommands.ts and mcpServersView.ts. Keep this work separate from tool-name prefixing tracked by https://github.com/microsoft/vscode/issues/244644 and from the narrower plugin-management display defect at https://github.com/microsoft/vscode/issues/316362.
- **Open decisions:**
  - What stable public identity determines that definitions from different sources represent the same MCP server, without collapsing distinct configured instances that share a label or endpoint?
  - When an identical-server group is discovered, should VS Code automatically select by source priority with an override, or require the user to choose before either copy is enabled?
  - Should extensions receive stable identity and provenance through the proposed definition-query API, or should duplicate resolution remain entirely platform-owned with extensions observing only their own contribution state?
