[https://github.com/microsoft/vscode/issues/237074](https://github.com/microsoft/vscode/issues/237074)

## Summary

Keep this as the canonical request for notebook-cell protection and execution-control metadata. Current source preserves metadata but does not implement the requested protection modes; related reports were explicitly consolidated here, and 38 upvotes support retaining it.

## Change summary

Honor notebook-cell metadata for edit/delete protection, frozen or skipped execution, and persistent collapsed state.

## Best solution

Design notebook-cell protection with an explicit metadata contract, preserving ordinary cell behavior and notebook-format compatibility. Standard editable/deletable support is a sensible first stage; execution-control semantics and portable folding persistence need maintainer agreement before subsequent stages.

## Plan brief

- **Likely files:** `extensions/ipynb/src/deserializers.ts`, `extensions/ipynb/src/serializers.ts`, `src/vs/workbench/contrib/notebook/common/notebookCommon.ts`, `src/vs/workbench/contrib/notebook/browser/viewModel/cellEditorOptions.ts`, `src/vs/workbench/contrib/notebook/browser/contrib/cellCommands/cellCommands.ts`, `src/vs/workbench/contrib/notebook/browser/services/notebookExecutionServiceImpl.ts`, `src/vs/workbench/contrib/notebook/browser/controller/foldingController.ts`
- **Validation:** Use an .ipynb fixture containing ordinary, editable:false, deletable:false, and agreed execution-control cells. Verify editing and deletion protection independently, Run All versus individual execution, unchanged ordinary-cell execution, and metadata round-trip after save/reopen. Add focused coverage in extensions/ipynb/src/test/serializers.test.ts and src/vs/workbench/contrib/notebook/test/browser/notebookExecutionService.test.ts; verify portable header folding in a fresh workspace when that stage is included.
- **Behavior:**

  > Notebook cells should honor explicit metadata controlling whether their content can be edited, whether the cell can be deleted, and whether execution is permitted. The author's normal, read-only, and frozen modes must have distinct, documented behavior; bulk-only execution skipping is a separate requested behavior whose relationship to freezing needs agreement. Cells without these flags retain existing behavior, and saving/reopening must preserve the agreed metadata. Portable collapsed-state support remains within the issue's consolidated scope but can be delivered separately.
- **Trace:**

  > The ipynb deserializer preserves original cell metadata under cellMetadata.metadata, and the serializer writes it back; preservation is already present, but enforcement is not established. BaseCellEditorOptions derives readOnly from the notebook editor, while NotebookExecutionService.executeNotebookCells selects code cells and dispatches eligible handles without inspecting freeze metadata. FoldingController stores folding through view-state mementos rather than portable notebook metadata. https://github.com/microsoft/vscode/issues/158715, https://github.com/microsoft/vscode-jupyter/issues/8709, and https://github.com/microsoft/vscode/issues/284633 were consolidated into this issue, making it the existing owner of the broader work. The unresolved boundary is how format-specific metadata becomes a generic notebook protection contract, and whether execution flags prohibit every invocation or only bulk execution. Preserve existing whole-notebook readonly behavior, metadata round-tripping, kernel selection, and ordinary-cell execution; this is accidental-edit protection, not a security boundary.
- **Open decisions:**
  - Should frozen cells reject both individual and bulk execution, with a separate bulk-only skip mode, or should one execution-control mode cover both requests?
  - Should cell protection use a notebook-format-independent provider/API contract, or directly recognize Jupyter metadata conventions in the core notebook editor?
  - Which interoperable metadata convention should represent portable Markdown-header folding, and should writing that state be opt-in or automatic?

## Evidence

- **Existing capability check:** src/vs/workbench/contrib/notebook/browser/viewModel/cellEditorOptions.ts computes readOnly from this.notebookEditor.isReadOnly, not per-cell editable metadata. NotebookCellMetadata in src/vs/workbench/contrib/notebook/common/notebookCommon.ts is an arbitrary dictionary. Searches of notebook configuration and commands found no freeze or metadata-driven protection setting that covers the requested modes.
- **Metadata preservation is not enforcement:** extensions/ipynb/src/deserializers.ts:getNotebookCellMetadata copies original cell metadata into cellMetadata.metadata; extensions/ipynb/src/serializers.ts writes that metadata back. Preservation alone does not make editable:false or deletable:false effective in the notebook editor.
- **Execution gap:** src/vs/workbench/contrib/notebook/browser/services/notebookExecutionServiceImpl.ts:executeNotebookCells filters cells by CellKind.Code, existing execution state, and kernel-supported language before calling executeNotebookCellsRequest. The inspected path does not check run_control.frozen or distinguish metadata-based skip-execution modes.
- **Canonical protection request:** https://github.com/microsoft/vscode/issues/158715 was closed as a duplicate of this issue by a maintainer: https://github.com/microsoft/vscode/issues/158715#issuecomment-2646652845. Its earlier out-of-scope decision concerned only readonly/deletable support and was superseded by that consolidation; it is neither an open canonical nor evidence that the broader request is completed.
- **Jupyter ownership evidence:** https://github.com/microsoft/vscode-jupyter/issues/8709 records that honoring editable/deletable metadata was on longer-term plans and was closed into this issue: https://github.com/microsoft/vscode-jupyter/issues/8709#issuecomment-1221728508. This supports retaining the core notebook request rather than moving it back to Jupyter.

The latest commenter offers staged implementation, but the supplied discussion contains no maintainer approval resolving those different behaviors.
