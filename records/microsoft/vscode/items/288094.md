# Issue #288094 — When Copilot Chat Errors, it should RETRY instead of haltung

[https://github.com/microsoft/vscode/issues/288094](https://github.com/microsoft/vscode/issues/288094)

## Summary

Current main only automatically retries failed agent requests in auto-approve and Autopilot modes, so the broader request remains partially unmet. A maintainer already indicated retry work was underway; classify and route this for a decision on retry behavior in ordinary Agent mode.

## Change summary

Automatically retry recoverable Copilot Chat model errors instead of stopping the agent flow and requiring a manual retry.

## Best solution

Define a bounded automatic-recovery policy for transient model and network failures across the intended agent modes, while preserving immediate stops for cancellation, quota, rate-limit, refusal, and other non-recoverable outcomes. Coordinate retry-count configuration with https://github.com/microsoft/vscode/issues/313485.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/intents/node/toolCallingLoop.ts`, `extensions/copilot/src/extension/intents/test/node/toolCallingLoopAutopilot.spec.ts`, `extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts`, `extensions/copilot/src/extension/prompt/node/test/chatMLFetcherRetry.spec.ts`
- **Validation:** Extend the ToolCallingLoop retry tests to cover the chosen ordinary-Agent-mode behavior, retry limits, and terminal error classes, then run the targeted Vitest suites for toolCallingLoopAutopilot.spec.ts and chatMLFetcherRetry.spec.ts.
- **Behavior:**

  > When an agentic Copilot Chat request fails for a transient model or network reason, the session should recover automatically without requiring the user to click Retry. Recovery must be visible, bounded, and must not retry cancellation or terminal outcomes such as quota exhaustion, rate limiting, refusal, or an invalid request unless explicitly included by policy. Successful and manually cancelled turns must remain unchanged.
- **Trace:**

  > ToolCallingLoop.shouldAutoRetry in extensions/copilot/src/extension/intents/node/toolCallingLoop.ts currently permits up to three retries only for `autoApprove` and `autopilot`; the main loop performs the retry at lines 1496-1514. The adjacent Vitest suite explicitly confirms that an ordinary permission level does not retry. ChatMLFetcher has a separate opt-in transport retry path for configured server and network failures, so planning must avoid overlapping retry loops or duplicate user-visible progress. Keep cancellation, quota, rate-limit, off-topic, refusal, and inaccessible-vision-attachment handling outside automatic retries unless a maintainer deliberately changes that contract. The later https://github.com/microsoft/vscode/issues/313485 concerns configuration of the retry count rather than whether ordinary Agent sessions recover automatically.
- **Open decisions:**
  - Should automatic recovery cover ordinary Agent mode as well as auto-approve and Autopilot, or remain limited to unattended permission modes?
  - Which model-error classes are considered transient enough to retry, and what retry limit/backoff should users observe before the turn stops?
