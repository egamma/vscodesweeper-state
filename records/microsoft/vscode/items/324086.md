# Issue #324086 — Python notebook cell editor context menu is rendered behind the bottom panel on Windows

[https://github.com/microsoft/vscode/issues/324086](https://github.com/microsoft/vscode/issues/324086)

## Summary

Real, still-open stacking bug: the notebook code-cell editor's context menu uses a shadow-root attached at the editor's own DOM node (contextmenu.ts's `domForShadowRoot`), which is positioned `fixed` relative to whatever ancestor establishes a new containing block inside the notebook cell/list DOM — unlike a plain `.py` editor, whose editor DOM node sits at the top editor-group level and isn't clipped by the panel. A second reporter confirms the same class of issue for the Activity Bar too, suggesting the stacking-context root cause is broader than just the panel.

## Change summary

On Windows, right-clicking inside a Python notebook cell's code editor shows a context menu whose lower half (Cut/Copy/Paste) is rendered behind the bottom panel, while the cell-level (non-editor) context menu and a plain .py file's editor menu are unaffected.

## Best solution

Notebook/editor-core owners should trace why the shadow-root context menu container (see domForShadowRoot in src/vs/editor/contrib/contextmenu/browser/contextmenu.ts and ContextViewHandler.showContextView's FIXED_SHADOW path in src/vs/platform/contextview/browser/contextViewService.ts) ends up clipped/under the panel specifically for notebook cell editors — most likely an ancestor in the notebook cell list/webview backlayer establishing a new stacking/containing-block context that a plain text editor doesn't have — and either avoid the shadow-root attachment for notebook cells or raise its z-index/containing-block appropriately.

## Evidence

- **shadow-root menu attachment:** src/vs/editor/contrib/contextmenu/browser/contextmenu.ts:220 passes `domForShadowRoot: useShadowDOM ? this._editor.getOverflowWidgetsDomNode() ?? this._editor.getDomNode() : undefined` — for notebook code cells (which, unlike diff editors, don't override `overflowWidgetsDomNode`), the shadow root host is attached inside the cell's own editor DOM node rather than a top-level layout container.
- **FIXED_SHADOW positioning:** src/vs/platform/contextview/browser/contextViewService.ts:33 selects `ContextViewDOMPosition.FIXED_SHADOW` whenever a shadow-root container is supplied and isn't the top-level layout container — a `position: fixed` element is only clipped by the panel if some ancestor in the notebook cell/list DOM establishes a new containing block, which a plain `.py` editor's DOM ancestry apparently does not.
- **prior related report closed without a real fix:** https://github.com/microsoft/vscode/issues/184455 (diff-view variant) was closed in Dec 2024 as 'no longer reproduces', but only verified informally and not on Windows; this report and its Windows reproduction show the underlying issue persists there.
- **second reporter, different surface:** Comment from GiuseppePiscopo (2026-08-05) reports the same clipping behavior against the main Activity Bar, suggesting a shared root cause rather than something panel-specific.
