# Issue #27972 — Include support for system-wide mandatory/default settings

[https://github.com/microsoft/vscode/issues/27972](https://github.com/microsoft/vscode/issues/27972)

## Summary

Keep open for system-wide defaults that users and workspaces can override. Mandatory policy support addresses only part of the request; a maintainer explicitly reopened this issue to preserve the defaults requirement, which remains absent from the inspected configuration path.

## Change summary

Allow administrators to supply system-wide mandatory settings and overridable defaults for all users, with overridable defaults remaining the outstanding requirement.

## Best solution

Provide an administrator-deployable defaults source beneath explicit user and workspace settings while preserving mandatory policy precedence. Settle whether defaults remain a live configuration layer or only seed new users before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/configuration/common/configurations.ts`, `src/vs/platform/configuration/common/configurationModels.ts`, `src/vs/platform/environment/common/environmentService.ts`, `src/vs/workbench/services/configuration/browser/configuration.ts`, `src/vs/workbench/services/configuration/browser/configurationService.ts`, `src/vs/workbench/services/configuration/test/browser/configurationService.test.ts`
- **Validation:** Add targeted configuration-service tests showing the same administrator default applies to two independent user profiles, explicit user/workspace values override it, and mandatory policy still wins. After choosing persistence semantics, verify either that system-default changes propagate without rewriting user settings or that seeding occurs only on first launch and preserves existing settings.
- **Behavior:**

  > Administrators can deploy default settings once for a shared VS Code installation, and separate users receive those defaults without individually configuring their profiles. Users and workspaces can override defaults; mandatory policy values remain enforced. The original request permits first-launch seeding, whereas later discussion asks for a persistent lower-priority configuration layer. Acceptance must cover independent users, override precedence, existing user settings, and the agreed behavior when administrator defaults change.
- **Trace:**

  > DefaultConfiguration in src/vs/platform/configuration/common/configurations.ts obtains registered schema defaults; its workbench subclass in src/vs/workbench/services/configuration/browser/configuration.ts adds browser-host defaults and cached registered overrides. WorkspaceService in src/vs/workbench/services/configuration/browser/configurationService.ts constructs user configuration from the current profile. Configuration in src/vs/platform/configuration/common/configurationModels.ts merges the existing configuration layers and applies mandatory policies above them; the inspected path has no administrator-loaded desktop defaults source. Preserve existing policy enforcement and user/workspace precedence, and exclude system-wide extension installation from this work. https://github.com/microsoft/vscode/issues/147756#issuecomment-2768883131 explicitly preserves this issue for defaults; the newer related requests are https://github.com/microsoft/vscode/issues/314393 and https://github.com/microsoft/vscode/issues/312764. The unresolved boundary is the defaults persistence and deployment contract, not whether mandatory policy should become overridable.
- **Open decisions:**
  - Should administrator defaults remain a live lower-priority configuration layer, or only seed user settings on first launch?
  - What administrator-facing deployment contract should supply defaults across supported desktop platforms: conventional system files, an explicitly configured file location, OS management channels, or a combination?
