# Issue #72529 — Support restart of remote EH to avoid window reloads

[https://github.com/microsoft/vscode/issues/72529](https://github.com/microsoft/vscode/issues/72529)

## Summary

This remains a valid extension-host feature request: changing folders in a remote workspace can still require a full window reload, disrupting terminals and unsaved work. The Backlog milestone permits merits-based review, but there is no verified implementation, canonical duplicate, or scope decision supporting closure.

## Change summary

Support restarting local and remote extension hosts after workspace-folder changes without reloading the entire window.

## Best solution

Enable coordinated restart or reconfiguration of local and remote extension hosts when workspace folders change, preserving the workbench and terminal processes; close the remaining extension-host API gaps identified by the maintainer before removing the reload fallback.

## Plan brief

- **Likely files:** `src/vs/workbench/services/workspaces/electron-sandbox/workspaceEditingService.ts`, `src/vs/workbench/contrib/relauncher/browser/relauncher.contribution.ts`, `src/vs/workbench/services/extensions/common/extensionHostManager.ts`
- **Validation:** Add an integration scenario that changes workspace folders while connected remotely and verifies that the workbench window and an existing terminal process remain alive while extension hosts receive the updated workspace state.
- **Behavior:**

  > Adding or removing workspace folders in a remote window should not reload the entire workbench merely to update extension-host state. Existing editors, unsaved buffers, terminals, and long-running tasks must remain intact, while local and remote extensions observe the updated workspace and storage state. Acceptance should cover both adding the first folder and subsequent multi-root folder changes in a remote workspace.
- **Trace:**

  > The issue attributes the reload fallback to the inability to restart or reconfigure an extension host when a remote extension host also exists. The maintainer identified two associated contract gaps: legacy `rootPath` behavior and notification when workspace storage paths change. The relevant path spans workspace editing/relauncher contributions and extension-host lifecycle management; the plan must trace the current equivalents of the historical files before choosing a lifecycle contract. Preserve intentional reloads for global changes that genuinely require a full workbench restart, and do not alter explicit user-initiated reload behavior. Closed symptom reports such as https://github.com/microsoft/vscode/issues/83520 and https://github.com/microsoft/vscode/issues/127106 do not establish that this broader capability is complete.
- **Open decisions:**
  - Should workspace-folder changes restart local and remote extension hosts, or should both hosts remain running and receive enough lifecycle events to update workspace-root and storage-path state?
  - If a full reload remains necessary for an unsupported case, must VS Code warn and allow cancellation before disrupting terminals and unsaved work?
