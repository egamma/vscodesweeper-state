# Issue #72529 — Support restart of remote EH to avoid window reloads

[https://github.com/microsoft/vscode/issues/72529](https://github.com/microsoft/vscode/issues/72529)

## Summary

The requested capability remains missing on current main: changing the first workspace folder under a remote authority still reloads the entire window instead of restarting the extension hosts. The issue remains the established tracker for this remote-workspace lifecycle gap.

## Change summary

Allow remote extension hosts to restart after relevant workspace-folder changes without reloading the VS Code window and disrupting terminals or other workbench state.

## Best solution

Make remote workspace-folder transitions refresh the required extension-host state without reloading the window, while preserving terminals and other renderer-owned state and retaining the existing restart-veto lifecycle.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/relauncher/browser/relauncher.contribution.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/services/extensions/common/remoteExtensionHost.ts`
- **Validation:** In a remote SSH or Dev Container multi-root workspace, run a long-lived integrated-terminal process, change the first workspace folder, and verify that the window does not reload, the terminal process remains attached, workspace APIs reflect the new roots, and remote extensions remain operational.
- **Behavior:**

  > Changing the first folder of a remote workspace must not reload the VS Code window. The remote extension-host state must reflect the updated workspace while integrated terminals and other renderer-owned state remain intact. Existing restart-veto behavior must continue to protect components that cannot safely tolerate an extension-host restart. Acceptance requires exercising the transition in a real remote workspace and confirming both workspace API updates and preservation of a long-running terminal process.
- **Trace:**

  > WorkspaceChangeExtHostRelauncher in src/vs/workbench/contrib/relauncher/browser/relauncher.contribution.ts observes first-root changes. Its remoteAuthority branch calls IHostService.reload(), while the native local branch uses IExtensionService.stopExtensionHosts() and startExtensionHosts(). The extension-host lifecycle is implemented in src/vs/workbench/services/extensions/common/abstractExtensionService.ts, with the remote host implementation in src/vs/workbench/services/extensions/common/remoteExtensionHost.ts. The issue discussion says the workaround originally existed because restarting local and remote extension hosts together was not implemented safely. The boundary is workspace-triggered extension-host lifecycle behavior: terminal processes and unrelated workbench state must not be restarted, and deprecated workspace.rootPath plus workspace-storage-path updates must remain correct. https://github.com/microsoft/vscode/issues/319944 is a narrower local transition report, not a replacement canonical.
- **Open decisions:**
  - Can the existing stop/start extension-host lifecycle safely recreate both local and remote hosts during a remote workspace transition, or does the remote host require a distinct restart protocol?
  - Which extension-host and workspace storage state must be rebuilt so deprecated workspace.rootPath and workspace-storage-path notifications remain correct?
  - How should a restart veto affect a workspace-folder change that has already been applied?
