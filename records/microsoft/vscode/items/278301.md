# Issue #278301 — MCP: Encourage that MCP servers are installed via marketplace

[https://github.com/microsoft/vscode/issues/278301](https://github.com/microsoft/vscode/issues/278301)

## Summary

This team-authored Backlog feature request remains necessary: current main still exposes several distinct installation paths and identity schemes, while the related issue only covers deduplicating Marketplace and extension contributions. The desired Marketplace-first experience needs product design before implementation because extension-provided servers can require dynamic launch behavior that a static Marketplace installation cannot preserve.

## Change summary

Make the MCP Marketplace the preferred installation experience, move non-Marketplace paths behind advanced flows, and give locally configured servers an identifiable stable namespace.

## Best solution

Provide a coherent Marketplace-first installation journey and stable shareable server identities while retaining an advanced path for private, development, discovered, and dynamically extension-provided servers. The design must preserve extension-controlled launch arguments and project-specific SDK selection rather than treating every extension contribution as interchangeable with a static Marketplace package.

- **Behavior:**

  > Installing an MCP server should lead users through one clear Marketplace-first experience. Private, local-development, discovered, and dynamically extension-provided servers must remain available through an understandable advanced path. Server identities used by shared agent files must remain stable and communicate when a server is local, while equivalent Marketplace and extension entries should not appear as confusing duplicates. Extension-provided servers that depend on workspace-specific SDK selection or custom launch arguments must retain that behavior.
- **Trace:**

  > McpAddConfigurationCommand.getServerType() in src/vs/workbench/contrib/mcp/browser/mcpCommandsAddConfiguration.ts independently exposes manual transports, assisted package setup, external discovery, and Marketplace browsing; getServerId() then accepts an origin-independent user ID. The same class’s pickForUrlHandler() installs imported JSON directly without consulting the Marketplace. Identity construction is split across src/vs/workbench/contrib/mcp/common/mcpTypes.ts, common/discovery/extensionMcpDiscovery.ts, and common/discovery/installedMcpServersDiscovery.ts: extensions use extensionPrefixedIdentifier(), while configuration files use provenance-specific collection prefixes. https://github.com/microsoft/vscode/issues/271138 covers only deduplication between extension and Marketplace entries. Preserve dynamic extension providers and their launch semantics; do not collapse them into static Marketplace packages unless equivalence is explicitly established.
- **Open decisions:**
  - Should Marketplace preference be advisory, with advanced installation still directly available, or should non-Marketplace paths require an explicit advanced-mode transition?
  - When an extension contribution and Marketplace entry refer to the same server, which source is presented and enabled when their launch arguments or tool sets differ?
  - What canonical identifier may shared agent files persist across Marketplace, extension, configuration, discovery, workspace, and remote origins, and when should the visible local/ namespace apply?
  - Should import links redirect to a matching Marketplace entry automatically, offer both choices, or continue direct installation when no exact identity match can be proven?
