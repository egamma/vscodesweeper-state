# Issue #278301 — MCP: Encourage that MCP servers are installed via marketplace

[https://github.com/microsoft/vscode/issues/278301](https://github.com/microsoft/vscode/issues/278301)

## Summary

Keep open: marketplace browsing and some import-link redirection already exist, but manual installation remains prominent and server identity still depends on its source. This team-authored Backlog request needs a product decision that preserves the extension-provided capabilities described in the discussion; no qualifying fix or duplicate was established.

## Change summary

Prefer marketplace installation for MCP servers, make advanced installation paths secondary, and distinguish custom server identities to improve sharing of agent files.

## Best solution

Define a marketplace-first installation experience and portable server/tool identity contract without removing extension-controlled SDK selection or tool exclusions. Coordinate duplicate-source handling with https://github.com/microsoft/vscode/issues/271138, which does not cover this request's full installation UX and identity scope.

## Evidence

- **Existing capability is partial:** src/vs/workbench/contrib/mcp/browser/mcpCommandsAddConfiguration.ts:166-248, McpAddConfigurationCommand.getServerType(), presents Command and HTTP installation choices before Browse MCP Servers. src/vs/workbench/contrib/mcp/browser/mcpCommands.ts:1137-1176 still exposes workbench.mcp.addConfiguration through the Command Palette and MCP configuration editor. Marketplace browsing exists, but does not replace or subordinate these entry points as requested.
- **Conditional import redirection:** src/vs/workbench/contrib/mcp/browser/mcpWorkbenchService.ts:959-993, handleMcpInstallUri(), redirects to a verified gallery entry only when the payload includes config.gallery and the gallery is enabled. Other import payloads still open a custom installable server; this is partial coverage, not a complete implementation.
- **Source-specific identity remains:** src/vs/workbench/contrib/mcp/common/discovery/installedMcpServersDiscovery.ts constructs definition IDs as `${collectionId}.${server.name}` and labels them with server.name. ExtensionMcpDiscovery in src/vs/workbench/contrib/mcp/common/discovery/extensionMcpDiscovery.ts separately uses extensionPrefixedIdentifier for extension collections. These paths do not establish the requested universal local/ identity convention.
- **Tool naming has evolved but does not settle installation scope:** src/vs/workbench/contrib/mcp/common/mcpServer.ts:634-639 derives tool prefixes from announced server metadata, falling back to the configured label, through McpPrefixGenerator. This reduces dependence on configuration names in some cases, but does not implement marketplace-first installation or establish equivalence between all installation sources.
- **Discussion identifies compatibility requirements:** The supplied March 25 comment on https://github.com/microsoft/vscode/issues/278301 explains that Dart/Flutter extensions select a workspace-specific SDK, omit servers for unsupported SDK versions, and exclude server tools replaced by VS Code-integrated tools. A static marketplace installation cannot be assumed to preserve those behaviors.
- **Verified related issue is narrower:** https://github.com/microsoft/vscode/issues/271138 is open and predates this report. The maintainer explicitly defines its scope as detecting marketplace/extension duplicates and enabling only one source: https://github.com/microsoft/vscode/issues/271138#issuecomment-3743946224. It does not own the full request to simplify installation entry points and distinguish custom identities, so it is not a qualifying duplicate.
