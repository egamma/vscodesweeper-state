# Issue #241922 — Can't dnd image from built-in preview

[https://github.com/microsoft/vscode/issues/241922](https://github.com/microsoft/vscode/issues/241922)

## Summary

The bug remains source-reproducible on current main: the image preview exposes a generated HTTPS webview-resource URL, which chat treats as an external image URL instead of the underlying workspace file. The existing `bug` classification and Backlog milestone also rule out a judgment close.

## Change summary

Dragging a workspace image from the built-in image preview into chat should create a valid image attachment with a preview instead of submitting an unusable URL and producing a 400 response.

## Best solution

Preserve or recover the underlying workspace resource when an image is dragged from a trusted built-in preview, then resolve it through the normal local image attachment path. The generated webview HTTPS URL must not be sent as though it were a fetchable external image.

## Plan brief

- **Likely files:** `extensions/media-preview/src/imagePreview/index.ts`, `extensions/media-preview/media/imagePreview.js`, `src/vs/workbench/contrib/chat/browser/widget/chatDragAndDrop.ts`, `src/vs/workbench/contrib/webview/common/webview.ts`
- **Validation:** Open a local PNG in the built-in image preview, drag the rendered image into a vision-capable chat, verify that the attachment has an image preview and can be submitted without a 400 response; repeat with a workspace image rendered in Markdown preview and with a genuinely external HTTP image to ensure external URL drag-and-drop remains intact.
- **Behavior:**

  > Dragging a workspace image from the built-in image preview into chat creates the same usable image attachment as adding that file from Explorer: the attachment shows an image preview and reaches a vision-capable model as image data. It must not submit the preview's generated webview URL or produce a 400 response. External web-image drag-and-drop and ordinary file attachment behavior must remain unchanged. The Markdown preview case should also be checked because it can expose the same webview-resource boundary.
- **Trace:**

  > The image preview converts its workspace resource with `Webview.asWebviewUri` in `extensions/media-preview/src/imagePreview/index.ts`; `extensions/media-preview/media/imagePreview.js` assigns that result to the `<img>` without supplying the original resource during drag. In `src/vs/workbench/contrib/chat/browser/widget/chatDragAndDrop.ts`, a URI-list lacking the internal-resource MIME is handled as web content and passed to `ISharedWebContentExtractorService.readImage`. `src/vs/platform/webContentExtractor/node/sharedWebContentExtractorService.ts` performs an ordinary network fetch, while `src/vs/workbench/contrib/webview/common/webview.ts` documents that these generated HTTPS resource URLs are intended to be intercepted by a webview service worker, so the shared process cannot resolve the workspace image. The boundary is trusted built-in preview resources: do not weaken handling of arbitrary external URLs or expose unrelated local paths. The maintainer diagnosis is recorded at https://github.com/microsoft/vscode/issues/241922#issuecomment-2682928641.

## Evidence

- **preview source path:** `extensions/media-preview/src/imagePreview/index.ts` passes `webview.asWebviewUri(resource)` into the preview, while `extensions/media-preview/media/imagePreview.js` assigns that generated URL directly to the draggable `<img>` and installs no drag handler carrying the original workspace URI.
- **chat drop path:** `src/vs/workbench/contrib/chat/browser/widget/chatDragAndDrop.ts` parses `text/uri-list`; without an internal URI payload it routes the generated HTTPS value through `resolveHTMLAttachContext` and `downloadImageAsUint8Array` as an external URL.
- **failed resource boundary:** `src/vs/workbench/contrib/webview/common/webview.ts` constructs webview resource URLs under the hardcoded `*.vscode-resource.vscode-cdn.net` authority for interception inside a webview, but `src/vs/platform/webContentExtractor/node/sharedWebContentExtractorService.ts` uses ordinary `fetch` in the shared process and has no mapping back to the workspace resource.
- **maintainer diagnosis:** The maintainer comment at https://github.com/microsoft/vscode/issues/241922#issuecomment-2682928641 identifies the same mismatch: `text/uri-list` contains an HTTPS-looking link that actually points to a workspace file.
- **no landed fix:** The issue has no linked fixing PR, and current main still contains the producer/consumer mismatch after the later URL drag-and-drop work.
