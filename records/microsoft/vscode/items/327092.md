# Issue #327092 — Git: Clone silently does nothing after previously cloned repository is deleted

[https://github.com/microsoft/vscode/issues/327092](https://github.com/microsoft/vscode/issues/327092)

## Summary

Real bug, already traced and fixed by an open PR: `tryOpenExistingRepository` validates only the cached `workspacePath` (often a surviving parent folder), not the actual clone directory, so recloning after deleting the repo silently no-ops. An open PR references this issue with a fix, so the issue should stay open pending review/merge rather than being closed now.

## Change summary

Git: Clone silently does nothing when re-cloning a repo whose local copy was deleted, because the extension still finds a stale cache entry it treats as valid.

## Best solution

Review and land https://github.com/microsoft/vscode/pull/327198, which validates the actual repository path (not just workspacePath) and prunes stale cache entries before falling through to a real clone; keep the issue open until that PR merges.

## Evidence

- **current code:** extensions/git/src/cloneManager.ts:212-226 `tryOpenExistingRepository` only checks `fs.promises.stat(folder.workspacePath)` per cached entry; if the parent folder or a .code-workspace file still exists (even though the actual git clone directory under it was deleted), the entry is treated as valid and clone silently reuses/opens it instead of re-cloning.
- **fixing PR:** https://github.com/microsoft/vscode/pull/327198 (open, not merged) explicitly says: 'Git: Clone treated a cache hit as valid when only workspacePath still existed... Validate repositoryPath existence instead, prune stale cache entries, and fall through to a normal clone.' It carries 'Fixes #327092' and adds unit tests in extensions/git/src/test/cloneCache.test.ts.
- **corroboration:** Two independent commenters (phoehnel, contributory) confirm the same silent no-op behavior on 1.129.1.
