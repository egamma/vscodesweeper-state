# Issue #327092 — Git: Clone silently does nothing after previously cloned repository is deleted

[https://github.com/microsoft/vscode/issues/327092](https://github.com/microsoft/vscode/issues/327092)

## Summary

Real bug traced in current main, and an open PR already targets it with a closing reference — keep this open and let the linked PR land rather than closing or auto-fixing.

## Change summary

Git: Clone silently no-ops when re-cloning a URL whose local working copy was deleted but a parent folder/workspace path is still on disk.

## Best solution

Land https://github.com/microsoft/vscode/pull/327198, which replaces the workspacePath existence check with a repositoryPath check in extensions/git/src/cloneManager.ts (adding extensions/git/src/cloneCache.ts) so a deleted clone is no longer mistaken for a live one.

## Evidence

- **traced defect on main:** extensions/git/src/cloneManager.ts:213-219 `tryOpenExistingRepository` calls `fs.promises.stat(folder.workspacePath)` to decide whether a cached repo still exists — `workspacePath` can be a surviving parent folder or `.code-workspace` file even after the actual clone directory is deleted, so the repo is wrongly treated as 'existing' and cloning silently no-ops.
- **open fixing PR:** https://github.com/microsoft/vscode/pull/327198 ('git: recloning after deleted local clone no longer silently no-ops') contains 'Fixes #327092' and adds extensions/git/src/cloneCache.ts to validate repositoryPath instead of workspacePath; confirmed via `gh pr view` that cloneCache.ts does not yet exist on main (fix unmerged) and the PR's `mergedAt` is null with checks still in progress.
- **second confirmation:** Commenter phoehnel confirmed reproducing on 1.129.1 and noted there's also no manual re-clone path once a repo is registered in the workspace.
