# Issue #334809 — OS notification "Allow" confirms only one request when multiple confirmations are pending in the same turn

[https://github.com/microsoft/vscode/issues/334809](https://github.com/microsoft/vscode/issues/334809)

## Summary

Confirmed on current main: approving one OS notification action leaves additional confirmations pending without producing another notification. The issue should remain open as a chat notification bug.

## Change summary

Ensure users remain aware of additional confirmation requests after acting on an OS notification for one request.

## Best solution

When multiple approvals are pending, the OS notification flow must not imply that all input has been handled. A maintainer should choose whether that means reopening the session, approving all pending items, or issuing a follow-up notification for the next item.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chatWindowNotifier.ts`, `src/vs/workbench/contrib/chat/test/browser/chatWindowNotifier.test.ts`
- **Validation:** Extend the ChatWindowNotifier browser tests with two simultaneous pending tool confirmations, simulate selecting the OS notification action, and assert that one confirmation cannot leave the other pending without the maintainer-selected follow-up indication or session-opening behavior.
- **Behavior:**

  > When a turn has multiple pending confirmations, acting on its OS notification must not make the session appear fully unblocked while confirmations remain. The user must either be taken to the pending approvals, receive another visible notification, or intentionally approve all pending items. Single-confirmation behavior and question-carousel handling must remain correct.
- **Trace:**

  > ChatWindowNotifier in src/vs/workbench/contrib/chat/browser/chatWindowNotifier.ts observes `model.requestNeedsInput` only for a false-to-true transition. Its `_confirmAllow` method confirms the first waiting tool and returns, while ChatResponseModel and ChatModel continue exposing a truthy pending-input state for the next confirmation through src/vs/workbench/contrib/chat/common/model/chatModel.ts. Consequently no new transition occurs and the notifier does not run again. The existing notifier suite in src/vs/workbench/contrib/chat/test/browser/chatWindowNotifier.test.ts lacks a multi-confirmation action case. Keep the boundary to notification behavior: do not change the ordering or semantics of confirmations in the chat transcript.
- **Open decisions:**
  - For multiple pending confirmations, should the OS action open the session, approve all pending items, or approve one item and surface the next notification?

## Evidence

- **source reproduction:** src/vs/workbench/contrib/chat/browser/chatWindowNotifier.ts:96-106 only calls `_notifyIfNeeded` when `requestNeedsInput` changes from absent to present. Confirming one of several pending tools leaves that observable truthy, so no second notification is scheduled.
- **single-item action:** src/vs/workbench/contrib/chat/browser/chatWindowNotifier.ts:169-170 and 233-246 handle the OS `Allow` action by confirming the first waiting tool invocation and immediately returning; `_confirmAllow` deliberately stops after one item.

- **test gap:** src/vs/workbench/contrib/chat/test/browser/chatWindowNotifier.test.ts covers initial needs-input notification but has no case for acting on a notification while two tool confirmations are pending.
