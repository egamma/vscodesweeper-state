# Issue #131006 — Ensure that scm.focus command works in all cases

[https://github.com/microsoft/vscode/issues/131006](https://github.com/microsoft/vscode/issues/131006)

## Summary

Keep open: current source still restores focus to the SCM tree after a resource was focused, rather than consistently focusing the commit message input. This issue remains the relevant tracking item; the related reports do not establish a completed fix or an eligible duplicate canonical.

## Change summary

Make workbench.scm.focus reliably focus the commit message input after previously focusing or opening a changed file.

## Best solution

Deliver consistent commit-input focus for the reported command workflow in the SCM view, preserving explicit preserveFocus requests and ordinary resource-list navigation. Establish a focused regression check before changing the shared view-focus behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/scm/browser/scmViewPane.ts`, `src/vs/workbench/contrib/scm/browser/scm.contribution.ts`, `src/vs/workbench/services/views/browser/viewsService.ts`
- **Validation:** In a repository with changes, focus and open a resource from SCM, invoke workbench.scm.focus from the resulting diff editor, and type a commit message: typing must enter the commit input rather than activate tree navigation. Repeat with SCM initially hidden and already visible, and verify that invoking the command with preserveFocus: true does not move editor focus. The plan should establish an automated regression check for the retained-resource-focus case.
- **Behavior:**

  > After opening a changed file from the SCM view, invoking workbench.scm.focus must put keyboard focus in the commit message input so typing immediately enters a message. The result must not depend on whether a changed resource previously had focus or whether the view is already visible. Explicit preserveFocus requests must continue to avoid moving focus. Ordinary resource-list keyboard navigation must remain unchanged.
- **Trace:**

  > The generated FocusViewAction in src/vs/workbench/services/views/browser/viewsService.ts invokes openView for workbench.scm, with focus enabled unless preserveFocus is requested. SCMViewPane.focus() in src/vs/workbench/contrib/scm/browser/scmViewPane.ts checks tree.getFocus().length and only focuses a rendered input widget when the tree has no focused element; otherwise it calls tree.domFocus(), explaining the reported retained-resource case. The separate focusPreviousInput/focusNextInput commands in scm.contribution.ts use SCMViewPane.focusInput(), which explicitly reveals and focuses the input, but this does not change the original command. The accepted command-focused direction is documented at https://github.com/microsoft/vscode/issues/119904#issuecomment-900399753. Preserve ordinary list navigation, explicit preserveFocus behavior and existing input-cycling semantics; do not reopen the discarded API proposal. The defect is source-confirmed, but the uncertainty is how to establish an executable regression harness for view focus and account for other callers of the shared focus method.
