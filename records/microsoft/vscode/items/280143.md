# Issue #280143 — Give extension the ability to know where the current debug session is stopped

[https://github.com/microsoft/vscode/issues/280143](https://github.com/microsoft/vscode/issues/280143)

## Summary

Keep this open for debug API-owner discussion: querying DAP already provides stack locations, but exposing the editor's known stopped location without another adapter request remains unresolved. The final PHP/Xdebug objection is not answered by the JS-adapter approach.

## Change summary

Let language extensions obtain the active debug frame's source location to make scope-aware evaluatable-expression decisions.

## Best solution

Resolve whether the debug extension API should expose the active frame's existing source location, while preserving the distinction between expression discovery and adapter evaluation. Assess the PHP/Xdebug case explicitly rather than assuming adapters can all perform the scope analysis available to the JavaScript debugger.

## Evidence

- **Existing capability and remaining gap:** src/vscode-dts/vscode.d.ts:16769 exposes DebugSession.customRequest, and :17343 exposes debug.activeStackItem. However, DebugStackFrame at :17266 exposes only session, threadId and frameId, not a source URI or position. MainThreadDebugService's focus notification in src/vs/workbench/api/browser/mainThreadDebugService.ts:91-110 likewise sends identifiers without the location.
- **Provider contract:** src/vscode-dts/vscode.d.ts:3193-3206 still defines provideEvaluatableExpression(document, position, token) without stopped-location context. InlineValueContext at :3295-3306 does expose frameId and stoppedLocation, confirming the distinction described in https://github.com/microsoft/vscode/issues/280143.
- **Discussion remains unresolved:** In https://github.com/microsoft/vscode/issues/280143, the maintainer's December 9-10 comments recommend DebugSession.customRequest and adapter-side evaluation. The reporter accepts that querying stackTrace works but objects to repeating the request; the final December 10 comment explains that PHP/Xdebug lacks the scope information used by the JavaScript-adapter solution. This is not an explicit maintainer rejection of the remaining API request.
- **Existing hover evaluation support:** src/vs/workbench/contrib/debug/browser/debugHover.ts:493-510 passes the hovered expression's source, line and column into adapter evaluation with the focused stack frame. This supports the maintainer's adapter-side alternative but does not supply the stopped source location to EvaluatableExpressionProvider.
- **DAP workaround clarification:** src/vs/workbench/contrib/debug/common/debugProtocol.d.ts:1135-1141 defines stackTrace.startFrame as a frame index, not a frame ID. An extension using the suggested workaround must request the active thread's stack and match the returned frame ID; directly substituting activeStackItem.frameId as startFrame is not generally correct.

The supplied candidate https://github.com/microsoft/vscode/issues/197287 concerns contributed variable visualizations, not exposing execution-location context, so it does not meet the re-review duplicate bar.
