- **Validation:** Use deferred model-resolution and diff-computation promises to verify that the editor exposes loading feedback and a prepared leading diff while a later item remains pending, then appends later content in source order. Preserve the existing stale-resolution and disposal tests. Manually open a multi-diff with deliberately slow later resources and verify early content, loading feedback, and stable scroll/focus before all resources finish.
- **Behavior:**

  > Opening a multi-diff editor should provide immediate loading feedback rather than an unexplained empty interval. Prepared leading diffs should become visible without waiting for every later resource or diff computation, with remaining content appended in stable file order and loading feedback retained until completion. Loading must not repeatedly replace already visible content or disrupt restored scroll position, focus, and collapsed state. Acceptance should use controlled pending promises to establish early publication, not an unverified fixed latency threshold.
- **Trace:**

  > MultiDiffEditor.setInput awaits MultiDiffEditorInput.getViewModel before attaching the view model to the widget. MultiDiffEditorInput._createModel resolves both sides of every resource and waits for Promise.all before publishing documents and returning; its view-model factory then performs a further bounded readiness wait. MultiDiffEditorViewModel aggregates item creation and initial diff readiness before publishing items, so current initial publication remains batch-oriented. The widget already renders a Loading... placeholder and handles restored state and automatic first-change navigation, which must remain correct under incremental updates. Existing input tests use deferred resource resolutions and verify that replaced, removed, or disposed items cannot publish stale results. The maintainer's progressive-display direction is settled at https://github.com/microsoft/vscode/issues/199345#issuecomment-1829917438; the unresolved engineering work is the asynchronous publication and lifetime contract across these stages. Coordinate with https://github.com/microsoft/vscode/issues/240181, but do not expand this request into a mandatory full lazy-text-model redesign.

- **Initial model-resolution barrier:** src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts:100-111 awaits _createModel() before constructing the view model, then waits for diff readiness with a 1000 ms raceTimeout. In _createModel(), updateDocuments awaits Promise.all(docsPromises), and the method awaits that update before returning. A slow resource therefore holds back initial document publication.
- **Diff-publication barrier:** src/vs/editor/browser/widget/multiDiffEditor/multiDiffEditorViewModel.ts:96-116 aggregates all item-creation promises and all waitForInitialDiffOr1s promises before exposing the resulting items. Each initial diff wait races computation against a 1000 ms timeout. This bounds an individual diff wait but does not progressively publish prepared initial items.
