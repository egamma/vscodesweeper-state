# Issue #339762 — Automations blue badge should serve only when something needs attention rather than when in-progress?

[https://github.com/microsoft/vscode/issues/339762](https://github.com/microsoft/vscode/issues/339762)

## Summary

New, same-day UX suggestion for the Agents Window Automations badge: distinguish in-progress (animated) from needs-attention (solid blue) and use separate colors for needs-input/error states. No upvotes or maintainer input yet, but it's a reasonable, concrete design critique worth keeping open for design review.

## Change summary

Make the Automations badge visually distinguish 'run in progress' from 'automation needs attention', with distinct colors for needs-input (orange) and errored (red) states.

## Best solution

A maintainer/designer should decide the exact badge-state-to-color/animation mapping (in-progress vs needs-input vs error vs completed) for the Automations view indicator in src/vs/sessions/contrib/sessions/browser, since SessionStatus already distinguishes InProgress/NeedsInput/Error but the current badge doesn't visually differentiate them the way the reporter wants.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/sessions/electron-browser/sessionsApplicationBadge.ts`, `src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts`, `src/vs/sessions/contrib/sessions/browser/automationsNewBadge.ts`
- **Validation:** A visual/manual check or component-fixture screenshot test confirming the badge animates or changes color distinctly for InProgress vs NeedsInput vs Error vs completed states.
- **Behavior:**

  > The Automations badge should communicate run state at a glance: an in-progress run shows a distinct (e.g. animated) indicator, while a completed run awaiting review, a run needing input, and an errored run each show a visually distinct badge (e.g. solid blue / orange / red) that persists until the user addresses it. Acceptance: opening the Automations view while a run is still in progress should not look identical to 'needs your attention'.
- **Trace:**

  > SessionStatus (src/vs/sessions/services/sessions/common/session.ts) already models InProgress, NeedsInput, and Error distinctly, and SessionsApplicationBadge (src/vs/sessions/contrib/sessions/electron-browser/sessionsApplicationBadge.ts) currently derives a single numeric badge from configurable reasons (inputNeeded/unread/ciFailing) without mapping to distinct colors/animations. The Automations view's own badge elements (session-section-new-badge in sessionsList.ts, automationsNewBadge.ts) are a separate 'new automation available' indicator and not necessarily the element in the report's screenshot. Where uncertainty starts: which specific badge/indicator the screenshot refers to, and what the exact visual language (colors, animation) should be across states — that needs a maintainer/designer decision before any implementation.
- **Open decisions:**
  - Which specific badge is this (OS/dock application badge, activity-bar view badge, or an in-view per-run indicator), and does the fix apply to one or all of them?
  - What exact color/animation should represent each SessionStatus (InProgress, NeedsInput, Error, completed-needs-review)?
  - Should an in-progress run contribute to the attention badge count at all, or only once it transitions to a state needing the user?

## Evidence

- **status model exists:** SessionStatus already has InProgress, NeedsInput, and Error variants (src/vs/sessions/services/sessions/common/session.ts), so the underlying signal to distinguish states is available.
- **badge logic found:** src/vs/sessions/contrib/sessions/electron-browser/sessionsApplicationBadge.ts computes a single count/color badge from inputNeeded/unread/ciFailing options without an in-progress-vs-attention visual distinction; the Automations view's own badge rendering (sessionsList.ts, automationsNewBadge.ts) is a separate 'new automation' indicator, not a per-run status badge, so the exact UI element in the screenshot could not be fully traced without image access.
