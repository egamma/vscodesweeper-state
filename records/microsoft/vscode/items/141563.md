# Issue #141563 — AltGr keypress makes me press Home twice in Terminal for effect.

[https://github.com/microsoft/vscode/issues/141563](https://github.com/microsoft/vscode/issues/141563)

## Summary

Keep open: an independent reporter confirmed that AltGr causes the next non-character terminal keypress to be swallowed across multiple shells. The current input path was inspected, but neither a fix covering this exact trigger nor an eligible duplicate canonical was established.

## Change summary

After AltGr input on Windows, the terminal ignores the first Home, End, arrow, or other non-character keypress.

## Best solution

Restore reliable first-key handling after AltGr without changing character composition or terminal shortcut behavior. First reproduce on current Windows builds and distinguish VS Code keybinding interception from xterm.js input-state handling.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/terminal/browser/terminalInstance.ts`, `src/vs/workbench/contrib/terminal/browser/xterm/xtermTerminal.ts`
- **Validation:** On Windows with Norwegian or Swedish keyboard layout and extensions disabled, enter text in cmd and WSL terminals, type an AltGr-produced character, release all modifiers, then press Home or Left once. Verify that the first press moves the cursor. Repeat with End, Enter, and Backspace, and with spaces between the AltGr character and the tested key; compare with the same keys without preceding AltGr input.
- **Behavior:**

  > The reported failure occurs after AltGr input: the first subsequent non-character keypress does nothing, while the second works. Each Home, End, arrow, Enter, or Backspace keypress should take effect normally once AltGr is released. Spaces between the AltGr character and the next control key must not preserve a swallowed-key condition. Ordinary AltGr character insertion and intentional terminal shortcuts must remain unchanged.
- **Trace:**

  > TerminalInstance installs attachCustomKeyEventHandler in src/vs/workbench/contrib/terminal/browser/terminalInstance.ts, where StandardKeyboardEvent and softDispatch determine whether xterm receives an event. The same class forwards xterm onData through _handleOnData to the process manager; XtermTerminal in src/vs/workbench/contrib/terminal/browser/xterm/xtermTerminal.ts constructs the underlying terminal. The independent reproduction at https://github.com/microsoft/vscode/issues/141563#issuecomment-1024435466 establishes the historical failure, but the inspected current source does not conclusively identify the dropping stage. The related quote-composition fix at https://github.com/xtermjs/xterm.js/pull/3574 suggests checking dead-key state, without proving it is this defect or that this report is fixed. Diagnosis should first capture the current Windows event sequence and determine whether the event is filtered before xterm or lost inside its input handling. Preserve existing composition, shortcut, and shell-forwarding semantics; do not generalize this into left/right modifier support.
