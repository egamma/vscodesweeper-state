# Issue #255520 — Manage button not available when tabbing.

[https://github.com/microsoft/vscode/issues/255520](https://github.com/microsoft/vscode/issues/255520)

## Summary

The accessibility defect remains on current main: focusing an MCP server row does not make its action bar keyboard-focusable, unlike the established Extensions list behavior. The Manage action therefore remains unreachable through the expected Tab sequence.

## Change summary

Make the MCP server Manage button reachable by Tab after keyboard focus enters an MCP server row.

## Best solution

Bring MCP server rows in line with the Extensions list keyboard model: when a row has focus, Tab must enter its enabled actions, including Manage, while leaving unrelated rows' actions outside the tab order.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/browser/mcpServersView.ts`
- **Validation:** With an installed MCP server, focus its row using keyboard navigation, press Tab, and verify focus reaches every enabled row action including Manage; move to another row and verify actions from the previous row are no longer tabbable. Repeat the equivalent flow in Installed Extensions to confirm behavior remains consistent.
- **Behavior:**

  > When keyboard focus is on an installed MCP server row, pressing Tab reaches that row's enabled actions, including Manage, in logical order. Actions belonging to rows without focus remain outside the tab order. Arrow-key row navigation and opening a server from the row must remain unchanged.
- **Trace:**

  > McpServerRenderer in src/vs/workbench/contrib/mcp/browser/mcpServersView.ts creates each row ActionBar and permanently disables its focusability with `setFocusable(false)`. The analogous Renderer in src/vs/workbench/contrib/extensions/browser/extensionsList.ts toggles action-bar focusability through IExtensionsViewState focus and blur events, while McpServersListView currently has no equivalent connection between `WorkbenchPagedList.onDidChangeFocus` and rendered row actions. This directly accounts for the reporter-observable difference. Keep the change scoped to MCP list-row keyboard focus; do not alter editor action bars, context-menu contents, row opening, or Extensions-list behavior. The remaining uncertainty is validation infrastructure: there is no existing MCP view renderer test covering DOM focus, so the session should decide whether to introduce a focused browser test or use a documented manual keyboard check.

## Evidence

- **current source:** src/vs/workbench/contrib/mcp/browser/mcpServersView.ts:440-470 creates the MCP row ActionBar, calls `actionbar.setFocusable(false)`, and never changes it when the row gains or loses focus.
- **working reference:** src/vs/workbench/contrib/extensions/browser/extensionsList.ts:202-215 listens for the corresponding extension row's focus and blur events and toggles `data.actionbar.setFocusable(true/false)`, which explains why the reporter can reach Manage for installed extensions but not MCP servers.
- **established keyboard behavior:** https://github.com/microsoft/vscode/issues/51496#issuecomment-435147137 documents the expected Extensions-list interaction: once an item has focus, Tab moves focus to that item's actionable controls.
- **reporter confirmation:** The reporter confirmed that Manage is keyboard-accessible for installed extensions, isolating the discrepancy to the MCP view rather than a general keyboard or extension-environment problem.
