# Issue #155597 — Allow users to choose which editor to use for editing variable binary data

[https://github.com/microsoft/vscode/issues/155597](https://github.com/microsoft/vscode/issues/155597)

## Summary

This remains a valid, strongly supported backlog request: VS Code still needs a stable extensibility contract for selecting a debug memory viewer, and the related implementation PR was closed without merging. The existing open investigation should settle the extension point before implementation resumes.

## Change summary

Allow users or debug extensions to choose a memory-view editor instead of always opening binary variable data with the Microsoft Hex Editor.

## Best solution

Resolve the public-contract design in https://github.com/microsoft/vscode/issues/197287, then expose a stable debug-memory visualization extension point that lets compatible viewers participate without coupling them to VS Code's private memory URI contract.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/variablesView.ts`, `src/vs/workbench/contrib/debug/common/debug.ts`
- **Validation:** Use a debug adapter exposing a variable with a memoryReference, install two compatible memory viewers, invoke View Binary Data, select the non-Hex-Editor viewer, and verify it receives the correct memory context while the existing default flow continues to work.
- **Behavior:**

  > When binary data is available for a debug variable, users can open it with a compatible memory-view extension rather than being forced into the Microsoft Hex Editor. The selected viewer receives sufficient stable context to read, refresh, and edit memory for the active debug session. Existing users who make no choice retain a working default viewer flow.
- **Trace:**

  > The issue points to VariablesView's binary-data action in src/vs/workbench/contrib/debug/browser/variablesView.ts, which historically targeted the Hex Editor through a private memory-resource contract. Maintainers confirmed that this contract was intentionally not public because its shape may change for non-contiguous memory. The closed implementation attempt https://github.com/microsoft/vscode/pull/197458 explored settings-based selection, while https://github.com/microsoft/vscode/issues/197287 remains open for the broader debug visualization extension-point design. Keep the scope to debug memory-view selection and its public contract; do not fold unrelated DAP paging, refresh, or inaccessible-memory behavior into this request.
- **Open decisions:**
  - Should viewer selection be a user-configured default, an invocation-time picker, or an extension-contributed priority/default contract?
  - Does VS Code own the debug-memory data model and lifecycle, or may a selected viewer own reads, writes, refresh, and session binding through a stable context contract?
  - What compatibility behavior should apply when no compatible viewer is installed or a previously selected viewer is unavailable?
