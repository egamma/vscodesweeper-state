# Issue #197157 — Renaming folders in the explorer go blank before getting renamed

[https://github.com/microsoft/vscode/issues/197157](https://github.com/microsoft/vscode/issues/197157)

## Summary

The blank Explorer row remains source-reproducible on current main: submitting the rename removes the input immediately, while the item remains in editable rendering mode until the asynchronous file operation finishes. The older related issue reports a different observable failure, so it does not meet the stronger duplicate bar for this re-reviewed item.

## Change summary

Keep a folder's Explorer row visibly represented while an asynchronous rename is processing, including when the operation is slow or rejected.

## Best solution

Define a non-blank pending state for Explorer renames and retain it until the bulk edit settles, then restore the normal item or failure state. The interaction should prevent duplicate submission and make an explicit decision about progress and cancellation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/browser/fileActions.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Add a browser unit test using a deferred `IEditableData.onFinish` promise: after submitting a rename, assert the Explorer row remains visibly represented while the promise is pending, then assert the normal row returns when it settles; cover both successful and rejected operations.
- **Behavior:**

  > Submitting a folder rename must never leave a blank row while the file operation is pending. The pending state must remain visibly associated with the folder, must not permit duplicate submissions, and must transition back to the normal item when the operation succeeds or fails. Acceptance should cover a deliberately delayed rename and a rejected rename.
- **Trace:**

  > FilesRenderer.renderInputBox in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts synchronously hides, disposes, and removes the input before invoking the Promise-returning `IEditableData.onFinish`. renameHandler in src/vs/workbench/contrib/files/browser/fileActions.ts keeps the Explorer item editable while awaiting `applyBulkEdit`, so renderElement continues suppressing the ordinary file label and the row is blank. This confirms the current-main source path described in https://github.com/microsoft/vscode/issues/197157#issuecomment-2056951462. Keep the scope to rename-pending presentation and interaction; do not alter file-operation semantics or attempt to solve the underlying Windows file-lock behavior tracked by https://github.com/microsoft/vscode/issues/152633. The uncertainty begins with whether pending renames should expose progress and cancellation or use a disabled, non-cancellable input state.
- **Open decisions:**
  - While a rename is pending, should the rename input remain visible but disabled, or should the row switch to a distinct progress presentation?
  - Should an in-progress rename be cancellable from the Explorer row, or remain non-cancellable while preventing further input?

## Evidence

- **current source path:** On current main, src/vs/workbench/contrib/files/browser/views/explorerViewer.ts:1086-1092 synchronously hides and removes the input label before calling the Promise-returning `editableData.onFinish`.
