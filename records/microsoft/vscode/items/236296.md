# Issue #236296 — Strip characters from `"onEnterRules"` string

[https://github.com/microsoft/vscode/issues/236296](https://github.com/microsoft/vscode/issues/236296)

## Summary

Keep open: current source still couples character stripping to configured brackets and exposes no token-context condition for onEnterRules. This reopened Backlog request has maintainer interest and additional extension-author demand; the verified related issues do not own its full scope.

## Change summary

Allow language authors to control character stripping or token-context eligibility when evaluating onEnterRules.

## Best solution

Define a backward-compatible language-configuration capability that distinguishes YAML block-scalar headers from lookalike text inside strings and comments without declaring non-bracket characters as brackets. Settle the public contract for token-context filtering versus configurable preprocessing before implementation.

- **Behavior:**

  > Language authors need to distinguish genuine YAML block-scalar headers from matching text inside strings and comments when Enter rules run. In the supplied sample, pressing Enter after a genuine block-scalar indentation indicator should apply the nine-space action, but matching |9 or >9 text in scalar contents or comments should not. The distinction must remain possible with blank preceding lines and without registering | as a bracket. Existing language configurations must retain their behavior unless they opt into the new capability.
- **Trace:**

  > getEnterAction in src/vs/editor/common/languages/enterAction.ts obtains tokenized context through IndentationContextProcessor, then passes only processed text to OnEnterSupport.onEnter. IndentationLineProcessor.getProcessedTokens removes configured brackets from String, Comment and RegEx tokens; it has no independent character-stripping configuration. Both the editor OnEnterRule interface and the workbench serialized rule interface expose only text regex conditions and an action. Existing processor tests provide tokenized-model helpers and verify bracket removal, while onEnter.test.ts exercises regex rule evaluation. The trace establishes the missing capability, not a live reproduction with the reporter's prerelease YAML grammar. Keep default bracket behavior, existing comment rules, and Enter latency intact; https://github.com/microsoft/vscode/issues/247477#issuecomment-2939753234 explicitly raises compatibility concerns. Coordinate with https://github.com/microsoft/vscode/issues/164469 for shared token-context needs without treating its different string-splitting request as a duplicate.
- **Open decisions:**
  - Should the public capability provide token-context eligibility conditions, configurable token-specific character stripping, or both?
  - If token-context eligibility is exposed, does it describe the token at the cursor or the token containing the text matched by each rule condition? YAML headers and scalar contents can both involve string tokens, so this distinction affects whether the requested case is expressible.
