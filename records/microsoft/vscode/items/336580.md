# Issue #336580 — Transition GitHub and Microsoft authentication to host-owned auth

[https://github.com/microsoft/vscode/issues/336580](https://github.com/microsoft/vscode/issues/336580)

## Summary

Keep open: GitHub and Microsoft authentication still follows the client-brokered token path. The linked merged PR explicitly leaves this migration separate, and the host-owned protocol proposal remains open.

## Change summary

Move agent GitHub and Microsoft account discovery, sign-in, sign-out, credential refresh, and migration into the host while retaining client UI delegation and sandbox-compatible token brokering.

## Best solution

Establish the opt-in host-owned authentication contract with the protocol owners, then migrate the agent authentication lifecycle across the host and workbench. Preserve client-brokered authentication for hosts that require it and leave non-agent authentication consumers unaffected.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentHostAuthenticationService.ts`, `src/vs/platform/agentHost/common/agent.ts`, `src/vs/platform/agentHost/common/agentService.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts`
- **Validation:** The plan should establish executable host/client authentication tests covering account discovery, interactive sign-in with delegated browser UI, sign-out, refresh after credential expiry, and host restart without an extension host. Include migration from existing client-owned accounts and a capability-disabled sandboxed host that continues using authenticate without regression.
- **Behavior:**

  > An agent host supporting host-owned authentication owns its GitHub and Microsoft accounts and credential lifecycle rather than requiring VS Code to obtain and continuously forward tokens. Interactive flows may delegate browser/UI operations to VS Code, but account availability and refresh must not depend on the extension host remaining alive. Existing agent users need a defined migration experience, and sandboxed or capability-disabled hosts must retain the client-brokered path. Acceptance must cover both providers, host restart, expiration, sign-out, and compatibility with existing clients and hosts.
- **Trace:**

  > The current workbench path in src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts resolves AuthenticationSession objects through IAuthenticationService and passes their credentials through forwardAuthenticationToken; forceAuthenticationInteractively invokes the existing client setup flow. AgentHostAuthenticationService in src/vs/platform/agentHost/node/agentHostAuthenticationService.ts caches and replays supplied credentials, so host-side caching alone does not provide the requested ownership or renewal. The shared interfaces are in common/agent.ts and common/agentService.ts; the trace has not enumerated every provider, transport, and account-UI consumer required for migration. https://github.com/microsoft/agent-host-protocol/pull/404 remains an open docs-only proposal, so its commands and account channel are not yet an adopted contract. https://github.com/microsoft/vscode/pull/339251 explicitly excludes this migration. Preserve the existing brokered path and unrelated editor authentication consumers; planning must settle migration and sign-out semantics before implementation.
- **Open decisions:**
  - When enabling host-owned authentication for an existing client-owned account, should the user authenticate again or explicitly authorize migration of existing credentials?
  - Should signing out of an agent-host account affect only that host, or also sign out the corresponding VS Code account used by unrelated editor features?
