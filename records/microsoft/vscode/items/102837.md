# Issue #102837 — Allow extensions to contribute to peek widget title navigation action item

[https://github.com/microsoft/vscode/issues/102837](https://github.com/microsoft/vscode/issues/102837)

## Summary

Keep this accepted Backlog request open: extensions still cannot contribute title actions to the references/location peek widget. Existing editor-title and specialized peek menus do not cover it, and the related requests examined are not duplicate canonicals.

## Change summary

Allow extensions to contribute actions to location/reference peek titles, receiving the location currently shown as command context.

## Best solution

Provide a supported menu contribution surface for references/location peek title actions, with a documented current-location argument contract. Keep specialized comment, testing, call-hierarchy, and diff widgets outside the initial scope unless their owners explicitly agree to a shared contract.

- **Behavior:**

  > Extensions can contribute visible, keyboard-accessible actions to the title of a location/reference peek opened through editor.action.peekLocations or editor.action.showReferences. Invoking an action supplies the current shown location according to a documented public contract, including after switching references. Existing close and navigation actions continue to work, and unrelated editor-tab or specialized peek menus are unchanged.
- **Trace:**

  > editor.action.showReferences aliases editor.action.peekLocations in src/vs/editor/contrib/gotoSymbol/browser/goToCommands.ts. ReferenceWidget in src/vs/editor/contrib/gotoSymbol/browser/peek/referencesWidget.ts inherits PeekViewWidget._fillHead, which constructs a direct ActionBar with a close action in src/vs/editor/contrib/peekView/browser/peekView.ts. ReferenceWidget tracks the revealed reference separately from tree focus through _revealReference and _getFocusedReference; these internal concepts must not be assumed to define the public command argument. The extension menu registry in src/vs/workbench/services/actions/common/menusExtensionPoint.ts has no matching contribution point. The reporter settled the desired context as the current shown location, but the public argument representation and contribution-point scope remain to be designed. Preserve existing navigation and specialized peek behavior; https://github.com/microsoft/vscode/issues/175351 concerns a different editor-context submenu and is not the owner of this work.
- **Open decisions:**
  - What public command argument contract represents the current shown location: a Location-shaped object or separate URI and range arguments?
  - Should the initial contribution point cover only reference/location peeks opened by these commands, or also other peek widget types with different context contracts?
