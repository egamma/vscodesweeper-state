# Issue #264581 — Modifying the location of any test (TestController API) causes all other test in the file to snap back to their original locations ignoring unsaved changes

[https://github.com/microsoft/vscode/issues/264581](https://github.com/microsoft/vscode/issues/264581)

## Summary

Keep open for a testing-owner decision on partial location synchronization: current source still resets unrelated tracked positions when one test range is published. Although the maintainer originally described this as intentional, the later bug classification prevents an as-designed cleanup close.

## Change summary

Allow providers mixing statically discovered and runtime-discovered tests to update individual locations without resetting other tests' edit-tracked gutter positions.

## Best solution

Define how partial test-location updates coexist with file-wide synchronization in the testing API and decoration service. Preserve unchanged tests' useful tracked positions while retaining recovery when whole-file edits invalidate decoration tracking.

## Evidence

- **Current source confirms file-wide synchronization:** src/vs/workbench/api/common/extHostTestItem.ts:71-88 emits DocumentSynced whenever a test range is assigned, even before checking range equality. src/vs/workbench/contrib/testing/common/testItemCollection.ts:325-340 converts this into a URI-wide DocumentSynced diff carrying the document version.
- **Unrelated tracked decorations are reset:** In src/vs/workbench/contrib/testing/browser/testingDecorations.ts, TestingDecorationService records rangeUpdateVersionId for the entire resource. applyDecorations then checks every test decoration against its published line and recreates differing decorations when the document version matches. Thus editing the sample document and publishing only test11's range can reset other tests to stale provider-published positions.
- **Intent and unresolved contract:** https://github.com/microsoft/vscode/issues/264581#issuecomment-3282468360 explicitly defends file-wide synchronization as intentional recovery from unreliable decoration tracking and says an explicit synchronization API would need more extension-author demand. https://github.com/microsoft/vscode/issues/264581#issuecomment-3282516654 asks why per-item synchronization would not suffice; no subsequent answer settles that behavior. This is therefore classified as a requested behavior change rather than an accidental deviation from the implemented contract.
- **Later accepted triage:** The issue timeline shows bug and testing labels applied on 2025-12-09, after the September as-designed discussion. No later maintainer decline supersedes that classification, so the earlier comments do not justify a judgment close.
- **Existing capability check:** The testing configuration in src/vs/workbench/contrib/testing/common/configuration.ts exposes gutter visibility and click behavior, not a partial-location synchronization mode. The inspected range setter and collection path provide no per-item alternative to the URI-wide synchronization signal; hiding gutter decorations does not satisfy the request.
