# Issue #28409 — Add "line_padding_bottom", "line_padding_top" like sublime text

[https://github.com/microsoft/vscode/issues/28409](https://github.com/microsoft/vscode/issues/28409)

## Summary

The central ask — adjustable top/bottom line padding independent of line height (like Sublime's line_padding_top/bottom) — is still not implemented on main; only `editor.lineHeight` (a multiplier that also enlarges the cursor/selection block) and `editor.cursorHeight` (cursor-only) exist, neither of which gives the requested padding behavior. A prior review's implemented-on-main claim was independently refuted, so this stays open as a still-valid, unaddressed Backlog request.

## Change summary

Add Sublime-Text-style `line_padding_top`/`line_padding_bottom` settings so line spacing can be adjusted without inflating the cursor and selection highlight the way `editor.lineHeight` does.

## Best solution

Design a dedicated line-padding option (distinct from `editor.lineHeight`) in the editor view layout code (src/vs/editor/common/config/editorOptions.ts and the view line rendering/layout) that adds vertical space per line without scaling cursor/selection size — this likely needs a maintainer design decision on rendering approach (e.g. CSS padding vs. layout metric) before implementation.

## Plan brief

- **Likely files:** `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/browser/viewParts/lines/viewLines.ts`
- **Validation:** A view-layout test asserting that line padding can be set independently of lineHeight/cursor size, once the design is settled.
- **Behavior:**

  > Users should be able to add vertical padding above/below each line of text without the cursor and selection highlight growing to match, unlike today's `editor.lineHeight`, which scales the whole line box including the cursor block. Acceptance: a new setting (name TBD) changes visual line spacing while cursor height/selection height stay tied to font size, not the padding value.
- **Trace:**

  > Today `editor.lineHeight` (EditorLineHeight in src/vs/editor/common/config/editorOptions.ts, ~line 3383) is the only mechanism for line spacing, and it's consumed throughout view layout (viewLines.ts, viewLayout) as the single metric driving both text line box height and cursor/selection rendering — there is no separate padding metric. The boundary: do not change `lineHeight`'s existing semantics for users relying on it; the new setting must be additive. Where uncertainty starts: whether padding is implemented as CSS padding on the line DOM node, as an added layout metric separate from lineHeight, and whether top/bottom are split like Sublime's `line_padding_top`/`line_padding_bottom` or unified.
- **Open decisions:**
  - Should line padding be a single `editor.linePadding` value or split top/bottom like Sublime's two settings?
  - Should the cursor/selection continue to span only the font-size-driven line box, or should it expand to fill the padded line area?
  - Is this delivered as a core editor option, or should it remain a workaround via custom CSS/themes (extension-level) given the 'simple, uniform UI' guardrail?
