# Issue #338693 — Add undo stop after typing the last letter of opening counterpart of auto-closing pair

[https://github.com/microsoft/vscode/issues/338693](https://github.com/microsoft/vscode/issues/338693)

## Summary

Confirmed in source: for multi-character autoClosingPairs, `TypeWithAutoClosingCommand` (src/vs/editor/common/cursor/cursorTypeEditOperations.ts) inserts the typed last-letter of the open sequence and the auto-inserted close sequence as one combined text edit with a single undo stop before it and none after — so one undo removes both `n` and `end` together, matching the report exactly. The `bug` label is already applied, so per policy this stays open rather than being declined as as-designed.

## Change summary

When a multi-character auto-closing pair (e.g. `begin`/`end`) is completed by typing its last letter, undo removes the last letter and the whole auto-inserted closing sequence in one step instead of two.

## Best solution

Split the combined insertion in `TypeWithAutoClosingCommand`/`AutoClosingOpenCharTypeOperation._runAutoClosingOpenCharType` (cursorTypeEditOperations.ts) so the just-typed character and the auto-inserted close sequence land in separate undo groups when the pair's `open` is multi-character, without changing the well-established atomic undo behavior for single-character pairs.

## Plan brief

- **Likely files:** `src/vs/editor/common/cursor/cursorTypeEditOperations.ts`, `src/vs/editor/common/cursor/cursor.ts`
- **Validation:** A cursor.test.ts case that types 'begin' character by character in a language with a multi-character autoClosingPair, then calls model.undo() twice, asserting the buffer reads 'begin' after the first undo and 'begi' after the second (instead of jumping straight to 'begi').
- **Trace:**

  > The defect is confirmed at src/vs/editor/common/cursor/cursorTypeEditOperations.ts:161-171 and 907-914: typing the completing character of a multi-character autoClosingPair open sequence produces one command whose text is `typedChar + closeSequence`, pushed as a single undo unit (`shouldPushStackElementBefore: true`, `shouldPushStackElementAfter: false`). Where the uncertainty starts: whether the fix should special-case `pair.open.length > 1` only (safest, preserves all current single-char undo tests) or introduce a general mechanism to push an undo boundary between two commands executed for the same keystroke, and whether IME/composition completion (`chIsAlreadyTyped: true` path) should get the same treatment.
- **Open decisions:**
  - Should the extra undo stop apply only when the auto-closing pair's `open` is multi-character, or should it also change behavior for single-character pairs (e.g. typing `(`)?
  - Should the same split apply when the open sequence is completed via IME composition (chIsAlreadyTyped=true), or only for direct keystroke typing?

## Evidence

- **code path:** src/vs/editor/common/cursor/cursorTypeEditOperations.ts:161-171 `_runAutoClosingOpenCharType` always sets `shouldPushStackElementBefore: true, shouldPushStackElementAfter: false` and builds a single `TypeWithAutoClosingCommand` whose text is `(insertOpenCharacter ? ch : '') + closeCharacter` (line 909-914), i.e. the typed char and the auto-close text are one atomic edit/undo unit.
- **call site:** cursorTypeOperations.ts:182 calls `AutoClosingOpenCharTypeOperation.getEdits(..., chIsAlreadyTyped=false, ...)` for normal keystroke typing, so `insertOpenCharacter` is true and both `n` and `end` are combined — this is the exact scenario in the issue.
- **existing test:** cursor.test.ts:5372 'autoClosingPairs - multi-character autoclose' only asserts the resulting text ('beginend'), not undo granularity — no existing test covers or locks in the desired two-step undo.
- **related issue:** https://github.com/microsoft/vscode/issues/583 tracks whether multi-character autoClosingPairs work at all (a broader/older but different ask); it does not cover this undo-granularity behavior, so it is not a duplicate canonical.
