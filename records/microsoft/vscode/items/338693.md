# Issue #338693 — Add undo stop after typing the last letter of opening counterpart of auto-closing pair

[https://github.com/microsoft/vscode/issues/338693](https://github.com/microsoft/vscode/issues/338693)

## Summary

Real, reproducible undo-granularity bug confirmed by the reporter's own investigation of the type-command code path; no fix exists yet, and the reporter's own analysis shows a proper fix needs a design decision on how to split the combined insertion into two commands while preserving correct selections, so this stays open as a plan-tier item rather than an immediate implement.

## Change summary

When typing the last letter of a multi-character auto-closing pair opener (e.g. `begin`/`end`), a single undo removes both the typed letter and the auto-inserted closer together instead of as two separate undo stops.

## Best solution

Design how to split the single `typeCommand` insertion of the combined auto-close suffix (e.g. `nend`) into two logically separate edits/undo stops without breaking selection tracking — the reporter's attached markdown already lists considered alternatives and tradeoffs, so a maintainer should pick a direction before implementation.

## Plan brief

- **Likely files:** `src/vs/editor/common/cursor/cursorTypeEditOperations.ts`, `src/vs/editor/common/cursor/cursor.ts`
- **Validation:** A cursor/type-operations test typing the opening counterpart of a multi-character auto-closing pair (e.g. `begin`) and asserting two distinct undo stops: one removing only the last typed letter, one removing the auto-inserted closer.
- **Trace:**

  > Root cause: inserting the final character of a multi-character auto-closing pair opener currently triggers a single typeCommand insertion of the full suffix (e.g. `nend` when typing the final `n` of `begin`), merged into one undo stop, per the reporter's trace. The reporter considered splitting this into two commands (one for the typed letter, one for the auto-inserted closer) but found that correctly repositioning the selection for the second command is non-trivial — see the attached proposal markdown linked in the issue comment for alternatives explored. Boundary: do not change behavior for single-character auto-closing pairs, which already undo correctly.
- **Open decisions:**
  - Which of the approaches in the reporter's attached proposal (splitting into two commands vs. another mechanism) should be used to create two separate undo stops without breaking selection placement for the auto-inserted closer?
  - Is the added complexity/perf cost of two commands per keystroke acceptable given multi-character autoClosingPairs are a niche, custom-language-configuration feature?
