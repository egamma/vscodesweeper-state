# Issue #284672 — UI: Keep/Undo buttons in chat pane should only impact changes from that thread

[https://github.com/microsoft/vscode/issues/284672](https://github.com/microsoft/vscode/issues/284672)

## Summary

Keep open: the local editing implementation still shares file-review entries across chat sessions, so session-local commands do not isolate each thread's contributions. A maintainer accepted this direction; the newer granular-review discussion is related but does not qualify as a duplicate target for this re-reviewed report.

## Change summary

Make chat-thread Keep/Undo actions and change summaries reflect that thread's contributions rather than all pending edits to shared files.

## Best solution

Provide session-scoped review state, change counts, and accept/revert behavior that preserve other threads' contributions to the same file. Coordinate with the ongoing granular-review work while explicitly resolving shared-file and overlapping-edit semantics.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingServiceImpl.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedFileEntry.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedDocumentEntry.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingActions.ts`
- **Validation:** Create two local chats that make distinct edits to the same existing file. Keeping one chat's changes must leave the other's changes pending; undoing one chat's changes must preserve the other's content. Check session summaries and file-review diffs against the originating thread, then repeat with overlapping edits using the agreed conflict behavior.
- **Behavior:**

  > Two chat threads modifying the same file should retain independently reviewable contributions. Keep or Undo invoked within one thread should not acknowledge or revert the other thread's edits, and thread summaries should describe the originating thread's changes. Acceptance covers disjoint edits to one file, correct pending-review state in both chats, and explicitly agreed behavior for overlapping edits.
- **Trace:**

  > ChatEditingService._lookupEntry in chatEditingServiceImpl.ts acquires an existing modified-file entry from another session, and ChatEditingSession reuses it through _lookupExternalEntry. Session-level accept/reject commands therefore reach shared entry state rather than independently attributed contributions. The current document entry delegates Keep and Undo to its text-model change service. This establishes the local editing boundary, not equivalent behavior in every provider-backed harness. Preserve unrelated threads' content and existing single-session behavior; the full summary-consumer and attribution impact remains to be enumerated. The maintainer accepted session-specific behavior at https://github.com/microsoft/vscode/issues/284672#issuecomment-3711315517. Coordinate design with https://github.com/microsoft/vscode/issues/339363 without treating that newer umbrella as this report's duplicate canonical.
- **Open decisions:**
  - When two threads modify overlapping text, what should Undo of the earlier thread do if preserving the later thread's contribution cannot be achieved cleanly?
  - Should editor-level file review remain workspace-wide while thread controls and summaries become session-specific, or should selecting a thread also change the editor's review scope?
