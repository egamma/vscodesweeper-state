# Issue #289074 — Remove WebWorkerDescriptor Duplication (esmModuleLocation vs esmModuleLocationBundler)

[https://github.com/microsoft/vscode/issues/289074](https://github.com/microsoft/vscode/issues/289074)

## Summary

Keep open: current source still maintains separate worker locations for transpiled and bundler environments. The discussion supplies concrete Vite failures caused by incomplete descriptors; unification remains engineering work, not a completed cleanup.

## Change summary

Replace duplicated WebWorkerDescriptor module locations with one bundler-independent declaration that resolves correctly across supported build environments.

## Best solution

Establish a single worker-location contract supported by transpilation, production bundling, and Vite, preserving standalone Monaco worker overrides and extension-host iframe loading. Evaluate the proposed esbuild URL transformation against those environments before migrating descriptors.

## Plan brief

- **Likely files:** `src/vs/platform/webWorker/browser/webWorkerDescriptor.ts`, `src/vs/platform/webWorker/browser/webWorkerServiceImpl.ts`, `src/vs/editor/standalone/browser/services/standaloneWebWorkerService.ts`, `src/vs/editor/browser/services/editorWorkerService.ts`, `src/vs/workbench/services/extensions/browser/webWorkerExtensionHost.ts`, `src/vs/workbench/services/textMate/browser/backgroundTokenization/threadedBackgroundTokenizerFactory.ts`, `src/vs/workbench/contrib/output/browser/outputLinkProvider.ts`, `build/vite/vite.config.ts`, `build/next/index.ts`, `build/next/transpile.ts`
- **Validation:** In a writable implementation checkout, verify worker URL resolution in transpiled and production-bundled desktop/web builds and in the Vite workbench. Open a file with background tokenization enabled and an Output document containing a workspace-file link; verify worker startup and link detection without missing-worker-URL errors. Also verify standalone MonacoEnvironment.getWorker/getWorkerUrl overrides and extension-host iframe startup. These checks were not executed in this read-only review.
- **Behavior:**

  > Each worker entry point should have one authoritative location declaration rather than independently maintained transpiled and bundler locations. The same declaration must resolve to the intended emitted resource in supported development and production environments. Opening files and using output link detection in the Vite workbench must not fail because a descriptor lacks a second location. Existing standalone worker overrides and extension-host iframe behavior must remain compatible.
- **Trace:**

  > WebWorkerDescriptor currently stores two optional location fields, and WebWorkerService and StandaloneWebWorkerService select different fields. EditorWorkerService supplies both, whereas TextMateWorker and OutputLinkDetectionWorker supply only the transpiled location; build/vite/setup-dev.ts installs the standalone resolver, explaining the missing-location failures reported at https://github.com/microsoft/vscode/issues/289074#issuecomment-5768975006. Vite already has rollupEsmUrlPlugin, while build/next maintains explicit worker entry points and a transpilation rewrite for .ts?esm references. The extension-host implementation also passes an HTML iframe through getWorkerUrl, so the shared abstraction is not exclusively a worker-module abstraction. The trace establishes the remaining duplication, but does not establish a single URL form that all build lanes can safely consume. Preserve MonacoEnvironment overrides, worker bootstrap/localization behavior, and iframe origin handling; do not treat adding the two missing bundler fields as completion of the broader cleanup.
- **Open decisions:**
  - Must the unified location contract continue to cover HTML iframe resources, or is its supported resource scope limited to worker modules?
  - Must existing standalone descriptor consumers retain compatibility with both location fields during migration, or is a breaking replacement of that contract acceptable?

## Evidence

- **Duplication remains:** src/vs/platform/webWorker/browser/webWorkerDescriptor.ts still declares esmModuleLocation and esmModuleLocationBundler separately. EditorWorkerService.workerDescriptor in src/vs/editor/browser/services/editorWorkerService.ts supplies both the FileAccess JavaScript location and the relative TypeScript ?esm URL.
- **Separate resolution paths:** WebWorkerService.getWorkerUrl in src/vs/platform/webWorker/browser/webWorkerServiceImpl.ts reads only esmModuleLocation. StandaloneWebWorkerService.getWorkerUrl in src/vs/editor/standalone/browser/services/standaloneWebWorkerService.ts reads esmModuleLocationBundler after checking MonacoEnvironment overrides, and throws when it is absent.
- **Discussion and current source agree:** https://github.com/microsoft/vscode/issues/289074#issuecomment-5768975006 reports TextMateWorker and OutputLinkDetectionWorker failures in the Vite-served workbench, with stack traces and effects on tokenization and output links. Current build/vite/setup-dev.ts installs StandaloneWebWorkerService, while threadedBackgroundTokenizerFactory.ts and outputLinkProvider.ts still provide only esmModuleLocation. This supports the cleanup's motivation without establishing that production builds are affected.
- **Existing tooling is partial coverage:** build/vite/vite.config.ts already enables rollupEsmUrlPlugin from @vscode/rollup-plugin-esm-url, but this has not eliminated the descriptor fields. build/next/transpile.ts adjusts .ts?esm references to .js?esm, and build/next/index.ts separately lists worker entry points; these are distinct build surfaces the proposed unification must accommodate.
- **Additional contract boundary:** src/vs/workbench/services/extensions/browser/webWorkerExtensionHost.ts uses WebWorkerDescriptor both for extensionHostWorkerMain and for an HTML iframe URL without ?esm. A worker-module-only migration would miss an existing getWorkerUrl consumer.
