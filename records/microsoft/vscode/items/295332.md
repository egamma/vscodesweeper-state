# Issue #295332 — Auto deny Github Copilot-Chat to access file outside the current workspace.

[https://github.com/microsoft/vscode/issues/295332](https://github.com/microsoft/vscode/issues/295332)

## Summary

A real gap remains: current permission handling can still pause a session for a path-bearing read request outside the workspace, with no workspace-bound auto-deny or retry-confirmation policy. No older open issue with the same observable request was found, so the stronger re-review duplicate bar is not met.

## Change summary

Add an option that rejects likely accidental Copilot file access outside the active workspace without immediately pausing for approval, while preserving deliberate external access.

## Best solution

Provide an explicit workspace-bound permission policy that prevents accidental external-path prompts while retaining a deliberate, auditable override for legitimate external reads.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/platform/agentHost/node/copilot/copilotToolDisplay.ts`, `src/vs/platform/agentHost/test/node/copilotAgentSession.test.ts`, `extensions/copilot/src/extension/tools/node/toolUtils.ts`, `extensions/copilot/src/extension/tools/node/test/toolUtils.spec.ts`
- **Validation:** Add focused permission tests proving that an accidental outside-workspace request follows the selected non-blocking policy, a deliberate retry or configured grant reaches approval/access as designed, workspace-local requests remain unchanged, and external skill or instruction paths continue to work.
- **Behavior:**

  > When Copilot requests an accidental path outside the active working directories, the session should not immediately pause for user approval. The model should receive a clear rejection or correction opportunity, while intentional external access remains possible through an explicit, user-understandable mechanism. Workspace-local access and already-authorized external resources must remain unchanged. Acceptance includes accidental malformed paths, legitimate external skill reads, and deliberate external access.
- **Trace:**

  > Current Agent Host permission handling enters through `CopilotAgentSession._handlePermissionRequest` in src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts; path-bearing read requests are displayed through src/vs/platform/agentHost/node/copilot/copilotToolDisplay.ts and normally progress to PendingConfirmation. The older extension-side boundary helper in extensions/copilot/src/extension/tools/node/toolUtils.ts already distinguishes working-directory paths, configured additional read roots, external instruction/skill resources, and other external files, but its policy is confirmation-oriented rather than auto-deny or retry-to-confirm. Preserve sandbox enforcement, managed approval requirements, content-exclusion checks, configured read roots, and legitimate skill access. The uncertainty starts at the user-visible permission policy: what constitutes confirmation, which operations it covers, and how long any retry state persists.
- **Open decisions:**
  - Should the option always reject outside-workspace access, or should the first request return corrective feedback and an identical second request open the approval UI?
  - Should deliberate external access be enabled by a repeated request, a configured path grant, or both?
  - Does the policy apply only to file reads, or also to writes and shell commands whose filesystem targets are outside the workspace?
  - Is retry confirmation scoped to one tool call, one turn, or the full session?

## Evidence

- **current permission path:** In src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts, `_handlePermissionRequest` auto-rejects requests lacking a tool-call ID or belonging to an unroutable subagent, but path-bearing read requests otherwise continue toward PendingConfirmation; it has no workspace-bound deny or first-request correction policy.
- **partial existing behavior:** extensions/copilot/src/extension/tools/node/toolUtils.ts checks whether files and directories are outside the working directory. Nonexistent external files fail before confirmation and configured `chat.additionalReadAccessPaths` can exempt read-only paths, but existing external resources still require confirmation and there is no requested auto-deny or repeat-to-confirm option.
- **coverage:** extensions/copilot/src/extension/tools/node/test/toolUtils.spec.ts explicitly expects an existing external file to need confirmation, confirming that the central request is not already covered by the current helper behavior.
- **canonical search:** Repository searches for Copilot outside-workspace file access, external-file permissions, and auto-deny behavior found no older open issue with the same reporter-observable request. The supplied candidates concern sandbox path configuration, Docker sockets, MCP roots, or unrelated permission modes.
- **related report:** https://github.com/microsoft/vscode/issues/295332#issuecomment-3954002990 reports that external skill reads can also trigger the boundary, showing why legitimate external resources need an explicit exception rather than an unconditional deny.
