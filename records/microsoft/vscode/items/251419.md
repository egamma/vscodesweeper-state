# Issue #251419 — Linux native context menu captures all mouse input and becomes unresponsive

[https://github.com/microsoft/vscode/issues/251419](https://github.com/microsoft/vscode/issues/251419)

## Summary

Still live on current main: VS Code deliberately lets the OS/Chromium system window menu open over the app icon on Linux with the custom title bar, and dismissing it leaves a pointer grab that makes the mouse unusable desktop-wide (X11) or breaks window drag/resize (Wayland). A second reporter confirmed it with a screencast on both session types, so the `confirmation-pending` state is effectively satisfied; it needs a maintainer decision on whether to keep allowing the native menu there.

## Change summary

Right-clicking the app icon in the Linux custom title bar opens the native system menu, and after it is dismissed the pointer stays grabbed until the user Alt+Tabs away and back.

## Best solution

Decide whether Linux should keep the native window system menu over the app icon at all: either report/track the pointer-grab release as an Electron/Chromium Linux bug, or extend the existing `preventDefault()` in `BaseWindow` (src/vs/platform/windows/electron-main/windowImpl.ts) to cover the app-icon region on Linux too and show the custom `MenuId.TitleBarContext` menu instead, as is already done for the rest of the title bar.

## Plan brief

- **Likely files:** `src/vs/platform/windows/electron-main/windowImpl.ts`, `src/vs/workbench/electron-browser/parts/titlebar/titlebarPart.ts`, `src/vs/sessions/electron-browser/parts/titlebarPart.ts`
- **Validation:** On Linux (GNOME, both X11 and native Wayland) with the custom title bar: right-click the app icon, dismiss the resulting menu, then click elsewhere — the mouse must remain fully functional across the desktop and window drag/resize must still work without Alt+Tab.
- **Behavior:**

  > On Linux with the custom title bar, right-clicking the VS Code app icon must not leave the pointer grabbed after the menu is dismissed: subsequent clicks work normally across the desktop (X11) and the window can still be dragged and resized by its edges (native Wayland). Whatever menu is shown over the app icon must offer the same affordances users rely on today. Acceptance: the manual check above passes on X11 and Wayland, and right-clicking the rest of the title bar still shows the existing custom title bar context menu unchanged.
- **Trace:**

  > BaseWindow in src/vs/platform/windows/electron-main/windowImpl.ts (lines ~240-257) registers a `system-context-menu` listener for Windows and Linux when a custom title style is used, and on Linux only calls `e.event.preventDefault()` when the cursor is beyond the app icon (`cx > 35`), deliberately letting Chromium's native window menu open over the icon; beyond the icon it fires `_onDidTriggerSystemContextMenu`. That renderer-side event is consumed only under `isWindows` in src/vs/workbench/electron-browser/parts/titlebar/titlebarPart.ts:216 (and src/vs/sessions/electron-browser/parts/titlebarPart.ts:122), so Linux has no custom-menu path for the icon today. The defect itself (an unreleased pointer grab after the native menu closes) could not be confirmed from source — it needs a running Linux build — but it is confirmed on both X11 and Wayland in https://github.com/microsoft/vscode/issues/251419#issuecomment-2971469079 with a screencast. Boundary: do not change Windows behavior (the `cx > 35` workaround there references https://github.com/microsoft/vscode/issues/250632), do not touch the renderer CONTEXT_MENU handler in src/vs/workbench/browser/parts/titlebar/titlebarPart.ts:584, and do not alter native-title-bar setups.
- **Open decisions:**
  - Should Linux keep showing the OS native window system menu over the app icon, or should VS Code suppress it there (as it already does for the rest of the title bar) and show the custom TitleBarContext menu instead?
  - If the grab turns out to be an Electron/Chromium Linux defect, should this issue be reclassified as `upstream` and tracked there rather than worked around in VS Code?
  - If a workaround is taken, should it apply to all Linux sessions or only to the configurations where the grab reproduces (X11 and native Wayland)?

## Evidence

- **code path on main:** src/vs/platform/windows/electron-main/windowImpl.ts:240-257 — 'Setup windows/linux system context menu so it only is allowed over the app icon': on Linux with a custom title bar the `system-context-menu` event is only `preventDefault()`-ed when `cx > 35`, i.e. the native system menu is intentionally allowed over the app icon. That is exactly the surface the reporter right-clicks.
- **custom menu not wired on Linux:** src/vs/workbench/electron-browser/parts/titlebar/titlebarPart.ts:216-227 gates `onDidTriggerWindowSystemContextMenu` on `isWindows`, so the main-process fallback that would show the custom `MenuId.TitleBarContext` menu does not run on Linux; the renderer's own CONTEXT_MENU listener (src/vs/workbench/browser/parts/titlebar/titlebarPart.ts:584) covers non-drag areas instead.
- **independent confirmation:** https://github.com/microsoft/vscode/issues/251419#issuecomment-2971469079 — a second user reproduced on Ubuntu 22.04/25.04: native Wayland loses window drag/resize after dismissing the menu, and switching to X11 reproduced the OP's desktop-wide mouse grab, with a screencast. The maintainer (bpasero) could not reproduce, hence `confirmation-pending`.
- **likely root cause:** Both symptom variants (X11 full-desktop pointer grab, Wayland loss of the compositor-side drag/resize affordance) are classic unreleased input-grab behavior from the native menu, which points at Electron/Chromium's Linux menu runner rather than VS Code code; VS Code's contribution is choosing not to suppress that menu over the app icon. Not verifiable from source alone — the checkout is shallow (no history) and this cannot be traced without running a Linux build.
- **no fix landed:** The allow-over-app-icon logic and the Windows-only renderer wiring are both still present on current main (e3c23162), so nothing has changed the reported behavior.
