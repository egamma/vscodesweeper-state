# Issue #125993 — Webview Service Worker Error in registration due to invalid document state

[https://github.com/microsoft/vscode/issues/125993](https://github.com/microsoft/vscode/issues/125993)

## Summary

Keep open: maintainer-confirmed reproductions identify a Chromium service-worker provider failure affecting built-in and extension webviews. The merged Windows updater fix covers one contributing scenario, not the full cross-platform report.

## Change summary

Prevent webviews from failing service-worker registration with InvalidStateError, particularly when old and new VS Code processes overlap after an update.

## Best solution

Resolve the Chromium provider/session-state failure and prevent unsupported sharing of persistent session data between VS Code browser processes. Verify the Linux cross-version reproduction as well as Windows update behavior before treating this report as completed; repeated registration and broad cache deletion are not the accepted recovery design.

- **Runtime diagnosis:** https://github.com/microsoft/vscode/issues/125993#issuecomment-885840407 traces successful webview navigation and script loading followed by Blink rejecting registration because its ServiceWorkerContainer provider is absent. This is not evidence that GitGraph or another individual extension owns the defect.
- **Current source:** src/vs/workbench/contrib/webview/browser/pre/index.html:259-298 still registers the worker through navigator.serviceWorker.register and propagates registration rejection as 'Could not register service worker'. src/vs/platform/environment/electron-main/environmentMainService.ts:52 still constructs mainIPCHandle using productService.version. Source inspection establishes the relevant paths, not a fresh runtime reproduction.
- **Rejected recovery attempt:** https://github.com/microsoft/vscode/pull/333833 was closed without merging. At https://github.com/microsoft/vscode/pull/333833#issuecomment-5596170799, the maintainer explains that registration retries cannot repair an absent Blink provider, cache deletion can disrupt other webviews, and the strongest reproductions involve browser processes sharing persistent session data.
- **Partial landed fix:** https://github.com/microsoft/vscode/pull/335216 was closed without merging and points to merged https://github.com/microsoft/vscode/pull/336253, commit a1dab1c2990ce03e0a6f4aa8c01245ddb5c89ca2. Its main.ts diff releases instance ownership while waiting for the Windows Inno Setup update mutex, then reacquires it. Current src/vs/code/electron-main/main.ts:560-562 explicitly restricts this check to Windows versioned Inno installations, so it does not establish a fix for the original Ubuntu Snap trigger.

Although an early comment suggested that older issue as a duplicate, its current scope is elevated Windows execution under AppLocker, which does not absorb the confirmed Linux cross-version failure. https://github.com/microsoft/vscode/issues/326331 instead proposes a newer, opt-in webview architecture and is not an older same-symptom canonical.
- **Distinct recent regression:** https://github.com/microsoft/vscode/issues/339079 concerns grey embedded frames caused by a WebAssembly tier-up crash; its discussion explicitly reports successful service-worker registration. Its resolution therefore does not prove this registration failure is fixed.
- **Latest investigation remains inconclusive:** https://github.com/microsoft/vscode/issues/125993#issuecomment-6055944537 maps iframe navigation and reparenting paths but explicitly states that registration overlap was not demonstrated and the failure was not reproduced locally. This is a diagnostic lead, not a confirmed replacement root cause or fix.
