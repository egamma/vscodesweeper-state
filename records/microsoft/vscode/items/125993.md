Keep open as the established cross-platform webview registration issue. Maintainer-confirmed Chromium failures and recent reports remain relevant; the related Windows update fix does not establish resolution of the full report.

## Change summary

Webviews fail to initialize when Chromium rejects service worker registration with an invalid document state.

Resolve the Chromium/Electron registration failure and its triggering lifecycle or storage conditions, while preserving existing extension webview behavior. Investigate the retained per-origin state evidence before choosing a targeted recovery mechanism; retries or a Windows-only update fix do not establish a complete solution.

## Evidence

- **Maintainer-confirmed runtime failure:** https://github.com/microsoft/vscode/issues/125993#issuecomment-885840407 compares working and failing navigation traces and identifies Chromium's missing service worker provider as the rejection point. The maintainer subsequently confirmed reproduction at https://github.com/microsoft/vscode/issues/125993#issuecomment-961870836. This is not established as a GitGraph-specific extension defect.
- **Current source still exposes the failure:** src/vs/workbench/contrib/webview/browser/pre/index.html:259-300 registers the service worker once and rejects workerReady on registration failure; lines 977-984 report a fatal error and abandon content initialization. src/vs/workbench/contrib/webview/browser/webviewElement.ts:249-254 displays that error. These paths establish the consequence of a runtime rejection, not a deterministic reproduction of its cause.
- **Recent origin-specific investigation:** https://github.com/microsoft/vscode/issues/125993#issuecomment-5469818962 reports different persisted worker versions across origins on VS Code 1.135.0 and failure of registration enumeration on wedged origins. The supplied July 2026 report also describes controlled recovery after resetting only shared Service Worker state. These are useful diagnostic leads, not proof that a particular recovery design is sufficient.
- **Latest lifecycle analysis is explicitly inconclusive:** https://github.com/microsoft/vscode/issues/125993#issuecomment-6055944537 maps iframe navigation and reparenting but explicitly does not reproduce registration overlapping those operations. Current webviewElement.ts:417-511 matches that map: sandbox attributes are set on creation, while mountTo schedules a src assignment and appends the iframe. This does not conclusively identify the root cause.
- **Fix attempts and limited landed mitigation:** https://github.com/microsoft/vscode/pull/333833 and https://github.com/microsoft/vscode/pull/335216 were closed without merging. A maintainer directed the latter to https://github.com/microsoft/vscode/pull/336253, merged as a1dab1c2990ce03e0a6f4aa8c01245ddb5c89ca2. Its diff releases the main IPC server while waiting for the Windows Inno Setup mutex and then reclaims the instance; the check is Windows/install-specific. That can address an update interaction but does not demonstrate resolution of the reported Linux and macOS failures.
- **No verified duplicate canonical:** Canonical searches found no older open issue covering this same cross-platform invalid-document-state failure. https://github.com/microsoft/vscode/issues/122951 concerns elevated Windows processes under AppLocker; https://github.com/microsoft/vscode/issues/326823 concerns fetching /sw.js. https://github.com/microsoft/vscode/issues/326331 is a newer, opt-in architecture proposal, not a duplicate canonical for this re-reviewed report.
- **Adjacent resolved regression is distinct:** https://github.com/microsoft/vscode/issues/339079#issuecomment-5993526571 identifies its grey webview as an iframe process crash caused by WebAssembly tier-up compilation. Its discussion also reports successful service worker registration. That fix therefore does not establish resolution of this registration error.
