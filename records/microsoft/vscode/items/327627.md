# Issue #327627 — MCP servers matched via serverUrl in chat.mcp.allowedServers never finish initializing while the policy is active (work when policy removed)

[https://github.com/microsoft/vscode/issues/327627](https://github.com/microsoft/vscode/issues/327627)

## Summary

The controlled policy-on/policy-off comparison demonstrates a runtime enforcement regression for allowed HTTP MCP servers. Route this to the MCP area for investigation.

## Change summary

Remote MCP servers explicitly allowed by URL must initialize and expose tools while the enterprise allowlist is active.

## Best solution

Correct the runtime policy evaluation in `McpServer` so an allowed resolved HTTP launch remains connected, and add coverage that starts an allowlisted HTTP server through initialization and tool discovery.

- **controlled reproduction:** The report uses the same public no-auth DeepWiki URL and configuration with one variable changed: initialization repeatedly stalls with ChatAllowedMcpServers active, then discovers three tools within two seconds after policy removal.
- **scope isolation:** The failure affects URL-matched HTTP servers while command-matched stdio servers work under the same policy, narrowing it to remote-server runtime enforcement rather than general MCP connectivity.
- **implementation:** Commit https://github.com/microsoft/vscode/commit/e1b183798f02cc42c6be364c8b0eeeebfb7a5ed0 introduced the policy. Current `src/vs/workbench/contrib/mcp/common/mcpServer.ts` evaluates policy before startup and again after assigning the resolved connection, with reactive logic that can dispose a connection when the resolved identity is considered blocked.
- **coverage gap:** `src/vs/platform/mcp/test/common/allowedMcpServersService.test.ts` verifies URL matching in isolation but does not exercise HTTP connection initialization and tool discovery while the runtime policy is active.
