# Issue #197989 — Workspace Trust - Untrusted files don't open in the same window via Open Recent

[https://github.com/microsoft/vscode/issues/197989](https://github.com/microsoft/vscode/issues/197989)

## Summary

The bug remains source-reproducible on current main: custom-menubar Open Recent file actions enter the generic API opening path, where the default Windows/Linux policy selects a new window instead of matching File > Open. The existing `bug` classification and Backlog milestone should remain.

## Change summary

Opening an untrusted loose file from Open Recent creates another restricted window even though File > Open reuses the current restricted window under the same settings.

## Best solution

Make custom-menubar Open Recent file actions follow the same window-selection semantics as the native Open Recent menu and File > Open when `window.openFilesInNewWindow` is `default`, while preserving explicit modifier and `on`/`off` setting behavior.

  > With `window.openFilesInNewWindow` set to `default`, selecting a file from the custom File > Open Recent menu must reuse the current window, including when that window is in Restricted Mode. - **Trace:**

  > `MenubarControl.createOpenRecentMenuAction` in `src/vs/workbench/browser/parts/titlebar/menubarControl.ts` sends recent files through `IHostService.openWindow` with only `forceNewWindow`. On desktop, `NativeHostMainService.doOpenWindow` assigns `OpenContext.API`; `WindowsMainService.shouldOpenNewWindow` consequently defaults to a new window on Windows/Linux, whereas file-dialog and native-menubar requests use `DIALOG` and `MENU` contexts and default to reuse. The defect is therefore in the custom-menubar routing/options rather than workspace-trust evaluation itself. ## Evidence

- **source reproduction:** `src/vs/workbench/browser/parts/titlebar/menubarControl.ts` creates recent-file actions through `IHostService.openWindow` with `forceNewWindow: false` but without same-window context or an explicit reuse decision.
- **window-selection path:** `src/vs/platform/native/electron-main/nativeHostMainService.ts` translates that renderer request to `OpenContext.API`; `src/vs/platform/windows/electron-main/windowsMainService.ts` treats API requests as new-window requests on Windows/Linux when `window.openFilesInNewWindow` is `default`, because only `DIALOG` and `MENU` contexts default to reuse.
- **behavioral discrepancy:** `NativeHostMainService.doOpenPicked` uses `OpenContext.DIALOG` for File > Open, while `src/vs/platform/menubar/electron-main/menubar.ts` uses `OpenContext.MENU` for native Open Recent entries. Both therefore differ from the custom-menubar path and reuse the window by default.
- **canonical search:** Repository issue searches found no open older issue reporting this same observable Open Recent/workspace-trust symptom. The related https://github.com/microsoft/vscode/issues/125182 concerned repeatedly opening files when the explicit trust policy was `newWindow`, not this `default` Open Recent discrepancy.
