# Issue #295673 — Can't highlight while scrolling in Jupyter notebooks

[https://github.com/microsoft/vscode/issues/295673](https://github.com/microsoft/vscode/issues/295673)

## Summary

Credible regression report (1.105 works, 1.106+ broken) with exact steps, two GIFs and a second user confirming: click-dragging inside a notebook cell editor no longer extends the text selection, the notebook list scrolls instead. I could not execute the drag interaction and found no fix on main, so this stays open and should be routed to the notebook area; the reporter's steps are sufficient for a maintainer to retest as-is.

## Change summary

Click-dragging to select text inside a Jupyter notebook cell no longer extends the selection — the surrounding notebook scrolls instead — a regression since 1.105.

## Best solution

Reproduce and bisect 1.105→1.106, then restore drag-select inside cell editors: the notebook list should scroll while the cell editor's selection keeps extending, most likely in the editor's outside-editor drag-scroll path (src/vs/editor/browser/controller/mouseHandler.ts / dragScrolling.ts) interacting with the cell editor's hidden vertical scrollbar and handleMouseWheel:false configuration.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/mouseHandler.ts`, `src/vs/editor/browser/controller/dragScrolling.ts`, `src/vs/workbench/contrib/notebook/browser/view/renderers/cellRenderer.ts`, `src/vs/workbench/contrib/notebook/browser/viewModel/cellEditorOptions.ts`, `src/vs/workbench/contrib/notebook/browser/view/notebookCellList.ts`
- **Validation:** Manual: open a .ipynb with a cell taller than the viewport, press and hold the left button on code in that cell and drag downward past the bottom of the window — the notebook scrolls and the text selection keeps extending line by line; releasing leaves a multi-line selection. Compare against 1.105 behavior. Add an automated check only if the bisected change has a testable seam.
- **Behavior:**

  > In a Jupyter notebook, pressing the left mouse button on code inside a cell and dragging must extend the text selection, including when the drag moves past the visible area so the notebook scrolls. Today (1.106+ through 1.110-insider) the selection stops extending and only the surrounding notebook scrolls; 1.105 behaved correctly. Acceptance: drag-select within and beyond a tall cell produces a growing selection while the notebook scrolls; plain wheel scrolling over a cell still scrolls the notebook (cell editors deliberately do not consume the wheel); cell drag-and-drop reordering and selection in regular text editors are unchanged.
- **Trace:**

  > Notebook cell editors are configured with a hidden vertical scrollbar and `handleMouseWheel: false` (src/vs/workbench/contrib/notebook/browser/view/renderers/cellRenderer.ts:287-301) plus `alwaysConsumeMouseWheel: false` and `scrollBeyondLastLine: false` (src/vs/workbench/contrib/notebook/browser/viewModel/cellEditorOptions.ts:17-32), so a cell editor's viewport equals its content and cannot scroll itself. On drag, MouseDownOperation._onMouseDownThenMove (src/vs/editor/browser/controller/mouseHandler.ts:410-436) routes OUTSIDE_EDITOR targets into TopBottomDragScrolling / LeftRightDragScrolling (src/vs/editor/browser/controller/dragScrolling.ts), which scroll the editor's own view layout via `deltaScrollNow` and re-dispatch an edge-line mouse target — a no-op for a cell editor, and `_getPositionOutsideEditor` also classifies drags at/left of `layoutInfo.contentLeft` as outside targets. That is the most likely seam, but it is a hypothesis: the shallow checkout (single commit 5a31a5ddbb15d483ff772db522fcf1c63618157d) made it impossible to bisect 1.105→1.106 or to confirm which change regressed this, and the behavior is pointer-driven so it cannot be settled by reading source. Boundary: do not change wheel-scroll routing (cells intentionally delegate the wheel to the notebook list) and do not touch cell drag-and-drop reordering. The uncertainty starts at identifying the 1.106 change.
- **Open decisions:**
  - When a drag-select runs past the bottom of a cell, should the selection stop at that cell's boundary (current notebook model: one selection per cell editor) or should the notebook list auto-scroll while the selection continues extending within that cell?
  - Is the fix owned by the core editor's outside-editor drag-scroll path (making it defer scrolling to an embedding scrollable, e.g. a notebook list) or by the notebook contrib hooking the drag to scroll its list — i.e. does this change behavior for all embedded editors (chat, diff, cell editors) or only notebooks?
