# Issue #214536 — Anchor Selection with Search and Replace not working correctly

[https://github.com/microsoft/vscode/issues/214536](https://github.com/microsoft/vscode/issues/214536)

## Summary

The selection-loss problem is already tracked by an older, open issue: typing the search text replaces the original selection before Find in Selection captures it. The current source confirms that anchor-created selections follow this same path, so consolidate this report with that canonical.

## Change summary

Find and Replace fails to retain an anchor-created multiline selection when search text is entered before enabling Find in Selection.

## Best solution

Resolve preservation of the original search selection through https://github.com/microsoft/vscode/issues/192388, retaining this report's anchor-selection steps and JAWS observations as acceptance cases. The existing autoFindInSelection setting provides a workaround, not a fix for the reported interaction order.

## Evidence

- **Verified older canonical:** https://github.com/microsoft/vscode/issues/192388 was created on 2023-09-07, before this report, and is currently open with bug and editor-find labels. Its body explicitly describes selecting text, opening Find, typing a search term, losing the original selection, and consequently being unable to use Find in Selection on that original range. This is the same observable selection-loss sequence, not merely a related editor problem.
- **Anchor selection is an ordinary editor selection:** src/vs/editor/contrib/anchorSelect/browser/anchorSelect.ts: SelectionAnchorController.selectFromAnchorToCursor calls editor.setSelection(Selection.fromPositions(...)) and then cancels the anchor. There is no separate anchor-specific search scope; the reporter's first three lines become an ordinary selection.
- **Current source confirms the failing order:** src/vs/editor/contrib/find/browser/findWidget.ts:1023-1031 changes the search string with moveCursor=true. findModel.ts:188-265 researches matches, moves to a match when cursorMoveOnType is enabled, and calls editor.setSelection(match). The Find in Selection toggle at findWidget.ts:1113-1127 subsequently captures getSelections(), which is now the individual match rather than the original three-line selection.
- **Replacement consequence:** src/vs/editor/contrib/find/browser/findModel.ts:481-529 replaces within the captured find scope and researches afterward. Capturing only the selected 'he' match explains replacement of one occurrence followed by no remaining matches, rather than replacing all three occurrences in the original anchor-selected range. The exact JAWS speech was not tested.
- **Existing workaround and scope:** src/vs/editor/common/config/editorOptions.ts:1795-1799 defaults cursorMoveOnType to true and autoFindInSelection to never. findController.ts:488-514 supports autoFindInSelection=multiline, capturing the selection before search typing. A maintainer recommends that workaround at https://github.com/microsoft/vscode/issues/192388#issuecomment-1856208555; it does not preserve the original selection under the reporter's default interaction order.
- **Additional related reports:** https://github.com/microsoft/vscode/issues/284007 and https://github.com/microsoft/vscode/issues/250617 also describe search-driven selection narrowing, including later confirmations. They are newer than this item and are not used as duplicate targets. The older canonical explicitly owns the original-selection-loss behavior.
