# Issue #334998 — In Global Search, a click on the result does not trigger editor.findMatchForeground(or background) change

[https://github.com/microsoft/vscode/issues/334998](https://github.com/microsoft/vscode/issues/334998)

## Summary

Fresh, well-detailed report with clear repro steps; tracing the search view code shows a plausible event-ordering bug that matches the symptom, so this should be routed to the search area for a maintainer to confirm and fix rather than closed.

## Change summary

Clicking a Global Search result only changes the current-match highlight color in the editor every other click, requiring a double click to see the update.

## Best solution

In src/vs/workbench/contrib/search/browser/searchView.ts, the tree's onDidOpen handler sets the selected match/highlight and then calls onFocus→open(), which passes a `selection` to editorService.openEditor — this itself changes the editor's cursor position. The `onDidActiveEditorChange`-installed `onDidChangeCursorPosition` listener (registered once per active-editor change, ~line 1082-1088) then fires and immediately clears `currentSelectedFileMatch` via `setSelectedMatch(null)`, wiping the highlight that was just set. Because that listener is only re-installed when the *active editor* changes (not on every click), the very first click into a newly-activated editor is fine, but subsequent clicks within the same already-active editor reuse the stale listener and get self-cleared. The fix likely needs to distinguish a programmatic reveal-caused cursor move from a genuine user-initiated one (e.g. compare the new cursor position against the just-set match range before clearing).

- **self-clearing listener:** src/vs/workbench/contrib/search/browser/searchView.ts ~line 1081-1088: `onDidActiveEditorChange` installs an `onDidChangeCursorPosition` listener whose sole purpose is to clear the just-set highlight (`currentSelectedFileMatch?.setSelectedMatch(null)`) when the cursor moves — but it does not distinguish a cursor move caused by the search view's own `openEditor({selection})` reveal from a genuine user-initiated move, and is only reinstalled when the active editor itself changes, not per click.
