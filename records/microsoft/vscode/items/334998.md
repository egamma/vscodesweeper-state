# Issue #334998 — In Global Search, a click on the result does not trigger editor.findMatchForeground(or background) change

[https://github.com/microsoft/vscode/issues/334998](https://github.com/microsoft/vscode/issues/334998)

## Summary

Traced a plausible concrete root cause in current main: the search view's cursor-position listener clears the selected-match highlight the moment the newly clicked result is revealed in the editor, because revealing/selecting the match itself fires the same cursor-change event the listener treats as 'user moved away, clear highlight'.

## Change summary

Clicking a search result in the Search view highlights the current match in the editor only intermittently (works on the very first navigation, then requires a second click on subsequent results).

## Best solution

In src/vs/workbench/contrib/search/browser/searchView.ts, the cursor-position listener registered around the 'Setup cursor position monitoring' block (near line 1081-1088) should not clear currentSelectedFileMatch when the cursor change is the direct result of SearchView.open()/onFocus() revealing that same match — e.g. by suppressing the clear for the reveal-triggered selection change, or comparing the new cursor position against the just-selected match's range before clearing.

  > Thanks for the detailed repro — I traced this in the current source. When you click a result, `SearchView`'s `tree.onDidOpen` handler correctly marks the match as selected (painting it with `editor.findMatchForeground`/`findMatchBackground`), but the subsequent call to open the editor sets the selection to that same match's range, which fires the cursor-position listener registered in `searchView.ts` (the block that clears `currentSelectedFileMatch` on any cursor move meant to detect the user manually moving away). That listener doesn't distinguish 'user moved the cursor elsewhere' from 'we just revealed this very match', so it immediately clears the highlight it just set — matching your 'only after clicking twice' observation. This looks like a real fix candidate around `src/vs/workbench/contrib/search/browser/searchView.ts` lines ~1021-1088. (The foreground/background color question is a separate, smaller point worth confirming separately.)

## Evidence

- **selection/highlight wiring:** src/vs/workbench/contrib/search/browser/searchTreeModel/fileMatch.ts:277-298 setSelectedMatch()/isMatchSelected() drive updateHighlights() (lines 218-234), which paints the selected match with FileMatchImpl._CURRENT_FIND_MATCH (editor.findMatchForeground/Background) vs. the normal highlight decoration.
- **clicking a result:** src/vs/workbench/contrib/search/browser/searchView.ts:1021-1030 (tree.onDidOpen handler) calls currentSelectedFileMatch.setSelectedMatch(selectedMatch) — correctly painting the new current match — then calls this.onFocus(...) -> this.open(...).
- **open() moves the cursor:** searchView.ts:2239-2256 open() calls editorService.openEditor({resource, options: {selection: getEditorSelectionFromMatch(...), revealIfVisible: true}}), which sets the editor selection/cursor to the just-clicked match's range.
- **the race:** searchView.ts:1081-1088 registers editor.onDidChangeCursorPosition (via currentEditorCursorListener, declared at line 177) to call currentSelectedFileMatch?.setSelectedMatch(null) on ANY cursor move. Because the listener is attached on the first onDidActiveEditorChange (i.e. before subsequent same-file clicks), the very selection change from open() re-fires this listener and immediately clears the highlight it just set — explaining why only the very first navigation (before the listener exists) shows the highlight and subsequent clicks need to be repeated.
