# Issue #237975 — Find and Replace (regex) behavior changes when text is long (negated character class starts including newline)

[https://github.com/microsoft/vscode/issues/237975](https://github.com/microsoft/vscode/issues/237975)

## Summary

The original report duplicates the older, open issue about large-file regex replacement unexpectedly consuming neighboring lines. Current source confirms the match-count-dependent change from line-by-line matching to whole-document replacement.

## Change summary

Regex Replace All unexpectedly crosses line boundaries with negated character classes once the editor reaches its match-count limit.

## Best solution

Consolidate the large-file replacement defect under https://github.com/microsoft/vscode/issues/62651 and make bulk replacement preserve the matching semantics used by Find regardless of match count. Preserve this report's compact reproduction and threshold observations; the later workspace-search example should not be assumed to share this cause.

## Evidence

- **Verified older canonical:** https://github.com/microsoft/vscode/issues/62651 is open and was created on 2018-11-06, before this issue. It reports the same observable failure in editor Replace All: a negated-character-class regex works on a small document but consumes otherwise unaffected neighboring lines on a large document. Its pattern, ^([^\t<]+).*$, likewise permits newline inside the negated class when evaluated over the whole document.
- **Exact current-source trigger:** src/vs/editor/contrib/find/browser/findModel.ts defines MATCHES_LIMIT = 19999. FindModelBoundToEditorModel.replaceAll() switches to _largeReplaceAll() when there is no selection scope and matchesCount reaches that limit. The supplied long sample has 30000 ordinary REPLACE/ME/23 matches, while the short sample has only 30.
- **Confirmed semantic divergence:** In src/vs/editor/common/model/textModelSearch.ts, SearchParams.parseSearchRequest() and isMultilineRegexSource() classify the reported pattern as non-multiline, so TextModelSearch.findMatches() searches line by line. In findModel.ts, _largeReplaceAll() instead adds the multiline flag and calls modelText.replace() on the entire LF-normalized document. Thus [^/] can consume the newline between two KEEP/001 lines, allowing the replacement to collapse that pair to 001. This conclusively traces the original defect without executing code.
- **Independent reproduction and threshold evidence:** The supplied discussion records an independent reproduction on VS Code 1.96.3 and identifies a threshold around 19998 replacement lines. That matches the current editor's 19999-match branch, rather than a file-size or search.maxResults setting.
- **Existing discussion links are not canonicals:** https://github.com/microsoft/vscode/issues/496 is closed and concerns highlighting only the first 19999 matches. https://github.com/microsoft/vscode/issues/169017 is open but concerns search.maxResults not controlling editor highlighting. Neither owns the unexpected text modification tracked by the verified canonical.
- **Later comment has a distinct trigger:** The 2026-08-04 comment describes workspace search over a closed file with testing: ([^b\n]+), not the original editor Replace All threshold. Its quoted LLM explanation that large open files fall back to ripgrep is contradicted by _largeReplaceAll(), which uses JavaScript RegExp over the in-memory model. The closed-file observation remains useful evidence but does not establish a shared root cause.
