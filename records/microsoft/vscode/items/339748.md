# Issue #339748 — First tab in editor group to the side/bottom should not have border radius top left corner

[https://github.com/microsoft/vscode/issues/339748](https://github.com/microsoft/vscode/issues/339748)

## Summary

Real, source-confirmed CSS bug in the experimental Modern UI 'connected editor tabs' styling: the top-left corner radius is applied to every editor group's first tab unconditionally, not only to the group actually sitting in the grid's top-left position, exactly matching the reported screenshots.

## Change summary

When an editor group is split to the side or bottom, its first tab still shows a rounded top-left corner that should only appear on the group occupying the grid's actual top-left position.

## Best solution

Give editor-group-container elements position-awareness (a class set when a group sits in the grid's actual top-left slot, updated on layout/split changes) and gate the `border-top-left-radius` rule in connectedEditorTabs.css on that class instead of the blanket `.tab:first-child` selector.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/modernUI/browser/media/connectedEditorTabs.css`, `src/vs/workbench/browser/parts/editor/editorGroupView.ts`, `src/vs/workbench/browser/parts/editor/editorPart.ts`
- **Validation:** A test (likely in src/vs/workbench/test/browser/parts/editor/) asserting that only the editor-group-container occupying the grid's top-left slot carries the top-left-rounded class/state, and that a group split to the side or bottom does not.
- **Behavior:**

  > In the Modern UI 'connected editor tabs' style, only the editor group that is actually positioned at the top-left of the overall editor grid should show a rounded top-left corner on its first tab. Any other group — one split to the right, below, or elsewhere in the grid — should render that corner square/flat, since that corner is an internal seam, not the outer boundary of the editor area. Splitting, closing, or moving groups should keep exactly one group (the true top-left one) rounded at any time.
- **Trace:**

  > The rounding comes from `.tab:first-child:not(.connected-tab-upper-row) > .tab-fill { border-top-left-radius: var(--vscode-cornerRadius-large); }` in src/vs/workbench/contrib/modernUI/browser/media/connectedEditorTabs.css (~line 689), which matches the first tab of every `.editor-group-container`, not just the one in the grid's top-left corner. There is currently no DOM class or state exposing a group's position in the editor grid (checked editorGroupView.ts's classList toggles), so the fix needs new logic — likely driven by the editor part's grid/layout events — to mark the true top-left group, with the CSS selector updated to depend on that marker instead of `:first-child`. Boundary: do not change tab geometry for any group other than disambiguating this one corner, and don't regress the HC-theme or floating-panels variants of this same file.

## Evidence

- **source trace:** src/vs/workbench/contrib/modernUI/browser/media/connectedEditorTabs.css lines 689-695: `.tab:first-child:not(.connected-tab-upper-row) > .tab-fill { border-top-left-radius: var(--vscode-cornerRadius-large); ... }` applies to the first tab of EVERY `.editor-group-container`, with no conditional on the group's position within the editor grid.
- **no position tracking:** src/vs/workbench/browser/parts/editor/editorGroupView.ts only toggles classes like 'active', 'locked', 'empty' on the group element — there is no class or state reflecting whether a group is the grid's top-left group, so the CSS cannot currently distinguish groups by position.
- **feature context:** File is gated behind `.modern-ui-connected-editor-tabs` (workbench.experimental.modernUI's connected-tabs variant); issue author references the in-progress test plan item https://github.com/microsoft/vscode/issues/339385 for this same experimental surface.
