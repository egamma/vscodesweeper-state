# Issue #336072 — Cursor moves inconsistently

[https://github.com/microsoft/vscode/issues/336072](https://github.com/microsoft/vscode/issues/336072)

## Summary

The asymmetry is intentional: the default Ctrl+Left binding uses `WordNavigationType.WordStartFast`, which deliberately skips over a lone-separator 'word' followed by a regular character, while the default Ctrl+Right binding uses `WordNavigationType.WordEnd`, which has no such skip — a maintainer confirmed this exact asymmetric-navigation complaint is by design in a prior issue and pointed to the configurable alternate commands.

## Change summary

Ctrl+Right stops at every word boundary while Ctrl+Left (WordStartFast) skips some boundaries made of a single separator character, making left/right word navigation asymmetric.

## Best solution

Keep current default behavior (documented, longstanding, and already configurable); point the reporter to the explicit `cursorWordStartLeft`/`cursorWordStartRight` or `cursorWordEndLeft`/`cursorWordEndRight` commands if they want symmetric stops, as referenced in the VS Code 'Visual Studio style word navigation' update.

  > Thanks for the report. This is expected: the default Ctrl+Left binding (`cursorWordLeft`) intentionally skips over a lone-separator boundary followed by a regular character (see the `WordStartFast` handling in `cursorWordOperations.ts`), while Ctrl+Right (`cursorWordEndRight`) stops at every word end — so the two aren't meant to be symmetric out of the box. This exact asymmetric-navigation complaint came up before in https://github.com/microsoft/vscode/issues/242366, where a maintainer noted multiple word-navigation styles are supported and can be rebound (see https://code.visualstudio.com/updates/vMarch#_visual-studio-style-word-navigation-and-word-deletion). If you want cursor stops at every boundary in both directions, you can rebind Ctrl+Left/Right to the `cursorWordStartLeft`/`cursorWordStartRight` or `cursorWordEndLeft`/`cursorWordEndRight` commands instead of the defaults.
