# Issue #168045 — Git - git.rebasewhensync setting attempts a rebase when there is nothing to pull

[https://github.com/microsoft/vscode/issues/168045](https://github.com/microsoft/vscode/issues/168045)

## Summary

Keep open for the maintainer-acknowledged request to control merge preservation during rebase-based sync. Current source still exposes only a boolean rebase setting; the documented Git-config workaround does not provide that control while git.rebaseWhenSync remains enabled.

## Change summary

Allow rebase-based sync to preserve local merge topology instead of always selecting the plain rebase mode.

## Best solution

Provide an explicit, backward-compatible way to choose merge-preserving rebase for the built-in Git sync flow. Settle its scope and precedence relative to Git configuration and explicit rebase commands before implementation.

- **Behavior:**

  > Users who select merge-preserving rebase should be able to sync a branch containing local merge commits without flattening its merge topology. The original report covers a local merge when the upstream has nothing new to pull; a second user also reports repeated conflict resolution after merging main into a feature branch. Acceptance should verify the selected mode and resulting pushed history with both unchanged and advanced upstreams. Existing default behavior and users who intentionally choose ordinary rebase must remain compatible; preserving topology does not promise identical commit hashes or conflict-free replay.
- **Trace:**

  > git.sync and git._syncAll read the boolean git.rebaseWhenSync in extensions/git/src/commands.ts, while git.syncRebase explicitly passes true. Repository._sync in extensions/git/src/repository.ts forwards that value through _pullAndHandleTagConflict to Repository.pull in extensions/git/src/git.ts, where true appends `-r`; false omits the option and allows Git configuration to govern rebase behavior. The separate Repository.rebase method already accepts rebaseMerges, but sync does not call it. The reporter confirmed `git pull --rebase=merges` as the desired mode, and the maintainer accepted configurable merge handling in https://github.com/microsoft/vscode/issues/168045. Keep push behavior, tag-conflict handling, cancellation, and unrelated stack operations outside the change. The remaining uncertainty is which public configuration surface controls the mode and how it applies to explicit rebase commands and native Git configuration.
- **Open decisions:**
  - Should merge-preserving mode apply only to setting-driven sync, or also to explicit Sync (Rebase) and Pull (Rebase) commands?
  - Should users select merge preservation through an expanded git.rebaseWhenSync setting, a separate rebase-mode setting, or native Git configuration, and what precedence should apply when these disagree?
