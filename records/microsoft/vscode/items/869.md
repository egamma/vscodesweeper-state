# Issue #869 — Exclude all files except for...

[https://github.com/microsoft/vscode/issues/869](https://github.com/microsoft/vscode/issues/869)

## Summary

This remains a valid, highly supported feature request: current `files.exclude` expressions still cannot re-include paths hidden by a broader pattern. The On Deck milestone and 653 upvotes support retaining it, while the related design issue is younger and cannot serve as the canonical duplicate for this re-reviewed item.

## Change summary

Allow `files.exclude` to hide a broad set of paths while preserving explicitly selected files or directories.

## Best solution

Define exception semantics for `files.exclude` and implement them consistently in the shared glob-expression layer so Explorer, search, and other consumers do not disagree. Preserve existing configurations while supporting concise broad-exclude/specific-include cases.

## Plan brief

- **Likely files:** `src/vs/base/common/glob.ts`, `src/vs/base/test/common/glob.test.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `src/vs/workbench/services/search/common/fileSearchManager.ts`
- **Validation:** Add targeted glob-expression tests in `src/vs/base/test/common/glob.test.ts` covering a broad exclusion with directory and file exceptions, conflicting patterns, and existing boolean-disable behavior; add an Explorer filter test proving excluded siblings remain hidden while the excepted path and its traversable ancestors remain visible.
- **Behavior:**

  > `files.exclude` must support hiding a broad path set while retaining explicitly excepted files or directories, including the original hide-everything-except-one-folder case. Excepted descendants must remain reachable in Explorer rather than disappearing because an ancestor matched the broad exclusion. Existing configurations without exceptions must retain their current behavior, and equivalent exclude expressions must not produce contradictory results across Explorer and search. Acceptance should cover directory exceptions, individual-file exceptions, conflicting patterns, and workspace-scoped settings.
- **Trace:**

  > `FILES_EXCLUDE_CONFIG` is registered in `src/vs/workbench/contrib/files/browser/files.contribution.ts` as an object whose values enable or disable individual patterns. `FilesFilter.updateConfiguration` in `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts` passes that object to `glob.parse`; `FilesFilter.isVisible` then hides a resource whenever the parsed expression matches it. In `src/vs/base/common/glob.ts`, `parseExpressionPattern` drops false-valued patterns and `parsedExpression` combines enabled patterns as positive matches, so a false entry cannot reverse a broader true match. Search also derives provider exclusions from these expressions in `src/vs/workbench/services/search/common/fileSearchManager.ts`, which is why maintainers rejected an Explorer-only implementation in https://github.com/microsoft/vscode/pull/152225. The boundary is the exclude-expression contract and its consumers: preserve ordinary glob matching, sibling clauses, existing false-as-disabled configurations, and `.gitignore` behavior. https://github.com/microsoft/vscode/issues/134415 contains the unresolved semantics discussion but is younger than this issue.
- **Open decisions:**
  - Should exceptions use ordered `.gitignore`-style precedence, or order-independent two-pass semantics in which exceptions override all matching exclusions?
  - Should the public configuration contract use leading-`!` patterns, a separate include/exception field, or another representation that remains stable when settings from multiple scopes are merged?
  - Should exception semantics apply to every shared `IExpression` consumer, or only to exclusion settings such as `files.exclude` and `search.exclude`?

## Evidence

- **current source gap:** `src/vs/base/common/glob.ts` still defines `IExpression` as pattern-to-boolean/sibling-clause entries; `parseExpressionPattern` treats `false` as a disabled pattern (`NULL`), while `parsedExpression` combines enabled patterns as matches. Thus `"**/*": true` hides the path and `"**/Scripts": false` cannot re-include it.
- **Explorer code path:** `FilesFilter.updateConfiguration` in `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts` parses `files.exclude` directly with `glob.parse`, and `isVisible` hides any item matched by that expression. No separate include or exception pass exists on current main.
- **configuration contract:** `src/vs/workbench/contrib/files/browser/files.contribution.ts` documents boolean values only as enabling or disabling each pattern; it exposes no first-class exception/include mechanism for `files.exclude`.
- **related design issue:** https://github.com/microsoft/vscode/issues/134415 is open and explicitly discusses leading-`!` expression semantics intended to cover https://github.com/microsoft/vscode/issues/869, including unresolved ordering and conflicting-pattern behavior. It was created in 2021, later than this 2015 re-reviewed issue, so it does not meet the stronger canonical-duplicate bar.
- **prior implementation attempt:** https://github.com/microsoft/vscode/pull/152225 proposed negated `files.exclude` patterns but was closed without merging after maintainers noted that the behavior belongs in the shared glob parser and must also account for search consumers.
- **existing workarounds:** The discussion documents character-class patterns, workspace-folder restructuring, generators, and extensions, but these either become impractical for longer names or alter workspace structure; none provides the requested concise exception semantics in `files.exclude`.
- **demand and accepted status:** The issue has 653 community upvotes, remains active through 2026, carries `feature-request`, and is parked in the On Deck milestone.
