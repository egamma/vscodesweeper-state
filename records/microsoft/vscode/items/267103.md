# Issue #267103 — Copilot context-aware of recent file changes and edits

[https://github.com/microsoft/vscode/issues/267103](https://github.com/microsoft/vscode/issues/267103)

## Summary

A real gap remains: current Chat can inspect the repository's SCM changes on demand, but it does not offer configurable, automatic context from the user's recent editor edits. Maintainers explicitly classified this request as `feature-request` / `chat-agent` and placed it in Backlog, so it should remain open for design.

## Change summary

Add an optional Copilot Chat context source containing the last N files or edits made across the workspace.

## Best solution

Define an opt-in recent-edit context policy for Chat that provides useful multi-file development context while making inclusion visible and bounding history, token usage, persistence, and sensitive-content exposure. Reuse the existing edit-history tracking where appropriate without changing inline-completion behavior.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/inlineEdits/common/workspaceEditTracker/workspaceDocumentEditTracker.ts`, `extensions/copilot/src/extension/prompt/vscode-node/workspaceEditRecorder.ts`, `extensions/copilot/src/extension/tools/node/scmChangesTool.ts`
- **Validation:** The plan should end with unit coverage showing that the selected recent-edit policy includes the expected files/edits in Chat context, respects its configured limit and reset boundary, and leaves the existing `get_changed_files` and inline-edit history behavior unchanged; also manually verify the included context is visible in a Chat request.
- **Behavior:**

  > When the recent-edit context option is enabled, Copilot Chat can use a bounded history of edits made across workspace files without requiring those files to remain open or be attached manually. The user can tell that this context is being included and can disable or clear it. Selection obeys the chosen history limit and lifetime, and disabled behavior remains unchanged. Existing explicit attachments and the `get_changed_files` tool continue to work independently.
- **Trace:**

  > Current main exposes SCM state through `GetScmChangesTool` in `extensions/copilot/src/extension/tools/node/scmChangesTool.ts`, whose tool ID is `get_changed_files`; it reads repository changes but has no temporal recent-edit model. `WorkspaceDocumentEditHistory` in `extensions/copilot/src/platform/inlineEdits/common/workspaceEditTracker/workspaceDocumentEditTracker.ts` tracks up to a configured number of editor edits and keeps a FIFO of recently edited documents. `WorkspaceEditRecorder` consumes that tracker, but `RequestLoggerImpl` uses its output only for tool-call tracing, not request context. The plan must identify the Chat request-context integration point and preserve existing inline-edit diagnostics, request logging, explicit attachments, and SCM-tool behavior. Do not silently send an unbounded workspace edit history.
- **Open decisions:**
  - Should the option select the last N edit operations, the last N edited files, or files edited within a time window?
  - Should recent-edit context be automatically included on every Chat turn when enabled, or presented as suggested context that the user confirms?
  - What event clears the history: sending a turn, starting a new chat, changing workspace or branch, reloading the window, or an explicit user action?
  - Should unsaved edits, saved non-Git files, and Git working-tree changes all participate, and how should overlapping SCM and edit-history context be deduplicated?
  - What UI disclosure and token-budget limit are required so users can see and control which recent edits are sent?
