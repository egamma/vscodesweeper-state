# Issue #212679 — Context menus make webview on the side steal focus

[https://github.com/microsoft/vscode/issues/212679](https://github.com/microsoft/vscode/issues/212679)

## Summary

Keep open: the report provides sufficient steps to retest incorrect editor-group activation when opening menus beside a webview. Webview clipboard-focus handling has changed since the report, but the inspected changes do not establish that this separate focus-stealing behavior is fixed.

## Change summary

Opening a context menu outside a neighboring webview unexpectedly activates the webview's editor group, moving title actions and directing navigation into the wrong pane.

## Best solution

Preserve the originating editor group's activation when menus open outside a webview, while retaining webview clipboard commands and focus restoration for menus opened inside it. Reproduce the supplied Markdown-preview scenario first, then isolate the interaction between webview focus polling and workbench menu handling.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/webview/browser/pre/index.html`, `src/vs/workbench/contrib/webview/browser/webviewElement.ts`, `src/vs/workbench/contrib/webview/browser/webviewService.ts`, `src/vs/workbench/contrib/webview/test/browser/webviewElement.test.ts`
- **Validation:** On Linux, open a Markdown editor with its preview beside it and activate the text editor. Open and dismiss editor, sidebar, and title-bar menus; verify the preview does not become active, title actions do not jump, and Go to Definition or search-result navigation uses the intended editor group. Also verify copy/cut/paste from a webview's own context menu still target its focused input. Capture the isolated focus transition in an automated regression test once reproduced.
- **Behavior:**

  > Opening a context menu outside a visible webview must not activate that webview or change the active editor group. With a Markdown editor and preview side by side, editor title actions must stay associated with the intended group, and navigation must not replace the preview because it acquired focus unexpectedly. Menus opened inside a webview must continue to support clipboard operations and appropriate focus restoration.
- **Trace:**

  > The current webview shell polls document.hasFocus() and the vscode-context-menu-visible class in trackFocus in src/vs/workbench/contrib/webview/browser/pre/index.html. Its focus messages reach WebviewElement.handleFocusChange, and WebviewService.registerNewWebview updates activeWebview from the resulting events. The related report https://github.com/microsoft/vscode/issues/210108 bisected the regression to https://github.com/microsoft/vscode/pull/206529, which introduced the context-menu-visible focus alternative. Current WebviewElement sends visible:true for its own context menu and sends visible:false when the shared context-menu service hides a menu; that alone does not conclusively explain the outside-menu trigger. The recent clipboard restoration commit f5f64f08ab0e3ba27b764a1f65696d3c4bb233c7 addresses a different path. First reproduce and observe the focus transition; preserve webview-owned menu and clipboard behavior rather than treating removal of that functionality as a fix.
