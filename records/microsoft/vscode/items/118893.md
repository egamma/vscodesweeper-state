# Issue #118893 — Using key commands to scroll to top or bottom of document does not incorporate editor.paddingTop and editor.paddingButtom

[https://github.com/microsoft/vscode/issues/118893](https://github.com/microsoft/vscode/issues/118893)

## Summary

The bug remains present on current main: the buffer-boundary cursor commands minimally reveal the first or last line while excluding the configured editor padding from the visible range. The issue is already correctly routed to editor commands and should remain open.

## Change summary

Make the cursor-top and cursor-bottom keyboard commands preserve the configured space above the first line and below the last line.

## Best solution

Make buffer-boundary navigation reveal the corresponding document-edge padding while preserving existing minimal-reveal behavior for ordinary cursor movement and unrelated reveal APIs.

## Plan brief

- **Likely files:** `src/vs/editor/browser/coreCommands.ts`, `src/vs/editor/common/viewModel/viewModelImpl.ts`, `src/vs/editor/browser/viewParts/viewLines/viewLines.ts`
- **Validation:** Add and run a targeted editor browser test that configures nonzero top and bottom padding, executes cursorTop and cursorBottom from outside the destination viewport, and asserts the resulting scroll positions retain the corresponding padding; also verify ordinary minimal cursor reveals are unchanged.
- **Behavior:**

  > With nonzero editor top and bottom padding, invoking cursorTop must move the cursor to the first line and leave the configured top gap visible. Invoking cursorBottom must move it to the final line and leave the configured bottom gap visible. Selection variants should behave consistently, while normal cursor movement and reveal operations away from document boundaries must retain their current scrolling behavior.
- **Trace:**

  > TopCommand and BottomCommand in src/vs/editor/browser/coreCommands.ts move the cursor and call ViewModel.revealAllCursors with minimal reveal. ViewModel.revealAllCursors in src/vs/editor/common/viewModel/viewModelImpl.ts emits a Simple reveal request. ViewLines._computeScrollTopToRevealRange in src/vs/editor/browser/viewParts/viewLines/viewLines.ts computes the first-line box after top padding and the last-line box before bottom padding, then _computeMinimumScrolling aligns that box with the viewport edge, excluding the padding. The boundary is buffer-edge navigation: generic reveal behavior for ordinary cursor movement, API reveals, multi-cursor handling, scrollBeyondLastLine, and cursorSurroundingLines must not regress. The uncertainty is whether this should be expressed by the boundary commands or by narrowly scoped semantics in the shared reveal path.
- **Open decisions:**
  - Should buffer-edge commands request dedicated top/bottom reveal semantics, or should the shared minimal-reveal calculation recognize document-edge padding?
  - Should cursorTopSelect and cursorBottomSelect receive exactly the same padding-aware behavior?
  - How should bottom padding interact with editor.scrollBeyondLastLine so the command shows the configured gap without scrolling an additional viewport beyond the document?

## Evidence

- **setting contract:** src/vs/editor/common/config/editorOptions.ts defines editor.padding.top and editor.padding.bottom as the space between the editor edges and the first and last lines.
- **command path:** src/vs/editor/browser/coreCommands.ts implements cursorTop and cursorBottom through TopCommand and BottomCommand; both move to the buffer boundary and call viewModel.revealAllCursors(..., true).
- **source reproduction:** src/vs/editor/common/viewModel/viewModelImpl.ts translates that call into a minimal VerticalRevealType.Simple request. In src/vs/editor/browser/viewParts/viewLines/viewLines.ts, the first-line box starts after top padding and the last-line box ends before bottom padding; minimal scrolling therefore places those line boxes at the viewport edge and leaves the configured padding outside the viewport.
- **canonical search:** The suggested https://github.com/microsoft/vscode/issues/63663 is open but requests padding for centered editor layout and does not own the cursor-command behavior. Searches for cursorTop, cursorBottom, and editor padding found no open canonical covering this defect.
