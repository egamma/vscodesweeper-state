# Issue #340336 — Sessions: orphaned "Session" entries load, then disappear when opened

[https://github.com/microsoft/vscode/issues/340336](https://github.com/microsoft/vscode/issues/340336)

## Summary

Fresh, well-diagnosed report with log evidence and code pointers; current main confirms the traced behavior — a provisional session whose provider backing never materializes is silently retracted with no explanation to the user — and no canonical issue already owns this specific UX gap, so this should stay open for design/implementation.

## Change summary

An orphaned 'Session' entry appears in the sessions list, loads for a few seconds when clicked, then silently vanishes instead of opening or explaining the failure.

## Best solution

When a provisional session proves to have no provider backing and gets retracted after a failed open attempt, surface an explanation (toast/notification or an error-state entry) instead of silently removing it; the retraction path itself (agentHostStateManager.ts's `retractSurfacedSession`) and the restore failure (agentService.ts's `AHP_SESSION_NOT_FOUND: Session was never created on the backend`) are already traced — the remaining open question is how to communicate it client-side.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentHostStateManager.ts`, `src/vs/platform/agentHost/node/agentService.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionListStore.ts`
- **Validation:** A manual or automated check that, when a visible session fails to open because its provider backing never materialized, the user sees an explanatory message (not just the entry vanishing) — exact surfacing mechanism to be decided.
- **Behavior:**

  > A session entry that is already visible in the sessions list, when clicked, should either open normally or — if the host discovers it has no provider backing — tell the user why it can't be opened. It must not just silently disappear from the list after a multi-second load, leaving the user with no feedback. No conversation data is lost either way; this is purely about user-facing communication of the failure.
- **Trace:**

  > The failure path is: client subscribes to restore the session; agentService.ts throws `AHP_SESSION_NOT_FOUND: Session was never created on the backend` (~line 8865) because the session is still marked provisional once the provider catalogue becomes readable; this leads a caller (around agentService.ts lines ~4733/4798) to call `retractSurfacedSession` in agentHostStateManager.ts (~line 1050), which deletes the summary and fires `root/sessionRemoved` with no reason attached; the client (baseAgentHostSessionsProvider.ts `_handleSessionRemoved`, agentHostSessionListStore.ts's `root/sessionRemoved` handling) just removes the row. This exact sequence (restoredState undefined, listed:false, no explanation) is already asserted by an existing test in agentService.test.ts (~line 29538-29567), so it's the current intended behavior for the retraction half — the gap is purely in user communication. Do not touch the idle-provisional exclusion (#321269's fix, already in `_isIdleProvisional`) or the underlying reason the placeholder got exposed before catalogue validation — the reporter themselves could not establish why the backing was absent, and that root cause is out of scope for this report.
- **Open decisions:**
  - Should the client show a toast/notification explaining the failure, or keep the entry visible with an inline error/placeholder state the user can dismiss?
  - Should `root/sessionRemoved` (or a new notification) carry a reason/diagnostic string for this case, or should the client infer it purely from the preceding restore error?
  - Does this orphaned-session case warrant a 'Mark Done'-style action, as hinted by the reporter noting none was observed?

## Evidence

- **retraction is silent by design:** `retractSurfacedSession` in src/vs/platform/agentHost/node/agentHostStateManager.ts (line ~1050) only deletes the summary and fires `root/sessionRemoved`; it carries no reason/explanation payload for the client.
- **matching restore failure:** src/vs/platform/agentHost/node/agentService.ts line ~8865-8866 throws `AHP_SESSION_NOT_FOUND: Session was never created on the backend` for a still-provisional session once the catalogue is readable, which matches the reporter's captured protocol error -32001.
- **existing test encodes exactly this behavior:** src/vs/platform/agentHost/test/node/agentService.test.ts (~line 29538-29567) asserts a restore in this state yields `restoredState: undefined` and `listed: false` after the retraction — i.e. the session disappears from the list with no surfaced explanation, confirming the current design matches the report.
- **client never surfaces a reason:** src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts `_handleSessionRemoved` (line ~8125) and agentHostSessionListStore.ts's `root/sessionRemoved` handling (line ~354) just drop the entry from the local list; neither path shows the user why.
- **related but distinct prior fix:** The code comment at agentHostStateManager.ts ~line 695-699 cites #321269 for excluding *idle* provisional sessions from the list — already implemented — which is a different, narrower case than this report's already-surfaced, non-idle provisional entry failing on open.
