# Issue #227697 — LSP DocumentColor Refresh Request

[https://github.com/microsoft/vscode/issues/227697](https://github.com/microsoft/vscode/issues/227697)

## Summary

The refresh capability remains missing from the current API and editor plumbing. Keep this accepted, team-authored request open: the maintainer explicitly identified VS Code API support as the prerequisite for LSP support, and the linked XAML request remains blocked on it.

## Change summary

Allow language servers to refresh document color swatches after semantic initialization or changes to resources in other documents.

## Best solution

Provide an extension-facing document-color invalidation contract that refreshes affected editors without requiring edits to those documents, then coordinate the corresponding LSP request. Settle the refresh scope with the API owners before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`, `src/vs/editor/contrib/colorPicker/browser/colorDetector.ts`
- **Validation:** The plan should establish an executable extension-host/editor check using a color provider whose semantic result changes without a document edit: after invalidation, the visible swatch must update. Cover initially unavailable semantic colors and an externally changed resource, while preserving ordinary edit-driven refresh and ensuring disposed providers cannot trigger updates.
- **Behavior:**

  > A document color provider can report that its semantic color results have changed without modifying the document text. A visible XAML document must acquire resource-based swatches when semantic initialization completes and update them when the referenced color changes in another document. Existing literal-color decorations and edit-driven refresh must continue to work. Acceptance must exercise the provider-to-editor refresh path, not merely a direct provider call.
- **Trace:**

  > DocumentColorProvider in src/vscode-dts/vscode.d.ts and src/vs/editor/common/languages.ts exposes no invalidation event. ExtHostLanguageFeatures.registerColorProvider and MainThreadLanguageFeatures.$registerDocumentColorProvider forward color queries but no refresh signal; the neighboring folding-range provider registration demonstrates an existing event bridge. ColorDetector.updateColors in src/vs/editor/contrib/colorPicker/browser/colorDetector.ts listens for current-model content changes, while its constructor handles model, configuration, and provider registry changes. None represents changed semantic results from an already registered provider. The missing capability is confirmed by source inspection, not runtime execution. Preserve normal editing, decoration enablement, cancellation, and provider disposal behavior; changing XAML semantic resolution itself is outside this repository's part of the work. The consumer at https://github.com/dotnet/vscode-csharp/issues/7515 distinguishes refreshing the active document after initialization from refreshing other documents after a resource edit, leaving the public refresh granularity to settle.
- **Open decisions:**
  - Should document-color invalidation refresh every document matched by the provider, like a provider-wide folding-range event, or allow targeted documents so resource changes can avoid redundantly refreshing the edited document?
