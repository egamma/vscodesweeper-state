# Issue #243779 — Checkbox text should be click-able

[https://github.com/microsoft/vscode/issues/243779](https://github.com/microsoft/vscode/issues/243779)

## Summary

The common checkbox widget still renders only the checkbox control, leaving each caller to implement label activation separately. This team-authored Backlog request remains valid and should stay open for a consistent shared UX.

## Change summary

Make text associated with VS Code checkboxes clickable so it toggles the corresponding checkbox.

## Best solution

Provide an accessible shared checkbox-and-label interaction in the base UI and adopt it where text is semantically the checkbox label, while preserving independent actions such as issue-reporter disclosure links.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/toggle/toggle.ts`, `src/vs/base/browser/ui/toggle/toggle.css`, `src/vs/workbench/contrib/issue/browser/issueReporterOverlay.ts`, `src/vs/workbench/test/browser/componentFixtures/baseUI.fixture.ts`
- **Validation:** Add a browser UI test that clicks visible checkbox text and asserts one state-change event and updated checked state, while clicking an independent nested action does not toggle the checkbox; retain keyboard activation coverage.
- **Behavior:**

  > Visible text that semantically labels a checkbox should activate the same control when clicked or tapped. The checkbox must remain keyboard accessible and expose one accessible name, and one label activation must produce exactly one state change. Text or links serving a separate action, such as expanding issue-reporter diagnostic details, must retain that independent behavior.
- **Trace:**

  > Checkbox in src/vs/base/browser/ui/toggle/toggle.ts wraps an icon-only Toggle and uses its title only for hover and aria-label content; it has no visible label element or label activation contract. Callers therefore duplicate handling, as documented at https://github.com/microsoft/vscode/issues/243779#issuecomment-2731987333 and currently in chat-status settings. The older issue reporter in src/vs/workbench/contrib/issue/browser/issueReporterPage.ts uses native input/label associations, while src/vs/workbench/contrib/issue/browser/issueReporterOverlay.ts separates each custom Checkbox from text whose current action is disclosure. The boundary is checkbox labeling and activation: do not change disclosure semantics, checkbox state ownership, or unrelated Toggle consumers.
- **Open decisions:**
  - Should visible clickable text become the default contract whenever Checkbox receives a title, or should callers explicitly opt into a composite checkbox-and-label control so existing adjacent text can retain separate actions?

## Evidence

- **current base widget:** src/vs/base/browser/ui/toggle/toggle.ts defines Checkbox as an icon-only Toggle whose title supplies hover and aria-label text; it does not render or activate a visible label.
- **caller workaround:** The maintainer comment at https://github.com/microsoft/vscode/issues/243779#issuecomment-2731987333 identifies duplicated caller-side click handling and suggests a shared base widget.
- **current issue reporter:** src/vs/workbench/contrib/issue/browser/issueReporterOverlay.ts creates Checkbox controls separately from review-diag-heading-title and review-diag-title; the latter title area is assigned disclosure behavior rather than checkbox activation.
- **existing partial capability:** src/vs/workbench/contrib/issue/browser/issueReporterPage.ts uses native input/label associations for the older reporter markup, but this does not provide the requested behavior to consumers of the shared custom Checkbox widget.
- **canonical search:** The older open candidate https://github.com/microsoft/vscode/issues/163109 concerns enabling checkboxes in the Merge Editor, not clicking checkbox labels, so it does not own the same observable request.
