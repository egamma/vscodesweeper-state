# Issue #30065 — Language services should be able to provide debug console IntelliSense

[https://github.com/microsoft/vscode/issues/30065](https://github.com/microsoft/vscode/issues/30065)

## Summary

This team-authored Backlog request remains necessary: current main routes Debug Console completions exclusively through the debug adapter and prevents ordinary extension-host language providers from seeing the REPL input model. It is the canonical request for this capability and should stay open for API and data-flow design.

## Change summary

Allow opted-in language services to provide IntelliSense for Debug Console input using the active stack frame's source context.

## Best solution

Define a core extension contract that gives an opted-in language service the Debug Console input plus active source/frame context, while preserving runtime-aware debug-adapter completions and establishing how results from both sources are combined.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/repl.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`, `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/contrib/debug/test/browser/repl.test.ts`
- **Validation:** The plan should end with an automated Debug Console completion test proving an opted-in language provider receives REPL text and active source/frame context, alongside coverage that existing DAP completions and history suggestions retain their defined behavior.
- **Behavior:**

  > A language service can explicitly opt into providing completions for Debug Console input. When invoked, it receives enough source and active-stack-frame context to compute the same static-language suggestions it would provide near the paused source location. Debug adapters can continue supplying runtime-aware completions, and the chosen combination or precedence behavior is deterministic. Existing adapters and language services that do not opt in remain unchanged.
- **Trace:**

  > The Debug Console input is the `debug:replinput` model created in src/vs/workbench/contrib/debug/browser/repl.ts by `Repl`; `setMode()` assigns the active editor's language, but the model is marked as a simple-widget model and therefore is not synchronized to the extension host. `Repl.onDidFocusSession()` currently registers an internal provider only for sessions advertising `supportsCompletionsRequest`, and that provider calls `IDebugSession.completions`, which routes directly to DAP. Ordinary completion providers registered through src/vs/workbench/api/common/extHostLanguageFeatures.ts cannot participate because LanguageFeatureRegistry scoring rejects unsynchronized models. The boundary is Debug Console completion routing and any required extension contract; normal editor completion behavior, DAP completion compatibility, evaluation, and history navigation must remain unchanged. The related Python request https://github.com/microsoft/vscode/issues/235574 is a newer duplicate, not a competing canonical.
- **Open decisions:**
  - Should the public contract directly invoke an opted-in language provider with explicit paused-frame context, or establish a debugger-to-language-service communication channel that keeps VS Code out of the language-specific request?
  - When both the language service and debug adapter provide completions, should VS Code merge their results, prefer one source, or make the choice an explicit capability?
  - What source URI, position, and virtual-document semantics should language providers observe for Debug Console input, especially when the selected frame differs from the active editor?

## Evidence

- **current completion path:** On current main, src/vs/workbench/contrib/debug/browser/repl.ts:262-329 registers the Debug Console completion provider only when `supportsCompletionsRequest` is set and obtains suggestions solely through `session.completions(...)`, which sends the DAP `completions` request.
- **language-provider boundary:** src/vs/workbench/contrib/debug/browser/repl.ts:210 creates the `debug:replinput` model with `isForSimpleWidget: true`; src/vs/editor/common/model.ts:1624-1627 excludes such models from synchronization, and src/vs/editor/common/languageSelector.ts:35-66 gives unsynchronized models no match for ordinary extension-host language providers.
- **multiple language ecosystems:** The issue covers C#, and https://github.com/microsoft/vscode/issues/30065#issuecomment-896520764 confirms the same need for Ballerina. The newer Python request https://github.com/microsoft/vscode/issues/235574 was closed as a duplicate of this issue, making this the established canonical.
- **maintainer design discussion:** https://github.com/microsoft/vscode/issues/30065#issuecomment-312705504 supports the use case but proposes debugger-side language-service integration, while https://github.com/microsoft/vscode/issues/30065#issuecomment-312710638 explains why that coupling is unsuitable for some adapters and proposes a reverse communication channel.
- **no competing implementation:** No open microsoft/vscode pull request referencing issue 30065 was found, and no older open issue with the same reporter-observable request was identified.
