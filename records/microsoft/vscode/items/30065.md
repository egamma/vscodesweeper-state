# Issue #30065 — Language services should be able to provide debug console IntelliSense

[https://github.com/microsoft/vscode/issues/30065](https://github.com/microsoft/vscode/issues/30065)

## Summary

Keep open: current Debug Console completion still delegates to the debug adapter, rather than providing the requested language-service integration. Existing extension APIs expose useful building blocks, but do not establish the requested opt-in contract; this team-authored, accepted request remains necessary.

## Change summary

Allow language services to provide Debug Console IntelliSense using the selected stack frame's source context and the console's current input.

## Best solution

Define an opt-in language-service completion contract that supports statically typed languages without requiring their debug adapters to integrate with the language server. Preserve existing adapter-based completion for languages that do not opt in, and settle how static and runtime suggestions should coexist.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/repl.ts`, `src/vs/workbench/contrib/debug/browser/debugSession.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** End the plan with an executable extension-host or Debug Console integration check: pause in a statically typed source frame, request console completions from an opted-in language provider, verify source-frame context and console text/position, switch frames and verify context updates, then verify a non-opted-in debugger retains its existing adapter completions.
- **Behavior:**

  > An opted-in language service can supply Debug Console completions using the selected stack frame's source context together with the console input and cursor position. This must not require coupling an IDE-neutral debug adapter to the language server. Switching frames or sessions must update the context, while non-opted-in languages retain existing adapter-based behavior. Acceptance must cover both language-service completion and the unchanged adapter fallback.
- **Trace:**

  > Repl.onDidFocusSession in src/vs/workbench/contrib/debug/browser/repl.ts registers a debug-scheme completion provider gated by supportsCompletionsRequest and calls session.completions with the focused frame and console input. DebugSession.completions in src/vs/workbench/contrib/debug/browser/debugSession.ts forwards that request to the adapter. Repl.setMode follows the active editor's language, which is distinct from providing the selected frame's source context. The public API already exposes languages.registerCompletionItemProvider and debug.activeStackItem in src/vscode-dts/vscode.d.ts, so planning should account for those capabilities rather than assume no integration primitives exist. The uncertainty begins at the console-specific public contract and the relationship between language-service and adapter results. Preserve existing adapter behavior for non-opted-in languages and avoid language-specific implementation in core. The discussion in https://github.com/microsoft/vscode/issues/30065 establishes adapter/language-service separation as a requirement; https://github.com/microsoft/vscode/issues/235574 contributes documentation and signature-related use cases without proving those capabilities are already delivered.
- **Open decisions:**
  - Should opted-in language-service suggestions replace adapter suggestions, as originally proposed, or coexist with runtime suggestions?
  - Should the supported extension contract directly deliver console input and selected-frame source context to a completion provider, or expose a bridge through which an adapter delegates to the language service?
