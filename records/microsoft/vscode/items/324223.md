# Issue #324223 — Performance loss in the VS Code `fs` abstraction that potentionally hits all extensions

[https://github.com/microsoft/vscode/issues/324223](https://github.com/microsoft/vscode/issues/324223)

## Summary

The performance defect remains present on current main, but the open linked PR directly addresses it. Keep the issue open while https://github.com/microsoft/vscode/pull/324070 is reviewed and either landed or closed.

## Change summary

Local `workspace.fs` fast-path operations unnecessarily await a renderer RPC on every call, substantially slowing extensions that perform many small filesystem operations.

## Best solution

Review and land https://github.com/microsoft/vscode/pull/324070 after validating that activation is cached only after success and reset when the provider is disposed, with regression coverage for repeated fast-path operations.

## Evidence

- **current source:** Current main in src/vs/workbench/api/common/extHostFileSystemConsumer.ts:46,68,82,96,111,126 awaits `_proxy.$ensureActivation(uri.scheme)` before every shortcut operation, so each stat, readDirectory, createDirectory, readFile, writeFile, and delete crosses the RPC boundary.
- **benchmark:** The reporter supplied a dedicated reproduction extension and measurements showing direct operations from 1.7x to 84x faster, with the largest differences for low-latency virtual filesystem operations.
- **open fixing PR:** https://github.com/microsoft/vscode/pull/324070 is open, contains `Fixes #324223`, and changes the same file to cache the per-provider activation promise rather than issuing the renderer RPC for every operation.
