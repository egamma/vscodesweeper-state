# Issue #336866 — Allow configuring the default Changes view changeset

[https://github.com/microsoft/vscode/issues/336866](https://github.com/microsoft/vscode/issues/336866)

## Summary

Team-authored feature request (author is a MEMBER, which bars judgment closes anyway) that stays open on its merits: confirmed via the checkout that no such setting exists today, and a second commenter adds a real perf-driven use case, so there is genuine unresolved demand and no canonical issue owns it.

## Change summary

Add a setting (or persistence) to control which changeset (branch/uncommitted/session/last-turn) the Agents Changes view shows by default, instead of always resetting to the provider default.

## Best solution

Add an `agents.changes.defaultChangeset`-style setting honored by `findDefaultChangeset` in src/vs/sessions/contrib/changes/common/changesViewService.ts and the selection logic in the browser changesViewService.ts, with a maintainer decision on whether it's an explicit setting, a remembered last-selection, or both (and whether it also addresses the raised large-diff performance concern).

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/changes/common/changesViewService.ts`, `src/vs/sessions/contrib/changes/browser/changesViewService.ts`, `src/vs/sessions/contrib/changes/browser/changes.contribution.ts`
- **Validation:** A changesViewService test asserting the configured default changeset id is selected on view init and again after switching to a session where the prior selection doesn't apply.
- **Behavior:**

  > The Agents Changes view should let the user control which changeset (branch, uncommitted, session, last-turn) is shown by default, so it doesn't silently reset to a provider default (e.g. Branch Changes) every time the active session/chat changes. If the configured/remembered changeset is unavailable for the current provider, fall back to that provider's current default without erroring.
- **Trace:**

  > `findDefaultChangeset()` in src/vs/sessions/contrib/changes/common/changesViewService.ts:35 currently always resolves to the changeset marked `isDefault` (or first enabled); the browser-side ChangesViewService (src/vs/sessions/contrib/changes/browser/changesViewService.ts) tracks a `preferredChangesetId` and per-chat `selectedChangesetId` in `ISessionChangesetSelections`, but nothing persists a cross-session default. Settings for this view are registered in src/vs/sessions/contrib/changes/browser/changes.contribution.ts (currently only `sessions.changes.openSingleFileDiff`). Where the uncertainty starts: whether the fix is a new setting, a remembered last-selection (workspace/global storage), a workspace-type-aware default (uncommitted for in-place sessions), or some combination — and whether the large-diff responsiveness complaint from the second commenter is a separate issue or part of this one.
- **Open decisions:**
  - Should this be an explicit `agents.changes.defaultChangeset`-style setting (Settings Sync-friendly), an automatically remembered last-selected changeset, or both?
  - Should the default vary by context (e.g. uncommitted changes for sessions run in the main workspace vs. a dedicated worktree/branch)?
  - Is the large-diff/perf protection request (lazy loading or a size cap before rendering a huge branch diff) in scope for this issue, or should it be tracked separately?

## Evidence
