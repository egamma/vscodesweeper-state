# Issue #153527 — Edit sessions - staged files not maintained

[https://github.com/microsoft/vscode/issues/153527](https://github.com/microsoft/vscode/issues/153527)

## Summary

Keep open: Cloud Changes still transfers working-tree contents without preserving Git staging state. This team-authored, accepted Backlog request remains a real capability gap, and no qualifying canonical or concrete fix was found.

## Change summary

Preserve the distinction between staged and unstaged changes when storing and restoring an edit session on another machine.

## Best solution

Extend Cloud Changes to preserve Git staging state across machines without changing unstaged edits or staging additional content. Establish the treatment of partially staged files and existing destination index changes before implementation.

Add storage/restore coverage to the Edit session sync suite and verify legacy payloads still restore their file contents.
- **Behavior:**

  > Storing changes on one machine and restoring them on another currently preserves edited file contents but loses which changes were staged. For the reported case, the previously staged file should appear staged after restoration, while the other edited files remain unstaged. Acceptance compares both working-tree and staged diffs between equivalent source and destination repositories. Partially staged files and pre-existing destination staging require an explicit contract; restoration must not silently stage additional edits.
- **Trace:**

  > In src/vs/workbench/contrib/editSessions/browser/editSessions.contribution.ts, getChangedResources flattens SCM groups into URIs, and storeEditSession captures only filesystem contents or deletions. Change and Folder in common/editSessions.ts cannot represent staging state, and resumeEditSession writes or deletes working-tree files without reconstructing an index. WorkspaceStateSynchroniser transfers workspace storage, not repository index contents. GitEditSessionIdentityProvider in extensions/git/src/editSessionIdentityProvider.ts handles repository identity and publication only. These paths explain the missing capability in https://github.com/microsoft/vscode/issues/153527; the remaining design uncertainty is the staging-transfer contract and its integration with Git. Preserve legacy session restoration, existing conflict safeguards, and non-Git SCM behavior.
- **Open decisions:**
  - Should restoration preserve separate index and working-tree contents for partially staged files, or is the initial supported scope limited to wholly staged files?
  - When the destination already has staged changes, should restoration preserve and merge them, request confirmation, or refuse to restore staging?
