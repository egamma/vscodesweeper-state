# Issue #339056 — Insiders 1.141.0 .deb: chrome-sandbox lost setuid bit, app aborts with SUID sandbox FATAL on Ubuntu

[https://github.com/microsoft/vscode/issues/339056](https://github.com/microsoft/vscode/issues/339056)

## Summary

Fresh but well-diagnosed regression report: the reporter compared `dpkg-deb -c` contents across recent .deb builds and shows chrome-sandbox's setuid bit (4755) is present through 1.140.0 builds and missing starting with the first 1.141.0 Insiders build, matching a plausible pipeline cause I can independently see in the checkout — keeping open for a maintainer/agent to fix the packaging path.

## Change summary

Insiders 1.141.0 .deb ships chrome-sandbox without the setuid bit, so the app aborts with a SUID sandbox FATAL error on Ubuntu configs that can't fall back to the user-namespace sandbox.

## Best solution

Restore chrome-sandbox's setuid bit (mode 4755, owned by root) in the Linux .deb packaging path regardless of whether the compiled client arrives via in-job build output or the new downloaded `builds.tar.gz` artifact — e.g. explicitly chmod it before `fakeroot dpkg-deb` runs in build/gulpfile.vscode.linux.ts, mirroring the rpm spec's existing `%attr(4755, root, root)`.

## Plan brief

- **Likely files:** `build/azure-pipelines/linux/steps/product-build-linux-download-compilation.yml`, `build/azure-pipelines/linux/product-build-linux.yml`, `build/gulpfile.vscode.linux.ts`

- **Behavior:**

  > After the Linux packaging job started consuming a downloaded `builds.tar.gz` compilation artifact instead of an in-job build directory, the `chrome-sandbox` binary inside the resulting .deb loses its setuid bit (4755 -> 0755). Installed Insiders then aborts at startup with a SUID sandbox FATAL error on any Linux config that cannot use the unprivileged user-namespace sandbox (e.g. Ubuntu with `apparmor_restrict_unprivileged_userns=1` and no AppArmor profile for Insiders). Expected: the shipped .deb's chrome-sandbox keeps mode 4755, owned by root, regardless of how the compiled client was transported into the packaging job. Acceptance: `dpkg-deb -c` on a built .deb shows `chrome-sandbox` as `-rwsr-xr-x`.
- **Trace:**

  > build/azure-pipelines/linux/steps/product-build-linux-download-compilation.yml extracts the compile job's `builds.tar.gz` with a plain `tar -xzf ... -C $(Agent.BuildDirectory)` script step (not run as root, no `--preserve-permissions`/same-owner flags called out) — GNU tar strips setuid/setgid bits for a non-root extractor by default. The .deb is later built by `fakeroot dpkg-deb -Zxz -b ...` in build/gulpfile.vscode.linux.ts (~line 131), which packages the tree as-is with no explicit chmod or postinst fixup for chrome-sandbox, unlike the rpm spec's `%attr(4755, root, root)` (not verified further in this read-only pass, but consistent with the reporter's dpkg-deb -c evidence across versions). Boundary: the fix should restore chrome-sandbox's mode/owner specifically for the .deb packaging path without touching the rpm spec (already correct) or unrelated packaging steps. Where the uncertainty starts: whether to fix this in the download-compilation extraction step (so all downstream consumers of that artifact get correct modes) or locally just before `dpkg-deb -b` in gulpfile.vscode.linux.ts (narrower, deb-specific) — these differ in whether other consumers of the downloaded compilation artifact (if any) also get the fix.
- **Open decisions:**
  - Should the setuid bit be restored generically when extracting the `builds.tar.gz` compilation artifact (benefiting any consumer of that artifact), or only locally in the .deb packaging step right before `dpkg-deb -b`?
  - Should this also add a `postinst` fixup in the .deb (belt-and-suspenders, matching how some other packages guard against setuid loss on resinstall/extraction), or is a build-time chmod sufficient?

## Evidence

- **reporter's package diff:** dpkg-deb -c shows chrome-sandbox as `-rwsr-xr-x` (4755) in code 1.139.1, 1.140.0 and code-insiders 1.140.0 builds, but `-rwxr-xr-x` (0755, no setuid) starting with code-insiders 1.141.0-1790789516.
- **matching pipeline code in checkout:** build/azure-pipelines/linux/steps/product-build-linux-download-compilation.yml runs `tar -xzf $(Agent.TempDirectory)/compilation/builds.tar.gz -C $(Agent.BuildDirectory)` as a plain, non-root script step — consistent with GNU tar's default behavior of stripping setuid/setgid bits for a non-root extractor.
- **no fixup in deb packaging:** build/gulpfile.vscode.linux.ts line 131 runs `fakeroot dpkg-deb -Zxz -b ...` directly on the extracted tree with no explicit chmod/postinst step restoring chrome-sandbox's mode, unlike the rpm spec's explicit `%attr(4755, root, root)` (per the reporter, and consistent with what's in this checkout).
- **trigger condition:** Ubuntu ships an AppArmor userns profile only for the stable `code` binary, not `code-insiders`, so on kernels with `apparmor_restrict_unprivileged_userns=1` Insiders falls back to the SUID sandbox and aborts when chrome-sandbox lacks setuid — explains why this is a hard crash, not a cosmetic regression.
