# Issue #325909 — Extensions Auto Update enterprise policy is overridden by user settings

[https://github.com/microsoft/vscode/issues/325909](https://github.com/microsoft/vscode/issues/325909)

The defect remains present on current main, but https://github.com/microsoft/vscode/pull/329748 is an open human-owned fix that explicitly closes this issue. Keep the issue open while that PR is reviewed and either landed or closed.

## Change summary

User-level per-extension, publisher, and bulk auto-update controls can override an organization-managed ExtensionsAutoUpdate policy.

Review and land https://github.com/microsoft/vscode/pull/329748 after confirming that policy-locked values govern both update enforcement and every conflicting UI action, including previously pinned extensions.

## Evidence

- **current source:** In src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts, shouldAutoUpdateExtension unconditionally rejects pinned extensions and entries from the storage-backed disabledAutoUpdateExtensions list when auto-update is on; it does not inspect the policy value.
- **bulk bypass:** ExtensionsWorkbenchService.updateAutoUpdateForAllExtensions on current main proceeds to updateExtensionsPinnedState after attempting to change extensions.autoUpdate, so the bulk command can pin extensions even when organization policy prevents changing the effective configuration.
- **conflicting UI:** src/vs/workbench/contrib/extensions/browser/extensionsActions.ts enables the per-extension toggle without checking configurationService.inspect(AutoUpdateConfigurationKey).policyValue, while src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts exposes the bulk enable/disable commands based only on the effective configuration value.
- **open fixing PR:** https://github.com/microsoft/vscode/pull/329748 remains open, contains `Fixes #325909`, adds policy-aware enforcement and UI gating, and includes focused tests for policy-locked opt-outs and pinned extensions.
