# Issue #156546 — Allow to resolve save conflicts using the merge editor

[https://github.com/microsoft/vscode/issues/156546](https://github.com/microsoft/vscode/issues/156546)

## Summary

Keep open: current save-conflict handling still opens the diff editor, and no existing setting delivers the requested merge experience. The reopened Backlog request has explicit maintainer support for an opt-in setting and already serves as the canonical for a matching report.

## Change summary

Allow filesystem-versus-unsaved-editor conflicts to be resolved in a merge editor without a base, with clearer conflict-resolution wording.

## Best solution

Provide the maintainer-supported, disabled-by-default merge option in the file-save conflict flow while preserving the existing default comparison experience. Establish how two versions without a shared base are presented and reconciled before integrating merge completion with save-conflict handling.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/editors/textFileSaveErrorHandler.ts`, `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `src/vs/workbench/contrib/files/common/files.ts`, `src/vs/workbench/contrib/mergeEditor/browser/mergeEditorInput.ts`, `src/vs/workbench/contrib/mergeEditor/browser/mergeEditorInputModel.ts`
- **Validation:** In a development build, open a file, edit it without saving, change that file externally, then save in the editor. With the option disabled, verify the existing Compare flow remains unchanged. With it enabled, verify the conflict opens the agreed base-free merge experience, both versions remain available, and completing a resolution saves exactly the selected combined contents. Canceling must preserve unsaved edits; another external write during resolution must still trigger conflict protection.
- **Behavior:**

  > When saving a file whose disk contents changed while the editor held unsaved edits, users can opt into resolving those two versions through the merge editor without needing an SCM conflict or a supplied common ancestor. The existing comparison experience remains the default, consistent with the maintainer's disabled-by-default setting proposal. Users must be able to retain changes from either version and save their resolved result without silently discarding edits. Acceptance covers default versus opt-in behavior, completion, cancellation, and another external modification during resolution.
- **Trace:**

  > TextFileSaveErrorHandler.onSaveError in src/vs/workbench/contrib/files/browser/editors/textFileSaveErrorHandler.ts handles FILE_MODIFIED_SINCE and offers ResolveSaveConflictAction, whose run method calls TextFileContentProvider.open in src/vs/workbench/contrib/files/common/files.ts to construct a diff input. files.saveConflictResolution in src/vs/workbench/contrib/files/browser/files.contribution.ts selects asking versus overwriting, not the reconciliation UI. MergeEditorInput in src/vs/workbench/contrib/mergeEditor/browser/mergeEditorInput.ts and the factories in mergeEditorInputModel.ts require a base resource and carry their own result, save, and close lifecycle. The trace establishes the missing integration, but not an agreed base-free conflict model or a complete mapping of merge completion onto dirty-write protection. Preserve the default diff flow, existing explicit overwrite behavior, unsaved edits on cancellation, and protection against subsequent disk writes. The setting direction is settled at https://github.com/microsoft/vscode/issues/156546#issuecomment-1203694899 and reaffirmed at https://github.com/microsoft/vscode/issues/156546#issuecomment-1339450049; the matching scenario is documented in https://github.com/microsoft/vscode/issues/156915.
- **Open decisions:**
  - Without a common ancestor, should differing regions require explicit resolution, or should any differences be automatically combined, and what initial result should users see?
