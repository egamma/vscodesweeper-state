# Issue #301424 — Sessions: seeing terminal error popping up when working with multiple sessions on `vscode`

[https://github.com/microsoft/vscode/issues/301424](https://github.com/microsoft/vscode/issues/301424)

## Summary

The reported race remains source-reproducible on current main: Sessions can background a task terminal, then the task system tries to activate that terminal through a path that assumes it is still in a terminal group and throws.

## Change summary

Rapidly switching Agents Window sessions while background tasks run can produce a terminal activation error.

## Best solution

Make activation of a live backgrounded terminal restore it to its host before selecting it, and cover the task-reveal/session-switch race with a focused terminal service regression test.

- **Behavior:**

  > A live terminal associated with a running task can be activated after its Agents Window session was switched into the background. Revealing or reusing that task must not produce a "Terminal with ID … does not exist" error, and the terminal should become visible and active. Existing activation behavior for foreground, editor, and hidden tool terminals must remain unchanged.
- **Trace:**

  > SessionsTerminalContribution in src/vs/sessions/contrib/terminal/browser/sessionsTerminalContribution.ts moves terminals outside the active session scope through `ITerminalService.moveToBackground`, which removes a panel terminal from its group while keeping the instance alive. When an existing task is reused, `AbstractTaskService._handleInstancePolicy` calls `TerminalTaskSystem.revealTask`, which calls `TerminalService.setActiveInstance`. That method only invokes `showBackgroundTerminal` for `hideFromUser` terminals, so an ordinary backgrounded task terminal is passed to `TerminalGroupService.setActiveInstance`; `_getIndexFromId` throws because the instance is no longer in a group. Keep the boundary in terminal activation and preserve Sessions scoping and hidden tool-terminal lifecycle behavior; unrelated remote tunnel and split-layout issues are out of scope.

## Evidence

- **source trace:** src/vs/sessions/contrib/terminal/browser/sessionsTerminalContribution.ts `_updateTerminalVisibility` moves foreground terminals from inactive session scopes into the background, explicitly including task and manually created terminals.
- **failing path:** src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts `_handleInstancePolicy` calls `revealTask` when a running task is not visible; `TerminalTaskSystem.revealTask` then calls `ITerminalService.setActiveInstance` for that task terminal.
- **root cause:** src/vs/workbench/contrib/terminal/browser/terminalService.ts `setActiveInstance` restores a background terminal only when `shellLaunchConfig.hideFromUser` is true. A normal task terminal moved to the background by Sessions bypasses that restoration and reaches `TerminalGroupService.setActiveInstance`; `_getIndexFromId` then throws because the instance was removed from all groups.
- **canonical search:** https://github.com/microsoft/vscode/issues/333079 is newer and reports stale remote Agent Host tunnel launch failures, not this task-terminal activation exception; https://github.com/microsoft/vscode/issues/335133 and https://github.com/microsoft/vscode/issues/335252 are also newer and describe terminal selection/layout restoration rather than the same observable error.
