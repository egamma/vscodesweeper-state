# Issue #230081 — Ability to toggle panel

[https://github.com/microsoft/vscode/issues/230081](https://github.com/microsoft/vscode/issues/230081)

## Summary

Keep this accepted, 28-upvote request open: existing view commands provide partial toggling but do not restore the previously used sidebar view or expose the location/history needed by extensions. The older webview-toggle reports concern focus defects, not the full requested capability.

## Change summary

Let extensions toggle a contributed view for short interactions, restoring the previous sidebar view or hiding the sidebar when appropriate.

## Best solution

Provide an extension-callable, location-aware view toggle with agreed restoration and fallback semantics in the views service. Prefer a focused command contract unless extensions demonstrably need broader layout/history APIs.

## Plan brief

- **Likely files:** `src/vs/workbench/services/views/browser/viewsService.ts`, `src/vs/workbench/services/panecomposite/browser/panecomposite.ts`, `src/vs/workbench/api/browser/viewsExtensionPoint.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** Using a sample extension-contributed view, verify that invocation opens and focuses it, then a second invocation follows the agreed restoration/fallback contract. Repeat after moving the view between primary sidebar, secondary sidebar, and panel, including no prior view and a prior view that is unavailable. Existing .focus and .open command behavior must remain unchanged.
- **Behavior:**

  > An extension needs a reversible interaction with its contributed view: invoking its command opens and focuses the view, and invoking it again while focused exits that temporary interaction. The requested exit behavior restores a previously used view when one exists, with a defined fallback when none exists. Acceptance must cover user-moved views in both sidebars and the panel, without inadvertently hiding an unrelated region. Existing focus/open commands retain their established behavior.
- **Trace:**

  > ViewsService.registerFocusViewAction in src/vs/workbench/services/views/browser/viewsService.ts always opens the target, while registerOpenViewAction already checks FocusedViewContext and resolves the current location but does not restore prior views. registerOpenViewContainerAction likewise switches focus or closes the panel without navigation-history restoration. SwitchCompositeViewAction in src/vs/workbench/browser/parts/compositeBarActions.ts cycles visible container order, not visit history. IPaneCompositePartService in src/vs/workbench/services/panecomposite/browser/panecomposite.ts exposes a last-active container internally, but the public TreeView and WebviewView interfaces in src/vscode-dts/vscode.d.ts do not expose location/history. The remaining uncertainty is the new public contract and its restoration/fallback semantics, not whether .focus already supplies the capability. Preserve existing commands; the webview-focus defects tracked by https://github.com/microsoft/vscode/issues/194816 and https://github.com/microsoft/vscode/issues/182266 are related validation concerns, not duplicates of this request.
- **Open decisions:**
  - Should extensions receive a dedicated per-view toggle command, lower-level location/history APIs, or both?
  - Should exiting a focused view restore the last active container, the last focused individual view, or another defined navigation-history target?
  - When no usable prior target exists, should the toggle hide the containing region or focus a default view, and should that fallback differ between sidebars and the panel?
