# Issue #264725 — Symbols/files not linkified in thinking markdown

[https://github.com/microsoft/vscode/issues/264725](https://github.com/microsoft/vscode/issues/264725)

## Summary

The defect remains on current main: Copilot's response-stream linkification explicitly forwards thinking progress unchanged, while ordinary markdown is passed through the path-and-symbol linkifier. This team-authored bug should stay open for a cross-layer fix.

## Change summary

File paths and symbols shown in thinking markdown remain plain code text instead of becoming navigable links like references in the final response.

## Best solution

Extend the thinking-response pipeline so file and symbol references discovered by the existing Copilot linkifier retain thinking presentation while becoming navigable, with rendering and streaming behavior matching ordinary response references.

- **Validation:** Add a focused response-stream/linkification test that emits thinking text containing resolvable backticked file and symbol references, then assert the resulting thinking content exposes navigable references while unresolved code spans remain unchanged; add a ChatThinkingContentPart rendering test for the resulting anchors.
- **Behavior:**

  > Thinking or reasoning output that names a resolvable workspace file or symbol in inline-code formatting should present that reference as navigable, matching the capability available in normal chat output. Unresolvable inline code must remain ordinary code text, and the content must remain inside the thinking disclosure rather than becoming final-response markdown. Acceptance should cover both file and symbol references, streaming deltas, and an unresolved-code control case.
- **Trace:**

  > ResponseStreamWithLinkification in extensions/copilot/src/extension/linkify/common/responseStreamWithLinkification.ts sends normal markdown through ILinkifier but forwards thinkingProgress unchanged. The linkifier emits strings plus LinkifyLocationAnchor/LinkifySymbolAnchor parts, while ChatResponseThinkingProgressPart and IChatThinkingPart currently carry only string|string[] values through the proposed API and ext-host converters. ChatThinkingContentPart then renders the raw value directly, without the ordinary response's inline-reference metadata and ChatMarkdownDecorationsRenderer pass. The plan must trace how navigable reference identity can remain associated with thinking content across those boundaries; it must not move reasoning into the final response or heuristically link unresolved code text. https://github.com/microsoft/vscode/issues/158996 is related only at the broad link-UX level and does not own this work.

## Evidence

- **source-confirmed bypass:** extensions/copilot/src/extension/linkify/common/responseStreamWithLinkification.ts routes markdown through appendMarkdown() and ILinkifier, but thinkingProgress() directly enqueues _progress.thinkingProgress(thinkingDelta), so paths and symbols in reasoning never reach linkification.
- **representation gap:** src/vs/workbench/contrib/chat/common/chatService/chatService.ts models IChatThinkingPart as only string|string[] plus metadata, and src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatThinkingContentPart.ts renders that value directly as MarkdownString; unlike ordinary response content, it carries no inline-reference records for ChatMarkdownDecorationsRenderer.
- **API boundary:** src/vscode-dts/vscode.proposed.chatParticipantAdditions.d.ts and src/vs/workbench/api/common/extHostTypeConverters.ts preserve ChatResponseThinkingProgressPart as text-only thinking data, so retaining rich file/symbol anchors may require coordinated API, conversion, model, and rendering work rather than a renderer-only adjustment.
- **canonical search:** https://github.com/microsoft/vscode/issues/158996 concerns the editor's "Follow link" hover for lazily resolved document links, not missing file/symbol linkification in chat thinking, so it does not report the same observable symptom required for a re-reviewed duplicate close.
