# Issue #115214 — `context.secrets.onDidChange` fires without change

[https://github.com/microsoft/vscode/issues/115214](https://github.com/microsoft/vscode/issues/115214)

## Summary

Keep open: current source still permits change notifications for identical secret writes, conclusively in the browser embedder-provider path. No verified fixing commit or eligible older canonical issue was found.

## Change summary

Storing the same secret value twice should not emit a second change notification when the value has not changed.

## Best solution

Make no-op secret writes behave consistently across storage backends while preserving notifications for genuine changes in both the writing window and other windows. Confirm the native persisted-storage behavior before choosing the full fix boundary.

## Plan brief

- **Likely files:** `src/vs/workbench/services/secrets/browser/secretStorageService.ts`, `src/vs/platform/secrets/common/secrets.ts`, `src/vs/platform/secrets/test/common/secrets.test.ts`, `src/vs/workbench/api/browser/mainThreadSecretState.ts`, `src/vs/platform/encryption/electron-main/encryptionMainService.ts`
- **Validation:** Add event-count regression checks for two identical writes followed by a changed value, covering in-memory storage, persisted storage with a fake producing different ciphertext for identical plaintext, and an embedder provider. Acceptance: one notification for the initial write, none for the identical repeat, and one for the changed value. Manually repeat the extension snippet in two native windows and verify genuine changes still notify both windows.
- **Behavior:**

  > The reported command stores the same value twice under the same secret key and receives a change event for each write. An identical repeat should not signal a logical secret change; an initial store and a genuinely different value should continue to notify listeners. Verify this consistently for in-memory, persisted, and browser embedder storage. Genuine changes must continue to notify the writing window and other participating windows.
- **Trace:**

  > ExtensionSecrets.store delegates through ExtHostSecretState and MainThreadSecretState.doSetPassword to ISecretStorageService.set. BrowserSecretStorageService.set in src/vs/workbench/services/secrets/browser/secretStorageService.ts unconditionally emits after every successful embedder-provider write, conclusively establishing the reported no-op notification behavior on that path. BaseSecretStorageService.set in src/vs/platform/secrets/common/secrets.ts instead encrypts each write and forwards backing-storage events; native encryption delegates to Electron safeStorage.encryptString, so native same-value behavior remains unconfirmed without execution. Existing secrets tests use deterministic encryption and do not test repeated identical values. The remaining diagnosis is how persisted ciphertext changes and external storage notifications affect the full backend boundary, not whether the reported identical write should count as a logical change. Preserve the local and cross-window notification behavior documented in https://github.com/microsoft/vscode/issues/187247, and do not alter encryption strength, storage scopes, or extension key isolation.
