# Issue #297962 — Provide a way for custom test sessions to be re-run with commands like "Rerun last session"

[https://github.com/microsoft/vscode/issues/297962](https://github.com/microsoft/vscode/issues/297962)

## Summary

Custom test-session replay remains an API gap: current requests preserve test selection and profile identity, but not arbitrary launch context. Keep this accepted On Deck request open for testing API design; profiles offer partial coverage, not the requested per-session replay contract.

## Change summary

Allow extensions to make dynamically configured test sessions reproducible through the built-in rerun and debug commands.

## Best solution

Define a supported testing API contract for replaying extension-created sessions with their original dynamic configuration. Settle persistence and rerun-selection semantics with the testing API owner, accounting for the related profile and debug-restart discussion.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTesting.ts`, `src/vs/workbench/contrib/testing/common/testTypes.ts`, `src/vs/workbench/contrib/testing/browser/testExplorerActions.ts`, `src/vs/workbench/contrib/testing/common/testResult.ts`, `src/vs/workbench/contrib/testing/common/testResultStorage.ts`
- **Validation:** Use a minimal test-controller extension to start an externally configured session with a distinctive runtime filter or argument, then invoke Test: Rerun Last Run and Test: Debug Last Run and verify the original configuration is retained. Exercise reload and rerun-failed according to the agreed contract, while confirming ordinary profile-based runs remain unchanged.
- **Behavior:**

  > An extension can report results for a session launched with dynamic configuration outside the test runner, but the built-in replay commands cannot recover that configuration. The finished capability should let those commands reproduce the session's original execution context rather than silently fall back to a different invocation. Acceptance should cover a custom runtime filter or launch argument and preserve ordinary profile-based behavior. Persistence across reloads and interaction with rerun-failed require an explicit API contract.
- **Trace:**

  > TestRunRequest in src/vscode-dts/vscode.d.ts exposes test selection and a profile, not custom replay context. TestRunCoordinator.createTestRun in src/vs/workbench/api/common/extHostTesting.ts forwards only the predefined detached-run fields, and runControllerTestRequest constructs a new public request for the profile handler. RunOrDebugLastRun in src/vs/workbench/contrib/testing/browser/testExplorerActions.ts reuses the stored result request, whose contracts in common/testTypes.ts contain no extension-defined context. Profiles and TestRunProfile.tag provide reusable execution modes and applicability filtering, but no per-run dynamic payload. Preserve normal profile selection and existing result replay behavior; the uncertainty is the public replay contract, not whether arbitrary subclass fields currently survive. See https://github.com/microsoft/vscode/issues/144169#issuecomment-1079459501 and https://github.com/microsoft/vscode/issues/218102 for serialization and profile-design concerns.
- **Open decisions:**
  - Should custom-session replay be represented by serializable per-request context or by an expanded profile contract?
  - Must custom replay context survive window reloads, and what should users observe when it cannot be restored?
  - When replaying failed tests or switching from run to debug, which original custom execution parameters should be retained?
