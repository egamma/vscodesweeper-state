# Issue #339894 — preview output scroll isn't comprehensive

[https://github.com/microsoft/vscode/issues/339894](https://github.com/microsoft/vscode/issues/339894)

## Summary

Fresh team-authored testing feedback on the new chat terminal-output preview box; the vertical-scrollbar complaint is directly confirmed in source (it's hardcoded hidden, unlike the horizontal one), but the 'can't scroll to bottom' report needs a live repro before any fix — keeping open as a bundled follow-up for the feature that just landed.

## Change summary

In the chat terminal tool output preview box: scrolling feels hard, the view can't reach the bottom of the output, and there's no vertical scrollbar to show scroll position (only horizontal has one).

## Best solution

Give the vertical axis the same ScrollbarVisibility.Auto on hover/focus treatment the horizontal axis already has in chatTerminalToolProgressPart.ts, and separately confirm (with a live repro) whether _scrollOutputToBottom/_layoutOutput can leave the last line unreachable during streaming.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatTerminalToolProgressPart.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/media/chatTerminalToolProgressPart.css`

- **Behavior:**

  > In the chat terminal tool output preview box, users should be able to tell where they are in a long output via a vertical scrollbar (mirroring the existing horizontal one), and scrolling (mouse wheel, keyboard, drag) should reliably reach the true bottom of the output even while content is still streaming in.
- **Trace:**

  > `_createScrollableContainer` in chatTerminalToolProgressPart.ts constructs the DomScrollableElement with `vertical: ScrollbarVisibility.Hidden` and never changes it, while the MOUSE_ENTER/MOUSE_LEAVE/FOCUS_IN/FOCUS_OUT listeners only toggle `horizontal` between Auto and Hidden — this is a direct, confirmed gap for complaint #3. Complaint #2 ('can't scroll to bottom') is not yet confirmed from source alone: `_layoutOutput` sizes the container by `contentRows * rowHeight + outputPadding` against a `MAX_OUTPUT_ROWS` cap and a CSS max-height, and a comment there already flags a prior clipping race with async xterm rendering — this is a plausible but unverified cause and needs a live repro before diagnosing further. Do not change `_scrollOutputToBottom`'s scroll-lock semantics without reproducing the actual failure first.
- **Open decisions:**
  - Should the vertical scrollbar be shown via the same hover/focus toggle as horizontal, or always visible given it also conveys scroll position?
  - Is the 'can't reach the bottom' symptom a distinct bug in _layoutOutput's height/row-cap math, or purely a side effect of the missing vertical scrollbar affordance (i.e., resolved once #3 is fixed)?
