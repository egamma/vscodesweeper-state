# Issue #160197 — Comments: Go to Next Comment Thread *in Files*

[https://github.com/microsoft/vscode/issues/160197](https://github.com/microsoft/vscode/issues/160197)

## Summary

Cross-file comment navigation remains missing: current commands navigate only the active editor's threads, and the Comments view is a workaround rather than the requested editor workflow. Keep this accepted backlog request open; the maintainer and reporter agreed on expanded-thread navigation as the useful direction.

## Change summary

Provide a command to jump directly to the next expanded comment thread across files during code review.

## Best solution

Provide cross-file expanded-thread navigation in the core comments contribution while preserving existing single-file commands. Establish ordering, wraparound, and eligibility for threads in unopened files before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/comments/browser/commentsEditorContribution.ts`, `src/vs/workbench/contrib/comments/browser/commentsController.ts`, `src/vs/workbench/contrib/comments/common/commentCommandIds.ts`, `src/vs/workbench/contrib/comments/browser/commentService.ts`, `src/vs/workbench/contrib/comments/browser/commentsModel.ts`
- **Validation:** Using a comment-provider sample, create expanded and collapsed threads in at least two files, including an unopened file. Invoke the new command repeatedly from the editor and verify the agreed eligibility, resource ordering, destination focus, and end-of-list behavior. Confirm existing single-file next/previous commands remain unchanged.
- **Behavior:**

  > Code reviewers need to move directly from one expanded comment thread to the next across files without returning to the Comments view or selecting another file manually. The thread agreed that expanded-thread eligibility is useful beyond providers that expose resolved state. Acceptance should cover multiple files, skipping collapsed threads, reaching the destination thread, and preserving existing single-file navigation. Ordering, wraparound, and the treatment of unopened files must be settled before implementation.
- **Trace:**

  > In src/vs/workbench/contrib/comments/browser/commentsEditorContribution.ts, existing next-thread and next-commented-range commands obtain the active editor's CommentController. CommentController._findNearestCommentThread in commentsController.ts sorts and searches that editor's _commentWidgets; it neither traverses workspace resources nor filters on widget.expanded. ICommentService.commentsModel in commentService.ts exposes workspace thread data through CommentsModel.resourceCommentThreads in commentsModel.ts. CommentsView.openFile in commentsView.ts already uses revealCommentThread to reach a thread in another resource, but tree navigation is not the requested editor command. Preserve current single-file commands and provider-neutral behavior; an extension-specific PR workflow is outside this request. The historical expanded-state discussion at https://github.com/microsoft/vscode/issues/158414#issuecomment-1233068275 explains the direction, but does not settle eligibility for threads without a currently instantiated editor widget.
- **Open decisions:**
  - For an unopened file, should eligibility use the thread's initial collapsible state, remembered UI expansion state, or exclude threads until that file has been opened?
  - What resource order should cross-file navigation follow, and should reaching the final eligible thread wrap to the first?
  - Should the cross-file command focus the destination comment widget like Go to Next Comment Thread, or leave focus in the editor like Go to Next Commented Range?
