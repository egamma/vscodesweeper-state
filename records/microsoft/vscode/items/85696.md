Preserve legacy call-stack command arguments while providing and documenting structured session, thread, and stack-frame context.

## Best solution

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/callStackView.ts`, `src/vs/workbench/contrib/debug/test/browser/callStack.test.ts`, `src/vs/workbench/services/actions/common/menusExtensionPoint.ts`
- **Validation:** Add a call-stack command-context test asserting the legacy first argument and structured second argument for sessions, threads, and stack frames, then run the targeted `callStack` unit-test suite; verify the contributed-menu schema description exposes the agreed argument contract.
- **Behavior:**

  > Commands contributed to `debug/callstack/context` retain their existing first argument. They also receive a structured context argument that uniquely identifies the selected debug session, thread, or stack frame. The public contribution documentation states the argument order and fields that extension authors may rely on.
- **Trace:**

  > Current src/vs/workbench/contrib/debug/browser/callStackView.ts separates the legacy value in `getContextForContributedActions` from the structured value in `getContext`. The action bar and context menu pass the legacy value through menu options and the structured value as forwarded action context; src/vs/platform/actions/common/actions.ts preserves that order. Commit c6e58d126f6b5676242e32b34180b2a595f29b51 introduced the additional stack-frame context, and e102191a6ffdc4bfc572c538913f292314092e48 later added the frame name. The unresolved boundary is documentation: src/vs/workbench/services/actions/common/menusExtensionPoint.ts names the menu but describes none of its arguments. Preserve legacy argument values and internal debug-command behavior.
- **Open decisions:**
  - Which structured fields should be documented as a stable extension-facing contract: only sessionId/threadId/frameId, or also frameName and frameLocation?

## Evidence

- **runtime implementation:** Commit https://github.com/microsoft/vscode/commit/c6e58d126f6b5676242e32b34180b2a595f29b51 added session, thread, frame, and source-location context; current src/vs/workbench/contrib/debug/browser/callStackView.ts builds that structured context and forwards it after the legacy argument.
- **backward-compatible ordering:** src/vs/platform/actions/common/actions.ts constructs command arguments from `arg`/`args` first and appends forwarded action arguments when `shouldForwardArgs` is enabled. CallStackView supplies the legacy URI, numeric thread ID, or session ID as `arg` and the structured context as the action context.
- **documentation gap:** src/vs/workbench/services/actions/common/menusExtensionPoint.ts describes `debug/callstack/context` only as “The debug callstack view context menu”; it does not document argument order or the sessionId, threadId, frameId, frameName, and frameLocation fields.
- **existing tests:** src/vs/workbench/contrib/debug/test/browser/callStack.test.ts separately checks legacy and structured context helpers, while src/vs/platform/actions/test/common/menuService.test.ts checks generic legacy-first forwarding; no call-stack-specific test directly asserts the combined command arguments.
- **related PR:** https://github.com/microsoft/vscode/pull/109049 concerns search-view context extensibility and does not implement or document call-stack command arguments.
