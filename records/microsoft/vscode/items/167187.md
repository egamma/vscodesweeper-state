# Issue #167187 — Diffrenciate between read vs write references

[https://github.com/microsoft/vscode/issues/167187](https://github.com/microsoft/vscode/issues/167187)

## Summary

Keep this accepted, well-supported request open: built-in reference results still lack read/write classification and filtering. Existing occurrence decorations and the extension suggested in the discussion do not establish that the built-in request has been delivered.

## Change summary

Annotate reference results by read/write usage and allow users to filter results by that usage.

## Best solution

Provide language-provider-backed usage information in built-in reference results, with accessible annotations and filtering while preserving results from providers that cannot classify usage. Coordinate the public reference contract and language-service support before implementing the presentation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages.ts`, `src/vs/editor/contrib/gotoSymbol/browser/goToSymbol.ts`, `extensions/references-view/src/references/model.ts`, `extensions/references-view/package.json`
- **Validation:** Using the issue's TypeScript sample, verify that reference results distinguish the initialization and assignment on lines 10 and 30 from reads on lines 20 and 40, and that usage filtering returns the appropriate subset. Include contract/model tests for classified and unclassified providers, and verify that clearing the filter restores all results without changing navigation.
- **Behavior:**

  > Users can distinguish reads from writes in built-in reference search results and filter to the usage they are investigating. The supplied example expects initialization and assignment to count as writes and value accesses to count as reads. Providers without usage information must continue to produce usable reference results. Acceptance includes correct filtering, restoring all results, keyboard operation, and accessible usage labels.
- **Trace:**

  > The public ReferenceProvider in src/vscode-dts/vscode.d.ts and the editor contract in src/vs/editor/common/languages.ts return locations without usage classification. getReferencesAtPosition in src/vs/editor/contrib/gotoSymbol/browser/goToSymbol.ts requests references with includeDeclaration, while ReferencesModel in extensions/references-view/src/references/model.ts organizes locations by file and position. The built-in extension's package.json exposes no usage-filter command or setting. DocumentHighlightKind.Write already affects occurrence decorations, but that separate capability does not establish project-wide reference classification. Related contract discussion is at https://github.com/microsoft/vscode/issues/74237; TypeScript assignment-reference support is tracked at https://github.com/microsoft/TypeScript/issues/29462. Planning must establish the provider contract and presentation scope without regressing existing unclassified providers or ordinary reference navigation.
- **Open decisions:**
  - Should the public reference contract expose standardized read/write/declaration categories only, or also language-defined categories as requested in the discussion?
  - How should filtering treat references with unknown usage and references that both read and write a value?
  - Should usage annotation and filtering appear in both Peek References and the References view, or initially in one surface?
