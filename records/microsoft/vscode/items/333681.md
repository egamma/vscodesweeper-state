# Issue #333681 — Should session be aware of nested chats created manually?

[https://github.com/microsoft/vscode/issues/333681](https://github.com/microsoft/vscode/issues/333681)

## Summary

Keep open for a product decision: current main records manually created chats in the session catalog, but intentionally gives the parent conversation neither a membership notification nor automatic cross-chat awareness. This team-authored Backlog request asks whether that contract should change.

## Change summary

Make a session's parent chat aware that the user manually added another nested chat.

## Best solution

Define a bounded awareness contract for user-created peer chats—at minimum whether the parent can discover their identity and title on request—without implicitly sharing transcripts or granting cross-chat communication. Implement the selected contract in the Agent Host session tools or lifecycle path and cover both manual and tool-created chat membership.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/shared/sessionServerTools.ts`, `src/vs/platform/agentHost/node/agentService.ts`, `src/vs/platform/agentHost/node/agentSideEffects.ts`, `src/vs/platform/agentHost/test/node/sessionServerTools.test.ts`
- **Validation:** Add an Agent Host unit test that creates tool-origin and user-origin peer chats, asks through the selected parent-awareness mechanism, and verifies the manual chat is discoverable while unrelated transcript content remains unavailable unless explicitly requested.
- **Behavior:**

  > After a session has created nested chats and the user manually adds another peer chat, asking the parent about the session's nested chats should account for the manually added chat according to the selected awareness contract. Tool-created and user-created membership should not appear inconsistently to the user. Acceptance must also verify that awareness does not silently merge independent chat transcripts or expose conversation content beyond the chosen contract.
- **Trace:**

  > Current main already catalogs both creation paths: the multi-chat architecture in src/vs/platform/agentHost/AGENTS.md routes user-created and harness-created chats through AgentHostStateManager.addChat. The gap starts at the model-facing boundary: serializeSessions in src/vs/platform/agentHost/node/shared/sessionServerTools.ts emits session metadata but no peer-chat catalogue, while get_session_context targets the default chat unless given a chat-specific link. The architecture also explicitly says creation provenance does not grant communication privileges or trigger lifecycle notifications. Preserve exact-chat transcript ownership and provider-neutral catalog authority; do not merge histories or infer membership inside provider harnesses. The closed test-plan item is https://github.com/microsoft/vscode/issues/333402; broader model discussions at https://github.com/microsoft/vscode/issues/327582 and https://github.com/microsoft/vscode/issues/322934 do not settle this behavior.
- **Open decisions:**
  - Should parent awareness be on-demand catalogue discovery, a proactive notification when a manual peer chat is added, or both?
  - Which peer-chat metadata may the parent see without explicit attachment—identity and title only, status and activity, or a broader summary?
  - Should manually created chats remain transcript-isolated until the user explicitly references them, matching the current no-communication-privileges contract?
