# Issue #340507 — Claude Agent unavailable with Claude3PIntegration=true: unchecked, locked setting displays “Enabled by organization”

[https://github.com/microsoft/vscode/issues/340507](https://github.com/microsoft/vscode/issues/340507)

## Summary

The reporter's account is enterprise-managed with a Copilot Enterprise seat; Claude's governing policy is deliberately coded to force the harness off whenever Copilot managed settings are active, overriding a device-level MDM boolean — matching this report almost exactly, so the observed lock/disabled state looks intentional rather than a defect.

## Change summary

A macOS MDM Boolean policy (`Claude3PIntegration=true`) and an explicit user-setting override both fail to enable the Claude agent for an enterprise-managed account; the setting stays locked/unchecked showing a generic organization-managed indicator, and no 'New Claude Session' command appears.

## Best solution

If the current precedence is intended (managed-settings-governed accounts cannot be unlocked by a device policy or user setting), the fix is purely documentation/UX: make the settings indicator distinguish 'enabled by policy' from 'disabled by policy' so admins can tell why their MDM boolean had no effect, rather than showing the same neutral 'Managed by organization' label in both directions.

- **Proposed comment:**

  > Thanks for the detailed report and logs. This looks like intended behavior rather than a bug: `chat.agentHost.claudeAgent.enabled` is governed by the `Claude3PIntegration` policy, whose value callback (`thirdPartyAgentEnabledValue` in `src/vs/platform/policy/common/copilotManagedSettings.ts`) deliberately forces the setting to `false` whenever the account is governed by Copilot managed settings — on purpose, so a managed-settings-governed account can't bypass enterprise controls through a device-level MDM policy or a user setting. For an enterprise-managed GitHub account with a Copilot Enterprise seat, that's very likely why your `Claude3PIntegration=true` MDM policy and your explicit user setting are both overridden. The 'overlapping keys' log line is expected in this situation — it's the device policy and the managed-settings-derived policy both resolving the same key, with the managed-settings value taking precedence. I'd agree the generic 'Managed by organization' indicator doesn't make clear *which direction* a policy is enforcing, which is worth a UX follow-up, but the underlying lock itself matches the documented design. If you believe your organization's managed settings shouldn't be suppressing Claude for your account, that's a question for your GitHub Copilot enterprise administrator rather than a VS Code defect.

## Evidence

- **policy registration:** src/vs/platform/agentHost/common/agentHostStarter.config.contribution.ts:309-327 registers `chat.agentHost.claudeAgent.enabled` with `policy: { name: 'Claude3PIntegration', value: thirdPartyAgentEnabledValue }` — the same callback that forces it off for managed accounts.
- **overlap by design:** The logged 'overlapping keys' warning (src/vs/platform/policy/common/multiplexPolicyService.ts:55) is expected here: the native MDM policy channel and the GitHub account/managed-settings policy service both resolve a value for `Claude3PIntegration`, and `MultiplexPolicyService` is constructed with the account policy service last (src/vs/code/electron-main/main.ts:266, src/vs/workbench/electron-browser/desktop.main.ts:229), so the managed-settings-derived value wins over the raw device policy.
- **documented rationale:** .github/skills/policy-and-managed-settings/github-managed-settings.md:152 states this exact precedence explicitly: 'Claude3PIntegration and Codex3PIntegration ... forces its setting to false when the account disables chat preview features or when managedSettingsActive is true,' citing the same mirrors-the-sandbox-floor rationale.
- **generic indicator text:** src/vs/workbench/contrib/preferences/browser/settingsEditorSettingIndicators.ts:361 shows only the neutral 'Managed by organization' label for any policy-governed setting, regardless of whether the effective value is true or false — this is a repo-wide, pre-existing pattern, not something unique to Claude's gate.
