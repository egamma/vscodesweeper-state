# Issue #212853 — Can't click on links in streaming chat response

[https://github.com/microsoft/vscode/issues/212853](https://github.com/microsoft/vscode/issues/212853)

## Summary

The bug remains necessary and is the canonical report for streaming-response interactions lost during DOM replacement. The original fix predates the reopen, later reports were closed as duplicates of this issue, and current main still rerenders markdown during streaming.

## Change summary

File and method links visible in a streaming chat response do not activate when their DOM element is replaced between pointer down and click dispatch.

## Best solution

Make activation of visible chat links robust across streaming updates, preferably by preserving interactive DOM identity or otherwise retaining the activation across replacement, with coverage for an update occurring between pointer down and pointer up.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatMarkdownContentPart.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatIncrementalRendering/chatIncrementalRendering.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/chatContentParts/chatMarkdownContentPart.test.ts`
- **Validation:** Create a deterministic browser-level regression check that presses a visible file link, advances the streaming render before release, and verifies that the target opens exactly once; also run the targeted ChatMarkdownContentPart and chat renderer unit suites.
- **Behavior:**

  > A visible file or method link in a streaming chat response opens its target on the first normal pointer activation, including when another response chunk is rendered between pointer down and pointer up. Streaming updates must not steal focus or require a second click. Link behavior after the response completes and rendering of non-link markdown must remain unchanged.
- **Trace:**

  > The issue discussion conclusively identifies replacement of the clicked DOM node between pointer down and click dispatch as the failure. Current main still reaches that condition: ChatListItemRenderer.doRender calls ChatMarkdownContentPart.tryIncrementalUpdate, and IncrementalDOMMorpher invokes the part's full renderMarkdown callback for buffered updates; with the experimental path disabled, the list renderer disposes and recreates the whole markdown part. The earlier disposable-lifetime fix in https://github.com/microsoft/vscode/pull/215907 landed before the issue was reopened and does not address this DOM event race. Scope the plan to interactive content in a streaming markdown part; do not redesign completed-response rendering, markdown parsing, or editor-opening semantics. Related reports https://github.com/microsoft/vscode/issues/243117 and https://github.com/microsoft/vscode/issues/195949 were consolidated into this issue.
- **Open decisions:**
  - Should the interaction guarantee cover only markdown file and method links, or every interactive control whose DOM node can be replaced while a response streams?

## Evidence

- **confirmed reproduction:** A maintainer reproduced the timing-dependent failure and identified DOM replacement between pointer events as the cause in https://github.com/microsoft/vscode/issues/212853#issuecomment-2192868781.
- **current source path:** On current main, ChatListItemRenderer.doRender still routes streaming markdown through ChatMarkdownContentPart.tryIncrementalUpdate in src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts. IncrementalDOMMorpher then invokes ChatMarkdownContentPart.renderMarkdown for buffered updates; its own documentation in src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatIncrementalRendering/chatIncrementalRendering.ts states that each update rerenders through the standard markdown path.
- **non-incremental path:** When chat.experimental.incrementalRendering.enabled is false, ordinary markdown updates are not absorbed by ChatMarkdownContentPart.tryIncrementalUpdate, so ChatListItemRenderer disposes and reconstructs the rendered part. The setting remains experimental and defaults to false in src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts.
- **reopen invalidates original fix:** https://github.com/microsoft/vscode/pull/215907 merged as commit 85e9b0786cc505d85f326991227de364a5bd7293 and referenced this issue, but the reporter reopened the issue afterward because the click failure persisted. That pre-reopen commit cannot support an implemented-on-main close.
- **canonical ownership:** The same observable file-reference failure reported in https://github.com/microsoft/vscode/issues/243117 was closed as a duplicate pointing back to this issue. The older related https://github.com/microsoft/vscode/issues/195949 was likewise closed in favor of this canonical report, so neither is a valid open duplicate target.
- **no competing fix:** A search of open microsoft/vscode pull requests referencing 212853 returned no results.
