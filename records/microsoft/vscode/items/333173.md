# Issue #333173 — renderWhitespace: the dot of a space is painted at its pre-widget column when an inline 'after' decoration sits immediately before it

[https://github.com/microsoft/vscode/issues/333173](https://github.com/microsoft/vscode/issues/333173)

## Summary

Well-documented, self-confirmed rendering bug in the whitespace overlay's column math when an inline `after` decoration precedes a real space; not something I can execute to trace to a single line, but the report (isolated test harness, working mirror cases, two-version confirmation with screenshots) is strong enough to keep open for engineering follow-up.

## Change summary

With `editor.renderWhitespace: all`, the middle-dot for a space immediately following an inline `after` decoration is painted at the space's pre-widget column instead of its actual, widget-shifted column.

## Best solution

Have someone with a running build confirm in the browser whether `WhitespaceOverlay._applyRenderWhitespace` (src/vs/editor/browser/viewParts/whitespace/whitespace.ts) — which resolves each whitespace column via `ctx.visibleRangeForPosition(new Position(lineNumber, charIndex + 1))` — is getting a pixel offset that ignores the preceding `after` decoration's rendered width, and whether that traces into `RenderedViewLine`'s DOM-position/pixel-cache logic in src/vs/editor/browser/viewParts/viewLines/viewLine.ts (e.g. the `isBasicASCII` monospace-offset correction at lines ~650-656, or the `_pixelOffsetCache`/`characterMapping.getHorizontalOffset` path, which is derived purely from model character widths and has no notion of inline decoration width).

## Evidence

- **candidate code path:** src/vs/editor/browser/viewParts/whitespace/whitespace.ts _applyRenderWhitespace() computes each dot's left position from ctx.visibleRangeForPosition(Position(lineNumber, charIndex+1)) — a purely model-column-based lookup.
- **possible root cause:** src/vs/editor/browser/viewParts/viewLines/viewLine.ts RenderedViewLine._actualReadPixelOffset() (lines 628-658) reads the real DOM position via characterMapping.getDomPosition(column), but then — when input.isBasicASCII — overrides the measured DOM result with `spaceWidth * characterMapping.getHorizontalOffset(column)` whenever the two are close, and getHorizontalOffset is computed purely from model character widths with no awareness of inline 'after'/'before' decoration widths.
