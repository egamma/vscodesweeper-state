# Issue #202083 — Terminal cannot be dragged out to a new window directly

[https://github.com/microsoft/vscode/issues/202083](https://github.com/microsoft/vscode/issues/202083)

## Summary

Keep open: direct dragging from the terminal panel into a new window remains missing in current source. The existing move command provides a workaround, and maintainers have consolidated subsequent reports into this issue.

## Change summary

Allow dragging a terminal directly from the bottom panel into a new auxiliary window without first moving it into an editor tab.

## Best solution

Support terminal-tab drag-out using the established auxiliary-window interaction while preserving the running terminal session. Keep this issue as the canonical report for that gesture, distinct from detaching entire views or launching a standalone terminal application.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/terminal/browser/terminalTabsList.ts`, `src/vs/workbench/contrib/terminal/browser/terminalView.ts`, `src/vs/workbench/contrib/terminal/browser/terminalService.ts`, `src/vs/workbench/browser/parts/editor/editorTabsControl.ts`, `src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts`
- **Validation:** In desktop VS Code, start a terminal process in the panel and drag its terminal tab outside the window: a new auxiliary window should contain the same running session without an intermediate editor-tab move. Repeat for the single-terminal header and terminal tab list. Verify internal drops and canceled drags do not create windows, and existing editor-tab drag-out and terminal move commands remain unchanged.
- **Behavior:**

  > A user can drag a terminal directly from the panel into a new auxiliary window without first moving it into an editor tab. The resulting window contains the existing terminal session, preserving its process and contents. The gesture should work for both the single-terminal header and terminal tab list. Dropping within the application or canceling a drag must not accidentally create a window, and existing terminal rearrangement remains available.
- **Trace:**

  > TerminalTabsDragAndDrop in src/vs/workbench/contrib/terminal/browser/terminalTabsList.ts exports terminal resource identifiers in onDragStart and handles incoming drops, but has no auxiliary-window drag-completion path. The single-terminal header in terminalView.ts separately exports the same transfer type on DRAG_START. TerminalService.moveIntoNewEditor in terminalService.ts already moves an instance through AUX_WINDOW_GROUP, establishing that session-preserving window movement exists independently of the missing gesture. Editor-tab drag-out is implemented in MultiEditorTabsControl, with outside-window detection, positioning, and setting/modifier behavior in EditorTabsControl. The unresolved technical scope is how that lifecycle can serve both terminal drag sources without changing editor dragging, internal terminal drops, or cancellation behavior. https://github.com/microsoft/vscode/issues/237926 and https://github.com/microsoft/vscode/issues/255785 were consolidated here; detaching entire views under https://github.com/microsoft/vscode/issues/193267 is outside this request.

## Evidence

- **Missing direct gesture:** src/vs/workbench/contrib/terminal/browser/terminalTabsList.ts:620–812 implements TerminalTabsDragAndDrop. onDragStart exports terminal resource identifiers, and drop handles rearrangement and attachment, but the class has no drag-end handler that creates an auxiliary window. The single-tab source in src/vs/workbench/contrib/terminal/browser/terminalView.ts likewise registers DRAG_START to export terminal identifiers without a corresponding drag-out window-creation path.
- **Existing capability is only a workaround:** workbench.action.terminal.moveIntoNewWindow is registered in src/vs/workbench/contrib/terminal/browser/terminalActions.ts:385–390 and calls TerminalService.moveIntoNewEditor, which delegates to moveToEditor(source, AUX_WINDOW_GROUP) in terminalService.ts:813–815. This directly moves a terminal through a command, but does not implement the requested drag gesture.
- **Editor drag-out precedent:** src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts:1357–1388 handles editor-tab drag completion, creates an auxiliary editor part, and moves the editors. editorTabsControl.ts:525–562 supplies outside-window checks, positioning, and workbench.editor.dragToOpenWindow/Alt-key semantics; that behavior is not wired into the terminal panel drag sources.
- **Earlier request was not complete coverage:** https://github.com/microsoft/vscode/issues/199845 is closed and requested both commands and terminal drag-out. Its discussion mentions AUX_WINDOW_GROUP, but https://github.com/microsoft/vscode/issues/202083 records the remaining gesture after that closure. Timeline inspection shows this issue was reopened on 2025-12-08T18:22:59Z; no post-reopen fixing commit was established.
- **This issue owns the duplicate cluster:** https://github.com/microsoft/vscode/issues/237926 was closed as a duplicate of this issue by https://github.com/microsoft/vscode/issues/237926#issuecomment-2592940958. https://github.com/microsoft/vscode/issues/255785 was also directed here by https://github.com/microsoft/vscode/issues/255785#issuecomment-3628423770. Both describe the same panel-to-editor-to-window workaround.
- **Canonical-search scope distinction:** Open-issue searches for terminal drag/window, detach, and pop-out did not establish an older canonical with the same observable symptom. https://github.com/microsoft/vscode/issues/199417 concerns failures moving terminals between existing windows; https://github.com/microsoft/vscode/issues/193267 concerns detaching whole views and panels; https://github.com/microsoft/vscode/issues/34442 explicitly tracks launching a standalone terminal application. These do not replace this terminal-instance drag-out request.
