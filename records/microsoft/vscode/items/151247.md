# Issue #151247 — SCM view doesn't maintain highlight after reload

[https://github.com/microsoft/vscode/issues/151247](https://github.com/microsoft/vscode/issues/151247)

## Summary

Keep open: current source still permits restored-editor highlighting to be missed when Git resources arrive after the initial reveal. This team-authored follow-up has no verified fixing commit or same-symptom canonical.

## Change summary

- **Trace:**

  > SCMViewPane.onDidActiveEditorChange in src/vs/workbench/contrib/scm/browser/scmViewPane.ts searches currently available resources and sets tree selection/focus only on a match. onDidChangeVisibleRepositories invokes it, but later resource-group changes invoke updateChildren without another reveal. ## Evidence

- **Reported trigger:** https://github.com/microsoft/vscode/issues/151247 describes an untracked test_a.md selected in SCM before reload, missing its highlight afterward, and editor switching restoring highlighting. The report includes before-and-after screenshots.
- **Current source failure path:** src/vs/workbench/contrib/scm/browser/scmViewPane.ts:1754-1801 selects the active editor only when a matching SCM resource already exists. onDidChangeVisibleRepositories invokes that reveal, but resource-group and resource updates at lines 1813 and 1828-1829 invoke only updateChildren. updateChildren at lines 1980-2002 refreshes the tree without retrying active-editor selection. Consequently, resources arriving after the initial reveal can appear without the restored editor being selected.
- **Asynchronous resource population:** extensions/git/src/repository.ts creates resource groups around lines 1020-1023, then _updateModelState awaits repository metadata and Git status before _updateResourceGroupsState assigns resourceStates around lines 3093-3096. This supplies the late-resource ordering that the SCM selection path does not handle.

Selection restoration at lines 1280-1285 therefore does not recover a selected resource first discovered in a later refresh. scm.autoReveal is already enabled by default in scm.contribution.ts:289-293, so enabling that setting is not a solution to this startup ordering.
