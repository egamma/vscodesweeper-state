# Issue #226092 — [Accessibility] Support audio cue for commented range

[https://github.com/microsoft/vscode/issues/226092](https://github.com/microsoft/vscode/issues/226092)

## Summary

Keep open: existing comment navigation and editor-wide announcements do not provide passive discovery of commented ranges while reading code. The reporter clarified this distinction, another user supported it, and the remaining signal-design questions warrant accessibility-owner discussion.

## Change summary

Provide an optional, default-off audio cue that exposes code-review comment ranges during ordinary editor navigation, with discoverability in accessibility help.

## Best solution

Provide low-disruption, opt-in feedback for ranges containing review comments in the core comments/editor accessibility integration. Agree on range-boundary and repetition semantics before implementation; explicit comment-navigation commands are complementary, not a replacement.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/comments/browser/commentsController.ts`, `src/vs/workbench/contrib/accessibilitySignals/browser/editorTextPropertySignalsContribution.ts`, `src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts`, `src/vs/workbench/contrib/accessibility/browser/accessibilityConfiguration.ts`, `src/vs/workbench/contrib/comments/browser/commentsAccessibility.ts`
- **Validation:** In a screen-reader-enabled editor containing single-line and multiline review-comment threads, enable the proposed cue and navigate normally through uncommented lines and the full commented ranges without invoking comment commands. Verify the agreed entry/repetition behavior, silence when disabled or at the default setting, coexistence with error/warning signals, and accessibility-help discoverability.
- **Behavior:**

  > Blind developers should discover ranges containing code-review comments while reading code normally, without first choosing a comment-navigation command. Feedback must be optional, disabled by default, and minimally disruptive alongside other accessibility signals. Accessibility help should explain how to enable and interpret it. Acceptance covers single-line and multiline review-comment ranges, ordinary navigation, disabled behavior, and the repetition semantics agreed with the maintainer.
- **Trace:**

  > The request at https://github.com/microsoft/vscode/issues/226092 concerns review-comment threads, not language comment syntax. CommentsController.onEditorChangeCursorPosition updates context keys but provides no audible feedback; getCommentsAtLine detects only the glyph line, so it does not establish coverage of the full thread range. _findNearestCommentingRange provides spoken bounds for explicit navigation, and beginComputeAndHandleEditorChange provides an editor-wide availability announcement; neither supplies passive range discovery. EditorTextPropertySignalsContribution supplies existing cursor-driven signals for markers, folding and breakpoints, while AccessibilitySignal and accessibilityConfiguration.ts contain no comment-range signal. Preserve explicit navigation, existing announcements, and extension-provided comment semantics; commentable ranges without an existing thread are distinct from the requested commented ranges. The remaining uncertainty is the user-facing signal cadence and sound design, not whether command-based navigation already satisfies the request.
- **Open decisions:**
  - Should feedback occur only when entering a commented range, on each newly visited line within it, or also when leaving it so users can recognize its extent?
  - What sound should identify a commented range while remaining distinguishable and minimally disruptive alongside existing error and warning cues?
