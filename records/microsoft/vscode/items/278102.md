# Issue #278102 — [wsl] Pipe to `code -` does not work in WSL

[https://github.com/microsoft/vscode/issues/278102](https://github.com/microsoft/vscode/issues/278102)

## Summary

Keep open and classify as a bug: multiple users confirmed that `code -` opens an empty editor from WSL, Git Bash, and PowerShell, while the current stdin implementation remains unchanged. The linked report is younger and closed, so it cannot be the canonical duplicate under the re-review rules.

## Change summary

Piping command output into `code -` can open an empty editor instead of displaying the piped content.

## Best solution

Diagnose the shared CLI stdin temporary-file and editor-refresh flow across the local and server CLIs, then ensure the editor reliably observes all piped content in WSL and native Windows shells without changing argument ordering or wait semantics.

## Plan brief

- **Likely files:** `src/vs/code/node/cli.ts`, `src/vs/server/node/server.cli.ts`, `src/vs/platform/environment/node/stdin.ts`
- **Validation:** Reproduce from WSL with `printf 'stdin-marker\n' | code -` and from native Windows PowerShell with `'stdin-marker' | code -`; in each case verify that the opened editor contains the marker, then repeat with delayed multi-chunk input to ensure later writes appear.
- **Behavior:**

  > Running `code -` with piped input opens an editor containing the complete input in WSL and native Windows shells. The editor must not remain empty while the CLI reports that it is reading through a temporary file. Delayed or multi-chunk input must continue updating until stdin closes, while existing `--wait` behavior remains unchanged.
- **Trace:**

  > The local path in src/vs/code/node/cli.ts creates a temporary path, registers readFromStdin, and passes that file to the launched instance before the stream has necessarily ended. The remote path in src/vs/server/node/server.cli.ts uses the same src/vs/platform/environment/node/stdin.ts helper, whose Queue appends chunks by repeatedly opening and closing the file so file watchers should observe updates. Independent reports across WSL, Git Bash, and PowerShell indicate that the failure is not necessarily WSL-extension-specific, but the exact boundary between stream writing, path translation, and workbench file refresh is not established. Preserve CLI argument ordering, chat stdin handling, temporary-file permissions, and `--wait` cleanup semantics. The younger closed report https://github.com/microsoft/vscode/issues/300383 supplies corroborating evidence but cannot absorb this re-reviewed issue.

## Evidence

- **confirmed behavior:** The original report reproduces with `yes | code -` on VS Code 1.106.1 under WSL; https://github.com/microsoft/vscode/issues/278102#issuecomment-3767392231 independently reports the same behavior in Windows Git Bash, and https://github.com/microsoft/vscode/issues/278102#issuecomment-4111502766 confirms it in PowerShell and Bash on 1.114.0.
- **linked report:** https://github.com/microsoft/vscode/issues/300383 reports the same empty-editor symptom on native Windows, but it was created after this issue and is closed. Its reporter self-closed after one Insiders success, followed by another user reporting the failure on 1.116.0, so it is neither an eligible canonical nor proof that this issue is fixed.
- **current source:** src/vs/code/node/cli.ts creates and opens a `code-stdin-*` temporary file while src/vs/platform/environment/node/stdin.ts asynchronously appends incoming chunks through a Queue; src/vs/server/node/server.cli.ts uses the same helper for remote/server CLI input. This remains the relevant current-main path for the reported behavior.
- **no fixing change:** Upstream history for src/vs/platform/environment/node/stdin.ts contains no change after this issue was filed; the latest substantive stdin fixes predate the report. No merged PR or commit referencing https://github.com/microsoft/vscode/issues/278102 was found.
