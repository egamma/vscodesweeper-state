# Issue #106131 — Provide an option for TextEdit to respect the indentation level

[https://github.com/microsoft/vscode/issues/106131](https://github.com/microsoft/vscode/issues/106131)

## Summary

Keep open: current TextEdit APIs still lack opt-in indentation adjustment for CompletionItem.additionalTextEdits. Existing snippet whitespace controls do not cover this path, and no verified canonical issue owns the request.

## Change summary

Allow extension authors to opt individual TextEdits into surrounding-indent adjustment while preserving literal whitespace by default.

## Best solution

Have the API and suggest owners assess a backward-compatible indentation option for additional completion edits. Preserve existing literal TextEdit semantics unless an extension explicitly requests adjustment.

## Evidence

- **Current API gap:** src/vscode-dts/vscode.d.ts:3733–3798 defines TextEdit with range, newText and newEol, but no indentation or keepWhitespace option. CompletionItem.additionalTextEdits remains TextEdit[] at line 5091.
- **Different application paths:** src/vs/editor/contrib/suggest/browser/suggestController.ts:354–375 applies synchronous additional edits through executeEdits and EditOperation.replaceMove(range, edit.text); lines 417–420 do the same for asynchronously resolved edits. By contrast, the primary completion uses snippetController.insert with adjustWhitespace controlled by CompletionItemInsertTextRule.KeepWhitespace at lines 444–449.
- **Existing capabilities are partial:** src/vscode-dts/vscode.d.ts:5067–5072 documents CompletionItem.keepWhitespace for the primary insertText, not additional edits. SnippetTextEdit.keepWhitespace exists at lines 3839–3842, but SnippetTextEdit is a separate API and is not accepted by CompletionItem.additionalTextEdits; TextEditor.insertSnippet is likewise a separate operation.
- **Reporter-linked precedent:** https://github.com/microsoft/vscode/issues/32158 is closed and concerns tab-to-space conversion for code-action edits. https://github.com/microsoft/vscode/issues/32158#issuecomment-339593548 explains why ordinary edits preserve supplied text, but does not settle this later request for an explicit, backward-compatible opt-in.
