# Issue #339689 — Unclear how many of my sessions the checkbox options will automatically delete / mark done

[https://github.com/microsoft/vscode/issues/339689](https://github.com/microsoft/vscode/issues/339689)

## Summary

Valid, freshly filed UX clarity request for the new worktree-cleanup editor's automation settings: confirmed in source that the 'Mark as done after N days' and 'Delete after N days' rows render only a day-count input with no indication of how many current sessions that threshold would affect.

## Change summary

Show, next to each of the two automation day-threshold checkboxes (mark merged sessions done, delete completed sessions), how many current sessions the chosen N would affect.

## Best solution

Compute and display a live 'N sessions affected' hint next to each threshold input in renderAutomaticSetting, reusing the eligibility/merged-session criteria that already drives the table below so the number stays consistent with what the user sees.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/sessionInputBanners/browser/sessionWorktreeCleanupEditor.ts`, `src/vs/sessions/contrib/sessionInputBanners/browser/sessionWorktreeCleanupService.ts`
- **Validation:** A test or manual check asserting the mark-as-done and delete rows display a session count that matches the number of sessions meeting that threshold's criteria, and that the count updates when the day value changes.
- **Behavior:**

  > Each of the two automation rows (mark merged sessions as done after N days; delete completed sessions after N days) should show how many current sessions the active N value would affect, so the user can judge the setting's impact without manually scanning the table below. The count should update when the user edits the day value for that row.
- **Trace:**

  > renderAutomaticSetting() in sessionWorktreeCleanupEditor.ts builds each row from only a checkbox, label, and day `<input type=number>`; it has no count logic today. The worktree list rendered above already carries per-session lastUsed/eligibility info (see renderWorktreeRow / ISessionWorktreeCleanupCandidate in sessionWorktreeCleanupService.ts) that is the likely source for 'affected' counts, but 'merged and inactive >= N days' (mark-as-done) is a different predicate than plain worktree cleanup eligibility and isn't currently computed in this file — that's the gap to design, not just the rendering.
- **Open decisions:**
  - Does the affected-session count recompute live on every keystroke/change of the day input, or only on blur/commit?
  - Is the 'affected' set for mark-as-done defined purely by merged-PR + inactivity, independent of the worktree-cleanup eligibility table above, or should it reuse that exact eligibility computation for consistency?
  - Should the count be an exact number or an approximate/capped count for performance on large session counts?
