# Issue #143672 — Selecting a part in the layout picker should highlight it

[https://github.com/microsoft/vscode/issues/143672](https://github.com/microsoft/vscode/issues/143672)

## Summary

Keep open: Customize Layout still lacks feedback highlighting the workbench part represented by the focused picker item. The linked design discussion supports this capability, and no verified open canonical owns the same request.

## Change summary

Highlight the corresponding workbench region when its item is focused in the layout picker so users can distinguish similar layout icons.

## Best solution

Provide transient, theme-consistent identification of the corresponding workbench part in Customize Layout, without changing layout merely by navigating the picker. Settle the presentation and treatment of hidden parts before implementation.

- **Fit:** aligned
- **Reason:** Helping users associate layout controls with their workbench regions improves discoverability and consistent core UI interactions.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/actions/layoutActions.ts`, `src/vs/workbench/services/layout/browser/layoutService.ts`
- **Validation:** Run workbench.action.customizeLayout and navigate between Panel and Status Bar with the keyboard and mouse. Confirm the corresponding visible region is distinctly identified, navigation alone does not change layout, and identification clears when the picker closes. Verify the agreed hidden-part behavior and theme/high-contrast presentation.
- **Behavior:**

  > Users navigating Customize Layout should be able to identify which workbench region a visibility item represents, particularly Panel versus Status Bar. Feedback should track the relevant picker item without toggling visibility or moving parts merely because the user navigates. It should disappear when navigation leaves the relevant item or the picker closes. Acceptance includes keyboard and mouse navigation, unchanged explicit toggle behavior, and the agreed treatment of hidden regions.
- **Trace:**

  > CustomizeLayoutAction in src/vs/workbench/browser/actions/layoutActions.ts registers workbench.action.customizeLayout and builds visibility entries through ToggleVisibilityActions. Its run method preserves picker focus across context updates and invokes commands on acceptance or item-button activation, but does not react to active-item changes with workbench-region feedback. IWorkbenchLayoutService in src/vs/workbench/services/layout/browser/layoutService.ts exposes part containers and visibility information; this establishes a likely integration boundary, not a prescribed implementation. Preserve existing command execution, focus retention, and layout persistence semantics. The design discussion at https://github.com/microsoft/vscode/issues/137633#issuecomment-1021763106 supports highlighting visible regions but does not settle hidden-region behavior or a finalized visual treatment.
- **Open decisions:**
  - What transient visual treatment should identify the represented region consistently across themes and high-contrast modes?
  - When the represented part is hidden, should navigation provide no region highlight or show a non-layout-changing indication of its location?
