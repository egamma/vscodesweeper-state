# Issue #346518 — Remote-SSH(from Mac) to Windows waits 300 seconds for Agent Host Supervisor before opening the workspace

[https://github.com/microsoft/vscode/issues/346518](https://github.com/microsoft/vscode/issues/346518)

## Summary

Keep open: the current core CLI awaits supervisor readiness before starting the editor server, allowing the reported 300-second delay. The blocking dependency is confirmed from source; why the Windows supervisor fails to become ready remains undiagnosed.

## Change summary

Prevent an unavailable Agent Host Supervisor from delaying ordinary Remote-SSH workspace startup for five minutes.

## Best solution

Allow ordinary remote editing to start promptly when the supervisor is unavailable, while preserving functioning agent-host connections and explicit failure diagnostics. Investigate the Windows readiness failure separately from the editor-startup dependency.

## Plan brief

- **Likely files:** `cli/src/commands/tunnels.rs`, `cli/src/tunnels/control_server.rs`, `cli/src/commands/agent_host.rs`
- **Validation:** Establish a controlled case where supervisor readiness never arrives and verify ordinary editor-server startup completes without waiting for the 300-second deadline. Repeat the reported Mac-to-Windows Cmd+Q/reconnect sequence, and verify that an immediately ready supervisor still supplies a working agentHostProxy connection.
- **Behavior:**

  > After fully quitting VS Code on macOS, reconnecting to a Windows host with remote.SSH.useExecServer enabled must not wait five minutes solely because the Agent Host Supervisor is unavailable. Ordinary remote editing should remain usable, and supervisor failures should remain diagnosable. Acceptance must cover both a supervisor that never becomes ready and one that becomes ready normally.
- **Trace:**

  > command_shell in cli/src/commands/tunnels.rs creates a lazy shared ensure_supervisor_running future and passes it to the control-server request handler. handle_serve in cli/src/tunnels/control_server.rs awaits that future before resolving or starting the editor server. ensure_supervisor_running in cli/src/commands/agent_host.rs waits for a readiness sentinel with a fixed 300-second timeout, matching the reporter's log exactly. The source establishes the blocking dependency but does not establish why readiness fails after the Windows reconnect. Bridge endpoint information currently enters the server's startup arguments, so changing startup ordering requires examining bridge availability and shared-future lifecycle rather than merely moving an await. Preserve successful agent-host connectivity and explicit errors; unrelated AI opt-out work in https://github.com/microsoft/vscode/issues/328397 is not this issue's acceptance criterion.

## Evidence

- **Reporter trigger and timing:** https://github.com/microsoft/vscode/issues/346518 supplies versions, settings, and a repeatable Mac-to-Windows reconnect sequence after Cmd+Q. Its remote CLI log records supervisor startup at 11:10:29, timeout at 11:15:29, and successful editor-server startup immediately afterward.
- **Current Remote-SSH CLI path:** cli/src/commands/tunnels.rs:146–186, command_shell, constructs a shared lazy ensure_supervisor_running future and passes it through ServeStreamParams.active_agent_host. Deferring creation until a serve request does not remove the editor-startup dependency.
- **Confirmed blocking dependency:** cli/src/tunnels/control_server.rs:814–845, handle_serve, awaits active_agent_host before constructing and resolving ServerParamsRaw. Supervisor failure is explicitly tolerated, but only after that await finishes; normal server startup cannot proceed during the wait.
- **Exact timeout:** cli/src/commands/agent_host.rs:55 defines SUPERVISOR_READY_TIMEOUT as Duration::from_secs(5 * 60). ensure_supervisor_running awaits spawn_supervisor_and_wait_ready, whose readiness loop at lines 867–895 returns the same 300-second timeout message shown in the report.

Their reports were read; neither establishes ownership of this Windows readiness timeout blocking ordinary editor startup.
