# Issue #211369 — Syntax highlighting sometimes gets out of sync

[https://github.com/microsoft/vscode/issues/211369](https://github.com/microsoft/vscode/issues/211369)

## Summary

Keep open: repeated captures show rendered colors disagreeing with VS Code's own token inspector, and another user observed the behavior in TypeScript and JavaScript. The intermittent edit/undo race needs a deterministic regression test before the responsible semantic-token or rendering layer can be fixed.

## Change summary

Syntax colors can become stale or split within a token after ordinary editing, undo, or external file changes, while Inspect Tokens and Scopes reports the expected token and foreground.

## Best solution

Build a deterministic semantic-token race reproduction around rapid edits and undo, then ensure both the stored token ranges and rendered view lines converge on the latest document version. Keep this distinct from viewport-only scrolling and cross-file invalidation reports unless instrumentation establishes a shared root cause.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/semanticTokens/browser/documentSemanticTokens.ts`, `src/vs/editor/contrib/semanticTokens/test/browser/documentSemanticTokens.test.ts`, `src/vs/editor/common/tokens/sparseTokensStore.ts`, `src/vs/editor/test/common/model/tokensStore.test.ts`, `src/vs/editor/common/viewModel/viewModelImpl.ts`
- **Validation:** Add a targeted editor unit test with a delayed document semantic-token provider, rapid edit plus undo before the response completes, and assertions that the final merged line tokens and emitted token-change ranges match the latest model; the test should remain stable under repeated execution.
- **Behavior:**

  > After typing, undoing, saving, or receiving an external file update, syntax highlighting must converge on the latest document contents. A single semantic token must not remain visually split into old and new colors when Inspect Tokens and Scopes reports one foreground for the full token. Acceptance requires a deterministic delayed-provider regression test covering edit plus undo and confirming the final rendered-token inputs match the latest model.
- **Trace:**

  > Document semantic-token requests are coordinated by ModelSemanticColoring in src/vs/editor/contrib/semanticTokens/browser/documentSemanticTokens.ts. Edits arriving during a request are accumulated, applied to the returned SparseMultilineTokens, and followed by another request; TokenizationTextModelPart in src/vs/editor/common/model/tokens/tokenizationTextModelPart.ts independently applies each edit to SparseTokensStore. Token changes then pass through ViewModelImpl in src/vs/editor/common/viewModel/viewModelImpl.ts to invalidate rendered lines. The issue evidence confirms a disagreement between displayed colors and the inspector, but does not establish whether the corruption is in pending-change reconciliation, SparseTokensStore, event-range conversion, or view caching. The boundary is same-document semantic highlighting during edits: do not fold in the separate cross-file refresh design from https://github.com/microsoft/vscode/issues/130486 or assume the viewport/folding behavior in https://github.com/microsoft/vscode/issues/210295 has the same root cause.
- **Open decisions:**
  - Does instrumentation place the first mismatch in the semantic tokens stored on the text model, or only in the rendered view-line cache?
  - Does the encompassing-deletion fix from https://github.com/microsoft/vscode/pull/274079 also eliminate the rapid edit/undo case, or is a separate reconciliation defect still present?
  - Should stale in-flight results continue to be position-adjusted and displayed temporarily, or should they be discarded when an undo or overlapping edit makes safe reconciliation uncertain?

## Evidence

- **confirmed behavior:** The reporter captured the mismatch repeatedly in screenshots and video, including after rapid typing/undo and a Git branch change; https://github.com/microsoft/vscode/issues/211369#issuecomment-2158594103 shows Inspect Tokens and Scopes reporting one full token while the editor paints it with different colors.
- **cross-language confirmation:** A separate user reported the same symptom in TypeScript and JavaScript at https://github.com/microsoft/vscode/issues/211369#issuecomment-2245463834, weakening the hypothesis that this is specific to the Dart extension.
- **current request path:** src/vs/editor/contrib/semanticTokens/browser/documentSemanticTokens.ts records edits arriving during a semantic-token request, adjusts the returned SparseMultilineTokens with those pending edits, applies them, and schedules another request. Rapid edit/undo sequences exercise this asynchronous reconciliation path.
- **storage and rendering path:** src/vs/editor/common/model/tokens/tokenizationTextModelPart.ts updates SparseTokensStore on every model edit and emits token-change events; src/vs/editor/common/viewModel/viewModelImpl.ts converts those events to ViewTokensChangedEvent, which invalidates rendered lines. The available source does not establish whether the stale state originates in storage, event ranges, or the rendered-line cache.
- **related fix is not conclusive:** https://github.com/microsoft/vscode/pull/274079 fixed empty SparseTokensStore pieces after an encompassing deletion for https://github.com/microsoft/vscode/issues/247053, but it neither references this issue nor demonstrates coverage of the reported rapid typing/undo and external-change scenarios.
- **canonical search:** https://github.com/microsoft/vscode/issues/210295 concerns viewport semantic-token requests changing after scrolling/folding, while https://github.com/microsoft/vscode/issues/130486 concerns cross-file invalidation; neither fully owns this report's same-document edit/undo mismatch.
