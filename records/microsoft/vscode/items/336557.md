# Issue #336557 — Touch long-press context menus flash-close on Android Chromium: four interacting hide paths with no Android exemption (iOS only)

[https://github.com/microsoft/vscode/issues/336557](https://github.com/microsoft/vscode/issues/336557)

## Summary

Well-diagnosed touch-only bug on Android Chromium: current main still has the iOS-only exemption in contextview.ts and the unconditional blur-hide in contextMenuHandler.ts that the reporter cites, so the report holds against `main`; keeping open for a maintainer to decide how much of the four-path fix to take on.

## Change summary

Long-press context menus on Android Chromium (touch) open and then immediately flash-close, due to four interacting hide paths (relayout hide, blur hide, duplicate show, focus-steal blur) that only exempt iOS, not Android.

## Best solution

Extend the iOS-only exemptions in contextview.ts and contextMenuHandler.ts to cover Android coarse-pointer/touch, and dedupe the dual context-menu synthesis in listWidget.ts noted as related to #332619/#331838 — but a maintainer should first decide how many of the four paths need fixing versus just the highest-impact one or two.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/contextview/contextview.ts`, `src/vs/platform/contextview/browser/contextMenuHandler.ts`, `src/vs/base/browser/ui/list/listWidget.ts`
- **Validation:** Manual verification on an actual Android Chromium touch device (long-press a file-tree item and an editor region) that the context menu stays open; no existing automated test harness covers touch/coarse-pointer context-menu interactions.
- **Behavior:**

  > On Android Chromium (touch, coarse pointer), long-pressing a file-tree item or editor region should open a context menu that stays open until the user dismisses it, matching current iOS and desktop behavior. Today it flashes closed within ~10-50ms. Acceptance: manual long-press testing on an Android touch device shows the menu remains stable; iOS and desktop behavior must remain unchanged.
- **Trace:**

  > Four independent hide triggers cascade from one long-press gesture: (1) contextview.ts:329 hides on relayout because `canRelayout === false` is only exempted for iOS, not Android, and the virtual-keyboard-collapse resize trips this; (2) contextMenuHandler.ts:100 unconditionally hides on window BLUR, which the Android system selection ActionMode toolbar triggers; (3) listWidget.ts ~L1455-1483 combines mouse `contextmenu` and Monaco's `-monaco-gesturecontextmenu` events, so one long-press can call `showContextView` twice and the second show disposes the first menu (related: https://github.com/microsoft/vscode/issues/332619, https://github.com/microsoft/vscode/issues/331838); (4) post-open native-EditContext focus restoration blurs the menu's action container, triggering ActionBar's onDidBlur hide. All four are confirmed present on current main via direct source reading. The boundary: do not touch iOS or desktop behavior, and do not remove blur/resize hide handling generally — only add Android/touch-specific exemptions or dedupe logic.
- **Open decisions:**
  - Fix all four hide paths, or just the highest-impact one (likely path 1, the relayout hide)?
  - Should the Android exemption be gated on `platform.isAndroid` plus coarse pointer, or a broader touch/virtual-keyboard heuristic?
  - Is deduping the dual context-menu synthesis in listWidget.ts (paths shared with #332619/#331838) done here or left to those issues?
