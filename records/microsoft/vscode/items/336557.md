# Issue #336557 — Touch long-press context menus flash-close on Android Chromium: four interacting hide paths with no Android exemption (iOS only)

[https://github.com/microsoft/vscode/issues/336557](https://github.com/microsoft/vscode/issues/336557)

## Summary

The reporter reconfirmed the Android Chromium failure on VS Code 1.137.0, and current main still contains the interacting resize, blur, and duplicate-context-menu paths identified by their telemetry. Route this to the touch/pointer and menus owners; no older issue found reports the same flash-close symptom.

## Change summary

Long-pressing an editor or file-tree item in Android Chromium briefly opens VS Code's context menu before resize, blur, duplicate-show, or focus-restoration events close it.

## Best solution

Keep a touch-opened context menu stable across Android Chromium's transient virtual-keyboard and selection-toolbar lifecycle while preserving normal dismissal on explicit outside interaction, Escape, genuine window deactivation, and desktop pointer flows. Ensure one long press produces only one VS Code context-menu opening.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/contextview/contextview.ts`, `src/vs/platform/contextview/browser/contextMenuHandler.ts`, `src/vs/base/browser/ui/list/listView.ts`, `src/vs/base/browser/ui/list/listWidget.ts`, `src/vs/base/browser/touch.ts`, `src/vs/base/test/browser/ui/contextview/contextview.test.ts`
- **Validation:** On Android Chromium with the virtual keyboard active, long-press both a file-tree item and selected editor text and verify exactly one VS Code context menu remains usable until an explicit action or dismissal. Repeat outside-click, Escape, genuine tab/window deactivation, desktop right-click, iOS touch, and Firefox touch checks; add browser tests covering non-relayout context views and duplicate native/synthesized context-menu delivery where the harness permits.
- **Behavior:**

  > A long press on a file-tree item or editor region in Android Chromium must open one VS Code context menu that remains visible and actionable after the virtual keyboard collapses or the native selection toolbar appears. Explicit outside interaction, Escape, selecting an action, and genuine window deactivation must continue to dismiss it. Desktop mouse behavior, Firefox touch behavior, and existing iOS handling must remain unchanged.
- **Trace:**

  > The reporter captured four closures from one Android Chromium long press and reconfirmed the symptom on VS Code 1.137.0. Current main retains the non-relayout hide with only an iOS exemption in src/vs/base/browser/ui/contextview/contextview.ts, menu and window blur hides in src/vs/platform/contextview/browser/contextMenuHandler.ts, synthetic held-touch context-menu dispatch in src/vs/base/browser/touch.ts, and merged native/synthetic context-menu sources in src/vs/base/browser/ui/list/listView.ts flowing through List.onContextMenu in listWidget.ts. These are shared infrastructure paths, so the investigation must establish which Android events are transient without weakening real blur, outside-click, keyboard-cancel, mouse, or non-Android behavior. The related open touch issues https://github.com/microsoft/vscode/issues/332619, https://github.com/microsoft/vscode/issues/331838, and https://github.com/microsoft/vscode/issues/125310 describe different observable failures and do not absorb this report.

## Evidence

- **current reproduction:** The reporter retested code-server 4.137.0 / VS Code 1.137.0 and confirmed that Android Chromium still flash-closes the menu while Firefox on the same tablet does not: https://github.com/microsoft/vscode/issues/336557#issuecomment-5715230501.
- **resize teardown path:** On current main, src/vs/base/browser/ui/contextview/contextview.ts:359-371 hides a visible context view when `canRelayout === false`; the only pointer-event exemption is `platform.isIOS`, leaving Android viewport relayouts on the hide path.
- **blur teardown paths:** src/vs/platform/contextview/browser/contextMenuHandler.ts:97-100 hides the context view both when the menu reports blur and when the target window emits `blur`, matching two telemetry-reported closures.
- **dual event sources:** src/vs/base/browser/touch.ts:213-220 synthesizes `-monaco-gesturecontextmenu` after a held touch, while src/vs/base/browser/ui/list/listView.ts:1161 combines that event with the browser's native `contextmenu`; src/vs/base/browser/ui/list/listWidget.ts forwards the combined stream without touch deduplication.
- **canonical search:** The older open issues https://github.com/microsoft/vscode/issues/332619 and https://github.com/microsoft/vscode/issues/331838 concern leaked cancelled touches and submenu scrolling respectively. https://github.com/microsoft/vscode/issues/125310 concerns when an iPad menu first appears, not an Android menu immediately disappearing, so none meets the re-review duplicate bar.
