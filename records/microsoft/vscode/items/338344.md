# Issue #338344 — `executeTask()` resolves for a fetched task that never runs when the task lookup fails

[https://github.com/microsoft/vscode/issues/338344](https://github.com/microsoft/vscode/issues/338344)

## Summary

Confirmed on main: `executeTask()` swallows the rejection from `$executeTask` in three places (both branches of node's `ExtHostTask.executeTask` and the browser/web variant in common `ExtHostTaskBase.executeTask`), so a failed task lookup leaves the caller with a `TaskExecution` that never starts or ends — the exact hang the reporter describes. The reporter's own fix PR was closed unmerged, deferred to maintainers, so the gap remains.

## Change summary

`executeTask()` resolves with a TaskExecution even when the underlying `$executeTask` lookup fails, so callers waiting on task start/end hang forever.

## Best solution

Make `executeTask()` await `$executeTask` and reject the caller when the lookup fails, while correctly cleaning up the per-task execution tracking for overlapping calls (some of which may still succeed) — the design the closed PR at https://github.com/microsoft/vscode/pull/338345 sketched but didn't land.

## Plan brief

- **Likely files:** `src/vs/workbench/api/node/extHostTask.ts`, `src/vs/workbench/api/common/extHostTask.ts`, `src/vs/workbench/api/browser/mainThreadTask.ts`
- **Validation:** A test in src/vs/workbench/api/test/node/extHostTask.test.ts (or the equivalent common suite) asserting `executeTask()` rejects when the mocked `$executeTask` rejects, including an overlapping-calls case where one succeeds and one fails.
- **Behavior:**

  > When `$executeTask` rejects because the fetched task could not be re-resolved on the main thread, the `Promise<vscode.TaskExecution>` returned by `vscode.tasks.executeTask()` must reject with that error instead of resolving. Neither `onDidStartTask` nor `onDidEndTask` should ever fire for the failed execution. When multiple overlapping `executeTask()` calls target the same task and only some fail, the failing calls reject while the succeeding ones still resolve and run normally.
- **Trace:**

  > The swallowed rejection is in src/vs/workbench/api/node/extHostTask.ts:74 and :90 (`this._proxy.$executeTask(handleDto/dto).catch(() => {...})`) and in src/vs/workbench/api/common/extHostTask.ts:791 (`.catch(error => { throw new Error(error); })`, which also fails to propagate). In all three, the `execution` object is already computed and returned to the caller before the `$executeTask` call settles. The main-thread side (src/vs/workbench/api/browser/mainThreadTask.ts `$executeTask`) rejects with `Error('Task not found')` when `ITaskService.getTask` returns undefined — that is the rejection being lost. Do not change the main-thread lookup/rejection behavior; the fix belongs in the extension-host callers. The execution-tracking map touched by `getTaskExecution`/`addCustomExecution` (common/extHostTask.ts) is shared by other call sites (start/end task notification handlers) — cleanup on a failed lookup must not remove an execution entry that another overlapping, still-running call is relying on. See https://github.com/microsoft/vscode/pull/338345 for the author's own (closed, unmerged) attempt at this cleanup logic.
- **Open decisions:**
  - When overlapping executeTask() calls target the same task and one fails the lookup while another succeeds, do the failing calls reject individually while the succeeding ones proceed unaffected, or does a failure affect all pending callers for that task?
  - Should the fix be applied uniformly across the node and web/common ExtHostTask implementations in the same change, given both have the same swallowed-rejection bug?

## Evidence

- **swallowed rejection (node):** src/vs/workbench/api/node/extHostTask.ts:74 and :90 both do `this._proxy.$executeTask(...).catch(() => { /* not actionable */ })` without awaiting or propagating, while `execution` (returned to the caller) is computed and returned before this fires.
- **swallowed rejection (web):** src/vs/workbench/api/common/extHostTask.ts:791 does `.catch(error => { throw new Error(error); })`, which throws inside an unhandled promise callback and does not reject the promise returned to the extension — same class of bug in the web/common implementation.
- **main-thread lookup failure:** src/vs/workbench/api/browser/mainThreadTask.ts's `$executeTask` rejects with `new Error('Task not found')` when `this._taskService.getTask(...)` resolves to `undefined` — confirms the rejection this issue is about is real and reachable.
- **author's own attempted fix, self-closed:** https://github.com/microsoft/vscode/pull/338345 (state: closed, merged: false) implemented awaiting + rethrow with execution-map cleanup for overlapping calls, but the author closed it saying 'leaving the fix to the maintainers' — no maintainer has picked it up.
- **shared execution tracking:** `getTaskExecution`/`addCustomExecution` in src/vs/workbench/api/common/extHostTask.ts are used from several call sites (onDidStartTask/onDidEndTask handlers, custom execution flows), so cleanup semantics for a failed lookup need to account for those consumers.
