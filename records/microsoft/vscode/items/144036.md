# Issue #144036 — Feature Request: Add way of getting all the color presentations in a specific range of a document in the vscode API

[https://github.com/microsoft/vscode/issues/144036](https://github.com/microsoft/vscode/issues/144036)

## Summary

Keep this accepted API request open: existing commands expose colors and presentations, but do not provide a caller-excluding query suitable for a color provider to inspect competing results without re-entering itself. The request has 31 upvotes, and the related closed decorator reports do not resolve that coordination gap.

## Change summary

Allow extensions to inspect colors and presentations already supplied for a document range so they can avoid conflicting color pickers.

## Best solution

Have the API and color-picker owners define a supported provider-coordination contract, building on the existing execution commands rather than adding a redundant general query. Settle whether extensions should inspect other providers' results or whether the editor should resolve overlapping contributions.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostApiCommands.ts`, `src/vs/editor/contrib/colorPicker/browser/color.ts`, `src/vs/editor/contrib/colorPicker/browser/colorPickerContribution.ts`, `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/test/browser/extHostApiCommands.test.ts`
- **Validation:** After choosing the contract, add extension-host API coverage with two providers reporting the same range: verify that the supported coordination flow terminates without recursive self-invocation and permits one effective color contribution. Run the targeted 'Color provider' tests through scripts/test.sh; preserve existing command results and defaultColorDecorators behavior.
- **Behavior:**

  > Extensions should be able to coexist with built-in and other extension color providers without producing redundant color-picker contributions for the same range. Ordinary color and presentation queries already exist; the missing behavior is safe coordination while supplying a provider's own results. Acceptance should cover two overlapping providers, a non-overlapping contribution that remains visible, and a terminating coordination flow without recursive self-invocation. The intended relationship between detected colors and supplemental presentations must be explicit.
- **Trace:**

  > src/vs/workbench/api/common/extHostApiCommands.ts registers vscode.executeDocumentColorProvider and vscode.executeColorPresentationProvider. Their editor-side handlers in src/vs/editor/contrib/colorPicker/browser/colorPickerContribution.ts invoke color.ts:_findColorData, which queries matching providers without identifying or excluding the caller and strips provider provenance from extension-facing results. The hover path in hoverColorPickerParticipant.ts retains the detecting provider rather than automatically collecting presentations from every provider. editor.defaultColorDecorators only governs the special DefaultDocumentColorProvider fallback and does not settle general provider coordination. Preserve ordinary execution-command behavior and existing provider registration semantics unless the API owners explicitly approve a contract change. https://github.com/microsoft/vscode/issues/242213 and https://github.com/microsoft/vscode/issues/34341 address narrower UI/configuration cases, not this remaining API boundary.
- **Open decisions:**
  - Should overlapping color contributions be coordinated through an extension-facing query of other providers, or resolved automatically by the editor?
  - Should an extension be able to add presentations to a color detected by another provider without contributing its own color decoration?

## Evidence

- **Accepted request and demand:** https://github.com/microsoft/vscode/issues/144036 is in Backlog with 31 upvotes. The discussion supplies additional extension-author use cases: regex-based color discovery, suppressing overlapping providers, and adding presentations to colors detected by another provider.
- **Existing capability checked:** src/vs/workbench/api/common/extHostApiCommands.ts exposes vscode.executeDocumentColorProvider(uri), returning ColorInformation[], and vscode.executeColorPresentationProvider(color, { uri, range }), returning ColorPresentation[]. The existing 'Color provider' test in src/vs/workbench/api/test/browser/extHostApiCommands.test.ts exercises both. Thus ordinary color discovery and presentation execution already exist.
- **Remaining coordination gap:** In src/vs/editor/contrib/colorPicker/browser/colorPickerContribution.ts, both execution commands call _findColorData in color.ts. That function invokes matching providers without a caller-exclusion parameter; ExtColorDataCollector and ColorPresentationsCollector return results without provider identity. Calling the corresponding command from a provider callback therefore includes that provider again, rather than safely querying only competing contributions.
- **Presentation-only workaround boundary:** src/vs/editor/contrib/colorPicker/browser/hoverColorPicker/hoverColorPickerParticipant.ts creates the hover using colorData.provider, while color.ts:getColorPresentations calls that particular provider. Registering another provider solely to supply presentations does not automatically augment the hover for another provider's detected color, matching the limitation described in comment 6.
- **New setting is partial coverage:** src/vs/editor/common/config/editorOptions.ts registers editor.defaultColorDecorators with auto, always, and never. In color.ts, this specially controls DefaultDocumentColorProvider, not coordination among all registered extension or language providers. https://github.com/microsoft/vscode/issues/242213#issuecomment-2929461273 recommends auto for its narrower duplicate-default-decorator scenario; that closed issue does not establish completion of this API request.
