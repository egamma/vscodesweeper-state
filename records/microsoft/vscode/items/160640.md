# Issue #160640 — Git - add an `--ignore-matching-lines` option as for `git diff`

[https://github.com/microsoft/vscode/issues/160640](https://github.com/microsoft/vscode/issues/160640)

## Summary

Keep open: existing diff settings do not cover ignoring changes that match a regular expression, and a maintainer explicitly welcomed an implementation. No verified canonical duplicate or completed fix was found.

## Change summary

Allow regex-based suppression of diff noise, such as automatically updated timestamp lines, comparable to git diff --ignore-matching-lines.

## Best solution

Provide an opt-in comparison filter that suppresses matching-only changes without modifying file contents or silently changing staging behavior. First settle whether this is a Git-specific capability or a shared diff-editor option, since Git's visual comparisons use the editor rather than displaying git diff output.

## Plan brief

- **Likely files:** `extensions/git/package.json`, `extensions/git/src/commands.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/git.ts`, `src/vs/editor/common/config/editorConfigurationSchema.ts`, `src/vs/editor/common/diff/linesDiffComputer.ts`
- **Validation:** After scope is agreed, compare a tracked file against its previous revision with only a timestamp-line change matching the configured regex, then with an additional substantive change. Verify the matching-only change is suppressed, substantive changes remain visible, disabling the filter restores the full comparison, and neither file contents nor the Git index changes. Include a mixed hunk to pin the agreed git diff -I semantics.
- **Behavior:**

  > Users want to exclude predictable changed lines, such as generated last-modified timestamps, from comparisons using a regular expression. Existing whitespace filtering does not solve this. An enabled filter should suppress matching-only changes while retaining substantive changes, and disabling it should restore the ordinary comparison. Acceptance must establish how mixed hunks behave and confirm that comparison filtering does not modify files or the Git index.
- **Trace:**

  > Commands.openChange in extensions/git/src/commands.ts delegates to Resource.openChange in extensions/git/src/repository.ts. ResourceCommandResolver.resolveChangeCommand opens vscode.diff with original and modified resource URIs, so the visual diff is not merely the textual output of the Git subprocess methods in extensions/git/src/git.ts. The editor configuration in src/vs/editor/common/config/editorConfigurationSchema.ts offers trim-whitespace suppression and unchanged-region hiding, while ILinesDiffComputerOptions in src/vs/editor/common/diff/linesDiffComputer.ts has no regex-filter contract. The thread at https://github.com/microsoft/vscode/issues/160640 establishes maintainer interest but does not settle Git-only versus shared-editor scope or exact mixed-hunk behavior. Preserve existing comparisons when filtering is disabled and keep content and staging semantics unchanged unless explicitly approved. The file list identifies inspected entry points, not a complete implementation design.
- **Open decisions:**
  - Should regex filtering apply only to Git source-control comparisons or also to ordinary file comparisons in the shared diff editor?
  - Should filtering follow git diff -I semantics, suppressing a hunk only when every changed line matches, or independently hide matching changed lines within mixed hunks?
