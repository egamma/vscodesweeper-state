# Issue #133278 — Allow the OS to handle custom URIs. Cannot open links with custom URL schema (e.g. slack://)

[https://github.com/microsoft/vscode/issues/133278](https://github.com/microsoft/vscode/issues/133278)

## Summary

Still unimplemented on main: the opener service hardcodes a small allowlist of schemes (mailto, http, https, vsls) for external opening; custom URI schemes like slack://, hook://, tel: fall through to the EditorOpener and are mishandled as file paths. This is the canonical issue — three other reports were closed as duplicates of it. With 31 upvotes, an On Deck milestone, and clear maintainer engagement (mjbvz traced the fix path), this should stay open.

## Change summary

Allow VS Code to delegate URIs with custom/unknown schemes to the OS opener instead of treating them as file paths.

## Best solution

Extend the default opener in `src/vs/editor/browser/services/openerService.ts` (line ~136) to recognize non-internal, non-file, non-command schemes that aren't in the hardcoded list and route them through `_doOpenExternal` — with a confirmation prompt for untrusted or unknown schemes (as mjbvz outlined in comment 4). The webview link validation in `mainThreadWebviews.ts` also needs a corresponding update. Security-wise, always prompt before launching an unknown protocol handler, even in trusted workspaces.
