# Issue #133278 — Allow the OS to handle custom URIs. Cannot open links with custom URL schema (e.g. slack://)

[https://github.com/microsoft/vscode/issues/133278](https://github.com/microsoft/vscode/issues/133278)

## Summary

Keep open: current source still restricts custom-protocol links, and this issue already serves as the canonical request for several closed duplicates. Supporting OS handlers remains accepted work, with an explicit maintainer requirement for confirmation before launching applications from extension pages.

## Change summary

Allow custom-protocol links in Markdown source and preview to launch their OS-registered applications safely.

## Best solution

Provide a consent-aware external-application opening path shared by Markdown and webviews, preserving internal URI and command handling. Retain the maintainer-required confirmation for extension-page application links even in trusted workspaces rather than removing the scheme restrictions alone.

## Evidence

- **Current webview restriction:** src/vs/workbench/api/browser/mainThreadWebviews.ts: standardSupportedLinkSchemes contains http, https, mailto, vscode, and vscode-insider. isSupportedLink additionally permits the product protocol and enabled command URIs, but returns false for arbitrary schemes such as slack and hook before onDidClickLink invokes the opener.
- **Current external-opening boundary:** src/vs/editor/browser/services/openerService.ts: shouldOpenExternal selects mailto, http, https, and vsls unless the caller explicitly supplies openExternal. extensions/markdown-language-features/src/util/openDocumentLink.ts recognizes absolute non-file URIs, but its openExternal helper sends non-HTTP schemes through vscode.open rather than vscode.env.openExternal. Recognizing a custom URI therefore does not itself provide the requested OS delegation.
- **Existing setting does not cover the request:** The Markdown configuration and URL contribution registrations expose no arbitrary-protocol enabling setting. workbench.trustedDomains.promptInTrustedWorkspace controls trusted-domain prompting; src/vs/workbench/contrib/url/browser/trustedDomainsValidator.ts returns early for non-HTTP(S) schemes, so this setting does not supply application-launch consent or enable custom schemes.
- **Maintainer diagnosis and safety requirement:** https://github.com/microsoft/vscode/issues/133278#issuecomment-942927740 documents a confirmed Slack reproduction, identifies both the webview and opener restrictions, and requires prompting for application URIs from extension pages even in trusted workspaces. Removing the restrictions without that protection would not fulfill the agreed direction.
- **Verified canonical role:** Maintainer comments closed https://github.com/microsoft/vscode/issues/133365 in favor of this issue and marked https://github.com/microsoft/vscode/issues/169086, https://github.com/microsoft/vscode/issues/170455, and https://github.com/microsoft/vscode/issues/175750 as its duplicates. Searches for custom schemes and protocol links found no verified older open issue owning the full request. The older matching report https://github.com/microsoft/vscode/issues/104429 is closed for insufficient information, not a usable duplicate target.

The discussion includes additional Logos and notebook use cases; the Dendron-specific workaround at https://github.com/dendronhq/dendron/pull/1317 does not provide general Markdown or webview support.
