# Issue #344124 — Agents window: Akusto #kusto tool in a background session opens Kusto Explorer in the focused session

[https://github.com/microsoft/vscode/issues/344124](https://github.com/microsoft/vscode/issues/344124)

## Summary

The current extension webview path still targets the focused editor group without carrying the invoking session, so background tools can put their UI into another session's tabs. Keep this accepted, team-authored bug open; the platform contract needs a maintainer decision.

## Change summary

Prevent an editor opened by a background session's extension tool from becoming part of the focused session's editor tabs.

## Best solution

Give extension tools a supported way to avoid cross-session editor placement while preserving the user's focused session. Decide whether that means session-targeted editor opening or exposing enough invocation/focus context to suppress background reveals.

- **Validation:** Use two Agents-window sessions and an extension tool that creates a webview with ViewColumn.Active and preserveFocus: true. Invoke it in A, focus B before creation, and verify B's tabs and focus remain unchanged; switch back to A to check the chosen placement contract. Also verify explicit user-triggered opens and ordinary editor-window behavior remain unchanged.
- **Behavior:**

  > A background session's extension tool must not add its editor UI to the currently focused session's tabs. Reproduce by starting a delayed tool in A, switching to B, and letting the tool create its first webview. B must retain its tabs and focus. The maintainer must settle whether A receives the editor without being focused or the tool defers revealing it until an explicit user action.
- **Trace:**

  > ExtHostWebviewPanels.createWebviewPanel forwards only column/focus options, and MainThreadWebviewPanels resolves the active column to the currently active group. WebviewWorkbenchService.openWebview opens a pinned editor there; preserveFocus does not associate it with the initiating chat. BaseLayoutController assigns the singleton editor working set to the active session/chat, consistent with LAYOUT_CONTROLLER.md. This confirms the generic platform path described in https://github.com/microsoft/vscode/issues/344124 without executing Akusto. The boundary is extension-originated editor placement in the Agents window: preserve explicit opens, ordinary editor-window semantics, and layer direction. Akusto's singleton results selection is a separate extension behavior, not something session attribution alone resolves.
- **Open decisions:**
  - Should the supported contract place background-tool editors into the invoking session's working set without switching focus, or expose session/focus context so extensions can defer automatic reveals?
  - If session-targeted opening is selected, should both text-editor and webview show options accept the opaque tool invocation token or an explicit chat-session resource?
