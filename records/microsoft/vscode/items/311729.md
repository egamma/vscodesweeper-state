# Issue #311729 — Accessibility: Make chat action buttons persistently visible (or add setting) for voice/eye-tracker users

[https://github.com/microsoft/vscode/issues/311729](https://github.com/microsoft/vscode/issues/311729)

## Summary

A real accessibility gap remains on current main: chat code-block and response actions are visually hidden until hover or focus, with no setting for voice-control users who need persistent visual targets. Keep this open for an accessibility and chat UX decision on persistent visibility, text labels, and scope.

## Change summary

Provide a persistent, visually discoverable presentation of Copilot Chat actions for users who operate VS Code through voice control or eye tracking.

## Best solution

Provide an accessibility-oriented chat preference that keeps relevant response and code-block actions visible without hover, and decide whether it should also render visible text labels for OCR-based voice targeting. The behavior should cover the affected chat action surfaces consistently while retaining the compact default experience for users who do not enable it.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/codeBlockPart.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/media/codeBlockPart.css`, `src/vs/workbench/contrib/chat/browser/widget/media/chat.css`, `src/vs/workbench/contrib/accessibility/browser/accessibilityConfiguration.ts`
- **Validation:** With the chosen accessibility behavior enabled, render a chat containing multiple completed responses and a code block, move pointer and keyboard focus outside each response, and verify that all in-scope actions remain visible and voice/OCR-targetable; with it disabled, verify the existing compact hover/focus behavior remains unchanged.
- **Behavior:**

  > Voice-control and eye-tracker users must be able to discover and target the in-scope chat actions without first hovering an unknown location. Actions selected for this behavior remain visibly identifiable when neither their response nor code block is hovered or focused. If visible text labels are included, OCR-based control must be able to distinguish actions such as Copy, Run, and Insert. The ordinary compact presentation must remain available according to the product decision.
- **Trace:**

  > Current code-block actions are rendered in `.interactive-result-code-block-toolbar`; codeBlockPart.css suppresses that container with zero opacity and disabled pointer events until hover/focus, while CodeBlockPart only forces visibility during tracked hover or an open dropdown. `CodeBlockPart._configureForScreenReader()` creates and exposes the toolbar DOM for assistive technology but does not make it visually persistent. Response header and footer action visibility is controlled separately in widget/media/chat.css, so the issue spans more than the code-block toolbar. Existing accessibility configuration has chat progress and checkmark preferences but no persistent-action preference. Preserve keyboard navigation, ARIA labels, lazy toolbar construction where compatible, and the existing compact behavior outside the chosen accessibility mode.
- **Open decisions:**
  - Should actions be persistently visible by default, only while an accessibility preference is enabled, or automatically under an existing accessibility mode?
  - Does persistent visibility apply only to code-block actions, or consistently to response header and footer actions as well?
  - Must the accessible presentation include visible text labels for OCR targeting, or are persistently visible icon buttons with tooltips and ARIA labels sufficient?
  - If text labels are shown, should every action receive one or only primary actions such as Copy, Run, and Insert?

## Evidence

- **other response actions are also conditionally visible:** src/vs/workbench/contrib/chat/browser/widget/media/chat.css hides header toolbars outside hover/focus at lines 246-249 and gives completed-response footer toolbars zero opacity at lines 340-347, revealing them for the most recent response, focus, or group hover at lines 350-357.
