# Issue #346149 — Disabling a Copilot CLI-installed plugin in VS Code also disables it in Copilot CLI; no way to hide CLI plugins in VS Code only

[https://github.com/microsoft/vscode/issues/346149](https://github.com/microsoft/vscode/issues/346149)

## Summary

Keep open for a VS Code-only plugin exclusion design. Current source deliberately synchronizes global enablement with the owning runtime; workspace-local overrides and partial duplicate detection do not fully provide the requested isolation.

## Change summary

Allow independently installed VS Code and Copilot CLI plugins to coexist without duplicate contributions or cross-tool disabling.

## Best solution

Provide an explicit VS Code-local inclusion scope without silently changing Copilot CLI's global state, while retaining intentional runtime-global management. Define how equivalent installations are identified and selected before changing existing enablement semantics.

- **Behavior:**

  > Users with equivalent plugins installed independently in VS Code and Copilot CLI need a way to avoid duplicate VS Code contributions without disabling the CLI installation. The chosen local exclusion must persist at its documented scope. Explicit runtime-global management must remain distinguishable from VS Code-only inclusion, and policy-managed plugins must retain their enforced state.
- **Trace:**

  > setAgentPluginEnablement in src/vs/workbench/contrib/chat/common/plugins/agentPluginService.ts explicitly invokes the installation's runtime callback for profile/global states, whereas workspace states only update the local model. CopilotCliAgentPluginDiscovery in agentPluginServiceImpl.ts wires the callback to IAgentHostService.setPluginEnabled and imports the runtime's enabled state as the local default. Existing tests assert this synchronization, so removing the callback would change an intentional contract rather than merely repair an accidental write. agentPluginEnablement.ts and CollisionEnablementModel already suppress some equivalent installations, but CLI marketplace bucket identities do not generally match VS Code repository identities. Preserve remote/provider ownership, enterprise enforcement and explicit global management. https://github.com/microsoft/vscode/issues/343334 is relevant migration work, not a settled answer to local isolation. Uncertainty begins at which user-visible scope and interaction should deliver that isolation.
- **Open decisions:**
  - Should the existing profile-labelled toggle become VS Code-local, or should a separate local-exclusion action preserve its current runtime-global behavior?
  - Should local exclusion apply across VS Code profiles or only within the selected profile?
  - When equivalent independent installations are detected, should VS Code select one automatically or preserve an explicit user choice?
