# Issue #339264 — git.worktreeSymlinkFolders: removing a worktree deletes symlink target

[https://github.com/microsoft/vscode/issues/339264](https://github.com/microsoft/vscode/issues/339264)

## Summary

Traced the code path and the gap is real: deleteWorktree (extensions/git/src/repository.ts) just delegates to native `git worktree remove` with no step that first unlinks the junction/symlinks created by `git.worktreeSymlinkFolders`, so if native git's recursive removal follows the Windows junction, the symlink target's contents are deleted. Opt-in and brand-new feature, but potential data loss outside the worktree, so this stays open rather than being dismissed as stale.

## Change summary

With git.worktreeSymlinkFolders enabled, removing a worktree deletes the contents of the symlink target directory instead of just the symlink/junction itself.

## Best solution

Before calling repository.deleteWorktree -> `git worktree remove`, have VS Code explicitly detect and unlink (not rmdir) the symlinks/junctions it created in the worktree (or that it finds via lstat) so native git's recursive directory removal never has to traverse them.

## Plan brief

- **Likely files:** `extensions/git/src/repository.ts`, `extensions/git/src/worktreeSymlink.ts`, `extensions/git/src/git.ts`
- **Validation:** A test (or manual repro on Windows) confirming that after enabling git.worktreeSymlinkFolders, creating a worktree, and running git.deleteWorktree, the symlink target directory and its contents remain intact while only the worktree's junction/symlink and worktree itself are removed.
- **Open decisions:**
  - Should VS Code persist the list of symlinked folders per worktree (e.g. in workspace/global state) so deleteWorktree can precisely unlink them, or should it re-scan the worktree directory for symlinks/junctions at delete time?
  - If a symlink/junction is found at delete time, should VS Code always unlink it before calling `git worktree remove`, or only when it can confirm it was VS Code-created (to avoid touching user-created symlinks)?
  - Does this need platform-specific handling (Windows junctions vs. POSIX symlinks), given `git worktree remove`'s behavior may already differ there?

## Evidence

- **symlink creation:** extensions/git/src/worktreeSymlink.ts createWorktreeSymlink() creates a Windows 'junction' (fsPromises.symlink(sourcePath, targetPath, 'junction')) pointing from the worktree into the main repo for configured folders.
- **no cleanup on delete:** extensions/git/src/repository.ts deleteWorktree() (line ~2267) only calls this.repository.deleteWorktree(path, options) which in git.ts just runs `git worktree remove [--force] <path>` — there is no step anywhere that re-identifies and unlinks the previously created symlink folders before removal, and the createdDirectories list from _symlinkWorktreeFolders is never persisted or reused at delete time.
- **feature recency:** worktreeSymlink.ts and its config option are very recent additions to this repo, consistent with this being an unhandled edge case rather than a regression in long-stable code.
