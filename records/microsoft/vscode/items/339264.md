# Issue #339264 — git.worktreeSymlinkFolders: removing a worktree deletes symlink target

[https://github.com/microsoft/vscode/issues/339264](https://github.com/microsoft/vscode/issues/339264)

## Summary

Real, unaddressed gap: VS Code's deleteWorktree flow never removes or neutralizes the symlinks/junctions created by the experimental git.worktreeSymlinkFolders setting before handing removal off to native `git worktree remove`, so the reported data-loss path is plausible and unmitigated in the current source.

## Change summary

Removing a Git worktree created with git.worktreeSymlinkFolders deletes the contents of the symlink's target directory instead of just the symlink.

## Best solution

In Repository.deleteWorktree (extensions/git/src/repository.ts) / Git.deleteWorktree (extensions/git/src/git.ts), unlink the symlinks/junctions placed by createWorktreeSymlink before invoking native `git worktree remove`, so the recursive native removal can never traverse into the linked target directory.

## Plan brief

- **Likely files:** `extensions/git/src/repository.ts`, `extensions/git/src/git.ts`, `extensions/git/src/worktreeSymlink.ts`
- **Validation:** A test (in or alongside worktreeSymlink.test.ts) that creates a worktree with git.worktreeSymlinkFolders set, deletes the worktree, and asserts the symlink's target directory and its files still exist afterward in the main worktree.
- **Behavior:**

  > Deleting a Git worktree that was created with git.worktreeSymlinkFolders must remove only the symlink/junction placeholders VS Code placed inside that worktree, never follow them into the main worktree's real directories. After the delete (via the Worktrees UI or git.deleteWorktree / git.deleteWorktree2), the target directories the symlinks pointed at, and all their contents, must remain fully intact; only the worktree directory and its own symlink entries should be gone. Acceptance: a test that creates such a worktree, deletes it, and confirms the symlink target directory/files survive.
- **Trace:**

  > Repository.deleteWorktree (extensions/git/src/repository.ts ~line 2267) delegates entirely to Git.deleteWorktree (extensions/git/src/git.ts ~line 2291), which just runs `git worktree remove [--force] <path>` — the native git binary performs the actual filesystem removal, and nothing in VS Code's code unlinks or protects the symlinks/junctions that createWorktreeSymlink (extensions/git/src/worktreeSymlink.ts) placed inside that same worktree via fsPromises.symlink(sourcePath, targetPath, process.platform === 'win32' ? 'junction' : 'dir'). No test in worktreeSymlink.test.ts covers removal. Boundary: the fix belongs in the removal flow (repository.ts/git.ts, plus a possible cleanup helper in worktreeSymlink.ts) — do not change symlink creation or the unrelated worktreeInclude copy logic. Whether native `git worktree remove` actually follows the junction/symlink into its target on Windows was not executed/verified in this read-only sandbox, but the reporter's precise steps plus the total absence of any VS Code-side mitigation make the mechanism credible.
- **Open decisions:**
  - Should cleanup re-derive candidate symlink folders by recomputing the current git.worktreeSymlinkFolders patterns at delete time, or should VS Code persist/track the exact set of paths it symlinked at creation time?
  - Should the removal step defensively unlink ANY symbolic link/junction found within the worktree tree (safer, also covers externally-created links), or only the ones VS Code itself is confident it created?
  - If a given link can't be safely verified/unlinked, should the whole worktree delete be blocked (favoring safety) or should it log a warning and proceed with the native removal?

## Evidence

- **deletion path:** Repository.deleteWorktree (extensions/git/src/repository.ts:2267) only calls this.repository.deleteWorktree(path, options), which in git.ts:2291-2299 runs `git worktree remove [--force] <path>` via the native git binary — no VS Code code touches the worktree's symlinks before that call.
- **symlink creation:** createWorktreeSymlink (extensions/git/src/worktreeSymlink.ts) creates a directory symlink on POSIX or a 'junction' on Windows at targetPath pointing at the corresponding folder in the main worktree (fsPromises.symlink(sourcePath, targetPath, 'junction'|'dir')).
- **no removal counterpart:** worktreeSymlink.ts and worktreeSymlink.test.ts contain no removal/cleanup logic or tests for the symlinks they create — grepping for 'remove'/'delete' in the test file returns nothing.
