# Issue #250398 — Clicking a diff tag should reveal the diff in the open change editor not opening a new diff editor.

[https://github.com/microsoft/vscode/issues/250398](https://github.com/microsoft/vscode/issues/250398)

## Summary

The polish gap remains on current main: activating an edit pill always opens a standalone two-way diff instead of revealing that resource in an already-open changes editor. This team-authored issue was subsequently accepted as `polish`, so it should remain open for the chat UX owners.

## Change summary

Make a chat edit pill reveal its file in the open changes editor rather than opening another diff editor.

## Best solution

When the relevant chat changes editor is already open, reuse it and reveal the pill's before/after resource; retain an intentional fallback when no matching changes editor exists.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatMarkdownContentPart.ts`, `src/vs/workbench/contrib/chat/browser/editorChatResponseFileChangesService.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/chatContentParts/chatChangesSummaryPart.test.ts`
- **Validation:** Add a chat browser unit test with a matching open multi-diff editor: activating an edit pill must reuse that editor and pass revealData for the selected before/after resource without adding another editor; also cover the agreed no-match fallback.
- **Behavior:**

  > Activating a chat edit pill while the corresponding changes editor is open reveals that file's diff in the existing editor and does not create another editor tab. The reveal targets the pill's exact before/after resource and preserves normal modifier-key opening behavior. The agreed fallback applies when no corresponding changes editor is open.
- **Trace:**

  > CollapsedCodeBlock in src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatMarkdownContentPart.ts currently handles activation through showDiff(), which always opens a standalone resource diff. Chat changes editors are opened by openChatFileChanges() in src/vs/workbench/contrib/chat/browser/editorChatResponseFileChangesService.ts with randomly generated multi-diff source URIs. MultiDiffEditorInput.matches() compares source URIs, while MultiDiffEditor in src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditor.ts already supports revealing a resource through viewState.revealData. The uncertainty starts at how a pill and an open changes editor should share stable identity and what should happen when multiple or no matching editors exist. Do not change ordinary file opening, created/deleted-file handling, or unrelated multi-diff consumers.
- **Open decisions:**
  - When no corresponding changes editor is open, should activating the pill keep today's standalone two-way diff behavior or open a changes editor containing the request's change set?
  - If more than one changes editor contains the resource, should matching be scoped to the same chat request, the same chat session, or the active editor?

## Evidence

- **current source:** src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatMarkdownContentPart.ts wires CollapsedCodeBlock activation to showDiff(), which directly calls IEditorService.openEditor with original and modified resources; it does not look for or reveal within an existing changes editor.
- **changes editor capability:** src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditor.ts applies IMultiDiffEditorOptions.viewState.revealData by calling the multi-diff widget's reveal() method, so the underlying editor supports revealing a specific resource.
- **matching limitation:** src/vs/workbench/contrib/chat/browser/editorChatResponseFileChangesService.ts creates each chat multi-diff source with a random URI, while MultiDiffEditorInput.matches() in src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts matches multi-diff editors by source URI. The current path therefore has no stable identity connecting an edit pill to the relevant open changes editor.
