# Issue #324175 — Should Browser become visible when Agent opens it?

[https://github.com/microsoft/vscode/issues/324175](https://github.com/microsoft/vscode/issues/324175)

## Summary

Keep open: current source supports background browser pages and a browser pill, but active-session browsing can still reveal the browser automatically. The remaining question is the default reveal policy and whether an explicit user request should authorize a tool-driven reveal.

## Change summary

Keep agent browsing hidden by default, expose an activity indicator with an open action, and allow explicitly requested browser reveals.

## Best solution

Settle the active-session browser reveal policy, reusing the existing browser pill for discovery and manual opening. Coordinate with background-page lifecycle work without treating that infrastructure request as a substitute for this user-facing decision.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/browserView/browser/sessionBrowserView.ts`, `src/vs/sessions/contrib/chat/browser/sessionBrowsersControl.ts`, `src/vs/workbench/contrib/browserView/electron-browser/browserViewWorkbenchService.ts`, `src/vs/workbench/contrib/browserView/electron-browser/tools/openBrowserTool.ts`
- **Validation:** After settling the contract, exercise agent page creation in active and inactive sessions: ordinary browsing must follow the chosen visibility policy, the browser pill must open the correct live page, an explicitly requested reveal must follow the agreed authorization semantics, and read/click operations must work while the page remains hidden.
- **Behavior:**

  > An agent opening a page in the active session can currently make the browser visible even when the user does not want to monitor it. The requested experience keeps browsing unobtrusive while making the live page discoverable and manually openable. Acceptance must cover active and inactive sessions, explicit user-requested reveals, and successful browser interaction without requiring the user to open the page.
- **Trace:**

  > OpenBrowserTool._openNewPage in src/vs/workbench/contrib/browserView/electron-browser/tools/openBrowserTool.ts requests preserveFocus but not background opening, and exposes no reveal parameter. BrowserViewWorkbenchService._openEditorForCreatedView applies conditional inactive behavior; SessionBrowserViewController in src/vs/sessions/contrib/browserView/browser/sessionBrowserView.ts prevents automatic opening for inactive owning sessions but permits it for active ones. SessionBrowsersControl already supplies browser discovery and explicit opening, so the visibility decision does not require inventing a separate browser list. Preserve session ownership, page-sharing boundaries and manual browser opening. https://github.com/microsoft/vscode/issues/311974 concerns background-page lifecycle, while https://github.com/microsoft/vscode/issues/332409 identifies a hidden-page interaction constraint. The unresolved boundary is the user-facing reveal contract, not the existence of background-page infrastructure.
- **Open decisions:**
  - Should ordinary agent-created pages remain hidden by default in active sessions across both the Agents Window and the regular workbench, or only in the Agents Window?
  - Should an explicit user request let the agent reveal a page through a tool parameter, or should revealing remain a user-operated action?

## Evidence

Its input schema exposes url and forceNew, but no explicit reveal control. Preserving keyboard focus does not itself prevent editor visibility.
- **Active-session gap remains:** src/vs/sessions/contrib/browserView/browser/sessionBrowserView.ts: SessionBrowserViewController permits automatic editor opening for the active owning session. src/vs/workbench/contrib/browserView/electron-browser/browserViewWorkbenchService.ts: _openEditorForCreatedView marks agent editors inactive when the chat widget is not visible or the target group contains that session's chat editor, rather than applying a universal hidden default.
