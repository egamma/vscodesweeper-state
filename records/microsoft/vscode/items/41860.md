# Issue #41860 — Allow to "Scope to this" in explorer

[https://github.com/microsoft/vscode/issues/41860](https://github.com/microsoft/vscode/issues/41860)

## Summary

This remains the accepted canonical request: current Explorer filtering is temporary and does not provide a folder-scoped tree, while newer same-symptom reports continue to be closed into this issue. Its Backlog milestone and 173 community upvotes strongly support keeping it open for design and implementation.

## Change summary

Add an Explorer action that temporarily narrows the tree to a selected folder without changing the workspace root or its configuration.

## Best solution

Provide a reversible Explorer scope with a folder context-menu action and a clear reset affordance, while preserving the actual workspace roots and extension-host view of the workspace. A maintainer should first settle persistence, multi-folder behavior, and whether scope affects only Explorer or also Quick Open, Search, and new terminals.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/browser/fileActions.ts`, `src/vs/workbench/contrib/files/browser/fileActions.contribution.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Add targeted Explorer view tests, runnable with `scripts/test.sh --grep "Files - ExplorerView"`, covering entering scope on a nested folder, showing only that subtree, resetting to the original workspace roots, and preserving existing files.exclude behavior.
- **Behavior:**

  > A user can invoke a folder action in Explorer to temporarily display that folder as the focused tree without changing the workspace root or workspace configuration. The scoped view has an obvious way to return to the complete Explorer, and existing files.exclude rules continue to apply. Acceptance should cover entering and leaving scope, nested folders, and whichever multi-root and reload semantics the maintainer selects. Quick Open, Search, and terminal behavior must follow the explicitly chosen product boundary rather than changing incidentally.
- **Trace:**

  > ExplorerView.setTreeInput in src/vs/workbench/contrib/files/browser/views/explorerView.ts currently chooses only the workspace roots supplied by IExplorerService. ExplorerFindProvider in explorerViewer.ts can temporarily filter tree contents but restores its saved input and has no selected-folder scope model. Explorer context actions are registered in fileActions.contribution.ts, with handlers generally implemented in fileActions.ts; the existing ExplorerView test harness can exercise tree input and context behavior. Current files.exclude handling belongs to FilesFilter and must remain configuration-driven rather than being overwritten as an implementation shortcut. This issue is the canonical record: https://github.com/microsoft/vscode/issues/232360 and https://github.com/microsoft/vscode/issues/148486 were directed here. Do not change actual workspace membership or restrict extensions' filesystem view unless a maintainer explicitly chooses that broader contract.
- **Open decisions:**
  - Is folder scope strictly an Explorer presentation state, or should it also constrain Quick Open, Search, and the working directory of newly created terminals?
  - Does scope persist across window reloads and workspace reopening, or end with the current window session?
  - Should multiple selected folders be scopeable together, especially in multi-root workspaces, or should the first version support exactly one folder?
  - When the active editor is outside the scope, should auto-reveal leave the scope unchanged, temporarily expose the file, or reset the scope?

## Evidence

- **current source gap:** src/vs/workbench/contrib/files/browser/views/explorerView.ts:setTreeInput always derives the tree input from IExplorerService.roots (lines 849-867); there is no selected-folder scope state.
- **existing filtering is not coverage:** src/vs/workbench/contrib/files/browser/views/explorerViewer.ts:ExplorerFindProvider implements a transient find/filter session, saves the original input and view state, and restores them when the session ends. It does not establish a folder as the Explorer root.
- **missing command surface:** src/vs/workbench/contrib/files/browser/fileActions.contribution.ts registers the Explorer context-menu actions but contains no Scope to This or Focus Folder action.
- **canonical ownership:** A VS Code maintainer closed the newer same-symptom report https://github.com/microsoft/vscode/issues/232360 as a duplicate of this issue. https://github.com/microsoft/vscode/issues/148486 was likewise closed as a duplicate after requesting Explorer folder isolation.
- **existing demand:** The issue is in the Backlog milestone with 173 community upvotes, and a maintainer previously described it as a fair feature request.
- **workaround limitation:** The discussion confirms that available extensions emulate the behavior by modifying files.exclude; commenters note that this can conflict with existing exclusions and does not represent a native, reversible Explorer scope.
- **no landed implementation:** The linked implementation attempts https://github.com/microsoft/vscode/pull/54905 and https://github.com/microsoft/vscode/pull/54911 were closed without merging, and current source still lacks the requested state and command.
