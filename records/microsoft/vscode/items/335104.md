# Issue #335104 — Agents window unable to open PR view

[https://github.com/microsoft/vscode/issues/335104](https://github.com/microsoft/vscode/issues/335104)

## Summary

Real, unfixed bug: the Agents window can't open a GitHub PR webview, and a collaborator ties it to a broader gap — the sessions/Agents-window layer doesn't register `workbench.extensions.installExtension` (confirmed via source), so extension-driven UI like the GHPR view or an install prompt fails. A Copilot coding-agent PR attempted a fix but was closed unmerged (WIP), so this isn't yet resolved on main.

## Change summary

Opening the GHPR pull-request webview from the Agents window fails to render, unlike the regular workbench.

## Best solution

Decide how much of the extensions contribution surface (command registration, install/enable flows, webview view hosting) the sessions/Agents-window layer needs to expose so extension-provided views like the GHPR PR webview work there; the closed WIP PR https://github.com/microsoft/vscode/pull/335408 is a starting point for scoping the fix.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/extensions/browser/extensions.contribution.ts`, `src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts`
- **Validation:** A regression test confirming the GHPR PR webview view renders when opened from the Agents window (or, at minimum, that `workbench.extensions.installExtension` resolves there).
- **Behavior:**

  > Opening a pull request from the Agents window should render the GHPR webview view, matching the standard workbench. Where the underlying cause is a missing install/enable command, invoking it from the Agents window should succeed instead of the 'command not found' error seen in the related report. Acceptance: manually or via test, confirm the PR webview renders in the Agents window for a repo with the GitHub Pull Requests extension available.
- **Trace:**

  > src/vs/sessions/contrib/extensions/browser/extensions.contribution.ts (the Agents-window extensions contribution) does not register `workbench.extensions.installExtension`, which src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts does for the main workbench — confirmed via grep, not full runtime trace. The exact mechanism by which this blocks the GHPR PR webview specifically (install prompt vs. webview-view registration vs. extension host scoping) is not yet pinned down; the closed WIP PR https://github.com/microsoft/vscode/pull/335408 attempted this trace but didn't land a fix. Boundary: do not broadly widen what commands/extensions the Agents window exposes without a scoping decision — this could affect security/perf posture of that layer.
- **Open decisions:**
  - Should the Agents window support the full `workbench.extensions.installExtension` flow (and if so, with what UI), or should GHPR webview access be special-cased separately?
  - Is the intended fix to make the sessions layer able to host arbitrary extension-contributed webview views, or only a narrower allowlist (e.g. just GHPR)?
