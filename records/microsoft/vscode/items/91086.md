# Issue #91086 — [npm] load description/homepage from referenced node module version

[https://github.com/microsoft/vscode/issues/91086](https://github.com/microsoft/vscode/issues/91086)

## Summary

The requested metadata resolution remains absent on current main: dependency hovers still query npm using the package-name key and ignore the declared GitHub dependency spec. A maintainer explicitly welcomed a PR, so this should remain open despite its age and lack of upvotes.

## Change summary

Show description and homepage metadata for the dependency reference declared in package.json instead of always querying the registry package with the same key.

## Best solution

For dependency values that identify another package source or version, resolve hover metadata from that declared npm package spec while preserving current registry-name behavior for ordinary semver dependencies. The supported spec types and fallback behavior should be settled before implementation.

## Plan brief

- **Likely files:** `extensions/npm/src/features/jsonContributions.ts`, `extensions/npm/src/features/packageJSONContribution.ts`, `extensions/npm/src/test/packageJSONContribution.test.ts`
- **Validation:** Add npm extension tests asserting that hover lookup for `"indexeddb": "github:azer/indexeddb"` uses the declared reference, while an ordinary semver dependency continues to use its package-name key; run `npm run test-extension -- --label npm`.
- **Behavior:**

  > Hovering a package.json dependency declared with a supported external package reference shows the description and homepage for the referenced package, not an unrelated registry package sharing the dependency key. Ordinary registry dependencies continue to show their current metadata. Unsupported or unresolvable references degrade without breaking package.json hover behavior. Acceptance tests must cover the reported `github:azer/indexeddb` case and an unchanged semver dependency.
- **Trace:**

  > On current main, JSONHoverProvider in extensions/npm/src/features/jsonContributions.ts computes a jsonc-parser Location and passes only the document URI and location to PackageJSONContribution. PackageJSONContribution.getInfoContribution in extensions/npm/src/features/packageJSONContribution.ts takes the final location path segment as the package name; fetchPackageInfo and npmView therefore query metadata for `indexeddb`, never the declared `github:azer/indexeddb` value. The existing npm test suite covers parseNpmViewOutput but not this lookup-selection path. Keep completion behavior, registry fallback, installed-version reporting, and unrelated package.json sections unchanged. The uncertainty starts at which npm dependency-spec forms should participate and what fallback is expected when a referenced source cannot provide metadata.
- **Open decisions:**
  - Should referenced metadata lookup apply to every dependency spec npm can resolve, or initially only hosted Git forms such as `github:user/repo`?
  - When referenced-spec metadata lookup fails, should the hover fall back to metadata for the dependency key, or omit remote metadata to avoid showing information for the wrong package?
