# Issue #311148 — Agents App: Support multi-root workspaces with cross-repo change tracking and worktrees

[https://github.com/microsoft/vscode/issues/311148](https://github.com/microsoft/vscode/issues/311148)

## Summary

Keep open and classify as a feature request: current main has multi-folder session infrastructure, but workspace-file selection and complete multi-repository Changes behavior remain missing. The request has 32 upvotes, and the verified related issues do not satisfy the stronger duplicate bar for this re-reviewed item.

## Change summary

Support opening multi-root workspace files in the Agents Window, selecting a repository per session, creating repository-specific worktrees, and reviewing changes across those sessions.

## Best solution

Complete the Agents Window workflow from workspace-file selection through repository-scoped sessions and worktrees, with repository identity and changes visible across the workspace. Reuse the existing multi-folder session model and coordinate with the related changeset work rather than treating additional folder context as full coverage.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts`, `src/vs/sessions/services/sessions/common/session.ts`, `src/vs/sessions/contrib/workspace/browser/workspaceFolderManagement.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/agentHostSessionChangesets.ts`, `src/vs/sessions/contrib/changes/browser/changesViewService.ts`, `src/vs/sessions/contrib/changes/browser/changesView.ts`
- **Validation:** Acceptance scenario: open a .code-workspace containing three independent Git repositories, create one worktree-isolated session targeting each repository, edit a file in each session, and verify repository labels, separate worktrees, repository-grouped diffs, and independent apply/merge behavior in one Agents Window. The plan should also establish focused regression checks for workspace-file resolution and secondary-root changes without changing single-folder behavior.
- **Behavior:**

  > A user can open a .code-workspace containing multiple independent Git repositories in the Agents Window and choose a target repository for each new session. Each isolated session uses a worktree belonging to its selected repository, and its repository identity remains visible. Changes from active sessions are discoverable in one place, grouped by repository, with independent repository-level apply or merge actions. Validate using three repositories and one edited file in each isolated session; existing single-folder workflows must remain unchanged.
- **Trace:**

  > ISessionWorkspace and ISessionFolder in src/vs/sessions/services/sessions/common/session.ts already represent multiple folders with individual Git information, and WorkspaceFolderManagementContribution mounts the active chat's folders. WorkspacePicker._browseForLocalFolder in src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts currently selects exactly one directory and disallows files. Agent Host already documents additional repository worktrees and chat-specific workspace scopes, so the missing capability is not a wholly absent workspace model. AgentHostSessionChangesets still filters multi-root last-turn changes to the primary working directory, while ChangesViewService derives repository operation state from folders[0]. Preserve provider-neutral session contracts and existing single-repository isolation behavior; additional context attachments are not equivalent to opening and managing the requested workspace. Coordinate with https://github.com/microsoft/vscode/issues/330148 and https://github.com/microsoft/vscode/issues/318936, neither of which is a valid duplicate target for this older re-reviewed item. The unresolved boundary is how the workspace remains available during repository-scoped session creation and how a cross-session overview coexists with chat-scoped Changes.
- **Open decisions:**
  - When a session targets one repository from a multi-root workspace, should the other repositories remain available as read-only context, editable context, or only as candidates for separate sessions?
  - Should the unified repository-grouped Changes overview be a separate workspace-level surface or a mode of the existing active-chat Changes panel?
