# Issue #304764 — Expose `mode` property on breakpoint classes to match DAP 1.65 `BreakpointMode` support

[https://github.com/microsoft/vscode/issues/304764](https://github.com/microsoft/vscode/issues/304764)

## Summary

The public breakpoint API still lacks mode support even though the internal implementation transports it. Keep this request open: the older related report covers source-breakpoint creation and display, but does not clearly own the full multi-class API proposal here.

## Change summary

Expose a supported, typed breakpoint mode property and constructor argument through the extension API.

## Best solution

Define the public breakpoint-mode contract for existing breakpoint classes, including consistent readback and display behavior. Explicitly settle instruction-breakpoint scope, since the current extension declarations do not expose an InstructionBreakpoint class.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTypes.ts`, `src/vs/workbench/api/common/extHostDebugService.ts`, `src/vs/workbench/api/browser/mainThreadDebugService.ts`
- **Validation:** The plan should end with an extension API test that creates breakpoints with an advertised mode using typed constructors, adds them through vscode.debug.addBreakpoints, and verifies mode readback and adapter request payloads. Manually verify that the Breakpoints view identifies the selected mode and that existing constructor calls remain compatible.
- **Behavior:**

  > Extensions should be able to create and inspect supported breakpoint modes without casts or undocumented property injection. Existing breakpoint constructor calls must remain compatible, and selected modes must reach the adapter unchanged. Acceptance should cover public typing, breakpoint readback, DAP forwarding, and the reported mode visibility limitation. The supported breakpoint classes must be agreed before implementation.
- **Trace:**

  > The public declarations in src/vscode-dts/vscode.d.ts omit mode, while Breakpoint, SourceBreakpoint, and FunctionBreakpoint in src/vs/workbench/api/common/extHostTypes.ts already accept and store it. ExtHostDebugService.addBreakpoints serializes mode for source and function breakpoints, and MainThreadDebugService.$registerBreakpoints forwards it without modeLabel. No InstructionBreakpoint class was found in the public or proposed declaration files, so that part is not merely an additional constructor argument. Preserve existing breakpoint behavior and do not expand unrelated DAP capabilities. https://github.com/microsoft/vscode/issues/230705 documents the overlapping source-breakpoint and display problem; https://github.com/eclipse-cdt-cloud/cdt-gdb-vscode/pull/211 demonstrates downstream use of the unsupported path.
- **Open decisions:**
  - Should this proposal expose mode only on existing extension API breakpoint classes, or also introduce an InstructionBreakpoint extension API?

## Evidence

- **Public API gap:** src/vscode-dts/vscode.d.ts:17081–17143 declares Breakpoint, SourceBreakpoint, and FunctionBreakpoint without a mode property or constructor parameter. Searching src/vscode-dts/*.ts also found no InstructionBreakpoint declaration or proposed breakpoint-mode API.
- **Internal support is not public coverage:** src/vs/workbench/api/common/extHostTypes.ts:1947–2002 already stores readonly mode and accepts it in SourceBreakpoint and FunctionBreakpoint constructors. src/vs/workbench/api/common/extHostDebugService.ts:425–468 serializes bp.mode, and src/vs/workbench/api/browser/mainThreadDebugService.ts:208–232 forwards it into the debug model. These internal paths explain the workaround but do not provide the requested public TypeScript contract.
- **Older related report verified:** https://github.com/microsoft/vscode/issues/230705 is open, was created on 2024-10-07, and reports the same source-breakpoint workaround and missing Breakpoints-view mode label. Its body is limited to source breakpoints and mode-label propagation; it does not clearly encompass this request's FunctionBreakpoint and InstructionBreakpoint API scope, so it is not a verified full-scope canonical for this re-reviewed item.
- **Linked extension PR preserves the gap:** https://github.com/eclipse-cdt-cloud/cdt-gdb-vscode/pull/211 merged on 2026-04-29. Its description explicitly retains the `(sp as any).mode` workaround and the missing Breakpoints-panel mode display; it implements extension commands rather than fixing the VS Code public API.
