## Summary

Keep open: the reported Windows shutdown-and-relaunch sequence is sufficient to retest, but source inspection cannot confirm why the restored windows lose their terminal editors. Current main includes auxiliary-window restoration and terminal revival; neither a fixing commit nor an open canonical covering this failure was verified.

## Change summary

Terminal sessions opened in separate windows return as empty VS Code windows after shutting down Windows and relaunching VS Code.

## Best solution

Ensure auxiliary windows restore their eligible terminal editors and supported persisted terminal state after application shutdown. Diagnose window-layout restoration separately from terminal serialization and process revival; this does not imply preserving a running Claude Code process across a PC shutdown.

With persistent sessions enabled, compare Developer: Reload Window, File: Exit followed by relaunch, and Windows shutdown followed by relaunch. Verify that the auxiliary window restores its terminal editor and supported saved state, with an equivalent terminal in the main window as a control; then compare the reported Claude Code workflow.
- **Behavior:**

  > A terminal in a separate VS Code window reportedly returns as an empty window after Windows shutdown and VS Code relaunch. Establish whether an ordinary integrated terminal reproduces this before involving extension-created terminals. For terminals eligible for persistence, acceptance requires restoring the terminal editor in its auxiliary window and the terminal state supported by the configured revival policy. Restarting arbitrary foreground applications across a PC shutdown is not part of this acceptance contract.
- **Trace:**

  > EditorParts.restoreParts and restoreState in src/vs/workbench/browser/parts/editor/editorParts.ts recreate auxiliary layouts independently of terminal process revival. TerminalInputSerializer in terminalEditorSerializer.ts serializes only terminals with a persistent process ID and shouldPersist; TerminalEditorService.reviveInput reconstructs their editor inputs. TerminalService._onBeforeShutdownAsync and _shouldReviveProcesses in terminalService.ts govern saved process state, while terminalProcessManager.ts determines persistence eligibility. Source inspection establishes these boundaries but does not locate the failing step for the reported Windows shutdown. The older auxiliary-restoration work at https://github.com/microsoft/vscode/issues/195887 predates this report and is not evidence of a subsequent fix. Preserve existing persistence settings and ordinary shutdown semantics; first distinguish a missing serialized terminal editor from a restored editor whose process cannot revive.

- **Current window restoration:** src/vs/workbench/browser/parts/editor/editorParts.ts:434-459 restores saved auxiliary parts when the main editor part restores its state; createState and restoreState persist and recreate each auxiliary part's editor layout. - **Terminal persistence eligibility:** src/vs/workbench/contrib/terminal/browser/terminalEditorSerializer.ts: TerminalInputSerializer.canSerialize requires a numeric persistentProcessId and terminalInstance.shouldPersist. deserialize calls TerminalEditorService.reviveInput in terminalEditorService.ts. terminalProcessManager.ts excludes feature terminals without reconnection properties and transient terminals from normal persistence, so window restoration and terminal restoration can diverge.
