# Issue #336665 — Allow agents to create research sessions without a new worktree

[https://github.com/microsoft/vscode/issues/336665](https://github.com/microsoft/vscode/issues/336665)

## Summary

Milestone 1.140.0 is assigned, which is a real scheduling milestone and blocks any close under the hard keep-open rules, independent of the merits — but on the merits this also looks like a real, unresolved product question rather than something already covered.

## Change summary

Give an orchestrating agent an explicit, unambiguous way to create an independent session in the current workspace without a new worktree, for read-only research work, without requiring the schema to be misread as "omit = no worktree".

## Best solution

A maintainer should decide whether `create_session` should let an agent set `worktree: false` on its own initiative for research-only work (today's schema text restricts that to explicit user requests), or whether a separate purpose/readOnly flag is warranted; then tighten the tool description and AGENTS.md accordingly.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/shared/sessionServerTools.ts`, `src/vs/platform/agentHost/AGENTS.md`
- **Validation:** Once decided, a `sessionServerTools.test.ts` case exercising `create_session` with `relationship: independent`, a new workspace, and the agreed-upon no-worktree signal should resolve to folder isolation instead of worktree isolation.
- **Trace:**

  > The tool's `worktree` argument and its AGENTS.md description currently gate `false` on an explicit user request, so an agent that independently judges a task to be read-only research has no documented, agent-initiated way to skip worktree creation; omitting the field falls through to 'inherit or default to worktree' logic in `getCreateSessionArgs`/session creation resolution (sessionServerTools.ts), never to folder isolation. Do not change the inheritance behavior for the `currentSession` relationship or for cases where the workspace matches the creating session's own project — those paths are unaffected and out of scope.
- **Open decisions:**
  - Should an orchestrating agent be allowed to set `worktree: false` on its own initiative for read-only/research work, without a literal user request, or should a distinct purpose/readOnly signal be introduced instead?
  - If a new signal is introduced, what should it be called and how should it interact with the existing `worktree` boolean and the inherit-from-parent-session default?

## Evidence

- **current schema text:** src/vs/platform/agentHost/node/shared/sessionServerTools.ts: the `worktree` input description says 'Set true only when the user explicitly asks to create a worktree, or false only when the user explicitly asks to work without one. Omit to preserve the existing isolation behavior: inherit the creating session's isolation for the same project, otherwise use worktree isolation.' — omission is documented as 'inherit', not 'no worktree'.
- **resolution logic:** getCreateSessionArgs/resolveCreateSessionRequest (same file, ~lines 526-568, 851-870): when `workspace` is supplied and `worktree` is omitted, isolation defaults to 'worktree' unless the target workspace matches the creating session's own project, in which case it inherits that session's isolation. There is no path where an omitted `worktree` on a genuinely new workspace skips worktree creation.
- **AGENTS.md spec:** src/vs/platform/agentHost/AGENTS.md 'Server-tool creation provenance' section: 'Agents must set it only when the user explicitly asks to create a worktree (true) or work without one (false); otherwise they must omit it.' — this explicitly ties `worktree: false` to a user request, which is at odds with an agent autonomously deciding no worktree is needed for research.
