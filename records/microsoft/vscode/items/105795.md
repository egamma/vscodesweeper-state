# Issue #105795 — Go to next error/warning/info

[https://github.com/microsoft/vscode/issues/105795](https://github.com/microsoft/vscode/issues/105795)

## Summary

Keep open: built-in problem navigation still includes errors, warnings, and information together, so severity-selective shortcuts remain missing. The request has 92 upvotes, and the verified older related issue requests different navigation behavior rather than covering this full scope.

## Change summary

Allow next and previous problem navigation to select diagnostic severities independently, within the current file or across files.

## Best solution

Provide independently bindable severity-selective navigation in the existing marker-navigation feature, preserving the current unfiltered shortcuts. Settle the command contract and interaction with Problems view filters before implementation.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/gotoError/browser/gotoError.ts`, `src/vs/editor/contrib/gotoError/browser/markerNavigationService.ts`, `src/vs/workbench/contrib/notebook/browser/contrib/marker/markerProvider.ts`
- **Validation:** Use a fixture with errors, warnings, and information in two files. Verify independently selected severities for both navigation directions and both file scopes, wraparound, no matching diagnostics, and updates as diagnostics disappear. Confirm existing F8/Shift+F8 and Alt+F8/Shift+Alt+F8 behavior remains unchanged, and notebook navigation retains its resource scope. Add runnable marker-navigation tests for the settled contract; no tests or builds were run during this read-only review.
- **Behavior:**

  > Users can independently bind navigation that visits only selected diagnostic severities, including errors-only, warnings-only, and information-only. Selection works in both directions within the current file and across files, without visiting excluded severities. Existing unfiltered shortcuts retain their behavior. Acceptance includes wraparound, no matching diagnostics, and diagnostic changes during navigation; interaction with Problems view filters remains a product decision.
- **Trace:**

  > MarkerNavigationAction.run in src/vs/editor/contrib/gotoError/browser/gotoError.ts forwards only direction and file scope to MarkerController.navigate. MarkerController obtains and reuses a MarkerList through IMarkerNavigationService, including when navigation opens another editor. In src/vs/editor/contrib/gotoError/browser/markerNavigationService.ts, MarkerList reads a fixed Error|Warning|Info mask; problems.sortOrder changes ordering, not membership. Problems view severity filters are not part of that path. The notebook MarkerListProvider in src/vs/workbench/contrib/notebook/browser/contrib/marker/markerProvider.ts supplies notebook-scoped resource filtering, which must remain intact. Preserve existing command defaults, navigation presentation, and resource boundaries; automatic highest-severity fallback from https://github.com/microsoft/vscode/issues/97643 is related but not equivalent. The remaining uncertainty is the public command contract and whether explicit severity selection also honors Problems view filters.
- **Open decisions:**
  - Should severity selection be exposed through dedicated commands, arguments on the existing commands, or both?
  - Should explicitly severity-selective navigation operate independently of Problems view filters, or also exclude diagnostics hidden by those filters?

## Evidence

- **Existing command boundary:** src/vs/editor/contrib/gotoError/browser/gotoError.ts registers editor.action.marker.next, editor.action.marker.prev, editor.action.marker.nextInFiles, and editor.action.marker.prevInFiles. MarkerNavigationAction.run passes only direction and file scope to MarkerController.navigate; it does not consume severity arguments.
- **Missing severity selection:** src/vs/editor/contrib/gotoError/browser/markerNavigationService.ts constructs MarkerList with resource filtering only. Its updateMarker callback always reads MarkerSeverity.Error | MarkerSeverity.Warning | MarkerSeverity.Info, and move cycles through the resulting list.
- **Settings do not cover the request:** src/vs/workbench/contrib/markers/browser/markers.contribution.ts registers problems.sortOrder with severity and position choices. MarkerList uses this setting to order markers within each resource, not exclude unwanted severities; Problems view severity filters are not consulted by this navigation path. F8 therefore does not provide errors-only navigation.
- **Verified related issue is not a canonical:** https://github.com/microsoft/vscode/issues/97643 is open and older, but its clarification requests cycling only the highest severity currently present, falling back when higher-severity problems disappear. That differs from independently selecting errors, warnings, or information regardless of other severities, so it does not absorb this re-reviewed request.
- **Duplicate direction:** https://github.com/microsoft/vscode/issues/103314 is closed. A maintainer explicitly marked it a duplicate of this issue at https://github.com/microsoft/vscode/issues/103314#issuecomment-726689911, supporting this issue as the existing home for separate severity shortcuts rather than providing a closing target.
- **Demand and workarounds:** The issue has 92 community upvotes and is accepted into Backlog. Comments recommend yy0931.go-to-next-error and Gist.go-to-problem; another suggests lowering spell-check diagnostics to Hint. These are external or partial workarounds, not built-in coverage or a maintainer decision to exclude the capability from core.
- **Canonical and implementation search:** Open-issue searches for next/error/warning, navigation/severity, and problem/filter/navigation found no verified canonical covering independent severity navigation. Searching open issues and PRs for 105795 returned this issue only; no open implementation candidate was identified.
- **Shared provider boundary:** src/vs/workbench/contrib/notebook/browser/contrib/marker/markerProvider.ts registers a MarkerListProvider that groups cell resources within a notebook. Any marker-navigation design must preserve this resource-scoping behavior rather than bypass the provider.
