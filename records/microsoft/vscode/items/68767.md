# Issue #68767 — Restart task fails if task already completed

[https://github.com/microsoft/vscode/issues/68767](https://github.com/microsoft/vscode/issues/68767)

## Summary

Current task policies cover automatic restart when a build is already running, and the restart helper now checks whether it has completed. However, the requested state-independent, explicitly targeted restart shortcut remains missing; keep this accepted On Deck request open.

## Change summary

Allow a task shortcut to start or restart its target regardless of whether that task is running, completed, or has never run.

## Best solution

Provide an explicitly targeted start-or-restart operation that honors the requested task regardless of its execution state, while preserving the default safeguards for watch tasks and unrelated running tasks. Retain the existing instance policies for users who only need automatic replacement of an active build.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts`, `src/vs/workbench/contrib/tasks/browser/task.contribution.ts`
- **Validation:** Exercise a keybinding with an explicit task argument when its target has never run, has completed, is running, and is inactive while an unrelated task runs. Verify the requested target starts or restarts exactly once, unrelated tasks remain untouched, and selecting restart after completion does not produce a termination warning; cover these cases in task-service command tests.
- **Behavior:**

  > An explicitly targeted task operation should start the selected task when inactive and restart it when running, without requiring the user to inspect its state first. An unrelated running task must not substitute for the requested target. A restart selected after the target finishes should still launch the target without a spurious termination warning. Existing default build and watch-task safeguards should remain unchanged unless the maintainer explicitly chooses otherwise.
- **Trace:**

  > AbstractTaskService._handleInstancePolicy already supports prompt-free active-instance replacement through runOptions.instancePolicy, and _restart checks activity before termination. The remaining gap is _runRestartTaskCommand in src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts: it enumerates only active tasks and bypasses its argument when exactly one task is active. task.contribution.ts currently names this public command Restart Running Task, so extending it to start inactive tasks changes its observable contract. The terminal-specific rerun action does not resolve arbitrary named tasks that have never run. https://github.com/microsoft/vscode/issues/106227 supplies an independent historical report of the prompt-completion case, but is closed and newer. Preserve unrelated task executions, default watch-task behavior, and existing task resolution and save-before-run semantics; no code was executed and no fixing commit was established.
- **Open decisions:**
  - Should an explicit argument to workbench.action.tasks.restartTask enable start-or-restart behavior for inactive tasks, or should that behavior be exposed through a separate command while Restart Running Task retains its active-only contract?
