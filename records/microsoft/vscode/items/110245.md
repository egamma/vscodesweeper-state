# Issue #110245 — Allow `createWebviewPanel` to open tab in preview mode

[https://github.com/microsoft/vscode/issues/110245](https://github.com/microsoft/vscode/issues/110245)

## Summary

The requested capability remains missing: createWebviewPanel exposes no preview option, and the workbench explicitly opens these panels pinned. Keep this team-authored, accepted Backlog request open; the related reports do not provide a valid duplicate target.

## Change summary

Allow extension-created webview panels to participate in normal preview-tab behavior instead of always opening permanent tabs.

## Best solution

Provide an opt-in public API for webview preview tabs while preserving existing callers' pinned behavior and respecting the user's preview-editor setting. Settle the panel promotion and replacement semantics with the API owners before implementation.

- **Validation:** Use an Extension Development Host to create successive opted-in preview webviews with workbench.editor.enablePreview enabled: verify preview tab state and replacement, then pin a panel and verify it survives subsequent opens. Repeat with preview disabled and with existing callers that omit the option; both must retain permanent-tab behavior. Add targeted API option-forwarding and workbench tab-lifecycle coverage once the contract is agreed.
- **Behavior:**

  > Extensions currently cannot request preview-tab behavior when creating standalone webview panels, so browsing items can accumulate permanent tabs. An opted-in panel should follow the agreed standard preview replacement and promotion behavior, while existing callers remain unchanged. Acceptance must cover successive preview opens, explicit pinning, disabled preview editors, and the existing focus-preservation behavior.
- **Trace:**

  > The public createWebviewPanel declaration in src/vscode-dts/vscode.d.ts has no preview option. ExtHostWebviewPanels.createWebviewPanel and WebviewPanelShowOptions carry only column and focus preferences to MainThreadWebviewPanels.$createWebviewPanel, and WebviewWorkbenchService.openWebview explicitly sets pinned: true. This establishes the missing capability without executing code. Preserve existing creation defaults, focus behavior, and custom-editor behavior; custom editors are not equivalent to standalone panels without document resources. The related https://github.com/microsoft/vscode/issues/140248 records maintainer interest and questions around promoting edited panels, but it is newer and closed, not a duplicate target. The remaining uncertainty is the public contract for preview promotion and replacement, not whether the creation path currently supports preview.
- **Open decisions:**
  - Should the initial API support only standard user-driven pinning, or also let an extension promote a preview panel when an interaction changes its content or state?
  - Should an opted-in webview use the editor group's shared preview slot, replacing and being replaced by other preview editors, or have a webview-specific reuse boundary?
