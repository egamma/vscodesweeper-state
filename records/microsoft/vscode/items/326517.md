## Summary

Plausible bug in the tools configuration picker for custom agent frontmatter — the 'edit' group tools may not reflect their saved state when the dialog reopens. However, the report is on an older build (1.129.0 vs 1.129.1), mixes two potentially unrelated issues (edit checkbox state and apply_patch), and hasn't been confirmed by anyone. Requesting info on whether it reproduces on the latest build.

## Change summary

The tools configuration dialog for custom agents always shows 'edit' sub-tools as unchecked when reopened, even though they were previously saved to the frontmatter.

## Best solution

If confirmed on latest, investigate `toToolAndToolSetEnablementMap` and `computeItems` in `chatToolPicker.ts` — when frontmatter contains individual edit sub-tool names like `edit/createFile` rather than the top-level `edit`, the toolset's checked state is false and the child checked states may not propagate correctly in the tree picker UI. The fix likely belongs in `src/vs/workbench/contrib/chat/browser/actions/chatToolPicker.ts` or `src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts`.

## Evidence

- **tools picker code path:** The tools configuration dialog is implemented in src/vs/workbench/contrib/chat/browser/actions/chatToolPicker.ts. When individual edit sub-tools (e.g. `edit/createFile`) are in the frontmatter, `toToolAndToolSetEnablementMap` at src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts:1600 resolves them correctly as enabled, but the parent toolset 'edit' stays disabled since it's not in the frontmatter names set.
- **dual appearance of tools:** In `computeItems`, tools belonging to a toolset appear both as children of the toolset tree item AND as direct children of the Built-In bucket. The `collectResults` function at line 597 uses AND logic for duplicates — if a tool is unchecked in any appearance, it stays unchecked.
- **apply_patch separate concern:** The apply_patch 'command not found' issue is likely unrelated — apply_patch is a built-in tool handled by the Copilot extension's edit tool implementation, not a shell command. This may be a separate WSL-specific issue.
