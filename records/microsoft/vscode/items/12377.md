# Issue #12377 — Mac: Provide a setting to hide the title bar and inline the window controls

[https://github.com/microsoft/vscode/issues/12377](https://github.com/microsoft/vscode/issues/12377)

## Summary

Keep this accepted, well-supported request open: current settings do not remove the dedicated title-bar row in a normal macOS window while retaining inline traffic lights. The verified related requests are newer and cannot replace this re-reviewed report.

## Change summary

Provide a supported macOS layout that saves vertical space by integrating window controls into existing workbench chrome instead of a separate title-bar row.

## Best solution

Design an opt-in compact macOS layout that retains native window controls and usable drag regions without requiring installation-file patches. Settle whether controls occupy the sidebar header or an integrated editor-tab row before implementation, coordinating with the UI-density exploration.

- **Behavior:**

  > Users should be able to reclaim the dedicated title-bar row in a normal macOS window while retaining native window controls integrated into existing workbench chrome. The mode must provide usable window dragging and avoid collisions with tabs or sidebar content. Acceptance includes ordinary and split-editor windows, hidden-sidebar configurations, and fullscreen transitions. Existing default layouts remain unchanged.
- **Trace:**

  > desktop.contribution.ts registers native/custom title-bar styles and a visibility setting whose non-fullscreen hiding option requires the native title bar. shouldShowCustomTitleBar in src/vs/workbench/services/layout/browser/layoutService.ts otherwise retains a title-bar row on macOS outside fullscreen. src/vs/platform/windows/electron-main/windows.ts constructs the Electron window with titleBarStyle='hidden' for custom chrome, while TitlebarPart in src/vs/workbench/browser/parts/titlebar/titlebarPart.ts handles the control-side layout. The missing capability is an integrated layout, not merely hiding title text or exposing another Electron style. The maintainer position at https://github.com/microsoft/vscode/issues/30557#issuecomment-328325004 favors proper built-in support rather than CSS hacks. Coordinate design with https://github.com/microsoft/vscode/issues/168671 and https://github.com/microsoft/vscode/issues/107123 without treating either newer issue as a duplicate canonical. Preserve default behavior, native control semantics, and unrelated platform layouts; uncertainty starts at the chosen integration surface and its behavior when that surface is hidden.
- **Open decisions:**
  - Should the opt-in layout place native controls above the sidebar/activity bar as originally illustrated, or integrate them into the editor-tab row?
  - When the sidebar or activity bar is hidden, where should the integrated controls and window-drag region remain available?
