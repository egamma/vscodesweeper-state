# Issue #110766 — Allow an output to go into full-screen mode

[https://github.com/microsoft/vscode/issues/110766](https://github.com/microsoft/vscode/issues/110766)

## Summary

Keep this accepted notebook-output request open: current webview frames still do not delegate fullscreen permission, and output preview does not provide renderer-initiated fullscreen. The discussion establishes maintainer interest and concrete widget use cases; no verified older canonical or landed implementation was found.

## Change summary

Allow notebook outputs, including interactive widgets and video, to enter fullscreen from their renderer controls.

## Best solution

Support user-initiated notebook-output fullscreen consistently on desktop and web, with reliable exit and restoration of the notebook experience. Establish the supported renderer scope and validate Electron behavior before treating iframe permission changes as a complete solution.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/webview/browser/webviewElement.ts`, `src/vs/workbench/contrib/webview/browser/pre/index.html`, `src/vs/workbench/contrib/webview/electron-browser/webviewElement.ts`, `src/vs/workbench/contrib/notebook/browser/view/renderers/backLayerWebView.ts`
- **Validation:** On desktop and web, open a trusted notebook containing an HTML output with a user-clicked requestFullscreen() button and a supported video output. Verify supported content fills the fullscreen surface without unrelated workbench overlays, exits through Escape or its fullscreen control, and restores notebook focus and layout. Repeat from a non-fullscreen and already-fullscreen window, and verify ordinary output rendering is unchanged.
- **Behavior:**

  > Notebook renderer controls should be able to present supported output content in fullscreen rather than remaining constrained to the cell. Interactive widgets and video are concrete use cases in the discussion. Fullscreen should behave consistently on desktop and web, and exiting it should restore the notebook layout and usable focus. Acceptance must exercise actual user-initiated entry and exit; opening a separate output-preview editor alone does not satisfy the request.
- **Trace:**

  > BackLayerWebView._createInset in src/vs/workbench/contrib/notebook/browser/view/renderers/backLayerWebView.ts constructs notebook content using the shared webview service. WebviewElement._createElement in src/vs/workbench/contrib/webview/browser/webviewElement.ts and the inner-frame construction in src/vs/workbench/contrib/webview/browser/pre/index.html both omit fullscreen permission delegation. ElectronWebviewElement inherits the outer-frame construction. The existing notebook.cellOutput.openInOutputPreview command ultimately uses BackLayerWebView too, so it is not equivalent to the requested browser API behavior. The original reproduction at https://github.com/microsoft/vscode/issues/110766#issuecomment-752291391 shows that enabling iframe permission alone historically did not settle desktop behavior; current Electron behavior remains untested. Preserve existing script, sandbox, trust, and ordinary rendering restrictions, and do not assume a shared-webview change should enable fullscreen for every other webview consumer. The maintainer response at https://github.com/microsoft/vscode/issues/110766#issuecomment-1863357481 supports at least selected notebook MIME types but does not settle the complete supported-content contract.
- **Open decisions:**
  - Should fullscreen be available to arbitrary interactive notebook renderer content, or initially restricted to selected MIME types such as video?
  - Should this capability be notebook-specific, or also become available to other extension webviews through the shared hosting contract?
