# Issue #110766 — Allow an output to go into full-screen mode

[https://github.com/microsoft/vscode/issues/110766](https://github.com/microsoft/vscode/issues/110766)

## Summary

Keep open: notebook renderers still lack fullscreen permission in the current webview iframe chain. Output Preview provides more space but does not enable renderer-requested fullscreen; the thread establishes concrete notebook-widget demand.

## Change summary

Allow notebook output content, including interactive widgets and videos, to enter fullscreen from its own controls.

## Best solution

Provide a supported fullscreen experience for notebook outputs on desktop and web, preserving renderer interaction and returning cleanly to the notebook. First settle whether support covers arbitrary interactive outputs or only selected MIME types; enlarging an output editor alone does not satisfy the request.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/webview/browser/webviewElement.ts`, `src/vs/workbench/contrib/webview/browser/pre/index.html`, `src/vs/workbench/contrib/notebook/browser/view/renderers/backLayerWebView.ts`
- **Validation:** On desktop and web, open a trusted notebook containing an HTML output with a user-clicked element.requestFullscreen() control, then exercise a video or interactive widget under the agreed support scope. Verify the requested output fills the fullscreen presentation without workbench overlap, remains interactive, and exits back to the original notebook with focus and layout restored. Confirm unrelated webviews retain their intended permissions.
- **Behavior:**

  > Notebook output renderers currently cannot use their own fullscreen controls, even when the same content supports fullscreen in browser Jupyter. Supported output content should enter fullscreen following an explicit user action, remain interactive, and return to the notebook without losing output state. Acceptance must cover desktop and web, fullscreen exit, and preservation of ordinary notebook layout and interaction. The supported output categories remain a product decision.
- **Trace:**

  > BackLayerWebView._createInset in src/vs/workbench/contrib/notebook/browser/view/renderers/backLayerWebView.ts hosts notebook renderers through the shared webview service. WebviewElement._createElement in src/vs/workbench/contrib/webview/browser/webviewElement.ts and the nested iframe construction in src/vs/workbench/contrib/webview/browser/pre/index.html both omit fullscreen permission. These source findings establish the current permission gap, but do not prove that permission delegation alone produces correct Electron fullscreen layout. Existing notebook.cellOutput.openInOutputPreview opens a separate editor and does not enable the renderer's Fullscreen API. The original desktop experiments and platform differences are documented at https://github.com/microsoft/vscode/issues/110766#issuecomment-752291391; current desktop behavior still requires an executable investigation. Preserve unrelated webview permissions and ordinary notebook behavior rather than assuming a global webview policy change is authorized.
- **Open decisions:**
  - Should fullscreen be available to arbitrary interactive notebook renderers, including the Q# widget use case, or initially only to selected output MIME types such as video?
