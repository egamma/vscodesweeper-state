# Issue #158471 — Command to substitute variables from launch config should also get workspaceFolder as an argument

[https://github.com/microsoft/vscode/issues/158471](https://github.com/microsoft/vscode/issues/158471)

## Summary

A real API gap remains on current main: command-variable handlers receive the configuration object but not the originating workspace folder, preventing extensions from distinguishing otherwise identical multi-root debug configurations. The issue is already correctly routed to the API and debug backlog and should remain open.

## Change summary

Pass the originating workspace folder, or undefined for folderless configurations, as an additional argument to commands invoked by launch-configuration variable substitution.

## Best solution

Define and document the command-variable callback contract, preserving the configuration as the first argument and supplying the originating `WorkspaceFolder` or `undefined` as the second. Before implementation, decide whether this contract is launch-specific or applies to every consumer of the shared configuration resolver, including tasks.

## Plan brief

- **Likely files:** `src/vs/workbench/services/configurationResolver/browser/baseConfigurationResolverService.ts`, `src/vs/workbench/services/configurationResolver/common/configurationResolver.ts`, `src/vs/workbench/services/configurationResolver/test/electron-browser/configurationResolverService.test.ts`, `src/vs/workbench/contrib/debug/common/debugger.ts`
- **Validation:** Extend the Configuration Resolver Service unit tests to capture command arguments and assert that a workspace-scoped command variable receives `[configuration, workspaceFolder]`, while a folderless configuration receives `[configuration, undefined]`; run `scripts/test.sh --grep "Configuration Resolver Service"`.
- **Behavior:**

  > When a command variable is evaluated for a launch configuration associated with a workspace folder, its command receives the resolved configuration as the first argument and that workspace folder as the second argument. A configuration without an associated folder supplies `undefined` as the second argument. Existing command substitution results, cancellation behavior, and the first argument remain unchanged. Acceptance includes both workspace-scoped and folderless unit cases.
- **Trace:**

  > `Debugger.substituteVariables` in `src/vs/workbench/contrib/debug/common/debugger.ts` carries the selected `IWorkspaceFolder` into `IConfigurationResolverService.resolveWithInteractionReplace`. `BaseConfigurationResolverService.resolveWithInteraction` in `src/vs/workbench/services/configurationResolver/browser/baseConfigurationResolverService.ts` retains that folder for ordinary variable evaluation but invokes command variables with only `expr.toObject()`. The resolver is shared with tasks, as shown by the `section: 'tasks'` cases in `src/vs/workbench/services/configurationResolver/test/electron-browser/configurationResolverService.test.ts`, so changing the generic invocation may establish the same second-argument contract outside debugging. Preserve the existing first argument, return-type validation, input-variable behavior, and contributed-variable behavior. The related Azure Functions report is https://github.com/microsoft/vscode-azurefunctions/issues/3077; the broader variable-resolution API request at https://github.com/microsoft/vscode/issues/46471 does not replace this narrower contract decision.
- **Open decisions:**
  - Should the workspace-folder second argument be part of the command-variable contract for every consumer of the shared resolver, including tasks, or only for command variables originating from launch configurations?
