# Issue #18064 — Allow extension commands to define the behaviour when Alt modifier is pressed

[https://github.com/microsoft/vscode/issues/18064](https://github.com/microsoft/vscode/issues/18064)

## Summary

Keep this accepted API request open: extension QuickPicks still cannot observe acceptance modifiers, and item buttons do not deliver the requested modifier gesture. The same-symptom sibling is newer, so it cannot replace this re-reviewed issue.

## Change summary

Let extensions distinguish normal QuickPick acceptance from modifier-assisted acceptance to offer actions such as opening a project in a new window.

## Best solution

Provide a backward-compatible QuickPick acceptance contract that exposes the relevant modifier state, while retaining item buttons as discoverable alternative actions. Settle the public API and input-source scope with the API owner; keep tree-item and general command activation changes separate.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadQuickOpen.ts`, `src/vs/workbench/api/common/extHostQuickOpen.ts`, `src/vs/platform/quickinput/browser/quickInputController.ts`, `src/vs/platform/quickinput/browser/quickInputActions.ts`
- **Validation:** Use a development extension with createQuickPick to record acceptance information for plain Enter, Ctrl/Cmd+Enter, Alt+Enter, Shift+Enter, plain click and modifier-click. Verify that each supported gesture exposes the agreed metadata, unmodified acceptance remains unchanged, and existing item-button actions still work; add automated bridge coverage for that contract.
- **Behavior:**

  > An extension displaying a project list can distinguish ordinary acceptance from the supported modifier-assisted acceptance gestures and choose current-window versus new-window behavior. The reporter also requested knowing whether acceptance came from mouse or keyboard. Item buttons remain a discoverable alternative, not a replacement for modifier gestures. Acceptance checks should cover supported keyboard and mouse combinations and preserve existing extensions' ordinary acceptance behavior.
- **Trace:**

  > QuickInputController.registerKeyModsListeners in src/vs/platform/quickinput/browser/quickInputController.ts already tracks ctrlCmd, alt and shift, and internal PickerQuickAccessProvider acceptance handlers receive picker.keyMods. The extension boundary drops that context: MainThreadQuickOpen.$createOrUpdate forwards only a session ID, the ExtHostQuickOpenShape protocol carries no acceptance metadata, and ExtHostQuickOpen fires a void event matching vscode.d.ts. The showQuickPick convenience path also returns only selected handles. Existing QuickPick item buttons cover explicit actions, not the requested gesture. The uncertainty is the public contract and whether input-source information and the convenience API belong in its initial scope; do not expand this into tree-item or arbitrary command modifier dispatch. https://github.com/microsoft/vscode/issues/121204 describes the same QuickPick work, while https://github.com/microsoft/vscode/issues/336540 is a separate tree-item request.
- **Open decisions:**
  - What backward-compatible public contract should expose acceptance modifiers, and should Ctrl and Cmd remain combined as in core's ctrlCmd state or be distinguishable?
  - Should the initial API include mouse-versus-keyboard acceptance provenance and the showQuickPick convenience API, or be limited to modifier information on createQuickPick acceptance?
