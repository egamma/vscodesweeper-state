# Issue #268346 — Kernel disposed because Notebook was closed or Cell was Deleted, when in fact notebook wasn't closed and cell wasn't deleted

[https://github.com/microsoft/vscode/issues/268346](https://github.com/microsoft/vscode/issues/268346)

## Summary

Keep open: multiple reporters confirmed unexpected notebook closure or cell cancellation, including without Continue installed, and a maintainer explicitly requested a core fix. Current main contains a narrower reload safeguard, but neither that change nor Continue's workaround establishes that the reopened report is fully resolved.

## Change summary

Remote notebooks unexpectedly lose their document or running-cell state after saving or a few minutes of inactivity, preventing further execution.

## Best solution

Preserve open notebook and cell identities across saves, non-destructive reloads, and extension-triggered document access. Reproduce the remaining failure on current builds and distinguish whole-document disposal from save-triggered cell replacement before choosing a bounded core fix.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/notebook/common/notebookEditorModel.ts`, `src/vs/workbench/contrib/notebook/common/model/notebookTextModel.ts`, `src/vs/workbench/contrib/notebook/common/model/notebookCellTextModel.ts`, `src/vs/workbench/contrib/notebook/common/notebookEditorModelResolverServiceImpl.ts`, `src/vs/workbench/api/common/extHostNotebook.ts`, `src/vs/workbench/contrib/notebook/test/browser/notebookTextModel.test.ts`
- **Validation:** On a current build connected to WSL or Remote-SSH, run a notebook cell containing a print/time.sleep loop for more than three minutes; exercise manual saving and files.autoSave=afterDelay separately. Verify execution continues, the notebook remains usable, and no false cell-deletion or notebook-close event occurs. Once a current trigger is isolated, add a regression to the notebook model or document-lifecycle suite that fails for that trigger before the fix.
- **Behavior:**

  > An open remote notebook must remain usable when saved or left idle; an executing cell must not be treated as deleted unless it was actually removed. Existing reports provide a minimal print/time.sleep loop, save-triggered cancellation, and a separate whole-document disposal symptom after a few minutes. Acceptance requires execution to survive manual and automatic saving and the notebook to accept subsequent executions after the idle interval. Actual user-requested notebook closure, cell deletion, and substantive external file changes must retain their intended behavior.
- **Trace:**

  > NotebookFileWorkingCopyModel.update in src/vs/workbench/contrib/notebook/common/notebookEditorModel.ts deserializes file contents and calls NotebookTextModel.reset. Current reset/computeEdits and NotebookCellTextModel.fastEqual already preserve executing cells across internal-metadata-only changes, introduced by https://github.com/microsoft/vscode/pull/232678 for https://github.com/microsoft/vscode/issues/230017. However, the window/Jupyter logs at https://github.com/microsoft/vscode/issues/268346#issuecomment-3334773217 show the working copy itself being disposed before the extension host loses the notebook document. Notebook model reference ownership is managed in notebookEditorModelResolverServiceImpl.ts, while extHostNotebook.ts translates removed-document deltas into notebook-close events. The remaining uncertainty is which current operation incorrectly releases or replaces the live model; historical reports do not establish that causal chain on main. Keep normal reference cleanup and external-change handling intact, and do not treat disabling autosave or excluding notebooks in another extension as the core solution.

## Evidence

- **Confirmed minimal reproduction:** https://github.com/microsoft/vscode/issues/268346#issuecomment-3334772852 supplies a print/time.sleep loop and logs showing an executing cell becoming index -1 and being cancelled; the reporter confirms both automatic and manual saves trigger it. Independent confirmation appears at https://github.com/microsoft/vscode/issues/268346#issuecomment-3334773437. These establish historical reproduction, not a current-main execution result.
- **Whole-document disposal evidence:** https://github.com/microsoft/vscode/issues/268346#issuecomment-3334773217 includes window logs disposing the notebook working copy at 16:54:08, followed by Jupyter reporting isClosed=true and then NO notebook document on another execution. This is broader than an executing cell's metadata changing during reload.
- **Reopened beyond extension-specific diagnosis:** The timeline records closure on 2024-05-30 and reopening on 2024-07-10. https://github.com/microsoft/vscode/issues/268346#issuecomment-3334771931 reports reproduction without Continue; https://github.com/microsoft/vscode/issues/268346#issuecomment-3334772137 reports reproduction with other extensions disabled and no other application opening the notebook.
- **Related core fix is narrower:** https://github.com/microsoft/vscode/pull/232678 merged commit https://github.com/microsoft/vscode/commit/0865c01675143b95d234763a326268957fe5a86c for https://github.com/microsoft/vscode/issues/230017. Its diff makes NotebookTextModel.reset pass executing-cell handles into computeEdits and makes NotebookCellTextModel.fastEqual ignore internal metadata differences for executing cells. These safeguards remain in current source, but the diff does not establish protection against unexpected whole-document disposal.
- **Current source boundary:** src/vs/workbench/services/workingCopy/common/storedFileWorkingCopyManager.ts queues reloads for clean working copies after file updates. src/vs/workbench/contrib/notebook/common/notebookEditorModel.ts routes file updates through NotebookFileWorkingCopyModel.update into NotebookTextModel.reset. The current metadata safeguard prevents one replacement case; the source inspection did not conclusively identify the remaining trigger.
- **Maintainer direction and workaround limitations:** https://github.com/microsoft/vscode/issues/268346#issuecomment-3334773473 explicitly requests preventing the problem in core. The referenced https://github.com/continuedev/continue/commit/d393ee915b523885cb338722bdf81a1e6eee8812 skips .ipynb import-definition processing and parsing; it avoids an extension workflow rather than fixing VS Code's document lifecycle.

Searches for notebook disposal, reload/kernel, and save/execution symptoms found no verified older open canonical owning this report's full scope.
