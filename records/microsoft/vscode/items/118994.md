# Issue #118994 — Please provide a function in API to get horizontal pixel coordinate of any character in any line.

[https://github.com/microsoft/vscode/issues/118994](https://github.com/microsoft/vscode/issues/118994)

## Summary

Keep this accepted, well-supported API request open: current extension APIs still do not expose rendered character coordinates, and the monospace workaround does not cover mixed-width fonts or inlay hints. The remaining work needs an API-owner decision about the public geometry contract.

## Change summary

Expose accurate horizontal coordinates for document positions to extensions, including positions affected by variable-width glyphs and inline content.

## Best solution

Define an extension-facing capability that lets visual extensions obtain accurate rendered horizontal positions without approximating character widths. API owners should settle coordinate semantics and off-screen behavior before implementation, preserving editor responsiveness.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTextEditor.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadEditors.ts`, `src/vs/editor/browser/editorBrowser.ts`, `src/vs/editor/browser/view.ts`
- **Validation:** After the API contract is agreed, exercise an extension against mixed-width Latin/Georgian text and enabled inlay hints, checking reported horizontal positions against rendered character boundaries. Repeat after horizontal scrolling, editor zoom and word wrapping; verify the agreed off-screen result without unexpectedly scrolling the editor.
- **Behavior:**

  > Visual extensions such as Blockman cannot accurately align decorations by multiplying character counts by a nominal width when glyph widths vary or inlay hints insert rendered content. The desired capability provides accurate horizontal positions for document characters through the extension API. Acceptance must cover mixed-width glyphs and inlay hints, with explicit behavior for scrolling, zoom, wrapping and unavailable positions. The request concerns a missing capability, not a demonstrated defect in existing core behavior.
- **Trace:**

  > TextEditor in src/vscode-dts/vscode.d.ts and MainThreadTextEditorsShape in src/vs/workbench/api/common/extHost.protocol.ts expose no rendered-coordinate query. Internal ICodeEditor.getOffsetForColumn is available only for rendered lines; View.getOffsetForColumn in src/vs/editor/browser/view.ts maps model to view coordinates, flushes rendering and returns a measured left offset or -1. CodeEditorWidget.getScrolledVisiblePosition applies gutter and scrolling offsets, illustrating that coordinate origins differ between existing internal methods. These methods establish a possible measurement boundary, not an already-shipped extension capability. The ch-unit workaround discussed in https://github.com/microsoft/vscode/issues/125341 does not meet the mixed-width/inlay-hint requirement. Related https://github.com/microsoft/vscode/issues/162863 records API-philosophy concerns about exposing pixels but requests the reverse mapping and cannot absorb this older report. Preserve existing decoration behavior and editor performance; uncertainty begins at the public contract, particularly arbitrary off-screen positions and wrapped-line coordinates.
- **Open decisions:**
  - Must the API return coordinates for arbitrary off-screen document positions, as requested, or may it report unavailable geometry outside the rendered viewport?
  - What coordinate origin and unit should extensions receive, and how should the result behave under horizontal scrolling, editor zoom and wrapped lines?
  - At a document position containing injected text or inlay hints, which visual boundary should the returned coordinate represent?
