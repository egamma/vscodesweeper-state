# Issue #101718 — "Add Selection To Previous Find Match" interferes with "Add Selection To Next Find Match"

[https://github.com/microsoft/vscode/issues/101718](https://github.com/microsoft/vscode/issues/101718)

## Summary

Keep this accepted editor-command request open: current source still searches from the last-added selection, so reversing direction encounters an already-selected occurrence instead of expanding the selection. The matching later report was explicitly closed as a duplicate of this issue, and no verified older canonical owns the same request.

## Change summary

Allow Add Selection to Next/Previous Find Match to expand a selection set in both directions without stalling on already-selected matches.

## Best solution

Make the existing add-occurrence commands compose predictably so users can select neighboring occurrences above and below their starting point. Establish the behavior for noncontiguous selection sets before changing the shared multicursor search path, while preserving move-selection and ordinary Find behavior.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/multicursor/browser/multicursor.ts`, `src/vs/editor/contrib/multicursor/test/browser/multicursor.test.ts`
- **Validation:** Add cases to the existing Multicursor selection suite using five lines containing 'foo': explicitly select line 3, invoke Next then Previous, and assert selections cover lines 2, 3, and 4; repeat with Previous then Next. Run scripts/test.sh --run src/vs/editor/contrib/multicursor/test/browser/multicursor.test.ts. Also cover repeated alternation, exhaustion of available matches, and unchanged move-selection behavior.
- **Behavior:**

  > Users can start at a middle occurrence and grow a multicursor selection toward both earlier and later occurrences using the existing add-occurrence commands. With five identical occurrences and the third initially selected, Next then Previous selects the second, third, and fourth; reversing command order selects the same set. Existing selections remain selected, and directional expansion does not stall merely because the nearest match is already selected. Acceptance includes repeated alternation and termination when no additional distinct matches remain.
- **Trace:**

  > MultiCursorSession._getNextMatch and _getPreviousMatch in src/vs/editor/contrib/multicursor/browser/multicursor.ts anchor both searches to the last-added selection and return a single model match without considering the existing selection set. The add methods append that result; CursorCollection.normalize in src/vs/editor/common/cursor/cursorCollection.ts merges overlapping selections, explaining the reported apparent no-op. The same search helpers also serve MoveSelectionToNextFindMatchAction and MoveSelectionToPreviousFindMatchAction, whose replacement semantics must remain unchanged. Matching options, ordinary Find traversal, cursor normalization, and select-all behavior are outside the requested change. The existing Multicursor selection suite in src/vs/editor/contrib/multicursor/test/browser/multicursor.test.ts provides the command-level harness. https://github.com/microsoft/vscode/issues/135373 confirms the alternating-direction scenario and was explicitly consolidated into this issue; https://github.com/microsoft/vscode/issues/43046 requests a distinct all-cursors operation. The remaining uncertainty is how directional expansion should behave for noncontiguous selections.
- **Open decisions:**
  - For noncontiguous selections, should each add-occurrence command choose the nearest unselected match in its direction from the last-added selection, including gaps, or extend from the corresponding outermost selected occurrence?

## Evidence

- **Current command path:** src/vs/editor/contrib/multicursor/browser/multicursor.ts:382–454: MultiCursorSession._getNextMatch and _getPreviousMatch both search from allSelections[allSelections.length - 1]. Neither excludes existing selections. Starting with the third of five identical occurrences, Next appends the fourth; Previous then returns the already-selected third rather than the second.
- **Why selection expansion stalls:** src/vs/editor/common/cursor/cursorCollection.ts:normalize merges overlapping selections when multiCursorMergeOverlapping is enabled.
