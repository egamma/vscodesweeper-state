# Issue #296136 — Diff editor select and git stage issues with code deletions

[https://github.com/microsoft/vscode/issues/296136](https://github.com/microsoft/vscode/issues/296136)

## Summary

Keep open for native selection across inline deleted content: current source supports browser-based copying, not unified editor selection or granular deletion staging. The linked staging issue covers only part of this report, so it is not a canonical for the full request.

## Change summary

Support consistent editor selection across inline deleted and surviving text, including staging individual deleted lines.

## Best solution

Define consistent selection semantics for original text displayed inside the inline diff, with accurate copy and staging behavior. Coordinate deletion staging with https://github.com/microsoft/vscode/issues/9475 while preserving the separate cross-boundary selection requirement here.

## Plan brief

- **Likely files:** `src/vs/editor/browser/widget/diffEditor/components/diffEditorViewZones/diffEditorViewZones.ts`, `src/vs/editor/browser/widget/diffEditor/components/diffEditorViewZones/copySelection.ts`, `src/vs/editor/browser/widget/diffEditor/components/diffEditorViewZones/inlineDiffDeletedCodeMargin.ts`, `extensions/git/src/commands.ts`
- **Validation:** Use an inline Git diff containing a multiline deletion between unchanged lines and a nearby addition. Check selection within deleted lines and across deleted/surviving boundaries, copied text and newline fidelity, and staging only a chosen subset of deletions without staging adjacent additions. Repeat with deletion-only changes and verify existing side-by-side behavior remains unchanged; the plan should identify automated coverage for the chosen selection contract.
- **Behavior:**

  > Inline deleted content can currently be selected for copying, but that selection behaves differently from normal editor selection and cannot drive granular Git staging. The goal is predictable selection within and across deleted blocks, with copying that reflects the selected displayed content and staging that acts on precisely the intended changed lines. Acceptance must include multiline deletions, deletion-only changes, and nearby additions that should remain unstaged. Existing added-text selection and side-by-side behavior must remain intact.
- **Trace:**

  > DiffEditorViewZones in src/vs/editor/browser/widget/diffEditor/components/diffEditorViewZones/diffEditorViewZones.ts renders multiline deleted content as view-zone DOM rather than modified-model lines. The selectable CSS and enableCopySelection in copySelection.ts use browser selection and translate it to the original text model only for copying. CommandCenter.stageSelectedChanges in extensions/git/src/commands.ts instead consumes activeTextEditor.selections in modified-document coordinates. The record therefore establishes two disconnected selection paths, but not a regression from previously unified native selection. https://github.com/microsoft/vscode/issues/9475 owns the granular deletion-staging requirement, while the closed https://github.com/microsoft/vscode/issues/8226 addressed basic deleted-text selection/copying. The uncertainty begins at the public selection contract across original and modified content; preserve ordinary editing, existing copy fidelity, and side-by-side semantics.
- **Open decisions:**
  - Should a selection spanning original deleted text and modified surviving text become an editor selection exposed to extension commands, or remain a distinct diff-specific selection with explicitly supported actions?
  - When a displayed selection includes both deleted and added lines, should staging apply exactly those selected original/modified lines independently, rather than treating the replacement hunk as a unit?

## Evidence

- **report and clarification:** https://github.com/microsoft/vscode/issues/296136 describes browser-like selection of deleted content, inability to select continuously across deletions, and missing granular staging. The reporter's follow-up isolates the selection behavior to inline view; side-by-side selection behaves normally.
- **current selection implementation:** src/vs/editor/browser/widget/diffEditor/components/diffEditorViewZones/diffEditorViewZones.ts:205-285 renders multiline deleted content as a DOM view zone. style.css:557-566 explicitly enables browser text selection, and copySelection.ts reads ownerDocument.getSelection() and maps that DOM range to the original model for copying. This does not establish a native editor selection spanning original and modified text.
- **staging boundary:** extensions/git/src/commands.ts:1777-1815 implements git.stageSelectedRanges using activeTextEditor.selections and ranges in the modified document. The browser selection used for inline deleted content is not consumed by this command. InlineDiffDeletedCodeMargin provides copy and revert actions, not selected-deletion staging.
- **existing capability check:** diffEditor.renderSideBySide provides normal selection in the original editor, as the reporter confirms, but does not deliver continuous inline selection. diffEditor.experimental.useTrueInlineView is documented as rendering word changes inline; allowsTrueInlineDiffRendering in diffEditorViewZones.ts:647-654 restricts eligible changes, so it does not resolve arbitrary multiline deleted blocks.
