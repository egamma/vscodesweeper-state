# Issue #335086 — Copilot Chat BYOK OpenAI-Responses custom endpoint fails on 2nd turn with "previous response not found" since ~1.134: request no longer sends store:true

[https://github.com/microsoft/vscode/issues/335086](https://github.com/microsoft/vscode/issues/335086)

## Summary

Confirmed on current main by reading source: CustomEndpointOAIEndpoint.createRequestBody (extensions/copilot/src/extension/byok/vscode-node/customEndpointProvider.ts, lines 259-265) deletes `store` from the request body when `zeroDataRetentionEnabled` is unset, but does not set `ignoreStatefulMarker`, so the base class still attaches `previous_response_id` from the stored marker. A companion unit test explicitly documents this combination (`storePresent: false` + `previousResponseId: customResponsesMarker`), confirming it's the current, intended-but-flawed behavior, not something already fixed.

## Change summary

Custom-endpoint (BYOK) Responses-API conversations fail on the 2nd turn with 'previous response not found' because the client omits `store` while still chaining `previous_response_id`, for gateways whose default isn't to persist responses without an explicit `store:true`.

## Best solution

A maintainer needs to pick a fix direction: either keep sending `store: true` by default for custom endpoints as before (reverting the intentional 'let the custom impl decide' behavior added for this class), or make the recovery path robust — the automatic InvalidStatefulMarker retry in platform/endpoint/node/chatEndpoint.ts only triggers today for OpenAI's literal `previous_response_not_found` code; the reporter's gateway returns the spec's generic `not_found` code, which doesn't get classified the same way and so never self-heals via retry.

- **test documents the exact reported combination:** extensions/copilot/src/extension/byok/vscode-node/test/customEndpointProvider.spec.ts:236-249, test 'omits store after cloning a Custom Endpoint Responses endpoint when zeroDataRetentionEnabled is omitted' asserts `storePresent: false` together with `previousResponseId: customResponsesMarker` — i.e. the client omits store yet still chains previous_response_id, exactly the failure mode described.
- **self-heal retry is narrow:** extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts:1669 only classifies `jsonData?.code === 'previous_response_not_found'` (OpenAI's own wording) as `ChatFailKind.InvalidPreviousResponseId` (which drives the automatic retry in platform/endpoint/node/chatEndpoint.ts:556-562); a generic OpenAI-compatible `code: 'not_found'` response (as in the reporter's capture) is not covered by that specific branch, so no automatic retry/self-heal occurs for their gateway.
- **user-confirmed workaround:** Reporter's comment confirms explicitly setting `zeroDataRetentionEnabled: false` in the model config restores `store: true` via the base-class fallback and fixes the failure — consistent with the traced code.
