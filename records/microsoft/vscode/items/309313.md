# Issue #309313 — Automatically update in Administrator in Windows

[https://github.com/microsoft/vscode/issues/309313](https://github.com/microsoft/vscode/issues/309313)

## Summary

Keep open: current source still disables updates for every elevated user-scope installation, including the built-in Administrator scenario. The older UAC-disabled report is related, but does not establish coverage of account-specific elevation when machine-wide UAC remains enabled.

## Change summary

Allow automatic updates for a user-scope installation running under Windows' built-in Administrator account without requiring a system-wide installation.

## Best solution

Define and support the always-elevated account cases in the Windows updater while retaining protections against making a regular user's installation unusable. Coordinate with the UAC-disabled work, explicitly preserving this report's built-in Administrator case.

## Plan brief

- **Likely files:** `src/vs/platform/update/electron-main/updateService.win32.ts`, `src/vs/platform/native/electron-main/nativeHostMainService.ts`, `src/vs/platform/native/common/native.ts`, `src/vs/platform/update/common/update.config.contribution.ts`
- **Validation:** On a disposable Windows VM, exercise a built user-scope installation under the built-in Administrator account with Admin Approval Mode disabled, including with machine-wide UAC enabled. Verify the agreed eligibility behavior and complete an available update. Contrast with an elevated regular administrator account with UAC enabled, verify its protection remains intact, and confirm ordinary non-elevated user-scope updates still work.
- **Behavior:**

  > A user running a user-scope installation under Windows' built-in Administrator account wants automatic updates without switching to a system-wide installation or manually downloading each release. Currently the updater disables this scenario solely because the process is elevated. Acceptance must explicitly cover the account-specific case rather than testing only machine-wide UAC disablement. Regular users' installations must remain usable from their normal non-elevated sessions.
- **Trace:**

  > Win32UpdateService.initialize() in src/vs/platform/update/electron-main/updateService.win32.ts disables all elevated user-target installations before calling the base initializer. NativeHostMainService.isAdmin() in src/vs/platform/native/electron-main/nativeHostMainService.ts supplies only an elevation boolean, and the registered update settings do not override this gate. The maintainer explained the regular-account ACL concern and acknowledged the reporter's built-in-account distinction in https://github.com/microsoft/vscode/issues/309313#issuecomment-4248400466. https://github.com/microsoft/vscode/issues/298494 owns related machine-wide UAC-disabled work, but its stated reproduction does not establish the account-specific case. The unresolved boundary is which Windows account and approval-mode combinations the product should support; do not treat blanket removal of the elevation restriction as the agreed outcome.
- **Open decisions:**
  - Should automatic updates support the built-in Administrator account with Admin Approval Mode disabled even when machine-wide UAC remains enabled, in addition to the machine-wide UAC-disabled scenario?

## Evidence

- **Current source still blocks the requested scenario:** src/vs/platform/update/electron-main/updateService.win32.ts, Win32UpdateService.initialize(), sets State.Disabled(DisablementReason.RunningAsAdmin) and returns whenever productService.target === 'user' and nativeHostMainService.isAdmin() is true. There is no exception here for the built-in Administrator account or UAC state.
- **Elevation detection does not distinguish account cases:** src/vs/platform/native/electron-main/nativeHostMainService.ts, isAdmin(), delegates on Windows to native-is-elevated and returns a boolean. The updater's eligibility check does not distinguish an elevated regular account from an always-elevated built-in Administrator session.

Win32UpdateService.initialize() returns before AbstractUpdateService.initialize() reaches the configured update-mode handling.

After the reporter distinguished the built-in Administrator account, the maintainer acknowledged that distinction at https://github.com/microsoft/vscode/issues/309313#issuecomment-4248400466.

It reproduces the same disabled-update notification with machine-wide UAC explicitly turned off; this report specifically concerns the built-in Administrator account, whose elevation behavior need not imply that machine-wide UAC is disabled.
