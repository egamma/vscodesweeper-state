# Issue #95182 — Support "perspectives" like approach in VSCode 

[https://github.com/microsoft/vscode/issues/95182](https://github.com/microsoft/vscode/issues/95182)

## Summary

Keep this accepted, well-supported request open: profiles and layout commands provide partial building blocks, but not named, independently saved perspectives with save/reset semantics. The older related issues cover narrower or different workflows, and a later saved-layout request was explicitly consolidated here.

## Change summary

Provide named perspectives for switching component-focused or task-focused workbench layouts within one window.

## Best solution

Design lightweight named layout snapshots that restore view placement, visibility, sizes, and editor-group arrangement without changing unrelated settings or extensions. Decide explicitly whether folder/workspace scoping belongs to the same feature or remains separate, since the original request includes it.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/actions/layoutActions.ts`, `src/vs/workbench/browser/layout.ts`, `src/vs/workbench/services/views/browser/viewDescriptorService.ts`, `src/vs/workbench/browser/parts/editor/editorCommands.ts`, `src/vs/workbench/services/layout/browser/layoutService.ts`
- **Validation:** After agreeing scope, manually save distinct editing and debugging layouts, switch between them in one window, modify one temporarily, reset it, and reload the window. Verify the agreed view visibility, locations, sizes, and editor-group arrangement are restored while settings, keybindings, extensions, and unsaved edits remain unchanged; exercise any agreed folder-scoping behavior separately. Add targeted coverage using the layout, viewDescriptorService, and editorGroupsService test suites where applicable.
- **Behavior:**

  > Users want named perspectives that switch between component-focused or task-focused arrangements without juggling windows or manually rebuilding the layout. The discussion specifically requests saved layouts distinct from temporary adjustments, with a way to restore the saved arrangement while leaving unrelated editor preferences unchanged. Acceptance should cover switching between editing/debugging and different screen-size layouts, restoration after reload, and preservation of unsaved edits. The original request also includes folder/workspace scoping, whose relationship to layout snapshots must be settled before defining complete acceptance.
- **Trace:**

  > CustomizeLayoutAction in src/vs/workbench/browser/actions/layoutActions.ts exposes individual workbench controls and default restoration, not named snapshot management. LayoutStateModel in src/vs/workbench/browser/layout.ts persists current visibility, positioning, and sizes using mixed workspace/profile scopes; ViewDescriptorService in src/vs/workbench/services/views/browser/viewDescriptorService.ts stores view customizations in profile storage. registerEditorGroupsLayoutCommands in src/vs/workbench/browser/parts/editor/editorCommands.ts provides vscode.getEditorLayout and vscode.setEditorLayout for editor-group trees. Profiles can share default resources, but UserDataProfileManagementService.changeCurrentProfile changes the profile lifecycle, so profile availability alone does not prove layout-only coverage. Preserve existing profile behavior, ordinary layout persistence, and unsaved editor contents; automatic debug-triggered switching is described as nonessential in the discussion. https://github.com/microsoft/vscode/issues/216977 was consolidated here, while https://github.com/microsoft/vscode/issues/41860 tracks the narrower Explorer-scoping capability. Uncertainty starts at the public snapshot contract and its relationship to workspace scoping, not at the choice of implementation helpers.
- **Open decisions:**
  - Does a perspective change only the workbench layout, or also the active folder/workspace scope requested in the original report?
  - Are named perspectives workspace-specific, reusable across workspaces, or both?
  - Which state belongs in a saved perspective: view locations, visibility and sizes, editor-group geometry, and/or the actual open editors?
  - Should each perspective preserve temporary adjustments separately from an explicit saved baseline, including across window reloads, as requested in the discussion?
