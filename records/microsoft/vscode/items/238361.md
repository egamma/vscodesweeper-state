# Issue #238361 — `vscode.workspace.fs.copy` does not copy folders properly on github.dev

[https://github.com/microsoft/vscode/issues/238361](https://github.com/microsoft/vscode/issues/238361)

## Summary

The current source still explains the reported result: the HTTP filesystem provider identifies every resource as a file, so copying an extension directory writes its HTTP response body instead of traversing its children. Keep this accepted backlog bug open; no verified canonical issue or landed fix was found.

## Change summary

Copying an HTTP-hosted extension directory into a github.dev workspace creates a file containing the directory listing instead of copying the directory tree.

## Best solution

Support directory-aware copying for web-hosted extension assets through a defined directory metadata and enumeration contract. Preserve ordinary HTTP file reads and existing recursive copying for providers that already expose directories correctly.

- **Likely files:** `src/vs/workbench/services/extensions/browser/webWorkerFileSystemProvider.ts`, `src/vs/workbench/services/extensions/browser/extensionService.ts`, `src/vs/platform/files/common/fileService.ts`, `src/vs/platform/files/test/browser/inmemoryFileService.test.ts`

Include an ordinary JSON file resembling a directory listing to ensure it remains a file. Manually repeat the reported extension command in github.dev; no checks were executed during this read-only review.
- **Behavior:**

  > Calling vscode.workspace.fs.copy on a directory in a web-hosted extension should copy its directory tree into the workspace, rather than create a regular file containing directory-listing JSON. Acceptance should cover nested files and directories, preserve their contents, and leave ordinary HTTP-hosted files unchanged. Existing desktop and local-filesystem copy behavior must remain unchanged.
- **Trace:**

  > ExtHostConsumerFileSystem.copy delegates through MainThreadFileSystem.$copy to FileService.copy. The browser ExtensionService registers FetchFileSystemProvider for HTTP and HTTPS; that provider always returns FileType.File from stat, fetches raw response bytes in readFile, and does not support readdir. FileService.doMoveCopy branches on the resolved source's isDirectory flag, which explains why the reported listing becomes destination file contents. The defect is on the source-provider side; the evidence does not establish a GitHub destination-provider defect. The unresolved boundary is how extension asset hosting identifies and enumerates directories reliably without interpreting arbitrary JSON files as directories. Keep generic HTTP file behavior and already-correct recursive copying unchanged. Report: https://github.com/microsoft/vscode/issues/238361.
- **Open decisions:**
  - Which explicit directory metadata and listing contract should web-hosted extension assets support, and should directory-aware behavior apply only to extension asset hosts or to other HTTP resources that implement that contract?
