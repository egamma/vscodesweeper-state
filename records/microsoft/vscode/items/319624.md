- **Full follow-up:** https://github.com/microsoft/vscode/issues/319624#issuecomment-4638758206 reports GENERIC_LIBRARY_PATH and GENERIC_SCRIPT_EXEC_PATH persisting in the integrated terminal but not an external terminal after exports were commented out. Reinstalling and deleting caches did not help; the comment does not establish that all VS Code processes and their inherited login-session environment were restarted.
- **Shell resolution boundary:** src/vs/platform/shell/node/shellEnv.ts:getResolvedShellEnv skips resolution for CLI launches unless --force-user-env is supplied and caches the resolution promise in memory. doResolveUnixShellEnv inherits process.env and invokes the detected shell with interactive/login arguments (-i -l -c for Bash), rather than independently parsing the five files. src/vs/base/node/shell.ts:getSystemShellUnixLike selects SHELL or the account shell. Which files load therefore depends on the actual shell and startup-file chain.
- **Extension-host environment path:** src/vs/base/parts/sandbox/electron-browser/preload.ts:79-89 merges process.env, resolved shellEnv, and window userEnv in that order and retains the resulting promise. src/vs/workbench/services/extensions/electron-browser/localProcessExtensionHost.ts:_start obtains that environment through IShellEnvironmentService and additionally applies debugExtensionHost.env. These identify launch inheritance and debug overrides as relevant variables, but do not conclusively explain the reporter's missing Bash export.
- **Terminal inheritance:** src/vs/workbench/contrib/terminal/common/terminalEnvironment.ts:createTerminalEnvironment merges baseEnv unless strictEnv is requested. Commenting out an export does not itself remove a variable already inherited by a running process, so the follow-up alone does not prove an on-disk VS Code cache defect.
