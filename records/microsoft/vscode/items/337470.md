# Issue #337470 — Agents window stalls after Copilot runtime panic during MCP/plugin refresh

[https://github.com/microsoft/vscode/issues/337470](https://github.com/microsoft/vscode/issues/337470)

## Summary

Team-authored crash report from the day of filing; the underlying Rust panic is in the shared Copilot runtime process, not something visible in this TS checkout, and there's no fix commit to cite yet. Author association (MEMBER) blocks any judgment close regardless — this stays open for investigation.

## Change summary

A panic in the shared Copilot CLI runtime (thread 'copilot-cabi') during MCP/plugin refresh (clientPluginsChanged) corrupts the connection and stalls every open Agents window chat, not just the one that triggered the refresh, until Insiders is restarted.

## Best solution

Harden the agent host's client-restart path (copilotAgent.ts, around _requestClientRestart/_applyPendingClientRestart and getRestartReason) to detect a crashed/panicked shared runtime process and transparently respawn it (or at least surface a recoverable error) instead of leaving all chats stuck on 'Connection is closed'.

- **Trace:**

  > The reported panic ('thread copilot-cabi panicked ... Unfold must not be polled after it returned Poll::Ready(None)') originates in the compiled Copilot CLI runtime, triggered around a clientPluginsChanged refresh (see getRestartReason, copilotAgent.ts:7372-7380). The host already has a restart pipeline for config/tool/plugin changes (_requestClientRestart / _applyPendingClientRestart, copilotAgent.ts ~1224-1290), but that pipeline is driven by detected config diffs, not by detecting that the underlying process itself has died or is returning 'Connection is closed'. Where the uncertainty starts: how process-level crash detection would be wired to that existing restart path, and whether recovery should be per-chat or whole-runtime — this needs input from whoever owns the copilot-cabi/runtime process lifecycle.
- **Open decisions:**
  - Should a panicked shared runtime be detected and auto-respawned transparently, or should it surface a clear error asking the user to restart/retry?
  - Should recovery be scoped per-chat (isolate the failure) or require restarting the whole shared runtime for all chats?
