# Issue #323463 — Session info shows incorrect context size

[https://github.com/microsoft/vscode/issues/323463](https://github.com/microsoft/vscode/issues/323463)

## Summary

Keep open for a UX decision: 400K is the intentionally computed total window, but labeling the 272K input selection and the 400K input-plus-output total as the same “context size” is confusing. This is team-authored, and the maintainer discussion explicitly seeks a clearer presentation rather than rejecting the concern.

## Change summary

Clarify why selecting a 272K input context tier produces a 400K total context-window denominator in session information.

## Best solution

Make the picker and usage details distinguish the selected input-token tier from the total context window, including the response reserve, while preserving the request’s 272K input limit and the widget’s accurate 400K total.

- **Behavior:**

  > Choosing the 272K context option must continue to limit prompt/input tokens to 272K while allowing the model’s reserved output capacity, for a 400K total window. The picker and session usage details must make those two quantities distinguishable rather than presenting both as an unexplained “context size.” The usage percentage and output-reserve visualization must remain based on the 400K total. Accessibility labels must communicate the same distinction.
- **Trace:**

  > The picker renders the configured `contextSize` value under “Context Size” in src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerConfiguration.ts. The usage path resolves that value as the input limit, then getModelContextWindowTotal in src/vs/workbench/contrib/chat/common/languageModels.ts adds max output tokens; ChatContextUsageDetails renders the resulting total under “Context Window” with a response-reserve legend. This matches the explicit contract in https://github.com/microsoft/vscode/issues/323186, so the arithmetic and request limits must not change. The uncertainty starts at the user-facing terminology and whether the picker, usage details, or both should expose the input-versus-total relationship. https://github.com/microsoft/vscode/issues/293125 is related context-widget work but reports different observable symptoms and is not a duplicate canonical.
- **Open decisions:**
  - Should the configuration surface be named as an input/prompt limit, should it also display the resulting total window, or should the usage details alone explain that the selected tier excludes the reserved response budget?
