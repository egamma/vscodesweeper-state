# Issue #325576 — Work tree created for the prompt "List my sessions"

[https://github.com/microsoft/vscode/issues/325576](https://github.com/microsoft/vscode/issues/325576)

## Summary

Current main intentionally defaults Git-backed sessions to worktree isolation and materializes that worktree before the first prompt reaches the provider, so a read-only “List my sessions” request still creates one. This reopened, team-authored issue disputes that product design; the team-author protection rules out an as-designed close and the desired lazy-isolation semantics need a maintainer decision.

## Change summary

Avoid creating an isolated worktree for session prompts that only perform read-only operations such as listing sessions.

## Best solution

Define when selected worktree isolation must become physical: ideally preserve isolation as session configuration while delaying materialization until a request actually needs workspace execution or modification. The design must also specify whether an explicit Worktree selection always overrides prompt-based laziness and how a request transitions safely from read-only to workspace-dependent work.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentService.ts`, `src/vs/platform/agentHost/node/shared/worktreeIsolation.ts`, `src/vs/platform/agentHost/test/node/agentService.test.ts`, `src/vs/platform/agentHost/test/node/shared/worktreeIsolation.test.ts`
- **Validation:** Add an AgentService unit test proving that a newly created Git-backed session can complete the read-only “List my sessions” flow without invoking `gitService.addWorktree`, plus a companion test proving that the chosen workspace-dependent boundary materializes exactly one worktree before provider workspace access.
- **Behavior:**

  > A session configured for worktree isolation should not create a Git worktree merely because its first request lists existing sessions or performs another operation that needs no workspace. When the conversation reaches an operation that requires isolated workspace access, the worktree must exist before that operation runs, and modifying requests must retain today's isolation guarantee. Acceptance requires tests covering both a read-only first request with zero worktree creations and the selected transition to exactly one isolated worktree.
- **Trace:**

  > Current main resolves an unspecified Git-backed isolation configuration to `worktree` in `WorktreeIsolation.resolveIsolationConfig` at src/vs/platform/agentHost/node/shared/worktreeIsolation.ts. `AgentService._resolveWorkingDirectoryBeforeSend` in src/vs/platform/agentHost/node/agentService.ts treats the pending isolation state as sufficient to call `_resolveWorktreeBeforeSend` before every first provider send; `_resolveWorktreeBeforeSend` passes the prompt to `WorktreeIsolation.resolveOnFirstSend`, but neither layer distinguishes read-only session tools from workspace-dependent work. `resolveOnFirstSend` immediately invokes `resolveWorkingDirectory`, which performs worktree creation. Preserve existing isolation for modifying requests, failure visibility, idempotent single materialization, and explicit folder isolation; do not conflate this with https://github.com/microsoft/vscode/issues/321727, which concerns retaining a monorepo subfolder after a worktree already exists.
- **Open decisions:**
  - Should prompt-sensitive laziness apply even when the user explicitly selected Worktree, or only when Worktree came from the default or inherited configuration?
  - Which observable boundary triggers materialization: admitting any workspace-dependent request, the first workspace tool invocation, or only the first operation capable of modifying files?
  - If a conversation starts read-only and later needs a workspace, should it transparently materialize the configured worktree or require renewed user confirmation?
