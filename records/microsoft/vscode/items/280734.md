# Issue #280734 — Allow canceling fetch call on the tool call itself

[https://github.com/microsoft/vscode/issues/280734](https://github.com/microsoft/vscode/issues/280734)

## Summary

Keep open: canceling one running tool without ending the turn remains a distinct capability gap. Maintainers explicitly support a generic solution across tools, but the interaction design is unsettled.

## Change summary

Allow users to cancel a running fetch directly from its tool-call UI while letting the agent turn continue.

## Best solution

Provide a consistent, accessible per-invocation cancellation interaction across chat tools, including fetch, without canceling sibling calls or the enclosing turn. Settle the interaction design with the chat-tools owners before implementation.

- **Validation:** Add focused tool-service coverage with two pending invocations in one request: canceling the selected call must signal only its token, leave the sibling and request active, and allow subsequent tool execution. Manually exercise a slow webpage fetch and activate cancellation from its tool row using both pointer and keyboard; verify the call finishes as canceled and the turn continues.
- **Behavior:**

  > A user waiting on a slow fetch can cancel that invocation from its chat tool-call UI without stopping the whole turn. Other calls in the same turn remain unaffected, and the agent can continue after receiving the canceled outcome. The interaction should apply consistently across tools and be keyboard- and screen-reader-accessible. Existing whole-turn cancellation must retain its current behavior.
- **Trace:**

  > ChatToolInvocationPart selects the tool-specific renderer, and ChatToolProgressSubPart renders ordinary progress through ChatProgressContentPart in src/vs/workbench/contrib/chat/browser/widget/chatContentParts. LanguageModelToolsService.invokeTool in browser/tools/languageModelToolsService.ts creates a cancellation source per invocation, but the exposed cancellation operation in common/tools/languageModelToolsService.ts is request-wide; its implementation disposes every tracked call for the request. These inspected paths establish a gap between invocation-level execution cancellation and an independently actionable tool row, not a confirmed regression. Maintainers accepted generic cross-tool cancellation at https://github.com/microsoft/vscode/issues/280734#issuecomment-3613005231, but did not settle its appearance. Preserve request-wide cancellation, sibling execution, and existing approval behavior; do not treat the separate suggestion for delayed continue confirmations as an already-agreed requirement.
- **Open decisions:**
  - Should running tools expose cancellation through a persistent labeled action, a hover/focus-revealed stop control, or a tool-row menu action?
