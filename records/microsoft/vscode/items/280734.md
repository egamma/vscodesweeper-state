# Issue #280734 — Allow canceling fetch call on the tool call itself

[https://github.com/microsoft/vscode/issues/280734](https://github.com/microsoft/vscode/issues/280734)

## Summary

Keep open as an under-discussion feature request: maintainers agree that per-tool cancellation should be generic, but the user interaction and cancellation contract remain undecided. The Backlog milestone and lack of an older canonical with the same observable request do not support a close.

## Change summary

Allow users to cancel an in-progress tool call from its chat UI without canceling the entire turn.

## Best solution

Define a generic chat-tool cancellation contract and UI that lets a user stop the active tool while preserving the turn, with consistent behavior for fetch, terminal, and other cancellable tools.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser`, `src/vs/workbench/contrib/chat/common`
- **Validation:** Add chat tool-call UI tests covering cancellation of a long-running cancellable tool: the tool stops, the turn follows the selected continuation semantics, and canceling the whole turn remains unchanged.
- **Behavior:**

  > While a tool call is running, the chat UI exposes a direct cancellation affordance on that tool call. Activating it stops only that operation instead of requiring cancellation of the entire turn. The behavior should apply consistently to cancellable tools, including a slow fetch, and should clearly communicate the resulting tool state.
- **Trace:**

  > The report demonstrates that a long-running fetch can currently be stopped only by canceling the entire chat turn. Maintainers in https://github.com/microsoft/vscode/issues/280734 agree that this is a generic tool-call concern and mention terminal behavior as related precedent, but they do not settle the interaction design or post-cancellation turn semantics. Scope the plan to the shared chat tool-call rendering and execution/cancellation contract rather than a fetch-specific affordance; existing whole-turn cancellation must remain intact. The trace did not establish a bounded file-level implementation because the open product decisions affect both the shared UI and execution lifecycle.
- **Open decisions:**
  - Should the cancellation affordance always be visible, appear on hover over the running indicator, or appear only after a tool has run for a threshold?
  - After a tool call is canceled, should the model automatically continue the current turn with a canceled result, or should the turn pause and require explicit user confirmation to continue?
  - Which tools advertise per-call cancellation, and what user-visible state should non-cancellable tools show?
