# Issue #127063 — Smart Scroll: Unlock when scrolling down to the last line

[https://github.com/microsoft/vscode/issues/127063](https://github.com/microsoft/vscode/issues/127063)

## Summary

The requested scroll-position behavior remains absent on current main. A maintainer-backed implementation briefly landed but was reverted because ordinary scroll events produced false negatives, so this accepted Backlog request needs a more reliable design rather than closure.

## Change summary

Make Output smart scrolling disengage when the user scrolls up and re-engage when they scroll back to the latest output.

## Best solution

Make `output.smartScroll.enabled` reliably follow deliberate vertical scrolling—locking away from the bottom and unlocking at the bottom—while retaining the existing cursor-based interaction and avoiding state changes from programmatic or incidental scroll events.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/output/browser/outputView.ts`, `src/vs/workbench/contrib/output/browser/output.contribution.ts`, `src/vs/workbench/contrib/output/test/browser/outputView.test.ts`
- **Validation:** Add an Output-view behavioral test or equivalent runnable harness covering active output appends: deliberate scrolling up locks, reaching the bottom unlocks, programmatic reveals/content growth do not spuriously change the lock, and clicking the last line still unlocks; supplement it with the same manual sequence in the Output panel.
- **Behavior:**

  > With `output.smartScroll.enabled`, deliberately scrolling away from the latest Output content stops automatic scrolling, and scrolling back to the bottom resumes it. The existing ability to resume by clicking the last line remains available. Appending output, revealing a find result, resizing the panel, or other programmatic scrolling must not incorrectly flip the user's lock state. Acceptance covers both directions while output is arriving continuously.
- **Trace:**

  > `OutputViewPane.renderBody` in `src/vs/workbench/contrib/output/browser/outputView.ts` currently reveals the last line after model changes when unlocked and updates `scrollLock` only for explicit cursor movement. PR https://github.com/microsoft/vscode/pull/283596 added an `onDidScrollChange` listener that assigned the lock from `scrollTop + layout height >= scrollHeight`, but https://github.com/microsoft/vscode/pull/284218 reverted it after false negatives. `IScrollEvent` in `src/vs/editor/common/editorCommon.ts` has changed flags and dimensions but no event-origin field, so the planning session must trace which user and programmatic operations emit indistinguishable vertical-scroll events and establish an integration-level regression test. Preserve the existing setting and cursor-based behavior; do not broaden the work into general editor scrolling semantics.

## Evidence

- **current source gap:** Current `src/vs/workbench/contrib/output/browser/outputView.ts` updates `scrollLock` only from explicit cursor changes; `onDidChangeModelContent` merely reveals the last line while unlocked, and there is no `onDidScrollChange` handling.
- **existing capability is partial:** `src/vs/workbench/contrib/output/browser/output.contribution.ts` documents `output.smartScroll.enabled` as locking and unlocking through clicks, so the existing setting does not cover scroll-wheel-only re-engagement.
- **reverted implementation:** https://github.com/microsoft/vscode/pull/283596 implemented the requested scroll-position behavior and merged as commit 1d4be24a051d0bb5379128a8c7e5379f77abcd2d, but https://github.com/microsoft/vscode/pull/284218 reverted it in commit 900e7cb348ddf36932721b2bfa45f487c827eed1 after a maintainer reported false negatives handling scroll events.
- **event-model constraint:** `IScrollEvent` in `src/vs/editor/common/editorCommon.ts` exposes geometry and changed flags but no user-versus-programmatic provenance; the reverted implementation changed the lock on every `scrollTopChanged` event based only on bottom geometry.
- **maintainer direction:** https://github.com/microsoft/vscode/issues/127063#issuecomment-1861886398 explicitly supports disabling smart scroll when scrolling up and re-enabling it at the bottom; the later revert comment identifies an implementation problem rather than withdrawing that direction.
