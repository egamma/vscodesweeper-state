# Issue #166450 — Debugging: Support single-thread execution requests

[https://github.com/microsoft/vscode/issues/166450](https://github.com/microsoft/vscode/issues/166450)

## Summary

The capability remains unimplemented on current main and is supported by several debug-adapter authors. This should remain open while the debug maintainers choose the user-facing semantics for switching between all-thread and single-thread execution.

## Change summary

Expose DAP single-thread continue and stepping requests when a debug adapter advertises `supportsSingleThreadExecutionRequests`.

## Best solution

Carry the single-thread intent through VS Code's debug execution APIs and send `singleThread: true` for the chosen commands, gated on the adapter capability. The UI should clearly distinguish single-thread actions from all-thread actions and keep both keyboard and screen-reader discovery intact.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/common/debug.ts`, `src/vs/workbench/contrib/debug/common/debugModel.ts`, `src/vs/workbench/contrib/debug/browser/debugSession.ts`, `src/vs/workbench/contrib/debug/browser/debugCommands.ts`, `src/vs/workbench/contrib/debug/browser/callStackView.ts`, `src/vs/workbench/contrib/debug/browser/debugToolBar.ts`, `src/vs/workbench/contrib/debug/browser/runAndDebugAccessibilityHelp.ts`, `src/vs/workbench/contrib/debug/test/browser/debugSession.test.ts`
- **Validation:** Add a debug browser unit test with a mocked adapter advertising `supportsSingleThreadExecutionRequests`, invoke both single-thread and all-thread execution paths, and assert the recorded DAP arguments contain `singleThread: true` only for the selected single-thread path; run it with `scripts/test.sh --grep "single-thread execution"`.
- **Behavior:**

  > When a debug adapter advertises `supportsSingleThreadExecutionRequests`, users can deliberately continue, step over, step into, step out, reverse-continue, or step back either one selected thread or all threads. The interface clearly communicates which mode an action will use, remains fully keyboard operable, and documents the behavior in Run and Debug accessibility help. Adapters without the capability retain the existing all-thread behavior and do not receive unsupported request arguments.
- **Trace:**

  > The DAP types in src/vs/workbench/contrib/debug/common/debugProtocol.d.ts already define the capability and request fields. Execution flows from command handlers in debugCommands.ts through Thread methods in common/debugModel.ts and IDebugSession methods in common/debug.ts to debugSession.ts, where request objects currently omit `singleThread`. Call-stack inline actions in callStackView.ts and global actions in debugToolBar.ts share command IDs, so their semantics cannot currently diverge. The boundary is execution-request mode selection for capable adapters; do not alter behavior for adapters that omit the capability or change unrelated thread presentation. The broader concurrency work at https://github.com/microsoft/vscode/issues/116109 is related but does not own this specific DAP capability gap.
- **Open decisions:**
  - Should single-thread execution be an explicit mode toggle affecting all execution commands, or should thread-inline Call Stack actions operate on one thread while the global debug toolbar continues all threads?
  - If a mode toggle is chosen, should its state persist across debug sessions or reset to all-thread execution for each session?

## Evidence

- **current source:** On current main, src/vs/workbench/contrib/debug/browser/debugSession.ts constructs continue, next, stepIn, stepOut, stepBack, and reverseContinue requests without the DAP `singleThread` argument.
- **capability present but unused:** src/vs/workbench/contrib/debug/common/debugProtocol.d.ts defines `supportsSingleThreadExecutionRequests` and the `singleThread` request fields, but the capability has no use in the debug implementation outside those protocol declarations.
- **UI path:** src/vs/workbench/contrib/debug/browser/callStackView.ts registers the same continue and stepping command IDs for thread-inline actions that src/vs/workbench/contrib/debug/browser/debugToolBar.ts uses for the global toolbar; debugCommands.ts resolves a thread but provides no execution-mode distinction.
- **independent confirmation:** https://github.com/microsoft/vscode/issues/189313 was closed by a maintainer with an explicit statement that the capability was not implemented and a link back to this issue.
- **current adapter demand:** The open https://github.com/llvm/llvm-project/pull/200314 reports that lldb-dap supports single-thread execution for several requests and required local VS Code changes to exercise `singleThread: true`.
- **canonical check:** The older open https://github.com/microsoft/vscode/issues/116109 concerns scalable presentation and navigation for highly concurrent languages. It is related but does not report the same observable omission of the established DAP `singleThread` request flag, so it does not meet the stronger duplicate bar for this re-reviewed item.
