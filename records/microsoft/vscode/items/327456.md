# Issue #327456 — Git extension keeps refs/remotes/<upstream>/<branch> permanently open, preventing atomic Git ref replacement on non-Unix filesystems

[https://github.com/microsoft/vscode/issues/327456](https://github.com/microsoft/vscode/issues/327456)

## Summary

Keep open: the reporter isolated Git ref replacement failures to the built-in Git extension's upstream watcher, and current main still requests that individual-file watch. No verified canonical or fixing commit was found; filesystem-specific validation is needed before choosing the final behavior.

## Change summary

Prevent upstream-ref monitoring from blocking Git's atomic replacement or removal of loose remote refs on filesystems that prohibit unlinking open files.

## Best solution

Preserve timely upstream-change detection without retaining handles that obstruct Git ref replacement. Investigate the Git extension's DotGitWatcher on an affected mount, including nested branch names and loose-to-packed ref transitions.

## Plan brief

- **Likely files:** `extensions/git/src/repository.ts`, `extensions/git/src/watch.ts`
- **Validation:** Establish a repeatable check on an SSHFS-backed filesystem that prohibits unlinking open files: open a repository with an existing loose upstream ref in VS Code, run git pack-refs --all --prune and fetch a changed upstream ref, and verify both succeed without rename/unlink errors. Also verify external upstream changes still refresh source-control state, including a branch name containing '/', and loose-ref deletion/recreation. This check was not executed during the read-only review.
- **Behavior:**

  > With the built-in Git extension active, upstream monitoring must not prevent Git from atomically replacing or removing remote refs on a filesystem that prohibits unlinking open files. The reporter observed failures during Git operations and removed them by locally disabling transient upstream watchers. Acceptance should cover successful fetch and git pack-refs --all --prune on an affected mount, as well as continued upstream-change detection for ordinary and slash-containing branch names. A maintainer should settle whether monitoring remains transparent or an explicit opt-out is part of the supported behavior.
- **Trace:**

  > DotGitWatcher.updateTransientWatchers in extensions/git/src/repository.ts disposes the previous transient watcher, constructs the complete loose upstream-ref path using dotGit.commonPath or dotGit.path, and passes that file path to watch(). extensions/git/src/watch.ts converts it to a RelativePattern base with '*'; the extension-host service requests nonrecursive watching, and the Node backend can watch the file itself. The reporter's local bypass establishes a credible causal lead, and current main retains the same target construction, but watcher reuse and mount-specific backend behavior prevent conclusively reproducing the operating-system lock from source alone. git.autorefresh only suppresses event-driven status refresh and does not gate watcher creation. Preserve worktree common-directory handling, watcher disposal, and unrelated working-tree monitoring; do not broaden this into a general file-watcher redesign without evidence. The original report and proposed optional-setting alternative are at https://github.com/microsoft/vscode/issues/327456.
- **Open decisions:**
  - Should upstream monitoring remain transparent without a new setting, or should users also receive an explicit opt-out that sacrifices immediate upstream-change notifications?
