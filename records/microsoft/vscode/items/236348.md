# Issue #236348 — `vscode://vscode-remote/wsl+<distro>/path/to/file` des not use already open window 

[https://github.com/microsoft/vscode/issues/236348](https://github.com/microsoft/vscode/issues/236348)

## Summary

The defect remains visible in current main: a remote protocol URL without a line suffix is classified as a folder, so it cannot follow the existing authority-aware file-opening path. A maintainer confirmed the behavior, and a second reporter reproduced it recently.

## Change summary

Opening a remote file through a `vscode://vscode-remote/...` URL should reuse the existing window connected to that remote instead of replacing it or opening another window.

## Best solution

Define an unambiguous, backward-compatible way for protocol URLs to identify remote files, then route those files through the existing authority-aware window reuse path without changing remote-folder URL behavior.

## Plan brief

- **Likely files:** `src/vs/code/electron-main/app.ts`, `src/vs/platform/windows/electron-main/windowsMainService.ts`
- **Validation:** Add protocol-opening coverage that starts with an existing window for a matching remote authority, opens a remote file URL into that window, and verifies that existing remote-folder URLs retain their current behavior.
- **Behavior:**

  > A protocol URL identifying a file in a remote authority already open in VS Code opens that file in the matching existing window. It must not replace the existing workspace or create an unnecessary window. Remote folder and `.code-workspace` URLs must retain their current behavior, and `windowId=_blank` must continue to request a new window.
- **Trace:**

  > `App.getWindowOpenableFromProtocolUrl` in `src/vs/code/electron-main/app.ts` converts `vscode://vscode-remote/...` links into `vscode-remote://...` openables. It currently recognizes only `.code-workspace` paths and files carrying a `:line` suffix; all other paths become folders. `WindowsMainService` already filters candidate windows by `filesToOpen.remoteAuthority` and reuses a matching window for file openables. The historical rationale and existing `:line[:column]` contract are recorded in https://github.com/microsoft/vscode/issues/108257; preserve folder-link compatibility and explicit `windowId=_blank` behavior. The older https://github.com/microsoft/vscode/issues/209188 covers the opposite requested-window behavior and should not absorb this issue.
- **Open decisions:**
  - How should a bare `vscode://vscode-remote/...` URL distinguish a file from a folder without remote stat access while preserving existing folder links?
  - Should bare remote file URLs become supported directly, or should the product retain the explicit `:line[:column]` file marker and improve the resulting behavior or guidance?

## Evidence

- **source trace:** In `src/vs/code/electron-main/app.ts`, `getWindowOpenableFromProtocolUrl` returns `fileUri` only for a remote path ending in `:line`; every other non-workspace remote path is returned as `folderUri` at lines 1032-1041.
- **window reuse path:** `src/vs/platform/windows/electron-main/windowsMainService.ts` lines 581-617 reuse an existing window with the matching remote authority only when the resolved openable is a file; folder openables instead enter the workspace/folder-opening flow.
- **maintainer reproduction:** A maintainer confirmed the reported new-window behavior and explicitly renamed the issue to track it as a bug: https://github.com/microsoft/vscode/issues/236348#issuecomment-2516806123
- **recent confirmation:** A second reporter confirmed the same observable behavior in August 2026 when opening OSC8 source links: https://github.com/microsoft/vscode/issues/236348#issuecomment-3222528588
- **protocol ambiguity:** The earlier completed issue https://github.com/microsoft/vscode/issues/108257 documents why remote URLs historically require a `:line[:column]` suffix to identify a file: the main process cannot stat the remote path and bare paths are treated as folders.
- **canonical search:** The older open issue https://github.com/microsoft/vscode/issues/209188 concerns the opposite symptom—remote links replacing a window when the caller requests a new one—so it does not meet the same-observable-symptom requirement for this re-reviewed item.
