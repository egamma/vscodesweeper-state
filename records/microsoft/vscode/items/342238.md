# Issue #342238 — chat.exploreAgent.defaultModel not applied in Copilot CLI (agent host) sessions; no way to set subagent models from VS Code

[https://github.com/microsoft/vscode/issues/342238](https://github.com/microsoft/vscode/issues/342238)

## Summary

The setting-to-harness mismatch remains in current source: the configured Explore definition is restricted to local sessions, while agent-host sessions hide the runtime's subagent configuration command. Keep this open; the source confirms the ignored-setting path, although the reported serving model was not independently observed.

## Change summary

Make Explore model preferences effective and configurable within VS Code's Copilot CLI agent-host sessions.

## Best solution

Provide an explicit, discoverable model-selection contract for the runtime-owned Explore subagent. Resolve whether the existing Explore setting applies across harnesses and how it interacts with CLI preferences before implementing the integration.

- **Validation:** After agreeing on the preference contract, verify a fresh Copilot CLI session with Sonnet selected and Explore configured to Haiku actually invokes Explore with Haiku, using runtime model diagnostics rather than the parent-model display. Exercise conflicting CLI preferences, an unset preference, an unavailable model, and unchanged local-session selection; add targeted configuration and completion tests for the chosen surface.
- **Behavior:**

  > A user configures Explore to use Haiku while the main Copilot CLI session uses Sonnet, but the VS Code Explore setting does not reach that session's runtime-owned subagent. Users need a discoverable way within VS Code to choose the effective Explore model and understand the scope of that preference. Acceptance must establish actual subagent model selection, preserve local-session behavior, and define predictable behavior when a configured model is unavailable.
- **Trace:**

  > ExploreAgentProvider._buildCustomizedConfig() consumes the existing setting, while provideCustomAgents() restricts its generated definition to sessionTypes: ['local']. RunSubagentTool.resolveSubagentModel() consumes agent-definition models on the separate workbench path; no matching Explore-setting consumer was found under src/vs/platform/agentHost. CopilotSlashCommandCompletionProvider hides subagents, and the existing executionSubagent.model control is for a different worker. The trace confirms the missing integration but does not establish an SDK contract for overriding built-in Explore defaults. Preserve runtime ownership of model enforcement and existing CLI preferences; do not assume exposing a terminal-oriented slash command alone supplies a working VS Code interaction.
- **Open decisions:**
  - Should chat.exploreAgent.defaultModel also govern Copilot CLI agent-host sessions, or should those sessions expose a separate runtime-owned preference with the existing setting explicitly scoped to local sessions?
  - If the existing setting applies across harnesses, which preference wins when it conflicts with a model already configured through the CLI, and is the VS Code choice session-scoped or shared with standalone CLI sessions?

## Evidence

- **Confirmed local-only application:** extensions/copilot/src/extension/agents/vscode-node/exploreAgentProvider.ts reads chat.exploreAgent.defaultModel in _buildCustomizedConfig(), but provideCustomAgents() returns the resulting definition with sessionTypes: ['local']. Thus the reporter's configured Haiku preference is not supplied through this provider to a Copilot CLI session.
