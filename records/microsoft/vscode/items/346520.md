# Issue #346520 — agentHost: SQLite database breaks on WEKAFS with WAL

[https://github.com/microsoft/vscode/issues/346520](https://github.com/microsoft/vscode/issues/346520)

## Summary

Current source still permits WAL on WekaFS despite the shared-memory restriction on cross-host access. Keep this open while the existing fix proposal is reviewed and landed.

## Change summary

Prevent Agent Host SQLite databases on WekaFS shared storage from using WAL, avoiding cross-host corruption.

## Best solution

Review and land https://github.com/microsoft/vscode/pull/346521, which excludes WekaFS from WAL eligibility and adds the corresponding regression case.

## Evidence

- **Current source:** src/vs/platform/agentHost/node/agentHostSqliteJournal.ts omits WekaFS type 0x18031977 from LINUX_NETWORK_FILE_SYSTEM_TYPES. For a Linux database on that filesystem, canUseWriteAheadLog returns true and configureSqliteJournal attempts PRAGMA journal_mode = WAL, contrary to its documented network-filesystem restriction.
- **Affected persistence paths:** Both src/vs/platform/agentHost/node/agentHostDatabase.ts:4511 and src/vs/platform/agentHost/node/sessionDatabase.ts:697 call configureSqliteJournal when opening their databases, so the eligibility omission reaches Agent Host persistence.
- **Existing implementation candidate:** The supplied timeline identifies https://github.com/microsoft/vscode/pull/346521 as open. Its fetched diff adds WekaFS type 0x18031977 to the exclusion set and a Linux WekaFS test expecting WAL eligibility to be false; neither addition is present in the checkout.
- **Verification boundary:** Source inspection confirms incorrect WAL eligibility for the reported two-host shared-storage scenario. Actual database corruption was not executed or independently observed; the read-only checkout was left unchanged.
