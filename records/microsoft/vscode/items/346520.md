# Issue #346520 — agentHost: SQLite database breaks on WEKAFS with WAL

[https://github.com/microsoft/vscode/issues/346520](https://github.com/microsoft/vscode/issues/346520)

## Summary

Keep open: current source incorrectly permits WAL on WekaFS, matching the reported corruption risk when two hosts share storage. An open fixing PR already addresses the omission and should be reviewed before closing.

## Change summary

Keep Agent Host SQLite databases on rollback journaling when stored on WekaFS.

## Best solution

Review and land https://github.com/microsoft/vscode/pull/346521, retaining rollback journaling on WekaFS while preserving WAL for supported local filesystems.

## Evidence

- **Current source defect:** src/vs/platform/agentHost/node/agentHostSqliteJournal.ts omits WekaFS type 0x18031977 from LINUX_NETWORK_FILE_SYSTEM_TYPES. On Linux, canUseWriteAheadLog therefore returns true for that type, and configureSqliteJournal attempts PRAGMA journal_mode = WAL followed by synchronous = NORMAL. The helper explicitly documents that WAL's shared-memory index cannot be shared between machines.
- **Affected database paths:** src/vs/platform/agentHost/node/agentHostDatabase.ts:4511 and src/vs/platform/agentHost/node/sessionDatabase.ts:659 both invoke configureSqliteJournal during database opening, so the omission affects central and session persistence.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/346521 is verified open and explicitly fixes https://github.com/microsoft/vscode/issues/346520. Its diff adds WekaFS type 0x18031977 to the exclusion set and a Linux WekaFS case expecting canUseWriteAheadLog to return false.
- **Verification boundary:** The incorrect journal-selection branch is confirmed from current source; actual multi-host database corruption was not executed or independently observed. Inspection remained read-only.
