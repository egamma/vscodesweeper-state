# Issue #100611 — Fail to load timeline info when activate timeline view using keyboard shortcut

[https://github.com/microsoft/vscode/issues/100611](https://github.com/microsoft/vscode/issues/100611)

## Summary

The keyboard path remains broken on current main: `files.openTimeline` silently does nothing without a URI argument. This team-authored, accepted bug must remain open, and the documented `timeline.focus` workaround does not fully cover pinned timelines.

## Change summary

Invoking Open Timeline from a keyboard shortcut fails to load timeline data for the active file.

## Best solution

Make keyboard invocation load the active resource's timeline while preserving the explorer context-menu behavior. A maintainer should first settle whether argument-less invocation pins that resource or keeps following the active editor.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/timeline/browser/timeline.contribution.ts`, `src/vs/workbench/contrib/timeline/browser/timelinePane.ts`
- **Validation:** Invoke `files.openTimeline` through a keybinding with an active file and no command argument; verify that the Timeline view opens with that file's entries, then verify the chosen pin/follow behavior when switching editors and that explorer context-menu invocation still opens the explicitly selected resource.
- **Behavior:**

  > Invoking Open Timeline from a keyboard shortcut while a file editor is active must open the Timeline view and load entries for that file instead of leaving the view empty. Explorer context-menu invocation with an explicit resource must remain unchanged. Switching editors afterward must follow the pin/follow behavior selected by the maintainer, and invoking the command without an eligible active resource must not display stale timeline data.
- **Trace:**

  > The `files.openTimeline` command in src/vs/workbench/contrib/timeline/browser/timeline.contribution.ts accepts an argument and calls `ITimelineService.setUri` only when that argument is a URI. Keyboard invocation supplies no URI, so it never reaches `TimelineService.setUri` in src/vs/workbench/contrib/timeline/common/timelineService.ts, which is the path that opens the view and emits the resource change. `TimelinePane.setUriCore` in src/vs/workbench/contrib/timeline/browser/timelinePane.ts disables follow mode, updates the resource, and loads data. The existing `timeline.focus` command is a partial workaround but has different pin/follow semantics. Preserve explicit-resource context-menu behavior and avoid changing unrelated view focus infrastructure; https://github.com/microsoft/vscode/issues/234683 is related only to broader keyboard-focus discoverability.
- **Open decisions:**
  - When `files.openTimeline` is invoked without a URI, should it load and pin the active editor resource like an explicit explorer invocation, or focus the view while continuing to follow the active editor?

## Evidence

- **current source:** In src/vs/workbench/contrib/timeline/browser/timeline.contribution.ts, the `files.openTimeline` handler calls `ITimelineService.setUri` only when `URI.isUri(arg)`; a normal keybinding supplies no resource, so the handler has no effect.
- **loading path:** src/vs/workbench/contrib/timeline/common/timelineService.ts shows that `TimelineService.setUri` opens the Timeline view and emits the URI change; src/vs/workbench/contrib/timeline/browser/timelinePane.ts then disables following, sets the URI, and loads the timeline. The argument-less command never reaches this path.
- **workaround limitation:** The 2024 confirmation on https://github.com/microsoft/vscode/issues/100611 reports that `timeline.focus` works only with care around pinning, so it does not fully replace the reported command behavior.
