# Issue #140980 — Debug targets that don't exist in launch.json

[https://github.com/microsoft/vscode/issues/140980](https://github.com/microsoft/vscode/issues/140980)

## Summary

The issue is still necessary: dynamically supplied debug configurations are intentionally persisted, but stale entries can remain after their provider is unavailable and the Run and Debug UI offers no supported way to identify or remove them. This team-authored Backlog bug has a later independent confirmation and no verified older canonical with the same observable symptom.

## Change summary

Persisted dynamic debug configurations can remain visible after their providing extension is unavailable, with no discoverable origin or in-product removal action.

## Best solution

Keep enough provider metadata with recent dynamic configurations to identify their source, validate or prune entries whose provider is unavailable, and provide a supported removal action in the Run and Debug configuration picker without requiring deletion of all workspace storage.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts`, `src/vs/workbench/contrib/debug/browser/debugActionViewItems.ts`, `src/vs/workbench/contrib/debug/test/browser/debugConfigurationManager.test.ts`
- **Validation:** Add debug configuration manager tests that restore a persisted dynamic configuration with no available provider and verify the chosen stale-entry behavior, plus a picker-level test or explicit manual check that one dynamic entry can be identified and removed without deleting unrelated recent configurations.
- **Behavior:**

  > A recent dynamic debug configuration must not become an unexplained permanent entry after its provider is unavailable. Users must be able to identify the configuration's source and remove the stale entry from the Run and Debug experience without deleting all workspace storage. Static launch.json configurations and valid dynamic configurations must retain their current selection and start behavior.
- **Trace:**

  > Recent dynamic configurations are persisted under DEBUG_RECENT_DYNAMIC_CONFIGURATIONS and restored by DebugConfigurationManager in src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts. The restore path retains the debug type, name, and configuration but does not validate that a matching provider is currently available; getDynamicProviders() only filters registered providers by type. DebugActionViewItem in src/vs/workbench/contrib/debug/browser/debugActionViewItems.ts adds those restored entries to the picker and starts them, but has no removal or provider-discovery interaction. The reporter reproduced persistence with extensions disabled, and the later comment confirms that deleting workspaceStorage removes the entries. Preserve launch.json configuration editing, valid dynamic provider behavior, and unrelated workspace storage.
- **Open decisions:**
  - Should an unavailable provider cause its persisted dynamic configurations to be removed automatically, hidden until the provider returns, or retained with an unavailable-source indication?
  - Should removal be exposed as a per-entry action in the configuration picker, through the existing gear action when a dynamic entry is selected, or both?
  - Must provider identity be persisted with each recent dynamic configuration so the UI can name its source after the provider is disabled or uninstalled?
