## Plan brief

- **Likely files:** `src/vs/base/browser/ui/menu/menu.ts`, `src/vs/base/browser/ui/menu/menubar.ts`, `src/vs/base/browser/ui/actionbar/actionbar.ts`
- **Validation:** On current Windows, enable Magnifier's keyboard-focus tracking, focus the custom menubar with Alt, enter each top-level menu, and navigate with arrow keys; verify Magnifier follows every focused menu item, including a context menu positioned over the panel, while keyboard navigation and native menus remain unchanged.
- **Behavior:**

  > With Windows Magnifier configured to follow keyboard focus, navigating VS Code's custom menubar and its opened menu items must move the magnified viewport to every focused item. This must also hold for context menus displayed outside their originating editor region. Existing keyboard navigation, submenu behavior, and the native-menu path must remain unchanged.
- **Trace:**

  > The issue was reproduced by two maintainers and again in Electron 11 Insiders. Menu constructs a vertical ActionBar with role `menu` in src/vs/base/browser/ui/menu/menu.ts, while its action items receive role `menuitem`; ActionBar.updateFocus in src/vs/base/browser/ui/actionbar/actionbar.ts invokes real DOM focus rather than aria-activedescendant. The failure was reported only with Windows Magnifier, not ZoomText or web, and could also occur when the shared context-menu widget extended outside the editor area. That makes the accessibility focus/bounds events crossing the Electron UI Automation bridge the unresolved boundary; first confirm those events on current Windows before assigning ownership. Do not replace the established menu keyboard-focus model or regress context menus that already track correctly. The editor-caret defect at https://github.com/microsoft/vscode/issues/105558 was separate and is already closed.
