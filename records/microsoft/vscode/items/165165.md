# Issue #165165 — Support custom "reverse requests" from debug adapters

[https://github.com/microsoft/vscode/issues/165165](https://github.com/microsoft/vscode/issues/165165)

## Summary

Keep open: this API-proposal tracks a still-valid extension API gap for handling custom debug-adapter reverse requests. The discussion supports the capability but leaves public-contract questions around handler selection and custom capabilities unresolved.

## Change summary

Allow extensions to register handlers for custom reverse requests sent by debug adapters and return responses to the adapter.

## Best solution

Design a proposed debug API that registers custom reverse-request handlers by command, defines collision and lifecycle semantics, and determines whether custom capabilities must be advertised alongside handlers; keep the proposal open through API finalization.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.debugVisualization.d.ts`, `src/vs/workbench/api/common/extHostDebugService.ts`, `src/vs/workbench/api/browser/mainThreadDebugService.ts`, `src/vs/workbench/contrib/debug/common/debugModel.ts`
- **Validation:** Add extension-host API tests with a mock debug adapter that sends a custom reverse request, verifies the registered extension handler receives its arguments and returns a response, and verifies the defined behavior for unknown commands and competing registrations.
- **Behavior:**

  > A debug extension can register a handler for a named custom reverse request from its debug adapter and asynchronously return either a successful response body or a defined error. Standard DAP reverse requests and custom event handling remain unchanged. The finalized contract must define registration scope, disposal, unknown-request behavior, and conflicts between extensions.
- **Trace:**

  > The existing public API exposes `DebugSession.customRequest` for extension-to-adapter requests and `debug.onDidReceiveDebugSessionCustomEvent` for adapter-to-extension custom events, but the issue identifies no corresponding adapter-to-extension request/response hook. Reverse requests pass through the debug session implementation and extension-host/main-thread debug bridge; the proposal should remain within that debug API path and must not alter handling of standard DAP requests such as `runInTerminal`. The source of uncertainty begins at the public contract: which extension owns a command, how collisions resolve, and whether handlers advertise custom capabilities to the adapter. The issue is protected by its `api-proposal` label and must stay open through finalization.
- **Open decisions:**
  - Is a custom reverse-request handler scoped to a debug type, a debug session, or globally, and which extension is eligible to register it?
  - What user-observable error or precedence behavior applies when no handler or multiple handlers exist for the same request command?
  - Must registration also advertise custom capabilities to the debug adapter, and if so what public capability shape is exposed?
