# Issue #200511 — Expose API/configuration to add supported language IDs for `typescript-language-features`

[https://github.com/microsoft/vscode/issues/200511](https://github.com/microsoft/vscode/issues/200511)

## Summary

Keep open: plugin-contributed languages receive language providers, but several built-in TypeScript commands and editor-context features still recognize only JavaScript and TypeScript. The requested supported-language extension point remains missing, and the canonical searches found no issue that supersedes this request.

## Change summary

Expose a supported API or contribution mechanism for additional language IDs to participate in built-in TypeScript language features without patching the extension bundle.

## Best solution

Define an extension-facing supported-language contract in typescript-language-features, including which command, editor-context, and status features an opted-in language inherits. Preserve existing plugin language-provider support and standard JavaScript/TypeScript behavior.

## Plan brief

- **Likely files:** `extensions/typescript-language-features/src/api.ts`, `extensions/typescript-language-features/src/configuration/languageIds.ts`, `extensions/typescript-language-features/src/tsServer/plugins.ts`, `extensions/typescript-language-features/src/typeScriptServiceClientHost.ts`, `extensions/typescript-language-features/src/ui/activeJsTsEditorTracker.ts`, `extensions/typescript-language-features/src/ui/managedFileContext.ts`, `extensions/typescript-language-features/src/languageFeatures/sourceDefinition.ts`
- **Validation:** In an extension-host integration check, contribute a test language backed by a TS server plugin and opt it in through the agreed public contract. Verify that opening its document activates the agreed managed-editor context and command/status features without bundle patching; verify an unregistered language stays excluded and existing JavaScript/TypeScript behavior remains unchanged.
- **Behavior:**

  > Language-extension authors should be able to opt additional language IDs into the agreed built-in TypeScript feature surfaces using a supported contract rather than rewriting the extension bundle. Existing plugin-backed language providers alone do not satisfy this request because editor recognition and some commands remain restricted to the four built-in language IDs. Acceptance should exercise a contributed test language, an unregistered language, and ordinary JavaScript/TypeScript files, with no change to existing defaults.
- **Trace:**

  > PluginManager.readPlugins() in extensions/typescript-language-features/src/tsServer/plugins.ts already discovers contributed language IDs, and TypeScriptServiceClientHost.getAllModeIds() plus registerExtensionLanguageProvider() uses them for language services. Separately, src/configuration/languageIds.ts hard-codes jsTsLanguageModes and isSupportedLanguageMode(); ActiveJsTsEditorTracker, ManagedFileContextManager, and SourceDefinitionCommand consume that restricted recognition. The original workaround in https://github.com/vuejs/language-tools/pull/3788 explicitly patches both shared language-mode surfaces. src/api.ts currently offers plugin configuration but no supported-language registration. The uncertainty is the public participation contract and which additional feature surfaces opting in should promise, not whether plugin languages are already discovered. Preserve current provider registration, standard-language behavior, and disabled-scheme restrictions; the JSON and HTML precedents linked in the discussion are not implementations of this TypeScript contract.
- **Open decisions:**
  - Should supported-language participation be declared through extension contributions, registered dynamically through getAPI(), or supported through both, and must participation changes take effect without reloading?
  - Which built-in TypeScript command, editor-context, and status features should participation guarantee for a custom language, beyond the language providers already supplied by typescriptServerPlugins.languages?

## Evidence

- **Existing contribution provides partial coverage:** extensions/typescript-language-features/src/tsServer/plugins.ts reads contributes.typescriptServerPlugins[].languages and configNamespace. TypeScriptServiceClientHost in src/typeScriptServiceClientHost.ts includes those IDs in getAllModeIds() and registers extension language providers. This supports plugin-backed language services, but does not extend the shared supported-language predicates.
- **Requested extension point remains absent:** extensions/typescript-language-features/src/api.ts exposes configurePlugin() and onCompletionAccepted through getAPI(0), with no supported-language registration method. src/configuration/languageIds.ts still hard-codes javascript, javascriptreact, typescript, and typescriptreact in jsTsLanguageModes and isSupportedLanguageMode().
- **Observable remaining boundary:** src/ui/activeJsTsEditorTracker.ts and src/ui/managedFileContext.ts use isSupportedLanguageMode() to recognize managed script editors and set typescript.isManagedFile. src/languageFeatures/sourceDefinition.ts also rejects documents failing that predicate with 'Unsupported file type.' Plugin languages therefore do not automatically inherit these features.
