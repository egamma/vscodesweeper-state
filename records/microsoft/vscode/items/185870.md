# Issue #185870 — Editor rulers disappear randomly in large files

[https://github.com/microsoft/vscode/issues/185870](https://github.com/microsoft/vscode/issues/185870)

## Summary

The issue remains necessary: a second user confirmed the artifact, and the current default DOM renderer still draws each ruler as one extremely tall element rather than keeping it viewport-relative. The optional GPU renderer avoids that DOM path but does not resolve the default behavior.

## Change summary

Configured editor rulers develop distracting gaps or disappear while scrolling sufficiently large files.

## Best solution

Keep rulers continuous throughout large files by making the default DOM ruler rendering viewport-relative, or otherwise avoiding the browser's unreliable rendering of extremely tall box-shadow elements, without changing ruler positions, colors, or scrolling behavior.

## Plan brief

- **Likely files:** `src/vs/editor/browser/viewParts/rulers/rulers.ts`, `src/vs/editor/browser/viewParts/rulers/rulers.css`, `src/vs/editor/browser/view.ts`
- **Validation:** Launch Code OSS with the default DOM editor renderer, configure `editor.rulers` to `[80, 100, 120]`, open `vscode.d.ts` and a roughly 3,000-line fixture, then scroll through each file at several zoom levels; all three rulers must remain continuous without gaps while their positions and colors remain unchanged.
- **Behavior:**

  > With multiple `editor.rulers` configured, every ruler must remain continuously visible while scrolling large files. The behavior must hold in the default DOM renderer, including the roughly 3,000-line case reported by a second user. Ruler columns, custom colors, zoom behavior, and normal editor scrolling must remain unchanged.
- **Trace:**

  > The default path in src/vs/editor/browser/view.ts constructs `Rulers` when no GPU view context is active. In src/vs/editor/browser/viewParts/rulers/rulers.ts, every ruler is a single element extending from the top of the scrollable content to `Math.min(scrollHeight, 1000000)`, while src/vs/editor/browser/viewParts/rulers/rulers.css renders its line with an inset box shadow. The report and later confirmation indicate Chromium intermittently fails to paint that tall element, but the precise browser threshold remains unverified. The GPU implementation in src/vs/editor/browser/viewParts/rulersGpu/rulersGpu.ts is an alternative path, not coverage for the default renderer. Preserve ruler configuration semantics and avoid broad changes to editor scrolling or unrelated view parts.
- **Open decisions:**
  - Should the DOM ruler be rendered relative to the visible viewport, or should the existing large-number coordinate virtualization be extended to reposition it?
  - Which Chromium, display-scale, and zoom combinations must be covered to make the rendering regression test reliable?
  - Is the DOM path expected to remain supported independently of the experimental GPU renderer?

## Evidence

- **current source:** src/vs/editor/browser/viewParts/rulers/rulers.ts still represents each configured ruler as one `.view-ruler` element whose height is `Math.min(ctx.scrollHeight, 1000000)`; it is not repositioned on ordinary vertical scrolling.
- **rendering mechanism:** src/vs/editor/browser/viewParts/rulers/rulers.css draws the ruler using an inset `box-shadow` on that tall element, matching the rendering mechanism implicated by the report.
- **independent confirmation:** The 2025-05-01 comment reports the same random gaps in files of roughly 3,000 lines, so the problem is not supported only by the original 2023 reproduction.
- **alternative renderer:** src/vs/editor/browser/view.ts selects RulersGpu only when a GPU view context exists; otherwise it continues to instantiate the affected Rulers DOM implementation. The broader WebGPU tracker https://github.com/microsoft/vscode/issues/221145 therefore does not absorb or complete this default-renderer bug.
- **no fixing change:** Repository history contains no commit referencing https://github.com/microsoft/vscode/issues/185870; the later ruler fix in https://github.com/microsoft/vscode/pull/286122 addresses negative zoom and does not change the tall-element behavior.
