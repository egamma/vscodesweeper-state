# Issue #170829 — Perf: Tasks problem matcher and JSON schemas block startup

[https://github.com/microsoft/vscode/issues/170829](https://github.com/microsoft/vscode/issues/170829)

## Summary

Keep open: current main still constructs task schemas and problem-matcher registries during module loading. The linked deferral PR was closed without merging, and its discussion confirms that delaying registration alone did not remove the eager cloning.

## Change summary

Avoid eagerly constructing task problem matchers and JSON schemas during workbench startup when they are not yet needed.

## Best solution

Make expensive task initialization demand-driven while preserving extension contribution handling, tasks.json validation, and watch-task reconnection on reload. Establish the initialization dependencies and profile the actual module-loading cost before choosing the lifecycle boundary.

- **Behavior:**

  > Workbench startup should not eagerly perform expensive task-schema and problem-matcher initialization solely because task modules are imported. Required task functionality must remain available when first used, including tasks.json validation and extension-contributed matchers. Acceptance requires profiling that demonstrates removal of unnecessary startup work alongside functional checks of those task workflows.
- **Trace:**

  > workbench.common.main.ts statically imports task.contribution.ts, which statically imports both schema modules and problemMatcher.ts. The schema modules execute deep cloning and reference rewriting at module scope, while problemMatcher.ts constructs both registries and fills defaults on import. The AfterRestored TaskRegistryContribution only installs schema-update listeners and does not defer those operations. The closed, unmerged attempt at https://github.com/microsoft/vscode/pull/183039 did not show a substantial improvement, and its discussion identifies remaining module-factory cloning. abstractTaskService.ts awaits matcher readiness before running or reconnecting tasks, and the matcher extension point depends on the pattern extension point. The unresolved technical boundary is which schema and contribution-registration work must remain available during extension processing versus which initialization can wait for demand; other consumers have not been exhaustively traced. Preserve task execution, contributed matchers, schema updates, and watch-task reconnection rather than merely moving registration later.
