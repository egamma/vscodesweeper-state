# Issue #257247 — Extended git conflict markers are not handled correctly

[https://github.com/microsoft/vscode/issues/257247](https://github.com/microsoft/vscode/issues/257247)

## Summary

Extended conflict-marker support remains missing in the current parser. Keep this accepted Backlog request open; the older reports inspected do not cover the same observable symptom.

## Change summary

Recognize and correctly resolve Git conflicts whose markers are longer than seven characters, including the reported eight-character rename-conflict case.

## Best solution

Support Git-generated extended marker lengths consistently across conflict detection, labels, and resolution, preserving ordinary seven-character handling. Verify both inline conflict actions and the merge editor against the supplied rename-conflict scenario.

## Evidence

- **Reported trigger:** https://github.com/microsoft/vscode/issues/257247 supplies https://github.com/Andree2/GitMerge250 and a branchB-to-main merge that produces eight-character markers in rename.txt. The reporter states that shortening those markers to seven characters restores recognition.
- **Current parser limitation:** extensions/merge-conflict/src/mergeConflictParser.ts defines splitterMarker as '=======' and scanDocument accepts the separator only through line.text === splitterMarker. An eight-character '========' separator is skipped; scanItemTolMergeConflictDescriptor subsequently rejects the conflict because scanned.splitter is absent. Header and footer name extraction also assumes a seven-character marker.
- **Existing capability check:** extensions/merge-conflict/package.json exposes CodeLens, decoration, navigation, and comparison-position settings, but no marker-length option. These settings cannot change the parser's exact separator comparison; manually shortening markers is a workaround rather than coverage of the requested capability.
- **Related merge-editor handling:** src/vs/workbench/contrib/mergeEditor/browser/mergeMarkers/mergeMarkersController.ts recognizes start/end markers by seven-character prefixes, while extensions/git/src/commands.ts findFirstConflictMarker extracts labels after seven characters. Prefix recognition alone does not address separator parsing or consistent extended-marker labels. The reported post-resolution marker retention was not executed or conclusively traced.
