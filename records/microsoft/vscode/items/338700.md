# Issue #338700 — Indent/outdent onEnter rule should add an indented line in the middle and place cursor there

[https://github.com/microsoft/vscode/issues/338700](https://github.com/microsoft/vscode/issues/338700)

## Summary

Traced the reported behavior in cursorTypeEditOperations.ts and enterAction.ts: the code is confirmed to reproduce as described, but the fix isn't a simple bug patch — it collides with a design assumption that every built-in `indentOutdent` + `appendText` usage in this repo relies on, so it needs a maintainer decision before an agent changes it.

## Change summary

When an onEnterRule uses `indentAction: indentOutdent` with `appendText` (e.g. `end`) and no matching `afterText` already in the document, VS Code appends the text onto the first (indented) line instead of placing it on its own outdented line with the cursor on the blank indented line above it.

## Best solution

Needs a design call: `getEnterAction`/`typeCommand`'s IndentOutdent branch (src/vs/editor/common/languages/enterAction.ts, src/vs/editor/common/cursor/cursorTypeEditOperations.ts) currently always folds `appendText` into the first line's indentation, which is exactly right for the existing docComment-style ` * ` marker and the bracket `\t` cases, but wrong for a use case like `begin`/`end` where `appendText` is meant to be a full closing line. A blanket change would alter behavior for extensions/typescript-basics, php, java (docComment) and typescript-basics' `()/{}/[]` indent rules, so this needs either a new mechanism to distinguish 'mid-line marker' vs 'closing-line text' or an opt-in flag, decided with a maintainer.

- **Trace:**

  > Root cause: for `IndentAction.IndentOutdent`, `getEnterAction` (enterAction.ts) leaves `appendText` un-prefixed when it's already truthy and the action isn't plain `Indent`, and `cursorTypeEditOperations.ts`'s IndentOutdent branch folds `indentation + appendText` into the FIRST of the two inserted lines (`increasedIndent`), then places the cursor at its end — this is correct for the doc-comment ` * ` marker and bracket `\t` cases (extensions/java, php, typescript-basics language-configuration.json) which all pair `appendText` with an existing closer matched via `afterText`, but wrong when `appendText` represents a standalone closing keyword (like `end`) with no existing `afterText` match. The boundary: don't touch the existing docComment/bracket paths that already pass; whatever the maintainer decides (e.g. a new field, or conditioning on absence of afterText) must not change lines that already have a matched closer.
- **Open decisions:**
  - Should there be a new mechanism (e.g. a distinct property, or behavior keyed off whether `afterText` matched an existing closer) to let `appendText` mean 'insert this as the closing line' instead of always folding it into the indented middle line?
  - If yes, what should the on-enter language-configuration schema/API look like, and does it need a new stable or proposed API surface documented in vscode.d.ts?

## Evidence

- **code path:** src/vs/editor/common/cursor/cursorTypeEditOperations.ts lines 565-574: for IndentOutdent, `increasedIndent = config.normalizeIndentation(r.indentation + r.appendText)` is placed on the FIRST inserted line, and the cursor is placed at the end of that line via `ReplaceCommandWithOffsetCursorState(range, typeText, -1, increasedIndent.length - normalIndent.length, true)` — matching the reported `begin\nend|` result exactly.
- **appendText handling:** src/vs/editor/common/languages/enterAction.ts lines ~38-48: when appendText is truthy and indentAction is IndentOutdent (not Indent), no tab is prepended and appendText is passed through unchanged, so it lands on the indented first line rather than the outdented second line.
- **existing usages all rely on current behavior:** Every built-in `indentOutdent`+`appendText` config (extensions/java, extensions/php, extensions/typescript-basics doc-comment rules use `appendText: " * "`; typescript-basics' `()/{}/[]` rules use `appendText: "\t"`) assumes appendText is a middle-line marker paired with an existing closer matched via `afterText`, not a synthesized full closing line — changing the semantics would affect all of these.
