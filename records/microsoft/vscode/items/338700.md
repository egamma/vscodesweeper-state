# Issue #338700 — Add way to add text on next line with onEnter rules

[https://github.com/microsoft/vscode/issues/338700](https://github.com/microsoft/vscode/issues/338700)

## Summary

Confirmed on main that `indentOutdent`'s `appendText` is placed on the first (indented) line rather than the outdented second line, matching the report; the author's own follow-up comment proposes a concrete new `appendTextNextLine` field on `EnterAction`, which is a public API/language-configuration contract change that needs a maintainer design decision before implementation.

## Change summary

Request a way for an `onEnterRules` `indentOutdent` action to place appended text on the outdented (second) line instead of the indented (first) line, so the cursor lands between the two generated lines.

## Best solution

Design and land a language-configuration extension (e.g. the author's proposed `appendTextNextLine` on `EnterAction`) in languageConfiguration.ts/enterAction.ts and the cursor type-edit logic in cursorTypeEditOperations.ts, exposed through the Monaco and VS Code extension API surfaces consistently.

## Plan brief

- **Validation:** A cursor type-command test asserting that for an `indentOutdent` rule using the new field, the appended text lands on the outdented line and the cursor remains on the indented line — before/after behavior change.
- **Behavior:**

  > When an `onEnterRules` entry with `indentAction: indentOutdent` fires, the language-configuration author should be able to place generated text on the second (outdented) line rather than the first, with the cursor staying on the first (indented) line. Existing configurations using only `appendText` must be unaffected (new field is opt-in). Acceptance: typing `begin` + Enter with the new field set to `end` produces `begin\n  |\nend` instead of today's `begin\nend|`.
- **Trace:**

  > Root cause confirmed in src/vs/editor/common/cursor/cursorTypeEditOperations.ts (lines ~566-575): for IndentAction.IndentOutdent the code builds `typeText = '\n' + increasedIndent + '\n' + normalIndent` where `increasedIndent` already includes `r.appendText`, so appended text always lands on the first line. EnterAction is defined in src/vs/editor/common/languages/languageConfiguration.ts (~lines 251-279) with only `appendText`/`removeText`; onEnter.ts and languageConfigurationRegistry.ts wire the rule matching. The boundary: do not change behavior for IndentAction.Indent/None/Outdent or existing `appendText` semantics — only add a new opt-in path for the outdented line. Related (unverified) reports: https://github.com/microsoft/vscode/issues/244880 and https://github.com/microsoft/vscode/issues/583. Uncertainty starts at the API shape itself — field name, whether it's Monaco-only or also exposed via the VS Code extension API, and whether it should generalize beyond `indentOutdent`.
- **Open decisions:**
  - Should the new capability be an opt-in `appendTextNextLine` field on `EnterAction` as proposed, or a different shape (e.g. a structured per-line text list)?
  - Does this apply only to `IndentAction.IndentOutdent`, or should analogous next-line placement be supported for other indent actions?
  - Does adding this field require going through the formal API-proposal process for the extension/Monaco surfaces, or can it ship directly as a non-breaking addition?
