- **Validation:** On a WebGPU-capable build, configure editor.experimentalGpuAcceleration='on', editor.wordWrap='off', and editor.rulers=[80]; open a file with lines longer than 160 columns and scroll horizontally past column 80. The plan should establish an executable regression check for the clipping boundary before implementation.
- **Behavior:**

  > With GPU editor rendering enabled, a column ruler must remain confined to the text-content viewport. Horizontally scrolling it beyond the viewport's left edge must hide it rather than draw it over line numbers. This must hold on initial rendering and after editor layout changes. Ruler positioning within the text area and DOM-rendered editor behavior must remain unchanged.
- **Trace:**

  > The reporter confirmed recurrence after https://github.com/microsoft/vscode/pull/237671, and https://github.com/microsoft/vscode/issues/235437 supplies explicit horizontal-scroll steps for the same symptom. RulersGpu in src/vs/editor/browser/viewParts/rulersGpu/rulersGpu.ts registers column-positioned rectangles, and RectangleRenderer.draw in src/vs/editor/browser/gpu/rectangleRenderer.ts clips them using ViewGpuContext.contentLeft. In src/vs/editor/browser/gpu/viewGpuContext.ts, that observable starts at zero and is refreshed only by global configuration-service events, while the rectangle shader's viewport offset reads the editor's actual layout. Editor-local layout changes have their own configuration event path, and ViewLinesGpu shares the potentially stale clipping observable. This establishes a concrete initialization/synchronization lead, but not which lifecycle condition produced the reporter's later screenshot. First establish the current-build failing scenario and a regression check; preserve shared text rendering, ruler column semantics, and DOM fallback behavior.
