# Issue #337090 — Open in VS Code seems to kill the tunnel connection

[https://github.com/microsoft/vscode/issues/337090](https://github.com/microsoft/vscode/issues/337090)

## Summary

Fresh, team-authored bug report (0 days old) with a first-hand repro and screenshot showing the Dev Container + tunnel connection getting torn down after clicking 'Open in VS Code' from the Agents window; no fix exists yet on main, so this stays open for investigation.

## Change summary

Clicking 'Open in VS Code' for a Dev Container session over a tunnel connection appears to kill the tunnel before the container finishes installing/loading.

## Best solution

Trace the 'Open in VS Code' handoff path (src/vs/sessions/browser/openInVSCodeUtils.ts, sessionRemoteConnection.ts) together with the Dev Container/tunnel agent host connector (src/vs/sessions/common/devContainerAgentHostService.ts, providers/remoteAgentHost/electron-browser/tunnelAgentHostServiceImpl.ts) to find why the tunnel is disposed mid-install, since this spans multiple session/agent-host components and needs a maintainer to scope which layer owns the disposal.

## Plan brief

- **Likely files:** `src/vs/sessions/browser/openInVSCodeUtils.ts`, `src/vs/sessions/browser/parts/sessionRemoteConnection.ts`, `src/vs/sessions/common/devContainerAgentHostService.ts`, `src/vs/sessions/contrib/providers/remoteAgentHost/electron-browser/tunnelAgentHostServiceImpl.ts`
- **Validation:** Reproduce a Dev Container + tunnel session in the Agents window, click 'Open in VS Code', and confirm the tunnel/dev container connection survives and finishes installing rather than being torn down.
- **Behavior:**

  > Clicking 'Open in VS Code' on a Dev Container session that is connected via a tunnel should hand off to the local VS Code window without disrupting the underlying tunnel/dev container connection; the container should finish installing and the local window should attach successfully. Currently the tunnel connection appears to close and the container install stalls. Acceptance: repeating the reporter's steps (tunnel + Dev Container session in Agents window, then Open in VS Code) results in a successfully attached local window with the container finishing setup, and the tunnel is not prematurely disposed.
- **Trace:**

  > Not yet traced to a specific root cause — the report implicates the handoff from the Agents window's 'Open in VS Code' action (src/vs/sessions/browser/openInVSCodeUtils.ts, sessionRemoteConnection.ts) into the Dev Container + tunnel agent host connector (src/vs/sessions/common/devContainerAgentHostService.ts, src/vs/sessions/contrib/providers/remoteAgentHost/electron-browser/tunnelAgentHostServiceImpl.ts, devContainerAgentHostConnector.contribution.ts). Uncertainty starts at which component disposes the tunnel: whether the Open-in-VS-Code action disposes the Agents-window-side connection object that the tunnel depends on, or whether the local window's connect attempt races the still-installing container. Do not change the resolveRemoteAuthority contract or the general tunnel lifecycle for non-Dev-Container flows.
- **Open decisions:**
  - Should the Agents-window tunnel/session connection stay alive after 'Open in VS Code' hands off to the local window, or is a fresh connection expected in the local window regardless?
  - If the container is still installing when the user clicks 'Open in VS Code', should the action wait/queue until install completes, or attempt an immediate handoff?
