# Issue #203344 — New System commands to toggle collapse state

[https://github.com/microsoft/vscode/issues/203344](https://github.com/microsoft/vscode/issues/203344)

## Summary

Keep this accepted, community-supported request open: current commands can reveal or hide a contributed view, but do not expose its collapse state independently. The existing workbench-views routing is appropriate, and no matching canonical was verified.

## Change summary

Expose commands to programmatically collapse and expand a specific contributed view without removing it or disposing its WebviewView.

## Best solution

Provide an extension-callable command contract for controlling individual view expansion while preserving the existing manual-collapse lifecycle. Settle its behavior for inactive containers and single-view containers before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/services/views/browser/viewsService.ts`, `src/vs/workbench/services/views/browser/viewDescriptorService.ts`, `src/vs/workbench/browser/parts/views/viewPaneContainer.ts`, `src/vs/workbench/contrib/webviewView/browser/webviewViewPane.ts`
- **Validation:** In an Extension Development Host, contribute a webview view alongside another view, invoke the agreed collapse/expand commands, and verify that collapse leaves its header available, expansion restores its body, and onDidDispose does not fire. Repeat with a single-view container and an inactive container according to the agreed contract; ensure existing toggleVisibility behavior remains unchanged.
- **Behavior:**

  > An extension needs to control whether its contributed view is expanded or collapsed without removing the view from its container. Collapsing should preserve the WebviewView object and leave the normal user expansion affordance available wherever the container supports it. Expansion should restore the view body. Acceptance checks must distinguish WebviewView disposal from the existing iframe-document retention policy and cover single-view and inactive containers.
- **Trace:**

  > For https://github.com/microsoft/vscode/issues/203344, the current command registrations expose open/focus in src/vs/workbench/services/views/browser/viewsService.ts and toggleVisibility/removeView in src/vs/workbench/services/views/browser/viewDescriptorService.ts, but not individual collapse control. ViewsService.closeView can call setExpanded(false), yet its single-view branch hides the entire part, so it does not establish a uniform collapse contract. ViewPaneContainer records expansion changes through ViewContainerModel.setCollapsed, and WebviewViewPane responds to body visibility by claiming or releasing its overlay. The public WebviewView documentation distinguishes collapse from disposal and separately documents iframe deallocation. Preserve existing hide/show commands, persisted manual expansion behavior, and webview resource-retention semantics. The remaining uncertainty concerns what the new command promises when the target container is inactive or has a merged single-view header.
- **Open decisions:**
  - Should extensions receive an explicit collapse/expand command contract, a toggle-only contract, or both?
  - When the target container is inactive or displays a single view with a merged header, should collapse update the view's stored expansion state without revealing or hiding the whole container, or be limited to views with an independently collapsible header?
