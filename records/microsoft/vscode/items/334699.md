# Issue #334699 — [Bug] Markdown table headers are not rendering correctly in extension details

[https://github.com/microsoft/vscode/issues/334699](https://github.com/microsoft/vscode/issues/334699)

## Summary

Confirmed real defect on current main: table header alignment from Markdown (`style="text-align:center"` etc.) is stripped by the DOM sanitizer's attribute allowlist, and the extension README iframe's default styles then force `th { text-align: left }` for every header regardless of the source alignment — matching the reporter's screenshots exactly. A contributor has already diagnosed the same root cause in a comment and is working on a fix, so this stays open for that work to land.

## Change summary

Markdown table header cell alignment (center/right) is lost when rendered in the Extensions view's README/details panel.

## Best solution

Land the fix a contributor is already proposing: preserve alignment for headers, e.g. by allowing/augmenting the `style` (or a safe alignment-only) attribute in the sanitizer config used for extension README rendering, or by only defaulting `th { text-align: left }` when no explicit alignment is present — verified against all four alignment cases (default/left/center/right) as the commenter outlined.

## Evidence

- **sanitizer strips style:** src/vs/base/browser/domSanitize.ts `defaultAllowedAttrs` (lines 85-104) does not include `style`, and extensionEditor.ts's call to renderMarkdownDocument (src/vs/workbench/contrib/extensions/browser/extensionEditor.ts:767-775) only overrides `allowedLinkProtocols`, so any inline `text-align` alignment markdown-it/marked emit on `<th>`/`<td>` is dropped by DOMPurify.
- **hardcoded left alignment:** src/vs/workbench/contrib/markdown/browser/markdownDocumentRenderer.ts:72-73 sets `th { text-align: left; }` in DEFAULT_MARKDOWN_STYLES used for the README iframe, so once the alignment attribute is stripped every header renders left-aligned — matching the reporter's second screenshot.
- **contributor diagnosis:** Comment from pentaoa (2026-09-22) independently traces the same cause (`align` preserved by the parser but overridden by the default left-align CSS rule) and states intent to fix with coverage for all four alignment cases.
