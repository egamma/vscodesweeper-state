# Issue #174579 — Background Task With No Output Never Completes

[https://github.com/microsoft/vscode/issues/174579](https://github.com/microsoft/vscode/issues/174579)

## Summary

A real gap remains: a newly started, silent background task cannot automatically release its dependent debug launch through the current output-driven readiness mechanism. Keep this team-authored request open for a decision on explicit start-only semantics; no verified canonical or fixing commit was found.

## Change summary

Allow a silent, long-running background prelaunch task to unblock debugging without exiting or emitting problem-matcher output.

## Best solution

Provide an explicit way for task/debug configuration to treat process startup as sufficient for a prelaunch dependency, while preserving output-based readiness for existing watch tasks. Specify clearly that process startup does not guarantee that a server or emulator is ready to accept connections.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugTaskRunner.ts`, `src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts`, `src/vs/workbench/contrib/tasks/common/jsonSchema_v2.ts`, `src/vs/workbench/contrib/tasks/common/tasks.ts`
- **Validation:** Create a silent, long-running local server task and reference it as preLaunchTask. Under the agreed opt-in semantics, one debug launch must proceed without task output, task termination, or Debug Anyway. Verify that existing output-matched background tasks still wait for their endsPattern and that startup failure and cancellation do not launch debugging.
- **Behavior:**

  > A silent server or emulator runs indefinitely as a background prelaunch task, but its dependent debugger currently cannot proceed automatically because no readiness output arrives. Provide a deliberate way to express when such a prerequisite permits debugging without requiring process exit or fabricated output. Acceptance must cover a single automatic launch, continued operation of the background process, startup failure, and cancellation. Existing output-based watch-task readiness must remain unchanged.
- **Trace:**

  > DebugTaskRunner.runTask in src/vs/workbench/contrib/debug/browser/debugTaskRunner.ts waits on inactivePromise for a newly launched background task; it does not accept the task's ProcessStarted event as readiness. TerminalTaskSystem._executeInTerminal in src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts emits ProcessStarted from terminal.processReady but emits Inactive from WatchingProblemCollector's BackgroundProcessingEnds. WatchingProblemCollector in src/vs/workbench/contrib/tasks/common/problemCollectors.ts requires an output line to reach its end-pattern handling; activeOnStart only begins processing. The current task schema has no start-only policy, and manually starting the task first or choosing Debug Anyway is only a workaround. Preserve readiness matching for ordinary watch tasks and do not equate process creation with application-level readiness implicitly. https://github.com/microsoft/vscode/issues/70283 tracks background-dependency error propagation, not this silent-start requirement. The uncertainty is the public configuration contract for opting into startup-only readiness and whether that contract also applies to task dependencies.
- **Open decisions:**
  - Should the explicit startup-only policy belong to the task and apply to both preLaunchTask and dependsOn, or belong to the launch configuration and affect only debugging?
  - Is successful process startup sufficient for the supported contract, with service readiness left to the user, or must the feature also support a non-output readiness condition before debugging proceeds?
