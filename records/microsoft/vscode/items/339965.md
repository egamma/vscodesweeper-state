# Issue #339965 — Agents window: Create PR uses wrong GitHub account when Copilot and repository accounts differ

[https://github.com/microsoft/vscode/issues/339965](https://github.com/microsoft/vscode/issues/339965)

## Summary

Credible, well-diagnosed report: Agent Host's auth token store (`AgentHostAuthenticationService`) keeps a single token per (resource, scopes) key with no per-repository or per-account disambiguation, and the Create PR flow only throws an actionable auth-required error when no token exists at all — not when the stored token belongs to the wrong GitHub account for that specific repo. There's a real gap here, but closing it needs a product decision on account-selection UX, not just a bugfix.

## Change summary

The Agents window's built-in Create PR flow has no way to pick/sign in with a different GitHub account for repository API operations than the one used for Copilot, so a repo-inaccessible token surfaces as a raw 404 instead of a sign-in prompt.

## Best solution

Design a repository-scoped account picker for GitHub API operations in the Agent Host PR flow (separate from the Copilot auth resource), and have `AgentHostPullRequestOperationHandler._resolveContext` surface an actionable `AHP_AUTH_REQUIRED`-style prompt when the stored repo token lacks access, rather than letting the raw GitHub API 404 propagate.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentHostAuthenticationService.ts`, `src/vs/platform/agentHost/node/agentHostPullRequestOperationHandler.ts`, `src/vs/platform/agentHost/common/agent.ts`
- **Validation:** A test asserting that when the stored repo-resource token is valid but the API call returns 403/404 (insufficient repo access), the handler surfaces an `AHP_AUTH_REQUIRED`-style actionable error rather than propagating the raw GitHub API error, and that a per-repo account preference can be set and reused in `_resolveContext`.
- **Behavior:**

  > When the repository GitHub account differs from the signed-in Copilot account, Create PR should let the user select or sign in with the repository-appropriate account, remember that choice per repository/workspace, and show an actionable sign-in/account-selection prompt instead of a raw 404 when the stored token lacks access to the target repo. Existing single-account workflows (Copilot and repo account the same) must be unaffected.
- **Trace:**

  > `AgentHostAuthenticationService` (agentHostAuthenticationService.ts) stores exactly one token per `(resource, scopes)` key with no account axis. `AgentHostPullRequestOperationHandler._resolveContext` (agentHostPullRequestOperationHandler.ts:261-272) fetches that single token for the repo resource and only raises the actionable `AHP_AUTH_REQUIRED` protocol error when no token is present; a present-but-wrong-account token flows straight into the GitHub API call (`_searchPullRequests`/`findPullRequestByHeadBranch`), surfacing as an unhandled 404. The boundary: do not change the Copilot-resource auth path (lines ~640-647) or the push/SSH flow, which already works correctly as B; the gap is specifically in repo-resource token selection and error translation. Related: this is a brand-new (0 days old), uncommented report with no obvious duplicate found via GitHub search.
- **Open decisions:**
  - Should the account picker be a new UI surface in the Agents window Create PR flow, or should it delegate to the GitHub Pull Requests extension's existing account-switching UX?
  - Should the per-repository account preference be persisted at the workspace level, the repository level, or per-session, and where (settings vs. a dedicated credential store)?
  - Should a 403/404 on the repo API call always be translated into a sign-in prompt, or only after confirming the failure is auth-related (to avoid masking genuine not-found errors)?

## Evidence

- **single-token store:** src/vs/platform/agentHost/node/agentHostAuthenticationService.ts: `_tokens` is keyed only by `(resource, scopes)` via `_key()`; `getAuthToken`/`_getAuthToken` return the one stored token for a resource, with no concept of per-repository or per-account selection.
- **no disambiguation in PR flow:** src/vs/platform/agentHost/node/agentHostPullRequestOperationHandler.ts:261-272 calls `this._authenticationService.getAuthToken({ resource: repoResource.resource, scopes: repoResource.scopes_supported })` and only throws the actionable `AHP_AUTH_REQUIRED` error (line 266-271) when no token exists at all — a token that exists but can't access the private repo (wrong account) is used anyway, leading to the reported raw 404 from the GitHub API call site.
- **same pattern for Copilot resource:** Lines 640-647 of the same file show the Copilot-resource token lookup follows the identical single-token pattern, confirming there is no separate account-selection path anywhere in this handler.
