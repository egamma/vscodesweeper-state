# Issue #156423 — Smooth scrolling has limited upper speed and causes skipping to make up

[https://github.com/microsoft/vscode/issues/156423](https://github.com/microsoft/vscode/issues/156423)

## Summary

The reported jump remains present in current main's smooth-scrolling algorithm: rapidly accumulated wheel deltas can create a distant target, and the large-distance animation deliberately skips most of that distance at its one-third transition. The issue is already routed to the editor scrolling area and should remain open.

## Change summary

Fast physical-wheel input can outrun the editor's smooth-scroll animation, leaving it behind the accumulated target and producing a large catch-up jump.

## Best solution

Rework the shared smooth-scrolling behavior so repeated high-speed wheel input remains responsive without a discontinuous catch-up jump, while preserving ordinary low-speed easing and bounded animation work. The animation semantics need design and regression coverage before implementation because the shared primitive serves more than the editor.

## Plan brief

- **Likely files:** `src/vs/base/common/scrollable.ts`, `src/vs/base/test/common/scrollable.test.ts`, `src/vs/base/browser/ui/scrollbar/scrollableElement.ts`
- **Validation:** Add deterministic tests in src/vs/base/test/common/scrollable.test.ts that simulate successive high-speed targets and assert bounded target lag with no discontinuous viewport-scale position jump, while retaining the existing ordinary-distance easing cases.
- **Behavior:**

  > With editor smooth scrolling enabled, rapid physical-wheel input must remain visually responsive to the accumulated wheel position rather than falling progressively behind. Ending the gesture or reaching the file boundary must not produce a large catch-up jump. Normal-speed smooth scrolling must retain gradual easing, and disabling smooth scrolling must preserve immediate scrolling.
- **Trace:**

  > Mouse-wheel events enter ScrollableElement._onMouseWheel in src/vs/base/browser/ui/scrollbar/scrollableElement.ts, which adds each delta to Scrollable.getFutureScrollPosition() and requests another smooth target for classified physical wheels. Scrollable.setScrollPositionSmooth in src/vs/base/common/scrollable.ts combines the new target from the currently rendered state and begins another fixed-duration animation. Once the accumulated distance exceeds 2.5 viewport heights, SmoothScrollingOperation._initAnimation uses createComposed; its transition jumps from stop1 to stop2, omitting the middle distance. The existing 500-line test in src/vs/base/test/common/scrollable.test.ts demonstrates that discontinuity. The boundary is the shared smooth-scroll animation and physical-wheel path: immediate scrolling, low-speed easing, non-wheel programmatic scrolling, and unrelated terminal/xterm scrolling must not regress.
- **Open decisions:**
  - Should high-speed input shorten the animation duration, preserve wheel-derived velocity, or use another interpolation model to bound lag?
  - Should the existing long-distance middle skip remain for programmatic navigation while physical-wheel scrolling uses different behavior?
  - What maximum target lag or per-frame movement should define acceptable high-speed scrolling across shared Scrollable consumers?

## Evidence

- **current wheel path:** src/vs/base/browser/ui/scrollbar/scrollableElement.ts:_onMouseWheel accumulates every wheel delta against getFutureScrollPosition(), then calls setScrollPositionSmooth() for physical mouse wheels.
- **source reproduction:** src/vs/base/common/scrollable.ts:Scrollable.setScrollPositionSmooth restarts a 125 ms-class animation from the current rendered state whenever the pending target changes; SmoothScrollingOperation._initAnimation switches to a composed animation once the distance exceeds 2.5 viewports.
- **explicit skip:** The composed animation changes from stop1 to stop2 at completion 0.33, skipping the middle of a long distance. src/vs/base/test/common/scrollable.test.ts codifies this: the 500-line case advances from lines 29-70 at 25 ms to lines 482-523 at 50 ms.
- **confirmed scope:** The reporter confirmed at https://github.com/microsoft/vscode/issues/156423#issuecomment-1196778035 that the behavior occurs only with editor.smoothScrolling enabled and later confirmed it remained present at https://github.com/microsoft/vscode/issues/156423#issuecomment-1279951017.
- **canonical search:** The open https://github.com/microsoft/vscode/issues/28795 concerns accumulated Electron/X11 events across window focus on Linux, not the macOS editor animation behavior here. The closed https://github.com/microsoft/vscode/issues/187283 concerns terminal trackpad lag and does not absorb this editor issue.
