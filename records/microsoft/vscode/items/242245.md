# Issue #242245 — Newly installed extensions not activating on `workspaceContains` tigger

[https://github.com/microsoft/vscode/issues/242245](https://github.com/microsoft/vscode/issues/242245)

## Summary

The remote installation path remains defective on current main: it converts the exact `workspaceContains:.venv` directory check into a file search, so the newly installed extension is not activated until reload. This team-authored issue should remain open; no commit or merged PR explicitly referencing it was found.

## Change summary

A newly installed extension does not activate from an already-satisfied `workspaceContains:.venv` event in a remote workspace, although startup activation succeeds after reload.

## Best solution

Make dynamically added extensions evaluate exact `workspaceContains` paths consistently with startup activation in remote workspaces, while preserving the bounded-search behavior for genuine glob patterns. Add regression coverage for installing an extension while an exact matching directory already exists.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/services/extensions/common/workspaceContains.ts`
- **Validation:** Add a targeted extension-service test for a remote workspace where `.venv` already exists, dynamically add an extension declaring `workspaceContains:.venv`, and assert that its activation is requested without a reload; run it with `scripts/test.sh --grep "workspaceContains"`.
- **Behavior:**

  > When an extension declaring `workspaceContains:.venv` is installed into an already-open remote workspace containing that directory, it must activate without reloading the window. The same extension must remain inactive when `.venv` is absent. Existing startup activation, glob matching, and timeout behavior must remain unchanged.
- **Trace:**

  > `AbstractExtensionService._deltaExtensions` updates extension hosts and then invokes `_activateAddedExtensionIfNeeded` for each addition. In `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, that method sets `forceUsingSearch` for every remote authority even though its host supplies remote-capable `IFileService.exists`. `checkActivateWorkspaceContainsExtension` in `src/vs/workbench/services/extensions/common/workspaceContains.ts` consequently classifies the exact `.venv` path as a glob-search input, and `checkGlobFileExists` performs file search, which does not match the directory. The boundary is dynamically added extension activation: do not broaden ordinary workspace file-search semantics or alter startup/glob timeout behavior without an explicit decision.
- **Open decisions:**
  - Should the dynamic remote-install path use `IFileService.exists` for exact paths, or should the search path gain explicit directory matching semantics?
  - Does the selected behavior need to cover only exact directory paths such as `.venv`, or also directory-shaped glob patterns tracked by https://github.com/microsoft/vscode/issues/2739?

## Evidence

- **current source path:** In `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `_activateAddedExtensionIfNeeded` sets `forceUsingSearch` whenever `remoteAuthority` is present and passes it to `checkActivateWorkspaceContainsExtension` after the extension-host delta.
- **source-confirmed mismatch:** In `src/vs/workbench/services/extensions/common/workspaceContains.ts`, `forceUsingSearch` routes even the exact `.venv` path into `checkGlobFileExists`; that function constructs a file-search query rather than calling the supplied `IFileService.exists` path used for local exact matches.
- **directory-search behavior:** https://github.com/microsoft/vscode/issues/2739 records the established behavior that `workspaceContains` file search does not match directories. That explains why the forced-search installation path misses `.venv`, while the exact-path startup check can succeed after reload.
