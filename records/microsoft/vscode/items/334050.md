# Issue #334050 — GitHub username in Accounts menu does not update after renaming the account on github.com

[https://github.com/microsoft/vscode/issues/334050](https://github.com/microsoft/vscode/issues/334050)

## Summary

Confirmed in source: once a GitHub session's account label is cached in secret storage, it is never re-fetched, so a username change on github.com never propagates to the Accounts menu; this is a real gap, not a misreading of the report.

## Change summary

The Accounts menu keeps showing a stale GitHub username after the user renames their account on github.com.

## Best solution

Design a refresh path for the cached GitHub account label (e.g. periodic or on-demand re-validation via getUserInfo) in extensions/github-authentication/src/github.ts, balancing freshness against the extra API call on every session read.

## Plan brief

- **Likely files:** `extensions/github-authentication/src/github.ts`
- **Validation:** A test asserting that an existing persisted session's account.label reflects an updated getUserInfo() response after the chosen refresh mechanism runs, without a fresh sign-in.
- **Behavior:**

  > When a signed-in GitHub account's username changes on github.com, the Accounts menu in VS Code should reflect the new username within a reasonable time (e.g. on next session read/renewal), without requiring the user to manually sign out and back in. Existing sessions for other, unchanged accounts must not be disturbed.
- **Trace:**

  > readSessions() in extensions/github-authentication/src/github.ts only calls getUserInfo() to fill in account info when a stored session lacks one entirely (session.account is undefined); once a label is cached, it is never re-validated. checkForUpdates() and renewNow() do not touch account metadata either. A fix must not force a getUserInfo() call on every single readSessions() invocation without considering the added latency/API cost — that policy choice (always vs. periodic vs. TTL-based) is the open decision.
- **Open decisions:**
  - Should the account label be re-validated against GitHub on every session read, on a periodic/TTL basis, or only on explicit user action — trading freshness against the added API call cost on session load?

## Evidence

- **caching path:** readSessions() in extensions/github-authentication/src/github.ts (lines ~669-712) only calls this._githubServer.getUserInfo(...) to populate account.label when `!session.account` — i.e. only for legacy sessions missing cached account info. Once account.label is stored, it is reused verbatim on every subsequent read, with no re-validation against GitHub.
- **no periodic refresh:** checkForUpdates() (line 607) only diffs session IDs against the keychain to detect sign-in/sign-out from other windows; it never re-fetches or updates an existing session's account label. renewNow() (line 529) only handles token renewal, not account metadata refresh.
- **new sign-in path:** tokenToSession() (line 891) and sessionFor() (line 841) do call getUserInfo fresh when creating a brand-new session, so a genuinely new session would get the current username — the reporter's claim that a full sign-out/sign-in didn't help suggests either session reuse or a separate caching layer, which is worth asking about but doesn't change the core confirmed defect.
