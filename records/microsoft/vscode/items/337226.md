# Issue #337226 — serve-web: blank page when an edge proxy rewrites inline scripts (CSP nonce regression vs 1.130.0)

[https://github.com/microsoft/vscode/issues/337226](https://github.com/microsoft/vscode/issues/337226)

## Summary

Confirmed on current main: the CSP for the web workbench bootstrap uses only a per-request nonce (no hash fallback), so any edge proxy that rewrites/copies inline `<script>` tags (Cloudflare Rocket Loader and similar) blocks all bootstrap scripts and yields a blank page — a real regression from 1.130.0's wider hash-based CSP. A maintainer has already engaged (commit reference in comments), so this stays open rather than closing.

## Change summary

`code serve-web` shows a blank page when an edge/CDN proxy rewrites inline bootstrap `<script>` tags, because the per-request CSP nonce (introduced in commit 90c58123) has no fallback for rewritten scripts, unlike 1.130.0's broader `sha256` hash allowlist.

## Best solution

A maintainer should choose between (a) reintroducing sha256 hash fallbacks for the small set of static bootstrap scripts in workbench.html/workbench-dev.html — the codebase already has this exact pattern in `WebClientServer._getScriptCspHashes`, currently only used for callback.html — restoring 1.130.0-style compatibility, or (b) leaving the CSP nonce-only and instead adding a client-visible error/fallback UI when the bootstrap scripts are blocked, per the reporter's 'possible improvements'. Either requires product/security sign-off, not just an implementation pass.

## Plan brief

- **Likely files:** `src/vs/server/node/webClientServer.ts`, `src/vs/code/browser/workbench/workbench.html`, `src/vs/code/browser/workbench/workbench-dev.html`
- **Validation:** A `webClientServer` test asserting the emitted CSP `script-src` allows the actual bootstrap script content (via hash) even when the nonce attribute value differs from what's referenced in the CSP header — or, for the error-UX path, a workbench bootstrap test that renders a visible message when the AMD/`_VSCODE_FILE_ROOT` globals are absent at `workbench.js` load time.
- **Behavior:**

  > When `code serve-web` / `serve-web`'s workbench is loaded through an intermediary that rewrites or otherwise leaves inline `<script>` tag content intact but disturbs the nonce association (e.g. Cloudflare Rocket Loader), the bootstrap should either still execute (if hash-based fallback is chosen) or, at minimum, present a visible, actionable message instead of a silent blank page (if UX-only fix is chosen). Acceptance depends on which path a maintainer picks.
- **Trace:**

  > webClientServer.ts:441 generates a fresh `createScriptNonce()` per request and embeds it into workbench.html/workbench-dev.html's inline `<script nonce="...">` tags (webClientServer.ts:149 builds the matching CSP `script-src`). Before commit 90c581236a85cae04047ff72d7483989bbd59506, the CSP additionally listed 5 sha256 hashes for these scripts, tolerating proxies that garble the nonce but leave script bodies intact; that hash list was dropped in favor of nonce-only. A working, precedented hash-computation helper (`_getScriptCspHashes`, webClientServer.ts:503) already exists and is used for the unrelated `/callback` route. The boundary: do not touch the per-request nonce mechanism itself (it's the primary, correct defense) or the `/callback` CSP path; any fix should be additive (extra hashes) or purely client-side (bootstrap failure detection), not a revert to the static nonce.
- **Open decisions:**
  - Should CSP `script-src` for the web workbench bootstrap regain a sha256 hash allowlist (alongside the nonce) for the fixed, static inline scripts in workbench.html/workbench-dev.html, restoring 1.130.0-era proxy compatibility — or was removing that fallback in commit 90c58123 an intentional hardening the team wants to keep, in which case this scenario becomes officially unsupported?
  - If the CSP is not changed, should the client bootstrap (workbench.js) detect that earlier inline scripts never ran (e.g. missing `_VSCODE_FILE_ROOT`) and render a visible error instead of a blank page, and is that feasible given CSP blocks execution before any handler can run?
  - Should `serve-web`/remote-web docs be updated to document known incompatibility with edge script-rewriting features (Cloudflare Rocket Loader and similar) regardless of which code fix (if any) is chosen?

## Evidence

- **regression commit:** https://github.com/microsoft/vscode/commit/90c581236a85cae04047ff72d7483989bbd59506 replaced the static `'nonce-1nline-m4p'` CSP nonce and its multi-hash `script-src` with a random per-request nonce (`createScriptNonce()`), removing the hash-based fallback that let intermediaries which copy/rewrite the nonce out of the surrounding markup still validate.
- **current main CSP:** src/vs/server/node/webClientServer.ts:149 builds `script-src` with only `'nonce-${scriptNonce}'` plus two unrelated fixed hashes (webWorkerExtensionHostIframe and one other) — no hashes for the workbench.html/workbench-dev.html bootstrap scripts themselves, matching the reporter's CSP diff exactly.
- **existing hash-fallback pattern:** src/vs/server/node/webClientServer.ts:503 `_getScriptCspHashes()` already computes sha256 hashes of inline `<script>` bodies and is used for the /callback route's CSP (webClientServer.ts:532) but is not applied to the main workbench bootstrap route — a directly reusable, precedented mechanism for a fix.
- **static script bodies:** src/vs/code/browser/workbench/workbench.html now reads config via `document.getElementById(...)` instead of inlining `{{...}}` values directly into script text, so the bootstrap script bodies are identical across renders — hashing them for a CSP allowlist is technically straightforward.
- **maintainer engagement:** Comment from collaborator dmitrivMS links the impacting commit, indicating the team is already looking into root cause.
