# Issue #337226 — serve-web: blank page when an edge proxy rewrites inline scripts (CSP nonce regression vs 1.130.0)

[https://github.com/microsoft/vscode/issues/337226](https://github.com/microsoft/vscode/issues/337226)

## Summary

Well-diagnosed, source-confirmed report: the per-request CSP nonce (correct security posture, added since 1.130.0) is legitimately incompatible with edge proxies that rewrite inline `<script>` tags (e.g. Cloudflare Rocket Loader), causing a silent blank page with no actionable diagnostic — worth keeping open for a diagnostics/documentation improvement, not a security regression to revert.

## Change summary

code serve-web renders a blank page with no actionable error when an edge proxy (e.g. Cloudflare Rocket Loader) rewrites inline bootstrap `<script>` tags, since CSP now uses a per-request nonce instead of the old static one.

## Best solution

Keep the per-request nonce (it's the correct security posture, as the reporter agrees) but add a `securitypolicyviolation` listener in the web bootstrap so a blocked inline script surfaces an actionable message instead of a blank page, and note the known incompatibility with script-rewriting proxies (Rocket Loader etc.) in the serve-web/remote-web docs.

Acceptance: reproducing the blocked-inline-script scenario shows a rendered error state, and unaffected loads (no rewriting proxy) are unchanged.
- **Trace:**

  > createScriptNonce() (src/vs/server/node/webClientServer.ts:136) generates a fresh random nonce per request and createWorkbenchContentSecurityPolicy() (same file, lines 144-158) embeds it plus two sha256 hashes into script-src. When a proxy rewrites the six bootstrap `<script>` tags' `type` attribute (as Cloudflare Rocket Loader does), the browser's CSP blocks execution and the loader eventually throws the generic `Cannot determine URI for module id!` from src/vs/base/common/network.ts:386, with no CSP-specific context. No `securitypolicyviolation` event listener currently exists anywhere in the web bootstrap path. The boundary: do not weaken or revert the per-request nonce (that is a deliberate, correct hardening) — the fix is purely additive diagnostics/documentation, not a CSP relaxation. Where uncertainty starts: whether to add a client-side violation listener (and what UI it should render), whether doc-only is sufficient for v1, and whether any additional CSP allowance (e.g. broader hash coverage) is warranted for common rewriting proxies.
- **Open decisions:**
