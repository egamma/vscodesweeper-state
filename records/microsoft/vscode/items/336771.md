## Change summary

A user-overridden `path` for the built-in `PowerShell` profile name is reportedly ignored on Windows, causing Windows PowerShell 5.1 to launch instead of the user's custom-location PowerShell 7 install.

## Best solution

If reproduced on current Insiders, trace whether `ITerminalProfileService.availableProfiles` (browser side, consumed by `terminalProfileResolverService.ts`) is using a stale/cached profile list rather than re-running `detectAvailableProfiles`/`applyConfigProfilesToMap` (src/vs/platform/terminal/node/terminalProfiles.ts) after the config change — my read of that node-side merge logic shows the user's `path` array should already take precedence for the reserved `PowerShell` name.

## Evidence

- **source trace: config override wins:** src/vs/platform/terminal/node/terminalProfiles.ts `applyConfigProfilesToMap` (line 442-454) fully replaces the detected map entry for a name (e.g. `PowerShell`) with the user's config object via `profilesMap.set(profileName, value)` whenever the user value has a `path` or `source` key — it doesn't merge with the auto-detected `{source: ProfileSource.Pwsh}` entry.
- **source trace: path branch honored:** In `getValidatedProfile` (line 183-269), since the user's object has `path` and not `source`, `hasKey(profile, {source:true})` is false, so `originalPaths = profile.path` (the user's array) is used, not the built-in Pwsh auto-detection paths.
- **source trace: absolute-path fallback doesn't need PATH:** `validateProfilePaths` (line 456-498) checks the user's second array entry `E:\\PowerShell\\7\\pwsh.exe` via a direct `fsProvider.existsFile(normalize(actualPath))` (line 492) — this does not depend on PATH resolution at all, so even a stale process PATH shouldn't prevent it from being found.
- **reporter evidence:** Renderer log shows `creationOptions.shellPath` resolving to `WindowsPowerShell\v1.0\powershell.exe` on the reported shipped build (1.138.0), and reporter traced the same conceptual flow in the minified bundle — this is real evidence of a symptom, but the exact code path producing it (workbench-side profile caching vs. node-side detection) isn't fully pinned down here.
- **related issue:** Reporter cross-references https://github.com/microsoft/vscode/issues/300624 as a related but distinct downstream symptom (extension hardcoding a PowerShell path), not a duplicate of this report.
