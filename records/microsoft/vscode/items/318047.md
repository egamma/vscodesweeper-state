# Issue #318047 — Proposal: Workspace-Scoped Extension Sessions for VS Code

[https://github.com/microsoft/vscode/issues/318047](https://github.com/microsoft/vscode/issues/318047)

## Summary

A real extension-management gap remains: profiles and workspace-scoped enablement provide the underlying isolation manually, but VS Code does not offer the proposed default-deny session picker or a discoverable per-workspace allowlist flow. Route this to the extensions area for product design rather than closing it.

## Change summary

Make each workspace select and remember an extension session so only its explicitly chosen extensions load by default.

## Best solution

Build on existing workspace-associated Profiles and workspace-scoped extension enablement to offer an optional, discoverable extension-set workflow, while avoiding an unconditional startup prompt until maintainers decide the default experience and migration semantics.

- **Reason:** Reducing unnecessary extension activation advances the project's durable security and performance themes, although the interaction must preserve a simple, lightweight default experience.

## Plan brief

- **Likely files:** `src/vs/workbench/services/userDataProfile/browser/userDataProfileManagement.ts`, `src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditor.ts`, `src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts`, `src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsActions.ts`
- **Validation:** End the plan with workbench tests demonstrating that a workspace remembers its selected extension set across reloads, activates only that set, and preserves existing Profiles and manual Enable/Disable (Workspace) behavior.
- **Behavior:**

  > A user can choose a saved extension set for a folder or workspace and have that choice remembered. On subsequent opens, extensions outside the selected set remain unloaded while explicitly selected extensions are available. Existing users must retain their current extension behavior unless they opt into any new isolation model. Profiles, Workspace Trust, remote workspaces, and manual workspace enablement must continue to behave coherently.
- **Trace:**

  > Current per-workspace enablement is implemented by ExtensionEnablementService and surfaced through the bulk and per-extension actions in src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts and extensionsActions.ts. Workspace-to-profile association already exists in UserDataProfileManagementService, and the Profiles editor exposes associated folders and workspaces. The missing layer is a first-class selection lifecycle for named extension sets and a settled rule for whether it is opt-in or the default. https://github.com/microsoft/vscode/issues/40239 is related but narrower because it asks for configuration-file control; https://github.com/microsoft/vscode/issues/52116 owns the separate permissions and sandboxing discussion. Keep capability permissions and theme sandboxing outside this issue's implementation boundary.
- **Open decisions:**
  - Should extension-session isolation be opt-in, prompted only for new workspaces, or become the default behavior for every workspace?
  - Should a session be an extension-only construct or an existing Profile whose settings, keybindings, and other resources necessarily switch with its extensions?
  - When an extension is installed after a session is selected, should it remain inactive until explicitly added, or inherit the user's current global enablement state?

## Evidence

- **existing workspace controls:** src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts registers `workbench.extensions.action.enableAllWorkspace` and `workbench.extensions.action.disableAllWorkspace`, while src/vs/workbench/contrib/extensions/browser/extensionsActions.ts exposes per-extension Enable/Disable (Workspace) actions. These are manual controls rather than remembered named sessions selected when a workspace opens.
- **existing profile association:** src/vs/workbench/services/userDataProfile/browser/userDataProfileManagement.ts resolves a profile associated with the current workspace and persists profile switches through `setProfileForWorkspace`; src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditor.ts exposes the profile's associated folders and workspaces. This supplies much of the storage model but not the proposed default-deny picker and extension-only session UX.
- **related canonical search:** https://github.com/microsoft/vscode/issues/40239 is older and open, but it specifically tracks declaring workspace extension enablement in a configuration file. It does not fully own this issue's broader reporter-observable request for named sessions, an opening prompt, remembered selection, and default-unloaded extensions, so the stronger re-review duplicate bar is not met.
- **separate permissions work:** The follow-up suggestion about capability permissions and sandboxing overlaps the older open https://github.com/microsoft/vscode/issues/52116 and should remain separate from the workspace-session proposal.
