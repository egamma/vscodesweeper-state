# Issue #127015 — Create command to resolve one CompletionItem

[https://github.com/microsoft/vscode/issues/127015](https://github.com/microsoft/vscode/issues/127015)

## Summary

The requested API capability remains missing: itemResolveCount resolves an initial batch, not an item selected later. Keep this accepted Backlog request open; exposing deferred resolution requires a public identity and lifetime contract.

## Change summary

Allow extensions to resolve an individual previously returned completion item on demand, avoiding eager resolution of unrelated items.

## Best solution

Provide a supported deferred-resolution API that preserves the originating provider and item identity without resolving the entire completion list. Settle result lifetime and cross-process identity semantics first, and distinguish command result ordering from the suggest widget's contextual ranking.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostApiCommands.ts`, `src/vs/editor/contrib/suggest/browser/suggest.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/common/extHostTypeConverters.ts`, `src/vs/workbench/api/test/browser/extHostApiCommands.test.ts`
- **Validation:** Extend src/vs/workbench/api/test/browser/extHostApiCommands.test.ts with a provider recording resolve calls: obtain an unresolved list, select a non-prefix item, resolve it later, and assert that only that original item reaches its originating provider and its details are returned. Cover the agreed lifetime/expiration contract and preserve existing itemResolveCount behavior.
- **Behavior:**

  > An extension can obtain completion candidates without eagerly resolving them and later request details for one chosen item. Selecting an item far down the returned list must not require resolving preceding items or invoking the completion provider again. Acceptance checks must demonstrate correct provider attribution, no unrelated resolutions, and defined behavior when the original results are no longer valid. Any ordering guarantee must state whether it describes command results or the editor's context-dependent display order.
- **Trace:**

  > vscode.executeCompletionItemProvider is registered in src/vs/workbench/api/common/extHostApiCommands.ts and delegates to _executeCompletionItemProvider in src/vs/editor/contrib/suggest/browser/suggest.ts. That command resolves a prefix before returning and disposes provider results shortly afterward. MainThreadLanguageFeatures uses a provider handle and internal item ID for resolution; CompletionsAdapter retains the original provider items only until list release, while CompletionItem.to does not expose that identity. This establishes the API gap, but not a safe public lifecycle design. Preserve existing batch-resolution behavior and ordinary suggest-widget resolution. The earlier discussion at https://github.com/microsoft/vscode/issues/44846 identifies the lifecycle concern; it is closed, not a canonical for the remaining work.
- **Open decisions:**
  - Must deferred resolution support completion items serialized across a Live Share or language-server boundary, or only the original returned objects within one extension host?
  - What public lifetime contract applies to returned completion results: explicit session release, automatic expiration, or validity tied to document state, and what should callers observe after invalidation?
  - Is selected-item resolution sufficient, or should this API also guarantee ordering corresponding to the editor's displayed completion list?
