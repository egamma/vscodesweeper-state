# Issue #148041 — Detect when our `vscode://` UriHandler isn't registered on the OS and inform the user

[https://github.com/microsoft/vscode/issues/148041](https://github.com/microsoft/vscode/issues/148041)

## Summary

Keep open: authentication fallbacks mitigate failed redirects, but current source still lacks a general OS URI-handler availability check or actionable registration guidance. This team-authored item has no verified complete fix or eligible duplicate.

## Change summary

Detect unavailable OS registration for VS Code's URI scheme and inform users or let extensions select an alternative flow.

## Best solution

Establish a reliable, platform-aware URI-handling capability contract and use it to provide actionable guidance or avoid unusable callback flows. Coordinate the extension-facing portion with https://github.com/microsoft/vscode/issues/236405 without closing this older report into it.

## Plan brief

- **Likely files:** `src/vs/platform/url/electron-main/electronUrlListener.ts`, `src/vs/platform/url/common/url.ts`, `src/vscode-dts/vscode.d.ts`, `extensions/github-authentication/src/githubServer.ts`, `extensions/github-authentication/src/flows.ts`
- **Validation:** The plan should define executable capability tests for available, unavailable, and indeterminate registration, then manually check Linux archive and Windows portable installations with and without a working handler: unavailable callbacks should produce the agreed guidance or alternative flow, while registered installations retain working callbacks. These checks were not run during this read-only review.
- **Behavior:**

  > An installation whose OS cannot deliver the VS Code callback URI should not leave users to diagnose an unexplained authentication dead end. Users should receive actionable guidance, or extensions should have enough capability information to choose an appropriate alternative. Acceptance must cover missing registration and a working registered installation, without presenting indeterminate registration as a definite failure. Existing successful authentication and fallback paths must remain usable.
- **Trace:**

  > ElectronURLListener in src/vs/platform/url/electron-main/electronUrlListener.ts attempts registration on non-portable Windows and relies on package-installed desktop integration on Linux; it does not expose availability. IURLService in src/vs/platform/url/common/url.ts concerns dispatch rather than OS capability, and window.registerUriHandler in src/vscode-dts/vscode.d.ts returns only a Disposable. GitHubServer.login and the flows in extensions/github-authentication/src/flows.ts already provide alternative authentication mechanisms, but those are not a general registration detector. https://github.com/microsoft/vscode/issues/236405 tracks the related extension capability contract, and https://github.com/microsoft/vscode/pull/287063 provides partial portable-mode improvements. The uncertainty begins at how reliably each platform can establish callback availability and what that result should mean to users and extensions. Preserve portable-mode isolation, working handlers, and existing fallback behavior; automatic reassignment of OS protocol ownership is not an established requirement.
- **Open decisions:**
  - Should the initial capability be exposed to extensions, presented as core user guidance, or both?
  - Should capability describe OS scheme registration alone or whether a callback can reach the current VS Code instance, including alternate user-data directories?
  - What should users and extensions observe when registration availability cannot be determined reliably?

## Evidence

- **Current registration path:** src/vs/platform/url/electron-main/electronUrlListener.ts registers the scheme through app.setAsDefaultProtocolClient only on non-portable Windows, ignores its return value, and contains no registration-availability check or user notification. Linux still relies on a packaged code-url-handler.desktop shortcut.
- **Existing capability does not cover the request:** src/vs/platform/url/common/url.ts exposes URL creation, dispatch, and handler registration, not OS registration status. src/vscode-dts/vscode.d.ts declares window.registerUriHandler(handler): Disposable; it does not report whether OS callbacks can reach the application.
- **Fallbacks are mitigation:** extensions/github-authentication/src/flows.ts orders LocalServerFlow before UrlHandlerFlow, while githubServer.ts selects flows and offers alternatives after cancellation or failure. These mechanisms do not establish OS registration availability. https://github.com/microsoft/vscode/issues/147104#issuecomment-1109108734 explicitly describes its fallback as a workaround for this issue; https://github.com/microsoft/vscode/issues/148717#issuecomment-1118929847 likewise distinguishes the fallback shipped in 1.67 from this remaining work.
