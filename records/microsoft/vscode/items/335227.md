# Issue #335227 — When using custom endpoints, virtual tools cause the model to fail to accurately discover the tools

[https://github.com/microsoft/vscode/issues/335227](https://github.com/microsoft/vscode/issues/335227)

## Summary

The reported failure remains relevant on current main for custom model identifiers and OpenRouter models that do not pass the tool-search capability heuristic: large MCP toolsets still fall back to generated virtual groups, whose clustering and descriptions can hide the required tool. Route this to the MCP and language-model management owners rather than closing it.

## Change summary

Custom-endpoint models can fail to discover tools in large MCP toolsets because generated virtual-tool categories are inaccurate and tool search cannot be explicitly enabled.

## Best solution

Allow Responses-compatible custom endpoints to declare tool-search support explicitly, while retaining a reliable discovery path for OpenRouter or other endpoints that cannot use that protocol. The broader virtual-grouping quality problem should remain covered here even if the explicit custom-endpoint capability work is consolidated with https://github.com/microsoft/vscode/issues/334424.

## Plan brief

- **Validation:** Add deterministic unit coverage showing that an explicitly tool-search-capable custom Responses endpoint bypasses virtual grouping, explicit false preserves grouping, and a large MCP toolset on an unsupported endpoint retains discoverable issue-management capability.
- **Behavior:**

  > A custom endpoint that supports client-executed Responses API tool search can opt into it without impersonating another model family. With a large MCP toolset, the selected model can discover and call a relevant tool such as list_issues rather than losing it behind an unrelated virtual category. Endpoints that explicitly disable or cannot support tool search continue using a fallback that preserves discoverability, and existing known-model behavior remains unchanged.
- **Trace:**

  > DefaultToolCallingLoop.getAvailableTools in extensions/copilot/src/extension/prompt/node/defaultIntentRequestHandler.ts returns all tools only when endpoint.supportsToolSearch is true; otherwise it delegates to ToolGrouping. ChatEndpoint derives that capability from capabilities.supports.tool_search or modelSupportsToolSearch, but CustomEndpointBYOKModelProvider and resolveModelInfo expose no fine-grained configured value, so arbitrary custom ids and provider-prefixed OpenRouter families fall through to virtual grouping. VirtualToolGrouper clusters MCP tools and virtualToolSummarizer.tsx generates category names and descriptions through a utility model without a deterministic capability-coverage check. Keep known-model capability detection and ordinary small-toolset behavior unchanged. https://github.com/microsoft/vscode/issues/334424 covers the narrower explicit custom Responses capability and should inform or absorb that portion of the design.
- **Open decisions:**
  - Should the public contract be a tri-state per-model toolSearch capability in chatLanguageModels.json, or should compatible custom endpoints be detected automatically?
  - Should this issue also require improved virtual-group discoverability for OpenRouter and other endpoints that cannot use Responses API tool search, or should that behavior be tracked separately?

## Evidence

- **current source path:** extensions/copilot/src/extension/prompt/node/defaultIntentRequestHandler.ts bypasses ToolGrouping only when endpoint.supportsToolSearch is true; otherwise it calls ToolGrouping.compute for the complete tool list.
- **capability gap:** extensions/copilot/src/extension/byok/vscode-node/customEndpointProvider.ts has no per-model tool-search field, while extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts derives supportsToolSearch from metadata or a model-family heuristic. CustomEndpoint model family defaults to the configured model id in extensions/copilot/src/extension/byok/common/byokProvider.ts, so renamed models cannot reliably activate tool search.
- **grouping behavior:** extensions/copilot/src/extension/tools/common/virtualTools/virtualToolGrouper.ts clusters extension/MCP tools using embeddings and then asks copilot-utility-small to generate group names and summaries. extensions/copilot/src/extension/tools/common/virtualTools/virtualToolSummarizer.tsx does not validate that each generated category exposes every important capability represented by its member tools, matching the reported list_issues misclassification.
- **partial existing control:** The existing github.copilot.chat.virtualTools.threshold setting can disable virtual tools with value 0, but it does not provide the requested per-endpoint tool-search capability and does not by itself solve transport limits for very large toolsets.
- **related narrower issue:** https://github.com/microsoft/vscode/issues/334424 is older and open, and specifically requests an explicit Responses API tool-search flag for custom endpoints. It does not fully absorb this report's broader OpenRouter and inaccurate virtual-grouping symptoms, so the stronger re-review duplicate bar is not met.
