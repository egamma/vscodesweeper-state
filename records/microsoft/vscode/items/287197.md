# Issue #287197 — Agent: Allow MCP servers to extend default code search tools

[https://github.com/microsoft/vscode/issues/287197](https://github.com/microsoft/vscode/issues/287197)

## Summary

Keep this accepted, team-authored request open: MCP tools can participate in agent searches, but the inspected code does not provide the requested metadata-based replacement contract or index-readiness gating. No verified fixing commit or qualifying duplicate was found.

## Change summary

Allow indexed search providers exposed through MCP to substitute for built-in lexical and semantic code-search tools when their index is available.

## Best solution

Define an interoperable search-capability and readiness contract between MCP tool registration and Copilot tool selection, preserving built-in search when no suitable provider is available. Settle substitution scope and provider-selection behavior before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts`, `extensions/copilot/src/extension/tools/vscode-node/toolsService.ts`, `extensions/copilot/src/extension/tools/node/codebaseTool.tsx`, `extensions/copilot/src/extension/tools/node/findTextInFilesTool.tsx`
- **Validation:** Use a controllable MCP search server to exercise index-ready, index-unavailable, and disconnected states. Verify the agreed tool-selection behavior for lexical and semantic searches, restoration of built-in search when the provider becomes unavailable, and unchanged behavior without a replacement provider.
- **Behavior:**

  > An agent can use an existing indexed search provider exposed through MCP as a substitute for the relevant built-in code-search capability. The substitute is eligible only while its backing service and index are available. Acceptance must cover lexical and semantic searches, readiness transitions, and normal built-in search when no eligible substitute exists. Whether substitution removes built-in tools from the model's choices remains a maintainer decision.
- **Trace:**

  > McpLanguageModelToolContribution._syncTools in src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts maps MCP definitions into language-model tool registrations with a generic mcp tag. Copilot's ToolsService.getEnabledTools and getToolOverridesForEndpoint in extensions/copilot/src/extension/tools/vscode-node/toolsService.ts select enabled tools and apply internal model-specific overrides. CodebaseTool uses IWorkspaceChunkSearchService, while FindTextInFilesTool uses ISearchService; the inspected paths do not connect MCP metadata to search substitution. The proposed AI text-search provider API targets scheme-based Search View results rather than this contract. Preserve existing tool enablement, approval behavior, and search behavior for users without a participating provider. https://github.com/microsoft/vscode/issues/292972 provides modernization context, while https://github.com/microsoft/vscode/issues/280530 concerns metadata exposure; neither settles the requested behavior.
- **Open decisions:**
  - Should an eligible provider replace built-in search tools in the model's available tool set, or remain alongside them with a preference signal, and can it replace lexical and semantic search independently?
  - What externally observable capability and readiness contract should an MCP provider publish to become eligible for substitution?
  - When multiple eligible providers cover the same workspace, should selection be user-controlled or automatic?
