# Issue #142973 — Language Detection crashes language server due to misdetection.

[https://github.com/microsoft/vscode/issues/142973](https://github.com/microsoft/vscode/issues/142973)

## Summary

Keep open: extensionless files with unrecognized shebangs still enter content-based language detection, and existing controls do not selectively protect those files while preserving untitled detection. The maintainer proposed addressing this distinction; no verified canonical owns the remaining request.

## Change summary

Prevent automatic language misclassification of extensionless scripts with unrecognized shebangs without disabling useful detection in untitled editors.

## Best solution

Establish a policy for automatic detection of extensionless files with unrecognized shebangs in the text-file model, preserving registered first-line recognition and untitled-editor detection. Decide whether this protection is default behavior or an opt-in control before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/services/textfile/common/textFileEditorModel.ts`, `src/vs/workbench/common/editor/textEditorModel.ts`, `src/vs/workbench/browser/workbench.contribution.ts`, `src/vs/workbench/services/textfile/test/browser/textFileEditorModel.test.ts`
- **Validation:** Add focused text-file model tests for the chosen policy: an extensionless file beginning with an unrecognized shebang retains plaintext under protection even when a fake detector would return JSON; recognized firstLine contributions still select their language; ordinary extensionless files retain the agreed behavior. Verify separately that untitled editors still auto-detect. Run the relevant text-file and untitled model unit suites using scripts/test.sh; no tests were executed during this read-only review.
- **Behavior:**

  > An extensionless script with a first-line shebang identifying an unregistered interpreter should be protectable from automatic assignment to an unrelated language. This must not require disabling automatic detection in untitled scratchpads. Registered first-line language recognition must continue working, and explicit user language choices must remain authoritative. Acceptance checks should distinguish unknown shebangs, recognized shebangs, ordinary extensionless text, and untitled editors under the policy selected by the maintainer.
- **Trace:**

  > TextFileEditorModel.autoDetectLanguage in src/vs/workbench/services/textfile/common/textFileEditorModel.ts waits for extension registration and limits automatic detection to extensionless plaintext files on the default URI scheme, but has no unknown-shebang exclusion. BaseTextEditorModel.createTextEditorModel performs registered firstLine recognition first, while doAutoDetectLanguage subsequently applies content-detection results. LanguageDetectionWorkerClient.detectLanguage falls back to worker inference after URI recognition; the worker samples the content without an unknown-shebang stop condition. The existing workbench.editor.languageDetection boolean is language-scoped rather than file-versus-untitled scoped. Preserve registered language contributions, explicit language choices, and untitled detection; do not expand this into changes to Go language-server robustness or the classifier's training. The maintainer's proposed direction is recorded at https://github.com/microsoft/vscode/issues/142973#issuecomment-1140280583. The uncertainty is product policy for unknown shebangs, not whether the current source permits content inference; the historical JSON prediction and gopls crash were not executed or independently confirmed on current main.
- **Open decisions:**
  - Should extensionless files with unrecognized first-line shebangs remain plaintext by default, or should users opt into that protection?
  - Should the control protect only unknown-shebang scripts, or allow automatic detection to be disabled for all extensionless saved files while retaining it for untitled editors?
