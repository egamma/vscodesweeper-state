# Issue #166472 — [Accessibility] Add an option to allow Alt+F5 to jump to the next --word-diff instead of the whole line

[https://github.com/microsoft/vscode/issues/166472](https://github.com/microsoft/vscode/issues/166472)

## Summary

Keep open: current navigation still targets line-level changes, not successive changed words within a line. This accepted accessibility request has maintainer support, and the related closed report explicitly identifies this issue as its canonical.

## Change summary

Provide optional word-level change navigation with Alt+F5 so screen reader users can focus successive modified locations instead of reading entire changed lines.

## Best solution

Provide opt-in navigation among individual changed ranges, preserving existing line-level navigation by default. Plan the treatment of deletions and spoken change descriptions with the accessibility and diff-editor owners before implementation.

## Plan brief

- **Likely files:** `src/vs/editor/browser/widget/diffEditor/diffEditorWidget.ts`, `src/vs/editor/browser/widget/diffEditor/components/accessibleDiffViewer.ts`, `src/vs/editor/common/config/editorConfigurationSchema.ts`, `src/vs/workbench/contrib/scm/browser/quickDiffWidget.ts`, `src/vs/workbench/browser/parts/editor/diffEditorCommandsService.ts`
- **Validation:** After the product choices are settled, compare two versions of a line containing three separated changed words. With word-level navigation enabled, repeatedly press Alt+F5 and Shift+Alt+F5 and verify successive changed-word landing positions and wraparound; repeat with the option disabled to confirm existing line-level behavior. Include insertion-only and deletion-only ranges, and verify focused text and change descriptions with NVDA on Windows.
- **Behavior:**

  > Screen reader users currently navigate to an entire changed line and must inspect unchanged text to locate each modification. The requested opt-in behavior lets repeated Alt+F5 presses visit successive changed words within that line and cycle through the changes; reverse navigation should visit them in reverse order. Existing line-level behavior remains available. Acceptance must cover three separated changes on one line, wraparound, insertions, deletions, and screen reader output that identifies the focused change without requiring a full-line comparison.
- **Trace:**

  > DiffEditorCommandsService.navigateInDiffEditor delegates to DiffEditorWidget.goToDiff, which chooses line-range mappings using the cursor line and calls _goTo to land at column 1. The separate SCM Alt+F5 path is GotoNextChangeAction in quickDiffWidget.ts; its setPositionAndSelection explicitly selects a full line for screen reader users. Detailed mappings already expose innerChanges, but these navigation paths do not traverse them. AccessibleDiffViewer has group/line navigation and likewise reveals column-1 positions; diffEditor.experimental.useTrueInlineView only changes rendering. Preserve default line navigation and existing accessibility signals, and assess both comparison-editor and SCM paths rather than assuming they share one implementation. https://github.com/microsoft/vscode/issues/184229#issuecomment-1642241916 establishes this issue as the canonical word-navigation request. The uncertainty is user-visible behavior for deleted ranges and the additional spoken or hover description requested in https://github.com/microsoft/vscode/issues/166472#issuecomment-1912724549.
- **Open decisions:**
  - For a deleted word with no modified-side text, should navigation focus the original-side deleted range or remain on the modified side and announce the deletion at its anchor?
  - Should the initial feature include insertion/deletion/modification descriptions in the hover and screen reader output, or should that additional presentation remain a follow-up?
