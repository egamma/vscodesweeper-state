# Issue #166472 — [Accessibility] Add an option to allow Alt+F5 to jump to the next --word-diff instead of the whole line

[https://github.com/microsoft/vscode/issues/166472](https://github.com/microsoft/vscode/issues/166472)

## Summary

Keep open: Alt+F5 still navigates between line-level diff hunks rather than individual changed words. This accepted accessibility request has maintainer support, and the existing inline-word rendering setting does not provide the requested navigation.

## Change summary

Provide optional word-level diff navigation so repeated Alt+F5 presses focus each changed word instead of the start of a changed line.

## Best solution

Provide opt-in navigation through individual changed spans while preserving existing hunk navigation by default. Plan accessible identification of insertions, deletions, and modifications alongside that navigation, as requested in the discussion.

Cover insertion-only and deletion-only ranges and manually verify the announced change information with a screen reader in inline and side-by-side views.
- **Behavior:**

  > Screen reader users should be able to opt into navigating individual word changes instead of reading entire changed lines. For three separated changed words on one line, repeated Alt+F5 presses should reach each word in order and cycle back; reverse navigation should traverse the same targets backward. Existing hunk-level navigation remains available and unchanged by default. Acceptance includes usable insertion and deletion targets and accessible identification of the change kind, with the exact presentation agreed during planning.
- **Trace:**

  > Alt+F5 is registered as workbench.action.compareEditor.nextChange in src/vs/workbench/browser/parts/editor/diffEditorCommands.ts and reaches DiffEditorWidget.goToDiff through DiffEditorCommandsService.navigateInDiffEditor. In src/vs/editor/browser/widget/diffEditor/diffEditorWidget.ts:724–747, the target is selected using modified start line numbers and revealed at column 1, so multiple changed spans on one line cannot be visited separately. DetailedLineRangeMapping.innerChanges in src/vs/editor/common/diff/rangeMapping.ts already exposes character-level range mappings, which may be absent; these are not necessarily the word-level targets the reporter expects. diffEditor.experimental.useTrueInlineView changes rendering only, and AccessibleDiffViewer remains group/line oriented. Preserve default hunk navigation, existing diff computation, and existing F7 review behavior unless the maintainer explicitly expands the scope. The discussion at https://github.com/microsoft/vscode/issues/166472 establishes the cycling goal and requests change-kind information on hover; https://github.com/microsoft/vscode/issues/184229#issuecomment-1642241916 directs the related navigation work here. Planning uncertainty begins with navigation granularity and how deletion-only changes are focused and described; no implementation or runtime check was performed.
- **Open decisions:**
  - Should the opt-in target each computed inner changed span, each changed word within those spans, or expose both word and character granularity?
  - For deletion-only changes, should navigation focus the corresponding modified-side anchor or move to the deleted text in the original editor?
  - Should change-kind information appear automatically on navigation, or only when the user explicitly opens the hover, and what text should be announced?
