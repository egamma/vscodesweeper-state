# Issue #257923 — Managed hovers leak `hoverwidget` disposables

[https://github.com/microsoft/vscode/issues/257923](https://github.com/microsoft/vscode/issues/257923)

## Summary

Keep open: the newer hover API now exposes a hide callback, but the deprecated managed-content API still lacks that lifecycle hook. No verified fix referencing this team-authored issue establishes that its original cleanup concern is complete.

## Change summary

Ensure dynamically created managed-hover content can release its resources when the hover is dismissed.

## Best solution

Use the newer hover API's onDidHide lifecycle for content cleanup where callers can migrate, and explicitly resolve the remaining deprecated managed-hover lifecycle concern before retiring this debt item.

## Evidence

- **Maintainer direction:** https://github.com/microsoft/vscode/issues/257923#issuecomment-3188021819 explains that the managed API is deprecated and that disposal is not necessarily a direct dispose call; https://github.com/microsoft/vscode/issues/257923#issuecomment-3602430397 proposes supporting the lifecycle in newer hovers.
- **New API already supports cleanup:** src/vs/base/browser/ui/hover/hover.ts defines IHoverOptions.onDidHide, documented to fire once per shown hover. HoverService._showHover in src/vs/platform/hover/browser/hoverService.ts registers that callback in the hover's DisposableStore. src/vs/platform/hover/test/browser/hoverService.test.ts contains tests for disposal callbacks and delayed hovers that never show; these were inspected, not executed.
- **Legacy API remains distinct:** src/vs/base/browser/ui/hover/hover.ts still defines IManagedHoverTooltipHTMLElement without a disposal callback, and IManagedHoverOptions includes onDidShow but not onDidHide. ManagedHoverWidget in src/vs/platform/hover/browser/updatableHoverWidget.ts forwards onDidShow and cancels pending content computation through onDidHide; this does not establish a general content-disposal contract.
- **Original path has changed:** HoverService.setupManagedHover now resides in src/vs/platform/hover/browser/hoverService.ts. Its hideHover helper clears hoverWidget only after calling dispose when disposeWidget is true; mouseleave calls hideHover(false, ...). The originally reported reference-clearing path is therefore not unchanged, but that alone does not prove the requested content lifecycle is complete.

It requests a different observable capability and fails the older-canonical requirement for this re-reviewed item.
