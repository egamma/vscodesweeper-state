# Issue #338895 — MCP tools silently dropped when tool IDs collide after trancation to 64 chars

[https://github.com/microsoft/vscode/issues/338895](https://github.com/microsoft/vscode/issues/338895)

## Summary

Confirmed on main via source: McpTool truncates prefix+name to 64 chars (mcpServer.ts:1333) without collision handling, and _syncTools' deferred registration loop (mcpLanguageModelToolContribution.ts) has no per-tool error isolation, so one duplicate-ID throw aborts the rest of the batch — matching the reporter's exact symptom.

## Change summary

MCP tool IDs are truncated to 64 chars without uniqueness handling; a resulting ID collision throws inside the deferred registration loop and silently drops every subsequent tool in that batch.

## Best solution

Disambiguate truncated tool IDs (e.g. replace the tail with a short hash of the full name when prefix+name exceeds 64 chars) in mcpServer.ts, and make the registration loop in mcpLanguageModelToolContribution.ts resilient per-tool (try/catch around each registerTool call) so one bad ID doesn't drop unrelated tools.

- **Behavior:**

  > When an MCP server exposes multiple tools whose prefixed names collide after the 64-char ID truncation, all of them should still appear in the tool picker with distinct, stable IDs — not just the tools before the first collision. A tool registration failure for one tool must not prevent other, unrelated tools from registering in the same sync pass. Acceptance: two colliding-name tools get distinct McpTool.id values, and a forced registration error for one tool does not stop siblings from being registered.
- **Trace:**

  > Root cause 1: src/vs/workbench/contrib/mcp/common/mcpServer.ts:1333 builds `this.id` by slicing `idPrefix + name` to `McpToolName.MaxLength` (64, defined in mcpTypes.ts:1195) with no collision handling, so distinct tool names that share a 64-char prefix collapse to the same id. Root cause 2: src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts `_syncTools` (~line 107) processes `server.tools.read(reader)` in a single pass; when a later tool shares an id with one already added to the in-pass `tools` map, it hits the `existing` branch (line 162) and calls `registerTool` immediately, while the earlier tool's registration was only deferred into `toRegister` (line 173) and executed later in the unguarded `for (const fn of toRegister) fn();` loop (lines 186-188) — that later call throws via languageModelToolsService.ts:311 ('already registered'), aborting the loop and dropping every tool queued after it. Boundary: do not change the general autorun/registration architecture, tool discovery, or the 64-char cap itself (that limit is correct per model provider constraints) — only the id-disambiguation logic and the loop's per-item error isolation.

## Evidence

- **id truncation, no dedup:** src/vs/workbench/contrib/mcp/common/mcpServer.ts:1333 — `this.id = (idPrefix + _definition.name).replaceAll('.', '_').slice(0, McpToolName.MaxLength)` (MaxLength=64 in mcpTypes.ts:1195); two different tool names sharing the first 64 chars after prefixing collide with no disambiguation.
- **unguarded registration throw:** src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts:311 throws `Tool "${id}" is already registered.` when a duplicate ID is registered.
- **loop abort on throw:** src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts:186-188 runs `for (const fn of toRegister) fn();` with no try/catch; because a colliding tool with the same id overwrites the map entry in-place and registers immediately (lines 162-175), the deferred fn() for the earlier tool throws when it runs later, aborting the remaining registrations in that autorun pass — matching the reported 'tools after it are silently dropped' behavior.
