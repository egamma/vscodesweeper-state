# Issue #171837 — Add prelaunch Command as well for launch configuration

[https://github.com/microsoft/vscode/issues/171837](https://github.com/microsoft/vscode/issues/171837)

## Summary

Keep this accepted Backlog request open: current launch configuration supports task references and command-variable interpolation, but neither fully provides the requested standalone pre-launch execution with configuration-specific inputs. The older parameter-sharing issue covers the repeated-IP problem, not the additional requirement to avoid a separate task definition.

## Change summary

Allow launch configurations to execute a pre-launch command directly and supply configuration-specific inputs without defining a separate task in tasks.json.

## Best solution

Define a supported pre-launch execution contract that can consume launch-specific values without duplicate prompts or intermediary task definitions. Coordinate parameter-sharing semantics with https://github.com/microsoft/vscode/issues/27157 while deciding whether this request exposes VS Code commands, inline shell/process tasks, or both.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/common/debug.ts`, `src/vs/workbench/contrib/debug/browser/debugAdapterManager.ts`, `src/vs/workbench/contrib/debug/browser/debugService.ts`, `src/vs/workbench/contrib/debug/browser/debugTaskRunner.ts`, `src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts`, `src/vs/workbench/services/configurationResolver/browser/baseConfigurationResolverService.ts`
- **Validation:** In an isolated test workspace, create two launch configurations with different target-IP values and no tasks.json. For the execution form selected by the maintainer, verify that the pre-launch operation receives the selected configuration's IP, completes before debugger launch, and does not prompt again for that value. Exercise failure and cancellation according to the agreed contract, and verify existing named-task preLaunchTask configurations retain their behavior.
- **Behavior:**

  > The reporter wants a launch configuration to invoke a pre-launch operation without requiring a separate tasks.json definition. A target value such as a remote IP address should be usable by both the operation and debugger without repeated entry. The thread additionally proposes an inline shell-task object, so the supported execution form remains a product decision. Acceptance should demonstrate configuration-specific values, deterministic pre-launch ordering, the agreed failure/cancellation behavior, and unchanged existing preLaunchTask behavior.
- **Trace:**

  > DebugAdapterManager.updateDebugAdapterSchema derives object-valued preLaunchTask from task-definition schemas; it is not an inline shell-task schema. DebugTaskRunner.runTask delegates to AbstractTaskService.getTask, which locates existing configured or provider tasks. DebugService resolves launch variables before running that task and passes only the workspace and task identifier. BaseConfigurationResolverService.resolveWithInteraction already invokes command variables with the enclosing configuration, but that path is interpolation with string-result constraints rather than a general execution hook. https://github.com/microsoft/vscode/issues/27157 owns related parameter-sharing work, but not the no-tasks.json execution requirement. Preserve existing task lookup, task completion/error handling, and variable-substitution behavior; the uncertainty begins with which execution and argument-sharing contract this new surface should expose.
- **Open decisions:**
  - Should the supported pre-launch operation be a VS Code command, an inline shell/process task, or both?
  - Should the operation receive the entire resolved launch configuration or only explicitly declared arguments, and how should already-entered launch inputs be shared?
  - What observable completion, failure, and cancellation contract should apply, particularly for VS Code commands that return no value?
