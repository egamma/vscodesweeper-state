# Issue #189634 — Open file as file read-only through command flag

[https://github.com/microsoft/vscode/issues/189634](https://github.com/microsoft/vscode/issues/189634)

## Summary

Keep this accepted, 42-upvote request open: current read-only settings and editor commands do not provide invocation-level control through the local or remote code CLI. No verified older canonical owns the same request.

## Change summary

Allow the code CLI to open specified files read-only, including files outside the workspace and files opened remotely.

## Best solution

Expose read-only file opening through the CLI consistently across local and remote entry points, using the existing editor read-only behavior without changing filesystem permissions. Settle the lifetime and already-open-file semantics before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/environment/node/argv.ts`, `src/vs/platform/environment/common/argv.ts`, `src/vs/platform/windows/electron-main/windowsMainService.ts`, `src/vs/workbench/api/node/extHostCLIServer.ts`, `src/vs/workbench/services/filesConfiguration/common/filesConfigurationService.ts`
- **Validation:** On local and remote installations, invoke the chosen read-only flag with a writable file outside the workspace and verify editing is blocked immediately while filesystem permissions and persistent settings remain unchanged. Repeat with multiple files, new-window and reuse-window flows, and an already-open file; verify ordinary CLI opening remains writable. Check reopening and reload against the agreed lifetime semantics.
- **Behavior:**

  > Users can request read-only opening of specified files through the code command, locally and remotely, including files outside the workspace. The file must be protected from editing when first displayed, without requiring a follow-up editor command or prior settings changes. Ordinary CLI file opening remains unchanged, and the feature does not change filesystem permissions. Acceptance must cover multiple files, window reuse and the agreed behavior for already-open files, reopening and reload.
- **Trace:**

  > src/vs/platform/environment/node/argv.ts registers CLI options but has no read-only opening flag. Native file-opening handling is in src/vs/platform/windows/electron-main/windowsMainService.ts; the remote pipe contract OpenCommandPipeArgs and CLIServerBase.open in src/vs/workbench/api/node/extHostCLIServer.ts also omit read-only intent. FilesConfigurationService.isReadonly and updateReadonly in src/vs/workbench/services/filesConfiguration/common/filesConfigurationService.ts already implement resource-keyed session overrides, and the active-editor command in src/vs/workbench/contrib/files/browser/fileActions.ts uses that service. Existing settings and commands cover read-only editing but not invocation-level CLI control. Preserve provider read-only restrictions, filesystem permissions and ordinary opening behavior. The trace establishes the missing entry-point capability, but does not establish the complete transport into renderer editor opening or resolve lifetime and already-open-resource semantics. https://github.com/microsoft/vscode/issues/4873 supplies the underlying mode; https://github.com/microsoft/vscode/issues/241434 concerns a separate, narrower diff-side request.
- **Open decisions:**
  - Should CLI-requested read-only state last for the resource's current window session, end when its editor closes, or survive window reload?
  - When the requested file is already open and writable, should the invocation make all editors for that resource read-only in the receiving window or leave existing editors unchanged?
