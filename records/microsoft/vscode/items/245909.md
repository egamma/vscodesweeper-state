# Issue #245909 — MCP support substitutions as command line args

[https://github.com/microsoft/vscode/issues/245909](https://github.com/microsoft/vscode/issues/245909)

## Summary

Keep open: MCP arguments already support variable substitution, but values loaded from the server's envFile are unavailable during that substitution, so the example's central requirement remains unmet. This team-authored request is already correctly routed to chat-mcp; no qualifying fix or older canonical was established.

## Change summary

Allow MCP command-line arguments to reference environment variables supplied by the server's configured envFile.

## Best solution

Support file-backed argument substitution in the MCP launch pipeline with explicit lookup and precedence semantics. Preserve existing process-environment substitutions and server environment behavior, and document the distinction between substitution inputs and the spawned process environment.

Run the relevant suites through scripts/test.sh with targeted selectors.
- **Behavior:**

  > An MCP server should be able to receive a command-line argument whose value comes from its configured environment file, without requiring that value to be exported before VS Code starts. The supplied PostgreSQL example captures the goal, with the envFile path corrected to ${workspaceFolder}/.env. Acceptance must establish the resulting argument value, behavior when the same name exists in multiple environment sources, and unchanged behavior for configurations without envFile.
- **Trace:**

  > McpRegistry._replaceVariablesInLaunch in src/vs/workbench/contrib/mcp/common/mcpRegistry.ts performs configuration substitution before launching the server. ExtHostMcp.$substituteVariables in src/vs/workbench/api/common/extHostMcp.ts delegates to the ordinary variable resolver without loading envFile. ExtHostMcpNode.startNodeMpc in src/vs/workbench/api/node/extHostMcpNode.ts subsequently reads envFile into the child environment and overlays explicit env entries, but does not resolve the arguments against that environment. The separate portable environment expansion also uses process.env rather than envFile. This ordering matches the maintainer explanation at https://github.com/microsoft/vscode/issues/250074#issuecomment-2922701066. Preserve unrelated variable resolution, remote execution authority, and existing server-environment behavior; the unresolved boundary is whether file-backed lookup changes the existing ${env:NAME} contract and how conflicting values are selected.
- **Open decisions:**
  - Should existing ${env:NAME} expressions in MCP arguments read the configured envFile, or should file-backed values require a distinct explicit reference?
  - When a referenced name exists in process.env, envFile, and the server's explicit env object, which sources should participate in argument lookup and which value should win?
