# Issue #34627 — Support symbolic link folders in areas like debug, extensions

[https://github.com/microsoft/vscode/issues/34627](https://github.com/microsoft/vscode/issues/34627)

## Summary

Keep open: current URI canonicalization does not unify symbolic-link paths with their targets, and the existing settings do not cover the requested cross-editor, debugger, and extension behavior. This maintainer-expanded tracking issue has 60 upvotes; the closely related canonical-path proposal is newer and cannot replace it under the re-review rules.

## Change summary

Provide consistent file identity across symbolic-link and target paths so navigation, debugging, Git annotations, and extensions agree on the file being edited.

## Best solution

Establish a shared symlink-aware file-identity contract for editor navigation and consuming features, with an explicit policy for preserving workspace aliases versus selecting resolved target paths. Coordinate the canonical-path option proposal at https://github.com/microsoft/vscode/issues/130082 without treating it as a replacement for this broader tracking issue.

## Plan brief

- **Likely files:** `src/vs/platform/uriIdentity/common/uriIdentityService.ts`, `src/vs/workbench/services/editor/browser/editorService.ts`, `src/vs/platform/uriIdentity/test/common/uriIdentityService.test.ts`, `src/vs/workbench/services/editor/test/browser/editorService.test.ts`, `extensions/git/src/model.ts`
- **Validation:** After choosing the path policy, verify a temporary workspace containing a tracked source file and a symlink to it: open both through Explorer and terminal navigation, then debug through the symlinked path. Check editor reuse, selected document URI, breakpoint decorations, and Git gutters against the agreed contract; add targeted URI-identity and editor-service tests and run them with scripts/test.sh --run src/vs/platform/uriIdentity/test/common/uriIdentityService.test.ts --run src/vs/workbench/services/editor/test/browser/editorService.test.ts.
- **Behavior:**

  > Opening a file through its symbolic-link path and its target can produce separate editor identities, inconsistent Git annotations, and debugger navigation that separates breakpoint decorations from the source editor. The intended improvement is consistent behavior across these entry points while respecting intentional workspace aliases. Acceptance must specify which path is displayed and exposed to extensions, whether equivalent paths reuse an editor, and how debugger breakpoints and Git annotations remain associated with the same file. Existing non-symlink navigation must remain unchanged.
- **Trace:**

  > UriIdentityService.asCanonicalUri in src/vs/platform/uriIdentity/common/uriIdentityService.ts performs lexical path normalization and URI comparison-key caching, not filesystem target resolution. EditorService.isOpened in src/vs/workbench/services/editor/browser/editorService.ts uses that canonicalization; distinct symlink and target paths therefore remain distinct at this boundary. The Git extension independently resolves repository roots in extensions/git/src/model.ts:getRepositoryExact, which does not provide a shared file-identity policy. Search-following and watcher-inclusion settings cover traversal and notifications, not editor identity. https://github.com/microsoft/vscode/issues/130082 proposes an optional resolved-target policy, while this issue's discussion also requests preserving workspace aliases. The trace establishes the gap, not a complete cross-feature implementation boundary; do not assume changing URI comparison alone settles debugger or extension contracts, and keep hardlink identity and file-provider copy/move semantics outside the initial scope.
- **Open decisions:**
  - Should equivalent paths select the resolved filesystem target, preserve the workspace alias, or reuse the first-opened path, and should that policy be opt-in?
  - Should extensions and debug adapters receive the selected canonical URI exclusively, or must the originally requested alias remain available as part of the contract?
