## Summary

Keep open: the confirmed WSL context-menu failure points to the native Explorer-command component's incorrectly built x64 DLL, rather than an AppX access restriction. An upstream repair PR remains open, and the WSL-specific failure still needs verification after that repair is adopted.

## Evidence

- **Confirmed reproduction and revised diagnosis:** https://github.com/microsoft/vscode/issues/334716#issuecomment-6067199203 independently confirms the failure on VS Code 1.140 and 1.141. Direct COM invocation returns S_OK without starting Code.exe for a WSL folder, while a C:\ folder launches normally. PID matching identifies the AppX lifecycle events as belonging to the 32-bit DllHost, not Code.exe; launching Code.exe inside the package succeeds with another window already open, although cold start was not tested.
- **Upstream source matches silent failure:** https://github.com/microsoft/vscode-explorer-command/blob/main/src/explorer_command.cc: ExplorerCommandHandler::Invoke calls GetDisplayName(SIGDN_FILESYSPATH), invokes ShellExecuteW only on success, and otherwise skips the item before returning S_OK. This matches the commenter's observed 0x80070057 path-resolution failure and absence of a Code.exe process.
- **Architecture defect and pending repair:** https://github.com/microsoft/vscode-explorer-command/issues/26 is open and includes dumpbin output identifying code_explorer_command_x64.dll as machine 14C (x86). Current upstream main.gyp places TargetMachine outside msvs_settings. https://github.com/microsoft/vscode-explorer-command/pull/27 explicitly fixes that issue but is still OPEN with mergedAt null; it is not a landed fix.
- **Current VS Code integration:** build/win32/explorer-dll-fetcher.ts downloads architecture-named DLL artifacts from microsoft/vscode-explorer-command release v8.0.0-398351. resources/win32/appx/AppxManifest.xml registers Directory, Directory\Background, and file verbs through a COM surrogate, and build/gulpfile.vscode.ts substitutes the architecture-named DLL into that registration. Source inspection establishes the adoption path, not the downloaded binary's actual machine type.
- **Related reports are not verified symptom-equivalent canonicals:** https://github.com/microsoft/vscode/issues/334009 is older and open, but reports the incorrectly built DLL without the same WSL silent-failure symptom. It therefore does not meet this re-reviewed item's stronger duplicate bar. https://github.com/microsoft/vscode/issues/262129 asks for automatic WSL-remote opening, not repair of a command that launches nothing.
- **Verification boundary:** The full issue and comment were read, along with current integration and upstream invocation sources. No Windows execution or artifact inspection was performed in this read-only macOS checkout, so the upstream PR's effectiveness for both reported Explorer invocation variants remains unverified.
