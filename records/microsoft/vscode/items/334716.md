# Issue #334716 — Windows 11 Explorer context menu "Open with Code" silently fails on `\\wsl.localhost\` (WSL) paths — Code.exe launched from the packaged verb runs inside an AppX container

[https://github.com/microsoft/vscode/issues/334716](https://github.com/microsoft/vscode/issues/334716)

## Summary

Fresh, thoroughly-diagnosed report (0 days old, no maintainer triage yet) — the reporter traced a real silent-failure path when the Win11 top-level 'Open with Code' verb (hosted via the packaged code_explorer_command DLL, a prebuilt binary not in this source repo) spawns Code.exe inside a desktop AppX container that can't reach `\\wsl.localhost\` paths, so the CLI path is dropped via the doExtractPathsFromCLI/resolveOpenable `ignoreFileNotFound` flow without any dialog. This needs Windows-integration maintainer attention, not an automated close.

## Change summary

On Windows 11, right-clicking a `\\wsl.localhost\...` folder and choosing the top-level Explorer 'Open with Code' verb does nothing — the packaged launch silently fails while the CLI (`code.cmd`) and the regular (non-top-level) context menu both open the same path fine.

## Best solution

A Windows-integration maintainer needs to look at how the AppX-packaged `code_explorer_command_x64.dll` surrogate spawns `Code.exe` and whether the desktop AppX container it inherits can be avoided (or the path validated) before the CLI arg gets silently dropped in `resolveOpenable`/`doExtractPathsFromCLI` (src/vs/platform/windows/electron-main/windowsMainService.ts); since the DLL itself is a prebuilt binary from a separate build artifact (build/checksums/explorer-dll.txt) not present in this checkout, the actual fix likely lives outside this repo's TS source, but the silent-drop-with-no-dialog behavior in windowsMainService.ts could also be hardened to log/report failures like this.
