# Issue #334716 — Windows 11 Explorer context menu "Open with Code" silently fails on `\\wsl.localhost\` (WSL) paths — Code.exe launched from the packaged verb runs inside an AppX container

[https://github.com/microsoft/vscode/issues/334716](https://github.com/microsoft/vscode/issues/334716)

## Summary

Well-diagnosed report: the packaged Win11 context-menu verb runs Code.exe inside an AppX desktop container that cannot see WSL's 9P-based `\wsl.localhost\` share, so the path validation silently drops the argument and the process exits with no window — consistent with the `ignoreFileNotFound` path-filtering logic in windowsMainService.ts and the sparse-package COM surrogate declared in the AppX manifest. No maintainer has looked at this yet.

## Change summary

Right-clicking a WSL (`\\wsl.localhost\...`) folder in Windows 11 Explorer and choosing the packaged top-level "Open with Code" verb does nothing, while the same path works fine via the CLI.

## Best solution

Someone with Windows packaging expertise needs to confirm whether the sparse-package/AppX container applied to the COM surrogate (code_explorer_command DLL, see build/checksums/explorer-dll.txt and resources/win32/appx/AppxManifest.xml) can be relaxed or given loopback/network access for `wsl.localhost`, or whether the spawned Code.exe needs to escape the container before resolving UNC paths; likely belongs with whoever owns the Windows Explorer context-menu / installer packaging.
