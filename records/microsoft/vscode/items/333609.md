# Issue #333609 — Update model picker UX

[https://github.com/microsoft/vscode/issues/333609](https://github.com/microsoft/vscode/issues/333609)

## Summary

Keep open: the merged redesign is still an opt-in experiment, while the team-authored issue and discussion retain unresolved decisions about tabs, provider grouping, list density, and configuration placement. The On Deck milestone also records this as accepted work rather than a completed default experience.

## Change summary

Redesign the model picker to make model configuration and cost implications clearer while organizing Copilot and third-party provider models without overwhelming most users.

## Best solution

Use the experimental picker to settle the observable UX decisions, then graduate a compact default experience that exposes provider-specific organization only when relevant and keeps model configuration close to pricing information.

- **Behavior:**

  > The default model picker should remain compact for users with only Copilot models while making additional providers understandable when configured. Users must be able to find models, understand configuration and cost implications, and change supported options without unstable controls or hover-dependent discovery. Acceptance should cover Copilot-only, single-BYOK-provider, and multiple-provider states, including keyboard and screen-reader navigation.
- **Trace:**

  > https://github.com/microsoft/vscode/pull/334332 introduced the tabbed picker, provider destinations, model details cards, telemetry, tests, and a component fixture. Current main selects that path through `chat.experimentalModelPicker`, registered as default false in src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts and consumed by ModelPickerWidget in src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerWidget.ts; the existing flat picker remains the default. Provider grouping and section construction live in modelPickerTabs.ts, with coverage in modelPickerTabs.test.ts. The uncertainty begins at the product boundary: when provider tabs appear, how many tabs are exposed, which models are condensed, and where configuration is presented. Preserve existing model selection, entitlement filtering, accessibility, and configuration semantics while evaluating the presentation.
- **Open decisions:**
  - Should provider tabs appear only after a user configures BYOK, and should multiple BYOK providers receive separate tabs or share one BYOK destination?
  - Which models should remain visible in the default Copilot list, and should recent, pinned, recommended, and legacy models remain distinct user-visible sections?
  - Should thinking effort, context size, and cost impact live in the model details pop-out, remain directly visible in the picker, or use another persistent surface that does not depend on hover?
  - What evidence from the experiment is sufficient to replace the current flat picker and remove the opt-in setting?
