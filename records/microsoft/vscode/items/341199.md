# Issue #341199 — Agent Host auth restart wait blocks history restore, unrelated session prompts, and cancellation

[https://github.com/microsoft/vscode/issues/341199](https://github.com/microsoft/vscode/issues/341199)

## Summary

Team-authored, freshly filed, well-diagnosed bug. The deferred-restart wait and waiter are still present on main in copilotAgent.ts. Keep open; no close applies.

## Change summary

A deferred Copilot SDK client restart blocks a history restore, which blocks the per-client dispatch queue, so other sessions' prompts and cancellations never run.

## Best solution

Make history restore for non-resident sessions not wait on the deferred restart. Alternatively, stop it from holding the per-client dispatch queue, so cancellations and other sessions' actions still run. Coordinate with the related deferred-auth-restart issues #341007 and #340468.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/platform/agentHost/node/agentService.ts`
- **Validation:** An agent service test: with a deferred restart pending and a restore in flight, a cancel action for another session still applies.
- **Behavior:**

  > A pending deferred SDK client restart must not block unrelated session history restore, new prompts, or cancellation. Cancellation must always be applied. Active turns must still not be torn down by the restart.
- **Trace:**

  > _ensureClientForSession in copilotAgent.ts awaits _pendingClientRestartWaiter when connector auth mismatches. getChatMessages for a non-resident session goes through it. AgentService.dispatchAction serializes by client ID across sessions, so one blocked action stalls the rest. The boundary is that the restart must stay deferred while chats are busy. Related: #341007 and #340468.
- **Open decisions:**
  - Should history restore read from persisted data without the restarted client, or fail fast and retry?
  - Should the dispatch queue be keyed per session, or should cancellation bypass the queue?
