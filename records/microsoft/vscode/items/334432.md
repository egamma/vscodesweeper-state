# Issue #334432 — Copilot Chat: switching a session to autopilot mid-conversation injects task_complete instructions into the middle of the system prompt, invalidating prefix cache for third-party (chatProvider) models

[https://github.com/microsoft/vscode/issues/334432](https://github.com/microsoft/vscode/issues/334432)

## Summary

Still present on current main: the autopilot `task_complete` block (and the voice-mode / template-variable blocks) are rendered inside `baseInstructions` and collapsed into the single leading system message, so toggling autopilot mid-session rewrites the system prefix and invalidates automatic prefix caching for providers without cache breakpoints. Routing to the chat agent area; the report already contains a maintainer-grade trace, so the remaining work is a placement decision, not more info.

## Change summary

Request-scoped conditional system blocks (autopilot `task_complete`, voice mode, template variables) are merged into the middle of the leading system prompt, busting the upstream prefix cache for third-party `chatProvider` models when the session mode changes mid-conversation.

## Best solution

Move the request-scoped conditional instruction blocks out of the leading system prefix in `agentPrompt.tsx` — render them after conversation history (trailing system block or appended to the latest user message), the same way `getOrFreezeCustomizationsIndex`'s `drift` is handled — so the system prefix stays byte-stable across turns and a mode toggle only invalidates the appended tail.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/prompts/node/agent/agentPrompt.tsx`, `extensions/copilot/src/extension/prompts/node/base/promptRenderer.ts`, `extensions/copilot/src/extension/intents/node/agentIntent.ts`
- **Validation:** A prompt-rendering test that renders AgentPrompt twice for the same conversation — once with `permissionLevel` non-autopilot and once with `'autopilot'` — and asserts the leading system message text is byte-identical across the two renders (the autopilot instruction appearing only after conversation history).
- **Behavior:**

  > Switching a chat session to autopilot (or toggling voice mode, or changing template variables) mid-conversation must not change the leading system message text. The autopilot `task_complete` instruction must still reach the model and still produce the same behavior (summary + `task_complete` call on completion), but it must be positioned so that only content after the conversation history changes. Acceptance: rendering the same conversation with and without autopilot yields an identical first system message; the autopilot instruction is present in the rendered prompt in both the first-autopilot-turn and later-turn cases; existing agent prompt tests still pass.
- **Trace:**

  > Confirmed on HEAD 3b486b1f by reading the source: `AgentPrompt.render` in extensions/copilot/src/extension/prompts/node/agent/agentPrompt.tsx sets `isAutopilot` (line 130) from `promptContext.request?.permissionLevel` and renders the `task_complete` `<SystemMessage priority={80}>` (lines 140-143) inside `baseInstructions`, which is emitted before `SummarizedConversationHistory` / `AgentConversationHistory` / `AgentUserMessage`. PromptRenderer.render in extensions/copilot/src/extension/prompts/node/base/promptRenderer.ts then concatenates consecutive system messages into one, so the conditional text is embedded in the leading system blob and every downstream token (including the entire history) falls out of an automatic prefix cache when the flag flips. The same file already solves this class of problem for the customizations index via `getOrFreezeCustomizationsIndex`, which freezes the system-prompt value and emits a `drift` block in the latest user message explicitly to avoid system-prompt cache churn — that is the precedent to follow, but `isAutopilot`, `isVoiceModeInput` and `templateVariablesContext` are outside it. Boundary: do not change the system-message collapsing in promptRenderer.ts for other callers, do not change when `task_complete` is enabled (agentIntent.ts:~289), and do not alter the frozen-customizations mechanism. Related, non-duplicate: https://github.com/microsoft/vscode/issues/340561.
- **Open decisions:**
  - Should request-scoped conditional instructions be rendered as a trailing system block after conversation history, or appended to the latest user message like the existing `drift` block?
  - Does the scope cover all three conditional blocks (autopilot `task_complete`, voice mode, template variables), or only the autopilot one reported here?
  - Is relocating the `task_complete` instruction out of the leading system prompt acceptable for model compliance on autopilot sessions, or must system-prefix stability be achieved some other way (e.g. always emitting the block with a mode marker)?
