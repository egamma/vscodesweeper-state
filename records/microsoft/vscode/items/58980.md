# Issue #58980 — Relative problem paths don't take `cwd` into account

[https://github.com/microsoft/vscode/issues/58980](https://github.com/microsoft/vscode/issues/58980)

## Summary

The requested task-aware problem-matcher path resolution remains missing on current main. Keep this accepted, team-authored request open; the maintainer explicitly identified a compatibility concern that needs a product decision.

## Change summary

Allow relative problem paths to resolve against the task's working directory without repeating that directory in fileLocation.

## Best solution

Provide a supported task-working-directory reference for problem matchers, preserving explicitly configured fileLocation behavior and existing task compatibility. Decide whether task-relative resolution is opt-in or becomes the default before implementation.

- **Validation:** After choosing the compatibility contract, run a shell task with options.cwd='${workspaceFolder}/builddir' that emits 'sample.c:1:1: error: test', with distinct sample.c files in the workspace root and builddir. Using the agreed task-aware matcher configuration, the Problems entry must open builddir/sample.c without duplicating the directory expression in fileLocation. Also verify that an explicit fileLocation override wins and legacy configurations retain the agreed compatibility behavior.
- **Behavior:**

  > A task started in a workspace subdirectory should be able to resolve relative diagnostic filenames against that task's working directory without repeating the directory expression in its problem matcher. Today, omitting the fileLocation override resolves those filenames against the workspace instead. Acceptance must distinguish files with the same relative name in the workspace root and task directory, cover an explicit fileLocation override, and preserve the agreed behavior of existing tasks. Whether this capability changes the default or requires opt-in remains a maintainer decision.
- **Trace:**

  > ProblemMatcherParser.createProblemMatcher in src/vs/workbench/contrib/tasks/common/problemMatcher.ts defaults relative filePrefix to '${workspaceFolder}' and retains inherited matcher locations unless fileLocation is explicitly overridden. TerminalTaskSystem._resolveMatchers in src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts resolves that prefix independently of _resolveOptions, which handles task options.cwd; getResource joins diagnostic filenames to the resolved matcher prefix. The existing '${cwd}' branch in src/vs/workbench/services/configurationResolver/common/variableResolver.ts refers to the workspace or VS Code process, not the launched task. These source paths establish the remaining feature gap without executing code. Preserve explicit matcher prefixes and unrelated variable semantics; terminal link detection is outside the reported diagnostic-resolution boundary. The compatibility concern is recorded at https://github.com/microsoft/vscode/issues/58980#issuecomment-423091053, and https://github.com/microsoft/vscode/issues/69409 supplies a duplicate report specifically about '${cwd}'.
- **Open decisions:**
  - Should task-working-directory resolution require explicit opt-in, preserving existing matcher defaults, or become the default for relative problem paths? If opt-in, what public configuration or variable contract should users adopt?
