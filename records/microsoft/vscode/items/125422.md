# Issue #125422 — Setting service should return default value when json scheme is invalid

[https://github.com/microsoft/vscode/issues/125422](https://github.com/microsoft/vscode/issues/125422)

## Summary

Keep open: current main still returns consolidated configuration values without schema validation, and maintainers have explicitly agreed that validation belongs in the configuration service. This is a team-authored, accepted debt item with no fixing commit or open implementation PR.

## Change summary

Make configuration reads reject values that do not match the registered setting schema and fall through to the next valid configured value or default.

## Best solution

Have the configuration service centrally validate non-default values against registered schemas, falling through configuration precedence when an override is invalid, while supporting explicitly registered compatibility behavior for complex or legacy values. Reads should not rewrite settings files or alter synchronization.

## Plan brief

- **Likely files:** `src/vs/platform/configuration/common/configurationService.ts`, `src/vs/platform/configuration/common/configurationModels.ts`, `src/vs/platform/configuration/common/configurationRegistry.ts`, `src/vs/platform/configuration/test/common/configurationService.test.ts`, `src/vs/base/common/verifier.ts`
- **Validation:** Extend the ConfigurationService unit suite with registered primitive, enum, object, override, and legacy-compatible settings; run `scripts/test.sh --grep 'ConfigurationService'` and verify invalid values fall through to the next valid scope/default while valid values and raw settings files remain unchanged.
- **Behavior:**

  > Reading a registered setting must return a value allowed by that setting's schema. If a configured value is invalid, resolution falls through to the next valid value in configuration precedence and ultimately the registered default, without rewriting the settings file or changing what is synchronized. Valid values, language overrides, resource-specific values, and intentionally supported legacy formats must retain their defined behavior. Extension-facing configuration reads must follow the contract selected during planning.
- **Trace:**

  > ConfigurationService.getValue in src/vs/platform/configuration/common/configurationService.ts delegates to Configuration.getValue. Configuration.getValue in src/vs/platform/configuration/common/configurationModels.ts currently consolidates configuration layers and returns ConfigurationModel.getValue without value validation; ConfigurationModelParser consults IConfigurationRegistry schemas only for filtering. Registered schemas and defaults are available from src/vs/platform/configuration/common/configurationRegistry.ts. src/vs/base/common/verifier.ts provides primitive and object verifiers, but its current use in the editor part is manually declared and does not implement general JSON-schema or configuration-precedence validation. The boundary is read-time effective-value resolution: do not mutate user files, sanitize synchronized data, or silently remove settings. Related consumer validation in https://github.com/microsoft/vscode/pull/197242 is precedent, not completion of this configuration-service work.
- **Open decisions:**
  - When an object or array only partially violates its schema, should the entire value at that configuration scope be rejected, or should valid nested content be retained while invalid members fall back?
  - For settings that intentionally accept legacy values outside their declared schema during migration, must compatibility be represented in the schema or a registered validator, or should consumers have an explicit raw-value read contract?
  - Should extension-facing workspace.getConfiguration reads always receive the same validated effective value as internal IConfigurationService consumers, or retain access to malformed configured values for compatibility?

## Evidence

- **current source:** On current main, src/vs/platform/configuration/common/configurationService.ts delegates getValue directly to Configuration.getValue; src/vs/platform/configuration/common/configurationModels.ts:787-790 returns the consolidated model value without consulting the registered schema.
- **schema availability:** src/vs/platform/configuration/common/configurationRegistry.ts exposes registered setting schemas through IConfigurationRegistry.getConfigurationProperties(), but ConfigurationModelParser in src/vs/platform/configuration/common/configurationModels.ts uses them for filtering rather than validating value types.
- **maintainer direction:** https://github.com/microsoft/vscode/issues/125422#issuecomment-1792147435 records the latest maintainer direction: validate in the configuration service, use registered types/defaults for simple settings, permit exceptional validators for complex settings, and validate user-configured values when getValue is called.
- **canonical tracker:** https://github.com/microsoft/vscode/issues/191536 was closed as a duplicate of this issue after demonstrating the same malformed-value behavior through workspace.getConfiguration; no open PR currently references or fixes https://github.com/microsoft/vscode/issues/125422.
