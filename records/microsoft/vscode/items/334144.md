# Issue #334144 — Icons render as missing glyphs in Remote-SSH since 1.136.0 — glicons.woff2 fails to load

[https://github.com/microsoft/vscode/issues/334144](https://github.com/microsoft/vscode/issues/334144)

## Summary

Confirmed regression, source-reproducible on current main: the `vscode-managed-remote-resource` protocol handler in `setupManagedRemoteResourceUrlHandler` treats an empty `Referer` header (which the workbench's own icon/font/svg requests legitimately send) as failing the `!request.referrer` guard, so every remote-hosted icon/font request is silently blocked — exactly matching the community's traced root cause. No fix is present yet.

## Change summary

Since 1.136.0, extension/product icons and the glicon font fail to load over Remote-SSH (net::ERR_FAILED on vscode-managed-remote-resource://), rendering as tofu/empty boxes.

## Best solution

Fix the referrer guard in `src/vs/code/electron-main/app.ts` (`setupManagedRemoteResourceUrlHandler`) to not reject requests whose referrer is empty/undefined (only workbench pages, which legitimately send an empty referrer for these subresource loads, should be allowed; only genuine `vscode-webview://`-originated requests should be blocked) — and separately fix `notFound()`/the 500 branch to return an `ArrayBufferView` (not a raw string) since the scheme is registered via `registerBufferProtocol`, which otherwise causes Electron to fail the request outright regardless of the referrer fix.

## Evidence

- **source confirmation:** src/vs/code/electron-main/app.ts, setupManagedRemoteResourceUrlHandler(): `if (!request.referrer || request.referrer.startsWith(`${Schemas.vscodeWebview}://`)) { return callback(notFound()); }` — `!request.referrer` is true for an empty-string referrer, which the workbench's own icon/font/svg requests carry, so they are wrongly rejected.
- **buffer-protocol defect:** `notFound()` returns `{ statusCode: 404, data: 'Not found' }` (a string), but the scheme is registered with `protocol.registerBufferProtocol`, which requires an ArrayBufferView for `data` — Electron's buffer-protocol path fails such responses with `net::ERR_FAILED` instead of delivering a clean 404, matching the exact console error reporters see.
- **community root-cause analysis:** Comment by apimentasoto (https://github.com/microsoft/vscode/issues/334144#issuecomment, 2026-09-04) traces this to PR #332793 (milestone 1.136.0) which added the referrer check; matches the observed `net::ERR_FAILED` on `vscode-managed-remote-resource://` and the main-process 'Blocked vscode-managed-remote-resource request' log line reported by phanthaitrung.
- **scale of impact:** 20 upvotes, 15 comments in 1 day, `recent-regression` label already applied, and several related issues (https://github.com/microsoft/vscode/issues/334166, https://github.com/microsoft/vscode/issues/334185, https://github.com/microsoft/vscode/issues/334404, https://github.com/microsoft/vscode/issues/334451, https://github.com/microsoft/vscode/issues/334364) have already been closed pointing back to this one, indicating it is the emerging canonical for this regression.
