# Issue #340306 — Copilot sandbox should allow to modify permissions on the fly

[https://github.com/microsoft/vscode/issues/340306](https://github.com/microsoft/vscode/issues/340306)

## Summary

Fresh (1-day-old), clearly-described feature request about the Copilot agent-sandbox permission dialog: when a sandboxed operation hits a path outside the workspace, the current dialog gives no way to allow it once or adjust the policy, pushing users to disable sandboxing entirely. No existing mechanism covers this, so it stays open for product design.

## Change summary

When a sandboxed Copilot agent session is blocked from touching a file outside the workspace, offer in-dialog actions to allow the operation once or to adjust the sandbox policy for the session/future sessions, instead of forcing the user to disable sandboxing globally.

## Best solution

Extend the sandbox violation/confirmation UI (near src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatSandboxPrerequisiteConfirmationSubPart.ts and the agent-host sandbox policy plumbing in src/vs/platform/agentHost/node/copilot/copilotSandboxPolicy.ts) with explicit 'allow once' and 'update policy' actions, designed together with the sandbox policy engine team.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatSandboxPrerequisiteConfirmationSubPart.ts`, `src/vs/platform/agentHost/node/copilot/copilotSandboxPolicy.ts`, `src/vs/platform/agentHost/node/copilot/agentHostSandboxEngine.ts`
- **Validation:** A reproduction (manual or scripted) where a sandboxed session hits an out-of-workspace path and the dialog offers a working 'allow once' and/or 'update policy and continue' action that lets the session proceed without fully disabling the sandbox.
- **Trace:**

  > Traced the existing sandbox confirmation UI (chatSandboxPrerequisiteConfirmationSubPart.ts, limited to 'Apply Fix/Install' and 'Cancel') and the sandbox-unsupported notification (agentHostSandboxNotification.ts, dismiss-only) — neither offers a path to allow a single out-of-workspace operation or adjust the policy. The sandbox policy itself is read via copilotSandboxPolicy.ts/copilotSandboxPolicyDisplay.ts but is not mutable from this dialog. What must not change: the sandbox's default-deny safety posture for unapproved paths.
- **Open decisions:**
  - Should 'allow once' apply only to the exact path/operation, or to the broader pattern that triggered the denial?
  - When the user chooses to 'modify the sandbox policy', does that change apply only to the current session or persist across future sessions?
  - Should changing the policy from this dialog require re-confirmation of the specific pending operation, or auto-resume it?

## Evidence

- **current confirmation UI:** src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatSandboxPrerequisiteConfirmationSubPart.ts only exposes 'Apply Fix and Retry/Install' and 'Cancel' for sandbox prerequisite/remediation issues — no 'allow once' or 'adjust policy and continue' action for an out-of-workspace file access denial.
- **sandbox-unsupported notification:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSandboxNotification.ts only surfaces a dismissible warning when sandboxing itself is unsupported; it has no actions either, consistent with the reporter's experience of no actionable path.
- **existing policy inspection only:** src/vs/platform/agentHost/node/copilot/copilotSandboxPolicyDisplay.ts adds a '/policy' slash command to view the effective sandbox policy in an editor, but there is no in-dialog way to modify it or grant a one-off exception.
