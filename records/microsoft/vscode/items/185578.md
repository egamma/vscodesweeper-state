# Issue #185578 — Git - VS Code doesn't act correctly when re-using a merged PR's branch

[https://github.com/microsoft/vscode/issues/185578](https://github.com/microsoft/vscode/issues/185578)

## Summary

A VS Code maintainer (lszomoru) confirmed in the thread that VS Code fails to detect when a branch's upstream has been deleted even after `git fetch --prune`, so this stays open as a real bug; I could not verify from source whether it's since been fixed, and the prior review's cited fix commit was already refuted, so no close is warranted without a new, verifiable fix commit.

## Change summary

After creating a branch from another (already-merged/deleted) remote branch, VS Code shows stale/incorrect upstream tracking and ahead/behind counts instead of treating the branch as fresh and unpublished.

## Best solution

Confirm whether the existing '[gone]' upstream-handling in extensions/git/src/git.ts getBranch (which clears `upstream` when `for-each-ref` reports status `[gone]`) actually resolves lszomoru's confirmed bug on current main, and separately decide — as a product/UX call — whether a branch created via `git checkout -b <new> <remote>/<other>` should be displayed as a fresh unpublished branch rather than auto-tracking the source branch's ahead/behind counts.

## Plan brief

- **Likely files:** `extensions/git/src/git.ts`, `extensions/git/src/repository.ts`
- **Validation:** Manually verify: (1) after merging and deleting a remote branch, run `git fetch --prune` locally and confirm VS Code's Source Control / status bar no longer shows an upstream/ahead-behind for that local branch; (2) run `git checkout -b <new> origin/<other>` and check whether the status bar still shows ahead/behind against the source branch, and whether that is considered correct or should change.
- **Behavior:**

  > When a local branch's remote-tracking ref has been deleted (post-merge, after `git fetch --prune`), VS Code's branch status (status bar / Source Control) should stop showing an upstream and stale ahead/behind counts for it. Separately, decide and confirm whether a branch created from another branch (`git checkout -b <new> <remote>/<other>`) should be shown as a fresh, unpublished branch instead of tracking/ahead-behind against the source branch.
- **Trace:**

  > extensions/git/src/git.ts getBranch() parses `git for-each-ref --format=...%(upstream:track)...` and already special-cases the `[gone]` status to null out `upstream` (and therefore ahead/behind defaults to 0) — this logic appears to directly address the maintainer-confirmed bug in comment https://github.com/microsoft/vscode/issues/185578#issuecomment (lszomoru, 2023-06-26). Whether extensions/git/src/repository.ts's branch-status refresh (triggered by fetch/prune) actually surfaces this updated state end-to-end was not traced further and would need runtime verification (not possible in this read-only checkout). Do not change git's own `branch.autoSetupMerge` tracking defaults; the open design question is purely about how VS Code *displays* a branch's relationship once created.
- **Open decisions:**
  - Should VS Code treat a branch created via `git checkout -b <new> <remote>/<other>` as a fresh, unpublished branch (hiding/suppressing ahead/behind against the source branch) instead of showing it tracks and diverges from the source branch, which is git's own default tracking behavior?
  - Does the existing '[gone]' handling in getBranch() fully resolve lszomoru's confirmed bug (stale upstream/ahead-behind after fetch --prune), or is there a remaining gap in how repository.ts refreshes branch status after a prune?
