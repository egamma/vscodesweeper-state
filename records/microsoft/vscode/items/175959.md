# Issue #175959 — Allow to fork utility process from a worker thread

[https://github.com/microsoft/vscode/issues/175959](https://github.com/microsoft/vscode/issues/175959)

## Summary

Keep open: utility-process creation still runs through Electron's main-process API, so the requested worker-thread capability remains unfulfilled. The related terminal migration does not resolve this separate spawning limitation.

## Change summary

Allow utility processes to be forked from a Node.js worker thread to avoid blocking Electron's main thread during process creation.

## Best solution

Electron should provide worker-thread-safe utility-process creation or equivalent nonblocking spawning. VS Code can then adopt that capability in its shared utility-process launcher and reassess startup deferral using performance measurements.

## Evidence

- **Current spawning path:** src/vs/platform/utilityProcess/electron-main/utilityProcess.ts:261 calls utilityProcess.fork directly inside UtilityProcess.doStart. The inspected launcher contains no worker-thread spawning option.
- **Upstream API boundary:** https://github.com/electron/electron/blob/main/docs/api/utility-process.md documents utilityProcess as a Main-process API and exposes no worker-thread spawning capability. This supports upstream ownership, but does not establish the duration of any synchronous blocking.
- **Existing worker abstraction is not coverage:** src/vs/platform/utilityProcess/electron-main/utilityProcessWorkerMainService.ts creates UtilityProcessWorker instances whose spawn() calls WindowUtilityProcess.start. These are utility-process-backed workers, not Node.js worker threads that perform the fork.
- **Related migration has different scope:** https://github.com/microsoft/vscode/issues/175335 is closed and concerns moving the PTY host into a utility process. Its comment https://github.com/microsoft/vscode/issues/175335#issuecomment-1452491211 explicitly identifies this issue as separate spawning-performance work. Current ElectronPtyHostStarter.start in src/vs/platform/terminal/electron-main/electronPtyHostStarter.ts still uses UtilityProcess.start on the main-process path.
- **Startup deferral remains, with changed semantics:** src/vs/workbench/services/sharedProcess/electron-browser/sharedProcessService.ts:connect waits for Promise.race([this.restoredBarrier.wait(), timeout(2000)]). The timeout is a deadlock safeguard rather than an unconditional two-second delay; this deferral does not provide worker-thread process creation.
- **Canonical and history checks:** Open-issue searches for utility/worker, utility/thread, and fork/main-process terminology found no verified canonical owning this capability. The checkout is shallow, and inspected local history supplied no concrete fixing commit; neither a duplicate nor a completed close is substantiated.
