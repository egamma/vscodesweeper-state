# Issue #334611 — sticky request overlaps with the editable input that has the same content

[https://github.com/microsoft/vscode/issues/334611](https://github.com/microsoft/vscode/issues/334611)

## Summary

Current main explicitly renders a sticky copy of the active request while its editable input is present, preserving the reported overlap path. This member-authored issue should remain open while maintainers decide whether editing suppresses sticky scroll or retains it without obscuring the input.

## Change summary

Editing a request while scrolling can leave a sticky copy of that request overlapping the editable input containing the same text.

## Best solution

Ensure the active request's sticky representation cannot overlap or duplicate its editable input. Preserve normal sticky-request behavior outside edit mode and have the chat area owner choose whether edit mode hides the sticky row or lays it out separately.

- **Behavior:**

  > When a request is being edited, scrolling must not place a sticky copy of that request over the editable input containing the same content. Editing and keyboard focus must remain usable, and ordinary sticky requests outside edit mode must remain unchanged. Acceptance should cover a non-empty edited request after scrolling, an empty edited value, and restoration of normal sticky behavior after editing ends.
- **Trace:**

  > ChatListRenderer in src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts deliberately recognizes `isStickyAndEditing` and renders `delegate.getEditingValue()` into a sticky request element. ChatWidget.clickedRequest in src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts simultaneously installs the real `.chat-edit-input-container` in the source request row, producing the two active representations behind the reported overlap. The existing `does not create an empty sticky row while editing a request to an empty value` test explicitly expects the sticky row to return for non-empty edited text, so it does not enforce the desired non-overlap behavior. Keep normal non-editing sticky scroll, request-edit semantics, and accessibility of the input unchanged; the uncertainty is limited to the sticky row's observable behavior during editing.
- **Open decisions:**
  - While the sticky request is actively being edited, should the sticky row be hidden entirely, or remain visible in a layout that cannot cover or duplicate the editable input?
