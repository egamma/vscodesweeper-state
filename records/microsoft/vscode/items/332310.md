# Issue #332310 — File links use Windows paths in non-Local multi-root sessions on Remote WSL

[https://github.com/microsoft/vscode/issues/332310](https://github.com/microsoft/vscode/issues/332310)

## Summary

Well-diagnosed, source-traceable bug in the experimental multi-root agent-host session feature: links get wrapped through the agent-host URI scheme even when they already carry a fully-qualified remote URI, and the 'local' agent-host authority's label formatter always uses the client's own OS rather than the remote host's, producing Windows-style paths that don't resolve in a Remote-WSL window.

## Change summary

In a Remote - WSL multi-root workspace, file links from a non-Local multi-root session render with Windows backslashes and fail to open; the same links work when the session is delegated to Local.

## Best solution

In stateToProgressAdapter.ts's link rewriting (rewriteLinkTokenRaw/rewriteAgentHostLinkTarget), avoid re-wrapping URIs that are already fully-qualified for a filesystem provider (e.g. vscode-remote://) through the vscode-agent-host scheme, and fix agentHostLabelFormatter's OS assumption at agentHostFileSystemService.ts:63 (using client-side OS for LOCAL_AGENT_HOST_AUTHORITY) so path separators match the actual remote host rather than the renderer's own platform.

## Evidence

- **OS-dependent label formatter:** src/vs/platform/agentHost/common/agentHostFileSystemService.ts:63 registers agentHostLabelFormatter(LOCAL_AGENT_HOST_AUTHORITY, OS) using the client renderer's own OperatingSystem (OS from base/common/platform.js), which is Windows in an Electron Remote-WSL window regardless of the actual remote host OS; agentHostLabelFormatter (agentHostUri.ts:264) then picks backslash separators purely from that OS value.
- **double-wrapping of already-addressed remote URIs:** rewriteLinkTokenRaw/rewriteAgentHostLinkTarget (stateToProgressAdapter.ts:2003-2145) only skip wrapping when connectionAuthority === 'local' AND scheme === file (see wrapAgentHostUri in agentHostUri.ts:108); a manually-provided vscode-remote://wsl+ubuntu/... link is not in EXTERNAL_LINK_SCHEMES, so it gets wrapped as vscode-agent-host://[connectionAuthority]/path?_ah=[meta], which matches the reported 'No file system provider found for resource ...wsl%2Bubuntu...' failure when the wrapped URI is later unwrapped/resolved.
