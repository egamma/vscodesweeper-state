# Issue #320530 — Copilot tool list showing wrong name for tools

[https://github.com/microsoft/vscode/issues/320530](https://github.com/microsoft/vscode/issues/320530)

## Summary

The regression remains in current main: MCP tool prefixes and list classifications prefer the server-announced name over the unique configured key, so multiple instances of one server become difficult to distinguish. The related closed issue's fix only adds the key as a picker description and does not resolve model-facing tool names or every tool-list surface.

## Change summary

Restore distinguishable MCP tool names when multiple configured servers announce the same server name.

## Best solution

Preserve a readable announced server name while ensuring every tool-list surface and model-facing tool identifier retains the configured server's unique identity. The naming must remain stable and unambiguous when multiple configurations launch the same binary or announce the same `serverInfo.name`.

- **Behavior:**

  > When two MCP configurations have different configured keys but announce the same server name, users and the model must be able to distinguish their tools without repeated tool searches. Tool identifiers must remain unique and stable across refreshes, and relevant tool-list surfaces must expose the configured identity. A single server with a registry-style key should retain the readable announced title behavior introduced by https://github.com/microsoft/vscode/pull/318638.
- **Trace:**

  > McpServer in src/vs/workbench/contrib/mcp/common/mcpServer.ts derives `preferredName` from cached `serverName || definition.label`; `McpPrefixGenerator.take` then collision-resolves identical announced names numerically, and the resulting prefix is passed to each `McpTool`. ToolDataSource.classify in src/vs/workbench/contrib/chat/common/tools/languageModelToolsService.ts independently prefers `serverLabel`, and chatContext.ts consumes that classification in the Add Context list. https://github.com/microsoft/vscode/pull/325003 only added `source.label` as secondary text in chatToolPicker.ts, so it did not change these paths. Preserve the readable-name improvement for unique servers and avoid changing MCP protocol metadata; the unresolved boundary is which client-side naming representation should carry configured identity when announced names collide.
- **Open decisions:**
  - When multiple configured MCP servers announce the same name, should model-facing tool names return to using the configured JSON key, combine the announced name with that key, or use the configured key only for colliding instances?
  - Should every tool-list surface always show the configured key as secondary identity, or only when announced server names collide?
