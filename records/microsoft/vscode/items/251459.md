# Issue #251459 — Allow Extensions to Register In-Process MCP Servers via In-Memory Transport

[https://github.com/microsoft/vscode/issues/251459](https://github.com/microsoft/vscode/issues/251459)

## Summary

The extension API still supports only stdio and HTTP MCP server definitions, leaving the requested in-process transport unsupported. Keep this accepted On Deck request open for API design; neither the existing HTTP workaround nor the related prompt-contribution work delivers the central capability.

## Change summary

Allow extensions to expose extension-host-resident MCP servers without launching another process or opening a network listener.

## Best solution

Design an extension API for connecting an in-process MCP server to VS Code's MCP client, with explicit connection ownership and disposal semantics. Preserve existing MCP controls and stdio/HTTP behavior while allowing the server to share its extension's state and authentication.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostMcp.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/common/extHostTypeConverters.ts`, `src/vs/workbench/api/browser/mainThreadMcp.ts`, `src/vs/workbench/contrib/mcp/common/mcpTypes.ts`
- **Validation:** End the plan with an extension-host integration check that registers an in-process MCP server, discovers and invokes a tool sharing extension state, and verifies disconnection on registration disposal and extension deactivation, without creating a child process or network listener. Include regression checks for existing stdio and HTTP providers.
- **Behavior:**

  > An extension can expose an MCP server running inside its own extension host without a separate process or network listener. VS Code can discover and invoke that server's tools, which can use the extension's existing state and authentication. Disposing the registration or deactivating the extension disconnects the server and removes its availability. Existing stdio and HTTP server registration continues to behave as before.
- **Trace:**

  > The public McpServerDefinition union in src/vscode-dts/vscode.d.ts accepts only stdio and HTTP definitions. ExtHostMcpService.registerMcpConfigurationProvider in src/vs/workbench/api/common/extHostMcp.ts converts those definitions and sends serialized collections to the main thread; McpServerDefinition.from in src/vs/workbench/api/common/extHostTypeConverters.ts has only HTTP and stdio branches. McpServerTransportType and McpServerLaunch in src/vs/workbench/contrib/mcp/common/mcpTypes.ts encode the same restriction. Runtime handling uses HTTP handles or Node child processes, so an extension-host-resident transport is not exposed by this path. The remaining uncertainty is the public transport contract and its integration across the extension-host boundary, not whether the current HTTP workaround satisfies the request. Preserve existing server controls and existing transport semantics. The separate contribution work in https://github.com/microsoft/vscode/issues/251580 supplies a concrete consumer but does not implement this capability.
- **Open decisions:**
  - Should the public API accept an MCP SDK-compatible Transport directly, as requested, or expose a VS Code-owned message transport contract that extensions adapt to?
