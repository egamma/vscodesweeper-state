# Issue #133239 — Support remote extension host profiling

[https://github.com/microsoft/vscode/issues/133239](https://github.com/microsoft/vscode/issues/133239)

## Summary

Remote extension host profiling remains missing: the Running Extensions action explicitly targets the local process, and the remote host exposes no inspection endpoint through the extension service. Keep this team-authored request open; the current source supports the reported limitation, and no verified canonical or fixing commit was found.

## Change summary

Allow users to capture CPU profiles of the remote extension host from the Running Extensions editor.

## Best solution

Provide remote-host profiling through the existing Running Extensions workflow, with clear identification of the host being recorded and usable profile attribution for remote extensions. Establish host-selection and remote-connection behavior before implementation.

Verify the saved CPU profile contains the remote workload, attribution identifies the remote extension, and the UI identifies the recorded host. Repeat in a local-only window to confirm existing local profiling remains functional; exercise remote disconnection during recording.
- **Behavior:**

  > Users working in a remote window can record a CPU profile of extensions executing in the remote extension host rather than receiving only a local-host profile. The interface makes the recorded host clear when local and remote hosts coexist. Acceptance includes a saved profile containing a known remote extension workload and useful attribution to that extension. Existing local-only recording, stopping, opening, and saving continue to work.
- **Trace:**

  > The report at https://github.com/microsoft/vscode/issues/133239 is directly supported by the current command path: StartExtensionHostProfileAction delegates to ExtensionHostProfileService.startProfiling(), which requests only ExtensionHostKind.LocalProcess. AbstractExtensionService.getInspectPorts() filters managers by kind, while RemoteExtensionHost.getInspectPort() returns undefined and enableInspectPort() returns false, so the remote endpoint is unavailable through this contract. ExtensionHostProfiler accepts a host and port, but its _distill() lookup includes only file-scheme extension locations, adding a remote attribution boundary. The service currently retains one profiling session and one last profile. The trace establishes the missing capability but does not establish remote inspector transport or connection lifecycle design. Preserve existing local profiling and profile export behavior; do not expand this request into unrelated automatic profiling or extension debugging work.
- **Open decisions:**
  - When local and remote extension hosts coexist, should Start Extension Host Profile prompt for a host, offer separate host-specific actions, or record both?
