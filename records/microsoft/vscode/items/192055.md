# Issue #192055 — TreeView reveal creates a race condition with `TreeDataProvider#getChildren`

[https://github.com/microsoft/vscode/issues/192055](https://github.com/microsoft/vscode/issues/192055)

## Summary

The underlying race condition between TreeView reveal and concurrent refresh is still present on main. The "already registered" throw was mitigated (commit 856ea291a57 makes it graceful instead of throwing), but the root cause — concurrent `_fetchChildrenNodes` calls from reveal and debounced refresh — remains unresolved. An open PR (#250239) addresses this but has not merged.

## Change summary

TreeView reveal during a concurrent refresh causes a race condition where `_fetchChildrenNodes` is called concurrently for the same parent, leading to broken tree state.

## Best solution

Review and land https://github.com/microsoft/vscode/pull/250239 (or an alternative fix) that serializes or cancels concurrent fetch operations during reveal+refresh. The token-based staleness check in `_fetchChildrenNodes` helps but doesn't cover all interleaving scenarios described by the reporter and commenters.

- **race condition fix attempt:** Commit 950ca05d5c9 ('Reapply element already registered race condition fix') added token-based staleness checks in `_fetchChildrenNodes` (lines 749–780 of extHostTreeViews.ts), but commenters confirm the race still triggers.
- **open PR:** https://github.com/microsoft/vscode/pull/250239 is open and unmerged, directly targeting this issue.
- **source trace:** In src/vs/workbench/api/common/extHostTreeViews.ts, `_fetchChildrenNodes` can still be called concurrently for the same parent from both the reveal path and the debounced refresh path.
