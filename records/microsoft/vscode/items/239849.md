# Issue #239849 — Searching `c` no longer brings up the `C` extension first

[https://github.com/microsoft/vscode/issues/239849](https://github.com/microsoft/vscode/issues/239849)

## Summary

The accepted bug remains on current main: locally installed matches are prepended without relevance sorting, so a one-character query preserves installation-list order rather than placing the strongest name match first.

## Change summary

Improve free-form extension search so the most relevant installed extension, such as C/C++ for `c`, appears before weak local matches.

## Best solution

Rank matching installed extensions before passing them to `PreferredExtensionsPagedModel`, prioritizing exact and prefix matches in extension names and display names over incidental description matches while preserving gallery relevance for the remaining results.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/extensions/browser/extensionsViews.ts`, `src/vs/workbench/contrib/extensions/test/electron-browser/extensionsViews.test.ts`
- **Validation:** Add an ExtensionsViews test with several installed extensions matching `c` through different fields and assert that the exact or strongest display-name match is first while the gallery results retain their relative order.
- **Behavior:**

  > Free-form extension search should show installed extensions before gallery-only results without leaving those installed matches in arbitrary local-list order. For query `c`, the installed C/C++ extension should rank ahead of extensions that match only weakly through a longer name or description. Explicit user-selected sort orders must remain authoritative, and gallery-only results must retain their service-provided relevance order.
- **Trace:**

  > `ExtensionsListView.queryGallery` in src/vs/workbench/contrib/extensions/browser/extensionsViews.ts calls `getPreferredExtensions` for ordinary free-form searches. That method uses broad substring predicates over each local extension's name, display name, and description but performs no scoring or sorting; `PreferredExtensionsPagedModel` then prepends the returned entries in that unchanged order. This conclusively reproduces the reported ordering defect from source. Tests in src/vs/workbench/contrib/extensions/test/electron-browser/extensionsViews.test.ts already exercise ordinary search, preferred results, and explicit sort behavior, but not relevance among local matches. Keep the boundary to ordering the locally installed preferred subset: do not replace Marketplace ranking, alter explicit `@sort` behavior, or reorder gallery-only results. The uncertainty starts with the desired relevance tiers and tie-breaking behavior for local fields.
- **Open decisions:**
  - Should local relevance emulate a general fuzzy scorer, or use explicit tiers such as exact name/display-name match, then prefix match, then other name matches, with description-only matches last?

## Evidence

- **current source:** In src/vs/workbench/contrib/extensions/browser/extensionsViews.ts, `getPreferredExtensions` filters local extensions with substring checks across name, display name, and description, then returns the resulting array without relevance sorting.
- **observable failing path:** `queryGallery` passes that unchanged local array to `PreferredExtensionsPagedModel`, whose constructor places entries at the beginning in their existing order. Therefore searching `c` cannot promote C/C++ over weaker local matches unless it already occurs earlier in `extensionsWorkbenchService.local`.
