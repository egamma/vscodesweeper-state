# Issue #241932 — macOS Configuration Profiles: Only watch for configuration if profile detected on startup

[https://github.com/microsoft/vscode/issues/241932](https://github.com/microsoft/vscode/issues/241932)

## Summary

Keep open: the native macOS watcher still starts without checking for an installed profile and watches the whole managed-preferences directory. The proposed performance benefit remains unmeasured, and startup-only detection needs to be reconciled with live policy installation.

## Change summary

Evaluate reducing macOS policy-watcher overhead by detecting profiles at startup or narrowing the watched preferences paths.

## Best solution

Measure watcher overhead on unmanaged Macs before choosing an optimization in the native policy-watcher implementation. Any change should preserve live profile installation, updates, and removal unless maintainers explicitly approve different behavior.

## Evidence

- **Current VS Code integration:** src/vs/code/electron-main/main.ts:220–238 selects NativePolicyService on macOS using the product bundle identifier, not profile presence, and also constructs NativeManagedSettingsService. src/vs/platform/policy/node/nativePolicyService.ts creates the native watcher when policy definitions change; it has no installed-profile detection gate.
- **Native implementation still contains the requested optimization gap:** package.json declares @vscode/policy-watcher ^1.6.0. In https://github.com/microsoft/vscode-policy-watcher/blob/v1.6.0/src/macos/PolicyWatcher.cc, PolicyWatcher::Execute creates and starts an FSEventStream for /Library/Managed Preferences/ before refreshing policy values. It neither gates watching on profile presence nor restricts the watch to a product-specific plist.
- **Performance benefit is not established:** https://github.com/microsoft/vscode/issues/241932 explicitly calls the improvement theoretical and supplies no measurements. The native worker waits on dispatch_semaphore_wait after refreshing policies, so an active watcher alone does not establish significant idle CPU overhead.
- **Existing live-update expectation:** The originating test plan, https://github.com/microsoft/vscode/issues/241781, says applying a new profile should be picked up automatically without relaunching VS Code and requires immediate detection of profile updates. Disabling observation when no profile exists at startup could affect that behavior.
- **Canonical and fix search:** Repository issue searches covering policy watchers, managed preferences, configuration profiles, and policy performance found no verified older open issue owning this optimization. https://github.com/microsoft/vscode/issues/245803 concerns slow Git operations with policies enabled and is a newer, closed report, not a canonical for reducing watching on unmanaged Macs. The native watcher history inspected still leaves the unconditional directory-wide stream in place; no concrete fixing commit was identified.
