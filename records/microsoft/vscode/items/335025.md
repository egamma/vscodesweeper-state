# Issue #335025 — Setting to make the "Open in Browser" button and actions always use the external browser

[https://github.com/microsoft/vscode/issues/335025](https://github.com/microsoft/vscode/issues/335025)

## Summary

Keep open: existing settings can disable localhost interception or hide the globe button, but cannot retarget the existing browser actions externally. The request has 31 upvotes and was accepted into Backlog; the older default-browser request does not cover its distinct button behavior.

## Change summary

Allow users to retain browser-opening buttons and actions while choosing their external browser as the destination.

## Best solution

Provide a consistent opt-in external destination for the existing browser-opening affordances, using the configured external browser without first creating an integrated browser tab. Settle the title-bar button's behavior when there is no URL and whether configurable file types belong in this change or a separate follow-up.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/browserView/electron-browser/features/browserTabManagementFeatures.ts`, `src/vs/workbench/contrib/browserView/electron-browser/features/browserNavigationFeatures.ts`, `src/vs/workbench/contrib/browserView/test/electron-browser/features/browserNavigationFeatures.test.ts`
- **Validation:** With an external destination selected, manually exercise the title-bar globe using the agreed URL-selection behavior, the editor-title action on a local HTML file, and localhost links from terminal and chat. Confirm external opening without an intermediate integrated tab, honoring workbench.externalBrowser for HTTP(S); include a Windows file path containing spaces. Repeat with the unchanged default destination and verify existing integrated-browser behavior. Add focused action-routing tests that assert which opener or editor receives each invocation.
- **Behavior:**

  > Users can keep the browser-opening affordances visible while choosing an external browser instead of an integrated browser tab. Supported local-file actions and localhost links should open directly at the selected destination, without requiring an integrated-browser round trip. External HTTP(S) opening should honor workbench.externalBrowser, and users who do not opt in should retain existing behavior. Acceptance must cover file-editor actions, terminal/chat links, and the agreed title-bar interaction.
- **Trace:**

  > In src/vs/workbench/contrib/browserView/electron-browser/features/browserTabManagementFeatures.ts, OpenFileInIntegratedBrowserAction constructs a BrowserViewUri editor directly, while OpenOrListBrowsersAction either lists integrated tabs or invokes OpenIntegratedBrowserAction. The latter can open without a URL and then presents the integrated URL picker, so external-mode title-bar behavior is not specified by the existing flow. LocalhostLinkOpenerContribution separately controls interception through workbench.browser.openLocalhostLinks. OpenInExternalBrowserAction in browserNavigationFeatures.ts already bypasses contributed openers but requires an existing integrated page. Preserve unrelated explicit integrated-browser and agent-tool behavior; do not treat this preference as blanket browser disablement. https://github.com/microsoft/vscode/issues/316139 concerns localhost defaults, and https://github.com/microsoft/vscode/issues/323733 concerns the Windows external-open workaround; neither replaces this request.
- **Open decisions:**
  - When external mode is selected and the title-bar globe has no explicit URL, should it prompt for a URL, open the active browser-renderable resource, or launch the external browser without a URL—and should existing integrated tabs still affect that interaction?
  - Should configurable browser-renderable file extensions requested in the comments be included in this feature, or remain a separate follow-up with the existing supported file types preserved?
