# Issue #341093 — Local harness - MCP elicitation isn't shown and requests times out

[https://github.com/microsoft/vscode/issues/341093](https://github.com/microsoft/vscode/issues/341093)

## Summary

Thanks for the detailed debugging. The race you describe is plausible in the source: after the first POST, the client opens the standalone GET SSE stream without awaiting it. It's unclear whether the server SDK should instead route the elicitation on the originating request's stream, so this stays open for a maintainer to decide where the fix belongs.

## Change summary

An MCP elicitation sent from a tool handler is sometimes lost and times out on the first attempt, because the client's standalone GET SSE stream isn't open yet.

## Best solution

In extHostMcp.ts, make the streamable-HTTP client establish the standalone GET SSE stream before the first tool call can trigger server-initiated requests, or otherwise guarantee delivery. Separately, confirm whether the MCP SDK should send elicitations on the related request's stream.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostMcp.ts`, `src/vs/workbench/api/test/common/extHostMcp.test.ts`
- **Validation:** Add a test in extHostMcp.test.ts where the first POST response is delayed, and assert the GET backchannel is open before a server-initiated request is delivered.
- **Behavior:**

  > A server-initiated elicitation sent during the first tool call is delivered to the client every time, with no timeout on the first attempt. The result should not depend on the order of the GET SSE and POST requests.
- **Trace:**

  > In extHostMcp.ts the HTTP connection calls `_attachStreamableBackchannel()` unawaited after the first successful POST, so the standalone GET may arrive after the server has already tried to send. The reporter's logs show GET arriving after the elicitation POST in the failing case. What is not established is whether the server SDK should use the request-scoped stream instead. Don't change the legacy SSE fallback or auth handling.
- **Open decisions:**
  - Should the client block the first tool request until the GET backchannel is open, or only guarantee delivery with minimal added latency?

## Evidence

- **client code path:** src/vs/workbench/api/common/extHostMcp.ts (~line 533-535): after the first successful POST (`wasUnknown`), `_attachStreamableBackchannel()` is called without await, so the GET can arrive after later POSTs.
- **reporter's logs:** Comments 3 and 4 show GET arriving after the elicitation POST in the failing run and before it in the passing run. Comment 5 shows a delay workaround on the server side.
- **open question:** The MCP spec routes server requests tied to a client request on that request's POST stream. The reporter's server SDK may be using the standalone stream, so the fix may belong in the SDK as well as in the VS Code client.
- **related issues:** https://github.com/microsoft/vscode/issues/340231 and https://github.com/microsoft/vscode/issues/340294 are Local-harness MCP issues but report different symptoms, so this isn't a duplicate of either.
