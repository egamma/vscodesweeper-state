# Issue #336483 — [Accessibility] Reliably expose scrollable regions in Sidebar via UIAutomation

[https://github.com/microsoft/vscode/issues/336483](https://github.com/microsoft/vscode/issues/336483)

## Summary

Legitimate accessibility gap for voice-control/dictation users: VS Code's custom scrollbar widget is explicitly marked `role="presentation"`, so it's invisible to UIAutomation regardless of platform; no existing issue tracks exposing ScrollPattern/scrollbar controls for sidebar and panel regions.

## Change summary

Expose scrollable regions of the Sidebar (and per a follow-up comment, Output/Terminal/Problems/Debug Console panes) via UIAutomation ScrollPattern or Scrollbar control patterns, to support voice-driven scrolling.

## Best solution

Accessibility team should evaluate whether the shared `AbstractScrollbar`/`ScrollableElement` widgets (src/vs/base/browser/ui/scrollbar/abstractScrollbar.ts, scrollableElement.ts) can safely change from `role="presentation"` to something UIA maps to a scrollbar/ScrollPattern control, without breaking screen-reader users who currently ignore that node.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/scrollbar/abstractScrollbar.ts`, `src/vs/base/browser/ui/scrollbar/scrollableElement.ts`
- **Validation:** Manual verification with a UIA inspection tool (e.g. Windows Accessibility Insights) confirming a ScrollPattern or scrollbar control is exposed for the sidebar's scrollable region after the change, without regressing NVDA/JAWS/Narrator behavior on the same widget.
- **Trace:**

  > The shared scrollbar widgets (`AbstractScrollbar`, `ScrollableElement`) set `role="presentation"` on their DOM node, which removes them from the accessibility tree and therefore from Windows UIAutomation, blocking voice-control tools (e.g. Talon) from targeting scroll regions in the sidebar and other panes. Where the uncertainty starts: whether to change the role/pattern exposed by this shared widget (risking regressions for existing screen-reader users who currently skip it), or add a separate accessible scroll affordance only for these panes.
- **Open decisions:**
  - Should the fix change the shared `role="presentation"` scrollbar widget (affecting every consumer, including editors), or be scoped narrowly to sidebar/panel containers only?
  - Should VS Code expose a UIA ScrollPattern (implying native-like scroll semantics) or a simpler Scrollbar control pattern, and does either risk changing current screen-reader (NVDA/JAWS/Narrator) behavior on these widgets?
  - Should the follow-up scope (Output/Terminal/Problems/Debug Console panes) be included in the same change or split into a separate, later issue?

## Evidence

- **root cause found in source:** src/vs/base/browser/ui/scrollbar/abstractScrollbar.ts and scrollableElement.ts both call `this.domNode.setAttribute('role', 'presentation')` on the custom scrollbar DOM node, which hides it from the accessibility tree (and thus from UIAutomation) entirely.
- **no existing tracking issue:** Candidate canonicals (font size #519, intellisense position #33752) are unrelated keyword-search false positives; no open issue specifically tracks UIA ScrollPattern/scrollbar exposure.
- **scope grew via comment:** Reporter's 2026-09-27 comment extends the ask to Output/Terminal/Problems/Debug Console panes, making this cross-cutting across several contrib areas rather than a single bounded widget change.
