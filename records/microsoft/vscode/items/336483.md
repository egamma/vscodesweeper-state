# Issue #336483 — [Accessibility] Reliably expose scrollable regions in Sidebar via UIAutomation

[https://github.com/microsoft/vscode/issues/336483](https://github.com/microsoft/vscode/issues/336483)

## Summary

Keep open: current custom scrollbars are explicitly hidden from the accessibility tree, and the inspected scrolling options do not provide the requested UIAutomation exposure. This is a distinct accessibility capability request; its Windows automation behavior needs investigation before implementation.

## Change summary

Expose sidebar scrollable regions through UIAutomation ScrollPattern or usable ScrollBar objects, with output, terminal, problems, and debug console panes also requested in the follow-up.

## Best solution

Provide discoverable, operable accessibility scrolling for workbench regions without requiring pointer targeting or changing existing screen-reader navigation. Start by inspecting the Windows UIAutomation tree for sidebar lists, then establish which shared scrolling surfaces and panel-specific implementations need support.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/scrollbar/abstractScrollbar.ts`, `src/vs/base/browser/ui/scrollbar/scrollableElement.ts`, `src/vs/base/browser/ui/list/listView.ts`, `src/vs/platform/list/browser/listService.ts`
- **Validation:** On Windows, populate Explorer, Search, and Extensions with content exceeding their viewport; inspect each region using Accessibility Insights or another UIAutomation client. Verify discovery of an operable ScrollPattern or ScrollBar object and invoke scrolling through UIAutomation, confirming that the intended region moves and reported position updates. Repeat for the requested panels and verify existing keyboard and screen-reader navigation remains intact.
- **Behavior:**

  > Voice-control software cannot reliably discover and scroll sidebar regions through UIAutomation. Scrollable Explorer, Search, and Extensions regions should expose an actionable scrolling interface, preferably ScrollPattern or alternatively usable ScrollBar objects, so assistive software can target the intended region without pointer coordinates. The reporter also requests equivalent support for output, terminal, problems, and debug console panes. Acceptance requires inspecting and invoking the exposed Windows automation interface, not merely making a scrollbar visually persistent or adding DOM attributes.
- **Trace:**

  > AbstractScrollbar in src/vs/base/browser/ui/scrollbar/abstractScrollbar.ts unconditionally assigns role='presentation' and aria-hidden='true' to custom scrollbar nodes. ScrollableElement in src/vs/base/browser/ui/scrollbar/scrollableElement.ts wraps content and these controls in a presentation-role container with hidden overflow; ListView in src/vs/base/browser/ui/list/listView.ts uses SmoothScrollableElement with its own Scrollable state. The inspected options and workbench.list scrolling settings change visual or input behavior rather than expose an automation interface. These findings identify the shared sidebar investigation path, not a proven native UIAutomation fix; uncertainty starts at Chromium's mapping of these virtualized regions and extends to the separate panel implementations. Preserve virtualization, existing keyboard navigation, and screen-reader semantics. Related traditional-scrollbar requests at https://github.com/microsoft/vscode/issues/15106 and https://github.com/microsoft/vscode/issues/337240 do not own this automation-discoverability requirement.
