# Issue #131502 — Source code downloaded via the debuggers sourceRequest creates lots of duplicate open files across debug sessions

[https://github.com/microsoft/vscode/issues/131502](https://github.com/microsoft/vscode/issues/131502)

## Summary

The cross-session duplication remains present on current main: debug-source URIs include the session ID, so otherwise identical sources necessarily become different editor resources. The auto-close setting mitigates tab accumulation but does not provide the requested source identity, editor reuse, breakpoint continuity, or history cleanup.

## Change summary

Reuse stable debugger-provided sources across debug sessions instead of opening a new read-only editor resource for every session.

## Best solution

Define an explicit, adapter-controlled stable identity contract for virtual sources, then let VS Code reuse the corresponding editor resource across sessions while resolving content through the active session. Sources without a reliable identity must remain session-scoped so different generated content is never conflated.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/common/debugSource.ts`, `src/vs/workbench/contrib/debug/common/debugContentProvider.ts`, `src/vs/workbench/contrib/debug/browser/debugSession.ts`, `src/vs/workbench/contrib/debug/common/debugProtocol.d.ts`, `src/vs/workbench/contrib/debug/test/browser/debugSource.test.ts`
- **Validation:** Extend the `Debug - Source` unit suite and run `scripts/test.sh --grep "Debug - Source"`; the selected contract must reuse one URI for the same stable source across sessions, keep unstable sources distinct, and avoid conflating sources whose content identity changes.
- **Behavior:**

  > Opening the same debugger-provided source in successive debug sessions should reuse one editor resource rather than adding duplicate tabs and history entries. The reused editor must obtain content from the applicable live session and preserve source-associated editor state such as breakpoints where the identity contract permits it. Distinct generated sources that merely share a display name or path must remain separate, and sources without a reliable stable identity must retain safe session-scoped behavior.
- **Trace:**

  > Source identity originates in `getUriFromSource` in src/vs/workbench/contrib/debug/common/debugSource.ts, which embeds both the session ID and sourceReference in the debug URI; `DebugSession.getSource` in src/vs/workbench/contrib/debug/browser/debugSession.ts then caches by that full URI. `DebugContentProvider.createOrUpdateContentModel` in src/vs/workbench/contrib/debug/common/debugContentProvider.ts decodes the same session ID to route the DAP source request, so editor identity and content-routing identity are currently coupled. The DAP declaration in src/vs/workbench/contrib/debug/common/debugProtocol.d.ts explicitly says sourceReference is valid only for one session, and path is optional. The existing close-on-end setting is a fallback mitigation and should not be removed or have its default changed as part of this work. https://github.com/microsoft/vscode/issues/85290 is related but covers disk-versus-virtual equivalence within a session; this issue's boundary is cross-session identity for virtual sources.
- **Open decisions:**
  - Which adapter-provided contract establishes stable cross-session identity: a new explicit source identity/stability field, a checksum-backed identity, or a documented path-plus-reference convention?
  - When a source reports the same stable identity but different content or checksum in a later session, should VS Code update the existing editor resource or preserve separate versioned resources?
  - Should stable editor identity be standardized in DAP for other clients, or introduced first as a VS Code-specific capability while retaining session-scoped behavior for adapters that do not opt in?

## Evidence

- **current source path:** src/vs/workbench/contrib/debug/common/debugSource.ts:getUriFromSource constructs every nonzero-sourceReference URI with `session=${sessionId}&ref=${raw.sourceReference}`. Two sessions therefore produce unequal resources even when the source name, path, reference, and contents match.
- **content-resolution dependency:** src/vs/workbench/contrib/debug/common/debugContentProvider.ts parses the session from the resource and uses that session to load the source, while src/vs/workbench/contrib/debug/browser/debugSession.ts caches sources by the complete URI. Removing the session component without redesigning this lookup would break content resolution.
- **test confirms current identity:** src/vs/workbench/contrib/debug/test/browser/debugSource.test.ts explicitly expects an internal source URI such as `debug:internalModule.js?session%3DaDebugSessionId%26ref%3D11`, confirming the session-scoped behavior on current main.
- **partial workaround:** https://github.com/microsoft/vscode/pull/199898 and follow-up https://github.com/microsoft/vscode/pull/203500 added and fixed `debug.closeReadonlyTabsOnEnd`. Current src/vs/workbench/contrib/debug/browser/debugService.ts closes session-owned debug editors only when that opt-in setting is enabled; it does not deduplicate resources or remove their history entries.
- **maintainer intent:** https://github.com/microsoft/vscode/issues/131502#issuecomment-1858737012 records a maintainer's intent to deduplicate sources across sessions, while the subsequent discussion identifies the unresolved identity problem for adapters whose sourceReference is only session-local or whose sources have no path.
- **older related issue is not canonical:** https://github.com/microsoft/vscode/issues/85290 is older and open, but reports duplicate disk-backed versus sourceRequest editors within a debugging flow, not repeated virtual-source editors across sessions. It does not satisfy the re-review requirement of the same reporter-observable symptom.
- **related protocol discussion:** https://github.com/microsoft/debug-adapter-protocol/issues/444 discussed URI capability negotiation but was closed without a protocol change after the motivating feature changed direction. It therefore does not resolve stable cross-session source identity.
