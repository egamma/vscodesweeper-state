# Issue #321881 — VS Code can become stuck reopening the Agent login window and prevent access to the normal editor

[https://github.com/microsoft/vscode/issues/321881](https://github.com/microsoft/vscode/issues/321881)

## Summary

Confirmed on current main: generic startup restoration can persist the Agents workspace as the last active window and reopen only its non-dismissible sign-in surface. Multiple users reproduced this through 1.130 on Windows and Linux, including with extensions disabled.

## Change summary

Closing the normal editor before a signed-out Agents window can make later VS Code launches restore only the blocking Agents sign-in window.

## Best solution

Ensure an ordinary launch can always reach a normal editor after this window-closing sequence, while preserving explicit Open in Agents behavior. A maintainer should choose whether Agents windows are excluded from generic restoration, accompanied by an editor window, or given a reliable escape from the signed-out gate.

## Plan brief

- **Likely files:** `src/vs/platform/windows/electron-main/windowsStateHandler.ts`, `src/vs/platform/windows/electron-main/windowsMainService.ts`, `src/vs/platform/windows/test/electron-main/windowsStateHandler.test.ts`, `src/vs/sessions/browser/sessionsAuthGate.ts`, `src/vs/sessions/test/browser/sessionsAuthGate.test.ts`
- **Validation:** Add focused window-restoration coverage for a persisted Agents workspace being the last active window, then run the relevant Windows State Storing test; if the chosen design changes the escape behavior, also run the Sessions - Auth Gate tests.
- **Behavior:**

  > After opening Agents while signed out, closing the normal editor first, closing Agents, and launching VS Code normally, the user must be able to reach a normal editor without command-line recovery. An Agents window may also be restored if that is the intended policy, but its sign-in state must not be the only accessible surface. Explicit Open in Agents and `--agents` launches must retain their current intent.
- **Trace:**

  > WindowsStateHandler.saveWindowsState() and onBeforeCloseWindow() in src/vs/platform/windows/electron-main/windowsStateHandler.ts can leave the special Agents workspace in lastActiveWindow when it is closed last. On the next argument-free launch, WindowsMainService.getPathsToOpen() calls doGetPathsFromLastSession(), which resolves that workspace like any other; openInBrowserWindow() identifies agentSessionsWorkspace and loads the Sessions workbench. SessionsAuthGate still permits a blocking window-level sign-in gate unless the experimental signed-out path is enabled and a suitable provider exists. The boundary is startup restoration and signed-out reachability: explicit Agents launches, normal workspace restoration, and provider-specific authentication requirements must not regress. The related narrower confirmation is https://github.com/microsoft/vscode/issues/330079.
- **Open decisions:**
  - Should a normal desktop launch exclude the Agents workspace from generic last-session restoration, or restore it alongside a normal editor window?
  - Should the non-dismissible Agents sign-in surface always expose a route back to the editor, independently of provider availability and experimentation settings?

## Evidence

- **confirmed reports:** The reporter reconfirmed on 1.125 and 1.130 with extensions disabled; independent comments confirm the same lockout on 1.127, 1.129, and 1.130 across Windows and Xubuntu.
- **state persistence path:** src/vs/platform/windows/electron-main/windowsStateHandler.ts saves the last remaining non-extension-development window as lastActiveWindow, including its workspace, without distinguishing the Agents workspace.
- **startup restoration path:** WindowsMainService.getPathsToOpen() and doGetPathsFromLastSession() in src/vs/platform/windows/electron-main/windowsMainService.ts restore lastActiveWindow.workspace on an argument-free launch; openInBrowserWindow() then recognizes the special agentSessionsWorkspace and loads it as a Sessions window.
- **blocking auth remains possible:** src/vs/sessions/browser/sessionsAuthGate.ts documents the Agents-window sign-in surface as a non-dismissible modal. Its signed-out escape is conditional on the chat.agentHost.allowSignedOutWhenUsable experimentation opt-in and a provider usable without GitHub, so it does not generally prevent this lockout.
- **related confirmation:** https://github.com/microsoft/vscode/issues/330079 is a later, narrower team-authored report of the same forced sign-in state under --transient; it remains open and supports the diagnosis rather than replacing this older, broader report.
