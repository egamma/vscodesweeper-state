# Issue #317481 — Feature Request: [Chronicle] Surface chat session titles and deep-links in standup/search output

[https://github.com/microsoft/vscode/issues/317481](https://github.com/microsoft/vscode/issues/317481)

## Summary

The request remains relevant on current main and should be routed to the chat area. Chronicle now derives useful summaries, but still emits raw session IDs and lacks the provider-qualified identity needed by VS Code's existing session deep-link mechanism.

## Change summary

Show recognizable chat-session titles in Chronicle output and make session references open the corresponding chat directly.

## Best solution

Define a stable session-reference contract shared by Chronicle and the chat UI: expose an authoritative display title and an openable resource for supported sessions, then have Chronicle render that title and link consistently in standup, search, and tips output while leaving unsupported external session types as labeled plain text.

- **Validation:** Add focused Chronicle store/tool tests proving that a supported session result carries its authoritative display title and openable reference, plus a chat integration check that selecting the rendered link opens that exact session; verify unsupported session types remain informative and non-clickable.
- **Behavior:**

  > Chronicle standup, search, and tips output should identify each referenced session with a human-readable title rather than relying on an opaque ID. For session types that VS Code can reopen, the reference should be clickable and open that exact session. Sessions originating from surfaces without a supported VS Code destination must remain clearly labeled without producing a broken link. Existing grouping, ordering, and result limits must remain unchanged.
- **Trace:**

  > Chronicle's output contract is prompt-defined in extensions/copilot/assets/prompts/skills/chronicle/SKILL.md, where standup and search currently render raw IDs. SessionRow in extensions/copilot/src/platform/chronicle/common/sessionStore.ts has `summary` but no authoritative title or session resource; sessionStoreTracker.ts derives that summary from the first user message. Core already supports provider-qualified `agent-host-session://` links through src/vs/platform/agentHost/common/openSessionLink.ts and its workbench opener, but Chronicle aggregates multiple agent surfaces and retains only raw IDs plus coarse host metadata. The uncertainty starts at the contract between the extension-owned session store and core chat: the implementation must not fabricate provider URIs from IDs or make non-openable cloud/CLI sessions appear clickable. No older canonical issue was found.
- **Open decisions:**
  - Should Chronicle display the authoritative chat UI title, its derived summary, or an explicit fallback hierarchy when the UI title is unavailable?
  - Which indexed session origins are guaranteed to have an openable VS Code destination, and how should unsupported CLI, coding-agent, review, or cross-device sessions be presented?
  - Should a supported link open in the current chat surface or in the Agents window, and should that destination vary by session type?

## Evidence

- **current Chronicle output:** extensions/copilot/assets/prompts/skills/chronicle/SKILL.md still formats standup sessions as `full-session-id` and search results as raw `session-id` values.
- **metadata gap:** extensions/copilot/src/platform/chronicle/common/sessionStore.ts defines SessionRow with `summary` but no title or openable session resource; extensions/copilot/assets/prompts/skills/chronicle/SKILL.md explicitly says there is no title and to use summary.
- **summary behavior:** extensions/copilot/src/extension/chronicle/vscode-node/sessionStoreTracker.ts derives `summary` from the first user request, so it is not the authoritative title shown by the chat session UI.
- **existing deep-link infrastructure:** src/vs/platform/agentHost/common/openSessionLink.ts implements `agent-host-session://<provider>/<rawSessionId>` links, and src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/openSessionLinkOpener.contribution.ts opens them. Chronicle stores only a raw ID plus coarse host/agent metadata, so it cannot safely construct this provider-qualified URI for every indexed surface.
- **canonical search:** GitHub lexical and hybrid searches for Chronicle titles, chat-session IDs, and chat-session deep links found no older open issue with the same reporter-observable request; under the re-review duplicate rule, no duplicate close is justified.
