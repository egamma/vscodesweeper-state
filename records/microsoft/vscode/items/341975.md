# Issue #341975 — Copilot harness: slow per-turn checkpointing in an existing chat, even after switching from a multi-root workspace to a single folder

[https://github.com/microsoft/vscode/issues/341975](https://github.com/microsoft/vscode/issues/341975)

## Summary

Thanks for the detailed timings. The report is complete: the checkpoint stage accounts for 58–337 s before dispatch in an existing chat, but a fresh chat takes under 4 s. I could not confirm the cause by running the code, so this stays open for the agent host owners.

## Change summary

Per-turn checkpointing in an existing Copilot-harness chat blocks message dispatch for minutes, even after the window changes from a multi-root workspace to a single folder.

## Best solution

Investigate agentHostCheckpointService and the checkpoint/changeset contribution. Check whether the checkpoint scope is retained from the original multi-root workspace, and whether per-repo git status and write-tree runs can be scoped, parallelized or made non-blocking. Also show a 'checkpointing' status in the UI.

  > A follow-up turn in an existing chat should not wait minutes on checkpointing. Checkpoint scope should match the session's current folders, and long checkpoints should be visible in the UI. Acceptance: checkpoint time in an existing chat after switching to a single folder is comparable to a fresh chat.
- **Trace:**

  > The report points to sendStages.checkpoint as the dominant cost, with many sequential git status, git add and git write-tree runs across repos. The stale-multi-root-scope hypothesis is unverified. Start by tracing how agentHostCheckpointService determines the repo roots, whether gitRepositoryRootsContribution persists them, and how the checkpoint step blocks dispatch. Do not change the semantics of checkpoint content. Related: https://github.com/microsoft/vscode/issues/341543.
