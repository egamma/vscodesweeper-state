# Issue #339621 — Dev extension host broken in serve-web

[https://github.com/microsoft/vscode/issues/339621](https://github.com/microsoft/vscode/issues/339621)

## Summary

Confirmed on current main: the security-hardening guard added in the cited security-fix commit still blocks extension-dev-host options from a `code serve-web` payload in packaged builds, so F5-debugging an extension over serve-web silently no-ops. This is a real regression, but the right fix needs a maintainer decision on how to re-admit the legitimate serve-web flow without reopening the vulnerability the guard was added for, so routing to the area team rather than closing.

## Change summary

Launching the dev extension host (F5) while running VS Code via `code serve-web` no longer loads the extension under development.

## Best solution

A maintainer who owns the web/serve-web and extension-host-debug security boundary should design a narrower check (e.g. an explicit serve-web opt-in, or trusting the payload only for connections that originated the server session) that lets `extensionDevelopmentPath` etc. through for serve-web while still blocking an arbitrary embedding page from forging the payload against a packaged build.

## Plan brief

- **Likely files:** `src/vs/workbench/services/environment/browser/environmentService.ts`
- **Validation:** A test in environmentService.test.ts (alongside the existing 'ignores extension host options from payload in production' test added by the security-fix commit) asserting extensionDevelopmentPath IS honored for a serve-web-originated payload while still being ignored for an arbitrary non-serve-web built-browser payload.
- **Behavior:**

  > Running `code serve-web`, opening a workspace, and using F5 to launch the dev extension host should load the extension under development (e.g. the helloworld sample's 'Hello World' command becomes available), matching desktop-debugging behavior. Today it silently does nothing in a packaged serve-web build. The fix must preserve the original security guarantee: a third party embedding the web workbench in an iframe/tab must still be unable to forge `extensionDevelopmentPath` et al. against someone else's running packaged instance.
- **Trace:**

  > `resolveExtensionHostDebugEnvironment()` in src/vs/workbench/services/environment/browser/environmentService.ts only processes `this.payload` (built from `options.workspaceProvider.payload` in the constructor, ~line 295) when `!this.isBuilt || this.enableSmokeTestDriver` (line 318). That condition was added in https://github.com/microsoft/vscode/commit/06a2bc84d0555f4c7ebd176809673e61fa49c6ff (PR microsoft/vscode#330308) to stop an arbitrary web page from injecting extension-dev-host options into someone else's packaged VS Code instance. For `code serve-web`, the client is a packaged (`isBuilt === true`) build and `enableSmokeTestDriver` is false, so the same guard also blocks the legitimate case where the user themself launched their own server and is debugging their own extension. The boundary: any fix must not simply remove or loosen the guard to trust the payload unconditionally in built binaries — it needs a way to distinguish 'the operator who started `serve-web` on this machine/session' from 'any page that can reach the workbench URL'.
- **Open decisions:**
  - What should gate payload-sourced extension-dev-host options in a packaged build: a new explicit `serve-web` CLI opt-in flag, a check tied to how the connection/session was established, or something else — and who signs off on the security implications?
  - Should this only apply to `code serve-web` specifically, or to any programmatic `workspaceProvider.payload` consumer in a built browser workbench?

## Evidence

- **guard still present on main:** src/vs/workbench/services/environment/browser/environmentService.ts:317-318, resolveExtensionHostDebugEnvironment(): `if (this.payload && (!this.isBuilt || this.enableSmokeTestDriver))` — verbatim unchanged at HEAD (3d5764c1) from the cited commit.
- **source of the guard:** Introduced by https://github.com/microsoft/vscode/commit/06a2bc84d0555f4c7ebd176809673e61fa49c6ff (PR microsoft/vscode#330308, 'Adopt security fixes on main'), which changed the unconditional payload read to require `!isBuilt || enableSmokeTestDriver` — this is exactly the diff the reporter links.
- **effect:** In a packaged VS Code served via `code serve-web`, `isBuilt` is true and `enableSmokeTestDriver` is false by default, so the whole for-loop over `this.payload` (which carries `extensionDevelopmentPath`, `extensionDevelopmentKind`, etc. from `options.workspaceProvider.payload`, set in the constructor) is skipped — matching the reported symptom that the extension under development never loads.
