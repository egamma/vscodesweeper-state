# Issue #337496 — opening an agents window on a machine hosting a agents tunnel will cause sessions to disappear

[https://github.com/microsoft/vscode/issues/337496](https://github.com/microsoft/vscode/issues/337496)

## Summary

Fresh, detailed report from a team member (COLLABORATOR) about pinned sessions disappearing when a machine's agent host identity switches from the integrated agent host to a standalone tunnel; team-authored issues stay open barring mechanical evidence, and there's none here yet — no comments, no fix commit, no confirmed repro.

## Change summary

Switching a remote machine from the integrated agents-window agent host to a standalone `code-insiders agent --tunnel` process causes a previously pinned session on that host to become invisible, and the local agents window keeps preferring the old (now-replaced) host identity.

## Best solution

Diagnose how host/session identity and pin state are keyed when the same physical machine is served first by the integrated agent host and then by a standalone tunnel — likely in the gateway/location-preference selection logic (tunnelGatewaySelection.ts, remoteAgentHostLocationPreferenceService.ts) and the sessions provider/pin persistence (baseAgentHostSessionsProvider.ts) — and ensure pinned sessions survive a host-type swap or are clearly reconciled instead of silently dropped.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/common/tunnelGatewaySelection.ts`, `src/vs/platform/agentHost/browser/remoteAgentHostLocationPreferenceService.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/sessions/contrib/providers/remoteAgentHost/browser/remoteAgentHostActions.ts`
- **Validation:** A test (or manual repro) confirming that a pinned session's identity/pin flag survives when a machine's agent host advertisement changes from the integrated agent host's editor endpoint to a standalone tunnel endpoint, and that the location preference doesn't silently keep pointing at a dead integrated host.
- **Behavior:**

  > When the agent host serving a given machine changes from the integrated agents-window process to a standalone tunnel (or vice versa), any session the user pinned before the switch should either remain visible/pinned, or the user should get a clear signal that the session moved/disappeared rather than silent loss. The agents window should also let the user re-point their location preference at the new host type on demand rather than getting stuck always preferring the old one.
- **Trace:**

  > The reporter's steps involve: (1) integrated agent host + remote connection, pin a session, (2) close the integrated host and start a standalone `code-insiders agent --tunnel` on the same machine, (3) start and pin a new session there, (4) reopen the agents window and restart it — the previously-pinned session is missing, and the local window keeps preferring the old (dead) host. `selectEditorGatewayEndpoint`/`selectDedicatedGatewayFallback`/`resolveGatewaySelection` in tunnelGatewaySelection.ts resolve endpoint choice per hostKey using a saved IRemoteAgentHostLocationPreferenceService preference — worth confirming whether the hostKey or preference survives a host-type change, and whether pinned-session storage in the sessions providers is keyed to an endpoint/instance identity that goes stale when the host type flips. Not yet reproduced or traced end-to-end; no fix commit exists. Nothing here should touch delegated-tunnel semantics (`inventory.delegatedInstanceId` short-circuit) which is explicitly documented as intentional.
- **Open decisions:**
  - Should a pinned session's identity be tied to the physical machine/tunnel rather than the specific agent-host process type, so it survives an integrated-to-standalone (or reverse) swap?
  - When the previously-preferred host type is gone, should the agents window silently fall back to the new host, or prompt the user (similar to the existing location-preference modal) to confirm/update their preference?
  - Is a session that 'disappears' actually deleted, or just no longer discoverable under the old identity — and if recoverable, how should the UI surface that?
