# Issue #338876 — VS Code / GitHub Copilot Chat’s Copilot CLI harness integration

[https://github.com/microsoft/vscode/issues/338876](https://github.com/microsoft/vscode/issues/338876)

## Summary

Well-documented, first-hand reproduction (exact error text, logs, and a working standalone-CLI comparison) of a Copilot CLI harness session-creation failure specific to a GHEC/enterprise tenant; source inspection finds a plausible contributing cause (a hardcoded 'https://github.com' host fallback in the auth-info resolution path) but the exact failing branch isn't confirmed, so this needs a maintainer/agent diagnosis pass before a fix.

## Change summary

Copilot CLI harness session.create fails with a 401 'Bad credentials' error for a user signed into a GitHub Enterprise Cloud (GHEC, EU data residency) tenant, while standalone Copilot CLI and standard VS Code Copilot chat work fine with the same account.

## Best solution

Trace why CopilotCLIModels/getAuthInfo's model/session auth calls 401 for GHEC tenants when the same GitHub session works for standard Copilot chat — likely candidate is the hardcoded `host: 'https://github.com'` fallback in `getAuthInfo()` (extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotCli.ts) not accounting for `ICopilotTokenStore.githubEnterpriseUri`, though the primary `resolveAuthInfoFromToken` path (from the external `@github/copilot/sdk` package) needs confirming too.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotCli.ts`, `extensions/copilot/src/platform/authentication/vscode-node/copilotTokenManager.ts`, `extensions/copilot/src/platform/authentication/common/copilotTokenStore.ts`
- **Validation:** Reproduce against a GHEC/enterprise tenant (or a mocked enterprise auth session) and confirm CopilotCLIModels/getAuthInfo resolves the correct enterprise host/token instead of 401ing; add a regression test asserting getAuthInfo returns the enterprise host when githubEnterpriseUri is set.
- **Behavior:**

  > Opening a new Copilot CLI harness session while signed into a GitHub Enterprise Cloud (GHEC) tenant should authenticate successfully and fetch available models, matching the behavior of standard VS Code Copilot chat and the standalone Copilot CLI on the same account. Currently session.create fails with a 401 'Bad credentials' error. Acceptance: a session created under a GHEC/enterprise auth context succeeds and lists models without the 401.
- **Trace:**

  > extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotCli.ts `getAuthInfo()` retrieves a GitHub session via `authentService.getGitHubSession('any', ...)` and tries `resolveAuthInfoFromToken` (from the external `@github/copilot/sdk` package); if that returns nothing it falls back to `{ type: 'token', ..., host: 'https://github.com' }`, which does not consult `ICopilotTokenStore.githubEnterpriseUri` (extensions/copilot/src/platform/authentication/common/copilotTokenStore.ts) the way `copilotTokenManager.ts` does elsewhere for enterprise auth. Diagnosis must first confirm, with a live or mocked GHEC session, whether this fallback path (vs. the SDK's own token resolution) is what's actually hit, since the SDK internals aren't visible in this checkout. Boundary: do not touch the non-enterprise (github.com) auth path, which is reported as working.

## Evidence

- **reporter repro:** Exact error 'SDK session authentication failed: Failed to fetch Copilot user info: 401 Unauthorized: {"message":"Bad credentials"}' plus extension log excerpt showing the same 401 from [CopilotCLIModels]; reporter confirms standalone `copilot` CLI 1.0.89 and standard VS Code Copilot chat succeed with the same GHEC account, isolating the failure to the CLI-harness integration.
- **hardcoded host fallback:** extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotCli.ts getAuthInfo() falls back to `{ type: 'token', token: copilotToken?.accessToken ?? '', host: 'https://github.com' }` when `resolveAuthInfoFromToken` returns no userInfo — this ignores any GHE tenant host, unlike ICopilotTokenStore.githubEnterpriseUri (extensions/copilot/src/platform/authentication/common/copilotTokenStore.ts) which the rest of the extension already tracks for enterprise auth (see copilotTokenManager.ts resolveGitHubSessionUri usage).
- **unconfirmed root cause:** The primary success path calls `resolveAuthInfoFromToken` from the external `@github/copilot/sdk` npm package (not present in this checkout), so whether the 401 stems from that SDK call, from the fallback path, or from a token-scope issue for GHEC/EU-residency tenants cannot be conclusively traced from source alone.
