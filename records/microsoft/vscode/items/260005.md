# Issue #260005 — vscode should not inject a common Env name as `BROWSER`  in terminal when ssh connect.

[https://github.com/microsoft/vscode/issues/260005](https://github.com/microsoft/vscode/issues/260005)

## Summary

The reported injection remains in current main: remote terminal environment construction sets BROWSER to VS Code's browser helper, overwriting inherited values. Keep this accepted bug open; resolving the collision needs a compatibility decision about remote browser opening.

## Change summary

Prevent VS Code's remote terminal browser integration from unexpectedly setting or overwriting the user-visible BROWSER environment variable.

## Best solution

Remote terminals should avoid unexpected BROWSER collisions while retaining an explicit way to open URLs on the local machine. Decide whether that requires changing the default injection or exposing a supported opt-out; renaming the variable alone would change the integration contract.

- **Proposed comment:**

  > Thanks for the report. Remote terminal setup still sets `BROWSER` to VS Code's local-browser helper and can overwrite an inherited value. In the remote settings for your remote OS, setting `"BROWSER": null` under `terminal.integrated.env.linux`, `terminal.integrated.env.osx`, or `terminal.integrated.env.windows` removes it from newly opened terminals, although that also disables browser-opening tools that rely on this variable. Keeping this open to resolve the collision without unexpectedly breaking remote browser opening.

- **Behavior:**

  > Opening an SSH remote terminal currently introduces BROWSER even when the user did not define it, causing scripts that test its presence to take an unexpected branch. An inherited BROWSER value is also overwritten before terminal settings are applied. The desired outcome is to prevent these unexpected collisions while providing a supported remote-to-local browser-opening workflow. Acceptance must cover absent and user-defined BROWSER values, explicit terminal environment overrides, and browser opening under the selected compatibility contract.
- **Trace:**

  > buildUserEnvironment in src/vs/server/node/extensionHostConnection.ts merges process, shell and resolver environments before assigning BROWSER to the browser helper unless without-browser-env-var is enabled. RemoteTerminalChannel in src/vs/server/node/remoteTerminalChannel.ts uses that environment for terminal creation; createTerminalEnvironment in src/vs/workbench/contrib/terminal/common/terminalEnvironment.ts preserves BROWSER through sanitization and then applies terminal settings. The source conclusively explains the reported presence check without executing the checkout. The helper's purpose is local browser opening, and buildUserEnvironment is shared with remote extension-host startup, so changing its contract can affect more than interactive terminals. The existing server argument and null-valued terminal settings are opt-outs, not proof that the default collision was fixed.
