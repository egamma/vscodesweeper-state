# Issue #211299 — a11y issue on tooltips

[https://github.com/microsoft/vscode/issues/211299](https://github.com/microsoft/vscode/issues/211299)

## Summary

Keep this canonical accessibility request open for a placement-policy decision. Current source still allows element-anchored hovers to flip below small targets, and a maintainer recently consolidated the same observable problem from https://github.com/microsoft/vscode/issues/265015 into this issue.

## Change summary

Prevent workbench tooltips from being obscured by the mouse pointer, particularly with large cursors and small icon or coverage-bar targets.

## Best solution

Establish a consistent workbench-hover placement policy that keeps informational tooltips clear of the pointer across coverage bars, sidebar icons, and toolbars while preserving keyboard access and Alt-based hover locking.

## Plan brief

- **Likely files:** `src/vs/platform/hover/browser/hoverWidget.ts`, `src/vs/platform/hover/browser/hoverService.ts`, `src/vs/platform/hover/test/browser/hoverService.test.ts`, `src/vs/workbench/contrib/testing/browser/testCoverageBars.ts`
- **Validation:** Extend src/vs/platform/hover/test/browser/hoverService.test.ts with placement cases for small targets near the top edge and verify that the resulting hover bounds do not intersect the modeled pointer-clearance region; manually confirm coverage bars and representative sidebar and toolbar icons with the normal and enlarged OS cursor.
- **Behavior:**

  > Informational workbench tooltips must remain readable without requiring the pointer to move off their target. Coverage bars, sidebar icons, and toolbar buttons should place their tooltip outside the pointer's occupied region, including when limited viewport space forces placement away from the preferred side. Keyboard-triggered hovers and Alt-based hover locking must continue to work.
- **Trace:**

  > ManagedTestCoverageBars in src/vs/workbench/contrib/testing/browser/testCoverageBars.ts uses the element hover delegate. HoverWidget.layout in src/vs/platform/hover/browser/hoverWidget.ts starts above the target and `adjustVerticalHoverPosition` flips below when the hover would cross the top edge; the resulting below-target placement can intersect a cursor over a small target. HoverService in src/vs/platform/hover/browser/hoverService.ts also has mouse-style placement with a fixed horizontal offset, showing that placement behavior is centralized but supports different consumer policies. The scope is workbench hover geometry and its representative consumers; do not alter editor-content hover semantics or remove the existing Alt-lock accessibility path. https://github.com/microsoft/vscode/issues/265015 confirms the same symptom across toolbar icons and was consolidated here.
- **Open decisions:**
  - Should pointer-safe placement become the default for every element-anchored workbench tooltip, or only for compact informational targets such as coverage bars and icon-only actions?
  - When neither above nor below placement provides adequate pointer clearance, should the tooltip move laterally, use a larger fixed clearance, or expose a user-configurable cursor offset?

## Evidence

- **current source:** src/vs/workbench/contrib/testing/browser/testCoverageBars.ts still registers coverage-bar tooltips with `getDefaultHoverDelegate('element')`; src/vs/platform/hover/browser/hoverWidget.ts defaults above the target but flips to `HoverPosition.BELOW` when there is insufficient room above, leaving the reported overlap path present on current main.
- **shared infrastructure:** src/vs/platform/hover/browser/hoverService.ts and src/vs/base/browser/ui/hover/hoverDelegateFactory.ts support both element and mouse placement. Mouse-style targeting adds a fixed horizontal offset, while vertical placement remains governed by the target and available-space logic, so this is a shared placement-policy question rather than only a coverage-bar defect.
- **maintainer direction:** In https://github.com/microsoft/vscode/issues/211299#issuecomment-2079645984, a maintainer preferred considering a global fix rather than a coverage-bars-only change; another commenter confirmed the symptom across sidebar icons with the default cursor.
- **canonical issue:** The later independently reproduced report https://github.com/microsoft/vscode/issues/265015 was closed on 2026-08-27 with `/duplicate of #211299`, explicitly establishing this issue as the canonical tracker for tooltip-below-cursor positioning.
- **conflicting precedent:** https://github.com/microsoft/vscode/issues/238614 was closed as designed with Alt-lock suggested as a workaround, but the newer maintainer duplicate routing into this still-open Backlog issue shows that the broader accessibility request remains intentionally tracked.
