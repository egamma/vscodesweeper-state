# Issue #348946 — Agent Host: let scheduled automations and remote messages activate an idle-retired SSH agent host

[https://github.com/microsoft/vscode/issues/348946](https://github.com/microsoft/vscode/issues/348946)

## Summary

Keep open: current source still lacks schedule-aware SSH host lifetime and disconnected-target activation. Existing Mission Control credentials and active-turn lifetime protection do not cover clientless scheduling without GitHub-environment registration.

## Change summary

Allow known managed remote agent hosts to activate for messages and scheduled work rather than requiring a connected Agents window.

## Best solution

Define supported on-demand activation and unattended scheduling contracts for managed hosts, preserving idle retirement, version-matched launches, and runtime authorization. Separate message-triggered reconnection from the broader clientless execution and credential-lifetime decision.

## Plan brief

- **Likely files:** `src/vs/server/node/serverAgentHostManager.ts`, `src/vs/platform/agentHost/node/agentHostAutomationService.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/sessions/contrib/remoteSessions/browser/remoteSessionMessageRouter.ts`, `src/vs/sessions/contrib/remoteSessions/browser/remoteSessionSource.ts`
- **Validation:** On a managed Linux SSH host, disconnect the last client before an automation becomes due and verify the chosen activation contract, run history, and subsequent idle retirement. From another connected host, send to a known disconnected target and verify exact-chat delivery after activation or an explicit unreachable-host error. Repeat with unavailable credentials and applicable policy restrictions to confirm authorization is preserved.
- **Behavior:**

  > Scheduled work currently waits after the last client disconnects and the SSH server retires; remote messages require the target to be connected already. The desired capability is activation of a known managed host when work requires it, without losing exact conversation identity or silently dropping messages. Acceptance must distinguish reconnect-on-message from truly clientless scheduled execution, and demonstrate that idle hosts still retire according to the agreed contract. Unreachable hosts and unavailable execution credentials must remain explicit outcomes.
- **Trace:**

  > ServerAgentHostManager::_updateLifetimeToken tracks active sessions, client connections, and GitHub-environment registration, but not future automation triggers. Its _startOnce credential installation is conditional on GitHub-environment mode; AgentService delegates scheduling readiness to CopilotAgent::isReadyForAutomation, and AgentHostAutomationService defers unavailable execution. RemoteSessionMessageRouter::resolve and remoteSessionSource.ts resolve only existing connection state and reject offline targets rather than launching them. The merged work at https://github.com/microsoft/vscode/pull/338392 and https://github.com/microsoft/vscode/pull/348787 covers active-turn lifetime and Mission Control credentials respectively, not this combination. Preserve exact host/chat identity, trust and approval checks, provider authorization, existing catch-up semantics, and version-matched managed launches. Source inspection establishes these boundaries but does not establish a clientless supervisor design or a cold-start execution result.
- **Open decisions:**
  - Should the first supported scope be message-triggered managed reconnection, or also scheduled execution with no connected client?
  - Should imminent schedules retain an otherwise idle server, or should scheduled execution require an external wake-and-retire lifecycle?
  - What explicit opt-in and administrator-governed authorization contract should permit host-owned scheduled execution independently of GitHub-environment registration?
