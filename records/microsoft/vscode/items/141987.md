# Issue #141987 — Usability: "source" (extension / owner) of a problem diagnostic not discoverable

[https://github.com/microsoft/vscode/issues/141987](https://github.com/microsoft/vscode/issues/141987)

## Summary

Keep this accepted feature request open: current source still does not carry the reporting extension's identity into diagnostic markers or expose it in Problems. The request has 33 upvotes, and the related attribution reports were consolidated into this issue rather than providing a replacement canonical.

## Change summary

Make the actual reporting extension discoverable for every extension diagnostic, independently of its optional source string or diagnostic collection name.

## Best solution

Provide framework-owned extension attribution in copied diagnostic data and a discoverable presentation in Problems and editor diagnostic surfaces, while preserving extension-supplied source descriptions. Agree on the presentation and compatibility contract before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostDiagnostics.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadDiagnostics.ts`, `src/vs/platform/markers/common/markers.ts`, `src/vs/workbench/contrib/markers/browser/markersModel.ts`, `src/vs/workbench/contrib/markers/browser/markersTreeViewer.ts`, `src/vs/workbench/contrib/markers/browser/markersTable.ts`, `src/vs/editor/contrib/hover/browser/markerHoverParticipant.ts`
- **Validation:** Use a test extension that creates unnamed and named diagnostic collections, with both absent and identical source strings across two extensions. Verify copied Problems data identifies the actual reporting extension in each case and the agreed UI exposes that identity without losing source/code information. Cover attribution propagation in extHostDiagnostics.test.ts and mainThreadDiagnostics.test.ts, then exercise Problems and editor presentation.
- **Behavior:**

  > Users can identify the actual extension that reported a diagnostic without guessing from its message, collection name, or optional source string. Copied Problems data includes framework-owned attribution even for unnamed collections and absent sources. Two extensions using the same source remain distinguishable. The agreed presentation makes attribution discoverable while retaining existing diagnostic messages, codes, and source descriptions.
- **Trace:**

  > ExtHostDiagnostics.createDiagnosticCollection in src/vs/workbench/api/common/extHostDiagnostics.ts knows the extension identifier, but its bridge forwards only collection owner and marker entries; the identifier remains in trace logging. Diagnostic.from in extHostTypeConverters.ts preserves optional source text, and the marker interfaces lack an extension-identity field. MainThreadDiagnostics assigns an extension-host origin used for forwarding and cleanup, not individual-extension attribution. Marker.toString copies those marker fields, while Problems renderers and MarkerHoverParticipant display source/code. Preserve collection lifecycle, extension-host forwarding, and extension-authored source semantics; task-generated and other non-extension markers must remain supported without fabricated attribution. The unresolved boundary is the user-facing placement and fallback behavior, not whether source text reliably identifies an extension. Related reports https://github.com/microsoft/vscode/issues/155831 and https://github.com/microsoft/vscode/issues/164498 already consolidate demand here.
- **Open decisions:**
  - When source is absent, should the extension identity appear inline as its fallback, or remain separate attribution discoverable through details or a tooltip?
  - Which surfaces should expose attribution in the first delivery: Problems and copied JSON only, or also editor hovers and Show Problem navigation?
  - Should attribution be confined to workbench marker data, or also become observable through the public diagnostics API?
