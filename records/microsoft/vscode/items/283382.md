# Issue #283382 — Nicer looking errors for response errors in panel chat

[https://github.com/microsoft/vscode/issues/283382](https://github.com/microsoft/vscode/issues/283382)

## Summary

Keep open: this team-authored, maintainer-accepted chat UX request remains explicitly tracked as ongoing work, and current main still renders ordinary response failures as bordered cards with red error icons and inline low-level diagnostics.

## Change summary

Present panel-chat response failures with calmer styling, friendlier recovery guidance, and less prominent technical diagnostics.

## Best solution

Give common transient response failures a calm, actionable presentation while retaining technical request details through a secondary disclosure or copy affordance. Clarify the retry action hierarchy so the card and response toolbar do not expose apparently redundant actions.

- **Behavior:**

  > Panel-chat response failures should communicate what happened and the useful recovery action without leading with raw request IDs, backend reasons, or an unnecessarily severe visual treatment. Technical details must remain available for diagnostics, and distinct conditions such as filtering, quota exhaustion, and rate limiting must retain appropriate messaging. The response must expose one clear retry path rather than apparently redundant retry controls, while preserving keyboard and screen-reader access.
- **Trace:**

  > Generic response errors flow through IChatResponseErrorDetails into ChatListRenderer.renderChatErrorDetails in src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts, which defaults unspecified levels to ChatErrorLevel.Error and creates ChatErrorContentPart. ChatErrorWidget in src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatErrorContentPart.ts selects the red error icon; the shared .chat-notification-widget rules in widget/media/chat.css provide the bordered card. Core agent-host error wording is assembled in src/vs/workbench/contrib/chat/common/chatErrorMessages.ts, where Failed and NetworkError include request IDs and reasons inline and Unknown retains the low-level “no response was returned” wording. Keep specialized quota, rate-limit, filtering, confirmation-button, accessibility, and diagnostic behavior intact; the uncertainty starts at the desired user-visible severity, details disclosure, and retry hierarchy. The originating discussion is https://github.com/microsoft/vscode-copilot-issues/issues/336 and the newer UI tracker is https://github.com/microsoft/vscode/issues/295788.
- **Open decisions:**
  - Should transient provider and network failures use warning/info presentation while reserving the red error treatment for non-recoverable failures, and which error categories belong in each severity?
  - Should request IDs and backend reasons be hidden behind an expandable details control, exposed only through a copy-diagnostics action, or shown both ways?
  - Which retry affordance should remain when the error card and response toolbar can both resend the request?
