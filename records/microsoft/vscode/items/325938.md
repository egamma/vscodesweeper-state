## Plan brief

- **Likely files:** `resources/linux/code.desktop`, `build/gulpfile.vscode.linux.ts`, `build/gulpfile.vscode.ts`, `src/mainImpl.ts`
- **Validation:** On Linux Mint Cinnamon X11, install the current official APT build, record xprop WM_CLASS and the installed desktop entry's StartupWMClass, launch from the menu, pin the window, close it, and relaunch from the pin. Acceptance: one correctly associated taskbar entry with the VS Code icon, including after opening another window.
- **Behavior:**

  > The reporter's official APT installation produces a separate Cinnamon taskbar entry with a generic icon instead of associating the running window with its launcher. The expected behavior is a single launcher-associated application group using the VS Code icon. Verify this on current Cinnamon X11 with both an initial launch and a pinned-launcher relaunch; another VS Code window should remain associated with the same application.
- **Trace:**

  > resources/linux/code.desktop obtains StartupWMClass from @@DESKTOP_NAME@@, which prepareDebPackage in build/gulpfile.vscode.linux.ts replaces with product.linuxDesktopName. build/gulpfile.vscode.ts packages the application name from product.nameShort and a desktopName from product.applicationName; src/mainImpl.ts also sets Electron's desktop name when the installed entry exists. These paths expose several identity inputs but do not conclusively determine the current runtime WM_CLASS or Cinnamon matching result. The checkout contains OSS branding rather than the official APT product configuration, so diagnosis must first inspect the affected packaged build. Preserve Snap-specific identity handling and avoid expanding this into configurable per-window classes, which is separate work tracked at https://github.com/microsoft/vscode/issues/284420.
