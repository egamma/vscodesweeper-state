# Issue #246722 — Go to Symbol in Workspace: Add a new setting to exclude symbols provided by dependencies

[https://github.com/microsoft/vscode/issues/246722](https://github.com/microsoft/vscode/issues/246722)

## Summary

Keep this accepted Backlog request open: current workspace-symbol search has no provider-independent control for excluding dependency symbols. The 24 upvotes and AL, C++, and generated-file examples establish demand; the verified related issues do not fully own this request.

## Change summary

Allow workspace-symbol navigation to exclude dependency symbols while retaining access to the complete symbol list.

## Best solution

Provide a consistent way to search project-owned symbols without dependency noise, preserving the existing full search. Agree on provider-side scope semantics and the user-facing control before implementation, accounting for virtual package resources and dependencies located inside workspace folders.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/search/browser/symbolsQuickAccess.ts`, `src/vs/workbench/contrib/search/common/search.ts`, `src/vs/workbench/contrib/search/browser/search.contribution.ts`, `src/vs/workbench/contrib/search/browser/searchQuickAccess.contribution.ts`, `extensions/typescript-language-features/src/typescriptServiceClient.ts`
- **Validation:** End the plan with executable picker/provider tests using mixed project and dependency symbols, including virtual URIs and dependencies inside a workspace folder. Verify the chosen project-only control excludes dependency results, full search retains them, and existing ranking, cancellation, and navigation remain unchanged; manually check AL and C++ provider behavior.
- **Behavior:**

  > Go to Symbol in Workspace can return dependency symbols ahead of project symbols, making local navigation difficult in AL and C++. Users should be able to select project-only results while retaining access to the complete list. Acceptance should include dependencies stored inside workspace folders and virtual package resources, not only files outside the workspace. The generated-file and symbol-kind requests in the discussion need an explicit scope decision rather than being silently treated as dependency exclusion.
- **Trace:**

  > SymbolsQuickAccessProvider in src/vs/workbench/contrib/search/browser/symbolsQuickAccess.ts consumes all results from getWorkspaceSymbols and applies text matching; skipLocal is declaration-kind filtering, not project-origin filtering. src/vs/workbench/contrib/search/common/search.ts aggregates providers whose query accepts only a search string and cancellation token, and whose results expose no dependency-origin field. The JavaScript/TypeScript provider already sends excludeLibrarySymbolsInNavTo in extensions/typescript-language-features/src/typescriptServiceClient.ts, establishing a provider-specific capability rather than a universal solution. Preserve the existing full search, provider cancellation, scoring, and opening behavior. The provider-first guidance at https://github.com/microsoft/vscode/issues/209902#issuecomment-2045713593 and the separate kind-filtering discussion at https://github.com/microsoft/vscode/issues/86761 are relevant design context, not duplicate ownership.
- **Open decisions:**
  - Should project-only search be a persistent setting, a separate command, or a per-search scope control while the existing command remains unchanged?
  - What defines project-owned versus dependency symbols for providers using virtual resources or packages inside workspace folders?
  - Does this request include arbitrary generated-file exclusions and symbol-kind filtering, or should those remain separate capabilities?

## Evidence

- **Accepted community demand:** https://github.com/microsoft/vscode/issues/246722 has 24 body upvotes and the Backlog milestone. The supplied May 1, 2025 bot comment confirms promotion after reaching the community threshold; https://github.com/microsoft/vscode/wiki/Issues-Triaging describes that promotion as acceptance.
- **Current picker capability:** At checkout c0f2e898b16593abb270bf06ac9f4256acf3c650, src/vs/workbench/contrib/search/browser/symbolsQuickAccess.ts calls getWorkspaceSymbols and filters by symbol/container text, with an optional skipLocal check based on symbol kind and containerName. That check concerns local declarations, not dependency ownership. Neither its configuration getter nor search.contribution.ts exposes dependency exclusion; searchQuickAccess.contribution.ts registers the # picker as workbench.action.showAllSymbols.
- **Provider contract boundary:** src/vs/workbench/contrib/search/common/search.ts defines provideWorkspaceSymbols(search, token), aggregates provider results, and deduplicates them. IWorkspaceSymbol carries a location but no dependency/project-origin classification, and the query contract has no scope option. Workspace-folder membership alone would not distinguish dependencies stored under .alpackages or generated files inside src.
- **Existing language-specific setting:** extensions/typescript-language-features/package.json registers js/ts.workspaceSymbols.excludeLibrarySymbols, defaulting to true; package.nls.json documents TypeScript 5.3+ support. src/typescriptServiceClient.ts sends it as excludeLibrarySymbolsInNavTo. This addresses JavaScript/TypeScript library symbols, not AL or C++ providers, and does not provide arbitrary exclusion of the reported src/routeTree.gen.ts file.
- **Discussion and workaround:** The supplied discussion at https://github.com/microsoft/vscode/issues/246722 requests separate workspace-only and complete searches, adds symbol-kind filtering and generated-file examples, and confirms C++ standard-library noise. The author's Advanced Tools Suite for AL Language workaround supplies workspace-only AL object navigation, but does not cover the cross-language core request.
- **Verified related issues, not canonicals:** https://github.com/microsoft/vscode/issues/86761 is open and older, but its body and discussion concern symbol-kind visibility rather than dependency origin. https://github.com/microsoft/vscode/issues/209902 is open and older, but reports excluded build results after reload that change after opening a declaration file. https://github.com/microsoft/vscode/issues/304477 concerns search.exclude and Markdown results and is newer. None establishes an older canonical with the same observable dependency-search problem under the re-review duplicate bar.
- **Existing maintainer guidance:** https://github.com/microsoft/vscode/issues/209902#issuecomment-2045713593 explains that extensions should honor exclusion settings or supply project configuration, because UI filtering spends computation before discarding results. This informs the design boundary, but does not settle this accepted request for a dependency-specific control or separate search command.
