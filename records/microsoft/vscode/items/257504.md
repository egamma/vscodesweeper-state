# Issue #257504 — NES: Word Wrap not supported

[https://github.com/microsoft/vscode/issues/257504](https://github.com/microsoft/vscode/issues/257504)

## Summary

The gap remains on current main: NES modified-line previews use non-wrapping render paths, so long edits can be clipped even when the host editor wraps. This is the older, better-scoped report for the NES symptom and should remain open in the Backlog.

## Change summary

Make NES modified-line previews respect editor word wrapping so the complete suggested change remains visible.

## Best solution

NES previews should inherit the host editor's effective wrapping behavior across both line-replacement and side-by-side presentations, with layout height, width, decorations, and hit targets following the resulting visual lines.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/inlineCompletions/browser/view/inlineEdits/inlineEditsView.ts`, `src/vs/editor/contrib/inlineCompletions/browser/view/inlineEdits/inlineEditsViews/inlineEditsLineReplacementView.ts`, `src/vs/editor/contrib/inlineCompletions/browser/view/inlineEdits/inlineEditsViews/inlineEditsSideBySideView.ts`, `src/vs/editor/contrib/inlineCompletions/test/browser/layout.test.ts`
- **Validation:** Add an inline-edits browser/layout test or component fixture using a narrow, word-wrapped editor and a long single-line replacement; verify the modified text wraps into visible visual lines without clipping, then run the targeted inline-completions test suite.
- **Behavior:**

  > When word wrap is active, an NES replacement must display the complete modified text within the available editor width rather than clipping content beyond the viewport. Both original and modified sides must remain aligned and readable, including long Markdown or TeX lines and edits near the logical line end. With wrapping disabled, existing non-wrapped behavior must remain unchanged.
- **Trace:**

  > InlineEditsView._determineView in src/vs/editor/contrib/inlineCompletions/browser/view/inlineEdits/inlineEditsView.ts selects line-replacement or side-by-side rendering according to edit shape and available width. InlineEditsLineReplacementView._modifiedLineElements renders modified logical lines without wrapped visual-line geometry, while its `_layout` derives overlay width and height from unwrapped widths and original line heights. InlineEditsSideBySideView constructs its embedded preview editor with all word-wrap options forced off and computes placement from maximum content widths. The boundary is NES preview rendering and geometry: do not alter accepted edit text, provider behavior, ordinary editor wrapping, or the separate Agent-edit path tracked by https://github.com/microsoft/vscode/issues/256329. The younger matching report https://github.com/microsoft/vscode/issues/295342 provides another acceptance scenario for long wrapped Markdown lines.

## Evidence

- **current source:** src/vs/editor/contrib/inlineCompletions/browser/view/inlineEdits/inlineEditsViews/inlineEditsSideBySideView.ts creates the modified preview editor with `wordWrap`, `wordWrapOverride1`, and `wordWrapOverride2` explicitly set to `off`.
- **current layout path:** src/vs/editor/contrib/inlineCompletions/browser/view/inlineEdits/inlineEditsViews/inlineEditsLineReplacementView.ts renders each modified logical line through `renderLines(...withSetWidth(false))`, records its unwrapped minimum width, and sizes the overlay from that width rather than wrapped visual-line geometry.
- **confirmed impact:** https://github.com/microsoft/vscode/issues/257504#issuecomment-3198318711 reports that edits beyond the visible portion of long Markdown and TeX lines cannot be inspected, and https://github.com/microsoft/vscode/issues/257504#issuecomment-3634718868 confirms the NES symptom persisted.
- **later matching report:** https://github.com/microsoft/vscode/issues/295342 is a younger open report of the same NES modified-suggestion clipping on wrapped Markdown lines, strengthening this issue as the canonical report rather than providing an older duplicate target.
