# Issue #112730 — Offer to open a workspace from empty explorer

[https://github.com/microsoft/vscode/issues/112730](https://github.com/microsoft/vscode/issues/112730)

## Summary

The requested capability remains absent on current main, and the On Deck milestone plus maintainer-supported design discussion establish this as accepted but unresolved work. No older open issue was found with the same observable request, so the stronger re-review duplicate bar is not met.

## Change summary

Expose Open Workspace from the empty Explorer through an Open Folder split button or dropdown without displacing the primary Open Folder action.

## Best solution

Keep Open Folder as the clear primary action while making Open Workspace discoverable through an accessible secondary menu, backed by a welcome-view mechanism that can consistently group related opening actions without adding more competing buttons.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/explorerViewlet.ts`, `src/vs/workbench/browser/parts/views/viewPane.ts`, `src/vs/workbench/common/views.ts`
- **Validation:** Launch Code OSS with an empty local window and verify that activating the primary control opens the folder picker, the alternate Open Workspace action opens the workspace-file picker, both actions are keyboard and screen-reader accessible, and the existing remote, web, and editor-open welcome variants retain their current behavior.
- **Behavior:**

  > In an empty Explorer, Open Folder remains the obvious primary action and continues to open the folder picker directly. Open Workspace is discoverable from the same control and opens the workspace-file picker. The grouped control must be fully keyboard navigable and expose understandable labels to assistive technology. Existing empty-Explorer behavior for remote windows, web environments, already-open editors, and unsupported workspace transitions must remain unchanged.
- **Trace:**

  > The empty Explorer welcome content is registered in src/vs/workbench/contrib/files/browser/explorerViewlet.ts, where the no-folder variants currently emit one standalone `Open Folder` command link. ViewWelcomeController.render in src/vs/workbench/browser/parts/views/viewPane.ts turns exactly one linked-text node on a line into a Button; multiple nodes fall back to inline links. IViewContentDescriptor in src/vs/workbench/common/views.ts carries content, ordering, conditions, preconditions, and secondary-button styling, but no grouped-action contract. The issue discussion considered multiple possible contracts—multiple command links, a submenu reference, and extension-contributed choices—and later related discussion at https://github.com/microsoft/vscode/issues/158530 confirmed the broader concern about competing welcome actions. Preserve the existing context-key conditions and command enablement; do not broaden this into redesigning unrelated welcome surfaces until the contribution scope is decided.
- **Open decisions:**
  - Should the alternate menu contain only the core Open Folder and Open Workspace actions, or serve as an extensible opening-actions surface for remote filesystem and repository providers?
  - If extensions can contribute choices, is that a public welcome-view contribution contract or a core-owned submenu with defined ordering and a guaranteed primary action?
