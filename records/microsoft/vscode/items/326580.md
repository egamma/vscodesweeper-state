# Issue #326580 — Linux desktop entry bypasses /usr/bin/code wrapper and causes extension initialization failures

[https://github.com/microsoft/vscode/issues/326580](https://github.com/microsoft/vscode/issues/326580)

## Summary

Plausible core bug: VS Code resolves the user shell environment for the extension host only when NOT launched via the CLI wrapper (isLaunchedFromCli checks VSCODE_CLI, set by cli.js but not when the desktop entry launches the Electron binary directly) — this is the mechanism that plausibly explains why a spawned subprocess (codex app-server) behaves differently depending on launch path, but I could not execute a live reproduction to confirm it, so this needs a maintainer/community confirmation rather than a close.

## Change summary

Extensions that spawn subprocesses (here, the Codex extension's app-server) hang on Linux when VS Code is launched via the packaged .desktop entry (direct Electron binary) but work when launched via the /usr/bin/code CLI wrapper.

## Best solution

Route to the extension-host/environment area for investigation of src/vs/platform/shell/node/shellEnv.ts and src/vs/code/electron-main/app.ts#resolveShellEnvironment — specifically whether shell-env resolution timing/content differs meaningfully between GUI-launch (desktop entry) and CLI-launch (/usr/bin/code) paths, and whether the extension host waits correctly on IShellEnvironmentService.getShellEnv() before spawning child processes.

## Evidence

- **wrapper vs desktop entry:** resources/linux/code.desktop uses Exec=@@EXEC@@ which build/gulpfile.vscode.linux.ts substitutes to /usr/share/<app>/<app> (direct Electron binary), while /usr/bin/code (resources/linux/bin/code.sh) invokes cli.js via ELECTRON_RUN_AS_NODE=1, and src/cli.ts sets process.env['VSCODE_CLI'] = '1' before the app process starts.
- **env-resolution gate:** src/vs/platform/shell/node/shellEnv.ts getResolvedShellEnv() skips resolving a login-shell environment when isLaunchedFromCli(env) is true (VSCODE_CLI==='1'), i.e. behaves differently for the two launch paths; extension host env comes from IShellEnvironmentService.getShellEnv() (src/vs/workbench/services/extensions/electron-browser/localProcessExtensionHost.ts:227), which is fed by this same resolution.
- **independent confirmations:** Reproduced independently on Linux Mint and KDE Neon by the reporter; commenter crliu3227 confirms a related failure mode with Remote-SSH; two open openai/codex issues (https://github.com/openai/codex/issues/34308, https://github.com/openai/codex/issues/34184) describe the same Codex-hangs-in-VS-Code-on-Linux symptom.
