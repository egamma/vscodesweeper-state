# Issue #326580 — Linux desktop entry bypasses /usr/bin/code wrapper and causes extension initialization failures

[https://github.com/microsoft/vscode/issues/326580](https://github.com/microsoft/vscode/issues/326580)

## Summary

The desktop entry using the direct Electron binary is intentional and long-standing. VS Code already resolves the shell environment at startup when not launched from CLI (via `getResolvedShellEnv` in `src/vs/platform/shell/node/shellEnv.ts`). The Codex extension's failure to initialize in this standard launch path is an extension-side bug.

## Change summary

The OpenAI Codex extension hangs during initialization when VS Code is launched from the Linux desktop entry rather than the terminal CLI wrapper.

## Best solution

Report to the Codex extension maintainers at https://github.com/openai/codex — the extension needs to handle VS Code's standard desktop-launch environment resolution (which may complete asynchronously after extension activation). The desktop entry's use of `/usr/share/code/code` is by design; VS Code spawns a login shell to resolve PATH and other variables in this path.

  > Thanks for the detailed report. The desktop entry using `/usr/share/code/code` (the direct Electron binary) rather than the CLI wrapper is intentional and long-standing. When VS Code detects it wasn't launched from a CLI (no `VSCODE_CLI` env variable), it explicitly resolves the user's shell environment by spawning a login shell at startup (`src/vs/platform/shell/node/shellEnv.ts`). This provides PATH and other variables that extensions may need.
  > 
  > The Codex extension's failure to initialize in this standard launch path is an extension-side issue — likely a timing problem where it tries to spawn its server before VS Code's shell environment resolution completes, or an issue with how the extension locates its binary.
  > 
  > Since this only reproduces with the Codex extension (and you confirmed it doesn't occur with extensions disabled), I'd recommend reporting it to the extension's maintainers at https://github.com/openai/codex — there are already related reports there (https://github.com/openai/codex/issues/34308).
  > 
  > Your workaround of changing the desktop entry to use `/usr/bin/code` works because that path sets `VSCODE_CLI=1`, which tells VS Code to skip the async shell env resolution (the terminal already provided the environment). The extension likely needs to properly await the environment or use a more robust binary discovery mechanism.
