# Issue #326580 — Linux desktop entry bypasses /usr/bin/code wrapper and causes extension initialization failures

[https://github.com/microsoft/vscode/issues/326580](https://github.com/microsoft/vscode/issues/326580)

## Summary

Keep open to diagnose the launch-dependent extension initialization failure: another user independently confirmed the desktop-entry workaround, and current packaging still launches the raw executable. The source establishes different environment-resolution paths, but does not establish whether VS Code or Codex owns the failing handshake.

## Change summary

Codex initialization hangs when VS Code starts from the packaged Linux desktop entry but succeeds through the CLI wrapper.

## Best solution

Identify the environment or process-launch difference responsible for the handshake failure, then correct it in the owning component so supported desktop launches initialize extensions reliably. Do not change all desktop entries to the CLI wrapper without establishing why that bypass helps and checking URL-handler and Remote-SSH behavior.

## Evidence

- **Concrete reproduction and disputed remote scope:** https://github.com/microsoft/vscode/issues/326580 supplies package versions, two Linux distributions, initialization logs, fresh-profile troubleshooting, and desktop-versus-CLI steps. The reporter claims local and Remote-SSH coverage, but the second comment says the workaround appears ineffective for Remote-SSH; remote behavior remains unresolved.
- **Independent confirmation:** https://github.com/openai/codex/issues/34308#issuecomment-5042903167 independently confirms that replacing the desktop entry's raw-executable command with /usr/bin/code resolves the failure. This corroborates the reported symptom, not a current-main source diagnosis.
- **Current packaging:** build/gulpfile.vscode.linux.ts substitutes /usr/share/${product.applicationName}/${product.applicationName} for @@EXEC@@ in the ordinary desktop and URL-handler templates. resources/linux/code.desktop uses that placeholder for normal and new-window launches; resources/linux/code-url-handler.desktop uses it for --open-url.
- **Launch paths are intentionally distinct:** resources/linux/bin/code.sh invokes the executable with ELECTRON_RUN_AS_NODE=1 and resources/app/out/cli.js. src/cli.ts sets VSCODE_CLI=1; src/vs/code/node/cli.ts removes ELECTRON_RUN_AS_NODE before launching the GUI. src/vs/platform/shell/node/shellEnv.ts:getResolvedShellEnv skips shell resolution for CLI launches unless --force-user-env is supplied, while ordinary Linux GUI launches resolve the shell environment. These differences are plausible diagnostic leads, not proof that bypassing the wrapper is itself a defect.
- **Related closure does not prove resolution:** https://github.com/openai/codex/issues/34184 was closed after its reporter said the problem disappeared. That thread also includes plugin/network errors and a different workaround; it provides neither a fixing commit nor confirmation that this issue's desktop-launch dependency was corrected. https://github.com/openai/codex/issues/34308 remains open.
- **Canonical search:** Open-issue searches for desktop-entry, launcher, Codex, and Linux shell-environment failures found no verified older canonical owning this symptom. https://github.com/microsoft/vscode/issues/337589 concerns renamed desktop files breaking pinned shortcuts, not extension initialization after a successful launch, and is newer than this report.
