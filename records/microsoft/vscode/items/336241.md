# Issue #336241 — Copilot hangs on screenshot / image viewing

[https://github.com/microsoft/vscode/issues/336241](https://github.com/microsoft/vscode/issues/336241)

## Summary

Keep open as a high-impact Copilot core bug: repeated logs from multiple sessions show client-dispatched tool completions being forwarded successfully while the corresponding session completion is lost, leaving turns indefinitely blocked. The report is detailed enough to investigate without further reporter input, and no verified canonical or merged fix is identified.

## Change summary

Copilot agent turns can remain indefinitely in progress after a client tool succeeds because the completion is not consumed by the session.

## Best solution

Trace and harden the client-dispatch completion path in the Agent Host so every accepted tool completion settles the matching pending tool call exactly once, with a bounded timeout and a visible recoverable error if acknowledgment fails.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost`, `extensions/copilot`
- **Validation:** Add an Agent Host protocol test that dispatches a client tool, delivers its successful completion across the relevant timing boundaries, and asserts the pending tool call settles and the turn continues; add a timeout-path case asserting a visible error instead of an indefinitely active turn.
- **Behavior:**

  > After a client-dispatched Copilot tool completes successfully, the matching agent turn must resume exactly once and must not remain indefinitely in progress. This must hold for image/browser tools and ordinary file tools, across supported models. If completion cannot be acknowledged within a bounded interval, the turn must terminate with a visible, recoverable error rather than silently hanging.
- **Trace:**

  > The reporter's Agent Host logs show `AgentSideEffects` forwarding a client tool completion with `source=client-dispatch` and `success=true`, but the matching session-level `Tool completed: <id>` event is absent for the stalled call while adjacent calls complete normally. The failure spans screenshotPage and view tools and multiple providers, placing the investigation in the client-dispatch/AHP completion handoff rather than a tool implementation or one model. Related issues https://github.com/microsoft/vscode/issues/335378 and https://github.com/microsoft/vscode/issues/321432 may share pending-response infrastructure, but neither is verified here as the same observable defect. Preserve normal exactly-once completion behavior and avoid model-specific handling; the uncertainty begins at which transport, pending-call registry, or lifecycle transition drops or indefinitely waits on the completion.
- **Open decisions:**
  - What user-visible timeout and recovery behavior should apply when a successfully forwarded tool completion is not acknowledged by the session?
