# Issue #135792 — Deleted files from explorer should match styling from deletions on disk

[https://github.com/microsoft/vscode/issues/135792](https://github.com/microsoft/vscode/issues/135792)

## Summary

The styling gap remains: opening a deleted file from SCM still supplies a literal “(Deleted)” tab title, while orphaned file editors receive a strikethrough decoration. Keep this accepted polish item open; no verified older canonical owns the same observable mismatch.

## Change summary

Use the existing deleted-file visual treatment for tabs opened from SCM instead of appending “(Deleted)” to their names.

## Best solution

SCM deletion previews should communicate deletion through the shared tab decoration and hover treatment while retaining access to the historical contents. Establish how that treatment applies to Git revision resources without incorrectly marking ordinary historical revisions as deleted.

- **Reason:** Reusing the established deletion treatment makes equivalent file states visually consistent without adding another UI surface or setting.

## Plan brief

- **Likely files:** `extensions/git/src/repository.ts`, `extensions/git/src/decorationProvider.ts`, `src/vs/workbench/browser/labels.ts`, `src/vs/workbench/services/textfile/browser/textFileService.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** In a Git repository with a committed file, compare an already-open tab after deleting the file on disk with the preview opened by clicking its deletion in SCM. Repeat with Explorer deletion and both unstaged and staged deletions: the SCM preview must use the established strikethrough/hover treatment without a literal '(Deleted)' suffix and still display the historical contents. Check that ordinary historical revisions and modified-file previews retain their existing titles and styling.
- **Behavior:**

  > A deleted tracked file opened from SCM currently displays a filename followed by '(Deleted)', unlike the shared decoration treatment used for an open file deleted on disk. The finished behavior should convey deletion through the established tab styling and hover rather than the literal suffix. Both staged and unstaged deletion previews must remain readable. Ordinary historical revisions and other SCM statuses must not acquire deletion styling.
- **Trace:**

  > ResourceCommandResolver in extensions/git/src/repository.ts constructs the '(Deleted)' title and opens the HEAD Git URI for Status.DELETED and Status.INDEX_DELETED. Git SCM rows already carry strikeThrough, but the separate FileDecoration returned by Resource.resourceDecoration does not, and the public FileDecoration contract in src/vscode-dts/vscode.d.ts has no such property. GitDecorationProvider forwards deletion decorations to the unstaged preview URI, while TextFileService provides the established strikethrough treatment only for orphaned managed text-file models; ResourceLabel consumes that internal decoration metadata. These paths establish the remaining mismatch without executing the UI. The uncertainty starts at how deletion-preview identity and styling can cross the extension/workbench boundary without affecting unrelated readable historical revisions; the relevant editor-opening bridge and other decoration consumers still need tracing. Preserve historical content access and unrelated SCM titles. The design precedent is https://github.com/microsoft/vscode/issues/130526; https://github.com/microsoft/vscode/issues/179031 describes a related but distinct restoration-status problem.

## Evidence

- **Current SCM title path:** extensions/git/src/repository.ts:534–560, 616–625, 661–675: ResourceCommandResolver.getTitle returns '{0} (Deleted)' for Status.DELETED and Status.INDEX_DELETED. Those states resolve to a readable HEAD Git URI, and resolveChangeCommand passes the explicit title to vscode.open.
- **Existing deletion treatment:** src/vs/workbench/services/textfile/browser/textFileService.ts:124–158 supplies strikethrough, listErrorForeground, and a 'Deleted' tooltip for orphaned text-file models. src/vs/workbench/browser/labels.ts:688–705 consumes decoration.strikethrough. This covers orphaned file editors, not automatically the readable historical Git resource opened from SCM.
- **Partial capability is not coverage:** extensions/git/src/repository.ts:252–279 already supplies strikeThrough for deleted SCM resource rows, but resourceDecoration at lines 312–316 constructs a FileDecoration containing badge, tooltip, and color only. extensions/git/src/decorationProvider.ts:137–147 forwards that decoration to the deleted working-tree preview URI. src/vscode-dts/vscode.d.ts:8251–8281 exposes no strikethrough property on FileDecoration, so removing the title suffix alone would not deliver the requested treatment.
