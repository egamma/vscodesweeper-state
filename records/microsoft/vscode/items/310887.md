# Issue #310887 — Remote SSH + Remote Tunnel = Failed tunnel on wrong machine

[https://github.com/microsoft/vscode/issues/310887](https://github.com/microsoft/vscode/issues/310887)

## Summary

Keep open for investigation of Windows tunnel startup recovery: the reporter restored connectivity by deleting the local lock file, but that workaround does not establish a product fix. Desktop tunnel coordination has changed since the report; the supplied setup steps, logs, and recovery sequence suffice to retest, although the initial failure trigger remains uncertain.

## Change summary

Remote Tunnel Access repeatedly fails with Windows singleton pipe access errors after an unsuccessful setup, requiring manual deletion of tunnel-stable.lock to recover.

## Best solution

Make built-in Windows tunnel startup recover safely from failed setup without manual lock-file deletion, while preserving ownership of any live tunnel. Diagnose the singleton lock and named-pipe state first; the reporter explicitly accepts hosting the local machine, so changing which machine hosts the tunnel is not required.

- **Trace:**

  > The desktop IRemoteTunnelService is registered in the local shared process by src/vs/platform/remoteTunnel/electron-browser/remoteTunnelService.ts; tunnel launches now run through TunnelProcessCoordinator.
