# Issue #228750 — URI not properly serialized when sent to webworker

[https://github.com/microsoft/vscode/issues/228750](https://github.com/microsoft/vscode/issues/228750)

## Summary

The generic web-worker transport still does not preserve URI marshalling metadata; local file search continues to carry the explicit workaround that motivated this team-authored engineering-debt issue. Keep it open for a protocol-level design decision.

## Change summary

Make URI-containing arguments and results retain enough serialization metadata to be revived correctly across the web-worker RPC boundary.

## Best solution

Define and test a consistent serialization contract for web-worker requests, replies, and events so nested URIs round-trip as URI instances without feature-specific revival code, while preserving structured-clone support for transferable values.

## Plan brief

- **Likely files:** `src/vs/base/common/worker/webWorker.ts`, `src/vs/base/common/marshalling.ts`, `src/vs/workbench/services/search/worker/localFileSearch.ts`
- **Validation:** Add and run a targeted base worker test that round-trips nested URIs through requests, replies, and events while retaining ArrayBuffer transfer behavior; then verify vscode.dev local-folder search no longer needs search-specific URI revival.
- **Behavior:**

  > Values passed through the web-worker RPC API must preserve supported marshalled types, including URIs nested in objects and arrays. Receivers should observe URI instances consistently for request arguments, replies, and events. ArrayBuffer transfer behavior and ordinary structured-clone-compatible values must remain intact. Acceptance includes a worker round-trip test and successful local-folder search on vscode.dev without feature-specific URI handling.
- **Trace:**

  > WebWorkerProtocol in src/vs/base/common/worker/webWorker.ts wraps arguments and results in message classes and passes them directly to postMessage. URI.toJSON() in src/vs/base/common/uri.ts supplies `$mid`, but structured clone does not invoke that method; revive() in src/vs/base/common/marshalling.ts therefore cannot recognize the cloned URI-shaped object. Local search compensates in reviveFolderQuery() in src/vs/workbench/services/search/worker/localFileSearch.ts by calling URI.revive on known fields. Commit aae780bf4347d88d6676630aee619d0bd5882655 introduced that workaround for https://github.com/microsoft/vscode/issues/227742, and no later generic fix referencing this issue was found. The boundary is the shared worker protocol: transferable objects, errors, events, and existing worker clients must not regress.
- **Open decisions:**
  - Should the worker protocol adopt explicit serialization envelopes for supported marshalled types, or transform URI values while retaining native structured clone for the rest of each message?
  - Which directions and message kinds must guarantee revival: request arguments, replies, events, subscription arguments, or all of them?
  - How should serialization preserve ArrayBuffer transfer semantics and avoid costly deep traversal of large worker messages?

## Evidence

- **current transport:** src/vs/base/common/worker/webWorker.ts sends RequestMessage, ReplyMessage, and EventMessage objects directly through postMessage; it performs no generic marshalling or URI transformation before structured clone.
- **marshalling mismatch:** src/vs/base/common/uri.ts adds `$mid: MarshalledId.Uri` through URI.toJSON(), while src/vs/base/common/marshalling.ts revives URIs only when `$mid` is present. Structured clone does not invoke toJSON(), leaving revive() without its URI discriminator.
- **workaround remains:** src/vs/workbench/services/search/worker/localFileSearch.ts still uses reviveFolderQuery() to call URI.revive explicitly for folder and exclude-pattern URIs, with a TODO documenting that generic revive() does not work.
- **workaround origin:** Commit aae780bf4347d88d6676630aee619d0bd5882655 added the explicit local-file-search revival for https://github.com/microsoft/vscode/issues/227742 before this issue was filed; it does not reference or complete https://github.com/microsoft/vscode/issues/228750.
- **maintainer diagnosis:** The existing comment confirms that web-worker RPC has historically relied on structured clone rather than the JSON-based marshalling path.
