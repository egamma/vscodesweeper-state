# Issue #228750 — URI not properly serialized when sent to webworker

[https://github.com/microsoft/vscode/issues/228750](https://github.com/microsoft/vscode/issues/228750)

## Summary

Keep this team-authored Backlog debt open: current main still relies on structured cloning without URI marshalling, while local file search and other worker consumers explicitly revive URI-shaped values as workarounds.

## Change summary

Make URI values retain their serialization semantics when crossing VS Code's generic web-worker protocol.

## Best solution

Define and validate a consistent worker-transport contract in which URI arguments, results, and events can be revived without per-consumer workarounds, while preserving native structured-clone behavior and transferable ArrayBuffers.

## Plan brief

- **Likely files:** `src/vs/base/common/worker/webWorker.ts`, `src/vs/base/common/marshalling.ts`, `src/vs/base/common/uri.ts`, `src/vs/workbench/services/search/worker/localFileSearch.ts`
- **Validation:** Add a loopback worker-protocol test that sends and returns nested URI values through request, reply, and event paths, verifies they revive with the original components, and confirms ArrayBuffer transfer and ordinary structured-cloneable values remain intact.
- **Behavior:**

  > Values sent through an IWebWorker channel should retain the semantics promised by VS Code's transport abstractions. In particular, nested URI arguments, results, and events must arrive in a form that generic marshalling can revive, without each consumer manually walking its payload. Ordinary structured-cloneable values and transferable ArrayBuffers must continue to work unchanged.
- **Trace:**

  > WebWorkerProtocol._send in src/vs/base/common/worker/webWorker.ts passes Message objects directly to postMessage, and the receive path dispatches cloned arguments and results without marshalling. URI serialization in src/vs/base/common/uri.ts depends on Uri.toJSON adding MarshalledId.Uri, while revive in src/vs/base/common/marshalling.ts requires that marker; structured cloning does not invoke toJSON. LocalFileSearchWorker therefore manually revives URI-bearing fields in src/vs/workbench/services/search/worker/localFileSearch.ts, and the TextMate worker contains similar explicit revival. https://github.com/microsoft/vscode/pull/228519 fixed the immediate local-search regression but deliberately did not resolve this shared transport behavior. The boundary is the generic worker protocol: preserve transfer-list handling, native structured-clone support, channel behavior, and existing non-URI payload semantics.

## Evidence

- **current transport:** src/vs/base/common/worker/webWorker.ts WebWorkerProtocol._send forwards request and reply objects directly to postMessage; incoming arguments, results, and events are dispatched without a marshalling or revival pass.
- **URI marshalling gap:** src/vs/base/common/marshalling.ts revive only recognizes a URI when `$mid` is MarshalledId.Uri, while src/vs/base/common/uri.ts adds that marker through Uri.toJSON; the structured-clone path does not invoke toJSON.
- **remaining workaround:** src/vs/workbench/services/search/worker/localFileSearch.ts reviveFolderQuery explicitly applies URI.revive to folder, exclude-pattern folders, and extra file resources, with a TODO asking why generic revive cannot be used.
- **broader pattern:** src/vs/workbench/services/textMate/browser/backgroundTokenization/worker/textMateTokenizationWorker.worker.ts also explicitly calls URI.revive for worker-delivered URI components, showing that the transport limitation is not isolated to local file search.
- **linked symptom fix:** https://github.com/microsoft/vscode/pull/228519 fixed https://github.com/microsoft/vscode/issues/227742 with a localized search workaround; its description explicitly leaves the general serialization problem for a longer-term solution and does not reference this issue.
