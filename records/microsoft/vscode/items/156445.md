# Issue #156445 — Allow to merge to a resulting file that does not exist

[https://github.com/microsoft/vscode/issues/156445](https://github.com/microsoft/vscode/issues/156445)

## Summary

Keep open: current source still requires an existing merge-result file, and the discussion establishes a concrete need from external SCM integrations. The remaining product decision is when to create the destination and what cancelling the merge should leave behind.

## Change summary

Allow a four-path merge invocation to open successfully when the specified result file does not yet exist.

## Best solution

Support a missing destination in the merge editor and its CLI entry points without requiring users to pre-create it. Settle creation and cancellation semantics explicitly, accounting for SCM tools that interpret the destination's existence as a completed merge.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mergeEditor/browser/mergeEditorInput.ts`, `src/vs/workbench/contrib/mergeEditor/browser/mergeEditorInputModel.ts`, `src/vs/workbench/contrib/mergeEditor/browser/commands/commands.ts`, `src/vs/workbench/browser/layout.ts`, `src/vs/workbench/electron-browser/window.ts`
- **Validation:** With three existing input/base files and an absent fourth destination, run code --merge input1 input2 base result in both a fresh and an existing window. Verify the merge editor opens, saving or accepting writes the merged output to the specified path, and discarding follows the agreed destination-existence contract. Repeat with an existing destination to verify unchanged behavior.
- **Behavior:**

  > A four-path merge invocation should open the merge editor even when the supplied destination does not exist, without requiring manual file creation. Saving or accepting should produce the merged result at that destination. The session must establish whether opening creates a file immediately or defers creation, and what discarding leaves on disk, because SCM integrations may use file existence to identify successful completion. Existing-destination workflows must retain their current behavior; omitting the fourth argument is outside this request.
- **Trace:**

  > pathsToEditors in src/vs/workbench/common/editor.ts represents missing paths with forceUntitled, but the merge-input construction in browser/layout.ts and electron-browser/window.ts retains only the result URI. MergeEditorInput.resolve delegates to one of the factories in mergeEditorInputModel.ts, and both resolve args.result through ITextModelService before creating the merge model. The resolver uses the text-file service for file URIs, whose initial resolution propagates FILE_NOT_FOUND. Temporary working-copy mode is therefore not an existing workaround for an absent destination. WorkspaceMergeEditorModeFactory also saves the resolved destination before merge initialization, so creation and discard semantics need an explicit product contract. Preserve existing-result behavior and do not expand the work into omitted-output CLI support or new exit-code semantics. https://github.com/microsoft/vscode/issues/156456 tracks the related omitted-output request but is closed; it is not a duplicate canonical.
- **Open decisions:**
  - Should a missing merge destination be created when the editor opens, or remain absent until the user saves or accepts the merge, with discarding leaving no file?
