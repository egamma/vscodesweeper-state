# Issue #333392 — Shared process crashes at startup when child helper executable vsce-sign.exe is blocked by enterprise policy

[https://github.com/microsoft/vscode/issues/333392](https://github.com/microsoft/vscode/issues/333392)

## Summary

Plausible, well-described robustness gap (a blocked signing helper apparently takes down the whole shared process), but I can't confirm the exact failure path from source alone — the JS-level call site already wraps both the module load and the verify() call in try/catch, so a clean JS exception wouldn't crash the process; the reported crash more likely comes from the OS/EDR force-terminating the process tree when it blocks the child executable, which is outside what code-reading can confirm. Requesting the shared-process log and a check of a known workaround setting before deciding next steps.

## Change summary

In environments where enterprise endpoint policy blocks the vsce-sign.exe helper VS Code spawns for extension signature verification, the shared process crashes at startup instead of degrading gracefully with a clear diagnostic.

## Best solution

Have the reporter confirm whether disabling `extensions.verifySignature` avoids the crash and attach the shared-process log around the crash; if confirmed, the signature-verification code path (src/vs/platform/extensionManagement/node/extensionSignatureVerificationService.ts, invoked from the shared process per src/vs/code/electron-utility/sharedProcess/contrib/extensions.ts) needs additional isolation/handling for a blocked child-process spawn so a policy block degrades to 'verification skipped' rather than terminating the whole process.
