# Issue #335929 — Setting `permissions.ask` breaks all auto-allow settings in all GitHub Copilot Harnesses

[https://github.com/microsoft/vscode/issues/335929](https://github.com/microsoft/vscode/issues/335929)

## Summary

Filed hours ago with only the auto-bot reply so far; the reported behavior — any `permissions.ask` rule flipping the whole session into a managed-approval mode that overrides default auto-allow and drops the 'Allow for session' option — matches this repo's own documented description of how the Copilot SDK/runtime evaluates managed settings, and the reporter confirms it reproduces identically in the standalone Copilot CLI and App, so the root cause looks upstream in the shared SDK rather than in VS Code's own code.

## Change summary

Setting any `permissions.ask` rule in `managed-settings.json` makes the Copilot runtime require approval (with only 'Allow once') for every unmatched action, defeating existing default auto-allow settings, across all Copilot harnesses.

## Best solution

Forward this to the Copilot Agent/SDK team that owns managed-settings evaluation: `src/vs/platform/policy/common/copilotManagedSettings.ts` explicitly documents that 'contributing any rule at all makes the runtime's managed policy active,' which requires approval for unmatched shell/read/write/URL/factory requests and deliberately avoids emitting an `allow` list because the runtime treats a covered `allow` entry as unconditional grant rather than a scoping hint — so the fix (letting an `ask` list coexist with the normal auto-approve defaults) has to happen in the SDK's rule-resolution semantics, not in VS Code's settings bridge.
