# Issue #116544 — Active/Inactive tab have no different opacity (git decoration)

[https://github.com/microsoft/vscode/issues/116544](https://github.com/microsoft/vscode/issues/116544)

## Summary

Keep open: current tab styling still applies file-decoration colors without distinguishing active and inactive labels. Existing settings offer workarounds, not the requested distinction while retaining decorations; no eligible open canonical or concrete fixing commit was found.

## Change summary

Visually distinguish active and inactive editor-tab labels while preserving Git and other file-decoration colors.

## Best solution

Provide a theme-aware distinction between active and inactive decorated tab labels in the editor-tabs surface, preserving decoration meaning and high-contrast readability. Agree on the theming contract before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts`, `src/vs/workbench/browser/parts/editor/media/multieditortabscontrol.css`, `src/vs/workbench/common/theme.ts`
- **Validation:** In a running development build, open several Git-modified files with decoration colors enabled and switch the active tab; repeat with diagnostic-colored files. Confirm that inactive decorated labels are distinguishable from the active label while decoration meaning remains visible, across dark, light and high-contrast themes and focused/unfocused editor groups. Check that disabling decoration colors preserves existing foreground behavior.
- **Behavior:**

  > Decorated editor-tab labels currently retain the same decoration color when switching between active and inactive tabs. The desired result is a visible active/inactive label distinction without disabling Git or diagnostic decoration colors. Acceptance must cover both decoration sources, theme readability and editor-group focus states. Undecorated tabs and the existing decoration-disable setting must retain their behavior.
- **Trace:**

  > MultiEditorTabsControl forwards the decoration-colors option to ResourceLabel without activity-dependent treatment. ResourceLabel applies a decoration-specific color class, whose rules in DecorationsService supply a color independently of the parent tab's active/inactive foreground tokens. The existing inactive foreground transparency therefore does not affect decorated labels. Related reports https://github.com/microsoft/vscode/issues/120345 and https://github.com/microsoft/vscode/issues/123251 corroborate the same gap but are closed, newer reports, not duplicate targets. Keep the work scoped to editor-tab presentation; do not globally dim decorations in Explorer or other resource-label consumers. The remaining uncertainty is the user-facing theming contract, not whether disabling decorations provides equivalent coverage.
- **Open decisions:**
  - Should inactive decoration emphasis follow the existing tab foreground transparency automatically, or be independently configurable through theme color tokens?
