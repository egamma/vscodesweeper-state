# Issue #226734 — Consider to support streaming for file search results

[https://github.com/microsoft/vscode/issues/226734](https://github.com/microsoft/vscode/issues/226734)

## Summary

File-search streaming remains absent from the current provider API and implementation. Keep this accepted On Deck request open: the related consumer-side request explicitly points here, and no verified older canonical owns the same capability.

## Change summary

Allow file-search providers to deliver results incrementally rather than returning a complete array.

## Best solution

Define a streaming file-search API contract that permits incremental provider results and considers extension consumers such as findFiles2. Preserve existing matching, exclusions, limits, cancellation, and compatibility without requiring a Quick Open UI redesign.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.fileSearchProvider2.d.ts`, `src/vscode-dts/vscode.proposed.findFiles2.d.ts`, `src/vs/workbench/services/search/common/fileSearchManager.ts`, `src/vs/workbench/api/common/extHostSearch.ts`, `src/vs/workbench/api/common/extHostWorkspace.ts`
- **Validation:** Use an extension provider that emits one URI, waits on a controlled gate, then emits another. Verify that the agreed streaming consumer receives the first URI before provider completion, cancellation prevents subsequent delivery, and existing nonstreaming consumers retain their expected results; cover filtering and maxResults in the file-search tests.
- **Behavior:**

  > An extension-backed file search should be able to supply matching files incrementally instead of withholding every match until the search finishes. The agreed streaming interface must make an early match observable before completion. Existing callers must retain compatible results, and matching, exclusions, result limits, and cancellation must remain correct. Whether incremental consumption is exposed through findFiles2 in the same change remains a scope decision.
- **Trace:**

  > FileSearchProvider2 in src/vscode-dts/vscode.proposed.fileSearchProvider2.d.ts returns ProviderResult<Uri[]> and has no progress parameter. FileSearchEngine.doSearch in src/vs/workbench/services/search/common/fileSearchManager.ts awaits that array before processing matches, so the manager's later batching is not provider streaming. The text-search proposal already has a progress-based contract, while findFiles2 still returns a complete URI array. The related discussion at https://github.com/microsoft/vscode/issues/226834#issuecomment-2327209155 favors a general async iterator and explicitly points to this issue, but does not establish a complete public contract. The trace establishes the missing capability, not a finalized transport or compatibility design; preserve current filtering, caching/session behavior, cancellation, and legacy API semantics.
- **Open decisions:**
  - Should the provider-facing streaming contract use an async iterable, as favored in the related discussion, or a progress callback consistent with text search, and how should existing array-returning providers remain supported?
  - Should this work expose incremental results to findFiles2 consumers immediately, or initially cover only the file-search provider contract and its internal consumers?

## Evidence

- **Current provider contract:** src/vscode-dts/vscode.proposed.fileSearchProvider2.d.ts declares provideFileSearchResults(pattern, options, token): ProviderResult<Uri[]> with no progress callback or iterable return.
