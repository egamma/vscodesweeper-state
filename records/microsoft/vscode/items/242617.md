# Issue #242617 — add active editor state information to editor's text area aria label

[https://github.com/microsoft/vscode/issues/242617](https://github.com/microsoft/vscode/issues/242617)

## Summary

Keep open: active editor state is available in the window title, but the text area's accessible label does not include that information. The maintainer-supported request remains useful for editor switching; its announcement timing needs a design decision to avoid excessive speech.

## Change summary

Include active editor state in the editor text area's accessible label, with a setting to disable it.

## Best solution

Make relevant active editor state available when a screen reader user focuses an editor, including after Ctrl+Tab, with the disable setting already supported in the discussion. Settle how background state changes affect announcements before implementation.

While staying in one editor, change its problem count and verify the agreed announcement policy with NVDA and VoiceOver; preserve existing filename, preview/pinned, group, and window-title behavior.
- **Behavior:**

  > Screen reader users switching editors with Ctrl+Tab can miss active editor state because the window title is not announced. Relevant state should be available through the focused text editor, and users must be able to disable the additional information as agreed in the discussion. Acceptance includes switching between differently decorated files, refocusing an editor after its state changes, and confirming that disabling the feature restores the existing label. Background updates must follow an explicit announcement policy so problem-count changes do not create unintended excessive speech.
- **Trace:**

  > AbstractTextEditor.computeConfiguration and computeAriaLabel in src/vs/workbench/browser/parts/editor/textEditor.ts supply the editor control's ariaLabel through computeEditorAriaLabel in src/vs/workbench/browser/editor.ts. That helper currently adds preview/pinned and group context to the input label, but does not consult resource decorations. WindowTitle in src/vs/workbench/browser/parts/titlebar/windowTitle.ts already derives activeEditorState from decorationsService.getDecoration(editorResource, false)?.tooltip; accessibility.windowTitleOptimized only governs the window-title presentation. Preserve existing editor identification and window-title semantics, and avoid unintentionally changing tab labels because computeEditorAriaLabel is shared with tab rendering. The uncertainty is how state changes while an editor remains focused should affect its accessible label and speech. https://github.com/microsoft/vscode/issues/89098 documents repeated label speech after suggestion acceptance and is relevant to evaluating verbosity, not a duplicate.
- **Open decisions:**
  - Should active editor state update the accessible label while the editor remains focused, potentially triggering speech on each change, or should state refresh only when the editor is focused?
