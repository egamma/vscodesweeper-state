# Issue #145696 — Expose checkbox in extension dialog API

[https://github.com/microsoft/vscode/issues/145696](https://github.com/microsoft/vscode/issues/145696)

## Summary

A real extension API gap remains on current main: modal messages cannot specify a checkbox or return its state, although the internal dialog service supports both. This team-authored feature request is accepted in the Backlog and has an API design direction from maintainers, so it should remain open for proposal design.

## Change summary

Allow extensions to add a checkbox such as “Don't Show Again” to modal dialogs and observe its final state.

## Best solution

Develop a proposed extension API for modal dialogs that accepts checkbox metadata and returns the checkbox state with the selected action, while preserving compatibility with existing show-message overloads and consistent native/custom dialog behavior.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostMessageService.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadMessageService.ts`, `src/vs/workbench/api/test/browser/extHostMessagerService.test.ts`
- **Validation:** Extend the `ExtHostMessageService` modal tests and API tests to verify that checkbox metadata reaches IDialogService.prompt, the selected action and checked state return to the extension, cancellation follows the chosen contract, and existing message overloads remain compatible; run `scripts/test.sh --grep ExtHostMessageService`.
- **Behavior:**

  > An extension can show a modal information, warning, or error dialog with a labeled checkbox and optional initial checked state. After the user chooses an action, the extension can observe both the selected item and the checkbox state. Existing extensions using the current show-message overloads behave unchanged, and the supported dialog renderers present equivalent checkbox semantics.
- **Trace:**

  > The stable MessageOptions contract in src/vscode-dts/vscode.d.ts exposes only `modal` and `detail`. ExtHostMessageService serializes those fields through MainThreadMessageOptions, and MainThreadMessageService constructs an IDialogService.prompt without `checkbox` and returns only its `result`. The platform dialog contract already exposes ICheckbox and returns checkboxChecked, so the missing boundary is the extension API, protocol, and result mapping rather than the dialog widgets themselves. The existing modal tests in src/vs/workbench/api/test/browser/extHostMessagerService.test.ts exercise this exact path. Keep non-modal notification behavior and existing showInformationMessage/showWarningMessage/showErrorMessage overload compatibility unchanged. The design direction discussed at https://github.com/microsoft/vscode/issues/145696#issuecomment-1367613845 leaves the public contract choice open.
- **Open decisions:**
  - Should checkbox support evolve `MessageOptions.modal` into a structured modal-options contract, or be introduced through a separate extension dialog API?
  - What backward-compatible return contract should expose checkbox state alongside the selected MessageItem or string?
  - Should the checkbox contract guarantee identical behavior for native and custom modal dialog renderers, including dismissal?
