# Issue #301078 — Include remote execution context in Copilot's <environment_info>

[https://github.com/microsoft/vscode/issues/301078](https://github.com/microsoft/vscode/issues/301078)

## Summary

A real gap remains on current main: Copilot's agent prompt reports the execution host OS but omits the remote-window context already available through `IEnvService.remoteName`. The request fits VS Code's AI-assisted and remote-development themes, but the prompt contract needs a maintainer decision about whether to expose remote type or execution capabilities.

## Change summary

Include remote execution context in Copilot's `<environment_info>` so agents avoid inappropriate local-GUI actions in remote workspaces.

## Best solution

Give the agent an accurate, stable description of where its tools execute and whether local desktop capabilities are available, derived from the existing remote environment signal without exposing unstable remote-authority details.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/prompts/node/agent/agentPrompt.tsx`, `extensions/copilot/src/extension/prompts/node/agent/test/agentPrompt.spec.tsx`
- **Validation:** Add prompt-rendering coverage for local and representative remote `IEnvService.remoteName` values, asserting `<environment_info>` accurately distinguishes their execution contexts while preserving the existing OS information.
- **Behavior:**

  > In a remote VS Code window, Copilot's environment context identifies that agent tools execute in a remote environment and provides enough information to avoid assuming desktop GUI capabilities. Local windows remain identified as local, and the existing execution-host OS information remains accurate. Acceptance should cover local, SSH, WSL, Dev Container, Codespaces, and tunnel-style contexts without asserting capabilities that a remote name alone cannot guarantee.
- **Trace:**

  > `GlobalAgentContext` in `extensions/copilot/src/extension/prompts/node/agent/agentPrompt.tsx` constructs `<environment_info>` solely from `UserOSPrompt`, whose `render` method reads `IEnvService.OS`. `IEnvService.remoteName` is already defined in `extensions/copilot/src/platform/env/common/envService.ts` and backed by `vscode.env.remoteName` in `extensions/copilot/src/platform/env/vscode/envServiceImpl.ts`, so the missing information is in prompt construction rather than environment discovery. Existing agent prompt tests live in `extensions/copilot/src/extension/prompts/node/agent/test/agentPrompt.spec.tsx`. Preserve the distinction between the remote execution host and the local VS Code UI; do not imply that every remote authority has identical GUI, browser, clipboard, or notification capabilities.
- **Open decisions:**
  - Should `<environment_info>` expose the raw/normalized remote kind, an explicit set of available execution capabilities, or both, given that remote identity alone does not always determine GUI availability?

## Evidence

- **current prompt gap:** `extensions/copilot/src/extension/prompts/node/agent/agentPrompt.tsx` renders `<environment_info>` using only `UserOSPrompt`; `UserOSPrompt.render` emits only `The user's current OS is: ...` and does not read remote state.
- **available signal:** `extensions/copilot/src/platform/env/common/envService.ts` already exposes `IEnvService.remoteName`, and `extensions/copilot/src/platform/env/vscode/envServiceImpl.ts` implements it with `vscode.env.remoteName`.
