# Issue #340483 — Agent Host: MCP servers without protected-resource metadata can never authenticate (empty `authorization_servers` in fallback)

[https://github.com/microsoft/vscode/issues/340483](https://github.com/microsoft/vscode/issues/340483)

## Summary

Thanks for the detailed report. The source confirms it: when an MCP server provides no protected-resource metadata, the Copilot agent host builds a fallback resource with no `authorization_servers`, so the renderer has no authorization server to try. A second user confirmed the issue and the v2 workaround.

## Change summary

OAuth MCP servers without RFC 9728 protected-resource metadata (for example Atlassian v1) never authenticate in the Agent Host, because the fallback resource has no `authorization_servers`.

## Best solution

In `_protectedResourceFromMcpAuthRequest`, default `authorization_servers` to the server URL's origin when there is no valid metadata, matching the MCP-spec fallback the extension host already uses. The renderer resolver should also log when it has no authorization server to try.

## Evidence

- **root cause:** src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts `_protectedResourceFromMcpAuthRequest` (~line 3778): when `request.resourceMetadata` is absent or invalid, it returns only `{ resource, resource_name, scopes_supported }`, with no `authorization_servers`.
- **renderer consumer:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts (lines ~701, 759, 952) iterates `resource.authorization_servers ?? []`, so an undefined list means no provider is ever tried. I did not trace the full silent-failure path or whether it logs.
- **confirmation and workaround:** A second reporter hit the same failure on Windows with WSL. Both reporters confirmed that the v2 URL, which publishes metadata, works.
