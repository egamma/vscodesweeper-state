# Issue #336045 — Second click after selecting from command center interpreted as double click on underlying UI

[https://github.com/microsoft/vscode/issues/336045](https://github.com/microsoft/vscode/issues/336045)

## Summary

Reporter confirmed reproduction on both current stable (1.137) and Insiders, and no fix is visible on main — this stays open as a real, if narrow, mouse-event pass-through bug where a double-click on a command-center/menu item leaks its second click to the UI element revealed underneath.

## Change summary

Double-clicking a command center dropdown entry (e.g. a quick-pick action) causes the second click of that double-click to register as a click/dblclick on whatever UI is now exposed underneath (e.g. creating a new untitled file when the editor area/tab bar is behind it).

## Best solution

Needs investigation into where the dropdown/quick-pick dismiss should consume or debounce the trailing click so it doesn't reach the newly revealed element — likely touching the dropdown/menu dismiss path (src/vs/base/browser/ui/contextview/contextview.ts) and/or the dblclick handlers that create new files (src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts, singleEditorTabsControl.ts) — before deciding the exact fix point.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/contextview/contextview.ts`, `src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts`, `src/vs/workbench/browser/parts/editor/singleEditorTabsControl.ts`, `src/vs/workbench/browser/parts/titlebar/commandCenterControl.ts`
- **Validation:** A manual repro: open an empty window, open the command center dropdown, double-click an entry with a single action (not one that opens a nested list), and confirm no new untitled editor/tab is created in addition to the entry's own action.
- **Behavior:**

  > Double-clicking a dropdown/menu entry from the command center (or command palette) should perform only that entry's action once; the underlying editor area or tab bar that becomes visible after the menu closes must not also receive a click or double-click event from the same physical double-click. Acceptance: repeating the reporter's steps (open empty window, double-click 'Search for Text' from the command center) performs the search action without also creating a new untitled file.
- **Trace:**

  > The reported second click is delivered to the DOM element that becomes visible once the dropdown/quick-pick closes after the first click of the double-click; that revealed element (editor tab bar / empty editor area) has its own EventType.DBLCLICK listener in src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts (line ~423) and singleEditorTabsControl.ts that opens a new untitled file. No existing code path (checked src/vs/base/browser/ui/contextview/contextview.ts and actionbar/actionViewItems.ts) suppresses or consumes a trailing click after a menu/dropdown dismissal. Where the uncertainty starts: whether the fix belongs in the dropdown/menu dismiss logic (swallow the next click within a short window) or in the underlying dblclick handlers (ignore a click whose timestamp/target indicates it originated from a menu dismissal) — this is a product/behavior choice a maintainer should weigh in on, since it affects all dropdown/quick-pick dismiss paths, not just the command center.
- **Open decisions:**
  - Should the fix live in the shared dropdown/context-menu dismissal path (suppressing the trailing click globally) or in each individual dblclick handler on underlying UI (editor tabs, etc.)?
  - Is any trailing click after a menu dismissal within a short window suppressed, or only clicks that land on a specific set of "dangerous" targets (e.g. those that create new files)?

## Evidence
