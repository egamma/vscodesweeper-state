# Issue #312484 — Allow opening the integrated browser to a specified URL from 'tasks' and the 'code' cli.

[https://github.com/microsoft/vscode/issues/312484](https://github.com/microsoft/vscode/issues/312484)

## Summary

Keep open: existing commands and debug-server readiness automation cover parts of this workflow, but do not establish support for both tasks and the code CLI. The comment provides a useful task workaround; a supported CLI entry point remains a meaningful gap.

## Change summary

Allow tasks and the code CLI to open a specified URL in the integrated browser without clicking terminal output.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/browserView/electron-browser/features/browserTabManagementFeatures.ts`, `src/vs/platform/environment/common/argv.ts`, `src/vs/platform/environment/node/argv.ts`, `src/vs/code/node/cli.ts`, `src/vs/code/electron-main/app.ts`, `src/vs/workbench/services/configurationResolver/browser/baseConfigurationResolverService.ts`
- **Validation:** The plan should end with runnable checks that a tasks.json task and a code CLI invocation each open the supplied URL in the integrated browser without interaction, preserve URL query and fragment values, and select the documented window. Verify that ordinary file-opening CLI behavior and existing browser commands remain unchanged.
- **Behavior:**

  > Users can open a specified URL in the integrated browser from a VS Code task and from the code CLI without finding and clicking terminal output. The development-server workflow should have a documented way to open the page when it is available. Acceptance must cover both entry points, URL preservation, and predictable window targeting; existing browser commands and ordinary CLI file opening must retain their behavior.
- **Trace:**

  > OpenIntegratedBrowserAction in src/vs/workbench/contrib/browserView/electron-browser/features/browserTabManagementFeatures.ts already accepts a URL string or options and opens a browser editor through IEditorService. extensions/simple-browser/src/extension.ts delegates simpleBrowser.api.open to that command on desktop, matching the partial workaround in https://github.com/microsoft/vscode/issues/312484. Task command inputs run through baseConfigurationResolverService.ts, which passes input args as one command argument and expects a string or nullish result; browser-opening commands return void, so side-effect execution is not itself a clean task completion contract. The debug-server-ready extension separately supports openIntegratedBrowser after detecting a server URL. CLI argument registrations contain no integrated-browser launch option, and the existing --open-url path handles application protocol URLs rather than establishing this feature. The remaining uncertainty is the supported public automation interface and its targeting/readiness semantics, not how to render or navigate a browser page; browser storage, agent sharing, and page permissions are outside this request.
- **Open decisions:**
  - What supported CLI syntax should open an integrated-browser URL, and which window should receive it when multiple windows are open or none exists?
  - Should task support rely on a documented command-input workflow or provide an explicit task operation with defined completion behavior?
  - Should this feature only open the supplied URL immediately, leaving server readiness to existing task/debug mechanisms, or include waiting for the development server?
