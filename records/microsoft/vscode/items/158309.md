# Issue #158309 — Git - Git error (Cannot fast-forward to multiple branches.) when syncing during autofetch

[https://github.com/microsoft/vscode/issues/158309](https://github.com/microsoft/vscode/issues/158309)

## Summary

Still reproduces on main: user-initiated sync/pull does not wait for an in-flight autofetch, allowing concurrent git fetch operations on the same repo. 78 upvotes and 'On Deck' milestone — valid bug, keeping open.

## Change summary

When autofetch is enabled, a user-initiated git sync/pull can race with an in-flight autofetch, causing 'Cannot fast-forward to multiple branches' or 'incorrect old value provided' errors.

## Best solution

Serialize remote git operations in `extensions/git/src/repository.ts` so that `run()` waits for any in-flight fetch/pull/sync to complete before starting another. Alternatively, cancel or skip the autofetch when a user-initiated sync/pull starts. The autofetch already uses `whenIdleAndFocused()` to avoid starting during operations, but the reverse guard is missing — `run()` should acquire a mutex or check for in-flight Fetch operations before starting Sync/Pull.

  > The bug is a concurrency race between autofetch and user-initiated sync/pull in the VS Code git extension. In extensions/git/src/autofetch.ts, the `run()` loop (line 107) calls `this.repository.whenIdleAndFocused()` before starting a fetch — so autofetch won't START during another operation. But in extensions/git/src/repository.ts, the `run()` method (line ~2702) has NO reciprocal guard: when the user clicks sync, `run(Operation.Sync, ...)` executes immediately even if an autofetch `run(Operation.Fetch, ...)` is in flight. Both invoke `git fetch` concurrently on the same repo, corrupting FETCH_HEAD and producing 'Cannot fast-forward to multiple branches'. Fix by adding serialization of remote operations in `run()` — either a queue/mutex for operations with `remote: true`, or cancel/abort the in-flight autofetch when a user sync/pull starts. Do NOT change the autofetch timer logic or the `whenIdleAndFocused` guard (that direction already works). Keep the fix minimal: only serialize overlapping remote operations, do not restructure the operation system. Add a test in the git extension test suite verifying that a Sync operation does not run concurrently with a Fetch operation. See also comment suggesting `--no-write-fetch-head` for autofetch as a complementary mitigation.

## Evidence

- **race in run():** extensions/git/src/repository.ts `run()` (line ~2702) does not serialize operations — it registers the operation and immediately runs it. Multiple operations (Fetch + Sync) can overlap.
- **one-directional guard:** Autofetch (extensions/git/src/autofetch.ts line 109) calls `whenIdleAndFocused()` which checks `operations.isIdle()`, so autofetch won't start during sync. But sync/pull's `run()` has no reciprocal check, so user sync starts while autofetch is mid-flight.
- **Fetch is non-readOnly:** extensions/git/src/operation.ts line 156: Fetch has `readOnly: false`, so `isIdle()` returns false during fetch — but only autofetch checks `isIdle()`, not user operations.
- **no fix on main:** git log --grep=158309 and git log on autofetch.ts show no related fix. The race condition is present on current main.
