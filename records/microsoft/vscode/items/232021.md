# Issue #232021 — Dragging a view or tab could show grabbing hand

[https://github.com/microsoft/vscode/issues/232021](https://github.com/microsoft/vscode/issues/232021)

## Summary

This remains a valid workbench drag-and-drop polish request. Current main provides a grabbing cursor for modal-editor dragging but not for ordinary editor tabs, views, or view containers, and the older auxiliary-window issue does not cover the full request.

## Change summary

Show a grabbing cursor while users drag editor tabs, views, and view containers.

## Best solution

Provide consistent grabbing feedback during internal tab and view drag operations while preserving native drop-effect feedback for invalid or external targets; first settle the expected cross-platform fallback where the operating system overrides or poorly renders that cursor.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/dnd.ts`, `src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts`, `src/vs/workbench/browser/parts/editor/media/multieditortabscontrol.css`, `src/vs/workbench/browser/parts/views/viewPaneContainer.ts`, `src/vs/workbench/browser/parts/views/media/views.css`
- **Validation:** Launch VS Code on macOS, Windows, and Linux; drag an editor tab, an editor group, a view, and a view container over valid internal targets, invalid internal targets, and outside the window. Confirm grabbing feedback appears for the agreed states, ends immediately after drop or cancellation, and does not mask native copy, move, or not-allowed feedback.
- **Behavior:**

  > Dragging an editor tab, editor group, view, or view container should provide consistent grabbing feedback for the agreed portion of the drag. The cursor must return to normal immediately after a drop or cancellation. Native feedback that communicates copy, move, invalid targets, or external drops must remain understandable. Acceptance requires checking the behavior on macOS, Windows, and Linux because native drag cursors differ by platform.
- **Trace:**

  > Editor-tab and group drag handling lives in `MultiEditorTabsControl` in src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts; its tab CSS currently uses `cursor: pointer`. View and view-container dragging flows through `CompositeDragAndDropObserver.registerDraggable` in src/vs/workbench/browser/dnd.ts, with registrations in `ViewPaneContainer` and `PaneCompositePart`. A local precedent exists in `ModalEditorPart`, which toggles a `dragging` class and styles it as `cursor: grabbing`. The boundary is visual pointer feedback: preserve existing transfer data, drop effects, drag images, reordering semantics, keyboard behavior, and accessibility semantics. https://github.com/microsoft/vscode/issues/199953 documents native external-drop constraints but does not cover this request's full internal view-and-tab scope.
- **Open decisions:**
  - Should the grabbing cursor remain visible for the entire native drag, including invalid and external targets, or only while the pointer is over a valid internal move target where it will not obscure native drop-effect feedback?
  - If a platform does not render a useful grabbing cursor during native drag-and-drop, should VS Code accept the platform cursor or provide a different consistent fallback?

## Evidence

- **current tab path:** src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts handles editor and group drag starts, while src/vs/workbench/browser/parts/editor/media/multieditortabscontrol.css leaves ordinary tabs at `cursor: pointer`; neither path applies dragging cursor state.
- **current view path:** src/vs/workbench/browser/dnd.ts `CompositeDragAndDropObserver.registerDraggable` centralizes view and composite drag start/end handling, and callers in src/vs/workbench/browser/parts/views/viewPaneContainer.ts and src/vs/workbench/browser/parts/paneCompositePart.ts currently register draggable elements without cursor-state callbacks.
- **existing precedent:** src/vs/workbench/browser/parts/editor/modalEditorPart.ts toggles a `dragging` class during modal-editor header dragging, and src/vs/workbench/browser/parts/editor/media/modalEditorPart.css maps that state to `cursor: grabbing`; this behavior does not cover normal tabs or views.
- **related but not canonical:** https://github.com/microsoft/vscode/issues/199953 is older and open, but it primarily tracks native drop feedback for auxiliary-window and external drop areas. It does not own the broader view-and-tab drag-state request here, so it does not meet the stronger duplicate bar for this re-reviewed item.
- **maintainer signal:** A maintainer described the treatment as worth trying, while the discussion left Windows cursor rendering and the exact drag-state condition to be tested.
