## Plan brief

- **Likely files:** `src/vs/workbench/browser/layout.ts`, `src/vs/workbench/browser/actions/layoutActions.ts`, `src/vs/workbench/browser/workbench.contribution.ts`, `src/vs/base/browser/ui/sash/sash.ts`
- **Validation:** After agreeing on scope, exercise vscode.dev at phone and tablet viewport sizes with touch input: open and edit a file, reveal and dismiss the sidebar, resize or switch panels, and operate controls with the on-screen keyboard visible. Verify the agreed mobile behavior, keyboard accessibility, and unchanged desktop layout and Zen Mode behavior; include layout-state tests for any new transitions.
- **Behavior:**

  > The request concerns the regular vscode.dev editing workbench on phones and tablets, where desktop-sized controls and competing panels make touch interaction difficult. A successful first increment should let users edit files and reach essential navigation without precision tapping or unusable panel arrangements. Acceptance should cover phone and tablet viewports, touch navigation, the on-screen keyboard, and keyboard accessibility while preserving desktop behavior. Existing Zen Mode and panel resizing provide partial functionality, not complete acceptance of the request.
- **Trace:**

  > src/vs/workbench/browser/layout.ts owns toggleZenMode and resizePart; the former hides workbench parts and the latter changes grid dimensions. src/vs/workbench/browser/actions/layoutActions.ts exposes existing layout actions, and src/vs/workbench/browser/workbench.contribution.ts registers density options that currently distinguish default and compact spacing. src/vs/base/browser/ui/sash/sash.ts already supports gesture-driven resizing. These are starting points, not a complete diagnosis of every mobile interaction; the shared-control impact of larger touch targets remains to be scoped. Preserve desktop layout, existing customization, and keyboard access rather than treating reduced chrome alone as a mobile solution. https://github.com/microsoft/vscode/issues/85254 documents related Safari-specific limitations, while https://github.com/microsoft/vscode/issues/302363 concerns a separate, narrower agent-supervision experience.
- **Open decisions:**
  - Should a mobile layout activate automatically for small touch viewports, be explicitly selected, or combine automatic selection with a user override?
  - Should small-screen sidebars and panels overlay the editor, replace it temporarily, or retain the existing resizable split layout?
  - Which behaviors belong in the first increment: larger touch targets, sidebar gestures, reduced chrome, or a defined subset?
