# Issue #55253 — Problem matchers should support creating related diagnostic information

[https://github.com/microsoft/vscode/issues/55253](https://github.com/microsoft/vscode/issues/55253)

## Summary

Keep open: current problem matchers still cannot attach related locations to a primary diagnostic. This is maintainer-accepted, team-authored work; existing multiline matching and the related programmatic-matching request do not satisfy or supersede it.

## Change summary

Allow task problem matchers to attach compiler notes and secondary source locations as related diagnostic information.

## Best solution

Expose a supported task problem-matching contract that preserves the primary error and attaches secondary messages with their own navigable locations. Decide whether that contract is declarative, programmatic, or both, and document it with a compiler diagnostic example.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/tasks/common/problemMatcher.ts`, `src/vs/workbench/contrib/tasks/common/problemCollectors.ts`, `src/vs/workbench/contrib/tasks/test/common/problemMatcher.test.ts`, `src/vs/workbench/contrib/tasks/test/common/problemCollectors.test.ts`
- **Validation:** Add matcher and collector tests using the Haxe examples from https://github.com/microsoft/vscode/issues/55120: one primary marker must contain relatedInformation with the secondary message and its own file/line, including a same-file earlier-line case. Run the task problemMatcher and problemCollectors unit suites and confirm existing single-line and multiline behavior remains unchanged.
- **Behavior:**

  > A task's compiler output can describe a primary error followed by explanatory notes at other source locations. The resulting diagnostic should retain the primary error's location and severity and expose those notes as related information with independently navigable locations, rather than unrelated Problems entries. Acceptance should cover both another-file and same-file earlier-line notes, while preserving existing matcher behavior for configurations that do not request association.
- **Trace:**

  > The motivating examples are in https://github.com/microsoft/vscode/issues/55120, and the accepted capability is tracked by https://github.com/microsoft/vscode/issues/55253. In src/vs/workbench/contrib/tasks/common/problemMatcher.ts, IProblemPattern, ProblemPatternParser and Schemas.ProblemPattern expose no related-information contract. AbstractLineMatcher.fillProblemData combines text into a single IProblemData while retaining the first location; getMarkerMatch emits no relatedInformation, and MultiLineMatcher does not create secondary location records. The marker interfaces in src/vs/platform/markers/common/markers.ts already support relatedInformation, and problemCollectors.ts delivers matcher-produced markers to the marker service. The unresolved boundary is the public mechanism for expressing associations, not whether linked diagnostics are desirable. Preserve existing matcher configuration and unrelated problem ordering behavior; https://github.com/microsoft/vscode/issues/59337 is a related programmatic API direction, not a verified duplicate.
- **Open decisions:**
  - Should related diagnostic information be expressible in declarative problem-matcher configuration, through a programmatic task matching API, or both?
  - What public association semantics should determine which secondary output records belong to a primary diagnostic and when that diagnostic group ends?
