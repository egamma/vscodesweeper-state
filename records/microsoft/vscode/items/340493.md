# Issue #340493 — Copilot Agent Host does not appear to respect the selected GitHub account when multiple accounts are signed in

[https://github.com/microsoft/vscode/issues/340493](https://github.com/microsoft/vscode/issues/340493)

## Summary

Account selection after initialization has been corrected, but a startup path still forwards the first eligible session before the preferred account is available. Keep this open for that remaining gap; the merged fix explicitly documents it.

## Change summary

Make Agent Host authentication and model discovery honor the selected Copilot account when multiple GitHub accounts are signed in, including during startup.

## Best solution

Retain the landed preference-aware session selection and prevent initial authentication from temporarily using another account while the preferred identity is unresolved. Preserve single-account behavior and avoid indefinitely blocking session restoration when no default-account provider registers.

- **Behavior:**

  > With multiple GitHub accounts signed in, opening the Copilot harness must not temporarily authenticate as a different account while the selected account is still initializing. Once the selected identity is available, authentication and model discovery must use it. Existing account switching, explicit session selection, and single-account operation must remain intact. Startup must not wait indefinitely when a default-account provider is absent.
- **Trace:**

  > The preference-aware fix in https://github.com/microsoft/vscode/pull/343394 is present, but its documented startup follow-up remains. resolveSessionForProtectedResource reads currentDefaultAccount synchronously; resolveAuthenticationSessionForResource takes the unrestricted first-session branch when that value is null. DefaultAccountService starts with null and establishes its account asynchronously, while getDefaultAccount waits on a barrier that depends on provider registration and refresh. AgentHostChatContribution authenticates independently and retries on later account changes. The unresolved boundary is distinguishing an initializing preferred identity from a genuinely unavailable one and ensuring authentication retries without delaying unrelated restoration. Preserve the landed preference selector, explicit preferred-session precedence, and unrelated provider authentication.

## Evidence

- **Confirmed user impact:** https://github.com/microsoft/vscode/issues/340493#issuecomment-6135841562 supplies Windows logs showing zero Agent Host models with multiple stored sessions and ten models after signing back into one account. https://github.com/microsoft/vscode/issues/340493#issuecomment-6267767884 independently reports personal-account model usage and charges despite selecting the business account.
- **Substantial fix already landed:** https://github.com/microsoft/vscode/pull/343394 merged as https://github.com/microsoft/vscode/commit/d489b0e92f109fe186a4c803324dbffbf5110839. Its agentHostAuth.ts diff replaces unrestricted first-session selection with default-account matching and selectAuthenticationSession, including protection against silently falling back to another account when several are signed in. The checkout contains these changes.
- **Explicitly unfinished startup behavior:** The Known follow-up section of https://github.com/microsoft/vscode/pull/343394 states that initial authentication can precede default-account initialization, use the old first-session behavior, and correct itself about one second later. The author observed the model list switching between accounts during live testing; the PR deliberately leaves this path unresolved.
- **Remaining path in current source:** src/vs/workbench/services/accounts/browser/defaultAccount.ts initializes defaultAccount to null and fills it asynchronously in setDefaultAccountProvider. src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts:903-913 passes currentDefaultAccount directly into resolution. At lines 487-505, a null default account leaves usesDefaultAccount false and permits sessions.find(...) to choose the first eligible session without consulting the selected account.
- **Initialization boundary:** DefaultAccountService.getDefaultAccount waits on initBarrier, which opens only after a registered provider's initial refresh. AgentHostChatContribution._authenticateWithServer starts authentication independently and listens for later default-account changes. Consequently, waiting unconditionally is not a safe substitute: a provider may never register, as the merged PR also explains.
- **Related report is newer:** https://github.com/microsoft/vscode/issues/342001 is open and reports missing Copilot-routed models in the Claude harness with multiple accounts. It was created on 2026-10-16, after this issue's 2026-10-08 creation, so it cannot serve as the canonical for closing this re-reviewed item.
- **Workarounds are not complete fixes:** https://github.com/microsoft/vscode/issues/340493#issuecomment-6291972003 reports that disabling chat.defaultToCopilotHarness avoids the affected harness and that signing an account out and back in changes the outcome. Neither establishes correct multi-account startup authentication.
