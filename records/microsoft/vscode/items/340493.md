# Issue #340493 — Copilot Agent Host does not appear to respect the selected GitHub account when multiple accounts are signed in

[https://github.com/microsoft/vscode/issues/340493](https://github.com/microsoft/vscode/issues/340493)

## Summary

Confirmed from source: the Agent Host's protected-resource authentication flow never consults the per-extension account preference, so with multiple GitHub accounts signed in it can authenticate using a different account than the one explicitly selected for the Copilot extension.

## Change summary

Agent Host model picker shows models from the wrong GitHub account when multiple accounts are signed in and the Copilot extension's account preference points to a non-default one.

## Best solution

Thread the owning extension's id (and provider id) into resolveAuthenticationSessionForResource/resolveSessionForProtectedResource so it can consult IAuthenticationExtensionsService.getAccountPreference the same way the MCP auth path already does via authenticationMcpService.getAccountPreference, instead of picking whichever non-rejected session getSessions() returns first.

- **Likely files:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts`, `src/vs/workbench/services/authentication/browser/authenticationExtensionsService.ts`
- **Validation:** A test asserting that, with two GitHub sessions for the same scopes/provider and an explicit account preference set via IAuthenticationExtensionsService, resolveSessionForProtectedResource/authenticateProtectedResource selects the preferred account's session rather than the first one returned by getSessions().
- **Trace:**

  > resolveAuthenticationSessionForResource (agentHostAuth.ts ~L375-465) iterates authorization_servers, calls authenticationService.getSessions(providerId, scopes, {...}, true), and returns the first session for which isAuthenticationSessionCandidate (L208) is true — that function only excludes a previously-rejected session, with no notion of a preferred account. Contrast with the MCP-specific flow (~L1076) which does call authenticationMcpService.getAccountPreference(mcpServerId, providerId) before choosing a session. The equivalent extension-scoped API, IAuthenticationExtensionsService.getAccountPreference(extensionId, providerId), exists (authenticationExtensionsService.ts:256) but is never called from this path. Do not touch the MCP-specific account-preference logic (L1060-1110) or the rejected-session quarantine semantics (isSameAuthenticationSession/isAuthenticationSessionCandidate) — only add preference consultation to the general resource-resolution path. Open question: authenticateProtectedResources/authenticateProtectedResourceWithServices currently receive no extensionId at all, so it is unclear whether preference should be looked up per-agent, per-provider, or some other key before a session is chosen.
- **Open decisions:**
  - Which identity (agent id, owning extension id, or something else) should key the account-preference lookup for a given protected resource/agent in the Agent Host flow?
  - When multiple agents/resources in the same Agent Host session want different accounts for the same provider, how should conflicting preferences be resolved?

## Evidence

- **missing preference lookup:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts resolveAuthenticationSessionForResource (lines ~375-465) calls authenticationService.getSessions(...) and picks the first session passing isAuthenticationSessionCandidate (line 208), which only checks a cached rejection, not any account preference.
- **preference exists but is unused here:** The same file's MCP-specific path (line 1076) does call authenticationMcpService.getAccountPreference(mcpServerId, providerId) before selecting a session; the generic protected-resource path used for Agent Host/Copilot resources has no analogous call to IAuthenticationExtensionsService.getAccountPreference(extensionId, providerId) (workbench/services/authentication/browser/authenticationExtensionsService.ts:256), which is what 'Manage Extension Account Preferences' actually writes.
- **no extensionId threaded through:** authenticateProtectedResources/authenticateProtectedResourceWithServices (lines ~563-733) never receive or pass an extensionId, so even if the lookup were added, it's unclear which extension's preference should govern a given protected resource/agent.
