# Issue #348183 — terminal-suggest watches every PATH directory and holds directory handles, blocking third-party app updates on Windows

[https://github.com/microsoft/vscode/issues/348183](https://github.com/microsoft/vscode/issues/348183)

## Summary

Keep open: current main still creates lifetime PATH watchers independently of the suggestions setting. The supplied Windows steps and handle evidence suffice to retest; the native rename failure was not independently exercised in this Linux, read-only checkout.

## Change summary

Terminal suggestions retain PATH-directory watches even when disabled, reportedly preventing Windows application updaters from renaming installation directories.

## Best solution

Make disabling terminal suggestions prevent and release its PATH watches, preserving completion freshness when re-enabled. Coordinate the remaining enabled-state locking behavior with the filesystem-watcher investigation without losing this issue's separate feature-lifecycle requirement.

- **Behavior:**

  > Windows application updates must not be blocked by terminal-suggest PATH watches when terminal suggestions are disabled. This must hold both when disabled before extension activation and when switched off afterward, without requiring a window restart. Re-enabling suggestions must preserve working, fresh executable completions. Reproduce the reported parent-directory rename failure before choosing acceptance criteria for enabled-but-idle terminals.
- **Trace:**

  > extensions/terminal-suggest/src/terminalSuggestMain.ts activate() initializes PathExecutableCache and unconditionally invokes watchPathDirectories() against the activation environment. The asynchronous directory loop registers every watcher in context.subscriptions, with no shorter lifetime or setting-change handling; watcher callbacks invalidate PathExecutableCache through refresh(). The workbench's terminal.suggest.contribution.ts disposes its own addons when disabled, not these extension-owned resources. The missing lifecycle connection is confirmed from source, but the Windows native-handle consequence has not been independently executed. Preserve enabled completion invalidation and avoid expanding this into general filesystem-watcher or cross-window redesign. https://github.com/microsoft/vscode/issues/334673 covers the underlying API rename behavior; https://github.com/microsoft/vscode/issues/331457 covers stale watches after directory replacement.
- **Open decisions:**
  - Beyond releasing watches when disabled, must application-directory renames also succeed while suggestions remain enabled but idle, and what user-visible activity defines that idle state?
