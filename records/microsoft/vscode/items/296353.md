# Issue #296353 — Feature Request: Add "wait" or "sleep" builtin tool for AI agents

[https://github.com/microsoft/vscode/issues/296353](https://github.com/microsoft/vscode/issues/296353)

## Summary

Keep open: existing terminal tools cover command-completion waits, but not a general shell-independent delay with optional followup execution. No verified open canonical or concrete implementation was found; this team-authored request needs a product-contract decision rather than a judgment close.

## Change summary

Provide an agent-callable builtin tool for timed pauses, optionally followed by another tool invocation.

## Best solution

Define a bounded, cancellable delay contract in the builtin agent-tool surface, while preserving event-driven terminal completion instead of encouraging polling. Decide whether followup execution belongs inside that contract or remains a subsequent agent tool call.

- **Validation:** The plan should define runnable fake-timer tests proving the delay does not finish before its requested duration, cancellation promptly ends it, and invalid or over-limit durations follow the agreed contract. If followup execution is included, verify it occurs only after completion, respects normal tool approval, and does not run after cancellation.
- **Behavior:**

  > Agents need a shell-independent way to pause for a requested duration before continuing their workflow. The pause must be cancellable and must not require repeated model calls while waiting. Existing foreground command waits and background terminal completion notifications must retain their behavior. Acceptance checks should cover elapsed duration, cancellation, agreed duration limits, and any approved followup semantics.
- **Trace:**

  > The inspected builtin chat and Copilot tool surfaces contain no dedicated wait/sleep tool. runInTerminalTool.ts defines terminal-bound sync/async waits and completion notifications; getTerminalOutputTool.ts takes only an execution id and returns an output snapshot. These partially address build-completion scenarios but do not establish a general delay contract. The remaining uncertainty is product scope and public input semantics, not a confirmed defect in terminal waiting. Preserve event-driven command completion and ordinary tool permission checks. The closed slash-command request at https://github.com/microsoft/vscode/issues/253412 and the newer detached-wake request at https://github.com/microsoft/vscode/issues/336056 are related context, not duplicate targets.
- **Open decisions:**
  - Should the initial tool only pause and return to the agent, or also accept and execute the proposed nested followup tool invocation?
  - What duration unit and maximum supported delay should the public tool contract expose?
