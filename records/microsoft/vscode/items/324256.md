- **reported trigger:** https://github.com/microsoft/vscode/issues/324256 provides a concrete reproduction: set editor.fontFamily to somejunknonexistingfont, open Markdown preview, and observe serif code instead of the editor's monospace fallback. The reporter also identifies inline code as affected.
- **current source defect:** src/vs/workbench/contrib/webview/browser/themeing.ts:57 assigns the nonempty raw configuration.fontFamily to editorFontFamily, and line 85 exports it as --vscode-editor-font-family. extensions/markdown-language-features/media/markdown.css:405 uses that variable for all code elements, with the monospace stack only inside var()'s fallback. An unavailable font does not unset the variable, so the configured missing font bypasses that stack. This traces the defect without executing the preview.
- **editor consistency:** src/vs/editor/common/config/fontInfo.ts:116-120, BareFontInfo.getMassagedFontFamily(), appends the platform default font family when the configured family differs. The platform defaults at lines 222-230 include monospace, explaining why the editor handles the same setting differently.
- **open implementation candidates:** GitHub inspection confirms https://github.com/microsoft/vscode/pull/325629 and https://github.com/microsoft/vscode/pull/326118 are both OPEN with mergedAt null, and both contain Fixes #324256. The former proposes CSS-level fallbacks; the latter proposes reusing editor fallback logic in shared webview theming. Neither establishes a landed fix.
