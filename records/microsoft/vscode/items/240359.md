# Issue #240359 — Support translations in Code OSS

[https://github.com/microsoft/vscode/issues/240359](https://github.com/microsoft/vscode/issues/240359)

## Summary

Keep open: source-built Code OSS web still lacks a self-contained language-pack localization path. A maintainer acknowledged the gap, and a later report was explicitly consolidated into this issue.

## Change summary

Enable source-built Code OSS web distributions to load translated workbench strings from language packs without relying on Microsoft's translation service.

## Best solution

Provide a documented, independently usable way to generate and serve build-matched workbench translations before web startup. Preserve the existing hosted translation path while deciding whether OSS support belongs in packaging tooling or a self-hosted runtime service.

## Plan brief

- **Likely files:** `src/vs/server/node/webClientServer.ts`, `src/vs/workbench/services/localization/browser/localeService.ts`, `src/vs/platform/languagePacks/browser/languagePacks.ts`, `build/lib/nls.ts`, `src/vs/server/test/node/webClientServer.test.ts`
- **Validation:** Build an OSS web distribution using the reported vscode-reh-web-linux-${NODE_ARCH}-min task, supply a non-English language pack through the agreed supported path, select that display language, and reload. Verify translated workbench strings load before startup without Microsoft's translation service, persist across reloads, and return to English when selected; retain coverage of the existing hosted bootstrap URL path.
- **Behavior:**

  > A source-built Code OSS web distribution should have a supported, documented way to display its workbench in a language supplied by a language pack without depending on Microsoft's hosted translation service. Selecting a supported language and reloading should load matching translated workbench strings before initialization and preserve the selection across reloads. Existing hosted VS Code localization and English startup must continue to work. Acceptance must use a packaged OSS web build, not merely verify that the language-selection command exists.
- **Trace:**

  > ConfigureDisplayLanguageAction in src/vs/workbench/contrib/localization/common/localizationsActions.ts delegates to WebLocaleService.setLocale, which records a locale cookie and reloads. src/vs/server/node/webClientServer.ts reads that cookie and constructs a translated nls.messages.js URL only through productService.nlsCoreBaseUrl; the checked-in OSS product configuration supplies no such endpoint. WebLanguagePacksService in src/vs/platform/languagePacks/browser/languagePacks.ts does not expose installed language packs, while build/lib/nls.ts emits globally indexed default messages and metadata. The maintainer explicitly identifies language-pack unpacking and pre-workbench translation loading as the missing OSS process: https://github.com/microsoft/vscode/issues/240359#issuecomment-2654580731. The trace establishes the missing delivery boundary, not a complete implementation design; decide how an OSS distributor supplies build-matched translations before prescribing changes. Keep desktop localization, extension-string translation, and existing hosted service behavior outside the requested behavioral change.
- **Open decisions:**
  - Should OSS web localization require distributors to pre-generate and host translations at packaging time, or support language packs installed and converted after deployment?
  - Should the supported delivery contract remain a separately configured translation endpoint, or include translations served directly by the packaged OSS web server?
