# Issue #232406 — Option to enable `tsconfig.json` relative loading of TypeScript language service plugins

[https://github.com/microsoft/vscode/issues/232406](https://github.com/microsoft/vscode/issues/232406)

## Summary

Keep this accepted, well-supported request open: current configuration supports explicit plugin search paths, not resolution relative to each tsconfig.json. The earlier security rationale for rejecting the flag needs a maintainer decision before implementation; neither a completed fix nor a qualifying open canonical was established.

## Change summary

Allow users to opt into resolving TypeScript language service plugins relative to the tsconfig.json declaring them, including with pnpm's isolated dependency layout.

## Best solution

Provide an explicitly approved, default-off way to resolve each project's declared plugin version without hoisting or maintaining workspace-wide probe paths. The TypeScript area should first reconcile that behavior with its earlier decision against enabling local plugin loads.

Include two projects using different plugin versions to check that resolution remains project-specific, and verify that project files alone cannot enable an option intended to require user approval.
- **Behavior:**

  > A user can explicitly opt into loading a TypeScript language service plugin relative to the tsconfig.json declaring it, even when workspace TypeScript resolves into pnpm's isolated store outside that project. The project should receive its own installed plugin version without public hoisting or manually maintained probe paths. Existing defaults and explicit plugin-path behavior remain unchanged. Acceptance should cover the reported pnpm layout and two projects declaring different versions of the same plugin; the requested unresolved-plugin notification is secondary, not necessary to establish the central capability.
- **Trace:**

  > TypeScriptServerSpawner.getTsServerArgs in extensions/typescript-language-features/src/tsServer/spawner.ts constructs --pluginProbeLocations from TypeScriptPluginPathsProvider and extension-contributed plugins, but never supplies --allowLocalPluginLoads. TypeScriptPluginPathsProvider.resolvePluginPath resolves user-specified paths against workspace folders, so it cannot express automatic resolution relative to each declaring configuration. package.json registers the machine-scoped js/ts.tsserver.pluginPaths setting, and src/configuration/configuration.ts reads it with compatibility fallback. web/src/webServer.ts already parses --allowLocalPluginLoads, but that parser alone does not enable the feature. The unresolved boundary is product approval: https://github.com/microsoft/vscode/issues/45856#issuecomment-373467962 explicitly rejected this flag, while the newer request is accepted into Backlog and documents a remaining pnpm case. Preserve default behavior and existing plugin contribution semantics; this review did not execute the scenario or inspect TypeScript's internal resolver.
- **Open decisions:**
  - Should the earlier prohibition on enabling project-relative plugin loading be revised to permit an explicit user-controlled opt-in, or must approval remain limited to individually specified plugin search paths?
