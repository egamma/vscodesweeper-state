## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/callStackView.ts`, `src/vs/workbench/contrib/debug/browser/debugSession.ts`, `src/vs/workbench/contrib/debug/common/debugProtocol.d.ts`
- **Validation:** Agree on an explicit concurrency scenario and acceptance contract, then use a synthetic debug adapter with a very large logical-thread population to check focused-thread navigation, on-demand detail retrieval, and request volumes. Verify ordinary small-thread debugging remains unchanged; do not treat stack-frame paging as thread-population paging.
- **Behavior:**

  > Developers debugging highly concurrent programs need to find and inspect relevant execution contexts without navigating or materializing every thread and stack. The discussion includes filtering, grouped stacks, persistent selection, and hierarchical processes, alongside a distinct current-thread-only workflow. A planning session should select the first supported experience and define observable acceptance checks for scale and navigation. Existing ordinary multithread debugging must remain usable.
- **Trace:**

  > CallStackDataSource in src/vs/workbench/contrib/debug/browser/callStackView.ts obtains getAllThreads() and presents the returned threads, with a compact representation only for single-thread sessions. DebugSession.fetchThreads in src/vs/workbench/contrib/debug/browser/debugSession.ts retrieves the complete adapter response through raw.threads(); the bundled protocol contract has no thread-query paging or filtering arguments. Existing delayed stack loading operates inside individual threads and does not address population discovery. The discussion at https://github.com/microsoft/vscode/issues/116109#issuecomment-868897263 explores grouped call graphs, while https://github.com/microsoft/vscode/issues/116109#issuecomment-2192730386 demonstrates that physical GPU threads also need scalable discovery. The uncertainty starts at the user-facing representation and adapter contract, not at a missing local guard. Coordinate with https://github.com/microsoft/vscode/issues/214824 and https://github.com/microsoft/vscode/issues/163080 without assuming those narrower features complete this exploration.
- **Open decisions:**
  - Should the initial experience focus on selecting a small set of threads, inspecting aggregated parallel stacks, or both?
  - Should logical tasks and physical threads share the existing thread model, or should the UI expose a separate concurrency model?
  - Which filtering, paging, grouping, and hierarchy semantics must adapters expose through a shared protocol contract?
