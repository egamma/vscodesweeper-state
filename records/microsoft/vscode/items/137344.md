# Issue #137344 — "Check for Update" does not behave as expected

[https://github.com/microsoft/vscode/issues/137344](https://github.com/microsoft/vscode/issues/137344)

## Summary

Keep this accepted feature request open: explicitly checking for updates on macOS still initiates a download rather than offering a check-only result. Current progress indicators partially address the feedback concern, but the central download-consent capability remains missing.

## Change summary

Separate checking for an available update from downloading it, and clearly communicate download completion.

## Best solution

Provide an explicit check-only update flow that reports the available version and leaves downloading to a separate user action. Decide how that flow fits the existing update commands and settings, using the current progress and ready-state UI rather than introducing redundant notifications.

- **Behavior:**

  > The reporter wants to learn whether a newer version is available without committing bandwidth to its download. A check-only flow must show the available version and let the user explicitly start downloading later; an up-to-date result must remain clear. Download progress and readiness must be visible without reopening the application menu. Acceptance should distinguish feed metadata requests from update-archive downloads and preserve existing automatic-update behavior outside the agreed scope.
- **Trace:**

  > CheckForUpdateAction in src/vs/workbench/contrib/update/browser/update.contribution.ts and update.check in browser/update.ts both call IUpdateService.checkForUpdates(true). AbstractUpdateService forwards that explicit check to DarwinUpdateService.doCheckForUpdates, which invokes Electron's autoUpdater and transitions to Downloading when an update is available. DarwinUpdateService already contains checkForUpdateNoDownload and an AvailableForDownload state, but its no-download branch is conditioned on a non-explicit metered check; the manual command cannot select it. Current badges and title-bar UI already expose progress and readiness, so the original lack-of-feedback observation is only partially current. The remaining uncertainty is the public command/default behavior and whether completion needs additional notification beyond those indicators; automatic updates, restart/install semantics, and unrelated platform behavior must not change incidentally. https://github.com/microsoft/vscode/issues/245767 is a newer related request with maintainer interest, not an eligible canonical for closing this re-reviewed issue. The original upstream-support observation should be reassessed against the current feed-check capability before choosing the design.
- **Open decisions:**
