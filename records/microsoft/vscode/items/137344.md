# Issue #137344 — "Check for Update" does not behave as expected

[https://github.com/microsoft/vscode/issues/137344](https://github.com/microsoft/vscode/issues/137344)

## Summary

The central request remains unmet: manually checking for updates on macOS still initiates downloading without a separate confirmation. Keep this accepted, 20-upvote backlog request open; newer related reports do not supersede it.

## Change summary

Separate manual update discovery from downloading, and clearly communicate when a downloaded update is ready.

## Best solution

Provide a manual check-only flow that reports the available version and lets the user explicitly start downloading, with clear completion feedback. Coordinate the behavior with the related newer request without replacing this older report.

## Plan brief

- **Likely files:** `src/vs/platform/update/electron-main/updateService.darwin.ts`, `src/vs/platform/update/electron-main/abstractUpdateService.ts`, `src/vs/platform/update/common/update.config.contribution.ts`, `src/vs/workbench/contrib/update/browser/update.contribution.ts`, `src/vs/workbench/contrib/update/browser/update.ts`
- **Validation:** With an update available on macOS and update.mode=manual, invoke Check for Updates and verify that the available version is reported without requesting the update archive; declining leaves it undownloaded, while explicitly choosing Download starts downloading. Verify the no-update result, completion feedback, and unchanged automatic-update behavior outside the chosen scope.
- **Behavior:**

  > A user who manually checks for updates should be able to learn which version is available before committing to a download. Declining or dismissing the result must not start downloading. Explicitly accepting the download should retain the existing installation workflow and provide clear ready-state feedback. Acceptance must cover both available-update and no-update outcomes.
- **Trace:**

  > CheckForUpdateAction in src/vs/workbench/contrib/update/browser/update.contribution.ts calls checkForUpdates(true), which AbstractUpdateService forwards to DarwinUpdateService.doCheckForUpdates. The Darwin implementation invokes Electron's combined check/download operation for explicit checks; its direct-feed checkForUpdateNoDownload helper is currently selected only by the non-explicit metered branch. The settings registration defines manual mode as a check-scheduling choice, not a download-consent choice. Existing update badges and title-bar feedback partially address the secondary visibility complaint but do not separate discovery from downloading. The newer open https://github.com/microsoft/vscode/issues/245767 describes the same central gap; the closed https://github.com/microsoft/vscode/issues/198792 captures the feedback aspect. Preserve automatic-update, installation, and restart semantics outside the behavior explicitly agreed with the maintainer; no implementation or runtime validation was performed in this read-only review.
- **Open decisions:**
  - Should all explicit Check for Updates actions become check-only, should this apply only in manual update mode, or should it be an opt-in behavior?
  - Should completed explicit downloads produce an immediate notification or dialog, or is the current ready-state title-bar and badge feedback sufficient?

## Evidence

- **Current manual-check path:** In src/vs/workbench/contrib/update/browser/update.contribution.ts, CheckForUpdateAction runs checkForUpdates(true). AbstractUpdateService.checkForUpdates in src/vs/platform/update/electron-main/abstractUpdateService.ts forwards that explicit check to doCheckForUpdates. DarwinUpdateService.doCheckForUpdates in src/vs/platform/update/electron-main/updateService.darwin.ts then calls electron.autoUpdater.checkForUpdates(), initiating the existing combined check/download flow.
