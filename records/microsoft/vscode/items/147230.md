# Issue #147230 — Play audio-cues for suggest widget

[https://github.com/microsoft/vscode/issues/147230](https://github.com/microsoft/vscode/issues/147230)

## Summary

Keep open: current source provides signals for inline suggestions, but not for opening or closing the completion suggest widget. Maintainers supported exploring this capability; its default behavior and interaction with existing spoken feedback still need a product decision.

## Change summary

Provide distinct audio feedback when the completion suggest widget opens and closes.

## Best solution

Provide configurable suggest-widget lifecycle signals that distinguish the completion list from inline suggestions, with sounds and defaults agreed with accessibility users and the audio designer. Preserve existing suggestion announcements and avoid redundant feedback during list updates.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/suggest/browser/suggestWidget.ts`, `src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts`, `src/vs/workbench/contrib/accessibility/browser/accessibilityConfiguration.ts`
- **Validation:** After agreeing the defaults, manually trigger suggestions in a file with a completion provider, dismiss with Escape, and accept a suggestion. Verify the agreed open/close sounds occur once per visibility transition, remain silent when disabled, and do not repeat during list navigation or refresh. Repeat with inline suggestions enabled and with VoiceOver or NVDA to check for overlapping or redundant feedback.
- **Behavior:**

  > The completion suggest widget should have audible visibility feedback distinct from the existing inline-suggestion cue. The thread proposes an open sound when the widget appears and a close sound when it disappears. Users must be able to control the feedback, and existing completion announcements must remain usable. Acceptance should cover manual and automatic opening, dismissal, acceptance, list updates, and coexistence with inline suggestions under the agreed defaults.
- **Trace:**

  > SuggestWidget in src/vs/editor/contrib/suggest/browser/suggestWidget.ts exposes onDidShow and onDidHide but has no signal-service integration. _show() is used for loading, empty, open, frozen, and details states, so its event cannot be assumed to represent only a new completion-list visibility transition; hideWidget() also fires its event without an explicit prior-visibility check. AccessibilitySignal.inlineSuggestion is registered in src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts and played by InlineCompletionsController for inline-completion state, not widget lifecycle. Current accessibility configuration exposes that inline signal but no widget lifecycle signal. Preserve completion speech, keyboard behavior, and existing inline-suggestion semantics. https://github.com/microsoft/vscode/issues/147230#issuecomment-1724430680 establishes the proposed open/close timing, while the thread leaves default noise management and audio design unresolved; https://github.com/microsoft/vscode/pull/174606 covers ghost-text announcements instead.
- **Open decisions:**
  - Should suggest-widget sounds be enabled automatically for screen-reader users or require explicit opt-in?
  - Which distinct open and close sounds should be used, and should overlapping inline-suggestion feedback be suppressed when the completion widget appears?
  - Should loading and no-suggestions displays produce the same lifecycle sounds as a populated completion list?
