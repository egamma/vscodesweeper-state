# Issue #306077 — Permission settings(bypass/default/autopilot)on prompt file level

[https://github.com/microsoft/vscode/issues/306077](https://github.com/microsoft/vscode/issues/306077)

## Summary

A real prompt-customization gap remains on current main: prompt files can select an agent, model, mode, and tools, but cannot declare a permission level. This should be routed to chat customizations for a product and security-contract decision rather than closed.

## Change summary

Allow each reusable prompt file to select Default Permissions, Bypass Approvals, or Autopilot when it runs.

## Best solution

Define a safe prompt-file permission contract in the chat customizations area, including whether a file may elevate beyond the current session or configured default and how managed policy constrains it. If elevation is allowed, the selected level should be visible and subject to the existing confirmation and enterprise-policy protections.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/promptSyntax/promptFileParser.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/languageProviders/promptFileAttributes.ts`, `src/vs/workbench/contrib/chat/browser/promptSyntax/runPromptAction.ts`, `src/vs/workbench/contrib/chat/test/common/promptSyntax/service/promptFileParser.test.ts`
- **Validation:** Add parser and prompt-execution coverage showing that each supported permission value is recognized and applied when a prompt runs, while an enterprise-restricted or otherwise disallowed elevation remains blocked by the existing permission policy.
- **Behavior:**

  > A reusable prompt file can declare the permission mode under which it should run: Default Permissions, Bypass Approvals, or Autopilot. Running that prompt produces a clearly visible effective permission mode and continues to honor enterprise restrictions and elevated-permission confirmations. Prompts without the attribute retain today's session-inherited behavior. Acceptance must cover all supported values, omission of the attribute, and a policy-blocked elevation.
- **Trace:**

  > Prompt-file frontmatter metadata is defined in src/vs/workbench/contrib/chat/common/promptSyntax/languageProviders/promptFileAttributes.ts; its prompt schema currently has agent, model, tools, and mode but no permission field. RunPromptBaseAction.execute in src/vs/workbench/contrib/chat/browser/promptSyntax/runPromptAction.ts runs a prompt by inserting its slash command into the current widget and calling acceptInput(), which leaves permission selection with the current session. ChatPermissionLevel is defined in src/vs/workbench/contrib/chat/common/constants.ts, while the global default is registered in src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts. The boundary is prompt execution and permission selection: existing session defaults, confirmation warnings, and managed-policy restrictions must remain authoritative. https://github.com/microsoft/vscode/issues/323620 concerns a later high-risk-action gate and is related but not the same observable request.
- **Open decisions:**
  - May a prompt file elevate above the current session permission level, or may it only preserve or reduce that level?
  - Should a prompt-declared elevated level apply only to that invocation or change the visible permission mode for the rest of the session?
  - What confirmation should be shown when a prompt requests Bypass Approvals or Autopilot, especially when the prompt came from workspace-controlled content?

## Evidence

- **current prompt schema:** src/vs/workbench/contrib/chat/common/promptSyntax/languageProviders/promptFileAttributes.ts registers prompt-file attributes for name, description, argumentHint, model, tools, agent, and mode, but no permission-level attribute.
- **current execution path:** RunPromptBaseAction.execute in src/vs/workbench/contrib/chat/browser/promptSyntax/runPromptAction.ts inserts the prompt slash command into the current chat widget and calls acceptInput(), so execution inherits the widget/session permission state rather than reading a prompt-specific permission.
- **existing capability boundary:** src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts describes chat.permissions.default as the starting level for new local sessions and states that each session remembers its selected permission mode; it does not provide prompt-file scoping.
- **related issue:** https://github.com/microsoft/vscode/issues/323620 is open but was created after this re-reviewed issue and reports a different symptom—Autopilot skipping high-risk actions—so it cannot be the canonical duplicate.
