# Issue #235164 — Find widget in file explorer should progress and show number of found elements

[https://github.com/microsoft/vscode/issues/235164](https://github.com/microsoft/vscode/issues/235164)

## Summary

A real Explorer find UX gap remains on current main: matching elements are counted internally and announced to screen readers, while delayed progress appears at the Explorer level, but the find widget itself exposes neither a visible result count nor a busy state. This team-authored Backlog request should remain open for a product decision about the generic tree-widget scope and count semantics.

## Change summary

Show search progress and the number of matching files or elements directly in the File Explorer find widget.

## Best solution

Give the tree find widget consistent, accessible visible feedback for completed match counts and asynchronous work, while preserving its existing keyboard navigation and ARIA result announcements. Decide whether that behavior applies to every tree find widget or only async Explorer searches before implementation.

- **Behavior:**

  > While an asynchronous File Explorer find is running, the find widget provides visible progress feedback. When the search completes, it displays an accurate localized count of matching elements, including zero results, and updates as the query or find toggles change. Existing filter/highlight behavior, keyboard navigation, warning messages, and concise screen-reader result announcements remain unchanged. Acceptance includes pending-to-complete transitions, cancellation by subsequent typing, zero/one/many matches, and both find modes.
- **Trace:**

  > FindWidget in src/vs/base/browser/ui/tree/abstractTree.ts currently renders an input and action bar only. FindController already maintains synchronous matchCount and announces it through alertResults(). AsyncFindController in src/vs/base/browser/ui/tree/asyncDataTree.ts additionally owns asyncWorkInProgress and IAsyncFindResult.matchCount, but suppresses rendering while pending. ExplorerFindProvider in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts performs the asynchronous search, reports delayed progress through ProgressLocation.Explorer, and calculates matches from both files and directories. The boundary is find-status presentation: do not alter search matching, phantom-item construction, filter/highlight semantics, focus movement, or existing ARIA announcements. The older open issues https://github.com/microsoft/vscode/issues/173742 and https://github.com/microsoft/vscode/issues/174377 concern discoverability and navigation rather than this status-feedback behavior.
- **Open decisions:**
  - Should visible result counts be a uniform capability of every tree find widget, or an Explorer-only behavior for its asynchronous provider?
  - Should the displayed Explorer count include both matching files and directories, as the current provider metadata does, or files only?
  - Should in-widget progress appear immediately after the find debounce or retain the existing delayed-progress behavior used by the Explorer?
