# Issue #291999 — GitHub Copilot Connection Pool Issue with Forticlient VPN

[https://github.com/microsoft/vscode/issues/291999](https://github.com/microsoft/vscode/issues/291999)

## Summary

The current Copilot networking path still propagates ordinary Undici connection timeouts without resetting the fetcher's pooled connections or attempting recovery. The report should remain open and route to the chat networking owners, although the claimed dead-socket root cause needs environment-level confirmation.

## Change summary

Copilot Chat requests stop recovering after idle periods on a FortiClient full-tunnel VPN until the extension host is reloaded.

## Best solution

Make Copilot networking recover safely from stale or timed-out pooled connections by invalidating the affected pool and retrying only when doing so cannot duplicate a non-idempotent request. Confirm the precise FortiClient failure mode before choosing whether recovery belongs in the Node fetch adapter or the higher-level fallback policy.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/networking/node/fetcherFallback.ts`, `extensions/copilot/src/platform/networking/node/nodeFetchFetcher.ts`, `extensions/copilot/src/platform/networking/node/baseFetchFetcher.ts`, `extensions/copilot/src/platform/networking/test/node/fetcherFallback.spec.ts`
- **Validation:** Add networking tests that inject an Undici-style `UND_ERR_CONNECT_TIMEOUT`, verify the chosen pool-reset/retry behavior, and verify that unsafe non-idempotent requests are not duplicated; then manually repeat the issue's idle-period scenario through FortiClient full-tunnel VPN.
- **Behavior:**

  > After a successful Copilot Chat request followed by an idle period on a VPN that expires connection state, the next request should either complete through a fresh connection or fail once with a clear network error; it must not remain spinning indefinitely or require reloading the window. Recovery must not submit the same non-idempotent model request twice. Existing proxy, certificate, and fetcher-fallback behavior must remain unchanged.
- **Trace:**

  > Node fetch requests use the lazy shared Undici agent in extensions/copilot/src/platform/networking/node/nodeFetchFetcher.ts. BaseFetchFetcher.disconnectAll() in extensions/copilot/src/platform/networking/node/baseFetchFetcher.ts does nothing, and fetchWithFallbacks() in extensions/copilot/src/platform/networking/node/fetcherFallback.ts only disconnects and retries errors classified as Electron network-process crashes. Consequently an Undici `UND_ERR_CONNECT_TIMEOUT` is propagated without pool invalidation. The reporter's logs and reload workaround are consistent with this path, but do not conclusively distinguish stale pooled state from FortiClient blocking a new connection. Keep the scope to Copilot fetch recovery; do not add broad global HTTP settings without evidence that other VS Code networking stacks share the defect.
- **Open decisions:**
  - Which requests may be retried automatically after a connect timeout without risking a duplicate model submission or charge: only requests proven not to have connected, only idempotent methods, or all Copilot requests with request-level deduplication?
  - Should a qualifying timeout reset only the Node fetch Undici pool, switch to another configured fetcher, or perform both in a defined order?

## Evidence

- **current source path:** extensions/copilot/src/platform/networking/node/fetcherFallback.ts retries after disconnect only when `isNetworkProcessCrashedError` recognizes an Electron network-process crash; an Undici `UND_ERR_CONNECT_TIMEOUT` from Node fetch falls through and is rethrown.
- **connection pool:** extensions/copilot/src/platform/networking/node/nodeFetchFetcher.ts routes requests through a process-lifetime lazy `undici.Agent({ allowH2: true })`, while its inherited `disconnectAll()` implementation in extensions/copilot/src/platform/networking/node/baseFetchFetcher.ts is a no-op.

These establish the observable failure, but `ss` showing no active connection does not by itself prove that a dead pooled socket was reused.
