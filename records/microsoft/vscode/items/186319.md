# Issue #186319 — [Feature] Debug Hovers Are Not Resizable

[https://github.com/microsoft/vscode/issues/186319](https://github.com/microsoft/vscode/issues/186319)

## Summary

Debug hovers still use a separate, non-resizable widget on current main. Keep this accepted feature request open: a later report was explicitly consolidated here, and ordinary editor-hover resizing does not cover it.

## Change summary

Allow users to resize debug hovers to inspect values and expanded objects more comfortably.

## Best solution

Provide user-controlled resizing for DebugHoverWidget, consistent with ordinary editor content hovers, while preserving expression evaluation, tree navigation, scrolling, and stable placement.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugHover.ts`, `src/vs/workbench/contrib/debug/browser/media/debugHover.css`, `src/vs/workbench/contrib/debug/test/browser/debugHover.test.ts`
- **Validation:** Establish a browser-level widget resizing check. Manually pause a debug session, hover an object with long names and enough children to overflow, and drag the hover edges to grow and shrink it; verify actual usable content dimensions change, scrolling and expansion still work, and placement remains usable above and below the expression. Also check a scalar-value hover and confirm ordinary editor-hover resizing is unchanged.
- **Behavior:**

  > Debug hovers should allow users to grow and shrink their visible content rather than being limited to automatic sizing. An expanded object with long names and many children should become easier to inspect after enlargement. Resizing must preserve value rendering, tree expansion, scrolling, focus, and dismissal. Check both object and scalar hovers, with the hover placed above and below its expression.
- **Trace:**

  > DebugHoverWidget in src/vs/workbench/contrib/debug/browser/debugHover.ts is independent of the editor's ResizableContentWidget. Its create() builds the scalar and complex-value containers, while layoutTree() calculates automatic dimensions and clamps object-tree width to 550 pixels; debugHover.css imposes the same complex-value width ceiling. Ordinary ContentHoverWidget already has resizing infrastructure, but that infrastructure does not reach debug hovers. Preserve evaluation and expression lookup semantics; this is a presentation capability, not a debug-adapter change. The existing debugHover.test.ts covers expression lookup only, so the planning session must establish widget-level verification before implementation. Additional user evidence was consolidated from https://github.com/microsoft/vscode/issues/249889.

## Evidence

- **Current capability gap:** src/vs/workbench/contrib/debug/browser/debugHover.ts: DebugHoverWidget implements IContentWidget directly; create() constructs plain containers without resizing controls. layoutTree() automatically computes height and clamps tree width to 400–550 pixels. src/vs/workbench/contrib/debug/browser/media/debugHover.css additionally caps .complex-value at 550px. These paths provide automatic sizing and scrolling, not user-controlled resizing.
