# Issue #257433 — Git Graph should support reset, soft reset and maybe squashing through the context menu

[https://github.com/microsoft/vscode/issues/257433](https://github.com/microsoft/vscode/issues/257433)

## Summary

The graph still lacks the requested reset and squash actions. Related open issues cover individual parts, but none verified here explicitly owns the complete request; retain the accepted Backlog item while clarifying scope.

## Change summary

Allow resetting the current branch to a selected graph commit, including soft reset, and potentially squashing selected commits.

## Best solution

Provide commit-targeted reset actions in the built-in Git graph with explicit reset semantics and appropriate safeguards. Coordinate the optional squash capability with https://github.com/microsoft/vscode/issues/214809 rather than designing a competing squash workflow.

## Plan brief

- **Likely files:** `extensions/git/package.json`, `extensions/git/src/commands.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/git.ts`
- **Validation:** In a disposable Git repository with several commits and staged/unstaged edits, invoke reset from a selected graph commit and verify HEAD, index, and working-tree results for each approved mode; cancellation must leave all state unchanged. If squash is included, verify the approved selection rules, resulting commit message, and preservation of the final tree.
- **Behavior:**

  > A user can target a commit in the built-in Source Control Graph and reset the current branch to it, including a soft reset that preserves index and working-tree contents. The operation must target the selected commit rather than merely undoing HEAD. Any destructive mode must communicate its consequences before execution. Whether this work also includes squashing selected commits remains a scope decision.
- **Trace:**

  > The graph's history-item context menu is contributed by extensions/git/package.json, with handlers such as Commands.cherryPick2 in extensions/git/src/commands.ts receiving a SourceControlHistoryItem. Commands.undoCommit only resets to HEAD~; the lower-level Git.reset in extensions/git/src/git.ts accepts a target and chooses --soft or --hard. The inspected menu exposes neither arbitrary-target reset nor squash. Preserve existing undo-commit and cherry-pick behavior. Coordinate reset work with https://github.com/microsoft/vscode/issues/217987 and squash work with https://github.com/microsoft/vscode/issues/214809; neither individually covers the combined request. The uncertainty is the user-facing reset modes and whether optional squash belongs in this delivery.
- **Open decisions:**
  - Which reset modes should the graph expose beyond the explicitly requested soft reset, and what confirmation should destructive modes require?
  - Should this item deliver reset only, leaving squash to the existing squash request, or include a coordinated multi-commit squash workflow?
