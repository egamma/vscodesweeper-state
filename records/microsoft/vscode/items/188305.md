# Issue #188305 — Test UI should surface continuous run on gutter test icon

[https://github.com/microsoft/vscode/issues/188305](https://github.com/microsoft/vscode/issues/188305)

## Summary

The gutter still lacks built-in continuous-run controls and continuous-run state feedback. Keep this accepted request open: the existing Explorer actions and programmatic commands do not cover the requested gutter interaction, and no verified canonical or open implementation PR was found.

## Change summary

Expose continuous-run controls in test gutter context menus and reflect the enabled state in the gutter.

## Best solution

Provide continuous-run controls for eligible tests directly from the gutter, synchronized with the Test Explorer and backed by the existing continuous-run service. Settle how the gutter represents continuous mode alongside test results and multiple tests sharing a line before implementing the complete experience.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/testing/browser/testingDecorations.ts`, `src/vs/workbench/contrib/testing/browser/testExplorerActions.ts`, `src/vs/workbench/contrib/testing/common/testingContinuousRunService.ts`
- **Validation:** Using a test provider with a continuous-capable profile, right-click a test gutter icon, enable continuous run, and verify synchronized controls and state in the gutter and Test Explorer. Disable it from each surface and verify synchronization in both directions. Repeat with passed, failed, and running tests, inherited continuous mode, multiple tests sharing a line, and a profile without continuous support.
- **Behavior:**

  > Users can enable and disable continuous testing for an eligible test from its editor gutter context menu without navigating to the Test Explorer. The gutter communicates continuous-run state and stays synchronized when that state changes elsewhere. Completion includes meaningful feedback alongside ordinary test-result states and sensible behavior when several tests share a gutter icon. Existing run, debug, coverage, and error-inspection interactions remain available.
- **Trace:**

  > RunTestDecoration.getTestContextMenuActions in src/vs/workbench/contrib/testing/browser/testingDecorations.ts constructs built-in gutter actions but contains no continuous-run action. ContinuousRunTestAction in src/vs/workbench/contrib/testing/browser/testExplorerActions.ts already toggles individual tests through ITestingContinuousRunService, but its menu registrations target only MenuId.TestItem. createRunTestDecoration in testingDecorations.ts chooses icons from result state, while replaceOptions only compares visibility and result states; continuous enablement is absent from this path. The existing service in common/testingContinuousRunService.ts owns enablement and change notifications, so preserve its execution semantics and the existing Explorer behavior. The maintainer explicitly requires gutter state feedback for completion in https://github.com/microsoft/vscode/issues/188305; the programmatic command work in https://github.com/microsoft/vscode/issues/210848 does not deliver that surface. The remaining uncertainty is the user-visible representation of continuous mode alongside results, inherited enablement, and shared-line test groups.
- **Open decisions:**
  - How should the gutter communicate continuous-run enablement while retaining passed, failed, running, and retired test-result feedback?
  - What state and available continuous-run actions should a shared gutter icon show when its tests have mixed enablement or inherit continuous mode from a parent?
