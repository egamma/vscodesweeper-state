# Issue #134405 — Add file references provider 

[https://github.com/microsoft/vscode/issues/134405](https://github.com/microsoft/vscode/issues/134405)

## Summary

Keep open: current main still implements file-reference searches separately for TypeScript and Markdown, without the requested shared extension API. Related issues cover user-facing searches and references-view presentation, not this distinct provider contract.

## Change summary

Expose a language-independent file-reference provider API returning reference locations for a target URI.

## Best solution

Agree on a public file-reference provider contract and its shared invocation experience, then make built-in language implementations consumers of that contract. Coordinate with LSP without making protocol standardization a prerequisite for the VS Code API.

- **Reason:** A shared provider contract enables language extensions to supply specialized analysis while VS Code supplies consistent navigation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `extensions/typescript-language-features/src/languageFeatures/fileReferences.ts`, `extensions/markdown-language-features/src/languageFeatures/fileReferences.ts`, `extensions/references-view/src/references/index.ts`
- **Validation:** After agreeing on the API, add an extension-host API test registering a mock file-reference provider and invoking the shared file-reference query for a target URI; assert returned URI/range locations, cancellation delivery, and removal after registration disposal. Manually verify that TypeScript and Markdown file-reference searches retain navigation behavior without changing workspace settings.
- **Behavior:**

  > Extensions should be able to supply references to an entire target file through a common VS Code contract, without inventing a language-specific command and presentation workaround. Results must retain the locations of individual references so users can navigate to them. Existing TypeScript and Markdown searches must retain their language-specific analysis and navigation. Acceptance should include a third-party mock provider participating through the agreed shared entry point.
- **Trace:**

  > The stable ReferenceProvider contract in src/vscode-dts/vscode.d.ts is document-and-position based, and no file-reference registration contract was found in the inspected stable/proposed API declarations or extension-host API sources. FileReferencesCommand in extensions/typescript-language-features/src/languageFeatures/fileReferences.ts and FindFileReferencesCommand in extensions/markdown-language-features/src/languageFeatures/fileReferences.ts independently obtain locations and temporarily change references.preferredLocation to display them. The references-view handler in extensions/references-view/src/references/index.ts explains that workaround but does not provide a discovery contract. Preserve existing symbol-reference behavior and language-service analysis; safe deletion and folder-reference aggregation are separate capabilities, not automatic consequences of this API. https://github.com/microsoft/vscode/issues/66162 supplies user-facing context, while https://github.com/microsoft/vscode/issues/151896 separately tracks presentation control. The trace establishes the missing surface, but not an agreed public invocation contract or the full extension-host/main-thread integration design.
- **Open decisions:**
  - Should the initial public contract include a standard user-facing Find File References command and shared results presentation, or expose provider registration and programmatic querying without prescribing the UI?
  - Is the initial provider contract limited to document-selector-matched files, or must it also cover arbitrary resource URIs such as non-text assets?

## Evidence

- **Existing API does not cover the request:** src/vscode-dts/vscode.d.ts:3717–3730 defines ReferenceProvider.provideReferences(document, position, context, token), and line 15038 registers that position-based provider. Searches across stable/proposed declarations and extension-host API sources found no FileReferenceProvider or registerFileReferenceProvider contract.
- **Current built-in capabilities remain custom:** extensions/typescript-language-features/src/languageFeatures/fileReferences.ts implements typescript.findAllFileReferences by calling tsserver's fileReferences request. extensions/markdown-language-features/src/languageFeatures/fileReferences.ts implements markdown.findAllFileReferences using MdLanguageClient.getReferencesToFileInWorkspace. These commands provide language-specific searches, not a provider registration surface other extensions can implement.
- **Discussion workaround persists in source:** Both built-in implementations temporarily update references.preferredLocation to view, invoke editor.action.showReferences, and restore the setting. extensions/references-view/src/references/index.ts registers its showReferences handler only when that setting is view. This matches the presentation workaround described in the supplied Svelte comment; it does not establish a shared file-reference API.
- **Canonical search and scope distinction:** Repository issue searches for file references and file-reference providers identified no verified duplicate API request. https://github.com/microsoft/vscode/issues/66162 is open and requests user-facing file/folder usage searches, while https://github.com/microsoft/vscode/issues/52844 requests safe deletion. Neither establishes ownership of this distinct extension-provider contract, and this re-reviewed item requires the same observable request before a duplicate close.
- **Related presentation request is not a canonical:** https://github.com/microsoft/vscode/issues/151896 remains open and explicitly distinguishes forcing the references view from the provider API requested here. https://github.com/microsoft/vscode/issues/115014 is closed and concerns history-entry rendering for the existing TypeScript command, not API delivery.
