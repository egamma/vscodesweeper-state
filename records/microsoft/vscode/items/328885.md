# Issue #328885 — Memory leak: main process buffers terminal output indefinitely in an unbounded Event.buffer (1.15M events / 602 MB) -> OOM closes all windows

[https://github.com/microsoft/vscode/issues/328885](https://github.com/microsoft/vscode/issues/328885)

## Summary

Traced a real, unbounded-growth path in current main: ProxyChannel.fromService wraps service events in Event.buffer, which buffers forever until a first listener ever attaches for the life of the shared IPC channel — an orphaned pty host process that no window ever (re)connects to will accumulate output events indefinitely with no cap, matching the reporter's heap snapshot and retainer chain exactly. Corroborated independently by a second reporter with a matching crash signature (VSCODE_CRASH_REPORTER_PROCESS_TYPE=ptyHost).

## Change summary

An orphaned pty host process with no connected IPC listener buffers terminal output events in an unbounded array forever, eventually exhausting V8's heap and crashing the process (taking all windows down with it).

## Best solution

Terminal/platform team should add a bound (or dispose-on-idle) to the buffered events created by ProxyChannel.fromService in src/vs/base/parts/ipc/common/ipc.ts (or promote Event.buffer's existing dev-only leak warning threshold into an actual cap/drop policy in src/vs/base/common/event.ts), and/or ensure orphaned pty host processes are reaped/disposed promptly via the existing orphan-detection path in src/vs/platform/terminal/node/ptyService.ts so their event sources stop producing before the IPC buffer can grow unbounded.

  > Thanks for the extremely well-documented report — the heap snapshot, retainer chain, and crash dumps make this easy to follow. Tracing it in the current source: `Event.buffer` (src/vs/base/common/event.ts) never caps its internal array and only stops buffering once a first listener has *ever* attached for the life of the buffered event; `ProxyChannel.fromService` (src/vs/base/parts/ipc/common/ipc.ts) shares that single buffered event across the whole IPC channel's lifetime. If a pty host process becomes fully orphaned (matching the 'Process had no disconnect runners but was an orphan' log line, which already exists in src/vs/platform/terminal/node/ptyService.ts) and no window ever (re)connects to it, its output event buffer has no listener to trigger a flush and grows without bound until OOM. This lines up with the second reporter's crash dumps showing the pty host process as the one that actually died. Routing to the terminal area for a fix — likely either bounding/disposing the IPC event buffer, or reaping orphaned pty host processes sooner so they stop producing before the buffer can grow unbounded.

## Evidence

- **buffer never re-caps:** src/vs/base/common/event.ts:515-601 Event.buffer subscribes eagerly and pushes to `buffer` unconditionally until the first-ever listener triggers `flush()`; after that `buffer` is permanently null and never re-enters buffering. No size cap exists, only a dev-only console.warn via `_bufferLeakWarnCountThreshold`/`_bufferLeakWarnTimeThreshold` (lines 36-37, 525-551).
- **shared, process-lifetime scope:** src/vs/base/parts/ipc/common/ipc.ts:1160-1163 ProxyChannel.fromService creates one Event.buffer per event name per channel registration; IPCServer.registerChannel (ipc.ts:985-990) shares that same channel/buffer instance across every client connection for the life of the server, so the leak requires a specific event to have zero listeners for the process's whole lifetime — plausible for a fully orphaned pty host.
- **orphan detection exists but doesn't stop the leak:** src/vs/platform/terminal/node/ptyService.ts:828 logs 'Process had no disconnect runners but was an orphan' — exactly the log line quoted in the issue and comment — confirming the orphan path is real and already instrumented, but doesn't cap or dispose the shared IPC event buffer.
- **independent corroboration:** Comment by li-xiu-qi reports the same crash signature with ~20 parallel agentic-CLI terminals and confirms via minidump parsing that VSCODE_CRASH_REPORTER_PROCESS_TYPE=ptyHost, consistent with the orphaned-pty-host mechanism rather than the literal 'main (browser) process' framing in the title.
- **no recent fix:** `git log --oneline -3 -- src/vs/base/parts/ipc/common/ipc.ts src/vs/base/common/event.ts` shows no related change; the unbounded-buffer behavior is unmodified on current main.
