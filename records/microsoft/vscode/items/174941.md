# Issue #174941 — Git - extension API gives repository remotes with aliases

[https://github.com/microsoft/vscode/issues/174941](https://github.com/microsoft/vscode/issues/174941)

## Summary

Keep open: the built-in Git API still exposes literal remote aliases on its normal discovery path. The merged GitHub Pull Requests changes mitigate individual consumers, not this API gap.

## Change summary

Expose Git-resolved fetch and push URLs through the built-in Git extension API when URL aliases are configured.

## Best solution

Make resolved remote URLs available to Git API consumers with Git-compatible insteadOf and pushInsteadOf semantics, while preserving inexpensive model refreshes. A maintainer-guided plan should establish the API contract and configuration-refresh behavior before implementation.

- **Behavior:**

  > Extensions need meaningful fetch and push URLs for repositories cloned through Git URL aliases, without independently implementing Git configuration semantics. For the supplied gh:user/private example, consumers should be able to obtain git@github.com:user/private. Acceptance must cover insteadOf, pushInsteadOf, longest-prefix matching, explicit push URLs, and unchanged behavior for ordinary remotes. The completed design must specify when effective configuration changes become visible and preserve responsive Git model refreshes.
- **Trace:**

  > Repository.getRemotes() in extensions/git/src/git.ts normally reads the repository config through getRemotesFS(); parseGitRemotes() copies literal URL properties without consulting effective global configuration. The Git subprocess fallback is reached only after filesystem discovery fails, so valid aliased remotes remain literal. extensions/git/src/repository.ts refreshes remotes with the model, and ApiRepositoryState.remotes in extensions/git/src/api/api1.ts exposes those values unchanged. Existing parser tests live in extensions/git/src/test/git.test.ts. https://github.com/microsoft/vscode/pull/238675 was closed without merging after the maintainer identified subprocess cost on every write-operation refresh; https://github.com/microsoft/vscode-pull-request-github/pull/8754 confirms consumer-side mitigation does not resolve this core gap. Preserve ordinary remote handling and existing read-only remote semantics; uncertainty remains around the resolved-URL public contract and effective-configuration invalidation guarantees.
- **Open decisions:**
  - Should existing Remote.fetchUrl and Remote.pushUrl always become effective Git-resolved URLs, or should the API retain literal values and expose resolved URLs separately?
  - When global or included Git configuration changes, must resolved API URLs update automatically, or may they remain cached until a defined refresh or reload?
