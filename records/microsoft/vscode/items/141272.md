# Issue #141272 — Testing API: allow extension to control sort-order of `TestController`s it contributes

[https://github.com/microsoft/vscode/issues/141272](https://github.com/microsoft/vscode/issues/141272)

## Summary

Controller ordering remains an API gap: TestItem.sortText does not provide ordering control for TestControllers. Keep this accepted Backlog request open; the previously suggested duplicate covers test items, and the newer workspace-scoping discussion does not replace this request.

## Change summary

Allow an extension to order its TestControllers independently of their displayed labels.

## Best solution

Provide a backward-compatible controller-ordering contract in the testing API, retaining existing ordering for extensions that do not opt in. Settle how extension-defined controller order interacts with the explorer's existing sorting modes before implementation.

Verify that the chosen API permits the requested order without changing labels, that controllers not opting in retain existing behavior, and that switching among location, status, and duration sorting follows the agreed precedence.
- **Behavior:**

  > An extension contributing multiple populated TestControllers cannot currently choose their sequence independently of their displayed labels. The desired capability is to express controller ordering without adding visible label prefixes. Acceptance should cover opposite label and requested orders, unchanged behavior for extensions not opting in, and the agreed interaction with existing explorer sorting modes.
- **Trace:**

  > TestController in src/vscode-dts/vscode.d.ts has no ordering property, while TestItem has sortText. ExtHostTesting.createTestController in src/vs/workbench/api/common/extHostTesting.ts creates an internal collection root and forwards controller label changes to it; TestItemRootImpl in src/vs/workbench/api/common/extHostTestItem.ts is not exposed as a public controller TestItem. TreeSorter.compare in src/vs/workbench/contrib/testing/browser/testingExplorerView.ts already consumes item sortText but otherwise falls back to labels after its other sorting criteria. This establishes the missing public capability, not an approved API design. Preserve existing TestItem ordering and existing controllers' behavior unless a maintainer explicitly approves a compatibility change. https://github.com/microsoft/vscode/issues/130882 covers item ordering, and https://github.com/microsoft/vscode/issues/207557 supplies related multi-controller use cases without settling controller-ordering semantics.
- **Open decisions:**
  - Should controller ordering be explicitly opt-in through a new API property, or should controller IDs determine ordering as the reporter suggested, changing existing behavior?
  - Should extension-defined controller order take precedence over status and duration sorting, or only replace the label-based fallback?
