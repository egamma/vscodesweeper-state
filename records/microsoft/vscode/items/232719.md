# Issue #232719 — No close icon when Activity Bar Top

[https://github.com/microsoft/vscode/issues/232719](https://github.com/microsoft/vscode/issues/232719)

## Summary

Keep this canonical UI-polish request open: current source intentionally removes the Secondary Side Bar close action when the Activity Bar is at the top or bottom, but later reports have been consolidated here and maintainers are still discussing the appropriate pointer-accessible layout affordance.

## Change summary

Provide a nearby pointer-accessible way to hide the Secondary Side Bar when the Activity Bar is positioned at the top.

## Best solution

Choose a consistent pointer dismissal affordance for both side bars when the Activity Bar is horizontal, coordinating it with the broader layout-control placement discussion in https://github.com/microsoft/vscode/issues/232798.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/auxiliarybar/auxiliaryBarActions.ts`, `src/vs/workbench/browser/parts/auxiliarybar/auxiliaryBarPart.ts`, `src/vs/workbench/browser/parts/sidebar/sidebarPart.ts`, `src/vs/workbench/test/browser/parts/auxiliaryBarPart.test.ts`
- **Validation:** Run the targeted AuxiliaryBarPart unit tests and manually set `workbench.activityBar.location` to `top`, open the Secondary Side Bar, and verify that it has a discoverable pointer affordance that hides it without changing default-position behavior or causing toolbar overflow.
- **Behavior:**

  > With the Activity Bar positioned at the top, a user who opens the Secondary Side Bar must have a discoverable nearby pointer affordance for hiding it. The primary and secondary side bars should retain intentional visual consistency, and constrained widths must not produce avoidable toolbar overflow. Existing command-palette, keybinding, and default Activity Bar behavior must remain available.
- **Trace:**

  > The omission is explicit in src/vs/workbench/browser/parts/auxiliarybar/auxiliaryBarActions.ts: the `ToggleAuxiliaryBarAction` entry in `MenuId.AuxiliaryBarTitle` is conditioned on `ActivityBarPosition.DEFAULT`. AuxiliaryBarPart in src/vs/workbench/browser/parts/auxiliarybar/auxiliaryBarPart.ts places its composite bar at the top or bottom for horizontal Activity Bars and already uses responsive toolbar overflow. Maintainer rationale in https://github.com/microsoft/vscode/issues/233939#issuecomment-2482204621 establishes that the current behavior was chosen for symmetry, space, and discoverability of reopening rather than being accidental. The unresolved design boundary is whether this issue should restore an in-part close affordance or be fulfilled through the nearby layout-control model discussed in https://github.com/microsoft/vscode/issues/232798; do not alter unrelated view-container switching or command/keybinding behavior.
- **Open decisions:**
  - For horizontal Activity Bars, should pointer dismissal use a local close icon in each side bar or a persistent layout toggle positioned beside the corresponding side bar?
  - If a local close icon is used, should it appear in both primary and secondary side bars to preserve their intended symmetry?

## Evidence

- **current source:** src/vs/workbench/browser/parts/auxiliarybar/auxiliaryBarActions.ts registers the `Hide Secondary Side Bar` title action only when `workbench.activityBar.location` equals `default`; top and bottom therefore still omit the close icon on current main.
- **intentional behavior:** A maintainer explained at https://github.com/microsoft/vscode/issues/233939#issuecomment-2482204621 that the action is hidden for horizontal Activity Bars to keep primary and secondary side bars consistent, avoid earlier overflow, and avoid hiding a side bar without an obvious way to restore it.
- **canonical status:** https://github.com/microsoft/vscode/issues/238100 was closed as a duplicate of this issue, and a maintainer later redirected the broader close-button request https://github.com/microsoft/vscode/issues/274349 here, confirming that this remains the canonical request.
- **related design:** The open https://github.com/microsoft/vscode/issues/232798 discusses moving layout toggles near the parts they control, but it was created after this re-reviewed issue and covers broader layout-control placement rather than the same missing-close-button symptom, so it is not a valid duplicate canonical.
- **available alternatives:** The `workbench.action.toggleAuxiliaryBar` command remains available through the command palette, keyboard shortcut, menus, and layout controls, but those alternatives do not provide the requested local pointer affordance.
