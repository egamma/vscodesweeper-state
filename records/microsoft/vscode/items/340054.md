# Issue #340054 — Untitled custom-editor switching can strand text and blocks safe Reopen With transitions

[https://github.com/microsoft/vscode/issues/340054](https://github.com/microsoft/vscode/issues/340054)

## Summary

Team-authored (hediet, MEMBER), same-day report with a detailed, source-verified trace of a real defect — hard keep-open rule applies regardless, and no fix exists yet on main; the fix needs a maintainer design decision before implementation, so this is plan-tier, not implement-tier.

## Change summary

Switching an untitled text document to a readonly/opaque custom editor (e.g. image preview) unconditionally reverts the original untitled text model even though the destination never consumes the bytes, stranding the text; separately, the blanket ban on 'Reopen Editor With...' for non-default untitled editors also blocks safe transitions between text-backed custom editors (e.g. Markdown) and the standard text editor.

## Best solution

Introduce an ownership/capability-based eligibility check (building on the existing `isTextEditor` flag in CustomEditorCapabilities) used consistently in MainThreadCustomEditorModel.create's revert logic, getAvailableEditorIds, the Reopen With picker, and the resolver/open path — only revert/clear the untitled model when the destination actually consumes or owns the text, and allow safe text<->text-backed-custom transitions while rejecting unsupported transfers without data loss.

## Plan brief

- **Likely files:** `src/vs/workbench/api/browser/mainThreadCustomEditors.ts`, `src/vs/workbench/common/contextkeys.ts`, `src/vs/workbench/contrib/customEditor/browser/customEditorInput.ts`, `src/vs/workbench/contrib/customEditor/common/customEditor.ts`, `extensions/media-preview/src/imagePreview/index.ts`, `extensions/media-preview/src/mediaPreview.ts`
- **Validation:** A test (or manual scenario) asserting that opening an untitled text document with a non-text-owning custom editor (e.g. imagePreview.previewEditor) preserves the untitled text model/content on revert to the default editor, while editable text-backed custom editors (e.g. markdown) can still round-trip safely through 'Reopen Editor With...' without data loss.
- **Behavior:**

  > Switching an untitled document to a custom editor must not destroy the original text unless the destination editor actually takes ownership of that text. If the destination doesn't consume the bytes (e.g. a readonly/binary preview), the untitled text model should remain intact so reopening with the standard text editor restores the original content. Conversely, switching between the standard text editor and a text-backed custom editor (one with `isTextEditor: true`) over the same resource should be allowed via 'Reopen Editor With...', preserving content, dirty state, and undo/redo. Acceptance: the image-preview repro in the issue no longer strands the sentinel text, and text-backed custom editors can round-trip to/from the default text editor via the picker and `vscode.openWith`.
- **Trace:**

  > Two independent gaps combine into the data-loss path. (1) MainThreadCustomEditorModel.create (src/vs/workbench/api/browser/mainThreadCustomEditors.ts ~L540-562) always reverts the untitled text model after forwarding `untitledDocumentData` to the extension via `$createCustomDocument`, regardless of the returned `editable` value or whether the custom provider actually consumed the bytes — verified directly on current main. (2) getAvailableEditorIds (src/vs/workbench/common/contextkeys.ts ~L357) unconditionally returns `[]` for any untitled editor whose `editorId` isn't the default text editor, which blocks the 'Reopen Editor With...' picker (and by extension `vscode.openWith`) even for text-backed custom editors that could safely round-trip. CustomEditorCapabilities.isTextEditor (src/vs/workbench/contrib/customEditor/common/customEditor.ts:28) already exists and could discriminate these cases but is used by neither path today. The boundary: do not touch the existing double-dirty-prompt prevention (comment referencing #125293) for supported transfers, and do not remove the restriction for genuinely opaque/binary custom editors. Where the uncertainty starts: the exact contract for 'safe transition' (resource/content identity requirements, how extension activation/async capability resolution is handled before the revert decision, and whether this applies to both directions of switching) needs maintainer sign-off before implementation.
- **Open decisions:**
  - What exact ownership/capability signal determines a 'safe' transition — is `isTextEditor` sufficient, or does it need a new explicit capability/contract on CustomEditorCapabilities?
  - How should the revert decision in MainThreadCustomEditorModel.create wait for extension-provided capability information (activation timing) before committing to revert vs. preserve?
  - Should unsupported untitled transfers be rejected outright with an error (as proposed) or allowed with a warning, and what UX should surface that rejection?

## Evidence

- **unconditional revert:** MainThreadCustomEditorModel.create (src/vs/workbench/api/browser/mainThreadCustomEditors.ts, around line 540-562) calls `untitledTextEditorService.get(resource)?.revert()` whenever `untitledDocumentData` is present, without checking the returned `editable` flag or whether the destination actually consumed the bytes — confirmed on current main.
- **blanket untitled block:** getAvailableEditorIds in src/vs/workbench/common/contextkeys.ts returns `[]` for any untitled editor whose `editorId !== DEFAULT_EDITOR_ASSOCIATION.id`, with no distinction for text-backed custom editors — confirmed on current main.
- **existing capability unused:** CustomEditorCapabilities.isTextEditor already exists in src/vs/workbench/contrib/customEditor/common/customEditor.ts:28 but is not consulted by either of the above code paths.
- **no recent fix:** `git log` on mainThreadCustomEditors.ts and contextkeys.ts shows no related recent change; the reported behavior is unfixed on main.
- **sibling issue:** Related report https://github.com/microsoft/vscode/issues/340055 covers an overlapping symptom (readonly untitled custom editors stuck dirty) but is a distinct narrower report, not a canonical for this broader ownership/transition issue.
