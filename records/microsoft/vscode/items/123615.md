# Issue #123615 — [api][commands] Open new window and a file

[https://github.com/microsoft/vscode/issues/123615](https://github.com/microsoft/vscode/issues/123615)

## Summary

This team-authored API request still describes a concrete gap: an extension cannot cleanly pass resolver-specific startup data while opening a remote window and then show a notebook with editor options. The current URI-encoded workaround changes remote identity and has caused recently-opened and workspace-trust problems, so the protected item should remain open for an API decision.

## Change summary

Provide an extension API for opening a new remote window with resolver-specific arguments and a file or notebook to show, without encoding session data into the remote authority.

## Best solution

Define a stable window-opening API contract that keeps resolver startup parameters separate from remote workspace identity and supports opening a resource with the required editor options in the new window.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostCommands.ts`, `src/vs/workbench/api/browser/mainThreadCommands.ts`, `src/vs/workbench/services/remote/common/remoteAuthorityResolver.ts`
- **Validation:** Add extension API tests that open a remote window with resolver startup data, verify the resolver receives it without changing the canonical remote authority, and verify the requested notebook opens with preview and focus options honored.
- **Behavior:**

  > An extension can open a new window on a remote authority, supply resolver-specific startup data without embedding it in the authority or workspace URI, and request that a file or notebook be shown in that window. Repeating the operation for the same authority and folder must retain the same remote workspace identity, avoiding duplicate recent entries and repeated workspace-trust prompts caused by session-specific authority strings. The requested editor options, including preview and focus behavior, must be preserved.
- **Trace:**

  > The report identifies `vscode.newWindow` as accepting only a `remoteAuthority`, forcing Azure ML to encode resolver arguments into a `vscode-remote` authority. Because those arguments include session-unique values, VS Code treats otherwise identical remote windows as distinct; the thread also records a repeated workspace-trust consequence. The consumer then calls `showNotebookDocument` with `preserveFocus: false` and `preview: false`, which means a simple resource argument may not preserve the needed behavior. Keep the boundary to the remote window/command and extension API handoff: do not make session metadata part of canonical remote identity, recently-opened identity, or workspace-trust identity. The supplied related item https://github.com/microsoft/vscode-tools-for-ai/issues/1030 is downstream and closed, not a canonical owner.
- **Open decisions:**
  - Should the public contract expose opaque resolver-specific startup data, or only a VS Code-owned resource-to-open contract?
  - If a resource is opened in the new window, which editor options must the cross-window API guarantee, including preview and focus semantics?
