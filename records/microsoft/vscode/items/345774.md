# Issue #345774 — MCP OAuth refresh races across VS Code windows invalidate rotating refresh tokens

[https://github.com/microsoft/vscode/issues/345774](https://github.com/microsoft/vscode/issues/345774)

## Summary

Keep open: current source permits separate windows to refresh the same persisted grant concurrently and publish conflicting token sets. The reported loss of unattended MCP authentication remains actionable; cross-window coordination needs architectural planning.

## Change summary

Prevent concurrent OAuth refreshes across windows from invalidating rotating refresh tokens or discarding a newer usable session.

## Best solution

Provide grant-scoped refresh coordination across windows sharing credential storage, with persistence that rejects stale refresh results and stale removals. Preserve silent MCP authentication and recover a newer stored credential before treating a losing refresh as a signed-out session.

- **Validation:** Extend the DynamicAuthProvider tests with two independent provider instances sharing persistence and a rotating-token mock endpoint. Run scripts/test.sh --run src/vs/workbench/api/test/browser/extHostAuthentication.test.ts --grep 'DynamicAuthProvider'. Assert one refresh exchange per shared grant, convergence on the usable credential, and preservation of newer credentials after delayed success or invalid_grant; additionally validate the selected coordinator across separate window clients.
- **Behavior:**

  > Two windows sharing an OAuth grant must not refresh it concurrently. After access-token expiry, both consumers must obtain a usable credential without requiring another interactive sign-in. A delayed or failed refresh must not overwrite or delete credentials already renewed by another window. Acceptance includes concurrent refresh requests, delayed persistence, and invalid_grant after another consumer has renewed the grant.
- **Trace:**

  > ExtHostAuthentication._providerOperations serializes calls only inside one extension host. DynamicAuthProvider.getSessions in src/vs/workbench/api/common/extHostAuthentication.ts refreshes a token snapshot and schedules removal before the network result; TokenStore.update publishes a complete array through MainThreadAuthentication.$setSessionsForDynamicAuthProvider. DynamicAuthenticationProviderStorageService persists that array to application-scoped secret storage without conditional replacement. The AgentHostContribution MCP authentication handler runs in both window types, providing competing consumers. Existing DynamicAuthProvider tests support injectable fetch behavior, but the inspected fixture uses one provider and a no-op persistence proxy. The unresolved technical boundary is where application-wide refresh ownership and conditional publication can be enforced across processes; this is broader than an in-process queue change. Preserve profile-sharing semantics, provider/client identity, and unrelated interactive authentication behavior; https://github.com/microsoft/vscode/issues/343436 tracks separate downstream reauthentication problems.

## Evidence

- **Reported trigger:** https://github.com/microsoft/vscode/issues/345774 reports two extension hosts refreshing session 603460365 within 5 ms, followed by invalid_grant, session disappearance, and HTTP 401 during scheduled automation.
- **Only process-local serialization:** src/vs/workbench/api/common/extHostAuthentication.ts declares _providerOperations on each ExtHostAuthentication instance; $getSessions queues by providerId within that instance. Separate extension hosts therefore do not share refresh ownership.
- **Refresh and stale-removal path:** DynamicAuthProvider.getSessions in src/vs/workbench/api/common/extHostAuthentication.ts:597-638 snapshots tokens, marks the existing token for removal before awaiting refresh, catches refresh errors, and still calls TokenStore.update. TokenStore.update constructs and publishes the resulting token array without an expected-version check.
- **Shared persistence boundary:** src/vs/workbench/services/authentication/browser/dynamicAuthenticationProviderStorageService.ts:169-189 reads and replaces a complete secret keyed by authProviderId and clientId; its change listener propagates updates but does not serialize refresh transactions. BaseSecretStorageService in src/vs/platform/secrets/common/secrets.ts uses instance-local sequencing and APPLICATION storage for these keys. src/vs/platform/storage/common/storage.ts:242-245 explicitly defines APPLICATION as shared across workspaces and profiles.
- **Both-window authentication consumers:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostChatContribution.ts:227-254 registers MCP authentication handling and explicitly documents that the contribution runs in both windows. autoAuthenticateMcpServer in agentHostAuth.ts invokes resolveMcpServerAuthentication with allowInteraction:false; its authentication queue is not an application-wide refresh transaction.
- **Related but distinct report:** Verified https://github.com/microsoft/vscode/issues/343436 is open and read its body and comments. It addresses server cancellation and duplicate interactive logins after refresh credentials are already rejected, not cross-window refreshes that invalidate otherwise usable rotating credentials. Fixing those downstream symptoms would not satisfy this report.
- **Inspection limits:** Source inspection confirms the missing cross-window coordination and conditional persistence. No runtime reproduction or build was performed, and the checkout was not modified; the specific Notion rotation sequence is supported by the reporter's logs rather than independently executed.
