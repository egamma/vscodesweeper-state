# Issue #252521 — Merge Editor Public API

[https://github.com/microsoft/vscode/issues/252521](https://github.com/microsoft/vscode/issues/252521)

## Summary

A supported public merge-editor integration remains missing for custom SCM extensions. The older API proposal covers opening and identifying merge tabs, but does not explicitly cover the acceptance and conflict-state integration raised by the quoted discussion, so it is not a verified full-scope duplicate.

## Change summary

Expose a supported merge-editor API that custom SCM extensions can use instead of relying on internal commands.

## Best solution

Define the supported extension contract for opening merge editors and observing merge completion and unresolved conflicts, coordinated with https://github.com/microsoft/vscode/issues/153213. Preserve existing merge behavior while deciding which lifecycle information custom SCM providers should receive.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.tabInputTextMerge.d.ts`, `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/contrib/mergeEditor/browser/commands/commands.ts`, `src/vs/workbench/contrib/mergeEditor/browser/mergeEditorInputModel.ts`
- **Validation:** An extension-host acceptance scenario should open a merge editor using the agreed supported contract and verify distinguishable outcomes for completing a resolved merge, completing with unresolved conflicts, canceling completion, and closing without accepting.
- **Behavior:**

  > Custom SCM extensions need a supported way to integrate the built-in merge editor without depending on undocumented commands. The cited use case also needs to distinguish a completed merge from closing an editor with unresolved conflicts. Acceptance should exercise opening with base, incoming, current and result resources, together with the lifecycle outcomes the maintainer elects to expose. Existing built-in Git merge behavior must remain unchanged.
- **Trace:**

  > OpenMergeEditor in src/vs/workbench/contrib/mergeEditor/browser/commands/commands.ts registers `_open.mergeEditor` and forwards four resources to IEditorService. src/vscode-dts/vscode.proposed.tabInputTextMerge.d.ts exposes proposed tab metadata and references https://github.com/microsoft/vscode/issues/153213, which tracks identification and opening rather than an explicit completion/conflict contract. AcceptMerge checks unhandledConflictsCount internally and returns successful after accepting and closing, including when the user explicitly completes with conflicts. mergeEditorInputModel.ts records acceptance and remaining conflicts internally through reportClose. The uncertainty is the intended public lifecycle contract, not the existing editor's conflict-resolution behavior; do not change merge algorithms, confirmation behavior or built-in Git semantics.
- **Open decisions:**
  - Should the supported public contract cover only opening and identifying merge tabs, or also expose completion, cancellation and unresolved-conflict state for custom SCM providers?
  - If lifecycle information is exposed, how should completing with conflicts differ observably from completing a resolved merge and closing without accepting?
