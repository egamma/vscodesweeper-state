# Issue #334573 — Unclear loading indicator when trying to send to a disconnected session

[https://github.com/microsoft/vscode/issues/334573](https://github.com/microsoft/vscode/issues/334573)

## Summary

Team-authored (COLLABORATOR) UX bug: sending to a session backed by a disconnected tunnel shows an indefinite loading spinner instead of a clear error. No fix commit references this issue on main, and the related issue (#335569) describes a different symptom (unresponsive Send after returning to a session), so it isn't a verified duplicate. Team-authored status keeps this open regardless.

## Change summary

In the Agents window, trying to send a message to a new session whose backing tunnel is disconnected shows only a persistent loading spinner with no error or actionable indication.

## Best solution

Surface the connection/disconnection state (already tracked by ConnectionDiagnosticsService in src/vs/sessions/contrib/providers/remoteAgentHost/browser/connectionDiagnosticsService.ts) in the chat send/loading UI so a disconnected tunnel produces a visible error instead of an indefinite spinner.

## Plan brief

- **Likely files:** `src/vs/sessions/browser/parts/sessionRemoteConnection.ts`, `src/vs/sessions/contrib/providers/remoteAgentHost/browser/connectionDiagnosticsService.ts`, `src/vs/sessions/contrib/providers/remoteAgentHost/browser/tunnelAgentHost.contribution.ts`
- **Validation:** A manual repro: disconnect a tunnel, open a new session against it, send a message, and confirm the UI surfaces a distinct error/disconnected state rather than an indefinite spinner.
- **Behavior:**

  > When a user sends a message in a new Agents-window session whose backing host/tunnel is disconnected, the UI should show a clear, actionable error/disconnected indicator instead of (or in addition to replacing) the persistent loading spinner. Reconnecting or explicit user action should be prompted rather than leaving the spinner spinning indefinitely.
- **Trace:**

  > The disconnect/connection state is already modeled in ConnectionDiagnosticsService (src/vs/sessions/contrib/providers/remoteAgentHost/browser/connectionDiagnosticsService.ts, status kinds 'connected'/'connecting'/'disconnected', disconnect reasons at lines ~135-190), but it is unconfirmed whether the send/loading UI in sessionRemoteConnection.ts consults this state when a *new* session is created against an already-disconnected host (as opposed to a live session losing connection). The boundary: do not change reconnect/retry semantics for still-connecting sessions — only the display when the host is confirmed disconnected before/during a send attempt.
- **Open decisions:**
  - Should the new-session send flow proactively check tunnel connection status before allowing Send, or only surface the error after a timeout/failed round-trip?
  - What is the exact user-facing message/state (inline error, toast, disabled Send with tooltip) for a disconnected-tunnel session?
