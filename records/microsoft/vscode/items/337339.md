# Issue #337339 — Agent Host: reused background subagent approval is orphaned after parent cancellation, leaving chat at Analyzing

[https://github.com/microsoft/vscode/issues/337339](https://github.com/microsoft/vscode/issues/337339)

## Summary

Team-authored, detailed bug report with a traced lifecycle/routing defect confirmed against current main source — hard keep-open (team-authored, no cited fix commit) applies regardless, and the evidence itself supports keeping it open rather than closing.

## Change summary

Reusing a background subagent (write_agent) after its parent turn was cancelled orphans the subagent's permission approval: the chat gets stuck at 'Analyzing' with no visible approval UI while events pile up in an internal buffer forever.

## Best solution

In node/agentSideEffects.ts, decide (with a maintainer) whether a resumed subagent after cancellation should reconstruct its catalog/routing entry or fail deterministically and settle any buffered permission requests immediately, then implement that in _resumeSubagentSession / _handleAgentSignal's buffering path so a 'Cannot resume unknown subagent' can never leave a live pending_confirmation stuck in _pendingSubagentSignals indefinitely.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentSideEffects.ts`
- **Validation:** A new agentSideEffects.test.ts case: start a background subagent, cancel the parent turn (cancelSubagentSessions), then emit subagent_resumed followed by a pending_confirmation signal for the same parentToolCallId — assert the permission request is settled (either denied or the subagent chat is properly re-registered and resumed) rather than remaining buffered in _pendingSubagentSignals with no active turn.
- **Behavior:**

  > When a background subagent spawned via write_agent is reused after its parent turn was cancelled, the subsequent resume must either (a) properly reconstruct the subagent's chat routing so its turns and any tool permission requests reach the normal approval UI, or (b) fail visibly and settle (deny) any outstanding permission requests immediately, clearing the parent chat from 'Analyzing'. In no case may events for that child keep accumulating in an internal buffer indefinitely while the UI shows no way to act.
- **Trace:**

  > cancelSubagentSessions() in src/vs/platform/agentHost/node/agentSideEffects.ts deletes the subagent's _subagentChats entry and its _pendingSubagentSignals buffer for the parent chat. A later SDK-side subagent_resumed signal is rejected by _resumeSubagentSession() as an unknown subagent (logged, no recovery). Meanwhile _handleAgentSignal()'s buffering path (~line 637-676) only auto-denies a pending_confirmation signal when no buffer yet exists for that parentToolCallId; once any earlier non-confirmation signal has created a buffer, a later permission request joins that buffer and is never drained, because subagent_started (which would trigger _drainPendingSubagentSignals) never arrives for a resumed session. Boundary: do not change the catalog single-path invariant (I4) or the general cancellation cleanup for subagents that are not reused; the fix must be scoped to how a post-cancellation resume/buffer is reconciled. Related: reporter's live debugger evidence and manual one-off recovery via respondToPermissionRequest (issue comment, 2026-09-22T19:28:58Z).
- **Open decisions:**
  - Should reusing a background subagent after parent cancellation reconstruct its catalog/routing entry (treating the resume like a fresh subagent_started), or should the resume fail deterministically with a visible error?
  - For a permission request that lands for an unroutable/orphaned subagent while a buffer already exists (not just when the buffer is empty), should it always be auto-denied immediately rather than joining the buffer?
  - When a subagent cannot be resumed, should the parent chat's turn/UI state be explicitly settled (e.g. surfaced as an error) instead of silently remaining at 'Analyzing'?

## Evidence

- **cancellation clears routing:** src/vs/platform/agentHost/node/agentSideEffects.ts cancelSubagentSessions() (around line 1186) calls this._subagentChats.deleteAll(parentChatURI) and this._pendingSubagentSignals.deleteAll(parentChatURI) — removing the child chat's routing registration entirely on parent cancellation.
- **resume rejected as unknown:** _resumeSubagentSession() (around line 1137-1142) looks up this._subagentChats.get(parentChatURI, toolCallId); if it's gone (as it is post-cancellation) it only logs `[AgentSideEffects] Cannot resume unknown subagent ...` and returns — it never re-adds the chat to the catalog nor settles anything.
- **indefinite buffering path traced:** In _handleAgentSignal() (around line 637-676), once any non-pending_confirmation signal with the same parentToolCallId creates a buffer entry in _pendingSubagentSignals, a subsequent 'pending_confirmation' signal for that parentToolCallId is appended to that existing buffer instead of hitting the immediate-deny branch at line 660-664 (which only fires when no buffer exists yet) — and since subagent_started never arrives to trigger _drainPendingSubagentSignals, the permission request (and every later signal) is buffered forever, matching the reporter's live-debugger evidence of 1600 buffered signals with an unresolved permission.
- **live confirmation:** Author used dbgjs/CDP to inspect the live host heap and confirmed `_subagentChats._data.get(parentChat) === undefined` while `_pendingSubagentSignals` held the accumulated signals, and manually invoked the existing respondToPermissionRequest handler as a one-off recovery (comment from 2026-09-22T19:28:58Z).
