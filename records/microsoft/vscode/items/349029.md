# Issue #349029 — Agent Host uses stale extension-contributed MCP launch configuration after settings change

[https://github.com/microsoft/vscode/issues/349029](https://github.com/microsoft/vscode/issues/349029)

## Summary

Keep open: the reported sequence is sufficient to retest, and current source still allows cached extension launch definitions to reach Agent Host without activating their provider. The exact failure has not been confirmed, and neither extension ownership nor per-chat retention is established.

## Change summary

Refresh extension-contributed MCP launch configuration after settings changes so existing Agent Host chats stop using obsolete environment values.

## Best solution

Ensure Agent Host receives the current provider-derived launch configuration after a server restart, including after window reload. First distinguish stale extension discovery from provider publication and session-side retention; the available evidence does not establish that a per-chat fingerprint is the right solution.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/common/discovery/extensionMcpDiscovery.ts`, `src/vs/workbench/contrib/mcp/common/mcpRegistry.ts`, `src/vs/workbench/api/common/extHostMcp.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostLocalCustomizations.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostMcpServerSupport.ts`
- **Validation:** With a controlled extension MCP provider, populate the launch cache with environment value A, change its setting to B, restart the server, and invoke a tool from the existing Agent Host chat. Repeat after window reload and compare a new chat; inspect provider publication and actual process environment to verify B is used without editing storage.
- **Behavior:**

  > An existing Agent Host chat continues launching an extension-contributed MCP server with an obsolete environment value after its extension setting changes. After updating the setting and restarting the server, tool calls should use the current provider-derived value, including after window reload. Acceptance must observe the launched configuration or process environment, not only the Customizations UI.
- **Trace:**

  > ExtensionMcpDiscovery restores workspace-cached server definitions as lazy, cached collections. McpRegistry.discoverCollections skips cached collections, while resolveConnection explicitly loads them; collectNonPluginMcpServers instead forwards definitions read from mcpService.servers. ExtHostMcpService also supports provider change notifications, so whether the provider activated and republished must be established before attributing the failure to host session retention. Compare existing and new chats to locate that boundary. Preserve lazy discovery, enablement, and unrelated MCP sources; do not assume arbitrary extension settings can be fingerprinted by core. https://github.com/microsoft/vscode/issues/343729 is relevant activation context, not a confirmed duplicate.

## Evidence

- **Concrete reported sequence:** https://github.com/microsoft/vscode/issues/349029 describes changing the SSH host, restarting the server, reloading VS Code, and observing the original host in a tool failure. Editing the persisted extension-server entry changed the outcome, but this remains a single-installation observation.
- **Persistent discovery cache:** src/vs/workbench/contrib/mcp/common/discovery/extensionMcpDiscovery.ts restores mcp.extCachedServers from workspace storage. ExtensionMcpDiscovery._registerCollection exposes those serialized launch definitions through a lazy collection marked isCached.
- **Different refresh paths:** src/vs/workbench/contrib/mcp/common/mcpRegistry.ts discoverCollections excludes cached lazy collections, whereas resolveConnection explicitly invokes collection.lazy.load(). In agentHostLocalCustomizations.ts:320-321, collectNonPluginMcpServers reads mcpService.servers directly; agentHostMcpServerSupport.ts resolves the current registered definitions for forwarding.
- **Provider updates remain a separate boundary:** src/vs/workbench/api/common/extHostMcp.ts:253-254 subscribes to provider.onDidChangeMcpServerDefinitions and republishes definitions. The discussion does not show whether this extension activated and published an updated definition, so the comment's claim that activation is ruled out is not demonstrated.
- **Related but not established duplicates:** Verified https://github.com/microsoft/vscode/issues/343729 is open and concerns missing provider activation; it is relevant to the cached-definition path but does not establish ownership of this settings-refresh failure. https://github.com/microsoft/vscode/issues/332782 is an open migration overview. Open reports https://github.com/microsoft/vscode/issues/338495 and https://github.com/microsoft/vscode/issues/340144 concern inventory visibility rather than obsolete extension-provided launch values.
