# Issue #335219 — Custom chat-completions model fails intermittently with HTTP/2 GOAWAY (Undici) and truncated request body (Node https fetcher)

[https://github.com/microsoft/vscode/issues/335219](https://github.com/microsoft/vscode/issues/335219)

## Summary

Real bug traced in source: Copilot's built-in single-retry logic for transient network errors never fires for this Undici HTTP/2 GOAWAY failure because the error code it matches on doesn't match the code Undici actually sets, so a retry mechanism that already exists for exactly this class of failure silently misses it.

## Change summary

Custom chat-completions endpoints behind an HTTP/2-terminating proxy intermittently fail with an unretried Undici GOAWAY SocketError, and the Node https fallback fetcher reportedly truncates large request bodies.

## Best solution

Extend the retry allowlist in `canRetryOnceNetworkError` (src/vs.../platform/networking/common/networking.ts) to also cover Undici's GOAWAY SocketError so the existing single-retry-on-network-error path actually engages for this failure mode; the Node-https truncation claim (nodeFetcher.ts) needs separate confirmation since the write/end path looks correct in isolation and the truncation may be proxy-side.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/networking/common/networking.ts`, `extensions/copilot/src/platform/networking/node/nodeFetcher.ts`
- **Validation:** A unit test asserting `canRetryOnceNetworkError` returns true for an Undici SocketError raised via the HTTP/2 GOAWAY path (code `UND_ERR_SOCKET`, message containing "GOAWAY"), and a manual/integration check against a proxy that sends GOAWAY mid-stream showing the request is retried once instead of surfacing to the user.
- **Behavior:**

  > When the Undici HTTP/2 client throws a SocketError because the upstream sent a GOAWAY frame mid-request, Copilot's existing single-retry-on-network-error mechanism should catch it and retry once (as it already does for other transient network codes), instead of the error reaching the user unretried. The Node https fetcher should never truncate a valid JSON request body regardless of size. Acceptance: a GOAWAY SocketError is retried once and, if the retry succeeds, no error is shown to the user; large bodies (30k+ tokens) sent via the Node https fetcher arrive intact at the server.
- **Trace:**

  > Root cause for symptom 1: `canRetryOnceNetworkError` (extensions/copilot/src/platform/networking/common/networking.ts, ~line 573) matches only Node-native http2 error codes; Undici's own GOAWAY error is a `SocketError` with `.code === 'UND_ERR_SOCKET'` (confirmed against undici v7.24.x–v7.26.0 source, the version range covering the pinned `^7.24.1`), so it never matches and the retry in `networkRequest`'s `.catch` (same file, ~line 553) never fires. Do not touch the CAPI request path (`isCAPIRequestMetadata` branch) or existing retry codes. For symptom 2, `nodeFetcher.ts`'s `_fetch` write/end sequence looks correct for chunked bodies of any size from source alone — this needs an actual reproduction (or proxy log) before concluding it's a Copilot defect rather than a gateway/proxy limitation.
- **Open decisions:**
  - Should the retry allowlist match Undici's generic `UND_ERR_SOCKET` code broadly, or narrow the check to GOAWAY-specific SocketErrors (e.g. also inspecting the error message) to avoid silently retrying unrelated socket failures?
  - Is the Node https fetcher truncation a real Copilot defect, or an artifact of the reporter's specific proxy/gateway — does it need its own reproduction before scoping a fix?

## Evidence

- **retry allowlist:** src/platform/networking/common/networking.ts `canRetryOnceNetworkError()` retries on ['ECONNRESET','ETIMEDOUT','ERR_CONNECTION_RESET','ERR_NETWORK_CHANGED','ERR_HTTP2_INVALID_SESSION','ERR_HTTP2_STREAM_CANCEL','ERR_HTTP2_GOAWAY_SESSION','ERR_HTTP2_PROTOCOL_ERROR','ERR_FAILED'] matched against `reason?.code`, gated by `canRetryOnce` (defaults to true).
- **actual error code mismatch:** Undici's `SocketError` class (lib/core/errors.js) hardcodes `this.code = 'UND_ERR_SOCKET'`, and the GOAWAY handler in lib/dispatcher/client-h2.js (`getGoAwayError`) throws exactly that SocketError for non-NO_ERROR GOAWAY codes — its `.code` never equals the Node-native `ERR_HTTP2_GOAWAY_SESSION` string the allowlist checks for, so the retry branch never triggers for this failure.
- **package pin:** extensions/copilot/package.json pins `undici: "^7.24.1"`; confirmed via registry/tag checkout that v7.24.x–v7.26.0 lack the newer automatic GOAWAY-replay handling added later upstream (kGoAwayReplayAttempts), so neither Undici itself nor Copilot's own retry wrapper currently absorbs this GOAWAY.
- **second symptom not source-confirmed:** src/platform/networking/node/nodeFetcher.ts `_fetch()` does `req.write(body); req.end()` with no explicit Content-Length, which Node handles via chunked encoding for arbitrary body sizes — nothing in this file obviously truncates large bodies, so the reported 400 may originate at the reporter's proxy/gateway rather than in this fetcher.
