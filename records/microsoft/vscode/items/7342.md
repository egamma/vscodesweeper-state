# Issue #7342 — take advantage of tsserver model of code for faster TypeScript builds

[https://github.com/microsoft/vscode/issues/7342](https://github.com/microsoft/vscode/issues/7342)

## Summary

Keep open: current TypeScript build tasks still invoke a separate compiler rather than reuse the editor's tsserver model. Maintainers explicitly accepted investigating server-backed emit and project checking; neither the existing watch tasks nor the related integration request establishes that this performance request is resolved.

## Change summary

Reuse tsserver's existing parsed and checked project model for TypeScript builds instead of duplicating that work in a separate tsc process.

## Best solution

Establish a supported server-backed build path that reuses the editor's TypeScript project state while preserving project-wide diagnostics and emit correctness. Assess the current TypeScript protocol and measure the benefit before deciding the VS Code integration.

Compare emitted files and dependent-file diagnostics against tsc using the same project configuration; measure initial and repeated build latency and compiler-process memory, and verify that the measured path actually reuses the editor's server model.
- **Behavior:**

  > Building a TypeScript project should be able to reuse the project model already maintained for editor language features instead of reparsing and rechecking it in an independent compiler. The benefit must be demonstrated on a representative project rather than inferred from architecture alone. Emitted output and project-wide error reporting must remain consistent with the project's compiler configuration, including errors introduced in dependent files.
- **Trace:**

  > TscTaskProvider in extensions/typescript-language-features/src/task/taskProvider.ts currently resolves a tsc executable and creates shell-based build and watch tasks; project references select -b rather than changing that process boundary. The existing typescript.tsserverRequest command exposes read-only emit-output, but that is not a project build integration. The historical design discussion at https://github.com/microsoft/TypeScript/issues/11526 establishes protocol availability, not an efficient complete builder adopted by VS Code. The uncertainty begins with whether the current server protocol can provide project-wide emit and diagnostics without excessive client orchestration or harming interactive language-service responsiveness. Preserve existing compiler task behavior and configuration compatibility while evaluating that boundary. https://github.com/microsoft/vscode/issues/973 is related integration context, while https://github.com/microsoft/vscode/issues/8201 explicitly deferred builder tracking to this issue.
