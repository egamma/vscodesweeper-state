# Issue #282578 — Tweak terminal suggest setting to be off by default for certain problematic configs

[https://github.com/microsoft/vscode/issues/282578](https://github.com/microsoft/vscode/issues/282578)

## Summary

Keep open: terminal suggestions still use a boolean enablement setting, with no powerlevel10k-specific automatic disablement. Existing automatic-trigger settings reduce interruptions but do not deliver the requested per-terminal compatibility default.

## Change summary

Introduce auto/on/off terminal-suggestion enablement, with auto disabling suggestions when powerlevel10k is detected.

## Best solution

Provide prompt-aware automatic enablement while retaining explicit on/off overrides. Settle compatibility for existing boolean configurations before changing the setting's public contract; fixing individual powerlevel10k completion defects remains separate work.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/terminalContrib/suggest/common/terminalSuggestConfiguration.ts`, `src/vs/workbench/contrib/terminalContrib/suggest/browser/terminal.suggest.contribution.ts`, `src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts`, `src/vs/platform/terminal/common/terminal.ts`, `src/vs/workbench/contrib/terminalContrib/suggest/test/browser/terminalSuggestConfiguration.test.ts`, `src/vs/workbench/contrib/terminalContrib/suggest/test/browser/terminalSuggestAddon.test.ts`
- **Validation:** Add focused configuration and contribution tests covering auto with p10k and a supported non-p10k prompt, explicit on/off overrides, late prompt detection, live configuration changes, and the chosen legacy-boolean semantics. Manually verify a zsh/powerlevel10k terminal is disabled under auto but can use suggestions under on, while a supported non-p10k terminal remains enabled. No tests were executed in this read-only review.
- **Behavior:**

  > Terminal suggestions offer auto, on, and off enablement. In auto mode, detecting powerlevel10k disables suggestions for that terminal; explicit on permits suggestions despite that prompt and explicit off disables them. Other supported shells retain their existing suggestion behavior under auto. Acceptance must cover detection arriving after terminal initialization, configuration changes in an existing terminal, and the agreed treatment of previously saved boolean values.
- **Trace:**

  > terminalSuggestConfiguration.ts currently exposes a boolean enabled setting with default true. TerminalSuggestContribution in terminal.suggest.contribution.ts reads it at xtermOpen and on configuration changes, while the manual-trigger keybinding compares the setting directly with true. The existing zsh shell-integration script emits PromptType=p10k, and ShellIntegrationAddon publishes it through PromptTypeDetectionCapability, but suggestion enablement does not consume that capability. TerminalProcessManager also passes the setting into boolean shellIntegration.suggestEnabled process options, so the plan must enumerate downstream consumers before changing the contract. Preserve completion ranking, provider behavior, shell integration, and unrelated prompt compatibility; this request changes enablement defaults rather than repairing the separate completion defects described at https://github.com/microsoft/vscode/issues/282352. The unresolved public-contract boundary is how existing boolean configurations behave after introducing string modes.
- **Open decisions:**
  - Will existing boolean values remain supported, and should a saved true preserve unconditional enablement like on or adopt compatibility-aware behavior like auto?
