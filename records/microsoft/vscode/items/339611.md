# Issue #339611 — Renderer OOM during Copilot external ingest: unbounded file search returns millions of files

[https://github.com/microsoft/vscode/issues/339611](https://github.com/microsoft/vscode/issues/339611)

## Summary

Source-confirmed on main: Copilot's external-ingest reconciliation requests an unbounded file search (`Number.MAX_SAFE_INTEGER` results, no cancellation) whose matches accumulate unbounded in `mainThreadSearch.ts`'s `SearchOperation` Map, exactly matching the reporter's diagnosed renderer OOM path — this needs an owner, not a close.

## Change summary

Copilot external-ingest workspace reconciliation runs an unlimited `**/*` file search that can return millions of matches and OOM-crash the renderer on large, unexcluded workspaces.

## Best solution

Bound/stream the `reconcileDbFiles` file enumeration in `externalIngestIndex.ts` (cap `maxResults`, process incrementally/in batches with real cancellation) instead of requesting `Number.MAX_SAFE_INTEGER` matches in one call, and consider whether `SearchOperation`'s unbounded `Map` accumulation in `mainThreadSearch.ts` should also guard against pathologically large result sets.

- **Behavior:**

  > Opening a large workspace with Copilot external ingest enabled must not be able to crash (OOM) the renderer regardless of workspace size or exclude-setting configuration. Workspace file enumeration for ingest reconciliation should be bounded or streamed/chunked so no single search call can produce or retain millions of in-memory results. Acceptance: reconciling a workspace with an extremely large file count completes without unbounded memory growth in the renderer, and a capped/streamed search path has a test proving the cap is enforced.
- **Trace:**

  > Root cause traced via rg/view on main: `reconcileDbFiles()` in extensions/copilot/src/platform/workspaceChunkSearch/node/codeSearch/externalIngestIndex.ts (around the `findFilesWithDefaultExcludes` call) requests all matches at once with `Number.MAX_SAFE_INTEGER` and `CancellationToken.None`, doing per-file `shouldTrackFile` filtering only after the full result set returns. Those matches flow through `src/vs/workbench/api/browser/mainThreadSearch.ts`'s `SearchOperation.addMatch()`, which stores every match keyed by URI in an unbounded `Map` with no size limit. The boundary: do not change ingest's correctness semantics (which files eventually get indexed) or touch unrelated search providers/text search — only the enumeration strategy and/or result accumulation ceiling. Related: issue body cites https://github.com/microsoft/vscode/blob/07f806f999227108933c2e30515b26eecc1fda74/extensions/copilot/src/platform/workspaceChunkSearch/node/codeSearch/externalIngestIndex.ts#L911 and https://github.com/microsoft/vscode/blob/07f806f999227108933c2e30515b26eecc1fda74/src/vs/workbench/api/browser/mainThreadSearch.ts#L107.
- **Open decisions:**
  - Should the fix cap/limit the search's maxResults (risking incomplete ingest) or switch to incremental/streamed enumeration with real cancellation support?
  - Should mainThreadSearch's SearchOperation itself gain a hard ceiling on accumulated matches (protecting all search consumers), or is this strictly an ingest-caller responsibility?
