# Issue #239534 — Single character change triggers 3 'textDocument/inlayHint' request in Python

[https://github.com/microsoft/vscode/issues/239534](https://github.com/microsoft/vscode/issues/239534)

## Summary

Still reproduces on current main: the inlay hints controller's scheduling logic in onDidChangeModelContent fires redundant LSP requests because the RunOnceScheduler's async callback allows re-entry from concurrent event sources (scroll change and a delayed timeout). Two team members confirmed the reproduction.

## Change summary

A single character edit triggers 3 textDocument/inlayHint LSP requests instead of 1, wasting language server resources.

## Best solution

Consolidate the scheduling in `inlayHintsController.ts` so that when a content change fires, the scroll-change handler and the delayed timeout don't each independently re-schedule while the async provider call is still in flight. The CancellationStore at line 241 already cancels stale requests, but the scheduler still dispatches them. A guard (e.g. checking if an in-flight request already covers the same ranges, or coalescing the scroll/content/timeout paths into a single pending request) would reduce the 3 requests to 1.

- **Fix prompt:**

  > In src/vs/editor/contrib/inlayHints/browser/inlayHintsController.ts, the `_update()` method creates a `RunOnceScheduler` (line 243) whose callback is async (it awaits `InlayHintsFragments.create`). The problem: once the scheduler fires and enters its async callback, `isScheduled()` returns false, so concurrent event handlers re-schedule and trigger duplicate provider requests. Three sources cause this on a single keystroke: (1) `onDidChangeModelContent` calls `scheduler.schedule()` at line 299; (2) `onDidScrollChange` calls `scheduler.schedule()` at line 286 (typing can cause scroll); (3) a `disposableTimeout` at line 297 calls `scheduler.schedule(0)` after 800ms+. Fix: add an in-flight guard (e.g. a boolean `_isRequestInFlight` or similar) so that while the async callback is executing, new `schedule()` calls are deferred until it completes — then re-schedule once if any were suppressed. Alternatively, restructure so the scroll handler skips scheduling when a content-change-triggered request is already pending. Do NOT remove the delayed re-schedule at line 297 entirely — its purpose is to allow a full redraw after the cursor settles — but ensure it doesn't create a redundant request when one is already in flight. Validate with a test that counts calls to `InlayHintsFragments.create` after a simulated content change + scroll change, asserting exactly 1 call instead of 3.
