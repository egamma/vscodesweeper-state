# Issue #333819 — Confirmation request is shown in wrong chat

[https://github.com/microsoft/vscode/issues/333819](https://github.com/microsoft/vscode/issues/333819)

## Summary

The wrong-chat routing remains possible on current main when multiple chat widgets share a session resource. The related fix PR was closed without merging, and the team-authored accepted bug must remain open while maintainers decide whether to support this startup-page combination or remove it.

## Change summary

A confirmation originating in the chat view can be associated with the Agent Sessions welcome-page chat instead.

## Best solution

Decide whether `agentSessionsWelcomePage` remains a supported startup editor; if it does, confirmation handling must preserve the originating chat location when resolving among widgets that share a session resource.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chat.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatWidgetService.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatListWidget.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatContentParts.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatConfirmationContentPart.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatErrorConfirmationPart.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/chatContentParts/chatErrorConfirmationPart.test.ts`
- **Validation:** Run the targeted `ChatErrorConfirmationContentPart` browser unit test with a view-chat and welcome-chat widget sharing one session resource; confirming from each surface must retain that surface's `ChatAgentLocation` and must not select the other widget.
- **Behavior:**

  > When the same chat session is visible in both the chat view and the Agent Sessions welcome-page surface, a confirmation must remain associated with the surface where the user acted. Accepting, rejecting, or retrying there must not route request options through the other widget. Existing behavior for sessions displayed in only one widget must remain unchanged.
- **Trace:**

  > `ChatWidgetService.getWidgetBySessionResource` in `src/vs/workbench/contrib/chat/browser/widget/chatWidgetService.ts` returns the first widget matching a session resource and cannot distinguish two locations. Confirmation paths in `chatConfirmationContentPart.ts` and `chatErrorConfirmationPart.ts` use that lookup to derive request options. Current render context does not carry a chat location through `IChatContentPartRenderContext`, and `ChatListWidget` passes renderer options without adding its `_location`. The unmerged https://github.com/microsoft/vscode/pull/333838 confirms this same trace and sketches regression coverage, but it cannot be treated as a fix. Keep the boundary to multi-widget confirmation routing; do not alter confirmation semantics or unrelated widget lookups.
- **Open decisions:**
  - Should `workbench.startupEditor: agentSessionsWelcomePage` remain supported alongside the regular chat view, requiring location-correct confirmation routing, or should that startup-page capability be removed so the dual-surface scenario no longer exists?
