# Issue #332840 — Builtin GitHub MCP server: no way to select tools

[https://github.com/microsoft/vscode/issues/332840](https://github.com/microsoft/vscode/issues/332840)

## Summary

Still a real gap on main: agent-host MCP servers — including the built-in GitHub one — expose only a server-level on/off toggle, and their tool lists render read-only, so there is no per-tool selection anywhere in Chat Customizations; the member comment confirms the gap is general rather than specific to the built-in server, so the item should stay open as the design question for per-tool MCP enablement.

## Change summary

Let users enable/disable individual tools of the built-in GitHub MCP server, the way tool selection works for other MCP servers.

## Best solution

Decide and implement per-tool enablement for agent-host MCP servers as a whole (a tool-level enablement concept in the agent-host customization protocol plus toggles in the connected-sources rows of toolsListWidget.ts), with the built-in GitHub server feeding the selected subset into its X-MCP-Tools header in githubMcpServer.ts.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/aiCustomization/toolsListWidget.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostToolSetEnablementService.ts`, `src/vs/platform/agentHost/node/shared/mcpCustomizationController.ts`, `src/vs/platform/agentHost/node/shared/githubMcpServer.ts`, `src/vs/platform/agentHost/common/state/protocol/channels-session/state.ts`
- **Validation:** A Chat Customizations tools-list test asserting that a connected MCP server's child tool rows expose an enablement toggle whose state round-trips through the enablement service, plus a githubMcpServer test asserting the X-MCP-Tools header reflects a user-selected tool subset.
- **Behavior:**

  > In Chat Customizations, expanding an MCP server under 'Connected Sources' — including the built-in GitHub MCP server — lets the user enable or disable individual tools, not just the whole server. The chosen subset persists across sessions at the agreed scope and is what the agent actually sees; for the built-in GitHub server the enabled subset is what is advertised to the remote server. Server-level enable/disable keeps working, and a disabled server still hides all of its tools. Acceptance: toggles appear and round-trip on connected server tool rows, and the built-in GitHub server's advertised tool list matches the selection.
- **Trace:**

  > The connected-sources rows are built in `_computeConnectedServerEntries` in src/vs/workbench/contrib/chat/browser/aiCustomization/toolsListWidget.ts; tools are listed via `server.listTools()` for display only, and `ToolsConnectedRowRenderer.renderElement` shows a CustomizationToggle solely when `entry.server` is set, so child tool rows have no enablement control. Tool-level state today lives in IAgentHostToolSetEnablementService (`setToolEnabled`) and only covers tool sets from extensions/internal sources. The agent-host protocol has no tool-level customization (`CustomizationType` in src/vs/platform/agentHost/common/state/protocol/channels-session/state.ts), and the built-in GitHub server is a single on/off customization bound to `chat.agentHost.githubMcpServer.enabled` (src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:1910) whose tool list is fixed in `getGitHubMcpTools`/`createGitHubMcpServerConfiguration` (src/vs/platform/agentHost/node/shared/githubMcpServer.ts, `X-MCP-Tools` header). Boundary: do not change server-level enablement semantics, the gh-CLI-aware default tool list, or the setting that gates the built-in server. Uncertainty starts at whether per-tool state belongs in the agent-host customization protocol or stays a workbench-side enablement store, and whether the built-in GitHub server's header must be recomputed on selection change (which implies a session relaunch). Related: https://github.com/microsoft/vscode/issues/332840.
- **Open decisions:**
  - Does per-tool selection apply to all agent-host MCP servers uniformly, or only to the built-in GitHub server as a special case?
  - At what scope does a tool selection persist — global, workspace, or per session — and does it follow the existing MCP server enablement scope?
  - For the built-in GitHub server, is changing the selection allowed to require a session relaunch (the tool list is advertised in the X-MCP-Tools header at startup), or must it apply live?

## Evidence

- **no per-tool enablement on main:** In src/vs/workbench/contrib/chat/browser/aiCustomization/toolsListWidget.ts, the 'Connected Sources' group builds rows via `_computeConnectedServerEntries`; only rows carrying `entry.server` get a CustomizationToggle (`data.toggle.domNode.style.display = entry.server ? '' : 'none'`), while child tool rows are rendered label-only. Tool-level toggles exist only for extension/internal tool sets (`setToolEnabled`), not for agent-host MCP servers.
- **protocol has no tool customization:** src/vs/platform/agentHost/common/state/protocol/channels-session/state.ts `CustomizationType` has plugin/directory/agent/skill/prompt/rule/hook/mcpServer — no tool-level type, so per-tool enablement has no representation in the agent-host customization protocol today.
- **built-in GitHub server is all-or-nothing:** src/vs/platform/agentHost/node/shared/githubMcpServer.ts computes a fixed tool list (`getGitHubMcpTools`) into the `X-MCP-Tools` header, and src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:1910 maps the built-in server to the single on/off setting `chat.agentHost.githubMcpServer.enabled` (AgentHostGitHubMcpServerEnabledSettingId).
- **thread:** dmitrivMS (MEMBER) notes tool management is absent for other MCP servers in Chat Customizations too — https://github.com/microsoft/vscode/issues/332840#issuecomment-0 — so the premise of an inconsistency specific to the built-in server does not hold; the remaining ask is general per-tool MCP control.
