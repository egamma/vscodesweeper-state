# Issue #339841 — Couldn't run simple terminal command: Sandboxing is enabled but this policy is not supported on this host

[https://github.com/microsoft/vscode/issues/339841](https://github.com/microsoft/vscode/issues/339841)

## Summary

Team-authored report (hard keep-open rule applies regardless) describing a real gap: on Windows ARM with `chat.agent.sandbox.enabled` on, a terminal command fails with a raw SDK `GenericFailure` ('Sandboxing is enabled but this policy is not supported on this host...') and no notification appears in either the editor or Agents window, even though `AgentHostSandboxNotification`/`CopilotSandboxDiagnostics` exist specifically to surface unsupported-sandbox-capability warnings.

## Change summary

On Windows ARM with sandboxing enabled, a simple terminal command fails with a cryptic 'Sandboxing is enabled but this policy is not supported on this host' GenericFailure and no explanatory UI notification is shown.

## Best solution

Make the existing sandbox-unsupported notification path (`CopilotSandboxDiagnostics`/`AgentHostSandboxNotification`) reliably catch this case — either by having `getHostSupport()`'s capability check include whatever 'network_filtering on Windows ARM' condition this host hits, or by routing the SDK's `GenericFailure` through the same chat-input notification surface — so the user sees a clear, actionable message instead of (or in addition to) the inline tool error.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotSandboxDiagnostics.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSandboxNotification.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`
- **Validation:** A reproduction on a Windows ARM host (or a host-support mock returning the same capability shape) showing the sandbox-unsupported notification appears before/alongside the command failure.
- **Trace:**

  > CopilotSandboxDiagnostics.update() (src/vs/platform/agentHost/node/copilot/copilotSandboxDiagnostics.ts) calls rpc.sandbox.getHostSupport() and filters returned capabilities to a fixed allow-list (shell, filesystem_enumeration, network, network_filtering, denied_paths) before writing agentSandboxDiagnosticsMetaKey, which AgentHostSandboxNotification.ts renders as a dismissible warning. The reporter's error text ('Windows sandbox network filtering needs local network access... BaseContainer reaches the local listener over host loopback') suggests a 'network_filtering'-shaped failure, which the filter does already allow through — so either the host-support probe didn't flag it proactively (the real failure only surfaced when the command actually ran), or the update() call hadn't completed/was racing the first command. Do not change the capability allow-list without confirming which case this is.

## Evidence

- **diagnostics path:** src/vs/platform/agentHost/node/copilot/copilotSandboxDiagnostics.ts queries rpc.sandbox.getHostSupport() and writes reasons into the agentSandboxDiagnosticsMetaKey session meta, which src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSandboxNotification.ts turns into a chat-input warning notification — but the reporter saw no notification at all.
- **capability filter:** copilotSandboxDiagnostics.ts line ~46-52 only surfaces capabilities named 'shell', 'filesystem_enumeration', 'network' (when outbound requested), 'network_filtering', or 'denied_paths' (when configured) — it's unclear whether the specific Windows-ARM local-network/loopback condition from the error message maps to one of these or falls through uncaught.
- **non-default setting:** Reporter's own comment confirms `chat.agent.sandbox.enabled: "on"` is a non-default setting, and the host is Windows ARM — a narrow combination.
