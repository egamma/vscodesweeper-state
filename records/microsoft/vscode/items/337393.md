No commenter independently confirms reproduction, and 'use them normally' does not identify the output workload or duration.
- **Current renderer lifecycle:** src/vs/workbench/contrib/terminal/browser/xterm/xtermTerminal.ts:908–975 loads @xterm/addon-webgl, guards overlapping loads, disposes the previous renderer before replacement, and handles context loss. Lines 1053–1071 dispose the addon, and lines 1181–1186 invoke renderer disposal when the terminal is disposed. These paths do not conclusively explain GPU-process memory growth during normal use; environment-dependent GPU allocation cannot be verified from this source alone.
- **Workaround is not intended coverage:** src/vs/workbench/contrib/terminal/common/terminalConfiguration.ts:345–354 registers terminal.integrated.gpuAcceleration with auto/on/off and default auto. The off option explicitly trades rendering speed for reliability; its effectiveness does not establish that excessive memory usage under the default is intentional.
- **Reporter-linked issue has different evidence:** https://github.com/microsoft/vscode/issues/333977 is open, but reports renderer handle leakage and OS freezes, including with terminal GPU acceleration disabled. Its reporter later identified Claude Code terminal streaming as the trigger and withdrew the claimed version regression: https://github.com/microsoft/vscode/issues/333977#issuecomment-5524860740. This does not establish the same root cause as the extension-disabled GPU-process OOM report.
