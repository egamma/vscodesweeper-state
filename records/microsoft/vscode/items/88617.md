# Issue #88617 — onDebugInitialConfigurations activation event causes extensions to load when pressing F5 to run other projects

[https://github.com/microsoft/vscode/issues/88617](https://github.com/microsoft/vscode/issues/88617)

## Summary

The unwanted activation remains source-reproducible on current main: pressing F5 without a known debug type broadcasts `onDebugInitialConfigurations` before showing the debugger picker. The issue was deliberately reopened for future work and moved to Backlog in March 2026, so it should remain open while the discovery/activation contract is redesigned.

## Change summary

Avoid activating every initial-debug-configuration provider when F5 is pressed for a project whose debugger type is not yet known.

## Best solution

Separate debugger discovery from provider activation so the initial picker can be populated without loading every debugger extension, then activate only the selected debugger's provider while preserving discoverability for provider-backed configurations.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugAdapterManager.ts`, `src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts`, `src/vs/workbench/contrib/debug/test/browser/debugConfigurationManager.test.ts`
- **Validation:** Add a debug browser test that invokes the no-known-type F5/guess-debugger path with multiple initial-configuration providers and verifies that unrelated providers are not activated before selection, while the selected debugger can still supply its initial configuration; retain a manual Extension Development Host check using the mock-debug reproduction.
- **Behavior:**

  > When F5 is pressed without a launch configuration or an active editor that identifies a debugger, VS Code must not activate unrelated extensions merely to populate the debugger picker. After the user chooses a debugger, that debugger's initial-configuration provider must still activate and participate normally. Debugging with an already known type and existing launch configurations must remain unchanged.
- **Trace:**

  > `DebugService.createSession` in `src/vs/workbench/contrib/debug/browser/debugService.ts` enters `DebugAdapterManager.guessDebugger(false)` when no debug type is available. In `src/vs/workbench/contrib/debug/browser/debugAdapterManager.ts`, the no-language candidate path broadcasts `onDebugInitialConfigurations` before filtering candidates, and `activateDebuggers` sends the unsuffixed event to all matching extensions. `ConfigurationManager.provideDebugConfigurations` also broadcasts the same event before filtering registered providers by type. The uncertainty begins at debugger discovery: current candidate visibility can depend on runtime provider registration, so avoiding eager activation may change which options appear before a user selects a debugger. Preserve known-type activation, dynamic configuration behavior, and existing launch-configuration resolution. Related precedent: https://github.com/microsoft/vscode/issues/37929; distinct newer task activation report: https://github.com/microsoft/vscode/issues/175202.
- **Open decisions:**
  - Should the initial debugger picker show only debuggers discoverable from declarative contributions, or must provider-only candidates remain visible before any extension is activated?
  - Should `onDebugInitialConfigurations` gain type-specific activation semantics while retaining the existing unsuffixed event for compatibility, or should discovery move away from this activation event entirely?

## Evidence

- **current source path:** `DebugService.createSession` calls `DebugAdapterManager.guessDebugger(false)` when no configuration type is known (`src/vs/workbench/contrib/debug/browser/debugService.ts`). In `src/vs/workbench/contrib/debug/browser/debugAdapterManager.ts`, `guessDebugger` calls `activateDebuggers('onDebugInitialConfigurations')` when there is no identifying editor language, before constructing the debugger picker.
- **broadcast activation:** `DebugAdapterManager.activateDebuggers` invokes the unsuffixed `extensionService.activateByEvent(activationEvent)` and `onDebug`; no type is supplied from the reported F5 path, so every extension declaring `onDebugInitialConfigurations` is eligible for activation.
- **older precedent:** https://github.com/microsoft/vscode/issues/37929 documents the same underlying discovery constraint: initial-configuration providers were activated because VS Code did not yet know which debugger the user would choose. It is closed and therefore cannot be a duplicate canonical; its maintainer discussion also shows that avoiding activation requires changing debugger discovery rather than treating the report as unexplained extension behavior.
- **reopen and backlog decision:** This issue was closed with `*out-of-scope` on 2020-11-02, then explicitly reopened by a debug maintainer because the team might tackle it later. It was subsequently assigned to the Backlog milestone on 2026-03-04.
- **related issue distinction:** https://github.com/microsoft/vscode/issues/175202 is newer and currently attributes its reproduced extra activation to `onTaskType:docker-build`, not `onDebugInitialConfigurations`; it does not satisfy the stronger canonical-duplicate bar for this re-reviewed item.
