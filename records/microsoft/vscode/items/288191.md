# Issue #288191 — Can't apply changes from background agent after undoing previously

[https://github.com/microsoft/vscode/issues/288191](https://github.com/microsoft/vscode/issues/288191)

## Summary

Keep open: the current background-session implementation intentionally advances its baseline after Apply, so undoing workspace changes does not make them available to apply again. This team-authored request needs a working-set/reapply behavior decision, not a judgment close.

## Change summary

Allow background-agent changes to be applied again after they were applied successfully and then discarded through SCM.

## Best solution

Provide an explicit way to recover previously applied background-session changes without overwriting unrelated workspace edits. Agree on whether ordinary Apply restores discarded changes or a separate reapply action does so, alongside the working-set discussion in https://github.com/microsoft/vscode/issues/291756.

- **Behavior:**

  > After applying background-agent changes and discarding them through SCM, users need a discoverable way to restore those same session changes without asking the agent to regenerate them. Restoration must preserve unrelated workspace edits and must not duplicate changes that remain applied. Acceptance should cover discarding all applied files and discarding only one of several applied files. The ordinary Apply action versus a separate reapply action remains a maintainer decision.
- **Trace:**

  > In extensions/copilot/src/extension/chatSessions/vscode-node/chatSessionWorktreeServiceImpl.ts, applyWorktreeChanges computes committed-session patches from baseCommit to branchName and intentionally advances baseCommit to the session branch HEAD after success. A subsequent Apply with no new agent commits returns on an empty patch; SCM discard affects the destination workspace, not that saved session baseline. The Apply command in copilotCLIChatSessionsContribution.ts delegates to this method, and package.json exposes the corresponding command surfaces. Preserve incremental application of newly generated changes, legacy stash-migration behavior, and protection of unrelated destination edits. https://github.com/microsoft/vscode/issues/291756#issuecomment-3822418060 records the outstanding-versus-historical working-set distinction and an unresolved consistency discussion. The investigation establishes the committed-session behavior without runtime execution; it does not establish a finalized restoration contract.
- **Open decisions:**
  - Should ordinary Apply restore previously applied changes discarded through SCM, or should restoration require a separate explicit reapply action?
  - Should previously applied files remain discoverable in the background session's normal working set, or only through a separate historical-changes surface?
