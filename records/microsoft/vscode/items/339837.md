# Issue #339837 — Browser: blank child page shouldn't auto-select the URL bar

[https://github.com/microsoft/vscode/issues/339837](https://github.com/microsoft/vscode/issues/339837)

## Summary

Fresh, credible team-reported bug (screenshot included) with a plausible root cause traced in source; keeping open. The fix needs a design decision on how to distinguish a script-opened child tab from a genuine new blank tab, so this is plan-tier rather than a bounded implement.

## Change summary

A child browser tab opened via window.open() with no URL (a blank page) incorrectly auto-selects/focuses the URL bar, as if it were a manually opened new tab.

## Best solution

In BrowserNavigationFeatures.tryFocus() (src/vs/workbench/contrib/browserView/electron-browser/features/browserNavigationFeatures.ts), suppress the auto-open-picker heuristic for tabs created as a child/popup (window.open) rather than a plain new tab — likely by threading the existing parentViewId/opener signal (already captured in IBrowserViewEditorOpenOptions and electron-main's setWindowOpenHandler createWindow call) through to BrowserEditorInput so tryFocus() can check it.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/browserView/electron-browser/features/browserNavigationFeatures.ts`, `src/vs/workbench/contrib/browserView/common/browserEditorInput.ts`, `src/vs/platform/browserView/electron-main/browserView.ts`, `src/vs/platform/browserView/common/browserView.ts`
- **Validation:** A test (or manual check) confirming that calling window.open() with no URL from an integrated browser page opens a new tab without the URL bar being focused/selected, while an explicitly user-opened new blank tab (e.g. via the New Tab command) still auto-opens the URL picker as before.
- **Behavior:**

  > When a page running inside the integrated browser calls window.open() (including with no arguments, landing on about:blank), the resulting child tab should open without the URL input being auto-focused/selected. A genuine user-initiated new blank tab (e.g. the 'New Integrated Browser Tab' command) should continue to auto-open the URL picker as today. Acceptance: opening a script-created child tab leaves the tab/webview focused, not the URL bar; the existing new-tab-picker behavior for manually created tabs is unchanged.
- **Trace:**

  > BrowserNavigationFeatures.tryFocus() (src/vs/workbench/contrib/browserView/electron-browser/features/browserNavigationFeatures.ts, ~lines 307-324) decides whether to auto-open the URL picker using `!url && !this._hasInitiatedNavigation`, where url comes from `this.editor.model?.url ?? input.url`. For a window.open()-created child tab this condition can still read as 'no url yet', so the picker opens and selects the text via browserUrlBarWidget.ts's `_selectAll()`. The main-process side already distinguishes this case: setWindowOpenHandler's createWindow callback in src/vs/platform/browserView/electron-main/browserView.ts (~line 216-220) passes `parentViewId: id` when creating the child view, and IBrowserViewEditorOpenOptions (src/vs/platform/browserView/common/browserView.ts ~line 292) already models parentViewId — but this is currently only consumed by browserViewWorkbenchService.ts to place the new tab in the right editor group, not forwarded into BrowserEditorInput for tryFocus() to consult. The boundary: do not change the picker behavior for tabs with no parentViewId (plain new tabs) or tabs that have already started navigating (`_hasInitiatedNavigation` true) — only the no-url, has-parent-view(-id) case should skip the auto-picker. Related: https://github.com/microsoft/vscode/issues/339435 (closed) is in the same window.open()/child-page area.
- **Open decisions:**
  - Should the signal distinguishing a 'don't auto-focus' tab be the existing parentViewId (any child/popup tab) or a narrower flag specific to window.open() with no explicit URL — i.e. should a window.open('https://example.com') child tab (which already has a real destination) also skip the auto-picker, or only a truly blank one?
  - Does suppressing the auto-picker mean the new child tab receives no initial focus at all, or does focus move into the page content area instead of the URL bar?

## Evidence

- **suspect heuristic:** BrowserNavigationFeatures.tryFocus() in src/vs/workbench/contrib/browserView/electron-browser/features/browserNavigationFeatures.ts (~line 307-324) auto-opens the URL picker (which selects all text, via browserUrlBarWidget.ts's openUrlPicker/_selectAll) whenever `!url && !this._hasInitiatedNavigation` — intended for user-opened blank new tabs, but also fires for script-opened child tabs that land on about:blank before navigating further.
- **existing signal not wired through:** src/vs/platform/browserView/electron-main/browserView.ts's setWindowOpenHandler already passes `parentViewId: id` when creating a child view (line ~219), and IBrowserViewEditorOpenOptions (src/vs/platform/browserView/common/browserView.ts line ~292) carries parentViewId, but BrowserEditorInput (src/vs/workbench/contrib/browserView/common/browserEditorInput.ts) does not currently expose this to the navigation feature, so tryFocus() cannot distinguish a popup child from a plain new tab.
- **related prior issue:** https://github.com/microsoft/vscode/issues/339435 (closed) dealt with document.write() to an about:blank child page — same window.open()/child-page interaction area, suggesting active recent work here.
