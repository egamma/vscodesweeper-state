# Issue #319371 — cursoring down through Arabic letters in parenthesis is odd

[https://github.com/microsoft/vscode/issues/319371](https://github.com/microsoft/vscode/issues/319371)

## Summary

The defect remains explainable on current main: vertical movement approximates screen position with logical columns even though that mechanism explicitly does not work well for RTL text, while horizontal movement handles only whole-line direction rather than local bidirectional runs. The existing editor RTL routing is appropriate and the issue should remain open.

## Change summary

Cursor movement through Arabic text containing parenthesized bidirectional runs jumps between unexpected visual positions.

## Best solution

Make vertical movement preserve the caret's rendered horizontal position across bidirectional lines and define consistent left/right behavior at local bidi-run boundaries, without changing LTR navigation semantics.

- **Behavior:**

  > In mixed Arabic and neutral punctuation, arrow-key navigation must move the caret predictably through adjacent visual positions. Moving vertically through the parenthesized lines should preserve the intended rendered horizontal position rather than jumping across a bidi run. Moving left and right should not flip-flop between distant visual positions. Existing LTR navigation, selection extension, grapheme handling, and wrapped-line behavior must remain unchanged.
- **Trace:**

  > On current main, MoveOperations.vertical in src/vs/editor/common/cursor/cursorMoveOperations.ts derives both positions through CursorColumns, whose documentation in src/vs/editor/common/core/cursorColumns.ts explicitly says the approximation does not work well for RTL text. CursorMoveCommands._moveLeft and _moveRight in src/vs/editor/common/cursor/cursorMoveCommands.ts use only a line-level TextDirection switch, while src/vs/editor/browser/viewParts/viewLines/viewLine.ts delegates actual mixed-direction placement to browser bidi rendering. Neutral parentheses can therefore reorder visually without being represented in the logical-column movement model. The uncertainty starts at how rendered caret stops should be exposed to common cursor commands without coupling model-only navigation to DOM layout. Preserve LTR, grapheme, injected-text, wrapping, and selection semantics.
- **Open decisions:**
  - Should left/right navigation follow visual bidi caret order within each run or preserve logical text order while only vertical movement becomes render-aware?
  - Which layer should provide rendered bidi caret positions without introducing a browser DOM dependency into common cursor movement?
  - How should visual-position state be preserved across wrapped lines, injected text, and lines with different base directions?
