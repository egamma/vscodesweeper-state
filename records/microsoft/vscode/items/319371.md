# Issue #319371 — cursoring down through Arabic letters in parenthesis is odd

[https://github.com/microsoft/vscode/issues/319371](https://github.com/microsoft/vscode/issues/319371)

## Summary

The current editor source still mixes logical-column cursor movement with browser-computed bidi rendering, which explains the unstable movement around neutral parentheses in Arabic text. The older RTL issues are related but do not report this same parenthesis-triggered navigation symptom, so the stronger duplicate bar for this re-reviewed issue is not met.

## Change summary

Cursor movement through Arabic lines becomes visually unstable when it enters parenthesized text.

## Best solution

Keep logical text ordering intact while making vertical and horizontal navigation through mixed-direction runs and neutral punctuation visually predictable. The editor team should first settle the intended visual-versus-logical cursor semantics, including selection behavior, then cover the supplied Arabic sample with a browser-level regression test.

## Plan brief

- **Likely files:** `src/vs/editor/common/cursor/cursorMoveOperations.ts`, `src/vs/editor/browser/viewParts/viewLines/viewLine.ts`, `src/vs/editor/browser/viewParts/viewLines/viewLines.ts`, `src/vs/editor/browser/viewParts/viewCursors/viewCursor.ts`, `src/vs/editor/test/browser/controller/cursor.test.ts`
- **Validation:** Create a browser-level editor regression test using the issue's Arabic sample that records rendered cursor positions while moving up, down, left, and right through the parenthesized runs; verify movement follows the chosen semantics without oscillating or unexpectedly reversing, while existing LTR cursor tests remain unchanged.
- **Behavior:**

  > In mixed-direction Arabic text containing parentheses, moving the cursor with arrow keys must remain predictable when crossing into, through, and out of the parenthesized run. Repeated up/down navigation should not make the caret flip between unrelated visual positions, and horizontal movement must follow the explicitly chosen visual or logical convention consistently. Selection variants must follow the same documented convention. The supplied nine-line sample is the acceptance fixture.
- **Trace:**

  > Current movement is logical-column based: MoveOperations.leftPosition/rightPosition adjust string offsets, and MoveOperations.vertical in src/vs/editor/common/cursor/cursorMoveOperations.ts derives a target from CursorColumns rather than rendered bidi geometry. Rendering follows a separate path: src/vs/editor/browser/viewParts/viewLines/viewLine.ts delegates mixed-direction ordering to browser layout and exposes DOM-derived ranges through getVisibleRangesForRange(), which viewLines.ts uses for rendered positions. Parentheses are bidi-neutral, so browser placement can diverge sharply from the logical column assumed by movement. https://github.com/microsoft/vscode/issues/65648 records unresolved disagreement over visual versus logical arrow semantics, while https://github.com/microsoft/vscode/issues/83365 concerns neutral punctuation rendering; neither is an exact canonical for this re-reviewed symptom. Preserve plain-text logical order and existing LTR navigation behavior; do not broaden this issue into general RTL paragraph alignment.
- **Open decisions:**
  - Within mixed-direction runs, should left/right arrows follow the caret's visual screen direction or advance through logical text order?
  - When moving up or down between bidi lines, should VS Code preserve the rendered horizontal pixel position or the logical character column?
  - Should Shift+Arrow selection use the same movement convention as an unmodified arrow key, or preserve logical-order selection semantics?

## Evidence

- **current source path:** On current main, src/vs/editor/common/cursor/cursorMoveOperations.ts implements left/right movement by incrementing or decrementing logical UTF-16 columns, while vertical() preserves CursorColumns.visibleColumnFromColumn() computed from the raw line rather than the rendered bidi position.
- **rendering mismatch:** src/vs/editor/browser/viewParts/viewLines/viewLine.ts marks mixed RTL lines with dir="ltr" and delegates bidi placement to the browser; its DOM-backed getVisibleRangesForRange() can determine rendered positions, but that geometry is not used by MoveOperations when choosing the next cursor position.
