# Issue #232984 — Editor GPU: Handle the case where glyphs do not fit into standard atlas page slabs

[https://github.com/microsoft/vscode/issues/232984](https://github.com/microsoft/vscode/issues/232984)

## Summary

Keep open: current source handles some oversized-slab allocations, but extreme zoom still exposes hard atlas limits without graceful recovery. No verified fixing commit or older canonical reporting the same symptom was found.

## Change summary

Prevent GPU editor rendering from breaking when high-DPI zoom produces glyphs that exceed ordinary atlas allocation capacity.

## Best solution

Make GPU text rendering remain usable across supported zoom levels, including allocation failures, while preserving GPU texture and buffer limits. Diagnose the zoom-driven capacity failure before choosing recovery behavior; the existing larger-slab overflow path should remain intact.

## Evidence

- **reported reproduction:** https://github.com/microsoft/vscode/issues/232984 describes enabling GPU acceleration on macOS or a high-DPI display and repeatedly zooming in until rendering breaks. The author's comment points directly to TextureAtlasPage's failed-allocation handling.
- **partial handling already exists:** src/vs/editor/browser/gpu/atlas/textureAtlasSlabAllocator.ts, TextureAtlasSlabAllocator.allocate, enlarges slabs for the first glyph on an empty page and returns undefined for oversized slabs on populated pages. TextureAtlas._tryGetGlyph then tries another page. src/vs/editor/test/browser/gpu/atlas/textureAtlas.test.ts explicitly covers both oversized-slab cases, so the retained TODO alone does not prove those cases remain broken.
- **remaining source failure path:** TextureAtlasSlabAllocator.allocate throws when glyph dimensions exceed the canvas. TextureAtlas._getGlyphFromNewPage throws at the 16-page limit. In src/vs/editor/browser/gpu/viewGpuContext.ts, DPR changes clear the shared atlas, but TextureAtlas.clear retains the pageSize calculated at construction. Slab dimensions are recalculated from the new DPR, while GlyphRasterizer scales glyphs with fontSize × DPR. These paths retain allocation failure conditions during zoom; no runtime reproduction or exact zoom threshold was measured.
- **neighboring fix is insufficient:** https://github.com/microsoft/vscode/commit/c9e34148a99e73204dbde2b3db9fbe51b41ee48e only clamps the slab-size shift for negative zoom levels. Its diff does not address positive extreme zoom, oversized glyph recovery, or page exhaustion, so it is not a fixing commit for this report.
- **canonical search:** https://github.com/microsoft/vscode/issues/221145 is open but tracks the overall WebGPU renderer, not this same observable allocation failure. https://github.com/microsoft/vscode/issues/227116 concerns packing efficiency and is closed; https://github.com/microsoft/vscode/issues/232979 concerns a GPUBuffer error and is also closed. Searches for glyph/atlas and atlas/zoom reports found no verified open same-symptom canonical satisfying the prior-review duplicate bar.
