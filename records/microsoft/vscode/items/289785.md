# Issue #289785 — Search result navigation does not provide target selection/range to custom editors (webview editors)

[https://github.com/microsoft/vscode/issues/289785](https://github.com/microsoft/vscode/issues/289785)

## Summary

Keep open: current main has a proposed navigation controller for custom text editors, but no stable API covering the requested custom-editor navigation. The existing search/custom-editors routing is appropriate, and the related reports do not establish an eligible duplicate canonical.

## Change summary

Expose the clicked Search match's target range to custom editors so they can reveal the exact match, including subsequent clicks in an already-open editor.

## Best solution

Provide a stable, panel-specific navigation contract that delivers Search target ranges to custom editors without parsing internal search output. Build on the existing proposed custom-text-editor navigation capability and have API owners settle the public contract and coverage for CustomEditorProvider.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vscode-dts/vscode.proposed.customTextEditorNavigation.d.ts`, `src/vs/workbench/contrib/customEditor/browser/customEditorInput.ts`, `src/vs/workbench/api/common/extHostCustomEditors.ts`, `src/vs/workbench/api/browser/mainThreadCustomEditors.ts`, `src/vs/workbench/api/test/browser/mainThreadCustomTextEditorNavigation.test.ts`
- **Validation:** With a custom editor as the default for a file containing two distant Search matches, click each match and verify that its exact range reaches the intended panel both on initial opening and when the panel is already open. Validate both provider types within the agreed public contract, preserve focus behavior, and run the existing mainThreadCustomTextEditorNavigation tests plus regression coverage for Search-triggered navigation.
- **Behavior:**

  > Clicking a global Search match in a file handled by a custom editor must make that match's exact source range available to the owning extension. Clicking a different match in the same already-open file must deliver the new target, rather than retaining the first location. The extension decides how to reveal or highlight that range in its own UI. Acceptance must cover initial opening, repeated navigation, panel targeting, and the agreed provider coverage without relying on internal commands or parsing human-readable Search output.
- **Trace:**

  > SearchView.open in src/vs/workbench/contrib/search/browser/searchView.ts already passes the selected match through editor options. CustomEditorInput.applyOptions forwards that selection when an ICustomTextEditorNavigation controller exists. MainThreadCustomEditors creates the controller only for custom text providers advertising supportsNavigation, and ExtHostCustomEditors enforces the customTextEditorNavigation proposed-API gate. The proposal defines panel-local revealRange, selection, focus, and cancellation semantics, but stable vscode.d.ts exposes neither that controller nor an equivalent navigation contract for CustomEditorProvider. Preserve ordinary text-editor navigation and existing custom providers that do not opt in. The remaining uncertainty is the stable public API design and how its source-range contract applies to non-text custom providers; this is not merely a missing Search-side range calculation.
- **Open decisions:**
  - Should the stable API expose the proposed panel-local revealRange controller with its selection, focus, and cancellation semantics, or a smaller target-range notification contract?
  - What public source-range semantics should CustomEditorProvider expose when its custom document is not represented by a TextDocument?

## Evidence

- **Existing capability is proposed and text-only:** src/vscode-dts/vscode.proposed.customTextEditorNavigation.d.ts declares CustomTextEditorProvider.resolveCustomTextEditorNavigation and a panel-local CustomTextEditorNavigation.revealRange callback. src/vs/workbench/contrib/customEditor/browser/customEditorInput.ts:68–73 forwards options.selection to that controller. src/vs/workbench/api/common/extHostCustomEditors.ts:195–203 explicitly requires the customTextEditorNavigation proposed API; src/vs/workbench/api/browser/mainThreadCustomEditors.ts:323–324 enables it only for CustomEditorModelType.Text.
