## Change summary

Opening a workspace on an AFP volume prevents external Git operations from writing the index until the workspace is closed.

## Plan brief

- **Likely files:** `extensions/git/src/repository.ts`, `extensions/git/src/watch.ts`, `extensions/git/src/git.ts`, `src/vs/platform/files/node/watcher/nodejs/nodejsWatcherLib.ts`
- **Validation:** On a disposable netatalk-backed AFP repository with an upstream branch, compare external `git add` with the workspace closed and open in a current VS Code build; record Git output, Git-extension logs, mount path, and open handles. Any eventual fix must make staging succeed with the workspace open, retain status/upstream-change updates, and preserve the same operations on a local filesystem.
- **Behavior:**

  > The reporter can stage changes from an external terminal on an AFP repository when VS Code is closed, but receives `fatal: Unable to write new index file` when its workspace is open. Opening the workspace should not prevent external Git writes. First establish this behavior on a current build using a disposable AFP repository, then verify successful staging with the workspace open and continued Git status updates. The reported rebase/squash and Windows failures are related observations, not yet proven to share the AFP cause.
- **Trace:**

  > DotGitWatcher in extensions/git/src/repository.ts watches the Git directory and installs transient watchers for the current upstream ref; extensions/git/src/watch.ts delegates those requests to workspace.createFileSystemWatcher. getStatus in extensions/git/src/git.ts already disables optional Git locks. The current NodeJS watcher in src/vs/platform/files/node/watcher/nodejs/nodejsWatcherLib.ts reuses recursive watches where possible and refuses direct macOS fs.watch requests beneath /Volumes/, so reading the watcher registration alone does not confirm the current AFP failure. The uncertainty starts at the reporter's actual mount path and which handle or subprocess prevents index writing. https://github.com/microsoft/vscode/issues/327456 supplies a related remote-ref watcher diagnosis, but its ref-replacement symptom is not proof of this index-write failure. Preserve upstream notifications, local-filesystem behavior, and the network-watch crash safeguard associated with https://github.com/microsoft/vscode/issues/106879.

- **Independent confirmations:** https://github.com/microsoft/vscode/issues/95810#issuecomment-619033087 reports command-line Git becoming unusable with a workspace open on Windows. https://github.com/microsoft/vscode/issues/95810#issuecomment-656296377 reports blocked rebase/squash operations relieved by closing VS Code. These support the historical defect, but do not establish identical root causes or reproduction on current main.
- **Current Git-extension watcher path:** extensions/git/src/repository.ts:474-503 constructs DotGitWatcher, watches the Git directory, and creates a transient watcher using the upstream ref path. extensions/git/src/watch.ts:13-14 delegates to workspace.createFileSystemWatcher with RelativePattern(location, '*'). This remains a relevant investigation path, not conclusive proof of the AFP index-write failure.

The latter safeguard addresses the different network-disconnection crash in https://github.com/microsoft/vscode/issues/106879; it does not prove this AFP report fixed, particularly without the reporter's mount path.
