# Issue #163043 — New "initialSize" does not allow to fit the content

[https://github.com/microsoft/vscode/issues/163043](https://github.com/microsoft/vscode/issues/163043)

## Summary

Content-fitting sizing for contributed views remains unsupported: initialSize still controls proportional allocation, not content height. Keep this Backlog request open; the related testing-view report explicitly points here as the owner of the missing capability.

## Change summary

Allow extension-contributed views to fit their content instead of specifying only a numeric initial size.

## Best solution

Retain this as the canonical request for content-aware contributed-view sizing. Before implementation, the views owner should decide whether fitting applies only at first display or continues as content changes, and how it interacts with manual resizing.

## Evidence

- **Current contribution contract:** src/vs/workbench/api/browser/viewsExtensionPoint.ts:100,168–170,502–508 declares initialSize?: number, registers a numeric schema, and converts numeric values to a layout weight only when the extension owns the container. There is no content-fitting value on this contribution path.
- **Current sizing behavior:** src/vs/workbench/browser/parts/views/viewPaneContainer.ts:736–748 computes initial sizes as container height or width multiplied by each view's share of total weight. It does not measure content, so numeric initialSize does not satisfy the central request.
- **Built-in behavior is not an extension capability:** src/vs/workbench/contrib/files/browser/views/openEditorsView.ts:569–573,598–623 implements specialized content-dependent minimum and maximum body sizes using element counts and explorer.openEditors settings. Those settings govern Open Editors, not arbitrary extension-contributed views.
