# Issue #285106 — Unified management for persisted Copilot Chat history across different workspace contexts

[https://github.com/microsoft/vscode/issues/285106](https://github.com/microsoft/vscode/issues/285106)

## Summary

A real gap remains: current main indexes, lists, and deletes local chat sessions only within the active workspace context. No older issue reports the same observable management problem, and the newer orphan-recovery issue cannot be the canonical for this re-reviewed item.

## Change summary

Provide a unified way to discover, inspect, and delete locally persisted Copilot Chat sessions across workspace contexts.

## Best solution

Expose locally persisted sessions through a global management surface with workspace provenance and reliable deletion, while preserving workspace isolation when a session is opened for continued work. Decide separately whether single-file and folder contexts should automatically share or merge sessions.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts`, `src/vs/workbench/contrib/chat/common/chatService/chatService.ts`, `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/localAgentSessionsController.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentSessionsActions.ts`, `src/vs/workbench/contrib/chat/test/common/model/chatSessionStore.test.ts`, `src/vs/workbench/contrib/chat/test/browser/agentSessions/localAgentSessionsController.test.ts`
- **Validation:** Extend the chat session store and local agent sessions controller unit suites with two distinct workspace contexts, verifying that the chosen global surface lists each session with its origin, deletes only the selected persisted session, and preserves the decided opening and context-isolation semantics.
- **Behavior:**

  > Users can discover locally persisted Copilot Chat sessions even when their originating workspace is not active, identify the workspace context associated with each session, and delete selected sessions without reopening that workspace. Opening or continuing a cross-workspace session follows an explicitly chosen isolation policy rather than silently mixing workspace context. The existing active-workspace history experience and current-session deletion continue to work.
- **Trace:**

  > ChatSessionStore in src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts derives its file root and index scope from the active workspace; its index, reads, and deletion APIs cannot enumerate another workspace. LocalAgentSessionsController in src/vs/workbench/contrib/chat/browser/agentSessions/localAgentSessionsController.ts presents only `chatService.getHistorySessionItems()` from that store, while agentSessionsActions.ts delegates deletion back to the same active-context service. Workspace-transition migration copies sessions only when VS Code observes an in-window transition, so it does not supply global discovery. The closed https://github.com/microsoft/vscode/pull/295130 is not an implementation baseline. Preserve active-workspace session behavior and avoid conflating this management request with full-text search in https://github.com/microsoft/vscode/issues/254027, agent grounding in https://github.com/microsoft/vscode/issues/301174, or the narrower recovery work in https://github.com/microsoft/vscode/issues/305818.
- **Open decisions:**
  - Should inactive-workspace sessions appear directly in the existing sessions picker, or in a separate management-only view?
  - When a user opens an inactive-workspace session, should it remain read-only, open its original workspace, or be copied into the current workspace?
  - Should opening a file inside its parent folder automatically expose or merge sessions created in the single-file context, or should those contexts remain distinct and only be linked through the global manager?
  - Should bulk deletion apply globally, per originating workspace, or only to an explicit selection?

## Evidence

- **workspace-scoped storage:** On current main, src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts constructs `storageRoot` from the active workspace ID and stores `ChatIndexStorageKey` at `StorageScope.WORKSPACE` except for empty windows. `getIndex()`, `deleteSession()`, and `clearAllSessions()` therefore operate only on that active context.
- **workspace-scoped UI:** src/vs/workbench/contrib/chat/browser/agentSessions/localAgentSessionsController.ts obtains history exclusively through `chatService.getHistorySessionItems()`, which reads the active `ChatSessionStore` index; there is no global workspace enumeration or provenance in this controller.
- **partial current behavior:** ChatSessionStore.handleWorkspaceTransition copies session files during an in-window workspace transition, but this does not provide a global audit/delete surface and does not discover arbitrary inactive or legacy workspace stores.
- **closed implementation attempt:** https://github.com/microsoft/vscode/pull/295130 is closed without merge. Its final diff only changed chat export and smoke-test files, and a maintainer explicitly stated that it did not implement what it claimed.
- **related newer issue:** https://github.com/microsoft/vscode/issues/305818 is open and covers recovery after moved, renamed, or deleted workspaces. It was created after this re-reviewed issue and addresses a narrower orphan-recovery symptom, so it cannot serve as the required older same-symptom canonical.
- **distinct history requests:** https://github.com/microsoft/vscode/issues/254027 concerns full-text search within history, while https://github.com/microsoft/vscode/issues/301174 concerns model access to prior sessions; neither owns cross-workspace auditing and deletion.
