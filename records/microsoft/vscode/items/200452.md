# Issue #200452 — Aux window workspace file explorer selects wrong file

[https://github.com/microsoft/vscode/issues/200452](https://github.com/microsoft/vscode/issues/200452)

## Summary

A real auxiliary-window interaction gap remains on current main: changing the active window can auto-scroll the Explorer before the pending click is applied, moving the intended target. The Backlog milestone and unresolved maintainer discussion bar an as-designed decline.

## Change summary

Prevent Explorer auto-reveal during an auxiliary-window focus transition from moving the tree underneath a pending file click.

## Best solution

Define and implement cross-window auto-reveal behavior that preserves the user's pointer target while retaining normal reveal behavior for explicit editor changes. The existing `false` and `focusNoScroll` settings are workarounds, but neither preserves the default auto-scroll behavior without this interaction risk.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/services/editor/browser/editorService.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Using a multi-root workspace, place one editor in an auxiliary window, scroll the Explorer so the active files occupy different regions, alternate editor focus between windows, and click a visible sibling file in the Explorer; the clicked file must open and the tree must not move the target before the click is applied. Normal auto-reveal after an explicit editor change must remain intact.
- **Behavior:**

  > With `explorer.autoReveal` enabled, switching focus between a primary editor and an auxiliary-window editor must not cause a subsequent Explorer click to act on a different row than the one under the pointer. Explicit editor changes should continue to reveal the active file according to the configured auto-reveal mode. Acceptance requires the reporter's multi-root, two-window sequence to select the clicked file repeatedly without a tree jump redirecting the action.
- **Trace:**

  > ExplorerView in src/vs/workbench/contrib/files/browser/views/explorerView.ts listens to every `IEditorService.onDidActiveEditorChange` event and calls `selectActiveFile()`. That path reaches `selectResource()`, which scrolls an offscreen active item before updating focus and selection when reveal is `true`; window activation can therefore reposition the shared Explorer before the mouse action completes. The issue discussion confirms this event ordering, while `explorer.autoReveal: false` and `focusNoScroll` demonstrate that suppressing scrolling avoids the symptom at the cost of expected reveal behavior. Keep ordinary same-window explicit editor changes and all three existing setting semantics in scope; do not conflate this with the closed preview-editor regression at https://github.com/microsoft/vscode/issues/211806.
- **Open decisions:**
  - When active-editor identity changes solely because focus moves between the primary and auxiliary windows, should Explorer auto-reveal be suppressed, deferred until the pointer action completes, or performed only after an explicit editor selection?

## Evidence

- **current source path:** On current main, src/vs/workbench/contrib/files/browser/views/explorerView.ts registers `editorService.onDidActiveEditorChange` and immediately calls `selectActiveFile()`; that delegates to `explorerService.select()` and `selectResource()`, whose default `true` reveal mode calls `tree.reveal(item, 0.5)` when the active file is offscreen.
- **confirmed mechanism:** The maintainer discussion at https://github.com/microsoft/vscode/issues/200452#issuecomment-1848859724 identifies the same ordering: activating the first window changes the active editor, the tree scrolls to reveal it, and the click is then applied where the intended target used to be.
- **existing workaround:** src/vs/workbench/contrib/files/browser/files.contribution.ts exposes `explorer.autoReveal` values `false` and `focusNoScroll`; src/vs/workbench/contrib/files/browser/views/explorerView.ts only scrolls for `true` or `force`, so these modes avoid the jump but require giving up normal automatic scrolling.
