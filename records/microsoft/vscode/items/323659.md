# Issue #323659 — bug: TreeView selection becomes corrupted when a context key update changes item context menu visibility

[https://github.com/microsoft/vscode/issues/323659](https://github.com/microsoft/vscode/issues/323659)

## Summary

Confirmed on current main: `TreeRenderer.onDidChangeMenuContext` fires `tree.rerender()` per affected item during a context-key change, which splices list rows and corrupts the visual multi-selection state. An open PR exists but has not merged.

## Change summary

TreeView multi-selection becomes visually corrupted when a context key update changes an item's context menu visibility, because `tree.rerender()` splices list rows re-entrantly during the context-change event.

## Best solution

Land the approach from https://github.com/microsoft/vscode/pull/323692 (or equivalent): replace the `tree.rerender()` splice path with the renderer's existing in-place re-render so inline-action visibility refreshes without mutating list rows, preserving multi-selection.

## Evidence

- **buggy code path:** src/vs/workbench/browser/parts/views/treeView.ts line 760: `renderer.onDidChangeMenuContext(e => e.forEach(e => this.tree?.rerender(e)))` splices list rows on context-key change, corrupting visual selection.
- **root cause traced:** Lines 1584–1597: `onDidChangeContext` collects affected items and fires `_onDidChangeMenuContext`, which triggers per-item `tree.rerender()` — a list splice that is re-entrant during the context-change event and breaks the list's selection trait.
- **open PR:** https://github.com/microsoft/vscode/pull/323692 proposes replacing the splice with an in-place re-render; not yet merged.
