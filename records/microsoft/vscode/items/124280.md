# Issue #124280 — Provide a smart run/debug command for loose files

[https://github.com/microsoft/vscode/issues/124280](https://github.com/microsoft/vscode/issues/124280)

## Summary

Keep open: existing run/debug extension points and TypeScript build tasks do not provide the requested setup-free loose-file TypeScript experience. Maintainers accepted work in the bundled TypeScript extension, and the older out-of-the-box debugging report was explicitly consolidated into this issue.

## Change summary

Provide discoverable run/debug support for standalone TypeScript files without requiring a workspace or manual compiler setup, including guidance when runtime dependencies are missing.

Complete the language-specific loose-file experience through the bundled TypeScript extension and JavaScript debugger, following the thread's agreed no-launch.json direction while preserving configured project workflows. Reassess runtime and compilation requirements against current Node.js capabilities before settling the missing-dependency experience.

## Plan brief

- **Likely files:** `extensions/typescript-language-features/package.json`, `extensions/typescript-language-features/src/extension.ts`, `extensions/typescript-language-features/src/commands/index.ts`, `extensions/typescript-language-features/src/task/taskProvider.ts`, `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`
- **Validation:** In a clean profile with only bundled extensions enabled and no folder open, save a standalone TypeScript file containing a type annotation and console.log, invoke its run/debug affordance and F5, verify output and breakpoint binding without manually creating launch.json or installing tsc, and verify no generated files appear beside the source. Repeat with Node.js absent and with an existing configured TypeScript project to check actionable runtime guidance and preservation of project behavior.
- **Behavior:**

  > A beginner opening a saved standalone TypeScript file without a workspace should have a discoverable way to run it and debug it without manually creating launch.json or arranging a compiler toolchain. Console output and breakpoints should work, and generated artifacts should not clutter the source directory. When required runtime dependencies are unavailable, the experience should provide actionable guidance rather than an opaque launch failure. Existing explicitly configured TypeScript projects must retain their build and debug behavior; initializing a multi-file project is outside the original scope.
- **Trace:**

  > The editor run/debug contribution point already exists in src/vs/workbench/contrib/debug/browser/debug.contribution.ts. The bundled TypeScript extension's package.json, src/extension.ts, and src/commands/index.ts do not register the requested run/debug path, while TscTaskProvider.provideTasks in src/task/taskProvider.ts explicitly skips no-workspace windows and depends on an external compiler executable. The accepted direction at https://github.com/microsoft/vscode/issues/124280#issuecomment-942181963 and https://github.com/microsoft/vscode/issues/124280#issuecomment-942634176 places the language-specific experience in the TypeScript extension with delegation to js-debug. The source inspection establishes that those TypeScript extension surfaces do not deliver the requested flow, but does not establish how much current Node.js and js-debug behavior already covers; that is the first planning investigation. Preserve explicit launch configurations and project compiler semantics, and do not turn the separate Python configuration discussion into generic debugger policy. The older report https://github.com/microsoft/vscode/issues/87972 was explicitly consolidated here.
- **Open decisions:**
  - When Node.js is missing or too old for the supported loose-file flow, should VS Code offer a guided installation action or explain the requirement and link to installation instructions?
