# Issue #206547 — Improve localization experience of WebViews

[https://github.com/microsoft/vscode/issues/206547](https://github.com/microsoft/vscode/issues/206547)

## Summary

Keep open: the reporter solved manual initialization, but automatic localization support for extension webviews remains missing. A maintainer explicitly endorsed improving this experience, and the related notebook-renderer proposal does not cover general webview panels.

## Change summary

Let extension webviews use the extension's selected localization bundle without manually passing a resource URI and initializing localization before rendering.

## Best solution

Define a supported webview localization contract that makes the owning extension's translations available before localized UI renders, while retaining compatibility with existing webviews. Coordinate with the notebook-renderer localization proposal without treating that narrower surface as a duplicate.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostLocalizationService.ts`, `src/vs/workbench/api/common/extHostWebview.ts`, `src/vs/workbench/contrib/webview/browser/pre/index.html`
- **Validation:** After choosing the contract, exercise an extension with a React webview and a translated bundle: select the matching VS Code display language and verify translated text on the first render without extension-authored URI passing. Repeat with the default language, missing translations, and two extensions with different bundles; verify fallback text, bundle isolation, and compatibility with existing manual initialization.
- **Behavior:**

  > An extension author should be able to localize a React webview using the same selected translations as the extension without manually transmitting a bundle URI and arranging localization startup. Localized strings should be available before the first localized render. Default-language and missing-translation cases should retain source-string fallback. Existing webviews and their manual localization integrations must continue working.
- **Trace:**

  > ExtHostLocalizationService in src/vs/workbench/api/common/extHostLocalizationService.ts selects translations using appLanguage and caches bundles by extension ID. The stable vscode.l10n API in src/vscode-dts/vscode.d.ts exposes those bundles and their URIs to extension code, but ExtHostWebview in src/vs/workbench/api/common/extHostWebview.ts does not propagate them into webview startup. The generated acquireVsCodeApi in src/vs/workbench/contrib/webview/browser/pre/index.html currently contains only messaging and state methods. The reporter's manual URI/config initialization works, and the maintainer explicitly identified automatic loading as the desired improvement in https://github.com/microsoft/vscode/issues/206547. Uncertainty starts at the public contract: how webview code accesses localization and when it becomes ready. Preserve extension-specific bundle isolation, existing content-security behavior, and manual integrations; changing navigator.language is not the reported requirement. Coordinate with https://github.com/microsoft/vscode/issues/170919, whose notebook-renderer API is related but narrower.
- **Open decisions:**
  - Should webview localization expose a host-backed translation API, or provide bundle access for author-selected localization libraries, and should adoption be opt-in?
  - Should localization be ready synchronously when the webview API is acquired, or should authors await an explicit readiness contract before their first localized render?

## Evidence

- **Workaround and accepted direction:** In https://github.com/microsoft/vscode/issues/206547, the reporter confirmed that passing webview.asWebviewUri(vscode.l10n.uri) and awaiting @vscode/l10n.config before rendering solves their immediate problem. TylerLeonhardt endorsed this workaround on 2024-02-29 but stated that ideally localization would load automatically. The accepted Backlog milestone and maintainer direction rule out a decline close.
- **Existing capability and remaining gap:** src/vscode-dts/vscode.d.ts:18199–18269 exposes vscode.l10n.t, bundle, and uri for extensions, including undefined bundles in the default language. src/vs/workbench/api/common/extHostLocalizationService.ts selects bundle.l10n.<appLanguage>.json and caches it per extension. These provide the inputs for manual localization, not automatic initialization inside a webview.
- **Current webview boundary:** src/vs/workbench/api/common/extHostWebview.ts forwards extension-provided HTML through $setHtml and serializes webview content options without localization metadata. src/vs/workbench/contrib/webview/browser/pre/index.html:219–255 generates acquireVsCodeApi with postMessage, setState, and getState only; it exposes no localization API or bundle initialization.
- **Related proposal is not a canonical duplicate:** https://github.com/microsoft/vscode/issues/170919 is verified open and older, but specifically requests localization for notebook renderer scripts through their renderer API/import contract. It does not own automatic localization for arbitrary React webview panels, so it does not satisfy this re-reviewed item's same-symptom duplicate bar.
- **Closed language-passing reports:** https://github.com/microsoft/vscode/issues/207178 is closed as a duplicate of https://github.com/microsoft/vscode/issues/207071, which is also closed and concerns passing the display language or changing navigator.language. Both are newer than this report and neither is an eligible canonical for automatic bundle initialization.
