# Issue #93149 — Make extension defined task types work in code-workspace files

[https://github.com/microsoft/vscode/issues/93149](https://github.com/microsoft/vscode/issues/93149)

## Summary

Keep this accepted tasks feature request open: workspace-file parsing exists, but folder-dependent extension task resolution still has a scope gap. Maintainers have directed related reports here, and no verified older canonical or concrete fixing commit supersedes it.

## Change summary

Allow extension-defined tasks, including npm scripts, to be configured in a .code-workspace file and referenced by workspace-level preLaunchTask.

## Best solution

Define an unambiguous folder-binding contract for extension-defined workspace-file tasks, then support their resolution and execution through the tasks service and provider boundary. Preserve existing folder tasks and shell/process workspace tasks.

- **Behavior:**

  > An extension-defined task stored in a .code-workspace file should be resolvable by its workspace-level preLaunchTask reference and execute against the intended workspace folder. The supplied npm buildfordebug example should build before the debugger starts rather than report a missing task. Multi-root cases must select the intended folder unambiguously, including when multiple folders contain the same script name. Existing folder task definitions and workspace shell/process tasks must retain their behavior.
- **Trace:**

  > AbstractTaskService._computeWorkspaceFileTasks parses workspace tasks, and ConfiguringTask.from preserves WorkspaceFile provenance; there is no simple parser-only rejection to remove. _computeWorkspaceTasks keys these configurations by workspace-file URI, whereas _getGroupedTasks groups provider-contributed tasks by folder URI, and _getCustomTaskPromises matches within those keys before falling back to provider.resolveTask. NpmTaskProvider.resolveTask in extensions/npm/src/tasks.ts requires WorkspaceFolder scope to locate package.json. The trace establishes the folder-resolution boundary but not a settled cross-provider binding contract or an executed reproduction. Related reports https://github.com/microsoft/vscode/issues/108928 and https://github.com/microsoft/vscode/issues/136187 have already been directed here. Keep the separate cppdbg regression discussed in https://github.com/microsoft/vscode/issues/148019 outside this feature's scope, and preserve existing task identity and shell/process behavior.
- **Open decisions:**
  - How should a task declared in a .code-workspace file identify its target folder, and what user-visible behavior should occur when that folder is omitted in a multi-root workspace?
  - What scope should extension task providers receive for a workspace-file task bound to a folder: the selected WorkspaceFolder or workspace scope with a separate folder-binding contract?
