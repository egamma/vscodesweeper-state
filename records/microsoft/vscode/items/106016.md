# Issue #106016 — Workbench hover: a lot of whitespace in this case

[https://github.com/microsoft/vscode/issues/106016](https://github.com/microsoft/vscode/issues/106016)

## Summary

The visual gap remains in the shared workbench-hover sizing policy: long unbroken content can determine the overlay width and leave substantial whitespace around shorter lines. No older canonical or issue-linked fixing commit was found, so this should remain open as workbench polish.

## Change summary

Make workbench hovers containing long unbroken text use a more compact, editor-consistent layout without clipping their content.

## Best solution

Define a consistent policy for long unbroken hover values, then align the shared workbench hover with editor hovers so code-like content is readable without forcing the entire overlay to an unnecessarily wide intrinsic size.

- **Behavior:**

  > A workbench hover containing a long unbroken value should remain compact and readable rather than allowing that value to create a disproportionately wide surface with empty space around shorter content. The value must remain fully accessible without clipping, and ordinary prose, links, actions, constrained-window positioning, and editor hovers must retain their existing behavior. Acceptance should cover both a normal viewport and a viewport narrower than the preferred hover width.
- **Trace:**

  > WorkbenchHoverWidget in src/vs/platform/hover/browser/hoverWidget.ts renders plain strings with `whiteSpace = 'pre-wrap'` and measures the resulting container through `clientWidth` during layout. The shared workbench CSS in src/vs/platform/hover/browser/hover.css allows an outer width up to 700px, while src/vs/base/browser/ui/hover/hoverWidget.css gives non-code markdown separate 500px and break-word behavior. This confirms that long no-wrap content can govern the shared overlay's intrinsic width; the discussion at https://github.com/microsoft/vscode/issues/106016#issuecomment-690771275 additionally raises editor-style monospace presentation. Keep the scope within shared hover content sizing and presentation: do not change context-view anchoring, focus behavior, hover persistence, or unrelated editor-hover semantics.
- **Open decisions:**
  - Should long unbroken code-like values wrap within a compact hover, remain on one scrollable line, or use another overflow presentation?
  - Should workbench hovers automatically render these values in editor-style monospace presentation, and if so how should the UI distinguish code-like values from ordinary prose?

## Evidence

- **current source:** src/vs/platform/hover/browser/hoverWidget.ts assigns plain-string content `whiteSpace = 'pre-wrap'`, while src/vs/platform/hover/browser/hover.css caps the outer hover at 700px; an unbroken value can therefore drive the overlay toward that cap even when surrounding lines are short.
- **markdown sizing:** src/vs/base/browser/ui/hover/hoverWidget.css separately caps ordinary markdown hover contents at 500px and applies `word-wrap: break-word`, showing that width and wrapping behavior still varies by content representation rather than following one compact workbench-hover policy.
