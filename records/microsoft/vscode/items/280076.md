# Issue #280076 — when downvoting copilot chat response multi selection is not possible

[https://github.com/microsoft/vscode/issues/280076](https://github.com/microsoft/vscode/issues/280076)

## Summary

The multi-selection gap remains on current main: chat feedback choice steps are explicitly single-select and the service stores one option per step. Keep this accepted polish item open, but plan the interaction and telemetry contract before implementation.

## Change summary

Allow users to select multiple applicable reasons when giving negative feedback on a Copilot Chat response.

## Best solution

Support an opt-in multi-choice feedback step that preserves existing single-choice surveys, provides an explicit submit action, and exposes correct keyboard and screen-reader selection state. The feedback telemetry contract must carry all selected reason IDs without affecting ordinary binary thumbs-down votes.

- **Behavior:**

  > When a negative-feedback survey permits multiple reasons, users can select and deselect every applicable reason before explicitly submitting. Mouse and keyboard interaction must expose the same behavior, and screen readers must announce each option's selected state. Existing single-choice surveys and ordinary binary thumbs-down voting remain unchanged. Submission records every selected reason exactly once.
- **Trace:**

  > Current main explicitly renders feedback choices as a single-select listbox in ChatModelFeedbackSurveyWidget.renderChoiceStep, and ChatCardListbox maintains only one active/aria-selected option. ChatModelFeedbackSurveyService.answerChoice stores one string per step and advances or submits immediately, while the telemetry event has one answerId. The older thumbs-down detail UI added by https://github.com/microsoft/vscode/commit/13d64e98d8075cf3863236ad13f56750e990f27d was also single-choice; current chatTitleActions.ts retains only the binary vote path. Keep the boundary within configurable chat feedback surveys: do not change normal vote semantics or make unrelated survey questions multi-select. The uncertainty begins at whether multi-selection is a new step kind or an opt-in property and how the answer collection crosses the telemetry boundary.
- **Open decisions:**
  - Should multi-selection be an explicit per-step capability that preserves existing single-choice behavior, or should negative-feedback reason steps become multi-select by default?
  - Should selected reasons be emitted only once on an explicit Submit action, or should selection changes also produce step telemetry before final submission?
