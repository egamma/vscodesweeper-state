# Issue #342544 — Show available link handlers in a Quick Pick

[https://github.com/microsoft/vscode/issues/342544](https://github.com/microsoft/vscode/issues/342544)

## Summary

Keep this focused deliverable open: existing external-opener and editor pickers cover parts of the request, but not general link-handler discovery and switching with preserved navigation intent. The parent story explicitly delegates this work here, rather than superseding it.

## Change summary

Provide an explicit link-handler Quick Pick and a way to switch the current target's handler without changing future defaults or losing opening context.

## Best solution

Provide a consistent, explicitly invoked handler-selection experience that preserves the original target and placement, while leaving ordinary clicks and configured defaults unchanged. Reuse existing opener/editor selection capabilities where applicable, and settle the discoverability gestures with the maintainer before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/opener/common/opener.ts`, `src/vs/editor/browser/services/openerService.ts`, `src/vs/workbench/contrib/externalUriOpener/common/externalUriOpenerService.ts`, `src/vs/workbench/browser/parts/editor/editorCommands.ts`
- **Validation:** Extend opener tests in src/vs/editor/test/browser/services/openerService.test.ts and external-opener tests in src/vs/workbench/contrib/externalUriOpener/test/common/externalUriOpenerService.test.ts for selected-handler dispatch, original-target preservation, side-opening intent, cancellation without opening, and unchanged defaults. End-to-end acceptance should open a supported target, switch its handler without reconstructing the link, and verify placement/context; the chosen entry point must also work by keyboard.
- **Behavior:**

  > Users can explicitly list matching link handlers, distinguish their names, and identify the current/default handler where known. Selecting a handler opens the original target with its navigation context and placement intent preserved where supported; cancelling leaves the current view unchanged. Users can switch the already-open target to another matching handler without reconstructing its link. Ordinary clicks remain unchanged, and one-time selection never implicitly changes future defaults.
- **Trace:**

  > ExternalUriOpenerService in src/vs/workbench/contrib/externalUriOpener/common/externalUriOpenerService.ts has a named-handler Quick Pick, but configured/preferred selection bypasses it and the service does not retain a current target for switching. IOpenerService in src/vs/platform/opener/common/opener.ts exposes opening and registration rather than general handler discovery; its implementation in src/vs/editor/browser/services/openerService.ts dispatches sequentially and already forwards sourceUri and side-opening intent to external handlers. reopenEditorWith in src/vs/workbench/browser/parts/editor/editorCommands.ts provides editor-specific switching with selection/options preservation, not a general link-handling contract. These are partial capabilities, not proof the request is implemented. Preserve ordinary-click behavior, explicit default configuration, cancellation semantics, and existing editor safeguards. https://github.com/microsoft/vscode/issues/342050 explicitly delegates this deliverable here, while https://github.com/microsoft/vscode/issues/342545 owns the cross-surface support audit. The unresolved boundary is how users discover and invoke selection before opening and switching afterward; the proposed transient action and gestures are alternatives, not settled requirements.
- **Open decisions:**
  - Which user-facing entry points should expose handler selection before opening and switching afterward: a persistent command, the proposed transient status-bar action, modified mouse/keyboard gestures, or a combination?
  - If transient discovery is adopted, what keyboard-accessible persistent alternative and reduced-motion behavior should accompany it?

## Evidence

- **Existing external-opener capability and limitation:** src/vs/workbench/contrib/externalUriOpener/common/externalUriOpenerService.ts already implements showOpenerPrompt with named handlers, cancellation, and selected-handler delegation. However, getOpeners short-circuits for configured or preferred handlers, and openExternal bypasses the picker for a single handler; this is not an explicitly invokable all-matching-handler selector or a current-target switching facility.
- **Existing configuration is not the requested operation:** src/vs/workbench/contrib/externalUriOpener/common/configuration.ts registers workbench.externalUriOpeners for HTTP/HTTPS opener preferences. Configuring a future default does not satisfy this issue's explicitly separate one-time selection and current-target switching requirements.
- **Existing editor switching is partial coverage:** src/vs/workbench/browser/parts/editor/editorCommands.ts registers workbench.action.reopenWithEditor. reopenEditorWith resolves editor context, preserves selection/options, invokes OpenWithEditorPicker, and returns on cancellation, but operates on existing editors converted through toUntyped(), not on arbitrary original links and all matching link handlers.
- **Shared opening contract:** src/vs/platform/opener/common/opener.ts exposes IOpener.open and registration but no general handler-enumeration or current-target switching contract. src/vs/editor/browser/services/openerService.ts dispatches registered openers until one handles the target and forwards sourceUri plus ViewColumn.Beside to contributed external openers; existing intent propagation should be preserved.
