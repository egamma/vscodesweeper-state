# Issue #210854 — Changing lettercase of directory causes unbound breakpoints as VSCode does not refresh path

[https://github.com/microsoft/vscode/issues/210854](https://github.com/microsoft/vscode/issues/210854)

## Summary

The bug remains present on current main: breakpoints retain their original URI while VS Code handles case-only folder renames as move operations, leaving the debug model with stale path casing.

## Change summary

Case-only directory renames leave source breakpoints associated with the directory's previous casing, which can make them unbound.

## Best solution

Keep existing breakpoints attached to their files when a VS Code file or directory move changes the resource path or casing, persist the updated URI, and resend the affected breakpoint paths consistently to active debug sessions.

## Evidence

- **current source:** src/vs/workbench/contrib/debug/browser/debugService.ts registers only fileService.onDidFilesChange; onFileChanges removes deleted breakpoints but does not observe FileOperation.MOVE or rebase breakpoint resources.
- **stale URI path:** src/vs/workbench/contrib/debug/common/debugModel.ts stores Breakpoint._uri as readonly, returns it through originalUri, serializes it unchanged, and IBreakpointUpdateData has no resource field, so the existing breakpoint cannot acquire the renamed path.
- **move event available:** src/vs/workbench/services/editor/browser/editorService.ts handles FileOperation.MOVE and maps resources under a moved directory to the target URI, confirming that VS Code-originated renames expose the source and target needed to preserve resource identity.

It is closed, and its still-open PR https://github.com/microsoft/vscode/pull/232791 addresses adapter-source canonicalization rather than updating breakpoint URIs after a directory rename, so it is not a valid duplicate canonical or a complete fix for this report.
