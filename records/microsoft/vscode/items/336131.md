# Issue #336131 — Windows User Installer becomes corrupted after reboot with a pending background update

[https://github.com/microsoft/vscode/issues/336131](https://github.com/microsoft/vscode/issues/336131)

## Summary

Traced the exact code path on main: build/win32/code.iss's CurStepChanged skips invoking inno_updater.exe when SessionEndFileExists() is true (line 1864, log text matches the reporter's log verbatim), but earlier extraction/removal steps have already run, leaving neither the old nor new install bootable. This is a real, niche-but-severe installer defect that needs a maintainer decision on the intended recovery behavior before an agent should touch it.

## Change summary

When Windows reboots with a pending VS Code background update and the OS session ends before inno_updater.exe runs, the install is left half-updated and neither the old nor new Code.exe can start.

## Best solution

Design a safe fallback in the Inno Setup update flow (build/win32/code.iss / updateService.win32.ts) so a session-end abort either finishes the swap atomically via inno_updater or guarantees the previous working install stays fully intact — likely by staging the new files before touching the old resources, or by resuming/replaying the pending inno_updater invocation on next manual launch.

## Plan brief

- **Likely files:** `build/win32/code.iss`, `src/vs/platform/update/electron-main/updateService.win32.ts`
- **Validation:** A maintainer-approved manual reproduction: stage a background update, force a session-ending abort before inno_updater runs, then confirm the previous install still launches (or the update completes) after reboot.
- **Trace:**

  > The defect is confirmed in build/win32/code.iss's CurStepChanged: when a background update is staged and Windows begins shutting down before the app closes, SessionEndFileExists() causes the script to skip the Exec() call to inno_updater.exe (the component that actually swaps in the new versioned resources and cleans up old ones), per the log line at line 1864. The reporter's install was left with only Code.exe, new_Code.exe, and updating_version — no icudtl.dat, resources, locales or Electron DLLs anywhere — meaning steps upstream of this Exec() already removed/never restored the resources needed by the OLD Code.exe, while the NEW resources were never swapped in either. The boundary: do not change the background-update download/staging pipeline (Squirrel-equivalent parts of updateService.win32.ts before doApplyUpdate) or the manual-update flow; the fix is scoped to how CurStepChanged handles an aborted session-end path.
- **Open decisions:**
  - Should an aborted-by-session-end background update leave the previous version's install fully intact and bootable (skip forward, retry inno_updater on next manual launch), or should Setup instead be changed to still complete inno_updater synchronously (bounded time) before allowing Windows shutdown to proceed?
  - If the previous install can no longer be guaranteed intact by the time session-end is detected, should the installer stage the new versioned resources before removing/altering anything from the old install, so a partial abort always leaves one complete, launchable version?
