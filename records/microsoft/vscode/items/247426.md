# Issue #247426 — Feature Request: Introduce `modelDescriptionHook` for Dynamic Tool Descriptions

[https://github.com/microsoft/vscode/issues/247426](https://github.com/microsoft/vscode/issues/247426)

## Summary

Current main partially addresses this request through proposed model-filtered runtime tool definitions, but it does not provide a per-request description hook or expose arbitrary request context. The issue should remain open while API owners decide whether model-scoped definitions are sufficient and whether this capability should become generally available to extensions.

## Change summary

Allow extensions to provide language-model tool descriptions dynamically according to the selected model and other request context.

## Best solution

Define the supported extension contract for model-specific tool descriptions, preferably building on model-scoped runtime tool definitions without introducing asynchronous description resolution into every request. Finalize the appropriate API only after deciding whether non-model request context is a supported requirement.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.languageModelToolSupportsModel.d.ts`, `src/vs/workbench/api/common/extHostLanguageModelTools.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadLanguageModelTools.ts`, `src/vs/workbench/contrib/chat/common/tools/languageModelToolsService.ts`, `src/vs/workbench/contrib/chat/test/browser/tools/languageModelToolsService.test.ts`
- **Validation:** Add or extend language-model tool API tests to demonstrate that two selected models receive the intended descriptions while unaffected tools retain their existing static descriptions; if request context is supported, include a test showing when a context change does and does not recompute the description.
- **Behavior:**

  > An extension can describe the same logical language-model tool appropriately for different supported models without modifying workspace files. The model receives the description selected for its current request, while models without a specialization retain a defined fallback behavior. Tool identity, user-visible naming, enablement, and invocation behavior remain stable. Any supported non-model context and its refresh semantics must be explicitly defined and tested.
- **Trace:**

  > Static extension contributions are parsed in src/vs/workbench/contrib/chat/common/tools/languageModelToolsContribution.ts, where `modelDescription` remains a required string. Current main also has the proposed `LanguageModelToolDefinition` and `lm.registerToolDefinition` API in src/vscode-dts/vscode.proposed.languageModelToolSupportsModel.d.ts; definitions carry model selectors through ExtHostLanguageModelTools and MainThreadLanguageModelTools into `IToolData`. `toolMatchesModel` in src/vs/workbench/contrib/chat/common/tools/languageModelToolsService.ts filters definitions by id, vendor, family, or version, and tests cover that filtering. This provides a plausible model-specific-definition mechanism but no callback at description-consumption time and no arbitrary request-context input. The design boundary is tool metadata selection: invocation preparation and workspace instruction-file management should not be repurposed.
- **Open decisions:**
  - Should extensions specialize descriptions by registering model-scoped definitions, or should VS Code expose a callback that receives the active model for each request?
  - Are contextual inputs beyond model identity part of the public contract, and if so, which bounded context is exposed?
  - What fallback description is used when no model-specific definition matches?
  - Should this capability remain proposed for selected extensions or be designed for stabilization in the public extension API?

## Evidence

- **static API remains:** src/vs/workbench/contrib/chat/common/tools/languageModelToolsContribution.ts still requires package.json `modelDescription` to be a single static string.
- **partial proposed capability:** src/vscode-dts/vscode.proposed.languageModelToolSupportsModel.d.ts now defines `lm.registerToolDefinition`, runtime descriptions, and `models?: LanguageModelChatSelector[]`; src/vs/workbench/api/common/extHostLanguageModelTools.ts forwards these definitions into core.
- **model filtering implementation:** https://github.com/microsoft/vscode/pull/278904 merged as https://github.com/microsoft/vscode/commit/1980c621403da74ae018a29b748938689d7ea070 and added model-aware tool filtering; current tests in src/vs/workbench/contrib/chat/test/browser/tools/languageModelToolsService.test.ts cover selectors by model id, vendor, and family.
- **remaining scope:** The proposed API selects pre-registered definitions through model selectors; it does not call an extension when a request needs a description or pass arbitrary request context to description generation.
- **API direction remains unsettled:** In https://github.com/microsoft/vscode/issues/277472#issuecomment-3612635885, a maintainer distinguished closely tuned core tools from extension tools and questioned whether extensions need the same flexibility; that broader issue was later closed after model-filtered runtime tools landed.
- **related extension usage:** https://github.com/tlaplus/vscode-tlaplus/pull/372 demonstrates the reporter's extension adopting language-model tools, but it does not implement or supersede the requested VS Code API capability.
