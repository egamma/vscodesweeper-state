# Issue #10561 — Execute functions during snippet expansion

[https://github.com/microsoft/vscode/issues/10561](https://github.com/microsoft/vscode/issues/10561)

## Summary

Keep open: completion providers support dynamic snippet text and follow-up commands, but they still do not provide the consistent Insert Snippet and snippet-only tab-completion experience requested here. This team-authored, accepted Backlog request has 70 upvotes and needs an API design decision, not a staleness close.

## Change summary

Allow extensions to generate context-sensitive snippet text and perform expansion-time actions consistently across completion, Insert Snippet, and tab completion.

## Best solution

Define an extension API contract for dynamically resolved snippets that preserves consistent discovery and insertion across the existing snippet entry points. Keep language-specific generation in extensions, and settle asynchronous resolution and expansion-time action semantics before implementation.

- **Validation:** After agreeing on the API, use a test extension providing a constructor snippet whose name depends on the enclosing class and an observable acceptance action. Invoke it through completion, Insert Snippet, and snippet-only tab completion; verify consistent availability, context-sensitive output, preserved placeholder navigation, and exactly-once actions. Exercise delayed resolution and cancellation, and retain existing static-snippet behavior. No execution was performed during this read-only review.
- **Behavior:**

  > Extensions should be able to offer snippets whose inserted text depends on language context and whose acceptance can perform the required extension-owned actions. The same snippet should be discoverable and usable through completion, Insert Snippet, and snippet-only tab completion rather than working only in IntelliSense. Acceptance should cover constructor-name generation, placeholder navigation, and a representative expansion-time action across all three entry points. Existing static snippets and ordinary completions must retain their behavior.
- **Trace:**

  > CompletionItem already supports SnippetString, additionalTextEdits, and post-insertion commands in src/vscode-dts/vscode.d.ts. InsertSnippetAction uses ISnippetsService and inserts an existing codeSnippet; TabCompletionController separately matches getSnippetsSync results for onlySnippets mode. SnippetSession resolves variables through a fixed list of built-in delegates, not an extension registration API. The unresolved boundary is bridging asynchronous extension-owned generation with consistent snippet discovery and insertion, rather than implementing C# semantics in core. The maintainer rejection at https://github.com/microsoft/vscode/issues/130325#issuecomment-899338950 establishes the synchronous tab-completion constraint; https://github.com/microsoft/vscode/issues/111158 documents deferred-resolution and picker-integration needs but is closed, not a canonical. Preserve static-snippet prefix matching and existing completion behavior; the public extension contract and asynchronous user experience remain undecided.
- **Open decisions:**
  - Should the public contract expose commands or custom variables within snippet text, or separately registered dynamic snippets that appear in all snippet entry points?
  - When expansion requires an asynchronous extension response, what waiting, cancellation, and document-change behavior should users receive across Insert Snippet and snippet-only tab completion?
  - What ordering and undo guarantees should expansion-time actions have relative to inserting the snippet and entering placeholder navigation?
