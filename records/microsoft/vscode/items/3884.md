# Issue #3884 — Revisit VS Code folder structure for app data, settings, extensions

[https://github.com/microsoft/vscode/issues/3884](https://github.com/microsoft/vscode/issues/3884)

## Summary

Keep this umbrella open: current main still mixes disposable caches with user configuration and retains home-directory paths for extensions, runtime arguments, and shared state. Existing overrides only partially cover the request; the broader cross-platform path and migration policy remains unresolved.

## Change summary

Separate configuration, disposable caches, persistent state, and extensions into platform-appropriate directories with consistent naming and safe migration.

## Best solution

Agree on a cross-platform directory and override policy, then deliver it through staged, independently verifiable migrations without treating irreplaceable state or installed extensions as disposable cache. Retain this issue as the umbrella and use the focused runtime-argument and shared-state issues for their respective subproblems.

## Plan brief

- **Likely files:** `src/vs/platform/environment/node/userDataPath.ts`, `src/vs/platform/environment/common/environmentService.ts`, `src/vs/platform/environment/node/argv.ts`, `src/mainImpl.ts`, `src/vs/platform/environment/test/node/userDataPath.test.ts`, `src/vs/platform/environment/test/node/environmentService.test.ts`
- **Validation:** The plan should define executable path-resolution and migration tests for each supported platform and a launch acceptance matrix: create settings, keybindings, snippets, installed extensions, and persistent state in the legacy layout; launch through both CLI and normal GUI entry points; verify preservation and consistent root selection; delete only the designated cache tree and verify regeneration without losing persistent data. Preserve explicit overrides, portable mode, and stable/Insiders separation.
- **Behavior:**

  > Users should be able to distinguish configuration and persistent data from disposable caches through a supported platform-appropriate directory policy. The policy must work consistently across CLI and GUI launches, including launch paths that do not carry custom flags. Any migration must preserve settings, keybindings, snippets, installed extensions, and persistent user state. Removing designated disposable caches must not remove irreplaceable data, and product variants and portable mode must remain isolated.
- **Trace:**

  > getDefaultUserDataPath in src/vs/platform/environment/node/userDataPath.ts selects platform roots, while AbstractNativeEnvironmentService in src/vs/platform/environment/common/environmentService.ts derives configuration, caches, extension downloads, extensions, runtime arguments, and shared state. Current source confirms that cacheHome equals userDataPath and that several other roots remain independently home-based. src/mainImpl.ts configures Electron's userData root and independently discovers argv.json before normal workbench initialization, so changing only a workbench getter would not establish a consistent launch policy. Existing CLI and environment overrides are partial capabilities, not completion of the central request. Preserve their compatibility and portable/product-variant behavior; do not classify workspace history or extension contents as disposable without a settled recovery contract. https://github.com/microsoft/vscode/issues/162712 and https://github.com/microsoft/vscode/issues/330061 own focused subproblems, not the whole umbrella. The uncertainty begins with the intended new default layout, GUI-safe override contract, and migration behavior.
- **Open decisions:**
  - Should platform-appropriate directories become the defaults for existing installations through migration, apply only to new installations, or remain an opt-in layout?
  - On macOS, should explicitly requested XDG locations override native Library locations, and what persistent override mechanism must also work for GUI launches without inherited environment variables?
  - Which contents belong in configuration, persistent data/state, and disposable cache, particularly installed extensions, workspace storage, history, and shared state; should deleting any proposed extension cache trigger automatic restoration?

## Evidence

- **Existing capability and remaining gap:** src/vs/platform/environment/node/userDataPath.ts:getUserDataPath supports portable mode, VSCODE_APPDATA, and --user-data-dir. getDefaultUserDataPath honors XDG_CONFIG_HOME on Linux, uses APPDATA/Roaming on Windows, and Library/Application Support on macOS. These relocate the combined user-data tree rather than independently separating configuration and caches.
- **Caches still share the configuration root:** src/vs/platform/environment/common/environmentService.ts:AbstractNativeEnvironmentService.cacheHome returns userDataPath; appSettingsHome appends User; extensionsDownloadLocation defaults to userDataPath/CachedExtensionVSIXs. src/mainImpl.ts also assigns Electron's userData path to this root. The requested default separation is therefore not implemented.
- **Extensions and runtime arguments:** src/vs/platform/environment/common/environmentService.ts:extensionsPath supports --extensions-dir and VSCODE_EXTENSIONS, but otherwise uses userHome/productService.dataFolderName/extensions. argvResource still uses that home-directory product folder. src/mainImpl.ts:getArgvConfigPath independently resolves the same legacy argv.json location, and its supported runtime-argument lists do not include user-data-dir, extensions-dir, or shared-data-dir.
- **Shared-state path:** src/vs/platform/environment/common/environmentService.ts:appSharedDataHome supports --shared-data-dir and portable mode, then defaults to userHome/productService.sharedDataFolderName. It does not resolve XDG_STATE_HOME or provide a corresponding persistent environment override.
