# Issue #333665 — Agent host: file watches fail with ENOPRO in a remote window, because the host is handed vscode-remote URIs it cannot resolve

[https://github.com/microsoft/vscode/issues/333665](https://github.com/microsoft/vscode/issues/333665)

## Summary

Well-diagnosed, source-confirmed bug: in a dev-container/remote window, agent host watchers are handed vscode-remote:// working-directory URIs the host's own file service has no provider for, so customization and workspace watches silently fail. The reporter has already traced the exact call sites and opened a fix PR, so this should stay open pending that PR's review/merge rather than being treated as a fresh auto-fix target.

## Change summary

In a remote/dev-container window, agent host file watchers (ClaudeCustomizationWatcher, SessionMcpDiscovery, agentHostFileMonitorService) are passed vscode-remote:// URIs instead of the host's own file: paths, so IFileService.watch throws ENOPRO and the watch never attaches.

## Best solution

Land the linked fix (https://github.com/microsoft/vscode/pull/333683, 'agentHost: watch customizations on the host's own filesystem'), which reportedly rewrites/maps these working-directory URIs to the host's local filesystem namespace before watching; verify it also fixes the change-matching logic (ClaudeCustomizationWatcher's trigger comparison and SessionMcpDiscovery's .mcp.json resolution) since the reporter notes even an attached watch would currently match nothing against file: change events.
