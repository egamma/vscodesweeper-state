# Issue #309912 — Feature request: allow extension-contributed models in Copilot CLI model selection (flagged opt-in)

[https://github.com/microsoft/vscode/issues/309912](https://github.com/microsoft/vscode/issues/309912)

## Summary

A real capability gap remains on current main: Copilot CLI publishes its SDK models into VS Code's language-model registry but does not consume extension-contributed models for CLI selection. The request needs a product and security design decision, so it should remain open as under discussion.

## Change summary

Allow explicitly opted-in extension-contributed language models to participate in Copilot CLI model selection with provenance and existing trust controls preserved.

## Best solution

Define a supported bridge that lets eligible extension-contributed models enter the Copilot CLI catalog and route inference back through their registered provider, gated by an explicit managed opt-in and displaying provider provenance. Reuse the existing Agent Host BYOK bridge where its trust and proxy semantics apply rather than creating an unrelated provider contract.

- **Validation:** Add model-catalog and session-initializer tests showing that an extension-contributed model is absent and unresolved when opt-in is disabled, then enumerated with provenance and resolved without default-model fallback when enabled; existing SDK-model selection tests must remain unchanged.
- **Behavior:**

  > When the approved opt-in is disabled, Copilot CLI model selection behaves exactly as it does today. When enabled, eligible extension-contributed models appear in the existing picker with publisher and extension provenance and can be selected for a CLI session without silently falling back to a built-in model. Ineligible, unavailable, or untrusted providers remain excluded, and selection failures are explicit. The setting and UI must make the trust boundary and rollback path clear.
- **Trace:**

  > CopilotCLIModels in extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotCli.ts obtains its catalog only from the Copilot SDK's getAvailableModels and registers those results outward through vscode.lm; it never enumerates extension-provided models. CopilotCLIChatSessionInitializer.resolveModel in extensions/copilot/src/extension/chatSessions/copilotcli/vscode-node/copilotCLIChatSessionInitializer.ts accepts only IDs resolved by that SDK-backed catalog and otherwise chooses the default. Current Agent Host code already has a separately gated BYOK bridge through AgentHostClientByokLmChannel and ByokLmProxyService, establishing adjacent trust and transport machinery but not adoption on this Copilot CLI path. https://github.com/microsoft/vscode/issues/333802 confirms a remaining catalog mismatch for extension-provided models, while https://github.com/microsoft/vscode/pull/309913 closed without code. Preserve existing first-party selection and default fallback behavior when the feature is disabled; broader Agent Host and generic chat model-selection behavior are outside this issue's boundary.
- **Open decisions:**
  - Should eligibility cover every extension-contributed language model that declares the required capabilities, or only models marked as BYOK and approved for agent execution?
  - Is opt-in global, workspace-scoped, session-scoped, or a combination, and must enterprise policy be able to disable it?
  - Should unsupported extension-model selection fail explicitly, or may the UI prevent selection before session creation; silent fallback must not be retained as an observable outcome?
