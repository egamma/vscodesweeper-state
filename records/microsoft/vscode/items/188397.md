# Issue #188397 — VS Code not responding on launching

[https://github.com/microsoft/vscode/issues/188397](https://github.com/microsoft/vscode/issues/188397)

## Summary

Keep this open as the established Linux startup-hang report: maintainer profiling points to Chromium keyring initialization blocking Electron's main process. Multiple confirmations and the current synchronous runtime calls support continued investigation, not a completed or not-reproducible close.

## Change summary

Prevent Linux startup from becoming unresponsive when the OS keyring is locked or fails to respond.

## Best solution

Resolve the blocking keyring initialization in Electron/Chromium and verify its adoption through VS Code's EncryptionMainService. Startup should remain responsive without requiring users to select weaker encryption; distinguish the graphics-related reports from the confirmed keyring cases.

## Evidence

- **Maintainer root-cause diagnosis:** https://github.com/microsoft/vscode/issues/190360#issuecomment-1702275524 identifies a 25-second main-process stall in EncryptionMainService.isEncryptionAvailable. https://github.com/microsoft/vscode/issues/190360#issuecomment-1702285694 traces that call into Chromium's OS crypt storage-backend initialization.
- **Current runtime boundary:** src/vs/platform/encryption/electron-main/encryptionMainService.ts still invokes safeStorage.isEncryptionAvailable(), encryptString(), and decryptString() synchronously. isEncryptionAvailable() wraps the result in Promise.resolve only after the native call returns; that does not prevent a native keyring call from blocking the main process. Source inspection establishes the boundary, not current-environment reproduction.
- **Authentication trigger:** src/vs/workbench/api/browser/mainThreadSecretState.ts routes $getPassword through secretStorageService.get. The supplied Arch Linux report on VS Code 1.87.2 stops at the matching 'Getting password for vscode.github-authentication' trace, consistent with the maintainer's runtime diagnosis.
- **Independent confirmations:** https://github.com/microsoft/vscode/issues/188397#issuecomment-2550592659 reports recurring startup freezes on VS Code 1.95.2 and correlates them with fingerprint login and keyring unlocking; password login avoids the hang. https://github.com/microsoft/vscode/issues/188397#issuecomment-2911179939 independently confirms that workaround on Ubuntu 24.04.
- **This issue already owns consolidated reports:** https://github.com/microsoft/vscode/issues/195070#issuecomment-1903225089 explicitly merges the Debian startup-freeze report into this issue because selecting the basic password store addresses it. That closed satellite is not a duplicate target or evidence that this issue was fixed.
- **Canonical search:** Searches for keyring freezes, keychain unresponsiveness, and password-store hangs found no verified older canonical with the same observable symptom. https://github.com/microsoft/vscode/issues/187338 is older and open, but its report concerns failed keyring detection and encryption errors rather than startup freezing, so it does not satisfy the stronger duplicate bar for this re-reviewed item.
- **Workaround is not completion:** src/vs/workbench/services/secrets/electron-browser/secretStorageService.ts explicitly describes bypassing the OS keyring as 'weaker encryption'. The basic password-store workaround therefore does not establish that normal keyring-backed startup is fixed. No concrete behavior-fixing commit was established; available local history is insufficient to prove resolution.
