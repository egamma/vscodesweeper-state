# Issue #339807 — Successfully migrated UI is a bit rough

[https://github.com/microsoft/vscode/issues/339807](https://github.com/microsoft/vscode/issues/339807)

## Summary

Team-authored UX feedback on the brand-new customization migration dashboard's "all migrations complete" state; traced in source to two independently-scrolling regions and an oversized header, confirming the reported roughness, but the right visual fix is a design call, not a drop-in patch.

## Change summary

When all customizations are migrated, the migration dashboard shows an oversized page header plus a separately height-constrained, scrollable activity log, producing a cramped/rough layout.

## Best solution

Rework the completed-state layout in customizationMigrationDashboard.ts / customizationMigrationDashboard.css so the page has a single coherent scroll region (or the activity list gets a less arbitrary height budget than the current `max-height: 40%`), rather than a large static header stacked over two separately-scrolling panes.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationDashboard.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/media/customizationMigrationDashboard.css`

- **Behavior:**

  > When a user has finished migrating all customizations, the dashboard should present a clean completed-state layout: no overly large static header dominating the view, and no awkward nested/height-constrained scroll region for the activity log. Acceptance: visually inspect the completed state at the width from the report's screenshot and confirm there is one natural scroll affordance (or clearly separated, intentionally-sized regions), not a cramped 40%-capped activity list under an oversized header.
- **Trace:**

  > In showOverview() (customizationMigrationDashboard.ts:304-335), the completed state renders renderHeader() (adds the title row + intro paragraph +, if overview.result is set, renderResult()'s .migration-result success banner) but skips renderMigrationTree() (and thus the layoutTree sizing described at customizationMigrationDashboard.ts:358-365), so nothing constrains the header's relative size. Separately, .migration-activity is capped to max-height: 40% with its own overflow-y: auto (customizationMigrationDashboard.css:315-321), independent of the page's own scroll. The boundary: do not touch the in-progress (non-complete) migration tree layout path, which already has its own sizing logic and is reported as fine — only the completed/all-migrated rendering path and the activity section's height budget are in scope.
- **Open decisions:**
  - Should the completed-state page scroll as one region (letting the activity list grow naturally), or should the activity list keep its own scroll box but with a different/less arbitrary height budget than 40%?
  - Should the success banner (.migration-result) be condensed/restyled for the completed state so the header doesn't dominate the page?

## Evidence

- **oversized header:** In showOverview() (src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationDashboard.ts:304-335), when allMigrationsComplete is true there is no migration tree (no layoutTree sizing), so the static .migration-page-header plus the .migration-result success banner (media/customizationMigrationDashboard.css:298-313) dominate the page relative to the remaining content.
- **constrained second scroll region:** .migration-activity is independently scrollable and height-capped: `flex: 0 1 auto; min-height: 0; max-height: 40%; overflow-y: auto;` (media/customizationMigrationDashboard.css:315-321), which combined with the overall page scroll produces exactly the 'two scrollable regions, one heavily height-constrained' described in the report and screenshot.
