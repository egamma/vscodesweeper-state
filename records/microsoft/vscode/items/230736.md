# Issue #230736 — Support Ghost Cells In Notebooks - Insert Cells In Edit Mode

[https://github.com/microsoft/vscode/issues/230736](https://github.com/microsoft/vscode/issues/230736)

## Summary

Keep open: the current notebook insertion and editing commands enter Markdown edit mode by moving focus, which does not satisfy background ghost-cell insertion. A maintainer has proposed two approaches, but the extension-facing behavior remains undecided and no verified canonical issue absorbs this request.

## Change summary

Allow extensions to present distinguishable suggested Markdown cells without interrupting typing in the current notebook cell.

## Best solution

Provide an extension-accessible notebook capability that supports suggested Markdown cells while preserving the user's active editor and selection. Resolve whether this means non-focusing edit-mode insertion or decoration support for rendered Markdown, retaining existing interactive command defaults.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/notebook/browser/controller/insertCellActions.ts`, `src/vs/workbench/contrib/notebook/browser/controller/editActions.ts`, `src/vs/workbench/contrib/notebook/browser/notebookEditorWidget.ts`, `src/vs/workbench/contrib/notebook/browser/viewModel/baseCellViewModel.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** Use an extension-driven notebook scenario: keep typing with a nonempty selection in cell A while inserting and updating suggested Markdown cells below it. Verify the suggestions have the agreed visual distinction, keyboard focus and selection remain in A, acceptance produces ordinary Markdown cells in the agreed mode, and existing interactive insertion/edit commands retain their behavior. The plan should establish automated notebook coverage for the chosen contract.
- **Behavior:**

  > An extension can insert and update suggested Markdown cells while the user continues editing another notebook cell. Suggestions must be visually distinguishable without substituting code cells for Markdown cells or moving keyboard focus and selection away from the user's editor. Accepting a suggestion must produce an ordinary Markdown cell with an explicitly agreed presentation mode. Existing interactive notebook insertion and editing behavior must remain unchanged.
- **Trace:**

  > InsertCellCommand.runWithContext in src/vs/workbench/contrib/notebook/browser/controller/insertCellActions.ts inserts a cell and then calls focusNotebookCell; the Markdown insertion actions request editor focus. EditCellAction in browser/controller/editActions.ts also enters through focusNotebookCell. In browser/notebookEditorWidget.ts, that method changes focus and sets CellEditState.Editing, while browser/viewModel/baseCellViewModel.ts defaults cells to Preview. The public NotebookCellData and NotebookEditor contracts in src/vscode-dts/vscode.d.ts expose no independent edit-state control. Maintainer comments at https://github.com/microsoft/vscode/issues/230736#issuecomment-2397794801 and https://github.com/microsoft/vscode/issues/230736#issuecomment-2397799899 suggest different observable approaches; neither is selected. The extension workaround documented in https://github.com/jlewi/foyle/issues/168 does not resolve the core API gap. Scope this work to extension-driven suggested Markdown presentation and focus preservation; broader multiplayer editing and arbitrary cell-removal focus behavior are separate concerns.
- **Open decisions:**
  - Should extensions expose suggested Markdown through non-focusing edit-mode insertion/state control, or through supported decorations on rendered Markdown cells?
  - When a suggested Markdown cell is accepted without explicitly moving focus to it, should it remain in edit mode or switch to rendered preview?
