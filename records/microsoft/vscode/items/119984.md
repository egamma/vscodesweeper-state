# Issue #119984 — EnvironmentVariableCollection in remote vs local terminals

[https://github.com/microsoft/vscode/issues/119984](https://github.com/microsoft/vscode/issues/119984)

## Summary

Keep open: the current environment collection API still cannot restrict contributions to remote terminals. This team-authored, accepted Backlog request has no verified fixing commit or qualifying older duplicate.

## Change summary

Allow extensions to restrict environment variable mutations to remote terminals rather than also affecting local terminals in a remote window.

## Best solution

Provide an explicit terminal-target scope for environment contributions while preserving existing unscoped behavior. The terminal API owners should settle the public scope semantics before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/platform/terminal/common/environmentVariable.ts`, `src/vs/platform/terminal/common/environmentVariableCollection.ts`, `src/vs/workbench/api/common/extHostTerminalService.ts`, `src/vs/workbench/api/browser/mainThreadTerminalService.ts`, `src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts`, `src/vs/workbench/contrib/terminal/browser/remoteTerminalBackend.ts`, `src/vs/workbench/contrib/terminal/test/common/environmentVariableCollection.test.ts`
- **Validation:** Extend the environmentVariableCollection unit suite with target-scope filtering cases and run it through scripts/test.sh with a targeted selector. In a Remote-SSH window, contribute a uniquely named remote-only variable, open both a remote terminal and a local terminal, and verify that only the remote terminal receives it while an unscoped contribution still reaches both.
- **Behavior:**

  > An extension must be able to contribute environment variables to remote terminals without those variables appearing in local terminals opened in the same remote window. Existing contributions without a target restriction must retain their current behavior. Acceptance should cover a remote-only contribution alongside an unscoped contribution in both terminal types, including interaction with workspace-folder scoping.
- **Trace:**

  > The public API in src/vscode-dts/vscode.d.ts offers mutation application timing and workspace-folder scopes, but no terminal-target scope. MainThreadTerminalService.$setEnvironmentVariableCollection publishes contributions into the shared environment service without distinguishing the originating extension host. TerminalProcessManager._resolveEnvironment applies that merged collection with only a workspace-folder scope, and filterScope in src/vs/platform/terminal/common/environmentVariableCollection.ts filters only by workspace folder index. This establishes the missing capability without executing terminals. The plan must trace remote backend transport, persistence, and environment-change reporting before defining the complete implementation boundary; preserve unscoped contributions and existing strictEnv semantics. Related https://github.com/microsoft/vscode/issues/125389 concerns strictEnv, while https://github.com/microsoft/vscode/issues/277958 illustrates reverse-direction locality leakage and is not a duplicate of this request.
- **Open decisions:**
  - Should terminal locality be expressed as a collection scope, a per-variable mutation option, or both?
  - Does remote-only mean any remote terminal in the window, or terminals associated with a specific remote authority?
