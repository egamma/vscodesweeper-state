# Issue #336860 — Settings Sync: consider recovery from transient authentication session lookup failures

[https://github.com/microsoft/vscode/issues/336860](https://github.com/microsoft/vscode/issues/336860)

## Summary

Keep open for the Settings Sync owner’s decision. Current main still converts an empty scoped-session lookup into an unavailable account and a sign-in prompt, while the older authentication issue deliberately split out this distinct local-recovery question.

## Change summary

Prevent Settings Sync from remaining stuck in a signed-out state after a transient authentication session lookup failure.

## Best solution

Decide whether Settings Sync should provide bounded recovery while the provider API cannot distinguish transient lookup failure from session absence. Any local recovery should retain the persisted session preference but must continue honoring explicit session-removal and terminal authentication-failure events.

- **Validation:** Exercise Settings Sync with a test authentication provider whose persisted session first yields an empty scoped lookup and later succeeds: verify recovery occurs without interactive sign-in, while an explicit removed-session event still clears the account and exposes the sign-in action.
- **Behavior:**

  > A temporary authentication lookup failure must not leave Settings Sync permanently showing "Sign in to Sync Settings" when the persisted session later becomes usable without interactive authentication. Settings Sync should recover automatically under the owner-approved policy. Explicit session removal, revoked credentials, and terminal authentication failures must still transition to the signed-out state. Acceptance should cover both transient recovery and genuine session removal.
- **Trace:**

  > UserDataSyncWorkbenchService.updateCurrentAccount() in src/vs/workbench/services/userDataSync/browser/userDataSyncWorkbenchService.ts looks up the persisted currentSessionId and assigns _current = undefined whenever getSessions() returns no match. update() then calls updateToken(undefined) and sets AccountStatus.Unavailable, which src/vs/workbench/contrib/userDataSync/browser/userDataSync.ts turns into the sign-in action and badge. The persisted session ID is cleared separately by onDidChangeSessions() for an explicit removal and by onDidAuthFailure(), so the current code already has a distinction that can bound any Settings Sync recovery policy. The provider-side cause and confirmed reproduction remain tracked by https://github.com/microsoft/vscode/issues/333975. Do not weaken explicit removal or terminal authentication-failure handling, and do not broaden this issue into redesigning the authentication provider contract.
- **Open decisions:**
  - While the authentication API represents transient token-acquisition failures as an empty session list, should Settings Sync provide its own bounded automatic recovery, or should it remain unavailable until the provider-layer contract in https://github.com/microsoft/vscode/issues/333975 is corrected?
