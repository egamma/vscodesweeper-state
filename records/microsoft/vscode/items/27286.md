# Issue #27286 — Explorer / Opened Editors Sorting

[https://github.com/microsoft/vscode/issues/27286](https://github.com/microsoft/vscode/issues/27286)

## Summary

Keep this open as the canonical Explorer custom-sorting request. Current main still exposes only fixed sort modes, later reports continue to be consolidated here, and the maintainer-confirmed design questions around extension latency and competing sort providers remain unresolved.

## Change summary

Support customizable Explorer ordering, including prioritized filenames or patterns and potentially extension-provided sorting.

## Best solution

Define one deterministic custom-sorting contract that preserves fast initial Explorer rendering and specifies how multiple contributions compose. Keep this canonical issue open until the remaining Explorer sorting scenarios are covered; the completed Open Editors work does not resolve them.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/browser/explorerService.ts`, `src/vs/workbench/contrib/files/common/files.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** Add targeted FileSorter/configuration tests proving the selected custom rules produce deterministic ordering, preserve every existing sort mode by default, define conflict precedence, and retain a renderable fallback when an extension contribution is unavailable or delayed.
- **Behavior:**

  > Users need to express Explorer ordering beyond the fixed built-in modes, including prioritizing selected filenames or patterns and supporting project- or language-specific order. Existing workspaces must retain their current ordering unless custom sorting is explicitly configured. Results must be deterministic when multiple rules or providers apply, and the Explorer must remain promptly renderable if extension-host data is delayed. Acceptance should cover custom priority, fallback ordering, conflicting contributions, files versus folders, and unchanged existing modes.
- **Trace:**

  > The configuration surface in src/vs/workbench/contrib/files/browser/files.contribution.ts exposes a closed enum plus lexicographic and reverse options. ExplorerService in src/vs/workbench/contrib/files/browser/explorerService.ts reads that configuration, and FileSorter.compare in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts synchronously applies it; no custom/provider branch exists. The public extension declarations under src/vscode-dts and workbench API plumbing expose no Explorer sorting provider. The issue is the canonical tracker, as confirmed by later duplicate closures including https://github.com/microsoft/vscode/issues/296457#issuecomment-5833897386. The uncertainty begins at the public contract and runtime behavior identified by the maintainer: whether customization is declarative or extension-driven, how competing contributions compose, and what users see while extension-host results are pending. Preserve existing default modes, workspace-root ordering, and the already-completed Open Editors sorting behavior unless the chosen contract explicitly expands scope.
- **Open decisions:**
  - Should custom Explorer ordering be a declarative user/workspace setting, a public extension API, or both?
  - If extensions can contribute sorting, what deterministic precedence or composition contract applies when multiple extensions contribute incompatible orders?
  - When extension-provided ordering is delayed or unavailable, should the Explorer block, render immediately with built-in ordering and later re-sort, or use another explicitly defined fallback?
