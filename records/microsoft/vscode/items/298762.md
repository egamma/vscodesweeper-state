# Issue #298762 — Remove simple browser extension

[https://github.com/microsoft/vscode/issues/298762](https://github.com/microsoft/vscode/issues/298762)

## Summary

The migration remains incomplete: Simple Browser still ships as an extension, and core's web browser service has no iframe implementation. Keep this team-authored cleanup open; desktop command delegation covers only part of the requested work.

## Change summary

Remove the Simple Browser extension while retaining its legacy commands and providing an iframe-based browser in core for web.

## Best solution

Core should own the web iframe browser and compatibility entry points, allowing the extension and its build wiring to be retired without losing web browsing. Plan the migration across browser contributions, legacy commands, URL opening, and restored browser tabs before implementation.

## Plan brief

- **Likely files:** `extensions/simple-browser/package.json`, `extensions/simple-browser/src/extension.ts`, `extensions/simple-browser/src/simpleBrowserView.ts`, `src/vs/workbench/contrib/browserView/browser/browserView.contribution.ts`, `src/vs/workbench/contrib/browserView/electron-browser/browserView.contribution.ts`, `src/vs/workbench/workbench.web.main.ts`, `src/vs/workbench/browser/parts/editor/editorConfiguration.ts`, `build/gulpfile.extensions.ts`, `build/npm/dirs.ts`, `build/lib/extensions.ts`
- **Validation:** In desktop and web workbenches without the Simple Browser extension, invoke simpleBrowser.show and simpleBrowser.api.open with a frameable test URL and verify that browsing still works. Check the web localhost opener, iframe navigation and reload, and restoration of a previously saved simpleBrowser.view tab; desktop commands must continue opening the integrated browser.
- **Behavior:**

  > The Simple Browser extension is no longer required or bundled, but its existing command IDs remain callable. Desktop callers continue to reach the integrated browser, while web users retain iframe-based browsing provided by core. Acceptance checks must cover both legacy commands and the existing web URL-opening flow, with an explicit compatibility outcome for previously saved Simple Browser tabs.
- **Trace:**

  > extensions/simple-browser/src/extension.ts currently owns both legacy command registrations, external URI opening, and the simpleBrowser.view serializer. It delegates to workbench.action.browser.open when available and otherwise uses SimpleBrowserManager and SimpleBrowserView, whose HTML contains the iframe. Core's web entry point imports src/vs/workbench/contrib/browserView/browser/browserView.contribution.ts, but that contribution supplies unavailable-service stubs rather than a browser editor; the desktop contribution registers the native editor separately. Build references and the editor auto-lock configuration also name Simple Browser, so the full retirement boundary extends beyond deleting its folder. Preserve desktop native-browser behavior and do not assume Electron browser capabilities can run in an iframe. The closed request https://github.com/microsoft/vscode/issues/331784 establishes that distinction, not a reason to abandon this migration. The trace establishes the ownership split, but not a complete cross-layer migration or restoration design.
- **Open decisions:**
  - Must previously saved simpleBrowser.view tabs reopen automatically after the extension is removed, or is compatibility limited to the legacy commands?

## Evidence

- **Extension still present:** extensions/simple-browser/package.json still declares desktop and browser entry points, simpleBrowser.show, activation for simpleBrowser.api.open, and webview restoration. build/gulpfile.extensions.ts, build/npm/dirs.ts, and build/lib/extensions.ts still include the extension.
- **Partial compatibility already implemented:** extensions/simple-browser/src/extension.ts registers simpleBrowser.show and simpleBrowser.api.open. Both delegate to workbench.action.browser.open when that command exists, otherwise they use SimpleBrowserManager; the external URI opener follows the same split. The legacy registrations therefore still depend on the extension.
- **Web implementation remains extension-owned:** extensions/simple-browser/src/simpleBrowserView.ts creates the webview panel and sandboxed iframe. In contrast, src/vs/workbench/contrib/browserView/browser/browserView.contribution.ts registers WebBrowserViewWorkbenchService whose createBrowserView and getOrCreateLazy methods throw 'Integrated Browser is not available in web.'
