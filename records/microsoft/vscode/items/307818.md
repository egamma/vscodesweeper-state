Source Control should automatically update after files are modified in a devcontainer whose workspace resides on the Windows filesystem.

## Plan brief

- **Likely files:** `extensions/git/src/repository.ts`, `src/vs/server/node/remoteFileSystemProviderServer.ts`, `src/vs/platform/files/node/watcher/parcel/parcelWatcher.ts`
- **Validation:** On Windows 11, open a Windows-filesystem Git checkout through Dev Containers with git.autorefresh enabled. Save a tracked-file modification while the window is focused and Git is idle; verify that Source Control updates without manual Refresh. Correlate Git trace and remote filesystem-watcher events, and repeat with file creation and deletion.
- **Behavior:**

  > After reopening a Windows-hosted repository in a devcontainer, saving a tracked-file modification should update the Source Control changes list automatically. Manual Refresh currently updates the list and serves as the control showing that Git can discover the change. Acceptance must preserve the Windows-filesystem workspace rather than substitute WSL2 or a container volume.
- **Trace:**

  > Repository in extensions/git/src/repository.ts subscribes to workspace filesystem events and routes them through onFileChange to a debounced status operation. That operation can be suppressed by configuration, repository size, active operations or window focus. The remote filesystem provider configures recursive watcher options in src/vs/server/node/remoteFileSystemProviderServer.ts; native recursive watching is implemented in src/vs/platform/files/node/watcher/parcel/parcelWatcher.ts. Source inspection did not establish whether notifications are missing or Git suppresses an event that arrives. Begin by reproducing and observing that boundary; preserve existing refresh settings and focus/throttling semantics, and do not introduce general polling based solely on this report.
