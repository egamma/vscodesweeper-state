# Issue #132776 — Display 2 spaces instead of 4 without changing the code or project settings

[https://github.com/microsoft/vscode/issues/132776](https://github.com/microsoft/vscode/issues/132776)

## Summary

Keep this accepted, well-supported request open: current settings change tab display width or editing indentation, not the visual width of existing space indentation. Maintainers have consolidated newer requests here, and no verified older open canonical owns the same work.

## Change summary

Allow users to display space-indented code at a preferred indentation width without changing source characters or project indentation requirements.

## Best solution

Provide an opt-in editor presentation capability that decouples leading-space indentation width from stored indentation, with consistent guides, cursor positioning, selections, and wrapping. Establish its rendering and accessibility contract before implementation rather than relying on the reported buggy extension workaround.

## Plan brief

- **Likely files:** `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/common/viewLayout/viewLineRenderer.ts`, `src/vs/editor/browser/viewParts/viewLines/viewLine.ts`, `src/vs/editor/browser/viewParts/indentGuides/indentGuides.ts`, `src/vs/editor/common/viewModel/monospaceLineBreaksComputer.ts`, `src/vs/editor/browser/gpu/renderStrategy/viewportRenderStrategy.ts`, `src/vs/editor/test/common/viewLayout/viewLineRenderer.test.ts`, `src/vs/editor/test/common/viewModel/monospaceLineBreaksComputer.test.ts`
- **Validation:** Plan regression checks in the existing viewLineRenderer and monospaceLineBreaksComputer suites for four-space indentation displayed at two-column width and the inverse. Verify interactively that nested and blank-line guides, mouse hit-testing, caret positions, selections, wrapping, and scrolling agree with the presentation, while opening and saving leaves source text unchanged and new indentation still inserts the project's required characters. Include DOM/GPU rendering and screen-reader checks under the agreed contract.
- **Behavior:**

  > A user viewing a four-space-indented file can choose a two-column visual indentation without changing existing source characters or the project's four-space editing requirements. The inverse accessibility use case, displaying two-space indentation more widely, is also represented in the discussion. New indentation must retain the project's stored indentation convention while using the chosen presentation. Guides, caret positions, selections, and wrapping must remain consistent with the displayed text, and disabling the capability must restore existing behavior. Visual resizing must not be represented as automatically solving Braille indentation.
- **Trace:**

  > The existing editor.action.changeTabDisplaySize action updates tabSize, while viewLineRenderer gives each source space one unit of width regardless of that option; editor.indentSize governs editing rather than an independent visual space width. IndentGuidesOverlay derives guide placement from model indentation and font geometry, and viewLine position mapping, monospace wrapping, and GPU rendering also contain width assumptions, so this is not a standalone CSS adjustment. The supplied Stretchy Spaces experience demonstrates why guide and scrolling consistency belong in the acceptance boundary. Maintainers have consolidated https://github.com/microsoft/vscode/issues/187116, https://github.com/microsoft/vscode/issues/215923, and https://github.com/microsoft/vscode/issues/323076 here. Preserve source text, project formatting requirements, and existing behavior when the feature is disabled; automatic whitespace conversion is outside this request. Uncertainty remains in the user-facing presentation control and treatment of partial or mixed indentation, plus whether this is visual-only or includes an explicitly chosen accessible-navigation contract.
- **Open decisions:**
  - Should users select a target visual width per indentation level, or a multiplier for leading-space width, and how should that preference interact with detected indentation?
  - How should presentation handle partial indentation levels and mixed leading tabs and spaces without changing source characters?
  - Should the first version preserve existing character-by-character navigation and accessible text exactly, or introduce an explicit indentation-block navigation or Braille presentation mode?
