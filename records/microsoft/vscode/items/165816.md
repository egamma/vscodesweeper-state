# Issue #165816 — _sendLineData can freeze the renderer for seconds for very long lines

[https://github.com/microsoft/vscode/issues/165816](https://github.com/microsoft/vscode/issues/165816)

## Summary

The synchronous long-line assembly path remains on main when line-data listeners are attached, including task problem matchers. Lazy activation reduced exposure but did not resolve that path; retain this issue and settle how responsiveness should be protected without losing task diagnostics.

## Change summary

Prevent extremely long wrapped terminal lines from monopolizing the renderer while assembling line-data events.

## Best solution

Make LineDataEventAddon handle extreme wrapped output without long synchronous renderer stalls, with an explicit compatibility contract for task problem matchers. Determine whether complete line delivery must be preserved or whether bounded, potentially lossy delivery is acceptable before implementing a cutoff.

- **Behavior:**

  > Extremely long wrapped output in a terminal with active line-data consumers must not cause multi-second renderer stalls during line assembly. Ordinary wrapped lines must continue to reach task problem matchers with their existing content and ordering. Acceptance must cover both newline-triggered emission and Windows cursor-position-triggered emission, as well as diagnostics beyond any proposed length threshold. Whether oversized lines may lose content remains a product-contract decision; do not assume a 1024-character limit is safe.
- **Trace:**

  > LineDataEventAddon._sendLineData in src/vs/workbench/contrib/terminal/browser/xterm/lineDataEventAddon.ts synchronously translates every retained row of a wrapped logical line and prepends the result before emitting it. TerminalInstance loads this addon on the first onLineData listener, and TerminalTaskSystem forwards emitted lines to watching and start-stop problem collectors. https://github.com/microsoft/vscode/commit/38ddde8782ac6413a1303f5b1e398e130b536313 addressed lazy activation for https://github.com/microsoft/vscode/issues/166031, not the cost of assembly with listeners present. The existing addon tests establish complete wrapped-line and Windows cursor-move delivery behavior, which must remain unchanged for ordinary input. The source confirms synchronous work proportional to the retained wrapped output, but no current runtime measurement establishes the reported three-second duration. Planning should resolve the oversized-line delivery contract and responsiveness budget; terminal search performance in https://github.com/microsoft/vscode/issues/152548 is a separate observable problem.
- **Open decisions:**
  - Must oversized logical lines remain complete for task problem matchers and other onLineData consumers, or may their delivery be truncated or skipped? If loss is acceptable, what limit and observable handling should consumers receive?
