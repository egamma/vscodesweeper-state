# Issue #255894 — Ability to share chat threads

[https://github.com/microsoft/vscode/issues/255894](https://github.com/microsoft/vscode/issues/255894)

## Summary

A real gap remains: current VS Code can export and import chat files, but it does not create a viewable share link. This team-authored Backlog request is the oldest canonical report, so it should remain open for product and service design.

## Change summary

Allow users to publish a Copilot chat thread, including prompts and tool history, through a shareable viewing link.

## Best solution

Provide an explicit, privacy-conscious sharing flow that publishes a selected chat snapshot to a hosted viewer and returns a revocable link. The design should build on existing chat serialization and cloud-session infrastructure while clearly defining included content, access control, and retention.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/actions/chatImportExport.ts`, `src/vs/workbench/contrib/chat/common/model/chatModel.ts`, `extensions/copilot/src/extension/chronicle/vscode-node/remoteSessionExporter.ts`, `extensions/copilot/src/extension/chronicle/node/cloudSessionApiClient.ts`
- **Validation:** End the plan with action and service tests proving that an explicitly shared session produces a viewable URL containing the approved content, while unshared or revoked sessions remain inaccessible; include an end-to-end manual check from VS Code through the hosted viewer.
- **Behavior:**

  > A user can explicitly share the current Copilot chat and receive a link that another intended viewer can open without importing a local file. The shared snapshot contains only the content categories approved by the product design, with sensitive context disclosed before publishing. The user can revoke sharing, after which the link no longer exposes the conversation. Existing local JSON import/export remains available and unchanged.
- **Trace:**

  > Current chat serialization and local transfer are implemented by workbench.action.chat.export/import in src/vs/workbench/contrib/chat/browser/actions/chatImportExport.ts using ChatModel.toExport from src/vs/workbench/contrib/chat/common/model/chatModel.ts. Cloud synchronization already flows through RemoteSessionExporter and CloudSessionApiClient under extensions/copilot/src/extension/chronicle, but the traced client has no public-link, visibility, or revocation contract. The newer https://github.com/microsoft/vscode/issues/281284 explores Gists as an interim transport and does not supersede this broader first-party sharing request. Planning must cover the VS Code action, service contract, hosted viewer, access policy, and redaction boundary; it must not weaken existing session-indexing consent or silently publish chats.
- **Open decisions:**
  - Who may open a shared link: anyone with the link, authenticated GitHub users, or explicitly selected organization members?
  - Which session content is included by default, especially tool inputs and outputs, file contents, terminal output, repository metadata, and hidden model context?
  - Is a shared thread an immutable snapshot or a live view that incorporates later turns?
  - What retention, expiration, and revocation behavior applies to published links?
  - Should sharing be implemented as a first-party hosted viewer, or should the initial product surface use an existing transport such as GitHub Gists?

## Evidence

- **existing capability:** src/vs/workbench/contrib/chat/browser/actions/chatImportExport.ts registers workbench.action.chat.export and workbench.action.chat.import, but these only write and read a local chat.json file; they do not create a hosted or viewable link.
- **current cloud path:** extensions/copilot/src/extension/chronicle/vscode-node/remoteSessionExporter.ts synchronizes session events to cloud storage, while extensions/copilot/src/extension/chronicle/node/cloudSessionApiClient.ts exposes create, submit, get, list, and delete operations; no public-sharing or share-link operation was found in the traced paths.
