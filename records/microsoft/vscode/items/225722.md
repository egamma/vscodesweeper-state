# Issue #225722 — Editor GPU: Persist texture atlas to disk

[https://github.com/microsoft/vscode/issues/225722](https://github.com/microsoft/vscode/issues/225722)

## Summary

Keep this protected plan-item open: current GPU rendering shares an in-memory atlas but still warms it anew after startup, so persistent reuse remains missing.

## Change summary

Persist the editor GPU texture atlas across window startups and invalidate cached data when rendering inputs change.

## Best solution

Retain this focused planning item within the WebGPU renderer work and establish a persistent atlas cache that avoids repeated rasterization without delaying initial rendering or reusing incompatible glyphs.

- **Existing capability and remaining gap:** src/vs/editor/browser/gpu/viewGpuContext.ts maintains a static ViewGpuContext._atlas and constructs TextureAtlas when the window's GPU device resolves. This shares the atlas across editor views in memory, not across process startups.
- **Current warm-up and invalidation:** src/vs/editor/browser/gpu/atlas/textureAtlas.ts initializes fresh atlas pages and an empty _warmedUpRasterizers set; getGlyph schedules _warmUpAtlas for each previously unseen rasterizer. Warm-up rasterizes ASCII glyphs for token colors through IdleTaskQueue. Theme changes clear the atlas, and viewGpuContext.ts also clears it on device-pixel-ratio changes. These paths contain no persistent cache restoration.
- **Configuration check:** src/vs/editor/common/config/editorOptions.ts registers editor.experimentalGpuAcceleration with on/off values and default off. It selects the renderer; it does not provide atlas persistence or eliminate GPU warm-up.
- **Related umbrella verified:** https://github.com/microsoft/vscode/issues/221145 is open and explicitly tracks the multi-month WebGPU renderer effort, including the possibility of caching texture atlas pages to disk.
