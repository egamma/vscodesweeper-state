# Issue #232538 — Give more control over syncing rapidly updating documents with extensions

[https://github.com/microsoft/vscode/issues/232538](https://github.com/microsoft/vscode/issues/232538)

## Summary

A real gap remains: current main forwards every synchronized model change immediately to extensions, while chat code blocks and editing flows can update models continuously during streaming. The earlier targeted implementation was rejected in favor of a holistic rapid-edit design, and no replacement is present.

## Change summary

Provide a way to suppress, defer, or otherwise identify extension synchronization while a text model is receiving rapid incomplete updates.

## Best solution

Design a model-level rapid-edit contract that covers chat code blocks, inline chat, and streamed edits to ordinary files while preserving normal extension document versions and editor lifecycle behavior. A maintainer should first decide whether extensions receive a consolidated final change or explicit rapid-edit state notifications.

## Plan brief

- **Likely files:** `src/vs/editor/common/model.ts`, `src/vs/workbench/api/browser/mainThreadDocuments.ts`, `src/vs/workbench/api/browser/mainThreadDocumentsAndEditors.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/codeBlockPart.ts`, `src/vs/workbench/api/test/browser/mainThreadDocuments.test.ts`, `src/vs/workbench/api/test/browser/mainThreadDocumentsAndEditors.test.ts`
- **Validation:** Add main-thread document synchronization tests covering a model entering rapid-edit state, receiving multiple changes, and leaving that state; verify the chosen extension-visible event/version contract and run `scripts/test.sh --grep "MainThreadDocuments"`.
- **Behavior:**

  > When VS Code streams a sequence of incomplete edits into a text model, language extensions should not be forced to process every transient intermediate state. Once the rapid-edit interval ends, extensions must observe a coherent current document with correct versioning. Ordinary user edits and models outside rapid-edit intervals must retain their existing synchronization behavior. The contract must cover chat code blocks, inline chat, and streamed edits to regular files.
- **Trace:**

  > `shouldSynchronizeModel` in `src/vs/editor/common/model.ts` currently makes a static decision based only on model size and simple-widget status. `ModelTracker` in `src/vs/workbench/api/browser/mainThreadDocuments.ts` forwards every content event immediately, while `MainThreadDocumentsAndEditors` separately maintains extension-visible document and editor membership. `CodeBlockPart.setText` in `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/codeBlockPart.ts` demonstrates one producer of rapid updates, and chat editing has additional regular-file edit paths. https://github.com/microsoft/vscode/pull/233455 was closed after review identified dynamic synchronization membership as risky and too narrow; https://github.com/microsoft/vscode/pull/233821 reverted the prior dual-model workaround. The boundary is extension synchronization during explicitly marked rapid edits: normal content events, document/editor lifecycle, final model contents, and unrelated editor contribution behavior must not regress.
- **Open decisions:**
  - Should extensions receive one consolidated content change after rapid editing, receive ordinary changes tagged with rapid-edit state, or receive separate start/end notifications?
  - Is rapid-edit state an internal text-model capability, an extension-facing API, or both?
  - How should document version IDs, dirty state, and extension-visible document/editor membership behave while synchronization is deferred?
  - Which producers may mark rapid edits, and how should nested, canceled, or interrupted edit intervals be handled?

## Evidence

- **current synchronization path:** On current main, `shouldSynchronizeModel` in `src/vs/editor/common/model.ts` only excludes oversized and simple-widget models; it has no temporary rapid-edit state.
- **extension-host forwarding:** `ModelTracker` in `src/vs/workbench/api/browser/mainThreadDocuments.ts` subscribes to every `ITextModel.onDidChangeContent` event and immediately calls `$acceptModelChanged`, so synchronized extensions observe each streamed update.
- **streaming model updates:** `CodeBlockPart.setText` in `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/codeBlockPart.ts` appends with `applyEdits` or replaces with `setValue`; non-simple code-block models therefore continue through the ordinary synchronization path.
- **rejected narrow approach:** Closed PR https://github.com/microsoft/vscode/pull/233455 attempted dynamic control of `shouldSynchronizeModel`, but review concluded that changing synchronized status was risky and that the solution must also cover inline chat and Copilot edits to regular files.
- **revert preserves the gap:** Merged PR https://github.com/microsoft/vscode/pull/233821 reverted the dual-model workaround and explicitly described the revert as temporary pending a better fix for https://github.com/microsoft/vscode/issues/232538.
- **related narrower issue:** https://github.com/microsoft/vscode/issues/230326 remains open for exposing completed chat code blocks; this issue owns the broader synchronization mechanism needed across rapidly edited models.
