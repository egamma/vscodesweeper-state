# Issue #232538 — Give more control over syncing rapidly updating documents with extensions

[https://github.com/microsoft/vscode/issues/232538](https://github.com/microsoft/vscode/issues/232538)

## Summary

Keep open: current document synchronization still forwards each model change, and the proposed change-reason API does not provide rapid-edit lifecycle or synchronization controls. Maintainers explicitly requested a solution covering both streaming code blocks and edits to regular files; the related merged PR reverted an earlier approach rather than completing that work.

## Change summary

Give VS Code and language extensions a way to avoid unnecessary processing of incomplete documents during rapid streamed edits.

## Best solution

Agree on a rapid-edit contract covering chat code blocks, inline chat, and edits to regular files, while preserving coherent extension document state. Decide whether extensions should receive lifecycle hints while synchronization continues, or whether synchronization itself should be deferred.

- **Behavior:**

  > Rapid streamed edits should not force participating language extensions to repeatedly perform expensive work on transient, incomplete document states. The behavior must cover chat code blocks and edits to ordinary files, not only hide incomplete panel code blocks. Extensions must retain coherent document contents and versions, and normal editing must remain unchanged. Acceptance checks must cover completion and interruption of a rapid-edit sequence under the chosen public contract.
- **Trace:**

  > shouldSynchronizeModel in src/vs/editor/common/model.ts filters only oversized and simple-widget models. MainThreadDocumentsAndEditors uses that predicate to expose models and editors, while ModelTracker in src/vs/workbench/api/browser/mainThreadDocuments.ts forwards each content event to ExtHostDocuments.$acceptModelChanged in src/vs/workbench/api/common/extHostDocuments.ts. The proposed textDocumentChangeReason API supplies attribution but does not itself define a rapid-edit interval or suppress synchronization. In https://github.com/microsoft/vscode/pull/233455#issuecomment-2473302844, a maintainer rejected a code-block-only synchronization toggle as insufficient and requested coverage of regular-file edits as well. https://github.com/microsoft/vscode/pull/233821 reverted the earlier dual-model implementation rather than resolving this request. Preserve document/editor lifecycle consistency, final text/version correctness, and ordinary editing; uncertainty starts at whether the new contract changes synchronization or only advises consumers to defer expensive work.
- **Open decisions:**
  - Should extensions continue receiving every document update with explicit rapid-edit lifecycle hints, or should synchronization itself be deferred during the interval?
  - What extension-visible completion semantics should apply when streaming is cancelled or fails, including when consumers must resume processing the final available document state?
