# Issue #137614 — Multiple quiet login requests (different scopes) from an extension to a single AuthenticationProvider are indistinguishable on the Accounts menu

[https://github.com/microsoft/vscode/issues/137614](https://github.com/microsoft/vscode/issues/137614)

## Summary

Keep open: current Accounts menu entries still cannot distinguish different scope requests from the same extension and provider. Interactive authentication now supports explanatory detail, but that does not cover quiet requests; this issue remains the maintainer-selected home for scope-display improvements.

## Change summary

Make authentication requests with different scopes distinguishable and explain which permissions each request needs.

## Best solution

Provide meaningful request context in the Accounts menu and explain requested permissions before authentication proceeds. Preserve the existing quiet-request behavior, with a maintainer decision on how extensions and providers supply understandable descriptions.

Verify the Accounts menu lets the user distinguish their purposes before choosing, and any confirmation explains the selected request. Confirm each choice authenticates its original scope set, interactive detail still works, and silent: true creates no menu entry.
- **Behavior:**

  > Two quiet authentication requests from the same extension to the same provider currently appear with identical Accounts menu labels despite requesting different permissions. Users should be able to distinguish their purposes before choosing and understand the permissions associated with the selected request. Quiet requests must remain non-modal until the user acts, and choosing an entry must authenticate the corresponding original request. Existing interactive explanatory detail and fully silent requests must retain their behavior.
- **Trace:**

  > AuthenticationExtensionsService.requestNewSession in src/vs/workbench/services/authentication/browser/authenticationExtensionsService.ts keys requests separately but builds menu titles using only the provider label and extension name. Its command handler calls createSession directly with the captured scope request and provider options. MainThreadAuthentication.loginPrompt in src/vs/workbench/api/browser/mainThreadAuthentication.ts accepts interactive explanatory detail, while AuthenticationGetSessionPresentationOptions in src/vscode-dts/vscode.d.ts exposes that detail only through interactive options. Source inspection establishes that the completed work in https://github.com/microsoft/vscode/issues/117358 does not distinguish quiet menu requests. The maintainer consolidated https://github.com/microsoft/vscode/issues/96609 into this issue, making this the remaining scope-presentation record. Preserve request identity, scope selection, session preferences, and quiet-versus-silent semantics; the unresolved boundary is the user-facing description contract, not request bookkeeping.
- **Open decisions:**
  - Should request distinctions use extension-supplied purpose text, provider-supplied human-readable scope descriptions, or both, and what should users see when neither description is available?
