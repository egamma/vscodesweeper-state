# Issue #256761 — Install button should be first tab stop on extension page

[https://github.com/microsoft/vscode/issues/256761](https://github.com/microsoft/vscode/issues/256761)

## Summary

Keep open: the extension editor still places focusable header content before Install, and the linked implementation was closed without merging after the author reported that it did not work. The issue already has the appropriate accessibility and extensions labels.

## Change summary

Make Install the first keyboard tab stop on an extension details page when installation is available.

## Best solution

Deliver Install-first keyboard navigation across the extension editor, not merely within its action bar, while preserving the existing visual and DOM action order requested in the PR discussion. Verify the complete editor-entry and tab-navigation flow before treating this as resolved.

Establish a repeatable browser regression check for this flow before implementation.
- **Behavior:**

  > On an extension details page where installation is available, keyboard users should reach Install as the first page tab stop rather than traversing metadata or unrelated actions first. Other interactive header controls must remain keyboard-accessible. The visual layout and DOM order of toolbar actions must remain unchanged. Acceptance must exercise entry into the complete editor and Tab/Shift+Tab navigation, including a page where Install is unavailable.
- **Trace:**

  > ExtensionEditor.createEditor() in src/vs/workbench/contrib/extensions/browser/extensionEditor.ts creates the focusable root and extension-name heading before the actions container. The extension toolbar calls ActionBar.setFocusable(), whose implementation in src/vs/base/browser/ui/actionbar/actionbar.ts selects the first enabled view item without controlling earlier page elements. ExtensionEditor.focus() delegates to activeElement, and onNavbarChange() can focus the selected content, so initial editor entry also needs examination. https://github.com/microsoft/vscode/pull/257353 tried changing only toolbar view-item focusability and was closed unmerged; the author reported failure at https://github.com/microsoft/vscode/pull/257353#issuecomment-3632981656. Preserve action DOM order as requested at https://github.com/microsoft/vscode/pull/257353#issuecomment-3377558645, and avoid changing unrelated action bars. The remaining uncertainty is how to exercise and pin the complete browser focus sequence; the inspected extension test directories contain no dedicated extension-editor focus suite.
