# Issue #256761 — Install button should be first tab stop on extension page

[https://github.com/microsoft/vscode/issues/256761](https://github.com/microsoft/vscode/issues/256761)

## Summary

The accessibility defect remains on current main: the extension-page ActionBar selects its first enabled action as the tab stop, while Install appears much later in the unchanged DOM order. The only linked fix attempt was closed unmerged after the issue author confirmed that it did not work, so this team-authored Backlog bug should remain open.

## Change summary

Make the Install button the first keyboard tab stop on an uninstalled extension's details page without changing the actions' DOM order.

## Best solution

Give the extension editor a supported way to choose Install as the action bar's initial tab stop while retaining DOM order and roving arrow-key navigation, including after action enablement changes.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/extensions/browser/extensionEditor.ts`, `src/vs/base/browser/ui/actionbar/actionbar.ts`, `src/vs/base/test/browser/actionbar.test.ts`
- **Validation:** End with an automated browser test, or an equivalent runnable accessibility check, showing that Tab enters an uninstalled extension page on Install, only one action has tabIndex 0, DOM order is unchanged, arrow navigation still works, and action enablement changes preserve the Install entry point.
- **Behavior:**

  > On an uninstalled extension's details page, pressing Tab into the primary action area must focus Install first. The actions must retain their existing DOM and visual order, and arrow-key navigation within the action bar must continue to work. Changes in action enablement must not move the tab entry point away from Install while Install is available.
- **Trace:**

  > ExtensionEditor builds the primary actions in src/vs/workbench/contrib/extensions/browser/extensionEditor.ts, with InstallDropdownAction after fourteen other entries, and initializes focus by calling ActionBar.setFocusable(true). ActionBar.setFocusable() in src/vs/base/browser/ui/actionbar/actionbar.ts always makes the first enabled BaseActionViewItem focusable; the extension editor repeats that reset whenever action enablement changes. The closed attempt at https://github.com/microsoft/vscode/pull/257353 manipulated ActionBar view items after initialization, but https://github.com/microsoft/vscode/pull/257353#issuecomment-3632981656 records that runtime testing failed. Preserve the current DOM order as explicitly required in https://github.com/microsoft/vscode/pull/257353#issuecomment-3377558645, and do not alter tab behavior for unrelated action bars.
