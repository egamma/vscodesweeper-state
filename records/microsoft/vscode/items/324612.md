# Issue #324612 — Main process crashes with SQLITE_BUSY on new APPLICATION_SHARED storage (.vscode-shared\sharedStorage\state.vscdb) when two instances run concurrently

[https://github.com/microsoft/vscode/issues/324612](https://github.com/microsoft/vscode/issues/324612)

## Summary

The crash remains reproducible across current Windows and macOS builds, and current main still lets SQLite transaction lock failures reject through the main-process storage flush path. Keep this open while the linked draft fix is reviewed and prepared for upstream submission.

## Change summary

Transient SQLITE_BUSY failures while writing application storage can become unhandled main-process exceptions and terminate every VS Code window.

## Best solution

Review and upstream the bounded recovery implemented by https://github.com/cstolting-collab/vscode/pull/1, ensuring transient lock contention waits or retries without losing pending writes or producing an unhandled rejection, while preserving existing recovery behavior for non-transient SQLite errors.

## Evidence

- **independent reproductions:** Three reporters reproduced the same `transaction(): SQLITE_BUSY` followed by `[uncaught exception in main]` on releases through 1.139.0; one report documents seven Crashpad dumps, and the later macOS reproduction shows the defect also affects ordinary application storage rather than only `.vscode-shared`.
- **current source:** At main commit dd7687527a42277a9625f06391880cb5aaa4fc83, `src/vs/platform/storage/electron-main/storageMain.ts` constructs both `BaseProfileAwareStorageMain` and `ApplicationSharedStorageMain` SQLite databases without the available `busyTimeout` option.
- **failure path:** `src/vs/base/parts/storage/node/storage.ts` lines 413-425 reject an `END TRANSACTION` SQLITE_BUSY after marking the connection erroneous, with no transaction-level retry or rollback; `src/vs/base/parts/storage/common/storage.ts` lines 363-383 clear pending inserts/deletes before awaiting `database.updateItems`, so a rejected flush is not preserved for retry.
- **open fix attempt:** The open draft https://github.com/cstolting-collab/vscode/pull/1 explicitly references this issue and adds contention recovery, failed-flush preservation, rejection containment, and regression coverage. Its focused storage validation passed, but it has not been submitted or merged upstream.
- **impact:** Multiple independent reports show the main process terminating all windows shortly after the storage error, including repeated crashes across several releases and both Windows and macOS.
