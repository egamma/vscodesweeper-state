# Issue #324612 — Main process crashes with SQLITE_BUSY on new APPLICATION_SHARED storage (.vscode-shared\sharedStorage\state.vscdb) when two instances run concurrently

[https://github.com/microsoft/vscode/issues/324612](https://github.com/microsoft/vscode/issues/324612)

## Summary

Confirmed in current source: ApplicationSharedStorageMain opens its SQLiteStorageDatabase without a busyTimeout, and SQLiteStorageDatabase.transaction() has no SQLITE_BUSY retry at all (only connect() retries once), so a lock collision between two concurrently-writing processes/windows rejects into an unhandled rejection that crashes the main process — matching the reported log signature exactly.

## Change summary

The new multi-process APPLICATION_SHARED storage DB can hit SQLITE_BUSY during an ordinary write transaction, and that error is unhandled and crashes the whole main process instead of being retried or contained.

## Best solution

In src/vs/platform/storage/electron-main/storageMain.ts, pass a `busyTimeout` option when constructing the SQLiteStorageDatabase for ApplicationSharedStorageMain (it's the one scope explicitly meant for multi-process access); in src/vs/base/parts/storage/node/storage.ts, add bounded retry/backoff for SQLITE_BUSY inside transaction() (not just connect()), and ensure that failure path cannot surface as an unhandled rejection that terminates the process.

## Evidence

- **no busyTimeout on shared storage:** src/vs/platform/storage/electron-main/storageMain.ts:378 constructs `new SQLiteStorageDatabase(storageFilePath, { logging: this.createLoggingOptions() })` for ApplicationSharedStorageMain.doCreate() with no `busyTimeout`, so `PRAGMA busy_timeout` is never set for this multi-process-shared DB (compare the option definition at src/vs/base/parts/storage/node/storage.ts:23-33).
