# Issue #274673 — Copilot Chat does not load/takes very long to load models on remote

[https://github.com/microsoft/vscode/issues/274673](https://github.com/microsoft/vscode/issues/274673)

## Summary

Keep open: the supplied timestamps identify a roughly 14-minute experimentation fetch that blocked Copilot Chat activation and model registration. Current main still awaits the initial experimentation fetch before creating contributions, so the underlying blocking path remains even though its network transport has since improved.

## Change summary

Copilot Chat activation and model availability can be delayed for many minutes in a remote window while the initial experimentation request is pending.

## Best solution

Ensure a slow or unreachable experimentation service cannot indefinitely block Chat contributions and model registration, while preserving a defined policy for cached or late-arriving experiment assignments.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/extension/vscode/extension.ts`, `extensions/copilot/src/platform/telemetry/node/baseExperimentationService.ts`, `extensions/copilot/src/platform/telemetry/vscode-node/microsoftExperimentationService.ts`, `extensions/copilot/src/platform/telemetry/test/node/experimentation.spec.ts`
- **Validation:** Add a targeted Vitest case with a non-settling or delayed TAS `initialFetch` and verify that Chat contributions become available within the chosen bound while a later successful fetch still updates treatments; run the experimentation and activation-related unit suites.
- **Behavior:**

  > Opening Copilot Chat in a remote window must not leave models unavailable for many minutes solely because the experimentation service is slow or unreachable. Authentication and model registration should become usable within a defined bounded interval. Experiment assignments that arrive later must still be applied according to the selected freshness policy, and normal fast startup must remain unchanged.
- **Trace:**

  > The issue timestamps show token acquisition completing around 10:05, followed by no Chat contribution activity until `[BaseExperimentationService] Initial fetch completed` at 10:18:48. On current main, `baseActivate` in `extensions/copilot/src/extension/extension/vscode/extension.ts` awaits `IExperimentationService.hasTreatments()` before constructing contributions; `BaseExperimentationService.hasTreatments()` in `extensions/copilot/src/platform/telemetry/node/baseExperimentationService.ts` waits for the delegate's `initialFetch`. TAS transport now runs through `createTasFetch` in `extensions/copilot/src/platform/telemetry/vscode-node/tasFetch.ts`, including proxy handling from https://github.com/microsoft/vscode/commit/8bed8782864c64dbd3e42219b79672b0acff1009, but the activation wait itself remains unbounded at the extension layer. Keep model fetching, authentication semantics, and successful experiment refresh behavior in scope; do not broaden this into general remote indexing or Chat request-performance work.
- **Open decisions:**
  - When the initial experimentation fetch is still pending, should Chat activate immediately from cached/default treatments, or wait only for a maintainer-defined deadline before proceeding?
