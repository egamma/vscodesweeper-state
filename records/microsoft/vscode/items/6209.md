# Issue #6209 — isWatching/background task as preLaunchTask in launch.json

[https://github.com/microsoft/vscode/issues/6209](https://github.com/microsoft/vscode/issues/6209)

## Summary

Keep open: background preLaunchTasks already work with watching problem matchers, but the maintainer explicitly retained this issue for readiness monitoring without an artificial diagnostic pattern. Current source still requires that coupling; the related modernization request is newer and cannot replace this re-reviewed item.

## Change summary

Allow long-running preLaunchTasks to signal readiness through output patterns without requiring a diagnostic problem matcher.

## Best solution

Provide supported readiness-only monitoring in the task configuration, preserving existing problem matchers and debugger waiting semantics. Settle the extension Task API implications with the tasks owner and coordinate the overlapping modernization work.

Manually configure a long-running shell preLaunchTask that emits an initial busy line followed by 'webpack: bundle is now VALID.': F5 must wait for readiness, launch debugging while the task remains running, and reuse the ready task on subsequent launches. Existing watching problem matchers must retain their behavior.
- **Behavior:**

  > A long-running server task used as preLaunchTask can declare output-based readiness without a dummy diagnostic pattern or an unrelated inherited problem matcher. Debugging waits until the configured readiness output appears rather than requiring process termination. Once ready, the task continues running, and subsequent debug launches reuse it when appropriate. Existing diagnostic matching and background-task configurations remain compatible; automatic task termination after debugging is outside this request.
- **Trace:**

  > The retained scope is explicit in https://github.com/microsoft/vscode/issues/6209#issuecomment-350994475: background preLaunchTasks already work, but readiness regexes should not require artificial problem matching. The task schema in src/vs/workbench/contrib/tasks/common/jsonSchema_v2.ts lacks task-level background monitoring, and ProblemMatcherParser in src/vs/workbench/contrib/tasks/common/problemMatcher.ts requires a diagnostic pattern before adding watching configuration. WatchingProblemCollector in src/vs/workbench/contrib/tasks/common/problemCollectors.ts obtains readiness patterns only from problem matchers. DebugTaskRunner.runTask in src/vs/workbench/contrib/debug/browser/debugTaskRunner.ts already waits for inactivity and reuses ready running tasks, so preserve those semantics rather than bypassing readiness. The public Task surface in src/vscode-dts/vscode.d.ts exposes isBackground and named problemMatchers but no independent monitor, and the maintainer explicitly flagged API consequences. Coordinate with https://github.com/microsoft/vscode/issues/141102 without treating that newer issue as a duplicate canonical; optional beginsPattern behavior requested there is not automatically part of this issue.
- **Open decisions:**
  - Should independent readiness monitoring also be available to extension-provided vscode.Task objects, and what public configuration/API contract should represent it?
