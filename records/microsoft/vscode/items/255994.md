# Issue #255994 — `New Window with Profile` > `New Profile...` shows broken Profiles editor

[https://github.com/microsoft/vscode/issues/255994](https://github.com/microsoft/vscode/issues/255994)

## Summary

The broken first-open layout remains plausible on current main: the Profiles editor starts asynchronous tree population without awaiting it, then immediately sizes the tree from its initially empty content. No fixing commit or older canonical issue was found, so this accepted Backlog bug should remain open.

## Change summary

Opening New Profile from New Window with Profile after reloading with no editors leaves the profile configuration form blank while its title and action buttons remain visible.

## Best solution

Make the Profiles editor reliably display and size the complete new-profile form when it is the first editor opened after reload, while preserving the existing behavior when the editor was already initialized.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditor.ts`
- **Validation:** Launch VS Code with all editors closed, reload the workbench, run File > New Window with Profile > New Profile..., and verify that the complete profile configuration form is visible and usable on the first open; repeat after closing and reopening the Profiles editor.
- **Behavior:**

  > After reloading a workbench with no open editors, invoking File > New Window with Profile > New Profile... must show the complete new-profile form, not only its title and action buttons. The name, icon, source/content choices, and other applicable fields must be visible and usable on the first open. Reopening the editor and switching among existing and unsaved profiles must continue to render their forms correctly.
- **Trace:**

  > The command in src/vs/workbench/contrib/userDataProfile/browser/userDataProfile.ts awaits openProfilesEditor() and then invokes createNewProfile(). Selection of the new model element reaches ProfileWidget.render() in src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditor.ts. That method starts WorkbenchAsyncDataTree.setInput(), which returns a promise, but immediately continues; ProfileWidget.layout() can therefore read contentHeight before the asynchronous children have populated and collapse the tree to zero height. The issue screenshot at https://github.com/microsoft/vscode/issues/255994 matches that boundary: synchronous title and button content appears while the async tree is absent. Keep the scope to first-open initialization and layout; do not alter profile creation semantics or the separate decision about opening a new window tracked in https://github.com/microsoft/vscode/issues/244619.

## Evidence
