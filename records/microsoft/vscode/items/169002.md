# Issue #169002 — Editor triggers keyboard open on scroll on mobile

[https://github.com/microsoft/vscode/issues/169002](https://github.com/microsoft/vscode/issues/169002)

## Summary

Keep open: a maintainer confirmed the unwanted keyboard activation, and a newer Android report describes the same symptom. This older issue remains the appropriate tracking item; the browser-level trigger still needs diagnosis.

## Change summary

Scrolling an editor after dismissing the mobile virtual keyboard unexpectedly opens it again.

## Best solution

Ensure editor scrolling does not reactivate the virtual keyboard while preserving deliberate tap-to-edit behavior. Diagnose the touch gesture and input-focus interaction on Android before changing shared gesture handling.

## Plan brief

- **Likely files:** `src/vs/base/browser/touch.ts`, `src/vs/editor/browser/controller/pointerHandler.ts`, `src/vs/editor/browser/controller/mouseHandler.ts`
- **Validation:** On Android Chrome using a development web build, open a long editable file, tap to show the virtual keyboard, dismiss it with Back, then perform short drags, long drags, and repeated flings. Scrolling must continue without reopening the keyboard; a deliberate tap must still focus editing and show the keyboard. Capture native touch/pointer events, generated gesture events, and input focus changes to distinguish the failing path.
- **Behavior:**

  > After a user dismisses the virtual keyboard, scrolling an editable file must not reopen it. The report includes an independent maintainer confirmation and a newer Android Chrome report with the same steps. Acceptance requires checking short and long touch scrolling and repeated flings on Android, while preserving intentional tap-to-edit behavior and normal scrolling.
- **Trace:**

  > PointerHandler in src/vs/editor/browser/controller/pointerHandler.ts selects PointerEventHandler for mobile Android with pointer-event support, otherwise TouchHandler when TouchEvent exists. Both gesture Change handlers scroll without explicitly focusing the input, while their Tap handlers call focusTextArea; the pointer handler ignores touch pointer-down, but the fallback inherits the content-focus path in MouseHandler._onMouseDown. Gesture.onTouchEnd in src/vs/base/browser/touch.ts uses a 700 ms hold threshold and 30-pixel displacement checks, then prevents the native default after dispatch. An external patch attributes the symptom to touchend cancellation at https://github.com/coder/code-server/issues/1887#issuecomment-1822041214, but this hypothesis has not been verified against the current browser event sequence. Begin by observing which handler and event actually reactivate input; do not assume the external patch is sufficient or change shared tap, selection, context-menu, or inertia semantics without checking their consumers. The newer same-symptom report is https://github.com/microsoft/vscode/issues/288955.
