# Issue #169002 — Editor triggers keyboard open on scroll on mobile

[https://github.com/microsoft/vscode/issues/169002](https://github.com/microsoft/vscode/issues/169002)

## Summary

The defect path remains on current main: a small touch movement can scroll the editor and then be classified as a tap, which focuses the editor input and opens the mobile keyboard. This older, confirmed report should remain the canonical issue rather than being folded into the narrower physical-trackpad report.

## Change summary

Scrolling the editor by touch on Android can focus the editor and open the virtual keyboard.

## Best solution

Ensure a gesture that scrolls the editor cannot subsequently activate the editor input, while preserving focus and cursor placement for genuine taps. A maintainer should first choose whether that distinction belongs in the shared gesture recognizer or only in the editor pointer handler.

## Plan brief

- **Likely files:** `src/vs/base/browser/touch.ts`, `src/vs/editor/browser/controller/pointerHandler.ts`
- **Validation:** Exercise synthetic touchstart/touchmove/touchend sequences in a browser test and verify that a movement which changes editor scroll position does not focus the editor input, while a stationary tap still does; confirm the same behavior on vscode.dev in Android Chrome.
- **Behavior:**

  > Dragging to scroll editor content on a mobile touch device must not focus the editor or open the virtual keyboard when the gesture ends. A genuine tap must continue to place the cursor, focus the editor input, and allow typing. Acceptance should cover a short movement below the current displacement threshold as well as an ordinary tap.
- **Trace:**

  > Gesture.onTouchMove in src/vs/base/browser/touch.ts emits EventType.Change, which PointerEventHandler.onChange in src/vs/editor/browser/controller/pointerHandler.ts converts into editor scrolling. Gesture.onTouchEnd independently emits EventType.Tap when the gesture is shorter than 700 ms and its final displacement is below 30 pixels; PointerEventHandler.onTap then calls focusTextArea(). This establishes a current path where one gesture scrolls and subsequently focuses the input. The uncertainty starts at ownership: changing Gesture affects every registered touch target, while tracking the distinction in PointerEventHandler limits behavior to the editor. Preserve genuine tap-to-focus behavior, selection gestures, pen handling, and non-editor touch consumers. Related narrower report: https://github.com/microsoft/vscode/issues/255975.
- **Open decisions:**
  - Should a touchmove categorically cancel tap classification in the shared Gesture recognizer, or should the editor alone suppress focus after it has consumed movement as scrolling?
  - What movement threshold should distinguish incidental finger jitter from an intentional scroll without degrading tap-to-position behavior?
  - Should the physical-trackpad behavior in https://github.com/microsoft/vscode/issues/255975 be covered by the same change or remain separately scoped?

## Evidence

- **current source path:** src/vs/base/browser/touch.ts dispatches EventType.Change for every touchmove, but on touchend still dispatches EventType.Tap when elapsed time is under 700 ms and final displacement is under 30 pixels; it does not record that scrolling already occurred.
- **keyboard focus:** src/vs/editor/browser/controller/pointerHandler.ts handles EventType.Change by scrolling and handles EventType.Tap by calling viewHelper.focusTextArea(), so the same short gesture can both scroll and focus the mobile input.
- **confirmed platforms:** A VS Code team member confirmed the behavior on vscode.dev using Android and a Surface with Edge: https://github.com/microsoft/vscode/issues/169002#issuecomment-1348655761
- **later related report:** https://github.com/microsoft/vscode/issues/255975 remains open and reports a narrower Android physical-trackpad scrolling problem while linking this issue because scrolling also focuses the keyboard; it does not supersede the broader touch-scroll report.
- **no fixing change found:** History after the report retains the gesture classification and tap-to-focus behavior. Commit 57c5c8801d7dc8f41af17c16ac07efd077abfbcc only restricts PointerEventHandler to phones and does not prevent a scroll gesture from later being treated as a tap.
