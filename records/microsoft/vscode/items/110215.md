# Issue #110215 — Make it possible to disable editors following the highlighted entry in the problems list

[https://github.com/microsoft/vscode/issues/110215](https://github.com/microsoft/vscode/issues/110215)

## Summary

Keep open: current main still opens an editor when keyboard selection changes in the Problems view, and maintainers support addressing the accessibility problem through a shared consumer-level solution. The only implementation PR was closed without merging after discussion rejected its Problems-only filtering approach.

## Change summary

Allow keyboard users to review Problems entries with the arrow keys without moving editor focus or opening files until they explicitly activate an entry.

## Best solution

Define a shared, content-agnostic consumer abstraction for list-based views that can separate keyboard navigation from explicit activation, then use it in Problems and evaluate the equivalent Search and Comments behavior. Preserve current behavior by default and keep Enter and pointer activation opening the selected location.

- **Behavior:**

  > Users who opt out of follow-on-navigation can move through Problems entries with the arrow keys without changing the active editor, cursor location, or editor focus. Pressing Enter or activating an entry with the pointer still opens its location. Existing behavior remains the default. The chosen public control must have clearly defined scope across other list-based views with the same interaction.
- **Trace:**

  > ResourceNavigator in src/vs/platform/list/browser/listService.ts converts every keyboard selection change into onDidOpen; MarkersView in src/vs/workbench/contrib/markers/browser/markersView.ts then calls openFileAtElement. SearchView and CommentsView consume the same open event for comparable reveal behavior. https://github.com/microsoft/vscode/pull/282677 filtered events only inside MarkersView and added a Problems-specific setting, but it was closed without merging. Maintainer discussion requires the base tree to remain content-agnostic and favors a shared abstraction among consumers; do not couple tree nodes to Problems content or change explicit Enter, pointer, multi-selection, or side-by-side activation semantics.
- **Open decisions:**
  - Should the public opt-out be one shared setting governing Problems, Search, Comments, and other participating views, or separate per-view settings backed by the same shared activation abstraction?
