# Issue #242003 — Extensions cannot contribute to scm/resourceState/context if the SCM provider is in another extension host

[https://github.com/microsoft/vscode/issues/242003](https://github.com/microsoft/vscode/issues/242003)

## Summary

The cross-host SCM command-argument gap remains in current source. Keep this accepted Backlog request open under scm; the related menu proposals do not cover the reported behavior.

## Change summary

Allow SCM resource context-menu commands to receive usable resource information when the command and SCM provider run in different extension hosts.

## Best solution

Define a supported cross-host resource argument containing at least the resource URI, while preserving existing same-host provider-object behavior. The SCM API owners should settle that contract before implementation.

Extensions can contribute menu items already; the missing capability is usable cross-host command arguments, not menu registration.
- **Current serialization:** MainThreadSCMResource.toJSON in src/vs/workbench/api/browser/mainThreadSCM.ts:165-172 serializes only $mid, sourceControlHandle, groupHandle, and handle. Although the resource holds sourceUri, that URI is not included in the serialized argument.
- **Host-local resolution:** The argument processor in src/vs/workbench/api/common/extHostSCM.ts:992-1007 resolves SCM resource handles through that host's _sourceControls map. If the receiving host has no matching provider, it returns the raw argument rather than constructing a SourceControlResourceState or providing a URI. This directly supports the reporter's described limitation.
