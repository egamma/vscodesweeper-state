# Issue #265496 — Add support in vscode for Agent Client Protocol (ACP)

[https://github.com/microsoft/vscode/issues/265496](https://github.com/microsoft/vscode/issues/265496)

## Summary

This remains a well-supported request for first-party ACP interoperability: community extensions demonstrate feasibility, but they do not satisfy the requested built-in, complete integration. No older canonical with the same request or merged implementation is identified, so the existing under-discussion issue should remain open.

## Change summary

Add first-party Agent Client Protocol support so third-party agent CLIs can participate consistently in VS Code's chat and agent workflows.

## Best solution

Define first-party ACP client support in the core chat/agent-host architecture, including the protocol-to-VS Code capability mapping and any stable extension API needed for features that community extensions currently reach through proposed APIs.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost`, `src/vs/workbench/contrib/chat`, `extensions/copilot`
- **Validation:** Exercise an ACP-compatible agent through a VS Code agent session and verify session creation, prompt/response streaming, tool calls and approvals, file edits, cancellation, and session restoration without provider-specific UI behavior.
- **Behavior:**

  > VS Code can connect to an ACP-compatible agent and expose it through the native agent/chat experience without requiring a provider-specific workflow. Core ACP interactions—including session startup, streamed responses, tool calls and approvals, file changes, cancellation, errors, and restoration—behave consistently with native agent sessions. Existing Copilot and directly integrated CLI-agent experiences remain unchanged.
- **Trace:**

  > The issue asks for first-party ACP client support rather than merely a third-party extension. Community implementations demonstrate protocol feasibility, but comments report that complete integration currently depends on experimental/proposed chat session APIs and that the stable chat participant surface does not expose every required behavior. The likely boundary spans Agent Host protocol/lifecycle infrastructure under src/vs/platform/agentHost, chat session presentation under src/vs/workbench/contrib/chat, and provider integration under extensions/copilot. Existing provider-specific integrations and their richer capabilities must not regress or be forced down to ACP's least-common-denominator feature set. The supplied related VS Code issues do not own this same observable request, and no merged first-party implementation is identified.
- **Open decisions:**
  - Should ACP agents be a first-party Agent Host provider managed by VS Code, or should core expose a stable extension API that lets ACP client extensions create fully native agent sessions?
  - Which ACP capabilities are required for the initial supported contract, and how should VS Code present an agent whose ACP implementation omits optional capabilities?
  - Should ACP agents appear alongside built-in providers in the native agent picker, or remain extension-contributed entries with distinct trust and enablement UX?
