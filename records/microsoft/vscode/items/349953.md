# Issue #349953 — Agents window: send_remote_message stops for good after 50 sends per window lifetime; only a window reload resets it

[https://github.com/microsoft/vscode/issues/349953](https://github.com/microsoft/vscode/issues/349953)

## Summary

Keep open as the operation-budget redesign explicitly deferred by the original feature. The permanent 50-request ceiling remains on main and is deliberately tested, so changing its recovery semantics is a feature decision rather than repairing an accidental regression.

## Change summary

Allow legitimate long-running remote messaging to continue beyond 50 lifetime requests without reloading the Agents window, while retaining runaway-loop protection.

## Best solution

Define a recoverable remote-message budget and retry-retention contract, then implement it in the Sessions-owned router. Preserve exact-chat routing, approvals, trust checks, and protection against duplicate or uncertain delivery.

- **Behavior:**

  > Remote messaging currently stops permanently after 50 distinct requests across an Agents window, even when successful messages were spread over hours. Legitimate coordination should be able to resume without a window reload under an explicitly defined budget contract, while runaway traffic remains bounded. Acceptance must demonstrate the chosen exhaustion and recovery behavior, its scope across source chats, and unchanged duplicate-delivery protection.
- **Trace:**

  > RemoteSessionMessageRouter.send in src/vs/sessions/contrib/remoteSessions/browser/remoteSessionMessageRouter.ts uses requests both as an idempotency cache keyed by source chat and request ID and as a lifetime admission counter. Entries retain their promises after success or failure; no expiry or reset exists. SendRemoteMessageTool and RemoteSessionToolsContribution keep that router alive across calling chats. The existing router test explicitly requires rejection after 50 completed sends, so the intended replacement contract is not established by neighboring behavior. https://github.com/microsoft/vscode/issues/336682 explicitly defers budget redesign. Keep exact-chat identity, approval and workspace-trust enforcement, FIFO dispatch, and uncertain-delivery safeguards unchanged; the unresolved boundary is which operations consume budget and when budget and retry records may expire independently.
- **Open decisions:**
  - What observable exhaustion and recovery contract should replace the lifetime ceiling: time-based replenishment, an explicit reset, or another bounded mechanism, and with what limits?
  - Should admission be shared across the window or scoped per source chat, and which definitively undelivered failures should consume budget?
  - How long must identical tool-call retries return the original result, and what should happen when a retry arrives after its retained result expires?
