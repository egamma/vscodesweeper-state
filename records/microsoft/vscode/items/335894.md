# Issue #335894 — Sessions list can show stale In Progress status when input is needed

[https://github.com/microsoft/vscode/issues/335894](https://github.com/microsoft/vscode/issues/335894)

## Summary

Confirmed on current main: after the detailed session-state subscription expires, the list can retain a stale main-chat status even while lightweight session updates carry the current aggregate status. This team-authored bug should remain open; the older related issue reports different frozen-state symptoms and does not meet the re-review duplicate bar.

## Change summary

Keep the Sessions list's main-chat status current when a multi-chat Agent Host session begins waiting for input after its full-state subscription expires.

## Best solution

Preserve the intentional distinction between main-chat and aggregate session status while ensuring the status inputs consumed by visible list rows remain current across subscription expiry. Settle whether that requires a lightweight per-chat status contract or a different subscription lifetime, then add focused coverage for the Input Needed transition and peer-chat promotion boundary.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/sessions/contrib/providers/agentHost/test/browser/localAgentHostSessionsProvider.test.ts`, `src/vs/platform/agentHost/common/state/protocol/channels-session/state.ts`
- **Validation:** ./scripts/test.sh --grep "main chat status after the session-state subscription expires"; the focused provider regression must show an InProgress-to-InputNeeded main-chat transition after advancing beyond the 30-second lease, without opening the session, while a peer-only InputNeeded state does not incorrectly become the parent row's main-chat state.
- **Behavior:**

  > For a multi-chat Agent Host session, when the main chat changes from In Progress to Input Needed after the detailed session-state subscription has expired, the Sessions list must update immediately without opening the session. A peer chat requiring input must retain its own row/status semantics and must not be mistaken for the main chat merely because aggregate session status is promoted. The behavior must remain correct after the 30-second lease boundary and when the session later becomes visible again.
- **Trace:**

  > The parent-row status is derived by getSessionRowStatus in src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts from session.mainChat.status. AgentHostSessionAdapter in src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts derives that status from _defaultChatStatusOverride for multi-chat sessions; _applyChatCatalog refreshes the override from detailed SessionState.chats. BaseAgentHostSessionsProvider releases that subscription after SESSION_STATE_SUBSCRIPTION_IDLE_MS, while _handleSessionSummaryChanged updates only aggregate cached.status and lightweight chat metadata. The existing provider test proves the override remains stale after 31 seconds and currently recovers only because ChatTurnComplete explicitly reacquires state. SessionChatSummary intentionally omits volatile status, so the uncertainty begins at the boundary between lightweight summary design and subscription retention; do not collapse main-chat status into aggregate status because peer activity can promote the aggregate independently.
- **Open decisions:**
  - Should lightweight SessionChatSummary expose enough per-chat status to keep list presentation current, changing the public AHP summary contract, or should VS Code retain/reacquire the detailed SessionState subscription for sessions whose list rows consume main-chat status?

## Evidence

- **confirmed source path:** On current main, getSessionRowStatus in src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts reads session.mainChat.status for the parent row, while AgentHostSessionAdapter in src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts stores multi-chat default status in _defaultChatStatusOverride and refreshes it only from a full SessionState chat catalog.
- **lease expiry:** BaseAgentHostSessionsProvider.SESSION_STATE_SUBSCRIPTION_IDLE_MS is 30 seconds, and _keepSessionStateAlive disposes the detailed session-state subscription when the lease expires. _handleSessionSummaryChanged updates cached.status but cannot update _defaultChatStatusOverride from aggregate status without confusing peer-chat Input Needed with main-chat Input Needed.
- **existing regression proof:** src/vs/sessions/contrib/providers/agentHost/test/browser/localAgentHostSessionsProvider.test.ts contains 'turn completion refreshes main chat status after the session-state subscription expires'; after advancing 31 seconds it explicitly observes staleStatus === SessionStatus.InProgress. Recovery currently depends on a later ChatTurnComplete action reopening the subscription, which does not cover an ask_user/Input Needed transition.
- **protocol boundary:** SessionSummary.chats uses SessionChatSummary in src/vs/platform/agentHost/common/state/protocol/channels-session/state.ts, whose documented contract intentionally omits volatile status. The detailed ChatSummary in src/vs/platform/agentHost/common/state/protocol/channels-chat/state.ts does carry status, so exposing it through lightweight summaries would be an AHP contract decision rather than a local field copy.
- **related issue:** https://github.com/microsoft/vscode/issues/327639 is older and open, but reports a broader nondeterministic stream freeze involving opposite status errors, inert rename/read actions, and missing permissions. It does not report this same lease-expiry-driven In Progress-to-Input Needed symptom, so it is not a valid canonical for this re-reviewed item.
