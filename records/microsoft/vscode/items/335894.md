# Issue #335894 — Sessions list can show stale In Progress status when input is needed

[https://github.com/microsoft/vscode/issues/335894](https://github.com/microsoft/vscode/issues/335894)

## Summary

Team-authored (roblourens), source-verified bug in the Agents Window sessions list: confirmed on current main via the exact 30s idle-release window and the default-chat status override cache described in the report. No fix has landed yet; the report itself flags two viable fix strategies, so this needs a maintainer design call before implementation.

## Change summary

After a session's full session-state subscription idles out (30s), the Sessions list keeps showing 'In Progress' for a multi-chat session even after the main chat asks for input, until the row is opened.

## Best solution

Design how the lightweight session summary (or its deltas) can carry enough default-chat/active-chat status to keep the list row correct without the full session-state subscription, or otherwise change the subscription-release strategy so visible list rows stay fed — a maintainer should pick the direction in src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts before an agent implements it.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts`, `src/vs/sessions/contrib/providers/agentHost/test/browser/localAgentHostSessionsProvider.test.ts`
- **Validation:** Extend/adapt the existing provider test at localAgentHostSessionsProvider.test.ts:6573 (which already reproduces the stale-cache behavior after the 30s subscription release) to assert the default-chat status reflects InputNeeded once `root/sessionSummaryChanged` reports it, without requiring the session to be reopened.
- **Behavior:**

  > When a multi-chat Agent Host session's full session-state subscription has idled out (30s) and the main chat then requests input, the Sessions list row must switch to 'Input Needed' as soon as the host reports it via `root/sessionSummaryChanged`/`listSessions`, without requiring the user to open the session first. Acceptance: the adapted provider test simulating this sequence (idle timeout, then InputNeeded summary) shows the default-chat/main-chat status updating without a session open, and existing sessions-list/provider tests still pass.
- **Trace:**

  > `BaseAgentHostSessionsProvider` populates `_defaultChatStatusOverride` (around line 1031) only from the full session-state chat catalog; `defaultChatStatus` (around line 1320) reads that override when set, else falls back to the aggregate `this.status`. The idle-release timer (`SESSION_STATE_SUBSCRIPTION_IDLE_MS = 30_000`, line ~5797) tears down the full subscription for non-visible sessions via `_keepSessionStateAlive`'s idle timers, after which `root/sessionSummaryChanged` keeps the aggregate status current but never refreshes the cached override — `sessionsList.ts` (around line 224-234) reads that stale `mainChat.status` for the parent row. Do not simply copy the aggregate status into the override on every summary change: a peer chat can push the aggregate to InputNeeded while the main chat itself is not, which the report explicitly warns is 'not generally correct'. Related PRs that introduced this parent-row behavior: https://github.com/microsoft/vscode/pull/332931 and https://github.com/microsoft/vscode/pull/333999.
- **Open decisions:**
  - Should the lightweight session summary/delta protocol be extended to carry default-chat/active-chat status so list rows stay accurate without a full subscription, or should the subscription-release strategy change so visible-list status inputs stay live?
  - If summary/delta protocol changes are chosen, is that a client-only change or does it require an Agent Host protocol change coordinated with the host implementation?
