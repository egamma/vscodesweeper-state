# Issue #333268 — Automations: guard deletion against concurrent definition changes

[https://github.com/microsoft/vscode/issues/333268](https://github.com/microsoft/vscode/issues/333268)

## Summary

Keep open: current source still deletes by ID after confirmation without comparing the reviewed definition, and concurrent removal can produce a provider lookup error. The issue is correctly routed to automations and remains necessary.

## Change summary

Protect automation deletion against concurrent definition changes and distinguish successful deletion, changed definitions, and already-deleted definitions.

## Best solution

Provide authoritative guarded deletion with explicit outcomes, consumed consistently by confirmation flows and provider routing. Establish how that contract works across current Agent Host and cloud providers without mistaking a client-side preflight comparison for atomic protection.

- **Behavior:**

  > A deletion confirmation applies only to the editable automation definition reviewed when confirmation began. If that definition changes before authoritative deletion, preserve the newer definition and its history and clearly report the conflict; if it has already disappeared, clearly report that outcome without a generic provider error. An unchanged definition remains deletable, and runtime-only progress must not create a false conflict. Both card deletion entry points must behave consistently, with provider guarantees explicitly defined.
- **Trace:**

  > confirmAndDeleteAutomation in src/vs/sessions/contrib/sessions/browser/views/automationsView.ts retains a descriptor across the confirmation await but passes only its ID to deletion. ProviderAutomationService.deleteAutomation requires a currently discoverable definition, so concurrent removal fails before reaching storage. AgentHostAutomationStore dispatches resource-only AutomationRemoved, while AgentHostAutomationService.handleRemove serializes mutations and _handleRemove treats an absent resource as a no-op without comparing reviewed state. ReconnectableAgentHostAutomationStore forwards the same ID-only contract, and CloudAutomationStore also has no expected-definition deletion input. The architecture now places local/remote persistence in the host and describes cloud REST as lacking atomic compare-and-swap; the remaining uncertainty is the supported guarantee across providers and version-skewed conforming hosts, not whether the UI race exists. Preserve provider identity, advertised resource URIs, capability checks, active-run removal restrictions, and the distinction between runtime and editable state. https://github.com/microsoft/vscode/pull/333226 is the originating context-menu change, not a completed guarded-deletion fix.
- **Open decisions:**
