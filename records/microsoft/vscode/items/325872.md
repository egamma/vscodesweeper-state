## Summary

Keep open: the report provides sufficient update steps and installation evidence to retest the extension-host crashes, but its incremental-copy diagnosis conflicts with the CLI's existing atomic rename. Main now isolates and serializes staging downloads; that addresses a plausible race, not a verified cause of this report.

## Change summary

A remote server update left required node_modules missing from the live installation, causing extension-host crashes and repeated reconnections.

## Best solution

Establish how the complete staging installation became an incomplete live installation, then ensure the CLI installation and recovery paths cannot repeatedly reuse that broken server. Keep this in the core CLI/server area rather than treating Remote-SSH's involvement as proof of extension ownership.

## Plan brief

- **Likely files:** `cli/src/download_cache.rs`, `cli/src/tunnels/code_server.rs`, `cli/src/tunnels/control_server.rs`
- **Validation:** On a disposable Linux remote, exercise a client-triggered server update and extension-host startup while recording staging/live contents and CLI logs. Establish a failing case that leaves required modules missing and repeats reconnections; acceptance is a complete usable installation or explicit failure with successful recovery on a subsequent connection. Include concurrent same-version installation attempts when testing the staging-race hypothesis.
- **Behavior:**

  > The reporter updated the client, connected through Remote-SSH, and received a server installation missing required modules despite a complete staging copy. The extension host exited immediately and the window repeatedly reconnected until the installation was manually restored. A completed update must support extension-host startup; a broken installation must not be repeatedly accepted as usable. Validate this on a disposable remote without changing or deleting user extensions or workspace data.
- **Trace:**

  > ServerBuilder::setup in cli/src/tunnels/code_server.rs downloads and extracts through DownloadCache::create, then checks the staged entrypoint with --version unless requirements checking is skipped. Both the reported version and current source finalize with std::fs::rename, so incremental copying is not an established cause. Current DownloadCache::create accepts existing target directories without rerunning setup validation. Commit https://github.com/microsoft/vscode/commit/94db63f469854cdab2f2805612f4ff99f15bd3a7 adds isolated staging and download locking, but whether that race produced this report remains unknown. handle_serve in cli/src/tunnels/control_server.rs evicts on a server-launch ServerUnexpectedExit, which is distinct from a later extension-host crash. https://github.com/microsoft/vscode/issues/338114 provides a separate cache-eviction/NFS lead, not proof of the same cause here. First establish the installation failure and recovery sequence; preserve intentional permission-error handling and keep automatic version rollback outside the initial diagnosis.
