## Summary

This is the same Node.js system-certificate crash on macOS as #277064 — the A/B experiment on `http.systemCertificatesNode` re-enabled the broken code path for this user, triggering the known `ReadMacOSKeychainCertificates` crash. The root cause and workaround are identical.

## Change summary

Extension host crashes with exit code 6 on macOS 26.4 when Node.js attempts to read system certificates from the macOS Keychain.

## Best solution

Consolidate on https://github.com/microsoft/vscode/issues/277064 — both report the same `ReadMacOSKeychainCertificates` crash, same workaround (`systemCertificatesNode: false`), same root cause (Node.js/OpenSSL x509 name parsing crash on macOS). The remaining work — either fixing the Node.js upstream crash or removing the A/B experiment that re-enables the broken path — belongs in one place.

## Evidence

- **same root cause:** https://github.com/microsoft/vscode/issues/277064 identified the crash in Node.js `ReadMacOSKeychainCertificates` (crypto_context.cc:527) when `http.systemCertificatesNode` is enabled — identical to this report's symptom and workaround.
- **A/B experiment re-enables setting:** In src/vs/platform/request/common/request.ts lines 326-328, `http.systemCertificatesNode` carries `experiment: { mode: 'auto' }`, allowing the A/B system to override the default `false` to `true` for some users — explaining why this user hit the crash despite the default being off since commit 16cd8a75cc7 (Nov 2025).
- **default disabled:** Commit 16cd8a75cc73a5dc0042a37ace05b217ec225171 (2025-11-18) set `systemCertificatesNodeDefault = false`, and chrmarti confirmed on #277064 that the setting was also turned off via A/B — but the experiment mechanism still exists and can re-enable it.
- **identical workaround:** Both this issue and #277064 are resolved by setting `"http.systemCertificatesNode": false`.
