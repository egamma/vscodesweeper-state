# Issue #177452 — Please give extensions access to native AST tokens (At least partially)

[https://github.com/microsoft/vscode/issues/177452](https://github.com/microsoft/vscode/issues/177452)

## Summary

Keep this accepted, well-supported API request open: current proposed APIs do not provide the requested structural information. The older bracket-position request covers only part of its scope, so it is not a canonical duplicate.

## Change summary

Expose native structural information to extensions, starting with bracket positions outside comments and strings and potentially extending to string delimiters, tags, and indentation-based blocks.

## Best solution

Design a bounded, tokenizer-independent extension API for structural queries, with explicit document-version, availability, and performance semantics. Separate the existing bracket-pair capability from language-specific structural information that VS Code cannot universally derive from TextMate tokens.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.tokenInformation.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostLanguages.ts`, `src/vs/workbench/api/browser/mainThreadLanguages.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/editor/common/model/bracketPairsTextModelPart/bracketPairsImpl.ts`
- **Validation:** The plan should end with an extension-host integration check querying nested brackets, brackets inside comments and strings, and a pair enclosing the viewport whose endpoints are outside it. Exercise edits during an asynchronous query and a large or incompletely tokenized document, asserting the chosen version/availability contract and measuring renderer responsiveness. If indentation structure is included, validate the reporter's Python multiline-dictionary example. No executable checks were run in this read-only review.
- **Behavior:**

  > Extensions should be able to obtain native structural information without bundling a second parser for the same basic editor capability. The minimum requested behavior is identifying bracket positions while excluding brackets inside comments and strings. Broader requested information includes string delimiters, markup tags, and Python/YAML indentation boundaries. Acceptance must cover nested structures, edits during queries, unsupported or incompletely tokenized documents, and large-document performance under an explicitly agreed public contract.
- **Trace:**

  > BracketPairsTextModelPart in src/vs/editor/common/model/bracketPairsTextModelPart/bracketPairsImpl.ts already maintains native bracket information and supports range-intersection queries. The extension language bridge in mainThreadLanguages.ts and extHostLanguages.ts instead exposes a proposed point-token query; its extension-host side checks document versions, and the separate full-syntax-highlighting proposal returns presentation runs only. TextMate tokenization is not a universal language AST and does not itself provide reliable indentation-block boundaries. The older open https://github.com/microsoft/vscode/issues/131062 supplies relevant bounded-query and synchronization discussion but covers only the bracket subset. Preserve existing native tokenization, bracket rendering, and editor responsiveness; a full parser for every language is not an established prerequisite. The uncertainty starts at the extension-facing scope and consistency guarantees, not at whether the internal bracket query exists.
- **Open decisions:**
  - Should the initial public contract expose only native bracket pairs, or also structural information for strings, tags, and indentation-based languages?
  - Should queries return version-tagged snapshots that callers may reject, or guarantee correspondence with a specific requested document version?
  - What should extensions observe when structural information is unavailable, incomplete, or limited for performance: no result, an explicitly partial result, or deferred completion?

The verified open https://github.com/microsoft/vscode/issues/99356 documents renderer overload from repeated point-token requests; current ExtHostLanguages.tokenAtPosition also rejects results when the document version changes.
