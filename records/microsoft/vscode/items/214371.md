# Issue #214371 — VSCode forces file type associations on macos

[https://github.com/microsoft/vscode/issues/214371](https://github.com/microsoft/vscode/issues/214371)

## Summary

Keep open: macOS packaging still declares supported document types unconditionally, and no existing control was found that makes this registration opt-in. The reports of overriding an explicit default application warrant investigation, but neither a current fix nor an older open canonical was established.

## Change summary

Allow macOS users to decline VS Code file-type registration without editing and re-signing the application bundle.

## Best solution

Establish supported macOS behavior that preserves explicit default-application choices and addresses unwanted automatic associations without modifying the signed bundle. First distinguish Launch Services selecting a registered handler from an actual override of a user-selected default, then decide whether optional registration is needed.

## Plan brief

- **Likely files:** `build/lib/electron.ts`, `build/gulpfile.vscode.ts`
- **Validation:** On an isolated macOS account, record default handlers for representative supported extensions before installation, after installing VS Code, after selecting another application through Finder Get Info > Open With > Change All, and after launching and updating VS Code. Verify explicit choices survive; any approved opt-out must also survive updates without editing or re-signing the bundle.
- **Behavior:**

  > Installing VS Code should not unexpectedly replace a user's explicitly chosen application for supported file types. The report additionally requests control over automatic file-type association, including types without an explicit default. Establish acceptance checks for installation, launch, reinstall, and update, with and without an existing user-selected handler. The supported outcome must not require modifying or re-signing the application bundle.
- **Trace:**

  > build/lib/electron.ts constructs a static darwinBundleDocumentTypes list through darwinBundleDocumentType and darwinBundleDocumentTypes, and build/gulpfile.vscode.ts passes that configuration into Electron packaging. Source inspection confirms unconditional document-handler declarations but does not prove that VS Code actively replaces user-selected defaults; that uncertainty starts at macOS Launch Services behavior. The internal files.associations and workbench.editorAssociations settings do not control operating-system handlers. https://github.com/microsoft/vscode/issues/51252#issuecomment-395330008 previously distinguished registration from default selection and reported unsuccessful reproduction. Preserve supported Open With discovery and ordinary file opening while investigating; do not treat wholesale removal of document declarations as an established solution.
- **Open decisions:**
  - Should macOS continue registering supported document types automatically while preserving explicit defaults, or should users be able to decline registration itself, including automatic selection for file types with no existing default?

## Evidence

- **Current packaging:** build/lib/electron.ts defines darwinBundleDocumentType and darwinBundleDocumentTypes with role 'Editor' and an unconditional config.darwinBundleDocumentTypes list covering many source-file extensions. build/gulpfile.vscode.ts:354 onward spreads this config into the Electron packaging configuration. This confirms registration remains present, not that macOS necessarily overrides explicit user defaults.
- **Existing-capability check:** The files.associations registration in src/vs/workbench/contrib/files/browser/files.contribution.ts maps filenames to editor languages; workbench.editorAssociations in src/vs/workbench/services/editor/common/editorResolverService.ts selects editors inside VS Code. Neither controls Finder or Launch Services associations. No macOS registration opt-out was found in the inspected packaging, native, startup, or preferences paths.
- **Discussion and workaround:** https://github.com/microsoft/vscode/issues/214371 includes a repeat occurrence after reinstalling in February 2025, an independent October 2025 report that an explicit Open With choice is overwritten after launching VS Code, and a November 2025 shortcut for removing CFBundleDocumentTypes. These support continuing investigation; modifying and re-signing the application is not a supported product control.
- **Earlier Windows resolution:** https://github.com/microsoft/vscode/issues/8687 is closed. Its resolution added the Windows installer checkbox 'Register Code as an editor for supported file types'; later comments report the macOS problem. That Windows change does not establish a fix for this request.
- **Earlier macOS investigation:** https://github.com/microsoft/vscode/issues/51252 is closed. In https://github.com/microsoft/vscode/issues/51252#issuecomment-395330008, a maintainer explained Info.plist registration, could not reproduce default-association overrides, and invited evidence of improvements. This establishes uncertainty about the mechanism, not a verified resolution of the later report.
- **Canonical and history limits:** Open-issue searches for macOS file associations, LSHandlerRank, default applications, and default editors did not establish an older open issue owning the same symptom. The checkout is shallow, so available git history cannot establish when a relevant behavior change landed; no fixing commit is claimed.
