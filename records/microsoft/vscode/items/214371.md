# Issue #214371 — VSCode forces file type associations on macos

[https://github.com/microsoft/vscode/issues/214371](https://github.com/microsoft/vscode/issues/214371)

## Summary

Keep open for the macOS installation owner: document-handler registration remains unconditional, and no supported opt-in control was found. The reported overwriting of existing defaults needs separate macOS verification; neither referenced closed issue establishes that this request is resolved.

## Change summary

Make macOS file-type registration opt-in without requiring users to modify and re-sign the application bundle.

## Best solution

Provide a supported way to control macOS document-handler registration that survives application updates, while preserving explicitly selected default applications. First distinguish automatic selection for previously unassociated types from the separately reported replacement of existing defaults.

## Evidence

- **Current packaging behavior:** build/lib/electron.ts defines DarwinDocumentType and both document-type helpers with role 'Editor', then unconditionally supplies config.darwinBundleDocumentTypes for many extensions, including h, js, py, and txt. No registration opt-in or handler-rank field appears in this configuration. build/gulpfile.vscode.ts imports that config for Electron packaging.
- **Existing-capability boundary:** The inspected packaging configuration provides no supported opt-out. Finder's association controls are not equivalent to disabling application registration, and the supplied discussion reports that an 'Always use this application' choice is overwritten. Source inspection alone cannot establish that Launch Services currently reproduces that overwrite.
- **Discussion and workaround:** At https://github.com/microsoft/vscode/issues/214371, the author reported recurrence after reinstalling in February 2025, another commenter reported replacement of an explicit association in October 2025, and a November 2025 comment supplied a shorter way to remove CFBundleDocumentTypes. These support continued demand, but editing and re-signing the bundle is not a supported product control.
- **Windows predecessor does not resolve macOS:** https://github.com/microsoft/vscode/issues/8687 is closed. Its maintainer investigation added a Windows installer checkbox, 'Register Code as an editor for supported file types': https://github.com/microsoft/vscode/issues/8687#issuecomment-234303525. Later comments explicitly report the remaining macOS problem.
- **macOS predecessor is not a canonical or fixing reference:** https://github.com/microsoft/vscode/issues/51252 is closed. At https://github.com/microsoft/vscode/issues/51252#issuecomment-395330008, the maintainer explained that Info.plist declares supported file types and could not reproduce default replacement, inviting evidence of improvements. That is not a landed opt-in capability or a verified current non-reproduction.
- **Canonical and history search:** Open-issue searches for macOS file associations, default-editor selection, LSHandlerRank, and CFBundleDocumentTypes found no verified older canonical owning this opt-in request. The supplied candidate titles concern unrelated capabilities. The checkout has only a shallow main snapshot, and the inspected recent remote history for build/lib/electron.ts supplied no concrete fixing commit.
