# Issue #114851 — VIM mode like sublime

[https://github.com/microsoft/vscode/issues/114851](https://github.com/microsoft/vscode/issues/114851)

## Summary

Keep this accepted, strongly supported request open: extension-host affinity addresses one latency concern, but does not deliver built-in Vim-style modal editing. The related platform issues cover narrower requirements, not the full request; a maintainer should settle the native-mode versus extension-platform direction.

## Change summary

Provide a reliable, responsive Vim-style modal editing experience comparable to Sublime's mode.

## Best solution

Define the supported modal-editing contract and decide whether to deliver it through a native mode or targeted platform capabilities for existing extensions. Prefer reusable platform improvements where they meet that contract without duplicating Vim implementations.

## Plan brief

- **Likely files:** `src/vs/editor/browser/coreCommands.ts`, `src/vs/editor/common/model/textModel.ts`, `src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts`, `src/vs/workbench/services/extensions/common/extensionRunningLocationTracker.ts`, `src/vscode-dts/vscode.proposed.findTextInFiles.d.ts`
- **Validation:** After agreeing on scope, define representative modal-editing checks for mode transitions, motions, operators, undo, and selection behavior. Compare typing responsiveness with a deliberately blocking completion-provider extension, with and without affinity isolation, and compare modal search with built-in Find on the same large document; establish measurable acceptance thresholds before implementation.
- **Behavior:**

  > Users want responsive, reliable Vim-style modal editing comparable to Sublime rather than merely another extension recommendation. The discussion identifies extension-host contention, unexpected edits or cursor movements, and large-file search as concerns, but does not define the required Sublime/Vim compatibility subset. The planning session must establish that subset and the supported delivery model. Acceptance should cover representative modal operations, predictable undo and selection behavior, and agreed responsiveness checks without degrading ordinary non-modal editing.
- **Trace:**

  > The existing mitigation is extensions.experimental.affinity, registered in src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts and consumed by ExtensionRunningLocationTracker._computeAffinity in src/vs/workbench/services/extensions/common/extensionRunningLocationTracker.ts. It separates eligible extension execution during initial allocation, but supplies no modal-editing implementation. src/vs/editor/browser/coreCommands.ts registers the overwritable Handler.Type command, while TextModel.findMatches in src/vs/editor/common/model/textModel.ts provides internal document search. The open typing-contention issue https://github.com/microsoft/vscode/issues/75627 covers only one concern; https://github.com/microsoft/vscode/issues/59924 tracks a proposed workspace-search API, not this entire experience. The complete discussion at https://github.com/microsoft/vscode/issues/114851#issuecomment-781372526 presents native Vim and reusable platform improvements as alternatives without settling them. Preserve default editing behavior and existing extension contracts; no specific defect or bounded implementation has been conclusively diagnosed here.
- **Open decisions:**
  - Should VS Code provide a built-in modal mode, or guarantee the required experience through platform capabilities consumed by separately installed extensions?
  - Which observable compatibility contract should be supported: Sublime-style Vim behavior, a defined Vim subset, or a configurable modal-editing framework?
