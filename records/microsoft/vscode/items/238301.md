# Issue #238301 — Highliting optimisation is not always correct for asymmetric highlits

[https://github.com/microsoft/vscode/issues/238301](https://github.com/microsoft/vscode/issues/238301)

## Summary

Still present on main: the word highlighter optimization at lines 679–686 of wordHighlighter.ts skips re-fetching highlights when the cursor moves to any existing decoration range, which breaks asymmetric highlights. No fix has been committed. A team member (Yoyokrazy) acknowledged the issue and is considering the best approach.

## Change summary

Word highlighter skips re-requesting document highlights when the cursor moves to another highlighted range, which produces stale results when language servers return asymmetric highlight sets.

## Best solution

Narrow the early-return optimization in `WordHighlighter._run()` (src/vs/editor/contrib/wordHighlighter/browser/wordHighlighter.ts, lines 679–686) so it only skips the request when the cursor stays within the *original* queried range (the range that initiated the current highlight set), not when it moves to any other range in the result set. As DanTup suggested, this is a minor increase in LSP requests and avoids needing a new setting or API change.
