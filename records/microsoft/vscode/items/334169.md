# Issue #334169 — Claude agent host harness ignores ANTHROPIC_BASE_URL / ANTHROPIC_AUTH_TOKEN (cc-switch and other Anthropic-compatible relays)

[https://github.com/microsoft/vscode/issues/334169](https://github.com/microsoft/vscode/issues/334169)

## Summary

Traced a concrete asymmetry on main: the native-transport detection query never enables settingSources, so it can't see ANTHROPIC_BASE_URL/ANTHROPIC_AUTH_TOKEN configured only via ~/.claude/settings.json's env object (the cc-switch pattern), which keeps hasExistingSetup false and forces the harness back to the proxy/GitHub path — matching the reported symptom. Kept open (re-review, no older canonical owns this) with plan-tier readiness since real product decisions remain.

## Change summary

The built-in Claude harness's native (BYO-Anthropic) transport doesn't pick up ANTHROPIC_BASE_URL/ANTHROPIC_AUTH_TOKEN when they're only set via ~/.claude/settings.json's env object (e.g. by cc-switch), so relay-only users can't use the Agents window without GitHub/Anthropic account credentials.

## Best solution

Align buildModelEnumerationOptions with buildOptions's settingSources (or otherwise teach isClaudeAccountSetUp to see settings.json-sourced env credentials), and have a maintainer decide whether a configured relay should win native transport even when a GitHub token is present — right now GitHub sign-in always short-circuits to proxy regardless of relay config.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/claude/claudeSdkOptions.ts`, `src/vs/platform/agentHost/node/claude/claudeTransportMode.ts`, `src/vs/platform/agentHost/node/claude/claudeAgent.ts`
- **Validation:** A test in claudeSdkOptions.test.ts / claudeTransportMode.test.ts asserting that an account whose only credential source is a settings.json-configured ANTHROPIC_BASE_URL/ANTHROPIC_AUTH_TOKEN is detected as 'existing setup' and resolves to native transport when signed out (and per the maintainer's decision, potentially even when signed in to GitHub).
- **Behavior:**

  > When a user has configured ANTHROPIC_BASE_URL/ANTHROPIC_AUTH_TOKEN only via ~/.claude/settings.json's `env` object (no OS-level env vars, no `claude login` keychain entry), the Claude harness in the Agents window should be able to use that relay as a native credential source — at minimum when signed out of GitHub with `chat.agentHost.allowSignedOutWhenUsable` enabled. Acceptance: the native model-enumeration path reports a usable setup for such a configuration, and a session actually routes through the configured relay instead of prompting for GitHub sign-in or hitting api.anthropic.com directly.
- **Trace:**

  > buildModelEnumerationOptions() in src/vs/platform/agentHost/node/claude/claudeSdkOptions.ts builds the throwaway SDK query used by _fetchNativeModels() (claudeAgent.ts) to populate accountInfo()/tokenSource/apiKeySource, which feeds isClaudeAccountSetUp() and resolveClaudeTransportMode() in claudeTransportMode.ts. Unlike the real session's buildOptions(), which sets settingSources: ['user','project','local'] (documented elsewhere in this directory as the mechanism that loads ~/.claude/settings.json), buildModelEnumerationOptions() never sets settingSources, so a settings.json-only relay credential is plausibly invisible to that detection query, leaving hasExistingSetup false and forcing the 'proxy' fallback. Separately, resolveClaudeTransportMode() unconditionally prefers 'proxy' whenever hasGitHubToken is true, before ever checking for a configured relay — the boundary between 'detection bug' and 'GitHub always wins' is the open decision below. Do not change proxy-mode behavior or GitHub-signed-in users who want Copilot-routed models.
- **Open decisions:**
  - Should a native relay configured via ~/.claude/settings.json's env block be detected as a usable setup by the model-enumeration query, on par with OS-env or keychain credentials?
  - When both a GitHub token and a configured relay are present, should the relay ever take precedence over the Copilot proxy, or should GitHub sign-in continue to always win (current behavior)?
  - Should this parity be gated behind the existing experimental chat.agentHost.allowSignedOutWhenUsable flag, or does it need its own opt-in?

## Evidence

- **real session sets settingSources:** src/vs/platform/agentHost/node/claude/claudeSdkOptions.ts buildOptions() passes settingSources: ['user','project','local'] (line ~199), which is documented elsewhere in this dir as the mechanism that loads ~/.claude/settings.json (CONTEXT.md, phase17-plan.md: "the SDK loads them via settingSources").
- **enumeration query omits it:** buildModelEnumerationOptions() (claudeSdkOptions.ts, ~line 279) builds the throwaway query used to decide native-setup availability; its settings.env only sets CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC and it never sets settingSources, so it would not load ~/.claude/settings.json's env block the way the real session does.
- **gating logic:** isClaudeAccountSetUp() (claudeTransportMode.ts) only trusts accountInfo().apiProvider/tokenSource/apiKeySource from that same enumeration query; resolveClaudeTransportMode() falls back to 'proxy' whenever hasExistingSetup is false, which routes the user back to GitHub/Copilot sign-in — exactly what the reporter observed.
- **GitHub-signed-in short-circuit:** resolveClaudeTransportMode() (claudeTransportMode.ts) returns 'proxy' whenever hasGitHubToken is true, before ever consulting the relay — so even a correctly-detected relay setup would be ignored for GitHub-signed-in users, a separate design question.
- **feature is experimental:** The whole native path is gated behind chat.agentHost.allowSignedOutWhenUsable (agentHostCustomizationConfig.ts), described as experimental — so behavior here is still actively evolving.
