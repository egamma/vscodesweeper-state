# Issue #142133 — [Request] [Notebooks] Allow arbitrary values in a cell's language selector.

[https://github.com/microsoft/vscode/issues/142133](https://github.com/microsoft/vscode/issues/142133)

## Summary

Keep open for notebook API and UX discussion: current main still cannot distinguish dynamically named execution targets sharing one language in the built-in cell language picker. The existing status-bar API offers an alternative, but the thread has not settled whether it adequately replaces the requested combined selection; this team-authored issue is protected from a judgment close.

## Change summary

Allow notebook extensions to expose dynamically named per-cell execution targets while retaining the underlying language used for editing.

## Best solution

Agree on an extension-facing way to select a cell's language and execution target without registering fake languages or requiring magic commands. Preserve language identity independently of execution availability, as requested by the notebook maintainer, and settle whether the existing custom status-bar picker is sufficient or a new core contract is needed.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/contrib/notebook/browser/controller/editActions.ts`, `src/vs/workbench/contrib/notebook/common/notebookKernelService.ts`

Check ordinary language selection and Markdown conversion remain unchanged, and that language editing remains possible without an available connection.
- **Behavior:**

  > A notebook extension should let users distinguish multiple execution targets that share one editing language, such as two SQL database connections or two C# runtimes. Selecting a target must provide enough identity for the extension to route execution without requiring a magic command in the cell source. Language editing must remain available independently of connection availability. Acceptance should cover distinct target selection, correct execution routing, unchanged syntax-language behavior, and compatibility with ordinary notebooks.
- **Trace:**

  > NotebookController.supportedLanguages in src/vscode-dts/vscode.d.ts remains string[]; the internal kernel contract in src/vs/workbench/contrib/notebook/common/notebookKernelService.ts also uses string[]. ChangeCellLanguageAction.showLanguagePicker in src/vs/workbench/contrib/notebook/browser/controller/editActions.ts deduplicates IDs, obtains registered language names, and applies only the selected languageId, so it has no separate target identity. The existing notebooks.registerNotebookCellStatusBarItemProvider API can host an extension-defined picker, but does not replace the built-in control. The full proposal at https://github.com/microsoft/vscode/issues/142133#issuecomment-1076698152 needs both named entries and retrieval of the selected entry. The maintainer response at https://github.com/microsoft/vscode/issues/142133#issuecomment-1189674365 establishes that language must remain independent of execution, but does not settle the combined-selection UX or a new API contract. Preserve existing language semantics and offline editing; do not treat display labels alone as sufficient execution identity.
- **Open decisions:**
  - Should combined language-and-target selection remain an extension-owned status-bar or cell-creation interaction, or should VS Code expose a new built-in notebook selection surface?
  - If a new core contract is needed, what stable execution-target identity should an extension receive and retain separately from the cell's language ID and human-readable label?

## Evidence
