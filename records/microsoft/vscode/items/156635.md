# Issue #156635 — Slow to populate the Terminal > Integrated > Tabs: Default Icon dropdown

[https://github.com/microsoft/vscode/issues/156635](https://github.com/microsoft/vscode/issues/156635)

## Summary

Still reproduces on main by tracing the code: the custom SelectBox's measureMaxDetailsHeight still synchronously renders every option's markdown description (hundreds of codicons for this setting) to find the max details-pane height on first open, and the caching added since doesn't survive the settings tree's virtualized re-renders. The prior review's implemented-on-main close (commit 75de1296711) was already refuted; I find a different, still-present root cause, not a new fix, so this stays open.

## Change summary

Opening the Terminal > Integrated > Tabs: Default Icon dropdown in the Settings editor takes ~3 seconds because the codicon list is huge.

## Best solution

Avoid rendering every option's markdown description just to size the details pane — e.g. cap/estimate the details height instead of a true max, or only measure the currently visible/selected option(s) — in selectBoxCustom.ts's layoutSelectDropDown/measureMaxDetailsHeight path.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/selectBox/selectBoxCustom.ts`, `src/vs/workbench/contrib/preferences/browser/settingsTree.ts`
- **Validation:** A SelectBox/selectBoxCustom unit or settings-editor integration test asserting the details-pane height computation does not synchronously render markdown for every option when the dropdown has a very large option list (e.g. hundreds of entries), and that opening remains fast.
- **Behavior:**

  > Opening the Default Icon (or any codicon-backed) dropdown in the Settings editor should feel instant, not take ~3 seconds, regardless of how many codicon options exist. The details pane below the option list should still size reasonably (no visible jump/clipping as the user scrolls or selects different options). Acceptance: opening a SelectBox-based setting with hundreds of markdown-described options renders the dropdown without a multi-second synchronous pause, and the details pane remains usable.
- **Trace:**

  > In src/vs/base/browser/ui/selectBox/selectBoxCustom.ts, layoutSelectDropDown() (line ~634) calls measureMaxDetailsHeight() (line ~588) the first time `_hasDetails` is true and `_cachedMaxDetailsHeight` is undefined; that function loops over every option calling updateDetail(index) and forces a layout read via offsetHeight, i.e. renders markdown for every option synchronously. `_hasDetails` becomes true whenever any option carries a `description` (setOptions(), line ~313), which is the case for terminal.integrated.tabs.defaultIcon because terminalIconSchema (src/vs/platform/terminal/common/terminalPlatformConfiguration.ts:30-34) supplies a markdown description per codicon (hundreds of entries), wired through SettingEnumRenderer.renderValue in src/vs/workbench/contrib/preferences/browser/settingsTree.ts (~line 1929-1970). The cache meant to avoid repeat work is reset on every setOptions() call unless the new options array is reference-equal item-by-item (src/vs/base/common/arrays.ts:28-43 default comparator), but settingsTree.ts constructs new option objects on every render, so in the real (virtualized) Settings editor the cache rarely survives and the full scan reruns. Boundary: do not change SelectBox's general API/behavior for small option lists (the common case) or alter how options/descriptions are supplied to settingsTree.ts — the fix should target how the details-pane height is computed for the dropdown-open path, not the per-option description content.
- **Open decisions:**
  - Should the details pane be sized from a fixed/estimated height (sacrificing exact-fit sizing for performance) instead of a true max over all options, and is a visible size change acceptable for very large option lists?
  - Should the fix only measure the currently selected/visible option(s) and accept that the pane may resize as the user scrolls, or must one static height still be computed up front?
  - Should the equality check used to decide whether to reuse `_cachedMaxDetailsHeight` be changed (e.g. to a content/value comparator) so the cache actually survives repeated renders of the same logical setting in the virtualized tree, and is that change safe for other SelectBox consumers?

## Evidence

- **root cause still present:** src/vs/base/browser/ui/selectBox/selectBoxCustom.ts:587-599 measureMaxDetailsHeight() iterates `this.options.forEach` calling updateDetail(index) and reading offsetHeight for EVERY option, called from layoutSelectDropDown() on first dropdown open whenever `_hasDetails` is true.
- **setting has hundreds of markdown-described options:** src/vs/platform/terminal/common/terminalPlatformConfiguration.ts:30-34 terminalIconSchema sets `markdownEnumDescriptions: Array.from(getAllCodicons(), icon => `$(${icon.id})`)` for terminal.integrated.tabs.defaultIcon, and settingsTree.ts's SettingEnumRenderer.renderValue (~line 1950-1965) passes each as a per-option `description`/`descriptionIsMarkdown`, which sets `_hasDetails = true` in selectBoxCustom.ts:313-315.
- **cache doesn't survive virtualized re-renders:** selectBoxCustom.ts:304-317 setOptions() only reuses `_cachedMaxDetailsHeight` when `arrays.equals(this.options, options)` is true, but the default item comparator is reference equality (`src/vs/base/common/arrays.ts:28-43`) and SettingEnumRenderer.renderValue builds a brand-new options array/objects on every render (settingsTree.ts ~1950-1965), so the virtualized settings tree's template reuse resets `_hasDetails`/`_cachedMaxDetailsHeight` on essentially every re-render, forcing the full all-option markdown measurement again on the next dropdown open.
