# Issue #225417 — support finding matches in the debug console's output

[https://github.com/microsoft/vscode/issues/225417](https://github.com/microsoft/vscode/issues/225417)

## Summary

Keep open: current tree find can identify matching output rows, but the output renderers do not display the match highlights. This team-authored issue remains the canonical request, with recent maintainer confirmation and additional demand from a consolidated report.

## Change summary

Make find matches visible within Debug Console output, including long messages and evaluated values.

## Best solution

Complete output-match highlighting in the Debug Console while preserving ANSI styling, links, and responsiveness for large output. Keep match counters, navigation buttons, and reverse filtering in their separately tracked requests.

- **Behavior:**

Acceptance must include large-output responsiveness; match counters, navigation buttons, and reverse filtering are separately tracked.
- **Trace:**

  > Repl creates a find-enabled WorkbenchAsyncDataTree in src/vs/workbench/contrib/debug/browser/repl.ts and searches each element through toString(true); ReplOutputElement.toString includes output text. FindFilter in src/vs/base/browser/ui/tree/abstractTree.ts returns a fuzzy or contiguous score for the matching row. In src/vs/workbench/contrib/debug/browser/replViewer.ts, evaluation inputs consume that score, but output and evaluation-result renderers do not pass match highlights to DebugExpressionRenderer. The shared renderer already supports highlights through its ANSI and link-rendering paths, but score offsets must be reconciled with the displayed text, including source suffixes and repeated-output counts. The original provider prerequisite https://github.com/microsoft/vscode/issues/212077 is closed; no runtime or performance behavior was verified. Planning should settle occurrence semantics and the performance acceptance criterion before implementation.
- **Open decisions:**
  - Should output highlighting show only the fuzzy or contiguous match selected by the existing tree-find semantics, or every occurrence of the query within each matching output row?
