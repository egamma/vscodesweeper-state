# Issue #149153 — Support to detect file links in output

[https://github.com/microsoft/vscode/issues/149153](https://github.com/microsoft/vscode/issues/149153)

## Summary

Keep open: current output link detection still depends on workspace-root patterns, leaving remote file URIs outside the workspace without the required remote target. The related outside-workspace request is newer, and the older file-position request does not establish the same observable symptom, so neither clears the re-review duplicate bar.

## Change summary

Support opening remote file links emitted to an output channel even when their targets are outside every workspace folder.

## Best solution

Extend output-channel file-link support so the reported outside-workspace remote files open correctly, while preserving local links, existing workspace links, and efficient detection. Coordinate with the related outside-workspace path request without discarding this older remote-URI report.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/output/common/outputLinkComputer.ts`, `src/vs/workbench/contrib/output/browser/outputLinkProvider.ts`, `src/vs/workbench/contrib/output/test/browser/outputLinkProvider.test.ts`
- **Validation:** In WSL and Remote-SSH, create existing files inside and outside the opened workspace, emit their file URIs through a minimal extension output channel, and verify both open the corresponding remote files. Repeat locally to preserve local opening. Add output-link tests asserting the selected URI scheme and authority for both locations, and run scripts/test.sh --run src/vs/workbench/contrib/output/test/browser/outputLinkProvider.test.ts after implementation.
- **Behavior:**

  > An extension running remotely emits file URIs for existing files inside and outside the opened workspace. Clicking either link should open the intended remote file, without requiring the user to enlarge the workspace or accidentally creating a local file. Local output links and existing workspace-file navigation must continue to work. Acceptance includes the reporter's extensionless filename case in WSL and Remote-SSH, plus local regression checks.
- **Trace:**

  > OutputLinkProvider passes workspace folder URIs to OutputLinkComputer, whose computePatterns/createPatterns recognize workspace-root text and whose $computeLinks constructs targets using the corresponding folder URI. This explains why recognized workspace paths retain remote scheme and authority while an outside-workspace file URI falls through to ordinary URL handling; EditorOpener.open does not supply remote reinterpretation. The source still contains this detection boundary, but no remote execution was performed. The maintainer classified the requested expansion as a feature at https://github.com/microsoft/vscode/issues/149153#issuecomment-1141680018. Existing DocumentLinkProvider APIs allow extension-specific handling, not general automatic coverage. Preserve existing workspace patterns, local-link semantics, and output responsiveness; broader relative-path and custom-label support are outside this report. Planning must establish how an output channel distinguishes remote file references from intentionally local file URIs; coordinate related work at https://github.com/microsoft/vscode/issues/163778.
- **Open decisions:**
  - In a remote window, should outside-workspace file URIs always resolve on the remote host, or should interpretation depend on the output channel's producer so intentionally local file links remain local?
