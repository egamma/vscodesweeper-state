Real gap confirmed in source: no existing setting suppresses the SCM 'Worktrees' artifact group or the worktree-aware checkout prompts, so this is a valid feature request that should be routed to the git area owner.

## Change summary

Add a setting to fully disable the integrated Git worktrees UI (Source Control listing group and branch-checkout worktree prompts).

  > Thanks for the detailed report and reproduction steps. Looking at the source, this checks out: `git.detectWorktrees` only controls whether VS Code auto-opens worktree folders as extra repositories (extensions/git/src/model.ts) — it doesn't gate the 'Worktrees' group in Source Control (extensions/git/src/artifactProvider.ts always populates it) or the worktree-conflict checkout prompt (extensions/git/src/commands.ts). A real opt-out would need to touch both of those. Routing to the Git area for consideration.

## Evidence

- **detectWorktrees only controls auto-open:** extensions/git/src/model.ts `checkForWorktrees()` (using `shouldDetectWorktrees` from `git.detectWorktrees`) only decides whether to auto-open worktree folders as extra repositories; it has no effect on the SCM artifact listing.
- **Worktrees group always populated:** extensions/git/src/artifactProvider.ts always registers a `worktrees` SourceControlArtifactGroup and `provideArtifacts('worktrees')` unconditionally calls `this.repository.getWorktreeDetails()` — no config check exists there.
- **checkout prompt not gated either:** extensions/git/src/commands.ts around line 2939-2960 handles `GitErrorCodes.WorktreeBranchAlreadyUsed` by prompting via `handleWorktreeBranchAlreadyUsed`, triggered whenever git itself refuses the checkout — there is no setting to skip this path.
- **precedent issue:** https://github.com/microsoft/vscode/issues/278774 (closed) only flipped the `detectWorktrees` default to false, confirming it never addressed the listing/prompt behavior the reporter is asking about.
- **community corroboration:** Multiple independent commenters (xmatthias, halllo, ClaudeMetz) confirm the same pain, including a possible perf/init-time complaint from a repo with many worktrees.
