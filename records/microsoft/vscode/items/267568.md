## Evidence

- **Reported boundary:** https://github.com/microsoft/vscode/issues/267568 reports macime's 1hand-right layout emitting raw q/w/a/s/z/x in VS Code 1.104.1 and Hyper, while TextEdit, Chrome, and iTerm receive the mapped characters. Ordinary Hangul composition keys work, indicating a specific IME delivery problem rather than complete lack of composition support.
- **Maintainer discussion:** The supplied discussion links https://github.com/xtermjs/xterm.js/issues/3836 as only potentially related; Tyriar explicitly notes that xterm.js generally waits for composition. Reading that upstream issue shows an iOS/iPadOS Korean combining failure, not an established diagnosis of macime's raw-key substitution.
- **Current VS Code input boundary:** src/vs/workbench/contrib/terminal/browser/terminalInstance.ts:890 forwards xterm.raw.onData to _handleOnData. Its custom keyboard handler at lines 1157–1223 handles shortcuts and returns true for ordinary printable keys; it contains no macime mapping logic. package.json currently declares @xterm/xterm ^6.1.0-beta.304.
- **Upstream handling remains a diagnostic lead:** Reading https://github.com/xtermjs/xterm.js/blob/master/src/browser/CoreBrowserTerminal.ts shows _keyDown consulting CompositionHelper before evaluating and emitting keyboard results, while _inputEvent gates insertText delivery on composed/_keyDownSeen and screen-reader mode. These paths are relevant, but the report lacks the event trace needed to identify which one mishandles macime; source inspection alone does not establish resolution.
- **Linked upstream report is distinct:** https://github.com/xtermjs/xterm.js/issues/6089 is open and describes deferred composition sends being cancelled during fast typing under load. Its body explicitly distinguishes this issue's raw-key consumption from that scheduling defect, so it is not proof of a shared fix.
- **Related direct-commit reports:** https://github.com/xtermjs/xterm.js/issues/5887 and https://github.com/xtermjs/xterm.js/issues/6045 are open and document dropped or duplicated direct-commit input with keyCode=229 and unusual input/keydown ordering. They provide useful instrumentation leads, but neither establishes the event sequence or root cause of macime's mapped keys appearing as raw Latin keys.
