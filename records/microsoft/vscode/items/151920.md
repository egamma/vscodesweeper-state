# Issue #151920 — Add additional (or custom) InlayHintKinds

[https://github.com/microsoft/vscode/issues/151920](https://github.com/microsoft/vscode/issues/151920)

## Summary

Keep open: current VS Code supports themeable unclassified hints, but not additional independently styled hint categories. The request has 57 upvotes, remains accepted in Backlog, and the canonical search found no older open issue covering the same capability.

## Change summary

Allow additional or custom inlay hint categories so extensions can distinguish closing labels and other annotations from type and parameter hints.

## Best solution

Define a theme-integrated category contract for non-type/non-parameter hints, coordinated with LSP, while preserving existing kinds and their fallback behavior. Decide whether this should expose additional standardized kinds or extension-defined categories before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages.ts`, `src/vs/workbench/api/common/extHostTypeConverters.ts`, `src/vs/editor/contrib/inlayHints/browser/inlayHintsController.ts`, `src/vs/platform/theme/common/colors/editorColors.ts`
- **Validation:** After the contract is chosen, exercise a provider emitting type, parameter, unclassified, and two distinct nonstandard hint categories. Verify the new categories can be themed independently, existing categories retain their behavior, and unsupported categories receive the documented fallback; cover conversion and renderer behavior with targeted tests.
- **Behavior:**

  > Extensions should be able to expose language-specific inlay annotations, such as Dart closing labels, with styling distinguishable from type and parameter hints and from other annotation categories. Current unclassified hints provide one shared themeable appearance, which does not satisfy independent category customization. Acceptance should demonstrate distinct categories with independently configurable theme colors while preserving existing type, parameter, and unclassified behavior. Multiline documentation expansion is not settled by the original styling request and should not be implicitly promised.
- **Trace:**

  > The public InlayHintKind enum in src/vscode-dts/vscode.d.ts and the editor enum in src/vs/editor/common/languages.ts contain only Type and Parameter. InlayHintsController._fillInColors in src/vs/editor/contrib/inlayHints/browser/inlayHintsController.ts maps those kinds to dedicated theme colors and all other hints to the shared generic colors registered in src/vs/platform/theme/common/colors/editorColors.ts. InlayHintKind conversions in src/vs/workbench/api/common/extHostTypeConverters.ts currently pass the enum value through. This establishes a missing category contract, not a failure to render kindless hints. The discussion at https://github.com/microsoft/vscode/issues/151920 favors using inlay hints rather than introducing general decorations into LSP; preserve existing theming and provider behavior. Uncertainty begins at the public category and theming contract and its LSP interoperability, not at whether the existing renderer has a generic fallback.
- **Open decisions:**
  - Should the API expose additional standardized InlayHintKind values, extension-defined categories, or both?
  - If custom categories are supported, what stable identity and theme customization contract should they expose, including fallback behavior in clients that do not recognize them?
