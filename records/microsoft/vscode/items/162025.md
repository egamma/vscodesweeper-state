# Issue #162025 — Hard to tell that Edit Sessions were turned on with two different auth providers

[https://github.com/microsoft/vscode/issues/162025](https://github.com/microsoft/vscode/issues/162025)

## Summary

Keep open: the discussion established an account-selection UX gap, not a failure to restore changes when using the same identity. Current Cloud Changes code still lacks source-identity guidance during Continue Working On, and the verified related issues do not supersede this report.

## Change summary

Make it easier to recognize and avoid using different Cloud Changes authentication identities in the source and destination environments.

## Best solution

Make the Cloud Changes identity understandable during cross-environment continuation and provide an actionable way to resolve an identity mismatch. Preserve separate account storage and deliberate account selection; choose the user-facing guidance with the maintainer before implementation.

Add focused automated coverage for the selected account-guidance behavior.
- **Behavior:**

  > Cloud Changes continuation currently fails to retrieve edits when source and destination use different authentication identities, without making that mismatch clear to the user. The finished experience should make the identity requirement understandable and provide a clear recovery path without conflating accounts or silently changing the selected identity. Acceptance covers both web-to-desktop and desktop-to-web continuation, while matching-identity restoration remains unchanged. The exact guidance and recovery interaction require a maintainer decision.
- **Trace:**

  > EditSessionsWorkbenchService.getAuthenticationSession in src/vs/workbench/contrib/editSessions/browser/editSessionsStorageService.ts reuses a locally cached session before prompting; getAllSessions supplies account/provider labels but no source-identity context. registerResetAuthenticationAction exposes a generic Turn off Cloud Changes action, so existing manual reconfiguration is not proactive mismatch guidance. The Continue Working On action in src/vs/workbench/contrib/editSessions/browser/editSessions.contribution.ts passes a stored editSessionId and continueOn flag without source-account information. The thread confirms successful restoration after aligning identities, and https://github.com/microsoft/vscode/issues/167665 independently confirms the same problem. https://github.com/microsoft/vscode/issues/162099 discusses source-identity hints but leaves their user-visible behavior unresolved. Keep account isolation, explicit user choice, and existing matching-account restoration intact; this is not a request to let different identities access each other's stored changes.
- **Open decisions:**
  - Should continuation proactively show the source Cloud Changes identity, guide account selection using it, or present recovery guidance only when restoration fails?
  - When the destination is already configured with a different identity, should it retain that selection and offer explicit reconfiguration, or offer a one-time restore using the source identity?
