# Issue #90301 — Allow to use decorations in quick input (e.g. for editors picker)

[https://github.com/microsoft/vscode/issues/90301](https://github.com/microsoft/vscode/issues/90301)

## Summary

Keep open: current editor and file pickers still lack resource decorations, and maintainers have accepted the goal but not settled its presentation. This issue already owns two duplicate reports and is correctly routed.

## Change summary

Show Git file-status decorations in the Ctrl+Tab editor picker, with related discussion covering file Quick Open.

## Best solution

Provide readable resource decorations in editor and file pickers without obscuring unsaved-change indicators or row actions. Settle badge placement and color behavior with the maintainer before implementing the shared presentation.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/editor/editorQuickAccess.ts`, `src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts`, `src/vs/platform/quickinput/browser/quickInputList.ts`, `src/vs/workbench/browser/labels.ts`
- **Validation:** In a Git workspace, open clean, modified, and untracked files, including one with unsaved changes. Check Ctrl+Tab and file Quick Open for the agreed status presentation, preservation of dirty/close/split actions, and stable alignment with long descriptions and filtering. Verify keyboard navigation and screen-reader status information, including a high-contrast theme.
- **Behavior:**

  > The Ctrl+Tab editor picker should expose Git modified/untracked status that is already available in Open Editors, rather than showing only unsaved-change state. Related reports consolidated here also request decoration colors in file Quick Open. Decoration presentation must remain distinguishable from unsaved edits and must not obscure existing actions. Acceptance should cover clean, modified, untracked, and unsaved files, long descriptions, filtered lists, keyboard navigation, and accessible status information.
- **Trace:**

  > Ctrl+Tab is registered in src/vs/workbench/browser/parts/editor/editorActions.ts and uses ActiveGroupEditorsByMostRecentlyUsedQuickAccess. BaseEditorQuickAccessProvider.doGetEditorPickItems in editorQuickAccess.ts builds icon classes and dirty/close buttons without querying IDecorationsService; createAnythingPick in anythingQuickAccess.ts has the same missing resource-decoration input. QuickInputList in src/vs/platform/quickinput/browser/quickInputList.ts renders IconLabel and accepts extra classes through iconClasses, while ResourceLabel rendering in src/vs/workbench/browser/labels.ts demonstrates how decoration classes are obtained and applied. This establishes the missing capability without executing the checkout. Keep workbench decoration-service dependencies out of lower-layer quick-input rendering, and preserve picker ordering, filtering, acceptance, and existing action semantics. https://github.com/microsoft/vscode/issues/121416 and https://github.com/microsoft/vscode/issues/175294 were explicitly consolidated into this issue. Uncertainty starts at the visible layout: the thread has not settled decoration placement, color use, or simultaneous display with dirty and action controls.
- **Open decisions:**
  - Should pickers display both resource-decoration colors and badges, or badges alone, and should that follow the existing editor-decoration settings?
  - Where should status badges appear relative to labels, descriptions, dirty indicators, and action buttons so rows remain consistently scannable?
