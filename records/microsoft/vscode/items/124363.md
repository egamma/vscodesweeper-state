[https://github.com/microsoft/vscode/issues/124363](https://github.com/microsoft/vscode/issues/124363)

## Summary

The shared IconPath type and webview support are now present, but the API alignment remains incomplete. Keep this open to resolve the remaining comment API contracts and distinguish deliberate exceptions from unfinished adoption.

## Change summary

Align extension API icon properties around Uri, light/dark URI pairs, and ThemeIcon support.

Finish the cross-area API audit, implementing consistent icon support where appropriate and explicitly documenting intentional exceptions. Settle the comment-author avatar contract with the comments owner before broadening that API.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostComments.ts`, `src/vs/workbench/contrib/comments/browser/commentNode.ts`, `src/vs/workbench/contrib/comments/browser/commentReply.ts`
- **Validation:** The plan should end with extension API checks for each approved icon shape and a runnable extension-host scenario exercising comment author/reaction icons across light and dark themes, including ThemeIcon where approved; existing URI and string-path behavior must remain compatible.
- **Behavior:**

  > Extension authors should have consistent icon capabilities across the APIs included in the agreed scope: URI images, light/dark image pairs, and theme icons. Any intentional exception must have an explicit contract rather than an accidental type mismatch. Acceptance should exercise each approved shape in the actual UI across light and dark themes while preserving existing URI and string-path inputs.
- **Trace:**

  > src/vscode-dts/vscode.d.ts defines IconPath and already applies it to WebviewPanel, but CommentAuthorInformation and CommentReaction still expose narrower contracts. In src/vs/workbench/api/common/extHostComments.ts, convertToReaction uses pathOrURIToURI and author icons remain URI-shaped; commentNode.ts:updateCommentUserIcon and commentReply.ts:updateAuthorInfo render avatars as URI-backed images. This establishes that remaining work spans declarations, transport, and rendering rather than a type-alias substitution. SCM already supports ThemeIcon and separate light/dark decorations, so preserve those existing contracts and legacy string inputs. https://github.com/microsoft/vscode/pull/232471 supplies the shared type, and https://github.com/microsoft/vscode/issues/90616 covers the completed webview slice. The uncertainty begins with the unresolved author-avatar exception and whether editor decoration icons raised in the discussion belong in this cleanup.
- **Open decisions:**
  - Should CommentAuthorInformation.iconPath support ThemeIcon and light/dark URI pairs, including a theme-icon fallback avatar, or remain intentionally URI-only?
  - Does this cleanup include gutterIconPath and contentIconPath, as suggested in the discussion, or are those separate editor-decoration API work?

## Evidence

- **Shared type is only partial completion:** https://github.com/microsoft/vscode/pull/232471 merged the IconPath extraction as commit 6d074207225be7a299080c2202469ecbe3ff5df0. The author's subsequent 2024-10-29 comment on https://github.com/microsoft/vscode/issues/124363 explicitly says differing iconPath shapes remain.
- **Current API coverage and remaining gaps:** src/vscode-dts/vscode.d.ts:973 defines IconPath; WebviewPanel.iconPath at line 10100 now uses it. CommentAuthorInformation.iconPath at line 17614 remains Uri-only, and CommentReaction.iconPath at line 17629 remains string | Uri, excluding ThemeIcon and light/dark pairs.
- **Runtime work remains:** src/vs/workbench/api/common/extHostComments.ts:792 forwards the author icon as a URI; convertToReaction at lines 800–806 converts icons with pathOrURIToURI. src/vs/workbench/contrib/comments/browser/commentNode.ts:219–225 renders author icons as img elements from revived URIs, and commentReply.ts:206–211 likewise expects a URI. Widening declarations alone would not deliver the requested support.
- **Existing SCM capability differs structurally:** src/vscode-dts/vscode.d.ts:16439–16485 already allows string | Uri | ThemeIcon for SCM resource icons and supplies separate light/dark decoration objects. https://github.com/microsoft/vscode/issues/128258 is closed; it addresses one component, not the complete API alignment.
- **Unsettled public contract:** The 2022-12-09 discussion on https://github.com/microsoft/vscode/issues/124363 questions whether comment-author icons should remain user-image URIs; the author counters that a ThemeIcon could represent a default avatar. That observable API decision remains unresolved in the supplied discussion.
- **Related work is not a canonical replacement:** https://github.com/microsoft/vscode/issues/90616 is closed and covers webview ThemeIcon support only. https://github.com/microsoft/vscode/issues/232439 is also closed and concerns file icons in selected surfaces. Neither owns this broader remaining work; canonical searches for iconPath alignment and ThemeIcon support found no verified open replacement, and an open-PR search for 124363 returned none.
