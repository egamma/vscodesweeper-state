## Summary

Keep this team-authored Backlog umbrella open. Current main has gained substantial session orchestration support, but the model-facing tool surface still lacks explicit plan-approval and PR/issue-session entry points, and partial completion of one tracked gap does not complete the broader item.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/shared/sessionServerTools.ts`, `src/vs/platform/agentHost/common/serverToolNames.ts`, `src/vs/platform/agentHost/node/agentService.ts`, `src/vs/sessions/services/sessions/common/sessionsProvider.ts`
- **Validation:** For each agreed child capability, add focused SessionServerTools and provider/orchestrator coverage; the plan should end with `./scripts/test.sh --grep 'SessionServerTools'` plus the targeted Agent Host provider tests for any new protocol or lifecycle seam.
- **Behavior:**

  > Agent sessions should expose the remaining orchestration primitives needed to coordinate work across projects and GitHub artifacts. An orchestrating agent should be able to discover eligible projects, establish the intended branch or fork relationship, participate in an explicit plan-approval flow, and start work from a pull request or issue without losing session provenance. Existing create_session, send_message, list_sessions, and get_session_context behavior must remain compatible. Acceptance criteria should be specified separately for each capability before implementation.
- **Trace:**

  > The model-facing orchestration inventory is defined in src/vs/platform/agentHost/node/shared/sessionServerTools.ts and named through src/vs/platform/agentHost/common/serverToolNames.ts. Current create_session accepts relationship, workspace, worktree, title, and model; list_sessions exposes session-derived project and Git metadata, but there are no plan-approval or PR/issue-session tools. src/vs/sessions/SESSIONS.md places chat creation and forking behind provider capabilities, while src/vs/platform/agentHost/AGENTS.md documents host-owned project resolution and fork behavior, so some original gaps are now partially covered beneath the server-tool surface. The uncertainty begins at the public tool contracts and ownership boundaries for configured-project discovery, approval state, and GitHub-artifact entry points. Preserve provider-neutral Sessions contracts and do not collapse the existing session-versus-chat relationship semantics while planning the remaining work. Related partial work: https://github.com/microsoft/vscode/pull/332767 and https://github.com/microsoft/vscode/issues/332770.
- **Open decisions:**
  - Should project discovery expose only projects represented by existing sessions, or a broader configured-project catalog that can be used before any session exists?
  - What user-observable states and actions constitute plan approval: approve or reject a plan within the originating chat, create a follow-up session, or both?
  - When starting from a pull request or issue, which repository, branch, isolation, and session relationship should be inferred, and which choices must remain explicit to the user?
  - Should the remaining capabilities stay consolidated under this umbrella or be represented as independently shippable child issues with separate tool contracts?
