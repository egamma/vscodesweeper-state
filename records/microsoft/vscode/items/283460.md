Keep open as an upstream Chromium/Ozone Wayland keyboard regression. Multiple reports confirm the failure, including October 2026; the claimed Chromium 152 fix needs concrete provenance and confirmation in VS Code before proposing completion.

## Change summary

## Evidence

- **Confirmed platform-specific regression:** The discussion at https://github.com/microsoft/vscode/issues/283460 includes independent Kubuntu, Fedora KDE/Wayland, and Ubuntu confirmations. The February 15 report isolates the failure to --ozone-platform=wayland and confirms --ozone-platform=x11 restores deletion in VS Code 1.109.3; Electron's native-Wayland default change exposed the affected path.
- **Recent diagnostic evidence:** The October 7, 2026 comment reports the same failure in VS Code 1.140.0 on GNOME/Wayland: compositor tools emit KP_Delete, but Electron delivers code NumpadDecimal, keyCode 110, and key Unidentified. X11 compatibility mode works, and remapping KP_Delete to Delete at the xkb layer also works. This identifies an upstream key-translation problem rather than an installed-extension defect.
- **Current source handling:** src/vs/base/browser/keyboardEvent.ts:11-48 converts browser keyCode through EVENT_KEY_CODE_MAP; src/vs/base/common/keyCodes.ts maps browser keyCode 110 to NumpadDecimal. src/vs/workbench/services/keybinding/common/macLinuxKeyboardMapper.ts:969-989 deliberately dispatches numpad keys using keyCode to preserve NumLock behavior. The reported malformed event therefore remains a decimal key rather than Delete on this source path.
- **Existing expectation and workaround limits:** src/vs/workbench/services/keybinding/test/node/macLinuxKeyboardMapper.test.ts:1620 expects NumpadDecimal accompanied by KeyCode.Delete to resolve as Delete. The May discussion confirms custom numpad_decimal bindings help editor deletion but do not restore native deletion in find/search input boxes; forcing decimal bindings is not complete coverage and risks conflating NumLock states.
- **Upstream fix lead is not completion proof:** The thread links https://issues.chromium.org/issues/429730008 and https://issues.chromium.org/issues/405793116. A September 24 comment says Chromium 152 fixes the problem, but supplies no behavioral fix commit. Current .npmrc targets Electron 43.7.7; that dependency version alone establishes neither the upstream fix's provenance nor correct behavior on this Wayland path. The checkout is shallow and no issue-specific fixing commit was found in its available history.
