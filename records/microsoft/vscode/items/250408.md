# Issue #250408 — Tool / Toolset attachment pill is not clickable

[https://github.com/microsoft/vscode/issues/250408](https://github.com/microsoft/vscode/issues/250408)

## Summary

Keep open: current source still renders tool and toolset attachment pills without an activation action. The thread establishes a consistency concern, but leaves the destination for activation undecided; this team-authored request should not be declined.

## Change summary

Make tool and toolset chat attachment pills actionable, consistent with other navigable attachments.

## Best solution

Define a useful activation destination for each tool reference type, then support mouse and keyboard activation consistently in chat input and submitted messages. Opening user toolset definitions is a concrete option from the discussion; ordinary tools and extension/MCP toolsets still need a product decision.

- **Validation:** After choosing activation semantics, attach an individual tool, a user-defined toolset, and an extension/MCP toolset through # or Add Context. Verify that clicking and pressing Enter/Space reach the agreed destination in both input and submitted messages, and that removal still removes the attachment without invoking navigation.
- **Behavior:**

  > Tool and toolset attachment pills currently look actionable but do not navigate when activated. The goal is a useful, consistent activation behavior with equivalent mouse and keyboard access. The thread offers focusing the referenced entry in Configure Tools and opening user-defined toolset files as possible destinations, but does not settle the full behavior. Acceptance should cover individual tools and toolsets in both input and submitted messages while preserving attachment removal and tool enablement state.
- **Trace:**

  > ToolSetOrToolItemAttachmentWidget in src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentWidgets.ts resolves tool metadata and renders a pointer cursor and hover without registering an activation handler. AbstractChatAttachmentWidget supplies focusability, a button role, removal handlers, and optional resource-opening helpers, but no default navigation. Both ChatInputPart and ChatAttachmentsContentPart use this widget for tool/toolset references. ConfigureToolsAction provides workbench.action.chat.configureTools, while ConfigureToolSets provides chat.configureToolSets and can open a user toolset's source.file. The source inspection confirms the missing interaction, not the correct destination; that uncertainty is also explicit in https://github.com/microsoft/vscode/issues/250408. Preserve existing tool selection, enablement, submission, and deletion semantics; this request does not call for redesigning those systems.
- **Open decisions:**
  - What should activation open for an individual tool or an extension/MCP toolset: Configure Tools focused on that reference, a details surface, or another destination?
  - Should user-defined toolset activation open its definition directly, or use the same destination as other tool references?
