# Issue #236405 — We need an API or some way to know that URI Handling is possible

[https://github.com/microsoft/vscode/issues/236405](https://github.com/microsoft/vscode/issues/236405)

## Summary

Keep open: portable-mode improvements do not provide the requested general URI-handling capability API, and the author explicitly identified remaining Linux archive-install scenarios. The existing APIs distinguish portable mode and register callbacks, but do not tell extensions whether an external callback can reach this instance.

## Change summary

Expose whether external URI callbacks can reach the running VS Code instance so extensions can select a working authentication flow.

## Best solution

Define an extension-facing capability contract that accounts for missing OS protocol registration and callbacks reaching a different user-data-dir instance. Coordinate with the related protocol-detection issue without treating portable-mode detection as complete coverage.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostUrls.ts`, `src/vs/workbench/api/browser/mainThreadUrls.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/platform/url/electron-main/electronUrlListener.ts`
- **Validation:** Validate the agreed capability contract against a registered desktop installation, an unregistered Linux archive installation, portable mode, and a custom --user-data-dir instance alongside a normal instance. Verify an extension can choose a working authentication fallback when callbacks cannot reach it, while existing URI-handler registration and working callback flows remain unchanged.
- **Behavior:**

  > Extensions need to know whether an external URI callback can reach their running VS Code instance before selecting an authentication flow. The reported failure opens another instance and leaves the initiating instance waiting; manually switching to local-server authentication succeeds. Acceptance must cover both missing OS protocol registration and a registered protocol pointing at a different instance, not portable mode alone.
- **Trace:**

  > window.registerUriHandler in src/vscode-dts/vscode.d.ts returns only Disposable, and ExtHostUrls.registerUriHandler in src/vs/workbench/api/common/extHostUrls.ts registers an internal callback without an external-reachability result. ElectronURLListener in src/vs/platform/url/electron-main/electronUrlListener.ts performs Windows OS registration outside portable mode, with no custom user-data-dir in its registration arguments. env.isAppPortable and the GitHub loopback-server redirect changes cover a narrower condition; the author explicitly says Linux non-RPM/DEB cases remain at https://github.com/microsoft/vscode/issues/236405#issuecomment-3918912229. https://github.com/microsoft/vscode/issues/148041 is related missing-registration work, not a verified duplicate of the wrong-instance scenario. The unresolved boundary is what reliability the API can promise across OS registration, instance selection, and changing system state; preserve existing callback dispatch and authentication fallback behavior.
- **Open decisions:**
  - Does the capability describe OS protocol registration alone, or whether a callback can reach the requesting VS Code instance, including custom user-data directories?
  - When reachability cannot be determined reliably, should the API expose an explicit unknown state or provide a documented best-effort boolean?
  - Is capability information a query-time snapshot, an observable environment property, or part of URI-handler registration?

## Evidence

- **Existing capability is narrower:** src/vscode-dts/vscode.d.ts:10797-10805 exposes env.isAppPortable, explicitly defined by portable-mode data-directory use. It does not report OS protocol registration or whether callbacks will reach a custom --user-data-dir instance. window.registerUriHandler at lines 11706-11727 returns only Disposable; env.asExternalUri resolves a callback URI rather than exposing a capability result.
- **Registration does not establish external reachability:** src/vs/workbench/api/common/extHostUrls.ts, ExtHostUrls.registerUriHandler, records an extension handler and invokes $registerUriHandler without checking OS registration. src/vs/platform/url/electron-main/electronUrlListener.ts registers the Windows protocol client only outside portable mode; its registration arguments contain --open-url but do not preserve a custom --user-data-dir.
