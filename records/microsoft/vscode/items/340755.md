# Issue #340755 — Linux: archive builds use the com.microsoft.VSCode app_id when the system package is installed

[https://github.com/microsoft/vscode/issues/340755](https://github.com/microsoft/vscode/issues/340755)

## Summary

Thanks for the detailed report. The source confirms it: src/mainImpl.ts sets the desktop name whenever /usr/share/applications/<linuxDesktopName>.desktop exists, without checking that the running build is the installed package. This stays open for routing.

## Change summary

Archive (tar.gz) builds on Linux adopt the system package's app_id when the RPM or deb is also installed.

## Best solution

Only call setDesktopName for the system-installed desktop file when the running executable belongs to the installed package (for example, process.execPath under the install directory). Archive builds would then keep the desktopName from their own package.json.

## Plan brief

- **Likely files:** `src/mainImpl.ts`
- **Validation:** Manual check on Linux Wayland: with the system package installed, launch an extracted archive build whose desktopName differs. The window app_id must equal the archive's desktopName, and the system package must still report com.microsoft.VSCode.
- **Behavior:**

  > A Linux archive or portable build must not adopt the system package's desktop name just because the system package's .desktop file exists. The system-installed build keeps its current behavior, and snap handling is unchanged. Acceptance: an archive build with a custom desktopName reports that app_id with the RPM or deb also installed.
- **Trace:**

  > src/mainImpl.ts (lines ~70-78) uses fs.existsSync on /usr/share/applications/<linuxDesktopName>.desktop as the only condition. The fix must decide whether the running build is the installed package. Do not change the snap branch or the non-Linux behavior. Where the uncertainty starts: whether to detect this by execPath, by an install-location marker, or by something in product.json, since rpm, deb and Flatpak layouts differ.
- **Open decisions:**
  - How should a build be recognized as the system-installed package: execPath under /usr/share/<applicationName>, a product.json marker, or another mechanism?
  - Should other layouts (Flatpak, custom install prefixes, symlinked launchers) keep the current behavior?

## Evidence

- **code:** src/mainImpl.ts lines 70-78: after the snap branch, app.setDesktopName(`${product.linuxDesktopName}.desktop`) runs whenever fs.existsSync of the /usr/share/applications path is true. The check never compares process.execPath with the installed package location.
- **no fix:** Current main has no guard for the archive-build case. There are no comments and no linked fix PR in microsoft/vscode; the only cross-reference is a downstream workaround in wpilibsuite/WPILibInstaller-Avalonia.
