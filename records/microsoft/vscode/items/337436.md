# Issue #337436 — Automation sessions briefly flicker in the Sessions list

[https://github.com/microsoft/vscode/issues/337436](https://github.com/microsoft/vscode/issues/337436)

## Summary

Fresh, clearly-described bug already scheduled for the 1.140.0 milestone — a real version milestone, so per the hard keep-open rule this must stay open regardless of other evidence; a maintainer has already committed to fixing it in that release.

## Change summary

Automation sessions briefly flash into the Sessions list and disappear when the Agents window opens or the local Agent Host restarts.

## Best solution

Ensure the filtered-out automation sessions never render transiently during Agent Host initialization/restart — likely a race in how sessionsList.ts / agentHostAutomationStore.ts populate the list before the automation-filter state is settled.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/agentHostAutomationStore.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/localAgentHostSessionsProvider.ts`
- **Validation:** A test (or manual repro per the issue's steps) confirming that during Agent Host restart / Agents window init, sessions that should be filtered as automations never appear transiently in the rendered sessions list.
- **Behavior:**

  > When the Agents window opens or the local Agent Host restarts, automation sessions that should be excluded from the main Sessions list must never appear there, even momentarily. Today they flash in for 1-2 seconds before being filtered out, causing visible flicker. Acceptance: repeating the issue's repro (open a repo with non-archived automations, run 'Developer: Restart Local Agent Host', watch the list) shows no flicker.
- **Trace:**

  > The Sessions list (src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts) renders a dedicated automations section (AUTOMATIONS_SECTION_ID) and reads automation state via derived observables from IAutomationService and automationSessions; the underlying session data during Agent Host restart flows through agentHostAutomationStore.ts and localAgentHostSessionsProvider.ts. The likely cause is that the general/non-automation session list is populated before the automation-owned sessions are filtered out of it, so they render briefly until the filter catches up. Trace not yet run against actual restart timing; boundary: don't change how automation sessions are displayed within their own section, only prevent them from transiently appearing in the non-automation list during init/restart.
- **Open decisions:**
  - Should the sessions list wait for automation filtering state to be ready before first render (delay-until-ready), or should filtering be applied synchronously/optimistically as soon as any session data arrives, to decide the right fix approach for the observable ordering?
