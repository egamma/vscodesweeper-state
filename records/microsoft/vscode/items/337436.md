# Issue #337436 — Automation sessions briefly flicker in the Sessions list

[https://github.com/microsoft/vscode/issues/337436](https://github.com/microsoft/vscode/issues/337436)

## Summary

Confirmed in source: automation-session visibility is derived from two independently-resolved async sources (the session listing and the Agent Host automation catalogue subscription), so a session can briefly surface as non-automation before the catalogue settles and flags it, causing the reported flicker — this is a real, still-open bug.

## Change summary

Automation sessions briefly appear and then disappear from the Sessions list during Agents-window init and Agent Host restart.

## Best solution

Gate automation-session visibility in localAgentHostSessionsProvider.ts on the automation catalogue's readiness (`catalogueState`), similar to the existing `authenticationPending` barrier for the first session listing, so a session's automation membership is known before it's ever surfaced.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/providers/agentHost/browser/localAgentHostSessionsProvider.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/agentHostAutomationStore.ts`
- **Validation:** Extend the existing test 'derives automation provenance from the authoritative host catalogue' (localAgentHostSessionsProvider.test.ts) to assert that a session which the catalogue will later mark as automation is never returned as non-automation from getSessions() before the catalogue settles — i.e. no transient unmarked state is observable.
- **Behavior:**

  > A session that belongs to an automation run must never be shown in the main Sessions list, including during the brief window while the Agents window is initializing or the local Agent Host is restarting. Today it can flash into view for 1-2 seconds before disappearing. Acceptance: opening the Agents window or restarting the local Agent Host with existing automation sessions produces no visible flicker, and a test confirms the session is never surfaced unmarked before the catalogue resolves.
- **Trace:**

  > localAgentHostSessionsProvider.ts's getSessions() (line 275) relies on `_automationSessionResources`, rebuilt only once `this.automations.runs` (agentHostAutomationStore.ts line 115, fed by an AHP catalogue subscription with its own `catalogueState` readiness) resolves — independently of the session-list fetch triggered via `_refreshSessions()` off `authenticationPending` (lines 237-252) and `onAgentHostStart` (lines 225-231). The existing test at localAgentHostSessionsProvider.test.ts:3534 shows a session returned unmarked by getSessions() before the catalogue arrives, then flipped after. The boundary: do not change how `isAutomation` is computed once the catalogue has resolved, and do not alter behavior for sessions that are never part of an automation. Where the uncertainty starts: whether to withhold the entire session list until `catalogueState !== 'loading'` (adds latency to the already-optimized eager cache load commented at lines 168-172) or only withhold sessions whose automation membership is not yet known, and whether the same gate should re-apply on every Agent Host restart.
- **Open decisions:**
  - Should the whole Sessions list wait for the automation catalogue to settle before showing any session, or should only sessions of uncertain automation status be withheld?
  - Should this gating re-apply on every Agent Host restart (not just first load), given the restart case is explicitly called out in the report?
  - What should happen if the catalogue subscription errors (`catalogueState: 'error'`) — show all sessions anyway, or keep withholding?

## Evidence

- **race condition traced:** localAgentHostSessionsProvider.ts getSessions() (line 275) calls syncAutomationSessionMarkers() (line 281), which marks a session as automation only if its resource is in `_automationSessionResources` — a set rebuilt from `this.automations.runs`, itself derived (agentHostAutomationStore.ts line 115) from a separate AHP catalogue subscription that resolves independently of the session list fetch triggered in the constructor (lines 237-252, 225-231).
- **existing test demonstrates exact sequence:** src/vs/sessions/contrib/providers/agentHost/test/browser/localAgentHostSessionsProvider.test.ts:3534 'derives automation provenance from the authoritative host catalogue' calls provider.getSessions() before agentHost.setAutomationCatalog(...), gets back the session unmarked (isAutomation=false), then only after the catalogue call does isAutomation flip to true (and later false again on delete) — this is precisely the show-then-hide flicker reported.
- **readiness signal already exists:** agentHostAutomationStore.ts exposes `catalogueState: 'loading' | 'ready' | 'error'` (derived from `_catalog.verifiedValue`), which is not currently consulted when building/returning sessions in localAgentHostSessionsProvider.ts.
