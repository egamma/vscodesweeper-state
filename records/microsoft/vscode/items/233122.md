# Issue #233122 — Add support for adding `svg` as attachments

[https://github.com/microsoft/vscode/issues/233122](https://github.com/microsoft/vscode/issues/233122)

## Summary

This team-authored, Backlog-accepted request remains necessary: current main excludes SVG from supported image attachments and instead marks an attached `.svg` file as fully omitted. The issue must stay open because no factual close applies, and the thread shows maintainer scheduling intent rather than abandonment.

## Change summary

Allow SVG files to be added to panel chat as image attachments.

## Best solution

Define consistent SVG attachment semantics across panel chat and language-model providers, including whether SVG is preserved as `image/svg+xml` or safely rasterized for providers that only accept raster formats, while retaining explicit access to SVG source when needed.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/model/chatModel.ts`, `src/vs/workbench/contrib/chat/common/languageModels.ts`, `src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentResolveService.ts`, `src/vs/workbench/contrib/chat/browser/chatImageUtils.ts`, `src/vs/workbench/contrib/chat/test/browser/chatAttachmentResolveService.test.ts`
- **Validation:** Add attachment resolver coverage showing that selecting an `.svg` produces the decided image representation rather than a fully omitted file entry, plus an image-processing test confirming the bytes and MIME type delivered to the model-facing path.
- **Behavior:**

  > Users can select or drop an SVG into panel chat and see it accepted as an image attachment rather than fully omitted. The model receives a usable representation with the fidelity and fallback behavior chosen by the maintainer. Existing PNG, JPEG, GIF, and WebP attachment behavior remains unchanged, and users can still intentionally provide SVG source as textual file context where that workflow is supported.
- **Trace:**

  > `CHAT_ATTACHABLE_IMAGE_MIME_TYPES` in `src/vs/workbench/contrib/chat/common/model/chatModel.ts` drives the extension check in `ChatAttachmentResolveService.resolveImageEditorAttachContext`; SVG is absent. The fallback in `resolveResourceAttachContext` explicitly marks `.svg` as `OmittedState.Full`. `resizeImage` in `src/vs/workbench/contrib/chat/browser/chatImageUtils.ts` may return small images unchanged, while the model-facing MIME enums currently contain only raster formats, so adding SVG to the extension map alone would not establish compatible provider behavior. Preserve all existing raster-image handling and do not conflate this request with https://github.com/microsoft/vscode/issues/285334, whose reporter wants SVG source treated as text.
- **Open decisions:**
  - Should an attached SVG reach capable models as native `image/svg+xml`, or should VS Code always rasterize it to a supported image format before model handoff?
  - When native SVG is unavailable for the selected model, should attachment transparently use a raster fallback or remain unsupported with an explicit user-facing explanation?

## Evidence

- **current source gap:** `CHAT_ATTACHABLE_IMAGE_MIME_TYPES` in `src/vs/workbench/contrib/chat/common/model/chatModel.ts` includes PNG, JPEG, GIF, and WebP but not SVG, so `resolveImageEditorAttachContext` cannot classify `.svg` as an image.
- **current fallback behavior:** `ChatAttachmentResolveService.resolveResourceAttachContext` in `src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentResolveService.ts` explicitly assigns `OmittedState.Full` to `.svg`, confirming that current main does not deliver its contents as an image attachment.
- **provider boundary:** `ChatImageMimeType` in `src/vs/workbench/contrib/chat/common/languageModels.ts` and `ByokLmImageMimeType` in `src/vs/platform/agentHost/common/agentHostByokLm.ts` contain raster formats only; supporting SVG therefore requires a product decision about native forwarding versus normalization, not only adding an extension to a list.
