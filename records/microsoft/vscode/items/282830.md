# Issue #282830 — Link to edit a global setting from a non-default profile opens wrong settings.json file

[https://github.com/microsoft/vscode/issues/282830](https://github.com/microsoft/vscode/issues/282830)

## Summary

Keep open: the settings editor still distinguishes application-scoped settings from settings explicitly applied to all profiles when choosing the JSON file to open. The existing application-settings command provides a workaround, but does not satisfy the request for the setting's own edit link to open its effective configuration file.

## Change summary

Make “Edit in settings.json” open the default profile's settings file for settings explicitly applied to all profiles.

## Best solution

Have the per-setting JSON edit link respect the effective application-level target for settings applied to all profiles, while preserving active-profile navigation for ordinary user settings and existing workspace and remote targets.

## Evidence

- **Current edit-link path:** src/vs/workbench/contrib/preferences/browser/settingsTree.ts:1247–1252 emits the setting key from SettingComplexRenderer. settingsEditor2.ts:1209–1211 passes that key to openSettingsFile with revealSetting and edit enabled.
- **Remaining navigation gap:** src/vs/workbench/contrib/preferences/browser/settingsEditor2.ts:1040–1052 selects openApplicationSettings only when the registered configuration scope belongs to APPLICATION_SCOPES; it does not consult isSettingAppliedForAllProfiles. Other local-user settings go to openUserSettings, even when explicitly shared across profiles.
- **Effective scope already recognized elsewhere:** src/vs/workbench/contrib/preferences/browser/settingsTreeModels.ts:298–307 routes inspection to ConfigurationTarget.APPLICATION for a local-user setting when isSettingAppliedForAllProfiles is true in a non-default profile. This distinction is absent from the edit-link navigation.
- **Existing capability is only a workaround:** workbench.action.openApplicationSettingsJson is registered in src/vs/workbench/contrib/preferences/browser/preferences.contribution.ts:294. PreferencesService.openApplicationSettings opens defaultProfile.settingsResource, whereas openUserSettings opens currentProfile.settingsResource (preferencesService.ts:115–116, 282–295). The command opens the correct file manually but does not correct the per-setting link.
