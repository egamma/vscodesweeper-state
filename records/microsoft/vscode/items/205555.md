# Issue #205555 — Add support to show the extension name from which inline suggestion is displayed in hover UI

[https://github.com/microsoft/vscode/issues/205555](https://github.com/microsoft/vscode/issues/205555)

## Summary

Keep this accepted, community-supported request open: the current ghost-text hover does not automatically identify the supplying extension. Provider-specific commands and Ansible's attribution comment are workarounds, not equivalent built-in coverage.

## Change summary

Identify the extension supplying the currently displayed inline suggestion when users cycle through suggestions in the hover UI.

## Best solution

Provide consistent extension attribution in the inline-suggestion hover that updates with the selected suggestion, without requiring extension-authored commands or inserting attribution into suggested code. Settle how that identity appears alongside existing toolbar actions and optional provider branding.

- **Reason:** Consistent attribution makes the shared completion UI understandable when multiple extensions contribute suggestions.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/inlineCompletions/browser/hintsWidget/inlineCompletionsHintsWidget.ts`, `src/vs/editor/contrib/inlineCompletions/browser/hintsWidget/hoverParticipant.ts`, `src/vs/editor/contrib/inlineCompletions/browser/model/inlineCompletionsModel.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`
- **Validation:** Use two inline-completion providers with distinct extension names and no attribution commands. Open the ghost-text hover and cycle Next/Previous: the displayed identity must follow the selected suggestion, including providers without displayName metadata. Verify existing commands, navigation, acceptance text, keyboard access and the always-visible toolbar remain correct.
- **Behavior:**

  > When multiple extensions provide inline suggestions, users can identify which extension supplied the suggestion currently displayed in the editor from its hover UI. Attribution follows Next/Previous selection and does not depend on extensions adding commands or comments to the suggested code. Providers without custom display-name metadata must remain identifiable. Existing acceptance and provider-specific command behavior must remain unchanged.
- **Trace:**

  > InlineCompletionsModel.activeCommands derives commands from selectedInlineCompletion.source.inlineSuggestions; InlineSuggestionHintsContentWidget renders navigation, counts and optional commands, but has no extension-attribution input. hoverParticipant.ts constructs the same widget for the hover surface. ExtHostLanguageFeatures.registerInlineCompletionsProvider forwards the extension identifier and optional metadata.displayName separately, while InlineSuggestionGutterMenuData.fromInlineSuggestion already uses that optional displayName for the distinct inline-edits gutter menu. The remaining design boundary is how extension identity is presented in the existing hover and distinguished from provider branding; avoid changing suggestion text, provider ordering or command ownership. https://github.com/microsoft/vscode/issues/169336 resolved command coexistence, and https://github.com/ansible/vscode-ansible/pull/1117 supplies an extension-local ghost-text workaround; neither implements this shared attribution surface.
- **Open decisions:**
  - Should extension attribution be persistently visible in the hover toolbar or appear in a dedicated hover detail section?
  - When a provider supplies a custom displayName, should the hover show both that branding and the owning extension name, or only the extension name?
