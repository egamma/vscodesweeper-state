# Issue #344361 — GHCP chats not connecting when opening project 

[https://github.com/microsoft/vscode/issues/344361](https://github.com/microsoft/vscode/issues/344361)

## Summary

Keep open: the report identifies a concrete startup race where a managed OTel policy restart interrupts connecting chats and leaves them failed. Current main has automatic transport recovery, but recovery of the interrupted chat-loading operation remains unconfirmed; the supplied timing and logs suffice to retest.

## Change summary

Chats interrupted by an enterprise OTel policy-triggered Agent Host restart should recover after the host reconnects instead of remaining at a transport error.

## Best solution

Ensure interrupted chat loading recovers after a successful local Agent Host reconnection while preserving enterprise policy enforcement, conversation identity, history, and drafts. Treat restart-free OTel reconfiguration as related work rather than assuming it already resolves this recovery failure.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/electron-main/electronAgentHostStarter.ts`, `src/vs/platform/agentHost/electron-browser/localAgentHostService.ts`, `src/vs/platform/agentHost/browser/agentHostProtocolClient.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts`
- **Validation:** Delay a settled managed OTel policy response until an existing chat is awaiting its initial session or chat snapshot, then allow the policy-triggered host restart. After reconnection, verify that the same open chat loads its history and accepts input without reopening the tab, preserves its draft, and does not duplicate turns; verify that the replacement host applies the managed policy.
- **Behavior:**

  > Opening a project with saved Agent Host chats can overlap late arrival of enterprise OTel policy. If the resulting host restart interrupts chat loading, those chats should recover when the host becomes available instead of retaining a terminal transport error. Acceptance checks must cover interrupted session and chat hydration, retained conversation identity and drafts, and continued enforcement of the settled enterprise policy.
- **Trace:**

  > ElectronAgentHostStarter restarts the shared host when AgentHostOTelPolicyState accepts a policy change requiring replacement. LocalAgentHostServiceClient configures automatic protocol reconnection, while AgentHostProtocolClient._handleTransportClose rejects in-flight requests with a transport-lost error. AgentHostSessionHandler.provideChatSessionContent waits for session/chat subscriptions and materializes hydration errors as historyLoadError; _whenSubscriptionHydrated settles on onDidError. The unresolved boundary is whether restored subscriptions also recover a chat whose initial content load already completed with an error. Reproduce that sequence before choosing the implementation boundary; preserve policy readiness, fail-closed behavior, subscription ownership, and cancellation semantics. https://github.com/microsoft/vscode/issues/340967 concerns eliminating OTel restarts, while https://github.com/microsoft/vscode/pull/338623 introduced the late-policy replacement mechanism rather than proving interrupted-chat recovery.

## Evidence

- **Concrete startup trigger:** https://github.com/microsoft/vscode/issues/344361 reports Code 1.143.1 on Windows: Agent Host starts at 09:56:13.865, receives an enterprise OTel policy restart at 09:56:22.990, and starts again at 09:56:25.394. Chats connecting during that interval reportedly remain at 'Transport lost'; there are no confirming comments.
- **Restart remains on current main:** src/vs/platform/agentHost/electron-main/electronAgentHostStarter.ts handles AgentHostOTelPolicyIpcChannel by updating AgentHostOTelPolicyState, notifying windows, and firing _onRequestRestart when settled policy requires replacement. This matches the reported restart log and is VS Code-owned behavior, not evidence of third-party extension failure.
- **Transport recovery does not prove chat-load recovery:** src/vs/platform/agentHost/electron-browser/localAgentHostService.ts enables automatic local reconnection and emits onAgentHostStart after connection recovery. In src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:937-989, _handleTransportClose rejects in-flight requests with transportLostError before scheduling reconnection.
- **Relevant chat-loading path:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:1724-1920 waits for session/chat hydration and converts subscription failures into historyLoadError and a visible failed-load response. _whenSubscriptionHydrated also settles on subscription errors. These paths make the report plausible, but the complete reconnect-to-editor recovery sequence was not conclusively reproduced.

It fixes https://github.com/microsoft/vscode/issues/338630, concerning unapplied exporter settings and repeated Local reload prompts, not the reported failure to recover connecting chats. It is not a substantiated fix for this report.
