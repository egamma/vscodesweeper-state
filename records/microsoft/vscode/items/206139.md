# Issue #206139 — [Testing API Feature] Add a new api in TestRun to reset test item to its initial state (unknown, not run)

[https://github.com/microsoft/vscode/issues/206139](https://github.com/microsoft/vscode/issues/206139)

## Summary

The per-item reset capability is still missing from the Testing API. Existing invalidation and global result-clearing behavior do not cover the request, and the linked Jest change documents a concrete downstream workaround.

## Change summary

Allow a testing extension to return an individual test item's displayed result to unknown/not run without clearing unrelated results.

## Best solution

Define a supported per-item reset contract in the Testing API, including its interaction with previous runs, then implement it consistently in result aggregation and persistence. Preserve unrelated tests and controllers rather than relying on global result clearing.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTesting.ts`, `src/vs/workbench/contrib/testing/common/testResult.ts`, `src/vs/workbench/contrib/testing/common/testResultService.ts`, `src/vs/workbench/contrib/testing/test/common/testResultService.test.ts`
- **Validation:** Add result-service tests covering a previously passed or failed test reset to unknown, fallback to older results, unrelated tests remaining unchanged, and the chosen descendant/history semantics. Run the targeted testResultService suite; manually verify the suite-error/recreated-child scenario described in the linked Jest PR.
- **Behavior:**

  > A testing extension needs to return a selected test item to unknown/not run after an earlier result is no longer an accurate representation. Deleting and recreating the same item and invalidating its results currently leave the old outcome available for display. Acceptance should demonstrate that the reset item no longer displays that cached outcome while unrelated test results remain intact. The contract must specify how reset interacts with historical runs and descendants.
- **Trace:**

  > The stable TestRun interface in src/vscode-dts/vscode.d.ts exposes no reset operation. In src/vs/workbench/api/common/extHostTesting.ts, invalidateTestResults delegates to retirement; LiveTestResult.markRetired in src/vs/workbench/contrib/testing/common/testResult.ts preserves the outcome. TestResultService.getStateById in src/vs/workbench/contrib/testing/common/testResultService.ts skips Unset results and falls back to older runs, so introducing an unset outcome alone would not establish the requested display semantics. The existing testing.clearTestResults command clears completed runs globally and must not be treated as a selective solution. https://github.com/jest-community/vscode-jest/pull/1165 documents a downstream workaround, not an implementation of the requested API. Preserve ordinary run-state reporting and unrelated controllers' results; uncertainty starts at the public reset contract and its historical-result semantics.
- **Open decisions:**
  - Should reset affect only the item's state in the current TestRun, or also prevent previous runs from supplying the displayed outcome?
  - Should resetting a suite apply only to that item or recursively to its descendants?

## Evidence

- **Public API gap:** src/vscode-dts/vscode.d.ts:18650 onward defines TestRun state methods for queued, running, skipped, failed, errored, and passed outcomes, but no unknown/reset method. TestRun.end() is not an operation for clearing a selected item's previously recorded result.
- **Invalidation preserves outcomes:** TestController.invalidateTestResults() is documented as marking results outdated in src/vscode-dts/vscode.d.ts:18559–18575. Its implementation in src/vs/workbench/api/common/extHostTesting.ts calls $markTestRetired; LiveTestResult.markRetired in src/vs/workbench/contrib/testing/common/testResult.ts sets retired=true without clearing recorded state.
- **Existing command is broader than requested:** ClearTestResultsAction in src/vs/workbench/contrib/testing/browser/testExplorerActions.ts registers testing.clearTestResults and calls ITestResultService.clear() without an item argument. In src/vs/workbench/contrib/testing/common/testResultService.ts, clear() removes all completed results while retaining active runs; it is not a selective test-item reset.
- **Historical fallback matters:** TestResultService.getStateById in src/vs/workbench/contrib/testing/common/testResultService.ts:125–134 skips results whose computedState is Unset and continues searching older results. Merely assigning an unset state in a new run would therefore not reliably suppress a cached previous outcome.
- **Downstream demand, not a core fix:** https://github.com/jest-community/vscode-jest/pull/1165 was merged on 2024-08-12. Its description explicitly links https://github.com/microsoft/vscode/issues/206139, explains that recreated tests retain cached results after suite compilation/dependency errors, and works around the missing API by propagating the suite status to child tests.
- **Canonical and fix search:** Repository issue searches for testing reset, clear, unknown, invalidateTestResults, and TestRun reset found no verified open canonical owning this capability. Available git history searches found no fixing commit for this request; the supplied keyword candidates do not establish an equivalent reset API.
