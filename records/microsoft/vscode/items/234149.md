# Issue #234149 — Allow extensions to augment an existing language's configuration, such as surroundingPairs

[https://github.com/microsoft/vscode/issues/234149](https://github.com/microsoft/vscode/issues/234149)

## Summary

Keep open: current source still replaces individual language-configuration fields rather than augmenting their arrays, and the extension API cannot convey surroundingPairs. Markdown now includes dollar-sign surrounding pairs, but that solves the motivating example rather than the requested extension capability.

## Change summary

Allow extensions to add language-configuration entries, such as surrounding pairs, without replacing an existing language's entries.

## Best solution

Provide an explicitly defined augmentation contract for language-configuration contributions that preserves existing replacement behavior. Settle its supported fields, precedence, and disposal semantics before implementing it across configuration loading and the extension API.

Add an extension-host bridge check that the supported augmentation data reaches the editor. Manually verify in Markdown that both existing and extension-added pairs surround a selection. These checks were not executed during this read-only review.
- **Behavior:**

  > An extension can contribute additional surrounding pairs to an existing language without reproducing or replacing that language's baseline pairs. Selecting Markdown text and typing an extension-added opening delimiter surrounds the selection, while the original Markdown delimiters continue to work. Removing the extension's contribution restores the remaining configuration. Existing callers that intentionally replace configuration fields must retain their behavior; acceptance also includes overlapping contributions according to the agreed precedence contract.
- **Trace:**

  > ComposedLanguageConfiguration._resolve and combineLanguageConfigurations in src/vs/editor/common/languages/languageConfigurationRegistry.ts resolve contributions by priority and order, replacing each supplied field wholesale. Declarative configurations loaded by LanguageConfigurationFileHandler in src/vs/workbench/contrib/codeEditor/common/languageConfigurationExtensionPoint.ts enter that same pipeline. The runtime API has a separate limitation: LanguageConfiguration in src/vscode-dts/vscode.d.ts lacks surroundingPairs, ExtHostLanguageFeatures.setLanguageConfiguration does not serialize it, and MainThreadLanguageFeatures.$setLanguageConfiguration leaves it undefined. CharacterPairSupport prefers explicit surroundingPairs over its autoClosingPairs fallback, explaining the later comment's Markdown result. The uncertainty starts at the public augmentation contract, not at whether the gap exists; preserve existing replacement callers and keep embedded-language selection behavior outside this request. https://github.com/microsoft/vscode/pull/233981 supplies the motivating dollar pair directly but does not provide augmentation, and https://github.com/microsoft/vscode/issues/133397 tracks a distinct embedded-language problem.
- **Open decisions:**
  - Should additive contributions be exposed through declarative language configuration, the runtime extension API, or both?
  - Which configuration fields support augmentation initially: surroundingPairs only, paired-character arrays more generally, or other rule arrays too?
  - When additive contributions overlap existing entries, what precedence and duplicate handling should users observe, including after a contribution is disposed?
