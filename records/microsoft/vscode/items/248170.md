Keep open: the latest controlled reproduction identifies an Electron/BoringSSL certificate-validation difference, and current MCP requests still use the affected Node fetch path. This issue already owns the SSE and Streamable HTTP reports; neither a verified fix nor an older same-symptom canonical was established.

## Change summary

Allow HTTPS MCP connections to authenticate successfully using a system-trusted .NET development certificate without disabling TLS verification.

## Best solution

Resolve the trusted-leaf certificate validation difference in Electron's Node/BoringSSL integration and verify its adoption on VS Code's MCP request path. Preserve rejection of untrusted certificates rather than recommending a global TLS-verification bypass.

## Evidence

- **Controlled upstream reproduction:** https://github.com/microsoft/vscode/issues/248170#issuecomment-5769577367 reports testing otherwise identical certificates with and without keyCertSign: standalone Node/OpenSSL accepted both, while Electron 43.6.0/BoringSSL rejected the certificate without that usage with UNABLE_TO_VERIFY_LEAF_SIGNATURE. This directly explains rejection of the system-trusted, non-CA .NET development certificate.
- **Current MCP request path:** At checkout e3c2316227ee9a4b24449b779409e3ff4d0126a9, src/vs/workbench/api/node/extHostMcpNode.ts:158-185 delegates ordinary HTTPS requests to McpHTTPHandle._fetchInternal. In src/vs/workbench/api/common/extHostMcp.ts:935-938, requests explicitly use redirect: 'manual'; _fetchInternal at lines 998-999 calls global fetch.
- **Existing settings do not cover the remaining failure:** src/vs/platform/request/common/request.ts already defaults systemCertificatesNodeDefault to true. However, src/vs/workbench/api/node/proxyResolver.ts:170-212 routes manual-redirect requests through @vscode/proxy-agent's patched Node fetch even when http.electronFetch is enabled. Consequently, switching the general fetch setting does not move these MCP requests onto the Chromium certificate-validation path.
- **Related upstream change is not proof of resolution:** https://github.com/dotnet/aspnetcore/issues/64261 is closed and addresses missing SKI/AKI extensions causing ambiguous certificate selection when multiple trusted certificates share a subject. The September 2026 reproduction identifies a separate keyCertSign trust requirement, so that certificate-generation change does not establish that this issue is fixed.
- **This issue is already the consolidation target:** https://github.com/microsoft/vscode/issues/248245 is closed as a duplicate, with https://github.com/microsoft/vscode/issues/248245#issuecomment-2863407150 pointing to this issue. It contributes the Streamable HTTP manifestation of the same trusted-certificate connection failure, not an open canonical to close against.
- **Canonical search and review limits:** Read-only searches for open MCP certificate, certificate-title, and BoringSSL issues did not establish an older report with the same observable symptom. The older https://github.com/microsoft/vscode/issues/185135 concerns CLI extension installation behind a corporate proxy, not the demonstrated trusted .NET leaf-certificate failure. No runtime reproduction was performed, and the checkout's shallow history did not provide a verifiable fixing commit.
- **TLS safety boundary:** The thread reports NODE_TLS_REJECT_UNAUTHORIZED=0 as a workaround, but maintainers explicitly warn that it disables TLS authentication globally. That bypass is not an acceptable resolution for a connection that should succeed through existing certificate trust.
