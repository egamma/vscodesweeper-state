# Issue #341659 — Stop "Agent host session" spam in git log --all

[https://github.com/microsoft/vscode/issues/341659](https://github.com/microsoft/vscode/issues/341659)

## Summary

Keep open: current Agent Host code still creates checkpoint commits reachable through git log --all, and the existing checkpoint setting does not govern this capture path. Multiple commenters confirm the friction; no verified canonical owns this specific request.

## Change summary

Allow users to prevent or safely remove Agent Host checkpoint commits that clutter all-ref Git history and consume repository storage.

## Best solution

Make Agent Host checkpoint persistence controllable without requiring manual ref deletion or switching harnesses. Decide the supported opt-out and cleanup behavior, including how checkpoint-dependent comparison and restoration behave afterward.

- **Likely files:** `src/vs/platform/agentHost/node/agentHostCheckpointService.ts`, `src/vs/platform/agentHost/node/chatContributions/checkpointAndChangeset/checkpointAndChangesetContribution.ts`, `src/vs/platform/agentHost/node/agentSideEffects.ts`, `src/vs/platform/agentHost/common/agentHostSchema.ts`, `src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts`, `src/vs/platform/agentHost/test/node/agentHostCheckpointService.test.ts`
- **Validation:** In a disposable Git repository, record refs and HEAD, use an Agent Host Copilot session for two completed turns under the chosen opt-out, and verify that no new Agent Host checkpoint commits become reachable through git log --all. Check the agreed comparison/restoration behavior, normal capture when enabled, and cleanup without removing user branches, tags, or another session's refs.
- **Behavior:**

  > Using Agent Host Copilot currently creates synthetic checkpoint commits visible in all-ref Git history, even though they are not commits on the user's branch. Users need a supported way to stop this persistence and understand how existing checkpoints can be removed. Acceptance must cover repeated turns, persistence of the selected preference, and clearly defined comparison/restoration behavior when checkpoint storage is unavailable. Cleanup must leave user history and unrelated sessions intact.
- **Trace:**

  > AgentSideEffects begins captureTurnStartCheckpoint before provider dispatch; CheckpointAndChangesetContribution invokes captureTurnCheckpoint after successful or terminal-error turns. AgentHostCheckpointService writes the reported messages through AgentHostGitService.commitTree and anchors the resulting chain under refs/agents; CopilotAgent also captures a baseline during materialization. These are host-owned snapshots, not agent shell commits or user-branch commits. The registered chat.checkpoints.enabled setting is not consulted on these capture paths, and deletion cleanup is tied to recorded session/chat storage. Preserve ordinary branch/index behavior and correct change attribution; indiscriminate ref deletion is not a supported replacement for those contracts. https://github.com/microsoft/vscode/issues/342038 corroborates the setting gap, while https://github.com/microsoft/vscode/issues/339363 is related review-UX work rather than a verified duplicate. Uncertainty begins at the user-facing persistence, cleanup, and fallback contract.
- **Open decisions:**
  - Should stopping repository checkpoint commits disable checkpoint-dependent comparison/restoration, or should those capabilities remain available through storage outside the user's repository?
  - Should the supported control prevent only future captures, or also offer explicit removal of existing checkpoints with a clear statement of the history capabilities that will be lost?

## Evidence
