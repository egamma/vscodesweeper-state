# Issue #173888 — Could we have vscode.open and vscode.diff support customize open mode?

[https://github.com/microsoft/vscode/issues/173888](https://github.com/microsoft/vscode/issues/173888)

## Summary

Keep this accepted API request open: editor options control preview and placement, but do not let an extension choose the mouse gesture that invokes a tree item's command. The request has 22 upvotes and was explicitly promoted to Backlog; no verified older canonical or completed implementation was found.

## Change summary

Allow extension tree items opening editors with vscode.open or vscode.diff to specify an activation gesture independently of workbench.list.openMode.

## Best solution

Define an extension-tree activation contract that supports the agreed gesture overrides while preserving existing behavior when no override is provided. API owners should settle its scope and supported gestures before implementation, since command execution currently happens after the tree has already selected the opening gesture.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/browser/parts/views/treeView.ts`, `src/vs/platform/list/browser/listService.ts`, `src/vs/workbench/api/common/extHostApiCommands.ts`
- **Validation:** Using a sample extension tree with vscode.open and vscode.diff items, exercise the agreed activation override under both singleClick and doubleClick global settings. Verify the configured gesture invokes the intended command, unspecified items retain global behavior, and keyboard activation, preview/pinning, and opening to the side remain unchanged.
- **Behavior:**

  > An extension needs to choose the mouse activation gesture for a tree item that opens an editor or diff without changing the user's global list opening setting. Preview-tab options alone do not meet this goal. Acceptance should exercise the agreed overrides with both global opening modes and both commands, while confirming that items without an override retain existing behavior. Existing keyboard activation and editor preview, pinning, and placement conventions must remain intact.
- **Trace:**

  > ResourceNavigator in src/vs/platform/list/browser/listService.ts determines mouse activation using its internal openOnSingleClick option or workbench.list.openMode before emitting onDidOpen. The custom tree in src/vs/workbench/browser/parts/views/treeView.ts resolves and executes TreeItem.command from that event, forwarding event context to the internal open/diff commands. Command registrations in src/vs/workbench/api/common/extHostApiCommands.ts and src/vs/workbench/browser/parts/editor/editorCommands.ts already support editor options, but those options operate after the activation decision. The public types in src/vscode-dts/vscode.d.ts expose no corresponding gesture override. The uncertainty is the public scope and supported gestures, not whether preview options already solve the request. Preserve default list behavior and unrelated built-in trees; https://github.com/microsoft/vscode/issues/141145 concerns preserving existing opening conventions, not this new contract.
- **Open decisions:**
  - Should activation overrides apply to individual TreeItems or to an entire extension TreeView?
  - Should the public contract support only single-click and double-click activation, or also higher click counts requested by the reporter?
