# Issue #334409 — Remote SSH: Copilot incorrectly requests external-file permission for workspace paths involving symlinks

[https://github.com/microsoft/vscode/issues/334409](https://github.com/microsoft/vscode/issues/334409)

## Summary

Traced a real gap in the workspace-external-file check: it resolves the full realpath of a requested file (including any symlink/bind-mount on the workspace root itself) but then compares that resolved path against the literal, unresolved workspace folder list, so a workspace opened through a symlinked or bind-mounted root always looks external. Existing tests only cover symlinks *inside* the workspace, not a symlinked workspace root, confirming this scenario is untested and unfixed.

## Change summary

Copilot's read_file tool wrongly prompts for external-file permission on files that are genuinely inside the workspace when the workspace root itself is reached through a symlink or bind mount (Remote SSH), and similarly for Windows directory junctions.

## Best solution

In extensions/copilot/src/extension/tools/node/toolUtils.ts, getWorkspaceFileExternalConfirmation should also resolve the workspace folder itself (not just the requested file) before containment-checking the resolved path, so a fully-resolved file path under a fully-resolved workspace root is recognized as internal; add a unit test in toolUtils.spec.ts where the workspace directory itself is a symlink to another location and a direct file inside it should not require confirmation.

## Evidence

- **containment check:** extensions/copilot/src/extension/tools/node/toolUtils.ts:287-304 getWorkspaceFileExternalConfirmation calls resolveRealPathForNonexistent(uri, workspaceFolder), which for an existing file just does a full fs realpath() (line 311) — this also resolves any symlink on the workspace root itself, not just below it.
- **mismatched comparison:** The resolved path is then checked with `getFolder(resolvedUri)` (toolUtils.ts:302), which compares against the literal configured workspace folder from WorkingDirectory.getFolder (extensions/copilot/src/platform/workspace/common/workingDirectory.ts:39-46) — if the workspace root is itself a symlink/bind mount, the resolved path never matches the unresolved folder, so `isInsideWorkspace` is false and confirmation is (incorrectly) required.
- **test gap:** extensions/copilot/src/extension/tools/node/test/toolUtils.spec.ts's `isExternalSymlinkedFile`/`isFileExternalAndNeedsConfirmation` suite (lines ~332-446) only tests symlinks *inside* the workspace (files or subdirectories), never a symlinked/bind-mounted workspace root — the reported scenario has no test coverage.
- **second report:** A second commenter (rotemdan) reports the same class of issue with Windows directory junctions used inside the workspace, and wants a setting to trust such links — a related but distinct ask worth tracking alongside the root cause.
