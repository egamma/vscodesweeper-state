# Issue #334409 — Remote SSH: Copilot incorrectly requests external-file permission for workspace paths involving symlinks

[https://github.com/microsoft/vscode/issues/334409](https://github.com/microsoft/vscode/issues/334409)

## Summary

Traced a real containment bug on main: the external-file check resolves the requested file's real path fully but then compares it against the workspace folder's *unresolved* URI, so a symlinked/bind-mounted workspace root produces a false external-file confirmation for files that are actually inside the workspace.

## Change summary

Over Remote SSH, Copilot's read_file tool asks for external-file permission for files that are actually inside the workspace, when the workspace root itself is a symlinked or bind-mounted path.

## Best solution

In getWorkspaceFileExternalConfirmation (extensions/copilot/src/extension/tools/node/toolUtils.ts), resolve the workspace folder's own real path (or otherwise normalize both sides consistently) before checking `getFolder(resolvedUri)`, so a symlinked workspace root doesn't make an in-workspace file look external.

- **Fix prompt:**

  > Bug: over Remote SSH, Copilot's read_file tool shows an 'Allow reading external files?' prompt for files that are actually inside the workspace, when the workspace root is opened through a symlink or bind mount (e.g. workspace path `/home/user/project` resolves via realpath to `/mnt/workspaces/project`). Root cause, traced in extensions/copilot/src/extension/tools/node/toolUtils.ts, function `getWorkspaceFileExternalConfirmation` (lines ~287-304): it computes `workspaceFolder = getFolder(uri)` (the workspace root URI as opened, unresolved), then fully resolves the target file's canonical path via `resolveRealPathForNonexistent` -> `realpath()`, producing e.g. `/mnt/workspaces/project/file.txt`. It then re-checks containment with `getFolder(resolvedUri)`, but `getFolder` (see workspaceService.ts `getWorkspaceFolder` and workingDirectory.ts `WorkingDirectory.getFolder`) only does a plain URI/string `isEqualOrParent` comparison against the *unresolved* workspace folder, so the resolved file path no longer matches the symlinked workspace root and the file is wrongly flagged as external. Fix boundary: normalize the workspace folder itself (e.g. realpath-resolve `workspaceFolder` once, or resolve `resolvedUri` relative to the resolved workspace root similarly to how `resolveRealPathForNonexistent` already handles `stopAt`) before the final `getFolder(resolvedUri)` containment check, so both sides of the comparison use consistent (either both raw or both resolved) paths. Do not change behavior for genuinely external symlinks (file's real target truly outside any workspace folder) — those must still require confirmation; the existing tests in toolUtils.spec.ts (lines 367-447) covering symlinked files/directories inside a real (non-symlinked) workspace root must keep passing. Add a new test where the workspace directory itself is a symlink to a separate real directory (skip the `fs.realpathSync` normalization used for `workspaceDirectory` in the existing `beforeEach`), place a plain file under it, and assert no confirmation is required when accessed via the symlinked workspace path.

## Evidence

- **containment check:** extensions/copilot/src/extension/tools/node/toolUtils.ts:287-304 `getWorkspaceFileExternalConfirmation`: `workspaceFolder = getFolder(uri)` uses the raw (possibly symlinked) workspace URI, then `resolvedUri = resolveRealPathForNonexistent(uri, workspaceFolder)` fully resolves the file's canonical path via `realpath()`, and finally `isInsideWorkspace = getFolder(resolvedUri) !== undefined` re-checks containment against the *unresolved* workspace folder URI — so if the workspace root is itself a symlink/bind mount, the resolved file path no longer falls under it.
- **workspace lookup:** extensions/copilot/src/platform/workspace/common/workspaceService.ts:129-130 `getWorkspaceFolder` and workingDirectory.ts:39-46 `WorkingDirectory.getFolder` both do a plain `isEqualOrParent` string/URI comparison against the workspace folder as opened — neither realpath-resolves the workspace root, so there is no normalization on that side.
- **test gap:** extensions/copilot/src/extension/tools/node/test/toolUtils.spec.ts:332-448 covers symlinked *files* and symlinked *parent directories* inside a real (non-symlinked) workspace root, but has no case where the workspace root URI itself differs from its realpath — exactly the reported scenario.
