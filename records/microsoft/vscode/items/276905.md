# Issue #276905 — Very hard to resize split panes

[https://github.com/microsoft/vscode/issues/276905](https://github.com/microsoft/vscode/issues/276905)

## Summary

The report remains relevant on current main: split-view sashes have only a 4px default hit target, while adjacent pane headers are draggable, matching the demonstrated failure to acquire the resize cursor and the resulting pane drag. The existing size setting is a useful workaround but does not resolve the reported regression in default behavior.

## Change summary

Resizing vertically or horizontally split panes is unreliable because the narrow resize target is frequently missed and the pane is dragged instead.

## Best solution

Restore reliable sash hit-testing and resize-cursor feedback near draggable pane headers without making adjacent controls or scrollbars harder to use; retain `workbench.sash.size` as an accessibility/customization option rather than requiring users to discover it.

- **Behavior:**

  > Vertical and horizontal split dividers must be easy to acquire with the default settings. Moving onto the divider should consistently show the resize cursor, and dragging there must resize rather than move the pane. Pane-header drag-and-drop and nearby scrollbar interaction must remain available. Increasing `workbench.sash.size` should continue to enlarge the configurable hit area.
- **Trace:**

  > The shared sash defaults to a 4px hit area in src/vs/base/browser/ui/sash/sash.css and src/vs/base/browser/ui/sash/sash.ts. Pane headers are independently draggable through `PaneDraggable` in src/vs/base/browser/ui/splitview/paneview.ts, matching the fallback behavior shown in the report when the sash is missed. `SashSettingsController` in src/vs/workbench/contrib/sash/browser/sash.ts can enlarge the target, but https://github.com/microsoft/vscode/issues/185770 records that large values interfere with scrollbars. The uncertainty starts at the desired interaction boundary: preserve the visible divider and pane drag behavior while deciding how much nearby pointer space should preferentially acquire the sash.
- **Open decisions:**

## Evidence

- **current source:** src/vs/base/browser/ui/sash/sash.css defines `--vscode-sash-size: 4px`, and src/vs/base/browser/ui/sash/sash.ts uses a matching default `globalSize = 4`, leaving a narrow pointer target on current main.
- **competing drag path:** src/vs/base/browser/ui/splitview/paneview.ts makes pane headers draggable and registers `dragstart` on them, explaining why a pointer just outside the sash can initiate pane movement instead of resizing.
