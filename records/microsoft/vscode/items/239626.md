# Issue #239626 — Multiple Linux VNC sessions VS code does not open individual sessions

[https://github.com/microsoft/vscode/issues/239626](https://github.com/microsoft/vscode/issues/239626)

## Summary

Keep this accepted, community-supported request open: current instance routing does not distinguish Linux displays. Separate user-data directories provide a workaround, but do not deliver display-aware launching with the user's usual configuration.

## Change summary

Allow VS Code launched from different Linux VNC sessions to open on each session's own display rather than forwarding every launch to the first instance.

## Best solution

Define display-aware Linux instance behavior in the desktop startup and launch services, including how simultaneous instances handle user data. Preserve ordinary same-display window reuse and provide predictable launching across VNC sessions.

## Plan brief

- **Likely files:** `src/vs/platform/environment/electron-main/environmentMainService.ts`, `src/vs/base/parts/ipc/node/ipc.net.ts`, `src/vs/code/electron-main/main.ts`, `src/vs/platform/launch/electron-main/launchMainService.ts`, `src/vs/platform/environment/node/argv.ts`
- **Validation:** On Linux under one user account, start two VNC/X sessions with different DISPLAY values. Launch Code in each using the agreed configuration and verify that each window appears on its invoking display; repeat with --new-window, file/folder arguments, and another launch on the first display. Verify same-display reuse, explicit --user-data-dir isolation, and the agreed settings/profile persistence behavior.
- **Behavior:**

  > Launching VS Code in a second Linux VNC session currently forwards the launch to an instance on the first session's display. The desired capability is to open on the invoking session's display while retaining predictable user configuration. Acceptance requires two simultaneous displays, correct placement from both sessions, and unchanged same-display reuse. Separate user-data directories are an existing workaround, not full coverage of the request.
- **Trace:**

  > EnvironmentMainService.mainIPCHandle in src/vs/platform/environment/electron-main/environmentMainService.ts calls createStaticIPCHandle in src/vs/base/parts/ipc/node/ipc.net.ts without a display identifier. CodeMain.claimInstance in src/vs/code/electron-main/main.ts forwards a second launch to the existing process on socket collision and terminates the caller. LaunchMainService.startOpenWindow in src/vs/platform/launch/electron-main/launchMainService.ts performs window operations in that existing process, even for --new-window. Source inspection establishes the routing boundary, but it does not establish safe concurrent access to one user-data directory or validate Electron behavior across display servers. Preserve same-display reuse, existing explicit instance isolation, and non-Linux behavior. Historical same-symptom reports https://github.com/microsoft/vscode/issues/57843 and https://github.com/microsoft/vscode/issues/103772 are closed, so this accepted request remains necessary.
- **Open decisions:**
  - Should Linux launches automatically select an instance by the invoking display, or should display-aware instance selection be explicitly enabled?
  - Should simultaneous display sessions share the normal user-data/profile state, or use isolated state, and what settings persistence should users observe across those sessions?
