# Issue #329764 — [regression] GitHub Copilot chat up arrow deletes current chat content.

[https://github.com/microsoft/vscode/issues/329764](https://github.com/microsoft/vscode/issues/329764)

## Summary

Confirmed on main: the built-in `history.showPrevious`/`history.showNext` keybinding `when` clause no longer includes `!isComposing` (src/vs/platform/history/browser/contextScopedHistoryWidget.ts:114-118, 129-133), and the removal-matching logic in keybindingResolver.ts only tolerates the default `when` becoming *more* specific over time, not less — so users who unbound Up/Down with the old (more specific) `when` clause silently get the default binding reactivated.

## Change summary

A previously-working `-history.showPrevious`/`-history.showNext` keybinding override (with `!isComposing` in its `when`) no longer suppresses the built-in Up/Down chat-history navigation after the default `when` clause dropped that condition, so Up arrow again overwrites in-progress chat input.

## Best solution

A maintainer needs to decide whether to restore `!isComposing` to the default `when` clause in contextScopedHistoryWidget.ts (undoing the apparent simplification) or to generalize `KeybindingResolver._isTargetedForRemoval`/`whenIsEntirelyIncluded` so that a *removal* rule still matches when the default's `when` clause becomes strictly less restrictive, not just more restrictive as fixed for https://github.com/microsoft/vscode/issues/293802 — either fix is a keybinding-semantics call, not a mechanical patch.

## Evidence

- **current when clause:** src/vs/platform/history/browser/contextScopedHistoryWidget.ts:111-139 registers history.showPrevious/showNext with when = historyNavigationWidgetFocus && historyNavigationBackwardsEnabled==true && suggestWidgetVisible==false — no isComposing reference anywhere in this file or platform/history.
- **asymmetric removal logic:** src/vs/platform/keybinding/common/keybindingResolver.ts:91-118 uses whenIsEntirelyIncluded(defaultWhen, removalWhen) = implies(defaultWhen, removalWhen); this only succeeds when defaultWhen is at least as restrictive as removalWhen. If defaultWhen drops a clause (becomes broader) while the user's removal when-clause still requires it, implication fails and the removal rule no longer disables the default binding.
- **prior report / workaround:** https://github.com/microsoft/vscode/issues/276373 (closed) — reporter's Dec 1 2025 comment captured the then-current default when clause as `historyNavigationBackwardsEnabled && historyNavigationWidgetFocus && !isComposing && !suggestWidgetVisible`, matching what they used to unbind Up; this issue reports that clause has since narrowed on the default side, silently breaking the override.
