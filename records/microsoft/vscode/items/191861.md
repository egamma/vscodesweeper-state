# Issue #191861 — Add `--github-auth` to serve-web

[https://github.com/microsoft/vscode/issues/191861](https://github.com/microsoft/vscode/issues/191861)

## Summary

The requested CLI capability is still missing: serve-web does not recognize or forward --github-auth, and production server rendering does not inject the supplied authentication session. The earlier merged PR restored only the browser-side reader; the issue was reopened afterward and remains necessary.

## Change summary

Allow code serve-web to initialize GitHub authentication from an explicitly supplied token on first browser load.

## Best solution

Provide an explicit, end-to-end token bootstrap contract for serve-web, including supported token scopes and production-server behavior. Preserve normal interactive authentication when the supplied token cannot satisfy an extension's requirements; automatic extraction from gh is outside this request.

Check Settings Sync initialization, insufficient-scope behavior, and unchanged interactive sign-in when the flag is omitted. Do not assume a PAT can satisfy every Copilot or extension authentication requirement.
- **Behavior:**

  > A user explicitly supplies a GitHub token when starting code serve-web and opens the web editor in a fresh browser profile. The CLI accepts the option and the browser initializes the corresponding GitHub account for supported authentication uses without requiring an initial interactive login. Existing browser credentials and ordinary sign-in without the option retain their current behavior. Acceptance must cover a built server, not only development mode, and document which token types and scopes are supported.
- **Trace:**

  > ServeWebArgs in cli/src/commands/args.rs has no GitHub token option, and start_version in cli/src/commands/serve_web.rs does not forward one to the downloaded server. The Node server already registers github-auth, but WebClientServer constructs the workbench authentication session only for non-built environments and advertises fixed scope sets. LocalStorageSecretStorageProvider.loadAuthSessionFromElement in src/vs/code/browser/workbench/workbench.ts already consumes the session metadata and initializes GitHub and Settings Sync entries. https://github.com/microsoft/vscode/pull/191862 restored that reader before the issue was reopened; it did not complete the CLI path. https://github.com/microsoft/vscode/issues/214089 distinguishes explicit token provisioning from automatic gh discovery and records token-scope/application-ID limitations. Preserve existing credential persistence and normal interactive authentication; do not expand the work into automatic gh token extraction. Source inspection establishes the missing capability, but no code was executed.
- **Open decisions:**
  - Which token types and scope contract should --github-auth support: a documented fixed minimum or explicitly supplied scope metadata?
  - For a built serve-web instance, should the supplied token initialize every fresh browser client that can access that instance, or should provisioning require a narrower client/session boundary?
