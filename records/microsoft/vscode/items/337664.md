# Issue #337664 — Extension host pegged at 100% CPU by busy-loop in `consume` (agent host / copilot-chat 0.65.x–0.66.x) on very large workspaces

[https://github.com/microsoft/vscode/issues/337664](https://github.com/microsoft/vscode/issues/337664)

## Summary

Well-diagnosed fresh report (CPU profile, strace, A/B isolation) of a busy-loop in the bundled Copilot Chat extension hammering the extension host, but the evidence points only at a minified bundle position I cannot map to a specific source symbol in this checkout, so this needs the Copilot Chat team's own profiling rather than an automated verdict.

## Change summary

On very large remote workspaces, the Copilot Chat/agent-host extension enters a sustained 100% CPU busy-loop inside a bundled `consume` function, causing remote heartbeat timeouts and endless reconnect loops.

## Best solution

Route to the Copilot Chat team to symbolicate the `consume` hot path in extension.js against a source map and add backoff/yielding to whatever retry or streaming loop is spinning under this large-workspace workload; the separate zh-hans i18n log-flood finding is a smaller, more clearly diagnosable follow-up.

## Evidence

- **reporter's CPU profile:** V8 CPU profile shows 92% of 10s sampled time inside `consume @ dist/extension.js:24`, reproduced against both the built-in agent host (copilot 1.0.84.70) and marketplace github.copilot-chat 0.65.0/0.66.0.
- **source ambiguity:** extensions/copilot/src has several similarly-named `consume`/`consumeStream`/`consumeReadable` symbols (src/util/vs/base/common/{iterator.ts,stream.ts,async.ts}) and a tool-calling loop (src/extension/intents/node/toolCallingLoop.ts); the minified bundle position alone doesn't disambiguate which one is spinning.
- **A/B isolation by reporter:** Disabling the built-in agent host or removing github.copilot-chat returns the extension host to idle CPU; copilot-chat 0.48.1 does not exhibit the loop under the same workload, pointing at a regression introduced between those versions.
