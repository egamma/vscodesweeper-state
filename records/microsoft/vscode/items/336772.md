# Issue #336772 — /remote on fails in VS Code 1.137+ with "Failed to set up remote session" and "Session is not an adoptable legacy chat"

[https://github.com/microsoft/vscode/issues/336772](https://github.com/microsoft/vscode/issues/336772)

## Summary

Well-documented regression (works on 1.136, breaks on 1.137/1.138, verified on two machines/repos with a fresh profile) affecting the Copilot CLI `/remote on` command. Current-main source shows the error text comes from the Agent Host's legacy-chat adoption gate (`agentService.ts`), which plausibly explains the failure for a session that hasn't materialized yet, but the shallow checkout (single commit) prevents pinning an exact fixing commit or confirming the precise code path, so this stays open rather than closing.

## Change summary

`/remote on` in a Copilot CLI chat session fails with 'Failed to set up remote session' and a console error 'Session is not an adoptable legacy chat', starting in VS Code 1.137 (regression from 1.136).

## Best solution

A maintainer with full history should trace why `/remote on`'s `session.commands.invoke` call reaches the Agent Host adoption gate in src/vs/platform/agentHost/node/agentService.ts (the exact thrown string 'Session is not an adoptable legacy chat: ${sessionStr}') for a not-yet-persisted/untitled copilotcli session, and either widen the adoption check or route CLI-internal command invocations around it.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentService.ts`, `extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotcliSession.ts`
- **Validation:** Reproduce `/remote on` in a Copilot CLI chat session on 1.138 and confirm whether the Agent Host adoption gate throws for the untitled `copilotcli:` session; once traced, add a regression test around the adoption/invoke path that fails before and passes after the fix.
- **Behavior:**

  > Running `/remote on` in a GitHub Copilot Chat CLI session should enable Mission Control remote control (as it did on 1.136) instead of failing with 'Failed to set up remote session'. Acceptance: the command succeeds (or gives a real GitHub-auth/repo-resolution error) for an authenticated user in a GitHub repo, without the 'Session is not an adoptable legacy chat' console error.
- **Trace:**

  > The reported console error string is thrown in src/vs/platform/agentHost/node/agentService.ts's restore/adoption path when a session is unregistered and fails `adoption.eligible`/`adoption.native` checks — this looks like the underlying cause, since `/remote`'s command flow in extensions/copilot/.../copilotcliSession.ts (`_handleRemoteControl`) issues `session.commands.invoke` against a session that may not yet be a persisted/registered chat (`copilotcli:/untitled-...`). Not yet confirmed: the exact call path from `_handleRemoteControl` through to the Agent Host's `restoreSession`/adoption check, and why it only started failing in 1.137/1.138 — the checkout has no history prior to a single commit, so the regression-introducing change couldn't be located. The boundary: don't loosen adoption checks broadly (they exist to prevent claiming sessions away from the extension host); scope any fix to how CLI-internal command invocations reach that gate.
