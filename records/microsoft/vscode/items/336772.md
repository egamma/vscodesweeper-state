# Issue #336772 — /remote on fails in VS Code 1.137+ with "Failed to set up remote session" and "Session is not an adoptable legacy chat"

[https://github.com/microsoft/vscode/issues/336772](https://github.com/microsoft/vscode/issues/336772)

## Summary

The reported error strings trace directly to a real code path: agentService.ts throws exactly "Session is not an adoptable legacy chat" when a legacy Copilot CLI chat fails the eligibility check in copilotAgent.ts's ensureChatAdopted, which requires an on-disk extension-host marker file. This looks like a genuine regression in the 1.137+ legacy-chat adoption/migration gate, but the exact reason the reporter's GitHub-Chat-panel session fails that check (vs. an Agents-window session) needs more tracing before a fix is safe.

## Change summary

"/remote on" (Copilot CLI remote control) fails with "Failed to set up remote session" / "Session is not an adoptable legacy chat" when used from the VS Code GitHub Chat panel (not the Agents window), starting in 1.137.

## Best solution

Diagnose why a legacy Copilot CLI chat opened via the classic GitHub Chat panel is not recognized as an adoptable session (missing extension-host marker file, or the restore/adoption gate introduced in the migrateLegacyEnabled rollout being too strict for this surface), then adjust the eligibility check in src/vs/platform/agentHost/node/copilot/copilotAgent.ts (`_isExtensionHostCliSession`/`ensureChatAdopted`) or the refusal path in agentService.ts's `restore()` accordingly.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/platform/agentHost/node/agentService.ts`, `extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotcliSession.ts`
- **Validation:** A restored regression/integration test confirming `/remote on` succeeds for a legacy Copilot CLI session opened via the classic GitHub Chat panel (not the Agents window) without producing the AHP `AH_SESSION_NOT_FOUND` error.
- **Behavior:**

  > Running "/remote on" in a Copilot CLI chat opened from the classic VS Code GitHub Chat view (not the Agents window) should enable remote control the same way it did before 1.137, without the "Failed to set up remote session"/"Session is not an adoptable legacy chat" error. Where the uncertainty starts: whether such sessions are missing the extension-host marker file entirely, or whether the migration gate added around 1.137 is refusing a category of session it should allow.
- **Trace:**

  > agentService.ts's `restore()` (around line 7429-7461) calls `agent.ensureChatAdopted`; when the result is `{ eligible: false, native: false }` and there is no already-registered session, it throws `Session is not an adoptable legacy chat`. `ensureChatAdopted` in copilotAgent.ts (line ~3922) returns that ineligible result via `_isExtensionHostCliSession` (line 3763, marker-file backed) returning false at line 3943. The open question is what state the reporter's session is in when this check runs — first reproduce against current main with a fresh legacy Copilot CLI chat started from the GitHub Chat panel before touching either file.
- **Open decisions:**
  - Is the fix in the extension host (ensure the marker file / session persistence happens before /remote on can run), or in the agent-host eligibility/restore gate (broaden what counts as adoptable for this surface)?
  - Should sessions from the classic GitHub Chat panel be treated identically to Agents-window sessions for adoption purposes, or do they need a distinct code path?
