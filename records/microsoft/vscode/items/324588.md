# Issue #324588 — Setting `update.mode: none` does not cancel the update's download

[https://github.com/microsoft/vscode/issues/324588](https://github.com/microsoft/vscode/issues/324588)

## Summary

Keep open: the current request implementation removes its cancellation listener when response headers arrive, leaving the installer download running when update.mode changes to none. The updater cancels its token but then waits for that download to finish.

## Change summary

Disabling updates during an active Windows installer download should stop the transfer rather than let it finish.

## Best solution

Ensure cancellation remains effective throughout the installer response-body transfer and that disabling updates settles without waiting for the full download. Preserve normal download completion, temporary-file cleanup, and re-enabling updates.

- **Behavior:**

  > Changing update.mode to none while a Windows installer is actively downloading must stop the transfer rather than download the remaining installer first. Cancellation must settle into Disabled without staging or applying the cancelled package. Ordinary completed downloads and a fresh download after re-enabling updates must continue to work.
- **Trace:**

  > AbstractUpdateService observes update.mode changes and calls the Windows cancelUpdate hook. Win32UpdateService.doCheckForUpdates passes checkCancellationTokenSource.token to the download request, consumes context.stream through fileService.writeFile, and checks cancellation again after writing. In src/vs/platform/request/node/requestService.ts, nodeRequestAttempt disposes its cancellation listener on the request's response event, although body consumption is still pending; cancelling the updater token then cannot abort that transfer. The desktop RequestService in src/vs/platform/request/electron-utility/requestService.ts uses this implementation with Electron net.request. The unresolved technical scope is cancellation and terminal-event behavior across the shared Node/Electron transport and response-stream consumers, not the intended update behavior. Preserve redirect, retry, successful-completion, and cleanup semantics. Coordinate with https://github.com/microsoft/vscode/pull/329266, which addresses neighboring installer-process and scheduling work rather than establishing a download-body fix.

## Evidence

- **Exact failing source path:** src/vs/platform/request/node/requestService.ts: nodeRequestAttempt resolves the request context when headers arrive, then req.on('response', () => cancellationListener.dispose()) removes the token listener before the response body finishes. Cancellation during the subsequent body download therefore no longer calls req.abort().
- **Updater cancellation cannot interrupt the body:** src/vs/platform/update/electron-main/updateService.win32.ts: doCheckForUpdates passes its check token to the installer request and writes context.stream to the temporary package. cancelUpdate cancels checkCancellationTokenSource and awaits checkPromise; the post-download token check prevents staging the installer but does not stop the transfer.
- **Actual desktop transport:** src/vs/code/electron-main/main.ts registers the electron-utility RequestService. src/vs/platform/request/electron-utility/requestService.ts delegates to the Node request implementation using Electron net.request, so the premature cancellation-listener disposal is on the reported desktop update path.
- **Intended behavior:** https://github.com/microsoft/vscode/issues/324437 explicitly requires switching update.mode to none during Downloading to tear down the in-flight request and reach Disabled. Its discussion also identifies the cached Windows installer as a reproduction consideration. The report is a MEMBER-authored regression against that contract, not a request to redefine update behavior.
- **Canonical search:** Open-issue searches for update.mode cancellation and cancellation of downloads found no verified canonical for this symptom. https://github.com/microsoft/vscode/issues/76641 concerns detecting other users' running installations; https://github.com/microsoft/vscode/issues/312125 concerns installer MoveFile permission failures. Neither owns cancellation of an active download.
- **Related implementation work:** https://github.com/microsoft/vscode/pull/329266 is open and addresses update scheduling and background installer-process cancellation, referencing different issues. Its description does not establish a fix for cancellation during response-body download; coordinate with that work without treating it as completion or a duplicate.
