# Issue #324588 — Setting `update.mode: none` does not cancel the update's download

[https://github.com/microsoft/vscode/issues/324588](https://github.com/microsoft/vscode/issues/324588)

## Summary

Real, traceable gap: the update-cancellation plumbing added for `update.mode` runtime changes cancels the check/download token, but the underlying HTTP request in `nodeRequestAttempt` drops its cancellation listener as soon as response headers arrive, so an in-progress body download can no longer be aborted once headers have been received — matching the reported symptom that the installer finishes downloading anyway.

## Change summary

Switching `update.mode` to `none` mid-download should abort the in-flight update download, but the download completes anyway.

## Best solution

Fix the underlying request layer: in src/vs/platform/request/node/requestService.ts's `nodeRequestAttempt`, the cancellation listener is disposed on the `'response'` event (line 293), well before the response body/stream is consumed — so a cancellation fired after headers arrive (e.g. from AbstractUpdateService.cancelUpdate's checkCancellationTokenSource.dispose(true)) no longer calls req.abort(). Keep the listener alive through body consumption (or forward the token into the returned stream) so mid-download cancellation actually aborts the socket.

- **Fix prompt:**

  > In src/vs/platform/request/node/requestService.ts, `nodeRequestAttempt` (lines ~200-296) registers `cancellationListener = token.onCancellationRequested(...)` which calls `req.abort()`, but then immediately disposes that listener on the `'response'` event (line 293: `req.on('response', () => cancellationListener.dispose());`) — i.e. as soon as HTTP headers arrive, before the response body/stream is read. This means once the promise resolves with `{ res, stream }`, a later cancellation of the same token (as done by AbstractUpdateService.cancelUpdate()/Win32UpdateService.cancelUpdate() in src/vs/platform/update/electron-main/{abstractUpdateService,updateService.win32}.ts when `update.mode` is switched to `none` mid-download) no longer aborts the socket, so the download silently continues to completion in the background. Fix by keeping the cancellation listener alive for the lifetime of the response body consumption instead of disposing it on `'response'` — e.g. dispose it when the resolved `res`/stream ends or errors (`res.on('end', ...)`, `res.on('close', ...)`, or wiring disposal into the `streamToBufferReadableStream` consumption) so `req.abort()` still fires and correctly terminates the socket if the token is cancelled after headers have arrived but while the body is still streaming. Do not change retry/backoff behavior in `nodeRequest`, redirect handling, or the resolved `IRequestContext` shape — only extend the cancellation listener's lifetime. Validate with a new test in src/vs/platform/request/test/node/requestService.test.ts using a slow local HTTP server: cancel the token mid-stream (after headers, before body completes) and assert the request/socket is aborted rather than allowed to finish. ## Evidence

- **cancellation wiring:** src/vs/platform/update/electron-main/abstractUpdateService.ts lines 195-256 reconfigure()/doReconfigure() call disable() -> cancelUpdate() when update.mode changes to 'none', and Win32UpdateService.cancelUpdate() (updateService.win32.ts lines 515-539) disposes checkCancellationTokenSource(true) to abort the in-flight check/download.

- **electron path shares the code:** src/vs/platform/request/electron-utility/requestService.ts's RequestService extends the same node RequestService/nodeRequestAttempt, so the electron-main update download goes through the identical vulnerable code path.
