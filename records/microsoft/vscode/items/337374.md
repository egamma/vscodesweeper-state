# Issue #337374 — Agent hooks on Windows: Claude-format ${CLAUDE_PLUGIN_ROOT} hook fails - Local harness spawns WSL bash, passes a backslashed Windows path, and never sets the env var

[https://github.com/microsoft/vscode/issues/337374](https://github.com/microsoft/vscode/issues/337374)

## Summary

Well-diagnosed, source-confirmed bug: on Windows with both WSL2 and Git Bash installed, Claude-format plugin hooks that target bash fail because the interpreter and path-substitution logic don't cooperate. Real code gap, but fixing it correctly requires a maintainer decision on interpreter selection, so this stays open rather than closing.

## Change summary

A Claude-format plugin hook using `bash "${CLAUDE_PLUGIN_ROOT}/..."` fails on Windows: the wrong bash (WSL) runs, the substituted path keeps Windows backslashes instead of being POSIX-ified, and CLAUDE_PLUGIN_ROOT is not visible in the hook's environment.

## Best solution

Teach the hook pipeline to (1) resolve a bash-targeted hook command to Git Bash rather than falling through PATH to the WSL bash.exe stub on Windows, and (2) emit a POSIX-style path (forward slashes, properly quoted) for CLAUDE_PLUGIN_ROOT/PLUGIN_ROOT substitution when the target interpreter is a POSIX shell, so the env var and the substituted token agree with what the shell can consume.

## Plan brief

- **Open decisions:**
  - Should a hook that specifies (or defaults to) bash on Windows prefer Git Bash over the WSL bash.exe stub found via PATH, and how should Git Bash be located/detected?
  - When the target interpreter is a POSIX shell, should CLAUDE_PLUGIN_ROOT/PLUGIN_ROOT substitution always emit a forward-slash path (and always quote it), even though other interpreters (PowerShell/cmd) expect the native Windows form?
  - If WSL bash is still reachable as a fallback, should the harness explicitly forward CLAUDE_PLUGIN_ROOT via WSLENV, or is avoiding WSL entirely (by preferring Git Bash) the intended fix?

## Evidence

- **path substitution keeps native separators:** src/vs/platform/agentPlugins/common/pluginParsers.ts `shellQuotePluginRootInCommand` (line ~541) and `interpolateHookPluginRoot` (line ~833) substitute `${CLAUDE_PLUGIN_ROOT}` with `pluginUri.fsPath` verbatim — on Windows this is a backslashed path — with no POSIX conversion for bash-targeted commands.
- **quoting only applied when shellUnsafeChars matches:** `shellUnsafeChars = /[\s&|<>()^;!`"']/` (pluginParsers.ts line 535) does not match backslashes, so a plain Windows path like `D:\source\repos\...` takes the simple `command.replaceAll(token, fsPath)` branch instead of the quoting/escaping branch, matching the reporter's finding that quoting is lost for exactly this kind of path.
- **no Git-Bash-vs-WSL interpreter selection:** extensions/copilot/src/platform/chat/node/hookExecutor.ts `getShellCommand()` only special-cases Windows when ComSpec is cmd.exe (routes to PowerShell); otherwise it returns `{ command: hookCommand, args: [], shell: true }`, which on Windows spawns via cmd.exe and resolves a bare `bash` through PATH — landing on the WSL launcher in System32 per microsoft/WSL#13277, with no logic anywhere to prefer Git Bash for a hook that specifies `shell: 'bash'`.
- **no 'shell' hint recognized:** src/vs/workbench/contrib/chat/common/promptSyntax/hookSchema.ts only maps legacy `bash`/`powershell`/`windows`/`linux`/`osx` fields (normalizeHookCommand, line ~327); it has no handling for Claude's per-hook `shell: "bash"` field, so there is no signal available to force a POSIX-shell-aware interpreter/path choice even if one were implemented.
- **related but distinct open issues:** https://github.com/microsoft/vscode/issues/312314 (hookExecutor.ts hardcodes PowerShell, ignoring the user's configured shell) and https://github.com/microsoft/vscode/issues/307478 (Copilot-format plugin hooks can't resolve relative bundled-script paths) touch the same files/area but are different symptoms — neither is a duplicate of this CLAUDE_PLUGIN_ROOT/bash-on-Windows report.
