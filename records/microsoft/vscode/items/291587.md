## Summary

Keep open: the MCP HTTP transport still sends origin-server authentication challenges into OAuth discovery, without a Negotiate authentication path. The supplied server sample and maintainer interest support investigating this accepted, team-authored request.

Support Windows integrated authentication for HTTP MCP servers that return HTTP 401 with WWW-Authenticate: Negotiate.

- **Behavior:**

  > An HTTP MCP server requiring Windows integrated authentication currently returns a Negotiate challenge, after which VS Code attempts OAuth discovery and cannot connect. For a permitted server and supported environment, authentication should negotiate using the intended Windows identity and establish the MCP session without Fiddler or an irrelevant OAuth client-ID prompt. Unsuccessful negotiation should produce an actionable failure rather than loop through inappropriate OAuth setup. Existing Bearer authentication, explicit configured headers, proxy authentication, and cross-origin credential protections must remain intact.
- **Trace:**

  > McpHTTPHandle._fetchWithAuthRetry in src/vs/workbench/api/common/extHostMcp.ts treats 401/403 as OAuth discovery triggers; createAuthMetadata only extracts Bearer challenges before discovery and default-metadata fallback. _fetch calls _fetchInternal with manual redirects; ordinary HTTP URLs in McpHTTPHandleNode use the shared global fetch, whose patch in src/vs/workbench/api/node/proxyResolver.ts selects Node fetch for manual redirects. The existing Kerberos lookup is wired to proxy authorization, not an MCP origin-server challenge, consistent with https://github.com/microsoft/vscode/issues/291587#issuecomment-3834777847. The reporter's runnable sample and hostname instructions are at https://github.com/microsoft/vscode/issues/291587#issuecomment-3822534024. Source inspection establishes the missing dispatch path, but does not establish native handshake behavior or identity selection in remote extension hosts. Preserve the current destination checks, redirect credential stripping, OAuth behavior, and proxy behavior; this is not a general networking-authentication redesign.
- **Open decisions:**
  - Should a Negotiate challenge from a configured MCP origin automatically use the current Windows identity, as requested, or require explicit per-server consent or opt-in before using ambient credentials?
  - Is initial support limited to local Windows extension hosts, or must remote extension hosts also support it; if remote hosts are included, which identity is used?
