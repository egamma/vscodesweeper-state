# Issue #331593 — Pet keeps moving back to middle

[https://github.com/microsoft/vscode/issues/331593](https://github.com/microsoft/vscode/issues/331593)

## Summary

Team-authored bug report (roblourens) filed hours ago, no fix or PR yet — traced the likely cause on main: the resize-observer handler in ChatPetWidget reapplies the pet's raw absolute pixel offset instead of its stored relative position when the sidebar toggle changes the drag bounds, so a sequence of bound-width changes drifts the pet toward the middle.

## Change summary

Toggling the sidebar visibility after placing the chat pet on one side causes it to end up centered instead of staying near its chosen side.

## Best solution

In src/vs/workbench/contrib/chat/browser/widget/chatPetWidget.ts, have the DisposableResizeObserver callback (and the analogous branch in _setScale) recompute the horizontal position from the stored relative position via getChatPetRestoredHorizontalPosition against the new bounds — the same approach already used in _restoreHorizontalPosition — instead of clamping _getCurrentLeft()'s raw pixel value through _setHorizontalPosition.

- **Fix prompt:**

  > The chat pet (src/vs/workbench/contrib/chat/browser/widget/chatPetWidget.ts) drifts to the middle after the user places it on one side, then toggles the sidebar open and closed. Root cause: in the DisposableResizeObserver callback (~line 1086-1093) and in _setScale (~line 1867), when _hasCustomPosition is true, the code calls `this._setHorizontalPosition(this._getCurrentLeft())` on every bounds change — `_getCurrentLeft()` reads the raw CSS `left` in pixels, and `_setHorizontalPosition` only clamps that absolute value against the new `minimumLeft`/`maximumLeft`, it does not rescale by the pet's relative position within the bounds. As a result, successive bounds-width changes (sidebar open shrinks the drag area, sidebar close restores it) leave the pet clamped near the new bounds rather than restored to its original relative offset, so repeated toggles converge it toward the center. The correct pattern already exists: `getChatPetRestoredHorizontalPosition(relativePosition, minimumLeft, maximumLeft)` (around line 703) and `_restoreHorizontalPosition()` (around line 2138) recompute the pixel position from a stored relative fraction (0..1) of the current bounds, but this recomputation is only used on first layout (`_positionInitialized` false), not on later resizes. Fix: in the resize-observer callback and in `_setScale`, when `_hasCustomPosition` is true, instead of calling `_setHorizontalPosition(this._getCurrentLeft())`, read the pet's current relative position (compute it from the current left and the *previous* bounds before they change, or read the stored value via `this.chatPetService`'s horizontal position observable) and pass it through `getChatPetRestoredHorizontalPosition` against the *new* bounds to get the target left, mirroring `_restoreHorizontalPosition`. Do not change drag, throw, or hop behavior, and do not touch the default (`_hasCustomPosition === false`) branch, which already recomputes correctly via `_setDefaultHorizontalPosition`. Validate with a new unit test in chatPetWidget.test.ts (or a focused test of the pure position functions) that simulates: set custom position near one edge -> shrink bounds (sidebar shown) -> restore original bounds (sidebar hidden) -> assert the pet's relative/left position matches its original placement rather than drifting to center. Related: https://github.com/microsoft/vscode/issues/331593.
