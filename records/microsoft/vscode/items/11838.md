# Issue #11838 — Trigger language auto detection mechanism

[https://github.com/microsoft/vscode/issues/11838](https://github.com/microsoft/vscode/issues/11838)

## Summary

Keep open: extensions can now set a document's language, but silent, resource-targeted access to built-in language detection remains missing. The existing command only changes the active editor and warns when detection fails, matching the limitation identified in the discussion.

## Change summary

Let extensions invoke VS Code's language detection for document content without interactive side effects.

## Best solution

Provide an extension-facing detection contract backed by LanguageDetectionService, allowing extensions to obtain a language result without changing editor focus or displaying notifications. Decide whether this should be a typed language API or a supported command contract before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostLanguages.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadLanguages.ts`, `src/vs/workbench/services/languageDetection/browser/languageDetectionWorkerServiceImpl.ts`, `src/vs/workbench/contrib/languageDetection/browser/languageDetection.contribution.ts`
- **Validation:** End the plan with extension-host API or command tests showing that detection can operate on the agreed target, handles an undetectable document without a warning in silent mode, and preserves unrelated editor focus and language. Retain existing setTextDocumentLanguage and interactive editor.detectLanguage behavior.
- **Behavior:**

  > An extension fetching or pasting content can request VS Code's built-in language detection without forcing an interactive notification. Explicit language assignment already exists and is not the remaining gap. Acceptance should cover recognizable content and content with no detection result, including a target other than the active editor if the chosen contract supports one. Existing user-invoked detection must retain its current behavior.
- **Trace:**

  > The stable setter in src/vscode-dts/vscode.d.ts is implemented through extHost.api.impl.ts and ExtHostLanguages.changeLanguage, but no detection counterpart was found in the extension API surface. LanguageDetectionService.detectLanguage in src/vs/workbench/services/languageDetection/browser/languageDetectionWorkerServiceImpl.ts already accepts a resource and optional supported language IDs and returns a language ID or undefined. The editor.detectLanguage action in src/vs/workbench/contrib/languageDetection/browser/languageDetection.contribution.ts instead targets the active editor, mutates its language, returns no result, and warns on failure. These observations substantiate the January 2023 API suggestion and June 2024 command limitation in https://github.com/microsoft/vscode/issues/11838. Preserve the detection algorithm, existing explicit setter, and interactive command semantics; the unresolved boundary is the extension-facing public contract.
- **Open decisions:**
  - Should extensions receive a typed languages.detectLanguage API returning a language ID, or a supported command contract for invoking detection silently?
  - Should the contract detect an explicitly supplied document/resource without changing its language, or apply the detected language as part of invocation?

## Evidence

- **Existing setter covers only part of the request:** src/vscode-dts/vscode.d.ts:14736-14746 declares vscode.languages.setTextDocumentLanguage(document, languageId). src/vs/workbench/api/common/extHost.api.impl.ts:667-668 delegates to ExtHostLanguages.changeLanguage. This sets a known language but does not determine it from content.
- **Command workaround remains interactive:** src/vs/workbench/contrib/languageDetection/browser/languageDetection.contribution.ts registers editor.detectLanguage. Its run method returns Promise<void>, uses IEditorService.activeTextEditorControl, changes that editor's model language, and calls notificationService.warn("Unable to detect editor language") when no match is found. It accepts neither a target resource nor a silent option, confirming the limitation described in the June 2024 comment.
- **Internal detection capability exists:** src/vs/workbench/services/languageDetection/browser/languageDetectionWorkerServiceImpl.ts implements LanguageDetectionService.detectLanguage(resource: URI, supportedLangs?: string[]): Promise<string | undefined>. It delegates to the detection worker with language-history biases. Searches of src/vscode-dts and src/vs/workbench/api found no corresponding detectLanguage extension API.
