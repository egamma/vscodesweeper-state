# Issue #204074 — Multi diff editor: provide right context for current resource

[https://github.com/microsoft/vscode/issues/204074](https://github.com/microsoft/vscode/issues/204074)

## Summary

The per-resource menu context gap remains in current source: toolbar commands receive the item's URI, but resource-based menu conditions do not automatically receive its accompanying context keys. Keep this accepted Backlog request open; no verified canonical owns the same work.

## Change summary

Provide the current file's resource context keys for actions within each multi-diff entry instead of inheriting the multi-diff container's resource.

## Best solution

Make resource-dependent menu conditions resolve against the relevant multi-diff entry, while preserving container-level context for whole-editor actions. Establish which resource each action surface represents, particularly for original versus modified sides.

- **Behavior:**

  > Extension-contributed actions in a multi-diff entry must be able to use resource-based menu conditions for that entry rather than the synthetic multi-diff container. Validate filename, extension, scheme, path, and language conditions across multiple entries, including added and deleted files. Context must remain correct when entries are recycled during scrolling. Whole-editor actions must retain their container-level meaning; the resource identity for side-specific actions requires an agreed contract.
- **Trace:**

  > DiffEditorItemTemplate in src/vs/editor/browser/widget/multiDiffEditor/diffEditorItemTemplate.ts creates the toolbar's scoped context service, but only binds entry-specific state and optional caller-supplied contextKeys. Its ActionRunnerWithContext already forwards modifiedUri ?? originalUri to commands, which does not change menu-condition evaluation. ResourceContextKey in src/vs/workbench/common/contextkeys.ts supplies the standard resource fields, while editorGroupView.ts establishes the inherited active-input resource. The editor-layer widget cannot directly import workbench helpers; workbenchUIElementFactory.ts and MultiDiffEditor's WorkbenchUIElementFactory are the existing integration boundary. Preserve command arguments, whole-editor context, and virtualization behavior. Related https://github.com/microsoft/vscode/issues/212877 addresses command targeting rather than this gap, and https://github.com/microsoft/vscode/issues/226921 is a closed notebook requirements list, not a duplicate target. The remaining product uncertainty is how the requested context applies across original and modified action surfaces.
- **Open decisions:**
  - For actions associated with the original diff side, should resource conditions identify that original URI, while entry-title actions retain the existing modified-URI-with-original-fallback identity, or should all entry actions share one primary resource?

## Evidence

- **Current toolbar context:** src/vs/editor/browser/widget/multiDiffEditor/diffEditorItemTemplate.ts creates a scoped context service for the actions element and constructs MenuId.MultiDiffEditorFileToolbar. ActionRunnerWithContext forwards modifiedUri ?? originalUri when executing an action, but neither construction nor setItem populates the standard resource, resourceScheme, resourceFilename, resourcePath, resourceLangId, or resourceExtname keys from that URI.
- **Existing capability is partial:** IDocumentDiffItem.contextKeys in src/vs/editor/browser/widget/multiDiffEditor/model.ts allows explicitly supplied per-item keys, and multiDiffEditorInput.ts propagates resolver-provided keys. This is internal caller-supplied metadata, not automatic resource context for entries opened through vscode.changes; passing a URI to a command also does not satisfy its menu's when clause. The public menu registration remains multiDiffEditor/resource/title in src/vs/workbench/services/actions/common/menusExtensionPoint.ts.
- **Inherited resource context:** src/vs/workbench/browser/parts/editor/editorGroupView.ts sets ResourceContextKey from the active EditorInput. MultiDiffEditor.scopedContextKeyService exposes the widget scope, but src/vs/editor/browser/widget/multiDiffEditor/multiDiffEditorWidgetImpl.ts does not automatically override the standard resource keys per entry. This explains why entry toolbar conditions can inherit the multi-diff container resource.
