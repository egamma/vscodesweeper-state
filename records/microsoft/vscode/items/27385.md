# Issue #27385 — Add option to use windows keymap on MacOS

[https://github.com/microsoft/vscode/issues/27385](https://github.com/microsoft/vscode/issues/27385)

## Summary

Keep open: current source still selects built-in and extension keybindings using the host OS, without a selectable keymap platform. This accepted Backlog request has 97 upvotes, and maintainers have consolidated matching reports here; existing extensions and manual overrides only partially cover it.

## Change summary

Allow users to select another operating system's keymap, including platform-specific extension bindings, independently of their actual operating system.

## Best solution

Provide an opt-in keymap-platform selection covering built-in and extension-contributed shortcuts while preserving host keyboard handling and user overrides. Settle modifier semantics and the treatment of host-specific commands before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/keybinding/common/keybindingsRegistry.ts`, `src/vs/workbench/services/keybinding/browser/keybindingService.ts`, `src/vs/platform/keyboardLayout/common/keyboardConfig.ts`, `src/vs/workbench/services/keybinding/test/browser/keybindingIO.test.ts`
- **Validation:** End planning with executable coverage that selects Windows bindings on a macOS host for both a core rule and an extension manifest containing distinct win/mac entries. Verify the chosen physical modifiers, unchanged native-platform defaults when selection is unset, and precedence of user overrides; manually check representative editor and extension commands on macOS.
- **Behavior:**

  > Developers switching operating systems want to retain a familiar keymap without manually maintaining a large override file. An opt-in selection should apply the chosen platform's built-in shortcuts and extension-contributed platform variants. With no selection, existing native-platform behavior must remain unchanged, and explicit user shortcuts must retain precedence. Acceptance must include a Windows keymap on macOS and an extension whose win and mac entries differ, using the modifier semantics agreed during planning.
- **Trace:**

  > KeybindingsRegistryImpl.registerKeybindingRule in src/vs/platform/keybinding/common/keybindingsRegistry.ts selects and decodes core rules using OS. WorkbenchKeybindingService.bindToCurrentPlatform and _asCommandRule in src/vs/workbench/services/keybinding/browser/keybindingService.ts independently select extension variants using that same host OS. The registry now exposes getDefaultKeybindingsForOS, but that enumeration is not active keymap selection and covers core rules only. Keyboard dispatch/layout settings and settingsSync.keybindingsPerPlatform serve different purposes; KeybindingIO.readUserKeybindingItem reads explicit user key strings. Keep actual host-platform contexts, keyboard layout handling and user override precedence distinct from the requested keymap selection. Maintainers consolidated matching reports at https://github.com/microsoft/vscode/issues/43666 and https://github.com/microsoft/vscode/issues/76006; https://github.com/microsoft/vscode/issues/299021 is only related export work. The trace establishes the missing selection paths, but does not settle physical modifier mapping or how host-specific commands should behave.
- **Open decisions:**
  - On macOS, should a selected Windows keymap retain literal Windows modifiers, or translate some modifiers to host equivalents?
  - Should keymap selection preserve host-specific shortcut exceptions and evaluate platform when-clauses against the actual host, or emulate the selected platform for those shortcuts as well?

## Evidence

- **Current platform selection:** src/vs/platform/keybinding/common/keybindingsRegistry.ts:103–143 selects core rules through bindToCurrentPlatform and decodes modifiers using OS. src/vs/workbench/services/keybinding/browser/keybindingService.ts:606–627 likewise selects extension manifest key/mac/linux/win bindings through the host OS, not a configurable keymap platform.
- **Existing settings do not cover the request:** src/vs/platform/keyboardLayout/common/keyboardConfig.ts registers keyboard.dispatch and keyboard.mapAltGrToCtrlAlt for keyboard-event interpretation; keyboard.layout in src/vs/workbench/services/keybinding/browser/keyboardLayoutService.ts concerns web keyboard layouts. settingsSync.keybindingsPerPlatform in src/vs/platform/userDataSync/common/userDataSync.ts controls synchronization of user bindings, not the platform chosen for default or extension bindings.
- **Workarounds and related syntax:** Comments 14, 15 and 22 on https://github.com/microsoft/vscode/issues/27385 describe copying default shortcuts and installing Windows/Linux keymap extensions, including acknowledged extension conflicts and partial coverage. src/vs/workbench/services/keybinding/common/keybindingIO.ts reads the user binding's key field, not mac/win/linux overrides. https://github.com/microsoft/vscode/pull/54894 merged platform when-clause contexts, whereas https://github.com/microsoft/vscode/pull/45995 closed without merging; neither provides a global keymap-platform selector.

- **Export capability is narrower:** KeybindingsRegistry.getDefaultKeybindingsForOS in src/vs/platform/keybinding/common/keybindingsRegistry.ts:208 enumerates core rules for a supplied OS, but does not change active keybindings or include extension rules in that enumeration. https://github.com/microsoft/vscode/issues/299021 concerns exporting defaults for documentation, not selecting an active cross-platform keymap; it is newer and does not absorb this request.

The discussion supplies clear demand for both built-in defaults and platform-specific extension keymaps, rather than an isolated support question.
