# Issue #319440 — Add fixed OAuth callback port option for MCP servers in Copilot

[https://github.com/microsoft/vscode/issues/319440](https://github.com/microsoft/vscode/issues/319440)

## Summary

Keep open: current VS Code tries a predefined callback port, but does not expose the requested per-server override or guarantee that port when occupied. The accepted Backlog request has maintainer interest, and no verified open canonical or fixing PR was found.

## Change summary

Allow MCP servers to specify an OAuth callback port that matches a pre-registered loopback redirect URI.

## Best solution

Provide an opt-in per-server callback-port contract through MCP configuration and the dynamic authentication flow, preserving existing behavior when omitted. Define remote/web applicability and shared-provider behavior before implementation.

- **Validation:** Extend the loopback-server tests to start a listener on a selected available port and assert the exact redirect URI, exercise the agreed occupied-port behavior, and confirm omitted configuration retains the existing predefined-port/ephemeral-fallback behavior. Validate configuration propagation and manually authenticate against an authorization server that accepts only the registered loopback URI. These checks were not executed during this read-only review.
- **Behavior:**

  > An MCP server using a pre-registered OAuth client can select a predictable loopback callback port without relaxing the authorization server's redirect validation. The authorization request and token exchange must use the same callback URI. Omitted configuration preserves existing authentication behavior. Acceptance includes successful strict-redirect authentication, explicit occupied-port behavior, and the agreed handling of remote/web environments.
- **Trace:**

  > The HTTP MCP OAuth schema in src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts does not expose a callback port. ExtHostMcp forwards authentication metadata through src/vs/workbench/api/common/extHost.protocol.ts to MainThreadMcp, which may reuse an existing provider. Dynamic provider creation in src/vs/workbench/api/common/extHostAuthentication.ts currently receives no callback-port option. NodeDynamicAuthProvider constructs LoopbackAuthServer, whose start() tries DEFAULT_AUTH_FLOW_PORT 33418 before falling back to an ephemeral port; its actual callback uses 127.0.0.1 and the root path. The loopback flow is excluded in remote extension hosts. Preserve unspecified-port defaults, loopback-only binding, PKCE, state validation, and consistent authorization/token redirect URIs; changing host or path is not established by this request. The trace establishes the local gap but does not enumerate all shared-provider and remote/web consumers.
- **Open decisions:**
  - When two MCP servers reuse the same authentication provider but configure different callback ports, must each server's interactive sign-in honor its own port, or should conflicting configurations be rejected?
  - Should callbackPort be supported only for local desktop loopback authentication, and how should remote/web clients report a configured option they cannot honor?

## Evidence

- **Existing capability is partial:** src/vs/base/common/oauth.ts defines DEFAULT_AUTH_FLOW_PORT as 33418. src/vs/workbench/api/node/loopbackServer.ts, LoopbackAuthServer.start(), first binds that port on 127.0.0.1 but retries with port 0 on EADDRINUSE. Its redirectUri is http://127.0.0.1:<port>/, not the illustrative localhost:<port>/callback in the request. This provides a best-effort predefined port, not a configurable guaranteed callback port.
- **Configuration gap:** src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts, mcpRemoteServerSchema.properties.oauth, permits clientId and enterpriseManaged with additionalProperties: false; callbackPort is absent. src/vs/workbench/api/common/extHostMcp.ts passes clientId and enterpriseManaged into IMcpAuthenticationDetails, but no callback-port option.
- **Authentication boundary:** src/vs/workbench/api/node/extHostAuthentication.ts, NodeDynamicAuthProvider._createWithLoopbackServer(), constructs LoopbackAuthServer without a port argument and uses server.redirectUri for both authorization and token exchange. The loopback flow is enabled only outside remote extension-host environments. src/vs/workbench/api/browser/mainThreadMcp.ts also reuses authentication providers through getOrActivateProviderIdForServer, so per-server options require consideration beyond changing the listener alone.
- **Demand and ownership:** https://github.com/microsoft/vscode/issues/319440 has 11 community upvotes and is accepted into Backlog with authentication and mcp labels. The supplied June 8 maintainer comment reports encountering this with Slack MCP and links https://github.com/anthropics/claude-code/issues/37714.
- **Related external report:** https://github.com/christiaangoossens/hass-oidc-auth/issues/344#issuecomment-4651245037 links this request after encountering invalid redirect URLs with Home Assistant. Its closure does not establish that VS Code added configurable callback ports.
- **Earlier precedent does not decline this request:** https://github.com/microsoft/vscode/issues/257462#issuecomment-3124517197 explicitly supports trying the predefined port and retaining an ephemeral fallback for compliant servers. https://github.com/microsoft/vscode/issues/278512#issuecomment-3633353505 attributes a DCR redirect mismatch to authorization-server noncompliance. Both issues are closed, neither is a duplicate target, and neither decision addresses an optional user-selected port while preserving defaults.
