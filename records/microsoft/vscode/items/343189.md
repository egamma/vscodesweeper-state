# Issue #343189 — Main process policy watchers permanently hold 2 of 4 libuv threads on macOS. Slow open() stalls file access in all windows

[https://github.com/microsoft/vscode/issues/343189](https://github.com/microsoft/vscode/issues/343189)

## Summary

Keep open: the native policy-watcher dependency still queues a lifetime-long semaphore wait onto libuv's shared worker pool, matching the reported starvation mechanism. Track the dependency fix here through adoption; the upgrade reminder does not establish that this is resolved.

## Change summary

Prevent macOS policy watchers from consuming shared libuv workers indefinitely and amplifying slow filesystem operations into cross-window stalls.

## Best solution

Make native policy watching independent of the shared filesystem worker pool in microsoft/vscode-policy-watcher, then adopt the corrected dependency in VS Code while preserving policy updates and disposal. Increasing the pool size mitigates starvation but does not remove the lifetime worker reservations.

## Evidence

- **Current VS Code integration:** src/vs/code/electron-main/main.ts:218–243 constructs both NativePolicyService and NativeManagedSettingsService on macOS. Their implementations in src/vs/platform/policy/node/nativePolicyService.ts and nativeManagedSettingsService.ts each retain a watcher created through @vscode/policy-watcher.
- **Dependency root cause:** https://github.com/microsoft/vscode-policy-watcher/blob/main/src/main.cc calls watcher->Queue(). https://github.com/microsoft/vscode-policy-watcher/blob/main/src/macos/PolicyWatcher.cc derives the watcher from AsyncProgressQueueWorker and keeps Execute running in a while (!disposed) loop containing dispatch_semaphore_wait(sem, DISPATCH_TIME_FOREVER). This reserves a shared worker until disposal rather than only while processing a change.
- **Dependency version and unresolved source:** The checkout's package.json and package-lock.json select @vscode/policy-watcher 1.6.0, also the version declared by the dependency's current main. Its current macOS implementation retains the blocking worker design; no concrete fixing commit was identified.
- **Actionable reproduction:** https://github.com/microsoft/vscode/issues/343189 supplies an isolated launch with UV_THREADPOOL_SIZE=2, sampled PolicyWatcher::Execute semaphore waits, a contrasting successful launch with size 3, and a size-32 workaround. These details suffice for macOS retesting; no runtime reproduction was performed in this read-only Linux checkout.
- **Related evidence, not a verified duplicate:** https://github.com/microsoft/vscode/issues/321902#issuecomment-4808027243 attributes that closed report to Microsoft Defender delaying extension-manifest open() calls, supporting the slow-I/O trigger but not resolving worker reservation. The open reports https://github.com/microsoft/vscode/issues/327479 and https://github.com/microsoft/vscode/issues/337272 describe overlapping stalls without establishing ownership of this specific native-watcher defect.
- **No established canonical or pending fix:** A public issue search for libuv and policy found no other report establishing the same root cause. The reviewed issue's timeline contains no linked fixing PR; https://github.com/microsoft/vscode/issues/287800 concerns a Windows ReadDirectoryChangesW busy loop, not macOS semaphore waits.
