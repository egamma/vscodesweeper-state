# Issue #343189 — Main process policy watchers permanently hold 2 of 4 libuv threads on macOS. Slow open() stalls file access in all windows

[https://github.com/microsoft/vscode/issues/343189](https://github.com/microsoft/vscode/issues/343189)

## Summary

Keep open: the native policy-watcher dependency still parks a libuv worker for each watcher, and current VS Code creates both policy and managed-settings watchers in the macOS main process. The report provides a concrete starvation reproduction and an independent confirmation of the slow-file-access symptoms; no completed fix or verified duplicate was established.

## Change summary

Prevent long-lived macOS policy watchers from exhausting the main process's shared filesystem worker pool and amplifying slow file opens into cross-window stalls.

## Best solution

Address the lifetime-long libuv worker occupation in microsoft/vscode-policy-watcher, then adopt the corrected dependency in VS Code while preserving initial policy delivery, change notifications, and disposal. Increasing the pool size can mitigate contention but does not remove the underlying worker reservation.

## Evidence

- **Current VS Code integration:** src/vs/code/electron-main/main.ts constructs NativePolicyService and NativeManagedSettingsService on macOS. Their implementations in src/vs/platform/policy/node/nativePolicyService.ts and src/vs/platform/policy/node/nativeManagedSettingsService.ts each call createWatcher from @vscode/policy-watcher and retain the watcher until replacement or disposal.
- **Dependency root cause:** package.json declares @vscode/policy-watcher ^1.6.0. In https://github.com/microsoft/vscode-policy-watcher/blob/v1.6.0/src/macos/PolicyWatcher.cc, PolicyWatcher derives its worker behavior from AsyncProgressQueueWorker and Execute loops until disposal, waiting with dispatch_semaphore_wait(sem, DISPATCH_TIME_FOREVER). The upstream main version of that file retains the same blocking loop; https://github.com/microsoft/vscode-policy-watcher/blob/main/src/main.cc queues each watcher with watcher->Queue(). This supports dependency-owned worker starvation rather than an installed-extension defect.
- **Concrete reproduction and discussion:** https://github.com/microsoft/vscode/issues/343189 supplies an isolated UV_THREADPOOL_SIZE=2 startup reproduction, sampled worker stacks in PolicyWatcher::Execute, and a UV_THREADPOOL_SIZE=3 comparison. The reporter confirms the issue on 1.143.0; ChrisAbra independently reports similar macOS/Defender stalls, and the reporter identifies slow extension package.json opens and a UV_THREADPOOL_SIZE=32 mitigation.
