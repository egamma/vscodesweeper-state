# Issue #343189 — Main process policy watchers permanently hold 2 of 4 libuv threads on macOS. Slow open() stalls file access in all windows

[https://github.com/microsoft/vscode/issues/343189](https://github.com/microsoft/vscode/issues/343189)

## Summary

Keep open: the bundled policy-watcher dependency still parks a libuv worker for each active macOS watcher, supporting the reported threadpool-starvation mechanism. The reporter confirmed 1.143.0 is affected; the supplied reduced-threadpool reproduction is actionable without further basic information.

## Change summary

Prevent long-lived macOS policy watchers from consuming the shared filesystem worker pool and amplifying slow file opens into cross-window stalls.

## Best solution

Resolve the permanent worker occupancy in microsoft/vscode-policy-watcher and adopt the corrected dependency in VS Code while preserving initial policy delivery, change notifications, and disposal. Verify both the reduced-threadpool startup case and cross-window file access under slow I/O; a larger pool is mitigation, not request isolation.

## Evidence

- **Concrete reproduction and current-version confirmation:** https://github.com/microsoft/vscode/issues/343189 supplies an isolated launch with UV_THREADPOOL_SIZE=2, a main-process sample locating both workers in PolicyWatcher::Execute, and a contrasting successful launch with size 3. - **VS Code integration:** src/vs/code/electron-main/main.ts:218–243 constructs separate NativePolicyService and NativeManagedSettingsService instances on macOS. src/vs/platform/policy/node/nativePolicyService.ts::_updatePolicyDefinitions and src/vs/platform/policy/node/nativeManagedSettingsService.ts::updateWatcher each call the native createWatcher API.
- **Bundled dependency contains the mechanism:** package-lock.json resolves @vscode/policy-watcher to 1.6.0. In https://github.com/microsoft/vscode-policy-watcher/blob/v1.6.0/src/macos/PolicyWatcher.cc, PolicyWatcher inherits its asynchronous-worker behavior through its constructor, and Execute loops until disposal, calling dispatch_semaphore_wait(sem, DISPATCH_TIME_FOREVER) after delivering updates. Waiting for preference changes therefore does not return the worker to the pool.
- **Upstream implementation remains active:** https://github.com/microsoft/vscode-policy-watcher/blob/main/src/PolicyWatcher.hh declares PolicyWatcher as AsyncProgressQueueWorker<const Policy *>; https://github.com/microsoft/vscode-policy-watcher/blob/main/src/main.cc queues it with watcher->Queue(). The current upstream macOS Execute implementation still contains the indefinite semaphore wait. The ownership boundary is the native dependency, not an installed third-party extension.
