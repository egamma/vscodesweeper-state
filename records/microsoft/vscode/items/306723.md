# Issue #306723 — The terminal title for a workspace-scoped task in a multi-root workspace shows a misleading folder suffix

[https://github.com/microsoft/vscode/issues/306723](https://github.com/microsoft/vscode/issues/306723)

## Summary

The misleading suffix remains source-reproducible: workspace-file tasks inherit the first workspace folder, which is then used to qualify their terminal titles regardless of execution directory. Keep this with the tasks area; the report already supplies sufficient reproduction details.

## Change summary

Workspace-scoped task terminals incorrectly display the first workspace folder as their title qualifier, even when the task executes elsewhere.

## Best solution

Make workspace-file task terminal titles distinguish their actual scope without presenting an arbitrary workspace folder as their owner. Preserve legitimate folder-task disambiguation and execution-directory resolution; agree on the workspace-level title presentation before implementation.

Add executable regression coverage for workspace-file versus folder-scoped title qualification once the format is chosen.
- **Behavior:**

  > A task defined in a .code-workspace file currently displays the first workspace folder in parentheses even when that folder neither owns the task nor matches its execution directory. Its terminal title should accurately communicate the agreed workspace-level identity instead of attributing it to an arbitrary root. Reordering workspace folders must not change that identity. Folder-scoped task disambiguation and the task's resolved execution directory must remain intact.
- **Trace:**

  > AbstractTaskService._computeWorkspaceTasks obtains the first root through _getAFolder and supplies it to _computeWorkspaceFileTasks. The custom-task parser in taskConfiguration.ts stores that root in the WorkspaceFile source configuration, and CustomTask.getWorkspaceFolder returns it. TerminalTaskSystem._createTerminalName uses getQualifiedLabel for every multi-root task; CommonTask.getQualifiedLabel appends the stored folder name without considering source kind or cwd. The resulting shellLaunchConfig.name becomes a static terminal title, so normal terminal title templates do not remove the qualifier. The attribution path is confirmed from current source; do not change variable resolution, execution cwd, task identity, or shared picker labels unnecessarily. The unresolved boundary is the user-visible title format for workspace-file tasks, not whether tools is a valid owner. Related https://github.com/microsoft/vscode/issues/287059 concerns restoration rather than this initial naming path.
- **Open decisions:**
  - For workspace-file tasks, should terminal titles omit the qualifier, identify the .code-workspace file, or identify the resolved execution directory?
