# Issue #319084 — Problem to clone again deleted git repo

[https://github.com/microsoft/vscode/issues/319084](https://github.com/microsoft/vscode/issues/319084)

## Summary

The deleted-clone failure remains present in current source, but the same root cause is already tracked by an open, better-diagnosed issue with a matching fix proposal. Consolidate this report there, preserving its Linux Mint reproduction and Windows confirmation.

## Change summary

Cloning a previously deleted repository should perform a fresh clone rather than reopen its surviving parent folder or silently stop.

## Best solution

Track the stale clone-cache defect in https://github.com/microsoft/vscode/issues/327092 and review its open implementation candidate, https://github.com/microsoft/vscode/pull/327198. A surviving workspace folder must not establish that the deleted repository still exists.

## Evidence

- **Reported trigger and confirmation:** https://github.com/microsoft/vscode/issues/319084 reports deleting a cloned repository, restarting VS Code, and attempting to clone the same URL; VS Code opens the parent folder instead. The October 1 comment independently confirms reuse of the old path on Windows.
- **Current source confirms the defect:** extensions/git/src/repositoryCache.ts stores repositoryPath separately from workspacePath; _findWorkspaceForRepo can associate a clone with its containing workspace folder. In extensions/git/src/cloneManager.ts:217–246, tryOpenExistingRepository checks workspacePath unless returnRepositoryPath is requested. A surviving parent therefore keeps the deleted clone's cache entry valid, and the single-entry branch opens that parent or returns immediately when it is already the current workspace, bypassing cloneRepository.
- **Verified canonical:** https://github.com/microsoft/vscode/issues/327092 is currently open and labeled bug. Its complete report and independent confirmations describe cloning the same URL after deleting the local clone, with no destination picker or Git clone operation. These are outcomes of the same stale-cache path that opens the surviving parent in this report.
- **Matching open implementation candidate:** https://github.com/microsoft/vscode/pull/327198 is open and explicitly fixes https://github.com/microsoft/vscode/issues/327092. Its body and diff identify the surviving parent/workspacePath check as the cause and propose validating repositoryPath instead, with a case for a deleted clone under a surviving parent. This directly covers the reviewed report; it is not a landed fix.
- **Related cases distinguished:** https://github.com/microsoft/vscode/issues/333037 concerns repositories with no prior clone history, while https://github.com/microsoft/vscode/pull/309247 concerns offering Clone again for cached existing clones. Neither is a better canonical than the deleted-clone defect tracked in https://github.com/microsoft/vscode/issues/327092.
