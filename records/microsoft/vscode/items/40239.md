# Issue #40239 — Feature Request: Enable/disable extensions from config file

[https://github.com/microsoft/vscode/issues/40239](https://github.com/microsoft/vscode/issues/40239)

## Summary

Keep open: current workspace enablement remains in internal storage, not a project configuration file. Profiles and recommendations provide useful alternatives but do not deliver the requested repository-maintained enable/disable configuration; 839 upvotes and maintainer-directed duplicates support retaining this accepted Backlog request.

## Change summary

Allow a workspace configuration file to specify which installed extensions should be enabled or disabled for that workspace.

## Best solution

Provide portable, project-maintained extension enablement configuration integrated with workspace extension management. Decide its consent and precedence semantics before implementation, preserving personal profile settings and enterprise restrictions outside the workspace.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts`, `src/vs/workbench/services/extensionManagement/test/browser/extensionEnablementService.test.ts`, `src/vs/workbench/services/extensionRecommendations/common/workspaceExtensionsConfig.ts`, `src/vs/workbench/contrib/extensions/common/extensionsFileTemplate.ts`
- **Validation:** After agreeing the configuration contract, add workspace enablement tests covering an installed globally disabled extension explicitly enabled by project configuration, an enabled extension explicitly disabled by it, and an unlisted extension retaining its existing state. Verify the same project configuration on a fresh user profile, workspace isolation, configuration removal, and preservation of enterprise restrictions; use src/vs/workbench/services/extensionManagement/test/browser/extensionEnablementService.test.ts for the enablement assertions.
- **Behavior:**

  > Users need a portable workspace configuration that declares both enabled and disabled installed extensions without repeatedly rebuilding profiles or manually toggling each extension. Recommendations alone do not satisfy this requirement, particularly when an extension is already installed but globally disabled. Acceptance must cover both directions, opening the same configured project with fresh user state, and leaving unrelated workspaces unchanged. Consent and precedence must be agreed before those acceptance expectations become executable.
- **Trace:**

  > ExtensionEnablementService._getUserEnablementState in src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts resolves workspace-enabled and workspace-disabled lists before global state; its _getExtensions and _setExtensions persist those lists in StorageScope.WORKSPACE. WorkspaceExtensionsConfigService reads .vscode/extensions.json and workspace extension configuration, but its interface and ExtensionsConfigurationSchema currently describe recommendations only. Profiles can serialize disabled flags through ExtensionsResource, but applying a profile is a separate operation rather than reading project enablement declarations. extensions.allowed is application-scoped and must not be weakened by workspace choices. Existing manual enablement, profile behavior, dependency constraints, and enterprise restrictions remain boundaries to preserve. https://github.com/microsoft/vscode/issues/230609#issuecomment-2437659519 establishes this issue as an existing consolidation target; https://github.com/microsoft/vscode/issues/347 is related provisioning work, not a verified replacement for this contract.
- **Open decisions:**
  - Should project enable/disable declarations take effect automatically when a workspace opens, or require explicit user acceptance, and how should later file changes be handled?
  - When project declarations conflict with a user's manual workspace enablement choices, which takes precedence and can the user retain a local override?
  - Should the configuration express only explicit enable/disable overrides, or also offer an allowlist mode that disables unlisted extensions?
