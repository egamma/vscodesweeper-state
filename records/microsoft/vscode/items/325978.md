# Issue #325978 — WorkspaceEdit.entries() and get() are missing SnippetTextEdits

[https://github.com/microsoft/vscode/issues/325978](https://github.com/microsoft/vscode/issues/325978)

## Summary

Current main still omits snippet edits from `WorkspaceEdit.entries()` and `get()`: both methods deliberately filter the internal edit list to plain text edits. The issue is valid and should remain open for API ownership and implementation.

## Change summary

Make `WorkspaceEdit.entries()`, `get()`, and likely `has()` account for `SnippetTextEdit` entries instead of exposing an incomplete view of the edit.

## Best solution

Define a backward-compatible API representation for mixed `TextEdit` and `SnippetTextEdit` workspace entries, then update the extension-host `WorkspaceEdit` accessors and API tests so inspection reflects every applicable edit.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostTypes.ts`, `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/test/browser/extHostTypes.test.ts`
- **Validation:** Add extension-host API tests that create mixed text and snippet workspace edits and assert that `get(uri)`, `has(uri)`, and `entries()` expose each edit according to the chosen public type contract; run the targeted extHostTypes unit tests.
- **Behavior:**

  > Extensions must be able to inspect every edit represented by a `WorkspaceEdit`. After adding text and snippet edits, `get(uri)`, `has(uri)`, and `entries()` must not report that a URI is empty or absent solely because its edits contain snippets. Existing behavior for plain text, file, notebook, and metadata edits must remain compatible.
- **Trace:**

  > `WorkspaceEdit` in src/vs/workbench/api/common/extHostTypes.ts stores `SnippetTextEdit` instances as `FileEditType.Snippet`, but `get()` and `entries()` select only `FileEditType.Text`; `has()` delegates to `get()`, so it inherits the omission. The current declarations in src/vscode-dts/vscode.d.ts expose only `TextEdit[]` from `get()` and `entries()`, which is where the trace reaches a public-contract decision. Keep the change scoped to inspection of workspace edits; do not alter how edits are serialized or applied. The related https://github.com/microsoft/language-server-protocol/issues/2290 is about snippet whitespace semantics and is not a canonical issue for this API gap.
- **Open decisions:**
  - Should `WorkspaceEdit.get()` and `entries()` widen their public return types to arrays containing both `TextEdit` and `SnippetTextEdit`, or should snippet inspection be exposed through separate API members to preserve the existing return contract?

## Evidence

- **current source:** In src/vs/workbench/api/common/extHostTypes.ts, `WorkspaceEdit.get()` and `WorkspaceEdit.entries()` both filter `_edits` with `edit._type === FileEditType.Text`, while `SnippetTextEdit` values added by `set()` are stored as `FileEditType.Snippet`; the snippet branch is therefore unreachable through these readers on current main.
- **API contract gap:** src/vscode-dts/vscode.d.ts declares `get(uri): TextEdit[]` and `entries(): [Uri, TextEdit[]][]`, so returning snippets requires an explicit public-contract decision rather than only removing the implementation filter.
- **confirmed report:** The issue body supplies a minimal example for `entries()`, and the follow-up comment confirms the same omission through `get(uri)`; both match the current source path.
- **related item:** https://github.com/microsoft/language-server-protocol/issues/2290 concerns whitespace handling in LSP `SnippetTextEdit`; it does not own this VS Code extension API inspection gap.
