# Issue #325978 — WorkspaceEdit.entries() and get() are missing SnippetTextEdits

[https://github.com/microsoft/vscode/issues/325978](https://github.com/microsoft/vscode/issues/325978)

## Summary

Confirmed on current main: `WorkspaceEdit` stores snippet edits but its map-like inspection methods ignore them. This should remain open and route to the API area, with an API-compatibility decision before implementation.

## Change summary

`WorkspaceEdit.has()`, `get()`, `entries()`, and consequently `size` omit resources whose edits are `SnippetTextEdit` values.

## Best solution

Make the public `WorkspaceEdit` inspection surface represent both `TextEdit` and `SnippetTextEdit` entries while preserving ordinary text-edit behavior and avoiding an unnecessary source-compatibility break for extension authors.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostTypes/workspaceEdit.ts`, `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/test/browser/extHostTypes.test.ts`
- **Validation:** ./scripts/test.sh --run src/vs/workbench/api/test/browser/extHostTypes.test.ts, with coverage asserting that a WorkspaceEdit containing only a SnippetTextEdit is reported by has(), get(), entries(), and size while existing TextEdit behavior remains unchanged.
- **Behavior:**

  > Extensions must be able to inspect every text or snippet edit added to a WorkspaceEdit. A resource containing a SnippetTextEdit must be visible through the map-like inspection surface, including has(), get(), entries(), and size. Existing TextEdit results and resource grouping must remain unchanged, and notebook or file operations must not begin appearing as text edits.
- **Trace:**

  > WorkspaceEdit.set() in src/vs/workbench/api/common/extHostTypes/workspaceEdit.ts recognizes SnippetTextEdit and stores it as FileEditType.Snippet. The same class implements has(), get(), and entries() using predicates that accept only FileEditType.Text; size delegates to entries(), so all four surfaces omit snippet-only resources. The stable declarations in src/vscode-dts/vscode.d.ts currently expose TextEdit[] return values even though set() accepts TextEdit | SnippetTextEdit, which is where API compatibility uncertainty begins. Relevant tests are in src/vs/workbench/api/test/browser/extHostTypes.test.ts; snippet serialization coverage in extHostTypeConverter.test.ts confirms that application/transport is a separate path and must remain unchanged.
- **Open decisions:**
  - Can the existing get() and entries() return types be widened to include SnippetTextEdit without an unacceptable source-compatibility break, or is a new snippet-aware inspection API required?
  - Should toJSON(), which currently delegates to entries(), expose snippet edits as part of this correction or retain its existing serialization shape?

## Evidence

- **source reproduction:** In src/vs/workbench/api/common/extHostTypes/workspaceEdit.ts, set() stores SnippetTextEdit values as FileEditType.Snippet, but has(), get(), and entries() only accept FileEditType.Text. The reported snippet URI is therefore excluded deterministically on current main, and size inherits the omission from entries().
- **public API mismatch:** src/vscode-dts/vscode.d.ts allows WorkspaceEdit.set() to receive TextEdit | SnippetTextEdit, while get() and entries() return only TextEdit arrays. The has() documentation nevertheless promises true when the resource will be touched.
- **missing coverage:** src/vs/workbench/api/test/browser/extHostTypes.test.ts tests ordinary WorkspaceEdit map behavior, and src/vs/workbench/api/test/browser/extHostTypeConverter.test.ts tests snippet serialization, but no test covers snippet values through has(), get(), entries(), or size.
