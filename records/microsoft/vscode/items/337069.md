# Issue #337069 — Notebook NES: edits mispositioned when enhancedNextEditSuggestions is enabled

[https://github.com/microsoft/vscode/issues/337069](https://github.com/microsoft/vscode/issues/337069)

## Summary

Fresh, well-documented bug report with concrete internal trace evidence showing NES edit offsets computed against the concatenated notebook document being misapplied to the cell's own document when the experimental enhancedNextEditSuggestions/UseAlternativeNESNotebookFormat setting is on; keep open for area triage and deeper root-cause tracing.

## Change summary

With github.copilot.chat.notebook.enhancedNextEditSuggestions.enabled on, NES suggestions in notebook cells are inserted at the wrong offset (concatenated-notebook coordinates instead of cell-local coordinates), corrupting the resulting text, especially in larger notebooks.

## Best solution

Trace the alt-notebook <-> cell offset translation path (toAltOffsetRange / toOffsetRange in extensions/copilot/src/platform/notebook/common/alternativeNotebookTextDocument.ts and the edit-application code in extensions/copilot/src/extension/inlineEdits/vscode-node/parts/vscodeWorkspace.ts) to find where an edit's offset range, computed in the concatenated alt-document space, is applied without being re-mapped back to the target cell's local document space — this is an experimental (default-off) setting so a narrow, well-tested fix is appropriate rather than a redesign.

- **Behavior:**

  > With github.copilot.chat.notebook.enhancedNextEditSuggestions.enabled true, when a next-edit suggestion is accepted/applied in a notebook cell, the inserted text must land at the correct position within that cell's own document — not appended without a line break at an offset computed against the whole concatenated notebook. Behavior with the setting off (which already works) must remain unchanged. Acceptance: typing in a cell of a large, multi-cell notebook with the setting on produces the same correctly-positioned, properly-indented suggestion insertion as with the setting off.
- **Trace:**

  > The alternative notebook format path builds a single concatenated string representation of the notebook (createAlternativeNotebookDocument / toAltOffsetRange in extensions/copilot/src/platform/notebook/common/alternativeNotebookTextDocument.ts) and NES edits appear to be generated/tracked using offsets in that concatenated space (see vscodeWorkspace.ts's toAltOffsetRange/getNotebookSelections). The reporter's own trace log shows an edit at [68,69) being checked against a rejection-collector offset of [3608, 3608) in the same interaction — a scale mismatch consistent with an edit range not being translated from alt-document coordinates back into the target cell's local document coordinates before being applied. I have not yet located the exact call site where this translation is skipped or done incorrectly; do not restructure the alt-notebook format or touch the non-experimental (setting-off) code path. Related, but distinct in scope: https://github.com/microsoft/vscode/issues/264432 (general cross-cell NES polish), cited by the reporter as related, not a duplicate.
- **Open decisions:**
  - Is the offset bug in edit generation (the model/provider producing alt-document-space ranges) or in edit application (vscodeWorkspace.ts / alternativeNotebookTextDocument.ts failing to re-map ranges to the cell), and should the fix normalize at generation time or application time?
