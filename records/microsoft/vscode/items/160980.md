# Issue #160980 — Add version support for published diagnostics

[https://github.com/microsoft/vscode/issues/160980](https://github.com/microsoft/vscode/issues/160980)

## Summary

Internal marker version metadata exists, but extensions still cannot publish diagnostics with the document version they analyzed. Keep this accepted Backlog request open: the existing bookkeeping does not provide version-aware replacement or relocation of late diagnostics.

## Change summary

Allow published diagnostics to carry their analyzed document version so stale results can be handled correctly after edits.

## Best solution

Define an extension-facing diagnostic version contract and its handling of stale publications in the diagnostics API and marker pipeline. Distinguish rejecting obsolete results from relocating results across intervening edits; internal publication-time version stamps do not satisfy either contract by themselves.

- **Behavior:**

  > A diagnostics producer should be able to identify the document version it analyzed rather than having every publication implicitly attributed to the latest document. Versioned publications should follow a documented policy that prevents older results from incorrectly superseding newer results. The request also seeks correct diagnostic placement after intervening edits, whose semantics must be decided. Acceptance checks should cover reordered results and edits between analysis and publication, while preserving existing unversioned diagnostics behavior.
- **Trace:**

  > DiagnosticCollection.set in src/vs/workbench/api/common/extHostDiagnostics.ts converts diagnostics to markers and stamps modelVersionId from the currently tracked document via ExtHostDiagnostics.createDiagnosticCollection. Diagnostic.from in src/vs/workbench/api/common/extHostTypeConverters.ts and the public Diagnostic/DiagnosticCollection declarations in src/vscode-dts/vscode.d.ts provide no producer-supplied version. Internal marker interfaces already carry optional modelVersionId, but MarkerDecorations.update in src/vs/editor/common/services/markerDecorationsService.ts preserves existing decorations by marker identity rather than implementing version-aware publication or historical range transformation. The comment at https://github.com/microsoft/vscode/issues/160980#issuecomment-1305260539 confirms that the work associated with https://github.com/microsoft/vscode/issues/159555 was internal-only. Preserve unversioned collection behavior and unrelated-provider decoration stability. The uncertainty begins at the public version contract and the treatment of results computed before intervening edits.
- **Open decisions:**
  - Should a versioned publication older than the current document be rejected, or remain displayable when no newer diagnostic publication exists?
  - Does the initial API contract include transforming ranges across intervening edits, or only version-aware acceptance and replacement of diagnostic batches?
  - Is the producer's analyzed version associated with an entire resource publication or with individual diagnostics, and what does an omitted version mean?
