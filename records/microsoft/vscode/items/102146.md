# Issue #102146 — Open remote settings GUI when extension executes workbench.action.openSettings with query in remote session

[https://github.com/microsoft/vscode/issues/102146](https://github.com/microsoft/vscode/issues/102146)

## Summary

Current source still directs workbench.action.openSettings to local User settings, including calls with a query. A separate remote-settings command offers partial coverage, but the requested automatic targeting remains absent and the maintainer-endorsed scope-selection contract needs clarification.

## Change summary

Allow extensions to open filtered Settings UI at the appropriate remote scope instead of local User settings.

## Best solution

Provide a reliable extension-invocable way to open filtered Remote Settings UI regardless of the user's JSON-editor preference. Decide whether the generic command should infer remote scope or retain its current behavior with explicit scope selection available separately.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/preferences/browser/preferences.contribution.ts`, `src/vs/workbench/services/preferences/browser/preferencesService.ts`, `src/vs/workbench/services/preferences/common/preferences.ts`
- **Validation:** In a Remote-SSH or WSL session, invoke the extension-facing command selected by the agreed contract with a settings query. Verify that the Settings UI opens with Remote selected and the query applied, under both workbench.settings.editor='ui' and 'json'; also verify the agreed behavior for ordinary local calls and calls without a query.
- **Behavior:**

  > An extension should be able to direct a remote-session user to filtered Remote Settings UI without requiring the user to switch away from local User settings. The invocation should reliably show the requested UI even when the user's normal settings-editor preference is JSON. Acceptance must cover both settings-editor preferences and preserve the agreed behavior of local and unfiltered settings commands.
- **Trace:**

  > The generic command handler in src/vs/workbench/contrib/preferences/browser/preferences.contribution.ts passes its sanitized query to PreferencesService.openSettings, which assigns USER_LOCAL and forces UI rendering for nonempty queries. The separate workbench.action.openRemoteSettings handler accepts a query object and reaches PreferencesService.openRemoteSettings, which assigns USER_REMOTE but inherits the configured editor preference; its public argument sanitizer does not accept jsonEditor. Thus explicit remote targeting already exists, while automatic targeting and unconditional remote-UI selection are not supplied by the reported command path. The maintainer comment at https://github.com/microsoft/vscode/issues/102146#issuecomment-657104815 favors scope selection without defining automatic switching. The newer matching report https://github.com/microsoft/vscode/issues/115158 was closed in favor of this issue. Preserve unrelated settings scopes and JSON-opening commands; uncertainty starts at the extension-facing targeting contract, not the internal choice of helper.
- **Open decisions:**
  - Should a queried workbench.action.openSettings call automatically select Remote in a remote session, or should generic calls retain local targeting while extensions explicitly request Remote Settings UI?

## Evidence

- **Current generic command:** src/vs/workbench/contrib/preferences/browser/preferences.contribution.ts:251-255 converts a string argument into { query } and calls PreferencesService.openSettings. In src/vs/workbench/services/preferences/browser/preferencesService.ts:222-231, openSettings unconditionally assigns ConfigurationTarget.USER_LOCAL and forces the UI for a nonempty query; it does not infer remote scope.
- **Existing capability and limits:** src/vs/workbench/contrib/preferences/browser/preferences.contribution.ts:551-567 registers workbench.action.openRemoteSettings and accepts an object containing query. PreferencesService.openRemoteSettings at preferencesService.ts:298-310 selects USER_REMOTE. However, sanitizeOpenSettingsArgs does not expose jsonEditor, and the remote path inherits workbench.settings.editor through PreferencesService.open; unlike generic openSettings, a query does not force the UI. This is useful partial coverage, not the requested generic-command behavior or an unconditional filtered remote-UI entry point.
- **Maintainer direction:** https://github.com/microsoft/vscode/issues/102146#issuecomment-657104815 clarifies that the UI command historically restored the previously selected scope and endorses allowing extension authors to specify a scope. It does not settle automatic remote selection versus explicit targeting, so a decline close would contradict the accepted direction.
