# Issue #339753 — Copilot keep prompting for sign in when using GHE (github enterprise)

[https://github.com/microsoft/vscode/issues/339753](https://github.com/microsoft/vscode/issues/339753)

## Summary

Keep open: multiple users confirmed the cross-window sign-in prompt, including on 1.143.0 after the cited GHE fix. The later 1.146.0 success report is encouraging, but does not establish that the remaining failure is resolved.

## Change summary

Opening another VS Code window incorrectly prompts already-authenticated Copilot users to sign in again in existing windows.

## Best solution

Retest the documented multi-window GHE scenario and identify whether remaining prompts originate from endpoint initialization or authentication-session reconciliation. Existing authenticated windows should retain usable credentials without showing setup dialogs when another window opens.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostTerminalContribution.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostRootConfigForwarder.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostChatContribution.ts`
- **Validation:** With an authenticated GHE profile, fully activate one workspace, open additional windows using the same profile, wait for activation, and return to every existing window. No sign-in dialog should appear and Copilot should remain usable; repeat on Windows and macOS, including a previously affected profile before signing out or clearing account state.
- **Behavior:**

  > Opening an additional VS Code window must not show a Copilot sign-in dialog in existing windows whose account remains authenticated. Copilot must continue working without dismissing dialogs or repeating browser authorization. Validate after full workspace activation and repeated window openings, retaining the affected profile state. Genuine sign-out or credential rejection must still permit the normal authentication flow.
- **Trace:**

  > The documented trigger is activation of a newly opened window, followed by a sign-in prompt in existing windows despite usable credentials. https://github.com/microsoft/vscode/commit/eef761e9628e777317a554114f0202a070e98f0b addressed shared enterprise-endpoint initialization in AgentHostTerminalContribution and asynchronous forwarding lifetime in AgentHostRootConfigForwarder; both protections remain present. A subsequent GHE report on 1.143.0 confirms that fix did not cover every affected profile. Current revokeAuthenticationForRemovedSessions in agentHostAuth.ts distinguishes unavailable, resolved, and empty session resolutions; the remaining failure has not been localized to one of these branches. Related reports https://github.com/microsoft/vscode/issues/341034 and https://github.com/microsoft/vscode/issues/342264 provide session-replacement and token-change leads, not verified identical causes. Begin by reproducing with retained profile state and correlating endpoint changes, session reconciliation, and dialog activation; preserve legitimate sign-out handling and do not assume every authentication prompt shares this cause.

## Evidence

- **Confirmed reproduction:** https://github.com/microsoft/vscode/issues/339753#issuecomment-5994961334 supplies concrete steps: fully activate the first workspace, open another window, then return to the first. Multiple commenters confirm the prompt; dismissing it leaves Copilot working.
- **Landed partial fix:** https://github.com/microsoft/vscode/commit/eef761e9628e777317a554114f0202a070e98f0b explicitly references this issue. Its AgentHostTerminalContribution diff waits for getDefaultAccount() before forwarding GithubEnterpriseUri and preserves an unavailable enterprise endpoint rather than publishing an empty string. AgentHostRootConfigForwarder also rejects forwarding after disposal or disablement. These protections remain in current source.
- **Failure after the fix:** https://github.com/microsoft/vscode/issues/339753#issuecomment-6314771852 confirms the exact new-window trigger on macOS with GHE in 1.143.0. https://github.com/microsoft/vscode/issues/339753#issuecomment-6315934794 says signing out, disabling Copilot, and deleting ~/.copilot did not resolve it. The October 11 commit therefore cannot establish completion of the whole report.
- **Later recovery:** https://github.com/microsoft/vscode/issues/339753#issuecomment-6950001758 reports success on Windows with 1.146.0 after signing out and back in. This is evidence of improvement, not a concrete later fix identifying why the previously failing case is now covered.
- **Canonical search:** https://github.com/microsoft/vscode/issues/341034 and https://github.com/microsoft/vscode/issues/342264 are open related cross-window authentication reports. Both are younger than this issue, have no milestone, and have fewer upvotes (1 and 2 versus 13); neither qualifies as its canonical under the re-review rules. The named predecessors https://github.com/microsoft/vscode/issues/336407 and https://github.com/microsoft/vscode/issues/337562 are closed.
- **Current source boundary:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts:revokeAuthenticationForRemovedSessions currently re-resolves protected resources, preserves unavailable resolutions, forwards replacement credentials, and clears credentials only on an empty resolution. This prevents concluding from the historical symptom alone that the current reconciliation path is defective; authenticated multi-window verification remains necessary.
