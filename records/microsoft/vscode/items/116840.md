# Issue #116840 — [html] handle HTML-escaped characters in links

[https://github.com/microsoft/vscode/issues/116840](https://github.com/microsoft/vscode/issues/116840)

## Summary

The defect remains visible in current source: both the HTML document-link provider and the generic editor link detector preserve `&amp;` in the navigation target. The older related issue concerns JavaScript diagnostics rather than link navigation, so it is not a duplicate under the stronger re-review rule.

## Change summary

Decode entity references in HTML and XML link targets so Ctrl/Cmd-click navigation opens the URL represented by the document rather than its escaped source text.

## Best solution

Make HTML-aware document links navigate to the semantically decoded URL while retaining the source range for highlighting. A maintainer should also decide whether the XML and XMLDoc cases belong in format-specific providers or require a broader core contract, without changing literal URLs in ordinary text.

## Plan brief

- **Likely files:** `extensions/html-language-features/server/src/modes/htmlMode.ts`, `extensions/html-language-features/server/src/test/links.test.ts`, `extensions/html-language-features/server/package.json`, `extensions/html-language-features/server/package-lock.json`, `src/vs/editor/common/languages/linkComputer.ts`, `src/vs/editor/test/common/modes/linkComputer.test.ts`
- **Validation:** Add entity-containing link cases and run `npm test --prefix extensions/html-language-features/server`; if the generic link contract is changed, also run `scripts/test.sh --grep "Editor Modes - Link Computer"`.
- **Behavior:**

  > In an HTML document, Ctrl/Cmd-clicking `<a href="https://www.example.com/foo.html?bar&amp;baz">` opens `https://www.example.com/foo.html?bar&baz`, while the complete escaped source remains the highlighted link range. Existing links containing literal ampersands or percent-encoded components continue to navigate unchanged. If XML/XMLDoc support is included in the selected scope, the same semantic decoding applies there without decoding entity-looking text in language-agnostic plain-text URLs.
- **Trace:**

  > HTML links flow from extensions/html-language-features/server/src/modes/htmlMode.ts into vscode-html-languageservice's `HTMLDocumentLinks`; its `createLink` path uses the scanner's raw attribute value and does not decode entities. Documents without a language-specific provider fall back to `LinkComputer` in src/vs/editor/common/languages/linkComputer.ts, which uses the literal source substring as the URL. `LinksList` in src/vs/editor/contrib/links/browser/getLinks.ts merges overlapping provider results, so HTML-specific results supersede the generic fallback but currently preserve the same escaped target. The boundary is URL interpretation: source ranges and ordinary literal URLs must remain unchanged, and the unrelated JavaScript-diagnostics behavior in https://github.com/microsoft/vscode/issues/111760 is out of scope.
- **Open decisions:**
  - Should this issue cover only entity decoding in HTML-aware document links, or also require format-specific support for the reported XML and C# XMLDoc cases? A global generic-link decode would also reinterpret literal `&amp;` text outside markup.

## Evidence

- **current HTML path:** extensions/html-language-features/server/src/modes/htmlMode.ts delegates document links directly to `htmlLanguageService.findDocumentLinks`; the current vscode-html-languageservice implementation in https://github.com/microsoft/vscode-html-languageservice/blob/main/src/services/htmlLinks.ts passes the raw scanned attribute value through `getWorkspaceUrl`, with no entity decoding.
- **current generic path:** src/vs/editor/common/languages/linkComputer.ts constructs each target with `line.substring(...)`, so an XML or other generic link containing `&amp;` still produces a URL containing those literal characters.
- **confirmed report:** The reporter retested on VS Code 1.53.2 and confirmed that both HTML and XML links retained `&amp;`: https://github.com/microsoft/vscode/issues/116840#issuecomment-780683229.
- **related issue is distinct:** https://github.com/microsoft/vscode/issues/111760 is older and open, but reports diagnostics for `&quot;` inside JavaScript-valued attributes, not incorrect hyperlink navigation, so it does not own the same observable symptom.
