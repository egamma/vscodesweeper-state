# Issue #332881 — Agents Window: "Commit Changes" is not always available

[https://github.com/microsoft/vscode/issues/332881](https://github.com/microsoft/vscode/issues/332881)

## Summary

Keep open: current source still derives Commit availability from the selected changeset rather than independently from pending working-tree changes. The newer Git/worktree overview discusses discoverability, but it is not a valid duplicate target for this re-reviewed report.

## Change summary

Keep Commit Changes accessible when users select a Changes view other than Uncommitted Changes.

## Best solution

Make committing pending working-tree changes discoverable independently of the diff being inspected, while preserving existing operation enablement and commit semantics. Coordinate this focused improvement with the broader Git/worktree workflow discussion without replacing this report.

- **Behavior:**

  > Users with pending working-tree changes should be able to find and invoke Commit without first switching the Changes picker to Uncommitted Changes. Changing the inspected diff must not silently change the commit target or introduce pushing or synchronization. Acceptance checks should cover selection changes, invocation against the intended workspace, and existing disabled/running states.
- **Trace:**

  > ChangesHeaderChangesetOperationsActionContribution in src/vs/sessions/contrib/changes/browser/changesActions.ts reads activeSessionChangesetObs for existing sessions and filters its operations to Commit; its header command is not exposed through F1. The corresponding changesActions.test.ts explicitly encodes selection-scoped contribution. AgentHostChangeset maps provider-advertised operations per changeset in src/vs/sessions/contrib/providers/agentHost/browser/agentHostSessionChangesets.ts, so availability cannot be treated as solely a button-rendering concern. The trace establishes the selection dependency but does not establish operation availability for every provider or historical changeset. Preserve provider validation, workspace targeting, and the distinction between committing and syncing. https://github.com/microsoft/vscode/issues/336620 supplies broader design context, while https://github.com/microsoft/vscode/issues/323444 identifies the separate no-op-without-uncommitted-changes case.

## Evidence

- **Report and discussion:** https://github.com/microsoft/vscode/issues/332881 describes the precise selection-dependent limitation. The reporter confirmed it persisted after upgrading to 1.135.0, and another commenter independently described difficulty finding the button.
- **Existing capability and remaining gap:** src/vs/sessions/contrib/changes/browser/changesActions.ts:449-497 documents and implements the current header behavior: existing sessions contribute only the Commit operation belonging to activeSessionChangesetObs. The command workbench.contrib.sessions.changesHeaderChangesetOperation.commit therefore does not independently guarantee access while inspecting another changeset; it is registered with f1: false.
- **Current test contract:** src/vs/sessions/contrib/changes/test/browser/changesActions.test.ts contains 'changesets contribute operations to the Changes editor header for draft and existing sessions' and explicitly states that existing sessions contribute Commit from the selected changeset. Combined with the header's selected-changeset lookup, current availability depends on provider-advertised operations; inspecting the header alone cannot establish consistent availability across every Changes selection.
