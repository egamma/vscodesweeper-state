# Issue #332881 — Agents Window: "Commit Changes" is not always available

[https://github.com/microsoft/vscode/issues/332881](https://github.com/microsoft/vscode/issues/332881)

## Summary

Traced this in the Agents Window changes code: the "Commit Changes" button reflects changeset-scoped operations reported by the active changeset, and the host only advertises the commit operation on the Uncommitted Changes changeset — so it legitimately disappears when Branch Changes or Session Changes is selected. This is current by-design behavior, not a rendering bug, but it's a real UX rough edge worth a product decision.

## Change summary

In the Agents Window Changes view, the "Commit Changes" action is only shown when the "Uncommitted Changes" changeset tab is selected, not when Branch Changes or Session Changes is selected.

## Best solution

Decide whether commit should be reachable from any changeset tab (e.g. by having the button bar fall back to invoking the operation against the Uncommitted Changes changeset even when a different one is selected) or whether the current per-changeset operation model is intentional and should instead be clarified in the UI (e.g. disabled state with an explanatory tooltip) — likely lands in src/vs/sessions/contrib/changes/browser/changesView.ts and changesActions.ts.

## Evidence

- **changeset-scoped button bar:** src/vs/sessions/contrib/changes/browser/changesView.ts (operationActionGroupsObs, ~line 381) builds the title-bar button/dropdown from `changesViewService.activeSessionChangesetOperationsObs`, i.e. only the operations the currently selected changeset reports.
- **operation source:** Changeset operations come from the agent host protocol per changeset (src/vs/sessions/contrib/providers/agentHost/browser/agentHostSessionChangesets.ts, createChangesets) — Branch Changes / Uncommitted Changes / Session Changes changesets are each wrapped separately, and the host decides which operations (e.g. AGENT_HOST_COMMIT_CHANGESET_OPERATION_ID) apply to which changeset.
- **explicit uncommitted-only registration:** src/vs/sessions/contrib/changes/browser/changesActions.ts NewSessionUncommittedChangesetOperationsActionContribution (~line 395) explicitly filters `candidate.id === UNCOMMITTED_CHANGES_CHANGESET_ID` before registering toolbar actions for a new/untitled session, reinforcing that commit is currently tied to that one changeset by design.
- **user follow-up:** Comment from ProTip (2026-09-08) corroborates the confusion: they couldn't find the commit button because it wasn't showing for their selected changeset.
