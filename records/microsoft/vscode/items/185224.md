# Issue #185224 — Code Actions - Fix All Support

[https://github.com/microsoft/vscode/issues/185224](https://github.com/microsoft/vscode/issues/185224)

## Summary

A real gap remains: current VS Code supports flat `source.fixAll` actions but has no API or hierarchical UI for choosing document, project, or solution scope. Maintainers accepted the direction while explicitly leaving the API and general-purpose UX design open, so this On Deck request should remain open under discussion.

## Change summary

Add scoped Fix All code actions and a compact UI that groups equivalent fixes instead of listing every scope as a separate action.

## Best solution

Design a general hierarchical code-action contract and widget that lets providers expose related action variants, including document/project/solution Fix All scopes, without flattening them into the main list. Coordinate the public VS Code API and LSP contract so language clients can preserve those scope semantics.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages.ts`, `src/vs/editor/contrib/codeAction/browser/codeActionMenu.ts`, `src/vs/editor/contrib/codeAction/browser/codeActionController.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`
- **Validation:** Add code-action widget tests showing that related document/project/solution variants appear under one action and that selecting each variant invokes the provider with the selected scope; add extension-host/main-thread API conversion tests preserving the chosen scope.
- **Behavior:**

  > When a provider offers the same fix at multiple scopes, the Code Actions UI presents one compact entry from which the user can choose the applicable document, project, or solution variant. Unrelated quick fixes and existing single-scope actions retain their current ordering and one-step invocation. The design should also support non-Fix-All actions that expose several related alternatives without flattening them into a long list. Acceptance requires widget coverage for grouping and keyboard selection plus API transport coverage for the selected variant.
- **Trace:**

  > Current main recognizes `source.fixAll` in `src/vs/editor/contrib/codeAction/common/types.ts`, but `CodeAction` remains flat in `src/vs/editor/common/languages.ts` and `src/vscode-dts/vscode.d.ts`. `toMenuItems` in `src/vs/editor/contrib/codeAction/browser/codeActionMenu.ts` emits one list item per action, while `CodeActionController.showCodeActionList` applies the selected item directly. The extension-host bridge runs through `src/vs/workbench/api/common/extHostLanguageFeatures.ts` and `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`; any public contract must survive that boundary and coordinate with the LSP-side design. Preserve existing provider compatibility, action-kind filtering, direct invocation of single actions, and code-actions-on-save behavior. The uncertainty begins at the public representation and user interaction for related variants, especially the maintainer request to make the mechanism broader than Fix All.
- **Open decisions:**
  - Should users see a general hierarchy of related code-action variants, or a Fix-All-specific scope picker?
  - Which scope vocabulary and semantics should the public contract guarantee across single-folder, multi-root, and language-defined project or solution models?
  - Should choosing a parent action immediately use a preferred/default scope, or always open the available variants?

## Evidence

- **current API gap:** On current main, `CodeAction` in `src/vs/editor/common/languages.ts` and `src/vscode-dts/vscode.d.ts` is a flat action with title/edit/command/kind metadata; it has no scope variants, children, or equivalent grouping contract.
- **current UI gap:** `src/vs/editor/contrib/codeAction/browser/codeActionMenu.ts` converts every returned action into an individual `IActionListItem`; its headers group broad action kinds but cannot collapse equivalent scoped fixes into a selectable hierarchy.
- **partial existing capability:** `src/vs/editor/contrib/codeAction/common/types.ts` defines `source.fixAll`, and `src/vs/editor/contrib/codeAction/browser/codeActionCommands.ts` exposes `editor.action.fixAll`, but these only request existing provider-supplied Fix All actions and do not provide document/project/solution scope selection.
- **maintainer direction:** https://github.com/microsoft/vscode/issues/185224#issuecomment-1593007495 says the feature is wanted but requires new API and UI and should not be rushed.
- **general UX requirement:** https://github.com/microsoft/vscode/issues/185224#issuecomment-1841650594 asks that the eventual UX handle general cases where a fix offers multiple alternatives, rather than only Fix All.
- **canonical search:** Searches for scoped, nested, hierarchical, and submenu code actions found no older open microsoft/vscode issue with the same observable request; https://github.com/microsoft/vscode/issues/156886 concerns previewing and selectively applying workspace edits, not choosing scoped variants before applying an action.
