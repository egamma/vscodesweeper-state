# Issue #320813 — GitHub sign-in lockout: FetcherService treats 401 as terminal with no engine fallback when the transport drops the Authorization header

[https://github.com/microsoft/vscode/issues/320813](https://github.com/microsoft/vscode/issues/320813)

## Summary

Keep open: the reported sign-in failure has detailed diagnostic evidence, and current source still stops engine fallback on every 401. Neither the cause of the missing credentials nor recovery through another engine in the affected instance has been established.

## Change summary

GitHub sign-in remains blocked when an authenticated user-info request returns a missing-credentials 401 and the fetcher refuses to try another transport.

## Best solution

Establish a bounded recovery contract for authenticated GitHub user-info requests that return a missing-credentials response, while preserving terminal handling of genuinely invalid credentials and rate limits. Validate recovery independently of a cold restart before changing the shared fetcher's policy.

Include genuine Bad credentials, absent Authorization, response-body preservation, and the existing single-request 429 check. Separately verify whether alternate-engine recovery works without restarting an affected instance.
- **Behavior:**

  > The reporter successfully completes OAuth but cannot finish sign-in because user-info lookup repeatedly returns Requires authentication until VS Code is fully restarted. The goal is bounded recovery when credentials supplied by the caller fail to reach the GitHub user-info endpoint, without amplifying requests for invalid tokens or rate-limited responses. Acceptance must distinguish missing-credentials responses from genuine credential rejection and demonstrate recovery without relying on a cold restart.
- **Trace:**

  > GitHubServer.getUserInfo in extensions/github-authentication/src/githubServer.ts calls fetchUserInfo in common/gitHubAccount.ts, which supplies Authorization and retryFallbacks. FetchHttpClient.send in httpClient.ts forwards this to node/fetch.ts, where shouldNotRetry classifies every 401 as terminal and fetchWithFallbacks returns before trying another engine. fetchUserInfo then reads the response message and throws it. The transport defect itself was not captured, and both Electron-first and Node-first requests reportedly failed before restart, so successful alternate-engine recovery remains unproven. Preserve the rate-limit protection associated with https://github.com/microsoft/vscode/issues/282083 and avoid broad changes to unrelated requests or authentication providers. The existing fetching test suite can exercise controlled engine-specific responses, but it does not reproduce the poisoned network state.
- **Open decisions:**
  - Should an authenticated GitHub user-info request receiving 401 Requires authentication make a bounded alternate-transport attempt, or retain terminal handling and offer explicit restart-oriented recovery?
