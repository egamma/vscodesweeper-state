# Issue #115409 — Settings editor: Support .enabled to hide other settings in the namespace by convention 

[https://github.com/microsoft/vscode/issues/115409](https://github.com/microsoft/vscode/issues/115409)

## Summary

Keep open under discussion: current settings filtering does not hide dependent settings when a namespace's .enabled setting is false. The thread identifies a genuine tradeoff between reducing clutter and preserving discoverability that needs a product decision.

## Change summary

Reduce Settings editor clutter by hiding or de-emphasizing settings whose controlling feature is disabled.

## Best solution

Agree on dependency-aware settings presentation that reduces irrelevant controls without making settings undiscoverable in search. Keep this focused request separate from the broader extension-settings discussion until browsing, searching, and editing behavior are settled.

- **Trace:**

  > SettingsTreeFilter.filter in src/vs/workbench/contrib/preferences/browser/settingsTree.ts currently handles category, scope, and group filtering without consulting sibling .enabled values. SettingsTreeModel.createSettingsTreeGroupElement and SearchResultModel.updateChildren in src/vs/workbench/contrib/preferences/browser/settingsTreeModels.ts have separate browsing and search visibility paths; neither implements this dependency relationship. IConfigurationPropertySchema in src/vs/platform/configuration/common/configurationRegistry.ts has registration inclusion and ordering metadata, which do not provide dynamic dependency presentation. Source inspection establishes the missing capability, not an agreed design. Preserve configuration persistence and runtime feature semantics: this request concerns Settings editor presentation only. The broader discussion at https://github.com/microsoft/vscode/issues/70589 supplies grouping alternatives but does not decide this specific behavior. The uncertainty begins with whether to hide settings at all and how search should expose inactive settings.
- **Open decisions:**
  - When a controlling feature is disabled, should dependent settings be hidden, collapsed, or remain visible with an inactive-state hint?
  - Should search always expose dependent settings, and can users edit them without first enabling the feature?
  - Should dependency relationships be inferred automatically from the .enabled namespace convention or explicitly declared by setting contributors?
