# Issue #152252 — Go To Source Definition UX improvements

[https://github.com/microsoft/vscode/issues/152252](https://github.com/microsoft/vscode/issues/152252)

## Summary

Both requested improvements remain missing: the explicit command still reports empty results through an error notification, and definition results discard uncertainty metadata. Keep this team-authored request open for editor/API design; the related references-classification issue does not cover its full scope.

## Change summary

Use inline feedback for empty source-definition results and distinguish guessed definition targets from verified ones.

## Best solution

Make source-definition feedback consistent with ordinary definition navigation and provide an understandable uncertainty indication for both single-target navigation and multiple-target peek results. Agree on the location metadata contract and presentation before implementing the uncertainty portion.

## Plan brief

- **Likely files:** `extensions/typescript-language-features/src/languageFeatures/sourceDefinition.ts`, `extensions/typescript-language-features/src/languageFeatures/definitions.ts`, `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages.ts`, `src/vs/editor/contrib/gotoSymbol/browser/goToCommands.ts`, `src/vs/editor/contrib/gotoSymbol/browser/referencesModel.ts`
- **Validation:** Exercise typescript.goToSourceDefinition with controlled empty, verified, unverified, and mixed protocol results. Verify empty results produce inline feedback rather than an error notification; single and multiple unverified targets receive the agreed uncertainty presentation; verified targets and ordinary definition navigation retain their existing behavior.
- **Behavior:**

  > Go To Source Definition should report an ordinary absence of targets inline, consistently with Go To Definition, rather than as an error notification. Users should be able to recognize guessed targets, including a single navigation destination and individual results in a multiple-target peek. The uncertainty behavior also applies to ordinary Go To Definition when its protocol response contains unverified results. Acceptance must cover empty, verified, unverified, and mixed results without changing target selection or navigation semantics.
- **Trace:**

  > SourceDefinitionCommand.execute in extensions/typescript-language-features/src/languageFeatures/sourceDefinition.ts maps findSourceDefinition results to plain locations, then opens one target or shows references; its empty-result branch still uses showErrorMessage. The editor.action.goToLocations command in src/vs/editor/contrib/gotoSymbol/browser/goToCommands.ts already supports inline noResultsMessage feedback through SymbolNavigationAction and MessageController. TypeScriptDefinitionProvider.provideDefinition in definitions.ts also drops uncertainty when constructing DefinitionLink objects, including when js/ts.preferGoToSourceDefinition is enabled. The public and editor-internal LocationLink contracts currently contain only location/range information; ReferencesModel consumes those links. The remaining uncertainty starts at the metadata contract and how guessed results should be communicated, especially after single-target navigation. Preserve existing resolution algorithms, target ordering, and verified-result navigation; https://github.com/microsoft/vscode/issues/74237 is related API-design context, not a replacement for this request.
- **Open decisions:**
  - How should uncertainty be communicated for a single navigated target versus individual targets in a multiple-result peek?
  - Should the shared location API expose an explicit uncertainty flag or a broader result-classification contract, and how should it apply consistently to ordinary definition results?

## Evidence

- **Empty-result behavior remains:** extensions/typescript-language-features/src/languageFeatures/sourceDefinition.ts: SourceDefinitionCommand.execute still calls showErrorMessage("No source definitions found.") after an empty response. Nonempty results use vscode.open for one target or editor.action.showReferences for multiple targets.
- **Existing inline capability is not adopted:** src/vs/editor/contrib/gotoSymbol/browser/goToCommands.ts: editor.action.goToLocations accepts noResultsMessage; SymbolNavigationAction displays it through MessageController when there are no references. The explicit typescript.goToSourceDefinition command does not use this path, matching the integration opportunity identified in the issue's June 22 maintainer comment.
- **Uncertainty metadata is not surfaced:** sourceDefinition.ts converts protocol results into vscode.Location objects. extensions/typescript-language-features/src/languageFeatures/definitions.ts likewise constructs DefinitionLink objects using only URI and range fields. Neither path preserves unverified; src/vscode-dts/vscode.d.ts LocationLink and src/vs/editor/common/languages.ts LocationLink have no uncertainty field.
- **Existing setting provides only partial coverage:** extensions/typescript-language-features/package.json registers js/ts.preferGoToSourceDefinition. definitions.ts uses it to prefer source targets during ordinary Go to Definition, but it neither changes the explicit command's empty-result notification nor exposes uncertainty.
