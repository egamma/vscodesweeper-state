# Issue #340454 — Watermark keeps `Open Chat` after chat is disabled

[https://github.com/microsoft/vscode/issues/340454](https://github.com/microsoft/vscode/issues/340454)

## Summary

Confirmed from source: the empty-editor watermark's `registerListeners()` in editorGroupWatermark.ts never listens for `onDidChangeContext`, and `cachedWhen` (consulted first in `filterEntries()`) is only refreshed at shutdown, so `Open Chat` lingers after `chat.disableAIFeatures` flips the gating context keys mid-session.

## Change summary

The watermark keeps showing `Open Chat` (with its keybinding) after chat is disabled via `chat.disableAIFeatures`, because the watermark doesn't re-evaluate its entries when the underlying context keys change.

## Best solution

Subscribe to `IContextKeyService.onDidChangeContext` in `registerListeners()`, re-render/re-filter entries whose `when` depends on the changed keys, and refresh `cachedWhen` from the live evaluation at that point instead of only at shutdown — as the reporter already proposes.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/editor/editorGroupWatermark.ts`
- **Validation:** A test or manual check: toggle `chat.disableAIFeatures` to true at runtime (no reload) and assert the watermark's `Open Chat` entry is removed; also verify an entry whose context becomes true again reappears.
- **Behavior:**

  > When a watermark entry's `when` context (e.g. chatSetupHidden/chatSetupDisabledInWorkspace becoming true via chat.disableAIFeatures) changes during the session — whether from a direct settings edit or an extension's configurationDefaults applied after first render — the watermark must re-evaluate and drop (or add) the affected entries without requiring a reload. cachedWhen must reflect the live state going forward, not just at shutdown.
- **Trace:**

  > editorGroupWatermark.ts registerListeners() subscribes only to onDidChangeConfiguration (for the watermark's own enablement setting) and contextService.onDidChangeWorkbenchState — never to contextKeyService.onDidChangeContext. filterEntries() checks cachedWhen[entry.id] first (short-circuiting to true even on a fresh render) and cachedWhen is only written in the onWillSaveState SHUTDOWN handler. The boundary: don't change the shutdown caching purpose (avoiding flicker on next session's initial render) — only add live re-evaluation while the window is open; don't touch the render()/filterEntries() general flow beyond what's needed to re-run on context changes.
- **Open decisions:**
  - Should cachedWhen be updated for every context change immediately, or only for entries whose `when` references the changed context keys (perf vs. simplicity tradeoff the reporter is asking about)?
  - Should the re-evaluation call render() wholesale or do a narrower incremental update of just the affected entries?
