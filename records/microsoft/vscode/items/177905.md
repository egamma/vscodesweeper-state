# Issue #177905 — Cannot drag file from one window to another

[https://github.com/microsoft/vscode/issues/177905](https://github.com/microsoft/vscode/issues/177905)

## Summary

The null-error modal is guarded on current source, but the central vscode.dev cross-window copy still has no working transfer path. Without a genuine fixing commit to cite, this accepted bug should remain open while the intended web behavior is decided.

## Change summary

Dragging a file between two vscode.dev Explorer windows fails to copy it and historically displayed a null-property error dialog.

## Best solution

Define the supported cross-window web Explorer behavior, then either transfer file contents between accessible provider contexts or reject the drop without an error dialog. Preserve ordinary native-file uploads and desktop Explorer drag-and-drop behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/browser/fileImportExport.ts`, `src/vs/workbench/browser/dnd.ts`, `src/vs/platform/dnd/browser/dnd.ts`
- **Validation:** Open two vscode.dev windows on different repositories and drag a file from one Explorer into the other: verify the maintainer-chosen copy or rejection behavior, verify no null-property dialog appears, and confirm dragging a native local file into each web Explorer still uploads successfully.
- **Behavior:**

  > Dragging a file between two vscode.dev Explorer windows must have a defined outcome. If cross-window copying is supported, the destination repository receives the file with its original contents; if the provider boundary cannot be crossed, the drop is rejected without an exception dialog or misleading success indication. Native-file uploads into vscode.dev must remain functional, and no path may display "Cannot read properties of null (reading 'name')".
- **Trace:**

  > FileDragAndDrop.onDragStart in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts calls fillEditorsDragData, which writes provider-backed file URIs to DataTransfers.RESOURCES, but writes CodeDataTransfers.FILES only for file-scheme resources. On the target web window, FileDragAndDrop.drop treats the browser event as NativeDragAndDropData and invokes BrowserFileUpload in src/vs/workbench/contrib/files/browser/fileImportExport.ts; that path consumes webkit filesystem entries rather than the serialized VS Code resource. BrowserFileUpload.doUpload now filters null webkitGetAsEntry() results, which addresses the cosmetic exception but leaves the cross-window copy absent. Keep desktop file-scheme drag-and-drop, normal web uploads, editor-area drops, and unrelated remote-to-local behavior outside the change boundary. Related but non-canonical issues are https://github.com/microsoft/vscode/issues/93599 and https://github.com/microsoft/vscode/issues/164.
- **Open decisions:**
  - When source and target vscode.dev windows use different filesystem-provider contexts, should an Explorer drop copy the file contents across windows, or should VS Code explicitly reject that operation without an error dialog?

## Evidence

- **current source path:** In src/vs/workbench/contrib/files/browser/views/explorerViewer.ts, FileDragAndDrop.onDragStart writes CodeDataTransfers.FILES only for file-scheme resources. On a web drop, FileDragAndDrop.drop routes NativeDragAndDropData to BrowserFileUpload rather than a resource-aware cross-window copy path.
- **remaining gap:** src/vs/workbench/browser/dnd.ts serializes provider-backed resources into DataTransfers.RESOURCES, but BrowserFileUpload in src/vs/workbench/contrib/files/browser/fileImportExport.ts consumes browser filesystem entries instead. A vscode.dev resource represented only by custom transfer data therefore is not copied into the target repository.
- **modal guard:** BrowserFileUpload.doUpload now checks the result of webkitGetAsEntry() and skips null entries before reading entry.name, preventing the reported null dereference. The checkout is a single root snapshot commit whose unrelated subject does not identify this issue or provide valid fix provenance, so it cannot support an implemented-on-main close.
- **maintainer direction:** The maintainer comment at https://github.com/microsoft/vscode/issues/177905#issuecomment-1479621155 says cross-window support was uncertain but explicitly confirms that showing a null modal is defective.
- **confirmed impact:** A second report at https://github.com/microsoft/vscode/issues/177905#issuecomment-2446169338 confirms the same null-property message on a web Explorer drop, although that native-file upload itself succeeds.
- **canonical search:** https://github.com/microsoft/vscode/issues/93599 is older but concerns remote-to-local desktop windows, while https://github.com/microsoft/vscode/issues/164 broadly tracks native application and clipboard integration. Neither reports the same vscode.dev cross-window symptom required for a duplicate close on this re-reviewed issue.
