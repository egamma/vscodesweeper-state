# Issue #338905 — Hide Migrations from the Customizations sidebar when no migrations are pending

[https://github.com/microsoft/vscode/issues/338905](https://github.com/microsoft/vscode/issues/338905)

## Summary

Confirmed from source: `updateSidebarMigrationShortcut()` in aiCustomizationManagementEditor.ts shows the sidebar Migrations shortcut whenever the migration feature setting is enabled, independent of whether there are any pending candidates — but an existing test ('keeps the unified sidebar entry reachable when all workspace migrations are skipped') shows the team deliberately keeps the entry visible at zero-count in at least the workspace-skip case, so a blanket 'hide at count 0' fix would regress that intent and needs a maintainer call on the exact semantics.

## Change summary

The Migrations sidebar entry (with warning icon) stays visible in the Customizations pane even after all pending migrations are completed.

## Best solution

Distinguish 'temporarily zero because workspace migrations are skipped' (keep entry reachable, per the existing test) from 'genuinely nothing left to migrate anywhere' (hide the entry, or at least drop the warning icon) in updateSidebarMigrationShortcut(), src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagementEditor.ts.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagementEditor.ts`, `src/vs/workbench/contrib/chat/test/browser/aiCustomization/aiCustomizationManagementEditor.test.ts`
- **Validation:** A test in aiCustomizationManagementEditor.test.ts asserting `migrationShortcutContainer.style.display === 'none'` (and no warning icon/count) once every migration category is fully migrated with nothing skipped, while the existing 'keeps ... reachable when all workspace migrations are skipped' test continues to pass unchanged.
- **Behavior:**

  > When there are truly no pending or skipped-but-recoverable migrations across every category, the sidebar's 'Migrations' shortcut should not be shown with its warning icon suggesting action is needed. If a workspace-only migration is merely skipped (recoverable), the entry should remain reachable as today. If new migrations later become available, the entry should reappear. Acceptance: a new 'fully migrated, nothing skipped' scenario hides the shortcut; the existing skip-recoverable test keeps passing.
- **Trace:**

  > updateSidebarMigrationShortcut() (aiCustomizationManagementEditor.ts:1940) computes `enabled` purely from `isMigrationCategoryEnabled()` (line 3202), which only reflects the feature/enablement setting, never the actual candidate `count` computed a few lines above it. The existing test at aiCustomizationManagementEditor.test.ts:2629 documents that staying visible at count 0 is intentional for the 'all workspace migrations skipped' case. The open question is whether 'count === 0 and nothing skipped' should hide the entry entirely (vs. keep it reachable with a neutral, non-warning presentation) — do not simply gate on `count > 0`, as that regresses the skip-reachability test. Do not change the skip-filter logic itself (getMigrationCandidateStorage/migrationWorkspaceSkipped) — that behavior is out of scope.
- **Open decisions:**
  - When there are zero pending migrations everywhere (no skips involved), should the sidebar entry disappear entirely, or stay reachable with a neutral (non-warning) icon/label instead of the current warning treatment?
  - Should the 'keep entry reachable when workspace migrations are skipped' behavior be preserved as-is, or should skipped-but-inactive items also eventually stop showing the warning icon?
