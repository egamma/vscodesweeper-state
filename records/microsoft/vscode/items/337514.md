# Issue #337514 — automations screen has lots of error text that's unclear what it means

[https://github.com/microsoft/vscode/issues/337514](https://github.com/microsoft/vscode/issues/337514)

## Summary

Team-authored bug with no fix commit on main referencing this issue, so no mechanical evidence for a close — stays open. Traced the root cause from the attached screenshot and source: multiple unavailable-provider reasons get concatenated into one run-on sentence rendered as plain `<p>` text, producing the garbled, overflowing wall of text shown.

## Change summary

The Automations view's 'Some automations are unavailable' banner shows a long, confusing, overflowing block of concatenated error text when several providers are unavailable.

## Best solution

Restructure `formatUnavailableAutomationsMessage`/its rendering in automationsView.ts to present each unavailable provider's reason as a distinct, clearly separated line (or list item) instead of one flattened sentence, and ensure the description container wraps instead of overflowing.

- **Behavior:**

  > When two or more automation providers are unavailable and have distinct unavailableReason strings, the 'Some automations are unavailable' banner must present each provider's reason legibly and separately (not as one run-on sentence), and the description area must not visually overflow its container. Single-provider and no-reason cases are unaffected. Acceptance: a test on the message-building function confirms distinct, non-duplicated per-provider reason text, and the rendered description box contains the full text without visual overflow.
- **Trace:**

  > Root cause is two-fold: (1) formatUnavailableAutomationsMessage in automationCataloguePresentation.ts (lines 17-24) builds one long localized sentence via `reasons.join(' ')` when unavailableProviders.length > 1, giving no visual separation between providers' reasons; (2) automationsView.ts (lines 887-889, also used at line ~940 for the partial state) renders that string as plain `textContent` in a `<p class="automations-cards-state-description">`, whose CSS rule has no overflow/wrap handling, matching the clipped/overflowing box in the attached screenshot. The boundary: do not change the underlying IAutomationProviderDescriptor.unavailableReason data model or the catalogue-state logic in providerAutomationService.ts — this is presentation-only. Where uncertainty starts: whether the fix renders a list of DOM nodes (requiring automationsView.ts to build multiple elements instead of one string) or just reformats the localized string with clearer separators, and whether automationsAccessibility.ts (which also consumes unavailableProviders text, e.g. line ~130) needs the same restructuring for the accessible view.
- **Open decisions:**
  - Should each unavailable provider's reason render as its own list item/line in the DOM, or is a better-formatted single sentence (with clearer separators/punctuation) sufficient?
  - Should the accessible view (automationsAccessibility.ts) get the same restructured presentation, or is its current plain-text summary acceptable as-is?
  - If reasons are identical across providers (as in the screenshot), should they be deduplicated/merged rather than repeated per provider?
