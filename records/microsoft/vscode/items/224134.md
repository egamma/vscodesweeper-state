# Issue #224134 — OnClick and hover events on gutter icons

[https://github.com/microsoft/vscode/issues/224134](https://github.com/microsoft/vscode/issues/224134)

## Summary

Keep open: extensions still lack general click and hover events for gutter decorations. The existing context-menu contribution does not satisfy this request, and the 51 upvotes support retaining the accepted Backlog item.

## Change summary

Expose gutter-decoration interactions so extensions can create or remove line decorations when users click or hover.

## Best solution

Define a supported extension API for gutter-decoration activation and hover interaction, preserving breakpoint behavior and providing accessible interaction alternatives. Coordinate its contract with the existing glyph-margin API and multiple-decoration discussions rather than treating the context-menu workaround as completion.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTextEditors.ts`, `src/vs/workbench/api/common/extHostTypeConverters.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadEditors.ts`, `src/vs/editor/contrib/hover/browser/glyphHoverComputer.ts`, `src/vs/workbench/contrib/testing/browser/testingDecorations.ts`
- **Validation:** Use an extension-development fixture that contributes a gutter decoration and records interactions. Verify that left-click identifies the correct document, line, and decoration; hover follows the agreed notification contract; removing decorations stops subsequent notifications; and existing breakpoint, testing, and right-click menu behavior remains intact. Include an overlapping-decoration case and keyboard/screen-reader checks under the chosen contract.
- **Behavior:**

  > An extension can respond to clicking or hovering its gutter decoration and create or remove decorations on the affected line. Existing gutterIconPath rendering, context-menu contributions, and hover text do not provide these general interaction notifications. Acceptance must demonstrate correct decoration identity, document and line targeting, lifecycle behavior, and compatibility with breakpoints and testing. The final public contract must also specify accessible activation and how overlapping decorations receive interactions.
- **Trace:**

  > The public decoration contracts in src/vscode-dts/vscode.d.ts provide rendering and hover content but no click or hover events. Decoration conversion runs through src/vs/workbench/api/common/extHostTypeConverters.ts and the text-editor bridge in extHostTextEditors.ts and mainThreadEditors.ts. Built-in testing handles editor.onMouseDown directly in testingDecorations.ts, while glyphHoverComputer.ts reads internal glyphMarginHoverMessage content. EditorLineNumberContextMenu supplies right-click menu actions, not arbitrary decoration activation. Preserve these existing behaviors; do not assume internal zIndex support is already public API. Coordinate with https://github.com/microsoft/vscode/issues/47559 and https://github.com/microsoft/vscode/issues/179725; neither was verified as covering the complete click-and-hover event request under the re-review rules. The uncertainty is the public interaction contract, not whether rendering icons is already possible.
- **Open decisions:**
  - Should extensions receive decoration activation events, associate commands with decorations, or have both capabilities?
  - What hover contract should be exposed: enter/leave notifications, hover-content provision, or both?
  - When decorations overlap, which decoration receives activation and hover, and how can users access the remaining actions without changing breakpoint behavior?

## Evidence

- **Current API gap:** src/vscode-dts/vscode.d.ts exposes gutterIconPath through ThemableDecorationRenderOptions and hoverMessage through DecorationOptions, but these decoration contracts expose neither click handlers nor hover events, and no decoration zIndex option. Displaying hover text is not notification of a hover interaction.
- **Existing capability is only a workaround:** src/vs/workbench/services/actions/common/menusExtensionPoint.ts registers editor/lineNumber/context. EditorLineNumberContextMenu.doShow in src/vs/workbench/contrib/codeEditor/browser/editorLineNumberMenu.ts handles right-click or macOS Ctrl-click and passes lineNumber and uri to menu actions; it does not expose arbitrary decoration left-click or hover events.
- **Built-in interactions are internal:** src/vs/workbench/contrib/testing/browser/testingDecorations.ts:446–460 listens to internal editor.onMouseDown and dispatches to test decorations. Its click implementation checks the glyph-margin target and lane. src/vs/editor/contrib/hover/browser/glyphHoverComputer.ts renders internal glyphMarginHoverMessage content; neither mechanism establishes a general public extension interaction API.
- **Closed predecessor does not prove completion:** https://github.com/microsoft/vscode/issues/5455 is closed, but its discussion distinguishes the context-menu solution from direct icon activation. https://github.com/microsoft/vscode/issues/5455#issuecomment-1790651824 accepts the menu for one extension's needs, while https://github.com/microsoft/vscode/issues/5455#issuecomment-1843821658 explicitly asks whether clicking an icon can execute an action. A closed issue cannot serve as the duplicate canonical.
- **Related open design work:** https://github.com/microsoft/vscode/issues/179725 remains open and proposes multiple-decoration layout, overflow, click handlers, and extension-contributed actions. https://github.com/microsoft/vscode/issues/179725#issuecomment-1507526626 explicitly separates rendering priority from click-handler work. The merged https://github.com/microsoft/vscode/pull/179910 implements glyph rendering by zIndex, not this public interaction API.
