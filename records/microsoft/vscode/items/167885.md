# Issue #167885 — Editor find input controls are visually grouped but not programmatically associated / focus order inconsistent

[https://github.com/microsoft/vscode/issues/167885](https://github.com/microsoft/vscode/issues/167885)

## Summary

Keep open: current source still lacks separate semantic associations for the Find and Replace controls and retains the intentionally interleaved focus order. The maintainer has identified UI reorganization as the direction, so this needs a design decision rather than closure or a tab-order-only fix.

## Change summary

Programmatically associate find and replace options with their respective inputs and reconcile keyboard navigation with the visual grouping.

## Best solution

Agree on an editor Find/Replace layout that communicates each input's associated options while preserving the maintainer's requirement for quick navigation between the two fields. Validate the resulting visual structure, accessibility tree, and forward/reverse keyboard navigation together.

- **Validation:** After the maintainer agrees on the layout, open editor Find with Replace collapsed and expanded; inspect the accessibility tree and traverse every control with Tab and Shift+Tab. Confirm each input's options have an identifiable semantic association, focus follows the agreed visual structure, quick Find/Replace switching remains available, and VoiceOver or NVDA communicates the distinction between Find options and Preserve Case.
- **Behavior:**

  > Find options should be programmatically identifiable as belonging to Find, and Preserve Case as belonging to Replace. Opening Replace should not leave keyboard users navigating an unexplained sequence that conflicts with the visual relationships. The agreed experience must preserve efficient switching between Find and Replace, which the maintainer explicitly requires. Acceptance covers both expanded and collapsed states, forward and reverse navigation, and screen-reader identification of the associated controls.
- **Trace:**

  > FindWidget._buildDomNode in src/vs/editor/contrib/find/browser/findWidget.ts constructs separate visual find-part and replace-part containers, but neither exposes a named semantic group. The shared FindInput and ReplaceInput classes in src/vs/base/browser/ui/findinput individually label inputs and toggles without grouping them by purpose. _onFindInputKeyDown and _onReplaceInputKeyDown explicitly produce Find input → Replace input → Find options, followed by Preserve Case through the regex handler. https://github.com/microsoft/vscode/pull/172979 adds an outer dialog role but deliberately leaves this focus order unchanged. The maintainer at https://github.com/microsoft/vscode/issues/167885#issuecomment-1854817829 requires quick switching between fields and suggests UI reorganization; do not treat adding extra intervening tab stops as an already-approved solution. https://github.com/microsoft/vscode/issues/91211 is related visual-label design work, not a canonical for this semantic and navigation request. The unresolved boundary is the user-visible layout and navigation contract; shared input widgets also have consumers beyond editor Find, so avoid unintended changes to those surfaces.
- **Open decisions:**
  - What visual grouping and keyboard-navigation sequence should reconcile identifiable Find/Replace option groups with the maintainer's requirement to switch quickly between the two inputs?
