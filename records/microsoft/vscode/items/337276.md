# Issue #337276 — Automations: optionally skip a run while a previous session is still running

[https://github.com/microsoft/vscode/issues/337276](https://github.com/microsoft/vscode/issues/337276)

## Summary

Team-authored feature request (author is a maintainer), only 1 day old, parked in Backlog — no evidence supports a close; keeping open as under-discussion since the author's own issue body flags open design questions.

## Change summary

Add an opt-in per-automation setting so a scheduled/triggered run is skipped (not queued or cancelled) while a prior run's session is still active.

## Best solution

Design and implement an overlap guard in the automation trigger/scheduling path (likely server/Agent-Host side, coordinated with IAutomationService.runAutomation and the existing 'alreadyRunning' result) that atomically checks run state before dispatch and surfaces a 'skipped: previous run still running' occurrence in the UI.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/automations/automationService.ts`, `src/vs/sessions/contrib/automations/browser/automationRunner.ts`, `src/vs/sessions/contrib/automations/browser/providerAutomationService.ts`
- **Validation:** A test asserting a scheduled trigger occurrence is recorded as 'skipped' (with the still-running reason) instead of dispatching a new run when the option is enabled and a prior session for the same automation is still active, plus a concurrency test that two simultaneous triggers cannot both dispatch a run.
- **Trace:**

  > Established that no skip/overlap-guard code exists today: automationRunner.ts's run() always calls automationService.runAutomation and only reports an already-running session back to the caller (for manual Run Now), it never skips a scheduled trigger occurrence. The design starting point is IAutomationService (automationService.ts) and wherever trigger scheduling lives (likely Agent-Host/provider side, not fully visible in this repo) — https://github.com/microsoft/vscode/issues/337276.
- **Open decisions:**
  - What exactly counts as 'still running' — does a session awaiting user input/approval count, or only actively executing sessions?
  - Where does the atomic overlap check live — client-side in automationRunner, or must it be enforced by the Agent Host/provider to be race-free across triggers?
  - How is the per-automation opt-in setting surfaced and stored (automation config schema vs. a new UI toggle)?

## Evidence

- **no existing skip mechanism:** src/vs/sessions/contrib/automations/browser/automationRunner.ts has no overlap/skip logic for scheduled triggers; grep for 'skip|overlap|still running|concurrent' returns nothing.
- **related but distinct capability:** IAutomationService.runAutomation already returns an 'alreadyRunning' result kind (src/vs/workbench/contrib/chat/common/automations/automationService.ts:153) used by the manual 'Run Now' path in automationRunner.ts, but that surfaces the existing run rather than silently skipping a scheduled trigger occurrence with a recorded skip reason — the requested behavior is a distinct, unimplemented feature.
- **self-identified open design question:** The issue body itself says 'The precise definition of "still running" ... should be documented as part of the design,' i.e. the author flags unresolved scope before implementation.
