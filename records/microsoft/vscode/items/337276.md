# Issue #337276 — Automations: optionally skip a run while a previous session is still running

[https://github.com/microsoft/vscode/issues/337276](https://github.com/microsoft/vscode/issues/337276)

## Summary

Keep open: current automation scheduling already prevents overlapping runs unconditionally, but it does not provide the requested per-automation option or record blocked occurrences as skipped. The remaining work needs a design decision about disabled-option behavior against today's serialized scheduling.

## Change summary

Offer an opt-in, atomic per-automation overlap guard that records skipped occurrences and their reason without queuing work or cancelling the existing session.

## Best solution

Define a per-automation overlap policy and an observable skipped-occurrence contract across host scheduling, persisted history, and the automation UI. Preserve existing definitions deliberately, and coordinate with the related sleep/timeout discussion without expanding this request into timeout redesign.

- **Validation:** Extend agentHostAutomationService.test.ts with fake-timer cases covering a due trigger during an active run, a persisted skipped occurrence and reason, no deferred replay of that occurrence, normal execution after completion, simultaneous admission, and the chosen disabled/absent-option behavior. Add adapter/UI coverage for displaying the skipped reason and preserving the configured policy across edits and reloads.
- **Behavior:**

  > When the per-automation guard is enabled, a trigger arriving while an earlier run remains active creates no new session and records that occurrence as skipped because the previous session is still running. The skipped occurrence is not queued and does not cancel the existing session; later triggers execute normally after completion. Concurrent triggers cannot both admit sessions under the guard. The design must document active-session semantics and establish compatible behavior for disabled or absent configuration.
- **Trace:**

  > AgentHostAutomationService._scheduleNext excludes automations with _activeRunFor, while _claimDueRuns exits before processing their schedule cursors; this is unconditional serialization, not the requested configurable skip accounting. _createManualRun separately returns the active run, and mutations are serialized through _enqueueMutation. AutomationDefinition has no overlap policy, and protocol/workbench run-status models have no skipped outcome. Existing lifecycle documentation already counts sessions awaiting input or client work as running. Generated protocol files are inspection references, not direct-edit targets; shared-contract changes require coordination with the protocol source. Preserve manual request idempotency, unrelated automations, and existing cancellation/timeout behavior. https://github.com/microsoft/vscode/issues/341272 is related context for overlap policy, not a duplicate target or authorization to redesign sleep handling here.
- **Open decisions:**
  - When the option is disabled or absent on an existing automation, should today's serialized scheduling and catch-up behavior remain, or should later occurrences be allowed to start concurrently as the original request assumes?
