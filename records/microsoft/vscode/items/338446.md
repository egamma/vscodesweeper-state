# Issue #338446 — Clipped corners and missing borders in Modern High Contrast themes

[https://github.com/microsoft/vscode/issues/338446](https://github.com/microsoft/vscode/issues/338446)

## Summary

Real visual bug in the new experimental Modern UI feature: High Contrast themes aren't accounted for in the CSS that rounds/borders the editor part and floating panels, so overflow-hidden clipping applies without a compliant HC border to justify it — matching the reported clipped corners and missing borders.

## Change summary

Enabling workbench.experimental.modernUI with a Default High Contrast theme clips the editor's rounded corners and drops borders on the editor tabs and actions bar.

## Best solution

Add High Contrast overrides to the Modern UI editor-border and floating-panel CSS (matching the `:is(.hc-black, .hc-light)` pattern already used in activityBar.css/tabs.css) — either flatten corner radii in HC or ensure a visible HC-compliant border color accompanies the rounding, and audit the tab/action-bar border selectors for the same gap.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/modernUI/browser/media/editorBorder.css`, `src/vs/workbench/browser/media/floatingPanels.css`, `src/vs/workbench/contrib/modernUI/browser/media/tabs.css`, `src/vs/workbench/contrib/modernUI/browser/media/connectedEditorTabs.css`
- **Validation:** Manually toggle workbench.experimental.modernUI on with Default High Contrast Light/Dark and confirm the editor frame, tab left border, and actions-bar right border render fully (no clipped corners, no missing borders), matching the screenshots in the issue.
- **Behavior:**

  > With `workbench.experimental.modernUI` enabled and a Default High Contrast (Light or Dark) theme active, the editor area's card frame should render with a visible, HC-compliant border and either square or intentionally-rounded corners — not a rounded/clipped corner with an invisible or missing border. Editor tabs must show all four borders (including the left one), and the editor actions toolbar must show its right border. Non-HC themes are unaffected.
- **Trace:**

  > src/vs/workbench/contrib/modernUI/browser/media/editorBorder.css draws `.part.editor` with `border-radius: var(--vscode-cornerRadius-large)` and `overflow: hidden` unconditionally; its border color falls back to a 12%-mix (`color-mix(in srgb, var(--vscode-foreground) 12%, transparent)`), which is not how HC themes render meaningful borders. src/vs/workbench/browser/media/floatingPanels.css rounds panel/sidebar/auxiliarybar corners the same way with no HC branch. By contrast, src/vs/workbench/contrib/modernUI/browser/media/tabs.css and activityBar.css already special-case `:is(.hc-black, .hc-light)` for related concerns, showing the established pattern this code is missing. Do not touch non-HC rendering or the core (non-modernUI) editor chrome; scope changes to the `.modern-ui`-gated HC selectors only. No related open issue found.
- **Open decisions:**
  - In High Contrast themes, should Modern UI corners/borders flatten to square edges (matching HC's flat aesthetic) or keep rounding but with an explicit HC-compliant border color/width?
  - Should the editor tabs' HC border/x-button-centering issue and the actions-bar missing-border issue be fixed as one pass or tracked as separate follow-ups?

## Evidence

- **no HC guard on editor border:** src/vs/workbench/contrib/modernUI/browser/media/editorBorder.css rounds and borders `.part.editor` (`border-radius: var(--vscode-cornerRadius-large)`, `overflow: hidden`) with no `:is(.hc-black, .hc-light)` exclusion or override, unlike activityBar.css and tabs.css which do gate HC (e.g. tabs.css:53, :285-286).
- **no HC guard on floating-panel rounding:** src/vs/workbench/browser/media/floatingPanels.css applies `border-radius: var(--vscode-cornerRadius-large)` in multiple rules with zero HC-specific overrides found via grep.
- **very recent feature:** Both files' last touching commit (9cd7e663, 2026-09-30) is part of ongoing Modern UI work; the feature (`workbench.experimental.modernUI`, described at src/vs/workbench/browser/workbench.contribution.ts:837) is still an active experiment, consistent with an HC gap not yet addressed.
