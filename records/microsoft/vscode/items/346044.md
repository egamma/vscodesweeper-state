# Issue #346044 — Agents window can't use a non-default profile

[https://github.com/microsoft/vscode/issues/346044](https://github.com/microsoft/vscode/issues/346044)

## Summary

Keep open: current source explicitly binds the Agents window to its internal, default-backed profile. Supporting non-default profiles and defining shared-state semantics require a product decision; the related customization and model-pin fixes do not resolve that broader gap.

## Change summary

Allow the Agents window to use a non-default profile and establish consistent sharing rules for profile-backed state.

## Best solution

Define how the Agents window selects its backing profile and which state remains profile-isolated versus shared across windows. Implement that contract consistently in window initialization, profile resources, and state storage rather than accumulating feature-specific exceptions.

## Plan brief

- **Likely files:** `src/vs/platform/windows/electron-main/windowsMainService.ts`, `src/vs/platform/userDataProfile/common/userDataProfile.ts`, `src/vs/platform/userDataProfile/electron-main/userDataProfile.ts`, `src/vs/workbench/contrib/userDataProfile/browser/userDataProfile.ts`
- **Validation:** After agreeing on the contract, exercise Default and Work profiles with distinguishable settings, model configuration and model pins; open and reload the Agents window and verify its selected resources and state sharing match that contract. Add focused regression cases to src/vs/platform/userDataProfile/test/electron-main/userDataProfileMainService.test.ts for the agreed resource-inheritance behavior.
- **Behavior:**

  > An editor using a non-default Work profile currently opens an Agents window backed by Default resources and separate internal-profile state. The goal is a supported, predictable relationship between the Agents window and user profiles. Acceptance must cover opening, switching and reloading windows with distinguishable Default and Work settings and model state, while preserving isolation wherever the agreed contract requires it.
- **Trace:**

  > windowsMainService.ts selects the internal Agents profile before loading every sessions window, bypassing normal profile resolution. userDataProfile.ts defines AGENTS_WINDOW_PROFILE_FLAGS with default-resource inheritance but without globalState, and toUserDataProfile constructs the resulting separate storage location. The Preferences profile submenu is excluded for sessions windows in the userDataProfile contribution. These source paths establish the limitation without executing the application; uncertainty starts at the desired profile-selection and persistence contract. https://github.com/microsoft/vscode/pull/343386 addresses specific globally shared switches, while https://github.com/microsoft/vscode/pull/346052 addresses model-pin identity matching; neither settles this design. Preserve ordinary editor profile behavior and avoid treating all profile state as globally shareable without an explicit decision.
- **Open decisions:**
  - Should the Agents window follow the launching editor's profile, expose an independently persisted profile choice, or support both?
  - Which state should remain isolated by the selected profile, which should be shared with editor windows using that profile, and which should be application-wide?
  - When editor windows use different profiles, should changing the Agents window's backing profile affect existing sessions or only subsequently opened sessions?
