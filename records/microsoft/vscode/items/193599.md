# Issue #193599 — Highlight confusable Unicode characters for file explorer

[https://github.com/microsoft/vscode/issues/193599](https://github.com/microsoft/vscode/issues/193599)

## Summary

This remains a valid, accepted Explorer feature request: current main renders filenames without Unicode-confusable analysis, and no older open issue reports the same Explorer symptom. As a team-authored item in the Backlog milestone with maintainer support, it should remain open for design and implementation.

## Change summary

Highlight visually confusable Unicode characters when different scripts are mixed within an Explorer file or folder name.

## Best solution

Reuse the existing Unicode-confusable analysis for Explorer resource labels while preserving find-match highlighting, compressed-folder labels, locale exceptions, theming, and an equivalent non-visual warning for screen-reader users. First settle whether the behavior is Explorer-specific or applies to every shared ResourceLabel surface.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/browser/labels.ts`, `src/vs/editor/common/services/unicodeTextModelHighlighter.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Add an Explorer browser test that renders Latin-only, Cyrillic-only, and mixed Latin/Cyrillic filenames and verifies that only the confusable character in the mixed-script name receives the warning presentation, without losing existing find-match ranges; include an accessibility assertion for the warning text.
- **Behavior:**

  > When a file or folder name mixes scripts and contains a character confusable with basic ASCII, the Explorer makes that character perceptibly distinct. Names written consistently in one script are not warned merely for containing non-ASCII text. Existing Explorer filtering, compressed-folder navigation, decorations, and filename readability remain unchanged. The warning must also be conveyed without relying solely on color or sight.
- **Trace:**

  > Explorer rows flow through FilesRenderer.renderStat in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts, which supplies the filename and find-filter `matches` to ResourceLabel.setResource. ResourceLabelWidget in src/vs/workbench/browser/labels.ts forwards those ranges to IconLabel but performs no Unicode analysis. UnicodeTextModelHighlighter.computeUnicodeHighlightReason in src/vs/editor/common/services/unicodeTextModelHighlighter.ts already identifies ambiguous characters with locale-aware rules, and the issue discussion explicitly points to that implementation. The boundary is filename presentation: do not alter filesystem identity, normalization, sorting, or editor-content behavior, and preserve existing find-match and compressed-label semantics. The uncertainty begins at whether this policy belongs only in Explorer or in the shared ResourceLabel abstraction used by tabs, breadcrumbs, SCM, and other workbench surfaces.
- **Open decisions:**
  - Should confusable-character warnings be limited to Explorer file and folder names, or consistently appear in every workbench surface that uses ResourceLabel?
  - Should Explorer follow the editor's configured Unicode-highlight options and locale exceptions, or use a fixed mixed-script filename policy?
  - What user-facing accessible representation should accompany the visual warning: an annotated tree-item name, contextual detail, or another non-visual warning?
