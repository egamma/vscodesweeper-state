# Issue #333722 — Report Issues doesn't show editor while in Automations

[https://github.com/microsoft/vscode/issues/333722](https://github.com/microsoft/vscode/issues/333722)

## Summary

Real, traceable layout bug in the Agents Window: opening the Report Issue editor while a custom view (Automations) is active doesn't reveal the editor, and there's no way to force it via the layout toolbar since the custom view suppresses the editor grid node regardless of partVisibility.editor. Team-authored (COLLABORATOR), but no factual fix-commit exists yet, so it stays open per policy anyway.

## Change summary

While the Automations custom view is showing in the Agents Window, opening Report Issue (an editor) produces no visible editor and no layout control to reveal it.

## Best solution

Have explicit editor opens like Report Issue dismiss the active custom view (mirroring the documented rule that 'explicit session and chat open actions dismiss the active custom view'), likely in workbench.ts's onWillOpenEditor/revealEditorOnOpen path.

## Plan brief

- **Likely files:** `src/vs/sessions/browser/workbench.ts`, `src/vs/sessions/browser/singlePaneWorkbench.ts`, `src/vs/sessions/services/customView/browser/customViewService.ts`
- **Validation:** A workbench/layout-controller test asserting that opening an editor (e.g. via the issue reporter input) while a custom view is active dismisses the custom view and reveals the editor part.
- **Behavior:**

  > When a custom view (e.g. Automations) is active and the user triggers Report Issue (or another explicit editor-opening action), the resulting editor should be visible — the custom view should be dismissed the same way it already is for explicit session/chat opens, per LAYOUT.md. Reactive/background editor opens should continue to preserve the custom view as documented.
- **Trace:**

  > workbench.ts's revealEditorOnOpen (~line 1278) reacts to editorService.onWillOpenEditor and only toggles partVisibility.editor; it never calls customViewService.hideCustomView(). _applyCustomViewGridVisibility (~line 2518) independently forces the editor grid node hidden whenever ICustomViewService.activeCustomView is set, so partVisibility.editor becoming true has no visible effect while a custom view is active. Boundary: do not change the mutual-exclusion invariant itself (custom view vs. Sessions Part/Editor/AuxBar/Panel) or the reactive-fallback behavior for session/chat lifecycle opens (LAYOUT.md, 'Custom views' section) — only decide which editor-open paths count as 'explicit' enough to dismiss the custom view.
- **Open decisions:**
  - Should every editor open (any IEditorService.openEditor call reaching the main groups) dismiss the active custom view, or only a specific allow-list of explicit user actions (Report Issue, Open File, etc.)?
  - Should dismissing the custom view on editor open also restore the previously-hidden Sessions Part/Auxiliary Bar/Panel, or leave them hidden until the user explicitly reopens the custom view?

## Evidence

- **custom view exclusivity:** src/vs/sessions/LAYOUT.md: 'A custom view is mutually exclusive with the Sessions Part, grid Editor, Auxiliary Bar, and Panel.' Only explicit session/chat opens are documented as dismissing it; editor opens are not.
- **traced code path:** src/vs/sessions/browser/workbench.ts revealEditorOnOpen() (~line 1278) only sets partVisibility.editor via setEditorHidden(false, true); it never calls this.customViewService.hideCustomView(). _applyCustomViewGridVisibility() (~line 2518) keeps the editor grid node hidden whenever a custom view descriptor is active, independent of partVisibility.editor, so the Report Issue editor input opens into a part still suppressed by the custom view.
- **no manual override:** layoutActions.ts / _applyCustomViewGridVisibility gate editor visibility on activeCustomView, not on a user-toggleable state, matching the reporter's observation that the top-right layout toolbar can't reveal the editor.
