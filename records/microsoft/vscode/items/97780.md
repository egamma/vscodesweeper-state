# Issue #97780 — Tab key when indenting with spaces does not insert correct number of spaces

[https://github.com/microsoft/vscode/issues/97780](https://github.com/microsoft/vscode/issues/97780)

## Summary

A real editor-command gap remains on current main: pressing Tab inside leading whitespace calculates insertion from the cursor column rather than indenting the line from its existing indentation. No open canonical issue fully covers the requested enabled-tab-stop behavior, so the Backlog request should remain open.

## Change summary

When the caret is anywhere inside leading space indentation, Tab should advance the entire line to the next indentation stop and place the caret at the end of that indentation.

## Best solution

Have the editor owner decide whether `editor.useTabStops` should make leading indentation atomic for the Tab command, matching the requested Xcode/TextMate behavior while preserving ordinary Tab insertion outside leading whitespace.

## Plan brief

- **Likely files:** `src/vs/editor/common/cursor/cursorTypeEditOperations.ts`, `src/vs/editor/test/browser/controller/cursor.test.ts`
- **Validation:** Add and run a focused cursor controller test in src/vs/editor/test/browser/controller/cursor.test.ts that starts with four leading spaces, places the caret at each position within that indentation, invokes CoreEditingCommands.Tab, and expects eight leading spaces with the caret at the indentation end; retain coverage that Tab outside leading whitespace remains cursor-relative.
- **Behavior:**

  > With space indentation and tab stops enabled, pressing Tab anywhere within a line's leading indentation should advance the whole line to the next indentation stop and leave the caret at the end of the resulting indentation. For a four-space-indented line and indent size four, pressing Tab from any caret position within those four spaces should produce eight leading spaces. Tab outside leading indentation and behavior when tab stops are disabled must remain explicitly defined and covered.
- **Trace:**

  > Tab input reaches TabOperation.getCommands in src/vs/editor/common/cursor/cursorTypeEditOperations.ts. For an empty selection on a line containing non-whitespace text, it calls _replaceJumpToNextIndent, which derives spaces from the caret's visible column and returns a ReplaceCommand over only that empty selection; the complete leading indentation and `config.useTabStops` are not consulted. This directly explains the four-spaces-plus-caret-at-column-2 result of seven spaces. Existing cursor tests in src/vs/editor/test/browser/controller/cursor.test.ts assert cursor-relative insertion in ordinary text but do not cover a caret within leading indentation. Preserve cursor-relative Tab behavior after the first non-whitespace character and avoid expanding the scope to mixed tab/space representation tracked by https://github.com/microsoft/vscode/issues/5394.
- **Open decisions:**
  - Should `editor.useTabStops: true` make Tab inside leading whitespace a whole-line indentation action that moves the caret to the indentation end, or should VS Code retain cursor-relative insertion there?

## Evidence

- **current source behavior:** In src/vs/editor/common/cursor/cursorTypeEditOperations.ts, TabOperation.getCommands routes an empty selection on a non-whitespace-only line to _replaceJumpToNextIndent; lines 868-881 calculate spaces solely from the caret's visible column and insert them at the selection, without considering the line's complete leading indentation.
- **source-confirmed example:** With four leading spaces, indentSize 4, and the caret at column 2, _replaceJumpToNextIndent computes three inserted spaces from visible column 1, producing the reported seven-space indentation rather than shifting the line to eight spaces.
- **existing test contract:** src/vs/editor/test/browser/controller/cursor.test.ts currently tests cursor-relative Tab insertion under 'Cursor honors insertSpaces configuration on tab', but has no case for treating a caret within leading whitespace as a whole-line indentation operation.
- **canonical search:** https://github.com/microsoft/vscode/issues/228286 is open but primarily requests fixed-width indentation when `editor.useTabStops` is disabled and also covers auto-indent; it does not fully own this issue's requested behavior when tab stops are enabled. https://github.com/microsoft/vscode/issues/5394 and https://github.com/microsoft/vscode/issues/42740 concern separate tab-display and indent widths, while https://github.com/microsoft/vscode/issues/63388 concerns preserving relative alignment across selected lines.
