# Issue #338959 — /vscode-pet is no longer showing up.

[https://github.com/microsoft/vscode/issues/338959](https://github.com/microsoft/vscode/issues/338959)

## Summary

Confirmed defect: once the pet is put 'on the run,' it becomes stuck with no reliable way to bring it back — the translateY offset in CSS and the small click target at default/shrunken scale make the restore click unreachable, and /vscode-pet doesn't clear the stuck onTheRun state, it only toggles overall enablement. A contributor already traced this in the thread; no fix has landed on main.

## Change summary

After putting the chat pet 'on the run,' it becomes invisible/unclickable and can't be restored, even via the /vscode-pet slash command.

## Best solution

Fix the restore path in the chat pet widget: either give the on-the-run state a guaranteed minimum clickable hit area regardless of scale, or have ChatPetService.toggle()/the /vscode-pet slash command clear the onTheRun flag so re-enabling always restores visibility.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/media/chatPet.css`, `src/vs/workbench/contrib/chat/browser/widget/chatPetWidget.ts`, `src/vs/workbench/contrib/chat/browser/chatPetService.ts`, `src/vs/workbench/contrib/chat/browser/chatSlashCommands.ts`
- **Validation:** A chat pet widget/service test that puts the pet on the run at a reduced scale, then confirms either (a) a minimum clickable hit area remains and clicking it restores the pet, or (b) re-running /vscode-pet (toggle) clears `chat.vscodePet.onTheRun` and the pet becomes visible again.
- **Behavior:**

  > When the chat pet is sent 'on the run' via the context menu, the user must always have a working way to bring it back — either a persistently clickable visible portion of the pet regardless of its current scale, or the /vscode-pet slash command reliably restoring full visibility. Acceptance: at every supported scale (100%, 60%, 40%), the pet either exposes a clickable hit region that calls setOnTheRun(false), or toggling the pet via /vscode-pet clears the stuck onTheRun state so the pet reappears normally.
- **Trace:**

  > Root cause has two contributing parts, both confirmed from source: (1) `.chat-pet-button.on-the-run` in chatPet.css applies a fixed `translateY(var(--vscode-spacing-size400))` (40px) regardless of the button's scale-dependent size from `_setScale`/`_getDisplaySize` in chatPetWidget.ts, so at reduced scales the whole button moves behind the chat input with no exposed hit area; (2) the /vscode-pet slash command (chatSlashCommands.ts line 80) calls `ChatPetService.toggle()`, which only flips `_enabled` (chatPetService.ts line 177) and never calls `setOnTheRun(false)`, so the persisted `chat.vscodePet.onTheRun` storage flag survives re-enabling and the pet reappears already hidden. Do not change the achievement/animation state machine or other transient states (dizzy, falling, etc.) — scope is limited to the on-the-run positioning/hit-area and the restore path. See contributor diagnosis in the issue thread for line-accurate citations matching this trace.
- **Open decisions:**
  - Should the restore mechanism be a guaranteed minimum clickable hit area at every scale, or should re-toggling the pet (via /vscode-pet or re-enabling) unconditionally clear the onTheRun state?
  - If a minimum hit area is added, how much of the pet must remain visible/clickable above the chat input at the smallest scale?

## Evidence

- **fixed CSS offset:** src/vs/workbench/contrib/chat/browser/widget/media/chatPet.css line ~328: `.chat-pet-button.on-the-run { transform: translateY(var(--vscode-spacing-size400)); }` applies a fixed 40px offset regardless of the button's scaled size.
- **scale-dependent button size:** src/vs/workbench/contrib/chat/browser/widget/chatPetWidget.ts `_setScale`/`_getDisplaySize` compute button dimensions as `CHAT_PET_SOURCE_SIZE/2 * scale`; at reduced scale (e.g. 40-60%) the button is smaller than the fixed 40px offset, hiding the entire clickable target behind the chat input.
