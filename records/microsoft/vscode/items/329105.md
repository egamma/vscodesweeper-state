# Issue #329105 — Support dictation in automation composer

[https://github.com/microsoft/vscode/issues/329105](https://github.com/microsoft/vscode/issues/329105)

## Summary

Keep open: existing dictation supports chat composers but does not cover the automation dialog's prompt editor or arbitrary text boxes. This team-authored request remains actionable, and no qualifying duplicate or explicitly linked fixing commit was found.

## Change summary

Support dictation in the automation composer, with a broader aspiration to dictate into arbitrary text boxes.

## Best solution

Provide editor-targeted dictation in the automation prompt composer without submitting a chat request or saving the automation. Decide separately whether arbitrary text-box support should share a general focused-input dictation contract.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/automations/browser/automationDialog.ts`, `src/vs/sessions/contrib/automations/browser/automationDialogService.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatSpeechToTextActions.ts`, `src/vs/workbench/contrib/chat/browser/speechToText/dictationSession.ts`, `src/vs/sessions/contrib/automations/test/browser/automationDialog.test.ts`
- **Validation:** Verify that dictation started with the automation prompt focused inserts the transcript into that prompt, leaves any previously focused chat unchanged, and neither submits a chat request nor saves the automation. Check stop/cancel, closing the dialog during recording, preservation of typed text, and keyboard command handling; cover targeting and dialog-command behavior in focused tests.
- **Behavior:**

  > Users can dictate an automation prompt while creating or editing an automation. The transcript goes into the intended prompt editor without sending a chat request or saving the form, and existing typed text remains intact. Stopping or cancelling dictation and closing the dialog must not leave recording active against a disposed editor. The broader request for arbitrary text boxes requires an explicit scope and targeting decision before its acceptance criteria can be finalized.
- **Trace:**

  > automationDialog.ts renderForm builds a ChatInputPart with MenuId.AutomationsDialogInput and a minimal stub widget; it does not register a normal chat-widget dictation target. ToggleChatSpeechToTextAction in chatSpeechToTextActions.ts selects an invocation widget or lastFocusedWidget, whereas NewChatInputWidget in newChatInput.ts has its own explicitly editor-targeted toggleDictation path. dictationSession.ts already supports an ICodeEditor through startDictation, but not arbitrary DOM text boxes. AutomationDialogService also restricts keyboard commands through automationDialogAllowableCommands. Preserve automation scheduling, persistence, and ordinary chat submission semantics; the uncertainty is the user-facing scope and target-selection contract, not which helper to reuse. https://github.com/microsoft/vscode/issues/325486 is related ordinary-chat speech work, not a verified duplicate.
- **Open decisions:**
  - Should this request deliver automation-prompt dictation first, or include arbitrary editable text boxes in the same feature?
  - For arbitrary text-box support, should dictation follow the currently focused input or remain attached to the input where recording began?
