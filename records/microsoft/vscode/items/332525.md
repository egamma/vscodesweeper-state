# Issue #332525 — Rename input does not provide horizontal scroll for long file names in Explorer

[https://github.com/microsoft/vscode/issues/332525](https://github.com/microsoft/vscode/issues/332525)

## Summary

A real Explorer usability gap remains for long names: rename uses a row-constrained single-line input with no visible scrolling affordance or expansion. It should stay open as polish and be routed to the file Explorer area.

## Change summary

Make long file and folder names comfortably viewable and editable in the Explorer's inline rename control.

## Best solution

Adopt a consistent long-text editing treatment for Explorer rename, either expanding the focused editor over available row content with a sensible maximum or providing an explicit horizontal navigation affordance, while preserving keyboard selection and tree layout behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/browser/media/explorerviewlet.css`
- **Validation:** In a narrow Explorer with horizontal scrolling enabled, rename a file whose name exceeds the viewport and verify that both ends are discoverable and editable using mouse and keyboard, F2 selection cycling still works, Enter/Escape retain their behavior, and normal tree horizontal scrolling is restored after editing.
- **Behavior:**

  > When a file or folder name is longer than the visible Explorer row, entering rename mode must provide an understandable way to reach and inspect the entire name. Keyboard caret movement, selection, F2 selection cycling, Enter confirmation, and Escape cancellation must continue to work. Ending rename must restore the Explorer's prior horizontal-scrolling state.
- **Trace:**

  > ExplorerItemRenderer.renderInputBox in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts creates a standard single-line InputBox and initially selects the basename. The edited control is constrained to the row by src/vs/workbench/contrib/files/browser/media/explorerviewlet.css, while ExplorerView.setEditable in src/vs/workbench/contrib/files/browser/views/explorerView.ts temporarily disables tree horizontal scrolling. These paths explain why enabling Explorer horizontal scrolling does not reveal more of the rename editor. Keep the change scoped to Explorer rename: do not alter generic InputBox behavior or tree scrolling outside edit mode. The unresolved design boundary is whether the focused editor expands over neighboring row content or remains row-bound with an explicit horizontal navigation affordance.
- **Open decisions:**
  - Should long-name rename expand over the Explorer row up to a maximum width, or remain constrained and expose a visible horizontal scrolling affordance?

## Evidence

- **layout constraint:** src/vs/workbench/contrib/files/browser/media/explorerviewlet.css:34-53 constrains the edited item and its InputBox to the Explorer row using flex sizing and width: 100%; the generic input styling also keeps the text control at width: 100%.
