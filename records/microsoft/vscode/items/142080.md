# Issue #142080 — An Extension API to initiate an OAuth2 authentication process using a "popup" browser window instead of opening a new tab for the same

[https://github.com/microsoft/vscode/issues/142080](https://github.com/microsoft/vscode/issues/142080)

## Summary

Keep open: the extension API still does not expose the OAuth popup experience available to trusted web-embedder URLs. This accepted Backlog request has 32 upvotes; the maintainer's latest statement indicates no current plans, not a scope rejection.

## Change summary

Allow web extensions to initiate OAuth authentication in a browser popup on vscode.dev, with URI-handler callbacks and a defined completion lifecycle.

## Best solution

Define a web-extension authentication popup contract that preserves opener isolation for arbitrary providers and explicitly addresses closing on completion or cancellation. Keep desktop authentication delegated to the external browser, as clarified in the discussion.

- **Reason:** Closing an extension-API gap would let authentication providers offer a more consistent web experience without bundling provider-specific functionality into core.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostWindow.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadWindow.ts`, `src/vs/workbench/browser/window.ts`, `src/vs/base/browser/dom.ts`
- **Validation:** After agreeing the contract, exercise a web extension on vscode.dev against a controlled OAuth provider outside the embedder allowlist: initiate sign-in from a user action, verify popup presentation without replacing the editor tab, complete and cancel authentication, verify URI-handler delivery and the agreed closure behavior, and exercise popup blocking. Confirm the provider cannot navigate the editor through window.opener and desktop/default openExternal behavior remains unchanged.
- **Behavior:**

  > A web extension using an OAuth provider other than the built-in Microsoft or GitHub providers should be able to request authentication in a browser popup instead of forcing navigation to another tab. The authentication redirect must still reach the extension's registered URI handler. Completion, cancellation and blocked-popup behavior must follow an explicit contract, including whether the popup closes automatically. Desktop authentication and ordinary external-link behavior remain unchanged.
- **Trace:**

  > env.openExternal in src/vs/workbench/api/common/extHost.api.impl.ts forwards through ExtHostWindow and MainThreadWindow.$openUri to the opener service without a popup option. BrowserWindow.setupOpenHandlers in src/vs/workbench/browser/window.ts chooses popup behavior from openerAllowedExternalUrlPrefixes, an embedder-only option declared in src/vs/workbench/browser/web.api.ts. src/vs/base/browser/dom.ts retains window.opener in windowOpenPopup but isolates ordinary external links with windowOpenNoOpener; these are not interchangeable trust contracts. The stable extension API provides callback URI resolution but no popup lifecycle control, and the proposed externalUriOpener API does not fill that gap. The uncertainty starts at the public behavior for arbitrary-provider popup isolation and automatic closing, raised at https://github.com/microsoft/vscode/issues/142080#issuecomment-1343366246. Preserve the desktop boundary clarified at https://github.com/microsoft/vscode/issues/142080#issuecomment-1343362973 and existing isolation for ordinary external links; browser popup-blocker behavior still needs runtime validation.
- **Open decisions:**
  - Must arbitrary-provider authentication popups support automatic closure on completion or cancellation, or is explicit manual closure an acceptable initial public contract?
  - Should the public contract be a web-only popup preference on external opening, or an authentication-specific capability with completion and cancellation lifecycle semantics?

## Evidence

The extension bridge in src/vs/workbench/api/common/extHost.api.impl.ts:470–474 and src/vs/workbench/api/browser/mainThreadWindow.ts:58–74 forwards tunneling and contributed-opener options, but no popup preference.
