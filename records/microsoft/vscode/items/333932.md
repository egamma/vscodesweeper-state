# Issue #333932 — Remember VS Code Layout Size When Switching Between Different Screen Sizes

[https://github.com/microsoft/vscode/issues/333932](https://github.com/microsoft/vscode/issues/333932)

## Summary

Current main retains one machine/profile-scoped sidebar size rather than separate sizes for different displays, so the requested per-display restoration remains a real layout capability gap. Route this to the layout area as a feature request rather than closing it against broader saved-layout work.

## Change summary

Remember and restore preferred sidebar and editor proportions when a window moves between displays with different dimensions.

## Best solution

Define display-aware layout persistence that restores each display configuration's preferred workbench-part dimensions without disrupting ordinary window resizing. The layout owners should first decide whether identity follows the physical display, its dimensions, or a user-selected saved layout.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/layout.ts`, `src/vs/platform/native/common/native.ts`, `src/vs/platform/native/electron-main/nativeHostMainService.ts`, `src/vs/workbench/services/host/electron-browser/nativeHostService.ts`
- **Validation:** Add a focused layout-state test covering two display/window configurations with distinct sidebar sizes, then manually move an Electron window from a large display to a smaller display and back and verify that each configured size is restored without overriding deliberate resizing on the active display.
- **Behavior:**

  > A VS Code window can retain distinct workbench-part dimensions for substantially different display configurations. After configuring the sidebar on a large display, moving to a smaller display and configuring it there, then returning to the large display restores the large-display preference. Ordinary resizing on the current display remains predictable, and restarting VS Code preserves the remembered preferences according to the chosen persistence contract.
- **Trace:**

  > In src/vs/workbench/browser/layout.ts, LayoutStateKeys.SIDEBAR_SIZE is a single profile/machine-scoped `sideBar.size` value, and the onWillSaveState handler stores only the currently rendered grid width. The panel and auxiliary bar use the same single-value pattern. NativeHostMainService in src/vs/platform/native/electron-main/nativeHostMainService.ts reports display topology or metrics changes, but the native contract in src/vs/platform/native/common/native.ts does not report a particular window crossing displays. The exact relative-sizing requests https://github.com/microsoft/vscode/issues/156240 and https://github.com/microsoft/vscode/issues/216717 were closed by the community lifecycle rather than implementation. The broader https://github.com/microsoft/vscode/issues/95182 remains related but does not settle whether restoration should be automatic. Preserve normal single-display resizing and do not expand the scope to arbitrary perspective management.
- **Open decisions:**
  - Should layout preferences be keyed to a physical display identity, display dimensions/scaling, or window-size classes when monitors cannot be identified reliably?
  - Should moving between displays restore layouts automatically, or should users select named saved layouts as contemplated by https://github.com/microsoft/vscode/issues/95182?
  - Should remembered values preserve absolute part dimensions, proportional dimensions, or both depending on the available display size?

## Evidence

- **current source:** src/vs/workbench/browser/layout.ts defines SIDEBAR_SIZE as the single `sideBar.size` InitializationStateKey at StorageScope.PROFILE and StorageTarget.MACHINE, then overwrites that value with the current grid width during onWillSaveState; there is no display-keyed size map.
- **platform boundary:** src/vs/platform/native/electron-main/nativeHostMainService.ts exposes `onDidChangeDisplay` only for display metrics/add/remove events, while src/vs/platform/native/common/native.ts exposes no event for a window moving from one display to another. Automatic restoration therefore requires design across the native-window and workbench-layout boundary.
- **prior exact request:** https://github.com/microsoft/vscode/issues/156240 requested percentage-based panel sizing when moving between differently sized monitors; it was closed only by the feature-request upvote lifecycle, not because the capability was implemented or declined on product grounds.
- **renewed exact request:** https://github.com/microsoft/vscode/issues/216717 renewed the same multi-display sizing request and included discussion of retaining values by resolution; it was also closed by the community upvote lifecycle.
- **related broader work:** https://github.com/microsoft/vscode/issues/95182 is an older open saved-layout/perspectives request whose comments describe switching between laptop and external-monitor layouts, but its central contract is manually selectable saved layouts rather than automatic per-display restoration, so it does not meet the stronger same-symptom duplicate bar for this re-reviewed item.
