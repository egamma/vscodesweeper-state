# Issue #243017 — Cannot remove folders from workspace (Profiles view)

[https://github.com/microsoft/vscode/issues/243017](https://github.com/microsoft/vscode/issues/243017)

## Summary

This is the accepted canonical request for removing stale explicit workspace associations from the default profile. It has 68 upvotes, is parked in the Backlog, and current main still deliberately disables the action, so it should remain open for a profiles-area design and implementation.

## Change summary

Allow users to remove obsolete folder and workspace paths shown under the default profile without manually editing profile storage.

## Best solution

Let users discard an explicit default-profile association while preserving the existing fallback that an unassigned workspace opens with the default profile. The Profiles view should no longer retain obsolete paths merely because there is no alternative profile assignment.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditor.ts`, `src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditorModel.ts`, `src/vs/workbench/services/userDataProfile/browser/userDataProfileManagement.ts`, `src/vs/platform/userDataProfile/common/userDataProfile.ts`, `src/vs/platform/userDataProfile/test/common/userDataProfileService.test.ts`
- **Validation:** Add a focused profile-service test proving that removing an explicit default-profile workspace association clears its persisted entry while profile lookup still falls back to the default profile; run it with `scripts/test.sh --grep 'remove default profile workspace association'`. Also verify in the Profiles editor that Delete Path removes a stale default-profile row and that reopening the folder still selects the default profile.
- **Behavior:**

  > A user can remove an obsolete folder or workspace path displayed under the default profile. Removing the explicit association must not make the workspace unusable or alter the normal rule that an unassigned workspace falls back to the default profile. The row must remain absent after reload, and existing change-profile behavior for non-default profiles must remain unchanged.
- **Trace:**

  > WorkspaceUriActionsColumnRenderer.createDeleteAction in src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditor.ts disables Delete Path when the row belongs to `getDefaultProfileToUse()`. UserDataProfileElement.updateWorkspaces and AbstractUserDataProfileElement.saveProfile in userDataProfilesEditorModel.ts already represent removal as an updated workspace list, but IUserDataProfileManagementService.updateProfile in src/vs/workbench/services/userDataProfile/browser/userDataProfileManagement.ts rejects default-profile updates. The lower-level UserDataProfilesService.updateProfile in src/vs/platform/userDataProfile/common/userDataProfile.ts can update default-profile workspace associations, persists only explicit associations, and profile resolution already falls back to the default when none exists. Keep non-default reassignment, current profile switching, agent-sessions workspace protection, and the separate persistence report https://github.com/microsoft/vscode/issues/254996 outside this issue's behavioral change.
- **Open decisions:**
  - Should removal be available for every explicit default-profile association, including an existing or currently open workspace, or only for paths that no longer exist?
  - Should the Profiles view continue displaying explicit default-profile associations with a removable action, or stop storing and presenting default associations because unassigned workspaces already resolve to the default profile?
