# Issue #224933 — Sidebar does not remember original width when it is forced to narrow due to a smaller window

[https://github.com/microsoft/vscode/issues/224933](https://github.com/microsoft/vscode/issues/224933)

## Summary

The defect remains source-reproducible on current main: a constrained window can shrink the low-priority side bar, but subsequent expansion gives the recovered space to the high-priority editor instead of restoring the side bar's previous width. The existing layout and grid-widget routing is appropriate.

## Change summary

Restore the side bar's user-selected width after a temporary window-size constraint forces it narrower.

## Best solution

Retain the last user-selected side bar width as its preferred target across constraint-driven window resizing, while preserving manual sash resizing, visibility toggling, and proportional-layout behavior.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/splitview/splitview.ts`, `src/vs/base/test/browser/ui/splitview/splitview.test.ts`, `src/vs/workbench/browser/layout.ts`, `src/vs/workbench/browser/parts/sidebar/sidebarPart.ts`
- **Validation:** Add a SplitView test that starts with a user-sized low-priority view, contracts the container until that view is forced narrower, expands to the original container size, and asserts that the user-selected width is restored; also verify that a later manual resize replaces the remembered target and existing visibility/proportional-layout tests remain unchanged.
- **Behavior:**

  > After a user sizes the primary side bar, temporarily making the window too narrow may reduce that width, but restoring sufficient window space must restore the user's prior side-bar width. A subsequent manual sash resize becomes the new preferred width. Hiding and showing the side bar, ordinary editor growth, and proportional layouts must retain their existing behavior.
- **Trace:**

  > The workbench deserializes its grid with proportional layout disabled in src/vs/workbench/browser/layout.ts. SidebarPart is low priority and EditorPart is high priority, so SplitView.layout in src/vs/base/browser/ui/splitview/splitview.ts consumes contraction and expansion deltas according to priority without retaining a pre-constraint target. The existing `low layout priority` test in src/vs/base/test/browser/ui/splitview/splitview.test.ts conclusively reproduces the loss by expanding a previously constrained low-priority view only to its minimum. Commit 8ef958807693b22e3c83a9f2ace226e8ca995c28 and https://github.com/microsoft/vscode/issues/334167 cover visibility restoration through `onViewChange`, not this window-layout path. Preserve that toggle fix, manual sash semantics, and proportional SplitView behavior.
- **Open decisions:**
  - Should constraint-driven width restoration apply only to the primary and auxiliary workbench side bars, or to every low-priority SplitView consumer such as terminal and sessions layouts?

## Evidence

- **current source path:** src/vs/workbench/browser/layout.ts constructs the workbench grid with `proportionalLayout: false`; src/vs/workbench/browser/parts/sidebar/sidebarPart.ts marks the primary side bar as `LayoutPriority.Low`, while src/vs/workbench/browser/parts/editor/editorPart.ts marks the editor as `LayoutPriority.High`.
- **source reproduction:** SplitView.layout in src/vs/base/browser/ui/splitview/splitview.ts applies each window-size delta to the high-priority views first. After the editor reaches its minimum, the side bar is forced narrower; when space returns, the editor consumes it first, and no prior side-bar target width is retained.
- **existing test contract:** The `low layout priority` test in src/vs/base/test/browser/ui/splitview/splitview.test.ts explicitly demonstrates the loss: sizes `[66, 68, 66]` contract to `[20, 20, 20]` and then expand to `[20, 160, 20]`, leaving the low-priority view at minimum size.
- **related issue:** https://github.com/microsoft/vscode/issues/333932 reports the same observable monitor-resize problem but was created after this re-reviewed issue, so it cannot serve as the older canonical; this issue is the better consolidation target.
- **different recent fix:** Commit 8ef958807693b22e3c83a9f2ace226e8ca995c28 fixes https://github.com/microsoft/vscode/issues/334167 by making visibility-triggered constraint changes priority-aware. It changes `SplitView.onViewChange`, not the `SplitView.layout` contraction-and-expansion behavior reported here.
- **unrelated API work:** The open https://github.com/microsoft/vscode/pull/330545 adds commands for extensions to get and set side-bar width; it does not automatically restore a width lost during window resizing and does not reference this issue.
