# Issue #337437 — Agent Host: Claude sessions are never reaped — 91 orphaned `claude` processes after 8 days, plus O(n) state broadcasts to unknown sessions

[https://github.com/microsoft/vscode/issues/337437](https://github.com/microsoft/vscode/issues/337437)

## Summary

Keep open: the reporter provided a confirmed long-running reproduction with severe memory pressure, and no older open issue owns the same process-accumulation and unknown-session broadcast symptoms. Current main contains residency and customization-storm safeguards, but the reported behavior contradicts those safeguards and still needs a focused lifecycle diagnosis.

## Change summary

Claude-backed Agent Host sessions retain live child processes after becoming Done, while customization updates repeatedly emit actions for removed or unknown sessions.

## Best solution

Ensure an archived or otherwise unobserved Claude session releases its live SDK runtime while preserving durable resumability, and prevent customization refreshes for removed sessions from producing unknown-session envelopes. Trace why the existing residency, subscription, and structural-dedup guards did not bound this workload; split the two fixes only if diagnosis shows independent causes.

- **Behavior:**

  > After a Claude-backed conversation becomes Done and no client still observes it, its live SDK child process must terminate while its durable transcript remains resumable. Keeping many completed conversations must not grow the number of live Claude processes without bound. A customization-source change may refresh relevant resident sessions, but it must not repeatedly emit actions for removed sessions or amplify into an O(N^2) envelope/log storm. Acceptance requires deterministic lifecycle and state-dispatch regressions covering release, later restoration, structural deduplication, and stale-session action suppression.
- **Trace:**

  > The report confirms that Done sessions retained and even respawned Claude children, despite current AgentSessionResidency in src/vs/platform/agentHost/node/agentSessionResidency.ts releasing archived or excess idle sessions through AgentService._releaseSession. ClaudeAgent._releaseChat in src/vs/platform/agentHost/node/claude/claudeAgent.ts aborts and disposes the live ClaudeAgentSession while retaining its backing for cold resume, so the uncertainty begins before or around release eligibility: a lingering subscription, hold, active-state classification, or missing archive transition may prevent that path. AgentSideEffects._publishSessionCustomizations already deduplicates identical snapshots, and ClaudeCustomizationWatcher excludes runtime-churn paths, but AgentHostStateManager.dispatchServerAction still logs an unknown session action and proceeds to emit its envelope. Preserve durable session data, reconnect/resume behavior, active-turn pinning, and customization publication for genuinely resident sessions; do not turn idle release into destructive deletion. Related lifecycle issue https://github.com/microsoft/vscode/issues/337153 has a different observable failure and is not a canonical duplicate.

## Evidence

- **confirmed impact:** The issue reports 91 live Claude child processes after eight days, about 8 GB RSS, 73,875 unknown-session warnings, and a burst that left the machine effectively unresponsive under compressor and swap pressure.
- **lifecycle follow-up:** https://github.com/microsoft/vscode/issues/337437#issuecomment-5792502811 reports that marking a session Done emitted no lifecycle event, retained its process, and that terminating the process caused Agent Host to rebuild it about one second later. The same window contained 337 tracked sessions but only nine visible conversations.
- **current residency path:** src/vs/platform/agentHost/node/agentSessionResidency.ts uses a default soft limit of 10 resident sessions and releases archived sessions even below that limit, provided no subscription, active turn, restore, or other hold blocks release. src/vs/platform/agentHost/node/agentService.ts routes that release through every catalog chat and then evicts session state.
- **Claude teardown path:** src/vs/platform/agentHost/node/claude/claudeAgent.ts::_releaseChat calls _disposeLiveSession for an idle live chat; that aborts the Claude session and removes its disposable entry. src/vs/platform/agentHost/node/claude/claudeSdkPipeline.ts wires disposal to AbortController.abort(), which is documented as terminating the SDK subprocess.
- **broadcast path:** src/vs/platform/agentHost/node/agentHostStateManager.ts logs a non-passive session action for an unknown session but continues to construct and emit its envelope. That matches the reported repeated `Action for unknown session` output rather than dropping the stale action.
- **existing storm mitigations:** src/vs/platform/agentHost/node/agentSideEffects.ts structurally deduplicates SessionCustomizationsChanged results and documents the prior O(N^2) fan-out; src/vs/platform/agentHost/node/claude/customizations/claudeSessionCustomizationDiscovery.ts also limits watcher triggers to customization-specific paths. The report therefore needs diagnosis of how removed sessions still enter this path, not another generic debounce.
- **canonical search:** The older related issue https://github.com/microsoft/vscode/issues/337153 concerns a long-running session hanging while loading history, not retained Claude processes or unknown-session customization broadcasts. Searches found no older open issue with the same reporter-observable symptoms and no open PR referencing this issue.
