# Issue #337437 — Agent Host: Claude sessions are never reaped — 91 orphaned `claude` processes after 8 days, plus O(n) state broadcasts to unknown sessions

[https://github.com/microsoft/vscode/issues/337437](https://github.com/microsoft/vscode/issues/337437)

## Summary

Thanks for the exceptionally thorough diagnosis. The source corroborates the core claim: idle-session eviction (`AgentService._evictSessionState`, which calls `IAgentChats.releaseChat` and actually tears down the live SDK process) fires only when a session loses its last subscriber (`_subscriptions.hasSessionSubscribers`); marking a session "Done" in the Sessions UI does not unsubscribe it, so neither the process nor the in-memory `_sessionStates` entry is ever released. `AgentHostStateManager.getSessionUris()` (backed by that same never-shrinking `_sessionStates` map) is exactly what `AgentSideEffects._publishSessionCustomizationsForAgent` fans a customization change out to, so the broadcast-storm symptom is a direct consequence of the same leak, not a separate bug.

## Change summary

Claude agent-host chat sessions (and their child `claude` processes) are never reaped after the UI marks them "Done", and stale session references accumulate O(n) customization-change broadcasts to "unknown" sessions.

## Best solution

Make the Sessions view actually drop its subscription (or otherwise signal completion) when a session is marked Done/archived so `AgentService`'s existing subscriber-based eviction (`_evictSessionState` / `releaseChat`) can run; separately, decide whether `AgentHostStateManager` should proactively drop a session from its broadcast set (or stop respawning a killed SDK process) rather than only reconciling lazily. Both are design decisions best made together with a maintainer who owns the Sessions view lifecycle.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentService.ts`, `src/vs/platform/agentHost/node/agentHostStateManager.ts`, `src/vs/platform/agentHost/node/agentSideEffects.ts`, `src/vs/platform/agentHost/node/claude/claudeAgent.ts`
- **Validation:** A test/harness that marks a session 'Done' (or otherwise closes it in the UI sense), asserts the corresponding subscription drops, that idle eviction (`_evictSessionState`/`releaseChat`) subsequently runs, and that a later customization-change broadcast no longer targets that session.
- **Behavior:**

  > Marking a chat session as 'Done'/closed in the Sessions UI should, within a bounded time, result in its backing SDK process being released (via the existing `releaseChat` path) and its session state removed from the broadcast set, so it neither holds memory/process resources nor receives further `session/customizationsChanged` (or other) broadcasts. Killing an idle backing process should not cause it to be silently and permanently respawned. Acceptance: after marking N sessions Done and waiting past the GC/eviction grace period, process count and `_sessionStates` size return to the count of only actively-subscribed/open sessions, and a subsequent customization change logs zero 'Action for unknown session' warnings for the closed sessions.
- **Trace:**

  > Eviction (`AgentService._evictSessionState`, agentService.ts:5952) and the `_runSessionGc` path (agentService.ts ~5931) are both gated on `this._subscriptions.hasSessionSubscribers(resource)` returning false; nothing in the current code unsubscribes a session purely because the Sessions UI moves it to the 'Done' group, so these sessions stay resident in `AgentHostStateManager._sessionStates` (agentHostStateManager.ts) indefinitely. That same map backs `getSessionUris()` (line 659), which `AgentSideEffects._publishSessionCustomizationsForAgent`/`_publishAllSessionCustomizations` (agentSideEffects.ts:533-548) iterate on every customization change, explaining the broadcast-storm symptom as a direct consequence of the leak. Separately, Claude's `_releaseChat` (claudeAgent.ts:1626) only tears down the live process, retaining `_chatBackings` for cold resume — the reporter's finding that killing the process spawns an immediate resume-on-send replacement is consistent with this by-design cold-resume path being triggered unexpectedly by something (unclear what) rather than a stray retry loop; that needs its own investigation. Boundary: do not change the resume-on-send contract for legitimately active sessions, and do not make `releaseChat` destructive (per the existing comment at agentService.ts:4784, it must stay non-destructive for idle eviction). Related reports the reporter already ruled out: https://github.com/microsoft/vscode/issues/337153, https://github.com/microsoft/vscode/issues/334159, https://github.com/microsoft/vscode/issues/332073, https://github.com/microsoft/vscode/issues/307401, https://github.com/microsoft/vscode/issues/334421.
- **Open decisions:**
  - Should marking a session 'Done' in the Sessions UI actively unsubscribe/release its backing process (freeing memory promptly), or is the current design intentionally lazy (keep-alive until VS Code-level idle/GC) and instead needs a lower idle timeout or a size/age cap?
  - Should `AgentHostStateManager`/`AgentSideEffects` proactively unregister a session's broadcast target on repeated 'unknown session' misses instead of re-warning indefinitely, and if so after how many misses or what condition?
  - Is the observed permanent respawn of a killed backing process (Claude) an intended cold-resume-on-send behavior misfiring, or does it need a cap/backoff on automatic resume?

## Evidence

- **eviction is subscriber-gated:** src/vs/platform/agentHost/node/agentService.ts:5952 `_evictSessionState` is only invoked on unsubscribe, and `_runSessionGc` (~5931) bails out via `this._subscriptions.hasSessionSubscribers(resource)` — a session with a live subscriber (even one just marked 'Done' in the UI) is never evicted.
- **eviction really does kill the process:** agentService.ts:4803 idle eviction calls `provider.chats.releaseChat(...)`, which for Claude (src/vs/platform/agentHost/node/claude/claudeAgent.ts:1626 `_releaseChat`) calls `_disposeLiveSession(target)` — confirming the mechanism exists and is not simply absent, just never triggered for 'Done' sessions.
- **broadcast fan-out reuses the same leaked set:** agentSideEffects.ts:533-548 `_publishSessionCustomizationsForAgent`/`_publishAllSessionCustomizations` iterate `this._stateManager.getSessionUris()`, i.e. `agentHostStateManager.ts:659 getSessionUris() = [...this._sessionStates.keys()]` — the same in-memory map the leak keeps growing, so every customization change refans to every never-evicted session.
- **AGENTS.md acknowledges the warning exists but as a small ordering race, not this scale:** src/vs/platform/agentHost/node/claude/phase6.5-plan.md:184 describes 'Action for unknown session' as a transient fork-ordering artifact fixed to count 0 in testing — the reporter's 73,875-occurrence, 156-distinct-session burst is a different order of magnitude, consistent with the leak rather than that known race.
- **related but distinct issues:** Reporter's own cross-references (#337153, #334159, #332073, #307401, #334421) were checked by them and none describe process accumulation or the unknown-session broadcast; no exact duplicate found in the candidate-canonical search either.
