# Issue #308442 — Feature Request: Native LM Studio Integration (like Ollama)

[https://github.com/microsoft/vscode/issues/308442](https://github.com/microsoft/vscode/issues/308442)

## Summary

Keep open: Custom Endpoint already enables LM Studio conversations and editing, but it does not deliver the requested native onboarding, model discovery, and CLI/server integration. With 75 upvotes and accepted Backlog status, the remaining work merits a scoped product decision rather than a completed or duplicate close.

## Change summary

Provide discoverable LM Studio integration with automatic model enumeration, provider configuration, and a coordinated local-runner launch experience.

## Best solution

Deliver an LM Studio onboarding experience that discovers available models and their usable capabilities without per-model JSON maintenance, reusing the existing endpoint transport. Decide whether this is a named provider or a generic local-endpoint workflow, and separate VS Code responsibilities from changes to LM Studio's CLI.

## Plan brief

- **Likely files:** `extensions/copilot/package.json`, `extensions/copilot/src/extension/byok/vscode-node/byokContribution.ts`, `extensions/copilot/src/extension/byok/vscode-node/customEndpointProvider.ts`, `extensions/copilot/src/extension/byok/vscode-node/abstractLanguageModelChatProvider.ts`, `extensions/copilot/src/extension/byok/vscode-node/test/customEndpointProvider.spec.ts`
- **Validation:** The plan should define provider tests using an LM Studio-shaped model-list response and a manual acceptance scenario: connect to a running local server, discover and select models without individual JSON entries, change the available models, refresh the list, and complete an agent file edit with a tool-capable model. Preserve existing manually configured Custom Endpoint behavior.
- **Behavior:**

  > Users should be able to connect LM Studio to VS Code chat without maintaining a separate JSON entry for every available model. The selected workflow should expose available models and usable capability/context metadata, and reflect changes to the server's model list. Existing manually configured endpoints must remain usable. Acceptance includes selecting a discovered tool-capable model and completing an actual workspace edit; server-launch behavior must be settled before implementation.
- **Trace:**

  > BYOKContrib._buildProviders registers providers in extensions/copilot/src/extension/byok/vscode-node/byokContribution.ts, and extensions/copilot/package.json declares their configuration surfaces. CustomEndpointBYOKModelProvider supports configured models and an optional generic discovery path; AbstractOpenAICompatibleLMProvider filters discovered models lacking known or resolved capabilities. No named LM Studio provider appears in those registrations. The discussion at https://github.com/microsoft/vscode/issues/308442 confirms that manual endpoint access is useful but leaves native discovery unresolved. Preserve current endpoint transport, manual configuration, and BYOK policy enforcement; do not treat unrelated local-model tool failures as part of this feature. The request for an lms launch command crosses into the external runner's CLI, and the built-in Ollama provider is now deprecated, leaving the intended integration boundary unsettled.
- **Open decisions:**
  - Should users receive a named LM Studio provider, or a generic local OpenAI-compatible endpoint workflow with equivalent automatic discovery?
  - Should VS Code connect only to an already-running server, or offer an explicit action to detect and start LM Studio, and which launch responsibilities remain with the external CLI?
