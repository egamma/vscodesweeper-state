# Issue #316431 — `vsce publish` validation doesn't check engine vs `@types/vscode` dependency correctly

[https://github.com/microsoft/vscode/issues/316431](https://github.com/microsoft/vscode/issues/316431)

## Summary

The validation gap is confirmed in the current `microsoft/vscode-vsce` source and is already tracked there by an older open issue with the same observable behavior. This should be moved to the owning repository and consolidated with that discussion rather than closed from the VS Code tracker.

## Change summary

`vsce` accepts an `@types/vscode` caret range whose resolved version can exceed the minimum supported `engines.vscode` version.

## Best solution

Consolidate this report into https://github.com/microsoft/vscode-vsce/issues/1063 and update `vscode-vsce` validation to compare the effective installed types version or otherwise prevent permissive ranges from bypassing its compatibility guarantee.

## Evidence

- **source reproduction:** Current https://github.com/microsoft/vscode-vsce/blob/main/src/validation.ts parses the declared `@types/vscode` range and compares its lower-bound version with `engines.vscode`, while `src/test/validation.test.ts` explicitly accepts `validateVSCodeTypesCompatibility('*', '^1.30.0')`; it never examines the version actually resolved in the lockfile or installed dependency graph.
- **existing canonical:** https://github.com/microsoft/vscode-vsce/issues/1063 is open, older than this report, and describes the same symptom: `@types/vscode: ^1.84.0` resolves to a newer API version while passing validation against `engines.vscode: ^1.84.0`.
- **consumer workaround:** https://github.com/Dart-Code/Dart-Code/pull/6149 adjusts one extension's dependency to restore its build, but does not fix the validator's range-handling behavior.
