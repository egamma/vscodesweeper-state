# Issue #232231 — Suggest to enable recommended extensions if they are disabled

[https://github.com/microsoft/vscode/issues/232231](https://github.com/microsoft/vscode/issues/232231)

## Summary

A real gap remains on current main: workspace recommendations discard every installed extension except those disabled by extension kind, so an installed extension disabled globally or for the workspace produces no enablement suggestion. The accepted Backlog request should remain open; no older open issue reports this same observable prompting behavior.

## Change summary

Prompt users to enable installed-but-disabled workspace-recommended extensions, rather than treating every installed extension as already satisfied.

## Best solution

Workspace recommendations should distinguish uninstalled extensions from installed-but-disabled ones and offer the appropriate install or workspace-enablement action, including a coherent experience when both kinds occur together.

## Vision fit

- **Fit:** aligned
- **Reason:** Making workspace recommendations reflect extension enablement state improves settings fidelity and the extension workflow without adding an unrelated core capability.
- **Evidence:** Durable themes: Workbench & core UX includes settings fidelity, and Extension ecosystem includes extension-management quality.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/extensions/browser/extensionRecommendationNotificationService.ts`, `src/vs/workbench/contrib/extensions/browser/extensionRecommendationsService.ts`, `src/vs/workbench/contrib/extensions/test/electron-browser/extensionRecommendationsService.test.ts`
- **Validation:** Extend the extension recommendations tests with disabled-global and disabled-workspace installed recommendations, asserting that an enablement suggestion appears while an installed enabled recommendation remains suppressed; also cover a mixed set containing an uninstalled and a disabled recommendation.
- **Behavior:**

  > Opening a workspace should surface a workspace recommendation when the recommended extension is installed but disabled. The resulting action should enable it in the intended scope rather than reinstall it, while installed and already-enabled recommendations remain suppressed. Uninstalled recommendations must retain their current install flow, including when both kinds are recommended together.
- **Trace:**

  > ExtensionRecommendationsService.promptWorkspaceRecommendations gathers workspace recommendations and delegates after a delay to ExtensionRecommendationNotificationService.promptWorkspaceRecommendations. In src/vs/workbench/contrib/extensions/browser/extensionRecommendationNotificationService.ts, the installed-extension filter excludes only DisabledByExtensionKind before treating every remaining installed extension as satisfying the recommendation; the notification path then assumes all retained entries need installation. EnableForWorkspaceAction in src/vs/workbench/contrib/extensions/browser/extensionsActions.ts demonstrates that EnabledWorkspace is already supported for an installed disabled extension. Existing tests explicitly expect no prompt whenever recommendations are installed, but do not model enablement state. Keep existing suppression for enabled extensions, ignored recommendations, and environment/kind/trust-imposed states; the uncertainty begins at the user-facing prompt and scope semantics for user-disabled recommendations.
- **Open decisions:**
  - Should accepting a recommendation enable a user-disabled extension only for the current workspace, or globally when it was disabled globally?
  - When recommendations mix uninstalled and installed-disabled extensions, should one notification expose separate Install and Enable actions or present the two groups separately?

## Evidence

- **current source gap:** In src/vs/workbench/contrib/extensions/browser/extensionRecommendationNotificationService.ts, promptWorkspaceRecommendations filters installed extensions only when their state is DisabledByExtensionKind; lines 190-194 still remove recommendations for DisabledGlobally and DisabledWorkspace extensions solely because they are installed.
- **install-only notification path:** The same file's promptRecommendationsNotification/showRecommendationsNotification path describes the action as Install and calls installGalleryExtensions; it has no branch for enabling an already-installed recommendation.
- **existing enablement capability:** src/vs/workbench/contrib/extensions/browser/extensionsActions.ts defines extensions.enableForWorkspace and applies EnablementState.EnabledWorkspace, so users can currently perform the operation manually from the extension UI, but workspace recommendations do not surface it.
- **existing test codifies current behavior:** src/vs/workbench/contrib/extensions/test/electron-browser/extensionRecommendationsService.test.ts contains 'No Prompt for valid workspace recommendations if they are already installed' without distinguishing enabled from disabled installations.
