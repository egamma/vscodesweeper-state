# Issue #162455 — Add a specific panel for TODO-style comments

[https://github.com/microsoft/vscode/issues/162455](https://github.com/microsoft/vscode/issues/162455)

## Summary

Keep this accepted, strongly supported request open: current diagnostics and Problems filters do not provide a first-class TODO category with an independently filtered view. The related diagnostic-severity request is newer and narrower, not a valid duplicate target for this re-reviewed item.

## Change summary

Provide a native way for language extensions to publish TODO comments separately from ordinary problems, with independent presentation and filtering.

## Best solution

Define a shared TODO publishing contract and an independently filtered TODO surface that consumes language-provided locations rather than rescanning source text. Settle compatibility and optional presentation before implementation, coordinating the diagnostic-category work with https://github.com/microsoft/vscode/issues/198454.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/platform/markers/common/markers.ts`, `src/vs/workbench/api/common/extHostDiagnostics.ts`, `src/vs/workbench/api/browser/mainThreadDiagnostics.ts`, `src/vs/workbench/contrib/markers/browser/markers.contribution.ts`, `src/vs/workbench/contrib/markers/browser/markersFilterOptions.ts`
- **Validation:** The plan should end with an executable API/workbench check using a fixture extension that publishes TODO(myname), TODO(othername), an informational diagnostic, a warning and an error. Verify TODO navigation and independent author filtering without hiding ordinary problems, correct updates/removal, and the agreed optional or legacy Problems presentation.
- **Behavior:**

  > Language extensions need a native way to publish syntax-aware TODO locations without treating them as ordinary problems or requiring a separate text-scanning extension. Users must be able to browse and filter TODOs independently, including filtering TODO(myname) without suppressing errors and warnings. Acceptance should exercise publication, updates, removal, navigation and independent filtering with mixed TODO and ordinary diagnostic entries. Whether TODOs remain available in Problems and whether the separate surface is optional must be settled with the maintainer.
- **Trace:**

  > The current public contract in src/vscode-dts/vscode.d.ts exposes four diagnostic severities and only Unnecessary/Deprecated tags; the corresponding MarkerSeverity, MarkerTag and IMarkerData in src/vs/platform/markers/common/markers.ts have no TODO category. DiagnosticCollection in src/vs/workbench/api/common/extHostDiagnostics.ts synchronizes marker data to MainThreadDiagnostics.$changeMany in src/vs/workbench/api/browser/mainThreadDiagnostics.ts, which publishes it through IMarkerService.changeOne. The Problems registration and settings live in src/vs/workbench/contrib/markers/browser/markers.contribution.ts; FilterOptions in markersFilterOptions.ts provides text/source filtering but no semantic TODO distinction or independent TODO surface. This inspection establishes the missing contract, not a complete design across language providers and the workbench. Preserve ordinary diagnostic severity, navigation and filtering behavior; do not assume core should scan source files. Coordinate with the younger category/filter request at https://github.com/microsoft/vscode/issues/198454; the Dart references at https://github.com/Dart-Code/Dart-Code/issues/5434 and https://github.com/Dart-Code/Dart-Code/issues/6118 document why existing Comments and setting toggles do not satisfy this request.
- **Open decisions:**
  - Should language extensions publish TODOs through a diagnostic category or through a separate TODO API, and what migration contract should existing diagnostic producers follow?
  - Should the separate TODO surface be optional, and should classified TODOs remain available in Problems for users who prefer the existing presentation?
