# Issue #175351 — Make the peek submodule contributable

[https://github.com/microsoft/vscode/issues/175351](https://github.com/microsoft/vscode/issues/175351)

## Summary

Keep open: the built-in Peek submenu still has no extension contribution point on current main, and the discussion explicitly supports exposing it. Existing custom-submenu contributions do not fill that gap, and the related open requests concern different surfaces.

## Change summary

Allow extensions to contribute commands to the existing editor-context Peek submenu instead of creating a separate Peek submenu.

## Best solution

Expose the existing MenuId.EditorContextPeek through the extension menu contribution contract, preserving the built-in submenu and its navigation commands. Keep custom peek-widget APIs and extension-authored command capitalization outside this request's scope.

## Plan brief

- **Likely files:** `src/vs/workbench/services/actions/common/menusExtensionPoint.ts`, `src/vs/editor/contrib/gotoSymbol/browser/goToCommands.ts`, `src/vs/platform/actions/common/actions.ts`
- **Validation:** In an Extension Development Host, register a test command and contribute it to the agreed Peek menu location. Verify it appears inside the existing built-in Peek submenu, executes when selected, honors its when clause and group ordering, and leaves built-in Peek actions unchanged without creating a second submenu.
- **Behavior:**

  > Extensions should be able to place their commands inside the existing Peek submenu of the editor context menu. A contributed command must respect normal menu visibility and ordering rules and execute normally. Built-in Peek commands and unrelated editor-context contributions must remain unchanged. The request does not require custom peek widgets or automatic correction of extension-authored labels.
- **Trace:**

  > The built-in submenu is registered in src/vs/editor/contrib/gotoSymbol/browser/goToCommands.ts using MenuId.EditorContextPeek, declared in src/vs/platform/actions/common/actions.ts. The apiMenus array in src/vs/workbench/services/actions/common/menusExtensionPoint.ts does not expose that MenuId, while its handler accepts only registered API keys or separately registered extension submenus. Extension submenus receive api-prefixed identities, so they cannot target the existing built-in submenu. The discussion at https://github.com/microsoft/vscode/issues/175351#issuecomment-1452444884 identifies this exact boundary, and https://github.com/microsoft/vscode/issues/175351#issuecomment-1453144716 supports exposing it. The remaining contract uncertainty is the public contribution identifier and whether it is immediately stable or initially proposed. Keep widget-title contributions and custom ZoneWidget APIs separate.
- **Open decisions:**
  - What public menu contribution identifier should extensions use for the built-in Peek submenu, and should that contract be available in stable immediately or initially require a proposed-API opt-in?
