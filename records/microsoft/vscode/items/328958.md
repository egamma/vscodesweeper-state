# Issue #328958 — Windows taskbar Jump List offers to pin `.code-workspace` entries as folders instead of workspace files

[https://github.com/microsoft/vscode/issues/328958](https://github.com/microsoft/vscode/issues/328958)

## Summary

The folder icon is explained by current source, but the reported change from opening a workspace to opening its containing folder is not. Request current-build confirmation and the pinned entry's actual target before deciding whether this is a workspace-launch regression or an icon discrepancy.

## Change summary

New Windows Jump List pins reportedly open the containing folder instead of the selected .code-workspace file.

## Best solution

Workspace Jump List entries should retain their workspace-file launch target after pinning. Establish where the observed target diverges from WorkspacesHistoryMainService's existing --file-uri construction before choosing a fix; distinguish that failure from the shared folder icon.

## Evidence

- **Current launch-target construction:** src/vs/platform/workspaces/electron-main/workspacesHistoryMainService.ts:440-450 selects recent.workspace for workspace history entries and generates --file-uri with workspace.configPath. Only folder URI entries generate --folder-uri. This path does not substitute a workspace file's containing folder.
- **History preserves workspace identity:** src/vs/platform/workspaces/common/workspaces.ts:73-75 identifies workspace entries by their workspace property; restoreRecentlyOpened at lines 337-370 restores workspace identifiers and configPath separately from folderUri entries. WorkspacesHistoryMainService.getRecentlyOpened supplies this history to the Jump List builder.
- **Icon does not establish launch target:** src/vs/platform/workspaces/electron-main/workspacesHistoryMainService.ts:452-461 sets iconPath to explorer.exe and iconIndex to 0 for both workspace and folder tasks, explicitly to simulate a folder icon. A workspace entry can therefore look like a folder while still launching with --file-uri.
