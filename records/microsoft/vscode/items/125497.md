# Issue #125497 — Search editor isRegex argument

[https://github.com/microsoft/vscode/issues/125497](https://github.com/microsoft/vscode/issues/125497)

## Summary

Still valid on current main: the search-command argument names remain inconsistent (`workbench.action.findInFiles` takes `isRegex`, `search.action.openNewEditor` takes `isRegexp`, `editor.actions.findWithArgs` takes `searchString`/`replaceString`), so this keybinding-argument papercut is unresolved; keeping it open as an API-naming polish item that needs a maintainer's compatibility decision.

## Change summary

Align the regex (and query/replace) argument names across the find/search commands so keybindings don't need per-command spellings.

## Best solution

Pick one canonical spelling (`isRegex`, `query`, `replace`) and accept it on all three commands, keeping the existing names as backwards-compatible aliases via the existing legacy-arg translation in searchEditor.contribution.ts and the args schema in findController.ts, rather than a breaking rename.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/search/browser/searchActionsBase.ts`, `src/vs/workbench/contrib/searchEditor/browser/searchEditor.contribution.ts`, `src/vs/workbench/contrib/searchEditor/browser/constants.ts`, `src/vs/editor/contrib/find/browser/findController.ts`
- **Validation:** A test (search editor / find controller suites) asserting that each command accepts both the canonical and the legacy argument spelling and produces the same resulting search state, plus the published args schemas listing both.
- **Behavior:**

  > A user writing a keybinding can use one spelling of the regex flag (and of query/replace) across `workbench.action.findInFiles`, `search.action.openNewEditor`, and `editor.actions.findWithArgs`, and the command behaves identically. Existing keybindings using today's names (`isRegexp`, `regexp`, `searchString`, `replaceString`) must keep working unchanged — no user's keybindings.json breaks. The command-argument schemas (used for keybinding IntelliSense) should advertise the canonical names. Acceptance: for each command, passing either spelling yields the same search configuration.
- **Trace:**

  > The three entry points are: `IFindInFilesArgs` in src/vs/workbench/contrib/search/browser/searchActionsBase.ts (`isRegex`, line 80), which already translates to the search editor's name at line 144 (`isRegexp: args.isRegex`); the `search.action.openNewEditor` schema and `SearchConfiguration` in src/vs/workbench/contrib/searchEditor/browser/searchEditor.contribution.ts:270 and src/vs/workbench/contrib/searchEditor/browser/constants.ts:30 (`isRegexp`); and `IFindStartArguments`-style args in src/vs/editor/contrib/find/browser/findController.ts:86-88 (`searchString`/`replaceString`/`isRegex`). `translateLegacyConfig` (searchEditor.contribution.ts:247) is the existing alias mechanism that already remaps the older `regexp` arg and is the natural place for compatibility. The boundary: `SearchConfiguration.isRegexp` is also the persisted search-editor serialization key (searchEditorSerialization.ts:124/171/224) — the on-disk `.code-search` header format must NOT change, so this is a command-argument alias problem, not a model rename. Related: https://github.com/microsoft/vscode/issues/138366 and https://github.com/microsoft/vscode/issues/138365.
- **Open decisions:**
  - Which spelling becomes canonical for the regex flag — `isRegex` (editor + findInFiles) or `isRegexp` (search editor)?
  - Should `editor.actions.findWithArgs` gain `query`/`replace` as the canonical names, with `searchString`/`replaceString` kept as aliases?
  - Are the old argument names kept permanently as silent aliases, or deprecated with a warning and a removal horizon?
