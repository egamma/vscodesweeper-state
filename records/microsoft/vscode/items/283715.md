# Issue #283715 — Include variable shape info when asking agent to make edits

[https://github.com/microsoft/vscode/issues/283715](https://github.com/microsoft/vscode/issues/283715)

## Summary

Keep open: current notebook context support only partially covers this request—inline prompts include richer runtime metadata, but the notebook-summary tool exposes names and types without values, summaries, or dimensions. This team-authored request still needs a decision on automatic runtime context for Edits and Agent; no qualifying fix or canonical duplicate was established.

## Change summary

Provide notebook kernel variable shape information when Copilot makes notebook edits in Edits and Agent modes.

## Best solution

Give notebook editing requests relevant, bounded runtime shape context so generated code can use actual data structures rather than guessing. Establish which metadata should be supplied automatically and evaluate the performance and editing-quality tradeoff identified in the report.

- **Behavior:**

  > When asking Copilot to edit an executed notebook, the model should receive relevant runtime structural information rather than relying only on source code or variable names and types. The goal applies to both Edits and Agent and should not require rerunning cells to discover existing data shapes. Acceptance should establish that representative dataframe or array metadata reaches the model, unavailable runtime information does not prevent editing, and collection does not materially degrade latency or editing quality.
- **Trace:**

  > NotebookVariables in extensions/copilot/src/extension/prompts/node/panel/notebookVariables.tsx fetches variables through INotebookService but renders only names and types. NotebookSummary in extensions/copilot/src/extension/tools/node/notebookSummaryTool.tsx includes that renderer, and editCodeIntent2.ts enables the summary tool for notebook-related requests. InlineChatNotebookVariables in extensions/copilot/src/extension/prompts/node/inline/inlineChatNotebookCommonPromptElements.tsx already renders values, summaries, and indexed-child counts, providing richer-context prior art. The service implementation obtains variables through jupyter.listVariables or vscode.executeNotebookVariableProvider; the local interface has no dedicated shape field, so provider metadata coverage must be established. Preserve existing inline behavior, avoid implicit cell execution, and keep unrelated output-attachment work out of scope. The unresolved boundary is which structural metadata is available and should be included automatically before editing rather than only through a tool call. Related discussions are https://github.com/microsoft/vscode/issues/283153 and https://github.com/microsoft/vscode/issues/283670.
- **Open decisions:**
  - Should runtime shape context be attached automatically before the first editing response for every referenced notebook, or only for the active notebook, with other notebooks remaining tool-driven?
  - Should automatic context contain structural summaries and dimensions only, or also bounded variable values and cell-output content?

## Evidence
