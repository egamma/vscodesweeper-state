# Issue #330807 — Copilot chat overview shows number of lines added/removed when there is none

[https://github.com/microsoft/vscode/issues/330807](https://github.com/microsoft/vscode/issues/330807)

## Summary

Two independent users confirm the chat session overview keeps showing stale +/- line-change badges after the changes have already been kept inside the session itself — a real UI staleness bug, but I could not pin down with certainty which caching layer fails to refresh.

## Change summary

The chat sessions overview/list still shows a pending changes badge (lines added/removed) for a session even after the user clicked 'Keep' on all the edits inside that session.

## Best solution

Trace why the session-list item's `changes` (built from `IChatDetail.stats`, computed in `chatModelToChatDetail`/`awaitStatsForSession` in src/vs/workbench/contrib/chat/common/chat.ts and chatServiceImpl.ts) doesn't refresh in the overview after an accept/keep action fires on a `ChatEditingModifiedFileEntry`; likely the session-list provider isn't re-invoking `getLiveSessionItems()` (or an intermediate cache in agentSessionsModel.ts / localAgentSessionsController.ts) on the entry's state-change observable.

## Evidence

- **stats computation:** chatModelToChatDetail() in src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:2369 calls awaitStatsForSession(model) which sums linesAdded/linesRemoved across all editingSession.entries.get() (src/vs/workbench/contrib/chat/common/chat.ts:41-71).
- **keep resets diff:** chatEditingModifiedDocumentEntry._doAccept() calls this._textModelChangeService.keep() (src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingTextModelChangeService.ts:317-319), which sets originalModel to the modified content and resets diffInfo to nullDocumentDiff — so the in-session view correctly shows no pending changes.
- **corroborating comment:** xguarch confirmed the same behavior on 1.133.0 (macOS) in a comment, independent of the original Windows report, which supports treating this as a reproduced/confirmed bug rather than a one-off.
- **uncertain root cause:** I could not find, without running the app, the exact spot where the sessions-overview list fails to re-fetch/re-render after the state-changing keep action; getLiveSessionItems() itself recomputes live each call, so the staleness likely lives in a list/provider caching layer (agentSessionsModel.ts or agentHostSessionListController.ts) that isn't invalidated by the entry's accept event.
