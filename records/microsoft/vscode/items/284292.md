# Issue #284292 — Allow language model providers to influence model ordering in the model selector

[https://github.com/microsoft/vscode/issues/284292](https://github.com/microsoft/vscode/issues/284292)

## Summary

A real API gap remains: providers cannot express general ranking or discovery tags, while the picker still alphabetizes ordinary models. The existing promotional metadata partially overlaps with featuring models but is specifically designed for promotions, so it does not fully cover trending or provider-defined ordering.

## Change summary

Allow language-model providers to influence picker ordering or identify models as trending or featured.

## Best solution

Define a constrained provider-facing discovery mechanism that preserves consistent picker behavior—such as standardized presentation tags or a bounded ranking hint—rather than honoring arbitrary provider order without mediation.

- **Validation:** Extend the model-picker item tests to provide models in non-alphabetical order with the chosen metadata and assert the resulting promoted/order behavior, while confirming unannotated models retain deterministic alphabetical ordering.
- **Behavior:**

  > A language-model provider can identify models that deserve elevated discovery, or supply a bounded ordering signal, through the provider API. The model selector reflects that signal predictably without allowing one provider to disrupt other providers, pinned models, recent models, or the Auto model. Models without the new metadata retain deterministic ordering. The accepted tests must cover both annotated and ordinary models.
- **Trace:**

  > LanguageModelChatInformation in src/vscode-dts/vscode.d.ts currently exposes identity, display text, limits, and capabilities but no general discovery metadata. src/vs/workbench/api/common/extHostLanguageModels.ts maps provider information into ILanguageModelChatMetadata, whose shape is defined in src/vs/workbench/contrib/chat/common/languageModels.ts. buildFlatModelItems and appendOtherModels in src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerItemSections.ts alphabetize ordinary models; appendPromotedModels separately handles recents, control-manifest featured entries, and proposed promotional metadata. The existing `promo` path is a partial precedent but must not be silently redefined as a general popularity signal. Preserve pinned, recent, Auto, provider grouping, and unavailable-model precedence.
- **Open decisions:**
  - Should the public contract expose a bounded numeric ordering hint, standardized tags such as trending/featured, or both?
  - Should provider discovery metadata reorder models only within that provider's group, or also promote models into the picker’s top-level discovery section?
  - Which precedence should provider-supplied metadata have relative to user-pinned and recently used models?
