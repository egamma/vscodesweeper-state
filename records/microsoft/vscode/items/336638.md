# Issue #336638 — Remote session reopen can show a stale, incomplete conversation

[https://github.com/microsoft/vscode/issues/336638](https://github.com/microsoft/vscode/issues/336638)

## Summary

Confirmed on main: `loadRemoteSession` returns the cached `ChatModel` from `acquireExistingSession` before ever calling `getOrCreateChatSession`, so a model that was mid-request when the remote connection dropped stays permanently 'in progress' even though the provider/session list shows it idle. Real, well-diagnosed bug by the reporting collaborator; needs a maintainer decision on reconciliation strategy before implementation.

## Change summary

Reopening a remote chat session after a disconnect can show a stale cached conversation stuck 'in progress', missing response parts the provider produced while disconnected.

## Best solution

Detect that the cached model's completion is still pending due to a disconnect and reconcile it against the authoritative provider snapshot from `getOrCreateChatSession` (either replacing the stale model or patching in the missed parts) before returning it from `loadRemoteSession`.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts`, `src/vs/workbench/contrib/chat/common/model/chatModel.ts`
- **Validation:** A chatService.test.ts case that simulates a cached model left in-progress by a disconnect, then calls loadRemoteSession again and asserts the returned model reflects the authoritative (completed) snapshot from getOrCreateChatSession rather than the stale in-progress state.
- **Behavior:**

  > When a remote chat session is reopened after having disconnected mid-response, the reopened conversation must reflect the authoritative completed state from the provider (no longer show 'in progress' when the session list shows it idle, and include any response parts produced while disconnected). Sessions that are genuinely still in progress (still connected) continue to behave as today. Acceptance: a test that disconnects a cached in-progress model, reconnects, and asserts the reopened model's completion state and content match the freshly resolved provider session.
- **Trace:**

  > In src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts, `loadRemoteSession` (line 725) calls `this.acquireExistingSession(sessionResource, debugOwner)` (line 730) and returns that cached `IChatModelReference` immediately if present, before ever awaiting `this.chatSessionService.getOrCreateChatSession(sessionResource, token)` (line 741). If the cached ChatModel was attached to a connection that dropped while a response was still streaming, its request-in-progress observable and response parts are never updated — verified by reading the early-return path, no additional staleness check exists there. The boundary: do not change the fast-path behavior for sessions that are still actively connected (the whole point of the early return is to avoid an unnecessary re-resolve for live sessions) — only the disconnected/stale case needs reconciliation. Reporter's own repro screenshot and code excerpt line up exactly with this code path.
- **Open decisions:**
  - How is 'stale because of a disconnect' distinguished from 'legitimately still in progress' — a connection/session generation id, a disconnect flag on the model, or something else?
  - Should the stale cached model be replaced wholesale with a freshly created model from the provider snapshot, or patched in-place to append missed response parts?
  - Does this reconciliation need to run on every `loadRemoteSession` call (perf cost) or only when the model is known to be in a state that could be stale (e.g., request in progress)?
