# Issue #62637 — [theme] inspect tool for workbench colors

[https://github.com/microsoft/vscode/issues/62637](https://github.com/microsoft/vscode/issues/62637)

## Summary

Keep open as an under-discussion theme-authoring request: current VS Code provides live color customization, generated CSS variables, and theme export, but no integrated click-to-identify workbench color inspector. This issue remains the canonical report; the younger related issue was explicitly closed in its favor.

## Change summary

Add an interactive developer mode for identifying which workbench theme color identifiers affect a selected UI element, potentially with a path to edit those colors.

## Best solution

Provide an opt-in developer action that lets theme authors select a workbench element and see the applicable registered color identifiers and descriptions, with a direct route to the corresponding `workbench.colorCustomizations` entries. The design should reuse the existing color registry and generated `--vscode-*` variables without changing normal workbench interaction or adding persistent UI.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/themes/browser/themes.contribution.ts`, `src/vs/workbench/services/themes/browser/colorThemeCss.ts`, `src/vs/platform/theme/common/colorUtils.ts`
- **Validation:** Launch the workbench, enable the proposed developer action, select representative themed elements such as an editor tab and activity-bar item, and verify that the displayed identifiers correspond to the contributing `--vscode-*` variables and that any offered customization updates the selected element live.
- **Behavior:**

  > Theme authors can enter an explicit developer inspection mode and select a workbench UI element without triggering its normal action. The resulting view identifies the registered workbench color identifiers relevant to that element and provides their descriptions. If editing is included, changing a reported color updates through the existing `workbench.colorCustomizations` flow. Leaving inspection mode restores normal interaction without persistent UI or state changes.
- **Trace:**

  > Theme colors are registered through the color registry in src/vs/platform/theme/common/colorUtils.ts and emitted as `--vscode-*` variables by `generateColorThemeCSS` in src/vs/workbench/services/themes/browser/colorThemeCss.ts. Theme commands live in src/vs/workbench/contrib/themes/browser/themes.contribution.ts; its existing `workbench.action.generateColorTheme` enumerates the same registry but only exports a complete theme document. The editor's token inspector is a useful interaction precedent, but workbench elements can receive several variables, derived colors, inline styles, or participant-generated rules, so the exact meaning of a reported “relevant color” is not settled. Keep normal workbench event handling, ordinary theme application, and the editor token inspector unchanged. The related https://github.com/microsoft/vscode/issues/89400 was explicitly consolidated into this canonical issue.
- **Open decisions:**
  - Should the first version only identify and document relevant color identifiers, or also write selected values into `workbench.colorCustomizations`?
  - When an element's computed appearance combines inherited variables, derived colors, opacity, and participant-generated CSS, which contributors should the inspector present and how should it distinguish direct from indirect matches?
  - Should inspection suppress all normal workbench interaction until explicitly exited, or use a temporary modifier-based selection model that preserves ordinary interaction outside each selection?

## Evidence

- **current capability:** src/vs/workbench/services/themes/browser/colorThemeCss.ts generates a `--vscode-*` CSS variable for every resolved color registry entry, so generic Developer Tools can expose raw variables but does not map a clicked workbench element into a purpose-built theme-authoring experience.
- **existing tooling gap:** src/vs/workbench/contrib/themes/browser/themes.contribution.ts registers `workbench.action.generateColorTheme`, which exports all current registered colors, but contains no action for selecting a workbench element or identifying the colors applied to it.
- **live editing already exists:** The maintainer confirmed in https://github.com/microsoft/vscode/issues/62637#issuecomment-451998329 that editing `workbench.colorCustomizations` updates colors live; the reporter clarified that discovery of the correct color identifier, rather than live application itself, is the unresolved request.
- **canonical status:** In https://github.com/microsoft/vscode/issues/89400#issuecomment-582359674, a maintainer identified this issue as the existing color-inspector request and closed that younger report as its duplicate.
- **no existing coverage:** Current theme action registrations and repository searches show no workbench equivalent of the editor's `editor.action.inspectTokens`; the central click-to-discover workflow therefore remains missing on main.
