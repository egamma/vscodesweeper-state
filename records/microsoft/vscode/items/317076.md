# Issue #317076 — Visible editor does not refresh document links until tab switch or reopen

[https://github.com/microsoft/vscode/issues/317076](https://github.com/microsoft/vscode/issues/317076)

## Summary

Keep open: current source still lacks a supported provider notification for refreshing document links after external dependencies change. The linked discussion explicitly recommends adding this VS Code API, and the existing editor-api classification remains appropriate.

## Change summary

Allow extensions to refresh document-link underline and activation in an unchanged visible document when external dependency state changes.

## Best solution

Provide a supported document-link invalidation API that causes visible editors to recompute provider results without editing the document or switching tabs. Coordinate its contract with language-client integration rather than treating arbitrary LSP request responses as editor updates.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages.ts`, `src/vs/editor/contrib/links/browser/links.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`
- **Validation:** Use a test document-link provider whose results change independently of document text. With the document continuously visible, trigger supported invalidation and verify links disappear and reappear in both directions without model edits or tab switches; repeat with a read-only document and assert unchanged text and dirty state. Cover notification forwarding through the extension-host bridge and preserve normal document-edit refresh behavior.
- **Behavior:**

  > Extensions can notify VS Code that document-link results changed because an external dependency or configuration changed. An unchanged visible document then gains or loses the corresponding link underline and activation without tab switching, reopening, or text edits. The behavior must work for read-only documents without changing text or dirty state. Existing document-edit refresh and link resolution behavior remain intact.
- **Trace:**

  > DocumentLinkProvider in src/vscode-dts/vscode.d.ts and LinkProvider in src/vs/editor/common/languages.ts expose computation and resolution but no result-change notification. LinkDetector in src/vs/editor/contrib/links/browser/links.ts recomputes on model/content/language/configuration and provider-registry changes, not changes to an existing provider's external state. Registration in ExtHostLanguageFeatures and MainThreadLanguageFeatures forwards no document-link event, while _executeLinkProvider in getLinks.ts returns results without repainting the editor. The linked discussion https://github.com/microsoft/vscode-languageserver-node/issues/1492#issuecomment-3007441612 identifies a VS Code refresh API as the intended direction. The unresolved boundary is the public invalidation contract and its language-client integration, not automatic consumption of arbitrary LSP responses. Preserve read-only behavior, normal edit-triggered recomputation, existing link resolution, and provider lifecycle cleanup; do not use fake edits as the refresh mechanism.
- **Open decisions:**
  - Should document-link invalidation be provider-wide, matching existing folding-range and inlay-hint change events, or allow targeting individual documents?

## Evidence

- **Existing-capability check:** src/vscode-dts/vscode.d.ts:5402–5425 exposes provideDocumentLinks and resolveDocumentLink but no change event. src/vs/editor/common/languages.ts:1898–1901 likewise has no provider invalidation event. Folding-range and inlay-hint providers already expose change events, providing neighboring API precedent.
- **Current editor refresh path:** In src/vs/editor/contrib/links/browser/links.ts, LinkDetector schedules computation on document content, model, language, links-option, or provider-registry changes. External dependency changes alone do not trigger this path; computeLinksNow updates decorations only after obtaining provider results.
- **Existing command does not repaint:** src/vs/editor/contrib/links/browser/getLinks.ts:171 onward registers _executeLinkProvider, which obtains and returns links, then disposes its result list. It does not update LinkDetector decorations, so executing a provider is not an in-place refresh mechanism.
- **Maintainer-endorsed API direction:** https://github.com/microsoft/vscode-languageserver-node/issues/1492#issuecomment-3004250043 explains that a manually issued request returns results to its caller, not the editor, and recommends a VS Code refresh API. https://github.com/microsoft/vscode-languageserver-node/issues/1492#issuecomment-3007441612 explicitly asks for that API request in this repository.
