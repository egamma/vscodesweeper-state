# Issue #325132 — Agents window should show and continue local Copilot Chat Agent sessions

[https://github.com/microsoft/vscode/issues/325132](https://github.com/microsoft/vscode/issues/325132)

## Summary

The integration gap remains on current main: workbench-local Chat sessions have their own catalog, while the Agents Window Copilot provider deliberately includes only Cloud sessions. Older related issues cover local-harness availability or conversation porting, but none reports the same observable session-discovery and continuation gap required for a duplicate close on this re-review.

## Change summary

Make local Copilot Agent conversations discoverable and continuable across the Chat view and Agents Window without fragmenting session history.

## Best solution

Provide one coherent session identity and continuation experience across the Chat view and Agents Window, with an explicit user-visible handoff only if the workbench-local and Agent Host backends cannot share a live session. Settle that identity and ownership contract before implementation.

- **Behavior:**

  > A local Copilot Agent conversation started in the Chat view can be found and continued from the Agents Window without silently losing or duplicating its history. Returning to the Chat view exposes the same continued conversation, or an explicit linked-copy boundary if that is the chosen product contract. Cloud, Copilot CLI, and third-party Agent Host session discovery must remain unchanged. Acceptance should cover a persisted session after reload as well as a currently loaded conversation.
- **Trace:**

  > LocalAgentsSessionsController in src/vs/workbench/contrib/chat/browser/agentSessions/localAgentSessionsController.ts projects IChatService live models and persisted local history into the workbench Chat sessions catalog. CopilotChatSessionsProvider._refreshSessionCache in src/vs/sessions/contrib/providers/copilotChatSessions/browser/copilotChatSessionsProvider.ts filters its source catalog to AgentSessionProviders.Cloud, while the provider specification assigns local sessions to Agent Host providers. Therefore no provider-neutral ISession currently adapts an ordinary workbench-local conversation for the Agents Window. https://github.com/microsoft/vscode/issues/318358 establishes maintainer interest in multi-client access, while https://github.com/microsoft/vscode/issues/323970 records the unresolved port-versus-shared-identity questions. The boundary is session discovery, identity, and continuation; do not alter unrelated Cloud or external Agent Host catalogs.
- **Open decisions:**
  - Must both surfaces preserve one canonical session identity and live history, or is an explicitly linked imported copy acceptable when crossing from the workbench-local harness to Agent Host?
  - Should the first supported contract be one-way discovery of Chat-view sessions in the Agents Window, or must compatible sessions created in the Agents Window also appear immediately in the Chat view?
