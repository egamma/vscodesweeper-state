# Issue #170101 — npm.packageManager=auto incorrectly assumes yarn as package manager for running tasks

[https://github.com/microsoft/vscode/issues/170101](https://github.com/microsoft/vscode/issues/170101)

## Summary

Keep open: multiple commenters confirm incorrect Yarn selection, and current source still contains the workspace-based Yarn heuristic. Two linked fix PRs remain open, so the issue should await review and a landed fix rather than be closed as completed.

## Change summary

Automatic package-manager detection selects Yarn for npm or pnpm projects, causing npm-type tasks to invoke the wrong runner.

## Best solution

Review the overlapping fixes in https://github.com/microsoft/vscode/pull/243250 and https://github.com/microsoft/vscode/pull/302916 and land a solution that respects project package-manager evidence without treating a workspaces field alone as proof of Yarn. Verify both the reported Corepack/pnpm case and npm workspace subfolders before closing.

## Evidence

- **Reported trigger and confirmations:** https://github.com/microsoft/vscode/issues/170101 supplies an npm-type task, packageManager=pnpm@7.9.3, pnpm lock/workspace files, no yarn.lock, and the resulting Corepack rejection of yarn run bar. Comments independently confirm wrong Yarn selection in npm workspace subfolders and continued occurrence in 2025.
- **Current detection path:** extensions/npm/src/preferred-pm.ts still imports find-yarn-workspace-root. isYarnPreferred accepts a workspace-root result without a Yarn lockfile; findPreferredPM does not read package.json's packageManager field. However, a detected pnpm lockfile is ranked before Yarn, so this heuristic alone does not conclusively reproduce every detail of the original pnpm configuration on current main.
- **Current task configuration:** extensions/npm/src/tasks.ts:getScriptRunner now reads npm.scriptRunner, while getPackageManager reads npm.packageManager; both use detectPackageManager when set to auto. getRunScriptCommand uses the script runner. Thus the original npm.packageManager workaround is not sufficient guidance for current script tasks.
- **Open implementation candidates:** GitHub reads verified that https://github.com/microsoft/vscode/pull/243250 remains OPEN and explicitly says Fixes #170101, and https://github.com/microsoft/vscode/pull/302916 remains OPEN and addresses this report through packageManager precedence and replacement of the workspace heuristic. Neither has merged; https://github.com/microsoft/vscode/pull/302354 is closed without merging.
