# Issue #90521 — Support custom QuickPick filter logic

[https://github.com/microsoft/vscode/issues/90521](https://github.com/microsoft/vscode/issues/90521)

## Summary

Keep this accepted, 25-upvote API request open: current stable APIs provide a partial workaround, but do not expose custom filtering or full control over matching and ordering. A maintainer explicitly retained it as a separate proposal, and the verified related issues do not replace its scope.

## Change summary

Allow extensions to supply custom QuickPick matching, including reordered words or regex, with optional delayed filtering for large item sets.

## Best solution

Define a stable extension API contract that lets extension-owned search determine QuickPick results without competing built-in filtering or unwanted reordering. Resolve whether that contract needs a callback and built-in delay or can be satisfied by matching opt-outs and extension-managed updates, while coordinating the separate highlighting proposal.

- **Behavior:**

  > Extensions should be able to implement regex or reordered-word searches without exposing artificial matching text in item labels, descriptions or details. Results selected by custom search must not be discarded by an unrelated built-in matcher. Large-list searches should follow an explicitly agreed timing contract and must not leave results for an obsolete query. Existing QuickPicks that do not opt in must retain their current matching, ordering and keyboard behavior.
- **Trace:**

  > QuickPick.doSetValue in src/vs/platform/quickinput/browser/quickInput.ts filters the renderer list before broadcasting onDidChangeValue. QuickInputList.filter in src/vs/platform/quickinput/browser/quickInputList.ts computes built-in matches, honors alwaysShow for unmatched ordinary items, and applies the configured ordering. The stable declarations in src/vscode-dts/vscode.d.ts support extension-managed item updates but omit matchOnLabel and sorting control; sortByLabel is still proposed. TransferQuickPick and MainThreadQuickOpen.$createOrUpdate identify the extension-host boundary that any agreed contract must traverse. This establishes an API gap, not a confirmed defect in alwaysShow, and no runtime reproduction was attempted. Preserve default behavior and do not absorb unrelated highlighting work from https://github.com/microsoft/vscode/issues/83424. Coordinate matching and ordering with https://github.com/microsoft/vscode/issues/83425 and https://github.com/microsoft/vscode/issues/73904; the uncertainty is the public filtering and scheduling contract, not where to place a helper.
- **Open decisions:**
  - Should the public API provide a custom filter callback, or expose matching and ordering opt-outs so extensions own result computation through onDidChangeValue and items updates?
  - If a callback is exposed, does it replace built-in matching or post-process its results, and which behavior governs highlighting and ordering?
  - Should VS Code provide a filterDelay contract, or should debouncing and obsolete-query handling remain extension-managed?
