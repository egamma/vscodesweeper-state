# Issue #146330 — Allow WebviewViews to be explicitly created, so badges can be shown

[https://github.com/microsoft/vscode/issues/146330](https://github.com/microsoft/vscode/issues/146330)

## Summary

Keep open: current main still requires a WebviewView to become visible before an extension receives the object needed to set its badge. This issue is already the canonical request for that API gap, with multiple reports closed into it.

## Change summary

Allow extensions to publish WebviewView badges at startup without first opening the view.

## Best solution

Provide an extension API that supports badges before the first reveal without changing the user's selected or expanded views. API owners should decide whether this requires explicit hidden view creation or a metadata API independent of webview resolution, preserving lazy content allocation.

## Vision fit

- **Fit:** aligned
- **Reason:** Closing this extension API gap enables consistent badge behavior between tree views and webview views without requiring disruptive navigation.
- **Evidence:** Public roadmap values: "Simple, uniform UI and UI interactions" and "The power lives in extensions"; durable theme: extension ecosystem API hygiene.

- **Validation:** Use an extension activated independently of its contributed view. Start with that view's container inactive, publish a nonzero badge, and verify the activity badge appears without opening, expanding, or focusing the view. Verify badge updates and removal before first reveal, then open the view and confirm normal resolution and badge behavior remain intact.
- **Behavior:**

  > An activated extension can publish and update a badge for its contributed WebviewView before the user first opens that view. Publishing the badge must not switch containers, expand the view, or move focus. Acceptance covers initial publication, updates, and removal while hidden, followed by normal first-reveal behavior. The public API and whether publishing metadata invokes the provider need agreement before implementation.
- **Trace:**

  > WebviewViewPane.updateTreeVisibility in src/vs/workbench/contrib/webviewView/browser/webviewViewPane.ts gates activate on body visibility; activate creates the internal view and calls webviewViewService.resolve. MainThreadWebviewsViews in src/vs/workbench/api/browser/mainThreadWebviewViews.ts assigns a handle during resolution, and ExtHostWebviewViews.$resolveWebviewView in src/vs/workbench/api/common/extHostWebviewView.ts constructs the extension-facing object whose badge setter uses that handle. The current declarations document this visibility-driven lifecycle, and show(preserveFocus) reveals the view rather than resolving it invisibly. Preserve existing reveal, focus, disposal, and lazy webview-content behavior. The original badge PR explicitly left this gap open: https://github.com/microsoft/vscode/pull/144775. The trace establishes the limitation, but not an approved new API contract.
- **Open decisions:**
  - Should extensions explicitly create or resolve a hidden WebviewView, invoking its provider, or publish badge metadata without resolving the webview?
  - Should the new pre-resolution API cover only badges, or also title and description metadata represented by the related requests consolidated here?

## Evidence

- **Current API boundary:** src/vscode-dts/vscode.d.ts:10225–10348 exposes badge on WebviewView and explicitly documents that resolveWebviewView runs when the view first becomes visible. registerWebviewViewProvider provides registration rather than a view object; the inspected stable and proposed declarations expose no createWebviewView equivalent.
- **Current source path:** In src/vs/workbench/contrib/webviewView/browser/webviewViewPane.ts, updateTreeVisibility calls activate only when isBodyVisible() is true. activate constructs the WebviewView and invokes webviewViewService.resolve. In src/vs/workbench/api/common/extHostWebviewView.ts, $resolveWebviewView creates the extension-facing object; its badge setter therefore remains unavailable before resolution.
- **Existing capabilities do not cover the request:** WebviewView.show(preserveFocus) explicitly reveals and expands the view, so preserving focus does not preserve hidden state. retainContextWhenHidden preserves content after creation rather than creating an unresolved view. src/vs/workbench/contrib/webviewView/browser/webviewView.contribution.ts contains service registration, not a setting or command for hidden initialization.
- **Original merged PR leaves this gap:** https://github.com/microsoft/vscode/pull/144775 merged on 2022-03-30 before this issue was filed. Its body explicitly identifies the same inability to assign a badge before resolveWebviewView, so the merged badge API is not a fix for this follow-up.
- **Established canonical ownership:** https://github.com/microsoft/vscode/issues/164974 describes the identical missing startup badge and was closed as a duplicate of this issue: https://github.com/microsoft/vscode/issues/164974#issuecomment-1314472632. https://github.com/microsoft/vscode/issues/152382 requests resolution without showing the view and was likewise directed here: https://github.com/microsoft/vscode/issues/152382#issuecomment-1254340249.
- **Related metadata request:** https://github.com/microsoft/vscode/issues/199483 asks to update a title before initialization and was also closed into this issue: https://github.com/microsoft/vscode/issues/199483#issuecomment-1843895741. This supports considering the API lifecycle rather than treating badges as a rendering defect.
