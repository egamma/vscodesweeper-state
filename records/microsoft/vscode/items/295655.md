# Issue #295655 — Spawn UNKNOWN in Search/Chat

[https://github.com/microsoft/vscode/issues/295655](https://github.com/microsoft/vscode/issues/295655)

## Summary

Confirmed on multiple managed Windows environments: AppLocker/WDAC blocks VS Code's bundled rg.exe, breaking workspace search and Agent mode. The issue should remain open to track graceful behavior when process execution is denied.

## Change summary

Workspace search and repository-aware Agent mode fail with `spawn UNKNOWN` when Windows application-control policy blocks bundled ripgrep.

## Best solution

Search should detect ripgrep launch failures caused by Windows policy, report a clear actionable diagnostic, and provide a viable non-ripgrep fallback where possible; Chat should not surface the raw process error as an opaque response.

## Plan brief

- **Likely files:** `src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts`, `src/vs/workbench/services/search/node/ripgrepSearchUtils.ts`, `src/vs/workbench/services/search/common/searchService.ts`
- **Validation:** Add or extend search-service tests with a process launcher that fails using the Windows policy-blocked spawn error; verify the chosen fallback or diagnostic is returned instead of an opaque `spawn UNKNOWN`, while normal ripgrep search behavior remains unchanged.
- **Behavior:**

  > When Windows application-control policy prevents VS Code's bundled ripgrep from starting, workspace search must not fail with only an opaque `spawn UNKNOWN` message. VS Code should either continue through a supported fallback or clearly explain that the search executable was blocked and identify the affected capability. Repository-aware Agent mode must handle the same underlying search failure without replacing the chat response with an illegible raw process error. Normal ripgrep-backed search must remain unchanged.
- **Trace:**

  > The issue discussion traces the failure from Agent mode to core workspace search: sidebar search fails too, while Ctrl+P recent-file lookup still works. A trace shows `RipgrepSearchEH#search` launching `node_modules/@vscode/ripgrep-universal/bin/win32-x64/rg.exe`; managed Windows environments then report WDAC/AppLocker enforcement, Constrained Language Mode, group-policy blocking, and AppLocker event 8004. Relevant core paths are the ripgrep launch/error handling under `src/vs/workbench/services/search/node/` and the search-service fallback boundary in `src/vs/workbench/services/search/common/searchService.ts`. Preserve ripgrep as the normal engine and do not weaken or bypass operating-system policy; the uncertainty begins at what supported fallback, if any, can provide workspace text search without spawning the blocked executable.
- **Open decisions:**
  - When ripgrep is blocked by application-control policy, should workspace text search fall back to a slower built-in implementation, or fail with a targeted policy diagnostic?
  - If a fallback is provided, which search semantics and limits must it preserve before VS Code warns that results may be incomplete?
  - Should Agent mode continue with reduced repository-search capability after this failure, or stop with a clear capability-specific message?

## Evidence

- **confirmed reproduction:** Multiple commenters reproduced workspace-search and Agent-mode failure on managed Windows systems; the June 4 trace shows VS Code launching bundled `@vscode/ripgrep-universal/bin/win32-x64/rg.exe` immediately before failure.
- **policy root cause:** Commenters reported WDAC enforcement, stacked Code Integrity policies, Intune management, and PowerShell Constrained Language Mode; one reporter confirmed the problem disappeared after removing AppLocker/WDAC policy.
- **direct policy evidence:** The August 19 report reproduced `rg.exe` being blocked by group policy and correlated it with AppLocker event 8004; workspace search fails independently of Copilot authentication.
- **remaining product gap:** The latest maintainer discussion identifies the unresolved behavior: VS Code lacks a graceful fallback or sufficiently clear handling when ripgrep cannot be spawned in restricted environments.
- **related reports:** The referenced issues https://github.com/microsoft/vscode/issues/297358, https://github.com/microsoft/vscode/issues/300296, and https://github.com/microsoft/vscode/issues/298323 are closed and therefore cannot serve as duplicate canonicals; no older open issue with the same reporter-observable symptom was provided or verified.
