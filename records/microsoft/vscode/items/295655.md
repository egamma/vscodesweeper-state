# Issue #295655 — Spawn UNKNOWN in Search/Chat

[https://github.com/microsoft/vscode/issues/295655](https://github.com/microsoft/vscode/issues/295655)

## Summary

Keep open: independent reports connect the Search/Chat failures to enterprise policy blocking the bundled rg.exe, and current source still propagates ripgrep launch failures without a fallback. The existing search label is appropriate; no verified fix or older canonical reporting the same symptom was found.

## Change summary

Workspace search and file-backed Agent chat fail with an opaque spawn UNKNOWN error when Windows application-control policy blocks rg.exe.

## Best solution

Have the search owner define supported behavior when enterprise policy prevents ripgrep execution, including actionable diagnostics and whether a policy-compatible fallback is appropriate. Workspace search itself currently uses ripgrep, so delegating to it alone would not resolve the failure.

## Evidence

- **Confirmed reproduction and executable-level diagnosis:** https://github.com/microsoft/vscode/issues/295655#issuecomment-4622471602 reports the failure on Windows 11 with VS Code 1.123 and no extensions installed, provides the exact RipgrepSearchEH command, and confirms that directly executing the bundled rg.exe returns 'This program is blocked by a group policy'. This is a credible confirmed reproduction, not merely an authentication hypothesis.
- **Policy correlation:** https://github.com/microsoft/vscode/issues/295655#issuecomment-4633468240 reports that removing the application-control policies resolved the problem. https://github.com/microsoft/vscode/issues/295655#issuecomment-4718828254 independently documents enforced WDAC and PowerShell Constrained Language Mode. These observations identify an environmental trigger without establishing a defect in Electron or ripgrep itself.
- **Current source preserves the failure path:** src/vs/base/node/ripgrep.ts resolves the bundled @vscode/ripgrep-universal executable. src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts:65-88 spawns that executable and rejects launch errors as SearchErrorCode.rgProcessError, preserving the original error message rather than using an alternative search engine. src/vs/workbench/services/search/node/ripgrepFileSearch.ts:17-27 also directly spawns the bundled executable.
- **Fallback suggestion is not an existing solution:** https://github.com/microsoft/vscode/issues/295655#issuecomment-5341563997 proposes falling back to workspace search. However, RipgrepSearchProvider.provideTextSearchResults in src/vs/workbench/services/search/node/ripgrepSearchProvider.ts delegates folder searches to RipgrepTextSearchEngine, so the ordinary workspace-search provider shares the blocked executable dependency.
- **Separate signature-verification problem:** The reporter's March 20 comment states that updating Copilot Chat to 0.40.1 resolved extension signature verification but left spawn UNKNOWN unchanged. The signature problem and authentication messages therefore do not establish resolution of this issue.
- **Canonical search and historical precedent:** Open-issue searches for spawn UNKNOWN, ripgrep policy, ripgrep fallback, and AppLocker found no verified older canonical with this same Search/Chat symptom. https://github.com/microsoft/vscode/issues/112538 and https://github.com/microsoft/vscode/issues/122951 concern elevated Chromium sandbox or webview startup, not this ripgrep search failure. https://github.com/microsoft/vscode/issues/195895 describes policy-blocked ripgrep but is closed and cannot serve as a duplicate canonical.
- **Related reports consolidate here:** The closed search report https://github.com/microsoft/vscode/issues/300296 was directed to this issue in https://github.com/microsoft/vscode/issues/300296#issuecomment-4064560868, supporting retention of this thread as the existing collection point.
