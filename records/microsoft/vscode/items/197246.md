# Issue #197246 — Notebooks can open but not be usable

[https://github.com/microsoft/vscode/issues/197246](https://github.com/microsoft/vscode/issues/197246)

## Summary

Keep open: the discussion confirms a notebook identity failure beyond the original Pylance trigger, and current source still treats authority variants differently between remote file loading and notebook lookup. No qualifying fix or older open canonical was established; this team-authored issue needs an agreed URI-handling contract before implementation.

## Change summary

Opening a remote notebook through an authority-altered cell URI creates a second notebook identity and leaves both notebooks unable to execute cells.

## Best solution

Ensure notebook navigation cannot create an identity mismatch that breaks execution in an already-open notebook. Notebook and remote file-service owners should agree whether unsupported authority variants are rejected or resolved to an existing document, then verify consistent editor and extension-host behavior.

Acceptance: the original remains usable, and the altered URI follows the agreed rejection or identity-resolution contract without an orphaned notebook document.
- **Behavior:**

  > A definition or reference result containing an authority-altered remote notebook cell URI must not leave the original notebook unable to execute. The historical reproduction opens a second apparent copy, then execution fails in both copies with a notebook-not-found error. Validate the agreed handling of the altered URI and continued execution in the original notebook. Valid notebook navigation and navigation between genuinely distinct resources must remain unchanged.
- **Trace:**

  > The thread confirms the historical failure and separates core document identity handling from Pylance's subsequently fixed URI-generation bug. Current notebookEditorInputFactory and NotebookModelResolverServiceImpl canonicalize and key the supplied notebook URI without recovering a missing authority. ExtUri.getComparisonKey retains authority, whereas createRawURITransformer.transformIncoming discards it when mapping vscode-remote resources to server-local files; ExtHostNotebookController.getNotebookDocument performs URI-keyed lookup. This establishes the identity discrepancy, not a current end-to-end execution reproduction. Start by retesting the authority-altered navigation path with a controlled definition provider. Preserve scheme-based file-provider registration and distinctions between genuinely different remote resources. The unresolved product boundary is whether unsupported authority variants should fail navigation or resolve to the existing notebook; the discussion at https://github.com/microsoft/vscode/issues/197246#issuecomment-1793117477 does not settle that contract.
- **Open decisions:**
  - When remote notebook navigation supplies a cell URI with a missing or mismatched authority, should VS Code reject navigation explicitly or resolve it to the existing notebook, and which authority variants are supported?
