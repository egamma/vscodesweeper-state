# Issue #344387 — Clarify how "This Computer" relates to remote tunnels and sharing controls

[https://github.com/microsoft/vscode/issues/344387](https://github.com/microsoft/vscode/issues/344387)

## Summary

Keep open for design: current sharing controls and remote management exist, but they do not explain their shared machine identity across the three surfaces. The collaborator's navigation and local-computer-section mockups establish interest without settling the final interaction.

## Change summary

Connect the local computer's sharing identity and controls across the environment picker, antenna menu, and Remote Environments editor while distinguishing hosting from client connection state.

## Best solution

Provide a consistent local-machine identity across these surfaces, with discoverable navigation and sharing controls that clearly distinguish hosting from connecting. Use the collaborator's mockups to settle the local-computer presentation before implementation, preserving existing remote connection semantics.

Manually verify sharing off, starting, and active with no client connection: the machine remains recognizable across all three surfaces, hosting is not described as client connectivity, and keyboard navigation reaches the approved sharing and management controls.
- **Behavior:**

  > Users should recognize that This Computer and its named shared tunnel can represent the same machine. Sharing/hosting state must be distinguishable from whether this client has connected to a remote host. Sharing and management controls should be discoverable across the antenna menu and Remote Environments editor without silently changing the selected environment or initiating a connection. Acceptance includes sharing disabled, starting, and active with no connected client.
- **Trace:**

  > The antenna implementation in src/vs/workbench/contrib/chat/electron-browser/toggleRemoteConnectionsActionViewItem.ts already owns sharing-method selection and a named footer, but its method list has no management navigation. src/vs/sessions/contrib/chat/browser/sessionEnvironmentPicker.ts exposes This Computer and a separate management entry. RemotesModel.update() in src/vs/sessions/contrib/providers/remoteAgentHost/browser/remotesModel.ts builds tunnel rows from inventory and client connection status; local hosting identity currently protects deletion rather than identifying the row. RemotesWidget renders the grouped table without a local sharing section. The discussion at https://github.com/microsoft/vscode/issues/344387 proposes connecting these surfaces, but leaves final presentation open. Preserve connection, deletion, account, and policy behavior; sharing must not be conflated with connecting. Shared workbench code must not import the Sessions layer.
- **Open decisions:**
  - Should the local machine have a dedicated This Computer section, an annotation on its tunnel row, or both, and should that tunnel remain separately selectable in the environment picker?
  - Which current-machine controls should Remote Environments expose: sharing-method selection, host rename, and copy address, as explored in the mockups, or a smaller initial set?
