- **Possible startup wait on current main:** src/vs/code/electron-main/main.ts:352–372 calls checkInnoSetupMutex before completing first-instance startup. Lines 560–589 poll the product's '-updating' mutex for up to 30 seconds and log elapsed time. This is a plausible contributor, but the report does not establish that this mutex was held; the code alone does not reproduce the reported 30–50-second delay.
- **Update lifecycle boundary:** src/vs/platform/update/electron-main/abstractUpdateService.ts:177–178 initializes the update service after AfterWindowOpen. updateService.win32.ts:148–174 resumes an interrupted update when 'updating_version' exists. These paths do not by themselves prove that resuming a pending update blocks the initial window.
- **Installer handoff:** build/win32/code.iss:1830–1855 stages a background update, waits for the application mutex to disappear, then invokes inno_updater synchronously unless shutdown or cancellation intervenes. Distinguishing this handoff from a merely downloaded update requires logs from the affected launch.

Manual mode disables automatic update checks, and disabling background updates changes automatic staging; neither proves that an already-active installer can be safely deferred during launch.
