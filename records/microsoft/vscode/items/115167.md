# Issue #115167 — openExternalUri as a middleware

[https://github.com/microsoft/vscode/issues/115167](https://github.com/microsoft/vscode/issues/115167)

## Summary

Current source supports browser fallback without the original double-validation flow, but does not expose middleware continuation between extension openers. Keep this team-authored request open: no fixing commit explicitly referencing it was identified, and the older API issue does not report the same observable problem required for a duplicate on re-review.

## Change summary

Allow an external URI opener to perform interception work and delegate to another opener or the default browser without repeating the opening dialog.

## Best solution

Separate the already-supported default-browser fallback from the remaining request for continuation between extension openers. The opener API owners should decide whether that additional public contract is warranted; any continuation must preserve normal link validation rather than bypass it.

## Evidence

- **Existing fallback capability:** src/vscode-dts/vscode.proposed.externalUriOpener.d.ts documents env.openExternal options.allowContributedOpeners, including 'default' to force the standard external opener. This supplies browser fallback, not a next-opener continuation. workbench.externalUriOpeners selects an opener by URI pattern; it does not compose middleware.
- **Current validation ordering:** In src/vs/editor/browser/services/openerService.ts, OpenerService.open invokes contributed external openers before _validate and returns immediately when an opener handles the URI. An opener delegating through env.openExternal without contributed openers then reaches validation on the delegated call, rather than validating both before interception and after delegation. This source trace indicates the original double-validation mechanism has changed; no runtime reproduction was attempted.
