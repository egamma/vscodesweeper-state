# Issue #286162 — Support runtime feature experimentation

[https://github.com/microsoft/vscode/issues/286162](https://github.com/microsoft/vscode/issues/286162)

## Summary

Keep open: runtime feature switches are still configured statically, without the requested experimentation-service integration. This is team-authored accepted work, and neither a qualifying fix nor an older canonical owning the same request was found.

## Change summary

Connect Electron/Chromium runtime feature controls to VS Code's experimentation service so runtime behavior can be evaluated across treatment groups.

## Best solution

Provide a controlled bridge between ExP assignments and early runtime feature configuration, with defined activation timing and existing experiment opt-outs respected. Use the network-buffer experiment as the first acceptance case rather than treating its hard-coded value as completion of the general capability.

- **Validation:** Use a targeted test ExP or developer treatment override to assign two NetAdapterMaxBufSize values, then launch fresh application processes and verify their effective runtime feature parameters. Confirm that unassigned and experiment-disabled launches retain the intended defaults, and use the streaming HTTP/2 scenario linked from https://github.com/microsoft/vscode/issues/268800 to check that the assigned parameter actually affects the runtime path.
- **Behavior:**

  > VS Code can evaluate supported runtime features using its existing experimentation service instead of requiring a hard-coded runtime configuration for every participant. The initial acceptance case is NetAdapterMaxBufSize: treatment groups must receive distinguishable effective buffer parameters on the applicable application launch. Unassigned users retain the intended default, and existing experiment opt-outs remain effective. The plan must define when a fetched or changed assignment becomes active.
- **Trace:**

  > configureCommandlineSwitchesSync in src/mainImpl.ts runs during early process initialization and currently appends static Electron/Chromium feature strings, including NetAdapterMaxBufSizeFeature:NetAdapterMaxBufSize/8192. WorkbenchAssignmentService in src/vs/workbench/services/assignment/common/assignmentService.ts resolves treatments asynchronously and emits assignment-refetch events later in the workbench lifecycle. The configuration experiment processing in src/vs/workbench/services/configuration/browser/configurationService.ts supports startup-latched setting defaults but does not establish an early runtime-switch bridge. This confirms a remaining integration gap, not a defect in the existing buffer setting. https://github.com/microsoft/vscode/issues/268800 supplies the concrete runtime experiment and observable performance scenario; it does not own the broader integration. Preserve unrelated runtime switches, existing command-line behavior, and experiment opt-outs. The uncertainty starts at assignment activation timing and which runtime features the first supported contract should expose.
- **Open decisions:**
  - Should newly fetched runtime assignments take effect only on the next full application launch, or must they affect the first launch that receives the assignment?
  - Should the initial capability support only explicitly approved runtime features such as NetAdapterMaxBufSize, or expose a broader runtime feature-and-parameter contract?
  - When an experiment assignment conflicts with an explicit runtime command-line feature value, which value should take precedence?
