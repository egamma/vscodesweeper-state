# Issue #188257 — Disposing a webview view when extension host is restarted

[https://github.com/microsoft/vscode/issues/188257](https://github.com/microsoft/vscode/issues/188257)

## Summary

Keep open: disposing the webview-view provider still does not hide its view in current source. An open PR explicitly targets this issue and needs maintainer review rather than a competing implementation.

## Change summary

Hide the webview view when its provider is disposed during an extension-host restart.

## Best solution

Review https://github.com/microsoft/vscode/pull/225982 against the workspace-folder restart scenario, ensuring provider disposal removes the orphaned view and subsequent provider registration remains usable.

## Evidence

- **Reported trigger:** https://github.com/microsoft/vscode/issues/188257 describes adding a folder to a single-folder workspace while a webview view is open; deactivate disposes the provider, but the view remains visible. The discussion also reports an orphaned webview whose messages no longer reach the extension.
- **Provider disposal path:** In src/vs/workbench/api/common/extHostWebviewView.ts, ExtHostWebviewViews.registerWebviewViewProvider returns a disposable that unregisters the provider through $unregisterWebviewViewProvider. In src/vs/workbench/api/browser/mainThreadWebviewViews.ts, that method disposes only the provider registration. WebviewViewService.register in src/vs/workbench/contrib/webviewView/browser/webviewViewService.ts returns a disposable that only deletes the resolver; it neither disposes nor hides the existing view.
- **View remains visible:** In src/vs/workbench/contrib/webviewView/browser/webviewViewPane.ts, the WebviewView.dispose callback resets activation and clears webview resources but does not call viewService.closeView. Thus even extension-host-side cleanup of the tracked WebviewView does not hide its view container.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/225982 was verified OPEN and explicitly references this issue with closing syntax. Its diff adds a close operation backed by viewService.closeView to the webview-view disposal path. It has not merged, so it is not evidence of a completed fix.
- **Older related report is not an established canonical:** https://github.com/microsoft/vscode/issues/70656 was verified OPEN. Its original report and discussion concern editor WebviewPanels, disposal and serializer reconnection after extension reload; this issue specifically concerns disposing a WebviewViewProvider and hiding its contributed view. The related symptom does not establish that the older report owns this distinct API lifecycle behavior.
- **Other related scope:** https://github.com/microsoft/vscode/issues/225410 was verified OPEN and concerns custom text editors becoming orphaned and unsaved custom-editor data after extension-host restarts or crashes, not provider-disposal visibility for contributed webview views.
- **Workaround limitation:** The workaround posted on https://github.com/microsoft/vscode/issues/188257 closes and reopens orphaned editor tabs through window.tabGroups. It does not establish a solution for contributed webview-view containers.
