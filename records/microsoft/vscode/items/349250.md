Created on 2026-11-17, it reports the same Agents window failure with remote HTTP MCP: Authenticate does nothing in a side chat, while main-chat authentication succeeds and subsequently unblocks the side chat.
- **Current source confirms resource mismatch:** src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatToolAuthenticationSubPart.ts passes context.element.sessionResource to getMcpServers and authenticateMcpServer. In src/vs/workbench/contrib/sessions/browser/agentHostCustomizationService.ts, _resolveTarget only calls _getSession; unlike getCustomAgents and getBackendChatResource, it does not fall back to getSessionForChatResource. SessionsManagementService.getSession matches session resources or previous identities, not individual chat resources.
- **Both observed consequences follow:** In src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationService.ts, unresolved targets make getMcpServers return [] and authenticateMcpServer log the reported session-not-available warning and return false. The authentication card conditionally omits Disable for This Session when no MCP server resolves, and its click handler subsequently focuses the input.
