# Issue #307349 — Chat session history entry silently unresponsive with no recovery path when session fails to deserialize

[https://github.com/microsoft/vscode/issues/307349](https://github.com/microsoft/vscode/issues/307349)

## Summary

Keep open: malformed local session data still becomes an undefined load result that bypasses the existing user-visible error handler. Current source does provide deletion from the sessions context menu, but silent load failure and recovery remain unresolved.

## Change summary

Make chat-history deserialization failures visible and provide a safe recovery path for readable conversation data.

## Best solution

Distinguish a failed persisted-session load from a new or missing session, and give users an actionable failure state without overwriting recoverable data. Retain the existing deletion action; agree on partial-recovery and preservation semantics before expanding recovery behavior.

- **Existing notification does not cover this failure:** src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:705–739 propagates missing sessionData as undefined from acquireOrRestoreLocalSession. src/vs/workbench/contrib/chat/browser/widgetHosts/viewPane/chatViewPane.ts:1548–1579 passes that undefined reference into showModel; its 'Failed to open chat session' notification only runs for thrown exceptions. Thus a deserialization failure takes the fresh-session fallback rather than that notification.
- **Replay still rejects malformed records:** src/vs/workbench/contrib/chat/common/model/objectMutationLog.ts:345–398 parses each nonempty log line with JSON.parse and applies mutations without a partial-recovery result. A malformed JSONL record throws into the store's outer catch, making the general malformed-session failure source-reproducible; this does not independently prove the report's specific missing-response explanation.
