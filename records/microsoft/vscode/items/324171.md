# Issue #324171 — Agents Window Browser: Help user setup browser open action

[https://github.com/microsoft/vscode/issues/324171](https://github.com/microsoft/vscode/issues/324171)

## Summary

Keep open: current main supports manually configuring and pinning a persisted browser URL, but does not automatically capture the active URL or connect server-task generation to that browser workflow. This team-authored request still describes a meaningful gap; the older preview issues overlap without owning its full persistence and relaunch requirements.

## Change summary

Automatically remember a workspace's active browser URL for future sessions and help generate a server task when the site requires one.

## Best solution

Extend the Agents Window browser/run workflow to remember and reopen the relevant URL without manual configuration, preserving explicit task and URL choices. Coordinate server discovery with the existing frontend-preview work and reuse the existing run-command generation capability.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/chat/browser/runScriptAction.ts`, `src/vs/sessions/contrib/chat/browser/sessionsTasksService.ts`, `src/vs/sessions/contrib/browserView/browser/sessionBrowserView.ts`, `src/vs/sessions/skills/generate-run-commands/SKILL.md`, `src/vs/sessions/contrib/chat/test/browser/runScriptAction.test.ts`, `src/vs/sessions/contrib/chat/test/browser/sessionsTaskService.test.ts`
- **Validation:** After settling the product contract, verify that opening and navigating a site without configuring a URL allows relaunch from a later session; explicit tasks and manually configured URLs remain authoritative. Verify the server-required case produces a usable run task without overwriting unrelated tasks. Add focused launch-selection and persistence coverage in the existing runScriptAction and sessionsTaskService suites; a live Agents Window check should cover browser navigation and server startup.
- **Behavior:**

  > A user who opens a website in an Agents Window workspace should be able to reopen the remembered site in a future session without entering its URL manually. With no explicit run task, the Play or dedicated Browser action should use the recorded URL. When a local server is required, the workflow should help establish a runnable server task. Acceptance must include persistence across session changes and preservation of existing explicit task and URL configuration.
- **Trace:**

  > RunScriptContribution in src/vs/sessions/contrib/chat/browser/runScriptAction.ts reads repository-scoped browserUrl and pinnedBrowser state from SessionsTasksService; browser invocation currently uses simpleBrowser.show, while URL capture is a manual quick-input operation. SessionsTasksService persists this configuration in application storage, keyed by repository, rather than deriving it from browser navigation. SessionBrowserViewController in src/vs/sessions/contrib/browserView/browser/sessionBrowserView.ts tracks browser/session ownership but does not write the launch URL. Explicit task generation already delegates to /generate-run-commands and its built-in skill. Preserve explicit task selection, configured URLs, unrelated tasks, and browser ownership behavior. Coordinate with https://github.com/microsoft/vscode/issues/317569 for server discovery; uncertainty begins with which URL is remembered when several tabs or sessions share a repository and whether that memory follows the repository or individual session.
- **Open decisions:**
  - Should automatically remembered URLs be shared across all sessions for a repository, matching current manual configuration, or retained separately for each session?
  - When multiple browser tabs exist, which URL becomes the future launch target, and should subsequent navigation replace it automatically?
