# Issue #336735 — Codex Agent Host restarts the full MCP server set in an existing thread

[https://github.com/microsoft/vscode/issues/336735](https://github.com/microsoft/vscode/issues/336735)

## Summary

Traced a concrete mechanism on main that matches the report: the Codex agent's `_customizationEnablementService.onDidChange` handler in codexAgent.ts unconditionally sets `session.materializedMcpSig = undefined` for any session whose configuration resource is affected by a customization-enablement change — even when the change is a non-MCP `Plugin`-type target — forcing the next `_ensureCurrentLaunchBeforeTurn` comparison to mismatch and trigger a full MCP restart wave regardless of whether the actual merged MCP server set changed.

## Change summary

The Codex Agent Host restarts all configured MCP servers on a subsequent turn in the same thread even though the user made no MCP configuration change.

## Best solution

Scope the invalidation in the `onDidChange` handler (src/vs/platform/agentHost/node/codex/codexAgent.ts, ~lines 1318-1333) so `materializedMcpSig` is only cleared when the affected target actually changes the merged MCP server set (or, better, recompute and compare the actual signature before forcing a mismatch), rather than unconditionally invalidating on every customization-enablement event for the session — especially since `controller.applyAll(...)` already appears to live-apply MCP changes to the running thread in the same handler, making the subsequent full-restart trigger look redundant for genuinely unrelated changes.

- **Open decisions:**

## Evidence

- **restart trigger:** `_ensureCurrentLaunchBeforeTurn` (lines 6026-6067) compares the recomputed `mcpSignature` to `session.materializedMcpSig`; once the latter is forced to `undefined`, the comparison mismatches even if `_buildSessionMcpServers` would recompute the identical signature, causing `_markSessionForReload` + `_resumeSession` to run and resend the full MCP set (matches the user's own trace of `_buildSessionMcpServers()`/`_ensureCurrentLaunchBeforeTurn()`).

- **live-apply already present:** The same handler already calls `controller.applyAll(inventoryToSdkServers(...))` on `session.mcpController` before invalidating the signature, suggesting the full-restart path may be an unintended double-application rather than the only mechanism for applying enablement changes.
