# Issue #336735 — Codex Agent Host restarts the full MCP server set in an existing thread

[https://github.com/microsoft/vscode/issues/336735](https://github.com/microsoft/vscode/issues/336735)

## Summary

The mechanism the reporter describes matches current main exactly: `_ensureCurrentLaunchBeforeTurn` (codexAgent.ts:6026) recomputes the MCP/tools/customization signatures before every turn and, on any mismatch after the first turn, calls `_markSessionForReload` + `_resumeSession`, which sends `thread/resume` with the full `_buildSessionMcpServers()` set (codexAgent.ts:6600-6689) — there's no partial/incremental MCP update path. Whether the observed repeat restarts stem from a genuinely stale signature bug or from `thread/resume` legitimately requiring the full server list is not something I can settle by reading the source alone.

## Change summary

Codex Agent Host resends the entire MCP server set (including expensive npx-launched local servers and OAuth flows) on an existing thread's second turn, even when the user made no MCP configuration change.

## Best solution

Diagnose (with reproduction) exactly which trigger flips `session.materializedMcpSig`/`materializedCustomizationsSig` between the first and second turn in the reporter's scenario — likely candidates are `_buildCustomizationLaunch`'s signature (codexAgent.ts:1945-1994, e.g. `session.customizationDirectory` or workspace agent/skill discovery re-scans) or `_refreshSessionMcpDiscovery`'s onDidChange (codexAgent.ts:2737-2760) — and either stabilize the signature so a no-op turn doesn't drift, or (if `thread/resume` genuinely needs the full config) special-case sending only servers whose materialized state actually changed.
