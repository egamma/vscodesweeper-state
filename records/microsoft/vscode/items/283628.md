# Issue #283628 — Copilot Chat: when stopping the response, re-populate the input textbox with the input for editting

[https://github.com/microsoft/vscode/issues/283628](https://github.com/microsoft/vscode/issues/283628)

## Summary

A real Copilot Chat workflow improvement remains open: stopping a response currently cancels generation without restoring the submitted request, while the existing history and edit-request features require a separate action. The existing under-discussion classification remains appropriate.

## Change summary

Restore the submitted Copilot Chat request to the composer when the user stops its response so it can be corrected and resent.

## Best solution

Design stop-response behavior that makes the canceled request immediately editable while protecting any newer draft and deciding whether its attachments and input state should also be restored.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/actions/chatExecuteActions.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts`, `src/vs/workbench/contrib/chat/test/browser/actions/chatExecuteActions.test.ts`
- **Validation:** Add action-level tests covering Stop with an empty composer and with a draft typed during generation, then run the targeted chatExecuteActions test suite; the resulting behavior must match the maintainer's decisions for draft and attachment restoration.
- **Behavior:**

  > When a user stops an active Chat response because the submitted request needs correction, that request should be immediately available for editing rather than requiring copy/paste or history navigation. The plan must define what happens if the user has already typed a new draft and whether the original request's attachments and other input state return. Acceptance should cover stopping with an empty composer, stopping with a nonempty newer draft, and resending the restored request.
- **Trace:**

  > ChatCancelAction in src/vs/workbench/contrib/chat/browser/actions/chatExecuteActions.ts currently delegates directly to IChatService.cancelCurrentRequestForSession and does not interact with the composer. ChatInputPart.acceptInput in src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts stores the submitted input state in history before clearing the editor, and navigateHistory already restores text, attachments, and contribution state. ChatWidget.startEditing/clickedRequest in src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts provides another restoration path for explicitly editing a sent request. The boundary is the user-initiated Stop action: cancellation from session teardown, edit replacement, or stop-and-send must not acquire this behavior accidentally.
- **Open decisions:**
  - If the user typed a new draft while the response was running, should Stop preserve that draft, replace it with the canceled request, or combine the two through an explicit choice?
  - Should stopping restore the canceled request's attachments and contributed input state as well as its text?

## Evidence

- **current stop path:** ChatCancelAction in src/vs/workbench/contrib/chat/browser/actions/chatExecuteActions.ts calls cancelCurrentRequestForSession for the active session but does not restore request input or attachments.
- **current submission behavior:** ChatInputPart.acceptInput in src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts records the submitted input in history and then clears the composer; navigateHistory can restore it, but only through an additional history-navigation action.
- **partial existing capability:** ChatWidget.startEditing/clickedRequest in src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts can populate an editor with a previous request and its context, but this is an explicit edit-request workflow rather than the requested automatic behavior after Stop.
