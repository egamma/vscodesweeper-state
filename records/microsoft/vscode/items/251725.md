# Issue #251725 — MCP `resources/read` doesn't support multiple Resources in result

[https://github.com/microsoft/vscode/issues/251725](https://github.com/microsoft/vscode/issues/251725)

## Summary

Keep open: directory browsing has since been added, but current source still does not reliably expose the returned resources as readable documents. The existing sample is sufficient; the remaining work is in resource-result handling and picker URI identity.

## Change summary

Allow users to browse and read every resource returned by a single MCP resources/read response instead of encountering a directory error.

## Best solution

Complete multi-content resource handling in the MCP resource browser, preserving each returned resource's identity and content without requiring directory-shaped URIs. Agree on the selection behavior before extending the existing directory-navigation implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/browser/mcpResourceQuickAccess.ts`, `src/vs/workbench/contrib/mcp/common/mcpResourceFilesystem.ts`, `src/vs/workbench/contrib/mcp/common/mcpTypes.ts`, `src/vs/workbench/contrib/mcp/test/common/mcpResourceFilesystem.test.ts`
- **Validation:** Use the issue's server handlers, select System Prompts through MCP: Browse Resources, and verify both returned documents can be read as foo1 and foo2 without a directory error or double-wrapped server URI. Repeat with a parent URI without a trailing slash and with returned URIs outside a common directory. Add focused regression coverage for the agreed result-selection contract and preserve the existing ResourceFilesystem tests.
- **Behavior:**

  > An MCP resource read may return multiple content entries whose URIs differ from the requested URI. Users must be able to discover and read every returned entry rather than encountering a directory-only editor error. The supplied System Prompts example must expose prompt-1.md and prompt-2.md with their respective foo1 and foo2 contents. Ordinary single-resource opening must remain unchanged; acceptance should also cover responses without directory hints or a shared URI hierarchy.
- **Trace:**

  > McpBrowseResourcesCommand leads to AbstractMcpResourceAccessPick, whose acceptance handler calls McpResourcePickHelper.navigate before opening an editor. Directory navigation was added by https://github.com/microsoft/vscode/commit/6e14077b6de2cdbb46632e2147ec51b4f1810e75, but navigate currently wraps already-namespaced filesystem child URIs with McpResourceURI.fromServer again. Independently, navigation depends on trailing-slash or inode/directory hints, while McpResourceFilesystem.stat and _readFile infer a directory whenever no returned content matches the requested URI. The existing filesystem tests cover directory classification and enumeration, not successful browser selection of returned documents. Keep ordinary file reads, resource templates, and existing attachment behavior intact. The unresolved product boundary is how arbitrary multi-content results are presented and selected; the reporter offers automatic tabs or a selection dialog, and the maintainer accepted support without choosing between them.
- **Open decisions:**
  - For general multi-content responses, should Browse Resources open all returned documents automatically or present a selection step, and should that step support selecting multiple entries?

## Evidence

- **Accepted behavior:** The report supplies a concrete server response and Browse Resources steps. A maintainer explicitly accepted supporting this case: https://github.com/microsoft/vscode/issues/251725#issuecomment-3001944132.
- **Partial implementation:** Commit https://github.com/microsoft/vscode/commit/6e14077b6de2cdbb46632e2147ec51b4f1810e75 added directory navigation through McpResourcePickHelper.navigate and the picker acceptance handler. Its merged PR, https://github.com/microsoft/vscode/pull/272623, references the related, now-closed https://github.com/microsoft/vscode/issues/262368. This is relevant progress, not proof that all multi-resource responses work.
- **Remaining URI defect:** src/vs/workbench/contrib/mcp/browser/mcpResourceQuickAccess.ts:147-159 passes child.resource.toString() from IFileService.resolve into McpResourceURI.fromServer again. These children already use the mcp-resource filesystem scheme; fromServer in common/mcpTypes.ts:1145-1153 wraps that scheme into the path a second time. Selecting a child therefore decodes to an mcp-resource URL rather than the server's original file://prompts/prompt-1.md or file://prompts/prompt-2.md, so the supplied server response cannot yield the intended readable child document.
- **General multi-content gap:** McpResourcePickHelper.navigate requires a trailing slash or inode/directory MIME type before displaying resolved children. Meanwhile, common/mcpResourceFilesystem.ts:151-162 classifies responses without a matching requested URI as directories, and _readFile at lines 212-227 rejects them. Valid multi-content responses without directory hints can therefore still fall through to opening a directory in the editor.
- **Canonical and PR search:** Read-only GitHub searches for MCP resources and resources/read contents found no verified open canonical covering this browser defect and no open PR mentioning this issue. https://github.com/microsoft/vscode/issues/291004 concerns agent-programmatic resource access, not this user-driven browsing failure.
