# Issue #288245 — Feature request: Recognise Copilot context tags when pasting into chat box

[https://github.com/microsoft/vscode/issues/288245](https://github.com/microsoft/vscode/issues/288245)

## Summary

Current main still lacks this capability: plain-text paste does not resolve valid context-tag text into the dynamic references that render as active chips. Keep the request open under discussion and route it to the chat-input area.

## Change summary

Recognize valid Copilot context references such as `#file:app.component.ts` in pasted plain text and activate them in the chat input.

## Best solution

Pasted context references should resolve through the same semantics as interactively selected chat completions, producing active references when unambiguous while preserving unresolved text unchanged.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input/editor/chatPasteProviders.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts`, `src/vs/workbench/contrib/chat/browser/attachments/chatDynamicVariables.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/input/editor/chatPasteProviders.test.ts`
- **Validation:** Extend the Chat Paste Providers unit suite to verify that an unambiguous pasted `#file:` token becomes an active inline reference, surrounding text is preserved, and invalid or unresolved tokens remain plain text.
- **Behavior:**

  > Pasting prompt text containing a valid context reference should produce the same active reference users receive when selecting that reference through chat completion. Surrounding prompt text and multiple references must retain their original ordering. Invalid or unresolved reference-like text must remain editable plain text without silently attaching unrelated context.
- **Trace:**

  > `PasteTextProvider` in `src/vs/workbench/contrib/chat/browser/widget/input/editor/chatPasteProviders.ts` currently has no plain-text context-reference resolution path. Active file chips are backed by `IDynamicVariable` entries created by `BuiltinDynamicCompletions` in `chatInputCompletions.ts` and tracked by `ChatDynamicVariableModel` in `browser/attachments/chatDynamicVariables.ts`. The custom clipboard path added for https://github.com/microsoft/vscode/issues/249523 preserves references copied from another chat input but cannot recover references from ordinary editor text. The boundary is chat-input paste handling: existing plain paste, serialized chat-to-chat paste, GitHub-link attachment, long-text artifact, and completion behavior must remain intact.
- **Open decisions:**
  - Should automatic paste recognition initially cover only `#file:` references, or every context-reference kind that can be selected through chat completion?
  - When a pasted file token is ambiguous across workspace folders, should it remain plain text or prompt the user to select a target?

## Evidence

- **current source gap:** `PasteTextProvider` in `src/vs/workbench/contrib/chat/browser/widget/input/editor/chatPasteProviders.ts` handles GitHub URLs, long-text artifacts, editor-copy metadata, and serialized chat attachments, but contains no path that parses plain-text `#file:` references into attachments or dynamic references.
- **active-reference path:** `BuiltinDynamicCompletions` in `src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts` creates file-reference completion entries and registers their `IDynamicVariable` through `ChatDynamicVariableModel.addReference`; merely inserting the same text does not invoke that path.
- **related issue distinction:** https://github.com/microsoft/vscode/issues/249523 covered preserving already-active references when copying between chat inputs. Its implementation uses the custom `application/vnd.chat.attachment+json` clipboard payload in `CopyAttachmentsProvider`, so it does not cover plain text copied from an editor as reported here.
- **canonical search:** Exact searches for pasted `#file:` and context-tag text found this issue and the closed https://github.com/microsoft/vscode/issues/249523, but no older open issue reporting the same plain-text-paste symptom.
