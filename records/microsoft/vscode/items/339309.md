# Issue #339309 — Claude agent host: between-turn 'resume rebuild' kills subagents and drops replies

[https://github.com/microsoft/vscode/issues/339309](https://github.com/microsoft/vscode/issues/339309)

## Summary

Thanks for the detailed report. The between-turn rebuild path still exists on main, and a second reporter confirms it on 1.141 with MCP respawns. I found no fix, so this stays open.

## Change summary

Between-turn 'resume rebuild' in the Claude agent host kills running background subagents and can drop the assistant's reply.

## Best solution

Defer or avoid the between-turn rebind while subagents are running, or hand them off to the new session. Also make SDK-initiated notice turns not consume the pending user turn's result slot, and avoid restarting stdio MCP servers on a client-tool re-announce that changes nothing.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/claude/claudeSdkPipeline.ts`, `src/vs/platform/agentHost/node/claude/claudeAgentSession.ts`
- **Validation:** A pipeline test in src/vs/platform/agentHost/test/node/claudeSdkPipeline.test.ts showing that a rebind with running subagents is deferred or preserves them, and that a notice-turn result does not close the pending user turn.
- **Behavior:**

  > Between turns, a client-tool or customization re-announce must not discard a live SDK session while background subagents are running. A subagent stopped-notice turn must not consume the pending user turn's result, and the real reply must render. A no-op client-tool re-announce must not respawn MCP servers.
- **Trace:**

  > ClaudeAgentSession.send() pre-flight calls rebindForRestart() when the tool diff or customization diff is dirty. That goes through ClaudeSdkPipeline._rebindQuery('restart'), which swaps in a resumed query and kills in-process subagents. Boundary: keep the rebind needed for real tool-set or plugin changes, and keep the abort/crash recovery path as is. Related: https://github.com/microsoft/vscode/issues/332073 and https://github.com/microsoft/vscode/issues/337904. The uncertainty starts at how a deferred rebind interacts with a changed tool set.
- **Open decisions:**
  - When subagents are running and the tool set changed, defer the rebind until they finish, or hand them off to the new session?
  - Should a client re-announce with an identical tool set skip the rebind and the MCP respawn entirely?

## Evidence

The design docs (phase10/11 plans) confirm that a client-tool diff or customization change triggers a restart rebind at the send() pre-flight.
