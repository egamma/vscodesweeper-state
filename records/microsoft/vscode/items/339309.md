# Issue #339309 — Claude agent host: between-turn 'resume rebuild' kills subagents and drops replies

[https://github.com/microsoft/vscode/issues/339309](https://github.com/microsoft/vscode/issues/339309)

## Summary

Fresh, carefully diagnosed report with matching source evidence: no code path in ClaudeSdkPipeline/ClaudeAgentSession defers or hands off a between-turn rebind while background subagents are running, and the prompt queue's result-slot handling doesn't distinguish an SDK-initiated notice turn from the pending user turn. Kept open for design + fix; too fresh and too architecturally deep for an automatic close.

## Change summary

A between-turn SDK session rebind (triggered by tool/MCP/directory/permission drift) kills running background subagents and the prompt queue's result-slot logic then lets a tiny stopped-notice turn consume the pending user turn's result, dropping the real reply.

## Best solution

Either defer `_rebindQuery`/`rebindForRestart` while `SubagentRegistry` shows running background spawns, or make the rematerializer hand them off to the fresh session; separately, harden `ClaudePromptQueue`'s result/turn-close logic so an SDK-initiated notice turn (sdkUuid=undefined / stopped-notice) can't close out a different pending user turn.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/claude/claudeSdkPipeline.ts`, `src/vs/platform/agentHost/node/claude/claudeAgentSession.ts`, `src/vs/platform/agentHost/node/claude/claudeSubagentRegistry.ts`, `src/vs/platform/agentHost/node/claude/claudePromptQueue.ts`
- **Validation:** A claudeSdkPipeline/claudeAgentSession test asserting that a rebind triggered while a background SubagentSpawn is still running either (a) is deferred until the subagent completes, or (b) preserves/hands off the subagent to the rebuilt session instead of discarding it; plus a claudePromptQueue test asserting an SDK-initiated notice turn (sdkUuid=undefined) cannot close out a different pending user turn's result slot.
- **Trace:**

  > `ClaudeSdkPipeline._rebindQuery`/`rebindForRestart` (claudeSdkPipeline.ts) discard the live `_warm`/`_abortController` and rebuild via the rematerializer whenever desired state drifts (restart, client-tool diff, MCP/directory/permission changes), with no check against `ClaudeAgentSession.subagents` (SubagentRegistry) for still-running background spawns — traced via rg/read, no guard present on main. Separately, `ClaudePromptQueue.resetForRebind` re-parks queue state without distinguishing an SDK-initiated notice/result (sdkUuid=undefined) from the pending user turn's result slot, matching the reported log sequence where a 23ms stopped-notice turn closes the real turn and the actual reply (`result for sdkUuid=undefined`) is never rendered. Boundary: do not change the rematerializer's resume semantics or the general tool/MCP-diff rebind triggers themselves — only how a rebind behaves when subagents are in flight, and how queue result-matching selects which pending turn a result belongs to.
- **Open decisions:**
  - Should a between-turn rebind be deferred until running background subagents finish, or should the rematerializer hand off / re-attach those subagents to the freshly rebuilt session?
  - How should the prompt queue identify which pending user turn a given SDK result belongs to, so an SDK-initiated notice turn (sdkUuid=undefined) can never consume a different turn's result slot?
