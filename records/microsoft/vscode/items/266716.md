## Evidence

- **Confirmed renderer OOM:** The report records CodeWindow renderer termination with reason oom on Windows 11 and VS Code 1.104.0 after opening a Node.js workspace with Copilot enabled. In https://github.com/microsoft/vscode/issues/266716#issuecomment-3349954462, a maintainer analyzed the supplied trace, confirmed the workbench reached its 4GB JavaScript heap limit, and identified growth from approximately 600MB to 3GB during editing-session restoration.
- **Storage-specific isolation:** https://github.com/microsoft/vscode/issues/266716#issuecomment-3383698897 records 264MB across approximately 2,400 files in ChatEditingSessions and the reporter's confirmation that removing that folder stopped the crash. This supports investigating persisted editing state rather than treating the report as an extension-host heap-setting question.
- **Current restoration path:** src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSessionStorage.ts:49-120 still reads referenced contents into strings cached by hash, materializes initialFileContents and recentSnapshot, and revives the timeline. ChatEditingSession._init in src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts:290-314 retains initial contents and restores the timeline and snapshot entries. This identifies the relevant path but does not conclusively establish the reported memory amplification on current main.
- **Relevant change, not a verified fix:** https://github.com/microsoft/vscode/commit/f2d4661d83723e47852bf27eeb5a5ff3827d87ff replaces eager deserialization of linearHistory and pendingSnapshot with persisted timeline state in chatEditingSessionStorage.ts. Its diff removes the Promise.all over historical snapshots, but it does not reference this issue or establish that restoring the reporter's dataset no longer exhausts the heap; it is a retest lead, not sufficient fix provenance.
