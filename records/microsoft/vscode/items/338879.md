# Issue #338879 — Can not install local MCP server from MCP registry by Azure API Center when allowlist is enabled as enterprise policy.

[https://github.com/microsoft/vscode/issues/338879](https://github.com/microsoft/vscode/issues/338879)

## Summary

Traced in source: the allowlist identity computed for gallery (not-yet-installed) local/stdio MCP servers never includes a derived command, so a `serverCommand` allowlist entry can never match before install — only `serverName`/`serverUrl` can. This is the exact bug the reporter hit (install blocked by an enterprise `allowedMcpServers` policy even though the same command works once manually added to mcp.json).

## Change summary

Installing a local/stdio MCP server surfaced from an MCP registry (e.g. Azure API Center) is blocked by an enterprise `allowedMcpServers` command allowlist, even though the same resolved command passes the allowlist when added manually to mcp.json.

## Best solution

Make `AllowedMcpServersService.toIdentity()` (src/vs/platform/mcp/common/allowedMcpServersService.ts) derive a predicted command for local/stdio gallery packages — mirroring the command/args computation already done post-resolution in `AbstractCommonMcpManagementService.getMcpServerConfigurationFromManifest` (mcpManagementService.ts) — so the pre-install `canInstall` gate can match `serverCommand` allowlist entries the same way the resolved-config check already does.

## Plan brief

- **Likely files:** `src/vs/platform/mcp/common/allowedMcpServersService.ts`, `src/vs/platform/mcp/common/mcpManagementService.ts`, `src/vs/platform/mcp/test/common/allowedMcpServersService.test.ts`
- **Validation:** Add a test asserting a gallery server whose manifest resolves (via getMcpServerConfigurationFromManifest-equivalent logic) to command ['npx','@playwright/mcp@latest'] is allowed pre-install when the allowlist contains {serverCommand:['npx','@playwright/mcp@latest']}, and still blocked when it doesn't match.
- **Behavior:**

  > When an enterprise `chat.mcp.allowedServers`/managed-settings allowlist contains a `serverCommand` entry, installing a local (stdio) MCP server surfaced from an MCP registry/gallery (e.g. Azure API Center) whose resolved command+args match that entry should succeed via the normal Install UI — the same as if the equivalent entry were hand-added to mcp.json. Today it is always blocked with 'This mcp server cannot be installed because this Model Context Protocol server is not in the list of servers allowed...' regardless of whether the command actually matches. Acceptance: a matching local/stdio gallery server installs successfully through the UI; a non-matching one remains correctly blocked.
- **Trace:**

  > `AllowedMcpServersService.toIdentity()` in src/vs/platform/mcp/common/allowedMcpServersService.ts (~lines 113-126) only derives `url` for gallery servers with `configuration.remotes[0]`; for package/stdio-based servers it returns `{name, url: undefined}` with no `command`, so `checkMcpServerAllowed`/`isMcpServerMatched` (allowedMcpServers.ts) can never satisfy a `serverCommand` matcher at this phase — only `serverName` (or being treated as 'unresolved') can pass. This feeds both `AbstractMcpManagementService.canInstall` (mcpManagementService.ts:667-673, used by the Install button via src/vs/workbench/contrib/mcp/browser/mcpWorkbenchService.ts:698-719) and the gallery install's early checks. Once the manifest IS resolved — `AbstractCommonMcpManagementService.getMcpServerConfigurationFromManifest` (mcpManagementService.ts:73-186) computes command='npx'/args=['identifier@version'] for RegistryType.NODE, etc. — and re-checked as an `IInstallableMcpServer` with `config.command`, the identity picks up the command correctly (src/vs/platform/mcp/node/mcpManagementService.ts:29-60), explaining why the reporter's manual mcp.json edit worked. Boundary: do not change the matching semantics in allowedMcpServers.ts or the already-correct resolved-config enforcement (`ensureServerAllowed`) — only the pre-install identity derivation for gallery/local servers needs to predict the command. Where the uncertainty starts: whether to reuse/extract the package→command derivation verbatim or approximate it, how to handle a manifest with multiple packages/registry types not yet chosen, and how unresolved package arguments should affect the match.
- **Open decisions:**
  - Should the pre-install identity reuse/extract the exact package→command/args derivation from getMcpServerConfigurationFromManifest, or is a simpler 'command + identifier@version' approximation acceptable for the allowlist check?
  - When a gallery manifest offers multiple packages/registry types, should the pre-install check evaluate all of them against the allowlist, or only the one that will actually be installed?
  - Should an unresolved/variable-dependent package argument make the pre-install match conservative ('allowed', like the existing unresolved-URL logic) or still 'not allowed', to avoid letting an unverifiable command slip past the allowlist?

## Evidence

- **pre-install identity never computes a command:** src/vs/platform/mcp/common/allowedMcpServersService.ts lines 113-126 (`toIdentity`): for a gallery server it only extracts `url` from `configuration.remotes[0]`; for package/stdio-based entries it returns `{ name, url: undefined }` with no `command` at all, so `serverCommand` matchers in allowedMcpServers.ts can never match at this phase.
- **UI gate reproduces the exact reported message:** src/vs/platform/mcp/common/mcpManagementService.ts lines 667-673 (`AbstractMcpManagementService.canInstall`) calls `allowedMcpServersService.isAllowed(server)` with the raw gallery server and formats "This mcp server cannot be installed because {0}" — matching the reporter's exact error. This is invoked from `McpWorkbenchService.canInstall` in src/vs/workbench/contrib/mcp/browser/mcpWorkbenchService.ts:698-719, which backs the Install button.
- **resolved path works, confirming the gap:** src/vs/platform/mcp/node/mcpManagementService.ts lines 29-60 (`installFromGallery`) computes `mcpServerConfiguration.config` via `getMcpServerConfigurationFromManifest` (command='npx', args=['@playwright/mcp@latest']) and re-checks via `ensureServerAllowed(installable)` against the now-present `config` — this is the resolved path that DOES match a `serverCommand` entry, matching the reporter's step 8 workaround of hand-editing mcp.json.
