# Issue #338879 — Can not install local MCP server from MCP registry by Azure API Center when allowlist is enabled as enterprise policy.

[https://github.com/microsoft/vscode/issues/338879](https://github.com/microsoft/vscode/issues/338879)

## Summary

Traced this in the allowlist code: when an enterprise `serverCommand` allowlist is set, browsing/installing a local (stdio-package) MCP server straight from a registry is blocked because the pre-install identity built for gallery servers never carries command information for local packages — only for remotes. Manually adding the same server to mcp.json works because that path builds the identity from the resolved config, which does carry the command.

## Change summary

Installing a local/stdio MCP server discovered via a gallery/registry (e.g. Azure API Center) is refused by a `serverCommand`-based enterprise allowlist, even though the identical server works when added manually to mcp.json.

## Best solution

Make `AllowedMcpServersService.toIdentity()` (src/vs/platform/mcp/common/allowedMcpServersService.ts) recognize gallery servers that only have local `packages` (no `remotes`) as having an as-yet-unresolved command, and route them through the existing unresolved-command deferral path in `checkServerAllowedBeforeResolution` (same logic already used for command entries containing unresolved config variables) so a `serverCommand` allowlist entry can provisionally allow them pending the post-install resolved check.

## Plan brief

- **Likely files:** `src/vs/platform/mcp/common/allowedMcpServersService.ts`, `src/vs/platform/mcp/common/allowedMcpServers.ts`, `src/vs/platform/mcp/test/common/allowedMcpServersService.test.ts`
- **Validation:** A new allowedMcpServersService test: a gallery server with only local `packages` (no `remotes`) against a `serverCommand`-only allowlist should be permitted pre-install (deferred), matching the existing 'defers command/URL policies for ... unresolved inputs' test pattern already in the suite.
- **Behavior:**

  > Installing a local (stdio/package-based) MCP server discovered from a registry/gallery should be permitted when a `chat.mcp.allowedServers`/managed `serverCommand` entry matches the command the server will actually be launched with, exactly as it is when the same server is added manually to mcp.json. Today it is always refused pre-install for such servers whenever any allowlist is configured (unless a `serverName` entry also exists), because the gallery-side identity used for the install gate never carries a command. Acceptance: a gallery server with only local packages and a matching `serverCommand` allowlist entry can be installed from the UI/registry the same as via mcp.json; deny/allow behavior for remote (URL-based) gallery servers is unchanged.
- **Trace:**

  > Root cause is `AllowedMcpServersService.toIdentity()` in src/vs/platform/mcp/common/allowedMcpServersService.ts (lines 113-126): for `IGalleryMcpServer`/`IInstallableMcpServer` without an already-resolved `config`, it builds `{ name, url }` from `mcpServer.configuration.remotes` only, ignoring `mcpServer.configuration.packages` entirely, so `command` is always `undefined` for local/stdio gallery servers. `matchesMatcher()` in allowedMcpServers.ts (lines 95-106) then can't match any `serverCommand` matcher since `identity.command` is undefined. The install gate (`canInstall`/`ensureServerAllowed` in mcpManagementService.ts, lines 361-366 and 667-673) calls `isAllowed(server)` with this same unresolved identity, producing the reported error. Contrast with `checkServerAllowedBeforeResolution` (allowedMcpServersService.ts lines 74-97), which already has a deferral mechanism for commands containing unresolved config variables (permits install when any `serverCommand`-shaped allowlist entry exists, then re-checks with the resolved command via `isServerAllowed`) — that same deferral needs to also fire for 'local package, command not yet computed' rather than only 'command computed but has variable placeholders'. Boundary: do not change matching semantics for remote/URL servers, do not touch the resolved-phase (`isServerAllowed`) exact-match logic, which already works correctly per the reporter's manual-edit test (step 8).
- **Open decisions:**
  - Should the pre-install identity for a local-package gallery server be treated as fully unresolved (deferred to post-install check, permitting install whenever any `serverCommand`-shaped allowlist entry exists, mirroring the existing config-variable deferral), or should VS Code attempt a best-effort partial command synthesis (e.g. from `runtimeHint`/`identifier`) for a tighter pre-install match?
  - Does this deferral require a shape change to the shared `IMcpServerIdentity` contract (e.g. an explicit 'unresolved' flag) given it's also consumed by src/vs/workbench/contrib/mcp/common/mcpServer.ts, or can it stay internal to AllowedMcpServersService?

## Evidence

- **toIdentity gap:** src/vs/platform/mcp/common/allowedMcpServersService.ts lines 113-126: for gallery servers, toIdentity() only derives `url` from `mcpServer.configuration.remotes`; `mcpServer.configuration.packages` (the local/stdio case, e.g. the reporter's npm/@playwright/mcp package) is never inspected, so `command` stays `undefined`.
- **match consequence:** matchesMatcher() in allowedMcpServers.ts (lines 95-106) requires `identity.command !== undefined` to match a `serverCommand` matcher; with `command` and `url` both undefined, only a `serverName` matcher could ever allow the server, so a `serverCommand`-only allowlist entry (as in the reporter's managed-settings.json) can never permit a locally-packaged gallery server before install.
- **install-time gate:** canInstall()/ensureServerAllowed() in mcpManagementService.ts (lines 361-366, 667-673) call `allowedMcpServersService.isAllowed(server)` with the same unresolved gallery representation, producing exactly the reported error text 'This mcp server cannot be installed because This Model Context Protocol server is not in the list of servers allowed by your organization.'
- **manual path works:** Manually adding the resolved mcp.json entry (as in the reporter's step 8) goes through `isServerAllowed`/`isServerAllowedBeforeResolution` with a fully resolved `command` array, which does match the `serverCommand` matcher — explaining why the same server starts fine when hand-edited.
- **no test coverage:** src/vs/platform/mcp/test/common/allowedMcpServersService.test.ts only exercises installable-server command matching and gallery URL/remote matching; there is no test for a gallery server with local `packages` and no `remotes`, consistent with this gap being unhandled.
