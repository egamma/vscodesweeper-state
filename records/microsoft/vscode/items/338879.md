# Issue #338879 — Can not install local MCP server from MCP registry by Azure API Center when allowlist is enabled as enterprise policy.

[https://github.com/microsoft/vscode/issues/338879](https://github.com/microsoft/vscode/issues/338879)

## Summary

Thanks for the detailed report. This still reproduces from source: gallery servers are checked against the allowlist by name or first remote URL only, so a local npm/stdio server with a command allowlist entry is blocked before install.

## Change summary

Gallery MCP servers that are local package-based (stdio) cannot be installed under an enterprise allowlist, even when their command is allowlisted.

## Best solution

In allowedMcpServersService.ts, make the pre-install gallery check derive the candidate command from the package (e.g. runtimeHint plus identifier@version) or defer the command check to the resolved phase, so allowlisted serverCommand entries match gallery installs.

## Plan brief

- **Likely files:** `src/vs/platform/mcp/common/allowedMcpServersService.ts`
- **Validation:** Unit test in the allowedMcpServersService suite: a gallery server with a single npm stdio package and an allowlist containing the matching serverCommand is allowed; one not in the list stays blocked.
- **Behavior:**

  > A gallery MCP server delivered as a local package (npm/stdio, no remotes) can be installed from the MCP gallery when the managed allowlist contains a serverCommand matching the command it would run. Servers not matching still show the 'not in the list of servers allowed by your organization' message. Behavior with no allowlist is unchanged.
- **Trace:**

  > IAllowedMcpServersService.isAllowed -> toIdentity() produces an identity with no command for gallery servers, so checkServerAllowed in the 'definition' phase can only match by name or URL. The command is known only after resolution. The boundary is the allowlist matching logic: do not loosen matching for servers that do not match any entry. Uncertainty: how to derive the command (runtimeHint, args, versions, package arguments) reliably before install.
- **Open decisions:**
  - Should the pre-install gallery check infer the command from package metadata, or allow gallery installs to proceed and enforce the allowlist only at resolution time?
  - Should allowlist matching treat version-pinned and unpinned package arguments (e.g. @latest vs a pinned version) as equivalent?

## Evidence

- **code path:** src/vs/platform/mcp/common/allowedMcpServersService.ts toIdentity() (lines ~122-125): for gallery servers it returns only { name, url: remotes[0] }, with no command, so serverCommand allowlist entries can never match before install.
- **corroboration:** A second commenter reproduced it on 1.141.2 with the default GitHub registry and server-managed settings.
- **workaround:** A manual mcp.json entry with the same command runs fine, because it goes through the config path that includes the command.
