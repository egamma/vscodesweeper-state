# Issue #157112 — Add support for running custom tasks in VS Code Web

[https://github.com/microsoft/vscode/issues/157112](https://github.com/microsoft/vscode/issues/157112)

## Summary

Keep this accepted request open: current source supports custom execution and conditionally exposes task commands, but that does not establish reliable end-to-end support for the supplied web extension. The related open issues cover narrower problems, not an older canonical owning this request.

## Change summary

Officially support extension-provided CustomExecution tasks in VS Code Web, including discoverable task commands and clear execution limitations.

## Best solution

Make custom task discovery and execution reliable in serverless web workspaces while keeping shell/process execution unavailable without a suitable backend. First retest the supplied sample and establish the supported discovery and menu behavior with the tasks maintainer.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts`, `src/vs/workbench/contrib/tasks/browser/task.contribution.ts`, `src/vs/workbench/contrib/tasks/common/taskService.ts`, `src/vs/workbench/api/common/extHostTask.ts`, `src/vs/workbench/api/browser/mainThreadTask.ts`
- **Validation:** Run the supplied task-provider-sample in current serverless VS Code Web with a workspace and compare with desktop: Tasks: Run Task must list and execute its custom task, including pseudoterminal output and completion. Repeat without a workspace to verify the maintainer-agreed scope behavior; verify shell/process tasks remain unsupported and ordinary web startup does not eagerly fetch every provider.
- **Behavior:**

  > A web extension providing CustomExecution tasks should have a reliable, discoverable way to list and run those tasks in serverless VS Code Web. The supplied sample currently reports desktop success but a web command that does nothing. Acceptance should cover task discovery, execution, output, and completion while clearly distinguishing custom execution from unavailable local shell/process execution. Establish whether empty-window execution is part of the supported contract before using it as an acceptance requirement.
- **Trace:**

  > BaseExtHostTask in src/vs/workbench/api/common/extHostTask.ts announces custom execution support, and MainThreadTask forwards that registration to AbstractTaskService. TaskExecutionSupportedContext includes custom execution, and task.contribution.ts already uses it for task menu visibility; workbench.action.tasks.runTask is also registered in the command palette. AbstractTaskService's runTask handler checks _trust() before proceeding, while _activateTaskProviders() performs onTaskType activation after extension registration. The supplied sample declares a browser entry and onStartupFinished activation, so a missing activation-event declaration cannot be assumed to explain its failure. Inspection establishes existing plumbing, not the sample's exact failure; the first step is to reproduce and inspect readiness, provider discovery, and task-system registration. Preserve desktop and remote-backed execution and avoid indiscriminate startup provider fetching. Related work is tracked at https://github.com/microsoft/vscode/issues/157041, https://github.com/microsoft/vscode/issues/167283, and https://github.com/microsoft/vscode/issues/213825.
- **Open decisions:**
  - Should web task menus be visible whenever the extension host supports CustomExecution, or only when a compatible task definition or configured custom task is available?
  - Does official custom-task support include execution without an open workspace, or only workspace-scoped tasks?
