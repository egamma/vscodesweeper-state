# Issue #341401 — Workbench loads ~2x slower in dev builds since Electron 43 (vscode-file:// handler moved to protocol.handle + net.fetch)

[https://github.com/microsoft/vscode/issues/341401](https://github.com/microsoft/vscode/issues/341401)

## Summary

Keep open: current main mitigates the development-build startup regression by restoring registerFileProtocol, but explicitly retains this issue as the dependency for returning to protocol.handle. The underlying Electron performance work remains in progress.

## Change summary

Restore development-build workbench loading performance after the Electron 43 migration to protocol.handle with nested net.fetch calls.

## Best solution

Complete the Electron local-file fetch optimizations, adopt them in VS Code's runtime, and verify comparable startup performance before returning vscode-file resources to protocol.handle. Retain the deprecated-handler mitigation until that path is ready.

- **Confirmed performance regression:** The issue supplies controlled macOS A/B measurements and Linux CI comparisons. The October 28 maintainer confirmation adds Windows measurements: protocol.handle plus net.fetch takes 7.5–8.1 seconds to restore editors, versus 2.4–2.6 seconds with registerFileProtocol, while loading 4,774 modules.
- **Current source contains an explicit mitigation:** src/vs/platform/protocol/electron-main/protocolMainService.ts:54–55 registers vscode-file through defaultSession.protocol.registerFileProtocol. Its adjacent TODO explicitly says to avoid the protocol.handle nested file fetch until https://github.com/microsoft/vscode/issues/341401 is resolved. handleResourceRequest returns file paths through the callback rather than fetching their contents through net.fetch.
