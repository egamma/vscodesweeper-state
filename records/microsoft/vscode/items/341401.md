# Issue #341401 — Workbench loads ~2x slower in dev builds since Electron 43 (vscode-file:// handler moved to protocol.handle + net.fetch)

[https://github.com/microsoft/vscode/issues/341401](https://github.com/microsoft/vscode/issues/341401)

## Summary

Thanks for the detailed measurements. This is a team-authored, milestoned (1.143.0) perf regression with a collaborator already pointing at two missing upstream Electron commits. It stays open. I did not run the code, so I could not confirm the dev-build slowdown myself.

## Change summary

Dev-build workbench load is about 2x slower since Electron 43 replaced registerFileProtocol with protocol.handle + net.fetch for the vscode-file:// handler.

## Best solution

Either revert vscode-file:// to registerFileProtocol or pick up the Electron 43 backports of the two upstream commits the collaborator named. Then re-measure dev and packaged startup. If protocol.handle stays, consider a faster Response path, since the local A/B showed fs.readFile is quicker than net.fetch.

## Plan brief

- **Likely files:** `src/vs/platform/protocol/electron-main/protocolMainService.ts`
- **Validation:** Run the Launch, Multiroot and Quick Open smoke suites on a dev build and compare the wait for .monaco-workbench against the 1.5–1.9s baseline. Also compare packaged-build startup.
- **Behavior:**

  > Dev-build workbench load time returns to roughly its pre-Electron-43 level, about 1.5–1.9s locally, with no change to vscode-file:// resource resolution or its security restrictions. Acceptance: the A/B smoke measurement shows the regression gone and the Linux Electron smoke tests stop timing out.
- **Trace:**

  > The vscode-file:// handler in protocolMainService.ts moved from registerFileProtocol, where Chromium serves the file, to protocol.handle + net.fetch(file://), where each response goes through the main process. Dev builds load thousands of module files this way. I did not trace the code. The issue's local A/B isolates this handler as the only variable. Do not weaken the path-allowlist or validation logic in the handler. Related: https://github.com/microsoft/vscode/issues/341382 and https://github.com/microsoft/vscode/issues/332935.
- **Open decisions:**
  - Revert to the deprecated registerFileProtocol now, or wait for the Electron backports?
  - If protocol.handle stays, is a custom fs-based Response acceptable, given that it is still slower than registerFileProtocol?

## Evidence

- **CI timing:** The wait for .monaco-workbench rose from about 7.2s to 12.2s on slow runners and from about 4.7s to 8.4s on fast runners, across about 110 runs. The issue links a controlled same-base comparison.
- **Local A/B:** Per the issue, protocol.handle + net.fetch takes 3.0–3.2s, registerFileProtocol takes 1.5–1.9s, and protocol.handle with fs.readFile takes 2.0–2.2s.
