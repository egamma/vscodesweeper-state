# Issue #337966 — macOS 27: "Path does not exist" when opening folders with Portuguese (pt-BR) accented names on SMB share via File > Open Folder

[https://github.com/microsoft/vscode/issues/337966](https://github.com/microsoft/vscode/issues/337966)

## Summary

Fresh, well-diagnosed report; the source confirms the reporter's theory — dialogMainService.ts forcibly converts every path from the native Open dialog to NFC on macOS, which breaks on SMB shares that genuinely store folder names as raw NFD bytes (unlike local HFS+/APFS, which auto-normalizes). Keeping open pending a maintainer decision on how to safely relax the blanket normalization.

## Change summary

Opening a folder with accented Portuguese characters via File > Open Folder fails with 'Path does not exist' when the folder lives on an SMB share that stores names in NFD form, because VS Code force-converts the dialog's returned path to NFC before checking it on disk.

## Best solution

In dialogMainService.ts's normalizePath, don't unconditionally force NFC — first check whether the NFC-converted path exists, and fall back to the original (possibly NFD) path when it doesn't, so both native HFS+/APFS decomposition and literal-NFD network shares (SMB/Samba) resolve correctly.

  > Selecting a folder through File > Open Folder on macOS should succeed even when the underlying filesystem (e.g., an SMB/Samba share) stores the folder name in NFD form rather than NFC. If the NFC-normalized path doesn't exist but the original path does, VS Code should use the original path instead of failing with 'Path does not exist'. Behavior for local HFS+/APFS volumes (where NFC conversion is needed) must remain unchanged.
- **Trace:**

  > src/vs/platform/dialogs/electron-main/dialogMainService.ts, `normalizePath`/`normalizePaths` (used by `showOpenDialog`/`showSaveDialog`) unconditionally rewrites every returned macOS path via `normalizeNFC` from src/vs/base/common/normalization.ts before it's handed off (e.g. to windowsMainService.ts's path resolution, which later reports 'Path does not exist' at line ~920 when the rewritten path can't be found). The fix must not remove NFC normalization outright — it exists for a reason on native Apple filesystems — so the boundary is to make the conversion conditional on the NFC path actually resolving, falling back to the original path otherwise. https://github.com/microsoft/vscode/issues/337966 has the full repro and byte-level diagnosis.
- **Open decisions:**
  - Should the existence check happen inside `normalizePath` itself (making it async and fs-aware), or should the caller retain the original path as a fallback candidate for a later resolution step?
  - Does this fallback belong only in `showOpenDialog`/`showSaveDialog` normalization, or should the same existence-aware NFC/NFD fallback also apply to CLI-provided paths and File > Open Recent for consistency?
