# Issue #333175 — Remote agent host keeps running an old build after the server updates

[https://github.com/microsoft/vscode/issues/333175](https://github.com/microsoft/vscode/issues/333175)

## Summary

Keep open: current source still permits a newer remote server to reuse an arbitrarily old, reachable agent-host supervisor, and the remote client's restart method remains empty. This team-authored issue is the older report; the later stale-host report does not qualify as its duplicate canonical.

## Change summary

Prevent remote windows from silently using stale agent-host builds and provide recovery without manually killing remote processes.

## Best solution

Make remote agent-host selection and lifecycle management prevent stale-build reuse while preserving sessions belonging to other connected clients, with an actionable recovery path in the remote window. Retain this issue for that work and distinguish the current-build catalog-enumeration failure reported in the comments from the stale-build defect.

Validate the chosen recovery contract in editorRemoteAgentHostServiceClient.test.ts. End with a two-client Remote-SSH check across a server update: the new window must not silently attach to an unsuitable old host, recovery must not require a shell kill, and existing sessions must behave according to the agreed lifecycle contract. These are proposed checks; none were executed in the read-only checkout.
- **Behavior:**

  > After a remote server update, opening a remote window must not silently reuse an unsuitable older agent host solely because its endpoint remains reachable. If the remote host cannot serve that window, the user must have an actionable recovery path rather than an unexplained empty session list or stuck chat requiring a manual process kill. Acceptance must include two connected clients, legacy registry entries, and preservation of existing sessions according to the agreed recovery contract. The same ProviderCatalogUnavailableError on a current-build host is a separate reproduction and must not be treated as proof of stale-build reuse.
- **Trace:**

  > AgentHostEndpointMetadata in cli/src/tunnels/agent_host_registry.rs has no build identity, and select_live_standalone_endpoint selects reachable standalone TCP endpoints without a compatibility check. classify_agent_host in cli/src/tunnels/agent_host.rs turns that selection into Reuse; ensure_supervisor_running in cli/src/commands/agent_host.rs returns it, and apply_to_bridge supplies it to the remote server. The supervisor's run_update_loop waits while its child remains running, although an explicit POST /upgrade endpoint now exists. EditorRemoteAgentHostServiceClient.restartAgentHost remains empty, so that endpoint is not a complete recovery path for this client. The unresolved boundary is how a newer window should coexist with clients still using the older shared host, not whether the stale-reuse path exists. Preserve editor-owned endpoint isolation and do not assume the shared-cache deletion work in https://github.com/microsoft/vscode/issues/338114 or the current-build catalog failure is fixed by changing reuse. https://github.com/microsoft/vscode/issues/334296 supplies a later confirmed stale-host reproduction and recovery evidence.
- **Open decisions:**
  - Must an automatically selected host match the requesting window's exact server commit, or may a different build serve it under an explicitly defined compatibility contract?
  - When other clients still use an unsuitable older shared host, should the newer window receive an isolated host, or should recovery offer a coordinated shared-host upgrade with explicit handling of existing sessions?
