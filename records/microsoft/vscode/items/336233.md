# Issue #336233 — Extension host utility process crashes intermittently (exit code 134) when launching Extension Development Host via F5 (js-debug auto-attach)

[https://github.com/microsoft/vscode/issues/336233](https://github.com/microsoft/vscode/issues/336233)

## Summary

Two independent reporters describe a matching, distinctive crash signature (utility-process extension host aborting with exit code 134 within ~1-1.2s of start, only via F5/js-debug auto-attach injection, never via Ctrl+F5 or manual CLI attach) across separate VS Code versions — credible enough to treat as reproduced, but the root cause (core utility-process handling vs. the debug-arg injection path) still needs to be pinned down by someone who can reproduce natively on Windows.

## Change summary

The extension host utility process intermittently crashes with exit code 134 right after 'Loading development extension' specifically when launched via F5 (js-debug auto-attach), never via Ctrl+F5 or manual CLI + attach.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/electron-browser/localProcessExtensionHost.ts`, `src/vs/platform/utilityProcess/electron-main/utilityProcess.ts`
- **Validation:** Reproduce on Windows with a debugger or minidump attached to the crashing utility process to identify the actual abort site, then add a regression test/manual repeated-F5 check that no longer crashes.
- **Behavior:**

  > Launching the Extension Development Host via F5 should not crash the extension host utility process. Currently, on some Windows machines, F5 (which routes through js-debug auto-attach and injects `--inspect`/`--inspect-brk` exec args) intermittently but frequently crashes the utility process with exit code 134 within ~1 second, before any extension code runs and before exthost.log is even created. Ctrl+F5 and a manual CLI launch + attach on port 9333 are stable on the same machine/workspace. Acceptance: repeated F5 launches on an affected machine no longer produce UtilityProcess exit code 134 crashes at the 'Loading development extension' stage.
- **Trace:**

  > src/vs/workbench/services/extensions/electron-browser/localProcessExtensionHost.ts builds execArgv for the extension host process, injecting `--inspect=`/`--inspect-brk=` plus `--dns-result-order=ipv4first`/`--experimental-network-inspection` when a debug port is set (the F5/js-debug path) — this differs from the stable CLI+manual-attach path the reporters use as a workaround, matching the reported crash-only-on-F5 pattern. No crash dump exists (Crashpad stays empty) and the crashed window has no exthost.log folder at all, meaning the abort happens before the extension host process's own bootstrap logs anything — this points at very early utility-process startup, possibly in Electron/Node's own inspector bootstrap under these injected flags, not core VS Code logic. Where the uncertainty starts: whether the abort is in VS Code's utility process spawn/init code, in Node's inspector agent handling the injected flags, or in js-debug's own auto-attach negotiation — this needs an actual native reproduction (debugger or minidump) on Windows to settle, which is outside what source-reading alone can confirm.
- **Open decisions:**
  - Is the crash caused by VS Code's own utility-process bootstrap (localProcessExtensionHost.ts / utilityProcess.ts) or by js-debug's auto-attach injection of debug exec args — i.e. does the fix belong in this repo or in microsoft/vscode-js-debug?
  - Can a maintainer capture a native crash dump or attach a debugger to the utility process at the moment of the exit-134 abort to identify the actual failing code path, since Crashpad is not producing a report here?
