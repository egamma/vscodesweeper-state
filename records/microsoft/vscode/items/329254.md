# Issue #329254 — Add option to sort extensions view with available updates first

[https://github.com/microsoft/vscode/issues/329254](https://github.com/microsoft/vscode/issues/329254)

## Summary

Keep open: current main prioritizes available updates only in the implicit default ordering and offers no selectable updates-first sort. The Backlog milestone records this as accepted work, so the older out-of-scope precedent does not justify a decline close.

## Change summary

Add an Extensions view sort option that keeps extensions with available updates ahead of current extensions while users install updates manually.

## Best solution

Provide an explicit updates-first ordering for installed extensions that reorders the list as update availability changes, while preserving the established handling of incompatible, deprecated, and restart-required extensions.

- **Reason:** This extends an existing Extensions view sorting interaction and improves manual extension-update management without adding a separate UI surface.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/extensions/browser/extensionsViews.ts`, `src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts`, `src/vs/workbench/contrib/extensions/common/extensionQuery.ts`, `src/vs/workbench/contrib/extensions/test/electron-browser/extensionsViews.test.ts`
- **Validation:** Extend the `ExtensionsViews Tests` suite with mixed outdated/current extensions and run `scripts/test.sh --grep "ExtensionsViews Tests"`; verify the selected ordering remains updates-first as an extension's outdated state changes and that existing sort modes retain their behavior.
- **Behavior:**

  > The Extensions view offers a selectable ordering that keeps installed extensions with available updates ahead of current extensions. After a manual update completes, that extension leaves the updates group without disrupting the selected ordering. Existing Name, Updated Date, Published Date, Rating, and Install Count sorts remain unchanged, and `@outdated` continues to act as a filter.
- **Trace:**

  > Installed-extension ordering runs through `ExtensionsListView.filterInstalledExtensions` in src/vs/workbench/contrib/extensions/browser/extensionsViews.ts. With no explicit sort it partitions results into incompatible, deprecated, outdated, action-required, and ordinary groups; with `options.sortBy` set it instead calls `sortExtensions`, whose available local mode is UpdateDate. The Sort By actions are registered in src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts, while query parsing and suggestions live in src/vs/workbench/contrib/extensions/common/extensionQuery.ts. The boundary is installed/local extension ordering: do not change marketplace ranking or turn the existing `@outdated` filter into a sort. The older same-symptom issue https://github.com/microsoft/vscode/issues/34471 is closed and cannot absorb this issue.
- **Open decisions:**
  - When updates-first is selected, should incompatible and deprecated extensions retain their current precedence over extensions with available updates, or should every outdated extension appear first regardless of other status?
  - Should the selectable ordering apply only to the Installed view, or also to other local-extension searches that return both outdated and current extensions?

## Evidence

- **current source:** src/vs/workbench/contrib/extensions/browser/extensionsViews.ts:455-535 groups outdated extensions near the front only when `options.sortBy` is undefined; selecting any explicit sort bypasses that grouping.
- **missing capability:** src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts:1286-1320 registers Install Count, Rating, Name, Published Date, and Updated Date sorts, but no sort based on the `outdated`/available-update state. The existing `@outdated` query filters out current extensions rather than sorting the full installed list.
