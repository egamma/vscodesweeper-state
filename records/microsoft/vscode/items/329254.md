# Issue #329254 — Add option to sort extensions view with available updates first

[https://github.com/microsoft/vscode/issues/329254](https://github.com/microsoft/vscode/issues/329254)

## Summary

Reasonable, narrow gap: the installed extensions list only sorts outdated extensions first via an internal default heuristic (used only when no explicit @sort is set), not as a selectable, persistent sort option — routing to the extensions-view area rather than closing.

## Change summary

Add an explicit, selectable sort option that keeps extensions with available updates at the top of the Extensions view list, even after other sorts or after manually updating a few extensions.

## Best solution

Add an 'updates available' sort mode alongside the existing @sort: options (name, installs, rating, publishedDate, updateDate) in src/vs/workbench/contrib/extensions/browser/extensionsViews.ts, so it can be explicitly chosen and persists independent of the default installed-list heuristic.

## Evidence

- **existing default heuristic:** In filterInstalledExtensions (src/vs/workbench/contrib/extensions/browser/extensionsViews.ts, ~lines 471-533), when options.sortBy is undefined the installed list already buckets incompatible/deprecated/outdated/actionRequired/noActionRequired and sorts outdated before noActionRequired — this is likely what the reporter sees 'by default'.
- **no explicit sort-by-updates option:** The @sort: switch (lines 243-249) only supports 'installs', 'rating', 'name', 'publishedDate', 'updateDate' — none of these represent 'has update available first', and setting any of them (options.sortBy !== undefined) bypasses the outdated-first bucketing entirely (line 471-473).
- **separate outdated-only view exists:** There is already an @outdated / @updates query and an 'Available Updates' view (OutdatedExtensionsView, filterOutdatedExtensions) but that filters to only outdated extensions rather than sorting the full installed list with updates first.
