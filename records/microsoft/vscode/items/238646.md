# Issue #238646 — New file using keyboard only in file explorer not working on macbook

[https://github.com/microsoft/vscode/issues/238646](https://github.com/microsoft/vscode/issues/238646)

## Summary

Keep open as the canonical report: the macOS Explorer context menu still allows the underlying Enter-to-Rename keybinding to override the selected menu action. A later report reproduced the same symptom on a current main build, and multiple matching reports were closed as duplicates of this issue.

## Change summary

Using Shift+F10 and Enter to choose New File or New Folder in the macOS Explorer context menu invokes Rename on the selected folder instead.

## Best solution

When a native context menu is active, keyboard input used to navigate and activate that menu must not dispatch keybindings against the underlying Explorer; Enter should run the highlighted menu action while preserving Enter-to-Rename when no menu is open.

## Plan brief

- **Likely files:** `src/vs/workbench/services/contextmenu/electron-browser/contextmenuService.ts`, `src/vs/workbench/services/keybinding/browser/keybindingService.ts`, `src/vs/workbench/contrib/files/browser/fileActions.contribution.ts`, `src/vs/workbench/services/contextmenu/test/electron-browser/contextmenuService.test.ts`
- **Validation:** On macOS, focus an Explorer folder, open its context menu with Shift+F10, select New File and New Folder with arrow keys, and press Enter; each highlighted action must run without starting Rename. Then dismiss the menu and verify Enter still starts Rename on the focused Explorer item.
- **Behavior:**

  > In the macOS Explorer, Enter activates the highlighted native context-menu item while that menu is open. It must not invoke the underlying Explorer Rename command, including when the menu was opened with Shift+F10 and New File or New Folder is selected. Outside a context menu, the existing macOS Enter-to-Rename behavior remains unchanged. The same menu behavior should hold whether the menu was opened from the keyboard or mouse.
- **Trace:**

  > The Explorer registers `renameFile` on macOS Enter under `FilesExplorerFocusCondition` in src/vs/workbench/contrib/files/browser/fileActions.contribution.ts. NativeContextMenuService in src/vs/workbench/services/contextmenu/electron-browser/contextmenuService.ts emits menu lifecycle events but leaves the underlying Explorer context eligible, while src/vs/workbench/services/keybinding/browser/keybindingService.ts dispatches window keydown events through that context. The collision is confirmed by https://github.com/microsoft/vscode/issues/242513 and by a later current-main reproduction at https://github.com/microsoft/vscode/issues/284949; https://github.com/microsoft/vscode/issues/239982 was consolidated into this issue. Preserve Enter-to-Rename when no menu is active and avoid changing mouse context-menu selection or unrelated Explorer commands. The remaining uncertainty is the safest shared boundary for suppressing underlying keybindings during a native popup and how to exercise that boundary in automation.

- **dispatch path:** src/vs/workbench/services/keybinding/browser/keybindingService.ts dispatches window keydown events through the active context, so the underlying Explorer remains eligible to receive `renameFile` while the native menu is active.
