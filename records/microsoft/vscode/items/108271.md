# Issue #108271 — Add an explorer/title menu contribution point

[https://github.com/microsoft/vscode/issues/108271](https://github.com/microsoft/vscode/issues/108271)

## Summary

Keep open: this accepted On Deck request has 60 upvotes and multiple concrete extension use cases, while maintainers have endorsed an Explorer-specific contribution with overflow handling. Current `view/title` infrastructure provides much of the mechanism, but the supported Explorer contract and action-placement policy remain unsettled.

## Change summary

Allow extensions to contribute actions specifically to the File Explorer title, with excess actions placed in an overflow menu.

## Best solution

Establish a supported Explorer-scoped title-action contract using the existing view-title menu infrastructure, defaulting contributed actions to overflow so the four built-in navigation icons remain uncluttered. A maintainer should decide whether that contract is a dedicated `explorer/title` contribution or the generic `view/title` contribution with a documented stable Explorer view identifier.

## Plan brief

- **Likely files:** `src/vs/workbench/services/actions/common/menusExtensionPoint.ts`, `src/vs/workbench/browser/parts/views/viewPane.ts`, `src/vs/workbench/browser/parts/views/viewMenuActions.ts`, `src/vs/workbench/contrib/files/common/files.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`
- **Validation:** In an Extension Development Host, contribute one Explorer title action intended for overflow and one control action targeting another view; verify the Explorer action appears only in the Explorer's More Actions menu, invokes its command, and leaves the four built-in navigation icons unchanged.
- **Behavior:**

  > Extensions can contribute an action specifically to the File Explorer title without the action appearing in unrelated views. Contributed actions follow an explicit placement policy that preserves the Explorer's existing primary-action cap and provides discoverable overflow access. Built-in Explorer actions and title actions in other views remain unchanged. Acceptance includes an extension-host scenario proving Explorer-only visibility and command invocation.
- **Trace:**

  > The generic contribution is registered as `view/title` in src/vs/workbench/services/actions/common/menusExtensionPoint.ts. ViewPane in src/vs/workbench/browser/parts/views/viewPane.ts creates a scoped `view` context key from its view ID, while the File Explorer ID is `workbench.explorer.fileView` in src/vs/workbench/contrib/files/common/files.ts. ViewMenuActions in src/vs/workbench/browser/parts/views/viewMenuActions.ts classifies `navigation` as primary and other groups as secondary, so the existing machinery already supports scoped actions and overflow in principle. The uncertainty starts at the public contract: whether extensions should use a documented stable Explorer ID with `view/title` or receive a dedicated `explorer/title` menu, and which contributed groups may occupy primary icon slots. Keep changes bounded to title-menu contribution and placement; do not alter Explorer item context menus, built-in action behavior, or other views' contribution semantics.
- **Open decisions:**
  - Should the supported public contract be a dedicated `explorer/title` contribution point, or `view/title` with a documented stable File Explorer view identifier?
  - Must all extension-contributed Explorer title actions go to the overflow menu, or may extensions opt into primary icon placement under a defined cap?
