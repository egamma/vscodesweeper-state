# Issue #335297 — Copilot permissions cannot be revoked while running

[https://github.com/microsoft/vscode/issues/335297](https://github.com/microsoft/vscode/issues/335297)

## Summary

The reporter confirmed the defect on 1.137.0, and current source still snapshots the permission level when a request starts, so downgrading the picker cannot revoke Autopilot behavior for that running request. Keep this open for a live permission-update design spanning the chat UI and participant execution path.

## Change summary

Changing a running Copilot request from Autopilot to Default Permissions should immediately stop autonomous question replies and elevated behavior without requiring the turn to be cancelled.

## Best solution

Make permission downgrades authoritative for subsequent actions in the active turn, including question handling, tool approval, retries, and Autopilot continuation. The implementation should propagate a session-scoped live permission update across the workbench-to-extension-host boundary rather than only changing the next request's input state.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts`, `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts`, `src/vs/workbench/api/common/extHostTypeConverters.ts`, `src/vscode-dts/vscode.proposed.chatParticipantPrivate.d.ts`, `src/vs/workbench/contrib/chat/common/tools/builtinTools/askQuestionsTool.ts`, `extensions/copilot/src/extension/intents/node/toolCallingLoop.ts`
- **Validation:** Add an integration or participant test that starts an Autopilot request, changes the active session to Default Permissions before an ask-questions invocation, and verifies that the question waits for user input and later tool calls no longer receive Autopilot approval; existing uninterrupted-Autopilot tests must continue to auto-reply.
- **Behavior:**

  > A user can downgrade an in-progress Copilot turn from Autopilot to Default Permissions without cancelling it. Actions requested after the downgrade must follow Default Permissions: questions wait for the user, tools request approval where applicable, and the loop no longer applies Autopilot-only retry or continuation behavior. Actions already completed before the downgrade remain unchanged, and uninterrupted Autopilot turns retain their current behavior.
- **Trace:**

  > ChatInputPart.setPermissionLevel in src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts updates session/input state, but ChatServiceImpl has already copied the submitted level into IChatAgentRequest. ExtHostTypeConverters then exposes that captured value as the readonly ChatRequest.permissionLevel contract in src/vscode-dts/vscode.proposed.chatParticipantPrivate.d.ts. AskQuestionsTool reads the request model's captured modeInfo, while the Copilot ToolCallingLoop repeatedly reads its original request.permissionLevel, conclusively reproducing the stale-permission behavior in current source. The plan must cover the live update path for an active request, not merely the picker display or the next turn. Preserve intentional auto-reply behavior when Autopilot has not been revoked, as documented in https://github.com/microsoft/vscode/issues/319841.

## Evidence

- **confirmed reproduction:** The reporter reproduced on VS Code 1.137.0 by switching from Autopilot to Default Permissions during a ten-second command; the later question was still auto-answered as if the user were unavailable.
- **permission picker path:** src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts:1571-1585 updates the current picker value, session option, and input model, but does not update the already-created request.
- **request snapshot:** src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:1778-1846 copies options.modeInfo.permissionLevel into the request sent to the participant, and src/vs/workbench/api/common/extHostTypeConverters.ts:3490-3508 converts that value into an extension-host ChatRequest.
- **immutable participant contract:** src/vscode-dts/vscode.proposed.chatParticipantPrivate.d.ts:118-122 exposes permissionLevel as readonly and describes it as applying to the request, leaving no live downgrade channel for a running participant invocation.
- **observable failing path:** src/vs/workbench/contrib/chat/common/tools/builtinTools/askQuestionsTool.ts:195-215 retrieves the active request and auto-replies whenever its captured modeInfo.permissionLevel is Autopilot, even after the picker has changed.
- **extension loop snapshot:** extensions/copilot/src/extension/intents/node/toolCallingLoop.ts repeatedly reads options.request.permissionLevel for Autopilot retries, continuation, and yielding, so the broader running loop also retains the original value.
- **related behavior:** https://github.com/microsoft/vscode/issues/319841 documents that question auto-reply is intentional while Autopilot is active; it does not address this report's distinct failure to observe an explicit mid-turn downgrade.
- **canonical check:** https://github.com/microsoft/vscode/issues/336425 is newer and concerns workspace-folder trust rather than revoking a running turn's permission level, so it is not a duplicate canonical under the re-review rule.
