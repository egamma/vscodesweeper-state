## Plan brief

- **Likely files:** `src/vs/workbench/contrib/terminal/browser/terminalInstance.ts`, `src/vs/workbench/contrib/terminal/browser/xterm/xtermTerminal.ts`
- **Validation:** On Windows with a Linux shell through WSL or SSH, enable mouse reporting with echo -e "\e[?1003;1006h" and compare ordinary movement, left-button dragging, and release before and after Move into New Window. Drag and release sequences must remain available in both windows and after docking back. Also verify tmux mouse-enabled selection or pane resizing in an auxiliary window.
- **Behavior:**

  > A terminal with mouse tracking enabled loses drag and release reports when moved from the editor area into an auxiliary window, although ordinary motion reports continue. Moving the terminal must preserve the same mouse-reporting behavior as the main window so mouse-driven TUI interactions remain usable. Acceptance checks compare motion, dragging, and release before moving, after moving, and after docking back, and include a tmux mouse interaction.
- **Trace:**

  > TerminalInstance.detachFromElement and attachToElement in src/vs/workbench/contrib/terminal/browser/terminalInstance.ts reparent an existing terminal wrapper; attachToElement calls raw.open again to pick up window changes. XtermTerminal constructs the underlying terminal with the main document as documentOverride in src/vs/workbench/contrib/terminal/browser/xterm/xtermTerminal.ts. The investigation must establish how the bundled xterm implementation updates document-level mouse listeners during that reattachment; its source was not available locally, so the root cause is not proven. Preserve terminal contents, process identity, main-window mouse behavior, and the existing DOM-creation convention. Independent reports at https://github.com/microsoft/vscode/issues/281851 and https://github.com/microsoft/vscode/issues/316246 support this issue remaining the canonical report. First reproduce on current main, then determine whether the defect belongs in VS Code integration or xterm.
