# Issue #290763 — uvx not found when trying to start MCP server although available in the terminal

[https://github.com/microsoft/vscode/issues/290763](https://github.com/microsoft/vscode/issues/290763)

## Summary

Keep open: two team members confirmed that generated MCP configurations cannot find `uvx` on WSL and macOS, and current main still launches stdio servers with the extension host's process environment rather than an explicitly resolved user-shell environment.

## Change summary

MCP servers installed from PyPI manifests fail to start when `uvx` is available in the integrated terminal but absent from the extension host process PATH.

## Best solution

Define and consistently implement the environment contract for MCP stdio processes so commands installed on the user's normal shell PATH can be launched across local macOS/Linux and remote WSL contexts, with regression coverage for the manifest-generated `uvx` configuration.

## Plan brief

- **Likely files:** `src/vs/workbench/api/node/extHostMcpNode.ts`, `src/vs/workbench/api/test/common/extHostMcp.test.ts`, `src/vs/platform/shell/node/shellEnv.ts`
- **Validation:** Repeat the PyPI portion of https://github.com/microsoft/vscode/issues/290552 on WSL and macOS with `uvx` installed only on the normal user-shell PATH; the generated server must start without an absolute command path or `/usr/bin` symlink.
- **Behavior:**

  > An MCP server configuration generated from a PyPI package manifest must start when `uvx` is available through the user's normal shell environment, including WSL and macOS launches from the VS Code UI. The MCP process should not require an absolute executable path or a system-directory symlink merely because the integrated terminal and extension host inherited different PATH values. Explicit `env` entries in the MCP configuration must retain their existing override and PATH-append semantics.
- **Trace:**

  > The test-plan item https://github.com/microsoft/vscode/issues/290552 generates an stdio launch whose command is `uvx`; two team members confirmed lookup failures on WSL and macOS. `MainThreadMcp` in `src/vs/workbench/api/browser/mainThreadMcp.ts` forwards the resolved launch to the matching extension host. `NodeExtHostMpcService.startNodeMpc` in `src/vs/workbench/api/node/extHostMcpNode.ts` copies `process.env`, applies `envFile` and configured `env`, then passes that environment to `spawn`; it does not call the shell-environment resolver used elsewhere under `src/vs/platform/shell/node/shellEnv.ts`. The boundary is MCP stdio process environment construction: preserve explicit environment configuration, command arguments, working-directory handling, and Windows command-script escaping. The uncertainty starts at which shell-derived environment is authoritative for local and remote extension hosts and when it should be resolved.
- **Open decisions:**
  - Should MCP stdio commands resolve against the user's login-shell environment, the extension host process environment, or a documented merge of both when their PATH values differ?
  - For remote authorities such as WSL, should environment resolution follow the remote user's shell independently of the local client's environment?

## Evidence

- **confirmed reproduction:** The author reproduced the failure under WSL and https://github.com/microsoft/vscode/issues/290763#issuecomment-3815087324 reports the same observable `uvx` lookup failure on macOS.
- **environment diagnostic:** https://github.com/microsoft/vscode/issues/290763#issuecomment-4870177298 demonstrates that an MCP-launched `bash -c 'echo $PATH'` receives a PATH different from the terminal and works around the failure only by placing `uvx` in `/usr/bin`.
- **current source:** On current main, `NodeExtHostMpcService.startNodeMpc` in `src/vs/workbench/api/node/extHostMcpNode.ts` initializes the child environment with `{ ...process.env }` and passes it directly to `spawn`; no user-shell environment is resolved on this path.
- **expected test behavior:** https://github.com/microsoft/vscode/issues/290552 explicitly requires the PyPI manifest flow to generate an `uvx --index-url ...` configuration and successfully run the server.
