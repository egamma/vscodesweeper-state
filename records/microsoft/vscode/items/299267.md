# Issue #299267 — Allow filtering Git worktree list per window to show only the active worktree

[https://github.com/microsoft/vscode/issues/299267](https://github.com/microsoft/vscode/issues/299267)

## Summary

Keep open: current settings do not provide an automatic, window-specific active-worktree filter. Older highlighting requests cover only the alternative presentation improvement, while the closely related opt-out request is newer and cannot be the canonical for this re-reviewed item.

## Change summary

Allow each worktree window to limit its Source Control Repositories list to the current worktree without maintaining exclusions for every sibling.

## Best solution

Provide a window-scoped way to focus the Git repositories/worktrees surface on the workspace's own worktree, while preserving deliberate access to other worktrees. Decide whether this controls displayed entries only or also automatic opening of sibling repositories; coordinate with the related opt-out request without expanding this issue into branch-checkout behavior.

- **Trace:**

  > GitArtifactProvider in extensions/git/src/artifactProvider.ts registers a worktrees artifact group and returns every worktree detail, sorting the main worktree first without matching the workspace's current worktree. SCMRepositoriesViewPane in src/vs/workbench/contrib/scm/browser/scmRepositoriesViewPane.ts renders the provider's artifact groups and entries. The uncertainty is whether the requested focus should hide entries only or also prevent sibling repositories from opening and contributing changes. Related https://github.com/microsoft/vscode/issues/324494 requests a broader opt-out, while https://github.com/microsoft/vscode/issues/286259 and https://github.com/microsoft/vscode/issues/288242 address highlighting only.
- **Open decisions:**
  - Should window-focused behavior only filter the Repositories view, or also prevent sibling worktrees from being opened as SCM repositories and contributing changes?

## Evidence

- **Current worktree listing:** extensions/git/src/artifactProvider.ts: GitArtifactProvider registers the worktrees group and provideArtifacts('worktrees') maps all results of repository.getWorktreeDetails(). Sorting prioritizes the main worktree, not the worktree open in the window; icons distinguish main and Copilot worktrees, not the current workspace worktree.
- **Detection is not presentation filtering:** extensions/git/package.json registers git.detectWorktrees as a resource-scoped boolean, currently defaulting to false. extensions/git/src/model.ts: Model.open/checkForWorktrees uses it to gate automatic scanning of worktree repositories, but GitArtifactProvider does not consult it when listing worktree artifacts.
- **Existing capabilities are partial:** git.ignoredRepositories is window-scoped and Model.shouldRepositoryBeIgnored matches explicitly listed repository paths. It does not automatically select the current worktree or filter the worktree artifact list. scm.repositories.selectionMode controls repository selection, scm.repositories.visible controls view sizing, and scm.repositories.explorer toggles all repository artifacts rather than selectively hiding sibling worktrees.
- **Discussion and workaround:** The reporter confirmed unchanged behavior after updating to 1.110.0; other commenters reported it in 1.118.1 and 1.127.0. Richard Ling described accidentally mixing tasks across worktrees and supplied explicit git.ignoredRepositories exclusions in workspace or folder settings. That workaround requires maintaining sibling paths and does not deliver the automatic filter requested in https://github.com/microsoft/vscode/issues/299267.
