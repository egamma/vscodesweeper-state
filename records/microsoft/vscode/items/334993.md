# Issue #334993 — Parent folder remains selected after navigating into it with ↓, causing accidental deletion

[https://github.com/microsoft/vscode/issues/334993](https://github.com/microsoft/vscode/issues/334993)

## Summary

Traced in source: the base List's keyboard controller only moves focus on plain Down/Up arrow (KeyboardController.onDownArrow in src/vs/base/browser/ui/list/listWidget.ts just calls focusNext + setAnchor, never setSelection — only Enter syncs selection to focus), so the highlighted selection can stay on a folder while focus/shift-extension moves into its children; the Explorer's delete path then collapses the mixed selection to the parent via resources.distinctParents in fileActions.ts, deleting the whole folder. This is a real, traceable interaction gap but is fresh (0 days, no confirmations yet), so it stays open rather than closing.

## Change summary

After clicking a parent folder and pressing Down/Shift+Down to select children, the parent stays part of the underlying selection, so a context-menu Delete on the children also deletes the parent folder.

## Best solution

Decide, in src/vs/base/browser/ui/list/listWidget.ts's KeyboardController (onUpArrow/onDownArrow) and/or the Explorer's tree selection handling, whether plain arrow-key navigation should also update selection (or whether the delete/context-menu path should use focus+visible selection rather than the stale selection trait); this is a cross-cutting List/Tree widget behavior change and needs a maintainer/UX call, not a narrow local fix, given how many consumers rely on current focus/selection semantics.
