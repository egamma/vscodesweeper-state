# Issue #334993 — Parent folder remains selected after navigating into it with ↓, causing accidental deletion

[https://github.com/microsoft/vscode/issues/334993](https://github.com/microsoft/vscode/issues/334993)

## Summary

Traced the exact mechanism in the list/tree widget: focus and selection are separate traits, and plain arrow-key navigation (KeyboardController.onDownArrow/onUpArrow in listWidget.ts) only moves focus, never selection — so a prior single selection on the parent folder persists until an explicit selecting action (click, Enter, Shift+arrow extends from the anchor). Combined with the Explorer's context-menu Delete acting on the selection set rather than the focused row, this creates a real footgun where the parent gets deleted along with intended children. This looks like an unintended interaction of by-design widget semantics rather than a simple isolated bug, so it needs a maintainer product decision on the right fix (e.g., single arrow-key nav should collapse selection to the newly focused row) rather than an automated patch.

## Change summary

In the Explorer, pressing ↓ moves keyboard focus but leaves the previous selection highlight on the original (parent) folder; Shift+↓ then extends the still-active selection to include the parent, so context-menu Delete removes the parent folder unintentionally.

## Best solution

A maintainer should decide whether plain arrow-key navigation in WorkbenchList/Tree (src/vs/base/browser/ui/list/listWidget.ts, KeyboardController.onDownArrow/onUpArrow) should also update selection to the new focus (matching typical OS file-explorer conventions) when no modifier is used, since this affects every List/Tree consumer in the product, not just the file Explorer — this is a cross-cutting UX/accessibility tradeoff, not a narrow patch.
