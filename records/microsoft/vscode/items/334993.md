# Issue #334993 — Parent folder remains selected after navigating into it with ↓, causing accidental deletion

[https://github.com/microsoft/vscode/issues/334993](https://github.com/microsoft/vscode/issues/334993)

## Summary

The reported behavior matches the Explorer's deliberate focus-versus-selection model: arrow keys move keyboard focus, Shift+Arrow extends the existing selection, and a context menu opened on a selected row operates on the whole selection. This is established list behavior rather than a deletion defect.

## Change summary

Make plain arrow-key navigation replace the Explorer selection so a previously selected parent cannot remain in a later multi-selection.

## Best solution

Keep the established distinction between keyboard focus and selection, including context-menu actions applying to the full selection. To target one item, make it the sole selection before invoking Delete; changing this would require a broader product decision about Explorer selection navigation.

  > Thanks for the report. The dashed outline represents keyboard focus, while the solid background represents selection: Down moves focus without replacing the selection, Shift+Down extends that existing selection, and opening a context menu on any selected row intentionally preserves the full selection for commands such as Delete. To act on only one item, first make that item the sole selection; if the context menu is opened on an unselected row, the Explorer also replaces the previous selection with that row.

## Evidence

- **keyboard navigation:** src/vs/workbench/browser/actions/listCommands.ts implements `list.focusDown` through `navigate`/`updateFocus`; selection follows focus only when the widget explicitly enables `selectionNavigation`. The Explorer options in src/vs/workbench/contrib/files/browser/views/explorerView.ts enable multi-selection but do not enable selection navigation, so Down intentionally moves focus without replacing selection.
- **range selection:** src/vs/workbench/browser/actions/listCommands.ts implements `list.expandSelectionDown` by moving focus and then calling `expandMultiSelection`, which adds the newly focused tree item to the existing selection rather than discarding previously selected items.
- **context-menu contract:** ExplorerView.onContextMenu in src/vs/workbench/contrib/files/browser/views/explorerView.ts replaces the selection only when the context-menu target is not already selected. Tests in src/vs/workbench/contrib/files/test/browser/explorerView.test.ts explicitly verify that right-clicking an item belonging to a multi-selection preserves every selected item and exposes all of them as command targets.
- **delete targeting:** The delete handlers in src/vs/workbench/contrib/files/browser/fileActions.ts call `explorerService.getContext(true)`, and Explorer's `getContext` deliberately returns the complete selection when multiple items are selected.
