# Issue #114741 — Add an api for extensions to detect/observe Zen mode

[https://github.com/microsoft/vscode/issues/114741](https://github.com/microsoft/vscode/issues/114741)

## Summary

The extension API still appears to lack a supported way to read or observe Zen Mode state, and comments document several distinct extension scenarios that need it. The Backlog milestone does not block cleanup, but there is neither a verified older canonical nor evidence that the central request is implemented.

## Change summary

Expose Zen Mode state and state changes through the extension API so extensions can adapt their UI and behavior.

## Best solution

Define a small, read-only workbench/window API that exposes the current Zen Mode state and an event for subsequent changes, backed by the existing layout Zen Mode state. The API design should settle event semantics and behavior across extension-host startup and window reload before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadWindow.ts`, `src/vs/workbench/browser/parts/editor/editorCommandsContext.ts`
- **Validation:** Add extension API tests that read the initial Zen Mode state, toggle Zen Mode through the workbench command, and assert exactly one state-change notification for each real transition, including enter and exit.
- **Behavior:**

  > Extensions can determine whether the current VS Code window is in Zen Mode and observe later transitions into and out of it. The initial value is correct when an extension activates while Zen Mode is already active, and notifications occur only when the state changes. Existing Zen Mode commands, restoration behavior, and layout semantics remain unchanged.
- **Trace:**

  > The request concerns a public extension-facing projection of the workbench's existing Zen Mode state, not a new Zen Mode behavior. The relevant boundary spans the public API declaration, extension-host/main-thread protocol, API implementation, and the workbench layout/context state that currently drives Zen Mode; current issue labels identify `api`, `layout`, and `workbench-zen`. Concrete consumers are recorded in https://github.com/gitkraken/vscode-gitlens/issues/1338 and https://github.com/DavidAnson/vscode-markdownlint/issues/93. Keep sidebar policy, editor-width behavior, and the semantics of entering/exiting Zen Mode outside this issue.
- **Open decisions:**
  - Should Zen Mode state be exposed as a dedicated window/workbench property and event, or through a more general public layout-state contract that can later cover other workbench modes?
  - Should the observable state represent only the current window's live Zen Mode state, including a correct initial value after restoration, or expose any persisted restore intent as a separate contract?
