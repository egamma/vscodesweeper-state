# Issue #337525 — Integrated Browser: 'Open in External Browser' fails for local HTML files

[https://github.com/microsoft/vscode/issues/337525](https://github.com/microsoft/vscode/issues/337525)

## Summary

Thanks for the report. A commenter reproduced this on Windows with 1.141.0 and found a likely root cause: the `file:///c%3A/...` URL is passed to the OS with the drive-letter colon percent-encoded, and the page opens once `%3A` is changed back to `:`. The source path is consistent with this, so the issue stays open.

## Change summary

'Open in External Browser' fails when the Integrated Browser is showing a local file: URL.

## Best solution

Make the external-open path for file: URLs hand the OS a form it accepts (`:` instead of `%3A` in the drive letter, or a filesystem path), in the browser action or in the native host's shell open. Add a unit test for the Windows drive-letter case.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/browserView/electron-browser/features/browserNavigationFeatures.ts`, `src/vs/platform/native/electron-main/nativeHostMainService.ts`, `src/vs/editor/browser/services/openerService.ts`
- **Validation:** A unit test that a file URL with a Windows drive letter (`file:///c%3A/x.html`) reaches the external opener as `file:///c:/x.html`. A manual check on Windows that the page opens in the default browser.
- **Behavior:**

  > With a local .html file open in the Integrated Browser, 'Open in External Browser' opens the same file in the system default browser on Windows, macOS and Linux. http(s) behavior and the configured `workbench.externalBrowser` handling must not change.
- **Trace:**

  > The Integrated Browser model URL contains the encoded drive letter (file:///c%3A/...). OpenInExternalBrowserAction passes that string to IOpenerService.open with openExternal: true. The opener preserves the string, and NativeHostMainService.doOpenShellExternal calls shell.openExternal with it. Confirmation so far is the commenter's manual test, not an execution. Boundary: do not change the http(s) path or the opener behavior for other callers. Related: #323733.

## Evidence

- **commenter repro:** https://github.com/microsoft/vscode/issues/337525 comment from imare32: Windows 11, VS Code 1.141.0. The address bar shows file:///c%3A/..., and editing %3A to : in the external browser makes the page open.
- **action code:** OpenInExternalBrowserAction in src/vs/workbench/contrib/browserView/electron-browser/features/browserNavigationFeatures.ts calls openerService.open(url, { openExternal: true }) with the model URL string as-is.
- **opener:** src/vs/editor/browser/services/openerService.ts `_resolveExternalUriOpenTarget` keeps the original string unchanged when the parsed URI round-trips to the same string. A pre-encoded %3A therefore reaches the native host.
- **native host:** src/vs/platform/native/electron-main/nativeHostMainService.ts `openExternal` sends non-http(s) URLs straight to shell.openExternal(url) with no normalization.
