# Issue #226194 — Scroll lists by page

[https://github.com/microsoft/vscode/issues/226194](https://github.com/microsoft/vscode/issues/226194)

## Summary

The paging gap remains on current main: list page commands still navigate by item boundaries, so an item taller than the viewport cannot be paged through while retaining focus. This team-authored Backlog request should remain open; the only implementation attempt was closed without merging.

## Change summary

Make keyboard page navigation scroll within list rows that span multiple viewports instead of immediately moving focus to another row.

## Best solution

Define whether the existing `list.focusPageUp` and `list.focusPageDown` commands should gain within-row scrolling semantics or whether separate page-scroll commands are required, then cover the chosen behavior with tall-item list-widget tests.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/list/listWidget.ts`, `src/vs/base/test/browser/ui/list/listWidget.test.ts`, `src/vs/workbench/browser/actions/listCommands.ts`
- **Validation:** Extend the list-widget unit suite with a row substantially taller than the viewport and run `scripts/test.sh --grep "Page up and down"`; verify repeated page-down/page-up operations scroll by viewport-sized increments while retaining focus until the row boundary, and preserve existing normal-row behavior.
- **Behavior:**

  > When focus is on a list row taller than the visible viewport, keyboard page-down and page-up operations allow the user to traverse that row one viewport at a time instead of skipping its hidden content. Focus remains on that row while more of it remains in the requested direction, then navigation proceeds to the adjacent row at the boundary. Existing paging behavior for ordinary rows, filtered lists, and sticky-scroll padding remains unchanged.
- **Trace:**

  > The commands `list.focusPageDown` and `list.focusPageUp` in src/vs/workbench/browser/actions/listCommands.ts delegate to `List.focusNextPage` and `List.focusPreviousPage` in src/vs/base/browser/ui/list/listWidget.ts. Those methods currently choose an item at the viewport edge; after scrolling they clear focus and recurse, which does not intentionally preserve focus within a multi-page row. The existing tall-item test in src/vs/base/test/browser/ui/list/listWidget.test.ts uses an item exactly one viewport high and therefore does not cover the reported case. Closed, unmerged https://github.com/microsoft/vscode/pull/283973 demonstrates a bounded candidate and test shape, but should not be treated as shipped behavior. Keep filtering, ordinary-row navigation, accessibility focus, and tree sticky-scroll padding semantics outside the behavioral change.
- **Open decisions:**
  - Should paging within an oversized row become the behavior of the existing `list.focusPageUp` and `list.focusPageDown` commands, or should VS Code expose separate page-scroll commands so existing focus-navigation semantics remain unchanged?

## Evidence

- **current source:** On current main, `List.focusNextPage` and `List.focusPreviousPage` in src/vs/base/browser/ui/list/listWidget.ts derive focus from the viewport-edge item and clear/recompute focus after scrolling; they contain no path that deliberately retains focus while paging through a row taller than the viewport.
- **current tests:** src/vs/base/test/browser/ui/list/listWidget.test.ts covers ordinary 20px rows and a row exactly equal to the 200px viewport, but not a row spanning multiple pages.
- **slow alternative:** The existing `list.scrollUp` and `list.scrollDown` commands in src/vs/workbench/browser/actions/listCommands.ts move `scrollTop` by only 10 pixels per invocation, matching the issue's concern that they are unsuitable for paging.
- **unmerged implementation:** https://github.com/microsoft/vscode/pull/283973 implemented within-row paging and added a tall-item test, but it was closed unmerged on 2026-07-04; therefore it is not evidence of implementation on main.
- **canonical status:** https://github.com/microsoft/vscode/issues/231438 was closed explicitly in favor of this issue, confirming that this issue remains the canonical tracker for keyboard paging through long chat responses.
