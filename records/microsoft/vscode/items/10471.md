# Issue #10471 — Lift `setContext` from a command to proper API

[https://github.com/microsoft/vscode/issues/10471](https://github.com/microsoft/vscode/issues/10471)

## Summary

Keep this accepted, well-supported API request open: current main still exposes setting context through a command, without a public context-reading API. The discussion establishes demand, but scoped context semantics and the maintainer's objections to a generic getter require API design before implementation.

## Change summary

Provide a proper extension API for setting context keys and address extensions' need to read or act on relevant context state.

## Best solution

Define a supported context interaction contract with API owners, separating the existing custom-key write capability from scoped built-in-state access. Resolve the scope and performance concerns raised on the rejected getter PR rather than reviving a root-only getter that cannot satisfy the reported editor and focus use cases.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostApiCommands.ts`, `src/vs/platform/contextkey/browser/contextKeyService.ts`
- **Validation:** After choosing the contract, run an extension-host integration scenario with two editors holding different scoped values and focus moving between an editor, its suggest widget, and a view. Verify the documented scope yields the expected state or conditional action, while existing executeCommand('setContext', ...) contributions remain functional.
- **Behavior:**

  > Extensions can currently write custom context keys through a command, but lack a dedicated public context API and cannot generally inspect the scoped state described in the discussion. The intended outcome is a supported contract that addresses agreed extension use cases without presenting a root-container value as the state of the focused editor or widget. Acceptance must distinguish custom-key writes, different editors' scoped values, and focus-dependent widget state. Existing setContext command consumers and when-clause behavior must remain compatible.
- **Trace:**

  > src/vs/workbench/api/common/extHostApiCommands.ts maps setContext to _setContext, whose handler in src/vs/platform/contextkey/browser/contextKeyService.ts creates a context key through the injected service. The same service's getContextKeyValue reads its own container, whereas getContext(target) resolves a target-associated container; this is the central boundary a public read contract must address. No dedicated getter or setter API was found in src/vscode-dts. https://github.com/microsoft/vscode/pull/118722 was closed after maintainers explained that root-only reads miss scoped values and broad asynchronous reads or mirroring introduce costs. https://github.com/microsoft/vscode/issues/249741 and https://github.com/microsoft/vscode/pull/249742 explored conditional execution but are closed, not landed solutions. The uncertainty starts at the public contract, not at whether an internal getter exists; preserve existing context scoping and command compatibility.
- **Open decisions:**
  - Should this API cover only extension-owned custom keys, or also expose built-in and other extensions' context state?
  - For supported scoped use cases, should extensions receive readable state with an explicit scope contract, or submit bindings or conditions for VS Code to evaluate in the relevant context?
  - If readable state is supported, what observable freshness and change-notification guarantees should extensions receive as focus and widget state change?
