# Issue #345857 — Can't "Keep" or "Undo" chat file changes

[https://github.com/microsoft/vscode/issues/345857](https://github.com/microsoft/vscode/issues/345857)

## Summary

Keep open: current source rejects Keep and Undo when sibling forks have distinct edit histories for the same file, including previously accepted changes. The report provides a concrete two-fork sequence, and neither inspected related report establishes a duplicate.

## Change summary

Keep and Undo become unusable after two chats forked from the same parent sequentially modify the same file.

## Best solution

Make sequential fork edits reviewable without losing earlier accepted changes or overwriting unrelated edits. Reconcile cross-chat edit history and acceptance boundaries in the Agent Host changeset operations rather than removing their conflict safeguards.

- **Behavior:**

  > After accepting a file change in one fork, a second fork from the original parent can change that file and successfully Keep or Undo its pending change. Keep leaves the edited content intact and clears the pending change; Undo preserves the previously accepted content. Both actions must preserve unrelated edits and must not leave the parent and sibling chats permanently stuck with an unresolvable pending change.
- **Trace:**

  > AgentHostChangesetService.openTrackedSessionDatabases supplies sibling histories to both operations. AgentHostAcceptChangesOperationHandler deduplicates inherited rows but rejects distinct sibling rows, including history retained after acceptance; AgentHostDiscardChangesOperationHandler rejects other-chat records before calculating unaccepted edits. Existing acceptance tests encode both inherited-row success and multi-chat rejection, confirming that removing the checks alone would violate established safeguards. The unresolved technical boundary is how to reconcile ordering and acceptance across separate databases while preserving external-edit conflicts, nonce checks, and turn coordination. Assess the overlapping history work in https://github.com/microsoft/vscode/pull/345537 before choosing an implementation; it references a different report and does not establish a fix here.
