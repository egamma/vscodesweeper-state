# Issue #338439 — Integrated Browser: Unable to attach element as context if session hasn't started

[https://github.com/microsoft/vscode/issues/338439](https://github.com/microsoft/vscode/issues/338439)

## Summary

Team-authored bug (no fix commit exists yet, so no close is available under the team-authored close rules), and the source traces to a real, confirmed gap: the Agents Window's new-session composer is not registered with `IChatWidgetService`, so the browser's 'add element to chat' feature — which only resolves a target via `revealWidget()`/`lastFocusedWidget` — silently finds nothing before a session starts.

## Change summary

Adding a browser element as chat context does nothing when the Agents Window session hasn't sent its first message yet.

## Best solution

Bridge the browser element-attachment path to the new-session composer's own attachment mechanism (it already supports `addAttachments` for `initialAttachments`) without violating the workbench/sessions layering boundary — likely via a small target-resolution contract that both a full `IChatWidget` and the pre-session composer can satisfy.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/browserView/electron-browser/features/browserEditorChatFeatures.ts`, `src/vs/sessions/contrib/chat/browser/newChatWidget.ts`, `src/vs/workbench/contrib/chat/browser/chat.ts`
- **Validation:** An integration/unit test driving the browser 'add element to chat' action while an Agents Window session has been created but no message sent, asserting the element attachment ends up in the composer's attachment list (e.g. via NewChatInput.addAttachments) rather than silently vanishing.
- **Trace:**

  > Root cause: NewChatWidget's composer (src/vs/sessions/contrib/chat/browser/newChatWidget.ts) is never registered with IChatWidgetService — confirmed by an explicit in-code comment noting tip-link routing must avoid falling through to `IChatWidgetService.lastFocusedWidget` for exactly this reason. BrowserEditorChatIntegration._revealChatWidgetForAttachment (src/vs/workbench/contrib/browserView/electron-browser/features/browserEditorChatFeatures.ts) only looks up targets through that same registry, so before a session starts there is no widget for it to find and `addContext` is never called — matching the reporter's 'nothing happens'. What must not change: the existing behavior once a session/widget exists (that path already works and is unaffected). Where uncertainty starts: whether the fix routes into NewChatInput.addAttachments directly (already used for initialAttachments) via some new cross-layer contract, or whether the browser feature should force-start a session first — a layering-safe design choice a maintainer should make.
- **Open decisions:**
  - Should attaching an element before a session starts feed the new-session composer's existing `addAttachments`/initialAttachments mechanism, or should the action implicitly start the session first?
  - What is the layering-safe contract for exposing an 'attachment target' that both a full IChatWidget and the sessions-only pre-session composer can satisfy, given sessions may depend on workbench but not vice versa?

## Evidence

- **explicit design gap:** src/vs/sessions/contrib/chat/browser/newChatWidget.ts (~lines 386-390) has a comment stating tip-link routing is scoped locally 'so they do not fall through to IChatWidgetService.lastFocusedWidget (which this composer is not registered with)' — the new-session composer is confirmed absent from the widget registry the browser feature relies on.
- **attachment resolution path:** src/vs/workbench/contrib/browserView/electron-browser/features/browserEditorChatFeatures.ts `_revealChatWidgetForAttachment` (around line 417) resolves a target purely via `chatWidgetService.revealWidget()` / `.lastFocusedWidget`, both of which only see registered `IChatWidget` instances.
- **existing but disconnected mechanism:** NewChatWidget already supports seeding attachments before a session exists via `this._newChatInput.addAttachments(...this.options.initialAttachments)` (line ~376), but nothing wires the browser element-attach action into it.
