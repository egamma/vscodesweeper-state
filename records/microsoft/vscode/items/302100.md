- **Validation:** In a current development build, create 11 todos, advance and complete them through successive manage_todo_list writes, then send a follow-up and inspect its actual model-request todoList block. It must show all 11 completed without a corrective write. Repeat after scrolling away from and back to older todo tool invocations; compare a direct tool read with the injected block to distinguish storage rollback from prompt reuse.
- **Behavior:**

  > After successful manage_todo_list updates, the next user turn must receive the latest statuses for the same chat session. The reported failure replaces completed or in-progress statuses with an earlier snapshot and causes the agent to repeat finished work. Acceptance requires matching the injected todoList block to the last successful write, including an 11-item list, without requiring the agent to rewrite it. Historical transcript rendering must not revert current task state.
- **Trace:**

  > ManageTodoListTool.handleWriteOperation() writes the session list through ChatTodoListService, and handleReadOperation() retrieves that same list. TodoListContextProvider.getCurrentTodoContext() invokes the read operation; TodoListContextPrompt renders the result inside the user context in agentPrompt.tsx. A separate writer exists in the ChatToolInvocationPart constructor, which copies invocation-specific todo data into the service without checking recency. This can explain stale reads if an older invocation is reconstructed, but the reported follow-up trigger and actual reconstruction order remain unconfirmed. https://github.com/microsoft/vscode/issues/299234 contains a related dual-writer diagnosis but is closed and does not establish resolution of this issue. Preserve session isolation, restored-session todo availability, and non-todo tool rendering; do not automatically mark todos completed merely because the agent says the task is finished.
