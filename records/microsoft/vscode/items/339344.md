# Issue #339344 — Improve keyboard access to Quick Pick item buttons with Tab

[https://github.com/microsoft/vscode/issues/339344](https://github.com/microsoft/vscode/issues/339344)

## Summary

Well-researched, fresh accessibility/UX request documenting a real keyboard-navigation gap in Quick Pick item action buttons, confirmed against current source. No maintainer has weighed in and the proposed interaction model has several open design choices, so this needs a maintainer's input before implementation.

## Change summary

Make Tab explicitly switch between Quick Pick item navigation and item action buttons, instead of relying on default DOM focus traversal, so filtering, selection, and repeated button actions don't break keyboard flow.

## Best solution

A maintainer should decide the exact interaction model (single-button auto-trigger vs. explicit toolbar-focus mode, how multi-button items behave, how Escape/Tab return to item navigation) in quickInputActions.ts/quickInputList.ts, then implement explicit Tab handling instead of relying on ActionBar's default DOM focus traversal.

## Plan brief

- **Likely files:** `src/vs/platform/quickinput/browser/quickInputActions.ts`, `src/vs/platform/quickinput/browser/quickInputList.ts`, `src/vs/base/browser/ui/actionbar/actionbar.ts`
- **Validation:** A quick input test that simulates Tab from a selected item with one action button and asserts the action fires and the next item becomes selected; a second test verifying Tab/Escape returns from the action toolbar to item navigation without dismissing the picker.
- **Behavior:**

  > Pressing Tab while a Quick Pick item is selected should explicitly move between 'item navigation' and 'item action' states rather than relying on default DOM focus order. For an item with exactly one button, Tab should trigger that action directly and preserve a sensible selection afterward (e.g., the next item) so Up/Down navigation continues naturally. For items with multiple buttons, Tab should enter an explicit action-focus state, and there should be a way (e.g., Escape or Shift+Tab) to return to item navigation without dismissing the picker. The input should not lose a usable state during this interaction.
- **Trace:**

  > quickInputList.ts builds a ToolBar for item actions (lines ~390-397) but quickInputActions.ts has no KeyCode.Tab handling to coordinate transitions between the list and the toolbar; actionbar.ts only handles Tab for intra-toolbar focus trapping/navigation (lines ~171, ~206), so the item-to-button transition today is ordinary DOM tab order, matching the report. The boundary: don't change ActionBar's general keyboard handling for toolbars used outside Quick Pick; scope the fix to the Quick Pick list/toolbar interaction. Where uncertainty starts: the exact state machine for multi-button items and how to re-enter list navigation needs a design decision.
- **Open decisions:**
  - Should a single-button item's Tab action auto-trigger immediately, or just move focus to the button (requiring Enter)?
  - For multi-button items, what key returns focus to item navigation — Escape, Shift+Tab, or something else — without closing the Quick Pick?
  - After a button action removes/changes the list (e.g., closing an editor), which item should become selected?
