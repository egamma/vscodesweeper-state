# Issue #237345 — Git - remote name should be considered when checking out a branch

[https://github.com/microsoft/vscode/issues/237345](https://github.com/microsoft/vscode/issues/237345)

## Summary

Still a real gap on main: checking out a remote branch always uses git's DWIM short name, so a second remote with the same branch name collides — keep open; a maintainer needs to decide the naming contract before implementation.

## Change summary

When checking out a remote-tracking branch, allow the local branch name to include the remote name (e.g. via a setting) so identical branch names across multiple remotes don't collide.

## Best solution

Give the git extension an opt-in naming strategy for tracking checkouts — have CheckoutRemoteHeadItem.run pass an explicit local branch name (derived from the remote) to `git checkout -b <name> --track <remote>/<branch>` instead of relying on git's DWIM short name — after a maintainer settles the setting shape and default.

## Plan brief

- **Likely files:** `extensions/git/src/commands.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/git.ts`, `extensions/git/package.json`, `extensions/git/package.nls.json`
- **Validation:** A git extension test (or a manual scripted check against a repo with two remotes exposing the same branch name) asserting that, with the new option enabled, checking out `origin_b/dev` while a local `dev` already exists succeeds and produces a distinctly named local branch tracking `origin_b/dev`.
- **Behavior:**

  > In a repository with several remotes that share branch names, checking out a remote branch from the Git: Checkout to… quick pick must not fail just because a local branch with the short name already exists. The ask is an opt-in way to have the local branch name carry the remote (e.g. `origin_b/dev` for `origin_b/dev`), analogous to how `git.branchPrefix` shapes newly created branch names. Default behavior must stay exactly as today (git's DWIM short name) when the option is off. Acceptance: with the option on, checking out `origin_a/dev` and then `origin_b/dev` both succeed and yield two distinct local branches, each tracking its own remote; with the option off, the existing checkout flow and its reuse of an existing tracking branch are unchanged.
- **Trace:**

  > The remote checkout path is CheckoutRemoteHeadItem.run in extensions/git/src/commands.ts: it first calls repository.findTrackingBranches(this.ref.name) and checks out an existing tracking branch when one exists, otherwise calls repository.checkoutTracking(this.ref.name). Repository.checkoutTracking (extensions/git/src/repository.ts:2322) forwards to Git.checkout (extensions/git/src/git.ts:2046), which assembles `git checkout -q --track <treeish>` and never passes `-b <localName>`, so the local name is entirely git's DWIM choice and the second same-named remote branch collides. git.branchPrefix exists but is wired only into the create-branch and worktree paths (commands.ts:3004 and 3536, repository.ts:1955), so it does not reach this path. Boundary: do not change the default naming, do not alter the findTrackingBranches reuse branch, and do not touch detached checkout, the create-branch command, or the worktree naming logic. Where the uncertainty starts: whether this is a new boolean, a template-style setting, or a reuse/extension of git.branchPrefix semantics, and what happens when even the remote-qualified name is already taken.
- **Open decisions:**
  - What is the setting's shape and name — a boolean such as `git.checkoutPrependRemoteName`, or a template string (e.g. `{remoteName}/{branchName}`) that lets users choose the separator and order?
  - What local branch name is produced by default when the option is on — literally `<remote>/<branch>` (a slash-containing branch name, legal in git but ambiguous with remote refs in some commands), or a sanitized form such as `<remote>-<branch>`?
  - When the remote-qualified local branch already exists, should checkout silently switch to it, or prompt the user as it does for other conflicts?
  - Does the option also apply when a tracking branch already exists under the plain short name (reuse it, or create the qualified one)?

## Evidence

- **gap confirmed on main:** extensions/git/src/commands.ts CheckoutRemoteHeadItem.run calls repository.checkoutTracking(this.ref.name) when no tracking branch exists; Repository.checkoutTracking (extensions/git/src/repository.ts:2322) calls this.repository.checkout(treeish, [], { track: true }), and Git.checkout (extensions/git/src/git.ts:2046) builds `git checkout -q --track <remote>/<branch>` with no `-b <name>`. Git's DWIM then names the local branch after the short branch name only, which fails when that name already exists.
- **no covering setting:** The only branch-naming settings in extensions/git/package.json are git.branchPrefix, git.branchRandomName.*, git.branchValidationRegex, git.branchWhitespaceChar and git.branchSortOrder. git.branchPrefix is used only in the create-branch/worktree paths (commands.ts:3004, 3536; repository.ts:1955) and never in the tracking-checkout path, so nothing today covers the request.
- **maintainer engagement:** A VS Code git maintainer asked the reporter for the equivalent terminal commands (https://github.com/microsoft/vscode/issues/237345#issuecomment-2700644085) and the reporter answered with `git checkout -b {remote}/{branch} {remote}/{branch}`; the issue was then placed in the Backlog milestone, so it is accepted-but-unscheduled rather than declined.
