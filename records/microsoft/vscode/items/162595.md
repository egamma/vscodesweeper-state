# Issue #162595 — Define and apply guidance for icon toggle states

[https://github.com/microsoft/vscode/issues/162595](https://github.com/microsoft/vscode/issues/162595)

## Summary

Keep open: the Search/SCM icon changes addressed only part of the request, and current source still uses different conventions across views. A maintainer explicitly reaffirmed this issue as the home for all-up UX guidance in September 2025.

## Change summary

Define reusable guidance for state-toggle icons and tooltips, then apply it consistently across locking, pinning, visibility, and view-mode controls.

## Best solution

Publish a shared convention grounded in the thread's agreed current-state icons and action-oriented tooltips, with explicit treatment of genuinely different controls such as playback. Audit existing view-mode and locking controls against that guidance rather than treating the Search/SCM changes as completion.

## Evidence

- **Maintainer-defined convention:** https://github.com/microsoft/vscode/issues/162595#issuecomment-1294244112 specifies a flat-list icon for a flat list and a tree icon for a tree, with the tooltip describing the action. Subsequent comments support that direction; later discussion raises discoverability and exceptional-control concerns rather than establishing completion.
- **Partial implementation:** https://github.com/microsoft/vscode/pull/164835 merged as 77381abe3628e4ef3be48bf6e1538eb885fe8711. Its diff only swaps list/tree icon assignments in Search and SCM; it does not define reusable guidance or apply it across locking, pinning, and visibility controls.
- **Existing capability and remaining inconsistency:** Current src/vs/workbench/contrib/search/browser/searchActionsTopBar.ts:158-208 implements search.action.viewAsTree with searchShowAsList while in list mode, and search.action.viewAsList with searchShowAsTree while in tree mode. Conversely, src/vs/workbench/contrib/markers/browser/markers.contribution.ts:162-210 shows Codicon.listTree in table mode and Codicon.listFlat in tree mode: Problems represents the destination while Search represents the current state.
- **Lock metaphor remains relevant:** src/vs/workbench/contrib/output/browser/output.contribution.ts:344-369 still assigns Codicon.lock with the tooltip 'Turn Auto Scrolling Off' and Codicon.unlock when CONTEXT_OUTPUT_SCROLL_LOCK is true. This retains the exact viewport-versus-content locking distinction debated in the thread, which the Search/SCM swap did not settle.
- **Explicit ownership reaffirmed:** https://github.com/microsoft/vscode/issues/162441#issuecomment-3321437777 closes the narrower lock-inconsistency report as a duplicate of this issue, stating that UX guidance will be resolved here. That September 2025 maintainer statement supports retaining this team-authored item and rules out a judgment-based decline.
- **Later report corroborates the gap:** https://github.com/microsoft/vscode/issues/240043 reports Search versus Problems view-toggle inconsistency in VS Code 1.97.0. It is closed and narrower than this issue, so it is evidence of the remaining inconsistency, not a valid duplicate canonical.
