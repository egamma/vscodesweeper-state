# Issue #339391 — Delayed profile-storage notification overwrites a newer pending local value and rolls extension globalState back

[https://github.com/microsoft/vscode/issues/339391](https://github.com/microsoft/vscode/issues/339391)

## Summary

Keep open: current source still allows an older storage notification to overwrite a newer pending or in-flight local value and propagate the rollback to extension globalState. The report supplies a deterministic regression candidate, and the existing workbench-state routing is appropriate.

## Change summary

Prevent delayed notifications of earlier local storage writes from rolling newer extension globalState back.

## Best solution

Preserve newer local state through pending and in-flight writes without suppressing legitimate subsequent external changes. Establish and test reconciliation across storage notifications, acknowledgments, and failures; a pending-map guard alone does not cover the reported scope.

- **Behavior:**

  > A delayed notification of an earlier single-client write must not replace that client's newer local value or resurrect a locally deleted key while the newer operation is pending or in flight. Extension globalState must not consume and subsequently persist the regressed object. Genuine later external updates must continue to propagate after reconciliation. Acceptance includes deterministic pending-insert, pending-delete, in-flight, and failure-ordering checks; conflict-free merging of genuinely concurrent whole-object edits is outside this issue.
- **Trace:**

  > Storage.set updates cache and pendingInserts immediately, but Storage.acceptExternal in src/vs/base/parts/storage/common/storage.ts overwrites that cache without accounting for outstanding local work. Storage.flushPending clears the pending collections before database.updateItems settles, so pending-only protection does not cover the full report. StorageDatabaseChannel in src/vs/platform/storage/electron-main/storageIpc.ts debounces notifications, while the client protocol in src/vs/platform/storage/common/storageIpc.ts carries neither writer identity nor revision. MainThreadStorage forwards the resulting complete extension object, and ExtensionMemento replaces its current value before later whole-object writes. The shared Storage abstraction also serves IndexedDBStorageDatabase in src/vs/workbench/services/storage/browser/storageService.ts, so changes must preserve its legitimate external-update behavior. Source inspection confirms the controlled older-notification failure, but a complete reconciliation design across acknowledgments, failed writes, and subsequent external notifications has not been established. Preserve existing public memento semantics and keep the separate Codex recovery defects outside this change; the source report is https://github.com/microsoft/vscode/issues/339391.
