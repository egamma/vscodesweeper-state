# Issue #339391 — Delayed profile-storage notification overwrites a newer pending local value and rolls extension globalState back

[https://github.com/microsoft/vscode/issues/339391](https://github.com/microsoft/vscode/issues/339391)

## Summary

Thanks for the detailed report. Storage.acceptExternal applies incoming values without regard to pending local inserts or deletes, so a delayed notification can roll back a newer local value. The in-flight case needs a design decision, so this stays open.

## Change summary

A delayed storage-change notification overwrites a newer pending local value in Storage and rolls extension globalState back.

## Best solution

Make Storage (or the storage IPC channel) ignore or reconcile notifications for keys with pending or in-flight local writes, for example with writer identity or a revision. Add the proposed regression test to the Storage suite.

## Plan brief

- **Likely files:** `src/vs/base/parts/storage/common/storage.ts`, `src/vs/platform/storage/electron-main/storageIpc.ts`, `src/vs/base/parts/storage/test/node/storage.integrationTest.ts`
- **Validation:** Add the reporter's 'delayed older echo preserves a pending local value' test to the Storage Library suite; it should fail before the change and pass after.
- **Behavior:**

  > A delayed notification for an older write by the same client must not replace that client's newer pending or in-flight value for the same key. External updates must still apply once local writes have settled. Acceptance: the proposed regression test passes and existing storage tests still pass.
- **Trace:**

  > Storage.acceptExternal in src/vs/base/parts/storage/common/storage.ts updates the cache without checking pendingInserts or pendingDeletes. flushPending clears those maps before the database write resolves, so a pending-key guard leaves the in-flight window open. StorageDatabaseChannel in src/vs/platform/storage/electron-main/storageIpc.ts publishes events without writer identity or revision. Do not change last-writer-wins behavior for genuine concurrent edits from two clients.
- **Open decisions:**
  - Should the fix be client-side suppression while writes are pending or in flight, or should events carry writer identity or a revision?
  - Should deletes that arrive while a local insert is pending be ignored?
