# Issue #339391 — Delayed profile-storage notification overwrites a newer pending local value and rolls extension globalState back

[https://github.com/microsoft/vscode/issues/339391](https://github.com/microsoft/vscode/issues/339391)

## Summary

Well-researched, source-confirmed ordering bug: Storage.acceptExternal overwrites the cache on a delayed external notification without checking pendingInserts/pendingDeletes, and the author explicitly shows a naive pending-map guard still misses the in-flight window — real design work remains before a fix is safe.

## Change summary

A delayed debounced storage-change notification echoing an earlier own write can overwrite a newer pending (or in-flight) local value, silently rolling back an extension's globalState/profile storage.

## Best solution

Design a reconciliation boundary in Storage/StorageDatabaseChannel (e.g. revisioned writes or writer-identity tagging) so a delayed own-echo notification cannot clobber a pending or in-flight local write; the reporter's regression test in storage.integrationTest.ts is a good starting fixture once the approach is chosen.

## Plan brief

- **Likely files:** `src/vs/base/parts/storage/common/storage.ts`, `src/vs/platform/storage/electron-main/storageIpc.ts`, `src/vs/base/parts/storage/test/node/storage.integrationTest.ts`
- **Validation:** The provided/adapted regression test ('delayed older echo preserves a pending local value') in storage.integrationTest.ts should fail before the fix and pass after, plus the in-flight variant the reporter describes but did not include verbatim.
- **Behavior:**

  > A delayed external storage-change notification that is actually an echo of the same client's own earlier write must not overwrite a newer pending or in-flight local write for the same key. After the fix, Storage.get(key) and the extension's observable memento must reflect the latest local write even if an older external notification for that key arrives afterward, while genuine external updates from another client still apply normally once no conflicting local write is pending/in-flight.
- **Trace:**

  > Storage.acceptExternal (src/vs/base/parts/storage/common/storage.ts:164-189) blindly applies any external value to this.cache; pendingInserts/pendingDeletes (declared :128-129) are populated in set()/delete() but never consulted there. flushPending (:363-384) resets those maps to new empty collections before awaiting database.updateItems(), so even a guard like `pendingInserts.has(key) || pendingDeletes.has(key)` (which the reporter tested and confirmed handles the pending case) cannot catch a write that is already in flight to the DB. The debounced republish in StorageDatabaseChannel (src/vs/platform/storage/electron-main/storageIpc.ts, ~line 38-43) sends events back to the originating client with no revision/writer-id, which is why an own-echo is indistinguishable from a real external change today. Boundary: do not weaken genuine cross-client conflict resolution (last-writer-wins for real concurrent edits from two clients is explicitly out of scope per the reporter) — the fix must only suppress a *delayed echo of the same client's own earlier write*, not change multi-client semantics.
- **Open decisions:**
  - Should notifications/writes carry a revision number or writer identity so a client can recognize and discard a delayed echo of its own write, or should in-flight writes be tracked in a separate structure that acceptExternal consults alongside pendingInserts/pendingDeletes?
  - For the in-flight window specifically (after flushPending clears the pending maps but before the DB write resolves), what is the mechanism to prevent acceptExternal from applying a stale echo — e.g. track an in-flight map cleared only on DB-write completion, or defer external updates until any outstanding flush settles?
  - Does the fix belong in the renderer-side Storage class alone, or does it also require changes to StorageDatabaseChannel's debounce/publish logic to avoid echoing to the originating client at all?

## Evidence

- **source confirmation:** src/vs/base/parts/storage/common/storage.ts lines 164-189 (acceptExternal) unconditionally sets this.cache.set(key, value) on any external change, with no check against pendingInserts/pendingDeletes (declared lines 128-129).
- **pending-clear race:** flushPending (lines 363-384) resets pendingInserts/pendingDeletes to empty maps before the async database.updateItems() resolves, creating the in-flight window the reporter calls out as unfixed by a simple guard.
- **debounced IPC echo:** src/vs/platform/storage/electron-main/storageIpc.ts ~line 43 debounces onDidChangeStorage and republishes to all profile subscribers including the originating client, with no writer identity or revision, matching the report's 'external: true' observation.
- **reproduction:** Reporter provides a deterministic test for src/vs/base/parts/storage/test/node/storage.integrationTest.ts and ran the pinned Storage class in a reduced harness, reproducing pending-insert rollback, resurrection during pending delete, and in-flight rollback.
