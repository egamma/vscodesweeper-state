# Issue #306375 — Greater extensibility for hooks beyond shell scripts

[https://github.com/microsoft/vscode/issues/306375](https://github.com/microsoft/vscode/issues/306375)

## Summary

Keep open: current hook configuration and execution still target shell commands, not extension-contributed VS Code commands. This team-authored Backlog request identifies a remaining extensibility gap; no verified canonical or explicitly linked implementation was found.

## Change summary

Allow agent lifecycle hooks to invoke extension-contributed VS Code commands through an API instead of requiring shell scripts.

## Best solution

Define a supported non-shell hook execution contract that integrates extension-contributed commands with hook inputs, results, cancellation, and execution context. Preserve existing shell hooks and settle the public API and configuration semantics with the maintainer before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.chatHooks.d.ts`, `src/vscode-dts/vscode.proposed.chatPromptFiles.d.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/hookSchema.ts`, `extensions/copilot/src/extension/chat/vscode-node/chatHookService.ts`, `extensions/copilot/src/platform/chat/common/hookExecutor.ts`, `extensions/copilot/src/platform/chat/node/hookExecutor.ts`
- **Validation:** The plan should end with an extension-host integration check registering a test extension command and triggering a lifecycle hook: verify invocation, delivery of the agreed hook input, and handling of its result. Include failure/cancellation cases and confirm existing shell hooks remain unchanged.
- **Behavior:**

  > An agent lifecycle hook should be able to invoke a command contributed by an installed VS Code extension without launching a shell script. The supported contract should define the input received by that command and how its completion or failure affects the hook. Acceptance should demonstrate invocation of a test extension command at the configured lifecycle event and preservation of existing shell-hook behavior.
- **Trace:**

  > src/vs/workbench/contrib/chat/common/promptSyntax/hookSchema.ts accepts shell-command hook definitions, and src/vscode-dts/vscode.proposed.chatHooks.d.ts exposes resolved shell commands through ChatRequestHooks. The existing chat.registerHookProvider in src/vscode-dts/vscode.proposed.chatPromptFiles.d.ts supplies configuration resources, not executable callbacks, so it does not satisfy the request. ChatHookService in extensions/copilot/src/extension/chat/vscode-node/chatHookService.ts delegates to IHookExecutor; NodeHookExecutor in extensions/copilot/src/platform/chat/node/hookExecutor.ts spawns a shell process. This establishes the local execution gap, not a finished design for all agent harnesses. Preserve shell configuration compatibility and existing hook flow-control behavior. The uncertainty starts at the public non-shell registration/invocation contract and which session execution environments support it.
- **Open decisions:**
  - Should non-shell hooks reference extension-contributed command IDs in hook configuration, use an extension-registered lifecycle callback API, or support both?
  - What hook inputs and result semantics should extension commands receive and return, including whether they can block an operation?
  - Which session environments should support VS Code command hooks, and what should users observe when the required extension host is unavailable?
