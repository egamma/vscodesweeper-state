# Issue #205857 — Making refactors is stressful because I don't know when they will or will not show the refactor preview

[https://github.com/microsoft/vscode/issues/205857](https://github.com/microsoft/vscode/issues/205857)

## Summary

Keep open: maintainers explicitly accepted improving preview discoverability, and current main still communicates preview availability through a mouse-oriented DOM tooltip rather than a visible or accessible keyboard affordance. The related issue is younger and narrower, so it is not a valid canonical duplicate for this re-reviewed item.

## Change summary

Make it clear before applying a refactor whether preview is available, including when navigating the code-action menu exclusively by keyboard.

## Best solution

Choose and implement a consistent code-action-menu affordance that tells keyboard and screen-reader users both whether the focused action supports preview and which keybinding invokes it, without adding misleading preview hints to command-only actions.

## Plan brief

- **Likely files:** `src/vs/platform/actionWidget/browser/actionList.ts`, `src/vs/platform/actionWidget/test/browser/actionList.test.ts`, `src/vs/editor/contrib/codeAction/browser/codeActionController.ts`, `src/vs/editor/contrib/codeAction/browser/codeActionMenu.ts`
- **Validation:** ./scripts/test.sh --runGlob "**/actionList.test.js", plus a manual keyboard-only check that focusing previewable and non-previewable refactors communicates the correct availability before either action is applied.
- **Behavior:**

  > When a user navigates the Refactor or Code Actions menu with the keyboard, they can determine before applying an action whether preview is available and learn the configured preview keybinding. The same state is conveyed to screen-reader users. Actions that cannot actually produce a preview must not advertise one, and the normal apply flow must remain unchanged.
- **Trace:**

  > Current preview execution is wired through `previewSelectedCodeAction` in src/vs/platform/actionWidget/browser/actionList.ts. `ActionItemRenderer.renderElement` places apply/preview guidance in the row's DOM `title`, but the action-list accessibility provider omits that information. `CodeActionController.showCodeActionList` computes `canPreview` through `onHover`, while grouped entries from `toMenuItems` in src/vs/editor/contrib/codeAction/browser/codeActionMenu.ts do not start with a visible preview marker. Preserve preview execution and code-action resolution semantics; this issue concerns advance discoverability, not adding preview support to command-backed actions tracked by https://github.com/microsoft/vscode/issues/210171.
- **Open decisions:**
  - Should preview availability be shown persistently in each eligible row, only for the focused row, or through another keyboard-triggered hint?
  - Should non-previewable actions explicitly communicate apply-only behavior, or should only previewable actions receive additional guidance?
  - What announcement wording and frequency communicates the preview keybinding to screen-reader users without making routine code-action navigation noisy?
