# Issue #334892 — Agents window renderer OOM during plugin sync: resourceRead Base64 encoding reaches 4 GB heap

[https://github.com/microsoft/vscode/issues/334892](https://github.com/microsoft/vscode/issues/334892)

## Summary

Traced the reported crash path in the current source: the agent-client filesystem provider's `readFile` (src/vs/platform/agentHost/common/agentHostFileSystemProvider.ts:490-500) reads an entire remote file into memory via a single non-chunked `resourceRead`, whose reverse handler (src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:2205-2210) base64-encodes the whole buffer with the per-character-concatenation `encodeBase64` in src/vs/base/common/buffer.ts:431-464 — no size guard or streaming path exists, so a large plugin bundle file (the report's ~228 MB `claude.exe`) can plausibly exhaust the renderer heap. This is a genuine, still-open gap, not a design choice already declined.

## Change summary

Opening the Agents window and syncing an installed plugin whose bundle contains a very large binary can OOM-crash the renderer because the resourceRead path base64-encodes the whole file in one non-chunked in-memory string.

## Best solution

Add a size ceiling (or true streaming/chunked transfer) to the agent-client filesystem provider's readFile/resourceRead path so plugin sync (or any large resourceRead) cannot materialize an unbounded base64 string in the renderer; this is a protocol-level design change, not a one-line guard, so it needs a maintainer decision on approach before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/common/agentHostFileSystemProvider.ts`, `src/vs/platform/agentHost/browser/agentHostProtocolClient.ts`, `src/vs/platform/agentHost/node/agentPluginManager.ts`, `src/vs/base/common/buffer.ts`
- **Validation:** A test in agentHostFileSystemProvider.test.ts (or agentPluginManager.test.ts) asserting a large synthetic file is either transferred without materializing the whole base64 string in one allocation, or is rejected/skipped past an explicit size ceiling — exact shape depends on the chosen approach.
- **Trace:**

  > Root cause traced to: agentHostFileSystemProvider.readFile() → connection.resourceRead(uri, Base64) → reverse handler in agentHostProtocolClient.ts reads the whole file and calls encodeBase64() (buffer.ts) which builds the base64 string via unbounded '+=' concatenation. agentPluginManager._syncPlugin() drives a cross-provider fileService.copy() over this path for plugin bundles, so a very large bundled binary (e.g. the reporter's 228MB claude.exe) is read and base64-encoded in one shot with no size guard. What must NOT change: the resourceRead/resourceWrite wire protocol's semantics for small/typical files, and the existing FileReadWrite capability contract used elsewhere. Where uncertainty starts: whether the fix should add true chunked/streaming transfer (new protocol capability, more invasive) or a pragmatic size ceiling that fails/skips oversized reads (simpler but changes plugin-sync behavior for huge bundles) — that's a product/architecture call for a maintainer.
- **Open decisions:**
  - Should the agent-host resource protocol gain a real streaming/chunked read-write capability, or should oversized resourceRead calls simply fail/be skipped with a size ceiling?
  - If a size ceiling is chosen, should plugin sync skip/exclude large binaries from being synced at all (e.g., only sync source/config files, not native executables in node_modules), or surface an error to the user instead?
  - Should the disablement mismatch also be addressed here — i.e., should chat.plugins.enabledPlugins actually gate sync when the value is user-set rather than policy-only — or is that a separate follow-up issue?

## Evidence

- **non-streaming readFile:** src/vs/platform/agentHost/common/agentHostFileSystemProvider.ts readFile() (around line 490) calls connection.resourceRead(originalUri, ContentEncoding.Base64) and returns the fully decoded buffer — no chunking, and capabilities (line 173-177) declare only FileReadWrite, not a streaming open/read/close capability.
- **reverse handler encodes whole file:** src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:2205-2210 handles 'resourceRead' by reading the entire resource and calling encodeBase64(result.bytes) in one call, sent as a single reply.
- **encodeBase64 is unbounded string concatenation:** src/vs/base/common/buffer.ts encodeBase64() (lines 431-464) builds the output via `output += ...` per 3-byte group with no chunk/array-join strategy, consistent with the reporter's crash-dump analysis and the v8-oom-location pointing at this call site.
- **plugin sync goes through this path:** src/vs/platform/agentHost/node/agentPluginManager.ts:_syncPlugin calls this._fileService.copy(pluginUri, destDir, true) where pluginUri is a toAgentClientUri()-wrapped URI; cross-provider copy falls back to readFile+writeFile since only FileFolderCopy/FileReadWrite capabilities are declared (no native cross-provider copy), so a large bundled binary is read whole through the base64 path traced above.
- **no size guard found:** grep for maxSize/byteLength/size-limit checks in agentPluginManager.ts and agentHostFileSystemProvider.ts returned nothing — there is no existing safeguard against large-file reads.
