# Issue #339223 — Claude-format .claude/settings.json hooks enforced fail-closed on Windows; useClaudeHooks/useHooks/hookFilesLocations disables ignored

[https://github.com/microsoft/vscode/issues/339223](https://github.com/microsoft/vscode/issues/339223)

## Summary

Thorough, well-evidenced report with four independently confirmable root causes in the Local agent harness's Claude-format hook handling on Windows; current main source confirms at least two of them, so this is a real bug that needs routing, not a quick close.

## Change summary

On Windows, a Claude-format `.claude/settings.json` with PreToolUse hooks causes every Copilot agent tool call to be denied, because the hooks can't actually execute (wrong shell, missing env var) yet errors are treated as fail-closed denials, and the documented opt-out settings don't appear to help.

## Best solution

Fix the Local harness's Claude-hook compatibility layer in extensions/copilot/src/platform/chat/node/hookExecutor.ts (bash-syntax commands are never routed through a POSIX-capable shell on Windows) and src/vs/workbench/contrib/chat/common/promptSyntax/hookClaudeCompat.ts (the `matcher` field from Claude's nested hook format is parsed but never used to filter by tool name, so one hook gates every tool call) — this consolidates with the overlapping shell/env diagnosis in https://github.com/microsoft/vscode/issues/337374.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/chat/node/hookExecutor.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/hookClaudeCompat.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts`
- **Validation:** A hookExecutor test on Windows confirming a bash-syntax Claude hook command either executes correctly or is skipped (not fail-closed), plus a hookClaudeCompat test asserting a hook with matcher `Bash` only fires for Bash-type tool calls.
- **Behavior:**

  > On Windows, a workspace Claude-format hook file (`.claude/settings.json`/`settings.local.json`) with bash-syntax PreToolUse commands should either execute those commands correctly (e.g. via a bundled POSIX-capable shell or Git Bash) or be gracefully skipped with a warning — not fail-closed-deny every subsequent tool call. A hook's `matcher` (e.g. `Bash`, `Edit|Write`) should scope which tool calls trigger it, not apply to every tool call.
- **Trace:**

  > Root cause A: extensions/copilot/src/platform/chat/node/hookExecutor.ts `getShellCommand()` never selects a POSIX-capable shell for bash-syntax commands on Windows — it special-cases only `cmd.exe`-as-ComSpec (switches to PowerShell) and otherwise does `shell: true`, so bash operators (`||`, `[ ]`, `case`) are mishandled. Root cause B: src/vs/workbench/contrib/chat/common/promptSyntax/hookClaudeCompat.ts `parseClaudeHooks` -> `extractHookCommandsFromItem` (hookSchema.ts) discards the `matcher` string entirely — no filtering by tool name is applied anywhere in this parse path. Do not change the fail-closed exit-code-2 semantics for Copilot-native hooks (`languageModelToolsService.ts`) — that behavior is intentional for that format; the question is how Claude-format compatibility should degrade. Related: https://github.com/microsoft/vscode/issues/337374, https://github.com/microsoft/vscode/issues/312314. Unexplained: the reporter says `chat.useClaudeHooks: false` had no effect, but PromptsConfig.USE_CLAUDE_HOOKS already defaults to `false` and is checked in promptsServiceImpl.ts before parsing Claude files — this discrepancy is unresolved from source alone.
- **Open decisions:**
  - Should Claude-format hook commands be executed via a bundled/detected POSIX shell (e.g. Git Bash) on Windows, or should unexecutable Claude-format hooks simply be skipped with a warning instead of attempted via PowerShell/cmd?
  - Should the `matcher` field in Claude-format hooks be implemented to scope hook invocation by tool name, matching Claude Code's own behavior, or is ignoring it an intentional compatibility simplification that should instead be documented?
  - Why did the reporter see Claude-format hooks enforced when `chat.useClaudeHooks` already defaults to false and no override was present — is there an experiment/treatment path that can flip this default, and if so should it respect workspace-level opt-outs unconditionally?

## Evidence

- **shell mismatch confirmed on main:** extensions/copilot/src/platform/chat/node/hookExecutor.ts `getShellCommand()` only special-cases Windows when ComSpec is cmd.exe (switching to PowerShell with `-Command`); otherwise it falls back to `shell: true` (spawns via ComSpec/cmd). Nothing in this path invokes bash or a POSIX shell, so Claude hook commands written in bash syntax (`||`, `[ -f ... ]`, `case...esac`) cannot execute correctly on Windows.
- **matcher ignored, confirmed on main:** src/vs/workbench/contrib/chat/common/promptSyntax/hookClaudeCompat.ts `parseClaudeHooks()` reads each Claude hook entry via `extractHookCommandsFromItem(item, ...)` but never reads or applies the entry's `matcher` field (e.g. `Bash`, `Edit|Write`) to filter which tool calls trigger the hook — every parsed command is collected unconditionally for the hook type, matching the reporter's observation that one PreToolUse hook now gates every tool call.
- **fail-closed by design:** src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts constructs the `Denied by {hookType} hook: {reason}` message (line ~436) when a hook returns a blocking error; hookExecutor.ts treats a non-JSON/failed spawn as `NonBlockingError` or `Error` depending on exit code, so a hook that can't run at all due to the shell mismatch surfaces as a denial rather than being skipped.
- **opt-out setting appears correctly wired but default is already off:** `chat.useClaudeHooks` (PromptsConfig.USE_CLAUDE_HOOKS) defaults to `false` in src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts, and src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts skips Claude-format hook files when this is `false` (line ~1376) — so the reporter's claim that hooks fired despite the documented default-off behavior is not explained by anything found in this checkout and needs reporter/maintainer follow-up (possibly an experiment flight or restricted-setting scoping quirk, not visible from source alone).
- **related reports:** Reporter cross-references https://github.com/microsoft/vscode/issues/337374 (same symptom via Claude plugin hooks, WSL-bash/path diagnosis) and https://github.com/microsoft/vscode/issues/312314 (hookExecutor hardcodes the Windows shell) as narrower/overlapping diagnoses of the same shell problem.
