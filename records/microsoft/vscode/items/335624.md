# Issue #335624 — Word wrapping breaks when line contains right arrow characters (→) with Iosevka SS11 font

[https://github.com/microsoft/vscode/issues/335624](https://github.com/microsoft/vscode/issues/335624)

## Summary

This is the documented trade-off of the default `editor.wrappingStrategy: simple` algorithm, which assumes all characters share the same pixel width; it explicitly does not guarantee correct wrapping when glyphs (like this font's wide arrow) are wider than a regular character. Switching to `advanced` (which delegates to real browser layout) resolves it.

## Change summary

A line of many U+2192 (→) arrow characters in the Iosevka SS11 font does not word-wrap and overflows the viewport.

## Best solution

Point the reporter to `editor.wrappingStrategy: "advanced"`, which measures actual rendered widths via the DOM and wraps correctly for non-uniform-width glyphs; no core code change is warranted for the default `simple` strategy's documented limitation.

- **Proposed comment:**

  > Thanks for the report and the detailed repro. This is a known trade-off of the default `editor.wrappingStrategy: "simple"` algorithm: it assumes every character occupies the same pixel width (with only a fullwidth-CJK exception), which is documented as working correctly for monospace fonts and scripts with equal-width glyphs. Iosevka SS11 renders the → glyph noticeably wider than a regular character, so the fast width estimate undercounts the line and the forced wrap point is never reached.
  > 
  > Switching to `"editor.wrappingStrategy": "advanced"` delegates wrapping to the browser's real layout engine and should wrap this line correctly, at the cost of being slower on very large files. I don't think a core change to the default `simple` algorithm is warranted here, so I'm closing as as-designed — please reopen if `advanced` doesn't resolve it for you.

## Evidence

- **documented trade-off:** src/vs/editor/common/config/editorOptions.ts (WrappingStrategy, ~line 3063) describes 'simple' as: 'Assumes that all characters are of the same width. This is a fast algorithm that works correctly for monospace fonts and certain scripts ... where glyphs are of equal width.' Default is 'simple'.
- **fast-path width computation:** src/vs/editor/common/viewModel/monospaceLineBreaksComputer.ts computeCharWidth() only special-cases CJK/fullwidth characters (strings.isFullWidthCharacter) as width 2; any other character (including U+2192 arrow glyphs drawn unusually wide by a font like Iosevka SS11) is assumed width 1, so the computed visible-column total under-counts the real rendered width and the forced-wrap threshold is never reached.
- **monospace detection is separate from wrap-strategy selection:** src/vs/editor/browser/config/fontMeasurements.ts measures the actual rightwards-arrow glyph width against other monospace test chars (line ~188-227) and can correctly conclude the font is non-monospace for whitespace-rendering purposes, but src/vs/editor/common/viewModel/viewModelLines.ts createLineBreaksComputer() picks the fast monospace-assuming computer whenever `wrappingStrategy !== 'advanced'`, regardless of that detected non-monospace-ness.
- **advanced path measures real widths:** src/vs/editor/browser/view/domLineBreaksComputer.ts renders the actual line into a constrained-width DOM node and reads the browser's own line-break offsets, so it is unaffected by non-uniform glyph widths.
