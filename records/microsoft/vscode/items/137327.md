# Issue #137327 — Debugging on OSX with iTerm as external terminal creates a new window each time

[https://github.com/microsoft/vscode/issues/137327](https://github.com/microsoft/vscode/issues/137327)

## Summary

Keep open: current main still creates a new iTerm window for every external-terminal debug launch. The thread establishes maintainer support for safe session reuse with shell integration; neither an existing setting nor a verified canonical issue covers the request.

## Change summary

Reuse an idle iTerm session across successive debug launches while preserving separate terminals for concurrent sessions.

## Best solution

Provide safe reuse of a previously created iTerm session when it is at a shell prompt, retaining new-window behavior when reuse cannot be established safely. Make the shell-integration prerequisite discoverable, following the direction accepted in the discussion.

- **Validation:** On macOS with iTerm shell integration enabled, launch a short-lived debug target using console: externalTerminal and terminal.external.osxExec: iTerm.app, let it return to the shell prompt, and launch it again: the same session should be reused. Keep a target running and launch a concurrent session: it must receive a separate terminal. Repeat with shell integration disabled and with the remembered window closed: launching must remain functional and must not send commands into a busy or unrelated session. Verify prerequisite guidance and unchanged Apple Terminal behavior.
- **Behavior:**

  > Successive external-terminal debug launches using iTerm should reuse the previously created session when it is idle at a shell prompt. A running debug target must never receive another launch command; concurrent targets need separate terminals. Without reliable idle detection, including when shell integration is unavailable, launches should continue to create a new window. Users should be able to discover the shell-integration prerequisite without relying solely on release notes.
- **Trace:**

  > MacExternalTerminalService.runInTerminal in src/vs/platform/externalTerminal/node/externalTerminalService.ts chooses iTermHelper.scpt for iTerm.app. Read-only decompilation confirms that src/vs/workbench/contrib/externalTerminal/node/iTermHelper.scpt always creates a window, whereas neighboring TerminalHelper.scpt remembers a terminal and checks whether it is busy. The discussion at https://github.com/microsoft/vscode/issues/137327#issuecomment-972660690 accepts shell-prompt-based detection and favors first-use guidance; it does not require migration to the Python API. Preserve concurrent debugging, command argument and environment handling, and the existing Apple Terminal path. The renderer service in src/vs/platform/externalTerminal/electron-browser/externalTerminalService.ts proxies to the main process; the trace has not established the complete notification and persistence path. Existing external-terminal unit tests do not exercise the AppleScript reuse behavior, so the plan must establish real-iTerm acceptance coverage.
