# Issue #137327 — Debugging on OSX with iTerm as external terminal creates a new window each time

[https://github.com/microsoft/vscode/issues/137327](https://github.com/microsoft/vscode/issues/137327)

## Summary

The requested iTerm reuse behavior remains absent on current main: each invocation still creates a new window, while the macOS Terminal helper reuses its previous idle tab. The issue should remain open for the accepted shell-integration-based design and its user-facing fallback.

## Change summary

Reuse an idle iTerm session across sequential external-terminal debug runs instead of creating a new window for every run.

## Best solution

Bring iTerm behavior in line with the macOS Terminal helper by reusing the prior session when iTerm shell integration can confirm that it is at a prompt, while retaining separate sessions for concurrent debug runs and a safe new-window fallback when reuse cannot be established.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/externalTerminal/node/iTermHelper.scpt`, `src/vs/platform/externalTerminal/node/externalTerminalService.ts`, `src/vs/platform/externalTerminal/test/node/externalTerminalService.test.ts`
- **Validation:** On macOS with iTerm shell integration enabled, run the same `console: "externalTerminal"` debug configuration twice sequentially and verify that the second run reuses the idle session; start overlapping runs and verify that the active session is not reused. Disable shell integration and verify the agreed fallback and notification behavior.
- **Behavior:**

  > Sequential debug launches configured with iTerm as the external terminal should reuse the previous iTerm session when that session is available at a shell prompt. An active session must never be reused, so overlapping debug runs continue in separate sessions. When shell integration cannot establish that a session is idle, behavior must fall back safely without sending a command into a busy session. Acceptance includes sequential reuse, concurrent-session isolation, and the agreed user-facing behavior when shell integration is disabled.
- **Trace:**

  > MacExternalTerminalService.runInTerminal in src/vs/platform/externalTerminal/node/externalTerminalService.ts selects iTermHelper.scpt for `iTerm.app`. The current compiled AppleScript at src/vs/workbench/contrib/externalTerminal/node/iTermHelper.scpt unconditionally creates a default-profile window, whereas TerminalHelper.scpt persists the last window/TTY and reuses it only when it is not busy. The thread established that iTerm's `is at shell prompt` can provide the corresponding safety check when shell integration is enabled; without integration it evaluates false, naturally preserving the current new-window fallback. Keep the boundary to iTerm external-terminal launching: do not change integrated-terminal behavior, debug adapter semantics, or reuse an active session. https://github.com/microsoft/vscode/issues/63813 is related accumulation work but does not replace this iTerm-specific request. The remaining uncertainty is how VS Code should expose the shell-integration requirement without producing repetitive notification noise.
- **Open decisions:**
  - When iTerm shell integration is unavailable, should VS Code preserve the current new-window fallback and show a one-time notification explaining the reuse requirement, or preserve the fallback silently?
