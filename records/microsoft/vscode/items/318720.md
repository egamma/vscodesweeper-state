# Issue #318720 — Performance Issues Large Find-Replace

[https://github.com/microsoft/vscode/issues/318720](https://github.com/microsoft/vscode/issues/318720)

## Summary

Current main still opens and retains every affected text model before applying a bulk edit, confirming the reported performance defect. This should remain open as the new canonical report and be routed to bulk workspace-edit/search owners.

## Change summary

Large workspace replacements open thousands of documents concurrently and trigger expensive language-server and save-participant work.

## Best solution

Rework `BulkTextEdits` to bound concurrently resolved models while preserving validation and unified undo semantics, then make search replacement save affected resources with similarly bounded concurrency.

## Evidence

- **current source:** `src/vs/workbench/contrib/bulkEdit/browser/bulkTextEdits.ts` `_createEditsTasks` creates a model reference for every edited resource concurrently via `Promise.all`; all references remain alive until `apply` finishes and disposes the complete task collection.
- **save amplification:** `src/vs/workbench/contrib/search/browser/replaceService.ts` applies the complete edit collection first, then starts saves for every affected model together; save participants can consequently generate the reported formatting traffic.
- **confirmed report:** https://github.com/microsoft/vscode/issues/318720#issuecomment-4575400649 records 500 `didOpen` events before changes and formatting, followed much later by `didClose`, matching the current source lifecycle.
- **historical root cause:** https://github.com/microsoft/vscode/issues/64485#issuecomment-790444360 identifies the same bulk-edit stages—open all documents, validate all, edit all, then clean up—and recommends breaking up huge edits.
