# Issue #318720 — Performance Issues Large Find-Replace

[https://github.com/microsoft/vscode/issues/318720](https://github.com/microsoft/vscode/issues/318720)

## Summary

Keep open: an independent commenter reproduced large workspace replacement slowdown locally and remotely with extensions disabled, and current source still resolves all affected models before applying edits and then launches saves concurrently. The supplied 10,000-file sample is sufficient for performance investigation; clangd is not the sole explanation.

## Change summary

Replacing text across thousands of files causes prolonged UI slowdown and excessive concurrent document and save activity.

## Best solution

Make workspace Replace All scale without overwhelming model resolution, save participants, or the UI, while preserving grouped undo, existing dirty buffers, formatting settings, and save-error handling. Profile the extension-free sample first, then the remote clangd case, to distinguish core costs from language-server amplification.

## Evidence

- **Independent reproduction:** https://github.com/microsoft/vscode/issues/318720#issuecomment-5372382997 confirms slowdown with all extensions disabled, locally on macOS and over Remote SSH on version 1.134.0. It supplies a complete 10,000-file sample and a literal replacement from 123 to 456.
- **Document lifecycle evidence:** https://github.com/microsoft/vscode/issues/318720#issuecomment-4575400649 records a 500-file clangd log in which all didOpen notifications precede didChange and formatting, while saves and closes continue much later. This supports investigating excessive simultaneous document activity, without proving clangd's thread behavior is owned by VS Code.
- **Current replacement path:** PlainTextSearchHeadingImpl.replaceAll in src/vs/workbench/contrib/search/browser/searchTreeModel/textSearchHeading.ts passes all matches to ReplaceService.replace. In src/vs/workbench/contrib/search/browser/replaceService.ts, replace awaits one bulk-edit operation and then immediately maps every edit to a save promise, awaiting Promises.settled without a concurrency limit.
- **Current bulk-edit preparation:** BulkTextEdits._createEditsTasks in src/vs/workbench/contrib/bulkEdit/browser/bulkTextEdits.ts starts model-reference resolution for every resource and awaits Promise.all before applying edits. Its multi-resource apply path synchronously iterates all tasks and creates a shared MultiModelEditStackElement, so changing this behavior requires preserving workspace undo semantics.
- **Save and disposal boundary:** FormatOnSaveParticipant in src/vs/workbench/contrib/codeEditor/browser/saveParticipants.ts honors editor.formatOnSave and invokes the selected formatter for eligible saves. ResourceModelCollection.destroyReferencedObject in src/vs/workbench/services/textmodelResolver/common/textModelResolverService.ts waits for textFileService.files.canDispose before disposing text-file models; releasing bulk-edit references therefore does not guarantee immediate document closure.
- **Canonical search:** https://github.com/microsoft/vscode/issues/234314 is older and open, but reports a proliferation of rg processes around approximately 200 files; the evidence does not establish that it owns this report's model-resolution and save fan-out problem. https://github.com/microsoft/vscode/issues/127621 concerns search-result refresh costs before replacement, and https://github.com/microsoft/vscode/issues/30874 concerns pathological regex evaluation in an editor. None was verified as a same-work canonical.
- **Unconfirmed secondary damage:** The independent commenter also reports missing file contents after interrupting replacement and declining saves, but explicitly could not reproduce that consistently. This warrants checking interruption behavior during investigation, not classifying the established defect as data loss.
