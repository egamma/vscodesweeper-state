# Issue #174770 — Add missing commands for list expansion

[https://github.com/microsoft/vscode/issues/174770](https://github.com/microsoft/vscode/issues/174770)

## Summary

The request remains open and relevant: VS Code still lacks general list commands for recursively expanding the focused node or all currently resolved nodes. Async trees rule out an unbounded literal “expand everything,” but the maintainer discussion identifies a viable bounded interpretation rather than rejecting the capability.

## Change summary

Add general list commands for recursively expanding the focused subtree and the resolved portion of an entire tree, enabling consistent keybindings across tree views.

## Best solution

Define expansion commands over already-resolved nodes, with an explicit depth bound where needed, and expose them consistently through the shared tree/list command layer rather than individual views.

- **Behavior:**

  > Users can bind shared commands that recursively expand the focused tree node and expand an entire tree under a finite, documented policy. The commands behave consistently across compatible workbench trees and do not attempt unbounded traversal of an infinite async tree. Existing single-node expansion and collapse commands remain unchanged.
- **Trace:**

  > The request concerns the shared workbench list/tree command surface, likely centered on command registration in src/vs/platform/list/browser/listServiceCommands.ts and tree operations exposed through src/vs/platform/list/browser/listService.ts and src/vs/base/browser/ui/tree/abstractTree.ts. The maintainer discussion at https://github.com/microsoft/vscode/issues/174770#issuecomment-1441888091 establishes the boundary: recursively expanding an unbounded async tree is unsafe, while operating on resolved nodes is feasible. The extension API's depth-limited `TreeView.reveal` and reported per-node overhead do not provide equivalent coverage. Preserve lazy loading and existing single-node/collapse semantics; scrolling from the first comment is a separate request and should remain out of scope.
- **Open decisions:**
  - Should whole-tree expansion affect only nodes already resolved in memory, or may it resolve new children up to a caller-specified finite depth?
  - Should focused recursive expansion use a fixed command policy or accept a depth argument analogous to editor movement commands?
