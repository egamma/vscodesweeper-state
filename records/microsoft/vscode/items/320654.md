# Issue #320654 — MCP server connection keep prompting for authentication using dynamic client registration when attempting to fetch resource metadata.

[https://github.com/microsoft/vscode/issues/320654](https://github.com/microsoft/vscode/issues/320654)

## Summary

Current source still turns a 401 from a header-authenticated MCP server into OAuth discovery and can prompt again after cancellation. Keep this older report open; the closely matching later report is related, not an eligible duplicate target.

## Change summary

Prevent repeated, unactionable OAuth registration prompts when a header-authenticated MCP server rejects a request after successful tool discovery.

## Best solution

Make cancellation end automatic authentication prompting for the current connection attempt, and surface the underlying HTTP/session error clearly. Settle how static-header authentication should interact with OAuth fallback without breaking automatic discovery for legitimate OAuth servers.

- **Behavior:**

  > A static-header MCP connection can discover tools successfully and then show unrelated OAuth registration dialogs after a later HTTP error. Declining authentication must not lead to repeated automatic dialogs for the same connection attempt; the underlying failure must remain visible. Acceptance should cover successful header authentication, a subsequent missing-session 401, failed metadata discovery, and cancellation. Legitimate OAuth discovery and negotiated MCP session handling must remain functional.
- **Trace:**

  > McpHTTPHandle._fetchWithAuthRetry in src/vs/workbench/api/common/extHostMcp.ts promotes authentication-status responses into createAuthMetadata, whose failed discovery produces default metadata. _addAuthHeader logs ordinary cancellation errors and returns, allowing the configured Authorization header to satisfy the forceNewRegistration retry condition; later requests can attempt authentication again through cached metadata. mainThreadMcp.ts and extHostAuthentication.ts expose declined consent/client registration as ordinary errors. This confirms repeated authentication opportunities, not the private server's complete infinite-loop scenario. _sendStreamableHttp and _attachStreamableBackchannel use server-issued session IDs, so determine which request received the missing-session response before attributing that error to VS Code. Preserve valid OAuth discovery, static credentials, and session negotiation. https://github.com/microsoft/vscode/issues/334970 describes the same fallback concern but is newer; coordinate the behavioral contract without closing this older report into it.
- **Open decisions:**
  - When a server has configured static authentication headers but no explicit OAuth configuration, should a 401/403 without usable OAuth discovery metadata surface the HTTP failure without registration, or should legacy OAuth fallback remain available through an explicit user action?
