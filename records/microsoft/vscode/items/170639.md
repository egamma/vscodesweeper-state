# Issue #170639 — "Customize layout" UI is very confusing

[https://github.com/microsoft/vscode/issues/170639](https://github.com/microsoft/vscode/issues/170639)

## Summary

The central usability gap remains on current main: visibility state is hidden until hover or focus, while independently composable options are still grouped as “Modes.” The picker now distinguishes visibility actions from selected options internally, but it does not communicate those semantics clearly enough at rest.

## Change summary

Make Customize Layout clearly distinguish independent toggles from mutually exclusive choices and expose each item's current state without requiring hover.

## Best solution

Give the picker persistent, semantically distinct state affordances for independent toggles and exclusive choices, and replace “Modes” with terminology that reflects whether Full Screen, Zen Mode, and Centered Layout can coexist. Preserve accurate keyboard and screen-reader state communication while simplifying the visual hierarchy.

- **Behavior:**

  > Customize Layout must communicate each item's current state at a glance, without requiring pointer hover. Independently composable toggles must be distinguishable from mutually exclusive choices, and section terminology must accurately describe those interaction rules. Keyboard users must be able to operate every control, and screen readers must receive the same state information shown visually.
- **Trace:**

  > CustomizeLayoutAction in src/vs/workbench/browser/actions/layoutActions.ts maps visibility entries through CreateToggleLayoutItem and position/alignment entries through CreateOptionLayoutItem. Visibility state is rendered as an item button with `alwaysVisible: false`; src/vs/platform/quickinput/browser/media/quickInput.css hides such actions at rest and reveals them on hover or focus. Full Screen, Zen Mode, and Centered Layout remain independently evaluated entries beneath the “Modes” separator. The boundary is the Customize Layout presentation and its quick-input state semantics; do not change unrelated quick-pick action visibility globally without enumerating its other consumers. https://github.com/microsoft/vscode/issues/143667 separately tracks screen-reader announcement of checked layout state and should remain distinct.
- **Open decisions:**
  - Should independent layout states use persistent checkbox/switch semantics, or remain action rows with a persistent state indicator?
  - Should Full Screen, Zen Mode, and Centered Layout remain independently composable under a renamed section, or should any of them become mutually exclusive?

## Evidence

- **hidden state:** CustomizeLayoutAction sets `alwaysVisible: false` on visibility-state buttons. src/vs/platform/quickinput/browser/media/quickInput.css hides quick-input item actions by default and reveals them only on hover, focus, or when marked always-visible, confirming that most visibility state is absent at rest.
