# Issue #81757 — API to toggle between flat tree (list) and tree for custom view

[https://github.com/microsoft/vscode/issues/81757](https://github.com/microsoft/vscode/issues/81757)

## Summary

The reusable custom-view API remains missing: SCM supports list/tree switching internally, but extensions must still supply their own hierarchy and switching logic. Keep this accepted, team-authored Backlog request open for API design; the linked implementation attempt was closed without merging.

## Change summary

Expose reusable list/tree switching for extension-contributed resource views, using SCM-style resource hierarchy and compact-folder behavior.

## Best solution

Define an opt-in custom-view API that lets resource-oriented extensions offer consistent flat and hierarchical presentations without independently rebuilding SCM's resource-tree machinery. Settle its applicability and generated-item identity/reveal contract before implementation.

- **Validation:** End the design with an executable extension-host scenario using resources in nested and single-child folders: switch between list and tree, verify the same resources remain accessible and revealable, check compact-folder behavior against SCM, and confirm existing custom views retain their current behavior without opting in.
- **Behavior:**

  > Resource-oriented custom views should be able to offer flat and hierarchical presentations without each extension implementing its own resource-grouping machinery. The original context seeks consistency with SCM, including compact single-child folders. Acceptance should exercise switching on nested resources, resource activation and reveal in both modes, and unchanged behavior for existing views that do not opt in.
- **Trace:**

  > TreeViewOptions, TreeView, and TreeDataProvider in src/vscode-dts/vscode.d.ts currently leave hierarchy construction to the provider; resourceUri supplies presentation metadata rather than grouping. ExtHostTreeViews forwards creation options through extHost.protocol.ts to MainThreadTreeViews, and the custom widget in src/vs/workbench/browser/parts/views/treeView.ts uses WorkbenchAsyncDataTree. SCMTreeDataSource and the view-mode actions in src/vs/workbench/contrib/scm/browser/scmViewPane.ts demonstrate the existing internal resource-tree behavior, but are not a public custom-view capability. The original discussion at https://github.com/microsoft/vscode-references-view/pull/54 favors sharing that machinery; its unmerged implementation is context, not a pending human-owned fix. Uncertainty begins at the public contract for eligible data and generated folder nodes. Preserve existing provider-defined hierarchies and SCM behavior; https://github.com/microsoft/vscode/issues/304713 is a related consumer requirement, not a replacement canonical.
- **Open decisions:**
  - Should the initial API support only URI-backed resource collections, as suggested by the original discussion, or arbitrary provider-defined custom hierarchies?
  - How should generated folder nodes participate in the public element-identity, selection, command, and reveal contracts?
