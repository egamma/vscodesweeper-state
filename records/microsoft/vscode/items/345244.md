# Issue #345244 — VS Code Insiders 1.145.0: OOM crash (-536870904) truncates 28 MB text file by 13,217 lines during recovery

[https://github.com/microsoft/vscode/issues/345244](https://github.com/microsoft/vscode/issues/345244)

## Summary

Keep open: repeated renderer OOMs and truncated recovery are reported on both Insiders and stable, and current source still permits interrupted backups to be restored as complete documents. The backup-integrity defect needs investigation independently of the allocation causing the OOM.

## Change summary

After an OOM while editing a large text file, recovery silently restores a backup missing thousands of lines.

## Best solution

Preserve a complete recoverable snapshot when backup updates are interrupted, without increasing renderer memory pressure. Separately diagnose the recurrent renderer allocation growth; ordinary file-save atomicity alone does not establish that crash recovery is safe.

- **Validation:** Extend WorkingCopyBackupService tests with an existing complete backup and a replacement stream interrupted after its preamble and an initial content chunk; recreate the service and verify recovery does not silently accept the incomplete replacement. Run scripts/test.sh --run src/vs/workbench/services/workingCopy/test/electron-browser/workingCopyBackupService.test.ts after implementation. Separately reproduce repeated edits to a disposable approximately 28 MB, 427,300-line text file on Windows and inspect renderer memory growth and recovery content.
- **Behavior:**

  > Editing a large plain-text document can repeatedly terminate the renderer with an OOM, after which recovery sometimes loses thousands of lines that were already present on disk. Recovery must not present an interrupted backup update as a complete restored document. Acceptance should cover interruption during replacement of a complete backup and verify that previously recoverable content survives. Diagnose the allocation growth separately rather than treating additional physical RAM as protection against renderer heap exhaustion.
- **Trace:**

  > WorkingCopyBackupServiceImpl.backup prefixes snapshot content with metadata and writes directly to the backup resource without requesting atomic writing. FileService's buffered path opens and incrementally writes the destination; DiskFileSystemProvider.open truncates an existing Windows file first. WorkingCopyBackupServiceImpl.resolve checks the preamble delimiter but not body completeness, and TextFileEditorModel.doResolveFromBackup consumes the remaining stream as dirty document content. This establishes the interruption hazard, not the exact cause of the reporter's OOM or proof that it happened during a backup write. Preserve existing snapshot encoding, legitimate document deletions, and ordinary save behavior; smaller recovered content alone cannot distinguish corruption from intentional edits. https://github.com/microsoft/vscode/issues/98063 is relevant shared file-I/O work, while https://github.com/microsoft/vscode/issues/256665 records the prior backup-specific concern. The older OOM diagnosis in https://github.com/microsoft/vscode/issues/252259 is a lead, not a diagnosis of this recurrence.
