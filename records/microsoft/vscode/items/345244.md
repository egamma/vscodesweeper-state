## Plan brief

- **Likely files:** `src/vs/workbench/services/workingCopy/common/workingCopyBackupService.ts`, `src/vs/workbench/services/workingCopy/electron-browser/workingCopyBackupService.ts`, `src/vs/platform/files/common/fileService.ts`, `src/vs/platform/userData/common/fileUserDataProvider.ts`, `src/vs/workbench/services/workingCopy/test/electron-browser/workingCopyBackupService.test.ts`
- **Validation:** Using disposable synthetic data, interrupt a streamed replacement backup after a valid preamble and partial content, restart recovery, and compare the recovered document with the last complete backup and saved original. Add regression coverage in workingCopyBackupService.test.ts showing that interrupted replacement cannot silently become a successful truncated recovery.
- **Behavior:**

  > An OOM during editing must not cause recovery to silently present an incomplete backup as the complete document. The reported Windows failure removed approximately 13,000 trailing lines from both the recovered editor and its backup while the saved original remained more complete. Acceptance should cover interrupted backup replacement using synthetic large text, preservation of a complete recovery candidate, and unchanged recovery for normally completed backups.
- **Trace:**

  > WorkingCopyBackupServiceImpl.backup in src/vs/workbench/services/workingCopy/common/workingCopyBackupService.ts writes prefixed document content directly through IFileService.writeFile. FileUserDataProvider only enforces atomic writes for selected profile files; backups are outside that set. FileService.doWriteBuffered and DiskFileSystemProvider.open allow a destination to be truncated and populated incrementally, while backup resolution validates the preamble rather than payload completeness. NativeWorkingCopyBackupService joins writes during orderly shutdown, which does not establish protection against OOM termination. The unresolved boundary is whether this incident interrupted a backup write or produced incomplete content before persistence; diagnose that before selecting a fix, and do not assume the OOM itself has the same cause. Existing related work is https://github.com/microsoft/vscode/issues/98063, with earlier backup truncation discussed at https://github.com/microsoft/vscode/issues/256665. Use synthetic documents rather than requesting public disclosure of the sensitive crash dump.
