# Issue #345244 — VS Code Insiders 1.145.0: OOM crash (-536870904) truncates 28 MB text file by 13,217 lines during recovery

[https://github.com/microsoft/vscode/issues/345244](https://github.com/microsoft/vscode/issues/345244)

## Summary

Keep open: the edit-telemetry snapshot leak is confirmed, and multiple reporters describe truncated recovery after OOM crashes. An open fixing PR addresses both failures but has not merged.

## Change summary

Prevent edit telemetry from retaining consumed full-document snapshots and prevent interrupted backup writes from producing silently truncated recovery documents.

## Best solution

Review and land https://github.com/microsoft/vscode/pull/345796 after confirming bounded renderer memory during repeated edits and preservation of complete backups across interrupted writes.

## Evidence

- **Confirmed reproduction and workaround:** In the supplied discussion at https://github.com/microsoft/vscode/issues/345244, collaborator dmitrivMS reports renderer heap growth from approximately 391 MB to 768 MB after 40 insert/delete edits to a large plain-text file. Discarding consumed snapshots stabilized memory across another 200 edits. The reporter subsequently confirmed that disabling telemetry.editStats.enabled stopped the OOMs.
- **Current source retains consumed snapshots:** src/vs/workbench/contrib/editTelemetry/browser/helpers/vscodeObservableWorkspace.ts creates a new StringText from textModel.getValue() on every content change. helpers/utils.ts:iterateObservableChanges emits both current and previous values through AsyncIterableSource. In src/vs/base/common/async.ts, AsyncIterableObject.emitOne appends values to _results, while its iterator advances an index without releasing consumed entries. DocumentWithAnnotatedEdits uses this stream for document-lifetime edit processing.
- **Recovery consistency remains a separate concern:** src/vs/workbench/services/workingCopy/common/workingCopyBackupService.ts:backup writes the prefixed document stream directly to backupResource through fileService.writeFile, without staging and replacing it in that method. The reporter found the same truncation in the backup itself; another commenter independently reported losing most of a recovered file. Source inspection confirms the retention defect, but interrupted-write recovery was not executed in this read-only review.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/345796 is open, unmerged, and explicitly states 'Fixes #345244.' It proposes non-replaying edit-change streams and staged atomic backup replacement, with reported large-file memory measurements and targeted validation. This is an implementation candidate, not an already-landed fix.
- **Related tracking does not absorb the full report:** https://github.com/microsoft/vscode/issues/256665 is closed and its comments redirect atomic-backup concerns to https://github.com/microsoft/vscode/issues/98063. The latter remains open but addresses atomic file writes, not the independently confirmed edit-telemetry memory leak; it therefore does not own this report's full scope.
- **Concrete impact:** The original reporter describes repeated OOMs across Insiders and stable builds, recovery missing approximately 13,217 lines, and some lost unsaved work. A second reporter independently describes OOM-associated recovery data loss. These confirmations and the traced retention path support elevated attention.
