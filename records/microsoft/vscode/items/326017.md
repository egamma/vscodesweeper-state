# Issue #326017 — Enabling (not using) Copilot Chat crash-loops the extension host with a V8 out-of-memory abort

[https://github.com/microsoft/vscode/issues/326017](https://github.com/microsoft/vscode/issues/326017)

## Summary

Extremely well-documented crash loop: enabling Copilot Chat (without ever opening a chat session) causes the extension host to OOM-abort every ~13s in a large git repo, verified by the reporter with heap sampling, macOS crash reports, and a clean disable/enable A-B test — this needs a Copilot Chat maintainer to trace the actual trigger path.

## Change summary

Merely enabling (not using) GitHub Copilot Chat in a large git workspace repeatedly OOM-crashes the extension host (V8 FatalProcessOutOfMemory), looping indefinitely until the extension is disabled.

## Best solution

A Copilot Chat maintainer should trace what runs on activation/window-restore even with no chat session started — the pathspec.txt evidence points at the worktree checkpoint machinery (extensions/copilot/src/extension/chatSessions/vscode-node/chatSessionWorktreeCheckpointServiceImpl.ts, using getUncommittedFilePaths in extensions/copilot/src/platform/git/vscode-node/utils.ts) possibly being invoked for a restored/orphaned session on a huge repo, which then drives vscode.git's decorations provider into repeatedly processing 9500+ resources; that combination needs a repro in a large workspace with an existing chat-session worktree to confirm and fix.

## Evidence

- **A/B isolation:** Reporter confirms disabling GitHub Copilot Chat stops the loop and re-enabling reproduces it, isolating the cause to the extension.
- **checkpoint code path:** extensions/copilot/src/extension/chatSessions/vscode-node/chatSessionWorktreeCheckpointServiceImpl.ts:275 runs `git add -A --pathspec-from-file=<pathspec.txt>` built from getUncommittedFilePaths() in extensions/copilot/src/platform/git/vscode-node/utils.ts:98-121; the reporter found live pathspec.txt files under github.copilot-chat/vscode-sessions-<id>/ with ~9573 paths, matching the log line `[Decorations] CAPPING events from decorations provider vscode.git 9575` (src/vs/workbench/api/common/extHostDecorations.ts) emitted right before each exit.
- **trigger unclear:** sessionRequestLifecycle.ts:97 only calls checkpointService.handleRequest() on the first chat request of a session, so the exact activation-time trigger with 'no chat session opened' as reported isn't confirmed from source alone — a maintainer needs to check for stale/restored session state driving this on window load.
