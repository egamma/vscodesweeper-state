# Issue #316996 — [Bug] Incomplete Sanitization in conversationFeature.ts: Double-Escaping Bug Allows Shell Argument Injection in Git Commit Message

[https://github.com/microsoft/vscode/issues/316996](https://github.com/microsoft/vscode/issues/316996)

## Summary

Security-sensitive issue describing a real shell-argument-injection bug in the Copilot commit-message sanitization code. The defect is still present on current main (line 299 of conversationFeature.ts). Keeping open per security policy — a human must handle routing and resolution.

## Change summary

The commit-message sanitization in conversationFeature.ts applies double-quote escaping before backslash escaping, causing `"` to become `\"` and breaking the shell argument boundary, which enables shell argument injection in `git commit -m` commands.

## Best solution

Swap the escaping order on line 299 of `extensions/copilot/src/extension/conversation/vscode-node/conversationFeature.ts`: escape backslashes first, then double quotes, then dollar signs. The CodeQL suppression comment should be updated or removed once the order is corrected. A team member should also evaluate whether `sendText` with a hand-assembled shell command is the right approach here versus using the Git extension's commit API directly, which would avoid shell-escaping entirely.

## Evidence

- **defect on main:** Line 299 of extensions/copilot/src/extension/conversation/vscode-node/conversationFeature.ts still reads: `commitMessage.replace(/"/g, '\"').replace(/\\/g, '\\\\').replace(/\$/g, '\\$')` — quote escape before backslash escape, producing `\\"` from a `"` input, which splits the shell argument.
- **code trace:** For input `test"`: step 1 yields `test\"`, step 2 re-escapes the backslash to `test\\"`. In a double-quoted shell string `git commit -m "test\\"..."`, `\\` is a literal backslash and the next `"` closes the argument, exposing remaining content as additional shell tokens.
- **CodeQL suppression:** The line carries a `[SM02383]` suppression with the comment 'Backslashes are escaped as part of the second replace' — but the comment describes the intended behavior, not the actual behavior: the second replace re-escapes backslashes introduced by the first replace, which is the root cause.
