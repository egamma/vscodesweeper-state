# Issue #3220 — Custom peek widgets

[https://github.com/microsoft/vscode/issues/3220](https://github.com/microsoft/vscode/issues/3220)

## Summary

Keep open: persistent, independently expandable rich results in ordinary source editors remain an extension-API gap. The proposed editor-insets API supplies part of the infrastructure, but its fixed-height contract does not cover the full request; 185 upvotes and concrete extension-author use cases support retaining this accepted backlog work.

## Change summary

Allow extensions to display multiple persistent inline evaluation widgets with expandable values, arrays, plots, and structured data in ordinary source files.

## Best solution

Provide an extension-facing contract for persistent, expandable results anchored to source locations, leaving evaluation and visualization to extensions. Coordinate its design with the editor-insets proposal while preserving this issue's requirements for compact presentation, expansion, and multiple simultaneous widgets.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.editorInsets.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostCodeInsets.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadCodeInsets.ts`
- **Validation:** Use an extension-host development sample to place two result widgets at different source lines, expand and collapse an array/tree result, display a plot, move focus between the editor and widgets, and scroll. Both widgets must remain independently usable while the hosting editor stays visible, expansion must not modify document text, and the agreed compact presentation and viewport behavior must hold.
- **Behavior:**

  > Extensions should be able to attach rich evaluation results to locations in an ordinary source file without converting it to a notebook or modifying its text. Multiple results must coexist and remain visible when focus moves away. Values should have a compact presentation, with arrays, plots, and structured data expandable on demand. Acceptance should exercise two simultaneous results, independent expansion and collapse, focus changes, and scrolling.
- **Trace:**

  > The current proposed editorInsets API is declared in src/vscode-dts/vscode.proposed.editorInsets.d.ts and gated in src/vs/workbench/api/common/extHost.api.impl.ts. ExtHostEditorInsets in src/vs/workbench/api/common/extHostCodeInsets.ts creates independently handled webviews; MainThreadEditorInsets and EditorWebviewZone in src/vs/workbench/api/browser/mainThreadCodeInsets.ts mount them in editor view zones. Both the public height property and the zone height are readonly, and the protocol exposes no height-update operation. The merged MVP at https://github.com/microsoft/vscode/pull/66418 therefore establishes infrastructure, not the complete requested contract. Coordinate with https://github.com/microsoft/vscode/issues/85682, but do not substitute the single transient hover requested by https://github.com/microsoft/vscode/issues/175234. Keep evaluation and result rendering extension-owned; notebooks, document edits, and built-in inline chat are outside this request. Uncertainty starts at the public presentation and resizing semantics, not at whether the proposed API exists.
- **Open decisions:**
  - Should the supported presentation be a compact inline attachment that expands into a view zone, or a collapsible view-zone result from the outset?
  - Should expanded height be controlled explicitly by the extension or negotiated from rendered content, and what viewport stability should users be guaranteed during resizing?

## Evidence

- **Demand and requested behavior:** https://github.com/microsoft/vscode/issues/3220 has 185 community upvotes and a Backlog milestone. Its body requires multiple widgets that survive focus changes and expand rich results; the supplied discussion includes Julia and Calva extension use cases and explicitly distinguishes this workflow from notebooks and transient peek windows.
- **Existing-capability check:** src/vscode-dts/vscode.proposed.editorInsets.d.ts declares window.createWebviewTextEditorInset and WebviewEditorInset, but height is readonly and there is no resize operation. src/vs/workbench/api/common/extHost.api.impl.ts:967-969 gates creation with checkProposedApiEnabled(extension, 'editorInsets'); the API is absent from stable src/vscode-dts/vscode.d.ts.
- **Partial implementation, not completion:** src/vs/workbench/api/browser/mainThreadCodeInsets.ts implements EditorWebviewZone with readonly heightInLines and stores multiple zones in MainThreadEditorInsets._insets. src/vs/workbench/api/common/extHostCodeInsets.ts maintains multiple inset handles and disposes them when their hosting editors cease to be visible. This provides embedded webviews, not a finished compact-to-expanded widget contract.
- **Discussion workaround:** The final supplied comment points to https://github.com/microsoft/vscode/issues/85682#issuecomment-1546768001 as an experimental editorInsets workaround. https://github.com/microsoft/vscode/pull/66418 is verified merged, but describes itself as an MVP; its existence does not establish completion of the requested extension capability.
- **Canonical search and scope:** Searches for custom peek widgets, inline evaluation, and editor insets found no verified open issue that fully absorbs this request. https://github.com/microsoft/vscode/issues/85682 remains open and tracks the proposed fixed-height inset API; its discussion requests additional resizing and floating presentation. https://github.com/microsoft/vscode/issues/175234 remains open but explicitly requests a single hover webview hidden on focus loss, unlike this issue's multiple persistent widgets.
- **Owner direction:** https://github.com/microsoft/vscode/issues/85682#issuecomment-1729178552 says inset API finalization was not planned at that time, not that the capability was rejected. Stable decorations and webview panels offer partial alternatives, while the supplied discussion explains why notebooks, side panels, and inline completions do not meet the ordinary-source-file workflow.
