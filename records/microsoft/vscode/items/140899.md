# Issue #140899 — Add support for palettes/named colors in the color picker

[https://github.com/microsoft/vscode/issues/140899](https://github.com/microsoft/vscode/issues/140899)

## Summary

Keep open: the current color picker still lacks extension-provided palettes of selectable named colors. The request has 62 upvotes, was explicitly accepted into the Backlog, and already carries the appropriate area labels.

## Change summary

Allow extensions or language servers to contribute named color palettes displayed as selectable swatches alongside the color picker.

## Best solution

Define an extension-facing palette contract and an accessible swatch selection experience in the existing editor color picker, while preserving current color presentation and document-edit behavior. Palette contents should remain provider-owned rather than hard-coding language-specific collections into the editor.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages.ts`, `src/vs/editor/contrib/colorPicker/browser/colorPickerModel.ts`, `src/vs/editor/contrib/colorPicker/browser/colorPickerParticipantUtils.ts`, `src/vs/editor/contrib/colorPicker/browser/colorPickerParts/colorPickerBody.ts`
- **Validation:** Use a test extension contributing two distinctly named palette entries: opening the picker must expose both, pointer and keyboard selection must select the intended color, and accepting it must apply the provider-defined document representation. Verify providers without palettes retain existing picker behavior and color-presentation edits; establish automated coverage for the agreed API and selection contract.
- **Behavior:**

  > Extensions or language servers should be able to supply a collection of named colors that users can browse and select alongside the existing color picker. Selecting an entry should choose that exact color without manually adjusting sliders, with its name available to assistive technology. Providers that do not contribute palettes must retain existing behavior. Acceptance must cover palette display, pointer and keyboard selection, and the agreed document representation when a named entry is accepted.
- **Trace:**

  > The request and its 62 upvotes are recorded at https://github.com/microsoft/vscode/issues/140899, which was accepted into the Backlog. Current DocumentColorProvider in src/vscode-dts/vscode.d.ts supplies document colors and presentations of a single supplied color, not arbitrary palette entries. ColorPickerBody in src/vs/editor/contrib/colorPicker/browser/colorPickerParts/colorPickerBody.ts builds the saturation and slider controls without a swatch collection; ColorPickerModel stores one color and its textual presentations. createColorHover and updateColorPresentations in src/vs/editor/contrib/colorPicker/browser/colorPickerParticipantUtils.ts obtain those presentations, while updateEditorModel applies the selected presentation's main and additional edits. Preserve these existing edit semantics and keep language-specific palette contents outside editor core. The unresolved boundary is the public palette contribution contract and how a named palette selection determines inserted text, not a defect in the current single-color presentation API.
- **Open decisions:**
  - Should palette contributions extend DocumentColorProvider for a document and color location, or use a separately registered palette provider with its own applicability contract?
  - Does selecting a named palette entry preserve that entry's symbolic identity for insertion, or select only its RGBA value and let the existing presentation provider determine the inserted text?
