# Issue #30191 — Change Vertical Scrollbar Width

[https://github.com/microsoft/vscode/issues/30191](https://github.com/microsoft/vscode/issues/30191)

## Summary

Keep open: current source still lacks user-configurable Explorer/workbench scrollbar dimensions; editor settings and the Modern UI size toggle do not cover the request. This accepted Backlog item has 85 upvotes, and the related open request is newer, so it is not a valid duplicate target for this re-review.

## Change summary

Allow users to configure scrollbar widths and heights outside the editor, especially the Explorer's vertical scrollbar.

## Best solution

Provide supported numeric scrollbar sizing for workbench surfaces, including Explorer, with consistent horizontal and vertical controls. Preserve existing editor-specific sizing and establish how the workbench controls interact with Modern UI and explicitly sized widgets.

## Plan brief

- **Likely files:** `src/vs/platform/list/browser/listService.ts`, `src/vs/base/browser/ui/list/listView.ts`, `src/vs/base/browser/ui/scrollbar/scrollableElement.ts`, `src/vs/workbench/contrib/modernUI/browser/modernUI.contribution.ts`, `src/vs/editor/common/config/editorOptions.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`
- **Validation:** End the plan with browser tests covering the agreed sizing contract and a manual check using a long Explorer tree: changing the configured vertical width changes its scrollbar hit target, horizontal sizing follows the agreed independent control, reload retains the settings, and explicit editor sizes and Modern UI transitions obey the agreed precedence.
- **Behavior:**

  > Users cannot currently choose a numeric width for the Explorer scrollbar even though editor scrollbars support numeric dimensions. The goal is supported sizing for non-editor workbench scrollbars, with independent horizontal and vertical control requested in the discussion. Acceptance must demonstrate a wider, draggable Explorer target and consistent behavior across the workbench surfaces included in the agreed scope, without requiring injected CSS or installation-file edits.
- **Trace:**

  > ExplorerView constructs WorkbenchCompressibleAsyncDataTree in src/vs/workbench/contrib/files/browser/views/explorerView.ts; shared list behavior comes through src/vs/platform/list/browser/listService.ts and src/vs/base/browser/ui/list/listView.ts. ListView supplies no explicit scrollbar sizes, so SmoothScrollableElement uses the global default in src/vs/base/browser/ui/scrollbar/scrollableElement.ts and subscribes to default-size changes. ModernUIContribution currently controls that default with a fixed 8-versus-10 choice. Editor dimensions remain independently configured in src/vs/editor/common/config/editorOptions.ts, and explicitly sized scrollable elements bypass global defaults; the complete consumer inventory has not been established. The maintainer already acknowledged the editor-only gap at https://github.com/microsoft/vscode/issues/30191#issuecomment-872298811, and https://github.com/microsoft/vscode/issues/160804 records related all-scrollbar demand. Do not treat fading, scrollbar arrows, or sash behavior mentioned in comments as prerequisites for delivering dimension controls.
- **Open decisions:**
  - Should the new controls affect only workbench lists and trees, or serve as defaults across other non-editor scrollable surfaces, including widgets that currently specify fixed dimensions?
  - Should explicitly configured dimensions take precedence over Modern UI sizing, with the existing UI-dependent defaults retained only when no custom dimension is configured?
