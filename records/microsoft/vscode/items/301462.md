# Issue #301462 — [UX]: Settings menu does not indicate when user settings are overridden by settings.json files in a multi-root workspace

[https://github.com/microsoft/vscode/issues/301462](https://github.com/microsoft/vscode/issues/301462)

## Summary

The missing folder-level modification indicator is already tracked by an older, verified open issue covering the same observable symptom. Consolidate this report there, preserving its concrete multi-root reproduction.

## Change summary

Show when settings in a multi-root workspace folder override settings displayed in the User settings editor.

## Best solution

Consolidate on https://github.com/microsoft/vscode/issues/57370 and extend the existing settings modification indicators to identify folder-level settings without materially slowing the Settings editor.

## Evidence

- **Verified older canonical:** https://github.com/microsoft/vscode/issues/57370 is OPEN, was created on 2018-08-28, and requests that the existing “Modified in Workspace” decoration also list folders where a setting is modified. This is the same missing Settings editor indication reported here, satisfying the stronger duplicate bar for a re-reviewed item.
- **Maintainer diagnosis:** https://github.com/microsoft/vscode/issues/57370#issuecomment-416808198 explicitly explains that folder modification detection was omitted because inspecting every setting across every workspace folder could be expensive. https://github.com/microsoft/vscode/issues/57370#issuecomment-417026382 discusses lazy inspection when a row renders and measuring performance.
- **Current source confirms the capability gap:** src/vs/workbench/contrib/preferences/browser/settingsTreeModels.ts:322-356 constructs overriddenScopeList from workspace, remote and user values, but does not add folder entries. inspectSetting at lines 754-756 supplies a resource only when the selected target is a folder URI. src/vs/workbench/contrib/preferences/browser/settingsEditorSettingIndicators.ts:395-447 renders modification indicators from that list, so the existing surface does not cover folder-only modifications while viewing User settings.
- **Report-specific evidence to retain:** https://github.com/microsoft/vscode/issues/301462 supplies an extensions-disabled reproduction on VS Code 1.111.0 / Ubuntu 22.04: two workspace roots, editor.cursorStyle and editor.cursorWidth configured in one root’s .vscode/settings.json, effective editor changes but no User settings modification indicator. Its comparison with opening the folder directly illustrates the canonical issue without introducing a distinct requirement.
- **Initial leads do not own this work:** https://github.com/microsoft/vscode/issues/40233 requests private per-user workspace settings, and https://github.com/microsoft/vscode/issues/40239 requests configuration-driven extension enablement. Neither addresses the missing folder modification decoration.
