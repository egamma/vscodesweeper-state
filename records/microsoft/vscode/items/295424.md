# Issue #295424 — Error Code: net::ERR_CONNECTION_CLOSED

[https://github.com/microsoft/vscode/issues/295424](https://github.com/microsoft/vscode/issues/295424)

## Summary

Keep this open as the canonical chat connection-closure bug. Maintainer consolidation, cross-platform reports, and a newer report on VS Code 1.130 show that long-running Copilot requests can still terminate with `net::ERR_CONNECTION_CLOSED` despite the existing retry path.

## Change summary

Copilot Chat requests, particularly longer Agent requests, can lose their response when the underlying connection closes and the retry also fails.

## Best solution

Use the captured request IDs and networking telemetry to distinguish Electron transport, intermediary, and service-side closures, then make transient connection loss recover without discarding the turn. Consolidate newer same-symptom reports such as https://github.com/microsoft/vscode/issues/327415 into this canonical issue while preserving their long-running-request evidence.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts`, `extensions/copilot/src/extension/prompt/node/test/chatMLFetcherRetry.spec.ts`, `extensions/copilot/src/platform/networking/node/chatWebSocketManager.ts`, `extensions/copilot/src/platform/networking/node/chatWebSocketTelemetry.ts`
- **Validation:** Add a deterministic networking test that models `ERR_CONNECTION_CLOSED` after a partially received response, a successful connectivity probe, and a second transport attempt; finish the plan with a targeted Copilot unit test demonstrating recovery from a transient closure while preserving the existing terminal-error behavior for persistent failures.
- **Behavior:**

  > A transient connection closure during a Copilot Chat or Agent response should not terminate the turn and discard progress when connectivity can be re-established. Long-running requests must recover consistently across supported transports, while persistent failures must still surface an accurate actionable error. Acceptance should cover closure after response data has begun, successful retry recovery, and a bounded terminal failure when repeated attempts cannot reconnect.
- **Trace:**

  > The issue log shows Electron's connection entering an HTTP/2 draining state, followed by `ERR_CONNECTION_CLOSED`; the extension retries with its default fetcher and receives another closure. Current main routes eligible network failures from `ChatMLFetcher.fetchMany` through `_retryAfterError` in extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts, which probes CAPI before retrying and returns the original processed error when recovery fails. Existing coverage in extensions/copilot/src/extension/prompt/node/test/chatMLFetcherRetry.spec.ts models `ENOTFOUND` followed by a successful retry, not repeated closure after streaming has started. The uncertainty begins at ownership of the closure—Electron transport, an intermediary, or the Copilot service—so preserve current behavior for permanent offline failures and avoid broad retry-policy changes until request telemetry and a deterministic failing case identify the boundary. The newer https://github.com/microsoft/vscode/issues/327415 supplies additional evidence that long-running Agent requests remain affected.

## Evidence

- **direct failure log:** The report from VS Code 1.109.3 on macOS records `net::ERR_CONNECTION_CLOSED` with `drain_error: -100`, `drain_description: Connection closed`, and `error_source: TcpConnection`; it then logs a retry with the default fetcher followed by another connection-closed failure.
- **maintainer consolidation:** On 2026-04-15, a maintainer linked and closed numerous Windows, macOS, and Linux reports—including https://github.com/microsoft/vscode/issues/310032, https://github.com/microsoft/vscode/issues/299690, and https://github.com/microsoft/vscode/issues/302448—in favor of this issue, then applied the existing `bug` and `chat` labels.
- **recent confirmation:** https://github.com/microsoft/vscode/issues/327415 is a newer open report on VS Code 1.130 with two independent users observing the same error during long planning or multi-step Agent requests; it is younger and narrower than this canonical report.
- **current source:** On current main, `ChatMLFetcher.fetchMany` in extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts retries eligible network failures through `_retryAfterError` after a CAPI connectivity probe, but returns the processed `NetworkError` when recovery produces no result. extensions/copilot/src/platform/chat/common/commonTypes.ts then renders the generic network-error message.
- **existing test coverage:** extensions/copilot/src/extension/prompt/node/test/chatMLFetcherRetry.spec.ts covers a successful retry after an `ENOTFOUND` error, but not the reported sequence of an HTTP/2 connection entering a draining state and closing again after retry.
