# Issue #253498 — Using the same link again should do file validation before I accept it

[https://github.com/microsoft/vscode/issues/253498](https://github.com/microsoft/vscode/issues/253498)

## Summary

The validation-order question remains relevant on current main: URL consent occurs before the destination is known, while the existing-file check happens later in the filename picker. This team-authored Backlog request should remain open for a product decision about how repeated links are recognized and presented.

## Change summary

Detect that a customization file from a repeated install link already exists and surface that state before asking the user to accept a redundant installation.

## Best solution

Define duplicate-install semantics for customization links, then present the existing-file outcome at the earliest safe point without accessing an untrusted remote URL before consent or weakening the destination-specific collision check.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/promptSyntax/promptUrlHandler.ts`, `src/vs/workbench/contrib/chat/browser/promptSyntax/pickers/askForPromptName.ts`, `src/vs/workbench/contrib/chat/test/browser/promptSyntax/promptUrlHandler.test.ts`
- **Validation:** Add prompt URL handler tests covering a repeated link whose inferred filename exists and a link installed to a different name or destination, asserting the agreed dialog sequence and that no existing file is overwritten.
- **Behavior:**

  > Opening a customization install link that resolves to an already-existing destination must surface that state before the user completes a redundant installation, and the existing file must not be overwritten. A repeated link must remain installable under a different valid name or destination if that is part of the chosen product behavior. Acceptance tests must cover both the collision and non-collision flows while preserving the security consent required before remote content is accessed.
- **Trace:**

  > PromptUrlHandler.handleURL in src/vs/workbench/contrib/chat/browser/promptSyntax/promptUrlHandler.ts currently shows shouldBlockInstall first, fetches the remote content second, and only then asks for a source folder and filename. askForPromptFileName in src/vs/workbench/contrib/chat/browser/promptSyntax/pickers/askForPromptName.ts performs the actual fileService.exists check for the selected destination, so validation cannot precede the initial consent dialog under the current sequence. The final createFile call is non-overwriting, preserving the file-safety boundary. No existing prompt URL handler test was found, and no PR or older canonical issue owns this exact request. Do not weaken the rule that untrusted remote content is accessed only after explicit consent.
- **Open decisions:**
  - Does "the same link again" mean the same source URL was previously installed, or only that its inferred filename already exists in the destination the user would select?
  - Should an existing match suppress the initial URL-consent dialog, show a dedicated already-installed message, or continue to folder/name selection with the collision shown there?
  - If the same URL was installed under another name or in another customization folder, should that count as already installed or remain a valid separate installation?
