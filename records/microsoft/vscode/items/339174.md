# Issue #339174 — Keep default chat input permissions in sync across chat surfaces

[https://github.com/microsoft/vscode/issues/339174](https://github.com/microsoft/vscode/issues/339174)

## Summary

Confirmed from source: Editor chat and Agents Window each manage permission level independently — Editor chat seeds from `chat.permissions.default` and only writes per-session option state, while Agents Window writes the per-session approval config — neither writes back to a shared default, so a choice made in one surface never becomes the seed for the other. This is a real, reproducible gap, but closing it raises a product question (should a picker change silently rewrite a global user setting?) that a maintainer should weigh in on before implementation.

## Change summary

Changing the default chat input permission level (e.g. to Allow All) in one chat surface should carry over as the default in other chat surfaces.

## Best solution

Design a sync mechanism in src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts and src/vs/sessions/contrib/providers/agentHost/browser/agentHostPermissionPickerDelegate.ts so a permission-level change in either surface updates the shared seed (`ChatConfiguration.DefaultPermissionLevel` or an equivalent), scoped and gated appropriately (e.g. still respecting policy restrictions and `chat.tools.global.autoApprove`).

- **Validation:** A test asserting that changing the permission level in one chat surface's delegate updates the value a newly-created chat input in another surface seeds its default from.
- **Trace:**

  > Editor chat's `ChatInputPart.getDefaultPermissionLevel()` (chatInputPart.ts:1593) reads `ChatConfiguration.DefaultPermissionLevel` once to seed a new input's `_currentPermissionLevel`; `setPermissionLevel()` (line 1578) never writes that setting back, only a per-session option. Agents Window's `AgentHostPermissionPickerDelegate.setPermissionLevel()` (agentHostPermissionPickerDelegate.ts:281) writes only the active session's approval config value via the provider, not any shared default. Where the uncertainty starts: should either path update `chat.permissions.default` (or an equivalent cross-surface store) automatically, at what scope (global vs. workspace), and how this interacts with `chat.tools.global.autoApprove` and policy-restricted levels (`isAutoApprovePolicyRestricted`) — none of this is decided in the issue or the code today.
- **Open decisions:**
  - Should a permission-level change in one chat surface automatically update the persisted `chat.permissions.default` user/workspace setting, or only propagate at runtime to currently-open surfaces?
  - If it writes to settings, at what scope (user vs. workspace) and should it respect existing policy restrictions the same way the per-surface pickers already do?
  - Does this syncing apply to Agents Window sessions' per-session approval config too, or only to the shared 'default for new sessions' seed?

## Evidence

- **Editor chat seeds from config only:** src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts:1593-1596 `getDefaultPermissionLevel()` reads `ChatConfiguration.DefaultPermissionLevel` (chat.permissions.default); `setPermissionLevel()` at line 1578 only sets the in-memory observable and the per-session option (`chatSessionsService.setSessionOption`), never writing that config back.
- **Agents Window writes per-session only:** src/vs/sessions/contrib/providers/agentHost/browser/agentHostPermissionPickerDelegate.ts:281-306 `setPermissionLevel()` writes the approval value into that session's own config (`provider.setSessionConfigValue`) and never touches `ChatConfiguration.DefaultPermissionLevel` or `defaultSettingKey` (`ChatConfiguration.DefaultConfiguration`, line 96).
- **No shared write-through:** No reference to `ChatConfiguration.DefaultPermissionLevel` as a write target exists in either file or in chatSessionsService — confirmed via rg across src/vs/workbench/contrib/chat and src/vs/sessions.
