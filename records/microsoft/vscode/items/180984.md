# Issue #180984 — Reopening a file (notebook) should open it as a notebook instead of as a text file

[https://github.com/microsoft/vscode/issues/180984](https://github.com/microsoft/vscode/issues/180984)

## Summary

This accepted Backlog feature request remains necessary: current history entries preserve the text-editor override even after a newly installed extension registers a more appropriate notebook editor. The item is team-authored, no fixing commit is identifiable, and the older related issue reports a different observable symptom, so it must remain open.

## Change summary

When reopening a file from Quick Open history after installing its notebook provider, resolve it as a notebook instead of preserving the earlier text-editor fallback.

## Best solution

Quick Open history should preserve deliberate editor choices while allowing files previously opened through an automatic fallback to be re-resolved when the available editor registrations change. The workbench history and editor-resolver owners should settle how automatic versus explicit choices are represented before implementation.

- **Behavior:**

  > A resource initially opened as text because its notebook provider is unavailable should reopen with the appropriate notebook editor after that provider becomes available. A deliberate editor choice made through “Reopen Editor With” must retain the persistence behavior selected by the maintainer. Acceptance should cover both the automatic-fallback transition and the explicit-choice case without changing normal Quick Open history ordering.
- **Trace:**

  > HistoryService in src/vs/workbench/services/history/browser/historyService.ts converts file-backed EditorInput instances to untyped history entries through EditorHelper.preferResourceEditorInput. FileEditorInput.toUntyped in src/vs/workbench/contrib/files/browser/editors/fileEditorInput.ts stores the current editor ID as `options.override`, and AnythingQuickAccess in src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts reuses that history entry. EditorResolverService in src/vs/workbench/services/editor/browser/editorResolverService.ts honors the stored override before default resolution, even when later extension registration adds a more suitable editor. The resolver already exposes registration-change events and editor matching, but the history path does not distinguish an automatically selected fallback from a user-explicit override. Preserve history ordering, unrelated custom-editor choices, and ordinary Explorer opens; https://github.com/microsoft/vscode/issues/166161 concerns an untitled-cell URI resolution problem and is outside this boundary.
- **Open decisions:**
  - When the matching editor set changes, should Quick Open always re-resolve the resource, or only re-resolve entries whose stored editor was selected automatically rather than explicitly by the user?
  - If an explicitly selected editor is later unregistered and then registered again, should its preference remain sticky across that interval or be replaced by the current default?
