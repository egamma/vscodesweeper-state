# Issue #236300 — CTRL+A randomly breaks in Jupyter notebooks

[https://github.com/microsoft/vscode/issues/236300](https://github.com/microsoft/vscode/issues/236300)

## Summary

Keep open as the established report for notebook selection commands losing the correct focus context. Multiple commenters confirmed the output-right-click trigger and workaround, and the latest report still observes the failure; no verified fix or older canonical was found.

## Change summary

After interacting with notebook outputs, Ctrl+A and other editor shortcuts can stop operating on the active code cell.

## Best solution

Restore reliable command routing when focus returns from notebook outputs or their context menus to a cell editor, while preserving output selection and notebook-container shortcuts. Diagnose the focus-event sequence before choosing a bounded fix in the notebook editor/webview integration.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/notebook/browser/notebookEditorWidget.ts`
- **Validation:** In a notebook with a multiline code cell and rendered output, right-click the output, dismiss its menu, click into the code editor, and press Ctrl+A. Repeat across cells and menu interactions while recording keybinding troubleshooting output and notebookOutputFocused. Acceptance: all text in the active editor is selected; Escape dismisses editor suggestions before leaving edit mode; Ctrl+A still selects output text when output actually has focus and cells when the notebook container has focus.
- **Behavior:**

  > Interacting with a notebook output context menu must not leave subsequent cell-editor shortcuts routed to output or container commands. Once the code editor has focus, Ctrl+A must select its text and Escape must retain normal editor behavior. Preserve the existing distinct Select All behaviors for output focus and notebook-container focus. Repeated output-menu-to-editor transitions should not require More Actions, reopening the notebook, or changing keybindings to recover.
- **Trace:**

  > NotebookEditorWidget binds NOTEBOOK_OUTPUT_FOCUSED to its scoped context service in src/vs/workbench/contrib/notebook/browser/notebookEditorWidget.ts. Its webview focus and blur subscriptions set and clear _outputFocus; focusNotebookCell also sets it when entering output focus, but its editor branch does not explicitly clear it. Discussion-confirmed reproduction starts with right-clicking an output, and the related logs at https://github.com/microsoft/vscode/issues/241024 show notebook.cell.output.selectAll winning dispatch when the reporter expects cell text selection. This identifies the focus/context synchronization boundary, not a conclusive source-level root cause: establish whether context-menu transitions suppress, reorder, or otherwise invalidate the expected focus notifications. Preserve legitimate output and container command routing rather than removing keybinding conditions. https://github.com/microsoft/vscode/issues/338182 supplies related Linux symptoms, but its drag-selection failures are not yet proven to have the same cause.
