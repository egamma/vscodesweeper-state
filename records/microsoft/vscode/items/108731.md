# Issue #108731 — Remote-SSH & WSL: Support trash

[https://github.com/microsoft/vscode/issues/108731](https://github.com/microsoft/vscode/issues/108731)

## Summary

Keep this accepted, well-supported request open: current remote filesystem providers still lack trash support, and files.enableTrash cannot enable a capability the provider does not implement. This issue already owns the SSH/WSL work; recovery workarounds and the newer confirmation-dialog request do not replace it.

## Change summary

Support recoverable deletion of files and folders to trash in Remote-SSH and WSL workspaces.

## Best solution

Provide remote-side trash support integrated with the existing filesystem capability and Explorer deletion flow. Agree on remote trash location and unsupported-environment behavior before implementation, preserving explicit permanent deletion and local trash behavior.

## Plan brief

- **Likely files:** `src/vs/server/node/remoteFileSystemProviderServer.ts`, `src/vs/platform/files/node/diskFileSystemProvider.ts`, `src/vs/platform/files/common/diskFileSystemProviderClient.ts`, `src/vs/workbench/services/remote/common/remoteFileSystemProviderClient.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/browser/fileActions.ts`
- **Validation:** In an Ubuntu Remote-SSH workspace and a WSL workspace with files.enableTrash=true, delete a file and a non-empty folder through Explorer and verify both can be restored from the agreed trash destination. Verify explicit permanent deletion and files.enableTrash=false still delete permanently, local trash behavior is unchanged, and an unavailable or failing remote trash facility never silently performs permanent deletion.
- **Behavior:**

  > Remote-SSH and WSL users currently receive permanent deletion rather than the recoverable trash deletion available locally. The requested capability must cover files and non-empty folders through the normal Explorer deletion flow. Acceptance requires restoring their contents from the agreed trash destination, preserving explicit permanent deletion and the files.enableTrash setting, and making unavailable or failed trash operations clear to the user. Undo and Local History alone do not satisfy persistent trash recovery.
- **Trace:**

  > ExplorerView requires files.enableTrash and FileSystemProviderCapabilities.Trash to expose trash deletion. RemoteFileSystemProviderClient constructs DiskFileSystemProviderClient without its optional trash capability, and RemoteAgentFileSystemProviderChannel constructs a Node DiskFileSystemProvider whose delete path implements removal rather than trash. The local Electron channel has a separate shell.trashItem implementation, so enabling the client capability alone would not implement remote recovery. The unresolved boundary is which remote trash facility and restoration contract to support, particularly on headless SSH hosts and WSL. Preserve local Electron deletion and explicit permanent deletion; unrelated confirmation suppression is tracked at https://github.com/microsoft/vscode-remote-release/issues/5615. https://github.com/microsoft/vscode/issues/107233 was consolidated into this issue, and the thread's trash-cli extension demonstrates a workaround rather than built-in adoption.
- **Open decisions:**
  - Should WSL and SSH deletion target the remote operating system's trash, a VS Code-managed recoverable store, or a configurable destination; is Windows Recycle Bin integration part of the WSL scope?
  - When no usable remote trash facility exists, should Explorer retain permanent-delete-only behavior or offer a managed recoverable alternative?

## Evidence

- **Accepted community demand:** https://github.com/microsoft/vscode/issues/108731 has 81 body upvotes and the Backlog milestone; the October 2020 bot comment records promotion after sufficient community support. The fully read policy at https://github.com/microsoft/vscode/wiki/Issues-Triaging describes Backlog as accepted work and promotion at 20+ upvotes.
- **Existing setting does not supply remote support:** src/vs/workbench/contrib/files/browser/files.contribution.ts registers files.enableTrash with default true. In src/vs/workbench/contrib/files/browser/views/explorerView.ts:759-762, the Explorer trash context requires both that setting and FileSystemProviderCapabilities.Trash. RemoteFileSystemProviderClient's constructor in src/vs/workbench/services/remote/common/remoteFileSystemProviderClient.ts supplies only pathCaseSensitive, not trash; src/vs/platform/files/common/diskFileSystemProviderClient.ts adds the Trash capability only when extraCapabilities.trash is enabled.
- **Remote backend gap remains:** RemoteAgentFileSystemProviderChannel in src/vs/server/node/remoteFileSystemProviderServer.ts constructs the Node DiskFileSystemProvider. Its capabilities in src/vs/platform/files/node/diskFileSystemProvider.ts omit Trash, and its delete method performs recursive removal or unlink/rmdir without a trash branch. By contrast, src/vs/platform/files/electron-main/diskFileSystemProviderServer.ts overrides deletion to call Electron shell.trashItem. The inspected source therefore does not satisfy the requested remote recoverable deletion.
- **Canonical ownership:** https://github.com/microsoft/vscode/issues/107233 is closed, and a maintainer explicitly marked it duplicate of this issue: https://github.com/microsoft/vscode/issues/107233#issuecomment-721393454. https://github.com/microsoft/vscode-remote-release/issues/5615 is open but was created in 2021, later than this report, and also requests confirmation suppression. It is related, not an older canonical satisfying the re-review duplicate bar. Open-issue searches for remote trash, WSL trash, and remote recycle-bin support found no verified older canonical owning this request.
- **Workarounds do not complete the request:** The supplied discussion reports recovery through Undo and server-side Local History, but also reports limitations recovering folders. The June 2025 comment says https://github.com/2bitbit/trash4wsl-in-vscode supports SSH as well as WSL by executing trash-cli remotely through a separate context-menu action. This is a useful optional workaround, not built-in Explorer/provider support or a maintainer decision to decline the accepted request.
- **Core boundary:** Although SSH and WSL connections are supplied by Remote Development extensions, the inspected deletion backend and Explorer capability handling live in microsoft/vscode. The discussion also records that this issue was transferred from the remote tracker, and a maintainer consolidated the WSL report here; transferring it back would not address the identified core gap.
