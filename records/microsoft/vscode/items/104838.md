# Issue #104838 — Git - Clone to an alternate directory name

[https://github.com/microsoft/vscode/issues/104838](https://github.com/microsoft/vscode/issues/104838)

## Summary

Keep this accepted, well-supported request open: the interactive clone flow still selects a parent directory without allowing a custom repository folder name. The existing git area label is appropriate, and no verified canonical or completed implementation supersedes it.

## Change summary

Allow users to choose the repository's destination folder name when cloning through VS Code.

## Best solution

Expose an editable clone destination in the built-in Git workflow, retaining the repository-derived name as the default. Settle the destination-selection interaction before implementation; changing how already-open folders follow external renames is outside this request.

## Plan brief

- **Likely files:** `extensions/git/src/cloneManager.ts`, `extensions/git/src/commands.ts`, `extensions/git/src/git.ts`, `extensions/git/src/test/cloneManager.test.ts`
- **Validation:** Extend the CloneManager suite to verify that an explicitly chosen name reaches the clone operation and determines the returned repository path, while accepting the default preserves repository-derived naming and cancelling prevents cloning. Manually clone a repository named repo.git into a chosen parent with the name my-repo and verify that the resulting folder and subsequent Open action use parent/my-repo, not parent/my-repo/repo; repeat with Git: Clone (Recursive).
- **Behavior:**

  > Users cloning through VS Code can choose a destination folder name different from the repository's URL-derived name. For example, cloning repo.git with the chosen name my-repo produces parent/my-repo, without an additional repo child directory. Accepting the default retains the familiar repository-derived name, and cancelling destination selection creates no clone. Opening or adding the finished clone uses its actual destination. Both ordinary and recursive interactive cloning should offer consistent destination semantics.
- **Trace:**

  > git.clone and git.cloneRecursive in extensions/git/src/commands.ts delegate to CloneManager in extensions/git/src/cloneManager.ts. Its cloneRepository method selects a parentPath and invokes Git.clone without targetName, so extensions/git/src/git.ts derives the child name from the URL. The low-level ICloneOptions already supports targetName, and _git.cloneRepository supplies it from an explicit localPath; these internal capabilities do not expose naming in the interactive workflow. Existing CloneManager tests in extensions/git/src/test/cloneManager.test.ts provide a starting harness for clone-call and post-clone behavior. Preserve recursive/ref handling, cancellation, existing-clone reuse, and the default naming behavior; do not expand this work into tracking externally renamed workspace roots. The latest skipped-dialog comment may involve cache reuse or a separate defect and is not a prerequisite for this feature. The remaining product uncertainty is whether naming becomes an additional editable step or part of choosing the full destination.
- **Open decisions:**
  - Should interactive cloning retain the parent-folder picker and add an editable repository-name step, or replace it with a picker for the full destination path?
