# Issue #190917 — Hot reload in extension development - automatically reload the Extension Development Host window

[https://github.com/microsoft/vscode/issues/190917](https://github.com/microsoft/vscode/issues/190917)

## Summary

This remains a valid, well-supported Backlog feature request: 80 community upvotes establish demand, and the discussion indicates that current workflows still require manual Extension Development Host reloads or external development harnesses.

## Change summary

Automatically reload the Extension Development Host when extension or webview source changes during development.

## Best solution

Provide an opt-in extension-development workflow that watches built extension output and safely reloads the Extension Development Host, while preserving the existing manual reload command and avoiding reload loops; webview-only hot module replacement should remain compatible but independently controlled.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugExtensionHostAction.ts`, `src/vs/workbench/api/node/extensionHostProcess.ts`, `src/vs/workbench/services/extensions/common/extensionHostManager.ts`
- **Validation:** Launch an Extension Development Host from an extension workspace, modify and rebuild its extension output, and verify the host reloads once without manual input; confirm ordinary non-extension debug sessions and the existing manual reload command remain unchanged.
- **Behavior:**

  > During an extension-development debug session, saving and rebuilding extension code can opt into automatically reloading the Extension Development Host so the new code becomes active without Ctrl+Shift+F5. A single output change must cause at most one reload, and failed or incomplete builds must not create a reload loop. Existing manual reload behavior remains available. Webview HMR may refresh independently without forcing unnecessary host reloads.
- **Trace:**

  > The issue concerns the Extension Development Host debug lifecycle and extension-host restart path, likely spanning src/vs/workbench/contrib/debug/browser/debugExtensionHostAction.ts, src/vs/workbench/api/node/extensionHostProcess.ts, and src/vs/workbench/services/extensions/common/extensionHostManager.ts. The report establishes that Ctrl+Shift+F5 currently performs the needed reload manually, while webview tooling only refreshes renderer content. The uncertainty begins at watcher ownership and reload triggering: VS Code could observe built extension output, coordinate with an extension build task, or expose a development-only mechanism used by tooling. The boundary is extension-development sessions only; normal debug sessions, production extension hosts, activation semantics, and existing manual reload behavior must not change. Related context: https://github.com/microsoft/vscode/issues/93146.
- **Open decisions:**
  - Should VS Code watch compiled extension output itself, or should build tooling signal that a successful build is ready to reload?
  - How should automatic reload be opted into and scoped so ordinary extension-development sessions retain current behavior?
  - Should webview changes reload only the webview when HMR is available, while extension-host output changes reload the full Extension Development Host?
  - What debounce and failure behavior prevents partial builds or rapid output changes from causing repeated reloads?
