# Issue #190917 — Hot reload in extension development - automatically reload the Extension Development Host window

[https://github.com/microsoft/vscode/issues/190917](https://github.com/microsoft/vscode/issues/190917)

## Summary

The central request remains unimplemented on current main and has been accepted into the Backlog with 80 community upvotes. Existing commands can manually restart the debug session or reload webviews, but no built-in watcher automatically restarts an Extension Development Host after extension output changes.

## Change summary

Automatically reload an Extension Development Host when an extension's compiled code or webview assets change during development.

## Best solution

Provide an opt-in extension-development workflow that watches selected build outputs, debounces changes, and restarts the active Extension Development Host while coordinating independently reloadable webview content.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugCommands.ts`, `src/vs/workbench/contrib/debug/browser/debugService.ts`, `src/vs/workbench/contrib/debug/common/debug.ts`
- **Validation:** Exercise an Extension Development Host launch with automatic reload enabled, modify a configured compiled output, and verify exactly one debounced session restart occurs; verify unrelated workspace changes and configurations without the option do not restart, and existing manual restart behavior remains unchanged.
- **Behavior:**

  > Extension authors can opt into automatic reload for an Extension Development Host debugging session. Saving or rebuilding a configured extension output triggers one debounced restart without requiring Ctrl/Cmd+Shift+F5; unrelated files do not restart the session. Existing projects remain manual by default unless maintainers explicitly choose an automatic default, and manual restart continues to work. Webview-only updates should retain their faster independent reload path when a host restart is unnecessary.
- **Trace:**

  > The manual entry point is `RESTART_SESSION_ID` in src/vs/workbench/contrib/debug/browser/debugCommands.ts, which resolves the focused debug session and calls `IDebugService.restartSession`. In src/vs/workbench/contrib/debug/browser/debugService.ts, `restartSession` recognizes extension-host sessions through `getExtensionHostDebugSession` and delegates to `IExtensionHostDebugService.reload`; this path already handles restart tasks but has no file-change trigger. Webview refresh is separate in `ReloadWebviewAction` at src/vs/workbench/contrib/webviewPanel/browser/webviewCommands.ts and only invokes `webview.reload()`. Preserve existing manual restart, task sequencing, non-extension debug sessions, and webview-only reload behavior. The uncertainty begins at the public opt-in and watch contract: which paths count as completed build output, how multiple changes are coalesced, and whether a host restart or full development-window reload is promised.
- **Open decisions:**
  - Should automatic reload be enabled through an explicit launch-configuration option, another extension-development setting, or by default for Extension Development Host sessions?
  - Should users configure the watched build outputs, or should VS Code infer them from extension metadata and build tasks?
  - Does the feature contract promise restarting only the extension-host debug session, or reloading the entire Extension Development Host window?

## Evidence

- **accepted demand:** https://github.com/microsoft/vscode/issues/190917 has 80 community upvotes, and https://github.com/microsoft/vscode/issues/190917#issuecomment-1763242731 records that it passed the community threshold and was moved to the Backlog.
- **current restart path:** src/vs/workbench/contrib/debug/browser/debugCommands.ts registers `workbench.action.debug.restart` behind Ctrl/Cmd+Shift+F5 and explicitly calls `IDebugService.restartSession`; src/vs/workbench/contrib/debug/browser/debugService.ts then calls `extensionHostDebugService.reload` for an extension-host session. No source-change watcher is connected to that path.
- **webview capability is partial:** src/vs/workbench/contrib/webviewPanel/browser/webviewCommands.ts registers `workbench.action.webview.reloadWebviewAction`, which reloads current webviews but does not rebuild or restart the host extension.
- **related issue boundary:** https://github.com/microsoft/vscode/issues/93146 was closed as out of scope specifically for framework-managed webview-content hot reload; its maintainer response points to the Reload Webviews command and does not cover automatic Extension Development Host restart.
- **unloading precedent is distinct:** https://github.com/microsoft/vscode/issues/199026 declined safely unloading extension code in-place because extension side effects cannot be comprehensively reversed. The present request instead permits restarting the Extension Development Host window, so that precedent does not decide its full scope.
