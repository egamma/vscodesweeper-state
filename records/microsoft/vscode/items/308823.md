# Issue #308823 — Copilot Chat: SSE stream inactivity timeout (60s) should be configurable — causing mid-stream failures under backend congestion

[https://github.com/microsoft/vscode/issues/308823](https://github.com/microsoft/vscode/issues/308823)

## Summary

The original hardcoded 60-second timeout is no longer present on main, but the underlying streaming-resilience gap remains: the current Messages and Responses SSE loops have no explicit idle policy or configurable timeout. This should stay open and be routed to the chat networking/request-failure owners.

## Change summary

Define a resilient, configurable policy for stalled Copilot SSE streams and ensure recoverable HTTP/2 GOAWAY failures do not terminate the active request.

## Best solution

Establish one streaming-idle and recovery policy across the Messages and Responses API paths, deciding whether users need a setting or whether retry and centrally managed limits provide a better experience. Validate the separately reported GOAWAY retry mismatch against the current fetcher before including it in the same implementation.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/endpoint/node/messagesApi.ts`, `extensions/copilot/src/platform/endpoint/node/responsesApi.ts`, `extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts`, `extensions/copilot/src/platform/networking/common/networking.ts`, `extensions/copilot/package.json`
- **Validation:** Add endpoint tests with a controllable response body that emits an initial SSE chunk and then stalls; verify the chosen idle policy settles the turn within the configured limit, cancellation destroys the stream, and healthy streams remain unaffected. Add a networking test for the current GOAWAY error shape if that failure still reaches this retry layer.
- **Behavior:**

  > A Copilot streaming response that pauses indefinitely must not leave the turn hanging or fail at an undocumented hardcoded threshold. The product should apply a consistent, documented idle policy across supported SSE endpoints, with the chosen timeout or retry behavior observable to users. User cancellation must promptly terminate a stalled stream, while healthy long-running streams continue normally. Recoverable HTTP/2 GOAWAY failures should follow the agreed retry behavior rather than surfacing immediately.
- **Trace:**

  > Current main no longer contains the reported bundled 60-second timer. Instead, processResponseFromMessagesEndpoint in extensions/copilot/src/platform/endpoint/node/messagesApi.ts and processResponseFromChatEndpoint in responsesApi.ts directly await response.body chunks without an idle guard. ChatEndpoint.processResponseFromChatEndpoint accepts a CancellationToken but drops it for both paths. A later report, https://github.com/microsoft/vscode/issues/321432, confirms the resulting indefinite-stall failure; an observe-only watchdog was merged in f8574878be86c229f5d9710cdde25354bff25dde and reverted in f1339a4faf544e6c6435ed1692a96e3cb55a10ac. Keep the scope to stream lifecycle and network recovery; do not alter model parsing or normal completion semantics. The reported GOAWAY error originated in an older generated bundle, so its exact current error shape must be confirmed before changing the retry classifier.
- **Open decisions:**
  - Should stream idleness be controlled by a user-visible setting, or by a centrally managed/adaptive timeout with no new configuration surface?
  - When the idle limit is reached, should the current turn fail immediately or be replayed automatically after disconnecting the stale connection?
  - Should the same idle policy apply to every Messages and Responses API endpoint, including custom/BYOK endpoints, or only GitHub-hosted Copilot requests?
