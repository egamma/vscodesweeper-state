# Issue #163582 — Git - Remote WSL2 git.path does not respect Windows Git.exe

[https://github.com/microsoft/vscode/issues/163582](https://github.com/microsoft/vscode/issues/163582)

## Summary

Keep open for the Git owner: the configured executable is honored, but repository discovery fails when using Windows Git from WSL2. Current source includes additional repository-path normalization, but it does not establish that the reported initial rev-parse failure is fixed; the supplied steps and logs suffice to retest.

## Change summary

Using Windows git.exe through git.path in a WSL2 window prevents the built-in Git integration from discovering an existing repository.

## Best solution

Reproduce repository discovery with Windows Git launched by the WSL extension host, comparing its working directory and environment with the successful terminal invocation. Resolve the confirmed interoperability failure in the built-in Git execution/discovery path while preserving native Linux Git behavior.

## Plan brief

- **Likely files:** `extensions/git/src/git.ts`, `extensions/git/src/model.ts`
- **Validation:** In a Windows 11 WSL2 remote window, open a repository where terminal git.exe rev-parse --show-toplevel succeeds, configure git.path to /mnt/c/Program Files/Git/bin/git.exe, and verify that SCM discovers the repository and displays a deliberately modified tracked file. Repeat with native WSL Git; test both a /mnt/c repository and a repository in the WSL filesystem to establish the supported boundary.
- **Behavior:**

  > The reporter can use Windows Git successfully from a WSL2 terminal, but selecting the same executable for VS Code leaves the repository absent from SCM. Establish whether the same repository can be discovered through the built-in Git integration and whether tracked changes appear. Acceptance requires comparing terminal and extension-host execution for the same repository, with native WSL Git remaining unaffected.
- **Trace:**

  > In extensions/git/src/git.ts, findGit accepts the configured executable, Git.spawn invokes this.path, and Git._exec uses a generic git prefix in logs. Git.getRepositoryRoot first executes rev-parse --show-toplevel; its relative-path fallback only runs after that command succeeds, so it does not address the logged initial failure. In extensions/git/src/model.ts, Model.openRepository catches discovery failure before exposing an SCM repository. The uncertainty starts at Windows Git's working directory and environment when invoked through WSL interoperability; the source alone does not prove the cause. Preserve native Git discovery and avoid expanding the investigation into signing or Yubikey support: signing is the motivation, not the failing operation. The report is https://github.com/microsoft/vscode/issues/163582; https://github.com/microsoft/vscode/issues/275989 describes a different cross-environment worktree configuration failure.

## Evidence

- **Reported trigger and failure:** https://github.com/microsoft/vscode/issues/163582 supplies Windows 11, WSL2, VS Code 1.73.0-insider, the configured /mnt/c/Program Files/Git/bin/git.exe executable, and logs showing successful version detection followed by rev-parse --show-toplevel failing with 'not a git repository'. The reporter says terminal invocation of git.exe works; no comments independently confirm reproduction.
- **Executable selection is honored:** extensions/git/src/git.ts: findGit validates configured hints through findSpecificGit; Git.spawn executes cp.spawn(this.path, args, options). Git._exec formats command logs with the literal '> git', so that log prefix does not indicate that the configured executable was ignored.
- **Current discovery path:** extensions/git/src/git.ts:504-525 runs rev-parse --show-toplevel before attempting relative-path normalization. Git.exec passes the repository directory as cwd; Git.spawn and sanitizePath only normalize Windows drive-letter case, with no explicit WSL interoperability conversion on this path. These facts identify the investigation boundary, but cannot establish Windows executable working-directory behavior without WSL.
- **Why discovery disappears:** extensions/git/src/model.ts: Model.openRepository calls getRepositoryRoot before creating the repository and catches discovery failures with a trace log. This matches the reported missing SCM repository, without proving the underlying cause of git.exe's failure.
- **Canonical search:** Repository issue searches for WSL with git.path, Windows Git, and git.exe with 'not a git repository' found no verified open canonical for this behavior. https://github.com/microsoft/vscode/issues/275989 was read and concerns Windows cloning that writes an absolute core.worktree path subsequently rejected by Linux Git, rather than Windows Git repository discovery from a WSL extension host.
- **Fix not established:** Inspection of the current discovery and spawn code, Git-file history, and commit-message searches for this issue and WSL/Git fixes did not identify a concrete behavior-changing fix for the reported trigger. No runtime reproduction was attempted because the checkout is read-only and the available host is macOS.
