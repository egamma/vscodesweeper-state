# Issue #349963 — Editor window: feed the agent-host session list of ChatSessionsService from the sessions provider (one source of truth)

[https://github.com/microsoft/vscode/issues/349963](https://github.com/microsoft/vscode/issues/349963)

## Summary

Keep open: the editor-window controller still projects its items and changes from a separate session-list store. The batching change bounds downstream work but does not establish one source of truth; provider lifetime remains an explicit design decision.

## Change summary

Source editor-window agent-host chat session items from the sessions provider when the new sessions list is enabled, preserving the existing path when disabled.

## Best solution

Share the provider-backed session list with IChatSessionsService while preserving item metadata, child chats, controller actions, and availability to hidden-view consumers. Settle provider lifetime before implementation and retain the store where actions and moved-chat tracking still require it.

Extend editorWindowSessionsRuntime tests for the chosen hidden-view lifetime contract, and check that disabling the new list preserves the store-backed path and controller actions.
- **Behavior:**

  > With the new sessions list enabled in a local editor window, IChatSessionsService consumers should receive the provider-backed session list and its change feed. Labels, status, archived/read state, activity, timing, changes, metadata and visible child chats must remain equivalent to the existing projection. Session lookup and in-progress information must remain available while the Chat view and chat part are hidden. Turning the setting off must preserve existing behavior, including controller actions and moved-chat handling.
- **Trace:**

  > AgentHostSessionListContribution creates a separate AgentHostSessionListStore outside the Agents window. AgentHostSessionListController reads that store in items and projects its events through _projectDelta; _makeItemFromSummary and _makeItem establish the existing conversion contract. BaseAgentHostSessionsProvider already exposes a debounced and filtered onDidChangeSessions feed. EditorWindowSessionsRuntime._update releases its provider hold when relevant surfaces are hidden, which prevents assuming providers are permanently available. The uncertainty starts at the lifetime contract, not at whether duplication exists. Preserve store-dependent actions, moved-chat catalog behavior, existing resource identities and the setting-disabled path. https://github.com/microsoft/vscode/pull/349478 addresses downstream batching, not this consolidation.
- **Open decisions:**
  - When the new list is enabled but all session surfaces are hidden, should providers remain held and live, or should IChatSessionsService switch to a store-backed source while preserving uninterrupted items and avoiding false deltas?

## Evidence

The controller's items getter reads getSessions(), and its change event projects the store's onDidChangeSessions.
- **Independent notification processing:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionListStore.ts subscribes directly to the connection's onDidNotification at line 135 and handles root/sessionSummaryChanged at line 443. Separately, BaseAgentHostSessionsProvider exposes its own debounced and filtered onDidChangeSessions feed.
- **Lifetime decision confirmed:** src/vs/workbench/contrib/sessions/browser/editorWindow/editorWindowSessionsRuntime.ts acquires providers only while a configured view or the chat part is visible, and clears its hold otherwise. agentsViewProviders.ts explicitly documents that sessions are known only while providers are held.
- **Mapping and action boundary:** AgentHostSessionListController._makeItemFromSummary and _makeItem currently derive status, read/archive state, activity, timing, changes, metadata and visible peer-chat children from summaries. Actions and _resolveChat also access the store, so replacing list reads does not make the store removable.
