# Issue #334871 — Quick chat that is associated with workspace cannot change workspace

[https://github.com/microsoft/vscode/issues/334871](https://github.com/microsoft/vscode/issues/334871)

## Summary

This remains a real feature gap on current main: workspace attachment is intentionally implemented as a one-time workspace-less-to-workspace conversion, so an attached chat cannot transition again. The team-authored request is accepted in the Backlog and should stay open for workspace-transition design.

## Change summary

Allow a Quick Chat that has already attached to one workspace to change its current workspace while preserving the conversation.

## Best solution

Support a safe in-place workspace transition for an existing default chat, preserving its identity and history while consistently updating provider state, workspace metadata, customizations, changes, trust, and worktree ownership.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/chatContributions/sessionWorkspaceConversion/sessionWorkspaceConversionService.ts`, `src/vs/platform/agentHost/node/agentService.ts`, `src/vs/platform/agentHost/node/shared/sessionServerTools.ts`, `src/vs/platform/agentHost/test/node/sessionWorkspaceConversion.test.ts`, `src/vs/platform/agentHost/test/node/sessionServerTools.test.ts`
- **Validation:** Add focused unit coverage that attaches a workspace-less session to workspace A, keeps `set_workspace` available under the chosen product contract, transitions the same session and chat to workspace B, and verifies identity/history preservation plus authoritative workspace metadata, trust, worktree cleanup, customization refresh, and rollback on failure.
- **Behavior:**

  > A Quick Chat that has attached to workspace A can request workspace B without creating a replacement conversation. Its session and chat identity, title, transcript, and pending user task remain intact, and subsequent tools operate only in the newly selected workspace. The transition must communicate progress and failure as the initial attachment does, and a failed transition must leave the previous workspace usable and authoritative.
- **Trace:**

  > Current workspace changes flow through `set_workspace` in src/vs/platform/agentHost/node/shared/sessionServerTools.ts and `SessionWorkspaceConversionService` in src/vs/platform/agentHost/node/chatContributions/sessionWorkspaceConversion/sessionWorkspaceConversionService.ts. `AgentService._createSessionServerToolAccessor` exposes the tool only while `readSessionWorkspaceless` is true, and `_validateConversion` independently enforces that same one-way boundary. The successful conversion clears the workspace-less marker, persists workspace-transition metadata, refreshes server tools and customizations, and explicitly prevents another conversion. Provider working-directory mutation already exists, but the current transaction and rollback logic assumes the old directory is disposable workspace-less scratch state; the uncertainty starts where an established workspace or managed worktree must be replaced without losing or misattributing changes. Preserve the existing confirmation, workspace-trust, deferred-turn, and failure-reporting contracts; do not broaden this into arbitrary peer-chat or multi-root restructuring. The originating test plan is https://github.com/microsoft/vscode/issues/334457.
- **Open decisions:**
  - When the current workspace has edits or an owned worktree, should switching be blocked, retain the old workspace in the session, or detach and clean it up after an explicit warning?
  - After switching, should the previous workspace and its changes remain visible in the session-wide workspace and changes surfaces, or should workspace B fully replace workspace A?
  - Should repeated workspace transitions be exposed only for providers that already support mutable working directories, or become a required cross-provider Agents Window behavior?
