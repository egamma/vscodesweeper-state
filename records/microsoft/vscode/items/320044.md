# Issue #320044 — Remote session/task persistence: Detach, preserve, and reattach all active tasks, terminals, and extension processes in VS Code Remote

[https://github.com/microsoft/vscode/issues/320044](https://github.com/microsoft/vscode/issues/320044)

## Summary

Keep this accepted Backlog request open: existing terminal and task reconnection covers only part of the requested independent remote-session lifecycle. The 49 upvotes establish demand, and the verified related issues do not own its full scope.

## Change summary

Allow remote workspace activity to survive client closure or extended disconnection and reattach with its running state and accumulated output intact.

## Best solution

Define a remote-session lifecycle independent of the client connection, with explicit retention and reattachment guarantees for terminals and tasks. Establish which extension work and debug connections can participate, distinguishing preservation of live execution from restoration of saved UI or output.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/terminal/browser/terminalService.ts`, `src/vs/workbench/contrib/terminal/common/terminalConfiguration.ts`, `src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts`, `src/vs/workbench/contrib/tasks/browser/task.contribution.ts`, `src/vs/workbench/api/node/extensionHostProcess.ts`
- **Validation:** On a remote workspace, start a terminal command and a background task that periodically append numbered output, detach or close the client, and reconnect after the configured grace interval. Verify execution continued without restarting, terminal/task identity is reattached, and disconnected-period output and completion status remain available. Separately exercise supported extension work and debugger sessions according to the agreed contract, and verify existing reload reconnection and explicit termination still behave as intended.
- **Behavior:**

  > Users want to leave a remote workspace without stopping its running terminals, tasks, and supported extension or debugger activity, then reconnect to the same live work and review output produced while absent. Restoring scrollback and starting replacement processes is not equivalent to preserving execution. Acceptance must cover deliberate client closure and a disconnection longer than the current grace interval, including a job that finishes while the client is away. Unsupported session types and retention limits need explicit, user-visible guarantees rather than a promise that every connection can always resume.
- **Trace:**

  > TerminalService in src/vs/workbench/contrib/terminal/browser/terminalService.ts already restores remote terminal layout through _reconnectToRemoteTerminals, but _onWillShutdown preserves eligible processes only for ShutdownReason.RELOAD. The terminal configuration distinguishes process revival from live preservation. task.reconnection is documented for reloads, and TerminalTaskSystem assigns reconnection metadata to background tasks. The socket-based extension-host path in src/vs/workbench/api/node/extensionHostProcess.ts schedules termination after connection loss and cancels those timers on reconnection. These source paths establish partial capability, not a complete diagnosis of debugger, forwarding, or arbitrary extension-process restoration. Preserve existing reload and explicit-termination behavior; the planning boundary is which activities acquire an independent remote lifecycle and how long that lifecycle lasts. https://github.com/microsoft/vscode/issues/318997 and https://github.com/microsoft/vscode/issues/324350 are related narrower efforts, not duplicate targets.
- **Open decisions:**
  - Should live remote-session preservation occur automatically on ordinary window close, or require an explicit detach action or opt-in?
  - Which activities are guaranteed to survive in the initial contract: shell terminals and tasks only, or also extension-owned work, debugger sessions, and forwarded connections?
  - What retention duration and termination controls should apply to detached execution and accumulated output?
  - When live reattachment is impossible, should reconnect show saved output and a stopped-session state, or offer an explicitly identified restart?

## Evidence

- **Existing capabilities are partial:** src/vs/workbench/contrib/terminal/common/terminalConfiguration.ts:554-571 registers terminal.integrated.enablePersistentSessions for window reloads and terminal.integrated.persistentSessionReviveProcess for restoring contents and recreating processes after shutdown. Recreation does not preserve a running build, training job, or debugger session. src/vs/workbench/contrib/terminal/browser/terminalService.ts:452-471 already reconnects remote terminals from stored layout information.
- **Client-close lifecycle gap:** src/vs/workbench/contrib/terminal/browser/terminalService.ts:705-720 detaches eligible terminal processes only when persistent sessions are enabled and the shutdown reason is RELOAD; other shutdown reasons dispose the instances. This does not provide the requested explicit detach-and-preserve behavior on window close.
- **Task and extension-host boundaries:** src/vs/workbench/contrib/tasks/browser/task.contribution.ts:549-553 describes task.reconnection as reconnecting tasks with problem matchers on window reload. terminalTaskSystem.ts:1593-1616 attaches reconnection metadata to background tasks. src/vs/workbench/api/node/extensionHostProcess.ts:215-262 terminates a disconnected extension host after its reconnection grace timer expires, rather than offering an independent durable session lifecycle.
