## Plan brief

- **Likely files:** `cli/src/auth.rs`, `cli/src/tunnels/dev_tunnels.rs`
- **Validation:** Run a Microsoft-authenticated Linux tunnel through both GUI and service startup for longer than the reported two-to-five-day failure window, recording credential-renewal and reconnect diagnostics without secrets. Verify access survives normal renewal and transient reconnects without manual restart; once the cause is isolated, add a deterministic regression check for that renewal or recovery sequence.
- **Behavior:**

  > A Linux tunnel that initially works becomes inaccessible after roughly two to five days, logging HTTP 401 while obtaining a host token. The reporter reproduced this with Microsoft authentication and both GUI and service startup; manual stop/start restores access. Normal credential renewal and recoverable disconnections should preserve unattended access without a GUI restart. Any unavoidable reauthentication requirement should be clearly distinguished from recoverable failure and have a documented supported recovery path.
- **Trace:**

  > LookupAccessTokenProvider::refresh_token in cli/src/tunnels/dev_tunnels.rs issues the host-token lookup and produces the reported error wording. ActiveTunnelManager::spawn_tunnel retries failed lookups and polls Auth::keep_token_alive, which lives in cli/src/auth.rs and maintains credentials separately. Auth::do_refresh_token supports Microsoft refresh grants, while keep_token_alive terminates on HTTP 4xx authentication failures. This traces the diagnostic but does not prove whether the delayed rejection originates in credential handling, service policy, or another condition; the first step is a current long-running reproduction. Preserve legitimate authentication rejection and do not introduce traffic-based keepalive workarounds without evidence. The closed discussion at https://github.com/microsoft/vscode/issues/230058 already considered hourly token activity and switching providers, and neither establishes a fix for this report.

## Evidence

- **Reported trigger and recovery:** https://github.com/microsoft/vscode/issues/236724 reports Linux tunnels failing after roughly two to five days with HTTP 401 during host-token lookup. Both GUI startup and `code tunnel service install` were tried; switching from GitHub to Microsoft authentication did not resolve it, while manually stopping and restarting the tunnel restored access.
- **Discussion already addresses the suggested workaround:** In https://github.com/microsoft/vscode/issues/230058#issuecomment-2408322367 a maintainer explains that the CLI already touches GitHub tokens hourly. https://github.com/microsoft/vscode/issues/230058#issuecomment-2539920421 says Microsoft authentication has a refresh endpoint. This report explicitly follows up with unsuccessful Microsoft-account testing, so repeating that suggestion would not answer it.
- **Current credential renewal:** cli/src/auth.rs, Auth::keep_token_alive, schedules renewal using credential expiry or an hourly default, stores refreshed credentials, and exits on authentication HTTP 4xx errors. Auth::do_refresh_token uses the refresh-token grant when available. These mechanisms establish intended automatic maintenance, not successful multi-day operation in the reported environment.
- **Matching diagnostic path:** cli/src/tunnels/dev_tunnels.rs, LookupAccessTokenProvider::refresh_token, requests a host token through get_tunnel and wraps failures as 'failed to lookup tunnel for host token'. ActiveTunnelManager::spawn_tunnel retries that failure with 'Error refreshing access token, will retry', matching the report. Source inspection alone does not establish why the service returns 401 after several days.

No verified canonical absorbs this report; https://github.com/microsoft/vscode/issues/230058 is closed and cannot serve as a duplicate target.
