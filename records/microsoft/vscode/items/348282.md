## Evidence

- **Current source confirms the race:** At checkout 9cc2376778e119f759ff710c1238fdc58d402d7a, src/vs/workbench/services/textfile/browser/textFileService.ts:436–498 awaits doSaveAsTextFile and then reverts the source without checking for intervening edits. doSaveAsTextFile copies sourceTextModel.createSnapshot() into the target and returns the asynchronous targetModel.save(), leaving the reported late-edit interval unguarded.
- **Destructive source lifecycle:** src/vs/workbench/services/untitled/common/untitledTextEditorModel.ts:292–306 clears the source contents, clears dirty state and fires onDidRevert. src/vs/workbench/services/untitled/common/untitledTextEditorInput.ts:72 disposes the input on that event. This explains why text accepted after the copied snapshot is neither saved to the target nor retained in the source.
- **Concrete application reproduction:** https://github.com/microsoft/vscode/issues/348282 documents official 1.147.0-insider macOS arm64 reproduction using the editor type command during a public save-participant gate, plus production-service reproduction and recovery controls. The extension exposes the timing; the destructive behavior is in core Save As handling.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/348284 is open, has no merged timestamp, and explicitly states Fixes #348282. Its proposed source-version preservation addresses this race; an unmerged proposal is not evidence that main is fixed.
