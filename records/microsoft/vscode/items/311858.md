# Issue #311858 — Improve multi-worktree workflows (grouping terminals, editors, and agents)

[https://github.com/microsoft/vscode/issues/311858](https://github.com/microsoft/vscode/issues/311858)

## Summary

The Agents Window already provides session-scoped terminals and editor restoration, but that only partially covers the requested worktree-centered workflow. Keep this accepted Backlog request open for a scoped design discussion; the linked implementation PR was closed without merging, and no verified older canonical absorbs the full request.

## Change summary

Treat each worktree, its terminals, editors, and parallel agents as a cohesive context that is easy to identify, switch, and review.

## Best solution

Build on existing Agents Window context restoration rather than duplicating it, and define the remaining worktree identity, running-activity overview, and cross-context review experience. First settle whether the context must also work independently of agent sessions in the regular workbench.

- **Behavior:**

  > Users working in parallel worktrees need to identify which terminals, editors, agents, and changes belong to each context without losing their place when switching. New terminals should start in the selected context's directory, while switching contexts should preserve ongoing work and restore the appropriate editor state. Acceptance should exercise two worktrees with distinct agents, multiple terminals, and different editor sets, including switching back and reviewing each context's changes. The plan must distinguish already-supported session behavior from the remaining worktree-centered experience.
- **Trace:**

  > SessionsTerminalContribution in src/vs/sessions/contrib/terminal/browser/sessionsTerminalContribution.ts already tracks terminals by session ID and reacts to active-session changes to select the working directory and terminal projection. BaseLayoutController in src/vs/sessions/contrib/layout/browser/baseSessionLayoutController.ts saves and restores session/chat editor working sets after workspace folders match the incoming working directory. The sessions.experimental.layoutScope registration changes editor and panel ownership, not terminal ownership, so these are not a single worktree-owned state model. The built-in Git extension exposes worktree-opening commands in extensions/git/package.json. https://github.com/microsoft/vscode/pull/317806 explored independent regular-workbench context switching but was closed unmerged; https://github.com/microsoft/vscode/issues/336620 documents related orientation and review gaps. Preserve existing terminal lifecycle and editor restoration contracts while determining the intended context boundary. The unresolved scope is whether this experience is session-centric within the Agents Window or also worktree-centric outside it.
- **Open decisions:**
  - Should the cohesive context experience be limited to the Agents Window, or also support worktree switching in the regular workbench without an agent session?
  - When multiple agent sessions use the same worktree, should users see one shared worktree context with combined activity and editor state, or separate session contexts grouped under that worktree?
