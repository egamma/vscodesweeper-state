# Issue #338614 — MCP servers from ~/.copilot/mcp-config.json are not shown in AI Customization

[https://github.com/microsoft/vscode/issues/338614](https://github.com/microsoft/vscode/issues/338614)

## Summary

Traced the mechanism: `~/.copilot/mcp-config.json` is only surfaced into VS Code's MCP registry through the `ExternalDiscoverySource.Copilot` filesystem-discovery adapter, which is gated by `chat.mcp.discovery.enabled` — a setting that defaults to `false` for every source (Claude Desktop, Cursor, Windsurf, and Copilot alike). The AI Customization editor's top-level MCP list reads from that same registry (`mcpService.servers`), so without opting in, these servers won't appear there. Whether Copilot's own config should be exempted from the same opt-in gate used for competitor tools is a product call no maintainer has made, so this stays open rather than closing as as-designed.

## Change summary

MCP servers defined in the GitHub Copilot CLI's global `~/.copilot/mcp-config.json` are not listed in the AI Customization UI.

## Best solution

A maintainer should decide whether the Copilot-owned `~/.copilot/mcp-config.json` source should be exempted from the general opt-in `chat.mcp.discovery.enabled` gate (since it's VS Code's own AI assistant config, not a third-party tool like Claude/Cursor/Windsurf) and always surfaced in AI Customization, or whether the UI should instead surface a prompt/link to enable `chat.mcp.discovery.enabled.copilot` for users who want this.

- **Behavior:**

  > MCP servers a user has configured in `~/.copilot/mcp-config.json` (the GitHub Copilot CLI's own global config) should be visible and manageable from the AI Customization UI without additional setup, distinct from third-party tool configs (Claude Desktop, Cursor, Windsurf) which remain opt-in via `chat.mcp.discovery.enabled`.
- **Trace:**

  > AI Customization's server list (aiCustomizationManagementEditor.ts:1406) reads `IMcpService.servers`, populated by `FilesystemMcpDiscovery` adapters gated on the `chat.mcp.discovery.enabled` config object (nativeMcpDiscoveryAbstract.ts, default false for every key including `copilot`). `CopilotMpcDiscoveryAdapter` (nativeMcpDiscoveryAdapters.ts) already knows how to parse `~/.copilot/mcp-config.json` via `getCopilotGlobalMcpConfigurationResource`, it's just never invoked unless the user opts in. The boundary: do not change gating for the other (genuinely third-party) discovery sources — Claude Desktop, Cursor, Windsurf should remain opt-in. Related: https://github.com/microsoft/vscode/issues/337840 (a different, session-scoped display bug for the same underlying file) and the closed https://github.com/microsoft/vscode/issues/338720 (a stale-refresh bug in the same area, already fixed) — worth checking neither already covers this before implementing.
- **Open decisions:**
  - Should `~/.copilot/mcp-config.json` (GitHub Copilot's own config, not a third-party competitor tool) be exempted from the opt-in `chat.mcp.discovery.enabled` gate entirely, or should AI Customization instead surface a one-time prompt/link inviting the user to enable that specific source?
  - If exempted from the gate, should the servers also become active/usable in chat by default, or only shown read-only/disabled in AI Customization until the user explicitly enables them?

## Evidence

- **discovery gate default:** src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts registers `chat.mcp.discovery.enabled` with `default: Object.fromEntries(allDiscoverySources.map(k => [k, false]))`, so the `copilot` source is off by default.
- **adapter wiring:** src/vs/workbench/contrib/mcp/common/discovery/nativeMcpDiscoveryAdapters.ts's CopilotMpcDiscoveryAdapter reads getCopilotGlobalMcpConfigurationResource(...) (~/.copilot/mcp-config.json) but is only invoked when FilesystemMcpDiscovery's `_fsDiscoveryEnabled` observable (bound to `chat.mcp.discovery.enabled`) includes `copilot: true` (nativeMcpDiscoveryAbstract.ts).
- **test confirms intent:** src/vs/workbench/contrib/mcp/test/common/nativeMcpDiscoveryAdapters.test.ts has a test literally named 'does not watch the Copilot user MCP configuration by default', confirming the off-by-default behavior is deliberate for the discovery mechanism itself.
- **AI Customization uses the same registry:** src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagementEditor.ts:1406 iterates `this.mcpService.servers`, which is populated by the gated discovery adapters above — so the UI inherits the same opt-in behavior with no additional hint to the user.
- **related open issue:** https://github.com/microsoft/vscode/issues/337840 shows Agent Host user MCP servers from the same file DO appear in Customizations in some (session-scoped) flows, just mis-grouped — suggesting a separate, non-opt-in path exists for active agent sessions, which is inconsistent with the standalone AI Customization editor's behavior.
