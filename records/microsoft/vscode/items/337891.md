# Issue #337891 — Agents Customization window: Improve UX for configuring plugin enabled/disabled state across global and workspace scope

[https://github.com/microsoft/vscode/issues/337891](https://github.com/microsoft/vscode/issues/337891)

## Summary

Reasonable UX proposal for the Agents Customization window's plugin management; current enablement model is a flat per-item boolean with no global/workspace scope distinction, so the gap described is real, but this needs maintainer design input on the storage/UI model before implementation.

## Change summary

Replace the plugin on/off toggle in the Agents Customization window with a three-state (enabled / workspace-disabled / globally-disabled) control that makes the disable scope explicit.

## Best solution

Design a scope-aware enablement model for plugins (and likely other customization item types) in the AI Customization management UI/service layer, then implement a three-state toggle once the persistence semantics (global vs. workspace disable, storage keys) are agreed.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationItemSource.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationListWidget.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagement.ts`
- **Validation:** A test in aiCustomizationItemsModel.test.ts/aiCustomizationListWidget.test.ts asserting the toggle reflects and can set workspace-only vs. global disable state for a plugin item.
- **Behavior:**

  > In the Agents Customization window, each plugin shows a three-state control: Enabled, Workspace disabled, or Globally disabled, always reflecting the plugin's effective state in the current workspace. Selecting 'Workspace disabled' persists only for the current workspace; the other two states persist as a global setting. The tooltip/label makes the active scope explicit.
- **Trace:**

  > Enablement today is tracked as a flat ResourceSet via IPromptsService.getDisabledPromptFiles(type), consumed in aiCustomizationItemSource.ts (`enabled: !disabledPromptFiles.has(p.uri)`), with no workspace-vs-global scope concept in the storage or the list widget UI (aiCustomizationListWidget.ts). Adding scope requires deciding where workspace-scoped disable state is stored (workspace storage vs. a settings key) and how it composes with the existing global disable set — that decision belongs to a maintainer before implementation. Do not restructure the underlying prompts/skills discovery pipeline; only the enablement bookkeeping and toggle UI are in scope.
- **Open decisions:**
  - Where is workspace-scoped disable state persisted (workspace storage vs. a workspace settings key) and does it survive workspace rename/move?
  - How does the three-state toggle interact with existing bulk enable/disable actions and multi-root workspaces?
  - What exact labels/tooltips communicate the three states, and do other customization types (skills, MCP servers) get the same treatment or just plugins?
