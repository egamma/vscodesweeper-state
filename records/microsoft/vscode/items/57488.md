# Issue #57488 — Git - Linux ssh-agent/ssh-askpass problem

[https://github.com/microsoft/vscode/issues/57488](https://github.com/microsoft/vscode/issues/57488)

## Summary

Keep open: the launcher environment defect diagnosed in the thread remains in current source. Integrated SSH prompting and the reported desktop-askpass workarounds do not restore access to an agent configured by shell startup files.

## Change summary

Git actions launched through the VS Code UI fail to use an already-unlocked SSH agent when a desktop launcher starts the CLI without the shell-initialized environment.

## Best solution

Make desktop-launcher startup obtain the shell environment needed by built-in Git without disrupting environment inheritance for genuine terminal launches. Keep desktop keyring/askpass integration distinct from this missing-agent-environment defect.

## Plan brief

- **Likely files:** `resources/linux/bin/code.sh`, `src/cli.ts`, `src/vs/code/node/cli.ts`, `src/vs/platform/environment/node/argvHelper.ts`, `src/vs/platform/shell/node/shellEnv.ts`, `src/vs/code/electron-main/app.ts`
- **Validation:** On Linux, with all VS Code instances stopped, configure the login shell startup file to export a live SSH_AUTH_SOCK containing an unlocked key while the desktop launcher environment lacks that variable. Launch code through rofi/dmenu and perform a built-in Git fetch or push: it must use that agent without a passphrase prompt. Repeat from an initialized terminal and verify its inherited agent environment remains intact; retain the explicit force-user-env and force-disable-user-env behaviors. Planning should identify automated regression coverage for these startup cases.
- **Behavior:**

  > Starting VS Code through a Linux desktop launcher must allow built-in Git to use an already-unlocked SSH agent configured in the user's shell startup files, even when the launcher itself lacks the socket variable. Fetch, pull, and push should not fail authentication or request that key's passphrase again solely because of the launch method. Starting from an initialized terminal must preserve its inherited environment. Validate fresh application startup, not a new window attached to an existing instance.
- **Trace:**

  > The original diagnosis is documented at https://github.com/microsoft/vscode/issues/57488#issuecomment-417259290 and remains traceable in current source. resources/linux/bin/code.sh enters src/cli.ts, which marks the process VSCODE_CLI=1; src/vs/code/node/cli.ts passes the environment to the desktop process. isLaunchedFromCli in src/vs/platform/environment/node/argvHelper.ts tests that marker, and getResolvedShellEnv in src/vs/platform/shell/node/shellEnv.ts consequently skips shell resolution unless forced. Built-in Git inherits process.env, while Askpass only supplies prompt helpers, so a missing SSH_AUTH_SOCK remains missing. The uncertainty is the shared startup-environment consumer boundary and how to validate launcher detection without changing genuine CLI inheritance; that trace was not completed across all consumers. Preserve explicit environment-control flags and keep desktop keyring prompting, tracked separately at https://github.com/microsoft/vscode/issues/242494, outside the original agent-inheritance acceptance scope.

## Evidence

- **Confirmed diagnosis:** In https://github.com/microsoft/vscode/issues/57488#issuecomment-417259290, joaomoreno reports a screen-sharing reproduction: rofi launches the PATH CLI without a shell-initialized environment, shell resolution is skipped, and the SSH agent configuration from .zshrc is missing. Subsequent comments independently confirm launcher-versus-terminal differences.
- **Current source retains the failing path:** At checkout eef761e9628e777317a554114f0202a070e98f0b, resources/linux/bin/code.sh invokes the CLI entry point; src/cli.ts sets VSCODE_CLI=1; src/vs/code/node/cli.ts copies process.env into the desktop child environment. src/vs/platform/environment/node/argvHelper.ts:isLaunchedFromCli checks only that marker, and src/vs/platform/shell/node/shellEnv.ts:getResolvedShellEnv returns an empty result for it unless --force-user-env is supplied. Thus a fresh rofi launch lacking SSH_AUTH_SOCK still skips the shell startup files that would supply it.
- **Git authentication boundary:** extensions/git/src/git.ts combines process.env with Git-specific overrides when spawning Git. extensions/git/src/askpass.ts supplies SSH_ASKPASS and SSH_ASKPASS_REQUIRE=force but does not discover SSH_AUTH_SOCK. This provides a prompt fallback, not access to an existing agent whose socket was never inherited.
- **Workarounds are partial coverage:** The thread documents terminal-based launching, exporting SSH_AUTH_SOCK in .profile, and disabling git.useIntegratedAskPass with desktop SSH_ASKPASS variables. Current Askpass.getEnv() supports that last setting, and --force-user-env bypasses the CLI shell-resolution skip. Neither establishes automatic correct environment detection for the original launcher scenario.

It concerns KWallet/ksshaskpass retrieval when integrated askpass overrides the desktop helper; its reporter says explicitly running ssh-add lets VS Code authenticate. It does not own the original failure to inherit an already-populated agent environment, so folding this broader report into it would lose distinct work.
