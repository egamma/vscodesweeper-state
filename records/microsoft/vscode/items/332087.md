# Issue #332087 — Agent host: enabling AHP debug logging stops the chat rendering incrementally

[https://github.com/microsoft/vscode/issues/332087](https://github.com/microsoft/vscode/issues/332087)

## Summary

Thorough, well-instrumented report from the author with concrete before/after measurements showing incremental chat rendering collapses into one final paint when either AHP debug-logging setting is enabled, even though the host keeps emitting deltas evenly. A follow-up comment complicates the diagnosis further (the effect also appeared workspace-specific with all logging off in one dev container), so the root cause is not yet pinned down — this needs a maintainer or the reporter to isolate the mechanism before a fix is scoped.

## Change summary

Enabling chat.agentHost.ahpJsonlLoggingEnabled or chat.agentHost.agentDebugLog.enabled makes the chat UI stop rendering incrementally, painting the whole response in one shot at the end of the turn instead of streaming it.

## Best solution

A maintainer (or the reporter, who already has strong repro data) should trace the client-side path from WebSocketProtocolTransport's message handler through to the chat renderer to find what differs when a per-frame observer (the AHP logger or debug-log listener) is attached — the report's own workspace-specific finding suggests the settings may just be correlated triggers rather than the root cause, so isolating that is the next concrete step before any code change.

## Evidence

- **host-side confirmation:** AgentHostStateManager's envelope logging showed the host still emitting ~100 chat/delta envelopes evenly across the turn, so the frames are produced and sent correctly — the collapse happens client-side.
- **code path cited:** src/vs/platform/agentHost/node/webSocketTransport.ts lines ~66-71 and 87-93 show `this._ahpLogger?.log(message, ...)` followed synchronously by `this._onMessage.fire(message)` / `this._ws.send(text)` on every frame — confirmed by reading the file, matching the report's citation.
- **logger implementation:** src/vs/platform/agentHost/common/ahpJsonlLogger.ts:log() does one JSON.stringify plus VSBuffer.fromString per call and defers actual disk I/O via a queued `_scheduleDrain`, consistent with the report's own analysis that this alone shouldn't obviously block rendering.
- **unresolved complication:** Comment 1 reports the effect reproducing with all three logging settings off in one workspace but not another on the same build, which the reporter flags as 'workspace-specific' — undermining a simple logging-causes-it explanation and leaving the true trigger unidentified.
