# Issue #332087 — Agent host: responses render only at turn end because the optimistic turn start is never retired

[https://github.com/microsoft/vscode/issues/332087](https://github.com/microsoft/vscode/issues/332087)

## Summary

Confirmed on current main: the ChatTurnStarted reducer resets `responseParts` to `[]` (protocol/channels-chat/reducer.ts:339-349), and `ChatSubscription._recomputeOptimistic` replays any still-pending turn-start on top of confirmed state on every reconcile. The existing `_promotePendingTurnStartIfTerminal` guard (agentSubscription.ts:528-546) only retires the pending start on terminal actions (Complete/Cancelled/Error), so mid-turn `chat/delta` envelopes keep getting folded into confirmed state while optimistic state keeps re-wiping `responseParts` back to empty — exactly the reported symptom. An open PR already targets the actual fix, so this stays open rather than closed or auto-fixed.

## Change summary

Chat responses render as a single paint at turn end instead of streaming, because the optimistically-applied `chat/turnStarted` pending action is never retired by an intermediate backend action and keeps resetting the replayed turn's response parts to empty.

## Best solution

Land https://github.com/microsoft/vscode/pull/332122 ("retire the optimistic turn start on the first backend action") or the related https://github.com/microsoft/vscode/pull/334011 ("Make the chat/turnStarted reducer idempotent"), which extend retirement beyond just terminal actions to the first backend action for the turn — that removes the replay-reset window entirely.

- **partial existing fix only covers terminal actions:** src/vs/platform/agentHost/common/state/agentSubscription.ts:528-546 `_promotePendingTurnStartIfTerminal` only promotes/retires the pending turnStarted when the incoming action is ChatTurnComplete/ChatTurnCancelled/ChatError — not on chat/delta, so mid-turn replay still resets responseParts.
