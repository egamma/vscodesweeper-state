# Issue #259901 — Assisted MCP server installation should support custom package sources

[https://github.com/microsoft/vscode/issues/259901](https://github.com/microsoft/vscode/issues/259901)

## Summary

The central request remains unimplemented on current main: assisted setup still queries public registries directly or explicitly pins NuGet.org. Keep this accepted, team-authored Backlog request open and plan a consistent package-source strategy across the supported ecosystems.

## Change summary

Allow assisted MCP installation to discover packages through configured private/custom package sources and an appropriate workspace context.

## Best solution

Define a shared assisted-install contract that supplies workspace context and uses ecosystem-native package tooling or equivalent configured-source discovery, while preserving public-registry behavior and useful publisher metadata where available.

## Vision fit

- **Fit:** aligned
- **Reason:** Supporting private package sources makes the core MCP installation experience work in common enterprise AI-development environments without requiring a parallel manual setup flow.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/browser/mcpCommandsAddConfiguration.ts`, `src/vs/workbench/contrib/mcp/test/browser/mcpConfigurationEntryPoints.test.ts`, `extensions/copilot/src/extension/mcp/vscode-node/commands.ts`, `extensions/copilot/src/extension/mcp/vscode-node/nuget.ts`, `extensions/copilot/src/extension/mcp/test/vscode-node/commands.spec.ts`, `extensions/copilot/src/extension/mcp/test/vscode-node/nuget.stub.spec.ts`
- **Validation:** From extensions/copilot, run `npm run test:unit -- src/extension/mcp/test/vscode-node/commands.spec.ts src/extension/mcp/test/vscode-node/nuget.stub.spec.ts`; add deterministic cases proving configured custom sources are used and existing public-registry discovery remains supported. Extend the MCP configuration entry-point test to verify the selected workspace context reaches validation.
- **Behavior:**

  > When assisted MCP setup is launched for a package available through a configured custom source, validation should discover it using that ecosystem’s effective package configuration rather than requiring publication to the central registry. Public-registry packages must continue to work. Source selection must use a documented, deterministic context for workspace, multi-root, and global installation targets, and failures must distinguish missing package-manager tooling from a package that was not found.
- **Trace:**

  > The core entry point in src/vs/workbench/contrib/mcp/browser/mcpCommandsAddConfiguration.ts invokes `github.copilot.chat.mcp.setup.validatePackage` without workspace context. The extension receives that contract in IValidatePackageArgs and routes validation through McpSetupCommands.validatePackageRegistry in extensions/copilot/src/extension/mcp/vscode-node/commands.ts. NPM, Python, and Docker currently use fixed public HTTP endpoints there; NuGet uses native `dotnet` commands in extensions/copilot/src/extension/mcp/vscode-node/nuget.ts but explicitly supplies NuGet.org and starts discovery from the home directory. https://github.com/microsoft/vscode-copilot-chat/pull/546 is useful prior art for command execution and deterministic tests, while the experimental NPM implementation from https://github.com/microsoft/vscode/pull/262558 was removed by https://github.com/microsoft/vscode/pull/264342 and is not an active implementation. Preserve the existing assisted-generation, consent, telemetry, and destination-selection behavior; uncertainty begins at source precedence, workspace selection, and the supported fallback when native tooling is unavailable.
- **Open decisions:**
  - Which configuration context determines package sources for workspace, multi-root, user, and Copilot-global destinations, and which workspace folder wins when more than one is available?
  - Should native package-manager tooling be required for custom-source discovery, or should assisted setup fall back to the existing public-registry HTTP lookup when the relevant CLI is unavailable?
  - Must the first implementation cover NPM, Python, NuGet, and Docker together, or should ecosystems ship incrementally under one documented contract?
  - When a private source does not expose publisher or README metadata, what identity and consent information should assisted setup show instead?

## Evidence

- **current NPM, Python, and Docker path:** extensions/copilot/src/extension/mcp/vscode-node/commands.ts:318-369 implements McpSetupCommands.validatePackageRegistry with fixed HTTP endpoints at registry.npmjs.org, pypi.org, and hub.docker.com, so configured private sources are not consulted.
- **current NuGet path:** extensions/copilot/src/extension/mcp/vscode-node/nuget.ts constructs NuGetMcpSetup with source https://api.nuget.org/v3/index.json, uses os.homedir() for discovery, and passes the fixed source to `dotnet package search` and `dotnet tool install`; its comments explicitly reference https://github.com/microsoft/vscode/issues/259901 as future work.
- **missing workspace contract:** src/vs/workbench/contrib/mcp/browser/mcpCommandsAddConfiguration.ts:421-429 sends package type, name, target format, and schema to the Copilot validation command, but no workspace URI or working-directory context. extensions/copilot/src/extension/mcp/vscode-node/commands.ts defines the matching IValidatePackageArgs without such context.
- **partial NuGet work:** https://github.com/microsoft/vscode-copilot-chat/pull/546 merged native .NET CLI lookup, but its description explicitly says NuGet.org remained hard-coded and custom package sources were only enabled as future work.
- **NPM exploration did not persist:** https://github.com/microsoft/vscode/pull/262558 merged an experimental npm CLI installation service, but https://github.com/microsoft/vscode/pull/264342 subsequently deleted it as unused. Current main has no NpmPackageService and assisted NPM validation still uses the public HTTP endpoint.
