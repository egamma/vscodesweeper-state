# Issue #246833 — Reconsider Workbench Hover Max Height option (`maxHeigtRatio`)

[https://github.com/microsoft/vscode/issues/246833](https://github.com/microsoft/vscode/issues/246833)

## Summary

Keep this team-authored debt item open: `maxHeightRatio` remains part of the shared hover contract and now has several consumers and dedicated tests, while no later change referencing this issue resolves the requested API-design decision.

## Change summary

Reconsider whether workbench hovers should expose a caller-selected maximum-height ratio and, if retained, whether `maxHeightRatio` is the right contract and name.

## Best solution

Settle a uniform hover-sizing contract for the shared widget, deciding whether available geometry should determine the limit or consumers should retain an explicit override; preserve the existing long-content scrolling and fixed-action behavior.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/hover/hover.ts`, `src/vs/platform/hover/browser/hoverWidget.ts`, `src/vs/platform/hover/test/browser/hoverService.test.ts`, `src/vs/workbench/browser/parts/statusbar/statusbarPart.ts`, `src/vs/workbench/contrib/update/browser/postUpdateWidget.ts`, `src/vs/sessions/contrib/accountMenu/browser/account.contribution.ts`
- **Validation:** Run `scripts/test.sh --grep "HoverService"` and verify tests cover the chosen maximum-height behavior for default, constrained, and short-content hovers while keeping action rows visible and overflowing content scrollable.
- **Behavior:**

  > Workbench hovers need a deliberate and consistently named maximum-height behavior. Default and consumer-specific hovers must remain usable in small windows, long content must scroll without clipping fixed action or status rows, and short content must not gain unnecessary scrolling. Acceptance should cover the default limit and every retained consumer-specific sizing mode.
- **Trace:**

  > Commit 705045f9010512f92871ab793be8a978247f77cf added `IHoverAppearanceOptions.maxHeightRatio` and the corresponding calculation in `HoverWidget.adjustHoverMaxHeight` to unblock https://github.com/microsoft/vscode/issues/242377. Current main retains the interface in src/vs/base/browser/ui/hover/hover.ts and implementation in src/vs/platform/hover/browser/hoverWidget.ts, with three production consumers selecting different ratios. Commit 6a1e7baf5dd84b3c40ce137c59858651bb159b2b later made ratio-constrained content scroll correctly and added coverage in src/vs/platform/hover/test/browser/hoverService.test.ts. The unresolved boundary is the sizing contract itself; do not regress long-content scrolling, fixed action visibility, forced-position geometry, or short-hover behavior.
- **Open decisions:**
  - Should all workbench hovers derive their maximum height uniformly from available window and anchor geometry, or should individual consumers continue to select visibly different height limits?
  - If consumer control remains, should the observable contract stay a viewport-height ratio or use a sizing concept that better represents the intended hover behavior?
