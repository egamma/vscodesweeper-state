# Issue #234758 — Right-clicking injected text caused funny selection

[https://github.com/microsoft/vscode/issues/234758](https://github.com/microsoft/vscode/issues/234758)

## Summary

This remains a valid editor rendering/input bug: a maintainer reproduced the native DOM selection, and current main still makes hovered editor lines natively selectable on macOS. No fixing commit or canonical issue was found.

## Change summary

Right-clicking injected editor text such as ghost text or an inlay hint can create an unintended native DOM selection.

## Best solution

Prevent context-clicking injected text from leaving a native DOM selection while preserving the macOS Look Up interaction that requires selectable editor text.

## Plan brief

- **Likely files:** `src/vs/editor/browser/viewParts/viewLines/viewLines.css`, `src/vs/editor/browser/config/editorConfiguration.ts`, `src/vs/editor/browser/controller/mouseHandler.ts`
- **Validation:** On macOS with EditContext disabled, render both ghost text and an inlay hint, right-click each, and verify no native DOM selection remains; then verify force-click or three-finger Look Up still works on ordinary editor text.
- **Behavior:**

  > Right-clicking ghost text, inlay hints, or other injected text must not create or leave a browser-native DOM selection distinct from the editor selection. The editor context menu and existing editor selection must continue to behave normally. On macOS, the Look Up gesture on ordinary editor text must remain available.
- **Trace:**

  > The report was reproduced by a VS Code team member across the available Insiders and released builds. On current main, src/vs/editor/browser/config/editorConfiguration.ts adds the `mac` editor class, while src/vs/editor/browser/viewParts/viewLines/viewLines.css changes hovered line DOM to `user-select: text`, overriding the normal non-selectable editor-line rules. That rule exists to support the macOS Look Up behavior tracked by https://github.com/microsoft/vscode/issues/85632. Context-menu dispatch runs through MouseHandler in src/vs/editor/browser/controller/mouseHandler.ts; the uncertainty starts at whether selection should be constrained through styling or context-menu event handling. The boundary is editor DOM selection during context-click: editor model selection, injected-text rendering, and macOS Look Up behavior must not otherwise change.
- **Open decisions:**
  - Should native selection be prevented specifically for injected-text DOM, or cleared during the context-menu interaction?
  - How should the solution preserve macOS Look Up selection without making right-clicked injected text selectable?

## Evidence

- **confirmed reproduction:** A VS Code team member reported that both Insiders and released-build bisects reproduced the behavior across all tested builds, indicating a longstanding defect rather than a recent regression.
- **current source path:** src/vs/editor/browser/viewParts/viewLines/viewLines.css sets `user-select: text` on hovered `.lines-content`, `.view-line`, and `.view-lines` elements on macOS, overriding the normal `no-user-select` rules and allowing browser-native selection within rendered lines.
- **compatibility constraint:** The selectable-on-hover CSS explicitly preserves the macOS Look Up behavior tracked by https://github.com/microsoft/vscode/issues/85632, so resolving the context-click artifact must not disable that feature.
- **canonical search:** Repository issue searches for injected-text right-click selection and macOS DOM selection found no separate open issue that owns this defect.
