# Issue #279185 — Save as Custom Agent from Tools Window

[https://github.com/microsoft/vscode/issues/279185](https://github.com/microsoft/vscode/issues/279185)

## Summary

The requested save-from-tools workflow remains absent on current main, while adjacent custom-agent creation and tool persistence capabilities exist. This team-authored Backlog request should stay open for a product decision about the new agent's scope and persistence.

## Change summary

Allow a configured tool selection to be saved as a named custom agent directly from the Configure Tools window.

## Best solution

Provide a lightweight Save as Custom Agent path from Configure Tools that carries the current tool selection into a new agent definition, asks for the necessary identity and storage choices, and makes the resulting agent available to chat, prompts, and handoffs.

## Vision fit

- **Fit:** aligned
- **Reason:** Turning a repeated tool configuration into a reusable custom agent advances AI-assisted development while keeping the interaction integrated with the existing customization model.
- **Evidence:** Durable themes: AI-assisted development and Workbench & core UX; the request consolidates repeated configuration into the existing custom-agent surface rather than adding an unrelated subsystem.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/actions/chatToolPicker.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatToolActions.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/chatSelectedTools.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/customizationCreatorService.ts`, `src/vs/workbench/contrib/chat/browser/promptSyntax/newPromptFileActions.ts`
- **Validation:** Add focused tests proving the save flow receives the picker’s current enablement map and creates an agent definition with the expected tools, plus a component or UI-level check that the secondary save action is offered without changing normal Apply behavior.
- **Behavior:**

  > After adjusting tools in Configure Tools, a user can save that configuration as a named custom agent without reconstructing the selection elsewhere. The resulting agent preserves the agreed configuration scope and appears wherever custom agents can be selected, including chat, prompts, and handoffs. The existing Apply behavior continues to update the current global, session, or editable-agent scope exactly as it does today. Cancellation must leave both the active tool configuration and customization files unchanged.
- **Trace:**

  > ConfigureToolsAction in src/vs/workbench/contrib/chat/browser/actions/chatToolActions.ts invokes showToolsPicker in chatToolPicker.ts and sends the returned ToolAndToolSetEnablementMap to ChatSelectedTools.set(). ChatSelectedTools currently writes that map to profile state, session state, or an existing writable agent file; there is no creation branch. CustomizationCreatorService and NEW_AGENT_COMMAND_ID provide nearby agent-creation paths, but neither accepts a preselected tool map. The work should remain within chat tool selection and custom-agent creation; MCP installation, tool-set management, existing-agent rewrite semantics, and normal Apply behavior must not change. The uncertainty starts at the new agent's copied fields, storage scope, and activation behavior.
- **Open decisions:**
  - Does Save as Custom Agent copy only the current tool selection, or also inherit the selected agent's instructions, model, handoffs, and other user-visible configuration?
  - Should the new agent be stored at user scope, workspace scope, or chosen each time through the existing customization-location picker?
  - After saving, should the current chat immediately switch to the new agent, or should creation leave the active agent unchanged?
  - Should Save as Custom Agent be available only while configuring the default Agent, or also act as Save As for existing custom agents?

## Evidence

- **current tools flow:** On current main, src/vs/workbench/contrib/chat/browser/actions/chatToolPicker.ts exposes Add MCP Server, Install Extension, and Configure Tool Sets buttons; accepting the picker only returns the selected enablement map. It has no Save as Custom Agent action.
- **current persistence behavior:** src/vs/workbench/contrib/chat/browser/actions/chatToolActions.ts passes the picker result to ChatSelectedTools.set(), while src/vs/workbench/contrib/chat/browser/widget/input/chatSelectedTools.ts persists it globally, for the session, or back into an existing writable custom-agent file. None of those paths creates a new agent from the selection.
- **adjacent capability:** src/vs/workbench/contrib/chat/browser/aiCustomization/customizationCreatorService.ts and src/vs/workbench/contrib/chat/browser/promptSyntax/newPromptFileActions.ts provide guided and file-based custom-agent creation, including tools frontmatter, but they do not receive the current Configure Tools selection.
- **related design direction:** https://github.com/microsoft/vscode/issues/247566#issuecomment-2834692445 says tool selection was expected to move toward agent configuration, supporting this direction, but that issue concerns a tools-icon state indicator and does not report the same observable request.
- **not a duplicate:** https://github.com/microsoft/vscode/issues/261385 is an older open request for a general guided agent/prompt creation flow. It does not cover saving an already-adjusted Configure Tools selection as a new agent, so it does not meet the stronger same-symptom duplicate bar for this re-reviewed issue.
