## Summary

The current source still drops agent-host models at the extension-host API boundary, despite their availability in the workbench model picker. Keep this open while the linked draft fix is reviewed; an open implementation proposal is not a completed fix.

## Change summary

Allow extensions to discover and resolve agent-host language models through vscode.lm.selectChatModels and request.model.

## Best solution

Review the approach in https://github.com/microsoft/vscode/pull/343139 and land an appropriate bridge between workbench-owned models and the extension-host LM API, preserving explicit model selection rather than silently substituting a default.

- **Current source: model discovery boundary:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostLanguageModelProvider.ts:180-215 publishes workbench-owned models with identifiers `${this._vendor}:${m.id}` and vendor metadata. MainThreadLanguageModels.$selectChatModels in src/vs/workbench/api/browser/mainThreadLanguageModels.ts:215-217 returns service-selected identifiers, but ExtHostLanguageModels.selectLanguageModels in src/vs/workbench/api/common/extHostLanguageModels.ts:533-540 constructs API objects only from its local cache and filters out missing entries. That cache is populated by $provideLanguageModelChatInfo for extension-host providers, leaving workbench-owned agent-host models unavailable through this path.
