# Issue #334582 — Agent shell init script is not applied when sandboxing is enabled

[https://github.com/microsoft/vscode/issues/334582](https://github.com/microsoft/vscode/issues/334582)

## Summary

Team-authored bug report (TylerLeonhardt, MEMBER) with no cited fix commit, so the hard keep-open rule for team-authored issues applies regardless of staleness — this stays open. The root cause is confirmed by tracing current `main`: the generated shell init script sources `$HOME/.bashrc`/PowerShell profiles, but the sandbox read-root grant only covers the generated script's own directory, not the user's actual profile file, so the source silently no-ops under sandboxing.

## Change summary

When shell tool sandboxing is enabled, the Agent Host's generated shell init script can no longer read the user's actual shell profile (`~/.bashrc` / PowerShell profile), so profile-based env vars and activation are silently skipped.

## Best solution

Extend the sandbox read-root computation (`getVSCodeSandboxReadRoots` in src/vs/platform/agentHost/common/vscodeSandboxPaths.ts, consumed via `_sandboxExtraReadonlyPaths` in copilotAgentSession.ts) to also grant read-only access to the specific profile file(s) the generated init script sources — `$HOME/.bashrc` on macOS/Linux, and the resolved `CurrentUserAllHosts`/`CurrentUserCurrentHost` PowerShell profile paths on Windows — when the init-script setting is enabled.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/common/vscodeSandboxPaths.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/platform/agentHost/common/shellInitScript.ts`
- **Validation:** A sandboxed Copilot shell-tool command run with `chat.agentHost.shellTool.initScript.enabled` and sandboxing both on should be able to read `$HOME/.bashrc` (or the resolved PowerShell profile) and see env vars exported there, matching the reporter's repro steps.
- **Trace:**

  > `createBashInitScript`/`createPowerShellInitScript` (src/vs/platform/agentHost/common/shellInitScript.ts) emit a script that sources the user's real shell profile file. `_sandboxExtraReadonlyPaths`/`getVSCodeSandboxReadRoots` (vscodeSandboxPaths.ts) only grant read access to the generated script's own directory (`shellInitDirectory`), not the profile file itself, so under sandboxing the `source "$HOME/.bashrc"` line silently fails (`|| builtin true` swallows the error) and no profile content is applied. The boundary: do not change the generated script content or the init-script enablement path, only the sandbox read-root grant when the init-script setting is enabled. Where uncertainty starts: which exact profile path(s) to grant and how to compute the PowerShell profile location(s) host-side (PowerShell doesn't expose `$PROFILE` to the host before the shell runs) differ in security exposure and are a maintainer decision.
- **Open decisions:**
  - Should the sandbox grant exactly the single resolved profile file (tightest exposure) or a slightly broader set (e.g. common profile-adjacent includes) for `~/.bashrc`?
  - How should the host compute the Windows PowerShell `CurrentUserAllHosts`/`CurrentUserCurrentHost` profile paths without invoking PowerShell itself, across Windows PowerShell and PowerShell 7+?
  - Should this grant apply unconditionally whenever the init-script setting is on, or only after the script is first materialized (mirroring the existing `shellInitDirectory` lazy-grant pattern)?

## Evidence

- **generated script sources the real profile:** src/vs/platform/agentHost/common/shellInitScript.ts:60-78 builds a bash init script containing `if [ -r "$HOME/.bashrc" ]; then builtin source "$HOME/.bashrc" ...`; the PowerShell variant (lines 80-108) sources `$PROFILE.CurrentUserAllHosts`/`CurrentUserCurrentHost`.
- **sandbox grant covers only the generated file, not the real profile:** src/vs/platform/agentHost/common/vscodeSandboxPaths.ts:getVSCodeSandboxReadRoots only adds `shellInitDirectory` (the materialized `init.sh`/`init.ps1` written by `_materializeShellInitScript` in copilotAgentSession.ts:5529) — there is no grant for `$HOME/.bashrc` or any PowerShell profile path, so the sandboxed shell cannot read it, matching the reporter's `missing` result for `test -e "$HOME/.bashrc"`.
