- **Behavior:**

  > Whole-file staging and unstaging can take several seconds without progress feedback when optimistic updates are enabled. Slow operations should provide feedback without requiring users to disable optimistic updates. Acceptance must cover pending operations, completion and failure, both progress-setting values, and unchanged staging results. Whether fast operations display progress immediately or remain indicator-free requires the Git owner's decision.
- **Trace:**

  > CommandCenter.git.stage calls Repository.add, and git.unstage calls Repository.revert in extensions/git/src/commands.ts. Both repository methods pass !optimisticUpdateEnabled() as the operation's showProgress flag in extensions/git/src/repository.ts. OperationManager.shouldShowProgress in extensions/git/src/operation.ts ignores operations with that flag false, and the Source Control progress listener uses this predicate. Repository.run awaits the Git operation before applying the optimistic resource-group update, so the suppression can cover a real wait before the row moves. Preserve git.showProgress opt-out, existing resource-group results, and unrelated Git-operation behavior; diagnosing Windows Git execution slowness is outside this feedback improvement. The maintainer accepted investigating progress improvements at https://github.com/microsoft/vscode/issues/189407#issuecomment-1691274389, but the thread does not settle progress timing for fast operations.
- **Open decisions:**
  - Should optimistic stage/unstage operations show progress immediately, including fast operations, or only after a delay so fast operations remain indicator-free?
