# Issue #317569 — Automatically detect and offer local frontend build preview in Agents window

[https://github.com/microsoft/vscode/issues/317569](https://github.com/microsoft/vscode/issues/317569)

## Summary

Keep open: existing task actions, configured worktree automation, and browser pills provide pieces of the workflow, but do not establish automatic frontend-task selection and preview discovery. The older browser UI issue explicitly treats this issue as its engineering workstream, rather than superseding it.

## Change summary

Automatically identify and start the appropriate frontend development task, discover its live endpoint, and offer a preview button in the Agents window.

## Best solution

Deliver a session-aware frontend preview workflow that reuses existing task and browser infrastructure, with explicit rules for automatic execution, endpoint selection, and consent. Resolve those product boundaries with the maintainer before implementation; coordinate presentation with https://github.com/microsoft/vscode/issues/314789.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/chat/browser/runScriptAction.ts`, `src/vs/sessions/contrib/chat/browser/sessionsTasksService.ts`, `src/vs/sessions/contrib/chat/browser/worktreeCreatedTaskDispatcher.ts`, `src/vs/sessions/contrib/chat/browser/sessionBrowsersControl.ts`, `src/vs/sessions/contrib/browserView/browser/sessionBrowserView.ts`
- **Validation:** After agreeing the execution policy, exercise a frontend workspace with no running server, one with an existing server, and one with multiple candidate endpoints. Verify the intended task starts only under the agreed conditions, an existing server is not duplicated, the preview button opens the selected session's endpoint, and rejected permission or unavailable endpoints do not expose ports or offer a misleading ready preview.
- **Behavior:**

  > Frontend work in the Agents window should offer a live preview without requiring a separate agent prompt or manual build-task startup. The workflow should recognize an already-running suitable server and avoid starting a duplicate. Acceptance must cover a single unambiguous project, multiple candidate tasks or endpoints, and the agreed consent and exposure boundaries. The issue does not yet define the user-visible behavior when selection is ambiguous.
- **Trace:**

  > RunScriptContribution in src/vs/sessions/contrib/chat/browser/runScriptAction.ts provides explicit task execution, user-requested /generate-run-commands, and manual browser URL configuration. ISessionsTasksService in sessionsTasksService.ts supplies configured session tasks, while WorktreeCreatedTaskDispatcher automatically executes explicitly tagged worktreeCreated tasks, not inferred frontend tasks. SessionBrowsersControl in sessionBrowsersControl.ts lists existing chat-owned browser views rather than discovering a new development server. These source paths establish useful infrastructure but not end-to-end coverage of the request. Preserve configured task execution and session ownership while defining the new workflow. The older https://github.com/microsoft/vscode/issues/314789 coordinates browser presentation and explicitly points back to this issue for engineering; it is not a duplicate target established by this review.
- **Open decisions:**
  - What user-visible trigger and consent permit starting a detected frontend task automatically, and what should happen when no task is clearly preferred?
  - When multiple running endpoints or frontend projects are available, should the preview choose a default or require the user to select one?
  - Is the initial scope limited to local loopback previews, or does it include remote port forwarding, and what approval is required before changing port exposure?
