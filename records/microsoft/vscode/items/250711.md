# Issue #250711 — Copilot overrides language server's preselect item in completion list

[https://github.com/microsoft/vscode/issues/250711](https://github.com/microsoft/vscode/issues/250711)

## Summary

Keep this accepted Backlog request open: current source still allows inline completions to override language-server preselection. The related closed reports do not provide an open duplicate target or a verified fix, and the precedence policy needs a maintainer decision.

## Change summary

Preserve context-aware language-server preselection when Copilot favors a different completion-list item.

## Best solution

Define how explicit language-server preselection should interact with inline-completion matching in the editor suggest pipeline, so type-aware defaults remain useful without disabling Copilot. Decide whether that precedence is the default or an opt-in behavior before implementation.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/inlineCompletions/browser/model/suggestWidgetAdapter.ts`, `src/vs/editor/contrib/suggest/browser/suggestController.ts`, `src/vs/editor/contrib/suggest/browser/suggestMemory.ts`, `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/contrib/inlineCompletions/test/browser/suggestWidgetModel.test.ts`
- **Validation:** Extend the Suggest Widget Model test harness with two completion-list items, one explicitly preselected and another matched by an active inline completion. Assert the focused and accepted item under the approved precedence policy, including the no-preselect case and unchanged manual navigation. Supplement with the reporter's C# enum scenario with Copilot enabled and disabled; do not execute validation in this read-only review.
- **Behavior:**

  > A language server can explicitly prefer a type-appropriate completion, but an active inline completion currently causes another matching list item to receive initial focus. The desired outcome is that semantic preselection remains useful while inline suggestions stay available. Acceptance must verify both initial focus and the item accepted from the widget, with and without an explicit preselect item. Whether this behavior is unconditional or opt-in remains a maintainer decision.
- **Trace:**

  > InlineCompletionsController supplies the active inline completion edit to ObservableSuggestWidgetAdapter. SuggestWidgetAdaptor registers a priority-100 selector that chooses the longest suggest edit augmented by that inline edit; SuggestController stops after that selector succeeds, before its priority-0 memory selector can honor completion.preselect. The existing conflict-display setting affects InlineCompletionsModel's ghost-text visibility, not this selection precedence. The source establishes the interaction, but not a language-independent rule for semantic validity. Keep manual list navigation, ordinary inline completion acceptance, and cases without explicit language-server preselection within their existing contracts unless the maintainer explicitly chooses otherwise. The current test harness in suggestWidgetModel.test.ts supports both completion and inline providers, but its mocked memory service always selects index 0, so validation must represent the explicit-preselect case accurately. Related reports are https://github.com/microsoft/vscode/issues/249814 and https://github.com/microsoft/vscode/issues/199094; neither is an open canonical.
- **Open decisions:**
  - Should explicit language-server preselection take precedence over inline-completion matching by default, or only through an opt-in selection policy?
