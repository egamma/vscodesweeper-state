# Issue #318103 — Agents Window: support extension development workflow (extensionDevelopmentPath + debugger)

[https://github.com/microsoft/vscode/issues/318103](https://github.com/microsoft/vscode/issues/318103)

## Summary

A real extension-development gap remains on current main: the debugger launch path does not route `--agents` into an Agents Window, and opening Agents from an existing development host does not inherit that window's extension-development/debug configuration. The issue is already assigned, correctly routed, and accepted into Backlog, so it should remain open for a design choice between the two proposed workflows.

## Change summary

Allow extension authors to launch or open an Agents Window with an extension development path loaded and its extension host attached to the debugger.

## Best solution

Provide a supported Agents Window extension-development workflow that preserves `extensionDevelopmentPath`, `debugId`, extension-host inspection arguments, and reload/debug lifecycle behavior. A maintainer should first decide whether this is a dedicated `extensionHost` launch mode, inheritance when opening Agents from a development host, or both.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/extensionHostDebugService.ts`, `src/vs/platform/native/electron-main/nativeHostMainService.ts`, `src/vs/platform/windows/electron-main/windowsMainService.ts`
- **Validation:** Add an Electron-level extension-development launch test that starts an `extensionHost` configuration targeting Agents and asserts the resulting sessions window receives `extensionDevelopmentPath`, `debugId`, and extension-host inspection arguments; then verify a breakpoint in the development extension is hit and remains attached after reload.
- **Behavior:**

  > An extension author can run a supported extension-host debug configuration for the Agents Window without packaging and installing a VSIX. The resulting window loads the development extension rather than only its installed copy, attaches the extension-host debugger, honors breakpoints, and preserves debugging across the normal reload lifecycle. Regular Extension Development Host launches and ordinary Agents Window launches must remain unchanged.
- **Trace:**

  > The process startup branch in src/vs/code/electron-main/app.ts routes to WindowsMainService.openAgentsWindow only when parsed process arguments contain `agents`. BrowserExtensionHostDebugService.openExtensionDevelopmentHostWindow in src/vs/workbench/contrib/debug/browser/extensionHostDebugService.ts uses a fixed payload allowlist that includes extension-development and debugger fields but omits `agents`, so that route opens a regular development window. Conversely, NativeHostMainService.openAgentsWindow in src/vs/platform/native/electron-main/nativeHostMainService.ts uses environmentMainService.args, not the invoking window configuration, and WindowsMainService.ensureAgentsWindow does not inherit development state from contextWindowId. The boundary is launch/configuration propagation across the debug, native-host, and window-main paths; normal window selection, installed-extension behavior outside development mode, and non-Agents debugging must not change. No open canonical issue or VS Code fixing PR was found.
- **Open decisions:**
  - Should the supported primary workflow be an Agents-specific mode of the `extensionHost` debug launch, inheritance when opening Agents from an existing Extension Development Host, or both?
  - When development and installed copies share an extension identifier, should the development copy replace the installed copy using normal Extension Development Host precedence or coexist under Agents-specific rules?
  - Which development/debug fields should cross from the invoking window, and should that inheritance occur only for an explicit development launch to avoid leaking debug state into ordinary Agents windows?

## Evidence

- **debug launch gap:** On current main, BrowserExtensionHostDebugService.openExtensionDevelopmentHostWindow in src/vs/workbench/contrib/debug/browser/extensionHostDebugService.ts copies only extensionDevelopmentPath, extensionTestsPath, extensionEnvironment, debugId, inspect-brk-extensions, and inspect-extensions into the new window payload; it does not recognize or route the `agents` argument.
- **Agents startup path:** src/vs/code/electron-main/app.ts opens an Agents Window only when the process-level parsed CLI has `args['agents']`; the browser extension-host debug path instead calls its workspace provider to open a normal development window.
- **missing inheritance:** NativeHostMainService.openAgentsWindow in src/vs/platform/native/electron-main/nativeHostMainService.ts constructs the Agents Window request from environmentMainService.args rather than the invoking window's configuration. WindowsMainService.ensureAgentsWindow in src/vs/platform/windows/electron-main/windowsMainService.ts preserves that request but does not inherit extensionDevelopmentPath or debugId from contextWindowId.
