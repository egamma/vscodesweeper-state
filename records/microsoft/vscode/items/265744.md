# Issue #265744 — Have voice input in command palette/ settings search

[https://github.com/microsoft/vscode/issues/265744](https://github.com/microsoft/vscode/issues/265744)

## Summary

Keep open: current dictation does not cover Command Palette or Settings search, so the requested accessibility capability remains missing. This team-authored request has study-backed maintainer interest; no verified canonical or completed implementation was found.

## Change summary

Support voice input for finding and invoking commands and searching settings.

## Best solution

Provide accessible voice input in the Command Palette and Settings search using the existing speech infrastructure. First settle whether spoken commands should populate results for explicit selection or directly execute recognized actions.

## Plan brief

- **Likely files:** `src/vs/platform/quickinput/browser/quickInputController.ts`, `src/vs/platform/quickinput/browser/quickInputBox.ts`, `src/vs/workbench/contrib/preferences/browser/settingsEditor2.ts`, `src/vs/workbench/contrib/codeEditor/browser/suggestEnabledInput/suggestEnabledInput.ts`, `src/vs/workbench/contrib/chat/browser/speechToText/chatSpeechToTextService.ts`, `src/vs/workbench/contrib/chat/browser/speechToText/dictationSession.ts`
- **Validation:** After the interaction contract is chosen, manually open the Command Palette and speak a terminal-creation or file-opening request, verifying the agreed selection/execution behavior; then dictate a Settings search and verify its query and results update. Check stop, cancel and dismissal release recording and never insert text into an unrelated editor; preserve ordinary keyboard search and existing chat/editor/terminal dictation.
- **Behavior:**

  > Users should be able to use voice in the Command Palette to find or invoke actions such as creating a terminal or opening a file, and in Settings search to find settings. Neither surface should send the transcript to an unrelated editor or chat input. Acceptance must cover both requested surfaces, keyboard and screen-reader access, and stopping or cancelling recording. Whether a recognized command executes immediately or awaits explicit selection remains undecided.
- **Trace:**

  > The existing editor entry point is EditorDictationStartAction in src/vs/workbench/contrib/codeEditor/browser/dictation/editorDictation.ts; it requires the EditorDictation contribution on its target ICodeEditor. SettingsEditor2 builds SuggestEnabledInputWithHistory, whose CodeEditorWidget contribution list in src/vs/workbench/contrib/codeEditor/browser/suggestEnabledInput/suggestEnabledInput.ts omits EditorDictation. Command Palette input instead goes through QuickInputController and QuickInputBox, backed by FindInput. Shared transcript insertion in src/vs/workbench/contrib/chat/browser/speechToText/dictationSession.ts currently targets ICodeEditor, and ChatDictationSurface in chatSpeechToTextService.ts names chat, editor and terminal only. These source boundaries establish missing integration, not a chosen interaction design; preserve existing dictation destinations and ordinary search behavior. https://github.com/microsoft/vscode/issues/328808 is related focus-aware entry-point work, not a duplicate or a settled design for these surfaces.
- **Open decisions:**
  - Should Command Palette voice input transcribe a query for explicit result selection, interpret natural-language requests and execute them directly, or offer both modes?
