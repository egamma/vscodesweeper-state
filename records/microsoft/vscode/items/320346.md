# Issue #320346 — Allow configuring a separate (cheaper) model for context compaction (/compact)

[https://github.com/microsoft/vscode/issues/320346](https://github.com/microsoft/vscode/issues/320346)

## Summary

The requested capability remains missing on current main: manual `/compact` and agent background compaction use the active conversation endpoint. Route this feature request to chat summarization for a product decision on whether compaction should use the existing utility-model setting or receive a dedicated model setting.

## Change summary

Allow users to select a cheaper language model for manual and automatic conversation compaction instead of always using the active chat model.

## Best solution

Define a consistent model-selection contract for foreground and background compaction, preferably reusing the existing utility-model infrastructure unless compaction needs a distinct compatibility or billing boundary. Preserve summary quality, provider compatibility, context-window accounting, and predictable fallback behavior.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/intents/node/agentIntent.ts`, `extensions/copilot/src/extension/intents/node/test/agentSummarizeCommand.spec.ts`, `extensions/copilot/src/extension/prompts/node/agent/summarizedConversationHistory.tsx`, `src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts`, `src/vs/workbench/contrib/chat/browser/utilityModelContribution.ts`
- **Validation:** Extend the agent summarize-command tests to select distinct active and compaction endpoints, then assert that `/compact` and the chosen automatic-compaction scope use the configured endpoint while preserving fallback to the active endpoint when no applicable model is configured.
- **Behavior:**

  > Users can choose which available language model performs conversation compaction without changing the model used for normal chat responses. The selected scope must be explicit: manual `/compact`, automatic/background compaction, or both. When the configured model is unavailable or unset, compaction follows a documented fallback and reports failures rather than silently using an unintended model. Compacted history remains usable by the active conversation model and continues to report compaction usage accurately.
- **Trace:**

  > In extensions/copilot/src/extension/intents/node/agentIntent.ts, `handleSummarizeCommand` obtains the endpoint from the current `ChatRequest` and passes it through `SummarizedConversationHistory`; `AgentIntentInvocation._startBackgroundSummarization` similarly sends the request through `this.endpoint`. The actual summary request is assembled in extensions/copilot/src/extension/prompts/node/agent/summarizedConversationHistory.tsx. General utility model selection already exists through `chat.utilityModel` and `chat.utilitySmallModel`, registered in src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts and resolved by extensions/copilot/src/extension/prompt/vscode-node/endpointProviderImpl.ts, but agent compaction does not use those families. The boundary is compaction endpoint selection: normal chat model selection, summary format, history anchoring, and unrelated utility flows must remain unchanged.
- **Open decisions:**
  - Should compaction reuse `chat.utilitySmallModel`, reuse `chat.utilityModel`, or expose a dedicated compaction-model setting with independent persistence and documentation?
  - Should the selected compaction model govern both explicit `/compact` and automatic/background compaction, or should those flows remain independently configurable?
  - When the configured compaction model is unavailable or incompatible with the conversation context, should the observable fallback be the active chat model or an explicit compaction failure?
