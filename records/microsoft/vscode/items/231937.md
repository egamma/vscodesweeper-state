# Issue #231937 — Let's consider to use a concrete type for `toolInvocationToken`

[https://github.com/microsoft/vscode/issues/231937](https://github.com/microsoft/vscode/issues/231937)

## Summary

The API debt remains on current main: `ChatParticipantToolToken` is still `never`, while its runtime value exposes the internal invocation context. An approved concrete opaque-token implementation was closed after becoming conflicted, so the implementation should be refreshed against the current session-resource context.

## Change summary

Replace the `never`-typed tool invocation token with a concrete opaque type that prevents callers from accidentally passing unrelated token-like values.

## Best solution

Adapt the approved opaque `unique symbol` token design from https://github.com/microsoft/vscode/pull/248452 to the current `IToolInvocationContext` shape, preserving `sessionResource` and `workingDirectory` internally without exposing them through the extension API.

- **Behavior:**

  > Chat requests expose a concrete opaque `ChatParticipantToolToken` that extensions can pass back to `lm.invokeTool`, but cannot accidentally replace with a cancellation token or ordinary object. A token originating from a chat request preserves the current session and working-directory association when invoking a tool. Forged tokens are rejected, and invoking tools without chat context remains unchanged.
- **Trace:**

  > src/vscode-dts/vscode.d.ts currently aliases `ChatParticipantToolToken` to `never`. `ChatAgentRequest.to` in src/vs/workbench/api/common/extHostTypeConverters.ts creates the runtime value by freezing an `IToolInvocationContext` and casting it to `never`; `ExtHostLanguageModelTools.invokeTool` validates and casts it back before crossing to the main thread. The approved but unmerged https://github.com/microsoft/vscode/pull/248452 established the opaque `unique symbol` interface and extension-host-owned token identity approach; its old implementation keyed tokens by `sessionId`, while current main carries `sessionResource` and optional `workingDirectory`. Preserve that current context and tool-routing behavior, do not expose either internal field through the public token, and do not change tool confirmation or non-chat invocation semantics.

- **current runtime path:** src/vs/workbench/api/common/extHostTypeConverters.ts constructs the token by casting a frozen `IToolInvocationContext` containing `sessionResource` and `workingDirectory` to `never`; src/vs/workbench/api/common/extHostLanguageModelTools.ts later validates and casts that object back to the internal context.
