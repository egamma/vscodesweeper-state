# Issue #100856 — Extension doesn't activate after install

[https://github.com/microsoft/vscode/issues/100856](https://github.com/microsoft/vscode/issues/100856)

## Summary

The requested activation-failure UX remains missing on current main, and this team-authored Backlog item should stay open. Failed activation is recorded as telemetry and console output, but the Running Extensions view can remain at “Activating...” and command invocation can still end with the generic “command not found” error.

## Change summary

Clearly identify an extension whose activation failed in Running Extensions and provide a more informative error when invoking one of its unregistered commands.

## Best solution

Expose failed activation as extension runtime status and present it prominently in the extension UI, while ensuring commands contributed by that extension report the activation failure rather than an unrelated missing-command message. A maintainer should first decide whether this also warrants a notification, given the established concern that notifications make extension failures appear to be VS Code failures.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/common/extensions.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/contrib/extensions/browser/abstractRuntimeExtensionsEditor.ts`, `src/vs/workbench/services/commands/common/commandService.ts`, `src/vs/workbench/services/commands/test/common/commandService.test.ts`
- **Validation:** Use a test extension whose activate function throws, then verify that Running Extensions reports activation failure instead of “Activating...” and that invoking its contributed command reports the activation failure rather than only `command '<id>' not found`; add focused service and command tests for those states.
- **Behavior:**

  > When an installed extension fails during activation, VS Code must expose that terminal failure state rather than implying that activation is still in progress. Running Extensions should identify the failed extension and make its activation error discoverable. Invoking a command contributed by that extension should explain that activation failed instead of reporting only that the command was not found. Successfully activated extensions and genuinely unknown commands must retain their current behavior.
- **Trace:**

  > The extension host reports failure through MainThreadExtensionService.$onExtensionActivationError in src/vs/workbench/api/browser/mainThreadExtensionService.ts. AbstractExtensionService._onDidActivateExtensionError in src/vs/workbench/services/extensions/common/abstractExtensionService.ts currently records telemetry only, while IExtensionsStatus in src/vs/workbench/services/extensions/common/extensions.ts has no failure field. AbstractRuntimeExtensionsEditor in src/vs/workbench/contrib/extensions/browser/abstractRuntimeExtensionsEditor.ts treats activationStarted without activationTimes as still activating. CommandService._tryExecuteCommand in src/vs/workbench/services/commands/common/commandService.ts has only registry state and therefore emits the generic missing-command error. The boundary is activation-failure diagnostics: normal activation, runtime-error reporting, and truly unknown command behavior must not change. The notification-policy discussion is recorded at https://github.com/microsoft/vscode/issues/101242 and https://github.com/microsoft/vscode/issues/179633.
- **Open decisions:**
  - Should activation failure be surfaced only in extension-specific UI, or also through a global notification under limited conditions?
  - How should command execution associate an unregistered contributed command with the extension whose activation failed?
  - Should Running Extensions display the full activation error inline, in a hover/detail action, or through the extension details view?

## Evidence

- **current activation-error path:** src/vs/workbench/services/extensions/common/abstractExtensionService.ts `_onDidActivateExtensionError` emits telemetry but does not store the error in ExtensionStatus or fire an extension-status change.
- **runtime status model:** src/vs/workbench/services/extensions/common/extensions.ts `IExtensionsStatus` contains activationStarted, activationTimes, and runtimeErrors, but no activation-failure state or error.
- **Running Extensions behavior:** src/vs/workbench/contrib/extensions/browser/abstractRuntimeExtensionsEditor.ts includes every extension with activationStarted, and renders “Activating...” whenever activationTimes is absent; it has no failed-activation rendering path.
- **command error path:** src/vs/workbench/services/commands/common/commandService.ts waits for activation and then `_tryExecuteCommand` rejects with `command '<id>' not found` when activation did not register the contributed command, without identifying the failed extension.
- **related maintainer decision:** https://github.com/microsoft/vscode/issues/101242 documents that suppressing global error notifications for installed-extension activation failures was intentional, but it does not reject an in-context failure indication in Running Extensions.
- **overlapping discussion:** https://github.com/microsoft/vscode/issues/179633 discusses making activation failures more visible, but focuses on global UI notifications and does not fully own this older issue's Running Extensions and command-error requirements.
