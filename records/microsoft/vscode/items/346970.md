  > Starting workspace text search over a OneDrive shortcut to a shared SharePoint library reportedly freezes VS Code and progressively blocks the Windows desktop. Establish a controlled reproduction and require the resulting behavior to preserve desktop responsiveness and search cancellation while retaining normal local-file results.
- **Trace:**

  > RipgrepTextSearchEngine.searchWithRipgrep in src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts spawns ripgrep in the selected folder and forwards cancellation through child-process kill. getRgArgs supplies traversal, exclusion, size, and threading options without explicit cloud-placeholder treatment. The report at https://github.com/microsoft/vscode/issues/346970 isolates folder inclusion, but does not prove whether hydration, enumeration, ripgrep, or the Windows provider causes the hang. Diagnosis must establish that boundary before choosing a code change; do not assume SharePoint shortcuts behave like ordinary symbolic links or silently exclude all cloud-backed files.

## Evidence

- **Concrete report:** https://github.com/microsoft/vscode/issues/346970 reports Code 1.145.2 on Windows 10.0.26200, a shared SharePoint shortcut containing online-only files, and a freeze beginning when workspace text search starts. Removing that folder makes the same search complete normally.
- **Current search execution:** src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts: searchWithRipgrep launches ripgrep with the workspace folder as cwd. Cancellation calls rgProc.kill(); completion waits for the child process close event. This establishes the relevant execution boundary, not the cause of the system-wide hang.
- **Cloud-file handling:** In the same file, getRgArgs passes include/exclude globs, optional --max-filesize, --follow, and --threads, then searches '.'. The inspected path contains no explicit OneDrive/SharePoint placeholder handling; ordinary symlink controls do not establish safe handling of cloud placeholders.
- **Mitigation limits:** The reporter confirms only removing the folder from the workspace. search.followSymlinks, search.exclude, and files.watcherExclude are suggested mitigations, not verified fixes; watcher exclusions alone do not control this ripgrep content-search path.
- **Verification limits:** No Windows/OneDrive reproduction was executed in this read-only Linux checkout. Local history is shallow, and inspection identified no concrete fixing commit or verified duplicate; neither a completed close nor a not-reproducible close is supported.
