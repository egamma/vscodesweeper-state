# Issue #336250 — Chat - Input area usability improvements

[https://github.com/microsoft/vscode/issues/336250](https://github.com/microsoft/vscode/issues/336250)

## Summary

The originally reported reference-loss bug is fixed, but three distinct chat-input UX gaps remain on current main: stable invalid references, editing an existing reference, and clearer separation between `#` and `@`. Route this to the chat-input UX owners for design.

## Change summary

Make inline chat references stable and editable while giving `#` references and `@` agents distinct, predictable completion semantics.

## Best solution

Define a consistent chat-input reference contract in which invalid references remain visibly actionable, existing references can be reopened through mouse and keyboard interaction, and `#` versus `@` has an intentional division of responsibility without unexpectedly breaking existing prompts.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts`, `src/vs/workbench/contrib/chat/browser/attachments/chatDynamicVariables.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputEditorHover.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/input/editor/chatInputCompletions.test.ts`, `src/vs/workbench/contrib/chat/test/browser/attachments/chatVariables.test.ts`
- **Validation:** Add targeted chat-input completion and dynamic-variable tests covering the approved `#`/`@` result sets, invalid-reference lifecycle and send eligibility, plus an executable keyboard-accessibility check for reopening and replacing an existing reference.
- **Behavior:**

  > Inline references should remain understandable and recoverable while users edit a prompt. An unresolved reference should follow an explicitly chosen visual and submission policy rather than disappearing unexpectedly. Users should be able to reopen an existing reference and choose a replacement through both pointer and keyboard interaction. `#` and `@` completion results should follow a documented, predictable division while preserving whichever compatibility guarantees the maintainer selects.
- **Trace:**

  > The completed edit-before-reference case is tracked by https://github.com/microsoft/vscode/issues/333941 and fixed through https://github.com/microsoft/vscode/pull/333965; do not regress that behavior. BuiltinDynamicCompletions and ToolCompletions in src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts deliberately accept both chatVariableLeader and chatAgentLeader and preserve the typed leader, producing the reported overlap. ChatDynamicVariableModel in src/vs/workbench/contrib/chat/browser/attachments/chatDynamicVariables.ts owns reference tracking and decorations, including removal when an edit touches reference text. ChatAttachmentReferenceHoverParticipant in src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputEditorHover.ts handles image preview only and supplies no general replace-reference interaction. Keep the scope within chat-input reference semantics and interaction; do not redesign attachment storage or the broader completion framework.
- **Open decisions:**
  - Should `#` be reserved for context/references and `@` for agents, and what compatibility must be retained for existing prompts that use `@` for files or tools?
  - When a selected reference no longer resolves, should submission be blocked until it is repaired or removed, or should the unresolved text be sent as ordinary prompt content?
  - Which pointer and keyboard activation contract should reopen an existing reference for replacement: ordinary activation, an explicit action, or the workbench’s link-style modifier interaction?
