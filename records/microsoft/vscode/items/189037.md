# Issue #189037 — Allow extension link detection to run on exception popups

[https://github.com/microsoft/vscode/issues/189037](https://github.com/microsoft/vscode/issues/189037)

## Summary

A real extension API gap remains on current main: exception stack traces use only VS Code's built-in debug link detector, so extensions cannot recognize custom schemes such as Dart's `package:` URIs. The request is already accepted into the Backlog and no open canonical issue owns this exception-popup behavior.

## Change summary

Allow extensions to detect and handle custom links in stack traces rendered by the debug exception popup.

## Best solution

Design a reusable extension link-provider contract that can serve non-document debug surfaces, then invoke it for exception stack-trace text while retaining the existing built-in web and file-path detection.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/exceptionWidget.ts`, `src/vs/workbench/contrib/debug/browser/linkDetector.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`, `src/vscode-dts/vscode.proposed.d.ts`
- **Validation:** Add extension-host/main-thread API tests proving that a registered provider receives exception stack-trace text and returns a custom-scheme link, plus a debug browser test proving activation opens the provider-supplied target while existing web and file links remain functional.
- **Behavior:**

  > Extensions can identify ranges in a debug exception popup's stack-trace text and supply targets for schemes that VS Code's built-in detector does not understand. Provider-supplied links are clickable and open their supplied targets. Existing built-in web URL and file-path links continue to work, and plain exception text remains unchanged when no provider returns a link.
- **Trace:**

  > ExceptionWidget in src/vs/workbench/contrib/debug/browser/exceptionWidget.ts currently passes stackTrace directly to the internal LinkDetector. LinkDetector in src/vs/workbench/contrib/debug/browser/linkDetector.ts synchronously recognizes built-in web and path patterns and has no extension-provider path. The public API currently has separate DocumentLinkProvider and TerminalLinkProvider contracts in src/vscode-dts/vscode.d.ts, neither of which applies to this DOM-rendered popup. The boundary is extension link detection for non-document debug text: preserve existing built-in detection, hover behavior, accessibility text, and exception-widget layout. The related Test Peek request at https://github.com/microsoft/vscode/issues/157500 does not own this surface, while the later debug-console request https://github.com/microsoft/vscode/issues/210428 is closed.
- **Open decisions:**
  - Should the public contract be scoped to exception stack traces, or intentionally cover other non-document debug text surfaces such as the debug console?
  - What context should providers receive so extensions can distinguish the rendering surface and debug session without exposing unstable internal widget details?
  - When provider-supplied and built-in links overlap, which result takes precedence from the user's perspective?

## Evidence

- **current source gap:** src/vs/workbench/contrib/debug/browser/exceptionWidget.ts creates the internal LinkDetector and directly calls linkify for exceptionInfo.details.stackTrace; there is no extension-provider invocation on this path.
- **built-in detector boundary:** src/vs/workbench/contrib/debug/browser/linkDetector.ts documents and implements detection for web URLs and absolute or relative file paths; its link parts do not expose custom-scheme handling to extensions.
- **surface-specific APIs:** src/vscode-dts/vscode.d.ts exposes DocumentLinkProvider and TerminalLinkProvider, but exception popup content is neither a text document nor a terminal, so those existing APIs do not cover the request.
- **related request:** https://github.com/microsoft/vscode/issues/157500 concerned Test Peek output, not exception popups, and is closed; its discussion confirms that link-provider support has been tied to individual rendering surfaces.
- **canonical search:** The broader debug-console request https://github.com/microsoft/vscode/issues/210428 was created after this issue and is closed through the feature-request lifecycle, so it cannot be the canonical for this re-reviewed item.
- **extension evidence:** https://github.com/Dart-Code/Dart-Code/issues/4600 remains open and identifies this API gap as blocking navigation from Dart exception locations.
