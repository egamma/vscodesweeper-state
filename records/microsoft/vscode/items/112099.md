# Issue #112099 — Downloading files and folders should preserve executable bit

[https://github.com/microsoft/vscode/issues/112099](https://github.com/microsoft/vscode/issues/112099)

## Summary

A real gap remains on current main: VS Code can now discover executable metadata, but cross-provider downloads still copy only file contents and do not restore the executable bit. The accepted Backlog request should remain open while native and browser behavior is designed.

## Change summary

Preserve a remote file's executable bit when downloading files or folders to a local filesystem.

## Best solution

Preserve executable metadata when the source provider reports it and the destination supports Unix permissions, including recursively downloaded folders, while defining a clear fallback for browser downloads and unsupported targets.

## Plan brief

- **Likely files:** `src/vs/platform/files/common/fileService.ts`, `src/vs/platform/files/common/files.ts`, `src/vs/platform/files/node/diskFileSystemProvider.ts`, `src/vs/workbench/contrib/files/browser/fileImportExport.ts`, `src/vs/platform/files/test/node/diskFileService.integrationTest.ts`
- **Validation:** Add a cross-provider file-service copy test whose source stat reports FilePermission.Executable and whose Unix disk destination is asserted executable after copying; include a recursive-folder case and verify non-executable files remain non-executable.
- **Behavior:**

  > Downloading an executable file from a remote workspace to a Unix-like local filesystem preserves its executable status. Folder downloads preserve that status independently for each contained file, while non-executable files remain non-executable. Downloads to platforms or browser targets that cannot express Unix permissions must retain their current successful content-transfer behavior. Acceptance includes cross-provider tests for executable, non-executable, and recursive-folder downloads.
- **Trace:**

  > Native FileDownload in src/vs/workbench/contrib/files/browser/fileImportExport.ts creates a ResourceFileEdit with copy enabled, which reaches FileService.copy in src/vs/platform/files/common/fileService.ts. For different providers, doCopyFile and doCopyFolder transfer bytes and create entries but never propagate IFileStatWithMetadata.executable. Commit https://github.com/microsoft/vscode/commit/a6cb18a1abae59def0b3da269268f9c73bd02d43 added internal executable metadata, and DiskFileSystemProvider now reports it from Unix mode bits, so the original metadata blocker is partly removed. Browser download paths use Web File System Access or ordinary browser downloads, whose permission capabilities differ. Preserve existing content copying, overwrite handling, cancellation, and behavior on unsupported platforms; the uncertainty begins at the public behavior promised when the destination cannot apply executable metadata.
- **Open decisions:**
  - Should the guarantee be limited to native Unix-like destinations, or should browser downloads use a metadata-preserving container or another user-visible fallback?
  - Is the supported contract specifically the executable bit requested here, or broader permission preservation for future provider metadata?

## Evidence

- **current download path:** src/vs/workbench/contrib/files/browser/fileImportExport.ts:824-874 implements native downloads as a cross-provider ResourceFileEdit copy; browser paths at lines 658-798 write bytes through browser APIs without applying permissions.
