# Issue #152633 — Renaming a folder that is locked by an application locks up explorer for ~1 minute and eventually fails with EPERM

[https://github.com/microsoft/vscode/issues/152633](https://github.com/microsoft/vscode/issues/152633)

## Summary

The minute-long failure remains directly reproducible from current source: Windows folder renames retry `EPERM` and `EBUSY` for up to 60 seconds before surfacing the error. This accepted file-explorer bug should remain open while maintainers decide how to balance prompt locked-folder feedback against retries for transient antivirus locks.

## Change summary

Renaming a locked folder on Windows leaves the Explorer rename operation pending for roughly one minute before reporting `EPERM`.

## Best solution

Make locked-directory renames remain responsive and either fail promptly with an actionable error or present visible, cancellable retry progress, while preserving recovery from genuinely transient Windows file locks. The scope should also establish whether VS Code-owned watcher handles can be released safely before renaming.

## Plan brief

- **Likely files:** `src/vs/base/node/pfs.ts`, `src/vs/base/test/node/pfs/pfs.test.ts`, `src/vs/platform/files/node/diskFileSystemProvider.ts`, `src/vs/workbench/contrib/files/browser/fileActions.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`
- **Validation:** On Windows, hold an open handle that prevents a directory rename and verify the Explorer operation follows the chosen prompt/progress/cancellation behavior without an unexplained 60-second stall; also add or extend a PFS rename test covering persistent versus transient `EPERM`/`EBUSY` handling.
- **Behavior:**

  > When a Windows directory cannot be renamed because an application holds a lock, Explorer must remain responsive and communicate the pending or failed operation instead of appearing stuck for roughly one minute. If retries remain, their progress must be visible and cancellable; if the operation fails promptly, the error must identify the locked-resource condition. Successful renames and recovery from brief transient locks must continue to work. Acceptance includes a locked-directory scenario and a transient-lock scenario.
- **Trace:**

  > Explorer rename starts in `renameHandler` in `src/vs/workbench/contrib/files/browser/fileActions.ts`, which awaits `explorerService.applyBulkEdit` before clearing the editable state. The local disk provider reaches `DiskFileSystemProvider.rename` in `src/vs/platform/files/node/diskFileSystemProvider.ts`, which calls `Promises.rename` with its default timeout. In `src/vs/base/node/pfs.ts`, `rename` defaults `windowsRetryTimeout` to 60000 and `renameWithRetry` loops on `EACCES`, `EPERM`, and `EBUSY`; a normal rename target does not exist, so the initial target-stat check does not terminate retries for a persistently locked source folder. The related blank-row report https://github.com/microsoft/vscode/issues/197157 identifies the same awaited operation but remains a separate UI symptom. Preserve successful moves, cross-device fallback, and useful recovery from transient antivirus locks; do not broaden the work to unrelated file operations until the retry-policy boundary is decided.
- **Open decisions:**
  - Should a locked directory rename fail immediately, use a shorter fixed retry window, or retain the current long retry policy for transient Windows locks?
  - If retries remain, should Explorer keep the rename input active with cancellable progress, or leave editing mode and show progress elsewhere?
  - Is the intended scope limited to error and progress handling, or should VS Code also release and restore its own watcher handles around directory renames when it owns the lock?

## Evidence

- **current source:** `src/vs/platform/files/node/diskFileSystemProvider.ts` (`DiskFileSystemProvider.rename`) sends Explorer moves to `Promises.rename(fromFilePath, toFilePath)` without overriding its retry timeout.
- **confirmed delay:** `src/vs/base/node/pfs.ts` defines `rename(..., windowsRetryTimeout = 60000)` and `renameWithRetry`, which repeatedly retries Windows `EACCES`, `EPERM`, and `EBUSY` failures until that timeout. For a nonexistent rename target, the first-attempt target check does not abort, so a locked source directory follows the full retry path.
- **Explorer path:** `src/vs/workbench/contrib/files/browser/fileActions.ts` (`renameHandler`) awaits `explorerService.applyBulkEdit` before ending the editable state, so the Explorer rename remains pending for the duration of the filesystem retry.
- **continued reports:** The issue has independent confirmations from 2023 and 2025, including https://github.com/microsoft/vscode/issues/152633#issuecomment-3224183347 reporting that the behavior persists while an application is running.
- **canonical status:** https://github.com/microsoft/vscode/issues/247830 was closed in 2025 as a duplicate of this issue, confirming that this remains the canonical report for the long wait followed by a locked-resource failure.
- **related UI symptom:** The younger open issue https://github.com/microsoft/vscode/issues/197157 tracks the distinct blank Explorer-row symptom. Its maintainer analysis links the symptoms to the asynchronous rename operation and suggests retaining the rename box with progress or cancellation, but it cannot be the canonical duplicate for this re-reviewed older report.
