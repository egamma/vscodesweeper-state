# Issue #148558 — Keep the current reference search results and open new reference in new view

[https://github.com/microsoft/vscode/issues/148558](https://github.com/microsoft/vscode/issues/148558)

## Summary

Keep this accepted, well-supported request open: built-in reference history can rerun earlier searches, but it does not retain independently viewable result sets while a new search runs. The extension workarounds in the discussion do not establish that the native capability is implemented or declined.

## Change summary

Allow users to retain a reference search result set and open subsequent reference searches in separate views.

## Best solution

Provide an explicit way to retain independently navigable reference results in the built-in References experience. Decide the presentation and retention semantics with a maintainer before implementation, preserving the existing single-view search and history behavior.

## Plan brief

- **Likely files:** `extensions/references-view/package.json`, `extensions/references-view/src/extension.ts`, `extensions/references-view/src/tree.ts`, `extensions/references-view/src/references/index.ts`
- **Validation:** In a workspace with working reference providers, search references for symbol A, retain its results, then search symbol B. Verify that A and B remain independently accessible and navigable, and that ordinary unretained searches, history selection, refresh, and clear retain their existing behavior.
- **Behavior:**

  > Users reading code need to keep one symbol's reference results available while searching another symbol. An explicit retention action should prevent the retained results from being replaced by subsequent searches and allow each retained result set to be navigated independently. Acceptance should exercise searches for two symbols and verify that both result sets remain accessible. Ordinary searches without retention must preserve their existing behavior.
- **Trace:**

  > The built-in extension creates one SymbolsTree in extensions/references-view/src/extension.ts and contributes one references-view.tree in package.json. Reference searches in src/references/index.ts feed that tree through SymbolsTree.setInput, which replaces the active input and disposes the previous session in src/tree.ts. TreeInputHistory retains search inputs and reruns them through the same tree; it does not expose multiple retained result views. The discussion on https://github.com/microsoft/vscode/issues/148558 supplies extension alternatives and a concrete branching-navigation use case. The remaining uncertainty is the product contract for presenting and retaining independent results, not whether history already fulfills the request. Preserve existing provider integration, unretained searches, and call/type hierarchy behavior; cascading peek is separate work.
- **Open decisions:**
  - Should retained result sets appear as separate References views or as independently selectable result sets within one References surface?
  - Should retained results remain snapshots until explicitly refreshed, or automatically track changes to the workspace?
  - Should retained result sets survive a window reload, or last only for the current session?

## Evidence

- **Existing capability and remaining gap:** extensions/references-view/package.json registers one references-view.tree view, references.preferredLocation with peek/view choices, and references-view.pickFromHistory. extensions/references-view/src/tree.ts implements history by rerunning a prior input through TreeInputHistory._reRunHistoryItem; SymbolsTree.setInput replaces the active input and disposes the previous session. This is not simultaneous retention of independently viewable result sets.
- **Current search path:** extensions/references-view/src/extension.ts creates one SymbolsTree. In extensions/references-view/src/references/index.ts, both references-view.findReferences and the view-mode editor.action.showReferences handler call setInput on that same tree; neither exposes a Keep Results operation.
- **Accepted demand:** https://github.com/microsoft/vscode/issues/148558 is in Backlog with 32 community upvotes, exceeding the 20-upvote promotion threshold. Comments describe losing the parent symbol's results while following aliases and nested reference searches.
- **Discussion workarounds:** The supplied discussion recommends happiness86.vscode-references-plus, jrieken.references-plusplus, and a Multiple References Results extension. These are alternatives for retaining or revisiting searches, not proof that the requested built-in multi-result experience exists.

That decision does not cover retaining separate References tool views, and it is not an open canonical for this re-reviewed item.
