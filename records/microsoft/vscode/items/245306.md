## Evidence

- **Reporter intent:** https://github.com/microsoft/vscode/issues/245306 asks why official Node 20 requires older glibc than the reporter's Node 20.18.2 binary and how to package OSS for glibc 2.17. The reporter explicitly reiterates this distinction after reading the linked FAQ; the CentOS 7 and Amazon Linux 2 comments do not establish a separate core defect.
- **Historical packaging distinction:** https://github.com/microsoft/vscode/blob/1.98.2/build/gulpfile.reh.js constructs a glibc-specific asset name using VSCODE_NODE_GLIBC, downloads custom assets when product.nodejsRepository differs from https://nodejs.org, and selects check-requirements-linux-legacy.sh when VSCODE_NODE_GLIBC is '-glibc-2.17'. Its stock-nodejs.org download branch instead downloads the standard Node archive. The environment variable alone does not rebuild stock Node or change its ABI requirements.
- **Maintainer explanation already linked in discussion:** https://github.com/microsoft/vscode/issues/203375#issuecomment-2713481375 states that 1.98 was the last release supporting glibc below 2.28 and identifies the custom-library workaround for later versions. The linked issue is closed, so it is not an eligible duplicate canonical.
- **Current source and documented workaround:** Current build/gulpfile.reh.ts still distinguishes product-provided Node assets from stock nodejs.org assets. resources/server/bin/code-server-linux.sh applies a custom linker and library path when VSCODE_SERVER_CUSTOM_GLIBC_LINKER, VSCODE_SERVER_CUSTOM_GLIBC_PATH, and VSCODE_SERVER_PATCHELF_PATH are supplied. https://code.visualstudio.com/docs/remote/faq#_can-i-run-vs-code-server-on-older-linux-distributions documents this as an unsupported technical workaround for servers requiring glibc 2.28 or later.
