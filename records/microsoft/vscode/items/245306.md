## Summary

The central ask is an explanation of the runtime difference between a self-built OSS server and the official legacy server, not a demonstrated VS Code defect. Answer the two compatibility questions and close as a support question.

## Change summary

Explain why the official 1.98.2 server runs on GLIBC 2.17 while a self-built OSS server using a standard Node 20 binary does not.

## Best solution

Explain the distinction between the Node version and the libraries against which its binary was built. For a custom OSS distribution, compatibility requires a consistently compatible runtime and native dependencies; for current official servers, point to the documented custom-sysroot workaround without promising restored GLIBC 2.17 support.

- **Proposed comment:**

  > Thanks for the context. A Node version does not uniquely determine its GLIBC requirement: that also depends on how the binary was built. The 1.98.2 server build distinguishes standard nodejs.org downloads from product-specific artifacts and includes a GLIBC 2.17 legacy packaging path: https://github.com/microsoft/vscode/blob/1.98.2/build/gulpfile.reh.js. This explains why the official legacy server can behave differently from your OSS package without using the newer custom-sysroot workaround.
  > 
  > For your OSS build, a GLIBC 2.17-compatible Node binary alone is not sufficient unless the server's native dependencies are compatible too. Current official servers require GLIBC 2.28; the documented alternative for older hosts is the custom-sysroot workaround at https://code.visualstudio.com/docs/remote/faq#_can-i-run-vs-code-server-on-older-linux-distributions, which is not an officially supported configuration. Closing this as a compatibility/build question rather than a VS Code bug.
