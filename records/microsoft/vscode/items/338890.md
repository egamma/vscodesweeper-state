# Issue #338890 — NativeEditContext: tapping a keyboard suggestion on Android corrupts the line

[https://github.com/microsoft/vscode/issues/338890](https://github.com/microsoft/vscode/issues/338890)

## Summary

Excellent, source-verified bug report: three compounding defects in NativeEditContext's Android/on-screen-keyboard handling, all confirmed present on current main via direct code inspection. Kept open for a fix, not a close.

## Change summary

On Android with the on-screen keyboard and NativeEditContext, tapping a keyboard suggestion after moving the caret corrupts the line, because the EditContext text buffer is never fully replaced and the caret/selection math is computed against stale/incorrect offsets.

## Best solution

Fix the three specific defects in nativeEditContext.ts: replace the full previous EditContext text length (not the previous update length) in `_updateEditContext`, measure `positionDelta` from the end of the typed text relative to `min(selectionStartOffset, updateRangeStart)`, and read the prefix/suffix substrings using pre-edit offsets consistently in `_emitTypeEvent`.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts`
- **Validation:** Add/extend a NativeEditContext unit test simulating a collapsed-selection textupdate event after prior edits, asserting `editContext.text` matches the model text (not padded with stale tail characters) and that resulting caret/selection offsets match the keyboard's reported selection, not a computed drift.
- **Behavior:**

  > After typing text and then receiving a keyboard `textupdate` event (as Android/Gboard sends when committing a suggestion after moving the caret), the EditContext's internal `text` buffer must always match the current model line exactly — no leftover characters from prior edits appended after it — and the caret/selection reported back to the EditContext must equal the keyboard's actual reported selection, not an offset drift from stale prefix/suffix copies. Acceptance: the three reproduction sequences in the issue (tap mid-word suggestion, mid-word replacement, caret moved by tap) each produce the expected line content, not a corrupted one.
- **Trace:**

  > Three co-located defects in src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts: (1) `_updateEditContext` (line 421) calls `updateText(0, this._previousEditContextText.length, newText)`, replacing only the length of the previous write instead of the full existing buffer, so keyboard-added characters accumulate past the line end; (2) `_emitTypeEvent`'s `positionDelta` (line 458) is computed as `e.selectionStart - (e.updateRangeStart + e.text.length)`, which doesn't account for copied prefix/suffix text also present in `text`, so the caret can land far past the keyboard's actual selection; (3) the prefix/suffix substrings at lines 450 and 454 are read from `this._editContext.text` using offsets that are valid pre-edit but the buffer has already been mutated by Blink by the time they're read. Boundary: do not touch composition-mode (IME with underline) handling — the report is specifically about the no-composition, plain-insertion Android path. Prior related change referenced by reporter: microsoft/vscode#298272 (first released 1.111), not independently verified here.
- **Open decisions:**
  - Should the full-length replace in `_updateEditContext` unconditionally use the full previous EditContext text length, or does that risk perf/behavior regressions on other (non-Android) EditContext consumers that a maintainer should weigh in on before changing this shared code path?

## Evidence

- **defect 1 confirmed:** src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts:421 calls `this._editContext.updateText(0, this._previousEditContextText.length, newText)`, replacing only as many characters as the previous write instead of the whole prior text, matching the reporter's described tail-duplication bug.
- **defect 2 confirmed:** Line 458: `positionDelta = e.selectionStart - (e.updateRangeStart + e.text.length)` ignores the copied prefix/suffix text length as the reporter describes, causing the caret to land past the keyboard's actual selection.
- **defect 3 confirmed:** Lines 450 and 454 read `this._editContext.text.substring(...)` at offsets computed before the edit was applied, i.e. from the already-mutated buffer, as claimed in the report.
- **reporter identifies regression source:** Report cites PR/issue #298272 (first released 1.111) as replacing a full-buffer `updateText(0, Number.MAX_SAFE_INTEGER, text)` with the current partial-length version; not independently verified via git blame in this review but consistent with current code shape.
