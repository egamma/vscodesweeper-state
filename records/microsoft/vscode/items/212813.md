# Issue #212813 — VSCode started with `--extensionDevelopmentPath` crashes after the computer enters in sleep mode

[https://github.com/microsoft/vscode/issues/212813](https://github.com/microsoft/vscode/issues/212813)

## Summary

The defect remains on current main: a transient remote socket close during extension development is treated as extension-host termination, which ultimately closes the development window instead of allowing normal reconnection.

## Change summary

A Windows extension-development window connected to WSL terminates after sleep interrupts the remote extension-host socket.

## Best solution

Remote extension-development sessions should tolerate transient socket loss through the existing persistent-protocol reconnection flow, while preserving the current window-close behavior for a genuinely terminated development extension host.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/common/remoteExtensionHost.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts`, `src/vs/workbench/services/extensions/test/common/remoteExtensionHost.test.ts`
- **Validation:** Add a targeted RemoteExtensionHost lifecycle test that emits a transient socket-close event during extension development and verifies that `onExit` does not fire before reconnection; retain coverage that permanent protocol disposal fires `onExit`, then run that test suite.
- **Behavior:**

  > An extension-development window connected to WSL must remain open when sleep or a temporary network interruption closes the remote extension-host socket. It should enter the normal remote reconnection flow and resume when the connection returns. A permanent extension-host termination must still end the development session according to the established lifecycle. Acceptance requires a transient-close test and a permanent-disposal test covering these distinct outcomes.
- **Trace:**

  > RemoteExtensionHost.start in src/vs/workbench/services/extensions/common/remoteExtensionHost.ts registers both `onDidDispose` and `onSocketClose`; only development hosts convert the first socket-close event directly into `_onExtHostConnectionLost`. That fires `onExit`, which AbstractExtensionService treats as a development-host exit and NativeExtensionService turns into `closeWindow()`. PersistentProtocol in src/vs/base/parts/ipc/common/ipc.net.ts separately supports reconnecting with a replacement socket, so the development-only listener prevents that recovery path. The maintainer diagnosis at https://github.com/microsoft/vscode/issues/212813#issuecomment-2147341288 confirms this same flow. Preserve permanent-disposal handling and normal non-development remote behavior; the uncertainty begins at debugger-session behavior during and after reconnection.
- **Open decisions:**
  - Should an attached extension-host debugging session remain attached across remote reconnection, or be ended and reattached after the remote host reconnects?
  - If the remote extension host cannot reconnect permanently, should the extension-development window retain its current close-on-host-exit behavior or remain open with a disconnected-state error?

## Evidence

- **confirmed diagnosis:** A VS Code maintainer traced the failure to the socket-close handler and explained that development remote extension hosts do not attempt reconnection: https://github.com/microsoft/vscode/issues/212813#issuecomment-2147341288
- **current source:** src/vs/workbench/services/extensions/common/remoteExtensionHost.ts:136-144 still calls `_onExtHostConnectionLost` immediately from `protocol.onSocketClose` when `_isExtensionDevHost` is true; ordinary remote sessions do not take that path.
- **window termination path:** The resulting exit reaches AbstractExtensionService._onExtensionHostCrashOrExit in src/vs/workbench/services/extensions/common/abstractExtensionService.ts:872-882, then NativeExtensionService._onExtensionHostExit in src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts:471-488, which calls `closeWindow()` for a development host.
- **reconnection capability:** PersistentProtocol already supports socket replacement through `beginAcceptReconnection` and `endAcceptReconnection` in src/vs/base/parts/ipc/common/ipc.net.ts:952-989, so the development-only socket-close handling bypasses an existing recovery mechanism.
