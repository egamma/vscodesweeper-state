# Issue #212813 — VSCode started with `--extensionDevelopmentPath` crashes after the computer enters in sleep mode

[https://github.com/microsoft/vscode/issues/212813](https://github.com/microsoft/vscode/issues/212813)

## Summary

The defect remains in current main: a transient remote extension-host socket close bypasses the persistent reconnection flow for extension-development windows and ultimately closes the window. Keep this open for the extension-host/remote owners to decide the correct debugger-aware reconnection lifecycle.

## Change summary

An extension-development window connected to WSL closes after sleep because the transient remote extension-host disconnection is treated as a terminal host exit.

## Best solution

Remote extension-development hosts should survive transient WSL socket loss through the existing persistent reconnection flow, while still closing the development window after a genuine host exit or permanent connection failure. The debugger attachment lifecycle and terminal-failure signal need to be defined before implementing that distinction.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/common/remoteExtensionHost.ts`, `src/vs/platform/remote/common/remoteAgentConnection.ts`, `src/vs/workbench/services/extensions/test/browser/remoteExtensionHost.test.ts`
- **Validation:** Add a targeted RemoteExtensionHost unit test that simulates a transient socket close followed by ConnectionGain and asserts that onExit does not fire, then simulates the chosen permanent-failure event and asserts that onExit fires exactly once.
- **Behavior:**

  > An Extension Development Host connected to WSL must remain open when sleep or another transient interruption closes its remote socket and reconnection succeeds. Its debugging session must remain usable after recovery. The development window must still close after an actual remote extension-host exit or an exhausted/permanent reconnection failure, and ordinary non-development remote windows must retain their current behavior.
- **Trace:**

  > RemoteExtensionHost.start in src/vs/workbench/services/extensions/common/remoteExtensionHost.ts registers an extension-development-only onSocketClose listener that immediately calls _onExtHostConnectionLost. That emits onExit, which AbstractExtensionService routes through NativeExtensionService._onExtensionHostExit; the native implementation stops extension hosts, disposes the management connection, and closes the window. Meanwhile, PersistentConnection in src/vs/platform/remote/common/remoteAgentConnection.ts treats the same socket close as recoverable and starts its reconnection loop, so the development-host listener terminates the window before recovery can succeed. The reporter's flow and the maintainer diagnosis at https://github.com/microsoft/vscode/issues/212813#issuecomment-2147341288 confirm this path; https://github.com/microsoft/vscode/issues/308408 provides a later independent observation. The boundary is the extension-development remote-host lifecycle: normal remote reconnection behavior, genuine host exits, and expected explicit development-session shutdown must not change.
- **Open decisions:**
  - Which signal should terminate a remote Extension Development Host window: protocol disposal, ReconnectionPermanentFailure, confirmed remote process exit, or a combination?
  - Can the existing debugger attachment remain valid across PersistentConnection recovery, or must it be explicitly reattached after ConnectionGain?
  - Should transient reconnection be allowed during both startup handshake and an established extension-development session, or only after initialization?

## Evidence

- **maintainer diagnosis:** https://github.com/microsoft/vscode/issues/212813#issuecomment-2147341288 confirms that sleep closes the WSL extension-host socket and that the extension-development path gives up instead of reconnecting.
- **current source:** src/vs/workbench/services/extensions/common/remoteExtensionHost.ts:136-144 still calls _onExtHostConnectionLost immediately from protocol.onSocketClose when _isExtensionDevHost is true.
- **reconnection bypass:** src/vs/platform/remote/common/remoteAgentConnection.ts:580-605 and 645-729 independently start the PersistentConnection reconnection loop on socket close; the RemoteExtensionHost listener reports an exit before that recovery can complete.
- **window termination:** src/vs/workbench/services/extensions/common/remoteExtensionHost.ts:187-203 emits onExit, and src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts:471-487 handles an extension-development host exit by stopping hosts, disposing the management connection, and calling closeWindow().
- **later corroboration:** https://github.com/microsoft/vscode/issues/308408 independently captured the same socket-close/reconnection race in 2026. That issue is closed and therefore cannot serve as a duplicate canonical; its later workaround addressed a separate WSL mirrored-networking failure.
