# Issue #189517 — Autoclosing pairs is represented as object and as array of string

[https://github.com/microsoft/vscode/issues/189517](https://github.com/microsoft/vscode/issues/189517)

## Summary

The extension API still forwards undefined pair delimiters when given JSON-style tuple entries, allowing malformed configuration to break editor initialization. Keep this accepted, team-authored issue open for API-boundary hardening; the related reports do not establish a qualifying duplicate or landed fix.

## Change summary

Prevent mixed tuple/object auto-closing pairs passed from parsed language configuration files from causing downstream editor exceptions.

## Best solution

Keep malformed extension configuration from reaching editor pair construction, with an actionable diagnostic or explicitly supported normalization. Resolve whether the imperative API should accept JSON-style tuples before treating those representations as interchangeable.

- **Behavior:**

- **Trace:**

  > ExtHostLanguageFeatures._serializeAutoClosingPair reads object properties from each entry without checking its shape, so tuple entries produce undefined open and close values. MainThreadLanguageFeatures.$setLanguageConfiguration forwards them into the language configuration service; CharacterPairSupport constructs the conditional pairs, and AutoClosingPairs subsequently dereferences open.charAt. By contrast, LanguageConfigurationFileHandler._extractValidAutoClosingPairs validates and normalizes tuples on the JSON-file path. The public API currently requires AutoClosingPair objects with SyntaxTokenType exclusions, so JSON/API equivalence is not established. The confirmed diagnosis and request for API-boundary protection appear in https://github.com/microsoft/vscode/issues/189109#issuecomment-1663115862 and https://github.com/microsoft/vscode/issues/189109#issuecomment-1663398249. Preserve existing JSON-file support and valid API behavior; do not fold the separate string-valued notIn report into this fix without an explicit scope decision.
- **Open decisions:**
  - Should setLanguageConfiguration reject JSON-style tuple entries with an actionable diagnostic under its existing object-only contract, or explicitly accept and normalize those tuples?
