# Issue #312578 — workbench.secondarySideBar.defaultVisibility is ignored in Agents

[https://github.com/microsoft/vscode/issues/312578](https://github.com/microsoft/vscode/issues/312578)

## Summary

The gap remains on current main: the Agents layout controller deliberately opens Files for a new session when it has no Agents-specific visibility state, without consulting `workbench.secondarySideBar.defaultVisibility`. A later fix preserved closing the pane from an uncreated session, but it does not cover the reported setting or closing it from a created session.

## Change summary

Opening a new Agents session reopens the secondary sidebar despite the global default-visibility setting and the user's preceding close action.

## Best solution

Define how the global secondary-sidebar default and the Agents-specific persisted choice interact, then make new-session layout restoration honor that precedence without changing per-session restoration for existing sessions.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/layout/browser/desktopSessionLayoutController.ts`, `src/vs/sessions/contrib/layout/test/browser/desktopSessionLayoutController.test.ts`
- **Validation:** Add focused LayoutController tests covering `workbench.secondarySideBar.defaultVisibility: hidden`: after closing the auxiliary bar on a created session, activating a new untitled session must not open the Files container; tests must also pin the chosen behavior after an explicit show.
- **Behavior:**

  > With `workbench.secondarySideBar.defaultVisibility` set to `hidden`, opening a new Agents session must not unexpectedly reveal the secondary sidebar after the user has closed it. Existing-session visibility restoration must remain per-session. Acceptance must cover creating a new session after closing the pane and the precedence selected for a later explicit show.
- **Trace:**

  > `LayoutController._syncAuxiliaryBarVisibility` in `src/vs/sessions/contrib/layout/browser/desktopSessionLayoutController.ts` treats an uncreated session with no `_newSessionViewState` as default-visible and opens the Files container. The global setting is interpreted by `src/vs/workbench/browser/layout.ts`, but the Sessions controller does not read it. Commit https://github.com/microsoft/vscode/commit/63cb2689e908aa92b92bb31876e9b72d63f9a296 covers only toggling the whole side pane while the active session is uncreated; its created-session branch remains a no-op. Preserve existing per-session restoration and the Changes-versus-Files container selection; the uncertainty is limited to precedence between the global default and explicit Agents visibility state.
- **Open decisions:**
  - When `workbench.secondarySideBar.defaultVisibility` is `hidden`, should it only initialize the new-session shared visibility before the first explicit Agents-window choice, or should it continue suppressing automatic opening for every new session even after the user explicitly shows the pane?

## Evidence

- **current source:** `src/vs/sessions/contrib/layout/browser/desktopSessionLayoutController.ts` documents `_newSessionViewState === undefined` as defaulting the auxiliary bar to visible; `_syncAuxiliaryBarVisibility` then calls `_openDefaultAuxiliaryBarContainer()` for every uncreated session unless that Agents-specific state is explicitly false. The controller never reads `workbench.secondarySideBar.defaultVisibility`.
- **setting semantics:** `src/vs/workbench/browser/layout.ts` reads `workbench.secondarySideBar.defaultVisibility` and maps `hidden` to a hidden auxiliary bar, but the Sessions controller subsequently has an independent new-session auto-open path.
- **partial related fix:** https://github.com/microsoft/vscode/pull/323109, merged as https://github.com/microsoft/vscode/commit/63cb2689e908aa92b92bb31876e9b72d63f9a296, records a whole-side-pane close only when the active session is uncreated. Its diff explicitly leaves created sessions unchanged and does not consult the reported setting.
