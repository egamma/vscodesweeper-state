# Issue #313466 — Copilot Chat: Provide approval mechanism (and obvious denial notification) when fetching resources

[https://github.com/microsoft/vscode/issues/313466](https://github.com/microsoft/vscode/issues/313466)

## Summary

Keep open: current fetch tooling supports approval, but does not fully cover the requested denial explanation and recovery experience. Source inspection confirms that network-blocked URLs can still receive the reported misleading 'invalid URL' completion message.

## Change summary

Clearly explain rejected fetches and provide an approval or recovery action when the applicable restrictions permit it.

## Best solution

Distinguish malformed URLs, user-denied requests, and network-policy blocks in the fetch tool's displayed outcome. Provide a discoverable approval-management or retry path for user-configurable restrictions without allowing approval to override enforced policy.

## Evidence

- **Existing approval capability:** src/vs/workbench/contrib/chat/electron-browser/builtInTools/fetchPageTool.ts declares canRequestPreApproval and canRequestPostApproval. FetchWebPageTool.prepareToolInvocation constructs 'Fetch web page?' confirmations for qualifying untrusted resources, so approval is not universally absent.
- **Remaining misleading-denial path:** In fetchPageTool.ts, _parseUris places network-filter-rejected HTTP(S) URLs into blockedUris. prepareToolInvocation then combines blockedUris with invalidUris in the same invalid array and renders the exact reported 'Fetched resource, but the following was an invalid URL' message. Blocked URLs are excluded from urlsNeedingConfirmation, while invoke separately returns the network filter's explanatory error to the model.
- **Existing configuration is partial coverage:** src/vs/workbench/contrib/chat/common/constants.ts identifies chat.tools.urls.autoApprove. That setting and the existing confirmation flow do not establish an after-the-fact recovery action for the blocked-URL completion path above.
