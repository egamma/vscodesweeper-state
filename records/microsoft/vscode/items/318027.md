# Issue #318027 — GitHub Copilot Chat is unresponsive

[https://github.com/microsoft/vscode/issues/318027](https://github.com/microsoft/vscode/issues/318027)

## Summary

The attached extension-host profile confirms a roughly 21-second synchronous stall while Copilot constructs a model request for a long agent conversation. This has a distinct profiled request-building path from the renderer and notification freezes in the related reports, so it should remain open for diagnosis rather than be consolidated speculatively.

## Change summary

Long-running local-agent conversations grow beyond 2 GB and block the Copilot Chat extension host long enough for VS Code to report it as unresponsive.

## Best solution

Profile and bound request construction for large agent histories so serialization or transformation is incremental or performed away from the extension-host event loop, while also ensuring completed conversation state is not retained unnecessarily.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts`, `extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts`, `extensions/copilot/src/platform/networking/common/networking.ts`, `extensions/copilot/src/platform/tokenizer/node/tokenizer.ts`
- **Validation:** Add a performance regression test that builds and submits a synthetic long agent history representative of the report, asserting request construction completes without a multi-second extension-host event-loop stall and without unbounded retained-memory growth across repeated turns.
- **Behavior:**

  > A long-running local-agent conversation must remain responsive when another model request is prepared. Request construction must not block the extension-host event loop for seconds, and repeated turns must not cause conversation-related memory to grow without a bound. Existing request payload semantics, tool history, and model-specific request formats must remain unchanged.
- **Trace:**

  > The reporter's extension-host CPU profile contains a single approximately 21.29-second sample under bundled `createRequestBody`, reached from `fetchMany` and `_makeChatRequest2`; the process snapshot also shows severe memory pressure. On current main, `ChatMLFetcherImpl.fetchMany` in `extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts` calls `IChatEndpoint.createRequestBody` synchronously before network activity. `ChatEndpoint.createRequestBody` in `extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts` selects the Responses, Messages, or CAPI body builder, but the minified frame cannot be mapped confidently to one current builder, so diagnosis should begin by instrumenting those paths with a large retained history. Keep renderer virtualization and OS-notification behavior out of scope because https://github.com/microsoft/vscode/issues/316407 and https://github.com/microsoft/vscode/issues/281743 exercise different processes and stacks.
- **Open decisions:**
  - What upper-bound behavior should users observe when a conversation is too large to prepare within the responsiveness budget: automatic history compaction, an explicit size warning, or both?

## Evidence

- **confirmed profile:** The profile attached at https://github.com/microsoft/vscode/issues/318027#issuecomment-4521511827 records a 21.4-second capture in which one sample accounts for about 21.29 seconds inside an anonymous bundled Copilot function called through `invokeFunction` from `createRequestBody`, `fetchMany`, and `_makeChatRequest2`.
- **observed impact:** The report records a 1,471 MB extension-host process with only 0.80 GB system memory free, while the reporter observed Copilot Chat consuming more than 2 GB during a long local-agent conversation.
- **current request path:** `extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts` synchronously calls `chatEndpoint.createRequestBody` before starting request logging and network work; `extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts` dispatches that construction through `createResponsesRequestBody`, `createMessagesRequestBody`, or `createCapiRequestBody`.
- **not the renderer canonical:** https://github.com/microsoft/vscode/issues/281743 primarily tracks whole-window renderer freezes, including OS-notification blocking, while this issue supplies an extension-host profile rooted in model request construction. https://github.com/microsoft/vscode/issues/316407 concerns chat-view rendering and scrolling, also a different code path.
