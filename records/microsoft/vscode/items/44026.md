# Issue #44026 — [theming] customize file icons in settings

[https://github.com/microsoft/vscode/issues/44026](https://github.com/microsoft/vscode/issues/44026)

## Summary

This remains the canonical, well-supported request for overriding file-icon associations without maintaining a complete icon-theme extension. Current main still exposes only theme selection, while the Backlog feature request has 102 community upvotes.

## Change summary

Allow users to override filename, extension, language, and folder icon associations through settings while retaining the selected file icon theme.

## Best solution

Add a theme-aware customization setting analogous to color customizations, then merge validated user associations into the selected file icon theme with documented precedence. A maintainer should first decide whether overrides may reference only icons supplied by the active theme or may also define custom image assets.

## Vision fit

- **Fit:** unclear
- **Reason:** Settings-based icon overrides improve workbench customization and settings fidelity, but unrestricted custom assets or extensive association controls could conflict with the lean-core and extension-first guardrails.
- **Evidence:** The durable Workbench & core UX theme includes settings fidelity, while the values also state that “The power lives in extensions” and favor a lightweight default experience.

## Plan brief

- **Likely files:** `src/vs/workbench/services/themes/common/workbenchThemeService.ts`, `src/vs/workbench/services/themes/common/themeConfiguration.ts`, `src/vs/workbench/services/themes/browser/workbenchThemeService.ts`, `src/vs/workbench/services/themes/browser/fileIconThemeData.ts`, `src/vs/workbench/services/themes/test/browser/fileIconThemeData.test.ts`
- **Validation:** Extend the FileIconThemeData tests and theme-service configuration tests to verify that user associations override selected-theme associations, unaffected associations remain intact, theme changes recompute the merged result, and invalid or unavailable icon references are rejected or ignored according to the chosen contract; run the targeted `FileIconThemeData` and workbench theme service unit suites.
- **Behavior:**

  > Users can customize selected file-icon-theme associations without creating or publishing a replacement theme extension. Overrides cover the association categories approved by the maintainer and coexist with all unaffected definitions from the active theme. The precedence, theme scoping, configuration scope, and handling of missing icon definitions are stable and documented. Changing the active theme or the customization setting updates rendered icons without altering language associations or syntax highlighting.
- **Trace:**

  > The selectable theme setting is registered in src/vs/workbench/services/themes/common/themeConfiguration.ts through `ThemeSettings.FILE_ICON_THEME`; there is no icon equivalent of `workbench.colorCustomizations`. FileIconThemeLoader in src/vs/workbench/services/themes/browser/fileIconThemeData.ts loads one extension resource and converts its filename, extension, folder, and language associations directly into CSS. WorkbenchThemeService listens for `workbench.iconTheme` changes but has no customization-change path to reload the active file-icon theme. The completed work in https://github.com/microsoft/vscode/issues/14662 supplies fallback icons from language extensions and must remain unchanged; it does not satisfy user overrides. The boundary is file-icon theme configuration and loading—do not change `files.associations`, language detection, or syntax-highlighting behavior. Uncertainty starts at the public setting contract: whether users may reference existing theme definitions only or supply assets, how overrides are scoped to themes/workspaces, and which association categories are supported.
- **Open decisions:**
  - May a customization only map names, extensions, folders, and language IDs to icon definitions already supplied by the active theme, or may it also define custom SVG/PNG/font assets?
  - Are overrides global across icon themes, theme-specific in the style of color customizations, or both, and which layer wins when both are present?
  - Which configuration scopes are supported—user/profile only, or workspace and folder settings as well?
  - Which association categories are in the initial contract: filenames and extensions only, or also language IDs, folder names, expanded folders, and root folders?

## Evidence

- **current configuration:** src/vs/workbench/services/themes/common/themeConfiguration.ts registers `workbench.iconTheme` only as selection of an installed theme; unlike workbench colors and token colors, it defines no file-icon customization setting.
- **current loader boundary:** src/vs/workbench/services/themes/browser/fileIconThemeData.ts reads `fileExtensions`, `fileNames`, `folderNames`, and `languageIds` solely from the selected extension-provided icon-theme document and generates CSS from those associations; it does not merge user settings.
- **different shipped capability:** https://github.com/microsoft/vscode/issues/14662 was completed by https://github.com/microsoft/vscode/pull/118846 and lets language extensions provide fallback icons. That does not let users override an existing theme's associations or assign their own icons.
- **canonical status:** The newer https://github.com/microsoft/vscode/issues/183176 was closed explicitly as a duplicate of https://github.com/microsoft/vscode/issues/44026, confirming this issue owns the user-customization request.
