# Issue #168127 — Support for different default language

[https://github.com/microsoft/vscode/issues/168127](https://github.com/microsoft/vscode/issues/168127)

## Summary

Keep open: current localization still assumes English source strings, and a maintainer-supported implementation is awaiting review in two open PRs. The issue already has the appropriate localization area label.

## Change summary

Allow extensions to declare a non-English source locale and load English translations from bundle.l10n.en.json.

## Best solution

Review the coordinated core and localization-tooling changes in https://github.com/microsoft/vscode/pull/238485 and https://github.com/microsoft/vscode-l10n/pull/178. Deliver extension-specific default locales while preserving the no-bundle-loading fast path for existing English-source extensions.

## Evidence

- **Current capability gap:** In src/vs/workbench/api/common/extHostLocalizationService.ts, the constructor sets isDefaultLanguage from appLanguage === LANGUAGE_DEFAULT; src/vs/base/common/platform.ts defines LANGUAGE_DEFAULT as 'en'. Both initializeLocalizedMessages and getMessage bypass bundle loading or lookup for English. Consequently, the reporter's l10n.t('Hola') returns the inline Spanish string even when bundle.l10n.en.json exists.
- **Manifest support:** src/vs/platform/extensions/common/extensions.ts:355-357 declares l10n?: string. ExtHostLocalizationService.getBundleLocation treats it as a directory path, not an object with defaultLocale. The current built-in localization surface does not cover the requested per-extension source locale; the custom translator in the discussion is a workaround, not native support.
- **Open core implementation:** https://github.com/microsoft/vscode/pull/238485 was verified OPEN with mergedAt null. Its body explicitly references this issue and proposes l10n: { location, defaultLocale }, English-bundle loading for non-English-source extensions, and backward compatibility for existing manifests.
- **Open tooling implementation:** https://github.com/microsoft/vscode-l10n/pull/178 was verified OPEN. It explicitly references this issue and coordinates manifest parsing in export with source-language handling in generate-xlf.
- **Maintainer-supported direction:** The supplied discussion records a maintainer proposing an opt-in defaultLocale manifest field to avoid unnecessary English-case bundle requests, requiring core support, and offering to review the implementation. The complete contributor discussion at https://github.com/microsoft/vscode/issues/168127#issuecomment-2600142931 and https://github.com/microsoft/vscode/issues/168127#issuecomment-2607111026 confirms the coordinated runtime and tooling approach.
