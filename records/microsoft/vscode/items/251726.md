# Issue #251726 — Support MCP Debugging with any command (e.g. `bun`, `deno`, `pnpm run server.ts`)

[https://github.com/microsoft/vscode/issues/251726](https://github.com/microsoft/vscode/issues/251726)

## Summary

Keep open: MCP development-mode debugging still rejects Bun and Deno, and a maintainer explicitly supported adding those runtimes. Package-manager wrappers have a separate child-process limitation; neither the existing configuration nor the reporter's Node workaround covers the central request.

## Change summary

Allow MCP server debugging with alternative JavaScript runtimes and, where feasible, commands that launch the server indirectly.

## Best solution

Extend MCP development-mode debugging to supported alternative runtimes without requiring projects to switch to Node. Preserve the distinction between direct runtime launches and npm/pnpm wrappers: the latter need a separately established child-process debugging solution, not merely removal of the executable check.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/common/mcpDevMode.ts`, `src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts`, `src/vs/workbench/contrib/mcp/test/common/mcpDevMode.test.ts`

Validate actual Bun/Deno MCP servers by starting them through MCP development mode, hitting a breakpoint in server code during a tool call, and confirming stdio tool responses still work; test wrapper commands separately only if that scope is approved.
- **Behavior:**

  > Developers should be able to debug an MCP server running under a supported alternative JavaScript runtime without converting its launch to Node. Acceptance requires hitting a breakpoint in the server's source while retaining working MCP stdio communication and existing Node/Python debugging behavior. Direct Bun/Deno support must not be presented as support for npm/pnpm scripts unless attachment to the spawned server process is demonstrated.
- **Trace:**

  > McpDevModeDebugging.transform in src/vs/workbench/contrib/mcp/common/mcpDevMode.ts handles only node and debugpy, validates executable names, and transforms launch arguments before attaching a debugger. The configuration schema in src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts exposes the same two choices. In https://github.com/microsoft/vscode/issues/251726, the maintainer accepted alternative-runtime support but identified child-process attachment as the reason package-manager wrappers were excluded. Source inspection establishes the gap, not that Node's adapter or inspector arguments work unchanged for Bun/Deno. Preserve existing Node/debugpy launch semantics and MCP stdio transport; protocol compatibility and the configuration contract remain to be established.
- **Open decisions:**
  - Should alternative runtimes use explicit runtime-specific dev.debug.type values, or should the existing JavaScript debugging configuration infer the runtime from the launch command?

## Evidence

- **Existing capability and remaining gap:** src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts:135-179 exposes only node and debugpy under dev.debug. There is no Bun, Deno, or arbitrary-launch debugging option in this schema.
- **Current launch restriction:** McpDevModeDebugging.transform in src/vs/workbench/contrib/mcp/common/mcpDevMode.ts checks the node branch against /node[0-9]*$/ and throws for other commands. It then starts a pwa-node attach session and prepends --inspect-brk=127.0.0.1:<port>; accepting another executable alone would not establish runtime compatibility or wrapper child-process attachment.
- **Maintainer-supported direction:** In https://github.com/microsoft/vscode/issues/251726, connor4312's June 18, 2025 comments explicitly support adding Deno and Bun, explain why npm/pnpm child-process launches were excluded, and identify mcpDevMode.ts as the implementation entry point. A decline close would contradict that accepted direction.
- **Workaround is partial:** The reporter's June 17, 2025 comment in https://github.com/microsoft/vscode/issues/251726 uses node with tsx/esm and experimental TypeScript stripping. This enables a Node-based launch but does not preserve a Bun/Deno runtime or support pnpm scripts.
