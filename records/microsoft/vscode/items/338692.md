# Issue #338692 — New line in auto-closing pair moves cursor to the line below

[https://github.com/microsoft/vscode/issues/338692](https://github.com/microsoft/vscode/issues/338692)

## Summary

Traced the root cause in the cursor auto-closing command: the cursor-position and decoration-range math assumes the closing pair text is single-line and simply subtracts its character length, which breaks when the close string itself contains a newline (as in the reported `\nend` pair) — a real, still-open defect worth fixing.

## Change summary

When a language's autoClosingPairs close string contains a newline (e.g. `close: "\nend"`), the cursor lands on the wrong line/column after auto-closing instead of staying right after the typed open text, and onEnter rules aren't applied on the new line.

## Best solution

Fix the position/range math in BaseTypeWithAutoClosingCommand / TypeWithAutoClosingCommand (src/vs/editor/common/cursor/cursorTypeEditOperations.ts) and the ReplaceCommandWithOffsetCursorState delta logic (src/vs/editor/common/commands/replaceCommand.ts) to compute line/column offsets by walking the actual lines of the inserted close text rather than treating its length as a flat column offset; separately decide, as a product question, whether/how onEnter rules should fire for the injected line and how the auto-closed decoration ranges (cursor.ts, autoClosedCharactersRanges) should represent a multi-line close string.

## Plan brief

- **Likely files:** `src/vs/editor/common/cursor/cursorTypeEditOperations.ts`, `src/vs/editor/common/commands/replaceCommand.ts`, `src/vs/editor/common/cursor/cursor.ts`
- **Validation:** A cursor/typing test using a language configuration with `autoClosingPairs: [{ open: 'begin', close: '\nend' }]` that types `begin` and asserts the cursor stays at the end of `begin` on the original line (not on the `end` line), and that the auto-closed decoration range is well-formed.
- **Behavior:**

  > Typing an auto-closing pair's `open` string whose `close` string contains a newline (e.g. `open: 'begin'`, `close: '\nend'`) should insert the full close text on the following line(s) but leave the cursor immediately after the typed open text on the original line — not on the newly-inserted line. Acceptance: a typing test with such a language configuration confirms the cursor position and that the tracked auto-closed-character range covers the actual multi-line close text without producing a malformed range.
- **Trace:**

  > The defect is in TypeWithAutoClosingCommand (src/vs/editor/common/cursor/cursorTypeEditOperations.ts:907-914), which sets `columnDeltaOffset = -closeCharacter.length` assuming the close text is single-line; this offset is applied by ReplaceCommandWithOffsetCursorState.computeCursorState (src/vs/editor/common/commands/replaceCommand.ts:131-135) via `Position.delta(lineNumberDeltaOffset, columnDeltaOffset)`, which cannot express 'go back N lines and to a specific column' — only a same-line column shift. The same length-based arithmetic in BaseTypeWithAutoClosingCommand._computeCursorStateWithRange (cursorTypeEditOperations.ts:900-902) computes `closeCharacterRange`/`enclosingRange`, which feed the auto-closed-character decorations in cursor.ts:376-378 used for skip-over-typing behavior. Do not change the single-line fast path (most autoClosingPairs have single-character close strings); the fix must special-case or generalize for close strings containing `\n`. Related: https://github.com/microsoft/vscode/issues/583 (open, tracks the broader begin/end autoClosingPairs feature this bug builds on). Left open for the maintainer: whether the decoration/skip-over semantics for a multi-line close range need redefining, and whether onEnter rules should run on the injected line as the reporter additionally requests.
- **Open decisions:**
  - Should the auto-closed-character decoration (and skip-over-typing behavior) track only the last line of a multi-line close string, or the whole span — and does that change the existing single-line decoration contract?
  - Should onEnter rules be applied to the newly-inserted line when the close string contains a newline, as the reporter requests, or is that a separate follow-up feature outside this bug's scope?

## Evidence

- **root cause:** src/vs/editor/common/cursor/cursorTypeEditOperations.ts:912 sets `columnDeltaOffset = -closeCharacter.length` in TypeWithAutoClosingCommand; this is applied via `srcRange.getEndPosition().delta(this._lineNumberDeltaOffset, this._columnDeltaOffset)` in ReplaceCommandWithOffsetCursorState.computeCursorState (src/vs/editor/common/commands/replaceCommand.ts:134), which only shifts the column on the same line and has no notion of the close text spanning lines — for `close: "\nend"` (length 4) this yields the wrong line/column instead of positioning the cursor at the end of the typed open text.
- **downstream impact:** The same range, `closeCharacterRange`/`enclosingRange` computed in BaseTypeWithAutoClosingCommand._computeCursorStateWithRange (cursorTypeEditOperations.ts:900-902) using single-line column arithmetic, feeds the auto-closed-character decorations tracked in src/vs/editor/common/cursor/cursor.ts:376-378, so a multi-line close string would also produce a malformed decoration range, not just a bad cursor position.
- **linked issue:** https://github.com/microsoft/vscode/issues/583 tracks the broader feature of begin/end-style autoClosingPairs and is still open/under discussion, so this bug sits on top of an already-unsettled feature area.
- **secondary ask:** The reporter also asks that onEnter rules apply on the newly-inserted line and its auto-closing counterpart — that's a separate design question, not yet decided anywhere in the codebase.
