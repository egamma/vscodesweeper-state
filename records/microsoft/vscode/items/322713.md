# Issue #322713 — Setup error: Explorer integration code_explorer_command_x64.dll not unloaded / There was an error while deleting a directory

[https://github.com/microsoft/vscode/issues/322713](https://github.com/microsoft/vscode/issues/322713)

## Summary

Real, traceable installer bug: the Windows setup's COM-surrogate kill step can fail unhandled in SYSTEM-context (Intune) silent installs, leaving the context-menu DLL loaded and causing the later directory-delete step to fail — this matches the reporter's logs and screenshot, and no fix has landed since the prior review.

## Change summary

Intune-driven (SYSTEM context) silent install/uninstall of VS Code on Windows intermittently fails with 'There was an error while deleting a directory' because the explorer context-menu COM surrogate DLL is not unloaded first.

## Best solution

Harden KillContextMenuComSurrogate in build/win32/code.iss so a Get-CimInstance/WMI failure under a SYSTEM/Intune execution context doesn't silently abort the whole kill step, and decide whether the subsequent directory-delete should retry/tolerate a still-locked DLL instead of hard-failing enterprise rollouts.

## Plan brief

- **Likely files:** `build/win32/code.iss`
- **Validation:** Verify on an Intune-managed (SYSTEM-context) Windows install/uninstall that KillContextMenuComSurrogate no longer exits non-zero and that the post-uninstall 'error while deleting a directory' no longer occurs across repeated update cycles.
- **Trace:**

  > KillContextMenuComSurrogate() in build/win32/code.iss (lines 1712-1733) runs 'Get-CimInstance Win32_Process -Filter ... | Where-Object ... | ForEach-Object { try { Stop-Process ... } catch {} }' before the installer removes the previous version folder (RemoveAppxPackage and CurStepChanged, lines 1793/1857/1868). Only the Stop-Process call is guarded by try/catch; a thrown Get-CimInstance/WMI error is not caught, so the whole command exits non-zero (as logged by the reporter) and the surrogate DLL stays loaded, which is consistent with the later 'error while deleting a directory / permission denied' failure. This was added for https://github.com/microsoft/vscode/issues/294546 but the reporter's 1.133.0 Intune logs (SYSTEM context) show it still failing. Do not touch the AppxPackage add/remove logic or the normal (non-Intune) update path, which are unaffected.
- **Open decisions:**
  - Should the Get-CimInstance/Where-Object pipeline also be wrapped so a WMI enumeration failure under a restricted SYSTEM token is swallowed/logged rather than aborting the whole kill step?
  - If the kill still can't succeed in a SYSTEM/Intune context (e.g. due to session isolation or WMI access restrictions), is there an alternative termination mechanism the team wants to use instead of Get-CimInstance/Stop-Process?
  - Should the subsequent directory-delete/inno_updater --gc step retry or tolerate a locked context-menu DLL instead of surfacing a hard 'error deleting a directory' failure that can break managed rollouts?

## Evidence

- **mitigation already present:** build/win32/code.iss:1712-1733 defines KillContextMenuComSurrogate(), added for https://github.com/microsoft/vscode/issues/294546, which spawns a PowerShell Get-CimInstance/Stop-Process pipeline to kill dllhost.exe COM surrogates hosting the context-menu CLSID before the installer deletes the old version folder (called from RemoveAppxPackage and from both the background-update and foreground-update branches of CurStepChanged, lines 1793/1857/1868).
- **unhandled failure path:** Only the per-item Stop-Process call is wrapped in try/catch (line 1724); the outer Get-CimInstance/Where-Object pipeline is not, so if CIM/WMI enumeration itself throws (plausible under a restricted SYSTEM token spawned by the Intune Management Extension), the whole PowerShell command exits non-zero and the surrogate is never killed — this is exactly what the reporter's log shows ('PowerShell exited with non-zero code 1') immediately before later install/uninstall failures.
- **reporter confirmation:** Reporter supplied an Intune install/uninstall log in comment https://github.com/microsoft/vscode/issues/322713#issuecomment (2026-08-19) still showing the same non-zero PowerShell exit on 1.133.0, i.e. after the prior review's date, so the mitigation has not resolved the enterprise/Intune case.
- **related but distinct:** https://github.com/microsoft/vscode/issues/316356 concerns the same PowerShell-spawn mechanism but is about the window being visibly spawned during update checks, not about the kill failing and blocking directory deletion — not the same observable symptom, so not a duplicate target.
