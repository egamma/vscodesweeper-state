# Issue #322713 — Setup error: Explorer integration code_explorer_command_x64.dll not unloaded / There was an error while deleting a directory

[https://github.com/microsoft/vscode/issues/322713](https://github.com/microsoft/vscode/issues/322713)

## Summary

Still open and still matching current `main`: the installer's only mitigation for the Windows 11 context-menu DLL holding the install folder is a single best-effort PowerShell pass (`KillContextMenuComSurrogate` in build/win32/code.iss) that logs a non-zero exit and continues anyway — exactly the sequence in the reporter's 1.133.0 Intune log. The report is complete (full Inno Setup logs, exact silent install/uninstall command lines, repeated 1.125 → 1.133), so it needs no further info from the reporter; it needs a Windows maintainer to retest the documented commands on a Win11 machine with the packaged context menu installed.

## Change summary

Silent system-level install/update over an existing installation fails because `code_explorer_command_x64.dll` stays loaded, so the old versioned directory cannot be deleted ("error while deleting a directory" / permission denied).

## Best solution

Make the context-menu DLL unload robust in build/win32/code.iss rather than best-effort: verify the handle is actually released after `KillContextMenuComSurrogate` (retry/wait, and handle hosts other than `dllhost.exe`), and decide what the installer does when it is not — today a non-zero PowerShell exit is only logged and setup proceeds into the failing directory delete.

## Plan brief

- **Likely files:** `build/win32/code.iss`
- **Validation:** Manual: on a Windows 11 machine with the packaged (Win11) context menu installed and Explorer having loaded the context-menu DLL, run the reporter's exact silent system-level upgrade command (`VSCodeSetup-x64-<ver>.exe /VERYSILENT /SUPPRESSMSGBOXES /FORCECLOSEAPPLICATIONS /mergetasks="addcontextmenufiles,addcontextmenufolders,addtopath" /LOG=…`) over an existing install; the log must show the surrogate kill completing and the `inno_updater --gc` removal of the previous versioned folder succeeding, with no "error while deleting a directory".
- **Behavior:**

  > A silent system-level install or update over an existing VS Code installation must not fail because the Explorer context-menu DLL (`code_explorer_command_x64.dll`) is still loaded: the previous versioned resources folder is removed and the appx package is replaced without a permission-denied or "error while deleting a directory" message. This must hold for unattended deployments (Intune) where no user can dismiss a dialog, and when VS Code windows were open and force-closed by setup. Acceptance: on a Win11 box where Explorer has loaded the context-menu DLL, the reporter's documented silent install and uninstall command lines complete with the log showing the surrogate kill succeeding and `inno_updater --gc` deleting the old folder; when the handle genuinely cannot be released, setup's behavior is deliberate and logged rather than an opaque delete failure.
- **Trace:**

  > The mitigation lives in `KillContextMenuComSurrogate` (build/win32/code.iss:1716-1737): a single hidden PowerShell pass enumerating `dllhost.exe` processes whose command line contains `/Processid:{FileExplorerContextMenuCLSID}` and `Stop-Process -Force`-ing them. It is purely best-effort — `ShellExec` failure and a non-zero exit are only logged, there is no wait/retry, and no check that the DLL handle on `******ionedResourcesFolder}` was actually released. Its callers then proceed unconditionally: `RemoveAppxPackage` (:1797, reached from `CurUninstallStepChanged` at :1956 and from the `[Files]` `BeforeInstall` at :112) and the two `inno_updater --gc` invocations at :1865 (background update, system target) and :1876 (foreground versioned update) that delete the previous versioned folder. The reporter's 1.133.0 Intune log shows exactly this: the kill logging `PowerShell exited with non-zero code 1`, then setup continuing into the failing delete. Where the certainty ends: I could not execute the installer, and the checkout is shallow (no history to blame), so the reason the handle survives — a host other than `dllhost.exe` (e.g. `explorer.exe` loading the packaged COM server in-proc), an appx-staged file lock, or the kill racing a re-launched surrogate — is unestablished. Boundary: this is installer-only; do not change the Windows 11 context-menu registration/appx model itself, the `ShouldUseWindows11ContextMenu` decision logic (:1568), or the legacy Win10 context-menu paths. Related: https://github.com/microsoft/vscode/issues/294546 (the `--gc` blockage the kill was introduced for), https://github.com/microsoft/vscode/issues/316356 (the hidden PowerShell window this kill produces — any redesign should resolve both), and the original https://github.com/microsoft/vscode/issues/62476 this report follows up on.
- **Open decisions:**
  - When the context-menu DLL handle cannot be released, should silent setup fail loudly with a specific exit code and log line (so Intune reports a deployment failure), or continue and leave the stale versioned folder for a later `--gc` pass?
  - Is it acceptable for the installer to restart or terminate `explorer.exe` (user-visible) to release an in-proc handle, or must the unload stay confined to COM surrogate processes?
  - Should the installer keep shelling out to PowerShell for this at all, given https://github.com/microsoft/vscode/issues/316356 reports the hidden window as its own problem — or move the unload into a native helper (e.g. inno_updater) with proper handle enumeration and retry?

## Evidence

- **mitigation is best-effort on current main:** build/win32/code.iss:1716-1737 — `KillContextMenuComSurrogate` runs one `Get-CimInstance Win32_Process … dllhost.exe | Stop-Process -Force` pass; a `ShellExec` failure or non-zero exit code is only written to the log (`'KillContextMenuComSurrogate: PowerShell exited with non-zero code '`), with no retry, no wait, and no verification that the DLL handle was released.
- **matches the reporter's log verbatim:** The 1.133.0 uninstall log in comment 1 shows `KillContextMenuComSurrogate: stopping COM surrogate(s) …` followed 3s later by `PowerShell exited with non-zero code 1`, after which setup continues into `Get-AppxPackage` and the directory delete — i.e. the known failure path, not an unknown state.
- **call sites that depend on it:** build/win32/code.iss:1797 (`RemoveAppxPackage`, also used by `CurUninstallStepChanged` at :1956) and :1865/:1876 (before `inno_updater --gc` on versioned updates) all assume the kill succeeded; the `--gc` path is the one that deletes the previous versioned folder.
- **no fix found on main:** The shard checkout is shallow (single commit, no history), so `git log`/`git blame` forensics are unavailable, but the current source of build/win32/code.iss still contains the unguarded single-pass kill — no retry, verification, or alternative unload path exists, so there is no commit to cite as a fix.
- **candidate canonicals do not own this:** https://github.com/microsoft/vscode/issues/316356 reports the *side effect* of this same mitigation (a hidden PowerShell window spawning to kill dllhost), not the failed unload/delete; https://github.com/microsoft/vscode/issues/334716 is about the packaged verb launching inside an AppX container for WSL paths. Neither reports this observable symptom, so neither is a duplicate canonical for this re-reviewed item.
