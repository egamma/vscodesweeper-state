# Issue #138535 — Allow better progress notifications (eg. percentage/text status) for progress notifications VS code shows during events like willRenameFiles etc.

[https://github.com/microsoft/vscode/issues/138535](https://github.com/microsoft/vscode/issues/138535)

## Summary

Keep this accepted, 25-upvote request open: current file-operation notifications still cannot consume extension-reported progress or yield to an extension's notification. The workspace-edit area is already appropriate; the remaining work needs a decision about the progress API and notification ownership.

## Change summary

Allow extensions handling file-operation events to provide meaningful progress without displaying a second notification alongside VS Code's participant notification.

## Best solution

Provide one coherent progress experience during file-operation participation, preserving cancellation and timeout behavior. Decide whether extensions report into the built-in notification or explicitly take over its presentation, including how multiple participants are represented.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/browser/mainThreadFileSystemEventService.ts`, `src/vs/workbench/api/common/extHostFileSystemEventService.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/test/browser/extHostFileSystemEventService.test.ts`
- **Validation:** Use a development extension whose onWillRenameFiles handler registers a delayed WorkspaceEdit through waitUntil and emits staged progress during an Explorer folder rename. Verify that exactly one notification presents the chosen status/percentage behavior, completion applies the edit, and cancellation or timeout stops participation without leaving stale progress. Repeat with two participating extensions and with an extension that supplies no progress.
- **Behavior:**

  > During a slow folder rename, an extension computing edits should be able to show meaningful status or percentage progress without a second notification appearing alongside VS Code's participant notification. Existing extensions that do not provide progress must retain the current waiting experience. Acceptance checks must cover one participant, multiple participants, normal completion, cancellation and timeout. The thread additionally asks for visibility into which extensions are running; its presentation should be decided alongside the central notification-ownership contract.
- **Trace:**

  > MainThreadFileSystemEventService's fileOperationParticipant in src/vs/workbench/api/browser/mainThreadFileSystemEventService.ts creates the notification and invokes $onWillRunFileOperation without using the withProgress reporter. ExtHostFileSystemEventService._fireWillEvent in src/vs/workbench/api/common/extHostFileSystemEventService.ts awaits extension listeners and returns collected edits and contributor names after completion; no intermediate status travels along this path. FileWillRenameEvent in src/vscode-dts/vscode.d.ts exposes cancellation and waitUntil but no progress or notification-ownership contract, and the corresponding RPC surface is in src/vs/workbench/api/common/extHost.protocol.ts. Generic ExtHostProgress.withProgress creates an independent progress handle, so it is not an existing consolidation mechanism. Preserve participant execution, cancellation, timeout, edit confirmation and application semantics; disabling participants is not a valid substitute for suppressing duplicate UI. The uncertainty is the user-visible/public contract, not whether the gap exists. Related cancellation work at https://github.com/microsoft/vscode/issues/135391 does not satisfy https://github.com/microsoft/vscode/issues/138535.
- **Open decisions:**
  - Should extensions report into VS Code's participant notification, take over presentation with their own notification, or have both capabilities?
  - When several extensions participate, what status and percentage should the single notification display, and should it identify the active extensions?
