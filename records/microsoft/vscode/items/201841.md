# Issue #201841 — `onDidChangeTabs` fires before `vscode.window.activeTextEditor` has been updated

[https://github.com/microsoft/vscode/issues/201841](https://github.com/microsoft/vscode/issues/201841)

## Summary

The ordering gap remains possible on current main: tab changes and active-text-editor state are published from independent workbench events, so an extension can observe the new active tab with the previous active text editor. This accepted Backlog bug should remain open while the API owners decide the intended cross-API ordering contract.

## Change summary

Ensure that an active-tab change event does not expose a stale `vscode.window.activeTextEditor` when switching between text-editor tabs.

## Best solution

Define whether `onDidChangeTabs` guarantees coherence with `activeTextEditor` for tabs backed by text editors, then enforce that contract in the workbench-to-extension-host synchronization path without implying that every tab has a text editor.

## Plan brief

- **Likely files:** `src/vs/workbench/api/browser/mainThreadEditorTabs.ts`, `src/vs/workbench/api/browser/mainThreadDocumentsAndEditors.ts`, `src/vs/workbench/api/common/extHostEditorTabs.ts`, `extensions/vscode-api-tests/src/singlefolder-tests/window.test.ts`
- **Validation:** Add an extension API integration test that opens two text documents in one group, switches between their tabs, and asserts inside the resulting `window.tabGroups.onDidChangeTabs` callback that `window.activeTextEditor.document.uri` matches the newly active `TabInputText` URI.
- **Behavior:**

  > When an extension receives `window.tabGroups.onDidChangeTabs` for an active-tab switch between two text-editor tabs, `window.activeTextEditor` must reflect the newly active text editor if the API contract guarantees coherence. The behavior for tabs without text-editor backing must remain well-defined and must not fabricate a `TextEditor`. Acceptance requires an integration test that inspects both APIs inside the event callback rather than after awaiting the tab switch.
- **Trace:**

  > `MainThreadEditorTabs` in `src/vs/workbench/api/browser/mainThreadEditorTabs.ts` reacts to `IEditorService.onDidEditorsChange` and sends `TAB_UPDATE` immediately from `_onDidTabActiveChange`; `ExtHostEditorTabs.$acceptTabOperation` then fires `onDidChangeTabs` synchronously. Active editor state is computed independently by `MainThreadDocumentAndEditorStateComputer` in `src/vs/workbench/api/browser/mainThreadDocumentsAndEditors.ts`, primarily after `onDidActiveEditorChange` and code-editor focus/model events. The issue's debugger evidence and https://github.com/microsoft/vscode/issues/201841#issuecomment-1877812679 confirm that these paths can arrive in the reported order. Preserve the tabs API's ability to represent notebooks, webviews, terminals, and other tabs without `TextEditor` backing; the uncertainty starts at whether coherence is promised specifically when the newly active tab does have a synchronized text editor.
- **Open decisions:**
  - Should `onDidChangeTabs` guarantee that `window.activeTextEditor` is already coherent when the newly active tab has text-editor backing, or should these APIs remain independently ordered with that limitation explicitly documented?

## Evidence

- **reported reproduction:** The issue provides direct steps and debugger evidence: switching between two text-editor tabs fires `onDidChangeTabs` while `activeTextEditor` still references the previous tab.
- **current tab event path:** `src/vs/workbench/api/browser/mainThreadEditorTabs.ts` subscribes to `IEditorService.onDidEditorsChange`; `_onDidTabActiveChange` immediately sends a `TAB_UPDATE`, which `src/vs/workbench/api/common/extHostEditorTabs.ts#$acceptTabOperation` immediately turns into `onDidChangeTabs`.
- **independent editor state path:** `src/vs/workbench/api/browser/mainThreadDocumentsAndEditors.ts#MainThreadDocumentAndEditorStateComputer` recomputes active editor state from separate `onDidActiveEditorChange`, model, and editor-focus events. There is no synchronization with the tab-model RPC before the tab event is emitted.
- **maintainer diagnosis:** https://github.com/microsoft/vscode/issues/201841#issuecomment-1877812679 explains that the tabs API listens to lower-level events and can publish a tab before construction and `activeTextEditor` synchronization complete; it also notes that tabs intentionally are not guaranteed to have text-editor backing.
- **canonical search:** Repository issue searches for `onDidChangeTabs` with `activeTextEditor` and broader stale-active-editor wording found no older open issue reporting the same observable symptom.
