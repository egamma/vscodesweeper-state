# Issue #169253 — Git - Untracked Folders

[https://github.com/microsoft/vscode/issues/169253](https://github.com/microsoft/vscode/issues/169253)

## Summary

Keep open: current Git status handling still requires full untracked-file enumeration or hides untracked changes entirely. This reopened, team-authored Backlog request needs a maintainer-led design decision; no qualifying fix or older canonical was established.

## Change summary

Support efficient untracked-folder discovery in large repositories, with automatic or on-demand expansion in Source Control.

## Best solution

Provide a performance-conscious untracked mode that preserves awareness of new directories without always enumerating their contents. Resolve the folder presentation and expansion contract with the Git and SCM owners before implementation, accounting for the extension-API limitations identified in the discussion.

Extend the GitStatusParser suite in extensions/git/src/test/git.test.ts for the agreed directory representation and verify stage/ignore/delete behavior manually in Source Control. These checks were not executed during this read-only review.
- **Behavior:**

  > Large-repository users currently choose between enumerating every untracked file and hiding untracked changes entirely. The desired capability preserves awareness of untracked directories while avoiding unnecessary full enumeration. The finished design must specify whether folders are visible resources with automatic or on-demand expansion, or whether file-only presentation is retained through selective enumeration. Acceptance includes a measured performance benefit on a representative repository, no silently omitted untracked directories in the new mode, and unchanged behavior for existing modes.
- **Trace:**

  > extensions/git/src/git.ts Repository.getStatus selects -uall unless untrackedChanges is hidden, when it selects -uno. GitStatusParser.parseEntry discards slash-terminated paths, so normal-mode directory output is not currently usable without further work. extensions/git/src/repository.ts Repository.getStatus converts parsed untracked entries into Resource objects in the existing working-tree or untracked group. SCMTreeDataSource.getChildren in src/vs/workbench/contrib/scm/browser/scmViewPane.ts exposes already-populated resource-tree children rather than fetching Git contents when a folder expands. The author recorded both folder-level UX and file-only selective enumeration alternatives, then deferred the former over extension-API limitations: https://github.com/microsoft/vscode/issues/169253#issuecomment-1385294187. The closed, unmerged https://github.com/microsoft/vscode/pull/136698 is historical input, not an active implementation candidate; its maintainer discussion rejects exposing raw Git arguments as settings. Preserve existing modes and nested-repository handling; do not assume every slash-terminated status entry is an ordinary directory. The uncertainty starts at the observable folder/expansion contract and the API support needed to deliver it.
- **Open decisions:**
  - Should the new mode expose untracked directories as actionable Source Control resources, or retain file-only presentation through selective enumeration?
  - If directories are exposed, when should their contents be enumerated, and how should users configure automatic versus on-demand expansion?
  - For a collapsed untracked directory, should stage, ignore, and delete act on the entire directory, and how should that scope be communicated?
