# Issue #259270 — "Column number" does not properly display columns and just counts code points

[https://github.com/microsoft/vscode/issues/259270](https://github.com/microsoft/vscode/issues/259270)

## Summary

Keep open: the status bar still counts Unicode code points with expanded tabs rather than rendered character widths, and existing tests explicitly preserve that behavior. The request needs a decision about what “Col” should represent; the related open reports do not cover its full scope.

## Change summary

Make the status-bar column indicator meaningful for zero-width, wide, and variable-width characters, or provide a clearly defined character-position alternative.

## Best solution

Establish a consistent, documented meaning for the editor’s position indicator, accounting for the trade-off between visual alignment and source-character offsets. Resolve that contract with the related Unicode-column reports before changing counting or navigation behavior.

Manually compare the status indicator and line navigation using those samples in monospace and proportional fonts. No tests were executed during this read-only review.
- **Behavior:**

  > The current position indicator advances for a zero-width space and treats emoji and wide characters as one column, despite their different rendered widths. The finished design should give the displayed position a clear meaning and predictable results for tabs and Unicode text. Acceptance must cover the supplied zero-width sample, emoji, CJK, and proportional-font behavior under the agreed metric. Whether this means visual columns or a source-character position remains a product decision.
- **Trace:**

  > EditorStatus obtains the displayed column through CodeEditorWidget.getStatusbarColumn, which delegates to CursorColumns.toStatusbarColumn. That helper counts code points and expands tabs; the cursorColumns tests explicitly encode those semantics. The separate visibleColumnFromColumn helper uses grapheme iteration and approximate wide-character handling, not actual font measurements, and does not solve the zero-width case. Keep model positions and existing navigation contracts unchanged unless the maintainer explicitly includes them in scope. https://github.com/microsoft/vscode/issues/254382 covers the wide-character subset; https://github.com/microsoft/vscode/issues/188677 highlights conflicting source-offset expectations. The trace establishes current behavior, but not which replacement contract the project wants.
- **Open decisions:**
  - Should the position indicator represent visual columns, or should it expose a source-character offset instead; if the latter, should that offset count UTF-16 units, Unicode code points, or grapheme clusters?
  - If visual columns are chosen, what should the indicator mean for proportional fonts and non-integer character widths, and should vertical navigation use the same definition?

## Evidence

- **Current status-bar behavior:** src/vs/editor/common/core/cursorColumns.ts, CursorColumns.toStatusbarColumn, iterates CodePointIterator, expands tabs to tab stops, and increments every other code point by one. Consequently, U+200B advances the displayed count by one, and an emoji also advances it by one regardless of rendered width.
- **Active call path and existing-capability check:** src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts:653–661, getStatusbarColumn, calls toStatusbarColumn directly; src/vs/workbench/browser/parts/editor/editorStatus.ts uses that result for the selection indicator. The inspected editor configuration and status-bar paths expose no selectable counting metric. CursorColumns.visibleColumnFromColumn is a separate approximation that handles wide characters but still advances U+200B and explicitly warns about variable-width text.
- **Established behavior:** src/vs/editor/test/common/core/cursorColumns.test.ts:72–126 explicitly expects one status-bar column per supplementary code point, emoji, and CJK character, while expanding tabs. This supports retaining the feature-request classification rather than treating the requested new metric as a straightforward regression fix.
- **Discussion expands the design boundary:** In https://github.com/microsoft/vscode/issues/259270, the reporter extends the request to emoji and non-integer rendered widths, then suggests character counting instead. The maintainer’s August 11 comment notes effects on vertical navigation and that columns are difficult to define for non-monospace fonts.
- **Verified related reports, not full-scope canonicals:** https://github.com/microsoft/vscode/issues/254382 is open and requests double-width counting for CJK and emoji, but does not own the zero-width and proportional-font requirements. https://github.com/microsoft/vscode/issues/188677 is open and requests consistency with source offsets and JavaScript stack traces, a different counting contract rather than equivalent visual-width behavior.
- **Reporter’s alternative:** https://github.com/microsoft/vscode/issues/257728 is closed and requests the character offset from the beginning of a line, explicitly distinguishing it from tab-expanded columns. It is neither an open duplicate target nor evidence that the visual-width request was implemented.
