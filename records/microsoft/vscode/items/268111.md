# Issue #268111 — Add API / command for showing a specific local chat session

[https://github.com/microsoft/vscode/issues/268111](https://github.com/microsoft/vscode/issues/268111)

## Summary

The API gap remains on current main: extensions can contribute provider-owned sessions, but cannot create and later reveal a specific VS Code-owned local chat session. The existing `api` and `chat` labels route it correctly, and no eligible older canonical issue was found.

## Change summary

Expose an extension API or supported command contract for creating a local chat session and later restoring that exact session in the chat UI.

## Best solution

Define a proposed extension API that creates a local session with a stable opaque identity and can reveal that session later, without exposing VS Code's internal session-resource encoding or storage format.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.chatSessionsProvider.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/common/extHostChatSessions.ts`, `src/vs/workbench/api/browser/mainThreadChatSessions.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatWidgetService.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatNewActions.ts`
- **Validation:** Add an extension API integration test that creates a local session, records the returned stable identity, switches away, reveals that identity again, and verifies that the same session resource and conversation are active.
- **Behavior:**

  > An extension can create a new VS Code-owned local chat session and retain a supported stable identity for it. At a later time, the extension can reveal that same session in the chat UI, including after another session has become active. Invalid, deleted, or inaccessible identities fail explicitly. Existing interactive New Chat and Open Chat command behavior remains unchanged.
- **Trace:**

  > `NewChatAction` in src/vs/workbench/contrib/chat/browser/actions/chatNewActions.ts currently creates a fresh session without accepting or returning a stable session identity. Local identities are constructed internally by `LocalChatSessionUri` in src/vs/workbench/contrib/chat/common/model/chatUri.ts, while `IChatWidgetService.openSession` in src/vs/workbench/contrib/chat/browser/widget/chatWidgetService.ts already performs the required reveal operation inside the workbench. The proposed controller API in src/vscode-dts/vscode.proposed.chatSessionsProvider.d.ts manages extension-provider sessions and does not expose VS Code-owned local sessions. The plan should preserve the private URI/storage representation and avoid expanding into transcript enumeration, which is separately discussed at https://github.com/microsoft/vscode/issues/318855.
- **Open decisions:**
  - Should extensions receive an opaque VS Code-generated session handle, or may they supply a stable caller-defined identifier?
  - Should creation and reveal be typed extension API operations, supported command arguments, or both?
  - Is the contract intentionally limited to VS Code-owned local sessions, or should the same reveal abstraction cover extension-provider session types?

## Evidence

- **current command gap:** `NewChatAction.run` in src/vs/workbench/contrib/chat/browser/actions/chatNewActions.ts accepts prompt/mode options but no session identifier; `runNewChatAction` creates a fresh session through `clearChatSessionPreservingType`.
- **internal capability:** src/vs/workbench/contrib/chat/browser/widget/chatWidgetService.ts exposes the internal `IChatWidgetService.openSession(sessionResource, ...)`, proving the workbench can reveal a specific session, but this service is not available to extensions.
- **local identity remains private:** src/vs/workbench/contrib/chat/common/model/chatUri.ts defines `LocalChatSessionUri.forSession` and the private `vscodeLocalChatSession` resource encoding; src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts generates local session IDs internally.
- **existing proposed API does not cover the request:** src/vscode-dts/vscode.proposed.chatSessionsProvider.d.ts lets extensions create controllers and provider-owned `ChatSessionItem` objects, but exposes no operation for creating or revealing a VS Code-owned local session.
- **related but not canonical:** https://github.com/microsoft/vscode/issues/318855 requests enumeration, history access, and lifecycle observation. It is newer than this re-reviewed issue and does not request creation or UI restoration, so it cannot serve as the duplicate canonical.
