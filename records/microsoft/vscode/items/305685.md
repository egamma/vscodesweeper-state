# Issue #305685 — Using "Toggle between Light/Dark Themes" resets theme

[https://github.com/microsoft/vscode/issues/305685](https://github.com/microsoft/vscode/issues/305685)

## Summary

The command still falls back to the configured preferred-theme values rather than remembering the themes selected through `workbench.colorTheme`. The broad synchronization fix was rejected, but the maintainer explicitly left room for a command-scoped improvement, so this should remain open.

## Change summary

Make repeated use of Toggle between Light/Dark Themes return to the user's previously selected light and dark themes instead of the product defaults.

## Best solution

Define command-scoped persistence semantics, then make the toggle round-trip the user's selected light and dark themes while preserving the documented authority of explicitly configured preferred-theme settings. Do not synchronize preferred settings on every ordinary color-theme change.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/themes/browser/themes.contribution.ts`, `src/vs/workbench/contrib/themes/test/browser/themes.contribution.test.ts`
- **Validation:** Add a browser unit test that invokes `workbench.action.toggleLightDarkThemes` with mocked theme and configuration services, verifies a custom dark-to-light-to-dark round trip, and pins the maintainer-selected behavior when an explicit preferred theme differs from the active theme.
- **Behavior:**

  > When no explicit preferred-theme override determines otherwise, toggling from a user-selected dark theme to light and back returns to that dark theme rather than the product default; the reverse light-to-dark-to-light flow behaves symmetrically. Explicit preferred-theme settings must continue to have predictable precedence according to the maintainer's decision. Automatic OS color-scheme detection and ordinary theme selection outside this command remain unchanged.
- **Trace:**

  > The command registered as `workbench.action.toggleLightDarkThemes` in src/vs/workbench/contrib/themes/browser/themes.contribution.ts examines the current theme only to choose the opposite preferred-setting key, then resolves that setting and calls `setColorTheme`; it retains no per-scheme selection. The preferred settings and their defaults are registered in src/vs/workbench/services/themes/common/themeConfiguration.ts. A global listener-based synchronization was proposed in https://github.com/microsoft/vscode/pull/309182 and rejected because it would modify preferred settings during ordinary theme changes; keep the solution confined to command behavior. No existing theme-contribution command test covers this path, but nearby contribution tests invoke registered handlers through `CommandsRegistry` with mocked services. Do not alter automatic OS theme detection or the unrelated Electron-upstream behavior tracked by https://github.com/microsoft/vscode/issues/286176.
- **Open decisions:**
  - When the active theme differs from an explicitly configured preferred theme of the same color scheme, should a toggle round trip return to the active theme or continue honoring the explicit preferred setting?
  - Should a theme learned by invoking the toggle command persist across window reloads, or only for the current session?

## Evidence

- **current source:** In src/vs/workbench/contrib/themes/browser/themes.contribution.ts, `workbench.action.toggleLightDarkThemes` selects only `ThemeSettings.PREFERRED_DARK_THEME` or `ThemeSettings.PREFERRED_LIGHT_THEME`; it never records or consults the currently selected theme beyond determining its color scheme.
- **default behavior:** src/vs/workbench/services/themes/common/themeConfiguration.ts gives the preferred-theme settings product defaults, so an unset preference causes the command to choose the default theme rather than the user's current theme.
- **maintainer direction:** https://github.com/microsoft/vscode/pull/309182#issuecomment-4232054119 rejects globally synchronizing preferred settings because that changes them without user consent, while explicitly suggesting that any improvement be confined to the toggle command.
- **closed fix attempt:** https://github.com/microsoft/vscode/pull/309182 referenced this issue but was closed without merging; therefore it is neither an implemented fix nor an open competing implementation.
- **canonical search:** The older https://github.com/microsoft/vscode/issues/286176 concerns Electron failing to report Linux OS color-scheme changes for automatic theme detection, not this command resetting to preferred-theme defaults, so it is not a duplicate canonical.
