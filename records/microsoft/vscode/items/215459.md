# Issue #215459 — Feature: add View: Balance Panes function

[https://github.com/microsoft/vscode/issues/215459](https://github.com/microsoft/vscode/issues/215459)

## Summary

This remains a valid Backlog feature request with 22 community upvotes. Current commands can resize incrementally or maximize and restore the panel, but none balances the editor and panel or toggles back to the previous ratio.

## Change summary

Add a View command that balances the editor and panel dimensions and can restore the user's previous layout.

## Best solution

Provide a keyboard-accessible Balance Panes command that divides the editor-panel axis equally while excluding side bars, with a predictable way to restore the previous ratio.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/actions/layoutActions.ts`, `src/vs/workbench/browser/layout.ts`, `src/vs/workbench/services/layout/browser/layoutService.ts`
- **Validation:** Exercise the command with the panel at the bottom, top, left, and right: the editor and panel should receive equal space along their shared axis, side-bar sizes must remain unchanged, and the approved repeated-invocation behavior must restore or retain the prior ratio as specified.
- **Behavior:**

  > Users can invoke a View command to give the main editor and panel equal space along their shared layout axis, regardless of whether the panel is horizontal or vertical. Primary and secondary side bars do not participate in the calculation or change size. The command must have defined behavior when invoked again after balancing and when either the editor or panel is hidden.
- **Trace:**

  > The existing size commands are registered in src/vs/workbench/browser/actions/layoutActions.ts and call IWorkbenchLayoutService.resizePart with fixed 60-pixel increments. The layout service already exposes getSize and setSize in src/vs/workbench/services/layout/browser/layoutService.ts, implemented by WorkbenchLayout in src/vs/workbench/browser/layout.ts. Panel maximization follows a separate path through workbench.action.toggleMaximizedPanel and WorkbenchLayout.toggleMaximizedPanel, which stores and restores the last non-maximized dimension while hiding or revealing the editor. The boundary is the editor-panel split: side bars and editor-group proportions must not be rebalanced. No older open canonical issue with the same observable behavior was found.
- **Open decisions:**
  - Should invoking Balance Panes while already balanced restore the immediately preceding editor-panel ratio, or should balancing be an idempotent one-way command?
  - When either the editor or panel is hidden, should the command reveal it and balance the layout, or remain unavailable until both are visible?

## Evidence

- **community demand:** The request received 22 upvotes and was explicitly promoted to the Backlog by https://github.com/microsoft/vscode/issues/215459#issuecomment-2424613929.
- **existing commands:** src/vs/workbench/browser/actions/layoutActions.ts registers workbench.action.increaseViewSize, workbench.action.decreaseViewSize, workbench.action.increaseViewHeight, and workbench.action.decreaseViewHeight as fixed-increment resizing commands; none computes an equal editor-panel split.
- **maximize behavior:** src/vs/workbench/browser/parts/panel/panelActions.ts registers workbench.action.toggleMaximizedPanel, while WorkbenchLayout.toggleMaximizedPanel in src/vs/workbench/browser/layout.ts hides the editor and later restores the last non-maximized panel size rather than balancing the two panes.
- **canonical search:** Searches for balance-pane, reset-panel-size, restore-panel-size, and toggle-panel-size requests found no older open issue with the same observable request. https://github.com/microsoft/vscode/issues/290270 is newer, closed, and asked for four panel-size buttons rather than equal editor-panel sizing, so it cannot serve as the canonical issue under the re-review rule.
