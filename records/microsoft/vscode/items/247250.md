# Issue #247250 — Diagnostics hover sort and clarity

[https://github.com/microsoft/vscode/issues/247250](https://github.com/microsoft/vscode/issues/247250)

## Summary

Keep this accepted, community-supported request open: current diagnostic hover rendering still lacks severity-first ordering and per-diagnostic severity indicators. The existing editor-hover label is appropriate, and no verified canonical issue absorbs both requirements.

## Change summary

Order overlapping diagnostic hover entries by severity and clearly distinguish errors, warnings, and informational diagnostics.

## Best solution

Provide a focused, severity-first diagnostic hover presentation in MarkerHoverParticipant, with severity cues consistent with the Problems view and understandable without color alone. Settle the visible severity presentation with the maintainer before implementation.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/hover/browser/markerHoverParticipant.ts`, `src/vs/editor/contrib/hover/browser/hover.css`, `src/vs/editor/contrib/hover/test/browser/contentHover.test.ts`

Manually check the same hover with keyboard navigation, screen-reader access, and light, dark, and high-contrast themes; retain functional diagnostic links, related information, and quick fixes.
- **Behavior:**

  > When diagnostics of different severities overlap the hovered position, the hover should present errors before warnings and informational entries, even when the error starts later in the source. Users should be able to identify each diagnostic's severity without relying solely on color. Preserve diagnostic messages, source/code links, related information, and existing actions. Acceptance checks should cover mixed-severity overlap, deterministic ordering for equal severities, and accessible severity identification.
- **Trace:**

  > In src/vs/editor/contrib/hover/browser/markerHoverParticipant.ts, MarkerHoverParticipant.computeSync collects marker hovers from line decorations. renderHoverParts renders every row first, then sorts the array only to choose the shared status-bar marker; this does not change DOM order. _renderMarkerHover does not render severity, and getAccessibleContent does not name it. In src/vs/editor/contrib/hover/browser/contentHoverRendered.ts, _renderHoverPartsForParticipant filters by owner without adding a severity order. Editor hover configuration in src/vs/editor/common/config/editorOptions.ts exposes no setting covering either request. Keep this work scoped to diagnostic hover presentation, preserving non-diagnostic participant ordering, marker ranges, and action behavior. The existing browser test suite is src/vs/editor/contrib/hover/test/browser/contentHover.test.ts; no execution was performed during this read-only review. The related https://github.com/microsoft/vscode/issues/174355 concerns feedback controls and should not expand this request's scope.
- **Open decisions:**
  - Should each diagnostic expose severity through Problems-style icons, explicit visible severity labels, or both? The request suggests icons but does not settle the visible presentation.
