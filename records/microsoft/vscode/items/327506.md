# Issue #327506 — [semantic] Add a `parameter` semantic token modifier

## Change summary

Add a standard `parameter` semantic-token modifier so themes can style parameter roles independently of primary token types such as `function`.

## Best solution

Let the Backlog Candidates voting period finish, then have the semantic-token/LSP owners decide whether parameter role is sufficiently universal and interoperable to standardize, including its treatment of ordinary parameters and type parameters.

## Plan brief

- **Likely files:** `src/vs/platform/theme/common/tokenClassificationRegistry.ts`, `src/vs/editor/common/languages.ts`
- **Validation:** Add semantic-token theming tests showing that `*.parameter` matches a `function.parameter` token while existing `function` and `parameter` selectors continue to behave unchanged.
- **Behavior:**

  > Themes should be able to style the parameter role independently of a semantic token's primary type. A function-valued parameter can retain its `function` classification and function color while also matching a parameter-role selector for italics. Existing token classifications, providers, and theme rules must remain compatible.
- **Trace:**

  > The report identifies a limitation in the standard semantic-token vocabulary rather than a failure of the current renderer: a token has one primary type, so a callable parameter classified as `function` loses a theme-selectable parameter role. The relevant boundary spans semantic-token modifier registration and matching, with likely entry points in src/vs/platform/theme/common/tokenClassificationRegistry.ts and src/vs/editor/common/languages.ts; language providers would adopt the modifier separately. https://github.com/microsoft/vscode/issues/97063 is related broader standards discussion, but available evidence does not verify it as a duplicate canonical. Do not alter existing primary token classifications or reinterpret existing theme selectors.
- **Open decisions:**
  - Should `parameter` become a standard semantic-token modifier, establishing parameter role as an interoperable protocol-level fact?
  - Should providers emit the modifier on tokens whose primary type is already `parameter`, or only when another primary type would otherwise hide the parameter role?
  - Should the modifier cover only runtime parameters, or also `typeParameter` tokens?
