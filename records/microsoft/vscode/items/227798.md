# Issue #227798 — Reveal  active file in file explorer  and ctrl+shift+ e  should work in diff editor

[https://github.com/microsoft/vscode/issues/227798](https://github.com/microsoft/vscode/issues/227798)

## Summary

The failure remains source-reproducible on current main: reveal commands use the diff's modified revision URI, which is not recognized as a workspace resource, so the working-tree file is never selected. The accepted Backlog bug should remain open while the diff-to-working-tree mapping and inaccessible failure behavior are designed.

## Change summary

Make Explorer reveal and keyboard navigation from a comparison diff select the corresponding working-tree file, or provide accessible feedback when no counterpart exists.

## Best solution

Give diff editors a reliable way to expose or resolve a working-tree counterpart for reveal operations, then select that resource in Explorer. When no counterpart exists, keep keyboard focus predictable and announce a concise localized status instead of failing silently.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/fileActions.ts`, `src/vs/workbench/contrib/files/browser/fileCommands.ts`, `src/vs/workbench/common/editor.ts`, `src/vs/workbench/contrib/files/test/browser/fileActions.test.ts`
- **Validation:** Open a GitLens Search & Compare diff whose path exists in the workspace, invoke “File: Reveal Active File in Explorer View,” and verify the working-tree file is selected and focused; repeat with no working-tree counterpart and verify a localized screen-reader announcement occurs without selecting an unrelated item. Add a browser unit test covering both resource outcomes.
- **Behavior:**

  > From a diff editor backed by historical or extension-provided resources, revealing the active file should select the corresponding file in the workspace when that counterpart exists. Ctrl/Cmd+Shift+E must continue to open and focus Explorer predictably. If no working-tree counterpart exists, the action must not fail silently: keyboard and screen-reader users receive concise localized feedback. Ordinary file editors and diffs whose modified side is already a workspace resource must retain their current behavior.
- **Trace:**

  > `ShowActiveFileInExplorer.run` in src/vs/workbench/contrib/files/browser/fileActions.ts extracts the diff's primary/modified resource and forwards it unchanged to `revealInExplorer`. `EditorResourceAccessor.getOriginalUri` in src/vs/workbench/common/editor.ts deliberately resolves `SideBySideEditor.PRIMARY` to the modified side, while the command handler in src/vs/workbench/contrib/files/browser/fileCommands.ts only selects URIs that `IWorkspaceContextService.isInsideWorkspace` accepts. Historical GitLens resources therefore reach the non-workspace fallback even when their path has a working-tree counterpart. The boundary is reveal/navigation behavior for diff resources: do not change normal diff rendering, generic URI identity semantics, or the established Ctrl/Cmd+Shift+E binding. The related https://github.com/microsoft/vscode/issues/325376 covers deleted-file diffs but does not replace this scenario.
- **Open decisions:**
  - Should VS Code core infer a working-tree resource from an extension-backed diff URI, or should diff providers supply an explicit working-tree counterpart through a public contract?
  - When no working-tree counterpart exists, should the reveal action keep focus in the diff or move focus to Explorer/Open Editors while announcing the failure?

## Evidence

- **source-reproducible path:** src/vs/workbench/contrib/files/browser/fileActions.ts:670-676 implements `workbench.files.action.showActiveFileInExplorer` by taking `EditorResourceAccessor.getOriginalUri(..., SideBySideEditor.PRIMARY)` and passing that URI directly to `revealInExplorer`.
- **diff resource selection:** src/vs/workbench/common/editor.ts:1424-1438 maps `SideBySideEditor.PRIMARY` for a diff input to its modified editor. For an extension-provided historical comparison, that is the revision resource rather than the corresponding working-tree resource.
- **silent non-workspace fallback:** src/vs/workbench/contrib/files/browser/fileCommands.ts:316-345 reveals only when `contextService.isInsideWorkspace(uri)` succeeds; otherwise it merely focuses the Open Editors view, with no notification or screen-reader status explaining why the file was not revealed.
- **keyboard behavior:** src/vs/workbench/contrib/files/browser/explorerViewlet.ts:267-272 binds Ctrl/Cmd+Shift+E to `workbench.view.explorer`. That command opens the Explorer but does not itself resolve a historical diff URI to a working-tree file.
- **related report:** https://github.com/microsoft/vscode/issues/325376 is a newer related report about reveal behavior for deleted-file diffs, but it does not cover this older report's GitLens comparison scenario or existing working-tree files and is not a canonical duplicate.
