# Issue #144806 — Visual Bug in Nested Folder Tree View

[https://github.com/microsoft/vscode/issues/144806](https://github.com/microsoft/vscode/issues/144806)

## Summary

The compact-folder inline-edit race remains source-reproducible on current main: switching creation modes can let the delayed blur cleanup clear the newer edit while the Explorer remains dimmed. The issue is already correctly accepted as a file-explorer bug in Backlog and should stay open.

## Change summary

Switching from New File to New Folder within a compact folder can leave the Explorer permanently dimmed with no active filename input.

## Best solution

Preserve the newest Explorer editable item when an older inline editor finishes asynchronously, and cover the overlapping New File/New Folder transition with a regression test.

- **Behavior:**

  > Starting New Folder while a New File input is active in a compact folder must replace the first inline editor without leaving a ghost item or permanently dimming the Explorer. Cleanup from the first editor must not cancel the newer editor. After the active editor finishes, all Explorer rows must return to normal opacity. Existing single-edit create and rename behavior must remain unchanged.
- **Trace:**

  > Inline editing is coordinated by `ExplorerService.setEditable` in src/vs/workbench/contrib/files/browser/explorerService.ts and rendered by `FilesRenderer.renderInputBox` in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts. The BLUR handler deliberately awaits `timeout(0)`, so the second creation command can install a new editable item before the first input's `onFinish` runs. The older `setEditable(stat, null)` currently clears `this.editable` without checking whether it still belongs to that stat; `ExplorerView.setEditable` independently toggles the tree's `highlight` class around asynchronous refreshes. Keep the scope to stale cleanup from overlapping inline edits; do not change compact-folder navigation, ordinary sequential creation, or rename semantics. The newer corroborating report is https://github.com/microsoft/vscode/issues/229233.

## Evidence

- **source-reproducible race:** In src/vs/workbench/contrib/files/browser/views/explorerViewer.ts, the input BLUR handler waits through `timeout(0)` before calling `editableData.onFinish`, allowing the second creation command to start first. src/vs/workbench/contrib/files/browser/explorerService.ts:255-268 then clears `this.editable` unconditionally when the older item calls `setEditable(stat, null)`, even if a newer item has become editable.
- **visual outcome:** src/vs/workbench/contrib/files/browser/views/explorerView.ts:457-480 manages the persistent `highlight` class around asynchronous refreshes, while src/vs/workbench/contrib/files/browser/media/explorerviewlet.css:12-15 dims every non-edited Explorer item to 0.3 opacity. Losing the newer editable state can therefore leave the reported all-grey tree.
- **current corroboration:** https://github.com/microsoft/vscode/issues/229233 reports the same New File/New Folder switch with compact folders enabled in VS Code 1.93.1, with extensions disabled, and remains open with `bug`, `file-explorer`, and `confirmed` labels. It is newer than this issue and therefore is supporting evidence rather than a canonical duplicate target.
