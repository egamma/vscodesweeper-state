# Issue #172865 — npm.packageManager=auto ignores task's cwd

[https://github.com/microsoft/vscode/issues/172865](https://github.com/microsoft/vscode/issues/172865)

## Summary

The defect remains in current main: npm tasks select their runner using the workspace root before the configured working directory is applied. Keep this older report open; the related subdirectory report is newer and cannot serve as its duplicate canonical.

## Change summary

Automatic package-manager selection should respect an npm task's configured working directory and its package-manager metadata.

## Best solution

Make automatic runner selection use the task's effective working directory while preserving explicit runner settings and existing task execution semantics. Coordinate the task-provider configuration boundary with the built-in npm extension; detector-only improvements do not resolve the missing cwd information.

- **Behavior:**

  > An npm task with options.cwd pointing to a pnpm project currently executes npm run even when that project contains pnpm-lock.yaml. Automatic selection must honor the task's effective directory so npm, yarn, and pnpm projects within one workspace can each use their own manager. Validate the attached three-task example and preserve explicit runner settings and existing task execution behavior.
- **Trace:**

  > NpmTaskProvider.resolveTask in extensions/npm/src/tasks.ts receives a task definition and scope but no configured options.cwd. createScriptRunnerTask selects its command using the workspace-folder URI, and findPreferredPM in extensions/npm/src/preferred-pm.ts consequently cannot see child-directory lockfiles. Main-thread TaskDTO.from leaves ConfiguringTask execution undefined and omits configuration options; CustomTask.createCustomTask in src/vs/workbench/contrib/tasks/common/taskConfiguration.ts applies those options after the provider has chosen the command. This confirms the reported mismatch without execution. The remaining planning work is to establish the task-provider contract and enumerate affected consumers before changing this cross-layer boundary; do not treat a detector-only change or setting a global pnpm override as satisfying the report. https://github.com/microsoft/vscode/issues/261630 provides newer related evidence, and its open detector PR https://github.com/microsoft/vscode/pull/302916 must be coordinated with but does not address this cwd flow.

## Evidence

- **Current source confirms the reported flow:** At checkout commit 0c9c0a4295a9222e12a605537738719455ae3056, extensions/npm/src/tasks.ts:60-79 resolves package.json from task.definition.path or the workspace root, without consulting options.cwd. createScriptRunnerTask at lines 338-349 selects the command through getRunScriptCommand(script, folder.uri, ...), so detection starts at the workspace root rather than the task directory.
- **Working directory is applied after command selection:** src/vs/workbench/api/browser/mainThreadTask.ts:346-382 serializes ConfiguringTask with execution undefined and does not send configurationProperties.options. src/vs/workbench/api/common/shared/tasks.ts:137-150 has no configuration-options field in ITaskDTO. src/vs/workbench/contrib/tasks/common/taskConfiguration.ts:1677-1707 subsequently overlays configured options on the already-selected contributed command. Thus a root without package-manager metadata selects npm even when execution is redirected to a pnpm subdirectory.
- **Detector cannot discover child-directory metadata from the root:** extensions/npm/src/preferred-pm.ts checks lockfiles in its supplied pkgPath; its pnpm findUp search walks ancestors, not children, and findPreferredPM falls back to npm. A pnpm-lock.yaml located only in use-pnpm therefore cannot influence detection initiated at the workspace root.
- **Full thread diagnosis:** https://github.com/microsoft/vscode/issues/172865#issuecomment-1420779627 identifies the missing task-provider configuration options and links a prototype at https://github.com/Viijay-Kr/vscode/pull/1, verified CLOSED. The maintainer acknowledged the cross-cutting complexity at https://github.com/microsoft/vscode/issues/172865#issuecomment-1421235686; this was not a decline of the reported behavior.
- **Related report is not an eligible canonical:** https://github.com/microsoft/vscode/issues/261630 is OPEN but was created on 2025-08-14, after this 2023 report. Its reporter explicitly identifies this older issue as related at https://github.com/microsoft/vscode/issues/261630#issuecomment-3190569175. Searches for npm/package-manager cwd and working-directory reports did not establish an older open canonical.
- **Related implementation does not fix the cwd boundary:** https://github.com/microsoft/vscode/pull/302916 is OPEN and changes only extensions/npm/src/preferred-pm.ts to prioritize package.json packageManager metadata and simplify detection. It does not change the directory supplied by tasks.ts or expose configured cwd to task providers, so it is not a completed fix for this report. Its predecessor https://github.com/microsoft/vscode/pull/302354 is CLOSED.
- **Settings and verification limits:** extensions/npm/package.json:244-286 now separates npm.packageManager for installation from npm.scriptRunner for scripts, both defaulting to auto. Explicitly selecting pnpm can work around the symptom but does not satisfy automatic selection across differently configured subdirectories. The report's prose says use-npm once, but its task JSON consistently specifies use-pnpm. Source was inspected without executing tasks or writing to the checkout.
