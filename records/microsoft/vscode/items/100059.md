# Issue #100059 — Layout: waterfall for restoring default views

[https://github.com/microsoft/vscode/issues/100059](https://github.com/microsoft/vscode/issues/100059)

## Summary

The startup waterfall remains on current main: sidebar, panel, and auxiliary-bar restoration all await the same default-view promise, including its wait for extension registration. The merged mitigation reduced the original regression but explicitly left this location-specific restoration work outstanding.

## Change summary

Restore each workbench view-container location independently so a default view in one location does not delay unrelated sidebar, panel, or auxiliary-bar restoration.

## Best solution

Separate default-view restoration coordination by view-container location while preserving default-view precedence within the affected location. A maintainer should first settle how unresolved extension-contributed view IDs affect first-paint behavior, then add startup timing coverage for sidebar-only and panel-only defaults.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/layout.ts`
- **Validation:** Launch the web workbench with delayed extension registration and an `IDefaultLayout` containing a sidebar-only contributed view while a panel is restored, then verify `code/didRestorePanel` occurs before default-view completion; repeat with a panel-only default and verify the sidebar restores independently.
- **Behavior:**

  > A configured default view delays restoration only for the view-container location in which that view belongs. A sidebar-only default must not delay panel or auxiliary-bar restoration, and a panel-only default must not delay either sidebar. The selected default view and stored container restoration behavior within the affected location must remain unchanged.
- **Trace:**

  > Layout.restoreParts in src/vs/workbench/browser/layout.ts currently creates one `restoreDefaultViewsPromise` and awaits it from all three location restore tasks. If a view ID is not registered yet, that promise waits for `IExtensionService.whenInstalledExtensionsRegistered()`, producing the cross-location waterfall directly in current source. PR https://github.com/microsoft/vscode/pull/100058, merged as e92f7ab746b74e5420b183cd4bcfd4ae2b2f75b3, intentionally provided only a partial mitigation. Keep editor restoration and default-view ordering within a location unchanged; the uncertainty begins when an extension-contributed view's location is unknown until registration completes.
- **Open decisions:**
  - When a configured default view's location is unknown until extension registration, should unrelated locations restore immediately even if the target location may switch later, or should first-paint stability take precedence until the location is known?

## Evidence
