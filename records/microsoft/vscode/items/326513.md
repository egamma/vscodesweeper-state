# Issue #326513 — Extension API to restart all language servers

[https://github.com/microsoft/vscode/issues/326513](https://github.com/microsoft/vscode/issues/326513)

## Summary

This is a valid API-design request in the Backlog Candidates lifecycle, so it should remain open as under discussion while the community window runs. The older linked request does not appear in the supplied cross-reference data as a verified open canonical, and the central capability is not established as already available.

## Change summary

Expose a generic extension API or built-in command that lets worktree-management extensions restart all active language servers without reloading the window and interrupting agent sessions.

## Best solution

Define a host-coordinated mechanism for workspace-root transitions that lets participating language extensions refresh or restart without reloading the window, while preserving active agent sessions. API owners should first decide whether this should be a public API, a command, or a lifecycle notification that language extensions handle.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`
- **Validation:** Add extension API tests proving the chosen mechanism requests a refresh for multiple registered language providers without reloading the extension host or terminating an active chat/agent session.
- **Behavior:**

  > A worktree-management extension can trigger a workspace-language refresh after switching roots without reloading the VS Code window. All participating language services receive enough lifecycle information to stop returning symbols from the prior worktree, while active AI agent sessions continue uninterrupted. Existing language features and extensions that do not participate retain their current behavior.
- **Trace:**

  > The requested surface is an extension-facing language lifecycle capability, with likely API declaration and ExtHost/MainThread plumbing in src/vscode-dts/vscode.d.ts and src/vs/workbench/api. The report establishes that per-extension restart commands do not compose into a generic operation and that window reload has an unacceptable agent-session side effect. The uncertainty begins at ownership: VS Code does not uniformly own extension-provided language servers, so API owners must determine whether the contract broadcasts a lifecycle request, invokes registered restart handlers, or exposes another workspace-root transition primitive. Keep the scope to coordinated language-state refresh and preservation of agent sessions; do not promise that VS Code can forcibly restart arbitrary extension-owned processes.
- **Open decisions:**
  - Should the public contract request that registered language extensions restart or refresh themselves, or should VS Code expose a host-owned operation with stronger restart semantics?
  - Should the operation target every participating language service or allow scoping by workspace folder, language, or document?
  - What observable result should callers receive when a language extension cannot or does not support restart?
