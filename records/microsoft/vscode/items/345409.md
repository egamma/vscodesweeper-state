# Issue #345409 — MCP: optional content pinning for package-based servers in `mcp.json`

[https://github.com/microsoft/vscode/issues/345409](https://github.com/microsoft/vscode/issues/345409)

## Summary

Keep open for human review of this security-sensitive content-pinning proposal. Current configuration supports versioned launcher arguments, but does not provide the requested artifact-integrity record and verification lifecycle.

## Change summary

Provide optional content pinning or a documented verification hook for package-launched MCP servers.

## Best solution

Have MCP and security owners decide the trust-anchor provenance, first-use and explicit reapproval semantics, and whether enforcement belongs in the client or an external verifier. Distinguish matching recorded content from establishing that content was reviewed or is safe.

## Evidence

- **Existing configuration does not cover the request:** src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts defines mcpStdioServerSchema with additionalProperties: false and command, args, environment, development, and sandbox options, but no integrity field or prelaunch verification hook. IMcpStdioServerConfiguration in src/vs/platform/mcp/common/mcpPlatformTypes.ts likewise exposes neither.
- **Version pinning is distinct from content pinning:** src/vs/platform/mcp/common/mcpManagementService.ts:141–159 constructs npm/Python package arguments using identifier@version and Docker arguments using identifier:version. These configuration-generation branches do not record artifact hashes. Docker digest arguments can address the OCI case, but do not supply the requested cross-launcher verification lifecycle.
- **Existing hash has a different purpose:** src/vs/workbench/contrib/mcp/common/mcpTypes.ts:839–841 hashes JSON.stringify(launch), not package artifact content. An unchanged launch configuration therefore does not establish unchanged package bytes.
- **Discussion identifies unresolved trust semantics:** https://github.com/microsoft/vscode/issues/345409#issuecomment-6559007968 distinguishes registry-provided hashes from the provenance of a recorded trust anchor, and calls out cloned pins, trust-on-first-use, and explicit reapproval. These are substantive product and security decisions, not merely a missing schema property.
- **Reporter clarification:** https://github.com/microsoft/vscode/issues/345409#issuecomment-6560177260 confirms the external verifier uses a committed lockfile and explicit rerecording, but does not itself distinguish locally recorded pins from inherited ones. That workaround does not establish an integrated VS Code capability.
- **Protected review boundary:** The proposal concerns supply-chain integrity and potentially misleading verification claims, so the security-sensitive keep-open rule applies. No implementation or runtime reproduction was attempted in the read-only checkout.
