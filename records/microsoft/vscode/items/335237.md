# Issue #335237 — editor.suggest.insertMode: "insert" not respected for completions using LSP InsertReplaceEdit (clangd 23.1.0+)

[https://github.com/microsoft/vscode/issues/335237](https://github.com/microsoft/vscode/issues/335237)

## Summary

Traced the insert/replace threading through VS Code's own completion pipeline (extHostLanguageFeatures → mainThreadLanguageFeatures → suggest.ts → suggestController.ts) and it correctly respects `editor.suggest.insertMode` given a well-formed `range: {insert, replace}` — this is long-standing, unchanged logic. The likely fault point is upstream of core: how clangd (via the separately-maintained `vscode-languageserver-node` client library) converts the raw LSP `InsertReplaceEdit` into the vscode API's CompletionItem.range, which this repo doesn't control. Not confident enough yet to close as `*caused-by-extension` without reproducing against that specific conversion path.

## Change summary

clangd 23.1.0+ completions using LSP InsertReplaceEdit ignore editor.suggest.insertMode: 'insert' and always apply the wider replace range.

## Best solution

Reproduce with a minimal extension that directly sets `CompletionItem.range = {inserting, replacing}` (bypassing vscode-languageserver-node) to confirm VS Code core is not at fault; if core behaves correctly there, this belongs with the clangd extension or with microsoft/vscode-languageserver-node's protocolConverter.ts (asCompletionItem/InsertReplaceRange handling), not this repo.

## Evidence

- **core range threading:** src/vs/editor/contrib/suggest/browser/suggest.ts:111-121 correctly builds editInsertEnd/editReplaceEnd from completion.range.insert/.replace when range is an InsertReplaceEdit-shaped object.
- **insertMode applied correctly:** src/vs/editor/contrib/suggest/browser/suggestController.ts:576-588 (getOverwriteInfo) picks editInsertEnd vs editReplaceEnd based on EditorOption.suggest.insertMode === 'replace', defaulting to insert.
- **extension host conversion:** src/vs/workbench/api/common/extHostLanguageFeatures.ts:1316-1333 forwards item.range.inserting/replacing faithfully when they differ from the computed default ranges; src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts:571-601 inflates the DTO back into insert/replace IRanges.
- **no recent regression:** git log -p on suggest.ts shows this insert/replace dual-range handling is long-standing, unchanged in the current diff history — no code evidence of a core regression coinciding with clangd 23.1.0.
- **external conversion layer:** clangd's LSP InsertReplaceEdit is converted to a vscode.CompletionItem.range by microsoft/vscode-languageserver-node (client/src/common/protocolConverter.ts, InsertReplaceRange type), a separate repository this issue does not have visibility into.
