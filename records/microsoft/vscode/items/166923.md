# Issue #166923 — Outline view for workspace but not only current file

[https://github.com/microsoft/vscode/issues/166923](https://github.com/microsoft/vscode/issues/166923)

## Summary

Keep open: current Outline remains editor-scoped, and workspace symbol search does not provide the requested docked, persistent browser. This accepted Backlog request has 29 upvotes; the related filtering and Explorer requests do not fully own its scope.

## Change summary

Provide a persistent workspace-wide symbol outline with filtering that remains available while inspecting symbol definitions.

## Best solution

Design a dockable workspace-symbol browsing surface that retains its query and results while navigating code, without requiring eager indexing of every document. Settle whether this is a query-driven results view or a complete hierarchical outline before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/outline/browser/outlinePane.ts`, `src/vs/workbench/contrib/outline/browser/outline.contribution.ts`, `src/vs/workbench/services/outline/browser/outline.ts`, `src/vs/workbench/contrib/search/browser/symbolsQuickAccess.ts`, `src/vs/workbench/contrib/search/common/search.ts`
- **Validation:** In a workspace with symbols in multiple files, open the proposed docked surface, filter symbols, navigate to definitions in different files, and verify that the surface, query, and results remain available across editor-focus changes. Verify existing document Outline and Go to Symbol in Workspace behavior remain unchanged, and exercise cancellation and responsiveness with a large provider result set.
- **Behavior:**

  > Users need to search and browse workspace symbols in a docked view while inspecting definitions, without repeatedly reopening a transient picker. The query and results should remain available when focus moves to an editor or another file becomes active. Symbols should identify their source files and navigate to their definitions. Acceptance must cover cross-file navigation, persistent filtering, and a responsive large-workspace experience; the existing document Outline must remain usable.
- **Trace:**

  > OutlinePane in src/vs/workbench/contrib/outline/browser/outlinePane.ts rebuilds its outline around the active IEditorPane, and IOutlineService in src/vs/workbench/services/outline/browser/outline.ts exposes that same editor-scoped contract. Workspace search instead runs through SymbolsQuickAccessProvider and getWorkspaceSymbols, which queries registered providers by search text. Quick Open focus-loss and input-preservation settings are useful workarounds but do not supply a docked view. The unresolved boundary is whether workspace outline means persistent query results or complete file/container hierarchy; provider query results alone do not establish complete enumeration. Preserve existing document-outline and workspace-picker contracts, and keep the later comment's dependency inspectors outside this request. Multi-word matching is separately tracked at https://github.com/microsoft/vscode/issues/109548 with https://github.com/microsoft/vscode/pull/151859; the newer Explorer-outline request at https://github.com/microsoft/vscode/issues/210420 is related design context, not a canonical for closing this report.
- **Open decisions:**
  - Should the workspace surface present persistent query-driven symbol results, or promise a complete browsable hierarchy of workspace symbols even before a query is entered?
  - Should workspace browsing be an alternate scope within Outline or a separate dockable view that can remain visible alongside the current-file Outline?

## Evidence

- **Existing Outline scope:** src/vs/workbench/contrib/outline/browser/outlinePane.ts listens to active-editor changes and calls _outlineService.createOutline(pane, OutlineTarget.OutlinePane, ...). src/vs/workbench/services/outline/browser/outline.ts likewise defines outline creation around an IEditorPane, not a workspace.
- **Existing capabilities are partial workarounds:** workbench.action.showAllSymbols in src/vs/workbench/contrib/search/browser/searchActionsSymbol.ts opens the '#' Quick Access picker. workbench.quickOpen.closeOnFocusLost=false and workbench.quickOpen.preserveInput=true, registered in src/vs/workbench/browser/workbench.contribution.ts, address focus loss and restoring input but do not create a docked workspace outline. The Outline configuration registration contains no workspace-scope option.
- **Filtering is not entirely absent:** SymbolsQuickAccessProvider.doGetSymbolPicks in src/vs/workbench/contrib/search/browser/symbolsQuickAccess.ts already uses scoreFuzzy2. Multi-part queries are generally split into symbol and container terms, so the report's filtering concern should be distinguished from a blanket absence of fuzzy matching.
- **Related filtering issue is narrower:** https://github.com/microsoft/vscode/issues/109548 is open and concerns multi-word workspace symbol matching, not a persistent browsing surface. Its open implementation candidate, https://github.com/microsoft/vscode/pull/151859, addresses that matching behavior rather than this issue's central request.
- **Canonical search:** Open-issue searches for workspace outline, symbol view, workspace symbols with panel, symbol browser, class browser, and project outline did not establish an older same-symptom canonical. https://github.com/microsoft/vscode/issues/210420 is open but newer, created in April 2024, and requests expandable file outlines inside Explorer; it is related, not a valid duplicate target for this re-reviewed November 2022 report.
- **Discussion and accepted demand:** https://github.com/microsoft/vscode/issues/166923 has 29 body upvotes and the Backlog milestone. The January 2023 bot comment confirms promotion after sufficient votes. The reporter explicitly wants a persistent filter; the contributor's draggable-find-widget workaround addresses obscured rows only. A later commenter reinforces cross-file browsing demand while also suggesting separate dependency-inspection capabilities.

- **Provider boundary:** getWorkspaceSymbols in src/vs/workbench/contrib/search/common/search.ts queries registered workspace-symbol providers with a search string. This supplies an existing query path, but does not establish complete enumeration or a cross-file document-symbol hierarchy.
