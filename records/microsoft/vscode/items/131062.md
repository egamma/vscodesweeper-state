# Issue #131062 — expose only the positions of those brackets colored by native bracket pair colorization

[https://github.com/microsoft/vscode/issues/131062](https://github.com/microsoft/vscode/issues/131062)

## Summary

The extension API gap remains: native bracket positions are available internally but are not exposed to extensions. Keep this team-authored Backlog request open for API design, particularly the consistency contract when documents change during asynchronous queries.

## Change summary

Expose native, token-aware bracket positions to extensions without requiring them to repeat bracket parsing.

## Best solution

Provide a performance-bounded extension API for bracket pairs intersecting a requested range, including enclosing pairs whose endpoints lie outside it. Settle document-version consistency and incomplete-result semantics before implementation, while keeping Blockman's rendering in the extension.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/textModelBracketPairs.ts`, `src/vs/editor/common/model/bracketPairsTextModelPart/bracketPairsImpl.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`, `src/vs/workbench/api/test/browser/extHostLanguageFeatures.test.ts`
- **Validation:** The plan should identify API bridge tests for a viewport query containing enclosing pairs with endpoints outside the viewport, document edits during an outstanding query, bounded/truncated responses, and unavailable bracket data. Validate token-aware results against native analysis for brackets inside comments and strings, without changing existing colorization or navigation behavior.
- **Behavior:**

  > Extensions should be able to obtain native bracket-pair positions intersecting a requested document range without independently parsing the document. A viewport query must include enclosing pairs even when their opening or closing brackets are outside the viewport. Callers must be able to distinguish usable results from stale, incomplete, or unavailable data under the agreed API contract. Acceptance should cover edits during asynchronous queries and retain bounded work for large documents.
- **Trace:**

  > BracketPairsTextModelPart.getBracketPairsInRange in src/vs/editor/common/model/bracketPairsTextModelPart/bracketPairsImpl.ts already queries native bracket pairs intersecting a range; BracketPairInfo in src/vs/editor/common/textModelBracketPairs.ts contains opening and optional closing ranges. Native colorization separately uses getBracketsInRange(range, true), so the plan must distinguish colorized bracket positions from the broader pair-query surface. Searches of src/vscode-dts and src/vs/workbench/api found no extension-facing query or bridge for these results. The thread accepts viewport-intersecting pairs, but https://github.com/microsoft/vscode/issues/131062#issuecomment-962923012 leaves asynchronous document consistency unresolved. Preserve current native colorization, matching, and navigation; do not expand this into general AST exposure or move Blockman's rendering into core. The related broader request at https://github.com/microsoft/vscode/issues/177452 is design context, not an eligible duplicate canonical.
- **Open decisions:**
  - What document-consistency contract should extensions receive when text changes during a query: version-tagged potentially stale results, rejection on version mismatch, or another explicit guarantee?
  - Should results represent only brackets participating in native colorization or all native bracket pairs, and how should unmatched brackets be represented?
  - What observable contract should apply when bracket data is unavailable or a result exceeds the query limit: explicit unavailability, a marked partial result, or another bounded response?
