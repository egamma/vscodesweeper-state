# Issue #337351 — Make agent bake-offs available as an agent-invokable tool

[https://github.com/microsoft/vscode/issues/337351](https://github.com/microsoft/vscode/issues/337351)

## Summary

Keep open: existing comparison UI and session-delegation tools provide useful building blocks, but do not deliver an agent-invokable, resource-bounded bake-off with structured results returned to its caller. This team-authored request still needs decisions about its tool contract and lifecycle.

## Change summary

Expose an Agent Host tool for isolated, bounded multi-candidate runs that return comparable results to the invoking agent.

## Best solution

Define a provider-neutral bake-off contract that reuses existing session and comparison capabilities, preserves the original task and evaluation criteria, and gives the caller structured outcomes with explicit limits, cancellation, cleanup, and approval semantics.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/common/serverToolNames.ts`, `src/vs/platform/agentHost/node/shared/sessionServerTools.ts`, `src/vs/sessions/services/sessions/common/sessionComparison.ts`, `src/vs/sessions/services/sessions/browser/sessionComparisonService.ts`, `src/vs/sessions/contrib/sessionComparison/browser/sessionComparisonTool.ts`, `src/vs/platform/agentHost/test/node/sessionServerTools.test.ts`, `src/vs/sessions/services/sessions/test/browser/sessionComparisonService.test.ts`, `src/vs/sessions/contrib/sessionComparison/test/browser/sessionComparisonTool.test.ts`
- **Validation:** The plan should establish focused automated coverage for invoking a bounded candidate set, immutable task/evaluation inputs, isolated writes, structured per-candidate outcomes, unavailable providers, partial failures, concurrency and timeout enforcement, cancellation, and cleanup. Existing sessionServerTools, sessionComparisonService, and sessionComparisonTool suites provide starting harnesses; no tests were executed during this read-only review.
- **Behavior:**

  > An agent can request a bounded comparison of explicitly selected candidates against one fixed task and evaluation contract. Candidate execution must not interfere with the calling session or other candidates, and the caller receives attributable, comparable outcomes with validation evidence and available usage signals. Unavailable candidates and partial failures remain explicit rather than disappearing from the result. Acceptance must cover enforced limits, cancellation, reliable cleanup, and the agreed approval and winner-adoption behavior.
- **Trace:**

  > The existing UI launches comparisons through NewChatWidget and ISessionComparisonService.startComparison; comparison records, Judge verdicts, timing, and token signals live under src/vs/sessions/services/sessions. SessionComparisonService currently launches all attempts through Promise.all, and its cancellation method records state rather than owning comprehensive candidate termination. ReadSessionComparisonTool and the completion tool in src/vs/sessions/contrib/sessionComparison/browser/sessionComparisonTool.ts operate on existing comparisons, with manifest reads restricted to Judge or synthesis participants. Agent Host create_session in node/shared/sessionServerTools.ts supplies model selection, optional worktree isolation, confirmation, and spawn backstops, but returns a link rather than a completed comparison. These are distinct renderer-side and host-side surfaces; the trace does not yet establish a headless orchestration contract spanning them. Preserve ordinary session delegation and the existing comparison workflow's advisory recommendation and explicit adoption/cleanup semantics unless the maintainer chooses otherwise. https://github.com/microsoft/vscode/pull/335498 provides existing workflow context; https://github.com/microsoft/vscode/issues/337410 covers only delegation.
- **Open decisions:**
  - Which candidate dimensions are supported initially: model/provider only, or also custom agent, permission profile, and prompt variation?
  - Does the tool wait for a completed comparison, or return a durable run handle with separately retrievable progress and results?
  - How are fixed success criteria supplied, and what authority may a Judge exercise without changing the task or evaluation contract?
  - What confirmation and resource-budget approval are required before spawning candidates, including any additional Judge or synthesis runs?
  - Which candidate artifacts survive completion or cancellation, and must adopting a winner always require explicit user confirmation?

## Evidence

- **Existing comparison capability:** src/vs/sessions/contrib/chat/browser/chat.contribution.ts registers sessions.chat.compareAgents.enabled, and newChatWidget.ts invokes ISessionComparisonService.startComparison from the new-session UI. src/vs/sessions/services/sessions/common/sessionComparison.ts defines attempts, Judge verdicts, validation provenance, timing, token counts, and selection. These cover substantial comparison functionality, but not the requested invoking-agent tool contract.
- **Existing comparison tools are not launch tools:** src/vs/sessions/contrib/sessionComparison/browser/sessionComparisonTool.ts defines vscode_readAttemptComparison and vscode_completeAttemptComparison. ReadSessionComparisonTool requires an existing comparisonId and rejects callers other than that comparison's Judge or synthesis session; it cannot launch a bake-off for an arbitrary calling agent.
- **Existing delegation is partial coverage:** src/vs/platform/agentHost/node/shared/sessionServerTools.ts exposes create_session with prompt, workspace, worktree, title, model, and relationship, plus confirmation and spawn backstops. formatCreateSessionResult returns a session/chat link rather than completed comparative outcomes. The schema has no candidate array or per-bake-off concurrency, timeout, or resource budget.
- **Remaining orchestration gap:** SessionComparisonService.startComparison in src/vs/sessions/services/sessions/browser/sessionComparisonService.ts limits comparisons to two through ten attempts and launches them through Promise.all. IStartSessionComparisonOptions has no configurable concurrency, timeout, or resource limits; cancelComparison records cancellation state rather than itself aborting and cleaning up every candidate. The existing UI workflow is not full coverage of this request.
