# Issue #337351 — Make agent bake-offs available as an agent-invokable tool

[https://github.com/microsoft/vscode/issues/337351](https://github.com/microsoft/vscode/issues/337351)

## Summary

Keep open: the existing comparison UI and session-delegation tools provide useful building blocks, but neither exposes the requested bounded, agent-invokable bake-off operation. This team-authored request needs decisions about the tool contract, resource authorization, and lifecycle ownership before implementation.

## Change summary

Expose an Agent Host tool that runs isolated candidate attempts under explicit limits and returns comparable structured evidence.

## Best solution

Provide a provider-neutral comparison invocation contract that preserves the existing frozen-task, isolated-attempt, and advisory-verdict semantics. Resolve how host-invoked runs relate to the current client-owned comparison service, including limits, cancellation, cleanup, and authorization, before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/common/agentServerTools.ts`, `src/vs/platform/agentHost/node/shared/sessionServerTools.ts`, `src/vs/sessions/services/sessions/common/sessionComparison.ts`, `src/vs/sessions/services/sessions/browser/sessionComparisonService.ts`, `src/vs/sessions/contrib/sessionComparison/browser/sessionComparisonTool.ts`, `src/vs/sessions/services/sessions/test/browser/sessionComparisonService.test.ts`, `src/vs/sessions/contrib/sessionComparison/test/browser/sessionComparisonTool.test.ts`
- **Validation:** End the plan with executable coverage for invoking a comparison from an ordinary agent session: identical task inputs, isolated candidate workspaces, enforced concurrency/time/resource bounds, structured per-candidate outcomes, unavailable-provider and partial-failure reporting, cancellation, and cleanup. Extend the existing comparison service/tool suites and add host-boundary coverage for the selected invocation contract; preserve the rule that recommendation alone never applies or deletes attempts.
- **Behavior:**

  > An agent can submit an explicit task and bounded candidate set and receive comparable structured outcomes without manually coordinating separate session tools. Candidate runs must not interfere with the caller or each other, and configured limits and cancellation must be enforceable. Results distinguish successful, failed, unavailable, and cancelled candidates and report available change, validation, duration, and usage evidence without inventing missing values. Recommendation must remain distinct from adopting a result, with adoption and cleanup behavior settled explicitly in the product contract.
- **Trace:**

  > The current comparison workflow is owned by SessionComparisonService in src/vs/sessions/services/sessions/browser/sessionComparisonService.ts, with its contract in common/sessionComparison.ts and architecture in src/vs/sessions/SESSION_COMPARISONS.md. startComparison launches attempts concurrently, while judging and synthesis use existing comparison records. ReadSessionComparisonTool in src/vs/sessions/contrib/sessionComparison/browser/sessionComparisonTool.ts accepts an existing comparisonId and restricts access to its Judge or synthesis participants; neither comparison tool launches a bake-off. Agent Host's applyCreateSessionTool in src/vs/platform/agentHost/node/shared/sessionServerTools.ts already offers individual model-selected, isolated delegation, but its result is a creation message rather than a comparison. Preserve provider-owned identities and permissions, frozen task inputs, original attempt worktrees, and advisory judging; platform/workbench code must not import the Sessions layer. The unresolved boundary is whether invocation requires an active owning client or survives independently in the host, and what public limits and result contract it promises. https://github.com/microsoft/vscode/pull/335498 supplies the existing UI comparison foundation; https://github.com/microsoft/vscode/issues/337410 covers narrower delegation, not this remaining capability.
- **Open decisions:**
  - Must a bake-off continue and remain callable without an attached Sessions client, or is an active client an explicit prerequisite?
  - Which candidate dimensions are supported initially, and what stable per-candidate result and evaluation-criteria contract does the caller receive?
  - What confirmation, concurrency, timeout, and resource-budget guarantees apply before and during a multi-candidate invocation?
  - When a run completes or is cancelled, which artifacts are retained for review, and what separate authorization is required to adopt a winner or delete candidate worktrees?

## Evidence

- **Existing comparison capability and remaining gap:** src/vs/sessions/SESSION_COMPARISONS.md documents UI-launched comparisons behind sessions.chat.compareAgents.enabled, isolated worktrees, frozen launch inputs, optional judging, and explicit synthesis. The documented tools readAttemptComparison and completeAttemptComparison inspect or complete an existing comparison; they do not initiate one.
- **Current tool restriction:** src/vs/sessions/contrib/sessionComparison/browser/sessionComparisonTool.ts defines ReadSessionComparisonTool with a required comparisonId and rejects callers outside that comparison's Judge or synthesis participants. This is not a general calling-agent comparison interface.
- **Delegation is partial coverage:** src/vs/platform/agentHost/node/shared/sessionServerTools.ts exposes create_session with model selection and worktree isolation, confirmation handling, and process-wide spawning backstops. applyCreateSessionTool starts one prompt and formatCreateSessionResult returns a creation message/link, not an aggregated comparison with configurable run limits and validation evidence.
- **Existing orchestration ownership:** src/vs/sessions/services/sessions/browser/sessionComparisonService.ts implements startComparison, concurrent attempt launching, cancelComparison, judging, and cleanup paths. src/vs/sessions/SESSION_COMPARISONS.md assigns orchestration and persisted records to ISessionComparisonService in the Sessions client, leaving a meaningful ownership decision for an Agent Host invocation surface.

Its maintainer comment at https://github.com/microsoft/vscode/issues/337410#issuecomment-5818169529 identifies create_session as supporting cross-provider delegation, not bounded comparative evaluation; it cannot serve as a duplicate target.
