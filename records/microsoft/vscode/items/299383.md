# Issue #299383 — Copilot: Support firewalled or airgapped remote machines via SSH

[https://github.com/microsoft/vscode/issues/299383](https://github.com/microsoft/vscode/issues/299383)

## Summary

This remains a valid Backlog feature request: current Copilot networking runs in the remote workspace extension host, so an SSH target without internet access cannot use the local machine's connectivity. The older identical request is in a deprecated Copilot tracker, making this core issue the appropriate place to retain the work.

## Change summary

Allow Copilot and Agent mode in a Remote-SSH workspace to reach model, indexing, and other external services through the connected local machine when the remote host has restricted or no internet access.

## Best solution

Provide a supported local-egress path for Copilot service traffic while workspace tools and file operations continue executing against the remote workspace, with explicit security, policy, and fallback semantics. The design should cover Agent mode and semantic indexing rather than only model requests.

## Plan brief

- **Likely files:** `extensions/copilot/package.json`, `extensions/copilot/src/extension/extension/vscode-node/services.ts`, `extensions/copilot/src/platform/networking/vscode-node/fetcherServiceImpl.ts`, `extensions/copilot/src/platform/networking/common/fetcherService.ts`, `src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts`
- **Validation:** In a Remote-SSH workspace whose remote host has outbound internet blocked while the local client remains online, run an Agent-mode request that reads and edits a remote file and invokes semantic search; model communication, tool calls, and indexing must succeed, remote URIs must remain intact, and a control check must confirm the remote host itself still has no external connectivity.
- **Behavior:**

  > Copilot remains fully usable in a Remote-SSH workspace when only the local VS Code machine has internet access. Model requests, authentication-dependent service calls, Agent-mode operations, and semantic indexing use the supported local egress path, while tools continue reading and modifying the remote workspace with correct remote URIs. Existing local and normally connected remote scenarios must retain their current proxy, certificate, cancellation, streaming, and fallback behavior.
- **Trace:**

  > The Copilot manifest at extensions/copilot/package.json has a Node `main` entry and no explicit extension kind; ExtensionManifestPropertiesService consequently classifies it as a workspace extension, and NativeExtensionHostKindPicker runs it in the remote host when available. Native service registration in extensions/copilot/src/extension/extension/vscode-node/services.ts binds IFetcherService to FetcherService. FetcherService in extensions/copilot/src/platform/networking/vscode-node/fetcherServiceImpl.ts constructs its Electron/Node fetchers in that same process, with NodeFetcher and NodeFetchFetcher performing outbound requests from the remote environment. The attached patch in https://github.com/microsoft/vscode/issues/299383#issuecomment-4430982378 addresses remote URI/path interpretation, not the missing cross-host network path, so that concern should remain separate. Preserve remote execution of workspace tools and existing proxy/CA behavior; do not solve this by moving all Copilot workspace logic to the local extension host.
- **Open decisions:**
  - Should local egress cover all Copilot-owned public network traffic, or only model, embedding, and semantic-index services?
  - Should local routing be automatic when remote connectivity fails, explicitly configured per remote target, or governed by an enterprise policy?
  - What user-visible trust and disclosure contract applies when remote workspace content is transported through the local machine, including fallback when the local relay is unavailable?

## Evidence

- **current execution model:** extensions/copilot/package.json declares a Node `main` entry and no `extensionKind`; src/vs/workbench/services/extensions/common/extensionManifestPropertiesService.ts deduces such extensions as `workspace`, while src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts selects the remote extension host when installed remotely.
- **network path:** extensions/copilot/src/extension/extension/vscode-node/services.ts registers `FetcherService`; extensions/copilot/src/platform/networking/vscode-node/fetcherServiceImpl.ts constructs Electron, Node fetch, and Node HTTPS fetchers inside that extension host.
