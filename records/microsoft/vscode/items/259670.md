# Issue #259670 — Terminal auto approve settings editor integration

[https://github.com/microsoft/vscode/issues/259670](https://github.com/microsoft/vscode/issues/259670)

## Summary

Keep open: current source still sends terminal auto-approval rules to JSON editing, and the related implementation PR was closed without merging. This issue remains the settings-editor integration canonical, with two later reports explicitly consolidated here.

## Change summary

Allow terminal auto-approval rules to be edited in the Settings editor instead of requiring settings.json editing.

Add focused Settings editor model/rendering tests for the selected experience and verify unrelated object settings retain their existing behavior.
- **Behavior:**

  > Users currently encounter an Edit in settings.json action when configuring terminal auto-approval rules. They should be able to manage these rules through the Settings editor, including boolean values, compound approve/matchCommandLine values, and ignoring inherited rules with null. Editing an individual rule should not require copying the full default rule set into user settings. Existing rule matching, approval semantics, and scope behavior must remain unchanged.
- **Trace:**

  > The schema for TerminalChatAgentToolsSettingId.AutoApprove in src/vs/workbench/contrib/terminalContrib/chatAgentTools/common/terminalChatAgentToolsConfiguration.ts contains boolean, nested-object, and null alternatives. In src/vs/workbench/contrib/preferences/browser/settingsTreeModels.ts, getObjectSettingSchemaType delegates each alternative to getObjectRenderableSchemaType; the nested object is unsupported and leads to SettingValueType.Complex. SettingComplexRenderer in src/vs/workbench/contrib/preferences/browser/settingsTree.ts then offers JSON editing; the neighboring ComplexObject renderer is read-only rather than a ready-made editing solution. https://github.com/microsoft/vscode/pull/261218 attempted specialized controls but was closed unmerged with the issue author's objection, so that patch must not be treated as an approved design. The boundary is configuration presentation and editing, not command approval enforcement or a new permission model. Related https://github.com/microsoft/vscode/issues/275220 concerns the approval picker and does not replace this Settings editor request.
- **Open decisions:**
  - Should compound approve/matchCommandLine rules be edited inline in the Settings editor, or through a dedicated rule-editing interaction opened from the setting?
