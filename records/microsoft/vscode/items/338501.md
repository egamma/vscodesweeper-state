# Issue #338501 — Chat unexpectedly resets to Ask across harnesses during mode availability changes

[https://github.com/microsoft/vscode/issues/338501](https://github.com/microsoft/vscode/issues/338501)

## Summary

Confirmed on current main: `validateCurrentChatMode()` calls `setChatMode(ChatModeKind.Agent)` when Agent is transiently unavailable (e.g. tools agent not yet connected after an extension-host reload), but `setChatMode()`'s fallback chain (`findModeById(mode) ?? findModeByName(mode) ?? findModeById(Agent) ?? ChatMode.Ask`) resolves to `ChatMode.Ask` since Agent isn't in the current mode list either, and `setChatMode2` persists that with its default `storeSelection: true` — matching the reporter's traced sequence exactly.

## Change summary

Chat mode unexpectedly and persistently resets from Agent/custom to Ask when a mode (Agent, or a custom agent) becomes transiently unavailable, e.g. during an extension-host reload or managed-settings change.

## Best solution

Redesign the interaction between `validateCurrentChatMode()`, `setChatMode`/`setChatMode2`'s fallback resolution, and `_restorePersistedCustomModeIfAvailable()` in chatInputPart.ts so a transient-unavailability fallback never overwrites the persisted user selection, while still respecting an explicit user choice made during the gap and current policy after it resolves.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts`, `src/vs/workbench/contrib/chat/common/chatModes.ts`
- **Validation:** A chat mode test that toggles `hasToolsAgent`/mode-list availability true → false → true (and separately toggles `chat.agent.enabled`) while a chat session is active in Agent or a custom mode, asserting both the visible mode and the persisted input-state mode remain the original selection once availability returns — per the reporter's suggested regression coverage in the follow-up comment.
- **Behavior:**

  > When Agent, a custom agent, or the tools-agent backend becomes temporarily unavailable (extension-host reload, managed-settings refresh, provider disconnect) and then becomes available again, the user's previously selected chat mode must be restored — the UI-visible mode and the persisted input-state mode must both end up back at the original selection, not stuck on 'Ask'. An explicit mode change the user makes during the unavailability window must still take effect and must not itself be silently overwritten. Acceptance: a test toggling mode-list/tools-agent availability off and back on confirms both current mode and persisted state return to the pre-gap selection.
- **Trace:**

  > In src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts, `registerChatModeValidation` (~line 2245) reacts to `modes.onDidChange` by calling `validateCurrentChatMode()` (~2263) then `_restorePersistedCustomModeIfAvailable()` (~2289). When the current mode (e.g. Agent) is absent from the just-changed mode list, `validateCurrentChatMode` calls `setChatMode(ChatModeKind.Agent)` (or Ask) with default `storeSelection: true`; `setChatMode`'s resolution chain (~1976-1986) can't find Agent either in that moment and falls through to `ChatMode.Ask`, and `setChatMode2` (~1989) immediately persists that into the session's input state via `_syncInputStateToModel()`. `_restorePersistedCustomModeIfAvailable` only reapplies *custom* (non-builtin) persisted modes (`!found.isBuiltin` check at ~2296), so a builtin Agent→Ask fallback is never subsequently undone when Agent reconnects. The reporter's traced real-world sequence (extension-host reload, managed-settings apply) and code inspection agree. The boundary: do not change custom-mode restoration behavior for the already-working case, and do not naively flip `storeSelection` to false in validation alone — the reporter demonstrates that alone reintroduces other regressions (custom-mode restoration undoing an explicit disable, Agent not restoring after re-enable, later state sync re-serializing the fallback). Related commits named in the issue: fd9cf8e3dd1 (#278683), 61915ccbab01b (#278650), 8fa554d6e0030 (#324843), fa5d013e93f (#331715).
- **Open decisions:**
  - Should the mode-availability validation path ever be allowed to persist an automatic fallback (Agent→Ask) into the session's stored input state, or should only explicit user-initiated mode changes be persisted?
  - When a mode becomes available again after a transient gap, should the system unconditionally restore the pre-gap selection, or must it detect and preserve an explicit user mode change made during the gap — and how is 'explicit during the gap' distinguished from 'stale persisted state'?
  - Should builtin modes (Agent) get the same late-restoration treatment that `_restorePersistedCustomModeIfAvailable` currently gives only to custom modes, and if so, does that conflict with policy-driven disablement (e.g. `chat.agent.enabled=false`) that should NOT be silently overridden on restore?
