# Issue #332404 — Copilot Agent switched to unrelated nonexistent web-app task after large tool outputs

[https://github.com/microsoft/vscode/issues/332404](https://github.com/microsoft/vscode/issues/332404)

## Summary

Keep open for Copilot Agent investigation: a team-authored report documents two independent occurrences where long stateful conversations switched to invented web-app tasks and performed unrelated autonomous actions. The repeated symptom and session identifiers provide strong evidence, but the available public data does not isolate whether the defect is in model behavior, backend conversation state, or client orchestration.

## Change summary

Prevent Copilot Agent from abandoning the active task and acting on fabricated prior state after large tool outputs in long Responses API conversations.

## Best solution

Correlate both supplied session and response IDs with backend traces, inspect the stateful Responses API chain around the four large tool-result batches, and add a regression or stress scenario that verifies the agent preserves the active task and does not claim unsupported actions.

## Plan brief

- **Likely files:** `extensions/copilot/src`
- **Validation:** Create a stateful Agent stress test that advances a conversation near the reported context size, appends several large parallel tool outputs, and asserts that the next response remains grounded in the active source-code task and does not assert nonexistent files, tests, or servers.
- **Behavior:**

  > In a long-running Agent conversation, adding several large tool results must not cause the next turn to switch to an unrelated task or treat fabricated prior actions as established state. The agent must continue the current request and ground claims about implementation, tests, files, and running processes in the visible conversation or actual tool evidence. Acceptance should cover repeated stateful turns near the reported context size and verify that no unrelated filesystem, package-manager, or process action is initiated.
- **Trace:**

  > Two sessions reported in https://github.com/microsoft/vscode/issues/332404 show the same transition immediately after four legitimate tool results, with one request near 367k input tokens and `hasPreviousResponseId: true`. The invalid content was logged as a successful model response rather than local tool synthesis, while the state referenced by `previous_response_id` is opaque in the available logs. Investigation therefore needs correlation of the supplied session/response IDs with provider/backend traces before determining whether the boundary is client conversation assembly, stateful response chaining, or model/service behavior. Preserve ordinary long-context tool-result handling and focus the diagnosis on unsupported task-state transitions; broader hallucination mitigation is outside this report's bounded symptom.
- **Open decisions:**
  - Should the product add a client-side safety check that blocks autonomous actions when the model's asserted task state has no support in the visible conversation, or rely on correcting the stateful model/backend chain?
  - If an unsupported task switch is detected, should Agent stop and ask the user to confirm the active task, or automatically resume the last user-requested task?
