# Issue #188307 — ExtensionHostManager: Trying to add a disposable to a DisposableStore that has already been disposed of

[https://github.com/microsoft/vscode/issues/188307](https://github.com/microsoft/vscode/issues/188307)

## Summary

The disposal race remains on current main: asynchronous extension-host startup work can register resources after ExtensionHostManager has been disposed. The issue should remain open for a bounded lifecycle fix and regression test.

## Change summary

Prevent ExtensionHostManager startup continuations from adding disposables after the manager has already been disposed.

## Best solution

Make extension-host startup teardown-safe so late success or failure continuations do not initialize customers, activate extensions, or retain latency-test registrations after disposal, while disposing any resources created by a late completion.

- **Behavior:**

  > Disposing ExtensionHostManager while its extension host is still starting must permanently stop manager-owned startup setup. Whether the pending start later resolves or rejects, no disposable may be added to the disposed manager, no extension activation or customer initialization may occur, and late-created resources must not leak. Normal startup behavior for a live manager must remain unchanged.
- **Trace:**

  > The constructor in src/vs/workbench/services/extensions/common/extensionHostManager.ts assigns `_proxy` from `IExtensionHost.start()`. Its rejection handler returns null, so the subsequent `_proxy.then` still runs and registers the latency provider even after `dispose()` has disposed the inherited store; a late successful start can similarly enter `_createExtensionHostCustomers` and register the RPC responsive-state listener after teardown. This matches the diagnosis in https://github.com/microsoft/vscode/issues/188307#issuecomment-1643367966. The boundary is ExtensionHostManager's asynchronous startup lifecycle: do not change successful live-host activation, telemetry semantics, or unrelated extension-service shutdown behavior.

## Evidence

- **current source:** In src/vs/workbench/services/extensions/common/extensionHostManager.ts, the constructor starts the host asynchronously at lines 117-153 and then unconditionally runs another `_proxy.then` continuation at lines 155-161 that calls `_register(registerLatencyTestProvider(...))`; `dispose()` at lines 168-182 can dispose the inherited store before either continuation runs.
- **failure path:** The startup rejection handler logs the error and returns null, converting the rejection into a fulfilled `_proxy`; this still executes the later continuation and attempts `_register` after disposal, matching the reported CI stack.
- **success race:** A late successful start calls `_createExtensionHostCustomers`, where src/vs/workbench/services/extensions/common/extensionHostManager.ts registers the RPC responsive-state listener on the same potentially disposed manager and creates customers after teardown.
