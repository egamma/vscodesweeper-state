# Issue #283598 — Git - Branch Protection Rules Should Use Upstream Branch name

[https://github.com/microsoft/vscode/issues/283598](https://github.com/microsoft/vscode/issues/283598)

## Summary

Keep open: branch protection still matches local branch names, so a differently named branch tracking origin/main remains unprotected. The merged workspace-settings workaround does not implement upstream-name matching; this team-authored Backlog request remains valid.

## Change summary

Make branch protection recognize protected upstream branches when their local tracking branches have different names.

## Best solution

Make the built-in Git protection check recognize main2 tracking origin/main without requiring users to enumerate local aliases. Settle whether upstream matching supplements or replaces local-name matching before changing the existing protection contract.

- **Behavior:**

  > With main configured as protected, committing through Source Control on main2 tracking origin/main should offer the protected-branch warning and new-branch choice. Users should not need to list every local alias of a protected upstream. Acceptance must also establish the intended treatment of local protected names tracking unprotected upstreams and branches without an upstream. Existing prompt-mode choices remain unchanged.
- **Trace:**

  > GitBranchProtectionProvider in extensions/git/src/branchProtection.ts publishes git.branchProtection patterns under the empty remote key. - **Open decisions:**
  - When an upstream exists, should its name replace local-name matching, or should either name matching a protected pattern trigger protection? The choice changes behavior for a local main tracking an unprotected remote branch.
  - Should upstream-name semantics apply to both git.branchProtection settings and extension-contributed remote rules, or only to the settings-based protection requested here?
