# Issue #337874 — Agents Window: MCP details lose source provenance or remain stuck loading

[https://github.com/microsoft/vscode/issues/337874](https://github.com/microsoft/vscode/issues/337874)

## Summary

Extremely well-diagnosed dual-root-cause bug, both parts confirmed against current `main`: the loading race in `EmbeddedMcpServerDetail` and the dropped provenance in Agent Host's top-level MCP reflection. No fix has landed yet, so this stays open for implementation.

## Change summary

MCP server details in the Agents Window either hang on 'Loading...' (source-backed servers) or show 'No definition is available' (Agent Host top-level servers) because of two independent bugs.

## Best solution

Fix root cause 1 by having `setMigratable()` avoid discarding an in-flight `loadSourceDefinition()` read on an unrelated input clone (e.g. compare identity/generation more carefully, or bump `renderGeneration` only on true render-affecting changes); separately extend `ISdkMcpServer`/the Agent Host reflection path to carry authoritative source-path metadata from the Copilot SDK inventory into `McpCustomizationController._buildTopLevel()` so `AbstractAgentHostCustomizationService.getMcpServers()` no longer has to suppress `sourceUri` for `mcp-top-level:` entries.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/aiCustomization/embeddedMcpServerDetail.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/platform/agentHost/node/shared/mcpCustomizationController.ts`
- **Validation:** A detail-view regression test with a pending source read followed by `setMigratable(false)` (as the reporter suggests) for root cause 1; an inventory-to-customization test asserting a top-level MCP server retains a usable `sourceUri`/source path for root cause 2.
- **Behavior:**

  > For root cause 1: opening an MCP server's details whose definition is loaded from a source file must finish loading even if migration/diagnostic state on the same server changes while the read is pending — no permanently-stuck 'Loading...' state. For root cause 2: an MCP server surfaced by the Agent Host's top-level reflection (not backed by a discovered plugin/directory) must still expose enough source provenance for the Agents Window to show or open its definition, across local and remote Agent Hosts and respecting `COPILOT_HOME`.
- **Trace:**

  > Root cause 1: `EmbeddedMcpServerDetail.renderItem()` (embeddedMcpServerDetail.ts:238-276) starts `loadSourceDefinition(server, source, renderGeneration)` capturing `server = this.current`; `AICustomizationManagementEditor.refreshMcpDetailMigrationState()` then calls `setMigratable()` (line 215), which clones `this.current` via spread without touching `renderGeneration`, so when the read resolves the identity check at line 503 fails and the result is silently dropped. Root cause 2: `CopilotAgentSession._applyMcpServerList()` (copilotAgentSession.ts:6886) maps SDK inventory entries into `ISdkMcpServer` via `_toSdkMcpServer`, discarding any source info before it reaches `McpCustomizationController._buildTopLevel()` (mcpCustomizationController.ts:474), which mints a synthetic `mcp-top-level:` id with no real source URI. Boundary: do not change plugin-backed MCP server rendering (which already carries `mcpSource`/`source.uri` correctly per the Figma case) or the migration-state UI itself — only the discard/suppression paths.
- **Open decisions:**
  - Should the SDK inventory contract add a source-path field to `ISdkMcpServer`, or should Agent Host resolve provenance itself (e.g. deriving it from `~/.copilot/mcp-config.json` equivalents) — the reporter explicitly warns against client-side guessing, so this needs an SDK/protocol decision.
  - How should this generalize to remote Agent Hosts and a non-default `COPILOT_HOME`, where the client cannot assume a local file path?

## Evidence
