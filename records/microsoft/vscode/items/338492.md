# Issue #338492 — Peer sessions list is inconsistent when marking peer sessions as done

[https://github.com/microsoft/vscode/issues/338492](https://github.com/microsoft/vscode/issues/338492)

## Summary

Reporter demonstrates with clear steps and a video that an archived ('marked done') peer session transiently reappears in the Sessions list when a new chat is added; this looks like a real catalog-hydration race rather than a UI nit, but I couldn't trace the exact fault in the provider/filter pipeline from source alone, so it stays open pending deeper diagnosis.

## Change summary

Marking a peer session as done (archiving it) correctly hides it, but adding a new chat afterward makes the archived session briefly flash back into the visible list before it settles again.

## Best solution

Diagnose whether a transient/incomplete provider-catalog republish (triggered by the new chat) is momentarily surfacing a stale, not-yet-archived facade for the peer session before the filter in SessionsList re-excludes it, per the 'transient incomplete catalogs' caveat already documented in SESSIONS_LIST.md; fix in the sessions provider/list filtering path once the race is pinned down.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`
- **Validation:** A test that archives a peer session, triggers whatever catalog event fires on new-chat creation, and asserts the archived session's row is never rendered/visible during that event sequence.
- **Behavior:**

  > After a peer session is marked done (archived), it must stay excluded from the main Sessions list through any subsequent catalog update, including the one triggered by creating a new chat. No archived session should transiently re-render as visible, even for a single frame/tick. Acceptance: a regression test that archives a session, fires a new-chat/catalog-refresh event, and asserts the archived session never becomes visible in the filtered list during that sequence.
- **Trace:**

  > Marking a session 'done' is the existing archive flow (ChatSessionArchiveActionWording.MarkAsDone in sessionsViewActions.ts) which sets session.isArchived via ISessionsManagementService.archiveSession. SessionsList filters with `!s.isArchived.get()` (sessionsList.ts). SESSIONS_LIST.md documents that providers may transiently publish incomplete catalogs while reconnecting/hydrating, meaning a session facade object can be (re)created without its archived flag populated yet. The suspected trigger is whatever catalog/session-list recompute fires when a new chat is added (possibly a full catalog republish from the agent host provider in baseAgentHostSessionsProvider.ts) momentarily surfacing a stale, not-yet-hydrated facade for the archived session. I did not conclusively trace which event handler or provider causes the republish on 'add new chat' — that is the open diagnostic step. Boundary: any fix must not change the documented behavior that non-definitive `onDidChangeSessions.removed` events should not drop list-owned state (SESSIONS_LIST.md, 'Durable user intent'); the archived flag itself, not catalog removal, should gate visibility.
- **Open decisions:**
  - Which event path actually republishes/recreates the peer session facade when a new chat is added — is it an agent-host catalog refresh, or a sessions-list recompute unrelated to the provider?
  - Should the fix suppress rendering while a facade is known-stale/hydrating, or ensure the archived flag is preserved across facade recreation so the filter never sees a false negative?

## Evidence

- **mark-as-done is archiving:** src/vs/sessions/contrib/sessions/browser/views/sessionsViewActions.ts shows ChatSessionArchiveActionWording.MarkAsDone is just a wording variant over the existing archive/unarchive flow (archiveSessionsWithUndo), so 'marked done' == session.isArchived.get() === true.
- **archived filtering:** src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts filters sessions with `filtered.filter(s => !s.isArchived.get())`; a transient read of a stale/rehydrating session facade whose isArchived observable hasn't caught up yet would let it slip back into the visible list.
- **documented hydration caveat:** src/vs/sessions/SESSIONS_LIST.md: "Providers may transiently publish incomplete catalogs while reconnecting or hydrating, so `onDidChangeSessions.removed` is not proof of deletion" — the spec already acknowledges transient catalog republish behavior that plausibly explains this flicker.
