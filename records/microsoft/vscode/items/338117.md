# Issue #338117 — `run_in_terminal` returns `Command produced no output` for `git branch --show-current` while chat displays the branch name

[https://github.com/microsoft/vscode/issues/338117](https://github.com/microsoft/vscode/issues/338117)

## Summary

Well-documented, deterministic repro from the reporter (consistent across 4+ calls and multiple models, with a clear comparison table against `git rev-parse --abbrev-ref HEAD` which works correctly), and a second independent reporter corroborates missing/truncated output from `run_in_terminal` under Git Bash. I traced the likely mechanism to the no-shell-integration output capture path but could not conclusively confirm the exact failure in the regex heuristics without live reproduction, so this stays open rather than being closed or definitively marked fixed.

## Change summary

`run_in_terminal` reports `Command produced no output` for `git branch --show-current` (and apparently other commands) in Git Bash on Windows, even though the terminal clearly shows the real output, misleading the model into thinking HEAD is detached.

## Best solution

Investigate and harden the no-shell-integration (`NoneExecuteStrategy`/`BasicExecuteStrategy`) output capture/stripping path in src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/ so single-line command output that coincides with prompt-like patterns isn't silently stripped to empty; likely needs instrumented reproduction with the reporter's actual Git Bash prompt to pin the exact regex/heuristic at fault.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/strategyHelpers.ts`, `src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/noneExecuteStrategy.ts`, `src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/basicExecuteStrategy.ts`
- **Validation:** Once the exact failure mode is reproduced, add a strategyHelpers/noneExecuteStrategy unit test asserting that a short, single-line command output (e.g. a bare branch name) adjacent to a Git-Bash-style two-line prompt is preserved rather than stripped to empty.
- **Behavior:**

  > When `run_in_terminal` (sync mode) runs a command that produces real, visible output in the terminal, the tool result returned to the model must contain that output (or an accurate error if capture genuinely failed) — it must never report 'Command produced no output' when the terminal pane shows non-empty output for the same invocation. Acceptance: a reproduction using a command whose output is a single short line (like `git branch --show-current`) adjacent to the shell's next prompt no longer yields an empty/no-output result when shell integration is basic or absent.
- **Trace:**

  > The 'Command produced no output' message is appended whenever the final captured/stripped output's `trim()` is empty (noneExecuteStrategy.ts:180, basicExecuteStrategy.ts:292, richExecuteStrategy.ts:240). For terminals without rich shell integration (plain Git Bash on Windows, as in this report), output is captured via xterm buffer markers and then run through `stripCommandEchoAndPrompt`/`_stripCommandEchoAndPromptOnce` in strategyHelpers.ts, which uses a set of regex heuristics to strip the command echo and trailing prompt-like lines. I attempted to trace exactly how a single-line output like `feature/widget` could be stripped along with Git Bash's two-line MINGW64 prompt, but my manual regex trace did not conclusively reproduce the empty result — the exact failure needs to be confirmed against the reporter's actual terminal rendering (possibly prompt wrapping, color codes, or a different line layout than I assumed). Do not restructure the whole execute-strategy pipeline or change shell-integration detection — the boundary is the output-stripping/'no output' determination logic in the files above. Related: comment from y2kbugger (https://github.com/microsoft/vscode/issues/338117#issuecomment variant, 2026-10-01) describing a related dropped-output symptom in the same code path.
- **Open decisions:**
  - Should the 'Command produced no output' heuristic be made more conservative (e.g. skip prompt-stripping, or verify against exit code / known-output commands) specifically for the no-/basic-shell-integration paths, even at the cost of occasionally leaving stray prompt fragments in the output?
  - Is there a reasonable path to encourage/auto-detect full shell integration for Git Bash on Windows so these strategies (which rely on fragile heuristics) are used less often for this environment?
