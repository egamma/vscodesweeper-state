# Issue #338117 — `run_in_terminal` returns `Command produced no output` for `git branch --show-current` while chat displays the branch name

[https://github.com/microsoft/vscode/issues/338117](https://github.com/microsoft/vscode/issues/338117)

## Summary

Thoroughly documented, self-consistent report (repeated with a fresh transcript in the comment) that `run_in_terminal` mislabels a real, empty-looking-but-actually-present single-line output as 'Command produced no output' for `git branch --show-current` in Git Bash on Windows — a plausible defect in the output-capture/prompt-stripping heuristics, but I could not pin the exact failing code path from source alone (no live terminal to exercise), so this stays open and unrouted rather than closed.

## Change summary

`run_in_terminal` tells the model a Git Bash command produced no output while the chat UI shows the actual branch name, causing the model to wrongly conclude HEAD is detached.

## Best solution

Diagnose whether the empty result comes from richExecuteStrategy/basicExecuteStrategy's fallback to xterm marker capture plus stripCommandEchoAndPrompt's prompt-fragment heuristics (which may consume a short, real one-line output as part of Git Bash's branch-in-prompt PS1), or from getOutput() itself being empty; then either fix the capture path or, per the reporter's suggestion, stop conflating 'output capture uncertain' with 'command produced no output' in the tool result.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/strategyHelpers.ts`, `src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/richExecuteStrategy.ts`, `src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/basicExecuteStrategy.ts`, `src/vs/workbench/contrib/terminal/common/scripts/shellIntegration-bash.sh`
- **Validation:** Add a unit test (alongside noneExecuteStrategy.test.ts / a rich/basic strategy test) that simulates a Git-Bash-style two-line prompt embedding the branch name (e.g. `user@host MINGW64 ~/repo (feature/widget)\n$ `) immediately after a one-line command output equal to that same branch name, and asserts the real output is preserved rather than reported as empty.
- **Behavior:**

  > When `run_in_terminal` runs a command like `git branch --show-current` whose only output is a single short line (here, a branch name), the tool result returned to the model must contain that line whenever it was actually printed to the terminal — matching what the chat UI displays. The tool must not report 'Command produced no output' unless the command genuinely produced no output (as it does for detached HEAD); if output capture is uncertain, that uncertainty should be represented differently from a confirmed-empty result. Acceptance: a new test proves that a one-line output matching text found in the following prompt line is still returned intact.
- **Trace:**

  > Both richExecuteStrategy.ts and basicExecuteStrategy.ts try `finishedCommand.getOutput()` first and fall back to `xterm.getContentsAsText()` between start/end markers, then in both cases call `stripCommandEchoAndPrompt()` (strategyHelpers.ts) before checking `output.trim().length === 0` to decide whether to append 'Command produced no output'. `stripCommandEchoAndPrompt`'s trailing-prompt stripping (`isCompletePrompt`/`isPromptFragment` regexes, lines ~149-181) is pattern-based on the captured text rather than driven by OSC 633 markers, and Git Bash's default PS1 (via git-prompt.sh) puts the current branch name in parentheses in the very next prompt line — a plausible collision for a one-line output that is itself a branch name. I could not execute a real Git Bash + shell-integration session in this read-only, no-build checkout to confirm which of getOutput(), the marker fallback, or the stripping regexes is the actual failure point, so the diagnosis stops here. Do not change the prompt-stripping behavior for other shells (PowerShell/cmd) that the existing regexes and tests already cover.
- **Open decisions:**
  - Should the tool only emit 'Command produced no output' when there is positive confirmation of an empty capture (e.g. a clean shell-integration `getOutput()` result), versus whenever heuristic marker/regex stripping happens to yield an empty string?
  - Should the tool distinguish 'output capture likely failed or was stripped' from 'command genuinely printed nothing' in its additionalInformation, as the reporter requests, and if so what should that wording be?
  - Does fixing this require special-casing Git Bash's branch-in-prompt PS1 inside stripCommandEchoAndPrompt, or should the fix instead prefer command-detection's getOutput() over heuristic marker-based capture for this class of shell?

## Evidence

- **output-empty logic:** src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/richExecuteStrategy.ts (~lines 204-241) and basicExecuteStrategy.ts (~lines 260-293) push 'Command produced no output' whenever the assembled `output.trim().length === 0`, without distinguishing a genuinely empty command result from a capture/stripping failure.
- **heuristic stripping:** src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/strategyHelpers.ts stripCommandEchoAndPrompt()/_stripCommandEchoAndPromptOnce() uses regex heuristics (isCompletePrompt/isPromptFragment, lines ~149-181) on marker-captured text to remove command echo and the next prompt; these are pattern-based, not shell-integration-marker-based, and Git Bash's default PS1 embeds the current branch name in the following prompt line, which is a plausible collision point for a one-line output like a bare branch name.
