# Issue #73748 — Be able disable task detection from tasks.json or override tasks execution

[https://github.com/microsoft/vscode/issues/73748](https://github.com/microsoft/vscode/issues/73748)

## Summary

Keep open: current task settings and provider APIs do not cover scheme-specific suppression or execution interception for arbitrary tasks.json tasks. This team-authored, accepted request still needs a public-contract decision; no qualifying fix or canonical duplicate was identified.

## Change summary

Allow filesystem-provider extensions to suppress tasks.json tasks for their URI schemes or control their execution with the originating resource available.

## Best solution

Define a scheme-aware task contract that prevents filesystem-provider tasks from unintentionally running locally while preserving ordinary local and Remote Development tasks. The task and extension-API owners should choose whether extensions suppress discovery or intercept execution, including how the originating URI is exposed.

- **Validation:** Use a test FileSystemProvider with a non-file workspace containing a shell task in .vscode/tasks.json. Verify the selected contract either suppresses that task or delegates its execution with the exact originating URI, without starting the unintended local command. Repeat with file: and vscode-remote: workspaces and a mixed-scheme workspace to confirm unaffected discovery and execution.
- **Behavior:**

  > A filesystem-provider extension needs control over tasks loaded from its remote or virtual resources because those commands may be invalid locally. The issue offers two alternative outcomes: suppress those tasks by URI scheme, or delegate their execution while retaining the originating tasks.json URI. Acceptance must demonstrate the chosen outcome for a non-file workspace and preserve existing local and Remote Development behavior. A mixed-scheme workspace must not lose valid tasks from unaffected folders.
- **Trace:**

  > AbstractTaskService._getConfiguration reads resource-scoped tasks configuration, and _computeWorkspaceFolderTasks parses it with platform information selected by workspaceFolder.uri.scheme. Its JSON-task availability gate is global shell/process support, not per-scheme extension control. TaskProvider.resolveTask handles unresolved tasks of a registered task type; it is not an interception contract for arbitrary resolved tasks. _executeTask dispatches to the task system after refreshing configuration. These paths establish the remaining capability gap without executing code. Preserve provider-specific resolution and existing file: and vscode-remote: execution semantics. https://github.com/microsoft/vscode/issues/33523 addresses a different resolution problem; https://github.com/microsoft/vscode/issues/197377 concerns URI substitution and does not absorb this request.
- **Open decisions:**
  - Should filesystem-provider extensions be able to suppress tasks.json discovery for their schemes, intercept execution, or support both contracts?
  - If execution interception is supported, what originating resource information must the public API expose, including tasks defined in a workspace file rather than a folder's tasks.json?
  - Should unregistered non-file schemes retain today's task discovery behavior or require explicit opt-in, and what compatibility guarantees apply to mixed-scheme workspaces?
