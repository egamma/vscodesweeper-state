# Issue #179725 — Support multiple decorations in editor glyph margin

[https://github.com/microsoft/vscode/issues/179725](https://github.com/microsoft/vscode/issues/179725)

## Summary

Dedicated breakpoint lanes, zIndex ordering, and internal glyph widgets are implemented, but actionable overflow and extension-facing interaction remain incomplete. Keep this staged proposal open: the verified related issues cover only parts of its scope.

## Change summary

Support predictable glyph-margin lanes with discoverable, keyboard-accessible overflow and actions for core and extension-contributed decorations.

## Best solution

Finish the remaining interaction design so decorations hidden by same-lane collisions remain discoverable and actionable without widening the gutter unnecessarily. Preserve breakpoint interaction and coordinate internal widget adoption with a separately agreed extension API contract.

## Plan brief

- **Likely files:** `src/vs/editor/browser/viewParts/glyphMargin/glyphMargin.ts`, `src/vs/editor/contrib/hover/browser/glyphHoverComputer.ts`, `src/vs/editor/contrib/hover/browser/glyphHoverWidget.ts`, `src/vs/editor/browser/editorBrowser.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** End the plan with an executable editor scenario placing differently prioritized actionable and non-actionable decorations on the same line and lane: verify overflow is indicated, every hidden decoration is discoverable, mouse and keyboard can invoke its own action, and breakpoint toggling remains independent. Cover winner selection and overflow enumeration with targeted editor tests; specify extension-host acceptance checks once the public contract is selected.
- **Behavior:**

  > When multiple decorations occupy the same glyph-margin lane, lower-priority decorations must remain discoverable rather than disappearing behind the winner. Users must be able to inspect non-actionable decorations and invoke each actionable decoration through mouse and keyboard interaction, with descriptive accessible labels. Breakpoint placement and toggling must remain predictable and independent of other decorations. Acceptance should include collisions involving different priorities and a mixture of actionable and non-actionable decorations without unnecessary gutter expansion.
- **Trace:**

  > GlyphMarginWidgets in src/vs/editor/browser/viewParts/glyphMargin/glyphMargin.ts collects both decoration and widget requests, sorts them by location and priority, and renders only the winner at each location; prepareRender still explicitly marks overflow as unfinished. GlyphHoverComputer and GlyphHoverWidget provide lane-filtered markdown messages, not an overflow icon/action surface. Internal widget access exists in src/vs/editor/browser/editorBrowser.ts, while src/vscode-dts/vscode.d.ts exposes gutterIconPath without equivalent widget or selection-event access. Preserve existing zIndex ordering and breakpoint-lane behavior; this is not a request to restore naive unbounded gutter expansion. https://github.com/microsoft/vscode/issues/185814 tracks core widget adoption, and https://github.com/microsoft/vscode/issues/47559 tracks extension exposure; neither absorbs the complete proposal. The unresolved boundary is the observable overflow presentation and the extension interaction contract, not whether existing internal widgets are available.
- **Open decisions:**
  - Which visual indicator should identify same-lane overflow, and how should it present the hidden decorations while keeping gutter width compact?
  - Should extension-contributed decoration actions use a command-bearing decoration contract, a selection event, or another public interaction contract?

## Evidence

The maintainer's April 12, 2023 comment endorses the proposal and recommends staged PRs; the author's April 13 comment explicitly separates zIndex ordering, overflow hover, click handlers, and the debug lane.
- **Existing capability and remaining overflow gap:** src/vs/editor/browser/viewParts/glyphMargin/glyphMargin.ts, GlyphMarginWidgets._collectSortedGlyphRenderRequests and prepareRender, orders requests by line, lane, and descending zIndex. prepareRender selects a winner per location, combines equal-priority decoration classes, and retains the explicit TODO 'Implement overflow for remaining decorations'; losing widgets receive no renderInfo and are hidden.
