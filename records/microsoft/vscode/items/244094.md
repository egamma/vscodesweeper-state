# Issue #244094 — Local server auth does not work when connected to remote

[https://github.com/microsoft/vscode/issues/244094](https://github.com/microsoft/vscode/issues/244094)

## Summary

Keep open for investigation of the maintainer-confirmed GitHub sign-in failure in remote workspaces. Current source places the server on the client and disables tunneling for the local extension host, but does not establish that the reported browser-opening failure is resolved.

## Change summary

Selecting the local-server GitHub authentication flow while connected to a remote workspace fails to open the local sign-in page.

## Best solution

Make local-server GitHub sign-in work in a desktop remote workspace as it does in a local workspace. First reproduce on a current build and distinguish browser-opening failure from loopback request failure; the source does not support assuming the listener runs remotely.

Compare with a local workspace and capture GitHub Authentication output and the browser-opening result if the remote case fails.
- **Behavior:**

  > The report describes local-server GitHub sign-in failing to open the local page when a desktop window is connected to a remote workspace. A maintainer confirmed the failure while GitHub Authentication was running on the client. The expected outcome is that the client browser reaches the client-side loopback server and authentication completes, regardless of whether the workspace is local or remote. Acceptance should compare those two workspace configurations on a current build.
- **Trace:**

  > LocalServerFlow.trigger in extensions/github-authentication/src/flows.ts starts LoopbackAuthServer, opens its 127.0.0.1 /signin URL, and waits for the OAuth response; it does not await the opening result. LoopbackAuthServer in extensions/github-authentication/src/node/authServer.ts binds locally and redirects /signin to GitHub. The local extension host supplies isRemote=false, and env.openExternal in src/vs/workbench/api/common/extHost.api.impl.ts consequently passes allowTunneling=false through MainThreadWindow.$openUri. These paths do not conclusively explain the observed failure; investigation must determine whether opening fails or the browser cannot reach the listener. Preserve the separation between client-side loopback authentication and genuine remote-host URL forwarding, and do not weaken OAuth state or nonce validation. The confirmed report is https://github.com/microsoft/vscode/issues/244094#issuecomment-2746356741; the later loopback redirect change at https://github.com/microsoft/vscode/commit/31620a3decb7f5ec0d6a3c55fab89ab17906a77e does not prove this initial-opening failure was fixed.
