# Issue #321202 — agent-host: AHP Client UI Library

[https://github.com/microsoft/vscode/issues/321202](https://github.com/microsoft/vscode/issues/321202)

## Summary

Keep open: this team-authored architectural request remains unmet on current main. VS Code has an internal AHP-to-chat adapter and reusable workbench widget, but no portable AHP client UI library, and no older canonical issue was found.

## Change summary

Provide reusable, composable UI components for AHP clients to render conversations, reasoning, tool calls, and related interaction states.

## Best solution

Define a supported browser-facing AHP presentation contract and extract reusable conversation components without requiring consumers to recreate VS Code's large workbench service graph. A maintainer-led design should first settle the package boundary, runtime/framework support, and stable customization surface.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/stateToProgressAdapter.ts`, `src/vs/sessions/contrib/chat/browser/chatView.ts`, `extensions/copilot/chat-lib/package.json`
- **Validation:** End the plan with browser component tests that feed representative AHP user messages, markdown, reasoning, running/completed tool calls, and confirmation states into the proposed public surface and assert equivalent rendering and action dispatch under at least two themes.
- **Behavior:**

  > A web-based AHP client can render a complete conversation using supported reusable components rather than independently implementing user and agent messages, reasoning, tool calls, and interaction states. Consumers can compose or replace parts, supply hooks for actions, and apply supported theming without depending on VS Code's workbench services. Acceptance should cover representative completed and streaming AHP states, tool confirmation dispatch, accessibility, and theme behavior through the public contract.
- **Trace:**

  > Current AHP integration is split between AgentHostSessionHandler and stateToProgressAdapter.ts, which translate protocol state into VS Code's IChatSessionHistoryItem and IChatProgress model, and ChatWidget in chatWidget.ts, which renders that model through a large workbench dependency graph. The Agents window reuses ChatWidget internally through src/vs/sessions/contrib/chat/browser/chatView.ts, but this remains inside VS Code's service and model boundary. The existing extensions/copilot/chat-lib package is a non-UI chat/inline-editing SDK and does not expose AHP presentation components. The uncertainty starts at the supported public boundary: package ownership, browser/runtime support, framework coupling, guaranteed AHP state coverage, and customization compatibility. Preserve existing VS Code chat rendering and AHP protocol semantics while designing the reusable contract; do not treat an internal widget refactor alone as satisfying external clients.
- **Open decisions:**
  - Is the supported deliverable an externally consumable package for independent AHP clients, or only a shared component layer for VS Code-owned surfaces?
  - Must the public UI contract be framework-neutral, or may it require React and expose React-specific lifecycle and composition semantics?
  - Which AHP conversation states and actions are guaranteed by the initial public contract, and which may be supplied through consumer-defined render hooks?
  - What theming and accessibility guarantees form part of the stable consumer contract?

## Evidence

- **current adapter:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/stateToProgressAdapter.ts contains VS Code-specific conversions such as turnsToHistory and activeTurnToProgress, mapping AHP turns, reasoning, and tool calls into IChatProgress and IChatSessionHistoryItem rather than exposing reusable UI components.
- **widget boundary:** src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts defines ChatWidget, but its constructor depends on a large set of VS Code workbench services including editor, configuration, context keys, chat models, tools, accessibility, telemetry, lifecycle, and Agent Host services, so it is not a portable AHP client component.
- **existing reuse:** src/vs/sessions/contrib/chat/browser/chatView.ts reuses the internal ChatWidget for the Agents window, showing that sharing exists inside the VS Code dependency-injection boundary but does not satisfy the proposed standalone client library.
- **existing SDK:** extensions/copilot/chat-lib/package.json describes @vscode/chat-lib as a chat and inline-editing SDK, but its package surface contains no AHP UI component contract; it does not cover the central request.
