# Issue #337675 — Windows Magnifier Cursor Tracking jumps back to beginning of line when selecting text

[https://github.com/microsoft/vscode/issues/337675](https://github.com/microsoft/vscode/issues/337675)

## Summary

Traced the reporter's (Gemini-assisted) root-cause analysis directly against current main and it holds up exactly: when the primary selection is non-empty, `_updateSelectionAndControlBounds` reports a bounding box spanning the whole line width from column 0, instead of the actual selection/caret extent, which is what makes Windows Magnifier (following the EditContext selection/control bounds via UIA) snap to the start of the line on the first Shift+Arrow keypress.

## Change summary

Windows Magnifier's 'follow text cursor' loses the caret and jumps to line start as soon as a selection begins, because the EditContext selection bounds collapse to full-line-width-from-column-0 for non-empty selections.

## Best solution

Compute real horizontal bounds for non-empty selections (e.g. via `RenderingContext.linesVisibleRangesForRange`) instead of defaulting `left` to `contentLeft` and `width` to the remaining line width, so `updateSelectionBounds`/`updateControlBounds` reflect where the selection actually is — but the exact shape for multi-line selections needs a maintainer's call before implementing.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts`
- **Validation:** No existing automated check; the plan should end with either a targeted unit test around `_updateSelectionAndControlBounds` (if a test harness is added) or an explicit manual verification with Windows Magnifier's 'follow text cursor' setting.
- **Behavior:**

  > When Windows Magnifier is set to follow the text cursor and the user extends a selection with Shift+Arrow, the magnifier viewport should track the moving selection endpoint (caret), not jump to the start of the line. The bounds VS Code reports via `EditContext.updateSelectionBounds`/`updateControlBounds` for a non-empty selection must reflect where the selection actually is on screen, not a fixed column-0-to-line-end rectangle.
- **Trace:**

  > `_updateSelectionAndControlBoundsData` (nativeEditContext.ts:569) only computes `_linesVisibleRanges` when the selection `isEmpty()`; for non-empty selections it sets it to null. `_updateSelectionAndControlBounds` (nativeEditContext.ts:579) then falls back to `left = parentBounds.left + contentLeft - this._scrollLeft` and `width = parentBounds.width - contentLeft` for non-empty selections — i.e. the full line width starting at column 0 — which is what the OS/UIA magnifier reads and snaps to. `linesVisibleRangesForRange` on `RenderingContext` (renderingContext.ts:13) is the existing primitive for computing real horizontal extents of a range and is the likely building block for a fix. Do not change the empty-selection (caret) path, which already works correctly per the reporter.
- **Open decisions:**
  - Should selectionBounds/controlBounds for a non-empty selection represent the full selected region's bounding box (potentially spanning multiple lines), or just the active/focus end of the selection (closer to a caret-tracking semantic), to best match what Windows Magnifier and other UIA-based tools expect?
  - How should multi-line selections be handled — a single bounding rect spanning all selected lines, or per-line rects, given `updateSelectionBounds` takes a single DOMRect?

## Evidence

- **available API for a fix:** src/vs/editor/browser/view/renderingContext.ts exposes `linesVisibleRangesForRange(range, includeNewLines)`, which could compute the actual horizontal extents of the selection instead of defaulting to full line width.
