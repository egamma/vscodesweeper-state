# Issue #337422 — Agents window: Files/Changes panel remains visible in embedded browser without a toggle

[https://github.com/microsoft/vscode/issues/337422](https://github.com/microsoft/vscode/issues/337422)

## Summary

Confirmed real gap: the desktop (non-single-pane) session layout controller has no rule hiding the Files/Changes side pane for Browser tabs, unlike the single-pane layout which already does this via `isEditorWithoutDockedDetails`. Keeping open; the fix needs a maintainer decision on the exact desired behavior before implementation.

## Change summary

In the desktop Agents-window layout, switching the active tab to an embedded browser leaves the Files/Changes auxiliary-bar panel visible with no way to hide it, unlike single-pane mode where Browser tabs auto-hide the detail panel.

## Best solution

Extend `src/vs/sessions/contrib/layout/browser/desktopSessionLayoutController.ts` (documented as rules D1-D11 in the companion .md) with an analogous rule to the single-pane `isEditorWithoutDockedDetails` behavior in `singlePaneExistingSessionStrategy.ts`/`singlePaneDraftSessionStrategy.ts`, or alternatively add a panel-toggle action to the embedded browser's toolbar; either resolves the reported gap.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/layout/browser/desktopSessionLayoutController.ts`, `src/vs/sessions/contrib/layout/browser/desktopSessionLayoutController.md`, `src/vs/sessions/contrib/layout/browser/singlePane/singlePaneSharedHelpers.ts`, `src/vs/sessions/contrib/browserView/browser/sessionBrowserView.ts`
- **Validation:** A desktop-layout-controller test asserting that activating a `BrowserEditorInput` hides `Parts.AUXILIARYBAR_PART` (mirroring the existing single-pane test 'hides details for self-contained editors...'), or a UI test verifying a toggle affordance is present in the browser toolbar.
- **Behavior:**

  > In the Agents window's regular (non-single-pane, wide) desktop layout, switching the active editor tab to an embedded browser should not leave the Files/Changes side panel occupying screen space with no way to dismiss it. Either the panel should auto-hide (restoring on switching back to Files/Changes, mirroring single-pane behavior), or the browser toolbar should gain a toggle control for it. Existing side-pane state/restore rules (D1-D11) for other tab types must be unaffected.
- **Trace:**

  > The desktop LayoutController (src/vs/sessions/contrib/layout/browser/desktopSessionLayoutController.ts) manages the auxiliary bar's visibility per documented rules D1-D11 in the sibling .md file, none of which reference the active editor type. The single-pane strategies already solve the same problem via `isEditorWithoutDockedDetails()` (src/vs/sessions/contrib/layout/browser/singlePane/singlePaneSharedHelpers.ts:56), which flags `BrowserEditorInput`, `CustomEditorInput`, and PR/Issue webview inputs as 'self-contained' and hides the docked detail panel — consumed in singlePaneExistingSessionStrategy.ts:407 and singlePaneDraftSessionStrategy.ts:552. Do not disturb the existing D1-D11 side-pane remembering/restore semantics for Files/Changes/maximize transitions; the new behavior must compose with them (e.g. does leaving Browser restore the pre-browser state per D3, and does this count as a D2 user choice or a forced/ignored state like D5's maximize override).
- **Open decisions:**
  - Should the desktop layout auto-hide the side pane when Browser becomes active (matching single-pane), or should a manual show/hide toggle be added to the embedded browser's toolbar instead?
  - If auto-hidden, should this be treated as a forced/temporary state like D5 (never recorded, always restores the prior side-pane state) or can the user override it while Browser is active?

## Evidence

- **single-pane already handles this:** src/vs/sessions/contrib/layout/browser/singlePane/singlePaneSharedHelpers.ts exports `isEditorWithoutDockedDetails()`, which returns true for `BrowserEditorInput`; it is consumed by singlePaneExistingSessionStrategy.ts:407 and singlePaneDraftSessionStrategy.ts:552 to hide the docked detail panel when a Browser tab becomes active.
- **desktop layout controller lacks it:** src/vs/sessions/contrib/layout/browser/desktopSessionLayoutController.ts never imports `BrowserEditorInput` or `isEditorWithoutDockedDetails`, and its companion spec desktopSessionLayoutController.md (rules D1-D11) documents no rule for hiding the auxiliary bar when a self-contained editor like Browser is active.
- **test confirms scope:** src/vs/sessions/contrib/layout/test/browser/desktopSessionLayoutController.test.ts only exercises `BrowserEditorInput` hiding behavior inside tests created via `createSinglePaneController()` (all labeled '[single-pane]'), with no equivalent coverage for the plain `createController()` (regular desktop/wide layout) path.
