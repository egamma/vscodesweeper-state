# Issue #347588 — Agent plugins are installed into two different folders

[https://github.com/microsoft/vscode/issues/347588](https://github.com/microsoft/vscode/issues/347588)

## Summary

Keep open as a storage-consolidation request: the two directories serve different ownership and caching purposes, rather than proving broken plugin resolution. Existing migration and forwarding work addresses related duplication but does not establish a single installation location.

## Change summary

Provide one predictable location for installed agent plugins instead of separate runtime installations and agent-host copies.

## Best solution

Define the authoritative installation and inspection location for each plugin while preserving necessary remote synchronization and revision isolation. Evaluate consolidation alongside the existing SDK-installation migration and forwarding work without treating all cached copies as duplicate installations.

## Evidence

- **Distinct storage roles:** src/vs/platform/agentHost/node/agentPluginManager.ts documents and implements {userDataPath}/agentPlugins/{key}/{nonce} as a client-customization materialization cache. Separate revisions deliberately avoid overwriting locked files and preserve copies used by running sessions; host-local customization URIs can bypass copying.
- **Runtime installation inventory:** CopilotCliAgentPluginDiscovery in src/vs/workbench/contrib/chat/common/plugins/agentPluginServiceImpl.ts obtains installed plugins through listPluginInstallations and reads their returned resource paths. CopilotSessionLauncher passes explicit pluginDirectories to the SDK; this does not establish the report's claim that the agent must search both directory trees.
- **Existing capability check:** chat.pluginLocations in src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts configures directories to discover, not a unified installation destination. AgentPluginRepositoryService also maintains a separate profile agentPluginsHome; neither mechanism satisfies the requested consolidation.
- **Related migration is narrower:** https://github.com/microsoft/vscode/issues/343334 is open and requests migration of legacy VS Code-managed installations to SDK ownership, explicitly preserving compatibility for other consumers. It does not require eliminating agent-host revision caches, so it is related rather than a verified canonical for this broader request.
- **Existing implementation candidate:** https://github.com/microsoft/vscode/pull/343899 is open and proposes stopping redundant forwarding of SDK-managed plugins while retaining forwarding for other sources and environments. Current checkout resolveCustomizationRefs already contains a copilotCliInstallation forwarding exclusion, but the available shallow history does not identify a fixing commit or prove complete storage consolidation.
- **Concrete duplication tracked separately:** https://github.com/microsoft/vscode/issues/344392 is open and documents duplicate hook execution, duplicate MCP processes, and Windows uninstall locking across native and forwarded copies. Those concrete failures are narrower than this issue's request for one filesystem location.
- **Report scope:** The body and attached https://github.com/user-attachments/files/34682643/issue-data.md identify Windows and VS Code 1.145.3, but provide no specific failed plugin lookup, stale update, or uninstall reproduction. The actionable request is consolidation; the listed failure risks are not demonstrated defects.
