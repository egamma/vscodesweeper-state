# Issue #329777 — Debug: "Add to Chat" on a stack frame with column 0 (per-spec "unknown") corrupts Range and permanently poisons the chat session

[https://github.com/microsoft/vscode/issues/329777](https://github.com/microsoft/vscode/issues/329777)

## Summary

Traced the reported path on current main and it holds up: a stack frame with DAP `column: 0` (spec-legal 'unknown') is passed unguarded into `new Range(...)` in getCallStackImpl, and that invalid range later throws when converted back to a `vscode.Position` during chat history reconstruction, poisoning the whole session.

## Change summary

Adding a debug variable to chat while paused at a stack frame with column 0 corrupts the frame's Range and permanently breaks the chat session on every subsequent turn.

## Best solution

Guard the zero/unset line-column case where the raw DAP stack frame is converted into a Range in src/vs/workbench/contrib/debug/common/debugModel.ts (getCallStackImpl, around line 692) — the sibling getScopes() method a few lines above already applies exactly this kind of truthiness guard for scope ranges, so there's a direct in-file precedent to follow.

## Evidence

- **unguarded Range construction:** src/vs/workbench/contrib/debug/common/debugModel.ts:692 builds `new Range(rsf.line, rsf.column, rsf.endLine || rsf.line, rsf.endColumn || rsf.column)` directly from raw DAP values with no validation, even though the DAP spec defines column 0 as 'unknown, client should ignore'.
- **existing in-file precedent:** src/vs/workbench/contrib/debug/common/debugModel.ts:539 (getScopes) already guards with `rs.line && rs.column && rs.endLine && rs.endColumn ? new Range(...) : undefined` before constructing a Range from raw DAP scope data — the call-stack path lacks the equivalent guard.
- **downstream throw:** src/vs/workbench/api/common/extHostTypeConverters.ts Range.to() (line 139-145) computes `startColumn - 1`; a startColumn of 0 yields `character: -1`, which throws in the `vscode.Position`/`Range` constructor validation used by extHostChatAgents2.ts's history-reconstruction path (ChatPromptReference.toReferences, line ~3602), matching the reported exthost stack trace.
- **partial existing guard:** src/vs/workbench/contrib/debug/browser/debugChatIntegration.ts:279-284 createPausedLocationEntry() only guards against an *empty* range (`range.isEmpty()`), not a zero-column one, and this location entry is attached automatically on every debug variable 'Add to Chat' via createDebugAttachments() (line 295), so the bad range is injected silently on an unrelated user action.
