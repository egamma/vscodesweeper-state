# Issue #41692 — Feature Request: Contribute commands with additional arguments

[https://github.com/microsoft/vscode/issues/41692](https://github.com/microsoft/vscode/issues/41692)

## Summary

Keep open: current command and menu contributions still cannot declare differently titled command-palette entries that invoke one handler with different fixed arguments. This accepted Backlog request has 20 upvotes, and no verified canonical or landed implementation covers its central ask.

## Change summary

Allow extensions to contribute multiple named command-palette entries that reuse one command handler with declaratively supplied arguments.

## Best solution

Provide a supported contribution contract for named, parameterized invocations of an existing command. Resolve how entry identity, titles, and arguments relate to commands and menus before implementing it; keybinding arguments and separately registered wrapper commands do not deliver the requested declarative reuse.

## Plan brief

- **Likely files:** `src/vs/workbench/services/actions/common/menusExtensionPoint.ts`, `src/vs/platform/actions/common/actions.ts`, `src/vs/workbench/contrib/quickaccess/browser/commandsQuickAccess.ts`, `src/vs/platform/quickinput/browser/commandsQuickAccess.ts`
- **Validation:** Use an extension fixture with one registered handler and two declaratively contributed palette entries carrying different titles and URL slugs. Invoke each entry and verify the handler receives its corresponding slug without separate wrapper registrations; also verify ordinary argument-free commands and existing keybinding arguments retain their behavior.
- **Behavior:**

  > An extension should be able to publish several distinctly named command-palette entries that invoke the same registered handler with different fixed arguments declared in its manifest. Selecting an entry must pass that entry's arguments, so documentation shortcuts can share one handler without separately registered wrappers. Existing argument-free commands and keybinding argument behavior must remain unchanged. Acceptance should exercise two entries with different titles and slugs and verify both handler invocations.
- **Trace:**

  > In src/vs/workbench/services/actions/common/menusExtensionPoint.ts, IUserFriendlyCommand, IUserFriendlyMenuItem, and their registration handlers expose no per-entry invocation argument contract; menu entries also reuse the registered command's presentation. CommandsQuickAccessProvider.getGlobalCommandPicks in src/vs/workbench/contrib/quickaccess/browser/commandsQuickAccess.ts converts palette menu actions into picks without contributed arguments. MenuItemAction.run in src/vs/platform/actions/common/actions.ts supports internal option arguments, and the quick-input command runner supports argument-bearing picks, but those internal mechanisms are not exposed through these extension contributions. The supplied discussion on https://github.com/microsoft/vscode/issues/41692 suggests placing arguments on menu entries because commands can be shared across menus, while the reporter also requires distinct palette titles. The uncertainty starts at the public identity and presentation contract for those parameterized invocations. Keep interactive argument entry and argument-schema completion outside this request; they are distinct from the fixed manifest arguments sought here.
- **Open decisions:**
  - What public contribution contract should represent distinctly titled invocations of one handler: command aliases with their own identities, or separately identified menu/palette entries with per-entry titles and arguments?
  - Should contributed arguments apply only to the selected menu/palette entry, or also define defaults when its command identity is invoked programmatically or through a keybinding?
