# Issue #173134 — Support command variables in a terminal profile's env property

[https://github.com/microsoft/vscode/issues/173134](https://github.com/microsoft/vscode/issues/173134)

## Summary

Command variables remain unsupported in the current terminal-profile resolution paths. Keep this accepted Backlog request open: the discussion supports dynamically selecting the Python interpreter, but the title's env-only scope and the body's executable-path requirement need reconciliation.

## Change summary

Allow shared terminal profiles to obtain dynamic values from extension commands, including the currently selected Python interpreter.

## Best solution

Provide project-shareable interpreter-aware profiles without developer-specific absolute paths. Settle whether this requires core command-variable support or a Python-contributed profile that also accommodates project-specific arguments; the thread favors the latter, but it does not establish coverage of the env request.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/terminal/browser/terminalProfileResolverService.ts`, `src/vs/workbench/contrib/terminal/common/terminalEnvironment.ts`, `src/vs/platform/terminal/common/terminalPlatformConfiguration.ts`, `src/vs/workbench/services/configurationResolver/common/variableResolver.ts`
- **Validation:** After agreeing scope, use a shared workspace profile and a selected non-default Python interpreter to launch a project-specific interactive shell; change the selected interpreter without editing the profile and verify the next terminal uses the new interpreter. If env command variables are included, verify a command-returned string reaches the terminal environment while existing workspace/env substitutions and null-valued deletions remain unchanged.
- **Behavior:**

  > The reporter wants checked-in terminal profiles that launch project-specific Python shells using each developer's currently selected interpreter, without committing absolute local paths. Existing plain python profiles do not guarantee that interpreter, and command-variable paths are unsupported. The title additionally requests command variables in profile env values, which the body does not demonstrate. Acceptance must cover the agreed surface and interpreter changes between terminal launches while preserving ordinary profile behavior.
- **Trace:**

  > TerminalProfileResolverService._resolveProfile in src/vs/workbench/contrib/terminal/browser/terminalProfileResolverService.ts resolves path and args using resolveWithEnvironment. createTerminalEnvironment and createVariableResolver in src/vs/workbench/contrib/terminal/common/terminalEnvironment.ts use the same non-interactive resolver for env values. AbstractVariableResolverService in src/vs/workbench/services/configurationResolver/common/variableResolver.ts resolves command variables from a supplied mapping, but these terminal callers do not execute commands or supply that mapping. The public window.registerTerminalProfileProvider API supports dynamically contributed profiles, matching the maintainer proposal at https://github.com/microsoft/vscode/issues/173134#issuecomment-1446734299. What remains uncertain is whether that extension-owned solution can cover the reporter's shared project-specific arguments and the title's env requirement. Preserve existing non-command substitutions, environment deletion semantics, and unrelated settings resolution.
- **Open decisions:**
  - Is the accepted scope command substitution in env values only, or also path and args as required by the reporter's shared Python-shell example?
  - Should user-defined profiles directly support command variables, or should the supported workflow be a Python-contributed profile that accommodates project-specific shell arguments?
