[https://github.com/microsoft/vscode/issues/300743](https://github.com/microsoft/vscode/issues/300743)

## Summary

Keep open: current Sync still invokes Git pull without an explicit submodule-recursion policy, and repository refresh waits for the operation to finish. The reported 30-plus-submodule scenario supplies enough steps to retest, but source inspection cannot confirm the minutes-long delay or establish that recursive fetching causes it.

## Change summary

Syncing a root repository with more than 30 submodules takes minutes and prevents Source Control changes from refreshing during the operation.

## Evidence

- **Reported reproduction:** https://github.com/microsoft/vscode/issues/300743 reports VS Code 1.111.0 on Windows 10.0.26200: open a project with 30-plus submodules and sync the root repository; syncing takes minutes and Current Changes stops updating. There are no comments independently confirming the cause.
- **Current Sync path:** extensions/git/src/commands.ts:4303-4310 routes git.sync to repository.sync. extensions/git/src/repository.ts:2395-2455 wraps pull and optional push in Operation.Sync; it can additionally fetch all branches when git.fetchOnPull is enabled.
- **Recursion remains delegated to Git:** extensions/git/src/git.ts:2455-2490 constructs git pull arguments for tags, unshallow, autostash, rebase, remote and branch, but adds neither --recurse-submodules nor --no-recurse-submodules. This supports investigating Git's effective configuration, not concluding that every reported submodule is necessarily updated.
- **Refresh scheduling:** extensions/git/src/repository.ts:2709-2746 updates model state after a mutating operation completes or fails. Its onFileChange path around lines 3191-3195 skips status while an operation is running, and whenIdleAndFocused waits for operation completion. This explains how a long-running Sync can delay the displayed changes, without proving the source of the delay.
- **Existing settings:** extensions/git/package.json registers git.fetchOnPull with default false. extensions/git/package.nls.json describes git.detectSubmodules as discovery and git.ignoreSubmodules as ignoring modifications in the file tree; neither provides an explicit pull-recursion control. No recurse-submodules setting or argument was found in the inspected Git extension registrations and source.
- **Canonical search:** Searches for submodules with sync, slow, pull and recurse-submodules found https://github.com/microsoft/vscode/issues/134921, which is open and broadly investigates delayed Git state updates. Its https://github.com/microsoft/vscode/issues/134921#issuecomment-943868732 mentions many submodules fetching in a loop, but does not establish the same root-pull recursion defect. It is related evidence, not a verified duplicate canonical for this report.
