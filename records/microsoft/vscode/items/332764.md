# Issue #332764 — VSCode server LEAKs server-main.js process.

[https://github.com/microsoft/vscode/issues/332764](https://github.com/microsoft/vscode/issues/332764)

## Summary

Keep open: Windows verification confirmed that the merged fix still leaves the original Node server running, and a subsequent Linux report identifies another surviving-process scenario. Current main retains the reported shutdown limitations; the pre-reopen fix does not establish completion.

## Change summary

Ensure code serve-web idle shutdown terminates its server and descendants rather than leaving orphaned server-main.js processes.

## Best solution

Make serve-web lifecycle cleanup reliably terminate its owned server processes on Windows and Linux, including when the launcher exits first. Diagnose the Windows termination failure and Linux reparenting sequence separately before choosing a lifecycle mechanism.

## Plan brief

- **Likely files:** `cli/src/commands/serve_web.rs`, `cli/src/util/command.rs`
- **Validation:** Repeat the documented Windows installed-CLI one-hour idle-timeout reproduction and the Linux Docker/Tini connect-disconnect-reconnect scenario, recording process identities and confirming all original server descendants exit while unrelated processes remain alive. Add runnable regression coverage for early launcher exit and failed graceful tree termination; retain the existing kill_tree_terminates_full_descendant_tree check.
- **Behavior:**

  > After all serve-web clients disconnect and the idle timeout expires, the original server and its owned descendants must terminate. Reconnecting must not accumulate old server-main.js or terminal-host processes. This must hold on Windows and Linux, including when the launcher exits before cleanup. Active clients and unrelated processes must remain unaffected.
- **Trace:**

  > ServerInstance::start_version in cli/src/commands/serve_web.rs launches the server entrypoint through new_script_command and monitors output, connection counts, an idle timer, and child.wait(). The timer invokes kill_tree but discards its result, then falls back to killing only the direct child; the child-exit branch breaks without descendant cleanup. In cli/src/util/command.rs, Windows kill_tree uses non-forced taskkill, while Unix cleanup walks current parent-child relationships and cannot recover already-reparented descendants. The Windows failure is confirmed at https://github.com/microsoft/vscode/issues/332764#issuecomment-5877049020; the exact taskkill failure remains unknown. The Linux early-launcher-exit explanation at https://github.com/microsoft/vscode/issues/332764#issuecomment-5887983884 needs a controlled trace, particularly because child.wait() can end monitoring before the idle timer. Preserve connection-based timeout behavior and isolate cleanup to processes owned by this server instance; shared kill_tree consumers must not regress.
