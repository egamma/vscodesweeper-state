# Issue #105625 — API for horizontal scroll position in TextEditor

[https://github.com/microsoft/vscode/issues/105625](https://github.com/microsoft/vscode/issues/105625)

## Summary

The horizontal scrolling API gap remains in current source, and this accepted Backlog request has 30 community upvotes. Keep it open for API design; the related notebook proposal covers a different surface, and no verified canonical was found.

## Change summary

Expose horizontal scroll position, programmatic positioning, and change notifications on TextEditor so extensions can synchronize multiple editors without relying on text ranges.

## Best solution

Provide an extension-facing horizontal scroll contract that supports observing and synchronizing individual text editors independently of document ranges. API owners should settle coordinate units, viewport information, and feedback-loop semantics before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/browser/mainThreadEditor.ts`, `src/vs/workbench/api/browser/mainThreadEditors.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/common/extHostTextEditor.ts`, `src/vs/workbench/api/common/extHostTextEditors.ts`, `extensions/vscode-api-tests/src/singlefolder-tests/editor.test.ts`
- **Validation:** After agreeing the API contract, add and run extension-host editor integration tests in extensions/vscode-api-tests/src/singlefolder-tests/editor.test.ts: open two editors with long unwrapped lines, observe horizontal movement, position either editor without changing its vertical viewport or selections, and verify bidirectional synchronization converges without repeated feedback. Include clamping and differing viewport/font-width cases; preserve existing visibleRanges and revealRange behavior.
- **Behavior:**

  > Extensions need to observe and set each TextEditor's horizontal viewport independently of document Range coordinates, enabling synchronized comparison editors. Horizontal movement must be observable even when the vertically visible lines do not change. Synchronization must converge without event feedback loops, and horizontal positioning must preserve vertical position and selections. Acceptance should cover two independently scrollable editors, differing viewport widths, and positions constrained by each editor's scrollable extent.
- **Trace:**

  > The public TextEditor declaration in src/vscode-dts/vscode.d.ts explicitly limits visibleRanges to vertical visibility. MainThreadTextEditorProperties in src/vs/workbench/api/browser/mainThreadEditor.ts recomputes properties on onDidScrollChange, but its delta and IEditorPropertiesChangeData in src/vs/workbench/api/common/extHost.protocol.ts contain only selections, options, and visible ranges. ExtHostTextEditor in src/vs/workbench/api/common/extHostTextEditor.ts exposes range-based revealRange without independent horizontal state. CodeEditorWidget already has internal getScrollLeft and setScrollLeft methods, while editorScroll in src/vs/editor/browser/coreCommands.ts provides relative column-based movement rather than the requested observation contract. Preserve existing range APIs, vertical scrolling, selections, and command behavior; no dedicated comparison UI is requested. https://github.com/microsoft/vscode/issues/311289 is a related notebook API discussion, explicitly not a duplicate. The unresolved boundary is the public contract for coordinates, viewport information, and distinguishing synchronized writes from user-originated movement.
- **Open decisions:**
  - What coordinate contract should extensions receive: CSS-pixel offsets and viewport width, character-based positions, or another representation, particularly when synchronized editors have different fonts or zoom levels?
  - Should horizontal change notifications carry an explicit caller-provided cause token, as requested, or use another documented contract for preventing synchronization feedback loops?

## Evidence

- **Existing API does not cover horizontal state:** src/vscode-dts/vscode.d.ts:1258–1394 defines TextEditor without horizontal position getters or setters. Its visibleRanges documentation explicitly says it accounts only for vertical scrolling, and revealRange accepts a document Range rather than an independent horizontal offset.
- **Scroll events lose horizontal information at the API boundary:** src/vs/workbench/api/browser/mainThreadEditor.ts:94–130 reads getVisibleRanges and generates deltas for selections, options, and visible ranges only. The onDidScrollChange listener at lines 320–326 recomputes those properties without forwarding horizontal position; src/vs/workbench/api/common/extHost.protocol.ts:2428–2458 likewise has no horizontal scroll property.
- **Existing command is only partial coverage:** src/vs/editor/browser/coreCommands.ts:1309–1438 registers editorScroll and supports left/right movement in column units, calculated relative to the existing position. It does not expose an editor-specific position getter or change event, so it cannot deliver the requested synchronization contract.
- **Underlying editor capability exists:** src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts:977–1015 implements getScrollLeft and setScrollLeft internally. These methods are not exposed by the extension-host TextEditor object in src/vs/workbench/api/common/extHostTextEditor.ts.
