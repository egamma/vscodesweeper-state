# Issue #226883 — Order of Compare Selected files by mouse

[https://github.com/microsoft/vscode/issues/226883](https://github.com/microsoft/vscode/issues/226883)

## Summary

The inconsistency remains on current main: Explorer preserves its selection ordering, while Open Editors and tabs explicitly move the context-menu target to the front and therefore place it on the left. This issue is the canonical report for that behavior and should remain open.

## Change summary

Make Compare Selected determine the original and modified sides consistently across Explorer folders, Open Editors, and editor tabs.

## Best solution

Use the same first-selected-to-original/left ordering for Compare Selected across all three surfaces, independent of which selected item opens the context menu, without changing context-target semantics for unrelated multi-resource commands.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/files.ts`, `src/vs/workbench/contrib/files/browser/fileCommands.ts`, `src/vs/workbench/contrib/files/test/browser/openEditorsView.test.ts`, `src/vs/workbench/test/browser/parts/editor/editorGroupModel.test.ts`
- **Validation:** Add targeted browser unit coverage for Compare Selected from Explorer, Open Editors, and tabs, selecting A then B and invoking the context menu from either item; run `scripts/test.sh --grep "Compare Selected"` and verify A is always original/left.
- **Behavior:**

  > Selecting file A and then file B and invoking Compare Selected must open A as the original/left side and B as the modified/right side in Explorer folders, Open Editors, and editor tabs. Invoking the command from either selected item's context menu must not reverse the pair. Existing Select for Compare/Compare with Selected behavior and unrelated multi-resource commands must remain unchanged.
- **Trace:**

  > The `compareSelected` handler in src/vs/workbench/contrib/files/browser/fileCommands.ts assigns the first resource returned by `getMultiSelectedResources` to `original`. In src/vs/workbench/contrib/files/browser/files.ts, Explorer returns its selection order unchanged, whereas Open Editors and tabs move the command argument to index 0. Tab selection adds another constraint: `EditorGroupModel.selectedEditors` in src/vs/workbench/common/editor/editorGroupModel.ts deliberately returns tab-sequential order, not selection chronology. The plan should trace the selection state available in each surface and identify a Compare Selected-specific ordering contract; do not change context-primary ordering for copy, open-to-side, remove-root, or other consumers of the shared helper. The newer https://github.com/microsoft/vscode/issues/234082 confirms the desired first-selected-left behavior and was closed as a duplicate of this canonical issue.

## Evidence

- **current source:** src/vs/workbench/contrib/files/browser/fileCommands.ts passes resources[0] as `original` and resources[1] as `modified` for `compareSelected`.
- **inconsistent resource ordering:** src/vs/workbench/contrib/files/browser/files.ts returns Explorer context order unchanged, but its Open Editors and tab branches explicitly splice the command target to index 0; right-clicking the other selected item therefore changes the left side.
- **tab selection limitation:** src/vs/workbench/common/editor/editorGroupModel.ts exposes `selectedEditors` in sequential tab order rather than selection chronology, so cross-surface first-selected semantics need a deliberate trace rather than a blind removal of the context-target reordering.
- **canonical ownership:** The newer https://github.com/microsoft/vscode/issues/234082 requested that the first selected tab appear on the left and was closed explicitly as a duplicate of this issue; https://github.com/microsoft/vscode/issues/237735 was likewise closed as its duplicate.
- **earlier partial fix:** Commit 09cc4e79f3ad5b84f13d25b648ade7956179c292 fixed https://github.com/microsoft/vscode/issues/225441 by mapping resources[0] to the original side, but it did not change the surface-specific ordering produced by `getMultiSelectedResources`.
