# Issue #226883 — Order of Compare Selected files by mouse

[https://github.com/microsoft/vscode/issues/226883](https://github.com/microsoft/vscode/issues/226883)

## Summary

Keep open: current main still assigns the diff sides differently for Explorer files, Open Editors, and editor tabs. This Backlog polish item is also the established canonical for two later reports.

## Change summary

Make Compare Selected use a predictable, consistent original/modified file order across the Explorer, Open Editors, and editor tabs.

## Best solution

Use the first-selected file as the original on the left and the second-selected file as the modified file on the right across all three surfaces, independent of which selected item opens the context menu.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/files.ts`, `src/vs/workbench/contrib/files/browser/fileCommands.ts`, `src/vs/workbench/common/editor/editorGroupModel.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`, `src/vs/workbench/contrib/files/test/browser/openEditorsView.test.ts`
- **Validation:** Add targeted coverage for Compare Selected from Explorer, Open Editors, and tabs: select A and then B, invoke the command from either selected item, and assert that the opened diff always has A as `original` and B as `modified`; repeat with reversed selection order.
- **Behavior:**

  > Selecting file A and then file B and invoking Compare Selected opens A as the original on the left and B as the modified file on the right. The result must be identical from the Explorer, Open Editors, and editor tabs and must not depend on which selected item receives the context-menu invocation. Reversing the selection order reverses the diff sides.
- **Trace:**

  > The command in src/vs/workbench/contrib/files/browser/fileCommands.ts maps the two URIs returned by getMultiSelectedResources directly to `original` and `modified`. In src/vs/workbench/contrib/files/browser/files.ts, the Explorer path preserves its context order, while the Open Editors and tab paths move the context-menu resource to index zero. The tab path additionally consumes EditorGroupModel.selectedEditors, which src/vs/workbench/common/editor/editorGroupModel.ts deliberately returns in sequential tab order rather than selection chronology. The session must establish how to preserve Compare Selected chronology without changing ordering semantics for unrelated multi-selection consumers. https://github.com/microsoft/vscode/issues/234082 confirms that first-selected-on-the-left is the intended observable outcome and was consolidated into this issue.

## Evidence

- **current source:** src/vs/workbench/contrib/files/browser/files.ts:getMultiSelectedResources returns Explorer context order unchanged, but explicitly moves the context-menu resource to the front for Open Editors and tabs; src/vs/workbench/contrib/files/browser/fileCommands.ts then uses resources[0] as `original` and resources[1] as `modified`.
- **tab ordering:** src/vs/workbench/common/editor/editorGroupModel.ts:selectedEditors returns selected editors in tab sequence rather than selection chronology, while getMultiSelectedResources subsequently moves the invoked tab to the front. The reported cross-surface inconsistency therefore remains in current main.
- **canonical status:** https://github.com/microsoft/vscode/issues/234082 requested that the first-selected tab appear on the left and was closed by a maintainer as a duplicate of this issue.
- **additional duplicate:** https://github.com/microsoft/vscode/issues/237735 independently reported the same Open Editors/tab ordering symptom and was closed with `*duplicate` after linking this issue.
- **selection-order precedent:** https://github.com/microsoft/vscode/issues/225441 records the earlier decision to restore first-selected-file-on-the-left behavior for the Explorer, leaving this issue's Open Editors and tab consistency work outstanding.
