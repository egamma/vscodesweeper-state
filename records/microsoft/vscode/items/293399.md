# Issue #293399 — "Cannot launch a terminal process in an empty workspace" restriction is problematic

[https://github.com/microsoft/vscode/issues/293399](https://github.com/microsoft/vscode/issues/293399)

## Summary

Keep open: current main still deliberately blocks non-home working directories in empty windows, preventing legitimate extension-driven project creation and Docker tasks. A maintainer acknowledged the limitation; changing this workspace-trust safeguard needs human review rather than a cleanup close.

## Change summary

Allow legitimate extension-created terminal processes to use a non-home working directory without first opening a workspace.

## Best solution

Support extension-driven project creation and tasks in empty windows without requiring the working directory to equal userHome, while preserving appropriate execution and workspace-trust protections. Terminal and workspace-trust maintainers should settle the intended permission boundary before changing the guard.

## Evidence

- **Current restriction:** src/vs/workbench/contrib/terminal/browser/terminalInstance.ts:1618–1643, TerminalInstance._createProcess, checks workspace trust and then independently rejects an empty workspace when normalized cwd differs from normalized userHome. It emits the reporter's exact error and returns before _processManager.createProcess. The Docker task's explicitly selected project directory meets this rejection condition.
- **Intentional existing behavior:** src/vs/workbench/contrib/terminal/test/browser/terminalInstance.test.ts:349–366 explicitly tests 'should not create a process with an unexpected cwd in an empty workspace'. This supports classifying the requested relaxation as a feature request rather than an accidental deviation from the existing contract. No tests were executed.
- **Existing settings do not cover the request:** src/vs/workbench/contrib/terminal/common/terminalConfiguration.ts registers terminal.integrated.cwd and terminal.integrated.allowInUntrustedWorkspace. The latter makes TerminalInstance._trust return true, but does not bypass the separate empty-workspace cwd guard. Changing the cwd to userHome would not preserve the extension task's required project directory.
- **Maintainer acceptance and independent reports:** https://github.com/microsoft/vscode/issues/293399#issuecomment-3861247642 acknowledges the point and suggests removing the restriction. https://github.com/microsoft/vscode/issues/293399#issuecomment-4043571412 reports project-creation extensions being affected, and https://github.com/microsoft/vscode/issues/293399#issuecomment-5795572141 reports Maven project creation failing.
- **Canonical search:** Searched open and closed reports for empty-workspace terminal failures and userHome. The older open https://github.com/microsoft/vscode/issues/279671 references https://github.com/microsoft/vscode/pull/279249#issuecomment-3578361942, whose reported local-empty-window symptom is a trust modal requiring 'trust folder & continue', not rejection of an extension-specified non-home cwd. It does not establish the same observable symptom required for a duplicate close of this re-reviewed item. Relaxing a trust-related execution guard therefore requires human consideration; extension ownership alone does not establish that every supplied directory is safe.
