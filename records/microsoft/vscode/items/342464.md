# Issue #342464 — Git: repository stays in Source Control when its workspace folder is removed while openRepository is in flight

[https://github.com/microsoft/vscode/issues/342464](https://github.com/microsoft/vscode/issues/342464)

## Summary

The reported race remains present in current main: workspace removal only disposes registered repositories, while an in-flight open can register the removed repository afterward. Keep this open and route it to Git; the report supplies sufficient reproduction details.

## Change summary

Prevent an asynchronous workspace-triggered repository open from leaving an orphan in Source Control and api.repositories after its workspace folder is removed.

## Best solution

Make repository registration respect intervening workspace-folder removal while preserving legitimate explicit, editor-driven, parent-repository, and worktree opens. Cover the removal-during-open ordering with a deterministic Git-extension regression test.

## Evidence

- **Current source confirms the race:** At checkout d1eaacc5a33577b2d5b533f5770962ad592ea705, extensions/git/src/model.ts:470-489 handles removed folders by consulting getOpenRepository and disposing only existing registrations. An opening repository is absent from that collection, so the removal event cannot dispose it.
- **Unchecked continuation after asynchronous work:** Model.openRepository in extensions/git/src/model.ts:600-705 checks workspace eligibility before awaiting getRepositoryDotGit, getRepositoryRootRealPath, and requestResourceTrust. If the folder is removed during those awaits, the continuation still constructs the Repository and calls this.open(repository), without checking whether its workspace-triggered opening is still valid.
- **Registration and serialization do not prevent the defect:** Model.open in extensions/git/src/model.ts:761-886 pushes the repository into openRepositories and fires onDidOpenRepository without workspace-membership validation. The sequentialize decorator in extensions/git/src/decorators.ts serializes openRepository calls only; it does not serialize workspace-folder removals with an outstanding open.
- **Concrete reporter evidence:** https://github.com/microsoft/vscode/issues/342464 provides a minimal workspace-swapping extension and reports repository registration 9-28 ms after removal, followed by persistence for 60 seconds. The current source permits exactly that ordering; no runtime reproduction was attempted in this read-only review.
- **Existing supported exceptions:** Model.isRepositoryOutsideWorkspace in extensions/git/src/model.ts:1114-1150 explicitly permits empty workspaces, agent-session workspaces, and known worktrees, and resolves workspace symlinks. openRepository also supports parent-repository settings and explicit-opening flags. A blanket requirement that every repository remain inside a workspace folder would change supported behavior beyond this report.

Its open implementation candidate, https://github.com/microsoft/vscode/pull/313554, addresses that persisted-state cleanup and does not establish a duplicate or fix for this race.
