# Issue #196009 — DebugAdapterTracker not working in web extensions

[https://github.com/microsoft/vscode/issues/196009](https://github.com/microsoft/vscode/issues/196009)

## Summary

The cross-extension-host limitation remains on current main: tracker factories are stored and invoked only in the extension host that owns the debug adapter. This issue should remain open as the canonical report for making DebugAdapterTracker registration work across extension hosts.

## Change summary

Allow a web extension's DebugAdapterTracker factory to observe matching debug sessions whose adapters run in another extension host.

## Best solution

Make the documented DebugAdapterTracker registration semantics independent of extension-host placement, with cross-host coverage proving that a tracker in the web/UI host receives lifecycle and DAP message callbacks for an adapter in another host.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostDebugService.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadDebugService.ts`, `extensions/vscode-api-tests/src/singlefolder-tests/debug.test.ts`
- **Validation:** Add an extension-host integration test that registers a '*' DebugAdapterTrackerFactory in the web/UI extension host, starts a debug adapter in a different extension host, and asserts that createDebugAdapterTracker plus lifecycle and DAP message callbacks are received.
- **Behavior:**

  > A DebugAdapterTrackerFactory registered by a web extension must observe matching debug sessions even when the debug adapter runs in another extension host. The factory must be created once for the matching session and receive the same lifecycle and DAP message callbacks available when tracker and adapter are colocated. Existing same-host tracking and debug-adapter behavior must remain unchanged.
- **Trace:**

  > ExtHostDebugServiceBase.registerDebugAdapterTrackerFactory in src/vs/workbench/api/common/extHostDebugService.ts records the factory only in the local _trackerFactories array. The same class invokes getDebugAdapterTrackers from $startDASession after locally creating the adapter, so an extension host without the adapter never consults its registered factories. src/vs/workbench/api/common/extHost.protocol.ts has no RPC for publishing tracker registrations or forwarding tracker callbacks, and MainThreadDebugService in src/vs/workbench/api/browser/mainThreadDebugService.ts only brokers the adapter owned by the selected extension host. The existing API test in extensions/vscode-api-tests/src/singlefolder-tests/debug.test.ts covers only a colocated tracker. Preserve same-host callback ordering, the one-second tracker creation timeout, and debug-adapter transport semantics; the later corroborating report is https://github.com/microsoft/vscode/issues/233184.

## Evidence

- **current source:** In src/vs/workbench/api/common/extHostDebugService.ts, registerDebugAdapterTrackerFactory stores factories only in that ExtHostDebugServiceBase instance, while getDebugAdapterTrackers is called from $startDASession only after that same extension host creates the adapter. There is no tracker registration RPC in MainThreadDebugServiceShape or ExtHostDebugServiceShape.
- **public API contract:** src/vscode-dts/vscode.d.ts documents registerDebugAdapterTrackerFactory for a debug type or '*' without documenting an extension-host locality restriction.
- **maintainer diagnosis:** The issue comment confirms that trackers are currently local to the extension host where the debug adapter lives.
- **canonical relationship:** The later report https://github.com/microsoft/vscode/issues/233184 was closed in favor of this issue; a maintainer confirmed that cross-host tracking needs substantial changes to debug-adapter handling. Because that report is newer, it cannot replace this re-reviewed issue as canonical.
- **test gap:** extensions/vscode-api-tests/src/singlefolder-tests/debug.test.ts exercises registerDebugAdapterTrackerFactory only with the tracker and adapter in the same extension-host scenario, so it does not cover the reported boundary.
