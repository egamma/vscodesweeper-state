## Evidence

- **Current source explains the reported trigger:** src/vs/workbench/contrib/webview/browser/resourceLoading.ts: checkResolvedContainment resolves the requested resource and rejects it unless its target lies inside an original or resolved allowed root. An npm-linked package outside the extension/workspace roots therefore reaches the exact denial message quoted in https://github.com/microsoft/vscode/issues/348022.
- **Intentional containment policy:** src/vs/workbench/contrib/webview/test/browser/resourceLoading.test.ts explicitly tests 'Denies links that resolve outside of all roots and allows links that stay inside'. Another test permits links whose targets fall inside another explicitly allowed root. This is intended behavior, not a demonstrated deviation from the current implementation contract.
- **Existing capability and remaining gap:** WebviewOptions.localResourceRoots in src/vscode-dts/vscode.d.ts allows explicit resource directories; src/vs/workbench/api/common/extHostWebview.ts defaults these to workspace folders and the extension location. Explicitly including the linked target can satisfy containment, but this does not provide the requested bypass or improve the denial diagnostic. The current diagnostic logs requestUri and resourceToLoad, not resolvedResource.
- **Independent confirmation and workaround:** https://github.com/microsoft/vscode/issues/348022#issuecomment-7221924279 confirms the same external-symlink 401 on a Linux Remote SSH filesystem from Windows, and reports success when opening the real dataset folder or adding it as a workspace folder.
