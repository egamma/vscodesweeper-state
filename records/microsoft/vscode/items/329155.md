# Issue #329155 — Agents window: group delegated sessions across connected AHP hosts

[https://github.com/microsoft/vscode/issues/329155](https://github.com/microsoft/vscode/issues/329155)

## Summary

Keep open: current main records cross-host creation provenance and supports related-session placement, but does not render separate downstream sessions beneath their originating workflow. The implementation-neutral relationship contract and its interaction with existing list placement need design work.

## Change summary

Group separately hosted delegated sessions in the Agents window while preserving native navigation, authoritative downstream state, and relationships across disconnections.

## Best solution

Support a provider-neutral delegation relationship that external orchestrators can publish and the Agents window can project into navigable workflow groups. Preserve each downstream session's existing provider ownership and direct observation rather than copying its transcript into the parent.

- **Behavior:**

  > An orchestration session and separately hosted downstream sessions can appear as one navigable workflow in the Agents window. An external orchestrator can publish the relationship without using VS Code's built-in delegation tools. Selecting a downstream node opens the native session from its owning host, with that host remaining authoritative for transcript, tools, approvals, and changes. Host disconnection preserves the relationship and exposes disconnected state; reconnection resumes direct observation. Acceptance must cover the agreed interaction with pinning, custom groups, filtering, and archiving.
- **Trace:**

  > ISession.createdBySession in src/vs/sessions/services/sessions/common/session.ts already exposes creation provenance. RemoteSessionService in src/vs/sessions/contrib/remoteSessions/browser/remoteSessionService.ts attaches remote-origin metadata, and AgentHostSession in baseAgentHostSessionsProvider.ts projects it into provider-neutral provenance. SessionsListModelService uses this for adjacent ordering and SessionGroupsService for inherited custom-group membership. SessionsList in src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts nests only chats belonging to the same session, so those mechanisms do not provide cross-host workflow hierarchy. The uncertainty begins at the externally publishable relationship contract and its placement semantics; preserve provider ownership, direct downstream observation, and existing lifecycle behavior. https://github.com/microsoft/vscode/pull/336690 provides related built-in delegation infrastructure, while https://github.com/microsoft/vscode/issues/277568 addresses a distinct inline-transcript surface. Inspection was read-only; no runtime validation was performed.
- **Open decisions:**
  - What externally publishable relationship contract should clients support: creation provenance only, or explicit task/tool-call delegation edges that can also relate existing sessions?
  - When delegation nesting conflicts with pinning, custom groups, filtering, or archiving, where should the downstream session appear and should an additional navigation reference remain under the parent?
