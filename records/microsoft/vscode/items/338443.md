# Issue #338443 — Sync Changes button fails silently

[https://github.com/microsoft/vscode/issues/338443](https://github.com/microsoft/vscode/issues/338443)

## Summary

Traced the reported silent failure to source: the Sync Changes toolbar button uses a plain ActionViewItem whose actionRunner swallows the command's rejection instead of surfacing it, unlike the sibling MenuEntryActionViewItem pattern used elsewhere in the same feature area that explicitly shows a notification on error.

## Change summary

Clicking 'Sync Changes' with a failing pull/push (e.g. rebase blocked by unstaged changes) shows no error to the user; the command just appears to do nothing.

## Best solution

Make SessionSyncChangesActionViewItem surface operation failures to the user (e.g. notify on the actionRunner's onDidRun error, matching MenuEntryActionViewItem.onClick), so a failed sync gives visible feedback instead of silently no-opping.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/changes/browser/sessionSyncChanges.ts`
- **Validation:** Extend src/vs/sessions/contrib/changes/test/browser/sessionSyncChanges.test.ts to assert that when invokeOperation rejects, the user is notified (e.g. a notificationService.error call or an equivalent visible error state), and that this does not regress the existing 'propagates operation failures' contract.
- **Behavior:**

  > When the Sync Changes button's operation fails (e.g. pull rejected due to unstaged changes, or any other sync error), the user must see a clear, visible error indication — a notification or an equivalent inline signal — instead of the button silently doing nothing. Successful syncs and the existing command-level error propagation (used by other callers/tests) must be unaffected.
- **Trace:**

  > The command intentionally rethrows failures (src/vs/sessions/contrib/changes/browser/sessionSyncChanges.ts SessionSyncChangesAction.run, confirmed by the existing test 'allows retries and propagates operation failures'). The gap is purely on the click path: SessionSyncChangesActionViewItem extends the base ActionViewItem (src/vs/base/browser/ui/actionbar/actionViewItems.ts), whose onClick fires actionRunner.run without awaiting or handling the result; ActionRunner.run (src/vs/base/common/actions.ts) itself catches the error and only exposes it via the onDidRun event, which nothing here subscribes to. Compare src/vs/platform/actions/browser/menuEntryActionViewItem.ts's onClick, which listens to onDidRun and calls notificationService.error. Do not change the command's own throw-on-failure contract (relied on by src/vs/sessions/contrib/changes/test/browser/sessionSyncChanges.test.ts) or the server-side agentHostSyncOperationHandler.ts error wrapping — only the missing UI-level error surfacing needs to change.
- **Open decisions:**
  - Should a failed sync show a notification toast, an inline error state on the toolbar button/icon, or both?
  - Should the fix be local to SessionSyncChangesActionViewItem, or should error surfacing become a shared behavior for all actionViewItemService-registered buttons (to avoid the same gap recurring elsewhere)?

## Evidence

- **server throws on failure:** src/vs/platform/agentHost/node/agentHostSyncOperationHandler.ts wraps pull/push failures in a ProtocolError('Failed to sync changes: ...') that propagates to the caller.
- **command rethrows by design:** SessionSyncChangesAction.run in src/vs/sessions/contrib/changes/browser/sessionSyncChanges.ts awaits sync.changeset.invokeOperation without catching; src/vs/sessions/contrib/changes/test/browser/sessionSyncChanges.test.ts has a test 'allows retries and propagates operation failures' asserting the command intentionally rejects on operation failure.
- **error swallowed at the view item:** SessionSyncChangesActionViewItem extends base ActionViewItem (src/vs/base/browser/ui/actionbar/actionViewItems.ts onClick just calls `this.actionRunner.run(...)` without awaiting/catching), and ActionRunner.run (src/vs/base/common/actions.ts) catches the thrown error internally and only fires it on the `onDidRun` event — nothing in sessionSyncChanges.ts listens for that event to show a notification.
- **contrast with menu-driven actions:** MenuEntryActionViewItem.onClick (src/vs/platform/actions/browser/menuEntryActionViewItem.ts:209-232) explicitly listens to actionRunner.onDidRun and calls `this._notificationService.error(err)` on failure — the pattern the Sync Changes button lacks.
