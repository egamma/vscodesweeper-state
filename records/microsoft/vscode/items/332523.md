# Issue #332523 — File names get cut off at the left edge when horizontal scroll is enabled

[https://github.com/microsoft/vscode/issues/332523](https://github.com/microsoft/vscode/issues/332523)

## Summary

The screenshot and current source show a real Explorer readability gap: at maximum horizontal scroll, the shared list widget reserves exactly the scrollbar width, leaving no breathing room between the final glyph and the vertical scrollbar. This should stay open and be routed to the Explorer/list-widget owners.

## Change summary

Leave visible trailing space after long Explorer labels when the tree is horizontally scrolled to its maximum extent.

## Best solution

Define consistent trailing breathing room for horizontally scrolling lists and trees in the shared list widget, rather than restoring Explorer-specific padding. Preserve existing tree indentation and scrollbar behavior.

- **Behavior:**

  > When the Explorer has horizontal scrolling enabled and is scrolled fully toward the end of a deeply indented or long filename, the complete label remains readable with visible breathing room before the vertical scrollbar or pane edge. Existing indentation, row selection, and scrollbar interaction remain unchanged. The behavior should also remain consistent across whichever shared list/tree surfaces the maintainer includes in scope.
- **Trace:**

  > Horizontal list sizing is implemented by ListView.updateScrollWidth and ListView.updateWidth in src/vs/base/browser/ui/list/listView.ts. They extend the measured widest row by 10 pixels, exactly matching DEFAULT_SCROLLBAR_SIZE in src/vs/base/browser/ui/scrollbar/scrollableElement.ts, so the reserve is consumed by the vertical scrollbar and supplies no additional visual gap. Explorer-specific row padding was removed by commit cf8033b511f5188639781b2f1021cc6263b1b332; the discussion in https://github.com/microsoft/vscode/issues/276382 states that spacing intended across widgets should be a central rule. Do not reintroduce arbitrary Explorer indentation or alter tree depth alignment; the uncertainty starts at whether trailing breathing room is a shared list-widget contract or an Explorer-only presentation requirement.
- **Open decisions:**
  - Should trailing breathing room at maximum horizontal scroll become the shared behavior for every horizontally scrolling list/tree, or be limited to the Explorer and other explicitly selected tree surfaces?

This accounts for the scrollbar itself but leaves no additional visual separation at maximum scroll.
