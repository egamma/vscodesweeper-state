# Issue #232790 — Toggling views/panels has inconsistent focus behaviour

[https://github.com/microsoft/vscode/issues/232790](https://github.com/microsoft/vscode/issues/232790)

## Summary

The focus inconsistency remains visible in current source, but the correct user-facing policy is unresolved. A previous fix was reverted after breaking established terminal, keyboard-only, and screen-reader workflows, so this needs a maintainer-led focus-behavior decision before another implementation.

## Change summary

Make focus behavior predictable when visibility commands reveal the primary side bar, secondary side bar, or panel.

## Best solution

Define and test an explicit focus policy for visibility toggles versus dedicated focus commands, including whether invocation from a keyboard shortcut and a layout control should differ. Then make all three workbench regions follow that policy without regressing terminal or screen-reader workflows.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/layout.ts`, `src/vs/workbench/browser/actions/layoutActions.ts`, `src/vs/workbench/browser/parts/panel/panelActions.ts`, `src/vs/workbench/browser/parts/auxiliarybar/auxiliaryBarActions.ts`
- **Validation:** Exercise Ctrl/Cmd+B, Ctrl/Cmd+J, the secondary-side-bar toggle, the corresponding layout controls, and explicit focus commands with Explorer, SCM, Terminal, and Debug Console active; verify the approved focus matrix with both keyboard-only navigation and a screen reader.
- **Behavior:**

  > Revealing the primary side bar, secondary side bar, or panel must follow a documented and predictable focus policy rather than depending on the active view's implementation timing. Dedicated focus commands must continue to reveal and focus their target. The accepted behavior must preserve keyboard-only and screen-reader usability and avoid regressing terminal workflows that depend on panel focus.
- **Trace:**

  > Current src/vs/workbench/browser/layout.ts reveals each region before opening its pane composite, but setSideBarHidden omits the focus argument while setPanelHidden and the auxiliary-bar path pass !skipLayout. ToggleSidebarVisibilityAction and TogglePanelAction route directly through setPartHidden, so the public commands inherit these different semantics. Commit d5746c5593f6afe15e44a9f7877a064df6605d11 attempted consistency by removing focus, and commit d47f63e5dcde69292e29018bd6fbb4bc93ccaaf1 reverted that behavior after terminal regressions. Keep explicit view-focus commands and hiding behavior out of scope; the unresolved boundary is the focus policy when a visibility command reveals a region.
- **Open decisions:**
  - When invoked by a keyboard shortcut, should a visibility toggle preserve the current focus or move focus into the newly revealed region?
  - Should activation from a pointer-based layout control follow the same focus policy as keyboard invocation, or focus the region the user clicked to reveal?
  - Must the panel retain its historical focus-on-reveal behavior for terminal workflows while side bars preserve focus, or should one uniform policy cover all three regions?

## Evidence

- **current source:** In src/vs/workbench/browser/layout.ts, setSideBarHidden reveals the grid view and calls openViewContainer without focus, while setPanelHidden and the auxiliary-bar path pass !skipLayout as the focus argument. The corresponding visibility actions in src/vs/workbench/browser/actions/layoutActions.ts and src/vs/workbench/browser/parts/panel/panelActions.ts do not establish a common focus policy.
- **reverted fix:** https://github.com/microsoft/vscode/pull/235622 implemented a no-focus policy in commit d5746c5593f6afe15e44a9f7877a064df6605d11, but https://github.com/microsoft/vscode/pull/236556 reverted it in commit d47f63e5dcde69292e29018bd6fbb4bc93ccaaf1 after terminal-focus regressions; the issue was subsequently reopened.
- **accessibility and compatibility:** Maintainer comments report broken terminal muscle memory and explicitly raise keyboard-only and screen-reader compatibility concerns. Other comments favor preserving focus for visibility-only commands, demonstrating an unresolved observable-behavior decision rather than an implementation-only question.
