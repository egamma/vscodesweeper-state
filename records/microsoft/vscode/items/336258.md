# Issue #336258 — `DocumentLink` click target is unpredictable when multiple providers return overlapping ranges — provider priority (score/isBuiltin/registration order) is not respected

[https://github.com/microsoft/vscode/issues/336258](https://github.com/microsoft/vscode/issues/336258)

## Summary

Keep open: the reporter confirmed the overlapping-link behavior on 1.137.0, and current source contains an unchecked ordering assumption that can defeat cross-provider overlap removal. The precise connection to the supplied single-link Markdown reproduction still needs diagnosis before adopting the proposed fix.

## Change summary

Ensure overlapping document links from different providers resolve consistently according to provider priority.

## Best solution

Make cross-provider link aggregation reliably honor registry priority without depending on provider result order, while preserving legitimate multiple links returned by a single provider. First establish why the minimal Markdown example bypasses the overlap removal already present.

## Evidence

- **Reporter confirmation:** https://github.com/microsoft/vscode/issues/336258 supplies a minimal extension and reports duplicate hover entries and the built-in target winning Cmd/Ctrl+click. The author's September 15 follow-up confirms the same behavior on 1.137.0 after the upgrade request.
- **Priority is already wired into aggregation:** src/vs/editor/common/languageFeatureRegistry.ts::_compareByScoreAndTime ranks score, built-in status, and registration time. src/vs/editor/contrib/links/browser/getLinks.ts::getLinks reverses that ordering and stores asynchronous results by index, so completion timing alone does not explain the defect.
- **Unchecked merge assumption:** src/vs/editor/contrib/links/browser/getLinks.ts::LinksList._union performs a two-pointer range merge without sorting either input. For a lower-priority list containing ranges [1:20–25, 1:2–5] and a higher-priority list containing [1:2–5], it emits the higher-priority link before the first old range, then appends both old ranges, retaining the conflicting lower-priority link. LinkProviderAdapter.provideLinks in src/vs/workbench/api/common/extHostLanguageFeatures.ts and $registerDocumentLinkProvider in src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts preserve provider array order.
- **Remaining diagnosis boundary:** Two providers each returning exactly one overlapping range would be deduplicated by the current _union. The supplied minimal document therefore needs its actual provider outputs inspected before attributing that exact reproduction solely to unsorted arrays. LinkDetector.getLinkOccurrence in src/vs/editor/contrib/links/browser/links.ts selects the first matching decoration without consulting provider priority if conflicting links survive aggregation.
- **Candidate is not a landed fix:** https://github.com/microsoft/vscode/compare/main...knaka:vscode:fix/document-link-overlap-priority contains candidate commit 967d5fe5290180d2d79ef92a269ff6ed22d8c762. Current checkout commit 959031245ebb1fe077e0d512e1397c0ae82006e4 still has neither its priority field nor its final overlap pass. No open PR referencing this issue was found.
- **Preserve same-provider alternatives:** https://github.com/microsoft/vscode/issues/151077#issuecomment-1172267763 shows a maintainer expecting three identical-range links from one provider to remain usable. That closed report concerned vscode-insiders URI handling, not cross-provider priority, and is not a canonical duplicate. The candidate's global overlap suppression would also remove same-provider alternatives.
