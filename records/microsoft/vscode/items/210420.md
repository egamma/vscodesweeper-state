# Issue #210420 — Expand source files in explorer (Combined outline/Project explorer)

[https://github.com/microsoft/vscode/issues/210420](https://github.com/microsoft/vscode/issues/210420)

## Summary

This remains a valid, accepted Backlog feature request with 26 community upvotes. The existing Outline view only follows the active editor, while the requested multi-file symbol hierarchy is still absent from the Explorer on current main.

## Change summary

Allow source-file nodes in the Explorer to expand into their classes, methods, and other document symbols for navigation across multiple files.

## Best solution

Provide a performant, accessible project-tree experience in which expandable source files expose document symbols and selecting a symbol opens its defining range, without changing ordinary file and folder navigation or the existing active-file Outline view.

## Vision fit

- **Fit:** aligned
- **Reason:** Faster navigation across project structure supports the developer inner loop and workbench UX, provided symbols are loaded lazily so the Explorer remains responsive.
- **Evidence:** Durable themes: “Workbench & core UX” and “Developer inner loop — editor.”

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/services/outline/browser/outline.ts`, `src/vs/workbench/contrib/codeEditor/browser/outline/documentSymbolsOutline.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Add an Explorer view test with a mock document-symbol provider that expands a source file into nested symbols, verifies symbol activation opens the defining range, and confirms ordinary file and folder nodes retain their existing behavior.
- **Behavior:**

  > Users can expand supported source files in the Explorer and see their document-symbol hierarchy across multiple files at once. Activating a class, method, or other symbol opens the corresponding file and range. Files without available symbols and ordinary folder navigation remain unchanged, and expanding symbol-capable files must not make normal Explorer loading noticeably slower.
- **Trace:**

  > The current Outline view is registered separately in src/vs/workbench/contrib/outline/browser/outline.contribution.ts and OutlinePane in outlinePane.ts recreates one IOutline from the active editor pane. DocumentSymbolsOutline in src/vs/workbench/contrib/codeEditor/browser/outline/documentSymbolsOutline.ts supplies the symbol tree and reveal behavior, but IOutlineService.createOutline currently accepts an IEditorPane rather than an arbitrary Explorer resource. The Explorer uses WorkbenchCompressibleAsyncDataTree in explorerView.ts and ExplorerDataSource in explorerViewer.ts; its child contract currently returns only ExplorerItem filesystem or nesting children. The planning boundary is the integration contract between these trees, including lazy symbol acquisition, mixed-node accessibility, ordering, and lifecycle. Preserve the existing active-file Outline view and normal filesystem operations, and do not eagerly resolve symbols for every workspace file. The older matching request https://github.com/microsoft/vscode/issues/158277 was declined, but this issue was subsequently accepted into the Backlog with sufficient community support.
- **Open decisions:**
  - Should every file backed by a document-symbol provider expose an expansion control, or only files after symbol availability has been established without opening them?
  - Should symbol children follow Outline ordering and filtering settings, source position, or a separate Explorer-specific contract?
  - When a file has both nested-file children and document symbols, how should those two child groups be presented and navigated accessibly?
