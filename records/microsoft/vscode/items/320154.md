# Issue #320154 — Can't create new profile from import and/or template

[https://github.com/microsoft/vscode/issues/320154](https://github.com/microsoft/vscode/issues/320154)

## Summary

This remains the canonical open bug for profile imports and built-in templates being discarded when one extension installation fails. Multiple later reproductions, trace logs, and the current source path confirm that the failure still aborts creation without presenting the underlying error.

## Change summary

Creating a profile from an imported file or built-in template can silently discard the entire profile when an included extension cannot be installed.

## Best solution

Profile creation should retain the successfully imported resources when a template references an already-present built-in extension, and any genuinely unavailable extensions should produce an actionable warning rather than an unexplained missing profile. The curated CDN templates should also stop requesting obsolete Copilot extension versions.

## Plan brief

- **Likely files:** `src/vs/workbench/services/userDataProfile/browser/extensionsResource.ts`, `src/vs/workbench/services/userDataProfile/browser/userDataProfileImportExportService.ts`
- **Validation:** Exercise `createProfileFromTemplate` with a template containing settings plus an extension version older than an installed built-in: the profile and settings must remain registered, no downgrade is attempted, and the chosen warning/error behavior is observable; also cover a genuinely incompatible non-built-in extension according to the selected failure policy.
- **Behavior:**

  > Creating a profile from an imported `.code-profile` or a built-in template must not silently leave the profile absent. A template entry for functionality already supplied by a newer built-in extension must not trigger a downgrade or discard the profile. Successfully imported settings and other resources must remain available, while extension failures follow an explicit, visible policy. Acceptance should cover the Python/Data Science-style obsolete Copilot entry and a genuinely incompatible non-built-in extension.
- **Trace:**

  > The confirmed trigger is a template whose `extensions` payload includes an obsolete `github.copilot` or `github.copilot-chat` marketplace version while a newer Copilot Chat is built in. `ExtensionsResource.apply` in `src/vs/workbench/services/userDataProfile/browser/extensionsResource.ts` gathers gallery installs and awaits `installFromGallery`; the reported downgrade rejection propagates from that loop. `UserDataProfileImportExportService.createProfileFromTemplate` in `src/vs/workbench/services/userDataProfile/browser/userDataProfileImportExportService.ts` catches the rejection, removes the profile, and suppresses the error, producing the reported no-op UI. The issue also canonically absorbs imports failing on other incompatible extensions, so the uncertainty begins at whether error tolerance is specific to already-satisfied built-ins or applies to extension installation failures generally. Keep unrelated profile replacement, cancellation, and ordinary extension installation semantics out of scope. Related evidence: https://github.com/microsoft/vscode/issues/320154#issuecomment-5144880054 and https://github.com/microsoft/vscode/issues/240149.
- **Open decisions:**
  - When one requested extension cannot be installed, should profile creation complete with that extension skipped and a warning, or fail atomically with an actionable error—and is the tolerant behavior limited to extensions already satisfied by a built-in version?
