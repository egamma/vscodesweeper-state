# Issue #336900 — Transform to Title Case incorrectly capitalizes letters after combining accents

[https://github.com/microsoft/vscode/issues/336900](https://github.com/microsoft/vscode/issues/336900)

## Summary

Traced and confirmed in current source: the Title Case regex treats a combining diacritical mark as a non-letter boundary character, so the letter right after it gets incorrectly capitalized.

## Change summary

Transform to Title Case capitalizes the letter following a Unicode combining accent, e.g. 'e' + U+0301 + 'lan' becomes 'ÉLan' instead of 'Élan'.

## Best solution

Exclude combining marks (\p{M}) from the 'boundary' negated character class in TitleCaseAction.titleBoundary so a combining accent is not mistaken for a word separator.

- **Behavior:**

  > Transform to Title Case must treat a base letter followed by Unicode combining marks (e.g. combining accents) as a single letter unit, not as a letter followed by a word-boundary. Given decomposed text like 'e' + U+0301 COMBINING ACUTE ACCENT + 'lan', running Transform to Title Case should produce 'E' + U+0301 + 'lan' (visually 'Élan'), matching the result already produced for the precomposed equivalent 'élan' -> 'Élan'. Only the first letter of each word should be capitalized; letters after a combining mark must remain untouched.
- **Trace:**

  > TitleCaseAction.titleBoundary (src/vs/editor/contrib/linesOperations/browser/linesOperations.ts:1218) is '(^|[^\p{L}\p{N}\']|((^|\P{L})\'))\p{L}' with the 'gmu' flags, applied via _modifyText (line 1229-1238) after lowercasing the whole string. Because a combining mark (Unicode category Mn) is excluded from \p{L} and \p{N}, it satisfies the negated boundary alternative '[^\p{L}\p{N}\']', so the regex treats it as a separator and capitalizes the letter that follows it. The boundary condition needs to also allow \p{M} (combining marks) as 'part of the preceding letter' rather than a boundary — e.g. by excluding \p{M} from the negated class, or by matching \p{L}\p{M}* as the base unit before deciding what starts a new word. Do not change SnakeCaseAction/CamelCaseAction/PascalCaseAction boundary regexes (lines 1243, 1244, 1273, 1301, 1348, 1349) or the general word-boundary semantics for non-combining separators — only the combining-mark misclassification in TitleCaseAction is in scope.

## Evidence

- **regex boundary:** src/vs/editor/contrib/linesOperations/browser/linesOperations.ts:1218 defines titleBoundary = '(^|[^\p{L}\p{N}\']|((^|\P{L})\'))\p{L}'. A combining mark (Unicode category Mn, e.g. U+0301) is not \p{L} or \p{N}, so it matches the negated boundary class '[^\p{L}\p{N}\']' and the following letter gets swept into the match and uppercased.
