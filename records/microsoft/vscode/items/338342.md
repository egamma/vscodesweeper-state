# Issue #338342 — Worktree isolation option not shown in Agents when git repo is init'd but there are no commits

[https://github.com/microsoft/vscode/issues/338342](https://github.com/microsoft/vscode/issues/338342)

## Summary

Confirmed in source: when a git repo has an unborn HEAD (no commits), `_getGitInfo` in worktreeIsolation.ts returns undefined, so the worktree-isolation UI option disappears entirely rather than being shown disabled or with an explanatory hover — a real gap, filed by a team member while testing a related issue.

## Change summary

Opening the Agents window on a git-initialized folder with zero commits silently omits the worktree-isolation option instead of explaining why it's unavailable.

## Best solution

Decide between the two proposed UX directions (show the option disabled with an explanatory hover vs. silently create an initial commit so isolation can proceed) before implementing — this is a product/UX call, not just a bug fix.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/shared/worktreeIsolation.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostChatInputPicker.ts`
- **Validation:** A worktreeIsolation test asserting the picker reports a disabled-with-reason (or auto-commit) isolation option for a repo with an unborn HEAD, rather than omitting it.
- **Behavior:**

  > When a workspace folder is a git repository with no commits (unborn HEAD), opening the Agents window's isolation option should not silently omit worktree isolation. Depending on the chosen design, it should either show the option disabled with a hover explaining that a repo needs a commit before a worktree can be created, or show it enabled and transparently create an initial commit when the user picks worktree isolation. Acceptance: the picker communicates *why* isolation is unavailable (or makes it work) instead of the option simply not appearing.
- **Trace:**

  > `_getGitInfo` in src/vs/platform/agentHost/node/shared/worktreeIsolation.ts (around line 1499) returns `undefined` whenever `revParse(repositoryRoot, 'HEAD')` fails, which is exactly what happens on an unborn HEAD; callers use that `undefined` to omit git-derived branch/isolation info, which propagates into the Agents window picker in src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostChatInputPicker.ts not offering the isolation control at all. worktreeIsolation.test.ts:237-253 confirms `resolveIsolationConfig` collapses the isolation enum to `['folder']` in this case, but nothing currently surfaces *why* to the user. Do not change the underlying limitation that `git worktree add` cannot target a repo with no commits — only the presentation.
- **Open decisions:**
  - Should the isolation option be shown disabled with an explanatory hover, or should choosing worktree isolation transparently create an initial commit so isolation can proceed?
  - If auto-committing, what commit message/content is used, and does the user need to be warned/confirmed first?

## Evidence

- **root cause:** src/vs/platform/agentHost/node/shared/worktreeIsolation.ts:1499-1514 `_getGitInfo` calls `this._gitService.revParse(repositoryRoot, 'HEAD')` and returns `undefined` when it fails (unborn HEAD, no commits), which upstream code uses to determine the picker's isolation option availability — comment at line 1505 explicitly notes 'Skip worktree isolation for a repo with no commits yet (unborn HEAD)'.
- **test coverage of the resolved config:** src/vs/platform/agentHost/test/node/shared/worktreeIsolation.test.ts:237-253 exercises `resolveIsolationConfig` with an unborn HEAD and asserts the isolation enum collapses to `['folder']` only — consistent with the reported missing UI option, but the test covers the resolver, not the picker's display/hover behavior the issue asks for.
