# Issue #307001 — High CPU usage: Infinite loop of rg (ripgrep) processes spawned when opening a folder with square brackets [] in its name

[https://github.com/microsoft/vscode/issues/307001](https://github.com/microsoft/vscode/issues/307001)

## Summary

Keep open: recent macOS and Windows confirmations identify expensive parent-directory searches caused by bracketed workspace paths, and the faulty resolution remains on main. An open draft PR explicitly targets this issue; review that candidate rather than closing before it merges or starting competing implementation work.

## Change summary

Opening a workspace with square brackets in its path causes prompt discovery to search ancestor directories repeatedly, accumulating ripgrep processes and exhausting resources.

## Best solution

Review and land the literal-path handling in https://github.com/microsoft/vscode/pull/341268 after validating its regression cases and affected-platform behavior. Workspace and home-directory prefixes should remain literal while explicitly configured glob patterns retain their supported semantics.

## Evidence

- **Confirmed macOS reproduction:** https://github.com/microsoft/vscode/issues/307001#issuecomment-6117443343 reports VS Code 1.141.0 repeatedly searching /Users/<user> with filePattern [mac]study/.github/instructions. Active rg processes increased from 118 to 746; removing brackets yielded zero active searches during the comparison sample.
- **Independent Windows confirmation:** https://github.com/microsoft/vscode/issues/307001#issuecomment-6123132069 reproduces with disabled extensions and fresh user data: an empty bracketed workspace under Documents produced 28 rg processes and 100% CPU, while a plain-named workspace under the same parent produced none. The smaller Desktop parent did not exhibit the buildup.
- **Current source retains the defect:** In src/vs/workbench/contrib/chat/common/promptSyntax/utils/promptFilesLocator.ts, toAbsoluteLocations joins the literal workspace URI with configuredLocation before calling resolveSearchLocation. That helper applies isValidGlob to every absolute-path segment, moving searchRoot above a bracketed workspace segment. searchFilesInLocation passes that ancestor and the remaining filePattern to fileSearch with shouldGlobMatchFilePattern: true. This confirms the erroneous search boundary, without independently proving an infinite retry loop.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/341268 is OPEN, draft, unmerged, and has this issue in closingIssuesReferences. Its description explicitly addresses literal workspace and home prefixes, preserves configured relative globs and parent-relative paths, and reports regression cases plus a successful installed-build Windows check. These are candidate-fix results, not evidence that main is fixed.
- **Earlier duplicate suggestion assessed:** The maintainer suggestion at https://github.com/microsoft/vscode/issues/307001#issuecomment-4167147887 points to https://github.com/microsoft/vscode/issues/305544. That issue remains open but concerns worktree traversal and findFiles ignore-policy behavior; its discussion does not establish that it owns this specific literal-path parsing defect.
- **Older bracket-path report:** https://github.com/microsoft/vscode/issues/286778 is verified open and describes the same bracket-triggered ancestor traversal on Windows, alongside discussion of other expensive searches. It is a strong consolidation lead, but this issue now carries the detailed cross-platform diagnosis and an explicitly linked open fixing PR; the active-PR keep-open rule applies.
