# Issue #24783 — vscode reads AltGr key as cursor-left move through X11 connections

[https://github.com/microsoft/vscode/issues/24783](https://github.com/microsoft/vscode/issues/24783)

## Summary

The defect remains active in remote X11/RDP Linux sessions: recent reporters confirm that AltGr still dispatches an unintended cursor-left action, while the `keyboard.dispatch: "keyCode"` workaround breaks other shortcuts. Keep this open for diagnosis at the browser-event and keyboard-mapping boundary.

## Change summary

Pressing AltGr through an X11 or Linux remote-desktop connection inserts the intended character but also moves the cursor left.

## Best solution

Make the default keyboard dispatch path distinguish the remote AltGr event from a genuine Left Arrow press without requiring the application-scoped `keyCode` fallback or regressing layout-dependent shortcuts such as Ctrl+/.

## Plan brief

- **Likely files:** `src/vs/base/browser/keyboardEvent.ts`, `src/vs/workbench/services/keybinding/browser/keybindingService.ts`, `src/vs/workbench/services/keybinding/electron-browser/nativeKeyboardLayout.ts`, `src/vs/workbench/services/keybinding/common/macLinuxKeyboardMapper.ts`
- **Validation:** Using a non-US layout through Windows-to-Ubuntu X11 forwarding or RDP, press AltGr alone and type an AltGr-composed character such as `{`: the character must be inserted without cursor movement under the default `keyboard.dispatch: "code"`, and Ctrl+/ plus existing Linux keyboard-mapper tests must remain functional.
- **Behavior:**

  > In a Linux VS Code session displayed through X11 forwarding or remote desktop, AltGr must behave as a modifier and must not invoke cursor-left. AltGr-composed characters such as `{` must be inserted at the current cursor position under the default `keyboard.dispatch: "code"`. Existing layout-sensitive shortcuts, including Ctrl+/, must continue to work without requiring a machine-wide dispatch workaround.
- **Trace:**

  > Commit 822ab91b892c0d6caa398dc28a9cb62f7f913725 introduced the code-versus-keyCode dispatch mode immediately before the reported VS Code 1.11 regression. The current keydown path starts in src/vs/workbench/services/keybinding/browser/keybindingService.ts, which wraps the incoming DOM KeyboardEvent in StandardKeyboardEvent and dispatches it. StandardKeyboardEvent in src/vs/base/browser/keyboardEvent.ts retains the browser `code`, extracts `keyCode`, and records AltGraph state. The Linux mapper selected by src/vs/workbench/services/keybinding/electron-browser/nativeKeyboardLayout.ts normally dispatches by scan code; selecting `keyboard.dispatch: "keyCode"` instead replaces it with FallbackKeyboardMapper, explaining both the workaround and its shortcut regressions. Reports across multiple remote technologies suggest that the incoming event or its mapping is distorted before command resolution, but source inspection alone does not establish whether VS Code can normalize it safely or whether Electron/Chromium must change. Preserve normal local Linux keyboard behavior and all genuine Left Arrow dispatch.
- **Open decisions:**
  - What exact `key`, `code`, `keyCode`, modifier, and AltGraph values arrive for AltGr and Left Arrow in each affected X11/RDP setup?
  - Can VS Code distinguish the malformed AltGr event from a genuine Left Arrow event without environment-specific heuristics?
  - If the event is already indistinguishable when delivered by Chromium, should the implementation be owned upstream with VS Code retaining only diagnostic or workaround behavior?

## Evidence

- **current confirmations:** Comments through July 2026 report the same behavior on Ubuntu 24.04 over Windows Remote Desktop, including with extensions disabled; several reporters also confirm that `keyboard.dispatch: "keyCode"` avoids the cursor movement but breaks Ctrl+/ and other shortcuts.
- **regression history:** Commit 822ab91b892c0d6caa398dc28a9cb62f7f913725 introduced `keyboard.dispatch` on 2017-03-30, immediately before the April 2017 report that the regression began with VS Code 1.11. Later commits retained the dispatch split but do not reference or resolve https://github.com/microsoft/vscode/issues/24783.
- **current source:** src/vs/platform/keyboardLayout/common/keyboardConfig.ts still defaults `keyboard.dispatch` to `code`; src/vs/workbench/services/keybinding/electron-browser/nativeKeyboardLayout.ts switches wholesale to FallbackKeyboardMapper only when the user selects `keyCode`, so the documented workaround remains a global dispatch trade-off rather than a fix.
- **event boundary:** src/vs/workbench/services/keybinding/browser/keybindingService.ts converts each incoming DOM keydown through StandardKeyboardEvent and dispatches it, while src/vs/base/browser/keyboardEvent.ts preserves both the browser-provided `code` and extracted `keyCode`. The remote-session distortion must be characterized at this boundary before assigning ownership to VS Code or Electron/Chromium.
- **canonical and fix search:** Searches of open microsoft/vscode issues for the AltGr cursor-left and keyboard.dispatch symptoms found no broader open canonical issue, and no open pull request referencing https://github.com/microsoft/vscode/issues/24783 was found.
- **demand:** The report has 21 community upvotes and repeated independent confirmations across X11 forwarding, WSLg, xrdp, Remmina, and virtual-machine remote desktop configurations.
