# Issue #181051 — Web support for sovereign aka national/gov clouds e.g. Mooncake, DoD

[https://github.com/microsoft/vscode/issues/181051](https://github.com/microsoft/vscode/issues/181051)

## Summary

Keep open: desktop sovereign-cloud authentication does not establish web support, and maintainers explicitly left the hosting and service boundaries unresolved. This team-authored, accepted request has neither a verified completing fix nor an eligible duplicate.

## Change summary

Support Microsoft sovereign-cloud authentication in VS Code for the web, including China and US Government environments.

## Best solution

Define the supported browser-authentication and hosting boundary, then deliver sovereign-cloud sign-in within that boundary. Keep Remote Tunnels service availability separate from the built-in Microsoft authentication capability; changing an authentication endpoint alone does not establish sovereign-cloud service support.

## Plan brief

- **Likely files:** `extensions/microsoft-authentication/package.json`, `extensions/microsoft-authentication/src/extension.ts`, `extensions/microsoft-authentication/src/node/authProvider.ts`
- **Validation:** The plan should end with an explicit browser acceptance scenario: in the agreed supported web deployment, request a microsoft-sovereign-cloud session for an authorized ChinaCloud or USGovernment test account, verify the correct authority is used and the consuming extension receives a usable session, and confirm ordinary public-cloud authentication remains unchanged. Validate Remote Tunnels separately only if explicitly included in the agreed scope.
- **Behavior:**

  > The requested capability is sovereign-cloud Microsoft authentication in VS Code for the web, continuing the desktop provider work. A supported browser deployment should let an extension explicitly request the sovereign provider and obtain a usable session from the selected cloud rather than the commercial authority. Acceptance must establish which web deployment and cloud combinations are supported. Authentication support must not imply that Settings Sync or Remote Tunnels is available in those clouds.
- **Trace:**

  > extensions/microsoft-authentication/package.json contributes microsoft-sovereign-cloud and microsoft-sovereign-cloud.environment, but declares a Node main entry point without a browser entry point. initMicrosoftSovereignCloudAuthProvider in extensions/microsoft-authentication/src/extension.ts resolves the configured environment and initializes MsalAuthProvider from src/node/authProvider.ts. This establishes existing Node-hosted functionality, not a browser token-acquisition path. https://github.com/microsoft/vscode/issues/162539 documents the dedicated-provider contract and consumer adoption requirement; preserve that distinction from the public microsoft provider. The discussion at https://github.com/microsoft/vscode/issues/181051#issuecomment-2330529006 leaves the public-hosted versus sovereign-hosted web boundary undecided. https://github.com/microsoft/vscode/issues/181051#issuecomment-2330591078 separately identifies dev tunnels service availability as an external prerequisite. The trace does not establish browser token exchange feasibility or a sovereign deployment, so those must be investigated before a bounded implementation can be defined.
- **Open decisions:**
  - Should supported sovereign-cloud web authentication operate from the existing publicly hosted vscode.dev deployment, require a sovereign-hosted deployment, or support both?
  - Is the first supported scope extension-consumed sovereign authentication only, with Remote Tunnels explicitly separate, or must it include end-to-end Remote Tunnels connectivity?
