# Issue #178078 — ViewPane saveState is not called before view is disposed

[https://github.com/microsoft/vscode/issues/178078](https://github.com/microsoft/vscode/issues/178078)

## Summary

The lifecycle gap remains on current main: removing a pane excludes it from the container's later save pass, while ViewPane disposal does not invoke saveState. This team-authored, under-discussion issue should stay open until the intended lifecycle contract is settled.

## Change summary

Ensure a ViewPane can persist its current state before it is disposed after being moved between view containers.

## Best solution

Define and test whether saveState is a guarantee of every ViewPane disposal or specifically of container-transfer disposal, then enforce that contract before subclass resources such as webviews are released.

- **Likely files:** `src/vs/workbench/browser/parts/views/viewPane.ts`, `src/vs/workbench/browser/parts/views/viewPaneContainer.ts`, `src/vs/workbench/contrib/webviewView/browser/webviewViewPane.ts`, `src/vs/workbench/contrib/webviewView/test/browser/webviewViewPane.test.ts`

- **Behavior:**

  > When a stateful view pane is removed and disposed while moving between view containers, its latest state must be persisted before resources needed to read that state are released. Recreating the view must restore that state. Existing storage-save behavior and state restoration for panes that remain mounted must continue to work, without duplicate persistence causing observable regressions.
- **Trace:**

  > ViewPane in src/vs/workbench/browser/parts/views/viewPane.ts exposes saveState but inherits disposal without calling it. ViewPaneContainer.removePane in src/vs/workbench/browser/parts/views/viewPaneContainer.ts removes the pane from paneItems, and the container's saveState later visits only the remaining panes. WebviewViewPane.saveState in src/vs/workbench/contrib/webviewView/browser/webviewViewPane.ts copies the live overlay state into its memento, establishing why persistence must precede disposal. The uncertainty begins at the shared lifecycle boundary: applying the guarantee to every ViewPane disposal affects all subclasses, while handling only view transfer narrows the contract. Preserve shutdown/storage-triggered saving and avoid changing ordinary visibility toggles or pane reordering that do not dispose the view.
- **Open decisions:**
  - Should saveState be a guaranteed part of every ViewPane disposal, or only of disposal caused by transferring a view between containers?
