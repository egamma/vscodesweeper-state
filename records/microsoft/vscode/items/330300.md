# Issue #330300 — Markdown previewer sometimes incorrectly renders ranges of text in math mode

[https://github.com/microsoft/vscode/issues/330300](https://github.com/microsoft/vscode/issues/330300)

## Summary

Real defect, but it lives in the `@vscode/markdown-it-katex` dependency (a separate Microsoft-owned repo) that `extensions/markdown-math` uses for `$...$` math parsing, not in microsoft/vscode's own source — routing to the markdown area rather than a close.

## Change summary

In the built-in Markdown math preview, prose containing two unrelated stray `$` signs (e.g. "$ /" and "0.00138 $/audio-h") gets rendered as a single inline math expression spanning everything between them.

## Best solution

The fix belongs in `@vscode/markdown-it-katex`'s `isValidInlineDelim`, which currently only checks the character on the *outer* side of each `$` (prevChar for opening, nextChar for closing) and never the inner side — so two isolated `$` signs surrounded by whitespace/punctuation get paired as math delimiters even though the README's documented Pandoc-style rule (non-space immediately inside each delimiter) would reject both here. Until that's tightened (and ideally made code-span-aware, since the scan also ignores backticks), users can work around it with `markdown.math.enabled: false` or by escaping the stray signs as `\$`.

## Evidence

- **extension wiring:** extensions/markdown-math/src/extension.ts loads `@vscode/markdown-it-katex` (via `require('@vscode/markdown-it-katex').default`) whenever `markdown.math.enabled` (default true) is set, and registers it as the markdown-it plugin for `$...$` inline math.
- **delimiter logic traced:** Downloaded @vscode/markdown-it-katex@1.1.2 (extensions/markdown-math/package.json pins ^1.1.1) and read dist/index.js's `isValidInlineDelim`: `can_open` only inspects the character *before* the `$` (must be whitespace/non-word/undefined), and `can_close` only inspects the character *after* the matched `$` (must be whitespace/non-word). Neither checks the character on the delimiter's inner side, so a `$` followed by a space (like the user's "$ /") still opens math, and a `$` preceded by a space (like "0.00138 $/audio-h") still closes it.
- **matches the report exactly:** First `$` in "were calibrated as $ / `sum(duration_delta)`," has a space before it -> can_open=true despite the space right after it. The next `$` in "0.00138 $/audio-h" has `/` right after it -> can_close=true despite the space right before it. That produces exactly the highlighted math span the reporter screenshotted, from right after "were calibrated as" through "0.00138".
- **documentation mismatch:** The plugin's own README states it follows Pandoc's convention ("the opening $ must have a non-space character immediately to its right, while the closing $ must have a non-space character immediately to its left"), but the shipped code does not enforce that — the implementation and the documented spec disagree, which is itself worth fixing upstream.
