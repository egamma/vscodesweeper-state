# Issue #253508 — MCP model access is not synced

[https://github.com/microsoft/vscode/issues/253508](https://github.com/microsoft/vscode/issues/253508)

## Summary

The accepted Backlog request remains necessary: current source stores MCP model access in a normal resource-scoped setting that should be eligible for Settings Sync, but no fix, test, or canonical issue establishes that the reported cross-device flow works.

## Change summary

Synchronize each MCP server's configured model-access allowlist across machines through Settings Sync.

## Best solution

Make user-level `chat.mcp.serverSampling` selections reliably round-trip through Settings Sync and appear in Configure Model Access on another machine, while preserving workspace-specific configuration scopes.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/common/mcpSamplingService.ts`, `src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts`, `src/vs/platform/userDataSync/common/settingsSync.ts`, `src/vs/platform/userDataSync/test/common/settingsSync.test.ts`
- **Validation:** Add or extend a Settings Sync test using two clients: write a user-level `chat.mcp.serverSampling` object on client one, sync both clients, and assert client two receives the same per-server `allowedModels` values; then verify Configure Model Access reads that synchronized value.
- **Behavior:**

  > Changing Configure Model Access for a user-installed MCP server on one machine must synchronize the selected model allowlist to another machine after Settings Sync runs. Opening Configure Model Access on the second machine must show the synchronized selections. Workspace-scoped MCP choices must retain their existing workspace semantics, and unrelated MCP configuration must remain unchanged.
- **Trace:**

  > The Configure Model Access action in src/vs/workbench/contrib/mcp/browser/mcpServerActions.ts dispatches `McpCommandIds.ConfigureSamplingModels`; the command updates the allowlist through `McpSamplingService.updateConfig` in src/vs/workbench/contrib/mcp/common/mcpSamplingService.ts. `_getConfig` defaults to `ConfigurationTarget.USER`, and `chat.mcp.serverSampling` is registered as `ConfigurationScope.RESOURCE` in src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts. Settings Sync only ignores machine and machine-overridable scopes in src/vs/platform/userDataSync/common/userDataSync.ts, so the user-level value appears eligible for sync; the unresolved point is why the reported two-client flow does not round-trip or rehydrate. Keep workspace and memory targets scoped as they are, and do not broaden this into synchronization of MCP server definitions or Copilot chat history. The maintainer expectation is recorded at https://github.com/microsoft/vscode/issues/253508#issuecomment-3028456594.

- **write path:** src/vs/workbench/contrib/mcp/common/mcpSamplingService.ts `_getConfig` selects the MCP collection's configuration target, defaulting to `ConfigurationTarget.USER`, and `updateConfig` writes the per-server model allowlist through `IConfigurationService.updateValue`.
