# Issue #297446 — Add ability to hide inaccessible models

[https://github.com/microsoft/vscode/issues/297446](https://github.com/microsoft/vscode/issues/297446)

## Summary

A real gap remains on current main: general model visibility controls were added, but inaccessible models sourced only from the control manifest still bypass that visibility state and cannot appear in Manage Models. The maintainer discussion supports the request but leaves the user-facing hide and restore affordances undecided.

## Change summary

Let users hide inaccessible models from the model picker after they have seen them, while retaining a discoverable way to restore them.

## Best solution

Apply persistent visibility state to unavailable control-manifest models and provide a discoverable hide and restore flow. A maintainer should first choose whether the UI offers per-model hiding, one global unavailable-model toggle, or both.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerWidget.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerTabs.ts`, `src/vs/workbench/contrib/chat/browser/chatManagement/chatModelsViewModel.ts`, `src/vs/workbench/contrib/chat/common/languageModels.ts`
- **Validation:** Extend the model-picker unit tests to show that a featured control-manifest model missing from the registered model list is initially displayed as unavailable, disappears after the chosen hide action, remains hidden after visibility state is restored, and can be made visible again through the chosen management surface.
- **Behavior:**

  > Users who cannot access a model can hide it after learning that it exists. Hidden inaccessible models stay out of the model picker across subsequent openings, and users have a discoverable way to restore them. Available models and inaccessible models that have not been hidden remain unchanged. Acceptance should cover hiding, persistence, and restoration for a featured model that exists only in the control manifest.
- **Trace:**

  > The picker receives registered models separately from control-manifest entries in src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerWidget.ts. `buildUnavailableEntries` in modelPickerTabs.ts emits featured control entries that are absent from the registered model set without checking `ILanguageModelsService.isModelHidden`. Manage Models in chatModelsViewModel.ts enumerates registered language-model groups, so those control-only entries cannot currently receive visibility controls there. https://github.com/microsoft/vscode/pull/317308 established persisted visibility for registered models, but not this control-only path. Preserve selection, routing, and availability behavior; visibility should affect presentation only.
- **Open decisions:**
  - Should users hide individual inaccessible models, hide all inaccessible models with one preference, or have both controls?
  - Where should the restore affordance live so a hidden control-manifest-only model remains discoverable: Manage Models, a setting, or another model-picker management surface?

## Evidence

- **current source gap:** src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerWidget.ts passes `controlModelsForTier` directly to both picker implementations, while only registered model arrays and recent/pinned identifiers are filtered through `ILanguageModelsService.isModelHidden`.
- **unavailable path:** src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerTabs.ts builds unavailable entries by iterating featured `controlModels` absent from the registered model list; this path does not consult model visibility.
- **management limitation:** src/vs/workbench/contrib/chat/browser/chatManagement/chatModelsViewModel.ts populates Manage Models from `getLanguageModelGroups()` and `lookupLanguageModel()`, so a control-manifest-only inaccessible model has no row where it can be hidden or restored.
- **related implementation:** https://github.com/microsoft/vscode/pull/317308 added visibility controls for registered models and provider groups, but its implementation does not cover control-manifest-only unavailable entries and it does not reference this team-authored issue.
- **maintainer direction:** The issue discussion explicitly agrees that inaccessible models should be hideable, while leaving the choice among a setting, context menu, or clickable hover affordance unresolved.
