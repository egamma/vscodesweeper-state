# Issue #325507 — Public API to observe agent/subagent chat session lifecycle & status from an extension

[https://github.com/microsoft/vscode/issues/325507](https://github.com/microsoft/vscode/issues/325507)

## Summary

Keep open as a feature request: current extension APIs do not provide recoverable, cross-provider observation of built-in agent sessions and subagent delegations. The discussion establishes a concrete extension use case, but the public contract still needs API-owner design review.

## Change summary

Expose opt-in, read-only agent and subagent lifecycle observation with coherent initial state, distinct run identities, and explicit resynchronization semantics.

## Best solution

Design a minimal proposed observer API at the extension-host boundary, drawing on internal session status and subagent metadata while excluding conversation payloads and control methods. Resolve snapshot, identity, recovery, and consent guarantees before committing to a stable contract.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.chatSessionsProvider.d.ts`, `src/vs/workbench/api/common/extHostChatSessions.ts`, `src/vs/workbench/api/browser/mainThreadChatSessions.ts`, `src/vs/workbench/contrib/chat/common/chatSessionsService.ts`, `src/vs/workbench/contrib/chat/common/chatService/chatService.ts`
- **Validation:** The plan should define executable extension-boundary tests for late attachment during an active delegation, snapshot-to-stream continuity, distinct retry identities, child termination after parent cancellation, explicit resynchronization after delivery gaps, consent revocation, and exclusion of payload data and out-of-scope sessions.
- **Behavior:**

  > An authorized extension can reconstruct and maintain a coherent view of built-in agent sessions and subagent activity without injecting instructions or writing signal files into the workspace. Attaching late or reloading must recover current state rather than depend on observing every earlier event, and retries must remain distinguishable from earlier attempts. Observation exposes lifecycle metadata only, not conversation content or agent-control operations. Acceptance must cover recovery, terminal outcomes, cancellation, and permission loss against the API contract agreed with the maintainer.
- **Trace:**

  > The current proposed chatSessionsProvider surface manages provider-owned items; MainThreadChatSessions forwards archived-state notifications only to matching provider controllers. Internal IChatSessionsService has item enumeration and change events, while IChatSubagentToolInvocationData carries activity and child-chat metadata, but neither establishes recoverable extension-facing lifecycle semantics. The proposed chat.onDidReceiveChatDebugEvent is a diagnostic surface, not an equivalent observer contract. The reporter explicitly endorsed snapshot/cursor recovery and separate run identities at https://github.com/microsoft/vscode/issues/325507#issuecomment-4953224135; the external fixture pack is synthetic design input only. Preserve existing provider ownership, session-management behavior, and diagnostic APIs, and keep transcript access and control operations outside this request. Uncertainty starts at how runtime activity across session providers maps to a durable public identity and recovery contract.
- **Open decisions:**
  - What lifecycle states and terminal outcomes are guaranteed across built-in and contributed providers, including cancellation and parent-to-child termination?
  - What snapshot, ordering, cursor lifetime, and resynchronization guarantees will the public observer contract provide?
  - How are session, run-attempt, and delegation identities scoped and retained across retries, reloads, and remote reconnections?
  - Which sessions may an extension observe, how is user consent scoped, and what explicit outcome does the observer receive on revocation or disconnect?

## Evidence

- **Existing session API does not cover observation:** src/vscode-dts/vscode.proposed.chatSessionsProvider.d.ts exposes registerChatSessionItemProvider and createChatSessionItemController for managing a provider's own items. ChatSessionItemController.onDidChangeChatSessionItemState is documented as an archived-state event, not a cross-provider runtime-status subscription.
- **Extension-host ownership boundary:** src/vs/workbench/api/browser/mainThreadChatSessions.ts:732-738 forwards archived-state changes only to controllers whose chatSessionType matches the session's providerType. This does not expose built-in sessions and their delegations to arbitrary observing extensions.
- **Internal data exists but is not the requested public contract:** src/vs/workbench/contrib/chat/common/chatSessionsService.ts:864-913 defines internal onDidChangeSessionItems and getChatSessionItems. src/vs/workbench/contrib/chat/common/chatService/chatService.ts:1252-1295 models subagent activity, agent names, timing, and child chat resources. These internal surfaces do not establish a public snapshot-plus-cursor observer contract.
- **Adjacent debug capability is insufficient:** src/vscode-dts/vscode.proposed.chatDebug.d.ts:782-797 exposes proposed chat.onDidReceiveChatDebugEvent for core-originated diagnostic events.
