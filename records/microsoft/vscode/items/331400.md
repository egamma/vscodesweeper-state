# Issue #331400 — fix: use fresh service accessor when lazily initializing chat attachment context (fixes #329610)

[https://github.com/microsoft/vscode/issues/331400](https://github.com/microsoft/vscode/issues/331400)

## Summary

Confirmed real bug via source: `hookUpSymbolAttachmentDragAndContextMenu` captures a `ServicesAccessor` that is later reused from a deferred `ensureContextKeyService` closure, which throws the illegal-state error on first context-menu open of a chat symbol attachment. A fix is already proposed in open PR #331416, so this stays open pending review/merge rather than being closed or auto-fixed now.

## Change summary

Right-clicking a chat symbol attachment/anchor throws 'Illegal state: service accessor is only valid during the invocation of its target method' because a stale accessor is reused lazily.

## Best solution

Land https://github.com/microsoft/vscode/pull/331416, which re-invokes `instantiationService.invokeFunction` inside `ensureContextKeyService` to obtain a fresh accessor for `setResourceContext`, matching the pattern already used in the `dragstart` handler a few lines above.

## Evidence

- **crash site:** src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentWidgets.ts, `setResourceContext` calls `accessor.get(IFileService)` on an accessor captured earlier and no longer valid.
- **root cause:** In `hookUpSymbolAttachmentDragAndContextMenu`, the `ensureContextKeyService` closure (lines ~2018-2024) calls `setResourceContext(accessor, ...)` using the outer `accessor` parameter, which is only valid during the synchronous `invokeFunction` call that created it; the closure runs later, on context-menu open.
- **open fixing PR:** https://github.com/microsoft/vscode/pull/331416 is OPEN (not merged, verified via gh pr view) and implements exactly the described fix (wrap `setResourceContext` in a fresh `instantiationService.invokeFunction` call).
