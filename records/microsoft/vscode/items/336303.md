# Issue #336303 — Rename-provider WorkspaceEdit loses destination casing through asCanonicalUri on Windows

[https://github.com/microsoft/vscode/issues/336303](https://github.com/microsoft/vscode/issues/336303)

## Summary

Keep open: current source still replaces a rename provider's destination spelling with cached canonical casing. The merged provider fix explicitly leaves this VS Code failure unresolved, and the older related issue describes a different observable symptom.

## Change summary

Preserve the requested destination casing in provider-supplied file renames without changing case-insensitive resource identity.

## Best solution

Ensure workspace-edit revival preserves the requested directory-entry spelling for rename destinations while retaining existing resource-identity semantics. Cover both direct case-only renames and intermediate renames back to a previously cached filename in the MainThreadBulkEdits tests.

## Evidence

- **Exact failing source path:** src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts:513–516 routes $provideRenameEdits through reviveWorkspaceEditDto. In src/vs/workbench/api/browser/mainThreadBulkEdits.ts, the ResourceFileEdit branch replaces newResource with uriIdentityService.asCanonicalUri(newResource), matching the reporter's debugger observations.
- **Cached casing overrides the destination:** src/vs/platform/uriIdentity/common/uriIdentityService.ts: asCanonicalUri uses a case-insensitive comparison key when the filesystem provider lacks PathCaseSensitive. A cache hit returns the first URI's path spelling. Once Something.py is cached, a destination of something.py therefore revives as Something.py, including after an intermediate _something.py rename.
- **Downstream outcome:** src/vs/workbench/contrib/bulkEdit/browser/bulkFileEdits.ts: RenameOperation.perform forwards the revived newUri as the move target. src/vs/platform/files/common/fileService.ts:820–823 treats exactly identical source and target URI strings as a no-op; otherwise the supplied target reaches the provider rename. This explains both the collapsed direct rename and the uppercase intermediate-rename destination.
- **Provider fix does not resolve this issue:** https://github.com/microsoft/pyrx/pull/9462 is merged, but its description explicitly calls it a Pylance-only partial fix and states that direct F2 and the uninterrupted underscore journey remain blocked by VS Code URI canonicalization. It references https://github.com/microsoft/vscode/issues/336303 as the remaining limitation.
- **Related issue is not a canonical duplicate:** https://github.com/microsoft/vscode/issues/137256 is older and open, but concerns stale document URI casing delivered to extensions after a disk rename, rather than workspace-edit revival altering the destination before the disk rename. Its discussion establishes stable canonical identity, not permission to overwrite requested rename spelling. It does not satisfy the same-observable-symptom requirement for this re-reviewed item.
- **Existing validation boundary:** src/vs/workbench/api/test/browser/mainThreadBulkEdits.test.ts already supplies a mock case-insensitive filesystem and a real UriIdentityService, but covers canonicalization of text-edit resources only. Destination-casing regressions can be isolated in this suite without Pylance. No tests or builds were run in the read-only checkout.
