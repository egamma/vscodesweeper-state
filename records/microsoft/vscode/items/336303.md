# Issue #336303 — Rename-provider WorkspaceEdit loses destination casing through asCanonicalUri on Windows

[https://github.com/microsoft/vscode/issues/336303](https://github.com/microsoft/vscode/issues/336303)

## Summary

Traced the exact mechanism in mainThreadBulkEdits.ts: rename destinations (`newResource`) are passed through `uriIdentityService.asCanonicalUri`, which is a case-insensitive dedup cache designed for stable resource identity (e.g. open editors), not for preserving a rename's requested destination spelling — so a case-only rename destination can be silently replaced by a stale cached casing.

## Change summary

On Windows (case-insensitive filesystem), a rename provider's WorkspaceEdit destination URI has its casing overwritten by a stale cached entry in the URI identity service during edit revival, producing a filename/import casing mismatch.

## Best solution

Rework how `reviveWorkspaceEditDto` canonicalizes `ResourceFileEdit.newResource` in src/vs/workbench/api/browser/mainThreadBulkEdits.ts (line 66) — a rename/create destination should not be silently coerced to a previously cached casing; the canonical cache in src/vs/platform/uriIdentity/common/uriIdentityService.ts should instead be refreshed to the new spelling, or the destination should skip canonicalization entirely. This needs a deliberate design decision since `asCanonicalUri` is relied on elsewhere for editor/model identity stability.

## Evidence

- **cache semantics that cause the collapse:** src/vs/platform/uriIdentity/common/uriIdentityService.ts:83-102 — `asCanonicalUri` looks up a case-insensitive comparison key (`getComparisonKey(uri, true)`) and, if a prior entry exists (e.g. an earlier uppercase `Something.py`), returns that cached URI's casing instead of the one passed in — matching the reporter's debugger trace exactly (steps 1-4 in the issue body).
