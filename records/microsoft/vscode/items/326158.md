# Issue #326158 — Mouse selection snapping around decoration before/after content: both edges of injected content should snap to the adjacent position

[https://github.com/microsoft/vscode/issues/326158](https://github.com/microsoft/vscode/issues/326158)

## Summary

Current main still collapses hit-test positions inside injected text before applying ordinary nearest-column snapping, leaving only one measured edge for the adjacent document position. This is a source-confirmed editor hit-testing bug and should be routed to the editor-lines area.

## Change summary

Mouse selection near wide decoration before/after content snaps across the injected width instead of treating both visual edges as the adjacent document position.

## Best solution

Make editor mouse hit testing treat both visual edges of injected content as equivalent positions at the injection boundary, while preserving normal midpoint snapping between real characters and existing selection-across behavior.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/mouseTarget.ts`, `src/vs/editor/common/modelLineProjectionData.ts`
- **Validation:** Add an editor browser test using `abc=def` with wide injected content before column 4, asserting mouse points from the midpoint of `c` through the injected content resolve to model column 4; run it with `./scripts/test.sh --grep "injected content mouse snapping"`.
- **Behavior:**

  > For injected before/after content at a document position, both visual edges represent that same document position during mouse hit testing. Selecting `abc` in `abc=def` must require no additional drag distance when wide content is injected between `c` and `=`. Starting a reverse selection at the injected content's left edge must include `c`, while selection across the injected content and ordinary midpoint snapping between real characters remain unchanged.
- **Trace:**

  > MouseTargetFactory.doHitTest in src/vs/editor/browser/controller/mouseTarget.ts detects injected text and normalizes the browser hit position through the view model with PositionAffinity.None. ModelLineProjectionData.normalizeOffsetInInputWithInjectionsAroundInjections in src/vs/editor/common/modelLineProjectionData.ts collapses positions inside an injection to a cursor stop. MouseTargetFactory.createMouseTargetFromHitTestPosition then compares one visible horizontal offset per view column, so it cannot retain two visual offsets for the same adjacent document position and the injected width enters the nearest-column interval. The boundary is editor hit testing: keyboard cursor navigation tracked by https://github.com/microsoft/vscode/issues/127703, decoration rendering, and normal snapping between real characters must not change. The uncertainty starts at whether mouse snapping should always expose both edges or honor InjectedTextCursorStops, and how that behavior should remain consistent across DOM, GPU, wrapped, and bidirectional lines.
- **Open decisions:**
  - Should mouse hit testing always treat both injected-content edges as snap targets, or should it honor InjectedTextCursorStops?
  - Must the first implementation cover DOM and GPU-rendered editor lines together, or is injected decoration content restricted to the DOM path?
  - Which browser-level test seam should validate measured visual-edge snapping without coupling the test to browser-specific caret APIs?

## Evidence

- **confirmed current behavior:** The reporter reproduced both anchor and endpoint cases on VS Code 1.129.0 with the minimal extension and extensions otherwise disabled: https://github.com/microsoft/vscode/issues/326158.
- **source trace:** On current main, MouseTargetFactory.doHitTest in src/vs/editor/browser/controller/mouseTarget.ts obtains injected text and normalizes its view position with PositionAffinity.None; createMouseTargetFromHitTestPosition then builds nearest-position intervals from a single visibleRange.left for the normalized column and its neighbors. It has no representation for both visual edges mapping to the same document position.
- **normalization behavior:** ModelLineProjectionData.normalizeOffsetInInputWithInjectionsAroundInjections in src/vs/editor/common/modelLineProjectionData.ts collapses offsets within injected text to a permitted cursor stop. Defaults allow both stops, but the subsequent mouse snapping path does not retain both edge coordinates.
- **related issue is distinct:** https://github.com/microsoft/vscode/issues/127703 remains open for keyboard cursor stops around inlay hints and includes deliberate navigation trade-offs; it does not own the generic mouse-selection geometry reported here.
- **no existing fix:** No current commit, merged PR, open PR, or open canonical issue referencing 326158 was found, and the implicated hit-testing path remains unchanged on main.
