# Issue #326158 — Mouse selection snapping around decoration before/after content: both edges of injected content should snap to the adjacent position

[https://github.com/microsoft/vscode/issues/326158](https://github.com/microsoft/vscode/issues/326158)

## Summary

Still reproduces on current main: the mouse hit-testing in `doHitTest` normalizes injected-text positions only after the browser's `caretRangeFromPoint` has already resolved the x-coordinate using a midpoint that spans the full injected content width. No code compensates for the injected width when deciding which adjacent document position to snap to. Well-described bug with a clear minimal repro.

## Change summary

Mouse selection snaps to the wrong document position around wide decoration `before`/`after` contentText because the injected content's rendered width inflates the snap midpoint between the two adjacent document positions.

## Best solution

In the hit-test pipeline (`MouseTargetFactory.doHitTest` in `src/vs/editor/browser/controller/mouseTarget.ts`), when the resolved position falls inside injected text, the snap decision should treat both visual edges of the injected content as mapping to the same document position — effectively collapsing the injected width out of the midpoint calculation. This is the mouse-side counterpart of the keyboard cursor-stop work tracked in https://github.com/microsoft/vscode/issues/127703.

The subsequent `normalizePosition` (line 1107) collapses to the document position but does not compensate for which side of the injected content the click was on.
