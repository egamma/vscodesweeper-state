# Issue #60670 — [folding] show folding actions at the end of folding range as well

[https://github.com/microsoft/vscode/issues/60670](https://github.com/microsoft/vscode/issues/60670)

## Summary

This remains the canonical, well-supported request for folding from the end of a range. Current main still renders and activates folding controls only at range starts, and the previous implementation PR was closed unmerged with a maintainer explicitly inviting a fresh PR.

## Change summary

Show an interactive folding control at the ending line of an expanded folding range so users can collapse long regions without returning to the start.

## Best solution

Add an end-of-range folding control that respects the existing folding-control visibility behavior, then define deterministic behavior for lines shared by multiple range endpoints or by an ending and starting range. A fresh implementation should follow the current decoration architecture rather than revive the obsolete PR.

## Plan brief

- **Likely files:** `src/vs/editor/common/model.ts`, `src/vs/editor/common/model/textModel.ts`, `src/vs/editor/browser/viewParts/linesDecorations/linesDecorations.ts`, `src/vs/editor/contrib/folding/browser/foldingDecorations.ts`, `src/vs/editor/contrib/folding/browser/folding.ts`, `src/vs/editor/test/common/model/modelDecorations.test.ts`, `src/vs/editor/contrib/folding/test/browser/foldingModel.test.ts`
- **Validation:** Add editor model/view tests proving an end-line decoration is emitted only on the final line, plus a folding interaction test or explicit workbench check: open a long foldable range, click its ending control, and verify that the intended range collapses while start controls and `editor.showFoldingControls` modes remain unchanged. Include cases where multiple ranges share an ending line and where one range ends as another begins.
- **Behavior:**

  > An expanded folding range exposes an interactive control at its ending line, allowing the user to collapse the same range without scrolling back to its start. Existing start-line folding controls and their visibility modes continue to behave as before. End controls must have deterministic behavior when multiple folding ranges share an ending line or when one range ends on the line where another begins. The feature's default visibility must follow the maintainer-approved product decision.
- **Trace:**

  > Current folding decorations in src/vs/editor/contrib/folding/browser/foldingDecorations.ts use `firstLineDecorationClassName`; IModelDecorationOptions and ModelDecorationOptions in src/vs/editor/common/model.ts and src/vs/editor/common/model/textModel.ts have no final-line counterpart, and LinesDecorations in src/vs/editor/browser/viewParts/linesDecorations/linesDecorations.ts renders only the start-line-specific class. FoldingController.onEditorMouseUp in src/vs/editor/contrib/folding/browser/folding.ts accepts a gutter click but toggles only when the selected region starts on that line. The closed https://github.com/microsoft/vscode/pull/77363 explored this feature, and the maintainer's closing comment recommended a fresh implementation based on a last-line decoration facility. Preserve existing start-control, collapsed-range, keyboard-command, and folding-provider behavior; the uncertainty begins at default enablement and endpoint collision semantics.
- **Open decisions:**
  - Should end-of-range controls appear by default wherever start controls appear, or require an opt-in editor setting?
  - When multiple folding ranges end on the same line, which range should the end control collapse?
  - When one range ends on the same line another range begins, should the gutter prioritize the ending control, the starting control, or expose both behaviors?
