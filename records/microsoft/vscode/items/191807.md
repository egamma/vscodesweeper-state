# Issue #191807 — Settings UI doesn't respect custom `title` for extension configuration option

[https://github.com/microsoft/vscode/issues/191807](https://github.com/microsoft/vscode/issues/191807)

## Summary

Keep open: extension authors still cannot independently control setting labels and category text without changing configuration keys. This issue is already the maintainer-designated consolidation point for that capability.

## Change summary

Allow extension-contributed settings to override generated display names and categories while preserving their configuration keys and stored values.

## Best solution

Define a supported configuration-metadata contract for custom setting and category labels, then carry it through the preferences model into the Settings editor. Preserve existing generated labels when overrides are absent and keep configuration identifiers unchanged.

## Vision fit

- **Fit:** aligned
- **Reason:** Separating presentation from stable configuration identifiers improves extension authoring and Settings UI fidelity without requiring configuration migrations.
- **Evidence:** Durable themes: extension ecosystem API hygiene and workbench settings fidelity; value: simple, uniform UI and UI interactions.

- **Behavior:**

  > Extension authors need to customize the displayed setting name and category without renaming configuration keys or migrating stored values. Custom spelling must survive the Settings editor's automatic word splitting. A setting-name override must support retaining its existing category, as requested in the discussion. Settings without overrides must retain their current presentation, identifiers, and values.
- **Trace:**

  > DefaultSettings.parseSetting() in src/vs/workbench/services/preferences/common/preferencesModels.ts omits ISetting.title from the parsed property. SettingsTreeSettingElement.initLabels() in src/vs/workbench/contrib/preferences/browser/settingsTreeModels.ts already recognizes internal title/categoryLabel metadata, but otherwise generates both labels through settingKeyToDisplayFormat(). The extension contribution schema documents configuration.title as a category subheading, not the requested per-setting presentation contract. The uncertainty is which public metadata fields and category-fallback semantics to expose, rather than whether configuration identifiers should change: they must remain stable. Existing grouping and ordering are not substitutes; maintainers explicitly consolidated the remaining custom-title work here from https://github.com/microsoft/vscode/issues/51778 and https://github.com/microsoft/vscode/issues/150891. No execution or checkout modifications were performed.
- **Open decisions:**
  - Should the public per-setting display-name override use the existing JSON Schema title field or a distinct VS Code-specific field, such as the customSettingTitle name raised in the discussion?
  - What public category-label contract should accompany the setting-name override, including whether an omitted category override retains the generated category and whether an explicitly empty category suppresses it?
