# Issue #291004 — MCP Resources Not Accessible to AI Agents - Breaking Intended Use Cases

[https://github.com/microsoft/vscode/issues/291004](https://github.com/microsoft/vscode/issues/291004)

## Summary

Keep open: the local Chat tool-registration path still does not expose general MCP resource discovery and reading to agents. Current main has programmatic resource forwarding through the MCP gateway, so the original UI-only description needs qualification, but that does not establish that the reported workflow is supported.

## Change summary

Let agents discover and read MCP resources during task execution without manual attachment or duplicated tool descriptions.

## Best solution

Provide a supported agent-facing resource-access contract that reuses existing MCP resource operations while preserving server enablement and user control. Decide whether this should be on-demand discovery and reading or explicitly configured context inclusion; existing manual attachment does not satisfy autonomous catalog lookup.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts`, `src/vs/workbench/contrib/mcp/common/mcpGatewayToolBrokerChannel.ts`, `src/vs/platform/mcp/node/mcpGatewayService.ts`, `src/vs/workbench/contrib/mcp/browser/mcpResourceQuickAccess.ts`
- **Validation:** Use an MCP fixture advertising resources with a catalog://list text resource and a separate query tool whose description omits catalog contents. In the intended Chat agent surface, ask which datasets are available and verify the agent obtains the catalog without manual attachment; confirm disabled servers remain unavailable and existing manual resource attachment still works.
- **Behavior:**

  > An MCP server can expose a dataset catalog or API schema as a resource without copying its contents into tool descriptions. During an agent task, the resource should be available through a supported discovery/read mechanism or an explicitly configured context-inclusion mechanism, without per-request manual attachment. Acceptance should exercise catalog://list with catalog information absent from tool descriptions and verify that the answer uses the resource contents. Existing user-directed attachments and server enablement controls must retain their behavior.
- **Trace:**

  > McpLanguageModelToolContribution._syncTools in src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts exposes server.tools but does not generate generic resource operations. McpResourceQuickAccess in src/vs/workbench/contrib/mcp/browser/mcpResourceQuickAccess.ts supports selecting resources and converting them into chat attachments. Current main also has listResourcesForServer/readResourceForServer in McpGatewayToolBrokerChannel, forwarded by src/vs/platform/mcp/node/mcpGatewayService.ts, so the report's original claim that resource methods are called only by UI code is no longer fully accurate. The remaining investigation must establish which agent surfaces consume that gateway resource capability and which still lack discovery/read access. https://github.com/microsoft/vscode/issues/251747 supplies related context-inclusion design discussion, including concerns about enumerating all resources on every request, but does not settle the on-demand access contract. Preserve existing attachment behavior and disabled-server boundaries; prompt auto-attachment and tool-result resource rendering are separate concerns unless explicitly included in the agreed scope.
- **Open decisions:**
  - Should agents receive on-demand resource discovery/read access, explicitly configured resource context inclusion, or both?
  - What user opt-in or approval behavior should govern agent resource discovery and reading?

## Evidence

- **Current agent-tool registration:** src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts, McpLanguageModelToolContribution._syncTools, registers model-visible entries from server.tools. This path does not synthesize general resources/list or resources/read tools from a server's resource capability.
- **Existing capability and its limit:** The existing command workbench.mcp.browseResources is registered through McpBrowseResourcesCommand. src/vs/workbench/contrib/mcp/browser/mcpResourceQuickAccess.ts converts selected resources into chat attachments through toAttachment and _resourceToAttachment; this is user-directed context inclusion, not autonomous discovery.
- **Programmatic infrastructure now exists:** src/vs/workbench/contrib/mcp/common/mcpGatewayToolBrokerChannel.ts implements listResourcesForServer and readResourceForServer, and src/vs/platform/mcp/node/mcpGatewayService.ts forwards them through listResources and readResource callbacks. Resource APIs therefore are not exclusively UI-only on current main, but forwarding alone does not prove agent-callable access in the local Chat workflow.
- **Maintainer-linked related request:** https://github.com/microsoft/vscode/issues/251747 is open and older, but requests automatic attachment of MCP prompts/resources as instructions rather than the same observable inability to discover and read resources on demand. Its discussion also cautions against enumerating every server's resources on every request: https://github.com/microsoft/vscode/issues/251747#issuecomment-2985931277. It is related design context, not a verified duplicate under the re-review bar.
- **Other resource reports are distinct:** https://github.com/microsoft/vscode/issues/313710 concerns inaccessible resource URIs returned by tool calls and is newer than this report. https://github.com/microsoft/vscode/issues/251725 concerns multiple contents in resources/read responses. https://github.com/microsoft/vscode/issues/340232 concerns preserving embedded-resource and resource-link presentation through Agent Host. None establishes an older canonical owning this report's same symptom.
