# Issue #162126 — Code action widget accessibility strangeness

[https://github.com/microsoft/vscode/issues/162126](https://github.com/microsoft/vscode/issues/162126)

## Summary

The central UX gap remains on current main: intentional pointer movement changes the action list's focused item, and Enter accepts that item rather than preserving the keyboard-selected action. The Backlog placement and maintainer agreement support keeping this accessibility polish open.

## Change summary

Decouple mouse hover from keyboard focus in the code action widget so pointer movement does not change which action Enter accepts.

## Best solution

Align the code action widget with Quick Open by maintaining independent hover and keyboard-focus states: pointer movement may provide hover feedback, while Enter continues to accept the item selected through keyboard navigation unless the user clicks.

## Plan brief

- **Likely files:** `src/vs/platform/actionWidget/browser/actionList.ts`, `src/vs/platform/actionWidget/browser/actionWidget.css`, `src/vs/platform/actionWidget/test/browser/actionList.test.ts`
- **Validation:** Update the ActionListWidget browser tests to establish keyboard focus on one row, move the pointer over another row, invoke `acceptSelected()`, and assert that the keyboard-focused action is accepted while pointer hover feedback remains available; verify click activation and existing keyboard-navigation tests remain unchanged.
- **Behavior:**

  > In a code action menu, moving the pointer over another action must not change the action selected by keyboard navigation. Pressing Enter accepts the keyboard-selected action; clicking accepts the clicked action. Pointer hover may still provide visual feedback, and arrow-key navigation continues to update the keyboard selection. The resulting interaction should match the established Quick Open distinction between hover and keyboard focus.
- **Trace:**

  > ActionListWidget in src/vs/platform/actionWidget/browser/actionList.ts currently has one focused index for both pointer hover and keyboard navigation: `onListHover` calls `_list.setFocus`, and `acceptSelected` executes that index. src/vs/platform/actionWidget/browser/actionWidget.css visually distinguishes mouse navigation by hiding the normal outline, but it does not separate the underlying state. Existing tests in src/vs/platform/actionWidget/test/browser/actionList.test.ts explicitly cover stationary-pointer suppression, pointer-driven focus, keyboard-only outlines, click selection, and acceptance. Preserve click activation, arrow-key navigation, high-contrast focus indication, submenu hover behavior, and stationary-pointer protection; the uncertainty is whether decoupling should be the shared action-widget contract or a code-action-specific mode.
- **Open decisions:**
  - Should pointer hover remain separate from keyboard focus for every ActionListWidget consumer, or only for the code action widget?
  - When no keyboard navigation has occurred, should Enter follow the initially focused action even after pointer movement, or may hover establish the initial active action?

## Evidence

- **current source behavior:** src/vs/platform/actionWidget/browser/actionList.ts:3127-3155 handles pointer hover by calling `_list.setFocus(focus)`, while `acceptSelected` at lines 2280-2292 accepts the currently focused index. Thus moving the pointer can still determine what Enter executes.
- **current test contract:** src/vs/platform/actionWidget/test/browser/actionList.test.ts includes `pointer movement enables hover on the initial row and subsequent rows`, which asserts that mouse movement changes `getFocusedElement()`; the neighboring stationary-pointer test only prevents accidental focus theft before actual pointer movement.
