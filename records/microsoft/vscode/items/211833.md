# Issue #211833 — Merge editor: expose commands for "accept left/right/combination" for current selection

[https://github.com/microsoft/vscode/issues/211833](https://github.com/microsoft/vscode/issues/211833)

## Summary

The left/right toggle commands already exist, as the discussion notes, but there is still no dedicated command to accept a combination for the active conflict. Keep this accepted Backlog request open for that remaining keyboard-access gap.

## Change summary

Expose keyboard-bindable commands to accept either input or an automatic combination for the active merge conflict.

## Best solution

Provide keyboard access to the active conflict's Accept Combination behavior without affecting other conflicts. Retain the existing left/right toggle commands and settle how keyboard users select the input order when combination order matters.

- **Trace:**

  > ToggleActiveConflictInput1 and ToggleActiveConflictInput2 in browser/commands/commands.ts delegate to MergeEditorViewModel.toggleActiveConflict in browser/view/viewModel.ts, which resolves activeModifiedBaseRange from the focused editor's cursor or an explicitly selected range. ModifiedBaseRangeState.toggle in browser/model/modifiedBaseRange.ts inverts inclusion, so sequential toggles are state-dependent even though they enable smart combination. ActionsSource.getItemsInput in browser/view/conflictActions.ts already implements the widget's Accept Combination behavior and exposes input ordering when isOrderRelevant; mergeEditor.acceptAllCombination operates over all ranges instead. Inspection found no registered active-conflict combination command. Preserve combination eligibility, existing merge algorithms, toggle semantics, bulk actions, and unrelated conflicts. The uncertainty is the public keyboard contract for selecting combination order, not where to place the implementation. https://github.com/microsoft/vscode/issues/247401 supplies related accessibility demand but is newer and is not a duplicate canonical for this issue.
- **Open decisions:**
  - For order-sensitive combinations, should keyboard users have explicit input-1-first and input-2-first actions, or should one action select its ordering from the focused input or a documented default?
