# Issue #339755 — Git: staging a file with unsaved edits silently stages stale on-disk content (commit/stash already prompt to save)

[https://github.com/microsoft/vscode/issues/339755](https://github.com/microsoft/vscode/issues/339755)

## Summary

The whole-file staging path still reads disk content without checking unsaved documents. Keep this as a request for a staging safeguard: existing commit/stash settings do not cover it, and the older autosave report covers only part of the requested behavior.

## Change summary

Offer an explicit save-or-proceed choice before whole-file staging when the targeted files have unsaved edits.

## Best solution

Have the Git area owner reconsider a configurable staging warning alongside the existing commit/stash safeguards, while preserving intentional disk-only staging and buffer-based partial staging. Coordinate the focus-change autosave case with https://github.com/microsoft/vscode/issues/171039 without folding this broader request into it.

- **Behavior:**

  > Whole-file staging can currently stage saved content that differs from the visible unsaved editor buffer without warning. The requested safeguard offers an explicit choice before staging, rather than silently saving. Acceptance must distinguish saving and staging the current buffer, intentionally staging disk content, and cancelling without changing the index. Focus-change autosave must not leave the staged result contrary to the chosen action. Partial staging must continue to include only the selected changes.
- **Trace:**

  > CommandCenter.stage, stageFile, and the whole-file stage-all variants in extensions/git/src/commands.ts call Repository.add, which ultimately invokes disk-based git add in extensions/git/src/git.ts. smartCommit and the stash flow independently inspect dirty documents and offer save prompts; their configuration does not apply to staging. In contrast, stageSelectedChanges calls _stageChanges and Repository.stage using content constructed from the editor buffer, so the report's proposed all-paths equivalence is inaccurate. Preserve that partial-staging distinction and existing commit/stash behavior; Repository.add also serves internal commit operations, not only user staging commands. The unresolved boundary is product policy for a new staging warning, including its default and target-document scope. https://github.com/microsoft/vscode/issues/22294 records an earlier decline, while https://github.com/microsoft/vscode/issues/171039 tracks a narrower focus-change autosave symptom. Source inspection confirms the whole-file disk path, but does not establish the reported autosave event ordering.
- **Open decisions:**
  - Should whole-file staging gain an unsaved-document warning, revisiting the earlier decision, and should it be enabled by default or opt-in?
  - Should the warning inspect only files targeted by the staging action, and what would an optional staged mode mean for a file not yet in the index?
