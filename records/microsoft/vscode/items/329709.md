# Issue #329709 — Drag Files from VS Code File Explorer to External Applications

[https://github.com/microsoft/vscode/issues/329709](https://github.com/microsoft/vscode/issues/329709)

## Summary

VS Code already exposes files dragged from the Explorer to the OS drag-and-drop surface via the HTML5 DownloadURL mechanism, so the core ask is shipped behavior with known, API-inherent limits — proposing an as-designed close rather than tracking as an open feature request.

## Change summary

Request to let users drag a file from the Explorer out to external applications (browser upload, Windows Explorer/Desktop, chat/email clients).

## Best solution

Keep the existing DownloadURL-based drag-out support (src/vs/workbench/browser/dnd.ts, fillEditorsDragData) as the shipped behavior; if reporters find it doesn't fire from the Explorer tree specifically, that would be a narrower, separately-reproducible bug, not this broad request.

- **Proposed comment:**

  > Thanks for the suggestion, and to manishScripts for looking into the mechanism. VS Code already supports this: when you drag a file from the Explorer, `fillEditorsDragData` (src/vs/workbench/browser/dnd.ts) sets the HTML5 `DownloadURL` data-transfer type for the dragged file, which is the same Chromium mechanism used to drag a browser tab/attachment out to the OS (Explorer, desktop, or another Chromium/Electron-based app). It currently only covers a single `file:` resource per drag, which is a limitation of that browser API rather than something VS Code chose not to support. If you're seeing it not work at all from the Explorer tree in a recent build, please open a focused bug with exact repro steps (target app, OS) so we can look at that specifically.

## Evidence

- **existing DownloadURL support:** src/vs/workbench/browser/dnd.ts:244-255 sets `event.dataTransfer.setData(DataTransfers.DOWNLOAD_URL, ...)` for a single `file:` resource with the comment 'enables support to drag a tab as file to desktop'.
- **wired up from the Explorer tree:** src/vs/workbench/contrib/files/browser/views/explorerViewer.ts:1772 calls `fillEditorsDragData(accessor, items, originalEvent)` from `FileDragAndDrop.onDragStart`, so Explorer tree drags go through the same DownloadURL-setting code path as editor tab drags.
- **documented limitations:** The code comment states the requirements explicitly: 'Chrome/Edge only', 'only a single file is supported', 'only file:/ resources are supported' — these are inherent to the underlying Chromium/HTML5 drag API VS Code (Electron) is built on, not a missing feature.
