# Issue #179018 — Support keybindings with > 2 chords in "Define keybinding" widget

[https://github.com/microsoft/vscode/issues/179018](https://github.com/microsoft/vscode/issues/179018)

## Summary

The requested capability is still missing: the recording widget explicitly resets after two chords, although the JSON parser accepts longer sequences. Keep this team-authored, accepted request open; no qualifying canonical duplicate or completed fix was found.

## Change summary

Allow the Define Keybinding widget to record and save keybindings containing more than two chords.

## Best solution

Bring the graphical keybinding recorder into parity with keybindings.json so users can enter longer sequences and confirm them with Enter. Preserve cancellation and incomplete-modifier handling, and settle how users restart a recording without disrupting the shared shortcut-search recorder.

- **Behavior:**

  > Users can define shortcuts containing more than two chords through the Define Keybinding widget instead of editing JSON manually. Recording successive complete chords must retain the intended full sequence until confirmation, and Enter must save that sequence. Existing single- and two-chord shortcuts, modifier entry, cancellation, and reopening remain usable. Acceptance includes both graphical keybinding definition entry points and the agreed behavior of the shared shortcut-search recorder.
- **Trace:**

  > KeybindingsSearchWidget.printKeybinding in src/vs/workbench/contrib/preferences/browser/keybindingWidgets.ts explicitly clears its chord array at length two, causing the third complete chord to replace the sequence. DefineKeybindingWidget uses that recorder, but its output rendering and getUserSettingsLabel already iterate over arbitrary chord arrays. The JSON path in src/vs/workbench/services/keybinding/common/keybindingIO.ts delegates to KeybindingParser.parseKeybinding in src/vs/base/common/keybindingParser.ts, which accepts successive chords until input is exhausted. src/vs/workbench/contrib/preferences/browser/keybindingsEditor.ts shares the recorder between shortcut search and definition; keybindingsEditorContribution.ts supplies the JSON editor overlay. Preserve runtime keybinding parsing and dispatch semantics; the request concerns recording UI, not a new shortcut format. The unresolved boundary is the user-visible replacement for two-chord rollover and whether search recording should follow the same interaction.
- **Open decisions:**
  - When recording no longer rolls over after two chords, how should users restart a sequence: through the existing Escape-to-clear interaction alone or an additional explicit interaction?
  - Should shortcut-search recording accumulate longer sequences with the same semantics as Define Keybinding, or preserve its current two-chord rollover?

## Evidence

- **Current recording limit:** In src/vs/workbench/contrib/preferences/browser/keybindingWidgets.ts, KeybindingsSearchWidget.printKeybinding resets this._chords when its length equals 2 before appending the next complete chord. The source explicitly marks this as a temporary two-chord limit.
- **Existing-capability check:** src/vs/base/common/keybindingParser.ts parses chords in a while loop until the input is exhausted; src/vs/workbench/services/keybinding/common/keybindingIO.ts uses that parser for user keybindings. Manual JSON therefore covers longer sequences, but not the requested graphical entry workflow. The registered editor.action.defineKeybinding command and graphical keybindings editor both reach DefineKeybindingWidget and its limited recorder.

DefineKeybindingWidget already renders all recorded chords in a loop and joins their settings labels; Enter confirms, while Escape clears or hides. Changing recording semantics therefore needs to account for both definition and search.
