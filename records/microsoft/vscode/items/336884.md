# Issue #336884 — Agents: Add comment to session content as context for the next turn, and let Send fork the session

[https://github.com/microsoft/vscode/issues/336884](https://github.com/microsoft/vscode/issues/336884)

## Summary

This remains a real Agents Window feature gap: current main can ask a side question or quote selected response text, and can fork at a checkpoint, but it cannot collect anchored response comments for the next request or combine the current draft with a fork operation. Related open issues cover narrower fork behavior, not this same observable workflow, so the re-reviewed item should remain open.

## Change summary

Let users attach multiple comments to selected assistant-response ranges for the next request and optionally send that request in a fork of the current conversation.

## Best solution

Provide a capability-gated response-comment draft associated with the current chat and source turn, carry its structured quoted context into the next successful request, and add a Send-menu action that sends the existing draft into a fork at the current turn. Preserve ordinary Send and the existing immediate side-question flow.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/chat/browser/responseSelectionSideChatController.ts`, `src/vs/sessions/contrib/chat/browser/chatView.ts`, `src/vs/sessions/services/sessions/common/session.ts`, `src/vs/sessions/services/sessions/common/sessionsManagement.ts`, `src/vs/sessions/contrib/chat/browser/sessionsChatAccessibilityHelp.ts`, `src/vs/sessions/contrib/chat/test/browser/responseSelectionSideChatController.test.ts`, `src/vs/sessions/contrib/chat/test/browser/sessionsChatAccessibilityHelp.test.ts`
- **Validation:** Add focused Sessions chat tests proving that multiple selected-response comments remain independently anchored, are included exactly once in the next successful request, and that the alternate send forks at the current turn while preserving the draft and attachments; retain tests for Ask in a Side Chat, Quote, ordinary Send, keyboard operation, and accessibility-help content.
- **Behavior:**

  > Selecting assistant-response text should offer an Add Comment action alongside the existing side-question and quote actions. Users can collect multiple comments, review which response excerpt each belongs to, and have all of them supplied as context on the next successful request without manually reconstructing quotes. Ordinary Send continues the current conversation; a separate Send-menu action sends the same draft and attachments into a fork rooted at the current turn. Existing Ask in a Side Chat, Quote, Copy, and explicit checkpoint-fork behavior must remain unchanged and keyboard accessible.
- **Trace:**

  > ResponseSelectionSideChatController in src/vs/sessions/contrib/chat/browser/responseSelectionSideChatController.ts owns the selected-response affordance and currently either sends a side chat immediately or inserts an unstructured blockquote. Session forking is routed through ISessionsManagementService.forkChatInSession and provider capabilities, while ForkConversationAction in src/vs/workbench/contrib/chat/browser/actions/chatForkActions.ts supplies the existing checkpoint gesture. The generic Send to New Chat command in chatExecuteActions.ts starts a clean conversation rather than invoking the fork contract. AgentFeedbackAttachmentContribution is useful precedent for carrying draft comments into one request, but its file/range model must not be reused as though rendered response text were a workspace file. Keep provider-specific transport behind the existing Sessions management/provider boundary, and update the existing Sessions chat accessibility help when the new actions and shortcut behavior are settled. Related issues https://github.com/microsoft/vscode/issues/323732 and https://github.com/microsoft/vscode/issues/296370 are narrower and do not absorb this request.
- **Open decisions:**
  - Are response comments transient draft context cleared after the next successful send, or persistent session annotations that survive navigation and reload?
  - When a provider supports multiple chats, should the alternate send create a peer chat inside the same session, or must it always create a separate top-level session as the issue requests?
  - Should fork-on-send receive a default keybinding, and if so should it follow the existing Send to New Chat binding or introduce the proposed Ctrl/Cmd+Alt+Enter behavior?

## Evidence

- **current selection actions:** src/vs/sessions/contrib/chat/browser/responseSelectionSideChatController.ts registers only Ask in a Side Chat, Quote, and Copy. Ask immediately calls createAndSendSideChat with the selected text, while Quote inserts a plain blockquote into the composer; neither stores multiple comments anchored to response ranges.
- **current fork path:** src/vs/workbench/contrib/chat/browser/actions/chatForkActions.ts implements Fork Conversation from a selected request/checkpoint, and src/vs/sessions/services/sessions/common/sessionsManagement.ts exposes forkChatInSession(session, sourceChat, turnId). There is no path that combines the current composer draft and attachments with that fork operation.
- **existing send alternative is not a fork:** SendToNewChatAction in src/vs/workbench/contrib/chat/browser/actions/chatExecuteActions.ts clears the current input, creates a new chat session, and resubmits the text; it does not seed the new conversation with history through the fork contract.
- **related issue:** https://github.com/microsoft/vscode/issues/323732 is older and open but asks only for access to Fork Conversation after the latest response; it does not request anchored comments or sending the current draft into the fork, so it does not meet the re-review duplicate bar.
- **related context request:** https://github.com/microsoft/vscode/issues/296370 is older and open but concerns preserving session memory during existing fork/new-chat operations. It does not describe the same response-comment and fork-on-send interaction.
- **existing analogous infrastructure:** src/vs/sessions/contrib/agentFeedback/browser/agentFeedbackAttachment.ts carries accepted file feedback into the next request and clears it after submission, but its model is tied to file URIs and editor ranges rather than assistant-response turns and rendered-text ranges.
