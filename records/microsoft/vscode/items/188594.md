# Issue #188594 — [themes] support non-HEX formats in color customizations

[https://github.com/microsoft/vscode/issues/188594](https://github.com/microsoft/vscode/issues/188594)

## Summary

A real gap remains on current main: theme customizations are still validated and parsed as hexadecimal colors only. The request is accepted in the Backlog and no older issue owns the same observable requirement, so it should remain open pending a decision on the supported color syntax.

## Change summary

Allow workbench and editor color customizations to use named, HSL/HSV, Lab/LCH, and other non-hex color formats.

## Best solution

Define a stable set of non-hex color syntaxes for theme customizations and support them consistently in schema validation, workbench colors, token colors, and semantic-token colors while preserving the existing internal color representation.

## Plan brief

- **Likely files:** `src/vs/base/common/color.ts`, `src/vs/base/test/common/color.test.ts`, `src/vs/workbench/services/themes/common/colorThemeData.ts`, `src/vs/platform/theme/common/colorUtils.ts`, `src/vs/workbench/services/preferences/common/preferencesValidation.ts`
- **Validation:** Add targeted parser and theme-service tests named around non-hex color customizations, then run `scripts/test.sh --grep "non-hex color customizations"`; cover each approved syntax, alpha handling, invalid input, and unchanged hex behavior.
- **Behavior:**

  > Theme color customization values may use the non-hex formats explicitly approved by the maintainer, and each resolves to the same rendered color as its equivalent hexadecimal value. Settings validation and runtime parsing must agree about which formats are accepted. Existing #RGB, #RGBA, #RRGGBB, and #RRGGBBAA values remain unchanged, while invalid values continue to produce clear validation rather than silently selecting an unrelated color.
- **Trace:**

  > Workbench overrides flow through ColorThemeData.setCustomColors and overwriteCustomColors in src/vs/workbench/services/themes/common/colorThemeData.ts, where string values currently call Color.fromHex. The registered schemas use the `color-hex` format in src/vs/platform/theme/common/colorUtils.ts, and preferences validation implements that format with Color.Format.CSS.parseHex in src/vs/workbench/services/preferences/common/preferencesValidation.ts. A broader parser exists at Color.Format.CSS.parse in src/vs/base/common/color.ts, but it currently supports only hex, legacy rgb/rgba, transparent, and named keywords and is not used by this customization path. Keep color references, `default`, theme-scoped overrides, and existing hex serialization behavior unchanged. https://github.com/microsoft/vscode/issues/56855 concerns variables and references, not this literal-format contract.
- **Open decisions:**
  - Which literal formats form the supported public contract: stable CSS color syntaxes only, or also non-CSS formats such as HSV?
  - For wide-gamut Lab/LCH/OKLab/OKLCH values, should VS Code convert and clamp to sRGB or preserve a wider-gamut representation?
  - Should the expanded syntax apply uniformly to workbench, TextMate token, and semantic-token color customizations, or only to `workbench.colorCustomizations`?

## Evidence

- **current source:** src/vs/workbench/services/themes/common/colorThemeData.ts:421-428 passes every string in workbench color customizations to Color.fromHex, so non-hex input is not interpreted as the requested color.
- **validation:** src/vs/platform/theme/common/colorUtils.ts:168-176 registers workbench color settings with format `color-hex`, and src/vs/workbench/services/preferences/common/preferencesValidation.ts:158-160 validates that format exclusively with Color.Format.CSS.parseHex.
- **partial parser capability:** src/vs/base/common/color.ts:670-684 has a separate CSS parser supporting hex, legacy rgb/rgba, transparent, and named keywords, but the theme customization path does not use it and the parser still lacks HSL, HSV, Lab, LCH, OKLab, and OKLCH.
- **related issue:** https://github.com/microsoft/vscode/issues/56855 is older and related, but it tracks reusable variables and references rather than acceptance of non-hex literal color formats; it does not meet the stronger same-symptom duplicate bar for this re-reviewed issue.
- **existing capability check:** Searches of current configuration registration and theme loading found no setting or command that enables non-hex literals in `workbench.colorCustomizations`; the current `themes` and `feature-request` classification remains accurate.
