# Issue #117327 — An extension spamming console.log will take a lot of CPU time in the render process

[https://github.com/microsoft/vscode/issues/117327](https://github.com/microsoft/vscode/issues/117327)

## Summary

The original Java extension trigger was mitigated externally, but the core protection gap remains: current main still serializes, forwards, and renders every extension-host console call without throttling. This team-authored issue should remain open while maintainers define how VS Code preserves useful diagnostics without allowing console spam to freeze the renderer.

## Change summary

Protect the renderer from excessive CPU use and UI freezes when an extension emits a high volume of console messages.

## Best solution

Bound the renderer-side cost of extension-host console forwarding while retaining useful extension diagnostics, with an explicit policy for throttling, coalescing, or dropping excessive output.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostConsoleForwarder.ts`, `src/vs/workbench/api/browser/mainThreadConsole.ts`
- **Validation:** Exercise an extension fixture that rapidly emits thousands of console messages and verify the workbench remains responsive while console output follows the agreed retention policy.
- **Behavior:**

  > An extension emitting sustained or bursty console output must not freeze the VS Code workbench or monopolize the renderer. Ordinary extension errors and diagnostic messages must remain discoverable. Acceptance requires a high-volume console fixture to leave the UI responsive and to exhibit the maintainer-selected retention behavior.
- **Trace:**

  > The issue was reproduced with verbose Java LSP tracing, with approximately 10 seconds of UI freeze; the Java extension later removed its duplicate console logging in https://github.com/redhat-developer/vscode-java/pull/1824. On current main, `AbstractExtHostConsoleForwarder._handleConsoleCall` in src/vs/workbench/api/common/extHostConsoleForwarder.ts serializes every call and sends it through `$logExtensionHostMessage`. `MainThreadConsole.$logExtensionHostMessage` in src/vs/workbench/api/browser/mainThreadConsole.ts then writes every entry to the renderer console without a rate or volume bound. Preserve ordinary diagnostics and extension-development debugging; the scope is protection against excessive output, not suppressing all extension console messages.
- **Open decisions:**
  - When an extension exceeds the safe console-output rate, should VS Code drop excess entries, coalesce them into a summary, or retain them outside the renderer?
  - Should protection use a fixed per-extension limit or a shared extension-host limit, which changes how one noisy extension affects diagnostics from others?

## Evidence

- **confirmed reproduction:** A maintainer reproduced the freeze with `java.trace.server: verbose` and attributed it to intense console usage in https://github.com/microsoft/vscode/issues/117327#issuecomment-789569647; another report measured roughly 10 seconds of UI freeze.
- **current source path:** src/vs/workbench/api/common/extHostConsoleForwarder.ts still calls `safeStringifyArgumentsToArray` and `$logExtensionHostMessage` for every console invocation, with no rate or volume bound.
- **renderer work:** src/vs/workbench/api/browser/mainThreadConsole.ts receives every forwarded entry and calls `log(entry, 'Extension Host')`; the current implementation has no throttling or backpressure for abusive output.
- **trigger mitigation:** https://github.com/redhat-developer/vscode-java/pull/1824 removed duplicate verbose LSP logging to `console.log`, mitigating the reported Java scenario but not the VS Code core failure mode assigned for protection.
- **canonical search:** Repository issue searches found no open canonical report that more broadly owns extension-host console spam causing renderer CPU saturation; https://github.com/microsoft/vscode/issues/103242 concerned opening large Output channels and is closed.
