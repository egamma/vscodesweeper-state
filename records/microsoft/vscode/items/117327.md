# Issue #117327 — An extension spamming console.log will take a lot of CPU time in the render process

[https://github.com/microsoft/vscode/issues/117327](https://github.com/microsoft/vscode/issues/117327)

## Summary

Keep open: maintainers reproduced that high-volume extension-host console logging can block the renderer for seconds. The Java extension removed its duplicate logging, but the issue was explicitly retained to make VS Code resilient to a noisy extension.

## Change summary

Prevent an extension that emits a large volume of console messages from consuming excessive renderer CPU and freezing the workbench.

## Best solution

Bound or batch extension-host console-message delivery and rendering so a noisy extension cannot monopolize the extension-host-to-renderer channel, while preserving useful diagnostics and directing sustained verbose logs to output channels.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostConsoleForwarder.ts`, `src/vs/workbench/api/browser/mainThreadConsole.ts`
- **Validation:** Add an extension-host integration or unit stress test that emits a large burst of console messages and verifies delivery is bounded or batched without blocking a concurrently scheduled renderer-side task, while ordinary console messages still appear.
- **Behavior:**

  > An extension emitting sustained high-volume console output must not make the workbench unresponsive or monopolize renderer CPU. Normal extension console diagnostics must remain available, and the protection must preserve ordering for messages that are retained. Acceptance should include a stress case comparable to verbose Java LSP tracing and a regression check for ordinary extension logs.
- **Trace:**

  > The discussion provides a confirmed reproduction using `java.trace.server: verbose`: the Java language server logged the same high-volume trace to both an output channel and `console`, and maintainers traced the delay through extension-host data delivery into the renderer. The Java-side mitigation in https://github.com/redhat-developer/vscode-java/pull/1824 removes that producer's duplicate console logging, but the maintainer explicitly retained this issue for core protection. The relevant boundary is extension-host console forwarding into the browser workbench, likely `ExtHostConsoleForwarder` in `src/vs/workbench/api/common/extHostConsoleForwarder.ts` and `MainThreadConsole` in `src/vs/workbench/api/browser/mainThreadConsole.ts`; output-channel behavior and ordinary diagnostic visibility must not regress. The uncertainty starts at the overload policy and whether protection belongs at serialization, IPC transport, renderer consumption, or multiple stages.
- **Open decisions:**
  - Should overload protection batch messages, rate-limit them, drop excess messages with a summary, or apply transport backpressure?
  - At which boundary should protection live: extension-host serialization, IPC delivery, renderer-side console handling, or a coordinated combination?
  - What ordering and retention guarantees must remain for ordinary extension console diagnostics?
