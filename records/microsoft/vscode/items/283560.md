# Issue #283560 — "Chat took too long to get ready" - Remote setups (WSL, Dev Containers, Remote SSH)

[https://github.com/microsoft/vscode/issues/283560](https://github.com/microsoft/vscode/issues/283560)

## Summary

Keep this open as the canonical tracking issue for remote Copilot Chat failures caused by inheriting an unreachable host-side loopback proxy. Multiple reporters and a maintainer confirmed the root cause and workarounds, while current main retains the proxy-inheritance behavior and no fixing PR is linked.

## Change summary

Copilot Chat fails to become ready in WSL, Dev Containers, and Remote SSH when the remote extension host inherits a host proxy bound to localhost.

## Best solution

Remote extension hosts should avoid silently inheriting an unusable loopback proxy, or present an actionable diagnostic that identifies the inherited proxy and the appropriate remote setting. The behavior should be consistent across WSL, Dev Containers, and Remote SSH without disrupting reachable host proxies.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts`, `src/vs/platform/request/common/request.ts`, `src/vs/workbench/api/node/proxyResolver.ts`, `extensions/vscode-api-tests/src/singlefolder-tests/proxy.test.ts`
- **Validation:** Exercise WSL, Dev Container, and Remote SSH configurations where the local proxy is bound to 127.0.0.1: Chat must either connect through a valid remote-reachable proxy or report the inherited loopback proxy with an actionable recovery path; existing reachable-proxy and explicitly configured remote-proxy scenarios must continue to pass.
- **Behavior:**

  > When a remote extension host inherits a local proxy address that is unreachable from the remote environment, Copilot Chat must not remain in the generic "Chat took too long to get ready" state. The user should either receive working proxy connectivity or a diagnostic that identifies the remote/local proxy mismatch and an actionable setting. Explicit remote proxy configurations and host proxies that are reachable from the remote must continue to work across WSL, Dev Containers, and Remote SSH.
- **Trace:**

  > The issue thread confirms that `127.0.0.1` names the remote environment in WSL rather than the Windows host, while the inherited proxy listens only on the host; mirrored networking or disabling `HTTP > Use Local Proxy Configuration` resolves the failure. In current main, NativeExtensionService in src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts reads `http.useLocalProxyConfiguration` and calls `updateProxyConfigurationsScope`; src/vs/platform/request/common/request.ts then scopes the proxy configuration as application-wide when host-proxy inheritance is enabled. Proxy resolution for extension-host requests continues through src/vs/workbench/api/node/proxyResolver.ts. This issue is the maintainer-designated canonical tracker, with https://github.com/microsoft/vscode/issues/283832 and https://github.com/microsoft/vscode/issues/284921 already consolidated into it. Preserve explicit remote proxy settings and reachable inherited proxies; unrelated authentication and service failures that produce the same generic Chat message are outside this issue's boundary.
- **Open decisions:**
  - When an inherited loopback proxy is unreachable remotely, should VS Code decline that inherited proxy automatically or preserve it and present an actionable blocking diagnostic?
  - Should the selected behavior be uniform across WSL, Dev Containers, and Remote SSH, or may remote providers define different handling based on whether host loopback forwarding is available?

## Evidence

- **confirmed root cause:** A maintainer confirmed at https://github.com/microsoft/vscode/issues/283560#issuecomment-3693863046 that 127.0.0.1 resolves to the remote environment rather than the Windows host, making the inherited host-side proxy unreachable.
- **confirmed reproductions:** Reporters reproduced the failure in WSL with Docker and in a macOS Dev Container; mirrored WSL networking or correcting the container proxy restored Chat, as recorded at https://github.com/microsoft/vscode/issues/283560#issuecomment-3690142259 and https://github.com/microsoft/vscode/issues/283560#issuecomment-3691466985.
- **canonical tracking decision:** A maintainer explicitly designated this as the tracking issue for proxy settings not being applied correctly on the remote side at https://github.com/microsoft/vscode/issues/283560#issuecomment-3693106119; https://github.com/microsoft/vscode/issues/283832 and https://github.com/microsoft/vscode/issues/284921 were subsequently closed as duplicates of it.
- **current source:** src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts reads `http.useLocalProxyConfiguration` and passes it to `updateProxyConfigurationsScope`; src/vs/platform/request/common/request.ts still defaults the setting from `remoteEnv.useHostProxy` and gives inherited proxy settings application scope. The existing workaround remains disabling `http.useLocalProxyConfiguration` in remote settings and configuring `http.proxy` there.
