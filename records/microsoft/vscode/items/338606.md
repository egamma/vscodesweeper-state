# Issue #338606 — [chat] Renderer crashes with -36861 while restoring large Copilot editing session

[https://github.com/microsoft/vscode/issues/338606](https://github.com/microsoft/vscode/issues/338606)

## Summary

Fresh but unusually well-diagnosed report: traced on current main that ChatEditingSession._initEntries eagerly restores every persisted snapshot entry (creating a text model per file) with no size/count budget, matching the reporter's -36861 renderer crash on a ~573 MiB / 564-file editing session. Routing to the chat area rather than closing; single report so far and no independent confirmation.

## Change summary

Restoring a very large persisted Copilot chat editing session (hundreds of MB, hundreds of files) eagerly creates a text model for every entry and can crash/OOM the renderer.

## Best solution

Bound the restore path in ChatEditingSession._initEntries (src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts) with a size/count budget and lazy hydration of older entries, with a recoverable fallback when the budget is exceeded — as the reporter's 'Proposed direction' suggests.

## Plan brief

- **Validation:** A test restoring a synthetic large chat editing session (many entries / large content) that asserts restore stays within a bounded memory/model-count budget instead of creating a model per entry.
- **Behavior:**

  > Restoring a Copilot chat session with a very large persisted editing state (hundreds of MB, hundreds of files) must not crash or OOM the renderer. Restore should apply a size/count budget, load a bounded initial set eagerly, and hydrate the remainder on demand or offer an explicit recovery/read-only fallback when the budget is exceeded.
- **Trace:**

  > ChatEditingSession._initEntries (src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts, ~lines 981-1019) loops over every snapshotEntry in the restored state and unconditionally calls _getOrCreateModifiedFileEntry / restoreFromSnapshot, which creates a text model per file via createTextModel — no cap on count or aggregate size exists on this path today. The boundary: do not change the streaming-edit accept path (_getOrCreateModifiedFileEntry's other callers around lines 265-1032) or normal small-session restore behavior — only the bulk restore loop in _initEntries needs bounding. Where uncertainty starts: what the budget should be, whether older/excess entries are lazily hydrated on access or need an explicit user action, and what the degraded/fallback UI looks like.
- **Open decisions:**
  - What size/count threshold triggers bounded restore instead of full eager restore?
  - Are excess entries hydrated lazily on first access, or does the user need to explicitly opt into loading them?
  - What does the user see when the budget is exceeded — a silent partial restore, a warning banner, or a read-only fallback?
