# Issue #125643 — Web: provide a `workbench.web.api.d.ts` for an embedder to develop against

[https://github.com/microsoft/vscode/issues/125643](https://github.com/microsoft/vscode/issues/125643)

## Summary

The declaration artifact requested by embedders is still absent on current main, while the internal embedder API continues to evolve. The On Deck milestone and maintainer discussion establish this as accepted work, but its public contract and build/distribution design still need planning.

## Change summary

Provide a supported TypeScript declaration artifact for external embedders of the VS Code web workbench.

## Best solution

Publish a stable, documented declaration for the supported web embedder surface and continuously verify that the workbench implementation conforms to it. The declaration should be distributed with the web build through a clearly supported consumption path.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/web.api.ts`, `src/vs/workbench/browser/web.main.ts`, `src/vs/workbench/browser/web.factory.ts`, `build/gulpfile.vscode.web.ts`, `build/lib/compilation.ts`
- **Validation:** Compile a minimal external TypeScript embedder fixture using only the produced web declaration and its published entry point, then run a build-time conformance/freshness check that fails when the implemented IWorkbench or construction options diverge from the declared contract.
- **Behavior:**

  > A web embedder can consume a supported TypeScript declaration without importing VS Code's internal `vs/` source tree. The declaration covers the supported construction options and returned workbench facade, includes usable documentation, and resolves all referenced types for an external TypeScript project. Acceptance requires a minimal external consumer to type-check successfully and an incompatible implementation/API change to fail the repository's conformance check.
- **Trace:**

  > The source contract currently lives in src/vs/workbench/browser/web.api.ts. Workbench.open in src/vs/workbench/browser/web.main.ts constructs the facade with `satisfies IWorkbench`, and src/vs/workbench/browser/web.factory.ts exposes create with IWorkbenchConstructionOptions, so internal implementation conformance exists. The source API imports many types from internal `vs/` modules, which is the boundary a standalone artifact must resolve. The existing Monaco declaration machinery in build/lib/monaco-api.ts and build/lib/compilation.ts demonstrates generation and freshness checking, but the thread's maintainer direction favors a deliberately curated web contract rather than automatically exposing internal types. The boundary is the embedder API: do not broaden unrelated internal modules into supported public API, and do not change runtime embedder behavior as part of producing the declaration.
- **Open decisions:**
  - Which subset of the types currently exported from web.api.ts is the supported stable embedder contract, rather than an incidental internal dependency?
  - What public artifact or package path should embedders depend on, and what compatibility guarantees should that distribution point carry?

## Evidence

- **current source:** src/vs/workbench/browser/web.api.ts still defines IWorkbench, IWorkbenchConstructionOptions, and the related embedder types, but repository search finds no workbench.web.api.d.ts or equivalent external declaration artifact.
- **implementation conformance:** src/vs/workbench/browser/web.main.ts returns an object using `satisfies IWorkbench`, while src/vs/workbench/browser/web.factory.ts accepts IWorkbenchConstructionOptions; current internal code therefore checks the runtime facade against the source interfaces but does not provide embedders a standalone declaration.
- **unresolved declaration graph:** src/vs/workbench/browser/web.api.ts imports public-facing types from numerous internal `vs/` modules, including URI, progress, editor, tunnel, authentication, and terminal types. A consumable declaration must deliberately define or bundle this dependency boundary rather than exposing unresolved internal imports.
- **maintainer direction:** The discussion favors a deliberately curated declaration with compile-time implementation validation; the issue author accepted handpicking the API but identified correctness validation as a remaining requirement.
- **related work:** https://github.com/microsoft/vscode/pull/147728 was closed without merging and concerned construction of the runtime embedder API, not publication of the requested declaration artifact.
- **canonical search:** A repository issue search for the declaration name and embedder TypeScript API found no other open microsoft/vscode issue owning this work; https://github.com/microsoft/vscode/issues/125643 remains the canonical request.
