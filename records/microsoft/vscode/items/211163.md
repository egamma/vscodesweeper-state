# Issue #211163 — Expanding a verbose hover can end up with a non expandable hover

[https://github.com/microsoft/vscode/issues/211163](https://github.com/microsoft/vscode/issues/211163)

## Summary

Keep open under discussion: current source still allows an expanded hover to lose its contraction action. The unresolved question is whether VS Code should preserve hover history or leave reversibility entirely to providers, as the maintainer discussion identifies.

## Change summary

Allow users to return to the previous hover after expansion produces a hover that does not support decreasing verbosity.

## Best solution

Establish the reversibility contract for verbose hovers in the editor hover implementation and proposed API. Resolve the recorded consistency concern before introducing editor-owned history, then make the chosen behavior explicit for provider authors.

- **Behavior:**

  > Expanding a verbose hover can replace it with content that offers no way to return to the previous presentation. The reporter requests preservation of the previous hover, while the maintainer raises consistency concerns when provider results change after the hover is reopened. Acceptance must establish predictable contraction behavior during a visible hover session and an explicit contract for reopening it. Existing providers that supply their own decrease behavior must remain supported.
- **Trace:**

  > HoverSource.supportsVerbosityAction in src/vs/editor/contrib/hover/browser/markdownHoverParticipant.ts reads only the current result's capability flags. MarkdownRenderedHoverParts.updateMarkdownHoverPartVerbosityLevel obtains a replacement through _fetchHover and replaces the rendered part; _fetchHover passes the current hover as previousHover but retains no navigation history. Both rendering and command execution then honor the replacement's flags, explaining the lost contraction path. The proposed API in src/vscode-dts/vscode.proposed.editorHoverVerbosityLevel.d.ts exposes those flags without promising history. The unresolved boundary is ownership of reversibility, not the mechanics of storing earlier results; see https://github.com/microsoft/vscode/issues/211163#issuecomment-2074436937. API finalization at https://github.com/microsoft/vscode/issues/333269 is related but does not resolve this behavior.
- **Open decisions:**
  - Should contraction restore editor-retained previous content even when the replacement hover does not advertise canDecreaseVerbosity, or should providers remain solely responsible for offering a reversible sequence?
  - If contraction uses retained content, is that history explicitly limited to the current visible hover session, allowing a newly opened hover to produce a different sequence?
