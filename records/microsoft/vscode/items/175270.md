# Issue #175270 — FR: Allow extension views to be defined as a fixed height.

[https://github.com/microsoft/vscode/issues/175270](https://github.com/microsoft/vscode/issues/175270)

## Summary

Keep open: contributed views still expose proportional initial sizing, not an option to preserve a user-selected height across container resizes. The existing API/tree-view routing is appropriate, and a maintainer has independently linked a concrete extension use case to this request.

## Change summary

Allow contributed views to retain a preferred fixed height across window or monitor changes, temporarily shrinking when necessary and recovering their preferred height afterward.

## Best solution

Define an opt-in contributed-view sizing contract that preserves the user's chosen height while allowing constrained layouts to remain usable. Keep proportional sizing as the default and settle the public contribution contract and constrained-space behavior before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/api/browser/viewsExtensionPoint.ts`, `src/vs/workbench/common/views.ts`, `src/vs/workbench/browser/parts/views/viewPaneContainer.ts`, `src/vs/base/browser/ui/splitview/paneview.ts`, `src/vs/base/browser/ui/splitview/splitview.ts`
- **Validation:** Use a sample extension with one flexible view and two opted-in views: manually size the latter, enlarge and shrink the container to simulate switching monitors, then constrain it below the preferred total and enlarge it again. Verify preferred heights remain stable when space permits and recover after temporary compression, while non-opted-in views retain proportional behavior. Pin the chosen contract with automated contribution-parsing and pane/split-view layout tests.
- **Behavior:**

  > An extension can opt a contributed view into retaining its preferred height instead of scaling proportionally when the view container changes height. A user-selected height remains stable whenever sufficient space exists. Temporary compression must not discard that preference: expanding the container restores it. Views without the opt-in retain their existing behavior.
- **Trace:**

  > The initialSize contribution in src/vs/workbench/api/browser/viewsExtensionPoint.ts becomes a relative descriptor weight, not an absolute sizing preference. ViewPaneContainer.computeInitialSizes in src/vs/workbench/browser/parts/views/viewPaneContainer.ts distributes available dimensions by those weights; saveViewSizes and restoreViewSizes handle stored sizes. PaneView creates a default-proportional SplitView, whose layout and saveProportions methods redistribute dimensions on container resize. SplitView already has an internal per-view proportionalLayout option, but the contribution path does not expose the requested contract; that internal option alone does not establish recovery of a preferred size after compression. Preserve existing initialSize semantics and default proportional behavior. Downstream demand is documented at https://github.com/microsoft/vscode-pull-request-github/issues/5278#issuecomment-1733338463. The remaining uncertainty is the public opt-in contract and how competing preferred sizes behave when space is insufficient.
- **Open decisions:**
  - Should the contribution declare only a non-proportional sizing mode that preserves the user's chosen height, or also an explicit preferred height supplied by the extension?
  - When multiple opted-in views cannot all retain their preferred heights, should compression be shared among them or follow a defined priority order?
  - Should the opt-in apply only to height in vertically stacked containers, or preserve the layout-axis size when the view moves into a horizontally arranged container?
