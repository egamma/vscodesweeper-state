# Issue #93024 — Minor UI inconsistencies: Input theme references

[https://github.com/microsoft/vscode/issues/93024](https://github.com/microsoft/vscode/issues/93024)

## Summary

The Settings search still mixes generic input foreground/background tokens with the setting-input border token. Keep this open for the maintainer-supported documentation and search-border theming improvements; the existing tokens do not provide independent Settings-search styling.

## Change summary

Clarify setting-input theme token scope and provide a coherent theming contract for the Settings editor search field.

## Best solution

Document that settings.textInput* colors describe setting-value controls, and settle the Settings search field's independent color-token and fallback contract. Preserve consistency with ordinary workbench inputs and deliberate compatibility with existing themes.

- **Behavior:**

  > Theme authors should be able to understand which colors govern setting-value controls and which govern Settings search. Acceptance should cover the agreed search-color scope, unset-token fallbacks, existing theme compatibility and unchanged styling of setting-value controls.
- **Trace:**

  > In src/vs/workbench/contrib/preferences/browser/settingsEditor2.ts, the search widget is SuggestEnabledInputWithHistory with only inputBorder overridden to settingsTextInputBorder. The settings color registry contains no dedicated search colors. The thread establishes that excluding search from setting-value foreground/background colors is intentional, while documentation clarification and reconsidering the border token have maintainer support: https://github.com/microsoft/vscode/issues/93024#issuecomment-2532387149. Do not reinterpret this as a broken setting-value control or change unrelated consumers of the shared input widget. The uncertainty is the public token scope and fallback contract, not where to place the implementation.
- **Open decisions:**
