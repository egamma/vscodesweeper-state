# Issue #332765 — Safari web: .webview-overlay-content height collapses with anchor-size(height)

[https://github.com/microsoft/vscode/issues/332765](https://github.com/microsoft/vscode/issues/332765)

## Summary

Traced conclusively in source: OverlayLayoutElement unconditionally applies CSS Anchor Positioning (`anchor()`/`anchor-size()`/`position-anchor`) with no `@supports` feature check or fallback, so on Safari < 26 (no anchor-positioning support) the overlay wrapper gets no computed size and the webview content collapses/disappears entirely.

## Change summary

The `.webview-overlay-content` host wrapper collapses to zero height in Safari because it relies solely on CSS Anchor Positioning (`anchor-size(height)`), which older Safari doesn't support.

## Best solution

Add a feature-detection fallback in src/vs/base/browser/overlayLayoutElement.ts (e.g. `CSS.supports('anchor-name: --a')` or `@supports (anchor-name: --a)` in floatingPanels.css) so unsupported browsers fall back to a JS-driven position/size sync (e.g. ResizeObserver + explicit top/left/width/height) instead of silently losing layout.

## Evidence

- **source trace:** src/vs/base/browser/overlayLayoutElement.ts `reapplyLayoutStyles()` sets `top: anchor(top)`, `left: anchor(left)`, `width: anchor-size(width)`, `height: anchor-size(height)` on `.content` unconditionally, with no feature-detection guard anywhere in the file or in floatingPanels.css.
- **no fallback found:** `rg "CSS.supports|@supports"` across overlayLayoutElement.ts, overlayWebview.ts, and floatingPanels.css returns no matches — there is no fallback path for browsers lacking CSS Anchor Positioning.
- **reporter diagnostic:** Comment from sixcolors confirms on Safari 18.6 the wrapper has none of the anchor styles applied (invalid values are dropped), leaving the element with no computed size; caniuse shows Anchor Positioning only ships in Safari 26+.
