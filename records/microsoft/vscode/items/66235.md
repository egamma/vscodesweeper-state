# Issue #66235 — Allow more powerful onEnterRules for cursor alignment

[https://github.com/microsoft/vscode/issues/66235](https://github.com/microsoft/vscode/issues/66235)

## Summary

Keep open: current onEnterRules still cannot compute variable-width argument alignment, and format-on-type remains a setting-dependent workaround. The older capture-group request does not cover the full requirement; this team-authored Backlog item has substantial demand and unresolved API design.

## Change summary

Allow language-defined Enter behavior to calculate variable-width continuation indentation without requiring format-on-type, with additional support requested for correcting the current line's indentation.

## Best solution

Define a language-configuration capability for context-dependent alignment that preserves responsive Enter handling and works independently of editor.formatOnType. Settle its tab-handling contract and whether current-line indentation correction belongs in the same capability before implementation.

- **Validation:** After selecting the contract, add executable editor tests with editor.formatOnType disabled: Enter after `def func(a,` aligns at visual column 10, while Enter after `def func(` inserts one configured indentation level. Cover varying function-name lengths, non-indent-multiple alignment columns, spaces and tabs, and unchanged legacy onEnterRules behavior; include current-line dedentation checks if that scope is accepted.
- **Behavior:**

  > Language extensions need to express context-dependent continuation alignment without enabling format-on-type. With spaces and a four-column indent, pressing Enter after `def func(a,` should place the next cursor at column 10, whereas pressing Enter after `def func(` should place it at column 5. Alignment must adapt to prefix length rather than enumerate fixed-width rules, and existing declarative rules must retain their behavior. The discussion additionally requests correcting an incorrectly indented current `else:` line, but whether that ships under the same contract remains undecided.
- **Trace:**

  > OnEnterSupport.onEnter in src/vs/editor/common/languages/supports/onEnter.ts evaluates regex predicates and returns a static action; EnterAction in src/vs/editor/common/languages/languageConfiguration.ts provides no computed alignment operation. getEnterAction in src/vs/editor/common/languages/enterAction.ts and the _enter path in src/vs/editor/common/cursor/cursorTypeEditOperations.ts turn that action into normalized indentation and inserted text. The language-configuration loader in src/vs/workbench/contrib/codeEditor/common/languageConfigurationExtensionPoint.ts validates appendText as a string, and FormatOnType._update remains gated by editor.formatOnType. Preserve existing rule compatibility and responsive Enter handling; the thread explicitly rules out executing extension callbacks directly in the renderer. https://github.com/microsoft/vscode/issues/17281 supplies capture-substitution context but does not cover the complete request, while https://github.com/microsoft/vscode/issues/208985 offers a newer tree-sitter design lead. The uncertainty is the public alignment contract, especially tab behavior and current-line edit scope, rather than whether static appendText already satisfies the request.
- **Open decisions:**
  - Should the capability expose synchronous declarative alignment operations only, or also a separately enabled indentation-provider contract with asynchronous correction behavior?
  - For tab-indented documents, should continuation alignment preserve leading tabs and add alignment spaces, or follow another explicitly defined visual-column policy?
  - Should the initial capability cover next-line alignment only, or also permit correcting the current line's indentation on Enter, as requested for Python `else:`?
