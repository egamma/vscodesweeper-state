# Issue #231927 — Tools declaration still supports `toolReferenceName`

[https://github.com/microsoft/vscode/issues/231927](https://github.com/microsoft/vscode/issues/231927)

## Summary

The API debt remains on current main: package contributions still expose separate `toolReferenceName` and `canBeReferencedInPrompt` properties and require both together. The thread leaves the replacement contract unresolved, so this should remain open for an API design decision.

## Change summary

Simplify the language-model tool contribution contract by removing `toolReferenceName` or combining it with prompt-reference enablement.

## Best solution

Define a backwards-compatible contribution contract that clearly separates tool availability, attachment visibility, and the optional `#` reference name, then migrate or deprecate the existing fields without breaking extensions.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/tools/languageModelToolsContribution.ts`, `src/vs/workbench/contrib/chat/common/tools/languageModelToolsService.ts`, `src/vscode-dts/vscode.proposed.languageModelToolSupportsModel.d.ts`
- **Validation:** Add targeted extension-point schema and registration tests covering every supported combination of prompt availability and reference naming, then run the relevant chat tools unit-test suite and validate existing built-in extension manifests.
- **Behavior:**

  > A language-model tool contribution should have an unambiguous contract for agent availability, attachment visibility, and optional `#` invocation. Extension authors should not need two independently declared fields when one is meaningless without the other, while existing valid contributions must remain compatible through any migration. Acceptance should cover schema diagnostics, registration behavior, attachment visibility, and explicit prompt references.
- **Trace:**

  > In src/vs/workbench/contrib/chat/common/tools/languageModelToolsContribution.ts, `IRawToolContribution` and the extension-point schema expose separate `toolReferenceName` and `canBeReferencedInPrompt` fields; the handler rejects the latter when the former is absent and then spreads both into `IToolData`. src/vs/workbench/contrib/chat/common/tools/languageModelToolsService.ts retains both fields as distinct runtime state, while src/vscode-dts/vscode.proposed.languageModelToolSupportsModel.d.ts also exposes the reference name for programmatic definitions. The issue discussion establishes that attachment pills can use the display name without the short reference name, so collapsing the fields changes a public contract rather than merely internal structure. Related discussion at https://github.com/microsoft/vscode/issues/245129 and https://github.com/microsoft/vscode/issues/246132 should inform the design. Preserve existing tool IDs, model-facing names, and established attachment behavior while deciding the contribution shape.
- **Open decisions:**
  - Should prompt-reference capability remain a boolean plus an optional independent short name, become a boolean-or-name property, or use a structured property that represents both behaviors?
  - What backwards-compatible deprecation or migration behavior should existing extensions receive when they declare the current two-field shape?

## Evidence

- **current schema:** src/vs/workbench/contrib/chat/common/tools/languageModelToolsContribution.ts still declares `toolReferenceName?: string` and `canBeReferencedInPrompt?: boolean` independently in `IRawToolContribution` and in the extension-point JSON schema.
- **current validation:** src/vs/workbench/contrib/chat/common/tools/languageModelToolsContribution.ts rejects package contributions where `canBeReferencedInPrompt` is true without `toolReferenceName`, confirming the coupling reported by the issue remains.
- **open contract decision:** The issue discussion identifies materially different public shapes: a `boolean | string` property versus an independent short name, with the maintainer noting that attachment-pill behavior does not use `toolReferenceName`.
- **related API work:** https://github.com/microsoft/vscode/issues/245129 is newer, remains open, and discusses simplifying agent enablement versus tool references; under the re-review duplicate rule it is related context, not an older canonical duplicate.
- **later behavior decision:** https://github.com/microsoft/vscode/issues/246132 records the maintainer position that tools available to the agent should also be visible as attachments, but it does not settle whether or how the two declaration properties should be combined.
