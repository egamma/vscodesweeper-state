# Issue #340233 — Agents window: allow disabling local customization sync to remote agent hosts

[https://github.com/microsoft/vscode/issues/340233](https://github.com/microsoft/vscode/issues/340233)

## Summary

Legitimate, well-scoped gap: no setting currently exists to bulk-disable forwarding of locally discovered skills/customizations to remote agent hosts, only per-item enablement. The request is brand new (same day, no upvotes/maintainer input yet), so it should sit with the team before design work starts.

## Change summary

Add a setting to stop the Agents window from forwarding locally discovered skills/customizations to remote agent hosts (globally or per host), while still allowing the remote environment's own customizations and the harness's built-ins.

## Best solution

A maintainer should decide the scope (global toggle vs. per-host override) for suppressing client-forwarded customizations, then extend the existing per-item enablement machinery (src/vs/platform/agentHost/node/agentHostCustomizationEnablementService.ts, customizationEnablementGate.ts) with a bulk 'don't forward local customizations' mode, alongside the related individual-disable work in #329751/#329753.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHost.contribution.ts`, `src/vs/platform/agentHost/node/agentHostCustomizationEnablementService.ts`, `src/vs/platform/agentHost/node/shared/customizationEnablementGate.ts`
- **Validation:** A test asserting that with the new setting disabled, a remote agent session's resolved customization set excludes client-forwarded (local) skills/plugins while still including remote-discovered customizations and the harness's built-in instructions.
- **Behavior:**

  > When the new setting is off, the Agents window must not forward locally discovered skills/customizations to a remote agent host at all (no per-skill revisiting needed when a new local skill is installed). Customizations discovered inside the remote environment itself, and the selected harness's built-in instructions/capabilities, must remain unaffected. The setting should be controllable at least globally; per-host override is an open question.
- **Trace:**

  > Today only per-item enablement exists via IAgentHostCustomizationEnablementService / customizationEnablementGate.ts (keyed by customization id/source), with no bulk switch; the configuration registered in remoteAgentHost.contribution.ts has no related setting. The boundary: do not change how remote-discovered or harness-builtin customizations are resolved — only gate the client-forwarded ('isClientBundled') ones. Where uncertainty starts: whether this is a single global APPLICATION-scope setting or needs a per-remote-host override, and how it composes with the existing per-item enablement UI from https://github.com/microsoft/vscode/issues/329751 and https://github.com/microsoft/vscode/issues/329753.
- **Open decisions:**
  - Is this a single global setting, a per-remote-host override, or both?
  - How should bulk-disable interact with existing per-item enablement decisions (e.g. does it override them, or only change the default)?

## Evidence

- **no existing bulk setting:** src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHost.contribution.ts only registers `missionControlEnabled`, `chat.remoteAgentHosts.enabled`, and `chat.agentHost.cloudSandbox.enabled` — nothing to suppress forwarding of locally discovered customizations.
- **existing granularity is per-item:** src/vs/platform/agentHost/node/agentHostCustomizationEnablementService.ts and customizationEnablementGate.ts manage enablement per customization id/source, matching the issue's complaint that disabling individual skills is cumbersome.
- **related work:** Issue references https://github.com/microsoft/vscode/issues/329751 and https://github.com/microsoft/vscode/issues/329753 about disabling individual customizations, framing this as the complementary bulk/global control.
