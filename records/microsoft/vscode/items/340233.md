# Issue #340233 — Agents window: allow disabling local customization sync to remote agent hosts

[https://github.com/microsoft/vscode/issues/340233](https://github.com/microsoft/vscode/issues/340233)

## Summary

Keep open: current source provides per-customization opt-outs, not a blanket remote-forwarding control. Agent-name deduplication would address the commenter's duplication symptom but would not prevent desktop-only instructions from reaching remote agents.

## Change summary

Allow users to stop forwarding local customizations to remote agent hosts while preserving remote-discovered customizations and harness-native capabilities.

## Best solution

Provide an explicit client-forwarding control at the customization publication boundary, without disabling remote discovery or native harness behavior. Decide its global versus per-host scope before implementation; treat obsolete forwarded revisions as a separate lifecycle concern.

- **Behavior:**

  > Users can opt out of local customization forwarding without disabling remote-discovered customizations or the selected harness's native instructions and capabilities. Newly installed local customizations must respect the opt-out without individual configuration. Re-enabling restores normal forwarding. If per-host overrides are supported, changing one host must not affect another.
- **Trace:**

  > AgentHostActiveClientService.acquireScope enables user-storage inclusion for remote session types. AgentCustomizationScope computes both wire refs and local custom-agent picker metadata through resolveCustomizationRefs and resolveLocalCustomAgents in agentHostLocalCustomizations.ts. AgentCustomizationSyncProvider currently supplies URI-level exclusions, not a host-wide state. The resolver also includes extension/built-in content, plugins and forwarded MCP definitions, so the exact opt-out boundary needs agreement. Preserve host-owned discovery and native harness capabilities; do not assume agent-name deduplication or deleting cached directories satisfies the forwarding request. The commenter's retained-revision report is related evidence, not a confirmed root cause.
- **Open decisions:**
  - Should the forwarding preference apply globally to all remote hosts, support per-host overrides, or both?
  - Should opting out also exclude VS Code-bundled skills and helper instructions, or preserve those while excluding user-, extension- and plugin-provided local customizations?
  - Should changing the preference withdraw forwarded content from active sessions immediately, or apply only to new sessions?
