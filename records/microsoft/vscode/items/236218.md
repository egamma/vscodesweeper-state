# Issue #236218 — Expose the current editor overtype state

[https://github.com/microsoft/vscode/issues/236218](https://github.com/microsoft/vscode/issues/236218)

## Summary

The extension API still does not expose the input mode or its changes, so synchronizing a webview's Monaco editor remains unsupported. Keep this accepted backlog request open; the existing toggle command does not cover observation.

## Change summary

Expose the current insert/overtype mode and a change event so extensions can synchronize embedded editors.

## Best solution

Provide a supported extension API for reading and observing input mode, allowing extensions to forward that state to their webviews. Settle the API's window-versus-editor scope without making per-editor overtype behavior a prerequisite.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/inputMode.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadEditors.ts`, `src/vs/workbench/api/common/extHostTextEditors.ts`
- **Validation:** Add extension API coverage that reads the initial mode, invokes editor.action.toggleOvertypeInsertMode, and verifies the observed state and change event match the new mode. Include subscription after overtype is already active, operation with a focused webview, and restoration of the original mode after the check.
- **Behavior:**

  > An extension can determine whether VS Code is in insert or overtype mode and observe subsequent changes through a supported API. This lets a webview initialize its standalone Monaco editor consistently and keep it synchronized without inferring state from cursor appearance or toggling VS Code speculatively. Acceptance includes obtaining the correct initial state when subscribing after a mode change and observing changes while a webview is active. Existing typing and toggle behavior must remain unchanged.
- **Trace:**

  > src/vs/editor/common/inputMode.ts owns the current renderer-level singleton and its change event. ToggleOvertypeInsertMode in src/vs/workbench/contrib/codeEditor/browser/toggleOvertype.ts changes that singleton but exposes neither a query result nor an extension event. The stable/proposed API declarations and extension-host bridge contain no input-mode exposure; existing editor-options synchronization in mainThreadEditor.ts, extHost.protocol.ts, and extHostTextEditors.ts carries other options only. The missing work is the supported API boundary, not implementing overtype itself. Preserve existing global toggle semantics and do not expand the request into per-editor overtype or a writable API. The thread at https://github.com/microsoft/vscode/issues/236218 leaves the public API's scope unsettled; https://github.com/microsoft/vscode/issues/1012 covers the already-implemented toggle behavior instead.
- **Open decisions:**
  - Should the read-only state and change event be window-scoped, matching today's shared mode and remaining available without a native text editor, or belong to TextEditor with defined behavior when editors are inactive or absent?

## Evidence

- **Existing internal capability:** src/vs/editor/common/inputMode.ts defines the InputMode singleton with getInputMode(), setInputMode(), and onDidChangeInputMode. The requested state and notification exist internally, but are not an extension-facing contract.
- **Existing command does not satisfy the request:** src/vs/workbench/contrib/codeEditor/browser/toggleOvertype.ts registers editor.action.toggleOvertypeInsertMode. Its run() method toggles the singleton and returns no state; invoking it cannot reliably read the current mode or subscribe to changes.
