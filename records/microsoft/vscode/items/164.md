# Issue #164 — Better drag and drop / clipboard integration of files across applications

[https://github.com/microsoft/vscode/issues/164](https://github.com/microsoft/vscode/issues/164)

## Summary

The central native file-transfer gap remains on current main and is constrained by Electron/Chromium integration. This accepted, highly supported upstream request should stay open; completed inbound-paste and desktop-drop work covers only part of it.

## Change summary

Support copying or dragging files and folders from VS Code into native file managers and other applications using native OS file-transfer formats.

## Best solution

Electron should expose reliable cross-platform native file clipboard and drag-transfer APIs, after which VS Code can adopt them in NativeClipboardService and the Explorer drag path while preserving its existing internal cross-window transfer.

## Evidence

- **current clipboard path:** src/vs/workbench/services/clipboard/electron-browser/clipboardService.ts:14-65 writes Explorer resources only to the private `code/file-list` clipboard format through `writeClipboardBuffer`; it does not publish native OS file-list formats consumable by Finder or Windows Explorer.
- **current drag path:** src/vs/workbench/contrib/files/browser/views/explorerViewer.ts:1768-1779 puts file paths in the custom `CodeDataTransfers.FILES` payload specifically for drag-and-drop between VS Code windows; there is no native file-transfer payload for arbitrary applications.
- **partial completion:** Inbound native clipboard paste was completed in https://github.com/microsoft/vscode/issues/130036 and desktop file dropping was completed in https://github.com/microsoft/vscode/issues/128975, but the issue checklist still leaves outbound native clipboard transfer, general native drag transfer, and archive-tool interoperability open.
- **upstream dependency:** https://github.com/electron/electron/issues/2853 covers native file transfer and clipboard support. It was closed as a duplicate with a maintainer noting that new native-file APIs were required; a later upstream comment explains that the cited duplicate concerned image data and did not provide file copying between Electron and the OS.
