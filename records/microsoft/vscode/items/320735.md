# Issue #320735 — Settings UI disagrees with actual value for application-scoped setting

[https://github.com/microsoft/vscode/issues/320735](https://github.com/microsoft/vscode/issues/320735)

## Summary

Legitimate bug: when a non-default profile's settings.json contains an APPLICATION-scoped setting (like `remote.SSH.configFile`), the extension API's `getConfiguration().get()` returns the profile's value instead of the application-level value from the default profile. The Settings UI correctly reads `applicationValue`, but the merged configuration leaks the profile's value because the profile's local user configuration isn't reparsed when extension settings register late (or the setting bypasses scope filtering).

## Change summary

Extension API returns a non-default profile's value for an APPLICATION-scoped setting instead of the application-level value from the default profile.

## Best solution

Fix the configuration resolution so that APPLICATION-scoped settings from non-default profile settings.json files are never surfaced via `getValue()`. The likely fix is in `src/vs/workbench/services/configuration/browser/configurationService.ts` — ensure that `onDefaultConfigurationChanged` triggers a reparse of the local user configuration even without a remote connection, or that the consolidated configuration model correctly gives `applicationConfiguration` priority over `localUserConfiguration` for APPLICATION-scoped keys.

## Evidence

- **scope filtering logic:** In src/vs/platform/configuration/common/configurationModels.ts:470-481, `shouldInclude` returns true for unregistered settings (scope === undefined) even when the profile's parseOptions.scopes excludes APPLICATION, allowing extension-contributed APPLICATION-scoped settings to leak into non-default profile configurations before the extension registers them.
- **reparse gap:** In src/vs/workbench/services/configuration/browser/configurationService.ts:754-756, `onDefaultConfigurationChanged` only reparses the local user configuration when `this.remoteUserConfiguration` exists. Without a remote, late-registering extension settings never trigger a reparse that would correctly filter out APPLICATION-scoped keys from the profile.
- **merge order:** In src/vs/platform/configuration/common/configurationModels.ts:1024, the consolidated config is `defaults.merge(application, user, workspace, memory)` — user (profile) wins over application in the merge, so a leaked APPLICATION-scoped setting from the profile overrides the correct application value.
- **settings UI is correct:** src/vs/workbench/contrib/preferences/browser/settingsTreeModels.ts:288-294 correctly uses `getTargetToInspect` to read `applicationValue` for APPLICATION-scoped settings in non-default profiles, explaining the UI/API discrepancy.
