# Issue #341059 — Sandbox pre-flight check flags name.ext tokens inside quoted strings and heredocs as file write targets

[https://github.com/microsoft/vscode/issues/341059](https://github.com/microsoft/vscode/issues/341059)

## Summary

Thanks for the detailed report. The `file.ext:NNN` token is most likely treated as an scp/ssh remote host by the sandbox domain extractor, which produces the phantom approval prompt. Keeping open; it needs a decision on how narrow the heuristic should be.

## Change summary

Sandbox pre-flight flags `name.ext:NNN` text in quoted strings and heredocs as an accessed host, and does not expand `$TMPDIR` in the real redirect operand.

## Best solution

Restrict host extraction in TerminalSandboxEngine so that `file.ext:line` citations in quoted strings and heredoc bodies are not treated as ssh/scp hosts. Expand `$VAR` and `~` in redirect operands before checking them against the file write policy.

- **Validation:** A terminalSandboxEngine test asserting that `echo "Zebra.cpp:713-714" > f` and a heredoc containing `source_file.cpp:713-714` produce no blocked domains, while `git clone host.com:repo` still does.
- **Behavior:**

  > Commands that only mention `name.ext:NNN` in quoted text or heredoc bodies must not trigger a domain or file approval prompt. Genuine scp/ssh remotes such as `git@github.com:org/repo` must still be detected. `$VAR` and `~` redirect operands must be expanded before the policy check.
- **Trace:**

  > `_extractDomains` in terminalSandboxEngine.ts applies `_sshRemoteRegex` to raw command text with no awareness of quoting or heredocs. The `$TMPDIR` mis-rendering and the file-write listing come from the file write analyzer and were not traced. Do not weaken the real URL and ssh detection.
- **Open decisions:**
  - Skip host-like tokens inside quoted strings and heredoc bodies, or only require a recognised TLD or a user@ prefix?
  - Should the pre-flight text scraping be removed in favor of kernel-level enforcement, as the reporter requests?
