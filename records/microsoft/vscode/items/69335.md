# Issue #69335 — Investigation: do not restart Extension host when first folder changes

[https://github.com/microsoft/vscode/issues/69335](https://github.com/microsoft/vscode/issues/69335)

## Summary

Keep open: current source still restarts the extension host when the first workspace folder changes, and the compatibility decision remains unresolved. This api-proposal tracking issue is protected from cleanup closure.

## Change summary

Allow first-folder changes without restarting extensions, while updating workspace.rootPath and delivering workspace-folder change events.

## Best solution

Resolve the compatibility policy for extensions that cache rootPath or use non-multiroot-aware language servers, then make supported first-folder changes preserve the extension host and notify extensions. Keep this issue as the tracking record rather than treating newer, narrower symptoms as its replacement.

## Evidence

- **Current restart implementation:** src/vs/workbench/contrib/relauncher/browser/relauncher.contribution.ts:269–346 defines WorkspaceChangeExtHostRelauncher. In WORKSPACE state, onDidChangeWorkspaceFolders compares the first folder URI and schedules a restart when it changes; the scheduler stops and starts native extension hosts or reloads remote windows. Extension tests and the Sessions window are exempt, but the ordinary workbench path remains.
- **Existing API contract and partial workaround:** src/vscode-dts/vscode.d.ts:13878–13881 explicitly documents that first-folder additions, removals, and changes restart extensions instead of delivering onDidChangeWorkspaceFolders. Lines 13913–13918 also document workspace-transition restarts. Appending a folder can avoid changing the first folder in an existing multi-root workspace, as discussed in the supplied thread, but does not cover removing or replacing the first folder.
- **Unresolved compatibility decision:** https://github.com/microsoft/vscode/issues/69335#issuecomment-581811202 identifies the unresolved choice between accepting changed behavior for non-multiroot-aware extensions and providing an LSP-client compatibility workaround. The supplied later discussion reports disrupted webviews and pseudoterminal subprocesses; it does not establish an accepted compatibility policy.
