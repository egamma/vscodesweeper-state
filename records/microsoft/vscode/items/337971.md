# Issue #337971 — Agents Window uses incorrect base branch for Branch Changes with existing Git worktree

[https://github.com/microsoft/vscode/issues/337971](https://github.com/microsoft/vscode/issues/337971)

## Summary

Thanks for the detailed report. Branch Changes still takes its base from the repository's `origin/HEAD` or an explicitly configured base branch, not from the current branch's upstream. A worktree created outside VS Code from `origin/dev` therefore falls back to `main` whenever `refs/remotes/origin/HEAD` points at `main`. Two caveats: I read the source only and did not run it, and I did not check how the Changes view picks its base from this git state.

## Change summary

For an existing (externally created) worktree or folder, the Agents window Branch Changes view compares against `main` instead of the branch's upstream (`dev`).

## Best solution

In `AgentHostGitService._computeSessionGitState`, when no base branch is configured, derive the base from the current branch's upstream (the same rule the worktree-creation flow uses). Fall back to `origin/HEAD` only when there is no upstream. A base-branch picker in the Changes pane would also address the request.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentHostGitService.ts`, `src/vs/platform/agentHost/node/agentHostGitStateService.ts`
- **Validation:** Add a unit test for `getSessionGitState` using a repo whose branch tracks `origin/dev` while `refs/remotes/origin/HEAD` points at `main`. It should expect `baseBranchName` to be `dev`.
- **Behavior:**

  > For a session on an existing folder or worktree with no configured base branch, Branch Changes should compare against the current branch's upstream (e.g. `origin/dev`) instead of `origin/HEAD`. If there is no upstream, the current `origin/HEAD` fallback is kept. An explicitly configured base branch still wins.
- **Trace:**

  > `_computeSessionGitState` in src/vs/platform/agentHost/node/agentHostGitService.ts sets `baseBranchName = configuredBaseBranch ?? parseDefaultBranchRef(origin/HEAD)`. The upstream is already parsed into `status.upstreamBranchName`. `AgentHostGitStateService` (around line 394) passes the configured base into this function. Uncertainty starts at the consumers of `baseBranchName` (Changes view, pull request creation, merge): precedence among the user-picked base, the upstream, and `origin/HEAD` must be settled there. Do not change the worktree-creation default in worktreeIsolation.ts.
- **Open decisions:**
  - Should the upstream branch always take precedence over `origin/HEAD` for existing folders, or only when it differs from the current branch's own remote counterpart? A branch tracking `origin/feat/x` should not become its own base.
  - Should a base-branch picker be added to the Changes pane in addition to the automatic default?

## Evidence

- **base selection:** src/vs/platform/agentHost/node/agentHostGitService.ts, `_computeSessionGitState` (around line 1232): `baseBranchName = configuredBaseBranch ?? parseDefaultBranchRef(defaultBranchRef)`. `defaultBranchRef` comes from `git symbolic-ref refs/remotes/origin/HEAD`. The branch's own upstream (`status.upstreamBranchName`) is never consulted for the base.
- **inconsistency with worktree creation:** src/vs/platform/agentHost/node/shared/worktreeIsolation.ts (around line 896) uses `branch.upstream?.name ?? defaultBranch.name` when VS Code creates the worktree itself. Existing-folder sessions do not get the same treatment.
- **possible cause on the reporter's side:** `origin/HEAD` is a local ref set at clone time and does not follow the GitHub default branch automatically. In the reporter's repo it may still point at `main`. This is likely, but unconfirmed.
