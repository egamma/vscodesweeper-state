# Issue #337971 — Agents Window uses incorrect base branch for Branch Changes with existing Git worktree

[https://github.com/microsoft/vscode/issues/337971](https://github.com/microsoft/vscode/issues/337971)

## Summary

Traced in source: for a worktree opened directly (not created through the Agents window), the base branch is resolved solely from the locally cached `refs/remotes/origin/HEAD` symbolic ref, which can be stale (e.g. after the GitHub default branch changed) and is preferred over an explicit upstream tracking branch — this explains the reported `main` instead of `dev`. This is a real, if niche, design gap rather than something already fixed on main.

## Change summary

Agents Window Branch Changes compares an existing (non-Agents-created) worktree's feature branch against the wrong base branch when the locally cached origin default-branch ref is stale.

## Best solution

Have the Agents Window's base-branch resolution for pre-existing worktrees prefer a more authoritative signal than the cached `origin/HEAD` symref when one is available (e.g. the feature branch's own upstream tracking ref), and/or let a maintainer decide whether to refresh `origin/HEAD` live or expose an explicit base-branch override in the Changes pane, as the reporter suggests.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentHostGitService.ts`, `src/vs/platform/agentHost/common/changesetUri.ts`, `src/vs/platform/agentHost/node/agentHostGitStateService.ts`
- **Validation:** Extend agentHostGitService.integrationTest.ts (which already sets up `refs/remotes/origin/HEAD` scenarios) with a case where the local origin/HEAD symref points at a stale branch (e.g. `main`) while the feature branch has an explicit upstream tracking a different branch (`origin/dev`); assert the resolved baseBranchName/Branch Changes description matches whatever resolution order the maintainer decides on.
- **Behavior:**

  > For a Git worktree/folder that already existed before being opened in an Agents Window session (not one created through the Agents window's own worktree flow), Branch Changes should compare the feature branch against the branch it was actually created from / meaningfully tracks, not a possibly stale locally cached default-branch reference. Acceptance: in a repo where the local `origin/HEAD` symref is stale (points to `main`) but the feature branch has an explicit upstream tracking a different branch (`origin/dev`), Branch Changes shows `feature → dev` and the diff excludes unrelated `main`↔`dev` differences.
- **Trace:**

  > `_computeSessionGitState` in src/vs/platform/agentHost/node/agentHostGitService.ts (lines 937-1010) computes `baseBranchName` from `configuredBaseBranch ?? parseDefaultBranchRef(defaultBranchRef)`, where `defaultBranchRef` comes from `git symbolic-ref --quiet refs/remotes/origin/HEAD` (line 952) — a purely local cache that Git does not refresh automatically when a remote's default branch changes. `configuredBaseBranch` is only populated when the session's config records `SessionConfigKey.Isolation === 'worktree'` with a stored branch (agentHostGitStateService.ts `resolveSessionBaseBranchName`, lines 520-529) — which does not happen for a worktree opened directly, exactly the reporter's scenario. Separately, `formatBranchChangesetDescription` (changesetUri.ts:105-119) always prefers `baseBranchName` over `upstreamBranchName` when both exist, so even though the reporter explicitly set the feature branch's upstream to `origin/dev`, the display and diff still anchor on the (possibly stale) `baseBranchName`. Boundary: do not change the worktree-created-via-Agents-window path (which already persists an authoritative `configuredBaseBranch`); the gap is specific to pre-existing worktrees/folders where the host has no persisted base branch and must infer one from local Git state.
- **Open decisions:**
  - When a pre-existing worktree's feature branch has an explicit upstream tracking ref that differs from the locally cached `origin/HEAD` default branch, should the host prefer the upstream branch over `origin/HEAD` for the Branch Changes base?
  - Should the host attempt to refresh a potentially stale `origin/HEAD` cache (e.g. via a live `git ls-remote --symref origin HEAD` or by running `git remote set-head origin -a`), and if so, how often / at what cost to startup latency?
  - Should users be able to manually pick/override the Branch Changes base branch in the Changes pane, as the reporter suggests, and if so where would that selection be persisted (session config vs. per-workspace Git state)?
