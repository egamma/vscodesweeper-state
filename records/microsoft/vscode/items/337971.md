# Issue #337971 — Agents Window uses incorrect base branch for Branch Changes with existing Git worktree

[https://github.com/microsoft/vscode/issues/337971](https://github.com/microsoft/vscode/issues/337971)

## Summary

Thanks for the detailed report. Three people have confirmed it, up to 1.141.2. The base branch for an existing worktree comes only from a configured base or the local `refs/remotes/origin/HEAD`. It never uses the branch's upstream, so a stale `origin/HEAD` pointing at `main` would give exactly the reported `feat/x → main`. I could not run it to confirm that.

## Change summary

For an existing Git worktree, Branch Changes in the Agents window compares against `main` instead of the branch's upstream or the repository's real default branch (`dev`).

## Best solution

When no base is explicitly configured, derive the base from the checked-out branch's upstream, or at least from a correct default-branch lookup. Also consider letting the user change the comparison base in the Changes view.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentHostGitService.ts`, `src/vs/platform/agentHost/node/agentHostGitStateService.ts`, `src/vs/sessions/contrib/changes/browser/changesViewService.ts`
- **Validation:** A test in the agentHostGitService tests: a repo whose origin/HEAD points to main and whose branch tracks origin/dev reports baseBranchName `dev`.
- **Behavior:**

  > For a session on an existing worktree where the user did not pick a base, Branch Changes compares against the branch the feature branch tracks or was created from (here `dev`), not a stale or mismatched `main`. The header shows `feat/test → dev`. Sessions with an explicit base, and sessions where VS Code creates the worktree, behave as before.
- **Trace:**

  > _computeSessionGitState in agentHostGitService.ts takes the base from `configuredBaseBranch` or `parseDefaultBranchRef(origin/HEAD)`, and the upstream is parsed but unused for this. resolveSessionBaseBranchName in agentHostGitStateService.ts passes this through for non-worktree folders. I could not confirm what the reporter's `origin/HEAD` points to, so the first step is to check whether it is stale (`git symbolic-ref refs/remotes/origin/HEAD`). The boundary is that sessions with a persisted `META_DIFF_BASE_BRANCH` must not change.
- **Open decisions:**
  - Should the base prefer the branch's upstream when it is a non-self remote branch, over origin/HEAD?
  - Should the Changes view also offer a user-selectable comparison base?

## Evidence

- **base resolution:** src/vs/platform/agentHost/node/agentHostGitService.ts (_computeSessionGitState, ~line 1264) sets `baseBranchName = configuredBaseBranch ?? parseDefaultBranchRef(origin/HEAD)`. It never looks at the upstream (`@{upstream}`), even though `status.upstreamBranchName` is already parsed.
- **state resolution:** src/vs/platform/agentHost/node/agentHostGitStateService.ts resolveSessionBaseBranchName returns this git-state base for non-worktree session folders, i.e. an existing worktree opened as a folder.
- **UI:** copilotChatSessionsChangesets.ts (~line 153) renders `branch → baseBranchName` straight from that state.
- **community:** Comments 2 and 3 report the same problem on 1.141.0 and 1.141.2, so it is not fixed in current builds.
