# Issue #199030 — File links: Support opening files with relative "file://" paths

[https://github.com/microsoft/vscode/issues/199030](https://github.com/microsoft/vscode/issues/199030)

## Summary

Keep this accepted, well-supported request open: current source supports a restricted relative-link syntax, but not the requested direct parent-relative form or consistent navigation through the hover. The referenced merged PR fixes Windows handling of the restricted syntax, not the full request.

## Change summary

Support portable, file-relative file:// links in source comments without requiring machine-specific absolute paths.

## Best solution

Define the supported relative-link syntax and make editor link activation resolve it consistently against the containing file's directory, including parent-directory traversal and the Follow Link hover. Preserve absolute and UNC file-link behavior; treat workspace-root links and remote-provider support as explicit scope decisions rather than silently expanding this request.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/links/browser/links.ts`, `src/vs/editor/contrib/hover/browser/markdownHoverParticipant.ts`, `src/vs/platform/markdown/browser/markdownRenderer.ts`
- **Validation:** Create a temporary repository fixture with nested source files and sibling/ancestor targets. On Windows and macOS or Linux, verify that each approved relative file:// form opens the same intended target through modifier-click, editor.action.openLink, and the Follow Link hover. Include multiple parent-directory segments and confirm existing absolute and UNC links retain their destinations; exercise remote models if included in the agreed scope.
- **Behavior:**

  > Repository comments should link to other files without embedding the repository's machine-specific absolute location. Approved file-relative forms must resolve from the containing file's directory, including traversal to ancestor directories, and reach the same target through modifier-click, Open Link, and the Follow Link hover. Moving the repository to a different absolute directory must not change those destinations. Existing absolute and UNC links must remain unchanged; workspace-root-relative links and remote support need explicit scope agreement.
- **Trace:**

  > LinkDetector.openLinkOccurrence in src/vs/editor/contrib/links/browser/links.ts contains a restricted relative-file conversion for string URLs and file-scheme models, recognizing only ./-prefixed forms. The requested direct ../ prefix is outside those branches; resources.originalFSPath and URI.joinPath in src/vs/base/common/resources.ts and uri.ts explain the platform conversion and normalization. getHoverMessage emits the original URL, and markdownHoverParticipant renders it through the platform MarkdownRendererService default action handler, bypassing LinkDetector's conversion. https://github.com/microsoft/vscode/pull/181475 adds Windows equivalents to the existing ./ checks only, despite its broader description. https://github.com/microsoft/vscode/issues/233151 documents the separate remote-model limitation. The uncertainty is the supported relative-URI contract and provider scope, not whether the referenced PR implemented all requested behavior; preserve absolute/UNC interpretation and do not expand into terminal or Quick Open normalization.
- **Open decisions:**
  - Which direct parent-relative file:// forms and separator conventions should be supported in addition to the existing ./-prefixed forms, while preserving absolute and UNC interpretation?
  - Should this request cover only local file-backed editor models, or also resolve these links within remote and virtual filesystem providers?
