# Issue #199030 — File links: Support opening files with relative "file://" paths

[https://github.com/microsoft/vscode/issues/199030](https://github.com/microsoft/vscode/issues/199030)

## Summary

A real gap remains: the merged fix (PR #181475, now in src/vs/editor/contrib/links/browser/links.ts) only resolves `file://./relative` and `file:///./relative` (same-directory) links; it never handles `..`-prefixed parent-directory traversal, which is exactly the issue's second example and what the latest commenter (2026-05-19) still can't get working. This matches the prior review's refutation of the earlier implemented-on-main claim — no new fix commit covers the remaining case, so this stays open.

## Change summary

Let file:// links use relative (not just absolute, machine-specific) paths so links work across machines/repos, including parent-directory (`..`) traversal.

## Best solution

Extend the relative-link handling in src/vs/editor/contrib/links/browser/links.ts (openLinkOccurrence) to also recognize `..`-prefixed relative file paths (not just `./`) and resolve them via resources.joinPath against the current document's URI, the same way the existing `./` case is handled; also check whether the hover-triggered 'Follow Link' path uses the same resolution as the direct click path (a commenter reported inconsistent behavior between the two).

## Plan brief

- **Likely files:** `src/vs/editor/contrib/links/browser/links.ts`
- **Validation:** A test in the links contribution test suite asserting that a `file://../relativeFile.txt` link resolves (via resources.joinPath) to the parent directory of the current document, mirroring the existing `./` test coverage.
- **Behavior:**

  > Clicking (or using hover 'Follow Link' on) a `file://` link whose path begins with a relative segment such as `..` or `./` should resolve relative to the current document's directory and open the target file, the same way `file://./x` and `file:///./x` already do. Acceptance: a new relative-link test for a `..`-prefixed path passes, and the existing `./` relative-link tests continue to pass.
- **Trace:**

  > src/vs/editor/contrib/links/browser/links.ts, openLinkOccurrence (around lines 221-254): after link.resolve(), for file-scheme model URIs the code inspects fsPath and only recognizes `/./`, `\.\`, `//./`, `\\.\\` prefixes before calling resources.joinPath(modelUri, relativePath) — there is no equivalent branch for `/../` or `\..\`. The boundary: do not change the resolution behavior for absolute file:// links or the existing `./` case; only extend the relative-detection condition and reuse the same resources.joinPath call. A commenter (jonbgamble, 2024-02-10) separately reported that direct ctrl-click works for relative links on mac/linux but the hover-triggered 'Follow Link' action does not on Windows/web — worth confirming both paths route through this same method before concluding the fix is complete. Related: https://github.com/microsoft/vscode/pull/181475 (prior partial fix), https://github.com/microsoft/vscode/issues/199030 (this issue).
- **Open decisions:**
  - Should relative resolution support arbitrary `..`/`.` combinations generally, or only the specific `..`-prefixed pattern reported here?
  - Does the hover 'Follow Link' command route through the same openLinkOccurrence resolution as direct click, and if not, should it be unified?
