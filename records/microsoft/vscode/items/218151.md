# Issue #218151 — Incorrect editor scroll position when moving between stack frames after hitting exception

[https://github.com/microsoft/vscode/issues/218151](https://github.com/microsoft/vscode/issues/218151)

## Summary

Keep open: an independent report confirms the same first-click failure after leaving an exception frame, and no verified fix covers it. The related open report is newer, so it cannot replace this re-reviewed issue as the canonical.

## Change summary

Selecting another stack frame after an exception sometimes leaves its execution line off-screen until the frame is clicked again.

## Best solution

Ensure the first stack-frame selection reveals its execution line after exception-widget layout changes, including with smooth scrolling and a short editor viewport. Retain this older report as the tracking issue and investigate the matching evidence in https://github.com/microsoft/vscode/issues/224676.

## Evidence

- **Reported trigger and configuration:** https://github.com/microsoft/vscode/issues/218151 describes a short editor viewport, a Python exception, and a failed first navigation away from the top frame followed by a successful second click. - **Independent reproduction:** https://github.com/microsoft/vscode/issues/224676 independently reports the same top-frame-to-other-frame first-click failure on macOS with VS Code 1.92.0, including successful subsequent clicks. https://github.com/microsoft/vscode/issues/224676#issuecomment-2277956090 also identifies the exception block as a possible contributor. These are historical reproductions, not a current-build execution.
- **Canonical search:** Searches for exception-widget scrolling and call-stack scrolling found the matching open https://github.com/microsoft/vscode/issues/224676, created on 2024-08-03, after this issue's 2024-06-25 creation. The stronger duplicate bar for re-reviewed items therefore prevents closing this older issue against it.
- **Current navigation and widget lifecycle:** src/vs/workbench/contrib/debug/browser/debugService.ts:1021-1050 opens the selected stack frame before calling viewModel.setFocus. Source.openInEditor in common/debugSource.ts requests CenterIfOutsideViewport; textCodeEditor.ts applies navigation options with ScrollType.Smooth. DebugEditorContribution.onFocusStackFrame then calls toggleExceptionWidget for a matching model, which removes the widget for a non-exception frame. ZoneWidget.dispose removes its view zone. This identifies a reveal/layout ordering interaction worth investigating, but does not conclusively establish the current failure.
- **Nearby change does not prove resolution:** https://github.com/microsoft/vscode/commit/4b985d9ed2bc22020d1c845dd0d160f50f3b704f changes showExceptionWidgetWithoutScroll to handle empty visible ranges and measure the correct whitespace when inserting a widget into an inactive editor. Its diff does not address revealing another stack frame while removing the active exception widget, so it is not evidence that this report is fixed.
- **Historical related fix:** https://github.com/microsoft/vscode/issues/29097#issuecomment-328878351 documents a 2017 fix for exception-widget relayout overriding stack-frame navigation. Current toggleExceptionWidget retains the resulting focused-frame restriction; that older fix predates the present report and does not establish resolution of its smooth-scrolling case.
