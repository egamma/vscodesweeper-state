# Issue #143924 — Delay starting the web worker extension host until activating first extension

[https://github.com/microsoft/vscode/issues/143924](https://github.com/microsoft/vscode/issues/143924)

## Summary

The requested startup optimization remains absent on current main: browser workbenches create the web worker extension host eagerly during extension-service initialization rather than waiting for the first relevant activation. This team-authored On Deck request should remain open despite its age.

## Change summary

Defer creation of the browser web worker extension host until a web extension first needs to activate.

## Best solution

Avoid loading the worker iframe and extension-host runtime until a web extension has an activation request, while preserving immediate activation, extension installation, restart, and extension-test behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/browser/extensionService.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/services/extensions/common/lazyCreateExtensionHostManager.ts`, `src/vs/workbench/services/extensions/test/browser/extensionService.test.ts`
- **Validation:** Add a targeted extension-service test showing that browser initialization with assigned web extensions does not start the web worker host, then request a matching activation event and assert that the host starts exactly once; run it with scripts/test.sh using the new test title as --grep.
- **Behavior:**

  > Opening VS Code for the Web must not start the web worker extension host merely because web extensions are installed or assigned to it. The host should start when the first assigned web extension actually needs activation, and that activation must complete normally. Immediate activation requests, extension installation or enabling, extension-host restart, and extension tests must retain their existing behavior.
- **Trace:**

  > BrowserExtensionHostFactory in src/vs/workbench/services/extensions/browser/extensionService.ts currently gives the initial LocalWebWorkerRunningLocation EagerManualStart. AbstractExtensionService._initialize creates managers early and _startOnDemandExtensionHosts starts every manager that is not EagerAutoStart, so WebWorkerExtensionHost.start creates the iframe before a specific activation. LazyCreateExtensionHostManager in src/vs/workbench/services/extensions/common/lazyCreateExtensionHostManager.ts is the existing lazy lifecycle abstraction, but it currently creates the real host when start receives any assigned extensions rather than on activation. Activation requests flow through AbstractExtensionService.activateByEvent/_activateByEvent, including a distinct Immediate path that must not regress. Keep local-process and remote-host startup behavior outside the scope of this work.

## Evidence

- **current browser startup:** src/vs/workbench/services/extensions/browser/extensionService.ts:240-251 assigns LocalWebWorkerRunningLocation an EagerManualStart startup mode on initial browser startup.
- **initialization path:** src/vs/workbench/services/extensions/common/abstractExtensionService.ts calls _startExtensionHostsIfNecessary during _initialize and later _startOnDemandExtensionHosts; every non-EagerAutoStart manager is started after extension discovery, before any particular extension activation is required.
- **worker creation:** WebWorkerExtensionHost.start in src/vs/workbench/services/extensions/browser/webWorkerExtensionHost.ts calls _startInsideIframe, which creates and appends the hidden worker-host iframe.
- **partial lazy infrastructure:** src/vs/workbench/services/extensions/common/lazyCreateExtensionHostManager.ts already supports LazyAutoStart, but its start method creates the actual host whenever any extensions are assigned to it; this is not activation-triggered. NativeExtensionHostFactory uses that mode for extensions.webWorker='auto', while BrowserExtensionHostFactory remains eager.
- **protected maintainer request:** https://github.com/microsoft/vscode/issues/143924 was authored by a repository member and remains assigned to the On Deck milestone with extension-host and web routing labels.
