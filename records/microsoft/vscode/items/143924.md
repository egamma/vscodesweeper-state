# Issue #143924 — Delay starting the web worker extension host until activating first extension

[https://github.com/microsoft/vscode/issues/143924](https://github.com/microsoft/vscode/issues/143924)

## Summary

The requested startup optimization remains unimplemented: current web startup creates the worker extension host after extension discovery whenever it has extensions, rather than waiting for the first activation. This team-authored On Deck item should remain open for an extension-host design decision.

## Change summary

Delay creation of the web worker extension host until a hosted extension is first activated.

## Best solution

Preserve extension discovery and contribution registration without creating the worker iframe, then instantiate the host when a direct or event-based activation first targets one of its extensions. Early, unrelated, and non-matching activation events must not start it.

- **Fit:** aligned
- **Reason:** Avoiding an unused worker and iframe improves web startup cost without removing extension capability.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/browser/extensionService.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/services/extensions/common/lazyCreateExtensionHostManager.ts`, `src/vs/workbench/services/extensions/common/extensions.ts`, `src/vs/workbench/services/extensions/test/browser/extensionService.test.ts`
- **Validation:** Add a targeted extension-service test with a fake local web-worker host proving that discovery and non-matching activation events do not call host start, while the first matching direct or event-based activation starts it exactly once and activates the extension.
- **Behavior:**

  > In VS Code for the web, discovering installed web extensions must not create the web worker extension-host iframe. The host starts exactly once when the first extension assigned to it needs activation, and that activation completes normally. Activation events with no matching web extension must leave the host stopped; subsequent activations must preserve existing behavior.
- **Trace:**

  > BrowserExtensionHostFactory in src/vs/workbench/services/extensions/browser/extensionService.ts currently marks the initial LocalWebWorker host EagerManualStart. AbstractExtensionService._initialize resolves extensions and then _startOnDemandExtensionHosts calls start() for that host. LazyCreateExtensionHostManager.start in src/vs/workbench/services/extensions/common/lazyCreateExtensionHostManager.ts creates the actual manager whenever its assigned-extension list is non-empty, so creation is delayed only until scanning, not until activation. Commit 557b8bf33e53e04ff20f722c916789e1226631f0 introduced the current manual-start behavior for a separate regression. The boundary is web-worker-host startup: extension scanning, contribution availability, remote-host routing, restart behavior, and eager local-process hosts must remain unchanged.
- **Open decisions:**
  - Should the existing LazyAutoStart mode acquire true activation-triggered semantics, or should a distinct startup mode represent hosts that have assigned extensions but remain dormant?
  - How should a dormant manager determine whether activateByEvent targets one of its extensions without starting the worker, including startup and workspaceContains activation events?
  - Which operations besides extension activation, such as inspection, tests, extension installation, or restart recovery, must force creation of the dormant host?

## Evidence

- **current startup path:** src/vs/workbench/services/extensions/browser/extensionService.ts selects ExtensionHostStartup.EagerManualStart for the initial LocalWebWorker host; AbstractExtensionService._startOnDemandExtensionHosts subsequently starts every non-EagerAutoStart host after extension discovery.
- **lazy behavior gap:** src/vs/workbench/services/extensions/common/lazyCreateExtensionHostManager.ts documents lazy creation, but start() creates the actual ExtensionHostManager as soon as myExtensions is non-empty rather than waiting for activate() or a matching activateByEvent() call.
