# Issue #143924 — Delay starting the web worker extension host until activating first extension

[https://github.com/microsoft/vscode/issues/143924](https://github.com/microsoft/vscode/issues/143924)

## Summary

Still open: the browser extension service (vscode.dev) eagerly starts the web worker extension host. The lazy-start infrastructure exists (`LazyAutoStart`, `LazyCreateExtensionHostManager`) and is used on the desktop path, but `BrowserExtensionHostFactory.createExtensionHost` always uses `EagerManualStart`/`EagerAutoStart` — never `LazyAutoStart`.

## Change summary

Delay starting the web worker extension host until an extension actually needs to activate, improving startup performance.

## Best solution

Update `BrowserExtensionHostFactory.createExtensionHost` in `src/vs/workbench/services/extensions/browser/extensionService.ts` (line ~246) to use `ExtensionHostStartup.LazyAutoStart` so the web worker extension host is only created when an extension activation is requested, mirroring the desktop lazy behavior.

## Evidence

- **desktop path already lazy:** src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts line 577: desktop web worker uses `LazyAutoStart` when `LocalWebWorkerExtHostEnablement.Lazy`.
- **lazy infrastructure exists:** src/vs/workbench/services/extensions/common/lazyCreateExtensionHostManager.ts: `LazyCreateExtensionHostManager` delays creating the real extension host manager until extensions are present, used when `startup === ExtensionHostStartup.LazyAutoStart` (abstractExtensionService.ts line 866).
