# Issue #100717 — View undo/redo history visually or an indicator or a counter

[https://github.com/microsoft/vscode/issues/100717](https://github.com/microsoft/vscode/issues/100717)

## Summary

Keep this accepted, well-supported request open: Local History does not expose the live redo state, and the inspected undo/redo commands do not provide the requested visual feedback. A maintainer should settle the presentation and scope before implementation.

## Change summary

Expose undo/redo history or a compact availability indicator or counter so users can recognize pending redo changes before editing.

## Best solution

Provide discoverable feedback about the active editor's undo/redo state without requiring users to execute undo or redo to inspect it. Decide whether compact availability feedback is sufficient or whether a navigable history surface is required, while preserving existing undo grouping and workspace-operation semantics.

## Plan brief

- **Likely files:** `src/vs/editor/browser/editorExtensions.ts`, `src/vs/editor/common/editorContextKeys.ts`, `src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts`, `src/vs/platform/undoRedo/common/undoRedo.ts`, `src/vs/platform/undoRedo/common/undoRedoService.ts`
- **Validation:** End the plan with an executable UI check: edit file A, undo, switch to file B, return to A, and verify that the chosen surface reports available redo without executing it. Verify that redo exhaustion and a new edit update that feedback, switching files selects the intended state, and inspecting feedback does not alter either stack. Include a workspace rename/refactoring case to check the agreed resource/global semantics.
- **Behavior:**

  > Users should be able to recognize available redo changes without invoking redo or undo merely to inspect the state. In the reported workflow, undo in file A, switch to another file, and return to A; the chosen feedback must accurately expose A's pending redo state before another edit discards it. Feedback must update when undo, redo, or a new edit changes availability, and viewing it must not modify history. Saved-file Timeline entries alone do not satisfy this live-state requirement.
- **Trace:**

  > IUndoRedoService in src/vs/platform/undoRedo/common/undoRedo.ts exposes per-resource past/future entries and availability queries. ResourceEditStack.pushElement in src/vs/platform/undoRedo/common/undoRedoService.ts clears future entries, while getElements exposes the current stacks. EditorContextKeys.canUndo/canRedo and their updates in src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts provide existing editor-local state hooks; src/vs/editor/browser/editorExtensions.ts registers static undo/redo menu entries without the requested feedback. LocalHistoryTimeline instead reads working-copy history entries and is not a live stack viewer. Preserve current grouping, history retention, keyboard commands, and cross-resource operation behavior; branching-history preservation is separate work tracked by https://github.com/microsoft/vscode/issues/20889. Operation-specific menu labels in https://github.com/microsoft/vscode/issues/91370 are related but narrower. The unresolved boundary is the visible surface and whether its state represents the active file or workspace operations.
- **Open decisions:**
  - Should the initial feature expose compact undo/redo availability, a numeric counter, or a navigable history list?
  - Should the displayed state represent only the active file, or also expose workspace-wide undo/redo operations, and how should users distinguish those scopes?
