# Issue #350337 — copilot-runtime.exe uses ~11 GB of RAM when the Agents window resumes a large session on launch

[https://github.com/microsoft/vscode/issues/350337](https://github.com/microsoft/vscode/issues/350337)

## Summary

Keep open: current source still allows history restoration to resume the Copilot runtime, but the reported 11 GB retention has not been independently confirmed. The supplied launch steps, process measurements, versions, and journal size suffice to retest; no verified fix or canonical covers the complete memory problem.

## Change summary

Restoring a large Copilot session on Agents window launch leaves copilot-runtime.exe holding approximately 11 GB of private memory.

## Best solution

Establish which allocations remain resident in the runtime after large-session restoration, then deliver bounded history loading across the runtime and VS Code restore boundary. Avoiding unnecessary eager resumes should complement, not substitute for, resolving excessive memory use when the session is actually opened.

## Evidence

- **Detailed process-specific report:** https://github.com/microsoft/vscode/issues/350337 identifies Windows stable 1.147.0, runtime 1.0.111-0, a 2,605 MB events.jsonl, a 19.54-second SDK resume, and approximately 10,869 MB private memory in copilot-runtime.exe rather than the agent host. Loading the entire journal is the reporter's hypothesis, not a confirmed allocation diagnosis.
- **Current eager restoration path:** src/vs/platform/agentHost/node/copilot/copilotAgent.ts:9752-9805 uses persisted-only history for specific cold-chat conditions; other history reads call _ensureResolvedChatSession. listSessionCanvases at lines 3563-3574 also resolves a runtime outside its cold-path guard. copilotSessionLauncher.ts:1343-1356 delegates resume to plan.client.resumeSession.
- **Paging does not establish bounded retention:** copilotAgent.ts:_doReadPersistedChatHistory requests persisted events in pages of 1,000. However, src/vs/platform/agentHost/node/copilot/copilotSessionHistory.ts:25-59 retains filtered pages and returns their flattened contents. This establishes host-side accumulation, not the cause of the child runtime's reported 11 GB footprint.
- **Related issues do not own the complete defect:** Verified open https://github.com/microsoft/vscode/issues/347653 concerns agent-host V8 OOM and crash loops; https://github.com/microsoft/vscode/issues/344559 concerns eager resume and journal replay latency; https://github.com/microsoft/vscode/issues/348200 concerns a redundant first-send restart. Their fixes could reduce startup work without bounding runtime memory during an intentional resume, so none is a verified full-scope duplicate.
- **Additional memory candidate differs:** Verified open https://github.com/microsoft/vscode/issues/343357 reports growing agent-host memory and CPU while explicitly describing low copilot-runtime usage, unlike this report.
- **Verification limits:** Read-only source inspection did not reproduce or measure runtime allocations. No open PR referencing 350337 was returned by the PR search, and no concrete fixing commit was established. The checkout remained clean.
