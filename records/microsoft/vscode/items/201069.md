# Issue #201069 — Cannot test Web Extensions in WSL2 or Dev Containers

[https://github.com/microsoft/vscode/issues/201069](https://github.com/microsoft/vscode/issues/201069)

## Summary

Remote-source web-extension development remains unsupported in the desktop host, and the existing browser/local-source workarounds do not cover the requested WSL2 and Dev Containers workflow. Keep this accepted Backlog request open; the older related activation issue does not establish the same development-host symptom.

## Change summary

Support running and debugging web extensions whose development source resides in WSL2 or a Dev Container.

## Best solution

Enable remote-source web extensions to run in the desktop web extension development host while preserving normal locally installed extension behavior. Until that capability is supported, document the limitation and provide an actionable diagnostic instead of exposing commands that cannot activate.

Compare with local Windows development and a normally installed published web extension. If the agreed scope is only an interim diagnostic, verify that the same unsupported launch produces a clear actionable message.
- **Behavior:**

  > A generated web extension developed in WSL2 or a Dev Container currently fails to run in the desktop Extension Development Host, although local Windows development works. The requested end state is remote-source web-extension development with working command activation and debugging, without moving source to the local filesystem or switching to a browser. Acceptance should cover both remote environments and preserve local development and published-extension runtime behavior. An interim diagnostic or documentation improvement must identify the unsupported development scenario without implying that published web extensions cannot run in remote workspaces.
- **Trace:**

  > The maintainer explicitly identifies remote-source web-extension development as unsupported at https://github.com/microsoft/vscode/issues/201069#issuecomment-2044507213. In nativeExtensionService.ts, the desktop ExtensionService disables allowRemoteExtensionsInLocalWebWorker, and NativeExtensionHostKindPicker.pickExtensionHostKind requires isInstalledLocally before selecting LocalWebWorker for a web extension. The extensionDevelopmentKind='web' launch option and extensions.webWorker setting enable a worker but do not bypass this placement restriction. Related routing and initialization surfaces are abstractExtensionService.ts, extensionRunningLocationTracker.ts, and webWorkerExtensionHost.ts; the trace has not established the complete remote-resource loading and debugging design. Preserve normal published-extension placement and local development behavior rather than treating this as a Remote-WSL extension defect. https://github.com/microsoft/vscode/issues/144513 concerns browser-origin resource loading and is related, not a verified duplicate of this desktop development workflow.
- **Open decisions:**
  - Should the first scoped change provide full desktop remote-source web-extension development support, or only an explicit unsupported-scenario diagnostic and documentation while full support remains tracked?
