# Issue #340508 — Agent Host: open canvases close when a send triggers a session configuration refresh

[https://github.com/microsoft/vscode/issues/340508](https://github.com/microsoft/vscode/issues/340508)

## Summary

Clean, well-diagnosed report with exact code pointers that still match current main line-for-line; a session configuration refresh treats an in-use chat like a fresh SDK residency, so the Agents window closes open canvases and never re-projects them even though the runtime still has them open.

## Change summary

A message send that triggers an Agent Host session configuration refresh (e.g. clientPluginsChanged) destroys and resumes the SDK session, which clears and never restores the chat's open canvas tabs in the Agents window.

## Best solution

Carry projected canvas state across a configuration-triggered session refresh (capture before destroy, resume with ResumeSessionConfig.openCanvases, don't ignore carried instances) instead of treating the refresh as a new residency that clears canvases — as the reporter's proposed fix outlines.

- **Behavior:**

  > When a chat's Agent Host session is refreshed mid-conversation due to a configuration change (e.g. clientPluginsChanged on send), any canvas open in that chat must remain visible in the Agents window — at most showing a temporarily-unavailable state while the provider reconnects — and must not require the agent to call open_canvas again to bring it back. Acceptance: a test simulating a config-refresh resume confirms the canvas tab/resource for a given instanceId survives the refresh.
- **Trace:**

  > destroySession in copilotAgentSession.ts (around line 4907) unconditionally calls _clearCanvasProjection (line 3336), which publishes an empty ChatCanvasesChanged that sessionCanvasService.ts (src/vs/sessions/contrib/canvases/electron-browser/sessionCanvasService.ts:104) treats as authoritative and closes the canvas editors. The replacement session's initializeSession (copilotAgentSession.ts:3209-3212) then adds every previously-open instance to _ignoredRestoredCanvasInstanceIds, so the runtime's rehydration session.canvas.opened events are dropped at line 9047. The boundary: a genuine new SDK residency (fresh session, not a same-chat refresh) must still start with an empty canvas collection per AGENT_HOST_SESSIONS_PROVIDER.md — do not change that path. Where the uncertainty starts: exactly how carried-but-reconnecting canvases should be represented (URL-less placeholder vs. different UI state) and how reconciliation against rpc.canvas.list() after projection becomes ready should be sequenced relative to the dropped rehydration events.
- **Open decisions:**
  - Should a carried canvas show a distinct 'reconnecting' UI state (no URL) or just silently wait, and does this differ from how extension-host reloads currently present reconnecting canvases?
  - Should reconciliation with rpc.canvas.list() after projection readiness fully replace the carried state, or merge with it, when the two disagree about which canvases are open?
