# Issue #335378 — Browser client tools never return: completions forwarded with source=client-dispatch are never delivered to the pending tool_use

[https://github.com/microsoft/vscode/issues/335378](https://github.com/microsoft/vscode/issues/335378)

## Summary

Thanks for the exceptionally detailed report — the log trace (tool succeeds in tens/hundreds of ms, a `Forwarding client tool completion: source=client-dispatch` line fires, but the pending `tool_use` never resolves) is a credible, well-instrumented repro of a real hang in the Agent Host client-tool completion path. I traced the general `onClientToolCallComplete` → `completeClientToolCall` → `_pendingClientToolCalls.respond` flow in `claudeAgentSession.ts`/`agentSideEffects.ts` and it looks structurally sound and is covered by unit tests for the common case, so the defect is likely a narrower race or routing gap specific to how browser-view client tools (`readPage`, `openBrowserPage`, `runPlaywrightCode`) are dispatched/registered versus ordinary server-side tools — not something I can conclusively pin down from source alone.

## Change summary

Browser client tool calls (readPage, openBrowserPage, runPlaywrightCode) complete successfully but their result is never delivered to the pending tool_use when forwarded with source=client-dispatch, hanging the turn indefinitely and leaving it uncancellable; a secondary bug drops steering messages sent during the hang.

## Best solution

Have the Agent Host / browser-view tool-dispatch owners add tracing (or a reproducible integration test) around the client-dispatch completion path for browser tools specifically — likely in how browserView tools register with the active-client tool registry vs. how `AgentSideEffects._notifyClientToolCallComplete` / `completeClientToolCall` resolve the parked deferred — since the general client-tool-completion mechanism is otherwise well-tested and appears correct for non-browser tools.
