# Issue #335378 — Browser client tools never return: completions forwarded with source=client-dispatch are never delivered to the pending tool_use

[https://github.com/microsoft/vscode/issues/335378](https://github.com/microsoft/vscode/issues/335378)

## Summary

Credible, well-instrumented bug: browser client tools in the Claude Agent Host harness hang indefinitely because a forwarded `client-dispatch` tool completion never reaches the pending `tool_use`, and a second reporter shows a related variant where the turn ends before the tool is even dispatched. Root cause isn't pinned down from source alone — it needs reproduction with the reporter's debug bundle before a fix is scoped.

## Change summary

Browser client tools (readPage, openBrowserPage, runPlaywrightCode) dispatched through the Agent Host's client-tool path hang forever — the tool runs and a completion is logged, but it's never delivered back to the waiting model turn, and Stop/interrupt can't cancel it either.

## Best solution

A maintainer should reproduce with the reporter's agenthost.log/debug bundle to confirm which async handoff drops the completion (the in-process MCP tool registration race in claudeAgentSession.ts/claudeClientToolMcpServer.ts, or the ChatService turn-tracking desync noted in the secondary evidence), then land a targeted fix plus a timeout/cancellation path so a dropped completion doesn't hang a turn forever.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentSideEffects.ts`, `src/vs/platform/agentHost/node/claude/claudeAgentSession.ts`, `src/vs/platform/agentHost/node/claude/clientTools/claudeClientToolMcpServer.ts`, `src/vs/platform/agentHost/common/pendingRequestRegistry.ts`
- **Validation:** After the root cause is confirmed, add a regression test (likely in pendingRequestRegistry.test.ts or an AgentSideEffects/claude session test) that reproduces the race/mismatch that drops a client-dispatch completion, and assert the pending tool_use resolves instead of hanging; it should fail before the fix and pass after.
- **Behavior:**

  > Calling a browser client tool (readPage, openBrowserPage, runPlaywrightCode) through the Claude Agent Host harness must always resolve the model's pending tool_use once the client reports a result — success or failure — within a bounded time, and the turn must remain cancellable (Stop must work) the whole time. Today the tool runs successfully, the host logs 'Forwarding client tool completion: source=client-dispatch', but the SDK's pending tool_use is never resolved, so the turn sits on Processing forever and Stop reports nothing to cancel.
- **Trace:**

  > The completion path is: workbench runs the tool and dispatches `ChatToolCallComplete` -> `agentSideEffects.ts` `_applyClientAction` switch (line 1873) calls `_notifyClientToolCallComplete(..., 'client-dispatch')` (line 1445), which logs and calls `agent.onClientToolCallComplete` -> `ClaudeAgent.onClientToolCallComplete` (claudeAgent.ts:2549) -> `session.completeClientToolCall` (claudeAgentSession.ts:1396) -> `PendingRequestRegistry.respond(toolCallId, ...)`. `respond()` is a no-op (returns false, drops the value) if no deferred is parked under that id — unlike `respondOrBuffer`, which is used elsewhere for exactly this kind of race. The deferred is parked by the in-process MCP tool handler in claudeClientToolMcpServer.ts when the SDK actually invokes it, which may not have happened yet when the host-side log line fires. This is a plausible but unconfirmed root cause; do not assume it without tracing the actual timing in the reporter's debug bundle — the secondary report (no dispatch at all) suggests a related but separate issue further upstream, possibly in turn/result sequencing (see also https://github.com/microsoft/vscode/issues/335299). Do not conflate the fix for this with the UI steering-message-vanishes secondary bug described in the same issue (a separate `ProtocolServer subscribe` failure on the changeset resource) — that is a distinct defect and should likely be its own follow-up.
- **Open decisions:**
  - Which of the plausible drop points (SDK in-process MCP registration race, agentSideEffects routing, or ChatService/turn-tracking desync noted in the secondary report) is the actual cause — needs a debug-bundle trace to confirm before scoping the fix.
  - Should resolving this also add a timeout/forced-cancellation safety net for client-dispatch tool completions, so a future dropped completion degrades to a failed tool call instead of hanging the turn indefinitely?
