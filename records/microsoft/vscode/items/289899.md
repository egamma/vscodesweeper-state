# Issue #289899 — Don't ask to enable workspace trust in system folders and temp directories

[https://github.com/microsoft/vscode/issues/289899](https://github.com/microsoft/vscode/issues/289899)

## Summary

A real workspace-trust UX gap remains on current main: startup prompting has no path-sensitive exemption for system roots, home directories, or temporary directories. The issue should stay open while maintainers define the safe cross-platform folder set and resulting restricted-mode behavior.

## Change summary

Avoid presenting the workspace-trust startup dialog when opening folders where making a persistent trust decision is not meaningful, such as temporary or system-root directories.

## Best solution

Define a conservative, platform-aware set of folders for which the startup trust modal is suppressed while the workspace remains untrusted and restricted-mode indicators continue to communicate its state. Preserve prompts for ordinary project folders and mixed workspaces unless maintainers explicitly choose otherwise.

- **Behavior:**

  > Opening an approved system-root, home, or temporary directory must not show the workspace-trust startup dialog when a persistent trust choice would be meaningless. The folder must remain in the maintainer-selected safe state, with restricted-mode status or banner behavior preserved as specified. Ordinary project folders must continue to follow `security.workspace.trust.startupPrompt`. Acceptance must cover the approved path categories on Linux, macOS, and Windows and at least one ordinary project path.
- **Trace:**

  > The startup decision is made by `WorkspaceTrustUXHandler.showModalOnStart` in src/vs/workbench/contrib/workspace/browser/workspace.contribution.ts. Its current guards cover trusted workspaces, immutable trust, virtual and empty workspaces, and the global startup-prompt preference; no guard examines local paths. Trust resolution in `WorkspaceTrustManagementService.doGetUriTrustInfo` in src/vs/workbench/services/workspaces/common/workspaceTrust.ts likewise has no system/temp classification. The existing `security.workspace.trust.startupPrompt: never` option is global and therefore does not satisfy selective suppression. Keep normal project-folder trust decisions and stored trusted-parent semantics unchanged; the uncertainty starts at which paths qualify and how multi-root workspaces containing both qualifying and ordinary folders behave.
- **Open decisions:**
  - Which exact platform-specific locations qualify: only filesystem roots and the OS-reported temporary directory, or also user home and descendants?
  - When the modal is suppressed, should the folder remain untrusted with the existing restricted-mode banner/status behavior, or should any indicator behavior also change?
  - Should a multi-root workspace suppress the prompt only when every folder qualifies, or when any qualifying folder is present?

## Evidence

- **current source gap:** src/vs/workbench/contrib/workspace/browser/workspace.contribution.ts:489-522 (`WorkspaceTrustUXHandler.showModalOnStart`) suppresses the modal for trusted, immutable-trust, virtual, and empty workspaces and according to the global startup-prompt setting, but does not inspect local folder paths.
- **existing capability is only global:** The `security.workspace.trust.startupPrompt` setting registered in src/vs/workbench/contrib/workspace/browser/workspace.contribution.ts supports `always`, `once`, or `never`; it cannot suppress prompts only for system or temporary folders while retaining them for meaningful project folders.
- **trust model has no path classification:** src/vs/workbench/services/workspaces/common/workspaceTrust.ts (`doGetUriTrustInfo` and `isTrustedVirtualResource`) handles stored trusted parents, virtual resources, remote trust, and agent-session workspaces, but contains no system-root, home-directory, or OS-temp classification.
