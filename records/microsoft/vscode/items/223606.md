# Issue #223606 — Auto indent issue: Lua multiline quotes `[[...]]` conflict with #210641 which removes brackets before passing text to indent rules

[https://github.com/microsoft/vscode/issues/223606](https://github.com/microsoft/vscode/issues/223606)

## Summary

Keep open: current source still strips Lua long-string and long-comment delimiters before indentation rules run, exposing string keywords and obscuring executable code after comments. The issue already has the correct area label; no verified fix or eligible older canonical was established.

## Change summary

Prevent indentation preprocessing from misinterpreting Lua keywords inside long strings and comments while preserving keywords outside them.

## Best solution

Make Lua indentation distinguish executable keywords from long-string and comment contents without losing token boundaries. Establish the compatibility contract before changing shared preprocessing, which also feeds other languages' Enter rules.

- **Behavior:**

  > Lua indentation must recognize executable keywords without treating keywords inside long strings or comments as code. Pressing Enter after if s == [[then]] must not increase indentation, while an executable then following a closed long comment must still increase it. Compact code such as if"true"then must retain recognizable token boundaries. Long-string/comment continuation lines and existing non-Lua Enter behavior must remain correct.
- **Trace:**

  > In src/vs/editor/common/languages/supports/indentationLineProcessor.ts, getProcessedTokens deletes configured bracket characters from string, comment, and regex tokens but leaves their other text. Lua configures square brackets, so its long-string and block-comment delimiters are destroyed before ProcessedIndentRulesSupport evaluates the indentation regex. The same processing also supplies IndentationContextProcessor and getEnterAction in src/vs/editor/common/languages/enterAction.ts, making a universal whitespace-replacement policy broader than this Lua case. Existing processor tests preserve non-bracket string/comment text, and the Lua string-keyword test in indentation.test.ts is skipped. The reporter's whitespace proposal addresses token concatenation, but its global compatibility and continuation-line semantics remain unsettled. See https://github.com/microsoft/vscode/issues/223606; inspect the complete discussion and the disposition of https://github.com/microsoft/vscode/pull/230632 before implementation.
- **Open decisions:**
  - Should indentation regexes receive token-filtered text universally, changing the existing cross-language contract, or should existing languages retain their current input unless explicitly opted into different behavior?

## Evidence

- **Current source confirms delimiter loss:** src/vs/editor/common/languages/supports/indentationLineProcessor.ts: IndentationLineProcessor.getProcessedTokens applies text.replace(bracketsRegExp, '') to String, Comment, and RegEx tokens, preserving their remaining contents. With Lua's configured square brackets, [[then]] becomes then and --[[then]] becomes --then.
- **Current Lua rules expose the reported failure:** extensions/lua/language-configuration.json registers [ and ] as brackets. Its increaseIndentPattern matches then as an indentation keyword and excludes text after --. Consequently, the reported if s == [[then]] exposes a false keyword, while if s == --[[then]] then loses the distinction between the block comment and the following executable then.
- **Reporter refined the proposal:** The supplied discussion at https://github.com/microsoft/vscode/issues/223606 rejects deleting token contents outright because if"true"then would collapse into ifthen.
