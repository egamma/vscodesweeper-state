# Issue #233394 — Allow to pin/filter a tree node with all it's child elements

[https://github.com/microsoft/vscode/issues/233394](https://github.com/microsoft/vscode/issues/233394)

## Summary

Keep open: current tree filtering matches labels rather than isolating a selected node with all its descendants. The older Explorer scoping request covers only one consumer, not this broader, team-authored tree-widget request.

## Change summary

Allow users to focus a tree on selected subtrees while retaining all their child elements.

## Best solution

Define a reversible subtree-focus interaction for shared tree widgets, with Explorer and Outline as concrete consumers. Explicitly distinguish structural subtree focus from the related request to filter Call Hierarchy by source file or module.

- **Fit:** aligned
- **Reason:** A shared subtree-focus interaction would reduce clutter in large trees while keeping navigation consistent across workbench views.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/tree/abstractTree.ts`, `src/vs/base/browser/ui/tree/asyncDataTree.ts`, `src/vs/platform/list/browser/listService.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/outline/browser/outlinePane.ts`
- **Validation:** The plan should finish with a runnable tree-widget test showing that focusing a parent retains differently named descendants and hides unrelated branches, then restores the original tree when focus is cleared. Manually check the chosen Explorer and Outline interactions without changing workspace roots or exclusion settings.
- **Behavior:**

  > Users should be able to narrow a tree to a selected subtree and see its descendants even when their labels do not match a search string. Clearing that focus should restore the full tree without changing the underlying workspace. Explorer and Outline are explicit use cases. Acceptance must distinguish retaining descendants from merely retaining ancestors of text matches; whether multiple subtrees and semantic Call Hierarchy scope are included needs agreement.
- **Trace:**

  > FindFilter.filter in src/vs/base/browser/ui/tree/abstractTree.ts evaluates labels independently, so an ancestor match does not automatically retain unmatched descendants. ExplorerFindProvider in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts has a separate asynchronous search path over workspace roots, including directory-name discovery, rather than selected-node subtree focus. Outline uses the shared tree find modes in src/vs/workbench/contrib/outline/browser/outlinePane.ts. https://github.com/microsoft/vscode/issues/41860 tracks the Explorer-only case and should inform the design, but does not replace this broader issue. https://github.com/microsoft/vscode/issues/233185 records a Call Hierarchy request involving source-file/class scope, which structural subtree focus may not satisfy. Preserve existing text-search behavior, workspace roots, and user exclusion settings; the expanded-nodes-only search proposal was explicitly rejected in this thread. The uncertainty begins at the shared user interaction and whether semantic Call Hierarchy scoping belongs in this feature's acceptance contract.
- **Open decisions:**
  - Should users focus one subtree at a time, or retain several independently selected subtrees together?
  - Does this feature include Call Hierarchy filtering by source file, module, or class, or is that a separate request beyond structural subtree focus?

## Evidence

- **Existing capability does not cover the request:** src/vs/base/browser/ui/tree/abstractTree.ts:631–731, FindFilter.filter, scores each element's keyboard-navigation label independently and returns TreeVisibility.Recurse for unmatched elements in filter mode. Matching a parent does not establish a selected subtree whose descendants are all retained. workbench.list.defaultFindMode selects highlight versus filter, not subtree focus.
- **Explorer filtering remains search-based:** src/vs/workbench/contrib/files/browser/views/explorerViewer.ts:371–425 and 587–637, ExplorerFindProvider.startFilterSession/doFilterFind/searchInWorkspace, searches workspace roots for matching files and directories and marks results and their ancestors. Directory-name matching exists, but it does not provide a selected-node pin retaining all descendants.
