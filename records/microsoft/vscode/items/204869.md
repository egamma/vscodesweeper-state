# Issue #204869 — Allow hovers to opt in to wrapping content

[https://github.com/microsoft/vscode/issues/204869](https://github.com/microsoft/vscode/issues/204869)

## Summary

Keep open: current workbench hovers support text wrapping and some width constraints, but ordinary side-positioned hovers still flip position before attempting a narrower layout. The requested opt-in preference remains distinct from those capabilities, and no verified canonical or fixing commit was found.

## Change summary

Allow workbench hover producers to prefer wrapping content within the available space before repositioning the hover.

## Best solution

Provide an opt-in workbench hover layout policy that tries a narrower, wrapped layout at the preferred position before falling back to repositioning. Preserve existing positioning behavior for producers that do not opt in.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/hover/hover.ts`, `src/vs/platform/hover/browser/hoverWidget.ts`, `src/vs/platform/hover/test/browser/hoverService.test.ts`
- **Validation:** Extend the HoverService layout tests with opted-in side-positioned text hovers under constrained width: assert wrapping retains the preferred side when viable, repositioning remains available when it is not, and non-opted-in behavior is unchanged. Manually inspect the Manage Trusted Extensions tooltip in progressively narrower windows.
- **Behavior:**

  > An opted-in workbench hover should prefer wrapping its readable text into the available space at its preferred position before moving to another position. Repositioning must remain available when the narrowed layout is unsuitable. Hovers without the opt-in retain their existing behavior. Acceptance should cover narrow and wide windows, both left and right positioning, and preservation of readable content.
- **Trace:**

  > In src/vs/platform/hover/browser/hoverWidget.ts, plain-string content already uses pre-wrap, but adjustHorizontalHoverPosition compares the current width with the available side space and flips or moves BELOW without first trying a narrower layout. IHoverPositionOptions in src/vs/base/browser/ui/hover/hover.ts has forcePosition, which constrains size but bypasses normal repositioning, and right-aligned vertical hovers have a separate width constraint. The reported authentication tooltip now includes a manual newline in manageTrustedExtensionsForAccountAction.ts; that does not establish adaptive behavior. Existing geometry tests live in src/vs/platform/hover/test/browser/hoverService.test.ts. Preserve default hover behavior and keep authentication access semantics out of scope. The remaining uncertainty is the user-visible threshold at which wrapping becomes less suitable than repositioning.
- **Open decisions:**
  - For opted-in hovers, what minimum readable width or maximum acceptable wrapped height should trigger repositioning instead of retaining the preferred side?
