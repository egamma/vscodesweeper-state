# Issue #126997 — Revisit `options.override`

[https://github.com/microsoft/vscode/issues/126997](https://github.com/microsoft/vscode/issues/126997)

## Summary

The debt remains on current main: editor selection is still stored as `IEditorOptions.override`, and editor matching and resolution continue to probe and mutate that option. The requested API cleanup is cross-cutting and still needs a maintainer decision about typed-input and special-resolution semantics.

## Change summary

Separate an untyped input's editor identity or selection from its transient open options instead of representing it as `options.override`.

## Best solution

Give untyped editor inputs a clear top-level editor-selection contract while preserving deliberate default, picker, exclusive-editor, diff, side-by-side, and custom-editor behavior. Before implementation, decide whether a typed input's own `editorId` is always authoritative and how non-ID resolution modes are represented.

## Plan brief

- **Likely files:** `src/vs/platform/editor/common/editor.ts`, `src/vs/workbench/common/editor.ts`, `src/vs/workbench/common/editor/editorInput.ts`, `src/vs/workbench/services/editor/browser/editorResolverService.ts`, `src/vs/workbench/services/editor/test/browser/editorService.test.ts`, `src/vs/workbench/test/browser/parts/editor/editorInput.test.ts`
- **Validation:** Extend the editor service and EditorInput unit suites to cover editor-ID selection for untyped resource, diff, merge, side-by-side, and untitled inputs; picker and exclusive-only resolution; matching by resource plus editor identity; and the chosen typed-input override behavior.
- **Behavior:**

  > An untyped editor input identifies or selects its editor independently from transient open behavior such as focus, activation, pinning, and stickiness. Opening and matching the same resource with different editor IDs remains deterministic, while default selection, picker selection, and exclusive-editor selection retain their intended behavior. Diff, merge, side-by-side, untitled, custom, and typed inputs must follow an explicitly documented rule. Acceptance is covered by focused editor service and EditorInput tests for each input form and resolution mode.
- **Trace:**

  > `IBaseUntypedEditorInput` in `src/vs/platform/editor/common/editor.ts` currently owns only an `options` bag, and `IEditorOptions.override` carries both string editor IDs and `EditorResolution` modes. `EditorInput.matches` in `src/vs/workbench/common/editor/editorInput.ts` probes that nested option, while `EditorResolverService.resolveEditor` in `src/vs/workbench/services/editor/browser/editorResolverService.ts` reads and rewrites it during resolution. Existing editor-service tests show that typed inputs may carry the option but are not re-resolved through it, leaving the contract unclear. Composite input definitions in `src/vs/workbench/common/editor.ts` and their differing diff/side-by-side semantics are part of the boundary. Preserve current user-visible editor selection and matching behavior; do not fold in the distinct pre-resolution group-selection work tracked by https://github.com/microsoft/vscode/issues/131619.
- **Open decisions:**
  - When `openEditor` receives a typed `EditorInput`, is that input's own `editorId` always authoritative, or must callers remain able to request a different editor for the same resource?
  - Should the top-level contract require a concrete editor ID, or support a discriminated selection value that also represents default resolution, picker selection, and exclusive-only resolution?
  - For compound inputs, should diff and merge use one top-level editor selection while side-by-side continues selecting each side independently?

## Evidence

- **current API:** On current main, `src/vs/platform/editor/common/editor.ts` defines `IBaseUntypedEditorInput.options?: IEditorOptions`, while `IEditorOptions.override?: string | EditorResolution` still combines editor IDs with `PICK` and `EXCLUSIVE_ONLY` resolution modes.
- **matching path:** `src/vs/workbench/common/editor/editorInput.ts` still implements `EditorInput.matches` by reading `otherInput.options?.override` and comparing it with the typed input's `editorId`, exactly the coupling called out in the report.
- **resolver path:** `src/vs/workbench/services/editor/browser/editorResolverService.ts` reads `options.override` for picker and editor selection, then writes the selected editor ID back into `untypedEditor.options` so matching works.
- **scope:** Current source has override-dependent callers and tests across editor groups, preferences, custom editors, notebooks, browser editors, chat, files, and user-data sync; `src/vs/workbench/services/editor/test/browser/editorService.test.ts` also explicitly exercises typed inputs carrying override options.
- **canonical search:** The related open https://github.com/microsoft/vscode/issues/131619 is younger and concerns group selection before untyped inputs are resolved, not the same API-shape debt, so it is not a valid canonical duplicate for this re-reviewed item.
