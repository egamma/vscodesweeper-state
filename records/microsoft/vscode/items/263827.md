# Issue #263827 — Make installing a specific version disable auto update until update is clicked

[https://github.com/microsoft/vscode/issues/263827](https://github.com/microsoft/vscode/issues/263827)

## Summary

A real gap remains on current main: selecting a specific gallery version pins the extension and suppresses auto-update, but clicking Update preserves that pin instead of resuming normal update behavior. This team-authored Backlog item must remain open, and no older issue with the same observable request was verified as a canonical duplicate.

## Change summary

Keep an extension pinned after installing a specific version until the user explicitly clicks Update, then resume its normal auto-update behavior.

## Best solution

Retain the existing version pin after a specific-version install, but clear that pin when the user explicitly updates the extension from the Extensions UI; subsequent automatic updates should then follow the global and per-extension auto-update configuration.

- **Behavior:**

  > Installing a specific extension version must prevent that extension from being automatically upgraded. When the user explicitly clicks Update, the latest compatible version is installed and the temporary version pin is removed, allowing later automatic updates according to the existing global and per-extension settings. VSIX installs and globally disabled auto-update behavior must retain their established semantics.
- **Trace:**

  > InstallAnotherVersionAction in src/vs/workbench/contrib/extensions/browser/extensionsActions.ts passes a selected version into ExtensionsWorkbenchService.install. ExtensionsWorkbenchService maps that to installGivenVersion, and the node/web extension management services persist pinned=true; shouldAutoUpdateExtension rejects pinned extensions. UpdateAction currently sets pinned=false only for a pinned VSIX source, while installFromGallery otherwise inherits extension.local.pinned, so an explicit update of a gallery version remains pinned. The pin is shared with CLI installs, profiles, Settings Sync, remote/web installs, and VSIX handling; those consumers must not have their persistence semantics broadened accidentally. The related broad proposal https://github.com/microsoft/vscode/issues/52116 is not a canonical issue for this specific lifecycle.
