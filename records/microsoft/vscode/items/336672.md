# Issue #336672 — Agents window "Changes" stuck

[https://github.com/microsoft/vscode/issues/336672](https://github.com/microsoft/vscode/issues/336672)

## Summary

Traced a plausible root cause in the multi-diff editor's eager item resolution, which has no cap on file count and would explain a freeze on a 4700-file/700k-line diff, but this is a single report with an extreme diff size and no confirmed repro, so keep it open rather than closing.

## Change summary

The Agents window's default 'Branch changes' panel stops responding when the underlying git diff is extremely large (thousands of files, hundreds of thousands of changed lines).

## Best solution

Give the multi-diff editor (or the session changes view specifically) a size/file-count threshold above which it shows a summary or lazy-loads items instead of eagerly creating a DocumentDiffItemViewModel + text models for every changed file at once.

## Plan brief

- **Likely files:** `src/vs/editor/browser/widget/multiDiffEditor/multiDiffEditorViewModel.ts`, `src/vs/sessions/contrib/changes/browser/sessionChangesService.ts`, `src/vs/sessions/contrib/changes/browser/changesView.ts`
- **Validation:** A reproduction with a very large synthetic diff (thousands of files) confirming the panel becomes responsive again once the fix is applied, plus a unit test asserting the view model does not eagerly create items beyond the chosen threshold.
- **Behavior:**

  > Opening the Agents window's 'Branch changes' panel on a session/branch with an extremely large diff (thousands of files, hundreds of thousands of changed lines) should not freeze the UI. Either the view should lazily resolve diff items as they scroll into view, or it should detect the diff is unusually large and show a lightweight summary/warning instead of eagerly diffing every file. Acceptance: the panel remains responsive and interactive even for such a diff.
- **Trace:**

  > MultiDiffEditorViewModel (src/vs/editor/browser/widget/multiDiffEditor/multiDiffEditorViewModel.ts) builds one DocumentDiffItemViewModel per changed document via `_createItem`, and its constructor awaits `Promise.all` over ALL items and their initial diffs before `isLoading` clears — there is no file-count/line-count cap or viewport-based deferral anywhere in this path or in the session changes contribution (src/vs/sessions/contrib/changes/browser/sessionChangesService.ts, changesView.ts). This plausibly explains why a 4700-file/700k-line diff hangs the panel, but this was traced from source only, not executed against a reproduction of that scale. Where uncertainty starts: whether the fix belongs generically in MultiDiffEditorViewModel (benefiting every multi-diff consumer) or narrowly in the sessions changes view, and whether the UX for an oversized diff is lazy virtualization or an explicit 'too large to display' fallback.
- **Open decisions:**
  - Should the fix live in the shared MultiDiffEditorViewModel (all multi-diff consumers benefit) or be scoped to the Agents window's session changes view only?
  - For an oversized diff, should the UI lazily resolve items as they scroll into view, or show a summary/warning and skip full diffing entirely?
  - What file-count or line-count threshold should trigger the fallback behavior?

## Evidence

- **eager resolution:** MultiDiffEditorViewModel (src/vs/editor/browser/widget/multiDiffEditor/multiDiffEditorViewModel.ts, lines 90-118) maps every document in `this._documentsArr` through `_createItem` via `mapObservableArrayCached(...).recomputeInitiallyAndOnChange`, then awaits `Promise.all(pending)` and `Promise.all(next.map(i => i.object.waitForInitialDiffOr1s.promise))` for ALL items — there is no cap, batching, or viewport-based lazy loading of diff items.
- **no size guard found:** Searched src/vs/workbench/contrib/multiDiffEditor and the sessions changes contribution (sessionChangesService.ts, changesView.ts, changesViewRenderer.ts) for a max-file/max-line threshold; none exists.
