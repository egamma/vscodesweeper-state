# Issue #26360 — Git - Support file stat mode changes

[https://github.com/microsoft/vscode/issues/26360](https://github.com/microsoft/vscode/issues/26360)

## Summary

Keep open: the built-in Git extension still represents executable-bit changes as ordinary modifications without explaining the mode transition. This remains the established report for that capability; the related closed reports do not provide a fixing commit or an eligible duplicate target.

## Change summary

Expose Git executable-bit changes in Source Control so users can understand changes that leave file contents identical, and investigate the reported discard and staging behavior.

## Best solution

Provide a clear, accessible indication of the old and new Git modes for staged and unstaged changes without altering textual diffs. Separately verify discard and staging against Git's index/worktree semantics, especially for index-only changes on Windows, before deciding whether those operations need changes.

## Plan brief

- **Likely files:** `extensions/git/src/repository.ts`, `extensions/git/src/git.ts`, `extensions/git/src/fileSystemProvider.ts`, `extensions/git/src/test/git.test.ts`
- **Validation:** In a disposable repository on a filesystem supporting executable bits, commit a script, change only its executable bit, and inspect both unstaged and staged Source Control entries. Verify that the selected UI explains each mode transition despite identical contents, handles combined content/mode changes, and leaves ordinary diffs unchanged. Check discard against git diff --summary, and separately exercise git update-index --chmod=+x on Windows to distinguish index-only changes from filesystem changes.
- **Behavior:**

  > A Git executable-bit change must be understandable in Source Control even when the file's text is unchanged. Users should be able to identify the direction of the mode transition for both staged and unstaged changes, including when textual changes also exist. Ordinary content diffs and staging semantics must remain unchanged. The reported ineffective discard and reversal after staging require separate reproduction against the relevant Git configuration and filesystem.
- **Trace:**

  > In extensions/git/src/repository.ts, getStatus() reduces Git status to generic Resource types, Resource.tooltip supplies generic status text, and ResourceCommandResolver.resolveChangeCommand() opens a content comparison. In extensions/git/src/fileSystemProvider.ts, readFile() obtains blob contents through the Git buffer path, which cannot itself explain metadata-only differences. extensions/git/src/git.ts getObjectDetails() already exposes mode metadata, but the inspected presentation path does not use it to describe mode transitions. Current clean() delegates tracked-file discard to Git checkout, so the historical discard failure is not conclusively diagnosed. Preserve the distinction between HEAD, index, and worktree and do not suppress legitimate mode changes or change core.fileMode as a workaround. The maintainer directed https://github.com/microsoft/vscode/issues/92060 here; https://github.com/microsoft/vscode/issues/43014 addresses a different partial-staging defect. The remaining product uncertainty is where mode information should appear and whether this work includes changes to operations beyond presentation.
- **Open decisions:**
  - Should executable-bit transitions be explained in the Source Control entry, the opened diff, or both?
  - Should the initial scope be mode-change presentation, with discard and index-only staging behavior handled separately after reproduction, or should those operation scenarios be included in this feature's acceptance contract?

## Evidence

- **Current source still lacks mode presentation:** At checkout eef761e9628e777317a554114f0202a070e98f0b, extensions/git/src/repository.ts maps porcelain M statuses to MODIFIED or INDEX_MODIFIED in getStatus(); Resource.tooltip returns only the generic status text. ResourceCommandResolver.resolveChangeCommand() opens vscode.diff with content URIs, while extensions/git/src/fileSystemProvider.ts readFile() obtains ordinary file contents through repository.buffer().
