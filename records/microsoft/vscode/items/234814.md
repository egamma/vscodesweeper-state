# Issue #234814 — Git - Command `git.openFile` does not do the same thing as the "Open File" icon button on a file that has been committed in diff view

## Summary

The keybinding still reopens a read-only Git revision on current main, unlike the editor-title button. Keep this issue open while the explicitly linked fixing PR is reviewed and landed.

## Change summary

Make git.openFile invoked without arguments open the editable working-tree file from a committed diff, matching the Open File button.

## Evidence

- **Current-source defect:** In extensions/git/src/commands.ts:1300–1326, CommandCenter.openFile converts an explicit git: URI to Uri.file(fromGitUri(arg).path), but its no-argument fallback uses window.activeTextEditor.document.uri unchanged. For the reporter's committed diff, that fallback passes the read-only git: revision to vscode.open rather than the working-tree file.
- **Post-commit trigger:** CommandCenter.getSCMResource in extensions/git/src/commands.ts:5710–5746 converts the active git: URI for lookup but returns only matching working-tree, index, or merge resource states. Once the committed file has no remaining changes, no resource matches, exposing openFile's unconverted active-editor fallback.
- **Command Palette discrepancy:** extensions/git/package.json:1264–1265 restricts the git.openFile Command Palette entry to resourceScheme == file && scmActiveResourceHasChanges, excluding the reported git: revision editor. The editor-title registrations at lines 2755–2768 expose the same command for Git diff and revision editors.
