## Plan brief

- **Likely files:** `src/vs/platform/sandbox/common/terminalSandboxEngine.ts`, `src/vs/platform/agentHost/node/copilot/sandboxConfigForSdk.ts`, `src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/tools/runInTerminalTool.ts`

- **Behavior:**

  > Setting `chat.agent.sandbox.allowNetwork` to true should relax network restrictions in the agent sandbox (while keeping filesystem restrictions), and false should keep network restricted. Currently toggling it produces no observable change for at least some users/platforms (confirmed on Fedora/snap and Windows), while at least one team member could not reproduce a difference either way. Acceptance: reproduce the exact scenario (likely involving a background/remote agent session or a specific OS sandbox runtime), find the code path where the flag is dropped or ignored, and confirm the flag has effect at that path with a targeted test.
- **Trace:**

  > The setting id `AgentSandboxSettingId.AgentSandboxAllowNetwork` / `AgentHostSandboxKey.AllowNetwork` is read in multiple independent places: terminalSandboxEngine.ts computes `allowNetwork` (via `_isSandboxAllowNetworkEnabled`/`_commandAllowNetwork`) and uses it to decide whether to send an empty vs. resolved domain list in the sandbox network payload (around line 661/720); sandboxConfigForSdk.ts maps it directly to `SandboxConfig.network.allowOutbound` for the Copilot SDK path (line 175/194); and settings are forwarded between remote and local hosts for isolated agent sessions (agentHostSandboxForwarder). No commit on main changes this recently (git log shows no matching change), and the failure mode isn't yet isolated to one of these paths — the maintainer thread was still probing configuration scope (workspace vs. user) as of the last comment. Do not assume the bug is in the terminal tool path alone; the reporter's screenshot suggests this may be exercised via a background/remote agent session rather than the interactive `run_in_terminal` tool.
