[https://github.com/microsoft/vscode/issues/342983](https://github.com/microsoft/vscode/issues/342983)

Keep open as performance debt: current source still commits each pending schema migration separately. The merged timeout adjustment described in the issue does not address migration batching; failure checkpoints and pre-release compatibility need consideration before implementation.

## Change summary

Reduce durable commits when opening a fresh or outdated agent-host database without weakening migration correctness or durability.

- **Behavior:**

  > Opening a new or outdated agent-host database should require fewer durable migration commits while producing the same final schema and preserving existing registrations and catalog data. Database durability must not be weakened to achieve the reduction. A migration failure must leave a consistent schema and user_version from which reopening can retry safely. Acceptance includes deterministic commit-count reduction and successful fresh, legacy, pre-release, and future-version compatibility checks.
- **Trace:**

  > AgentHostDatabase._ensureDatabase in src/vs/platform/agentHost/node/agentHostDatabase.ts reads user_version, calls normalizePreReleaseCatalogSchema, then wraps each pending migration in its own transaction. migrateChatV2Schema and migrateChatOriginSchema execute on the supplied connection; the normalizer owns a transaction in its catalog-rebuild branch, and existing-version repairs have another transaction after the migration loop. Current failure handling preserves previously committed migration steps, whereas a larger batch would roll those steps back together. The issue explicitly invites owner judgment about these boundaries: https://github.com/microsoft/vscode/issues/342983. Keep schema contents, migration order, durability settings, and older-build compatibility unchanged; the unresolved contract is which successful steps remain durable when a later migration fails.
- **Open decisions:**
  - When a later pending migration fails, may reopening observe the pre-batch schema/version with all work in that batch rolled back, or must any existing intermediate migration checkpoints remain durable?
