# Issue #309693 — Agents: Multiple sessions in same worktree cause changes Sync Pull Requests button to duplicate and to fire in the wrong session

[https://github.com/microsoft/vscode/issues/309693](https://github.com/microsoft/vscode/issues/309693)

## Summary

Keep open: the report has a maintainer-confirmed reproduction and describes session-state contamination that can invoke a pull-request operation in the wrong session. Current main has substantially changed this action pipeline, but the available checkout has no usable history identifying a fixing commit and no older same-symptom canonical owns the bug.

## Change summary

Multiple agent sessions sharing a worktree can render duplicate Sync Pull Request actions and execute the action against a session other than the one displayed.

## Best solution

Ensure the Changes action bar derives each pull-request operation from the displayed session and captures that session when invoked, with regression coverage for two sessions sharing one worktree and switching between them.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/changes/browser/changesView.ts`, `src/vs/sessions/contrib/changes/browser/changesActions.ts`, `src/vs/sessions/contrib/changes/browser/changesViewService.ts`, `src/vs/sessions/contrib/changes/test/browser/changesViewActions.test.ts`, `src/vs/sessions/contrib/changes/test/browser/changesViewService.test.ts`
- **Validation:** Create two agent sessions backed by the same worktree, give each distinct observable pull-request operations, repeatedly switch sessions, and verify that exactly one Sync Pull Request action is rendered and that invoking it records only the operation belonging to the displayed session; add an automated action-registration/dispatch regression test for that sequence.
- **Behavior:**

  > When multiple agent sessions share a worktree, the Changes surface must show only the actions belonging to the currently displayed session. Sync Pull Request must appear at most once and must execute against that displayed session even if another session was previously active. Switching between the sessions must update the button and its count without retaining actions or callbacks from the previous session.
- **Trace:**

  > The original report at https://github.com/microsoft/vscode/issues/309693 was independently confirmed by a team member. On current main, ChangesActionsBar in src/vs/sessions/contrib/changes/browser/changesView.ts rebuilds its widget from active-session observables, while ChangesetOperationsActionController in src/vs/sessions/contrib/changes/browser/changesActions.ts dynamically registers commands that capture the selected changeset and operation. The former built-in Sync Pull Request contribution in src/vs/sessions/contrib/providers/agentHost/browser/agentHostSkillButtons.ts is disabled with ContextKeyExpr.false(), so diagnosis should focus first on current changeset operation registration and any provider-contributed actions. Existing changesViewService tests cover selection isolation but not duplicate registration and dispatch across two sessions sharing a worktree. Preserve behavior for unrelated sessions and for multiple chats within one session; the boundary is action identity and invocation ownership, not worktree deduplication.
