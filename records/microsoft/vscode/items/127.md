# Issue #127 — Provide option to opt out of line ending normalisation for files

[https://github.com/microsoft/vscode/issues/127](https://github.com/microsoft/vscode/issues/127)

## Summary

Keep open: current text-model construction still normalizes mixed line endings, and files.eol does not provide a preservation mode. This accepted Backlog request has substantial demand and concrete use cases; no verified older canonical owns the same work.

## Change summary

Provide an opt-out from automatic line-ending normalization so editing and saving a mixed-EOL file preserves untouched line endings.

## Best solution

Offer a supported preservation mode across text-model loading, editing, and saving, while retaining explicit whole-file normalization. Establish the editing and API semantics with the editor-textbuffer owner before implementation; disabling normalization during loading alone is insufficient.

## Plan brief

- **Likely files:** `src/vs/editor/common/model/textModel.ts`, `src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeTextBufferBuilder.ts`, `src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeTextBuffer.ts`, `src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeBase.ts`, `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `src/vs/workbench/services/textfile/common/textFileEditorModel.ts`, `src/vs/editor/test/common/model/pieceTreeTextBuffer/pieceTreeTextBuffer.test.ts`
- **Validation:** After the preservation contract is agreed, add targeted text-buffer/model tests for mixed CRLF/LF/CR loading, editing, snapshot serialization, and undo/redo. Manually open a mixed-EOL fixture with save participants disabled, edit one non-newline character, save, and compare bytes: untouched terminators must remain identical. Verify explicit normalization and the existing default behavior separately.
- **Behavior:**

  > Users must be able to edit and save intentionally mixed-EOL text without normalizing untouched line endings. Acceptance includes a fixture containing CRLF, LF, and CR where changing one ordinary character changes only that character in the saved bytes. Users must retain an explicit way to normalize the whole document. The product contract must also define which terminators are used for newly inserted text and how preservation interacts with extension edits.
- **Trace:**

  > The normal text-model factory paths in src/vs/editor/common/model/textModel.ts all finish the piece-tree builder with its default normalization enabled. PieceTreeTextBufferFactory.create in pieceTreeTextBufferBuilder.ts chooses a predominant ending and rewrites differing terminators before model use. Although finish(false) exists internally, PieceTreeTextBuffer.applyEdits separately normalizes inserted text to the buffer EOL, so loading is not the entire boundary. files.eol currently configures a single default ending and offers no preservation option. The maintainer explanation at https://github.com/microsoft/vscode/issues/127#issuecomment-159306903 and the subsequent use cases establish the intended gap, but the full implications for model positions, snapshots, undo/redo, and extension-facing operations have not been traced. Preserve existing default behavior and explicit conversion unless the owner deliberately chooses otherwise; standalone CR support at https://github.com/microsoft/vscode/issues/35797 is related but does not subsume this request.
- **Open decisions:**
  - Should preservation be an explicit per-document mode, a persisted language/resource-scoped setting, or a mixed-EOL opening choice?
  - In preservation mode, should Enter use the document's predominant ending, the configured default, or the surrounding line's ending?
  - Should pasted and extension-supplied mixed-EOL text retain its supplied terminators, or should preservation apply only to existing, untouched content?

## Evidence

- **Existing capability does not cover the request:** src/vs/workbench/contrib/files/browser/files.contribution.ts registers files.eol with only LF, CRLF, and auto; auto selects the operating-system default, not mixed-EOL preservation. The EditorConfig workaround in the discussion selects a uniform ending and is explicitly rebutted by commenters as insufficient for mixed files.
- **Normalization remains on the loading path:** src/vs/editor/common/model/textModel.ts calls builder.finish() in createTextBufferFactory, createTextBufferFactoryFromStream, and createTextBufferFactoryFromSnapshot. In src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeTextBufferBuilder.ts, finish defaults normalizeEOL to true; PieceTreeTextBufferFactory.create chooses a predominant EOL and replaces every CRLF, CR, or LF with that ending when normalization is enabled.
- **Editing also assumes one EOL:** src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeTextBuffer.ts, in applyEdits around lines 272–286, compares inserted text with the buffer EOL and replaces differing line terminators. The internal builder.finish(false) capability therefore does not establish a complete, user-accessible preservation mode.
- **Maintainer explanation:** https://github.com/microsoft/vscode/issues/127#issuecomment-159306903 explains that the model normalizes on reading and keeps one predominant EOL for the file, then asks for mixed-EOL use cases. The subsequent discussion supplies HTTP golden files, XML CDATA, mixed-EOL patches, and a github.dev/Codespaces editing confirmation.
- **Demand and continuing relevance:** https://github.com/microsoft/vscode/issues/127 has 143 community upvotes and is accepted into Backlog. The supplied March 2026 report describes editing and saving a patch file, after which a binary-sensitive patch operation failed because the line endings changed; the July 2026 question does not establish a fix.
