# Issue #109954 — SCM - support for filesystem path using ssh://

[https://github.com/microsoft/vscode/issues/109954](https://github.com/microsoft/vscode/issues/109954)

## Summary

Keep this accepted, well-supported request open: built-in Git still operates on native filesystem paths rather than SSHFS-backed URIs. Remote-SSH is an alternative for some users, but does not satisfy the serverless filesystem-provider workflow described here.

## Change summary

Support Git source control for repositories opened through ssh:// filesystem providers without requiring a VS Code remote server.

## Best solution

Design a supported Git/SCM integration for SSH-backed filesystem providers that preserves remote resource identity and operates on the actual remote repository. Establish the execution and provider contract first; changing repository detection alone cannot make native Git access an extension-provided filesystem.

## Plan brief

- **Likely files:** `extensions/git/src/model.ts`, `extensions/git/src/git.ts`, `extensions/git/src/commands.ts`, `extensions/git/src/repository.ts`, `extensions/git/package.json`
- **Validation:** The plan should define an executable integration check using an SSHFS-backed workspace with no VS Code remote server: detect an existing remote Git repository, display changed files and diffs, stage and commit a remote edit, and initialize a repository remotely. Confirm operations affect only the intended remote repository, including when a local directory has the same path, and preserve existing native-filesystem Git behavior.
- **Behavior:**

  > Users opening a Git repository through an ssh:// filesystem provider should be able to use Source Control against that remote repository without requiring a VS Code remote server. Repository discovery, status, diffs, staging, and commits must retain the remote resource identity; initialization must create the repository remotely rather than at a matching local path. Existing native-filesystem and Remote-SSH Git workflows must remain unchanged. Acceptance requires an integration scenario that demonstrates these operations on the remote host and verifies that a same-path local directory is untouched.
- **Trace:**

  > In extensions/git/src/model.ts, onDidChangeWorkspaceFolders passes folder.uri.fsPath to openRepository, scanWorkspaceFolders/traverseWorkspaceFolder use native filesystem traversal, and onDidChangeVisibleTextEditors rejects non-file resources. Commands.init in extensions/git/src/commands.ts likewise reduces the selected resource to fsPath. Git.spawn/getCwd in extensions/git/src/git.ts ultimately invoke a native Git executable through cp.spawn; the virtualWorkspaces declaration in extensions/git/package.json does not supply a remote execution mechanism. This establishes a capability gap, not a bounded repository-detection fix: provider-backed file access and Git process execution must be considered together. The trace has not established a usable provider execution contract or enumerated all native-path assumptions across Repository and its consumers. Preserve existing local Git and Remote-SSH behavior; do not generalize this request into terminal, debugger, or arbitrary extension support. https://github.com/SchoofsKelvin/vscode-sshfs/issues/31 and https://github.com/SchoofsKelvin/vscode-sshfs/issues/366 corroborate the boundary and point to https://github.com/microsoft/vscode/issues/109954.
- **Open decisions:**
  - Should support be specific to SSH-backed providers or expose a reusable Git/SCM contract for arbitrary filesystem providers?
  - Should the supported workflow require Git installed on the remote host, or also cover hosts where only filesystem access is available?
