# Issue #345470 — URI with `windowId=1` is routed to window 10: the URL handler router matches the window id as a prefix

[https://github.com/microsoft/vscode/issues/345470](https://github.com/microsoft/vscode/issues/345470)

## Summary

The reported prefix collision remains in current main: a callback targeting window 1 selects window 10 when that connection appears first. Keep this open for correction and human assessment of the authentication-callback routing implications.

## Change summary

Route app-scheme callbacks to the exact window identified by windowId rather than another window whose ID shares its prefix.

## Best solution

Make URLHandlerRouter honor exact window identity while preserving existing fallback behavior when the requested connection is absent. Cover connection ordering and colliding numeric IDs with focused routing regression tests.

## Evidence

- **Defect confirmed in current source:** src/vs/platform/url/common/urlIpc.ts, URLHandlerRouter.routeCall, still constructs new RegExp(`window:${windowId}`) and returns the first matching hub.connections entry. For windowId=1 and connections ordered [window:10, window:1], the first entry matches and is returned incorrectly. This conclusively traces the reported trigger without executing code.
- **Window identity and callback provenance:** src/vs/platform/ipc/electron-browser/mainProcessService.ts constructs the IPC client context as exactly `window:${windowId}`. src/vs/workbench/services/url/electron-browser/urlService.ts, RelayURLService.create, appends the originating windowId to the URI query.
- **Ordering and active routing path:** src/vs/base/parts/ipc/common/ipc.ts stores connections in an insertion-ordered Set, removes disconnected connections, and exposes that order through connections. src/vs/code/electron-main/app.ts wires URLHandlerRouter into the urlHandler channel, with the active-window router as fallback.
