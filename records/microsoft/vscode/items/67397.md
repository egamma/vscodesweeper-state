# Issue #67397 — Support filter on type should in search tree

[https://github.com/microsoft/vscode/issues/67397](https://github.com/microsoft/vscode/issues/67397)

## Summary

Keep this accepted, team-authored request open: the Search results tree still lacks filename filtering that preserves matching files' result previews. The related open find-widget request is newer and explicitly distinguishes its broader scope, so it is not a valid duplicate target for this re-reviewed item.

## Change summary

Support filtering Search results by file labels while retaining the text matches beneath matching files.

## Best solution

Provide file-oriented filtering in the Search results tree without treating preview text as another search corpus or hiding the matches of retained files. Coordinate its interaction model with https://github.com/microsoft/vscode/issues/197634 while preserving this issue's specific acceptance criteria.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/search/browser/searchView.ts`, `src/vs/workbench/contrib/search/browser/searchResultsView.ts`, `src/vs/base/browser/ui/tree/abstractTree.ts`, `src/vs/workbench/contrib/search/test/browser/searchViewlet.test.ts`
- **Validation:** Exercise a Search results tree containing several files with multiple preview matches each: filtering by a file label must retain all of that file's previews, omit unrelated files, and restore the original results when cleared. Confirm the operation does not rerun the text search and that preview-only text does not select a file.
- **Behavior:**

  > Users can narrow the existing Search results tree by file labels. A retained file keeps its search-match previews even when those previews do not contain the filter text. Preview content is not independently searched by this filter, and clearing it restores the original results without rerunning the workspace query. Acceptance should cover multiple files, multiple previews per file, and both flat and hierarchical results layouts.
- **Trace:**

  > SearchView.createSearchResultsView in src/vs/workbench/contrib/search/browser/searchView.ts constructs a WorkbenchCompressibleAsyncDataTree without a keyboardNavigationLabelProvider. AbstractTree in src/vs/base/browser/ui/tree/abstractTree.ts creates its find machinery only when that provider exists; FindFilter.filter already supports multiple labels and an undefined-label visibility path. Those facilities establish useful prerequisites, not complete Search integration or proven parent/child behavior. Existing include/exclude controls trigger a new query and are not equivalent. Preserve workspace-search semantics and do not broaden this request into secondary matching of preview text or Search Editor filtering. https://github.com/microsoft/vscode/issues/197634 tracks the broader find-widget experience and should inform the interaction decision; https://github.com/microsoft/vscode/issues/67397#issuecomment-882780748 establishes the file-only scope. No code was executed in this read-only review.
- **Open decisions:**
  - Should file filtering use the standard tree find widget tracked by https://github.com/microsoft/vscode/issues/197634, or also support direct type-to-filter interaction as originally requested?
