# Issue #52116 — [Feature Request] Extension Permissions, Security Sandboxing & Update Management Proposal

[https://github.com/microsoft/vscode/issues/52116](https://github.com/microsoft/vscode/issues/52116)

## Summary

Keep open: this security-sensitive, Backlog-accepted feature request has 333 community upvotes, and current VS Code only implements portions of the proposal. Extension allowlisting and granular update controls do not provide capability declarations, permission prompts, or runtime sandbox enforcement.

## Change summary

Introduce extension capability declarations, user-visible permissions, runtime isolation or enforcement, and permission-aware update management.

## Best solution

Design a compatible extension security model spanning manifest capability declarations, install/update disclosure, user grants, and enforcement in the extension host. Existing allowlisting, Workspace Trust, and per-extension update controls should remain complementary safeguards rather than substitutes for runtime permissions.

## Evidence

- **protected security work:** The proposal concerns malicious extensions gaining filesystem, network, process, credential, and cross-extension access. Under the security-sensitive hard keep-open rule, this requires human security and architecture ownership rather than an automated close.
- **accepted demand:** The issue is assigned to the Backlog milestone, carries feature-request, extensions, and extension-host labels, and has 333 community upvotes, well above the 20-upvote backlog threshold.
- **partial allowlisting:** src/vs/platform/extensionManagement/common/extensionManagement.ts defines `extensions.allowed`, and src/vs/platform/extensionManagement/common/allowedExtensionsService.ts enforces extension or publisher allowlisting. This governs whether an extension may be installed or enabled, not which resources an enabled extension may access.
- **partial update management:** src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts implements per-extension and per-publisher auto-update state plus `extensions.autoUpdateDelay`; https://github.com/microsoft/vscode/issues/317770 confirms the delay control was completed. These cover part of the original update-management request but do not prompt for changed capabilities.
- **remaining permissions gap:** Current source contains no general extension manifest permission declaration or extension-host capability enforcement corresponding to filesystem, network, process, or cross-extension access. The newer open proposal https://github.com/microsoft/vscode/issues/314552 describes a narrower version of the same unresolved capability gap.
- **canonical search:** The older candidate https://github.com/microsoft/vscode/issues/40239 concerns workspace configuration for enabling or disabling extensions, while https://github.com/microsoft/vscode/issues/122951 concerns AppLocker process execution; neither reports the same observable need.
