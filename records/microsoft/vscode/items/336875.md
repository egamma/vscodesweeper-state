# Issue #336875 — Cursor Get Moved Immediately Somewhere After Typing While Opening The Git Diffs Inline Viewer

[https://github.com/microsoft/vscode/issues/336875](https://github.com/microsoft/vscode/issues/336875)

## Summary

Traced the exact cause in the inline (quick diff) peek widget: when the editor's model changes while the peek view doesn't have text focus, QuickDiffEditorController.onDidModelChange falls back to next(), which calls showChange(index, true) — forcibly repositioning the cursor and stealing focus back to the peek view's line, even though the user was typing in the main editor.

## Change summary

Typing in the editor while the inline git diff peek view is open causes the cursor to jump away unexpectedly a moment later.

## Best solution

In QuickDiffEditorController.onDidModelChange (src/vs/workbench/contrib/scm/browser/quickDiffWidget.ts), avoid the focus/position-stealing path of next() -> showChange(index, true) when the change originates from user edits outside the widget; the existing refresh() -> showChange(index, false) call just below already shows the pattern for updating the widget without moving the outer editor's cursor or focus.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/scm/browser/quickDiffWidget.ts`
- **Validation:** A test (new, since none exists for this file) that opens the quick diff peek widget without giving it text focus, edits the outer editor's model near the currently shown change, and asserts the outer editor's cursor position and focus are unchanged after the resulting onDidModelChange handling.
- **Behavior:**

  > While the inline git diff peek view is open and the user is typing in the main editor (not the peek view), edits should not move the main editor's cursor or steal focus back to the peek view's tracked line. The peek view may still update which change it displays, but only the refresh()-style non-intrusive update (no setPosition/focus) should run when the peek view itself isn't focused. Acceptance: typing near a shown-but-changed diff hunk keeps the cursor exactly where the user left it.
- **Trace:**

  > QuickDiffEditorController.onDidModelChange (src/vs/workbench/contrib/scm/browser/quickDiffWidget.ts:663-674) reacts to QuickDiffModel splices; when a splice affects the currently shown change index, it calls this.next() unconditionally, even though hasFocus() (line 666) already tells it the peek view lacks focus. next() (lines 563-581) resolves the closest change to the editor's current cursor line and calls widget.showChange(index) with the default usePosition=true, which (lines 255-262) calls editor.setPosition(...) and editor.focus() — moving the cursor and stealing focus from wherever the user was typing. The class's own refresh() method (lines 553-555) demonstrates the non-intrusive alternative: showChange(index, false), which updates the widget without touching editor position/focus. The boundary: do not change navigation behavior for explicit user-triggered next/previous actions (keyboard/command invocations) — only the implicit re-sync triggered by unrelated model edits while the widget lacks focus. Where uncertainty starts: whether the fix should route through refresh()-style behavior unconditionally when !hasFocus(), or whether next()'s cursor-repositioning is still wanted in some sub-case (e.g. the shown change was deleted entirely).
- **Open decisions:**
  - Should onDidModelChange ever call next() with usePosition=true when the peek view lacks focus, or should it always use the non-intrusive refresh()-style update in that case?
  - What should happen if the currently shown change is deleted outright while the widget lacks focus (close the widget vs. silently pick a nearby change without moving the cursor)?

## Evidence

- **focus-stealing path:** src/vs/workbench/contrib/scm/browser/quickDiffWidget.ts:663-674 — onDidModelChange checks `this.widget.hasFocus()` (which is `this.diffEditor.hasTextFocus()`, false while typing in the main editor) and, for any splice at/before the current widget index, calls `this.next()` instead of `this.refresh()`.
- **next() forces cursor + focus:** quickDiffWidget.ts:563-581 — next() computes the closest change to the current cursor line and calls `this.widget.showChange(index)` with the default `usePosition = true`.
- **showChange moves cursor and focus:** quickDiffWidget.ts:255-262 — when `usePosition` is true, showChange calls `this.editor.setPosition(position)` and `this.editor.focus()`, which matches the reported 'cursor gets moved immediately' symptom.
- **existing non-intrusive pattern:** quickDiffWidget.ts:553-555 — refresh() already calls `showChange(this.widget.index, false)`, i.e. update without moving the cursor/focus, showing the intended non-disruptive behavior exists elsewhere in the same class.
