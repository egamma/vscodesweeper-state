# Issue #332556 — Extension activation telemetry's `codeLoadingTime` is misleading

[https://github.com/microsoft/vscode/issues/332556](https://github.com/microsoft/vscode/issues/332556)

## Summary

The misleading measurement remains on current main: ESM loading is timed across an asynchronous `import()`, so unrelated event-loop work can inflate `codeLoadingTime`. The linked PR was closed without merging after maintainers rejected its loader changes, leaving the underlying issue unresolved.

## Change summary

Prevent concurrent extension activity from being attributed to an ESM extension's code-loading telemetry.

## Best solution

Define whether `codeLoadingTime` represents wall-clock load latency or attributable extension cost, then make both telemetry and the slow-extension UI use a measurement consistent with that definition without changing ESM evaluation ordering.

- **Behavior:**

  > An ESM extension's reported code-loading cost must not misleadingly attribute unrelated work from concurrently activating extensions to that extension. Telemetry and user-visible activation-time surfaces must use clearly defined, consistent semantics. CJS activation measurements and normal ESM loading behavior, including top-level await, module caching, cycles, and activation ordering, must remain correct. Acceptance requires a concurrent-load test demonstrating that a trivial ESM extension is not blamed for a neighboring expensive extension.
- **Trace:**

  > On current main, `_doLoadModule` in src/vs/workbench/api/node/extHostExtensionService.ts starts `ExtensionActivationTimesBuilder` before `await import()` and stops it after settlement; the builder in src/vs/workbench/api/common/extHostExtensionActivator.ts measures a plain `Date.now()` delta. That interval can include unrelated event-loop work, while downstream extension UI in abstractRuntimeExtensionsEditor.ts and extensionsWidgets.ts treats it as attributable activation cost. https://github.com/microsoft/vscode/pull/332571 attempted serialized and synchronous loading approaches, but maintainers closed it after concluding those approaches changed observable module-loader behavior or did not reliably isolate attribution. The boundary is extension activation measurement and its consumers: do not alter Node's ESM scheduling, cache, cycle, top-level-await, or public extension-export semantics merely to improve the metric.
- **Open decisions:**
  - Should `codeLoadingTime` continue to represent wall-clock latency until an extension is ready, or should it represent execution cost attributable to that extension?
  - If accurate attributable cost cannot be collected cheaply, should the existing wall-clock value remain telemetry-only and be removed from per-extension slow warnings, or should those surfaces use a different metric?

## Evidence

- **current source:** In src/vs/workbench/api/node/extHostExtensionService.ts, `_doLoadModule` calls `activationTimesBuilder.codeLoadingStart()` before `await import(module.toString(true))` and stops the timer only after that promise settles, so the ESM measurement remains a wall-clock interval spanning event-loop interleaving.
- **metric implementation:** src/vs/workbench/api/common/extHostExtensionActivator.ts implements `ExtensionActivationTimesBuilder` with `Date.now()` start/stop deltas and classifies `codeLoadingTime` as the time taken to load the extension's code; it has no attribution or contention adjustment.
- **rejected fix attempt:** https://github.com/microsoft/vscode/pull/332571 contains `Fixes #332556` but was closed without merging. Maintainer review agreed the metric is misleading while rejecting both the queue approximation and synchronous `require(esm)` because they alter loader behavior or provide unreliable attribution.
- **downstream impact:** src/vs/workbench/contrib/extensions/browser/abstractRuntimeExtensionsEditor.ts and src/vs/workbench/contrib/extensions/browser/extensionsWidgets.ts add `codeLoadingTime` to `activateCallTime` for extension activation displays, so inflated ESM measurements affect user-visible slow-extension attribution as well as telemetry.
- **canonical search:** A repository issue search for `codeLoadingTime`, ESM, and extension activation found no separate open canonical issue owning this defect.
