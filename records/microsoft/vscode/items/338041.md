# Issue #338041 — Workspace prompt files disappear from customization UI after window reload

[https://github.com/microsoft/vscode/issues/338041](https://github.com/microsoft/vscode/issues/338041)

## Summary

Detailed, self-consistent repro (files aren't actually lost — creating a prompt with an existing name reports a conflict, and the UI then refreshes to show them) indicating the AI customization UI misses an initial refresh/watcher event for workspace prompt files after a window reload. No fix found on main and root cause not conclusively traced from source, so this stays open pending deeper diagnosis in the prompts discovery/caching path.

## Change summary

After reloading the window, workspace prompt/migration items vanish from the AI customization UI until a 'New Prompt' attempt forces a refresh.

## Best solution

Diagnose why PromptsServiceCustomizationItemProvider / the underlying promptsService discovery cache (cachedFileLocations, cachedSkills, etc. in promptsServiceImpl.ts) isn't populated or its onDidChange isn't firing for the aiCustomizationItemsModel on first render after a reload, then ensure the customization editor forces (or the service emits) a refresh once workspace folders/files are actually known.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationItemsModel.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/promptsServiceCustomizationItemProvider.ts`
- **Validation:** After confirming the exact race, a manual check: reload the window with existing workspace prompt files present, open the customization UI immediately, and verify the files/migration banner render without needing a 'New Prompt' attempt.
- **Behavior:**

  > Immediately after a window reload, opening the prompt customization UI should show existing workspace prompt files and the migration banner right away, matching what a subsequent 'New Prompt' name-conflict check proves is already known to the underlying service. Today the UI renders empty until the user triggers an unrelated action (attempting to create a prompt with an existing name), which forces a refresh.
- **Trace:**

  > The customization UI (aiCustomizationItemsModel.ts) fetches each section lazily on first observation and otherwise refetches only on harness/source changes, workspace-folder changes, or the promptsService's own onDidChange emitters (backed by CachedPromise instances in promptsServiceImpl.ts keyed off cachedFileLocations). A reload doesn't fire onDidChangeWorkspaceFolders, so if the first discovery computation ran/cached before the workspace's prompt files were fully knowable, nothing currently forces a second pass — matching the reporter's observation that a later action (which does invalidate/refresh the cache) 'unsticks' it. Boundary: don't change the on-demand fetch model or the CachedPromise mechanics; the fix should ensure the *first* fetch reflects fully-ready state or is corrected once it is, without introducing extra always-on polling.
- **Open decisions:**
  - Should the fix live in promptsService's discovery caching (fire onDidChange once workspace readiness/file-watcher state settles) or in the aiCustomization UI (force one extra refresh shortly after activation on window restore)?
  - Is the underlying cause a missing initial file-watcher event, or the discovery cache being computed and cached too early relative to workspace/file-system readiness?

## Evidence

- **on-demand fetch model:** aiCustomizationItemsModel.ts markObserved() only triggers a fetch the first time a section is observed, and PromptsServiceCustomizationItemProvider.onDidChange only fires on promptsService discovery-cache invalidation events (promptsServiceImpl.ts CachedPromise/cachedFileLocations) — a plausible spot for a reload timing race where nothing re-invalidates the cache after the first (empty) computation.
- **workspace-folder listener:** aiCustomizationItemsModel.ts only refetches on workspaceContextService.onDidChangeWorkspaceFolders or workspaceService.activeProjectRoot changes — a reload doesn't change workspace folders, so if the initial promptsService discovery ran before file/workspace state was fully ready, nothing would trigger a corrective refetch.
- **no fix on main:** git log on promptsServiceImpl.ts and aiCustomizationItemsModel.ts shows no recent change addressing a reload-refresh gap.
