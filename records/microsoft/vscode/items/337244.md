# Issue #337244 — Perf: prompt timeline gutter/ruler re-renders every row and recomputes diff stats twice when opening a long session

[https://github.com/microsoft/vscode/issues/337244](https://github.com/microsoft/vscode/issues/337244)

## Summary

Fresh, well-diagnosed perf report from a maintainer, already correctly labeled (important/perf/chat/agents-window) and with an owner cc'd — I traced the described double-render/no-equality-function pattern in current source and it matches exactly, so this should stay open for the owning maintainer to implement.

## Change summary

Opening a long chat session causes the prompt timeline gutter/ruler to re-render every row and recompute every request's diff stats twice, because the derived tick observables lack a structural equality function and setTicks unconditionally re-renders every row even when a tick is unchanged.

## Best solution

Give `_ticks`/`_promptTicks` in promptTimelineModel.ts a structural equalsFn so a same-valued recompute is a no-op, and change `setTicks` in both promptTimelineGutterRail.ts and promptTimelineRulerRail.ts to skip re-rendering a row/mark whose tick object is unchanged from the previous call, while keeping the existing streaming-stat-update and accessibility (roving tabindex/aria-current) behavior intact.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/promptTimeline/promptTimelineModel.ts`, `src/vs/workbench/contrib/chat/browser/promptTimeline/promptTimelineGutterRail.ts`, `src/vs/workbench/contrib/chat/browser/promptTimeline/promptTimelineRulerRail.ts`
- **Validation:** Extend promptTimelineGutterRail.test.ts (and an equivalent ruler-rail/model test) to call setTicks twice with structurally-identical-but-new tick array instances and assert no DOM row is touched the second time (e.g. via a spy/mutation check on label/stat elements), while confirming the existing streaming-stat-update and roving-tabindex/aria-current tests still pass.
- **Behavior:**

  > Opening or updating a long chat session's prompt timeline should not re-render rows/marks or recompute a request's diff stat when nothing about that request's tick actually changed between two observable recomputes. A tick that is genuinely still streaming must keep updating live. Acceptance: a test asserting an unchanged tick produces no DOM mutation on a second setTicks call, plus the existing gutter-rail accessibility tests (roving tabindex, aria-current) continue to pass.
- **Trace:**

  > `_ticks`/`_promptTicks` (promptTimelineModel.ts:166-194) are plain `derived(...)` calls with no equality function, so every notification from the underlying view model during history restore produces a brand-new tick array even when values are identical. Downstream, `setTicks` in promptTimelineGutterRail.ts:397-425 and promptTimelineRulerRail.ts:173-199 detect 'same structure' (same requestIds in same order) but then unconditionally re-render every row/mark via `_renderRow`/`_renderMark`, re-touching DOM and recomputing stats for rows that didn't change. Do not alter the active-tick recompute in the constructor's autorun (lines 247-252), which reads `_baseTicks` not `_ticks`/`_promptTicks` and is unaffected. Where the uncertainty starts: the exact equality/diffing granularity (whole-array equalsFn vs. per-row reference caching) and how to keep a still-streaming tick's stat updating live is a design choice best settled with the file owner (cc'd in the issue) before implementation.
- **Open decisions:**
  - Should the fix live at the observable layer (equalsFn on `_ticks`/`_promptTicks` so an unchanged recompute never fires) or at the renderer layer (per-row diffing in `setTicks`), or both?
  - How should a tick that is still streaming (whose stat is expected to keep changing) be distinguished from one that is truly settled, so live updates aren't silently suppressed?

## Evidence
