# Issue #231304 — Folders in explorer disappear when clicked

[https://github.com/microsoft/vscode/issues/231304](https://github.com/microsoft/vscode/issues/231304)

## Summary

The maintainer-confirmed bug remains source-reproducible on current main: a nested `.gitignore` can evaluate its containing directory against an unscoped basename pattern, causing that directory to disappear after lazy expansion.

## Change summary

Nested `.gitignore` basename patterns are applied to their containing directory instead of only paths beneath that directory.

## Best solution

Make nested ignore-file matching honor Git's directory-relative scope, with regression coverage showing that `bfdd/.gitignore` containing `bfdd` ignores a descendant named `bfdd` but not the containing `bfdd` directory itself.

- **Behavior:**

  > A `.gitignore` applies relative to the directory containing it. If `/workspace/bfdd/.gitignore` contains `bfdd`, opening `/workspace/bfdd` must not hide that containing directory; the pattern may hide `/workspace/bfdd/bfdd`. The result must be identical before and after Explorer lazily discovers the nested ignore file, while existing root-level, nested, negation, directory-only, and case-sensitivity behavior remains unchanged.
- **Trace:**

  > ExplorerFilter.processIgnoreFile in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts constructs IgnoreFile with `dirUri.path`, which has no trailing slash, and stores it under the containing directory in `ignoreTreesPerRoot`. Filtering that directory finds the newly stored matcher through `findSubstr(resource)`. In src/vs/workbench/services/search/common/ignoreFile.ts, the constructor normalizes only the local `location` parameter, while `parseIgnoreFile` receives the unchanged `this.location`; a slashless basename pattern is then converted to `**/<name>` and can match the containing directory itself. Existing nested tests pass locations ending in `/`, so they miss the production input shape. Keep lazy `.gitignore` discovery and existing parent/negation semantics unchanged; the related lazy-hiding behavior tracked by https://github.com/microsoft/vscode/issues/210341 is outside this defect's scope.

## Evidence

- **confirmed defect:** A VS Code maintainer confirmed at https://github.com/microsoft/vscode/issues/231304 that this is a VS Code bug, and a second reporter reproduced it with all extensions disabled.
- **current source path:** src/vs/workbench/contrib/files/browser/views/explorerViewer.ts passes `dirUri.path` to `new IgnoreFile(...)` and, after lazy discovery of a nested `.gitignore`, uses the resulting matcher for the directory itself through `findSubstr(resource)` and `isPathIncludedInTraversal`.
- **source reproduction:** In src/vs/workbench/services/search/common/ignoreFile.ts, the constructor appends `/` only to its local `location` parameter but calls `parseIgnoreFile` with the unchanged parameter property `this.location`. A basename pattern such as `bfdd` therefore becomes `**/bfdd`, while the prefix guard still admits the containing `/.../bfdd` path, allowing that directory itself to match.
- **coverage gap:** src/vs/workbench/services/search/test/common/ignoreFile.test.ts covers nested ignore locations supplied with a trailing slash, but does not cover the production form passed by `ExplorerFilter.processIgnoreFile`, where `dirUri.path` has no trailing slash.
- **related issue is not canonical:** https://github.com/microsoft/vscode/issues/210341 is older and also observes a folder disappearing on click, but there the folder contains only intentionally ignored contents and the maintainer attributes the transition to lazy resolution. This report instead shows the containing directory being incorrectly matched by its own nested ignore rule, so the re-review duplicate bar is not met.
