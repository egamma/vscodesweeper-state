# Issue #218078 — Show removed entries in the settings editor

[https://github.com/microsoft/vscode/issues/218078](https://github.com/microsoft/vscode/issues/218078)

## Summary

This team-authored Backlog request remains necessary: current main still omits explicitly removed entries from the Settings editor, including false-valued `files.exclude` entries. No older issue with the same observable request was found, so it should remain open for settings-editor design.

## Change summary

Show object-setting entries whose inherited default values were explicitly removed, including removals contributed by extensions.

## Best solution

Represent removed object-setting entries in the Settings editor with a clear removed state and an understandable restoration action, while retaining their default-value source where available.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/preferences/browser/settingsTree.ts`, `src/vs/workbench/contrib/preferences/browser/settingsTreeModels.ts`, `src/vs/workbench/contrib/preferences/browser/settingsWidgets.ts`, `src/vs/workbench/contrib/preferences/test/browser/settingsEditor2.test.ts`
- **Validation:** Add a Settings editor browser test with a default `files.exclude` key overridden to `false`; verify the removed key remains visible with the chosen removed-state treatment and can be restored, while active and user-added entries retain their existing behavior.
- **Behavior:**

  > When an object setting removes an inherited default entry, the Settings editor must continue to show that key and clearly distinguish it from active entries. This includes entries removed by extension-provided configuration defaults. The user must be able to understand the effective state and restore the inherited entry without editing settings JSON. Active defaults, modified values, and user-added entries must retain their current behavior.
- **Trace:**

  > `SettingsTreeSettingElement.initSettingValueType` in src/vs/workbench/contrib/preferences/browser/settingsTreeModels.ts routes `files.exclude` through the include/exclude renderer. `getIncludeExcludeDisplayValue` in src/vs/workbench/contrib/preferences/browser/settingsTree.ts merges defaults with the scoped value, then filters out falsy entries, so explicit `false` removals are absent from the widget. The generic object renderer separately has setting-specific removed-default handling only for `workbench.editor.customLabels.patterns`. The original default-merging work is https://github.com/microsoft/vscode/pull/217179; preserve its source/provenance display and do not change configuration merge semantics or settings JSON serialization.
- **Open decisions:**
  - What visible treatment and restoration action should the Settings editor use for a removed entry so it is distinguishable from active, modified, and user-added entries?

## Evidence

- **current source gap:** In src/vs/workbench/contrib/preferences/browser/settingsTree.ts, `getIncludeExcludeDisplayValue` merges the default and scoped objects and then applies `.filter(key => !!data[key])`; an explicit `false` removal therefore disappears from the Settings editor.
- **affected routing:** src/vs/workbench/contrib/preferences/browser/settingsTreeModels.ts routes `files.exclude` and related settings through `SettingValueType.Exclude`, which uses the filtering path above.
- **limited existing support:** The generic object-setting path only recognizes removed-default behavior for `workbench.editor.customLabels.patterns` through `objectSettingSupportsRemoveDefaultValue`; it does not provide the requested general removed-entry presentation.
- **linked implementation boundary:** https://github.com/microsoft/vscode/pull/217179 merged extension-provided object defaults and their source metadata in commit aef28862c491e0d57b10f70e703932504afbcf63, but its include/exclude renderer retained the false-entry filter that motivates this follow-up.
- **canonical search:** Searches for removed entries, removed defaults, and `files.exclude` Settings editor behavior found no older open issue describing the same observable request; the matching result was this issue itself.
