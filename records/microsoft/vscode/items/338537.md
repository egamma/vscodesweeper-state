# Issue #338537 — Peer chat doesn't show customizations for separate workspace

[https://github.com/microsoft/vscode/issues/338537](https://github.com/microsoft/vscode/issues/338537)

## Summary

Team-authored bug (keep-open per the protected-items rule; no fix commit referencing this issue exists). The reporter's screenshots show a confirmed repro, and the source confirms the architectural root cause: session customizations are resolved and published per-session, not per-chat working directory, so a peer chat opened against a separate workspace still shows the main session's customizations.

## Change summary

Opening a peer chat scoped to a different workspace (e.g. a different repo) still shows the original session's customizations instead of the new workspace's own.

## Best solution

Resolve/publish the customizations snapshot per chat's effective working directory (not just per session) so a peer chat in a different workspace sees that workspace's own instructions/MCP servers/agents — likely needs a design decision on scope before implementation.

## Plan brief

- **Likely files:** `src/vs/sessions/services/agentHost/browser/agentHostCustomizationService.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/platform/agentHost/node/agentSideEffects.ts`
- **Validation:** A test asserting that a peer chat with its own `workingDirectories` override (e.g. a different workspace root) surfaces that workspace's own customizations/MCP servers in the customizations panel, distinct from the owning session's.
- **Trace:**

  > Session customizations are computed and published once per session (`_lastSessionStates.get(sessionId)?.customizations` in baseAgentHostSessionsProvider.ts, consumed via `AgentHostCustomizationService._resolveTarget` keyed only by `session.sessionId`). Peer chats can already have their own effective working directories (`ChatState.workingDirectories` override, merged in `mergeSessionWithDefaultChat`), but nothing re-derives customizations from that per-chat root — the customizations snapshot flows through the host-publish seam (`getChatCustomizations`/`AgentSideEffects._publishSessionCustomizations`, AGENTS.md §8b) scoped to the session, not the chat. The boundary: do not change the single-root default-chat path or the provider enablement/toggle persistence; the gap is specifically about which working directory's customizations are surfaced for a peer chat with an overridden root.
- **Open decisions:**
  - Should the customizations panel resolve per chat's effective working directory (peer chat's own root) instead of the session's primary root, or is single-root customization resolution an accepted limitation for now?
  - If per-chat resolution is added, must it apply uniformly across Claude/Copilot/Codex customization computation, or only to the UI listing (without changing which instructions/MCP servers are actually applied to that chat's turns)?
  - Does this require a protocol/seam change (host-published snapshot keyed by chat rather than session) or can it be achieved by filtering/recomputing client-side from the chat's working directories?

## Evidence

- **session-scoped resolution:** src/vs/sessions/services/agentHost/browser/agentHostCustomizationService.ts `_resolveTarget` calls `provider.getCustomizations(session.sessionId)` — keyed only by session id, with no chat/workingDirectory parameter, even though `IAgentHostCustomizationTarget` is resolved per `sessionResource`.
- **single customizations list per session:** src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts `getCustomizations(sessionId)` returns `this._lastSessionStates.get(sessionId)?.customizations` — one flat list per session, not per chat.
- **architecture confirms by design:** AGENTS.md §8b: 'getChatCustomizations(chat, context, hostCustomizations) receives the host's last published snapshot ... the owning session's last host-published customization snapshot' — explicitly session-scoped, while `ChatState.workingDirectories` (§2, `mergeSessionWithDefaultChat`) already lets a chat override its working directory. The mismatch between per-chat working directories and per-session customizations is the root cause.
- **related issue #338222:** This issue states it is testing/following up on https://github.com/microsoft/vscode/issues/338222, which introduced per-chat working-directory support that this customizations gap was not updated for.
