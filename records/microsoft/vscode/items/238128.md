# Issue #238128 — provide a way to collapse the extension info 

[https://github.com/microsoft/vscode/issues/238128](https://github.com/microsoft/vscode/issues/238128)

## Summary

The accessibility gap remains on current main: the extension editor has a fixed, non-collapsible information header that can crowd out the description at high zoom. Maintainers reproduced the problem and accepted the direction, so this Backlog request should remain open for interaction design.

## Change summary

Allow visually impaired users working at high zoom to collapse extension metadata, artwork, and action controls so the extension description remains usable.

## Best solution

Provide a keyboard-accessible collapsed state for the extension editor header that preserves essential identity and management actions while giving the description most of the viewport at high zoom. A maintainer should first settle whether collapse is explicit, responsive, or both, and whether the state persists.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/extensions/browser/extensionEditor.ts`, `src/vs/workbench/contrib/extensions/browser/media/extensionEditor.css`
- **Validation:** At a high window zoom level where the current header obstructs the extension description, verify with keyboard-only navigation that the header can be collapsed and restored, focus remains predictable, essential extension actions remain reachable, and the description scrolls through the available viewport.
- **Behavior:**

  > At high window zoom, a user can reduce the extension information header so the extension description receives a usable viewport without reducing text size. The operation must be discoverable and fully keyboard accessible, expose its expanded state to assistive technology, and retain access to essential extension-management actions. Expanding the header restores all metadata and controls without losing the user's place in the description.
- **Trace:**

  > ExtensionEditor.createEditor in src/vs/workbench/contrib/extensions/browser/extensionEditor.ts builds the icon, identity metadata, description, action bar, status, and recommendation into one `.header`, followed by the flexing `.body`. src/vs/workbench/contrib/extensions/browser/media/extensionEditor.css uses large fixed visual elements in that header and has no collapsed or height-responsive state; only the body details sidebar has a narrow-width adaptation. The reporter's video and maintainer reproduction in https://github.com/microsoft/vscode/issues/238128 establish the high-zoom accessibility problem. Preserve text sizing, extension action semantics, tab content, and body scroll position; the request is not to shrink typography. The uncertainty begins at the user-facing collapse policy and which header elements remain available while collapsed.
- **Open decisions:**
  - Should the header collapse only through an explicit user control, automatically when available height becomes constrained, or support both behaviors?
  - Which extension identity and management controls must remain visible in the collapsed state?
  - Should the collapsed state persist when switching extensions or reloading the window, or reset for each extension editor session?
