# Issue #202373 — Cursor position is incorrect in selection when cursorStyle is "Block"

[https://github.com/microsoft/vscode/issues/202373](https://github.com/microsoft/vscode/issues/202373)

## Summary

The reported rendering remains on current main, but it follows VS Code's documented caret-based selection model rather than violating the Selection API contract. This is a valid request for modal-editor-aware block-cursor behavior and should be routed to editor rendering, not closed as fixed or duplicate.

## Change summary

Make a block cursor appear over the final selected character during forward selections so modal-editing extensions can present character-oriented selection behavior.

## Best solution

Define an editor-level contract for character-oriented block-cursor selections that supports modal extensions without changing the existing half-open Selection API semantics for ordinary editor consumers.

## Evidence

- **current source path:** src/vs/editor/browser/viewParts/viewCursors/viewCursors.ts derives each rendered cursor position from Selection.getPosition(), while src/vs/editor/browser/viewParts/viewCursors/viewCursor.ts renders a block cursor over the grapheme beginning at that position. For a forward half-open selection, that is the character immediately after the selected text.
- **API contract:** src/vscode-dts/vscode.d.ts documents Selection.active as “The position of the cursor,” not the last included character; the current visual position therefore agrees with the API even though it does not provide modal-editor character semantics.
- **prior reports:** The same behavior was tracked as a feature request in https://github.com/microsoft/vscode/issues/97148 and https://github.com/microsoft/vscode/issues/2997. Both were closed through the historical feature-request lifecycle rather than by a fixing commit or a maintainer decision that the behavior is as designed.
- **canonical search:** https://github.com/microsoft/vscode/issues/114851 is an open request for a built-in Vim mode, but it is substantially broader and does not own this specific block-cursor rendering/API interoperability requirement.
