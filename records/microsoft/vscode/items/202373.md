# Issue #202373 — Cursor position is incorrect in selection when cursorStyle is "Block"

[https://github.com/microsoft/vscode/issues/202373](https://github.com/microsoft/vscode/issues/202373)

## Summary

Current main still renders a block cursor at the selection's active endpoint, which is after the final selected character for a forward selection. This is better classified as a modal-editing feature request and routed to the editor area because changing that presentation requires a product decision rather than correcting a broken Selection API contract.

## Change summary

Make a block cursor appear within a non-empty forward selection instead of over the character immediately following it.

## Best solution

Define an editor-level block-cursor selection presentation that supports modal extensions while preserving VS Code's existing half-open selection ranges and extension API coordinates. The editor owner should decide whether that behavior is automatic for block cursor styles or exposed as an opt-in mode.

- **Behavior:**

  > With a block-style cursor and a non-empty selection, forward and reverse selections should present the active cursor consistently for modal editing instead of making the forward cursor appear outside the selected text. Selection.anchor, Selection.active, copied text, and ordinary line-cursor behavior must retain their existing semantics. Acceptance must cover both block styles, both selection directions, empty selections, line boundaries, tabs, and multi-code-unit graphemes.
- **Trace:**

  > ViewCursors.onCursorStateChanged in src/vs/editor/browser/viewParts/viewCursors/viewCursors.ts takes Selection.getPosition() and forwards it directly to ViewCursor. The extension API contract in src/vscode-dts/vscode.d.ts describes active as the cursor position, so the boundary is visual/modal presentation: do not change Range or Selection coordinate semantics, copied content, or non-block cursor behavior. Exact predecessors https://github.com/microsoft/vscode/issues/97148 and https://github.com/microsoft/vscode/issues/2997 were closed by backlog voting rather than fixed, while https://github.com/microsoft/vscode/issues/114851 tracks the broader demand for modal editing.
- **Open decisions:**

  - Should a non-empty forward selection move the rendered block onto the preceding selected grapheme, hide the cursor, or use another visual treatment?
  - How should the presentation behave at line boundaries, across multi-line selections, and for tabs or multi-code-unit graphemes?
