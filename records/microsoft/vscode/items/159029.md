## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mergeEditor/browser/commands/commands.ts`, `src/vs/workbench/contrib/mergeEditor/browser/mergeEditorAccessibilityHelp.ts`, `src/vs/workbench/contrib/mergeEditor/browser/view/viewModel.ts`, `src/vs/workbench/contrib/mergeEditor/browser/view/editors/inputCodeEditorView.ts`, `src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts`
- **Validation:** Using a three-way merge containing multiple conflicts, enable a screen reader and accessibility signals. With keyboard input only, navigate conflicts, distinguish incoming/current/result context and handled state, invoke each supported conflict action, and complete the merge. Check Tab/Shift+Tab reachability with editor tab-focus mode enabled, and verify Alt+F1 documents the available actions; repeat with verbosity and signals disabled to ensure their controls are respected.
- **Behavior:**

  > A keyboard-only screen-reader user should be able to inspect and resolve a three-way merge without relying on visual conflict markers or mouse-only actions. Conflict navigation should communicate enough side and resolution-state context to make the next action clear. Existing navigation, input toggling, bulk acceptance, and completion commands already provide part of this workflow. Acceptance should cover individual conflict actions, completion-control reachability, discoverable help, and the agreed audible or spoken feedback.
- **Trace:**

  > commands.ts already registers navigation, individual input toggles, bulk acceptance, completion, and input switching. MergeEditorAccessibilityHelpProvider describes several of those commands. MergeEditorViewModel.goToConflict changes focus and cursor position without conflict-state feedback, while inputCodeEditorView.ts builds additional contextual actions outside the command-palette registrations inspected. The source establishes partial coverage, but actual screen-reader speech and focus order remain unverified. Preserve merge resolution, undo, existing commands, and notification behavior; notification.acceptPrimaryAction already handles the separate follow-up in https://github.com/microsoft/vscode/issues/175140. Coordinate the remaining scope with https://github.com/microsoft/vscode/issues/182682 and https://github.com/microsoft/vscode/issues/247401 without treating those newer reports as canonical duplicates.
- **Open decisions:**
  - Should accessible conflict inspection remain within the three editor panes with richer announcements, or provide a unified textual conflict presentation?
  - What audible and spoken context should identify conflict sides and handled versus unhandled state when navigating conflicts or moving through their lines?
