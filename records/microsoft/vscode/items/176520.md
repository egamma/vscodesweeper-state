# Issue #176520 — Support debug adapter server over WebSockets (similar to DebugAdapterServer)

[https://github.com/microsoft/vscode/issues/176520](https://github.com/microsoft/vscode/issues/176520)

## Summary

A real API gap remains on current main: extensions can manually bridge WebSockets through DebugAdapterInlineImplementation, but VS Code still has no built-in WebSocket debug-adapter descriptor or lifecycle handling. The debug maintainer explicitly considered built-in WebSocket support reasonable and kept this Backlog request open.

## Change summary

Allow a DebugAdapterDescriptorFactory to connect to a debug adapter over a WebSocket URL instead of requiring an extension-managed inline bridge.

## Best solution

Provide a supported WebSocket debug-adapter descriptor that handles DAP message transport and connection closure consistently with the existing socket and named-pipe descriptors. Settle the public API contract, including URL options and supported extension-host environments, before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTypes.ts`, `src/vs/workbench/api/common/extHostDebugService.ts`, `src/vs/workbench/api/node/extHostDebugService.ts`, `src/vs/workbench/contrib/debug/common/debug.ts`, `src/vs/workbench/contrib/debug/node/debugAdapter.ts`, `src/vs/workbench/contrib/debug/test/node/streamDebugAdapter.test.ts`
- **Validation:** Extend the stream debug-adapter test suite and run scripts/test.sh --grep "StreamDebugAdapter"; the new test should connect to a local WebSocket endpoint, complete a DAP initialize round trip, and verify connection-close behavior.
- **Behavior:**

  > A debug extension can return a descriptor for a ws:// or wss:// debug-adapter endpoint without implementing an inline protocol bridge. VS Code connects to that endpoint, exchanges DAP messages, and reports connection failures or unexpected closure through the same debug-session lifecycle used by its built-in transports. Existing executable, raw-socket, named-pipe, and inline descriptors remain unchanged.
- **Trace:**

  > The public descriptor union in src/vscode-dts/vscode.d.ts has no WebSocket form. Runtime descriptor classes live in src/vs/workbench/api/common/extHostTypes.ts; conversion to internal DTOs is handled by ExtHostDebugService in src/vs/workbench/api/common/extHostDebugService.ts, and node-specific adapter construction is selected in src/vs/workbench/api/node/extHostDebugService.ts. Internal descriptor types are in src/vs/workbench/contrib/debug/common/debug.ts, while socket transport and its lifecycle are implemented by NetworkDebugAdapter and SocketDebugAdapter in src/vs/workbench/contrib/debug/node/debugAdapter.ts. Existing socket coverage is in src/vs/workbench/contrib/debug/test/node/streamDebugAdapter.test.ts. The boundary is a new transport option: do not alter DAP semantics or the behavior of existing descriptors. https://github.com/microsoft/vscode/issues/178046 documents why the inline workaround's closure semantics are awkward and records maintainer preference for built-in WebSocket support.
- **Open decisions:**
  - Should the public descriptor accept only a WebSocket URL, or also expose subprotocols and connection headers needed for authenticated endpoints?
  - Must the descriptor work in both local Node and browser extension hosts, or is the initial contract limited to extension-host environments with an available WebSocket implementation?
  - When an established WebSocket closes without a DAP TerminatedEvent, should VS Code treat it exactly like an unexpected raw-socket closure?

## Evidence

- **current public API:** src/vscode-dts/vscode.d.ts still defines DebugAdapterDescriptor as DebugAdapterExecutable | DebugAdapterServer | DebugAdapterNamedPipeServer | DebugAdapterInlineImplementation; there is no WebSocket descriptor.
- **current transport path:** src/vs/workbench/api/node/extHostDebugService.ts creates SocketDebugAdapter only for DebugAdapterServer, while src/vs/workbench/contrib/debug/node/debugAdapter.ts implements that transport with net.createConnection and Content-Length-framed streams.
- **workaround is not equivalent:** DebugAdapterInlineImplementation can manually relay parsed DAP messages through a WebSocket, as discussed in the issue, but extensions must implement transport parsing, sending, disposal, and connection-failure behavior themselves.
- **maintainer direction:** In https://github.com/microsoft/vscode/issues/178046#issuecomment-1485688567, the debug maintainer said built-in WebSocket server support was preferable to adding more lifecycle API around inline implementations; https://github.com/microsoft/vscode/issues/178046 was later closed without implementing this request.
- **canonical search:** No separate open microsoft/vscode issue was found that owns WebSocket debug-adapter descriptor support; the related issue points back to this issue rather than replacing it.
