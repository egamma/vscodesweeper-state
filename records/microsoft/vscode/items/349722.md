# Issue #349722 — Extension auto-update keeps re-downloading VSIX files indefinitely when the disk is full (ENOSPC)

[https://github.com/microsoft/vscode/issues/349722](https://github.com/microsoft/vscode/issues/349722)

## Summary

Keep open: current source retries failed VSIX writes without distinguishing disk exhaustion, and subsequent auto-update cycles have no failure-based backoff. This is a core extension-management defect, not a problem owned by either downloaded extension.

## Change summary

Prevent repeated extension-update downloads during disk exhaustion and provide a single actionable notification.

## Best solution

Extension management should recognize disk-full failures, avoid immediate re-downloads, and constrain later automatic attempts while allowing recovery after space is freed. Agree on recovery and notification semantics before implementing the complete behavior.

- **Validation:** Extend downloader tests with a wrapped disk-full write failure and assert one download attempt while transient-error retries remain intact. Extend workbench-service tests with controlled time and repeated update checks to verify the agreed backoff, one notification per failure episode, and successful recovery. Manually repeat the reported pending-update scenario on an isolated space-limited filesystem, then free space and verify recovery.
- **Behavior:**

  > When an automatic extension update cannot write its VSIX because the destination filesystem is full, it must not immediately download the same package again. Subsequent automatic checks must avoid repeatedly consuming bandwidth while the failure persists, and the user must receive one actionable disk-full notification rather than repeated alerts. Updates must recover after space becomes available, while ordinary transient download failures retain their existing retry behavior. Acceptance checks must cover download counts, later update cycles, notification deduplication, and recovery.
- **Trace:**

  > ExtensionsDownloader.downloadVSIX invokes doDownload with two retries; doDownload retries all failures, and downloadFile creates a new temporary destination on every attempt. ExtensionsWorkbenchService.syncInstalledExtensionsWithGallery schedules autoUpdateExtensions for outdated extensions, and neither automatic scheduling nor candidate selection records a failure cooldown. DiskFileSystemProvider.toFileSystemProviderError maps ENOSPC to Unknown, and FileService.writeFile wraps that error, so the remaining trace must establish how disk-full identity survives gallery and extension-management error conversion and process boundaries. The existing downloader test suite has injectable gallery downloads and an in-memory filesystem suitable for deterministic failure tests. Preserve transient retries, manual update behavior, metered-connection gating, and existing publication-delay and consent checks. https://github.com/microsoft/vscode/issues/343873 owns abandoned-file reclamation, which is related but does not resolve this retry loop.
- **Open decisions:**
  - Should automatic updates resume through capped timed backoff or remain suspended until available space changes, and should that suspension survive a window restart?
