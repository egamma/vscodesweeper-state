# Issue #234476 — Settings Defaults gets very confused when updating extensions.

[https://github.com/microsoft/vscode/issues/234476](https://github.com/microsoft/vscode/issues/234476)

## Summary

The stale-schema path remains in current source: extension-point deltas compare extension identifiers only, so replacing an extension with a new version does not refresh its registered settings. Keep this report open; the closely matching restart report is newer and cannot supersede it under the re-review rules.

## Change summary

Refresh contributed settings and their defaults after an extension update and extension restart without requiring a window reload.

## Best solution

Ensure same-identifier extension replacements refresh configuration contributions, including added settings and changed defaults. Preserve unrelated extensions' contributions and validate replacement semantics across shared extension-point consumers before choosing the implementation boundary.

## Evidence

- **Concrete reproduction:** https://github.com/microsoft/vscode/issues/234476 describes upgrading Code Spell Checker from 3.0.1 to 4.0.21 with Settings open: 59 settings remain after restarting extensions and reopening Settings, while restarting VS Code reveals 77. The report supplies sufficient steps; additional basic reproduction information is unnecessary.
- **Current update path:** src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts:updateRunningExtensions collects the running extension identifier for removal and the updated local extension for addition, then calls startExtensionHosts({ toAdd, toRemove }). src/vs/workbench/services/extensions/common/abstractExtensionService.ts:startExtensionHosts passes these replacements through _deltaExtensions, which updates the registry and handles affected extension points.
- **Source-confirmed lost replacement:** src/vs/workbench/services/extensions/common/extensionsRegistry.ts:ExtensionPointUserDelta.compute, lines 76–106, constructs previous/current identifier sets and classifies additions/removals solely by identifier membership. An old and new manifest with the same extension identifier therefore produce neither an added nor a removed contribution, even when their configuration schemas differ.
- **Why settings stay stale:** src/vs/workbench/api/common/configurationExtensionPoint.ts:configurationExtPoint.setHandler, lines 262–383, removes cached configuration nodes only for delta.removed and registers new nodes only for delta.added. The empty replacement delta leaves extensionConfigurations and registered configuration unchanged. AbstractExtensionService._handleExtensionPoint supplies the new manifest to acceptUsers, but identifier-only delta computation discards the change.
- **Matching newer report:** https://github.com/microsoft/vscode/issues/283457 is open and reports that a newly contributed setting's default is absent after Restart Extensions but available after window reload, on 1.108.0-insider. It was created on 2025-12-14, after this report, so it is corroborating related work rather than an eligible older canonical for this re-reviewed item.
- **Related UI issue is distinct:** https://github.com/microsoft/vscode/issues/237496 concerns configuration values remaining visually stale while the Settings UI has focus and refreshing when focus changes. This report instead concerns manifest/schema replacement and persists after closing and reopening Settings; that issue does not own the same observable symptom.
- **Extension workaround is not a core fix:** https://github.com/streetsidesoftware/vscode-spell-checker/pull/5504 merged on 2026-09-11 and explicitly describes itself as a workaround for this issue, supplying extension-side fallback defaults for missing configuration. https://github.com/streetsidesoftware/vscode-spell-checker/issues/3804#issuecomment-2495520811 likewise identifies restarting VS Code as a workaround.
