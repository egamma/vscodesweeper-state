# Issue #193108 — Git - "Git: connect ENOENT" error 

[https://github.com/microsoft/vscode/issues/193108](https://github.com/microsoft/vscode/issues/193108)

## Summary

Keep open: multiple reporters confirm that Git commits cannot open their message editor when the IPC endpoint disappears or becomes stale, including a recent WSL report on 1.133.0. The issue is correctly routed to git; neither a complete fix nor an older canonical covering the same symptom was established.

## Change summary

Git commit and amend operations intermittently fail with connect ENOENT instead of opening the commit-message editor.

## Best solution

Make the built-in Git editor's IPC endpoint reliable across extension-host restarts and runtime-directory loss, with explicit handling when the endpoint cannot be established. Diagnose missing-directory and stale-handle failures separately before deciding whether they require distinct fixes.

Check that successful operations open the message editor and finish after it closes, and that unavailable IPC is handled explicitly rather than advertising an unusable endpoint. Establish automated regression coverage for each confirmed cause; no checks were executed during this read-only review.
- **Behavior:**

  > Git commit and amend operations that require message editing intermittently fail with connect ENOENT before opening the editor. Reports include extension-host restart, sleep/wake, stale endpoint names, and a missing WSL runtime directory. The acceptance goal is reliable message editing across supported lifecycle transitions, with explicit failure handling when IPC cannot be established. Commits with an explicit message and unrelated Git operations must retain their existing behavior.
- **Trace:**

  > main.ts creates an IPCServer and distributes its environment to Git and TerminalEnvironmentManager; GitEditor registers the git-editor handler. git-editor-main.ts calls IPCClient, which captures VSCODE_GIT_IPC_HANDLE and makes one HTTP request to that endpoint, exiting unsuccessfully on connection error. ipcServer.ts chooses XDG_RUNTIME_DIR without an existence check and resolves creation immediately after server.listen rather than after listening is confirmed. terminal.ts refreshes environmentVariableCollection at initialization and on Git configuration changes, but the effects on already-running shells across host restarts remain to be traced. The discussion at https://github.com/microsoft/vscode/issues/193108 supports both missing-directory and stale-endpoint cases; it does not prove that VS Code deletes runtime directories or intentionally renames sockets. Preserve message-editor completion semantics and shared askpass behavior, and do not broaden this work into the devcontainer identity-sync complaint. The uncertainty is the lifecycle mechanism behind each confirmed symptom and whether one bounded fix covers them.

- **Current Git editor failure path:** extensions/git/src/main.ts creates the IPC server and captures its environment for Git and terminal integration. extensions/git/src/gitEditor.ts registers the git-editor handler and selects git-editor.sh when an IPC server object exists. extensions/git/src/ipc/ipcClient.ts reads VSCODE_GIT_IPC_HANDLE and connects directly to that socketPath; extensions/git/src/git-editor-main.ts prints a connection error and exits with status 1, matching the reported failure before message editing.
- **Current runtime-directory and readiness handling:** extensions/git/src/ipc/ipcServer.ts:getIPCHandlePath uses a nonempty XDG_RUNTIME_DIR on Linux without checking that it exists. createIPCServer calls server.listen(ipcHandlePath) and immediately resolves an IPCServer rather than awaiting the listening event, so an asynchronous bind failure need not reach main.ts's initialization catch before the endpoint is advertised. No endpoint recreation is present in IPCClient. These are concrete diagnostic leads, not proof of one root cause for every platform.
