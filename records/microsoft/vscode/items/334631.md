# Issue #334631 — Agent host renders nothing for a skill that runs in a subagent

[https://github.com/microsoft/vscode/issues/334631](https://github.com/microsoft/vscode/issues/334631)

## Summary

Confirmed from source: a skill run as a subagent produces zero response parts and the turn's real output is silently dropped, plus two related root causes (backgrounded-subagent hidden presentation, permanently wedged session after a cancelled skill-subagent turn) bundled in the same thread. Stays open — the candidate canonical (#333174) is an umbrella/tracking issue, which per policy cannot be a duplicate target, and the re-review duplicate bar isn't met anyway.

## Change summary

When a skill runs as a Claude subagent, the parent turn shows a spinner and completes with an empty response — the real output only exists in the SDK transcript.

## Best solution

Fix the narrow, well-diagnosed defect first (surface the `result` message's text as a response part when a turn produced zero response parts and spent zero tokens, in ClaudeSdkPipeline._processMessages / claudeMapSessionEvents.ts), then have a maintainer decide the harder design question for the wedged-session recovery path (move the transcript aside, mint a new session id, or await prior-process exit) before tackling that half.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/claude/claudeSdkPipeline.ts`, `src/vs/platform/agentHost/node/claude/claudeMapSessionEvents.ts`, `src/vs/platform/agentHost/node/claude/claudeSubagentRegistry.ts`
- **Validation:** A ClaudeSdkPipeline test asserting a synthetic turn that ends in a `result` message with zero response parts and zero token usage produces exactly one response part carrying the result text, while an ordinary turn (nonzero tokens/response parts already streamed) is unchanged.
- **Behavior:**

  > A turn whose model work runs entirely inside a skill-spawned subagent (no `Task` tool_use, so no `toolUseId`) must not render as an empty bubble: when the turn ends with zero response parts and zero token usage, the SDK `result` message's text should appear as the turn's response. An ordinary turn, whose result text merely repeats content already streamed, must not have that text duplicated. Acceptance: the named pipeline test passes, and existing claudeSdkPipeline/claudeMapSessionEvents tests are unaffected.
- **Trace:**

  > SubagentRegistry (claudeSubagentRegistry.ts:126-171) is keyed strictly by `toolUseId`, so a skill-spawned agent (shape `{"agentType":"general-purpose"}`, no `toolUseId`) is never recorded and no subagent chat opens. Because the parent model never runs in this shape, `chat/usage` reports 0 tokens, and the `result` branch in ClaudeSdkPipeline._processMessages (claudeSdkPipeline.ts:692-709) only settles the queue head and logs the uuid — it never reads `message.result`; getResultErrorText (claudeMapSessionEvents.ts:528-536) only extracts text for error subtypes, so a successful result's text is discarded entirely. Do not change SubagentRegistry's toolUseId keying or the normal streamed-response path; the fix is additive (backfill on a genuinely empty, zero-token turn only). Related but distinct: comment 1 on https://github.com/microsoft/vscode/issues/334631 describes a second cause in the workbench presentation layer (`presentation: 'hiddenAfterComplete'` on a `run_in_background: true` subagent launch), and the issue body's 'related symptom' describes a chat left permanently unresumable (`resume` fails with 'No conversation found', `sessionId` fails with 'already in use') after a cancelled skill-subagent turn — the reporter names three possible repair strategies for that half without picking one. https://github.com/microsoft/vscode/issues/333174 is an umbrella/tracking issue consolidating many chat-surface defects; it does not itself own this specific fix.
- **Open decisions:**
  - Should the backgrounded-subagent hidden-presentation bug (comment 1) be fixed together with the main result-surfacing bug, or tracked/fixed separately?
  - For the permanently-wedged session after a cancelled skill-subagent turn, which repair strategy should be adopted: moving the conversationless transcript aside, minting a new session id and rebinding, or awaiting the prior process's exit (via `shutdownAndWait`) before reuse?
