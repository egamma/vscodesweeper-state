# Issue #176805 — Activation event for diagnostics

[https://github.com/microsoft/vscode/issues/176805](https://github.com/microsoft/vscode/issues/176805)

## Summary

Keep open: diagnostic-driven extension activation remains missing, and the discussion explicitly moved away from built-in view activation toward Diagnostic.source matching. This team-authored request needs an activation-contract decision, not a staleness close.

## Change summary

Allow extensions providing diagnostic code actions to activate when relevant diagnostics become available rather than at startup.

## Best solution

Define a diagnostic-driven activation contract in the extension-service and marker integration, supporting the cross-language use case described in the thread. Preserve the decision against general built-in-view activation and settle trigger timing and wildcard semantics before implementation.

- **Behavior:**

  > An extension supplying code actions for diagnostics should not need startup activation merely to register its provider. It should become active when diagnostics satisfy an agreed activation condition, including the author's cross-language use case. Acceptance must distinguish matching and nonmatching sources and demonstrate that the newly activated provider can supply its action. General built-in-view activation is not the requested end state after the discussion.
- **Trace:**

  > MainThreadDiagnostics in src/vs/workbench/api/browser/mainThreadDiagnostics.ts connects diagnostic publication and marker changes but does not request activation; ExtHostDiagnostics.onDidChangeDiagnostics in src/vs/workbench/api/common/extHostDiagnostics.ts is an event available to already-running extensions. IMarkerData.source is optional in src/vs/platform/markers/common/markers.ts, and MarkerService.onMarkerChanged reports changed resources rather than source names. AbstractExtensionService.activateByEvent in src/vs/workbench/services/extensions/common/abstractExtensionService.ts dispatches declared events and records requested events for restart. Existing onView activation is in the extension tree-view path, while Problems visibility only rebuilds marker subscriptions. https://github.com/microsoft/vscode/pull/178244 was closed without merging; https://github.com/microsoft/vscode-docs/pull/7127 only documented the built-in-view limitation. The unresolved boundary is when diagnostic-driven activation should occur and what wildcard matching promises; preserve existing diagnostic delivery and do not reopen general built-in-view activation.
- **Open decisions:**
  - Should diagnostic activation occur when matching diagnostics are published, even with all diagnostic UI hidden, or only when the user encounters them?
  - Should onDiagnosticSource:* match every diagnostic, including diagnostics with no source, and should diagnostics already present when an extension becomes available satisfy the activation condition?
