# Issue #339092 — Workspace settings are temporarily unavailable during implicit onLanguage activation after Reload Window

[https://github.com/microsoft/vscode/issues/339092](https://github.com/microsoft/vscode/issues/339092)

## Summary

Fresh, carefully documented report with detailed before/after logs confirmed by the reporter on both 1.125.0 and current 1.140.0 stable — a real timing race where language-triggered activation runs before the workspace configuration sync completes after Reload Window, specific to remote SSH setups.

## Change summary

After 'Developer: Reload Window', an extension activated implicitly via onLanguage:<id> sees the default config value (not the .vscode/settings.json workspace value) because workspace configuration hasn't finished syncing to the extension host yet; onStartupFinished activation doesn't have this problem.

## Best solution

Investigate the extension host startup sequence (ExtensionHostManager.activateByEvent / ExtHostConfiguration's initial IConfigurationInitData delivery) to see whether activation-event dispatch can be sequenced to wait for the initial configuration sync, at least for workspace-scoped reads; needs runtime tracing across the main/ext-host IPC boundary before a fix can be scoped.

- **Trace:**

  > Reporter's repro: with a reload of a window whose active editor has a language-contributing extension, that extension's onLanguage activation runs before the workspace's .vscode/settings.json value is available via getConfiguration()/inspect() — the value briefly reads as the schema default and only becomes correct shortly after. onStartupFinished-triggered activation does not show this gap. The uncertainty is where in ExtensionHostManager/ExtHostConfiguration's startup sequence the ordering guarantee should be added, and whether it should block activation or defer configuration reads instead.
- **Open decisions:**
  - Should workspace-scoped onLanguage activation wait for the initial configuration sync to complete before calling activate(), or should getConfiguration() itself defer/await until workspace config is loaded?
  - Is this specific to remote (SSH) extension hosts, or does it also need fixing for the local extension host path?

## Evidence

- **reporter confirmation:** Reporter re-tested on 1.140.0 (latest stable) after the triage bot's bump suggestion and confirmed the same behavior, with full console logs showing testPath resolves to the default value at ACTIVATE and only picks up the workspace value later.
- **architecture trace:** ExtensionHostManager.activateByEvent/_activateByEvent (src/vs/workbench/services/extensions/common/extensionHostManager.ts:327-355) dispatches activation events to the ext host independently of configuration sync; ExtHostConfiguration (src/vs/workbench/api/common/extHostConfiguration.ts) is constructed from an IConfigurationInitData payload delivered asynchronously, so a fast onLanguage activation during reload can plausibly race ahead of that payload landing — consistent with the reporter's observed timing (testPath correct immediately on activate in normal cases, but stale right after reload).
- **no existing fix:** git log on extHostConfiguration.ts and the workbench configuration service shows no recent related commit addressing this ordering.
