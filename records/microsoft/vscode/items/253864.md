# Issue #253864 — We should automatically accept Chat changes in certain scenarios

[https://github.com/microsoft/vscode/issues/253864](https://github.com/microsoft/vscode/issues/253864)

## Summary

Keep open: current main avoids the new-chat dialog by preserving sessions with pending edits, but mode switching still follows the keep/undo confirmation path and the broader edit-lifecycle design remains unfinished. Maintainers accepted the direction, and the Backlog milestone bars a decline close.

## Change summary

Eliminate disruptive pending-chat-edit dialogs by keeping or finalizing edits automatically when starting another chat, committing or discarding through SCM, or switching chat modes.

## Best solution

Globalize modified-file lifecycle and session attribution so pending edits survive navigation without a modal, remain discoverable and undoable from their originating session, and are reconciled predictably with SCM commit/discard and mode changes.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/actions/chatActions.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatNewActions.ts`, `src/vs/workbench/contrib/chat/browser/widgetHosts/editor/chatEditorInput.ts`, `src/vs/workbench/contrib/chat/common/model/chatModel.ts`, `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingServiceImpl.ts`
- **Validation:** Add chat action/service tests covering pending edits across New Chat and Edit-mode transitions, plus an integration-level check that committing or discarding affected files through SCM leaves no contradictory pending state; verify no keep/undo modal appears and the chosen undo semantics remain available.
- **Behavior:**

  > Starting a new chat, switching into or out of Edit mode, and committing or discarding files through SCM must not present the current pending-edits modal. User changes must not be lost: pending edits either remain visibly attributed and undoable from their originating session or are finalized according to the chosen transition contract. Unrelated files and explicitly rejected edits must remain unaffected. Acceptance covers sessions restored after reload and background sessions as well as the foreground chat.
- **Trace:**

  > New Chat runs through runNewChatAction in src/vs/workbench/contrib/chat/browser/actions/chatNewActions.ts and showClearEditingSessionConfirmation in src/vs/workbench/contrib/chat/browser/widgetHosts/editor/chatEditorInput.ts. PR https://github.com/microsoft/vscode/pull/280224 introduced model.willKeepAlive and persisted pending-edit revival, so this path now preserves edits without prompting rather than accepting them. Mode changes still run through handleModeSwitch in src/vs/workbench/contrib/chat/browser/actions/chatActions.ts, where modified entries invoke the shared keep/undo prompt. The maintainer discussion identifies the architectural boundary: modification state is still coupled to individual chat models, while the intended direction requires global file lifecycle and per-session attribution. Preserve explicit per-file Keep/Undo operations and avoid changing ordinary SCM behavior for files without chat edits.
- **Open decisions:**
  - When New Chat or a mode switch occurs, should pending edits be finalized as ordinary workspace changes, or remain attributed to the prior session and undoable from it?
  - When SCM commits or discards only part of a chat session's working set, should VS Code resolve only the affected files or finalize every pending edit from that session?
  - If multiple foreground or background sessions edit the same file, what user-visible ownership and undo behavior should apply after one session is committed, discarded, or archived?

## Evidence

- **partial implementation:** Merged https://github.com/microsoft/vscode/pull/280224 keeps chat models alive while edits are pending, eagerly revives such sessions, and suppresses the close/new-chat dialog when the model remains alive; it does not finalize all three requested flows.
- **current new-chat path:** On current main, src/vs/workbench/contrib/chat/browser/actions/chatNewActions.ts:346-354 calls handleCurrentEditingSession before clearing the visible chat, while src/vs/workbench/contrib/chat/browser/widgetHosts/editor/chatEditorInput.ts:543-550 suppresses confirmation when model.willKeepAlive is true. Pending edits are preserved rather than automatically accepted.
- **remaining mode-switch behavior:** src/vs/workbench/contrib/chat/browser/actions/chatActions.ts:1739-1779 still routes switches into or out of Edit mode through handleCurrentEditingSession when modified entries exist; the shared prompt in src/vs/workbench/contrib/chat/browser/widgetHosts/editor/chatEditorInput.ts:506-540 still offers Keep & Continue or Undo & Continue.
- **maintainer direction:** https://github.com/microsoft/vscode/issues/253864#issuecomment-3595259263 describes the longer-term need to detach document modification state from a 1:1 chat-session lifecycle, attribute changes to sessions, and support multiple/background sessions editing files.
- **accepted scope:** A maintainer accepted the new-session behavior once previous sessions became discoverable at https://github.com/microsoft/vscode/issues/253864#issuecomment-3037221728, and the related SCM request https://github.com/microsoft/vscode/issues/255432 was closed in favor of this issue rather than implemented as a separate canonical.
- **related prerequisite:** The open welcome/history work at https://github.com/microsoft/vscode/issues/251187 added recent sessions, supporting recovery from preserved edits, but it does not own the edit-lifecycle behavior requested here.
