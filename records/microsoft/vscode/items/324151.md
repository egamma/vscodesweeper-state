# Issue #324151 — Unable to connect to tunnel after updating service remotely

[https://github.com/microsoft/vscode/issues/324151](https://github.com/microsoft/vscode/issues/324151)

## Summary

Keep open as the canonical tunnel-update connection bug. Two companion reports were explicitly closed as duplicates of this team-authored issue, and no fixing commit or open fixing PR references it.

## Change summary

Updating the remote tunnel service and then the local VS Code client can leave the tunnel reachable from its host but reject client connections with a WebSocket failure or version mismatch.

## Best solution

Make tunnel service updates preserve client compatibility or reliably replace and restart an installed service before reconnecting. Cover the update sequence across the bundled tunnel CLI, installed service, and remote server handshake with a regression test.

## Plan brief

- **Likely files:** `src/vs/platform/remoteTunnel/node/tunnelProcessCoordinator.ts`, `src/vs/platform/remoteTunnel/node/codeTunnelCliProcess.ts`, `src/vs/server/node/remoteExtensionHostAgentServer.ts`, `src/vs/platform/remoteTunnel/test/node/tunnelProcessCoordinator.test.ts`
- **Validation:** Add a tunnel process regression test for an application/service version transition, then run the targeted TunnelProcessCoordinator node tests; the final plan should also verify that a client can reconnect after updating both the installed tunnel service and VS Code.
- **Behavior:**

  > A user connected through Remote Tunnels can accept a remote tunnel service update and update the local VS Code client without permanently losing access to the tunnel. After both updates and the client restart, reconnecting must either succeed with compatible components or complete the required service replacement before attempting the connection. Existing authentication and deliberate rejection of genuinely incompatible clients must remain intact.
- **Trace:**

  > The primary report at https://github.com/microsoft/vscode/issues/324151 ends in WebSocket status 1006 after the service and client update sequence. The independent report https://github.com/microsoft/vscode/issues/326199 exposes the more specific failure, "Client refused: version mismatch," and confirms that downgrading both client and remote server restores connectivity. That rejection is emitted by the commit comparison in src/vs/server/node/remoteExtensionHostAgentServer.ts. On the host side, RemoteTunnelService delegates lifecycle work to TunnelProcessCoordinator, whose service reconciliation checks installation state before running the bundled CLI resolved by CodeTunnelCli. The uncertainty starts at whether the installed service remains on the previous commit, whether the session CLI attaches to that stale service, or whether update ordering exposes another compatibility window. Preserve the handshake's protection against genuinely mismatched builds and avoid broad changes to unrelated remote connection types.
- **Open decisions:**
  - Which component remains stale after the reported update sequence: the installed tunnel service, its delegated server process, or the reconnecting client's endpoint metadata?
  - Should an application update proactively reinstall an existing tunnel service, or should the service/session protocol negotiate and complete its own compatible update before accepting clients?
  - What compatibility window, if any, should the remote server handshake permit without weakening the commit-mismatch safeguard?
