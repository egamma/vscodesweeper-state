# Issue #191904 — `DebugSession` objects are leaked

[https://github.com/microsoft/vscode/issues/191904](https://github.com/microsoft/vscode/issues/191904)

## Summary

Keep open: the initial leak fix was only partial, and follow-up PRs explicitly restored retained listeners because the DebugSession lifecycle was not yet safe. Current main still deliberately retains inactive sessions for REPL and extension-host revival, so there is no concrete commit proving the lifecycle debt is fully resolved.

## Change summary

Ensure repeatedly starting and stopping debug sessions does not retain DebugSession objects and their listeners indefinitely.

## Best solution

Define a complete DebugSession lifecycle that bounds inactive-session retention while preserving completed-session REPL history, restart behavior, and extension-host session revival, then cover repeated start/stop cycles with lifecycle and retention tests.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/common/debugModel.ts`, `src/vs/workbench/contrib/debug/browser/debugService.ts`, `src/vs/workbench/contrib/debug/browser/debugSession.ts`, `src/vs/workbench/contrib/debug/test/browser/callStack.test.ts`, `src/vs/workbench/contrib/debug/test/browser/repl.test.ts`
- **Validation:** Add a focused debug lifecycle test that runs at least ten same-configuration start/end cycles and asserts retained sessions and per-session listeners remain bounded, while existing restart and REPL tests continue to pass; repeat the issue's heap-snapshot scenario as the manual acceptance check.
- **Behavior:**

  > Repeatedly starting, stopping, and resuming the same debug configuration must not cause DebugSession objects, adapter state, or session listeners to grow linearly. Completed-session REPL output must remain available for the lifetime chosen by the maintainer, and restarting or reviving a session must preserve existing observable behavior. Acceptance requires bounded retained-session/listener counts after ten cycles and no regressions in debug console, restart, or stop-button behavior.
- **Trace:**

  > DebugModel in src/vs/workbench/contrib/debug/common/debugModel.ts keeps inactive sessions in its sessions array for REPL and extension-host revival and disposes only selected inactive sessions from addSession. DebugService.registerSessionListeners in src/vs/workbench/contrib/debug/browser/debugService.ts owns per-session listeners, while DebugSession in src/vs/workbench/contrib/debug/browser/debugSession.ts separates reconnectable rawListeners from lifetime-wide globalDisposables. https://github.com/microsoft/vscode/pull/191913 attempted disposal in these paths, but https://github.com/microsoft/vscode/pull/192951 deliberately restored part of the retention after restart regressions and assigned the complete lifecycle work back to this issue. Preserve restart, stop-button, completed REPL, child-session, and extension-host revival behavior; the uncertainty begins at the intended lifetime of an inactive session after its adapter ends.
- **Open decisions:**
  - After a debug adapter ends, how long should its completed-session REPL history and DebugSession identity remain observable before the session is disposed?
  - Which restart or extension-host revival scenarios require reusing the same DebugSession object rather than creating a replacement with preserved user-visible state?

## Evidence

- **partial fix:** https://github.com/microsoft/vscode/pull/191913 merged commit 1e528d7a4cba563f465265344e260394e2e8f332 and described fixing several DebugSession retention paths, but it did not close this issue.
- **explicit rollback:** https://github.com/microsoft/vscode/pull/192951 merged commit 9003ac66f660c39381f73198a05ea67670570221 and explicitly restored the DebugService listener leak because the DebugSession lifecycle was not considered safe; its description says the larger lifecycle work belongs in https://github.com/microsoft/vscode/issues/191904.
- **current source:** src/vs/workbench/contrib/debug/common/debugModel.ts still stores inactive sessions in DebugModel.sessions; getSessions documents that they are retained for REPL and extension-host session revival, while addSession only disposes selected inactive sessions when a replacement session is added.
- **listener lifecycle:** src/vs/workbench/contrib/debug/browser/debugService.ts registerSessionListeners now creates a per-session DisposableStore removed on onDidEndSession, while src/vs/workbench/contrib/debug/browser/debugSession.ts separately manages rawListeners and globalDisposables. These intertwined restart, end, and disposal paths require lifecycle-level validation rather than another isolated cleanup.
