# Issue #252509 — Search only in Open Editors issue

[https://github.com/microsoft/vscode/issues/252509](https://github.com/microsoft/vscode/issues/252509)

## Summary

Keep open: the reporter supplied exact reproduction steps, and an independent report confirms the same settings-triggered failure over SSH in 1.135.0. Current source still exposes a plausible user-data search-provider routing problem; no verified fix or eligible duplicate canonical was found.

## Change summary

Opening local user settings or keybindings in a remote window causes Search only in Open Editors to fail with a ripgrep spawn ENOENT error.

## Best solution

Make open-editor search handle local user-data resources in their owning filesystem context without breaking searches of remote files. Diagnose provider selection for vscode-userdata across local and remote extension hosts rather than treating this as a missing ripgrep installation or a WSL-only extension defect.

- **Behavior:**

  > In a Windows-to-Linux remote window, opening local user settings or keybindings through the preferences commands must not make Search only in Open Editors fail. Known matches in open remote files must remain available with those editors open. Searching local user-data content must respect its actual filesystem ownership rather than interpret its Windows path as a remote Linux directory. Acceptance includes both WSL and SSH and preserves ordinary local and remote search behavior.
- **Trace:**

  > QueryBuilder.commonQuery and commonQueryFromFileList in src/vs/workbench/services/search/common/queryBuilder.ts turn open editor resources into scheme-preserving folder queries. NativeExtHostSearch in src/vs/workbench/api/node/extHostSearch.ts unconditionally registers a vscodeUserData provider, while SearchService in src/vs/workbench/services/search/common/searchService.ts retains one provider per scheme and dispatches searches by that scheme. RipgrepSearchProvider handles user-data queries in src/vs/workbench/services/search/node/ripgrepSearchProvider.ts, and RipgrepTextSearchEngine uses the folder URI's fsPath as the spawn working directory. The independent report at https://github.com/microsoft/vscode/issues/252509#issuecomment-5480974907 confirms that the remote binary exists and that opening the same file through Explorer avoids the failure. The unresolved boundary is which extension host owns the user-data provider at runtime and how the preferences-created URI reaches it; the source inspection did not establish registration order or conclusively locate the correction. Preserve mixed local/remote search support and do not broaden this into general ENOENT handling or unrelated WSL search hangs.
