# Issue #336805 — MCP server remains stuck in Starting state after startup failure

[https://github.com/microsoft/vscode/issues/336805](https://github.com/microsoft/vscode/issues/336805)

## Summary

Confirmed as a real race in the Copilot Agent Host MCP lifecycle handling: a follow-up commenter traced logs showing a stale `session.mcp_servers_loaded` snapshot overwriting a newer `ready` state, and reading the source confirms there is no freshness/ordering guard between the `loaded` event, `statusChanged` event, and `rpc.mcp.list` inventory seed — any of the three can apply an out-of-order snapshot unconditionally.

## Change summary

MCP management page can get stuck showing 'Starting' after startup actually succeeds, because a late/duplicate `mcp_servers_loaded` snapshot overwrites the newer ready state.

## Best solution

Add ordering protection in CopilotAgentSession's MCP handling (`onMcpServersLoaded` / `onMcpServerStatusChanged` / `_refreshMcpServersFromRpc`, all feeding `_applyMcpServerList`/`_mcpCustomizations.applyAll`) so a late-arriving 'pending/starting' snapshot cannot regress a server already observed as connected/ready — the exact mechanism (sequence stamp vs. state-precedence rule) needs a maintainer decision since it must not also mask a legitimate restart-to-starting transition.
