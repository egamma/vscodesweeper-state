Its reproduction describes replacement in a Python notebook jumping from match 26 to 6 instead of continuing at 26. This is the same reporter-observable replacement-index jump, not merely a related notebook concern, and meets the stronger duplicate bar for a re-reviewed item.
- **Current source defect:** src/vs/workbench/contrib/notebook/browser/contrib/find/findModel.ts:424 computes the flattened match position after the previous selection, but _updateCurrentMatch at lines 503-504 reduces that position modulo findMatches.length, the number of matching cells rather than the total number of occurrences. With one matching code cell and multiple remaining occurrences, any restored index becomes zero; with multiple matching cells it can jump to another earlier index.
- **Replacement entry points:** src/vs/workbench/contrib/notebook/browser/contrib/find/notebookFindWidget.ts:177-179 routes Enter in the replacement input to replaceOne; replaceOne at lines 212-240 edits the active cell through NotebookViewModel.replaceOne. FindModel's notebook-content listener then schedules research, reaching the incorrect index normalization. The affected behavior is implemented in VS Code's notebook find infrastructure.
- **Additional corroboration:** The older open issue https://github.com/microsoft/vscode/issues/198434 includes https://github.com/microsoft/vscode/issues/198434#issuecomment-1831771965, reporting that manually selecting a later match and clicking Replace snaps the selection back to the first notebook match. In contrast, https://github.com/microsoft/vscode/issues/200293 describes a scrolling failure while the index advances, so it is not the chosen canonical.
