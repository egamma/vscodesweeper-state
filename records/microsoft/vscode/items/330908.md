# Issue #330908 — Extension command titles lose localization after installing/updating an extension until full restart (VS Code 1.133)

[https://github.com/microsoft/vscode/issues/330908](https://github.com/microsoft/vscode/issues/330908)

## Summary

Confirmed on current main by tracing the code: `ExtensionsScannerService.createNlsConfiguration` uses the raw, possibly-`undefined` `language` field instead of the `language ?? platform.language` fallback that is already applied when resolving `translations` a few lines earlier, so any scan path that omits `language` (used after install/update) silently disables locale lookup for that extension's manifest strings.

## Change summary

Extension command titles lose localization after an extension install/update until VS Code is fully restarted (a Reload Window is not enough).

## Best solution

In src/vs/platform/extensionManagement/common/extensionsScannerService.ts, make the `language` stored on `ExtensionScannerInput` consistent with the fallback already used for `translations` (i.e. `language ?? platform.language`), so `findMessageBundles`/`getLocalizedMessages` keep resolving `package.nls.<locale>.json` for extensions scanned via the post-install/update paths (`scanUserExtensionAtLocation`, `scanLocalExtension`) that don't explicitly pass a `language`.

## Evidence

- **root cause:** src/vs/platform/extensionManagement/common/extensionsScannerService.ts:488 resolves `translations` with `getTranslations(language ?? platform.language)`, but `createExtensionScannerInput` (line 505) stores the raw `language` param (which can be `undefined`) directly onto `ExtensionScannerInput`, and `ExtensionScannerInput.createNlsConfiguration` (line 552-559) copies that raw value into `NlsConfiguration.language`.
- **consuming guard:** `findMessageBundles` (line 908-930) checks `!nlsConfiguration.language` and, when true, returns the un-localized `package.nls.json` bundle without ever looking at `package.nls.<locale>.json` — matching the reporter's exthost warning "Using default string since no string found in i18n bundle".
- **asymmetric call sites:** The full-restart scan path (src/vs/workbench/services/extensions/electron-browser/cachedExtensionScanner.ts:57) explicitly passes `language` into `scanUserExtensions`, while the incremental post-install/update scan paths in src/vs/platform/extensionManagement/node/extensionManagementService.ts (`scanUserExtensionAtLocation` line 610/877 via `scanExistingExtension`, and `scanLocalExtension` line 871 via `scanUserExtensions({ profileLocation })`) all omit `language`, so only those incremental scans hit the bug.
- **no existing fix:** `git log` on extensionsScannerService.ts (HEAD 7fee8151) shows no recent commit touching this fallback; the asymmetry is present on current main.
