# Issue #182191 — Allow to target a setting in a workspace file to one of the roots

[https://github.com/microsoft/vscode/issues/182191](https://github.com/microsoft/vscode/issues/182191)

## Summary

Keep open: workspace-level glob settings still lack a portable way to target one named root. Maintainers explicitly invited this separate discussion, and the older variable-resolution request does not report the same observable problem required for a re-reviewed duplicate close.

## Change summary

Allow a glob in a .code-workspace setting to reference a named workspace root without embedding its absolute path.

## Best solution

Provide a documented root-reference syntax for supported path/glob settings, starting with the files.readonlyInclude use case. Preserve existing relative-glob behavior and avoid implicitly enabling arbitrary variable substitution throughout configuration.

## Plan brief

- **Likely files:** `src/vs/workbench/common/resources.ts`, `src/vs/workbench/services/filesConfiguration/common/filesConfigurationService.ts`, `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `src/vs/workbench/services/configurationResolver/common/variableResolver.ts`, `src/vs/workbench/test/common/resources.test.ts`
- **Validation:** Extend the ResourceGlobMatcher suite in src/vs/workbench/test/common/resources.test.ts with two roots containing identical relative paths: the agreed named-root pattern must match only the selected root, remain valid after relocating the workspace, and preserve existing relative and absolute matching. Include folder rename/removal checks according to the agreed contract; run the targeted suite in an implementation workspace, not this read-only checkout.
- **Behavior:**

  > A setting in a .code-workspace file can target files under one named workspace root without hard-coding its absolute location or requiring a settings file inside that root. With two roots containing the same relative filename, the targeted setting affects only the selected root. Moving the workspace and its folders together does not invalidate the reference. Existing unqualified relative patterns and absolute patterns retain their behavior.
- **Trace:**

  > FilesConfigurationService.createReadonlyMatcher reads files.readonlyInclude and files.readonlyExclude and passes their expressions directly to ResourceGlobMatcher. ResourceGlobMatcher.updateExpressions parses an expression per root; doGetExpression performs path normalization, and matches tests root-relative paths plus absolute paths when present, with no workspace-variable expansion. The configuration resolver separately supports named workspaceFolder variables, but this matching path does not call it. The maintainer invitation at https://github.com/microsoft/vscode/issues/4873#issuecomment-1543953520 establishes that settings-level named-root targeting is distinct from search-view selection. https://github.com/microsoft/vscode/issues/2809 provides related configuration-resolution context, not a verified duplicate for this re-reviewed report. The uncertainty starts at the public syntax and supported-setting scope; preserve current matching semantics and do not assume general configuration interpolation is approved.
- **Open decisions:**
  - Should named-root targeting use the existing ${workspaceFolder:name} syntax, or a distinct glob-specific root selector?
  - Should the initial contract apply only to readonly include/exclude settings, to all ResourceGlobMatcher-backed settings, or to a broader explicitly defined set of path settings?
  - What user-visible behavior should a supported setting have when its referenced workspace root is renamed, missing, or ambiguously named?
