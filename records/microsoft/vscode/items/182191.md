# Issue #182191 — Allow to target a setting in a workspace file to one of the roots

[https://github.com/microsoft/vscode/issues/182191](https://github.com/microsoft/vscode/issues/182191)

## Summary

Keep open: workspace-level glob settings still cannot portably target a named workspace root. Existing folder settings are a workaround, and the related issues do not establish an older canonical reporting the same observable limitation.

## Change summary

Allow path or glob settings in a .code-workspace file to reference a particular workspace root without absolute paths.

## Best solution

Provide a supported named-root reference for workspace-level path/glob settings, starting with the documented files.readonlyInclude use case. Agree on the supported settings and reference semantics before implementation, preserving existing literal patterns and folder overrides.

## Plan brief

- **Likely files:** `src/vs/workbench/common/resources.ts`, `src/vs/workbench/services/filesConfiguration/common/filesConfigurationService.ts`, `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `src/vs/workbench/services/configurationResolver/common/variableResolver.ts`, `src/vs/workbench/test/common/resources.test.ts`
- **Validation:** After the contract is agreed, add targeted ResourceGlobMatcher tests with two named roots containing identical relative file paths: a workspace-level root-qualified pattern must match only the selected root and remain valid when that root's absolute location changes. Verify existing relative and absolute patterns and configuration updates remain unchanged; manually confirm files.readonlyInclude in a multi-root .code-workspace file.
- **Behavior:**

  > A path/glob setting stored in a .code-workspace file should be able to identify a specific workspace root without embedding its absolute location or requiring a settings file inside that root. For files.readonlyInclude, identical relative paths in other roots must remain writable unless independently matched. Moving the workspace and its roots must not require rewriting machine-specific paths. Existing unqualified glob patterns and folder-level overrides must retain their behavior.
- **Trace:**

  > FilesConfigurationService.createReadonlyMatcher reads the resource-scoped setting and supplies it directly to ResourceGlobMatcher. ResourceGlobMatcher.updateExpressions parses configured keys separately for each root, while matches uses the resource's root-relative path and optionally its absolute path; doGetExpression does not expand workspace-root references. AbstractVariableResolverService in src/vs/workbench/services/configurationResolver/common/variableResolver.ts already recognizes named workspaceFolder arguments, but that behavior is not connected to this settings path. The current matcher test suite is src/vs/workbench/test/common/resources.test.ts. The discussion at https://github.com/microsoft/vscode/issues/182191 establishes the portable named-root goal, while https://github.com/microsoft/vscode/issues/2809 provides broader design context rather than a verified same-symptom canonical. Preserve existing literal settings interpretation and do not extend arbitrary extension settings without an agreed contract. Uncertainty begins at which settings participate and the observable semantics of invalid or ambiguous root references.
- **Open decisions:**
  - Should the initial supported surface cover only core path/glob settings such as files.readonlyInclude and files.readonlyExclude, or establish an opt-in contract for additional settings?
  - Should named-root references use the existing ${workspaceFolder:name} syntax, and what should users observe when that name is missing or ambiguous?
