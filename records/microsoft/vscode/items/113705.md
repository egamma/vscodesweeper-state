# Issue #113705 — Disallow navigating away from custom editors when retainContextWhenHidden is false and the backup has yet to run orfailed

[https://github.com/microsoft/vscode/issues/113705](https://github.com/microsoft/vscode/issues/113705)

## Summary

The requested backup-aware protection against hidden-webview disposal is still absent from current source. Keep this accepted Backlog request open: existing context retention is an alternative with substantial memory cost, and the related closed issues do not resolve its full scope.

## Change summary

Protect custom-editor state when switching tabs before a backup completes or after a backup fails.

## Best solution

Define a custom-editor lifecycle contract that preserves unsynchronized webview state across tab switches without requiring indefinite context retention. Decide whether navigation waits for persistence or the hidden context remains alive, including the behavior when persistence fails.

- **Behavior:**

  > Custom editors that cannot immediately synchronize large edits need a way to avoid losing webview-only state when a tab becomes hidden. Cover both switching before backup completes and switching after backup fails, without requiring indefinite retention of every hidden context. Acceptance must exercise both cases and confirm that a successfully persisted editor can release its context. Whether the tab switch waits or the hidden context remains alive requires a product decision.
- **Trace:**

  > WebviewEditor.setEditorVisible(false) in src/vs/workbench/contrib/webviewPanel/browser/webviewEditor.ts calls OverlayWebview.release in src/vs/workbench/contrib/webview/browser/overlayWebview.ts, which synchronously clears a non-retained context without checking custom-document backup state. MainThreadCustomEditorModel.backup and canHotExit in src/vs/workbench/api/browser/mainThreadCustomEditors.ts track persistence separately. The existing CustomDocument remains in the extension host, so the missing protection concerns unsynchronized webview state; do not change normal document reuse or assume every provider restores from backup on a tab switch. The retainContextWhenHidden boolean in src/vscode-dts/vscode.d.ts supplies unconditional retention, not persistence-aware reclamation. https://github.com/microsoft/vscode/issues/113507 contains related safe-to-dispose API discussion but is closed and does not settle this request. The design boundary is the coordination between hiding, persistence, and reclamation, including failure semantics; no patch or runtime reproduction was attempted.
- **Open decisions:**
  - Should an unpersisted custom editor delay tab navigation, or should navigation proceed while its hidden context remains alive until persistence succeeds?
  - If backup fails, should the editor retain its context and allow navigation, or require the proposed Save, Don't Save, or Cancel decision before navigation?
