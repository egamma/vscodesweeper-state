# Issue #236606 — Automatically adjust minimap scale according to display scale

[https://github.com/microsoft/vscode/issues/236606](https://github.com/microsoft/vscode/issues/236606)

## Summary

The defect remains on current main: minimap layout doubles its effective scale only when the display pixel ratio reaches 2, leaving fractional scales such as 1.75 undersized. The issue should remain open while maintainers decide how fractional display scaling should map onto the minimap's integer rendering model.

## Change summary

Keep the minimap at a consistent physical size when moving VS Code between displays with different scale factors.

## Best solution

Define and implement a stable mapping from fractional display pixel ratios to minimap size, updating automatically when the window moves between displays while preserving the configured minimap scale semantics and rendering performance.

## Plan brief

- **Likely files:** `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/test/browser/config/editorLayoutProvider.test.ts`
- **Validation:** Add editor layout tests for pixel ratios 1, 1.5 or 1.75, and 2 that assert the agreed minimap sizing behavior and verify that recomputing after a pixel-ratio transition produces the expected layout.
- **Behavior:**

  > The minimap should remain approximately consistent in physical size when a VS Code window moves between displays using different OS scale factors, including fractional factors such as 175%. A configured minimap scale must retain predictable meaning, and moving back to a 100% display must restore the corresponding size without requiring a settings change. Acceptance should cover both sides of the current 2x threshold and ensure existing 1x, 2x, and 4x behavior does not regress.
- **Trace:**

  > EditorConfiguration in src/vs/editor/browser/config/editorConfiguration.ts subscribes to PixelRatio changes and feeds the current ratio into EditorLayoutInfoComputer. In src/vs/editor/common/config/editorOptions.ts, `_computeMinimapLayout` leaves the configured scale unchanged below pixel ratio 2 and doubles it at 2 or above, creating the reported discontinuity at 175% scaling. Existing layout tests in src/vs/editor/test/browser/config/editorLayoutProvider.test.ts cover integer high-DPI ratios but not fractional ratios. The related report https://github.com/microsoft/vscode/issues/236999 independently reaches the same threshold. Non-integer rendering was previously declined in https://github.com/microsoft/vscode/issues/84168 because of aliasing and performance costs, so the plan must settle whether consistent sizing uses integer rounding or revisits that constraint; unrelated editor font and general window zoom behavior should remain unchanged.
- **Open decisions:**
  - Should fractional display scaling select a rounded integer minimap scale, or should the minimap support fractional effective scales despite the rendering and performance implications?
  - Should automatic display compensation multiply the user's configured `editor.minimap.scale`, or should the setting represent the final effective size regardless of display pixel ratio?

## Evidence

- **current source:** src/vs/editor/common/config/editorOptions.ts:2786 uses `pixelRatio >= 2 ? Math.round(input.minimap.scale * 2) : input.minimap.scale`; at a 1.75 pixel ratio the effective scale remains 1, while at 2 it jumps to 2.
- **display-change path:** src/vs/base/browser/pixelRatio.ts monitors `window.devicePixelRatio`, and src/vs/editor/browser/config/editorConfiguration.ts:98 recomputes editor options when it changes, so moving between displays reaches the minimap layout calculation but retains its discontinuous threshold.
- **test gap:** src/vs/editor/test/browser/config/editorLayoutProvider.test.ts covers minimap layouts at pixel ratios 2 and 4 but has no fractional-DPI case.
- **related confirmation:** https://github.com/microsoft/vscode/issues/236999 reports the same abrupt minimap-size transition through window zoom; a maintainer identified the same pixel-ratio threshold as its cause.
- **design constraint:** https://github.com/microsoft/vscode/issues/84168 documents that non-integer minimap scales require aliasing with performance and complexity costs and was closed as out of scope, leaving rounding versus a broader rendering change as an explicit product choice.
