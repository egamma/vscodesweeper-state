# Issue #236606 — Automatically adjust minimap scale according to display scale

[https://github.com/microsoft/vscode/issues/236606](https://github.com/microsoft/vscode/issues/236606)

## Summary

The mixed-DPI sizing defect remains on current main and is already correctly routed to the minimap area. The layout calculation responds to display pixel-ratio changes but applies a discontinuous scale adjustment, making the minimap physically smaller on displays below the 2x threshold.

## Change summary

Keep the minimap at a consistent physical size when a VS Code window moves between displays with different scaling factors.

## Best solution

Make minimap dimensions remain visually consistent across device-pixel-ratio changes while preserving integer-backed glyph rendering and the explicit `editor.minimap.scale` semantics. A maintainer should first choose how fractional display ratios map onto the minimap's integer raster scale.

## Plan brief

- **Likely files:** `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/test/browser/config/editorLayoutProvider.test.ts`
- **Validation:** Extend the EditorLayoutProvider minimap tests with pixel ratios 1, 1.5, 1.75, and 2, asserting consistent CSS-space minimap character width across simulated display changes while retaining the existing integer-ratio and minimap size-mode expectations.
- **Behavior:**

  > With the same `editor.minimap.scale` value, the minimap should retain a consistent physical size when a window moves between 100%, 150%, 175%, and 200% scaled displays. The transition must not abruptly resize at the 2x threshold. Existing explicit scale values and proportional, fill, and fit modes must continue to behave consistently.
- **Trace:**

  > EditorConfiguration in src/vs/editor/browser/config/editorConfiguration.ts listens to PixelRatio changes and recomputes editor options, so moving between displays already reaches the minimap layout path. In EditorLayoutInfoComputer._computeMinimapLayout in src/vs/editor/common/config/editorOptions.ts, `minimapScale` doubles only at `pixelRatio >= 2`, while CSS character width is `minimapScale / pixelRatio`; fractional ratios below 2 therefore shrink the minimap and crossing 2 causes a jump. The existing layout tests cover integer ratios but not 1.5 or 1.75. The boundary is minimap layout and raster sizing: preserve integer glyph-buffer behavior, rendering performance, explicit scale semantics, and all minimap size modes. https://github.com/microsoft/vscode/issues/236999 confirms the same threshold path for window zoom but does not cover the broader cross-display behavior.
- **Open decisions:**
  - Should fractional display ratios select a rounded integer raster scale, or should the minimap gain fractional resampling despite the rendering-quality and performance costs?
  - Should `editor.minimap.scale` remain an integer user multiplier applied on top of automatic DPI compensation, or should its schema and meaning change?
  - What tolerance defines physically consistent sizing around DPI thresholds without causing visible jumps when a window crosses displays?

## Evidence

- **source trace:** In src/vs/editor/common/config/editorOptions.ts, EditorLayoutInfoComputer._computeMinimapLayout doubles the configured minimap scale only when `pixelRatio >= 2`, then computes `minimapCharWidth` as `minimapScale / pixelRatio`. At 1.75x with scale 1 this yields about 0.57 CSS pixels, versus 1 CSS pixel at 1x, directly explaining the reported shrinkage.
- **display-change path:** src/vs/editor/browser/config/editorConfiguration.ts subscribes to PixelRatio.onDidChange and recomputes editor options; src/vs/base/browser/pixelRatio.ts monitors `window.devicePixelRatio`, including changes caused by moving a window between displays.
- **coverage gap:** src/vs/editor/test/browser/config/editorLayoutProvider.test.ts covers minimap layouts at integer pixel ratios including 2 and 4, but does not cover fractional ratios such as 1.5 or 1.75 where the discontinuity occurs.
- **related issue:** https://github.com/microsoft/vscode/issues/236999 remains open and reports the same threshold behavior through window zoom; a maintainer traced it to the same minimap-scale calculation. It is narrower than this issue's cross-display requirement and therefore is not a suitable canonical duplicate.
- **existing setting limitation:** `editor.minimap.scale` is restricted to integer values 1, 2, and 3 in src/vs/editor/common/config/editorOptions.ts and applies globally to the editor configuration, so it cannot keep the physical size consistent when moving between differently scaled displays.
