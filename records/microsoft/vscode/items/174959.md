# Issue #174959 — [folding] Allow us to know if a region is folded or not

[https://github.com/microsoft/vscode/issues/174959](https://github.com/microsoft/vscode/issues/174959)

## Summary

A real API gap remains: extensions can obtain possible folding ranges and invoke folding commands, but cannot inspect or observe the current collapsed state. Older requests were closed or only partially addressed, and none is an open canonical suitable for a duplicate close.

## Change summary

Expose whether editor regions are currently folded and notify extensions when their folding state changes.

## Best solution

Design a proposed text-editor API that exposes current collapsed ranges and fold-state changes while avoiding unconditional synchronization of view-model data. It should support capturing state before operations such as search and detecting automatic unfolding afterward.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/contrib/folding/browser/folding.ts`, `src/vs/editor/contrib/folding/browser/foldingModel.ts`, `src/vs/workbench/api/browser/mainThreadEditor.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/common/extHostTextEditor.ts`, `src/vs/workbench/api/common/extHostTextEditors.ts`
- **Validation:** Add extension-host/API tests that create nested folds and verify the selected public contract reports initial collapsed state and updates after manual fold, unfold, and automatic reveal; existing folding and text-editor API tests must remain passing.
- **Behavior:**

  > An extension can determine which regions of a visible text editor are currently collapsed, including enough range information to distinguish and later revisit them. It can observe folding-state changes caused by user commands and automatic editor actions such as revealing a search match. Foldable-but-expanded ranges remain distinguishable from collapsed ranges, and existing folding providers and commands retain their current behavior.
- **Trace:**

  > FoldingModel in src/vs/editor/contrib/folding/browser/foldingModel.ts owns the authoritative collapsed flags and emits `onDidChange`; FoldingController in src/vs/editor/contrib/folding/browser/folding.ts owns that model per editor and already serializes collapsed regions for internal view-state restoration. The public `FoldingRangeProvider` and `vscode.executeFoldingRangeProvider` expose candidate ranges only. MainThreadTextEditorProperties currently sends selections, options, and visible ranges through src/vs/workbench/api/common/extHost.protocol.ts to ExtHostTextEditor, so no collapsed state reaches extensions. The boundary should remain editor folding state: do not expose general view coordinates or change provider semantics. https://github.com/microsoft/vscode/issues/22276 documents the performance and consistency concerns around eagerly synchronizing view-model data; https://github.com/microsoft/vscode/issues/81498's `foldedLine` movement solves navigation only.
- **Open decisions:**
  - Should the public contract provide a synchronous TextEditor snapshot of collapsed ranges, or an opt-in asynchronous query/event model that avoids sending folding data to every extension host?
  - Should nested collapsed ranges all be reported, or only the effective outer ranges whose contents are currently hidden?
  - Which transitions must emit notifications: direct fold/unfold commands only, or also automatic reveal, restored editor state, and folding-range recomputation?

## Evidence

- **public API gap:** src/vscode-dts/vscode.d.ts exposes FoldingRangeProvider and vscode.executeFoldingRangeProvider, which return foldable ranges, but TextEditor has no collapsed-range property, folded-position query, or fold-state event.
- **internal state:** src/vs/editor/contrib/folding/browser/foldingModel.ts tracks `isCollapsed` and emits `FoldingModelChangeEvent` with `collapseStateChanged`; FoldingController.saveViewState in src/vs/editor/contrib/folding/browser/folding.ts also captures collapsed regions internally.
- **API boundary:** src/vs/workbench/api/browser/mainThreadEditor.ts and src/vs/workbench/api/common/extHost.protocol.ts currently synchronize selections, options, and visible ranges, but no folding state.
- **partial existing capability:** The current `cursorMove` command supports `by: "foldedLine"` in src/vs/editor/common/cursor/cursorMoveCommands.ts, addressing the navigation case from https://github.com/microsoft/vscode/issues/81498 and one comment here, but not state capture, restoration, or decoration layout.
- **older precedent:** https://github.com/microsoft/vscode/issues/22276 requested the same general query but was closed in 2017 for roadmap reasons after maintainers raised synchronization and view-model abstraction concerns. It is closed and therefore cannot serve as a duplicate canonical; this issue's Backlog milestone indicates the request was subsequently accepted for continued tracking.
