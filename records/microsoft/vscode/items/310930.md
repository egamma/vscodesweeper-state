# Issue #310930 — Stabilize `vscode.proposed.tunnels` API: enabling named portless tunnel aliases for AI-assisted devcontainer workflows

[https://github.com/microsoft/vscode/issues/310930](https://github.com/microsoft/vscode/issues/310930)

## Summary

Keep this accepted API request open: the tunnels API remains proposal-gated, and 24 upvotes earned its Backlog placement. Stabilization needs an API-owner decision, including clarification that the current label parameter does not guarantee a named, persistent devtunnels.ms endpoint.

## Change summary

Expose a supported extension API for programmatic tunnel creation and clarify support for predictable, named endpoints across devcontainer sessions.

## Best solution

Define a supported tunnel API contract and document the path to finalization, explicitly separating port display labels from provider-assigned endpoint names and persistence guarantees. Decide whether a minimal stable subset meets the workflow or whether named endpoint provisioning requires an additional contract.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.tunnels.d.ts`, `src/vscode-dts/vscode.proposed.resolvers.d.ts`, `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/browser/mainThreadTunnelService.ts`, `src/vs/workbench/services/remote/common/tunnelModel.ts`
- **Validation:** After agreeing the contract, exercise an extension without proposed-API enablement in a remote devcontainer: create a tunnel, reach the service through its returned address, and verify disposal. If deterministic aliases are included, verify the documented name and lifetime guarantees across container/window restarts and concurrent worktrees; a matching Ports-view label alone must not satisfy that check.
- **Behavior:**

  > Extensions need a supported way to create service tunnels without requiring users to enable a proposed API. The requested workflow additionally needs predictable named endpoints across development sessions, which is a stronger contract than assigning a port display label. Acceptance must distinguish successful programmatic forwarding from deterministic endpoint provisioning and verify whichever guarantees the API owners approve. Existing forwarding and URI-resolution behavior must remain compatible.
- **Trace:**

  > src/vscode-dts/vscode.proposed.tunnels.d.ts contains the requested declarations, and src/vs/workbench/api/common/extHost.api.impl.ts still gates them on the tunnels proposal. The stable alternative env.asExternalUri in src/vscode-dts/vscode.d.ts automatically forwards remote URLs but exposes no naming option and warns that returned URLs can become invalid. MainThreadTunnelService.$openTunnel maps label to forwarding name metadata; TunnelModel.doForward stores that name separately and does not supply it to tunnelService.openTunnel, so the source does not support the example's claimed alias guarantee. Tunnel types also appear in vscode.proposed.resolvers.d.ts, making compatibility with resolver consumers part of the API review. The uncertainty is the intended public contract, not a confirmed implementation defect. Keep devcontainer server-argument configuration separate, as tracked by https://github.com/microsoft/vscode-remote-release/issues/11595; https://github.com/microsoft/vscode/issues/115616 addresses port exclusion and is related but not a duplicate.
- **Open decisions:**
  - Should the supported contract cover tunnel creation and lifecycle only, or also guarantee caller-selected endpoint names and persistence across sessions?
  - Which tunnel members and options are ready for a stable public API, and which must remain proposed?
  - If deterministic endpoint names are supported, what are their provider scope, lifetime, and observable name-collision semantics?
