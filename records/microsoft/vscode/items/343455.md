# Issue #343455 — macOS: main process uses 100% CPU during Local History copy; bundled fs.copyFile spins after source truncation

[https://github.com/microsoft/vscode/issues/343455](https://github.com/microsoft/vscode/issues/343455)

## Summary

Keep open as an upstream runtime defect: the reporter's isolated reproduction and libuv's copy loop support a no-progress spin after source truncation. The Local History call path still reaches Node's copyFile; the original editor-side truncation trigger remains unconfirmed.

## Change summary

Ensure a file copy encountering early EOF terminates rather than spinning indefinitely and blocking Local History snapshot completion.

## Best solution

Correct the zero-progress copy loop in libuv and carry the fix through Node/Electron into VS Code's bundled runtime. Confirm the supplied macOS reproduction terminates with that runtime, then separately verify Local History completion without treating the original file writer as established.
