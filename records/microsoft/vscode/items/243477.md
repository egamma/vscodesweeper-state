# Issue #243477 — Variables/Watch 'F2' for 'Set Value' is broken

[https://github.com/microsoft/vscode/issues/243477](https://github.com/microsoft/vscode/issues/243477)

## Summary

The inconsistent F2 behavior remains evident on current main: Watch and Variables register different commands while resolving their target through the globally last-focused list, and Watch's keyboard command excludes child variables that its Set Value context menu supports. The issue should remain open in the debug area while the intended Watch F2 contract is settled and covered by focused keyboard tests.

## Change summary

Make F2 act predictably on the currently focused Variables or Watch entry without editing a stale or different expression.

## Best solution

Define one explicit F2 contract for root watch expressions and child variables, then make each debug view invoke that action only on its own focused item. Add coverage for switching focus between Watch and Variables and for assignable versus non-assignable entries.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugCommands.ts`, `src/vs/workbench/contrib/debug/browser/watchExpressionsView.ts`, `src/vs/workbench/contrib/debug/browser/variablesView.ts`, `src/vs/workbench/contrib/debug/test/browser/debugViewModel.test.ts`
- **Validation:** Exercise F2 after alternating keyboard focus between Watch and Variables, asserting that only the currently focused entry opens an editor; also verify root Watch expressions, assignable Watch children, read-only entries, and the corresponding Set Value context-menu availability.
- **Behavior:**

  > F2 in the debug sidebar must operate only on the entry currently focused in the currently focused Variables or Watch tree; it must never reopen or edit an entry from the other tree. Keyboard behavior and the Set Value context menu must agree for assignable and read-only variable entries. The established action for a root Watch expression must be explicitly preserved or deliberately changed, and covered by acceptance tests.
- **Trace:**

  > In src/vs/workbench/contrib/debug/browser/debugCommands.ts, the Watch F2 rule invokes EDIT_EXPRESSION_COMMAND_ID and accepts only Expression, while the Variables F2 rule invokes debug.setVariable and accepts Variable; both query IListService.lastFocusedList. ListService in src/vs/platform/list/browser/listService.ts retains the last widget that received focus, and DebugViewModel in src/vs/workbench/contrib/debug/common/debugViewModel.ts keeps selectedExpression globally across both trees. watchExpressionsView.ts and variablesView.ts independently rerender when that shared selection changes, which explains how stale cross-view targeting can surface. The context-menu Set Value command already accepts Expression or Variable, so keyboard handling does not cover the same Watch entries. Preserve unrelated DAP setVariable/setExpression selection, mutation, and refresh behavior.
- **Open decisions:**
  - For a root Watch expression, should F2 preserve the established Edit Watch Expression behavior, or should it invoke Set Value when the expression is assignable?
  - For an assignable child variable in Watch, should F2 invoke Set Value to match the context menu, while doing nothing for read-only entries?

## Evidence

- **current source:** src/vs/workbench/contrib/debug/browser/debugCommands.ts registers F2 as EDIT_EXPRESSION_COMMAND_ID for Watch but as debug.setVariable for Variables; both handlers obtain their target from IListService.lastFocusedList rather than a view-local command context.
- **behavior mismatch:** The Watch F2 handler accepts only Expression, while SET_EXPRESSION_COMMAND_ID accepts both Expression and Variable and the DebugWatchContext Set Value menu supports both item kinds. This directly leaves keyboard and context-menu behavior inconsistent for Watch children.
- **shared edit state:** src/vs/workbench/contrib/debug/common/debugViewModel.ts stores one global selectedExpression, and both variablesView.ts and watchExpressionsView.ts rerender from that state. Combined with a globally retained lastFocusedList, this permits an edit request to be rendered in a different debug tree from the user's intended target.
- **historical implementation:** https://github.com/microsoft/vscode/pull/127162 introduced Set Value for Watch expressions and Variables, but the current keyboard targeting behavior remains unchanged and that merged PR predates this report.
- **canonical search:** The cited https://github.com/microsoft/vscode/issues/115063 and https://github.com/microsoft/vscode/issues/124679 concern introducing DAP setExpression support, not F2 selecting a stale or unsupported debug-tree entry; no open older issue found owns this observable symptom.
