# Issue #217810 — Settings editor should have Accessibility TOC entry

[https://github.com/microsoft/vscode/issues/217810](https://github.com/microsoft/vscode/issues/217810)

## Summary

The requested top-level Accessibility entry is still missing: current main nests Accessibility and Accessibility Signals under Features. Two maintainers explicitly support promoting it, and the existing accessibility-settings command does not satisfy that navigation request.

## Change summary

Make Accessibility directly discoverable as a top-level category in the Settings editor table of contents.

## Best solution

Provide a top-level Accessibility category in the Settings editor, retaining keyboard navigation and access to accessibility signals. Confirm whether its contents should be the existing accessibility categories or all accessibility-tagged settings across categories before implementation.

Manually open unfiltered Settings with the TOC visible, navigate to Accessibility by keyboard, and confirm the existing workbench.action.openAccessibilitySettings command still returns accessibility-tagged settings.
- **Behavior:**

  > Opening the Settings editor with its table of contents visible should expose Accessibility without first expanding Features. Selecting it should show the agreed accessibility settings, with accessibility signals still discoverable. Keyboard navigation and the existing Open Accessibility Settings command must continue to work. Acceptance includes root-level TOC placement and preservation of unrelated settings categories.
- **Trace:**

  > The current hierarchy is defined by tocData in src/vs/workbench/contrib/preferences/browser/settingsLayout.ts: Accessibility and Accessibility Signals remain under Features. resolveSettingsTree and _resolveSettingsTree in src/vs/workbench/contrib/preferences/browser/settingsTree.ts resolve settings while preserving that hierarchy. workbench.action.openAccessibilitySettings in preferences.contribution.ts independently uses @tag:accessibility, which reaches settings outside the accessibility.* namespace. getMatchingSettings removes matched settings from the shared set unless multiGroupTocSettings allows multiple placements, so broad tag aggregation has observable consequences for existing categories. Maintainers support top-level placement at https://github.com/microsoft/vscode/issues/217810#issuecomment-2190092258 and https://github.com/microsoft/vscode/issues/217810#issuecomment-2211141681; uncertainty remains about membership, not whether promotion is desired. Keep configuration keys, values, and the existing command contract unchanged; a general Settings navigation redesign is outside this request.
- **Open decisions:**
  - Should the top-level Accessibility category contain the existing Accessibility and Accessibility Signals settings, or aggregate every accessibility-tagged setting across categories while retaining access from their existing categories?

## Evidence

- **Existing capability is partial:** src/vs/workbench/contrib/preferences/browser/preferences.contribution.ts:370–384 registers workbench.action.openAccessibilitySettings and opens Settings with @tag:accessibility. This provides filtered access, but does not introduce the requested top-level TOC entry.
- **Maintainer direction:** https://github.com/microsoft/vscode/issues/217810#issuecomment-2190092258 explicitly supports promoting Accessibility to its own top-level entry; https://github.com/microsoft/vscode/issues/217810#issuecomment-2211141681 agrees. These comments establish an accepted improvement rather than grounds for a decline close.
- **Content scope:** https://github.com/microsoft/vscode/issues/217810#issuecomment-2189343433 explains that accessibility settings span multiple categories and are grouped by a tag. In settingsTree.ts, _resolveSettingsTree preserves the declared hierarchy, while getMatchingSettings consumes matched settings except those in multiGroupTocSettings; aggregating tagged settings can therefore change their placement in other categories.

The verified open https://github.com/microsoft/vscode/issues/272077 proposes grouping and breadcrumbs, was created later, and does not report this same missing top-level Accessibility entry.
