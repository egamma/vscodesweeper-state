# Issue #263108 — Surface the vscode://schemas/color-theme schema to allow for programmatic use

[https://github.com/microsoft/vscode/issues/263108](https://github.com/microsoft/vscode/issues/263108)

## Summary

This accepted Backlog request still identifies a real gap: VS Code exposes the color-theme schema only through its internal runtime filesystem, while external theme tooling has no supported schema artifact or export path. The dynamic extension and active-theme inputs require a product decision about whether the public contract is a stable built-in baseline, an exact runtime export, or both.

## Change summary

Expose a machine-consumable color-theme JSON schema so theme authors can validate themes in external CLI and CI tooling.

## Best solution

Define and publish a supported schema contract for standalone tooling, with explicit semantics for extension-contributed colors and theme-dependent default snippets. A stable built-in schema could support portable CI validation, while an optional runtime export could provide exact validation for an installed extension set.

## Plan brief

- **Likely files:** `src/vs/workbench/services/themes/common/colorThemeSchema.ts`, `src/vs/platform/theme/common/colorUtils.ts`, `src/vs/workbench/services/themes/common/colorExtensionPoint.ts`, `src/vs/workbench/contrib/preferences/common/settingsFilesystemProvider.ts`
- **Validation:** The plan should end with an automated test that obtains the schema through the chosen public surface and uses a standalone JSON-schema validator to accept a representative valid theme and reject invalid property names and transparency-constrained values, with explicit coverage for the chosen extension-color semantics.
- **Behavior:**

  > Theme authors can obtain a supported, machine-consumable schema without opening VS Code and use it in CLI or CI validation. The schema detects invalid theme structure, known color identifiers, invalid values, and transparency constraints to the extent promised by the selected public contract. Its behavior for colors contributed by installed extensions and for theme-dependent defaults is documented and deterministic. Existing in-editor validation through vscode://schemas/color-theme remains compatible.
- **Trace:**

  > src/vs/workbench/services/themes/common/colorThemeSchema.ts defines the top-level schema but delegates workbench colors to the mutable registry schema in src/vs/platform/theme/common/colorUtils.ts. ColorRegistry.registerColor() and deregisterColor() alter its properties, while notifyThemeUpdate() changes completion defaults based on the active theme. src/vs/workbench/services/themes/common/colorExtensionPoint.ts feeds installed extensions' color contributions into that registry. src/vs/workbench/contrib/preferences/common/settingsFilesystemProvider.ts currently exposes the resulting schema only through VS Code's internal vscode:// filesystem. The boundary is to preserve internal schema resolution and extension-contributed in-editor validation; the uncertainty starts at defining what an external, portable schema promises when the installed extension set and active theme are unavailable.
- **Open decisions:**
  - Should the supported external contract be a stable schema for built-in color identifiers, an exact runtime export including installed extensions, or both surfaces?
  - If a portable built-in schema is published, should unknown extension-contributed color identifiers be accepted or rejected during standalone validation?
  - Are active-theme-dependent default snippets part of the exported contract, or should the external schema omit them to remain deterministic?
