# Issue #105774 — Using `moveViews` command with multiple windows open can cause not all views to move

[https://github.com/microsoft/vscode/issues/105774](https://github.com/microsoft/vscode/issues/105774)

## Summary

The multi-window race remains structurally present on current main: `vscode.moveViews` persists each requested view separately while profile-storage changes from other windows can replace the in-memory customization maps. No older canonical issue or fixing commit was found, so this should remain open.

## Change summary

Moving several views through `vscode.moveViews` can leave only some of them in the destination when another VS Code window is open.

## Best solution

Make a multi-view command operation persist its complete set of view-location changes atomically while preserving support for views originating in different containers, and cover cross-window storage synchronization with a regression test.

- **Trace:**

  > The command in src/vs/workbench/browser/parts/views/viewPaneContainer.ts deliberately processes each ID separately because `IViewDescriptorService.moveViewsToContainer` assumes a common source container. Each call reaches `ViewDescriptorService.moveViewsToContainer` in src/vs/workbench/services/views/browser/viewDescriptorService.ts and immediately writes the complete `views.customizations` profile value. External storage events enter `onDidStorageChange` and `onDidViewCustomizationsStorageChange`, which apply the stored layout and replace both customization maps, allowing an intermediate write to race with the remaining moves. The originating PR recorded known multi-window problems at https://github.com/microsoft/vscode/pull/105658#issuecomment-684085626. Keep support for mixed source containers and normal cross-window layout propagation; the boundary is atomicity of one multi-view command, not a redesign of view layout storage.
