# Issue #345417 — Voice Mode: support BYOK cloud providers and custom realtime endpoints beyond OpenAI

[https://github.com/microsoft/vscode/issues/345417](https://github.com/microsoft/vscode/issues/345417)

## Summary

Keep open: current Voice Mode supports direct OpenAI BYOK, but not the requested cloud-provider transports and authentication. The unified model-configuration proposal is related, but does not own the additional realtime integrations.

## Change summary

Support independently configured cloud and custom realtime voice providers while preserving full-duplex interaction and coding-agent permissions.

## Best solution

Define supported realtime capabilities and an incremental provider scope across Copilot BYOK and the workbench voice client. Coordinate model selection with https://github.com/microsoft/vscode/issues/342875 without treating its configuration work as implementation of cloud audio transports.

- **Behavior:**

  > Users can choose a supported realtime voice provider billed to their own account independently of the coding model. Voice remains full duplex, supports transcripts and interruption, and preserves agent confirmations; interrupting speech does not cancel an approved command. Unsupported protocols and authentication failures are explicit and never silently switch billing destinations. Acceptance includes at least one non-OpenAI provider or compatible custom gateway, with local microphone capture and playback in a remote workspace.
- **Trace:**

  > BYOKContrib._provideGptLiveSession in extensions/copilot/src/extension/byok/vscode-node/byokContribution.ts obtains only direct OpenAI credentials, and gptLiveSession.ts uses fixed OpenAI endpoints. The proposed speech API in src/vscode-dts/vscode.proposed.speech.d.ts exchanges SDP rather than describing multiple audio transports. VoiceClientService._connectGptLive in src/vs/workbench/contrib/chat/browser/voiceClient/voiceClientService.ts owns browser microphone capture, WebRTC playback, and the oai-events channel. Source inspection confirms the capability gap, but does not establish compatibility with the requested cloud protocols. Preserve existing permissions, credential isolation, direct OpenAI behavior, and explicit configured-provider failure handling. Coordinate configuration with https://github.com/microsoft/vscode/issues/342875; its registry design does not settle transport adoption.
- **Open decisions:**
  - Should the first supported scope cover only compatible WebRTC/SDP endpoints, or also a native cloud protocol requiring a different audio transport?
  - Should additional realtime providers be exposed through an extension-facing capability contract, built-in integrations, or both?
