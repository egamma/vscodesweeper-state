# Issue #163690 — Slow updates on Debian GNU/Linux

[https://github.com/microsoft/vscode/issues/163690](https://github.com/microsoft/vscode/issues/163690)

## Summary

Keep open while the linked implementation candidate is reviewed. Current Linux package scripts still rebuild the MIME database without `-n`, and the reporter explains why adding that flag alone may not eliminate unnecessary rebuilds.

## Change summary

Avoid unnecessary MIME database rebuilds that make Debian package upgrades take 10–15 minutes under the reported filesystem and I/O conditions.

## Best solution

Review https://github.com/microsoft/vscode/pull/318436 against the reporter's timestamp caveat before treating it as a complete fix. Package upgrades should avoid rebuilding unchanged MIME definitions while still refreshing the database when definitions actually change.

- **Reported trigger and impact:** https://github.com/microsoft/vscode/issues/163690 describes upgrading Code through aptitude on Debian with KDE and btrfs, followed by 10–15 minutes of installation activity dominated by update-mime-database and concurrent slow disk writes.
- **Full reporter follow-up:** https://github.com/microsoft/vscode/issues/163690#issuecomment-1312557776 explains that `-n` checks MIME package timestamps, so a freshly dated but substantively unchanged code-workspace.xml can still trigger a full rebuild. - **Current package scripts:** resources/linux/debian/postinst.template:20–22 and postrm.template:13–15 invoke `update-mime-database /usr/share/mime` without `-n`. resources/linux/rpm/code.spec.template:70–78 likewise invokes the tool without `-n`. This confirms the unoptimized invocation remains, but does not establish current execution time on the reporter's environment.
- **MIME packaging path:** build/gulpfile.vscode.linux.ts:66–69 packages resources/linux/code-workspace.xml as usr/share/mime/packages/<applicationName>-workspace.xml. That inspected path does not perform a comparison against the installed definition, so it does not resolve the reporter's content-versus-timestamp concern.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/318436 is verified OPEN with no merge timestamp and explicitly says `Fixes #163690`.
