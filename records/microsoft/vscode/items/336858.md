# Issue #336858 — Align repository enabledPlugins behavior with Copilot CLI

[https://github.com/microsoft/vscode/issues/336858](https://github.com/microsoft/vscode/issues/336858)

## Summary

Fresh, well-scoped feature request (0 days old) explicitly framed as the deferred follow-up from #300585, and confirmed against current source: `enabledPlugins` today only feeds a trust-gated `recommendedPlugins` set, not automatic install/enable/disable. Too new for any close signal; design decisions remain open before implementation.

## Change summary

Make VS Code auto-install/enable a plugin when `enabledPlugins` is `true` (and disable when `false`) in a trusted workspace's `.github/copilot/settings.json`, matching Copilot CLI's repo-scoped activation semantics, instead of only recommending manual installation.

## Best solution

Extend the workspace-trust-gated plugin pipeline (`pluginMarketplaceService.ts` / `workspacePluginSettingsService.ts`) so `enabledPlugins: true/false` drives actual per-repository install/activate/deactivate rather than just populating `recommendedPlugins`, while keeping global user plugin state untouched — this needs a maintainer decision on how repo-scoped enablement state is represented and persisted before an agent implements it.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/plugins/pluginMarketplaceService.ts`, `src/vs/workbench/contrib/chat/common/plugins/workspacePluginSettingsService.ts`, `src/vs/workbench/contrib/chat/common/plugins/agentPluginEnablement.ts`
- **Validation:** A test in pluginMarketplaceService.test.ts (or a new enablement test) asserting that a trusted-workspace `enabledPlugins: true` entry results in the plugin actually being installed/activated (not merely recommended), and that `false` deactivates it without writing to global user settings.
- **Behavior:**

  > In a trusted workspace declaring a marketplace/plugin in `.github/copilot/settings.json` (or `.claude/settings.json`), `enabledPlugins: true` should install and activate the plugin scoped to that repository; `false` should deactivate it for the repository; an absent key preserves the existing user/global state; repo-scoped enablement must never be written into global user settings; and repository plugin settings must be ignored entirely until the workspace is trusted.
- **Trace:**

  > Today, `WorkspacePluginSettingsService._readSettings` (src/vs/workbench/contrib/chat/common/plugins/workspacePluginSettingsService.ts) parses `enabledPlugins` into a `Map<string, boolean>` including both true and false values, but `PluginMarketplaceService` (src/vs/workbench/contrib/chat/common/plugins/pluginMarketplaceService.ts, ~L386-399) only reads the `true` entries into a trust-gated `recommendedPlugins` observable used for recommendation UI — there is no install/activate/deactivate action wired to these values, and `false` values are currently dropped entirely. The workspace-trust gate (`_workspaceTrustService.isWorkspaceTrusted()`) is already correctly in place and must be preserved. What's unresolved: how a 'repository-scoped' enabled/installed state is modeled and stored distinctly from user/global plugin state (likely via `agentPluginEnablement.ts` / `CollisionEnablementModel`), and how install actually gets triggered (silently vs. with any UI) — that boundary is the open decision. Related: https://github.com/microsoft/vscode/issues/300585 (deferred follow-up), https://github.com/microsoft/vscode/issues/327404 (current recommendation-flow bug), https://github.com/microsoft/vscode/issues/332083 (broader customization migration tracking, unverified as directly overlapping).
- **Open decisions:**
  - How is repo-scoped plugin enablement state represented/persisted separately from global user plugin state (e.g. in agentPluginEnablement.ts's enablement model)?
  - Does `enabledPlugins: true` trigger a silent auto-install, or does it still require some form of user confirmation given plugins can execute code?
  - How does `enabledPlugins: false` deactivation interact with a plugin the user has separately enabled globally — is repo-scoped deactivation an override or a hide?

## Evidence

- **current behavior confirmed:** src/vs/workbench/contrib/chat/common/plugins/pluginMarketplaceService.ts (around line 386-399) computes `recommendedPlugins` from `_workspacePluginSettingsService.enabledPlugins` only when `value` is truthy, gated by `workspaceTrustService.isWorkspaceTrusted()` — there is no auto-install/activate or `false`-driven deactivation path, matching the issue's description of 'recommendation requiring manual installation'.
- **parsing supports both true/false today:** workspacePluginSettingsService.ts `parseEnabledPlugins()` already stores both `true` and `false` values per key, but only the `true` branch is consumed downstream — the `false` (deactivate) semantics the issue asks for aren't wired up anywhere.
- **referenced predecessor work:** Issue body cites #300585 (original workspace-plugin implementation, which explicitly deferred enablement/disablement unification) and #327404 (a bug in the current recommendation flow) as related context.
