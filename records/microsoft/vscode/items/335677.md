# Issue #335677 — Work from Repository: Early pasting into repo picker does not show Clone from URL

[https://github.com/microsoft/vscode/issues/335677](https://github.com/microsoft/vscode/issues/335677)

## Summary

Team-authored bug report from active testing of the new unified repo picker; traced a plausible race condition in the repository quick pick's initial-load vs. search-debounce flow that would exactly produce the reported symptom, so this stays open for a fix rather than any close.

## Change summary

In the 'Work in Repository' picker, pasting a repo URL immediately (or even after the initial load finishes) doesn't surface the 'Clone from URL' quick pick entry.

## Best solution

Fix the race in `openRepositoryCommand` (extensions/copilot/src/extension/chatSessions/vscode-node/copilotCloudSessionsProvider.ts): the initial `fetchAllRepositoriesFromGitHub()` await unconditionally overwrites `quickPick.items` using an empty search value once it resolves, which can stomp on items already computed for a pasted URL (or a slow initial fetch stomping a completed search); guard the write to only apply when the current `quickPick.value` still matches what it was computed for, or use a request-generation token to discard stale results.

- **Fix prompt:**

  > In extensions/copilot/src/extension/chatSessions/vscode-node/copilotCloudSessionsProvider.ts, the `openRepositoryCommand` function (around line 631) awaits `fetchAllRepositoriesFromGitHub()` for the initial repo list, then unconditionally runs `quickPick.items = getRepositoryQuickPickItems(repos, '', options?.allowRepositoryUrl === true)`. Separately, `quickPick.onDidChangeValue` (around line 665) debounces 300ms and then calls `fetchAllRepositoriesFromGitHub(value)` before setting `quickPick.items` from the search value. Because both paths write to `quickPick.items` asynchronously with no ordering guarantee, if the initial fetch is still in flight when the user pastes a repo URL, the initial fetch's resolution can land after the search response and overwrite the items computed for the pasted URL with items computed for an empty string — dropping the 'Clone from URL' entry that `getRepositoryQuickPickItems` (line ~236) only adds when the current `value` matches a URL/SSH regex. Fix by tracking a monotonically increasing request/generation counter (or capturing `quickPick.value` at fetch start and comparing to the live value before writing `quickPick.items`), applied to BOTH the initial load and the debounced search fetch, so a stale async response can never overwrite a result computed for a newer value. Do not change `getRepositoryQuickPickItems`'s URL-detection regex or its output shape — only guard the two `quickPick.items =` assignment sites in `openRepositoryCommand`. Add/extend a test in extensions/copilot/src/extension/chatSessions/vscode-node/test/copilotCloudSessionsProvider.spec.ts that simulates the initial fetch resolving after a value change to a URL and asserts the Clone from URL item survives. - **race window:** Same file, ~line 631-680: `openRepositoryCommand` awaits `fetchAllRepositoriesFromGitHub()` for the initial repo list and then does `quickPick.items = getRepositoryQuickPickItems(repos, '', …)` unconditionally. If the user pastes a URL while that initial fetch is still in flight, its resolution overwrites the items computed from the paste with items computed for an empty string, dropping the Clone from URL entry — matching 'pasting right after the picker opened' and, if the initial fetch is slow enough, even after the busy indicator later appears to settle.
- **search debounce also unguarded:** The `onDidChangeValue` handler (same file, ~line 665-680) clears the previous `setTimeout` on new keystrokes but has no generation token on the underlying async `fetchAllRepositoriesFromGitHub(value)` call itself, so an earlier in-flight search can still resolve after a later one and overwrite its result.
