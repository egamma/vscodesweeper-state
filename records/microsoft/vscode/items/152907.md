# Issue #152907 — GitHub - Unable to push to existing fork with codespaces

[https://github.com/microsoft/vscode/issues/152907](https://github.com/microsoft/vscode/issues/152907)

## Summary

Keep open: multiple reporters confirm that pushing from an upstream Codespace to an existing personal fork fails, including through the integrated workflow. The checkout exposes the relevant integration boundary but does not establish a fix or a verified duplicate.

## Change summary

Pushing changes from an upstream Codespace to an existing fork fails with permission errors, while the suggested fork-creation flow rejects the already-existing fork.

## Best solution

Make the Codespaces GitHub push workflow reuse an existing fork and obtain the authorization needed to push to it without requiring users to upload personal SSH keys. Diagnose both the built-in GitHub permission-error handler and its delegated Codespaces fork operation, since changing the remote alone did not resolve the reported failure.

## Evidence

- **Reported trigger and failure:** https://github.com/microsoft/vscode/issues/152907 describes creating a Codespace on gregjones/httpcache, committing changes, and attempting to push to the existing tjamet/httpcache fork. Fork creation reports that the fork already exists, and an explicit HTTPS push to that fork returns HTTP 403.
- **Independent confirmations:** The supplied discussion includes the same failure on Azure/az-hop and its personal fork on 2022-08-19, another confirmation on 2024-10-30, and a private-organization repository case on 2025-04-24. These support reproduced status from the discussion; no live current-build reproduction was performed.
- **Current integration boundary:** extensions/github/src/pushErrorHandler.ts: GithubPushErrorHandler.handlePermissionDeniedError offers Create Fork and, when env.remoteName is codespaces, invokes github.codespaces.forkRepository. Only after that command succeeds does it rename the remote, add the returned fork as origin, and push. The implementation of the delegated command was not found in the inspected built-in GitHub, GitHub authentication, or Git sources, so the existing-fork failure cannot be conclusively diagnosed from this handler alone.
- **Adding a remote is not authorization:** extensions/github/src/remoteSourceProvider.ts lists and resolves GitHub repositories, including forks, and returns clone URLs. That capability does not itself authorize Git pushes to the selected repository; the reporter explicitly tried adding the fork remote and still encountered a permission failure.
- **Canonical search:** Read-only GitHub searches for codespaces fork and codespaces permission push did not identify a verified older issue owning this same symptom. The supplied candidate https://github.com/microsoft/vscode/issues/40239 concerns extension enablement configuration, not pushing to an existing fork, and is not an established canonical.
