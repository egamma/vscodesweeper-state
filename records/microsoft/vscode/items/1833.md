# Issue #1833 — Add some API to support GUI customization

[https://github.com/microsoft/vscode/issues/1833](https://github.com/microsoft/vscode/issues/1833)

## Summary

Existing APIs cover much of this request, including contributed panels, custom editors, workbench colors, and debug-toolbar actions. The broader request for extensible, VS Code-rendered UI remains only partially covered; retain this well-supported Backlog item while an API owner defines the remaining scope.

## Change summary

Expose theme-consistent UI contribution APIs so extensions supply content and behavior while VS Code supplies the widgets and presentation.

## Best solution

Document which examples are already supported, then define a bounded remaining API requirement for native, theme-consistent extension UI beyond tree views and menus. Preserve the extension-host boundary and uniform workbench presentation rather than exposing arbitrary workbench DOM or CSS modification.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/browser/viewsExtensionPoint.ts`, `src/vs/workbench/services/actions/common/menusExtensionPoint.ts`
- **Validation:** After selecting a concrete native UI scenario, exercise it with a sample extension: contribute the agreed content and actions, switch light/dark/high-contrast themes, operate it by keyboard, and disable the extension. Verify host-consistent presentation, working actions, and removal of the extension-owned contributions without changes to unrelated built-in UI.
- **Behavior:**

  > Extensions should be able to supply content and actions for an agreed set of native UI elements while VS Code controls their rendering and themes control their presentation. Existing panel, tree-view, custom-editor, testing, and toolbar contribution capabilities count as delivered portions of the request. Planning must identify a concrete remaining scenario that these APIs cannot adequately express. Acceptance should demonstrate that scenario with consistent theming, keyboard operation, and clean removal of extension-owned contributions.
- **Trace:**

  > src/vs/workbench/api/browser/viewsExtensionPoint.ts defines contribution containers and limits contributed view types to tree or webview. src/vscode-dts/vscode.d.ts exposes createTreeView, registerWebviewViewProvider, createWebviewPanel, registerCustomEditorProvider, and createTestController; these satisfy several historical examples but do not establish a general host-rendered widget composition contract. src/vs/workbench/services/actions/common/menusExtensionPoint.ts already exposes debug/toolBar. Webview theme integration in src/vs/workbench/contrib/webview/browser/pre/index.html supplies styling context while leaving document content extension-authored. The uncertainty is which additional native controls and placements the project intends to expose, not whether extensions can contribute any UI today. Preserve existing APIs, extension-host isolation, and built-in UI ownership; arbitrary workbench DOM/CSS access is not required by the issue's final proposal. https://github.com/microsoft/vscode/issues/41309 and https://github.com/microsoft/vscode/issues/334285 are related context, not duplicate canonicals.
- **Open decisions:**
  - Which additional native UI controls and workbench placements should extensions be able to contribute beyond the existing tree, menu, panel, and webview surfaces?
  - Should the remaining contract only create extension-owned UI, or also allow extensions to hide or replace existing built-in elements?

## Evidence

- **Accepted scope and demand:** https://github.com/microsoft/vscode/issues/1833 has the feature-request and api labels, a Backlog milestone, and 470 community upvotes. The body explicitly distinguishes extension-provided content from VS Code-provided UI templates and theme-controlled styling.
- **Existing panel and view capabilities:** src/vs/workbench/api/browser/viewsExtensionPoint.ts registers viewsContainers for activitybar, panel, and secondarySidebar; contributed views support tree or webview types and visibility conditions. These cover the example of adding an extension-owned bottom-panel view, but do not provide a general native widget-composition API.
- **Existing stable extension APIs:** src/vscode-dts/vscode.d.ts declares window.createTreeView, window.registerWebviewViewProvider, window.createWebviewPanel, window.registerCustomEditorProvider, and tests.createTestController. Custom editors and testing now have dedicated extension surfaces, addressing examples raised in the discussion without establishing unrestricted native UI composition.
- **Theming and toolbar examples:** src/vs/workbench/services/themes/common/themeConfiguration.ts registers workbench.colorCustomizations; src/vs/workbench/services/themes/common/themeExtensionPoints.ts registers productIconThemes. src/vs/workbench/services/actions/common/menusExtensionPoint.ts exposes debug/toolBar, covering the later question about contributing a debug-toolbar button.
- **Remaining presentation boundary:** Webview-based APIs allow extension-authored content rather than having VS Code render a general set of native controls from extension data. src/vs/workbench/contrib/webview/browser/pre/index.html supplies default styles and theme variables to webview documents; this is useful theme integration, not the host-owned widget model requested in the issue's concluding paragraph.
- **Discussion and related issues:** The author already marked side-panel customization and custom tabs complete. https://github.com/microsoft/vscode/issues/3112 is closed and covers workbench color theming, only part of this report. The Shortcut Menu Bar workaround mentioned in the thread addresses command buttons, not the full UI contribution contract.
- **Canonical search:** Read-only searches for GUI customization APIs and native UI APIs did not establish an older open canonical owning the full request. https://github.com/microsoft/vscode/issues/41309 is open but concerns an optional configurable toolbar; https://github.com/microsoft/vscode/issues/334285 is open but concerns interface evolution.
