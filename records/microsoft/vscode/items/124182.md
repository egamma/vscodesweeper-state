# Issue #124182 — Workspace Trust - Extension Development Host 

[https://github.com/microsoft/vscode/issues/124182](https://github.com/microsoft/vscode/issues/124182)

## Summary

The central defect remains visible on current main: extensions under development are unconditionally enabled, so an Extension Development Host cannot accurately exercise the manifest's untrusted-workspace restriction. This team-authored Backlog bug must remain open, and no older open issue with the same observable symptom was found.

## Change summary

Extension Development Host does not consistently enforce or reevaluate an extension's `untrustedWorkspaces` capability while testing trust-state changes.

## Best solution

Provide a supported Extension Development Host mode that enforces the developed extension's `untrustedWorkspaces` declaration and consistently reevaluates extension activation across trust transitions, while preserving any deliberate default developer override.

## Evidence

- **current source:** In src/vs/workbench/services/extensions/common/abstractExtensionService.ts, `filterEnabledExtensions` unconditionally adds every `extension.isUnderDevelopment` extension with the explicit comment `Never disable extensions under development`, bypassing the workspace-trust enablement calculation.
- **initial host startup:** src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts initializes the local extension host through `checkEnabledAndProposedAPI(..., true)` with the comment that extensions disabled by workspace trust are intentionally loaded; the browser extension host has the same trust-ignoring initial-start path.
- **trust transition path:** src/vs/workbench/contrib/extensions/browser/extensionEnablementWorkspaceTrustTransitionParticipant.ts reevaluates extension enablement when trust changes, but the developed extension still passes the unconditional `isUnderDevelopment` branch when extension descriptions are filtered.
