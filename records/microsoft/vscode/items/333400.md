[https://github.com/microsoft/vscode/issues/333400](https://github.com/microsoft/vscode/issues/333400)

## Summary

The API remains proposed on current main, so implementation has not fulfilled this request for finalization. Keep it open for API-owner review; two extension authors report successful use of complementary diff scenarios.

## Change summary

Consider promoting customEditorDiffs from proposed API to the stable extension API.

- **Behavior:**

  > Extension authors want supported custom diff rendering without opting into a proposed API. An approved stable contract should expose the agreed callbacks through stable typings and activate them without proposal enablement. Acceptance should cover those supported variants and preserve ordinary custom-editor behavior.
- **Trace:**

  > The complete proposed surface is in src/vscode-dts/vscode.proposed.customEditorDiffs.d.ts; its current callback names contain InlineDiff and SideBySideDiff. ExtHostCustomEditors.registerCustomEditorProvider in src/vs/workbench/api/common/extHostCustomEditors.ts gates both capabilities on customEditorDiffs proposal enablement for text and custom providers. The proposal remains registered in src/vs/platform/extensions/common/extensionsApiProposals.ts, while the built-in Markdown provider demonstrates inline adoption. https://github.com/microsoft/vscode/issues/298924 implemented the proposal, and https://github.com/microsoft/vscode/issues/315174 tracks a consumer rather than finalization. https://github.com/microsoft/vscode/issues/315925 supplies a restoration scenario to assess; its current runtime behavior was not verified. The uncertainty is whether the API owners approve the current public contract for stabilization, not whether diff support exists. Preserve existing diff presentation and ordinary editor behavior; unrelated navigation APIs are outside this request.
