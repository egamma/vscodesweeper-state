# Issue #326128 — Agents window: consolidate redundant progress spinners

[https://github.com/microsoft/vscode/issues/326128](https://github.com/microsoft/vscode/issues/326128)

## Summary

Keep open: current source still renders progress on active chat tabs and animates inline subagent status independently, so the requested consolidation is incomplete. The team has agreed on the direction, and the overlapping newer polish issue cannot replace this older, re-reviewed report.

## Change summary

## Plan brief

- **Likely files:** `src/vs/sessions/browser/parts/chatCompositeBar.ts`, `src/vs/sessions/browser/parts/media/chatCompositeBar.css`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatSubagentOpenChat.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatSubagentContentPart.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatProgressContentPart.ts`
- **Validation:** In an Agents-window session, compare a single active chat, multiple chats with inactive work, a running inline subagent, and a subagent opened in a chat tab. Verify no redundant active-chat spinner, a lightweight inline running indication, and discoverable permission requests in both collapsed and expanded subagent states; repeat with reduced motion and screen-reader navigation.
- **Behavior:**

  > Concurrent chat and subagent activity should communicate distinct work without several competing spinners for the same turn. Per-turn progress belongs in the response body, while session-level artifacts may retain their own state indication. Active or sole-chat progress must not add a redundant per-chat spinner, and running inline subagents should use a lightweight indication. Permission requests must remain discoverable and actionable after consolidation, including when a subagent is collapsed or opened in another tab.
- **Trace:**

  > ChatCompositeBar in src/vs/sessions/browser/parts/chatCompositeBar.ts selects its in-progress indicator without considering the active-chat flag, although it already uses that flag for unread suppression. ChatProgressContentPart supports shimmer, but the subagent status widget in chatSubagentOpenChat.ts independently creates running and waiting pixel spinners; ChatSubagentContentPart also owns expanded working-progress presentation. These independent surfaces show why replacing one glyph does not satisfy the complete request. The trace has not established every current above-input indicator or its lifecycle, so the session should begin with the requested trigger inventory. Preserve provider-neutral session state, permission actions, accessibility, and inactive-chat discoverability. Coordinate with https://github.com/microsoft/vscode/issues/331659; the remaining product uncertainty is how attention indicators are distributed when a permission request is already visible inline.
- **Open decisions:**
  - When a subagent permission request is visible in the active response body, should its active chat tab also retain an attention marker, or should tab attention be reserved for requests outside the visible active chat?
