# Issue #326128 — Agents window: consolidate redundant progress spinners

[https://github.com/microsoft/vscode/issues/326128](https://github.com/microsoft/vscode/issues/326128)

## Summary

Keep open as accepted Agents window polish: current main still presents overlapping progress affordances, while the maintainer discussion establishes a clear direction toward turn-local progress and session-level persistent artifacts. The issue is team-authored and no referenced fixing commit or verified duplicate supports a factual close.

## Change summary

Consolidate Agents window progress and permission indicators so each active operation has one meaningful, context-appropriate representation.

## Best solution

Keep turn-level tool, thinking, and subagent progress inside the response body; reserve input-area pills for artifacts that outlive a turn; suppress progress decoration for the active chat; and define one consistent permission-required indication that remains accessible without duplicating visual alerts.

- **Behavior:**

  > During an active turn, tool-call, thinking, and subagent progress appears within that turn's response body rather than being repeated above the input or on the active chat tab. Inactive chats may retain a compact progress indication when it helps users locate background work, while session-level pills remain only for artifacts that outlive a turn. A permission request has one visually leading alert treatment, without duplicate dots and banner-like pills, and its state remains available to keyboard and screen-reader users. Reduced-motion mode must communicate the same states without relying on shimmer or spinning animation.
- **Trace:**

  > The input-area duplication originates in SessionChatInputToolbar, which contributes SessionBackgroundActivitiesControl as the Subagents source for ChatInputPills; that control derives entries from tool-origin child chats. Inline subagent activity is independently rendered by ChatSubagentContentPart and OpenSubagentChatActionViewItem in the workbench chat content pipeline, including working and confirmation states. ChatCompositeBar._createTab computes tab indicator mode and currently chooses `in-progress` before considering whether the chat is active; its CSS renders a compact spinning codicon. Session-list title shimmer already demonstrates a reduced-motion-aware progress treatment in sessionsList.css. Preserve artifact/reference/browser pills and inactive-chat discoverability; do not remove semantic status from ARIA labels or screen-reader announcements. The unresolved boundary is the single canonical presentation for permission-required state across an active response and inactive chat navigation.
- **Open decisions:**
  - When a subagent needs permission, which single visual surface leads for the active chat, and should an inactive chat retain only a tab/list alert marker until opened?
