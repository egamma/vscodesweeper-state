# Issue #326695 — Surface the approval outcome somehow in chat

[https://github.com/microsoft/vscode/issues/326695](https://github.com/microsoft/vscode/issues/326695)

## Summary

A real UX gap remains on current main: assisted-permission denials can expose their risk assessment while awaiting confirmation, but successful automatic approvals leave no durable, discoverable outcome in the completed chat transcript. This team-authored testing follow-up should remain open while the low-noise presentation is designed.

## Change summary

Make assisted-permission approval outcomes discoverable in chat so users can understand why a tool call ran automatically or required confirmation.

## Best solution

Preserve the assisted-review result with each relevant tool invocation and expose it through a quiet post-execution affordance in the completed tool row. The design should cover automatic approvals and escalations without adding a separate transcript message for every tool call.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/platform/agentHost/common/state/protocol/channels-chat/state.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/stateToProgressAdapter.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/abstractToolConfirmationSubPart.ts`, `src/vs/platform/agentHost/test/node/copilotAgentSession.test.ts`, `src/vs/workbench/contrib/chat/test/browser/agentSessions/stateToProgressAdapter.test.ts`
- **Validation:** Add focused Copilot agent-session and chat-adapter tests showing that both an automatically approved recommendation and an escalated recommendation remain associated with the completed tool invocation, then verify the chosen completed-row affordance without introducing an additional transcript response part.
- **Behavior:**

  > When assisted permissions evaluates a tool call, the user can later inspect the outcome from that tool's chat row, including whether it was automatically approved or escalated for confirmation. The indication remains available after the tool completes and provides enough context to diagnose an unexpected decision. Routine approvals must not add a separate noisy transcript message for every tool call, and sessions outside assisted-permissions mode remain unchanged.
- **Trace:**

  > CopilotAgentSession._handlePermissionRequest in src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts consumes the assisted recommendation. A rejected recommendation reaches `pending_confirmation` with `riskAssessment`, but an approved ordinary read/write/shell request returns `approve-once` before publishing equivalent durable state. stateToProgressAdapter.ts converts pending assessments to `approvalReason`; abstractToolConfirmationSubPart.ts intentionally renders that badge only while the invocation is waiting for confirmation, so the explanation is absent after completion. Keep the change scoped to assisted-review provenance and chat tool presentation; do not alter the approval decision, permission policy, or execution behavior. https://github.com/microsoft/vscode/issues/326688 concerns evaluator customization and is related but does not own this presentation work.
- **Open decisions:**
  - Which completed-tool affordance should expose the outcome—a persistent badge, an icon with hover details, or details available only when the tool row is expanded?
  - Should completed rows retain the model's full explanation and safety result for both approvals and escalations, or show a compact outcome by default with the explanation only on demand?

## Evidence

- **approved path:** In src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts, CopilotAgentSession._handlePermissionRequest returns `approve-once` immediately when the assisted recommendation is `approve`; ordinary read, write, and shell requests do not emit a durable risk-assessment result into the chat state.
- **rejected path:** The same method attaches `riskAssessment` when a recommendation falls through to `pending_confirmation`, so rejected or escalated calls can explain why user approval is required.
- **presentation boundary:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/stateToProgressAdapter.ts maps pending `riskAssessment` data to `approvalReason`, while abstractToolConfirmationSubPart.ts explicitly limits the resulting risk badge to `WaitingForConfirmation`; it is not retained as a completed-tool outcome.
- **related issue:** https://github.com/microsoft/vscode/issues/326688 is older but requests customization of the assisted-permissions evaluator prompt, not visibility of each decision's outcome, so it does not meet the stronger same-symptom duplicate bar.
- **testing context:** The report was filed by a repository member while testing https://github.com/microsoft/vscode/issues/326555, whose test plan specifically exercised assisted permissions and the explanation shown when automatic approval is rejected.
