# Issue #330893 — agentHost: a minted top-level MCP customization is never retired, so one server stays published twice

[https://github.com/microsoft/vscode/issues/330893](https://github.com/microsoft/vscode/issues/330893)

## Summary

Verified against current main: the two latches described (reused `previous?.topLevelId` in `_applyOne`, and `_findPublishedMcpCustomization` short-circuiting on a top-level match before reaching `findMcpChildId`) are both still present exactly as described, so a minted top-level MCP customization is indeed never retired once the declaring child resolves. This is a real, well-diagnosed bug still open on main; #330890 (workbench display de-dup, still open) does not touch this session-state root cause.

## Change summary

Once `McpCustomizationController` mints a top-level customization for an MCP server before its plugin-declared child is resolvable, it never retires that top-level entry even after the child becomes resolvable, leaving one server published twice in session state for the rest of the session.

## Best solution

In src/vs/platform/agentHost/node/shared/mcpCustomizationController.ts, once `_findPublishedMcpCustomization`/`_applyOne` finds that a child id is now resolvable for a server that previously got a minted top-level id, emit `SessionCustomizationRemoved` for the stale `topLevelId` (reusing the existing `_remove` removal path) and switch the live entry back to the child, and change `_findPublishedMcpCustomization` to prefer/also check `findMcpChildId` so it doesn't perpetually short-circuit on the earlier top-level match. Add the controller-level regression test the reporter suggests (`applyOne` before child publish, then publish child, assert exactly one `McpServerCustomization`).
