# Issue #330893 — agentHost: a minted top-level MCP customization is never retired, so one server stays published twice

[https://github.com/microsoft/vscode/issues/330893](https://github.com/microsoft/vscode/issues/330893)

## Summary

Traced conclusively against current main: `mcpCustomizationController.ts` still has both latches exactly as described — `_applyOne` (line ~292) reuses `previous?.topLevelId` forever, and `_findPublishedMcpCustomization` (lines 390-395) returns on a top-level match before ever reaching `findMcpChildId`, so a minted top-level customization can never be retired once the declaring child becomes resolvable. PR #330890 (merged) only de-duplicates the display layer; the underlying session state duplication this issue targets is untouched.

## Change summary

A server whose MCP customization is minted top-level before its declaring child is published never gets demoted/retired once the child resolves, leaving two live customizations for one server for the rest of the session.

## Best solution

In `_applyOne`, once `_findPublishedMcpCustomization` finds a resolvable child for a server that currently has a minted `topLevelId`, emit `SessionCustomizationRemoved` for that `topLevelId` (reusing the same mechanism `_remove` already uses) and switch the live entry to the child id; also fix `_findPublishedMcpCustomization` so a top-level match doesn't short-circuit before checking whether a child now exists for the same name. Add the controller-level regression test the reporter suggests: `applyOne` before the child is published, then publish the child, then assert exactly one `McpServerCustomization` exists for that name.
