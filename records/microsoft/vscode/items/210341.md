# Issue #210341 — Folders cointaining only `.gitignore`d files are sometimes not hidden, disappear only on click

[https://github.com/microsoft/vscode/issues/210341](https://github.com/microsoft/vscode/issues/210341)

## Summary

The bug remains source-reproducible on main: nested `.gitignore` files are processed only after their containing folders are resolved, so ignored-only folders can remain visible until clicked. The older related issue concerns Explorer Find rather than this observable symptom and is closed, so it is not a valid duplicate target.

## Change summary

With `explorer.excludeGitIgnore` enabled, folders containing only ignored files can appear initially and disappear only after expansion.

## Best solution

Make initial Explorer visibility account for nested `.gitignore` files before a folder is expanded, while avoiding an unconditional full-workspace traversal that would regress Explorer performance. Add coverage for multiple unresolved sibling folders whose local `.gitignore` contains `*`.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Add an Explorer test with multiple initially unresolved sibling directories, each containing a `.gitignore` with `*`, and assert that `explorer.excludeGitIgnore` hides them before expansion; run `scripts/test.sh --grep "Files - ExplorerView"`.
- **Behavior:**

  > When `explorer.excludeGitIgnore` is enabled, a directory whose local `.gitignore` excludes all of its contents must not appear temporarily and then disappear when clicked. The result must be correct on initial Explorer rendering with multiple sibling directories, while ordinary folders and explicitly included content remain visible. Acceptance requires a regression test covering unresolved folders and verification that expanding folders is no longer required to establish their visibility.
- **Trace:**

  > ExplorerDataSource in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts resolves children through `ExplorerItem.fetchChildren`; collapsed directories therefore do not expose their nested `.gitignore` files. `FilesFilter.filter` calls `processIgnoreFile` only after a `.gitignore` item is visited, and `isIgnored` consults only the resulting `ignoreTreesPerRoot`, so the parent remains visible until expansion triggers discovery and `_onDidChange`. The maintainer confirmed this diagnosis at https://github.com/microsoft/vscode/issues/210341#issuecomment-2075323778. The boundary is Explorer ignore discovery and visibility: preserve `.gitignore` semantics, visible-editor exceptions, remote/file-system-provider behavior, and responsiveness for large workspaces. https://github.com/microsoft/vscode/issues/66971 addressed collapsed-folder discovery for Explorer Find, but its search-based path does not establish ignore rules for normal Explorer rendering.

## Evidence

- **source trace:** In src/vs/workbench/contrib/files/browser/views/explorerViewer.ts, `FilesFilter.filter` discovers and asynchronously processes a `.gitignore` only when that file appears among visited Explorer items; `isIgnored` cannot apply rules from an undiscovered ignore file.
- **lazy resolution:** In src/vs/workbench/contrib/files/browser/views/explorerViewer.ts, `ExplorerDataSource.getChildren` calls `ExplorerItem.fetchChildren` when a folder is resolved. Until that occurs, the nested `.gitignore` is unavailable to `FilesFilter`, matching the reported disappear-on-click behavior.
- **maintainer diagnosis:** https://github.com/microsoft/vscode/issues/210341#issuecomment-2075323778 identifies lazy folder resolution as the cause: clicking exposes the ignored children and then allows the folder to be hidden.
- **related issue:** https://github.com/microsoft/vscode/issues/66971 is older but closed and concerns resolving collapsed folders for Explorer Find/filter-on-type, not folders remaining visible until their nested `.gitignore` is discovered.
