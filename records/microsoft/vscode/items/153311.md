# Issue #153311 — Git - Lots of vscode socket files left in /tmp when using SSH

[https://github.com/microsoft/vscode/issues/153311](https://github.com/microsoft/vscode/issues/153311)

## Summary

Still a real gap on current main: every producer of these sockets only unlinks in its `dispose()` path, and nothing sweeps sockets orphaned by an ungraceful exit (dropped SSH connection, killed remote server), which is exactly why the 2022 git-extension fix did not stop the pile-up and the issue was reopened.

## Change summary

VS Code Remote-SSH leaves `vscode-git-*.sock` and `vscode-ipc-*.sock` files accumulating in `/tmp` on the remote host, and they are created world-readable on a multi-user machine.

## Best solution

Make socket cleanup survive abnormal termination — sweep orphaned `vscode-ipc-*`/`vscode-git-*` sockets belonging to the current user at server/extension-host startup (probing liveness before unlinking) — and create the sockets with restrictive permissions (0600) rather than relying on the user's umask.

## Plan brief

- **Likely files:** `src/vs/base/parts/ipc/node/ipc.net.ts`, `src/vs/workbench/api/node/extHostCLIServer.ts`, `extensions/git/src/ipc/ipcServer.ts`, `src/vs/server/node/remoteTerminalChannel.ts`, `src/vs/server/node/serverServices.ts`
- **Validation:** A node-layer test that creates several `vscode-ipc-*`/`vscode-git-*` socket paths in a temp dir, simulates an orphan (no listener bound), runs the new sweep, and asserts orphans are removed while a live, bound socket survives; plus an assertion on the created socket's file mode.
- **Behavior:**

  > After a remote VS Code session ends abnormally (SSH connection dropped, remote server or extension host killed), the `vscode-git-*.sock` and `vscode-ipc-*.sock` files it created must not accumulate in the remote host's /tmp: a later VS Code start on that host should leave no orphaned sockets behind. Sockets belonging to a still-running VS Code instance must never be removed — concurrent sessions by the same user on the same host must keep working (git credential helper, `code` CLI from the integrated terminal, remote terminal IPC). Sockets should also not be readable by other users on a shared host. Acceptance: orphaned sockets are gone after a restart, a live concurrent session's socket is untouched and its `code`/git flows still work, and newly created sockets are not world-accessible.
- **Trace:**

  > Three producers create these files and all of them clean up only in a graceful `dispose()`: `IPCServer.dispose()` in extensions/git/src/ipc/ipcServer.ts (the 2022 fix that did not close this issue), `CLIServerBase.dispose()` in src/vs/workbench/api/node/extHostCLIServer.ts, and the disposable around `createRandomIPCHandle()` in src/vs/server/node/serverServices.ts (~line 366); src/vs/server/node/remoteTerminalChannel.ts allocates another via `createRandomIPCHandle()`. `createRandomIPCHandle()` in src/vs/base/parts/ipc/node/ipc.net.ts picks `XDG_RUNTIME_DIR` when set (non-darwin) and falls back to `os.tmpdir()`, so on hosts without that variable every socket lands in shared /tmp. No code path on current main scans for and removes sockets orphaned by a killed process — that is the root cause of the reopen. No producer sets a socket mode (no `chmod` call in any of these files), which is why the entries are world-readable under a default umask. Boundary: do not change the socket naming/location scheme used by `VSCODE_GIT_IPC_HANDLE` and `VSCODE_IPC_HOOK_CLI` consumers (extensions/git/src/askpass*, server.cli.ts), and do not break concurrent same-user sessions. Related history: https://github.com/microsoft/vscode/issues/7758 (same symptom, previously fixed and regressed) and the confirming report https://github.com/microsoft/vscode/issues/153311#issuecomment-1204283745. The `pyright-*` directories in the report are owned by Pylance/Pyright, not this repo.
- **Open decisions:**
  - Should VS Code sweep orphaned sockets left by *other* (dead) instances of the same user at startup, or only guarantee its own cleanup on exit — i.e. is deleting files it did not create in this session acceptable?
  - How is liveness determined before unlinking a candidate socket (connect-probe vs. pid/age heuristics), and what happens to a socket whose owner is alive but unresponsive?
  - Should these sockets be created with 0600 permissions, and is tightening them from the current umask-derived mode an acceptable behavior change for any existing consumer that relies on cross-user access?
  - Should the sockets move to a per-user VS Code-owned directory (e.g. under the server data dir) when XDG_RUNTIME_DIR is unset, instead of shared /tmp?

## Evidence

- **cleanup only on graceful dispose (git):** extensions/git/src/ipc/ipcServer.ts: `IPCServer.dispose()` does `fs.unlinkSync(this._ipcHandlePath)` — this is the fix lszomoru described in https://github.com/microsoft/vscode/issues/153311#issuecomment-1346473069. It never runs when the extension host is killed with the SSH connection, which matches the reporter's reopen.
- **cleanup only on graceful dispose (CLI server):** src/vs/workbench/api/node/extHostCLIServer.ts: `CLIServerBase.dispose()` unlinks the handle created by `createRandomIPCHandle()`; this is the source of the `vscode-ipc-*.sock` files. Same ungraceful-exit gap.
- **no stale-socket sweep anywhere:** Grepping src/vs/server/node and the git extension on current main finds no startup scan that removes orphaned sockets; the only other unlink is a per-instance disposable in src/vs/server/node/serverServices.ts (~line 366). src/vs/base/parts/ipc/node/ipc.net.ts `createRandomIPCHandle()` only chooses XDG_RUNTIME_DIR (when set and non-darwin) or `os.tmpdir()` — on hosts without XDG_RUNTIME_DIR, like the reporter's, everything lands in shared /tmp.
- **world-readable sockets confirmed in source:** Neither ipc.net.ts, extensions/git/src/ipc/ipcServer.ts nor extHostCLIServer.ts calls `chmod` or sets a mode after `server.listen()`, so the socket mode is whatever the user's umask yields (0755 on a default 022 umask) — exactly the world-readable entries in the report. The reporter's second question is therefore still unanswered.
- **independent confirmation:** https://github.com/microsoft/vscode/issues/153311#issuecomment-1204283745 reproduces the same pile-up (plus `vscode-distro-env.*`) and links the older https://github.com/microsoft/vscode/issues/7758, showing this has regressed before.
- **reopened after the attempted fix:** Issue state is REOPENED: the December 2022 git-extension change shipped and the reporter still saw leftovers, so no implemented-on-main close is available; the checkout here is shallow (single commit), so no fix commit can be cited either.
- **pyright directories are out of scope:** The `pyright-*` directories in the report come from the Pylance/Pyright language server, not VS Code core — that part belongs to the Python/Pylance tooling, not this repo.
