# Issue #234708 — VSCode will silently never auto-update if it is not explicitly moved from the "Downloads" directory to "Application"

[https://github.com/microsoft/vscode/issues/234708](https://github.com/microsoft/vscode/issues/234708)

## Summary

The silent-failure gap remains in current source: macOS background update errors are logged but discarded before reaching the update UI. DMG installation addresses a common installation trigger, but does not establish that existing affected installations receive actionable notice.

## Change summary

Make blocked macOS automatic updates visible and provide accurate installation or quarantine recovery guidance.

## Best solution

Expose persistent macOS update blockers through the existing update UI with actionable recovery guidance, while preserving quiet handling of transient background failures. Do not assume moving the app to Applications resolves every case: several commenters already had it there.

Cover explicit checks, transient network failures, successful updates, and recovery after reinstalling through the DMG. Add focused error-processing and update-UI tests for the agreed behavior.
- **Behavior:**

  > An installation that cannot apply automatic updates must not leave the user indefinitely unaware of the blocker. Recovery guidance must distinguish the normal installation path from cases where the app is already in Applications. Acceptance should cover background and manual checks, repeated failures, and successful recovery without introducing repeated alerts for transient network failures.
- **Trace:**

  > DarwinUpdateService.doCheckForUpdates in src/vs/platform/update/electron-main/updateService.darwin.ts enters CheckingForUpdates with an explicit flag and invokes Electron autoUpdater. Its onError handler logs the failure but removes the message for background checks before emitting State.Idle. UpdateTitleBarEntry and UpdateTooltip consume state.error, so that discarded error cannot produce an actionable indication. preprocessError in src/vs/workbench/contrib/update/common/updateUtils.ts still supplies the historical quarantine link. The record at https://github.com/microsoft/vscode/issues/213909 establishes DMG installation as a mitigation, not a demonstrated repair of this reporting path. Preserve existing successful-update behavior and avoid treating all macOS update failures as quarantine failures; uncertainty starts at which persistent failures merit background exposure and how often users should be reminded.
- **Open decisions:**
  - Should a persistent installation blocker automatically open the update tooltip, or remain visible as a non-interrupting update indicator until the user opens it?
  - After the first notice, should the same unresolved blocker be shown again on restart, periodically, or only when the user explicitly checks for updates?

## Evidence

- **Current source confirms silent background failures:** src/vs/platform/update/electron-main/updateService.darwin.ts: DarwinUpdateService.doCheckForUpdates records whether a check is explicit; onError logs the Electron error but passes it to State.Idle only when the state is CheckingForUpdates with explicit=true. For automatic checks, the error becomes undefined, including a read-only-volume error.
- **Current UI cannot display the discarded error:** src/vs/workbench/contrib/update/browser/updateTitleBarEntry.ts shows the Idle error tooltip only when state.error is present; updateTooltip.ts renders the Idle error message from that same field.
