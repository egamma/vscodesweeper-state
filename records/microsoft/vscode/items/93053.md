# Issue #93053 — Please make it possible to add gutter (margin) before the text area

[https://github.com/microsoft/vscode/issues/93053](https://github.com/microsoft/vscode/issues/93053)

## Summary

Keep this accepted Backlog request open: current source can widen the decorations gutter, but does not provide the requested configurable margin with text-selection behavior. The older cursor-placement issue covers only part of the request, while the closer padding requests are newer and cannot serve as duplicate canonicals for this re-reviewed item.

## Change summary

Provide configurable space before editor text, with a choice between placing the caret and selecting whole lines when interacting with that space.

## Best solution

Provide an editor-native left margin whose rendering and mouse behavior agree, preserving folding, glyph decorations, and existing line-number interactions. Settle the public configuration and interaction contract with the editor owner, coordinating the overlapping requests without discarding this issue's additional requirements.

- **Validation:** After agreeing the contract, verify in an editor with folding and line numbers enabled that clicking the added text-selection margin places the caret at column 1 and dragging right selects a partial line; verify the alternative mode selects whole lines. Check empty lines, horizontal scrolling, and unchanged folding and glyph interactions, and add layout assertions in src/vs/editor/test/browser/config/editorLayoutProvider.test.ts.
- **Behavior:**

  > Users currently have a narrow target for placing the caret before the first character, and increasing gutter width does not create additional text-selection space. The requested outcome is configurable separation before editor text, with the proposed interaction modes supporting either ordinary caret placement and text dragging or whole-line selection. Acceptance should cover line-start clicks, partial-line dragging, empty lines, and unchanged folding and breakpoint interactions. Preserve the existing experience when the new capability is not enabled.
- **Trace:**

  > EditorLayoutInfoComputer.computeLayout in src/vs/editor/common/config/editorOptions.ts positions content immediately after lineDecorationsWidth; EditorPadding exposes only top and bottom padding. MouseTargetFactory._hitTestMargin in src/vs/editor/browser/controller/mouseTarget.ts classifies the intervening region as GUTTER_LINE_DECORATIONS, and MouseHandler._onMouseDown in src/vs/editor/browser/controller/mouseHandler.ts does not start ordinary text selection there. This establishes why gutter-width adjustments are only a visual workaround, without executing the editor. Coordinate with https://github.com/microsoft/vscode/issues/41574, https://github.com/microsoft/vscode/issues/135114, and https://github.com/microsoft/vscode/issues/206914; none was verified as a policy-valid canonical for this full request. The uncertainty starts at the public width and interaction contract, not at whether existing top/bottom padding satisfies the ask. Preserve existing gutter consumers; the author's later suggestion of independently customizable decoration lanes should not silently expand the initial margin work.
- **Open decisions:**
  - Should the new margin expose both text-selection and whole-line-selection modes, as requested, or provide text-selection behavior only?
  - Should margin width be configured in pixels, character units, or both, and how should it behave during horizontal scrolling?
  - Should separately customizable decoration margins from the later author comment be included in this feature or remain separate follow-up work?
