# Issue #275671 — Incrementally render markdown in chat

[https://github.com/microsoft/vscode/issues/275671](https://github.com/microsoft/vscode/issues/275671)

## Summary

Keep open: current incremental-rendering settings batch streaming updates, but still re-render the accumulated markdown rather than reuse completed blocks. The older related issues explicitly delegate this optimization here; they do not replace it.

## Change summary

Avoid repeatedly rendering completed markdown blocks while a chat response streams.

## Best solution

Make streaming markdown rendering reuse stable completed content while updating the unfinished portion, preserving existing markdown semantics and chat integrations. Establish safe reuse boundaries and measurable rendering-cost acceptance criteria before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatMarkdownContentPart.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatIncrementalRendering/chatIncrementalRendering.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatIncrementalRendering/buffers/paragraphBuffer.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentMarkdownRenderer.ts`, `src/vs/base/browser/markdownRenderer.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/chatContentParts/chatIncrementalRendering.test.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/chatContentParts/chatMarkdownContentPart.test.ts`
- **Validation:** Add targeted streaming tests that append to a long multi-block response and measure that unchanged completed blocks are not re-rendered on each append. Compare completed output with a one-shot render, including fenced code, lists, tables, reference links, and non-append updates; run the affected chat rendering suites and profile the same long-response stream before and after.
- **Behavior:**

  > Streaming a long chat response should not repeatedly render all previously completed markdown blocks as additional content arrives. The finished response must retain the same markdown meaning and chat behavior as the existing full renderer, including content whose interpretation changes when later text arrives. Acceptance should demonstrate reuse of stable completed content, equivalent final output, and reduced rendering work on a repeatable long-response stream.
- **Trace:**

  > ChatMarkdownContentPart wires IncrementalDOMMorpher to its existing renderMarkdown closure. ParagraphBuffer selects a growing prefix, and IncrementalDOMMorpher._flushRender forwards that prefix to the callback; the closure still renders the accumulated content through ChatContentMarkdownRenderer and the standard markdown pipeline. The low-level renderMarkdown in src/vs/base/browser/markdownRenderer.ts creates a fresh parser and sanitizes the supplied content on each call, so batching alone does not implement completed-block reuse. Preserve sanitization, markdown correctness, code-block integrations, and non-append update behavior; changes to shared rendering infrastructure require examining its other consumers. Safe reuse and invalidation boundaries have not been established, particularly for constructs whose interpretation depends on later content. https://github.com/microsoft/vscode/issues/275176 explicitly delegates this optimization here, and https://github.com/microsoft/vscode/issues/263896 tracks it as a distinct work item. The virtualization proposal at https://github.com/microsoft/vscode/pull/286464 was rejected and is closed, not an implementation to resume without design review.

## Evidence

- **Existing capability does not cover the request:** src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts:626-665 registers chat.experimental.incrementalRendering.enabled (default false) and chat.experimental.incrementalRendering.buffering. These control update timing and animation, not reuse of completed markdown blocks.
- **Current accumulated-content rendering:** In src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatIncrementalRendering/buffers/paragraphBuffer.ts, ParagraphBuffer.getRenderable returns a prefix starting at the beginning of fullMarkdown. IncrementalDOMMorpher._flushRender in chatIncrementalRendering.ts passes that accumulated prefix to its render callback. ChatMarkdownContentPart's callback then invokes renderMarkdown, whose renderer.render call receives the accumulated content.
- **Full rendering pipeline:** src/vs/workbench/contrib/chat/browser/widget/chatContentMarkdownRenderer.ts:132-149 forwards markdown to the renderer service. src/vs/base/browser/markdownRenderer.ts:221-267 creates a new Marked instance, lexes/parses the supplied value, sanitizes the resulting HTML, and replaces target content. Some code-block DOM can be preserved, but this does not avoid reprocessing completed prose blocks.
- **Older related issue delegates this work:** https://github.com/microsoft/vscode/issues/275176 is open, but concerns excessive updateThinking calls. Its author explicitly created this issue to track block-level incremental markdown rendering: https://github.com/microsoft/vscode/issues/275176#issuecomment-3493097978. It is related evidence, not a same-symptom canonical replacing this request.
- **Parent performance tracker:** https://github.com/microsoft/vscode/issues/263896 is open and lists this issue as a separate unchecked optimization alongside pagination and list-rendering work. It is an umbrella, not a reason to discard this dedicated implementation item.
- **Related PR was not merged:** https://github.com/microsoft/vscode/pull/286464 is closed with mergedAt and mergeCommit null. The maintainer rejected its virtualization approach and pointed back to this issue in https://github.com/microsoft/vscode/pull/286464#issuecomment-3721574502; it supplies neither a landed fix nor an active competing implementation.
