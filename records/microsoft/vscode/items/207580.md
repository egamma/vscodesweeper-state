# Issue #207580 — Allow WorkspaceEditMetadata to control whether changes are grouped by label by default

[https://github.com/microsoft/vscode/issues/207580](https://github.com/microsoft/vscode/issues/207580)

## Summary

Keep open: current main supports manual, profile-persisted grouping but has no edit-specific metadata control for its initial presentation. The request has 59 upvotes and was accepted into Backlog; related reports do not clearly own this distinct API contract.

## Change summary

Allow an extension to request label-based grouping for an individual workspace edit's preview.

## Best solution

Provide an edit-level grouping preference through the workspace-edit API and preview pipeline, while retaining user-controlled grouping. Agree on how that preference interacts with the user's saved choice before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostBulkEdits.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadBulkEdits.ts`, `src/vs/editor/browser/services/bulkEditService.ts`, `src/vs/workbench/contrib/bulkEdit/browser/preview/bulkEdit.contribution.ts`, `src/vs/workbench/contrib/bulkEdit/browser/preview/bulkEditPane.ts`
- **Validation:** Use an extension-host scenario that applies a WorkspaceEdit containing two distinct labels and needsConfirmation entries. Check the initial preview grouping with metadata absent and with each supported grouping preference, both on a fresh profile and after saving the opposite user preference. Verify manual grouping remains available, label groups contain the correct edits, confirmation selections are unchanged, and any persistence follows the agreed contract.
- **Behavior:**

  > Extensions currently cannot select label-based initial presentation for an individual workspace edit, even when its entries provide labels and require confirmation. The desired capability lets an extension express that preference before the preview opens, rather than requiring the user to toggle grouping afterward. Acceptance must cover an edit with multiple labels, metadata omission, conflicting saved user preferences, and manual regrouping. Existing edit application and confirmation semantics must remain unchanged.
- **Trace:**

  > WorkspaceEditMetadata in src/vscode-dts/vscode.d.ts currently contains only isRefactoring. ExtHostBulkEdits.applyWorkspaceEdit forwards that value through MainThreadBulkEditsShape.$tryApplyWorkspaceEdit in src/vs/workbench/api/common/extHost.protocol.ts; MainThreadBulkEdits maps it to the bulk-edit autosave option. IBulkEditOptions has no grouping field, and BulkEditPreviewContribution registers a handler that passes only edits to BulkEditPane.setInput. BulkEditPane loads groupByFile from profile storage with a true default, forces file grouping when there are not multiple categories, and saves manual grouping changes. Source inspection establishes the missing API capability, but the record does not settle precedence or persistence for an edit-supplied preference. Preserve confirmation selection, application behavior and the existing manual grouping controls; checkbox rendering and extension feedback actions are separate work. The older discussion at https://github.com/microsoft/vscode/issues/176984 is relevant context, not a verified duplicate canonical.
- **Open decisions:**
  - Should an edit-supplied grouping preference override an existing saved user preference, or apply only when the user has not chosen a grouping mode?
  - Should metadata-selected grouping remain local to that preview, or affect the grouping used for subsequent edits that omit the preference?
