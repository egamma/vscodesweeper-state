# Issue #305990 — Terminal in editor area prevents new tabs from opening in the expected editor group

[https://github.com/microsoft/vscode/issues/305990](https://github.com/microsoft/vscode/issues/305990)

## Summary

The reported routing matches intentional terminal editor group auto-locking, which prevents new files from opening into a dedicated terminal group. Existing configuration and the group's unlock control provide the requested behavior, and maintainers have explicitly confirmed this same scenario as designed.

## Change summary

Open new tabs beside the focused terminal in a secondary editor group instead of another group.

## Best solution

Keep the intentional locked-group routing and explain how to unlock the terminal group or disable terminal auto-locking through workbench.editor.autoLockGroups.

- **Proposed comment:**

  > Thanks for the report. Terminal-only editor groups are automatically locked by default, so new tabs open in another unlocked group even when the terminal has focus. This is intentional, as explained in https://github.com/microsoft/vscode/issues/154695#issuecomment-1179805445.
  > 
  > Click the group's lock icon to unlock it and allow new tabs to open there. To disable automatic locking for future terminal groups, set the `terminalEditor` entry in `workbench.editor.autoLockGroups` to `false`.

## Evidence

- **Exact maintainer precedent:** https://github.com/microsoft/vscode/issues/154695 describes placing a terminal alone in the right editor group, focusing it, and finding that new files and terminals open in the first group. In https://github.com/microsoft/vscode/issues/154695#issuecomment-1179805445, the terminal maintainer explains that this intentionally protects a persistent terminal group and identifies the lock icon and workbench.editor.autoLockGroups as the controls. The issue is closed with *as-designed.
- **Split-terminal precedent:** https://github.com/microsoft/vscode/issues/153953 reports moving a terminal into the editor area, splitting the editor, and having new terminals open in the primary group. https://github.com/microsoft/vscode/issues/153953#issuecomment-1176173390 explicitly identifies the group lock and workbench.editor.autoLockGroups, and the issue is closed with *as-designed.
- **Current default and configuration:** src/vs/workbench/browser/parts/editor/editorConfiguration.ts lists terminalEditor in AUTO_LOCK_DEFAULT_ENABLED and registers workbench.editor.autoLockGroups. Its description explicitly states that a matching first editor in a multi-group layout automatically locks the group and that locked groups are not default destinations for new editors. Setting the terminalEditor entry to false disables this automatic locking.
- **Current routing mechanism:** src/vs/workbench/browser/parts/editor/editorGroupView.ts, around lines 1263–1272, locks a group when its first newly opened editor has an auto-lock-enabled editor ID and multiple groups exist. src/vs/workbench/services/editor/common/editorGroupFinder.ts, in doFindGroup and isGroupLockedForEditor, intentionally skips a locked active group for an editor not already present and chooses an unlocked group instead. This explains why focusing the terminal does not make its locked group the destination for a new tab.
- **Related report is not a duplicate target:** https://github.com/microsoft/vscode/issues/299063 is closed and primarily concerns Ctrl+P routing between detached windows, not a terminal-only group in a split layout. The reporter's later comment at https://github.com/microsoft/vscode/issues/299063#issuecomment-4148423856 supplies the terminal-group symptom separately. No open canonical owning this exact behavior was verified; the closure proposal rests on the explicit as-designed precedent, not a duplicate claim.
