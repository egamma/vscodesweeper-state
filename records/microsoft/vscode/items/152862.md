# Issue #152862 — A change in VScode makes it confusing for a user to switch the to a different PowerShell environment in the Integrated Terminal.

[https://github.com/microsoft/vscode/issues/152862](https://github.com/microsoft/vscode/issues/152862)

## Summary

Keep open: manual pinning restores direct access, but current core still requires users to discover the language-status menu first. Maintainers acknowledged the discoverability problem and interest in default pinning; neither an applicable fix nor an older open same-symptom canonical was established.

## Change summary

Make the PowerShell session/version selector discoverable without requiring users to first find and manually pin its language-status item.

## Best solution

Improve discoverability through the shared language-status UI while preserving users' control over status-bar visibility. Resolve whether a user-controlled default-pinning option or a clearer shared entry point best addresses the reported problem; extension-controlled pinning was previously declined and should not be assumed.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/languageStatus/browser/languageStatus.ts`, `src/vs/workbench/contrib/languageStatus/browser/languageStatus.contribution.ts`
- **Validation:** Using a fresh profile with the PowerShell extension and a PowerShell file, verify that the agreed design makes the session selector discoverable without prior manual pinning, switching versions remains functional, and explicit user pin/unpin choices survive reload. Check the same discovery path with keyboard navigation and a screen reader.
- **Behavior:**

  > Users accustomed to clicking the visible PowerShell version struggle to find its replacement under the generic language-status entry. Manual pinning restores direct access but requires discovering that entry first. The finished design should make the session/version action discoverable while retaining user control over status-bar visibility and preserving session-switching behavior. Acceptance must include a fresh profile, persisted explicit pin/unpin choices, and keyboard and screen-reader access.
- **Trace:**

  > LanguageStatus in src/vs/workbench/contrib/languageStatus/browser/languageStatus.ts restores languageStatus.dedicated from profile storage, defaulting to no dedicated items; _createViewModel uses that set to choose separately visible entries. The combined entry opens its tooltip through ShowTooltipCommand, and _renderStatus supplies each command link and manual pin/unpin action. The contribution registration exposes no default-pinning setting. This establishes the core visibility boundary, not a failure in PowerShell's session-switching implementation. https://github.com/microsoft/vscode/issues/145995 records opposition to extension-controlled defaults while leaving user-controlled defaults open; later feedback in https://github.com/microsoft/vscode/issues/152862 supports addressing discoverability. Preserve existing explicit visibility choices and avoid changing terminal profiles or PowerShell runtime selection semantics.
- **Open decisions:**
  - Should the shared language-status experience offer user-controlled default pinning, or address first-use discoverability while retaining the current unpinned default?
