# Issue #201431 — [folding] Manual folding range not useful after copy-paste

[https://github.com/microsoft/vscode/issues/201431](https://github.com/microsoft/vscode/issues/201431)

## Summary

The defect remains on current main: replacing folded content can leave an unmatched collapsed provider range classified as a persistent manual/recovered range. The issue already has the correct folding-area label and no older open canonical owns the same symptom.

## Change summary

Replacing one folded indentation tree with another leaves stale manual folding ranges that interfere with folding the pasted content and can persist across restarts.

## Best solution

Preserve collapsed ranges across ordinary edits while discarding recovered ranges invalidated by a replacement edit, with the exact preservation boundary agreed by the editor-folding maintainer before implementation.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/folding/browser/folding.ts`, `src/vs/editor/contrib/folding/browser/foldingModel.ts`, `src/vs/editor/contrib/folding/browser/foldingRanges.ts`, `src/vs/editor/contrib/folding/test/browser/foldingModel.test.ts`, `src/vs/editor/contrib/folding/test/browser/foldingRanges.test.ts`
- **Validation:** Add a folding-model unit test reproducing the issue's fold-all and replacement-paste sequence, asserting that the pasted tree exposes only its newly computed indentation ranges while collapsed ranges unaffected by the replacement remain preserved; run the folding unit suite with `./scripts/test.sh --grep "FoldingModel|FoldingRanges"`.
- **Behavior:**

  > After folded content is replaced by pasted text, folding controls and ranges must correspond to the pasted document structure rather than stale ranges from the replaced text. Fold state outside the replaced region must remain intact. The stale range must not return after folding refresh or editor restoration. Existing explicit user-created folding ranges must retain their documented behavior.
- **Trace:**

  > FoldingController.onDidChangeModelContent in src/vs/editor/contrib/folding/browser/folding.ts triggers recomputation but does not carry the content-change ranges into the folding merge. FoldingModel._currentFoldedOrManualRanges in src/vs/editor/contrib/folding/browser/foldingModel.ts reads edit-tracked decorations for every collapsed or non-provider range. FoldingRegions.sanitizeAndMerge in src/vs/editor/contrib/folding/browser/foldingRanges.ts converts an unmatched collapsed provider range into FoldSource.recovered, after which it behaves as a manual range and is included in persistence state. This directly explains the issue and the restart persistence reported in the latest comment. The boundary is fold-state preservation: ranges unaffected by the replacement and explicit user-defined ranges must not be discarded. https://github.com/microsoft/vscode/issues/266597 and commit e85daf162a1e12151fc97ba0a8a092033cfb169c provide a cleanup workaround, not a root fix.
- **Open decisions:**
  - When a replacement edit invalidates a collapsed provider range, should VS Code always discard that range, or preserve it when content identity can still be established despite changed range boundaries?
  - Should recovered provider ranges remain eligible for persisted editor state, or should persistence be limited to ranges still matched by a provider plus explicitly user-defined ranges?

## Evidence

- **current source:** src/vs/editor/contrib/folding/browser/foldingModel.ts `_currentFoldedOrManualRanges` carries every collapsed provider range through an edit, and `FoldingModel.update` merges those ranges with newly computed provider ranges.
- **root cause:** src/vs/editor/contrib/folding/browser/foldingRanges.ts `FoldingRegions.sanitizeAndMerge` changes a previously collapsed provider range to `FoldSource.recovered` when no newly computed range has the same start line. Because non-provider ranges are carried forward on subsequent updates and included in the folding memento, the stale range can persist.
- **edit path:** src/vs/editor/contrib/folding/browser/folding.ts `onDidChangeModelContent` forwards the content change to the hidden-range model but triggers folding recomputation without retaining edit details; `triggerFoldingModelChanged` passes only current selections to `FoldingModel.update`.
- **maintainer confirmation:** The maintainer comment on https://github.com/microsoft/vscode/issues/201431 confirms that unmatched collapsed ranges are deliberately converted to manual ranges to avoid losing fold state, while acknowledging that the result is not useful for this example.
- **related workaround:** https://github.com/microsoft/vscode/issues/266597 explicitly identifies https://github.com/microsoft/vscode/issues/201431 as the underlying folding problem. Its merged fix, https://github.com/microsoft/vscode/commit/e85daf162a1e12151fc97ba0a8a092033cfb169c, improves `editor.removeManualFoldingRanges` as a cleanup command but does not prevent stale ranges from being created.
