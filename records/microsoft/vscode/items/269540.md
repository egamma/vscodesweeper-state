Keep open: notebook execution still lacks an execution-aware extension-host restart veto, and the maintainer has identified this as notebook-owned work. - **Maintainer direction:** The supplied 2025-10-02 comment by bpasero identifies notebook participation in the extension-host restart veto as the intended direction, citing https://github.com/microsoft/vscode/blob/148542970d877c495d49c283e39b18df5b7d81a4/src/vs/workbench/contrib/debug/browser/debugService.ts#L208-L213. Current debugService.ts:209-213 still vetoes stops while debug sessions are active.
- **Current workspace transition:** src/vs/workbench/services/workspaces/electron-browser/workspaceEditingService.ts:178-182 calls stopExtensionHosts with the reason "Opening a multi-root workspace" and aborts the transition if stopping is vetoed.
- **Current notebook protection gap:** src/vs/workbench/contrib/notebook/common/notebookEditorInput.ts:93-119 handles onWillStop through dirty/save state, returning immediately for a nonautomatic stop of a clean notebook. Its veto does not inspect execution state; searching the notebook contribution found no other onWillStop listener. This establishes the missing core protection, without executing Jupyter or confirming kernel termination at runtime.
- **Existing confirmation mechanism:** src/vs/workbench/services/extensions/common/abstractExtensionService.ts:765-820 collects restart vetoes and, for a nonautomatic stop, presents "Please confirm restart of extensions" with a "Restart Anyway" action. The requested protection can use this existing mechanism.
