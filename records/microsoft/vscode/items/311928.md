# Issue #311928 — Settings UI shows undefined for default values in nested configuration keys

[https://github.com/microsoft/vscode/issues/311928](https://github.com/microsoft/vscode/issues/311928)

## Summary

This is by design: VS Code's configuration system uses dot-separated keys as tree paths, so a key like `repro.test` cannot simultaneously hold a leaf value AND serve as an intermediate node for `repro.test.extra`. The `addToValueTree` function explicitly reports and ignores such conflicts.

## Change summary

When an extension registers both `x.y` and `x.y.z` as configuration keys, the Settings UI shows `undefined` for defaults and runtime reads are inconsistent.

## Best solution

Close as designed. The configuration model fundamentally treats dots as path separators in a tree structure — a key path cannot be both a leaf and a branch. Extension authors must use non-overlapping key hierarchies (e.g. `focus.behavior.folders.default` instead of `focus.behavior.folders` alongside `focus.behavior.folders.external`).

## Evidence

- **addToValueTree design:** src/vs/platform/configuration/common/configuration.ts:249-283 — `addToValueTree` splits keys on `.` and walks the tree; when a segment resolves to a non-object (e.g. a string leaf), it reports a conflict and ignores the key.
- **conflict path:** If `repro.test` is added first with value "b", then `repro.test.extra` tries to traverse `test` as an object but finds a string — triggering the conflict reporter at line 268: `Ignoring repro.test.extra as repro.test is "b"`.
- **long-standing design:** The `toValuesTree`/`addToValueTree` tree model has been the foundation of configuration storage since early VS Code; the conflict reporter was added intentionally to handle this case.
