# Issue #188612 — Ability to use and override default profile settings in a custom profile

[https://github.com/microsoft/vscode/issues/188612](https://github.com/microsoft/vscode/issues/188612)

## Summary

This remains a necessary, highly supported profiles feature: current partial profiles can either share the Default profile's entire settings resource or use an isolated copy, but cannot inherit defaults while storing profile-specific overrides. The team-authored issue already carries the appropriate under-discussion routing and has 162 upvotes.

## Change summary

Allow a custom profile to inherit live settings from the Default profile while overriding selected settings locally.

## Best solution

Provide an opt-in settings layer for custom profiles where Default-profile settings form the base, custom-profile values take precedence, and later Default-profile changes continue to flow through when not overridden. Preserve existing isolated and fully shared profile behavior.

## Plan brief

- **Likely files:** `src/vs/platform/userDataProfile/common/userDataProfile.ts`, `src/vs/workbench/services/configuration/browser/configuration.ts`, `src/vs/workbench/services/configuration/browser/configurationService.ts`, `src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditor.ts`, `src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditorModel.ts`, `src/vs/workbench/services/configuration/test/browser/configurationService.test.ts`
- **Validation:** Extend the configuration service profile tests to verify that an opted-in custom profile observes later Default-profile setting changes, locally overridden values win, removing an override falls back to Default, writes target the custom profile resource, and non-inheriting profiles remain unchanged.
- **Behavior:**

  > A custom profile can opt into inheriting settings from the Default profile while retaining its own settings overrides. Changes to non-overridden Default settings become visible in the custom profile, custom values take precedence, and removing a custom value restores the inherited value. Existing profiles that share all Default settings or keep isolated settings must retain their current behavior.
- **Trace:**

  > toUserDataProfile in src/vs/platform/userDataProfile/common/userDataProfile.ts currently implements useDefaultFlags.settings by aliasing the custom profile's settingsResource to the Default profile resource. WorkspaceService in src/vs/workbench/services/configuration/browser/configurationService.ts consequently loads one local user configuration rather than separate base and override models, while the Profiles editor represents the choice as “Default” versus “None.” Tests in src/vs/platform/userDataProfile/test/common/userDataProfileService.test.ts and src/vs/workbench/services/configuration/test/browser/configurationService.test.ts encode this shared-resource behavior. The investigation boundary is settings inheritance only: do not expand this issue into arbitrary profile hierarchies, extension inheritance, keybindings, tasks, or snippets. https://github.com/microsoft/vscode/issues/156144 shipped partial profiles and designated this issue as the settings-override follow-up; https://github.com/microsoft/vscode/issues/191516 confirms this issue owns the settings-only case.
- **Open decisions:**
  - Should the current “Default” settings choice change to inherited-with-overrides semantics, or should profiles expose separate choices for sharing the Default settings resource and inheriting it as a base?
  - How should workbench.settings.applyToAllProfiles interact with a profile-local override of the same setting: must the all-profiles value remain authoritative, or may the inheriting profile override it?

## Evidence

- **current source behavior:** In src/vs/platform/userDataProfile/common/userDataProfile.ts, toUserDataProfile assigns the Default profile's settingsResource directly when useDefaultFlags.settings is true; the custom profile therefore has no separate settings resource in which to store overrides.
- **configuration boundary:** src/vs/workbench/services/configuration/browser/configurationService.ts constructs localUserConfiguration from the single currentProfile.settingsResource and suppresses the separate application configuration when useDefaultFlags.settings is set. There is no Default-base plus custom-override settings layer.
- **existing capability is partial:** src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditor.ts offers “Default” or “None” for each profile resource. “Default” shares the resource wholesale; it does not satisfy the requested override behavior. workbench.settings.applyToAllProfiles only synchronizes an explicitly enumerated set of settings.
- **tests confirm the gap:** src/vs/platform/userDataProfile/test/common/userDataProfileService.test.ts asserts that a profile using Default settings has the same settingsResource as the Default profile. src/vs/workbench/services/configuration/test/browser/configurationService.test.ts likewise tests a single shared resource, not merged profile overrides.
- **canonical ownership:** The maintainer closed https://github.com/microsoft/vscode/issues/156144 after shipping partial profiles and explicitly created this issue to track overriding Default-profile settings. The later general-inheritance report https://github.com/microsoft/vscode/issues/191516 was closed with a maintainer comment directing its settings-only case back to this issue.
- **continued demand:** The issue has 162 community upvotes and multiple concrete scenarios involving shared editor appearance, key defaults, and language/toolchain-specific formatter or lint settings. A maintainer stated only that it was not yet planned, not that the request was declined.
