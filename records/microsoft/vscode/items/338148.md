# Issue #338148 — Pty host parses all terminal output a second time, even with persistent sessions disabled

[https://github.com/microsoft/vscode/issues/338148](https://github.com/microsoft/vscode/issues/338148)

## Summary

Confirmed on current main: the pty host's PersistentTerminalProcess always constructs an XtermSerializer (a full @xterm/headless instance plus ShellIntegrationAddon) and feeds it every output chunk via handleData, regardless of terminal.integrated.enablePersistentSessions or persistentSessionScrollback — shouldPersistTerminal only gates detach/revive, not serializer creation or feeding. This is a real, well-measured perf issue, but the serializer also backs pty-host-side shell-integration command tracking, so the fix needs a maintainer decision on scope.

## Change summary

Every terminal's pty host process double-parses all output through a headless xterm instance for serialization/replay, even when persistent sessions are disabled, wasting significant CPU (profiled: ~33% of pty host main-thread time in XtermSerializer.handleData).

## Best solution

Skip constructing/feeding the XtermSerializer when shouldPersistTerminal is false, but first work out (with a maintainer) what to do about the pty-host-side ShellIntegrationAddon.setNextCommandId path that also currently lives on that serializer, since disabling it isn't a pure no-op.

## Plan brief

- **Likely files:** `src/vs/platform/terminal/node/ptyService.ts`
- **Validation:** A pty host test asserting XtermSerializer.handleData (or equivalent xterm.write) is not invoked per output chunk when shouldPersistTerminal is false and shell integration isn't required, while shell-integration command detection (setNextCommandId) still works for the chosen scope.
- **Behavior:**

  > When terminal.integrated.enablePersistentSessions is false (and no reload-restore path needs a buffer), the pty host should not parse every output chunk through a full headless xterm terminal purely for serialization. CPU spent in the pty host for a given amount of terminal output should drop measurably (the reporter's vtebench numbers, ~33% of main-thread time in handleData, are the baseline). Existing shell-integration command detection and any legitimate reload/revive flows must continue to work for whatever scope the maintainer decides to keep.
- **Trace:**

  > PersistentTerminalProcess (src/vs/platform/terminal/node/ptyService.ts, constructor around lines 784-793) unconditionally creates an XtermSerializer, and onProcessData is wired at line ~823 to call this._serializer.handleData(e) for every process regardless of shouldPersistTerminal. XtermSerializer (class starting ~line 1032) wraps a full @xterm/headless Terminal plus a ShellIntegrationAddon; the addon's setNextCommandId is also called from a separate proxy path (ptyHostService.ts:268, ptyService.ts:486-487, 927-928) unrelated to the reviver/replay events. The boundary: do not change the persistent-session revive/replay behavior (serializeNormalBuffer, generateReplayEvent) for terminals where shouldPersistTerminal is true. Where the uncertainty starts: whether shell-integration command tracking must still run through a headless terminal when persistence is off, or whether ShellIntegrationAddon can be decoupled from XtermSerializer entirely — that determines whether the serializer is skipped outright or replaced with a lighter buffering scheme, per the reporter's two proposed directions.
- **Open decisions:**
  - Should pty-host-side shell integration command detection (ShellIntegrationAddon/setNextCommandId) still run when persistent sessions are disabled, or can it be dropped/moved to rely solely on the renderer-side detection?
  - When persistence is off, should raw output simply not be buffered at all (reload/restore falls back to renderer state), or should it be buffered raw and only parsed on-demand (e.g. lazy serialization on reload)?

## Evidence

- **unconditional serializer construction:** src/vs/platform/terminal/node/ptyService.ts lines ~784-793 (constructor) build `this._serializer = new XtermSerializer(...)` for every PersistentTerminalProcess with no check on shouldPersistTerminal, confirmed unchanged on main at commit 682c0f7.
- **unconditional double-parse:** ptyService.ts line ~822-823: `this._register(this.onProcessData(e => this._serializer.handleData(e)))` runs for all processes; XtermSerializer.handleData (line ~1066) calls `this._xterm.write(data)` on a full @xterm/headless instance regardless of persistence settings.
- **shouldPersistTerminal only gates detach:** ptyService.ts line ~837: `if (this.shouldPersistTerminal && ...)` only affects whether the process is kept alive on detach; it is not consulted anywhere in serializer setup or data feeding.
- **coupling with shell integration:** The same XtermSerializer hosts a ShellIntegrationAddon whose setNextCommandId (ptyService.ts ~927-928, ~1078-1079) is called from a separate proxy path (ptyHostService.ts:268-269, ptyService.ts:486-487) used for command-ID correlation, meaning a naive skip could regress shell integration command detection.
