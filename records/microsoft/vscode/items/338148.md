# Issue #338148 — Pty host parses all terminal output a second time, even with persistent sessions disabled

[https://github.com/microsoft/vscode/issues/338148](https://github.com/microsoft/vscode/issues/338148)

## Summary

Well-diagnosed, source-confirmed perf issue: the pty host's `PersistentTerminalProcess` always feeds every output chunk into `XtermSerializer.handleData`, independent of `shouldPersistTerminal`, so disabling persistent sessions buys no CPU savings as the reporter's benchmarks show.

## Change summary

The pty host always parses terminal output through a headless xterm serializer for reconnect/revive, even when persistent sessions are disabled, wasting CPU.

## Best solution

Gate the serializer/handleData path on `shouldPersistTerminal` (or otherwise avoid double-parsing when persistence is off) in src/vs/platform/terminal/node/ptyService.ts, but a maintainer should weigh in on how reload/replay behaves when the serializer is skipped before implementation starts.

## Plan brief

- **Likely files:** `src/vs/platform/terminal/node/ptyService.ts`
- **Validation:** A pty host test asserting XtermSerializer.handleData (or equivalent parsing) is not invoked when shouldPersistTerminal is false, while output still reaches the renderer correctly.
- **Behavior:**

  > When `terminal.integrated.enablePersistentSessions` is false, the pty host should not spend CPU re-parsing terminal output into a headless xterm instance for reconnect/revive purposes, since that buffer is never used. Output must still reach the renderer unaffected, and when persistence is enabled behavior is unchanged.
- **Trace:**

  > In src/vs/platform/terminal/node/ptyService.ts, PersistentTerminalProcess's constructor always registers `this.onProcessData(e => this._serializer.handleData(e)))` regardless of `shouldPersistTerminal`; the XtermSerializer (also hosting a ShellIntegrationAddon) is created unconditionally too. `shouldPersistTerminal` currently only gates `rawReviveBuffer` and the detach/shutdown decision (see `detach()`). Do not change the detach/shutdown persistence semantics or shell integration when persistence IS enabled. Related: https://github.com/microsoft/vscode/issues/317789 (shell integration parity) touches the same addon but not this specific double-parse question.
- **Open decisions:**
  - Should the serializer be skipped entirely when persistence is off (losing reload/revive-from-pty-host, falling back to renderer-side restore), or should raw output be buffered and parsed lazily only when a serialization/replay is actually requested?
  - If the serializer is skipped, does the ShellIntegrationAddon it hosts need an independent, lighter-weight path, or can shell integration tolerate not running through this instance when persistence is off?
