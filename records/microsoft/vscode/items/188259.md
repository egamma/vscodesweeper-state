# Issue #188259 — Allow contributing to the context menu in the TreeView's empty space 

[https://github.com/microsoft/vscode/issues/188259](https://github.com/microsoft/vscode/issues/188259)

## Summary

The requested extension contribution point is still missing: current TreeView code ignores context-menu events without an item. Keep this accepted Backlog request open; its 27 upvotes exceed the community threshold, and the title-menu workaround does not cover the requested interaction.

## Change summary

Allow extensions to contribute commands to the context menu opened on blank space below a TreeView's items.

## Best solution

Provide a supported, view-scoped menu contribution for TreeView blank space, with an explicit command-argument contract and no changes to existing item-context behavior. Settle that extension-facing contract before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/views/treeView.ts`, `src/vs/workbench/services/actions/common/menusExtensionPoint.ts`, `src/vs/platform/actions/common/actions.ts`
- **Validation:** Use a development extension with a populated TreeView and a view-scoped initialization command. Right-click the blank area below the nodes and verify the contributed command appears, executes with the agreed view-level arguments, and is absent from unrelated views. Verify existing item menus, item arguments, and multi-selection actions remain unchanged.
- **Behavior:**

  > Extension authors can expose initialization or add-node commands when users right-click blank space below a TreeView's nodes. Contributions are scoped to the intended view and do not require an artificial tree item. Acceptance requires the command to appear and execute from that blank-space menu while existing item-context and title-menu behavior remains unchanged.
- **Trace:**

  > In src/vs/workbench/browser/parts/views/treeView.ts, onContextMenu exits when treeEvent.element is null, so blank-space events never reach menu action construction. TreeMenus.getResourceContextActions and getActions operate on tree items, and the existing invocation context includes a clicked item handle. src/vs/workbench/services/actions/common/menusExtensionPoint.ts exposes view/title and view/item/context, which explain both the reported limitation and the title-menu workaround. The gap is directly visible in source; no runtime execution was performed. Preserve existing item selection, multi-selection, context keys, and command arguments. https://github.com/Ariubilig/CustomFileOrder/pull/7 supplies a concrete downstream example of the workaround rather than a fix. The remaining uncertainty is the public contribution and invocation contract, not whether the requested interaction is currently supported.
- **Open decisions:**
  - Should blank-space actions use a distinct view-level menu contribution point, or should view/item/context acquire a documented no-item invocation mode?
  - What documented command arguments and context keys should identify a blank-space invocation without implying a clicked or previously selected tree item?
