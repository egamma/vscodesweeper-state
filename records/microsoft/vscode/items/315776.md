# Issue #315776 — Can extensions detect that they are running in the agents window

[https://github.com/microsoft/vscode/issues/315776](https://github.com/microsoft/vscode/issues/315776)

## Summary

The public API gap remains on current main: VS Code exposes the requested boolean only through a gated proposed API, and a maintainer confirmed that the extension contract is still undecided. Keep this Backlog request open under discussion rather than treating the existing built-in-only capability as completion.

## Change summary

Allow ordinary extensions to detect when they are executing inside an Agents Window so they can suppress inappropriate notifications and prompts.

## Best solution

Settle the public extension contract for identifying an Agents Window, then either finalize the existing read-only workspace boolean or expose an equally reliable supported signal without expanding this issue into broader session-lifecycle observation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.agentSessionsWorkspace.d.ts`, `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `extensions/vscode-api-tests/src/singlefolder-tests/workspace.test.ts`
- **Validation:** Add extension API coverage that reads the supported workspace signal in both a normal workbench window and an Agents Window, asserting false and true respectively, while retaining coverage that unauthorized extensions cannot use any API left proposed.
- **Behavior:**

  > An ordinary extension can use a supported API to determine whether its extension host belongs to an Agents Window. The signal is true in an Agents Window and false in a normal VS Code window, allowing extensions to suppress UI that is inappropriate for the agent-focused environment. The result must be available early enough for activation-time notification and prompt decisions.
- **Trace:**

  > The requested state already reaches the extension host as `initData.environment.isSessionsWindow`. src/vs/workbench/api/common/extHost.api.impl.ts exposes it through `workspace.isAgentSessionsWorkspace`, but calls `checkProposedApiEnabled`, and the declaration exists only in src/vscode-dts/vscode.proposed.agentSessionsWorkspace.d.ts. Built-in consumers such as the Git extension opt into `agentSessionsWorkspace` through `enabledApiProposals`, so this does not satisfy ordinary extensions. The uncertainty begins at the public contract: whether a durable window-identity boolean should be finalized or whether extensions should receive a narrower supported capability signal. Keep broader agent-session lifecycle observation from https://github.com/microsoft/vscode/issues/325507 outside this issue's scope.
- **Open decisions:**
  - Should the stable contract expose Agents Window identity directly, or expose a narrower capability intended specifically for extensions deciding whether to present notifications and prompts?

## Evidence

- **current proposed API:** src/vscode-dts/vscode.proposed.agentSessionsWorkspace.d.ts declares `workspace.isAgentSessionsWorkspace`, while src/vs/workbench/api/common/extHost.api.impl.ts guards access with `checkProposedApiEnabled(extension, 'agentSessionsWorkspace')`; the property is absent from the stable src/vscode-dts/vscode.d.ts API.
