# Issue #337005 — Agents WSL: sandbox toggle shows off when session inherits an enabled remote host default

[https://github.com/microsoft/vscode/issues/337005](https://github.com/microsoft/vscode/issues/337005)

## Summary

Well-diagnosed report from a team member with debugger evidence and an exact code citation; confirmed on main that the sandbox toggle's fallback for an inherited/default session selection reads the local renderer configuration instead of the connected host's effective sandbox setting.

## Change summary

In the Agents window, the Sandboxing-for-terminal toggle shows off for a WSL-connected session left at the default/inherited sandbox selection, even though the WSL host's own config has sandboxing on and it is actually enforced.

## Best solution

Have `AgentHostPermissionPickerDelegate.getSandboxToggle`/`sandboxToggleSettingId` resolve the fallback ('globalEnabled') from the connected agent host's own effective sandbox configuration when the session selection is default, rather than from the local `_configurationService`, so the picker matches the terminal engine's actual `isEnabled()` state.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/providers/agentHost/browser/agentHostPermissionPickerDelegate.ts`, `src/vs/platform/agentHost/browser/agentHostSandboxToggle.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/agentHostSettingsShared.ts`
- **Validation:** A test asserting that when a WSL/remote-connected session's SandboxEnabled config is left at 'default' and the connected host's own sandbox setting is 'on', getSandboxToggle() reports checked === true (matching the terminal engine's isEnabled()).
- **Behavior:**

  > When an agent-host session's sandbox selection is left at default (inherited), the Sandboxing-for-terminal toggle and its permissions label must reflect the connected host's actual effective sandbox setting, not the local VS Code user/workspace setting. Explicit per-session on/off selections are unaffected and already display correctly. Acceptance: with a host config of sandbox.enabled = 'on' and local chat.agent.sandbox.enabled = false, a session left at 'default' shows the toggle on and the label includes the sandboxed qualifier; toggling explicit on/off continues to work as today.
- **Trace:**

  > getSandboxToggle() in src/vs/sessions/contrib/providers/agentHost/browser/agentHostPermissionPickerDelegate.ts (lines 222-236) builds `globalEnabled` from `this._configurationService.getValue(settingId)`, which only ever resolves the local renderer's configuration, never the connected agent host's own settings; agentHostSandboxToggle.ts folds this into `checked` as the fallback when `sessionEnabled` is undefined (default). The per-host settings surface in agentHostSettingsShared.ts/agentHostConfigEditor.ts is document/filesystem-provider oriented (JSONC editor backing), not a ready-made synchronous 'effective value' getter, so the boundary/uncertainty is exactly how to obtain a live, host-scoped sandbox value here without introducing async complexity into this synchronous getter — that's the open design question. Do not touch explicit on/off session selection handling, which already works. Related: https://github.com/microsoft/vscode/issues/336970 (the PR/issue this report is testing against).
- **Open decisions:**
  - Should the picker synchronously read a locally cached copy of the host's resolved sandbox config (kept up to date via a subscription/observable), or should getSandboxToggle become async/reactive to fetch the host value on demand — i.e., what is the right place to store/refresh the host-scoped effective sandbox setting?
  - Should this also cover other sandbox-related fallbacks (e.g., Windows-specific setting id) the same way, or is the fix scoped only to the default/inherited toggle display?

## Evidence

- **cited root cause:** src/vs/sessions/contrib/providers/agentHost/browser/agentHostPermissionPickerDelegate.ts:222-236 getSandboxToggle() computes globalEnabled via `this._configurationService.getValue<AgentSandboxEnabledSettingValue>(settingId)` (line 231), which is the local renderer's configuration service — verified in the checkout, matching the reporter's link to the same lines at commit c0f6c8c.
- **toggle formula:** src/vs/platform/agentHost/browser/agentHostSandboxToggle.ts line 24: `checked: disabled || (state.sessionEnabled ?? (state.managedEnabled || state.globalEnabled))` — when sessionEnabled is undefined (default/inherited), the toggle falls through to the local globalEnabled value, not anything host-scoped.
- **no host-scoped config path found:** No getter on IAgentHostSessionsProvider/agentHostSettingsShared.ts surfaced a synchronous, effective host-side sandbox value alongside session config; the per-host settings editor infra (agentHostSettingsShared.ts, agentHostConfigEditor.ts) is file-system/JSONC-document oriented rather than a live effective-value read, so the correct fix path (sync cache vs on-demand resolution) needs a maintainer/architecture look before implementation.
