# Issue #335581 — Agent Host WorkIQ MCP remains Running after XAA assertion expires

[https://github.com/microsoft/vscode/issues/335581](https://github.com/microsoft/vscode/issues/335581)

## Summary

Confirmed on main: the SDK-side MCP auth resolution drops the token's expiry, and the MCP UI maps `Ready` straight to Running with no separate stale-but-connected state, so an expired enterprise assertion leaves the server looking healthy with no sign-in affordance. A related second reporter (samvallad33) corroborates the same symptom. Well-diagnosed but needs a maintainer decision on how expiry/failure should propagate before implementation.

## Change summary

WorkIQ MCP servers keep showing as Running/enabled after their enterprise-managed (XAA) auth assertion expires, instead of transitioning to AuthRequired with a sign-in action.

## Best solution

Propagate `expiresIn` through `resolveMcpAuthentication` so the SDK can schedule proactive renewal, and/or map an OBO/tool-call auth failure to an `AuthRequired` transition (or a new stale-but-connected UI state) in the MCP management widget, likely coordinating with the refresh-token XAA work in #330983.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts`
- **Validation:** An Agent Host integration test with a short-lived enterprise-managed MCP credential asserting: expiry triggers proactive refresh or an AuthRequired transition, and the management UI stops reporting Running while auth is unusable.
- **Trace:**

  > Root cause has two parts confirmed from source: (1) `resolveMcpAuthentication` in copilotAgentSession.ts discards the `expiresIn` value computed in agentHostAuth.ts, so the SDK-side MCP connection cannot schedule proactive renewal; (2) an OBO/tool-call auth failure surfaces as a tool result rather than an OAuth transport challenge, so `mcp.oauth_required` is never emitted and the server's last `Ready` status (mapped to 'Running' in mcpListWidget.ts) never changes. Do not touch unrelated XAA reminting logic (#330983) or GitHub credential refresh (#334418) — those are prior art/related, not in scope for this fix.
- **Open decisions:**
  - Should expiry propagation drive proactive silent refresh, or should it force a status transition to AuthRequired when refresh isn't possible?
  - Should a tool-call auth failure (not just a transport challenge) directly trigger `AuthRequired`, or should the UI add a distinct 'stale/needs reauth' state instead of overloading Running/AuthRequired?

## Evidence

- **expiry dropped on resolve:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts:509 computes `expiresIn` from `session.expiresAfter` and forwards it in `IAgentHostAuthenticateRequest`, but `CopilotAgentSession.resolveMcpAuthentication` in src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:2633-2651 only responds with `{ kind: 'token', accessToken: params.token }` — no expiry is passed to the SDK.
