# Issue #335581 — Agent Host WorkIQ MCP remains Running after XAA assertion expires

[https://github.com/microsoft/vscode/issues/335581](https://github.com/microsoft/vscode/issues/335581)

## Summary

Confirmed on current main: `CopilotAgentSession.resolveMcpAuthentication` still resolves pending MCP auth with only `{ kind: 'token', accessToken }` (copilotAgentSession.ts:2695), dropping the `expiresIn` that `AuthenticateParams` already carries, and the MCP list widget still maps `McpServerStatus.Ready` straight to Running with no distinction for a stale/expired credential. No commit references this issue and nothing has landed since the prior review kept it open.

## Change summary

Enterprise-managed (XAA) WorkIQ MCP servers keep showing as Running with no sign-in affordance after their assertion expires, because expiry isn't propagated to the SDK and a tool-call auth failure never triggers an AuthRequired transition.

## Best solution

This needs a maintainer/agent-host design pass: decide whether the SDK's MCP token-result shape can carry `expiresIn` for proactive renewal (mirroring the GitHub credential prior art in #334418), and whether/how an OBO tool-result auth failure should force an `AuthRequired` transition and UI update in mcpListWidget.ts — then implement across copilotAgentSession.ts, agentHostAuth.ts, and the widget.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts`
- **Validation:** An Agent Host integration test with a deliberately short-lived enterprise-managed MCP credential asserting: (1) expiry causes proactive refresh or an AuthRequired transition, (2) the management UI stops reporting Running while auth is unusable, (3) a retried tool call succeeds after refresh.
- **Behavior:**

  > When a WorkIQ/XAA-authenticated MCP server's credential expires, VS Code should either refresh it proactively before expiry or transition the server to AuthRequired with an actionable sign-in control — it must never continue showing as Running/healthy once tool calls are failing solely due to an expired assertion. A retried tool call after sign-in should succeed.
- **Trace:**

  > resolveMcpAuthentication (copilotAgentSession.ts:2682-2699) resolves pending SDK auth callbacks with `{ kind: 'token', accessToken: params.token }` only, dropping `params.expiresIn` even though `AuthenticateParams` already carries it (agent.ts:319-333) and the GitHub credential path already threads `expiresIn` through an equivalent token result (copilotGitHubCredentials.ts:100). Separately, an OBO/tool-execution auth failure (e.g. AADSTS500133) never triggers `mcp.oauth_required`, so the transport-level Ready status never flips, and mcpListWidget.ts:772-778 renders Ready as Running unconditionally. Boundary: do not touch unrelated auth flows (GitHub token provider, non-MCP OAuth) or restructure the pending-request registry; the fix is scoped to MCP token-expiry propagation and the Ready→AuthRequired transition path. Related: https://github.com/microsoft/vscode/issues/330983, https://github.com/microsoft/vscode/issues/334418.
- **Open decisions:**
  - Does the SDK's MCP token-result type (McpAuthResult / the SDK's onMcpAuthRequest handler) actually support an `expiresIn`-like field for proactive renewal, or does that require an upstream SDK change first?
  - Should a tool-call auth failure (e.g. AADSTS500133) synthesize a local AuthRequired transition even without an `mcp.oauth_required` signal from the transport, and if so what heuristic identifies such failures?
  - Should the MCP list widget introduce an intermediate 'stale/needs re-auth' visual state distinct from both Running and AuthRequired, or reuse AuthRequired directly?
