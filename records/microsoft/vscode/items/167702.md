# Issue #167702 — Proper fix for line endings

[https://github.com/microsoft/vscode/issues/167702](https://github.com/microsoft/vscode/issues/167702)

## Summary

Keep open: this accepted Backlog feature request reached the 20-upvote promotion threshold, and automatically normalizing CR+CR+LF remains a product decision because that sequence can represent intentional line breaks as well as FTP corruption.

## Change summary

Detect CR+CR+LF while opening a file and normalize it to a single LF or CRLF instead of displaying an extra blank line.

## Best solution

Define a non-destructive editor behavior for malformed or unusual newline sequences, likely through explicit detection and an opt-in normalization action rather than unconditional mutation during file loading.

- **Behavior:**

  > Files containing CR+CR+LF should offer a safe way to recover from the extra CR introduced by broken ASCII-mode FTP transfers without silently corrupting intentional content. The selected behavior must define whether detection is automatic or opt-in and whether recovery produces LF or CRLF. Existing handling of ordinary LF, CRLF, CR, and mixed-EOL files must remain unchanged.
- **Trace:**

  > The report identifies the editor text-buffer ingestion and EOL interpretation path: CR+CR+LF is currently interpreted as two line terminators, producing blank lines. The likely boundary is text-buffer construction and line-ending normalization under src/vs/editor/common/model and its piece-tree builder; source-level behavior was not conclusive enough here to prescribe an implementation. Do not make FTP-specific assumptions in the generic text model or silently rewrite ambiguous byte sequences until the product behavior is settled. https://github.com/microsoft/vscode/issues/127 is related to line-ending preservation but does not cover repair of CR+CR+LF.
- **Open decisions:**
  - Should VS Code repair CR+CR+LF automatically on load, surface a warning with an explicit normalization action, or expose an opt-in setting?
