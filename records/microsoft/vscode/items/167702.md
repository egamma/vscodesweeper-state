# Issue #167702 — Proper fix for line endings

[https://github.com/microsoft/vscode/issues/167702](https://github.com/microsoft/vscode/issues/167702)

## Summary

This remains valid backlog work with 20 community upvotes: current main intentionally parses `CR CR LF` as two line endings, and no existing setting repairs that malformed sequence. The request is distinct from the broader mixed-EOL preservation work in https://github.com/microsoft/vscode/issues/127.

## Change summary

Recognize files corrupted by FTP ASCII-mode conversion from `CR LF` to `CR CR LF` and avoid displaying and saving an extra blank line for every source line.

## Best solution

Define a safe text-buffer policy for detecting and repairing systematic `CR CR LF` corruption without changing legitimate standalone-CR or mixed-line-ending files. The maintainer decision should cover whether repair is automatic, opt-in, or presented as an explicit normalization action.

## Plan brief

- **Likely files:** `src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeBase.ts`, `src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeTextBufferBuilder.ts`, `src/vs/editor/test/common/model/pieceTreeTextBuffer/pieceTreeTextBuffer.test.ts`
- **Validation:** Add targeted piece-tree text-buffer tests for loading `a\r\r\nb\r\r\n`, including chunk boundaries, and verify the agreed repair behavior while standalone-CR, CRLF, LF, and genuinely mixed-EOL cases retain their specified semantics.
- **Behavior:**

  > A text file systematically corrupted from CRLF to `CR CR LF` should be recoverable without displaying or saving an extra blank line after every content line. Legitimate files containing standalone CR or genuinely mixed line endings must not be silently damaged. Acceptance should cover opening, editing, and serializing the malformed input, plus unchanged behavior for ordinary LF, CRLF, and intentional CR cases.
- **Trace:**

  > On current main, `createLineStarts` in src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeBase.ts classifies the first CR in `CR CR LF` as a standalone line ending and the second CR plus LF as CRLF. `PieceTreeTextBufferFactory.create` in src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeTextBufferBuilder.ts then normalizes both detected endings independently, preserving the extra logical line. Existing piece-tree tests cover CR and CRLF operations but do not establish repair semantics for systematic `CR CR LF` input. The boundary is text-buffer ingestion and normalization; ordinary CR-only and mixed-EOL behavior must not change accidentally. https://github.com/microsoft/vscode/issues/127 concerns preserving mixed endings and does not define whether this malformed sequence should be repaired.
- **Open decisions:**
  - Should systematic `CR CR LF` input be repaired automatically, require an opt-in setting, or prompt through an explicit normalization action?
  - What detection threshold distinguishes FTP-induced corruption from intentional standalone CR followed by CRLF?
  - Should repair apply during decoding/text-buffer creation or only through a user-invoked file normalization operation?

## Evidence

- **current source behavior:** src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeBase.ts:createLineStarts treats a carriage return not immediately followed by LF as one line ending and the following CRLF as another, so `\r\r\n` produces two lines on current main.
- **normalization path:** src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeTextBufferBuilder.ts:PieceTreeTextBufferFactory normalizes each detected `\r`, `\n`, or `\r\n` independently to the selected model EOL; it has no malformed-`CR CR LF` repair path.
