# Issue #7536 — Implement editor undo stack serialization

[https://github.com/microsoft/vscode/issues/7536](https://github.com/microsoft/vscode/issues/7536)

## Summary

Keep open: individual edit records have binary serialization, but complete editor undo/redo stacks remain in memory rather than being recoverable across sessions. The maintainer explicitly distinguished these capabilities; this accepted Backlog request has 20 upvotes, and the verified related persistence requests are newer, not eligible duplicate targets for this re-reviewed item.

## Change summary

Support serializing and subsequently restoring a model's complete undo/redo history independently of its original in-memory lifetime.

## Best solution

Provide a restorable editor-history representation that preserves undo/redo ordering and rejects restoration against incompatible model contents. Coordinate its persistence contract with the hot-exit consumer tracked in https://github.com/microsoft/vscode/issues/15135, without treating in-memory edit-record serialization as completion.

## Plan brief

- **Likely files:** `src/vs/editor/common/model/editStack.ts`, `src/vs/editor/common/services/modelService.ts`, `src/vs/platform/undoRedo/common/undoRedo.ts`, `src/vs/platform/undoRedo/common/undoRedoService.ts`, `src/vs/editor/test/common/model/editStack.test.ts`, `src/vs/editor/test/common/services/modelService.test.ts`
- **Validation:** Extend the editStack/modelService tests with a history round trip into fresh service/model instances: make multiple edits, undo one, export/import the history, then verify both undo and redo, selections, EOL, and rejection of mismatched contents. If durable persistence is included, additionally verify edit/save, quit, restart, reopen, undo, and redo without retaining the original service objects.
- **Behavior:**

  > Editor history must be serializable and restorable without depending on the original live model or undo service. Restoring matching model contents should preserve both undo and redo history, their ordering, cursor state, and line-ending behavior. Existing in-session file reopening must continue to work. Acceptance must distinguish an independent history round trip from merely keeping existing elements in memory; restart persistence is an additional check if included in the agreed scope.
- **Trace:**

  > SingleModelEditStackData in src/vs/editor/common/model/editStack.ts already serializes individual edit payloads, but SingleModelEditStackElement retains their owning element and model association. ModelService._onWillDispose() in src/vs/editor/common/services/modelService.ts leaves history in UndoRedoService and stores hash/version metadata in _disposedModels; _createModelData() restores references only from those retained objects. ResourceEditStackSnapshot in src/vs/platform/undoRedo/common/undoRedo.ts contains element IDs, not edit contents, while UndoRedoService also tracks resource/workspace elements and group/source ordering. The remaining uncertainty is the complete history contract and its durable consumer, not the existence of a binary edit codec. Preserve content-compatibility checks and existing in-memory reopen behavior; do not assume arbitrary workspace undo callbacks can be serialized. https://github.com/microsoft/vscode/issues/15135 explicitly depends on this issue for hot-exit persistence.
- **Open decisions:**
  - Does this issue deliver a complete export/import history contract for consumers, or also durable storage and automatic restoration across VS Code sessions?
  - Does the initial contract support only independent text-model history, or also shared multi-resource edit groups, and what observable restoration behavior applies when such a group contains unsupported undo elements?
