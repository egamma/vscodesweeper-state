# Issue #23107 — Allow to configure editor auto reload behaviour

[https://github.com/microsoft/vscode/issues/23107](https://github.com/microsoft/vscode/issues/23107)

## Summary

Keep open: current source still automatically reloads clean text files while protecting dirty buffers, without the requested reload policy. The maintainer explicitly reopened this request and endorsed retaining declined external changes as dirty buffers; 69 upvotes support planning the remaining product choices.

## Change summary

Allow users to configure whether external file changes automatically replace editor contents, require confirmation, or leave the existing buffer intact.

## Best solution

Provide an explicit external-change policy in the text-file editor lifecycle, preserving current defaults and making retained buffers visibly dirty as the maintainer requested. Decide the supported modes and their interaction with auto-save and save-conflict settings before implementation.

- **Validation:** Extend the text-file model manager and model suites with simulated external updates: current defaults still reload clean buffers and preserve dirty buffers; a chosen retention mode preserves the old content and marks it dirty; confirmation mode follows the user's decision; subsequent saves and auto-save honor the agreed conflict policy. Manually verify the same scenarios with a file changed by another process and with a Git branch checkout.
- **Behavior:**

  > Users currently cannot choose how an open text editor reacts when its file changes externally. The requested capability should let users retain the existing buffer or explicitly accept replacement rather than always silently replacing clean buffers. Retaining content that differs from disk must make the editor dirty, as established by the maintainer. Acceptance must cover clean and already-dirty editors, external updates during auto-save, and subsequent save conflicts; existing defaults remain unchanged unless a maintainer explicitly chooses otherwise.
- **Trace:**

  > TextFileEditorModelManager.onDidFilesChange in src/vs/workbench/services/textfile/common/textFileEditorModelManager.ts queues reloads for clean models and ignores dirty models; reload rechecks that boundary before resolving. TextFileEditorModel.resolve in src/vs/workbench/services/textfile/common/textFileEditorModel.ts independently prevents disk resolution while dirty or saving. Save writes use lastResolvedFileStat.etag unless files.saveConflictResolution or explicit save options disable conflict checking. The existing file-change tests in src/vs/workbench/services/textfile/test/browser/textFileEditorModelManager.test.ts provide a starting harness. The maintainer settled dirty marking for retained divergent buffers at https://github.com/microsoft/vscode/issues/23107#issuecomment-1342190516 and endorsed existing conflict protection at https://github.com/microsoft/vscode/issues/23107#issuecomment-1342857869. What remains unsettled is the user-facing policy set, whether replacement of already-dirty buffers is supported, and how retention interacts with explicit overwrite-on-save configuration. This is a policy request, not evidence that current dirty-buffer protection is broken; unrelated log-tailing and notebook-watcher behavior remain outside this scope.
- **Open decisions:**
  - Which modes should be supported: automatic reload of clean buffers, confirmation, and retention only, or also explicit replacement of already-dirty buffers and backup-before-replacement?
  - When a retained buffer becomes dirty because disk content changed, should auto-save follow the existing saveConflictResolution setting even when overwriteFileOnDisk is configured, or require explicit acceptance before overwriting the external version?
  - Should the policy apply globally or support resource-level overrides, and should external deletion follow the same retention and confirmation behavior?

## Evidence

- **Current reload behavior:** src/vs/workbench/services/textfile/common/textFileEditorModelManager.ts:122–136 skips dirty models but queues clean models for reload on UPDATED or ADDED events. Its reload method at lines 338–350 rechecks dirty state and resolves from disk without a reload-policy choice.
- **Existing capabilities do not cover the request:** src/vs/workbench/contrib/files/browser/files.contribution.ts registers files.watcherExclude and files.saveConflictResolution, but neither provides confirmation or configurable buffer retention on external changes. files.saveConflictResolution selects askUser or overwriteFileOnDisk when saving, which is the opposite direction from reloading disk contents. The registered workbench.action.files.revert command provides manual reloading, not an external-change policy.
- **Maintainer direction after reopening:** https://github.com/microsoft/vscode/issues/23107#issuecomment-1342190516 explicitly reopens the request and says declining an external reload must make the buffer dirty. https://github.com/microsoft/vscode/issues/23107#issuecomment-1342857869 states that normal save-conflict prevention should protect the disk version, including during auto-save.

Lines 938–940 retain the last resolved etag unless conflict checking is explicitly disabled.
