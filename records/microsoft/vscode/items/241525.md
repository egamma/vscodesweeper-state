# Issue #241525 — Feature request: Fuzzy search files including file path

[https://github.com/microsoft/vscode/issues/241525](https://github.com/microsoft/vscode/issues/241525)

## Summary

Keep this accepted, 33-upvote request open: Quick Open already supports path matching and space-separated terms, but that does not establish that discovery is reliable in the reporter's large-workspace case. The older ranking discussion overlaps, but does not clearly own the reported difference between discovering unopened files and finding previously opened files.

## Change summary

Make Quick Open reliably discover files using directory names and multiple path fragments, without requiring the filename or prior access to the file.

## Best solution

Establish where unopened-file candidates disappear in a large workspace, then make path-based discovery reliable without sacrificing Quick Open responsiveness. Coordinate any ranking changes with https://github.com/microsoft/vscode/issues/25925 while retaining this report's distinct discovery concern.

Record target inclusion separately from ranking and compare cold versus warm search state.
- **Behavior:**

  > Users should be able to discover files through directory names and multiple path fragments without first opening those files or knowing their filenames. The report specifically expects components button to find both src/components/button.tsx and src/components/fancy/button.tsx, and components alone to discover files beneath that directory. Establish this behavior in a large synthetic workspace, distinguishing missing results from results that rank poorly. Existing filename navigation and interactive responsiveness must remain intact.
- **Trace:**

  > AnythingQuickAccessProvider.getFileSearchResults in src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts searches the first query term and, on a limit hit, additionally searches the original query; doGetFileSearchResults caps each request at 512 results. File discovery already matches relative paths through isFilePatternMatch in src/vs/workbench/services/search/common/search.ts, while src/vs/base/common/fuzzyScorer.ts independently scores multiple terms and normally prefers filename matches unless the query contains a path separator. These establish existing capability, not the cause of the reporter's missing unopened files. The uncertainty starts at candidate generation, truncation, exclusions, and history/cache differences in a large workspace; reproduce those distinctions before choosing a change. Preserve existing filename-search behavior and do not treat a global ranking rewrite as a prerequisite. https://github.com/microsoft/vscode/issues/25925 owns related ranking discussion but has not been verified to absorb the discovery symptom.

Therefore neither directory matching nor multiple-term matching is wholly absent.
- **Candidate generation needs investigation:** src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts:getFileSearchResults initially searches only the first term, then searches the full original query when that search hits its limit. doGetFileSearchResults requests at most MAX_RESULTS = 512 with sortByScore enabled. This is a concrete path to investigate for large-workspace omissions, not proof that it causes this report.
