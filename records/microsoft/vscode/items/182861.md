# Issue #182861 — Merge Editor overrides manually resolved conflicts

[https://github.com/microsoft/vscode/issues/182861](https://github.com/microsoft/vscode/issues/182861)

## Summary

Keep open: current initialization still replaces partially resolved content when any conflict marker remains. Historical maintainer discussion describes re-merging as intentional, so preserving manual resolutions needs an enhancement rather than a decline close against this accepted Backlog item.

## Change summary

Preserve saved manual conflict resolutions when opening the merge editor to resolve the remaining conflicts.

## Best solution

Support continuing a partially completed merge without replacing previously resolved text. Preserve the existing automatic merge capability, with the merge-editor owner deciding how it applies to the remaining marked conflicts.

Add initialization regression coverage and run the merge editor model suite with scripts/test.sh --run src/vs/workbench/contrib/mergeEditor/test/browser/model.test.ts.
- **Behavior:**

  > A user can resolve and save some conflicts in the normal editor, then continue in the merge editor without losing that work. Previously resolved text must survive, including custom resolutions matching neither branch. Remaining conflicts must still be resolvable, and accepting the merge must retain both the earlier and later resolutions. Marker-free results and ordinary untouched conflicted files must continue to work.
- **Trace:**

  > Commands.openMergeEditor in extensions/git/src/commands.ts supplies original Git inputs and the workspace result. WorkspaceMergeEditorModeFactory.createInputModel in src/vs/workbench/contrib/mergeEditor/browser/mergeEditorInputModel.ts treats any remaining opening conflict marker as grounds to reset the whole result. MergeEditorModel.initialize/reset in src/vs/workbench/contrib/mergeEditor/browser/model/mergeEditorModel.ts regenerates it solely from the original inputs, explaining why saved resolutions disappear. The temporary-result factory also initializes from an empty model with resetResult true. Historical intent is documented at https://github.com/microsoft/vscode/issues/162112#issuecomment-1262154016; restoration after aborting is separate work at https://github.com/microsoft/vscode/issues/161560. The design uncertainty is how remaining marked conflicts interact with automatic re-merging while preserving completed resolutions. Keep save/revert/undo behavior, Git input selection, and explicit Reset semantics outside the requested change unless preservation demonstrably requires otherwise.
- **Open decisions:**
  - For a partially resolved file, should remaining Git-marked conflicts still receive VS Code's automatic re-merge treatment, or remain unresolved until the user explicitly handles them?

## Evidence

- **Report and subsequent confirmation:** https://github.com/microsoft/vscode/issues/182861 describes resolving and saving some conflicts in the normal editor, then finding those resolutions replaced after opening the merge editor. The reporter confirmed the same problem on 1.95.1 on December 3, 2024; the original report also says it occurs with extensions disabled.
- **Current opening path:** extensions/git/src/commands.ts, Commands.openMergeEditor, passes the Git base/current/incoming versions and workspace output URI to _open.mergeEditor. src/vs/workbench/contrib/mergeEditor/browser/mergeEditorInput.ts selects WorkspaceMergeEditorModeFactory when mergeEditor.useWorkingCopy is false or absent.
- **Whole-result reset remains:** In src/vs/workbench/contrib/mergeEditor/browser/mergeEditorInputModel.ts, WorkspaceMergeEditorModeFactory.createInputModel saves the result, checks whether any line starts with conflictMarkers.start, and sets resetResult to that boolean. In src/vs/workbench/contrib/mergeEditor/browser/model/mergeEditorModel.ts, initialize calls reset, which replaces the entire result with computeAutoMergedResult(). That computation reads only base/input1/input2, not the saved partial result. Thus one remaining marker triggers replacement of previously resolved regions; marker-free results take the non-reset path.
- **Intent and classification:** https://github.com/microsoft/vscode/issues/162112#issuecomment-1262154016 explicitly describes the merge editor as re-merging with the original Git inputs. That supports classifying preservation as an enhancement to existing intentional behavior. The issue under review nevertheless carries bug and Backlog, so a judgment close would contradict its accepted triage.

Neither owns preservation of saved resolutions on initial opening, and the re-reviewed-item duplicate bar is not met.
