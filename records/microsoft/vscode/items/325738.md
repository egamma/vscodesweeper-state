# Issue #325738 — Agents Window over SSH: BYOK (custom model providers) unsupported + agent-host version mismatch blocks usage

[https://github.com/microsoft/vscode/issues/325738](https://github.com/microsoft/vscode/issues/325738)

## Summary

Still a real gap on current main: the agent-host server entrypoint used for remote hosts constructs its runtime with `byok: { kind: 'unavailable' }`, so BYOK/custom-provider models cannot run in SSH agent sessions — a maintainer confirmed this in the thread, the request has 28 upvotes and now sits in Backlog, so it stays open.

## Change summary

Bring BYOK/custom model provider parity (plus agent-host version pinning and a lower barrier for enabling provider extensions) to Agents Window sessions running over SSH.

## Best solution

Thread the renderer-side BYOK LM bridge (IByokLmBridgeRegistry / ByokLmProxyService, today only wired in src/vs/platform/agentHost/node/agentHostMain.ts) through the remote agent-host connection so src/vs/platform/agentHost/node/agentHostServerMain.ts can serve BYOK models, and pin the downloaded remote agent-host build to the client commit the way Remote-SSH/WSL do; the extension allow-listing barrier (`extensions.supportAgentsWindow`) is a separate, smaller UX follow-up.

- **Behavior:**

  > With `chat.agentHost.byokModels.enabled`, a user running an Agents Window session over SSH can select and use the same BYOK/custom-provider models that already work for a local agent session, and the remote agent-host build matches the client so the session connects instead of failing with a protocol-version mismatch. Acceptance: the model picker in an SSH agent session lists bridged BYOK models, a prompt completes through them, and Copilot-model sessions are unchanged.
- **Trace:**

  > BYOK in agent-host sessions is served by a renderer-side bridge: src/vs/platform/agentHost/node/agentHostMain.ts:132 passes `byok: { kind: 'renderer', bridgeRegistry: byokLmBridgeRegistry }`, while the server entrypoint used for remote hosts, src/vs/platform/agentHost/node/agentHostServerMain.ts:203, passes `byok: { kind: 'unavailable' }`, which makes agentHostServices.ts install NullByokLmProxyService and AgentHostUtilityModelService without BYOK support. A maintainer confirmed the gap in the thread; https://github.com/microsoft/vscode/pull/327105 only added an Auto fallback. The boundary: do not change the local-agent BYOK path or the Copilot catalog behavior, and keep the agent-host protocol interoperable with non-VS Code hosts (see .github/instructions/agent-host-interoperability.instructions.md). Uncertainty starts at how (and whether) the LM bridge should traverse the remote connection, and whether the version-pinning and extension-allow-listing asks are tracked here or split out; related reports: https://github.com/microsoft/vscode/issues/332085, https://github.com/microsoft/vscode/issues/333016, https://github.com/microsoft/vscode/issues/333802.
- **Open decisions:**
  - Should remote agent-host sessions proxy BYOK model calls back to the local renderer over the agent-host connection, or should the remote host hold provider credentials/endpoints itself?
  - Does the remote agent-host download pin to the client's exact commit (as Remote-SSH/WSL do) rather than the channel-latest server build?
  - Do the version-mismatch and `extensions.supportAgentsWindow` allow-listing asks stay in this issue, or move to separate issues so this one tracks BYOK parity only?
