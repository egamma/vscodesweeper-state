# Issue #227484 — Custom controls need to provide proper textual name, role, and state information 

[https://github.com/microsoft/vscode/issues/227484](https://github.com/microsoft/vscode/issues/227484)

## Summary

The accessibility defect remains on current main: folding controls are title-only `<div>` decorations inside an `aria-hidden` editor margin, so assistive technology cannot discover their name, role, or expanded state. The reopened issue is correctly accepted in the Backlog and should remain open for an editor-folding accessibility design.

## Change summary

Expose code-folding gutter controls with an accessible name, button role, expanded or collapsed state, and keyboard-operable behavior.

## Best solution

Represent each visible folding affordance through an accessible, keyboard-operable control or equivalent editor accessibility surface that reports its line, action, and current expanded state without exposing unrelated gutter decorations.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/folding/browser/foldingDecorations.ts`, `src/vs/editor/browser/viewParts/linesDecorations/linesDecorations.ts`, `src/vs/editor/browser/viewParts/margin/margin.ts`, `src/vs/editor/common/model.ts`, `src/vs/editor/common/model/textModel.ts`
- **Validation:** Add a browser-level editor rendering test that creates expanded and collapsed folding ranges and verifies that each exposed control has an accessible name and button role, reports the correct `aria-expanded` value before and after activation, and is keyboard operable without exposing unrelated margin decorations.
- **Behavior:**

  > A screen reader user must be able to identify each visible code-folding control as an interactive control, understand which line or range it affects, and hear whether it is expanded or collapsed. The control must be operable from the keyboard, and its state must update after activation. Mouse folding, folding commands, and unrelated gutter decorations must retain their existing behavior.
- **Trace:**

  > FoldingDecorationProvider in src/vs/editor/contrib/folding/browser/foldingDecorations.ts encodes state through separate collapsed and expanded icon classes plus mouse tooltips. LinesDecorationsOverlay in src/vs/editor/browser/viewParts/linesDecorations/linesDecorations.ts reduces those decorations to title-only `<div>` markup, while Margin in src/vs/editor/browser/viewParts/margin/margin.ts hides the entire containing subtree from assistive technology. The generic decoration types in src/vs/editor/common/model.ts and src/vs/editor/common/model/textModel.ts currently have no accessible-role or state metadata. The boundary is folding controls: unrelated line-number, glyph-margin, breakpoint, and decoration rendering must not become exposed or newly focusable.
- **Open decisions:**
  - Should folding controls become independently focusable gutter buttons, or should their action and expanded state be exposed through the editor's existing line-based accessibility model while editor focus remains in the text area?

## Evidence

- **current rendering:** src/vs/editor/browser/viewParts/linesDecorations/linesDecorations.ts renders each line decoration as a `<div>` with only class, style, and an optional `title`; it emits no role, accessible name, `aria-expanded`, or keyboard semantics.
- **hidden accessibility subtree:** src/vs/editor/browser/viewParts/margin/margin.ts sets the shared editor margin to `role="presentation"` and `aria-hidden="true"`, preventing folding-decoration descendants from appearing in the accessibility tree.
- **folding state:** src/vs/editor/contrib/folding/browser/foldingDecorations.ts distinguishes collapsed and expanded controls only through icon classes and localized mouse tooltips (`Click to expand the range.` / `Click to collapse the range.`); that state is not propagated as accessible metadata.
