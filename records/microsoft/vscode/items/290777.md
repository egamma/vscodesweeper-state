# Issue #290777 — Show disabled code actions in lightbulb/refactor menu

[https://github.com/microsoft/vscode/issues/290777](https://github.com/microsoft/vscode/issues/290777)

## Summary

A real UX gap remains on current main: filtered refactor menus can reveal disabled actions through “Show Disabled,” but lightbulb and generic code-action menus exclude them, and grouped entries do not expose the disabled reason. This needs a product decision about visibility and presentation rather than closure.

## Change summary

Let extensions make unavailable code actions discoverable in lightbulb and refactor menus, with the reason they are disabled.

## Best solution

Define a consistent code-action-menu policy that lets relevant disabled actions remain discoverable without overwhelming the primary list, and expose each disabled reason visually and to assistive technology while preserving existing execution and auto-apply semantics.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/codeAction/browser/codeActionController.ts`, `src/vs/editor/contrib/codeAction/browser/codeActionMenu.ts`, `src/vs/editor/contrib/codeAction/test/browser/codeAction.test.ts`
- **Validation:** Add editor code-action tests covering mixed enabled/disabled actions opened from the lightbulb and filtered refactor command, including the displayed and accessible disabled reason; run `scripts/test.sh --grep "CodeAction"`.
- **Behavior:**

  > Users opening the lightbulb or refactor menu should be able to discover relevant actions that are currently unavailable and understand why they are disabled. Disabled actions must remain non-executable, while enabled-action ordering, selection, preview, and auto-apply behavior remain unchanged. Acceptance must cover mixed enabled/disabled results, all-disabled results, grouped and ungrouped menus, keyboard navigation, and screen-reader access to the reason.
- **Trace:**

  > CodeActionController in src/vs/editor/contrib/codeAction/browser/codeActionController.ts passes `includeDisabledActions: false` from both `showCodeActionsFromLightbulb` and `showCodeActions`; only explicit filtered triggers set it from `filter.include`. `showCodeActionList` then selects `validActions` unless disabled actions are allowed and either `_showDisabled` is active or no valid actions exist. `toMenuItems` in src/vs/editor/contrib/codeAction/browser/codeActionMenu.ts marks entries disabled, but only the ungrouped path incorporates the disabled reason, replacing rather than supplementing the action title. The boundary is menu visibility and explanation: do not alter provider filtering, disabled-action execution, preview behavior, or auto-apply selection. The original policy is documented in https://github.com/microsoft/vscode/issues/85160, while https://github.com/microsoft/vscode/issues/145058 covers the narrower reason-presentation history.
- **Open decisions:**
  - Should returned disabled actions appear by default, behind a “Show Disabled” affordance, or only when the provider explicitly opts them into discovery?
  - Should the new policy apply equally to automatic lightbulb, generic code-action, and filtered refactor menus, or should those surfaces intentionally differ?
  - Should the disabled reason be secondary row text, a tooltip/details surface, or both, including what keyboard and screen-reader users hear?
