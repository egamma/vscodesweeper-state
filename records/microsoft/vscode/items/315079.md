# Issue #315079 — Improve communication for continuation options based on past usage

[https://github.com/microsoft/vscode/issues/315079](https://github.com/microsoft/vscode/issues/315079)

## Summary

A real product gap remains: current main offers fixed threshold actions but does not forecast exhaustion or choose the primary continuation option from usage patterns. This team-authored Backlog request is already accepted and under discussion, so it should remain open for recommendation-policy design.

## Change summary

Use past consumption, time remaining in the billing cycle, and task context to forecast credit exhaustion and prioritize the most appropriate continuation action.

## Best solution

Define a recommendation policy and required usage signals, then present a clear forecast and one contextually prioritized action while keeping all continuation options available. The design should reuse the existing quota notification and status surfaces without adding conflicting billing guidance.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chatQuotaNotification.ts`, `src/vs/workbench/contrib/chat/test/browser/chatQuotaNotification.test.ts`, `src/vs/workbench/services/chat/common/chatEntitlementService.ts`, `extensions/copilot/src/extension/chat/vscode-node/chatQuota.contribution.ts`, `extensions/copilot/src/platform/chat/common/chatQuotaService.ts`
- **Validation:** Add quota-notification tests covering representative early-cycle and late-cycle consumption scenarios, asserting the forecast text and prioritized action while confirming that all continuation options remain accessible.
- **Behavior:**

  > Users approaching or reaching their credit limit should see when their current usage rate is expected to exhaust the balance and a primary continuation action appropriate to that situation. Rapid early-cycle exhaustion should not receive the same primary recommendation as modest usage near reset, and relevant lower-cost model guidance should be offered when appropriate. Other valid continuation options must remain discoverable. Acceptance scenarios should cover early exhaustion, late-cycle exhaustion, additional budget already enabled, Auto already selected, and missing forecast data.
- **Trace:**

  > Current quota warnings are implemented by ChatQuotaNotificationContribution in src/vs/workbench/contrib/chat/browser/chatQuotaNotification.ts. The contribution detects crossings of fixed thresholds and resolves either a Manage Budget action or a treatment-gated Switch to Auto action using the current model; corresponding cases are in src/vs/workbench/contrib/chat/test/browser/chatQuotaNotification.test.ts. IQuotaSnapshot in src/vs/workbench/services/chat/common/chatEntitlementService.ts contains a point-in-time balance and reset timestamp but no usage history, while extensions/copilot/src/extension/chat/vscode-node/chatQuota.contribution.ts publishes quota snapshots from the Copilot service. The boundary is the UBB continuation experience: retain existing free-user, managed-plan, rate-limit, BYOK, and exhausted-notification behavior. https://github.com/microsoft/vscode/issues/315919 supplies the consolidated UX-study requirement; https://github.com/microsoft/vscode/issues/320135 concerns distinct optimization tips.
- **Open decisions:**
  - Which observable recommendation hierarchy should choose among upgrading, adding budget, waiting for reset, and switching models for early-cycle versus late-cycle projected exhaustion?
  - Should recommendations use only account usage rate and the selected model, or also inspect the current task or prompt to make task-specific model suggestions?
  - Should the forecast appear only when a quota threshold is crossed, remain visible in the status dashboard, or update proactively as usage changes?
