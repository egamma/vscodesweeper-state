# Issue #46471 — Expose API for variable substitution in contributed configuration

[https://github.com/microsoft/vscode/issues/46471](https://github.com/microsoft/vscode/issues/46471)

## Summary

Keep open: current source still lacks a public API for resolving variables in extension-contributed settings. The request has 104 upvotes and maintainer interest; existing task-specific support does not cover it, and related settings work leaves API and scope decisions unresolved.

## Change summary

Expose reusable variable resolution for extension-contributed configuration, with possible support for custom substitutions and allowed-variable controls.

## Best solution

Agree on an opt-in extension API that reuses VS Code's resolver without changing ordinary configuration reads or startup behavior. Decide whether predefined-variable resolution can ship independently of interactive and extension-contributed variables.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostConfiguration.ts`, `src/vs/workbench/api/common/extHostVariableResolverService.ts`, `src/vs/workbench/services/configurationResolver/common/configurationResolver.ts`, `src/vs/workbench/api/test/browser/extHostConfiguration.test.ts`, `src/vs/workbench/services/configurationResolver/test/electron-browser/configurationResolverService.test.ts`
- **Validation:** After agreeing on the API, add extension API coverage resolving ${workspaceFolder}, ${env:NAME}, and ${config:NAME} in contributed setting values, including explicit multi-root scope. Verify ordinary configuration get()/inspect() results remain unchanged and unsupported-variable behavior matches the agreed contract; extend the ExtHostConfiguration and Configuration Resolver Service suites without running them during this review.
- **Behavior:**

  > Extension authors should be able to obtain resolved contributed setting values using VS Code's supported substitution semantics rather than maintaining a parallel resolver. Ordinary configuration reads must retain their current behavior unless the caller explicitly opts in. Acceptance should cover workspace, environment, and configuration references with explicit workspace scope, plus the agreed behavior for unsupported variables. Interactive variables and extension-contributed substitutions require an explicit initial-scope decision.
- **Trace:**

  > ExtHostConfigProvider.getConfiguration() in src/vs/workbench/api/common/extHostConfiguration.ts returns raw looked-up values; the public declarations and API implementation expose no general variable-resolution entry point. Internal resolution exists in IConfigurationResolverService and ExtHostVariableResolverProviderService, with task-specific consumers in src/vs/workbench/api/node/extHostTask.ts. Public CustomExecution resolution covers task definitions only. https://github.com/microsoft/vscode/issues/81007#issuecomment-674074167 explains why the earlier general proposal returned to task-specific resolution. https://github.com/microsoft/vscode/pull/148514#issuecomment-1116218814 establishes the boundary against automatic configuration-layer expansion and startup work. Coordinate API design with https://github.com/microsoft/vscode/issues/140056 and broader settings semantics with https://github.com/microsoft/vscode/issues/2809; neither establishes that this full request is complete.
- **Open decisions:**
  - Should the initial API resolve only predefined, noninteractive variables, or also command/input variables requiring asynchronous evaluation and additional context?
  - Should resolution be a separate explicit API or an opt-in configuration accessor, and what workspace/editor context must callers supply?
  - Should extension-contributed substitutions and per-setting allowed-variable controls be part of the first public contract or deferred to separately scoped work?
