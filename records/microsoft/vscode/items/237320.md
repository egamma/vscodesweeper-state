# Issue #237320 — Explorer: Sticky folder cannot be dragged

[https://github.com/microsoft/vscode/issues/237320](https://github.com/microsoft/vscode/issues/237320)

## Summary

The interaction gap remains on current main: sticky tree rows are separately rendered copies and do not receive the drag-source wiring applied to ordinary list rows. The issue is already correctly classified and routed, so it should remain open for a shared-tree design decision.

## Change summary

Allow sticky folders in the Explorer to participate in drag-and-drop interactions like their ordinary tree rows.

## Best solution

Give sticky rows behavior consistent with their source rows, at least allowing an Explorer folder shown in sticky scroll to initiate the same file drag operation. Decide whether this parity belongs in the shared tree widget for every drag-enabled tree or should be limited to Explorer.

## Vision fit

- **Fit:** aligned
- **Reason:** Making two visual representations of the same tree item behave consistently advances the workbench UX direction and avoids a surprising interaction discontinuity.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/tree/abstractTree.ts`, `src/vs/base/browser/ui/list/listView.ts`, `src/vs/base/test/browser/ui/tree/objectTree.test.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`
- **Validation:** Add an ObjectTree browser test with sticky scroll and an ITreeDragAndDrop delegate, then assert that initiating a drag from the rendered sticky row invokes the delegate with the same element as the source tree row; include drop-target assertions if that behavior is selected.
- **Behavior:**

  > When an Explorer folder is represented by a sticky row, dragging that row should initiate the same file drag operation as dragging its ordinary tree row. Scrolling the source row into or out of sticky state must not change which ExplorerItem is dragged. Existing selection, context-menu, keyboard, and non-sticky drag behavior must remain unchanged. Whether sticky rows must also accept drops is an explicit scope decision.
- **Trace:**

  > StickyScrollWidget.createElement in src/vs/base/browser/ui/tree/abstractTree.ts renders a separate row copy and assigns the source list index, but it does not pass through ListView's drag-source setup. ListView in src/vs/base/browser/ui/list/listView.ts sets `draggable` and installs `dragstart` only for managed rows during item rendering. Explorer provides FileDragAndDrop from src/vs/workbench/contrib/files/browser/views/explorerViewer.ts through explorerView.ts, so the missing link is between the shared sticky copy and the existing tree DnD pipeline. The boundary is sticky-row interaction parity: do not alter FileDragAndDrop semantics, selection behavior, or ordinary-row dragging. The related https://github.com/microsoft/vscode/issues/257648 concerns overlap rendering rather than drag behavior.
- **Open decisions:**
  - Should drag-and-drop parity be provided by the shared tree sticky-scroll widget for every drag-enabled tree, or only by the Explorer?
  - Should a sticky row be both a drag source and a drop target, or is initiating a drag the intended scope?

## Evidence

- **current source:** src/vs/base/browser/ui/tree/abstractTree.ts, StickyScrollWidget.createElement, creates and renders a separate `.monaco-tree-sticky-row` with the source node's data index, but does not configure it as draggable or attach a dragstart handler.
- **drag source path:** src/vs/base/browser/ui/list/listView.ts configures `draggable` and registers `dragstart` only while rendering managed list rows through `dnd.getDragURI`; sticky row copies are outside that item-rendering path.
- **Explorer integration:** src/vs/workbench/contrib/files/browser/views/explorerView.ts supplies FileDragAndDrop to the tree, implemented in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts, so the Explorer supports dragging the underlying row but the sticky copy never reaches that integration.
