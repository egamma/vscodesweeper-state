# Issue #313828 — Improve the UI experience of the Customizations menu

[https://github.com/microsoft/vscode/issues/313828](https://github.com/microsoft/vscode/issues/313828)

## Summary

Keep open as an Agents Window information-architecture request: current customization entry points and workspace scoping do not deliver the proposed unified Settings experience. Related older issues cover centralization or modal grouping, not this report's full scope.

## Change summary

Provide a recognizable Settings entry and a spacious management surface with explicit workspace and provider scope in the Agents app.

## Best solution

Agree on a coherent Agents Window settings architecture that makes customization scope explicit and preserves access to ordinary application settings. Resolve naming, shortcut ownership, workspace navigation, and provider presentation together rather than treating the proposal as an icon-only polish change.

- **Behavior:**

  > The reporter wants configuration to be recognizable and accessible without understanding the Customizations drawer or the currently selected session provider. The proposed outcome is a Settings entry opening a full-window surface, with explicit global and workspace scope and accessible provider-specific configuration. Acceptance must verify navigation between two projects, distinguish global from workspace changes, retain access to application settings, and preserve session state when returning to the app. The exact naming, shortcut destination, and provider organization require maintainer agreement.
- **Trace:**

  > The current Overview action in src/vs/sessions/contrib/sessions/browser/customizationsToolbar.contribution.ts uses Codicon.home and opens the shared AICustomizationManagementEditorInput with active harness and workspace labels. aiCustomizationShortcutsWidget.ts retains the collapsible Customizations section, while sessionsView.ts supports alternative control/treatment presentations. SessionsAICustomizationWorkspaceService in src/vs/sessions/contrib/chat/browser/aiCustomizationWorkspaceService.ts derives project scope from the active chat unless a transient root override is set; shared management sections and visibility are supplied through workspace and harness services. Ordinary Settings owns CtrlCmd+Comma in src/vs/workbench/contrib/preferences/browser/preferences.contribution.ts. Preserve provider-neutral contracts, actual customization storage semantics, ordinary settings access, and the sessions-to-workbench layering boundary. https://github.com/microsoft/vscode/issues/264631 and https://github.com/microsoft/vscode/issues/297402 provide related design context but do not settle this proposal's full scope.
- **Open decisions:**
  - Should the Agents Window merge ordinary application settings and AI customizations into a single Settings destination, and should Command+, open that destination?
  - Should configuration navigation enumerate every added workspace independently of the active session, and what should the initial selected scope be?
  - Should providers appear side by side or remain selected one at a time with clearer scope and capability indicators?
  - Should customization management replace the app content with a full-window page and Back to App navigation, or retain a separate editor or modal presentation?
