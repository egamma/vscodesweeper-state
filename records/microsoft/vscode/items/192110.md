# Issue #192110 — Drag file another remote machine differs from origin

[https://github.com/microsoft/vscode/issues/192110](https://github.com/microsoft/vscode/issues/192110)

## Summary

The bug remains in current main: Explorer accepts a remote resource dropped into a window connected to a different remote, while that window's single remote filesystem provider sends the source path through its own connection without validating the URI authority. This can resolve an identically named path on the wrong machine, so the accepted bug should remain open.

## Change summary

Prevent Explorer drag-and-drop between windows connected to different remote machines from resolving the source path on the destination machine.

## Best solution

Explorer should reject a drop when a `vscode-remote` source authority differs from the destination authority, while preserving drag-and-drop within the same remote and existing local-file import behavior.

## Evidence

- **current drag path:** In src/vs/workbench/contrib/files/browser/views/explorerViewer.ts, FileDragAndDrop.onDragStart serializes remote resources through fillEditorsDragData, and handleDragOver accepts native DataTransfers.RESOURCES without comparing source and target authorities.
- **cross-window import path:** src/vs/workbench/contrib/files/browser/fileImportExport.ts ExternalFileImport.doImport extracts the source URI and importResources copies it to the target without checking whether their remote authorities differ.
- **root cause:** src/vs/workbench/services/remote/common/remoteFileSystemProviderClient.ts registers one vscode-remote provider backed by the current window's remote connection; src/vs/platform/files/common/diskFileSystemProviderClient.ts forwards stat/read/copy requests directly over that channel without authority validation.
