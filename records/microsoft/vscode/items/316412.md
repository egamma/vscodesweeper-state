# Issue #316412 — Built-in Copilot extension force-opens worktrees via public Git API, bypassing closed-list and git.detectWorktrees

[https://github.com/microsoft/vscode/issues/316412](https://github.com/microsoft/vscode/issues/316412)

## Summary

The reported force-open path remains in current source: Copilot repository lookups can reopen explicitly closed repositories and bypass workspace discovery boundaries. Keep this report open; the related newer report cannot be its duplicate canonical under the re-review rules.

## Change summary

Prevent automatic Copilot repository lookups from reopening closed worktrees and triggering costly Git activity despite repository-discovery settings.

## Best solution

Automatic Copilot metadata and session discovery should respect deliberate repository closure and workspace boundaries without breaking explicit repository-opening or worktree-management actions. Settle the public Git API's reopening contract before applying a blanket behavior change.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/git/vscode-node/gitServiceImpl.ts`, `extensions/git/src/api/api1.ts`, `extensions/git/src/api/git.d.ts`, `extensions/git/src/model.ts`, `extensions/copilot/src/extension/chatSessions/vscode-node/copilotCLIChatSessions.ts`, `extensions/copilot/src/extension/chatSessions/vscode-node/copilotCLIChatSessionsContribution.ts`
- **Validation:** Create a repository with linked worktrees and Copilot session history, close the worktree repositories in SCM, set git.detectWorktrees=false, and reload repeatedly. Verify that closed repositories stay absent and no Git API opening calls target them during passive session discovery. Also verify normal detectWorktrees=true discovery and explicit repository-opening/worktree-deletion actions retain their agreed behavior.
- **Behavior:**

  > Reloading a workspace must not let passive Copilot metadata or historical-session lookups undo the user's deliberate closure of worktree repositories. With git.detectWorktrees=false, those lookups must not indirectly reopen the closed worktrees or start their background Git activity. Ordinary worktree discovery when enabled must remain functional. Explicit user-requested repository opening and worktree management must follow the reopening contract agreed with the maintainer.
- **Trace:**

  > GitServiceImpl.getRepository and _getRepository in extensions/copilot/src/platform/git/vscode-node/gitServiceImpl.ts default to forceOpen=true and call gitAPI.openRepository when no open repository matches. ApiImpl.openRepository in extensions/git/src/api/api1.ts passes true for both openIfClosed and openIfParent; Model.openRepository in extensions/git/src/model.ts consequently skips closed-list and outside-workspace handling. This directly confirms the reported bypass, although the full reload scenario was not executed. Preserve enabled worktree discovery, trust checks, and explicit user-driven operations; the existing session-deletion callers demonstrate that force-opening is not exclusively passive discovery. https://github.com/microsoft/vscode/issues/326870 corroborates the cross-workspace symptom but is newer and cannot absorb this re-reviewed report. The uncertainty is the externally observable public API reopening contract, not which helper or file should implement the eventual behavior.
- **Open decisions:**
  - Should an explicit public Git API openRepository(root) request continue to reopen deliberately closed repositories by default, or should reopening require an explicit opt-in while the default honors the closed list?
