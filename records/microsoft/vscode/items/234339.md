# Issue #234339 — Status bar tooltip - add support for specifying a list of commands

[https://github.com/microsoft/vscode/issues/234339](https://github.com/microsoft/vscode/issues/234339)

## Summary

The core hover already supports command actions, but neither the stable nor proposed StatusBarItem API exposes a command list. Keep this accepted, team-authored request open to finish the extension-facing contract; the merged asynchronous-tooltip work does not satisfy that remaining requirement.

## Change summary

Allow extensions to supply commands rendered in a status bar item's hover action bar.

## Best solution

Expose a proposed extension API that carries tooltip content and command actions through the extension-host bridge into the existing native hover action bar. Settle its relationship to asynchronous tooltip providers while preserving existing tooltip and status bar click behavior.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.statusBarItemTooltip.d.ts`, `src/vs/workbench/api/common/extHostStatusBar.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadStatusBar.ts`, `src/vs/workbench/api/browser/statusBarExtensionPoint.ts`, `src/vs/workbench/api/test/browser/extHostStatusBar.test.ts`, `src/vs/workbench/test/browser/parts/statusbar/statusbarItem.test.ts`
- **Validation:** After agreeing the proposed API contract, add bridge and renderer tests proving an extension-supplied list produces native hover actions with the expected titles, command IDs, and arguments. Run the targeted extHostStatusBar.test.ts and statusbarItem.test.ts suites; manually verify a proposed-API extension's hover actions with mouse and keyboard, including asynchronous content and unchanged ordinary tooltip behavior.
- **Behavior:**

  > An extension can provide tooltip content together with a list of commands for a status bar item. Those commands appear in the native hover action bar, and invoking one executes its command with its supplied arguments. Existing string and markdown tooltips, asynchronous tooltip creation, and the item's ordinary click command continue to behave as before. Acceptance must exercise the extension-facing API through the bridge, rather than only an internal status bar entry.
- **Trace:**

  > ITooltipWithCommands in src/vs/workbench/services/statusbar/browser/statusbar.ts already models content and command actions, and StatusbarEntryItem.update in src/vs/workbench/browser/parts/statusbar/statusbarItem.ts forwards them to managed-hover actions. The missing boundary is the extension API: vscode.d.ts and vscode.proposed.statusBarItemTooltip.d.ts accept only string/markdown content, optionally provided asynchronously. ExtHostStatusBarEntry.update, the status bar protocol methods, and MainThreadStatusBar.$setEntry preserve that restriction through to IExtensionStatusBarItemService. https://github.com/microsoft/vscode/pull/238297 delivered asynchronous content but did not expose hover actions. Preserve current command conversion/lifetime behavior and existing tooltip semantics; native click-triggered dropdown menus requested in https://github.com/microsoft/vscode/issues/332578 are outside this issue. The uncertainty is the public shape and whether asynchronously resolved tooltip content can carry its own action list, not whether the renderer can display actions.
- **Open decisions:**
  - Should content and command actions be exposed through the existing proposed tooltip2 contract or through a separate proposed tooltip/action property?
  - Can an asynchronous tooltip provider return content and commands together, or must commands be supplied independently of the provider?
