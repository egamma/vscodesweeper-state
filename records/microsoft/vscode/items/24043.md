# Issue #24043 — Neo keyboard layout: Some Keys stopped working

[https://github.com/microsoft/vscode/issues/24043](https://github.com/microsoft/vscode/issues/24043)

## Summary

The issue remains necessary: a 2024 report reproduces the Neo-family modifier-layer failure with extensions disabled, both keyboard dispatch modes, and keybinding diagnostics, while a 2025 report confirms that layer-3 shortcuts still cannot be defined. The Backlog milestone does not block cleanup, but there is no evidence supporting a close.

## Change summary

Neo-family XKB layouts lose higher-layer key semantics when those keys are combined with Control or used while recording shortcuts.

## Best solution

Keep this as the keyboard-layout canonical and diagnose the Linux key event/native-keymap boundary for ISO_Level3_Shift and ISO_Level5_Shift combinations, ensuring resolved higher-layer keys remain intact when Control or Shift is also held.

## Plan brief

- **Likely files:** `src/vs/workbench/services/keybinding/browser/keyboardLayouts/layouts/linux.ts`, `src/vs/workbench/services/keybinding/browser/keyboardLayoutService.ts`, `src/vs/platform/keybinding/common/abstractKeybindingService.ts`
- **Validation:** On Linux X11 with `setxkbmap de neo` or `setxkbmap de bone`, use Developer: Toggle Keyboard Shortcuts Troubleshooting and verify that Ctrl combined with a Mod3/Mod4-generated navigation or punctuation key resolves to the generated key (for example Ctrl+Right or Ctrl+/), not the physical layer-1 key; also verify ordinary typing and existing US-layout shortcuts remain unchanged.
- **Behavior:**

  > On Neo-family XKB layouts, keys produced through Mod3 or Mod4 must retain their resolved meaning when combined with Control or Shift. Shortcut recording and dispatch should recognize combinations such as Ctrl plus a layer-generated arrow or punctuation key rather than dropping the layer modifier and dispatching the physical layer-1 key. Ordinary text entry, standard layouts, and explicit physical-key bindings must remain unchanged.
- **Trace:**

  > The discussion provides a confirmed Linux repro with extensions disabled and isolated settings: higher-layer typing works, but adding Control causes keybinding troubleshooting to resolve the physical layer-1 key. The implicated path spans Linux layout data/native-keymap handling into KeyboardLayoutService and the platform keybinding dispatch path; microsoft/node-native-keymap#19 is relevant prior work for ISO_Level3_Shift and ISO_Level5_Shift but did not eliminate the combined-modifier symptom. The uncertainty starts at whether current Electron events already contain the resolved higher-level key and VS Code discards it, or whether node-native-keymap/XKB translation must provide additional state. Preserve `keyboard.dispatch` semantics and behavior for standard layouts.
- **Open decisions:**
  - Does the current failing event lose the higher-layer symbol before VS Code receives it, inside native-keymap translation, or during VS Code keyboard-event conversion?
  - Should ISO_Level3_Shift and ISO_Level5_Shift be modeled as layout-selection modifiers only, or exposed as dispatch modifiers when combined with Control and Shift?
  - Which Neo-family layout and representative combinations should become the stable regression fixture without making the test environment depend on a desktop XKB installation?

## Evidence

- **current confirmation:** The 2024 comment reports the failure on an Arch Linux OSS build and Flathub build after testing both `keyboard.dispatch` values, resetting XKB, removing other layouts, and launching with `--disable-extensions` and an isolated user-data directory; its keybinding trace shows the higher-layer key collapsing to the layer-1 key when Control is held.
- **recent confirmation:** The 2025 comment confirms that shortcuts such as Ctrl+(, entered as Ctrl+Mod3+N on Neo2, still cannot be defined under either dispatch setting.
- **scope:** Reports across Neo2, Bone, KOY, and custom XKB layouts consistently identify failures involving ISO_Level3_Shift/ISO_Level5_Shift-derived keys and additional modifiers; typing often works while shortcut dispatch does not.
- **partial workarounds:** `keyboard.dispatch: keyCode`, removing conflicting shortcuts, and reapplying `setxkbmap` solve only subsets of the reports; they do not cover the central Control-plus-higher-layer shortcut failure.
- **related native-keymap work:** https://github.com/microsoft/node-native-keymap/pull/19 added support for XK_ISO_Level3_Shift and XK_ISO_Level5_Shift, but the later confirmed reports show that the broader combined-modifier behavior remains unresolved.
