# Issue #321477 — Drag and drop between different remotes is unsupported

[https://github.com/microsoft/vscode/issues/321477](https://github.com/microsoft/vscode/issues/321477)

## Summary

Current main still accepts a cross-window remote Explorer drop and then tries to resolve the source URI through the target window's remote file-system provider, producing the reported inaccessible-file error. This should remain open and be routed to the file Explorer and remote owners.

## Change summary

Dragging a file between VS Code windows connected to different remotes is accepted but fails with “The dropped file could not be accessed for import.”

## Best solution

Define consistent cross-remote drag behavior in the Explorer: either transfer the source contents through a cross-window mechanism, matching supported remote-to-remote copy/paste, or reject the drag before presenting it as an available operation.

## Plan brief

- **Validation:** Exercise two VS Code windows connected to different remote authorities: dragging a file from remote A onto remote B must either copy the correct contents successfully or be rejected before drop, without showing the inaccessible-import error; local-to-local and local-to-remote drag behavior must remain unchanged.
- **Behavior:**

  > Dragging a file between Explorer windows connected to different remotes must not advertise an operation that fails with an inaccessible-file error. The selected product behavior should be consistent for files and folders: either the source contents reach the target remote correctly, or the drag is visibly rejected before drop. Existing local and same-remote drag-and-drop behavior must remain unchanged.
- **Trace:**

  > FileDragAndDrop.onDragStart in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts only adds CodeDataTransfers.FILES for file-scheme resources, while fillEditorsDragData carries the vscode-remote URI. In the receiving window, ExternalFileImport.doImport/importResources in src/vs/workbench/contrib/files/browser/fileImportExport.ts attempts to resolve that URI through the target window's file service; a provider for the scheme exists, but it is connected to a different remote authority, so fileService.exists fails and emits the reported message. Related issue https://github.com/microsoft/vscode/issues/192110 confirms that cross-remote Explorer drag remains accepted as a bug, while https://github.com/microsoft/vscode/issues/93599 documents the broader cross-window remote-provider limitation. Preserve local, same-remote, and keyboard copy/paste behavior; avoid silently substituting a same-path resource from the target remote.
- **Open decisions:**
  - Should Explorer support copying file and folder contents between different remote authorities, or explicitly reject cross-remote drag-and-drop before the drop is accepted?

## Evidence

- **current source path:** On current main, FileDragAndDrop.onDragStart in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts publishes ordinary file paths through CodeDataTransfers.FILES only for resources using the file scheme; remote resources are carried through fillEditorsDragData instead.
- **failure path:** ExternalFileImport.doImport/importResources in src/vs/workbench/contrib/files/browser/fileImportExport.ts extracts the remote URI, activates a provider by scheme, and calls fileService.exists from the target window. When that window is connected to a different remote authority, the source cannot be resolved and the exact reported error is emitted.
- **related accepted bug:** https://github.com/microsoft/vscode/issues/192110 is an older open bug labeled file-explorer/help wanted for dragging between different remote machines. It is related but not a valid duplicate canonical under the re-review rule because its observable symptom is copying the target remote's same-path file, rather than this report's inaccessible-import error.
- **different topology:** https://github.com/microsoft/vscode/issues/93599 tracks remote-to-local drag and documents the same architectural limitation, but it does not report the same remote-to-remote operation and observable symptom required for a re-reviewed duplicate close.
- **test-plan context:** https://github.com/microsoft/vscode/issues/321354 explicitly tested remote-to-remote copy/paste after a transfer refactor; this report came from that testing and no linked fixing pull request or later fix commit exists.
