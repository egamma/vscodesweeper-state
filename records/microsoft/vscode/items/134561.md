# Issue #134561 — Add stronger checks to make sure an extension doesn't activate both locally and remotely

[https://github.com/microsoft/vscode/issues/134561](https://github.com/microsoft/vscode/issues/134561)

## Summary

Keep open: current main structurally assigns each extension identifier one running location, but there is no issue-referencing fix or focused regression coverage proving the requested stronger checks are complete. This team-authored debt item therefore does not meet the factual-close bar.

## Change summary

Strengthen extension-host allocation checks so one extension cannot activate simultaneously in local and remote extension hosts.

## Best solution

Make the single-host invariant explicit and regression-tested across initial allocation and dynamic extension updates, with a clear diagnostic if inconsistent host membership is ever produced.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/common/extensionRunningLocationTracker.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/services/extensions/test/common/extensionRunningLocationTracker.test.ts`
- **Validation:** Add a targeted extension-running-location test using one identifier present in both local and remote extension sets, asserting that initial allocation and a remove/add delta expose it to exactly one matching extension-host manager.
- **Behavior:**

  > An extension installed both locally and remotely must be eligible for activation in exactly one extension host. This must remain true during initial startup and after enable, install, update, or location-changing deltas. Acceptance requires a focused automated test that would fail if the same identifier were included in both local and remote host membership.
- **Trace:**

  > The original double-activation scenario is documented at https://github.com/microsoft/vscode/issues/128573#issuecomment-903514847. Current main centralizes allocation in ExtensionRunningLocationTracker._doComputeRunningLocation in src/vs/workbench/services/extensions/common/extensionRunningLocationTracker.ts, where an ExtensionIdentifierMap records one location per identifier. AbstractExtensionService then filters initial and delta extension sets by that location in src/vs/workbench/services/extensions/common/abstractExtensionService.ts. The existing tracker test file focuses on affinity and does not directly pin the local-plus-remote uniqueness invariant. Preserve extensionKind precedence, extension-development preferences, affinity behavior, and the ability to move an extension between hosts through a remove/add delta.
- **Open decisions:**
  - Is focused regression coverage sufficient, or should an inconsistent allocation also trigger a runtime assertion or diagnostic?
  - Which boundary should own the invariant check: running-location computation, per-host filtering, or extension-host delta dispatch?
  - Should production builds reject inconsistent membership, log it, or reserve a hard assertion for development and test builds?

## Evidence

- **original diagnosis:** https://github.com/microsoft/vscode/issues/128573#issuecomment-903514847 explains that the same extension was executing once in the UI host and again in the workspace host, causing duplicate command and view registration.
- **current allocation path:** src/vs/workbench/services/extensions/common/extensionRunningLocationTracker.ts stores one ExtensionRunningLocation per extension identifier; _doComputeRunningLocation combines local and remote descriptions through determineExtensionHostKinds and records one selected host kind.
