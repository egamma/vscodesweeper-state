# Issue #319305 — Open to the side reorders the order of the tabs even though it was already open

[https://github.com/microsoft/vscode/issues/319305](https://github.com/microsoft/vscode/issues/319305)

## Summary

Keep open for an explicit UX decision: current main still moves an already-visible session to the end when “Open to the Side” is invoked, while the originating test plan establishes that selecting an already-visible session should activate it without changing the grid. This team-authored, under-discussion item has no factual close basis.

## Change summary

Avoid reordering an already-visible Agents Window session when its context-menu “Open to the Side” action is invoked.

## Best solution

Decide whether “Open to the Side” should focus an already-visible session in place or deliberately reposition it; then encode that distinction in the Sessions service/action contract and a focused ordering regression test.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/sessions/browser/views/sessionsViewActions.ts`, `src/vs/sessions/services/sessions/browser/sessionsService.ts`, `src/vs/sessions/services/sessions/test/browser/sessionsManagementService.test.ts`, `src/vs/sessions/services/sessions/test/browser/visibleSessions.test.ts`
- **Validation:** Add a focused Sessions service/action test with visible order [A, B, C], invoke “Open to the Side” for B, and assert the maintainer-selected order and activation behavior; existing insertion and drag-reordering tests must remain unchanged.
- **Behavior:**

  > With three session views visible, invoking the session-list “Open to the Side” command for a session that is already visible currently moves that session to the rightmost position. The maintainer must decide whether the command should instead activate the existing view without altering its position. Once decided, the behavior must be consistent for single-selection and multi-selection without changing drag-and-drop reordering semantics.
- **Trace:**

  > OpenSessionToTheSideAction in src/vs/sessions/contrib/sessions/browser/views/sessionsViewActions.ts calls ISessionsService.openSessionToSide. SessionsService.openSessionToSide in src/vs/sessions/services/sessions/browser/sessionsService.ts anchors to the last visible session and calls insertAt for any requested session that is not already the anchor. VisibleSessions.insertAt in src/vs/sessions/services/sessions/browser/visibleSessions.ts intentionally moves an existing slot, and its unit tests confirm that generic insertion behavior. The uncertainty is at the action/service contract: whether this context-menu invocation should use move semantics for an existing session or only activate it. Preserve explicit drag-and-drop movement, fork placement, insertion of sessions not yet visible, and multi-select ordering.
- **Open decisions:**
  - When “Open to the Side” targets an already-visible session, should it focus the existing view in place or reposition that view beside the current rightmost session?
  - For a multi-selection containing both visible and hidden sessions, should visible sessions retain their positions while only hidden sessions are appended, or should the entire selection be reordered as one block?
