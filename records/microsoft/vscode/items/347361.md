# Issue #347361 — Can't drag text into rename textboxes

[https://github.com/microsoft/vscode/issues/347361](https://github.com/microsoft/vscode/issues/347361)

## Summary

Keep open to investigate text drops into Explorer naming inputs. Current main uses a shared inline-edit widget, but source inspection cannot confirm native drop behavior; the supplied steps and Linux/Wayland environment suffice to retest.

## Change summary

Dragging text into Explorer file or folder creation and rename inputs does not insert it.

## Best solution

Restore ordinary text-drop behavior inside Explorer naming inputs while preserving file and folder drag-and-drop. Treat creating a file by dropping text onto the Explorer background as a separate feature request.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/browser/parts/views/inlineEditInputBox.ts`, `src/vs/base/browser/ui/list/listView.ts`, `src/vs/workbench/test/browser/parts/views/inlineEditInputBox.test.ts`
- **Validation:** On Linux GNOME/Wayland, drag selected document text into empty and populated Explorer inputs for New File, New Folder, and Rename. Verify insertion, Enter acceptance, Escape cancellation, and unchanged file/folder drag-and-drop; compare with a standalone text input to isolate native behavior.
- **Behavior:**

  > Text dragged into an active Explorer file or folder naming input should insert using ordinary text-input behavior. Verify both empty and populated inputs during creation and rename, with normal filename validation and acceptance/cancellation preserved. Dropping text onto the Explorer background to create a file is outside this bug's scope.
- **Trace:**

  > Explorer renderInputBox in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts creates InlineEditInputBox, which wraps the native input implemented in src/vs/base/browser/ui/inputbox/inputBox.ts. The input widgets have no drag/drop listeners, while the enclosing ListView intercepts dragover and delegates payload acceptance to FileDragAndDrop.handleDragOver. That handler rejects native payloads without file/resource types, but source inspection alone does not establish whether this prevents native text insertion for the reporter's drag source. First reproduce with actual drag events and inspect payload types, event cancellation, and focus transitions. Preserve existing file/resource drops and shared-widget consumers; do not broaden the work to background-drop file creation. The editor-to-editor report at https://github.com/microsoft/vscode/issues/146651 has not been established as the same defect.
