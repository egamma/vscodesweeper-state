[https://github.com/microsoft/vscode/issues/177409](https://github.com/microsoft/vscode/issues/177409)

## Summary

Keep open for a focused performance retest: current source limits initial Markdown warmup, but still warms outputs across the document and processes returned dimensions individually. The reported large-notebook opening scenario is sufficient to retest; source inspection alone does not establish whether the renderer stalls persist.

## Change summary

Opening notebooks with thousands of cells can stall the renderer while warmup dimension messages trigger cell-height and list-layout updates.

## Best solution

Keep notebook opening responsive as cell count grows, including the work triggered by background output rendering. Profile the current warmup-to-layout path before choosing a bounded change, preserving accurate heights and scroll restoration.

## Evidence

- **Reported trigger:** https://github.com/microsoft/vscode/issues/177409 describes opening a notebook with thousands of cells and spending hundreds of milliseconds or seconds handling warmup dimensions in the renderer. There are no subsequent comments confirming resolution.
- **Current Markdown warmup differs:** src/vs/workbench/contrib/notebook/browser/notebookEditorWidget.ts:1694–1758 limits initial Markdown initialization to the cached viewport or the first five Markdown cells. In browser/contrib/viewportWarmup/viewportWarmup.ts, document-wide Markdown preview creation is commented out, while scrolling warms nearby previews. The original assertion that every Markdown cell is warmed on open therefore does not describe this current path.
- **Remaining document-wide output work:** NotebookViewportContribution._warmupDocumentNow still traverses every cell and calls _warmupCodeCell for code cells. Each eligible cell submits outputs up to outputDisplayLimit; browser/view/renderers/webviewPreloads.ts:2101–2107 schedules idle rendering per output, which does not by itself bound the renderer-side work caused by returned dimensions.
- **Dimension-to-layout path:** browser/view/renderers/backLayerWebView.ts:630–678 handles every dimension update individually. NotebookEditorWidget._updateOutputHeight finds the cell, updates its output height, and calls layoutNotebookCell; _updateMarkupCellHeight sets renderedMarkdownHeight. NotebookCellLayoutManager.layoutNotebookCell calls updateElementHeight2 synchronously outside rendering transactions, although it skips unchanged heights and coalesces pending layouts during transactions. These mechanisms require measurement before concluding that the reported stall remains or is fixed.
- **History does not establish a complete fix:** The checkout is shallow and contains no locally discoverable issue-referencing fix. Remote history for viewportWarmup.ts includes addb0791aca06f5267474e5188048aaf128778ae, which limits outputs per cell, and d97088ca06821d51484a4212aab29aad60b4b6d3, which requests idle output rendering and predates this report. Neither establishes that the full reported renderer-blocking behavior was fixed.

The older open https://github.com/microsoft/vscode/issues/117644 reports sluggish scrolling, not notebook-open warmup stalls; https://github.com/microsoft/vscode/issues/172345 concerns IPC during notebook saving.
