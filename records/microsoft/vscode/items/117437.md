# Issue #117437 — [product icon themes] No fallback for using icon contribution point

[https://github.com/microsoft/vscode/issues/117437](https://github.com/microsoft/vscode/issues/117437)

## Summary

The core request remains valid: extensions can alias a contributed icon to an existing icon, but there is still no fallback for a reference to an icon contributed by an optional, absent extension. The Backlog milestone and maintainer discussion support keeping this open for an API/schema design decision.

## Change summary

Allow an extension to reference another extension's product icon while falling back to a built-in codicon when that extension is not installed.

## Best solution

Define fallback semantics in the product-icon contribution contract so an extension-owned icon can prefer an optional external icon and otherwise resolve to a built-in icon, without requiring an extension dependency. The design should avoid duplicate ownership of a global icon identifier.

## Plan brief

- **Likely files:** `src/vs/platform/theme/common/iconRegistry.ts`, `src/vs/workbench/services/themes/common/productIconThemeSchema.ts`, `src/vs/workbench/services/themes/common/productIconThemeData.ts`
- **Validation:** Add extension-contribution tests covering an optional preferred icon with the provider installed and absent, asserting that the preferred glyph wins when available and the built-in codicon renders otherwise.
- **Behavior:**

  > An extension can contribute an icon for its own UI location that prefers an icon supplied by an optional extension and falls back to a built-in codicon when that provider is unavailable. Installing or enabling the provider selects its icon; uninstalling or disabling it restores the fallback rather than the error icon. Existing icon aliases and required extension-dependency behavior remain compatible.
- **Trace:**

  > The discussion confirms that an icon contribution may already use another registered icon ID as `default`, which covers aliases to known built-in icons but not an absent optional provider. The unresolved path is the extension-facing product-icon contribution schema and icon registration/resolution logic, likely around src/vs/platform/theme/common/iconRegistry.ts and product-icon theme schema/data handling under src/vs/workbench/services/themes/common/. The boundary is product-icon fallback resolution: do not broaden this into file-icon themes or change ordinary extension dependency semantics. The source trace must first confirm the current filenames and all consumers because this review did not execute the workbench.
- **Open decisions:**
  - Should fallback be declared at each icon reference or on a location-specific contributed icon?
  - If multiple extensions declare the same icon ID, what deterministic precedence and lifecycle semantics apply when providers are enabled, disabled, installed, or removed?
  - Should the contribution schema permit a preferred icon plus fallback explicitly, or model the behavior through ordered icon definitions?
