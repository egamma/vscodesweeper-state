## Evidence

- **generic substitution path:** installedMcpServersDiscovery.ts sets `variableReplacement` on every McpServerDefinition regardless of transport type (http or stdio), and mcpRegistry.ts's `_replaceVariablesInLaunch` calls `ConfigurationResolverExpression.parse(McpServerLaunch.toSerialized(launch))` then `resolveAsync`, which is transport-agnostic.
- **recursive parser covers headers:** configurationResolverExpression.ts's `parseObject` recurses into arrays (headers are stored as `[string,string][]` tuples via `Object.entries`), so `${env:...}` inside a header value string should be matched and substituted like any other field.
- **env resolution fallback:** variableResolver.ts's `env` case returns an empty string (not the literal placeholder) when the variable is undefined — so if resolution ran but the var wasn't found, the header would end up empty, not literally `${env:MY_VAR}`, which is inconsistent with the reporter's claim of a literal unsubstituted string being sent.
- **environment-dependent concern:** The report's own repro notes involve OS-level persisted env var propagation timing (a known Windows quirk where already-running parent processes don't see newly persisted user env vars until logoff/logon), which can't be verified by reading source and requires the reporter's confirmation.
