# Issue #337769 — Edit tracking slows down bulk text-model loading

[https://github.com/microsoft/vscode/issues/337769](https://github.com/microsoft/vscode/issues/337769)

## Summary

Team-authored perf report with a traced root cause: VSCodeWorkspace.documents builds a full VSCodeDocument (including a StringText snapshot of getValue() and change/language listeners) for every model unconditionally, and the existing 'ever visible' filter in AnnotatedDocuments only discards the result afterward — so the expensive work happens for files never opened in an editor. Stays open (team-authored, no fix commit referencing this issue exists yet); marking for planning since the fix crosses a layering boundary.

## Change summary

Edit tracking (editTelemetry) does expensive per-model work (content snapshot, listeners) for every text model on bulk load, including files never opened in an editor, because the visibility filter is applied after document construction instead of before it.

## Best solution

Gate VSCodeDocument construction in VSCodeWorkspace (or restructure so AnnotatedDocuments' visibility check runs before the expensive VSCodeDocument/StringText work) so unopened files never pay the cost, while still keeping tracking alive after a tab closes until the model is disposed, per the reporter's suggested fix.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/editTelemetry/browser/helpers/vscodeObservableWorkspace.ts`, `src/vs/workbench/contrib/editTelemetry/browser/helpers/annotatedDocuments.ts`
- **Validation:** A test or manual benchmark showing that resolving N text models that are never shown in an editor no longer constructs a VSCodeDocument/StringText snapshot for each of them, only for models that have been visible at least once (or are otherwise tracked), with tracking persisting after the tab closes until the model is disposed.
- **Behavior:**

  > Loading text models that are never opened in an editor (bulk resolution, e.g. during Agents window sessions) should not pay the cost of building edit-tracking state (content snapshot, change/language listeners) for each of them. Edit tracking should only materialize for a document once it has been visible in an editor at least once, and once materialized it should keep tracking after the tab closes, until the underlying model is disposed. Acceptance: resolving a large batch of never-opened models shows no observable construction/StringText work for those models; models that do become visible are still tracked normally, including after their tab closes.
- **Trace:**

  > VSCodeWorkspace.documents (vscodeObservableWorkspace.ts, mapObservableArrayCached over `models`) constructs a VSCodeDocument for every resolved model except those failing isTooLargeForSyncing — VSCodeDocument's constructor eagerly computes `new StringText(this.textModel.getValue())` and registers onDidChangeContent/onDidChangeLanguage listeners. AnnotatedDocuments (annotatedDocuments.ts) already has a `wasEverVisible` cache (derivedObservableWithCache) that would be the right gate, but it is applied to `this._workspace.documents` — i.e. after VSCodeDocument already exists — so it only skips building the downstream AnnotatedDocument, not the upstream VSCodeDocument cost the issue is about. The boundary: ObservableWorkspace/VSCodeWorkspace is a generic abstraction and does not currently depend on editor-group visibility (that lives in UriVisibilityProvider, constructed inside AnnotatedDocuments) — moving the check earlier means deciding whether visibility awareness moves into VSCodeWorkspace or the pipeline is restructured so the visibility signal is computed before VSCodeDocument construction. Do not change isTooLargeForSyncing filtering or the DocumentWithSourceAnnotatedEdits/CombineStreamedChanges/MinimizeEditsProcessor pipeline. Related: https://github.com/microsoft/vscode/issues/240181 (lazy text model loading, cited by the reporter as related, not a duplicate).
- **Open decisions:**
  - Should visibility-awareness move into VSCodeWorkspace/ObservableWorkspace itself, or should the pipeline be restructured so AnnotatedDocuments computes visibility before requesting/creating the underlying VSCodeDocument (keeping ObservableWorkspace visibility-agnostic)?
  - Once a document is disposed, should its accumulated tracking state be discarded immediately, or is there a data flush/telemetry step that must run first?

## Evidence

- **unconditional document creation:** src/vs/workbench/contrib/editTelemetry/browser/helpers/vscodeObservableWorkspace.ts:38 — mapObservableArrayCached over all models constructs a VSCodeDocument (except for isTooLargeForSyncing) regardless of editor visibility; VSCodeDocument's constructor immediately computes `new StringText(this.textModel.getValue())` and registers onDidChangeContent/onDidChangeLanguage listeners for every one.
- **visibility filter applied too late:** src/vs/workbench/contrib/editTelemetry/browser/helpers/annotatedDocuments.ts:32-35 — the `wasEverVisible` gate that decides whether to build an AnnotatedDocument only runs downstream of the already-constructed VSCodeDocument, so it cannot prevent the upstream cost the issue describes.
- **always-on default:** editTelemetry.contribution.ts registers EditTelemetryContribution unconditionally via registerWorkbenchContribution2 and editStats.enabled defaults to true, so this cost is paid in the default configuration for every bulk model load (e.g. Agents window multi-file sessions).
