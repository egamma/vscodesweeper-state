# Issue #290009 — Expose configurable private {extension,mcp} marketplace when launching code server

[https://github.com/microsoft/vscode/issues/290009](https://github.com/microsoft/vscode/issues/290009)

## Summary

Keep open: current server startup does not expose configuration for both private marketplaces without modifying product configuration. Existing settings provide only partial coverage, and the related policy issues do not supersede this request.

## Change summary

Allow server operators to configure private extension and MCP marketplaces at launch without group policy or release-by-release product.json edits.

## Best solution

Provide a supported server-operator configuration contract that reaches both the browser workbench and server marketplace consumers. Decide whether this is endpoint configuration or a broader server policy facility before implementation, preserving existing desktop policy behavior.

## Plan brief

- **Likely files:** `src/vs/server/node/serverEnvironmentService.ts`, `src/vs/server/node/serverServices.ts`, `src/vs/server/node/webClientServer.ts`, `src/vs/workbench/services/extensionManagement/browser/extensionGalleryManifestService.ts`, `src/vs/workbench/services/mcp/browser/mcpGalleryManifestService.ts`
- **Validation:** Using a built VS Code Server and controlled extension/MCP registry endpoints, launch with the agreed operator configuration and verify extension searches and MCP browsing use those endpoints without changing product.json. Repeat without overrides to confirm default behavior, and verify the agreed precedence against user configuration and any applicable managed policy.
- **Behavior:**

  > Server operators need to select private extension and MCP marketplaces without OS group policy or edits to installation files after each release. Acceptance requires both marketplace surfaces to use the configured endpoints in the browser workbench and associated server operations. With no operator configuration, existing defaults must remain unchanged. The supported configuration must remain usable after replacing the server installation with a newer release.
- **Trace:**

  > serverOptions and ServerParsedArgs in src/vs/server/node/serverEnvironmentService.ts expose no marketplace launch options, and serverServices.ts initializes configuration with NullPolicyService. webClientServer.ts constructs browser productConfiguration from the installed product service; its product.overrides.json mechanism is development-only. WebExtensionGalleryManifestService inherits product-based extension manifest construction and sends that manifest to the server, while WorkbenchMcpGalleryManifestService already reads the MCP gallery configuration before forwarding its manifest. This establishes asymmetric existing support, not a completed solution for both marketplaces. Preserve desktop policy behavior and avoid expanding the request into unrelated runtime or tool-permission controls. https://github.com/microsoft/vscode/issues/296520 corroborates the server policy gap, while https://github.com/microsoft/vscode/issues/278066 addresses a distinct account-discovery mechanism. The remaining uncertainty is the operator-visible contract and its authority relative to other configuration sources.
- **Open decisions:**
  - Should the supported launch contract configure only the two marketplace endpoints, or expose a general server policy file that also carries other enterprise controls?
  - Should operator-supplied marketplace endpoints be enforced for connected browser clients or act as overridable defaults, and what precedence should apply when account-managed configuration is also present?
