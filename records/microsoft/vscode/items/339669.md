# Issue #339669 — Flaky Tests: restores one durable transition before provider output after service restart

[https://github.com/microsoft/vscode/issues/339669](https://github.com/microsoft/vscode/issues/339669)

## Summary

Team-authored flaky-test report (2/20 failures in a cited Linux unit-test run) filed today with no fix yet — keep open. Tracing the source turned up a plausible, concrete root-cause candidate in SessionDatabase's write/read sequencing rather than in the test's own hydrate/restore assertions.

## Change summary

`SessionWorkspaceConversionService` unit test 'restores one durable transition before provider output after service restart' intermittently fails in CI (2 of 20 runs).

## Best solution

Audit SessionDatabase's read/write sequencing around workspace-transition persistence: getTurnWorkspaceTransitions() skips the whenIdle()/metadata-sequencer draining that its sibling getTurnDelegations() performs, and close() never drains _pendingWrites despite that being the documented purpose of the tracking set — either gap could let a restart race ahead of a still-in-flight transition write. Also worth noting the test itself violates this directory's own AGENTS.md convention (real on-disk SessionDatabase instead of ':memory:'), which may independently add timing noise; confirm whether that convention can be honored here before focusing solely on the sequencer fix.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/sessionDatabase.ts`, `src/vs/platform/agentHost/test/node/sessionWorkspaceConversion.test.ts`
- **Validation:** Run 'restores one durable transition before provider output after service restart' in a repeat loop (50-100x) before and after any fix to confirm the flake is gone; add a focused SessionDatabase-level test that calls setWorkspaceConversion()/setTurnWorkspaceTransition() without awaiting full sequencer drain and immediately calls close() then reopen + getTurnWorkspaceTransitions() to pin the exact race.
- **Behavior:**

  > After a simulated service restart (close + reopen of the same SessionDatabase), SessionWorkspaceConversionContribution.onHydrateTurns must reliably recover every already-persisted workspace transition and prepend its SystemNotification before replaying provider-authored turns — the test must pass every run, not ~90% of runs, with its existing assertions (requestHidden=true, workspaceContinuation=true, transition notification before the provider's markdown response, persistedTransitions containing both turn ids).
- **Trace:**

  > Two source-level gaps in src/vs/platform/agentHost/node/sessionDatabase.ts are consistent with this failure mode: (1) getTurnWorkspaceTransitions() (lines 685-700) omits the `await this.whenIdle()` guard that its sibling getTurnDelegations() (lines 643-645) has, and (2) close() (lines 1352-1354) never drains `_pendingWrites` via whenIdle() before closing the connection, despite that being the documented reason `_pendingWrites` exists (lines 461-468). Because setWorkspaceConversion/setTurnWorkspaceTransition acquire `_metadataSequencer` before `_turnUsageSequencer` (lines 442-448), a read or a close() that doesn't wait for the metadata sequencer to drain can observe/close before a still-in-flight transition write is fully committed. Do not touch the hydrate/restore ordering logic in SessionWorkspaceConversionContribution.onHydrateTurns itself — that logic is exercised correctly in the adjacent non-flaky tests ('restores every persisted workspace conversion at its own turn boundary'); the likely fix is isolated to SessionDatabase's write/read/close sequencing. Separately, the test does not follow this directory's own AGENTS.md convention of an in-memory database, which is worth revisiting once the sequencing root cause is confirmed or ruled out.
- **Open decisions:**
  - Should SessionDatabase.close() become durable-by-default (always drain _pendingWrites via whenIdle() before closing), given other call sites across agentHost may rely on close() returning promptly during shutdown?
  - Should getTurnWorkspaceTransitions() (and any other turn-usage reads that skip the metadata sequencer) be changed to wait for whenIdle()/the metadata sequencer, matching getTurnDelegations(), or is the intended contract that reads may race in-flight metadata writes elsewhere in the codebase?

## Evidence

- **read/write asymmetry:** src/vs/platform/agentHost/node/sessionDatabase.ts:643-645 getTurnDelegations() calls `await this.whenIdle()` before reading, but getTurnWorkspaceTransitions() (lines 685-700) queues only on `_turnUsageSequencer` and reads immediately, with no whenIdle()/metadata-sequencer wait.
- **sequencer ordering:** setWorkspaceConversion/setTurnWorkspaceTransition (sessionDatabase.ts:664-676) go through `_mutateMetadataAndTurnUsage`, which acquires `_metadataSequencer` before `_turnUsageSequencer` (lines 442-448). A read that bypasses `_metadataSequencer` entirely (as getTurnWorkspaceTransitions does) can run before a pending write even enters the turn-usage queue.
- **close() does not drain pending writes:** SessionDatabase.close() (sessionDatabase.ts:1352-1354) closes the underlying connection without calling `whenIdle()`, even though the `_pendingWrites` set exists expressly 'so whenIdle can await them before the process exits' (comment at lines 461-468) — the exact restart scenario this test simulates.
- **test violates repo's own flaky-test-avoidance convention:** src/vs/platform/agentHost/test/node/AGENTS.md requires `SessionDatabase.open(':memory:')` for every test touching SessionDatabase; this is the only test in the directory using a real on-disk file (sessionWorkspaceConversion.test.ts:1812-1834), which the convention is presumably there to avoid.
