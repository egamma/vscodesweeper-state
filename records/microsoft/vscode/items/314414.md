# Issue #314414 — Enforce `extensions.allowed` policy from the Remote (Server) side during Remote - SSH sessions

[https://github.com/microsoft/vscode/issues/314414](https://github.com/microsoft/vscode/issues/314414)

## Summary

This remains a valid, well-supported backlog request: current main performs extension allowlist checks in the remote server process, but that process uses `NullPolicyService`, so `/etc/vscode/policy.json` cannot supply the remote policy. Route it to the remote, extension-management, and group-policy owners for an architectural decision.

## Change summary

Enforce the remote machine's `extensions.allowed` enterprise policy for extensions installed into a Remote-SSH environment, independently of the client's local allowlist.

## Best solution

Make the VS Code Server's policy source authoritative for remote extension installation while exposing enough target-specific policy state for the client Extensions view to represent remote eligibility correctly. Preserve the local policy for local installations and define explicitly whether client and server restrictions intersect for remote operations.

## Plan brief

- **Likely files:** `src/vs/server/node/serverServices.ts`, `src/vs/server/node/serverEnvironmentService.ts`, `src/vs/platform/policy/common/filePolicyService.ts`, `src/vs/platform/extensionManagement/common/extensionManagementIpc.ts`, `src/vs/workbench/services/extensionManagement/common/remoteExtensionManagementService.ts`
- **Validation:** Add a targeted remote-server policy test that loads an `AllowedExtensions` value from a temporary policy source and verifies a disallowed remote installation is rejected, then run it with `scripts/test.sh --grep "remote server extension policy"`; also verify target-specific policy presentation in a Remote-SSH window.
- **Behavior:**

  > During a remote session, extensions installed into the remote environment must be evaluated against the remote machine's enterprise allowlist, while local installations remain governed by the client's policy. A disallowed remote extension must be rejected by the server even if installation is initiated through the client UI. The Extensions view must report eligibility for the selected local or remote target using the policy that governs that target.
- **Trace:**

  > The remote server creates its `ConfigurationService` with `NullPolicyService` in `src/vs/server/node/serverServices.ts`, so `AllowedExtensionsService` receives no remote policy despite being registered in the same server service collection. Remote install RPCs in `src/vs/platform/extensionManagement/common/extensionManagementIpc.ts` reach the native server `ExtensionManagementService`, whose VSIX and gallery paths already consult `IAllowedExtensionsService`; authoritative rejection therefore already has a server-side enforcement point. Native desktop and CLI startup use `FilePolicyService` with the Linux system policy path, providing the existing policy-loading precedent. The uncertainty begins at policy precedence and presentation: the client-side extension-management path also evaluates its own allowlist, while the Extensions view needs target-specific state. Local installation semantics and non-remote policy behavior must not change.
- **Open decisions:**
  - For remote installations, should eligibility be determined solely by the remote policy or by the intersection of client and remote policies?
  - Should server policy support be generic to every VS Code remote authority or introduced specifically for Remote-SSH?
  - How should remote policy state and denial reasons be surfaced to the client without making client enforcement authoritative?
  - Should the remote server watch policy-file changes during a session, and how should updated policy state reach the Extensions view?

## Evidence

- **server policy gap:** `src/vs/server/node/serverServices.ts` constructs the remote `ConfigurationService` with `new NullPolicyService()`, so policy definitions such as `AllowedExtensions` cannot receive values from the remote machine's `/etc/vscode/policy.json`.
- **server enforcement path:** `src/vs/server/node/serverServices.ts` registers `AllowedExtensionsService` and the native `ExtensionManagementService`; `src/vs/platform/extensionManagement/node/extensionManagementService.ts` and `src/vs/platform/extensionManagement/common/abstractExtensionManagementService.ts` reject VSIX and gallery installations when that service reports an extension is disallowed.
- **existing native policy pattern:** `src/vs/code/electron-main/main.ts` and `src/vs/code/node/cliProcessMain.ts` use `FilePolicyService` with `LINUX_SYSTEM_POLICY_FILE_PATH`, while the remote server does not use that established policy source.
- **remote IPC boundary:** `src/vs/platform/extensionManagement/common/extensionManagementIpc.ts` forwards remote VSIX and gallery installation calls to the server-side extension-management service, confirming that authoritative server rejection is technically within the existing core boundary.
