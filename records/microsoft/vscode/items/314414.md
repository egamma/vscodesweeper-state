# Issue #314414 — Enforce `extensions.allowed` policy from the Remote (Server) side during Remote - SSH sessions

[https://github.com/microsoft/vscode/issues/314414](https://github.com/microsoft/vscode/issues/314414)

## Summary

This remains a valid, well-supported Backlog request: current main explicitly gives the remote server a null policy source, so its extension-management service cannot enforce `/etc/vscode/policy.json`. Route it to the extensions and remote areas for design and implementation.

## Change summary

Allow a Remote - SSH server to enforce its own `extensions.allowed` enterprise policy for extensions installed into that remote environment.

## Best solution

Load managed policy in the VS Code Server, enforce the remote allowlist at the server-side extension-management boundary, and expose enough remote policy state for the client Extensions UI to accurately explain remote installation restrictions without conflating them with the client's local policy.

## Plan brief

- **Likely files:** `src/vs/server/node/serverServices.ts`, `src/vs/platform/extensionManagement/common/extensionManagementIpc.ts`, `src/vs/workbench/services/extensionManagement/electron-browser/remoteExtensionManagementService.ts`, `src/vs/server/test/node/serverMain.test.ts`
- **Validation:** Add server-side extension-management coverage that starts the service with a Linux file policy, permits an allowlisted remote extension, rejects a disallowed gallery or VSIX install, and verifies that local-only policy does not replace the remote policy.
- **Behavior:**

  > During a Remote - SSH session, extension installations targeting the remote environment must be evaluated against the policy configured on that remote machine. Local extension installations remain governed by the client's policy, and the Extensions UI must accurately identify restrictions originating from the remote policy. Acceptance should cover both allowed and denied remote installations and preserve existing behavior when the remote has no managed policy.
- **Trace:**

  > The remote server creates its ConfigurationService with NullPolicyService in src/vs/server/node/serverServices.ts, so `/etc/vscode/policy.json` cannot populate `extensions.allowed`. The same service graph registers AllowedExtensionsService and the native ExtensionManagementService, whose install paths already call `isAllowed`, making the absent policy source the confirmed enforcement gap. Separately, NativeRemoteExtensionManagementService receives the client's IAllowedExtensionsService, so client-side availability and messaging reflect local policy. The work must remain scoped to remote policy loading, server-side installation enforcement, and accurate remote UI state; it must not merge the local and remote allowlists or alter unrestricted remote sessions.

## Evidence

- **confirmed source gap:** On current main, src/vs/server/node/serverServices.ts constructs the remote ConfigurationService with `new NullPolicyService()` even though native Linux startup uses FilePolicyService for `/etc/vscode/policy.json` in src/vs/code/electron-main/main.ts.
- **server enforcement path:** src/vs/server/node/serverServices.ts registers AllowedExtensionsService and the native ExtensionManagementService; src/vs/platform/extensionManagement/node/extensionManagementService.ts checks `allowedExtensionsService.isAllowed()` for VSIX installs, while AbstractExtensionManagementService.canInstall() checks gallery extensions. The enforcement machinery exists but receives no server policy.
- **client policy path:** src/vs/workbench/services/extensionManagement/electron-browser/remoteExtensionManagementService.ts injects the workbench's IAllowedExtensionsService into the remote channel client, confirming that client-side eligibility and UI state currently derive from the local configuration.
