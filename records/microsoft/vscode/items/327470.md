# Issue #327470 — runNotebookCell a cell that generates audio takes up a lot of context

[https://github.com/microsoft/vscode/issues/327470](https://github.com/microsoft/vscode/issues/327470)

## Summary

Real bug, traced in source: when a notebook cell displays audio via IPython's `Audio(...)`, the output is a `text/html` item containing the whole clip base64-embedded in an `<audio src="data:audio/wav;base64,...">` tag, and the tool's size guard doesn't account for base64 tokenizing far worse than prose, so it slips through and gets embedded verbatim in the tool result.

## Change summary

Running a notebook cell that displays audio (via `display(Audio(...))`) balloons the chat context because the raw base64 audio data URI is included as literal text in the tool result.

## Best solution

In `RunNotebookCellOutput` (extensions/copilot/src/extension/tools/node/runNotebookCellTool.tsx), detect base64 data URIs for binary media (audio/video/image) embedded in `text/html` output and swap them for the existing 'output too large to be used as context' placeholder — instead of relying solely on the raw byte-length vs. `getCharLimit` check, which assumes a ~4 chars/token ratio that base64 blobs don't meet.

## Evidence

- **textItem branch has no binary-detection:** extensions/copilot/src/extension/tools/node/runNotebookCellTool.tsx lines 378-395: `text/html` is treated as plain text and only gated by `textItem.data.byteLength > getCharLimit(sizing.tokenBudget / sizeLimitRatio)` — no check for embedded base64 media.
- **getCharLimit assumption:** extensions/copilot/src/extension/prompts/node/inline/summarizedDocument/summarizeDocumentHelpers.ts:18 — `getCharLimit(tokensBudget) { return tokensBudget * 4; }` assumes ~4 chars/token, which undercounts tokens for base64 data (denser, less compressible), so a blob that 'fits' the char budget can still blow up actual token usage.
- **IPython Audio output shape:** IPython.display.Audio(embed=True) emits a `display_data` cell with a `text/html` MIME item containing `<audio controls src="data:audio/wav;base64,..."></audio>`; a 1s 44.1kHz mono WAV is ~88KB raw / ~118K base64 chars, consistent with the reporter's 29k→112.8k context jump.
- **existing precedent:** Image outputs are already special-cased (lines 180-188, extracted as `LanguageModelDataPart.image` instead of inline text) — audio/video data URIs inside `text/html` have no equivalent special handling.
