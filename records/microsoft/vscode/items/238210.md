# Issue #238210 — Inconsistent line copy-paste on Chromebook

[https://github.com/microsoft/vscode/issues/238210](https://github.com/microsoft/vscode/issues/238210)

## Summary

This remains a credible platform-dependent editor clipboard bug: multiple users confirmed that empty-selection copies lose line-copy paste semantics on Linux/ChromeOS and macOS. The current metadata recovery path can fall back to ordinary insertion when clipboard metadata is unavailable and the pasted text differs from the exact in-memory value.

## Change summary

Copying a line with an empty selection sometimes pastes its text at the cursor instead of inserting it as a new line.

## Best solution

Determine which clipboard transformation or event path drops the `isFromEmptySelection` metadata on affected systems, then preserve line-copy semantics without changing ordinary clipboard text pasted from external applications.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/editContext/clipboardUtils.ts`, `src/vs/editor/browser/controller/editContext/textArea/textAreaEditContextInput.ts`, `src/vs/editor/browser/controller/editContext/textArea/textAreaEditContext.ts`
- **Validation:** On an affected Linux/ChromeOS or macOS environment, place the cursor mid-line, press Ctrl+C and Ctrl+V, and verify the copied line is inserted as a separate line; also verify externally copied text still pastes at the cursor normally.
- **Behavior:**

  > With `editor.emptySelectionClipboard` enabled, copying with an empty selection copies the current line and pasting it inserts a separate line regardless of cursor column. This must behave consistently on Linux/ChromeOS, macOS, and other supported platforms. Text copied from outside VS Code, or copied from a non-empty selection, must continue to paste at the cursor normally.
- **Trace:**

  > Copy metadata is produced by `createClipboardCopyEvent` in src/vs/editor/browser/controller/editContext/clipboardUtils.ts and includes `isFromEmptySelection`. `createClipboardPasteEvent` first reads the custom `vscode-editor-data` MIME entry, then falls back to `InMemoryClipboardMetadataManager`, whose lookup requires exact equality between copied and pasted text. `TextAreaEditContext` in src/vs/editor/browser/controller/editContext/textArea/textAreaEditContext.ts enables `pasteOnNewLine` only when that metadata survives. The reported behavior is therefore consistent with metadata being unavailable and the exact-text fallback missing, but the issue record does not establish which clipboard normalization or event path causes that on the affected systems. Keep external clipboard content and explicit-selection paste semantics outside the change boundary.

## Evidence

- **confirmed reports:** The reporter reproduced with extensions disabled on ChromeOS/Linux, another user confirmed the same behavior on macOS 15.1, and a third confirmed it remained present in VS Code 1.100.3: https://github.com/microsoft/vscode/issues/238210
- **clipboard metadata path:** src/vs/editor/browser/controller/editContext/clipboardUtils.ts records `isFromEmptySelection` in `vscode-editor-data`, but its in-memory fallback retrieves that metadata only when the pasted text exactly equals the last copied text.
- **failure behavior:** src/vs/editor/browser/controller/editContext/textArea/textAreaEditContext.ts sets `pasteOnNewLine` only when paste metadata is present and marks the copy as originating from an empty selection; missing metadata therefore produces the reported insertion at the cursor.
- **prior report:** A maintainer explicitly determined that the reporter's case was distinct from the closed regression in https://github.com/microsoft/vscode/issues/201929 and requested this new issue.
- **canonical search:** No open microsoft/vscode issue found by the clipboard/empty-selection search clearly owns this platform-dependent metadata-loss problem.
