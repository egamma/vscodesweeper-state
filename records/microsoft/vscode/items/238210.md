# Issue #238210 — Inconsistent line copy-paste on Chromebook

[https://github.com/microsoft/vscode/issues/238210](https://github.com/microsoft/vscode/issues/238210)

## Summary

Keep open: multiple users confirmed that empty-selection line copies paste inline on affected Linux/Chromebook and macOS installations, and current source still depends on clipboard metadata surviving or matching exactly to select line-wise paste.

## Change summary

Copying a line with an empty selection can lose its line-copy provenance and paste the text at the cursor instead of on a new line.

## Best solution

Trace the clipboard payload on an affected system and make line-copy provenance survive the platform-specific copy/paste path without changing ordinary text pasted from external applications.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/editContext/clipboardUtils.ts`, `src/vs/editor/browser/controller/editContext/textArea/textAreaEditContext.ts`, `src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts`, `src/vs/editor/contrib/clipboard/browser/clipboard.ts`
- **Validation:** Capture the copy and paste DataTransfer payload on an affected Chromebook/Linux setup, add a regression test reproducing that payload through the clipboard event path, and verify Ctrl+C/Ctrl+V with an empty selection inserts the copied line above the cursor while externally copied text still pastes inline.
- **Behavior:**

  > With `editor.emptySelectionClipboard` enabled, copying without a selection and pasting in the editor must insert the copied line as a whole line above the cursor, regardless of the cursor column. This must hold on the affected Chromebook/Linux path and the reported macOS path. Text copied normally from another application must continue to paste at the cursor, and selected editor text must retain normal paste behavior.
- **Trace:**

  > Copy provenance is created by `generateDataToCopy` in src/vs/editor/browser/controller/editContext/clipboardUtils.ts, which sets `isFromEmptySelection` and writes it as `vscode-editor-data`; the same helper also stores metadata in memory keyed by the exact copied text. `TextAreaEditContext` and `NativeEditContext` only pass `pasteOnNewLine: true` when recovered metadata contains that flag, so the reported inline result means metadata is unavailable or mismatched at paste time. The precise loss point cannot be established from source alone because it depends on the clipboard payload produced by the affected platform. Preserve the boundary between editor-originated empty-selection copies and identical text originating externally, and do not alter selected-text or multicursor semantics. The earlier report at https://github.com/microsoft/vscode/issues/201929 was explicitly judged separate by a maintainer.
- **Open decisions:**
  - Which affected input path loses the custom `vscode-editor-data` payload: the text-area path, native EditContext path, Electron clipboard bridge, or platform clipboard normalization?
  - Which platform text transformations can safely be normalized for in-memory metadata matching without mistaking externally copied identical text for an editor line copy?

## Evidence

- **confirmed reports:** The original Chromebook/Linux reproduction was independently confirmed on macOS 15.1 at https://github.com/microsoft/vscode/issues/238210#issuecomment-2602236683 and again on VS Code 1.100.3 at https://github.com/microsoft/vscode/issues/238210#issuecomment-2987585820.
- **separate issue:** A maintainer explicitly determined that the Chromebook report was distinct from https://github.com/microsoft/vscode/issues/201929 and asked for this new issue at https://github.com/microsoft/vscode/issues/201929#issuecomment-2557309773.
- **current source path:** src/vs/editor/browser/controller/editContext/clipboardUtils.ts records `isFromEmptySelection` in `vscode-editor-data` and falls back to InMemoryClipboardMetadataManager only when pasted text exactly matches the copied text; textAreaEditContext.ts and nativeEditContext.ts set `pasteOnNewLine` only when that metadata is available.
- **current triage:** Maintainers classified the issue as `bug`, `editor-clipboard`, and `linux` in December 2025; the timeline contains no fixing PR, closing reference, or canonical duplicate.
