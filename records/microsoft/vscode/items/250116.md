Keep open: current source still drops same-identifier extension updates from contribution deltas, leaving debugger registrations and launch.json validation stale after Restart Extension. ## Evidence

- **Reported trigger and workaround:** https://github.com/microsoft/vscode/issues/250116 describes replacing C/C++ 1.25.3 with a VSIX adding cpplldb, then selecting Restart Extension: language-service features update, but the new debugger type remains unsupported until Reload Window. The author also reproduced the behavior on macOS.
- **Replacement reaches contribution handling:** src/vs/workbench/services/extensions/common/abstractExtensionService.ts: startExtensionHosts processes replacement updates through _handleDeltaExtensions; _deltaExtensions updates the extension registry and invokes _doHandleExtensionPoints. _handleExtensionPoint rebuilds contribution users from current descriptions and calls acceptUsers.
- **Current delta loses replacements:** src/vs/workbench/services/extensions/common/extensionsRegistry.ts: ExtensionPointUserDelta.compute compares only description.identifier membership. Replacing an extension with the same identifier produces neither an added nor a removed user, even when its version and debugger contributions change; there is no changed collection.
- **Debugger consumer retains stale state:** src/vs/workbench/contrib/debug/browser/debugAdapterManager.ts: AdapterManager.registerListeners creates or merges non-wildcard debugger contributions only from delta.added and removes them only from delta.removed. With both empty, newly contributed cpplldb is never registered, and updateDebugAdapterSchema rebuilds launch.json validation from the existing stale this.debuggers array. This confirms the reported failure path from source without executing code.
