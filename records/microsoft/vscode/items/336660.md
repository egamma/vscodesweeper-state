# Issue #336660 — Agents Window SSH fails with Kerberos/GSSAPI authentication while Remote-SSH works

[https://github.com/microsoft/vscode/issues/336660](https://github.com/microsoft/vscode/issues/336660)

## Summary

Confirmed real gap: the Agents Window's SSH connection code (ssh2-based) has no GSSAPI/Kerberos auth method at all, unlike Remote-SSH which can use the system OpenSSH client — this stays open as a genuine, unaddressed limitation, distinct from the unrelated host-key-format issue surfaced by the keyword search.

## Change summary

Agents Window SSH connections fail with Kerberos/GSSAPI-authenticated hosts that Remote-SSH connects to successfully.

## Best solution

A maintainer needs to pick a design: add GSSAPI support to the ssh2-based auth pipeline (if feasible at all — the ssh2 npm library historically doesn't support gssapi-with-mic/gssapi-keyex), shell out to the system SSH client as a fallback like Remote-SSH does, or have the Agents Window reuse an already-authenticated Remote-SSH tunnel instead of opening a second connection.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts`, `src/vs/platform/agentHost/common/sshRemoteAgentHost.ts`
- **Validation:** An integration/e2e test connecting the Agents Window's SSH client to a GSSAPI-only test host and confirming a successful session, once the chosen approach is implemented.
- **Trace:**

  > The Agents Window's SSH client builds its list of authentication attempts in _buildAuthAttempts (src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts) using only agent/publickey/password/keyboard-interactive; the underlying 'ssh2' npm package used for the raw protocol has no GSSAPI support built into this codebase's usage. Remote-SSH, by contrast, is understood to shell out to (or otherwise leverage) the system OpenSSH client, which negotiates gssapi-with-mic itself. The boundary for any fix is this connection-establishment path; do not change the existing publickey/agent/password/keyboard-interactive flows.
- **Open decisions:**
  - Should the Agents Window gain native GSSAPI/Kerberos support in its ssh2-based auth pipeline, or should it fall back to spawning the system SSH client (as Remote-SSH effectively does) for such hosts?
  - Should the Agents Window instead be able to attach to/reuse an already-established Remote-SSH connection rather than opening an independent SSH session at all?

## Evidence

- **auth methods enumerated:** src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts _buildAuthAttempts (lines ~1688-1745) only ever pushes 'agent', 'publickey', 'password', or 'keyboard-interactive' SSHAuthAttempt entries; no gssapi variant exists.
- **auth attempt type union:** The SSHAuthAttempt type (line ~170) and toAuthMethod() (line ~211) only handle publickey/agent/password/keyboard-interactive/none — ssh2's AnyAuthMethod gssapi types are never constructed.
- **library dependency:** The connection is built on the 'ssh2' npm package (import at line 7), which is a known limitation for GSSAPI/Kerberos support, unlike system OpenSSH used by Remote-SSH.
