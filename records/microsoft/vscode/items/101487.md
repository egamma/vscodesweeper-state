# Issue #101487 — Quick open: Include symbols should not block the search based on filename

[https://github.com/microsoft/vscode/issues/101487](https://github.com/microsoft/vscode/issues/101487)

## Summary

Keep open: current Quick Open still waits for workspace symbols before displaying newly searched files when includeSymbols is enabled. This accepted, community-supported request needs a decision about how late symbol results interact with keyboard navigation.

## Change summary

Display filename search results without waiting for slow workspace-symbol providers, then incorporate symbol results when available.

## Best solution

Quick Open should make completed file results usable while symbol search continues, without changing the item a user is navigating to or accepting. Settle the late-result ordering behavior in the search Quick Access area before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts`, `src/vs/platform/quickinput/browser/pickerQuickAccess.ts`, `src/vs/workbench/contrib/search/browser/symbolsQuickAccess.ts`
- **Validation:** Use a controlled workspace-symbol provider whose response remains pending while a matching file search completes. With includeSymbols enabled, assert that the file becomes visible and can be opened before releasing the symbol response; then release it and verify symbol visibility and the agreed keyboard-selection behavior. Repeat with a changed query and a closed picker to ensure stale results do not appear, and with includeSymbols disabled to preserve file-only behavior.
- **Behavior:**

  > With search.quickOpen.includeSymbols enabled, a Ctrl+P filename query must expose completed file matches while workspace-symbol results are still pending. Users must be able to open a file without waiting for the symbol provider. Later symbol results must become available without causing Enter to accept an unintended item during keyboard navigation. Acceptance checks should control provider completion order and cover query changes, picker dismissal, and unchanged file-only behavior.
- **Trace:**

  > AnythingQuickAccessProvider.getAdditionalPicks in src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts waits for both getFilePicks and getWorkspaceSymbolPicks, then jointly ranks their results. Its fast/slow return exposes help and history separately, but places all new files and symbols in the same slow promise. getWorkspaceSymbolPicks delegates to SymbolsQuickAccessProvider.getSymbolPicks in src/vs/workbench/contrib/search/browser/symbolsQuickAccess.ts, which awaits workspace-symbol collection. PickerQuickAccessProvider in src/vs/platform/quickinput/browser/pickerQuickAccess.ts already supports delayed additional results and active-fast-item preservation; that does not remove the inner file/symbol barrier. Preserve cancellation, history exclusion, matching, disabled-symbol behavior, and unrelated picker consumers. The thread at https://github.com/microsoft/vscode/issues/101487 leaves late-result intermixing unresolved; https://github.com/microsoft/vscode/issues/186560 corroborates the same latency but adds provider feedback that is outside this request's necessary scope. The source path was inspected only; runtime timing was not measured.
- **Open decisions:**
  - When symbols arrive after file results are already being navigated, should they enter the existing combined fuzzy ranking or remain in a separate stable section, and what ordering behavior should apply once keyboard navigation has begun?

## Evidence

- **Current blocking path:** In src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts, getAdditionalPicks awaits Promise.all([getFilePicks(...), getWorkspaceSymbolPicks(...)]) before sorting and returning either result set. For the reporter's trigger—Ctrl+P filename search with search.quickOpen.includeSymbols enabled—a pending symbol search therefore withholds completed file-search results.
- **Existing incremental support does not cover files:** AnythingQuickAccessProvider returns help and editor-history entries as fast picks, but files and symbols together as one additionalPicks promise. The 200 ms mergeDelay can expose history early, not newly searched files. src/vs/platform/quickinput/browser/pickerQuickAccess.ts supports this fast/slow split and preserves an active fast pick, but does not independently publish the two searches inside additionalPicks.
- **Existing setting is only a workaround:** src/vs/workbench/contrib/search/browser/search.contribution.ts registers search.quickOpen.includeSymbols with default false. Disabling it bypasses workspace symbols, while anythingQuickAccess.ts:getWorkspaceSymbolPicks delegates enabled queries to SymbolsQuickAccessProvider.getSymbolPicks. Disabling symbols does not satisfy the request to retain both result sources without blocking files.
- **Accepted request and unresolved UX:** https://github.com/microsoft/vscode/issues/101487 has 23 upvotes and was promoted to Backlog. The reporter clarified that incremental arrival, not files-first final ranking, is the central request; bpasero acknowledged that clarification and raised the risk of results becoming intermixed during navigation.
- **Older related issues are not canonicals:** https://github.com/microsoft/vscode/issues/27317 is open but concerns ranking and matching, not delayed filename-result publication. https://github.com/microsoft/vscode/issues/91445 concerns slow providers within the symbols picker and is closed after insufficient community votes; it is neither an open duplicate target nor a decision declining this accepted request.
- **Newer matching report:** https://github.com/microsoft/vscode/issues/186560 is open, was created on 2023-06-28, and reports approximately 15-second time-to-first-file-result with includeSymbols enabled, plus a separate request for slow-provider feedback. Its matching symptom corroborates the gap, but it is younger than this 2020 report and cannot be its canonical under the re-review rules.
