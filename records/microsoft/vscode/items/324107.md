# Issue #324107 — Agent window session in a new worktree doesn't open editor in the worktree location immediately

[https://github.com/microsoft/vscode/issues/324107](https://github.com/microsoft/vscode/issues/324107)

## Summary

Verified duplicate: the 'open in editor' action reads the session's workspace folder URI via `activeSession.workspace.get()`, which was stale before worktree materialization completed — the same root cause as https://github.com/microsoft/vscode/issues/322529, fixed in commit 6759ccd0c77.

## Change summary

Clicking 'Open in Editor' in the Agents window nav bar opens the original folder instead of the worktree until metadata catches up.

## Best solution

Consolidate on https://github.com/microsoft/vscode/issues/322529 — the worktree metadata timing fix (commit 6759ccd0c77) updates cached session adapters when the worktree is materialized, which is exactly the data `OpenSessionInVSCodeAction.getFolderUriToOpen` reads. If the symptom persists after that fix, a follow-up issue with new evidence would be appropriate.

## Evidence

- **root cause:** OpenSessionInVSCodeAction.getFolderUriToOpen (src/vs/sessions/electron-browser/actions/vscodeActions.ts:70-96) reads activeSession.workspace.get()?.folders[0]?.workingDirectory. Before the timing fix, this returned the original folder URI because worktree metadata had not yet propagated to the session adapter.
- **canonical issue:** https://github.com/microsoft/vscode/issues/322529 ('Worktree information is getting updated only after first turn') tracks the same worktree metadata timing problem. It is closed and verified.
- **fix commit:** https://github.com/microsoft/vscode/commit/6759ccd0c77 (PR #324280) fixes the timing by updating cached session adapters when worktree materialization publishes the final path, deferring Git-state refreshes, and overlaying live workspace metadata on session-list snapshots.
