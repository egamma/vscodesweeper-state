# Issue #117849 — [remote cli] support opening `file` URIs

[https://github.com/microsoft/vscode/issues/117849](https://github.com/microsoft/vscode/issues/117849)

## Summary

The original `$BROWSER` failure was removed in 1.54, but the reporter and maintainer explicitly confirmed that opening remote `file:` URIs still does not work. The remaining feature request should stay open for a product decision rather than be treated as fixed.

## Change summary

Provide a Remote WSL facility that opens a remote `file:` URI in the Windows host browser using a correctly translated UNC URI.

## Best solution

Define a supported remote-CLI URI-opening contract that can translate WSL file URIs to host-accessible URIs and safely launch the host browser, while preserving the existing behavior for ordinary HTTP(S) URLs.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/remote/browser/remote.contribution.ts`, `src/vs/workbench/contrib/remote/common/remoteExplorerService.ts`
- **Validation:** From a Remote WSL integrated terminal, invoke the chosen supported facility with `file:///tmp`; verify that the Windows browser receives a working `file://///wsl$/<distribution>/tmp` URI, and verify that existing HTTP(S) opening behavior is unchanged.
- **Behavior:**

  > Programs running in a Remote WSL terminal should have a supported way to request opening a remote `file:` URI in the host browser. A URI such as `file:///tmp` must resolve to the corresponding host-accessible WSL UNC URI and open successfully. HTTP(S) browser launching and non-remote terminal behavior must remain unchanged.
- **Trace:**

  > The issue's original path depended on VS Code setting `BROWSER` to its remote `browser.sh`; a maintainer says that behavior was removed in 1.54, but also confirms the central `webbrowser.open('file://...')` scenario remains unsupported. The reporter demonstrates that `wslview` can perform the required WSL-to-host URI translation, establishing feasibility but not which VS Code contract should expose it. The uncertainty starts at the public integration boundary: whether VS Code should expose a browser-compatible command through environment setup or a narrower remote CLI URI opener, and whether the contract is WSL-specific or common to remote authorities. Keep this scoped to URI opening; do not restore the old blanket `$BROWSER` behavior without deciding its effects on HTTP(S) and other remote environments.
- **Open decisions:**
  - Should remote applications consume this through a browser-compatible environment command, or through an explicit VS Code remote-CLI URI-opening contract?
  - Is host opening of `file:` URIs supported only for WSL paths, or must the contract define behavior for other remote authorities as well?
