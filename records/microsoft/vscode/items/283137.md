# Issue #283137 — Option to "pin" attached context files in Copilot Chat for persistent usage

[https://github.com/microsoft/vscode/issues/283137](https://github.com/microsoft/vscode/issues/283137)

## Summary

This accepted Backlog request remains necessary: current main clears ordinary file attachments after submission, while only prompt/instruction-file entries survive, and 31 upvotes demonstrate sustained demand for an explicit session-scoped context guarantee.

## Change summary

Allow users to pin explicitly attached Copilot Chat files so they remain visibly and reliably included across requests in the same conversation until unpinned.

## Best solution

Provide a session-scoped pinned state for explicit chat attachments, retain pinned pills after each submission, and define how their guaranteed inclusion interacts with context limits and conversation compaction.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentModel.ts`, `src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentWidgets.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts`, `src/vs/workbench/contrib/chat/common/attachments/chatVariableEntries.ts`
- **Validation:** Add a targeted ChatAttachmentModel test showing that normal submission clearing preserves a pinned ordinary file, removes an unpinned file, and that full clearing for a new chat removes both; also verify through the chat input that pinning keeps the attachment pill across consecutive submissions.
- **Behavior:**

  > Users can pin an explicitly attached file within one Copilot Chat conversation. A pinned file remains visibly attached and is included in subsequent requests until the user unpins or removes it; unpinned attachments retain the current post-submission behavior, and starting a new chat does not carry the pin forward. Acceptance should cover consecutive submissions, explicit unpin/removal, and new-chat clearing.
- **Trace:**

  > ChatInputPart.acceptInput in src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts calls ChatAttachmentModel.clear after submission. ChatAttachmentModel.clear in src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentModel.ts currently preserves only `promptFile` entries identified by isPromptFileVariableEntry; ordinary `file` entries are deleted. Attachment presentation and resource context menus are implemented in src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentWidgets.ts, while entry shapes live in src/vs/workbench/contrib/chat/common/attachments/chatVariableEntries.ts. The boundary is per-conversation explicit attachments: do not make pins global, alter automatic current-editor context, or change ordinary unpinned attachment behavior. The unresolved point is the public guarantee when pinned content exceeds the model context budget or the conversation is compacted.
- **Open decisions:**
  - When pinned files and other required context exceed the model context budget, must VS Code fail or prompt before sending, or may pinned content be reduced or omitted with an explicit warning?
  - Should pinning resend the file's current contents on every request, or preserve the originally attached snapshot until the user reattaches it?

## Evidence

- **current source behavior:** src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts calls `attachmentModel.clear()` after accepting input; src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentModel.ts removes every attachment except entries recognized by `isPromptFileVariableEntry`, so an ordinary user-attached file cannot currently remain pinned.
- **existing special case:** src/vs/workbench/contrib/chat/common/attachments/chatVariableEntries.ts defines prompt and instruction files as `promptFile` entries, confirming that persistence exists for that specialized context kind but not for arbitrary attached files.
