# Issue #326232 — Restore Remote-SSH support for 32-bit ARM Linux (armv7l) targets

[https://github.com/microsoft/vscode/issues/326232](https://github.com/microsoft/vscode/issues/326232)

## Summary

Keep open as a platform-support feature request: current source explicitly excludes ARM32 remote servers, so the requested capability remains missing. Restoring support requires a runtime and maintenance decision, not merely changing Remote-SSH or enabling a setting.

## Change summary

Restore officially supported remote editing and debugging on Linux armv7l devices without requiring a 64-bit OS or permanently frozen editor.

## Best solution

Evaluate a maintainable ARM32 server/runtime support path in the core server build and release infrastructure, coordinating Remote-SSH compatibility with its owners. Decide whether full current-server support or a supported compatibility server can satisfy embedded-device workflows before implementing either.

## Plan brief

- **Likely files:** `cli/src/update_service.rs`, `build/gulpfile.reh.ts`, `remote/.npmrc`, `build/azure-pipelines/linux/steps/product-build-linux-compile.yml`
- **Validation:** On a supported 32-bit Raspberry Pi OS armv7l target, connect from a current Windows VS Code client using Remote-SSH; verify server installation completes, a remote workspace opens, editing and an available debugger work, and reconnecting succeeds without freezing the client. Also verify existing Linux x64 and ARM64 connections remain functional.
- **Behavior:**

  > Users whose embedded Linux devices must remain on armv7l need an officially maintained way to edit and debug remotely without reflashing to a 64-bit OS or permanently pinning their editor. Current connections fail with UnsupportedPlatform("LinuxARM32"). Acceptance should demonstrate successful server installation, remote workspace editing, debugging with a compatible extension, and reconnection on a representative 32-bit Raspberry Pi OS device. The maintainer must first establish whether support means the current server or a compatibility server and what capabilities that supported path promises.
- **Trace:**

  > Platform::headless() in cli/src/update_service.rs explicitly rejects LinuxARM32 and LinuxARM32Legacy, and server release lookup turns that missing download segment into UnsupportedPlatform. build/gulpfile.reh.ts excludes armhf server targets, while build/azure-pipelines/linux/steps/product-build-linux-compile.yml skips ARM32 server production; remote/.npmrc selects Node.js 24.21.0. The source comment names Node.js v24's armv7 support removal, but the feasibility of a maintained alternative runtime and compatible server dependencies has not been established. Existing ARM32 desktop and CLI artifacts do not supply the requested server, and SFTP does not replace remote debugging. Preserve existing supported-platform behavior; do not treat removal of the platform guard alone as restored support. https://github.com/microsoft/vscode/issues/325867 describes a distinct Darwin archive-format failure, not this support gap.
- **Open decisions:**
  - Should official armv7l support provide the full current server or a compatibility server, and which editing, debugging, and extension capabilities must that option guarantee?
  - Which ARM32 OS/runtime baseline and update-support lifetime would the project commit to maintaining?

## Evidence

- **Current server exclusion:** cli/src/update_service.rs:238–255, Platform::headless(), explicitly returns None for LinuxARM32 and LinuxARM32Legacy, with a comment attributing the exclusion to Node.js v24 dropping 32-bit Linux armv7. TargetKind::Server delegates to headless(); release lookup converts the missing download segment to CodeError::UnsupportedPlatform.
- **Build and runtime boundary:** build/gulpfile.reh.ts:46–57 omits Linux armhf from BUILD_TARGETS. build/azure-pipelines/linux/steps/product-build-linux-compile.yml explicitly skips server builds when VSCODE_ARCH is armhf. remote/.npmrc currently selects Node.js 24.21.0. These are core server/runtime constraints, not evidence that the installed Remote-SSH extension itself is defective.
- **Existing capabilities do not cover the request:** cli/src/update_service.rs retains linux-armhf desktop archives and cli-linux-armhf CLI artifacts, but neither supplies an ARM32 remote server; web server downloads also delegate to headless(). The reported frozen-version workaround and SFTP workaround do not provide maintained Remote-SSH editing and debugging.
