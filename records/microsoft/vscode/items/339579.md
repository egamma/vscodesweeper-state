# Issue #339579 — Insiders 1.141.0: "Cannot find package 'koffi'" - build/.moduleignore strips koffi now required by @microsoft/mxc-sdk 0.9.0

[https://github.com/microsoft/vscode/issues/339579](https://github.com/microsoft/vscode/issues/339579)

## Summary

Confirmed from source: build/.moduleignore unconditionally strips koffi/@koromix/koffi-*, but package-lock.json shows @microsoft/mxc-sdk@0.9.0 directly depends on koffi (^3.2.1) at runtime — the exclusion comment predates that dependency and was never updated, so packaged Insiders builds >= 1.141.0 ship a broken mxc-sdk binding. Real gap, no fix on main yet.

## Change summary

Agent shell tooling fails with "Cannot find package 'koffi'" because build/.moduleignore strips koffi from the shipped product even though @microsoft/mxc-sdk 0.9.0 now requires it at runtime.

## Best solution

Narrow or drop the koffi/@koromix exclusion in build/.moduleignore so @microsoft/mxc-sdk's koffi dependency ships in the packaged product, likely mirroring the existing arch-aware filtering build/lib/copilot.ts already applies to @microsoft/mxc-sdk/bin/<arch> so only the target platform's koffi native binary is included.

## Plan brief

- **Behavior:**

  > A packaged VS Code build (>=1.141.0) must ship the koffi runtime that @microsoft/mxc-sdk's native bindings (dist/bindings/run.js) import, so agent shell tools backed by mxc-sdk work instead of throwing "Cannot find package 'koffi'". Acceptance: in a built product, the mxc-sdk koffi import resolves successfully on the target platform/architecture, without bloating the package with every platform's native koffi binary.
- **Trace:**

  > build/.moduleignore (~lines 270-273) strips `koffi/**` and `@koromix/koffi-*/**` under a comment stating only @github/copilot-sdk's unused in-process FFI transport needs koffi. That's now stale: package-lock.json shows @microsoft/mxc-sdk@0.9.0 declares `koffi: "^3.2.1"` as a direct dependency, and its dist/bindings/run.js imports koffi at runtime (per the issue and the PR #338828 description bumping mxc-sdk 0.8.0 -> 0.9.0, cited as adding koffi). build/lib/copilot.ts already has precedent for arch-aware mxc-sdk packaging (stripArchSpecificMxcSdkBinaries filtering @microsoft/mxc-sdk/bin/<arch>), suggesting the natural fix mirrors that pattern for @koromix/koffi-<platform>-<arch> rather than a blanket un-exclusion. Boundary: only the koffi/@koromix exclusion should change; do not touch unrelated .moduleignore rules such as the copilot-sdk/ripgrep entries covered by the separate issue https://github.com/microsoft/vscode/issues/337976.
- **Open decisions:**
  - Should the koffi/@koromix exclusion be dropped entirely (shipping koffi for all platforms), or narrowed to arch-aware filtering matching the existing @microsoft/mxc-sdk/bin/<arch> pattern in build/lib/copilot.ts?
  - Does @github/copilot-sdk's own (currently unused) in-process FFI transport still need any guard against shipping koffi, or is the whole exclusion now obsolete?
