# Issue #320587 — Git scheme URI fails to locate correct repo after splitting submodule

[https://github.com/microsoft/vscode/issues/320587](https://github.com/microsoft/vscode/issues/320587)

## Summary

Historical Git content is still resolved against the deepest currently open repository, even when the requested revision belongs to its parent. Keep this open; the failing lookup is confirmed in source, but automatic fallback versus explicit repository selection needs a maintainer decision.

## Change summary

Allow historical file comparisons from a parent repository after the file's directory becomes an independent nested repository.

## Best solution

Historical Git URI reads should resolve the requested content in the intended repository without changing ordinary working-tree and index repository selection. Decide whether existing path/ref URIs automatically search enclosing repositories or require an explicit repository identity for this case.

Acceptance includes exercising both metadata lookup and content reads with both repositories open.
- **Trace:**

  > Model.getRepository and getOpenRepository in extensions/git/src/model.ts select the deepest enclosing open repository using only the Git URI query path; the query ref does not participate. GitFileSystemProvider.getOrOpenRepository in extensions/git/src/fileSystemProvider.ts accepts that result immediately, and stat/readFile perform historical lookups only in that repository. Repository.buffer ultimately invokes git show against that repository in extensions/git/src/git.ts, so a parent-only pre-split commit cannot resolve. The source establishes this failure without running the UI. GitUriParams and GitUriOptions in extensions/git/src/uri.ts lack general repository identity; submoduleOf has distinct submodule-diff semantics and must not be repurposed silently. The issue at https://github.com/microsoft/vscode/issues/320587 proposes automatic reference-aware lookup or explicit repository selection but does not settle that observable contract. Preserve ordinary synchronous repository consumers and existing index/submodule behavior; a broad async API migration is not itself a product requirement.
- **Open decisions:**
  - Should existing path/ref Git URIs automatically resolve parent-only historical objects through enclosing repositories, or should callers explicitly identify the intended repository through a supported URI contract?

## Evidence

- **Reported trigger:** https://github.com/microsoft/vscode/issues/320587 describes vscode.diff with git URIs containing an absolute file path and a pre-split commit expression such as hash^1. The nested directory is an independent repository, explicitly not a Git submodule.
- **Current source confirms incorrect selection:** extensions/git/src/model.ts:929-931 and 973-997 show Model.getRepository delegating to getOpenRepository. For git URIs, it extracts only the query path, sorts open repositories by descending root length, and returns the first enclosing repository without examining ref. With both repositories open, sdk/drv/xxx therefore wins over sdk regardless of which repository contains the historical commit.
- **Historical read has no fallback:** extensions/git/src/fileSystemProvider.ts getOrOpenRepository immediately returns that selected repository. Both stat and readFile use it; failed historical object lookup becomes FileNotFound rather than trying the parent. extensions/git/src/git.ts:1586-1606 executes git show --textconv ref:relativePath in the selected repository. This conclusively establishes the missing historical-content path, although the reported empty diff presentation was not executed.
- **Existing URI mechanism does not cover this case:** extensions/git/src/uri.ts defines path, ref, and optional submoduleOf, but no general repository identity. submoduleOf is not a substitute: GitFileSystemProvider.readFile interprets it as a submodule diff request and calls diffIndexWithHEAD or diffWithHEAD rather than reading arbitrary historical file contents.
- **Historical validation distinction:** extensions/git/src/repository.ts:2676-2681 and extensions/git/src/git.ts:1612-1650 show that getObjectFiles uses ls-tree; getObjectDetails uses ls-files for index references and ls-tree for historical trees. The reporter's suggested historical check should not be treated as an ordinary current-index membership check.
