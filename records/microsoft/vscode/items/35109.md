# Issue #35109 — Allow to switch to folder/workspace without window reload

[https://github.com/microsoft/vscode/issues/35109](https://github.com/microsoft/vscode/issues/35109)

## Summary

Keep open: ordinary Open Folder still loads the workbench again, while existing reload-free workspace-entry mechanisms cover only narrower scenarios. The accepted Backlog request remains necessary; no verified older canonical or complete fix was found.

## Change summary

Allow opening a folder from an empty window and switching workspaces without reloading the window.

## Best solution

Support reload-free workspace transitions with correct destination state, editor and backup restoration, and extension-host lifecycle handling. Start by evaluating empty-window-to-workspace transitions, as suggested in the maintainer discussion, before extending this to existing-workspace switches.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/actions/workspaceActions.ts`, `src/vs/workbench/services/dialogs/electron-browser/fileDialogService.ts`, `src/vs/platform/windows/electron-main/windowsMainService.ts`, `src/vs/workbench/services/workspaces/browser/abstractWorkspaceEditingService.ts`, `src/vs/workbench/services/workspaces/electron-browser/workspaceEditingService.ts`
- **Validation:** On desktop, open an empty window, use Explorer's Open Folder button, and verify that the renderer document is not reloaded while the destination folder, settings and enabled extensions become active. Repeat with a previously opened destination containing saved editor state and untitled backups; verify the agreed restoration behavior. Extend acceptance checks to existing-workspace and remote transitions only if included in the approved scope.
- **Behavior:**

  > Opening a folder from an empty window should activate that folder without reloading the workbench. Workspace transitions must apply destination configuration and enabled extensions and handle destination editor state and backups consistently. Acceptance includes both a never-opened folder and a previously opened destination. The initial supported transition set and treatment of existing empty-window editors must be agreed before implementation.
- **Trace:**

  > OpenFolderAction in src/vs/workbench/browser/actions/workspaceActions.ts calls the native file-dialog opening path, which reaches WindowsMainService and loads the workbench document again. A separate reload-free entry path exists in AbstractWorkspaceEditingService.doEnterWorkspace and the electron WorkspaceEditingService.enterWorkspace; it initializes workspace configuration, preserves storage data, reinitializes backups and restarts extension hosts, but reloads when remoteAuthority is present. https://github.com/microsoft/vscode/pull/54129 explicitly documents why the internal entry command does not fulfill general workspace switching. The thread on https://github.com/microsoft/vscode/issues/35109 calls out state restoration, backups and lifecycle consequences as remaining work. Preserve ordinary folder identity, destination settings, extension enablement and existing multi-root behavior; replacing a single-folder workspace with a synthetic multi-root workspace is not equivalent coverage. The trace does not establish all state-restoration consumers or safe lifecycle boundaries, so planning must enumerate those before treating this as a bounded implementation.
- **Open decisions:**
  - Should initial reload-free support cover only empty-window-to-local-folder/workspace transitions, or also switching existing workspaces and remote contexts?
  - When an empty window already contains editors or untitled files, how should those coexist with the destination's restored editors and backups?

- **Partial implementation, not completion:** https://github.com/microsoft/vscode/pull/54129 is merged, but its description explicitly says it is not a full fix for this issue. Its _workbench.enterWorkspace mechanism does not restore destination UI state or merge destination untitled-file backups and was intended for narrower Live Share scenarios.
