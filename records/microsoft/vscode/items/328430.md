# Issue #328430 — Github Copilot change from Agent to Plan Mode triggers "Start Implementation" 

[https://github.com/microsoft/vscode/issues/328430](https://github.com/microsoft/vscode/issues/328430)

## Summary

Confirmed defect, root-caused by roblourens (MEMBER) and independently verified in the current checkout: switching from Agent to Plan mode under Autopilot auto-executes Plan's 'Start implementation' handoff, wiping the user's draft, because the built-in response mode lookup was dropped in a refactor. Should be routed for a fix, not closed; the current `info-needed` label no longer fits now that the repro and root cause are established.

## Change summary

In an Autopilot session, switching the mode picker from Agent to Plan mid-conversation (after a completed Agent response) deletes the user's typed prompt and auto-sends 'Start implementation' instead.

## Best solution

In `renderChatSuggestNextWidget()` (src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts), resolve the built-in response mode via `modes.findModeById(modeInfo.kind)` when `modeInfo.modeInstructions` is absent, before falling back to the current input mode; this restores correct handoff/mode resolution for responses produced by built-in modes like Agent.

- **Fix prompt:**

  > In src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts, `renderChatSuggestNextWidget()` (~line 1604) derives `responseMode` to decide which mode's handoffs to show/auto-execute. Today it only resolves the mode that produced the last response via `modeInfo?.modeInstructions?.name` (looked up with `modes.findModeByName(...)`); when the last response came from a *built-in* mode like Agent, `modeInfo.modeInstructions` is undefined (only custom modes persist it), so the code falls through to `this.input.currentModeObs.get()` — the *newly selected* mode (e.g. Plan) rather than the mode that actually produced the response. Since the user is in Autopilot (`this.inputPart.currentModeInfo.permissionLevel === ChatPermissionLevel.Autopilot`), it then immediately auto-executes Plan's first `send: true` handoff via `this.handleNextPromptSelection(autoSendHandoff)`, which overwrites the user's freshly-typed draft with the handoff prompt ('Start implementation') and submits it — this matches the reporter's video exactly. Fix: before falling back to `currentModeObs`, first try `modes.findModeById(modeInfo.kind)` when `modeInfo?.kind` is defined (built-in modes are identified by `ChatModeKind`, per `IChatRequestModeInfo.kind: ChatModeKind | undefined` in src/vs/workbench/contrib/chat/common/model/chatModel.ts, and `findModeById(id: string | ChatModeKind)` already exists in src/vs/workbench/contrib/chat/common/chatModes.ts). Only fall back to `currentModeObs.get()` when neither `modeInstructions.name` nor `kind` yields a match (very old sessions). Do not change the Autopilot auto-handoff behavior itself, the handoff-selection logic, or any other caller of `renderChatSuggestNextWidget`. Add a test covering: last response has `modeInfo = { kind: ChatModeKind.Agent, modeInstructions: undefined, ... }`, permission level Autopilot, current mode switched to Plan, non-empty draft in the input — assert the draft survives and no `handleNextPromptSelection`/auto-send occurs.
