# Issue #71177 — No clue that server ready action is running

[https://github.com/microsoft/vscode/issues/71177](https://github.com/microsoft/vscode/issues/71177)

## Summary

The requested feedback is still missing: the current server-ready action launches the external browser without announcing the matched address or launch attempt. Keep this accepted Backlog request open; the discussion supports adding feedback but leaves its presentation unsettled.

## Change summary

Provide visible feedback when a server-ready pattern matches and VS Code starts opening the configured browser.

## Best solution

Provide concise confirmation of the detected address and browser-launch attempt in the built-in debug-server-ready extension, without writing shell input or implying the browser is already visible. Settle whether this belongs in the Debug Console or a transient notification before implementation.

## Plan brief

- **Likely files:** `extensions/debug-server-ready/src/extension.ts`
- **Validation:** In an Extension Development Host, debug a small HTTP server with serverReadyAction.action set to openExternally and a known matching startup message. Exercise both Debug Console output and integrated-terminal output: verify the chosen feedback surface identifies the target and launch attempt before the external browser becomes visible, appears once per action, and writes no shell input. With a nonmatching pattern, verify no successful-detection message appears.
- **Behavior:**

  > When a configured server-ready pattern matches and VS Code initiates an external-browser launch, users should receive concise feedback identifying the target and the launch attempt, including when browser startup is slow. Feedback must not claim the browser is already visible or inject input into the integrated terminal. Acceptance covers matching output from both the Debug Console and integrated terminal, one announcement per triggered action, and no false success announcement when the pattern has not matched.
- **Trace:**

  > In extensions/debug-server-ready/src/extension.ts, debug-adapter output and terminal-data listeners feed ServerReadyDetector.detectPattern. A match flows through openExternalWithString to openExternalWithUri, whose openExternally branch calls vscode.env.openExternal without reporting detection or dispatch. The Trigger object already provides one-shot behavior shared with parent sessions. The discussion at https://github.com/microsoft/vscode/issues/71177 considers Debug Console feedback versus a transient notification; that user-visible choice remains unresolved. Preserve matching, URI construction, browser selection, and session-lifetime semantics, and do not treat terminal sendText as an output mechanism. Unmatched-pattern diagnostics are a separate concern: https://github.com/microsoft/vscode/issues/71074#issuecomment-476884568 explains that additional matching output may arrive at any time.
- **Open decisions:**
  - Should successful server detection and browser-launch feedback appear in the Debug Console, as a transient notification, or in both?
