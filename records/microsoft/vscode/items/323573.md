# Issue #323573 — Ability to reorder session chats

[https://github.com/microsoft/vscode/issues/323573](https://github.com/microsoft/vscode/issues/323573)

## Summary

The requested capability remains absent on current main: chat tabs can be dragged between or into split groups, but dropping within the same group cannot reorder them. This team-authored feature request has no older canonical issue or explicit fixing commit, so it should remain open.

## Change summary

Allow users to drag session chat tabs into a different order.

## Best solution

Support editor-like reordering within a chat tab strip, persist the resulting per-group order with the existing session chat-group layout, and preserve the current affordances for moving or splitting chats between groups.

## Plan brief

- **Likely files:** `src/vs/sessions/browser/parts/chatCompositeBar.ts`, `src/vs/sessions/browser/parts/chatGroupDropTarget.ts`, `src/vs/sessions/browser/parts/chatGroupsView.ts`, `src/vs/sessions/test/browser/chatGroupsView.test.ts`
- **Validation:** Add focused Sessions browser tests that reorder a tab within one group, assert the resulting `resourceIds` order, recreate the view, and assert that the order is restored while existing center-move and edge-split cases remain unchanged.
- **Behavior:**

  > Dragging a session chat tab within its current tab strip should let the user place it before or after another tab. The selected order should survive recreation of the session view through the existing persisted chat-group layout. Moving a tab between groups and dropping at a group edge to split it must continue to work, with a clear visual distinction from in-strip reordering.
- **Trace:**

  > ChatCompositeBar in src/vs/sessions/browser/parts/chatCompositeBar.ts starts tab drags but does not calculate an insertion target. ChatGroupDropTarget in src/vs/sessions/browser/parts/chatGroupDropTarget.ts treats the whole group as five center/edge zones, and ChatGroupsView._onChatDrop in src/vs/sessions/browser/parts/chatGroupsView.ts explicitly ignores a center drop when source and target are the same group. Each IGroupEntry already owns an ordered `resourceIds` array, and the serialized chat-groups layout restores that order. The boundary is the Sessions-owned chat tab/grid presentation: provider chat order and chat metadata must not be mutated. The same symptom was subsequently reported in https://github.com/microsoft/vscode/issues/333672.
- **Open decisions:**
  - Should the session's main chat participate in arbitrary tab reordering, or remain fixed as the first tab while only peer and nested chats can move?
  - What drop affordance should distinguish insertion within the current tab strip from moving the chat to another group or splitting the group?

## Evidence

- **current source:** In src/vs/sessions/browser/parts/chatGroupsView.ts, `_onChatDrop` returns immediately when a center drop has the same source and target group (lines 571-574); `_moveChatToGroup` only appends to a different target group. This leaves no same-strip reorder path.
- **drag behavior:** src/vs/sessions/browser/parts/chatGroupDropTarget.ts classifies drops only as group center or group edges; center moves between groups and edges create splits. src/vs/sessions/browser/parts/chatCompositeBar.ts supplies drag payloads but has no insertion-position handling for tabs.
- **persistence foundation:** src/vs/sessions/browser/parts/chatGroupsView.ts already stores each group's `resourceIds` in tab order and restores that order through `_restoreOrder`, so persisted ordering exists even though users cannot currently change it within a group.
- **related report:** https://github.com/microsoft/vscode/issues/333672 later reported the same observable behavior—dragging a nested chat tab offers layout splitting instead of reordering. It is younger than this re-reviewed issue and therefore cannot serve as its canonical duplicate.
