# Issue #267199 — ERR_HTTP2_PROTOCOL_ERROR

[https://github.com/microsoft/vscode/issues/267199](https://github.com/microsoft/vscode/issues/267199)

## Summary

Keep this open as the canonical Copilot HTTP/2 failure tracker. Multiple independent reports confirm long-running requests stall and fail, while current main retries only after the transport surfaces the error and has no HTTP/2-specific fallback policy.

## Change summary

Copilot Chat requests intermittently stall for several minutes and fail with net::ERR_HTTP2_PROTOCOL_ERROR, particularly during long Claude or subagent tasks and in some Zscaler environments.

## Best solution

Define and implement prompt recovery for stalled or reset HTTP/2 streams, including a bounded detection timeout and a safe retry or alternate-fetcher path that does not leave long-running agent tasks silently blocked.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts`, `extensions/copilot/src/extension/prompt/node/test/chatMLFetcherRetry.spec.ts`, `extensions/copilot/src/platform/networking/common/networking.ts`, `extensions/copilot/src/platform/networking/node/fetcherFallback.ts`, `extensions/copilot/src/platform/networking/test/node/fetcherFallback.spec.ts`
- **Validation:** Add deterministic retry tests that inject ERR_HTTP2_PROTOCOL_ERROR during a streaming chat request, advance fake timers to the chosen recovery bound, and assert the request either retries with the selected fallback fetcher or fails visibly without a multi-minute silent stall.
- **Behavior:**

  > A Copilot Chat request whose HTTP/2 stream stalls or is reset must not remain silently blocked for several minutes. Recovery should begin within a documented bounded interval and either resume through a safe automatic retry or surface an actionable failure promptly. Existing successful streaming requests and cancellation behavior must remain unchanged, and recovery must not accidentally duplicate user-visible tool side effects.
- **Trace:**

  > The detailed reproduction in https://github.com/microsoft/vscode/issues/283623 shows an Electron HTTP/2 RST_STREAM after a multi-minute subagent stall and was consolidated into https://github.com/microsoft/vscode/issues/267199. In extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts, network recovery starts only after processError classifies an already-surfaced failure; _retryAfterError then runs _checkNetworkConnectivity, and only network-change or network-process-crash cases switch to node-fetch. extensions/copilot/src/platform/networking/common/networking.ts includes ERR_HTTP2_PROTOCOL_ERROR in canRetryOnceNetworkError, but that path does not bound how long an active streaming response can remain stalled before failing. Keep the scope to Copilot chat transport recovery: do not treat proxy-specific workarounds as the fix or change unrelated token, quota, and model-selection behavior. The uncertainty begins at the public recovery contract for partially completed agent requests and the timeout at which a stream is considered stalled.
- **Open decisions:**
  - After an HTTP/2 failure following partial streamed output or tool activity, should Copilot automatically replay the request, or stop promptly and require explicit user retry to avoid duplicating side effects?
  - What user-observable inactivity bound should classify a Copilot HTTP/2 stream as stalled before recovery begins?
