# Issue #336416 — Access WSL tunnels from Agents web UI

[https://github.com/microsoft/vscode/issues/336416](https://github.com/microsoft/vscode/issues/336416)

## Summary

Team-authored, still-open feature gap: the Agents web UI's remote-tunnel connection only surfaces the Windows filesystem, not the WSL filesystem, and the agent host's tunnel path has no WSL awareness — this is a genuine, unresolved product gap, not a duplicate of the linked (also-open) Dev Containers tracking issue.

## Change summary

The Agents window (vscode.dev/agents) connecting over a remote tunnel to a Windows machine only exposes the Windows filesystem, not the WSL filesystem, even when the user intends to work in a WSL distro (unlike vscode.dev with the WSL extension installed).

## Best solution

Extend AgentHost's tunnel-based remote connection path to support WSL targets the way the existing Electron `wslRemoteAgentHostServiceImpl.ts` does for local usage, so the Agents web UI can browse/attach to a WSL filesystem over a tunnel.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/tunnelAgentHostService.ts`, `src/vs/platform/agentHost/electron-browser/wslRemoteAgentHostServiceImpl.ts`, `src/vs/platform/agentHost/node/agentHostMain.ts`
- **Validation:** Manually verify from the Agents web UI over a remote tunnel to a Windows host with WSL that 'Add Context... > Files...' and session file browsing show the WSL filesystem, not just the Windows filesystem.
- **Behavior:**

  > When a user connects to the Agents web UI (vscode.dev/agents) via a remote tunnel to a Windows machine that has a WSL distro, they should be able to browse and work with files inside the WSL filesystem (as they already can from vscode.dev with the WSL extension), not just the Windows filesystem. Acceptance: file pickers and session context in the Agents window surface the intended WSL distro's filesystem when connecting over a tunnel.
- **Trace:**

  > The desktop/Electron agent host already has WSL-aware handling in src/vs/platform/agentHost/electron-browser/wslRemoteAgentHostServiceImpl.ts, but the tunnel-based remote path (src/vs/platform/agentHost/node/tunnelAgentHostService.ts, agentHostMain.ts) has no WSL references, matching the reporter's observation that the Agents web UI over a tunnel only exposes the Windows filesystem. This was split off from https://github.com/microsoft/vscode/issues/317380, which was renamed to focus on Dev Containers only, suggesting WSL-over-tunnel is intentionally a separate, still-unaddressed gap. Where uncertainty starts: how WSL distro discovery/selection should be surfaced through the tunnel protocol and web UI is undecided.
- **Open decisions:**
  - How should a WSL distro be discovered/selected when connecting via a remote tunnel to the Agents web UI — auto-detected default distro, or an explicit picker?
  - Should this reuse the existing electron-browser WSL agent host implementation's logic, or does the tunnel protocol need its own WSL-aware service?

## Evidence

- **existing WSL support (local only):** src/vs/platform/agentHost/electron-browser/wslRemoteAgentHostServiceImpl.ts implements WSL awareness for the Electron/desktop agent host, but this file has no counterpart wired into the tunnel path.
- **no WSL handling in tunnel path:** grep for 'wsl' (case-insensitive) in src/vs/platform/agentHost/node/tunnelAgentHostService.ts and agentHostMain.ts returns no matches, consistent with the report that tunnel connections only see the Windows filesystem.
- **split from tracking issue:** Body notes this was split out of https://github.com/microsoft/vscode/issues/317380, which was renamed from 'WSL and Dev Containers support' to 'Dev Containers support' — WSL tunnel support appears to have been carved out as its own gap, not folded into that (also open) issue.
