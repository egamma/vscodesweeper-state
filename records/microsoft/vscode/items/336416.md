# Issue #336416 — Access WSL tunnels from Agents web UI

[https://github.com/microsoft/vscode/issues/336416](https://github.com/microsoft/vscode/issues/336416)

## Summary

Confirmed real gap: the browser/web Agent Host stubs out WSL entirely (NullWSLRemoteAgentHostService throws/returns empty), so a tunnel session only ever exposes the Windows filesystem from vscode.dev/agents. This was deliberately split out from the combined WSL+Dev Containers tracking issue after Dev Containers-in-WSL shipped, so it's real unfinished work, not a duplicate.

## Change summary

Expose the WSL filesystem/distro connections (not just the Windows host filesystem) when using a remote tunnel from the web Agents UI (vscode.dev/agents, insiders.vscode.dev/agents).

## Best solution

Design how a web/browser session can surface a WSL distro connection through the tunnel (likely extending the tunnel/relay transport and the browser AgentHost file system provider), then swap NullWSLRemoteAgentHostService for a real implementation on that path.

## Evidence

- **browser stub:** src/vs/platform/agentHost/browser/nullWslRemoteAgentHostService.ts implements IWSLRemoteAgentHostService as a no-op for browser contexts: isWSLAvailable() returns false, connect()/disconnect()/reconnect() all throw 'WSL is not available on this platform.'
- **desktop has real impl:** src/vs/platform/agentHost/electron-browser/wslRemoteAgentHostServiceImpl.ts and src/vs/platform/agentHost/node/wslRemoteAgentHostService.ts implement real WSL connection logic, confirming the gap is browser/web-specific, not a general product limitation.
