# Issue #336416 — Access WSL tunnels from Agents web UI

[https://github.com/microsoft/vscode/issues/336416](https://github.com/microsoft/vscode/issues/336416)

## Summary

Keep open: this team-authored issue deliberately preserves the WSL-over-tunnel capability that remained after the broader Agent Host issue was narrowed to Dev Containers. Current main supports browser tunnel hosts and local desktop WSL hosts separately, but does not expose WSL distributions behind a tunneled Windows host to the Agents web UI.

## Change summary

Allow vscode.dev/agents to discover and access WSL filesystems through a Windows machine connected by a VS Code remote tunnel.

## Best solution

Extend the remote tunnel/Agent Host contract so a web client can discover WSL distributions behind a tunneled Windows host, select the intended Windows or WSL environment, and route workspace browsing and agent sessions to that environment without changing ordinary tunnel behavior.

## Plan brief

- **Likely files:** `src/vs/sessions/sessions.web.main.ts`, `src/vs/sessions/contrib/providers/remoteAgentHost/browser/browserTunnelAgentHostService.ts`, `src/vs/sessions/contrib/providers/remoteAgentHost/browser/wslAgentHost.contribution.ts`, `src/vs/platform/agentHost/common/wslRemoteAgentHost.ts`, `src/vs/platform/agentHost/browser/nullWslRemoteAgentHostService.ts`
- **Validation:** Add browser tunnel/provider tests in src/vs/sessions/contrib/providers/remoteAgentHost/test/browser/ that model a Windows tunnel advertising a WSL distribution and verify the WSL workspace is selectable and routed independently of the Windows filesystem; manually confirm the same flow from vscode.dev/agents.
- **Behavior:**

  > When a remote tunnel terminates on Windows and that machine has an available WSL distribution, the Agents web UI can discover and select the WSL environment rather than exposing only the Windows filesystem. Workspace browsing and newly created agent sessions operate on the selected distribution's Linux filesystem. Selecting the ordinary tunnel host continues to expose the Windows environment, and tunnels without WSL remain unchanged.
- **Trace:**

  > The web entry point src/vs/sessions/sessions.web.main.ts registers browser tunnel discovery but installs NullWSLRemoteAgentHostService, whose implementation always reports WSL unavailable. BrowserTunnelAgentHostService in src/vs/sessions/contrib/providers/remoteAgentHost/browser/browserTunnelAgentHostService.ts creates a connection for the tunnel's advertised Agent Host only; WSLAgentHostContribution creates WSL providers solely from IWSLRemoteAgentHostService.getCachedDistros(), which has no browser-side remote source. Desktop WSL support therefore does not compose through a Windows tunnel. The boundary is tunneled-host discovery and routing: direct desktop WSL connections and existing Windows tunnel behavior must remain unchanged. The uncertainty starts at how a nested WSL target should be represented and selected in the host picker and persisted across reconnects.
- **Open decisions:**
  - Should each WSL distribution behind a Windows tunnel appear as an independent host entry, or should users first select the Windows tunnel and then choose its Windows or WSL environment?
  - Should selecting a tunneled WSL environment be persisted as a distinct reconnectable host, or rediscovered beneath the parent tunnel each time?

## Evidence

- **intentional follow-up:** https://github.com/microsoft/vscode/issues/317380 was renamed from “AgentHost: WSL and Dev Containers support” to “AgentHost: Dev Containers support,” then closed immediately before team member chrmarti opened https://github.com/microsoft/vscode/issues/336416 specifically for the remaining WSL-tunnel scenario.
- **web boundary:** src/vs/sessions/sessions.web.main.ts registers BrowserTunnelAgentHostService for tunnel access but binds IWSLRemoteAgentHostService to NullWSLRemoteAgentHostService; src/vs/platform/agentHost/browser/nullWslRemoteAgentHostService.ts reports WSL unavailable and returns no distributions.
- **existing capability gap:** src/vs/sessions/contrib/providers/remoteAgentHost/browser/browserTunnelAgentHostService.ts creates one tunnel connection entry for the advertised host, while src/vs/sessions/contrib/providers/remoteAgentHost/browser/wslAgentHost.contribution.ts only turns distributions supplied by IWSLRemoteAgentHostService into separate providers. There is no current path for a browser tunnel connection to supply the tunneled Windows host's WSL distributions.
