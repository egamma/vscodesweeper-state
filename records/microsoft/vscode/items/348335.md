# Issue #348335 — Linux: publish recent workspaces to the desktop (parity with Windows Jump List and macOS dock)

[https://github.com/microsoft/vscode/issues/348335](https://github.com/microsoft/vscode/issues/348335)

## Summary

Keep open as a Linux desktop-integration feature request: current source does not publish recent workspaces on Linux, and the verified related reports do not provide an open canonical. Acceptance of the VS Code integration remains a maintainer decision, dependent on Electron support.

## Change summary

Publish recently opened local folders and workspace files to Linux desktop recent-items registries.

## Best solution

Evaluate Linux integration in WorkspacesHistoryMainService once Electron provides suitable registration and removal semantics, preserving recency, other applications' entries, and portable-mode behavior. Keep Plasma's folder-launch handling separate and retain the existing directory MIME-type exclusion.

## Evidence

- **Current integration gap:** src/vs/platform/workspaces/electron-main/workspacesHistoryMainService.ts: addRecentlyOpened publishes individual local files only on Windows and schedules recent-document updates only on macOS. removeRecentlyOpened likewise schedules only macOS updates; updateMacOSRecentDocuments explicitly excludes other platforms.
- **Existing capability is insufficient:** src/vs/workbench/browser/actions/windowActions.ts registers workbench.action.openRecent for in-app access. resources/linux/code.desktop declares only the new-empty-window desktop action; neither surface publishes the MRU to Linux desktop recent-item consumers. Searches found no GBookmarkFile, GtkRecentManager, or recently-used.xbel integration in the inspected source and packaging directories.
- **Electron prerequisite:** https://github.com/electron/electron/blob/139c603a2a0b431de5b22b6da5a1cd37d00314c2/shell/browser/browser_linux.cc contains empty Browser::AddRecentDocument and Browser::ClearRecentDocuments implementations, while Browser::GetRecentDocuments returns an empty vector. This confirms the cited upstream capability gap, not a landed fix.
- **Reporter correction and workaround:** The supplied comment on https://github.com/microsoft/vscode/issues/348335 explains that Plasma opens recent folders in the default file manager because VS Code does not advertise inode/directory. resources/linux/code.desktop confirms that exclusion. The external proof of concept at https://github.com/intilinux-eng/vscode-recent-workspaces-linux is a workaround, not built-in coverage; the reporter explicitly separates the Plasma fix from this request.
- **Verified related reports:** https://github.com/microsoft/vscode/issues/324487 is open but requests macOS dock access to remote workspaces, not Linux publication of local resources. Targeted Linux recent-items and launcher searches found https://github.com/microsoft/vscode/issues/152151, which is closed and therefore cannot be a duplicate canonical.
- **Historical closure is not a scope decision:** https://github.com/microsoft/vscode/issues/152151#issuecomment-1420110984 states that the earlier Linux launcher request closed for insufficient community upvotes after 60 days, not because maintainers rejected desktop integration. The fully read https://github.com/microsoft/vscode/wiki/Issues-Triaging describes this community process; it does not justify declining this new, technically detailed proposal.
