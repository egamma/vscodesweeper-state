# Issue #339834 — On restart, the individual last updated times for a chat and its peers changed to all be the same

[https://github.com/microsoft/vscode/issues/339834](https://github.com/microsoft/vscode/issues/339834)

## Summary

Traced on main: when projecting a session summary into the Agent Sessions tree, peer-chat child items are always stamped with the session-level aggregate `modifiedAt` instead of a per-chat value, so after a restart (when the UI can only rebuild from the persisted summary, not live in-memory activity) every peer collapses to the same timestamp.

## Change summary

After restarting VS Code, a chat's peer chats all show the same 'last updated' relative time instead of their individual timestamps.

## Best solution

Decide how per-chat last-modified timing should be sourced for peer chats — either extend the Agent Host Protocol's SessionChatSummary catalog entry with a real per-chat modifiedAt field (the protocol doc explicitly says only the session-level aggregate is defined today), or compute/cache per-chat timestamps client-side from the `session/chatUpdated` activity stream — then update agentHostSessionListController.ts's `_makeItemFromSummary` to use that instead of `base.modifiedAt` for every child.

- **Behavior:**

  > After restarting VS Code, peer chats in the Agent Sessions tree should continue to show their own individual 'last updated' relative times (e.g. '1 min ago', '5 min ago'), matching what was shown before restart, rather than all collapsing to the same timestamp as the most-recently-active chat.
- **Trace:**

  > `_makeItemFromSummary` in agentHostSessionListController.ts builds each peer-chat child with `modifiedAt: base.modifiedAt`, where `base.modifiedAt` is the session-wide aggregate (`Date.parse(summary.modifiedAt)`), not a per-chat value — confirmed by reading the function body. The underlying `SessionChatSummary` protocol type (channels-session/state.ts, auto-generated, 'DO NOT EDIT') has no per-chat modifiedAt/createdAt field; its own doc comment says the session-level `modifiedAt` is intentionally just the max across chats. Before restart, differing per-peer timestamps evidently come from some other live/in-memory tracking (not part of this summary projection), which is lost on restart, leaving only the collapsed aggregate. The boundary: do not change the session-level aggregation semantics (`SessionSummary.modifiedAt` staying the max is correct and documented); the gap is specifically the lack of a per-chat timestamp surfaced to the catalog/consumer.
- **Open decisions:**
  - Should the Agent Host Protocol's SessionChatSummary catalog entry gain a real per-chat modifiedAt/createdAt field (a protocol/schema change, versioned and synced via scripts/sync-agent-host-protocol.ts), or should per-chat timestamps instead be tracked and cached client-side from session/chatUpdated activity without touching the protocol?
  - If a protocol field is added, how should older hosts that don't populate it be handled in the client (fallback to the aggregate, or hide the per-chat timestamp)?
