# Issue #278201 — Add an easy way for me to extend an MCP definition contributed by an extension

[https://github.com/microsoft/vscode/issues/278201](https://github.com/microsoft/vscode/issues/278201)

## Summary

The generic configuration gap remains on current main: `mcp.json` can define complete servers but cannot augment definitions contributed by extensions. This team-authored, under-discussion request should remain open while maintainers settle the public merge and precedence contract.

## Change summary

Allow users to extend an extension-contributed MCP server with additional headers, environment variables, or command arguments from `mcp.json`.

## Best solution

Provide a generic, configuration-file-based override contract for extension-contributed MCP definitions, with stable target identity, explicit scope precedence, predictable array merging, and safeguards around provider-resolved authentication data.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts`, `src/vs/workbench/api/common/extHostMcp.ts`, `src/vs/workbench/contrib/mcp/common/discovery/extensionMcpDiscovery.ts`, `src/vs/workbench/contrib/mcp/common/mcpService.ts`, `src/vs/workbench/contrib/mcp/test/common/mcpRegistry.test.ts`
- **Validation:** Add targeted MCP configuration and registry tests covering an override applied to an extension-contributed HTTP definition and a stdio definition, scope precedence, provider refreshes, unresolved targets, and unchanged behavior for ordinary complete server entries; run the corresponding MCP unit-test suite.
- **Behavior:**

  > Users can configure supported additions to an extension-contributed MCP server from an MCP configuration file rather than relying on extension-specific settings. The effective server should combine the provider definition with the configured headers, environment variables, or arguments according to documented and deterministic rules, and remain associated with the same contributed server when its provider refreshes. Invalid or missing targets must be surfaced rather than silently producing an unrelated server. Existing complete `mcp.json` server definitions and extension definitions without overrides must behave unchanged.
- **Trace:**

  > Current `mcp.json` validation in src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts only permits complete stdio or HTTP server entries. Extension definitions enter through ExtHostMcp.registerMcpConfigurationProvider in src/vs/workbench/api/common/extHostMcp.ts and are published as complete definitions in extension-owned collections; src/vs/workbench/contrib/mcp/common/discovery/extensionMcpDiscovery.ts restores and activates those collections. McpCollisionEnablementModel in src/vs/workbench/contrib/mcp/common/mcpService.ts only arbitrates same-label servers and provides no composition path. The GitHub provider in extensions/copilot/src/extension/githubMcp/common/githubMcpDefinitionProvider.ts confirms the motivating scenario is currently handled with server-specific settings. Preserve provider authentication resolution, existing server-collision behavior, and ordinary user/workspace server semantics; the uncertainty begins at the public identity, scope, precedence, and merge contract.
- **Open decisions:**
  - What stable public identifier should an override use to target an extension-contributed server, especially if its display label changes or a provider contributes multiple same-label definitions?
  - Which configuration scopes may override contributed definitions, and what precedence should user, remote-user, workspace, and workspace-folder values have?
  - For ordered fields such as `args`, should configured values append, prepend, or replace the provider's values?
  - Which fields may users override, and should provider-resolved authentication headers or other runtime-sensitive values always take precedence over configured values?
  - How should the UI and diagnostics represent an override whose extension or server is unavailable?

## Evidence

- **current schema gap:** On current main, src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts defines `servers` entries exclusively as complete `mcpStdioServerSchema` or `mcpRemoteServerSchema` objects; both reject unknown properties and the top-level schema has no `$extends` or equivalent override section.
- **separate extension path:** src/vs/workbench/api/common/extHostMcp.ts registers extension-provided definitions as a separate MCP collection and assigns IDs from the extension identifier plus server label. It publishes each provider's complete launch definition without consulting user-authored field overrides.
- **collision is not extension:** src/vs/workbench/contrib/mcp/common/mcpService.ts implements same-label collision behavior by disabling competing definitions or exposing suffixed definitions; it does not merge headers, environment variables, or arguments.
- **use-case-specific workaround:** extensions/copilot/src/extension/githubMcp/common/githubMcpDefinitionProvider.ts currently derives `X-MCP-Toolsets`, readonly, lockdown, and channel headers from GitHub-specific settings. This covers the motivating GitHub server but not the requested generic `mcp.json` capability for other contributed servers.
- **related item:** The later closed test-plan item https://github.com/microsoft/vscode/issues/279705 explicitly references this issue as the generic way users could configure contributed GitHub MCP headers. It is younger than this re-reviewed issue and does not own or implement the requested work.
- **canonical search:** Repository issue searches found no older open issue describing the same user-observable inability to augment an extension-contributed MCP definition; https://github.com/microsoft/vscode/issues/251515 concerns workspace storage of toolset files instead.
