# Issue #278201 — Add an easy way for me to extend an MCP definition contributed by an extension

[https://github.com/microsoft/vscode/issues/278201](https://github.com/microsoft/vscode/issues/278201)

## Summary

Keep open: GitHub-specific settings cover toolset selection, but not the requested general configuration overlay for extension-contributed servers. This team-authored proposal remains a product-design question in the already-correct MCP management area.

## Change summary

Allow users to augment extension-contributed MCP server headers, environment variables, and arguments from centralized MCP configuration.

## Best solution

Define a supported configuration overlay that preserves extension-provided server discovery and authentication while exposing user customizations in MCP configuration. Settle target identity, argument composition, and configuration precedence before implementation.

- **Validation:** The plan should end with executable MCP registry/configuration tests using a fake extension provider: verify an HTTP header overlay reaches the connection launch, stdio env/args follow the agreed composition rules, and removing the overlay restores provider defaults. Include checks that unrelated servers and extension authentication remain unchanged; no tests were run during this read-only review.
- **Behavior:**

  > Users should be able to customize an extension-contributed MCP server through centralized MCP configuration without recreating its endpoint or launch definition. The requested cases are adding X-MCP-Toolsets to an HTTP server and adding debugging environment variables or arguments to a stdio server. Extension discovery and authentication should continue to work, and unrelated servers should remain unchanged. Acceptance checks must cover applying and removing overlays, plus the maintainer-selected conflict and argument-composition semantics.
- **Trace:**

  > mcpServerSchema in src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts supports independent server definitions, but exposes no extension-definition overlay. ExtensionMcpDiscovery registers extension collections separately, and McpRegistry.resolveConnection obtains the provider launch before variable expansion and other launch transformations. GitHubMcpDefinitionProvider currently implements toolset customization through extension settings, establishing a partial workaround rather than the requested common mechanism. https://github.com/microsoft/vscode/issues/279705 explicitly preserves this distinction. The trace establishes the workbench path, not a complete design for every agent runtime consumer. Preserve provider-managed endpoints, authentication, trust, and enterprise enforcement; uncertainty starts at stable target identity and the public composition contract.
- **Open decisions:**
  - What stable identifier should configuration use to target a contributed server, including when its display label changes?
  - Should user-supplied args append to provider arguments or replace them, and how should conflicting headers/env values be resolved?
  - Which configuration scopes may customize an extension-contributed server, and what precedence should apply when multiple scopes provide overlays?
