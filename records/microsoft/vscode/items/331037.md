# Issue #331037 — Settings Sync: conflict actions use two contradictory naming schemes, causing accidental data loss

[https://github.com/microsoft/vscode/issues/331037](https://github.com/microsoft/vscode/issues/331037)

## Summary

Current main still uses opposing victim-oriented and winner-oriented names for equivalent Settings Sync conflict actions. This is accepted Backlog work with concrete accidental-loss evidence, and no open older canonical owns the inconsistency, so it should remain open.

## Change summary

Make Settings Sync conflict actions use one unambiguous naming scheme that consistently identifies whether local or remote data survives.

## Best solution

Use one outcome-oriented vocabulary across the conflict notification, conflicts view, and turn-on-sync dialog, while explicitly communicating when local settings will be overwritten. Preserve the underlying local-wins and remote-wins behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/userDataSync/browser/userDataSync.ts`, `src/vs/workbench/contrib/userDataSync/browser/userDataSyncConflictsView.ts`, `src/vs/workbench/services/userDataSync/browser/userDataSyncWorkbenchService.ts`
- **Validation:** Using two VS Code profiles or machines with conflicting settings, inspect the conflict notification, conflicts view, and turn-on-sync dialog: every surface must identify local-wins and remote-wins consistently, and selecting each action must overwrite only the opposite side.
- **Behavior:**

  > Settings Sync conflict actions must identify which version survives without requiring users to infer whether a label names the winner or the overwritten side. The notification, conflicts view, and turn-on-sync dialog must use the same naming model for local-wins and remote-wins. The destructive remote-wins action must make the local overwrite clear before execution. Selecting either action must retain its existing synchronization semantics.
- **Trace:**

  > In src/vs/workbench/contrib/userDataSync/browser/userDataSync.ts, onDidChangeConflicts labels acceptLocal as “Replace Remote” and acceptRemote as “Replace Local.” In src/vs/workbench/contrib/userDataSync/browser/userDataSyncConflictsView.ts, AcceptLocalAction and AcceptRemoteAction instead name the selected source. In src/vs/workbench/services/userDataSync/browser/userDataSyncWorkbenchService.ts, handleConflictsWhileTurningOn uses “Accept Local/Remote,” while replace(local) maps the remote resource when local is true. This confirms inconsistent terminology rather than incorrect synchronization routing. The earlier distinction was intentional in https://github.com/microsoft/vscode/issues/114982, so the uncertainty begins at the replacement vocabulary and warning behavior; do not alter conflict resolution semantics or fold in the separate German localization work from https://github.com/microsoft/vscode-loc/issues/2380.
- **Open decisions:**
  - Should every conflict surface name the surviving side as “Keep Local/Remote” or retain the established “Accept Local/Remote” vocabulary?
  - Should choosing the remote version include an explicit consequence message or confirmation that local settings will be overwritten?

## Evidence

- **current source contradiction:** src/vs/workbench/contrib/userDataSync/browser/userDataSync.ts labels the local-wins action “Replace Remote” and the remote-wins action “Replace Local,” while src/vs/workbench/contrib/userDataSync/browser/userDataSyncConflictsView.ts labels the equivalent actions “Accept Local” and “Accept Remote.”
- **destructive path:** In userDataSync.ts, “Replace Local” calls acceptRemote with conflict.remoteResource. In src/vs/workbench/services/userDataSync/browser/userDataSyncWorkbenchService.ts, the same remote-wins outcome is instead displayed as “Accept Remote” and replace(true) accepts preview.remoteResource with force enabled.
- **prior design:** https://github.com/microsoft/vscode/issues/114982 deliberately established “Replace” for dialogs and “Accept” for the diff context, but it is closed and therefore cannot be a duplicate canonical; this report supplies new evidence that switching schemes causes the same choice to be misread.
- **prior confusion:** https://github.com/microsoft/vscode/issues/133262 documents earlier maintainer and user confusion over whether “Replace Local” replaces local or cloud data, but it was closed after that particular dialog was removed and does not cover the current cross-surface inconsistency.
- **separate localization issue:** https://github.com/microsoft/vscode-loc/issues/2380 remains open for the German translation defect; it explicitly identifies https://github.com/microsoft/vscode/issues/331037 as the separate English/core wording problem.
