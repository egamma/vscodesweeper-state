# Issue #331037 — Settings Sync: conflict actions use two contradictory naming schemes, causing accidental data loss

[https://github.com/microsoft/vscode/issues/331037](https://github.com/microsoft/vscode/issues/331037)

## Summary

Confirmed in source: the Settings Sync conflict notification (userDataSync.ts) uses a 'Replace X' scheme that names the victim, while the Conflicts view and the turn-on flow use 'Accept X' (userDataSyncConflictsView.ts, userDataSyncWorkbenchService.ts) that names the winner — for the same operation. Concretely, the notification's 'Replace Local' button calls `acceptRemote()`, overwriting local content, which is exactly the accidental-loss scenario the reporter describes.

## Change summary

Unify the two contradictory conflict-resolution wording schemes ('Replace X' names the loser, 'Accept X' names the winner) so users can't misread one surface for the other and unintentionally overwrite their local settings.

## Best solution

Standardize on one scheme across all three surfaces — likely 'Accept Local'/'Accept Remote' (or 'Keep Local'/'Keep Remote' as the reporter suggests) — and retire 'Replace Local'/'Replace Remote' in src/vs/workbench/contrib/userDataSync/browser/userDataSync.ts (lines ~190-198) and the matching command labels in userDataSyncWorkbenchService.ts (lines ~434-439); this is a maintainer wording decision, not a mechanical fix.

## Evidence

- **conflicts view labels (winner-named scheme):** src/vs/workbench/contrib/userDataSync/browser/userDataSyncConflictsView.ts lines 144-165: `workbench.actions.sync.acceptRemote` is titled 'Accept Remote' and `workbench.actions.sync.acceptLocal` is titled 'Accept Local' — here the labeled side is the one that is KEPT, the opposite naming direction from the notification above.
- **turn-on flow labels (further scheme reuse):** src/vs/workbench/services/userDataSync/browser/userDataSyncWorkbenchService.ts lines 434-439: the internal key `replace local` renders as 'Accept &&Remote' and calls `this.replace(true)`, whose implementation uses `preview.remoteResource` when local=true — functionally consistent internally, but the same underlying decision is now labeled a third, different way.
