# Issue #331037 — Settings Sync: conflict actions use two contradictory naming schemes, causing accidental data loss

[https://github.com/microsoft/vscode/issues/331037](https://github.com/microsoft/vscode/issues/331037)

## Summary

Confirmed in the source: Settings Sync's conflict-resolution buttons use two genuinely inverted naming schemes across surfaces, and the reporter documents real, irreversible settings loss from misreading one of them — this is worth keeping open and routing to a UX/naming fix.

## Change summary

Settings Sync conflict-resolution actions are labeled inconsistently across surfaces ("Replace Local/Remote" vs "Accept Local/Remote"), and in one dialog the label's subject names the victim while in another it names the winner, so identical outcomes read as opposite choices.

## Best solution

Unify the wording across src/vs/workbench/contrib/userDataSync/browser/userDataSync.ts, userDataSyncConflictsView.ts, and services/userDataSync/browser/userDataSyncWorkbenchService.ts on one scheme that names the outcome (e.g. "Keep Local"/"Keep Remote", or consistently "Accept X" everywhere), retiring "Replace X"; a maintainer should pick the final wording since the issue itself proposes two viable options.

## Evidence

- **traced inversion #1:** src/vs/workbench/contrib/userDataSync/browser/userDataSync.ts:190-198 — the button labeled "Replace Local" calls `acceptRemote` (local is overwritten, remote content wins), and "Replace Remote" calls `acceptLocal` (remote is overwritten).
- **traced inversion #2:** src/vs/workbench/contrib/userDataSync/browser/userDataSyncConflictsView.ts:144-165 — separately exposes commands labeled "Accept Remote"/"Accept Local" for the same underlying acceptRemote/acceptLocal operations, using the opposite word ("Local"/"Remote") to describe the same winner as the button above.
- **third surface:** src/vs/workbench/services/userDataSync/browser/userDataSyncWorkbenchService.ts:434-439 — the turn-on-conflicts dialog labels the button that keeps remote content "Accept &&Remote" (internally keyed 'replace local') and the one that keeps local content "Accept &&Local" (keyed 'replace remote'), consistent with itself but using yet another key/label pairing.
- **reported harm:** Reporter documents concrete, irreversible data loss (deleted yaml/git/githubPullRequests settings, one value reverted) from picking "Replace Local" expecting it to mean 'keep local', when it actually meant 'local is replaced'.
