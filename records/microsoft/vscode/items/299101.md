# Issue #299101 — Like/Dislike buttons

[https://github.com/microsoft/vscode/issues/299101](https://github.com/microsoft/vscode/issues/299101)

## Summary

The selected state still relies entirely on theme-provided foreground, border, and background colors, so it can remain ambiguous in Gruvbox Dark Medium. This is actionable chat UI polish and should be routed to the panel-chat owners rather than closed.

## Change summary

Make a previously submitted Copilot thumbs-up or thumbs-down vote visually unmistakable when viewing the response later.

## Best solution

Give the selected feedback action a persistent non-color cue, such as a filled thumb glyph, while retaining the existing theme-aware styling and `aria-pressed` state across restored conversations.

- **Fit:** aligned
- **Reason:** Clear persistent state improves both accessibility and the consistency of a core chat interaction.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/actions/chatTitleActions.ts`, `src/vs/workbench/contrib/chat/browser/widget/media/chat.css`, `src/vs/workbench/contrib/chat/test/browser/actions/chatTitleActions.test.ts`
- **Validation:** With Gruvbox Dark Medium, a default dark theme, and a high-contrast theme, submit each vote, navigate away, and return: the selected action must remain distinguishable without relying only on color, the opposite action must remain unselected, and `aria-pressed` must report the correct state.
- **Behavior:**

  > After a user marks a Copilot response Helpful or Unhelpful, the chosen action must remain unmistakably selected when the conversation is revisited. The distinction must not depend on a subtle color change alone and must work in Gruvbox Dark Medium, default themes, and high-contrast themes. Keyboard operation and the existing `aria-pressed` semantics must remain intact.
- **Trace:**

  > The actions in src/vs/workbench/contrib/chat/browser/actions/chatTitleActions.ts use static outline thumb icons and derive their toggled state from `ChatContextKeys.responseVote`. ChatListRenderer restores that context key from the response model, and the base action view item exposes it as `aria-pressed`. The only visual selected-state treatment is the three `inputOption-active*` theme tokens in src/vs/workbench/contrib/chat/browser/widget/media/chat.css. The earlier accepted report https://github.com/microsoft/vscode/issues/229734 led to that styling through https://github.com/microsoft/vscode/commit/3089797ebc72db0839f3e1cbc325f48064f49c63, but the current report shows that a color-only treatment remains insufficient in at least one theme. Keep vote submission, persistence, animation, and the other footer actions out of scope.
- **Open decisions:**
  - Should the persistent selected state use a filled thumb glyph, a stronger button-surface treatment, or both as the standard chat feedback affordance?

## Evidence

- **current source:** src/vs/workbench/contrib/chat/browser/actions/chatTitleActions.ts registers static outline `Codicon.thumbsup` and `Codicon.thumbsdown` icons; the `toggled` expressions only track `ChatContextKeys.responseVote`.
- **current styling:** src/vs/workbench/contrib/chat/browser/widget/media/chat.css styles checked footer actions solely through `--vscode-inputOption-activeForeground`, `--vscode-inputOption-activeBorder`, and `--vscode-inputOption-activeBackground`, leaving no shape-based visual distinction when a theme supplies subtle values.
- **state persistence and accessibility:** src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts restores the response vote into the context key, while src/vs/base/browser/ui/actionbar/actionViewItems.ts exposes checked actions through `aria-pressed`; the state exists, but its visual representation remains color-only.
- **prior accepted defect:** https://github.com/microsoft/vscode/issues/229734 reported the same observable lack of feedback and was accepted as a bug. Its fix, https://github.com/microsoft/vscode/commit/3089797ebc72db0839f3e1cbc325f48064f49c63, introduced the active color-token styling still present today; because that issue is closed, it cannot serve as a duplicate canonical.
