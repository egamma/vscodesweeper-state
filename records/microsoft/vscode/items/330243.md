# Issue #330243 — Webview resources stream corrupted (every 256 KiB chunk delivered twice) when a second-instance CLI folder open lands during startup; corrupted response is then cached

[https://github.com/microsoft/vscode/issues/330243](https://github.com/microsoft/vscode/issues/330243)

## Summary

Keep this open as a core resource-streaming bug: measured reproductions demonstrate duplicated bytes and persistent cache corruption, while the merged external changes only avoid the startup trigger. The exact duplication point on current main remains unconfirmed; the log message cited as proof actually belongs to terminal request handling.

## Change summary

Prevent second-instance folder opens during startup from duplicating webview resource bytes and persisting corrupted responses.

## Best solution

Ensure webview resource responses remain byte-for-byte identical to their source files across startup and window-reuse transitions, with a recovery path for already-corrupted cache entries. Diagnose the first point of duplication across file streaming, Electron IPC, and webview delivery before choosing a bounded fix.

## Evidence

- **Measured reproduction:** https://github.com/microsoft/vscode/issues/330243 provides a standalone reproduction at https://github.com/lordrip/vscode-webview-corruption-repro: a second CLI folder open during startup produces adjacent repeated 262,144-byte chunks, including doubling small files, and subsequent sessions replay the cached corruption. The report records affected 1.132.0 runs and clean 1.122.0 controls; this review did not execute the reproduction.
- **Merged changes are workarounds:** https://github.com/redhat-developer/vscode-extension-tester/pull/2455 is merged but avoids the trigger through initial-launch resource arguments and a startup settle delay. It reports measured corruption without the workaround and clean runs with it. https://github.com/kaoto-archive/vscode-kaoto/pull/1476 similarly delays the second CLI open; neither changes VS Code's streaming implementation.
- **Current resource path:** src/vs/workbench/contrib/webview/browser/resourceLoading.ts: loadLocalResource calls IFileService.readFileStream. src/vs/platform/files/node/diskFileSystemProvider.ts:238-244 sets a 256 * 1024 read buffer, matching the measured duplication boundary. DiskFileSystemProviderClient.readFileStream forwards received IPC data into its stream, and WebviewElement.loadResource forwards that stream into the webview response. This identifies the diagnostic path, not a proven duplication cause.
- **Cache persistence remains plausible:** src/vs/workbench/contrib/webview/browser/pre/service-worker.js: resolveResourceEntry tees successful ETagged streams into the response and CacheStorage without validating their byte count. Its 304 handling clones the cached response. This supports the reported persistence mechanism if duplicated bytes enter the stream, but does not itself establish why duplication occurs.
- **Important correction to root-cause evidence:** The exact 'RequestStore#acceptReply was called without receiving a matching request' warning comes from src/vs/platform/terminal/common/requestStore.ts, used by PtyService and PtyHostService. The webview service worker's RequestStore instead exposes create/resolve and does not emit that warning. https://github.com/microsoft/vscode/issues/330243#issuecomment-5406027768 explicitly confirms lifecycle failures with --process-per-site but says doubled webview bytes were not reproduced.

No open VS Code PR referencing this issue was found in the search or supplied timeline.
