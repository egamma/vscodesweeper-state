# Issue #330243 — Webview resources stream corrupted (every 256 KiB chunk delivered twice) when a second-instance CLI folder open lands during startup; corrupted response is then cached

[https://github.com/microsoft/vscode/issues/330243](https://github.com/microsoft/vscode/issues/330243)

## Summary

Extremely well-documented, freshly filed race-condition report (0 days old, no maintainer engagement yet) describing webview resource streaming duplication tied to a second-instance CLI open during startup — plausible given the RequestStore/service-worker chunking pipeline I traced, but I could not execute the runnable repro to confirm the exact root cause, so this needs a real reproduction attempt before any close is considered.

## Change summary

When a second-instance CLI folder-open lands during VS Code startup, every streamed webview resource chunk is delivered twice (256 KiB doubling), corrupting large resources; the corrupted response then gets permanently cached by the webview service worker in CacheStorage, poisoning the profile for that webview indefinitely.

## Best solution

A webview-team maintainer should run the linked reproduction repo (https://github.com/lordrip/vscode-webview-corruption-repro) against current main and trace whether a second-instance window activation re-registers the 'load-resource' listener/reply channel on webviewElement.ts or the service worker's RequestStore (src/vs/workbench/contrib/webview/browser/pre/service-worker.js), which would explain the doubled chunks reported in the main-process log ('RequestStore#acceptReply was called without receiving a matching request').
