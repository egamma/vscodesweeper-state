# Issue #291685 — Make sharing of copilot instructions, skills etc globally easy for organizations

[https://github.com/microsoft/vscode/issues/291685](https://github.com/microsoft/vscode/issues/291685)

## Summary

Keep open as an under-discussion feature request: the existing location settings and extension contribution model provide local distribution workarounds, but they do not satisfy the clarified need for centrally managed instructions shared across a selected group of repositories and usable in remote or web environments.

## Change summary

Provide a simple organization-managed way to distribute Copilot instructions, skills, prompts, and agents across selected repositories without copying files into every repository or synchronizing every developer machine.

## Best solution

Define a portable customization-package or repository-reference mechanism that can be centrally maintained, scoped to selected repositories, permission-checked, and consumed consistently by desktop, remote, Codespaces, web, and CLI agent surfaces.

## Plan brief

- **Likely files:** `extensions/copilot/package.json`, `extensions/copilot/src/platform/customizations/common/customizationsService.ts`
- **Validation:** End-to-end acceptance should verify that one centrally maintained customization set applies to two opted-in repositories but not an unrelated repository, works without machine-local file synchronization in desktop and remote/web contexts, and reports inaccessible referenced sources without discarding accessible customizations.
- **Behavior:**

  > An organization can maintain Copilot instructions, skills, prompts, and agents once and apply them to a selected group of repositories. Developers should receive the same applicable customizations in local, remote, Codespaces, web, and CLI-capable workflows without copying files into every repository or pre-synchronizing every machine. Repository or source permissions must be honored, and an inaccessible source should produce a clear warning while other accessible customizations continue to load.
- **Trace:**

  > Current customization discovery is based on configured filesystem locations and extension-contributed resources under `extensions/copilot/`; the maintainer-confirmed settings are `chat.instructionsFilesLocations`, `chat.promptFilesLocations`, `chat.agentFilesLocations`, and `chat.agentSkillsLocations`. Those paths cover local or mounted storage but do not define a portable repository-group reference or fetching contract for web and ephemeral environments. The extension-package option supplies distribution but does not directly express the requested selected-repository scope. Preserve workspace-local instruction behavior and existing location settings; the uncertainty starts at the public source/reference model, trust and permission semantics, and which agent hosts must consume it consistently.
- **Open decisions:**
  - Should selected-repository sharing be declared by each consuming repository, assigned centrally by an organization, or support both models?
  - Which centrally hosted sources are part of the supported public contract: Git repositories, HTTPS resources, extension/customization packages, or a narrower set?
  - Must the first version provide identical discovery semantics across VS Code desktop, remote/Codespaces, vscode.dev, GitHub web Copilot, and Copilot CLI, or is a VS Code-only scope acceptable?
