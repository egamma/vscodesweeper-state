# Issue #123187 — Composable package.json extension manifest contributions through the use of external files

[https://github.com/microsoft/vscode/issues/123187](https://github.com/microsoft/vscode/issues/123187)

## Summary

Keep open: current desktop and web manifest loaders still read a single package.json without composing external contribution files. The maintainer acknowledged the authoring pain, and the canonical search found no older issue covering this same request.

## Change summary

Allow extension authors to organize contributions in separate, commentable files with deterministic composition into the extension manifest.

## Best solution

Define a supported contribution-composition contract for extension authors, including ordering, collisions, and schema support. Decide whether composition belongs in authoring/package tooling or runtime manifest loading, preserving consistent desktop, remote, web, and Marketplace behavior.

- **Behavior:**

  > Extension authors should be able to organize contributions by feature in separate files that support comments, rather than maintain one large inline contributes object. The request specifies include-array order followed by inline package.json contributions. Acceptance should demonstrate that every intended contribution remains available, composition is deterministic, and collisions and invalid fragments produce the agreed observable result. Desktop, remote, web, and packaged extensions must present equivalent contributions.
- **Trace:**

  > The desktop scanExtensionManifest path in src/vs/platform/extensionManagement/common/extensionsScannerService.ts reads and parses only package.json before scanExtension localizes and validates the manifest. The web getExtensionManifest path in src/vs/workbench/services/extensionManagement/browser/webExtensionsScannerService.ts likewise parses only package.json. src/vs/workbench/services/extensions/common/extensionsRegistry.ts supplies the contributes schema through registered extension points; no include handler was found in the targeted source search. Existing implicit activation generation addresses a related authoring annoyance, not fragment loading. Preserve ordinary manifests, localization, and existing contribution semantics; the broader localization and nightly-variant concerns in the maintainer comment are not requirements of this narrow request. The uncertainty begins at whether the supported contract composes during packaging or during loading, and how collisions and fragment schema discovery behave. https://github.com/microsoft/vscode/issues/97399 is related authoring work, not a verified duplicate.
- **Open decisions:**
  - Should external contribution files be a runtime manifest capability, or an authoring/package-time facility that produces a conventional standalone package.json?
  - Should duplicate contribution identities reject the extension or use deterministic last-in-wins behavior, and should that policy apply uniformly across contribution types?
  - How should contribution fragments receive schema association and completion support: a recognized filename convention, an explicit $schema, or discovery through the parent manifest?
