# Issue #123187 — Composable package.json extension manifest contributions through the use of external files

[https://github.com/microsoft/vscode/issues/123187](https://github.com/microsoft/vscode/issues/123187)

## Summary

Keep open: current manifest loading does not compose contributions from external files, and a maintainer acknowledged the authoring pain. The accepted Backlog request needs a product and tooling design, not a staleness-based close.

## Change summary

Allow extension authors to organize manifest contributions into external, commentable files composed in a defined order.

## Best solution

Agree on a supported contribution-composition contract across extension authoring, packaging, and desktop/web discovery. Decide whether composition is an authoring-time capability or a runtime manifest feature, with explicit collision and schema semantics.

## Plan brief

- **Likely files:** `src/vs/platform/extensionManagement/common/extensionsScannerService.ts`, `src/vs/workbench/services/extensionManagement/browser/webExtensionsScannerService.ts`, `src/vs/workbench/services/extensions/common/extensionsRegistry.ts`
- **Validation:** The plan should define executable acceptance checks using an extension with two external contribution files and inline contributions: verify composition order, duplicate handling, malformed or missing file diagnostics, and comment/schema support. For runtime composition, verify equivalent desktop and web discovery; for authoring-time composition, verify that the packaged manifest contains the agreed flattened contributions.
- **Behavior:**

  > Extension authors want to maintain contributions in separate feature-oriented files that support comments and editor validation, rather than one large package.json object. The requested precedence is external files in declared order, then inline package.json contributions. Acceptance must cover contributions from all sources and deterministic collision handling. Whether this is supported during authoring and packaging only or directly by VS Code at runtime remains a product decision.
- **Trace:**

  > Desktop discovery enters scanExtensionManifest in src/vs/platform/extensionManagement/common/extensionsScannerService.ts, which reads and returns a single parsed package.json. Web discovery uses getExtensionManifest in src/vs/workbench/services/extensionManagement/browser/webExtensionsScannerService.ts and has the same single-file contract. The contributes schema in src/vs/workbench/services/extensions/common/extensionsRegistry.ts is populated by contribution-point registrations, with no composition point found. These reads establish that native external-file composition is missing, but packaging-tool implementation and its compatibility requirements have not been traced. Existing implicit activation-event generation only addresses a secondary authoring concern. Preserve ordinary single-file manifests and existing contribution behavior; unrelated localization extraction and nightly-variant generation are outside the central request. The feature and maintainer acknowledgment are recorded at https://github.com/microsoft/vscode/issues/123187.
- **Open decisions:**
  - Should external contribution files be a runtime manifest contract supported by desktop and web VS Code, or an authoring-time format flattened during packaging?
  - Should duplicate contribution identities reject the composed manifest or use the requested last-source-wins precedence, and what diagnostics should authors receive?
  - What public file-format and schema-discovery contract should identify external contribution manifests and support comments?
