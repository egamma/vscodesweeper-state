# Issue #223276 — Potentially FATAL: Invalid `editor.language.brackets` or `editor.language.colorizedBracketPairs`

[https://github.com/microsoft/vscode/issues/223276](https://github.com/microsoft/vscode/issues/223276)

## Summary

Keep open: current source still accepts nested arrays as bracket delimiters and passes them into string-only operations, causing exceptions in editor language configuration and bracket tokenization. This remains a concrete editor-core validation defect, not an application crash or a verified duplicate.

## Change summary

Malformed editor.language.brackets or editor.language.colorizedBracketPairs values can break text editing, including editing settings.json to repair the configuration.

## Best solution

Ensure malformed user-configured bracket pairs cannot reach string-only editor consumers, while preserving valid pairs and existing empty-array semantics. The bounded configuration-validation path in src/vs/editor/common/languages/languageConfigurationRegistry.ts is the appropriate place to address this.

## Evidence

- **Exact trigger remains accepted:** In src/vs/editor/common/languages/languageConfigurationRegistry.ts, getCustomizedLanguageConfig reads both reported settings. validateBracketPairs checks only whether each pair is an array of length two, then casts its elements to CharacterPair without checking their types. Both reported nested-array examples therefore survive validation.
- **Brackets exception path:** ResolvedLanguageConfiguration constructs OnEnterSupport from the customized brackets. In src/vs/editor/common/languages/supports/onEnter.ts, its constructor passes each delimiter to _createOpenBracketRegExp or _createCloseBracketRegExp. These call escapeRegExpCharacters in src/vs/base/common/strings.ts, which executes value.replace; the array delimiter in [["<", [">"]]] has no replace method and throws before _safeRegExp can handle anything.
