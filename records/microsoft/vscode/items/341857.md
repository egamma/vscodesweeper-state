# Issue #341857 — Request: Add a Reliable Way to Disable All Experiments/A‑B Testing in VS Code Stable

[https://github.com/microsoft/vscode/issues/341857](https://github.com/microsoft/vscode/issues/341857)

## Summary

The central opt-out already exists: setting workbench.enableExperiments to false disables experiment assignments in the workbench and Copilot Chat after restarting VS Code. The report does not describe this setting being ignored; opting out of experiments is distinct from preventing ordinary changes delivered by updates.

## Change summary

Provide a single documented control to disable A/B experimentation in VS Code Stable, including Copilot.

## Best solution

Use the existing workbench.enableExperiments setting rather than introduce another switch, and explain its restart requirement and scope. This controls experiment assignments, not the versions of bundled dependencies or every product change delivered by an update.

- **Proposed comment:**

  > Thanks for the request. Set `"workbench.enableExperiments": false` in your User settings and restart VS Code. This existing setting disables A/B experiment assignments in both the VS Code workbench and Copilot Chat, without requiring you to turn off telemetry.
  > 
  > This does not freeze features across updates or change bundled Copilot dependency versions. If a specific experiment still changes behavior with this setting disabled after restarting, please share the affected feature and steps so we can investigate that opt-out failure.

## Evidence

- **Existing application-wide setting:** src/vs/workbench/services/assignment/common/assignmentService.ts:618-624 registers workbench.enableExperiments as an application-scoped boolean setting. src/vs/workbench/services/telemetry/common/workbenchTelemetryUtils.ts requires that setting to be true before enabling workbench experimentation.
- **Assignments are disabled, not merely their reporting:** WorkbenchAssignmentService constructs its TAS client only when experimentsEnabled is true (assignmentService.ts:283-286). getAssignedTreatment returns undefined without a client or when experimentation is disabled (lines 344-350), so normal treatment reads cannot recover cached assignments through this path.
- **Copilot honors the same setting:** extensions/copilot/src/extension/extension/vscode-node/services.ts, setupMSFTExperimentationService, reads workbench.enableExperiments and installs NullExperimentationService when false. extensions/copilot/src/platform/telemetry/common/nullExperimentationService.ts returns undefined for treatment queries; inline completion Features also consumes IExperimentationService in extensions/copilot/src/extension/completions-core/vscode-node/lib/src/experiments/features.ts.
- **Restart requirement:** src/vs/workbench/contrib/relauncher/browser/relauncher.contribution.ts includes workbench.enableExperiments among restart-sensitive settings and observes its changes. Both the workbench assignment service and Copilot service selection read the setting during initialization.
- **Existing public explanation:** https://code.visualstudio.com/docs/configure/telemetry#_feature-availability-and-telemetry documents A/B feature rollouts and the alternative of disabling usage telemetry to disable workbench experimentation. The dedicated workbench.enableExperiments setting provides an independent experimentation opt-out.
- **Discussion and scope:** https://github.com/microsoft/vscode/issues/341857 requests an opt-out but does not say workbench.enableExperiments was disabled or identify a treatment that survives it. The additional commenter supports the request but provides no contrary behavior. An unstable suffix on a bundled Copilot dependency is not, by itself, evidence of an experiment assignment.
