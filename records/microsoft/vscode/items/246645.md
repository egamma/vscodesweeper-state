# Issue #246645 — VScode read Right Alt key as AltGr key in sometime

[https://github.com/microsoft/vscode/issues/246645](https://github.com/microsoft/vscode/issues/246645)

## Summary

Keep open: a later commenter confirms Right Alt losing its modifier on a US layout, with a same-version bare Electron comparison that the earlier layout explanation does not cover. The evidence warrants investigating VS Code's process-specific keyboard handling; it does not yet establish the root cause or a landed fix.

## Change summary

Right Alt is intermittently reported as AltGraph without an Alt modifier, preventing ordinary Alt-based shortcuts from working on Windows.

## Best solution

Identify why the affected VS Code process produces different raw keyboard events from the matching bare Electron runtime, and restore ordinary Right Alt shortcuts on layouts without AltGr while preserving genuine AltGr input.

- **Validation:** On an affected Windows machine with US English active, compare raw keydown/keyup events in VS Code and the commenter's matching-version bare Electron application. Right Alt+Up/Down must invoke Move Line Up/Down as Left Alt does, including after switching between the reported installed layouts; genuine AltGr character entry and both keyboard.mapAltGrToCtrlAlt modes must retain their existing semantics.
- **Behavior:**

  > On a Windows keyboard layout without AltGr, Right Alt must remain usable for ordinary Alt shortcuts. The reported failure makes Right Alt+Up move the cursor instead of moving the line, while Left Alt works. Acceptance includes Right Alt+Up/Down matching Left Alt behavior before and after layout switches, without changing genuine AltGr input or the documented AltGr-to-Ctrl+Alt setting.
- **Trace:**

  > The confirmed comparison and minimal Electron application are in https://github.com/microsoft/vscode/issues/246645#issuecomment-5189598659. WorkbenchKeybindingService._registerKeyListeners in src/vs/workbench/services/keybinding/browser/keybindingService.ts logs the original DOM event, so the reported AltGraph key and missing modifier are already present before mapper resolution. StandardKeyboardEvent reads DOM modifier state, and WindowsKeyboardMapper.resolveKeyboardEvent optionally maps AltGr to Ctrl+Alt; neither inspection establishes the source of the incorrect raw event. KeyboardLayoutMainService loads native-keymap and reads/subscribes to native keyboard layouts, providing an investigation lead across the main-process boundary. The uncertainty starts at which VS Code process interaction changes browser-observed keyboard state; the matching bare Electron result is evidence against assuming a generic engine defect, not proof that native-keymap is responsible. Preserve genuine AltGr semantics and do not globally reinterpret every AltRight event as ordinary Alt.
