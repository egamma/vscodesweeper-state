# Issue #315781 — GitHub-cli session gets automatically moved under parent git directory

[https://github.com/microsoft/vscode/issues/315781](https://github.com/microsoft/vscode/issues/315781)

## Summary

Real bug: when a GitHub CLI session is started in a subfolder of a git repo, the session's workspace label resolves to the parent git repo's project name (via `project.displayName` in `buildAgentHostSessionWorkspace`), so it gets grouped under the parent repo in the sessions list. Local sessions avoid this because they use a different workspace-resolution path.

## Change summary

GitHub CLI sessions started in a subfolder of a git repository are incorrectly grouped under the parent git directory in the Agents window sessions list.

## Best solution

Fix the workspace-label logic so that sessions started in a subfolder use the subfolder name (or a combination that distinguishes the actual working directory) rather than always adopting the parent git project's `displayName`. The fix likely touches `buildAgentHostSessionWorkspace` in `src/vs/sessions/common/agentHostSessionWorkspace.ts` or how `project` metadata is populated for CLI sessions in the local agent host provider.

## Evidence

- **workspace label source:** In `src/vs/sessions/common/agentHostSessionWorkspace.ts` lines 106–124, when a `project` is present the label is `project.displayName` (the git repo root name), ignoring the actual working directory. A subfolder session gets grouped by this parent-repo label.
- **grouping mechanism:** In `src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts` line 3152–3153, `sessionWorkspaceLabel` uses `session.workspace.get()?.label`, so sessions sharing a parent repo label merge into one group.
- **local sessions unaffected:** The reporter notes local sessions don't have this problem — local chat sessions use `resolveWorkspace` which takes `basename(repositoryUri)` directly from the folder URI, not the git project metadata.
