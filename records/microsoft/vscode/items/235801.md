# Issue #235801 — Report issue fails with HTTP 401

[https://github.com/microsoft/vscode/issues/235801](https://github.com/microsoft/vscode/issues/235801)

## Summary

The accepted Backlog bug remains present on current main: the default legacy reporter posts with an existing GitHub token, but a 401 produces only a misleading console error and no user-visible recovery. The successful report linked in the discussion used another account and does not refute the reporter's cross-platform, account-specific failure.

## Change summary

Creating an extension issue silently fails when VS Code's stored GitHub session token is rejected with HTTP 401.

## Best solution

Give the issue reporter a user-visible recovery path for rejected GitHub credentials, preserving the entered report and allowing the user either to refresh authentication or continue through GitHub's browser issue form.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/issue/electron-browser/issueReporterService.ts`, `src/vs/workbench/contrib/issue/electron-browser/issueService.ts`, `src/vs/workbench/contrib/issue/browser/baseIssueReporterService.ts`, `src/vs/workbench/contrib/issue/test/browser/baseIssueReporterService.test.ts`
- **Validation:** Add an issue-reporter unit test whose GitHub issue POST returns 401 and assert that the chosen recovery UI is exposed while the entered title and body remain available; successful POST and preview-on-GitHub tests must remain unchanged.
- **Behavior:**

  > When GitHub rejects the issue reporter's stored credential, pressing Create on GitHub must not appear to do nothing. The reporter must explain that authentication failed, preserve the completed report, and provide the maintainer-selected recovery action. Successful authenticated creation and Preview on GitHub must continue to behave as before.
- **Trace:**

  > The desktop default remains the legacy auxiliary-window reporter because `issueReporter.wizard.enabled` defaults to false in src/vs/workbench/contrib/issue/electron-browser/issue.contribution.ts. NativeIssueService obtains the first existing GitHub session with `repo` scope in src/vs/workbench/contrib/issue/electron-browser/issueService.ts. IssueReporter.submitToGitHub in src/vs/workbench/contrib/issue/electron-browser/issueReporterService.ts posts with that token, collapses every non-OK response into a misleading console-only `Invalid GitHub URL provided.` message, and returns false; the equivalent base implementation has the same behavior. This conclusively preserves the reporter's 401/no-visible-outcome path on current main. Keep successful API creation, browser preview, and non-authentication failures in scope only as regression boundaries; do not redesign the wider issue reporter or attachment flow.
- **Open decisions:**
  - On HTTP 401, should the reporter ask the user to refresh GitHub authentication, fall back directly to the browser issue form, or present both recovery choices?

## Evidence

- **default path:** src/vs/workbench/contrib/issue/electron-browser/issue.contribution.ts keeps `issueReporter.wizard.enabled` false by default, and NativeIssueFormService.openReporter in src/vs/workbench/contrib/issue/electron-browser/nativeIssueFormService.ts routes that default to the legacy reporter.
- **source reproduction:** NativeIssueService in src/vs/workbench/contrib/issue/electron-browser/issueService.ts selects an existing GitHub session carrying the `repo` scope and passes its access token into the reporter. IssueReporter.submitToGitHub in src/vs/workbench/contrib/issue/electron-browser/issueReporterService.ts sends that token to the GitHub issues API; for every non-success response, including 401, it only logs `Invalid GitHub URL provided.` and returns false, leaving the button with no visible outcome.
- **reporter confirmation:** The reporter confirmed while signed in that the same account reproduces on both macOS and Windows: https://github.com/microsoft/vscode/issues/235801#issuecomment-2622577197.
- **linked report:** https://github.com/microsoft/vscode-python/issues/25084 shows that another account could create an issue through the reporter, but it does not test or resolve the rejected-token path reported here.
- **new wizard:** The newer wizard path in src/vs/workbench/contrib/issue/browser/issueFormService.ts opens a prefilled GitHub URL instead of directly creating the issue, but it is experiment-controlled and disabled by default, so it is not evidence that the reported default flow is fixed.
