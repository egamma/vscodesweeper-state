# Issue #174198 — Git - Cancel git Sync's pull (and the sync action itself) if behind the remote

[https://github.com/microsoft/vscode/issues/174198](https://github.com/microsoft/vscode/issues/174198)

## Summary

Keep open for the maintainer-supported alternative Pull/Push action-button experience. Current settings offer workarounds, but do not provide the requested state-dependent action or protection against newly discovered incoming commits.

## Change summary

Offer a configurable alternative to Sync that separates pulling from pushing and prevents unexpectedly integrating and publishing incoming changes in one action.

## Best solution

Preserve existing Sync semantics while offering the contextual Pull/Push alternative proposed by the maintainer. Settle whether discovering incoming commits during a Push action should stop before integration or permit pulling without pushing, and whether the alternative includes Fetch when neither side has pending commits.

## Plan brief

- **Likely files:** `extensions/git/src/actionButton.ts`, `extensions/git/src/commands.ts`, `extensions/git/src/repository.ts`, `extensions/git/package.json`, `extensions/git/package.nls.json`
- **Validation:** Use two local clones of a bare remote: create an unpushed commit in clone A, push a nonconflicting commit from clone B without refreshing A, then invoke A's alternative Push action. Verify no integrated history is pushed automatically. Also check known incoming commits select Pull, outgoing-only commits select Push, the agreed no-change state, and unchanged behavior for existing Sync users.
- **Behavior:**

  > Users can opt into explicit Git actions instead of the existing Sync action. Known incoming commits offer Pull rather than an action that also pushes local commits. If a Push action discovers previously unknown incoming commits, it must not automatically publish an integrated result before the user can review it. Acceptance includes the stale-remote two-clone scenario, ahead/behind action selection, and preservation of existing Sync behavior; Fetch visibility and whether discovery permits pulling remain decisions.
- **Trace:**

  > GitActionButton.getSyncChangesActionButton() in extensions/git/src/actionButton.ts renders ahead/behind counts but always invokes git.sync. Commands._sync() in extensions/git/src/commands.ts offers a generic pre-operation confirmation; Repository._sync() in extensions/git/src/repository.ts performs pull and then conditionally pushes based on HEAD.ahead, without comparing incoming state at invocation with incoming state discovered during the operation. The registered git.showActionButton properties in extensions/git/package.json control visibility only. The maintainer proposes preserving Sync and adding optional Pull/Push actions at https://github.com/microsoft/vscode/issues/174198#issuecomment-2451982028. Keep existing Sync, Git integration strategies, and ordinary standalone commands unchanged unless the agreed alternative explicitly requires otherwise. The uncertainty is the alternative's discovery-time integration behavior and its no-change presentation, not the existing code path.
- **Open decisions:**
  - When the alternative Push action discovers incoming commits, should it stop before integrating them, or pull them while withholding push for a later explicit user action?
  - When neither incoming nor outgoing commits are known, should the alternative display Fetch or omit the remote action?

## Evidence

- **Maintainer-supported direction:** https://github.com/microsoft/vscode/issues/174198#issuecomment-2451982028 proposes optional Pull and Push buttons rather than changing Sync semantics, showing only Pull when incoming changes are known. The reporter accepts preserving Sync and elaborates the alternative at https://github.com/microsoft/vscode/issues/174198#issuecomment-2452591447.
- **Current action-button capability:** extensions/git/src/actionButton.ts:232-255, getSyncChangesActionButton(), uses ahead/behind counts to display a button bound to git.sync. extensions/git/package.json:3991-4014 exposes git.showActionButton.commit/publish/sync visibility flags, not a contextual Pull/Push/Fetch mode.
- **Current synchronization path:** extensions/git/src/repository.ts:2549-2610, Repository._sync(), awaits the pull path and subsequently pushes when HEAD is ahead. It does not gate that push on whether incoming commits were known when the user clicked. This leaves the reported scenario possible when local commits and newly fetched remote commits merge successfully.
- **Workarounds do not cover the central ask:** extensions/git/src/commands.ts:4278-4308 shows git.confirmSync prompting before synchronization, not after newly discovered incoming changes. git.rebaseWhenSync changes integration strategy, not the pull-then-push contract. Manual git.pull/git.push and hiding Sync give control but not the requested contextual button. The pull.ff=only workaround documented at https://github.com/microsoft/vscode/issues/174198#issuecomment-2491504874 prevents non-fast-forward merges, not the full requested action-selection behavior.

It describes unexpected auto-merge and push when no incoming changes were displayed, but asks to skip pulling in that case; it does not own the additional known-incoming Pull-only behavior or configurable contextual actions established here. It therefore does not absorb this report's full scope.
