# Issue #331838 — Touch: dragging inside a menu dismisses the open submenu instead of scrolling

[https://github.com/microsoft/vscode/issues/331838](https://github.com/microsoft/vscode/issues/331838)

## Summary

The touch-scrolling defect is confirmed in the current source, and an open PR explicitly fixes this issue. Keep it open until that PR is validated and merged or closed.

## Change summary

Dragging inside an overflowing submenu on touch dismisses it before the gesture can scroll to otherwise unreachable actions.

## Best solution

Review and land https://github.com/microsoft/vscode/pull/331839 after validating on a touch device that phantom parent scroll events preserve the submenu while real parent movement still dismisses it.

## Evidence

- **confirmed reproduction:** The reporter reproduced the failure on VS Code 1.133.0 and current main, with Android device instrumentation showing multiple gesture-change events from one touchmove and no clamped parent scroll movement before dismissal.
- **current source:** src/vs/base/browser/ui/menu/menu.ts currently registers SubmenuMenuActionViewItem's parent onScroll handler without inspecting the event and unconditionally calls cleanupExistingSubmenu(true).
- **scroll discriminator:** src/vs/base/common/scrollable.ts computes ScrollEvent.scrollTopChanged and scrollLeftChanged from the clamped positions, providing the exact distinction between phantom raw-position updates and actual menu movement.
- **open fixing PR:** https://github.com/microsoft/vscode/pull/331839 is open, contains `Fixes #331838`, and guards submenu dismissal on scrollTopChanged or scrollLeftChanged in src/vs/base/browser/ui/menu/menu.ts.
- **distinct related report:** https://github.com/microsoft/vscode/issues/336557 was created later and reports Android long-press context menus flash-closing through several context-view, blur, and focus paths; it is not an older canonical with the same observable submenu-scrolling symptom.
