# Issue #160894 — `Auto Save` menu state not updated properly (vscode-web)

[https://github.com/microsoft/vscode/issues/160894](https://github.com/microsoft/vscode/issues/160894)

## Summary

Still present on main: the Auto Save menu toggle state update is delayed in vscode-web because the config→context-key→menu-change→menubar-update pipeline introduces extra latency in the web environment. No fix has been committed.

## Change summary

In vscode-web, the Auto Save menu checkmark doesn't update immediately when the setting changes — requires closing and reopening the menu.

## Best solution

Either listen for `files.autoSave` configuration changes directly in the menubar control (as the reporter's workaround suggests) to force an immediate `updateMenubar()`, or investigate why the context-key-driven menu change event path is slower in web than desktop. The fix likely belongs in `src/vs/workbench/browser/parts/titlebar/menubarControl.ts`.

  > In vscode-web, the File > Auto Save menu toggle doesn't update immediately when files.autoSave changes — the user must close and reopen the menu. The toggle uses `ContextKeyExpr.notEquals('config.files.autoSave', 'off')` (src/vs/workbench/contrib/files/browser/fileActions.contribution.ts:722), which relies on the context-key→menu-onDidChange→scheduled-updateMenubar pipeline. In web, this pipeline introduces a visible delay. The fix: in src/vs/workbench/browser/parts/titlebar/menubarControl.ts, in the `onConfigurationUpdated` method (line 198), add a check for `event.affectsConfiguration('files.autoSave')` that calls `this.updateMenubar()`. This ensures an immediate menu refresh on autoSave config changes. Do NOT restructure the broader menu update pipeline. Validate by confirming the toggle state updates on the first menu open after a config change, without requiring a close-reopen cycle.
