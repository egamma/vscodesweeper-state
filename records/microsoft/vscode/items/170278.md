# Issue #170278 — Alt+NumPadKey with num lock will still write the alt code character on top of performing the action

[https://github.com/microsoft/vscode/issues/170278](https://github.com/microsoft/vscode/issues/170278)

## Summary

Valid bug — on Windows, Alt+NumPad keys with NumLock off dispatch the bound keybinding (e.g. Alt+Left = go back) but also insert the alt-code character. No fix found on main; no comments or reproduction confirmation. The bug is niche (numpad + NumLock off + screen reader) and has had zero engagement, but it affects accessibility users.

## Change summary

Pressing Alt+NumPad4 (equivalent to Alt+Left when NumLock is off) triggers the navigation command but also types an unwanted diamond character from Windows' alt-code input mechanism.

## Best solution

The root cause likely sits in the Electron/Chromium layer — Windows generates a WM_CHAR message when Alt is released after numpad input, even when NumLock is off and the key acted as an arrow. VS Code would need to detect and suppress this phantom character insertion when the Alt+NumPad keydown was already consumed by a keybinding dispatch. The fix would likely touch `src/vs/editor/browser/controller/editContext/textArea/textAreaEditContextInput.ts` or the keybinding dispatch's preventDefault path. Given the Chromium involvement, this may also be an upstream issue worth verifying against current Electron.
