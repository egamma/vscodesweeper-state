# Issue #348360 — Stop button throws away all context from the turn

[https://github.com/microsoft/vscode/issues/348360](https://github.com/microsoft/vscode/issues/348360)

## Summary

Keep open: current source contains cancellation paths that can lose conversation metadata, but the reporter's exact path is not confirmed. The supplied stop-and-follow-up steps suffice to retest; neither a landed fix nor a verified canonical was established.

## Change summary

Preserve completed agent work and available conversation context when Stop interrupts a turn, so the next message can continue from that work.

## Best solution

Make cancellation retain completed assistant/tool history and communicate the interruption to the next request without continuing unwanted tools. Preserve provider-supported reasoning context, without promising recovery of model-internal reasoning that was never returned.

- **Behavior:**

  > Stopping an agent after completed useful work must interrupt execution without making the next request forget that completed work. The follow-up should retain available assistant messages and completed tool results, and recognize that the preceding turn was interrupted. Cancelled or unfinished tools must not be represented as successfully completed or automatically resumed. Acceptance should inspect the actual follow-up prompt rather than rely on the model's description of its memory.
- **Trace:**

  > The classic Copilot path runs through ToolCallingLoop, DefaultIntentRequestHandler, Turn, and ChatParticipantRequestHandler. throwIfCancelled can establish a metadata-free cancelled response, while Turn.setResponse rejects later replacement and addHistoryToConversation prefers the cached Turn over deserialization of returned metadata. Separately, ExtHostChatAgents2 permits only a one-second cancellation completion window before returning undefined. These are source-backed leads, not confirmation of which path the reporter used; establish the model/backend and cancellation timing first. ## Evidence

- **Reported trigger:** https://github.com/microsoft/vscode/issues/348360 describes macOS, VS Code 1.146.0, stopping a multi-minute agent turn after useful work, then sending a corrective follow-up that appears to lack the interrupted turn's context. There are no confirming comments or model/provider details.
- **Cancellation metadata hazard:** In extensions/copilot/src/extension/intents/node/toolCallingLoop.ts, throwIfCancelled sets the Turn response to Cancelled with CanceledResult. _runLoop catches cancellation after a previous result and returns accumulated rounds. DefaultIntentRequestHandler.getResult subsequently constructs metadata containing those rounds, but Turn.setResponse in extensions/copilot/src/extension/prompt/common/conversation.ts refuses subsequent assignments once the response is Cancelled.
- **Follow-up history path:** extensions/copilot/src/extension/prompt/node/chatParticipantRequestHandler.ts caches the Conversation and adds responseId to the returned result. addHistoryToConversation preferentially retrieves that cached Turn. Turn.rounds falls back to a synthetic round without tool calls when its stored response metadata lacks toolCallRounds, providing a concrete context-loss lead.
- **Additional cancellation boundary:** src/vs/workbench/api/common/extHostChatAgents2.ts wraps participant completion in raceCancellationWithTimeout(1000, ...), returning undefined if completion takes longer after cancellation. This can independently prevent returned history metadata from reaching the workbench; its relevance to this report remains unverified.
- **Related work is not proven coverage:** https://github.com/microsoft/vscode/pull/343824 is open and addresses interrupted commits for HydraFusion runtime workflows. It is not linked to this issue and does not establish coverage of the classic Copilot participant/history path traced here. https://github.com/microsoft/vscode/issues/295543 describes context disappearing while editing a clarification answer, not the same verified Stop-triggered failure.
