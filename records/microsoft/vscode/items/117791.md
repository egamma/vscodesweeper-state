# Issue #117791 — Git - Add more fields and sort options

[https://github.com/microsoft/vscode/issues/117791](https://github.com/microsoft/vscode/issues/117791)

## Summary

Status sorting already exists, but sorting changed files by modification time and displaying sortable addition/deletion counts remain missing. Keep this accepted Backlog request open; the verified related modification-time request is newer and does not cover its full scope.

## Change summary

Provide modification-time, status, lines-added, and lines-removed fields and sorting options when preparing Git commits.

## Best solution

Extend the existing SCM changes-list experience with optional modification-time and change-count information and corresponding sorting, preserving current defaults. Decide the presentation and staged-versus-working-tree counting semantics with the area maintainer, coordinating the modification-time portion with https://github.com/microsoft/vscode/issues/200916.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/scm/browser/scmViewPane.ts`, `src/vs/workbench/contrib/scm/browser/scm.contribution.ts`, `src/vs/workbench/contrib/scm/common/scm.ts`, `extensions/git/src/repository.ts`
- **Validation:** In a temporary Git repository, modify several files at distinct times with different addition/deletion counts, including a file with both staged and unstaged changes. Verify that each agreed metadata field displays the expected value and that selecting its sort orders the changes accordingly; verify existing name/path/status sorting and tree view remain unchanged. The plan should establish automated comparator and resource-data checks for the agreed semantics.
- **Behavior:**

  > When preparing a Git commit, users want to identify their most recently modified files and compare the amount of added and removed content without opening every diff. Status sorting is already available; modification-time sorting and visible sortable change counts are not. The finished capability should provide the agreed metadata presentation and ordering while preserving existing default sorting and tree-view behavior. Acceptance must cover staged and unstaged changes, files deleted from disk, and files for which textual line counts are unavailable.
- **Trace:**

  > The changes list is rendered by ResourceRenderer and ordered by SCMTreeSorter.compare in src/vs/workbench/contrib/scm/browser/scmViewPane.ts. ViewSortKey and the scm.defaultViewSortKey registration in scm.contribution.ts admit only name, path, and status; status sorting compares decoration tooltips. ISCMResource in src/vs/workbench/contrib/scm/common/scm.ts has no timestamp or change-count fields, so the requested metadata is not available through that resource contract. The built-in Git Resource implementation lives in extensions/git/src/repository.ts. Source inspection establishes the missing surface, but does not establish the full metadata acquisition and extension-host transport design. Preserve existing defaults, non-Git SCM providers, and tree ordering. Coordinate the modification-time portion with https://github.com/microsoft/vscode/issues/200916 without treating that younger, narrower report as a duplicate canonical.
- **Open decisions:**
  - Should the additional fields appear as optional sortable columns, or as another metadata presentation within the existing changes list?
  - Should lines-added and lines-removed describe each resource group's diff separately, including staged versus unstaged changes, or describe the total file change against HEAD?
  - How should deleted files with no filesystem modification time and binary files with no textual line counts be displayed and ordered?
