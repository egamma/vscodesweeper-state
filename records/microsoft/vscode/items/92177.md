# Issue #92177 — API for reading current word-wrap state (and toggling it) on a TextDocument

[https://github.com/microsoft/vscode/issues/92177](https://github.com/microsoft/vscode/issues/92177)

## Summary

A real extension API gap remains: extensions can invoke the active-editor toggle command, but cannot read the effective wrapping state or safely set and restore it through `TextEditorOptions`. The broader API contract needs design discussion, and the narrower opening-time request has substantial community support.

## Change summary

Expose the effective word-wrap state to extensions and allow them to control it temporarily for document presentation and decorations.

## Best solution

Design a TextEditor-scoped API that reports effective wrapping, emits option changes, and supports an explicit transient override with restoration semantics; it should also account for the opening-time scenario tracked by https://github.com/microsoft/vscode/issues/136927.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadEditor.ts`, `src/vs/workbench/api/common/extHostTextEditor.ts`, `src/vs/workbench/contrib/codeEditor/browser/toggleWordWrap.ts`, `src/vs/workbench/api/test/browser/extHostTextEditor.test.ts`, `src/vs/workbench/api/test/browser/mainThreadDocumentsAndEditors.test.ts`
- **Validation:** Add API tests that read the effective wrapping state, observe its change after a transient override, restore inherited behavior, and verify the existing toggle command remains consistent with the exposed state.
- **Behavior:**

  > Extensions need to determine whether a visible text editor is effectively wrapping lines and react when that state changes. They also need to apply a temporary wrapping override while presenting annotations or extension-opened content, then restore the user's inherited behavior without guessing the previous state. Existing user toggling and diff-editor synchronization must remain consistent. Acceptance should cover reading, change notification, explicit on/off control, and restoration to inherited configuration.
- **Trace:**

  > `TextEditorOptions` in `src/vscode-dts/vscode.d.ts` currently exposes no wrapping property. Its values flow through `IResolvedTextEditorConfiguration` and `ITextEditorConfigurationUpdate` in `src/vs/workbench/api/common/extHost.protocol.ts`, are read and applied by `MainThreadTextEditorProperties`/`MainThreadTextEditor` in `src/vs/workbench/api/browser/mainThreadEditor.ts`, and are surfaced by `ExtHostTextEditorOptions` in `src/vs/workbench/api/common/extHostTextEditor.ts`. The core toggle in `src/vs/workbench/contrib/codeEditor/browser/toggleWordWrap.ts` stores a transient model property, applies it through `wordWrapOverride2`, and derives effective state from `EditorOption.wrappingInfo`; this confirms the capability exists internally but not in the extension API. Preserve the command's behavior, diff synchronization, user configuration, and restoration semantics. The narrower opening-time case is tracked by https://github.com/microsoft/vscode/issues/136927.
- **Open decisions:**
  - Should the stable contract expose word wrapping as a mutable `TextEditorOptions` property with change events, as an opening option, or both?
  - Should extension control be a tri-state `on`/`off`/`inherit` override so extensions can restore user configuration, or a different public contract with equivalent observable restoration behavior?
  - Should setting the API state follow the existing model-associated toggle behavior across multiple views of one document, or be scoped independently to each visible text editor?

## Evidence

- **current API gap:** `src/vscode-dts/vscode.d.ts` exposes indentation, cursor style, and line numbers through `TextEditorOptions`, but no word-wrap state; `TextDocumentShowOptions` likewise has no wrapping option.
- **existing internal behavior:** `src/vs/workbench/contrib/codeEditor/browser/toggleWordWrap.ts` implements `editor.action.toggleWordWrap` using model-associated transient state and computes effective wrapping from `EditorOption.wrappingInfo`, but that state is not exposed to extensions.
- **API bridge boundary:** `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadEditor.ts`, and `src/vs/workbench/api/common/extHostTextEditor.ts` synchronize the existing `TextEditorOptions`; none carries wrapping information or updates.
- **related demand:** https://github.com/microsoft/vscode/issues/136927 is open in the Backlog and received enough community upvotes for its narrower request to choose word wrapping when an extension opens a document.
- **canonical search:** https://github.com/microsoft/vscode/issues/136927 covers only opening-time configuration, not this issue's broader read, change-notification, toggle, and restoration requirements, so it is not a valid canonical duplicate.
- **earlier discussion:** https://github.com/microsoft/vscode/issues/70485 requested readable wrapping state for mirrored editors and was closed through the information-needed flow after a maintainer questioned that specific synchronization use case; it does not settle the distinct decoration and temporary-override scenarios here.
