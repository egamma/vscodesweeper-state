# Issue #92177 — API for reading current word-wrap state (and toggling it) on a TextDocument

[https://github.com/microsoft/vscode/issues/92177](https://github.com/microsoft/vscode/issues/92177)

## Summary

A real extension API gap remains: extensions can toggle word wrap through the built-in command, but they cannot reliably read the effective per-editor state or control it as part of showing a document. The Backlog milestone permits judgment on the merits, and neither current source nor the related candidates provides a completed implementation or canonical replacement.

## Change summary

Expose the effective word-wrap state for a visible text editor and provide a supported API for changing it when an extension presents annotations.

## Best solution

Define an editor-scoped API that exposes effective word-wrap state and permits a temporary or explicit override without changing unrelated editors or persisting an unintended user-setting change. The API owners should decide whether this belongs on `TextEditor`, in show options, or as a scoped override with restoration semantics.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostTextEditors.ts`, `src/vs/workbench/api/browser/mainThreadEditors.ts`
- **Validation:** Add extension API tests that open two editors with different effective wrap states, verify the API reports each state, change one editor through the proposed API, and assert the other editor and persisted user configuration remain unchanged.
- **Behavior:**

  > An extension can determine whether word wrapping is effectively enabled for the relevant visible text editor, including editor-specific overrides rather than only the raw workspace setting. It can request a word-wrap change for that editor while presenting UI such as blame annotations, without unexpectedly changing other editors or permanently altering user configuration. Acceptance should cover separate editors with different states, the state notification/read path, and restoration or persistence behavior selected by the API owners.
- **Trace:**

  > The report is about an extension-facing gap around core editor word-wrap state, not the editor's existing user command itself. The likely path crosses the public declaration in src/vscode-dts/vscode.d.ts, extension-host editor objects in src/vs/workbench/api/common/extHostTextEditors.ts and src/vs/workbench/api/common/extHost.api.impl.ts, and the main-thread editor bridge in src/vs/workbench/api/browser/mainThreadEditors.ts. Existing configuration access cannot reliably represent an editor's effective state, while command invocation does not provide scoped state or restoration semantics. The boundary is editor-scoped word-wrap behavior: unrelated editor options, other visible editors, and user configuration must not change incidentally. Independent extension demand is recorded at https://github.com/microsoft/vscode/issues/92177#issuecomment-804532595.
- **Open decisions:**
  - Should the public state and control live on `TextEditor`, in `TextDocumentShowOptions`, or in a separate editor-options API?
  - Should changing word wrap be a persistent editor override or a temporary scoped override that can be restored?
  - How should extensions observe effective-state changes caused by user commands, configuration changes, or editor layout changes?
