# Issue #48659 — FileSystemProvider: no way of handling permissions issues

[https://github.com/microsoft/vscode/issues/48659](https://github.com/microsoft/vscode/issues/48659)

## Summary

The read-only portion was implemented, but the central elevation/unlock gap remains in the current FileSystemProvider API. With 389 community upvotes and a Backlog milestone, this should remain open.

## Change summary

Let filesystem providers represent permission restrictions and handle user-approved retries that unlock files or write with elevated privileges.

## Best solution

Design a provider-neutral API that exposes locked permissions and communicates an explicit user-approved unlock or elevated-write retry to the provider, without assuming a particular sudo or authentication mechanism.

## Evidence

- **current API gap:** src/vscode-dts/vscode.d.ts exposes only FilePermission.Readonly, while FileSystemProvider.writeFile receives only create and overwrite options; providers cannot handle an explicit unlock or elevated retry.
- **internal capability:** src/vs/platform/files/common/files.ts contains internal FilePermission.Locked, and src/vs/workbench/services/workingCopy/common/storedFileWorkingCopy.ts offers local elevated/unlock save actions, but those capabilities are not represented by the public provider contract.
- **partial implementation:** Commit c4546485f006e5676ddb3221e1b4d98a651c0d6d finalized per-file readonly metadata for https://github.com/microsoft/vscode/issues/73122, covering only one part of this request.
