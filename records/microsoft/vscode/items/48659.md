# Issue #48659 — FileSystemProvider: no way of handling permissions issues

[https://github.com/microsoft/vscode/issues/48659](https://github.com/microsoft/vscode/issues/48659)

## Summary

Keep open: current source explicitly restricts elevated saves to local files and still lacks an extension-provider contract for permission recovery. Internal read-only unlocking partially covers the original request, but the remaining provider API gap and substantial community demand warrant continued tracking.

## Change summary

Allow file system providers to support explicit permission-recovery operations, including elevated writes and removal of read-only restrictions.

## Best solution

Define a capability-based provider contract for user-requested permission recovery and integrate it with existing save-error actions. Preserve local elevated-save behavior and distinguish per-operation recovery from the broader request to switch the entire remote session's user.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/platform/files/common/files.ts`, `src/vs/platform/files/common/fileService.ts`, `src/vs/workbench/api/common/extHostFileSystem.ts`, `src/vs/workbench/contrib/files/browser/editors/textFileSaveErrorHandler.ts`, `src/vs/workbench/services/files/electron-browser/elevatedFileService.ts`
- **Validation:** After the contract is agreed, use a test file-system provider with a non-file scheme that initially rejects writes for insufficient permissions or a read-only restriction. Verify that supported recovery is offered and reaches the provider only after explicit user action, unsupported providers retain existing error behavior, failed or cancelled recovery retains unsaved edits, and ordinary saves plus local elevated saves remain unchanged.
- **Behavior:**

  > Extension file-system providers currently cannot participate through a supported API in the editor's elevated-save or read-only-unlock recovery workflow. A provider supporting the agreed recovery operation should let the user explicitly retry a failed save without running the whole editor or remote session as another user. Providers without that capability must retain their existing behavior, and cancellation or failure must preserve unsaved edits. Acceptance must cover permission-denied and read-only cases separately, along with unchanged ordinary and local elevated saves.
- **Trace:**

  > The public FileSystemProvider.writeFile contract in src/vscode-dts/vscode.d.ts exposes only create and overwrite. Internal unlock support exists in src/vs/platform/files/common/files.ts, but FileService.validateWriteFile rejects it without FileWriteUnlock, and ExtHostFileSystem.registerFileSystemProvider does not advertise that capability for extension providers. TextFileSaveErrorHandler and NativeElevatedFileService both restrict elevation to Schemas.file and explicitly cite this issue. This establishes a remaining API and save-workflow gap rather than an executable bug reproduction. The uncertainty starts at the provider's public recovery contract and its user-visible scope; preserve existing trust checks, local save behavior, and explicit consent. Whole-session user switching discussed in the thread and remote-only https://github.com/microsoft/vscode-remote-release/issues/1688 are related but do not replace this broader provider request.
- **Open decisions:**
  - Should the provider contract expose separate read-only-unlock and elevated-write capabilities, or one provider-defined permission-recovery operation, and what recovery choices should users see?
  - Should the initial contract cover save/write recovery only, or also permission-denied reads and directory operations; should choosing another user for an entire remote session remain separate?

## Evidence

- **Existing capability and remaining gap:** src/vscode-dts/vscode.d.ts:9694-9714 declares FileSystemProvider.writeFile options containing only create and overwrite. FileSystemError.NoPermissions and FilePermission.Readonly can describe failures or restrictions, but do not provide a supported elevated-write or unlock request contract.
- **Explicit current limitation:** NativeElevatedFileService.isSupported in src/vs/workbench/services/files/electron-browser/elevatedFileService.ts accepts only Schemas.file and explicitly references https://github.com/microsoft/vscode/issues/48659 as the missing generic support. Its elevated write requests workspace trust before calling nativeHostService.writeElevated.
- **Reporter-visible save path:** src/vs/workbench/contrib/files/browser/editors/textFileSaveErrorHandler.ts:138-182 offers SaveModelElevatedAction only when resource.scheme is Schemas.file. A permission-denied save through a non-file provider receives Retry rather than Retry as Admin/Sudo.
