# Issue #202860 — Zero width character highlighting broken for emojis containing ZWJs

[https://github.com/microsoft/vscode/issues/202860](https://github.com/microsoft/vscode/issues/202860)

## Summary

The reported inconsistency remains explainable in current source: appending an ASCII digit changes the word-context exemption, although the emoji sequence itself is unchanged. Keep this open under unicode-highlight for an emoji-aware refinement; no verified canonical or completed fix covers it.

## Change summary

Avoid changing invisible-character warnings for a valid emoji ZWJ sequence merely because an ASCII character follows it.

## Best solution

Recognize valid emoji ZWJ sequences consistently in Unicode highlighting without globally exempting joiners or weakening warnings for invisible characters embedded in ordinary text. Preserve explicit all-non-ASCII highlighting and unrelated word-context behavior.

## Evidence

- **Exact source path:** src/vs/editor/common/services/unicodeTextModelHighlighter.ts: computeUnicodeHighlights obtains word context through getWordAtText and passes it to CodePointHighlighter.shouldHighlightNonBasicASCII. src/vs/editor/common/core/wordHelper.ts: DEFAULT_WORD_REGEXP treats the emoji sequence and an adjacent digit as one word, excluding the surrounding quotes.
- **Cause of the differing warnings:** CodePointHighlighter.shouldHighlightNonBasicASCII suppresses highlighting when a word contains an unmistakably non-ASCII character but no basic ASCII characters. The standalone emoji satisfies that exemption; appending '1' disables it. U+200D is then classified as invisible because src/vs/base/common/strings.ts includes decimal 8205 in InvisibleCharacters. The invisible-character branch still contains 'TODO check for emojis'. This is a source trace, not an executed reproduction.
