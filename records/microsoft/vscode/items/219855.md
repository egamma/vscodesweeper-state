# Issue #219855 — [json] allow to override & replace existing schemas

[https://github.com/microsoft/vscode/issues/219855](https://github.com/microsoft/vscode/issues/219855)

## Summary

A real capability gap remains: matching schemas are intentionally combined, while the reporter wants a user-configured schema to override or replace schemas contributed by extensions. The maintainer discussion clarifies current behavior but does not establish that the requested override should be rejected.

## Change summary

Allow workspace or user `json.schemas` entries to override or replace other matching JSON schemas, including extension-contributed schemas.

## Best solution

Define an explicit JSON schema override mechanism rather than relying on ordering, because the language service combines matching schemas with `allOf`. The design should decide whether override semantics are expressed per mapping, per file pattern, or through a separate exclusion mechanism while preserving additive behavior by default.

## Plan brief

- **Likely files:** `extensions/json-language-features/server/src/jsonServer.ts`, `extensions/json-language-features/package.json`
- **Validation:** Add JSON language-features tests with overlapping built-in/extension, user, workspace, and document `$schema` associations, then verify the chosen override semantics while retaining additive validation for mappings that do not opt out.
- **Behavior:**

  > Users need an explicit way for a schema configured through `json.schemas` to replace other schemas matching the same JSON document, particularly schemas contributed by extensions. Existing additive behavior should remain the default unless the user opts into replacement. Acceptance must cover extension-contributed, user, workspace, and document-level schema associations and verify both override and ordinary additive cases.
- **Trace:**

  > The issue discussion establishes that matching schemas are combined through `allOf`, making registration order irrelevant to the requested behavior. The JSON extension gathers configured and contributed schema associations before passing them to the JSON language service; the likely boundary is the schema-association/configuration path in `extensions/json-language-features/server/src/jsonServer.ts` plus the `json.schemas` contribution schema in `extensions/json-language-features/package.json`. Do not silently change existing additive semantics or reinterpret every workspace mapping as exclusive. No older issue with the same reporter-observable symptom was identified in the supplied canonical search.
- **Open decisions:**
  - Should replacement be an explicit opt-in on each `json.schemas` mapping, or should every workspace/user mapping automatically suppress matching extension-contributed schemas?
  - If both user and workspace mappings match, should replacement suppress only extension schemas or also lower-scope user mappings?
  - Should an in-document `$schema` declaration remain authoritative over every configured replacement rule?
