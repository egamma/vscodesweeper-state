# Issue #348351 — First request of an automation-started agent-host session is missing client-provided tools (integrated browser tools) and plugin skills

[https://github.com/microsoft/vscode/issues/348351](https://github.com/microsoft/vscode/issues/348351)

## Summary

The first-turn client-tool gap remains in current source: automation creation supplies a synthetic client with no tools and starts the prompt without connected-editor preparation. Keep this open for the maintainer's investigation; captured plugins address part of the skills path but do not resolve browser-tool availability.

## Change summary

Automation-started sessions lack client-provided browser tools and reported plugin skills on their initial request, although a later interactive prompt acquires them.

## Best solution

Complete the maintainer's proposed opt-in connected-editor readiness contract so required tools are both advertised and executable before the automation's first message. Preserve headless runs and explicitly distinguish unavailable editor-tool requirements from successful execution.

- **Behavior:**

  > An automation explicitly requiring connected-editor tools must not silently execute its first prompt without those tools. With an authorized ready client, its first request can discover and invoke openBrowserPage without a follow-up or resume. Without such a client, the run exposes a distinguishable unavailable or waiting outcome. Ordinary headless automations remain supported, and selected captured plugin skills should be checked independently on the initial request.
- **Trace:**

  > AgentHostAutomationCustomizations.toRunActiveClient in src/vs/platform/agentHost/node/agentHostAutomationCustomizations.ts creates a plugin-only synthetic contribution with tools: []; absent captured plugins produce no contribution. AgentHostAutomationService._startRun passes that contribution through the AgentService execution adapter into _createSessionWithOrigin, then starts the initial message. AgentHostSessionHandler's interactive path acquires scoped contributions, claims an exact backend session through _ensureActiveClient, and watches input requests addressed to its connection identity. These source findings establish missing automation preparation, not a tested complete fix. The maintainer's requirements are recorded at https://github.com/microsoft/vscode/issues/348351#issuecomment-6990813731. Preserve headless execution, approvals, current tool enablement, immutable backend identities, and revocation/disconnect authority; do not borrow an arbitrary window or persist live handlers. Migration, page-identity errors, and token accounting are not proven consequences of this path.
- **Open decisions:**

  - When the required client is absent or disconnects before first-message readiness, should the run wait, fail, or require explicit user resumption?
