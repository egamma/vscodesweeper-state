# Issue #64358 — consider to allow for variable substitution in the inputs section

[https://github.com/microsoft/vscode/issues/64358](https://github.com/microsoft/vscode/issues/64358)

## Summary

Keep open: current source still passes input defaults to the prompt without expanding variables. The request has 57 upvotes, is already correctly routed, and no verified canonical issue absorbs it.

## Change summary

Allow non-interactive variables such as environment, configuration, workspace-folder, and active-file variables in input definitions, particularly prompt defaults.

## Best solution

Support predictable non-interactive expansion in the shared task/debug input resolver while retaining the boundary against recursive interactive input evaluation. Agree on the supported input fields and interaction with remembered answers before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/services/configurationResolver/browser/baseConfigurationResolverService.ts`, `src/vs/workbench/services/configurationResolver/common/variableResolver.ts`, `src/vs/workbench/services/configurationResolver/common/configurationResolverSchema.ts`, `src/vs/workbench/services/configurationResolver/test/electron-browser/configurationResolverService.test.ts`

Run the focused suite with scripts/test.sh --run src/vs/workbench/services/configurationResolver/test/electron-browser/configurationResolverService.test.ts after implementation in a writable development checkout.
- **Behavior:**

  > An input prompt whose default references a supported non-interactive variable should display its resolved value before the user accepts or edits it. Environment, configuration, workspace-folder, and active-file examples should work in their applicable contexts. Literal defaults and cancellation must remain compatible, and expanding an input definition must not unexpectedly execute commands or open another input prompt. Acceptance must cover both what the prompt displays and the value returned to the consuming task or debug configuration.
- **Trace:**

  > BaseConfigurationResolverService.resolveWithInteraction obtains definitions through resolveInputs and hands them to showUserInput in src/vs/workbench/services/configurationResolver/browser/baseConfigurationResolverService.ts. resolveInputs returns configuration values without expansion; promptString directly uses info.default after supplied and remembered values, while pickString constructs items from raw options. AbstractVariableResolverService.resolveAsync in common/variableResolver.ts already resolves ordinary variables, but is not applied to these definitions. ConfigurationResolverExpression also discovers nested substitutions during resolution, so preserving the non-interactive boundary requires explicit acceptance coverage rather than assuming all recursive evaluation is harmless. Existing single-prompt and single-pick tests are in test/electron-browser/configurationResolverService.test.ts. The maintainer's recursion/sequencing constraint is recorded at https://github.com/microsoft/vscode/issues/64358#issuecomment-618867063; the remaining uncertainty concerns the public field scope and remembered-answer behavior, not whether raw defaults currently reach the UI.
- **Open decisions:**
  - Should non-interactive substitution initially cover only promptString defaults, or also descriptions and pickString defaults, option labels, and option values?
  - When a variable-derived default changes between runs, should the prompt continue preferring the remembered answer or show the newly evaluated default?

## Evidence

- **Existing-capability check:** In src/vs/workbench/services/configurationResolver/browser/baseConfigurationResolverService.ts, resolveInputs reads configured input definitions without substitution. showUserInput passes info.description and info.default directly to Quick Input; prompt value precedence is supplied input value, remembered answer, then configured default. pickString similarly uses raw option values and compares them with raw info.default. The shared inputsSchema in common/configurationResolverSchema.ts exposes literal defaults and options, not an alternative expansion setting.
- **Existing resolver is not connected to input defaults:** src/vs/workbench/services/configurationResolver/common/variableResolver.ts provides resolveAsync and evaluateSingleVariable for ordinary variables, but the resolveInputs-to-showUserInput path does not apply them to input definitions. Expansion after accepting a prompt does not satisfy the request to display an expanded default before accepting it.
