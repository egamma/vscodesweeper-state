# Issue #339657 — worktree disk-usage traversal causes high CPU load

[https://github.com/microsoft/vscode/issues/339657](https://github.com/microsoft/vscode/issues/339657)

## Summary

Well-diagnosed, fresh report (same day) with concrete CPU profiles and exact code paths already pointed to; confirmed from source that the worktree disk-usage traversal issues one Agent Host RPC per child entry with unbounded per-directory concurrency, and separately that the AHP JSONL logger config isn't observed dynamically. Already correctly labeled (agents-window, performance); keep open for a fix.

## Change summary

Session worktree disk-usage measurement and/or AHP JSONL diagnostic logging drive sustained high renderer CPU (100%+, up to ~274%) during active Agent Host sessions.

## Best solution

Two independent, bounded fixes: (1) in worktreeDiskUsage.ts, replace the nested directory-level/child-level concurrency (MAX_CONCURRENT_REQUESTS directories at a time, but unbounded Promise.all over every child within a directory) with a single global concurrency-limited queue so large directories like node_modules can't burst thousands of simultaneous resourceResolve RPCs; (2) in LocalAgentHostService, react to chat.agentHost.ahpJsonlLoggingEnabled config changes by disposing/recreating _ahpLogger instead of only reading it once in the constructor.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/providers/agentHost/browser/worktreeDiskUsage.ts`, `src/vs/sessions/contrib/providers/agentHost/test/browser/worktreeDiskUsage.test.ts`, `src/vs/platform/agentHost/electron-browser/localAgentHostService.ts`, `src/vs/platform/agentHost/common/ahpJsonlLogger.ts`
- **Validation:** For the traversal fix: a test on getWorktreeDiskUsage asserting the number of concurrently in-flight resourceResolve calls never exceeds a fixed bound even for a directory with hundreds of children. For the logger fix: a test asserting the AHP logger is disposed/stops writing once the setting is toggled off via configuration change.
- **Behavior:**

  > Running an Agent Host session with a large worktree (e.g. containing node_modules) should not drive the Agents renderer to 100%+ CPU through disk-usage measurement; concurrent Agent Host RPC traffic for the traversal should be capped globally, not just per-directory. Separately, disabling chat.agentHost.ahpJsonlLoggingEnabled should stop an already-active AHP JSONL logger (and its file writes) without requiring a full Agent Host restart.
- **Trace:**

  > Traced via source: worktreeDiskUsage.ts's getWorktreeDiskUsage limits concurrent *directories* to MAX_CONCURRENT_REQUESTS (8) but fires one resourceResolve RPC per *child entry* inside each directory via an unbounded Promise.all — for a directory with thousands of entries this bursts thousands of simultaneous renderer-to-host IPC round trips, matching the reporter's traced MessagePort/ipc.mp.ts/postMessage hot path. Separately, localAgentHostService.ts reads the AHP logging setting once into a readonly `_ahpLogger` field and its only config-change listener only forwards OTel policy (line 196), so toggling the setting live has no effect on an existing connection — confirmed by the reporter's live test (comment 1) showing continued multi-GB log writes after disabling the setting. Do not change the resourceList/resourceResolve protocol surface or symlink-detection semantics (tested in worktreeDiskUsage.test.ts) as part of either fix without a maintainer decision; see https://github.com/microsoft/vscode/issues/339657 comments 1-3 for the full profiling detail.
- **Open decisions:**
  - Should the worktree traversal fix be a client-side global concurrency cap (quick mitigation, no protocol change) or a new batch/paginated stat RPC in the Agent Host protocol (bigger change, but removes the fundamentally one-RPC-per-file design)?
  - Should disk-usage measurement be moved off the renderer process entirely (as the reporter suggests), or is capping concurrency in place sufficient?
  - Should the AHP JSONL logger config-change handling (dispose/recreate on toggle) be fixed in the same change as the traversal burst, or tracked/landed separately since they're different code paths and services?
