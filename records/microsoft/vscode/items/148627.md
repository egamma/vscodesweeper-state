# Issue #148627 — Meta Mouse Cursor Mode

[https://github.com/microsoft/vscode/issues/148627](https://github.com/microsoft/vscode/issues/148627)

## Summary

Keep open for design exploration: existing inspectors cover tokens or context keys, not the requested unified explanation and customization of UI elements. The team-authored Backlog request has explicit design interest, and the older theme-inspector issue covers only part of its scope.

## Change summary

Introduce an inspection mode that explains hovered or clicked UI elements and exposes their relevant appearance and visibility controls.

## Best solution

Define a consistent, accessible inspection experience that connects UI elements to their meaning, governing settings, and theme colors. Coordinate the color-discovery portion with https://github.com/microsoft/vscode/issues/62637 without losing this request's broader interactive-help and feature-discovery goals.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/actions/developerActions.ts`, `src/vs/workbench/contrib/codeEditor/browser/inspectEditorTokens/inspectEditorTokens.ts`, `src/vs/workbench/services/themes/common/workbenchThemeService.ts`, `src/vs/editor/common/config/editorOptions.ts`
- **Validation:** After agreeing the initial scope, manually enter inspection mode and inspect a minimap, a colorized bracket, and a supported workbench element. Verify that inspection does not activate the underlying control, identifies its purpose and relevant settings or color tokens, exposes the agreed customization actions, and exits back to normal interaction; verify an equivalent keyboard-accessible path.
- **Behavior:**

  > Users should be able to identify unfamiliar UI elements without already knowing their feature names or configuration keys. Inspection should explain the selected element and expose the relevant appearance or visibility controls within the agreed initial scope. Inspection interactions must not accidentally activate the underlying UI, and leaving the mode must restore normal interaction. Acceptance should cover both newcomer-oriented feature discovery and theme-color discovery, with accessible operation rather than a mouse-only experience.
- **Trace:**

  > InspectContextKeysAction in src/vs/workbench/browser/actions/developerActions.ts already implements temporary DOM targeting and click interception, but its result is console output of context values. InspectEditorTokensController and editor.action.inspectTMScopes in src/vs/workbench/contrib/codeEditor/browser/inspectEditorTokens/inspectEditorTokens.ts provide editor-specific token inspection rather than workbench-wide explanations. Existing appearance controls include editor.minimap.enabled, editor.bracketPairColorization.enabled, and workbench.colorCustomizations; the missing capability is discovering their relationship to the pointed-at element. The trace does not establish a shared element-to-feature, setting, and color metadata contract, so this is design work rather than a bounded inspector patch. Preserve normal editor and workbench interactions outside inspection mode, and retain the thread's initial boundary that extension extensibility is a later step. Coordinate with the narrower color-inspection request at https://github.com/microsoft/vscode/issues/62637.
- **Open decisions:**
  - Which elements and explanations must the initial experience support: editor features, workbench controls, or both?
  - Should the initial mode only explain elements and link to existing settings, or also let users directly change visibility and theme colors?
  - Should newcomers and theme developers use one progressively detailed inspection surface or separate presentations, as raised in the discussion?
  - Should this initially complement the existing token inspector and context menus, or replace any of those user-facing entry points?
