# Issue #181794 — Vscode Sets breakpoint in both sessions in multicore debugging with single Debug Configuration 

[https://github.com/microsoft/vscode/issues/181794](https://github.com/microsoft/vscode/issues/181794)

## Summary

This remains a valid debug feature request: VS Code intentionally broadcasts breakpoints to every debug session, but multicore disassembly sessions need a way to scope address-based breakpoints. Maintainers confirmed both the gap and that fixing it requires a larger session/config-specific breakpoint design.

## Change summary

Allow a breakpoint created during multicore debugging to apply only to the user-selected debug session instead of every active session.

## Best solution

Design session- or debug-configuration-specific breakpoint ownership across the debug model and DAP-facing breakpoint dispatch, while preserving the current shared-breakpoint behavior for ordinary source debugging.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/common/debugModel.ts`, `src/vs/workbench/contrib/debug/common/debug.ts`, `src/vs/workbench/contrib/debug/browser/debugService.ts`
- **Validation:** Add debug-service/model tests with two active sessions showing that a session-scoped instruction breakpoint is sent only to its owning session, while an ordinary unscoped source breakpoint continues to be sent to both.
- **Behavior:**

  > In a multicore debug scenario, users can associate an instruction/address breakpoint with one debug session or configuration so that it is not installed in unrelated sessions where the same address may identify different code. Existing source breakpoints remain shared across sessions unless explicitly scoped. Acceptance must cover two simultaneous sessions with overlapping instruction addresses and verify both scoped and legacy shared behavior.
- **Trace:**

  > VS Code's current breakpoint model treats breakpoints as workspace-level objects and the debug service sends them to active sessions; the issue discussion confirms that this is intentional current behavior. For disassembly debugging, identical numeric addresses can represent different instructions in different cores, so broadcasting can stop in an unexpected session. The uncertainty begins at the public behavior and protocol boundary: session-only versus configuration-wide ownership, how users select that ownership, and whether scope persists across reloads. Related protocol discussion exists at https://github.com/microsoft/debug-adapter-protocol/issues/445, while the newer extension report https://github.com/Open-CMSIS-Pack/vscode-cmsis-debugger/issues/487 supplies current ecosystem evidence but cannot supersede this issue. Preserve default shared source-breakpoint semantics and avoid making the solution specific to one debug adapter.
- **Open decisions:**
  - Should breakpoint scope target one live debug session or a debug configuration whose future sessions inherit it?
  - How should users choose and see breakpoint scope in the breakpoint UI and editor/disassembly actions?
  - Should session/configuration scope persist across reloads, and if so at workspace or user scope?
  - Does the design require a DAP capability or additional breakpoint metadata, and what is the fallback for adapters that do not support it?
