## Summary

Keep this accepted, team-authored request open: current source does not provide built-in EditorConfig enforcement, and existing settings and extension support do not cover the full ask. ## Change summary

Provide first-party, out-of-the-box support for repository .editorconfig rules, including indentation and save-time whitespace behavior.

## Best solution

Deliver first-party EditorConfig support that consistently applies repository rules when opening and saving files. Establish the supported property contract and precedence against VS Code settings and formatters before implementation, accounting for the save-configuration concerns tracked separately.

- **Likely files:** `src/vs/editor/common/services/modelService.ts`, `src/vs/workbench/contrib/codeEditor/browser/saveParticipants.ts`, `src/vs/workbench/contrib/codeEditor/test/browser/saveParticipant.test.ts`

Include the README.md case from editorconfig/editorconfig-vscode issue 153 and verify unrelated files retain existing behavior. Add automated save-behavior coverage alongside the Save Participants suite in src/vs/workbench/contrib/codeEditor/test/browser/saveParticipant.test.ts; no execution was performed in this read-only review.
- **Behavior:**

  > A repository's .editorconfig rules should be honored out of the box without installing the community extension or manually duplicating its rules in workspace settings. Matching files should receive the agreed indentation, encoding, line-ending, and save-time whitespace behavior, including nested configuration and glob-specific overrides. Acceptance must include preserving Markdown trailing spaces when the effective EditorConfig rule disables trimming, according to the agreed precedence contract. Files without applicable EditorConfig rules should retain existing editing and saving behavior.
- **Trace:**

  > ModelService.getCreationOptions in src/vs/editor/common/services/modelService.ts reads language/resource-scoped VS Code configuration for model options. TrimWhitespaceParticipant, FinalNewLineParticipant, and TrimFinalNewLinesParticipant in src/vs/workbench/contrib/codeEditor/browser/saveParticipants.ts likewise consult IConfigurationService for save transformations; no EditorConfig resolution was identified on these paths. extensions/ini/package.json recognizes .editorconfig as a properties-language file but does not enforce its contents. https://github.com/editorconfig/editorconfig-vscode/issues/153 documents the trailing-space conflict, while https://github.com/microsoft/vscode/issues/65663 owns the related but narrower save-override request. Existing save-participant tests are in src/vs/workbench/contrib/codeEditor/test/browser/saveParticipant.test.ts. The trace identifies integration surfaces, not a complete design: configuration precedence, supported properties, and first-party delivery remain unsettled. Preserve non-EditorConfig behavior and do not assume that one formatter may suppress another.
- **Open decisions:**
  - Should out-of-the-box support be an always-available core capability or a bundled first-party extension that users can disable independently?
  - When an applicable EditorConfig rule conflicts with user, workspace, or language-specific VS Code settings, which source wins, and how should explicitly configured formatters interact with that rule?
  - Does the initial support contract cover all standard EditorConfig properties only, or also selected nonstandard or language-specific properties implied by the request to respect all settings?
