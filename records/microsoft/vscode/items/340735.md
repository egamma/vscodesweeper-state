# Issue #340735 — Prompt name matching degraded (regression)

[https://github.com/microsoft/vscode/issues/340735](https://github.com/microsoft/vscode/issues/340735)

## Summary

Thanks for the detailed report. Traced in current source: prompt slash-command completions build a multi-token `filterText`, and the suggest widget fuzzy-matches the typed text against that whole string. That lets `/document-` match `library-documentation`, and the commands are forced into registration order.

## Change summary

Typing `/document-` in chat lists prompts that don't start with or contain the typed text, in a poor order, instead of the prefix match first.

## Best solution

Make prompt slash-command filtering prefix/word-aware so the typed text can't fuzzy-match across the concatenated `filterText` variants. Rank exact prefix matches first, and decide whether the word-suffix matching intended by `getPromptSlashCommandFilterText` should be kept.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletionUtils.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts`
- **Validation:** A unit test with prompts `document-revise` and `library-documentation` asserting that `/document-` yields only `document-revise` and that `/g` yields prefix matches first.
- **Behavior:**

  > Typing `/document-` shows only prompts whose name matches the typed text, listed first when it is a prefix match. Typing `/g` shows prompts starting with `g` ahead of or instead of mere subsequence matches. Acceptance: with `document-revise` and `library-documentation` defined, `/document-` offers only `document-revise`.
- **Trace:**

  > The prompt slash-command provider in chatInputCompletions.ts (~L225-L285) sets `filterText: getPromptSlashCommandFilterText(c.name)`. That function in chatInputCompletionUtils.ts concatenates word-suffix variants with the full name in one string, which the editor suggest model fuzzy-scores as a whole. `sortText` is index-based. Do not change other completion providers (agents, variables, attachments). Where the uncertainty starts: the word-suffix variants were probably added on purpose so `/revise` finds `document-revise`.
- **Open decisions:**
  - Should typing a later word of a hyphenated name (for example `/revise`) still match `document-revise`, or should matching be prefix-only?
  - Should exact prefix matches always sort before other matches, and should non-prefix matches still be shown at all?

## Evidence

- **filterText construction:** `getPromptSlashCommandFilterText` in src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletionUtils.ts joins `/<suffix after each dash>`, `/<name>` and the display command with spaces. For `library-documentation` this gives `/documentation /library-documentation`.
- **why the mismatch:** The suggest widget fuzzy-scores the typed `/document-` against that whole string. `/document` matches `/documentation` and `-` matches the dash in `/library-`, so the item is shown. The same mechanism explains the `/g` and `/ge` reports, where subsequence matching spans the concatenated text.
- **ordering:** In chatInputCompletions.ts (~L282) `sortText` is `'a'.repeat(i + 1)`, so the order follows the command list index and exact prefix matches are not preferred.
- **report:** A second commenter confirms that single-letter and two-letter prefixes now match anywhere in a name. The history in the checkout is shallow, so I could not identify the introducing commit.
