# Issue #336727 — Feature Request: expose an `explorerResourceIsSymbolicLink` context key for when clauses

[https://github.com/microsoft/vscode/issues/336727](https://github.com/microsoft/vscode/issues/336727)

## Summary

A real extension-enablement gap remains on current main, and the issue is only 13 days into the Backlog Candidates community process with 8 upvotes. Keep it open as under discussion rather than overriding that process or the holding-bin milestone with a decline close.

## Change summary

Expose the focused or context-menu-targeted Explorer item's symbolic-link status as a when-clause context key for extension menu and keybinding contributions.

## Best solution

Define a stable public context-key contract for symbolic-link status and have the Explorer update it through the same focus and context-menu path used by its folder, readonly, and root keys. A maintainer should first decide whether that contract is Explorer-specific or belongs in the generic resource-context surface.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/common/files.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`
- **Validation:** In an Extension Development Host, contribute an explorer/context command guarded by the chosen symbolic-link context key; verify it appears for a symlink and not a regular file or folder when focused, right-clicked directly, and used through keyboard context-menu invocation.
- **Behavior:**

  > Extensions can condition Explorer menu items and keybindings on whether the active Explorer resource is a symbolic link. The context evaluates true for a symlink and false or unset for ordinary files, folders, and empty Explorer space. It follows the same focus and context-menu-target semantics as neighboring Explorer resource keys, including compact folders, multi-root workspaces, and remote file-system providers.
- **Trace:**

  > ExplorerItem.isSymbolicLink is populated in src/vs/workbench/contrib/files/common/explorerModel.ts and already drives core behavior in fileActions.ts. ExplorerView.setContextKeys in src/vs/workbench/contrib/files/browser/views/explorerView.ts publishes the current resource's folder, readonly, parent-readonly, root, and available-editor states; both focus changes and onContextMenu flow through it. The public RawContextKey declarations are in src/vs/workbench/contrib/files/common/files.ts, where no symlink key exists. The boundary is context publication: do not add a built-in reveal/copy command or change symlink resolution behavior. The older exact request https://github.com/microsoft/vscode/issues/167996 is closed and cannot absorb this issue.
- **Open decisions:**
  - Should the public contract be the Explorer-specific `explorerResourceIsSymbolicLink` key proposed here, or a generic resource-context key that can consistently represent symbolic-link status outside the Explorer as well?
