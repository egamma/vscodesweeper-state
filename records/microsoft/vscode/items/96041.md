# Issue #96041 — unable to input chinese character

[https://github.com/microsoft/vscode/issues/96041](https://github.com/microsoft/vscode/issues/96041)

## Summary

Keep open: multiple independent reports confirm that Chinese and Japanese input fails in the Snap distribution while the .deb installation works, including reports against 1.106.1. The current Snap launcher still has packaging-specific IME handling worth investigating; no verified fix or eligible older canonical was found.

## Change summary

Restore Chinese and other CJK input through host input methods in the Linux Snap distribution.

## Best solution

Make host IME composition work in the supported Snap distribution without requiring users to switch packages. Diagnose the launcher’s GTK input-module setup and display-backend selection before deciding whether the remaining fix belongs in VS Code packaging or an upstream component.

## Plan brief

- **Likely files:** `resources/linux/snap/electron-launch`, `resources/linux/snap/snapcraft.yaml`, `build/gulpfile.vscode.linux.ts`
- **Validation:** On Ubuntu with a working host IBus Chinese engine, install the current Snap, open a text editor, switch to Chinese input, and compose and commit characters; compare the same environment with the .deb package. Repeat with Fcitx and on X11 and Wayland, recording process arguments and input-module cache contents. The eventual fix must make the failing Snap scenario pass without regressing working input or launch behavior.
- **Behavior:**

  > Users of the Linux Snap distribution must be able to compose and commit Chinese and other CJK characters using a working host input method. Multiple reporters can use the same input method in the .deb installation but not in Snap. Acceptance requires reproducing a specific failing Snap configuration and demonstrating that composition works there afterward without requiring a package switch. Preserve working keyboard input and application startup in the other tested display-backend configurations.
- **Trace:**

  > prepareSnapPackage in build/gulpfile.vscode.linux.ts packages resources/linux/snap/snapcraft.yaml and resources/linux/snap/electron-launch; both Snap entry points invoke this launcher. The launcher changes GTK module discovery, generates an input-module cache on revision changes, and unconditionally appends --ozone-platform=x11. The newer report https://github.com/microsoft/vscode/issues/312549 attributes its Wayland/Copilot Chat failure to that final argument and reports success bypassing the wrapper, but this does not establish the cause of the older IBus and Fcitx reports. The desktop-legacy suggestion at https://github.com/microsoft/vscode/issues/96041#issuecomment-1253384037 is also unverified, and the package uses classic confinement. First establish the failing environment and whether module discovery, display-backend selection, or upstream toolkit behavior explains it. Keep unrelated Chrome OS input and candidate-popup positioning issues outside this diagnosis.

## Evidence

- **Current IME-sensitive launcher behavior:** resources/linux/snap/electron-launch sets GTK_PATH and GTK_EXE_PREFIX to Snap locations, generates GTK_IM_MODULE_FILE on revision changes, and ends with exec "$@" --ozone-platform=x11. These are concrete investigation points, but reading them does not establish which one causes all historical reports.
