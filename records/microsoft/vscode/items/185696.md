# Issue #185696 — Saving creates "end of file" issues

[https://github.com/microsoft/vscode/issues/185696](https://github.com/microsoft/vscode/issues/185696)

## Summary

The attachments identify automatic carriage-return normalization as the cause, rather than an end-of-file save defect. The verified open canonical issue already owns preserving mixed line endings and embedded carriage returns.

## Change summary

Preserve embedded carriage returns when editing and saving shell scripts so an unrelated comment edit does not break their syntax.

## Best solution

Consolidate this report into https://github.com/microsoft/vscode/issues/127, retaining the paired shell-script attachments as a concrete example of normalization changing executable behavior.

## Evidence

- **Exact attachment comparison:** Read both attachments linked from https://github.com/microsoft/vscode/issues/185696. The broken file is byte-for-byte identical to the working file after adding the reported comment space and replacing its two literal CR bytes with LF. The working file contains 344 LF bytes and two CR bytes; the broken file contains 346 LF bytes and no CR bytes. Both retain their final newline.
- **Shell-specific consequence:** The literal CR bytes occur on original LF-delimited lines 151 and 195, inside commented-out #IFS expressions. Replacing them with LF introduces actual shell line breaks, exposing the remainder of those commented expressions as shell input. This explains why an unrelated comment edit can lead to an unexpected-end-of-file parser error.
- **Current source:** src/vs/editor/common/model/textModel.ts calls builder.finish() when constructing text buffers. In src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeTextBufferBuilder.ts, finish defaults normalizeEOL to true; PieceTreeTextBufferFactory._getEOL selects LF for this predominantly LF sample, and create replaces /\r\n|\r|\n/g with that EOL. The current source therefore accounts for the exact attachment transformation.
- **Verified canonical:** https://github.com/microsoft/vscode/issues/127 is open and requests an option to opt out of automatic line-ending normalization after trivial edits. Its discussion explicitly covers embedded CR bytes whose replacement breaks file behavior, including https://github.com/microsoft/vscode/issues/127#issuecomment-418544059 and shell-script preservation scenarios. It owns the same underlying work at broader scope.
- **Maintainer precedent:** https://github.com/microsoft/vscode/issues/149433 reports literal CR being replaced by LF on save and breaking a shell script. In https://github.com/microsoft/vscode/issues/149433#issuecomment-1126059009, the editor maintainer explains the intentional normalization and directs tracking to the existing normalization issues, including https://github.com/microsoft/vscode/issues/127. This supports consolidation rather than declining this accepted report.
- **Reporter follow-up:** The supplied discussion confirms the behavior persisted after updating from VS Code 1.79.0 to 1.79.2. The attachment comparison provides a concrete diagnosis beyond the initial suggestion to upgrade.
