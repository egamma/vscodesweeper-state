- **Behavior:**

  > Opening a session from Inbox should have predictable presentation and an understandable way back to the prior Inbox context. The selected workflow tab, item, and list position should survive that round trip while the item remains available. Compare the Open Session button with the other session-opening entry point described in the report; intentional differences must be understandable rather than accidental.
- **Trace:**

  > InboxNotificationsView.runAction forwards OpenSession to ISessionsService.openSession; SessionsService._openSession resolves and activates the target through _showSession. Inbox focus hides the Sessions part, and setVisible(false) releases that visibility override. Show Inbox uses sessions.inboxNotifications.show to reopen the window canvas, while WindowCanvasService caches presentations and retains them across working-set restoration; existing tests already cover retained draft state. These mechanisms do not alone prove that the reported round trip works, and the precise second entry point needs examination in the running UI. Preserve provider-neutral session handling, existing canvas retention, and normal session navigation outside Inbox. Coordinate the return-history contract with https://github.com/microsoft/vscode/issues/345524; that issue does not cover the full presentation-consistency request.
- **Open decisions:**
  - Should equivalent session-opening entry points leave Inbox for a full-session view, or retain Inbox beside the session; if both presentations remain, how should their distinction be communicated?
  - Should returning to Inbox participate in standard Back/Forward navigation, use a dedicated return affordance, or support both?
