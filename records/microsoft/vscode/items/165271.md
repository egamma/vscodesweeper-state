# Issue #165271 — 100% CPU with explorer and code moving files to folders

[https://github.com/microsoft/vscode/issues/165271](https://github.com/microsoft/vscode/issues/165271)

## Summary

Keep open: the supplied CPU profile was analyzed by a maintainer and attributed to Explorer model updates, and current main still processes sustained file-event batches on a fixed 500 ms cadence. This issue is the established canonical for bulk Explorer-operation performance rather than a duplicate of the newer, broader reports.

## Change summary

Moving roughly 15,000 files externally while their workspace is open causes Explorer model synchronization to saturate the renderer CPU and substantially slow the operation.

## Best solution

Define a bounded refresh policy for sustained filesystem churn, then coalesce Explorer model reconciliation so bulk external moves do not repeatedly traverse and refresh the visible tree while still presenting changes within an acceptable delay.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/explorerService.ts`, `src/vs/workbench/contrib/files/test/browser/explorerService.test.ts`
- **Validation:** Extend the `Files - ExplorerService` tests with fake timers to stream file-change batches for longer than 500 ms and assert the agreed refresh count and latency, then run `scripts/test.sh --grep "Files - ExplorerService"`; benchmark the issue's 15,000-file move with the Explorer open and confirm renderer CPU and operation duration no longer regress materially versus the Explorer being closed.
- **Behavior:**

  > Bulk external file moves in an open workspace must not cause repeated Explorer reconciliation to saturate the renderer CPU or materially impede the underlying file operation. Explorer contents may update after a bounded delay, but must converge without requiring a manual refresh. Ordinary isolated file changes, edit-mode deferral, and refresh-on-focus behavior must remain responsive and correct.
- **Trace:**

  > The reporter reproduced the problem with extensions disabled and supplied a renderer CPU profile; a maintainer identified Explorer model maintenance as the hot path. In src/vs/workbench/contrib/files/browser/explorerService.ts, `onDidFilesChange` appends every event but schedules work only when no run is pending, producing fixed 500 ms processing windows during sustained churn. The scheduled callback walks visible resolved Explorer items through `doesFileEventAffect`; each item probes the entire queued event array before `refresh(false)` can rebuild the model. Existing focused tests in src/vs/workbench/contrib/files/test/browser/explorerService.test.ts cover deferred file changes only while editing, not sustained event streams. Preserve prompt handling of isolated changes and the existing editing/focus safeguards; the uncertainty begins at the desired Explorer update cadence during continuous bulk changes.
- **Open decisions:**
  - During sustained filesystem churn, should Explorer defer visible updates until a quiet period or refresh periodically with a bounded maximum latency?
  - What maximum refresh delay and bulk-operation performance budget should the regression test enforce?
