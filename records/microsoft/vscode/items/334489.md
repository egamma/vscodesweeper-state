# Issue #334489 — Alt keyup is missed while a webview editor has focus, silently turning a tab's Close button into "Close Other Editors"

[https://github.com/microsoft/vscode/issues/334489](https://github.com/microsoft/vscode/issues/334489)

## Summary

Real, still-reproducing bug on current main: a second reporter independently confirmed the exact repro cross-platform (Linux/Wayland vs. the original Windows report), and the source shows the mechanism is plausible and only partially mitigated.

## Change summary

After Alt+Tabbing away and back while a webview-backed editor (e.g. Markdown preview) has focus, VS Code keeps believing Alt is held, silently turning a tab's × into 'Close Other Editors' until any key is pressed.

## Best solution

Extend the existing partial fix in src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts (the #331979 blur-reset and mouse-altKey revalidation) and/or ModifierKeyEmitter in src/vs/base/browser/dom.ts to also resync on window focus/webview blur, per the reporter's own suggested mitigation, since the current mouse-revalidation clearly isn't catching the webview-focus case.

## Evidence

- **existing partial fix found:** src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts already resets alt-pressed on window blur (hostService.onDidChangeFocus, citing https://github.com/microsoft/vscode/issues/331979) and revalidates from real e.altKey on tab-bar mousemove/mousedown — yet this report and an independent Linux confirmation show the state still gets stuck when a webview has focus.
- **root-cause plausibility:** ModifierKeyEmitter (src/vs/base/browser/dom.ts, registerListeners) only attaches keydown/keyup capture listeners on windows registered via registerWindow — grep shows registerWindow is only called for auxiliary Electron windows (src/vs/workbench/services/auxiliaryWindow/browser/auxiliaryWindowService.ts, src/vs/platform/windows/electron-main/windowsMainService.ts), never for embedded webview iframes, so a keyup delivered inside a webview iframe's own document would not bubble to these listeners.
- **independent confirmation:** Comment by LavX reproduces the identical sequence on Fedora/KDE/Wayland (1.136.1, same commit), and notes the prior fix for https://github.com/microsoft/vscode/issues/332070 (closed against 1.136.0) does not hold in 1.136.1.
- **impact:** Reporter describes an actual data-loss incident (a set of long-running agent-session webview tabs wiped by one click) tied to the affordance added in 1.134 (https://github.com/microsoft/vscode/pull/328975).
- **shallow checkout limitation:** This checkout has only 1 commit of history, so git log/blame could not date when the existing partial mitigation landed or confirm no newer commit exists; could not verify a fix commit for this specific report.
