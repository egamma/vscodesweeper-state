# Issue #334489 — Alt keyup is missed while a webview editor has focus, silently turning a tab's Close button into "Close Other Editors"

[https://github.com/microsoft/vscode/issues/334489](https://github.com/microsoft/vscode/issues/334489)

## Summary

Well-diagnosed, cross-platform-confirmed (Windows + Linux) residual case of the Alt-latch tab-action bug, reported after the known general fixes for this exact class of bug already shipped — worth routing to the workbench-tabs owner for a targeted look at the webview-focus path rather than closing.

## Change summary

When a webview-backed editor (e.g. Markdown preview) has DOM focus during an Alt+Tab out-and-back, the released Alt key's keyup never reaches the main window, so a tab's close button can silently stay swapped to 'Close Other Editors'.

## Best solution

Investigate why the two existing Alt-latch mitigations in src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts (the `hostService.onDidChangeFocus` reset from #331979, and the mousemove/mousedown re-validation over tabsContainer) don't fully cover the case where a webview/iframe holds DOM focus across the Alt+Tab cycle — likely needs either a resync on window focus-gain (not just blur) or forwarding of the webview's key/modifier state back to the host `ModifierKeyEmitter`.

## Evidence

- **existing fix #1 (blur reset):** src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts lines 188-198: `hostService.onDidChangeFocus(hasFocus => { if (!hasFocus) this.setAltPressed(false); ... })`, explicitly citing https://github.com/microsoft/vscode/issues/331979, which was closed as fixed and milestoned 1.136.0.
- **existing fix #2 (mouse re-validation):** Same file, lines ~460-471: a capture-phase MOUSE_MOVE/MOUSE_DOWN listener on the tabs container re-syncs `isAltPressed` from the live mouse event's `e.altKey`, with a comment noting the keyup 'may have been missed while another application had focus'.
- **related closed issue confirms fix shipped:** https://github.com/microsoft/vscode/issues/332070 timeline shows it was labeled 'bug', commented 'Will be fixed in next release' by the area owner, milestoned 1.136.0, and later labeled 'verified' on 2026-08-31 — i.e. before this new report (1.136.1, filed 2026-09-04).
- **independent cross-platform confirmation:** Comment from LavX (Fedora/KDE/Wayland) reproduces the identical scenario on Linux with 1.136.1, ruling out a Windows-only regression and confirming the report is not a one-off.
- **reporter's own scoping:** Issue body explicitly tested and ruled out: normal text-editor focus (no repro), `--disable-extensions` (still webview-only repro), and confirms with the built-in Markdown preview webview — isolating the discriminator to webview/iframe DOM focus specifically.
