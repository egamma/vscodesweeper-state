# Issue #334489 — Alt keyup is missed while a webview editor has focus, silently turning a tab's Close button into "Close Other Editors"

[https://github.com/microsoft/vscode/issues/334489](https://github.com/microsoft/vscode/issues/334489)

## Summary

Well-documented, independently confirmed (Windows + Linux) bug where a missed Alt keyup while a webview iframe holds focus leaves the tab close button stuck in 'Close Others' mode; current main has a partial mitigation for the general Alt-stuck class (referencing #331979) but it likely doesn't cover the exact 'mouse stationary over the tab, focus regained via keyboard' path described here, so keeping this open for further investigation rather than closing.

## Change summary

Alt keyup is lost while a webview-backed editor has focus during Alt+Tab, silently latching the tab close button into destructive 'Close Other Editors' mode.

## Best solution

In src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts / src/vs/base/browser/dom.ts ModifierKeyEmitter, add an explicit re-sync of modifier state when the window regains OS focus (not just clear-on-blur + mousemove revalidation), so a stationary cursor over an already-hovered tab doesn't retain stale alt state; also consider the community's suggestion of gating the Alt-click 'Close Others' affordance behind an opt-in setting given the data-loss blast radius.

- **Proposed comment:**

  > Thanks for the very thorough report and reproduction (and to @LavX for confirming on Linux). Current `main` already has a partial mitigation for the general 'Alt stuck after losing window focus' class (in `multiEditorTabsControl.ts`, tied to https://github.com/microsoft/vscode/issues/331979) — it clears the alt-pressed state on window blur and re-validates on mouse move/down. However, that re-validation depends on a fresh mousemove event, which wouldn't fire if the cursor is already resting over the tab when focus returns — matching the exact repro described here. This looks like a remaining gap rather than a brand-new issue, and given the real data-loss risk from an accidental 'Close Others' click, it's worth someone with a live build tracing whether the focus-regain path still leaves stale alt state in the webview-focused case.

## Evidence

- **existing partial mitigation:** src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts lines ~187-200 and ~464-472 (current main) clear alt-pressed state on hostService.onDidChangeFocus(false) and re-validate via mousemove/mousedown e.altKey, explicitly citing https://github.com/microsoft/vscode/issues/331979 — but this relies on a fresh mousemove event, which a stationary cursor (as described in this report's repro) would not generate.
- **ModifierKeyEmitter blur-only reset:** src/vs/base/browser/dom.ts ModifierKeyEmitter.registerListeners only resets key status on window 'blur' (line ~1990); there is no explicit resync on window 'focus', consistent with the reporter's traced mechanism.
