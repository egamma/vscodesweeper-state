# Issue #138237 — Disassembly editor is not getting closed automatically after debug session ended

[https://github.com/microsoft/vscode/issues/138237](https://github.com/microsoft/vscode/issues/138237)

## Summary

This remains a valid, promoted Backlog feature request with 20 community upvotes. Current main leaves the singleton disassembly editor open after debugging, while the existing read-only-tab cleanup does not include it.

## Change summary

Automatically close the disassembly editor when its debug session ends, potentially under a user preference.

## Best solution

Define lifecycle semantics for the singleton disassembly editor, including concurrent sessions, and provide an opt-in or clearly chosen default for closing it when no relevant debug session remains.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/disassemblyView.ts`, `src/vs/workbench/contrib/debug/browser/debugService.ts`, `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`, `src/vs/workbench/contrib/debug/common/debug.ts`, `src/vs/workbench/contrib/debug/common/disassemblyViewInput.ts`
- **Validation:** Add a focused debug lifecycle test covering the chosen close policy, including one ended session and multiple concurrent sessions; manually verify the disassembly tab follows the selected preference after terminating the final relevant session.
- **Behavior:**

  > The disassembly editor follows an explicitly defined lifecycle when debugging ends. Under the selected close policy, ending the relevant or final debug session closes the disassembly tab; under the preserve policy, it remains open. Concurrent debug sessions must not cause the editor to disappear while it can still display an active session.
- **Trace:**

  > DisassemblyViewInput in src/vs/workbench/contrib/debug/common/disassemblyViewInput.ts is a resource-less singleton opened by the debug editor action and stack-frame navigation. DisassemblyView in src/vs/workbench/contrib/debug/browser/disassemblyView.ts observes debug state changes but only clears content when a new debugging period starts. DebugService in src/vs/workbench/contrib/debug/browser/debugService.ts already closes session-associated DEBUG_SCHEME editors for debug.closeReadonlyTabsOnEnd, but its resource/session filter excludes the disassembly input. The boundary is the disassembly editor lifecycle: source editors and existing read-only debug-tab behavior must remain unchanged. The older milestone https://github.com/microsoft/vscode/issues/129762 is related background, not a canonical report of this behavior.
- **Open decisions:**
  - Should closing the disassembly editor be unconditional, controlled by debug.closeReadonlyTabsOnEnd, or controlled by a dedicated preference, and what should its default be?
  - With concurrent debug sessions, should the singleton disassembly editor close only after the final session ends, or should it track and close with a particular focused or owning session?

## Evidence

- **current source:** src/vs/workbench/contrib/debug/browser/disassemblyView.ts listens to IDebugService.onDidChangeState, but only clears its table when debugging starts; it does not close the editor when the state becomes inactive.
- **editor lifecycle:** src/vs/workbench/contrib/debug/common/disassemblyViewInput.ts defines one singleton DisassemblyViewInput with no resource or debug-session association, so concurrent-session ownership is not currently represented.
- **existing setting gap:** src/vs/workbench/contrib/debug/browser/debugService.ts implements debug.closeReadonlyTabsOnEnd by closing editors whose resources use the debug scheme and encode the ending session ID. DisassemblyViewInput.resource is undefined, so that setting does not cover this editor.
- **community demand:** The request reached 20 upvotes and was promoted to the Backlog by the established feature-request process.
- **related milestone:** https://github.com/microsoft/vscode/issues/129762 is older and open, but its checklist does not include closing the disassembly editor after session termination and it does not report the same observable symptom required for a duplicate close on this re-reviewed issue.
