# Issue #159357 — Notebook API:  Interactive Renderers + Delay Loading

[https://github.com/microsoft/vscode/issues/159357](https://github.com/microsoft/vscode/issues/159357)

## Summary

Current main already warms notebook outputs across the document in the background, so rendering is no longer exclusively triggered by scrolling. However, that does not provide the immediate, extension-controlled rendering contract requested and acknowledged in the discussion; keep this open for an API decision.

## Change summary

Allow interactive notebook renderers or controllers to request eager output rendering when outputs depend on other outputs being initialized.

## Best solution

Define whether notebook extensions need an opt-in eager-rendering contract beyond the existing background warmup, including its completion and lifecycle guarantees. Preserve lazy/background rendering for ordinary notebooks and avoid making large notebooks render synchronously by default.

- **Validation:** Use a large notebook fixture with custom interactive outputs that exchange initialization messages through a controller, including outputs far outside the initial viewport. Record render callbacks without scrolling, then verify the chosen opt-in initialization/completion contract and unchanged default scheduling; also exercise collapsed outputs and renderer disposal.
- **Behavior:**

  > Interactive outputs can depend on other outputs being initialized, but extensions currently cannot declare the eager-rendering behavior requested here. Current background warmup may initialize offscreen outputs eventually, without supplying the requested immediate-rendering contract. Acceptance should demonstrate controller-mediated communication with offscreen outputs without scrolling under the chosen contract, while ordinary notebooks retain their existing performance-oriented scheduling.
- **Trace:**

  > NotebookViewportContribution in src/vs/workbench/contrib/notebook/browser/contrib/viewportWarmup/viewportWarmup.ts already schedules document-wide output warmup after model attachment, in addition to viewport warmup. _warmupCodeCell observes collapse, trust, and output-count constraints and passes createWhenIdle=true to NotebookEditorWidget.createOutput. That path reaches BackLayerWebView.requestCreateOutputWhenWebviewIdle and the webview html handler's outputRunner.enqueueIdle, so the historical scroll-only description does not fully describe current main. The renderer contribution schema has no scheduling declaration, and controller preload/messaging APIs do not guarantee output initialization. The uncertainty is the public contract needed beyond existing warmup, not the location of an implementation guard. Preserve trust protections and default performance behavior; the agreed request is recorded at https://github.com/microsoft/vscode/issues/159357.
- **Open decisions:**
  - Should eager initialization be declared per renderer or per notebook controller, and which outputs does that declaration cover?
  - Does the contract guarantee eventual offscreen initialization, expose an awaitable all-output completion point, or guarantee rendering order for dependent outputs?
  - Should an eager request include collapsed outputs and outputs beyond the existing display limit, or retain those exclusions?

- **background is not immediate:** src/vs/workbench/contrib/notebook/browser/notebookEditorWidget.ts: createOutput routes createWhenIdle requests to BackLayerWebView.requestCreateOutputWhenWebviewIdle. In src/vs/workbench/contrib/notebook/browser/view/renderers/webviewPreloads.ts, the html message handler uses outputRunner.enqueueIdle for these requests. This is background scheduling, not a documented guarantee that dependent outputs are initialized immediately or in dependency order.
