# Issue #145018 — Allow setting font weights or semibold/thin/heavy... in fontStyle in tokenColors

[https://github.com/microsoft/vscode/issues/145018](https://github.com/microsoft/vscode/issues/145018)

## Summary

Keep this accepted Backlog request open: current token theming still cannot express granular font weights, and the request has 37 upvotes. Existing editor-wide weight settings do not cover per-token styling, and no verified canonical satisfies the stronger duplicate bar for this re-reviewed item.

## Change summary

Allow token-color rules to select font weights such as light, semibold, and heavy instead of only toggling bold.

## Best solution

Design a supported per-token weight contract across theme resolution and editor rendering, retaining compatibility with existing bold styles and tokenization performance. Decide the public syntax and inheritance semantics with the theme/tokenization owners before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/services/themes/common/colorThemeSchema.ts`, `src/vs/workbench/services/themes/common/workbenchThemeService.ts`, `src/vs/workbench/services/themes/common/colorThemeData.ts`, `src/vs/platform/theme/common/tokenClassificationRegistry.ts`, `src/vs/editor/common/encodedTokenAttributes.ts`, `src/vs/editor/common/languages/supports/tokenization.ts`
- **Validation:** After agreeing on the contract, add theme-resolution checks in src/vs/workbench/services/themes/test/node/tokenStyleResolving.test.ts and tokenization checks in src/vs/editor/test/common/modes/supports/tokenization.test.ts. Verify in an editor using a multi-weight font that two token scopes can render distinct non-bold weights while existing bold/italic themes and unstyled tokens retain their behavior.
- **Behavior:**

  > Theme authors and users should be able to assign different non-binary font weights to token scopes, including lighter comments and semibold keywords. The editor-wide font weight must remain the default for tokens without an explicit override. Existing bold, italic, underline, and strikethrough rules must remain compatible. Acceptance should demonstrate two scopes using distinct weights in a multi-weight font and verify inheritance under the agreed public contract.
- **Trace:**

  > The token-settings schema in src/vs/workbench/services/themes/common/colorThemeSchema.ts permits four fontStyle keywords but no fontWeight; existing fontFamily, fontSize, and lineHeight token settings do not supply weight control. ColorThemeData in src/vs/workbench/services/themes/common/colorThemeData.ts copies those font attributes into token rules and maintains a TokenFontIndex, providing relevant existing infrastructure to investigate. TokenStyle in src/vs/platform/theme/common/tokenClassificationRegistry.ts carries boolean bold, while TokenMetadata in src/vs/editor/common/encodedTokenAttributes.ts packs four style flags and emits binary bold styling. The remaining uncertainty is how granular weights propagate through all tokenization and rendering consumers without changing existing contracts or degrading performance; those consumers have not been exhaustively traced. Preserve legacy theme behavior and avoid expanding this into unrelated font-family or size work. The discussion at https://github.com/microsoft/vscode/issues/145018 suggests a separate attribute, and https://github.com/microsoft/vscode/issues/28457 records historical metadata constraints; neither settles the new contract.
- **Open decisions:**
  - Should token weights be expressed through a separate numeric fontWeight attribute, named fontStyle weights, or both, and which values are supported?
  - When an explicit token weight coexists with fontStyle bold or an inherited weight, which value wins, and how does a rule reset to the editor-wide default?

- **Current theme-schema gap:** src/vs/workbench/services/themes/common/colorThemeSchema.ts:149-190 restricts fontStyle to italic, bold, underline, and strikethrough.
