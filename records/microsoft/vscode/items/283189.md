# Issue #283189 — Feature Request: Exclude Specific Files or Folders from Copilot Chat Context + Persistent Context Attachment

[https://github.com/microsoft/vscode/issues/283189](https://github.com/microsoft/vscode/issues/283189)

## Summary

The exclusion half is now supported on current main through `.copilotignore`, but arbitrary files still cannot be pinned as persistent chat context. Because the focused open trackers are younger than this re-reviewed issue, they cannot serve as duplicate canonicals; route this older report to the chat area and keep it open for consolidation.

## Change summary

Allow workspace paths to be excluded from Copilot context independently of `.gitignore`, and allow selected files to remain attached across chat turns.

## Best solution

Retain `.copilotignore` as the exclusion mechanism and add an explicit pinned state for user-attached files, with a clearly chosen persistence scope and without bypassing content-exclusion enforcement. A maintainer should consolidate the remaining attachment work with https://github.com/microsoft/vscode/issues/283137 while preserving this older issue's priority in that decision.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentModel.ts`, `src/vs/workbench/contrib/chat/common/model/chatModel.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/input/chatInputStatePersistence.test.ts`
- **Validation:** Add chat input/model tests proving that a pinned file remains attached across consecutive requests and the selected persistence boundary, while ordinary attachments retain their current behavior and ignored files cannot be pinned or read.
- **Behavior:**

  > Users can explicitly pin a file so it remains guaranteed context for subsequent chat turns within the persistence scope selected by the maintainer, with a visible pinned state and an explicit way to unpin it. Ordinary attachments continue using their current one-turn or suggested-context behavior. Reload and context-compaction behavior must match the selected scope. Files excluded by `.copilotignore` remain unavailable regardless of pin state.
- **Trace:**

  > `BaseIgnoreService` in `extensions/copilot/src/platform/ignore/node/ignoreServiceImpl.ts` already discovers `.copilotignore`, and file-tool paths enforce it through `IIgnoreService`, so exclusion is not the remaining implementation gap. `ChatAttachmentModel` in `src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentModel.ts` stores attachments without an arbitrary-file pinned property, and `clear(false)` preserves only prompt-file entries. `ChatModelInputState.toJSON` and `chatInputStatePersistence.ts` preserve draft attachments but provide no contract for automatically including one on later turns. The focused attachment discussion is https://github.com/microsoft/vscode/issues/283137, which is younger than this issue and therefore cannot be its re-review canonical. Keep ordinary attachment semantics, immutable conversation history, and `.copilotignore` enforcement out of scope for behavioral changes.
- **Open decisions:**
  - Should a pinned attachment persist only within the current conversation, across all chats in the workspace, or across the user profile?
  - After chat compaction or window reload, must the current file contents be re-read and guaranteed in each request, or is retaining the earlier conversation content sufficient?

## Evidence

- **exclusion capability on main:** `extensions/copilot/src/platform/ignore/node/ignoreServiceImpl.ts` defines `COPILOT_IGNORE_FILE_NAME = '.copilotignore'`; `BaseIgnoreService` discovers those files and applies their patterns through `isCopilotIgnored`. File-tool enforcement calls that service from `extensions/copilot/src/extension/tools/node/toolUtils.ts`, so the first requested outcome now has a built-in mechanism independent of `.gitignore`.
