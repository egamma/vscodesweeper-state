# Issue #345323 — Agent Host: provide a portable way for extension-contributed agent hooks to locate extension resources

[https://github.com/microsoft/vscode/issues/345323](https://github.com/microsoft/vscode/issues/345323)

## Summary

Keep open: existing plugin-root interpolation does not establish a portable resource-location contract for extension-contributed agent hooks. The additional plugin report identifies a related Agent Host forwarding gap, not evidence that the original request is completed.

## Change summary

Provide a supported way for extension-contributed agent hooks to locate bundled scripts across installation locations and local or remote hosts.

## Best solution

Define and document a host-resolvable resource-root contract for contributed agents, including availability of bundled resources on remote hosts. Preserve plugin-root compatibility for agent-scoped hooks without depending on extension-host process environment mutations.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotPluginConverters.ts`, `src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts`, `src/vs/platform/agentHost/node/agentPluginManager.ts`, `src/vs/platform/agentHost/test/node/copilotPluginConverters.test.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/hookSchema.ts`
- **Validation:** End with converter tests for owning-root substitution/environment and a manual contributed-agent check: install in a path containing spaces, trigger PreToolUse using a bundled script without hardcoded paths or activation-time environment injection, and repeat against a remote Agent Host. The script must execute from the correct contributed bundle without denying the tool because its path is unresolved.
- **Behavior:**

  > Extension authors can ship an agent and its hook scripts together without asking users to copy scripts or hardcode installation paths. A documented mechanism resolves those scripts on the executing local or remote host. Plugin-agent hooks retain the portable PLUGIN_ROOT behavior described in the discussion. Acceptance includes installation paths containing spaces and a remote host where the client's installation directory is unavailable.
- **Trace:**

  > The original activation-time process.env example crosses a process boundary and does not establish a supported shared environment. The Local parsing path in promptsServiceImpl.ts passes plugin provenance to parseSubagentHooksFromYaml, and hookSchema.ts applies interpolateHookCommandPluginRoot. Agent Host instead projects plugin agents in getCopilotCustomAgents, reads their frontmatter in toSdkCustomAgents, and forwards getCustomAgentHooks results without comparable owning-root context. AgentPluginManager copies contributed bundles to host-side storage, so resource availability must be established as well as path substitution. The unresolved boundary is the public contract for extension resources and what is bundled remotely; plugin compatibility is only part of the request. Preserve hook scope, existing trust gates, and denial behavior when hooks genuinely fail; do not propagate arbitrary extension-host environment variables. Related migration context is https://github.com/microsoft/vscode/issues/332083, not a duplicate canonical.
- **Open decisions:**
  - What supported root or resource-reference contract should extension-contributed agent hooks expose, and should it share the existing plugin-root semantics?
  - Which bundled extension resources should be made available on a remote execution host, and what should authors observe when required resources cannot be transferred?
