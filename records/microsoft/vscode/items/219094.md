# Issue #219094 — Extension Profiling Path PII-Masking Hides Relevant Information

[https://github.com/microsoft/vscode/issues/219094](https://github.com/microsoft/vscode/issues/219094)

## Summary

The profiling export intentionally removes absolute paths, but the resulting `piiRemoved/extension.js` entries also erase extension identity and materially reduce the profile's diagnostic value. This team-authored feature request remains necessary and should stay open for a privacy-preserving design.

## Change summary

Preserve enough extension identity in exported extension-host profiles to distinguish scripts, or provide a hidden option to disable path masking.

## Best solution

Keep user-specific path segments masked while replacing extension-root paths with a stable, non-PII extension identifier, so Chrome profiles distinguish scripts without exposing local filesystem data.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/extensions/electron-sandbox/runtimeExtensionsEditor.ts`, `src/vs/platform/profiling/common/profiling.ts`
- **Validation:** Export an extension-host CPU profile containing at least two extensions whose entry files share the same basename, load it in Chrome DevTools, and verify the entries remain distinguishable while user-specific absolute path segments are absent.
- **Behavior:**

  > An exported extension-host CPU profile must distinguish scripts belonging to different extensions even when their entry files have the same basename, such as `extension.js`. By default, user-specific absolute path information must remain absent. Acceptance requires loading a profile with two same-named extension entry files in Chrome DevTools and identifying each extension without exposing the user's filesystem path.
- **Trace:**

  > The reported save flow reaches runtimeExtensionsEditor.ts, which invokes the profiling path sanitization implemented in src/vs/platform/profiling/common/profiling.ts. The current basename-oriented masking causes scripts from different extension roots to collapse to entries such as `piiRemoved/extension.js`; two commenters independently confirm the diagnostic loss, and one demonstrates that bypassing the sanitization branch restores useful paths. The boundary is profile export privacy: do not expose user names, home directories, workspace paths, or arbitrary absolute paths. The uncertainty starts at the user-visible privacy contract—whether extension identity is always retained safely or raw paths may be enabled through an explicit setting.
- **Open decisions:**
  - Should exported profiles always replace an installed extension root with a stable extension identifier while continuing to mask all other path segments?
  - Should there also be an explicit opt-out that permits raw paths, and if so what scope and warning should that privacy-sensitive setting have?
