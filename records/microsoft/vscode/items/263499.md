# Issue #263499 — Split individual chat response parts to list rows

[https://github.com/microsoft/vscode/issues/263499](https://github.com/microsoft/vscode/issues/263499)

## Summary

The performance gap remains on current main: each response is still one virtualized tree row whose renderer materializes all response parts, so a long tool-heavy response can synchronously create substantial off-screen content. This issue should remain open as the focused work item for virtualizing individual response parts.

## Change summary

Render individual parts of a long chat response as virtualized rows instead of rendering the entire response in one row.

## Best solution

Virtualize response parts within the chat transcript while preserving each request/response as a coherent logical turn, including stable focus, keyboard navigation, accessibility, sticky scroll, and incremental updates.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatListWidget.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts`, `src/vs/workbench/contrib/chat/browser/chat.ts`, `src/vs/workbench/contrib/chat/browser/accessibility/chatAccessibilityProvider.ts`
- **Validation:** Add chat widget/renderer tests proving that a long response exposes only viewport-needed part rows while preserving incremental updates and response-level focus semantics; then profile opening the supplied long-session scenario and verify that off-screen code-block editors are not created during initial render.
- **Behavior:**

  > Opening a long coding-agent session must not synchronously render every part of a large response or create editors for off-screen code blocks. Scrolling must render additional response parts on demand without changing their order, content, or incremental-update behavior. A request and its response must remain understandable as one logical turn, with predictable keyboard and screen-reader navigation.
- **Trace:**

  > ChatListWidget in src/vs/workbench/contrib/chat/browser/widget/chatListWidget.ts virtualizes ChatTreeItem rows, but createRequestTreeItems only models request-to-response hierarchy. ChatListItemRenderer.renderChatResponseBasic in src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts expands the complete IChatResponseViewModel.response.value into content parts and renders that collection inside one response row, which defeats row virtualization for a long individual response. The reporter's trace and maintainer discussion at https://github.com/microsoft/vscode/issues/263499 confirm this architecture as the remaining bottleneck. The boundary is the transcript presentation layer: response ordering, streaming updates, code-block identity, sticky-scroll behavior, actions, and response-model persistence must not change. The broader https://github.com/microsoft/vscode/issues/263896 and https://github.com/microsoft/vscode/issues/290490 trackers still identify this focused work as outstanding.
- **Open decisions:**
  - Should Up/Down navigation and accessibility focus traverse every response-part row, or should the virtualized rows remain one logical response stop with internal navigation?
  - Which response-level UI elements and actions remain attached to the logical response container when its content parts are separate virtualized rows?

## Evidence

- **rendering path:** src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts renderChatResponseBasic reads the complete element.response.value array, converts it with annotateSpecialMarkdownContent, and passes the resulting content collection to renderChatContentDiff within the single response row.
