# Issue #278443 — linux mint issue

[https://github.com/microsoft/vscode/issues/278443](https://github.com/microsoft/vscode/issues/278443)

## Summary

Still reproduces on main: the GNOME/KDE wording and lack of a permanent suppression option both trace directly to NativeSecretStorageService.notifyOfNoEncryption, and this exact complaint has recurred across many closed issues on other distros for years without a fix landing, so it stays open.

## Change summary

On Linux Mint (Cinnamon), VS Code shows a 'running in a GNOME environment, OS keyring not available' notification on every launch, with no way to permanently dismiss it and no tailored guidance for non-GNOME environments.

## Best solution

In src/vs/workbench/services/secrets/electron-browser/secretStorageService.ts, decide (a) whether to offer a persisted 'don't show again' option alongside the existing 'Use weaker encryption' path, which today only appears when the detected provider is basicText, and (b) whether the isGnome/isKwallet wording should be softened since it's derived from Electron's safeStorage backend name, not actual desktop-environment detection, and can mislabel Cinnamon/other GTK-adjacent environments as GNOME.

## Plan brief

- **Likely files:** `src/vs/workbench/services/secrets/electron-browser/secretStorageService.ts`, `src/vs/platform/encryption/common/encryptionService.ts`
- **Validation:** A test asserting that once a 'don't show again' (or equivalent) choice is persisted, notifyOfNoEncryption does not re-prompt on a subsequent service instantiation/session.
- **Behavior:**

  > Users on environments where the OS keyring/libsecret backend is unavailable currently see an unsuppressible, every-launch notification. The end state should let a user who doesn't want OS keyring integration either permanently acknowledge the warning or opt into weaker encryption, regardless of which backend Electron detected (gnome/kwallet/basicText), and the wording should not assert a specific desktop environment that it did not actually detect.
- **Trace:**

  > NativeSecretStorageService.notifyOfNoEncryption (src/vs/workbench/services/secrets/electron-browser/secretStorageService.ts) only offers a persisted remediation ('Use weaker encryption', writing password-store to argv and reinitializing) when IEncryptionService.getKeyStorageProvider() returns KnownStorageProvider.basicText; the gnome/kwallet branches (isGnome/isKwallet in src/vs/platform/encryption/common/encryptionService.ts) only show a plain error prompt with a troubleshooting link, no suppression, and notifyOfNoEncryptionOnce only dedupes per-session. Do not change the basicText 'Use weaker encryption' flow, which already works as intended; the scope is the gnome/kwallet notification path and its wording.
- **Open decisions:**
  - Should users be able to permanently dismiss/suppress this security notification, or is repeating it every launch intentional to keep users aware their secrets aren't encrypted at rest?
  - Should the message stop asserting a specific desktop environment (GNOME/KDE) when it's only inferring from Electron's selected storage backend name, and if so what should the generic wording say?

## Evidence

- **current message logic:** src/vs/workbench/services/secrets/electron-browser/secretStorageService.ts lines 55-102: notifyOfNoEncryptionOnce only dedupes within a single session (createSingleCallFunction), so the notification/dialog reappears every launch; it only offers a persisted 'Use weaker encryption' remediation when the Electron safeStorage backend is KnownStorageProvider.basicText (line 74), not for the gnome/kwallet branches (lines 95-101) that just show a plain error prompt with no suppression.
- **wording source:** isGnome()/isKwallet() in src/vs/platform/encryption/common/encryptionService.ts map directly from Electron's safeStorage.getSelectedStorageBackend() value (e.g. 'gnome_libsecret'), not from any actual desktop-environment detection — so a Cinnamon-based distro like Linux Mint can still get the 'GNOME environment' wording purely because Chromium's OSCrypt picked a gnome-style libsecret backend.
- **recurrence:** The same exact message produced 10+ closed issues since 2023 on various distros (e.g. https://github.com/microsoft/vscode/issues/194530, https://github.com/microsoft/vscode/issues/202652, https://github.com/microsoft/vscode/issues/262995) and several newer open ones created after this issue (https://github.com/microsoft/vscode/issues/313711, https://github.com/microsoft/vscode/issues/318219, https://github.com/microsoft/vscode/issues/332559), none predating #278443, so there is no older open canonical to fold this into.
