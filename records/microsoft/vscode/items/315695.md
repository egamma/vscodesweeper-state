# Issue #315695 — Scroll syncing gets funky with markdown file open twice

[https://github.com/microsoft/vscode/issues/315695](https://github.com/microsoft/vscode/issues/315695)

## Summary

Keep open: current source still separates editor-driven scrolling from the broadcast that synchronizes the two Markdown diff panes. The issue already has the appropriate area label, and the broader diff-preview tracking issue does not establish a duplicate.

## Change summary

Scrolling Markdown source in a separate editor group moves only one pane of its rendered diff instead of keeping both panes aligned.

## Best solution

Keep both rendered diff panes synchronized when a matching source editor drives their scroll position, using the existing diff line mappings and preserving feedback-loop suppression.

Both preview panes must follow corresponding mapped positions, including across inserted or deleted blocks. Also scroll either preview directly and confirm existing synchronization remains stable without oscillation. Establish automated coverage for this editor-driven propagation before treating the work as implement-ready.
- **Behavior:**

  > With a side-by-side rendered Markdown diff open, scrolling a matching source editor in another group must keep both rendered panes aligned to corresponding document positions. Insertions and deletions must use the existing diff correspondence rather than assuming identical line numbers. Direct scrolling of either preview must continue to synchronize its counterpart without feedback loops, and ordinary non-diff previews must retain their behavior.
- **Trace:**

  > TopmostLineMonitor emits source-editor visible-range changes by URI; StaticMarkdownPreview in extensions/markdown-language-features/src/preview/preview.ts forwards matching changes through MarkdownPreview.scrollTo as updateView messages. In preview-src/index.ts, onUpdateView suppresses scroll events while moving the local preview, and the suppressed scroll listener is also the only caller of DiffScrollSyncManager.broadcastScroll. The counterpart therefore receives no synchronization message on the normal editor-driven path. previewManager.ts already supplies the shared channel and directional line mappings, while diffScrollSync.ts handles translation and incoming-scroll suppression. Preserve those mappings, non-diff behavior, and feedback-loop prevention; unrelated Markdown editor functionality is outside the boundary. The remaining planning work is to establish executable regression coverage for webview scroll propagation, not to decide the expected behavior. https://github.com/microsoft/vscode/issues/315333 documents the synchronization expectation, and https://github.com/microsoft/vscode/issues/315174 is related feature tracking rather than a verified same-symptom duplicate.

In src/preview/preview.ts:609–619, StaticMarkdownPreview responds only when isPreviewOf(event.resource) matches, then calls scrollTo; MarkdownPreview.scrollTo sends an updateView message.
- **Missing propagation:** extensions/markdown-language-features/preview-src/index.ts:157–176 handles updateView by scrolling with scrollDisabledCount set and does not broadcast the target line. Thus the normal source-driven scroll path moves the matching pane without notifying its counterpart.
