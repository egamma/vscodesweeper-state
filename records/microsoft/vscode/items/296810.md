# Issue #296810 — Agents ignore fileLinkification instructions — produce absolute Windows paths that break on click

[https://github.com/microsoft/vscode/issues/296810](https://github.com/microsoft/vscode/issues/296810)

## Summary

Still a valid issue on current main. The fileLinkification system prompt instructions tell agents to use workspace-relative paths and strip drive letters, but LLMs frequently ignore them — producing `[file](c:/path)` links that break because VS Code's URI parser treats `c:` as a scheme. The agent host path already has a `parseAbsoluteFileLinkTarget` post-processing function that correctly normalizes Windows absolute paths, but regular Copilot Chat responses do not go through that rewrite path. The related issue #296804 was closed as NOT_PLANNED.

## Change summary

Copilot Chat agent responses with Windows absolute-path markdown links fail on click because the drive letter is misinterpreted as a URI scheme.

## Best solution

Extend the existing `parseAbsoluteFileLinkTarget` / `rewriteMarkdownLinks` post-processing (currently used only for agent host connections in `stateToProgressAdapter.ts`) to also run on regular Copilot Chat markdown responses rendered through `chatMarkdownContentPart.ts`. This would fix broken links regardless of model compliance with prompt instructions. The prompt-only approach in `fileLinkificationInstructions.tsx` is insufficient because models don't reliably follow the instructions.

## Evidence

- **fileLinkification instructions exist:** extensions/copilot/src/extension/prompts/node/agent/fileLinkificationInstructions.tsx already instructs agents to 'Use / only; strip drive letters and external folders' and 'Do not use these URI schemes: file://, vscode://', but LLMs don't reliably comply.
- **post-processing exists for agent host only:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/stateToProgressAdapter.ts has `parseAbsoluteFileLinkTarget` which detects Windows paths via `win32.isAbsolute()` and converts them to proper file:// URIs, but this only runs when `connectionAuthority` is set (agent host connections).
- **rendering path lacks normalization:** The chat markdown content part at src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatInlineAnchorWidget.ts calls URI.parse(href) on link targets — when the href is `c:/path`, the parser treats `c` as a scheme, producing an unresolvable URI.
- **related issue closed NOT_PLANNED:** https://github.com/microsoft/vscode/issues/296804 reported the same core rendering problem and was closed as NOT_PLANNED on 2026-07-08, suggesting the team may not view a client-side fix as the right approach.
- **Linux confirmation:** Comment by @aryzing confirms similar linkification failures on Linux with GPT-5.4, indicating the problem is cross-platform (absolute paths, not just Windows drive letters).
