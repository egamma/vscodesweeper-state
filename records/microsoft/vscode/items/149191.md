# Issue #149191 — Increase max height for the hover widget?

[https://github.com/microsoft/vscode/issues/149191](https://github.com/microsoft/vscode/issues/149191)

## Summary

Keep this accepted request open: manual hover resizing and remembered dimensions provide partial relief, but initial image previews still have a core-imposed height limit with no configurable maximum. The extension maintainer confirmed the remaining limitation after resizing shipped, and no verified open canonical owns the same request.

## Change summary

Allow larger editor image hovers so previews can display the whole image without unnecessary scrolling.

## Best solution

Retain manual resizing while agreeing on a viewport-safe way for image previews to use sufficient space without requiring an initial resize after each restart. Decide whether that should be user-controlled hover sizing or content-aware sizing before implementing it in the editor hover.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/hover/browser/contentHoverWidget.ts`, `src/vs/editor/contrib/hover/browser/resizableContentWidget.ts`, `src/vs/editor/common/config/editorOptions.ts`
- **Validation:** In a fresh VS Code window, use gutter-preview with an image taller than the default hover cap but small enough to fit in available window space. Verify the agreed behavior displays the complete image without an initial manual resize; repeat after restarting and near the top and bottom of the editor. Confirm oversized content remains scrollable and ordinary text hovers retain the agreed default behavior.
- **Behavior:**

  > Image previews provided through editor hovers can be cropped by the initial hover height limit even when the window has enough space to display them. Manual resizing helps, but does not provide configurable or image-aware initial sizing after a restart. The finished behavior should let users obtain a complete preview within available window space under the agreed sizing policy. Acceptance must cover fresh-window behavior, subsequent hovers, restart behavior and content that genuinely exceeds available space.
- **Trace:**

  > ContentHoverWidget._updateMaxDimensions in src/vs/editor/contrib/hover/browser/contentHoverWidget.ts imposes the initial maximum dimensions, incorporating only static in-memory _lastDimensions from _resize. ResizableContentWidget in src/vs/editor/contrib/hover/browser/resizableContentWidget.ts calculates available space above and below the hover anchor. EditorHover in src/vs/editor/common/config/editorOptions.ts exposes no maximum-size setting. https://github.com/microsoft/vscode/pull/185540 and https://github.com/microsoft/vscode/issues/185743 establish existing resizing and remembered sizing, while https://github.com/kisstkondoros/gutter-preview/issues/171 confirms the initial-preview gap remained afterward. Preserve manual resizing and window-bound containment; do not expand this into a new built-in image-preview feature. The unresolved boundary is the user-visible initial-sizing policy, not the location of the implementation.
- **Open decisions:**
  - Should sufficient initial image-preview space come from a user-controlled hover-size preference, content-aware sizing, or durable remembered manual dimensions, and should that policy also affect ordinary text hovers?

- **existing capability and remaining limit:** src/vs/editor/contrib/hover/browser/contentHoverWidget.ts implements manual resizing in _resize and remembers dimensions in static _lastDimensions.
