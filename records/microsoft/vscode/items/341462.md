# Issue #341462 — Copilot CLI (Copilot SDK) agent sessions can't use visible VS Code terminals, so the user can't complete interactive auth (SSH/sudo passwords)

[https://github.com/microsoft/vscode/issues/341462](https://github.com/microsoft/vscode/issues/341462)

## Summary

Keep this team-authored request open and route it to the terminal area. Current source explicitly excludes Windows from the custom PTY terminal tools, leaving the reporter's interactive authentication workflow unsupported.

## Change summary

Let users interact with a Copilot SDK agent's terminal and let the agent continue using the same authenticated session.

## Best solution

Provide a supported, user-visible interactive terminal path for Copilot SDK sessions on Windows, preserving the live process across user authentication and subsequent agent input. Decide how that path integrates with runtime-owned shells and existing terminal ownership and permission boundaries.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts`, `src/vs/platform/agentHost/node/copilot/copilotShellTools.ts`, `src/vs/platform/agentHost/node/copilot/copilotNonPtyShellTerminals.ts`, `src/vs/platform/agentHost/node/agentHostTerminalManager.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatTerminalToolProgressPart.ts`
- **Validation:** On Windows, start a Copilot SDK session and request an SSH connection to a controlled test host requiring interactive authentication. Confirm the user can reveal the executing terminal, authenticate directly, and let the agent send a follow-up command and read its result in that same remote session; repeat with a sudo prompt. Verify ordinary non-interactive shell execution and existing permission enforcement remain unchanged.
- **Behavior:**

  > A Copilot SDK session on Windows must support the user completing interactive authentication in the process the agent is using. The user can see and type into that terminal, then the agent can send further input and read output without replacing the authenticated process. Acceptance includes SSH login followed by a command in the same remote session and an interactive sudo prompt, without requiring passwords in chat, passwordless sudo, or preconfigured SSH keys.
- **Trace:**

  > CopilotSessionLauncher in src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts registers createShellTools only on non-Windows platforms when the custom terminal setting is enabled. ShellManager in copilotShellTools.ts already represents persistent managed PTY shells, whereas NonPtyShellTerminalStreams in copilotNonPtyShellTerminals.ts publishes SDK shell output without an interactive PTY. ChatTerminalToolProgressPart._initializeTerminalActions explicitly avoids attaching an integrated terminal instance for non-PTY content. These paths establish why the existing setting does not solve the Windows report, but do not establish a supported runtime input bridge. Preserve runtime permission and sandbox enforcement, existing non-interactive execution, and host-advertised terminal identities. Related visibility and context work is recorded at https://github.com/microsoft/vscode/issues/341333 and https://github.com/microsoft/vscode/issues/329541; neither alone covers authentication continuity.
- **Open decisions:**
  - Should the supported interaction expose the SDK runtime's own shell to the user, or provide a separate managed interactive terminal tool alongside runtime-owned shell execution?
  - Must the initial capability also let the agent adopt arbitrary user-opened terminals, or is a shared agent-created terminal sufficient for the authentication workflow?

## Evidence
