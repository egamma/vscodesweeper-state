# Issue #325827 — Support registration of external agents via Extension API in the agents view

[https://github.com/microsoft/vscode/issues/325827](https://github.com/microsoft/vscode/issues/325827)

## Summary

Keep open: current main exposes internal agent-provider registration but no corresponding Extension API for first-class, lifecycle-managed external harnesses. Existing session APIs and remote AHP connections provide partial integration, while the related ACP and provider-neutrality requests do not supersede this API gap.

## Change summary

Allow extensions to register independently implemented agent runtimes with capability discovery and local or remote Agent Host lifecycle integration.

## Best solution

Define a proposed extensibility contract that lets third-party runtimes participate as first-class harnesses without core modifications, preserving orchestrator-owned session persistence and capability-driven behavior. Settle the execution boundary and host-lifecycle contract before implementation rather than exposing the entire internal IAgent interface unchanged.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.chatSessionsProvider.d.ts`, `src/vscode-dts/vscode.proposed.chatPromptFiles.d.ts`, `src/vs/platform/agentHost/common/agent.ts`, `src/vs/platform/agentHost/node/agentHostProviderService.ts`, `src/vs/platform/agentHost/node/agentHostMain.ts`, `src/vs/platform/agentHost/node/agentHostServerMain.ts`, `src/vs/sessions/contrib/providers/remoteAgentHost/browser/remoteAgentHostActions.ts`
- **Validation:** The plan should end with an extension-host integration scenario using a minimal independent runtime: install and activate its extension without core changes, observe its harness and advertised capabilities, create a session in the selected folder, exchange streamed messages, cancel a turn, reload and resume persisted history, and verify the agreed unregister/shutdown behavior. Exercise the agreed remote-host placement separately and preserve existing built-in provider behavior.
- **Behavior:**

  > An extension can contribute an independent agent runtime, rather than only prompts or models for an existing harness, and make it selectable without modifying VS Code core. Sessions use the selected working folder and expose only the capabilities the runtime supports. The accepted contract must specify creation, streaming, cancellation, persistence, reconnection and teardown behavior, including the supported local and remote placements. Acceptance should use a minimal third-party runtime and verify those behaviors alongside unchanged built-in harnesses.
- **Trace:**

  > agentHostMain.ts registers the built-in harnesses through AgentHostProviderService.registerProvider; agentHostServerMain.ts has corresponding server-side registration. IAgent in common/agent.ts supplies descriptor/capability discovery, observable model catalogs, exact-chat lifecycle operations and progress events, while the provider registry handles initialization and shutdown. The existing proposed chat-session APIs support session creation and request handling but do not enter this host registry. sessions.remoteAgentHost.add connects to an existing AHP endpoint, and the pi consumer confirms that path works without satisfying local harness ownership and lifecycle needs. Preserve orchestrator-owned session identities, persistence and chat membership rather than delegating those responsibilities to extension runtimes. https://github.com/microsoft/vscode/issues/340860 offers an ACP adapter direction, and https://github.com/microsoft/vscode/issues/341006 describes the broader UI goal; neither decides the registration contract here. Uncertainty begins at where extension-provided runtime code executes and how its lifetime relates to extension activation, host shutdown and reconnectable sessions.
- **Open decisions:**
  - Must extensions supply an implementation executing inside the Agent Host, or should the public contract register a separately hosted runtime or AHP endpoint, and which local and remote placements must the initial API support?
  - When an extension is disabled or VS Code closes, should contributed runtimes and active sessions terminate, remain available for reconnection, or expose an explicit capability-controlled choice?
