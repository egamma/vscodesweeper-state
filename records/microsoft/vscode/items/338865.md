# Issue #338865 — Code.exe cannot start VS Code on Windows 1.139.1 (versioned resources layout)

[https://github.com/microsoft/vscode/issues/338865](https://github.com/microsoft/vscode/issues/338865)

## Summary

Detailed, technically thorough report that a fresh Windows User Setup install of 1.139.1 fails to launch via Code.exe (Start Menu shortcut, direct exe, file association) while bin\code.cmd still works — but this is the first report of it (0 days old, no corroboration), and the actual resourcesPath resolution for the new versioned-resources layout lives in the native/patched Electron binary, which isn't visible in this JS-only checkout, so I can't independently confirm the defect. Asking the reporter to confirm on the latest build with --verbose output before triaging further.

## Change summary

After installing VS Code 1.139.1 (stable, x64 User Setup) on Windows, Code.exe no longer starts VS Code directly (silently exits 0/1/9 depending on args) because the new win32VersionedUpdate layout puts app resources under a commit-hash subfolder instead of next to Code.exe; only bin\code.cmd (which explicitly points at the hashed folder) still works.

## Best solution

A VS Code/Electron team member should verify that direct Code.exe invocation (Start Menu shortcut, `Code.exe <path>`, file associations) correctly resolves resources under the new `<hash>\resources\app` layout introduced by the versioned-resources feature (https://github.com/microsoft/vscode/pull/263998) — if the native resourcesPath lookup only accounts for the background-update/cli path and not a plain double-click launch, that's the gap to close.

## Evidence

- **versioned layout confirmed in source:** build/gulpfile.vscode.win32.ts and build/win32/code.iss show that when product.json has win32VersionedUpdate: true, app resources are laid out under `{app}\<first-10-chars-of-commit>\resources\app`, while Code.exe itself is copied to the install root ({app}\Code.exe) — matching exactly the install tree the reporter dumped (04c0d99f4f\resources\app next to a top-level Code.exe with no resources\ dir).
- **feature is recent and team-authored:** This layout was introduced by PR https://github.com/microsoft/vscode/pull/263998 ('feat: create versioned resources for windows setup'), authored by a VS Code/Electron team member and merged into the November 2025 milestone, i.e. shortly before this 1.139.1 stable release.
- **no visibility into native resourcesPath resolution:** The runtime logic that would make a native Code.exe (a patched/prebuilt Electron binary via @vscode/gulp-electron with `createVersionedResources`) find resources under the hashed subfolder is not present in this repo — only build-time packaging (build/lib/electron.ts, build/lib/util.ts:getVersionedResourcesFolder) and update-time garbage collection (src/vs/platform/update/electron-main/updateService.win32.ts) reference the versioned folder — so I cannot confirm from source alone whether normal double-click launches are handled.
- **no corroboration yet:** Issue is 0 days old with 0 reactions and no comments; if this were a universal break-on-every-fresh-Windows-install regression in the just-shipped stable, a rapid wave of duplicate reports would be expected.
