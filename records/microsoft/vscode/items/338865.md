## Plan brief

- **Likely files:** `build/lib/electron.ts`, `build/gulpfile.vscode.win32.ts`, `build/win32/code.iss`, `src/vs/code/node/cli.ts`
- **Validation:** On Windows 11 with a packaged User Setup installation, compare direct Code.exe launches with bin\code.cmd while recording inherited ELECTRON_RUN_AS_NODE. Verify no-argument shortcut launch, folder and file arguments, --new-window, and the registered file association both with no instance running and with an existing instance.
- **Behavior:**

  > The reporter's installed Code.exe exits without displaying a window, while bin\code.cmd starts VS Code successfully. Normal shortcuts, direct folder/file launches, and file associations should start or contact VS Code successfully in a normal desktop environment. Acceptance checks must cover both cold startup and an existing instance using the supported versioned installation layout.
- **Trace:**

  > build/lib/electron.ts and build/gulpfile.vscode.win32.ts intentionally support commit-prefixed resources, while build/win32/code.iss targets the root executable for shortcuts and file associations. The normal CLI branch in src/vs/code/node/cli.ts removes ELECTRON_RUN_AS_NODE before spawning process.execPath, providing an environment difference worth testing. Source inspection does not establish whether the reporter inherited that variable or encountered a native startup/resource-discovery defect. Preserve the supported layout and legitimate Electron-as-Node CLI operation; do not replace shortcut targets with CLI wrappers merely to hide the failure. The missing-resource update failure at https://github.com/microsoft/vscode/issues/336131 has materially different evidence and is not a confirmed canonical.

## Evidence

- **Complete reproduction:** https://github.com/microsoft/vscode/issues/338865 supplies Windows 11, installer version and commit, the installed directory layout, exact launch commands and exit codes, a clean-reinstall result, and a working CLI comparison. These are sufficient to start a reproduction; no current-main reproduction was executed.
- **Versioned layout is supported:** build/lib/electron.ts configures createVersionedResources and productVersionString using the first ten commit characters. build/gulpfile.vscode.win32.ts resolves product.json under that versioned directory. The absence of resources beside Code.exe is therefore not itself proof of a defective installation.
- **Direct launch is intended:** build/win32/code.iss:113-115 registers shortcuts targeting the root executable without application-path arguments; line 1273 registers the file-association command as the executable followed by the selected file.
- **Environment differential:** src/vs/code/node/cli.ts:224-229 copies process.env and removes ELECTRON_RUN_AS_NODE; lines 480-502 pass that environment to spawn(process.execPath, spawnArgs, options). Thus the working CLI does not prove direct executable resource discovery is broken: inherited ELECTRON_RUN_AS_NODE is a diagnostic hypothesis, not a confirmed cause.
- **Related reports are not verified duplicates:** https://github.com/microsoft/vscode/issues/336131 is open but reports missing application resources after reboot during a pending update, with both executables failing and repair succeeding. https://github.com/microsoft/vscode/issues/340178 is open but its follow-up says direct Code.exe launch works and identifies a stale shortcut. Neither establishes the same underlying defect as this report.
- **No completed fix established:** https://github.com/microsoft/vscode/pull/263998 introduced versioned resources; it does not demonstrate a fix for this later launch failure. Read-only startup searches and relevant packaging/CLI history did not identify a concrete fixing commit for this report.
