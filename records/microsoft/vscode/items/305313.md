[https://github.com/microsoft/vscode/issues/305313](https://github.com/microsoft/vscode/issues/305313)

Keep open: this is a team-authored AHP feature-gap tracker with no verified implementation, duplicate, or maintainer decision supporting closure. The protocol supports tool-result confirmation, but both the CopilotAgent request path and VS Code client handling remain identified as missing.

## Change summary

Implement end-to-end AHP tool-call result confirmation in CopilotAgent and the VS Code UI.

## Best solution

Define the user-visible confirmation flow and complete both ends of the AHP capability: CopilotAgent should request tool-result confirmation when appropriate, and VS Code should present and return the user's decision through the agent-host protocol.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/common/agentHostProtocol.ts`, `src/vs/platform/agentHost/node/agentHost.ts`
- **Validation:** Add an Agent Host protocol test that drives a tool call requiring result confirmation, verifies VS Code receives the confirmation request, returns approve or deny, and confirms the agent continues or stops accordingly.
- **Behavior:**

  > When an agent requests confirmation for a tool call result, VS Code presents a clear confirmation prompt and sends the user's approve or deny decision back over AHP. Approval lets the agent consume the result and continue; denial prevents the result from being accepted and remains visible in the turn state. Existing tool calls that do not request result confirmation must behave unchanged.
- **Trace:**

  > The issue establishes that protocol support exists but the CopilotAgent never requests tool-result confirmation and the VS Code client does not handle it. The relevant boundary is the AHP protocol/client path under src/vs/platform/agentHost together with the CopilotAgent implementation; related broader tracking exists at https://github.com/microsoft/vscode-internalbacklog/issues/7616 and https://github.com/microsoft/vscode-internalbacklog/issues/7868. Preserve existing pre-execution tool approval and ordinary tool-result handling; this work should not redefine those flows. The uncertainty starts at the user-visible semantics and lifecycle of result confirmation rather than at code placement.
- **Open decisions:**
  - Which tool-result states require confirmation, and is the request initiated solely by the agent or also enforceable by the VS Code client?
  - What should denial mean in the public behavior: discard the result, expose it as rejected context, or request a corrected tool result?
  - Should result confirmation reuse the existing tool approval UI and persistence semantics, or be presented as a distinct one-time decision?
