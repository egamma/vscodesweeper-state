# Issue #192144 — VSCode client libraries have invalid exports

[https://github.com/microsoft/vscode/issues/192144](https://github.com/microsoft/vscode/issues/192144)

## Summary

Keep open as an active package-format migration umbrella. A maintainer explicitly supports moving toward ESM, while the remaining AMD/CJS compatibility and cross-repository scope require a coordinated product and compatibility decision.

## Change summary

Publish VS Code client libraries with valid, standards-based package exports so Node.js and bundler consumers do not require custom resolution workarounds.

## Best solution

Define a staged migration for VS Code-owned client libraries, using explicit standards-based exports and real module formats, with compatibility tests for Node.js and browser bundlers. Decide which packages can become ESM-only and where Monaco or other consumers still require an AMD or CJS artifact before making semver-major releases.

## Plan brief

- **Likely files:** `build/monaco/package.json`, `build/gulpfile.editor.ts`, `src/vs/editor/editor.api.ts`
- **Validation:** For each migrated package, generate the publishable artifact and run a compatibility fixture that imports it from native ESM, requires it where CJS remains supported, and bundles its browser entry; for Monaco, run `npm run gulp editor-distro` before checking the generated package metadata and entries.
- **Behavior:**

  > VS Code-owned client packages expose only real module formats through standards-based package metadata. Supported Node.js consumers and browser bundlers resolve the intended implementation without custom aliases, deep imports, or faux-ESM interpretation. Any retained AMD or CJS entry remains explicitly supported and tested, and each incompatible format removal is released as a semver-major change.
- **Trace:**

  > This is a cross-repository package-contract migration rather than one isolated defect. In this checkout, build/gulpfile.editor.ts generates monaco-editor-core, build/monaco/package.json exposes an ESM path through the non-standard `module` field without an `exports` map, and src/vs/editor/editor.api.ts still contains AMD-specific integration. The language-server fixes in https://github.com/microsoft/vscode-languageserver-node/pull/1297 and https://github.com/microsoft/vscode-languageserver-node/pull/1326 demonstrate partial progress but do not settle the other packages or Monaco. The boundary is package generation and published module contracts: editor runtime behavior and unrelated source-module organization should remain unchanged. Uncertainty starts at the supported-format matrix and rollout order, especially whether Monaco must retain AMD and whether CJS remains a supported public entry.
- **Open decisions:**
  - Should the target public contract be ESM-only for every package that can make a semver-major release, or should selected packages continue dual-publishing CJS and ESM?
  - Must Monaco retain an AMD distribution for known consumers, and if so, for how long and as which explicitly exported entry?
  - Should this umbrella define one coordinated compatibility baseline and rollout across all listed VS Code-owned repositories, or approve migrations package by package?

## Evidence

- **maintainer direction:** In the 2025-12-01 comment, a VS Code maintainer answered that ESM-only is desired but said AMD dependents must first be identified and that the build supports both targets.
- **remaining Monaco contract:** Current main still generates monaco-editor-core through build/gulpfile.editor.ts into an esm directory, while build/monaco/package.json advertises only the non-standard module field and no package exports map; src/vs/editor/editor.api.ts also retains explicit AMD runtime compatibility.
- **partial fixes:** https://github.com/microsoft/vscode-languageserver-node/pull/1297 and https://github.com/microsoft/vscode-languageserver-node/pull/1326 fixed exports for vscode-languageserver-types and vscode-languageserver-textdocument, but they cover only two packages in this broader inventory.
