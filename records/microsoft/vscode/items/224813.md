# Issue #224813 — Unable to install extension 'vscode.git' because it is not found.

[https://github.com/microsoft/vscode/issues/224813](https://github.com/microsoft/vscode/issues/224813)

## Summary

The bug remains source-reproducible on current main: Restricted Mode removes `vscode.git` from the active extension registry, and the extension URL handler consequently treats this bundled extension as absent and attempts an impossible Marketplace installation. This team-authored Backlog bug also has an explicit maintainer commitment to address the behavior, so it must remain open.

## Change summary

Opening a `vscode://vscode.git/clone` deep link from a restricted empty window reports that the bundled `vscode.git` extension cannot be found instead of handling the clone or explaining the trust requirement.

## Best solution

Make extension URL routing distinguish an installed built-in extension disabled by workspace trust from an extension that is genuinely absent. For Git clone deep links, provide an explicit trust-aware outcome rather than attempting to install `vscode.git` from the Marketplace.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/browser/extensionUrlHandler.ts`, `src/vs/workbench/services/extensions/test/browser/extensionUrlHandler.test.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `extensions/git/src/protocolHandler.ts`, `extensions/git/package.json`
- **Validation:** Add a targeted extension URL handler test for an installed `vscode.git` extension disabled by workspace trust, asserting that opening `vscode://vscode.git/clone?...` does not execute `workbench.extensions.installExtension` and instead follows the selected trust-aware behavior; manually verify the same deep link from a restricted empty window.
- **Behavior:**

  > Opening a Git clone deep link from an untrusted empty window must not claim that the bundled `vscode.git` extension is missing or attempt to install it from the Marketplace. The user must receive the trust-aware behavior selected by the maintainer, while trusted-window clone links continue to open the normal clone flow. Acceptance requires coverage for both the restricted and trusted cases and preservation of installation behavior for genuinely absent third-party URI handlers.
- **Trace:**

  > `extensions/git/package.json` marks Git unsupported in untrusted workspaces. During extension-service initialization, `filterEnabledExtensions` in `src/vs/workbench/services/extensions/common/abstractExtensionService.ts` removes it from the registry; `ExtensionUrlHandler.handleURL` then consults that filtered registry and routes an undefined result to `handleUnhandledURL`, which invokes the extension-install command. The actual clone URI handler is `GitProtocolHandler` in `extensions/git/src/protocolHandler.ts`, registered only when the Git extension activates. The boundary is generic extension deep-link routing and workspace-trust semantics: do not make unsupported extensions generally active in restricted workspaces, and preserve Marketplace installation for truly absent extensions. The comments at https://github.com/microsoft/vscode/issues/224813#issuecomment-2370916731 and https://github.com/microsoft/vscode/issues/224813#issuecomment-2371682984 confirm both the trigger and maintainer acceptance.
- **Open decisions:**
  - When a Git clone deep link reaches a restricted empty window, should VS Code prompt to trust the window, support this clone operation without enabling the full Git extension, or show a targeted explanation that cloning is blocked until trust is granted?

## Evidence

- **source trigger:** `extensions/git/package.json` declares `capabilities.untrustedWorkspaces.supported: false`, so `filterEnabledExtensions` in `src/vs/workbench/services/extensions/common/abstractExtensionService.ts` excludes `vscode.git` while the window is untrusted.
- **failing path:** `ExtensionUrlHandler.handleURL` in `src/vs/workbench/services/extensions/browser/extensionUrlHandler.ts` calls `extensionService.getExtension('vscode.git')`; that service reads only the filtered registry. An undefined result immediately reaches `handleUnhandledURL`, which executes `workbench.extensions.installExtension` for the bundled extension.
- **confirmed symptom:** Multiple reporters confirmed that trusting the window makes GitLab and Azure DevOps clone links work, including https://github.com/microsoft/vscode/issues/224813#issuecomment-2370916731 and https://github.com/microsoft/vscode/issues/224813#issuecomment-3346548527.
- **maintainer direction:** A maintainer stated that the cause was understood and that it would be investigated in the next milestone: https://github.com/microsoft/vscode/issues/224813#issuecomment-2371682984.
- **current gap:** `src/vs/workbench/services/extensions/test/browser/extensionUrlHandler.test.ts` covers absent extensions and URI trust confirmation but has no case distinguishing an installed built-in extension disabled by workspace trust from an extension that is not installed.
