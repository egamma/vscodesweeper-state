# Issue #210509 — [Testing] Coverage API Issues: Monorepo & Accumulation

[https://github.com/microsoft/vscode/issues/210509](https://github.com/microsoft/vscode/issues/210509)

## Summary

Keep open: current source still selects coverage from one task, replaces it on subsequent coverage runs, and clears it after a non-coverage run. Multi-controller dispatch now has a broader implementation, but the coverage retention and aggregation gap remains; the newer accumulation request is related, not a valid duplicate target for this re-reviewed item.

## Change summary

Make coverage usable across multiple test controllers and partial runs without losing unrelated coverage or access to the latest available report.

## Best solution

Define coverage ownership and invalidation semantics that preserve unrelated controllers' reports without retaining misleading stale statistics, then make the coverage selection and reopening behavior follow that contract. Separately retest the original top-level multi-controller dispatch symptom against the current per-controller routing.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/testing/common/testCoverageService.ts`, `src/vs/workbench/contrib/testing/common/testCoverage.ts`, `src/vs/workbench/contrib/testing/browser/testExplorerActions.ts`, `src/vs/workbench/contrib/testing/common/testServiceImpl.ts`, `src/vs/workbench/contrib/testing/common/testProfileService.ts`
- **Validation:** Use two coverage-capable controllers with disjoint source files: run top-level coverage and verify both handlers execute; run their coverage separately and verify the agreed retention behavior; run an ordinary test and invoke testing.openCoverage to verify the agreed invalidation and recovery behavior. Include same-test reruns, overlapping files, and moved/deleted files to ensure retained reports do not silently produce stale aggregate statistics.
- **Behavior:**

  > Coverage from one test controller currently replaces another controller's coverage, and an ordinary test run clears the selected report. Users need a coherent way to inspect coverage across a mixed-language workspace and reopen the latest relevant report without rerunning every suite. Acceptance must define which reports remain valid after partial or non-coverage runs and how stale coverage is represented or removed. The original top-level coverage action must also be checked with two controllers to distinguish dispatch failures from displaying only one completed task.
- **Trace:**

  > TestCoverageService in src/vs/workbench/contrib/testing/common/testCoverageService.ts selects one TestCoverage and opens the first populated task on completion, otherwise clearing selection. OpenCoverage in src/vs/workbench/contrib/testing/browser/testExplorerActions.ts consults only the newest result. TestCoverage.append aggregates within one task's report, not across results. Current CoverageAllAction, TestService.runTests/runResolvedTests, and TestProfileService.getDefaultProfileForTest have per-controller dispatch paths, so the historical dispatch symptom needs a targeted retest rather than an assumed fix. Preserve the stale-coverage concern documented in https://github.com/microsoft/vscode/issues/202712; do not equate retaining unrelated controller coverage with retaining every historical measurement. Coordinate the retention design with https://github.com/microsoft/vscode/issues/283358 without closing this older, broader report into it.
- **Open decisions:**
  - Should the coverage view retain the latest report independently for each controller, or present an explicitly accumulated cross-run report, and how should overlapping files contribute to totals?
  - When a non-coverage run or source-file change invalidates some retained coverage, which reports should be cleared, preserved, or visibly marked stale, and what should Open Coverage restore?

## Evidence

- **Remaining single-report limitation:** src/vs/workbench/contrib/testing/common/testCoverageService.ts exposes selected as one TestCoverage. Its completed-result handler uses tasks.find(t => t.coverage.get()), opens only that task, and calls closeCoverage() when the completed run has no coverage. openCoverage() replaces selected rather than preserving other controllers' reports. These paths explain the replacement and disappearance described in https://github.com/microsoft/vscode/issues/210509.
- **Existing command does not recover older coverage:** OpenCoverage in src/vs/workbench/contrib/testing/browser/testExplorerActions.ts examines only results[0].tasks before calling openCoverage(). It does not search older results for the latest populated coverage report, so testing.openCoverage does not cover the reporter's recovery request after a newer ordinary test run.
- **Current multi-controller dispatch:** CoverageAllAction uses RunOrDebugAllTestsAction, which collects eligible controller roots and calls runTests with the Coverage group. In src/vs/workbench/contrib/testing/common/testServiceImpl.ts:154-210, runTests resolves profiles for individual tests; runResolvedTests at lines 270-289 groups targets by controller and dispatches each group. TestProfileService.getDefaultProfileForTest resolves within the test's controller. This differs from a first-controller-only implementation, but source inspection alone does not establish that the original extension configuration now works.
- **Existing capabilities are partial:** The coverage settings in src/vs/workbench/contrib/testing/common/configuration.ts control presentation, percentages, colors, toolbar, minimap, and Explorer visibility, not cross-run retention. TestCoverage.append in src/vs/workbench/contrib/testing/common/testCoverage.ts updates file coverage within a result/task; that is not aggregation across separate controller runs.

Preserving unrelated reports must reconcile these expectations rather than globally disabling clearing.
