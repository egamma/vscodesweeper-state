# Issue #193935 — Git commit message enforcement

[https://github.com/microsoft/vscode/issues/193935](https://github.com/microsoft/vscode/issues/193935)

## Summary

Keep open for a decision on clearer empty-message commit UX. The reporter confirmed the intended editor flow, but the remaining feedback request is not covered by the existing setting, and maintainers have consolidated subsequent reports here.

## Change summary

Make committing with an empty SCM message clearly communicate the next action rather than appearing to hang.

## Best solution

Make the transition from Commit to message authoring explicit while preserving editor-based input and message-free amend actions. The Git owner should settle the user-visible interaction before implementation; disabling the entire compound button conflicts with the constraint already recorded in the thread.

- **Likely files:** `extensions/git/src/actionButton.ts`, `extensions/git/src/commands.ts`, `extensions/git/src/gitEditor.ts`, `extensions/git/src/postCommitCommands.ts`
- **Validation:** In a disposable Git repository with a staged change, activate Commit with an empty SCM message and verify that the chosen message-authoring interaction is explicit and can be completed or cancelled without restarting. Repeat with git.useEditorAsCommitInput true and false, a supplied message, and Commit Amend without a new message; preserve the existing successful commit and amend behavior.
- **Behavior:**

  > Activating Commit with an empty SCM message currently enters another message-authoring interaction, which users can mistake for a stalled commit. The finished experience should make the required next step apparent without requiring a restart. Existing editor-based message authoring, quick input, commits with supplied messages, and amend operations without a new message must remain usable. The acceptance check should distinguish waiting for user input from an actual Git or editor failure.
- **Trace:**

  > In extensions/git/src/commands.ts, commitWithAnyInput chooses quick input when git.useEditorAsCommitInput is false, and smartCommit permits an empty input to proceed through the editor path when the setting is true. GitEditor.handle in extensions/git/src/gitEditor.ts opens the message document and resolves its request when the tab closes. ActionButton.getCommitActionButton in extensions/git/src/actionButton.ts exposes a compound action whose enabled state ignores message contents; postCommitCommands.ts supplies secondary actions including amend. The reporter confirmed the intended editor behavior, so this trace does not establish a real freeze or explain every subsequent hidden-editor report. The owner constraint at https://github.com/microsoft/vscode/issues/193935#issuecomment-1737592641 preserves secondary actions; do not treat disabling the whole button or removing editor input as an agreed outcome. The uncertainty is which user-visible interaction should communicate the transition to message authoring.
- **Open decisions:**
  - Should an empty-message Commit retain its current editor or quick-input transition with explicit feedback, or should message authoring become a separately labeled action while preserving message-free secondary actions?
