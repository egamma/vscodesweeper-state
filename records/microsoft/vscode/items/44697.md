# Issue #44697 — Feature request: Add support for modifier keys like right ctrl and right alt

[https://github.com/microsoft/vscode/issues/44697](https://github.com/microsoft/vscode/issues/44697)

## Summary

Side-specific modifier combinations remain unsupported in current source, and this accepted Backlog request has 83 upvotes. Keep it open for a compatibility-focused design discussion; existing scan-code bindings and external remapping do not cover the central ask.

## Change summary

Allow keyboard shortcuts to distinguish left and right Ctrl, Alt, Shift, and Meta modifiers.

## Best solution

Provide opt-in side-specific modifier bindings while preserving existing side-agnostic shortcuts and international-layout behavior. Agree on matching precedence and behavior when modifier-side information is unavailable before implementing the cross-platform keybinding changes.

## Plan brief

- **Likely files:** `src/vs/base/common/keybindings.ts`, `src/vs/base/common/keybindingParser.ts`, `src/vs/base/browser/keyboardEvent.ts`, `src/vs/workbench/services/keybinding/browser/keybindingService.ts`, `src/vs/workbench/services/keybinding/common/macLinuxKeyboardMapper.ts`, `src/vs/workbench/services/keybinding/common/windowsKeyboardMapper.ts`
- **Validation:** Extend parser and keyboard-mapper unit coverage to distinguish left-Ctrl+S and right-Ctrl+S while preserving generic Ctrl+S, and cover the agreed precedence and unknown-side behavior. Manually exercise the resulting bindings on Linux, Windows, and macOS, including both modifiers held, focus loss/re-entry, AltGr text entry, and existing modifier-only chords.
- **Behavior:**

  > Users cannot currently assign different commands to left-Ctrl+S and right-Ctrl+S; equivalent requests apply to Shift, Alt, and Meta. The finished capability should allow explicit side-specific combinations without changing existing side-agnostic shortcut definitions or default bindings. Acceptance must demonstrate distinct command dispatch for opposite modifier sides and continued operation of generic shortcuts. International text entry, modifier-only chords, and focus transitions must retain predictable behavior under the agreed matching rules.
- **Trace:**

  > KeybindingParser._readModifiers in src/vs/base/common/keybindingParser.ts produces only aggregate modifier flags, and Modifiers, KeyCodeChord, and ScanCodeChord in src/vs/base/common/keybindings.ts contain no modifier-side state. StandardKeyboardEvent in src/vs/base/browser/keyboardEvent.ts preserves the principal key's code but copies aggregate held-modifier flags; both MacLinuxKeyboardMapper.resolveKeyboardEvent and WindowsKeyboardMapper.resolveKeyboardEvent consume those flags. WorkbenchKeybindingService._registerKeyListeners dispatches keydown events and modifier-only keyup events, so merely retaining ControlRight in the key-code table would not distinguish its use while S is pressed. The discussion at https://github.com/microsoft/vscode/issues/44697 highlights missing modifier presses across focus boundaries, and proposes specific-before-generic matching without a maintainer decision settling that contract. Preserve existing generic shortcuts, AltGr handling, and modifier-only behavior; NumpadEnter is a related but distinct capability and should not substitute for solving modifier combinations. The trace establishes the current gap, not a complete design for recovering reliable modifier-side state across platforms.
- **Open decisions:**
  - When side-specific and generic bindings both match in the same context, should the side-specific binding always take precedence, with the generic binding used only as a fallback?
  - When a modifier was pressed before the window gained focus and its side is unknown, should only generic bindings be eligible until a fresh modifier press establishes the side?

## Evidence

- **Current representation and parser:** src/vs/base/common/keybindings.ts represents modifiers as four side-agnostic booleans in Modifiers, KeyCodeChord, and ScanCodeChord. src/vs/base/common/keybindingParser.ts, KeybindingParser._readModifiers, recognizes ctrl, shift, alt, and meta/win/cmd prefixes but no side-specific modifier prefixes. Bracketed scan codes identify the principal key, not the side of a held modifier.
- **Current event dispatch:** src/vs/base/browser/keyboardEvent.ts:148–154 copies the event's aggregate modifier flags and principal-key code. MacLinuxKeyboardMapper.resolveKeyboardEvent in src/vs/workbench/services/keybinding/common/macLinuxKeyboardMapper.ts:992–994 constructs a ScanCodeChord with those aggregate flags; WindowsKeyboardMapper.resolveKeyboardEvent in src/vs/workbench/services/keybinding/common/windowsKeyboardMapper.ts:413–416 does the same with KeyCodeChord. Neither can distinguish left-Ctrl+S from right-Ctrl+S.
- **Existing capability check:** src/vs/platform/keyboardLayout/common/keyboardConfig.ts registers keyboard.dispatch and keyboard.mapAltGrToCtrlAlt. The former selects code versus keyCode dispatch; the latter maps AltGraph to aggregate Ctrl+Alt. Neither enables side-specific modifiers. MacLinuxKeyboardMapper.resolveKeyboardEvent also explicitly normalizes NumpadEnter to Enter at lines 940–942, so the related comment request is not evidence that the central feature has shipped.
- **Discussion and acceptance:** The supplied discussion at https://github.com/microsoft/vscode/issues/44697 includes a maintainer's October 2021 suggestion to remap combinations externally to F13–F24, followed by objections concerning portability, displayed shortcut hints, and application context. The December 10, 2021 bot comment records promotion to Backlog after sufficient upvotes; the current count is 83. The earlier tentative scope objection is not a later decision overriding that acceptance.
- **Canonical search:** Repository issue searches for right Ctrl, left/right modifiers, and modifier titles found no verified older open issue owning this request. https://github.com/microsoft/vscode/issues/112149 describes the same feature, is closed, and its duplicate-detection comment points to this issue. https://github.com/microsoft/vscode/issues/178105 is another closed same-scope request, retired for insufficient votes rather than implementation; neither is a valid duplicate target.
- **Design boundary:** Comment 17 at https://github.com/microsoft/vscode/issues/44697 identifies that a letter-key event does not itself expose the side of held modifiers and that tracking previous events can miss presses outside the application. WorkbenchKeybindingService._registerKeyListeners in src/vs/workbench/services/keybinding/browser/keybindingService.ts dispatches individual keydown events and modifier-only keyup events; supporting modifier sides therefore involves more than changing the keyCodes.ts mapping.
