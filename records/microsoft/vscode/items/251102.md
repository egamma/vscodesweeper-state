# Issue #251102 — Built-in terminal has incorrect advance width for lots of ideographic, emoji, and non-spacing-mark characters

[https://github.com/microsoft/vscode/issues/251102](https://github.com/microsoft/vscode/issues/251102)

## Summary

Keep open as an upstream terminal Unicode-width limitation. Current main still exposes only Unicode 6 and 11 width providers, and the linked xterm.js work remains open; no verified fix or same-scope VS Code duplicate supports closing this report.

## Change summary

Update terminal character-width handling so newer emoji, ideographs, and combining marks occupy the appropriate number of cells without overlapping subsequent output.

## Best solution

Resolve Unicode-width and grapheme handling in xterm.js, then adopt the resulting provider in VS Code while preserving compatibility with terminal applications' width assumptions. Retain this report's concrete code-point examples as downstream acceptance cases.

- **Explicit upstream ownership:** Tyriar's supplied 2025-08-26 comment identifies https://github.com/xtermjs/xterm.js/issues/2668 as the upstream tracking issue. Read-only GitHub inspection confirms it is OPEN and covers Unicode-version width tables, ambiguous widths, and grapheme support.
- **Existing capability does not cover the request:** src/vs/workbench/contrib/terminal/common/terminalConfiguration.ts:544-552 registers terminal.integrated.unicodeVersion with only '6' and '11', defaulting to '11'. Switching this setting does not provide newer Unicode width definitions.
- **Current integration path:** src/vs/workbench/contrib/terminal/browser/xterm/xtermTerminal.ts:1165-1173 loads the unicode11 addon and selects raw.unicode.activeVersion from the configured version. package.json declares @xterm/addon-unicode11; the inspected terminal integration contains no newer Unicode or grapheme provider adoption.
- **Related report is narrower:** https://github.com/microsoft/vscode/issues/244411 is OPEN and was linked in the discussion, but its reproduction concerns a leading check-mark emoji. It does not establish ownership of this report's newer ideograph and combining-mark width cases, so it is not a verified full-scope canonical.
- **Older canonical search:** Searches for open terminal Unicode and emoji-width reports led to https://github.com/microsoft/vscode/issues/118905 and https://github.com/microsoft/vscode/issues/32840. Piping arbitrary commands through it was not supported and could interfere with applications managing their own display, so it does not resolve the central request.
