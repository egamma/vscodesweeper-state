# Issue #337848 — SDK hangs due to spamming listSessions

[https://github.com/microsoft/vscode/issues/337848](https://github.com/microsoft/vscode/issues/337848)

## Summary

Team-authored, freshly-filed performance bug with a detailed log-based diagnosis; the source confirms the mechanism (an unconditional full `client.listSessions()` bulk scan on every fallback-metadata prewarm, with no ID-scoping and a cache that's cleared the moment the last ref releases), but the reporter's own 'Likely fix' section lists several distinct remediation strategies that a maintainer needs to choose between.

## Change summary

Copilot's `prewarmSessionMetadata` re-enumerates the entire SDK session catalog (~4,858 sessions) on every fallback-metadata pass, even when only a handful of session IDs are actually needed, causing repeated multi-second/near-minute full scans and CPU spikes.

## Best solution

Scope or throttle the bulk prewarm so `AgentService._computeSessions`'s fallback path stops paying for a full-catalog `listSessions()` every time a small number of provider-fallback rows need metadata — likely by narrowing the SDK call to the needed session IDs (if the SDK supports it), extending/coalescing the short-lived cache across back-to-back calls, or both.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/platform/agentHost/node/agentService.ts`
- **Validation:** A regression test simulating a large SDK session catalog (e.g. thousands of sessions) with only a few fallback IDs needed, asserting the prewarm path no longer performs a full-catalog `listSessions()` (or performs it at most once) across a burst of near-simultaneous `_computeSessions` calls.
- **Open decisions:**
  - Should the SDK/CopilotClient support listing metadata for a specific set of session IDs, so the prewarm can be scoped to only the fallback sessions that actually need it instead of the whole catalog?
  - If ID-scoping isn't feasible, should the short-lived bulk cache be extended to live briefly across separate list computations (accepting some staleness) instead of being cleared the instant the last ref releases?
  - Should concurrent/back-to-back prewarm requests be explicitly coalesced (single-flight) so a burst of `listSessions` calls shares one bulk scan rather than triggering independent ones?

## Evidence

- **unconditional bulk scan:** src/vs/platform/agentHost/node/copilot/copilotAgent.ts:3149-3169 `prewarmSessionMetadata()` always calls `client.listSessions()` (full catalog) with no filter by needed session IDs, and the doc-comment above it (lines 3139-3145) confirms this is a deliberate 'one bulk `listSessions()` call' trade-off, not scoped to a subset.
- **trigger site:** src/vs/platform/agentHost/node/agentService.ts:3454-3471 `_computeSessions` calls `agent.prewarmSessionMetadata!()` for every provider with any fallback rows, regardless of how many fallback session IDs (here reportedly 47) actually need metadata versus the full SDK catalog (4,858).
- **short-lived cache, no coalescing:** The ref-counted cache (`_prewarmedSessionMetadata`/`_prewarmSessionMetadataRefs`) is cleared as soon as the last concurrent caller releases it, so back-to-back or near-simultaneous `listSessions` computations each re-trigger a fresh full bulk scan rather than sharing or reusing a recent one — matching the reporter's observed back-to-back 16:53:47/16:53:49 duplicate scans.
- **existing unit coverage:** src/vs/platform/agentHost/test/node/copilotAgent.test.ts:5692-5726 'prewarmSessionMetadata cache' only covers the hit/miss/disposal contract with a tiny 2-session catalog, not scan cost or back-to-back coalescing at scale.
- **cited PRs:** Reporter cites the introducing PRs microsoft/vscode#333896 and microsoft/vscode#332410 as where the bulk-prewarm optimization and centralized fallback metadata were added.
