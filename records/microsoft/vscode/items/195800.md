# Issue #195800 — VS Code Crashes from attempts to sign in

[https://github.com/microsoft/vscode/issues/195800](https://github.com/microsoft/vscode/issues/195800)

## Summary

Keep open as the established Linux sign-in freeze report: the thread contains confirmed reproductions, and the linked merged PR added diagnostics rather than fixing the hang. No verified older canonical or concrete post-reopen fix establishes that this work is complete.

## Change summary

Opening Settings Sync sign-in can leave VS Code unresponsive on Linux while accessing the system keyring.

## Best solution

Identify the blocking operation at the secret-storage/Electron safeStorage boundary and make sign-in handle an unavailable or unresponsive keyring without freezing VS Code. Coordinate backend-detection findings with https://github.com/microsoft/vscode/issues/223750, while distinguishing the later system-wide failures from the original application stall.

## Plan brief

- **Likely files:** `src/vs/platform/encryption/electron-main/encryptionMainService.ts`, `src/vs/platform/secrets/common/secrets.ts`, `src/vs/workbench/services/secrets/electron-browser/secretStorageService.ts`
- **Validation:** On a disposable fresh Debian GNOME installation, launch the current build with --disable-extensions --verbose --vmodule="*/components/os_crypt/*=1", then open Backup and Settings Sync and select Sign In. Establish the original failure with the affected keyring setup; after the eventual change, verify the window remains responsive and account selection either proceeds or reports unavailable storage. Repeat with an unlocked working keyring and verify authentication persists across restart.
- **Behavior:**

  > On affected Linux installations, selecting Settings Sync sign-in can stall VS Code at account discovery instead of presenting usable sign-in choices. The finished behavior must keep the application responsive when system-keyring access fails or does not complete, and provide an actionable outcome rather than requiring force quit. Working keyrings must retain normal sign-in and authentication persistence. Basic text encryption is an explicit weaker-storage workaround, not the acceptance criterion for fixing the default path.
- **Trace:**

  > BaseSecretStorageService in src/vs/platform/secrets/common/secrets.ts lazily initializes storage before secret reads and writes, awaiting IEncryptionService.isEncryptionAvailable(). EncryptionMainService in src/vs/platform/encryption/electron-main/encryptionMainService.ts directly invokes synchronous Electron safeStorage operations in the main process. NativeSecretStorageService in src/vs/workbench/services/secrets/electron-browser/secretStorageService.ts handles unavailable encryption after initialization resolves, so that notification path alone does not establish protection against a native stall. The discussion confirms reproduction on fresh Debian; https://github.com/microsoft/vscode/issues/229334 additionally identifies a stall checking encryption. https://github.com/microsoft/vscode/issues/223750 investigates incorrect GNOME_LIBSECRET selection, but its explanation has not been established for all configurations. https://github.com/microsoft/vscode/pull/223784 only adds logging. Diagnosis must first establish the current-build failing call and whether correction belongs in VS Code or Electron/Chromium; preserve working keyring behavior and do not silently weaken encryption or treat the later journal I/O failures as the same proven defect.
