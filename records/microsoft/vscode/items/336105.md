# Issue #336105 — Smart window reuse: seamlessly accept files/folders in multi-root workspace windows from external tools

[https://github.com/microsoft/vscode/issues/336105](https://github.com/microsoft/vscode/issues/336105)

## Summary

Real, partially-existing gap: file opens into a multi-root workspace already reuse the window via resolved-folder matching, but folder opens (CLI `code <folder>`, vscode:// handlers) do not check whether the folder is a root of an already-open workspace, so they still spawn new windows. This is a feature request needing a design decision (default behavior vs. opt-in) before implementation, not a close.

## Change summary

Reuse an open multi-root workspace window when an external tool (CLI, deeplink, IDE integration) targets a file or folder that is one of that workspace's roots.

## Best solution

Extend `findWindowOnWorkspaceOrFolder` in src/vs/platform/windows/electron-main/windowsFinder.ts to also resolve multi-root workspaces and check their folders (mirroring what `findWindowOnFile` already does), so folder-targeted opens reuse the containing workspace window the same way file-targeted opens already do.

- **Trace:**

  > findWindowOnFile already resolves multi-root workspaces and matches sub-folders for file targets (windowsFinder.ts lines 11-33); findWindowOnWorkspaceOrFolder, used for folder/workspace targets from CLI and other entry points in windowsMainService.ts, only compares exact configPath/single-folder URIs and never resolves workspace folders, so folder targets miss the same match. Boundary: don't change single-folder or extension-development-path matching; the fix is scoped to the workspace-folder resolution path.
- **Open decisions:**
  - Should reusing an existing multi-root workspace window for a folder that's already one of its roots be the new default behavior, or an opt-in setting/flag (given the CLI's existing -r/-a/-g override semantics)?
  - Should this resolution also apply uniformly to the vscode://file/... URL handler and IDE-emitted deeplinks, or only to the CLI open path?
  - When a folder is passed that isn't yet a root of the workspace, should VS Code add it to the workspace, or continue opening a new window (i.e., is 'add folder to existing multi-root workspace' in scope for this request)?

## Evidence

- **file case already works:** src/vs/platform/windows/electron-main/windowsFinder.ts findWindowOnFile (lines 11-33) resolves multi-root workspaces via localWorkspaceResolver and matches if any resolved folder is a parent of the target file — this already delivers the 'open file in existing multi-root window' behavior the issue describes.
- **folder case gap remains:** findWindowOnWorkspaceOrFolder (lines 44-60), used for folder/workspace opens (called from windowsMainService.ts around lines 529, 642, 674, 1464-1482), only compares the exact workspace configPath or single-folder URI — it never resolves a multi-root workspace's folders, so opening a folder that is already a root inside an open workspace still creates a new window.
