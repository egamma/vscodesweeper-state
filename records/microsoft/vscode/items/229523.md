# Issue #229523 — Surface find icon in explorer view toolbar

[https://github.com/microsoft/vscode/issues/229523](https://github.com/microsoft/vscode/issues/229523)

## Summary

The discoverability gap remains on current main: Explorer supports a capable find widget, but its title toolbar still exposes New File, New Folder, Refresh, and Collapse All without a Find action. A maintainer explicitly endorsed the request and deferred the Refresh-versus-Find decision to usage data, so this should remain open in the File Explorer backlog.

## Change summary

Expose an icon in the File Explorer title toolbar that opens the Explorer tree's find control, potentially replacing Refresh to avoid clutter.

## Best solution

Expose Explorer Find from the view title toolbar while preserving the established `list.find` behavior and keyboard access. The File Explorer owner should use action telemetry to decide whether Find is additive or replaces the Refresh action.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/browser/actions/listCommands.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Launch the workbench with a folder open, activate the Explorer Find toolbar action, and verify that focus moves to the Explorer and its existing find widget opens; confirm keyboard invocation still works and verify the maintainer-selected Refresh visibility behavior.
- **Behavior:**

  > The File Explorer title toolbar should provide a discoverable Find action that opens the same Explorer tree find widget available from `list.find`. Activating it must target the File Explorer even when another list or tree was most recently focused. Existing keyboard access and find behavior must remain unchanged. The final toolbar must follow the maintainer's decision on whether Refresh remains alongside Find or is replaced.
- **Trace:**

  > Explorer creates its async find provider and tree in src/vs/workbench/contrib/files/browser/views/explorerView.ts, while the generic `list.find` command in src/vs/workbench/browser/actions/listCommands.ts opens Find on `IListService.lastFocusedList`. Explorer title actions are registered in explorerView.ts through `MenuId.ViewTitle`; current main has no Find action there. The action therefore needs a reliable Explorer-targeting flow rather than blindly opening Find on whichever list was last focused. Keep the existing find provider, keyboard bindings, query semantics, and non-Explorer tree behavior unchanged. The broader custom-tree discoverability work remains tracked separately at https://github.com/microsoft/vscode/issues/173742.
- **Open decisions:**
  - Should Find be added alongside Refresh, or replace Refresh in the Explorer title toolbar based on action-usage data?

## Evidence

- **current source:** On current main, src/vs/workbench/contrib/files/browser/views/explorerView.ts:1106-1200 registers New File, New Folder, Refresh, and Collapse All in `MenuId.ViewTitle`; there is no Explorer Find title action.
- **existing capability:** src/vs/workbench/browser/actions/listCommands.ts:861-879 registers `list.find` and opens the focused tree's find widget, currently bound to Ctrl/Cmd+Alt+F and F3. This provides keyboard access but does not satisfy the requested visual discoverability.
- **maintainer direction:** The maintainer comment at https://github.com/microsoft/vscode/issues/229523#issuecomment-2370830735 says a Find toolbar action is reasonable and that usage data should inform whether Refresh is removed.
- **canonical status:** The later Explorer-specific request https://github.com/microsoft/vscode/issues/239060 was closed as a duplicate of this issue, reinforcing https://github.com/microsoft/vscode/issues/229523 as the canonical Explorer request.
- **related broader request:** https://github.com/microsoft/vscode/issues/173742 is older and requests discoverable Find controls for custom/contributed trees through `TreeViewOptions`; it is related but does not fully own the built-in File Explorer toolbar decision tracked here.
