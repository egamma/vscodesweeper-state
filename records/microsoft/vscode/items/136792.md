# Issue #136792 — Allow Run To Cursor to start debug session

[https://github.com/microsoft/vscode/issues/136792](https://github.com/microsoft/vscode/issues/136792)

## Summary

This remains a valid backlog feature request with 21 community upvotes. The macro workaround was explicitly described by the debug maintainer as imperfect and does not reliably provide the requested state-aware Run to Cursor behavior.

## Change summary

Allow Run to Cursor to start a debug session when no session is active, while retaining normal Run to Cursor behavior during an active session.

## Best solution

Extend the core debug Run to Cursor flow so an invocation without an active session starts the selected launch configuration and then runs to the requested source location, without issuing another start when debugging is already active.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugEditorActions.ts`, `src/vs/workbench/contrib/debug/browser/debugService.ts`
- **Validation:** Add debug workbench tests covering Run to Cursor with no active session and with an active stopped session; verify the former starts exactly one session and reaches the requested source location, while the latter preserves existing behavior.
- **Behavior:**

  > Invoking Run to Cursor with no active debug session starts debugging and stops at the selected executable source location. Invoking it during an active session keeps the existing Run to Cursor behavior and must not attempt to start a second session. Cancellation or startup failure must not leave persistent temporary breakpoints or alter later debug runs.
- **Trace:**

  > The request concerns the core `editor.debug.action.runToCursor` action in `src/vs/workbench/contrib/debug/browser/debugEditorActions.ts`, coordinated with debug-session startup through the debug service. The existing command-macro workaround sequences `workbench.action.debug.start` and Run to Cursor without owning debugger state or a reliable startup-to-target handoff; the maintainer explicitly characterized it as temporary in https://github.com/microsoft/vscode/issues/136792#issuecomment-965187467. Keep existing behavior for active sessions and avoid C++-specific handling because this is a core debug action shared by debug adapters. The unresolved boundary is how core represents and cleans up the initial cursor target while a session is being launched.
- **Open decisions:**
  - Should starting Run to Cursor use a temporary source breakpoint that is removed after the first stop, or require a debug-adapter-facing run-to-location contract during launch?
  - When several launch configurations are available, should Run to Cursor follow the normal Start Debugging selection flow or only use an already selected configuration?
