# Issue #129139 — Automatic disambiguation of file extensions

[https://github.com/microsoft/vscode/issues/129139](https://github.com/microsoft/vscode/issues/129139)

## Summary

Keep open: current language detection does not automatically disambiguate competing file-extension associations. This accepted Backlog request needs a product decision about conflict resolution, not a staleness close.

## Change summary

Determine the appropriate language for files whose extensions identify multiple languages, without requiring duplicated per-repository configuration.

## Best solution

Extend language selection to resolve ambiguous registered associations while preserving explicit user choices. Agree on the role of content detection, workspace history, and repository language metadata before implementation.

## Plan brief

- **Likely files:** `src/vs/editor/common/services/languagesAssociations.ts`, `src/vs/workbench/services/language/common/languageService.ts`, `src/vs/workbench/services/textfile/common/textFileEditorModel.ts`, `src/vs/workbench/services/languageDetection/browser/languageDetectionWorkerServiceImpl.ts`, `src/vs/workbench/browser/parts/editor/editorStatus.ts`
- **Validation:** After agreeing on behavior, add association and text-file-model tests with two registered languages sharing an extension and representative content for each. Verify the agreed selection, explicit files.associations and manual language-choice precedence, unchanged unambiguous associations, and deterministic handling of low-confidence content. If repository metadata is included, test its agreed precedence separately.
- **Behavior:**

  > Files sharing an extension across different languages should receive the appropriate language without requiring a new files.associations entry in every repository. The report includes MATLAB versus Objective-C .m files and Reason versus C++ .re files, and commenters also request reuse of .gitattributes language metadata. Acceptance must cover representative conflicting files, preserve explicit user associations and manual selections, and leave ordinary unambiguous files unchanged. The user-visible fallback for inconclusive detection remains to be decided.
- **Trace:**

  > In src/vs/editor/common/services/languagesAssociations.ts, getAssociations prioritizes configured mappings and getAssociationByPath resolves equal extension matches by registration order rather than content. TextFileEditorModel.autoDetectLanguage in src/vs/workbench/services/textfile/common/textFileEditorModel.ts excludes files with extensions or an already assigned non-plaintext language. LanguageDetectionWorkerClient.detectLanguage in src/vs/workbench/services/languageDetection/browser/languageDetectionWorkerServiceImpl.ts also returns a filepath quick guess before content inference, despite the service already supporting workspace/history biases. The Auto Detect picker branch in src/vs/workbench/browser/parts/editor/editorStatus.ts similarly favors filepath associations. Preserve existing explicit-choice precedence and avoid adding broad workspace scanning or retraining requirements without a product decision. The maintainer requested this separate work in https://github.com/microsoft/vscode/issues/129004#issuecomment-884577098; https://github.com/microsoft/vscode/issues/315199 is a related metadata request, not a duplicate canonical. The uncertainty starts at whether conflicts should be resolved automatically and how inconclusive results and repository metadata should affect selection.
- **Open decisions:**
  - When registered file associations conflict, should content detection automatically choose the language on open, or should VS Code require user confirmation?
  - When detection is inconclusive, should VS Code retain the current association silently or present the competing languages for selection?
  - Should .gitattributes language overrides be part of this feature, and if so, what precedence should they have relative to content detection and explicit files.associations?
