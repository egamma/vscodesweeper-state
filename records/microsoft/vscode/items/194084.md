# Issue #194084 — `task.json` -> `options.env` not working of `${env:VAR}` expansion

[https://github.com/microsoft/vscode/issues/194084](https://github.com/microsoft/vscode/issues/194084)

## Summary

Keep open for a tasks-owner decision: current source and documentation exclude options.env from task-variable substitution, so this requests an enhancement rather than demonstrating a regression. The owner has accepted it as work and consolidated other reports here; neither a fix nor an older open canonical covering this symptom was established.

## Change summary

Allow task command and argument ${env:VAR} references to resolve variables supplied through options.env.

## Best solution

Define task-local environment substitution semantics in the tasks area, including precedence and compatibility with inherited-environment references, then implement and document the agreed behavior. Preserve this issue as the existing consolidation point rather than redirecting it to the unrelated C/C++ parser fix.

- **Validation:** Run a shell task with command echo, args containing ${env:HELLO}, and options.env.HELLO set to vscode!, while HELLO is absent from the launching environment; the accepted behavior should print the configured value. Add executable coverage for the agreed precedence rules and verify that options.env.PATH containing ${env:PATH} still supports inherited-PATH extension, parent-only variables still resolve, and task-local values do not leak between tasks.
- **Behavior:**

  > The reporter wants a variable defined in task options.env to be usable through ${env:VAR} in the task command and arguments. Today the child process receives the variable, but VS Code substitutes an empty string when the variable is absent from its resolution environment. Acceptance should cover the supplied HELLO example, inherited variables, and isolation between tasks. The new contract must explicitly address name collisions and existing environment-extension expressions.
- **Trace:**

  > TerminalTaskSystem._resolveVariablesFromSet in src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts resolves collected placeholders without supplying options.env; _resolveOptions and shellLaunchConfig construction apply that environment separately. AbstractVariableResolverService.evaluateSingleVariable in src/vs/workbench/services/configurationResolver/common/variableResolver.ts reads its supplied or captured process environment and returns an empty string for missing env variables. MainThreadTask and the node ExtHostTask also resolve variables without a task-local environment. This source trace establishes the reported limitation, but the public tasks documentation explicitly describes it as current behavior. Preserve inherited-environment substitution, shell quoting, unrelated resolver consumers, and task isolation. The maintainer has consolidated https://github.com/microsoft/vscode/issues/181800 and https://github.com/microsoft/vscode/issues/246175 here; the global-versus-task environment merging report is related evidence, not proof of the same root cause. Planning must settle the compatibility contract before changing this shared resolution flow.
- **Open decisions:**
  - When options.env and the inherited environment define the same name, should ${env:VAR} in commands and arguments use the task-local value or preserve the inherited value?
  - Should ${env:VAR} inside options.env values continue to read only the inherited environment, preserving expressions such as PATH=${env:PATH}:extra, or also resolve other task-local entries?
