# Issue #289502 — Adopt new `ChatSessionItem.timing` shape for cli sessions

[https://github.com/microsoft/vscode/issues/289502](https://github.com/microsoft/vscode/issues/289502)

## Summary

Keep open: the CLI session service supplies `created` but still emits deprecated `startTime` and `endTime` instead of distinct last-request timestamps. Runtime compatibility preserves consumption of these items, but does not complete the requested migration.

## Change summary

Adopt `created`, `lastRequestStarted`, and `lastRequestEnded` with their documented lifecycle semantics for Copilot CLI session items.

## Best solution

Complete timing adoption in the bundled Copilot CLI session service, distinguishing session creation from the latest request's start and completion. Preserve an undefined completion timestamp while that request is running and undefined request timestamps before any request.

## Evidence

Live-wrapper paths at lines 523 and 561 and the fork notification at line 1081 also use deprecated startTime. None of these item construction paths populates lastRequestStarted or lastRequestEnded.
- **Documented timing contract:** src/vscode-dts/vscode.proposed.chatSessionsProvider.d.ts:357-389 defines created as session creation time, lastRequestStarted as the latest request start, and lastRequestEnded as the latest request completion. Request timestamps are undefined before any request, and lastRequestEnded is undefined while the latest request remains in progress; startTime and endTime remain deprecated compatibility fields.
- **Compatibility is not semantic migration:** src/vs/workbench/api/common/extHostTypeConverters.ts:4315-4333 falls back from lastRequestStarted to startTime and from lastRequestEnded to endTime. This accepts legacy CLI items but cannot recover distinct request timestamps from session creation and modification timestamps.
