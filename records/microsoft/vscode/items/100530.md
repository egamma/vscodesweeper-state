# Issue #100530 — Symbol occurrence highlighting overlaps occurrences of the selected text

[https://github.com/microsoft/vscode/issues/100530](https://github.com/microsoft/vscode/issues/100530)

## Summary

The color collision was partially addressed in 2022, but the central layering defect remains on current main: document highlights render after the active selection and can obscure it. Keep this open for an editor-rendering decision and regression coverage.

## Change summary

Ensure symbol-occurrence highlights do not obscure the active selection or make selection matches indistinguishable from semantic matches.

## Best solution

Preserve semantic document highlighting while ensuring the active selection and textual selection occurrences remain visually distinguishable when ranges overlap. The editor-rendering owners should choose a targeted precedence mechanism that does not disturb unrelated decorations or whitespace rendering.

## Plan brief

- **Likely files:** `src/vs/editor/browser/view.ts`, `src/vs/editor/browser/viewParts/selections/selections.css`, `src/vs/editor/browser/viewParts/decorations/decorations.css`, `src/vs/editor/contrib/wordHighlighter/browser/highlightDecorations.css`
- **Validation:** Add an editor rendering test with an opaque active-selection color and an overlapping `DocumentHighlightKind.Text` decoration, asserting that the selected range remains visibly on top while non-overlapping document highlights and selection occurrences retain their respective styles.
- **Behavior:**

  > When an extension returns a document highlight overlapping the active selection, the selected range must remain clearly visible. Selection occurrences and semantic or textual document highlights must remain distinguishable, including with opaque configured colors. Non-overlapping highlights, read/write highlight distinctions, whitespace decorations, and inactive selections must retain their existing behavior.
- **Trace:**

  > ContentViewOverlays in src/vs/editor/browser/view.ts adds SelectionsOverlay before DecorationsOverlay, causing the decoration output to follow the selection output. The corresponding `.cslr` and `.cdr` rules in src/vs/editor/browser/viewParts/selections/selections.css and src/vs/editor/browser/viewParts/decorations/decorations.css do not override that stacking order. Commit 376af084af1ef6ebf35cc1176dca84768aaf42d7 introduced dedicated `DocumentHighlightKind.Text` colors in src/vs/editor/contrib/wordHighlighter/browser/highlightDecorations.ts, resolving the identical-color portion but not overlapping precedence. The boundary is selection-versus-highlight compositing; unrelated editor overlays and extension-provided ranges must not change.
- **Open decisions:**
  - Should precedence be changed for the entire selections overlay or only for word/document-highlight decorations that overlap an active selection?
  - Should textual selection occurrences also outrank semantic document highlights, or should only the active selection do so?
  - How should the chosen stacking rule preserve whitespace, diagnostics, search matches, and other decoration layers?

## Evidence

- **current render order:** src/vs/editor/browser/view.ts registers SelectionsOverlay before DecorationsOverlay in ContentViewOverlays, so overlapping `.cdr` document decorations are emitted after `.cslr` selection elements.
- **current styling:** src/vs/editor/browser/viewParts/selections/selections.css and src/vs/editor/browser/viewParts/decorations/decorations.css provide no stacking rule that raises the active selection above document decorations; this matches the working CSS override reported in https://github.com/microsoft/vscode/issues/100530#issuecomment-2465135129.
- **partial mitigation:** Commit 376af084af1ef6ebf35cc1176dca84768aaf42d7 (https://github.com/microsoft/vscode/commit/376af084af1ef6ebf35cc1176dca84768aaf42d7) added `editor.wordHighlightTextBackground` and `editor.wordHighlightTextBorder`, separating `DocumentHighlightKind.Text` colors from selection-occurrence colors, but did not change selection precedence.
- **confirmed scope:** Multiple commenters confirmed the overlap, including a report that it affects languages beyond C/C++; the maintainer discussion also identified VS Code's mapping and rendering of `DocumentHighlightKind.Text` as the relevant core behavior.
