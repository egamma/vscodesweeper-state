# Issue #162099 — Could we avoid this prompt on the Desktop side?

[https://github.com/microsoft/vscode/issues/162099](https://github.com/microsoft/vscode/issues/162099)

## Summary

The requested web-to-desktop account handoff remains missing: Continue Working On passes the edit-session reference, but not the source authentication identity. Keep this accepted, team-authored request open; the related account-mismatch issue does not meet the re-review requirement of the same observable symptom.

## Change summary

Avoid asking users to remember and reselect their web Cloud Changes authentication provider and account when continuing on desktop.

## Best solution

Make desktop continuation use the source authentication identity to avoid redundant account selection where possible, while retaining necessary sign-in and consent. Define the behavior when desktop already uses a different Cloud Changes account before implementing the handoff.

Repeat with multiple available accounts, a different desktop Cloud Changes account, cancellation, and a legacy continuation URL without identity information.
- **Behavior:**

  > Continuing from web to desktop with working changes should not require remembering which provider and account were used for Cloud Changes on web. Desktop should retain enough source identity context to avoid redundant selection where possible, while still performing necessary authentication and consent. Acceptance must cover multiple accounts, cancellation, legacy links, and a desktop already configured with a different identity. The behavior of that conflicting-account case requires a product decision.
- **Trace:**

  > In src/vs/workbench/contrib/editSessions/browser/editSessions.contribution.ts, the Continue Working On action builds the destination URI with editSessionId and continueOn but no source identity. autoResumeEditSession initiates destination restoration or authentication. EditSessionsWorkbenchService.getAuthenticationSession in src/vs/workbench/contrib/editSessions/browser/editSessionsStorageService.ts uses local preferences and otherwise opens getAccountPreference; its Settings Sync bootstrap is web-only. IEditSessionsStorageService in src/vs/workbench/contrib/editSessions/common/editSessions.ts has no identity-handoff contract. The desktop protocol handler in src/vs/code/electron-main/app.ts handles continueOn, and environment contracts expose the existing continuation fields. Preserve normal authentication, explicit consent, cancellation, and legacy-link behavior; this is not credential transfer or continuous synchronization. https://github.com/microsoft/vscode/issues/162025 supplies related account-mismatch evidence, not a verified duplicate under the re-review rule.
- **Open decisions:**
  - When desktop already has Cloud Changes enabled with a different account, should continuation preserve that preference and request an explicit switch, or use the source identity for this restoration?
  - For a desktop with Cloud Changes disabled, does the explicit web-to-desktop continuation authorize destination enablement after authentication, or must desktop retain a separate enablement confirmation?
