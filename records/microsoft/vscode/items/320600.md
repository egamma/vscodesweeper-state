# Issue #320600 — Copilot Chat activation delayed 80-120s in WSL remote due to `onDidChangeSessions` IPC proxy latency

[https://github.com/microsoft/vscode/issues/320600](https://github.com/microsoft/vscode/issues/320600)

## Summary

The remote-startup delay is credibly reproduced in both WSL and Remote-SSH, and current main still has activation blockers that can wait on authentication initialization. The proposed event-only root cause is incomplete, so this needs diagnosis across the Copilot authentication and VS Code authentication-proxy paths rather than closure.

## Change summary

Copilot Chat activation waits 80–120 seconds for authentication during cold startup in remote extension hosts.

## Best solution

Identify which authentication RPC or token-bootstrap operation stalls in remote extension hosts, then ensure Copilot Chat activation is not blocked for minutes while cached GitHub authentication becomes available. Preserve normal sign-in, account-change, token-refresh, and BYOK behavior.

Sign-in, sign-out, account switching, token refresh, and BYOK-only startup must retain their current behavior. Keep unrelated authentication semantics and non-remote startup behavior out of scope. Related evidence is in https://github.com/microsoft/vscode/issues/319710 and https://github.com/microsoft/vscode/issues/321626.

## Evidence

- **confirmed symptom:** The issue includes timestamped WSL logs showing both activation blockers delayed about 84–85 seconds, and https://github.com/microsoft/vscode/issues/320600#issuecomment-4938440525 independently confirms the same behavior with Remote-SSH between Linux machines.
- **current Copilot path:** extensions/copilot/src/platform/authentication/vscode-node/authenticationService.ts still starts `_handleAuthChangeEvent()` during construction; extensions/copilot/src/platform/authentication/common/authentication.ts then awaits silent GitHub-session lookups before minting the Copilot token.
- **activation remains blocking:** extensions/copilot/src/extension/conversation/vscode-node/languageModelAccess.ts keeps an `activationBlocker` that awaits `_registerEmbeddings()`, whose initial update awaits `_authenticationService.getCopilotToken()`.
- **diagnosis conflict:** The reported build commit 6a44c352bd24569c417e530095901b649960f9f8 already called `_handleAuthChangeEvent()` proactively at startup and performed silent session requests, so waiting solely for `onDidChangeSessions` does not fully explain the delay and the suggested proactive lookup was already present.
- **platform proxy path:** src/vs/workbench/api/common/extHostAuthentication.ts routes `getAccounts` and `getSession` through `MainThreadAuthentication`; `$ensureProvider` in src/vs/workbench/api/browser/mainThreadAuthentication.ts may first activate the authentication provider.
- **related report:** https://github.com/microsoft/vscode/issues/319710 is older and reports the same observable startup delay, including logs from this issue's author, but it was closed as completed without a cited fixing commit and later received a report that the delay returned in 1.125.0. Because it is closed, it cannot be the canonical target for a duplicate close.
- **related authentication timeout:** https://github.com/microsoft/vscode/issues/321626 tracks widespread timeouts while registering the GitHub authentication provider, but it is newer than this re-reviewed issue and reports a different observable error, so it does not meet the stronger duplicate bar.
