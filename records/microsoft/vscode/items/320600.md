# Issue #320600 — Copilot Chat activation delayed 80-120s in WSL remote due to `onDidChangeSessions` IPC proxy latency

[https://github.com/microsoft/vscode/issues/320600](https://github.com/microsoft/vscode/issues/320600)

## Summary

Well-investigated activation-latency bug in remote (WSL/SSH) scenarios. The Copilot authentication flow passively waits for `onDidChangeSessions` IPC events that are delayed 80-120s when proxied from the local to remote extension host. The proactive `_handleAuthChangeEvent()` call at construction time also goes through IPC and stalls. A second reporter confirms the same symptom over SSH. Related issue #319710 focused on Claude SDK cold-start, a different root cause — this report isolates the auth-event proxy path and remains actionable.

## Change summary

Copilot Chat activation is blocked 80-120s in WSL/SSH remote workspaces because the `onDidChangeSessions` event and the initial `authentication.getSession` call are delayed by IPC proxy latency between the local and remote extension hosts.

## Best solution

The Copilot extension's `AuthenticationService` (in `extensions/copilot/src/platform/authentication/vscode-node/authenticationService.ts`) should not rely solely on the proxied `onDidChangeSessions` event for initial activation. Either (a) proactively call `vscode.authentication.getSession('github', scopes, { silent: true })` with a retry/timeout in the constructor to unblock activation faster, or (b) the VS Code platform (`src/vs/workbench/api/browser/mainThreadAuthentication.ts`) should eagerly forward cached sessions to remote extension hosts as part of the extension host initialization handshake, before extensions start activating. The fix likely spans both the Copilot extension auth layer and the platform's remote auth forwarding.

## Evidence

- **code path traced:** `extensions/copilot/src/platform/authentication/vscode-node/authenticationService.ts` line 27-40: constructor subscribes to `authentication.onDidChangeSessions` (IPC-proxied in remote) and calls `_handleAuthChangeEvent()` which calls `getGitHubSession('any', { silent: true })` — both go through IPC to the main thread when running in a remote extension host.
- **activation blocker:** `extensions/copilot/src/extension/conversation/vscode-node/conversationFeature.ts` line 87-106: `activationBlocker` promise blocks extension activation until `copilotToken` is available, which depends on the auth event arriving.
- **IPC proxy path:** `src/vs/workbench/api/browser/mainThreadAuthentication.ts` line 144: `onDidChangeSessions` fires `$onDidChangeAuthenticationSessions` to the ext host proxy; in remote scenarios this crosses the IPC bridge between local and remote extension hosts.
- **second reporter:** Comment by patroza confirms the same issue over SSH (Linux-to-Linux), ruling out WSL-specific causes.
- **related issue (different root cause):** https://github.com/microsoft/vscode/issues/319710 was closed as completed but focused on Claude SDK/`listSessions` cold start, not the auth-event IPC latency described here. A team member noted it may duplicate https://github.com/microsoft/vscode/issues/321901 (extension host unresponsive), suggesting the underlying issue is not fully resolved.
- **reporter's logs:** Output logs show `activationBlocker from 'languageModelAccess' took for 84285ms` and `activationBlocker from 'conversationFeature' took for 85187ms`, with the actual token fetch completing in ~1.2s once the event arrives — confirming the delay is IPC delivery, not network.
