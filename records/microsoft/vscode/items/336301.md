# Issue #336301 — Agent executes thousands of tool calls from one model response without a per-response limit

[https://github.com/microsoft/vscode/issues/336301](https://github.com/microsoft/vscode/issues/336301)

## Summary

Keep open: the reporter reproduced the runaway batch three times, and current main still has no response-level tool-call guard before thousands of requests are recorded and rendered. The limit and rejection semantics need coordination with the bundled Copilot runtime before implementation.

## Change summary

Bound the number of tool calls accepted from one model response so a pathological batch cannot consume resources and flood Chat with thousands of rows.

## Best solution

Enforce a response-level bound in the Copilot runtime before tool dispatch, terminate an oversized batch with a clear recoverable turn error, and keep transcript reconstruction and Chat rendering bounded. A maintainer should first settle the threshold and whether an oversized response is rejected entirely or partially accepted.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts`, `src/vs/platform/agentHost/node/copilot/mapSessionEvents.ts`, `src/vs/platform/agentHost/test/node/copilotAgentSession.test.ts`, `extensions/copilot/src/extension/chatSessions/vscode-node/taskTurnStreamer.ts`, `extensions/copilot/src/extension/chatSessions/vscode-node/test/copilotCloudSessionsProvider.spec.ts`, `package.json`, `package-lock.json`
- **Validation:** Use a deterministic Copilot provider/runtime test that returns one assistant response containing limit+1 tool requests; assert that execution starts no more than the accepted bound, the turn reports one recoverable oversized-response error, and transcript/UI reconstruction remains bounded rather than producing one row per rejected request.
- **Behavior:**

  > A single model response cannot schedule an unbounded number of tool calls. When a response exceeds the supported bound, VS Code stops the batch before excessive execution, presents one clear recoverable error, and remains responsive without rendering thousands of tool rows. Ordinary parallel tool batches, valid history replay, cancellation, and subsequent turns continue to work. Acceptance requires a deterministic oversized-response test that proves both execution and rendered output are bounded.
- **Trace:**

  > The reporter observed 3,871 memory requests in one assistant.message and confirmed the behavior three times. In src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts, assistant.message handling counts and iterates the complete toolRequests array without enforcing a bound; live tool execution is surfaced later through CopilotSessionWrapper.onToolStart, after the @github/copilot runtime has begun each call. src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts supplies SessionConfig to the pinned SDK but currently has no response-level tool-call policy. History reconstruction in src/vs/platform/agentHost/node/copilot/mapSessionEvents.ts and eager rendering in extensions/copilot/src/extension/chatSessions/vscode-node/taskTurnStreamer.ts also iterate every request, so rejected batches must remain bounded during replay as well as live execution. Preserve normal multi-turn limits and ordinary parallel calls; do not make memory-specific path heuristics the only protection.
- **Open decisions:**
  - What maximum number of tool calls may one assistant response contain, and should the bound be universal or vary for trusted internal tool classes?
  - When the bound is exceeded, should the entire response be rejected before execution or should a bounded prefix execute?
  - Should the transcript preserve metadata about every rejected request, or record one summarized oversized-batch error to keep persistence and rendering bounded?

## Evidence

- **confirmed reproduction:** The issue records one assistant response containing 3,871 memory requests, 3,870 executions, nearly 14 minutes of activity, and 2,253 reads of nonexistent synthesized paths; later comments report two additional reproductions, including a possible daily Insiders regression and elevated token usage.
- **current source:** src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts processes assistant.message.toolRequests without a length guard, adds the entire array length to telemetry, and iterates every request; SDK tool.execution_start events are observed only after the bundled runtime has started execution.
- **rendering path:** extensions/copilot/src/extension/chatSessions/vscode-node/taskTurnStreamer.ts eagerly iterates every assistant.message.toolRequests entry and creates a separate response part for each previously unseen toolCallId.
- **launch boundary:** src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts builds the @github/copilot-sdk SessionConfig but exposes no per-response tool-call limit or interception policy; package.json pins @github/copilot-sdk, so preventing dispatch likely requires a runtime contract rather than only suppressing UI events.
- **no current fix:** Current main contains no tool-request count guard in the Copilot session, event-mapping, launcher, or task-stream rendering paths, and post-report history contains no relevant fix.
