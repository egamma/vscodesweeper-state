# Issue #88219 — API to programatically expand/collapse tree view

[https://github.com/microsoft/vscode/issues/88219](https://github.com/microsoft/vscode/issues/88219)

## Summary

Keep open: current TreeView APIs still lack control over collapsing the contributed view itself. Existing expansion commands and initial-visibility settings cover only parts of the request; 56 upvotes and maintainer confirmation on a related report support API design work.

## Change summary

Allow extensions to programmatically expand and collapse their contributed tree-view panes, independently of tree-item expansion.

## Best solution

Provide an explicitly designed TreeView API for pane expansion and collapse without hiding or disposing the view. Settle the public API contract with the API owners, then integrate it with the existing pane lifecycle and layout behavior.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTreeViews.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadTreeViews.ts`, `src/vs/workbench/browser/parts/views/viewPaneContainer.ts`, `src/vs/workbench/api/test/browser/extHostTreeViews.test.ts`, `src/vs/workbench/api/test/browser/mainThreadTreeViews.test.ts`
- **Validation:** In an Extension Development Host, contribute two tree views to one container and invoke the approved API to collapse and re-expand one pane. Confirm that collapse retains its header, releases body space to the sibling, does not dispose the view or change tree-item expansion, and expansion restores its contents. Cover the approved API forwarding contract in the existing extHostTreeViews and mainThreadTreeViews suites, including an empty tree.
- **Behavior:**

  > Extensions need to collapse and re-expand their own contributed tree-view panes as their relevance changes. Collapse must retain the pane header rather than hide or dispose the view, and must be distinct from collapsing tree items. Acceptance should exercise two sibling views, verify that collapsing one releases space to the other, and verify restoration for both populated and empty trees.
- **Trace:**

  > TreeView in src/vscode-dts/vscode.d.ts and the object returned by ExtHostTreeViews.createTreeView expose no pane-collapse operation. MainThreadTreeViews.$reveal and the generated `${viewId}.focus` command open views; ViewPaneContainer.openView explicitly expands the target pane. The contribution-point visibility setting controls initial state only, while when clauses control inclusion rather than collapse. ViewPaneContainer already tracks expansion through setExpanded and persists collapse changes, with special single-view and merged-header behavior. Keep tree-item expansion, existing visibility semantics, and unrelated container behavior unchanged. The remaining design uncertainty is the new public API contract, not whether the existing surface fully covers this request. https://github.com/microsoft/vscode/issues/203344 is related command-surface work, not a replacement canonical for this older API request.
- **Open decisions:**
  - Should pane expansion control be exposed as an awaitable TreeView operation or as a writable expansion-state property?

## Evidence

- **Public API gap:** src/vscode-dts/vscode.d.ts:12144–12238 exposes readonly TreeView.visible, visibility events, element expansion events, and reveal(), but no operation or writable state for collapsing the view pane. src/vs/workbench/api/common/extHostTreeViews.ts:createTreeView likewise exposes no pane-collapse operation.
- **Existing capabilities are partial:** src/vs/workbench/services/views/browser/viewsService.ts:registerFocusViewAction registers `${viewId}.focus`, including preserveFocus support, and opens the view. MainThreadTreeViews.$reveal in src/vs/workbench/api/browser/mainThreadTreeViews.ts also opens the view. These support expansion, not the requested collapse. TreeView.reveal's expand option and the generated collapseAll action concern tree items, not the pane.
- **Initial state and conditional visibility are not runtime collapse:** src/vs/workbench/api/browser/viewsExtensionPoint.ts:141–165 registers contributes.views[].when and visibility. The latter explicitly controls initial installation state and stops applying after user changes; when controls whether a view is shown. Neither provides runtime pane collapse while retaining its header.
- **Existing pane machinery and boundary:** src/vs/workbench/browser/parts/views/viewPaneContainer.ts:openView calls view.setExpanded(true); onDidAddViewDescriptors records pane expansion changes through viewContainerModel.setCollapsed. updateViewHeaders also enforces special behavior for single-view and merged-header containers, which API design must account for rather than treating every pane as independently collapsible.
- **Maintainer confirmation and demand:** The supplied issue has 56 upvotes, an On Deck holding milestone, and a Docker-extension use case. In https://github.com/microsoft/vscode/issues/148875#issuecomment-1119360563, a maintainer explicitly says this API request must be addressed before an extension can implement button-triggered pane collapse.
