# Issue #185515 — files.Readonly has weak graphical support

[https://github.com/microsoft/vscode/issues/185515](https://github.com/microsoft/vscode/issues/185515)

## Summary

The graphical gap remains on current main: Explorer knows whether an item is read-only, but neither its built-in decorations nor the file-icon-theme schema exposes that state visually. The existing file-explorer and ux routing is appropriate, so this should stay open while the visual and extension-contract design is settled.

## Change summary

Make files and folders configured as read-only visually distinguishable in Explorer when a file icon theme is active.

## Best solution

Provide a consistent, accessible read-only indication in Explorer that works with file icon themes, while deciding whether themes may customize that indication or VS Code should render one universal decoration.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerDecorationsProvider.ts`, `src/vs/workbench/contrib/files/common/explorerModel.ts`, `src/vs/workbench/services/themes/common/fileIconThemeSchema.ts`, `src/vs/workbench/services/themes/browser/fileIconThemeData.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Add Explorer decoration or file-icon-theme loader tests for a resource matched by files.readonlyInclude, then verify the chosen read-only treatment appears with both the default icons and a contributed file icon theme without changing writable-resource rendering.
- **Behavior:**

  > A file or folder that VS Code considers read-only is visibly distinguishable from writable siblings in Explorer even when a contributed file icon theme is enabled. The indication must cover effective read-only state from configuration and file-system providers, remain understandable without relying solely on color, and leave writable resources unchanged. The chosen behavior should remain consistent for collapsed and expanded folders.
- **Trace:**

  > ExplorerItem.isReadonly in src/vs/workbench/contrib/files/common/explorerModel.ts already computes the effective state through IFilesConfigurationService. Explorer rendering enables file decorations in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts, but provideDecorations in explorerDecorationsProvider.ts never inspects isReadonly. Separately, the schema and CSS generation in src/vs/workbench/services/themes/common/fileIconThemeSchema.ts and browser/fileIconThemeData.ts have selectors for names, extensions, languages, and folder expansion, but no read-only selector or association. The public FileDecorationProvider can add a badge or color programmatically, but it does not make effective read-only state available to declarative icon themes. Keep the boundary to Explorer presentation and theming; editor read-only enforcement and delete confirmations already exist and should not change.
- **Open decisions:**
  - Should read-only state use one VS Code-owned Explorer decoration across every icon theme, or become a file-icon-theme association that theme authors can customize?
  - What visual treatment should represent read-only state while remaining accessible and composable with existing SCM and file decorations: a badge, icon variant, label treatment, or a defined combination?

## Evidence

- **current source gap:** src/vs/workbench/contrib/files/common/explorerModel.ts exposes ExplorerItem.isReadonly, but src/vs/workbench/contrib/files/browser/views/explorerDecorationsProvider.ts only decorates root errors, symbolic links, unknown items, and excluded items; it does not represent read-only state.
- **icon-theme limitation:** src/vs/workbench/services/themes/common/fileIconThemeSchema.ts supports associations by folder name, file name, extension, language, and expanded/root state, but has no association for read-only resources.
- **partial existing API:** src/vscode-dts/vscode.d.ts exposes FileDecorationProvider for programmatic badges, tooltips, and colors, but declarative icon themes cannot discover or associate icons with VS Code's effective read-only state, including provider and files.readonlyInclude results.
- **related extension report:** The reporter linked https://github.com/material-extensions/vscode-material-icon-theme/issues/2003 as evidence that an icon-theme author cannot express the requested state.
- **canonical search:** Repository issue searches for read-only folder icons and Explorer read-only decorations found no older open issue with the same observable symptom, so the stronger re-review duplicate bar is not met.
