# Issue #336440 — Allow configuring the maximum number of concurrent subagents

[https://github.com/microsoft/vscode/issues/336440](https://github.com/microsoft/vscode/issues/336440)

## Summary

Genuine, well-documented gap: VS Code has no setting to raise the hard-coded subagent concurrency cap, and two independent reporters (one BYOK, one Copilot Free) confirm the limit blocks common parallel-workflow patterns on current Stable (1.138/1.139). No fix exists on main, so this stays open as a feature request.

## Change summary

Add a setting to configure the maximum number of concurrently running subagents, which is currently a hard-coded, unconfigurable cap.

## Best solution

Surface a `chat.subagents.maxConcurrent`-style setting in the Agent Host chat contribution (alongside the existing `chat.subagents.*` settings in chat.shared.contribution.ts), wired through to whatever limiter the active provider SDK exposes — but this needs a design decision first, since the actual concurrency gate for the Copilot provider lives in the external copilot-sdk/runtime (not this repo) and is currently tied to GitHub plan tier rather than model provider.

## Vision fit

- **Reason:** Reducing artificial friction in agentic/subagent workflows is a concrete piece of the project's AI-assisted-development and developer-inner-loop investment, and a configurable limit (rather than a fixed 4) is a small, well-scoped extension of the existing `chat.subagents.*` settings surface.
- **Evidence:** Durable theme: AI-assisted development has grown into the project's center of gravity; durable theme: developer inner loop (editor, terminal, testing, debugging) includes agentic tooling ergonomics.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/constants.ts`, `src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts`, `src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts`, `src/vs/platform/agentHost/common`
- **Validation:** A test asserting a new chat.subagents.maxConcurrent (or equivalent) setting value is read and forwarded into the provider session configuration used to start an Agent Host session.
- **Behavior:**

  > Users should be able to raise (within a documented ceiling) the number of subagents that can run concurrently under a single agent tree, via a setting rather than a fixed value of 4. Setting a higher value should let a workflow like '5 parallel workers, each with a helper' proceed without the 'Maximum concurrent agent limit reached' rejection, for every model provider (including BYOK), not just Copilot-billed ones.
- **Trace:**

  > The rejection message and cap the issue reports do not originate in this repo: no TaskRegistry/subAgentLimiter/maxConcurrent symbols exist under src/vs/platform/agentHost or src/vs/workbench/contrib/chat, and the second commenter traced the real gate to `configureSubAgentLimiter` inside the bundled @github/copilot-sdk runtime, apparently driven by GitHub plan tier rather than the selected model provider. The only settings VS Code currently owns for subagents are in chat.shared.contribution.ts (allowInvocationsFromSubagents, defaultToAuto, useRichRendering, showCreditUsage) and the hard-coded RUN_SUBAGENT_MAX_NESTING_DEPTH=5 in runSubagentTool.ts — there is no maxDepth setting today despite the issue's claim. Do not conflate the depth constant with a concurrency limiter; they are unrelated mechanisms. Related: https://github.com/microsoft/vscode/issues/288048 (Live Subagents Panel — a different UI-visibility ask, not a canonical for this concurrency request).
- **Open decisions:**
  - Should VS Code expose a user-facing setting even though today's actual limiter lives in the external copilot-sdk runtime and is gated by GitHub plan tier — i.e., does this require coordinating a change in that external repo before a VS Code setting would have any effect?
  - Should the limit be global/process-wide, per-session, or per-agent-tree, and should it apply uniformly across all providers (Claude, Codex, Copilot) or only where each provider's SDK actually supports it?
  - If a hard ceiling is required for cost/capacity reasons, what should that ceiling be and how should VS Code surface a clamped value to the user?

## Evidence

- **no existing setting:** src/vs/workbench/contrib/chat/common/constants.ts and chat.shared.contribution.ts only define chat.subagents.allowInvocationsFromSubagents, .defaultToAuto, .useRichRendering, and .showCreditUsage — no maxConcurrent/maxDepth setting exists on main.
- **depth is hard-coded, not the claimed precedent:** RUN_SUBAGENT_MAX_NESTING_DEPTH = 5 in src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts is a compile-time constant gated by the boolean allowInvocationsFromSubagents setting, not a numeric chat.subagents.maxDepth setting as the issue assumes — so there's no existing precedent to copy verbatim.
- **limiter lives outside this repo:** No TaskRegistry, setSubAgentLimiter, or subAgentMaxConcurrent symbols exist anywhere under src/vs/platform/agentHost or src/vs/workbench/contrib/chat — the actual concurrency gate the issue references is implemented in the external @github/copilot-sdk runtime, confirmed independently by the second commenter tracing it to `configureSubAgentLimiter` in the bundled SDK.
- **corroboration:** brunogsystem confirms the same behavior on VS Code 1.138 and 1.139 Stable with a cap of 2 (not 4) for a BYOK/gateway setup, and traces the plan-tier gating even when no GitHub-billed model is in use.
