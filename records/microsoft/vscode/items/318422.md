# Issue #318422 — Duplicate Copilot agents shown when contributed by both VS Code extension and Copilot CLI plugin

[https://github.com/microsoft/vscode/issues/318422](https://github.com/microsoft/vscode/issues/318422)

## Summary

The defect remains source-reproducible on current main: extension and plugin agents are retained as separate URI-keyed modes, but the picker renders only their identical display names. This issue should remain the canonical report, with a maintainer deciding whether same-name agents are deduplicated or shown with provenance.

## Change summary

Make same-name custom agents from VS Code extensions and Copilot CLI plugins distinguishable or safely deduplicated in the Chat agent picker.

## Best solution

Define a consistent collision policy for custom agents, then apply it in the Chat mode service or picker so users never see indistinguishable choices while preserving access to intentionally distinct implementations.

- **Behavior:**

  > When an extension and a Copilot CLI plugin contribute agents with the same display name, the Chat agent picker must not present indistinguishable choices. Depending on the approved collision policy, it must either expose one deterministic entry or retain both with clear source provenance. Users must be able to predict which implementation will run, including when many collisions are present, while uniquely named agents retain their existing presentation and behavior.
- **Trace:**

  > PromptsService.computeAgentDiscoveryInfo in src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts returns every discovered agent and preserves its IAgentSource. ChatModes.refreshCustomPromptModes in src/vs/workbench/contrib/chat/common/chatModes.ts keys CustomChatMode instances by file URI, so extension and plugin copies with the same name coexist; CustomChatMode.source retains enough provenance to distinguish their storage origins. ModePickerActionItem.makeActionFromCustomMode in src/vs/workbench/contrib/chat/browser/widget/input/modePickerActionItem.ts renders mode.label without source information, producing identical rows. The boundary is custom-agent collision handling and picker presentation; do not alter unrelated @agent participant completion behavior or plugin discovery. The younger https://github.com/microsoft/vscode/issues/318590 was already consolidated into this canonical report.
- **Open decisions:**
  - When an extension and plugin provide the same agent name, should VS Code choose one by a documented precedence rule, or keep both selectable and display their provenance?
  - If both remain selectable, what stable user-facing provenance should distinguish them: source type only, contributing extension/plugin name, or both?

## Evidence

- **source reproduction:** src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts loads every discovered agent file, including plugin and extension contributions, into separate ICustomAgent records.
- **distinct identities:** src/vs/workbench/contrib/chat/common/chatModes.ts constructs CustomChatMode.id from each agent file URI and refreshCustomPromptModes keys instances by that URI, so equivalent extension and plugin files remain separate picker modes.
