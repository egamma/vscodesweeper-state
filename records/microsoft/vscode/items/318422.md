# Issue #318422 — Duplicate Copilot agents shown when contributed by both VS Code extension and Copilot CLI plugin

[https://github.com/microsoft/vscode/issues/318422](https://github.com/microsoft/vscode/issues/318422)

## Summary

The current source still permits indistinguishable same-name agents from extension and plugin sources. The linked deduplication PR was closed without merging, so it does not establish a fix.

## Change summary

Prevent extension-contributed and Copilot CLI plugin-contributed agents with the same display name from appearing as indistinguishable picker entries.

## Best solution

Make same-name agents unambiguous in the chat agent picker. Decide whether independently contributed agents should remain selectable with source labels or be resolved by a documented precedence rule before adopting name-based deduplication.

- **Validation:** Use an extension contribution and an enabled plugin contribution with the same agent name and different contents. Verify in the chat picker that the agreed behavior either preserves both with distinguishable source attribution or exposes only the documented precedence winner. Add focused coverage in the PromptsService getCustomAgents suite if discovery changes, and verify different-name agents and existing visibility/session filtering remain unchanged.
- **Behavior:**

  > Installing an extension and a Copilot CLI plugin that each contribute an agent named modernize-dotnet currently produces indistinguishable picker entries. Users must be able to identify which contribution they select, or receive a single agent under an explicitly agreed collision rule. Acceptance must cover contributions with different contents or versions, not assume identical names imply equivalent behavior. Agents with different names must remain available as before.
- **Trace:**

  > In src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts, computeListPromptFiles combines extension and plugin sources, computeAgentDiscoveryInfo parses every contribution, and agent identity is the file URI rather than its name. The default CustomizationHarnessService path filters by session type without resolving collisions; ChatModes.refreshCustomPromptModes retains the distinct IDs. In src/vs/workbench/contrib/chat/browser/widget/input/modePickerActionItem.ts, both become custom actions bearing the same label without source attribution. https://github.com/microsoft/vscode/pull/338037 proposed discovery-level deduplication but was closed unmerged. https://github.com/microsoft/vscode/issues/318590 documents why differing versions may need to remain distinguishable. Preserve enabled-state, invocation visibility, target and session filtering; the unresolved boundary is whether collisions suppress a contribution or preserve both selections.
- **Open decisions:**
  - Should same-name extension and plugin agents remain separately selectable with source attribution, or should one contribution suppress the other?
  - If collisions suppress contributions, which source takes precedence when their contents or versions differ?
