# Issue #185563 — Async data tree doesn't maintain consistency on focus and selection events. 

[https://github.com/microsoft/vscode/issues/185563](https://github.com/microsoft/vscode/issues/185563)

## Summary

Current main still exposes transiently different focus and selection snapshots when those traits change through separate operations. The desired event contract remains an unresolved design question, and this team-authored issue has no factual fix or duplicate supporting closure.

## Change summary

Make tree focus and selection notifications expose a mutually consistent state when consumers observe either change.

## Best solution

Define the atomicity contract at the extension TreeView boundary, preserving immediate low-level tree events while coalescing paired focus and selection changes where the public API requires a consistent snapshot.

## Evidence

- **current source:** src/vs/workbench/browser/parts/views/treeView.ts:773-784 still handles onDidChangeSelection and onDidChangeFocus independently, reads the other trait immediately, and fires onDidChangeSelectionAndFocus from each callback.
- **tree semantics:** src/vs/base/browser/ui/tree/abstractTree.ts:3192-3212 buffers each setSelection or setFocus operation separately; one operation does not defer its event until a subsequent operation updates the other trait.
- **API boundary:** src/vs/workbench/api/browser/mainThreadTreeViews.ts:203 sends each combined snapshot through one $setSelectionAndFocus RPC, while src/vs/workbench/api/common/extHostTreeViews.ts:588-601 updates both extension-host values before firing their individual API events. A stale peer value originating in treeView.ts can therefore still reach the proposed API.
- **related API issue:** https://github.com/microsoft/vscode/issues/170248 is older and remains open, but it requests exposure of the focused TreeView item; comments identify this issue as a prerequisite for finalizing that API, not the same reporter-observable symptom required for a duplicate close on re-review.
