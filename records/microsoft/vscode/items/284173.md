# Issue #284173 — Agent often generates invalid images, can't preview unsaved images(?)

[https://github.com/microsoft/vscode/issues/284173](https://github.com/microsoft/vscode/issues/284173)

## Summary

Keep open: current main still renders image previews from the filesystem rather than the dirty in-memory SVG document, explaining why valid agent-created SVG content fails until saved. This is also a team-authored, accepted bug, and no fixing commit or older canonical issue was found.

## Change summary

Agent-created images may be invalid, while valid unsaved SVG files show an image-load error until written to disk.

## Best solution

The image preview should display and refresh from the current in-memory content for dirty SVG documents without changing normal binary-image preview behavior. The separate invalid-raster-generation concern should either receive a defined validation behavior here or be tracked independently.

## Plan brief

- **Likely files:** `extensions/media-preview/src/imagePreview/index.ts`, `extensions/media-preview/src/mediaPreview.ts`, `src/vs/workbench/api/common/extHostCustomEditors.ts`
- **Validation:** Create or modify a valid SVG without saving, reopen it with Image Preview, and verify that the current in-memory image renders and refreshes after another unsaved edit; then save and confirm the rendered result does not change. Also verify that normal saved PNG/JPEG previews remain unchanged.
- **Behavior:**

  > A valid SVG created or modified by an agent must preview from its current unsaved contents instead of showing an image-load error until save. Subsequent unsaved SVG edits must refresh the preview, and saving must not be the event that first makes valid content render. Existing previews of saved binary images must continue to behave as before.
- **Trace:**

  > The image preview is registered as ImagePreviewManager, a CustomReadonlyEditorProvider, in extensions/media-preview/src/imagePreview/index.ts. Its custom document contains only the resource URI, and ImagePreview.getResourcePath exposes that URI directly to the webview; no text-document contents are passed through. MediaPreview in extensions/media-preview/src/mediaPreview.ts listens only to filesystem changes, which explains the save-dependent refresh. The custom-editor bridge in src/vs/workbench/api/common/extHostCustomEditors.ts distinguishes custom documents from CustomTextEditorProvider documents, so the uncertainty begins at how SVG previews should access dirty text state without changing binary-image semantics. The younger report https://github.com/microsoft/vscode/issues/320225 confirms the same unsaved-SVG symptom but is not a valid canonical for this re-reviewed item.
- **Open decisions:**
  - Should this issue cover only the unsaved-SVG preview defect, or must the same work also define user-visible handling for agents that produce invalid JPEG data?

## Evidence

- **current source path:** extensions/media-preview/src/imagePreview/index.ts registers ImagePreviewManager as a CustomReadonlyEditorProvider; openCustomDocument retains only the URI, and getResourcePath constructs a webview URI for that resource. It never reads a vscode.TextDocument or subscribes to onDidChangeTextDocument, so dirty in-memory SVG content is unavailable to the preview.
- **disk-only refresh:** extensions/media-preview/src/mediaPreview.ts refreshes MediaPreview through a workspace file-system watcher. The resulting render occurs after a disk change, matching the report that the valid SVG starts working only after save.
- **independent confirmation:** https://github.com/microsoft/vscode/issues/320225 independently reports that a valid unsaved SVG produces the same image-preview error. It is newer than this re-reviewed issue, so it cannot be the canonical duplicate.
