# Issue #329329 — Regression: Modern UI rounded corners break edge scrollbar dragging behavior

[https://github.com/microsoft/vscode/issues/329329](https://github.com/microsoft/vscode/issues/329329)

## Summary

Traced this in the layout source: the experimental Modern UI Update (`workbench.experimental.modernUI`) reserves a real 4px/2px margin around the outermost floating part (sidebar, auxiliary bar, panel) so the CSS gap/border/rounded-corner can be drawn, and that margin genuinely removes DOM area at the true window edge — so a mouse press there never reaches the part's scrollbar. This is real and reproducible from source, but confined to an experimental, opt-in-by-default-off setting, so it's a route-to-area fix rather than a broad regression.

## Change summary

With the experimental Modern UI Update enabled, the floating-panel margin at the outer window edge leaves the scrollbar hit area a few pixels short of the true screen edge, breaking the classic 'throw to the edge' scrollbar-drag pattern.

## Best solution

In src/vs/workbench/services/layout/browser/layoutService.ts (FLOATING_PANEL_MARGIN/FLOATING_PANEL_INNER_MARGIN) and the corresponding floatingPanels.css rules, extend the outermost card's true interactive/hit-test bounds (or add an invisible edge hit-strip as the reporter suggests) so window-edge pixels still route pointer events to the adjacent part's scrollbar even though the visual card is inset — this needs a layout/hit-testing design decision, not just a CSS tweak, since a mouse press in the margin currently lands on the grid view/sash, not the part.

## Evidence

- **margin is real and intentional:** src/vs/workbench/services/layout/browser/layoutService.ts defines FLOATING_PANEL_MARGIN=4 / FLOATING_PANEL_INNER_MARGIN=2, documented as reserved space for the CSS margin/border in floatingPanels.css; parts 'grow or shrink their content by this amount to leave room for the margin'.
- **CSS confirms the outer-edge gap:** src/vs/workbench/browser/media/floatingPanels.css applies `margin: 0 var(--vscode-spacing-size20) var(--vscode-spacing-size20) var(--vscode-spacing-size40)` to `.part.sidebar`/`.part.auxiliarybar` under `.floating-panels`, i.e. a real DOM-level gap between the card and the window edge, doubled at exposed top/bottom edges per the '.top-window-edge' rule.
- **setting is experimental, not default-on:** src/vs/workbench/browser/workbench.contribution.ts registers `LayoutSettings.MODERN_UI` with `default: false` and `tags: ['experimental']`, though it carries `experiment: { mode: 'auto' }`, so some users could be auto-enrolled without explicitly opting in — consistent with the reporter not realizing which setting caused it.
- **editor part itself has no added margin:** src/vs/workbench/contrib/styleOverrides/browser/media/editorBorder.css explicitly notes 'no margin is added, avoiding a relayout' for the editor part, so the reported gap is specific to whichever part (sidebar/auxbar/panel) sits at the outer window edge, not to every scrollbar.
