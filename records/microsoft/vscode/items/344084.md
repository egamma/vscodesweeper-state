# Issue #344084 — New remote (Codespace) installs synced extensions even when Extensions is unchecked in Settings Sync

[https://github.com/microsoft/vscode/issues/344084](https://github.com/microsoft/vscode/issues/344084)

## Summary

The reported resource-enablement bypass remains present in current main: first-time remote initialization reads and installs synced extensions while checking only global Settings Sync enablement. Keep this correctly routed bug open; the reported publisher-trust concern also warrants human review rather than automated closure or implementation.

## Change summary

New desktop remote connections install extensions from stale synced data even when Extensions is unchecked in Settings Sync.

## Best solution

Remote extension initialization should respect the user's Extensions sync selection while preserving explicitly configured remote installations and existing enabled-sync behavior. Have the extensions/settings-sync owners also assess the publisher-trust implications of these unsolicited installs.

## Evidence

- **Current failing path:** In src/vs/workbench/contrib/extensions/electron-browser/remoteExtensionsInit.ts, RemoteExtensionsInitializerContribution.initializeRemoteExtensions checks new remote/workspace state and isEnabled(), then reads SyncResource.Extensions without consulting isResourceEnabled(SyncResource.Extensions). A desktop connection with an authentication session and a retained cloud Extensions resource therefore reaches initialization despite the resource opt-out.
- **Independent enablement controls:** src/vs/platform/userDataSync/common/userDataSyncEnablementService.ts implements isEnabled() and isResourceEnabled() as separate stored controls. setResourceEnablement() changes resource enablement without disabling global sync; the initializer's global check cannot enforce the Extensions checkbox.
- **No downstream resource gate:** AbstractInitializer.initialize in src/vs/platform/userDataSync/common/abstractSynchronizer.ts checks content and parses sync data before invoking doInitialize, without checking resource enablement. AbstractExtensionsInitializer.generatePreview in src/vs/platform/userDataSync/common/extensionsSync.ts filters ignored and already-installed extensions, not the Extensions sync selection. RemoteExtensionsInitializer.doInitialize then installs eligible workspace extensions from that preview.
- **Existing intended distinction:** src/vs/workbench/services/extensionManagement/common/extensionManagementService.ts:742 combines isEnabled() with isResourceEnabled(SyncResource.Extensions), demonstrating that global sync enablement alone is insufficient elsewhere in extension management.
- **Desktop-specific evidence:** The initializer explicitly skips windows without a local extension-management server and is registered at LifecyclePhase.Restored in src/vs/workbench/contrib/extensions/electron-browser/extensions.contribution.ts. This agrees with the reporter's desktop-versus-web difference and delayed client-initiated installations.
- **Security-sensitive handling:** The report describes unexpected extension installation into an intentionally restricted remote environment. Current RemoteExtensionsInitializer.doInitialize supplies EXTENSION_INSTALL_SKIP_PUBLISHER_TRUST_CONTEXT when installing from the synced list. This substantiates a trust-sensitive review concern, but does not by itself establish an exploit; the security-sensitive keep-open and readiness exclusions apply.
