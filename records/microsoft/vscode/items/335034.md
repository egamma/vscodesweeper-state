# Issue #335034 — Codex Agent Host fails in workspaces using only an extension-registered filesystem

[https://github.com/microsoft/vscode/issues/335034](https://github.com/microsoft/vscode/issues/335034)

## Summary

Confirmed in source: Codex Agent Host derives its process cwd and workspace roots by calling `.fsPath` unconditionally on workspace-folder URIs (`codexAgent.ts` `_runtimeWorkspaceRoots`/`_workingDirectories`), with no scheme guard, unlike `setWorkingDirectory` which explicitly rejects non-`file` scheme resources. For a workspace backed only by an extension filesystem provider this produces a bogus path handed to the Codex app-server as `cwd`, matching the reported `AbsolutePathBuf deserialized without a base path` error.

## Change summary

Codex Agent Host fails to start a turn (cryptic protocol deserialization error) when the workspace is backed only by a non-file-scheme, extension-registered filesystem provider, instead of falling back gracefully like the regular Codex extension does.

## Best solution

Add an explicit scheme/absolute-path guard for workspace working directories before building the Codex launch/resume params (mirroring the check already in `setWorkingDirectory`, codexAgent.ts:4261), and decide product-wise whether Agent Host should reject such workspaces with a clear, actionable error or fall back to the extension-host Codex path — Codex fundamentally spawns a real OS subprocess, so genuine virtual-FS support is a much bigger undertaking than the guard itself.

- **Trace:**

  > The defect traces to codexAgent.ts:1960-1970 (`_workingDirectories`/`_runtimeWorkspaceRoots`), which builds the Codex thread's `cwd`/`runtimeWorkspaceRoots` from `directory.fsPath` for every workspace folder with no scheme validation, unlike the explicit `scheme !== Schemas.file` guard in `setWorkingDirectory` (codexAgent.ts:4261). For an extension-registered (non-file) filesystem workspace, this produces a non-absolute/non-native path that the Codex app-server rejects during protocol deserialization (`AbsolutePathBuf deserialized without a base path`), matching the reporter's stack. Do not touch the working-directory-change guard already in place, and do not assume Codex can ever meaningfully operate against a virtual FS — it spawns a real OS subprocess and needs a genuine disk path.
- **Open decisions:**
  - Should Agent Host simply refuse non-file-scheme workspaces up front with a clear error (and let the UI fall back to the regular Codex extension), or is there a design where Agent Host materializes/copies such workspaces to a real temp directory so Codex can still run?
  - If rejecting, should this be silent fallback to the extension-host Codex path (`chat.editor.codex.preferAgentHost` effectively ignored for that workspace) or a surfaced error to the user?
