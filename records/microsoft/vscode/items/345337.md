# Issue #345337 — Editor window: pass the workspace folder (or offer a folder picker) to workspace remote agent hosts that share the filesystem

[https://github.com/microsoft/vscode/issues/345337](https://github.com/microsoft/vscode/issues/345337)

## Summary

A real capability gap remains: editor-window remote sessions intentionally defer directory selection to the host, including hosts sharing the workspace filesystem. Keep this distinct follow-up open for a decision on explicit folder selection versus opt-in workspace inheritance.

## Change summary

Allow new editor-window chats on workspace-configured remote agent hosts to receive an explicitly selected or shared workspace directory.

## Best solution

Provide an explicit, host-addressable directory choice for new remote chats while preserving host-selected defaults for unrelated filesystems. Settle the opt-in and multi-root semantics before implementation, coordinating with the pending host-folder link work.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostChatContribution.ts`, `src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHost.contribution.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts`
- **Validation:** With a conforming AHP host serving two shared projects, open each project in an editor window and start a new chat using the agreed directory-selection mechanism. Inspect resolveSessionConfig and createSession frames for the intended host-space directory, confirm the agent operates in that project, and verify hosts without opt-in still choose their own default. Repeat with a multi-root workspace and an existing session to verify the chosen semantics and unchanged continuation behavior.
- **Behavior:**

  > New editor-window chats on workspace-configured hosts can target the intended project rather than always starting in the host's default directory. Directory forwarding must be explicit or opted into, not assumed for every remote host. The selected directory must agree between configuration resolution and session creation. Existing sessions retain their established directories, and hosts with unrelated filesystems retain host-selected defaults.
- **Trace:**

  > RemoteAgentHostContribution registers a null working-directory resolver for editor-listed remote hosts in src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostChatContribution.ts. AgentHostSessionHandler._resolveRequestedWorkingDirectory treats that null as authoritative and skips the new-session folder service and workspace fallbacks; its creation path already carries workingDirectories and the primary workingDirectory into the corresponding protocol calls. The registered chat.workspaceRemoteAgentHosts schema has no directory-selection control. https://github.com/microsoft/vscode/issues/344310 explicitly assumes non-shared filesystems, so it does not own this remaining capability. Coordinate with the open https://github.com/microsoft/vscode/pull/344467, which proposes host-folder links but does not supply workspace inheritance or a picker. Preserve connection-owned URI mapping, trusted-workspace restrictions, host defaults without opt-in, and existing-session directory identity. The uncertainty is the user-facing selection and inheritance contract, not whether the current resolver suppresses the workspace folder.
- **Open decisions:**
  - Should shared-filesystem hosts inherit workspace folders through a per-host opt-in, require an explicit folder picker, or support both?
  - In a multi-root workspace, should an opted-in new session receive every workspace folder or only a user-selected primary folder?
