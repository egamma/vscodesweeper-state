# Issue #326095 — Code Execution Permission Error in latest vscode

[https://github.com/microsoft/vscode/issues/326095](https://github.com/microsoft/vscode/issues/326095)

## Summary

Real bug traced in the CLI/tunnel code in this repo, not the remote-ssh extension itself: `ensure_executable` misclassifies a missing server binary (io error 2, NotFound) as a permission problem, and `control_server.rs` deliberately skips the corruption/eviction re-download path for that error class — leaving users permanently stuck with a broken vscode-server install and no automatic recovery.

## Change summary

After updating VS Code and connecting to a remote Linux host, the connection fails with 'is not executable and permissions could not be restored: No such file or directory (os error 2)', and reconnecting doesn't self-heal.

## Best solution

In `ensure_executable` (cli/src/tunnels/code_server.rs), distinguish `io::ErrorKind::NotFound` (binary/dir missing — a corrupted/incomplete install) from a genuine permission-denied case; a NotFound should be treated as corruption so `control_server.rs`'s eviction/re-download path (currently gated to `ServerUnexpectedExit` only) also runs for it, instead of leaving the user stuck requiring the manual `mv ~/.vscode-server/cli/servers/... .broken` workaround described in the comments.

## Evidence

- **error origin:** cli/src/tunnels/code_server.rs:358-368 `ensure_executable` calls `std::fs::metadata(path)`, which fails with `NotFound` ("No such file or directory (os error 2)") when the binary/dir is missing — exactly matching the reported error text — and this gets wrapped into `CodeError::ServerNotExecutable` at code_server.rs:656-663, conflating 'missing file' with 'not executable'.
