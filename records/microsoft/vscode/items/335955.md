# Issue #335955 — Settings editor and other webview-based panels cannot be detached into a real, independent OS window

[https://github.com/microsoft/vscode/issues/335955](https://github.com/microsoft/vscode/issues/335955)

## Summary

Real gap, but the report's diagnosis is off: Settings (`SettingsEditor2` in src/vs/workbench/contrib/preferences/browser/settingsEditor2.ts) extends `EditorPane` directly — it is not a webview/iframe editor — so the generic 'Move Editor into New Window' mechanism should apply to it like any other editor pane; something in how `SettingsEditor2Input` is treated (its `matches()` in preferencesEditorInput.ts always returns true for any two `SettingsEditor2Input` instances, singleton-like) plausibly interferes with moving it into an auxiliary window. This overlaps with existing open work on auxiliary/floating windows, so it should be routed rather than treated as a fresh ask.

## Change summary

Allow the built-in Settings editor (and similar core editors) to be detached into a separate OS window the same way regular text editor tabs can via 'Move Editor into New Window'.

## Best solution

Route to the workbench/editor-part owners already tracking auxiliary-window work (https://github.com/microsoft/vscode/issues/193267, open, Backlog milestone, `workbench-auxwindow` label) to decide whether `SettingsEditor2`'s singleton-style `matches()` should be adjusted to support moving into an aux window group, or whether this is an intentional limitation for the settings editor specifically.

  > Thanks for the report. One correction on the diagnosis: the Settings editor (`SettingsEditor2`) isn't actually webview/iframe-based — it's a regular `EditorPane` like other core editors — so this isn't the same iframe-reparenting gap that was closed in https://github.com/microsoft/vscode/issues/195715 (which covered extension-provided custom/webview editors). The likely culprit is that `SettingsEditor2Input` treats all instances as equal (matches() always returns true), which may prevent it from being moved into an auxiliary window group the normal way. This is closely related to the ongoing auxiliary-window work tracked in https://github.com/microsoft/vscode/issues/193267 — routing there for the workbench/editor-part owners to take a look.

- **related issue #193267 still open:** https://github.com/microsoft/vscode/issues/193267 ('Aux window: allow detaching views and panels') is open, in the Backlog milestone, has 58 comments and the `workbench-auxwindow` label — the active tracker for general view/panel detachment work, broader than but adjacent to this ask.
