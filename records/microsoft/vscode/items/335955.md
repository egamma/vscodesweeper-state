# Issue #335955 — Settings editor and other webview-based panels cannot be detached into a real, independent OS window

[https://github.com/microsoft/vscode/issues/335955](https://github.com/microsoft/vscode/issues/335955)

## Summary

Current source supports moving Settings and webview editors into auxiliary windows, but the reported Windows failure remains unconfirmed. The supplied Settings-to-new-window steps suffice to retest; neither linked issue establishes that this specific failure is resolved.

## Change summary

Moving Settings or a webview editor into a new window should produce an independently movable desktop window.

## Best solution

Verify the Settings failure on Windows and, if reproduced, restore the existing editor-to-auxiliary-window behavior. Keep arbitrary sidebar and panel detachment separate: that capability is already tracked by https://github.com/microsoft/vscode/issues/193267.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/preferences/browser/settingsEditor2.ts`, `src/vs/workbench/services/preferences/common/preferencesEditorInput.ts`, `src/vs/workbench/browser/parts/editor/editorActions.ts`, `src/vs/workbench/browser/parts/editor/editorGroupView.ts`, `src/vs/workbench/services/auxiliaryWindow/electron-browser/auxiliaryWindowService.ts`
- **Validation:** On Windows, with extensions disabled, open the graphical Settings editor and run workbench.action.moveEditorToNewWindow. Verify that Settings opens in a separate desktop window, can be moved to another monitor, remains usable, and can return to the main window. Repeat with a regular text editor as a control; separately identify any failing webview editor.
- **Behavior:**

  > The reporter says the graphical Settings editor stays confined to the main window when Move Editor into New Window is used. The expected behavior is a separate, independently movable desktop window containing usable Settings. First reproduce this operation on Windows and distinguish failure to create a window from failure to render or move the editor. General sidebar and panel detachment is a separate feature request, not an acceptance requirement for this bug.
- **Trace:**

  > SettingsEditor2.createEditor() in src/vs/workbench/contrib/preferences/browser/settingsEditor2.ts constructs ordinary DOM, not an iframe. SettingsEditor2Input inherits the permissive EditorInput.canMove() contract. BaseMoveCopyEditorToNewWindowAction.run() in src/vs/workbench/browser/parts/editor/editorActions.ts creates an auxiliary editor part, then EditorGroupView moves the editor into its target group. Current webview editors also explicitly claim and recreate their presentation for a changed target window through webviewEditor.ts and overlayWebview.ts. These paths establish intended support, not an observed Windows reproduction; uncertainty starts at the actual command outcome and target-window initialization. Preserve existing text-editor moves and do not expand this investigation into arbitrary view or panel detachment, which is tracked separately at https://github.com/microsoft/vscode/issues/193267.

## Evidence

- **Settings is not a webview:** src/vs/workbench/contrib/preferences/browser/settingsEditor2.ts:488–501 builds SettingsEditor2 using ordinary DOM elements. SettingsEditor2Input in src/vs/workbench/services/preferences/common/preferencesEditorInput.ts inherits EditorInput.canMove(), which returns true; the claimed iframe-based restriction does not explain this editor.
- **Existing move command:** workbench.action.moveEditorToNewWindow is registered in src/vs/workbench/browser/parts/editor/editorCommands.ts. BaseMoveCopyEditorToNewWindowAction.run() in editorActions.ts:2622–2642 creates an auxiliary editor part and moves the selected editors to it. EditorGroupView.doMoveOrCopyEditorAcrossGroups() opens the editor in the target group before closing its original presentation.
- **Webview adoption:** src/vs/workbench/contrib/webviewPanel/browser/webviewEditor.ts:166–167 claims the webview using the editor's target window. src/vs/workbench/contrib/webview/browser/overlayWebview.ts:132–151 detects a changed window ID, disposes the old webview presentation, and recreates it for that window. Current source therefore implements cross-window webview handling rather than a blanket prohibition.
- **Closed related implementation:** https://github.com/microsoft/vscode/issues/195715 is closed. The maintainer reported that iframe editor moves work, with limitations for dirty non-text custom editors lacking backups: https://github.com/microsoft/vscode/issues/195715#issuecomment-1997532478. This predates the present report and does not prove the reported Settings failure was fixed.
- **Open related request has different scope:** https://github.com/microsoft/vscode/issues/193267 remains open and concerns detaching sidebar views and panels, as clarified in https://github.com/microsoft/vscode/issues/193267#issuecomment-1831532246. It owns general panel detachment, but does not establish ownership of a failure to move the already-supported Settings editor; it is not a verified canonical duplicate for the full report.
- **Verification boundary:** The report identifies Windows 10, VS Code 1.137.0, extensions disabled, the Settings editor, and the Move Editor into New Window operation. Read-only source inspection cannot confirm the desktop outcome, and no execution or reproduction was performed.
