# Issue #156351 — Confusing dialog for contributed launch configs when errors occur

[https://github.com/microsoft/vscode/issues/156351](https://github.com/microsoft/vscode/issues/156351)

## Summary

The misleading launch.json action was removed, but the issue was reopened because the confusing generic variable-resolution message remains. Current source confirms that the structured variable kind is lost across the extension-host RPC boundary, preventing debug from presenting the requested context-specific message.

## Change summary

Show a clear, debug-specific error when a contributed launch configuration requires an active file, without referring users to launch.json or exposing `${file}` implementation details.

## Best solution

Preserve structured variable-resolution failure information across the debug extension-host boundary, then let the debug service present a localized message explaining that this configuration requires an open active file. Keep task and ordinary user-authored configuration error behavior unchanged.

- **Behavior:**

  > Starting a dynamically contributed debug configuration that depends on the active file while no file editor is active explains that the configuration requires an open active file. The prompt does not direct the user to launch.json and does not require them to understand `${file}` or the term “editor.” Existing messages and launch.json actions for user-authored configurations remain unchanged.
- **Trace:**

  > The file-variable failure originates as `VariableError(VariableKind.File, ...)` in src/vs/workbench/services/configurationResolver/common/variableResolver.ts. For extension-host-backed debug adapters, `ExtHostDebugService.$substituteVariables` sends that failure through RPC; `transformErrorForSerialization` does not retain the custom `variable` property, so `MainThreadDebugService` and `DebugService.substituteVariables` receive only a generic error and display its message. Commit cebad239e88e15b3738844e77cf26955d6b4d1a7 already suppresses the launch.json action for dynamic configurations and must remain intact. The uncertainty is confined to the typed failure representation across RPC and the appropriate test seam; do not change generic task resolution or messages for user-authored configurations. Related current report: https://github.com/microsoft/vscode/issues/336289.

- **generic presentation remains:** src/vs/workbench/contrib/debug/browser/debugService.ts catches substitution failures and passes only `err.message` to `showError`, so it cannot replace the `${file}`/“open an editor” text with the debug-specific explanation requested in the issue.
