# Issue #326895 — vscode_listCodeusages tool should implement some form of caching

[https://github.com/microsoft/vscode/issues/326895](https://github.com/microsoft/vscode/issues/326895)

## Summary

The repeated-result cost remains a real design gap on current main, and this team-authored request should stay open under the chat tools area. The implementation currently recomputes and emits the complete usage list on every invocation, but reducing model-context cost requires deciding both cache freshness and how repeated results are represented.

## Change summary

Avoid repeatedly recomputing and resending large code-usage result sets when an agent queries the same symbol.

## Best solution

Define a session-scoped usages-result cache with explicit invalidation for relevant source changes, then let repeated requests reuse a stable result or request only the needed subset without reinserting the complete reference list into model context.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/tools/usagesTool.ts`, `src/vs/workbench/contrib/chat/test/browser/tools/usagesTool.test.ts`
- **Validation:** Extend the UsagesTool unit suite to invoke the same symbol twice in an unchanged workspace and verify the agreed reuse behavior, then simulate a relevant model change and verify that the stale result is not reused.
- **Behavior:**

  > Repeated usages queries for the same symbol in an unchanged workspace should reuse prior work without reinserting an unnecessarily complete duplicate result into model context. Results must remain correct after relevant source changes and must not leak across unrelated workspaces or agent sessions. Acceptance should cover a repeated unchanged query, a changed source file, and isolation between distinct invocation contexts.
- **Trace:**

  > UsagesTool.invoke in src/vs/workbench/contrib/chat/browser/tools/usagesTool.ts resolves the input location and unconditionally calls getDefinitionsAtPosition, getReferencesAtPosition, and getImplementationsAtPosition before formatting every reference and preview into a new text result. UsagesTool is registered as a workbench contribution and currently has no cache state or invalidation dependencies. The current implementation does not create context.txt, so the uncertainty starts at the result contract: provider-result caching can reduce computation, but it cannot by itself reduce repeated model-context tokens while the same complete text payload is returned. The neighboring tests in src/vs/workbench/contrib/chat/test/browser/tools/usagesTool.test.ts provide mocks for providers and model/search services but do not cover repeated calls. Keep symbol resolution, workspace scoping, and non-cached single-invocation output behavior unchanged while planning the reuse contract.
- **Open decisions:**
  - On a cache hit, should the tool return a stable reusable handle or a delta/subset rather than the complete usage payload, so the observable behavior actually reduces model-context tokens?
  - Which source or workspace changes invalidate a cached symbol result, and is freshness required immediately after unsaved edits?
  - Is reuse scoped to one tool instance, one agent turn, or the full chat session, and must entries be isolated by working directory and symbol location?
