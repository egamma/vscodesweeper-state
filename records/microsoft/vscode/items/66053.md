[https://github.com/microsoft/vscode/issues/66053](https://github.com/microsoft/vscode/issues/66053)

## Summary

This remains a well-supported Backlog feature request with 44 community upvotes. The discussion identifies partial workarounds and an extension, but no evidence that current VS Code covers the full request for SVG completion, highlighting, embedded CSS, and Emmet support.

## Change summary

Provide first-class SVG language support across HTML/CSS IntelliSense, syntax highlighting, embedded styles, and Emmet completions.

## Best solution

Define the intended core-versus-extension boundary, then add reusable SVG tag and attribute metadata through the HTML/CSS language-service data-provider path while separately covering SVG TextMate grammar, embedded CSS/JavaScript, and Emmet behavior.

## Plan brief

- **Likely files:** `extensions/html-language-features`, `extensions/css-language-features`, `extensions/emmet`, `extensions/html`
- **Validation:** Add fixture-based language-feature checks for a standalone `.svg` file and inline `<svg>` in HTML, covering SVG element and attribute completions, CSS property/attribute handling, embedded `<style>` and `<script>` tokenization, and representative SVG Emmet abbreviations without regressing HTML behavior.
- **Behavior:**

  > Editing inline or standalone SVG should provide SVG-aware element and attribute completions, accurate syntax highlighting, and SVG Emmet abbreviations. CSS and JavaScript embedded in SVG should retain their normal language behavior. Existing HTML, CSS, and Emmet behavior outside SVG must remain unchanged.
- **Trace:**

  > The report spans the built-in HTML and CSS language-feature extensions, Emmet integration, and SVG grammar/tokenization rather than one bounded defect. Existing `emmet.includeLanguages` mapping supplies generic HTML behavior but misses SVG-specific metadata, while the referenced jock.svg extension is only partial evidence and does not settle whether the capability belongs in core. The issue explicitly points to custom HTML tag and CSS property data support as a possible metadata path. The boundary is SVG language intelligence and embedded-language handling; XML generally, SVG preview/diff rendering, and unrelated XML extensions are outside this issue.
- **Open decisions:**
  - Should VS Code ship SVG element and attribute metadata in its built-in web-language support, or should core provide only the extension API/data-provider capability and leave the metadata package to an extension?
  - Is the accepted scope both standalone `.svg` files and inline `<svg>` in HTML, including embedded `<style>` and `<script>`, or only completion support in HTML/CSS contexts?
  - Should SVG-specific Emmet abbreviations be enabled by default for the `svg` language, or remain opt-in through language mapping?
