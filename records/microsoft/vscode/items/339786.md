# Issue #339786 — API: expose selected SCM resources to extension commands invoked by keybindings

[https://github.com/microsoft/vscode/issues/339786](https://github.com/microsoft/vscode/issues/339786)

## Summary

Well-diagnosed, genuine API gap confirmed in source: SCM resource selection is only forwarded to menu-invoked commands via RepositoryPaneActionRunner, not to keybinding-invoked commands. No existing setting/command covers this and no canonical issue owns it, so this should stay open as a feature request pending API design.

## Change summary

Extension commands bound to a keybinding (rather than invoked from the SCM context menu) cannot obtain the currently selected SCM resources, unlike menu-invoked commands.

## Best solution

Design an opt-in mechanism or query API (e.g. a command like `scm.getSelectedResourceStates` or forwarding selection args to keybinding-bound commands when focus is in the SCM view) that lets extensions read `SCMViewPane.getSelectedResources()` outside the existing `scm/resourceState/context` menu path.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/scm/browser/scmViewPane.ts`
- **Validation:** Once the API shape is agreed, a test asserting that invoking the command via keybinding with a multi-selection active yields the same resource list as invoking it from the context menu.
- **Behavior:**

  > An extension command bound to a keybinding, invoked while the SCM resource list has focus, should be able to obtain the same selected SCM resource(s)/URIs that are already supplied when the same command is invoked from `scm/resourceState/context`. No existing editor-URI fallback should be substituted. Acceptance: with N files selected in Changes/Staged Changes, invoking via the keybinding yields all N resources (not just the active editor), matching the menu-invocation behavior.
- **Trace:**

  > `SCMViewPane.getSelectedResources()` (scmViewPane.ts:1917) reads `this.tree.getSelection()` and is only surfaced to command arguments through `RepositoryPaneActionRunner.runAction()` (scmViewPane.ts:467-480), which is wired up as the action runner for the context-menu/inline-action paths (scmViewPane.ts:1606, 1867). Commands triggered by a keybinding go through `ICommandService.executeCommand` directly and never pass through this action runner, so they receive no arguments. The boundary: do not change default command-argument behavior for keybindings elsewhere in the workbench; keep this scoped to an opt-in SCM-specific mechanism. Related: https://github.com/microsoft/vscode/issues/24916, https://github.com/microsoft/vscode/issues/207066, https://github.com/microsoft/vscode/issues/3553, https://github.com/microsoft/vscode/issues/316820, https://github.com/microsoft/vscode/issues/170248 (each narrower/different scope per the reporter's own analysis).
- **Open decisions:**
  - Expose this as a query command/API (e.g. a `vscode.commands.executeCommand` returning selected SCM resource URIs) versus an opt-in mechanism that forwards selection as arguments to keybinding-bound commands?
  - When nothing is explicitly selected, should the API return the focused item, an empty result, or nothing — and should staged/unstaged duplicates and multi-repository selections be disambiguated in the returned shape?

## Evidence
