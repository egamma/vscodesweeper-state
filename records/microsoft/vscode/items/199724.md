# Issue #199724 — Trying to populate a `DiagnosticCollection` progressively results in excessive calls to CodeAction provider.

[https://github.com/microsoft/vscode/issues/199724](https://github.com/microsoft/vscode/issues/199724)

## Summary

Keep open: current source still retriggers automatic code-action requests when progressive diagnostic updates leave the cursor's diagnostics unchanged. The closely related open request is newer, so it cannot replace this re-reviewed, team-authored item.

## Change summary

Support progressive diagnostic replacement without redundant code-action requests or unnecessary lightbulb disruption for unchanged diagnostics.

## Best solution

Define safe invalidation semantics for automatic code actions during progressive diagnostic updates, preferably retaining compatibility with whole-document DiagnosticCollection.set calls. Coordinate with https://github.com/microsoft/vscode/issues/215340; diagnostic-entry mutation APIs remain a separate public-contract decision.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/codeAction/browser/codeActionModel.ts`, `src/vs/editor/contrib/codeAction/test/browser/codeActionModel.test.ts`, `src/vs/platform/markers/common/markerService.ts`, `src/vs/workbench/api/common/extHostDiagnostics.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** Extend the CodeActionModel browser tests using runWithFakedTimers and a counting provider: keep the cursor and document text fixed, publish successive whole-document marker sets more than 250 ms apart, and assert no additional implicit requests when the agreed relevant diagnostics remain unchanged. Assert refresh when relevant diagnostics change or disappear, preserve explicit invocation and cursor-change behavior, and manually verify that progressive updates do not unnecessarily remove the existing lightbulb.
- **Behavior:**

  > Extensions can progressively replace whole-document diagnostic sets, including adding and removing errors, without unnecessarily recomputing automatic code actions for unchanged relevant diagnostics. The existing lightbulb should remain stable when its actions are still valid. Relevant diagnostic changes must refresh actions, and explicit code-action invocation must continue to request current results. Acceptance should measure provider-call counts across updates separated by the debounce interval and check lightbulb stability.
- **Trace:**

  > DiagnosticCollection.set in src/vs/workbench/api/common/extHostDiagnostics.ts sends complete replacement sets through MainThreadDiagnostics.$changeMany to MarkerService.changeOne. Nonempty replacements always emit a resource-level marker event. CodeActionOracle._onMarkerChanges in src/vs/editor/contrib/codeAction/browser/codeActionModel.ts responds to any marker event for the current document with a debounced automatic trigger, which reaches getCodeActions and invokes providers without comparing relevant diagnostics. The existing CodeActionModel tests already use MarkerService, counting triggers, and fake timers, providing a suitable validation harness. Preserve whole-set replacement semantics, diagnostic removals, manual invocation, and ordinary cursor-change behavior; do not suppress diagnostic events globally merely to reduce code-action requests. https://github.com/microsoft/vscode/issues/215340 discusses cursor-local invalidation and possible explicit provider invalidation, but does not settle that contract. The remaining uncertainty is which diagnostic changes can safely leave automatic actions valid and whether this request should also introduce entry-level collection mutation APIs.
- **Open decisions:**
  - May automatic code actions remain cached when diagnostics at the current selection are unchanged but diagnostics elsewhere in the document change, or must providers retain document-wide invalidation guarantees?
  - Should the accepted scope cover efficient whole-set replacement only, or also introduce public DiagnosticCollection APIs for adding and removing individual entries?

## Evidence

- **Existing API does not cover the request:** src/vscode-dts/vscode.d.ts:7171–7248 defines DiagnosticCollection.set as replacement, with resource-level delete and clear but no entry-level add/remove. Merging repeated URI tuples within one set call does not provide incremental mutation of an existing collection.
- **Current progressive-update path:** DiagnosticCollection.set in src/vs/workbench/api/common/extHostDiagnostics.ts replaces the stored array and sends the resulting markers through $changeMany. src/vs/workbench/api/browser/mainThreadDiagnostics.ts:87 forwards these to MarkerService.changeOne; src/vs/platform/markers/common/markerService.ts:179–200 replaces nonempty marker sets and fires a resource event without comparing unchanged entries.
- **Automatic requests remain resource-wide:** src/vs/editor/contrib/codeAction/browser/codeActionModel.ts:48–67 subscribes to marker changes and schedules an automatic trigger for any change to the current document, using a 250 ms debounce rather than diagnostic equality or cursor-local invalidation. Its automatic path calls getCodeActions again, and src/vs/editor/contrib/codeAction/browser/codeAction.ts:128 invokes providers. Updates separated by the debounce can therefore re-request actions despite unchanged diagnostics at the cursor.
- **Existing settings are not a solution:** src/vs/editor/contrib/codeAction/browser/codeActionContributions.ts registers nearby-quick-fix, menu-header, and focus-change settings, none of which controls progressive diagnostic invalidation. Turning editor.lightbulb.enabled off suppresses ordinary automatic requests but removes the desired lightbulb experience rather than satisfying the request.
