# Issue #175986 — Allow VS Code extensions to trigger audio cues

[https://github.com/microsoft/vscode/issues/175986](https://github.com/microsoft/vscode/issues/175986)

## Summary

Keep this accepted accessibility API request open: current source exposes signal playback internally, but not to extensions. The request has 23 upvotes, concrete extension use cases, and maintainer interest; the public semantics and customization contract still need design.

## Change summary

Allow extensions to trigger meaningful accessibility sounds, including extension-defined signals or custom tones.

## Best solution

Design an extension-facing accessibility-signal API that preserves semantic meaning and consistent user controls. Settle whether the initial contract includes extension-defined signals and generated audio, rather than exposing unrestricted playback of internal sounds.

- **Fit:** aligned

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts`, `src/vs/workbench/contrib/accessibility/browser/accessibilityConfiguration.ts`, `src/vs/workbench/contrib/accessibilitySignals/browser/commands.ts`
- **Validation:** After agreeing on the API contract, use a minimal extension to trigger the agreed signals on command failure and bookmark addition/removal/navigation. Verify distinct semantic feedback, disabled-signal and volume preferences, unchanged built-in signals, and operation without a webview in desktop and web extension hosts; add executable extension-API coverage for the agreed contract.
- **Behavior:**

  > Extension authors cannot currently request accessibility-signal playback through a supported VS Code API. The goal is meaningful nonvisual feedback for extension events such as an empty search result or bookmark state change, without requiring a webview solely for audio. Acceptance must demonstrate the agreed extension API, consistent user enablement and volume controls, and no change to existing built-in signal behavior. Whether custom generated tones are included in the initial contract remains a product decision.
- **Trace:**

  > IAccessibilitySignalService.playSignal in src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts already applies sound and announcement enablement, while playSound uses bundled media and configured volume. AccessibilitySignal construction and registration are private, and searches of src/vscode-dts and src/vs/workbench/api found no extension playback bridge. The commands in src/vs/workbench/contrib/accessibilitySignals/browser/commands.ts configure and preview internal signals rather than offering programmatic playback. https://github.com/microsoft/vscode/issues/175986#issuecomment-1840483826 establishes a preference for semantic signals, but leaves the public contribution and playback contract unsettled. https://github.com/microsoft/vscode/issues/145204 concerns sound themes and should inform compatibility, not absorb this API request. Preserve existing built-in signal semantics and user controls; the extension-host bridge and contribution schema remain design work rather than an identified bounded patch.
- **Open decisions:**
  - Should extensions initially trigger shared semantic signals, declare and trigger their own signals, or support both under an explicit ownership contract?
  - Does the initial API support generated tones or audio streams, or only semantic signals mapped to default sound assets?
  - How should extension-defined signals appear in the shared preferences experience, and which user customization guarantees belong in the public contract?
