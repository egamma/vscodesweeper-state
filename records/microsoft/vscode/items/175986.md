# Issue #175986 — Allow VS Code extensions to trigger audio cues

[https://github.com/microsoft/vscode/issues/175986](https://github.com/microsoft/vscode/issues/175986)

## Summary

Keep this accepted accessibility API request open: current core signal playback does not expose extension-triggered or extension-contributed signals. The request has 23 upvotes and concrete extension use cases, but its public contract needs maintainer design before implementation.

## Change summary

Allow extensions to trigger semantic accessibility signals and potentially contribute custom sounds or generated tones without requiring a webview.

## Best solution

Design an extension-facing semantic signal API that respects centralized accessibility preferences and supports meaningful extension-specific events. Settle whether arbitrary audio generation belongs in that contract or remains a separate capability.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts`, `src/vs/workbench/contrib/accessibility/browser/accessibilityConfiguration.ts`, `src/vs/workbench/contrib/accessibilitySignals/browser/commands.ts`
- **Validation:** After agreeing on the contract, use a test extension in desktop and web to trigger a command-failure signal and bookmark add/remove/navigation signals without opening a webview. Verify disabled signals remain silent, enabled signals play, and contributed signals are discoverable and configurable alongside core signals. Add extension-host/main-thread contract tests and signal-service tests for the selected ownership and enablement rules.
- **Behavior:**

  > Extensions need nonvisual feedback for events such as command failure and bookmark navigation without creating a webview solely for audio. The desired capability must preserve meaningful signal semantics and user control over playback. Acceptance should exercise distinct extension events on desktop and web and verify centralized enablement and discoverability. Whether generated tones and arbitrary audio are included remains a product-contract decision.
- **Trace:**

  > IAccessibilitySignalService.playSignal in src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts already combines sound and announcement behavior with configured enablement. AccessibilitySignal has private construction and registration, and the inspected public declarations, API factory, and extension-host protocol contain no corresponding extension signal bridge. ShowSignalSoundHelp in src/vs/workbench/contrib/accessibilitySignals/browser/commands.ts enumerates allAccessibilitySignals for preview and configuration; it is not an extension playback API. The maintainer direction at https://github.com/microsoft/vscode/issues/175986#issuecomment-1840483826 favors semantic identity and considers extension-owned declarations, while later comments request generated audio and unified preferences. Preserve existing core signal meanings and enablement behavior; do not treat the settings preview's enablement bypass as normal playback semantics. https://github.com/microsoft/vscode/issues/145204 concerns sound themes and is related design context, not a canonical duplicate.
- **Open decisions:**
  - May extensions trigger existing core semantic signals, only signals they contribute, or both?
  - Does the initial public contract support only declarative semantic signals with default sound files, or also generated tones, streams, and arbitrary audio playback?
  - What user-facing configuration and customization contract should extension-contributed signals share with core accessibility signals?

## Evidence

- **Existing capability and remaining gap:** src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts exposes internal IAccessibilitySignalService.playSignal, but AccessibilitySignal construction and registration are private. Searches of src/vscode-dts/vscode.d.ts, src/vs/workbench/api/common/extHost.api.impl.ts, and src/vs/workbench/api/common/extHost.protocol.ts found no corresponding audio or accessibility-signal API.
- **Settings and commands do not satisfy the request:** src/vs/workbench/contrib/accessibilitySignals/browser/commands.ts registers signals.sounds.help, which opens a picker to preview and configure registered core sounds. src/vs/workbench/contrib/accessibility/browser/accessibilityConfiguration.ts registers accessibility.signals.* preferences; neither surface lets an extension contribute or programmatically trigger its own semantic signal.
- **Maintainer design direction:** https://github.com/microsoft/vscode/issues/175986#issuecomment-1840483826 supports considering an API, emphasizes reuse by semantics rather than by sound, and suggests statically contributed signals with configurable default sounds. This is a design suggestion, not a settled public contract.
