# Issue #175986 — Allow VS Code extensions to trigger audio cues

[https://github.com/microsoft/vscode/issues/175986](https://github.com/microsoft/vscode/issues/175986)

## Summary

Keep open: current source provides internal accessibility-signal playback, but no extension API covering this request. The accepted Backlog item has 23 upvotes, multiple concrete use cases, and maintainer interest; its public API contract needs design before implementation.

## Change summary

Allow extensions to trigger semantic accessibility signals and contribute additional cues, potentially including generated tones.

## Best solution

Design an extension-facing accessibility-signal contract that preserves semantic meaning and integrates extension signals into user preferences. Settle the initial scope of existing-signal reuse, contributed semantics, and custom audio before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts`, `src/vs/workbench/contrib/accessibilitySignals/browser/commands.ts`, `src/vs/workbench/contrib/accessibility/browser/accessibilityConfiguration.ts`
- **Validation:** After the contract is agreed, use a sample extension on desktop and web to trigger a supported signal from a command and cursor-navigation event without creating a webview. Verify audible feedback when enabled, silence when disabled, global-volume behavior, and discovery/configuration of any contributed signals alongside core signals. If generated tones are included, verify the requested 440 Hz, 150 ms cue under the same agreed controls.
- **Behavior:**

  > Extension authors need nonvisual feedback for command outcomes and navigation events without creating a webview solely for audio. The supported contract should let an extension trigger meaningful accessibility signals while respecting user sound preferences. Bookmarks supplies a concrete acceptance scenario: feedback when a bookmark is added, encountered, or removed. The initial release must explicitly distinguish supported semantic signals from any deferred arbitrary-tone or streaming-audio capability.
- **Trace:**

  > IAccessibilitySignalService and AccessibilitySignal in src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts implement internal playback, semantic signal definitions, enablement, and volume; registration is private and sound resources are bundled. src/vs/workbench/contrib/accessibilitySignals/browser/commands.ts enumerates that registry for signals.sounds.help, while accessibilityConfiguration.ts declares existing signal settings. Searches found no corresponding public or proposed declaration in src/vscode-dts and no playback bridge in src/vs/workbench/api. The existing configuration and preview surfaces therefore do not solve extension-triggered playback. Preserve core signal meanings and user controls; the maintainer guidance at https://github.com/microsoft/vscode/issues/175986#issuecomment-1840483826 favors semantic consistency but leaves the extension contract unsettled. https://github.com/microsoft/vscode/issues/145204 is related sound-theme work, not a duplicate. The uncertainty begins at which semantics extensions may trigger or contribute and whether custom audio belongs in the first API.
- **Open decisions:**
  - May extensions trigger existing built-in semantic signals, only their own contributed signals, or both?
  - Does the initial contract include generated tones or custom audio sources, or only statically contributed semantic signals with default sounds?
  - What configuration contract makes extension signals discoverable and controllable alongside core signals, including defaults and user sound overrides?
