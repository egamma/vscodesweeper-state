# Issue #142946 — [css] Allow extensions to choose to use whether to use CSS default data provider

[https://github.com/microsoft/vscode/issues/142946](https://github.com/microsoft/vscode/issues/142946)

## Summary

The requested extension API gap remains on current main: contributed CSS data is always combined with the built-in provider. A maintainer explicitly welcomed a PR and suggested extending the custom-data format, so this Backlog item should remain open.

## Change summary

Allow an extension-contributed CSS custom-data file to replace, rather than always augment, the built-in CSS data provider.

## Best solution

Extend the CSS custom-data contract with an optional replacement flag, define how that flag composes when several custom-data files are active, and have the bundled CSS language server pass the resulting choice to `setDataProviders`.

## Plan brief

- **Likely files:** `extensions/css-language-features/server/src/customData.ts`, `extensions/css-language-features/server/src/cssServer.ts`, `extensions/css-language-features/server/src/test/customData.test.ts`
- **Validation:** Run `npm test --prefix extensions/css-language-features/server` with tests proving that ordinary custom data retains built-in completions, replacement custom data suppresses them while retaining contributed completions, and multiple-provider behavior matches the agreed contract.
- **Behavior:**

  > An extension can mark contributed CSS custom data as replacing the built-in CSS data rather than augmenting it. Without that marker, existing custom-data behavior remains unchanged. Replacement mode omits built-in properties, at-rules, pseudo-classes, and pseudo-elements while retaining all contributed data. The behavior for multiple active custom-data files is deterministic and documented.
- **Trace:**

  > `updateDataProviders` in `extensions/css-language-features/server/src/cssServer.ts` currently passes the literal `true` to `setDataProviders`, so the default provider is always installed. `fetchDataProviders` and `parseCSSData` in `extensions/css-language-features/server/src/customData.ts` return only `ICSSDataProvider` instances and discard top-level metadata. The language service already supports the required switch through `CSSDataManager.setDataProviders(builtIn, providers)`, but the current schema in https://github.com/microsoft/vscode-css-languageservice does not expose it. Preserve augmentation as the compatibility default and do not alter completion behavior for existing custom-data files. The uncertainty begins at aggregation semantics when several workspace or extension-contributed files are active.
- **Open decisions:**
  - When multiple custom-data files are active, should one file requesting replacement disable the built-in provider globally, or must replacement be expressed at the contribution-set level?
  - Should replacement apply uniformly to CSS, SCSS, and Less language services, or can the public contract scope it by language?

## Evidence

- **current source:** `extensions/css-language-features/server/src/cssServer.ts` still calls `languageServices[lang].setDataProviders(true, customDataProviders)`, unconditionally retaining the built-in provider.
- **custom-data parsing:** `extensions/css-language-features/server/src/customData.ts` parses only version, properties, at-directives, pseudo-classes, and pseudo-elements; it does not preserve replacement metadata.
- **public schema:** The current `docs/customData.schema.json` in https://github.com/microsoft/vscode-css-languageservice has no `useDefaultDataProvider` or equivalent property, so the public custom-data contract still lacks this capability.
- **maintainer direction:** A VS Code member confirmed the intended replacement-provider use case and invited a PR, suggesting a new property in the custom-data file: https://github.com/microsoft/vscode/issues/142946.
- **related capability:** https://github.com/microsoft/vscode/issues/135459 added extension-provided computed custom data, but it does not cover replacing the default provider and is therefore not a canonical duplicate.
- **canonical search:** Searches across open and closed VS Code and vscode-css-languageservice issues and PRs found no older issue or active PR owning the same replacement-provider request.
