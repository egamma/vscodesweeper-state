# Issue #339156 — [AutomaticInstructionsCollector] Core vs extension instructions mismatch filling the chat log

[https://github.com/microsoft/vscode/issues/339156](https://github.com/microsoft/vscode/issues/339156)

## Summary

Confirmed from source: on every agent turn (while the chat.experimental.collectInstructionsInExtension migration flag is off, the current default path), CustomInstructionsReferenceLogger.compare() recomputes the extension-side instruction collection and, on any mismatch with core, logs the full unbounded diff at Info level — exactly explaining the 33k-line log dump the reporter saw. This is real log spam worth fixing, though the user's belief that it inflated the model's context window is unconfirmed (the diff goes to the log output, not into promptContext.chatVariables).

## Change summary

A huge, unbounded core-vs-extension instruction parity diff is logged at Info level on every agent turn when the two sides disagree, flooding the Copilot Chat output log.

## Best solution

Gate or quiet the parity-check logging in CustomInstructionsReferenceLogger.compare() — e.g. cap the diff size, drop it to trace level, and/or restrict the comparison to internal/canary builds now that it's an in-flight migration diagnostic rather than a user-facing feature — while leaving actual instruction collection/resolution untouched.

- **Behavior:**

  > On every agent chat turn, whenever the core-supplied instruction references differ at all from what AutomaticInstructionsCollector.collect() computes in the extension, the full unbounded diff — including raw index-file markdown content — is written to the visible Copilot Chat output log at Info level. In workspaces with many instruction files (multi-root workspaces, or AGENTS.md/.instructions.md files reachable under node_modules), this can balloon to tens of thousands of log lines per turn. The fix should stop this unconditional, unbounded, user-visible log spam (cap size, lower log level, and/or restrict to internal builds) without changing which instructions are actually resolved or sent to the model.
- **Trace:**

  > CustomInstructionsReferenceLogger.compare() (extensions/copilot/src/platform/promptFiles/node/automaticInstructionsCollector.ts:867-886) is invoked unconditionally from the agent intent's buildPrompt() (extensions/copilot/src/extension/intents/node/agentIntent.ts:682-690) whenever chat.experimental.collectInstructionsInExtension is not true. It recomputes the extension-side collection, compares to core's, and on mismatch calls ICustomInstructionsDebugInfo.formatDiff(coreInfo, extInfo, true) (same file, ~line 947), producing an uncapped diff plus a raw content diff via formatStringDiff, then logs it with this._logService.info(...) at line 878 — Info being the default visible log level (extensions/copilot/src/platform/log/common/logService.ts). This path is independent of promptContext.chatVariables, so it does not actually reach the model prompt; the confirmed defect is log-channel verbosity, not context-window inflation. Boundary: do not alter collector.collect()'s actual instruction-resolution output or what gets merged into chatVariables — only the comparison/logging behavior is in scope. Where uncertainty starts: whether the team still needs this parity signal broadly (e.g. for finishing the collectInstructionsInExtension rollout) or can retire/gate it now.
- **Open decisions:**
  - Should the core-vs-extension parity check (compare()) keep running for all users, or be restricted to internal/canary builds now that it produces large, user-visible log output?
  - Should mismatch diffs be truncated/capped and/or logged at trace instead of info to avoid flooding the default Copilot Chat output channel?
  - Does the reported mismatch content itself (duplicated AGENTS.md entries pulled from nested node_modules) indicate a real divergence bug in how core vs. extension enumerate instruction files, separate from the logging verbosity, that also needs investigation?
