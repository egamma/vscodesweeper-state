# Issue #200419 — Git - input validation got broken in 1.85.0

[https://github.com/microsoft/vscode/issues/200419](https://github.com/microsoft/vscode/issues/200419)

## Summary

Keep open for the remaining validation-default and UX decisions. Diagnostics have replaced the overlapping warning, but validation remains disabled by default and still underlines entire overlong lines; the maintainer explicitly accepted further refinement.

## Change summary

Restore discoverable commit-message length guidance, with clearer over-limit feedback and reconsideration of the disabled default.

## Best solution

Finish the Git commit-input validation UX so users can identify excess characters without obscuring the Commit button, and settle whether validation should again be enabled by default. Preserve the existing opt-out and hard-wrap quick fixes.

- **Behavior:**

  > Users want commit-length guidance to be discoverable and useful while composing messages, rather than unexpectedly absent or requiring hover and manual counting. With validation enabled, subject and body limits should produce clear feedback that does not obscure committing. The maintainer must settle the default and whether excess-character underlining alone is sufficient or a visible overflow count is also needed. Acceptance should cover exact-limit and over-limit messages, explicit opt-out, and existing wrapping actions.
- **Trace:**

  > extensions/git/package.json registers git.inputValidation as a boolean with default false and thresholds of 50 for the subject and 72 for subsequent lines. GitCommitInputBoxDiagnosticsManager.onDidChangeTextDocument in extensions/git/src/diagnostics.ts exits when validation is disabled; when enabled, it computes the overflow count but attaches diagnostics to the whole line. GitCommitInputBoxCodeActionsProvider uses diagnostic ranges for both action selection and replacement edits, so changing visible diagnostic coverage must not truncate text during wrapping. The current localized description already includes commit/message terminology. The maintainer accepted further UX work and discussed restoring the default at https://github.com/microsoft/vscode/issues/200419#issuecomment-1979047489. Preserve explicit user preferences and keep the distinct migration bug at https://github.com/microsoft/vscode/issues/301463 outside this work's scope. Source inspection establishes the current capability; uncertainty starts at the desired default and presentation contract, not whether validation exists.
- **Open decisions:**
  - Should commit-message validation be enabled by default again, or remain an explicit opt-in?
  - Should feedback identify only excess characters through diagnostics, or also display the current line's overflow count without requiring hover?
