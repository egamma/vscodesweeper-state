# Issue #301701 — Searching for a commit (going from git blame to source control graph)

[https://github.com/microsoft/vscode/issues/301701](https://github.com/microsoft/vscode/issues/301701)

## Summary

The requested navigation remains missing: blame can open a commit's changes, but cannot reveal that arbitrary commit in the Source Control Graph. Keep this open; the related filtering request does not cover the same observable workflow.

## Change summary

Allow users to reveal a commit in the Source Control Graph directly from Git blame information or by entering its hash.

## Best solution

Provide discoverable, keyboard-accessible navigation from a known commit hash to its selected graph row, including commits not yet loaded. Decide how navigation interacts with repository selection and graph filters; terminal hash links are an additional entry point, not a prerequisite for the original request.

- **Behavior:**

  > Users who already know a commit from Git blame should be able to locate that commit in the built-in Source Control Graph without manually scrolling through history. The graph should reveal and select the exact commit, including when its row has not yet been loaded. Existing Open Commit behavior must remain available. Acceptance includes keyboard access and a defined outcome when the target is outside the active graph filter. Terminal Ctrl+click links are a related follow-up entry point, not required to satisfy the original blame workflow.
- **Trace:**

  > Git blame hover actions originate in extensions/git/src/blame.ts and use getHoverCommitHashCommands in extensions/git/src/hover.ts. The hash action invokes Commands.viewCommit in extensions/git/src/commands.ts, which opens a multi-diff editor rather than navigating the graph. SCMHistoryViewPane.revealCurrentHistoryItem in src/vs/workbench/contrib/scm/browser/scmHistoryViewPane.ts can load and select the current revision, but obtains that revision from historyItemRef rather than accepting an arbitrary commit. Graph keyboard navigation labels expose message and author only. The trace establishes the missing entry point and current-revision boundary; uncertainty starts at behavior for commits outside the active repository/filter. Preserve existing commit inspection and graph filtering semantics unless the maintainer explicitly chooses otherwise. https://github.com/microsoft/vscode/issues/253585 concerns message-based exclusion and is not a canonical for this navigation request.
- **Open decisions:**
  - When the requested commit is excluded by the active graph filter, should navigation change that filter to reveal it, or preserve the filter and offer an explicit way to include the commit?
