# Issue #145883 — [html] don't show closing element proposal as first entry if element is already closed later

[https://github.com/microsoft/vscode/issues/145883](https://github.com/microsoft/vscode/issues/145883)

## Summary

Keep open as a valid HTML completion-ranking improvement: a maintainer agreed that an end-tag proposal already satisfied later in the document should be sorted lower, and no verified canonical or implemented fix is identified.

## Change summary

Rank an HTML closing-tag completion below other suggestions when the corresponding element is already closed later in the document.

## Best solution

Teach the HTML language service's completion ranking to inspect following content and reduce the priority of an already-satisfied closing tag without removing it, preserving useful suggestions for nested common elements.

## Plan brief

- **Likely files:** `extensions/html-language-features/server/src/htmlServer.ts`
- **Validation:** Add or identify an HTML completion test for `<header>\n\t<\n</header>` that verifies the `/header` proposal remains available but is ranked below appropriate alternatives.
- **Behavior:**

  > Inside an HTML element that already has a matching closing tag later in the document, typing `<` should not place that element's closing-tag proposal first. The proposal should remain available because inserting an earlier close can be valid for nested common elements. Completion behavior outside this already-closed-later case must remain unchanged.
- **Trace:**

  > The issue records that HTML completion currently does not inspect content after the completion position. A maintainer explicitly favored lowering, rather than removing, the already-satisfied closing-tag proposal. The likely entry point is the HTML language feature server under extensions/html-language-features/server/src/htmlServer.ts, but ownership of ranking between VS Code integration and the HTML language service still needs tracing. Do not alter generic suggest-widget ordering or suppress valid closing-tag proposals globally. The cross-reference https://github.com/microsoft/vscode/issues/145550 is an accessibility issue about focused IntelliSense updates, not a canonical for this behavior.
- **Open decisions:**
  - Should the proposal receive a deterministic lower rank whenever a matching close exists later, or only when that later close matches the currently open element at the same structural nesting level?
