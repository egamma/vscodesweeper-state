# Issue #74342 — [themes] Allow to set a background color for settings / webview editors

[https://github.com/microsoft/vscode/issues/74342](https://github.com/microsoft/vscode/issues/74342)

## Summary

A real theming gap remains on current main: the Settings editor and extension details editor still inherit the text editor background, while no semantic color exists for their overall background or foreground. The issue is already accepted into the Backlog with `help wanted`, and no verified canonical owns this specific request.

## Change summary

Allow themes to give Settings and rich informational editors background and foreground colors distinct from code editors.

## Best solution

Introduce semantic theme colors for non-code editor surfaces, preserving `editor.background` and the existing foreground as defaults so current themes do not change. A maintainer should first settle whether Settings and rich editors share colors or receive surface-specific tokens, and which core editors belong to the rich-editor category.

## Vision fit

- **Fit:** aligned
- **Reason:** Semantic colors that distinguish code from informational workbench editors improve settings fidelity while preserving the existing theme system and default appearance.
- **Evidence:** Durable theme: “Workbench & core UX — layout flexibility, profiles, settings fidelity”; the proposed semantic tokens also retain the value of simple, uniform UI by centralizing the distinction in themes rather than adding per-view user controls.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/preferences/common/settingsEditorColorRegistry.ts`, `src/vs/workbench/contrib/preferences/browser/settingsTree.ts`, `src/vs/workbench/contrib/preferences/browser/tocTree.ts`, `src/vs/workbench/contrib/preferences/browser/media/settingsEditor2.css`, `src/vs/workbench/contrib/extensions/browser/media/extensionEditor.css`
- **Validation:** Add or extend theme-color registry coverage for the chosen semantic colors, then launch the workbench with contrasting `editor.background` and new surface-color overrides and verify that Settings and each approved rich-editor surface change while text editors and unspecified themes retain their existing appearance.
- **Behavior:**

  > Themes can style the Settings editor and the approved rich informational editor surfaces independently from code editors, including both background and foreground where the plan decides those are supported. Code editors continue using `editor.background` and `editor.foreground`. Themes that do not provide the new colors render exactly as before through compatible defaults. Acceptance requires checking Settings, every rich-editor surface included in scope, and an ordinary text editor with deliberately contrasting colors.
- **Trace:**

  > The Settings color registry in src/vs/workbench/contrib/preferences/common/settingsEditorColorRegistry.ts has component-level tokens but no overall background or foreground. SettingsTree and TOCTree explicitly map list backgrounds to `editorBackground`; the outer editor part also receives `editorBackground` in src/vs/workbench/browser/parts/editor/editorPart.ts. The extension details surface in src/vs/workbench/contrib/extensions/browser/media/extensionEditor.css supplies layout styling without a distinct surface background. Preserve current defaults and text-editor styling; do not redesign individual Settings controls or expose arbitrary per-webview overrides. https://github.com/microsoft/vscode/issues/32813 is related theme infrastructure work but does not own this user-visible separation.
- **Open decisions:**
  - Should Settings and all core rich informational editors share one semantic background/foreground pair, or should Settings and extension/rich editors expose separate color tokens?
  - Which core surfaces count as rich informational editors for this request: only extension details, or also release notes, Markdown preview, and other webview-backed editors?
  - Should foreground customization apply to the entire selected surfaces, or only to text that currently inherits the general workbench foreground?

## Evidence

- **current source:** src/vs/workbench/contrib/preferences/common/settingsEditorColorRegistry.ts registers colors for Settings headers, rows, and controls, but no overall Settings editor background or foreground color.
- **settings inheritance:** src/vs/workbench/contrib/preferences/browser/settingsTree.ts and tocTree.ts explicitly style their list backgrounds with `editorBackground` and their primary text with the general `foreground`, so the requested separation is absent on current main.
- **editor container:** src/vs/workbench/browser/parts/editor/editorPart.ts applies `editorBackground` to the shared editor-part container, while src/vs/workbench/contrib/extensions/browser/media/extensionEditor.css does not establish a distinct semantic background for the extension details editor.
- **related issue:** https://github.com/microsoft/vscode/issues/32813 is open and older, but it concerns programmatic access to theme and token colors for extension APIs, not independently theming Settings or rich editor surfaces; it is therefore not a valid duplicate canonical under the re-review rule.
- **maintainer disposition:** A maintainer clarified the request as separate colors for the Settings editor and rich editor, then passed it along; the issue is currently in the Backlog with `help wanted`, `feature-request`, `themes`, and `settings-editor`.
