# Issue #340350 — Gemini rejects WorkIQ retrieve MCP schema with invalid_request_body before invocation

[https://github.com/microsoft/vscode/issues/340350](https://github.com/microsoft/vscode/issues/340350)

## Summary

Well-diagnosed report with a clean A/B workaround; tracing the schema normalizer confirms a real gap — Gemini-family tool schemas only get nested-nullable and top-level anyOf/oneOf handling, not nested anyOf/const unions like WorkIQ's retrieve.capabilities, so these reach Gemini unnormalized and the model backend rejects the whole request before any tool call.

## Change summary

Gemini models reject an otherwise-valid MCP tool schema (nested anyOf/const capability union) with an opaque 400 invalid_request_body before any tool invocation.

## Best solution

Extend the Gemini-specific rules in extensions/copilot/src/extension/tools/common/toolSchemaNormalizer.ts to also normalize nested anyOf/oneOf and const discriminators (not just top-level, and not just nullable arrays), or at minimum surface a precise unsupported-schema diagnostic instead of letting the raw 400 propagate — a maintainer should decide which.

- **Behavior:**

  > Enabling an MCP tool whose schema contains a nested, optional array-of-nullable-objects property with an anyOf union of const-discriminated branches (like WorkIQ's retrieve.capabilities) should not cause Gemini models to reject the entire chat request with an opaque 400 before any tool call. Either the schema should be normalized into a Gemini-compatible form (as already done for simple nullable unions), or the extension should surface a precise, actionable diagnostic identifying the offending tool/schema instead of an opaque invalid_request_body.
- **Trace:**

  > normalizeToolSchema() in extensions/copilot/src/extension/tools/common/toolSchemaNormalizer.ts runs jsonSchemaRules over each tool's parameter schema. The Gemini-specific rule (lines 171-196) only rewrites `type: [T, "null"]` arrays into OpenAPI `nullable`. The separate oneOf/anyOf/allOf-stripping rule (lines 130-139) only inspects the schema root (`schema.hasOwnProperty(key)`), not nested nodes, unlike the array-items rule at lines 157-170 which correctly uses forEachSchemaNode. WorkIQ's retrieve.capabilities is a nested array of nullable objects whose items use anyOf with const discriminators — nested, so it is untouched and forwarded to Gemini as-is. Boundary: do not change behavior for gpt4ish/claude families (those already strip anyOf at top level only, intentionally per the existing comment 'validated this fails both for claude and 4o'); do not touch the existing nullable-array conversion. Refs: https://github.com/microsoft/vscode/issues/340350 (this issue); file extensions/copilot/src/extension/tools/common/toolSchemaNormalizer.ts.
- **Open decisions:**
  - Should the normalizer attempt to transform nested anyOf/const unions into a Gemini-compatible schema (and if so, how — merge branches into one permissive object, pick/flatten per discriminator, or emulate the reporter's JSON-string-encoding workaround), or should it instead detect this case and fail fast with a clear, user-facing 'unsupported schema' error naming the offending tool and field?
  - Should any schema transformation here risk changing validation semantics (as the existing nullable-union rule already does for multi-type unions), or is a hard error preferred when a lossless conversion isn't possible?

## Evidence

- **existing Gemini rule is narrow:** extensions/copilot/src/extension/tools/common/toolSchemaNormalizer.ts lines 171-196: the Gemini-specific jsonSchemaRule only converts `type: [T, "null"]` arrays to OpenAPI `nullable`; it does nothing for `anyOf`/`oneOf`/`const` discriminators.
- **anyOf/oneOf stripping is top-level only:** The rule at lines 130-139 removes `oneOf`/`anyOf`/`allOf`/... but only checks `schema.hasOwnProperty(key)` on the root schema object — it does not recurse via forEachSchemaNode, so nested anyOf/const (as in WorkIQ's `retrieve.capabilities` items) pass through untouched for every model family, including Gemini.
- **model family matches:** extensions/copilot/src/platform/endpoint/common/chatModelCapabilities.ts defines isGeminiFamily(), used by the normalizer's family check at line 173, consistent with the reported `gemini-3.8-flash` family.
- **reporter's workaround corroborates:** Replacing the nested anyOf/const union with a flat nullable string (JSON-encoded) made the request succeed for Gemini — exactly the kind of transformation the normalizer already does for nullable unions but not for anyOf/const unions.
