# Issue #206824 — Git - git doesn't find anymore the config from my home which is on a remote server

[https://github.com/microsoft/vscode/issues/206824](https://github.com/microsoft/vscode/issues/206824)

## Summary

Still-valid report that VS Code's built-in Git integration resolves the user's home (and therefore `.gitconfig`/`.ssh`) to `%USERPROFILE%` while Git for Windows in the same machine's terminal honours `HOME`/`HOMEDRIVE`+`HOMEPATH`/`HOMESHARE`; it is parked in Backlog with no fix on main, and four independent reporters describe the same behavior, so it should stay open under the `git` area.

## Change summary

On Windows with a roaming/network home directory (HOMESHARE / HOMEDRIVE+HOMEPATH), git commands spawned by the built-in Git extension do not pick up `.gitconfig` and `.ssh` from the network home, so authentication fails even though the same repo works from the terminal.

## Best solution

Make the environment the Git extension passes to spawned `git` processes preserve the Windows home-resolution variables the user's shell has (`HOME`, `HOMEDRIVE`/`HOMEPATH`, `HOMESHARE`) instead of effectively pinning the home to `%USERPROFILE%` — the fix belongs in the spawn/env plumbing in `extensions/git/src/git.ts` (and whatever sanitizes the env it inherits), with the askpass crash in `askpass-main.js` hardened separately so a missing credential prompt argument doesn't throw a raw `TypeError`.

## Plan brief

- **Likely files:** `extensions/git/src/git.ts`, `extensions/git/src/askpass.ts`, `extensions/git/src/askpass-main.ts`
- **Validation:** On a Windows setup where `HOMESHARE`/`HOMEDRIVE`+`HOMEPATH` point at a network home containing `.gitconfig` and `.ssh` (and `%USERPROFILE%` does not), `git config --global --list` run via the extension's git spawn path returns the same values as the integrated terminal's `git`, and a fetch/push over SSH succeeds without copying credentials locally.
- **Behavior:**

  > On Windows with a domain/network home directory, git operations run from VS Code's Source Control UI must resolve the global config and SSH keys the same way Git for Windows does from the terminal — honouring `HOME`, then `HOMEDRIVE`+`HOMEPATH`, then `USERPROFILE` — instead of only `%USERPROFILE%`. Acceptance: with `.gitconfig`/`.ssh` only on the network home, fetch/push from the UI succeeds, and `git config --global --list` through the extension matches the terminal. Secondary acceptance: when askpass receives an unexpected prompt/argv shape it reports a readable error rather than an unhandled `TypeError` with a dumped bundle.
- **Trace:**

  > The Git extension builds the child-process environment in `extensions/git/src/git.ts` (spawn/exec helpers merging `process.env` with extension-supplied vars) and injects the askpass hooks from `extensions/git/src/askpass.ts`; the reports indicate the spawned git sees a home resolving to `%USERPROFILE%` while the integrated terminal's git resolves the network share, so the first step is to compare the actual env (HOME, HOMEDRIVE, HOMEPATH, HOMESHARE, USERPROFILE) in the extension host / spawned git versus the terminal on such a machine and find where they diverge (Electron/main-process env handling is a candidate). The stack in the report also points at `extensions/git/src/askpass-main.ts`, where ssh prompt parsing indexes fixed argv positions and throws on a mismatch. Boundary: do not change credential storage or the askpass IPC protocol, and do not alter home resolution on macOS/Linux. Ref: https://github.com/microsoft/vscode/issues/206824
- **Open decisions:**
  - Should the Git extension explicitly replicate Git for Windows' home resolution order (HOME → HOMEDRIVE+HOMEPATH → HOMESHARE → USERPROFILE) for spawned git processes, or is the correct fix to stop VS Code from altering those variables at all?
  - If the network home is unreachable, what is the user-visible fallback — fail with a clear Source Control error, or silently fall back to %USERPROFILE% as today?
  - Should the askpass argv-shape failure surface as a user-facing Git error message, and is hardening it in scope for this issue or a separate one?
