# Issue #285492 — Feature Request: Add workspace-relative variant of ${resultsFiles} for search commands

[https://github.com/microsoft/vscode/issues/285492](https://github.com/microsoft/vscode/issues/285492)

## Summary

Keep this accepted, 27-upvote request open, but clarify its product boundary: ${resultsFiles} belongs to Find and Transform, not VS Code's built-in variable resolver, and core already accepts absolute search paths. Reliable reuse of result files remains worth designing; neither the reported root cause nor a duplicate close is established.

## Change summary

Provide a supported way to restrict successive workspace searches to files returned by the preceding search, including multi-root and remote workspaces.

## Best solution

Define a supported result-file handoff that preserves workspace identity and works with follow-up search commands. First decide whether core should expose result-file data for extensions or provide a built-in search-scoping capability, rather than treating an extension-defined variable as an existing core contract.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/search/browser/searchActionsBase.ts`, `src/vs/workbench/contrib/search/browser/searchActionsCopy.ts`, `src/vs/workbench/services/configurationResolver/common/variableResolver.ts`, `src/vs/workbench/services/search/common/queryBuilder.ts`
- **Validation:** The plan should end with an executable search-command regression covering two successive queries: the second searches complete files from the first result set, excludes other files, and correctly distinguishes identical relative filenames in separate workspace roots. Include a remote-workspace case preserving URI authority and retain existing absolute-path include behavior.
- **Behavior:**

  > Users want to search for one term and then search complete files containing that term for another term, without manually copying or rewriting result paths. The supported handoff must identify the correct files in single-root, multi-root, and remote workspaces. Acceptance should distinguish identically named files in different roots and ensure the second query does not search unrelated files. Existing extension variable behavior and absolute-path search inputs must remain compatible.
- **Trace:**

  > The example invokes Find and Transform's runInSearchPanel command, and that extension defines ${resultsFiles}; it is not a built-in variable found in the checked VS Code resolver. In core, findInFilesCommand in src/vs/workbench/contrib/search/browser/searchActionsBase.ts resolves string arguments through IConfigurationResolverService, while QueryBuilder.parseSearchPaths and expandOneSearchPath in src/vs/workbench/services/search/common/queryBuilder.ts already accept absolute paths and handle workspace-qualified relative paths. GetSearchResultsAction in src/vs/workbench/contrib/search/browser/searchActionsCopy.ts exposes formatted result text, not a typed workspace-preserving file-list contract. The trace therefore does not confirm the report's claimed absolute-path limitation; uncertainty starts at which new core contract is appropriate. https://github.com/microsoft/vscode/issues/20530 provides related file-set-search design context, not a verified duplicate. Preserve existing input semantics and do not assume core can alter an extension-owned variable.
- **Open decisions:**
  - Should VS Code expose workspace-preserving result-file data for extension consumers, or offer a built-in command/variable that scopes a subsequent search directly?
  - What should the supported handoff do with result files outside workspace roots or across different URI authorities?
