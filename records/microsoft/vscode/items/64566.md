# Issue #64566 — Interactive Diagnostics 

[https://github.com/microsoft/vscode/issues/64566](https://github.com/microsoft/vscode/issues/64566)

## Summary

Keep open: configurable hover length and interactive quick-info verbosity address some comments, but neither provides lazy, nested expansion within diagnostic messages. The current diagnostic API and renderer still lack that capability, and the verified older related issues cover formatting rather than the same interaction.

## Change summary

Allow diagnostic messages to expose lazily resolved, nested expandable spans, with progress feedback and consideration for inline highlighting and definition links.

## Best solution

Design a language-neutral diagnostic expansion contract and consistent interaction across diagnostic hovers, Problems, and F8 navigation, then coordinate language-service adoption. Reuse relevant hover capabilities without treating whole-hover expansion or a larger truncation limit as completion of per-span diagnostic exploration.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/contrib/hover/browser/markerHoverParticipant.ts`, `extensions/typescript-language-features/src/languageFeatures/hover.ts`
- **Validation:** The plan should end with an extension-backed acceptance scenario: display T<...> in a diagnostic, expand one span asynchronously with visible pending feedback, then expand a nested span without eagerly resolving unrelated content. Verify keyboard operation, cancellation/error behavior, and the agreed state-sharing semantics across hover, Problems, and F8; ordinary string diagnostics must remain unchanged.
- **Behavior:**

  > Users should be able to explore omitted portions of a diagnostic incrementally instead of choosing between permanently truncated and fully expanded messages. An expansion is resolved only when requested and may introduce further expandable portions. Pending work must provide progress feedback. Acceptance must distinguish this from merely increasing hover length or replacing an entire quick-info hover.
- **Trace:**

  > Diagnostic in src/vscode-dts/vscode.d.ts currently exposes a string message and static related information, while MarkerHoverParticipant._renderMarkerHover in src/vs/editor/contrib/hover/browser/markerHoverParticipant.ts renders that message as plain text. TypeScriptHoverProvider.provideHover in extensions/typescript-language-features/src/languageFeatures/hover.ts already supports quickinfo verbosity, but that is a separate provider path. The thread at https://github.com/microsoft/vscode/issues/64566#issuecomment-445307952 establishes the need for genuinely lazy exploration and discusses cross-surface state. The trace confirms the diagnostic-facing gap, but does not establish the complete API bridge, Problems, F8, or language-service implementation boundary. Preserve existing string diagnostics and avoid making unrelated type information eager; formatting-only work in https://github.com/microsoft/vscode/issues/54272 is related but not a replacement.
- **Open decisions:**
  - What public contract should identify expandable diagnostic spans and resolve nested content, including cancellation and failure behavior?
  - Should expansion state be shared across diagnostic hover, Problems, and F8 navigation, and when should diagnostic updates invalidate it?
  - Must the initial contract support inline syntax classification and definition targets, or only preserve a compatible path for adding them later?
