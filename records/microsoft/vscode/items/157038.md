# Issue #157038 — Undo Command only Un-Deleted/Un-Replaced 2 out of 4 Deleted Files when working on a remove server

[https://github.com/microsoft/vscode/issues/157038](https://github.com/microsoft/vscode/issues/157038)

## Summary

The data-loss path remains in current main: overwriting a destination folder records only the reverse move, so Undo moves the replacement back but does not restore the destination contents that the overwrite deleted.

## Change summary

Undo after dragging a folder over an existing same-named folder can fail to restore all files removed by the replacement, particularly on a remote filesystem.

## Best solution

Make overwrite moves preserve enough destination state for Undo to restore both the moved source and the complete pre-existing destination tree. The design should also prevent the UI from presenting an operation as undoable when a remote provider or size limit makes complete restoration impossible.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/bulkEdit/browser/bulkFileEdits.ts`, `src/vs/workbench/contrib/bulkEdit/test/browser/bulkFileEdits.test.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`
- **Validation:** Add a BulkFileEdits test that starts with distinct source and destination directory trees, performs a move with overwrite, invokes the registered undo element, and verifies that both trees and every original destination file are restored.
- **Behavior:**

  > Dragging a folder over an existing same-named folder and accepting Replace must not make the original destination files irrecoverable through the offered Undo operation. One Undo must restore the moved folder to its source and restore the complete destination tree as it existed before replacement, including files absent from the incoming folder. The behavior must work through remote filesystem providers or clearly prevent an undoable overwrite when complete restoration cannot be supported.
- **Trace:**

  > FileDragAndDrop.doHandleExplorerDropOnMove in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts retries a move conflict with `overwrite: true`. BulkFileEdits converts that edit into RenameOperation in src/vs/workbench/contrib/bulkEdit/browser/bulkFileEdits.ts; RenameOperation delegates the overwrite to IWorkingCopyFileService and creates its inverse only by swapping source and destination URIs. IWorkingCopyFileService.doMoveOrCopy in src/vs/workbench/services/workingCopy/common/workingCopyFileService.ts then delegates directly to IFileService.move, so no operation retains the overwritten destination tree. Existing tests cover restoring explicitly deleted files but not overwrite moves. Keep ordinary non-conflicting move/undo semantics unchanged, and do not limit the investigation to one remote provider because the missing destination state is in the shared bulk-edit path.
- **Open decisions:**
  - Should Undo guarantee restoration of an overwritten directory tree regardless of size, or should VS Code impose a documented backup limit and change the overwrite UX when that limit is exceeded?
  - When a remote filesystem provider cannot support a complete reversible overwrite, should VS Code block the replacement or allow it only with an explicit warning that the removed destination contents cannot be recovered by Undo?

## Evidence

- **current overwrite path:** src/vs/workbench/contrib/files/browser/views/explorerViewer.ts:1988-2015 retries a conflicting drag move as a ResourceFileEdit with `overwrite: true` and sends it through the bulk-edit undo stack.
