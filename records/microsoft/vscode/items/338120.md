# Issue #338120 — Agents: image-preview breadcrumb picker intermittently closes immediately due to delayed webview focus

[https://github.com/microsoft/vscode/issues/338120](https://github.com/microsoft/vscode/issues/338120)

## Summary

Team-authored bug report (hediet, MEMBER) with a thoroughly traced root cause confirmed against current main source; keeping open for a fix, not a close candidate.

## Change summary

In the Agents window's built-in Image Preview editor, the breadcrumb file/outline picker intermittently closes immediately (~8ms after gaining focus) because a stale, delayed webview focus message steals focus back from the picker.

## Best solution

Fix BreadcrumbsControl._onSelectEvent (src/vs/workbench/browser/parts/editor/breadcrumbsControl.ts) to activate the owning editor group without unconditionally stealing DOM focus via `_editorGroup.focus()` when opening the picker, while preserving existing reveal/navigation focus behavior; consider hardening WebviewElement's delayed focus (src/vs/workbench/contrib/webview/browser/webviewElement.ts) to cancel stale focus sends when focus intent changes.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/editor/breadcrumbsControl.ts`, `src/vs/workbench/contrib/webview/browser/webviewElement.ts`
- **Validation:** A deterministic regression test that controls ordering: simulate breadcrumb selection requesting editor focus, then a delayed webview focus send, then picker tree focus — assert the stale webview focus message does not steal focus back from the picker tree (and the reverse ordering where the picker is ready first still works).
- **Behavior:**

  > Clicking the final breadcrumb to open the sibling-file (or outline) picker must keep the picker open and focused until the user picks an item, presses Escape, or deliberately moves focus elsewhere — even when the editor is a webview-based editor (e.g. built-in Image Preview) with a slow, asynchronously-delivered focus message in flight. Normal reveal/navigation focus behavior (including modifier-click/open-to-side) must be unaffected, and `breadcrumbs.useQuickPick` mode must be separately verified.
- **Trace:**

  > `BreadcrumbsControl._onSelectEvent` (src/vs/workbench/browser/parts/editor/breadcrumbsControl.ts:609-622) unconditionally calls `this._editorGroup.focus()` before either revealing an item or opening the picker; the picker closes via `focusTracker.onDidBlur`. `WebviewElement._doFocus` (src/vs/workbench/contrib/webview/browser/webviewElement.ts:953-996) synchronously focuses the outer webview and separately schedules a delayed (50ms `ThrottledDelayer`) `_send('focus', undefined)` that can arrive after the picker's tree has already taken focus, stealing it back. Confirmed unchanged on current main (HEAD 682c0f7d). The boundary: do not change the picker's blur-to-close semantics or replace the race with a larger timeout; preserve existing reveal-in-editor focus transfer. Where uncertainty starts: whether to fix only the picker-opening path (leaving `_editorGroup.focus()` for reveal-in-editor) or also generally harden WebviewElement to cancel stale delayed focus sends, and whether `breadcrumbs.useQuickPick`'s quick-pick path needs an analogous change.
- **Open decisions:**
  - Should the fix be scoped narrowly to the picker-opening branch of _onSelectEvent (using activateGroup instead of focus()), or should WebviewElement's delayed focus mechanism itself be hardened to cancel stale sends when focus intent changes elsewhere?
  - Does the quick-pick variant (breadcrumbs.useQuickPick) need the same fix, or is its focus-stealing risk already mitigated by the existing quick-pick workaround noted in webviewElement.ts?

## Evidence

- **confirmed unconditional focus call:** src/vs/workbench/browser/parts/editor/breadcrumbsControl.ts line 622: `this._editorGroup.focus();` is called unconditionally in `_onSelectEvent` before the picker path, unchanged on current main (last touching commit is unrelated #338193 'sessions: show remote name in session hovers').
- **delayed webview focus mechanism confirmed:** src/vs/workbench/contrib/webview/browser/webviewElement.ts: `_doFocus` (line 960) synchronously focuses the outer webview then schedules `_focusDelayer.trigger(...)` (a 50ms `ThrottledDelayer`, line 148) which later calls `this._send('focus', undefined)` (line 996) — matches the reporter's traced call chain exactly.
- **existing precedent for similar race:** Lines 977-980 in webviewElement.ts already contain a comment/workaround acknowledging webview focus stealing after showing a quick pick, showing this class of race is a recognized but not fully solved problem area.
- **API for fix exists:** `activateGroup` is available on IEditorGroupsService (src/vs/workbench/services/editor/common/editorGroupsService.ts:355), supporting the reporter's proposed approach of activating the group without stealing focus.
