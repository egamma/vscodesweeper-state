# Issue #112107 — Add exists() function to FileSystemProvider

[https://github.com/microsoft/vscode/issues/112107](https://github.com/microsoft/vscode/issues/112107)

## Summary

The public filesystem API still lacks the requested existence check; the internal exists() helper is not available to extensions. Keep this accepted, team-authored Backlog request open for API design, consistent with the maintainer's explicit request to preserve it.

## Change summary

Expose an asynchronous filesystem existence check so extensions need not catch stat() failures for ordinary missing files.

## Best solution

Define a backward-compatible public existence-check contract for extension consumers, preserving stat() behavior and distinguishing absence from operational failures. API owners should decide whether this also requires a provider method or can use existing providers unchanged.

- **Behavior:**

  > Extensions need a portable asynchronous way to determine whether a URI exists without treating an ordinary missing resource as an exception. The motivating workflow checks for an existing destination before offering overwrite, skip, or cancel. Existing stat() callers and existing filesystem providers must remain compatible. Acceptance must cover local and contributed filesystems and explicitly distinguish the agreed behavior for missing resources from permission or availability failures; an existence result must not imply a later write is guaranteed to succeed.
- **Trace:**

  > The public FileSystemProvider and FileSystem declarations in src/vscode-dts/vscode.d.ts lack existence or access methods. ExtHostConsumerFileSystem.value in src/vs/workbench/api/common/extHostFileSystemConsumer.ts exposes stat() through a same-host provider shortcut or MainThreadFileSystem.$stat; _handleError() preserves distinct filesystem failure categories. FileService.exists() in src/vs/platform/files/common/fileService.ts is internal and collapses caught stat failures to false, so it neither exposes the requested capability nor establishes the appropriate public error contract. The existing 'vscode API - workspace-fs' suite covers successful stat(), missing files, and bad schemes. https://github.com/microsoft/vscode/issues/112107 names FileSystemProvider initially but later explicitly asks for workspace.fs.exists(); the record does not settle whether providers need a new method. Preserve stat() semantics and provider compatibility; unrelated permission-elevation and text-search APIs are outside this request.
- **Open decisions:**
  - Should the capability be exposed on workspace.fs only, or also as an optional FileSystemProvider method while retaining compatibility with existing providers?
  - Should the public contract be a pure exists(uri) check or an access-style API, and which failures besides FileNotFound should reject rather than return false?
