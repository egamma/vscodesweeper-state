# Issue #327846 — No visual hierarchy between session and its subsessions

[https://github.com/microsoft/vscode/issues/327846](https://github.com/microsoft/vscode/issues/327846)

## Summary

Keep open: current main records creator relationships but exposes them mainly through ordering and hover, while workspace grouping still uses each child session's worktree label. This leaves the reported parent-child hierarchy and source-workspace identity unclear, and the team-authored issue is protected from judgment closes.

## Change summary

Make the Sessions list visibly communicate which session created each subsession and which source workspace the hierarchy belongs to.

## Best solution

Give creator and child sessions a persistent, glanceable relationship in the Sessions list while retaining the child's worktree as secondary context. The design should define how that relationship behaves across workspace/date grouping, pinning, custom groups, and manual reordering.

## Plan brief

- **Validation:** Add focused Sessions list tests proving that a session with `createdBySession` retains visible creator and source-workspace context across workspace and date grouping, then validate the resulting hierarchy in the Sessions list component fixture.
- **Behavior:**

  > When one session creates another, the Sessions list must make their relationship understandable without requiring a hover. The user must also be able to identify the source project, such as `vscode`, while still distinguishing the child's isolated worktree. Acceptance should cover workspace and date grouping plus the interactions with pinning, custom grouping, and manual ordering.
- **Trace:**

  > `ISession.createdBySession` in src/vs/sessions/services/sessions/common/session.ts already carries the provider-neutral relationship. SessionsList currently consumes it for creator hover data in src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts and SessionsListModelService uses it for initial adjacent ordering, but `groupByWorkspace` independently buckets each session by its own workspace label. Existing hierarchy guides in SessionsList connect a session to its chat rows only. Keep the work provider-neutral and inside the Sessions list presentation/model boundary; do not change worktree isolation or provider session creation. The uncertainty begins at the desired tree/grouping semantics rather than metadata availability.
- **Open decisions:**
  - Should created sessions become collapsible children of their creator, or remain independently movable rows with a persistent creator relationship?
  - Should workspace sections use the source repository identity for created sessions and show the isolated worktree secondarily, or should each worktree remain a section with an additional parent-project cue?
  - When a child is pinned, placed in a custom group, or manually reordered, should its creator relationship remain visibly represented or be treated as overridden presentation state?
