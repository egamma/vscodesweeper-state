# Issue #182839 — editor.action.marker.next ignores Git conflicts

[https://github.com/microsoft/vscode/issues/182839](https://github.com/microsoft/vscode/issues/182839)

## Summary

A real gap remains on current main: conflict markers are decorations with separate navigation commands, while Alt+F8 reads diagnostics only. The request is already routed to the merge-conflict backlog and should remain open for a product decision about integrating conflicts with marker navigation.

## Change summary

Make editor.action.marker.next navigate every unresolved merge conflict, including conflicts inside comments that language diagnostics do not report.

## Best solution

Ensure every conflict parsed by the built-in merge-conflict extension participates in previous/next problem navigation without duplicating existing language diagnostics. Maintainers should decide whether conflicts should also appear as diagnostics in the Problems view or only participate in navigation.

- **Behavior:**

  > Previous/next problem navigation must reach every unresolved inline merge conflict, including conflicts inside comments that the language service does not diagnose. Existing diagnostics must remain navigable and conflicts must not produce duplicate navigation stops. Once a conflict is resolved or the document changes, its navigation entry must disappear. Acceptance uses a JavaScript file containing conflicts in code and JSDoc plus an ordinary language diagnostic.
- **Trace:**

  > editor.action.marker.next runs through MarkerController and MarkerList in src/vs/editor/contrib/gotoError/browser/gotoError.ts and markerNavigationService.ts; MarkerList currently reads only IMarkerService. The built-in merge-conflict extension independently discovers conflict ranges in extensions/merge-conflict/src/documentTracker.ts, decorates them in mergeDecorator.ts, and exposes separate navigation through commandHandler.ts. No diagnostic collection or other bridge connects those ranges to marker navigation on current main. Preserve the existing merge-conflict commands and normal language-diagnostic behavior; avoid duplicate stops where a language service already reports syntax errors around a conflict. The uncertainty begins at whether these conflicts should become visible Problems entries, as suggested in https://github.com/microsoft/vscode/issues/182839, or should be included only in marker navigation.
