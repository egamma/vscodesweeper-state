## Change summary

Gallery-installed MCP servers lose inline actions in mcp.json until VS Code is restarted.

## Best solution

Ensure eligible gallery-installed servers expose their inline actions immediately after installation, without restarting. Diagnose the discovery-to-CodeLens transition first; preserve valid registry server names rather than assuming camelCase is required.

## Evidence

- **Report provides a retest path:** https://github.com/microsoft/vscode/issues/313209 describes installing a gallery MCP server, opening mcp.json, observing missing actions for all servers, and recovering after restart on Windows with VS Code 1.118. No commenter independently confirms the reproduction or naming hypothesis.
- **No camelCase requirement in current schema:** src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts defines servers through additionalProperties without a property-name pattern. Its examples include mcp-server-time and my-mcp-server, so non-camelCase names are not inherently invalid.
- **CodeLens depends on discovered runtime state:** McpLanguageFeatures._provideCodeLenses in src/vs/workbench/contrib/mcp/browser/mcpLanguageFeatures.ts returns an empty lens list when no collection origin matches the file URI and skips entries without a matching runtime server. It compares the JSON property name directly with server.definition.label, or with the focused Agent Host server name; it does not validate camelCase.
- **Discovery preserves server names:** InstalledMcpServersDiscovery.sync in src/vs/workbench/contrib/mcp/common/discovery/installedMcpServersDiscovery.ts obtains enabled local servers, publishes label: server.name, and assigns the configuration URI as the collection origin. McpWorkbenchService.getEnabledLocalMcpServers filters by enablement and resolves name precedence. These dependencies are diagnostic leads, not proof of the reported failure.
