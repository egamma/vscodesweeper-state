# Issue #188903 — file operation context menu offset error

[https://github.com/microsoft/vscode/issues/188903](https://github.com/microsoft/vscode/issues/188903)

## Summary

The mouse-triggered case was resolved, but the confirmed keyboard path remains distinct: Shift+F10 anchors the menu to the focused row element, whose full width can displace the menu for a long folder name. The issue should remain open until the intended keyboard placement is chosen.

## Change summary

Keep an Explorer context menu invoked on a very long folder name positioned within the visible Explorer area.

## Best solution

Define a consistent keyboard-menu anchor within the visible portion of the Explorer row, then cover long and compressed folder names without changing mouse-triggered placement or generic context-menu behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Extend the Explorer context-menu browser tests with an overlong regular and compressed folder label, invoke the menu through Shift+F10, and assert that its effective anchor stays within the Explorer viewport; existing mouse-anchor tests must remain unchanged.
- **Behavior:**

  > Invoking the Explorer context menu from the keyboard on a folder whose name extends beyond the visible Explorer width must place the menu at a predictable visible location associated with that row. Regular and compressed folder rows must behave consistently. Mouse-triggered menus must continue opening at the pointer location, and context-menu actions must continue targeting the focused item.
- **Trace:**

  > List.onContextMenu in src/vs/base/browser/ui/list/listWidget.ts uses the focused row HTMLElement as the keyboard anchor. ExplorerView.onContextMenu in src/vs/workbench/contrib/files/browser/views/explorerView.ts forwards that element and substitutes a compressed-folder label when applicable. getAnchorRect in src/vs/base/browser/ui/contextview/contextview.ts measures the complete element bounds before layout2d positions the menu, so an overlong label can influence horizontal placement beyond the visible Explorer content. The maintainer confirmed this residual path at https://github.com/microsoft/vscode/issues/188903#issuecomment-1651872836. Keep the scope in Explorer keyboard anchoring; do not alter mouse positioning or generic context-view layout without evidence that other consumers need the same semantics.
- **Open decisions:**
  - Should a keyboard-invoked menu align to the nearest visible edge of the focused Explorer row, or be centered within that row's visible portion?
