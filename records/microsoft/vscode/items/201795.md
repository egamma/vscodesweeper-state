# Issue #201795 — Conflict between status bar items of different ext hosts

[https://github.com/microsoft/vscode/issues/201795](https://github.com/microsoft/vscode/issues/201795)

## Summary

Unnamed status bar items still collide across extension hosts in current source, matching the recent confirmed Insiders reproduction. Keep this issue open while the existing fix proposals are reviewed; neither has merged.

## Change summary

Prevent unnamed status bar items from different extension hosts from overwriting each other and losing independent lifecycle control.

## Best solution

Review and reconcile the existing proposals at https://github.com/microsoft/vscode/pull/201796 and https://github.com/microsoft/vscode/pull/214959 so unnamed extension items remain distinct across hosts and within an extension, while preserving the intentional cross-host reuse of setStatusBarMessage.

## Evidence

- **Current source confirms colliding identifiers:** In src/vs/workbench/api/common/extHostStatusBar.ts, ExtHostStatusBarEntry initializes a host-local static ID_GEN to zero. Its constructor assigns String(ExtHostStatusBarEntry.ID_GEN++) whenever no explicit id is provided, even when an extension is available. Separate hosts therefore generate identical internal entry identifiers.
- **Shared entry and lifecycle consequences:** src/vs/workbench/api/browser/statusBarExtensionPoint.ts keys ExtensionStatusBarItemService._entries solely by entryId. setOrUpdateEntry reuses the first entry's alignment and updates its accessor on a collision, returning DidUpdate. In src/vs/workbench/api/browser/mainThreadStatusBar.ts, MainThreadStatusBar.$setEntry registers disposal ownership only for DidDefine, so the second host's $disposeEntry has no registered entry to dispose.
- **Recent confirmed reproduction:** The 2026-10-08 comment on https://github.com/microsoft/vscode/issues/201795 supplies a minimal Node-host/browser-host reproduction on Insiders 1.142.0, commit 35c48f9946eecf40beed751940607f184a03b6de: two unnamed items collapse into one with alternating text, and the second host cannot independently hide or dispose its item. Supplying an explicit id separates the items.
- **Open implementation candidates:** GitHub reads confirm https://github.com/microsoft/vscode/pull/201796 remains OPEN and explicitly references this issue as its fix target. https://github.com/microsoft/vscode/pull/214959 also remains OPEN, despite the issue comment describing its approach as implemented; it is not evidence of a landed fix.
- **Maintainer-defined compatibility boundary:** https://github.com/microsoft/vscode/pull/201796#issuecomment-1885184292 explains that setStatusBarMessage intentionally reuses its entry across extension hosts, so replacing every generated identifier with a UUID would introduce other bugs. The recent issue reproduction additionally identifies why extension identity alone cannot distinguish multiple unnamed items from the same extension.
- **Related reports do not justify closing:** https://github.com/microsoft/vscode/issues/211952 describes the same overwrite symptom with extension affinity, but is closed and newer than this re-reviewed issue, so it cannot serve as a duplicate canonical. A search for open status-bar/host reports found no verified older canonical owning this defect. The merged https://github.com/microsoft/vscode/pull/338238 addresses hidden command-registration retention, not generated entry identifiers.
