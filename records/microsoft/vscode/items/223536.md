# Issue #223536 — Ability to set log levels by output channel

[https://github.com/microsoft/vscode/issues/223536](https://github.com/microsoft/vscode/issues/223536)

## Summary

The requested API remains absent on current main, and the Backlog milestone plus 34 community upvotes establish this as accepted work. Keep it open while the API owners decide how extension-selected levels interact with user-selected per-channel levels.

## Change summary

Allow extensions to choose an initial log level for each LogOutputChannel and optionally change that channel's level at runtime.

## Best solution

Provide a stable per-channel API that supports extension-driven logging sessions without requiring users to invoke Developer: Set Log Level, while defining clear precedence so extensions do not unexpectedly override an explicit user choice.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostOutput.ts`, `src/vs/workbench/api/common/extHostLoggerService.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadLogService.ts`
- **Validation:** Add an extension API test that creates two log output channels with different requested levels, changes one at runtime, and verifies each channel's logLevel/onDidChangeLogLevel state and corresponding main-thread logger level remain independent while the other channel is unchanged.
- **Behavior:**

  > An extension can select the initial log level of an individual LogOutputChannel and, if runtime mutation is included in the finalized contract, change that channel without opening the Set Log Level quick pick. Two channels from the same extension can use different levels, and changing one does not affect the other or the global level. The finalized behavior must explicitly preserve or override a user's per-channel choice according to the API owners' precedence decision.
- **Trace:**

  > The stable API in src/vscode-dts/vscode.d.ts exposes only readonly LogOutputChannel.logLevel and an onDidChangeLogLevel event; createOutputChannel accepts only { log: true }. ExtHostOutputService.createOutputChannel in src/vs/workbench/api/common/extHostOutput.ts derives the initial level from extension defaults and an explicitly registered user override, then createExtHostLogOutputChannel only mirrors level changes coming from the logger. Core already mutates a channel through IOutputService.setLogLevel from SetLogLevelAction, while MainThreadLoggerService propagates main-thread resource-level changes back to ExtHostLoggerService. The boundary is per-channel extension logging: global log-level behavior, ordinary OutputChannel behavior, and unrelated logger consumers must remain unchanged. The earlier https://github.com/microsoft/vscode/issues/170450 discussion exposes the same API question, but this issue subsequently gained sufficient demand and was accepted into the Backlog.
- **Open decisions:**
  - When an extension supplies or changes a channel level, does an explicit user-selected level for that channel take precedence, or may the extension override it?
  - Should the stable contract expose only a creation-time default, runtime mutation on LogOutputChannel, or both?

## Evidence

- **public API gap:** src/vscode-dts/vscode.d.ts exposes LogOutputChannel.logLevel as readonly and createOutputChannel(name, { log: true }) has no initial-level option; no proposed API declaration adds a setter or creation-time level.
- **existing internal capability:** src/vs/workbench/contrib/logs/common/logsActions.ts and src/vs/workbench/services/output/common/output.ts already support setting an individual channel's level internally through IOutputService.setLogLevel, but that capability is not exposed to extensions.
- **extension-host boundary:** src/vs/workbench/api/common/extHostOutput.ts reads extension and user-configured defaults when creating a channel and mirrors later level changes into the readonly property, but createExtHostLogOutputChannel provides no extension-callable mutation method.
- **accepted demand:** The issue received 34 upvotes, was moved to the Backlog, and includes several distinct extension-author use cases requiring programmatic per-channel levels.
- **related prior decision:** https://github.com/microsoft/vscode/issues/170450 requested a writable LogOutputChannel level and was closed as not planned in 2023, but this later issue was explicitly accepted into the Backlog after exceeding the community threshold, so that older decision does not justify declining the accepted item.
- **continued downstream need:** https://github.com/microsoft/typescript-go/pull/2049 references this issue while describing per-channel logging limitations; it updates that client's logging but does not implement the missing VS Code API.
