# Issue #160585 — [html] Extensions using htmlLanguageParticipants don't activate vscode.html-language-features

[https://github.com/microsoft/vscode/issues/160585](https://github.com/microsoft/vscode/issues/160585)

## Summary

The declarative contribution still does not activate the built-in HTML extension on current main. A maintainer accepted the intended auto-activation behavior, and extension-side workarounds do not resolve the underlying activation-contract gap.

## Change summary

Opening a language declared through `htmlLanguageParticipants` should activate `vscode.html-language-features` without requiring extension code or a temporary switch to HTML mode.

## Best solution

Provide a declarative activation path that activates the built-in HTML language-features extension when a document uses a contributed participant language, without activating or co-locating the contributing extension unnecessarily.

## Plan brief

- **Likely files:** `extensions/html-language-features/package.json`, `extensions/html-language-features/client/src/languageParticipants.ts`, `src/vs/platform/extensionManagement/common/implicitActivationEvents.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`
- **Validation:** Add an extension-service integration test with a fixture contributing a non-HTML `htmlLanguageParticipants` language; opening that language must activate `vscode.html-language-features` immediately while leaving the contributing extension independently hosted and not activation-dependent.
- **Behavior:**

  > When an installed extension declares a language through `htmlLanguageParticipants`, opening a document in that language activates `vscode.html-language-features` on the first open. HTML language features work without switching temporarily to HTML and without imperative `extensions.getExtension(...).activate()` code. The contributing extension is not activated merely because its participant language opens, and it is not forced onto the HTML extension's host.
- **Trace:**

  > The HTML extension manifest at extensions/html-language-features/package.json has static activation events only for HTML and Handlebars. Once activated, `startClient` in extensions/html-language-features/client/src/htmlClient.ts calls `getLanguageParticipants`, which scans contributions in extensions/html-language-features/client/src/languageParticipants.ts and configures the language client selector. The missing link precedes that code: opening a contributed participant language does not activate the HTML extension. `ImplicitActivationEventsImpl` in src/vs/platform/extensionManagement/common/implicitActivationEvents.ts derives events for the extension that owns each contribution, so directly registering a generator for `htmlLanguageParticipants` would activate the contributor rather than the built-in HTML extension and would not satisfy the host-independence requirement. Keep participant discovery and normal HTML/Handlebars behavior unchanged; the plan must identify the narrow core activation mechanism that can target the built-in extension across hosts.

## Evidence

- **current activation manifest:** extensions/html-language-features/package.json still activates only for `onLanguage:html` and `onLanguage:handlebars`; participant language IDs are not represented.
- **source trace:** extensions/html-language-features/client/src/htmlClient.ts calls `getLanguageParticipants()` only after the HTML extension has activated, while extensions/html-language-features/client/src/languageParticipants.ts discovers `htmlLanguageParticipants` contributions at that point. Opening a participant language therefore cannot bootstrap the extension.
- **architecture constraint:** src/vs/platform/extensionManagement/common/implicitActivationEvents.ts generates activation events for the extension owning a contribution. That mechanism cannot currently assign participant-derived `onLanguage` events to the separate `vscode.html-language-features` extension, matching the cross-extension-host concern in https://github.com/microsoft/vscode/issues/160585#issuecomment-1243459408.
- **maintainer intent:** A maintainer agreed that the HTML extension could auto-activate when a participant language is used: https://github.com/microsoft/vscode/issues/160585#issuecomment-1245030181.
- **downstream evidence:** https://github.com/samuelcolvin/jinjahtml-vscode/pull/118 merged an imperative activation workaround, while https://github.com/phoenixframework/vscode-phoenix/pull/23 attempted the same pattern. These demonstrate that the current workaround is imposed on participant extensions rather than solving the declarative contract.
- **canonical search:** A current GitHub search for `htmlLanguageParticipants` in open microsoft/vscode issues found only https://github.com/microsoft/vscode/issues/160585, so no older canonical issue owns this work.
