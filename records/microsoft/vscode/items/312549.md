# Issue #312549 — Linux (Snap) + Copilot Chat cannot type Chinese with IBus (can paste Chinese only)

[https://github.com/microsoft/vscode/issues/312549](https://github.com/microsoft/vscode/issues/312549)

## Summary

The report remains valid on current main: the Snap launcher unconditionally appends `--ozone-platform=x11`, overriding an explicit Wayland selection, while the reporter confirmed that bypassing the wrapper restores Chinese IME composition. Route this to the Snap/Linux owners rather than closing or treating it as a Copilot extension issue.

## Change summary

Allow Chinese IBus composition in Copilot Chat when running the official Snap under a Wayland session instead of forcing the launch back through XWayland.

## Best solution

Give Snap users a supported way to select native Wayland and Wayland IME without the launcher overriding their arguments, while retaining a safe X11 fallback. The maintainer should decide whether this is an explicit override only or a broader change to the Snap backend default.

## Plan brief

- **Likely files:** `resources/linux/snap/electron-launch`, `resources/linux/snap/snapcraft.yaml`, `build/gulpfile.vscode.linux.ts`
- **Validation:** Build the resulting Snap through its existing packaging pipeline, launch it on Ubuntu Wayland with IBus/libpinyin and explicit Wayland IME flags, verify Chinese composition works in Copilot Chat, then launch through the intended X11 fallback and verify startup and basic input still work.
- **Behavior:**

  > On a Wayland desktop, an official VS Code Snap launch must not silently override an explicit request for native Wayland. With IBus and libpinyin enabled, users must be able to compose and commit Chinese text directly in the Copilot Chat input, not only paste it. The supported X11 fallback must continue to start and accept normal input.
- **Trace:**

  > The Snap entry points in `resources/linux/snap/snapcraft.yaml` invoke `resources/linux/snap/electron-launch`. That wrapper currently terminates with `exec "$@" --ozone-platform=x11`, placing the forced backend after user arguments; `build/gulpfile.vscode.linux.ts` packages this file unchanged. The reporter confirmed the resulting duplicate platform arguments and confirmed that bypassing the wrapper restores IBus composition. Keep the change within Linux Snap launch behavior: do not alter Copilot Chat input handling or general editor IME composition. https://github.com/microsoft/vscode/issues/329142 independently identifies the same launcher mechanism, while https://github.com/microsoft/vscode/issues/207033 tracks the broader question of VS Code's default Linux display backend.
- **Open decisions:**
  - Should the Snap retain X11 as its default while honoring an explicit Wayland selection, or should it automatically prefer native Wayland when a Wayland session is detected?

## Evidence

- **current source:** `resources/linux/snap/electron-launch` on current main ends with `exec "$@" --ozone-platform=x11`, so the wrapper places X11 after and overrides user-supplied `--ozone-platform=wayland`.
- **packaging path:** `resources/linux/snap/snapcraft.yaml` launches both Snap applications through `electron-launch`, and `build/gulpfile.vscode.linux.ts` packages that wrapper, confirming this behavior is owned by the VS Code Snap build.
- **confirmed workaround:** The reporter observed both platform arguments in the process and confirmed that bypassing the wrapper with Wayland and Wayland-IME flags restores direct Chinese composition in Copilot Chat.
- **related issue:** https://github.com/microsoft/vscode/issues/329142 reports the same forced-X11 launcher mechanism, but it was created after this re-reviewed issue and therefore cannot be its canonical duplicate.
- **broader Wayland request:** https://github.com/microsoft/vscode/issues/207033 is older and tracks defaulting VS Code broadly to Wayland, but it does not report this same Snap/Copilot/IBus observable symptom, so it does not meet the stronger duplicate bar for a re-reviewed item.
