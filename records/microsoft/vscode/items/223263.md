# Issue #223263 — Improve Auto Update All (From Publisher) action experience

[https://github.com/microsoft/vscode/issues/223263](https://github.com/microsoft/vscode/issues/223263)

## Summary

The requested aggregate-state UX remains missing on current main, and a maintainer explicitly accepted improving the action across its scenarios. This team-authored Backlog item should remain open; the newer, narrower related request cannot replace it as a canonical issue under the re-review rules.

## Change summary

Make the publisher-wide auto-update action's check mark and enabled state accurately represent all installed extensions from that publisher.

## Best solution

Give the publisher action consistent aggregate semantics: checked only when every applicable extension from that publisher will auto-update, unchecked for mixed or disabled states, with predictable behavior when invoked from a mixed state.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/extensions/browser/extensionsActions.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts`, `src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts`, `src/vs/workbench/contrib/extensions/test/electron-browser/extensionsWorkbenchService.test.ts`
- **Validation:** Add publisher-state tests covering two installed extensions from one publisher in all-enabled, all-disabled, and mixed states; verify the action is checked only for all-enabled and that the agreed mixed-state invocation produces the expected state for both extensions.
- **Behavior:**

  > The `Auto Update All (From Publisher)` action must represent the effective auto-update state of all applicable installed extensions from that publisher. It is checked only when all are enabled and unchecked when the state is mixed or all are disabled. Its enabled state and result when invoked from a mixed state must follow one documented, predictable rule. Individual-extension and global auto-update behavior outside this publisher action must remain unchanged.
- **Trace:**

  > On current main, `MenuItemExtensionAction.update` in src/vs/workbench/contrib/extensions/browser/extensionsActions.ts derives the check mark by passing only the publisher string to `IExtensionsWorkbenchService.isAutoUpdateEnabledFor`. In src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts, the publisher-string path checks whether the publisher token exists, while `shouldAutoUpdateExtension` separately honors per-extension negative entries, creating the mixed-state mismatch reported in https://github.com/microsoft/vscode/issues/223263. Publisher mutations and change notifications run through `updateAutoUpdateEnablementFor`; registration and global-setting preconditions are in extensions.contribution.ts. The boundary is the publisher action's aggregate presentation and invocation semantics; do not redesign global auto-update configuration or unrelated extension update scheduling. The narrower https://github.com/microsoft/vscode/issues/263828 is related but younger and does not absorb this issue.
- **Open decisions:**
  - When a publisher has a mixed effective state, should invoking the unchecked action enable every applicable extension from that publisher, or should the action be unavailable until individual exceptions are resolved?

## Evidence

- **current source:** src/vs/workbench/contrib/extensions/browser/extensionsActions.ts:1473-1485 sets the publisher action's check mark from `isAutoUpdateEnabledFor(this.extension.publisher)`, not from the effective state of all installed extensions from that publisher.
- **state mismatch:** src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts:2350-2371 supports publisher enablement with per-extension `-<extensionId>` exceptions, while lines 2420-2435 report publisher enablement solely from the publisher entry. Therefore the publisher action can remain checked even when an extension from that publisher is explicitly excluded.
- **maintainer direction:** In https://github.com/microsoft/vscode/issues/223263, the author defines the expected aggregate check state, and a maintainer responds that they will review all scenarios and improve the action experience. That accepted direction bars a decline close.
- **related issue:** https://github.com/microsoft/vscode/issues/263828 is open but was created later and only asks to hide the action for one extension-level-disabled scenario. It is narrower than this older aggregate-state and enablement UX issue, so it is not a valid canonical for this re-reviewed item.
- **test gap:** src/vs/workbench/contrib/extensions/test/electron-browser/extensionsWorkbenchService.test.ts tests individual auto-update mutations but has no aggregate publisher-state coverage for a publisher with mixed per-extension overrides.
