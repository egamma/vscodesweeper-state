# Issue #129724 — Prevent menu dismissal due to updates for toolbar dropdowns

[https://github.com/microsoft/vscode/issues/129724](https://github.com/microsoft/vscode/issues/129724)

## Summary

The shared toolbar still dismisses an open dropdown when its actions are refreshed, while notebook callers retain local deferral workarounds. This accepted Backlog debt remains necessary and has no verified duplicate or completed generic fix.

## Change summary

Make toolbar action refreshes preserve an open dropdown instead of dismissing it when context-key-driven menu contents change.

## Best solution

Give the shared toolbar a lifecycle guarantee that action updates do not tear down a visible dropdown, while applying the latest pending actions after it closes. Once covered centrally, retire the notebook-specific deferral workarounds without changing ordinary toolbar refresh, overflow, or submenu behavior.

## Evidence

- **shared root cause:** On current main, src/vs/base/browser/ui/toolbar/toolbar.ts exposes dropdown visibility but ToolBar.setActions immediately calls clear() before rebuilding the action bar, which disposes the open dropdown.
- **menu update path:** src/vs/platform/actions/browser/toolbar.ts has MenuWorkbenchToolBar call _updateToolbar() from IMenu.onDidChange, then WorkbenchToolBar.setActions and ToolBar.setActions; context-key-driven menu changes therefore still reach the destructive refresh path.
- **workarounds remain:** src/vs/workbench/contrib/notebook/browser/view/cellParts/cellToolbars.ts and src/vs/workbench/contrib/notebook/browser/viewParts/notebookEditorToolbar.ts still track dropdownIsVisible and defer menu updates until the dropdown closes, demonstrating that the behavior has not been centralized.
- **original symptom:** https://github.com/microsoft/vscode/issues/129587 documents the notebook menu losing focus and closing; https://github.com/microsoft/vscode/issues/129587#issuecomment-888653846 explicitly identifies the copied workaround and requests a toolbar-level fix.
