# Issue #66000 — Scroll bar visibility should be configurable

[https://github.com/microsoft/vscode/issues/66000](https://github.com/microsoft/vscode/issues/66000)

## Summary

Keep open: current settings cover editor and title-area scrollbars, but not application-wide persistent visibility. This accepted Backlog request has 21 upvotes and explicit maintainer support for a global setting.

## Change summary

Make scrollbar visibility configurable across the application, including Explorer, debug views, and Terminal, with consideration for the Windows accessibility preference.

## Best solution

Provide a consistent application-wide visibility preference adopted across scrollable surfaces, preserving existing explicit per-surface settings under a documented precedence rule. Decide how the Windows always-show preference participates rather than treating reduced motion as an equivalent preference.

Add automated visibility-controller and representative workbench-consumer coverage for those semantics.
- **Behavior:**

  > Users need a supported way to keep needed scrollbars visible throughout VS Code, not only in text editors. Explorer, Terminal, debug views, and other covered scrollable surfaces should honor the same application-wide preference. Existing explicit surface settings must behave according to an agreed precedence contract. Acceptance includes persistent visibility after pointer departure, usable scrollbar handles, and the agreed response to setting and Windows accessibility-preference changes.
- **Trace:**

  > AbstractScrollableElement in src/vs/base/browser/ui/scrollbar/scrollableElement.ts defaults unspecified visibility to Auto and schedules hiding outside hover or dragging. ScrollbarVisibilityController in src/vs/base/browser/ui/scrollbar/scrollbarVisibilityController.ts can already keep a needed scrollbar visible when its visibility is Visible; ListView in src/vs/base/browser/ui/list/listView.ts instead defaults to Auto. Editor and title-area settings are independently registered in src/vs/editor/common/config/editorOptions.ts and src/vs/workbench/browser/workbench.contribution.ts, while no application-wide visibility registration was found in the inspected configuration surfaces. The maintainer explicitly requested global adoption in https://github.com/microsoft/vscode/pull/102741#discussion_r479809707; that PR was closed without merging. Reduced-motion CSS removes transitions but does not prevent hiding. The remaining investigation is to enumerate consumers, including Terminal's separate rendering path, and establish global versus explicit-setting precedence and Windows preference integration; traditional arrows, scrollbar width, and unrelated gutter layout are outside this request.
- **Open decisions:**
  - Does the application-wide preference override explicit editor/title-area visibility settings, or only supply their default behavior?
  - Should the default follow the Windows always-show-scrollbars preference, or should OS following be a separately selectable mode with an explicit fallback where detection is unavailable?

## Evidence

These settings address particular surfaces, not the application-wide behavior requested in the discussion.
