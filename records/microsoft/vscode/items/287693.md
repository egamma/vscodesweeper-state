# Issue #287693 — VSCode doesn't stop a diff operation on a large file when the editor window is closed.

[https://github.com/microsoft/vscode/issues/287693](https://github.com/microsoft/vscode/issues/287693)

## Summary

Keep open: current source cancels consumption of the diff result, but does not interrupt the running worker computation when the diff editor closes. The linked PR was closed without merging, and the maintainer-confirmed cancellation gap remains.

## Change summary

Stop expensive in-flight diff computation when its editor closes, including when diffEditor.maxComputationTime is set to 0.

## Best solution

Make abandoned diff computations interruptible without disrupting other editors or services using the shared editor worker. This needs a design and validation pass across diff-editor cancellation, worker ownership, and synchronous diff execution.

Keep another model/editor alive and verify subsequent worker operations still complete. A manual acceptance run should reproduce the Git-panel steps and measure worker CPU activity before and after closing only the diff editor.
- **Behavior:**

  > With diffEditor.maxComputationTime set to 0, opening a Git diff for a sufficiently expensive changed file starts a long-running computation. Closing that diff editor must stop computation that no longer has a consumer, rather than only suppressing its eventual result. Other open editors and their worker-backed operations must remain functional. Acceptance must observe interruption of already-running work; cancelling before dispatch or ignoring a completed result does not satisfy the report.
- **Trace:**

  > DiffEditorViewModel in src/vs/editor/browser/widget/diffEditor/diffEditorViewModel.ts cancels a token on disposal, but WorkerBasedDocumentDiffProvider.computeDiff in diffProviderFactoryService.ts checks it only after the worker call resolves. EditorWorkerService.computeDiff in src/vs/editor/browser/services/editorWorkerService.ts dispatches an uncancellable request; EditorWorker.$computeDiff in src/vs/editor/common/services/editorWebWorker.ts invokes the selected diff algorithm synchronously. DefaultLinesDiffComputer chooses InfiniteTimeout when the configured time limit is zero, so its timeout checks cannot respond to editor closure. The maintainer explains the worker-message limitation at https://github.com/microsoft/vscode/issues/287693#issuecomment-3748879548; https://github.com/microsoft/vscode/pull/287726 was closed without merging and its disposal polling does not resolve that limitation. The shared WorkerManager also serves other operations, so terminating it has consequences beyond this diff that this trace has not fully enumerated. Preserve existing time-limit semantics and unrelated worker consumers; the plan must establish a safe interruption boundary and a real in-flight validation harness.
