# Issue #346024 — SCM: main repository duplicated and hidden after an auto-detected worktree is removed externally

Keep open: the supplied steps, logs, and persisted state suffice to retest the duplicated and hidden main repository. Current main still uses the implicated restoration logic, but the external-removal trigger has not been confirmed against the newer code.

## Change summary

Externally removing an auto-detected worktree can leave the main repository duplicated and persistently hidden from Changes.

## Best solution

Establish how worktree removal produces duplicate registrations of the main repository, then preserve repository identity and visibility across removal and reload. Coordinate with the existing visibility-restoration PR without treating its narrower discovery-order fix as resolving duplication.

## Plan brief

- **Likely files:** `extensions/git/src/model.ts`, `extensions/git/src/repository.ts`, `src/vs/workbench/contrib/scm/browser/scmViewService.ts`
- **Validation:** In an isolated current VS Code profile, open a main repository with multiple detected worktrees, externally add and remove another worktree, then close and reopen the window. Check that the removed worktree disappears, the main repository occurs exactly once, its changes remain visible, and the result survives a second reload; also verify intentionally hidden repositories remain hidden when repository membership is unchanged.
- **Behavior:**

  > The reporter observes duplicate main-repository entries and missing main-repository changes after an externally created worktree is removed and the window reopened. The main repository should remain registered once and retain its prior visibility, while the removed worktree disappears. Confirm the sequence on current VS Code before changing behavior, and verify recovery persists across subsequent reloads without editing workspace storage.
- **Trace:**

  > Model.open in extensions/git/src/model.ts schedules worktree discovery on Git status and listens for repository disposal; Model.openRepository serializes opening and checks exact and real-path identity. SCMViewService.onWillSaveState serializes live provider keys, while onDidAddRepository restores visibility using the first matching persisted key. This explains why duplicate identities are ambiguous during restoration, but not how external removal creates them. Trace registration and disposal through the reported sequence before selecting the fix boundary. Preserve ordinary worktree discovery and intentional repository visibility choices; a blanket switch to URI-based persistence is not an established fix. https://github.com/microsoft/vscode/pull/334845 addresses a related discovery-order selection failure, not the demonstrated duplicate identity.

## Evidence

- **Concrete report:** https://github.com/microsoft/vscode/issues/346024 supplies an external worktree add/remove/reopen sequence, missing-HEAD and watcher errors, and persisted state containing two identical main-repository keys with neither selected. The reporter acknowledges that the reconstructed trigger is not yet deterministic; the only comment requests upgrading rather than confirming a reproduction.
- **Current persistence and restoration:** src/vs/workbench/contrib/scm/browser/scmViewService.ts: onWillSaveState constructs all from live repositories and visible using storage-key indexOf; onDidAddRepository restores selection through previousState.all.indexOf. Duplicate keys therefore share the first matching index. However, persisted all does not itself instantiate repositories, so the duplicate registration still requires diagnosis; positional storage alone does not establish the reported root cause.
- **Git lifecycle boundary:** extensions/git/src/model.ts: Model.openRepository is sequentialized and checks getRepositoryExact both before and after resolving the repository root. Model.open discovers worktrees after status updates and disposes repositories on RepositoryState.Disposed. These existing protections prevent concluding from source alone how external removal yields two main-repository providers.
- **Related but narrower implementation candidate:** https://github.com/microsoft/vscode/issues/334842 tracks hidden repositories after a newly discovered repository interrupts visibility restoration. Its open fix candidate, https://github.com/microsoft/vscode/pull/334845, clears previousState after selecting all repositories; it neither diagnoses duplicate main-repository registration nor references this issue. It is not a verified canonical for this report's full scope.
