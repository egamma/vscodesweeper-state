# Issue #343436 — MCP OAuth: Parallel tool calls after refresh token expiry stop the MCP server (`Canceled`) and spawn multiple browser logins on different ports

[https://github.com/microsoft/vscode/issues/343436](https://github.com/microsoft/vscode/issues/343436)

## Summary

Keep open: current source retains the failed-refresh session-removal path that stops an active MCP server while concurrent authentication requests can continue independently. The older parallel-login report covers only part of this issue; premature cancellation and the reported blocked-restart scenario remain distinct work.

## Change summary

Coordinate MCP re-authentication after refresh-token rejection so parallel tool calls do not trigger redundant browser logins, premature connection teardown, or abandoned authentication work that blocks recovery.

## Best solution

Make concurrent MCP authentication and server lifecycle behavior coherent: share equivalent interactive authentication, preserve intentional sign-out handling, and ensure abandoned authentication cannot indefinitely block subsequent connections. Coordinate the overlapping login-deduplication work with https://github.com/microsoft/vscode/issues/278708 without losing this report's independent server-stop failure.

## Evidence

- **Complete reproduction and current-version follow-up:** https://github.com/microsoft/vscode/issues/343436 provides expired-access-token plus invalid_grant steps, three concurrent tool calls, and correlated authentication/server logs. https://github.com/microsoft/vscode/issues/343436#issuecomment-6341170644 specifies VS Code 1.143.0 and adds the abandoned-login/provider-queue scenario.
- **Failed refresh removes the session:** In src/vs/workbench/api/common/extHostAuthentication.ts, DynamicAuthProvider.getSessions adds the old token to removedTokens before refreshing. A failed exchange leaves it removed through _tokenStore.update, and the returned session list becomes empty.
- **Server-stop race remains in current source:** In src/vs/workbench/api/browser/mainThreadMcp.ts, _onDidChangeAuthSessions silently calls _getSessionForProvider for running servers and calls server.stop() on UserInteractionRequiredError. _getSessionForProvider throws that error for the empty-session silent check, while interactive callers independently proceed through loginPrompt and createSession without a shared in-flight authentication task or server-lifetime cancellation parameter.
- **Parallel calls and provider queue:** src/vs/workbench/api/common/extHostMcp.ts sends Streamable HTTP requests through _sendStreamableHttp and awaits _addAuthHeader for each request. In src/vs/workbench/api/common/extHostAuthentication.ts, $createSession and $getSessions share _providerOperations.queue(providerId); serialization does not itself combine already-requested session creations.
- **Abandoned-login qualification:** NodeDynamicAuthProvider._createWithLoopbackServer in src/vs/workbench/api/node/extHostAuthentication.ts awaits raceCancellationError(server.waitForOAuthResponse(), token), so notification cancellation does exist. However, this wait has no local timeout and uses the authentication-progress token rather than an MCP server-lifetime token; closing the browser alone does not resolve it. The reporter's claim should not be broadened into a total absence of cancellation.
- **Verified related issue is narrower:** https://github.com/microsoft/vscode/issues/278708 is open and requests one OAuth login for parallel tool calls. Its discussion identifies missing serialization for re-authentication, but does not establish ownership of refresh-failure session removal stopping the server. Deduplicating logins alone would not eliminate that independent stop path, so it is not a full-scope duplicate canonical.
- **Related open PR does not fix the central report:** https://github.com/microsoft/vscode/pull/340072 is open and targets the unused fallback URI handler's timeout from https://github.com/microsoft/vscode/issues/340058. It does not reference this issue or address MainThreadMcp's session-removal shutdown and concurrent createSession behavior; avoid competing changes to that fallback-handler work.
