# Issue #163292 — Consider supporting embedded language grammars when using semantic tokens

[https://github.com/microsoft/vscode/issues/163292](https://github.com/microsoft/vscode/issues/163292)

## Summary

Keep this accepted, community-supported request open: current source still lets host semantic styling overwrite injected-language highlighting. Existing settings provide workarounds, not selective coexistence, and the verified older related issue does not report the same observable problem.

## Change summary

Allow injected embedded-language highlighting to coexist with host-language semantic tokens without requiring language-server-specific suppression.

## Best solution

Define an explicit, opt-in way to preserve embedded-language highlighting in selected ranges while retaining host semantic highlighting elsewhere. Settle the precedence and extension contract before changing the editor token merge behavior; host-directed embedded-language tokenization is related but need not be part of the first implementation.

## Plan brief

- **Likely files:** `src/vs/editor/common/tokens/sparseTokensStore.ts`, `src/vs/editor/common/services/semanticTokensProviderStyling.ts`, `src/vs/workbench/services/textMate/common/TMGrammars.ts`, `src/vs/workbench/services/textMate/common/TMGrammarFactory.ts`
- **Validation:** After choosing the contract, run an Extension Development Host with a Dart string-injection fixture like the ntm example in https://github.com/Dart-Code/Dart-Code/issues/4212. With semantic highlighting enabled, wait for analyzer tokens and verify embedded colors remain while an adjacent ordinary Dart string retains its semantic styling. Compare semantic highlighting disabled and verify ordinary non-embedded semantic highlighting and bracket behavior remain unchanged; add automated token-merge coverage for the agreed precedence.
- **Behavior:**

  > An extension's selected embedded-language regions should retain meaningful injected highlighting after host semantic tokens arrive, without turning off semantic highlighting for the document or requiring that server to recognize the extension's syntax. Ordinary host-language strings and other semantic tokens should retain their existing styling. Acceptance must cover a semantic string token spanning several embedded syntax tokens, an adjacent ordinary string, and behavior with semantic highlighting disabled. The opt-in and conflict rules are not yet settled.
- **Trace:**

  > SparseTokensStore.addSparseTokens in src/vs/editor/common/tokens/sparseTokensStore.ts merges semantic style masks over TextMate metadata, including tokens whose embedded language was established by TMGrammarFactory.createGrammar. SemanticTokensProviderStyling.getMetadata resolves host semantic styles from the legend and theme; it does not consult injected ranges. Source inspection establishes why the reported string-token overlay hides embedded colors, while https://github.com/Dart-Code/Dart-Code/issues/4212 supplies the concrete Dart scenario. Preserve normal semantic precedence outside explicitly supported embedded regions, ordinary string token classification, and bracket behavior. https://github.com/microsoft/vscode/issues/81558 discusses semantic identification of embedded regions, but does not itself settle coexistence with independently injected grammars. Uncertainty starts at which participant can opt a range into different precedence and how conflicting host and embedded styles should compose.
- **Open decisions:**
  - Should an injected grammar be able to opt its recognized ranges into embedded-highlight precedence without cooperation from the host semantic provider, and what extension-facing declaration authorizes that behavior?
  - Within an opted-in embedded range, should TextMate styling override all host semantic style attributes, or only particular attributes such as foreground while retaining other semantic styling?

## Evidence

- **current merge behavior:** src/vs/editor/common/tokens/sparseTokensStore.ts, SparseTokensStore.addSparseTokens, constructs a mask from SEMANTIC_USE_* flags and combines overlapping tokens as (TextMate metadata & inverse mask) | (semantic metadata & mask). A host string token with semantic foreground therefore overwrites embedded TextMate foreground throughout its range; this path has no embedded-language precedence exception.
- **existing capability check:** editor.semanticHighlighting.enabled disables semantic highlighting, and editor.semanticTokenColorCustomizations exposes enabled and styling rules in src/vs/workbench/services/themes/common/themeConfiguration.ts. SemanticTokensProviderStyling.getMetadata in src/vs/editor/common/services/semanticTokensProviderStyling.ts resolves styles by token type, modifiers and language, not injected TextMate ranges. These mechanisms do not selectively preserve injected highlighting while keeping the host's ordinary string semantic styling.
- **embedded grammar support is not semantic coexistence:** src/vs/workbench/services/textMate/common/TMGrammarFactory.ts, createGrammar, combines embeddedLanguages from injected grammars and passes them to loadGrammarWithConfiguration. This supports embedded TextMate tokenization, but the later sparse semantic merge still applies semantic style masks over those tokens.
- **documented design and closed predecessor:** https://github.com/microsoft/vscode/issues/113640#issuecomment-754061490 explicitly describes semantic-token precedence as intentional and suggests coordinating suppression with the host provider. That issue is currently closed following the community-upvote process, not a landed fix, so it cannot be an open duplicate canonical or establish that this accepted enhancement is implemented.
- **verified older related issue:** https://github.com/microsoft/vscode/issues/81558 is open and predates this report. Its central request is for semantic tokens to identify embedded-language regions, illustrated by Razor attributes and dynamic language embedding; it does not report existing injected highlighting being overwritten by host string tokens.
