# Issue #338448 — terminal output preview is wordwrapped but also has a horizontal scrollbar

[https://github.com/microsoft/vscode/issues/338448](https://github.com/microsoft/vscode/issues/338448)

## Summary

Fresh report (same day, no comments yet) from a maintainer testing their own recently-merged terminal output preview PR (#338053); screenshot shows the preview genuinely wrapping lines yet still displaying a horizontal scrollbar. No fix has landed on main for this file since, so it stays open as a real, unresolved visual bug.

## Change summary

The chat terminal tool output preview shows a horizontal scrollbar even though its content is word-wrapped and should fit the available width.

## Best solution

Reconcile the DomScrollableElement's scanDomNode overflow measurement in ChatTerminalToolOutputSection with the reflowed mirror width so the horizontal scrollbar (ScrollbarVisibility.Auto shown on hover/focus) only appears when content actually overflows after reflow.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatTerminalToolProgressPart.ts`
- **Validation:** After reflow is enabled and the terminal output wraps to fit the container width, the horizontal scrollbar should not appear on hover/focus for that output; a manual check comparing _outputBody scrollWidth vs clientWidth after _layoutMirrorWidth()/_layoutOutput() would confirm.
- **Behavior:**

  > When the terminal output preview reflows (word-wraps) to fit the available width, no horizontal scrollbar should appear on hover/focus, since there is nothing to horizontally scroll. Currently a horizontal scrollbar shows even though the content is wrapped. Acceptance: with TerminalOutputReflow enabled and output that wraps within the container, hovering/focusing the output does not reveal a horizontal scrollbar; scrolling still works normally for genuinely overflowing (non-wrapped) content.
- **Trace:**

  > ChatTerminalToolOutputSection wraps the rendered terminal mirror in a DomScrollableElement (_createScrollableContainer, chatTerminalToolProgressPart.ts ~1673) whose horizontal scrollbar visibility toggles to Auto on hover/focus (~1690-1702) and whose overflow is measured via scanDomNode (_layoutOutput). Separately, _layoutMirrorWidth() (~1954) resizes the mirror's columns to the container's clientWidth only when ChatConfiguration.TerminalOutputReflow is true. The mismatch likely comes from a difference between the width used to reflow the mirror and the width/box-sizing DomScrollableElement scans afterward (e.g. padding included in one but not the other, or scanDomNode running before the mirror's resize/re-render settles). Boundary: do not change the collapsed/expanded scrollbar-visibility toggling behavior itself, and do not disable horizontal scrolling for genuinely non-wrapped/overflowing output — only the false-positive case when content is actually wrapped. Related: https://github.com/microsoft/vscode/pull/338053 (the PR under test) and https://github.com/microsoft/vscode/issues/338448.
- **Open decisions:**
  - When reflow is on but a single unbreakable token (e.g. a very long path) still overflows the wrapped width, should the horizontal scrollbar be shown for that edge case, or should it be suppressed entirely whenever reflow is enabled?
