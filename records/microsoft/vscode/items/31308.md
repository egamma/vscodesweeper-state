# Issue #31308 — Support workspace projects / folders under different colors in sidebar and tabs

[https://github.com/microsoft/vscode/issues/31308](https://github.com/microsoft/vscode/issues/31308)

## Summary

Keep this accepted, well-supported request open: current theme settings and file decorations do not provide independent project-colored backgrounds across Explorer and inactive tabs. The recent rejection of tree background decorations settles that particular approach, but does not resolve or decline the full sidebar-and-tabs request.

## Change summary

Visually distinguish workspace projects using corresponding colors in the Explorer and editor tabs, including inactive tabs.

## Best solution

Agree on a supported project-identity treatment across Explorer and tabs that preserves theme consistency and existing state indicators. Use the existing extension decoration capability where sufficient, and explicitly settle the remaining tab-coloring and workspace-mapping requirements without assuming the rejected tree-background proposal can proceed.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts`, `src/vs/workbench/services/decorations/common/decorations.ts`, `src/vs/workbench/services/decorations/browser/decorationsService.ts`, `src/vs/workbench/common/theme.ts`, `src/vs/workbench/services/themes/common/themeConfiguration.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** After agreeing on the visual contract, open a multi-root workspace containing two projects with identically named files. Verify that both projects remain distinguishable in Explorer and simultaneously visible active/inactive tabs, that switching tabs does not recolor unrelated project identities, and that selection, dirty-state, diagnostic and high-contrast indicators remain legible.
- **Behavior:**

  > Users want to recognize which project a file belongs to before activating its tab, with a corresponding project identity visible in Explorer. Per-window colors or colors that change only with the active file do not satisfy this request. Acceptance should cover two workspace roots with identically named files and concurrently visible inactive tabs. The approved treatment must retain readable selection, diagnostic and modified-file indicators across themes.
- **Trace:**

  > The current FileDecoration API in src/vscode-dts/vscode.d.ts supports resource-based foreground colors and badges, not backgrounds; IDecorationData in src/vs/workbench/services/decorations/common/decorations.ts has the same boundary. DecorationsService generates foreground CSS, and MultiEditorTabsControl.redrawTabLabel already consumes resource decorations for tab labels. Tab background tokens in src/vs/workbench/common/theme.ts distinguish active/inactive and focus states, not project identity. https://github.com/microsoft/vscode/pull/310165 attempted background decoration support, including tabs, but was closed without merging; its maintainer response rejects tree backgrounds, as does https://github.com/microsoft/vscode/issues/239308#issuecomment-4959787872. The uncertainty is the approved visual and configuration contract, not whether that rejected PR landed. Preserve existing theme state semantics and do not treat internal CSS modification or active-file chrome changes as equivalent coverage.
- **Open decisions:**
  - Which persistent project-identity treatment is acceptable in Explorer and inactive tabs, given the explicit rejection of tree-row background colors?
  - Should project-color assignments be configured by users per workspace root, supplied by extensions through a supported API, or support both?
