# Issue #150938 — Add nvm support

[https://github.com/microsoft/vscode/issues/150938](https://github.com/microsoft/vscode/issues/150938)

## Summary

Keep open: built-in npm tasks still lack project-specific Node selection from .nvmrc, and the linked implementation PR closed without merging. Existing shell configuration can provide workarounds, but does not deliver native support for the requested behavior.

## Change summary

Allow npm script tasks to use the Node version selected by the project's .nvmrc rather than relying on the inherited PATH.

## Best solution

Provide deliberate .nvmrc-aware runtime selection for built-in npm script tasks, with defined activation and unavailable-version behavior. Resolve those product choices before implementing; debugger runtimeVersion support is related but does not cover task execution.

## Plan brief

- **Likely files:** `extensions/npm/src/tasks.ts`, `extensions/npm/package.json`, `extensions/npm/package.nls.json`, `extensions/npm/README.md`
- **Validation:** With nvm installed and two installed Node versions, set the inherited default to version A and the project's .nvmrc to version B. Run a package.json script containing node --version through both Tasks: Run Task and the Npm Script Explorer; under the approved activation mode, both must report B. Change .nvmrc and rerun, then verify unchanged behavior without activation or without .nvmrc and the approved outcome for an unavailable version.
- **Behavior:**

  > Built-in npm script tasks should offer project-specific Node selection from .nvmrc instead of requiring the project version to already be on the inherited PATH. Acceptance must cover execution from both the Tasks menu and Npm Script Explorer, and a subsequent run after changing .nvmrc. Activation, missing-version behavior, and fallback behavior must be agreed before implementation. Projects not using the feature must retain existing runner and shell behavior.
- **Trace:**

  > extensions/npm/src/tasks.ts:getRunScriptCommand selects a script runner and builds its arguments; createScriptRunnerTask constructs ShellExecution with the package.json directory as cwd but no .nvmrc-aware runtime selection. extensions/npm/package.json exposes runner selection, not Node-version selection. src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts executes through the automation/default profile or explicit task shell overrides, so custom shell initialization can affect runtime selection without providing native support. The unmerged attempt at https://github.com/microsoft/vscode/pull/150940 includes a concrete node --version acceptance scenario and reports of inconsistent results; its closure is not a product rejection. Keep the initial scope on built-in npm script tasks, preserving custom task-shell overrides and unrelated runners; debugger runtimeVersion integration is a separate possible extension of scope. The remaining uncertainty is the user-visible activation and failure contract, not whether the current npm provider reads .nvmrc.
- **Open decisions:**
  - Should .nvmrc-aware runtime selection activate automatically when nvm and .nvmrc are present, or require explicit opt-in?
  - When .nvmrc names an unavailable Node version or nvm cannot be found, should the task stop with an actionable error or fall back to the inherited runtime?
