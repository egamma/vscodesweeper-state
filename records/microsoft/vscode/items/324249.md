# Issue #324249 — Copilot Chat session is lost after VS Code crash only when workspace is opened via \\wsl.localhost on Windows (no Remote-WSL)

[https://github.com/microsoft/vscode/issues/324249](https://github.com/microsoft/vscode/issues/324249)

## Summary

The detailed Windows/UNC reproduction matrix identifies a real, narrowly scoped session-recovery failure that remains plausible on current main. Older crash-loss reports do not establish the same UNC-specific root cause, so this should remain open rather than be consolidated prematurely.

## Change summary

Copilot Chat sessions become unavailable after a crash when a local Windows window opens the workspace through a \\wsl.localhost UNC path.

## Best solution

Diagnose whether the UNC folder receives a different single-folder workspace identifier after restart, then preserve access to the existing workspace-scoped chat index and session files across abnormal termination without changing identity semantics for ordinary local or Remote-WSL workspaces.

- **Behavior:**

  > A Copilot Chat session created in a normal Windows VS Code window for a \\wsl.localhost workspace remains discoverable after VS Code terminates unexpectedly and the same workspace is reopened. Existing behavior for Windows-local folders and Remote-WSL workspaces remains unchanged. Recovery must use the previously persisted conversation rather than presenting an empty history.
- **Trace:**

  > ChatSessionStore in src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts keys both its session directory and index to the current workspace identity. On Windows, getSingleFolderWorkspaceIdentifier in src/vs/platform/workspaces/node/workspaces.ts salts a file workspace ID with stat.birthtimeMs; the current tests do not cover stability of WSL UNC metadata across launches. The report's strict matrix points to that identity boundary, but a Windows reproduction must confirm whether the ID changes or whether UNC timing instead exposes the asynchronous crash-write path. Commit 7393b0ec6071aca9ba95635a36588affb09db549 only migrates sessions during an observed in-process workspace transition. Keep ordinary local-folder identity, Remote-WSL behavior, session-retention limits, and normal shutdown semantics outside the change.

## Evidence

- **reproduction matrix:** The report isolates the failure to Windows VS Code opening a WSL filesystem through \\wsl.localhost without Remote-WSL; the same workflow passes with Remote-WSL and with a Windows-local folder.
- **workspace-scoped persistence:** src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts stores sessions below environmentService.workspaceStorageHome/<workspaceId>/chatSessions and stores the discovery index at StorageScope.WORKSPACE, so a changed workspace identity makes existing sessions appear absent.
- **likely identity boundary:** src/vs/platform/workspaces/node/workspaces.ts:getSingleFolderWorkspaceIdentifier derives Windows folder IDs from folderUri.fsPath plus stat.birthtimeMs; current tests cover ordinary paths but not \\wsl.localhost UNC filesystem metadata across launches.
- **current persistence behavior:** Current src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts synchronously updates the session index during onWillSaveState and then starts asynchronous session-file writes, but an actual process crash does not guarantee that shutdown path completes.
- **related reports are not canonical:** https://github.com/microsoft/vscode/issues/302900 concerns session loss after a crash in a Remote-WSL window, while https://github.com/microsoft/vscode/issues/317807 combines several session-list and remote-sync symptoms. Neither establishes the same no-Remote-WSL UNC path failure.
- **prior migration fix:** Commit 7393b0ec6071aca9ba95635a36588affb09db549 fixed chat-session migration when a workspace ID changes during an in-process workspace transition, but it does not cover an identity change detected only after a new process starts.
