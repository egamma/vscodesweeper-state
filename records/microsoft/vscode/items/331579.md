# Issue #331579 — NES 402 handler resets the Copilot token in an unbounded loop (quota latch never engages)

[https://github.com/microsoft/vscode/issues/331579](https://github.com/microsoft/vscode/issues/331579)

## Summary

The defect remains source-reproducible on current main: repeated NES 402 responses can reset and re-fetch the Copilot token indefinitely because the guard checks the unrelated code-completions quota. The downstream language-server mitigation does not fix the VS Code Copilot path, so this team-authored bug should remain open.

## Change summary

Bound Copilot token refreshes after NES 402 and chat quota failures so an unchanged or inapplicable quota field cannot trigger resets at request rate.

## Best solution

Allow at most the intended one refresh for a quota incident, then latch or back off repeated NES 402 and chat quota responses independently of free-tier code-completions quota. The behavior should cover paid plans while preserving successful-request recovery from stale quota state.

- **Behavior:**

  > Repeated NES HTTP 402 responses or chat quota failures must not reset and re-fetch the Copilot token at request rate when refreshing cannot change the failing entitlement. One refresh may update stale quota state, but subsequent equivalent failures must remain bounded or backed off for both free and paid users. Successful responses must continue to clear stale quota-exceeded state. Acceptance tests should cover absent and unrelated quota fields, paid-plan tokens, repeated failures, and recovery after success.
- **Trace:**

  > In extensions/copilot/src/platform/nesFetch/node/completionsFetchServiceImpl.ts, `CompletionsFetchService._fetchFromUrl` gates NES 402 refreshes on `CopilotToken.isCompletionsQuotaExceeded`. That getter in extensions/copilot/src/platform/authentication/common/copilotToken.ts reads only the free-tier `limited_user_quotas.completions` bucket, so an NES 402 can leave the guard false after every refreshed token; paid tokens also make it unconditionally false. The HTTP and WebSocket quota branches in extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts have the parallel `isChatQuotaExceeded` dependency for quota codes not necessarily represented by that free-tier bucket. The downstream language-server issue https://github.com/microsoft/copilot-language-server-internal/issues/1252 confirms the same failure mode but only guards its own consumer. Keep normal 401/403 authentication recovery and successful-response stale-quota clearing unchanged; unrelated completion enablement checks are outside this bug's scope.

## Evidence

- **current NES path:** extensions/copilot/src/platform/nesFetch/node/completionsFetchServiceImpl.ts still handles every HTTP 402 by testing `isCompletionsQuotaExceeded`, then calling `resetCopilotToken(response.status)` and awaiting `getCopilotToken()` whenever that unrelated guard remains false.
- **mismatched latch:** extensions/copilot/src/platform/authentication/common/copilotToken.ts defines `isCompletionsQuotaExceeded` solely from `isFreeUser` and `limited_user_quotas.completions`, defaulting a missing quota to available; it cannot represent an NES-specific allowance and is always false for paid users.
- **parallel chat path:** extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts uses the same refresh-until-`isChatQuotaExceeded` pattern for HTTP 402 and several CAPI quota codes, including billing and spend-limit failures that need not update the free-tier chat bucket.
- **downstream mitigation only:** https://github.com/microsoft/copilot-language-server-internal/issues/1252 was closed after downstream changes restricted token resets to 401/403 and added backoff, but its maintainer explicitly identified https://github.com/microsoft/vscode/issues/331579 as the still-needed upstream fix in VS Code's chat-lib source.
- **measured impact:** The issue reports that 78% of affected downstream users reset more than 100 times per day and 27% more than 1000 times, demonstrating sustained unnecessary token minting, CPU, and network use.
