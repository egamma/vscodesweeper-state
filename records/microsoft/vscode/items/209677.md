# Issue #209677 — Inline editing of debug variables

[https://github.com/microsoft/vscode/issues/209677](https://github.com/microsoft/vscode/issues/209677)

## Summary

This maintainer-authored Backlog request remains a real gap on current main: variables can be edited in the Variables view, but inline values and debug hovers do not expose equivalent editing. No older issue with the same observable request or linked implementation was found, so it should remain open for UX planning.

## Change summary

Allow users to edit a paused debug variable directly from its inline editor value or debug hover without moving to the Variables view or Debug Console.

## Best solution

Design a focused in-editor editing flow that reuses the existing DAP setVariable/setExpression handling and respects adapter capabilities and read-only variables. A maintainer should first choose whether the initial surface is debug hovers, inline values, or both, and which evaluatable expressions are safely editable.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugEditorContribution.ts`, `src/vs/workbench/contrib/debug/browser/debugHover.ts`, `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`, `src/vs/workbench/contrib/debug/test/browser/debugHover.test.ts`
- **Validation:** End the plan with targeted debug browser tests proving that the chosen in-editor surface offers editing only when setVariable or setExpression is supported, suppresses it for read-only values, submits the new value through the existing model operation, and refreshes the displayed value.
- **Behavior:**

  > While execution is paused, a user can invoke an edit action from the selected in-editor debug surface, see an input prefilled with the current value, submit a replacement, and see the displayed value refresh. Editing is unavailable for read-only values and when the active debug adapter supports neither setVariable nor setExpression. Cancelling leaves the value unchanged, and existing Variables-view editing continues to behave as before. The interaction must be keyboard and screen-reader accessible as well as discoverable with a pointer.
- **Trace:**

  > Inline values are assembled in DebugEditorContribution.updateInlineValueDecorations in src/vs/workbench/contrib/debug/browser/debugEditorContribution.ts and flattened into non-interactive injected-text decorations, so the rendered text currently loses the Variable/expression identity needed for mutation. DebugHoverWidget in src/vs/workbench/contrib/debug/browser/debugHover.ts retains Variable objects and reuses VariablesRenderer, but MenuId.DebugHoverContext lacks the Set Value registration that DebugVariablesContext has in src/vs/workbench/contrib/debug/browser/debug.contribution.ts. Existing VariablesView.canSetExpressionValue and Variable.setVariable already define the capability, read-only, setVariable, and setExpression behavior that should remain authoritative. Keep the change within debug editor/hover presentation and existing debug-model mutation APIs; do not change DAP or the Variables-view semantics. The uncertainty begins at the product surface and at whether arbitrary evaluatable expressions, rather than resolved Variable objects, are included.
- **Open decisions:**
  - Should the first supported editing surface be debug hovers, inline values, or both?
  - Should editing be limited to resolved Variable objects, or also support arbitrary evaluatable expressions when the adapter advertises supportsSetExpression?
  - For inline values, what keyboard-accessible invocation should accompany pointer interaction without interfering with normal editor selection and cursor placement?

## Evidence

- **current source gap:** src/vs/workbench/contrib/debug/browser/debugEditorContribution.ts renders inline values as injected-text decorations with InjectedTextCursorStops.None and a read-only hoverMessage; it does not retain an editable Variable or expose an edit interaction.
- **hover gap:** src/vs/workbench/contrib/debug/browser/debugHover.ts renders Variable objects using VariablesRenderer, but its context menu uses MenuId.DebugHoverContext; src/vs/workbench/contrib/debug/browser/debug.contribution.ts registers Set Value only for DebugVariablesContext and DebugWatchContext, not DebugHoverContext.
- **existing mutation path:** src/vs/workbench/contrib/debug/browser/variablesView.ts already enables editing supported, non-read-only variables and invokes Variable.setVariable; src/vs/workbench/contrib/debug/common/debugModel.ts routes that operation through setVariable or setExpression according to adapter capabilities.
