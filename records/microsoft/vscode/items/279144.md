# Issue #279144 — Show progress window when attempting to restart vscode during a background update

[https://github.com/microsoft/vscode/issues/279144](https://github.com/microsoft/vscode/issues/279144)

## Summary

Keep open: current startup waits silently for an active Windows update and exits if the wait expires; it does not provide the requested progress window. Nearby startup fixes do not complete this team-authored follow-up, and no qualifying canonical duplicate was found.

## Change summary

Show visible update progress when a user relaunches VS Code during a Windows background update, then launch VS Code when the update completes.

## Best solution

Provide a single visible waiting experience for launches blocked by an active Windows installer, followed by automatic startup when installation completes. Preserve the existing protection against launching during replacement of application files.

## Plan brief

- **Likely files:** `src/vs/code/electron-main/main.ts`, `build/win32/code.iss`, `build/win32/Cargo.toml`
- **Validation:** On a Windows setup installation, apply a background update, immediately quit, and relaunch while the installer mutex remains held. Confirm visible waiting feedback, repeat the launch attempt and confirm only one waiting experience, then let installation finish and confirm one successful VS Code startup. Also verify an ordinary launch without an active installer is unchanged.
- **Behavior:**

  > After applying a Windows background update and immediately quitting, attempting to relaunch must visibly explain that installation is still in progress rather than appearing to do nothing. Repeated launch attempts must not create duplicate progress windows or competing startups. Once installation completes, VS Code should launch automatically. Ordinary launches and the protection against starting while application files are being replaced must remain unchanged.
- **Trace:**

  > CodeMain.claimInstance and checkInnoSetupMutex in src/vs/code/electron-main/main.ts coordinate startup with the installer through the -updating mutex. The current path relinquishes IPC ownership, polls for approximately 30 seconds without UI, and either resumes startup or throws an error that is only logged. GetSetupMutex in build/win32/code.iss publishes the installer signal. The issue proposes a separate native waiting process and mutex, but this checkout contains only the updater executable and manifest, not its Rust implementation, so the native boundary and validation harness remain unresolved. Preserve setup-versus-archive gating and existing instance-ownership safety. https://github.com/microsoft/vscode/pull/263998 introduced the surrounding versioned-update work; https://github.com/microsoft/vscode/pull/292864 and https://github.com/microsoft/vscode/pull/336253 address adjacent launch races, not this visible waiting experience.

## Evidence

- **Reported intent and protection:** https://github.com/microsoft/vscode/issues/279144 is MEMBER-authored and explicitly says blocking launch during installation is expected; the missing capability is visible waiting feedback and subsequent launch. This is an accepted UX improvement, not grounds for an as-designed decline.
- **Current startup behavior:** src/vs/code/electron-main/main.ts:560–595, CodeMain.checkInnoSetupMutex, checks the -updating mutex for Windows versioned setup installations, releases instance ownership through onActive, and polls for approximately 30 seconds. It logs the wait but creates no progress UI; mutex release permits startup to continue, while an expired wait returns true.
- **Timeout remains invisible:** src/vs/code/electron-main/main.ts:361–386 throws a localized update-in-progress Error when the mutex remains active. handleStartupDataDirError at lines 495–505 only displays dialogs for EACCES or EPERM, so this generic update error is not shown through that dialog path.
- **Installer coordination:** build/win32/code.iss:1642–1651, GetSetupMutex, creates both the setup mutex and the -updating mutex during background updates. The launch guard therefore has a concrete installer-lifecycle signal, but no visible waiting experience on the inspected path.
- **Existing settings do not cover the request:** src/vs/platform/update/common/update.config.contribution.ts registers update.enableWindowsBackgroundUpdates and update.titleBar. Disabling background updates avoids the scenario rather than solving it, and the title-bar indicator cannot explain a launch blocked before any workbench window opens.
