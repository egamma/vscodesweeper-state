# Issue #134410 — Possible to disable automatic insertion of periods when using Codespaces on macOS?

[https://github.com/microsoft/vscode/issues/134410](https://github.com/microsoft/vscode/issues/134410)

## Summary

This remains a well-supported feature request: 20 community upvotes and several recent confirmations show that macOS automatic period insertion still disrupts code editing. The available `editor.editContext: false` workaround disables a broader input backend rather than providing the requested text-replacement control.

## Change summary

Provide a VS Code-scoped way to suppress macOS double-space period insertion without disabling the preference globally.

## Best solution

Give code editors a focused, consistent Desktop and web/Codespaces control for automatic text substitutions, preserving ordinary EditContext, IME, and accessibility behavior. At minimum, users should be able to suppress double-space period insertion without changing the system-wide preference.

## Plan brief

- **Likely files:** `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/browser/view.ts`, `src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts`, `src/vs/editor/browser/controller/editContext/textArea/textAreaEditContextInput.ts`
- **Validation:** On macOS with the system double-space period preference enabled, verify in both VS Code Desktop and vscode.dev/Codespaces that two spaces remain two spaces when the new control is enabled, while ordinary typing, IME composition, VoiceOver input, and the existing `editor.editContext` modes continue to work.
- **Behavior:**

  > Users need to prevent macOS from replacing two spaces with a period and space inside code editors without disabling the operating-system preference globally. The behavior should be consistent in VS Code Desktop and web/Codespaces and should not require disabling the entire EditContext input backend. Acceptance requires two spaces to remain unchanged when suppression is selected, while ordinary typing, IME composition, and screen-reader input remain functional.
- **Trace:**

  > The maintainer analysis at https://github.com/microsoft/vscode/issues/134410#issuecomment-937699451 traces the original web behavior to the hidden textarea retaining enough surrounding text for macOS replacement. Current source defaults `editor.editContext` to true in src/vs/editor/common/config/editorOptions.ts, and src/vs/editor/browser/view.ts selects NativeEditContext or TextAreaEditContext as complete input backends. The workaround from https://github.com/microsoft/vscode/issues/134410#issuecomment-3168461936 therefore changes the entire backend rather than controlling one substitution. The trace reaches both src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts and the textarea input path; uncertainty begins at the desired public scope of suppression. Preserve IME composition, long-press accents, accessibility-mode input, and unrelated non-editor text fields.
- **Open decisions:**
  - Should VS Code suppress only the macOS double-space period substitution, or expose a broader per-editor control for all automatic text replacements?

## Evidence

- **maintainer analysis:** https://github.com/microsoft/vscode/issues/134410#issuecomment-937699451 identifies this as a distinct feature request for suppressing the `<space><space>` to `.<space>` replacement, separate from support for macOS substitutions generally.
- **current workaround:** https://github.com/microsoft/vscode/issues/134410#issuecomment-3168461936 recommends `editor.editContext: false`, and a reporter confirmed that it prevents the behavior on macOS in https://github.com/microsoft/vscode/issues/134410#issuecomment-3170040306.
- **source trace:** src/vs/editor/common/config/editorOptions.ts registers `editor.editContext` as a broad boolean selecting the EditContext input API, while src/vs/editor/browser/view.ts switches wholesale between NativeEditContext and TextAreaEditContext. Current source contains no dedicated control for automatic period insertion.
- **continued demand:** The issue has reached 20 body upvotes, and comments from July-August 2025 provide multiple independent confirmations that globally disabling the macOS preference is inadequate because users want substitutions outside code editors.
- **related report:** https://github.com/microsoft/vscode/issues/254756 was closed after its reporter identified macOS double-space substitution as the cause, then linked back here; it does not replace this open feature request.
