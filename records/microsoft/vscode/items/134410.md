# Issue #134410 — Possible to disable automatic insertion of periods when using Codespaces on macOS?

[https://github.com/microsoft/vscode/issues/134410](https://github.com/microsoft/vscode/issues/134410)

## Summary

The requested dedicated suppression remains valid and has substantial demand: `editor.editContext: false` is a confirmed workaround, but it disables the entire EditContext input path rather than controlling macOS text replacement. The issue has reached 20 community upvotes and should remain open for an editor-input design decision.

## Change summary

Allow macOS automatic double-space period replacement to be disabled in VS Code without disabling it globally or abandoning the EditContext input path.

## Best solution

Provide an editor-scoped way to suppress automatic text replacement while retaining EditContext, IME, and accessibility behavior where possible. Maintainers should first decide whether this is one cross-platform editor setting, a macOS desktop substitutions control, or separate desktop and web behavior because browser-hosted Codespaces may expose different capabilities.

## Plan brief

- **Likely files:** `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts`, `src/vs/platform/menubar/electron-main/menubar.ts`
- **Validation:** On macOS with the system double-space-period preference enabled, verify in both desktop VS Code and vscode.dev/Codespaces that the chosen editor-scoped control prevents `x  ` from becoming `x. ` while preserving ordinary typing, long-press accented input, IME composition, and screen-reader input; verify the inverse state continues to honor the OS behavior where intended.
- **Behavior:**

  > With macOS automatic period insertion enabled globally, users need an editor-scoped way to type consecutive spaces in source code without receiving a period. The control must not require disabling the useful OS behavior in prose applications. Acceptance must cover desktop VS Code and the browser-hosted Codespaces scenario, with ordinary typing, IME, long-press accents, and screen-reader input remaining functional.
- **Trace:**

  > The original web behavior was traced by a maintainer to the hidden textarea retaining enough surrounding text for macOS replacement. Current main normally uses NativeEditContext when supported: `EditorOptions.editContext` defaults to true in src/vs/editor/common/config/editorOptions.ts, and `NativeEditContext._emitTypeEvent` in src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts converts EditContext replacement ranges into editor input. Commit b0668717b88f68426ebd8be0eafd8e7d9680726d enabled that path on stable, after which desktop users reported the same behavior. `editor.editContext: false` is confirmed to avoid it, but changes the complete input implementation and therefore is not equivalent to a dedicated replacement preference. Electron substitution roles are admitted by `createRoleMenuItem` in src/vs/platform/menubar/electron-main/menubar.ts but are not currently exposed. The boundary is text-input policy: do not regress EditContext, IME, accessibility, or unrelated macOS replacements while deciding whether browser and desktop can share semantics.
- **Open decisions:**
  - Should suppression be the default for code editors, an explicit editor setting, or a macOS substitutions menu state?
  - Can browser-hosted VS Code suppress this replacement while retaining EditContext, or must the web and Electron implementations expose different capabilities?
  - Should the control cover only double-space periods or all platform text replacements, and should its scope be per editor, workspace, or application?

## Evidence

- **confirmed demand:** The issue has 20 body upvotes, and several independent commenters confirmed that macOS double-space replacement interferes with code and comments while remaining desirable in email and other prose applications.
- **maintainer diagnosis:** https://github.com/microsoft/vscode/issues/134410#issuecomment-937699451 explains that the web editor's hidden textarea allows macOS replacement and explicitly classifies a dedicated suppression option as a feature request.
- **current workaround is broader than the request:** A commenter confirmed at https://github.com/microsoft/vscode/issues/134410#issuecomment-3170040306 that setting `editor.editContext` to `false` suppresses the behavior, but that setting selects the entire editor input implementation rather than controlling automatic replacement.
- **current source:** src/vs/editor/common/config/editorOptions.ts registers `editor.editContext` with default `true`; EffectiveEditContextEnabled selects NativeEditContext when supported. src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts forwards replacement ranges from EditContext text-update events into editor composition input.
- **regression context:** Commit b0668717b88f68426ebd8be0eafd8e7d9680726d enabled EditContext by default on stable in May 2025, matching reports that desktop behavior appeared around VS Code 1.101.
- **missing dedicated control:** Current main contains no editor option for automatic period/text-replacement suppression. src/vs/platform/menubar/electron-main/menubar.ts recognizes Electron substitution role types but does not instantiate a substitutions or text-replacement menu item.
