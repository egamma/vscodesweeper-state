# Issue #232559 — Error: Trying to add a disposable to a DisposableStore that has already been disposed of. The added object will be leaked!

[https://github.com/microsoft/vscode/issues/232559](https://github.com/microsoft/vscode/issues/232559)

## Summary

This remains actionable debt on current main: disposing an output channel before its asynchronous creation completes causes several continuations to add resources to the already-disposed channel store. The Backlog milestone reflects accepted work, and neither the older similarly worded issue nor current source provides grounds to close it.

## Change summary

Creating an extension-host output channel and disposing it immediately can emit a disposed-store warning and leak resources.

## Best solution

Make output-channel creation safe when disposal occurs during asynchronous initialization, ensuring late-created resources are cleaned up without warnings while preserving normal output and log-channel behavior.

- **Behavior:**

  > Creating an output channel and disposing it synchronously must not emit a DisposableStore warning or leave resources registered when asynchronous channel initialization later completes. This must hold for ordinary output channels and log output channels. Channels that remain alive must retain their existing registration, logging, visibility, and disposal behavior.
- **Trace:**

  > ExtHostOutputService.createOutputChannel in src/vs/workbench/api/common/extHostOutput.ts starts doCreateOutputChannel or doCreateLogOutputChannel and immediately returns a wrapper backed by channelDisposables. The wrapper can dispose that store while asynchronous directory creation or main-thread registration is pending; later continuations add the logger, deregistration callback, resolved channel, and map cleanup to the disposed store. The minimal reproduction and the 1.131.0 stack both identify doCreateOutputChannel. Keep the boundary within extension-host output-channel lifecycle handling: do not change global DisposableStore semantics or conflate this with the distinct ExtensionHostManager race in https://github.com/microsoft/vscode/issues/188307.
