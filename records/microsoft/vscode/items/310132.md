# Issue #310132 — Lost of Chat Sessions in Code UI - JSONL persist in Folders - Chat: Import Chat only works JSON (v1.115 -> v1.116 transition (?))

[https://github.com/microsoft/vscode/issues/310132](https://github.com/microsoft/vscode/issues/310132)

## Summary

The reported disappearance was transient and lacks enough detail to establish a current data-loss bug, but the follow-up identifies a real chat-portability gap: VS Code cannot recover its internal JSONL session logs through the JSON-only import command. This should remain open and be routed to the chat area for a recovery/import design decision.

## Change summary

Provide a first-class way to recover, import, export, or transfer persisted chat sessions, including sessions stored internally as JSONL.

## Best solution

Define a supported recovery and portability flow for on-disk chat sessions, coordinated with the orphan-recovery work in https://github.com/microsoft/vscode/issues/305818. Keep the stable export format distinct from internal operation logs, but provide a supported command that can discover, validate, and restore recoverable sessions without requiring users to manipulate workspace storage.

- **Validation:** Add targeted chat tests proving that the chosen recovery flow restores a valid persisted session while preserving existing exported-JSON import behavior and rejecting malformed operation logs.
- **Behavior:**

  > Users with valid chat-session data still present under workspace storage should have a supported way to make those sessions visible again without hand-editing storage or converting files with external scripts. Existing exported `.json` chats must remain importable. Invalid or partial session logs must be rejected with a clear error rather than appearing successfully restored. The plan should separately define whether transfer between Code and Code Insiders is part of this recovery surface.
- **Trace:**

  > The import action in src/vs/workbench/contrib/chat/browser/actions/chatImportExport.ts filters for `.json` and delegates to `parseChatImport`, which expects one exported `IExportableChatData` object in src/vs/workbench/contrib/chat/common/model/chatModel.ts. Persisted `.jsonl` files use a different internal operation-log representation replayed by `ChatSessionOperationLog` through `ChatSessionStore.readSessionFromLocation` in src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts. The reporter's sessions partially returned, so the v1.115-to-v1.116 disappearance itself is not confirmed from the supplied steps. https://github.com/microsoft/vscode/issues/305818 owns workspace-orphan discovery and recovery but not the entire portability request; avoid duplicating that issue's narrower workspace-relinking scope. Existing exported-JSON behavior and storage validation must not be weakened.
- **Open decisions:**
  - Should `Chat: Import Chat` accept validated internal JSONL operation logs, or should raw persisted sessions be handled by a separate recovery command while import remains limited to the stable export format?
  - Is transfer or synchronization between Code and Code Insiders part of the supported portability contract, or should this issue cover only recovery into the current installation?
  - Should recovery operate on explicitly selected files only, or discover recoverable sessions across workspace-storage buckets as part of the flow tracked by https://github.com/microsoft/vscode/issues/305818?

## Evidence

- **current import contract:** src/vs/workbench/contrib/chat/browser/actions/chatImportExport.ts registers only the `json` file extension and passes the selected file to `parseChatImport`; src/vs/workbench/contrib/chat/common/model/chatModel.ts parses one exported JSON object conforming to `IExportableChatData`.
- **internal storage format:** src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts reads `.jsonl` session files through `ChatSessionOperationLog.read`, while legacy `.json` files are parsed separately. An internal JSONL operation log therefore is not merely an exported chat with a different extension.
- **reporter follow-up:** The reporter said the sessions later returned, although not all of them, so the original v1.115-to-v1.116 loss is not a confirmed current reproduction; the remaining explicit request is for first-class import/export, bulk transfer, or synchronization.
- **related recovery work:** https://github.com/microsoft/vscode/issues/305818 is open and tracks discovering and recovering sessions orphaned by workspace moves or renames. It is related but does not fully absorb this report's JSONL import and Code/Insiders portability scope.
- **migration reports:** https://github.com/microsoft/vscode/issues/324959 is a newer open report with multiple confirmations of incomplete legacy-session recovery after upgrades, supporting the need for a durable recovery surface rather than proving this report's original transition symptom.
