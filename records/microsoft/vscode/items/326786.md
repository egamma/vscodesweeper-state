# Issue #326786 — vscode should be in the list already to toggle on screen recording

[https://github.com/microsoft/vscode/issues/326786](https://github.com/microsoft/vscode/issues/326786)

## Summary

Keep open: current main contains a macOS permission dead end where the issue reporter opens Screen Recording settings without first causing VS Code to be registered there. The source confirms the gap, and no older open canonical or landed fix owns it.

## Change summary

Ensure VS Code is already listed in macOS Screen Recording settings when the issue reporter directs the user there.

## Best solution

Make the user-initiated recording flow register VS Code with macOS screen-capture permissions before navigating to System Settings, while preserving the normal first-use native prompt and avoiding capture requests during application startup.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/issue/electron-browser/issueReporterEditorPane.ts`, `src/vs/workbench/contrib/issue/electron-browser/nativeRecordingService.ts`, `src/vs/workbench/contrib/issue/browser/recordingService.ts`
- **Validation:** On macOS with VS Code removed from Privacy & Security > Screen Recording, start recording from the issue reporter and follow its System Settings action; verify VS Code is present as a togglable entry without using the manual add button. Also verify an already-granted installation still begins recording and non-macOS recording behavior is unchanged.
- **Behavior:**

  > When the issue reporter needs macOS Screen Recording permission and sends the user to System Settings, VS Code must already appear in the Screen Recording application list so the user can enable it directly. A fresh permission request must retain the native macOS consent flow without producing duplicate guidance. Already-granted recording and non-macOS behavior must remain unchanged.
- **Trace:**

  > The recording-start handler in src/vs/workbench/contrib/issue/electron-browser/issueReporterEditorPane.ts returns immediately for `denied` or `restricted` permission and exposes an Open System Settings action. NativeRecordingService.openScreenCapturePermissionSettings in src/vs/workbench/contrib/issue/electron-browser/nativeRecordingService.ts only opens the macOS deep link, while the capture-source request that can register the application is reached through the blocked startRecording path. This makes the reported dead end source-reproducible on current main. Keep registration user-triggered; do not warm screen capture during startup, since eager capture requests have caused Linux portal prompts as documented in https://github.com/microsoft/vscode/issues/317948. Commit 773c2c53ee03806f2ad1b6a90c760a950d3fecdb is a useful implementation lead but is not on current main.

## Evidence

- **current source:** In src/vs/workbench/contrib/issue/electron-browser/issueReporterEditorPane.ts, the recording-start handler detects `denied` or `restricted`, shows the permission notification, and returns before calling `startRecording`; the notification's action only calls `openScreenCapturePermissionSettings()`.
- **registration gap:** src/vs/workbench/contrib/issue/electron-browser/nativeRecordingService.ts implements `openScreenCapturePermissionSettings()` solely by opening the `Privacy_ScreenCapture` System Settings deep link. The API call that obtains capture sources is reached only later through `startRecording`, so the denied path never performs the operation that can register VS Code with macOS TCC.
- **unlanded fix lead:** Commit 773c2c53ee03806f2ad1b6a90c760a950d3fecdb contains a directly relevant permission-flow revision, but `git merge-base --is-ancestor` confirms it is not an ancestor of current HEAD; it therefore cannot support an implemented-on-main close.
