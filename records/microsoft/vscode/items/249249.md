# Issue #249249 — Make it easier to distinguish & trigger chat completion types

[https://github.com/microsoft/vscode/issues/249249](https://github.com/microsoft/vscode/issues/249249)

## Summary

The request remains necessary: current main has type icons and isolated scoped behavior for sessions, but bare `#` still mixes files, symbols, attachments, and tools. Maintainer interest and two iteration-plan references support keeping this accepted chat-input improvement open.

## Change summary

Organize chat input completions into recognizable, triggerable categories such as files, symbols, and tools instead of presenting every `#` completion together.

## Best solution

Provide labeled top-level completion categories that lead into a keyboard-accessible second completion containing only that category's items, while preserving current attachment parsing and agent-host completion boundaries. Reuse the existing completion-kind icons and document the scoped workflow in Chat Accessibility Help.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/attachments/chatContextPickService.ts`, `src/vs/workbench/contrib/chat/browser/contextContrib/chatContextService.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatAccessibilityHelp.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/input/editor/chatInputCompletions.test.ts`
- **Validation:** Add a scoped-completion suite in src/vs/workbench/contrib/chat/test/browser/widget/input/editor/chatInputCompletions.test.ts and run `./scripts/test.sh --grep "scoped chat completions"`; verify bare `#` returns category entries, each accepted category exposes only its own items, and existing unscoped parsing and agent-host completion tests remain unchanged.
- **Behavior:**

  > Typing `#` in the chat input should initially present a small, clearly labeled set of completion categories rather than mixing every file, symbol, attachment, and tool. Entering or accepting a category such as files or tools should expose only valid items of that type through the normal keyboard completion flow. Completion labels and kinds must remain understandable without relying on icons alone, and Chat Accessibility Help must explain the workflow. Existing accepted references and agent-host-provided completions must continue to parse and execute as before.
- **Trace:**

  > BuiltinDynamicCompletions in src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts currently registers separate providers whose results converge on bare `#`; ToolCompletions independently contributes enabled tools. The session provider in that file demonstrates one scoped two-stage flow by inserting `#session:` and retriggering suggestions. IChatContextPickService in src/vs/workbench/contrib/chat/browser/attachments/chatContextPickService.ts centralizes Add Context items but carries no prefix or completion-provider contract, while ChatContextService adapts extension-contributed context pickers into that service. ChatInputPart already enables completion icons and suppresses only the generic Text icon, so the remaining problem is hierarchy and targeted triggering rather than a new visual surface. Chat Accessibility Help currently explains `#`/`@` attachment suggestions but not scoped categories. Keep agent-host-backed widgets on their existing host-provided completion path and do not change final attachment semantics outside the category workflow.
- **Open decisions:**
  - After a user accepts a top-level category, should VS Code automatically open the second completion list or require the user to invoke suggestions explicitly?
  - For tool completions, should the accepted text retain `#tool:<name>` or should `#tool:` be a transient scope that resolves to the existing `#<name>` reference syntax?

## Evidence

- **current source gap:** In src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts, BuiltinDynamicCompletions registers independent file, symbol, attachment, and session providers; the file provider calls addFileAndFolderEntries for a bare `#`, while ToolCompletions independently returns every matching enabled tool as `#<name>`. There is no common top-level category stage.
- **partial precedent:** The session provider in src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts already offers `#session` first, inserts `#session:`, and invokes `editor.action.triggerSuggest` for the second-stage session list. That scoped pattern has not been generalized to files, symbols, or tools.
- **service boundary:** src/vs/workbench/contrib/chat/browser/attachments/chatContextPickService.ts exposes registered items with labels, icons, and picker/value behavior, but has no completion prefix or completion-provider metadata. This matches the issue author's identified integration point and leaves the proposed unification incomplete.

The CSS only suppresses the generic Text glyph, so distinct type icons are already available but do not provide dedicated scoped triggering.
