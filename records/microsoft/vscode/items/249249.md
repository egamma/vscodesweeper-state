# Issue #249249 — Make it easier to distinguish & trigger chat completion types

[https://github.com/microsoft/vscode/issues/249249](https://github.com/microsoft/vscode/issues/249249)

## Summary

Keep open: completion icons now distinguish several types, but files, symbols, and tools still lack the requested category-first completion flow. A newer request describes the same remaining problem, but cannot supersede this older, previously reviewed issue.

## Change summary

Make chat context completions easier to distinguish and target through category-scoped suggestions.

## Best solution

Provide a consistent category-first completion experience for files, symbols, and tools, building on the existing session-prefix behavior. Coordinate the overlapping context-bucket request under this older issue and settle compatibility with direct references before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts`, `src/vs/workbench/contrib/chat/browser/attachments/chatContextPickService.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatContext.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/input/editor/chatInputCompletions.test.ts`
- **Validation:** Extend the chat input completion tests to assert category suggestions and category-restricted file, symbol, and tool results, then run that targeted suite through scripts/test.sh. Manually verify keyboard selection, follow-up suggestions, backspacing out of a category, and the agreed compatibility behavior for direct references.
- **Behavior:**

  > Chat context suggestions should let users choose a context type before navigating its candidates, instead of competing with unrelated file, symbol, and tool matches. Selecting or typing a category should expose only candidates belonging to that category. Existing icons provide partial differentiation but do not satisfy targeted completion. Acceptance should cover category discovery, scoped candidate lists, keyboard operation, and the agreed behavior of existing direct references.
- **Trace:**

  > BuiltinDynamicCompletions and ToolCompletions in src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts independently contribute candidates on shared #/@ triggers. Files insert #file:<name>, but that insertion format is not a general category-scoping mechanism. The sessionReference provider already implements a two-stage #session to #session: flow with editor.action.triggerSuggest. IChatContextPickService in browser/attachments/chatContextPickService.ts currently abstracts separate Add Context picks rather than prefix-aware completion contributions. ChatInputPart already enables suggestion icons, so restoring icons is not the remaining task. Agent-host-backed widgets delegate most completion providers to the host; do not assume changing local providers also changes those sessions. https://github.com/microsoft/vscode/issues/273774 independently describes the remaining bucket interaction but is newer than this issue. The unresolved product boundary is how category-first discovery coexists with current direct-name references.
- **Open decisions:**
  - Should bare # show only context categories, or retain recent/context candidates alongside those categories?
  - Should direct #<file-or-tool-name> completion remain available alongside category-scoped completion?
