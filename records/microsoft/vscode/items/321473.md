# Issue #321473 — Drag-and-drop from remote -> desktop creates a file with remote file URI

[https://github.com/microsoft/vscode/issues/321473](https://github.com/microsoft/vscode/issues/321473)

## Summary

The bug remains possible on current main: Explorer drags advertise a remote `vscode-remote` URI through standard native data-transfer types, allowing macOS Desktop to create an internet-location file instead of rejecting the unsupported drop.

## Change summary

Dragging a remote Explorer file to the macOS Desktop creates an internet-location file containing the remote URI instead of blocking the unsupported operation.

## Best solution

Remote Explorer drags should remain usable for supported VS Code-internal targets, while unsupported native targets receive no payload that can create an `.inetloc` or `.webloc` file.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/dnd.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`
- **Validation:** On macOS, drag a file from a Remote-SSH Explorer first to Finder and then directly to the Desktop; neither target should create an `.inetloc`, `.webloc`, or copied file, while Explorer reordering and supported VS Code-internal drag targets continue to work.
- **Behavior:**

  > Dragging a remote file from VS Code Explorer to an unsupported macOS native destination must not create an internet-location file containing the remote URI. Finder and Desktop should consistently reject the operation. Supported drag operations inside VS Code must remain unchanged.
- **Trace:**

  > FileDragAndDrop.onDragStart in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts forwards remote ExplorerItem resources to fillEditorsDragData. In src/vs/workbench/browser/dnd.ts, fillEditorsDragData publishes both a text representation and a standard `text/uri-list` entry for those remote resources, exposing the `vscode-remote` URI to macOS. Commit f9070acd20a269fb07dd15389676bd6875b9db05 attempted to exclude remote resources from the text payload because macOS creates URL bookmark files, but commit 93cfdd489c3b228840d0f86ec77c3636277c93ea reverted that guard and neither version excluded the standard URI-list payload. Keep internal transfer types and supported VS Code drag behavior in scope; do not turn this into implementation of remote-to-native downloading, which remains separately tracked by https://github.com/microsoft/vscode/issues/116989.

## Evidence

- **current source path:** In src/vs/workbench/contrib/files/browser/views/explorerViewer.ts, FileDragAndDrop.onDragStart passes remote ExplorerItem resources to fillEditorsDragData without disabling standard transfers.
- **native payload:** src/vs/workbench/browser/dnd.ts sets DataTransfers.TEXT from every file-system resource and sets Mimes.uriList from dragged editor resources; neither standard-transfer path excludes `vscode-remote` resources on current main.
- **reverted guard:** https://github.com/microsoft/vscode/commit/f9070acd20a269fb07dd15389676bd6875b9db05 explicitly identified macOS URL bookmark creation and filtered remote resources from the text payload, but https://github.com/microsoft/vscode/commit/93cfdd489c3b228840d0f86ec77c3636277c93ea reverted that guard along with the broader copy/paste refactor. The standard URI-list payload was not guarded by either version.
- **related but not duplicate:** https://github.com/microsoft/vscode/issues/116989 tracks failed remote-to-native downloading, while https://github.com/microsoft/vscode/issues/93599 primarily tracks remote-to-local VS Code transfer. Neither has the same reporter-observable Desktop `.inetloc` behavior required to close this re-reviewed issue as a duplicate.
