# Issue #339173 — Terminal shortcuts should take priority over VS Code commands when alternate buffer is active

[https://github.com/microsoft/vscode/issues/339173](https://github.com/microsoft/vscode/issues/339173)

## Summary

Real, well-diagnosed gap: the keyboard dispatch path in terminalInstance.ts has no alt-buffer awareness today, so `commandsToSkipShell` is an all-or-nothing global override rather than one that only applies while a normal shell prompt (not a TUI/alt-buffer app) is active. Worth keeping open as a design discussion rather than closing.

## Change summary

Make terminal keybinding passthrough (currently governed globally by `terminal.integrated.commandsToSkipShell`) alternate-buffer-aware, so shortcuts like Ctrl+P only reach the shell/app while the terminal's alt buffer (e.g. a TUI like vim or an AI agent CLI) is active, without disabling the VS Code shortcut elsewhere.

## Best solution

Extend the keyboard handling in TerminalInstance (around the `attachCustomKeyEventHandler` callback in src/vs/workbench/contrib/terminal/browser/terminalInstance.ts) to consult the existing `TerminalContextKeys.altBufferActive` state when deciding whether a `commandsToSkipShell` entry should skip the shell, likely behind a new opt-in setting since changing default global behavior could surprise existing users relying on `commandsToSkipShell` as an unconditional list.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/terminal/browser/terminalInstance.ts`, `src/vs/workbench/contrib/terminal/browser/terminalConfigurationService.ts`, `src/vs/workbench/contrib/terminal/common/terminalConfiguration.ts`
- **Validation:** A terminal integration/unit test confirming a `commandsToSkipShell` command reaches the shell when `terminalAltBufferActive` is true and is handled by VS Code when it is false (or whatever the agreed contract becomes).
- **Trace:**

  > The custom key handler in terminalInstance.ts (`attachCustomKeyEventHandler`, ~line 1157-1184) resolves keybindings and checks `shouldCommandSkipShell` unconditionally; `TerminalContextKeys.altBufferActive` (terminalContextKey.ts:91) tracks alt-buffer state and is refreshed via `_refreshAltBufferContextKey()` (terminalInstance.ts:1305) but is not read in this dispatch path today.
- **Open decisions:**
  - Should alt-buffer-aware passthrough be a new opt-in setting, or change the default behavior of `commandsToSkipShell` itself?
  - Should this apply to all commands in `commandsToSkipShell`/`DEFAULT_COMMANDS_TO_SKIP_SHELL`, or only to a configurable subset?
  - How should this interact with `sendKeybindingsToShell` and `allowChords`, which already globally affect the same dispatch path?

## Evidence

- **context key exists but unused for dispatch:** src/vs/workbench/contrib/terminal/common/terminalContextKey.ts defines `TerminalContextKeys.altBufferActive`, and it's used for some command `when` clauses (terminalActions.ts:81, `focusInAny_and_normalBuffer`), but the keyboard dispatch path never consults it.
- **global-only skip logic:** src/vs/workbench/contrib/terminal/browser/terminalInstance.ts:1181 decides to skip the shell purely from `this._terminalConfigurationService.shouldCommandSkipShell(resolveResult.commandId)` and `sendKeybindingsToShell`, with no alt-buffer check — confirming the reported global-only behavior.
- **setting description confirms scope:** src/vs/workbench/contrib/terminal/common/terminalConfiguration.ts:434-447 describes `commandsToSkipShell`/the `-` override as unconditional; `workbench.action.quickOpen` and `workbench.action.showCommands` are in `DEFAULT_COMMANDS_TO_SKIP_SHELL` (terminal.ts:565,567), matching the reporter's Ctrl+P example.
