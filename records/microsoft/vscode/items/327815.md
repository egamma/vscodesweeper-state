# Issue #327815 — Error when launching the VSCode via Code.exe

[https://github.com/microsoft/vscode/issues/327815](https://github.com/microsoft/vscode/issues/327815)

## Summary

Keep open: two users confirmed that digit-prefixed environment variables prevent the extension host from starting when launching Code.exe directly. Current source still forwards those keys to Electron; neither a landed fix nor an eligible older duplicate was established.

## Change summary

Launching Code.exe directly fails to start the extension host when the inherited environment contains a digit-prefixed variable such as SharePoint's `16`.

## Best solution

Make direct Windows launches start the extension host reliably with OS-valid inherited environment variables. Establish the precise Electron rejection condition before deciding whether the correction belongs in VS Code's environment handoff or Electron, without imposing dotenv naming restrictions on all Windows variables.

Compare a launch without that variable and a bin/code.cmd launch; preserve ordinary Windows variables such as ProgramFiles(x86). Establish an automated Electron utility-process regression check once the rejection condition is isolated.
- **Behavior:**

  > With a digit-prefixed inherited environment variable, direct Code.exe or Start-menu launches can open the window while failing to start the local extension host. The reporter and another user confirmed that removing such a variable restores extension loading, while bin/code.cmd provides a workaround. The expected outcome is reliable extension-host startup without requiring users to remove another application's environment variables. Acceptance should compare direct and CLI launches with and without the reported variable and confirm that ordinary Windows environment variables remain usable.
- **Trace:**

  > LocalProcessExtensionHost._start in src/vs/workbench/services/extensions/electron-browser/localProcessExtensionHost.ts obtains the shell environment and passes it through ExtensionHostStarter.start to WindowUtilityProcess. UtilityProcess.createEnv in src/vs/platform/utilityProcess/electron-main/utilityProcess.ts copies that environment and stringifies values before UtilityProcess.doStart calls Electron's utilityProcess.fork. removeDangerousEnvVariables in src/vs/base/common/processes.ts does not remove digit-prefixed keys, so the reported `16` key survives the inspected handoff. The remaining uncertainty is which Electron validation condition actually rejects the environment and whether the appropriate correction is local or upstream; Node's dotenv naming guidance alone does not establish that contract. Preserve normal Windows variable names and existing dangerous-variable filtering, and keep broader case-folding, NUL, and serialization proposals outside this report's acceptance scope.
