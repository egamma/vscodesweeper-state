# Issue #144120 — Can't read deeply nested files in narrow explorer

[https://github.com/microsoft/vscode/issues/144120](https://github.com/microsoft/vscode/issues/144120)

## Summary

A real readability gap remains: horizontal scrolling is an opt-in workaround, but it does not provide the requested automatic shift when only deeply nested rows are visible. The Backlog milestone records this as accepted work, and no older open issue owns the same observable request.

## Change summary

Automatically shift deeply nested Explorer rows left when a narrow viewport contains no shallow resources, keeping file names readable.

## Best solution

Provide an adaptive Explorer indentation or viewport offset that preserves visible hierarchy while making deeply nested names readable, without enabling the more expensive global horizontal-scrolling behavior by default.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/base/browser/ui/tree/abstractTree.ts`, `src/vs/platform/list/browser/listService.ts`, `src/vs/base/test/browser/ui/tree/objectTree.test.ts`
- **Validation:** Add browser-tree regression coverage for a narrow viewport containing only deeply nested visible nodes, then run `scripts/test.sh --grep "adaptive indentation"`; also manually confirm that revealing a shallow row restores normal indentation and that `workbench.list.horizontalScrolling` retains its current behavior.
- **Behavior:**

  > In a narrow Explorer where every visible resource is deeply nested, names remain readable instead of being consumed by off-screen indentation. The hierarchy must remain understandable, and normal indentation returns when shallower resources become visible. Explicit horizontal scrolling must continue to behave as configured. Acceptance covers both entering and leaving the deeply nested viewport state.
- **Trace:**

  > ExplorerView creates a WorkbenchCompressibleAsyncDataTree in src/vs/workbench/contrib/files/browser/views/explorerView.ts. Its shared TreeRenderer in src/vs/base/browser/ui/tree/abstractTree.ts derives indentation solely from node depth and a fixed indent size, with no awareness of the shallowest visible node. Workbench tree construction in src/vs/platform/list/browser/listService.ts independently applies `workbench.list.horizontalScrolling`, whose default remains false because of its documented performance cost. The existing setting is therefore a workaround, not implementation of the requested adaptive behavior. Keep explicit horizontal scrolling and ordinary mixed-depth tree layout unchanged; the uncertainty begins at whether this behavior should be Explorer-specific or a shared tree capability and how much hierarchy remains visible after shifting.
- **Open decisions:**
  - Should automatic left shifting apply only to the File Explorer, or consistently to every workbench tree with deeply nested visible rows?
  - When adaptive shifting is active, how much ancestor indentation or guide context must remain visible so users can still distinguish hierarchy?
  - Should adaptive shifting be disabled when `workbench.list.horizontalScrolling` is enabled, or should the two behaviors coexist?

## Evidence

- **existing workaround:** The maintainer comment at https://github.com/microsoft/vscode/issues/144120#issuecomment-1057062232 identifies `workbench.list.horizontalScrolling`, but also explains that its performance cost prevents enabling it by default.
- **current source:** src/vs/platform/list/browser/listService.ts registers `workbench.list.horizontalScrolling` with default `false` and a performance warning; Explorer inherits it through WorkbenchCompressibleAsyncDataTree in src/vs/workbench/contrib/files/browser/views/explorerView.ts.
- **remaining gap:** src/vs/base/browser/ui/tree/abstractTree.ts computes every rendered row's indentation as `defaultIndent + (node.depth - 1) * indent`; there is no viewport-aware adjustment when all visible nodes are deep.
- **canonical search:** The newer https://github.com/microsoft/vscode/issues/149136 was closed as a duplicate pointing back to this issue, while https://github.com/microsoft/vscode/issues/219644 concerns explicitly enabling a horizontal scrollbar. Neither supplies an older open canonical with the same automatic-shifting request.
- **later maintainer position:** At https://github.com/microsoft/vscode/issues/219644#issuecomment-2203095962 a maintainer reiterated that horizontal scrolling increases virtual-DOM size and layout work and is not planned as the default, leaving room for a less costly adaptive solution.
