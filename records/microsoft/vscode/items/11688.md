# Issue #11688 — Feature request: 'Ignore comments' checkbox in the 'Find' dialog

[https://github.com/microsoft/vscode/issues/11688](https://github.com/microsoft/vscode/issues/11688)

## Summary

Keep this accepted, well-supported request open: current editor Find and workspace text search still lack comment-aware filtering. This issue already serves as the canonical destination for narrower reports; the remaining work needs a language-coverage and performance design.

## Change summary

Provide an opt-in search filter that excludes matches in comments, including documentation comments, without excluding real code matches.

## Best solution

Define consistent comment-filtering semantics for editor Find and workspace search, then deliver an opt-in capability without slowing ordinary searches. Settle initial language coverage and unsupported-file behavior before implementation.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/find/browser/findState.ts`, `src/vs/editor/contrib/find/browser/findWidget.ts`, `src/vs/editor/contrib/find/browser/findModel.ts`, `src/vs/workbench/services/search/common/search.ts`, `src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts`, `src/vs/workbench/contrib/search/browser/search.contribution.ts`
- **Validation:** End the plan with executable editor-find and workspace-search acceptance tests: a term appearing in code, line comments, documentation/block comments, and string literals must retain code/string matches while excluding comment matches when enabled; disabling the filter must restore ordinary results. Cover the agreed unsupported-language behavior, multiline matches, navigation/count consistency, and representative large-workspace latency.
- **Behavior:**

  > Users searching documentation-heavy source files cannot currently exclude comment matches while retaining occurrences in executable code. An opt-in comment filter should remove matches classified as comments according to the agreed language policy while leaving ordinary search unchanged when disabled. Acceptance must distinguish comments from comment-like text in strings and keep displayed counts and navigation consistent with the filtered results. Workspace coverage and unsupported-language behavior must be explicitly agreed rather than implied.
- **Trace:**

  > Editor Find stores matching options in FindReplaceState and collects matches through FindModelBoundToEditorModel._findMatches, which delegates to the text model without comment classification. The editor.find configuration registrations contain no equivalent setting. Workspace search has a separate contract, IPatternInfo, and the disk-search path in RipgrepTextSearchEngine forwards textual matches without a comment-aware stage; editor token availability therefore does not by itself solve workspace search. Preserve existing regex, case, selection, cancellation, and ordinary-search behavior. This issue already owns both editor and workspace requests, as confirmed by https://github.com/microsoft/vscode/issues/237240 and https://github.com/microsoft/vscode/issues/205513 being closed into it. The trace establishes the missing capability, not a complete classification architecture or performance budget.
- **Open decisions:**
  - Should the initial release support both editor Find and workspace search, or explicitly deliver editor-only filtering first?
  - Which languages and embedded-language cases are supported initially, and what behavior and disclosure should users get when comment classification is unavailable or incomplete?
  - For a multiline match spanning both code and a comment, should any overlap with a comment exclude the entire match?
