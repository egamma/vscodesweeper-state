# Issue #246776 — Feature request: Reuse existing window when launching into a given profile, if profiles match

[https://github.com/microsoft/vscode/issues/246776](https://github.com/microsoft/vscode/issues/246776)

## Summary

Keep this canonical feature request open: it passed the community threshold, is parked in the Backlog, and current main still chooses reusable windows without considering the requested profile. A maintainer should first settle how `--profile` interacts with the existing window-reuse flags.

## Change summary

Make CLI launches with `--profile` reuse an existing window using that profile and create a new matching-profile window when none exists.

## Best solution

Make command-line window selection profile-aware: preserve explicit new-window behavior, prefer an appropriate existing window with the requested profile, and avoid opening content in a window using another profile. Define whether this happens for `--profile` alone or only with an explicit reuse mode before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/launch/electron-main/launchMainService.ts`, `src/vs/platform/windows/electron-main/windowsMainService.ts`, `src/vs/platform/windows/electron-main/windowsFinder.ts`, `src/vs/platform/windows/test/electron-main/windowsFinder.test.ts`
- **Validation:** Add automated main-process window-selection coverage for matching-profile reuse, mismatched-profile new-window creation, multiple matching windows, and explicit `--new-window`; run `scripts/test.sh --grep WindowsFinder` plus the targeted suite covering any routing logic retained in WindowsMainService.
- **Behavior:**

  > Launching a file or folder with a named profile must never route it into a window using a different profile. When reuse is enabled by the chosen CLI semantics, an appropriate existing window with the requested profile is focused and receives the content; if none exists, a new window using that profile opens. Explicit `--new-window` continues to create a new window. Acceptance must cover matching and mismatching profiles as well as multiple open windows.
- **Trace:**

  > The second-instance CLI path in src/vs/platform/launch/electron-main/launchMainService.ts carries `args.profile` into `IOpenConfiguration.forceProfile`. For file launches, WindowsMainService.doOpen in src/vs/platform/windows/electron-main/windowsMainService.ts filters candidates by remote authority, calls `findWindowOnFile`, and otherwise falls back to the last active window; no step filters or ranks by `ICodeWindow.profile`. `openInBrowserWindow` likewise reuses a supplied or last-active window before `resolveProfileForBrowserWindow` interprets `forceProfile`. Existing finder coverage is in src/vs/platform/windows/test/electron-main/windowsFinder.test.ts. Preserve workspace/path affinity, remote-authority isolation, explicit new-window behavior, and launches without `--profile`; the uncertainty begins at the public CLI semantics governing when profile matching implies reuse.
- **Open decisions:**
  - Should `--profile <name>` itself request reuse of a matching-profile window, or should profile-aware reuse require `--reuse-window` while plain `--profile` retains its current new-window behavior?
  - When several windows use the requested profile, should selection preserve the existing path/workspace affinity before falling back to the most recently active matching window?
