# Issue #286284 — 'fetch failed' with no 'try again'

[https://github.com/microsoft/vscode/issues/286284](https://github.com/microsoft/vscode/issues/286284)

## Summary

Keep open: the confirmed offline path detects the connection failure but still exposes only the generic “Language model unavailable” result instead of the existing actionable offline state. This is team-authored, and no explicit fixing commit or verified duplicate provides a mechanical close.

## Change summary

When Copilot Chat cannot obtain a model because the machine is offline, show a specific offline state with an accessible recovery action instead of only “Language model unavailable.”

## Best solution

Propagate the known offline condition through model selection and chat request handling so the user receives the existing check-connection guidance and a reliable recovery action, while preserving generic handling for non-network model failures.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/contextKeys/vscode-node/contextKeys.contribution.ts`, `extensions/copilot/src/extension/conversation/vscode-node/languageModelAccess.ts`, `extensions/copilot/package.json`, `extensions/copilot/package.nls.json`, `src/vs/workbench/api/common/extHostChatAgents2.ts`
- **Validation:** Add targeted tests covering token acquisition failing with a recognized offline error and the resulting chat-facing state; manually disable networking, send a prompt, verify specific offline guidance and a keyboard/screen-reader-accessible recovery action, then restore networking and verify recovery without losing the conversation.
- **Behavior:**

  > When a chat request cannot obtain a language model because VS Code has detected that Copilot is offline, the UI identifies the connectivity problem rather than reporting only “Language model unavailable.” It presents a keyboard- and screen-reader-accessible recovery action and retains the failed conversation context. After connectivity returns, recovery makes chat usable again without conflating unrelated model-unavailability errors with offline failures.
- **Trace:**

  > `ContextKeysContribution._inspectContext` in `extensions/copilot/src/extension/contextKeys/vscode-node/contextKeys.contribution.ts` already identifies token-fetch failures as `github.copilot.offline`, and the extension manifest/localization already provides an offline welcome state with `Retry Connection`. Separately, `LanguageModelAccess._getToken` catches the token error and returns no model; `ExtHostChatAgents2.getModelForRequest` then emits the generic `Language model unavailable` error without the offline cause. Core chat has a response-footer retry command, but that does not carry the extension's known connectivity state through this pre-model-selection path. Keep non-network model selection failures, BYOK behavior, and normal retry semantics unchanged. The related meta issues https://github.com/microsoft/vscode/issues/253136 and https://github.com/microsoft/vscode/issues/253137 cover broader failure clusters, not this specific recovery UX.
- **Open decisions:**
  - When offline is discovered after the user sends a prompt, should chat preserve the failed turn and show an inline offline recovery state, or transition to the existing offline welcome state and temporarily prevent sending?
  - After connectivity is restored, should the recovery action automatically resend the failed prompt or only refresh authentication/model availability and leave resubmission to the user?
