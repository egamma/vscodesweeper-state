# Issue #109151 — Text cursor indicator displays incorrect

[https://github.com/microsoft/vscode/issues/109151](https://github.com/microsoft/vscode/issues/109151)

## Summary

Still present on main: the Windows text cursor indicator follows the hidden textarea, which is positioned at the top-left or has 0/1px height when accessibility support is not detected as enabled. The OS-level cursor indicator feature is independent of screen reader detection, so users who enable it without a screen reader see it in the wrong place. No fix commit references this issue.

## Change summary

Windows 'text cursor indicator' accessibility feature displays at the wrong position in VS Code because the hidden textarea is not positioned at the actual cursor location.

## Best solution

When the Windows text cursor indicator is active (or more broadly, always on Windows), position the hidden textarea at the cursor location with proper dimensions — similar to the existing macOS/accessibility-enabled path at line 793 of textAreaEditContext.ts — so that OS-level cursor tracking features work correctly.

  > The Windows 'text cursor indicator' OS accessibility feature tracks the position of the focused textarea element. In src/vs/editor/browser/controller/editContext/textArea/textAreaEditContext.ts, the render method (around line 793) only positions the textarea at the actual editor cursor with proper height on macOS or when `this._accessibilitySupport === AccessibilitySupport.Enabled`. On Windows without a screen reader, the else branch (line 814) renders the textarea with 0 or 1px height, and when the cursor is outside the viewport, `_renderAtTopLeft()` places it at (0,0). This causes the Windows text cursor indicator to appear at the wrong location. The fix should extend the cursor-positioned rendering path (the one starting at line 793) to also apply on Windows (`platform.isWindows`), so the textarea tracks the real cursor position. Care must be taken not to break IME composition behavior or the existing macOS emoji picker positioning. Do not change the non-Mac, non-Windows, non-accessibility path. Validate with a unit test asserting that on Windows with accessibility support disabled, the textarea render data has the cursor's top/left and a non-zero height matching the line height.
