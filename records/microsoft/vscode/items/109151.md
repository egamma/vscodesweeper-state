# Issue #109151 — Text cursor indicator displays incorrect

[https://github.com/microsoft/vscode/issues/109151](https://github.com/microsoft/vscode/issues/109151)

## Summary

A later report of the same Windows text-cursor-indicator behavior received an explicit maintainer scope decision: the overlay is managed by Windows and cannot be reliably synchronized by VS Code. The existing editor implementation already provides best-effort caret geometry, so this can close as out of scope.

## Change summary

Make the Windows accessibility text cursor indicator remain aligned with the VS Code editor caret.

## Best solution

Retain VS Code's existing best-effort caret and accessibility geometry while leaving reliable rendering and synchronization of the Windows-managed indicator to the platform.

## Evidence

- **maintainer scope decision:** https://github.com/microsoft/vscode/issues/283921 reports the same Windows text cursor indicator appearing at random editor positions. A VS Code maintainer closed it on 2025-12-17 after explaining that Windows manages the overlay and VS Code has no explicit signal for controlling where it is rendered.
- **existing mitigation:** https://github.com/microsoft/vscode/pull/195934 placed the hidden textarea on the editor cursor when accessibility support is enabled; the change was verified with Windows magnifier software and remains in src/vs/editor/browser/controller/editContext/textArea/textAreaEditContext.ts.
- **current source boundary:** Current main supplies caret geometry through NativeEditContext._updateSelectionAndControlBounds in src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts and positions the fallback textarea in TextAreaEditContext._render, but contains no mechanism for rendering or directly synchronizing the Windows OS indicator.
