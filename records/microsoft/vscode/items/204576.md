# Issue #204576 — Tree Sticky Scroll Compression: Show most important parts

[https://github.com/microsoft/vscode/issues/204576](https://github.com/microsoft/vscode/issues/204576)

## Summary

A real gap remains on current main: compressed Explorer sticky rows retain ancestor-to-descendant label order, so horizontal overflow hides the more relevant trailing folders. The request should stay open while maintainers decide whether trailing-folder prioritization is Explorer-specific or part of the generic compressed-tree presentation.

## Change summary

Show the most relevant trailing folders in a one-line compressed tree sticky-scroll row, with an ellipsis for omitted ancestors.

## Best solution

Define an overflow behavior for compressed Explorer sticky rows that preserves the nearest folders and indicates omitted ancestors, without imposing Explorer-specific importance ordering on every compressible tree consumer.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/tree/objectTree.ts`, `src/vs/base/browser/ui/iconLabel/iconLabel.ts`, `src/vs/base/browser/ui/iconLabel/iconlabel.css`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`
- **Validation:** Exercise an Explorer path whose compressed sticky label exceeds the available width and verify that the nearest folders remain visible with an omission indicator; also verify that ordinary compressed Explorer rows and non-Explorer compressible trees retain their intended ordering and interaction.
- **Behavior:**

  > When a compressed Explorer sticky-scroll row is wider than its viewport, it should retain the folder names nearest the visible file and clearly indicate omitted ancestors. The row must remain one line, and a fully fitting path must continue to show every segment. Ordinary compressed Explorer rows and other tree consumers must not acquire an inappropriate importance order.
- **Trace:**

  > CompressibleStickyScrollDelegate.compressStickyNodes in src/vs/base/browser/ui/tree/objectTree.ts gathers elements in ancestor-to-descendant order. FileRenderer.renderCompressedElements in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts passes the corresponding name array to ResourceLabel, and Label.setLabel in src/vs/base/browser/ui/iconLabel/iconLabel.ts emits those segments in that order; iconlabel.css clips the resulting label at the trailing edge. Commit 16a32fa6c44885e7ea0b1eacb4944528602f8252 resolved only the max-item-count-one compression bug tracked by https://github.com/microsoft/vscode/issues/204613. The boundary is presentation and prioritization under horizontal overflow: do not alter sticky-node ancestry, compact-folder semantics, or compressed-node interaction tracked separately by https://github.com/microsoft/vscode/issues/203030. Uncertainty begins at the ownership boundary because the generic tree infrastructure has consumers whose important segment may be at the start rather than the end.
- **Open decisions:**
  - Should trailing-segment prioritization apply only to Explorer sticky rows, or should compressible tree consumers receive a public way to declare which segments are most important?
  - When all segments do not fit, should the row preserve only the trailing path with a leading ellipsis, or preserve both root context and trailing folders with a middle ellipsis?

## Evidence

- **current source:** src/vs/base/browser/ui/tree/objectTree.ts uses CompressibleStickyScrollDelegate.compressStickyNodes to collect compressed elements in ancestor-to-descendant order, while src/vs/workbench/contrib/files/browser/views/explorerViewer.ts maps that ordered list directly to folder labels.
- **overflow behavior:** src/vs/base/browser/ui/iconLabel/iconLabel.ts renders array labels from index 0 forward, and src/vs/base/browser/ui/iconLabel/iconlabel.css applies hidden overflow and ellipsis to the label containers; this preserves the leading ancestors rather than prioritizing the trailing folders.
- **linked bug:** https://github.com/microsoft/vscode/issues/204613 was fixed by commit 16a32fa6c44885e7ea0b1eacb4944528602f8252, but that change only enables compression when workbench.tree.stickyScrollMaxItemCount is 1; it does not change which folder names remain visible under horizontal overflow.
- **maintainer direction:** The maintainer comment on https://github.com/microsoft/vscode/issues/204576 agrees that the trailing folders are probably more important and suggests an initial ".../folderN-1/folderN" presentation.
- **design uncertainty:** The earlier discussion at https://github.com/microsoft/vscode/issues/199539 records that always showing the last elements produced an unpleasant scrolling experience and that other tree consumers may consider their first or second node most important. That issue is closed and cannot serve as a duplicate canonical.
