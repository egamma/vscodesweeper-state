# Issue #309680 — Agent mode create_file produces corrupted Go files due to race between empty file creation and gopls workspace/didCreateFiles

[https://github.com/microsoft/vscode/issues/309680](https://github.com/microsoft/vscode/issues/309680)

## Summary

Keep open: current source still creates an empty file and announces its creation before applying the agent's content, allowing gopls to insert a competing package declaration. The single-batch create_file improvement addresses a different race and does not eliminate this ordering gap.

## Change summary

Prevent agent-created Go files from acquiring duplicate package declarations or corrupted content when gopls initializes newly created files.

## Best solution

Make agent file creation and initial content application cooperate safely with file-creation listeners, without requiring users to disable gopls headers. Preserve normal extension notifications, existing-file edits, and chat edit review and undo behavior.

- **Trace:**

  > ChatEditingSession._acceptEdits awaits entry creation before applying incoming text edits. Its _createModifiedFileEntry creates an empty disk file through the bulk edit service, which reaches WorkingCopyFileService.doCreateFileOrFolder and announces creation to extensions before returning. gopls DidCreateFiles calls completion.NewFile, which can produce a start-of-file package insertion for that empty file; CreateFileTool independently supplies a start-of-file insertion through the chat stream. The related single-batch change at https://github.com/microsoft/vscode/commit/f6e4a3243e9761488236079d8ad26e652c95b6d7 removes per-line streaming but leaves this ordering intact. The trace establishes a duplicate-header interleaving, not all reported corruption signatures or every timing variant. Planning should establish deterministic event/edit ordering and the compatibility boundary before selecting a bounded remedy; do not suppress ordinary extension file events globally or overwrite unrelated user edits.

## Evidence

- **Current creation ordering:** In src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts, _acceptEdits first awaits _getOrCreateModifiedFileEntry and only then calls entry.acceptAgentEdits. _createModifiedFileEntry creates missing files with _bulkEditService.apply({ edits: [{ newResource: resource }] }), without contents. The initialContent parameter does not populate that creation edit.
- **Creation notification precedes agent content:** src/vs/workbench/services/workingCopy/common/workingCopyFileService.ts:346–385 creates the file and fires onDidRunWorkingCopyFileOperation before returning. src/vs/workbench/api/browser/mainThreadFileSystemEventService.ts:207 forwards the operation; src/vs/workbench/api/common/extHostFileSystemEventService.ts:321–331 emits onDidCreateFiles.
- **Competing insertions remain possible:** extensions/copilot/src/extension/tools/node/createFileTool.tsx:114–126 normally emits TextEdit.insert at position (0, 0) for a missing file. ChatEditingTextModelChangeService.acceptAgentEdits and _applyEdits apply the supplied edit to the current modified model. Separately, https://github.com/golang/tools/blob/master/gopls/internal/server/workspace.go calls completion.NewFile from DidCreateFiles, and https://github.com/golang/tools/blob/master/gopls/internal/golang/completion/newfile.go generates another start-of-file insertion when the observed file is empty and NewGoFileHeader is enabled. This establishes the duplicate-header interleaving from source; it does not establish every reported whitespace-corruption variant.
- **Related batching fix is not this fix:** https://github.com/microsoft/vscode/issues/301582 was closed citing https://github.com/microsoft/vscode/commit/f6e4a3243e9761488236079d8ad26e652c95b6d7. That commit replaces line-by-line generation with one TextEdit.insert; its diff does not change empty-file creation or creation-event ordering. Current main retains the insertion path, so the commit does not justify closing this report.
