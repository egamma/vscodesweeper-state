# Issue #249663 — MCP Auth Scope Selection

[https://github.com/microsoft/vscode/issues/249663](https://github.com/microsoft/vscode/issues/249663)

## Summary

Keep open: current authentication honors server-provided scope hints but does not provide user selection of a subset. The maintainer expressed interest in scope-selection UI, with human-readable scope presentation still unresolved; the related configuration request is newer and cannot replace this re-reviewed item.

## Change summary

Allow users to select a subset of OAuth scopes when authenticating to a remote MCP server, avoiding requests blocked by Conditional Access.

## Best solution

Provide an understandable, explicit scope-selection experience in MCP authentication while preserving automatic discovery for users who do not customize scopes. Settle how scope choices are described and how later server challenges interact with a user's selection, coordinating with https://github.com/microsoft/vscode/issues/316235.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostMcp.ts`, `src/vs/workbench/api/browser/mainThreadMcp.ts`, `src/vs/workbench/services/authentication/browser/authenticationMcpService.ts`, `src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts`, `src/vs/workbench/api/test/common/extHostMcp.test.ts`, `src/vs/workbench/api/test/browser/mainThreadMcp.test.ts`
- **Validation:** After the product decisions, use a controlled remote MCP server advertising two scopes to verify that selecting one sends only that scope in the authorization request; verify cancellation, unchanged default discovery, and the agreed behavior for subsequent insufficient-scope challenges. Add targeted coverage in extHostMcp.test.ts and mainThreadMcp.test.ts for the selected-scope contract and existing metadata precedence.
- **Behavior:**

  > Users connecting to an authenticated remote MCP server should be able to choose a subset of advertised OAuth scopes rather than always request the discovered set. The authorization request should reflect that choice, and users who do not customize scopes should retain the existing automatic behavior. Acceptance includes observing the requested scopes against a controlled server and checking cancellation and later scope challenges. The labels shown to users and the handling of a challenge for an excluded scope need maintainer agreement.
- **Trace:**

  > In src/vs/workbench/api/common/extHostMcp.ts, createAuthMetadata obtains scopes from WWW-Authenticate or protected-resource metadata, AuthMetadata.update replaces them on later challenges, and McpHTTPHandle._addAuthHeader forwards them to the main thread. In src/vs/workbench/api/browser/mainThreadMcp.ts, $getTokenFromServerMetadata computes resolvedScopes and passes them to _getSessionForProvider; no user subset selection occurs in this traced path. The OAuth schema in src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts has no scope override, and AuthenticationMcpService in src/vs/workbench/services/authentication/browser/authenticationMcpService.ts exposes session/account selection rather than scope selection. Preserve existing provider routing, account access controls, and automatic metadata behavior when customization is unused. The metadata workaround in https://github.com/microsoft/vscode/issues/249663#issuecomment-2991495251 is partial coverage, while https://github.com/microsoft/vscode/issues/316235 is related configuration work, not an older canonical. The uncertainty starts at the user-facing presentation and the contract between explicit selection and subsequent server challenges.
- **Open decisions:**
  - May the selector display raw OAuth scope identifiers when human-readable descriptions are unavailable, or must a description source be available before offering selection?
  - When a server subsequently requests a scope the user excluded, should VS Code prompt for explicit expansion or keep the selected subset and report that the operation requires additional authorization?
