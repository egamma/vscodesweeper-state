# Issue #285850 — Surface pinned editor state on hover when navigating files via Explorer

[https://github.com/microsoft/vscode/issues/285850](https://github.com/microsoft/vscode/issues/285850)

## Summary

Keep this accepted feature request open: Explorer hovers still do not expose editor pin state, and the request reached 20 upvotes and was promoted to Backlog. The issue already has the correct area label; a maintainer-guided design should settle how group-specific pinning is represented.

## Change summary

Show whether an Explorer file is pinned in an editor group through its hover, without adding persistent icons or changing the layout.

## Best solution

Extend the existing Explorer file hover with editor pin information while preserving its path and decoration details and keeping rows unchanged at rest. Agree on the meaning of the hint when the same resource is open in multiple editor groups, then implement and validate state updates.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Add focused Explorer rendering tests for the agreed pin-state semantics and updates after pin, unpin, and close. Manually open a file, invoke workbench.action.pinEditor, hover its Explorer row, then unpin and close it; verify the hint follows state, existing path/decorations remain, and row layout is unchanged. Repeat with the resource open in two groups under the agreed aggregation rule.
- **Behavior:**

  > An Explorer file hover should disclose its user-visible editor pin state without adding a persistent badge or changing the row layout. Existing path and decoration information must remain available. The hint must follow pin, unpin, and editor-close changes rather than remain stale. Acceptance includes unpinned and unopened files and the agreed behavior when a file is open in multiple editor groups.
- **Trace:**

  > FilesRenderer.renderStat in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts supplies resource-label options without consulting editor groups. The shared label renderer in src/vs/workbench/browser/labels.ts derives hover content from the path and registered decoration tooltips; ExplorerDecorationsProvider currently describes filesystem state only. The user-facing Pin command, workbench.action.pinEditor, calls group.stickEditor in src/vs/workbench/browser/parts/editor/editorCommands.ts, so the relevant state is isSticky rather than the separate internal isPinned flag. IEditorService.findEditors and IEditorGroup.isSticky expose the relevant resource/group relationship. Preserve existing Explorer layout, navigation, path information, and unrelated decoration behavior; do not broaden this into persistent pin badges or changes to editor pinning. No UI execution was performed in the read-only checkout. The remaining product uncertainty is how the hover aggregates pin state across editor groups.
- **Open decisions:**
  - When a resource is pinned in one editor group but unpinned in another, should Explorer report that it is pinned anywhere, report only the active group's state, or identify the groups in which it is pinned?
