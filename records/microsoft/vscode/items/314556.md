# Issue #314556 — Chat session persistence inlines image and tool binary data as base64, causing unbounded session growth

[https://github.com/microsoft/vscode/issues/314556](https://github.com/microsoft/vscode/issues/314556)

## Summary

The defect remains on current main: chat attachments and binary tool results are still encoded into the persisted session operation log, allowing image-heavy sessions to consume unbounded disk and memory. Maintainers have confirmed the problem and consolidated other reports into this issue, so it should remain open as the canonical bug.

## Change summary

Store chat image and binary payloads outside session JSONL while retaining durable references that can be restored, rendered, and reused in later requests.

## Best solution

Introduce session-scoped binary resource storage integrated with chat serialization and lifecycle management, preserving readable image data across reloads while keeping base64 out of JSONL. Deleting, clearing, trimming, or migrating sessions must consistently manage the associated resources, and existing inline sessions must remain readable.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/attachments/chatVariableEntries.ts`, `src/vs/workbench/contrib/chat/common/model/chatSessionOperationLog.ts`, `src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts`, `src/vs/workbench/contrib/chat/common/model/chatProgressTypes/chatToolInvocation.ts`, `src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts`, `src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts`, `src/vs/workbench/contrib/chat/test/common/model/chatSessionOperationLog.test.ts`, `src/vs/workbench/contrib/chat/test/common/model/chatSessionStore.test.ts`
- **Validation:** Run `scripts/test.sh --grep "ChatSession(OperationLog|Store)"` with tests proving persisted JSONL contains references rather than binary base64, restored attachments and tool outputs retain their original bytes, legacy inline sessions still load, and delete/clear/trim operations remove associated resources.
- **Behavior:**

  > Persisting a chat containing image attachments or binary tool output must not place the binary payload or its base64 representation in the session JSONL. Reloading the session must still restore readable bytes for rendering, extension participants, follow-up requests, and optional upload to model providers. Legacy sessions containing inline base64 must remain readable. Missing resources must be surfaced as unavailable rather than silently becoming empty data, and deleting, clearing, or trimming sessions must remove their associated resources.
- **Trace:**

  > Current request persistence flows through IChatRequestVariableEntry.toExport in src/vs/workbench/contrib/chat/common/attachments/chatVariableEntries.ts and the variableData/inputState schemas in src/vs/workbench/contrib/chat/common/model/chatSessionOperationLog.ts, which encode Uint8Array values as `$base64`. Tool serialization independently encodes binary output in IChatToolInvocation.toJSON and LanguageModelToolsService.toolResultToIO, while MCP conversion stores embedded blob values. ChatSessionStore.writeSession writes the resulting operation-log data directly to JSONL; internalDeleteSession, clearAllSessions, and trimEntries currently know only about session files and index entries. Existing decode paths establish the compatibility boundary: old inline payloads must continue to hydrate correctly. The implementation must not solve growth by dropping images, because durable screenshot restoration is intentional and https://github.com/microsoft/vscode/issues/295731 was completed by adding that persistence.
- **Open decisions:**
  - Should existing sessions with inline payloads be migrated into the resource store when loaded or rewritten, or remain inline while only newly persisted payloads use references?
  - When a referenced resource is missing, should a follow-up request omit that attachment and continue with a visible warning, or block sending until the user removes or replaces it?

## Evidence

- **request persistence path:** On current main, IChatRequestVariableEntry.toExport in src/vs/workbench/contrib/chat/common/attachments/chatVariableEntries.ts converts Uint8Array attachment values and element imageData to inline `$base64` strings. src/vs/workbench/contrib/chat/common/model/chatSessionOperationLog.ts invokes that conversion for both request variableData and draft inputState attachments.
- **tool persistence path:** IChatToolInvocation.toJSON in src/vs/workbench/contrib/chat/common/model/chatProgressTypes/chatToolInvocation.ts writes binary output as `base64Data`; LanguageModelToolsService.toolResultToIO in src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts writes data parts as base64-valued embeds; MCP output conversion in src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts likewise retains embedded blobs.
- **unbounded serialization:** ChatSessionStore.writeSession in src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts writes ChatSessionOperationLog output directly to the session JSONL. Its deletion and trimming paths manage only session JSON/JSONL files, and current main has no corresponding session-scoped binary resource store.
- **maintainer confirmation:** A maintainer confirmed encountering the problem and stated that images should not all remain in ChatModel memory: https://github.com/microsoft/vscode/issues/314556#issuecomment-4384764940.
- **canonical status:** Maintainers closed https://github.com/microsoft/vscode/issues/283352 and https://github.com/microsoft/vscode/issues/292795 as duplicates of this issue after identifying the same unbounded session growth and `Invalid string length` symptom. The older https://github.com/microsoft/vscode/issues/300013 is closed as not planned and therefore is not a valid duplicate target.
- **no current fix:** No open pull request references this issue, and source inspection shows all principal inline-base64 persistence paths described in the report remain present on current main.
