# Issue #339600 — Custom `LanguageModelChatProvider` with `imageInput: true` still blocks pasted images ("does not support images")

[https://github.com/microsoft/vscode/issues/339600](https://github.com/microsoft/vscode/issues/339600)

## Summary

Thanks for the extremely thorough report. The reporter isolated this to a specific BYOK `vscode.LanguageModelChatProvider` by A/B-testing against a built-in model in the same session, ruling out generic entitlement/sign-in causes, so this reads as a real, reproducible defect — but I traced the capability-mapping code on main and it looks correct in the places I checked, so the exact root cause isn't pinned down yet.

## Change summary

A custom LanguageModelChatProvider that declares capabilities.imageInput: true is shown with the vision badge in Manage Models, but pasted images are still blocked with a "does not support images" strikethrough when that model is selected.

## Best solution

Trace why `model.metadata.capabilities.vision` (set from `imageInput` in extHostLanguageModels.ts) ends up falsy at the moment chatAttachmentsContentPart.ts's currentModelDoesNotSupportImages() runs for this provider, even though the same `_modelCache` entry shows vision:true in Manage Models — likely a caching/refresh-timing discrepancy between the two read sites rather than a mapping bug.

- **Trace:**

  > `modelSupportsVision`/`currentModelDoesNotSupportImages` (chatAttachmentsContentPart.ts:126-128, chatAttachmentWidgets.ts:240-242) gate on `metadata.capabilities?.vision`, which extHostLanguageModels.ts:267 sets from the extension's declared `capabilities.imageInput` via `$provideLanguageModelChatInfo`, cached in `LanguageModelsService._modelCache` (languageModels.ts) and read identically by the Manage Models view (chatModelsViewModel.ts:353). I could not find a second code path or stale-copy mechanism by static reading, so the discrepancy likely requires live debugging (e.g. instrumenting `_modelCache` entries at paste time) to find — do not assume the mapping itself is wrong without confirming live, since the reporter already ruled out simple refresh/restart staleness.
- **Open decisions:**

## Evidence

- **capability mapping looks correct:** src/vs/workbench/api/common/extHostLanguageModels.ts:267 maps `m.capabilities.imageInput` to `metadata.capabilities.vision` for exactly this API (registerLanguageModelChatProvider / provideLanguageModelChatInformation).
- **shared cache, both UIs read same field:** Both the Manage Models view (chatModelsViewModel.ts:353 `modelEntry.metadata.capabilities.vision === true`) and the paste-gating check (chatAttachmentsContentPart.ts:128 `model.metadata.capabilities?.vision === false`) read `metadata.capabilities.vision` off the single `_modelCache` in languageModels.ts (LanguageModelsService) — no obvious separate/stale data source found by static reading.
- **reporter ruled out staleness:** Reporter tried the extension's own refresh-models command, a new chat tab, toggling the model in Manage Models, and a full Extension Development Host restart — none fixed it, which argues against a simple one-shot cache staleness explanation and keeps the real cause open.
- **related but distinct issues:** https://github.com/microsoft/vscode/issues/329560 (image data part missing from payload) was fixed by https://github.com/microsoft/vscode/pull/329646 and confirmed working later — this report explicitly persists on 1.140.0 well after that fix, and the symptom here (client-side strikethrough / UI gating) differs from that payload-construction bug, so it isn't the same root cause.
