# Issue #212425 — Open files in new window BUT reveal (existing window) if already open

[https://github.com/microsoft/vscode/issues/212425](https://github.com/microsoft/vscode/issues/212425)

## Summary

Keep this accepted, community-supported request open: current window selection still cannot combine new windows for newly opened files with revealing a file already open in another window. The existing settings do not cover that combination, and no verified older canonical owns the same behavior.

## Change summary

Allow externally opened files to reveal their existing window while opening files not already open in new windows.

## Best solution

Provide an opt-in window-level policy that finds an already-open file, including in folderless windows, and activates its editor instead of creating another window. Preserve existing opening modes and settle the new policy's interaction with explicit new-window requests before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/windows/electron-main/windowsMainService.ts`, `src/vs/platform/windows/electron-main/windowsFinder.ts`, `src/vs/workbench/browser/workbench.contribution.ts`, `src/vs/workbench/services/editor/common/editorGroupFinder.ts`, `src/vs/platform/windows/test/electron-main/windowsFinder.test.ts`
- **Validation:** On macOS, enable the agreed policy and open file A from Finder: a new window should appear. Focus an unrelated project window, then open A again: its original window and editor should activate without increasing the window count. Open previously unopened file B: it should receive a new window, not an editor in the project window. Repeat with A in a background tab of a folderless window and with Windows Explorer; verify existing opening modes and explicit CLI flags follow the agreed compatibility contract.
- **Behavior:**

  > Users need external file opening to distinguish a newly opened file from a file already open in another VS Code window. Under the new opt-in behavior, the first opening creates a new window, while a subsequent opening reveals the existing window and editor, including a background tab in a folderless window. Previously unopened files must not enter an unrelated project window. Existing modes remain unchanged unless the new behavior is enabled; explicit new-window precedence requires a product decision.
- **Trace:**

  > In src/vs/platform/windows/electron-main/windowsMainService.ts, shouldOpenNewWindow resolves the window policy before file routing, and the files-only path skips existing-window selection when that policy requests a new window. findWindowOnFile in src/vs/platform/windows/electron-main/windowsFinder.ts matches workspace containment rather than actual opened editors. workbench.editor.revealIfOpen is consumed by doFindGroup in src/vs/workbench/services/editor/common/editorGroupFinder.ts within the selected renderer, so it cannot solve independent-window routing. The configuration registrations are in src/vs/workbench/browser/workbench.contribution.ts, and the existing finder test suite is src/vs/platform/windows/test/electron-main/windowsFinder.test.ts. The trace stops at obtaining reliable editor membership across independent windows; the inspected routing does not provide that capability. Preserve unrelated folder routing, current opening modes, and editor-group behavior. The reporter's prototype is at https://github.com/jpilgrim/vscode/compare/main...jpilgrim:vscode:proto212425?diff=split&w=; no execution or prototype validation was performed.
- **Open decisions:**
  - Should already-open-file revelation be a separate window-level option or an additional window.openFilesInNewWindow mode?
  - When the new behavior is enabled, should an explicit --new-window request still create a second window for an already-open file?
