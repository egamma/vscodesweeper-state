# Issue #284747 — Failure with symlinks

[https://github.com/microsoft/vscode/issues/284747](https://github.com/microsoft/vscode/issues/284747)

## Summary

The symlink-path mismatch remains confirmed on a recent VS Code build, and no open canonical issue currently owns the Java-test failure. Keep this open as an upstream path-identity problem until ownership between Electron's folder-path handling and the Java tooling is established.

## Change summary

Java tests cannot be discovered or run when the opened workspace path contains a symbolic link.

## Best solution

Trace where the test item's canonical target URI diverges from the symlink-preserving workspace URI, then fix the owning component so Java test items resolve to their workspace without requiring users to open the physical path.

- **current core path:** On current main, `ExtHostWorkspaceImpl.getWorkspaceFolder` in `src/vs/workbench/api/common/extHostWorkspace.ts` performs a URI-prefix lookup through `_structure.findSubstr(uri)` and does not reconcile symlink and canonical filesystem identities.
- **consumer path:** Current `microsoft/vscode-java-test` code in `src/controller/testController.ts` passes the test item's URI directly to `workspace.getWorkspaceFolder`, so a canonical URI returned by Java tooling cannot match a workspace registered under its symlink path.
- **upstream attribution:** The earlier core investigation at https://github.com/microsoft/vscode/issues/74104#issuecomment-562050914 attributes platform-dependent symlink-path selection to the Electron-backed system dialog, but that closed issue did not resolve the Java test failure.
- **canonical search:** The exact Java-test tracking issue https://github.com/microsoft/vscode-java-test/issues/630 is closed, and searches of open microsoft/vscode issues for symlinked Java tests and symlinked workspaces found no open canonical with the same observable symptom.
