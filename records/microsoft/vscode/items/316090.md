# Issue #316090 — Multi process logging / perf tracing

[https://github.com/microsoft/vscode/issues/316090](https://github.com/microsoft/vscode/issues/316090)

## Summary

A real cross-process observability gap remains on current main. Agent Host now has substantial OTel support, but VS Code still lacks the proposed shared service spanning the renderer, extension host, Agent Host, and other process boundaries; the linked active proposal treats this issue as the core design track.

## Change summary

Add a unified logging and lightweight performance-tracing service that propagates correlation context across VS Code processes and asynchronous boundaries.

## Best solution

Design a core, opt-in OTel-compatible service with shared trace-context propagation, then land it incrementally across selected process boundaries and performance signals. Keep the existing process-specific logs and Electron content tracing working while the correlated path is introduced.

## Plan brief

- **Likely files:** `src/vs/platform/log/common/log.ts`, `src/vs/platform/log/common/logIpc.ts`, `src/vs/platform/agentHost/common/otel/agentHostOTelService.ts`, `src/vs/platform/agentHost/node/otel/agentHostOTelService.ts`, `src/vs/platform/otel/node/otlp/localOtlpReceiver.ts`, `src/vs/workbench/electron-browser/actions/developerActions.ts`
- **Validation:** End the first implementation slice with an integration test that sends correlated operations across at least one real VS Code IPC boundary and verifies that the exported spans retain one trace ID with correct parent/child relationships, while tracing-disabled behavior emits nothing.
- **Behavior:**

  > When opt-in tracing is enabled, a performance-sensitive operation crossing selected VS Code process or asynchronous boundaries remains identifiable as one correlated trace. Each participating component emits structured timing data without requiring raw user content, and existing process-specific logs remain available. With tracing disabled, normal behavior and performance-sensitive paths are unchanged. Acceptance requires an exported trace whose spans preserve the expected parent/child relationship across a real IPC boundary.
- **Trace:**

  > Current logging is centered on `ILogService`/`ILoggerService`; `LoggerChannelClient` and `LoggerChannel` in `src/vs/platform/log/common/logIpc.ts` exchange logger state and message batches without correlation context. Electron content tracing in `src/vs/workbench/electron-browser/actions/developerActions.ts` records Chromium categories but is not a structured service propagated through VS Code calls. OTel primitives and storage exist under `src/vs/platform/otel`, while `IAgentHostOTelService` and `AgentHostOTelService` provide an Agent Host-only implementation with W3C contexts and SDK exporters. The uncertainty begins at the shared service contract and first instrumentation slice: the linked proposal at https://github.com/microsoft/vscode-internalbacklog/issues/7829 names commands, file watching, extension lifecycle, and extension-host RPC, but no repository-wide contract or boundary has landed. Preserve existing logging channels, content tracing, telemetry consent behavior, and Agent Host exporters while designing the shared path.
- **Open decisions:**
  - Should the first core contract cover traces only, or also attach trace context and structured attributes to ordinary log records?
  - Which process boundary and performance signal constitute the first supported slice: command execution, extension-host RPC, file watching, or extension lifecycle?
  - What user-visible enablement, export, retention, and content-redaction contract should apply outside the existing Agent Host OTel settings?
  - Is correlation context propagated only through internal IPC contracts, or also exposed through an extension-facing API?

## Evidence

- **remaining source gap:** Current main has no general workbench/platform `IOTelService`; `src/vs/platform/agentHost/common/otel/agentHostOTelService.ts` explicitly defines an Agent Host-specific service and namespace (`vscode.agent-host`) for provider SDK telemetry and session correlation.
- **partial implementation:** `src/vs/platform/agentHost/node/otel/agentHostOTelService.ts` and `src/vs/platform/otel/node/otlp/localOtlpReceiver.ts` provide trace collection, storage, forwarding, and W3C context for Agent Host, but their consumers are confined to Agent Host providers rather than renderer, extension-host, command, file-watcher, or general RPC paths.
- **existing tracing is not equivalent:** `src/vs/workbench/electron-browser/actions/developerActions.ts` starts Electron content tracing using Chromium categories; it does not provide structured trace/span propagation through VS Code services and asynchronous IPC boundaries.
- **logging remains channel-oriented:** `src/vs/platform/log/common/logIpc.ts` transports logger registration, levels, visibility, and message batches over IPC without trace or span correlation metadata.
- **active design work:** The open proposal at https://github.com/microsoft/vscode-internalbacklog/issues/7829 explicitly cites https://github.com/microsoft/vscode/issues/316090 and defines a cross-process OTel stream spanning renderer, extension host, and Agent Host, confirming that this issue remains active rather than completed.
- **related issue is narrower:** https://github.com/microsoft/vscode/issues/293225 is open but focuses on Copilot Agent observability. It does not own this issue's broader VS Code process-wide logging and performance-tracing scope, so it is not a valid duplicate canonical.
