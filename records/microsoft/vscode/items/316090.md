# Issue #316090 — Multi process logging / perf tracing

[https://github.com/microsoft/vscode/issues/316090](https://github.com/microsoft/vscode/issues/316090)

## Summary

A real cross-process observability gap remains: current logging can cross IPC boundaries, and current OTel infrastructure covers Agent Host scenarios, but neither provides a general correlated timeline across the renderer, extension host, main process, and Agent Host. The request should remain open for architectural planning.

## Change summary

Provide unified structured logging and lightweight performance tracing that correlates operations across VS Code processes and asynchronous boundaries.

## Best solution

Establish a process-neutral correlation and tracing contract that existing log producers and performance instrumentation can participate in, with explicit scope, privacy, configuration, and overhead guarantees. Reuse the current logging IPC and platform OTel primitives rather than creating an Agent Host-specific parallel system.

## Plan brief

- **Likely files:** `src/vs/platform/log/common/log.ts`, `src/vs/platform/log/common/logIpc.ts`, `src/vs/platform/log/electron-main/loggerService.ts`, `src/vs/platform/otel/common/spanData.ts`, `src/vs/platform/otel/node/otlp/localOtlpReceiver.ts`
- **Validation:** End the plan with an automated multi-process fixture that starts a correlated operation in one process, continues it through at least one IPC boundary, and asserts that the exported events share one trace ID with correct parentage and bounded disabled-mode overhead.
- **Behavior:**

  > A diagnostic operation spanning VS Code processes should be inspectable as one ordered timeline rather than unrelated per-process logs. Correlation must survive asynchronous and IPC boundaries, while ordinary logs remain useful when tracing is disabled. Collection and export must have explicit privacy controls and must not impose material overhead in the default configuration. Acceptance should cover a renderer-to-main or extension-host boundary and an Agent Host boundary.
- **Trace:**

  > The shared logging contracts are ILogger and ILogService in src/vs/platform/log/common/log.ts. LoggerChannelClient and LoggerChannel in src/vs/platform/log/common/logIpc.ts transport logger operations but no correlation context, and LoggerMainService in src/vs/platform/log/electron-main/loggerService.ts organizes resources by window rather than trace. Existing reusable OTel primitives include completed span data in src/vs/platform/otel/common/spanData.ts and OTLP ingestion in src/vs/platform/otel/node/otlp/localOtlpReceiver.ts; AgentHostOTelService currently composes them for Agent Host-specific diagnostics. The boundary is broader than https://github.com/microsoft/vscode/issues/293225, which focuses on agent trajectories, so planning must preserve non-agent logging and avoid coupling the platform contract to Agent Host concepts. Uncertainty starts at the public correlation model, enabled process set, capture policy, and default overhead budget.
- **Open decisions:**
  - Which process boundaries are required in the first supported contract: renderer/main only, renderer/main/extension host, or all of those plus Agent Host and remote processes?
  - Should correlation be opt-in tracing alongside unchanged text logs, or should structured correlation identifiers become part of the general logging contract even when span export is disabled?
  - Which event attributes and payload classes may cross process boundaries or be exported, and what content-redaction behavior is required by default?
  - What disabled-mode and enabled-mode performance budgets must the service meet?

## Evidence

- **current logging boundary:** src/vs/platform/log/common/log.ts defines process-local ILogger/ILogService abstractions, while src/vs/platform/log/common/logIpc.ts forwards logger creation and messages over IPC; these APIs do not carry trace IDs, span IDs, or parent context.
- **existing OTel scope:** src/vs/platform/agentHost/node/otel/agentHostOTelService.ts and src/vs/platform/otel/node/otlp/localOtlpReceiver.ts provide span collection, storage, and forwarding for Agent Host diagnostics, but they do not form a general tracing service used by renderer, extension-host, and main-process operations.
- **related work:** https://github.com/microsoft/vscode/issues/293225 is an older open meta issue for Agent observability through OpenTelemetry. It is related but narrower than this issue's VS Code-wide multi-process logging and performance-tracing scope, so it does not satisfy the stronger duplicate bar for this re-review.
- **project direction:** The open proposal https://github.com/microsoft/vscode-internalbacklog/issues/7829 cross-references this issue, indicating active architectural consideration rather than evidence that the work is complete.
- **canonical search:** A repository issue search for multi-process logging and tracing found no older open microsoft/vscode issue covering the same general VS Code-wide observable behavior.
