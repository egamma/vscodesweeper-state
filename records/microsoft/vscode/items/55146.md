# Issue #55146 — "Quick Open" open all/multi-select files

[https://github.com/microsoft/vscode/issues/55146](https://github.com/microsoft/vscode/issues/55146)

## Summary

Keep this as the canonical request for bulk opening and multi-selection in Quick Open. Current source still accepts one result at a time, and maintainers have consolidated subsequent reports here.

## Change summary

Allow opening all matching Quick Open files or a selected subset without accepting each file individually.

## Best solution

Provide an integrated bulk-opening workflow in the file Quick Open provider, preserving its existing matching and single-file behavior. Settle the selection gestures and bulk-open scope before implementation rather than replacing Quick Open with a separate search dialog.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts`, `src/vs/platform/quickinput/browser/pickerQuickAccess.ts`, `src/vs/platform/quickinput/browser/quickInput.ts`, `src/vs/workbench/browser/actions/quickAccessActions.ts`, `src/vs/workbench/test/browser/quickAccess.test.ts`
- **Validation:** The plan should establish picker tests covering acceptance of multiple file results and preservation of single-result behavior. Manually verify Ctrl+P with several matching files: open a selected subset and all eligible displayed file results without repeated acceptance, while ordinary Enter and right-arrow behavior remain unchanged.
- **Behavior:**

  > Users should be able to open multiple files matching the existing Ctrl+P query without accepting each result separately. The requested workflow includes opening all matching file results and choosing a subset. Existing Quick Open matching must remain the source of those results, rather than introducing an unrelated search dialog. Acceptance should demonstrate bulk opening and subset selection while preserving ordinary single-file opening and background acceptance.
- **Trace:**

  > AnythingQuickAccessProvider in src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts enables background acceptance and supplies per-item openAnything callbacks. PickerQuickAccessProvider.provide in src/vs/platform/quickinput/browser/pickerQuickAccess.ts accepts only the first selected item; QuickPick in src/vs/platform/quickinput/browser/quickInput.ts has generic multi-selection support but defaults to single selection. Inspected command and configuration registrations do not expose the requested bulk file workflow. This is a missing capability, not a demonstrated defect in existing acceptance behavior. Shared picker changes must preserve other providers and existing single-file/background opening semantics. https://github.com/microsoft/vscode/pull/143460 is a closed, unmerged UX exploration; subsequent reports were consolidated into https://github.com/microsoft/vscode/issues/55146. The remaining uncertainty is the user-facing selection model and what constitutes the bulk-open set, especially when Quick Open combines file, history, and optional symbol results.
- **Open decisions:**
  - Should subset selection use direct Ctrl/Shift selection gestures, an explicit multi-select mode with checkboxes, or both?
  - Should Open All operate on the currently displayed eligible file results or every matching workspace file, and what confirmation or limit should apply to a large result set?

## Evidence

QuickPick defaults canSelectMany to false in src/vs/platform/quickinput/browser/quickInput.ts:537. This supports the reported right-arrow workaround, not bulk opening.
