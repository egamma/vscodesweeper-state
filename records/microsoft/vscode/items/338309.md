# Issue #338309 — BYOK Custom Endpoint: Mistral-hosted GLM 5.3 fails with `TypeError: e.replace is not a function` when response content is an array

[https://github.com/microsoft/vscode/issues/338309](https://github.com/microsoft/vscode/issues/338309)

## Summary

Traced a real defect in the BYOK chat-completions streaming path: the code assumes `delta.content` is always a string and crashes when a vendor (here GLM 5.3 hosted by Mistral) returns an array of content blocks — this matches the reported error and stack trace closely, though the fuller fix (how to treat 'thinking' blocks) needs a design call.

## Change summary

BYOK Custom Endpoint chat-completions responses whose `message`/`delta` content is a structured array (text + thinking blocks), rather than a plain string, crash the request instead of being parsed.

## Best solution

Fix `APIJsonDataStreaming.append`/`_removeCR` (and the shared SSE parsing in extensions/copilot/src/platform/networking/node/stream.ts, used from chatEndpoint.ts) to normalize non-string `delta.content` (arrays of `{type, text}` blocks) into plain text before calling `.replace()`, and decide whether 'thinking' blocks route through the existing reasoning/thinking delta channel or are dropped for this shape.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/networking/node/stream.ts`, `extensions/copilot/src/platform/networking/common/openai.ts`, `extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts`

- **Behavior:**

  > When a BYOK Custom Endpoint chat-completions model returns `message`/`delta.content` as an array of content blocks (e.g. `{type:'thinking',...}` and `{type:'text',...}`) instead of a plain string, Copilot Chat should extract and stream the text content without throwing, rather than failing the whole request with a generic 'firewall/network' error. Existing behavior for plain-string content responses must be unchanged. Acceptance: a new stream.ts test with an array-shaped delta/content passes without exception and yields the text block(s) as the response.
- **Trace:**

  > The parsing path is extensions/copilot/src/platform/networking/node/stream.ts: `SSEProcessor` (constructed in extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts:91) feeds each SSE chunk's `choice` into `APIJsonDataStreaming.append()`, which calls the private `_removeCR(text: string)` — `text.replace(/\r$/g, '')` — directly on `choice.delta.content`, typed `string | null` in the local `ChoiceJSON`/`ExtendedChoiceJSON` interfaces (lines ~166-207), with no `Array.isArray` guard. Outgoing message construction already handles array content (openai.ts `getCAPITextPart`, chatStream.ts lines 33-35) but nothing on the incoming/streaming side does. Do not change the outgoing-message array handling, which is unrelated and already correct; the fix is scoped to the incoming SSE/content parsing. Where the uncertainty starts: how 'thinking'-typed blocks should be surfaced (existing `RawThinkingDelta`/`extractThinkingDeltaFromChoice` machinery targets a different reasoning-model response shape, not this one).
- **Open decisions:**
  - Should content blocks with `type: 'thinking'` from this response shape be routed through the existing thinking/reasoning delta channel (RawThinkingDelta/extractThinkingDeltaFromChoice) so they render as reasoning UI, or simply ignored/concatenated as plain text for chat-completions BYOK endpoints?
  - When a response's content shape is genuinely unsupported/unrecognized, should the request fail with a specific, actionable error message (per the reporter's ask) rather than best-effort text extraction — and if so, what should that message say?

## Evidence

- **root cause candidate:** extensions/copilot/src/platform/networking/node/stream.ts: `APIJsonDataStreaming.append()` calls `_removeCR(choice.delta.content)` which does `text.replace(/\r$/g, '')` on line 53 — `ChoiceJSON.delta` is typed `{ content: string | null }` (line 177), but per the reporter's own curl test against `api.mistral.ai/v1/chat/completions` with `zai-glm-5-3`, `message.content` comes back as an array of `{type:'thinking'|'text', ...}` blocks, not a string — an array passed to `.replace()` throws exactly `TypeError: e.replace is not a function`.
- **stack trace match:** Reported stack shows `xH._provideLanguageModelResponse`; `extensions/copilot/src/extension/conversation/vscode-node/languageModelAccess.ts` defines `_provideLanguageModelResponse` (line 705), which calls into `makeChatRequest`/`ChatEndpoint`, whose `chatEndpoint.ts` (line 91) constructs the `SSEProcessor` from `stream.ts` that owns the crashing code.
- **no existing array-content handling on this path:** Unlike outgoing message construction (`extensions/copilot/src/platform/networking/common/openai.ts` `getCAPITextPart`, `chatStream.ts` lines 33-35) which already handles `Array.isArray(content)` for prompts, the incoming streaming-response parser in stream.ts has no equivalent guard for `delta.content` or `message.content` being an array.
- **existing partial infra:** The codebase already has a `RawThinkingDelta`/`extractThinkingDeltaFromChoice` mechanism (imported in stream.ts) for reasoning-model deltas, but it targets a different response shape than Mistral/GLM's array-of-content-blocks format, so it's unclear whether 'thinking' blocks here should route through that channel.
