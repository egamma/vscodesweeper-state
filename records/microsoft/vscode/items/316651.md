# Issue #316651 — Machine scoped configuration properties do not respect the correct scope

[https://github.com/microsoft/vscode/issues/316651](https://github.com/microsoft/vscode/issues/316651)

## Summary

The supplied extension and linked discussion demonstrate a machine-scoped local value leaking into a remote extension host when no remote value exists. Current configuration code and tests say that local machine values must be excluded in remote windows, so this remains a configuration/remote correctness bug that should be routed accordingly.

## Change summary

Machine-scoped extension settings set locally incorrectly become the effective value for a remote extension when the remote machine has no value.

## Best solution

Ensure the remote-window configuration lifecycle filters machine-scoped local user values after remote extension configuration contributions are registered, before configuration data reaches the extension host. Add a regression covering an extension-contributed machine setting that is registered during remote startup with only a local value present.

## Plan brief

- **Likely files:** `src/vs/workbench/services/configuration/browser/configurationService.ts`, `src/vs/workbench/services/configuration/browser/configuration.ts`, `src/vs/platform/configuration/common/configurationModels.ts`, `src/vs/workbench/services/configuration/test/browser/configurationService.test.ts`
- **Validation:** Add a configuration service regression that registers a machine-scoped setting after remote-window initialization with a local user value and no remote value, then run `scripts/test.sh --grep "machine settings in local user settings"`; the effective value and `userLocalValue` must remain unset while a subsequently configured remote value becomes effective.
- **Behavior:**

  > In a remote window, an extension-contributed machine-scoped setting must resolve only from the remote machine's user settings. A value configured in local user settings must not appear as the effective value or as the remote extension's global value when the remote setting is absent. Setting the value in remote user settings must make that remote value effective, while non-machine settings retain their existing local/remote inheritance behavior.
- **Trace:**

  > The reporter demonstrated the leak with a sample workspace extension and inspection output in https://github.com/microsoft/vscode-discussions/discussions/3067#discussioncomment-16932311. `getLocalUserConfigurationScopes` in src/vs/workbench/services/configuration/browser/configurationService.ts selects `LOCAL_MACHINE_SCOPES` for remote windows, and that list intentionally excludes `ConfigurationScope.MACHINE`; remote parsing includes machine scope through `REMOTE_MACHINE_SCOPES`. Configuration merging in src/vs/platform/configuration/common/configurationModels.ts makes a surviving local user value the fallback when the remote model is empty. Existing tests in src/vs/workbench/services/configuration/test/browser/configurationService.test.ts cover static and late default registration but not the reporter's full remote-extension installation/registration lifecycle, which is where the trace remains incomplete. Preserve inheritance for window/resource settings and remote precedence; the scope is only machine-scoped local-value leakage.

## Evidence

- **confirmed symptom:** The linked discussion https://github.com/microsoft/vscode-discussions/discussions/3067#discussioncomment-16932311 includes a remote-window inspection showing the local path in both `globalLocalValue` and effective `globalValue`; after setting a remote value, `globalRemoteValue` correctly takes precedence.
- **reproduction fixture:** https://github.com/aks273/vscode-configuration-scoping-issue contributes `configScopingIssue.machineString` with `scope: "machine"`, providing the sample extension requested by the maintainer.
- **expected source behavior:** src/vs/workbench/services/configuration/common/configuration.ts defines `LOCAL_MACHINE_SCOPES` without `ConfigurationScope.MACHINE`, while `REMOTE_MACHINE_SCOPES` includes it. src/vs/workbench/services/configuration/test/browser/configurationService.test.ts already asserts in `machine settings in local user settings does not override defaults` that a local machine value must not become effective in a remote window.
- **fallback path:** src/vs/platform/configuration/common/configurationModels.ts merges local user configuration with remote user configuration, with the remote model taking precedence. If lifecycle filtering leaves the local machine value in the local model, that merge explains the reported fallback when the remote model has no value.
- **canonical search:** https://github.com/microsoft/vscode/issues/177502 is closed and concerns proxy-setting selection, while https://github.com/microsoft/vscode/issues/182696 is a closed API feature request for separately targeting local and remote settings; neither is an open canonical reporting this same observable leak.
