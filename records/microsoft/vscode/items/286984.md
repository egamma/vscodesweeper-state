# Issue #286984 — Editor GPU: Optimize viewport scroll bar width calculation

[https://github.com/microsoft/vscode/issues/286984](https://github.com/microsoft/vscode/issues/286984)

## Summary

The viewport-width optimization remains necessary: current main still scans GPU-renderable lines and their characters on every text render. Keep this accepted Backlog debt open; the linked merged PR introduced that work rather than optimizing it.

## Change summary

Reduce repeated horizontal-scrollbar width calculation work in the GPU editor renderer, particularly for large viewports.

## Best solution

Make horizontal-scrollbar width maintenance avoid repeatedly measuring unchanged visible text in ViewLinesGpu, while preserving existing sizing and invalidation behavior. Establish a repeatable work-count or performance regression check before implementation.

## Plan brief

- **Likely files:** `src/vs/editor/browser/viewParts/viewLinesGpu/viewLinesGpu.ts`, `src/vs/editor/browser/gpu/renderStrategy/fullFileRenderStrategy.ts`
- **Validation:** Establish a repeatable check with GPU rendering enabled and a large viewport: render unchanged visible text repeatedly and count width-calculation or character-measurement work, demonstrating that it no longer repeats in proportion to all visible text. Verify horizontal scroll extent remains correct when scrolling to wider lines, editing text, inserting/deleting lines, and changing font, tab size, or display scale. No existing executable check for this contract was identified or run.
- **Behavior:**

  > With GPU editor rendering enabled, repeated renders of unchanged visible text should not repeatedly perform full per-character width measurement across the viewport. Horizontal scrolling must retain the same reachable text and sizing behavior. Acceptance must demonstrate reduced repeated calculation work for a large viewport and unchanged sizing after scrolling, edits, and width-affecting configuration changes.
- **Trace:**

  > ViewLinesGpu._renderText in src/vs/editor/browser/viewParts/viewLinesGpu/viewLinesGpu.ts always calls _updateMaxLineWidth after GPU submission. That method scans visible eligible lines, and _computeLineWidth scans their characters before comparing against the stored maximum. FullFileRenderStrategy.update in src/vs/editor/browser/gpu/renderStrategy/fullFileRenderStrategy.ts has an upToDateLines optimization, but it does not govern this separate width pass. https://github.com/microsoft/vscode/pull/286977 introduced the pass to correct horizontal scroll sizing; preserve that correction and existing GPU eligibility, DOM fallback, tab, and text-metric semantics. The remaining uncertainty is how to exercise repeated render-time width work deterministically without requiring an untested GPU fixture; existing inspected GPU tests cover other primitives, not this path. Avoid broad renderer refactoring or unrelated sizing fixes.
