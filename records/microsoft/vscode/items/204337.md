# Issue #204337 — Quick switch window don't allow multiple key presses to go to next window

[https://github.com/microsoft/vscode/issues/204337](https://github.com/microsoft/vscode/issues/204337)

## Summary

Keep open: the window picker still lacks automatic repeated-key cycling, and a maintainer explicitly endorsed making the editor pickers' navigation behavior generic. Existing navigation commands provide a configurable workaround, not the requested behavior from assigning a single shortcut.

## Change summary

Allow repeated presses of the Quick Switch Window shortcut to advance the selection while its modifier remains held.

## Best solution

Make repeated-shortcut navigation work consistently for Quick Switch Window without requiring a separate navigation binding, while preserving selection acceptance on modifier release. Assess the shared quick-input and keybinding behavior with the maintainer before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/electron-browser/actions/windowActions.ts`, `src/vs/workbench/browser/parts/editor/editor.contribution.ts`, `src/vs/workbench/browser/actions/quickAccessActions.ts`, `src/vs/platform/quickinput/browser/quickInput.ts`, `src/vs/platform/quickinput/browser/quickInputController.ts`
- **Validation:** On macOS, open at least three windows and bind only workbench.action.quickSwitchWindow to alt+tab. Hold Alt and repeatedly press Tab: the active selection must advance through the windows, including back to the current one; releasing Alt must focus the selected window. Confirm existing editor-picker cycling, arrow-key navigation, and Escape cancellation remain unchanged.
- **Behavior:**

  > Assigning a modifier-based shortcut to Quick Switch Window should be sufficient to cycle through its entries by repeatedly pressing the shortcut's non-modifier key. The picker remains open while the modifier is held and focuses the selected window when it is released. With at least three windows, repeated presses must advance beyond the initially selected next window and allow returning to the current window. Existing editor-picker navigation, arrow navigation, and cancellation must remain unchanged.
- **Trace:**

  > BaseSwitchWindow.run in src/vs/workbench/electron-browser/actions/windowActions.ts opens an inWindowsPicker quick pick and supplies the initiating command's keybindings as quickNavigate configuration. QuickPick.registerQuickNavigation in src/vs/platform/quickinput/browser/quickInput.ts uses that configuration to accept on modifier release, but does not implement repeated-key advancement. Editor cycling is separately registered under editorPickerContext in src/vs/workbench/browser/parts/editor/editor.contribution.ts. Generic navigation commands in src/vs/workbench/browser/actions/quickAccessActions.ts already reach QuickInputController.navigate, establishing a navigation primitive but not automatic reuse of the opening shortcut. The maintainer endorsed generic behavior at https://github.com/microsoft/vscode/issues/204337#issuecomment-1949382172. The remaining investigation is how shortcut dispatch can provide that behavior without interfering with other quick-input consumers; those consumers have not been fully enumerated. Window ordering, auxiliary-window grouping, and close buttons are outside this request; https://github.com/microsoft/vscode/issues/211983 tracks a separate ordering request.
