# Issue #338008 — Workbench.colorCustomizations setting not working

[https://github.com/microsoft/vscode/issues/338008](https://github.com/microsoft/vscode/issues/338008)

## Summary

Real regression, confirmed in source: `workbench.experimental.modernUI` was flipped to default `true` in this release (src/vs/workbench/browser/workbench.contribution.ts:836), and its bundled tabs.css unconditionally forces `--tab-border-top-color: transparent !important` and `display: none !important` on `.tab-border-bottom-container` for the plain single-active-tab case, so `tab.activeBorder`/`tab.activeBorderTop` customizations stop rendering even for users who never opted into Modern UI.

## Change summary

After upgrading, `tab.activeBorder`/`tab.activeBorderTop` (and other legacy tab color) customizations in `workbench.colorCustomizations` no longer take visible effect.

## Best solution

Make the Modern UI tabs module (src/vs/workbench/contrib/modernUI/browser/media/tabs.css) and its color derivation (src/vs/workbench/services/themes/browser/modernTabColorCustomizations.ts) fall back to the legacy resolved `tab.activeBorder`/`tab.activeBorderTop` color instead of forcing `transparent`/`display:none` — this is already the documented intent ("Explicit tab fill and label color customizations from tab.*, modernTab.*, and modernEditorTab.* override those defaults for connected and pill tabs alike", per the Modern UI README), so this is a genuine implementation gap rather than as-designed.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/modernUI/browser/media/tabs.css`, `src/vs/workbench/services/themes/browser/modernTabColorCustomizations.ts`, `src/vs/workbench/contrib/modernUI/browser/media/connectedEditorTabs.css`
- **Validation:** A themed CSS/unit test (extending src/vs/workbench/contrib/modernUI/test/browser/modernUI.contribution.test.ts, which already imports TAB_ACTIVE_BORDER/TAB_ACTIVE_BORDER_TOP and generateColorThemeCSS) asserting that when a theme/color-customization sets tab.activeBorder or tab.activeBorderTop, the generated Modern UI CSS variables resolve to that color instead of being forced transparent/hidden for a plain active (non-selected, non-multi-selected) tab.
- **Behavior:**

  > When a user sets `tab.activeBorder` and/or `tab.activeBorderTop` in `workbench.colorCustomizations` (or a theme defines them), the active editor tab should visibly show that border color, matching the documented Modern UI behavior that legacy tab.* customizations override the module's defaults for both connected and pill tab styles. Currently, with Modern UI on (now the default), the border is invisible for the ordinary single active tab. Acceptance: with `workbench.experimental.modernUI` on (either tab style) and a `tab.activeBorder`/`tab.activeBorderTop` customization set, the active tab shows the customized border; without a customization, the existing Modern UI default appearance is unchanged.
- **Trace:**

  > Root cause is in src/vs/workbench/contrib/modernUI/browser/media/tabs.css: line 78 unconditionally sets `--tab-border-top-color: transparent !important` for every `.tab` under `.modern-ui-tabs`, and only two narrow selectors (lines 337-347, matching `.tab.selected:not(.active)` or `.tab.active.multi-selected`) restore it from `--vscode-tab-activeBorderTop`/`--vscode-tab-selectedBorderTop` — the plain single active tab case is never restored. Separately, lines 279-281 unconditionally hide `.tab-border-bottom-container` (the element multiEditorTabsControl.ts's `doRedrawTabActive`, lines 1886-1902, uses to paint `tab.activeBorder` via `--tab-border-bottom-color`) for all tabs under `.modern-ui-tabs`, with no legacy-color exception. The module's own README documents that `tab.*` customizations should override Modern UI defaults for connected and pill styles alike, so the desired end state is well defined; what needs a maintainer's call is exactly how/where in this large, state-heavy stylesheet (dirty/sticky/hc/wrapping variants, plus the separate `connectedEditorTabs.css`) to gate the transparent/hidden defaults behind "no legacy customization present", and whether the related `modernEditorTab.*`-in-connected-mode report from the second commenter shares the same fix path or needs separate handling. Do not change the intended pill/connected visual redesign for users who have not customized these colors.
- **Open decisions:**
  - Should the fix detect an explicit legacy `tab.activeBorder`/`tab.activeBorderTop` customization and fall back to classic border rendering only for that case, or should Modern UI's connected/pill styles always render a (possibly reshaped) border derived from these colors whenever they resolve to non-null?
  - Does the second reported symptom (modernEditorTab.* colors only applying in 'pill' style, not the default 'connected' style) share the same fix, or is it a distinct gap in connectedEditorTabs.css/modernTabColorCustomizations.ts that should be tracked and fixed together?

## Evidence

- **default flip:** src/vs/workbench/browser/workbench.contribution.ts:834-839 registers `workbench.experimental.modernUI` with `'default': true` and `experiment: { mode: 'auto' }`, so this release turns Modern UI (and its tabs module) on for users by default without any opt-in setting change.
- **top-border override:** src/vs/workbench/contrib/modernUI/browser/media/tabs.css:78 sets `--tab-border-top-color: transparent !important;` on every `.tab` under `.modern-ui-tabs`. The only rules that later restore the color from `--vscode-tab-activeBorderTop` (lines 337-347) match `.tab.selected:not(.active)` or `.tab.active.multi-selected` — the ordinary single active tab (the reporter's case) is never re-matched, so `tab.activeBorderTop` is unrenderable.
- **bottom-border hidden:** src/vs/workbench/contrib/modernUI/browser/media/tabs.css:279-281 unconditionally sets `.tab-border-bottom-container { display: none !important; }` for all tabs under `.modern-ui-tabs`, which is the element multiEditorTabsControl.ts uses to paint `tab.activeBorder` (see `doRedrawTabActive` in src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts:1886-1902 setting `--tab-border-bottom-color` and toggling `tab-border-bottom`).
- **documented intent contradicted:** src/vs/workbench/contrib/modernUI/README.md states explicit `tab.*`/`modernTab.*`/`modernEditorTab.*` customizations should override Modern UI defaults for both connected and pill tab styles — the CSS above does not honor that for the plain active-tab border case.
- **second report:** Comment from nannerpusser corroborates a related symptom: `modernEditorTab.*` customizations only work in 'pill' tab style, not the new default 'connected' style, on the same 1.139.1 build.
