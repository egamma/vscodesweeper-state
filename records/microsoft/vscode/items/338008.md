# Issue #338008 — Workbench.colorCustomizations setting not working

[https://github.com/microsoft/vscode/issues/338008](https://github.com/microsoft/vscode/issues/338008)

## Summary

Real, community-corroborated regression tied to the Modern UI tab renderer becoming default in 1.139 — I found a plausible root cause in the CSS but couldn't fully confirm the exact failure path from source alone, so this stays open rather than closing or citing an unverified fix.

## Change summary

workbench.colorCustomizations entries for tab.activeBorder / tab.activeBorderTop (and related modernEditorTab tokens) stop visibly affecting the active tab underline after upgrading to 1.139, where the Modern UI tab style is active.

## Best solution

Confirm (via a running build) why the active-tab border customization is invisible in the Modern UI 'default look': src/vs/workbench/contrib/modernUI/browser/media/tabs.css:279-281 forces `display: none !important` on the classic `.tab-border-bottom-container` element that multiEditorTabsControl.ts populates from TAB_ACTIVE_BORDER/TAB_ACTIVE_BORDER_TOP, while the intended replacement (a border on `.tab-fill`, lines 311-316, driven by `--modern-ui-editor-tab-active-border(-top)` from modernTabColorCustomizations.ts) may not be rendering with sufficient visibility or may not apply in the exact 'default look' (non-pill) configuration the reporters describe.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/modernUI/browser/media/tabs.css`, `src/vs/workbench/services/themes/browser/modernTabColorCustomizations.ts`, `src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts`
- **Validation:** Launch a dev build with workbench.colorCustomizations setting tab.activeBorder/tab.activeBorderTop to a saturated, distinct color, confirm the active tab in the default (non-pill) Modern UI tab style visibly shows that color as a border/underline; if it doesn't, adjust CSS/JS so the customization is honored with adequate visual contrast.
- **Behavior:**

  > When a user sets workbench.colorCustomizations for tab.activeBorder and/or tab.activeBorderTop, the active editor tab should show a visibly colored border/underline matching that customization, in both the classic tabs UI and the Modern UI tab style (including its default, non-pill look). Acceptance: with a saturated custom color set, the active tab border is clearly visible in the default Modern UI look, not just in 'pill mode'.
- **Trace:**

  > The classic renderer (multiEditorTabsControl.ts lines 1034/1886-1904) writes the resolved TAB_ACTIVE_BORDER/TAB_ACTIVE_BORDER_TOP color onto a `.tab-border-bottom-container` element, but tabs.css (lines 279-281) hides that element with `display: none !important` whenever Modern UI tabs are active. The apparent replacement is a border on `.tab-fill` (tabs.css lines 311-316) fed by `--modern-ui-editor-tab-active-border(-top)`, which modernTabColorCustomizations.ts populates from the same legacy color IDs when the user has customized them (see resolveLegacyTabColor, lines 19-27). This should theoretically carry the customization through, but reporters describe the underline as fully absent in the Modern UI default look — I could not execute the app to see whether the CSS variable is actually empty, overridden elsewhere, or just rendered too subtly (e.g. clipped by `.tab-fill` sizing/`overflow`) to be noticed. Do not change the pill-mode rendering (`.modern-ui-editor-tab-group`/`.modern-ui-editor-tab` rules), which per comments already honors related tokens correctly. Related: https://github.com/microsoft/vscode/issues/326445 reports a similarly-titled 'workbench.colorCustomizations stop working' regression on an earlier version (V1.130) — cited only as a related lead, not verified as owning the same symptom, so not treated as a duplicate canonical.
- **Open decisions:**
  - Is the Modern UI default (non-pill) tab style intended to preserve a visible tab.activeBorder/activeBorderTop underline equivalent to the classic UI, or is a more subtle `.tab-fill` border an intentional design change that the customization should still visibly participate in?

## Evidence

- **legacy path disabled:** src/vs/workbench/contrib/modernUI/browser/media/tabs.css line 279-281 sets `.modern-ui-tabs .part.editor .tabs-container > .tab .tab-border-bottom-container { display: none !important; }`, which hides the element multiEditorTabsControl.ts (lines 1034, 1886-1904) uses to render TAB_ACTIVE_BORDER/TAB_ACTIVE_BORDER_TOP in the classic tabs UI.
- **replacement path exists but unverified:** src/vs/workbench/services/themes/browser/modernTabColorCustomizations.ts resolves the same legacy color IDs (TAB_ACTIVE_BORDER, TAB_ACTIVE_BORDER_TOP) into `--modern-ui-editor-tab-active-border(-top)` CSS variables, consumed by tabs.css lines 311-316 on `.tab.active > .tab-fill` — this should theoretically flow the user's customization through, but I could not execute the UI to confirm it renders visibly as reported.
- **community corroboration:** A second reporter (nannerpusser) independently confirms modernEditorTab color customizations only work in 'pill mode', not the Modern UI default look, and a third commenter reports the same usability problem (can't tell tabs apart) three days later.
- **reporter's own A/B evidence:** Reporter provided before/after screenshots comparing 1.138 (working) vs 1.139 (broken), and confirmed reverting to 1.138 restores the customization.
