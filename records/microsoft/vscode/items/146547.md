# Issue #146547 — Add an `onExtensionActivated` activation event

[https://github.com/microsoft/vscode/issues/146547](https://github.com/microsoft/vscode/issues/146547)

## Summary

A real capability gap remains: current extension dependencies activate only in the dependency direction, and the API exposes neither the requested activation event nor an equivalent activation-state notification. Keep the Backlog request open for an API and lifecycle decision.

## Change summary

Allow an extension to activate automatically when another named extension becomes active, without duplicating that extension's activation events.

## Best solution

Define whether VS Code should support a declarative reverse-dependency activation event, including ordering, failure, cycle, and cross-extension-host semantics. If accepted, integrate it with the existing activation registry and activator rather than changing the established direction of `extensionDependencies`.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/common/extensionsRegistry.ts`, `src/vs/workbench/services/extensions/common/extensionDescriptionRegistry.ts`, `src/vs/workbench/api/common/extHostExtensionActivator.ts`, `src/vs/workbench/api/test/common/extHostExtensionActivator.test.ts`
- **Validation:** Extend src/vs/workbench/api/test/common/extHostExtensionActivator.test.ts with an activation-order test proving that an extension declaring `onExtensionActivated:publisher.parent` remains inactive beforehand, activates after the named extension, and preserves existing `extensionDependencies` ordering.
- **Behavior:**

  > An extension may declare that it should activate when a named extension becomes active. It must remain inactive before that condition occurs and activate only after the named extension's activation has completed according to the chosen failure semantics. Existing activation events and the established behavior of `extensionDependencies` must remain unchanged.
- **Trace:**

  > ExtensionsActivator.activateByEvent in src/vs/workbench/api/common/extHostExtensionActivator.ts resolves only exact entries from ExtensionDescriptionRegistry's activation map. ExtensionsActivator._handleActivationRequest separately walks `extensionDependencies` from dependent to dependency, guaranteeing dependencies activate first but providing no reverse trigger. The public API in src/vscode-dts/vscode.d.ts offers imperative `Extension.activate()` and a static `isActive` flag, but no activation-state event; `extensions.onDidChange` concerns extension inventory changes. The boundary is the extension activation lifecycle: do not reverse or weaken existing dependency ordering, and account explicitly for extensions running in different extension hosts.
- **Open decisions:**
  - Should `onExtensionActivated:<id>` be available for any installed extension, or only when the declaring extension also names that ID in `extensionDependencies`?
  - Should the dependent activate only after successful completion of the named extension's activation, and what should happen when that activation fails?
  - How should reverse-activation chains, cycles, and extensions assigned to different extension hosts be handled?

## Evidence

- **current dependency semantics:** In src/vs/workbench/api/common/extHostExtensionActivator.ts, ExtensionsActivator._handleActivationRequest activates entries from the current extension's `extensionDependencies` before activating that extension; it does not activate extensions that depend on the current one.
- **activation-event gap:** ExtensionsActivator.activateByEvent in src/vs/workbench/api/common/extHostExtensionActivator.ts selects extensions through ExtensionDescriptionRegistry.getExtensionDescriptionsForActivationEvent. The activation-event schema in src/vs/workbench/services/extensions/common/extensionsRegistry.ts has no `onExtensionActivated` event.
- **existing API limitation:** src/vscode-dts/vscode.d.ts exposes `Extension.isActive` and imperative `Extension.activate()`, while `extensions.onDidChange` only reports installation, uninstallation, enablement, or disablement changes. There is no event notifying an extension that another extension became active.
- **reporter clarification:** The reporter confirmed that `extensionDependencies` already guarantees the parent activates before the child, but does not activate the child whenever the parent activates: https://github.com/microsoft/vscode/issues/146547#issuecomment-1352116958
- **canonical search:** Searches for open `onExtensionActivated`, dependent-extension activation, and `extensionDependencies` requests found no broader open issue that owns this exact reverse-activation requirement.
