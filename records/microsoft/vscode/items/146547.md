# Issue #146547 — Add an `onExtensionActivated` activation event

[https://github.com/microsoft/vscode/issues/146547](https://github.com/microsoft/vscode/issues/146547)

## Summary

This remains a real declarative activation gap: current `extensionDependencies` handling activates dependencies before dependents, but does not activate a dependent when its dependency activates. The request is already accepted into the Backlog and correctly routed to extension activation.

## Change summary

Add an activation event that activates an extension when a named extension successfully activates.

## Best solution

Define the lifecycle and cross-extension-host semantics of `onExtensionActivated:<extensionId>`, then add it to the activation-event registry and dispatch it after successful activation without changing the existing ordering contract of `extensionDependencies`.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/common/extensionsRegistry.ts`, `src/vs/workbench/api/common/extHostExtensionService.ts`, `src/vs/workbench/api/common/extHostExtensionActivator.ts`, `src/vs/workbench/api/test/common/extHostExtensionActivator.test.ts`
- **Validation:** Extend `src/vs/workbench/api/test/common/extHostExtensionActivator.test.ts` with activation-order tests proving that an extension registered for `onExtensionActivated:pub.parent` activates after `pub.parent` completes successfully, while unrelated extensions and ordinary `extensionDependencies` behavior remain unchanged.
- **Behavior:**

  > An extension may declaratively request activation when a named extension activates. The dependent activation must occur at the lifecycle point selected by the maintainer, with deterministic behavior for activation failures and cycles. Existing `extensionDependencies` ordering and unrelated activation events must remain unchanged. Acceptance should cover successful activation, failure behavior, and activation cycles or deduplication.
- **Trace:**

  > `ExtensionsActivator._handleActivationRequest` in `src/vs/workbench/api/common/extHostExtensionActivator.ts` implements only dependency-first activation, so parent activation does not discover or activate dependents. Supported manifest events are surfaced by `src/vs/workbench/services/extensions/common/extensionsRegistry.ts`; no extension-specific event is registered. Successful activation reaches `ExtHostExtensionService._activateExtension` in `src/vs/workbench/api/common/extHostExtensionService.ts`, which sends `$onDidActivateExtension` to the main thread after the extension's activation promise resolves. The uncertainty begins at the public lifecycle contract and at coordinating the resulting event across local, remote, and web extension hosts without introducing activation deadlocks. Keep the existing meaning and direction of `extensionDependencies`; this request adds a distinct opt-in activation relationship.
- **Open decisions:**
  - Should `onExtensionActivated:<id>` fire only after the target extension's activation promise resolves successfully, or also when activation starts or fails?
  - Must this activation relationship work across local, remote, and web extension-host boundaries, including when the two extensions run in different hosts?
  - What observable behavior should VS Code provide for cycles formed by `onExtensionActivated` events or by combinations of these events with `extensionDependencies`?

## Evidence

- **current dependency semantics:** `src/vs/workbench/api/common/extHostExtensionActivator.ts` `_handleActivationRequest` traverses `extensionDependencies` only from the extension being activated to its dependencies and waits for those operations; there is no reverse dependent-activation path.
- **activation event registry:** `src/vs/workbench/services/extensions/common/extensionsRegistry.ts` registers the supported activation-event snippets, including `onLanguage`, `onCommand`, and `onStartupFinished`, but no `onExtensionActivated` event exists on current main.
- **completion path:** `src/vs/workbench/api/common/extHostExtensionService.ts` `_activateExtension` reports successful completion through `$onDidActivateExtension`, but does not dispatch an extension-specific activation event.
- **existing API does not cover the request:** `src/vscode-dts/vscode.d.ts` exposes `extensions.getExtension`, `Extension.activate`, and `extensions.onDidChange`; `onDidChange` covers installation and enablement changes, while explicit `activate()` forces activation and does not declaratively activate a child when its parent activates.
- **related precedent:** https://github.com/microsoft/vscode/issues/113783 requested notification when another extension activates. A maintainer suggested a custom contribution-point pattern, but the issue was later closed only by the feature-request upvote process, not because an equivalent built-in event was implemented.
- **canonical search:** Searches for `onExtensionActivated`, `extensionDependencies` activation, and activation by another extension found no broader open canonical issue; https://github.com/microsoft/vscode/issues/146547 remains the direct open tracker.
