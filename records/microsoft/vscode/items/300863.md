# Issue #300863 — Opening a workspace within a directory whose name has changed results in Vscode recreating the directory under the old name

[https://github.com/microsoft/vscode/issues/300863](https://github.com/microsoft/vscode/issues/300863)

## Summary

Current main still has a source-reproducible path where hot-exit restores dirty files at an obsolete URI and auto-save recreates the missing parent hierarchy without warning. This should remain open and route to the hot-exit owners.

## Change summary

Reopening a workspace after an external parent-directory rename can silently recreate the old directory and save restored files into it.

## Best solution

Preserve restored dirty buffers without automatically recreating a missing workspace path, clearly identify the files as orphaned, and require an informed save or relocation decision from the user.

## Plan brief

- **Likely files:** `src/vs/workbench/services/workingCopy/common/storedFileWorkingCopy.ts`, `src/vs/workbench/browser/parts/editor/editorAutoSave.ts`, `src/vs/workbench/services/workingCopy/test/browser/storedFileWorkingCopy.test.ts`, `src/vs/workbench/contrib/files/test/browser/editorAutoSave.test.ts`
- **Validation:** Add a regression test that restores a dirty backup whose original parent no longer exists with after-delay auto-save enabled, then assert that the obsolete hierarchy is not created and the working copy remains recoverable; run `scripts/test.sh --grep "EditorAutoSave|StoredFileWorkingCopy"`.
- **Behavior:**

  > When VS Code restores dirty files after their workspace or parent directory was renamed or removed while the window was closed, it must not silently recreate the obsolete hierarchy through auto-save. The restored contents must remain recoverable, and the UI must clearly communicate that their original location is missing before anything is written. Existing auto-save behavior for files whose locations still exist must remain unchanged, and an explicit user-approved save must remain possible.
- **Trace:**

  > Hot-exit restoration reaches StoredFileWorkingCopy.doResolveFromBackup in src/vs/workbench/services/workingCopy/common/storedFileWorkingCopy.ts. It trusts the backup's historical `orphaned` metadata and does not stat the resource, so a path removed after backup creation is restored dirty but non-orphaned. EditorAutoSave in src/vs/workbench/browser/parts/editor/editorAutoSave.ts schedules that dirty working copy, and StoredFileWorkingCopy.doSave delegates to FileService.writeFile, whose missing-file path recursively creates parents in src/vs/platform/files/common/fileService.ts. This directly explains why only backed-up open files appear under the recreated old directory. Keep FileService's general create-with-parents contract unchanged because other create and save flows depend on it; the boundary is restored working copies whose original location disappeared while VS Code was closed.
- **Open decisions:**
  - When a restored dirty file's original parent is missing, should VS Code keep it dirty with a deleted-location warning until the user explicitly saves, or immediately prompt the user to choose a replacement location?

## Evidence

- **backup restoration:** src/vs/workbench/services/workingCopy/common/storedFileWorkingCopy.ts restores backup contents and the previously recorded `orphaned` flag without checking whether the resource or its parent still exists. A backup created before the external rename therefore reopens dirty at the obsolete URI while appearing non-orphaned.
- **automatic save trigger:** src/vs/workbench/browser/parts/editor/editorAutoSave.ts schedules auto-save for every newly registered dirty working copy when after-delay auto-save is configured, including a working copy restored from hot-exit backup.
- **directory recreation:** StoredFileWorkingCopy.doSave in src/vs/workbench/services/workingCopy/common/storedFileWorkingCopy.ts writes the restored snapshot to its original URI. FileService.writeFile in src/vs/platform/files/common/fileService.ts calls `mkdirp` whenever the target file is absent, recreating the complete obsolete parent path before writing.
- **existing tests:** src/vs/workbench/services/workingCopy/test/browser/storedFileWorkingCopy.test.ts verifies backup restoration and orphan metadata separately, while src/vs/workbench/contrib/files/test/browser/editorAutoSave.test.ts verifies dirty-model auto-save; neither covers a backup whose resource disappears while VS Code is closed.
- **canonical search:** Repository searches for renamed-parent, hot-exit, auto-save, and old-path recreation reports found no open issue that owns this same restore-and-recreate behavior.
