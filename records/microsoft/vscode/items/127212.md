# Issue #127212 — Custom editors: implement proper untitled editor factory

[https://github.com/microsoft/vscode/issues/127212](https://github.com/microsoft/vscode/issues/127212)

## Summary

The requested factory cleanup remains necessary: current main still allocates monotonically increasing untitled names and does not preserve associated-resource semantics through custom-editor creation and saving. Keep this accepted Backlog work open under its existing area labels.

## Change summary

Make custom-editor untitled factories reuse available generated names and preserve an associated file path, initial dirty state, and direct-save behavior.

## Best solution

Bring custom-editor untitled creation into line with the workbench's associated-resource contract, including saving to the supplied path without a dialog. Generated untitled identities should be reusable after disposal without colliding with live documents.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/customEditor/browser/customEditors.ts`, `src/vs/workbench/contrib/customEditor/browser/customEditorInput.ts`, `src/vs/workbench/contrib/customEditor/browser/customEditorInputFactory.ts`, `src/vs/workbench/api/browser/mainThreadCustomEditors.ts`, `src/vs/workbench/services/editor/test/browser/editorResolverService.test.ts`
- **Validation:** With an editable custom-document provider, create multiple resource-less untitled editors, dispose one, and create another: released numbering must be reusable without colliding with a live document. Run `code <nonexistent-path>.<custom-editor-extension>` and verify the associated path is displayed, the document starts dirty, and Save writes to that path without opening a picker. Verify ordinary unassociated untitled documents still prompt on Save, and exercise reload/restore of an associated untitled document. The plan should establish automated factory and save-path regression coverage for these cases.
- **Behavior:**

  > Custom editors must honor both forms of untitled input. Resource-less creation produces unique generated identities while editors are live and permits released names to be reused after disposal. Opening a nonexistent custom-editor file from the command line retains its associated path, starts dirty, and saves there without requesting a destination. Ordinary unassociated untitled documents must continue to request a destination, and restoration must not lose the distinction.
- **Trace:**

  > CustomEditorService.registerContributionPoints in src/vs/workbench/contrib/customEditor/browser/customEditors.ts increments a service-wide counter and forwards only resource to CustomEditorInput.create. The CLI-path conversion in src/vs/workbench/common/editor.ts supplies forceUntitled for nonexistent paths, and EditorResolverService forwards that untyped input to the factory. CustomEditorInput in src/vs/workbench/contrib/customEditor/browser/customEditorInput.ts transfers existing text content but does not carry explicit associated-resource state. MainThreadCustomEditorModel in src/vs/workbench/api/browser/mainThreadCustomEditors.ts classifies untitled documents by scheme and always invokes a destination picker for that branch. CustomEditorInputSerializer in src/vs/workbench/contrib/customEditor/browser/customEditorInputFactory.ts persists resource, dirty state, and backup identity, so restoration is a relevant boundary. The remaining planning work is to trace shared-document lifetime and restoration sufficiently to define regression coverage; preserve existing document sharing, content transfer, backup behavior, and ordinary Save As semantics. The notebook precedent at https://github.com/microsoft/vscode/issues/125028 explains the contract but does not resolve this custom-editor path.
