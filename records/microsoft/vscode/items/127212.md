# Issue #127212 — Custom editors: implement proper untitled editor factory

[https://github.com/microsoft/vscode/issues/127212](https://github.com/microsoft/vscode/issues/127212)

## Summary

The debt remains on current main: the custom-editor untitled factory still uses a monotonically increasing local counter and passes supplied resources through without implementing the documented associated-path semantics.

## Change summary

Make custom editors correctly create reusable untitled resources and preserve an associated file path for CLI-opened nonexistent files.

## Best solution

Bring the custom-editor resolver factory in line with `IUntitledTextResourceEditorInput`: recycle generated untitled names after disposal and retain the distinction between an untitled resource and its associated save target, with focused tests for both flows.

- **Rationale:** The intended factory contract and current violation are explicit in source, the work is localized, and both resource-lifecycle cases can be pinned with focused unit tests.
- **Likely files:** `src/vs/workbench/contrib/customEditor/browser/customEditors.ts`, `src/vs/workbench/contrib/customEditor/browser/customEditorInput.ts`, `src/vs/workbench/contrib/customEditor/test/browser/customEditors.test.ts`
- **Validation:** Add and run a targeted custom-editor unit suite asserting that disposing an anonymously created untitled input permits reuse of its generated resource, and that a nonexistent file resource produces an untitled, initially dirty input whose save target is the associated file path.
- **Behavior:**

  > Creating a custom editor without a resource produces a unique untitled resource while that editor is alive, and closing it makes that generated slot reusable instead of growing the counter forever. Opening a nonexistent custom-editor file from the CLI produces an untitled editor that displays the associated path, starts dirty, and saves to that path without prompting. Existing-file custom editors and explicit `untitled:` resources must retain their current behavior.
- **Trace:**

  > The unresolved factory is `CustomEditorService.registerContributionPoints` in src/vs/workbench/contrib/customEditor/browser/customEditors.ts: its `createUntitledEditorInput` callback either forwards the incoming URI unchanged or creates `untitled://Untitled-N` using a service-wide counter, with no disposal accounting. The input contract in src/vs/workbench/common/editor.ts distinguishes no resource, an explicit `untitled:` resource, and a non-untitled associated resource, but the custom-editor callback does not preserve that distinction. `CustomEditorInput.capabilities` in src/vs/workbench/contrib/customEditor/browser/customEditorInput.ts recognizes untitled state solely from the URI scheme, and its save path must continue to work through the custom document model rather than changing ordinary custom-editor save behavior. The notebook analogue at https://github.com/microsoft/vscode/issues/125028 is useful precedent but is not a canonical issue for this custom-editor work.
