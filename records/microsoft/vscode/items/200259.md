# Issue #200259 — Widget navigation steals editor focus

[https://github.com/microsoft/vscode/issues/200259](https://github.com/microsoft/vscode/issues/200259)

## Summary

Keep open: multiple reporters confirmed that widget navigation intercepts editor Command+Up/Down, and the merged PR added diagnostics rather than fixing the focus state. The matching open report is newer, so this re-reviewed issue should remain the canonical investigation.

## Change summary

Prevent widget-navigation shortcuts from intercepting Command+Up/Down when focus has returned to a source editor.

## Best solution

Identify the focus transition that leaves navigableContainerFocused active outside its container, then restore normal editor cursor navigation while preserving intentional navigation within widgets. Use the existing diagnostic logging to establish a deterministic reproduction before implementing a fix.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/actions/widgetNavigationCommands.ts`
- **Validation:** On macOS, capture navigable-container debug logs while moving between registered widgets and a source editor, including the notebook-cell workflow mentioned in the thread. Establish a repeatable transition, then verify Command+Up/Down invokes cursorTop/cursorBottom in the source editor while widget navigation still works inside its intended containers.
- **Behavior:**

  > An intermittently stale navigable-container focus state causes Command+Up/Down in a source editor to invoke widget navigation instead of moving the caret to the beginning or end of the document. Normal editor navigation must resume whenever focus leaves the navigable container for the source editor, without requiring a window reload. Intentional navigation between widgets inside a focused container must remain unchanged. Acceptance requires a repeatable failing focus-transition scenario and verification of both editor and widget behavior.
- **Trace:**

  > In src/vs/workbench/browser/actions/widgetNavigationCommands.ts, handleFocusEventsGroup maintains focused notifier indices, and NavigableContainerManager.register updates navigableContainerFocused and lastContainer from their aggregate notifications. The current bindings remain eligible when that context key is true and listFocus is false, which explains interception given the stale state the reporter inspected. The source inspection does not establish which notification or lifecycle transition leaves that state behind. https://github.com/microsoft/vscode/pull/209357 added logging through workbench.navigibleContainer.enableDebug and the Window debug log; it did not fix the state management. Begin with those diagnostics and the thread's notebook-navigation lead, preserving intended widget keybindings and avoiding a blanket exclusion of all text inputs. https://github.com/microsoft/vscode/issues/225613 contains a newer matching report and additional confirmation, not an older canonical issue.
