# Issue #144513 — Remote extension fails to activate in web worker extension host 

[https://github.com/microsoft/vscode/issues/144513](https://github.com/microsoft/vscode/issues/144513)

## Summary

The activation failure remains reproducible in current GitHub Codespaces, and current main still fetches the remote extension entry point from the cross-origin web worker. This issue should remain open as the canonical report while the hosted-embedder loading contract is designed.

## Change summary

Remote web extensions fail to activate in hosted environments when their entry point requires an authenticated request unavailable to the cross-origin web worker extension host.

## Best solution

Provide a supported entry-point loading path for hosted embedders that can use the main origin's service worker or authentication context without changing ordinary web-worker extension loading unnecessarily.

## Plan brief

- **Likely files:** `src/vs/workbench/api/worker/extHostExtensionService.ts`, `src/vs/workbench/api/common/extHostExtensionService.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadExtensionService.ts`
- **Validation:** In a GitHub Codespace, install a remote web extension whose browser entry point is served through vscode-remote-resource, activate it in the web-worker extension host, and verify that its entry point loads successfully without a CORS or authentication failure; also verify that a locally hosted web extension still activates.
- **Behavior:**

  > A web extension installed remotely in GitHub Codespaces must activate in the web-worker extension host even when its entry point is served through an authenticated remote-resource URL. Loading must not fail because the worker origin cannot access the main origin's service worker or cookies. Local and same-origin web extensions must continue to activate normally.
- **Trace:**

  > ExtHostExtensionService._loadCommonJSModule in src/vs/workbench/api/worker/extHostExtensionService.ts asks MainThreadExtensionServiceShape.$asBrowserUri to resolve the module but executes fetch from the worker origin. The latest Codespaces reproduction reports that this request bypasses the main-origin service worker and reaches github.dev without the required authentication context. The closed, unmerged https://github.com/microsoft/vscode/pull/144515 moved reading to MainThreadFileSystemShape.$readFile globally; maintainers rejected that broad placement and noted that only embedders such as Codespaces may need it. Keep nested Worker support in src/vs/workbench/api/worker/extensionHostWorker.ts out of scope because https://github.com/microsoft/vscode/issues/168942 tracks that separate limitation.
- **Open decisions:**
  - Should authenticated main-thread entry-point loading be an explicit capability supplied by hosted embedders, or the default behavior for every web-worker extension host?

## Evidence

- **current reproduction:** The September 14, 2026 comment confirms the failure on the latest GitHub Codespaces stable release and reports that the request bypasses the service worker and reaches github.dev without the required authentication cookies.
- **current source path:** src/vs/workbench/api/worker/extHostExtensionService.ts resolves the remote module through MainThreadExtensionServiceShape.$asBrowserUri, then calls fetch(browserUri.toString(true)) inside the web worker without an authenticated main-origin request path.
- **failed prior fix:** https://github.com/microsoft/vscode/pull/144515 proposed reading the entry point on the main thread but was closed without merging. The issue was closed on March 24, 2022, then reopened on March 29 after the reporter verified that the attempted fix did not work.
- **maintainer diagnosis:** A maintainer identified that the worker-origin request is not intercepted by the service worker and said a main-thread request might be appropriate only for embedders such as Codespaces, leaving an unresolved host-contract decision.
- **canonical status:** The open related report https://github.com/microsoft/vscode/issues/201069 points back to this issue as the likely cause. The closed https://github.com/microsoft/vscode/issues/168942 concerns nested Worker creation from remote extensions, a different limitation.
