# Issue #144513 — Remote extension fails to activate in web worker extension host 

[https://github.com/microsoft/vscode/issues/144513](https://github.com/microsoft/vscode/issues/144513)

## Summary

The bug remains reproducible in current GitHub Codespaces, and the previously proposed fix was not accepted because it requires an embedder-specific request path. The On Deck milestone does not prevent cleanup, but the fresh confirmed reproduction establishes that a real gap remains.

## Change summary

Remote-installed web extensions fail to activate in the web worker extension host because their entry point cannot be fetched across the webview and remote-resource origins.

## Best solution

Define an embedder-aware resource-loading contract so the worker extension host can delegate authenticated remote extension entry-point requests through the main thread only where required, without weakening origin or credential boundaries for ordinary web extensions.

## Plan brief

- **Likely files:** `src/vs/workbench/api/worker/extHostExtensionService.ts`
- **Validation:** In a GitHub Codespaces stable deployment, install a web-capable extension remotely and verify that its web entry point loads and activates in the web worker extension host without a CORS or authentication failure; also verify that ordinary same-origin web extension loading is unchanged.
- **Behavior:**

  > A web-capable extension installed on the remote side of a GitHub Codespace must activate in the web worker extension host. Its entry-point request must succeed across the worker and remote-resource origins while preserving the authentication and origin protections required by the embedder. Acceptance requires activation in current Codespaces without CORS or missing-cookie failures, with existing same-origin web extension activation unchanged.
- **Trace:**

  > The failure occurs while ExtHostExtensionService in src/vs/workbench/api/worker/extHostExtensionService.ts fetches a remote extension entry point from the web worker origin. The maintainer diagnosis at https://github.com/microsoft/vscode/issues/144513#issuecomment-1113016497 establishes that the main-thread-origin service worker cannot intercept this request; https://github.com/microsoft/vscode/pull/144515 explored main-thread delegation but was closed because that path must be embedder-specific. A September 2026 Codespaces reproduction adds that direct requests now pass CORS but cannot carry the required github.dev authentication cookies. The boundary is remote/embedder resource loading: same-origin worker loading and the general web-extension security model must not be weakened.
- **Open decisions:**
  - What explicit embedder capability or protocol should authorize delegation of remote extension resource requests through the main thread?
  - Should authentication be supplied by an embedder-owned resource endpoint or by a VS Code request bridge, given SameSite cookie restrictions?
  - Which remote environments should opt into the delegated path beyond GitHub Codespaces?

## Evidence

- **current reproduction:** A September 14, 2026 comment confirms reproduction on the latest GitHub Codespaces stable release and reports that the request bypasses the service worker, reaches github.dev, and lacks usable authentication cookies.
- **maintainer diagnosis:** https://github.com/microsoft/vscode/issues/144513#issuecomment-1113016497 identifies the root cause: worker-origin requests are not intercepted by the service worker installed on the main-thread origin.
- **closed fix attempt:** https://github.com/microsoft/vscode/pull/144515 proposed routing the request through the main thread, but it is closed rather than merged; the maintainer noted that such behavior must be limited to embedders such as Codespaces.
- **related remaining gap:** https://github.com/microsoft/vscode/issues/201069 remains open for testing web extensions in remote environments, but it does not clearly own the narrower authenticated cross-origin activation failure reported here.
