# Issue #241354 — vscode in linux with kde dont use xdg-open or default file-manager

[https://github.com/microsoft/vscode/issues/241354](https://github.com/microsoft/vscode/issues/241354)

## Summary

Keep open as an upstream Linux desktop-integration issue: VS Code delegates file-manager selection to Electron, whose reveal operation is not equivalent to xdg-open. No verified fix or eligible older canonical establishes that this report is resolved.

## Change summary

Make Open Containing Folder use the configured KDE file manager instead of opening Nemo when Dolphin is the directory default.

## Best solution

Ensure Electron's Linux reveal operation selects the appropriate desktop file manager while preserving file highlighting. Establish whether the remaining mismatch comes from Electron's portal/FileManager1 selection or the desktop session's service configuration before changing VS Code.

## Evidence

- **Reported trigger:** https://github.com/microsoft/vscode/issues/241354 reports that Open Containing Folder opens Nemo on KDE 6 despite xdg-mime identifying org.kde.dolphin.desktop and xdg-open opening Dolphin. Changing GTK_USE_PORTAL did not help; the March 2025 commenter discusses a file chooser and a custom distribution, so that comment does not conclusively reproduce this reveal-operation defect.
- **Current VS Code call path:** src/vs/workbench/contrib/files/electron-browser/fileCommands.ts:15–27 routes local resources through nativeHostService.showItemInFolder. src/vs/platform/native/electron-main/nativeHostMainService.ts:702–704 directly calls Electron shell.showItemInFolder(path), without selecting Nemo, Dolphin, or an inode/directory handler.
- **Upstream behavior:** The checkout's .npmrc targets Electron 43.7.7. https://github.com/electron/electron/blob/v43.7.7/shell/common/platform_util_linux.cc shows ShowItemHelper preferring the desktop portal's OpenDirectory operation, then org.freedesktop.FileManager1.ShowItems, with xdg-open used for the parent-folder fallback. Thus a working xdg-open command does not establish which application the reveal operation selects; the reporter's current portal and D-Bus state was not exercised.
- **Newer same-symptom report:** https://github.com/microsoft/vscode/issues/292305 is open and reports Open Containing Folder opening Thunar instead of the configured pcmanfm on VS Code 1.108.2 with extensions disabled. Created on 2026-02-02, it is younger than this issue and cannot be its canonical under the re-review rule.
- **Related but distinct symptom:** https://github.com/microsoft/vscode/issues/245355 is open but reports no file-manager window opening unless one is already running, rather than the wrong manager opening. Its maintainer comment explicitly distinguishes revealing a file from displaying a native file dialog: https://github.com/microsoft/vscode/issues/245355#issuecomment-2773072416.
