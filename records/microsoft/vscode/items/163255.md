# Issue #163255 — WORKSPACE_CONTAINS_TIMEOUT should be configurable

[https://github.com/microsoft/vscode/issues/163255](https://github.com/microsoft/vscode/issues/163255)

## Summary

Keep open: this accepted Backlog request has 31 community upvotes, and current main still hard-codes the workspaceContains search timeout at seven seconds without a corresponding setting.

## Change summary

Allow users to configure how long VS Code searches workspaceContains patterns before canceling extension activation.

## Best solution

Expose a bounded workspaceContains search-timeout setting that retains the current seven-second default and applies consistently to local, remote, and web extension-host activation.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/common/workspaceContains.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/api/common/extHostExtensionService.ts`, `src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts`, `src/vs/workbench/services/extensions/test/common/workspaceContains.test.ts`
- **Validation:** Add workspaceContains timeout tests and run `scripts/test.sh --grep "workspaceContains timeout"`; cover the unchanged seven-second default, a configured longer timeout allowing a delayed match, and cancellation at the configured limit.
- **Behavior:**

  > Users can configure how long VS Code searches workspaceContains activation patterns before treating the search as timed out. The existing seven-second behavior remains the default, while a longer configured value allows slow or large workspaces to complete activation discovery. Invalid values are rejected or safely bounded. The behavior is consistent across supported extension-host locations.
- **Trace:**

  > The timeout is currently a module-level constant in src/vs/workbench/services/extensions/common/workspaceContains.ts, where `_activateIfGlobPatterns` cancels `host.checkExists` after 7000 ms. The helper is reached through hosts constructed in src/vs/workbench/services/extensions/common/abstractExtensionService.ts and src/vs/workbench/api/common/extHostExtensionService.ts, so configuration must reach both paths consistently. Extension settings are registered in src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts, but no timeout setting exists today. Commit 9fd6ee7095e76a304556c06bbef16fc4f05cf697 established that timeout means no activation; preserve that semantic and the default duration. Do not alter activation-event matching, file-search behavior, or extension-specific activation policy.
- **Open decisions:**
  - Should the timeout be an application-level preference shared by all workspaces, or may individual workspaces override it?
  - Should one configured value govern local, remote, and web extension hosts, or should host-specific constraints cap or override it?
  - What minimum and maximum values should the public setting permit so users cannot accidentally create unbounded startup searches?
