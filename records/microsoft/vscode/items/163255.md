# Issue #163255 — WORKSPACE_CONTAINS_TIMEOUT should be configurable

[https://github.com/microsoft/vscode/issues/163255](https://github.com/microsoft/vscode/issues/163255)

## Summary

The requested configuration is still absent on current main, and this accepted Backlog request has 31 community upvotes. Keep it open for an extension-host design decision rather than closing or requesting more information.

## Change summary

Allow users to configure the timeout applied while resolving glob-based `workspaceContains` extension activation events.

## Best solution

Provide a bounded advanced timeout setting that applies consistently to local and remote extension activation while preserving the existing seven-second default and cancellation behavior. The setting's scope and safe range need maintainer agreement before implementation.

## Vision fit

- **Fit:** aligned
- **Reason:** Giving users controlled relief from failed extension activation on slower or larger workspaces supports both extension reliability and performance.
- **Evidence:** Durable themes: Performance and Extension ecosystem; the guardrail that performance trumps functionality makes a bounded, opt-in adjustment preferable to increasing the default globally.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/common/workspaceContains.ts`, `src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/api/common/extHostExtensionService.ts`
- **Validation:** Add focused workspaceContains tests covering the unchanged seven-second default and a short configured timeout that cancels the search without activating the extension; run them with `scripts/test.sh --grep "workspaceContains"`.
- **Behavior:**

  > Users with workspace searches that legitimately need longer than seven seconds can configure the `workspaceContains` activation timeout. The existing seven-second behavior remains the default, and a timed-out search still cancels without activating the extension. The configured value applies consistently to local and remote workspaces, with invalid or unsafe values rejected or constrained according to the agreed setting contract.
- **Trace:**

  > The timeout is a module constant in src/vs/workbench/services/extensions/common/workspaceContains.ts and is consumed by `_activateIfGlobPatterns`, which cancels `host.checkExists` when the timer fires. The shared helper is reached from AbstractExtensionService for workbench-side activation and ExtHostExtensionService for extension-host activation. Configuration registration for extension settings is in src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts. Commit 9fd6ee7095e76a304556c06bbef16fc4f05cf697 intentionally established the current cancellation and non-activation semantics; those semantics and the default timeout must not change. The uncertainty begins at how configuration should be scoped and made available consistently to both callers.
- **Open decisions:**
  - Should the timeout be application-, machine-, or workspace-scoped, particularly for remote workspaces?
  - What minimum, maximum, and special-value behavior should the setting permit?
  - Should callers pass a resolved timeout into the shared helper, or should the activation host contract expose it?
