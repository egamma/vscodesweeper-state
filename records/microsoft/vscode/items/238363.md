# Issue #238363 — Git - Opening diff from blame should reveal previously focused line

[https://github.com/microsoft/vscode/issues/238363](https://github.com/microsoft/vscode/issues/238363)

## Summary

Keep open: opening a commit from blame now reveals the file, but current code still does not reveal the previously focused line. A maintainer explicitly identified exact-line navigation as remaining work when closing a newer related report.

## Change summary

Reveal the corresponding historical line when opening a commit's multi-file diff from Git blame.

## Best solution

Complete blame-to-diff navigation in the built-in Git extension, using the corresponding line in the blamed revision rather than blindly reusing the working-document line number. Preserve existing file reveal and navigation from callers without line context.

## Plan brief

- **Likely files:** `extensions/git/src/blame.ts`, `extensions/git/src/hover.ts`, `extensions/git/src/commands.ts`, `extensions/git/src/git.ts`
- **Validation:** In a disposable Git repository, commit a distinctive line far below the first viewport, then make later committed and uncommitted insertions above it. Open that line's blamed commit through the decoration hover and status bar; the correct historical file and corresponding line must be visible. Also check an unchanged-coordinate case and existing commit navigation without blame context. The plan should establish automated coverage for historical coordinate mapping and the emitted reveal range.
- **Behavior:**

  > Opening a commit from blame should reveal the historical line corresponding to the line the user was inspecting, not merely the beginning of its file. This should work from the editor decoration hover and blame status bar. Later insertions above the line must not cause navigation to an unrelated historical line. Existing commit navigation without line context must retain its current behavior.
- **Trace:**

  > The decoration hover obtains LineBlameInformation but calls GitBlameController.getBlameInformationHover without passing its lineNumber; getHoverCommitHashCommands in extensions/git/src/hover.ts emits git.viewCommit arguments containing only URIs and a hash. The status-bar command likewise omits line context, and Commands.viewCommit in extensions/git/src/commands.ts creates a reveal object containing only modifiedUri. The workbench command already supports reveal.range, and MultiDiffEditor._applyOptions forwards it to the widget. The unresolved part is mapping the working-document location and resource to the blamed revision: the controller maps local changes for blame lookup, while parseGitBlame in extensions/git/src/git.ts discards original-line and historical-filename information. Establish that mapping before choosing implementation scope; do not change unrelated Timeline/history callers or add a navigation setting. https://github.com/microsoft/vscode/issues/259508#issuecomment-3209338909 explicitly distinguishes the completed file reveal from this remaining line reveal.

## Evidence

- **Current navigation loses line context:** extensions/git/src/hover.ts:getHoverCommitHashCommands and extensions/git/src/blame.ts:GitBlameStatusBarItem pass only document URI, commit hash, and reveal URI to git.viewCommit. extensions/git/src/commands.ts:5120–5139 constructs reveal with modifiedUri only; no range is supplied.
- **Existing capability is only partially connected:** src/vs/workbench/browser/parts/editor/editorCommands.ts:_workbench.openMultiDiffEditor accepts reveal.range and forwards it into revealData. src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditor.ts:_applyOptions passes that range to the widget. The Git caller does not use this capability, and the git.blame settings in extensions/git/package.json provide no exact-line navigation option.
- **Maintainer confirms remaining scope:** https://github.com/microsoft/vscode/issues/259508#issuecomment-3209338909 states that file reveal was implemented, but revealing the exact line is trickier and remains future work. That newer issue is closed, so it is not a duplicate canonical and its partial implementation does not complete this report.
- **Historical coordinates need further diagnosis:** extensions/git/src/blame.ts:mapModifiedLineNumberToOriginalLineNumber accounts for working-tree/index changes when locating blame information. extensions/git/src/git.ts:parseGitBlame retains the incremental blame header's final-line coordinates from segments[2], but does not retain its original-line coordinate from segments[1] or historical filename. The complete mapping to the selected commit's resource and line is not yet established.
- **Canonical and implementation search:** Read-only searches for blame/diff/reveal and blame/scroll found no verified older open issue owning this exact symptom. https://github.com/microsoft/vscode/issues/301701 requests navigation to the SCM graph, not a line in the commit diff; https://github.com/microsoft/vscode/issues/298248 concerns language-model tool registration. No open PR was returned by the search for 238363.
- **Inspection limits:** The checkout was inspected without builds, execution, or modifications. Local history exposes only the current snapshot commit for the implicated files, so no behavior-changing fix commit was established.
