# Issue #231837 — gif/video support in chat

[https://github.com/microsoft/vscode/issues/231837](https://github.com/microsoft/vscode/issues/231837)

## Summary

A real gap remains on current main: GIF attachments are reduced to one frame and video MIME types are not attachable. This team-authored Backlog feature request must remain open, and no older canonical with the same request was found.

## Change summary

Let chat understand animated GIFs and video attachments so it can describe motion or analyze screen recordings.

## Best solution

Support bounded temporal analysis of GIF and common video attachments, with explicit format, frame-sampling, size, and model-capability limits so screen recordings can be analyzed without excessive request cost.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/model/chatModel.ts`, `src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentResolveService.ts`, `src/vs/workbench/contrib/chat/browser/chatImageUtils.ts`, `src/vs/workbench/contrib/chat/test/browser/chatAttachmentResolveService.test.ts`
- **Validation:** Add targeted attachment tests for animated GIF and selected video formats, then run `scripts/test.sh --grep "ChatAttachmentResolveService"`; acceptance also requires a supported-model chat flow to receive multiple temporally distinct frames while enforcing the chosen cap.
- **Behavior:**

  > Chat should preserve enough temporal information from a supported animated GIF or screen recording to answer questions about motion and changes over time. Static image behavior must remain unchanged, and unsupported formats or model capabilities must be communicated rather than silently treating media as a complete single-frame attachment. Acceptance should cover temporally distinct frames, the selected resource cap, and graceful handling when video understanding is unavailable.
- **Trace:**

  > Current accepted image types are declared in src/vs/workbench/contrib/chat/common/model/chatModel.ts and exclude every video MIME type. ChatAttachmentResolveService accepts GIFs but marks them partially omitted; resizeImage in src/vs/workbench/contrib/chat/browser/chatImageUtils.ts draws the loaded GIF once onto a canvas, so only one frame survives. The attachment UI consequently tells users that the current GIF frame will be sent. Existing image attachment and resizing semantics must remain unchanged for PNG, JPEG, and WebP. The maintainer discussion at https://github.com/microsoft/vscode/issues/231837#issuecomment-2428035160 establishes frame extraction as the likely capability boundary but leaves sampling and hard caps unsettled.
- **Open decisions:**
  - Which video container and codec combinations are part of the supported user-facing contract?
  - How should frames be sampled across an animation or recording so short actions are represented without overwhelming the request?
  - What user-visible duration, frame-count, size, or token caps apply, and how should chat report truncation?
  - Should attachment availability depend on the selected model's media capabilities, or should VS Code always convert supported temporal media into image frames?

## Evidence

- **current GIF behavior:** src/vs/workbench/contrib/chat/browser/attachments/chatAttachmentResolveService.ts marks GIF attachments partially omitted, while src/vs/workbench/contrib/chat/browser/chatImageUtils.ts loads the animation into one Image and draws it once to a canvas, producing a single PNG frame.
- **video gap:** src/vs/workbench/contrib/chat/common/model/chatModel.ts limits attachable media to PNG, JPEG, GIF, and WebP; no video MIME type is accepted by ChatAttachmentResolveService.
- **confirmed product intent:** The maintainer discussion at https://github.com/microsoft/vscode/issues/231837#issuecomment-2428035160 confirms that existing GIF handling reads only one frame and identifies frame extraction plus request caps as the intended investigation.
