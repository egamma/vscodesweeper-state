# Issue #339228 — Models from a languageModelChatProviders extension don't appear in the chat model picker in a remote (WSL) window, but do appear under "Manage Models"

[https://github.com/microsoft/vscode/issues/339228](https://github.com/microsoft/vscode/issues/339228)

## Summary

Valid, well-documented report with logs/screenshots showing a real local-vs-remote (WSL) discrepancy for a third-party BYOK model provider, but the root cause spans two layers (the chat model picker's aggregation of remote-extension-host providers, and the Agent Host's `_extractRawModelId` logic that explicitly drops any non-matching `vendor/id` identifier as 'foreign') — needs a maintainer to decide whether the Agent Host path is intentionally scoped to known providers or should forward third-party vendor/id pairs, and to trace why the main picker (not just the Agent Host fallback) hides the models remotely.

## Change summary

Models from a third-party languageModelChatProviders extension (DeepSeek) appear in 'Manage Models' and work locally, but are missing from the chat model picker and silently fall back to the default model when the window is a WSL remote window.

## Best solution

A maintainer should determine (a) why the model-picker aggregation differs between local and remote extension hosts for languageModelChatProviders-contributed models, and (b) whether src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts's `_extractRawModelId` (which drops any identifier containing '/' that doesn't match the session's own prefix) should be extended to forward third-party vendor/id pairs to the Agent Host, or whether that's an intentional scope limit that needs clearer user-facing messaging.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts`, `src/vs/workbench/contrib/chat/common/languageModels.ts`
- **Validation:** A test confirming that a third-party languageModelChatProviders model contributed from a remote (WSL) extension host appears in the chat model picker and is not dropped as 'foreign' by the Agent Host when selected.
- **Behavior:**

  > A chat model contributed by a third-party extension via contributes.languageModelChatProviders should appear in the chat model picker and remain selectable in a remote (WSL) window, matching local-window behavior, and should not silently fall back to the default model when selected. Acceptance: the model shows up in the picker, selecting it persists across chat sessions in the remote window, and no 'Dropping foreign model identifier' fallback occurs for a legitimately contributed vendor/id pair.
- **Trace:**

  > The Agent Host's `_extractRawModelId` (src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts, ~line 6184-6251) strips a recognized session-type prefix from a language-model identifier, and treats any remaining identifier containing '/' as 'foreign', dropping it and falling back to the default model — this produces exactly the warning seen in the report's renderer log. It's unclear whether this is the root cause of the model missing from the picker itself, or a secondary symptom once the model isn't resolvable; the actual picker population/aggregation logic for remote-extension-host-contributed providers (likely in src/vs/workbench/contrib/chat/common/languageModels.ts) was not traced to confirm where the local/remote divergence originates. Boundary: do not change behavior for the main (non-Agent-Host) Copilot Chat experience, which reporter confirms still lists the model under 'Manage Models'.
- **Open decisions:**
  - Is the Agent Host's drop-as-foreign behavior for third-party vendor/id pairs intentional scope (Agent Host sessions only support a fixed provider set), or should it forward arbitrary extension-contributed models?
  - Is the chat-model-picker omission in the remote window a distinct bug in how remote-extension-host-contributed languageModelChatProviders are aggregated, separate from the Agent Host fallback?
  - Is this a genuine regression (per the reporter's note that it worked before a recent update) that should be bisected against recent releases?

## Evidence

- **matching code path:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts `_extractRawModelId` (~line 6238) emits the exact log text seen in the report — '[AgentHost] Dropping foreign model identifier ... falling back to default model' — whenever the identifier contains '/' and doesn't start with the session's own prefix, i.e. any third-party vendor/id pair from a languageModelChatProviders extension.
- **regression hint:** Reporter states the models were available in the WSL window until a recent VS Code update, suggesting this may be a regression rather than a pre-existing design limitation.
- **scope not fully traced:** Did not locate the separate code path that populates the visible chat model picker list (vs. the Agent Host's model-selection fallback), so it's unclear whether the picker-hiding and the Agent Host's drop-as-foreign behavior share one root cause or are two distinct issues.
