# Issue #166752 — Typing when simple filtering is enabled in the explorer should center the item

[https://github.com/microsoft/vscode/issues/166752](https://github.com/microsoft/vscode/issues/166752)

## Summary

The requested centering behavior remains absent on current main: filter typing focuses the match but only centers it when it is outside the viewport. The issue is already accepted in the Backlog and should remain open while the intended scope is decided.

## Change summary

Center the focused Explorer item when type-to-find runs with `workbench.list.defaultFindMode` set to `filter`, preserving context below the match.

## Best solution

Have filter-mode type navigation place the newly focused match near the viewport midpoint, while preserving existing highlight-mode and keyboard-navigation behavior. The maintainer should first decide whether this applies to every workbench tree or only the Explorer.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/tree/abstractTree.ts`, `src/vs/base/test/browser/ui/tree/objectTree.test.ts`
- **Validation:** Add a targeted browser tree test that enters filter find mode, moves focus to an already-visible match near a viewport edge, and verifies the agreed relative reveal position; run it with `scripts/test.sh --grep` using the new test title.
- **Behavior:**

  > With `workbench.list.defaultFindMode` set to `filter`, typing in the Explorer focuses the matching item and provides useful context below it by positioning it near the vertical center. This must work even when the match was already technically visible near a viewport edge. Existing highlight-mode behavior and arrow-key traversal must remain unchanged. Apply the same behavior to other workbench trees only if the maintainer chooses generic scope.
- **Trace:**

  > `FindController.applyPattern` in `src/vs/base/browser/ui/tree/abstractTree.ts` calls `tree.refilter()`, focuses the next matching node, and reveals it at `0.5` only when `getRelativeTop` returns null. That visibility guard explains why a match already on screen is focused without being recentered. `src/vs/platform/list/browser/listService.ts` supplies the configured default find mode to the shared tree widget, so changing this path may affect every workbench tree. Commit `7e2a93ab5d927a19687813dd560931c68cd9d33e` from https://github.com/microsoft/vscode/pull/180078 only changes navigation among matches and does not resolve this reveal behavior. Keep highlight mode, Alt navigation, and ordinary focus movement outside an active filter unchanged.
- **Open decisions:**
  - Should match centering apply to every workbench tree using filter find mode, or only to the Explorer?
  - Should each pattern update recenter the focused match even when focus remains on the same item, or only when filtering moves focus to a different match?

## Evidence

- **current source:** `FindController.applyPattern` in `src/vs/base/browser/ui/tree/abstractTree.ts` focuses the next matching node, but calls `tree.reveal(element, 0.5)` only when `getRelativeTop(element) === null`. An already-visible match therefore keeps its current edge position instead of being centered.
- **setting scope:** `src/vs/platform/list/browser/listService.ts` maps `workbench.list.defaultFindMode: "filter"` to the generic `TreeFindMode.Filter` used by workbench trees, so a change in the shared find controller could affect surfaces beyond the Explorer.
- **later related change:** Merged https://github.com/microsoft/vscode/pull/180078 changed navigation between filtered tree matches in commit `7e2a93ab5d927a19687813dd560931c68cd9d33e`; its diff changes focus filtering and Alt navigation, not match reveal or viewport centering.
- **canonical search:** The older and newer search results do not provide an open canonical with the same observable centering request. https://github.com/microsoft/vscode/issues/201312 concerns losing focus after expanding unmatched folders, a distinct symptom.
