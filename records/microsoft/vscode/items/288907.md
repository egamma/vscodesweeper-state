# Issue #288907 — Do not hide away thinking output if user is reading it

[https://github.com/microsoft/vscode/issues/288907](https://github.com/microsoft/vscode/issues/288907)

## Summary

Keep open: current main still auto-collapses collapsed-preview thinking without considering pointer engagement, while the discussion leaves the exact interaction unsettled. This is also a team-authored UX issue with maintainer interest, so a judgment close is not appropriate.

## Change summary

Prevent thinking output from disappearing while the user is actively reading it, while retaining an explicit way to collapse it.

## Best solution

Settle and implement an engagement-aware collapse policy in the chat thinking widget: active reading should not cause an abrupt layout change, an explicit and keyboard-accessible collapse action should remain available, and non-engaged previews should retain their current automatic behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatThinkingContentPart.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/chatContentParts/chatThinkingContentPart.test.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/media/chatThinkingContent.css`
- **Validation:** Extend the ChatThinkingContentPart browser tests to exercise the chosen engagement policy: a finishing collapsed-preview part remains expanded while actively read, its explicit keyboard-accessible action collapses it, and an unengaged part still auto-collapses.
- **Behavior:**

  > Thinking content must not disappear or cause an abrupt layout jump while the user is actively reading or interacting with it. Once automatic collapse is deferred, the user must have a clear, keyboard-accessible way to collapse the section. Thinking that is not being engaged with should retain the intended compact automatic behavior, and existing thinking-style modes must remain distinct.
- **Trace:**

  > ChatListRenderer.finalizeThinkingPart in src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts invokes ChatThinkingContentPart.collapseContent() for CollapsedPreview. That method in src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatThinkingContentPart.ts currently collapses immediately, whereas collapseContentWhenUnfocused() already protects keyboard-focused persistent reasoning. The existing test suite at src/vs/workbench/contrib/chat/test/browser/widget/chatContentParts/chatThinkingContentPart.test.ts asserts immediate collapse but has no pointer-engagement case. The closed implementation attempt at https://github.com/microsoft/vscode/pull/288908 demonstrates the likely boundary, but do not adopt its mouse-only interaction without preserving keyboard parity or change FixedScrolling and Collapsed semantics beyond the agreed policy.
- **Open decisions:**
  - Should active reading be inferred from pointer hover, explicit expansion, keyboard focus, or a combination of those signals?
  - After automatic collapse is deferred, should the section remain open until an explicit collapse action, or resume automatic behavior when engagement ends?
  - Should this behavior be the default interaction for collapsed previews or remain behind an opt-in setting?

## Evidence

- **current source:** On current main, src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts calls ChatThinkingContentPart.collapseContent() when CollapsedPreview thinking finishes, and src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatThinkingContentPart.ts implements collapseContent() as an unconditional setExpanded(false) for non-verbose tool chains; there is no pointer-hover guard.
- **partial accessibility precedent:** The same class has collapseContentWhenUnfocused(), which delays collapse while keyboard focus remains inside persistent reasoning, but finalizeThinkingPart uses that path only when suppressProgressShimmer is enabled; ordinary CollapsedPreview still collapses immediately.
- **unmerged implementation attempt:** https://github.com/microsoft/vscode/pull/288908 implemented hover-aware deferral plus an explicit Collapse button and an opt-in setting, but it was closed unmerged with review still required, so it is evidence of a bounded approach rather than a completed fix.
- **open product decision:** Maintainers discussed both the risk that cursor-dependent behavior could feel random and a Twitch-like pause-with-explicit-resume pattern at https://github.com/microsoft/vscode/issues/288907#issuecomment-3769867146 and https://github.com/microsoft/vscode/issues/288907#issuecomment-3774513239; no final interaction policy was recorded.
- **existing option is insufficient:** The reporter tested chat.agent.thinkingStyle=collapsed and explained at https://github.com/microsoft/vscode/issues/288907#issuecomment-3791301695 that it obscures progress and does not meet the central need to keep actively read content visible.
- **related issue:** https://github.com/microsoft/vscode/issues/290162 concerns selecting command text and does not report the same observable auto-collapse symptom, so it does not satisfy the stronger duplicate bar for this re-reviewed issue.
