# Issue #139937 — Add arguments property to npm tasks

[https://github.com/microsoft/vscode/issues/139937](https://github.com/microsoft/vscode/issues/139937)

## Summary

Keep this accepted Backlog request open: npm tasks still lack a separate arguments property, and the existing shell-task workaround does not deliver that capability. The related open report is newer and narrower, so it cannot replace this re-reviewed request.

## Change summary

Allow npm tasks to pass script arguments separately from the script name.

## Best solution

Provide an explicit argument contract in the built-in npm task provider that preserves literal script names and reliably forwards arguments across supported shells and script runners. Settle compatibility with the existing embedded-argument convention before implementation.

## Plan brief

- **Likely files:** `extensions/npm/package.json`, `extensions/npm/package.nls.json`, `extensions/npm/src/tasks.ts`
- **Validation:** Use a minimal package.json script that prints process.argv.slice(2), invoked through an npm preLaunchTask with separate arguments. Verify exact values for --app word, an argument containing spaces, and quotes under Windows Git Bash, PowerShell, and macOS zsh. Verify literal script names containing spaces and existing no-argument tasks remain functional, and exercise the agreed legacy embedded-argument behavior.
- **Behavior:**

  > An npm task can name a package.json script and supply its arguments separately, including the Office add-in case start:desktop with --app word. The invoked script receives the intended argument values without treating them as part of its name. Literal script names containing spaces remain usable, and tasks without arguments retain their existing behavior. Acceptance must cover exact argument values across the affected shells and the agreed compatibility behavior for legacy configurations.
- **Trace:**

  > The task schema in extensions/npm/package.json and INpmTaskDefinition in extensions/npm/src/tasks.ts expose script and path, but no separate arguments. NpmTaskProvider.resolveTask delegates to createScriptRunnerTask; getRunScriptCommand appends the whole script string, and escapeCommandLine applies a ---dependent quoting heuristic before ShellExecution. This source inspection establishes the missing capability, not a runtime verification of every historical shell failure. The provider also selects npm, yarn, pnpm, bun, node, or vp, so argument forwarding is a user-visible contract across runners. Preserve task-definition identity, package-directory resolution, detected tasks without arguments, and existing script-name support. https://github.com/microsoft/vscode/issues/115876 documents why the embedded -- convention exists; https://github.com/microsoft/vscode/issues/176277 supplies additional shell-specific cases. The uncertainty is compatibility and forwarding semantics, not whether automationProfile shell arguments solve the request.
- **Open decisions:**
  - When a task supplies explicit args, is script always treated as a literal script name, and what happens if script also contains the legacy embedded -- argument convention?
  - Does args represent arguments forwarded to the selected script consistently across script runners, or also permit runner-level options, and what separator behavior is part of that contract?

## Evidence

- **Maintainer-established scope:** In https://github.com/microsoft/vscode/issues/139937, the maintainer confirmed the Git Bash reproduction on 2022-01-07 and explicitly repurposed the report as support for an args property. The 2022-07-01 clarification says these arguments belong to the npm command, not the automation shell.
- **Capability remains missing:** extensions/npm/package.json contributes only script and path properties for npm task definitions. INpmTaskDefinition in extensions/npm/src/tasks.ts likewise declares only script and path; NpmTaskProvider.resolveTask passes kind.script to createScriptRunnerTask without forwarding a separate arguments property.
- **Current command construction:** In extensions/npm/src/tasks.ts:308-349, getRunScriptCommand appends the entire script string as one argument, and escapeCommandLine chooses weak or strong quoting based on whitespace and the presence of --. This existing compatibility mechanism is not a separate script-argument API.
