# Issue #337720 — Copilot Plan review handoff continues with the planning model after the model is changed

[https://github.com/microsoft/vscode/issues/337720](https://github.com/microsoft/vscode/issues/337720)

## Summary

Fresh, well-documented report with a clean repro and a harness comparison; tracing the agent-host Copilot code shows a plausible concrete mechanism (model changes and the in-flight turn share one FIFO per-chat queue), so this stays open pending a maintainer decision on the intended behavior.

## Change summary

In the Copilot Chat harness, switching the selected model after a plan is generated but before approving it does not affect the model used for the implementation continuation — it still uses the planning model.

## Best solution

Either make a model change requested during a pending plan review apply to the post-approval implementation continuation of that same turn, or — if the planning model is meant to stay locked for that turn — make the model picker communicate that lock instead of silently accepting a selection that has no effect.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerActionItem.ts`
- **Validation:** A copilotAgent(.Session) test that starts a turn, triggers a plan-review pause, calls `setModel`/`changeModel` while paused, then submits the plan-review answer, asserting the implementation continuation observes the newly selected model.
- **Behavior:**

  > When a user changes the selected model in the Copilot harness while a plan review is pending, the subsequent implementation ('Start implementation'/'Proceed with the implementation') should use the model selected at that point, not the model that produced the plan — matching the Local harness's behavior. If the planning model is deliberately locked for the remainder of that turn, the UI should make that clear rather than accepting a selection that silently has no effect.
- **Trace:**

  > `_changeModelOnce` in copilotAgent.ts queues its work via `this._queueChat(configurationId, sequencerKey, 'changeModel', ...)` (~line 5419), sharing the same per-chat `SequencerByKey` FIFO queue (`CopilotSessionLifetime.queueChat`, ~line 449) that `_queueChatTurn` uses for `'sendMessage'`/`'resumeTurn'` (~line 5212). The plan-review answer resolves an in-flight promise inside that already-running turn task (see the input-request wiring in copilotAgentSession.ts ~line 7150 and `handleSubmit`/`review.completion` in chatListRenderer.ts ~line 5227) rather than dispatching a new queued operation, so a `changeModel` call issued while the turn is paused for review is stuck behind it and only executes once the turn (including the approved implementation) completes. Boundary: this is scoped to the Copilot-harness `changeModel` vs. paused-turn interaction — don't alter the sequencer's general FIFO semantics for other operations, and don't touch the Local harness's (unaffected) model-switch path. Where the uncertainty starts: whether the intended fix reorders/preempts the queue for this case, or whether the model should simply stay locked with clearer UI feedback — the issue text itself proposes both options.
- **Open decisions:**
  - Should a model change requested while a plan review is pending immediately apply to the implementation continuation of that same turn, overriding the model that produced the plan?
  - If the planning model is meant to stay locked for the remainder of the turn, should the model picker be disabled or annotated while a plan review is pending so users don't believe an ineffective selection took effect?

## Evidence

- **shared chat queue:** src/vs/platform/agentHost/node/copilot/copilotAgent.ts `_changeModelOnce` (~line 5419) calls `this._queueChat(context.configurationId, context.sequencerKey, 'changeModel', ...)`, which runs on the same per-chat `SequencerByKey` (`CopilotSessionLifetime.queueChat`, ~line 449) used by `_queueChatTurn` for the `'sendMessage'`/`'resumeTurn'` operations (~line 5212).
