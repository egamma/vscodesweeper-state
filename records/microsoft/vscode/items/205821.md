# Issue #205821 — Option to auto-expand groups in variables panel while debugging

[https://github.com/microsoft/vscode/issues/205821](https://github.com/microsoft/vscode/issues/205821)

## Summary

A real gap remains on current main: the Variables view expands only the first non-expensive scope, while the existing lazy-variable setting controls a different behavior. The request has explicit maintainer interest but unresolved expansion and performance semantics, so it should remain open under discussion.

## Change summary

Provide an option or action that exposes relevant collapsed scope groups in the debug Variables view without requiring trial-and-error expansion.

## Best solution

Add an opt-in, discoverable scope-expansion control that exposes relevant non-expensive scopes while avoiding costly scopes and preserving explicit user expansion choices across stops where scope identity remains stable.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/variablesView.ts`, `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`, `src/vs/workbench/contrib/debug/common/debug.ts`, `src/vs/workbench/contrib/debug/test/browser/variablesView.test.ts`
- **Validation:** Extend the `Debug - Variable Debug View` browser unit suite and run `scripts/test.sh --grep "Debug - Variable Debug View"`; the final tests should cover the selected scope-expansion policy, exclusion of expensive scopes, and preservation of explicit user expansion state.
- **Behavior:**

  > The Variables view should provide a discoverable way to expose relevant scope groups without requiring users to open similarly named Block groups one by one. Scope data marked expensive must not be fetched automatically unless the chosen user-facing contract explicitly permits it. Explicit expansion or collapse choices should remain stable across debug stops whenever VS Code can correlate the scopes. Existing lazy-variable expansion behavior must remain independent.
- **Trace:**

  > VariablesView in src/vs/workbench/contrib/debug/browser/variablesView.ts restores `savedViewState`, retrieves the focused frame's scopes, and expands only the first scope for which `expensive` is false. The same file exposes `Collapse All` but no Expand All action. Scope identity and range information are built in StackFrame.getScopes in src/vs/workbench/contrib/debug/common/debugModel.ts, while DebugProtocol.Scope documents `expensive` as indicating that retrieving the scope may be large or costly. `debug.autoExpandLazyVariables` flows through debug.contribution.ts, common/debug.ts, debugSession.ts, and debugModel.ts but applies to lazy variable children, so it must not be repurposed. Historical discussion at https://github.com/microsoft/vscode/issues/93230 considered expanding every non-expensive scope but did not settle the UX or performance policy; the current issue's maintainers likewise left that decision open.
- **Open decisions:**
  - Should the user-facing control be a persistent auto-expand setting, a one-shot Expand All action, or both?
  - Should automatic expansion include every non-expensive scope, only Block or source-range-relevant scopes, or another bounded subset?
  - When a user explicitly collapses a scope, should that choice override automatic expansion for later stops in the same session?

## Evidence

- **current source:** src/vs/workbench/contrib/debug/browser/variablesView.ts sets the restored tree input and then expands only `scopes.find(s => !s.expensive)`; additional non-expensive Block scopes remain collapsed.
- **existing setting is different:** The `debug.autoExpandLazyVariables` registration in src/vs/workbench/contrib/debug/browser/debug.contribution.ts explicitly covers lazily resolved variables such as getters, not top-level debug scopes.
- **no existing expand action:** src/vs/workbench/contrib/debug/browser/variablesView.ts registers a Variables-view `Collapse All` action but no corresponding Expand All action.
- **maintainer assessment:** Maintainers in https://github.com/microsoft/vscode/issues/205821 state that the behavior is bothersome, that js-debug marks only Global as expensive, and that changing the behavior in VS Code core should be considered.
- **historical context:** https://github.com/microsoft/vscode/issues/93230 addressed unstable view-state preservation and first-scope expansion, but its discussion left expanding all non-expensive scopes unresolved because of behavior and cost concerns.
- **related but not duplicate:** https://github.com/microsoft/vscode/issues/179742 is older and open, but it concerns automatically resolving lazy variable children rather than expanding collapsed scope groups, so it does not satisfy the re-review same-symptom duplicate bar.
