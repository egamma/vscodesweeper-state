# Issue #341834 — Restored terminal sessions display incorrect command line in terminal information popup

[https://github.com/microsoft/vscode/issues/341834](https://github.com/microsoft/vscode/issues/341834)

## Summary

Thanks for the report. The cause is visible in the source. On restore, a terminal has no executable in its launch config, so the default profile (pwsh) is filled in, and the tooltip then shows that executable instead of the restored process's own. The reporter retested on 1.142.0 and still sees it.

## Change summary

Restored terminals all show the default profile's command line in the info tooltip instead of their own shell's.

## Best solution

Don't overwrite the executable and args with the default profile when the terminal is reattaching to a persistent process. Alternatively, populate the real executable and args from the persisted process data and show those in the tooltip.

- **Likely files:** `src/vs/workbench/contrib/terminal/browser/terminalInstance.ts`, `src/vs/workbench/contrib/terminal/browser/terminalTooltip.ts`
- **Validation:** Add a unit test for the terminal instance or tooltip. A terminal created with attachPersistentProcess and no executable must not take the default profile's path and args as its shellLaunchConfig. The test should fail before the change and pass after it.
- **Behavior:**

  > After restoring terminals that use different shells, such as Windows PowerShell 5.1 and PowerShell 7, each terminal's info tooltip must show its own process's executable. It must not show the default profile's. Terminals newly created without an executable keep getting the default profile as they do today. Acceptance: a reattached instance does not have its executable replaced by the default profile, and the existing terminal tests pass.
- **Trace:**

  > In TerminalInstance, after the xterm is ready, shellLaunchConfig.executable, args, icon, color and env are populated from getDefaultProfile() whenever shell integration is enabled and executable is empty. This runs even when shellLaunchConfig.attachPersistentProcess is set. The tooltip in terminalTooltip.ts then reads that executable. The boundary is this restore/reattach path: do not change how new terminals resolve the default profile. Whether the real executable is available from the persisted process data needs a check, since it may only be partly stored. If it is not, hiding the command line for reattached terminals is an acceptable conservative default.

## Evidence

- **tooltip source:** src/vs/workbench/contrib/terminal/browser/terminalTooltip.ts (getShellProcessTooltip) builds 'Command line' from instance.shellLaunchConfig.executable and args. It does not use the actual process.
- **root cause:** src/vs/workbench/contrib/terminal/browser/terminalInstance.ts, around lines 563-568: with shell integration enabled and no executable set, shellLaunchConfig.executable and args are set from getDefaultProfile(). The guard does not exclude attachPersistentProcess, so a reconnected terminal gets the default profile's path. The default profile is presumably PowerShell 7 here. I traced this in the source but did not run it.
- **reporter retest:** The reporter confirmed on 1.142.0 that the behaviour is unchanged. The PIDs are correct, which fits the process being right and only the displayed launch config being wrong.
