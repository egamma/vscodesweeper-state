# Issue #23991 — Keyboard mappings with `setxkbmap` on Linux not working

[https://github.com/microsoft/vscode/issues/23991](https://github.com/microsoft/vscode/issues/23991)

## Summary

The Linux remapping defect remains necessary to track: multiple users confirmed it across releases, the `keyboard.dispatch: keyCode` workaround has behavioral trade-offs, and a maintainer identified the X11/native-keymap implementation boundary. The Backlog milestone does not block a merits-based close, but there is no fixing commit or verified canonical issue supporting one.

## Change summary

VS Code's default keyboard dispatch can ignore XKB remappings such as mapping Caps Lock to Escape, while other Linux applications honor them.

## Best solution

Keep the issue as the canonical Linux key-remapping bug and investigate the native keyboard-layout/event translation boundary between VS Code and `microsoft/node-native-keymap`. The intended result is for default dispatch to honor XKB remappings without forcing users into `keyCode` mode and thereby changing unrelated shortcut positions.

## Plan brief

- **Likely files:** `src/vs/workbench/services/keybinding/browser/keyboardLayoutService.ts`, `src/vs/workbench/services/keybinding/browser/keyboardMapperFactory.ts`, `src/vs/workbench/services/keybinding/browser/keyboardLayouts`
- **Validation:** On Linux/X11, run `setxkbmap -option caps:escape`, restart VS Code, and use the keyboard-shortcuts troubleshooting output to verify that Caps Lock is interpreted as Escape under the default dispatch mode while ordinary shortcuts retain their configured logical layout; repeat with `keyboard.dispatch: keyCode` as a compatibility baseline.
- **Behavior:**

  > On Linux/X11, an XKB remapping such as `caps:escape` should be honored by VS Code's default keyboard dispatch, as it is by other native applications. Pressing the remapped Caps Lock key must produce Escape behavior in the editor and extensions, while the physical Escape key continues to work. The result must not require `keyboard.dispatch: keyCode` or cause unrelated shortcuts to move with the active layout.
- **Trace:**

  > The original regression starts with VS Code 1.11 and is reproducible with `setxkbmap -option caps:escape`; later comments confirm the same class of failure for Caps Lock-to-Backspace and Colemak mappings. VS Code exposes `keyboard.dispatch` as a choice between physical `code` handling and legacy `keyCode`; `keyCode` is only a workaround because it changes how other shortcuts are interpreted. A maintainer traced Linux layout support to the X11 implementation in https://github.com/microsoft/node-native-keymap and described the native XKB complexity. Investigation should begin at the workbench keyboard-layout mapper and its native-keymap data, while preserving keyboard behavior on Windows, macOS, web clients, and users without XKB remappings. The uncertainty starts at whether native-keymap lacks the effective remapped symbol data or whether VS Code discards it while constructing or applying the mapper.
- **Open decisions:**
  - Can the effective XKB remapping be represented by the existing native-keymap layout payload, or does microsoft/node-native-keymap require an API/data-model change?
  - Should logical remappings affect only resolved key values while preserving physical-code shortcut positions, and how should modifier remappings be represented?
  - Which X11 configurations beyond `caps:escape` must form the compatibility matrix before changing default dispatch behavior?

## Evidence

- **confirmed regression:** The report gives a concrete X11 reproduction using `setxkbmap -option caps:escape`, and commenters continued confirming equivalent XKB remapping failures through VS Code 1.55.2 and December 2023.
- **maintainer diagnosis:** A VS Code maintainer explained that the relevant implementation depends on X11 keyboard-map handling in https://github.com/microsoft/node-native-keymap and cited prior changes there, establishing that this is a known core/native-keymap integration problem rather than a Vim-extension defect.
- **incomplete workaround:** `keyboard.dispatch: keyCode` restores remapped-key behavior for several commenters, but one Colemak user reports that it also remaps all shortcuts according to the layout; this does not satisfy the central request under the default dispatch mode.
- **current relevance:** The June 2024 discussion confirms the workaround still applies on Plasma 6/X11, while the underlying default-dispatch behavior remains unresolved; lower-level remappers such as interception-tools and evremap are external workarounds.
- **related implementation:** https://github.com/microsoft/node-native-keymap/pull/19 added support for specific XKB level-shift symbols, but the supplied timeline does not identify it as a complete fix for arbitrary `setxkbmap` remappings in this issue.
