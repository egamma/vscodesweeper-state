# Issue #23991 — Keyboard mappings with `setxkbmap` on Linux not working

[https://github.com/microsoft/vscode/issues/23991](https://github.com/microsoft/vscode/issues/23991)

## Summary

This remains a well-confirmed Linux keybinding correctness bug: VS Code's default `code` dispatch does not consistently honor XKB remappings, while the `keyCode` compatibility mode is only a workaround with different shortcut semantics.

## Change summary

Honor Linux XKB keyboard remappings such as Caps Lock-to-Escape without requiring users to switch keybinding dispatch modes or redefine shortcuts.

## Best solution

Keep the issue open as the canonical Linux keymap-remapping defect and fix the native keyboard-layout resolution path, likely spanning VS Code's keyboard mapper and `microsoft/node-native-keymap`, while preserving physical-key shortcut behavior for users who rely on `code` dispatch.

## Plan brief

- **Likely files:** `src/vs/workbench/services/keybinding/browser/keyboardLayoutService.ts`, `src/vs/workbench/services/keybinding/browser/keyboardMapperFactory.ts`, `src/vs/workbench/services/keybinding/browser/nativeKeyboardLayout.ts`
- **Validation:** On Linux/X11, run `setxkbmap -option caps:escape`, restart VS Code with the default `keyboard.dispatch: "code"`, and verify through the Keyboard Shortcuts Troubleshooting output plus an Escape-bound command that Caps Lock is resolved as Escape while ordinary layout-dependent and physical-key shortcuts retain their existing behavior.
- **Behavior:**

  > With an XKB remapping such as `setxkbmap -option caps:escape`, VS Code should interpret Caps Lock as Escape consistently with other native applications under the default keyboard dispatch mode. Users should not need to switch to the legacy `keyCode` mode, redefine individual shortcuts, or use a lower-level remapping daemon. Existing physical-key shortcut behavior for layouts without such remappings must remain unchanged.
- **Trace:**

  > The report is a regression from VS Code 1.10 to 1.11 and has repeated independent confirmations. VS Code's `keyboard.dispatch: "keyCode"` path can expose the remapped logical key, while the default `code` path relies on VS Code's keyboard-layout mapping and the native `microsoft/node-native-keymap` data; comments show that selecting the former changes unrelated shortcut semantics, so it is not full coverage. The likely VS Code entry points are the native keyboard layout and mapper services under `src/vs/workbench/services/keybinding/browser/`, with X11/XKB decoding potentially owned by https://github.com/microsoft/node-native-keymap. Keep Wayland-only behavior and extension-specific Vim handling outside the initial X11 acceptance boundary; the core repro is a native Escape-bound command after `setxkbmap`.
- **Open decisions:**
  - Should logical XKB remappings override physical `code` dispatch for all remapped keys, or should VS Code expose a third dispatch mode based on the event's logical `key` value while preserving the existing `code` and `keyCode` contracts?

## Evidence

- **current classification:** The issue remains open in the Backlog with existing `bug`, `help wanted`, `keybindings`, and `linux` labels and has 287 community upvotes.
- **confirmed reports:** Multiple commenters independently confirmed XKB remappings being ignored across Ubuntu, Arch, Pop!_OS, and KDE setups through December 2023; the June 2024 exchange ultimately reconfirmed the compatibility workaround rather than a core fix.
- **partial workaround:** `keyboard.dispatch: "keyCode"` restores remapped keys for several reporters, but comments document that it remaps other shortcuts according to the layout and therefore does not satisfy the central request under the default `code` dispatch.
- **maintainer diagnosis:** A VS Code maintainer identified the relevant X11/native-keymap complexity and linked work in https://github.com/microsoft/node-native-keymap; this supports a real native keyboard mapping defect rather than an extension-specific problem.
- **related native-keymap work:** https://github.com/microsoft/node-native-keymap/pull/19 added support for additional XKB level-shift symbols, but neither the related-item record nor the discussion establishes that it fixes arbitrary `setxkbmap` remappings reported here.
- **canonical scope:** Later reports for Caps Lock/Escape, Backspace, and other remapped keys reference this issue, indicating that it remains the broad canonical report rather than a satellite suitable for duplicate closure.
