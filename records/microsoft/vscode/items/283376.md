# Issue #283376 — Decouple extension activation and auth

[https://github.com/microsoft/vscode/issues/283376](https://github.com/microsoft/vscode/issues/283376)

## Summary

Keep open: current main still couples extension activation to authentication or BYOK readiness, and the earlier decoupling attempt was reverted after breaking the signed-out chat flow. This team-authored debt item remains the designated home for resolving that lifecycle contract.

## Change summary

Separate Copilot extension activation from GitHub authentication while preserving correct provider, participant, BYOK, and signed-out setup behavior.

## Best solution

Make extension activation finish after the contributions required by activation events are registered, while independently updating authenticated chat capabilities as auth and model availability change. The design must preserve a functional signed-out first-message flow and clearly define what dependent extensions may assume after awaiting activation.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/extension/vscode/extension.ts`, `extensions/copilot/src/extension/common/contributions.ts`, `extensions/copilot/src/extension/conversation/vscode-node/conversationFeature.ts`, `extensions/copilot/src/extension/conversation/vscode-node/languageModelAccess.ts`, `extensions/copilot/src/extension/conversation/vscode-node/test/conversationFeature.test.ts`, `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts`, `src/vs/workbench/contrib/chat/common/languageModels.ts`
- **Validation:** Add targeted extension and chat-service tests proving that activation completes without GitHub auth, activation-event consumers receive the promised registrations, BYOK remains usable, and a signed-out first chat request enters the setup/sign-in experience instead of failing with a missing participant or model.
- **Behavior:**

  > Awaiting Copilot Chat extension activation must not wait indefinitely for GitHub sign-in. Signed-in, signed-out, anonymous-access, and BYOK users must still reach the appropriate chat experience, and sending a first message while signed out must offer the established setup/sign-in flow rather than fail because an agent or model is absent. Extensions that await Copilot activation need a documented, testable readiness guarantee.
- **Trace:**

  > baseActivate in extensions/copilot/src/extension/extension/vscode/extension.ts waits for every IExtensionContribution.activationBlocker collected by ContributionCollection. ConversationFeature in extensions/copilot/src/extension/conversation/vscode-node/conversationFeature.ts still ties its blocker and contribution enablement to Copilot-token, BYOK-model, and authentication-change state; LanguageModelAccess also contributes a blocker while registering model and embedding providers. Core's ChatService.activateDefaultAgent in src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts awaits extension activation and then expects the default agent to exist, while LanguageModelsService has the analogous provider expectation. The earlier nonblocking implementation in https://github.com/microsoft/vscode-copilot-chat/pull/1266 exposed the signed-out regression documented at https://github.com/microsoft/vscode/issues/275511 and was reverted by https://github.com/microsoft/vscode-copilot-chat/pull/1860. Preserve current signed-in, anonymous, and BYOK behavior; do not weaken activation-event readiness accidentally or reintroduce the missing-participant failure.
- **Open decisions:**
  - After dependent extensions await Copilot Chat activation, must chat participants and language-model providers already be registered, or does activation guarantee only that the extension's services and listeners are installed?
  - When GitHub authentication is absent, should the normal participant remain registered and initiate sign-in on invocation, or should core continue routing the request through the setup participant until authentication becomes available?
