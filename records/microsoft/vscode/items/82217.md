# Issue #82217 — Clarify that proxy settings are only applied to extensions

[https://github.com/microsoft/vscode/issues/82217](https://github.com/microsoft/vscode/issues/82217)

## Summary

The documentation gap remains on current main: `http.proxySupport` explicitly mentions extensions, but the related proxy and certificate settings still use broader descriptions that do not identify their consumers. The original blanket clarification is now outdated because these settings also feed newer core and Agent Host paths, so the issue should stay open for an accurate per-setting clarification.

## Change summary

Clarify which VS Code network consumers are affected by each HTTP proxy and certificate setting, and distinguish them from the Chromium command-line proxy used by other application traffic.

## Best solution

Update the HTTP configuration descriptions in `src/vs/platform/request/common/request.ts` to state the current scope of each setting, including the distinction between extension-host proxy support and application-level traffic. First confirm the modern consumers in the request service, extension-host proxy resolver, and Agent Host so the documentation does not repeat the now-inaccurate claim that every proxy setting applies only to extensions.

## Plan brief

- **Likely files:** `src/vs/platform/request/common/request.ts`, `src/vs/platform/request/node/requestService.ts`, `src/vs/workbench/api/node/proxyResolver.ts`, `src/vs/platform/agentHost/node/devContainerAgentHostService.ts`
- **Validation:** Inspect the HTTP settings in the Settings editor and confirm that each proxy/certificate description accurately distinguishes extension-host, core request-service, Agent Host, and Chromium command-line proxy behavior without changing runtime behavior.
- **Behavior:**

  > The Settings editor should tell users which network traffic each HTTP proxy and certificate setting affects. It must make clear when a setting affects extension-host requests and when it also affects newer core or Agent Host consumers, while distinguishing these settings from Chromium's `--proxy-server` handling. Acceptance requires that a user can determine from the descriptions whether changing a setting will affect extension installation and other application traffic.
- **Trace:**

  > `src/vs/platform/request/common/request.ts` registers the HTTP settings: only `http.proxySupport` explicitly says "for extensions," while the related descriptions remain generic. The extension-host path reads these settings in `src/vs/workbench/api/node/proxyResolver.ts`; the core request service reads proxy configuration in `src/vs/platform/request/node/requestService.ts`; newer Agent Host code also consumes synchronized proxy configuration. Commit https://github.com/microsoft/vscode/commit/3e399f14424384f736824338a6179c103e30160e shows that the extension wording predates the issue, while https://github.com/microsoft/vscode/commit/0d5a370187eae4e10390c7f50cf952e260050cb2 demonstrates subsequent scope expansion. Keep runtime proxy behavior and defaults out of scope; this issue is about accurately documenting the existing contract.
- **Open decisions:**
  - For each HTTP proxy and certificate setting, which user-observable network consumers should the Settings UI promise are affected: extension hosts only, core request-service callers, Agent Host, or a defined combination?
  - Should the descriptions explicitly state that Chromium-level application traffic requires command-line or operating-system proxy configuration when it is not routed through VS Code's request service?

- **historical wording:** Commit https://github.com/microsoft/vscode/commit/3e399f14424384f736824338a6179c103e30160e introduced the extension-specific `http.proxySupport` wording in 2018, before this report, so that wording is not a post-report fix for https://github.com/microsoft/vscode/issues/82217.

A blanket "extensions only" description would therefore no longer be accurate.
