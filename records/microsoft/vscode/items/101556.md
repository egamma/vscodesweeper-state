# Issue #101556 — [themes] 'Generate Color Theme From Current Settings' omits semantic token settings

[https://github.com/microsoft/vscode/issues/101556](https://github.com/microsoft/vscode/issues/101556)

## Summary

The gap remains on current main: the generated theme includes workbench colors and TextMate token colors but no semantic-token colors. The On Deck milestone and later maintainer acknowledgment support keeping this open for a scoped design and implementation.

## Change summary

Include semantic token highlighting state and color rules when generating a color theme from the current settings.

## Best solution

Make the generated theme preserve the active semantic highlighting behavior in valid color-theme fields, with tests covering customized semantic selectors and highlighting enablement.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/themes/browser/themes.contribution.ts`, `src/vs/workbench/services/themes/common/workbenchThemeService.ts`, `src/vs/workbench/services/themes/common/colorThemeData.ts`
- **Validation:** Add a targeted theme-generator test that applies `editor.semanticTokenColorCustomizations`, generates the theme object, and verifies that reloading it preserves the configured semantic selector styles and highlighting-enabled state; run it with `scripts/test.sh --grep "Generate Color Theme From Current Settings"`.
- **Behavior:**

  > Generating a color theme from current settings must preserve active semantic-token styling in fields accepted by the color-theme schema. A generated theme loaded without the original user customizations must retain the same customized semantic selector colors, font styles, and semantic-highlighting state. Existing workbench-color and TextMate-token export behavior must remain unchanged.
- **Trace:**

  > The command `workbench.action.generateColorTheme` in src/vs/workbench/contrib/themes/browser/themes.contribution.ts builds a JSON object containing `colors` and `theme.tokenColors` only. ColorThemeData in src/vs/workbench/services/themes/common/colorThemeData.ts separately stores theme and customized semantic rules, but those collections are private; IWorkbenchColorTheme in src/vs/workbench/services/themes/common/workbenchThemeService.ts exposes only the TextMate `tokenColors` collection. The loader already consumes the theme-file fields `semanticHighlighting` and `semanticTokenColors`, so the missing path is export-side. Preserve the existing generated workbench-color and TextMate-token structure, and do not change semantic token resolution during normal editing. The related report https://github.com/microsoft/vscode/issues/200448 confirms the omission but does not supersede this issue.
- **Open decisions:**
  - Should the generated theme flatten the complete effective semantic-token rule set, including rules inherited from the active base theme, or emit only the user's active semantic-token customizations alongside the base theme's existing behavior?

## Evidence

- **current source:** In src/vs/workbench/contrib/themes/browser/themes.contribution.ts, `workbench.action.generateColorTheme` serializes only `$schema`, `type`, `colors`, and `tokenColors`; it does not emit `semanticHighlighting` or `semanticTokenColors`.
- **semantic customization path:** src/vs/workbench/services/themes/common/colorThemeData.ts applies `editor.semanticTokenColorCustomizations` into private `customSemanticTokenRules` and `customSemanticHighlighting`, while `IWorkbenchColorTheme` in src/vs/workbench/services/themes/common/workbenchThemeService.ts exposes `tokenColors` but no corresponding semantic-rule export surface.

- **related issue:** https://github.com/microsoft/vscode/issues/200448 is newer and closed after redirecting its semantic-color symptom here, so it is corroborating evidence rather than an older open canonical for this re-reviewed item.
- **routing and interest:** The issue remains labeled `feature-request` and `themes` in the On Deck milestone, and two later commenters reported that the missing export still affected their theme-authoring workflow.
