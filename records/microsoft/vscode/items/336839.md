# Issue #336839 — Ensure enterprise Copilot OTel settings override environment variables

[https://github.com/microsoft/vscode/issues/336839](https://github.com/microsoft/vscode/issues/336839)

## Summary

Still open on main: resolveOTelConfigFromSettings passes policy-backed defaults through the ordinary setting* inputs (only policyCaptureIdentity and policyResourceAttributes use the policy lane), so COPILOT_OTEL_* / OTEL_EXPORTER_OTLP_* environment variables continue to outrank managed OTel values for enablement, endpoint, protocol, exporter type, outfile, service name and headers.

## Change summary

Enterprise-managed Copilot OTel settings can be disabled or redirected by process environment variables because policy provenance is lost in the VS Code settings resolver.

## Best solution

In extensions/copilot/src/platform/otel/common/otelConfigResolution.ts, preserve per-field policy provenance for the recognized enterprise OTel block and feed those values through the existing policy* inputs of resolveOTelConfig, with regression coverage for managed-over-env precedence (endpoint redirection and file-export diversion).

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/otel/common/otelConfigResolution.ts`, `extensions/copilot/src/platform/otel/common/otelConfig.ts`, `extensions/copilot/src/platform/otel/common/test/otelConfigResolution.spec.ts`
- **Validation:** Tests in extensions/copilot/src/platform/otel/common/test/otelConfigResolution.spec.ts asserting that, with a recognized enterprise OTel block, COPILOT_OTEL_ENABLED=false does not disable export, OTEL_EXPORTER_OTLP_ENDPOINT does not redirect the endpoint, and COPILOT_OTEL_FILE_EXPORTER_PATH does not divert to file export — failing before the change, passing after.
- **Behavior:**

  > When enterprise policy supplies Copilot OTel configuration, the managed values govern enablement, exporter type, OTLP endpoint and protocol, content capture, service name, outfile, and resource attributes/headers on key collisions; process environment variables can no longer disable telemetry, redirect it to another collector, or divert it to a file. Environment variables may still supply fields the policy genuinely omits, per the contract the maintainer settles. Acceptance: new precedence tests in otelConfigResolution.spec.ts pass (managed-over-env for enablement, endpoint redirection, and file-export diversion) and the existing otelConfig/otelConfigResolution suites still pass, including the captureIdentity omission-vs-denial semantics.
- **Trace:**

  > resolveOTelConfig in extensions/copilot/src/platform/otel/common/otelConfig.ts already implements policy > env > setting across every affected field (enabled ~l.146-165, protocol ~l.176-190, endpoint ~l.197-204, fileExporterPath ~l.205-210, exporterType ~l.214-224, captureContent ~l.226-230, serviceName ~l.252-256, resourceAttributes/headers ~l.258-271). The loss happens one layer up in resolveOTelConfigFromSettings (extensions/copilot/src/platform/otel/common/otelConfigResolution.ts): policy-backed values arrive via settings.inspect(key).defaultValue, are collapsed into an all-or-nothing hasEnterpriseSettings flag and a `read()` helper, then passed as settingEnabled/settingExporterType/settingOtlpEndpoint/settingProtocol/settingOutfile/settingServiceName/settingHeaders — so the policy* inputs stay undefined and env wins; rg confirms no production caller sets policyEnabled/policyOtlpEndpoint/policyServiceName/policyHeaders. captureIdentity already shows the intended shape (null sentinel distinguishing omission from managed denial, passed as policyCaptureIdentity), and normalizePolicyDefaultValue encodes the shared CopilotOtelEndpoint quirk where an unconfigured policy slot surfaces as ''. Boundary: do not change resolveOTelConfig's documented precedence order, the captureIdentity omission-vs-denial semantics, the '' endpoint normalization, or classifyOTelConfigDrift's reliance on defaultValues. Related: https://github.com/microsoft/vscode/issues/336701.
- **Open decisions:**
  - Inside a recognized enterprise OTel block, does a field left at its schema default count as managed (env locked out) or as omitted by policy (env may still supply it)?
  - Should policy enablement be authoritative in both directions — i.e. does a managed enabled=false hard-disable telemetry even when COPILOT_OTEL_ENABLED=true, given a schema default of false is indistinguishable from omission today?
  - For resourceAttributes and headers, do managed keys win per-key while env contributes other keys (current merge semantics), or does a managed block replace the map entirely?
