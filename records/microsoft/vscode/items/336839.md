# Issue #336839 — Ensure enterprise Copilot OTel settings override environment variables

[https://github.com/microsoft/vscode/issues/336839](https://github.com/microsoft/vscode/issues/336839)

## Summary

Confirmed on main: `resolveOTelConfigFromSettings` in otelConfigResolution.ts recognizes enterprise-managed OTel values (`hasEnterpriseSettings`) but wires almost all of them into the `setting*` inputs of `resolveOTelConfig` instead of the `policy*` inputs — so `COPILOT_OTEL_ENABLED`/`OTEL_EXPORTER_OTLP_ENDPOINT`/etc. still outrank policy for enablement, exporter type, endpoint, content capture, service name, and headers. `resolveOTelConfig` itself already implements correct policy>env>setting precedence, it's just fed the wrong channel. This has privacy/compliance implications (env vars can re-enable content capture or redirect telemetry despite a managed denial), so I'm keeping it at keep-open with no automated readiness rather than fast-tracking a fix.

## Change summary

Ensure enterprise-managed Copilot OTel policy settings (enablement, exporter/endpoint, content capture, service name, resource attributes/headers) take precedence over `COPILOT_OTEL_*`/`OTEL_EXPORTER_OTLP_*` environment variables, matching the already-correct policy>env>setting precedence built into `resolveOTelConfig`.

## Best solution

In extensions/copilot/src/platform/otel/common/otelConfigResolution.ts, route recognized managed values through `policyEnabled`/`policyExporterType`/`policyOtlpEndpoint`/`policyCaptureContent`/`policyOutfile`/`policyProtocol`/`policyServiceName`/`policyHeaders` (mirroring what's already done for `captureIdentity`/`resourceAttributes`) instead of `setting*`, and update the `otelConfigResolution.spec.ts` test that currently asserts env vars can override a managed `enabled`/`otlpEndpoint` ("preserves existing effective-setting resolution and env precedence") to assert the opposite.

## Evidence

- **resolver bug:** extensions/copilot/src/platform/otel/common/otelConfigResolution.ts: `read()` merges managed defaults into `settingEnabled`, `settingExporterType`, `settingOtlpEndpoint`, `settingCaptureContent`, `settingOutfile`, `settingProtocol`, `settingServiceName`, `settingHeaders` — none of the corresponding `policy*` fields of `OTelConfigInput` (checked via `grep -n "policyEnabled|policyExporterType|policyOtlpEndpoint..."`, no matches in that file except `policyCaptureIdentity`/`policyResourceAttributes`).
- **resolveOTelConfig already correct:** extensions/copilot/src/platform/otel/common/otelConfig.ts implements policy > env > setting precedence for every field (e.g. `enabledSignal = input.policyEnabled ?? envBool(env['COPILOT_OTEL_ENABLED']) ?? input.settingEnabled ...`), so the only gap is the caller's wiring.
- **existing test codifies the gap:** otelConfigResolution.spec.ts, test 'preserves existing effective-setting resolution and env precedence' asserts `COPILOT_OTEL_ENABLED: 'false'` disables a policy-enabled config, and `OTEL_EXPORTER_OTLP_ENDPOINT` overrides a managed `otlpEndpoint` — exactly the behavior the issue reports as wrong.
- **related issue:** https://github.com/microsoft/vscode/issues/336701 is cited as documenting this as an accepted gap while fixing a separate late-policy-initialization race; worth checking for overlap but it addresses a different symptom (init race, not env precedence).
