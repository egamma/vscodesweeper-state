# Issue #336839 — Ensure enterprise Copilot OTel settings override environment variables

[https://github.com/microsoft/vscode/issues/336839](https://github.com/microsoft/vscode/issues/336839)

## Summary

Confirmed from source: `resolveOTelConfigFromSettings` in otelConfigResolution.ts feeds managed OTel values into the `setting*` inputs of `resolveOTelConfig` instead of the `policy*` inputs, so for enabled/exporterType/otlpEndpoint/captureContent/outfile/protocol/serviceName/headers, `COPILOT_OTEL_*`/`OTEL_EXPORTER_OTLP_*` env vars outrank enterprise policy — the opposite of the documented 'policy > env > setting' precedence in otelConfig.ts. This is a real, still-open gap, not fixed on main.

## Change summary

Environment variables can currently override enterprise-managed Copilot OTel policy settings (enablement, endpoint, headers, etc.) instead of policy taking precedence.

## Best solution

In resolveOTelConfigFromSettings (otelConfigResolution.ts), pass the recognized managed values through the existing `policy*` OTelConfigInput fields (policyEnabled, policyExporterType, policyOtlpEndpoint, policyCaptureContent, policyOutfile, policyProtocol, policyServiceName, policyHeaders) when hasEnterpriseSettings is true, mirroring the pattern already used correctly for policyCaptureIdentity/policyResourceAttributes, and update the test that currently locks in the old precedence.

## Evidence

- **documented intended precedence:** otelConfig.ts's resolveOTelConfig doc comment states precedence as '1. Enterprise policy (highest) 2. COPILOT_OTEL_* env 3. OTEL_EXPORTER_OTLP_* env 4. - **caller mismaps policy into setting inputs:** otelConfigResolution.ts resolveOTelConfigFromSettings passes `settingEnabled: read('enabled')`, `settingExporterType: read(...)`, `settingOtlpEndpoint: read(...)`, `settingCaptureContent: read(...)`, `settingOutfile: read(...)`, `settingProtocol: read(...)`, `settingServiceName: read(...)` — even when hasEnterpriseSettings is true and read() returns the managed value, it lands in the setting* slot, so env vars (checked before settingX in resolveOTelConfig) win. Only captureIdentity and resourceAttributes are correctly routed through policyCaptureIdentity/policyResourceAttributes; policyHeaders is never populated at all.
- **existing test documents the buggy behavior:** src/platform/otel/common/test/otelConfigResolution.spec.ts, test 'preserves existing effective-setting resolution and env precedence' (~line 123-135), asserts that with settings.policy.enabled=true, `COPILOT_OTEL_ENABLED: 'false'` still disables it, and `OTEL_EXPORTER_OTLP_ENDPOINT` env still overrides the managed otlpEndpoint (enabledVia: 'setting') and headers merge lets env win on key collision alongside managed keys.
- **related issue:** Body cites https://github.com/microsoft/vscode/issues/336701 as documenting this as an accepted gap while a separate late-policy initialization race was fixed there.
