# Issue #293826 — Github Copilot Edit mode gone after latest update?

[https://github.com/microsoft/vscode/issues/293826](https://github.com/microsoft/vscode/issues/293826)

## Summary

Keep this under discussion as a well-supported request to restore a constrained Edit workflow. Current main deliberately removes both the setting and its temporary custom-agent replacement, while 42 upvotes and many independent comments document a meaningful gap between Edit and Agent mode.

## Change summary

Restore an Edit-like Copilot workflow for fast, predictable changes limited to selected, active, or explicitly attached files.

## Best solution

Provide a supported, low-friction editing mode that restricts context and modifications to explicitly selected files without invoking terminal commands or exploring the wider workspace. Maintainers should first decide whether that contract belongs in a distinct built-in mode, a maintained custom agent, or a constrained Agent configuration.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input/modePickerActionItem.ts`, `src/vs/workbench/contrib/chat/common/chatModes.ts`, `extensions/copilot/src/extension/agents/vscode-node/promptFileContrib.ts`
- **Validation:** End with automated coverage showing that the chosen Edit-like experience is selectable under its intended availability rules, can edit the active and explicitly attached files, and cannot read or modify unrelated workspace files or invoke terminal tools.
- **Behavior:**

  > Users need a fast, predictable Copilot editing workflow limited to the active file, selected content, and files they explicitly attach. It must not explore unrelated workspace content or execute terminal commands, and requests requiring broader access must clearly offer escalation to Agent mode. The experience must remain distinct from unrestricted Agent behavior in both context access and available tools.
- **Trace:**

  > The issue began when Edit was hidden in VS Code 1.109 and now represents a restoration request rather than a defect: current main intentionally removes the setting and custom-agent fallback in commit 8abc0d6b023890cd83c48230fc8e5e9b54de9080. `shouldShowBuiltInMode` in `src/vs/workbench/contrib/chat/browser/widget/input/modePickerActionItem.ts` exposes legacy `ChatMode.Edit` only when Agent mode is disabled by policy. Commit 64e60426cdb99c5ce069eeba8a335343719cf5bf previously supplied a custom Edit agent through `extensions/copilot/src/extension/agents/vscode-node/promptFileContrib.ts`, with an explicit active/attached-file allowlist and only read/edit tools, but that implementation was removed. Preserve unrestricted Agent behavior and the enterprise-policy fallback; the uncertainty begins at which supported surface should own the constrained editing contract.
- **Open decisions:**
  - Should the constrained workflow return as a distinct built-in Edit mode, a maintained built-in custom agent, or an explicit restricted configuration of Agent mode?
  - Should the workflow be available by default, opt-in through a user setting, or limited by an organizational policy?
  - Should selected text constrain edits within the active file, or should selecting any part of a file permit edits anywhere in that file?

## Evidence
