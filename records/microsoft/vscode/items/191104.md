# Issue #191104 — Consider persisting results for quick search

[https://github.com/microsoft/vscode/issues/191104](https://github.com/microsoft/vscode/issues/191104)

## Summary

Keep open: search.quickAccess.preserveInput partially addresses reopening Quick Search, but does not restore the previous result list and position. This team-authored Backlog request remains the canonical item for that broader capability.

## Change summary

Retain Quick Search results and the user's position when closing and reopening the picker.

## Best solution

Let Quick Search resume its previous results and focused position without requiring the user to navigate back through regenerated matches. Establish how this interacts with the existing input-preservation setting and explicit new searches before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/search/browser/quickTextSearch/textSearchQuickAccess.ts`, `src/vs/workbench/contrib/search/browser/searchActionsTextQuickAccess.ts`, `src/vs/workbench/contrib/search/browser/search.contribution.ts`, `src/vs/platform/quickinput/browser/quickAccess.ts`, `src/vs/platform/quickinput/browser/pickerQuickAccess.ts`
- **Validation:** In a workspace with multiple matching files, invoke workbench.action.quickTextSearch, enter a query, navigate and scroll to a later match, dismiss, and reopen. Verify the agreed query, results, active match, and visible position are restored; repeat after accepting a result and with search.quickAccess.preserveInput enabled and disabled. Verify that an explicit new query still produces fresh results.
- **Behavior:**

  > Quick Search currently provides optional input restoration but does not resume the previous result list and navigation position. The requested outcome is to leave the picker and return to the same search context without navigating through matches again. Acceptance should cover dismissal and result acceptance, restoration of the active match and visible position, and an explicit new query replacing the previous search.
- **Trace:**

  > TextSearchQuickAccess.defaultFilterValue reads search.quickAccess.preserveInput and returns DefaultQuickAccessFilterValue.LAST. QuickAccessController in src/vs/platform/quickinput/browser/quickAccess.ts stores accepted input values but creates a new picker on reopening. PickerQuickAccessProvider.provide requests picks again, and TextSearchQuickAccess._getPicks calls doSearch and constructs fresh match picks without restoring an active result; result ordering can prioritize the currently active editor. The existing input setting is therefore partial coverage, not evidence that full session restoration shipped. https://github.com/microsoft/vscode/issues/194523 was explicitly closed into this issue; history navigation in https://github.com/microsoft/vscode/issues/208651 is separate. Preserve explicit new-query behavior, editor preview/cancellation semantics, and Search-view transfer; uncertainty starts at the desired restoration policy and its relationship to the existing setting.
- **Open decisions:**
  - Should full result-and-position restoration be enabled by search.quickAccess.preserveInput, or should reopening resume the previous session independently of that setting?
  - Should reopening restore the last session after both cancellation and accepting a result, and should it take precedence over a search seeded from the current editor selection?

## Evidence

- **Existing capability is partial:** src/vs/workbench/contrib/search/browser/search.contribution.ts registers search.quickAccess.preserveInput, default false, specifically to restore the last input. TextSearchQuickAccess.defaultFilterValue in src/vs/workbench/contrib/search/browser/quickTextSearch/textSearchQuickAccess.ts maps it to DefaultQuickAccessFilterValue.LAST; it does not restore the selected match or scroll position.
- **Current reopening path:** src/vs/platform/quickinput/browser/quickAccess.ts creates a new picker and retains lastAcceptedPickerValues. PickerQuickAccessProvider.provide in src/vs/platform/quickinput/browser/pickerQuickAccess.ts requests picks again; TextSearchQuickAccess._getPicks invokes doSearch for nonempty input and reconstructs picks without a saved active match. _getPicksFromMatches also prioritizes the active editor's resource, rather than restoring the previous picker position.
