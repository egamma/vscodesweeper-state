# Issue #84981 — Support external diff algorithms in internal diff editor

[https://github.com/microsoft/vscode/issues/84981](https://github.com/microsoft/vscode/issues/84981)

## Summary

Keep this accepted, well-supported request open: current main offers several fixed diff implementations, but not extension-provided hunk computation or Git-configured algorithms in the internal diff editor. No verified older open canonical absorbs that remaining capability.

## Change summary

Allow external diff algorithms to supply hunks rendered by VS Code's internal diff editor, ideally respecting Git's configured algorithm.

## Best solution

Define a supported provider contract that lets extensions supply alternative diff results while retaining the internal editor's presentation and interactions. Maintainers should first settle provider selection and whether Git configuration affects only SCM comparisons or all file comparisons.

## Plan brief

- **Likely files:** `src/vs/editor/common/diff/documentDiffProvider.ts`, `src/vs/editor/browser/widget/diffEditor/diffProviderFactoryService.ts`, `src/vs/editor/browser/widget/diffEditor/diffEditorViewModel.ts`, `src/vs/editor/common/config/editorConfigurationSchema.ts`, `src/vscode-dts/vscode.d.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/commands.ts`
- **Validation:** The plan should end with an executable integration check using a test provider whose hunk alignment intentionally differs from the built-in algorithm: opening a normal internal diff editor must display the supplied alignment. Cover provider selection, changed document contents, cancellation, and unchanged behavior without a selected provider; exercise Git-configured selection separately if that scope is accepted.
- **Behavior:**

  > Users want alternative diff algorithms to determine the hunks displayed inside VS Code's normal diff editor, rather than opening another tool's interface. Selecting another bundled implementation is not sufficient: the requested capability includes extension-provided algorithms such as patience, histogram, or structural diffing. Acceptance should demonstrate that a provider's deliberately different hunk alignment appears in the internal editor while ordinary comparisons retain existing behavior when no provider is selected. Respecting Git's configured algorithm is a requested baseline whose scope needs a maintainer decision.
- **Trace:**

  > IDocumentDiffProvider in src/vs/editor/common/diff/documentDiffProvider.ts already describes asynchronous diff results, cancellation, and change notification, but is internal. WorkerBasedDocumentDiffProvider in src/vs/editor/browser/widget/diffEditor/diffProviderFactoryService.ts has an object-provider delegation branch; the factory options and diffEditor.diffAlgorithm configuration expose only fixed algorithm names. src/vs/editor/common/diff/externalLinesDiffComputer.ts loads the bundled @vscode/diff module, so advanced-external does not mean arbitrary external tools. QuickDiffProvider in src/vscode-dts/vscode.d.ts supplies baseline resources, not hunk computation. The Git extension opens comparisons through vscode.diff in extensions/git/src/repository.ts and extensions/git/src/commands.ts. Preserve the normal internal diff UI and default computation behavior; the uncertainty begins at extension-facing result semantics and selection scope. https://github.com/microsoft/vscode/issues/160259 and https://github.com/microsoft/vscode/issues/315177 are related design inputs, not duplicate canonicals.
- **Open decisions:**
  - Should Git's configured diff algorithm automatically control SCM comparisons, require explicit opt-in, or also affect non-SCM file comparisons?
  - Should the extension-facing contract accept line hunks alone or require character-level mappings and move information for the internal editor's richer interactions?
  - When multiple providers apply or a selected provider fails, what selection and user-visible fallback behavior should the product guarantee?
