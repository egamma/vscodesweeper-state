# Issue #176644 — balancedBracketScopes per bracket type

[https://github.com/microsoft/vscode/issues/176644](https://github.com/microsoft/vscode/issues/176644)

## Summary

Per-bracket-type scope filtering remains missing: current grammar contributions classify bracket eligibility for an entire token, not individual bracket types. Keep this accepted, team-authored request open; the related reports do not provide an eligible duplicate target or a verified fix.

## Change summary

Allow grammar authors to restrict angle-bracket matching to selected scopes without applying those restrictions to parentheses, square brackets, and braces.

## Best solution

Provide a backward-compatible grammar contribution contract for bracket-specific scope eligibility, supported by tokenization and bracket parsing. Preserve existing grammar-wide filters and distinguish this capability from the separate handling of embedded-grammar exclusions.

- **Validation:** The plan should end with executable tokenization/bracket-parser tests showing that angle brackets are recognized only in configured scopes while ordinary bracket types remain eligible in otherwise eligible code tokens. Cover coexistence with legacy scope filters, foreground/background tokenization parity, and a TypeScript generic containing an inline comment.
- **Behavior:**

  > Grammar authors should be able to restrict specific bracket types to selected TextMate scopes without imposing those restrictions on other bracket types. For TypeScript, generic angle brackets should remain colorizable while relational, arrow, and shift operators are excluded, without suppressing ordinary brackets in eligible code. Existing grammar contributions must retain their behavior when they do not opt into the new capability. Acceptance checks must distinguish bracket-specific eligibility from independent color pools and must preserve existing string/comment exclusions.
- **Trace:**

  > TMGrammars.ts currently declares only grammar-wide balancedBracketScopes and unbalancedBracketScopes arrays. textMateTokenizationFeatureImpl.ts converts these into selectors that TMGrammarFactory.createGrammar forwards to vscode-textmate; the background worker carries the same selector fields. TokenMetadata.containsBalancedBrackets reads a single eligibility bit, and TextBufferTokenizer.read uses it to gate recognition of all configured bracket types. This establishes the missing capability but not a complete design for representing bracket-specific eligibility or its compatibility semantics. https://github.com/microsoft/vscode/issues/165232 concerns embedded-grammar exclusions and remains a related, distinct boundary; https://github.com/rust-lang/rust-analyzer/issues/14985 supplies another consumer. Preserve existing contributions, token-type exclusions, and unrelated color-pool behavior; no runtime execution or checkout modifications were performed.
- **Open decisions:**
  - When bracket-specific selectors coexist with balancedBracketScopes or unbalancedBracketScopes, do they further restrict the existing eligibility rules or override those rules for the named bracket?
  - Is the contribution contract keyed by individual opening and closing bracket strings, as proposed in the issue, or by bracket pairs, and what eligibility applies to bracket types omitted from the configuration?
