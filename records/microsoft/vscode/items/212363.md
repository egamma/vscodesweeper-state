# Issue #212363 — Support distinguishing workspace folders based on query param differences

[https://github.com/microsoft/vscode/issues/212363](https://github.com/microsoft/vscode/issues/212363)

## Summary

Query-distinct workspace folders still collapse in the shared workspace lookup on current main. Keep this accepted Backlog request open: neither proposed fix merged, and the maintainer explicitly called for consistent support across components rather than a breadcrumb-only change.

## Change summary

Distinguish workspace folders whose URIs differ only in query parameters consistently across breadcrumbs, labels, editor navigation, and Explorer selection.

## Best solution

Establish consistent query-aware workspace association semantics across resource lookup and its workbench consumers, while preserving supported query-bearing editor URIs in ordinary workspaces. Resolve the compatibility concerns recorded on the broader, closed implementation attempt before pursuing a replacement.

Run the targeted workspace and ternary-search-tree suites in an implementation workspace. Repeat the supplied MemFS steps and check distinct breadcrumb names, ${folderName}, editor-picker labels, and Explorer selection when switching between roots.
- **Behavior:**

  > A multi-root workspace containing No Query at memfs:/ and Query at memfs:/?p=1 must retain distinct folder associations despite identical scheme, authority, and path. Opening files from either root must show the corresponding folder name in breadcrumbs, window-title folder variables, and editor pickers, and select the corresponding Explorer item. Existing behavior that associates a query-bearing editor resource with an ordinary containing workspace folder must remain supported. Acceptance includes both the provided MemFS scenario and regression checks for ordinary and nested workspace roots.
- **Trace:**

  > Workspace in src/vs/platform/workspace/common/workspace.ts constructs its foldersMap with query and fragment ignored, inserts folders in order, and resolves resources through getFolder/findSubstr. UriIterator.reset in src/vs/base/common/ternarySearchTree.ts confirms that the callback removes those URI components from lookup keys, collapsing the sample roots. BreadcrumbsModel and LabelService consume the resulting shared association; this is not solely a breadcrumb rendering problem. The existing workspace test explicitly preserves query-ignoring association for ordinary folders. Neither https://github.com/microsoft/vscode/pull/212436 nor https://github.com/microsoft/vscode/pull/237987 merged. The latter's changes-requested review identifies broader resource-lookup consistency concerns, while https://github.com/microsoft/vscode/pull/231715 addresses search separately. The trace establishes the workspace-map gap but does not enumerate every shared TST consumer or settle compatibility semantics; keep filesystem identity, editor identity, and unrelated trust behavior outside an incidental UI-only change.
- **Open decisions:**
  - When a resource query has no exact matching workspace root, should association fall back to a queryless root, and what should happen if only differently queried roots exist?
  - Should query-aware containment be a uniform resource contract or a workspace-association contract, and which existing consumers legitimately retain query-insensitive behavior?

## Evidence

- **Confirmed report and accepted scope:** The January 13, 2025 discussion provides a MemFS sample and explicit steps, followed by bpasero confirming the behavior and expanding the request to window titles, editor pickers, and Explorer selection. https://github.com/microsoft/vscode/issues/212363#issuecomment-2587493701 explicitly classifies this as a cross-component feature.
- **Current source still loses query identity:** In src/vs/platform/workspace/common/workspace.ts, Workspace's constructor and updateFoldersMap create TernarySearchTree.forUris(this.ignorePathCasing, () => true). UriIterator.reset in src/vs/base/common/ternarySearchTree.ts omits query and fragment when that callback returns true. Consequently, memfs:/ and memfs:/?p=1 share a map key; the later folder replaces the earlier lookup entry, and Workspace.getFolder uses that same map.
- **Existing capability does not cover the request:** Workspace.getFolder has no query-sensitive option, and the workspace contribution registrations inspected expose no setting or command for this behavior. src/vs/platform/workspace/test/common/workspace.test.ts explicitly tests that a resource query is ignored when resolving an ordinary containing folder. src/vs/workbench/browser/parts/editor/breadcrumbsModel.ts and src/vs/workbench/services/label/common/labelService.ts consume getWorkspaceFolder, so changing displayed folder names alone would not restore distinct associations.
