# Issue #295111 — Output limit should be client configurable

[https://github.com/microsoft/vscode/issues/295111](https://github.com/microsoft/vscode/issues/295111)

## Summary

The requested client-side output cap is still missing on current main: Copilot uses each model's server-advertised maximum directly. This should remain open and be routed to language-model management for a configuration-contract decision.

## Change summary

Let users configure the maximum Copilot response-token budget, defaulting to 32K instead of allowing GPT-5.3 Codex's advertised 128K.

## Best solution

Define a supported client-side output cap with a 32K default, clamp it to each model's advertised maximum and context window, and use the resulting effective limit consistently for request construction and prompt budgeting.

## Plan brief

- **Likely files:** `extensions/copilot/package.json`, `extensions/copilot/package.nls.json`, `extensions/copilot/src/platform/configuration/common/configurationService.ts`, `extensions/copilot/src/platform/endpoint/node/modelMetadataFetcher.ts`, `extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts`, `extensions/copilot/src/platform/endpoint/node/test/copilotChatEndpoint.spec.ts`
- **Validation:** From extensions/copilot, run `npm run test:unit -- src/platform/endpoint/node/test/copilotChatEndpoint.spec.ts` with cases showing that a 128K advertised maximum becomes 32K by default, an explicit configured cap is honored, and a server maximum below the cap remains unchanged.
- **Behavior:**

  > Copilot chat should use a client-controlled maximum response-token budget rather than always sending a model's full advertised output allowance. With no customization, a model advertising 128K output should receive an effective 32K limit, while models advertising less must retain their smaller supported limit. A configured value should affect both the outgoing request and the prompt/context reservation derived from that request budget.
- **Trace:**

  > On current main, ChatEndpoint in extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts stores the server-provided `max_output_tokens` unchanged, and ChatMLFetcherImpl.fetchMany in extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts places that value into `requestOptions.max_tokens`. ModelMetadataFetcher._hydrateResolvedModel computes a smaller output figure for prompt reservation but only updates `max_prompt_tokens`, so it does not cap the actual response request. The existing model-capability override schema has no output-limit field. Preserve lower server-advertised maxima and context-window validity; do not broaden this into BYOK provider metadata or unrelated context-widget work tracked by https://github.com/microsoft/vscode/issues/321761.
- **Open decisions:**
  - Should the supported configuration expose one client-wide output cap, or a per-model map so users can assign different caps to models with different response characteristics?

## Evidence

- **current request path:** extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts copies `capabilities.limits.max_output_tokens` directly into `_maxOutputTokens`; extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts then uses `chatEndpoint.maxOutputTokens` as the request's `max_tokens` value.
- **existing configuration gap:** The advanced `github.copilot.chat.modelCapabilityOverrides` setting in extensions/copilot/package.json supports only `family` and `thinkingInHistory`; it cannot override or cap output tokens.
- **partial prior work:** https://github.com/microsoft/vscode/issues/251927 introduced a 15% reservation heuristic, but current extensions/copilot/src/platform/endpoint/node/modelMetadataFetcher.ts uses that computed value only to reduce `max_prompt_tokens`; it does not replace the advertised `max_output_tokens` sent with requests.
- **canonical search:** Repository searches found no older open issue requesting the same user-configurable Copilot response cap; the related open token-limit reports concern premature truncation or BYOK display/budgeting rather than limiting an excessively large advertised output maximum.
