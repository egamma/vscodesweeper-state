# Issue #245891 — Feature Request: Allow extensions to control Activity Bar title casing (prevent automatic uppercase)

[https://github.com/microsoft/vscode/issues/245891](https://github.com/microsoft/vscode/issues/245891)

## Summary

Keep this accepted Backlog request open: Modern UI removes mandatory all-caps in some configurations, but still capitalizes sidebar titles and provides no extension-controlled authored-casing option. Neither the closed Explorer discussion nor the newer uppercase audit is a valid duplicate canonical.

## Change summary

Allow extension-contributed view-container titles to retain their authored casing instead of undergoing automatic uppercase transformation.

## Best solution

Preserve authored extension-title casing through a consistent workbench typography policy, preferably using the existing user-controlled casing preference rather than independent branding overrides. A maintainer should decide whether exact casing preservation is a global policy or an extension contribution contract.

## Plan brief

- **Likely files:** `src/vs/workbench/api/browser/viewsExtensionPoint.ts`, `src/vs/workbench/browser/parts/sidebar/media/sidebarpart.css`, `src/vs/workbench/contrib/modernUI/browser/media/fontRamp.css`, `src/vs/workbench/browser/workbench.contribution.ts`
- **Validation:** Use a development extension contributing an activitybar container titled 'myBrand Tools'. Verify its visible container title against the chosen contract with Modern UI enabled and disabled, and with workbench.experimental.modernUIUppercaseViewHeaders enabled and disabled; include built-in titles to confirm the existing user preference remains honored.
- **Behavior:**

  > An extension contributes a view container with a deliberately mixed-case title, but workbench styling changes its displayed casing. The requested outcome is a supported way to display that title exactly as authored. Modern UI already avoids all-caps by default, but capitalization still prevents exact preservation. Acceptance should cover mixed-case branding and sentence-case titles across the supported UI modes while preserving the agreed user-preference behavior.
- **Trace:**

  > In src/vs/workbench/api/browser/viewsExtensionPoint.ts, activitybar contributions register in ViewContainerLocation.Sidebar, and registerCustomViewContainer retains the original title string. The transformation is presentation-side: sidebarpart.css forces uppercase, while modernUI/browser/media/fontRamp.css substitutes capitalize and optionally restores uppercase. workbench.contribution.ts registers the existing Modern UI uppercase preference; there is no casing field in viewsContainerSchema. The remaining uncertainty is the public behavior contract, not where the string is lost. Preserve unrelated typography and existing user preferences. The closed discussion at https://github.com/microsoft/vscode/issues/191160 and the newer audit at https://github.com/microsoft/vscode/issues/340788 provide context but do not absorb this request.
- **Open decisions:**
  - Should exact authored casing be a uniform workbench policy for contributed titles, or an extension-selectable contribution capability?
  - If extensions can opt into authored casing, should the user's uppercase-header preference override that opt-in?
