# Issue #43440 — Option to disable font ligatures in certain syntactical constructs like strings

[https://github.com/microsoft/vscode/issues/43440](https://github.com/microsoft/vscode/issues/43440)

## Summary

Keep open: current settings control ligatures globally or per language, but do not provide syntax-specific suppression within a file. This accepted Backlog request has 51 upvotes, and a maintainer recently consolidated cross-token ligature reports into it.

## Change summary

Allow ligatures to remain enabled for code while being disabled in selected syntactic constructs such as strings and comments.

## Best solution

Provide syntax-aware ligature control that preserves the existing editor-wide and language-specific settings, with explicit semantics for ligatures crossing syntax boundaries. Use this issue to retain the related string-readability and cross-token colorization requirements.

- **Behavior:**

  > Users want to read literal character sequences in strings without disabling ligatures throughout the surrounding code. An opt-in syntax-aware control should suppress ligatures in the selected constructs while preserving existing behavior elsewhere and retaining language-specific overrides. Acceptance must demonstrate both uncombined string characters and unchanged ligatures in ordinary code using the same font. The related cross-token colorization examples need an explicit boundary policy rather than being assumed resolved by string-only suppression.
- **Trace:**

  > EditorFontLigatures in src/vs/editor/common/config/editorOptions.ts validates a boolean or CSS feature-settings string, and applyFontInfo in src/vs/editor/browser/config/domFontInfo.ts applies that value at the editor DOM level. The theme token schema in src/vs/workbench/services/themes/common/colorThemeSchema.ts has no per-token ligature field; font decoration CSS in src/vs/editor/common/languages/supports/tokenization.ts handles family and size instead. resolveRenderLineInput in src/vs/editor/common/viewLayout/viewLineRenderer.ts receives an editor-level ligature flag and uses it during token splitting. This establishes the missing configuration surface, not a completed design for propagating syntax-specific shaping through every renderer. Preserve existing global settings, language overrides, token colors, and default rendering performance. https://github.com/microsoft/vscode/issues/231128#issuecomment-5435135614 confirms that this issue also owns the cross-token ligature examples; the available history did not identify a concrete implementing commit.
- **Open decisions:**
  - Should syntax-specific suppression select standard token categories such as strings and comments, arbitrary TextMate scopes, or both?
  - Should ligatures spanning distinct syntax tokens always be suppressed, or only when one of the tokens has ligatures disabled?
