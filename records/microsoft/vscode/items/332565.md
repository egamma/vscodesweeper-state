# Issue #332565 — Worker bootstrap blob URLs are never revoked (13 GB of blob_storage on my machine)

[https://github.com/microsoft/vscode/issues/332565](https://github.com/microsoft/vscode/issues/332565)

## Summary

Confirmed on current main: `getWorkerBootstrapUrl` in webWorkerServiceImpl.ts creates a blob URL for every worker bootstrap script and never revokes it, so each worker permanently retains a ~1.1MB blob; this is exactly the leak the reporter traced, and the correct revoke pattern already exists elsewhere in the codebase (timerService.ts).

## Change summary

Blob URLs created for web worker bootstrap scripts (getWorkerBootstrapUrl) are never revoked, leaking memory/disk (blob_storage) proportional to worker creation count.

## Best solution

In src/vs/platform/webWorker/browser/webWorkerServiceImpl.ts, capture the blob URL returned by getWorkerBootstrapUrl and call URL.revokeObjectURL on it once whenESMWorkerReady resolves (or on worker error/dispose), following the same pattern already used in timerService.ts's perfBaseline worker.

- **Fix prompt:**

  > The worker bootstrap blob URL leak: in src/vs/platform/webWorker/browser/webWorkerServiceImpl.ts, `getWorkerBootstrapUrl` (around line 78-117) builds a Blob containing the NLS message table and product.json and returns `URL.createObjectURL(blob)`. In `_createWorker` (lines 33-38) the returned URL string (`workerUrlWithNls`) is used only to construct `new Worker(...)` and then goes out of scope — it is never passed to `URL.revokeObjectURL`, so every worker created permanently pins a ~1.1MB blob in memory/disk (`blob_storage`), confirmed via `grep -n revokeObjectURL` returning no matches in the file. The fix should capture the blob URL in `_createWorker`, and revoke it via `URL.revokeObjectURL(workerUrlWithNls)` once `whenESMWorkerReady(worker)` resolves (worker has finished importing the real script) or when the worker errors/fails to start — mirroring the existing pattern in src/vs/workbench/services/timer/browser/timerService.ts lines 593-601 which does `.finally(() => { worker.terminate(); URL.revokeObjectURL(blobUrl); })`. Do not revoke the URL before the worker has actually loaded (revoking too early can break the Worker constructor's fetch of the blob in some browsers), and do not change the Worker creation/message-passing pipeline (WebWorker class, whenESMWorkerReady, onmessage/onerror wiring) beyond adding the revoke call. Add a unit test asserting URL.revokeObjectURL is called exactly once with the created blob URL after the worker reports ready.
