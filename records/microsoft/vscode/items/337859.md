# Issue #337859 — Agent Host: chat URIs encode the owning session, contrary to AHP

[https://github.com/microsoft/vscode/issues/337859](https://github.com/microsoft/vscode/issues/337859)

## Summary

Confirmed against current main: `buildChatUri`/`buildDefaultChatUri`/`buildSubagentChatUri` in sessionState.ts still encode the owning session URI into the chat URI path, and `parseChatUri` still requires that encoding and rejects a bare `ahp-chat:/<uuid>` — which conflicts with the AHP chat-channel spec's stated identity model (server-allocated id, ownership via the session's `chats` catalog/`origin`, not the URI). This is a real protocol-conformance gap, not a stale report.

## Change summary

Agent Host chat URIs encode the owning session URI in their path/authority instead of using an opaque, server-allocated chat identifier as AHP's chat-channel spec requires, so protocol-conforming chat URIs without that encoding are rejected as malformed.

## Best solution

Move chat identity to opaque, server-allocated IDs recorded in session state's `chats` catalog/`origin` (as AHP specifies) instead of deriving/recovering ownership by decoding the URI path, while planning a compatibility path for already-persisted sessions and older clients before changing the established encoding — this needs a maintainer design decision given how many call sites depend on the current derivation.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/common/state/sessionState.ts`, `src/vs/platform/agentHost/node/agentHostStateManager.ts`
- **Validation:** A sessionState test asserting that a chat URI carrying an opaque server-allocated id (no embedded/derivable session encoding) round-trips through creation, default/additional chat selection, ownership lookup, and restoration without being rejected as malformed, and that a legacy encoded URI from a previously persisted session still resolves correctly.
- **Trace:**

  > Root cause is the identity model in buildChatUri/buildDefaultChatUri/buildSubagentChatUri (sessionState.ts, ~L1171-1200), which derives chat URIs deterministically from the owning session URI, and parseChatUri/parseRequiredSessionUriFromChatUri (~L1208-1252), which require and decode that encoding to recover ownership — contrary to the AHP chat-channel spec, where ownership is protocol state (session `chats` catalog / chat `origin`), not URI-derivable. Confirmed by reading current main (commit 11e39c07, same code as cited in the issue at e6bf68e3). Boundary: do not restructure unrelated session-URI handling or other AHP resource types; the fix is scoped to chat identity allocation/parsing and its consumers. Where uncertainty starts: how to keep already-persisted sessions/restored chats and older clients working through the transition — the issue itself flags this as an open concern ("Plan compatibility for existing persisted sessions, restored chats, and older clients").
- **Open decisions:**
  - Should chat identifiers become opaque server-allocated IDs (e.g. UUIDs) fully decoupled from the session URI, and is ownership then read exclusively from session state's chats/origin catalog?
  - What compatibility strategy (if any) is needed for already-persisted sessions/chats whose URIs were built with the old session-encoded scheme, and for older clients that still expect that encoding?
  - Does this rollout require a version/negotiation flag, or can it ship as a straight behavior change given Agent Host's current maturity?
