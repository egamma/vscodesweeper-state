# Issue #149393 — Sort options directly in Explorer menu

[https://github.com/microsoft/vscode/issues/149393](https://github.com/microsoft/vscode/issues/149393)

## Summary

Keep open: this accepted Backlog request reached 20 community upvotes, and current main still exposes Explorer sorting only through settings rather than an Explorer-local menu. The older related issues do not meet the re-review duplicate bar because they track broader sorting or extension-contribution concerns, not the same direct sorting control.

## Change summary

Expose Explorer sort property and direction controls directly in the Explorer UI, including name-descending order.

## Best solution

Provide an Explorer-local sorting menu backed by the existing `explorer.sortOrder` and `explorer.sortOrderReverse` configuration, without changing current sorting semantics. A maintainer should first settle the menu placement, persistence scope, and which advanced sorting settings belong in the menu.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Add targeted Explorer tests proving that selecting sort property and direction through the new UI updates the effective configuration and that name-descending order is reflected by FileSorter; run the corresponding files-contrib unit-test selector.
- **Behavior:**

  > Users can inspect and change the Explorer's sort property and direction directly from the Explorer without opening Settings. The control includes the existing property modes and supports reversed name sorting, satisfying the dated-filename workflow in the report. Changes have clearly defined persistence and scope, and existing sorting behavior remains unchanged when users do not interact with the control.
- **Trace:**

  > The configuration surface already exists in src/vs/workbench/contrib/files/browser/files.contribution.ts as `explorer.sortOrder`, `explorer.sortOrderLexicographicOptions`, and `explorer.sortOrderReverse`. ExplorerService exposes those values through `sortOrderConfiguration`, and FileSorter.compare in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts applies them, including reverse ordering. The missing path is UI discoverability: the Explorer title actions in src/vs/workbench/contrib/files/browser/views/explorerView.ts contain creation, refresh, and collapse actions but no sorting action. Keep the scope to controlling the existing Explorer sorter; do not alter Open Editors sorting, sorting semantics, or add custom-sort APIs. https://github.com/microsoft/vscode/issues/162675 confirms this issue is treated as the canonical direct-menu request; https://github.com/microsoft/vscode/issues/108271 is related title-menu infrastructure but not the same user-visible request.
- **Open decisions:**
  - Should sorting be exposed as a dedicated Explorer title button or inside the Explorer overflow menu?
  - Should selections update user-level, workspace-level, or session-only state?
  - Should the menu expose only sort property and reverse direction, or also the existing lexicographic and related Explorer sorting settings?

## Evidence

- **accepted demand:** The issue has 20 upvotes, carries `feature-request` and `file-explorer`, and was moved to the Backlog after the maintainer-authored community upvote process succeeded.
- **current capability:** src/vs/workbench/contrib/files/browser/files.contribution.ts registers `explorer.sortOrder`, `explorer.sortOrderLexicographicOptions`, and `explorer.sortOrderReverse`, so name-descending sorting is now possible through Settings.
- **remaining gap:** src/vs/workbench/contrib/files/browser/views/explorerView.ts registers New File, New Folder, Refresh, and Collapse actions in the Explorer title menu, but no action or submenu for changing sort property or direction.

Neither reports the same observable absence of a built-in direct sorting menu required for a re-reviewed duplicate close.
