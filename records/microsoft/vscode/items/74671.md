# Issue #74671 — Allow debugger contributions to specify filenames as well as languages to be default debugger

[https://github.com/microsoft/vscode/issues/74671](https://github.com/microsoft/vscode/issues/74671)

## Summary

The requested extension API capability remains absent on current main: debugger selection considers only the active document's language ID, not its filename or URI. Keep this Backlog feature request open for an extension-contract decision and classify it as under discussion.

## Change summary

Allow debugger contributions to identify themselves as the default debugger for documents matching filename patterns as well as language IDs.

## Best solution

Define a backward-compatible debugger contribution contract for document selectors, then use the active document's language and URI when choosing the default debugger so files such as `pubspec.yaml` can select the appropriate debugger without a prompt.

- **Likely files:** `src/vs/workbench/contrib/debug/common/debug.ts`, `src/vs/workbench/contrib/debug/common/debugSchemas.ts`, `src/vs/workbench/contrib/debug/common/debugger.ts`, `src/vs/workbench/contrib/debug/browser/debugAdapterManager.ts`, `src/vs/workbench/contrib/debug/test/node/debugger.test.ts`
- **Validation:** Extend the debug contribution tests to verify that existing language strings retain their behavior and that an active document matching an approved filename selector selects the sole matching debugger while nonmatching documents do not.
- **Behavior:**

  > A debugger extension can declare that it is applicable to an active document by filename or URI pattern, while existing language-only contributions continue to behave unchanged. When exactly one enabled debugger matches the active document, pressing F5 can select it without showing the debugger picker. A nonmatching filename must not make that debugger a candidate.
- **Trace:**

  > `DebugAdapterManager.guessDebugger` in `src/vs/workbench/contrib/debug/browser/debugAdapterManager.ts` reads the active model's language ID and filters candidates through `Debugger.interestedInLanguage`. That method in `src/vs/workbench/contrib/debug/common/debugger.ts` only checks membership in `IDebuggerContribution.languages`, which is typed as `string[]` in `src/vs/workbench/contrib/debug/common/debug.ts`; the matching contribution schema is in `src/vs/workbench/contrib/debug/common/debugSchemas.ts`. Existing tests for `Debugger` are in `src/vs/workbench/contrib/debug/test/node/debugger.test.ts`. Preserve selection behavior for existing string language entries and do not expand this request into workspace-wide file scanning or ranking; https://github.com/microsoft/vscode/issues/146338 discussed those broader heuristics separately.
- **Open decisions:**
  - Should the public contribution contract extend `languages` to accept language-or-document-filter entries, or introduce a separate filename-selector property while retaining `languages` as `string[]`?
  - Which document-selector fields and pattern base semantics should the JSON contribution contract support, particularly whether matching includes scheme and workspace-relative patterns?
