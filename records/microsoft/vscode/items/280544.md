# Issue #280544 — Agent sessions: recent sessions list flashes on first open of chat view

[https://github.com/microsoft/vscode/issues/280544](https://github.com/microsoft/vscode/issues/280544)

## Summary

Confirmed startup-state race: the recent-sessions list briefly renders while ChatViewPane is still restoring a non-empty session. The Backlog milestone does not prevent triage, and no older issue with the same visible flash was identified, so this should remain open.

## Change summary

Prevent the recent agent-sessions list from flashing when the chat view first opens and restores an existing session.

## Best solution

Expose restoration intent early enough for the ChatViewPane empty-state logic to distinguish a genuinely empty chat from a session that is still loading, while preserving the recent-sessions list for new empty chats.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chatViewPane.ts`, `src/vs/workbench/contrib/chat/browser/chatWidget.ts`
- **Validation:** Add a chat-view test that begins restoration of a non-empty session with delayed model availability and asserts that the recent-sessions container never becomes visible before the restored session is attached; separately assert that a genuinely empty new chat still shows recent sessions.
- **Behavior:**

  > When the chat view first opens after reload or update and an existing session is being restored, the recent-sessions list must not appear during the loading interval. The restored conversation should appear without an intermediate empty-state flash. A genuinely new empty chat must continue to show recent sessions. Acceptance should cover delayed restoration rather than only an immediately available model.
- **Trace:**

  > The confirmed race is in the ChatViewPane empty-state flow in `src/vs/workbench/contrib/chat/browser/chatViewPane.ts`: recent sessions are shown from the widget's initial `isEmpty` state before the restored ChatModel reaches the widget. The discussion at https://github.com/microsoft/vscode/issues/280544 records that `onDidChangeEmptyState` arrives too late and suggests that ChatViewPane may know restoration intent earlier, or that ChatWidget may need a loading-session state. The boundary is the initial restoration transition: do not suppress recent sessions for genuinely empty chats or alter normal session rendering. The uncertainty starts at which existing lifecycle signal can authoritatively distinguish restoring from empty without introducing another transient state.
- **Open decisions:**
  - Should the user-observable loading state be owned by ChatViewPane from its restoration context, or exposed as an explicit restoring-session state by ChatWidget?
