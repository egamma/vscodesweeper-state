# Issue #31153 — Git - Support interactive rebase

[https://github.com/microsoft/vscode/issues/31153](https://github.com/microsoft/vscode/issues/31153)

## Summary

Keep this accepted, well-supported request open: the built-in Git extension supports ordinary rebasing, but not initiating an interactive rebase or consolidating commits through the UI. The related interactive-rebase-editor request is newer and explicitly points back to this issue.

## Change summary

Provide a terminal-free interactive rebase workflow for cleaning up local commits, including squashing commits before submitting a PR.

## Best solution

Agree on an initial interactive-rebase experience in the built-in Git extension, using this issue as the older tracking record and incorporating the editor-specific demand from https://github.com/microsoft/vscode/issues/260637. Decide whether the initial experience edits Git's todo file or provides structured controls, and explicitly define the boundary for terminal-less web environments.

## Plan brief

- **Likely files:** `extensions/git/src/commands.ts`, `extensions/git/src/git.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/gitEditor.ts`, `extensions/git/package.json`, `extensions/git/package.nls.json`
- **Validation:** After agreeing on the UX, use a disposable repository with a base and three local commits: initiate interactive rebase from the VS Code UI, squash two commits, edit the resulting message, and verify the resulting history and unchanged final tree. Repeat with a conflict to verify continuation and abort restores the original history; confirm ordinary git.rebase behavior remains unchanged. Evaluate web acceptance separately against the agreed provider scope.
- **Behavior:**

  > Users should be able to start an interactive history-cleanup operation from the Git UI without typing a terminal command. The central acceptance case is consolidating local commits before a PR while controlling the resulting commit message. Conflict resolution and cancellation must leave users with a recoverable, understandable repository state. Existing ordinary rebasing must continue to work. The plan must explicitly state whether terminal-less web environments are included in the initial scope.
- **Trace:**

  > Commands.rebase in extensions/git/src/commands.ts selects a branch and delegates through the repository layer to Repository.rebase in extensions/git/src/git.ts, which constructs a non-interactive Git rebase invocation. GitEditor in extensions/git/src/gitEditor.ts opens Git-provided editor files, but does not supply interactive-rebase initiation or commit-consolidation UI. Source inspection establishes that ordinary rebase and editor integration are partial capabilities, not coverage of this request. Preserve ordinary rebase, existing editor configuration, and established conflict handling. https://github.com/microsoft/vscode/issues/260637 adds demand for a structured editor and explicitly points back to this older report. Uncertainty begins at the user-facing interaction model and the provider boundary for web environments; a local Git implementation must not be presented as satisfying github.dev.
- **Open decisions:**
  - Should the initial UI launch interactive rebase into an editable Git todo file, provide structured commit controls, or expose a focused squash/consolidation workflow?
  - Is the initial scope local Git repositories only, with web-provider support tracked separately, or must the feature also support terminal-less vscode.dev/github.dev workflows?
