# Issue #198159 — Broken full-page search result navigation for multiple folder directories of the same name in a workspace

[https://github.com/microsoft/vscode/issues/198159](https://github.com/microsoft/vscode/issues/198159)

## Summary

The navigation defect remains in current source: Search Editor identifies workspace roots by display name, and navigation selects the first root with that name. Keep this confirmed search bug open; renaming workspace folders remains a workaround, not a fix.

## Change summary

Search Editor results from same-named workspace roots can open a file in the wrong root or report that the file does not exist.

## Best solution

Ensure Search Editor result headers retain enough identity to navigate to the originating workspace folder even when folder names collide. Cover both newly executed searches and results opened from the Search view, while preserving navigation for existing saved searches.

Cover a file present only in the second root and identically named files in both roots, both Search Editor entry paths, and existing uniquely named-root and saved-search navigation. Manual acceptance: double-click the second root's result and verify the opened file's full path.
- **Behavior:**

  > In a workspace containing two folders with the same display name, Search Editor navigation must open the file that produced each result, not the first matching workspace root. Verify both a result whose relative file path exists only in the second root and results whose relative file paths exist in both roots. Results generated directly in Search Editor and opened from the Search view must behave consistently. Existing uniquely named-root and saved-search navigation must remain functional.
- **Trace:**

  > SearchEditor serializes paths with a relative ILabelService label in src/vs/workbench/contrib/searchEditor/browser/searchEditor.ts; createEditorFromSearchResult in searchEditorActions.ts uses the same formatting. searchEditorSerialization.ts stores those labels as plain-text file headers, and the label implementations prefix multi-root paths with the workspace folder's display name. In extensions/search-result/src/extension.ts, parseSearchResults calls relativePathToUri, whose multi-root branch selects the first workspace folder with that name; the resulting URI feeds definition navigation and document links. This conclusively explains the reported second-root failure without executing code. Keep the scope on accurate Search Editor navigation, not global Explorer or breadcrumb naming changes, and preserve existing saved-search compatibility. https://github.com/microsoft/vscode/issues/165398 was explicitly closed into this issue. The remaining planning need is an executable cross-boundary regression check; the inspected Search Editor tests did not establish coverage of this provider path.

## Evidence

- **Maintainer-confirmed reproduction:** In the supplied discussion for https://github.com/microsoft/vscode/issues/198159, andreamah confirmed that searching for text in the second of two same-named workspace roots and double-clicking its result produces a file-not-found error.
- **Current result serialization:** src/vs/workbench/contrib/searchEditor/browser/searchEditor.ts:633 and searchEditorActions.ts:210 both format result paths using labelService.getUriLabel(uri, { relative: true }). searchEditorSerialization.ts writes that label as the file header. src/vs/base/common/labels.ts:131-134 prefixes multi-root relative paths with folder.name; the formatted-resource branch in src/vs/workbench/services/label/common/labelService.ts likewise uses the folder name without collision disambiguation.
- **Exact failing navigation path:** SearchEditor.registerEditorListeners in src/vs/workbench/contrib/searchEditor/browser/searchEditor.ts invokes editor.action.goToDeclaration for a double-clicked result. The built-in provider in extensions/search-result/src/extension.ts parses its header through relativePathToUri, which resolves the root using workspaceFolders.filter(wf => wf.name === workspaceName)[0]. Thus a header for a file in the second tmp root resolves against the first tmp root; parseSearchResults propagates that incorrect URI to definition locations and document links.
