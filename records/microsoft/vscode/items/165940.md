# Issue #165940 — Allow more control of the status bar text for a LanguageStatusItem

[https://github.com/microsoft/vscode/issues/165940](https://github.com/microsoft/vscode/issues/165940)

## Summary

Keep open: separate pinned/flyout text exists only through a proposed API, while extension-selected default pinning remains unsupported. The open text-variants proposal covers part of this discussion, not its full scope, and maintainers have already engaged with the requested improvements.

## Change summary

Allow language status items to provide suitable pinned and flyout text, with additional requests for default pinning, tooltips, and clearer detail layout.

## Best solution

Evaluate and finalize separate text variants through https://github.com/microsoft/vscode/issues/192880, while retaining this issue for decisions on default pinning and the remaining presentation requests. Preserve user pin/unpin choices and the established distinction between editor-specific language status and project-wide status.

- **Validation:** In an Extension Development Host, create a language status item with descriptive flyout text and concise pinned text; verify both surfaces and the accessible label. For any approved default-pinning capability, verify first presentation, manual unpinning, window reload, and recreation of the same item, confirming that explicit user choices persist. Verify that switching to an unrelated editor retains existing selector-based visibility.
- **Behavior:**

  > Extension authors need concise pinned status text without losing descriptive context in the language-status flyout. The proposed text-variants API already supports this distinction, but the stable API does not. Several authors also request an initial pinned state for selected items; a maintainer must decide whether to expose that capability and how it interacts with saved user choices. Acceptance should cover both text surfaces, accessible labels, and pin-state persistence without broadening language status into project-wide status.
- **Trace:**

  > LanguageStatusItem in src/vscode-dts/vscode.d.ts exposes one stable text string and no pin-default property. The languageStatusText proposal adds text2, gated in ExtHostLanguages.createLanguageStatusItem in src/vs/workbench/api/common/extHostLanguages.ts; ILanguageStatus.label transports its value/shortValue object, and LanguageStatus renders value in the flyout and shortValue in _asStatusbarEntry. LanguageStatus maintains user-selected dedicated entries in the profile-scoped languageStatus.dedicated storage state. https://github.com/microsoft/vscode/issues/192880 owns the focused text-variants proposal, while https://github.com/microsoft/vscode/issues/167879 was folded into this issue for broader pinning requests. Preserve existing selector-based visibility, severity, busy indicators, command behavior, and accessibility semantics. The uncertainty is the public API and user-visible persistence contract, not where to place implementation helpers.
- **Open decisions:**
  - Should extensions be allowed to suggest an initial pinned state, and should that suggestion apply only before any explicit user pin/unpin choice?
  - Which additional presentation requests remain in scope after text variants: independent item tooltips, aligned label/detail columns, or neither?

## Evidence

- **Stable capability remains limited:** src/vscode-dts/vscode.d.ts:7273–7336 declares LanguageStatusItem.text as a string, with detail, busy, and command, but no separate pinned-text or default-pinning property. Swapping text/detail supports value-first presentation, not independent text for both surfaces.
- **Proposed text variants are implemented:** src/vscode-dts/vscode.proposed.languageStatusText.d.ts declares text2: string | { value: string; shortValue: string }. src/vs/workbench/api/common/extHostLanguages.ts gates text2 with checkProposedApiEnabled(extension, 'languageStatusText'); src/vs/workbench/contrib/languageStatus/browser/languageStatus.ts uses value in the flyout and shortValue in _asStatusbarEntry. This is proposed capability, not proof that the stable API satisfies the request.
- **Related proposal is narrower:** https://github.com/microsoft/vscode/issues/192880 is open and labeled api-proposal. Its author explicitly describes it as a focused effort after this discussion accumulated other asks: https://github.com/microsoft/vscode/issues/192880#issuecomment-1719529124. Bobbrow confirmed that the proposed text variants met their text needs at https://github.com/microsoft/vscode/issues/192880#issuecomment-1802170126, but that proposal does not own default pinning or all presentation requests.
- **Default pinning remains a product decision:** LanguageStatus in src/vs/workbench/contrib/languageStatus/browser/languageStatus.ts restores the dedicated-item set from profile storage and changes it through user pin/unpin actions. Neither LanguageStatusItem nor ILanguageStatus in src/vs/workbench/services/languageStatus/common/languageStatusService.ts supplies an extension-defined pin default. Flutter and C++ authors requested this capability at https://github.com/microsoft/vscode/issues/165940#issuecomment-1634321236 and https://github.com/microsoft/vscode/issues/165940#issuecomment-1634444281.
- **Existing tooltip support is partial:** LanguageStatus._asStatusbarEntry uses command.tooltip or detail for the pinned tooltip, and the flyout command link uses command.tooltip. These existing paths provide some tooltip support, but there is no independent LanguageStatusItem tooltip property; the flyout still renders label followed by detail and a separator rather than aligned value columns.
- **Maintainer direction and accepted scope:** A maintainer solicited concrete examples for separate text and default pinning at https://github.com/microsoft/vscode/issues/165940#issuecomment-1635788600. The later clarification at https://github.com/microsoft/vscode/issues/165940#issuecomment-1714097875 preserves editor-specific visibility and recommends Window progress for long-running initialization; the reporter accepted the intended text/detail ordering at https://github.com/microsoft/vscode/issues/165940#issuecomment-1717372771. These comments do not decline the entire request.
