# Issue #148974 — [Feature Request] Better alignment for file nesting

[https://github.com/microsoft/vscode/issues/148974](https://github.com/microsoft/vscode/issues/148974)

## Summary

Keep open: this accepted Backlog request has 68 community upvotes, remains observable in the current Explorer rendering logic, and is the canonical issue for several newer alignment reports. The remaining work requires a product decision about how file-nest twisties coexist with icon themes that hide arrows or omit folder icons.

## Change summary

Align same-level Explorer files consistently when file nesting is enabled with icon themes that hide Explorer arrows or do not provide folder icons.

## Best solution

Make sibling file labels and icons share one alignment in both collapsed and expanded states while retaining a discoverable expansion affordance for nesting parents. The Explorer owner should decide whether that behavior becomes the default or is exposed as an option, and whether the twistie uses a reserved gutter or an overlay/hover treatment.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/browser/media/explorerviewlet.css`, `src/vs/workbench/browser/parts/views/media/views.css`
- **Validation:** Verify an Explorer fixture or manual matrix with file nesting collapsed and expanded under Seti, Minimal, no-icons, and a theme declaring `hidesExplorerArrows`: same-level file labels/icons must align, nested children must remain one level deeper, and nesting parents must remain expandable by mouse and keyboard.
- **Behavior:**

  > With Explorer file nesting enabled, all files belonging to the same directory level should have consistently aligned labels and icons, including nesting parents, in both collapsed and expanded states. Nested children must remain visually one level deeper, and a nesting parent must retain a discoverable, keyboard-operable expansion affordance. Acceptance should cover themes with folder icons, themes without folder icons, themes that hide Explorer arrows, and no-icons mode without regressing ordinary folder indentation.
- **Trace:**

  > Explorer rendering reads icon-theme capabilities in `createFileIconThemableTreeContainerScope` in src/vs/workbench/contrib/files/browser/views/explorerView.ts and applies `align-icons-and-twisties`/`hide-arrows`. `FilesRenderer.renderStat` in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts forces a twistie for `stat.hasNests` when `theme.hidesExplorerArrows`, then marks nested children with `align-nest-icon-with-parent-icon`; the corresponding rules are in src/vs/workbench/browser/parts/views/media/views.css and src/vs/workbench/contrib/files/browser/media/explorerviewlet.css. This explains why nesting parents and ordinary sibling files retain different horizontal positions on affected themes. Preserve standard tree keyboard navigation, ARIA expanded state, ordinary folder hierarchy, and alignment for themes that already provide folder icons. Related reports https://github.com/microsoft/vscode/issues/161178, https://github.com/microsoft/vscode/issues/180654, and https://github.com/microsoft/vscode/issues/190681 point back to this canonical issue.
- **Open decisions:**
  - Should consistent file-nesting alignment replace the current behavior for all users, or be controlled by a new Explorer setting?
  - For themes that hide arrows or omit folder icons, should every sibling reserve a twistie gutter, or should the nesting-parent twistie overlay/reveal without moving its label?
