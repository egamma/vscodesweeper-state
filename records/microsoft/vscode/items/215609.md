- **Behavior:**

  > Renaming or permanently deleting a directory with approximately 100,000 files must not freeze the VS Code window, disconnect the remote workspace, or prevent unrelated dirty files from being saved. The Explorer must eventually reflect the completed operation, and normal small file operations and trash-enabled deletion must retain their existing behavior. Validate both rename and permanent deletion against the reporter's generated fixture in a Remote-SSH workspace.
- **Trace:**

  > Explorer permanent deletion starts in `deleteFiles` in src/vs/workbench/contrib/files/browser/fileActions.ts, becomes a recursive bulk file edit, and reaches `WorkingCopyFileService.delete` before the filesystem provider. `DiskFileSystemProvider.delete` in src/vs/platform/files/node/diskFileSystemProvider.ts requests `RimRafMode.MOVE`; `rimrafMove` in src/vs/base/node/pfs.ts returns quickly after a successful rename but awaits recursive `fs.promises.rm` when that rename fails. Rename separately reaches `DiskFileSystemProvider.rename`, so the shared symptom may instead involve remote filesystem transport, watcher traffic, or Explorer operation-event refreshes; the issue has no performance profile settling that boundary. The old Windows-trash report https://github.com/microsoft/vscode/issues/71243 is not the same path because this reproduction disables trash. Preserve trash behavior, undo/dirty-working-copy safeguards, filesystem events, and responsiveness of ordinary local operations.
