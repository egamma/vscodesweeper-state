# Issue #272848 — Chat response: render files and symbols consistently

[https://github.com/microsoft/vscode/issues/272848](https://github.com/microsoft/vscode/issues/272848)

## Summary

The inconsistency remains structurally possible on current main: bare inline-code spans become clickable only when the optimistic linkifier finds an exact symbol in the response's reference set, so adjacent code identifiers can render differently. Keep this open, but settle it together with the newer explicit-link proposal before implementation.

## Change summary

Make files and code symbols in chat responses use a predictable, consistent clickable presentation.

## Best solution

Define one linkification contract for chat responses, coordinated with https://github.com/microsoft/vscode/issues/313533: explicit symbol links should always render as anchors, while maintainers should decide whether bare backtick code retains heuristic linking or remains uniformly plain.

- **Behavior:**

  > Code references in one chat response must follow a predictable interaction rule instead of rendering some adjacent identifiers as clickable pills and others as plain inline code without an understandable distinction. Explicit symbol links must reliably navigate to their target. Acceptance should cover both a function and an interface name and verify the selected behavior for unresolved or non-explicit code spans.
- **Trace:**

  > Bare inline code is detected by InlineCodeSymbolLinkifier in extensions/copilot/src/extension/linkify/vscode-node/inlineCodeSymbolLinkifier.ts. It only creates LinkifySymbolAnchor when ReferencesSymbolResolver finds an exact symbol within context.references; findWordInReferences in extensions/copilot/src/extension/linkify/vscode-node/findWord.ts enforces the referenced-file/range and supported-language boundary. ResponseStreamWithLinkification then turns resolved anchors into ChatResponseAnchorPart, leaving misses as markdown. Explicit path-bearing links use SymbolLinkifier separately. Preserve ordinary markdown rendering and avoid broad workspace matches that create unrelated links. Coordinate the behavior with https://github.com/microsoft/vscode/issues/313533, which documents the false-positive cost of optimistic matching.
- **Open decisions:**
  - Should bare backtick code spans continue using optimistic symbol lookup, or should only explicit path-bearing symbol links be clickable?

## Evidence

- **resolution boundary:** extensions/copilot/src/extension/linkify/vscode-node/findWord.ts limits optimistic lookup to referenced files/ranges and supported Tree-sitter languages, which directly permits the reported mixed clickable/plain presentation.
