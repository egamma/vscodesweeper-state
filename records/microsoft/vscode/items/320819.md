# Issue #320819 — VSCode RG.exe verses VSCode Insiders RG activity

[https://github.com/microsoft/vscode/issues/320819](https://github.com/microsoft/vscode/issues/320819)

## Summary

Keep open for diagnosis: an independent commenter confirms thousands of repeated file enumerations, including after removing SARIF Viewer. Current source explains the command signature but does not establish the responsible caller, a complete fix, or a verified duplicate.

## Change summary

Investigate excessive repeated rg.exe file searches that consume CPU when VS Code starts or its search parent process restarts.

## Best solution

Identify the caller issuing repeated full-workspace enumerations and eliminate unnecessary repeat work at the responsible boundary, preserving legitimate search results and cancellation. Determine whether the remaining load comes from core or another extension before selecting the owning tracker or changing shared search behavior.

## Evidence

- **Independent confirmation:** https://github.com/microsoft/vscode/issues/320819#issuecomment-4702657650 reports hundreds or thousands of identical rg.exe --files requests on Windows with VS Code 1.124.2. Extension bisect identified SARIF Viewer as the largest contributor, but uninstalling it did not eliminate the repeated requests; this does not establish an extension-only cause.
- **Current search path:** src/vs/workbench/services/search/node/ripgrepFileSearch.ts:17-85 spawns ripgrep for a folder and constructs the reported --files, --hidden, --case-sensitive, --no-require-git, --no-ignore, --follow and --no-ignore-global flags from query options. src/vs/workbench/api/common/extHostWorkspace.ts:498-499 logs the extension identity for findFiles, and src/vs/workbench/api/browser/mainThreadWorkspace.ts:148-164 forwards file queries to the search service. These are diagnostic entry points, not proof of which caller caused this report.
- **Caching boundary:** src/vs/workbench/services/search/node/rawSearchService.ts:95-145 uses its cache path for sortByScore queries; other queries create a new search engine. Thus identical command-line arguments alone do not prove requests are incorrectly handled: caller frequency, workspace roots, query options and cancellation must be correlated.
- **Related cancellation fix is insufficient:** https://github.com/microsoft/vscode/commit/5fb292891882f8f42d41893d0041041719e82d0a changes FileWalker.cancel to kill only that walker's children and handles cancellation during asynchronous spawn. It does not merge or debounce repeated requests, and the report does not establish cancellation as its trigger; this is not sufficient evidence to close as implemented.
- **Orphan-process candidate is distinct:** https://github.com/microsoft/vscode/issues/193927 is open, but its diagnosed case concerns unkillable orphan processes and network-drive PATH lookups. https://github.com/microsoft/vscode/issues/193927#issuecomment-1793777699 explicitly distinguishes that low-CPU hung-process case from long-running high-CPU searches. The present report describes startup CPU consumption that eventually settles, so the same root cause is not established.
- **Canonical search:** Searches for open rg.exe and repeated-ripgrep reports found https://github.com/microsoft/vscode/issues/328122, which has a closely matching enumeration signature but an unconfirmed caller, and https://github.com/microsoft/vscode/issues/307001 and https://github.com/microsoft/vscode/issues/286778, which specifically require bracket-containing workspace paths. This report establishes neither chat-discovery ownership nor a bracket-path trigger, so none is a verified canonical.
