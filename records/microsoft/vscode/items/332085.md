# Issue #332085 — Agents window: BYOK custom-endpoint model not selectable for WSL workspaces

[https://github.com/microsoft/vscode/issues/332085](https://github.com/microsoft/vscode/issues/332085)

## Summary

Well-documented, specific bug: a BYOK custom-endpoint model is visible in the regular Chat view and the Language Models editor for a WSL workspace, but is missing from the Agents window model picker for that same workspace, while working fine in the Agents window for a local Windows workspace. The reporter did a clean A/B comparison, which is strong evidence, but confirming the exact code path needs a WSL environment I don't have here.

## Change summary

BYOK Custom Endpoint models don't appear in the Agents window model picker when the session's workspace is a WSL (Remote-WSL) folder, even though the same model is selectable for a local Windows workspace and in the regular Chat view.

## Best solution

An owner with a WSL environment should trace how the Agents window/agent host resolves its BYOK model list for a remote (WSL) workspace versus local: `src/vs/platform/agentHost/node/byokLmBridgeRegistry.ts` documents that both the main workbench and the dedicated Agents app register their own renderer BYOK bridge, each backed by its own extension host — the WSL gap likely comes from which extension host (local vs. remote) the Agents window attaches to, or from `resolveByokSessionConfig`/`ByokLmBridgeRegistry.getServingConnection()` picking a non-serving or wrong-scoped connection for a WSL-backed session.

## Evidence

- **byok bridge registry design:** src/vs/platform/agentHost/node/byokLmBridgeRegistry.ts documents that BYOK is serviced per-window: 'Both the main workbench and the dedicated Agents app register it (each runs a full extension host whose LM API holds the same BYOK models)... The registry does NOT aggregate per-window model sets; it surfaces the models from any one serving window' — a plausible seam for a WSL-specific gap if the Agents app's extension host doesn't see the same BYOK-registering extension host as the WSL workspace.
- **local profile-scoped config:** src/vs/workbench/contrib/chat/browser/languageModelsConfigurationService.ts reads chatLanguageModels.json from `userDataProfileService.currentProfile.languageModelsResource`, a local (non-remote) profile file, consistent with the model showing correctly in the Language Models editor and regular Chat view regardless of workspace.
- **agent host runs locally:** src/vs/platform/agentHost/electron-main/electronAgentHostStarter.ts and node/copilot/copilotSessionLauncher.ts show the agent host process (and the BYOK loopback proxy) is a local Electron-main-spawned child process, not something re-hosted inside the WSL distro — so a WSL-specific reachability issue would have to be in bridge selection/connection scoping rather than network forwarding.
