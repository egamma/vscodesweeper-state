# Issue #305773 — Profiles: Infinite loop on "Profile already exists" dialog when clicking Replace or Cancel

[https://github.com/microsoft/vscode/issues/305773](https://github.com/microsoft/vscode/issues/305773)

## Summary

This remains a reproducible cross-platform bug on the current code path: profile replacement can enter erroneous cleanup after extension-copy work fails, leaving the modal confirmation flow active and blocking the UI.

## Change summary

Replacing an existing profile while background extension operations are running repeatedly reopens the confirmation dialog and traps the user in a modal loop.

## Best solution

Make each profile-creation attempt own a single confirmation lifecycle and ensure failure cleanup never removes a profile that existed before the attempt. The profile import flow also needs to preserve and surface the original extension-copy failure rather than replacing it with a default-profile removal error.

## Plan brief

- **Likely files:** `src/vs/workbench/services/userDataProfile/browser/userDataProfileImportExportService.ts`, `src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditorModel.ts`, `src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditor.ts`
- **Validation:** Reproduce by starting extension installation, creating a profile from another profile or template under an existing name, and choosing Replace or Cancel; acceptance requires exactly one confirmation, a responsive Profiles UI, and preservation of the pre-existing profile when the copy operation fails. Add a targeted service test that injects a copy/apply failure for an existing Default and custom profile and asserts the existing profile is not removed.
- **Behavior:**

  > While extension installation or synchronization is active, attempting to create a profile under an existing name must show at most one replacement confirmation. Replace must proceed or report one actionable failure, while Cancel or Escape must return immediately to the Profiles UI. The existing profile must remain intact if copying its resources fails, and the window must never become trapped behind a recurring native dialog.
- **Trace:**

  > The confirmation is issued by getProfileToImport in src/vs/workbench/services/userDataProfile/browser/userDataProfileImportExportService.ts, which returns the already-existing profile on Replace. createFromProfile subsequently applies profile resources and copies extensions; its catch block treats that existing profile like a newly created profile and calls removeProfile. The Default case then reaches src/vs/platform/userDataProfile/common/userDataProfile.ts and throws `Cannot remove default profile`, matching the issue log. The Profiles editor invokes this through UserDataProfilesEditorModel.saveNewProfile, while UserDataProfilesEditorInput also exposes the same operation through editor save; the trace has not yet established which save/focus lifecycle event causes repeated confirmation after the rejection. Keep the investigation limited to profile creation/import, editor-save re-entry, and cleanup ownership; ordinary creation under a new name and unrelated profile deletion semantics must remain unchanged.

## Evidence

- **confirmed reproduction:** The reporter reproduced the same observable modal loop with custom and Default profile names, supplied recordings and a stack trace, and independently confirmed it on Windows and Ubuntu in https://github.com/microsoft/vscode/issues/305773.
