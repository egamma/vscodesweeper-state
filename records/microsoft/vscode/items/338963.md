# Issue #338963 — notebook.codeActionsOnSave does nothing when the notebook's first cell is markdown

[https://github.com/microsoft/vscode/issues/338963](https://github.com/microsoft/vscode/issues/338963)

## Summary

Confirmed in source: notebook-kind code actions (and the notebook format action) always run against `notebookModel.cells[0]` regardless of its cell kind, so when the first cell is markdown the action's language-scoped provider (e.g. Ruff for Python) never matches that cell's document and nothing happens, silently. This is a real, fairly broad-impact bug since starting a notebook with a markdown title cell is a very common convention; keeping open for a fix.

## Change summary

`notebook.codeActionsOnSave` (and notebook-level format-on-save) silently does nothing when the notebook's first cell is markdown instead of code.

## Best solution

In CodeActionOnSaveParticipant.participate and CodeActionParticipantUtils.checkAndRunFormatCodeAction (src/vs/workbench/contrib/notebook/browser/contrib/saveParticipants/saveParticipants.ts), stop anchoring notebook-kind actions on the literal first cell; pick the first cell whose kind/language the relevant provider would actually match (mirroring the `cell.cellKind !== CellKind.Code` skip pattern already used by TrimWhitespaceParticipant/TrimFinalNewLinesParticipant/InsertFinalNewLineParticipant in the same file), so a leading markdown cell no longer silently swallows the request.

- **Behavior:**

  > When notebook.codeActionsOnSave (or notebook-level formatOnSave) is configured and a notebook's first cell is markdown, the configured code action(s) should still be applied to the relevant code cell(s) on explicit save, instead of being silently skipped. Acceptance: a notebook with a markdown first cell and a code cell whose content a registered code-action/formatter provider would change gets that edit applied on save, matching behavior when the first cell is code.
- **Trace:**

  > CodeActionOnSaveParticipant.participate (saveParticipants.ts ~line 398) and CodeActionParticipantUtils.checkAndRunFormatCodeAction (~line 478) both hardcode `notebookModel.cells[0]` as the anchor cell whose text model is passed into getActionsToRun/applyOnSaveFormatCodeAction, with no regard for that cell's kind or language — so a markdown first cell causes the action's language-scoped provider to never match, producing a silent no-op. The boundary: do not change the cell-level code action path (editorCodeActionsOnSave, which already iterates all cells at line 434) or the excluded/included action filtering logic — only the anchor-cell selection for notebook-kind/format actions. Related code pattern to reuse: cellKind !== CellKind.Code filtering already used by TrimWhitespaceParticipant et al. in the same file.
- **Open decisions:**
  - Should the anchor cell be 'first cell with cellKind === Code', or should it try to match the specific language/provider for the configured action (and if so, how, given a provider is picked by document selector not by notebook awareness)?
  - If no code cell exists at all, should the action silently no-op (as today) or surface some indication to the user?
  - Does this selection logic need to change for both the notebook-kind code actions branch and the separate format-on-save anchor, or could/should they diverge?

## Evidence

- **root cause:** saveParticipants.ts line 398 (CodeActionOnSaveParticipant.participate, notebook-kind branch) and line 478 (CodeActionParticipantUtils.checkAndRunFormatCodeAction) both do `const cell = notebookModel.cells[0];` unconditionally and create a model reference only to that cell, with no check on cellKind or language.
- **why it silently no-ops:** applyOnSaveGenericCodeActions (line 494) calls getActionsToRun(model, codeActionKind, ...) against that single cell's text model; a provider like Ruff's organizeImports is registered for Python-language documents, so when cells[0] is the markdown cell its document selector never matches, actionsToRun is empty, and nothing is applied or logged as an error — exactly the reported symptom.
- **existing precedent in same file:** TrimWhitespaceParticipant (line 157), TrimFinalNewLinesParticipant (line 240), and InsertFinalNewLineParticipant (line 316) all explicitly skip cells where `cell.cellKind !== CellKind.Code`, showing the codebase already distinguishes markup vs code cells elsewhere in this exact file — the two cells[0] call sites are the outliers.
- **no existing test harness:** No dedicated unit/integration test file exists for saveParticipants.ts (only unrelated saveParticipant.test.ts files for codeEditor and extHost contributions), so there's no ready executable check to pin a fix against.
