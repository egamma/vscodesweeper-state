# Issue #336149 — GitHub Copilot Pet Achievements

[https://github.com/microsoft/vscode/issues/336149](https://github.com/microsoft/vscode/issues/336149)

## Summary

Keep open: this team-authored request asks for account-level achievement portability that the current application-shared storage does not explicitly provide independently of VS Code Settings Sync. No referenced fix or older canonical issue satisfies the factual-close bar for a team-authored item.

## Change summary

Persist Copilot Pet achievements with the user's GitHub identity so unlocked achievements transfer between devices and environments.

## Best solution

Define account-level persistence and merge semantics for pet achievements, preserving unlocks across devices without making machine-specific pet state portable. The design should clarify whether this uses VS Code Settings Sync or Copilot/GitHub account storage and how locally earned achievements are reconciled.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chatPetService.ts`, `src/vs/platform/userDataSync/common/globalStateSync.ts`
- **Validation:** Validate with two isolated VS Code user-data environments signed into the same intended account: unlock an achievement in the first, synchronize, and confirm it appears in the second without losing achievements earned independently there; machine-specific pet position must remain local.
- **Behavior:**

  > Pet achievements earned on one device should become available on another device associated with the same intended user identity. Independently earned achievements must merge without losing progress, and unlocked accessories should follow the corresponding achievements. Machine-specific presentation state, such as horizontal position, must remain local. Acceptance requires a two-environment account-sync scenario demonstrating transfer and merge behavior.
- **Trace:**

  > ChatPetService in src/vs/workbench/contrib/chat/browser/chatPetService.ts currently writes achievement, seen, and accessory keys to APPLICATION_SHARED storage with StorageTarget.USER and migrates older APPLICATION-scoped values. LocalGlobalStateProvider in src/vs/platform/userDataSync/common/globalStateSync.ts exports USER-targeted storage through Settings Sync, including APPLICATION_SHARED entries for the default profile. The original implementation at https://github.com/microsoft/vscode/pull/331883 explicitly states that this state is not GitHub, Copilot entitlement, or account data, which is where the requested behavior exceeds the existing path. The plan must establish the identity and persistence contract, conflict/merge behavior, and whether synchronization must work when VS Code Settings Sync is disabled. Do not broaden the work to machine-specific pet position or scale, and preserve idempotent unlock behavior and local-to-shared migration.
- **Open decisions:**
  - Must achievement portability work through the GitHub/Copilot identity when VS Code Settings Sync is disabled, or is enabling Settings Sync an acceptable product requirement?
  - When devices have different achievement sets or one device resets progress, should synchronization union unlocks permanently or propagate resets and removals?
