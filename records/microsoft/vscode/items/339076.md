# Issue #339076 — Call Stack pause header disappears when continued cleanup removes a newer stopped event

[https://github.com/microsoft/vscode/issues/339076](https://github.com/microsoft/vscode/issues/339076)

## Summary

Well-diagnosed race confirmed in current source: the `onDidContinued` cleanup filters `stoppedDetails` purely by `threadId`, so if a new `stopped` event for the same thread is pushed by `handleStop` before the older continued-cleanup's filter runs, the filter wipes out the newer stop record too, leaving the Call Stack pause header empty even though the thread is genuinely stopped.

## Change summary

Call Stack pause-reason header disappears because an older `continued` event's async cleanup removes a newer `stopped` event's record for the same thread.

## Best solution

In debugSession.ts, make the continued-cleanup only discard stop records that existed when the continued event was received (e.g. snapshot/tag records at the point `continued` is handled, rather than filtering the live array by threadId at cleanup time), so a stop added afterward for the same thread survives.

- **Trace:**

  > `onDidContinued` in src/vs/workbench/contrib/debug/browser/debugSession.ts (~line 1132) schedules cleanup via `statusQueue.run(affectedThreads, threadId => { this.stoppedDetails = this.stoppedDetails.filter(sd => sd.threadId !== threadId); ... })`. This filter is keyed only on `threadId`, not on which stop record was current when the continued event arrived. Meanwhile `handleStop` (~line 1353) does `this.stoppedDetails.push(event)` synchronously, before its own async thread-lookup/fetchThreads resolves — so a brand-new stop for the same thread can be pushed, and then wiped by the still-pending older continued-cleanup. `getStoppedDetails()` (line 987) and callStackView.ts's pause header (line 187) both treat an empty/filtered array as 'not paused for a reason'. The boundary: do not touch the `onDidInvalidated` cleanup path (debugSession.ts ~1326-1348), which intentionally clears and replays all stop records and is unrelated to this race; the fix should only change how the continued-cleanup decides which records to discard.
