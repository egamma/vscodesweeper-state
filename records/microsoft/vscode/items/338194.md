Acceptance: signed extensions install successfully in the supported environment, verifier execution succeeds, and invalid signatures remain rejected.
- **Behavior:**

  > Installing signed Marketplace extensions fails across multiple extensions on affected Fedora and Ubuntu systems, reporting UnknownError with Executed: false. Supported installations should have the runtime prerequisites needed to execute signature verification and install valid signed extensions. Failure diagnostics should distinguish an unavailable verifier runtime from an invalid extension signature. Signature enforcement must remain intact.
- **Trace:**

  > ExtensionDownloader.download() invokes ExtensionSignatureVerificationService.verify(), which imports @vscode/vsce-sign and converts exceptions from verify() into UnknownError with didExecute: false. The underlying exception text is retained only in trace output; ExtensionManagementService.downloadExtension() receives the result code and rejects installation in built distributions. The discussion at https://github.com/microsoft/vscode/issues/338194 points toward libssl.so.3 availability, but no captured verifier exception proves that cause, and the Ubuntu workaround also changes Settings Sync state. Linux dependency generation and Debian/RPM dependency lists are investigation leads, not confirmed defective files. First establish the failing native-runtime boundary; do not bypass verification or assume the installed extension publisher owns the defect.

- **Independent confirmations and reopening:** The supplied discussion records the original reporter's spontaneous recovery, another user's confirmation on two Fedora 45 machines, and a later Ubuntu 26.10 report on VS Code 1.142.0. The issue was reopened because the problem persisted; temporary recovery does not establish resolution.
- **Workaround evidence:** The October 16 comment reports installing the libssl.so.3 provider on Fedora Silverblue 45. The October 19 Ubuntu comment reports installing libssl3 together with disabling Settings Sync, restarting, and resyncing. These suggest a runtime dependency problem, but the combined Ubuntu workaround does not isolate which action mattered.
- **Current verification path:** src/vs/platform/extensionManagement/node/extensionSignatureVerificationService.ts calls @vscode/vsce-sign.verify(); a thrown exception becomes UnknownError with didExecute: false, and its error text is logged at trace level. This explains how the reported diagnostic can arise but does not identify the underlying exception.
- **Current installation failure path:** src/vs/platform/extensionManagement/node/extensionDownloader.ts passes the verifier's result code to ExtensionManagementService.downloadExtension() in src/vs/platform/extensionManagement/node/extensionManagementService.ts. In built distributions with verification enabled, UnknownError reaches the SignatureVerificationInternal failure path. This is core installation infrastructure, not evidence that the extensions being installed caused the failure.
