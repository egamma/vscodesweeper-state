# Issue #286332 — VS Code Feature Request: Extension API: Control Tree Item Expansion During Drag Operations

[https://github.com/microsoft/vscode/issues/286332](https://github.com/microsoft/vscode/issues/286332)

## Summary

Keep this accepted API request open: current main still automatically expands supported drag targets without extension-level control. It has 23 upvotes, explicit maintainer acknowledgment that new API is needed, and no verified canonical or landed implementation.

## Change summary

Allow extensions to prevent drag-hover expansion of selected tree items while preserving ordinary expansion and drag-and-drop elsewhere.

## Best solution

Design a narrowly scoped extension API that lets expensive or virtual tree nodes opt out of drag-hover expansion without disabling their normal expansion. Follow the Extension API process already confirmed by the area maintainer, preserving existing behavior for extensions that do not opt in.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTreeViews.ts`, `src/vs/workbench/api/browser/mainThreadTreeViews.ts`, `src/vs/workbench/browser/parts/views/treeView.ts`
- **Validation:** Use an extension-development fixture with a draggable item, a collapsed connection node whose getChildren records calls, and a folder target. Hover over the opted-out connection longer than 500 ms: it must remain collapsed without fetching children. Confirm explicit expansion still fetches children, ordinary folder hover-expansion still works, drops still reach their intended targets, and extensions without the new API retain existing behavior.
- **Behavior:**

  > Extensions need to prevent drag-hover from expanding selected connection or virtual nodes whose child resolution has expensive side effects. Such nodes must remain explicitly expandable, and dragging past them must not initiate child resolution. Folder hover-expansion and normal drag-and-drop must continue to work. Extensions that do not use the new capability must retain their current behavior.
- **Trace:**

  > In src/vs/workbench/browser/parts/views/treeView.ts, onDragOver returns autoExpand: true whenever a supported MIME type is present, without target-specific extension input. The shared tree adapter in src/vs/base/browser/ui/tree/abstractTree.ts expands the target after 500 ms. The stable TreeDragAndDropController declaration only exposes MIME types and drag/drop handlers, and the registration bridge in extHostTreeViews.ts and mainThreadTreeViews.ts has no expansion-policy channel. These paths establish the missing capability without executing the checkout; no connection-management runtime was exercised. Preserve ordinary expansion and existing default drag behavior, and do not broaden this into general manual collapsible-state management. https://github.com/microsoft/vscode/issues/300140 is already consolidated here; https://github.com/microsoft/vscode/issues/324498 is a related but closed broader proposal. The unresolved boundary is the public API contract, for which the maintainer explicitly requested the Extension API process.
- **Open decisions:**
  - Should expansion control be a persistent per-item opt-out or a drag-context-dependent controller callback, with the latter allowing different behavior for different dragged content?
  - Should the API control hover-expansion independently of drop acceptance, or define a combined drag-over contract that controls both?
