# Issue #193422 — Avoid unnecessary repaint in minimap during typing

[https://github.com/microsoft/vscode/issues/193422](https://github.com/microsoft/vscode/issues/193422)

## Summary

The unnecessary full minimap-decoration repaint remains directly visible in current source. This team-authored issue should stay open for a stateful dirty-region design and validation, rather than being consolidated with the broader Chromium repaint investigation.

## Change summary

Avoid clearing and redrawing the entire minimap decorations canvas when typing changes only a small region.

## Best solution

Track enough prior minimap-decoration state to update only dirty regions while preserving selection highlights, decorations, section headers, scrolling, and full invalidation when layout or theme changes.

## Plan brief

- **Likely files:** `src/vs/editor/browser/viewParts/minimap/minimap.ts`
- **Validation:** Use Developer Tools > Rendering > Paint flashing with the minimap enabled: typing within one line must repaint only the affected minimap region, while selection changes, decorations, section headers, scrolling, theme changes, and layout changes must continue rendering correctly.
- **Behavior:**

  > Typing within an existing line must not repaint the full minimap when only a small text or selection region changed. The minimap must still display selections, line highlights, decorations, and section headers correctly after edits and scrolling. Full-canvas invalidation remains acceptable for genuinely global changes such as layout or theme changes. Acceptance requires Paint flashing to show a bounded minimap update for the reported typing scenario without visual regressions in those decoration modes.
- **Trace:**

  > InnerMinimap.onSelectionChanged in src/vs/editor/browser/viewParts/minimap/minimap.ts marks the decoration layer dirty whenever typing moves the caret. InnerMinimap.renderDecorations then clears the entire decorations canvas and redraws every visible selection, decoration, and section header. By contrast, renderLines retains RenderData and limits putImageData to computed dirty vertical bounds. The uncertainty is the state and invalidation model needed across overlapping decorations, selection changes, scrolling, section headers, and global option/theme changes; choosing canvas APIs is an implementation detail. Do not alter minimap appearance, decoration ordering, or the existing text-layer rendering semantics. The broader Chromium behavior remains tracked separately at https://github.com/microsoft/vscode/issues/164503.

## Evidence

- **current source:** src/vs/editor/browser/viewParts/minimap/minimap.ts:1442-1445 marks decorations for rendering on every selection change, while renderDecorations at lines 1540-1569 clears the full decorations canvas with clearRect(0, 0, canvasInnerWidth, canvasInnerHeight) before redrawing all highlights and section headers.
- **existing delta path:** The text layer in src/vs/editor/browser/viewParts/minimap/minimap.ts:1960-2030 retains RenderData, computes dirty vertical bounds, and restricts putImageData to that range; the decorations layer has no equivalent retained-state or dirty-region path.
- **maintainer diagnosis:** https://github.com/microsoft/vscode/issues/193422#issuecomment-1724777465 identifies the same two-layer distinction and says the decorations renderer requires a delta-oriented reimplementation.
- **related issue:** https://github.com/microsoft/vscode/issues/164503 remains an open, broader Chromium/Remote Desktop investigation covering repaint coalescing across multiple editor regions; it does not replace this concrete core minimap optimization.
