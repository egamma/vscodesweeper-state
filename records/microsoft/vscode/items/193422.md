# Issue #193422 — Avoid unnecessary repaint in minimap during typing

[https://github.com/microsoft/vscode/issues/193422](https://github.com/microsoft/vscode/issues/193422)

## Summary

Current main still repaints the full minimap decorations canvas whenever typing moves the selection. This team-authored performance bug remains valid and needs a deliberate partial-invalidation design.

## Change summary

Avoid repainting the entire minimap decorations canvas for localized changes such as moving the cursor while typing.

## Best solution

Track the previously rendered minimap decorations and update only regions affected by selection, decoration, scroll, layout, or theme changes, while preserving the existing rendering order and appearance.

## Plan brief

- **Likely files:** `src/vs/editor/browser/viewParts/minimap/minimap.ts`
- **Validation:** With the minimap enabled and DevTools Rendering > Paint flashing active, type within one line and verify that only the affected minimap region flashes; additionally verify selection, decoration, section-header, scrolling, layout, and theme updates leave no stale pixels.
- **Behavior:**

  > Typing within a line should update only the minimap region whose text or decorations changed, rather than repainting the complete minimap. Selection highlights, diagnostics and other minimap decorations must retain their current appearance and z-order. Scrolling, resizing, theme changes, and section headers must not leave stale pixels. Acceptance includes comparing Paint Flashing before and after the change and exercising each full-invalidation scenario.
- **Trace:**

  > InnerMinimap in src/vs/editor/browser/viewParts/minimap/minimap.ts owns separate text and decorations canvases. Typing moves the cursor, onSelectionChanged() sets _renderDecorations, and renderDecorations() clears the complete decorations canvas before rebuilding all visible highlights; this conclusively preserves the reported behavior on current main. By contrast, renderLines() retains ImageData and writes only its computed dirty vertical range. The boundary is minimap rendering and invalidation: editor selection semantics, decoration ordering, scrolling behavior, and visual output must not change. The broader Remote Desktop symptom remains tracked at https://github.com/microsoft/vscode/issues/164503.
- **Open decisions:**
  - Should partial decoration rendering retain an ImageData buffer, diff the previous and current rectangles, or use another invalidation representation?
  - Which events must force a full repaint instead of a bounded repaint, particularly scrolling, layout changes, section headers, and theme changes?
  - How should the repaint-area contract be tested automatically given that existing editor tests do not instrument the minimap canvas rendering path?

## Evidence

- **current source path:** In src/vs/editor/browser/viewParts/minimap/minimap.ts, InnerMinimap.onSelectionChanged marks decorations dirty; render() then calls renderDecorations(), which executes clearRect(0, 0, canvasInnerWidth, canvasInnerHeight) before redrawing every visible selection and decoration.
- **contrasting optimized path:** The same file's renderLines() computes dirtyY1/dirtyY2 through _renderUntouchedLines() and limits putImageData() to that vertical range, while the decorations canvas has no equivalent partial-invalidation path.
- **maintainer diagnosis:** The issue's maintainer comment independently identifies the two-canvas design and states that the decorations renderer always clears and redraws the complete canvas.
