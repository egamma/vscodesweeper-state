# Issue #97190 — Provide some richer (optional) UI for custom tree views

[https://github.com/microsoft/vscode/issues/97190](https://github.com/microsoft/vscode/issues/97190)

## Summary

Keep this accepted, well-supported request open: current tree APIs cover filtering and rich hovers, but not embedded general-purpose inputs, inline editing, or a dedicated selection-details pane. Maintainers have explicitly consolidated input-box requests here; no verified older canonical or completed implementation supersedes it.

## Change summary

Expose optional native input controls and a selection-details pane in extension-contributed tree views.

## Best solution

Design optional tree-view APIs for the remaining input and details capabilities, preserving native keyboard navigation and accessibility without requiring extensions to rebuild their trees in webviews. Settle the public input/editing contract and details-pane scope before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTreeViews.ts`, `src/vs/workbench/api/browser/mainThreadTreeViews.ts`, `src/vs/workbench/browser/parts/views/treeView.ts`
- **Validation:** After agreeing the API contract, use an extension-host test extension contributing a native tree to exercise input acceptance/cancellation, focus restoration, and selection-driven details updates. Verify keyboard-only and screen-reader operation, and confirm existing filtering, rich hovers, selection, and expansion behavior remain unchanged.
- **Behavior:**

  > Extension authors can opt into native input and selection-details capabilities without replacing their tree with a webview. The discussion includes rich-query entry with associated actions and Explorer-like inline label editing; the original request also includes a details footer for selected items. Acceptance must cover the agreed input lifecycle, selection updates, keyboard and screen-reader interaction, and unchanged behavior for extensions that do not opt in.
- **Trace:**

  > The current stable TreeViewOptions, TreeView, TreeDataProvider, and TreeItem contracts in src/vscode-dts/vscode.d.ts contain no embedded-input, inline-edit, or dedicated details-pane API. ExtHostTreeViews.createTreeView in src/vs/workbench/api/common/extHostTreeViews.ts and MainThreadTreeViews in src/vs/workbench/api/browser/mainThreadTreeViews.ts bridge the existing surface to AbstractTreeView and TreeRenderer in src/vs/workbench/browser/parts/views/treeView.ts. Filtering and markdown hovers already exist and are explicitly checked off in the report; markdown messages and active-item observation are partial capabilities, not the missing controls. Maintainer comments at https://github.com/microsoft/vscode/issues/117502#issuecomment-784968713 and https://github.com/microsoft/vscode/issues/179938#issuecomment-1519891310 establish this issue as the destination for input-box requests. The uncertainty is the public control/editing contract and details-pane behavior, not whether the missing capability is already available. Preserve existing native-tree behavior and extension compatibility; this review made no changes or execution-based checks.
- **Open decisions:**
  - Should the public input API provide view-level query entry, per-item inline editing, or both, and what acceptance, cancellation, and validation behavior should each expose?
  - Should the details pane be a constrained native text/markdown surface or permit interactive content, and how should it represent multiple selected items?
