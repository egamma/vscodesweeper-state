# Issue #250442 — MCP sample confirmation should reuse LM confirmation logic

[https://github.com/microsoft/vscode/issues/250442](https://github.com/microsoft/vscode/issues/250442)

## Summary

The shared language-model consent platform is still missing: current source retains separate extension authentication and MCP sampling permission flows. Maintainers explicitly supported consolidation while preserving different consent granularity, so this accepted On Deck request should remain open for design.

## Change summary

Unify MCP sampling and extension language-model access on shared consent infrastructure without losing MCP-specific context and model restrictions.

## Best solution

Provide a common language-model access platform that supports extension-wide approval and granular MCP model permissions, while preserving separate consent for sampling during and outside tool calls. Resolve the grant scope and compatibility contract before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/common/mcpSamplingService.ts`, `src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts`, `src/vs/workbench/contrib/mcp/browser/mcpCommands.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatLanguageModelActions.ts`, `src/vs/workbench/api/common/extHostLanguageModels.ts`, `src/vs/workbench/api/browser/mainThreadLanguageModels.ts`
- **Validation:** Exercise an extension requesting authenticated LM access and an MCP server requesting sampling both during a tool call and from a delayed background request. Verify shared access management, independent in-tool/background grants, enforcement of selected model restrictions, extension-wide approval behavior, revocation, and preservation of existing grants across reload; add automated coverage for the agreed permission contract.
- **Behavior:**

  > Extensions and MCP servers should use a shared language-model consent platform rather than unrelated approval systems. MCP permissions must retain the distinction between requests during tool calls and background sampling, together with control over exposed models. Extensions must retain a convenient broad-approval option. Acceptance must cover approval, denial, revocation and reload persistence without silently broadening existing access.
- **Trace:**

  > McpSamplingService in src/vs/workbench/contrib/mcp/common/mcpSamplingService.ts owns contextual prompts, session grants, model selection and chat.mcp.serverSampling persistence. Extension access instead passes through ExtHostLanguageModels._getAuthAccess and MainThreadLanguageModels._registerAuthenticationProvider, keyed by the model-owning extension. ManageLanguageModelAuthenticationAction groups access by extension, while McpConfigureSamplingModels exposes a separate MCP model picker. The source confirms the platform split, but not a settled common grant contract. Preserve the existing distinction between sampling during and outside tool calls, and do not treat shared infrastructure as permission to expand trust. The agreed direction and unresolved extension-versus-vendor scope are recorded at https://github.com/microsoft/vscode/issues/250442#issuecomment-3013950119.
- **Open decisions:**
  - Should broad extension approval cover all models from the providing extension or only models from a selected vendor, including models added later?
  - How should existing extension-wide approvals and MCP sampling grants appear in the shared model-level access experience without requiring unnecessary reapproval or widening access?

## Evidence

- **Maintainer-supported direction:** The full discussion at https://github.com/microsoft/vscode/issues/250442#issuecomment-3013950119 proposes a shared platform with extension-wide approval and granular MCP permissions; https://github.com/microsoft/vscode/issues/250442#issuecomment-3014239156 endorses that direction while allowing a base-model compromise. This is accepted design work, not evidence that the current split should be declined as intentional.
- **Separate MCP consent remains:** src/vs/workbench/contrib/mcp/common/mcpSamplingService.ts implements its own _getMatchingModel, allowButtons and _showContextual flows, with separate allowedDuringChat/allowedOutsideChat grants and per-server allowedModels. getConfig/updateConfig persist those grants through chat.mcp.serverSampling rather than the extension authentication access mechanism.
- **Extension consent still has provider-wide scope:** src/vs/workbench/api/common/extHostLanguageModels.ts::_getAuthAccess requests an authentication session using INTERNAL_AUTH_PROVIDER_PREFIX plus the model-owning extension identifier. src/vs/workbench/api/browser/mainThreadLanguageModels.ts::_registerAuthenticationProvider explicitly registers one provider per extension, not per model.
