# Issue #250442 — MCP sample confirmation should reuse LM confirmation logic

[https://github.com/microsoft/vscode/issues/250442](https://github.com/microsoft/vscode/issues/250442)

## Summary

Keep open: current source still implements MCP sampling consent separately from extension language-model authorization. Maintainers explicitly supported a shared platform with different defaults, and the related account-menu cleanup did not deliver that integration.

## Change summary

Unify MCP sampling and extension language-model consent infrastructure while retaining their different model-access and request-context requirements.

## Best solution

Provide shared language-model access management for extensions and MCP servers, preserving granular MCP model restrictions and separate authorization during and outside tool calls. Settle how provider-wide extension grants coexist with model-level controls before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/common/mcpSamplingService.ts`, `src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts`, `src/vs/workbench/contrib/mcp/browser/mcpCommands.ts`, `src/vs/workbench/api/browser/mainThreadLanguageModels.ts`, `src/vs/workbench/services/authentication/browser/authenticationAccessService.ts`
- **Validation:** Exercise an extension LM request and MCP sampling against the same model provider, then inspect and revoke their grants through the agreed shared access surface. Verify that MCP model restrictions remain enforced, during-tool-call approval does not authorize background sampling, and existing grants retain their approved scope after migration.
- **Behavior:**

  > Extensions and MCP servers should use a coherent language-model consent and access-management platform instead of unrelated approval mechanisms. Extension-wide access must remain available without requiring repeated consent for each newly introduced model, while MCP servers retain model restrictions and separate permission for sampling during and outside tool calls. Acceptance must cover grant creation, inspection, revocation, and preservation of existing grants without silently broadening access. The product decision must specify how broad grants and model-level exceptions interact.
- **Trace:**

  > McpSamplingService in src/vs/workbench/contrib/mcp/common/mcpSamplingService.ts owns context-specific session grants, prompts, model filtering, and chat.mcp.serverSampling persistence independently of authentication access. McpConfigureSamplingModels in src/vs/workbench/contrib/mcp/browser/mcpCommands.ts writes per-server allowedModels. MainThreadLanguageModels._registerAuthenticationProvider in src/vs/workbench/api/browser/mainThreadLanguageModels.ts creates one synthetic authentication provider per providing extension and propagates allowed-extension access lists. These paths establish the remaining split without executing code. Preserve the distinction between MCP sampling consent and MCP server OAuth authentication, and do not weaken existing background-sampling or model-cost boundaries. The accepted design discussion is https://github.com/microsoft/vscode/issues/250442#issuecomment-3013950119; https://github.com/microsoft/vscode/issues/252677 explicitly treats the integration as unfinished after the account-menu cleanup. Uncertainty begins at the public semantics of broad versus granular grants and their migration, not at whether the current paths are separate.
- **Open decisions:**
  - Should the broad extension grant cover a providing extension or a model vendor, and how should explicit model denials interact with that grant?
  - How should existing provider-wide extension approvals and MCP sampling approvals appear in the shared access surface and carry forward without expanding their authorized scope?
