# Issue #245397 — Define + audit behavior for mixed-quality extension installation

[https://github.com/microsoft/vscode/issues/245397](https://github.com/microsoft/vscode/issues/245397)

## Summary

Keep open: current source contains quality-selection rules, but those rules do not establish completion of the requested UI/API behavior audit. No verified open canonical or concrete completing commit was found.

## Change summary

Define and audit release versus pre-release extension installation across Stable, Insiders, mixed-quality packs, and UI/programmatic entry points.

## Best solution

Establish an explicit installation-quality matrix, then document and test the agreed contract across extension-management entry points. Distinguish initial installation from changes to already-installed pack members rather than assuming all members must share one quality.

## Plan brief

- **Likely files:** `src/vs/platform/extensionManagement/common/abstractExtensionManagementService.ts`, `src/vs/platform/extensionManagement/common/extensionManagementCLI.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts`, `src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts`, `src/vs/workbench/contrib/extensions/test/electron-browser/extensionsWorkbenchService.test.ts`
- **Validation:** After agreeing the matrix, add parameterized installation tests covering Stable/Insiders, omitted/explicit release/pre-release selection, same/mixed-quality pack members, unavailable pre-release versions, and already-installed members. Exercise both workbench installation and workbench.extensions.installExtension, and run the relevant extensionsWorkbenchService unit suite; no tests were executed during this read-only review.
- **Behavior:**

  > Extension installation should have an explicit, predictable release/pre-release contract across Stable and Insiders and across UI and programmatic entry points. The contract must cover packs whose members have different available qualities and distinguish newly installed members from existing installations. Acceptance is a completed behavior matrix supported by executable tests, with any intentional entry-point differences documented.
- **Trace:**

  > AbstractExtensionManagementService in src/vs/platform/extensionManagement/common/abstractExtensionManagementService.ts derives the default quality preference from the product, adjusts it for the parent installation, and propagates it through getAllDepsAndPackExtensions. Existing members with matching application scope are skipped rather than automatically switched. ExtensionsWorkbenchService._install defaults identifier-based requests to the product preference, while workbench.extensions.installExtension exposes installPreReleaseVersion in extensions.contribution.ts; the CLI separately constructs installation options in extensionManagementCLI.ts. These paths identify the audit boundary, but source behavior alone does not settle the intended contract. Preserve unrelated installation, scope, and compatibility behavior, and do not treat synchronized switching of an entire installed pack as an accepted requirement: https://github.com/microsoft/vscode/issues/155109 declined that narrower request.
- **Open decisions:**
  - When a caller omits the quality option, should UI and programmatic installation share the same Stable/Insiders default, or intentionally have different defaults?
  - For newly installed pack members, should an explicit parent quality govern every member, or should members independently follow the product default when both qualities are available?
