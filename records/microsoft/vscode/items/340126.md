# Issue #340126 — Webview editor panels stall for minutes (suspect maxActiveHostResourceResponseBodies)

[https://github.com/microsoft/vscode/issues/340126](https://github.com/microsoft/vscode/issues/340126)

## Summary

Thoroughly diagnosed, source-confirmed defect: the webview service worker's host-resource-body semaphore (`maxActiveHostResourceResponseBodies = 32`) has no acquire timeout and only releases a permit when the response stream reaches EOF/error/cancel — a permit held by a never-fully-read or never-cancelled stream (e.g. a lazily-loaded/hidden restored tab) can starve new same-origin panels indefinitely. Worth routing to the webview area owner; no fix has landed.

## Change summary

Editor-tab webview panels of the same extension/view-type can stall for minutes (or until restart) because they share a fixed 32-permit semaphore in the service worker and a leaked/unreleased permit blocks new requests with no timeout.

## Best solution

Give the semaphore acquisition in service-worker.js a bounded wait (mirroring the existing 30s RequestStore resolveTimeout) and/or release permits proactively when a client/tab is hidden or discarded, so one stuck or never-finished stream can't starve all other same-origin panels indefinitely.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/webview/browser/pre/service-worker.js`
- **Validation:** A service-worker test (or manual repro) asserting that opening more same-origin panels than the permit limit, where one held stream is never read to completion, no longer blocks the next panel indefinitely — it should still resolve or surface a clear error within a bounded time.
- **Behavior:**

  > Opening a webview editor-tab panel whose origin is already at its host-resource-response-body permit limit must not hang forever if an earlier permit holder's stream never finishes being read. Panels should render within a bounded time or surface an error, not wait minutes with no indication to the user.
- **Trace:**

  > src/vs/workbench/contrib/webview/browser/pre/service-worker.js: `hostResourceResponseBodySemaphore.acquire()` (line 576) is awaited unconditionally with no timeout; `AsyncSemaphore.acquire()` (lines 112-133) queues callers in `this.waiters` when `activeCount >= maxConcurrency`, and a waiter is only resolved when `trackReadableStreamLifetime` (lines 182-218) fires its finish callback on stream EOF/error/cancel. A stream belonging to a backgrounded or lazily-restored tab may never be read to completion or cancelled, holding its permit indefinitely and starving new requests to the same origin. The limit itself (line 13, `maxActiveHostResourceResponseBodies = 32`) was added by commit 17d3b86b9361 (PR #326272) to fix FD exhaustion (issue #326092) — do not simply remove it, that reintroduces the original leak. Related: https://github.com/microsoft/vscode/issues/330243 on stable per-extension webview origins across sessions.
- **Open decisions:**
  - Should `acquire()` get a bounded timeout (like the existing 30s RequestStore timeout) that surfaces an error/retry instead of hanging forever, or should permits instead be proactively released when a client/tab becomes hidden or is discarded?
  - Is raising/making configurable the fixed limit of 32 an acceptable mitigation, or does that reintroduce the FD-exhaustion risk PR #326272 fixed?

## Evidence

- **semaphore has no timeout:** src/vs/workbench/contrib/webview/browser/pre/service-worker.js line 576 (confirmed on current main): `await hostResourceResponseBodySemaphore.acquire()` is awaited with no timeout; `AsyncSemaphore.acquire()` (lines 112-133) queues the caller in `this.waiters` indefinitely if `activeCount >= maxConcurrency`.
- **release tied to stream completion:** `trackReadableStreamLifetime` (lines 182-218) only calls the release callback on stream EOF, read error, or `cancel()` settling — a stream that is never fully read and never cancelled (plausible for a lazily-restored/hidden webview tab) keeps its permit forever.
- **limit origin:** Reporter correctly cites commit 17d3b86b9361 / PR #326272 (fixing FD exhaustion, issue #326092) as introducing `maxActiveHostResourceResponseBodies = 32` in 1.130.0; the limit and all cited line numbers match current main exactly.
- **shared origin across tabs:** Reporter notes VS Code keeps the webview origin stable per extension/view-type across sessions (see https://github.com/microsoft/vscode/issues/330243 for the analogous custom-editor case), so same-type panels in different windows share one semaphore instance via the one service worker.
