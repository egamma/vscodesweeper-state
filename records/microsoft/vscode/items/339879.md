# Issue #339879 — Agents: #339409 peer-chat recovery is undone when the phantom comes from a never-sent peer chat

[https://github.com/microsoft/vscode/issues/339879](https://github.com/microsoft/vscode/issues/339879)

## Summary

Confirmed in current main's source: `recoverChatSelectionCorruption` in agentHostPeerChatStore.ts (lines ~142-145) only marks a selected phantom verified if its backing chat DB has `agentHost.chatProviderData`, which a never-sent peer chat never writes — so that phantom stays registered, the recovery still completes and marks itself `completed: true`, and the still-registered phantom re-erases the parent's peer-chat catalogue on the next restore.

## Change summary

Peer-chat recovery (from #339476) can restore a session's peer-chat catalogue and then immediately lose it again when the phantom responsible was created by a peer chat that never sent a message.

## Best solution

Change the selected-phantom verification in `recoverChatSelectionCorruption` so it doesn't require `chatProviderData` for a phantom that is already selected/registered (the existing backing-dir path check is already strong evidence), and avoid persisting `completed: true` while any registered fragment phantom for the parent remains unverified — a maintainer should pick among the three approaches the reporter already sketched before an agent implements one.

- **Behavior:**

  > When a parent session's peer-chat recovery runs and one of the recoverable/selected phantoms was created by a peer chat that never sent a turn, that phantom must still be verified and unregistered like the others, and the recovery must not mark itself `completed` while any registered fragment phantom of the parent is still unverified. Acceptance: after recovery, no phantom belonging to the already-recovered parent remains registered, and a subsequent restore does not re-erase the parent's peer-chat catalogue.
- **Trace:**

  > In src/vs/platform/agentHost/node/agentHostPeerChatStore.ts, `recoverChatSelectionCorruption` verifies a phantom only via `CHAT_PROVIDER_DATA_METADATA_KEY` presence on its backing DB (around lines 142-145), which a never-sent chat never has, so it's excluded from `verifiedPhantomChatIds` even when `selected` is true. `_recoverChatSelectionCorruption` in agentService.ts (around line 3481) unregisters only the verified set and still allows `completed: true` to be persisted. The reported effect: the never-sent-chat phantom stays registered, is restored again shortly after, hits the original #339409 'not owned by' path, and re-erases the parent's recovered catalogue — and `completed: true` then blocks any further automatic retry. The fix must not weaken verification for the legacy/backup-driven (non-selected) candidates further up the same loop (lines ~120-137), which still need the existing remembered/deleted/backup checks. Related: https://github.com/microsoft/vscode/issues/339409, https://github.com/microsoft/vscode/issues/339476. Where the uncertainty starts: which of the reporter's three fix strategies to adopt — relaxing verification evidence for selected phantoms, unconditionally unregistering fragment-bearing restore registrations whose parent is registered, or deferring the `completed: true` write — since they differ in retry and unregistration semantics.
- **Open decisions:**
  - Should a selected phantom be verified from its backing-dir path check alone (no chat history required), or should VS Code instead always unregister restore-created fragment phantoms whose parent is registered, regardless of verification?
  - Should the recovery marker only be allowed to record `completed: true` once every currently-registered fragment phantom of the parent has been verified/unregistered, so an incomplete recovery can retry on a later launch?
