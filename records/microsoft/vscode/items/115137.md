# Issue #115137 — workbench.externalUriOpeners protocol glob patterns don't work

[https://github.com/microsoft/vscode/issues/115137](https://github.com/microsoft/vscode/issues/115137)

## Summary

Keep open: the documented `https://*` syntax works, but current source still does not support the requested `https:*` shorthand, which the discussion explicitly endorsed considering. This team-authored Backlog item has neither a verified fixing commit nor a qualifying duplicate.

## Change summary

Support scheme-only glob patterns such as `https:*` in `workbench.externalUriOpeners`.

## Best solution

Decide whether scheme-only shorthand should apply to opener configuration alone or to the shared URL-pattern contract, then implement and document the agreed behavior without changing existing host, port, or path matching.

- **Behavior:**

  > A user configures `workbench.externalUriOpeners` with `https:*` mapped to a registered opener and expects an HTTPS link to select that opener. Currently `https://*` works, but the shorter pattern does not. Acceptance should establish HTTPS-only matching, preserve existing pattern forms and opener-selection behavior, and make the accepted syntax discoverable in configuration documentation. Whether the same shorthand is accepted for trusted domains requires a maintainer decision.
- **Trace:**

  > ExternalUriOpenerService.getConfiguredOpenerForUri passes each configuration key directly to testUrlMatchesGlob in src/vs/platform/url/common/urlGlob.ts. That matcher recognizes an explicit scheme only when followed by `://`, so the reported `https:*` is interpreted as an authority pattern rather than a scheme selector. src/vs/workbench/contrib/externalUriOpener/common/configuration.ts documents patterns through additionalProperties, matching the author's final discovery that examples were attached to entries rather than the setting itself. The matcher is also consumed by src/vs/platform/url/common/trustedDomains.ts, so preserve existing host, port, path, and trust semantics outside the agreed scope. The discussion at https://github.com/microsoft/vscode/issues/115137#issuecomment-767795893 supports considering the shorthand but leaves its relationship to trusted domains unresolved. The older API umbrella https://github.com/microsoft/vscode/issues/109277 is related context, not a verified duplicate.
- **Open decisions:**
  - Should `https:*` become accepted syntax for both external URI opener patterns and trusted-domain patterns, or only for external URI opener configuration?
