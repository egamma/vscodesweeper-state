# Issue #314381 — Integrated terminals can inherit env vars from a previously opened repository/session

[https://github.com/microsoft/vscode/issues/314381](https://github.com/microsoft/vscode/issues/314381)

## Summary

The current source retains first-process environment keys that are absent from a later CLI window's environment, supporting the reported cross-repository contamination. Keep this open; correcting environment provenance needs investigation across window bootstrap and terminal environment construction.

## Change summary

Prevent integrated terminals opened in repository B from retaining repository A's project-specific environment variables from an earlier VS Code launch.

## Best solution

Make subsequent CLI windows' terminal environments reflect their own launch environment without resurrecting project-only variables from the surviving application process, while preserving normal shell initialization and explicit terminal environment overrides.

- **Behavior:**

  > A new integrated terminal in repository B must not acquire A-only project variables merely because VS Code was first launched from repository A and that application remains running. Variables explicitly exported by B's launching shell must remain available, including B's replacement values for overlapping keys. Acceptance uses distinct A-only, B-only, and overlapping sentinel variables with both windows open. Normal shell initialization and configured terminal environment overrides must remain intact.
- **Trace:**

  > The later CLI environment is forwarded by LaunchMainService.startOpenWindow, but preload.ts builds process.shellEnv by spreading process.env, shellEnv, and userEnv; missing keys in userEnv cannot erase first-process keys. The vscode:fetchShellEnv handler in app.ts similarly overlays the target window's environment onto process.env, while shellEnv.ts caches login-shell resolution for non-CLI launches. LocalTerminalBackend.getShellEnvironment supplies the merged result to TerminalProcessManager._resolveEnvironment and createTerminalEnvironment. This establishes the retention mechanism, not the exact fish/direnv runtime behavior. The uncertainty is how to establish a clean per-window baseline without altering other consumers of the shared bootstrap environment; enumerate those consumers and reproduce the macOS case before choosing a bounded implementation. Preserve intentional launch-variable inheritance, PATH initialization, and explicit overrides; terminal restoration and working-directory behavior in https://github.com/microsoft/vscode/issues/319200 are separate unless further evidence connects them.

## Evidence

- **source-reproducible inheritance path:** src/vs/base/parts/sandbox/electron-browser/preload.ts:74–89 constructs the shell environment as { ...process.env, ...shellEnv, ...userEnv }. When the application was initially launched with an A-only variable, a subsequent B userEnv lacking that key does not remove it. This directly accounts for the reported absent-in-B variable surviving into B's integrated terminal.
- **per-window CLI environment is available:** src/vs/platform/launch/electron-main/launchMainService.ts:startOpenWindow forwards userEnv for CLI launches. src/vs/code/electron-main/app.ts:658–681 also merges process.env with window.config.userEnv when handling vscode:fetchShellEnv. Neither merge treats absence from the later CLI environment as removal.
- **terminal consumes the merged environment:** ShellEnvironmentService.getShellEnv delegates to process.shellEnv; LocalTerminalBackend.getShellEnvironment memoizes that result. TerminalProcessManager._resolveEnvironment uses it when useShellEnvironment is enabled, and src/vs/workbench/contrib/terminal/common/terminalEnvironment.ts:createTerminalEnvironment copies the base environment before applying explicit overrides. No repository-specific cleanup removes an ordinary project variable such as COMPOSE_PROJECT_NAME.
- **existing setting is not isolation:** src/vs/platform/terminal/common/terminalPlatformConfiguration.ts:395–399 defines terminal.integrated.inheritEnv with default true. This controls shell-environment inheritance, not per-repository provenance; explicit null-valued terminal environment overrides can remove known keys but do not automatically isolate arbitrary A-only variables.
