# Issue #158853 — Tabs API does not allow to identify internal tabs

[https://github.com/microsoft/vscode/issues/158853](https://github.com/microsoft/vscode/issues/158853)

## Summary

This accepted Backlog request remains necessary on current main: internal editors still become an undefined extension-host tab input, webview tabs expose no backing resource, and the API cannot activate an existing tab. With 56 upvotes and direct downstream impact, it should remain open for API design.

## Change summary

Expose stable, nonlocalized identities and activation support for Settings, Keyboard Shortcuts, Markdown previews, and other tabs not represented by the existing typed Tab inputs.

## Best solution

Define a stable Tab API representation for non-resource editors and a way to activate an existing Tab without reopening it. Where a tab has a meaningful backing resource, such as Markdown preview, expose that association without inventing reopenable URIs for resource-less internal editors.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/browser/mainThreadEditorTabs.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/common/extHostEditorTabs.ts`, `src/vs/workbench/api/common/extHostTypes.ts`, `src/vs/workbench/api/test/browser/mainThreadEditorTabs.test.ts`, `src/vs/workbench/api/test/browser/extHostEditorTabs.test.ts`
- **Validation:** Add API-layer unit tests proving that Settings and Keyboard Shortcuts produce stable, nonlocalized tab identities instead of undefined inputs, that a Markdown preview exposes its agreed backing-resource relationship, and that the agreed activation operation selects the existing tab in its original group without reopening it; run the targeted MainThreadEditorTabs and ExtHostEditorTabs unit suites.
- **Behavior:**

  > Extensions enumerating tab groups must be able to identify Settings, Keyboard Shortcuts, Markdown previews, and other supported non-text tabs without relying on localized labels. They must be able to distinguish the same kind of tab across editor groups and activate an existing tab without reopening or duplicating it. Markdown previews should expose their backing document relationship if that is part of the chosen contract. Existing typed Tab inputs and tab-closing behavior must remain compatible.
- **Trace:**

  > `MainThreadEditorTabs._editorInputToDto` in src/vs/workbench/api/browser/mainThreadEditorTabs.ts converts only explicitly recognized EditorInput subclasses and falls back to `UnknownInput`; `ExtHostEditorTab._initInput` in src/vs/workbench/api/common/extHostEditorTabs.ts converts that fallback to undefined. SettingsEditor2Input and KeybindingsEditorInput are currently outside the recognized set, while the WebviewInput DTO carries only `viewType`. The stable declaration in src/vscode-dts/vscode.d.ts exposes no operation for activating a Tab, although the internal protocol already identifies tabs for move and close operations. Preserve the existing typed-input contracts and do not manufacture `vscode.open` URIs for editors that have no resource. https://github.com/microsoft/vscode/issues/162446 is related activation context but is closed and does not absorb this broader identity requirement.
- **Open decisions:**
  - Should non-resource editors expose specific public TabInput classes, or one generic opaque internal-editor input with a stable type identifier?
  - Should the public API add an operation that activates any existing Tab, or limit this work to identification and resource metadata?
  - Should resource-backed webviews such as Markdown preview expose their backing URI through TabInputWebview, or through a distinct preview/input contract?

## Evidence

- **current source gap:** In src/vs/workbench/api/browser/mainThreadEditorTabs.ts, `_editorInputToDto` recognizes a fixed set of editor classes and otherwise returns `TabInputKind.UnknownInput`; src/vs/workbench/api/common/extHostEditorTabs.ts maps that unknown kind to `undefined`.
- **internal editors:** SettingsEditor2Input in src/vs/workbench/services/preferences/common/preferencesEditorInput.ts and KeybindingsEditorInput in src/vs/workbench/services/preferences/browser/keybindingsEditorInput.ts are plain EditorInput subclasses not handled by `_editorInputToDto`; Keyboard Shortcuts has no resource, while Settings has a vscode-settings resource that is still not surfaced through the Tab API.
- **preview limitation:** The WebviewInput branch in src/vs/workbench/api/browser/mainThreadEditorTabs.ts serializes only `viewType`, and `TabInputWebview` in src/vscode-dts/vscode.d.ts likewise exposes only `viewType`, so a Markdown preview cannot identify its backing document through this API.
- **missing activation API:** The stable `TabGroups` API in src/vscode-dts/vscode.d.ts exposes tab/group change events and `close` overloads, but no operation to reveal or activate a Tab.
- **accepted demand:** The issue is in the Backlog milestone with 56 upvotes. A maintainer reopened it and said they would explore it at https://github.com/microsoft/vscode/issues/158853#issuecomment-1290526349.
- **related issues:** https://github.com/microsoft/vscode/issues/162446 is a younger, closed request limited to revealing a tab, and https://github.com/microsoft/vscode/issues/148085 remains open for moving tabs; neither is an older open canonical with the same observable symptom required for a re-reviewed duplicate close.
