# Issue #275220 — Should terminal auto approve use the tool approval UI?

[https://github.com/microsoft/vscode/issues/275220](https://github.com/microsoft/vscode/issues/275220)

## Summary

Keep open: terminal approvals still have their own controls rather than appearing in Manage Tool Approval. The existing configuration shortcut only partially covers the request, and neither verified related issue meets the stronger duplicate bar for this previously reviewed, team-authored item.

## Change summary

Expose run_in_terminal in Manage Tool Approval with an approve-all control and an action opening its auto-approval setting.

## Best solution

Make terminal approval preferences discoverable in the shared tool approval UI while retaining terminal-specific rules and existing enforcement. Settle the scope and persistence of the requested approve-all control before implementation; agent-host parity is related but does not replace this request.

- **Behavior:**

  > Users should find Run in Terminal in Manage Tool Approval even before configuring terminal approval rules. That entry should provide access to the terminal auto-approval setting and an approve-all control with an explicit, agreed scope. The resulting approval behavior must match the displayed scope without weakening existing policy restrictions or silently changing terminal rule semantics.
- **Trace:**

  > Manage Tool Approval calls LanguageModelToolsConfirmationService.manageConfirmationPreferences, whose relevant-tools filter depends on approval capability flags or a registered contribution. createRunInTerminalToolData has neither flag, and ChatAgentToolsContribution registers the terminal tool without such a contribution, leaving it outside the management tree. Existing terminal actions are generated by generateAutoApproveActions and handled by ChatTerminalToolConfirmationSubPart, including session-wide approval and opening chat.tools.terminal.autoApprove. The shared contribution contract already supports getManageActions and opting out of default approvals, but the current confirmation reference lacks prepared invocation data discussed in the thread. Preserve command analysis, terminal rule enforcement, policy restrictions, and existing invocation-level actions; this is a management-surface request, not authorization to redesign the permission engine. https://github.com/microsoft/vscode/issues/269610 provides settings-unification context, while https://github.com/microsoft/vscode/issues/326766 describes separate agent-host and SDK convergence work. The unresolved product boundary is what approve-all means in the shared manager and whether it persists beyond the session.
- **Open decisions:**
