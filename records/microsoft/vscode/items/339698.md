# Issue #339698 — References: Invalid URL read twice by NVDA

[https://github.com/microsoft/vscode/issues/339698](https://github.com/microsoft/vscode/issues/339698)

## Summary

Fresh, maintainer-authored a11y report testing an invalid/pending GitHub issue reference pill in chat — the reporter captured an exact NVDA transcript showing the link announced once inside the links-list dialog and again when focus returns to the document, so the repro is credible, but the exact DOM/ARIA cause (dual accessible-name sources on the anchor vs. browser URL exposure) isn't nailed down yet.

## Change summary

When a GitHub issue/PR chat reference link points at an invalid or still-loading number, NVDA announces both the link's descriptive label and its raw URL, effectively reading the link twice.

## Best solution

Investigate ChatRichLink's accessible-name handling for 'loading'/'failed' GitHub reference pills (src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatRichLink.ts) to see why the anchor's exposed name/description duplicates the URL in NVDA's link list and on focus, and ensure a single, clean announcement in those states.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatRichLink.ts`, `src/vs/workbench/contrib/github/browser/lazyGitHubResourceHover.ts`, `src/vs/workbench/contrib/github/browser/githubLinkPresentation.contribution.ts`
- **Validation:** A DOM-level check that the anchor's accessible name (via aria-label) doesn't also expose the raw href text a second time when in 'loading' or 'failed' state (e.g. no stray title/description attribute duplicating the URL), ideally confirmed manually with a screen reader.
- **Trace:**

  > ChatRichLink.update() (src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatRichLink.ts) sets the anchor's aria-label from presentation.ariaLabel and always removes title; the 'loading' state label text comes from lazyGitHubResourceHover.ts's getLoadingLabel / the loading fallback in chatRichLink's decorate(). What isn't yet established: why NVDA still reads the raw href a second time — whether another DOM node (authoredLabel span, a nested link, or the browser's native link-list URL column) is contributing a second accessible value, or whether this is simply how NVDA's Links List dialog surfaces href alongside the name (which could make it an upstream AT behavior rather than a VS Code defect).
- **Open decisions:**
  - Is the duplicate announcement caused by VS Code's DOM/ARIA markup (fixable here), or is it inherent to how NVDA's Links List dialog surfaces an anchor's href alongside its accessible name (not fixable in VS Code)?
  - If fixable, should invalid/loading GitHub reference pills suppress the href from the accessible tree entirely, or should the visible/announced label simply stop including redundant URL text?
