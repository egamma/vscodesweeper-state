# Issue #332126 — MSAL: stale session records in SecretStorage cause Settings Sync sign-out every ~1h

[https://github.com/microsoft/vscode/issues/332126](https://github.com/microsoft/vscode/issues/332126)

## Summary

Traced the reported failure mode in current main: the MSAL auth provider never removes an account whose silent-refresh fails with a permanent server error (e.g. invalid_grant/expired refresh token) — it just logs and `continue`s — and `getSessions`'s all-accounts dedup picks an arbitrary (possibly stale) account per homeAccountId. This matches the reporter's description of a stale/expired refresh token repeatedly causing Settings Sync sign-outs, and a second commenter confirms it still reproduces on 1.135.0, so this stays open for a maintainer decision on cleanup policy.

## Change summary

Personal Microsoft accounts accumulate stale MSAL session/cache records in SecretStorage that are never cleaned up, causing Settings Sync to sign out roughly every hour when a silent refresh hits one of the dead entries.

## Best solution

In extensions/microsoft-authentication/src/node/authProvider.ts, when getAllSessionsForPca's acquireTokenSilent fails with a permanent auth error (invalid_grant / interaction_required, not a transient/network error), call cachedPca.removeAccount(account) to prune the dead cache entry instead of only skipping it for that call; separately, decide whether to actively migrate/delete the legacy `pca:<clientId>` cache key once the new `pca:{clientId,authority}` format is populated (see the `// TODO: Remove the migrations in a version` note in publicClientCache.ts and accountAccess.ts).

## Evidence

- **no cleanup on silent-refresh failure:** extensions/microsoft-authentication/src/node/authProvider.ts getAllSessionsForPca (around line 530-540): on a caught AuthError from acquireTokenSilent, the code logs 'failed to acquire token silently, skipping account' and does `continue` — it never calls cachedPca.removeAccount(account), so the dead/stale account and its cache entry persist indefinitely.
- **arbitrary stale-account selection:** authProvider.ts getSessions() 'askingForAll' branch (lines 180-192) dedups accounts by homeAccountId using Map.set only when not already present, so whichever account entry MSAL's cache returns first for a homeAccountId wins — with multiple stale entries for the same user this can surface an old/expired one.
- **legacy cache keys never removed:** extensions/microsoft-authentication/src/common/accountAccess.ts and src/node/publicClientCache.ts read the legacy `accounts-<cloud>-<clientId>-<authority>` / `pca:<clientId>` keys once for a one-time migration ('TODO: Remove the migrations in a version') but do not delete the old keys, matching the reporter's observation of duplicate legacy+current cache entries.
- **reporter-provided repro/evidence:** Reporter's SecretStorage dump shows 5 session records and 2 PCA cache formats for one account; log excerpt shows AADSTS700082 (refresh token expired due to 90-day inactivity) from a token issued months earlier being used right after a fresh login.
- **unresolved on later release:** Comment from woobhurk (2026-08-28) reports the issue still persists in v1.135.0.
