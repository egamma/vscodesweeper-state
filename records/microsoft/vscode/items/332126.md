# Issue #332126 — MSAL: stale session records in SecretStorage cause Settings Sync sign-out every ~1h

[https://github.com/microsoft/vscode/issues/332126](https://github.com/microsoft/vscode/issues/332126)

## Summary

Detailed, well-evidenced bug in the built-in Microsoft authentication provider: SecretStorage accumulates dead legacy session/account keys that are migrated but never deleted, and the current MSAL code silently skips (rather than removes) accounts whose silent refresh fails — matching the reporter's logs and SecretStorage dump. Routing to the authentication area rather than closing.

## Change summary

Personal-MSA sign-ins to Settings Sync get silently signed out roughly every hour because stale/duplicate SecretStorage session and MSAL cache entries cause silent token refresh to fail and the account to be dropped.

## Best solution

Have the auth-provider owners investigate why a fresh interactive sign-in doesn't fully supersede a bad cached account entry in the live `pca:<clientId>` MSAL cache, and clean up the dead one-time-migration artifacts (`microsoft.login.keylist` legacy IStoredSession secrets, and the old `accounts-<cloud>-<clientId>-<authority>` key) that `extensions/microsoft-authentication/src/node/authProvider.ts` and `src/common/accountAccess.ts` migrate from but never delete.

## Evidence

- **unresolved TODO / no cleanup after migration:** extensions/microsoft-authentication/src/node/authProvider.ts `_migrateSessions()` reads legacy `IStoredSession` records via `BetterTokenStorage('microsoft.login.keylist', ...)`, migrates their refresh tokens into the PCA once (gated by `globalState.get('msalMigration')`), but never calls `deleteAll()` on the legacy storage — matching the reporter's dump of multiple untouched `f8cdef31-a31e-4b4a-93e4-5f571e91255a/1:live.com:<puid>/<guid>` secrets and the leftover `microsoft.login.keylist` key.
- **duplicate account-list keys never removed:** src/common/accountAccess.ts `AccountAccessSecretStorage.initialize()` migrates `accounts-<cloud>-<clientId>-<authority>` into `accounts-<cloud>` but leaves the old key in place (comment: 'TODO: Remove this method after a release with the migration'), matching the reporter's duplicate `accounts-AzureCloud` / `accounts-AzureCloud-<clientId>-<authority>` entries.
- **bad accounts are skipped, not evicted:** extensions/microsoft-authentication/src/node/authProvider.ts `getAllSessionsForPca()` (~line 538) catches `acquireTokenSilent` failures and only logs + `continue`s, never removing the offending account from the live MSAL cache, so a persistently invalid cached account keeps failing silent refresh on every check.
- **reporter's own diagnosis and workaround:** Reporter dumped `state.vscdb`, showed 5 stale session-shaped secrets plus duplicate legacy/current PCA cache keys for the same account, and confirmed that deleting the extension's SecretStorage keys (forcing a clean MSAL cache) resolves the repeated 1h sign-outs on both Windows and macOS.
