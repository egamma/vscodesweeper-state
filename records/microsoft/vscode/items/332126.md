# Issue #332126 — MSAL: stale session records in SecretStorage cause Settings Sync sign-out every ~1h

[https://github.com/microsoft/vscode/issues/332126](https://github.com/microsoft/vscode/issues/332126)

## Summary

Well-diagnosed report with a plausible root cause I could partly confirm in current main: `_migrateSessions`/`PublicClientApplicationsSecretStorage`/`AccountAccessSecretStorage` migrate old data forward but never delete the legacy SecretStorage keys, and `removeSession`/sign-out only clears the active MSAL cache, not those leftovers — consistent with the reporter's SecretStorage dump. Whether a stale legacy entry is actually re-read to cause the hourly silent-refresh failure (vs. a duplicate-tenant AccountInfo picked by the home-tenant preference in `getAllSessionsForPca`) isn't fully provable from source alone, so this needs an authentication-area engineer to confirm rather than a title-only close.

## Change summary

Settings Sync signs a personal Microsoft account out roughly every hour because stale/duplicate session and MSAL cache records accumulate in SecretStorage and are never cleaned up on sign-out or migration.

## Best solution

Authentication owners should verify whether stale legacy keys (`microsoft.login.keylist` items, `pca:{clientId,authority}`, `publicClientApplications-<cloud>`) or duplicate per-tenant `AccountInfo` entries in the live MSAL cache are the actual source of the failed silent refresh in `getAllSessionsForPca` (extensions/microsoft-authentication/src/node/authProvider.ts:451-544), then either delete leftover legacy keys after migration/sign-out or add a fallback to try other cached tenant entries for the same homeAccountId when the preferred one fails silently.

## Evidence

- **no legacy cleanup:** extensions/microsoft-authentication/src/node/authProvider.ts:117-139 `_migrateSessions` reads all old BetterTokenStorage sessions once (guarded by a `msalMigration` globalState flag) and migrates refresh tokens into the new PCA cache, but never calls `betterSecretStorage.deleteAll()` — the old `microsoft.login.keylist` and per-session secrets remain forever, matching the reporter's dump.
- **old key format not cleaned:** extensions/microsoft-authentication/src/node/publicClientCache.ts:275-291 and 305-318 migrate `publicClientApplications-<cloud>` (old, with authority) into `publicClients-<cloud>` (new) but never delete the old key; same pattern for `accounts-<cloud>-<clientId>-<authority>` in extensions/microsoft-authentication/src/common/accountAccess.ts:128-152.
- **sign-out doesn't touch legacy state:** extensions/microsoft-authentication/src/node/authProvider.ts:281-306 `removeSession` only removes matching accounts from the live MSAL PCA cache by homeAccountId; it has no path back to the legacy keys, matching the reporter's note that Accounts → Sign out didn't clear the stale records.
- **dedup-then-fail-silently:** extensions/microsoft-authentication/src/node/authProvider.ts:451-544 `getAllSessionsForPca` groups duplicate AccountInfo entries per homeAccountId and picks only the home-tenant entry to try `acquireTokenSilent`; on failure it just skips the account (`continue`) with no fallback to other cached tenant entries — consistent with the reporter's log showing one failed silent refresh causing `getSessions` to return 0 sessions.
- **shallow checkout:** Repo is a depth-1 shallow clone (`git rev-parse --is-shallow-repository` = true), so I could not check git history for an existing/attempted fix; none is referenced in the issue timeline either.
