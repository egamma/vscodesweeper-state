# Issue #251076 — File protocol links in editor do not open in WSL

[https://github.com/microsoft/vscode/issues/251076](https://github.com/microsoft/vscode/issues/251076)

## Summary

The bug remains in current main: editor link handling passes absolute `file:` URIs directly to the opener when the editor model uses a remote scheme, causing WSL paths to be interpreted on the Windows host. Keep it open under editor link handling and add WSL routing.

## Change summary

Absolute `file:///home/...` links in test-result editors and ordinary editors should open through the active WSL filesystem rather than the Windows host filesystem.

## Best solution

Make editor link resolution remote-aware so POSIX file URIs associated with a remote editor open through that editor's remote scheme and authority, while preserving intentional local-file links and existing relative-link behavior.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/links/browser/links.ts`, `src/vs/editor/contrib/links/test/browser/links.test.ts`
- **Validation:** Add and run an editor-links unit test covering a `vscode-remote://wsl+...` model with a `file:///home/...` link, plus regression cases showing local editor links and intentional host-file behavior remain unchanged.
- **Behavior:**

  > In an editor backed by WSL, activating an absolute POSIX `file:` link opens the corresponding file through the active WSL filesystem and honors any line location. The same behavior must hold in test-result message editors that use the default editor link detector. Existing local-workspace links and intentional client-local links must retain their current semantics.
- **Trace:**

  > Link activation reaches LinkDetector.openLinkOccurrence in src/vs/editor/contrib/links/browser/links.ts. Its special file-URI handling is gated by `modelUri.scheme === Schemas.file`; for a WSL-backed model that condition is false, and the original `file:///home/...` value is passed to IOpenerService as a host-local resource. The maintainer confirmation at https://github.com/microsoft/vscode/issues/251076#issuecomment-2960247698 establishes that this is the generic editor link path rather than test-result-specific rendering. The boundary is editor link resolution: terminal link detection and unrelated Agent Sessions link serialization must not change.
- **Open decisions:**
  - Should absolute `file:` links be mapped to the active remote scheme for every remote editor, or only for POSIX paths that cannot denote a valid client-local resource?
  - How should users intentionally open a client-local `file:` URI from a remote-backed editor after remote-aware resolution is introduced?

## Evidence

- **confirmed reproduction:** A VS Code maintainer confirmed the same failure with a file URI placed directly in an editor: https://github.com/microsoft/vscode/issues/251076#issuecomment-2960247698
- **current source:** In src/vs/editor/contrib/links/browser/links.ts, LinkDetector.openLinkOccurrence only applies file-URI path handling when the editor model itself has the `file` scheme. A WSL model uses a remote scheme, so the `file:///home/...` string reaches IOpenerService unchanged and is resolved as a host file.
- **canonical search:** https://github.com/microsoft/vscode/issues/233151 concerns relative `file://./...` links, while https://github.com/microsoft/vscode/issues/332310 concerns newer Agent Sessions path serialization; neither fully owns this issue's generic absolute-file-link behavior in remote editors.
