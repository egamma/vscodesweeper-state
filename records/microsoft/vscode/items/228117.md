# Issue #228117 — Perf telemetry for Code Actions from providers

[https://github.com/microsoft/vscode/issues/228117](https://github.com/microsoft/vscode/issues/228117)

## Summary

The requested provider-latency telemetry is still absent on current main: provider calls are timed only for trace logging, while the existing code-action event records application metadata rather than provider performance. This team-authored Backlog request should remain open for telemetry design and implementation.

## Change summary

Add performance telemetry for individual code-action provider invocations, including extension-provided checks used to decide whether actions are available.

## Best solution

Measure code-action provider latency at the invocation boundary and emit a GDPR-classified event with bounded trigger and provider metadata, without recording document paths or contents. The telemetry contract should distinguish completed, cancelled, and failed calls so performance analysis is meaningful.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/codeAction/browser/codeAction.ts`, `src/vs/editor/contrib/codeAction/test/browser/codeAction.test.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`
- **Validation:** Add a targeted code-action test using controlled providers and stub telemetry, asserting one latency event per selected provider with bounded trigger/outcome metadata and correct handling of completed, cancelled, and failed calls.
- **Behavior:**

  > VS Code records actionable latency telemetry when code-action providers are queried, including providers that perform availability checks before returning actions. Measurements distinguish successful, cancelled, and failed invocations and identify the trigger category without collecting document paths, source text, or action contents. Acceptance requires targeted tests proving that selected providers emit the expected bounded event and that cancellation and failure are classified consistently.
- **Trace:**

  > The shared invocation path is getCodeActions in src/vs/editor/contrib/codeAction/browser/codeAction.ts, where each selected provider's provideCodeActions method is awaited independently. That path currently has only a 1250ms progress callback; applyCodeAction later emits usage telemetry unrelated to provider latency. Extension-backed calls additionally pass through ExtHostLanguageFeatures._withAdapter in src/vs/workbench/api/common/extHostLanguageFeatures.ts, which computes elapsed time for trace logs but reports telemetry only on errors. Planning must establish whether the authoritative measurement surrounds the shared editor invocation or the extension-host adapter so calls are not double-counted and non-extension providers receive the intended treatment. Preserve provider concurrency, cancellation behavior, result filtering, and existing error handling.
- **Open decisions:**
  - What provider identity may the telemetry contract collect: a raw extension identifier, a reduced built-in/third-party category, or another privacy-preserving identifier?
  - Which invocation outcomes and trigger categories are in scope, and should high-frequency automatic queries be sampled while explicit and on-save queries are always recorded?
