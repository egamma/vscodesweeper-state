# Issue #350181 — Agents window: marking one file reviewed spawns 33 git processes, resolving the same context and working tree 2–3 times

[https://github.com/microsoft/vscode/issues/350181](https://github.com/microsoft/vscode/issues/350181)

## Summary

The review-click path still independently resolves the baseline and captures the working tree before and after a forced Branch refresh. Keep this performance issue open; the related reports address different sources of redundant work.

## Change summary

Reduce repeated Git context resolution and working-tree capture when marking Branch changeset files reviewed.

## Best solution

Make the review mutation and subsequent Branch publication avoid redundant Git work while preserving content-based review status when concurrent edits occur. Establish operation-scoped freshness and invalidation boundaries before sharing captured state across these services.

- **Behavior:**

  > Marking a file reviewed should not repeatedly resolve identical Git context or capture unchanged working-tree content within the resulting update. Published reviewed flags must remain content-based: an intervening edit must not remain reviewed because an older snapshot was reused. Acceptance includes lower Git-call counts for unchanged inputs, correct results after concurrent edits, and unchanged mark/unmark and legacy-ref behavior.
- **Trace:**

  > AgentService dispatch awaits setReviewState and forces refreshBranchChangeset. AgentHostReviewService._setReviewed resolves context and captures content; the refresh computes its fingerprint and Branch diff, then _computeReviewedInfo calls getReviewedPaths, which resolves context and captures content again. The remaining uncertainty is the safe lifetime of shared inputs across the review sequencer, asynchronous refresh scheduling, and external working-tree changes; the complete consumer and invalidation boundary has not been established.
