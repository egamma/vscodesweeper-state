# Issue #209023 — [json] Provide a way to disable the json-validation contribution point of a specific extension (e.g. ESLint)

[https://github.com/microsoft/vscode/issues/209023](https://github.com/microsoft/vscode/issues/209023)

## Summary

A real configuration gap remains: users cannot suppress one extension's static JSON-schema contribution while retaining the extension's other functionality. The Backlog feature request has no verified older canonical or maintainer decision supporting closure, so it should remain open for product discussion.

## Change summary

Allow users to disable or override the `jsonValidation` contribution from a specific extension without disabling that extension.

## Best solution

Define explicit precedence or enablement semantics for contributed JSON schemas, ideally allowing a user or workspace mapping to suppress a named extension contribution for selected files while preserving unrelated schemas and extension functionality. The JSON language-feature owners should decide the public configuration contract before implementation.

## Plan brief

- **Likely files:** `extensions/json-language-features/package.json`, `extensions/json-language-features/client/src/jsonClient.ts`
- **Validation:** Add JSON language-feature tests with an extension-contributed schema and a user schema for the same document, then verify the chosen suppression mechanism excludes only the selected contribution while retaining the user schema and unrelated contributed schemas.
- **Behavior:**

  > Users can keep an extension enabled while suppressing that extension's JSON-schema contribution for the affected file matching. A user- or workspace-configured replacement schema then applies without being merged with the suppressed contribution. Other capabilities of the extension and unrelated JSON-schema contributions remain active. Acceptance should cover both a direct file match such as `.eslintrc.json` and preservation of unrelated schema associations.
- **Trace:**

  > The reported path starts with an extension manifest `contributes.jsonValidation` entry, which the built-in JSON language features collect and forward to the JSON language service alongside user `json.schemas` associations. The missing product contract is selective suppression: the current issue record identifies no setting or command that disables one contributor without disabling the extension. The boundary is JSON schema association and precedence; ESLint execution, diagnostics, and unrelated contribution points must not change. https://github.com/microsoft/vscode/issues/230136 is related API work but is newer and addresses dynamic association rather than this observable suppression requirement.
- **Open decisions:**
  - Should suppression identify an extension as a whole, or individual schema associations by extension ID plus file match or schema URL?
  - Should a user or workspace schema automatically replace a conflicting contributed schema, or should suppression require an explicit opt-out setting?
  - Should suppression be configurable at user, workspace, and folder scopes, or only at workspace scope?
