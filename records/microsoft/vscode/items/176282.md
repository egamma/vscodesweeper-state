# Issue #176282 — Auto-attach remote session

[https://github.com/microsoft/vscode/issues/176282](https://github.com/microsoft/vscode/issues/176282)

## Summary

The accepted request remains unmet: serverReadyAction can start another debug configuration, but does not pass captured connection details into it. Keep this Backlog item open for designing that input contract; console selection and output duplication were addressed separately in the maintainer's response.

## Change summary

Allow connection details captured from server-ready output to supply the address and port of a subsequently started remote debugging session.

## Best solution

Define a supported way for serverReadyAction captures to populate the subsequent debug configuration, avoiding hard-coded device endpoints. Preserve existing named and inline configuration behavior, without expanding this work into output deduplication or task orchestration.

## Plan brief

- **Likely files:** `extensions/debug-server-ready/src/extension.ts`, `extensions/debug-server-ready/package.json`, `extensions/debug-server-ready/package.nls.json`
- **Validation:** Launch a debuggee that prints a dynamically selected inspector endpoint, then verify that serverReadyAction starts a Node attach session using that captured address and port without hard-coded endpoint values. Repeat with another endpoint and verify existing named, inline, and browser actions remain unchanged.
- **Behavior:**

  > A developer launches a local CLI that runs code on an external device and prints its inspector endpoint. The subsequent attach session should use the endpoint from that output rather than requiring each developer to edit an address and port in launch.json. Acceptance should cover two different endpoints with the same configuration and unchanged behavior for existing server-ready actions. Output deduplication and the separately reported console-selection behavior are outside the accepted feature scope.
- **Trace:**

  > ServerReadyDetector in extensions/debug-server-ready/src/extension.ts matches output and forwards the first capture through openExternalWithString to openExternalWithUri. Browser actions consume the resulting URI, but startDebugging invokes startDebugSession with only the configured name or inline object, losing the captured connection value. The schema in extensions/debug-server-ready/package.json exposes named and inline configurations without a capture-reference contract. The maintainer explicitly accepted passing inputs while leaving the design open at https://github.com/microsoft/vscode/issues/176282#issuecomment-1456735227. Preserve existing named configuration resolution, inline configurations, browser actions, and killOnServerStop semantics. The unresolved boundary is how users express captured values in the subsequent configuration, not whether the request should be supported.
- **Open decisions:**
  - What user-facing contract should expose serverReadyAction captures to the subsequent debug configuration: references usable in named configurations, substitution within inline configurations, or both?
  - Should the contract expose only the existing first capture, such as a complete inspector URI, or multiple captures so address and port can be supplied independently?

## Evidence

- **Maintainer accepted the scope:** https://github.com/microsoft/vscode/issues/176282#issuecomment-1456735227 explicitly supports passing inputs from serverReadyAction while noting layering concerns. It identifies console switching as expected existing behavior and explains why stdout/debugger-output deduplication is not reliably possible.
- **Current implementation still drops captured connection details:** In extensions/debug-server-ready/src/extension.ts, ServerReadyDetector.detectPattern forwards the first capture to openExternalWithString, which constructs a URI. However, openExternalWithUri's startDebugging branch passes only args.config or args.name to startDebugSession; the captured URI is not supplied to the new configuration.
- **Existing capabilities cover only part of the request:** extensions/debug-server-ready/package.json registers startDebugging with either a configuration name or an inline config. package.nls.json documents capture substitution for uriFormat, but that formatting belongs to URI/browser actions, not address/port substitution in the startDebugging configuration. Inline configuration support therefore does not deliver the central ask.
