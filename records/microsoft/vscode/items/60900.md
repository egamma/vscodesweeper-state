# Issue #60900 — Centered layout should be per workbench, not per editor area

[https://github.com/microsoft/vscode/issues/60900](https://github.com/microsoft/vscode/issues/60900)

## Summary

Keep this accepted, well-supported request open: current centered layout still centers within the editor area, so toggling a sidebar moves the editor even with fixed width enabled. This issue remains the appropriate tracker; no verified older canonical owns the same request.

## Change summary

Allow centered editors to remain centered within the whole workbench when sidebars toggle, moving or shrinking only when available space requires it.

## Best solution

Support workbench-relative centering that keeps the editor position and chosen width stable while sidebars fit in the surrounding space. Settle whether this replaces existing editor-area centering or is an opt-in mode, while preserving sash customization and constrained-window behavior.

- **Validation:** In a wide window, enable centered layout and toggle the primary sidebar on both sides, the secondary sidebar, and a side-positioned panel. Verify that the editor's workbench-relative center and chosen width remain unchanged whenever surrounding space suffices; then enlarge side parts or narrow the window and verify usable constrained layout without overlap. Repeat with fixed width enabled and disabled, inside and outside Zen mode, and check existing sash resizing and multi-group auto-resize behavior.
- **Behavior:**

  > Centered layout currently moves the editor when a sidebar opens because it centers within the remaining editor area. The requested behavior centers relative to the whole workbench and preserves the chosen width when side parts fit in the surrounding space. When space is insufficient, the editor should move or shrink only as necessary to remain usable. Acceptance should cover left and right sidebars, a side-positioned panel, narrow windows, and operation with and without Zen mode.
- **Trace:**

  > EditorPart constructs CenteredViewLayout in src/vs/workbench/browser/parts/editor/editorPart.ts and passes its own content dimensions through doLayout. CenteredViewLayout.layout and resizeSplitViews in src/vs/base/browser/ui/centered/centeredViewLayout.ts derive margins solely from that width; fixed-width mode changes width preservation, not the centering reference. Workbench side-part visibility and geometry are coordinated in src/vs/workbench/browser/layout.ts, outside this centered widget. The registrations in src/vs/workbench/browser/workbench.contribution.ts provide no workbench-relative centering option. Preserve existing sash customization and multi-group auto-resize semantics; floating sidebars and global enablement persistence are separate requests, not prerequisites. https://github.com/microsoft/vscode/issues/64666 was consolidated into this issue, while https://github.com/microsoft/vscode/issues/321806 is a newer overlapping request. The remaining product uncertainty is whether workbench-relative centering becomes the default or an additional selectable mode.
- **Open decisions:**
  - Should workbench-relative centering replace the current editor-area centering behavior, or should users explicitly opt into it while the existing mode remains available?
