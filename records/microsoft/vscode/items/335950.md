# Issue #335950 — getTask() and quickResolve() resolve tasks differently — side effect of an incorrect comparator?

[https://github.com/microsoft/vscode/issues/335950](https://github.com/microsoft/vscode/issues/335950)

## Summary

Confirmed in source: `getTask()` sorts `matchedTasks` with `.sort(task => task._source.kind === TaskSourceKind.Extension ? 1 : -1)` — a single-argument function used where `Array.prototype.sort` requires a two-argument comparator, so the second element is always ignored and the callback returns `-1` for every pair (since `matchedTasks` here never contains extension-sourced tasks). That's a comparator that violates the sort contract (never consistent for `compareFn(a,b)`/`compareFn(b,a)`), which in V8 manifests as an effective reversal, while `quickResolve()` picks `foundTasks[0]` from the unsorted, definition-ordered list — so identically-defined duplicate tasks resolve differently depending on the code path, exactly as reported.

## Change summary

getTask() (picker/direct resolution) and quickResolve() (dependsOn resolution) pick different tasks when duplicate task labels exist, because getTask() sorts matches with a broken (arity-mismatched, always-`-1`) comparator while quickResolve() takes the first definition order.

## Best solution

Fix the sort calls in `getTask()` (src/vs/workbench/contrib/tasks/browser/abstractTaskService.ts, around lines 977 and ~995) to use a proper two-argument comparator, e.g. `(a, b) => (a._source.kind === TaskSourceKind.Extension ? 1 : 0) - (b._source.kind === TaskSourceKind.Extension ? 1 : 0)`, which is a stable sort that preserves original definition order among non-extension tasks and aligns `getTask()`'s resolution with `quickResolve()`'s first-match behavior.
