Each returns -1 for a configured task even when comparing equally ranked configured tasks, violating comparator consistency and disturbing definition order.
- **Reported trigger and differing paths:** The three PreTask shell definitions in https://github.com/microsoft/vscode/issues/335950 make the ordering difference observable. _findWorkspaceTasks at lines 919-939 collects configured tasks in iteration order; quickResolve at lines 1971-1994 takes foundTasks[0] without sorting, whereas _executeTask at lines 2075-2087 re-resolves direct user launches through getTask after saving.
- **Broader scope:** The complete issue also identifies scope differences and fallback behavior. In abstractTaskService.ts:1997-2031, getResolverData overwrites label-map entries as it iterates tasks, so fullResolve can select the last matching label; fixing getTask's comparators alone does not establish consistency across every resolver path.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/339992 is currently OPEN and explicitly says Fixes #335950. Its description proposes removing the workspace-path sort and using a two-argument grouped-task comparator, with regression tests for duplicate-label order and configured-task precedence. This is an unmerged candidate, not a completed fix.
