# Issue #333203 — First usage of skill command from agent plugin is not recognized

[https://github.com/microsoft/vscode/issues/333203](https://github.com/microsoft/vscode/issues/333203)

## Summary

Real, independently corroborated bug: the first plugin/agent-skill slash command invoked after a window load reaches the model as plain text instead of the resolved skill/prompt content, and the chat UI even mis-highlights it as if it executed. A second reporter reproduced it reliably on 1.138.0 stable with a different plugin source and pinned it to a missing `promptFile` entry in `variableData` on first use after reload — this stays open pending a deeper trace since I found no related fix on main.

## Change summary

The first invocation of a slash command backed by an agent-plugin skill/command after a window (re)load is sent to the model as literal text instead of resolving to the skill's prompt file content; subsequent invocations in the same window work correctly.

## Best solution

Trace why the plugin/skill prompt-file content isn't attached to `variableData` on the very first slash-command send after a window load (likely a lazy-initialization or caching race in the plugin/prompt discovery path) and ensure the resolution completes before the request is dispatched, or the send is blocked/awaited until it does.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts`, `src/vs/workbench/contrib/chat/common/plugins/agentPluginServiceImpl.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts`
- **Validation:** A chat test that sends a plugin/skill slash command immediately after simulating a fresh window load / first plugin discovery and asserts the resulting request's variableData contains the resolved promptFile entry (not just the literal slash text).
- **Behavior:**

  > The first slash-command invocation of an agent-plugin skill/command in a freshly loaded (or just-reloaded) chat window must resolve to the skill/command's prompt file content the same way later invocations do — the model must receive the actual SKILL.md/command body, not the literal `/plugin command` text, and the chat UI must not show the 'skill executed' highlight when it did not. Acceptance: sending such a command as the very first chat message after a window load produces the same resolved request payload as sending it a second time.
- **Trace:**

  > Two independent reports place the defect in the path that turns a recognized plugin/skill slash command into a request: the stored request's `prompt` part correctly names the plugin/skill (`<plugin>:review-docs`), but `variableData` is missing the corresponding `promptFile` entry only on the first invocation after a window load or reload — every subsequent invocation in the same window attaches it correctly. This points to a lazy/caching race in plugin or prompt-file discovery (candidates: src/vs/workbench/contrib/chat/common/plugins/agentPluginServiceImpl.ts, src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts) that isn't awaited before the first send, in src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts. I did not isolate the exact race in this review (no checkout execution was attempted per the read-only constraint) — where uncertainty starts: whether the fix is awaiting plugin/skill discovery before allowing the first send, or eagerly warming the cache during plugin activation.
- **Open decisions:**
  - Should the first send of a plugin/skill command block until plugin/prompt discovery completes, or should discovery be warmed eagerly when a plugin is enabled/loaded?
  - Does the same race affect workspace prompt files after a reload (one comment notes a workspace prompt file's first use also succeeded but a plugin command right after it still failed), meaning the fix may need to target the plugin-specific discovery path specifically rather than the general prompt-file resolution path?

## Evidence

- **original repro:** Reporter shows on 1.135.0 that the first `/dummy print-hello-world` (a skill from a `chat.pluginLocations` plugin) is sent as plain text and not turned blue/recognized, but every later invocation works.
- **independent corroboration:** Comment from spinozaredux reproduces the same class of defect on 1.138.0 stable (commit 7debcd0) with a different plugin source (git marketplace `chat.plugins.marketplaces`), pinpointing that the stored request's `prompt` message part is `<plugin>:review-docs` but `variableData` lacks the `promptFile` entry for the command body on the first use after each `Developer: Reload Window`, and that `code chat -m agent '/<plugin> review-docs'` reproduces it scriptably.
- **no fix found:** No commits in src/vs/workbench/contrib/chat/common/plugins/agentPluginServiceImpl.ts on main touch this first-use behavior (`git log` shows only an unrelated merge commit); the relevant prompt-file attach path (chatWidget.ts, promptsServiceImpl.ts, agentPluginServiceImpl.ts) was not fully traced in this review.
