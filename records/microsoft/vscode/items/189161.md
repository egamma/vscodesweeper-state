# Issue #189161 — Opening the quick pick with a <path>@<symbol> pattern does not enter the symbol navigation mode

[https://github.com/microsoft/vscode/issues/189161](https://github.com/microsoft/vscode/issues/189161)

## Summary

Keep open: current source still intentionally excludes initial <path>@<symbol> input from symbol navigation, and the maintainer identified file-path disambiguation as the prerequisite for supporting it. This issue remains the canonical report; the later paste-related request was closed into it.

## Change summary

Support opening Quick Open with a complete <path>@<symbol> query without requiring incremental typing.

## Best solution

Extend Quick Open to resolve an initial file-and-symbol query while preserving access to filenames containing @. Establish how ambiguous or non-exact file prefixes should behave before implementing the enhancement in AnythingQuickAccessProvider.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts`, `src/vs/workbench/contrib/terminalContrib/links/browser/terminalLinkOpeners.ts`
- **Validation:** In a development build, create a symbol-bearing file and verify that pasting its complete path@symbol into a fresh Ctrl+P picker, and opening the equivalent terminal link, enters that file's symbol results without further typing. Verify that an existing literal filename containing @ still opens normally, incremental filename-then-@ navigation remains unchanged, and ambiguous/non-exact queries follow the agreed policy.
- **Behavior:**

  > A complete <path>@<symbol> query supplied when Quick Open opens should support navigating symbols in the named file without incremental typing. Single-paste input should offer the same capability. Existing literal file paths containing @ must remain accessible, and ordinary incremental symbol navigation must retain its behavior. Acceptance includes fresh-picker and terminal-link scenarios, literal @ filenames, and the agreed handling of ambiguous file prefixes.
- **Trace:**

  > AnythingQuickAccessProvider resets lastOriginalFilter and lastGlobalPicks on each picker run in src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts. _getPicks enables editor symbol search only after prior filtering, and getEditorSymbolPicks resolves symbols from lastGlobalPicks.active rather than independently resolving the file prefix. These deliberate requirements explain the initial-query limitation. The terminal search-link fallback in src/vs/workbench/contrib/terminalContrib/links/browser/terminalLinkOpeners.ts passes the complete text to quickAccess.show. Preserve literal @ path handling established by https://github.com/microsoft/vscode/issues/93845 and do not change global workspace-symbol search or terminal line/column navigation. https://github.com/microsoft/vscode/issues/218209 confirms the single-paste manifestation and was closed into this report. The unresolved product boundary is whether initial symbol navigation requires an exact file prefix or may select a fuzzy match when no literal full-query file exists.
- **Open decisions:**
  - When the complete query is not a literal existing file path, should initial <path>@<symbol> navigation require an exact file-prefix match, or may it use Quick Open's best fuzzy file match?
