# Issue #336663 — Flaky macOS/WebKit test: virtual wall and monotonic clocks stay consistent

[https://github.com/microsoft/vscode/issues/336663](https://github.com/microsoft/vscode/issues/336663)

## Summary

Fresh, well-diagnosed flaky-test report from a maintainer with a plausible root cause traced in the shared time-API restore helper; keep it open for the assigned owner, no evidence yet of a landed fix.

## Change summary

The virtualScheduling unit test comparing restored `performance.timeOrigin` to its pre-install snapshot occasionally fails by 1ms on macOS/WebKit CI.

## Best solution

In `pushGlobalTimeApi` (src/vs/base/test/common/virtualScheduling/globalTimeApi.ts), avoid falling back to `Reflect.deleteProperty` for `performance.timeOrigin` when no own descriptor existed before install — capture and re-freeze the actual pre-install value on restore instead of letting a possibly-nondeterministic native getter be re-invoked; or, if the underlying getter is legitimately non-deterministic in WebKit, loosen the test's exact-equality assertion for the restored origin to a small tolerance.

## Plan brief

- **Likely files:** `src/vs/base/test/common/virtualScheduling/globalTimeApi.ts`, `src/vs/base/test/common/virtualScheduling/virtualScheduling.test.ts`
- **Validation:** A test exercising pushGlobalTimeApi/dispose against a mocked `performance` object whose `timeOrigin` is an inherited (prototype) accessor returning slightly different values on successive calls, asserting the restored read matches the pre-install snapshot exactly.
- **Behavior:**

  > The `virtual wall and monotonic clocks stay consistent` test asserts that after installing and then disposing the virtual time API, `performance.timeOrigin` reads back exactly the value it had before installation. On macOS/WebKit CI this occasionally differs by 1ms. The fix should make the restored value stable and deterministic regardless of any native timing jitter in the underlying `performance.timeOrigin` implementation, without changing virtual-clock behavior while the API is installed. Acceptance: the flaky assertion no longer fires under repeated/mocked runs simulating a jittery native getter.
- **Trace:**

  > `captureGlobalTimeApi`/`pushGlobalTimeApi` (src/vs/base/test/common/virtualScheduling/timeApi.ts, globalTimeApi.ts) snapshot `performance.timeOrigin` by reading `Object.getOwnPropertyDescriptor(globalThis.performance, 'timeOrigin')`; if that attribute lives on the Performance prototype rather than as an own property (likely in WebKit per the IDL spec), the descriptor is undefined and `dispose()` falls back to `Reflect.deleteProperty`, which re-exposes the prototype's native getter instead of restoring a frozen value — a plausible cause of the observed 1ms drift, though unconfirmed without running WebKit itself. The boundary: do not change behavior while the virtual API is actively installed, only how `performance.timeOrigin` is restored on dispose. Related: https://github.com/microsoft/vscode/commit/d790d7d957f685337ab8a7f15e6dbd74f4ffe139 (#327980, introduced the assertion) and https://github.com/microsoft/vscode/actions/runs/35290385962/job/105431736782 (failing run).
- **Open decisions:**
  - Should the fix harden `pushGlobalTimeApi` to always restore an explicit frozen value instead of deleting the property, or is the underlying native `performance.timeOrigin` genuinely non-deterministic in WebKit, making a tolerant test assertion the right fix instead?
  - If the API is hardened, should the same treatment apply to `performance.now`'s descriptor restore for consistency?

## Evidence

- **capture path:** captureGlobalTimeApi/pushGlobalTimeApi in src/vs/base/test/common/virtualScheduling/{timeApi.ts,globalTimeApi.ts} snapshot `performance.timeOrigin` via `Object.getOwnPropertyDescriptor(globalThis.performance, 'timeOrigin')`; per the Performance IDL this attribute is typically defined on the prototype, not as an own property, so the descriptor lookup can return undefined.
- **restore fallback:** dispose() in globalTimeApi.ts calls `Reflect.deleteProperty(globalThis.performance, 'timeOrigin')` when no own descriptor was captured, which falls back to re-invoking the native (prototype) getter on the next read instead of returning a frozen snapshot — a plausible source of the observed 1ms drift specific to WebKit's implementation.
