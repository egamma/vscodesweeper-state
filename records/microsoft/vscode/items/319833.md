# Issue #319833 — Who can tell me? Set the rollback for synchronization. Should I regress to the left or the right? Can we have more obvious signs?

[https://github.com/microsoft/vscode/issues/319833](https://github.com/microsoft/vscode/issues/319833)

## Summary

The current Settings Sync history UI makes each row's identical Restore action easy to misinterpret. This is a valid, still-present UX clarity gap that should be routed to Settings Sync.

## Change summary

Make it clearer which Settings Sync history snapshot will replace the user's current data when Restore is selected.

## Best solution

The Restore action and confirmation should identify the selected resource snapshot, including its date or relative position, so users can distinguish restoring the newer versus older entry before replacing current data.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/userDataSync/browser/userDataSyncViews.ts`
- **Validation:** Add or extend a Settings Sync activity-view action test to invoke Restore on two differently dated handles and assert that each confirmation identifies the selected snapshot distinctly while the confirmed action replaces that same handle.
- **Behavior:**

  > Every Restore control in Settings Sync history must make clear that it restores the snapshot on its own row. Before current settings, extensions, keybindings, or snippets are replaced, the confirmation must identify the selected snapshot sufficiently to distinguish adjacent history entries. Remote and local history must remain distinguishable, and cancelling must leave current data unchanged.
- **Trace:**

  > The activity views are registered as `Sync Activity (Remote)` and `Sync Activity (Local)` by `UserDataSyncDataViews.registerActivityView` in src/vs/workbench/contrib/userDataSync/browser/userDataSyncViews.ts. `UserDataSyncActivityViewDataProvider.getSyncResourceHandles` gives each snapshot a repeated resource label plus a relative-time description. `registerDataViewActions` contributes an identical inline `Restore` action to every snapshot and confirms replacement using only the word “selected”, although the subsequent `replace` call targets the clicked handle's timestamp and URI. The boundary is the activity-history restore experience; conflict-resolution actions and synchronization behavior should not change.
- **Open decisions:**
  - Should the selected snapshot be identified by its exact timestamp, relative age, source machine, or a combination of those details in the Restore affordance and confirmation?
  - Should remote and local activity use different restore wording when both views are visible?

## Evidence

- **current source:** src/vs/workbench/contrib/userDataSync/browser/userDataSyncViews.ts registers the same inline `Restore` title and `Codicon.discard` icon for every `sync-resource-*` history row in `registerDataViewActions`, without distinguishing one snapshot from another.
- **confirmation ambiguity:** The confirmation in src/vs/workbench/contrib/userDataSync/browser/userDataSyncViews.ts asks only whether to replace the current resource “with selected”; it does not name the selected snapshot timestamp, machine, or whether it came from remote or local activity.
- **snapshot semantics:** UserDataSyncActivityViewDataProvider renders repeated resource labels with relative-time descriptions, while the action passes that row's `syncResourceHandle.created` and URI to `IUserDataSyncService.replace`; each icon therefore restores its own row, but the final confirmation does not expose that identity.
