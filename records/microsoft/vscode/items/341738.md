# Issue #341738 — The multi-diff editor forgets collapsed state

[https://github.com/microsoft/vscode/issues/341738](https://github.com/microsoft/vscode/issues/341738)

## Summary

Thanks for the clear repro. I traced it in the source: when the staged file leaves the group, the multi-diff widget loses its active item and re-runs its 'select first change' step, which expands the collapsed first file.

## Change summary

Staging a file from the SCM multi-diff editor re-expands a diff the user had collapsed.

## Best solution

Make the widget's automatic first-change navigation skip expanding collapsed items. It should only run on the initial load, not when an active item is removed from the list. Collapsed state set by the user should survive item removal.

## Plan brief

- **Likely files:** `src/vs/editor/browser/widget/multiDiffEditor/multiDiffEditorWidgetImpl.ts`, `src/vs/editor/browser/widget/multiDiffEditor/multiDiffEditorViewModel.ts`
- **Validation:** A test (or manual steps) with 3 changed files: collapse file 1, stage file 2 from inside it, and assert file 1 stays collapsed.
- **Behavior:**

  > In the SCM multi-diff editor, a diff the user collapsed stays collapsed when another file is staged and removed from the list. The initial open still selects and reveals the first change. Acceptance: collapse file 1, stage file 2, and file 1 is still collapsed.
- **Trace:**

  > The 'Initialize first change' autorun in multiDiffEditorWidgetImpl.ts re-fires when `activeDiffItem` becomes undefined after the focused item is removed. It calls `_navigateToChange('next')`, then `_goToFile`, which un-collapses item 0. The fix stays inside this navigation or initialization path. Do not change the explicit go-to-next/previous-change commands, which intentionally expand collapsed items. Where the uncertainty starts: whether to keep the item un-collapsing only for explicit navigation, and what should be active after removal.
- **Open decisions:**
  - When the active item is removed, should the editor pick a new active item, or leave none active? Either way, collapsed files must not be auto-expanded.
  - Should the automatic first-change selection on open still expand a collapsed first item restored from view state?

## Evidence

- **repro path:** In src/vs/editor/browser/widget/multiDiffEditor/multiDiffEditorWidgetImpl.ts, the 'Initialize first change' autorun (~line 293) runs whenever `viewModel.activeDiffItem` is undefined and loading is complete. It then calls `_navigateToChange('next')`.
- **active item cleared:** `activeDiffItem` (multiDiffEditorViewModel.ts) keeps the focused item, or its last value only while that item is still in `items`. Staging the focused file removes it from the SCM group, so `activeDiffItem` becomes undefined and the autorun fires again.
- **expansion:** `_navigateToChange` finds currentIndex -1 and calls `_goToFile(0, 'first')`. That sets `collapsed.set(false)` on the first item (lines ~660-664), which is the reported re-expansion.
- **resource source:** ScmResolvedMultiDiffSource in src/vs/workbench/contrib/multiDiffEditor/browser/scmMultiDiffSourceResolver.ts rebuilds the resources list from `group.onDidChangeResources`, so a staged file is dropped from the unstaged view.
