# Issue #125310 — iPad: context menu appears when releasing a long tap

[https://github.com/microsoft/vscode/issues/125310](https://github.com/microsoft/vscode/issues/125310)

## Summary

The release-only behavior remains in the current source: a stationary long press dispatches the context-menu gesture only from touchend. Keep this accepted Backlog bug open; the related iPad double-menu reports describe a different symptom and are newer.

## Change summary

Show the iPad editor context menu when a long press qualifies, without requiring the user to lift their finger.

## Best solution

Make iOS long-press feedback follow the native interaction described in the discussion, while preserving touch scrolling, selection, and other platforms' intended behavior. Plan the shared gesture change and verify the complete press-to-release interaction on an iPad before implementation.

## Plan brief

- **Likely files:** `src/vs/base/browser/touch.ts`, `src/vs/editor/browser/controller/pointerHandler.ts`, `src/vs/editor/browser/controller/mouseHandler.ts`
- **Validation:** On an iPad, press and hold editor text without moving: the context menu must appear while contact remains down, and releasing must neither reopen nor accidentally activate it. Check that a short tap still positions the cursor, a drag still scrolls without opening a menu, and Windows touch behavior remains consistent with the platform convention. The plan should identify an automated gesture-timing check covering the same event sequence.
- **Behavior:**

  > A stationary long press in an iPad text editor currently gives no context-menu feedback until the finger is released. The menu should appear once the long press qualifies while the finger remains down, without duplicate opening or accidental activation on release. Short taps and scrolling must retain their existing behavior. Other platforms should preserve their intended native interaction rather than inherit an unconditional iOS timing change.
- **Trace:**

  > Gesture in src/vs/base/browser/touch.ts records contact in onTouchStart and recognizes the long press only in onTouchEnd using HOLD_DELAY and movement bounds. In src/vs/editor/browser/controller/pointerHandler.ts, both PointerEventHandler and TouchHandler subscribe to that synthetic Contextmenu event and forward it through MouseHandler._onContextMenu in src/vs/editor/browser/controller/mouseHandler.ts. This conclusively explains the reported release-only trigger without executing the UI. The shared gesture utility also serves surfaces beyond the editor; their complete lifecycle requirements and the effects of subsequent touchmove/touchend on an already-open menu were not established in this review. The discussion at https://github.com/microsoft/vscode/issues/125310 favors native platform behavior and calls out accessibility timing. Keep unrelated native-menu duplication and touch-selection work outside this issue.

## Evidence

- **Current source reproduces the timing defect:** In src/vs/base/browser/touch.ts, Gesture.HOLD_DELAY is 700 ms. onTouchStart records the contact but schedules no hold callback; onTouchEnd dispatches EventType.Contextmenu only after release when the hold exceeds that delay and movement remains under 30 pixels on each axis. Keeping the finger stationary cannot trigger that synthetic menu before touchend.
- **Affected editor path:** In src/vs/editor/browser/controller/pointerHandler.ts, PointerHandler selects PointerEventHandler on iOS with pointer-event support. PointerEventHandler registers Gesture.addTarget on linesContentDomNode and forwards EventType.Contextmenu to MouseHandler._onContextMenu. The fallback TouchHandler uses the same gesture event, so neither path supplies a hold-time trigger.
- **Maintainer direction:** The supplied discussion on https://github.com/microsoft/vscode/issues/125310 acknowledges the missing feedback and identifies the shared Gesture utility's Windows-era behavior. It favors native platform conventions, notes that iOS menus should appear before release, and explicitly raises accessibility-dependent timing. This supports retaining the issue, not declining the request as designed.
- **Canonical search:** Open-issue searches for long press, long tap, and context-menu hold behavior found no verified older canonical for this symptom. https://github.com/microsoft/vscode/issues/170345 and https://github.com/microsoft/vscode/issues/194871 are open but concern overlapping native and VS Code menus after mouse or trackpad right-click; both are newer than this re-reviewed issue. The older https://github.com/microsoft/vscode/issues/47770 requests touch-drag text selection, not long-press menu timing.
- **Verification boundary:** The release-only dispatch is confirmed by source inspection, not by executing an iPad session. No fixing commit was established. Changes to the shared gesture lifecycle still need validation of menu behavior while contact continues and when the finger is subsequently released.
