# Issue #100274 — Git - Support `subst` drives

[https://github.com/microsoft/vscode/issues/100274](https://github.com/microsoft/vscode/issues/100274)

## Summary

Keep open: commenters confirmed that Git path mismatches persisted after the advertised improvements, and current source does not establish complete subst support. The newer Explorer-root regression is separate and does not absorb this report.

## Change summary

Preserve Git integration and workspace file identity when a repository is opened through a Windows subst drive.

## Best solution

Make the built-in Git extension consistently associate repository resources with the substituted workspace path, so decorations and diff navigation work without opening physical-path duplicates. First isolate the remaining failure on current Windows builds, distinguishing repository-root discovery from mixed-alias resource lookup.

## Plan brief

- **Likely files:** `extensions/git/src/git.ts`, `extensions/git/src/model.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/decorationProvider.ts`, `extensions/git/src/quickDiffProvider.ts`
- **Validation:** On Windows with current VS Code and Git versions recorded, run the issue's subst/repository setup for both a repository beneath the substituted drive and one at its root. Modify and save a tracked file; verify Explorer modification decorations, SCM paths under the substituted workspace, working Open Changes navigation, and Open File returning to the existing workspace-path editor. Repeat with a physical-path editor already open to identify ordering-dependent alias failures; retain normal-drive and submodule behavior.
- **Behavior:**

  > Opening a Git repository through a subst drive should retain working Explorer decorations, gutter changes, and diff navigation for workspace files. SCM resources should use the substituted workspace path rather than creating physical-path duplicates of those files. Acceptance covers repositories at the substituted drive root and in a subdirectory, with current VS Code and Git versions recorded. The empty-Explorer regression and third-party GitLens behavior must be distinguished from the built-in Git acceptance checks.
- **Trace:**

  > Git.getRepositoryRoot in extensions/git/src/git.ts already preserves an alias through relative rev-parse output for Git 2.31+, while the original Git 2.27 case bypasses that branch. Model.getRepositoryExact in extensions/git/src/model.ts deduplicates physical and alias roots, but getOpenRepository performs lexical containment against the stored root only. Repository status resources are constructed under that stored root, GitDecorationProvider uses exact URI keys, and GitQuickDiffProvider depends on the same repository lookup. The discussion confirms failures after the 1.99 improvements, but inspection cannot determine why the reported modern-Git setup selected physical-path resources. Begin with the documented Windows setups and capture discovered roots and resource URIs before attributing the remaining defect to a particular consumer. Preserve ordinary repository identity, submodule selection, and intentional exclusion of symbolic-link file entries. https://github.com/microsoft/vscode/issues/252361 tracks the separate directory-enumeration regression and is not a canonical for this work.

GitQuickDiffProvider.provideOriginalResource in extensions/git/src/quickDiffProvider.ts:42–45 rejects resources when that repository lookup fails. These paths explain why recognizing repository aliases alone does not ensure integration for both file spellings.
