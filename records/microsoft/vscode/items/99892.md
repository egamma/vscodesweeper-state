# Issue #99892 — Ellipsis in search viewlet shows more UI, not commands

[https://github.com/microsoft/vscode/issues/99892](https://github.com/microsoft/vscode/issues/99892)

## Summary

The search details control still uses an ellipsis to expand persistent include/exclude inputs. Keep this team-authored UX debt open: the inconsistency remains, and the discussion has not settled the replacement affordance.

## Change summary

Replace the Search view's overflow-style ellipsis with an affordance that clearly communicates expanding and collapsing search details.

## Best solution

Agree on a disclosure design that is distinguishable from the neighboring Replace toggle, then apply it to the Search view without changing filtering semantics. Consider the maintainer's request for an indication of active filters while details are collapsed.

- **Behavior:**

  > The Search view currently presents an ellipsis that expands persistent include/exclude inputs rather than opening an overflow menu. Mouse and keyboard activation, accessible state, and filtering behavior must remain functional. Whether collapsed active filters receive a visible indication needs explicit agreement.
- **Trace:**

  > searchDetailsIcon in src/vs/workbench/contrib/search/browser/searchIcons.ts defaults to Codicon.ellipsis. SearchView renders it in searchView.ts and routes mouse and keyboard activation through toggleQueryDetails, which updates stored expansion state, aria-expanded, visibility, focus, and layout. The existing workbench.action.search.toggleQueryDetails command invokes this same path, so command access does not resolve the visual inconsistency. The discussion at https://github.com/microsoft/vscode/issues/99892#issuecomment-653703691 identifies conflicting adjacent chevron meanings and hidden active filters; https://github.com/microsoft/vscode/issues/99892#issuecomment-653727429 leaves the design for UX discussion. Preserve search semantics, existing expansion behavior, and keyboard access; the later complaint about automatic expansion does not establish an agreed change to restoration policy. searchDetailsIcon also has consumers in quickTextSearch/textSearchQuickAccess.ts, so a shared icon change must not inadvertently alter unrelated navigation affordances.
- **Open decisions:**
  - Which disclosure presentation should replace the ellipsis while remaining distinguishable from the adjacent Replace toggle?
  - Should collapsed search details visibly indicate active non-default filters, and what should that indication communicate?
