# Issue #100522 — Silence the startup command printout in Integrated Terminal

[https://github.com/microsoft/vscode/issues/100522](https://github.com/microsoft/vscode/issues/100522)

## Summary

Keep open: the debug-terminal launch path still submits the full startup command without a suppression option. The request was explicitly accepted as a feature request, and subsequent Java and C# reports reinforce the need; the existing workarounds do not preserve the requested interactive-terminal experience.

## Change summary

Provide an option to hide debugger startup commands in the integrated terminal while retaining application output and interactive terminal functionality.

## Best solution

Design an opt-in quiet launch experience for integrated-terminal debugging that preserves input, cursor control, launch arguments, and environment setup. Keep command suppression distinct from filtering application or runtime diagnostics, and establish supported-shell behavior before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/api/node/extHostDebugService.ts`, `src/vs/workbench/contrib/debug/node/terminals.ts`, `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`, `src/vs/workbench/api/browser/mainThreadTerminalShellIntegration.ts`, `src/vs/workbench/contrib/terminal/browser/terminalInstance.ts`
- **Validation:** Using a DAP debug configuration with console set to integratedTerminal, launch a program with a long argument list that immediately prints a marker, reads stdin, and performs cursor positioning. With quiet launch enabled, verify that the startup command is absent from the viewport and scrollback, the first output marker is retained, interaction works, and cwd/environment/arguments are unchanged. Repeat on initial launch and terminal reuse, with shell integration enabled and disabled, across the agreed supported shells; verify unchanged behavior when the option is disabled.
- **Behavior:**

  > Integrated-terminal debugging currently exposes the full debugger-generated startup command, obscuring the beginning of application output. Users should be able to opt out of that command display without switching to the Debug Console or losing stdin and terminal cursor control. Acceptance must cover both a newly created terminal and a reused terminal, preserving early application output and correct launch parameters. Whether debugger/runtime diagnostic banners are included remains a separate scope decision.
- **Trace:**

  > ExtHostDebugService.$runInTerminal in src/vs/workbench/api/node/extHostDebugService.ts handles the integrated DAP launch, selects or creates a terminal, builds the command using prepareCommand in src/vs/workbench/contrib/debug/node/terminals.ts, and submits it through shell integration or sendText. MainThreadTerminalShellIntegration.$executeCommand in src/vs/workbench/api/browser/mainThreadTerminalShellIntegration.ts forwards the integrated path to TerminalInstance.runCommand in src/vs/workbench/contrib/terminal/browser/terminalInstance.ts. The existing debug.terminal.clearBeforeReusing setting clears before submission and does not meet the central ask. Source inspection establishes the missing launch option, but does not establish a portable suppression mechanism across shells. Preserve quoting, cwd/environment handling, terminal reuse, user-entered commands, and application output; do not treat task echo controls or fixed terminal width as equivalent solutions. https://github.com/Dart-Code/Dart-Code/issues/2563 and https://github.com/microsoft/vscode-dotnettools/issues/705 identify this issue as the core request.
- **Open decisions:**
  - Should quiet launch suppress only the injected command, or also debugger/runtime startup banners such as Node's inspector messages?
  - Must quiet launch work without shell integration on every supported shell, or may unsupported terminal configurations retain command echo with an explicit limitation?
  - Should the opt-in apply globally to integrated-terminal debugging or be selectable per debug launch configuration?

## Evidence

- **Current launch path:** src/vs/workbench/api/node/extHostDebugService.ts, ExtHostDebugService.$runInTerminal, constructs the launch command with prepareCommand and submits it through terminal.shellIntegration.executeCommand(command) or terminal.sendText(command). Neither branch offers startup-command suppression.
- **Command construction and shell-integration boundary:** src/vs/workbench/contrib/debug/node/terminals.ts, prepareCommand, includes executable arguments, working-directory changes when needed, and environment assignments. src/vs/workbench/api/browser/mainThreadTerminalShellIntegration.ts:112-113 forwards shell execution to terminal.runCommand(commandLine, true); shell integration alone is not a quiet-launch option.
- **Existing-capability check:** src/vs/workbench/contrib/debug/browser/debug.contribution.ts:558-562 registers debug.terminal.clearBeforeReusing, which clears previous content before launching rather than suppressing the new command. Task presentation.echo is registered in src/vs/workbench/contrib/tasks/common/jsonSchema_v2.ts and controls task presentation, not this DAP runInTerminal flow. Searches of debug and terminal configuration registrations found no equivalent launch-command suppression setting.
- **Accepted feature and insufficient workarounds:** https://github.com/microsoft/vscode/issues/100522#issuecomment-649673033 explicitly reopens the discussion as a feature request after explaining shell echo. The reporter explains that the Debug Console lacks the interactive input and absolute cursor positioning their application needs, and confirms that set +x does not suppress the injected launch command.
- **Independent demand and ownership:** https://github.com/microsoft/vscode/issues/100522#issuecomment-759962784 reports multiple Java users affected. https://github.com/Dart-Code/Dart-Code/issues/2563#issuecomment-645267780 identifies VS Code's DAP RunInTerminalRequest handling as the owning surface. https://github.com/microsoft/vscode-dotnettools/issues/705#issuecomment-1806086046 directs the same C# startup-command complaint to this issue.
