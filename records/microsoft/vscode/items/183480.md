# Issue #183480 — "Search files by name" is slow when using remote

[https://github.com/microsoft/vscode/issues/183480](https://github.com/microsoft/vscode/issues/183480)

## Summary

Keep open: multiple reporters confirm substantial remote Quick Open delays, including recent reports from large workspaces. Neither the merged logging changes nor the fork optimization establishes a landed fix for this reopened issue.

## Change summary

Remote filename searches become disproportionately slow in large workspaces, with successive keystrokes delaying the latest results.

## Best solution

Profile the built-in remote Quick Open pipeline and remove the demonstrated bottleneck while preserving fuzzy ranking, cancellation, caching, and multi-root behavior. Evaluate the linked fork against the actual native search path rather than assuming server-side scoring is absent.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts`, `src/vs/workbench/api/node/extHostSearch.ts`, `src/vs/workbench/services/search/node/rawSearchService.ts`, `src/vs/workbench/services/search/common/fileSearchManager.ts`, `src/vs/workbench/services/search/test/node/rawSearchService.integrationTest.ts`
- **Validation:** Retest the same large workspace locally and remotely, comparing cold and warm Quick Open searches, rapid character-by-character entry, and pasting the identical query. Record ripgrep, extension-host, and end-to-end timings plus RPC result counts; verify superseded queries do not delay the latest results and ranking remains unchanged. Establish a repeatable baseline and measurable acceptance threshold before implementing.
- **Behavior:**

  > In large remote workspaces, typing a filename into Quick Open can delay visible results for seconds or longer, even when enumeration itself is fast. The latest query should produce responsive results without accumulating delays from superseded input. Acceptance must cover cold and cached searches, typed versus pasted queries, and multi-root workspaces while preserving existing matching and ranking semantics.
- **Trace:**

  > AnythingQuickAccessProvider requests scored, limited searches and passes cancellation tokens through the search service. NativeExtHostSearch registers node/rawSearchService.SearchService for built-in filesystem search, whose sorted path already filters and ranks remotely before emitting matches. Cached filtering traverses cached entries synchronously, followed by arrays.topAsync sorting; these are investigation targets, not a proven complete diagnosis. The fork at https://github.com/maruthgoyal/vscode/commit/c1812b0179b8d56faaeac9ec565145bb7a623920 changes common/FileSearchManager, so its adoption and relevance to the reported native path must be established. Reporter reproductions confirm the symptom, but this read-only review did not execute a current-build performance reproduction. Preserve result limits, cancellation semantics, cache reuse, multi-root coverage, and fuzzy ordering; do not conflate the separate text-search cancellation issue with this report.
