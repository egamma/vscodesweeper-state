## Change summary

Disabling GPU and software rasterization is a confirmed workaround, not evidence that normal startup is fixed.

## Evidence

- **Report and trace:** https://github.com/microsoft/vscode/issues/193948 reports a 3–5-second empty-workspace startup regression in Code - OSS 1.82.2 on Arch Linux with KDE/X11 and no installed extensions. The reporter supplied startup marks and the requested runtime trace; the subsequent maintainer response identified a similar case in the older report.
- **Verified related report:** https://github.com/microsoft/vscode/issues/192493 was verified OPEN and was created on 2023-09-07. It documents the same 1.81-to-1.82 Linux startup regression with an empty workspace and extensions disabled. Its discussion distinguishes a corrected storage/shutdown problem from the remaining renderer-startup delay.
- **Runtime ownership:** https://github.com/microsoft/vscode/issues/192493#issuecomment-1731229132 identifies the untraced regression between window.loadUrl() and workbench script loading as runtime work, and explains that tracing changes the timings. The maintainer linked this exact diagnosis after reviewing the trace supplied for the issue under review.
- **Reporter confirms shared workaround:** In https://github.com/microsoft/vscode/issues/192493#issuecomment-1938556540, jurisevo confirms that --disable-gpu --disable-software-rasterizer improves startup on the affected Mesa Intel UHD Graphics machine. https://github.com/microsoft/vscode/issues/192493#issuecomment-1938926095 documents applying those flags to the desktop launcher.
- **Current-source limits:** Read-only inspection of src/mainImpl.ts found runtime tracing through contentTracing.startRecording and hardware-acceleration configuration through app.disableHardwareAcceleration. These facilities do not establish that default startup on the reporter's Linux graphics stack is fixed; no executable reproduction or concrete fixing commit was established.
