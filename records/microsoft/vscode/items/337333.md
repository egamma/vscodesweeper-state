# Issue #337333 — Dictation first-run experience does not clearly indicate model download

[https://github.com/microsoft/vscode/issues/337333](https://github.com/microsoft/vscode/issues/337333)

## Summary

Team-authored feature request (author is a VS Code maintainer) describing a real, confirmed UX gap — the dictation onboarding waveform UI gives no visual cue while the speech model is still downloading. Team-authored items are protected from judgment closes, and this is a legitimate ask anyway, so it stays open.

## Change summary

The Dictation waveform UI gives no clear 'model is downloading' indicator on first run, even though the microphone icon already shows a download treatment elsewhere.

## Best solution

Surface the model-download state inside the waveform card itself (e.g. a 'Downloading speech model…' label/spinner in place of or alongside the waveform) in src/vs/workbench/contrib/chat/browser/speechToText/dictationOnboarding.ts, sourced from whatever event already drives the existing mic-icon download treatment.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/speechToText/dictationOnboarding.ts`, `src/vs/workbench/contrib/chat/browser/speechToText/media/dictationOnboarding.css`
- **Validation:** A test in src/vs/workbench/contrib/chat/test/browser/dictationOnboarding.test.ts asserting the onboarding UI renders a downloading-state indicator when the model is not yet ready, and reverts to the normal waveform once ready.
- **Behavior:**

  > When Dictation is opened and the speech/model backend is still downloading, the onboarding card should visibly communicate that state (e.g. a short 'Downloading speech model…' message or spinner) instead of showing an active-looking waveform that silently does nothing when the user speaks. Once the model finishes downloading, the UI should transition to the normal live waveform. Acceptance: a new/updated test in dictationOnboarding.test.ts confirms the downloading indicator appears while the model is not ready and disappears once it is.
- **Trace:**

  > DictationOnboarding and MicrophoneWaveform in src/vs/workbench/contrib/chat/browser/speechToText/dictationOnboarding.ts start the waveform (this.waveform.start()) without checking any model-readiness/download state — traced via rg across the file, no 'download'/'loading'/status references found. The issue states a download treatment already exists on the microphone icon elsewhere in the UI, implying a download-progress signal is available somewhere in the speech provider/service layer, but its exact source wasn't located in this pass (src/vs/workbench/contrib/speechToText/common/speechService.ts's SpeechToTextStatus enum has no download-in-progress state, so the signal likely comes from the speech provider extension). Do not change the waveform's rendering/audio-level logic — only gate/augment its presentation on the download state.
- **Open decisions:**
  - What UI treatment should represent 'downloading' inside the onboarding card — inline text, a spinner replacing the waveform, or a dimmed waveform with a label?
  - Should the waveform still start (silently) during download, or should speaking be disabled/blocked with a message until the model is ready?

## Evidence

- **no download state in waveform:** src/vs/workbench/contrib/chat/browser/speechToText/dictationOnboarding.ts (MicrophoneWaveform, DictationOnboarding classes) has no reference to 'download', 'loading', or a model-readiness status — the waveform starts immediately regardless of model readiness.
- **existing indicator elsewhere:** The issue notes a 'download treatment on the microphone icon' already exists elsewhere in the UI, confirming the download-state signal exists but isn't wired into the onboarding waveform card.
