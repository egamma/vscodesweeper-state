# Issue #259225 — Add leading --purpose arg to processes to more easily identify them in task manager / htop etc

[https://github.com/microsoft/vscode/issues/259225](https://github.com/microsoft/vscode/issues/259225)

## Summary

Keep open for process-identification design discussion: existing diagnostics provide readable PID mappings, but do not establish the requested identification in external process monitors. The related high-CPU report does not own this broader capability.

## Change summary

Expose readable process roles, and potentially associated windows, near the start of VS Code subprocess command lines so external process monitors can identify them.

## Best solution

Provide concise, recognizable process identities in external monitoring tools without changing process behavior. First establish the supported Electron mechanisms and decide whether identities should include window or workspace context as well as process roles.

## Plan brief

- **Likely files:** `src/vs/platform/utilityProcess/electron-main/utilityProcess.ts`, `src/vs/platform/windows/electron-main/windowImpl.ts`, `src/vs/platform/diagnostics/electron-main/diagnosticsMainService.ts`
- **Validation:** On Linux, open two distinguishable VS Code windows and start terminal and extension-host activity; inspect their OS command lines with ps -ww -eo pid,ppid,args and htop, comparing identities against code --status. Confirm the agreed identities remain recognizable in a normally sized command column and existing startup and diagnostics still work. Check the agreed equivalent in Windows Task Manager and macOS process inspection before claiming cross-platform support.
- **Behavior:**

  > Users investigating VS Code resource usage should be able to identify relevant subprocess roles in external process monitors without deciphering long Electron command lines. The request prefers a readable leading purpose argument and gives window or project context as an example. Acceptance must demonstrate the agreed identity information in actual OS process output, not only inside VS Code's Process Explorer. Existing process execution and diagnostic behavior must remain unchanged.
- **Trace:**

  > UtilityProcess.doStart() in src/vs/platform/utilityProcess/electron-main/utilityProcess.ts constructs a type-plus-counter serviceName and delegates spawning to Electron utilityProcess.fork(); the OS visibility and argument ordering of this metadata were not established by executing the application. CodeWindow construction in src/vs/platform/windows/electron-main/windowImpl.ts supplies an opaque window-config argument through BrowserWindow webPreferences.additionalArguments. DiagnosticsMainService.getMainDiagnostics() already correlates window PIDs with titles and utility PIDs with readable names, but that mapping is consumed by VS Code diagnostics rather than exported as the requested leading argument. The design boundary crosses VS Code launch metadata and Electron-controlled process creation; determine supported mechanisms before promising an argument position or platform coverage. Preserve lifecycle, sandbox, debugging, and existing diagnostic semantics. https://github.com/microsoft/vscode/issues/213136 supplies motivation, not a canonical for this feature or evidence that all high CPU has one cause.
- **Open decisions:**
  - Should externally visible identities contain only stable process roles, or also window/workspace context such as the project's name?
  - Is a leading command-line identity required, or is another readable OS-visible identity acceptable on platforms where Electron does not support controlling argument placement?
