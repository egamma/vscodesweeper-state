# Issue #240240 — Terminal suggest: Support configuring fig specs

[https://github.com/microsoft/vscode/issues/240240](https://github.com/microsoft/vscode/issues/240240)

## Summary

User-supplied Fig specs remain unsupported in the checked-out main: the built-in provider uses a statically assembled spec list, and existing settings cannot extend it. Keep this accepted Backlog request open; specification precedence and workspace-level support need product decisions before implementation.

## Change summary

Allow users to supply custom Fig completion specs, with possible project-level specs and customization of bundled completions.

## Best solution

Provide a supported customization contract in the bundled terminal-suggest provider so users can supply specs for commands VS Code does not ship, with explicit collision semantics. Decide whether the initial contract includes workspace specs; preserve existing completion behavior when no customization is present.

## Plan brief

- **Likely files:** `extensions/terminal-suggest/src/terminalSuggestMain.ts`, `extensions/terminal-suggest/src/fig/figInterface.ts`, `extensions/terminal-suggest/package.json`, `extensions/terminal-suggest/README.md`, `extensions/terminal-suggest/src/test/terminalSuggestMain.test.ts`, `extensions/terminal-suggest/src/test/fig.test.ts`, `src/vs/workbench/contrib/terminalContrib/suggest/common/terminalSuggestConfiguration.ts`
- **Validation:** Exercise the real provider with a locally available test command and a user-supplied Fig spec containing a unique option; verify that option appears without changing bundled source. Add automated coverage for custom-spec discovery, the agreed collision behavior, invalid-spec diagnostics, and unchanged bundled completions without custom specs. If workspace specs are included, also verify workspace isolation and the agreed trust behavior.
- **Behavior:**

  > Users should be able to supply completion specifications for locally available commands that are not covered by VS Code's bundled specs, without modifying the installation or writing a separate completion-provider extension. Their custom options and subcommands should appear in terminal suggestions. Existing bundled completions should remain unchanged when no custom specs are supplied. Acceptance must cover the agreed behavior when custom and bundled specs name the same command, and workspace isolation if project-level specs are included.
- **Trace:**

  > In extensions/terminal-suggest/src/terminalSuggestMain.ts, availableSpecs is assembled from bundled imports, and activate passes it directly through getCompletionItemsFromSpecs to getFigSuggestions in extensions/terminal-suggest/src/fig/figInterface.ts. getFigSuggestions matches specs to available commands; its alias-resolution branch also consults the module-level availableSpecs, which matters when assessing customization coverage. Existing provider settings in src/vs/workbench/contrib/terminalContrib/suggest/common/terminalSuggestConfiguration.ts control provider enablement rather than spec discovery. The Fig test suites already accept supplied completionSpecs and assert option results, but they do not establish a production file-loading contract. Keep shell-function discovery, native alias injection, and bundled-spec lazy-loading work outside the initial customization boundary unless explicitly selected. Related but distinct work is tracked at https://github.com/microsoft/vscode/issues/210983, https://github.com/microsoft/vscode/issues/240241, and https://github.com/microsoft/vscode/issues/224505. The uncertainty starts at the user-facing customization contract, not at whether the current provider already loads user specs.
- **Open decisions:**
  - When a custom spec names a command already covered by a bundled spec, should it replace that spec or augment its suggestions?
  - Should the initial feature support only user-level specs, or also project-level specs; if project-level specs are included, when may their executable generators run relative to workspace trust?
