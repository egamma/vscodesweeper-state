# Issue #279704 — Figure out a way to advertise MCP servers contributed by extensions without such a high cost of tokens

[https://github.com/microsoft/vscode/issues/279704](https://github.com/microsoft/vscode/issues/279704)

## Summary

Keep open: current tool search reduces schema-token overhead on supported paths, but does not establish a complete extension-contributed MCP discovery and activation story. This team-authored request has neither an explicitly linked fixing commit nor a verified older duplicate covering the same symptom.

## Change summary

Make extension-contributed MCP servers discoverable to users and models without automatically including every tool definition in user requests.

## Best solution

Define the remaining extension-MCP discovery and activation contract around existing deferred tool search, preserving discoverability without eagerly advertising full tool schemas. Coordinate with the static-metadata API work, while distinguishing server startup costs from model-context costs.

- **Likely files:** `src/vs/workbench/contrib/mcp/common/mcpService.ts`, `src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts`, `extensions/copilot/src/extension/tools/common/virtualTools/virtualToolGrouper.ts`, `extensions/copilot/src/extension/tools/node/toolSearchTool.ts`, `extensions/copilot/src/platform/endpoint/node/responsesApi.ts`
- **Validation:** Use a fixture extension contributing an MCP server with a large tool inventory. Compare initial outbound tool schemas and token counts for unrelated and relevant prompts, verify relevant tools remain discoverable and callable, and record server startup behavior. Cover tool-search-supported and unsupported models; establish the token budget and expected fallback behavior during planning.
- **Behavior:**

  > An installed extension should not force its entire MCP tool inventory into unrelated requests merely to make its capabilities discoverable. Users and models must still be able to find and invoke relevant tools. Acceptance should measure initial schema-token overhead with a large contributed server, verify successful discovery and invocation, and exercise models both with and without native tool-search support.
- **Trace:**

  > McpService.autostart in src/vs/workbench/contrib/mcp/common/mcpService.ts starts enabled new/outdated servers for discovery unless chat.mcp.autostart is never. McpLanguageModelToolContribution registers their model-visible tools independently of request serialization. The Responses API serializer in extensions/copilot/src/platform/endpoint/node/responsesApi.ts already excludes deferred schemas when its tool-search conditions hold, so registration must not be equated with unconditional transmission. ToolSearchTool and VirtualToolGrouper provide existing discovery mechanisms to assess before adding another. The remaining uncertainty is the intended cross-model advertisement and activation experience, not whether any token-saving mechanism exists. Coordinate with https://github.com/microsoft/vscode/issues/272000 without treating static metadata as a solution to schema-token overhead; preserve explicit tool selection and existing enablement behavior.
- **Open decisions:**
  - Should extension-contributed servers remain automatically discoverable and startable by default, or require explicit user or model activation before their tools become available?
  - For models without tool-search support, what advertisement and fallback behavior should preserve discoverability without including the full contributed tool inventory?
