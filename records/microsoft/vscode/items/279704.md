# Issue #279704 — Figure out a way to advertise MCP servers contributed by extensions without such a high cost of tokens

[https://github.com/microsoft/vscode/issues/279704](https://github.com/microsoft/vscode/issues/279704)

## Summary

Keep open to settle the extension-contributed MCP discovery and token-budget policy. Current tool grouping and model-dependent tool search address part of the request, but do not establish complete coverage or an issue-referencing fix for this team-authored item.

## Change summary

Make extension-contributed MCP servers discoverable to users and models without automatically adding their entire tool catalog to every request.

## Best solution

Provide discoverable, on-demand MCP capabilities with a small initial tool-definition footprint, building on existing tool search and grouping. Decide the remaining startup and unsupported-model behavior separately from the static-metadata API work.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/common/mcpService.ts`, `src/vs/workbench/contrib/mcp/common/discovery/extensionMcpDiscovery.ts`, `extensions/copilot/src/extension/tools/common/virtualTools/virtualToolGrouper.ts`, `extensions/copilot/src/platform/endpoint/node/responsesApi.ts`
- **Validation:** Capture outgoing model requests for an extension-contributed MCP server with a large catalog: an unrelated first prompt must avoid eagerly transmitting the entire catalog, while a relevant prompt must discover and invoke a previously deferred tool. Repeat with and without native tool-search support, checking server startup, user discoverability, and existing enablement controls against the agreed policy.
- **Behavior:**

  > Extension-contributed MCP servers should remain discoverable without imposing their full tool-definition token cost on unrelated requests. Relevant requests must still be able to discover and invoke their tools. Acceptance should inspect the actual outgoing definitions and demonstrate successful invocation of a deferred tool, including the agreed fallback for models without native tool search.
- **Trace:**

  > ExtensionMcpDiscovery registers lazy collections, while McpService.autostart activates collections and starts eligible enabled servers according to configuration and cache state. VirtualToolGrouper.addGroups already groups extension and MCP catalogs, and responsesApi.ts omits deferred definitions when native tool search is active for an eligible non-subagent request. These are distinct layers: reducing transmitted definitions does not itself defer server startup or define how users discover a server. Preserve existing enablement and explicit tool-selection behavior. https://github.com/microsoft/vscode/issues/272000 addresses static metadata for startup avoidance, while https://github.com/microsoft/vscode/issues/319330 records discovery limitations under virtualization; neither is a verified duplicate of this request. The remaining uncertainty is the intended startup policy and model-independent advertisement contract.
- **Open decisions:**
  - Should enabled extension-contributed servers still start to enumerate tools before a relevant request, or remain stopped until the model or user explicitly selects their capabilities?
  - For models without native tool search, should initial requests expose compact server/category activation tools, or retain eager tool definitions under an explicit size or token budget?
