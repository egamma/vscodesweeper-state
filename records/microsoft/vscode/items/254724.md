# Issue #254724 — Shell integration fails with command sequences and hangs with sleep commands

[https://github.com/microsoft/vscode/issues/254724](https://github.com/microsoft/vscode/issues/254724)

## Summary

Keep open: moving the terminal tool to core bypassed the problematic extension API, but does not establish that this API defect was fixed. A later report corroborates missing output and completion for subshell commands, and no verified older canonical covers this report's full scope.

## Change summary

Subshell command sequences executed through shell integration lose captured output or leave extension consumers waiting indefinitely for completion.

## Best solution

Make the public TerminalShellIntegration API reliably associate subshell commands with their returned execution objects, deliver their output, and signal completion. Diagnose the original command shapes on current main before choosing a fix; preserve the distinction between command lifecycle events and raw terminal escape sequences.

- **Validation:** In a Linux/bash extension host on current main, execute `(echo a ; echo b)` and `(echo a ; sleep 1)` through terminal.shellIntegration.executeCommand(), call read() immediately, and record lifecycle events by execution identity. Verify output contains both echo results for the first command and a for the second, each iterable terminates within a bounded timeout after process exit, and completion references the returned execution. Repeat with the reproducer's PROMPT_COMMAND variants and a simple echo control; turn the captured failing event sequence into a regression test.
- **Behavior:**

  > An extension executing `(echo a ; echo b)` receives both output lines, and executing `(echo a ; sleep 1)` receives a and completes after the sleep rather than waiting indefinitely. The returned execution's read stream terminates and its completion event refers to that execution. Ordinary commands remain unchanged. Acceptance concerns output and lifecycle completion, not the presence of a raw OSC completion marker in captured output.
- **Trace:**

  > The original harness at https://github.com/KJ7LNW/vsce-test-terminal-integration filters start and end events by the execution object returned from executeCommand. InternalTerminalShellIntegration.startShellExecution in src/vs/workbench/api/common/extHostTerminalShellIntegration.ts associates pending executions using command-line equality or trimmed-line matching and creates a separate object when matching fails. MainThreadTerminalShellIntegration forwards command-detection events and accumulated terminal data, while TerminalInstance._onProcessData separates C and D sequences. The bash integration script supplies those sequences through preexec and prompt hooks. The original commands' actual marker sequence and command-line values have not been captured on current main, so the unresolved diagnosis is whether execution matching, shell emission, or delivery ordering causes the failure. The terminal-tool migration in https://github.com/microsoft/vscode/pull/255804 bypasses this API and is not sufficient fix evidence. Preserve existing public API semantics and do not require OSC D to appear in read() output or broaden the work to unrelated multiline cases.

## Evidence

- **Original reproduction:** https://github.com/microsoft/vscode/issues/254724 reports missing output for `(echo a ; echo b)` and an integration hang for `(echo a ; sleep 1)`, with a dedicated extension reproducer. Its src/terminal/terminal-handler.ts consumes execution.read() and filters lifecycle events by execution-object identity.
- **Maintainer diagnosis and workaround boundary:** https://github.com/microsoft/vscode/issues/255396#issuecomment-3108308534 identifies this report as an 'API sub-execution problem' addressed for the terminal tool by moving it to core. The merged https://github.com/microsoft/vscode/pull/255804 explicitly replaces extension APIs with richer internal APIs; that migration does not prove the original extension-facing behavior is repaired.
- **Later corroborating reproduction:** https://github.com/microsoft/vscode/issues/324392 is open and reports repeated Linux/bash subshell executions whose processes exit while execution.read() delivers zero data and onDidEndTerminalShellExecution never fires. This corroborates the API-level symptom, although the exact original commands were not executed during this read-only review.
- **Current execution matching:** src/vs/workbench/api/common/extHostTerminalShellIntegration.ts, InternalTerminalShellIntegration.startShellExecution, matches pending executions by command-line equality or isSubExecution's trimmed-line comparison. An unmatched high-confidence start creates a different execution object; emitData and endShellExecution operate on the current object. This is a relevant failure boundary, but the shell's actual reported command line for the original commands still needs capture.
- **Current data-delivery contract:** src/vs/workbench/contrib/terminal/browser/terminalInstance.ts:1670-1710 separates command-start and command-finished sequences before writing data. src/vs/workbench/api/browser/mainThreadTerminalShellIntegration.ts flushes accumulated data before forwarding completion and explicitly excludes the D sequence being parsed. Consequently, the reproducer's expectation that raw OSC 633;D must appear in the read stream is not itself proof of a defect.
