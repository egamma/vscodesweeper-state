# Issue #217869 — Override less specific code action with more specific code action

[https://github.com/microsoft/vscode/issues/217869](https://github.com/microsoft/vscode/issues/217869)

## Summary

This remains an accepted code-actions-on-save bug: a maintainer confirmed the behavior, and current main still resolves parent and child kinds without a defined most-specific-setting precedence. As a team-authored Backlog bug with no verified fix or canonical duplicate, it must remain open.

## Change summary

Make a specific code-action-on-save setting such as `source.fixAll.eslint: never` override a broader `source.fixAll: always` setting.

## Best solution

Define deterministic hierarchical precedence for `editor.codeActionsOnSave`, preferably making the most-specific matching kind control whether an action runs, and cover mixed parent/child values with save-participant tests.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/codeEditor/browser/saveParticipants.ts`, `src/vs/workbench/contrib/codeEditor/test/browser/saveParticipant.test.ts`, `src/vs/editor/contrib/codeAction/common/types.ts`

- **Behavior:**

  > Hierarchical `editor.codeActionsOnSave` entries need predictable precedence when broad and specific kinds conflict. With `source.fixAll: always` and a child such as `source.fixAll.eslint: never`, saving must not run the disabled child while other enabled descendants remain eligible. Existing behavior for non-conflicting settings and legacy array-form ordering must remain unchanged.
- **Trace:**

  > The report was confirmed as a known issue by a maintainer at https://github.com/microsoft/vscode/issues/217869#issuecomment-2189812632. In src/vs/workbench/contrib/codeEditor/browser/saveParticipants.ts, `participate` separates enabled settings from `never` exclusions, `createCodeActionsOnSave` collapses enabled subsets into their broader parent, and `getActionsToRun` forwards that parent plus exclusions to the code-action filter. src/vs/editor/contrib/codeAction/common/types.ts then applies exclusions per returned action kind through `excludesAction`; there is no configuration-level most-specific-wins resolution. The uncertainty starts at the public setting contract: whether a specific child always overrides a broader parent or whether broad enablement intentionally wins. Keep array-form ordering, language-specific configuration overrides, and unrelated code-action filtering out of scope.
- **Open decisions:**
  - When a broad code-action kind and a more-specific child have conflicting values, should the most-specific matching setting always determine whether the child action runs?
