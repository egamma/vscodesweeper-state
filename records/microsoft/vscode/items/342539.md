# Issue #342539 — powershellflags in settings.json not affecting powershell host in Copilot harness in vs code

[https://github.com/microsoft/vscode/issues/342539](https://github.com/microsoft/vscode/issues/342539)

## Summary

The central request already has a dedicated opt-in setting: chat.agentHost.shellTool.initScript.enabled loads current-user PowerShell profiles before Copilot SDK shell commands in local editor windows. Seeing -NoProfile in the process command line does not establish that this separate initialization mechanism is absent.

## Change summary

Allow Copilot harness PowerShell commands to deterministically load the user's profile and its toolchain/PATH configuration.

## Best solution

Use the existing shell initialization setting for local Copilot harness sessions rather than relying on PowershellFlags or agent instructions. Preserve the distinction between shell launch arguments and explicitly sourcing profiles before commands.

- **Proposed comment:**

  > Thanks for the report. For local Copilot harness sessions, enable `"chat.agentHost.shellTool.initScript.enabled": true` and leave `chat.agentHost.customTerminalTool.enabled` disabled. This sources `$PROFILE.CurrentUserAllHosts` and `$PROFILE.CurrentUserCurrentHost` before each SDK shell command, independently of agent instructions; the process can still show `-NoProfile` because profiles are sourced separately.
  > 
  > The setting currently applies to local editor windows. Sandbox profile-access limitations are tracked in https://github.com/microsoft/vscode/issues/334582, and remote-window support in https://github.com/microsoft/vscode/issues/342691.
