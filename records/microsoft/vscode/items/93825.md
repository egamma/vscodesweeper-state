# Issue #93825 — Allow context key expression that compares object properties

[https://github.com/microsoft/vscode/issues/93825](https://github.com/microsoft/vscode/issues/93825)

## Summary

Keep open: current context expressions support object-property membership, but not general property-value comparisons. Nested configuration cache invalidation now addresses the original stale-state mechanism, while the broader capability discussed in the thread remains missing.

## Change summary

Allow context expressions to compare values inside object-valued context keys and react when those values change.

## Best solution

Define property-value comparison semantics in the context-key expression system, preserving existing membership behavior and tracking changes through the owning object key. Treat the original Timeline example as motivation rather than requiring a change to its current storage-based filters.

## Plan brief

- **Likely files:** `src/vs/platform/contextkey/common/contextkey.ts`, `src/vs/platform/contextkey/common/scanner.ts`, `src/vs/platform/contextkey/browser/contextKeyService.ts`, `src/vs/platform/contextkey/test/common/parser.test.ts`, `src/vs/platform/contextkey/test/common/contextkey.test.ts`, `src/vs/platform/contextkey/test/browser/contextkey.test.ts`
- **Validation:** After agreeing the contract, add parser and evaluation tests for property-value comparisons, including absent properties and false values, plus change-event tests for replacing the owning object and updating nested configuration. Run the targeted contextkey parser, expression, and browser suites through scripts/test.sh; existing in/not-in behavior must remain unchanged.
- **Behavior:**

  > A context expression should be able to test an object's property value, rather than only whether the property exists. Conditions must reevaluate when the relevant value changes, including removal and re-addition. Acceptance checks should distinguish absent, false, and true properties and preserve existing membership semantics. The exact property-addressing and comparison contract requires a maintainer decision.
- **Trace:**

  > Context.getValue in src/vs/platform/contextkey/browser/contextKeyService.ts performs exact-key lookup for ordinary contexts, and ContextKeyEqualsExpr in src/vs/platform/contextkey/common/contextkey.ts compares the result against a literal. ContextKeyInExpr supports object membership and reports dependencies on both context keys, but ignores property values. ConfigAwareContextValuesContainer already invalidates cached nested configuration keys when a parent changes, so the original invalidation explanation is not the remaining general capability gap. Timeline currently uses profile storage and a regex-based filter, which should not be migrated as an incidental part of this request. The discussion in https://github.com/microsoft/vscode/issues/93825 favors avoiding traversal of every changed object. https://github.com/microsoft/vscode/issues/210719 supplies related configuration-object use cases but is not a canonical for this older request.
- **Open decisions:**
  - Should property-value comparisons support ordinary object-valued context keys as well as configuration objects?
  - What public expression syntax addresses properties, including literal property names containing dots, without changing existing dotted context-key meanings?
  - Which comparisons are supported, and how should missing properties differ from properties whose values are false or null?
