Existing Send Later and Automations features cover parts of this request, but recurring follow-ups retaining the original conversation remain a distinct gap. Keep this open; neither verified related issue covers the full request.

  > Thanks for the request. The Agents window already has a gated Send Later feature (`sessions.sendLater.enabled`) for one-time follow-ups in an existing local Agent Host chat. ## Evidence

- **Existing one-time capability:** src/vs/sessions/contrib/chat/browser/sharedChatInputComposer.contribution.ts registers sessions.sendLater. The sessions.sendLater.enabled setting is default-off in src/vs/sessions/contrib/sessions/browser/sessions.contribution.ts and describes scheduling new-session or existing-chat requests through supported local Agent Hosts.
- **Remaining conversation-continuity gap:** src/vs/sessions/contrib/automations/browser/automationTools.ts explicitly states that one-time creation defaults to currentChat, while other schedules create new sessions; currentSession copies the environment, not the conversation, and new-session requests do not copy history. Thus existing recurring Automations do not satisfy the requested same-session context.
- **Existing authorization and lifecycle contract:** src/vs/sessions/AUTOMATIONS.md restricts existing-conversation schedules to one-time scheduled chats. These enqueue into the exact original chat and use its current configuration and runtime authorization; pending schedules can be disabled or cancelled without deleting that conversation.
- **Related scheduling defect, not full canonical:** https://github.com/microsoft/vscode/issues/346539 was verified open. It reports /every producing no periodic output and listing schedules crashing in the Agents window, rather than owning the complete one-time, recurring, context-preserving scheduling request.
