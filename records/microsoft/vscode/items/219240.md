## Plan brief

- **Likely files:** `src/vs/workbench/contrib/notebook/browser/controller/coreActions.ts`, `src/vs/workbench/contrib/notebook/browser/contrib/format/formatting.ts`, `src/vs/workbench/contrib/notebook/browser/notebookEditorWidget.ts`

- **Behavior:**

  > Notebook users should be able to discover applicable formatting and code actions through coherent context menus. Existing Format Notebook command-palette behavior and formatting execution should remain available. Acceptance requires an agreed list of actions and menu locations, checked with and without applicable providers and in editable versus read-only notebooks.
- **Trace:**

  > The local notebookEditorWidget.ts routes cell-container menus through MenuId.NotebookCellTitle. Current coreActions.ts, inspected through the GitHub API because it is absent from the shard, also exposes that menu as an editor-context submenu under NOTEBOOK_EDITOR_FOCUSED. Current contrib/format/formatting.ts registers notebook.format in the command palette and conditionally in EditorContext, then executes notebook-format code actions before cell-formatting fallback. https://github.com/microsoft/vscode/pull/229241 supplies telemetry rather than menu completion, and https://github.com/microsoft/vscode/pull/229245 was not merged. The uncertainty is the intended remaining menu presentation, not the existence of formatting functionality; keep formatting execution and provider contracts outside this polish scope. https://github.com/microsoft/vscode/issues/212381 provides related formatting design context but does not absorb the whole request.
- **Open decisions:**
  - Which notebook-level and cell-level code actions should be exposed, and should they appear directly in the cell-editor menu, the Notebook Cell submenu, the cell-container menu, or a consistent combination?
  - Should Format Notebook be discoverable when a notebook-format code-action provider exists but the focused cell has no document-formatting provider?
