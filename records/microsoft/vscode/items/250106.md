# Issue #250106 — Add `zenMode.activityBarLocation` instead of `zenMode.hideActivityBar`

[https://github.com/microsoft/vscode/issues/250106](https://github.com/microsoft/vscode/issues/250106)

## Summary

This team-authored Backlog request remains unimplemented on current main and should stay open. The existing global Activity Bar location and Zen Mode visibility boolean cannot select a distinct Activity Bar location while Zen Mode is active.

## Change summary

Replace or supplement `zenMode.hideActivityBar` with a setting that controls the Activity Bar location specifically in Zen Mode, potentially including an inherited location.

## Best solution

Define the desired Zen Mode location semantics and compatibility behavior, then make Zen Mode apply and restore that location independently of `workbench.activityBar.location`.

- **Fit:** aligned
- **Reason:** Allowing Zen Mode to use a deliberate Activity Bar layout while faithfully restoring the normal workspace layout advances the workbench layout-flexibility and settings-fidelity theme.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/workbench.zenMode.contribution.ts`, `src/vs/workbench/services/layout/browser/layoutService.ts`, `src/vs/workbench/browser/layout.ts`
- **Validation:** Using an isolated profile, set the normal Activity Bar location to each supported value, enter Zen Mode with each proposed Zen Mode location value, verify the Activity Bar moves or hides accordingly without duplication, then exit Zen Mode and verify the original location and visibility are restored.
- **Behavior:**

  > Users can choose an Activity Bar location specifically for Zen Mode rather than only deciding whether Zen Mode hides it. Entering Zen Mode applies that selection without producing duplicate Activity Bars, and leaving Zen Mode restores the normal workbench location and visibility. An inheritance option, if selected, preserves the location configured by `workbench.activityBar.location`.
- **Trace:**

  > `src/vs/workbench/browser/workbench.zenMode.contribution.ts` exposes the existing boolean setting, while `ZenModeSettings` in `src/vs/workbench/services/layout/browser/layoutService.ts` names the key consumed by the layout implementation. `WorkbenchLayout.toggleZenMode` in `src/vs/workbench/browser/layout.ts` currently hides the Activity Bar from that boolean and listens to both it and the global location setting; `ZenModeConfiguration` contains no location value. The global enum is registered in `src/vs/workbench/browser/workbench.contribution.ts` with `default`, `top`, `bottom`, and `hidden`. Preserve normal non-Zen layout behavior and the fix for the duplicate-bar scenario discussed in https://github.com/microsoft/vscode/issues/246560; the unresolved boundary is the new public setting contract and migration behavior.
- **Open decisions:**
  - Should the Zen Mode setting support `inherit`, `default`, `top`, `bottom`, and `hidden`, and does `default` mean the standard side placement or inheritance from `workbench.activityBar.location`?
  - Should `zenMode.hideActivityBar` remain supported as a compatibility setting, be deprecated in favor of the location setting, or be retained as an overriding boolean?

## Evidence

- **current configuration:** `src/vs/workbench/browser/workbench.zenMode.contribution.ts` still registers only the boolean `zenMode.hideActivityBar`; no `zenMode.activityBarLocation` setting exists on current main.
- **existing capability gap:** `src/vs/workbench/browser/workbench.contribution.ts` registers `workbench.activityBar.location` with `default`, `top`, `bottom`, and `hidden`, but that setting is global and cannot specify a separate Zen Mode location.
- **current code path:** `src/vs/workbench/browser/layout.ts` reads `ZenModeSettings.HIDE_ACTIVITYBAR` while entering Zen Mode and reacts only to that boolean plus the global `LayoutSettings.ACTIVITY_BAR_LOCATION`; the `ZenModeConfiguration` type has no location field.
- **related issue:** https://github.com/microsoft/vscode/issues/246560 is a closed bug about duplicate Activity Bars, not an open canonical for this configuration request; its maintainer discussion explicitly spun this feature request into https://github.com/microsoft/vscode/issues/250106.
