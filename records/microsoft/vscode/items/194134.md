# Issue #194134 — Highlight matched words in similar commands

[https://github.com/microsoft/vscode/issues/194134](https://github.com/microsoft/vscode/issues/194134)

## Summary

The highlighting gap remains in current source: similar-command results do not receive the match highlights assigned to ordinary matches. Keep this accepted, team-authored request open; no verified canonical owns the same observable improvement.

## Change summary

Highlight matching search words in the Command Palette’s similar-command entries.

## Best solution

Show meaningful query-word highlights in similar-command results using the existing Quick Pick highlighting surface, without changing result inclusion or ranking. Agree on the visible matching semantics for tokenized and semantic results before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/quickinput/browser/commandsQuickAccess.ts`, `src/vs/workbench/contrib/quickaccess/browser/commandsQuickAccess.ts`, `src/vs/base/common/tfIdf.ts`
- **Validation:** Exercise the Command Palette with 'how do I change my language' and 'permalink copy', checking visible matching-word highlights in similar results. Cover ordinary matches, localized aliases, description-only matches and semantic suggestions without literal overlap; result membership, ranking and command execution must remain unchanged. Add provider-level assertions for highlight ranges under the agreed matching semantics.
- **Behavior:**

  > Similar-command entries should visibly identify matching query words even when the entire query does not match their labels. Ordinary command matches should retain their existing highlights. Results without visible textual overlap must not receive misleading highlights. Acceptance should cover natural-language queries, reordered words, localized aliases and semantic results while preserving command ranking and execution.
- **Trace:**

  > AbstractCommandsQuickAccessProvider._getPicks in src/vs/platform/quickinput/browser/commandsQuickAccess.ts assigns highlights only in the ordinary WORD_FILTER branch; TF-IDF fallback results receive a score but no highlights. PickerQuickAccessProvider.provide in src/vs/platform/quickinput/browser/pickerQuickAccess.ts disables automatic label, description and detail matching, so the missing highlights are not supplied downstream. TfIdfCalculator.splitTerms in src/vs/base/common/tfIdf.ts uses case-insensitive words of at least three characters and camel-case parts, while getTfIdfChunk indexes labels, aliases and descriptions. CommandsQuickAccessProvider.getRelatedInformationPicks in src/vs/workbench/contrib/quickaccess/browser/commandsQuickAccess.ts returns semantic suggestions that need not share literal query words. The uncertainty is the observable highlighting contract, not the existence of the gap; preserve scoring, thresholds, result ordering, AI enablement and accessible labels. The original two-provider test context is https://github.com/microsoft/vscode/issues/194021.
- **Open decisions:**
  - Should similar-result highlights represent literal query-word occurrences using existing word-match conventions, or precisely the normalized TF-IDF terms, including its minimum word length and camel-case matching?
  - Should semantic suggestions receive the same literal-overlap highlighting when words happen to match, or should highlighting be limited to results selected by textual similarity?
