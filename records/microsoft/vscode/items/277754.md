# Issue #277754 — Default worktree location has no write permission in dev container

[https://github.com/microsoft/vscode/issues/277754](https://github.com/microsoft/vscode/issues/277754)

## Summary

The permission failure remains possible on current main because worktree isolation still derives a sibling `<repo>.worktrees` directory, while a typical Dev Container mounts only the repository and cannot write its `/workspaces` parent. The later host-prepared Dev Container flow covers a distinct launch path, so this issue should stay open for a persistence and mount-contract decision.

## Change summary

Creating an isolated CLI agent session inside a Dev Container fails because the default sibling worktree directory is outside the writable workspace mount.

## Best solution

Define a durable worktree ownership contract for sessions started from an existing Dev Container: the isolated checkout must be created in writable persistent storage and made available inside the container without exposing unrelated host folders or silently placing user changes in ephemeral container storage.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/common/worktreePaths.ts`, `src/vs/platform/agentHost/node/shared/worktreeIsolation.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/devContainerAgentHostSessionsProvider.ts`, `src/vs/sessions/contrib/providers/remoteAgentHost/browser/remoteAgentHostSessionsProvider.ts`
- **Validation:** Add targeted worktree-isolation and Dev Container provider tests demonstrating that an isolation request originating from a workspace whose parent is not writable receives a writable, persistent worktree visible to the container; run those tests with scripts/test.sh using their suite/test grep.
- **Behavior:**

  > Starting an isolated agent session from an existing Dev Container must produce a usable Git worktree even when the parent of the mounted workspace is not writable. The worktree must remain durable across container recreation, must not require exposing unrelated host folders, and must preserve the requested isolation rather than silently losing changes. Existing non-container worktree placement and lifecycle behavior must remain unchanged.
- **Trace:**

  > Current main derives every managed worktree root through `getWorktreesRoot` in src/vs/platform/agentHost/common/worktreePaths.ts, which places it beside the repository. `WorktreeIsolation` in src/vs/platform/agentHost/node/shared/worktreeIsolation.ts creates that directory, so `/workspaces/repo` requires write access to `/workspaces`. The issue discussion establishes that the usual Dev Container mount exposes only the repository and that making the sibling container-local creates a data-durability hazard. Commit 737ece27f9e9bc341aedd3db7e9a216cd661c158 handles the newer flow where VS Code prepares a host worktree before launching a Dev Container, but it leaves the already-running-container path and generic root calculation intact. Preserve ordinary local worktree behavior and avoid broadening the container mount to unrelated sibling directories.
- **Open decisions:**
  - For an isolation request originating inside an existing Dev Container, should the worktree be persistent host-side storage mounted into the container, or explicitly container-local storage with different lifecycle semantics?
  - If a persistent isolated worktree cannot be prepared or mounted, should the session fail rather than continue in the original non-isolated workspace?
