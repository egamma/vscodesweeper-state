# Issue #239577 — Profile "Default" not showing text "All profiles"

[https://github.com/microsoft/vscode/issues/239577](https://github.com/microsoft/vscode/issues/239577)

## Summary

The issue remains credible on current main: the Profiles editor collapses local and remote installations by extension identifier even when their application-scope metadata differs, making the displayed "All Profiles" state and the extension selected by the toggle order-dependent. The accepted `bug` classification and Backlog milestone also rule out a judgment close.

## Change summary

The Profiles editor can omit or invert the "All Profiles" state for extensions in the Default profile, causing the corresponding action to remove the scope when the UI suggests it will add it.

## Best solution

Make the Profiles editor represent and toggle application scope consistently when the same extension is installed on multiple extension-management servers, with an explicit product decision for differing local and remote scope states.

- **Validation:** Add a Profiles model/service test with the same extension identifier installed locally and remotely under differing `isApplicationScoped` values; verify that the displayed state is deterministic and that invoking the action produces the state defined by the maintainer, including after the metadata-change refresh.
- **Behavior:**

  > The Profiles editor must show a deterministic and truthful "All Profiles" state for every extension. Invoking "Apply Extension to all Profiles" must move the represented installation or installations to that state rather than removing an already-applied scope because the UI was stale or reflected another extension host. Reopening or refreshing the profile must preserve the same indicator. Acceptance must cover the same extension installed locally and in a remote environment with both matching and differing scope metadata.
- **Trace:**

  > IWorkbenchExtensionManagementService.getInstalled in src/vs/workbench/services/extensionManagement/common/extensionManagementService.ts combines results from all extension-management servers. ExtensionsResource.getLocalExtensions in src/vs/workbench/services/userDataProfile/browser/extensionsResource.ts then collapses those results into a map keyed only by extension ID, so one host's `applicationScoped` value overwrites another's. UserDataProfileElement.getChildrenForResourceType in src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditorModel.ts renders that collapsed value, while the action independently selects the first matching result from another combined query. This source path explains the reporter's remote-WSL configuration and the observed inverse toggle. Preserve profile import/export and ordinary single-host behavior; the uncertainty begins only when installations with the same identifier disagree across extension hosts. Related context: https://github.com/microsoft/vscode/issues/207709.
- **Open decisions:**
  - When local and remote installations of the same extension have different application-scope states, should the single Profiles entry show a mixed state, separate host-specific entries, or an aggregate state?
  - In that mixed state, should "Apply Extension to all Profiles" update every installation represented by the entry or only the installation host associated with the selected profile context?

## Evidence
