# Issue #296823 — Copilot chat window not accessible any more because of `Unknown event type: "session.mode_changed"`

[https://github.com/microsoft/vscode/issues/296823](https://github.com/microsoft/vscode/issues/296823)

## Summary

The same session.mode_changed failure was independently confirmed, but subsequent recovery changes do not establish that affected sessions can now open with their history and remain usable. Keep this open: the reported error and session-opening workflow suffice to retest, although session loading has changed substantially since 1.109.5.

## Change summary

Opening a background-agent session containing session.mode_changed fails and leaves the Copilot Chat view unusable.

## Best solution

Affected sessions should open with their conversation history, and a session-loading failure must not disable the rest of Chat. Verify both outcomes against an affected transcript before treating the related recovery fixes as completing this report.

## Evidence

- **Reported trigger and workaround:** https://github.com/microsoft/vscode/issues/296823 reports opening a specific background-agent session on Windows with VS Code 1.109.5 and receiving Unknown event type: "session.mode_changed". The reporter's https://github.com/microsoft/vscode/issues/296823#issuecomment-3940841077 confirms that duplicating the workspace restores Chat only until the broken session is selected again.
- **Independent confirmation and canonical search:** https://github.com/microsoft/vscode/issues/296082 describes the identical event error and disappearing session list after opening a terminal CLI session. A maintainer confirms that symptom in https://github.com/microsoft/vscode/issues/291823#issuecomment-3922825554. Both related issues are now closed, so neither is a valid duplicate target; searches for session.mode_changed and Unknown event type found no verified open canonical covering this report.
- **Chat recovery fix:** https://github.com/microsoft/vscode/commit/b3df34cabdc94c7436fde5ce920e62cefb045bf1 changes src/vs/workbench/contrib/chat/browser/widgetHosts/viewPane/chatViewPane.ts: the session-loading catch disposes the pending clear operation, reports the error, and calls showModel(undefined) to restore a fresh Chat view. This addresses widget recovery, not deserialization of the affected session.
- **Partial-history recovery is not full session compatibility:** https://github.com/microsoft/vscode/commit/6b8d0f84c171b177ad5179821821e9011ef477ac adds an Unknown event type catch in CopilotCLIChatSessionContentProvider.getSessionHistory and reconstructs history directly from events.jsonl. Its participant guard explicitly warns and returns without handling a new request for an incompatible session. Current equivalents remain in extensions/copilot/src/extension/chatSessions/vscode-node/copilotCLIChatSessions.ts and copilotCLIChatSessionsContribution.ts.
- **Current loading path limits the completion claim:** Current extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotcliSessionService.ts, getChatHistoryImpl, catches SDK getSession failures and returns empty history/events. This behavior was introduced by https://github.com/microsoft/vscode/commit/382e40aeea80678fe6bdb3ab9019f81c80f5d063. Suppressing the loading exception does not prove that the reporter's transcript is readable or resumable, and can bypass the provider's exception-triggered partial-history fallback.
