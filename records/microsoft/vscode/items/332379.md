# Issue #332379 — Copilot Chat reports an invalid GitHub token while VS Code still shows the account as signed in

[https://github.com/microsoft/vscode/issues/332379](https://github.com/microsoft/vscode/issues/332379)

## Summary

A VS Code team member (TylerLeonhardt) explicitly reframed this as the central tracker for a Copilot GitHub-auth recovery UX, stating it stays open regardless of whether the original credential bug still reproduces — so this is not a case for needs-info or closing, it's an accepted UX gap awaiting design/implementation.

## Change summary

When Copilot reports an invalid GitHub token, the Accounts UI still shows the account as signed in with no discoverable way to re-authenticate specifically for Copilot, forcing trial-and-error sign-out/reload cycles.

## Best solution

Design and build a discoverable 'Sign In Again' recovery action (surfaced in the notification and/or Accounts UI) that re-authenticates the Copilot credential without a global sign-out, and clearly signals when Copilot auth is restored — including when BYOK models are configured.

## Plan brief

- **Likely files:** `extensions/github-authentication/src`, `extensions/copilot`
- **Validation:** A manual/automated check that after simulating an invalid Copilot GitHub credential, a 'Sign In Again' action appears, completes without global sign-out, and Copilot's chat surface reflects restored auth without requiring a window reload.
- **Behavior:**

  > When Copilot's GitHub credential becomes invalid, the user sees a discoverable 'Sign In Again' (or equivalent) action that re-authenticates just the Copilot credential — no global sign-out or repeated reloads required — and the UI (notification and/or Accounts menu) clearly indicates when Copilot authentication has been restored. This recovery path must also work when BYOK models are configured.
- **Trace:**

  > The gap is that the VS Code Accounts UI reflects whether a GitHub account session exists, not whether the specific credential/scope Copilot Chat is using is still valid — so an 'invalid token' notification from Copilot has no corresponding actionable state in Accounts. The maintainer's comment (https://github.com/microsoft/vscode/issues/332379#issuecomment, 2026-09-18) lays out the target behavior; the closed https://github.com/microsoft/vscode/issues/333593 addressed only the initial-invalidation bug, not this recovery-flow gap. Where uncertainty starts: which surface (notification action vs. Accounts menu item vs. both) hosts the re-auth entry point, and how the 'restored' state is signaled back to the user.
- **Open decisions:**
  - Should the 'Sign In Again' action live in the Copilot notification, the Accounts menu, or both?
  - How should VS Code represent an account that is signed in generally but has an invalid credential specifically for Copilot?
  - What confirmation (toast, notification update, status bar) indicates that Copilot authentication has been restored?
