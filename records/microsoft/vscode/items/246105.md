# Issue #246105 — Inline git blame is rendered before code when deleting a line

[https://github.com/microsoft/vscode/issues/246105](https://github.com/microsoft/vscode/issues/246105)

## Summary

Keep open for investigation of decoration positioning after line deletion and undo. Multiple reporters confirmed the behavior, and neither a concrete fixing commit nor an older canonical with the same symptom was established.

## Change summary

Built-in inline Git blame can move before surviving code after deleting a line and remain misplaced through undo.

## Best solution

Ensure built-in blame annotations remain after the appropriate line's code through deletion, undo, and redo. Diagnose the interaction between Git blame refreshes and editor decoration range tracking before deciding whether the correction belongs in the Git contribution or shared editor infrastructure.

## Plan brief

- **Likely files:** `extensions/git/src/blame.ts`, `src/vs/editor/browser/services/abstractCodeEditorService.ts`, `src/vs/editor/common/viewModel/inlineDecorations.ts`, `src/vs/editor/test/common/viewModel/inlineDecorations.test.ts`
- **Validation:** In a disposable Git repository with committed code surrounding an empty line, enable git.blame.editorDecoration.enabled and disable third-party extensions. Repeatedly invoke editor.action.deleteLines on empty and non-empty lines, then undo and redo without vertical cursor movement. Verify that no annotation appears before surviving code or remains at a stale position; capture the failing sequence in an automated regression test once the responsible lifecycle is identified.
- **Behavior:**

  > With built-in inline Git blame enabled, deleting a line can place its annotation before the surviving code, and undo may preserve the incorrect position. A displayed annotation must remain after the relevant line's code through repeated deletion, undo, and redo without requiring cursor navigation to repair it. Acceptance covers empty and non-empty deleted lines and preserves ordinary blame updates and the existing suppression of unnecessary annotations while typing.
- **Trace:**

  > The reporter and an independent commenter confirmed the behavior, with additional Ubuntu steps in https://github.com/microsoft/vscode/issues/247735, which was closed as a duplicate of this issue. In extensions/git/src/blame.ts, getEditorDecorationRange constructs an end-of-line point range, GitBlameEditorDecoration applies after-content styling, and GitBlameController refreshes on selection and diff-information events while suppressing equivalent blame values. The shared renderer in src/vs/editor/common/viewModel/inlineDecorations.ts renders after-content at the tracked range end; that is not a general end-of-line guarantee. The investigation has not established whether a migrated range survives an equivalent blame update, whether stale-diff clearing is bypassed, or whether another editor lifecycle interaction is responsible. Reproduce the precise event sequence before assigning the fix boundary, and preserve general decoration anchoring semantics, status-bar behavior, and typing-time suppression. The same-symptom https://github.com/microsoft/vscode/issues/277083 is newer and is related evidence rather than a canonical target.

- **Current blame lifecycle:** extensions/git/src/blame.ts creates zero-width end-of-line ranges in getEditorDecorationRange and applies after-content decorations in GitBlameEditorDecoration._createDecoration. GitBlameController listens to selection and diff-information changes, clears blame for stale diffs, and suppresses equivalent updates using isResourceBlameInformationEqual, which compares resource, line numbers, and blame identity rather than tracked decoration positions. This identifies a refresh interaction to investigate, but does not conclusively establish the event sequence causing the report.
- **Shared renderer boundary:** src/vs/editor/browser/services/abstractCodeEditorService.ts maps after-content styling and rangeBehavior into model decoration options. src/vs/editor/common/viewModel/inlineDecorations.ts positions afterContentClassName at the decoration's current range end, not necessarily the text line's end. Existing coverage in src/vs/editor/test/common/viewModel/inlineDecorations.test.ts verifies that positioning contract; changing it globally would affect unrelated decorations.
- **No established fix:** The linked performance issue https://github.com/microsoft/vscode/issues/245948 does not establish a fix for annotation positioning; this reporter explicitly confirmed persistence after 1.99.2. Inspection of Git blame commit history and this issue's cross-references identified no concrete fixing commit or linked open implementation PR.
