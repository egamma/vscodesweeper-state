# Issue #108954 — Matching bracket decoration and :after decoration clash

[https://github.com/microsoft/vscode/issues/108954](https://github.com/microsoft/vscode/issues/108954)

## Summary

The clash remains source-reproducible on current main: an `after` attachment at the matching bracket's start is inserted into the DOM range used to measure the bracket overlay, causing the overlay to span the injected text. No canonical issue or fixing commit was found, so this should remain open.

## Change summary

Matching-bracket highlighting incorrectly covers text injected by an extension decoration immediately before the bracket.

## Best solution

Bracket and other model-range overlays should measure only the corresponding model text, excluding adjacent injected `before` or `after` content, while preserving attachment placement and cursor mapping behavior.

## Plan brief

- **Likely files:** `src/vs/editor/common/viewLayout/viewLineRenderer.ts`, `src/vs/editor/browser/viewParts/viewLines/viewLine.ts`, `src/vs/editor/browser/viewParts/decorations/decorations.ts`, `src/vs/editor/test/common/viewLayout/viewLineRenderer.test.ts`
- **Validation:** Exercise the issue's extension-decoration scenario in an editor rendering test or equivalent browser check and assert that the `.bracket-match` overlay width covers only the bracket while the injected `after` text retains its position and styling.
- **Behavior:**

  > When extension-provided `before` or `after` content is adjacent to a matched bracket, the matching-bracket background and border must cover only the model bracket character. The injected content must keep its own styling and location. Cursor placement, hit testing, ordinary range decorations, and attachments away from brackets must remain unchanged.
- **Trace:**

  > `BracketMatchingController` creates both an overlay `className` and an inline foreground class for the model bracket range. Injected `after` content is represented as a zero-width `PSEUDO_AFTER` line part by `LineDecorationsNormalizer`, and `_renderLine` adjusts its model-to-DOM mapping through `partDisplacement`. `DecorationsOverlay` obtains the bracket rectangle through `linesVisibleRangesForRange`; the slow rendered-line path ultimately measures a DOM range whose endpoints can enclose the pseudo-element at the bracket's starting column. The uncertainty begins at the geometry contract: excluding injected content must not change cursor affinity, selection geometry, or attachment behavior for other overlay consumers.
- **Open decisions:**
  - Should model-range geometry exclude adjacent injected content globally, or should only decoration overlays request attachment-free geometry?
  - Which existing browser or component-test surface can assert rendered pixel bounds without weakening cursor and selection coverage?
