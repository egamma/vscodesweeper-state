# Issue #182011 — Copy & Paste support for Simple Browser

[https://github.com/microsoft/vscode/issues/182011](https://github.com/microsoft/vscode/issues/182011)

## Summary

Still unresolved on main: Simple Browser's webview wrapper (extensions/simple-browser/preview-src/index.ts) has no clipboard/keydown handling, and per maintainer analysis (comment by jmcphers) the content is loaded three iframes deep with a different origin, so VS Code's webview JS cannot attach listeners inside it — a real, non-trivial architectural limitation, not a quick fix. The prior review's cited fix commit was refuted and I found no replacement fix on current main, so this stays open.

## Change summary

Copy/paste (and context menu) don't work for content shown inside the Simple Browser's cross-origin content iframe.

## Best solution

Needs a maintainer-chosen approach per jmcphers' analysis: either an event-absorbing overlay layer over the webview, or a proxy that injects key/mouse forwarding into the loaded HTML — both are nontrivial, security-sensitive designs affecting extensions/simple-browser, so this should be scoped and decided before implementation.

## Plan brief

- **Likely files:** `extensions/simple-browser/preview-src/index.ts`, `extensions/simple-browser/src/simpleBrowserView.ts`, `extensions/simple-browser/media/main.css`
- **Validation:** Manual check: open Simple Browser on a cross-origin page (e.g. https://example.org), select text, and confirm Cmd/Ctrl+C and the right-click context menu both work to copy, and Cmd/Ctrl+V pastes into a form field on the page.
- **Behavior:**

  > Inside Simple Browser, selecting text on a loaded (cross-origin) page and using Ctrl/Cmd+C, the browser's native context menu Copy item, or Ctrl/Cmd+V into a form field should work the same as in a regular browser tab. Today none of these work for most sites because the wrapping webview has no handlers reaching the content iframe.
- **Trace:**

  > The Simple Browser page (extensions/simple-browser/preview-src/index.ts) wraps a `<iframe>` that itself loads a viewer iframe, which loads the actual cross-origin content iframe — three levels deep (see jmcphers' comment timeline 2024-05-30). Same-origin policy prevents the outer webview's JS from attaching keydown/clipboard/contextmenu listeners inside that innermost cross-origin frame, so no copy/paste events ever reach VS Code. The boundary: do not change same-origin webviews' existing context-menu handling (noted as already working two layers up); any fix must specifically address the innermost cross-origin content frame. Related: https://github.com/microsoft/vscode/issues/182642 was suggested as related in comment by gjsjohnmurray.
- **Open decisions:**
  - Should VS Code add a transparent event-absorbing overlay over the Simple Browser content iframe to intercept copy/paste/context-menu events before they reach the cross-origin frame, accepting the UX tradeoff of a slightly less direct page interaction?
  - Alternatively, should VS Code inject a key/mouse-forwarding script into the loaded third-party HTML via a proxy layer, and if so what are the security/CSP implications of rewriting arbitrary third-party page content?
  - Is partial support (e.g. relying on the existing Edit menu Copy command workaround) an acceptable permanent answer, or is a native-feeling in-page copy/paste considered a required fix?

## Evidence

- **no clipboard handling in source:** extensions/simple-browser/preview-src/index.ts has no keydown/copy/paste/context-menu handlers; the only message handling is for 'focus' and 'didChangeFocusLockIndicatorEnabled'.
- **no recent fix commits:** git log on extensions/simple-browser/ shows no commits addressing copy/paste since the last unrelated change (3a7c8e01, agentHost attribution, unrelated).
- **maintainer root-cause analysis:** jmcphers' 2024-05-30 comment traces the content iframe as three levels deep and cross-origin, meaning event handlers can't be attached due to browser same-origin policy — not a simple fix, two possible but unimplemented mitigations proposed.
