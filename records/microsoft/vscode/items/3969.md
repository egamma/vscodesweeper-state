# Issue #3969 — Add suggested completions for key chords

[https://github.com/microsoft/vscode/issues/3969](https://github.com/microsoft/vscode/issues/3969)

## Summary

Keep open: current chord dispatch still displays only a waiting message, not the available continuations. This accepted Backlog request has 52 upvotes, and neither the existing shortcut-search UI nor the verified related issues covers the native-chord discovery gap.

## Change summary

Show available command names and remaining keystrokes while a native keyboard chord is awaiting completion.

## Best solution

Provide accessible, context-aware discovery of native chord continuations without interrupting users who already know the shortcut. A maintainer should settle the presentation and activation behavior before implementation; telemetry-based personalization is optional, not necessary to satisfy the central request.

- **Behavior:**

  > Users who begin a native keyboard chord should be able to discover available continuations without cancelling the chord and searching the Command Palette. Suggestions should identify commands and the remaining keystrokes, reflecting the bindings applicable in the original context. Completing a known chord must retain its existing command and arguments. Acceptance includes custom and multi-step bindings, dismissal when chord mode ends, and equivalent keyboard and screen-reader access; optional personalized ranking is outside the minimum goal.
- **Trace:**

  > AbstractKeybindingService._doDispatch sends MoreChordsNeeded to _expectAnotherChord in src/vs/platform/keybinding/common/abstractKeybindingService.ts; the current path provides only a status message and a five-second inactivity timeout. KeybindingResolver.resolve in src/vs/platform/keybinding/common/keybindingResolver.ts already performs prefix matching and context evaluation, but returns a resolution outcome rather than a candidate collection. IKeybindingService in src/vs/platform/keybinding/common/keybinding.ts exposes inChordMode and registered bindings, but no pending-prefix discovery contract. The workbench implementation is src/vs/workbench/services/keybinding/browser/keybindingService.ts. Preserve dispatch precedence, when-clause semantics, keyboard-layout resolution, command arguments, IME handling, and focus-loss cleanup. Existing Keyboard Shortcuts searches and configurable which-key menus are separate workflows, not coverage of this request. https://github.com/microsoft/vscode/issues/107423 corroborates demand for a delayed overlay but is closed and younger; https://github.com/microsoft/vscode/issues/334775 addresses a different extension-hint contract. The remaining uncertainty is the user-facing activation and interaction design, not whether the current waiting path contains suggestions.
- **Open decisions:**
  - Should continuation hints appear immediately, after a pause, or only through explicit invocation, and should that behavior be enabled by default?
  - Should the surface remain informational while users finish the chord, or also support selecting a command with navigation keys, with explicit rules for preserving the original dispatch context?

## Evidence

- **current native-chord behavior:** At checkout commit 7f1c8a96ce99bcffba134a7db3ef9b1f57d30ca0, src/vs/platform/keybinding/common/abstractKeybindingService.ts routes ResultKind.MoreChordsNeeded to _expectAnotherChord. That method records the prefix, displays 'Waiting for second key of chord...' or 'Waiting for next key of chord...', and schedules timeout handling; it does not display candidate continuations.
- **resolver boundary:** src/vs/platform/keybinding/common/keybindingResolver.ts, KeybindingResolver.resolve, filters candidates by the pressed prefix and evaluates when clauses through _findCommand. Its incomplete-sequence result is MoreChordsNeeded, not a list of command names and remaining keys. Any discovery surface must agree with dispatch context and binding precedence.
- **existing-capability check:** The Keyboard Shortcuts editor supports Record Keys through keybindings.editor.recordSearchKeys and Show Same Keybindings through keybindings.editor.showConflicts, registered in src/vs/workbench/contrib/preferences/browser/preferences.contribution.ts. These require opening the editor and searching; they do not provide suggestions during native chord execution. Searches of the keybinding service, preferences contributions, and configuration/command surfaces found no chord-suggestion capability.
- **discussion and extension workarounds:** The supplied discussion links Leader Mode, Chord Heavy, VSpaceCode, and vscode-which-key. The 2024 comment explicitly distinguishes those workarounds from support for native chords. https://github.com/VSpaceCode/vscode-which-key documents customizable which-key menus, which is not evidence that VS Code automatically discovers continuations for its registered native bindings.
- **canonical search:** Repository searches for chord suggestions, which-key, keybinding discoverability, and shortcut popups found no verified older open issue owning this same request. https://github.com/microsoft/vscode/issues/107423 describes the same delayed chord-overlay idea but was created in 2020 and is closed following the community upvote process; it cannot be a duplicate canonical for this re-reviewed 2016 issue.
