# Issue #346559 — Expose custom text editor selections (e.g. the Markdown Editor) to extensions

[https://github.com/microsoft/vscode/issues/346559](https://github.com/microsoft/vscode/issues/346559)

## Summary

A distinct extension-API gap remains: built-in Chat can consume custom-editor selections, but other extensions cannot read that selection through the existing APIs. Keep open as a feature request; the previously closed reports do not own this remaining work.

## Change summary

Expose custom text editors' source-coordinate selections and selection changes read-only to consuming extensions.

## Best solution

Have the extension API owners evaluate a read-only document-and-selection contract for custom text editors, including active-panel changes and cleared or unavailable selections. Preserve existing TextEditor semantics rather than treating a webview as a full text editor.

## Evidence

- **Existing API does not cover consumers:** src/vscode-dts/vscode.proposed.customTextEditorNavigation.d.ts exposes selection and onDidChangeSelection on a controller returned by the owning CustomTextEditorProvider. In src/vs/workbench/api/common/extHostCustomEditors.ts:321–346, that controller forwards selections to the workbench; it provides no public accessor or consumer event for other extensions.
- **Tab API exposes identity only:** src/vscode-dts/vscode.d.ts:19469–19484 defines TabInputCustom with uri and viewType, but no selection. src/vs/workbench/api/browser/mainThreadEditorTabs.ts:165–170 likewise serializes only the custom editor's kind, viewType, and resource URI.
- **Built-in Chat coverage is internal:** src/vs/workbench/contrib/chat/browser/attachments/chatImplicitContext.ts:76–90 subscribes directly to CustomEditorInput.navigation; lines 224–228 obtain its model and selection internally. https://github.com/microsoft/vscode/pull/340717 is merged and explicitly describes implementing this without an extension API.
