# Issue #348975 — ResourceTree.delete() drops a folder element when its last child is deleted

[https://github.com/microsoft/vscode/issues/348975](https://github.com/microsoft/vscode/issues/348975)

## Summary

The defect remains in current main and has a maintainer-confirmed reproduction. Keep the issue open while the existing fix proposals are reviewed and landed.

## Change summary

Deleting a folder's last child incorrectly removes the folder's own ResourceTree element.

## Best solution

Land the existing fix through https://github.com/microsoft/vscode/pull/349880, coordinating with the original contribution at https://github.com/microsoft/vscode/pull/348976. Preserve element-bearing ancestors while retaining structural-node pruning and explicit subtree deletion.

## Evidence

- **Current source confirms the defect:** In src/vs/base/common/resourceTree.ts, ResourceTree._delete() recursively removes /foo/file.txt, then removes its parent when the returned element is defined and child.childrenCount === 0. It never checks child.element, so the reporter's /foo element is removed and collect(root) returns [].
- **Supported state and deletion boundary:** ResourceTree.add() preserves elements on intermediate nodes. The existing 'folders with data' test in src/vs/base/test/common/resourceTree.test.ts establishes that folders may have both elements and children, and that explicitly deleting such a folder removes its subtree.
- **Maintainer confirmation:** The supplied discussion at https://github.com/microsoft/vscode/issues/348975 includes a 2026-11-24 maintainer confirmation of the exact reproduction on current main and endorsement of preserving ancestors with elements.
- **Open implementation candidates:** Read-only GitHub inspection confirms https://github.com/microsoft/vscode/pull/348976 and https://github.com/microsoft/vscode/pull/349880 are both OPEN and both state 'Fixes #348975'. The latter carries the original fix with extended regression coverage and says it remains draft pending the original contributor's CLA.
- **Impact qualification:** The description of https://github.com/microsoft/vscode/pull/349880 reports that current production consumers rebuild their ResourceTrees rather than calling delete(). This supports treating the confirmed utility defect as correctness, not established user-file data loss.
