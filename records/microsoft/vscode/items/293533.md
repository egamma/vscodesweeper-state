# Issue #293533 — MCP: Cannot authenticate to multiple Atlassian sites simultaneously - OAuth credentials shared across MCP server configurations

[https://github.com/microsoft/vscode/issues/293533](https://github.com/microsoft/vscode/issues/293533)

## Summary

Keep open: current authentication supports multiple tokens and per-server account preferences, but does not distinguish same-account site bindings across MCP configurations. The discussion confirms demand, while the proposed origin-only overwrite diagnosis is incomplete and needs a standards-preserving design.

## Change summary

Allow multiple MCP configurations sharing an authorization server to retain independently selected Atlassian site or credential contexts.

## Best solution

Support independently selected credential/resource contexts for these MCP entries without changing OAuth issuer semantics or requiring Atlassian-specific handling. Establish whether isolation is explicit or automatic, including what happens to existing bindings after configuration changes.

## Plan brief

- **Likely files:** `src/vs/workbench/api/browser/mainThreadMcp.ts`, `src/vs/workbench/api/common/extHostAuthentication.ts`, `src/vs/workbench/services/authentication/browser/authenticationMcpService.ts`, `src/vs/workbench/services/authentication/browser/dynamicAuthenticationProviderStorageService.ts`, `src/vs/workbench/api/test/browser/mainThreadMcp.test.ts`, `src/vs/workbench/api/test/browser/extHostAuthentication.test.ts`
- **Validation:** Add a mocked regression in mainThreadMcp.test.ts with two server definitions sharing authorization server, scopes, and account label but distinct selected credential/resource contexts. Authenticate A, then B, and verify subsequent token retrieval for each retains its selected context, including after restoration. Cover the agreed rename/resource-change semantics and preserve existing issuer discovery, URL consent, and distinct-account selection. Confirm the same two-entry sequence with getAccessibleAtlassianResources in a maintainer-run live check.
- **Behavior:**

  > Two MCP configurations using the same authorization server must be able to maintain independently selected site or credential contexts. Authenticating entry B must not change which intended site entry A accesses. Existing single-entry authentication and intentional credential reuse must continue to work according to the agreed isolation policy. Acceptance includes repeated tool calls through both entries, restoration of their bindings, and explicit behavior when an entry is renamed or its resource changes.
- **Trace:**

  > MainThreadMcp resolves a provider from authorization-server and resource metadata, then retrieves sessions and chooses by a per-server account-label preference. AuthenticationMcpService.selectSession deduplicates choices by account.label, while DynamicAuthProvider's TokenStore maps tokens lacking identity claims to the same 'MCP' label. TokenStore retains distinct access tokens, so a shared persistence key alone does not prove overwrite; the trace establishes a selection limitation rather than the reporter's full causal explanation. Protected-resource metadata already contributes to provider identity, and URL-bound consent already exists; preserve both and keep issuer validation unchanged. The discussion at https://github.com/microsoft/vscode/issues/293533 contains conflicting accounts of multi-site versus site-specific tokens, so planning should establish the actual gateway/token behavior before choosing a public isolation contract. The older https://github.com/microsoft/vscode/issues/282354 concerns related account presentation, not a duplicate of this capability.
- **Open decisions:**
  - Should independent credential/resource bindings be automatic for each configured MCP entry, or explicitly selectable while retaining default credential sharing?
  - When an entry is renamed or its configured resource changes, should its binding be preserved through an explicit migration or require a fresh selection and authorization?
