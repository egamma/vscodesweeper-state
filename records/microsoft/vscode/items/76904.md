# Issue #76904 — Hirerarchical multi-root layout

[https://github.com/microsoft/vscode/issues/76904](https://github.com/microsoft/vscode/issues/76904)

## Summary

Keep this accepted, well-supported request open: current workspace loading and Explorer rendering still lack arbitrary hierarchical groups of workspace roots. Related requests do not provide an older canonical covering the same observable requirement.

## Change summary

Allow workspace folders to appear under named, nested Explorer groups independent of their filesystem locations.

## Best solution

Provide persistent, collapsible logical grouping of workspace roots while preserving existing folder settings, search scope, and extension-facing workspace membership. A maintainer should settle the configuration contract and whether separate Explorer views or editor-group behavior belong in this feature or follow-up work.

## Plan brief

- **Likely files:** `src/vs/platform/workspaces/common/workspaces.ts`, `src/vs/workbench/services/configuration/common/configurationModels.ts`, `src/vs/workbench/contrib/files/common/explorerModel.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/test/browser/explorerModel.test.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** After agreeing on the configuration contract, add workspace-conversion and Explorer tests for two-level logical groups containing unrelated folder paths, mixed grouped and ungrouped roots, and unchanged legacy flat workspaces. Manually open and reload that workspace, collapse a group, open its files, and verify all leaf folders remain searchable with their existing folder settings.
- **Behavior:**

  > Users need to organize independent workspace folders under named, collapsible groups that can themselves contain groups, without rearranging directories on disk. The example should display Project A and Project B as logical parents, Backend as a nested parent, and Common as an ungrouped root. Grouping should persist across workspace reloads, and existing flat workspace files must remain compatible. Acceptance should verify both the requested hierarchy and unchanged leaf-folder membership, search scope, and folder settings.
- **Trace:**

  > IStoredWorkspaceFolder and its guards in src/vs/platform/workspaces/common/workspaces.ts represent path/uri leaf entries, and toWorkspaceFolders processes them as a flat list; named folders-only containers are not recognized. WorkspaceConfigurationModelParser in src/vs/workbench/services/configuration/common/configurationModels.ts exposes that stored folder list. ExplorerModel in src/vs/workbench/contrib/files/common/explorerModel.ts constructs parentless roots, and the Explorer data source in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts returns the input roots directly. Existing compact-folder and file-nesting settings operate on filesystem children, not logical workspace groups. The uncertainty begins at the persisted grouping contract and whether groups are presentation-only or introduce additional workspace semantics; preserve legacy flat files and existing leaf-folder behavior. https://github.com/microsoft/vscode/issues/43188 concerns multiple workspaces rather than this hierarchy, while https://github.com/microsoft/vscode/issues/191859 explicitly points back to this report. No execution was performed in the read-only checkout.
- **Open decisions:**
  - Should grouping be serialized as recursive folders entries, metadata on a flat folder list, or a separate layout section, and what compatibility should existing workspace readers retain?
  - Should logical groups affect only Explorer presentation, or also provide separate Explorer views and editor-group associations described in the issue?
