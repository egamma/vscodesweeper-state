# Issue #175872 — setBreakpoints is called with sourceModified:false when source is dirty and new breakpoint is added

[https://github.com/microsoft/vscode/issues/175872](https://github.com/microsoft/vscode/issues/175872)

## Summary

The incorrect `sourceModified: false` path remains on current main: breakpoint edits caused by source changes are queued for save, but adding another breakpoint immediately sends all breakpoints with the default `false`. The issue should remain open while the debug area defines the intended dirty-source request lifecycle.

## Change summary

Adding a breakpoint after unsaved edits sends breakpoint locations from the modified buffer with `sourceModified: false`.

## Best solution

Make breakpoint synchronization consistently preserve the source-modified state across subsequent breakpoint operations, with the exact request timing aligned to a clarified DAP contract: either defer dirty-source requests until save or explicitly identify them as modified.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugService.ts`, `src/vs/workbench/contrib/debug/browser/breakpointEditorContribution.ts`, `src/vs/workbench/contrib/debug/test/browser/breakpoints.test.ts`
- **Validation:** Add a debug breakpoint-synchronization test that marks a resource pending after breakpoint decorations move, adds another breakpoint before save, and asserts the maintainer-selected request behavior before and after an UPDATED file event; run it with `scripts/test.sh --grep "sourceModified"`.
- **Behavior:**

  > Breakpoint requests must never describe locations from an unsaved, line-shifted buffer as unmodified source. Adding, removing, enabling, or otherwise changing a breakpoint while that source is dirty must follow one consistent DAP lifecycle. Saving the resource must leave the adapter with the complete current breakpoint set and the correct `sourceModified` value. Breakpoint behavior for clean resources must remain immediate and unchanged.
- **Trace:**

  > BreakpointEditorContribution.onModelDecorationsChanged in src/vs/workbench/contrib/debug/browser/breakpointEditorContribution.ts updates moved breakpoint locations through `DebugService.updateBreakpoints(..., true)`. DebugService records the URI in `breakpointsToSendOnResourceSaved`, but operations such as `addBreakpoints` independently call `sendBreakpoints(uri)`, whose default argument is false; the pending dirty-source state is not consulted. DebugService.onFileChanges later sends true and clears the pending URI after an UPDATED event. The defect is therefore source-reproducible and bounded to breakpoint synchronization, but https://github.com/microsoft/debug-adapter-protocol/issues/376 leaves the externally observable choice unresolved: defer requests while dirty, as historically documented at https://github.com/microsoft/vscode/issues/8077#issuecomment-230244837, or send them immediately with `sourceModified=true`. Do not change clean-resource breakpoint behavior, breakpoint location tracking, or unrelated debug request types.
- **Open decisions:**
  - While a source has pending line-moving edits, should subsequent breakpoint operations be withheld until save, or sent immediately with `sourceModified=true`?
  - What exact request and flag transition should occur on save so adapters that do and do not hot reload receive an unambiguous current breakpoint set?

## Evidence

- **current source:** In src/vs/workbench/contrib/debug/browser/debugService.ts, `addBreakpoints` calls `sendBreakpoints(uri)` without a flag, and `sendBreakpoints` defaults `sourceModified` to false before forwarding it to the debug session.
- **dirty-source path:** BreakpointEditorContribution.onModelDecorationsChanged in src/vs/workbench/contrib/debug/browser/breakpointEditorContribution.ts calls `updateBreakpoints(..., true)`, which only records the URI in `breakpointsToSendOnResourceSaved`; that pending state is not consulted when a later breakpoint operation calls `sendBreakpoints`.
- **save behavior:** DebugService.onFileChanges removes a pending URI and calls `sendBreakpoints(uri, true)` only after an UPDATED file event, confirming that the normal add-breakpoint path can send false while the same resource is pending save.
- **maintainer confirmation:** https://github.com/microsoft/vscode/issues/175872#issuecomment-1494755207 acknowledges that adding a breakpoint triggers a normal request with `sourceModified=false` and says this behavior needs investigation.
- **protocol decision:** https://github.com/microsoft/debug-adapter-protocol/issues/376 remains open and asks whether dirty-source breakpoint requests should be deferred or sent with `sourceModified=true`; it is related specification work, not a duplicate of this VS Code behavior bug.
- **historical behavior:** https://github.com/microsoft/vscode/issues/8077#issuecomment-230244837 documented the earlier contract: track breakpoint changes while dirty, send no requests until save, then send one request with `sourceModified=true`.
