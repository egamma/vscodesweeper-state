# Issue #329320 — [Copilot Agent] Explicitly selected read toolset is omitted from tools passed to a third-party language model provider

[https://github.com/microsoft/vscode/issues/329320](https://github.com/microsoft/vscode/issues/329320)

## Summary

A detailed, well-diagnosed report pointing at the Copilot extension's virtual tool grouping/expansion pipeline; I traced a plausible mechanism in the source (session-scoped tool-group caching plus per-turn ensureExpanded application) that could silently drop an explicitly-referenced toolset, but I can't fully pin the exact failure without executing the code, so this goes to the area owner rather than an auto-fix.

## Change summary

When a user explicitly references the `#read` toolset with a third-party language-model provider in Agent mode, the expanded `readFile` tool never reaches `options.tools` on the provider's `provideLanguageModelChatResponse`, even though it is enabled and referenced.

## Best solution

Have the Copilot Chat extension's tools/virtualTools owner trace `getAvailableTools()` in extensions/copilot/src/extension/prompt/node/defaultIntentRequestHandler.ts (which calls `toolGrouping.ensureExpanded(ref.name)` only when `this.toolGrouping` is falsy on this handler instance) together with `ToolGroupingService.create()` in extensions/copilot/src/extension/tools/common/virtualTools/toolGroupingService.ts (which returns a cached `ToolGrouping` per session id from an LRU cache) and `ToolGrouping._doCompute()` in toolGrouping.ts (which applies `_expandOnNext` after `addGroups`/trimming) to confirm whether cross-turn caching or trim ordering can drop an explicitly-referenced tool, and add a regression test asserting a `#`-referenced toolset's member tools always survive into `compute()`'s returned tool list on the very first turn.

## Evidence

- **expansion call site:** extensions/copilot/src/extension/prompt/node/defaultIntentRequestHandler.ts:788-798 only iterates `this.options.request.toolReferences` calling `this.toolGrouping.ensureExpanded(ref.name)` in the branch where `this.toolGrouping` is not yet set on the handler instance; it is skipped once a handler already has a grouping reference.
- **shared grouping cache:** extensions/copilot/src/extension/tools/common/virtualTools/toolGroupingService.ts:30-40 caches `ToolGrouping` instances in an `LRUCache<string, IToolGrouping>(3)` keyed by `sessionId`, reusing the same instance (and its expansion/trim state) across turns rather than creating a fresh one per turn.
- **trim/expand ordering:** extensions/copilot/src/extension/tools/common/virtualTools/toolGrouping.ts:132-171 `_doCompute` runs `addGroups` (rebuild), then applies `_expandOnNext`, then trims down to `HARD_TOOL_LIMIT`/`TRIM_THRESHOLD` by collapsing the lowest-`lastUsedOnTurn` expanded tool — a plausible place for a just-expanded tool to be re-collapsed if `lastUsedOnTurn` bookkeeping doesn't protect it in every path.
- **third-party vs first-party asymmetry:** getAvailableTools() in defaultIntentRequestHandler.ts returns tools unmodified when `this.options.invocation.endpoint.supportsToolSearch` is true, bypassing the whole virtual-grouping/expansion path — plausibly explaining why GitHub's own models are less likely to hit this than third-party `LanguageModelChatProvider` extensions that don't support tool search.
- **id/name mapping verified consistent:** src/vs/workbench/api/common/extHostLanguageModelTools.ts:49/63 sets `LanguageModelToolInformation.name = this._data.id`, and extHostTypeConverters.ts:3696-3707 sets the tool reference's `name` to the same `variable.id`, so the reference name used in `ensureExpanded` does correctly match the tool tree's node names — ruling out a naming mismatch as the cause and pointing back to the caching/ordering logic above.
