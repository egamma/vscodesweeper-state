# Issue #330184 — VS Code launches in the wrong RDP session

[https://github.com/microsoft/vscode/issues/330184](https://github.com/microsoft/vscode/issues/330184)

## Summary

Verified duplicate of the long-standing open issue https://github.com/microsoft/vscode/issues/132872, which tracks the exact same scenario (same Windows user, multiple concurrent RDP sessions, second session's window opens in the first session) and has years of active discussion and workarounds — proposing consolidation there.

## Change summary

On Windows Server with multi-session-per-user RDP enabled, launching VS Code in a second RDP session for the same user opens the window in the first session instead of the current one.

## Best solution

Keep the discussion at https://github.com/microsoft/vscode/issues/132872 (labeled bug/upstream). Root cause traced in this checkout: `createStaticIPCHandle` in src/vs/base/parts/ipc/node/ipc.net.ts (line 924) derives the Windows named-pipe name only from a hash of the user data directory, version, and type — with no Windows Terminal-Services session-id component — and Windows named pipes (`\\.\pipe\...`) are not session-isolated by default (unlike mutexes/events, which get per-session namespaces without a `Global\` prefix). So the second session's instance-detection client connects to the first session's already-listening pipe (`main.ts` claimInstance, around line 360-379) and asks it to open a window there.

## Evidence

- **canonical issue:** https://github.com/microsoft/vscode/issues/132872 is open, labeled bug/upstream/windows/remote-desktop/chromium, describes the identical symptom (same user, two RDP sessions, second window opens in the first session), and has ongoing comments through recent months with workarounds (e.g. `--user-data-dir=...%CLIENTNAME%`).
- **root cause traced:** src/vs/base/parts/ipc/node/ipc.net.ts:924-931 — `createStaticIPCHandle` builds the Windows pipe name as `\\.\pipe\<hash(userDataPath)>-<version>-<type>-sock`, with no session component; src/vs/code/electron-main/main.ts:352-410 `claimInstance` connects to that pipe on EADDRINUSE and forwards the open request to the existing (first-session) instance.
- **OS behavior:** Windows named pipes are global/system-wide by default and are not subject to the per-session Terminal-Services object-namespace isolation that applies to mutexes/events/semaphores unless a `Global\`/`Local\` prefix scheme is used — confirmed via public documentation and prior Stack Overflow discussion on this exact Terminal Services quirk.
- **same-user requirement:** This issue explicitly reproduces with `fSingleSessionPerUser=0` and the same logon — the same precondition as #132872 ("connect with different RDP Sessions using the same Windows User account").
