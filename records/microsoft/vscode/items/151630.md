# Issue #151630 — Explorer root is hard to work with when in a repo with many folders

[https://github.com/microsoft/vscode/issues/151630](https://github.com/microsoft/vscode/issues/151630)

## Summary

Keep open: current source still lacks a stable root drop target when a single-folder Explorer fills the viewport, and maintainers previously accepted this as Explorer polish for design exploration.

## Change summary

Make it practical to drag a nested file to the workspace root when folders occupy the entire visible Explorer.

## Best solution

Provide a discoverable, consistently available workspace-root target for file creation and drag-and-drop in crowded single-folder Explorer views without disrupting ordinary folder drop targets.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** In a non-maximized single-folder window opened on the VS Code repository, create a file under `.vscode`, ensure folder rows fill the Explorer viewport, and verify that the file can be dragged to the workspace root through the chosen root affordance without first collapsing or scrolling the tree; dropping onto an ordinary folder must remain unchanged.
- **Behavior:**

  > A crowded single-folder Explorer must retain a discoverable target for moving a nested file to the workspace root, even when no empty tree background is visible. The target must clearly represent the root rather than a neighboring folder. Existing drops onto folders and multi-root folder reordering must continue to behave as before.
- **Trace:**

  > ExplorerView in src/vs/workbench/contrib/files/browser/views/explorerView.ts uses the sole ExplorerItem root as the tree input for a single-folder workspace, so that root is not rendered as a selectable row. FileDragAndDrop.handleDragOver in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts offers folder targets for occupied rows and uses the undefined-target path for empty background; drop maps an undefined target to the last workspace root. When rows fill the viewport, that empty-background root path is effectively unavailable. The issue was repeatedly listed for UX exploration in https://github.com/microsoft/vscode/issues/163069, https://github.com/microsoft/vscode/issues/165643, and https://github.com/microsoft/vscode/issues/170413. Preserve ordinary directory drops, copy modifiers, compressed-folder targeting, and multi-root reordering; the uncertainty begins at which visible affordance should expose the single workspace root.
- **Open decisions:**
  - Which user-visible affordance should remain available as the workspace-root drop target when a single-folder Explorer has no empty background: a persistent root row, a dedicated drop region, or another discoverable interaction?

## Evidence

- **current source:** In src/vs/workbench/contrib/files/browser/views/explorerView.ts, ExplorerView sets the single workspace root itself as the tree input, while only multi-root workspaces render their roots as tree rows; consequently a single-folder workspace has no persistent visible root row to receive the drop.
- **drop path:** FileDragAndDrop.handleDragOver in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts treats a hovered directory as the drop target and relies on an undefined target for the empty-background path. FileDragAndDrop.drop then maps that undefined target to the workspace root, so the usable root target disappears when rows fill the viewport.
- **maintainer direction:** The October 2022, November 2022, and January 2023 iteration plans explicitly listed exploration of improving interaction with root files and folders in a crowded Explorer: https://github.com/microsoft/vscode/issues/163069, https://github.com/microsoft/vscode/issues/165643, and https://github.com/microsoft/vscode/issues/170413.
