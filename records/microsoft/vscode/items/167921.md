# Issue #167921 — Debug attach - launch.json pickProcess command launches before preLaunchTask

[https://github.com/microsoft/vscode/issues/167921](https://github.com/microsoft/vscode/issues/167921)

## Summary

This remains the canonical feature request for deferring interactive launch-variable resolution until after `preLaunchTask`. Current main still resolves `${command:pickProcess}` first, and a 2026 report of the same observable behavior was closed as a duplicate of this issue.

## Change summary

Allow a debug pre-launch task to create or prepare a process before `${command:pickProcess}` or other unrelated interactive launch variables are evaluated.

## Best solution

Use phased launch-variable resolution: resolve what is required to identify and run `preLaunchTask`, run the task successfully, and then resolve remaining command and input variables before the final debug configuration hook and session creation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugService.ts`, `src/vs/workbench/contrib/debug/common/debugger.ts`, `src/vs/workbench/services/configurationResolver/browser/baseConfigurationResolverService.ts`, `src/vs/workbench/services/configurationResolver/common/configurationResolver.ts`, `src/vs/workbench/services/configurationResolver/test/electron-browser/configurationResolverService.test.ts`
- **Validation:** Add a focused debug-start test recording command-resolution and task-run events: variables needed by `preLaunchTask` must resolve before the task, while `${command:pickProcess}` outside that property must execute only after the task succeeds; also verify that task failure prevents the picker from opening.
- **Behavior:**

  > Starting an attach configuration with a `preLaunchTask` must complete that task before prompting for `${command:pickProcess}` or evaluating other interactive variables unrelated to selecting the task. Variables required to determine the `preLaunchTask` itself must remain usable. If the task fails or is canceled, later interactive prompts must not appear. Configurations without a pre-launch task and non-interactive variable substitution must retain their existing behavior.
- **Trace:**

  > The ordering is in `DebugService.createSession` in src/vs/workbench/contrib/debug/browser/debugService.ts: `substituteVariables` processes the full provider-returned configuration before `DebugTaskRunner.runTaskAndCheckErrors`. `Debugger.substituteVariables` in src/vs/workbench/contrib/debug/common/debugger.ts delegates the entire object to `IConfigurationResolverService.resolveWithInteractionReplace`; `BaseConfigurationResolverService.resolveWithInteraction` then executes every unresolved command and input variable. The earlier https://github.com/microsoft/vscode/issues/95162 change only moved `resolveDebugConfigurationWithSubstitutedVariables` after the task and did not defer variable substitution. Preserve support for variables in the `preLaunchTask` property and preserve the two debug-configuration-provider phases; do not special-case C++, LLDB, or `pickProcess`, because comments demonstrate the same ordering problem with arbitrary command and input variables.
- **Open decisions:**
  - Should the pre-task phase resolve only variables reachable from the `preLaunchTask` property, deferring every other command/input variable until the task succeeds, or should another documented subset of launch properties resolve early?
  - When the same interactive variable appears both in `preLaunchTask` and elsewhere in the launch configuration, should it be evaluated once and reused or evaluated again after the task?

## Evidence

- **current source:** In src/vs/workbench/contrib/debug/browser/debugService.ts, `createSession` calls `substituteVariables` before `runTaskAndCheckErrors`; the latter runs `resolvedConfig.preLaunchTask`, so interactive command variables are necessarily invoked before the task on current main.
- **resolver behavior:** src/vs/workbench/contrib/debug/common/debugger.ts sends the complete configuration through `resolveWithInteractionReplace`, while src/vs/workbench/services/configurationResolver/browser/baseConfigurationResolverService.ts evaluates every unresolved command and input variable in that object.
- **remaining gap:** A comment reports that omitting the explicit `processId` lets one debugger's default picker run later, but explicitly configured and custom command variables still execute before the task; this workaround therefore does not cover the central request.
- **canonical confirmation:** https://github.com/microsoft/vscode/issues/287686 reported the same process-picker-before-task behavior against VS Code 1.108.0 and was closed in August 2026 as a duplicate explicitly tracked by https://github.com/microsoft/vscode/issues/167921.
- **earlier precedent:** https://github.com/microsoft/vscode/issues/75604 documented why resolving the whole configuration first was originally considered intentional, while the discussion here identifies the unresolved two-phase alternative needed to preserve variable use in `preLaunchTask`.
- **confirmed demand:** Multiple commenters reproduced the ordering across C++, LLDB, Go, Windows, macOS, Remote-SSH, and WSL scenarios, and the issue has 10 community upvotes.
