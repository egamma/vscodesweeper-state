# Issue #334256 — Vitest extension buttons are outside the panel viewport

[https://github.com/microsoft/vscode/issues/334256](https://github.com/microsoft/vscode/issues/334256)

## Summary

This looks like a real, still-open gap in core: the generic custom TreeView already got a 'stick actions to the visible right edge' CSS fix (the one referenced from issue #251722), but the dedicated Testing Explorer view was never given the same treatment, so long test/folder names still push its action buttons off-screen.

## Change summary

In the Testing Explorer view, inline action buttons (run/debug icons) for tests with long names or deep nested folder paths render outside the visible panel and become hard to reach.

## Best solution

Port the sticky-action CSS pattern from src/vs/workbench/browser/parts/views/media/views.css (`.customview-tree ... .actions { position: relative; right: var(--list-scroll-right-offset, 0px); }`, added for the NPM Scripts fix) into src/vs/workbench/contrib/testing/browser/media/testing.css for `.testing-stdtree-container .monaco-action-bar`, so the Testing Explorer's action bar behaves the same way when horizontal scrolling causes the label to overflow.

  > Thanks for the detailed report and screenshots. I traced this in the source: the generic extension TreeView styling (used e.g. by the built-in NPM Scripts view, per your linked https://github.com/microsoft/vscode/issues/251722) already has a rule that sticks inline actions to the visible right edge when horizontal scrolling causes overflow (`src/vs/workbench/browser/parts/views/media/views.css`). This looks like a genuine gap that should be ported over rather than something the Vitest extension itself can fix, since the Testing Explorer's rendering is entirely owned by VS Code core.

## Evidence

- **existing fix elsewhere in core:** src/vs/workbench/browser/parts/views/media/views.css lines 257-272 contain '/* When horizontal scrolling is enabled, shift actions back to the viewport's right edge */' rules using `right: var(--list-scroll-right-offset, 0px)`, applied to `.customview-tree` rows (used by generic extension TreeViews such as the built-in NPM Scripts view referenced in the report).
- **gap in testing view CSS:** src/vs/workbench/contrib/testing/browser/media/testing.css lines 34-81 define `.testing-stdtree-container`: when `.monaco-list.horizontal-scrolling` is active the `.label` gets `width: auto; overflow: visible` (intentionally overflowing for scroll), but `.monaco-action-bar` has no matching `right: var(--list-scroll-right-offset...)` rule to keep it pinned to the visible edge — no `list-scroll-right-offset` usage exists anywhere in testing.css.
- **confirmed same DOM/action-bar path:** src/vs/workbench/contrib/testing/browser/testingExplorerView.ts line 1526 (`wrapper.classList.add('testing-stdtree-container')`) and line 1533 (`new ActionBar(wrapper, ...)`) confirm the CSS selectors above target exactly the test tree rows' action bar.
- **reporter's own precedent:** Reporter cites https://github.com/microsoft/vscode/issues/251722 (closed, labels bug/tree-views/npm/insiders-released) as the prior fix for the same visual problem in the NPM Scripts panel; the underlying CSS mechanism from that fix is present on current main but not applied to the Testing view.
