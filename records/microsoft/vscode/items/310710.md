# Issue #310710 — Integrated browser "edit mode": use inline text edits as a signal for Copilot edits

[https://github.com/microsoft/vscode/issues/310710](https://github.com/microsoft/vscode/issues/310710)

## Summary

Keep this accepted backlog request open: current element commenting supplies browser context to Copilot, but does not let users edit page text inline and submit the before/after difference. The request has 22 upvotes, and no verified open canonical or landed implementation was found.

## Change summary

Let users temporarily edit rendered page text and submit those changes as context for Copilot to propose reviewable source edits.

## Best solution

Provide a text-only browser editing workflow that captures the original and edited copy with element context, then hands that intent to Copilot's normal source-edit review flow. Keep deterministic DOM-to-source mapping and non-text visual editing outside the initial scope.

## Plan brief

- **Likely files:** `src/vs/platform/browserView/electron-browser/preload-browserView.ts`, `src/vs/platform/browserView/common/browserView.ts`, `src/vs/platform/browserView/electron-main/browserViewFrameInspector.ts`, `src/vs/workbench/contrib/browserView/electron-browser/features/browserEditorChatFeatures.ts`
- **Validation:** On a local development page containing rendered text, enter the proposed edit mode, change the text inline, and save. Verify that Copilot receives the original and edited text with the correct element context and proposes normal reviewable source edits, rather than directly persisting DOM changes to files. Verify that ordinary element selection/commenting remains unchanged and that existing content-attachment consent and AI-availability gates are preserved.
- **Behavior:**

  > A user can temporarily edit text directly in an integrated-browser page rather than describe the replacement in chat. Saving supplies the original and replacement text, together with enough element context, for Copilot to propose source edits through its normal review flow. The feature does not promise deterministic DOM-to-source mapping. Acceptance should demonstrate that the submitted context preserves the exact requested copy change and that no source file is silently overwritten.
- **Trace:**

  > BrowserEditorChatFeatures currently turns an IElementData snapshot into a chat attachment through createElementContextValue and _attachElementDataToChat; comments are inserted separately by _insertElementCommentReference. The preload ElementPicker's _showCommentComposer and _submitComment collect a textarea comment without editing the selected page text. BrowserElementSelectionMode and IElementData in src/vs/platform/browserView/common/browserView.ts expose selection/commenting and current element context, but no text-edit transaction or before/after payload. BrowserViewFrameInspector is the existing main-process bridge for picked element data. The trace establishes adjacent infrastructure, not a finished design for temporary edits, rerenders, or navigation during editing; the planning session must establish that lifecycle and its validation. Preserve existing attachment consent, AI gating, and normal source-edit review, and exclude deterministic framework mapping and image editing. The broader alternative https://github.com/microsoft/vscode/issues/282975 is closed and does not absorb this accepted request.
- **Open decisions:**
  - When edit mode ends or the user cancels, should temporary page-text changes be restored automatically or remain visible until the page rerenders or reloads?
  - If the page rerenders or navigates before Save, should pending text edits be retained as a reviewable draft or explicitly discarded?
