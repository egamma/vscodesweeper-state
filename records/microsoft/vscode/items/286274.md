# Issue #286274 — Worktree entries shown in worktree list *and* top-level nodes is confusing

[https://github.com/microsoft/vscode/issues/286274](https://github.com/microsoft/vscode/issues/286274)

## Summary

Keep open for a worktree hierarchy decision: the repository explorer still presents opened worktrees as repository rows and as nested artifacts. The maintainer invited suggestions, and neither a referenced fix nor an older canonical covering the same duplication symptom was established.

## Change summary

Clarify worktree ownership and hierarchy when the same checkout appears both as a repository row and inside a Worktrees group.

## Best solution

Agree on a clear distinction between opened checkouts and worktree navigation in the Source Control Repositories explorer, then apply it consistently in main-repository and worktree-only windows. Preserve access to checkout changes and worktree actions rather than hiding either capability as a workaround.

- **Trace:**

  > RepositoryTreeDataSource.getChildren in src/vs/workbench/contrib/scm/browser/scmRepositoriesViewPane.ts flattens opened parent/child repositories into the explorer root and separately requests artifact groups under each repository. GitArtifactProvider in extensions/git/src/artifactProvider.ts supplies a Worktrees group and maps getWorktreeDetails results without filtering already-open checkout paths. Model.checkForWorktrees in extensions/git/src/model.ts controls automatic repository discovery, not artifact visibility. Disabling git.detectWorktrees or scm.repositories.explorer removes part of the experience rather than settling the hierarchy. - **Open decisions:**
