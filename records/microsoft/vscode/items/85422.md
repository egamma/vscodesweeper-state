# Issue #85422 — Change Start Debugging Extension Host on Running Extensions to not require a restart

[https://github.com/microsoft/vscode/issues/85422](https://github.com/microsoft/vscode/issues/85422)

## Summary

The central request remains unmet: the Running Extensions debug action still requests a restart without attempting to enable the running host's inspector. Debugging in a separate window is already implemented, but that partial coverage does not resolve the restart requirement.

## Change summary

Allow debugging an already-running extension host without restarting it and losing the state being investigated.

## Best solution

The Running Extensions debug action should attach to the existing local extension host without restarting when dynamic inspector activation is supported, preserving the current separate-window debugging behavior.

- **Behavior:**

  > A developer investigating a transient extension problem should be able to invoke debugging from Running Extensions without restarting a dynamically inspectable local extension host. The debugger should attach from a separate VS Code window, preserving the target process and its live state. Acceptance includes a fresh session with no inspection launch argument and no prior profiling, plus the already-enabled-inspector case. Hosts where inspection cannot be enabled must retain an explicit failure or fallback rather than pretending attachment succeeded.
- **Trace:**

  > DebugExtensionHostInNewWindowAction in src/vs/workbench/contrib/extensions/electron-browser/debugExtensionHostAction.ts uses getExtensionHostPort, which queries local inspector ports with tryEnableInspector=false and offers a relaunch when the result is empty. AbstractExtensionService.getInspectPorts forwards that flag to ExtensionHostManager.getInspectPort; the true path invokes the existing LocalProcessExtensionHost.enableInspectPort mechanism. Profiling and the Dev Tools debug command already take that activation path, explaining the profiling-first workaround recorded in https://github.com/microsoft/vscode/issues/85422. Separate-window attachment already exists through Storage and DebugExtensionsContribution and must remain intact. The shared helper also serves DebugExtensionHostAndRendererAction, so planning must account for that consumer without expanding into remote or web-worker debugging. Source inspection establishes the remaining capability gap; cross-platform runtime activation and attachment were not executed in this read-only review.
