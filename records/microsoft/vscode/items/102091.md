# Issue #102091 — Better API to associate a notebook cell document with its notebook

[https://github.com/microsoft/vscode/issues/102091](https://github.com/microsoft/vscode/issues/102091)

## Summary

The convenience API remains missing: extensions can discover the containing notebook by enumerating notebooks and cells, but there is no direct text-document-to-cell lookup. Keep this open for the notebook API owners; removing the old proposal did not implement the replacement discussed here.

## Change summary

Provide a convenient API to resolve a notebook cell and its containing notebook from a TextDocument.

## Best solution

Have the notebook API owners resolve whether to expose the sketched notebooks.getNotebookCell lookup or explicitly retain enumeration as the supported contract. If adopted, define lookup behavior around cell removal and notebook closure without introducing a container property on TextDocument.

Preserve existing notebook identity and lifecycle tests.
- **Behavior:**

  > Extensions starting with a TextDocument need a convenient way to determine whether it represents a notebook cell and obtain that cell's containing notebook. The thread prefers a cell-returning lookup rather than a container property on TextDocument. Existing enumeration achieves the association but does not provide the requested convenience API. If a helper is approved, acceptance must cover correct association across multiple notebooks, unrelated text documents, and the agreed removal and closure behavior.
- **Trace:**

  > The stable declarations in src/vscode-dts/vscode.d.ts expose workspace.notebookDocuments, NotebookDocument.getCells, and the NotebookCell.document/notebook relationship, but no notebooks.getNotebookCell. ExtHostCell.apiCell in src/vs/workbench/api/common/extHostNotebookDocument.ts preserves the document object used by the enumeration workaround. languages.match in src/vs/workbench/api/common/extHost.api.impl.ts already finds a containing notebook by comparing cell.document identity. https://github.com/microsoft/vscode/issues/102091#issuecomment-865050645 explains why a TextDocument container property was disfavored, and https://github.com/microsoft/vscode/issues/147414 documents removal of that proposal and the supported workaround. The remaining uncertainty is the public API decision, not whether notebook-cell associations exist internally. Preserve TextDocument ownership and notebook lifecycle semantics; unrelated notebook features are outside this request.
- **Open decisions:**
  - Should VS Code expose the proposed notebooks.getNotebookCell convenience API, or retain notebook/cell enumeration as the supported public contract?
  - If the helper is adopted, should documents whose cells have been removed or whose notebooks have closed always return undefined?
