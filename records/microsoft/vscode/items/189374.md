# Issue #189374 — Git - Add audio cues for sync changes operation

[https://github.com/microsoft/vscode/issues/189374](https://github.com/microsoft/vscode/issues/189374)

## Summary

Keep open: current Git Sync still lacks outcome-specific audio feedback, and maintainers have already supported exploring it. The existing task signals do not cover Git synchronization; the remaining decision is the sound design.

## Change summary

Provide accessible audio feedback when a user-initiated Git Sync operation succeeds or fails.

## Best solution

Provide configurable, distinguishable success and failure signals for user-initiated Git synchronization across the command, SCM action, and status-bar entry points. Settle the sound choices with accessibility maintainers while preserving existing Git error notifications and avoiding misleading feedback for cancellation.

## Plan brief

- **Likely files:** `extensions/git/src/commands.ts`, `extensions/git/src/repository.ts`, `src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts`, `src/vs/workbench/contrib/accessibility/browser/accessibilityConfiguration.ts`, `src/vs/workbench/contrib/accessibilitySignals/browser/commands.ts`
- **Validation:** With signal sound enabled, use a disposable repository and remote to exercise successful Sync and a controlled pull or push failure through Git: Sync, the SCM Sync Changes action, and the status-bar action. Verify one approved outcome signal per operation, no success signal before push finishes, no completion signal after dismissing confirmation or cancelling, silence when disabled, and preservation of existing error notifications.
- **Behavior:**

  > Screen-reader users should learn whether an explicitly initiated Git Sync succeeded or failed without navigating to the status bar. Feedback should distinguish success from failure and respect accessibility-signal preferences. The command-palette, SCM action, and status-bar entry points should behave consistently. Acceptance checks should cover successful pull/push completion, a controlled failure, cancellation, and disabled audio.
- **Trace:**

  > Commands._sync in extensions/git/src/commands.ts handles confirmation and delegates to Repository.sync; git.sync and git.syncRebase additionally suppress cancellation errors. Repository._sync in extensions/git/src/repository.ts wraps pull and conditional push in Operation.Sync, including a read-only-remote path and optional cancellable progress. No outcome signal is invoked on this path; existing command error handling already produces notifications and must remain intact. Task outcome signals and their settings exist in accessibilitySignalService.ts and accessibilityConfiguration.ts, but are not connected to Git Sync. The discussion at https://github.com/microsoft/vscode/issues/189374 establishes explicit user initiation, variable duration, and interest in sound design distinct from saving. The unresolved boundary is the audible outcome design and how the built-in Git extension reaches the workbench signal service; the inspected signal commands provide help/configuration rather than an established Git playback bridge.
- **Open decisions:**
  - Which sounds should identify Git Sync success and failure: distinct sync sounds or approved reuse of task sounds, while keeping the save sound distinct as requested in the discussion?
