# Issue #323266 — AI Chat: Add on/off toggles in the Customizations view to enable/disable each MCP server, tool, agent, skill, instruction, and plugin

[https://github.com/microsoft/vscode/issues/323266](https://github.com/microsoft/vscode/issues/323266)

## Summary

The request is partially covered by existing MCP, plugin, and configurable-tool switches, but uniform controls for all customization sources, category-wide toggles, and workspace-scoped persistence remain unfulfilled. Keep it open: the verified related issues cover narrower requirements, not this request's full scope.

## Change summary

Provide persistent, non-destructive per-item and category-wide enablement controls for MCP servers, tools, agents, skills, instructions, and plugins in Customizations.

## Best solution

Extend the existing Customizations experience with consistent enablement semantics enforced by each owning harness, while preserving configuration files and managed-policy restrictions. Establish workspace/profile precedence and the effect on active conversations before implementing the remaining categories.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagement.contribution.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationListWidget.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagementEditor.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/toolsListWidget.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/pluginListWidget.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts`, `src/vs/workbench/contrib/chat/common/customizationHarnessService.ts`
- **Validation:** After agreeing the supported scope, exercise one enabled item from each category and source in Customizations: disable it, send a new prompt, and verify it is absent from newly assembled context and unavailable for invocation without restarting. Re-enable it, reload the workspace, switch workspaces, and verify persistence and precedence; exercise category controls and confirm underlying files remain unchanged and policy-managed items cannot be overridden. Runtime-owned categories require corresponding provider-level checks, not only UI assertions.
- **Behavior:**

  > Users want to deactivate individual contributed AI capabilities without uninstalling extensions or deleting customization files. Existing switches cover some categories, but the requested end state is consistent per-item and category-wide controls across MCP servers, tools, agents, skills, instructions, and plugins. Acceptance must check actual context and invocation eligibility, reversibility without restart, and persistence at the agreed workspace and profile scopes. The effect on already-running turns and previously assembled conversation context must be defined explicitly.
- **Trace:**

  > McpListWidget.renderMcpListActions and PluginListWidget.renderInstalledListActions already render switches backed by their owning enablement models. ToolsSetRowRenderer and ToolsToolRowRenderer support configurable tool sets and members, but ToolsListWidget marks the copilot-cli tool set read-only. aiCustomizationManagement.contribution.ts exposes prompt-file enable/disable actions only for built-in skills, while PromptsService.setDisabledPromptFiles stores profile-level state and refreshes agent and skill caches. The shared harness contract is documented in src/vs/sessions/AI_CUSTOMIZATIONS.md; runtime discovery and enforcement cannot be inferred from a rendered disabled row. Preserve existing policy restrictions, configuration files, and unrelated customization discovery behavior. Related demand is recorded in https://github.com/microsoft/vscode/issues/290290 and https://github.com/microsoft/vscode/issues/309761; neither absorbs this broader request. The trace establishes partial UI coverage, but does not establish an end-to-end enablement contract for every harness and category.
- **Open decisions:**
  - Does the initial scope include runtime-owned built-in tools and independently disabling plugin-owned children, or should unsupported entries remain explicitly non-configurable?
  - How do workspace overrides interact with profile/global enablement, and does a category master switch preserve individual selections for later restoration?
  - Does disabling apply to subsequent turns only, or must it also affect an in-flight turn and context already assembled in an existing conversation?
