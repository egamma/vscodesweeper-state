# Issue #210627 — [A11y] Focus changes to custom editor when clicking on notebook toolbar overflow menu

[https://github.com/microsoft/vscode/issues/210627](https://github.com/microsoft/vscode/issues/210627)

## Summary

Still open on main: webview-based custom editors can steal focus when toolbar overflow menus are clicked in adjacent editors. No fix commit references this issue, and the underlying focus-claim mechanism in the webview element is unchanged.

## Change summary

Clicking a notebook toolbar overflow menu causes focus to jump to a webview-based custom editor in a side-by-side layout.

## Best solution

The webview focus handling in `src/vs/workbench/contrib/webview/browser/webviewElement.ts` fires `onDidFocus` whenever its iframe's `contentWindow` regains focus — including spurious re-focus events triggered by toolbar overlay interactions. The fix likely belongs in `webviewElement.ts` (the `handleFocusChange` / `_doFocus` path) or in the editor group's reaction to `onDidFocus`, adding a guard that suppresses focus claims when a menu overlay is active. The `help wanted` label is appropriate — this is a good community contribution target.

- **Fix prompt:**

  > When a webview-based custom editor is open side-by-side with a notebook (or any editor), clicking the notebook's toolbar overflow menu causes focus to jump to the custom editor. The root cause is in src/vs/workbench/contrib/webview/browser/webviewElement.ts: the iframe's contentWindow receives a spurious focus event when toolbar overlays interact with the DOM, and handleFocusChange (line 707) unconditionally fires _onDidFocus, which propagates through the overlay webview (src/vs/workbench/contrib/webview/browser/overlayWebview.ts line 236) and the webview editor pane (src/vs/workbench/contrib/webviewPanel/browser/webviewEditor.ts line 206) up to the editor group, causing a group focus switch. The _doFocus debouncer (line 965) already has a guard checking document.activeElement, but handleFocusChange from the iframe message handler path does not. The fix should add a guard in handleFocusChange or the iframe focus listener to suppress focus claims when a menu or overlay is the active element, or when the focus event is spurious (e.g. the webview iframe is not the intended focus target). Do NOT restructure the focus pipeline broadly — add a targeted guard. Validate with a test asserting that opening a context menu or overflow toolbar in an adjacent editor does not trigger the webview's onDidFocus event.
