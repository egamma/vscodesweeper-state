# Issue #317108 — vscode_listCodeUsages reports incomplete results to Copilot without a mechanism to warn it the results are incomplete

[https://github.com/microsoft/vscode/issues/317108](https://github.com/microsoft/vscode/issues/317108)

## Summary

The gap remains on current main: reference providers can return only locations, so the usages tool cannot distinguish complete results from a partial index. The older related proposal was closed after adding language-status UI, but that status does not carry completeness through the reference request to Copilot.

## Change summary

Allow a reference provider to mark results incomplete so the Copilot usages tool can warn the model or apply an appropriate retry or fallback policy.

## Best solution

Define how reference-result completeness crosses the extension-host boundary, then have the usages tool preserve partial results while clearly signaling their limitations to the model. The design should also settle whether retrying or supplementing those results is appropriate without degrading interactive Find All References.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`, `src/vs/workbench/contrib/chat/browser/tools/usagesTool.ts`
- **Validation:** Add extension-host API tests proving completeness metadata survives provider-to-main-thread transport, plus a usages-tool test proving incomplete results remain available but carry a model-visible warning while complete results retain their current output.
- **Behavior:**

  > When a language provider knows its reference results are incomplete, that state must reach the consumer together with the locations. The Copilot usages tool must not present those locations as an exhaustive result; it should expose the partial-result state and follow the agreed retry or fallback policy. Complete providers and the interactive Find All References experience must retain their current behavior. Acceptance includes transport and usages-tool tests for both complete and incomplete results.
- **Trace:**

  > ReferenceProvider in src/vscode-dts/vscode.d.ts and src/vs/editor/common/languages.ts returns only Location[], and the adapter/protocol path in extHostLanguageFeatures.ts, extHost.protocol.ts, and mainThreadLanguageFeatures.ts preserves only that array. getReferencesAtPosition in src/vs/editor/contrib/gotoSymbol/browser/goToSymbol.ts flattens provider arrays, after which UsagesTool in src/vs/workbench/contrib/chat/browser/tools/usagesTool.ts reports the filtered count as exhaustive. The existing language-status approach discussed in https://github.com/microsoft/vscode/issues/100890 is separate from an individual reference result and cannot currently inform the tool invocation. The boundary is reference completeness and its consumers; do not make Copilot infer C/C++ parsing state or special-case the C/C++ extension.
- **Open decisions:**
  - Should incompleteness be part of each ReferenceProvider result, and when multiple providers contribute, what aggregate state should consumers observe?
  - When the usages tool receives partial references, should it return them with a warning, retry after readiness changes, or supplement them with text search?
  - Should the new contract support all reference consumers, or is the intended public surface limited to agent/tool consumers while interactive Find All References continues unchanged?

## Evidence

- **reference API gap:** src/vscode-dts/vscode.d.ts and src/vs/editor/common/languages.ts define ReferenceProvider.provideReferences as ProviderResult<Location[]>; unlike CompletionList, the result has no incompleteness metadata.
- **tool path:** src/vs/workbench/contrib/chat/browser/tools/usagesTool.ts calls getReferencesAtPosition and reports the returned count as usages without any channel for completeness or provider status.
- **extension-host boundary:** src/vs/workbench/api/common/extHostLanguageFeatures.ts, src/vs/workbench/api/common/extHost.protocol.ts, and src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts transport only arrays of locations, confirming that an extension cannot currently attach this state.
- **related precedent:** https://github.com/microsoft/vscode/issues/100890 requested incomplete-result signaling across language providers but was closed after the language status API landed. Its closing comment explicitly left location-specific incomplete-result indication for case-by-case follow-up, and language status does not solve this report's model-facing result contract.
