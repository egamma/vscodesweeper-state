# Issue #167015 — Disabling Proxy support does not disable proxy agent redirection

[https://github.com/microsoft/vscode/issues/167015](https://github.com/microsoft/vscode/issues/167015)

## Summary

A real gap remains: current core Node requests still consume HTTP_PROXY/HTTPS_PROXY regardless of `http.proxySupport`, while that setting is explicitly documented as extension-only. This team-authored issue cannot receive a judgment close, and no older issue with the same observable symptom owns the requested core opt-out.

## Change summary

Provide a supported way to prevent VS Code core requests from using proxy environment variables when proxying is intentionally disabled.

## Best solution

Define a clear public contract for disabling proxy use in core network requests, then make the Node request service honor that contract without changing extension-host proxy behavior unintentionally.

## Plan brief

- **Likely files:** `src/vs/platform/request/common/request.ts`, `src/vs/platform/request/node/requestService.ts`, `src/vs/platform/request/node/proxy.ts`, `src/vs/platform/request/test/node/requestService.test.ts`
- **Validation:** Add request-service coverage for the selected opt-out contract, with HTTP_PROXY set to an invalid proxy, and run `scripts/test.sh --grep "Request Service"`; opted-out core requests must avoid a proxy agent while enabled/default behavior remains unchanged.
- **Behavior:**

  > Users need a supported configuration that prevents VS Code core HTTP requests from inheriting HTTP_PROXY and HTTPS_PROXY when proxying is intentionally disabled. With that configuration active, authentication and other core requests must connect directly rather than fail through an invalid environment proxy. Existing proxy-enabled behavior and extension-host proxy modes must remain intact. Acceptance requires automated coverage for both opted-out and default proxy behavior.
- **Trace:**

  > On current main, `RequestService.request` in src/vs/platform/request/node/requestService.ts merges process and shell environments and always passes them to `getProxyAgent`. `getProxyAgent` in src/vs/platform/request/node/proxy.ts unconditionally selects HTTP_PROXY/http_proxy or HTTPS_PROXY/https_proxy when no configured proxy URL exists. In contrast, `http.proxySupport` is registered in src/vs/platform/request/common/request.ts as extension-only and is consumed by the extension-host resolver in src/vs/workbench/api/node/proxyResolver.ts. This confirms the missing core opt-out, but not whether the existing extension setting should change meaning or a separate contract should be introduced. Preserve extension-host `off`/`on`/`fallback`/`override` semantics unless the maintainer explicitly chooses to broaden that setting.
- **Open decisions:**
  - Should `http.proxySupport: off` become a global proxy opt-out for both core and extensions, or should core requests receive a separate setting or startup option?
  - Should the core opt-out cover every VS Code-owned network stack or only the Node `IRequestService` path reported here?

## Evidence

- **current source:** src/vs/platform/request/node/requestService.ts resolves the shell environment for every request and calls `getProxyAgent` with it without consulting `http.proxySupport`.
- **proxy resolution:** src/vs/platform/request/node/proxy.ts selects HTTP_PROXY/http_proxy or HTTPS_PROXY/https_proxy whenever no explicit `http.proxy` value is configured; it has no core opt-out input.
