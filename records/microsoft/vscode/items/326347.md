# Issue #326347 — Portable VS Code modifies or replaces Windows shortcuts

[https://github.com/microsoft/vscode/issues/326347](https://github.com/microsoft/vscode/issues/326347)

## Summary

Traced to a real, unconditional code path: VS Code always sets the same Windows AppUserModelID for portable and installed builds, which is what causes Windows Explorer to re-associate the pinned Start/taskbar tile with whichever copy last ran — this is Windows shell behavior reacting to a shared AUMID, not VS Code directly rewriting the .lnk file, but the root cause is squarely in VS Code's startup code and worth a portable-mode guard.

## Change summary

Launching the portable Windows build re-points the existing installed VS Code's Start menu/taskbar shortcut at the portable copy instead of staying self-contained.

## Best solution

In src/vs/code/electron-main/app.ts, guard the `app.setAppUserModelId(win32AppUserModelId)` call (around line 684-687) with a check against `environmentMainService.isPortable` so portable launches don't advertise the same AppUserModelID as a regular install; this keeps the documented taskbar-grouping benefit for normal installs while stopping Windows from re-associating the installed copy's pinned shortcut with the portable exe.

## Evidence

- **root cause in source:** src/vs/code/electron-main/app.ts:684-687 calls `app.setAppUserModelId(win32AppUserModelId)` unconditionally on Windows whenever product.json defines `win32AppUserModelId`, with no portable-mode check; the adjacent comment states this is deliberately done 'to help Windows associate the running program with any shortcut that is pinned to the taskbar and prevent showing two icons in the taskbar for the same app.'
- **portable detection exists:** src/vs/platform/environment/electron-main/environmentMainService.ts:61 already exposes `isPortable` (`!!process.env['VSCODE_PORTABLE']`), which app.ts does not consult before setting the AUMID.
- **mechanism:** The report describes Windows overwriting the Start menu tile, which matches Windows' own AppUserModelID-based pinned-shortcut reassociation rather than VS Code writing to the .lnk file directly — same underlying identity collision either way.
- **second reporter:** asv7c2's 2026-08-15 comment corroborates the same symptom with a portable-only + no-install setup, ruling out simple instance-reuse as maintainer dmitrivMS suggested in the first comment.
