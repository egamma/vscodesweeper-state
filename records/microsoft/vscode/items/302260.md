# Issue #302260 — Browser: Favicon contrast

[https://github.com/microsoft/vscode/issues/302260](https://github.com/microsoft/vscode/issues/302260)

## Summary

Keep open as the accepted favicon-contrast improvement. The existing global theme setting offers a workaround, but does not provide browser-tab contrast independently of native UI; this team-authored Backlog item has no verified fix or duplicate.

## Change summary

Make integrated-browser favicons readable when the VS Code color theme differs from the system theme.

## Best solution

Agree on a browser favicon contrast policy that respects independently themed VS Code windows without unexpectedly changing page appearance or application-wide native UI. Preserve the existing global theme setting as a workaround rather than treating it as full coverage.

## Plan brief

- **Likely files:** `src/vs/platform/browserView/electron-main/browserView.ts`, `src/vs/platform/browserView/electron-main/browserViewEmulator.ts`, `src/vs/workbench/contrib/browserView/common/browserEditorInput.ts`, `src/vs/platform/theme/electron-main/themeMainServiceImpl.ts`
- **Validation:** Use a test page with distinct light/dark media-qualified favicons. Compare light-system/dark-workbench and dark-system/light-workbench combinations, switch workbench themes, and open differently themed windows simultaneously. Verify the chosen contrast policy, including its agreed effects on page appearance, while preserving window.systemColorTheme behavior and device emulation.
- **Behavior:**

  > A site's favicon can become difficult to distinguish in an integrated-browser editor tab when the workbench and system color schemes differ. The desired outcome is a readable icon under the supported theme combinations. Acceptance should cover theme changes and differently themed windows, and explicitly establish whether adapting the favicon may also alter the page's color scheme or native UI.
- **Trace:**

  > BrowserView's page-favicon-updated handler in src/vs/platform/browserView/electron-main/browserView.ts forwards Electron-selected images; BrowserEditorInput.getIcon() in src/vs/workbench/contrib/browserView/common/browserEditorInput.ts exposes the image directly. ThemeMainService in src/vs/platform/theme/electron-main/themeMainServiceImpl.ts controls application-wide electron.nativeTheme.themeSource through window.systemColorTheme, which the maintainer already identified as a workaround. BrowserViewEmulator currently emulates pointer characteristics but not prefers-color-scheme. Source inspection establishes the current boundary, not a runtime reproduction or a proven rendering fix. The unresolved question is the user-visible scope of adaptation; preserve existing native-theme controls and device-emulation behavior. The originating observation is https://github.com/microsoft/vscode/issues/300866#issuecomment-4070026277.
- **Open decisions:**
  - Should contrast adaptation affect only the favicon displayed by VS Code, or may it also change the embedded page's preferred color scheme to match the owning workbench window?

## Evidence

- **Accepted scope and workaround:** In https://github.com/microsoft/vscode/issues/302260, kycutler explains that Electron selects the site's icon using its native theme, recommends the existing auto setting, and explicitly classifies the remaining work as a feature request for the Backlog. The MEMBER author and accepted Backlog status preclude a judgment close.
- **Existing capability and limitations:** src/vs/workbench/services/themes/electron-browser/themes.contribution.ts registers window.systemColorTheme with default, auto, light, and dark values at application scope. src/vs/platform/theme/electron-main/themeMainServiceImpl.ts updates electron.nativeTheme.themeSource globally; auto follows the stored/preferred base theme, while Linux or enabled window.autoDetectColorScheme forces system behavior. This is not an independent per-browser or per-window favicon policy.
- **Current favicon path:** src/vs/platform/browserView/electron-main/browserView.ts handles page-favicon-updated by fetching the supplied URLs and forwarding the first successful image as a data URI. Neither inspected path adapts the image to the surrounding workbench theme.

That existing device-emulation path does not establish a shipped solution to this request.
