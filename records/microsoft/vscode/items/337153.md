# Issue #337153 — Agent Host: existing long-running Copilot session hangs loading history after successful SDK resume

[https://github.com/microsoft/vscode/issues/337153](https://github.com/microsoft/vscode/issues/337153)

## Summary

Fresh, carefully diagnosed report with a confirmed code-level root cause on current main: `_computeMappedEvents()` awaits `this._wrapper.session.getEvents()` with no timeout or cancellation, so a non-settling SDK history read leaves the chat stuck in a loading state forever with no recoverable error. Real gap remains; keep open and route to the agent-host area.

## Change summary

An existing long-running Copilot session hangs indefinitely loading history after a successful SDK session resume, because the persisted-event read has no timeout.

## Best solution

Add bounded timeout/cancellation handling around the `getEvents()` await in `CopilotAgentSession._computeMappedEvents()` so a non-settling history request surfaces as an actionable, recoverable error instead of an infinite loading spinner; the deeper 'why does the SDK read stall for this session' question is a separate follow-up requiring reproduction with the actual persisted history.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`
- **Validation:** A test simulating a `session.getEvents()` call that never resolves should cause `_computeMappedEvents()` (and thus session restoration) to reject with an actionable, recoverable error within the chosen bound, rather than hanging indefinitely.
- **Behavior:**

  > When restoring an existing session, if the SDK's persisted-history read (`getEvents()`) does not settle within a reasonable bound, the session load should fail with an actionable, recoverable error instead of leaving the chat UI in an indefinite loading state. Sessions whose history read completes normally must be unaffected. Acceptance: a simulated non-settling `getEvents()` call causes restoration to reject/timeout rather than hang forever.
- **Trace:**

  > `_computeMappedEvents()` in src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts (around line 3521) awaits `this._wrapper.session.getEvents()` unconditionally; there is no timeout, cancellation token, or fallback path if this promise never settles, so `_getMappedEvents()`'s memoized promise (and callers like `getMessages()`) hang indefinitely. Two independent diagnostic captures (details in the issue, not attached) confirm the SDK's `resumeSession` succeeds and only the subsequent history read stalls. Boundary: do not change the resume/sandbox-attach flow before this point, or the turn-reconstruction logic (`mapSessionEvents`) after a successful read — only the missing bound around the `getEvents()` await. The underlying reason the SDK read itself stalls for this specific session (size, a bad event, transport) is unconfirmed and out of scope for this fix; see the issue's own 'Suggested investigation' section.
- **Open decisions:**
  - What timeout/bound should apply to the history read before treating it as failed, and should it be configurable?
  - Should a timed-out history read be retryable in place, or does the user need to fully re-open/re-create the session view?
