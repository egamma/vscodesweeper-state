# Issue #234683 — keybinding's 'when' clause for 'view focused' and workbench's 'focus action' items for views are missing for some side bar views

[https://github.com/microsoft/vscode/issues/234683](https://github.com/microsoft/vscode/issues/234683)

## Summary

Keep open: the merged partial fix added several requested focus context keys, but current main still lacks acknowledged focus commands and retains state-changing or incorrectly named focus behavior. The existing Backlog, help-wanted, accessibility, and context-keys classifications appropriately capture the remaining work.

## Change summary

Provide consistent context keys and commands for keyboard users to focus sidebar views, their search inputs, result lists, and relevant header controls without unexpectedly changing view state.

## Best solution

Establish a consistent keyboard-focus contract for Search and Extensions: expose correctly named scoped context keys and commands for inputs and result lists, preserve active queries when merely moving focus, and decide separately whether view-header controls need a reusable workbench-level navigation mechanism.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsViewlet.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsViews.ts`, `src/vs/workbench/contrib/extensions/common/extensions.ts`, `src/vs/workbench/contrib/search/browser/searchActionsNav.ts`, `src/vs/workbench/contrib/search/browser/searchView.ts`, `src/vs/workbench/contrib/search/common/constants.ts`
- **Validation:** Add browser tests that execute the Search and Extensions focus commands with non-empty queries and verify the active element, preserved query text, and scoped context-key values for the input and result list; run them through scripts/test.sh with a focused grep for the new focus-command suite.
- **Behavior:**

  > Keyboard users can invoke distinct commands to focus the Search or Extensions input and result list. Moving focus does not clear an existing query, alter results, or otherwise reset the view. The documented focus context keys are true exactly while their corresponding view region has focus, and keyboard navigation remains usable when focus is on view-header actions. Existing commands retain compatible behavior unless the maintainer explicitly chooses to revise their public semantics.
- **Trace:**

  > Commit 0e262dcf8c51bfe505c7e6671b58a7e45c3452fa from https://github.com/microsoft/vscode/pull/234899 added the originally listed tree-focused context keys, so that portion is present on main. Extensions still has no registered `workbench.extensions.action.focusExtensionsList`; `ExtensionsViewlet.focusListView()` exists in src/vs/workbench/contrib/extensions/browser/extensionsViewlet.ts but is private and currently reached from input navigation rather than a public command. The existing `workbench.extensions.action.focusExtensionsView` calls `openSearch('')` in extensions.contribution.ts, which resets the query, while `ExtensionResultsListFocused` in extensions.ts contains a trailing space in its public key string. Search already exposes `search.action.focusSearchList` through searchActionsNav.ts, while its view-wide and input-specific context keys are scoped in searchView.ts and searchWidget.ts. Keep this work within focus commands and context contracts; do not rename established command IDs wholesale or change search execution semantics as part of the cleanup. The uncertainty begins with compatibility semantics for the existing Extensions focus command and whether heading-toolbar navigation is a generic ViewPane contract or separate follow-up work.
- **Open decisions:**
  - Should `workbench.extensions.action.focusExtensionsView` change to preserve the active query, or should its reset behavior remain compatible while a distinct input-focus command is introduced?
  - Should the issue's requested keyboard access to view-heading tabs and buttons become a reusable contract for all sidebar views, or remain scoped to explicit commands for Search and Extensions?

## Evidence

- **partial implementation:** Merged https://github.com/microsoft/vscode/pull/234899 in commit 0e262dcf8c51bfe505c7e6671b58a7e45c3452fa added `callStackFocused`, `outlineFocused`, `timelineFocused`, `searchResultListFocused`, and an Extensions result-list context key, but did not implement the full command and navigation request.
- **maintainer assessment:** https://github.com/microsoft/vscode/issues/234683#issuecomment-2507935850 confirms `search.action.focusSearchList` already exists while `workbench.extensions.action.focusExtensionsList` is still missing.
- **remaining Extensions behavior:** On current main, `workbench.extensions.action.focusExtensionsView` in src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts calls `IExtensionsWorkbenchService.openSearch('')`, explaining why invoking it clears the active query instead of only moving focus.
- **remaining context-key defect:** src/vs/workbench/contrib/extensions/common/extensions.ts currently declares `ExtensionResultsListFocused` with the literal key `extensionResultListFocused `, including a trailing space, so the reporter's expected `extensionResultListFocused` condition is not exposed under that name.
- **existing Search capability:** src/vs/workbench/contrib/search/browser/searchActionsNav.ts registers `search.action.focusSearchList` and routes it through `SearchView.moveFocusToResults()`, covering only the result-list portion of the Search request.
- **canonical search:** https://github.com/microsoft/vscode/issues/130880 concerns passing selected tree items to extension commands invoked by keybindings, not commands and context keys for moving focus among built-in sidebar controls; it does not report the same observable symptom and is not a duplicate canonical.
