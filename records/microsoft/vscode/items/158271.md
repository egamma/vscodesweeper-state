# Issue #158271 — Make `IMarkerService#read` ignore unsupported schemes by default

[https://github.com/microsoft/vscode/issues/158271](https://github.com/microsoft/vscode/issues/158271)

## Summary

Keep open: current MarkerService.read still returns markers from unsupported schemes, while statistics and the Problems model filter them separately. The linked merged PR explicitly deferred this service-level cleanup to this issue rather than completing it.

## Change summary

Make marker reads exclude unsupported URI schemes by default while retaining an explicit way to retrieve their diagnostics.

## Best solution

Establish a consistent default filtering contract in IMarkerService.read, preserving access for editor decorations, diagnostic forwarding, and cleanup consumers. Settle whether requesting a specific resource itself opts into unsupported schemes before migrating callers.

- **Behavior:**

Supported-scheme results, severity selection, and result limits must remain consistent. Editor squiggles, extension diagnostic forwarding, and marker cleanup must not regress. Acceptance must cover the agreed behavior of resource-specific queries as well as aggregate reads.
- **Trace:**

  > MarkerService.changeOne and changeAll retain unsupported-scheme markers, and both branches of MarkerService.read in src/vs/platform/markers/common/markerService.ts currently return them; _accept checks only severity. IMarkerReadOptions in src/vs/platform/markers/common/markers.ts has no scheme-inclusion contract, and ignoreResourceFilters controls a separate resource-pausing mechanism. Statistics and MarkersModel independently filter unsupportedSchemas. https://github.com/microsoft/vscode/pull/159180 removed write-time suppression to address a regression and explicitly deferred further cleanup here. MarkerDecorationsService depends on resource-specific reads for decorations and transient-model cleanup; MainThreadDiagnostics depends on reads for forwarding and owner cleanup. Preserve those capabilities rather than restoring write-time rejection. The unresolved boundary is whether a resource-specific read counts as an explicit request for unsupported diagnostics or requires a separate inclusion option.
- **Open decisions:**
