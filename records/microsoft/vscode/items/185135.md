# Issue #185135 — "self signed certificate in certificate chain" while attempting to install an extension via command line

[https://github.com/microsoft/vscode/issues/185135](https://github.com/microsoft/vscode/issues/185135)

## Summary

The CLI still uses the Node request path without Windows system-proxy discovery, while the UI uses Electron networking. A maintainer explicitly kept this issue as the tracker for automatically picking up the relevant proxy and certificate configuration, and no older open issue reports the same local-CLI symptom closely enough to meet the re-review duplicate bar.

## Change summary

Make command-line extension installation work with OS-configured corporate proxies and trusted corporate certificates as reliably as installation from the UI.

## Best solution

Define and implement a secure networking contract for standalone CLI extension installation that discovers applicable OS proxy configuration and trusts configured/system corporate CAs without requiring TLS verification to be disabled.

## Plan brief

- **Likely files:** `src/vs/code/node/cliProcessMain.ts`, `src/vs/platform/request/node/requestService.ts`, `src/vs/platform/request/node/proxy.ts`, `src/vs/platform/request/test/node/requestService.test.ts`
- **Validation:** Add targeted request-service coverage for selecting an OS-provided proxy when proxy environment variables are absent and for completing an HTTPS request through that proxy with a trusted test CA; then verify `code --install-extension` succeeds in the same setup without disabling strict SSL.
- **Behavior:**

  > Installing an extension with `code --install-extension publisher.name` should succeed when the machine's OS proxy configuration and trusted corporate CA are sufficient for installation from the VS Code UI. The CLI must continue enforcing certificate validation and must not require users to disable strict SSL. Explicit VS Code proxy settings and proxy environment variables must retain predictable precedence. Acceptance includes a successful CLI installation through a test proxy using a private trusted CA.
- **Trace:**

  > The standalone CLI registers RequestService in src/vs/code/node/cliProcessMain.ts and invokes ExtensionManagementCLI for --install-extension. RequestService.request() in src/vs/platform/request/node/requestService.ts merges process and shell environments, then src/vs/platform/request/node/proxy.ts selects only an explicit http.proxy setting or HTTP_PROXY/HTTPS_PROXY; it returns null for OS-only proxy configuration. RequestService.loadCertificates() can load system certificates, but that method is consumed by other networking surfaces and is not applied by the CLI request path itself. The UI's Electron networking behavior must remain unchanged, and the scope must not weaken TLS verification or broadly alter extension-host proxy patching. Related reports https://github.com/microsoft/vscode/issues/144625, https://github.com/microsoft/vscode/issues/131836, and https://github.com/microsoft/vscode/issues/34385 do not replace this local-CLI tracker.
- **Open decisions:**
  - Should the standalone CLI promise full parity with the UI's OS proxy behavior, including PAC and authenticated system proxies, or a narrower documented subset alongside explicit settings and environment variables?

## Evidence

- **current CLI path:** src/vs/code/node/cliProcessMain.ts registers the Node RequestService for the standalone CLI and routes --install-extension through ExtensionManagementCLI.
- **source gap:** src/vs/platform/request/node/requestService.ts merges process and resolved-shell environments before calling getProxyAgent; src/vs/platform/request/node/proxy.ts only recognizes http.proxy or HTTP_PROXY/HTTPS_PROXY variables and returns null when those are absent, so Windows system proxy settings are not discovered.
- **certificate support is not wired into CLI requests:** Commit 470d7704a61884dc12a9552733d21c57f551150f added Node system-certificate loading through RequestService.loadCertificates(), but RequestService.request() does not apply those certificates to its https.request path, so this commit does not establish that CLI extension downloads are fixed.
