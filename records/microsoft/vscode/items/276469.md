# Issue #276469 — Add API to detect the source of onDidOpenTextDocument

[https://github.com/microsoft/vscode/issues/276469](https://github.com/microsoft/vscode/issues/276469)

## Summary

Keep this accepted API request open: current document and editor events do not expose opening provenance. It has 30 upvotes and a concrete Peek Definition use case; no verified canonical issue or implementation was found.

## Change summary

Expose metadata allowing extensions to distinguish document-opening contexts such as Explorer, navigation, Peek, Quick Open, URI links, and programmatic opens.

## Best solution

Design a backward-compatible extension API for opening provenance, including the distinction between Peek and ordinary editors. Settle whether attribution describes initial document loading or each editor-opening action, since the existing document event does not fire again for an already-loaded document.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostDocuments.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadDocumentsAndEditors.ts`
- **Validation:** After agreeing the API contract, use an extension-host listener to exercise Explorer, Go to Definition, Peek Definition, Quick Open, vscode://file links, and workspace.openTextDocument. Check attribution for initially unloaded and already-loaded documents, distinguish Peek from ordinary editors, and verify that legacy onDidOpenTextDocument payloads and lifecycle behavior remain unchanged.
- **Behavior:**

  > Extensions currently receive a document-open notification without knowing which action caused the document to load. The requested capability distinguishes Explorer, definition navigation, Peek, Quick Open, URI links, and programmatic opening. The concrete PHP use case requires identifying Peek usage without relying on extension-specific stub paths. Acceptance should exercise those entry points and already-loaded documents under the agreed contract while preserving existing document-event behavior.
- **Trace:**

  > workspace.onDidOpenTextDocument in src/vs/workbench/api/common/extHost.api.impl.ts forwards ExtHostDocuments.onDidAddDocument, which emits only the TextDocument. MainThreadDocumentAndEditorStateComputer in src/vs/workbench/api/browser/mainThreadDocumentsAndEditors.ts observes model additions independently of editor state, and _toModelAddData carries no provenance through IDocumentsAndEditorsDelta in src/vs/workbench/api/common/extHost.protocol.ts. The public declaration in src/vscode-dts/vscode.d.ts explicitly makes this a document-lifecycle event, including language changes and excluding repeated opens of an already-loaded document. Existing active/visible editor events do not identify the initiating action. Preserve those legacy contracts; uncertainty starts at whether the new capability describes initial loading, subsequent editor presentation, or both. The concrete consumer scenario is documented in https://github.com/valeryan/vscode-phpsab/issues/190 and the parent request is https://github.com/microsoft/vscode/issues/276469.
- **Open decisions:**
  - Should provenance describe only the initial document load, every editor-opening action including already-loaded documents, or both through distinct events?
  - Which opening contexts are guaranteed public categories, and how should background loads or actions without a unique attributable source be represented?
