# Issue #338925 — permission request to message another session is very opaque

[https://github.com/microsoft/vscode/issues/338925](https://github.com/microsoft/vscode/issues/338925)

## Summary

Keep open and route to the Agent Host and subagent owners. Current source confirms that `send_message` confirmations expose only generic presentation, leaving the target and originating conversation opaque as reported.

## Change summary

Make cross-session message approval clearly identify and link the source and target conversations while explaining the message being authorized.

## Best solution

Present a human-readable, navigable source and target for `send_message` approval, including subagent provenance where applicable, while retaining the message content needed to make an informed permission decision.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/shared/sessionServerTools.ts`, `src/vs/platform/agentHost/test/node/serverToolGroups.test.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/stateToProgressAdapter.ts`, `src/vs/workbench/contrib/chat/test/browser/agentSessions/stateToProgressAdapter.test.ts`
- **Validation:** Add focused server-tool display and state-to-progress adapter tests showing that a pending `send_message` approval exposes understandable source and target context and a usable target-session link; manually verify the permission card from a subagent-initiated cross-session message.
- **Behavior:**

  > A request to send a message to another session or chat must identify where the request originated, where the message will go, and what message is being authorized. The user must be able to open the relevant target, and subagent-originated requests must not appear as unrelated activity in the parent conversation. Approval choices and ordinary non-orchestration tool confirmations must remain unchanged.
- **Trace:**

  > The `send_message` definition and input schema are in src/vs/platform/agentHost/node/shared/sessionServerTools.ts. Its `getSessionToolDisplay` branch currently emits only generic display and invocation strings, while `toolCallConfirmationMessages` in src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/stateToProgressAdapter.ts derives the permission card directly from those fields. `toolCallOriginMessage` adds MCP-server attribution only, despite Agent Host already retaining chat origins and session-creation provenance. Existing `agent-host-session://` open-link handling demonstrates a navigation path, but the trace does not establish whether approvals should navigate to the exact target chat or its owning session. Keep permission semantics and the `send_message` execution contract out of scope; this is presentation and contextual navigation work.
- **Open decisions:**
  - Should the approval card identify and open the exact target chat when one is addressed, or always present the owning session as the user-visible destination?
  - For a request originating in a subagent, should the card link directly to that subagent conversation, identify its parent conversation, or show both?
  - How much of the outgoing message should be shown by default in the approval card when it is long?

## Evidence

- **generic confirmation display:** In src/vs/platform/agentHost/node/shared/sessionServerTools.ts, `getSessionToolDisplay` returns only `displayName: "Send Message"` and `invocationMessage: "Send message"` for `SessionServerToolName.SendMessage`; unlike `SetWorkspace`, it supplies no contextual `confirmationTitle` or `confirmationMessage`.
