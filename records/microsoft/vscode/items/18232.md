# Issue #18232 — Allow to cycle through previous typed values in quick input picker

[https://github.com/microsoft/vscode/issues/18232](https://github.com/microsoft/vscode/issues/18232)

## Summary

Keep this accepted quick-input history request open: current settings restore one previous query but do not allow cycling through multiple typed values. Maintainers have explicitly identified this issue as the canonical widget-level request.

## Change summary

Allow keyboard navigation through previously typed quick-input values, including Go to Line and Quick Open queries.

## Best solution

Provide reusable, context-appropriate input history for quick input without replacing result-list navigation. Agree on history ownership, retention, and keyboard behavior before implementing the shared capability.

- **Reason:** Reusable keyboard-accessible query history improves the developer inner loop and makes quick input more consistent with existing search inputs.

## Plan brief

- **Likely files:** `src/vs/platform/quickinput/browser/quickInputBox.ts`, `src/vs/platform/quickinput/browser/quickInputActions.ts`, `src/vs/platform/quickinput/browser/quickAccess.ts`, `src/vs/platform/quickinput/common/quickInput.ts`, `src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts`
- **Validation:** After agreeing on the history contract, enter and accept three distinct Go to Line values and three Quick Open queries, reopen each picker, and verify backward/forward history navigation follows the agreed order and isolation rules. Check that normal result navigation, provider prefixes, and preserveInput behavior remain intact; repeat the chosen retention checks after reopening or reloading as applicable.
- **Behavior:**

  > Users should be able to recall multiple previously typed values in quick input without retyping them, including Go to Line values and Quick Open search queries. The existing preserveInput settings only recover one value and do not satisfy cycling through history. History navigation must remain distinguishable from navigating results and must not mix unrelated input contexts. Acceptance checks should exercise multiple entries, backward and forward navigation, reopening the picker, and the agreed retention behavior.
- **Trace:**

  > QuickAccessController.doShowOrPick in src/vs/platform/quickinput/browser/quickAccess.ts can restore one last accepted value per provider; registerPickerListeners overwrites that value on acceptance. QuickInputBox in src/vs/platform/quickinput/browser/quickInputBox.ts wraps FindInput, whose underlying input-box infrastructure has history helpers, but the quick-input wrapper does not expose a shared history contract. src/vs/platform/quickinput/browser/quickInputActions.ts already assigns Windows/Linux Alt+Up to separator or item navigation, so the originally requested shortcut conflicts with existing behavior. Preserve current result navigation, quick-access provider prefixes, and the existing single-value restoration settings. Maintainers identify this issue as the shared capability needed by https://github.com/microsoft/vscode/issues/40096 and as the canonical for https://github.com/microsoft/vscode/issues/272846. The remaining uncertainty is the user-visible history contract across providers and extension-created inputs, not whether a single-value workaround exists.
- **Open decisions:**
  - Should history be isolated per quick-access provider and explicitly identified extension input, or should any contexts share their previous values?
  - Should history record only accepted values, or also values from dismissed inputs, and should entries survive a window reload?
  - Which history-navigation shortcut should be used across platforms, given that Alt+Up already navigates quick-pick results on Windows and Linux?
  - Should history apply automatically to eligible quick inputs or require each input owner to opt in?
