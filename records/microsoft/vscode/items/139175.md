# Issue #139175 — Can't delete row from setting

[https://github.com/microsoft/vscode/issues/139175](https://github.com/microsoft/vscode/issues/139175)

## Summary

The remaining request is a way to remove inherited object-setting entries without contradicting configuration merging. Current source deliberately prevents that removal for ordinary default entries; the terminal-specific example has changed, but it does not resolve the broader case confirmed after reopening.

## Change summary

Allow users to remove default object-setting rows with an effective configuration result that matches what the Settings editor displays.

## Best solution

Agree on the supported semantics for suppressing inherited object keys, then make the Settings editor accurately expose those semantics without changing existing object-merge behavior unexpectedly. Preserve the consistency restored for extension settings rather than reintroducing a visual-only deletion.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/preferences/browser/settingsTree.ts`, `src/vs/workbench/contrib/preferences/browser/settingsTreeModels.ts`, `src/vs/workbench/contrib/preferences/browser/settingsWidgets.ts`
- **Validation:** Using the extension sample linked in the discussion, compare the Settings editor, settings.json, and vscode.workspace.getConfiguration() for a default key1 with and without a user-added key2. Any supported removal must remain effective after reload and agree across all three surfaces; reset must restore the default, and unrelated object settings must retain their existing merge behavior.
- **Behavior:**

  > An object setting with a default key remains present even when a user wants an effective value without that key. The reporter expects both an empty object and an object containing only a newly added key to be expressible. Any supported removal must affect configuration consumers, not merely hide a row in the editor. Acceptance must compare the displayed rows, persisted configuration, and effective API value before and after reload, while retaining reset behavior.
- **Trace:**

  > In src/vs/workbench/contrib/preferences/browser/settingsTree.ts, getObjectDisplayValue combines default and scoped values and marks ordinary non-null default entries non-removable. ObjectSettingDropdownWidget in settingsWidgets.ts omits the removal action for those entries. settingsTreeModels.ts:objectSettingSupportsRemoveDefaultValue currently enables a narrow exception for workbench.editor.customLabels.patterns, and SettingObjectRenderer.onDidChangeObject handles that exception using null values. The original terminal setting now defaults to an empty object and separately supports null replies, so it is no longer sufficient to assess the broader request. The discussion at https://github.com/microsoft/vscode/issues/139175#issuecomment-1170082763 and the regression at https://github.com/microsoft/vscode/issues/142820 establish that visual deletion alone is incorrect. Preserve existing object merging and extension-visible defaults; uncertainty begins at the public semantics for suppressing an inherited key, not at which UI helper to change.
- **Open decisions:**
  - Should effective removal be supported only for settings whose schemas and consumers explicitly define an unset value, or should VS Code introduce a general configuration contract for suppressing inherited object keys?

## Evidence

- **Confirmed remaining scope:** The reporter's https://github.com/microsoft/vscode/issues/139175#issuecomment-1170025680 describes the inability to remove the default key1 even after adding key2. The maintainer explains in https://github.com/microsoft/vscode/issues/139175#issuecomment-1170082763 that object settings merge defaults with scoped values and that the editor does not support effectively unsetting that key.
- **Current source preserves default rows:** src/vs/workbench/contrib/preferences/browser/settingsTree.ts:getObjectDisplayValue merges elementDefaultValue with elementScopeValue. Declared properties with non-null defaults are not removable; other default entries are removable only through objectSettingSupportsRemoveDefaultValue. src/vs/workbench/contrib/preferences/browser/settingsWidgets.ts renders the removal action only when item.removable is true.
- **Existing capability is narrow:** src/vs/workbench/contrib/preferences/browser/settingsTreeModels.ts:objectSettingSupportsRemoveDefaultValue allows only workbench.editor.customLabels.patterns. SettingObjectRenderer.onDidChangeObject in settingsTree.ts writes null when removing a supported default entry. This is not general support for deleting defaults from extension-contributed object settings.
