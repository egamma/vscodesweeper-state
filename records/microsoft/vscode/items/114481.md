# Issue #114481 — API `registerCallHierarchyProvider` does not work as expected and flakily

[https://github.com/microsoft/vscode/issues/114481](https://github.com/microsoft/vscode/issues/114481)

## Summary

The flakiness came from the language-feature registry breaking score ties by registration time, so a third-party call hierarchy provider and the built-in TS provider won at random; since https://github.com/microsoft/vscode/commit/edf0b737f34d5050cc04bba08af7a1c509f87678 the registry de-prioritizes built-in extensions' providers on ties, so the user's provider now wins deterministically — proposing a completed close.

## Change summary

A third-party `registerCallHierarchyProvider` lost to the built-in TypeScript provider about half the time in js/jsx/ts/tsx files, nondeterministically.

## Best solution

Treat as fixed on main by commit edf0b737: the non-builtin provider now consistently outranks the built-in TS call hierarchy provider at equal selector score; the remaining 'only the top-scoring provider is used' behavior is intentional and separate.

  > Thanks for the detailed repro and for sticking with this. The flakiness came from the language-feature registry: when your provider and the built-in TypeScript provider scored the same for a file, the tie was broken by registration time, so whichever extension happened to register last won — hence the roughly 50/50 behavior. That tiebreak changed in https://github.com/microsoft/vscode/commit/edf0b737f34d5050cc04bba08af7a1c509f87678: providers from built-in extensions are now de-prioritized when scores are equal, so a provider from an installed (non-built-in) extension wins consistently. No `extensionDependencies` workaround is needed anymore. Closing as resolved — please open a new issue if you still see a built-in provider taking over on a current build. The fix shipped in 1.78.0.

## Evidence

- **reporter's trigger:** Extension registers a call hierarchy provider for js/jsx; the built-in TypeScript extension registers one for the same languages. jrieken confirmed the conflict (https://github.com/microsoft/vscode/issues/114481#issuecomment-762112913) and that the workaround was activation ordering so the 'last provider wins' (https://github.com/microsoft/vscode/issues/114481#issuecomment-769545127) — i.e. the tie was broken by registration time, which is why it flipped about half the time.
- **fix commit and the diff lines that change the outcome:** https://github.com/microsoft/vscode/commit/edf0b737f34d5050cc04bba08af7a1c509f87678 ('Prefer installed drop providers over builtin providers', #179336) inserted a builtin de-prioritization into LanguageFeatureRegistry._compareByScoreAndTime *before* the `a._time < b._time` comparison, added `isBuiltin` to LanguageFilter, and threaded the extension description through `_transformDocumentSelector(selector, extension)` for every provider registration — including registerCallHierarchyProvider.
- **state on current main:** src/vs/editor/common/languageFeatureRegistry.ts:210-213 de-prioritizes builtin selectors ahead of the `_time` tiebreak; src/vs/workbench/api/common/extHostTypeConverters.ts:193,205 stamps `isBuiltin: extension?.isBuiltin` on the selector; src/vs/workbench/api/common/extHostLanguageFeatures.ts:2861-2864 passes the extension for call hierarchy registration. CallHierarchyModel.create (src/vs/workbench/contrib/callHierarchy/common/callHierarchy.ts) still takes `CallHierarchyProviderRegistry.ordered(model)[0]`, which is now deterministically the non-builtin provider.
- **unchanged by design:** Only the top-ranked provider serves a call hierarchy session (no merging across providers), and a `{ language: 'javascript' }` selector still requires the language to be contributed (the reporter's comment-8 observation) — both are intended behavior, not the flakiness reported here.
