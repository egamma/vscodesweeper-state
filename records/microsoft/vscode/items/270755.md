# Issue #270755 — Handle optional arguments properly installing/starting an MCP Server

[https://github.com/microsoft/vscode/issues/270755](https://github.com/microsoft/vscode/issues/270755)

## Summary

The defect remains source-reproducible on current main: MCP gallery argument processing discards optionality and can start a server with the unresolved input placeholder. This team-authored, accepted Backlog bug must remain open.

## Change summary

When an optional MCP server argument is skipped, VS Code should omit that argument instead of passing its unresolved input placeholder to the server.

## Best solution

Preserve argument requiredness through MCP gallery installation and launch resolution so declining an optional input removes the complete argument, including its named flag, while required inputs continue to block startup until resolved.

Run the targeted MCP unit suites with scripts/test.sh using a grep for McpManagementService and McpRegistry.
- **Behavior:**

  > Installing or starting an MCP server may prompt for an optional argument. If the user dismisses or leaves that input unset, the server still starts, but the entire optional argument is omitted; no literal ${input:...} value and no orphaned named flag reaches the process. Supplying the value passes the flag and value normally, while required arguments continue to require resolution. Acceptance covers both optional named and positional arguments without changing fixed or required arguments.
- **Trace:**

  > The manifest model in src/vs/platform/mcp/common/mcpManagement.ts exposes IMcpServerInput.isRequired. AbstractCommonMcpManagementService.processArguments in src/vs/platform/mcp/common/mcpManagementService.ts does not inspect it: named argument names are appended before input resolution, and generated IMcpServerVariable values do not retain optionality because that type in src/vs/platform/mcp/common/mcpPlatformTypes.ts has no corresponding field. McpRegistry variable resolution in src/vs/workbench/contrib/mcp/common/mcpRegistry.ts calls resolveWithInteraction but does not act on its undefined cancellation result before producing the final launch, allowing ConfigurationResolverExpression's documented unresolved-placeholder behavior to surface. The boundary is gallery-derived MCP launch arguments; do not change general configuration-variable cancellation semantics or required MCP input behavior. The related closed https://github.com/microsoft/vscode/issues/251803 concerns optional MCP prompt parameters rather than server installation arguments and does not own this remaining defect.

## Evidence

- **source reproduction:** In src/vs/platform/mcp/common/mcpManagementService.ts, processArguments reads IMcpServerArgument entries but never checks isRequired; for named arguments it unconditionally appends arg.name and then appends a ${input:...} placeholder when a description or default exists.
- **lost metadata:** src/vs/platform/mcp/common/mcpManagement.ts defines IMcpServerInput.isRequired, but src/vs/platform/mcp/common/mcpPlatformTypes.ts IMcpServerVariable has no required/optional field, so optionality is not retained in the generated MCP configuration.
- **cancellation path:** src/vs/workbench/services/configurationResolver/browser/baseConfigurationResolverService.ts returns undefined when an input is canceled, while src/vs/workbench/contrib/mcp/common/mcpRegistry.ts ignores the return value from resolveWithInteraction and proceeds to resolveAsync/fromSerialized; unresolved replacements are documented by ConfigurationResolverExpression as remaining intact.
- **maintainer intent:** The issue author's follow-up explicitly states that optional arguments should not be passed when the user does not set them: https://github.com/microsoft/vscode/issues/270755#issuecomment-3390435348
