## Evidence

- **Current source confirms the race:** In src/vs/workbench/api/common/extHostDocumentContentProviders.ts, registerTextDocumentContentProvider awaits lastEvent before constructing and assigning its successor. With three rapid events, the second and third handlers await the same first promise, then start provider requests concurrently. A delayed second response can therefore follow the third response.
- **Stale response reaches the model:** src/vs/workbench/api/browser/mainThreadDocumentContentProviders.ts::$onVirtualDocumentChange accepts each arriving value and applies computed edits without a provider-request generation check. Once the third update completes, a later second response can replace it, matching the supplied first → third → second reproduction.
- **Open fixing PR:** https://github.com/microsoft/vscode/pull/346986 is verified open, has no merged timestamp, and explicitly states Fixes #346976. Its proposed implementation queues refreshes per document URI and awaits main-thread acknowledgement; it is an existing implementation candidate, not a landed fix.
- **Related report is distinct:** https://github.com/microsoft/vscode/issues/347123 is open but concerns overlapping DAP loadedSource/source responses in DebugContentProvider. Its body explicitly distinguishes that path from extension-provided virtual documents, so it is not a canonical duplicate for this report.
