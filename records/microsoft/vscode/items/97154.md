# Issue #97154 — Use contentEditable for our hidden accessibility textArea

[https://github.com/microsoft/vscode/issues/97154](https://github.com/microsoft/vscode/issues/97154)

## Summary

Keep open for an accessibility design review against the newer EditContext implementation. Current main already supports div-based and optional rich screen-reader content, but that does not establish completion of the requested per-line semantic information or compatibility across input backends.

## Change summary

Investigate replacing the editor's hidden accessibility textarea with structured content that can expose line numbers, breakpoints, and other per-line information.

## Best solution

Evaluate the remaining semantic-accessibility requirements against NativeEditContext and ScreenReaderSupport rather than revive the old textarea replacement unchanged. Retain reliable selection, composition, and fallback-browser behavior while deciding what per-line information screen readers should announce.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts`, `src/vs/editor/browser/controller/editContext/native/screenReaderSupport.ts`, `src/vs/editor/browser/controller/editContext/native/screenReaderContentRich.ts`, `src/vs/editor/browser/controller/editContext/textArea/textAreaEditContext.ts`, `src/vs/editor/common/config/editorOptions.ts`
- **Validation:** Agree on the annotation contract, then manually verify it with NVDA on Windows and VoiceOver on macOS: navigate annotated lines and words, change selections, move focus to another selectable surface, and exercise IME composition. Check both native EditContext and textarea fallback behavior, and compare navigation responsiveness in a large file with rich content enabled and disabled.
- **Behavior:**

  > Screen-reader users should be able to obtain useful per-line editor information, such as line numbers and breakpoint state, without corrupting the text they edit or losing reliable navigation. Selection changes, focus transitions, and composition input must remain correct. Acceptance must specify which information is announced and when, avoid duplicate screen-reader announcements, and demonstrate acceptable responsiveness on large files.
- **Trace:**

  > The original prototype at https://github.com/microsoft/vscode/pull/98177 was closed without merging; its discussion documents the broad input compatibility risk. Current NativeEditContext constructs a div and attaches the browser EditContext API, while ScreenReaderSupport selects SimpleScreenReaderContent or RichScreenReaderContent using editor.renderRichScreenReaderContent. RichScreenReaderContent already builds per-line HTML and maps DOM selections to editor selections, so several original implementation obstacles now have existing mechanisms. TextAreaEditContext remains the fallback, and the inspected rich renderer does not establish semantic announcements for line numbers or breakpoints. https://github.com/microsoft/vscode/issues/249269 documents related problems reading complex spans, not a duplicate of the whole request. Preserve existing editing, clipboard, composition, and fallback behavior; uncertainty begins at the desired announcement contract and supported backend scope.
- **Open decisions:**
  - Which per-line information should be exposed, and should line numbers and breakpoint annotations be announced automatically during navigation or only on explicit request?
  - Must equivalent semantic information be available on textarea-fallback browsers, or is an initially native-EditContext-only capability acceptable?
