# Issue #205946 — Setting editor.find.seedSearchStringFromSelection to Selection still seed the Find Widget from not selected words

[https://github.com/microsoft/vscode/issues/205946](https://github.com/microsoft/vscode/issues/205946)

## Summary

The same observable behavior is tracked by an open issue with an open fixing PR. Consolidate there; the behavior remains present on main, so this is not a completed-fix close.

## Change summary

Find Next Selection replaces the previous search term with an unselected word despite the selection-only or never seeding setting.

## Best solution

Consolidate on https://github.com/microsoft/vscode/issues/300085 and review https://github.com/microsoft/vscode/pull/300086, reconciling its proposed behavior with the earlier deliberate exemption for selection-find commands.

## Evidence

- **Current source confirms the symptom:** src/vs/editor/contrib/find/browser/findController.ts:935-945 calls getSelectionSearchString(editor, 'single', false) in SelectionMatchFindAction.run() and overwrites the controller search string. At lines 43-65, an empty selection therefore falls back to the cursor word without consulting editor.find.seedSearchStringFromSelection.
- **Verified canonical and re-review eligibility:** https://github.com/microsoft/vscode/issues/300085 is OPEN and describes the same command replacing the previous search term with an unselected cursor word under the selection-only setting. - **Full scope and report-specific evidence:** https://github.com/microsoft/vscode/pull/300086 addresses both selection and never values for the shared next/previous selection-find action. It covers this report's Linux reproduction using cursor movement rather than pasting; both reach the same empty-selection fallback. The original reporter also requested review there: https://github.com/microsoft/vscode/pull/300086#issuecomment-5267829638.
- **Earlier behavior decision needs consideration:** https://github.com/microsoft/vscode/issues/165977 requested the opposite behavior: selection-find commands should ignore this setting. That closed report is historical context, not a duplicate target or evidence that the present request is fixed.
