# Issue #335822 — Manual automations can be disabled even though they remain runnable

[https://github.com/microsoft/vscode/issues/335822](https://github.com/microsoft/vscode/issues/335822)

## Summary

Confirmed on main: manual automations can be toggled Disabled via the card menu, but the run button's enabled state (and the underlying `canRunAutomation` check) never consults `automation.enabled`, so a 'disabled' manual automation remains fully runnable — the UI state is misleading for this schedule type.

## Change summary

A manual automation can be marked Disabled, but its Run button stays active and the automation can still be started, since disabling has no effect for schedule-less automations.

## Best solution

Decide (with a maintainer) whether manual automations should simply drop the Disable/Enable action and disabled badge entirely, or whether 'enabled' should also gate `canRunAutomation`/the run button for all schedule types — then wire the chosen behavior into automationsView.ts's card menu conditions and run-button enablement.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/sessions/browser/views/automationsView.ts`, `src/vs/sessions/contrib/automations/browser/providerAutomationService.ts`
- **Validation:** After the design is chosen: a test in automationsView.test.ts or providerAutomationService.test.ts asserting a manual automation either has no Disable action/badge, or that `canRunAutomation`/run button returns false once `enabled` is false.
- **Behavior:**

  > Disabling a manual automation should either be unavailable (no Disable action, no disabled badge) since there is no schedule to suspend, or — if the enabled flag is kept — actually prevent the automation from being run manually. Whichever is chosen, the UI state (badge/menu) and the actual runnability must agree; scheduled automations' existing disable behavior must be unaffected.
- **Trace:**

  > The disabled badge and Disable/Enable menu actions are driven purely by `automation.enabled` and `AutomationCardEnabledContext` with no schedule-type check (automationsView.ts ~2218-2246, 662-663). Separately, `canRunAutomation` (agentHostAutomationStore.ts:184, providerAutomationService.ts:173) and the run-button enablement (automationsView.ts:645) never read `automation.enabled`, so the two states are already decoupled for every schedule type — manual just exposes it because manual automations have no other mechanism (cron/schedule) that disabling would otherwise affect. Do not change scheduled-automation disable/suspend behavior; the boundary is the manual (`schedule.interval === 'manual'`) case and/or the run-button gating logic.
- **Open decisions:**
  - Should manual automations lose the Disable/Enable action and badge entirely, or should 'enabled' start gating runnability (via canRunAutomation) for all schedule types?
  - If the enabled flag is dropped for manual automations, does any persisted 'enabled: false' manual automation need a one-time migration?

## Evidence

- **run button ignores enabled:** src/vs/sessions/contrib/sessions/browser/views/automationsView.ts:645 sets `card.runButton.enabled = this.automationService.canRunAutomation?.(automation.id) !== false` — no reference to `automation.enabled` at all.
- **canRunAutomation semantics:** src/vs/sessions/contrib/providers/agentHost/browser/agentHostAutomationStore.ts:184 and providerAutomationService.ts:173 implement `canRunAutomation` purely around store/connection existence, not the enabled flag.
- **disable action shown for all schedules:** The DisableAutomationAction menu condition (automationsView.ts:2224) is gated only on `ChatAutomationsEnabledContext` and `AutomationCardEnabledContext`, with no schedule-type check, so it appears for manual automations too.
