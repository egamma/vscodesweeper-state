# Issue #228421 — Make URI Handlers available for vscode.dev

[https://github.com/microsoft/vscode/issues/228421](https://github.com/microsoft/vscode/issues/228421)

## Summary

Keep open: web URI callback plumbing already exists, but it does not establish the requested shareable link that opens vscode.dev, offers extension installation, and invokes its handler. The request has 31 upvotes and was accepted into Backlog; no qualifying canonical issue or concrete implementing fix was found.

## Change summary

Support shareable vscode.dev links that install or activate a target extension and deliver an extension-specific URI.

## Best solution

Provide a supported web deep-link entry point that reuses extension URI dispatch and installation handling, preserving the target URI through startup and any required installation. Distinguish this cold-start flow from callbacks generated inside an already-running workbench.

## Plan brief

- **Likely files:** `src/vs/code/browser/workbench/workbench.ts`, `src/vs/workbench/services/url/browser/urlService.ts`, `src/vs/workbench/services/extensions/browser/extensionUrlHandler.ts`, `src/vs/workbench/services/extensions/test/browser/extensionUrlHandler.test.ts`
- **Validation:** In a fresh browser profile, open the agreed shareable web URL for a test web extension that is not installed; accept installation and verify its URI handler receives the intended path, query, and fragment. Repeat with the extension installed and inactive, verify cancellation does not invoke the handler, and confirm existing generated authentication callbacks still work.
- **Behavior:**

  > An extension author can share a reusable link that opens vscode.dev and invokes that extension's URI handler without requiring desktop VS Code or an already-running browser workbench. If the web-compatible extension is missing, the user can accept installation and continue to the requested extension action. The handler receives the intended path, query, and fragment, and declining installation or required consent does not invoke it. Existing authentication callback behavior remains unchanged.
- **Trace:**

  > BrowserURLService in src/vs/workbench/services/url/browser/urlService.ts already forwards provider callbacks into IURLService. LocalStorageURLCallbackProvider in src/vs/code/browser/workbench/workbench.ts creates per-workbench pending request IDs and consumes their local-storage responses, establishing a return-callback mechanism rather than a demonstrated cold-start deep-link contract. ExtensionUrlHandler in src/vs/workbench/services/extensions/browser/extensionUrlHandler.ts already provides extension activation, buffering, consent, and missing-extension installation handling. The unresolved boundary is how the public vscode.dev entry point accepts a reusable extension URI and carries it through workbench startup; hosted deployment routing was not verified from this checkout. Preserve existing callback semantics and extension consent behavior, and do not expand this into arbitrary command execution. Related historical evidence is https://github.com/microsoft/vscode/issues/182047#issuecomment-1542665122.
- **Open decisions:**
  - What supported public URL format should authors share to identify the target extension and preserve its URI path, query, and fragment?
  - When a link is opened while vscode.dev is already running, should it invoke the extension in an existing workbench or initialize the workbench opened by that link?
