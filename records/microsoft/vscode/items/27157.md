# Issue #27157 — PreLaunchTask: support passing parameters from configuration to preLaunchTask

[https://github.com/microsoft/vscode/issues/27157](https://github.com/microsoft/vscode/issues/27157)

## Summary

Keep this accepted, well-supported request open: current launch-to-task execution still does not pass launch configuration values or resolved inputs to the task. A maintainer explicitly endorsed this issue as the home for the related input-sharing request.

## Change summary

Allow a launch configuration to pass configuration properties and resolved input values to its preLaunchTask without duplicate prompts or duplicated task definitions.

## Best solution

Define an explicit launch-to-task parameter contract that lets reusable tasks consume values from the selected debug configuration. Preserve independently runnable tasks and avoid interpreting debugger-specific attributes such as cwd automatically.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugAdapterManager.ts`, `src/vs/workbench/contrib/debug/browser/debugService.ts`, `src/vs/workbench/contrib/debug/browser/debugTaskRunner.ts`, `src/vs/workbench/contrib/debug/common/debug.ts`, `src/vs/workbench/contrib/tasks/common/taskService.ts`, `src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts`, `src/vs/workbench/services/configurationResolver/browser/baseConfigurationResolverService.ts`
- **Validation:** After agreeing on the contract, exercise a launch configuration that selects a target address once and invokes a task that echoes that address; both task and debugger must receive the same value with no second prompt. Also verify two launch configurations can supply different literal ports to the same task, standalone task execution retains its existing input behavior, and concurrent launches do not exchange values. Add focused automated coverage at the debug/task handoff and configuration-resolver boundaries.
- **Behavior:**

  > A reusable preLaunchTask should be able to receive values from the selected launch configuration, including values already obtained from interactive inputs. A target address selected once must be usable by both task and debugger without a second prompt, and different launch configurations must be able to supply different ports without duplicating tasks. Independent task execution and unrelated debug sessions must retain their existing behavior. The maintainer must settle the parameter-binding contract before implementation.
- **Trace:**

  > DebugService resolves the launch configuration before invoking DebugTaskRunner with only its preLaunchTask identifier; DebugTaskRunner subsequently calls taskService.run(task) without launch context. Debugger.substituteVariables resolves the 'launch' section, while TerminalTaskSystem independently resolves the 'tasks' section through BaseConfigurationResolverService. Existing ${config:...} variables read settings, and object-valued preLaunchTask entries identify tasks rather than passing arguments. The trace establishes the missing handoff, but not an agreed public schema or cross-section input contract. Preserve standalone task resolution, session isolation, and debugger ownership of attributes such as cwd; automatic cwd inheritance is not part of the accepted generic request. Maintainer endorsement of this issue is recorded at https://github.com/microsoft/vscode/issues/201785#issuecomment-1877440449.
- **Open decisions:**
  - Should passing values require explicit launch-to-task bindings, or should matching input IDs automatically share resolved values across launch.json and tasks.json?
  - Should the public contract supply task input values only, or also let tasks reference arbitrary resolved properties of the selected launch configuration?
  - When a binding refers to an input the task does not declare, should launch fail with a diagnostic or ignore that binding?
