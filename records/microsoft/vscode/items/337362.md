# Issue #337362 — Show MCP server health and authentication status in the chat input

[https://github.com/microsoft/vscode/issues/337362](https://github.com/microsoft/vscode/issues/337362)

## Summary

Genuine, currently-unimplemented gap: existing MCP status affordances (ChatMcpServersInteractionContentPart, ChatMcpAuthenticationContentPart) only render transiently inside a chat response after a request is sent, not persistently at the input before sending — so the request stands, though it overlaps with a related open issue on a different surface.

## Change summary

Add a persistent, low-noise indicator near the chat input that surfaces unhealthy/unauthenticated MCP servers and offers a direct recovery action.

## Best solution

Design and implement an input-adjacent MCP health affordance (e.g. in the chat input toolbar) driven by IMcpService server state, distinct from the existing in-response starting/auth content parts; coordinate scope with https://github.com/microsoft/vscode/issues/335528 which asks for the equivalent signal in the Customizations/Agents-window UI rather than the chat input.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input`, `src/vs/workbench/contrib/mcp/common/mcpService.ts`, `src/vs/workbench/contrib/mcp/common/mcpTypes.ts`
- **Validation:** A chat input test asserting the indicator appears only when an enabled MCP server is unhealthy/unauthenticated and exposes a working recovery action, and is absent when all enabled servers are healthy.
- **Behavior:**

  > When one or more enabled MCP servers require authentication, are stuck starting, failed to initialize, or otherwise can't provide tools, a visible indicator appears in or near the chat input identifying the affected server(s) and offering a direct recovery action (sign in, retry, view error, open MCP config). When all enabled servers are healthy, no indicator is shown.
- **Trace:**

  > MCP server connection/auth/starting state already flows through IMcpService (src/vs/workbench/contrib/mcp/common/mcpTypes.ts) and is currently only surfaced via response-scoped content parts (ChatMcpServersInteractionContentPart, ChatMcpServersStartingContentPart, ChatMcpAuthenticationContentPart under src/vs/workbench/contrib/chat/browser/widget/chatContentParts) that render after a message is sent and disappear. No code path renders this state near the chat input itself (checked src/vs/workbench/contrib/chat/browser/widget/input). Do not change the existing in-response starting/auth UX; the open question is where and how a new, input-adjacent, persistent summary indicator should live and how it should compose with https://github.com/microsoft/vscode/issues/335528's overlapping ask for the Customizations UI.
- **Open decisions:**
  - Should the input-level indicator be a distinct new UI element, or should it be unified with the Customizations UI health signal requested in #335528?
  - How should multiple simultaneously-unhealthy servers be summarized in a single indicator (list, count, worst-status only)?
  - Should this pre-send indicator ever block/warn before submitting a request that depends on a known-unhealthy server, or only inform?

## Evidence

- **related but distinct scope:** https://github.com/microsoft/vscode/issues/335528 (open, assigned to connor4312) asks for the same kind of persistent health signal but scoped to the Agents-window Customizations UI (Overview / MCP Servers row), not the chat input specifically — narrower overlap, not a full duplicate in either direction.
- **corroborating reports:** 335528 links three further open issues (#327640, #330837, #334271) describing MCP auth/tool-loss failures that surface with no reliable feedback, supporting real user impact in this problem space.
