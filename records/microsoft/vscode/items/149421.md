# Issue #149421 — Tooltip action to disable specific problems/linting rules

[https://github.com/microsoft/vscode/issues/149421](https://github.com/microsoft/vscode/issues/149421)

## Summary

Keep this accepted request open: individual lint settings and provider-supplied quick fixes exist, but they do not establish the requested unified, discoverable rule-configuration action in diagnostic tooltips. No verified older canonical owns the same request; the team-authored Backlog item should not be declined for inactivity.

## Change summary

Offer diagnostic-tooltip actions to configure or disable individual lint rules, including provider-owned configuration and user/workspace scope choices.

## Best solution

Provide a consistent diagnostic-hover entry point for rule configuration, with built-in CSS as an initial consumer and extensions retaining ownership of their configuration semantics. Decide whether existing code actions adequately express that experience or whether diagnostics need an explicit configuration contract.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/hover/browser/markerHoverParticipant.ts`, `src/vs/platform/markers/common/markers.ts`, `src/vscode-dts/vscode.d.ts`, `extensions/css-language-features/client/src/cssClient.ts`, `extensions/css-language-features/server/src/cssServer.ts`
- **Validation:** In an isolated development profile, create a CSS unknown-property warning and verify that its hover exposes the agreed rule-configuration action. Check user and workspace choices, cancellation without changes, suppression of only the selected rule, and unchanged ordinary quick fixes; exercise a sample extension whose action updates a project-specific configuration file.
- **Behavior:**

  > Users encountering a lint diagnostic should be able to discover how to configure or disable its specific rule from the diagnostic tooltip without searching manually for the setting. Built-in CSS should support the applicable user/workspace choices, while extensions can retain their own configuration files and prompts. Acceptance should cover rule-specific suppression, cancellation without side effects, and preservation of unrelated diagnostics and existing quick fixes. The exact shared interaction and extension contract need agreement before implementation.
- **Trace:**

  > MarkerHoverParticipant in src/vs/editor/contrib/hover/browser/markerHoverParticipant.ts obtains provider quick fixes and renders shared hover actions, but has no generic rule-configuration association. IMarkerData in src/vs/platform/markers/common/markers.ts and Diagnostic in src/vscode-dts/vscode.d.ts expose rule identifiers and documentation links, not configuration metadata. The CSS extension already registers per-rule ignore/warning/error settings and delegates code actions to its language service; its inspected client does not register a rule-configuration command. This establishes an existing configuration mechanism and a missing shared discovery contract, not a broken diagnostic path. Preserve extension ownership of rule semantics and configuration files; do not substitute disabling an entire diagnostic source. The supplied discussion links https://github.com/microsoft/vscode/issues/54272 as related presentation infrastructure, not as a duplicate. Uncertainty starts at whether provider quick fixes should remain the public mechanism or the product should introduce a distinct configuration interaction.
- **Open decisions:**
  - Should rule configuration remain under Quick Fix..., or should diagnostic tooltips expose a distinct, consistently named configuration action?
  - Should providers use the existing code-action contract exclusively, or should diagnostics expose explicit setting/configuration-command metadata for the shared experience?
