# Issue #81558 — Expanding semantic theming to support semantically embedded languages for colorization

[https://github.com/microsoft/vscode/issues/81558](https://github.com/microsoft/vscode/issues/81558)

## Summary

A real API gap remains on current main: semantic tokens can select token types and modifiers, but every token is themed using the host document's language ID. The existing `under-discussion` classification is appropriate while maintainers decide the public contract and whether this covers theming alone or broader embedded-language delegation.

## Change summary

Allow semantic highlighting providers to associate embedded-language regions or tokens with another language so language-specific colorization can apply inside mixed-language documents.

## Best solution

Define a language-aware semantic-token or embedded-region contract that lets Razor and similar providers apply the embedded language's theme rules without activating a full document-level provider, while preserving host-language styling outside those ranges.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/services/semanticTokensProviderStyling.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/editor/test/common/services/semanticTokensProviderStyling.test.ts`
- **Validation:** Add semantic-token API and styling tests for a mixed-language document, asserting that an embedded C# range resolves C#-scoped theme rules while surrounding Razor tokens continue resolving Razor-scoped rules.
- **Behavior:**

  > A semantic provider for a mixed-language document can identify an embedded range or its tokens as belonging to another language. Tokens in that region use the embedded language's semantic theme rules, while tokens outside it retain the host document's rules. Existing semantic-token providers that do not supply embedded-language information remain unchanged. Acceptance should cover at least one Razor-hosted C# range and verify host and embedded styling in the same model.
- **Trace:**

  > The stable extension API in src/vscode-dts/vscode.d.ts encodes each semantic token as five integers and has no language field. The rendering path in src/vs/editor/common/services/semanticTokensProviderStyling.ts accepts one language ID for the entire result, and documentSemanticTokens.ts supplies `model.getLanguageId()`. Theme infrastructure already supports language-qualified semantic selectors through `semanticTokenScopes`, but the provider cannot select a different language for individual tokens. The uncertainty begins at the public contract: the original request is colorization-only, while comments also request delegation to embedded language services. Preserve existing five-value providers and host-language styling semantics unless maintainers explicitly choose a breaking protocol revision.
- **Open decisions:**
  - Should the supported contract identify an embedded language only for semantic theming, or also delegate semantic processing to that language's providers?
  - Should language identity be attached to individual semantic tokens or supplied through a separate embedded-language range contract?
  - When host and embedded semantic providers produce overlapping tokens, which provider's language and classification should determine the rendered style?

## Evidence

- **current extension API:** src/vscode-dts/vscode.d.ts defines each semantic token with five values—position, length, token type, and token modifiers—and exposes no per-token or per-range language identifier.
- **current styling path:** src/vs/editor/common/services/semanticTokensProviderStyling.ts receives one `languageId` for the complete token result; `toMultilineTokens2` passes that same value to `getMetadata` for every token.
- **document language binding:** src/vs/editor/contrib/semanticTokens/browser/documentSemanticTokens.ts and viewportSemanticTokens.ts call `toMultilineTokens2` with `model.getLanguageId()`, so embedded tokens cannot independently select C#, JavaScript, or another embedded language's theme rules.
- **related exploration:** https://github.com/microsoft/vscode/issues/77133 closed after delivering the general semantic-highlighting API, but its closing comment did not claim that language-aware embedded ranges were implemented; this issue was created separately from that discussion.
- **independent use cases:** The discussion identifies Razor attributes, XSLT expressions, dynamically injected PEG.js JavaScript, and semantically processed comments, showing that the gap is not limited to the original Razor example.
