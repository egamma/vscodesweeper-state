# Issue #81558 — Expanding semantic theming to support semantically embedded languages for colorization

[https://github.com/microsoft/vscode/issues/81558](https://github.com/microsoft/vscode/issues/81558)

## Summary

The semantic-tokens API still has no way to associate token ranges with an embedded language, and the discussion identifies multiple extension scenarios that remain unsupported. The request is already correctly classified as under discussion and should stay open for an API design decision.

## Change summary

Allow semantic token providers to identify dynamically embedded language regions so those ranges can receive language-appropriate colorization or semantic processing.

## Best solution

Design an editor/language API for dynamic embedded-language regions that supports host-to-embedded handoff and sufficient context, rather than adding only a theme-style language property that cannot represent ambiguous termination rules.

## Plan brief

- **Likely files:** `src/vs/editor/common/languages.ts`, `src/vs/editor/common/services/languageFeaturesService.ts`, `src/vs/editor/contrib/semanticTokens/browser/documentSemanticTokens.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`
- **Validation:** Add API and editor tests using a host document with a dynamically identified embedded-language range, verifying language-aware token styling and correct handling of adjacent or nested host-language content.
- **Behavior:**

  > A language extension can identify dynamically embedded-language content within a host document so that the embedded region receives language-appropriate semantic colorization without requiring a static TextMate grammar declaration. Host-language highlighting outside the region remains unchanged. The design must cover straightforward bounded ranges and explicitly define behavior for embeddings whose endpoint depends on parsing by the embedded language.
- **Trace:**

  > The request concerns the semantic-token provider path and its extension-host/main-thread/editor contracts, likely spanning src/vs/editor/common/languages.ts, languageFeaturesService.ts, documentSemanticTokens.ts, and the extHost/mainThread language-feature bridge. Existing semantic tokens convey token type and modifiers but not a language identity or a protocol for handing parsing control between host and embedded language providers. The Razor and PegJS examples establish demand for dynamic embedding, while the XSLT comment identifies where a range-only abstraction stops being sufficient. Preserve ordinary semantic-token behavior and static TextMate embedded-language support; the uncertainty begins at whether this API is colorization-only or a broader embedded-language coordination mechanism.
- **Open decisions:**
  - Should the API only attach a language identity to bounded semantic ranges, or coordinate host-to-embedded provider handoff?
  - How should an embedded provider receive host context and determine when control returns to the host language?
  - Should language-aware theme resolution reuse existing embedded-language/TextMate behavior or introduce a separate semantic-token mechanism?
  - What nesting and overlap semantics should apply when embedded regions contain further embedded languages?
