# Issue #135033 — Allow option to deprioritize Symbols in Quick Open

[https://github.com/microsoft/vscode/issues/135033](https://github.com/microsoft/vscode/issues/135033)

## Summary

Keep open: current Quick Open can include or exclude workspace symbols, but cannot retain them below matching files. The request has maintainer support, and the older related issues do not establish a duplicate under the re-review bar.

## Change summary

Provide an option to rank matching files above workspace symbols in Quick Open without removing symbol results.

## Best solution

Offer an opt-in files-first ordering in the combined Quick Open results, preserving the current default ranking and dedicated symbol pickers. Agree on the configuration contract and result-limit behavior before implementation.

- **Behavior:**

  > Users who include workspace symbols in Quick Open need an opt-in way to place matching files before matching symbols rather than exclude symbols altogether. Acceptance includes mixed file/symbol matches, symbol-only matches, and explicitly agreed behavior for capped result sets.
- **Trace:**

  > AnythingQuickAccessProvider.getAdditionalPicks in src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts obtains files and workspace symbols together, merges them, and ranks the combined array with compareItemsByFuzzyScore before applying MAX_RESULTS, currently 512. Its configuration getter reads search.quickOpen.includeSymbols but no priority preference; registration lives in search.contribution.ts and the typed contract in contrib/search/common/search.ts. getWorkspaceSymbolPicks delegates to SymbolsQuickAccessProvider with skipLocal and skipSorting, so this request concerns the combined file picker rather than symbol-provider matching or dedicated symbol sorting. Source inspection establishes the missing capability, not an executed reproduction. Preserve history, symbol eligibility, provider timing, and default ranking. https://github.com/microsoft/vscode/issues/27317 supplies broader ranking context; https://github.com/microsoft/vscode/issues/101487 concerns latency rather than this ordering preference. Product uncertainty remains in how the preference is exposed and how files-first ordering interacts with the existing result cap.
- **Open decisions:**
