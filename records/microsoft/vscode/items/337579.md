# Issue #337579 — Markdown preview does not scroll to an HTML anchor (<a id>) in a linked file

[https://github.com/microsoft/vscode/issues/337579](https://github.com/microsoft/vscode/issues/337579)

## Summary

Still reproduces on current main: the `inEditor` half of the original report is already fixed (openDocumentLink.ts now uses resolved.positionOrRange via getRangeFromPositionOrRange), but the `inPreview` half remains broken — getLineElementForFragment in scroll-sync.ts still has no fallback for a fragment id on an element without a source line, exactly as the reporter diagnosed.

## Change summary

Clicking a cross-file link to an inline HTML anchor (<a id>) scrolls the Markdown preview to the top of the target file instead of the anchor.

## Best solution

Fix getLineElementForFragment in extensions/markdown-language-features/preview-src/scroll-sync.ts to fall back to document.getElementById(fragment) (walking up to the nearest ancestor with a source line) when no code-line element has a matching id — the reporter already attached a working patch along these lines.

## Plan brief

- **Likely files:** `extensions/markdown-language-features/preview-src/scroll-sync.ts`
- **Validation:** Manually verify with the reporter's repro (a.md linking to b.md#user where b.md has 50+ filler lines before an inline <a id="user">) that the preview scrolls to the anchor instead of the top, both with the default `inPreview` setting; decide whether a jsdom-based unit test for getLineElementForFragment should be added as part of the fix.
- **Behavior:**

  > Clicking a Markdown preview link whose target fragment matches an inline HTML anchor (e.g. `<a id="user"></a>`) in another file must scroll the preview of that file to the anchor's location, not to the top of the document. This should hold for both the default `markdown.preview.openMarkdownLinks: inPreview` setting. Headings-based fragments must continue to work exactly as before.
- **Trace:**

  > getLineElementForFragment (extensions/markdown-language-features/preview-src/scroll-sync.ts:333) only searches getCodeLineElements(documentVersion), which is built from elements that carry a source line; an inline `<a id>` placed mid-paragraph is rendered without a traceable source line and is never found, so the caller falls through to scrolling position 0 (top). The boundary: this is a lookup-only function — do not touch getCodeLineElements, the markdown language-service's resolveLinkTarget/includeHtmlIds table-of-contents logic, or the already-fixed inEditor path in extensions/markdown-language-features/src/util/openDocumentLink.ts. The reporter's attached diff (truncated in the issue body) adds a document.getElementById(fragment) fallback that walks up to the nearest ancestor with a source line, skipping body (line -1).

## Evidence

- **inEditor already fixed on main:** extensions/markdown-language-features/src/util/openDocumentLink.ts:64 now computes rangeSelection via getRangeFromPositionOrRange(resolved.positionOrRange), matching the reporter's confirmation that the inEditor case was fixed in 1.139.0.
- **inPreview still broken on main:** extensions/markdown-language-features/preview-src/scroll-sync.ts:333-336 — getLineElementForFragment only matches elements returned by getCodeLineElements (which require a source line); there is no fallback to document.getElementById for inline <a id> anchors, so the preview scroll lands at the top of the target file.
- **no test harness for this module:** No existing unit tests import scroll-sync.ts and no jsdom-based test pattern exists in extensions/markdown-language-features — this preview-src code runs only inside the webview, so an automated regression test isn't readily available.
- **related but distinct issue:** https://github.com/microsoft/vscode/issues/331624 is about anchor-to-heading links not navigating in the experimental Markdown editor, a different surface and symptom — not a canonical duplicate of this preview scroll-position bug.
