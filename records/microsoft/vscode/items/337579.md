# Issue #337579 — Markdown preview does not scroll to an HTML anchor (<a id>) in a linked file

[https://github.com/microsoft/vscode/issues/337579](https://github.com/microsoft/vscode/issues/337579)

## Summary

Confirmed live defect: the `inEditor` half the reporter described is already fixed on main (openDocumentLink.ts now reads `positionOrRange`), but the default `inPreview` case is still broken — the preview's fragment lookup only matches elements carrying a source line, so an inline `<a id>` anchor is never found and the preview scrolls to the top instead of the item.

## Change summary

Clicking a link to an inline HTML anchor (`<a id>`) in another Markdown file scrolls the preview to the top instead of the anchor.

## Best solution

Extend `getLineElementForFragment` in `extensions/markdown-language-features/preview-src/scroll-sync.ts` to fall back to `document.getElementById(fragment)` and walk up to the nearest ancestor with a source line when no code-line element matches by id directly — the reporter already sketched this fix in their comment.

## Plan brief

- **Likely files:** `extensions/markdown-language-features/preview-src/scroll-sync.ts`, `extensions/markdown-language-features/preview-src/index.ts`
- **Validation:** Reproduce with the reporter's a.md/b.md example (an inline `<a id="user">` after 50+ filler lines) and confirm the preview scrolls near the anchor instead of the top; no automated harness exists for preview-src today, so the plan should decide whether to add a small DOM-based test or rely on manual verification.
- **Behavior:**

  > Clicking a Markdown link whose fragment targets an inline HTML anchor (`<a id="...">`) in another file should scroll the opened preview to (or near) that anchor, the same way it already works for heading-based fragments and in the editor/`inEditor` mode. Currently the preview silently stays at the top. Acceptance: using the reporter's a.md/b.md repro, opening a.md's preview and clicking the link to b.md#user scrolls b.md's preview to the item, not the top.
- **Trace:**

  > `getLineElementForFragment` (extensions/markdown-language-features/preview-src/scroll-sync.ts:333-337) only matches elements returned by `getCodeLineElements`, which requires a `data-line` attribute (added to elements Markdown-it tags with source-line info). Inline `<a id>` elements are not tagged this way, so the function returns undefined and the caller in preview-src/index.ts (~line 133) takes no scroll action, leaving the preview at its initial position. The `inEditor` half of this report is already fixed on main — `MdLinkOpener.openDocumentLink` in src/util/openDocumentLink.ts:64 correctly consumes `resolved.positionOrRange` — so the remaining scope is preview-src/scroll-sync.ts only; do not touch the editor-opening path. The reporter's own draft patch (fallback to `document.getElementById` + walk up to the nearest source-line ancestor, skipping `document.body` at line -1) is a reasonable direction but was truncated in the comment.
- **Open decisions:**
  - Should the fallback scroll to the nearest enclosing source-line ancestor (imprecise but simple, as the reporter's patch does), or should the language service be asked to resolve a more precise line for HTML-id anchors so the preview can scroll exactly?

## Evidence

- **inEditor already fixed:** extensions/markdown-language-features/src/util/openDocumentLink.ts line 64 already uses `getRangeFromPositionOrRange(resolved.positionOrRange)`, not a raw `.position` field — confirms the reporter's own follow-up that the `inEditor` case is fixed in 1.139.0.
- **inPreview still broken:** extensions/markdown-language-features/preview-src/scroll-sync.ts lines 333-337: `getLineElementForFragment` only searches `getCodeLineElements`, i.e. elements carrying a `data-line`/`code-line` class; an inline `<a id>` has no such attribute, so the lookup returns undefined and preview-src/index.ts (~line 133) silently skips scrolling when no element is found.
- **reporter-supplied patch:** Comment at 2026-09-23T23:24:07Z includes a draft diff adding an `Element.getElementById` fallback with ancestor walk-up, matching the traced code path.
