# Issue #226412 — Watch expressions should allow LSP or debugger to remove inner whitespaces

[https://github.com/microsoft/vscode/issues/226412](https://github.com/microsoft/vscode/issues/226412)

## Summary

This remains a valid debugger feature request: multiline selections are added to Watch with formatting whitespace that makes the displayed expression hard to read. The discussion identifies several materially different contracts for normalization, and no older canonical issue is established, so it should remain open for a debugger/API design decision.

## Change summary

Allow a language-aware provider to simplify selected expressions before they are added to Watch, including safe whitespace, comment, and trailing-semicolon cleanup.

## Best solution

Define a language-aware expression-normalization contract for Add to Watch, then use its result for both display and evaluation without changing spaces inside strings or other semantically significant text. The debugger owner should first decide whether this is a formatter responsibility, a dedicated language-provider API, or display-only escaping.

- **Validation:** Add debugger tests that create a Watch expression from an indented multiline selection and verify the chosen normalized display/evaluation text, while preserving whitespace inside string literals and handling comments and a trailing semicolon according to the selected contract.
- **Behavior:**

  > Adding a valid multiline source expression to Watch should produce a readable expression without incidental indentation or line-break whitespace. Any normalization must preserve semantically significant whitespace, especially inside string literals. The accepted behavior must explicitly cover comments and trailing semicolons and verify that the expression displayed and the expression evaluated follow the chosen contract.
- **Trace:**

  > The confirmed path starts with the debugger's Add to Watch action taking selected source text and creating a watch expression; the current behavior preserves multiline indentation, as demonstrated by the maintainer in https://github.com/microsoft/vscode/issues/226412#issuecomment-2334669109. The uncertainty begins before implementation: generic trimming/newline escaping is suitable for display but cannot safely perform language-aware comment or token removal, while invoking range formatting may return edits outside the selected expression. A dedicated language-facing simplification contract would avoid guessing syntax but expands the public extension/API surface. Keep evaluation semantics for existing single-line expressions unchanged, and do not perform lexical whitespace removal in core that could alter strings or language-specific syntax.
- **Open decisions:**
  - Should normalization change the expression sent to the debug adapter, or only its rendered Watch-list representation?
  - Should language-aware simplification use the existing range formatter contract or a dedicated provider/API for evaluatable expressions?
  - Must the contract remove comments and trailing statement terminators, or is its scope limited to incidental leading, trailing, and line-break whitespace?
