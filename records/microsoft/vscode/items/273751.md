# Issue #273751 — Add Memory Feature to GitHub Copilot with VS Code Sync Directory Support

[https://github.com/microsoft/vscode/issues/273751](https://github.com/microsoft/vscode/issues/273751)

## Summary

The core ask — a persistent memory mechanism for Copilot across sessions — already shipped on main as the `copilot_memory` tool (user/session/repo scoped notes under `/memories/`), but the second half of the title, cross-device sync via VS Code's sync directory, is not implemented: memory files live in the extension's `globalStorageUri`, not in anything Settings Sync touches. Keeping open for that remaining, narrower gap rather than closing on the part that's done.

## Change summary

Give Copilot a persistent memory store and sync that memory data across devices through VS Code's built-in sync mechanism.

## Best solution

The persistent-memory half is done (see evidence); the remaining, distinct ask is a privacy-conscious way to carry `/memories/` (at least the user-tier) across devices — either by piggybacking on Settings Sync's resource model or a dedicated opt-in cloud sync for Copilot memory. That design choice, and whether repo/session tiers should ever leave the local machine, needs a maintainer decision before any implementation.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/tools/node/memoryTool.tsx`, `extensions/copilot/src/extension/tools/common/memoryCleanupService.ts`, `extensions/copilot/package.json`
- **Validation:** A test demonstrating a memory note written on one simulated profile/device is visible after the chosen sync mechanism runs on a second profile/device.
- **Behavior:**

  > Copilot's existing persistent memory (/memories/ user tier) should be available on a second device signed into the same account, without the user manually copying files. Session and repo-scoped memory tiers are local by design and out of scope for sync. Acceptance: a note written via the memory tool on device A appears via the memory tool on device B after the sync mechanism runs.
- **Trace:**

  > Memory files are resolved in extensions/copilot/src/extension/tools/node/memoryTool.tsx from `extensionContext.globalStorageUri`, which is per-machine extension storage untouched by Settings Sync (`src/vs/platform/userDataSync`) today — confirmed by reading the tool and finding no sync-related imports in it or memoryCleanupService.ts. The boundary: do not change the existing local storage format or the session/repo memory semantics; only the user-tier distribution path is in scope.
- **Open decisions:**
  - Sync via the existing Settings Sync resource model, or a separate opt-in Copilot-specific cloud sync?
  - Should sync be on by default or require explicit opt-in given memory can contain personal/workspace-derived notes?
  - Does sync cover only user-tier memory, or any part of repo/session tiers?
