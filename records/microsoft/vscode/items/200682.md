# Issue #200682 — Connecting to Live Share session causes NPE in workspace trust subsystem

[https://github.com/microsoft/vscode/issues/200682](https://github.com/microsoft/vscode/issues/200682)

## Summary

The underlying workspace-trust race remains on current main: asynchronous URI canonicalization can pair a stale URI snapshot with a changed live folder list, producing the reported undefined URI and blocking the first Live Share join. A newer telemetry issue confirms the same root cause, but it is younger than this re-reviewed issue and therefore is not a valid canonical duplicate.

## Change summary

Accepting workspace trust while joining a Live Share session can throw while processing an undefined workspace URI, forcing multiple reloads before the session opens.

## Best solution

Keep the canonical workspace folder metadata and canonical URI snapshot internally consistent when folders change during asynchronous resolution, so accepting trust completes the initial Live Share join without an exception or reload.

## Evidence

- **current source root cause:** In src/vs/workbench/services/workspaces/common/workspaceTrust.ts, resolveCanonicalUris() snapshots folder URIs before awaiting Promise.all, then constructs CanonicalWorkspace from a fresh live workspace object. CanonicalWorkspace.folders maps that live folder list by index into the earlier canonicalFolderUris snapshot, so a concurrent folder addition yields an undefined URI.
- **reported trigger and outcome:** https://github.com/microsoft/vscode/issues/200682 documents that accepting the trust prompt during the initial Live Share join passes an undefined entry to setUrisTrust()/getCanonicalUri(), where reading uri.scheme throws and aborts opening the workspace.
- **current corroboration:** https://github.com/microsoft/vscode/issues/311558#issuecomment-4285079510 traces the same undefined-scheme failure on 2026 Insiders to the CanonicalWorkspace snapshot race and identifies dynamic workspace-folder mutation during trust processing as the trigger.
