# Issue #276047 — Reconsider/remove `ChatResponseStream#externalEdit`

[https://github.com/microsoft/vscode/issues/276047](https://github.com/microsoft/vscode/issues/276047)

## Summary

Keep open: externalEdit remains exposed and actively used, and its implementation still follows the distinct attribution and disk-reload path questioned here. This needs an API migration decision, not a completed or duplicate close.

## Change summary

Reconsider or remove ChatResponseStream.externalEdit in favor of structured text edits that preserve normal user-versus-agent edit handling.

## Best solution

Agree on a supported structured-edit contract for external agents and migrate existing consumers without losing edit review, undo grouping, or concurrent user edits. Coordinate with the related applyEdit proposal, but retain this issue's distinct API cleanup scope.

- **Validation:** The plan should define executable coverage for an external-agent edit with intervening user typing: verify correct agent attribution, preservation of the user's edits, and working Keep/Undo and undo-stop grouping. Exercise the migrated Copilot CLI consumer, and retain the existing ExternalEditTracker and permissionHelpers test coverage where applicable.
- **Behavior:**

  > External agents should participate in the normal tracked-edit model without a competing callback API that classifies intervening user changes as agent changes or relies on reloading the edited document from disk. Existing external-agent integrations must retain native edit review and undo grouping through the agreed replacement contract. Acceptance must cover agent changes interleaved with user typing and verify that rejecting agent changes preserves the user's independent edits.
- **Trace:**

  > The proposed declaration in src/vscode-dts/vscode.proposed.chatParticipantAdditions.d.ts still exposes externalEdit beside textEdit. ExtHostChatAgents2 wraps callbacks in externalEdits messages, and MainThreadChatAgents2 forwards them to ChatEditingSession.startExternalEdits/stopExternalEdits. That session path saves and reloads document state, while ChatEditingTextModelChangeService._mirrorEdits bypasses its normal user-edit branch when external edits are in progress. ExternalEditTracker in extensions/copilot/src/extension/chatSessions/common/externalEditTracker.ts actively depends on this lifecycle and its returned undo-stop ID; Copilot CLI permission handling is a concrete consumer. Internal externalEdit progress parts are a separate surface and should not be removed merely because they share the name. The issue proposes textEdit as the replacement, while the later discussion at https://github.com/microsoft/vscode/issues/279040 raises token-associated workspace.applyEdit as a related direction; the supported replacement and migration boundary remain to be settled.
- **Open decisions:**
  - Should external agents submit structured changes through ChatResponseStream.textEdit as proposed here, or should the supported replacement be token-associated workspace.applyEdit coordinated with the related proposal?
  - Should externalEdit be removed once its current consumers migrate, or remain temporarily available with an explicit deprecation contract?
