# Issue #339918 — Agents window: worktree size scanning, high renderer CPU/memory, and hours-old AHP log backlog

[https://github.com/microsoft/vscode/issues/339918](https://github.com/microsoft/vscode/issues/339918)

## Summary

Team-authored (hediet, MEMBER) and not yet fixed — hard keep-open rule applies regardless, but the trace is also solid: current main still has unbounded per-file fan-out in getWorktreeDiskUsage and a non-cancelling raceTimeout, matching the report exactly.

## Change summary

In a long-lived Agents window, client-side worktree disk-usage scanning and AHP transport logging drive high renderer CPU/memory and a growing AHP log backlog, because the traversal has unbounded per-file RPC fan-out and the timeout around it doesn't actually cancel the underlying work.

## Best solution

Give worktreeDiskUsage.ts's traversal a real cancellation token (threaded through resourceList/resourceResolve) so sessionWorktreeCleanupService.ts's raceTimeout actually stops in-flight work instead of merely stopping to wait on it, and bound per-directory resourceResolve concurrency; separately bound/throttle AhpJsonlLogger's pending queue.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/providers/agentHost/browser/worktreeDiskUsage.ts`, `src/vs/sessions/contrib/sessionInputBanners/browser/sessionWorktreeCleanupService.ts`, `src/vs/base/common/async.ts`, `src/vs/platform/agentHost/common/ahpJsonlLogger.ts`
- **Validation:** A targeted repro: open an Agents window with several large (node_modules-heavy) worktree sessions, trigger worktree size measurement, and verify via CPU/memory profile or a unit test that in-flight resourceResolve RPCs stop (not just the awaiting raceTimeout caller) once the 10s timeout fires, and that AHP log write latency stays bounded under sustained traffic.
- **Behavior:**

  > Background worktree-size measurement in the Agents window must have bounded per-directory RPC concurrency, must actually cancel in-flight resourceResolve/resourceList calls when a per-worktree timeout fires (not just stop awaiting them), and AHP transport logging must not accumulate an unbounded write backlog under sustained protocol traffic. Acceptance: after the timeout fires for a slow worktree, no further RPCs for that worktree are observed; CPU/memory stay bounded with multiple large worktrees; the AHP log drain keeps pace with event generation.
- **Trace:**

  > getWorktreeDiskUsage (worktreeDiskUsage.ts:22-56) batches 8 directories per round but issues an unbounded Promise.all of resourceResolve calls over every child in that batch, and accepts no cancellation token. sessionWorktreeCleanupService.ts:200 wraps this in raceTimeout (async.ts, ~line 155), which only races a timer against the original promise and never calls .cancel()/aborts it — confirmed by reading raceTimeout's implementation, which has no cancellation side effect on `promise`. ahpJsonlLogger.ts (~100-140) serializes every message synchronously and pushes to a `_pending` buffer drained asynchronously via a chained `_queue`, which is consistent with the reported CPU/GC time and log backlog but has not been confirmed as the source of the 10.34GiB commit (reporter did no heap-retention analysis). Do not touch the per-session Limiter(2) concurrency cap or the progress-reporting behavior added in https://github.com/microsoft/vscode/issues/339348 — those are out of scope. The report itself notes the full causal chain (why renderer memory hit 10GB, whether logging alone drives it) is not fully isolated.
- **Open decisions:**
  - Should getWorktreeDiskUsage accept and honor a CancellationToken end-to-end (through resourceList/resourceResolve calls to the agent host), or should raceTimeout itself be changed to call .cancel() on cancelable promises passed to it?
  - Should per-file resourceResolve concurrency within a directory batch be capped independently of the 8-directory batch size, and if so what's an acceptable worktree-scan latency bound for node_modules-heavy trees?
  - Is the AhpJsonlLogger buffering/backlog issue (partly already tracked by https://github.com/microsoft/vscode/issues/339657) in scope for this fix or should it be handled separately there?

## Evidence

- **unbounded fan-out confirmed on main:** src/vs/sessions/contrib/providers/agentHost/browser/worktreeDiskUsage.ts:35-50 — MAX_CONCURRENT_REQUESTS=8 only bounds the directory batch size; the inner `Promise.all(children.entries.map(...))` issues an unbounded number of concurrent resourceResolve calls per directory, with no cancellation token parameter anywhere in getWorktreeDiskUsage.
- **non-cancelling timeout confirmed on main:** src/vs/base/common/async.ts raceTimeout (~line 155) races the original promise against a timer-resolved promise; it never calls `.cancel()` or aborts the original promise, so sessionWorktreeCleanupService.ts:200's 10s timeout around getDiskUsage lets the traversal keep running and keep issuing RPCs after the limiter slot is freed.
- **buffered async drain confirmed on main:** src/vs/platform/agentHost/common/ahpJsonlLogger.ts:~100-140 serializes each message synchronously then pushes to `_pending` and schedules an async `_drainPending`, consistent with the reported buffering/backlog and CPU time in stringify/encode/concat.
- **reporter's own cross-build check:** Issue body states the same traversal/timeout code was checked on both the latest published Insiders build and current main (6308cbdc3d4c4c98e60269e18dada4771269b7d5) on Oct 5, both still exhibiting the per-file fan-out and non-cancelling timeout.
- **related narrower issue:** https://github.com/microsoft/vscode/issues/339657 (open, filed same day) covers only the AhpJsonlLogger CPU overhead; this issue is broader (adds the worktree traversal cancellation/concurrency problem and the 10GB memory/log-backlog symptoms), so 339657 is not a canonical for this report.
