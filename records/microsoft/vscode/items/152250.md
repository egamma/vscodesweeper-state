# Issue #152250 — SCM - Add drag and drop support within the Source Control views

[https://github.com/microsoft/vscode/issues/152250](https://github.com/microsoft/vscode/issues/152250)

## Summary

Keep this accepted, well-supported request open: current SCM drag support exports resources, but dropping them within Source Control still does nothing. This issue remains the canonical request for provider-controlled resource transfers.

## Change summary

Allow source control extensions to handle resources dragged between SCM groups, such as moving files between Perforce changelists.

## Best solution

Provide an opt-in SCM extension contract for accepting resource drops, leaving version-control operations to the provider. Preserve existing drag-out behavior and support both the Perforce changelist workflow and the staged/unstaged scenario consolidated here.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/scm/browser/scmViewPane.ts`, `src/vs/workbench/contrib/scm/common/scm.ts`, `src/vs/workbench/api/browser/mainThreadSCM.ts`, `src/vs/workbench/api/common/extHostSCM.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** Use a development extension contributing two SCM resource groups: drag one and multiple resources onto the other group and verify the provider receives the agreed resource identities and target and can update its groups. Verify rejected drops perform no operation, providers without the capability remain unchanged, and dragging resources into editor tabs and editor text still works. Add executable SCM bridge and drop-dispatch tests once the API contract is agreed.
- **Behavior:**

  > Extensions contributing Source Control providers need to accept resources dragged onto another SCM group, allowing operations such as moving files between Perforce changelists. The extension owns the version-control meaning of the transfer; core must not assume that every drop stages files or rebases commits. Acceptance should cover single-resource and multi-resource transfers, provider rejection, providers without drop support, and preservation of existing drag-out-to-editor behavior.
- **Trace:**

  > SCMTreeDragAndDrop in src/vs/workbench/contrib/scm/browser/scmViewPane.ts exports resource URIs in onDragStart but has an empty drop method. SourceControl and SourceControlResourceGroup in src/vscode-dts/vscode.d.ts offer no corresponding extension callback, unlike contributed TreeView drag-and-drop controllers. The provider-facing boundary includes ISCMProvider in src/vs/workbench/contrib/scm/common/scm.ts, MainThreadSCMProvider/MainThreadSCM in src/vs/workbench/api/browser/mainThreadSCM.ts, and ExtHostSourceControl/ExtHostSCM in src/vs/workbench/api/common/extHostSCM.ts. The missing behavior is established from source; uncertainty begins at the public transfer contract and which drop sources and targets it supports. Preserve existing resource export and keep repository operations provider-owned. https://github.com/microsoft/vscode/issues/183786 was explicitly consolidated here, while https://github.com/microsoft/vscode/issues/183587 covers only drag-out behavior.
- **Open decisions:**
  - Should the initial contract support only transfers between resource groups of the same provider, or also cross-provider and external-file drops?
  - Should the SCM contract reuse TreeDragAndDropController-style MIME/DataTransfer semantics, or expose SCM-specific resource and target identities?
  - Which SCM elements are valid drop targets in the initial contract: resource groups only, or individual resources and provider roots as well?
