# Issue #337553 — Agents Window: Add an extensible environment picker

[https://github.com/microsoft/vscode/issues/337553](https://github.com/microsoft/vscode/issues/337553)

## Summary

Team-authored (COLLABORATOR) design proposal for the Agents Window, filed hours ago with no discussion yet — keep open; it's a real, well-scoped architecture ask but not something to auto-close or blindly implement.

## Change summary

Add an explicit, extensible environment picker (Local/Remote/Cloud) to the Agents Window new-session flow, decoupled from source/workspace and agent/harness selection.

## Best solution

Design the environment concept as a first-class, provider-extensible selection alongside the existing WorkspacePicker/newSessionComposerService in src/vs/sessions/contrib/chat/browser, reusing the remoteAgentHost provider infrastructure that already distinguishes local vs. remote/tunnel workspaces.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts`, `src/vs/sessions/contrib/chat/browser/newSessionComposerService.ts`, `src/vs/sessions/contrib/providers/remoteAgentHost/browser/webTunnelAgentHostService.ts`
- **Validation:** A design review confirming the environment-provider contribution contract, followed by a WorkspacePicker/composer test asserting environment selection is modeled independently of workspace/source selection.
- **Behavior:**

  > Users creating a new Agents Window session can explicitly pick an environment (starting with Local and Remote) independent of which workspace/source and agent/harness they pick. The picker must be extensible so new environment types (e.g. cloud, containerized) can register availability, display info, connection actions, and capability constraints without redesigning the picker. Unsupported source/environment/harness combinations must be disabled with a visible reason rather than silently switching. The chosen environment is remembered and remains visible before launch and when restoring/inspecting a session, with keyboard and screen-reader support.
- **Trace:**

  > Today, environment (local vs. remote) is implicit in workspace/source selection: WorkspacePicker in src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts groups items by SESSION_WORKSPACE_GROUP_LOCAL/REMOTE/GITHUB, and newSessionComposerService.ts tracks NewSessionWorkspacePreselectionSource, but there is no separate environment concept or provider registry. Remote/tunnel/dev-container connectivity already exists under src/vs/sessions/contrib/providers/remoteAgentHost/. The scope boundary: this should introduce a new environment-provider abstraction and picker UI without restructuring the existing workspace/source picker's own selection semantics. Related but distinct: https://github.com/microsoft/vscode/issues/334563 (broader workspace picker direction) — that issue does not own this narrower environment-picker scope, so this stays a separate, open item.
- **Open decisions:**
  - Is the environment-provider contribution model a new extension API surface, or an internal-only registry for now?
  - How is the user's environment selection persisted (per-workspace, per-profile, or session-scoped) and does it survive session restore across machines?
  - Where does the environment picker live relative to the existing WorkspacePicker — a new top-level control, or a facet integrated into the current picker UI?

## Evidence

- **no existing environment concept:** src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts and newSessionComposerService.ts model source/workspace selection (SESSION_WORKSPACE_GROUP_LOCAL/REMOTE/GITHUB, NewSessionWorkspacePreselectionSource) but conflate environment with workspace source, matching the issue's stated motivation.
- **existing remote infra to build on:** src/vs/sessions/contrib/providers/remoteAgentHost/{browser,electron-browser}/* already implements tunnel/dev-container/cloud-sandbox agent host connectors, which a future environment-provider API would likely sit on top of.
