# Issue #132872 — Cannot properly run multiple instances of VS Code within separate RDP sessions

[https://github.com/microsoft/vscode/issues/132872](https://github.com/microsoft/vscode/issues/132872)

## Summary

Keep open: current startup routing still identifies the running instance by user-data directory rather than Windows session, matching the independently confirmed wrong-session launches. This older report should remain the tracking issue; the newer matching report is not a valid duplicate target.

## Change summary

Launching VS Code or using Open with Code in a second same-account RDP session opens the window or file in the first session.

## Best solution

Make application startup and shell file-opening respect the invoking Windows session while preserving ordinary same-session window reuse. Investigate safe user-data ownership and any Electron/Chromium constraints before introducing concurrent session-local processes.

## Plan brief

- **Likely files:** `src/vs/code/electron-main/main.ts`, `src/vs/platform/environment/electron-main/environmentMainService.ts`, `src/vs/base/parts/ipc/node/ipc.net.ts`, `src/vs/platform/launch/electron-main/launchMainService.ts`
- **Validation:** On Windows Server configured to allow multiple sessions per account, keep VS Code running in RDP session A, then launch it normally and use Explorer Open with Code in session B. Both actions must present their windows/files in B, including when A is disconnected. Repeat with --new-window, verify ordinary same-session reuse, and verify that concurrent sessions and subsequent restarts preserve user settings and recoverable edits.
- **Behavior:**

  > Two simultaneous RDP sessions using the same Windows account must each be able to launch and interact with VS Code in their own session. Opening a file through Explorer in session B must not send it to session A, including when A is disconnected. Normal same-session window reuse and explicit separate --user-data-dir instances must continue working. Acceptance requires a Windows multi-session check of both application launch and shell file opening, plus confirmation that concurrent sessions preserve settings and recoverable edits.
- **Trace:**

  > EnvironmentMainService.mainIPCHandle derives instance identity from the user-data directory and application version; createStaticIPCHandle generates a Windows named pipe without session identity. CodeMain.claimInstance connects a second launcher to the existing endpoint, forwards arguments through ILaunchMainService, and exits; LaunchMainService.startOpenWindow then opens the requested window in the owning process. This source path matches the independent confirmation at https://github.com/microsoft/vscode/issues/132872#issuecomment-1544447398 and the newer report at https://github.com/microsoft/vscode/issues/330184. Distinct --user-data-dir paths bypass the collision but are not transparent coverage for Explorer integration. The trace establishes forwarding, not the safety of multiple main processes sharing user-data files or the full Electron/Chromium constraints reflected by existing labels. The plan must establish that ownership boundary without changing unrelated virtual-desktop restoration or normal same-session reuse.
- **Open decisions:**
  - Should simultaneous same-account RDP sessions share one user-data profile with session-local window state, or receive separate session-specific user-data profiles with different settings and restoration semantics?

## Evidence

- **Current startup path:** src/vs/platform/environment/electron-main/environmentMainService.ts constructs mainIPCHandle from userDataPath, 'main', and the application version. src/vs/base/parts/ipc/node/ipc.net.ts:773-779 hashes the directory and produces a Windows named pipe without a Windows-session identifier. Same-account sessions using the default directory therefore select the same endpoint.
- **Wrong-session forwarding:** src/vs/code/electron-main/main.ts:352-392 binds that endpoint or connects to its existing owner on EADDRINUSE; lines 445-478 forward launch arguments to the existing process and terminate the new launcher. LaunchMainService.start/startOpenWindow in src/vs/platform/launch/electron-main/launchMainService.ts opens windows through that existing process. This explains both the second-session launch and Open with Code triggers; no runtime reproduction was performed.
- **Maintainer diagnosis:** https://github.com/microsoft/vscode/issues/132872#issuecomment-945623010 identifies the application's singleton nature as the underlying problem and leaves investigation open. Existing upstream/chromium labels indicate runtime concerns, but the checkout also exposes concrete VS Code-owned forwarding logic; an exclusively upstream cause is not established.
- **Confirmed reproduction and incomplete workaround:** https://github.com/microsoft/vscode/issues/132872#issuecomment-1544447398 independently confirms that opening a log file in session 2 sends it to session 1. https://github.com/microsoft/vscode/issues/132872#issuecomment-1128293173 suggests distinct --user-data-dir paths, while https://github.com/microsoft/vscode/issues/132872#issuecomment-1315173974 reports that this does not cover Open with Code.
