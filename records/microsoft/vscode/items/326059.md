# Issue #326059 — "Render whitespace" doesn't show NBSP

[https://github.com/microsoft/vscode/issues/326059](https://github.com/microsoft/vscode/issues/326059)

## Summary

Current main conclusively retains the reported gap: both whitespace-rendering paths recognize only ASCII spaces and tabs. Route this source-confirmed bug to the editor whitespace-rendering area.

## Change summary

Render non-ASCII whitespace such as NBSP, figure space, and ideographic space when `editor.renderWhitespace` is enabled.

## Best solution

Render the supported Unicode space characters consistently in both whitespace-rendering paths while preserving each character's display width and the existing `all`, `boundary`, `selection`, and `trailing` semantics. Cover narrow, full-width, and zero-width cases explicitly so whitespace visualization does not alter text layout.

- **Behavior:**

  > With `editor.renderWhitespace` enabled, Unicode space characters such as NBSP, figure space, and ideographic space should receive visible whitespace markers under the same positional rules as existing spaces. `selection`, `boundary`, and `trailing` must continue to limit markers according to their documented modes. Rendering a marker must not change cursor mapping, wrapping, or the visual width of narrow, fixed-width, full-width, or zero-width characters.
- **Trace:**

  > Current main has two relevant paths. `WhitespaceOverlay._applyRenderWhitespace` in src/vs/editor/browser/viewParts/whitespace/whitespace.ts immediately skips every code point except `CharCode.Tab` and `CharCode.Space`; the legacy `_applyRenderWhitespace` in src/vs/editor/common/viewLayout/viewLineRenderer.ts performs the same classification and later assumes every non-tab whitespace token is U+0020. Boundary and trailing calculations call `firstNonWhitespaceIndex` and `lastNonWhitespaceIndex` from src/vs/base/common/strings.ts, whose intentionally ASCII-oriented definitions also recognize only spaces and tabs. Existing tests in src/vs/editor/test/browser/view/whitespace.test.ts and src/vs/editor/test/common/viewLayout/viewLineRenderer.test.ts cover only U+0020 and tabs. The boundary is whitespace visualization: indentation, trimming, tokenization, cursor mapping, and the underlying document characters must not change.
- **Open decisions:**
  - Which Unicode property defines the supported set: `White_Space`, `Space_Separator`, or an explicit subset that excludes line separators and U+FEFF?
  - Should all supported spaces use the existing dot marker, or should wide and zero-width characters have distinct marker geometry?
  - Should boundary and trailing classification use a renderer-specific Unicode predicate, or should the shared ASCII-oriented string predicates change for all callers?

## Evidence

- **current source:** `WhitespaceOverlay._applyRenderWhitespace` in src/vs/editor/browser/viewParts/whitespace/whitespace.ts skips every character except `CharCode.Tab` and `CharCode.Space`, so the default SVG renderer cannot mark U+00A0, U+2007, or U+3000.
- **legacy renderer:** `_applyRenderWhitespace` in src/vs/editor/common/viewLayout/viewLineRenderer.ts likewise treats only tabs and U+0020 as renderable whitespace; its rendering branch explicitly assumes a non-tab whitespace character must be `CharCode.Space`.
- **mode semantics:** src/vs/base/common/strings.ts implements `firstNonWhitespaceIndex` and `lastNonWhitespaceIndex` using only U+0020 and tabs, so non-ASCII spaces are also excluded from boundary and trailing classification.
- **documented expectation:** The `editor.renderWhitespace` registration in src/vs/editor/common/config/editorOptions.ts says it controls rendering of “whitespace characters,” without restricting that behavior to ASCII spaces and tabs.
- **confirmed current behavior:** The reporter reproduced the behavior with extensions disabled in VS Code 1.129.0 and Insiders 1.130.0, and supplied a test document covering several Unicode whitespace characters.
