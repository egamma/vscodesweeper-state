# Issue #262610 — Edit telemetry causes serious typing lag on large-ish documents

[https://github.com/microsoft/vscode/issues/262610](https://github.com/microsoft/vscode/issues/262610)

## Summary

Still reproduces on main: the edit telemetry tracker accumulates an ever-growing `AnnotatedStringEdit` via repeated `compose()` calls in `editTracker.ts`, causing O(n) work per keystroke on large documents. No fix has been committed since the issue was filed. The issue is assigned to hediet and milestoned On Deck — keeping open.

## Change summary

Edit telemetry causes 0.5–1 second typing lag on very large documents (e.g. the WHATWG HTML spec source file) because the edit tracker composes each keystroke with a growing edit history.

## Best solution

The `DocumentEditSourceTracker` in `src/vs/workbench/contrib/editTelemetry/browser/telemetry/editTracker.ts` should either cap the accumulated edit history, batch/debounce composition, or use a more efficient data structure so that per-keystroke cost does not grow linearly with session length. The windowed trackers (10/20-min focus windows) partially bound the problem but do not prevent lag within a single window on a very large document.

## Evidence

The compose() method in src/vs/editor/common/core/edits/edit.ts iterates all accumulated replacements (O(n+m) per call), so cost grows with session length.
- **no fix on main:** git log --since=2025-08-21 and git log --grep=262610 show no commits addressing this issue. The edit telemetry compose path is unchanged.
- **PR #258218 context:** cc1d3b609e0 (July 2025) disabled edit telemetry entirely to fix a memory leak. It was re-enabled, and the reporter saw the lag reappear in 1.103.1 (August 2025). The underlying per-edit cost was never addressed.
- **10/20-min windows:** cfbaed1c842 (Feb 2026) changed the windowed trackers to 10/20-minute focus windows, which bounds session length but does not prevent lag within a window when editing a very large document with many keystrokes.
