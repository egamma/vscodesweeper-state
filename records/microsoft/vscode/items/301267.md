# Issue #301267 — Support creating a new CLI session with the same folder/worktree

[https://github.com/microsoft/vscode/issues/301267](https://github.com/microsoft/vscode/issues/301267)

## Summary

Keep open: current code supports shared worktrees through session forking and explicit folder selection, but those paths do not establish that creating a fresh CLI session from an existing session's worktree is fully covered. The matching open request is newer, so it cannot replace this re-reviewed issue as the canonical.

## Change summary

Allow a new independent Copilot CLI session to use the folder or worktree already used by another session.

## Best solution

Provide a discoverable way to start a fresh CLI conversation in an existing worktree without creating another worktree or inheriting conversation history. Retain this older issue as the tracking point and coordinate the overlapping request at https://github.com/microsoft/vscode/issues/309027.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/chatSessions/vscode-node/copilotCLIChatSessions.ts`, `extensions/copilot/src/extension/chatSessions/vscode-node/folderRepositoryManagerImpl.ts`, `extensions/copilot/src/extension/chatSessions/vscode-node/sessionOptionGroupBuilder.ts`, `src/vs/sessions/contrib/chat/browser/newSessionAction.ts`
- **Validation:** Create a CLI session with worktree isolation, make a recognizable file change, then start a fresh CLI session targeting that same worktree. Verify distinct session identities, no inherited conversation turns, identical working directories, and visibility of the existing file change. Remove either session and verify the remaining session can still use the worktree.
- **Behavior:**

  > A user who has already worked in a CLI session's worktree can start another independent conversation in that exact directory. The new conversation does not inherit the original conversation's turns and does not create a replacement worktree. Both sessions see the same filesystem state, and removing one must not invalidate the other's working directory. Ordinary creation of a separately isolated session and existing conversation-fork behavior remain available.
- **Trace:**

  > CopilotCLIChatSessions registers a forkHandler in extensions/copilot/src/extension/chatSessions/vscode-node/copilotCLIChatSessions.ts, passing the existing workspace into forkSession; this is a related capability rather than a demonstrated fresh-conversation path. FolderRepositoryManagerImpl already recognizes explicitly selected folders associated with existing worktrees through metadataStore.getWorktreeSessions, while SessionOptionGroupBuilder.getRepositoryOptionItems filters worktrees out of the repository list. NewChatInSessionsWindowAction in src/vs/sessions/contrib/chat/browser/newSessionAction.ts inherits activeSession.workspace.uri, but this inspection did not establish that it preserves an existing isolated worktree through the full provider creation flow. Preserve trust checks, ordinary isolation behavior, fork semantics, and shared-worktree lifecycle protections. https://github.com/microsoft/vscode/issues/309027 asks for the same fresh-session experience but is newer; https://github.com/microsoft/vscode/issues/316862 provides acceptance precedent for preserving a worktree while another session uses it.
- **Open decisions:**
  - Should existing-worktree reuse be exposed as an explicit action on a session, as a selectable destination in the new-session picker, or both?
