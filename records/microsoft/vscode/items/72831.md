# Issue #72831 — FileSystemWatcher fires events to extensions before text documents are updated

[https://github.com/microsoft/vscode/issues/72831](https://github.com/microsoft/vscode/issues/72831)

## Summary

Keep open for an API-contract decision: current source still forwards file-system events independently of asynchronous document reloads. Existing document-change events cover the external-edit workaround, but do not settle the deletion/recreation concerns; this team-authored report has neither a verified fix nor an eligible canonical duplicate.

## Change summary

Provide a reliable way for extensions reacting to external file changes to obtain synchronized document contents and handle deletion/recreation without stale document state.

## Best solution

Resolve the synchronization contract in the extension API while preserving low-level watcher delivery and dirty-document contents. Evaluate the maintainer-suggested document-level notification approach, and separately retest the supplied deletion/recreation example before deciding whether it needs a distinct bug.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/browser/mainThreadFileSystemEventService.ts`, `src/vs/workbench/api/common/extHostDocuments.ts`, `src/vs/workbench/services/textfile/common/textFileEditorModelManager.ts`
- **Validation:** Run the sample from https://github.com/microsoft/vscode/issues/72831#issuecomment-486783062 against a development extension host, editing the file externally and recording watcher delivery, document-change delivery, and document contents. Separately run the deletion/recreation sample from https://github.com/microsoft/vscode/issues/72831#issuecomment-488066991 twice and check the Replace prompt and resulting disk contents. Validate the chosen contract without delaying existing watcher delivery or overwriting dirty documents.
- **Behavior:**

  > An extension receives a file watcher notification for an external edit and can observe the previous contents through openTextDocument because the document reload has not completed. Existing onDidChangeTextDocument subscriptions provide a workaround for already-known documents, but the thread also reports deletion/recreation and save-prompt problems. The finished design should give extension authors a defined way to observe synchronized document state without changing low-level watcher timing or discarding unsaved edits. Acceptance must cover external edits and establish separately whether the supplied deletion/recreation behavior still occurs.
- **Trace:**

  > MainThreadFileSystemEventService forwards onDidFilesChange directly to the extension host, while TextFileEditorModelManager.onDidFilesChange independently queues asynchronous reloads. ExtHostDocuments.ensureDocumentData immediately returns an existing cached document, consistent with the documented openTextDocument contract. The maintainers confirmed this ordering at https://github.com/microsoft/vscode/issues/72831#issuecomment-486966129 and opposed delaying watcher events; the C/C++ workaround in https://github.com/microsoft/vscode-cpptools/pull/3545 changes consumers rather than the core contract. The deletion sample uses an associated untitled URI and must not be assumed to share the same cause as the external-edit race. Preserve document identity, dirty-buffer contents, and existing watcher timing; uncertainty starts at which additional observable guarantee, if any, the API should expose.
- **Open decisions:**
  - Should the supported contract remain the existing combination of file-system and document-change events with clearer guidance, or should extensions receive a new document-level notification that distinguishes synchronization after external disk changes?

## Evidence

- **Maintainer diagnosis and intended boundary:** https://github.com/microsoft/vscode/issues/72831#issuecomment-486966129 confirms the original race, explicitly classifies it as a feature request, and suggests a document-level notification rather than delaying file-system events. https://github.com/microsoft/vscode/issues/72831#issuecomment-486968093 likewise rejects pausing watcher events.
- **Current source retains independent delivery:** src/vs/workbench/api/browser/mainThreadFileSystemEventService.ts:53-59 forwards IFileService.onDidFilesChange directly through $onFileEvent. Independently, src/vs/workbench/services/textfile/common/textFileEditorModelManager.ts:122-133 queues model reloads, and lines 169-183 and 338-350 perform asynchronous reload work. Watcher delivery does not await those reloads.
- **Existing-capability check:** src/vs/workbench/api/common/extHostDocuments.ts:81-85 still returns cached document data immediately. src/vscode-dts/vscode.d.ts:14157-14170 documents early return for already-open documents, and lines 14294-14299 expose onDidChangeTextDocument. That event supports the external-edit workaround, but onDidDeleteFiles at lines 14443-14449 explicitly excludes external disk changes and workspace.fs operations, so it is not a complete answer to the deletion scenario.
