# Issue #333316 — [Research/Bug] Environment block crossing the OS ⇄ JS-object boundary lacks a validation contract — one class of "invalid env" failures (invalid keys, case semantics, NUL/=/undefined) reaching the utility-process boundary

[https://github.com/microsoft/vscode/issues/333316](https://github.com/microsoft/vscode/issues/333316)

## Summary

Well-researched and code-confirmed: `createEnv()` in utilityProcess.ts inherits `process.env` and only strips a denylist of dangerous values via `removeDangerousEnvVariables`, never validating key-name legality, so a single illegal key (e.g. a leading-digit var left by some Windows installers) can throw at `fork()` and silently kill the whole utility-process stack. There's already an open PR proposing the exact fix, so this should stay open for that PR to land rather than being auto-closed.

## Change summary

Requests a validation contract on env keys crossing the OS↔JS boundary before forking utility processes, since illegal-but-OS-legal key names (and related NUL/`=`/undefined/case-folding edge cases) currently reach `spawn()` unvalidated and can crash child-process startup.

## Best solution

Land (after review) the linked PR https://github.com/microsoft/vscode/pull/333333, which adds `isValidEnvVariableKey()` in src/vs/platform/utilityProcess/common/envKey.ts and filters the inherited env in `createEnv()` (src/vs/platform/utilityProcess/electron-main/utilityProcess.ts) before forking — that directly closes the key-name gap described here; the other listed edge cases (NUL, embedded `=`, undefined round-trip, Windows case folding) can be tracked as follow-ups if not covered by that PR.
