# Issue #56356 — [api] Allow extensions to use the syntax highlighter 

[https://github.com/microsoft/vscode/issues/56356](https://github.com/microsoft/vscode/issues/56356)

## Summary

Keep open: current source exposes theme-aware syntax highlighting through a proposed API, but not through the stable extension API. The request has 60 upvotes and explicit maintainer interest; the remaining work is agreeing and finalizing the public contract, not replacing it with another bundled highlighter.

## Change summary

Expose VS Code's installed-language syntax highlighting and active theme to extensions for rendering consistent code samples in webviews and notebook renderers.

## Best solution

Provide a supported stable extension API for highlighting arbitrary code with installed grammars and the active theme, building on the existing documentSyntaxHighlighting proposal. API owners should settle whether styled token data sufficiently serves consumers or whether the contract should also provide rendered HTML/CSS.

- **Validation:** In a development extension, highlight a multiline sample using an installed language grammar and render it in a webview. Verify active-theme colors and font styles, preservation of the exact input text, embedded-language handling, and refresh after a theme change. The finalized API must be usable without proposed-API enablement; verify unknown-language and empty-input behavior against the agreed contract.
- **Behavior:**

  > Extensions need a supported way to render arbitrary code samples using VS Code's installed languages and active syntax-color theme rather than shipping independent grammar/theme reconstruction. A webview or notebook renderer must preserve the sample text and obtain enough highlighting information to present consistent code. Theme changes must allow consumers to refresh existing content. Acceptance includes multiline and embedded-language samples, empty input, an unavailable grammar, and use without proposed-API privileges.
- **Trace:**

  > The checkout already contains documentSyntaxHighlighting in src/vscode-dts/vscode.proposed.documentSyntaxHighlighting.d.ts. MainThreadLanguages.$computeFullSyntaxHighlighting in src/vs/workbench/api/browser/mainThreadLanguages.ts uses installed TextMate grammars and the token color map; ExtHostLanguages forwards the result and theme-change event. Both public members are explicitly proposal-gated in src/vs/workbench/api/common/extHost.api.impl.ts and absent from stable vscode.d.ts. The implementation returns styled runs rather than HTML/CSS and does not use semantic-token providers, so full editor-color equivalence should not be assumed. Preserve existing editor tokenization and unrelated Markdown rendering behavior. https://github.com/microsoft/vscode/issues/91279 is a related consumer request, not a canonical for this broader API gap. The uncertainty starts at the supported public output contract and whether its guarantees stop at TextMate syntax highlighting.
- **Open decisions:**
  - Should the stable API return styled tokens and a color map, as the current proposal does, or also directly provide the HTML/CSS requested for webview and notebook consumers?
  - Should the public contract guarantee TextMate syntax highlighting only, or include semantic highlighting when available?

## Evidence

- **Requested boundary and demand:** https://github.com/microsoft/vscode/issues/56356 requests syntax highlighting for extension webviews, including the user's theme and installed languages. The issue has 60 upvotes and is accepted into Backlog. The January 2023 comment requests code-string/language-ID input and HTML/CSS output for both webviews and notebook renderers.
- **Existing capability is proposed, not stable:** src/vscode-dts/vscode.proposed.documentSyntaxHighlighting.d.ts declares languages.computeFullSyntaxHighlighting(source, languageId), returning token lengths, foreground color-map indices, font styles, and a color map, plus onDidChangeSyntaxHighlighting. src/vs/workbench/api/common/extHost.api.impl.ts gates both members with checkProposedApiEnabled(extension, 'documentSyntaxHighlighting'); neither appears in src/vscode-dts/vscode.d.ts. This is substantive progress but does not provide the requested stable API to ordinary extensions.
- **Implementation trace:** MainThreadLanguages.$computeFullSyntaxHighlighting in src/vs/workbench/api/browser/mainThreadLanguages.ts obtains the TokenizationRegistry color map, resolves the language, creates its installed TextMate tokenizer, and returns styled runs. Theme changes are forwarded through ExtHostLanguages.$acceptSyntaxHighlightingThemeChanged in src/vs/workbench/api/common/extHostLanguages.ts. The path returns tokens rather than rendered HTML and does not invoke semantic-token providers.
