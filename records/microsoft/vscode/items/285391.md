# Issue #285391 — Support file nesting across separate directories (e.g., src/.cpp under include/.h for C++ projects)

[https://github.com/microsoft/vscode/issues/285391](https://github.com/microsoft/vscode/issues/285391)

## Summary

A real cross-directory file-nesting gap remains on current main. The request should stay open and be routed to file nesting; the two older reports describe the same limitation but are closed and therefore cannot serve as duplicate canonicals.

## Change summary

Allow Explorer file-nesting patterns to group related files located in separate directories, such as include/foo.h and src/foo.cpp.

## Best solution

Extend explicit file-nesting patterns to resolve relative child paths across the workspace tree while preserving each child's real resource identity. Keep CMake auto-detection outside the initial scope unless maintainers separately choose an automatic convention.

## Vision fit

- **Fit:** aligned
- **Reason:** Cross-directory nesting improves the Explorer's representation of common project layouts without adding always-on UI or bundled language-specific behavior.
- **Evidence:** Durable themes: Workbench & core UX and the developer inner loop; the explicit configuration also preserves the guardrail of a lightweight default experience.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/common/explorerModel.ts`, `src/vs/workbench/contrib/files/common/explorerFileNestingTrie.ts`, `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `src/vs/workbench/contrib/files/test/browser/explorerModel.test.ts`, `src/vs/workbench/contrib/files/test/browser/explorerFileNestingTrie.test.ts`
- **Validation:** Add an Explorer model test with sibling include/ and src/ directories asserting that a pattern such as "*.h": "../src/${basename}.cpp" presents src/foo.cpp under include/foo.h while retaining the child's src/foo.cpp resource, and that ordinary same-directory nesting remains unchanged.
- **Behavior:**

  > An explicit file-nesting child pattern may refer to a file outside the parent file's directory using a relative path. With include/foo.h and src/foo.cpp, configuring "*.h": "../src/${basename}.cpp" visually groups the source file under the header while commands on the child continue to target src/foo.cpp. Existing same-directory patterns and workspaces without such patterns remain unchanged. Automatic CMake detection is not required for the central request.
- **Trace:**

  > ExplorerItem.fetchChildren in src/vs/workbench/contrib/files/common/explorerModel.ts currently invokes ExplorerFileNestingTrie.nest with only immediate non-directory child names and then resolves matches from the same item's children map. ExplorerFileNestingTrie in src/vs/workbench/contrib/files/common/explorerFileNestingTrie.ts consequently operates on names rather than resources or a workspace hierarchy. The configuration schema in src/vs/workbench/contrib/files/browser/files.contribution.ts documents only directory-local behavior. Existing tests exercise filename matching in explorerFileNestingTrie.test.ts; the cross-directory acceptance case needs an Explorer model hierarchy in explorerModel.test.ts. Related closed reports are https://github.com/microsoft/vscode/issues/194567 and https://github.com/microsoft/vscode/issues/251501. Preserve resource identity, filesystem case handling, and all existing same-directory nesting semantics.
- **Open decisions:**
  - Should a cross-directory nested child disappear from its physical source directory as same-directory nested children do, or remain visible there and also appear beneath the configured parent?

## Evidence

- **current source limitation:** In src/vs/workbench/contrib/files/common/explorerModel.ts, ExplorerItem.fetchChildren partitions only the current directory's immediate children, passes only their names to ExplorerFileNestingTrie.nest, and resolves matches through this.children.get(name). A file under sibling directory src/ is therefore unavailable while nesting children of include/.
- **matcher boundary:** src/vs/workbench/contrib/files/common/explorerFileNestingTrie.ts accepts filename strings plus one dirname token and returns name-to-name relationships; it has no workspace-tree or resource-path lookup capable of resolving ../src/foo.cpp.
- **configuration contract:** src/vs/workbench/contrib/files/browser/files.contribution.ts describes file nesting as grouping related files 'in a directory' and documents filename substitutions, but no relative-path semantics.
- **closed related reports:** https://github.com/microsoft/vscode/issues/194567 and https://github.com/microsoft/vscode/issues/251501 report the same cross-directory limitation, but both were closed by the feature-request upvote lifecycle rather than fixed; neither can be the canonical target for a duplicate close.
- **canonical search:** A repository issue search for open file-nesting and cross-directory requests found no older open issue with the same reporter-observable symptom; the unrelated external PR in the timeline provides no VS Code implementation evidence.
