# Issue #580 — Can I get scope / scopeRange at a position?

[https://github.com/microsoft/vscode/issues/580](https://github.com/microsoft/vscode/issues/580)

## Summary

Keep open as the canonical request for extension access to grammar scopes and token ranges. Current APIs and developer tools provide only partial coverage, and the accepted Backlog request has substantial demand with 89 upvotes.

## Change summary

Expose grammar-derived token ranges and scope names at a document position through the extension API.

## Best solution

Design a supported token-context API that addresses positional ranges and grammar scope information without requiring extensions to retokenize documents independently. API owners should settle the exposed contract, tokenizer independence, and document-version consistency before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.tokenInformation.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostLanguages.ts`, `src/vs/workbench/api/browser/mainThreadLanguages.ts`, `src/vs/workbench/services/textMate/browser/tokenizationSupport/textMateTokenizationSupport.ts`
- **Validation:** After API owners choose the contract, add extension-host API tests using a contributed grammar that treats attrib-name as one token: querying inside either side of the hyphen must return the agreed grammar-derived range and scope/context information. Include edits between requests and responses, missing grammars, and comment/string contexts; verify results follow the chosen document-version and availability semantics.
- **Behavior:**

  > Extensions cannot currently obtain supported grammar scope names and corresponding token ranges at a document position. The original example requires attrib-name to be recognized as the grammar token rather than two words separated by a hyphen. A supported API should make the agreed scope/context information available without requiring each extension to independently parse the document. Acceptance must distinguish grammar-derived information from word regexes, theme colors, and incomplete semantic-token coverage, and define behavior when tokenization or document versions change.
- **Trace:**

  > TextDocument.getWordRangeAtPosition is documented as word-definition or regex based, not grammar based. ExtHostLanguages.tokenAtPosition calls MainThreadLanguages.$tokensAtPosition, which reads line-token offsets and StandardTokenType; its exposed declaration is deprecated and proposed-only, and contains no scope names. The documentSyntaxHighlighting proposal returns styling runs for supplied text, while captureSyntaxTokens independently invokes a grammar and the inspection command displays scopes in a widget. The boundary is a supported extension API and its tokenization access, not changing word-range semantics, themes, or semantic token providers. Maintainer discussion records grammar-coupling, representation, performance, and asynchronous consistency concerns, so the source trace establishes the gap but not an approved public contract. https://github.com/microsoft/vscode/issues/91555 was consolidated into https://github.com/microsoft/vscode/issues/580 and is related design history, not a replacement canonical.
- **Open decisions:**
  - Should the supported API expose TextMate scope stacks and grammar-derived ranges, or tokenizer-independent context information, and what information would satisfy the original custom-grammar use case?
  - What document-version and tokenization-availability guarantees should callers receive, including whether incomplete or stale results are permitted?

## Evidence

- **Existing word-range capability is incomplete:** src/vscode-dts/vscode.d.ts documents TextDocument.getWordRangeAtPosition(position, regex?) as separator-, language-word-definition-, or regex-based. The custom regex suggested in the discussion can include the hyphen in attrib-name, but does not return grammar scope names or grammar-derived token boundaries.
- **Positional token API remains proposed and narrower:** src/vscode-dts/vscode.proposed.tokenInformation.d.ts declares a deprecated languages.getTokenInformationAtPosition returning only StandardTokenType and Range. src/vs/workbench/api/common/extHost.api.impl.ts:798-800 gates it behind tokenInformation; MainThreadLanguages.$tokensAtPosition in src/vs/workbench/api/browser/mainThreadLanguages.ts:65-77 returns standard token classification and offsets, not TextMate scopes.
- **New highlighting proposal does not expose scopes:** src/vscode-dts/vscode.proposed.documentSyntaxHighlighting.d.ts exposes languages.computeFullSyntaxHighlighting(source, languageId), whose tokens contain length, foreground, and fontStyle. It tokenizes supplied text and exposes visual runs, not document-position scope information or access to existing document tokenization.
- **Developer tools are not the requested API:** src/vs/workbench/contrib/codeEditor/browser/inspectEditorTokens/inspectEditorTokens.ts provides Developer: Inspect Editor Tokens and Scopes as an editor widget. src/vs/workbench/contrib/themes/browser/themes.test.contribution.ts:358-371 implements captureSyntaxTokens by creating a grammar tokenizer and tokenizing supplied content; this internal testing facility is not a supported positional document API.
- **Maintainer acceptance and architectural concerns:** https://github.com/microsoft/vscode/issues/580#issuecomment-219539766 confirms the request remains on the backlog. https://github.com/microsoft/vscode/issues/580#issuecomment-253758584 describes substantial internal scope-representation work; https://github.com/microsoft/vscode/issues/580#issuecomment-273740251 distinguishes the inspection tool from an extension API and raises grammar-coupling concerns.
- **Canonical direction verified:** https://github.com/microsoft/vscode/issues/91555 is closed explicitly as a duplicate of this issue in https://github.com/microsoft/vscode/issues/91555#issuecomment-644171218. https://github.com/microsoft/vscode/issues/100484 is also closed and its discussion identifies this issue as the possible duplicate target. Searches for TextMate scope APIs found no verified older open issue with the same observable request; broader tokenizer and tree-sitter initiatives do not supersede it.
- **Workarounds and demand:** The provided discussion identifies HyperScopes and vscode-textmate-languageservice as workarounds, including positional scope/range methods, but also reports duplicate parsing and extension-host delays. https://github.com/microsoft/vscode/issues/580#issuecomment-1442873691 describes independent full-document tokenization. These do not establish access to VS Code's existing tokenization through a supported API; 89 body upvotes support retaining the accepted request.
