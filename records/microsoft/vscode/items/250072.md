# Issue #250072 — Minimap overlaps content by the width of the vertical scrollbar

[https://github.com/microsoft/vscode/issues/250072](https://github.com/microsoft/vscode/issues/250072)

## Summary

This remains a confirmed editor layout bug on current main. The linked fix attempt was closed unmerged after it introduced a scrollbar-position regression, so the issue still needs a corrected layout approach.

## Change summary

The right-side minimap overlaps the editor content by the configured vertical scrollbar width.

## Best solution

Correct the editor layout contract so content ends before the right-side minimap while the vertical scrollbar remains anchored consistently when the minimap is toggled.

## Plan brief

- **Likely files:** `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/browser/viewParts/editorScrollbar/editorScrollbar.ts`, `src/vs/editor/test/browser/config/editorLayoutProvider.test.ts`
- **Validation:** Add editor layout unit coverage for a right-side minimap with a nonzero vertical scrollbar width, including toggling the minimap, and verify that content and minimap extents do not overlap while the scrollbar's right-edge position remains unchanged.
- **Behavior:**

  > With the minimap on the right and a nonzero vertical scrollbar width, editor content must stop before the minimap rather than render beneath it. Toggling the minimap must not shift the vertical scrollbar away from the editor's right edge. Left-side minimap behavior and layouts with the scrollbar width set to zero must remain unchanged.
- **Trace:**

  > EditorLayoutInfoComputer in src/vs/editor/common/config/editorOptions.ts places a right-side minimap before the scrollbar but calculates `contentWidth` without subtracting that scrollbar offset, producing the reported overlap. EditorScrollbar._setLayout in src/vs/editor/browser/viewParts/editorScrollbar/editorScrollbar.ts then derives its container width from the same content width and the minimap width. The attempted correction in https://github.com/microsoft/vscode/pull/250315 changed both calculations, but maintainer testing found that it moved the scrollbar when the minimap was toggled, and the PR was closed unmerged. The boundary is the editor layout geometry: scrollbar anchoring, left-side minimaps, wrapping calculations, and existing content-width consumers must not regress.
- **Open decisions:**
  - Which layout quantity should represent the scrollbar-excluded content extent without changing the established meaning of `contentWidth` for its other consumers?
  - Should the correction live entirely in layout computation, in the scrollbar/minimap view sizing, or require a distinct geometry value shared by both?

## Evidence

- **confirmed reproduction:** A VS Code team member confirmed reproducing the issue in https://github.com/microsoft/vscode/issues/250072#issuecomment-2929441594.
- **current source:** On current main, src/vs/editor/common/config/editorOptions.ts computes the right-side `minimapLeft` as `outerWidth - minimapWidth - verticalScrollbarWidth`, while `contentWidth` remains `remainingWidth - minimapWidth`; those extents overlap by `verticalScrollbarWidth`.
- **closed fix attempt:** https://github.com/microsoft/vscode/pull/250315 attempted to account for the offset but was closed without merging after testing showed that toggling the minimap moved the vertical scrollbar.
- **layout coupling:** src/vs/editor/browser/viewParts/editorScrollbar/editorScrollbar.ts sizes the scrollbar container from `contentWidth` plus the right-side minimap width, so changing the shared content-width value also affects scrollbar placement.
