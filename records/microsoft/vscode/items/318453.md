# Issue #318453 — Should detect body overflow before preview on gh

[https://github.com/microsoft/vscode/issues/318453](https://github.com/microsoft/vscode/issues/318453)

## Summary

A real gap remains in the issue-reporting wizard: its URL-size fallback does not ensure that the body copied for manual pasting stays within GitHub's 65,536-character limit. This team-authored, On Deck request should remain open for an explicit overflow UX decision.

## Change summary

Detect an issue body that exceeds GitHub's character limit before opening the GitHub preview.

## Best solution

Have the issue reporter validate the complete generated body before preview and provide an accessible recovery path that produces a GitHub-acceptable body without silently discarding user content.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/issue/browser/issueFormService.ts`, `src/vs/workbench/contrib/issue/browser/issueReporterOverlay.ts`, `src/vs/workbench/contrib/issue/test/browser/issueReporterOverlay.test.ts`
- **Validation:** Add targeted issue-reporter tests covering bodies immediately below and above 65,536 characters, including an oversized user description and oversized generated diagnostic data; the accepted path must never send or instruct the user to paste a body above GitHub's limit.
- **Behavior:**

  > Before opening GitHub, the issue reporter detects when the complete generated issue body exceeds GitHub's 65,536-character limit. The user receives an accessible explanation and a recovery path that preserves the report without leading to GitHub's validation error. Bodies within the limit and the existing attachment-upload flow remain unchanged. Acceptance covers both an oversized user description and oversized generated diagnostic sections.
- **Trace:**

  > IssueReporterOverlay.buildIssueBody in src/vs/workbench/contrib/issue/browser/issueReporterOverlay.ts assembles the description and optional diagnostic sections, then IssueFormService.submitIssue in src/vs/workbench/contrib/issue/browser/issueFormService.ts appends media markdown and constructs the preview URL. The current MAX_URL_LENGTH branch may extract generated <details> blocks into issue-data.md, but its final fallback copies the original issueBody without checking GitHub's body-character limit. Preserve attachment upload, template selection, trusted-domain handling, and valid bodies below the limit. Any new validation message must follow the overlay's existing accessible error pattern, including an announced status or alert rather than color-only feedback.
- **Open decisions:**
  - When user-authored content alone exceeds GitHub's hard limit, should preview be blocked until the user shortens it, or should overflow content be preserved automatically in an uploaded attachment?
  - Should the limit be surfaced only when advancing to preview, or also as a live remaining-character indicator while composing the description?

## Evidence

- **current source:** src/vs/workbench/contrib/issue/browser/issueFormService.ts checks the encoded preview URL against MAX_URL_LENGTH = 7500 and, when still too large, copies the full issueBody to the clipboard. It does not validate issueBody against GitHub's 65,536-character body limit.
- **remaining failure path:** A user-authored description longer than GitHub's body limit is not removed by extractIssueData; submitIssue therefore copies the same oversized body and opens GitHub with instructions to paste it, where GitHub can still reject it.
- **existing mitigation:** The current extraction path can upload generated <details> sections as issue-data.md, but this only addresses generated diagnostic sections and URL size; it does not resolve an oversized user description.
