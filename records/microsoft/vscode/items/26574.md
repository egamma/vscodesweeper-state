# Issue #26574 — Find in Files "files to include" override .gitignore

[https://github.com/microsoft/vscode/issues/26574](https://github.com/microsoft/vscode/issues/26574)

## Summary

Keep open: include globs still override ignore-file rules in the current search implementation, and the cited ripgrep fix addresses a different path-handling problem. This accepted request has substantial demand, recent confirmations, and no verified canonical duplicate.

## Change summary

Allow Find in Files to narrow the search scope without overriding applicable .gitignore exclusions.

## Best solution

Make scoped search preserve ignore-file exclusions while retaining an explicit way to search ignored files. Settle compatibility for intentional includes of ignored paths before changing search query construction and ripgrep integration.

- **Behavior:**

  > Narrowing Find in Files to a subtree should retain applicable ignore-file exclusions rather than resurrect ignored generated files. Searching ignored files must remain possible through an explicit, agreed interaction. Acceptance should cover glob includes, directory scopes, nested ignore files, and multi-root searches without removing search-scope performance benefits.
- **Trace:**

  > getRgArgs in src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts emits positive -g arguments for include patterns; ripgrep documents these as overriding ignore logic. QueryBuilder.getFolderQueryForSearchPath in src/vs/workbench/services/search/common/queryBuilder.ts separately constructs directory-root queries, so directory scopes and glob scopes must not be treated as identical. search.useIgnoreFiles already defaults to true, but that setting does not override ripgrep's positive-glob precedence. The upstream commit https://github.com/BurntSushi/ripgrep/commit/c2f1653ddd37b76c82fb973673bf5bcc0888a1c1 fixes parent-ignore path construction, not this precedence contract. Current source was inspected without executing or modifying the checkout. Preserve explicit exclusion controls, legitimate ignored-file searches, and bounded traversal; the unresolved boundary is which include interactions should count as deliberate overrides.
- **Open decisions:**
  - With ignore handling enabled, should every include pattern preserve ignore-file exclusions, or should explicitly naming an ignored file or directory still override them? The thread contains users relying on both behaviors.

## Evidence

- **Current include-glob path:** src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts, getRgArgs, converts includes into positive -g arguments, including expanded directory components, and searches '.'. Enabling local ignore files does not change that glob precedence.
- **Dependency contract:** https://github.com/BurntSushi/ripgrep/blob/master/crates/core/flags/defs.rs documents --glob as always overriding other ignore logic. This explains the thread's concrete comparison between an ordinary search and rg with -g 'src/program_proof/**'; it is not evidence that ripgrep itself violates its intended behavior.
- **Existing capabilities are partial:** src/vs/workbench/contrib/search/browser/search.common.contribution.ts registers search.useIgnoreFiles, enabled by default, and search.useParentIgnoreFiles. QueryBuilder.getFolderQueryForSearchPath in src/vs/workbench/services/search/common/queryBuilder.ts also supports actual directory search roots. These are distinct from positive include globs and do not establish coverage of the full request. The thread's search.exclude workaround duplicates ignore rules rather than honoring .gitignore automatically.
- **Upstream fix does not cover this trigger:** https://github.com/BurntSushi/ripgrep/commit/c2f1653ddd37b76c82fb973673bf5bcc0888a1c1 changes parent-ignore absolute-path construction in crates/ignore/src/dir.rs. Its regression cases search directory arguments or change working directory; the diff does not change positive --glob precedence. It therefore cannot substantiate a completed close for this report.
