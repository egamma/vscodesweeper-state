# Issue #28636 — On highlight/select text - cannot unhighlight/deselect text on click - need to do ESC

[https://github.com/microsoft/vscode/issues/28636](https://github.com/microsoft/vscode/issues/28636)

## Summary

Keep open: current source still allows tiny pointer movement during a click to preserve the selection instead of deselecting it. Disabling drag and drop is only a workaround, and the newer related report does not supersede this issue.

## Change summary

Clicking inside selected editor text can fail to deselect it because incidental pointer movement activates text dragging.

## Best solution

Make ordinary clicks tolerant of incidental movement while preserving deliberate text dragging, including single-character selections. Resolve the activation tolerance with the editor owner; reports of failure without movement may require separate diagnosis.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/mouseHandler.ts`, `src/vs/editor/contrib/dnd/browser/dnd.ts`, `src/vs/editor/browser/editorDom.ts`
- **Validation:** Use a browser-driven editor check with editor.dragAndDrop enabled: select a multiline range, press inside it, move the pointer by one CSS pixel while held, and release inside the selection. Under the agreed tolerance, assert the selection collapses and text remains unchanged. Also check zero-movement clicks, deliberate moves outside the selection, single-character dragging, modifier-copy dragging, and Escape cancellation.
- **Behavior:**

  > An ordinary click inside selected text should deselect it even when the pointer moves incidentally during the click, without requiring Escape or disabling text drag and drop. Deliberate dragging must continue to move text, including single-character selections, and modifier-copy dragging must remain available. Acceptance should exercise both whole-document and smaller selections, with movement below and above the agreed activation tolerance. This scope addresses the confirmed movement-triggered case, not every environment-specific report of failure without movement.
- **Trace:**

  > MouseDownOperation.start in src/vs/editor/browser/controller/mouseHandler.ts selects the drag path immediately on a single press inside the current selection. GlobalEditorPointerMoveMonitor in src/vs/editor/browser/editorDom.ts forwards pointer movement from GlobalPointerMoveMonitor; _onMouseDownThenMove emits mouseDrag with no movement tolerance. DragAndDropController in src/vs/editor/contrib/dnd/browser/dnd.ts then records _dragSelection, and a drop inside that selection preserves it instead of executing the no-drag collapse path. This establishes the incidental-movement failure from current source without executing the editor. Preserve intentional dragging, copy modifiers, cancellation, and unrelated selection modes; do not broadly change the shared pointer monitor's consumers. https://github.com/microsoft/vscode/issues/28636#issuecomment-419982769 supports sensitivity adjustment but leaves its effect on short drags unresolved. https://github.com/microsoft/vscode/issues/147105 concerns similar symptoms with dragging disabled and should remain a separate diagnostic lead.
- **Open decisions:**
  - What pointer-movement or hold-time tolerance should distinguish an ordinary click from an intentional text drag while preserving short, single-character drags?

## Evidence

- **Current source reproduces the movement-triggered case:** src/vs/editor/browser/controller/mouseHandler.ts: MouseDownOperation.start enters the drag-and-drop branch on a single click inside a nonempty selection. _onMouseDownThenMove emits mouseDrag without checking movement distance or elapsed time. src/vs/base/browser/globalPointerMoveMonitor.ts forwards every pointermove with matching buttons, so even tiny movement reaches this branch.
- **Why the selection remains:** src/vs/editor/contrib/dnd/browser/dnd.ts: DragAndDropController._onEditorMouseDrag records _dragSelection when the pointer remains inside the selection. _onEditorMouseDrop collapses the selection when _dragSelection is null, but leaves it selected when a recorded drag ends inside that selection without the copy modifier. This establishes the reported incidental-movement path from source, not every no-movement variant in the discussion.
- **Existing capability is only a workaround:** src/vs/editor/common/config/editorOptions.ts:6324–6326 registers editor.dragAndDrop with default true. Setting it to false bypasses text dragging but removes a capability reporters explicitly want to retain; it does not provide activation tolerance.

A decline close would contradict that accepted direction.
