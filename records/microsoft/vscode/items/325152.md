# Issue #325152 — Port forwarding not working 

[https://github.com/microsoft/vscode/issues/325152](https://github.com/microsoft/vscode/issues/325152)

## Summary

The reported missing-host-token panic remains possible in current source: tunnel startup unconditionally expects the service response to contain a host token. Keep this open to diagnose why the token is absent and restore forwarding; the evidence shows the forwarding helper fails, not that the VS Code window crashes.

## Change summary

Built-in port forwarding fails during CLI startup with an “expected to have host token” panic.

## Best solution

Make tunnel startup and token refresh handle missing host tokens without panicking, and establish why the affected service response lacks the requested token so forwarding can succeed.

## Plan brief

- **Likely files:** `cli/src/tunnels/dev_tunnels.rs`, `cli/src/commands/tunnels.rs`
- **Validation:** Add Rust regression cases for tunnel responses with absent access_tokens, an access-token map without host, and a valid host token; run them with cargo test --manifest-path cli/Cargo.toml tunnels::dev_tunnels::test. Complete a Windows built-in port-forwarding check that starts a local HTTP server, forwards its port, and successfully requests its forwarded URL without a helper panic.
- **Behavior:**

  > Starting built-in port forwarding must not terminate the forwarding helper with an expect panic when a tunnel response lacks a host token. Valid host-token responses must continue to establish forwarding normally. Missing-token responses must produce an actionable failure or successful recovery rather than apparent success. Acceptance includes regression coverage for incomplete token responses and successful forwarding of a local HTTP server on Windows.
- **Trace:**

  > The report at https://github.com/microsoft/vscode/issues/325152 identifies the exact panic still present in get_host_token_from_tunnel in cli/src/tunnels/dev_tunnels.rs. The CLI forwarding startup in cli/src/commands/tunnels.rs constructs DevTunnels and calls start_new_launcher_tunnel, which retrieves or creates a tunnel, synchronizes tags, and passes the resulting Tunnel into the extraction helper. Host scope is requested, but the helper assumes that a successful response contains the host key; token refresh shares this assumption. The source establishes the panic for the reported response shape, but not whether lookup, creation, or tag synchronization supplied that response, nor why the service omitted the token. Preserve authentication requirements, token confidentiality, port privacy, and successful forwarding behavior; an empty token or silent fallback is not an acceptable outcome. The related port-protocol recovery commit does not address this failure.
