# Issue #283163 — @Docs like Cursor to index documentation sites

[https://github.com/microsoft/vscode/issues/283163](https://github.com/microsoft/vscode/issues/283163)

## Summary

Keep this accepted backlog request open: current fetch tooling ranks content from explicitly supplied pages, but does not provide whole-site documentation indexing. Maintainers have also consolidated other documentation-indexing requests onto this issue.

## Change summary

Allow users to index an arbitrary documentation site and retrieve relevant passages as Copilot context without supplying each page individually.

## Best solution

Design a reusable documentation-source experience that discovers pages from a supplied site URL and retrieves relevant, attributable passages for chat. Build on the existing URL chunk-ranking capability while settling source persistence, refresh behavior, and crawl boundaries before implementation.

- **Behavior:**

  > Users can supply an arbitrary documentation site's root URL and make its relevant documentation available to Copilot without manually enumerating child pages. Existing explicit-page fetching remains available. Acceptance uses a controlled multi-page documentation site, including a query whose answer appears only on a child page; persistence and refresh checks follow the maintainer's selected contract.
- **Trace:**

  > The registered copilot_fetchWebPage tool in extensions/copilot/package.json accepts explicit urls and a query. FetchWebPageTool.invoke in extensions/copilot/src/extension/tools/vscode-node/fetchWebPageTool.tsx delegates those URLs to vscode_fetchWebPage_internal, then passes their returned content to UrlChunkEmbeddingsIndex.findInUrls. That index, in extensions/copilot/src/platform/urlChunkSearch/node/urlChunkEmbeddingsIndex.ts, already computes embeddings and relevance scores but caches only supplied content in memory; it does not discover pages or manage reusable documentation sources. The core FetchWebPageTool in src/vs/workbench/contrib/chat/electron-browser/builtInTools/fetchPageTool.ts handles supplied-resource extraction and existing trust/network checks, which must remain intact. The unresolved boundary is the documentation-source lifecycle and site-discovery contract, not whether embedding-based ranking is available. Maintainers consolidated related requests here through https://github.com/microsoft/vscode/issues/265488#issuecomment-3673374891 and https://github.com/microsoft/vscode/issues/284294#issuecomment-3676138147.
- **Open decisions:**
  - Should registered documentation sources persist across sessions, and should their availability be scoped to a workspace or a user profile?
  - Should indexed documentation refresh automatically, only on explicit user request, or through a user-selectable policy?
  - What pages should a root URL authorize indexing: descendants under its path, the whole origin, or explicitly selected additional locations?
