# Issue #339816 — Show output just opens the task output and not an mcp specific output chanel

[https://github.com/microsoft/vscode/issues/339816](https://github.com/microsoft/vscode/issues/339816)

## Summary

Fresh, team-authored bug report with a concrete 4-step repro (found while testing #339524); keep open — no fix commit exists yet on main, and the exact failure point needs a bit more diagnosis before a fix lands.

## Change summary

Invoking 'Show Output' on a broken/failed MCP server opens the Output view but shows the previously-active channel (e.g. Tasks) instead of the MCP server's own output channel.

## Best solution

Trace why McpServer.showOutput()'s loggerId/channel lookup fails for a broken server (likely either a visibility/registration race in McpServer.showOutput — src/vs/workbench/contrib/mcp/common/mcpServer.ts:684-687 — or the 'Show Output' command failing to resolve a non-local/broken server), and have AbstractOutputService.showChannel (src/vs/workbench/contrib/output/browser/outputServices.ts:408-418) surface an explicit empty/error state instead of silently leaving the prior channel displayed when the requested channel id isn't found.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/common/mcpServer.ts`, `src/vs/workbench/contrib/output/browser/outputServices.ts`, `src/vs/workbench/contrib/mcp/browser/mcpCommands.ts`
- **Validation:** Manually reproduce with a deliberately broken MCP server definition, invoke Show Output, and confirm the MCP server's own output channel (not Tasks or any previously active channel) becomes active in the Output view; once a root cause is identified, name a specific unit/integration test around the chosen fix point (e.g. outputServices.test.ts for a showChannel fallback, or an mcp test for channel registration timing).
- **Behavior:**

  > Running 'Show Output' against a broken/failed MCP server must show that server's own MCP output channel (named 'MCP: <server label>'), not whichever output channel happened to be active before (e.g. Tasks). If no channel can be resolved at all, the Output view should make that visible (e.g. stay on an empty/no-channel state or show a clear indication) rather than silently leaving an unrelated channel on screen.
- **Trace:**

  > Two candidate mechanisms were found in the source but not conclusively distinguished: (1) McpServer.showOutput() (mcpServer.ts:684-687) flips the logger's hidden flag and calls showChannel with the loggerId; channel registration for a previously-hidden logger happens reactively in LogOutputChannels (logs.contribution.ts) off the onDidChangeVisibility event — if anything desynchronizes that from the immediate showChannel call for a server that errored before ever becoming visible, the id simply won't resolve. (2) AbstractOutputService.showChannel (outputServices.ts:408-418) has no fallback/error path when `getChannel(id)` returns undefined — it opens the Output view but skips `outputView.showChannel`, so the view keeps showing whatever was already active, exactly matching the reported symptom. Do not change unrelated output-channel behavior (compound/multi-source channels, log-level handling) — scope to the missing-channel case and to how a broken MCP server's id is produced/consumed.
- **Open decisions:**
  - Is the right fix in the MCP server's own showOutput/logger-visibility sequencing, in the generic IOutputService.showChannel fallback behavior (surfacing 'channel not found' broadly), or both?
  - When a broken server has no resolvable output at all, should Show Output clear/blank the Output view, or show a placeholder message, rather than leaving a prior channel visible?

## Evidence

- **showOutput call site:** McpServer.showOutput() (src/vs/workbench/contrib/mcp/common/mcpServer.ts:684-687) calls `this._loggerService.setVisibility(this._loggerId, true)` then `this._outputService.showChannel(this._loggerId, preserveFocus)`; the logger is created with `hidden: true` (line 566), and its output channel is only registered reactively via `LogOutputChannels.registerLogChannel` on the `onDidChangeVisibility` event (src/vs/workbench/contrib/logs/common/logs.contribution.ts:77-86, 137-157).
- **silent fallback in showChannel:** AbstractOutputService.showChannel (src/vs/workbench/contrib/output/browser/outputServices.ts:408-418) opens the Output view unconditionally but only calls `outputView.showChannel(channel, ...)` when `channel` is truthy — if the id isn't found in the registry, the view opens showing whatever channel was already active, with no error surfaced. This matches the reporter's own diagnosis ('likely indicating an output channel could not be found').
- **command path:** The explicit 'Show Output' quick-pick action in src/vs/workbench/contrib/mcp/browser/mcpCommands.ts (lines ~775-776) resolves the server and calls `server.showOutput()`; whether server resolution or the logger/channel timing is the actual failure point for a 'broken' server was not conclusively confirmed from source alone.
