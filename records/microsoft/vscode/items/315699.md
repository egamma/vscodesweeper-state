# Issue #315699 — Bring vscode-agents experience with worktrees to vscode

[https://github.com/microsoft/vscode/issues/315699](https://github.com/microsoft/vscode/issues/315699)

## Summary

Keep open: regular VS Code still lacks the requested integrated, session-independent worktree switcher. The linked proof-of-concept PR was closed without merging, and the older related reports do not establish a canonical covering this request under the re-review duplicate rules.

## Change summary

Provide one-click worktree switching in regular VS Code that changes Explorer, terminals, and Source Control together without requiring an AI session.

## Best solution

Provide a coherent worktree context switch in the regular workbench, independent of AI sessions, rather than treating SCM selection as a workspace switch. Settle how existing editors and running terminals are retained when switching before implementing the experience.

## Plan brief

- **Likely files:** `extensions/git/src/commands.ts`, `extensions/git/package.json`, `src/vs/workbench/contrib/scm/browser/scmViewService.ts`, `src/vs/workbench/contrib/scm/browser/workingSet.ts`, `src/vs/workbench/browser/parts/titlebar/commandCenterControl.ts`
- **Validation:** In regular VS Code, open a repository with two sibling worktrees containing distinguishable files. Switch between them through the proposed surface and verify that Explorer, Search/Quick Open, SCM, and new-terminal working directories consistently target the selected worktree without a confirmation dialog, a new window, or an AI session. Switch back with an unsaved editor and a running terminal to verify the agreed retention behavior.
- **Behavior:**

  > Regular VS Code should offer a single-click worktree context switch independent of AI sessions. Selecting another worktree should coordinate Explorer, file navigation/search, Source Control, and terminal context without opening another window or requiring confirmation for an ordinary switch. Acceptance must include switching between two sibling worktrees and switching back while retaining user state according to an explicit editor and terminal lifecycle contract.
- **Trace:**

  > The existing Git commands in extensions/git/src/commands.ts, including openWorktreeInCurrentWindow and artifactOpenWorktree, delegate to vscode.openFolder; extensions/git/package.json exposes current-window and new-window actions rather than an integrated context switch. SCMViewService.focus in src/vs/workbench/contrib/scm/browser/scmViewService.ts only changes repository focus. SCMWorkingSetController in src/vs/workbench/contrib/scm/browser/workingSet.ts restores editor working sets on history-reference changes, not workspace roots or terminal contexts. https://github.com/microsoft/vscode/pull/317806 contains a closed, unmerged prototype spanning a command-center switcher, per-worktree layouts, and terminals; its proposed files are not proof of current functionality. The remaining design uncertainty concerns state retention and running processes across switches; preserve existing explicit worktree-opening commands and ordinary branch-switch behavior. https://github.com/microsoft/vscode/issues/311858 is related multi-context design input, not a verified duplicate canonical.
- **Open decisions:**
  - Should each worktree retain a separate editor/layout state that is restored on return, or should open editors remain shared across worktree switches?
  - Should running terminals remain associated with their original worktree and be hidden/restored with that context, or remain visible across switches while only newly created terminals follow the selected worktree?
