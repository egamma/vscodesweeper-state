# Issue #169011 — Don't initialize with "Manual Resolution"

[https://github.com/microsoft/vscode/issues/169011](https://github.com/microsoft/vscode/issues/169011)

## Summary

Still a live, team-authored merge-editor bug: conflicts are initialized as "Manual Resolution" (unrecognized state) even after the result is reset, and the maintainer added a fresh example in December 2025 — keep open, no close evidence exists on current main.

## Change summary

When the merge editor opens, some conflicts come up already marked "Manual Resolution" instead of as unresolved conflicts the user can accept from either side.

## Best solution

Make initialization never land a range in ModifiedBaseRangeStateKind.unrecognized: after reset()/auto-merge, ranges whose result text doesn't map to a known input combination should fall back to an unhandled base state (or the diff/state mapping should be made robust enough that the mapping succeeds), in src/vs/workbench/contrib/mergeEditor/browser/model/mergeEditorModel.ts.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mergeEditor/browser/model/mergeEditorModel.ts`, `src/vs/workbench/contrib/mergeEditor/browser/model/modifiedBaseRange.ts`, `src/vs/workbench/contrib/mergeEditor/browser/model/diffComputer.ts`, `src/vs/workbench/contrib/mergeEditor/browser/view/conflictActions.ts`
- **Validation:** A case in src/vs/workbench/contrib/mergeEditor/test/browser/model.test.ts built from the issue body's base/input1/input2 (and from the minimal `#`/`Y`/6×`X` repro in the thread) asserting that no range is in the `unrecognized` state immediately after model initialization.
- **Behavior:**

  > Opening the merge editor on a freshly conflicted file must never present a conflict that is already labelled "Manual Resolution": every range starts either auto-resolved (one side only, or equal changes) or as an open conflict the user can accept from either input. The scenario in the issue body and the minimal repro in https://github.com/microsoft/vscode/issues/169011#issuecomment-2262241372 must both open with ordinary, actionable conflicts under the default `mergeEditor.diffAlgorithm: advanced`. "Manual Resolution" should remain reachable only after the user actually edits the result by hand. Existing auto-merge outcomes and the handled/unhandled counters must not regress.
- **Trace:**

  > State per conflict is `ModifiedBaseRangeState`; `ModifiedBaseRangeStateKind.unrecognized` (src/vs/workbench/contrib/mergeEditor/browser/model/modifiedBaseRange.ts:404-424) is what conflictActions.ts:221-224 renders as the "Manual Resolution" lens. MergeEditorModel computes each range's accepted state by diffing the result text back against the inputs (`computeState`, returning `ModifiedBaseRangeState.unrecognized` at mergeEditorModel.ts:434, driven from `updateBaseRangeAcceptedState` in the autorun around lines 178-200); when the initial result text — or the text produced by reset()/auto-merge — does not map onto any base/input1/input2 combination, the range comes up unrecognized at open time. `resetResult` is only set when the output file has conflict markers (mergeEditorInputModel.ts:332), so results written by other merge drivers are diffed as-is. The thread shows the mapping failure is often driven by diff granularity: the reporter notes `mergeEditor.diffAlgorithm: legacy` resolves the minimal case while `advanced` does not. Boundary: do not change the conflict-marker parsing or the user-initiated `mergeEditor.resetResultToBaseAndAutoMerge` command semantics, and keep the manual-edit path able to reach the unrecognized state. Related, narrower issues to read first: https://github.com/microsoft/vscode/issues/185357 (don't diff a result that was reset) and https://github.com/microsoft/vscode/issues/206422 (diff quality).
- **Open decisions:**
  - When a range's initial result text cannot be mapped to any input combination, should it be presented as an unresolved base conflict (losing whatever text was in the result there) or kept as-is but shown as unhandled rather than "Manual Resolution"?
  - Should initialization treat everything outside conflict markers in the output file as already resolved (as the reporter suggests), rather than diffing the whole result?
  - Is the intended fix to suppress the unrecognized state at initialization only, or to improve the advanced diff algorithm's conflict granularity so the mapping succeeds (which also affects https://github.com/microsoft/vscode/issues/206422)?
