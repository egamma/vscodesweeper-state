# Issue #244698 — Terminal Links highlight correct link but open incorrect one

## Summary

Keep open: this issue is mid-verification (`verification-found`), and the current search-link opener still selects the first matching path's line number rather than the clicked occurrence's.

## Change summary

Clicking the second terminal link for the same relative file incorrectly uses the first occurrence's line number.

Ensure terminal search-link activation preserves the clicked occurrence's line and column, including when the file cannot be resolved and Quick Access is used. Continue verification against the reporter's repeated-path example.

- **Current source reproduces the trigger:** In src/vs/workbench/contrib/terminalContrib/links/browser/terminalWordLinkDetector.ts, TerminalWordLinkDetector.detect attaches the entire output line as contextLine while retaining each word's own text and bufferRange. Both occurrences match the same path, so clicking the second selects the first suffix and rewrites text to `foo/file1.txt:1`. That text reaches quickAccess.show when exact resolution fails.
