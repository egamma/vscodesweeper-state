# Issue #72945 — [themes] Support for hue, saturation, lightness (HSL) color codes for theming

[https://github.com/microsoft/vscode/issues/72945](https://github.com/microsoft/vscode/issues/72945)

## Summary

A real capability gap remains on current main: workbench theme colors are still validated and loaded as hexadecimal values only. The related issue is newer, narrower, and closed, so it cannot serve as a canonical duplicate under the re-review rules.

## Change summary

Allow theme authors to express workbench colors using CSS HSL and HSLA syntax instead of converting them to hexadecimal.

## Best solution

Define the supported CSS color syntax for workbench theme values, then parse HSL/HSLA consistently in color-theme files, workbench color customizations, and contributed color defaults while retaining existing hexadecimal behavior.

## Plan brief

- **Likely files:** `src/vs/base/common/color.ts`, `src/vs/base/test/common/color.test.ts`, `src/vs/platform/theme/common/colorUtils.ts`, `src/vs/workbench/services/themes/common/colorThemeData.ts`, `src/vs/workbench/services/themes/common/colorThemeSchema.ts`, `src/vs/workbench/services/themes/common/colorExtensionPoint.ts`
- **Validation:** Add parser unit cases for accepted and rejected HSL/HSLA syntax in src/vs/base/test/common/color.test.ts and theme-service coverage showing equivalent HSL and hexadecimal values resolve to the same Color for both JSON theme `colors` and workbench.colorCustomizations; run the corresponding targeted Color and theme-service unit suites.
- **Behavior:**

  > Theme authors can use the approved HSL and HSLA syntax for workbench color values in JSON themes and workbench.colorCustomizations. Equivalent HSL/HSLA and hexadecimal inputs resolve to the same color and alpha value, while existing hexadecimal themes remain unchanged. Invalid color expressions continue to receive validation feedback rather than being silently accepted. Acceptance must cover opaque and translucent values in both theme files and user customizations.
- **Trace:**

  > On current main, ColorThemeData.overwriteCustomColors and _loadColorTheme in src/vs/workbench/services/themes/common/colorThemeData.ts pass strings directly to Color.fromHex. Workbench color schemas in src/vs/platform/theme/common/colorUtils.ts and src/vs/workbench/services/themes/common/colorThemeSchema.ts likewise advertise only `color-hex`. Color.Format.CSS in src/vs/base/common/color.ts already models and formats HSLA but does not parse it, providing the likely shared parsing boundary. Contributed color defaults in src/vs/workbench/services/themes/common/colorExtensionPoint.ts independently distinguish hex values from color references, so their contract must be considered as well. Preserve hexadecimal parsing and theme-color references; token-color and decoration syntax should remain outside this issue unless maintainers explicitly include them.
- **Open decisions:**
  - Should the public contract support only the legacy comma-separated hsl()/hsla() forms requested here, or also CSS Color Level 4 space-separated syntax, angle units, and slash alpha?
  - Should HSL/HSLA support apply only to workbench `colors` and workbench.colorCustomizations, or also to contributed color defaults and token-color schemas?

## Evidence

- **current source gap:** src/vs/workbench/services/themes/common/colorThemeData.ts parses both workbench.colorCustomizations and JSON theme `colors` through Color.fromHex, so the requested HSL/HSLA values are not supported.
- **schema restriction:** src/vs/platform/theme/common/colorUtils.ts and src/vs/workbench/services/themes/common/colorThemeSchema.ts describe workbench and theme color values with the `color-hex` format.
- **shared parser limitation:** src/vs/base/common/color.ts defines HSLA conversion and formatting, but Color.Format.CSS.parse handles hex, rgb/rgba, transparent, and named colors without parsing hsl/hsla.
