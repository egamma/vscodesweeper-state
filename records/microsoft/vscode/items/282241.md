# Issue #282241 — Use the `#tool:fullReferenceName` syntax in the chat input

[https://github.com/microsoft/vscode/issues/282241](https://github.com/microsoft/vscode/issues/282241)

## Summary

A real gap remains on current main: agent and prompt files use qualified `#tool:fullReferenceName` references, while chat input still completes and parses legacy short `#name` references. This team-authored, On Deck request should remain open for a compatibility and scope decision.

## Change summary

Use qualified `#tool:fullReferenceName` syntax when completing and resolving tool references in chat input.

## Best solution

Make chat-input completion, parsing, and rendering use the existing full-reference-name service so tools with colliding short names remain independently addressable, while explicitly deciding compatibility for persisted or manually entered legacy references.

- **Behavior:**

  > Chat input presents and accepts tool references using `#tool:fullReferenceName`, matching agent and prompt files. Two enabled tools with the same short name remain separately selectable and each reference resolves to the intended tool ID. Tool sets and qualified extension or MCP tool names are represented without ambiguity. Compatibility behavior for existing legacy `#shortName` input must be deliberately defined and tested.
- **Trace:**

  > The current parser in src/vs/workbench/contrib/chat/common/requestParser/chatRequestParser.ts recognizes only `#name` through `variableReg` and constructs lookup maps from short names. ToolCompletions in src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts likewise inserts short names, although ILanguageModelToolsService already exposes qualified-name generation and lookup in src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts. Prompt files already parse `#tool:` references in src/vs/workbench/contrib/chat/common/promptSyntax/promptFileParser.ts, establishing the requested syntax. The originating collision is documented at https://github.com/microsoft/vscode-copilot-release/issues/11480. Keep unrelated dynamic variables and attachment syntaxes unchanged; determine separately whether agent-host-backed chat inputs, whose completions are delegated, must migrate in the same change.
- **Open decisions:**
  - Should legacy `#shortName` tool references continue to resolve when unambiguous, or should chat input accept only `#tool:fullReferenceName` after migration?
  - Must the same change cover agent-host-backed chat inputs and their delegated completion protocol, or is this issue limited to the workbench-managed chat-input path?

## Evidence

- **chat parser gap:** src/vs/workbench/contrib/chat/common/requestParser/chatRequestParser.ts defines `variableReg` for legacy `#name` tokens, keys selected tools by `toolReferenceName` or display name, and cannot parse the `#tool:qualified/name` syntax.
- **chat completion gap:** ToolCompletions in src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts suggests `#${toolReferenceName}` or a tool-set reference name rather than calling `ILanguageModelToolsService.getFullReferenceName`; its token pattern also excludes qualified paths.
- **existing qualified-name infrastructure:** src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts already implements `getFullReferenceName` and `getToolByFullReferenceName`, including extension and tool-set qualification, while src/vs/workbench/contrib/chat/common/promptSyntax/promptFileParser.ts parses `#tool:<toolName>` with qualified names.
- **originating collision report:** https://github.com/microsoft/vscode-copilot-release/issues/11480 documented two tools with the same short name becoming indistinguishable; its final maintainer comment created this issue to own chat-input tool references. It is closed and reports the collision symptom rather than serving as an open duplicate canonical.
- **protected maintainer request:** The issue was authored by a repository member and is assigned to the On Deck holding milestone; there is no referenced implementing commit or verified open canonical issue supporting a factual close.
