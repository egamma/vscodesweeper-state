# Issue #158911 — Don't allow extension to annoy users with auth asks

[https://github.com/microsoft/vscode/issues/158911](https://github.com/microsoft/vscode/issues/158911)

## Summary

Keep open for the maintainer-agreed authentication UX improvement: current code still permits activation-time modal prompts. GitLens mitigated its own behavior, but VS Code does not enforce the requested interaction boundary.

## Change summary

Prevent extensions from showing disruptive authentication modals without an appropriate user interaction.

## Best solution

Make background authentication requests non-modal while preserving intentional sign-in flows initiated by commands and qualifying filesystem activation. Settle the interaction criteria and pending-request contract before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/api/browser/mainThreadAuthentication.ts`, `src/vs/workbench/api/common/extHostAuthentication.ts`, `src/vs/workbench/services/authentication/browser/authenticationExtensionsService.ts`, `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/test/browser/mainThreadAuthentication.integrationTest.ts`, `src/vs/workbench/api/test/browser/extHostAuthentication.integrationTest.ts`
- **Validation:** Extend the authentication API tests to distinguish background activation from qualifying command/filesystem interactions, asserting that background requests do not invoke a modal or begin provider sign-in before user action. Manually verify in a browser with a fixture extension calling getSession({createIfNone:true}) during activation: dismiss the passive indication, reload, and confirm no modal appears; explicitly invoke sign-in and confirm the intended flow still completes.
- **Behavior:**

  > An extension requesting authentication during ordinary background activation must not interrupt the user with a modal sign-in dialog, including after dismissal and page reload. Authentication must remain discoverable through a less disruptive surface, and intentional sign-in interactions must continue to work. The maintainer-agreed direction permits modal flows for command invocation and qualifying filesystem activation. Acceptance must cover background activation, dismissal/reload, explicit sign-in, and reuse of already authorized sessions.
- **Trace:**

  > ExtHostAuthentication.getSession in src/vs/workbench/api/common/extHostAuthentication.ts forwards extension identity and options to the main thread without interaction provenance. MainThreadAuthentication.doGetSession in src/vs/workbench/api/browser/mainThreadAuthentication.ts checks authorized sessions and then calls loginPrompt for createIfNone or forceNewSession; loginPrompt directly opens a dialog. The existing passive path delegates to AuthenticationExtensionsService.requestNewSession, which contributes an Accounts menu action and badge. Source inspection establishes the missing gate, but not a reliable interaction-provenance mechanism across asynchronous extension execution. Preserve existing account selection, authorization checks, and silent-session behavior; do not broaden this into restrictions on arbitrary extension message dialogs. The documented createIfNone:true overload promises a session, so deferral also has an observable API-contract consequence. https://github.com/microsoft/vscode/issues/233424 discusses related interaction provenance but has a different requested modal outcome.
- **Open decisions:**
  - Beyond command invocation and onFileSystem activation, which user interactions or activation events qualify for a modal, and how long does that qualification remain valid across asynchronous work?
  - For an unqualified createIfNone request, should getSession remain pending until the user acts on the passive sign-in affordance, or reject when immediate interaction is disallowed?
  - Should background requests use only the Accounts badge/menu or also a notification, and what should dismissal suppress across reloads?

## Evidence

- **Accepted core direction:** The September and December maintainer comments on https://github.com/microsoft/vscode/issues/158911 agree that createIfNone should not always produce a modal. The December comment identifies command invocation and onFileSystem activation as qualifying contexts, while leaving the complete activation-event list unresolved: https://github.com/microsoft/vscode/issues/158911#issuecomment-1355879846.
- **Current modal path:** src/vs/workbench/api/browser/mainThreadAuthentication.ts:451-500 enters loginPrompt whenever createIfNone or forceNewSession is set and no authorized session was returned. loginPrompt at lines 383-423 calls dialogService.prompt; this path does not check command execution or activation context.
- **Existing capability is only voluntary:** src/vscode-dts/vscode.d.ts:17903-17919 explicitly documents a modal for createIfNone:true and an Accounts badge for false. MainThreadAuthentication.doGetSession uses the passive request path at lines 540-549, and AuthenticationExtensionsService.requestNewSession creates an Accounts menu entry and updates the badge. These options let an extension behave quietly but do not prevent it from requesting a modal during activation; this is a requested behavior/contract change rather than a deviation from the documented API.
- **GitLens mitigation does not complete core work:** The GitLens author reports prompting only once and using the Accounts badge after dismissal. https://github.com/gitkraken/vscode-gitlens/issues/2166 is verified closed, but its extension-side mitigation does not add VS Code's requested platform restriction.
- **Related report is not a duplicate canonical:** https://github.com/microsoft/vscode/issues/233424 is verified open and asks to omit the confirmation modal after an explicit Copilot sign-in click, unlike this issue's unsolicited activation-time prompts. Its maintainer comment explicitly distinguishes the two goals and identifies missing interaction context: https://github.com/microsoft/vscode/issues/233424#issuecomment-2546106636. It is also newer than this re-reviewed issue.
- **Canonical search:** Open-issue searches for authentication modal, auth activation, and createIfNone found no verified older canonical owning this request. https://github.com/microsoft/vscode/issues/137614 concerns indistinguishable quiet-login menu entries, not unsolicited modals. https://github.com/microsoft/vscode/issues/283376 concerns activation blocking on authentication and is newer, not a canonical for this report.
