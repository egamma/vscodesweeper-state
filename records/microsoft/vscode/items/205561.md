# Issue #205561 — Built-in CodeLens for References

[https://github.com/microsoft/vscode/issues/205561](https://github.com/microsoft/vscode/issues/205561)

## Summary

Keep open: current CodeLens infrastructure still requires language-specific providers and does not generate reference counts from ReferenceProvider registrations. The accepted Backlog request has 27 upvotes and maintainer interest; its opt-in and performance contract needs design before implementation.

## Change summary

Provide shared reference-count CodeLens support with an extension-facing contract for identifying eligible symbols or ranges.

## Best solution

Design an opt-in reference CodeLens facility that lets language providers identify eligible locations while VS Code handles consistent presentation and controls. Preserve existing language-specific lenses and avoid expensive reference queries for providers that have not opted in.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages.ts`, `src/vs/editor/contrib/codelens/browser/codelens.ts`, `src/vs/editor/contrib/codelens/browser/codelensController.ts`, `extensions/typescript-language-features/src/languageFeatures/codeLens/referencesCodeLens.ts`
- **Validation:** After agreeing the contract, use a test extension with reference support but no custom CodeLens provider to verify reference counts and navigation for opted-in symbols. Verify disabled/non-opted-in providers receive no automatic reference requests, existing custom lenses are not duplicated, and expensive resolution follows the agreed visibility and cancellation behavior.
- **Behavior:**

  > An opted-in language can expose reference-count CodeLenses without implementing its own presentation and control logic. Eligible symbols show counts whose actions navigate to the corresponding references. Existing language-specific lenses remain usable without duplicates, and providers that have not opted in incur no automatic reference-query cost. Acceptance must cover enable/disable behavior, count accuracy, navigation, and cancellation of expensive computation.
- **Trace:**

  > ReferenceProvider in src/vscode-dts/vscode.d.ts accepts a single Position and does not identify CodeLens-eligible symbols or support range-based requests. CodeLensController in src/vs/editor/contrib/codelens/browser/codelensController.ts consumes the separate codeLensProvider registry, and getCodeLensModel in codelens.ts calls those providers directly. The TypeScript extension supplies its own symbol eligibility and reference resolution in extensions/typescript-language-features/src/languageFeatures/codeLens/referencesCodeLens.ts, demonstrating partial language-specific coverage rather than a shared facility. The discussion at https://github.com/microsoft/vscode/issues/205561 establishes that indiscriminate automatic reference queries are unacceptable but does not settle the public opt-in or range contract. Preserve existing CodeLens providers and ordinary Find References semantics; any LSP extension requires separate protocol coordination.
- **Open decisions:**
  - Should participation be declared through extension contributions, an optional reference-provider capability, or a separate provider contract?
  - Should the new contract expose eligible symbol locations for lazy per-symbol resolution, or provide batched reference counts for a requested document range?
  - What per-extension user controls govern shared lenses, and how should shared and existing custom reference lenses coexist?
