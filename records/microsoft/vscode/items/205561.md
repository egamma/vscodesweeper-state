# Issue #205561 — Built-in CodeLens for References

[https://github.com/microsoft/vscode/issues/205561](https://github.com/microsoft/vscode/issues/205561)

## Summary

A real cross-language API gap remains on current main. This Backlog request has 27 community upvotes and should remain open with its existing CodeLens and editor-symbols routing.

## Change summary

Provide an opt-in, editor-managed References CodeLens capability so language extensions do not implement separate reference-count lenses and settings.

## Best solution

Add an optional range-oriented reference API, coordinated with an LSP capability, so opted-in providers can efficiently enumerate referenceable symbols while VS Code owns the CodeLens UI and configuration. Preserve explicit opt-in because reference computation can be expensive and some extensions already provide their own lenses.

## Evidence

- **current API gap:** On current main, `ReferenceProvider.provideReferences` in `src/vscode-dts/vscode.d.ts` and `src/vs/editor/common/languages.ts` accepts only a single Position; it has no range-oriented method for efficiently discovering symbols across a visible document range.
- **existing capability is partial:** `extensions/typescript-language-features/src/languageFeatures/codeLens/referencesCodeLens.ts` implements References CodeLens specifically for JavaScript/TypeScript using TypeScript navigation-tree data. It does not provide the requested common behavior for other reference providers.
- **design constraints:** https://github.com/microsoft/vscode/issues/205561#issuecomment-1952896696 supports the idea while identifying the need for per-extension opt-in and safeguards against expensive reference computation.
- **proposed API direction:** https://github.com/microsoft/vscode/issues/205561#issuecomment-1952947839 explains why an independent extension cannot efficiently discover request positions and proposes a range-based VS Code/LSP capability.
- **cross-language demand:** The open Dart request https://github.com/Dart-Code/Dart-Code/issues/1605 points back to this issue as the preferred VS Code/LSP-level solution.
