# Issue #338867 — /btw side chat forces GitHub sign-in when signed out with BYOK models enabled

[https://github.com/microsoft/vscode/issues/338867](https://github.com/microsoft/vscode/issues/338867)

## Summary

Real gap, not yet fixed on main: a plausible model-selection race between the newly created side chat and the auth gate lets `/btw` force a GitHub sign-in even though the source chat is happily running signed-out on a BYOK model.

## Change summary

With `chat.agentHost.byokModels.enabled` + `allowSignedOutWhenUsable` and a signed-out BYOK session, sending `/btw <question>` forces a GitHub sign-in dialog even though normal messages on the same chat work fine.

## Best solution

Make the side-chat auth gate consult the chat's own carried-over BYOK model selection (set via `setChatModelId(..., ChatModelSource.CarriedOver)`) instead of only the request's explicit `userSelectedModelId`, so a freshly created side chat that inherits a BYOK model is never treated as auth-requiring on its first send.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`
- **Validation:** A test that creates a side chat inheriting a BYOK model in a signed-out `allowSignedOutWhenUsable` session and asserts `_ensureRequiredAuthentication`/`resolveAuthentication` is never invoked for the side chat's first request.
- **Behavior:**

  > When `allowSignedOutWhenUsable` is enabled and the source chat is running a BYOK model while signed out, starting a `/btw` side chat and sending its first message must NOT show the GitHub sign-in dialog — it should run on the same BYOK model as the source chat, exactly like a normal message on that chat. Acceptance: a named test exercising the side-chat creation + first-send path with a BYOK-only signed-out session shows no authentication resolution is triggered.
- **Trace:**

  > createSideChat() in src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts (~5974) correctly carries the source chat's model into the new backend chat and records it via `cached.setChatModelId(..., ChatModelSource.CarriedOver)`. But the auth gate that runs on the first send — `_ensureRequiredAuthentication` in agentHostSessionHandler.ts (~5766), which calls `modelRequiresAgentAuthentication` in agentHostAuth.ts (~51) — is fed `this._createModelSelection(request.userSelectedModelId, ...)`, and `request.userSelectedModelId` for a widget request comes from `ChatWidget.getSelectedModelRequestOptions()` (chatWidget.ts ~3879), which reads the widget's own `input.currentLanguageModel` picker state rather than the backend's carried-over selection. If that picker state isn't synced by the time the very first `/btw` message is composed, `model` is undefined, and `modelRequiresAgentAuthentication` returns true (agentHostAuth.ts line ~59-60: `if (!model) return true;`), forcing the sign-in dialog. Boundary: do not change the auth gate's behavior for chats that genuinely have no model selection (that must still require auth); do not touch the main-session creation path, only the side-chat/fork inherited-model case. Where uncertainty starts: I did not execute the flow to pin the exact millisecond-level timing of when `input.currentLanguageModel` gets hydrated for a newly split side-chat widget, or confirm whether it happens at all for a chat that has never had a manual model pick.
- **Open decisions:**
  - Should the side-chat widget eagerly hydrate its model picker from the backend's carried-over selection before composing the first request, or should the backend auth gate fall back to the chat's own recorded model when the request carries no explicit `userSelectedModelId`?
  - Should `modelRequiresAgentAuthentication`/`_ensureRequiredAuthentication` treat 'no explicit selection yet, but this chat has a known carried-over BYOK model on record' as not requiring auth, and if so, where should that lookup happen (session handler vs. auth helper)?

## Evidence

- **auth gate:** modelRequiresAgentAuthentication in src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts returns true when `model` is undefined (line ~59-60), even with allowSignedOutWhenUsable enabled.
- **gate call site:** _ensureRequiredAuthentication in agentHostSessionHandler.ts (~line 1970, 5766-5777) computes the model to check via `this._createModelSelection(request.userSelectedModelId, request.modelConfiguration)` — it does not fall back to the chat's own recorded model.
- **request-side model source:** ChatWidget.getSelectedModelRequestOptions() (src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts ~3879-3890) derives `userSelectedModelId` from `this.input.currentLanguageModel`, the widget's own picker state — not from the backend's carried-over side-chat model set in createSideChat().
- **carried-over model:** baseAgentHostSessionsProvider.ts createSideChat() (~5974-6023) correctly passes the source chat's model to `connection.createChat` and records it via `cached.setChatModelId(chat.resource, selectedModelId, ChatModelSource.CarriedOver)`, but that record is not what the auth check consults on the first send.
