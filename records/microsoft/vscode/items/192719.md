# Issue #192719 — MacOS scrolling inertia is not cancelled when stopped

[https://github.com/microsoft/vscode/issues/192719](https://github.com/microsoft/vscode/issues/192719)

## Summary

The gap remains on current main: cursor reveal changes the editor scroll position, but subsequent macOS momentum wheel events are still accepted and move the cursor out of view again. The issue is correctly routed and should remain open while the gesture-cancellation semantics are designed.

## Change summary

Stop a trackpad's remaining inertial scroll after typing or cursor navigation programmatically reveals the cursor.

## Best solution

A programmatic cursor reveal should terminate the active trackpad gesture for that editor without delaying or discarding a genuinely new scroll gesture. Maintainers should first decide whether this belongs in the editor's reveal path or in the shared scrollable-element gesture model.

- **Likely files:** `src/vs/base/browser/ui/scrollbar/scrollableElement.ts`, `src/vs/base/browser/mouseEvent.ts`, `src/vs/editor/browser/controller/mouseHandler.ts`, `src/vs/editor/browser/viewParts/editorScrollbar/editorScrollbar.ts`, `src/vs/base/test/browser/ui/scrollbar/scrollableElement.test.ts`
- **Validation:** Add a scrollbar/editor input test that sends a trackpad-style wheel sequence, performs a cursor-reveal scroll between deltas, and verifies trailing deltas do not move the viewport while a subsequent new gesture still does; manually confirm the six reported steps on macOS.
- **Behavior:**

  > When typing or keyboard navigation reveals the cursor while trackpad momentum is still producing wheel events, the cursor must remain visible instead of being scrolled away again. A genuinely new trackpad gesture must begin scrolling immediately, and ordinary uninterrupted inertial scrolling must remain unchanged. Acceptance requires an automated gesture-sequence regression test plus confirmation of the reported flow on macOS.
- **Trace:**

  > SmoothScrollableElement._onMouseWheel in src/vs/base/browser/ui/scrollbar/scrollableElement.ts accepts each trailing wheel delta independently. ViewLayout.setScrollPosition in src/vs/editor/common/viewLayout/viewLayout.ts performs the cursor-reveal reposition without communicating a gesture boundary to the scrollbar. IMouseWheelEvent in src/vs/base/browser/mouseEvent.ts has no native momentum-phase field, while MouseHandler already groups trackpad events heuristically for zoom. The uncertainty begins at the ownership boundary: cancellation could be editor-specific or part of the shared scrollable-element gesture model, which may also affect https://github.com/microsoft/vscode/issues/223470. Preserve uninterrupted inertia, physical mouse-wheel behavior, and immediate response to a new gesture.
- **Open decisions:**
  - Should cursor reveal cancel momentum only in editor scrollbars, or should any programmatic reposition terminate the active gesture in SmoothScrollableElement?
  - How should trailing momentum be distinguished from a new trackpad gesture when the DOM event exposes deltas but no momentum phase?
  - Should the scope also cover momentum transfer between scrollable elements tracked by https://github.com/microsoft/vscode/issues/223470?

## Evidence

- **current wheel path:** src/vs/base/browser/ui/scrollbar/scrollableElement.ts::_onMouseWheel applies every non-prevented wheel delta to the current/future scroll position; it has no state that cancels the remainder of a native momentum gesture after a programmatic reposition.
- **cursor reveal path:** src/vs/editor/common/viewLayout/viewLayout.ts::setScrollPosition changes the underlying scrollable immediately or smoothly, but does not notify EditorScrollbar or SmoothScrollableElement that an active input gesture should end.
- **gesture information:** src/vs/base/browser/mouseEvent.ts::IMouseWheelEvent exposes wheel deltas but no momentum-phase field. src/vs/editor/browser/controller/mouseHandler.ts uses a 50 ms timing heuristic to group trackpad events for zoom, showing that trailing inertia is recognized heuristically but is not cancelled on cursor movement.
- **earlier report:** https://github.com/microsoft/vscode/issues/100234 describes the same cursor-reveal problem on Windows, but it was closed by the feature-request upvote process rather than by an implementation; it is therefore neither an open canonical nor evidence of a fix.
- **related distinct issue:** https://github.com/microsoft/vscode/issues/223470 remains open for momentum transferring between different scrollable elements. It concerns the same shared input machinery but does not fully own this editor-specific cursor-reveal behavior.
