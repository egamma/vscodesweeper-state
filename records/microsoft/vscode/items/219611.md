# Issue #219611 — Git - Provide way to open the merge editor even if the "source control" pane doesn't load

[https://github.com/microsoft/vscode/issues/219611](https://github.com/microsoft/vscode/issues/219611)

## Summary

Keep this accepted request open: current source still ties the merge-editor button to potentially truncated Git status results. The confirmed workaround restores access by removing the limit, but does not provide the requested independent entry point.

## Change summary

Provide a discoverable way to open a conflicted file in the merge editor when Git status exceeds the Source Control limit.

## Best solution

Provide a supported merge-editor entry point for the active conflicted file that remains available when status enumeration is limited, while preserving the large-repository performance safeguard. Decide whether this is an explicit command or an automatically offered editor action.

## Plan brief

- **Likely files:** `extensions/git/package.json`, `extensions/git/src/commands.ts`, `extensions/git/src/model.ts`, `extensions/git/src/git.ts`, `extensions/git/src/repository.ts`
- **Validation:** In a disposable test repository, create more than 10,000 changed paths with a text conflict beyond the retained status subset. With git.statusLimit left at 10000, manually open that file and verify the chosen supported entry point opens the three-way merge editor and permits combining both changes. Verify ordinary conflicts still work, the status limit remains enforced, and non-conflicted files do not offer a misleading automatic action.
- **Behavior:**

  > A user resolving a large merge can open the merge editor for a manually opened conflicted file even when Source Control cannot enumerate that file because of git.statusLimit. Access must not require setting the limit to zero or manually extracting four merge input paths. The resulting editor must support the same combination workflow as opening a known conflict from Source Control. Existing normal-size repository behavior and the status performance safeguard must remain intact.
- **Trace:**

  > Repository.getStatus in extensions/git/src/git.ts truncates enumeration at a nonzero limit, and Repository.getStatus in extensions/git/src/repository.ts derives mergeGroup solely from that subset. Model.updateMergeChanges and Model.onDidChangeActiveTextEditor in extensions/git/src/model.ts make both merge-related context keys depend on that group, even though the active document contains conflict markers. extensions/git/package.json hides git.openMergeEditor from the Command Palette and gates its editor action on those contexts. Commands.openMergeEditor in extensions/git/src/commands.ts can derive the active text URI and construct Git merge inputs without mergeGroup membership, providing an existing execution path to investigate. The reporter confirmed the large-merge scenario and unlimited-status workaround in https://github.com/microsoft/vscode/issues/219611; no runtime reproduction was attempted. Preserve the status limit and ordinary merge, rebase, and stash input semantics; generic marker-containing files without usable Git merge inputs are not established as part of this request. The remaining product uncertainty is whether access should be an explicit command or an automatic editor action.
- **Open decisions:**
  - Should status-independent access be provided through an explicit Command Palette action for the active file, an automatically displayed editor action for eligible conflicted files, or both?
