# Issue #210709 — Git - Execute multiple git operations at the same time on different repositories

[https://github.com/microsoft/vscode/issues/210709](https://github.com/microsoft/vscode/issues/210709)

## Summary

Keep open: current source still disables Git commands across all repositories whenever any repository runs a blocking operation. This issue already owns the multi-root concurrency problem; the older report was explicitly consolidated here by a maintainer.

## Change summary

A commit, pull, or push in one repository disables Source Control Git actions for independent repositories in the same window.

## Best solution

Make repository-targeted Git actions reflect the target repository's operation state, allowing independent repositories to remain usable while preserving same-repository blocking. Cover repository menus, input actions, and commands consistently without introducing overlapping credential prompts.

- **Likely files:** `extensions/git/src/model.ts`, `extensions/git/src/operation.ts`, `extensions/git/src/repository.ts`, `extensions/git/package.json`, `src/vs/workbench/contrib/scm/browser/menus.ts`, `src/vs/workbench/contrib/scm/browser/scmInput.ts`
- **Validation:** Use a multi-root workspace containing two independent repositories and a deliberately delayed local Git hook to keep an operation in repository A active. Verify that repository B's Source Control commit, pull, and push actions remain enabled and can complete before A finishes, while conflicting actions in A remain blocked. Repeat through repository menus and input actions, check completion and failure restore enablement, and exercise concurrent authenticated remote operations for prompt regressions.
- **Behavior:**

  > A long-running commit, pull, or push in one repository must not disable repository-targeted Git actions for another independent repository in the same multi-root workspace. Conflicting operations within the busy repository must retain their existing protection. Acceptance requires an operation in repository B to complete while repository A remains busy, with consistent enablement across repository menus and input actions. Completion and failure must restore the appropriate state, and concurrent remote operations must not break credential handling.
- **Trace:**

  > Each Repository owns an OperationManager, and Repository.run() updates its operation state before and after execution. The cross-repository coupling occurs in updateOperationInProgressContext() inside extensions/git/src/model.ts, which aggregates every repository's shouldDisableCommands() result into the global operationInProgress context; extensions/git/package.json uses that context across many commands. SCMRepositoryMenus in src/vs/workbench/contrib/scm/browser/menus.ts already creates provider-specific context overlays, and scmInput.ts creates additional repository-specific menu contexts, but the inspected overlays do not carry operation state. The trace establishes the defect but does not yet enumerate all command and shared SCM consumers needed for consistent repository-scoped enablement. Preserve same-repository protection and existing command targeting; removing the global gate without replacement does not meet the contract. https://github.com/microsoft/vscode/issues/189296 was explicitly consolidated into this issue, while https://github.com/microsoft/vscode/issues/230033 documents a distinct authentication concurrency concern to consider without expanding this into an unrelated credential rewrite.

## Evidence

- **Confirmed current-source trigger:** In extensions/git/src/operation.ts, Commit, Pull, and Push are blocking operations, and OperationManager.shouldDisableCommands() returns true while any blocking operation is active. extensions/git/src/repository.ts:2871-2896 starts and ends that per-repository operation state around execution.
- **Cross-repository blocking root cause:** extensions/git/src/model.ts:851-864 defines updateOperationInProgressContext(), scans every open repository, and publishes the window-wide operationInProgress context as true if any repository should disable commands. extensions/git/package.json repeatedly uses !operationInProgress for command enablement, so pushing repository A also disables actions targeting repository B. This is a conclusive source trace, not an executed UI reproduction.
- **Repository context boundary:** src/vs/workbench/contrib/scm/browser/menus.ts:175-211 constructs SCMRepositoryMenus with provider-specific scmProvider and scmProviderRootUri context overlays, but no repository operation state. src/vs/workbench/contrib/scm/browser/scmInput.ts also creates provider-specific input menu contexts. The remaining work involves connecting Git operation state to these repository-specific surfaces rather than removing blocking globally.
