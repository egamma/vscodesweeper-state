# Issue #338697 — Tab in opening counterpart of auto-closing pair does not work

[https://github.com/microsoft/vscode/issues/338697](https://github.com/microsoft/vscode/issues/338697)

## Summary

Confirmed in source: pressing Tab never triggers autoClosingPairs whose `open` ends in a tab character, because Tab is a dedicated core command (indent/jump-to-indent) that never runs through the character-typing pipeline that checks autoClosingPairsOpenByEnd. This is real but interacts with several other overloaded Tab behaviors, so the fix needs a design decision before implementation.

## Change summary

An autoClosingPairs entry configured with a tab character at the end of `open` (e.g. `"open": "begin\t"`) never triggers the paired `close` text when Tab is pressed.

## Best solution

A maintainer should decide whether Tab-triggered autoClosingPairs should be supported at all given Tab's existing overloaded roles (indent, snippet tab-stop navigation, suggestion accept), then, if so, wire a check for autoClosingPairsOpenByEnd('\t') into the Tab command path (coreCommands.ts / TypeOperations.tab) without disturbing default indent behavior.

## Plan brief

- **Likely files:** `src/vs/editor/browser/coreCommands.ts`, `src/vs/editor/common/cursor/cursorTypeEditOperations.ts`, `src/vs/editor/common/cursor/cursorTypeOperations.ts`
- **Validation:** A test simulating a Tab keypress (via TypeOperations.tab) after typing text matching an autoClosingPair `open` ending in `\t` should insert the configured `close` text, once the design for coexisting with normal indent/tab-stop behavior is decided.
- **Behavior:**

  > When a language's autoClosingPairs entry has an `open` string ending in a tab character (e.g. `"begin\t"`), typing the preceding text and then pressing Tab is expected to trigger auto-closing and insert the paired `close` text, the same way it already works for `open` sequences ending in an ordinary character. Currently, pressing Tab never inserts the close text regardless of language configuration, and normal Tab indent/jump behavior must be preserved everywhere this doesn't apply.
- **Trace:**

  > Tab is bound to `CoreEditingCommands.Tab` in src/vs/editor/browser/coreCommands.ts (~L2024-2045), which calls `TypeOperations.tab` -> `TabOperation.getCommands` in src/vs/editor/common/cursor/cursorTypeEditOperations.ts (~L787-825); that path only builds indent/`ShiftCommand`/jump-to-next-indent edits and never calls `_findAutoClosingPairOpen` (~L322-350) or reads `autoClosingPairs.autoClosingPairsOpenByEnd`, which is wired exclusively into the character-typing/composition pipeline (`TypeOperations.typeWithInterceptors` / `CompositionTypeOperation`). Because Tab has its own dedicated command that never funnels through that interceptor pipeline, a pair whose `open` ends in `\t` can never match. Boundary: do not change default Tab indent/jump-to-indent behavior for the common case; any fix must reconcile auto-close matching with Tab's other overloaded roles (snippet tab-stop navigation, suggestion acceptance). Related: https://github.com/microsoft/vscode/issues/583.
- **Open decisions:**
  - Should the Tab key be allowed to trigger autoClosingPairs at all, given it already has overloaded meanings (indent, jump to next indent stop, accept suggestion, navigate snippet placeholders) — or should tab-terminated `open` sequences be documented as unsupported?
  - If supported, should matching an autoClosingPair `open` ending in `\t` take priority over normal indent insertion, and in which contexts (mid-line vs. start-of-line, inside vs. outside an active snippet/suggestion session)?

## Evidence

- **typing path checks autoClosingPairsOpenByEnd:** src/vs/editor/common/cursor/cursorTypeEditOperations.ts `_findAutoClosingPairOpen` (~L322-350) looks up `config.autoClosingPairs.autoClosingPairsOpenByEnd.get(ch)` and supports multi-character `open` sequences (e.g. `begin`), confirming keyword-style auto-closing already works for ordinary characters.
