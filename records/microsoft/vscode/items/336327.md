# Issue #336327 — ripgrep follows symlinks to directories above workspace, 800% CPU and gigabytes of logs

[https://github.com/microsoft/vscode/issues/336327](https://github.com/microsoft/vscode/issues/336327)

## Summary

Real, source-traceable behavior: with the default `search.followSymlinks: true`, VS Code invokes ripgrep with `--follow`, so a workspace symlink pointing at `/` makes ripgrep (via the walkdir crate) traverse the entire filesystem including /proc and /dev, spawning high-CPU processes and massive stderr logs during task-provider and workspaceContains scans. The reporter has already identified and linked the actual upstream fix PRs in ripgrep and walkdir; the root cause and fix live in that dependency, not in VS Code's own search code.

## Change summary

A workspace symlink pointing to `/` causes ripgrep (invoked with `--follow` by VS Code's search/task-provider scans) to traverse the whole filesystem, pegging CPU and flooding stderr logs.

## Best solution

Track upstream: once BurntSushi/ripgrep#3534 and BurntSushi/walkdir#220 merge and ripgrep cuts a release with the fix, bump the bundled `@vscode/ripgrep` version (currently 1.17.1/1.18.0 in package.json) to pick it up. No VS Code-side code change is needed beyond that dependency bump; the `--follow` flag construction in src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts is working as intended given the `search.followSymlinks` setting.
