# Issue #336327 — ripgrep follows symlinks to directories above workspace, 800% CPU and gigabytes of logs

[https://github.com/microsoft/vscode/issues/336327](https://github.com/microsoft/vscode/issues/336327)

## Summary

Keep open as an upstream traversal defect: both linked ripgrep/walkdir fixes remain open. Current VS Code has a loop-error fallback, but it does not prevent following a workspace symlink into ancestor directories or bound the resulting permission-error output.

## Change summary

Prevent background workspace searches from traversing ancestor directories through symlinks and consuming excessive CPU and stderr storage.

## Best solution

Track the ancestor-loop fixes in ripgrep and walkdir through merge and adoption in VS Code's bundled ripgrep. Verify that the reported workspace-reopen scenario avoids scanning the filesystem root while preserving ordinary symlink searches; assess bounded stderr retention separately in the file-search integration.

## Evidence

- **Concrete reported trigger:** https://github.com/microsoft/vscode/issues/336327 supplies a Linux reproduction: create a workspace symlink to /, reopen with built-in npm or TypeScript task discovery enabled, and observe high-CPU rg processes emitting /proc and /dev access errors. No execution was performed in the read-only checkout.
- **Upstream fixes remain pending:** https://github.com/BurntSushi/ripgrep/pull/3534 and https://github.com/BurntSushi/walkdir/pull/220 were both verified OPEN with no merge timestamp. Their descriptions identify ancestor directories above the traversal root as missing from loop detection, covering the parallel ripgrep walker and the single-threaded walkdir path respectively.
- **Current search invocation:** src/vs/workbench/services/search/node/ripgrepFileSearch.ts:getRgArgs passes --follow whenever folderQuery.ignoreSymlinks is false and launches rg with the workspace folder as cwd. Built-in task discovery still uses workspace.findFiles in extensions/npm/src/tasks.ts and extensions/typescript-language-features/src/task/tsconfigProvider.ts; workspaceContains.ts:checkGlobFileExists also invokes file search.
- **Existing mitigation is incomplete:** src/vs/workbench/services/search/node/fileSearch.ts retries without symlink following after RipgrepSymlinkLoopDetector trips. In node/ripgrepSearchUtils.ts, that detector requires more than 1000 stderr lines containing 'File system loop found'; permission-denied messages do not count. This is not an ancestor-traversal prevention mechanism.
- **Unbounded file-search stderr retention:** src/vs/workbench/services/search/node/fileSearch.ts:collectStdout passes stderr to collectData, which appends every Buffer to an array without a size limit. The source therefore retains a resource-amplification path consistent with the reported volume of stderr.
- **Canonical search:** Open-issue searches for symlink/ripgrep, symlink/root, and symlink/loop did not establish an older canonical with the same observable symptom. https://github.com/microsoft/vscode/issues/286778 describes bracket-containing Windows paths, whereas https://github.com/microsoft/vscode/issues/869 requests exclusion-pattern semantics; neither establishes ownership of this ancestor-symlink defect.
