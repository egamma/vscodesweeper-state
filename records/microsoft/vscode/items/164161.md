# Issue #164161 — Git - git reset --hard

[https://github.com/microsoft/vscode/issues/164161](https://github.com/microsoft/vscode/issues/164161)

## Summary

Keep this accepted, community-supported request open: the built-in Git UI still lacks the requested way to reset a local branch to its rewritten remote counterpart. The verified related requests are newer and cannot serve as duplicate canonicals for this re-reviewed item.

## Change summary

Provide a graphical way to fetch and hard-reset the current local branch to its remote counterpart after remote history has been rewritten.

## Best solution

Provide an explicitly destructive, confirmed Git UI operation that leaves the current branch and tracked working tree matching the selected remote target without pushing anything. Settle whether this is a dedicated upstream-reset action or part of a general reset-to-ref interface before implementation.

## Plan brief

- **Likely files:** `extensions/git/package.json`, `extensions/git/src/commands.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/git.ts`
- **Validation:** In disposable local and remote Git repositories, push a branch, amend and force-push it from a second clone, then use only the proposed VS Code UI to fetch and reset the first clone. Verify its current branch HEAD, index, and tracked working tree match the remote tip, branch tracking remains intact, and the remote is unchanged. Repeat with local tracked edits and local commits to verify the agreed warning and discard behavior; cancelling must leave local HEAD, index, and working tree unchanged.
- **Behavior:**

  > A GUI-only user can recover a local branch after someone rewrites its remote history by explicitly abandoning local commits and tracked changes and adopting the latest remote state. Completion leaves the current local branch, index, and tracked working tree matching the chosen remote target without force-pushing or changing the remote. The destructive consequences must be clear before confirmation, and cancellation must leave local branch and file state unchanged. Existing fetch, checkout, and undo-commit behavior remains unchanged.
- **Trace:**

  > The existing reset primitive is Git Repository.reset in extensions/git/src/git.ts, wrapped by Repository.reset in extensions/git/src/repository.ts. The only reset caller found in the built-in command surface is Commands.undoCommit in extensions/git/src/commands.ts, which targets HEAD~ with the default soft mode; package.json has no general reset UI registration. Commands.checkout2 selects an existing tracking branch rather than resetting it, so graph checkout does not resolve the reporter's divergent-history case. The shell-task workaround in https://github.com/microsoft/vscode/issues/164161 also force-pushes and must not define this feature's semantics. Related graph and timeline requests at https://github.com/microsoft/vscode/issues/257433 and https://github.com/microsoft/vscode/issues/327601 may inform interface design but are not older duplicate canonicals. Keep remote mutation, unrelated reset modes, and squashing outside the minimum acceptance scope; the remaining uncertainty is the public UI and confirmation contract, not availability of the underlying Git operation.
- **Open decisions:**
  - Should the initial interface be a dedicated reset-to-current-upstream action, or a general reset-to-ref action that also supports this recovery workflow?
  - What confirmation must users receive before discarding local commits and tracked edits, and how should the chosen remote target be identified in that confirmation?
