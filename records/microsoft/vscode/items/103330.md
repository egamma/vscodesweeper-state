# Issue #103330 — Improve debug actions for multi-target debugging

[https://github.com/microsoft/vscode/issues/103330](https://github.com/microsoft/vscode/issues/103330)

## Summary

A real multi-target debugging gap remains on current main: Continue and Pause operate on one focused or contextual thread, and the Call Stack view has no multi-selection path for applying an action across processes. The issue should remain open in the debug backlog for a product decision about all-target versus selected-target controls.

## Change summary

Allow Continue, Pause, and potentially other debug actions to run across all or a selected set of concurrent debug processes.

## Best solution

Provide coherent group actions for compound and multi-target sessions, preferably through selectable targets in the Call Stack view, while retaining the existing focused-target behavior for ordinary F5/F6 actions. The debug area should first settle whether the supported scope is all sessions, an explicit selection, or both.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugCommands.ts`, `src/vs/workbench/contrib/debug/browser/callStackView.ts`, `src/vs/workbench/contrib/debug/test/browser/callStack.test.ts`
- **Validation:** Extend the debug browser tests to create multiple concurrent sessions, select the agreed target scope, invoke Continue or Pause, and assert that the action reaches every selected target while leaving unselected targets unchanged; retain coverage that ordinary focused-target commands affect only the focused target.
- **Behavior:**

  > Users debugging a compound configuration with multiple processes need a single operation that applies Continue or Pause to the intended group instead of repeating the action process by process. The existing single-target Continue and Pause behavior must remain available. Acceptance should verify the chosen all-target or selected-target semantics across multiple sessions and verify that targets outside the chosen scope are unaffected.
- **Trace:**

  > Current commands route through getThreadAndRun in src/vs/workbench/contrib/debug/browser/debugCommands.ts, which resolves one thread from the command context or focused session before invoking Pause or Continue. CallStackView in src/vs/workbench/contrib/debug/browser/callStackView.ts maintains a singleton focused selection and registers inline actions only for an individual thread or single-thread session. The source therefore confirms that compound sessions have no group-action path. https://github.com/microsoft/vscode/issues/137953 covers automatically pausing peers after a stop and should be considered during design, but it is younger and does not replace this request. Preserve ordinary single-target command semantics and avoid changing debug-adapter thread behavior within one process unless the chosen product scope explicitly includes it.
- **Open decisions:**
  - Should group debug actions target every active session in the compound, only an explicit Call Stack selection, or offer both scopes?
  - Should group controls appear in the global debug toolbar, the Call Stack view, or both, and how should the UI communicate a mixed running/stopped selection?

## Evidence

- **current command behavior:** On current main, src/vs/workbench/contrib/debug/browser/debugCommands.ts:144-171 resolves exactly one contextual or focused thread in getThreadAndRun; the Pause and Continue handlers at lines 550-558 and 684-693 each invoke the action only on that thread.
- **current Call Stack behavior:** src/vs/workbench/contrib/debug/browser/callStackView.ts:416-428 explicitly replaces the tree selection with a single focused element, while lines 1138-1143 register Pause and Continue actions for an individual thread or single-thread session. No group-selection action is present.
- **related issue:** https://github.com/microsoft/vscode/issues/137953 is open but younger and requests the inverse automatic behavior—pausing other processes when one process breaks—rather than manually continuing or pausing a selected group. Under the re-review duplicate rule it is related, not a canonical duplicate.
- **older precedents:** https://github.com/microsoft/vscode/issues/5643 and https://github.com/microsoft/vscode/issues/36394 concern controlling multiple threads within one debug adapter, not coordinating separate targets in a compound session; both are closed and therefore cannot serve as duplicate canonicals.
- **maintainer direction:** A debug maintainer suggested Call Stack multi-selection as a possible direction but noted unresolved focus-management complexity; the issue remains assigned to the Backlog milestone with the existing feature-request and debug labels.
