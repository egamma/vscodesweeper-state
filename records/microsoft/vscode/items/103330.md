# Issue #103330 — Improve debug actions for multi-target debugging

[https://github.com/microsoft/vscode/issues/103330](https://github.com/microsoft/vscode/issues/103330)

## Summary

The request remains unmet: current debug commands act on one session's thread, not all or a selected group of debug targets. Keep this accepted backlog request open; the related automatic-pause request does not own the same behavior.

## Change summary

Provide debug actions that operate on all or a selected group of concurrently debugged processes.

## Best solution

Provide an explicit bulk-control workflow for multi-target debugging while preserving existing single-target controls. Settle whether the supported scope is all targets, selected targets, or both, and whether the workflow belongs in core or an extension.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugCommands.ts`, `src/vs/workbench/contrib/debug/browser/callStackView.ts`, `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`
- **Validation:** Launch a compound containing at least three independently stoppable debug targets and pause each at a breakpoint. Verify one bulk Continue invocation resumes exactly the intended targets, leaves excluded targets paused when subset selection is supported, and preserves ordinary single-target Continue behavior.
- **Behavior:**

  > Users debugging many concurrent processes currently have to repeat execution controls for each target. Provide an explicit operation that applies a supported debug action to the intended group without repeated per-target invocation. Acceptance must cover continuing multiple stopped targets, preserving ordinary single-target controls, and making the affected target scope clear. Whether that group means all targets, selected targets, or both requires a product decision.
- **Trace:**

  > In src/vs/workbench/contrib/debug/browser/debugCommands.ts, Continue and Pause call getThreadAndRun, which resolves one contextual or focused thread within one session. CallStackView in src/vs/workbench/contrib/debug/browser/callStackView.ts is the surface suggested by the maintainer for selection-based controls; debug.contribution.ts registers the debug contribution surface. Compound stopAll only coordinates termination and is not coverage for execution controls. Preserve existing single-target command and focus semantics; automatic suspension when another target breaks is separate work tracked by https://github.com/microsoft/vscode/issues/137953. The maintainer discussion at https://github.com/microsoft/vscode/issues/103330#issuecomment-1307999660 leaves both selection design and extension ownership unresolved; no implementation or runtime validation was performed.
- **Open decisions:**
  - Should bulk controls operate on all debug targets, an explicitly selected subset, or support both scopes?
  - Should this cross-target workflow be provided by core debug UI or by an extension?
  - Should the initial capability cover Continue and Pause only, or also coordinated stepping actions?

## Evidence

- **Current command behavior:** src/vs/workbench/contrib/debug/browser/debugCommands.ts:144–171 resolves a single contextual or focused thread in getThreadAndRun. workbench.action.debug.continue at lines 685–691 and workbench.action.debug.pause at lines 551–557 invoke that helper, without dispatch across sessions.
- **Existing capability is partial:** src/vs/workbench/contrib/debug/common/debugSchemas.ts exposes compound stopAll, but its documented behavior is terminating the other compound sessions when one is manually terminated. It does not provide bulk Continue, Pause, or stepping; compound launch already supplies the concurrent startup described in the report.
- **Maintainer discussion:** https://github.com/microsoft/vscode/issues/103330#issuecomment-1307999660 suggests call-stack multiselect, flags focus-management difficulty, and says this could be an extension candidate. This is exploratory, not a decision to decline core support.
- **Related issue is not a canonical:** https://github.com/microsoft/vscode/issues/137953 is currently open and requests automatically pausing other processes when one breaks. Its discussion explicitly treats continuing all processes as separate work. It is also newer than this re-reviewed item, so it cannot satisfy the stronger duplicate bar.
- **Extension precedent has narrower scope:** https://github.com/microsoft/vscode/issues/36394 is closed and concerns controlling multiple threads within a Java debug session. Its discussion recommends debug/callstack/context contributions and adapter customRequest calls, but does not establish a disposition for this cross-session, multi-process request.

Searches for continue-all, multi-target debugging, all-session controls, and multiple selection found no verified older open canonical covering this request.
