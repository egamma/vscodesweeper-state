## Evidence

- **Cell and metadata identity loss:** src/vs/workbench/services/notebook/common/notebookDocumentService.ts: generate encodes only the handle and scheme into the child fragment, and parse reconstructs the notebook with fragment: null. generateMetadataUri and parseMetadataUri likewise replace and discard the notebook fragment. The reported left/right notebook URIs therefore generate identical cell and metadata URIs.
- **Output round-trip failure:** src/vs/workbench/contrib/notebook/common/notebookCommon.ts:603-612 generates editor output URIs while retaining the original fragment, but extractCellOutputDetails in notebookDocumentService.ts interprets that fragment as a cell encoding or reconstructs the notebook with fragment: null. The supplied root/revision/side fragment is not restored.
- **Affected resolution paths:** NotebookDocumentWorkbenchService.getNotebook in notebookDocumentService.ts looks up the parsed parent in its ResourceMap. src/vs/workbench/contrib/notebook/common/notebookEditorModelResolverServiceImpl.ts:210-225 parses a cell URI before canonicalization and existing-model lookup, so the discarded fragment cannot distinguish the already-loaded revision.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/349400 is currently open, as verified from its public page, and is explicitly identified as the fix PR in https://github.com/microsoft/vscode/issues/349408. It proposes fragment preservation and round-trip/document-lookup tests; it is not a landed fix.
