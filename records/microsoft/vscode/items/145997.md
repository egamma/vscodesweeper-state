# Issue #145997 — Revisit storing entire search results in memento

[https://github.com/microsoft/vscode/issues/145997](https://github.com/microsoft/vscode/issues/145997)

## Summary

Keep open: dirty Search Editors still serialize every match range into workspace state, so the storage cleanup remains necessary. The earlier dirty-only restriction reduced the scope but did not implement the requested file-backed persistence.

## Change summary

Move bulky Search Editor restoration data out of storage-service mementos into file-backed persistence while preserving restored results and highlights.

## Best solution

Keep lightweight Search Editor configuration and references in workspace state, with bulk restoration data persisted through file-backed storage. Preserve dirty-editor recovery, existing serialized-state compatibility, and working-set restoration without accumulating orphaned files.

- **Behavior:**

  > A large search opened as a dirty Search Editor must not put its complete per-match restoration metadata into workspace-state values. Restarting must preserve the dirty results, search configuration, and match highlights. Existing persisted editors must remain recoverable, and named working sets must retain their existing restoration behavior. Lightweight search settings may continue using mementos.
- **Trace:**

  > SearchEditorInputSerializer in src/vs/workbench/contrib/searchEditor/browser/searchEditor.contribution.ts still emits getMatchRanges() for dirty inputs and restores those ranges during deserialization. EditorGroupModel.serialize(), EditorGroupView serialization, and EditorPart.saveState() carry that string into the workspace memento. SearchEditorInput.backup() already persists result text through working-copy backups, and SearchEditorModelFactory.tryFetchModelFromBackupService() restores that text and configuration. EditorParts.saveWorkingSet() also retains serialized editor state, so bulk-data lifetime extends beyond the immediate shutdown snapshot. The trace establishes the remaining payload but does not yet establish safe write ordering, migration, or cleanup across backup and working-set consumers; planning should complete that lifecycle analysis without changing visible Search Editor behavior. The accepted disk-storage direction is recorded in https://github.com/microsoft/vscode/issues/145997; https://github.com/microsoft/vscode/issues/145428 concerns a separate saved-file highlighting symptom.
