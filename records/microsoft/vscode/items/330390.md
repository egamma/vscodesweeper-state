# Issue #330390 — Chat view does not show active file indicator when opening a file in Markdown Editor Mode

[https://github.com/microsoft/vscode/issues/330390](https://github.com/microsoft/vscode/issues/330390)

## Summary

Traced a real gap in core: the Markdown Editor (WYSIWYG) custom text editor has no registered chat context provider and isn't a Monaco code editor, so ChatImplicitContextContribution's webview branch never resolves a fallback active-file value for it — matches the reporter's exact symptom and the 'switching to Text Editor mode fixes it' observation.

## Change summary

Chat view's active-file indicator never appears while a Markdown file is open in the new Markdown Editor (WYSIWYG custom editor) mode.

## Best solution

Decide, in src/vs/workbench/contrib/chat/browser/attachments/chatImplicitContext.ts, whether custom text editors backed by a real TextDocument (like vscode.markdown.editor) should fall back to attaching their resource as implicit file context when no chat context provider is registered for the viewType — this is a scoping decision (which custom editors should get this fallback vs. non-text webviews like image previews) rather than a pure mechanical fix.

## Evidence

- **custom editor registration:** extensions/markdown-language-features/src/preview/markdownEditorProvider.ts defines `MarkdownEditorProvider implements vscode.CustomTextEditorProvider` for viewType 'vscode.markdown.editor' (also declared as `"viewType": "vscode.markdown.editor"` in extensions/markdown-language-features/package.json).
- **custom editor input is a WebviewInput:** src/vs/workbench/contrib/customEditor/browser/customEditorInput.ts: `CustomEditorInput extends LazilyResolvedWebviewEditorInput` (src/vs/workbench/contrib/webviewPanel/browser/webviewWorkbenchService.ts:114), which itself `extends WebviewInput` — so findActiveWebviewEditor() in chatImplicitContext.ts does match it.
- **no fallback without a provider:** src/vs/workbench/contrib/chat/browser/attachments/chatImplicitContext.ts lines 252-258: `newValue` is only overwritten with `webviewContext` if `chatContextService.contextForResource(webviewEditor.input.resource, undefined, webviewEditor.input.viewType)` returns a value; there is no unconditional fallback to `webviewEditor.input.resource` itself.
- **no registered provider for this viewType:** `grep -rl "registerChatContextProvider" extensions/` found no matches — no built-in extension (including markdown-language-features) registers a chat context provider, so `contextForResource` returns undefined for 'vscode.markdown.editor'.
- **code editor path finds nothing:** findActiveCodeEditor() in the same file relies on ICodeEditorService/getVisibleTextEditorControls, which won't surface a Monaco editor for a webview-rendered custom editor — consistent with the reporter's observation that switching to Text Editor mode (a real Monaco editor) immediately restores the indicator.
