# Issue #292587 — [Feature Request] User-Contributed Accessibility Help System

[https://github.com/microsoft/vscode/issues/292587](https://github.com/microsoft/vscode/issues/292587)

## Summary

Keep open: current accessibility help supports developer-authored providers and extension view contributions, but not user-defined help through settings. The attached design establishes a real gap; its broader verbosity, announcement, and focus-restoration changes need a maintainer design pass.

## Change summary

Allow users to customize context-specific Alt+F1 accessibility help through settings, with built-in fallback and optional appended content.

## Best solution

Provide an opt-in customization layer for existing accessibility help contexts while preserving localized defaults, dynamic keybindings, and provider-specific focus restoration. Agree on the first-release scope before adopting the attachment's wider announcement and verbosity redesign.

- **Behavior:**

  > Users should be able to supply context-specific Alt+F1 help through settings without authoring an extension or TypeScript provider. Unconfigured contexts must retain their built-in localized help, and supported keybinding references must reflect current bindings. The proposal requests both replacement and appended content; acceptance should cover their agreed semantics and ensure dismissing customized help preserves the existing return-focus behavior. Global verbosity and announcement changes are separate scope decisions, not prerequisites established by the central request.
- **Trace:**

  > AccessibleViewRegistry in src/vs/platform/accessibility/browser/accessibleViewRegistry.ts stores implementations selected by context and priority; AccesibleViewContributions in src/vs/workbench/contrib/accessibility/browser/accessibleViewContributions.ts connects them to AccessibilityHelpAction and IAccessibleViewService.show(). The display implementation in src/vs/workbench/contrib/accessibility/browser/accessibleView.ts reads provider.provideContent(), checks existing verbosity settings, and invokes provider.onClose(). accessibilityConfiguration.ts exposes hint toggles but no user-content setting. ExtensionAccessibilityHelpDialogContribution supports extension-authored view content, not user customization of built-in help. Preserve Accessible View content, provider-specific dynamic help, current keybinding resolution, and return-focus behavior unless the maintainer explicitly approves a broader change. The design attached to https://github.com/microsoft/vscode/issues/292587 is a proposal, not an approved settings or extension contract; uncertainty begins at its new global controls and context-identifier semantics.
- **Open decisions:**

  - Which context identifiers form the supported user-facing settings contract, and does the initial release include extension-provided contexts?
  - Should existing per-feature focus-restoration behavior remain authoritative, or should this feature introduce the attachment's universal restoration behavior across help contexts?
