# Issue #268102 — Chat fetch tool can't read content from my private GitHub repos

[https://github.com/microsoft/vscode/issues/268102](https://github.com/microsoft/vscode/issues/268102)

## Summary

Keep open: the fetch tool still uses an unauthenticated browser, and existing repository search does not retrieve private issue discussions by URL. The maintainer explicitly retained this request pending a decision between authenticated GitHub fetching and relying on GitHub MCP.

## Change summary

Let Chat retrieve private GitHub content from a supplied URL using an authorized account, rather than returning an unexpected anonymous-access 404.

## Best solution

Settle whether private GitHub URLs should be handled through authenticated API retrieval or an available GitHub MCP tool, with a clear explanation when neither can access the resource. Preserve anonymous fetching for ordinary web pages; an explanatory message alone does not deliver the remaining content-access request.

Verify the chosen path retrieves the requested content or clearly explains unavailable access; also check a public page, an inaccessible repository, and existing fetch approval/network restrictions. Add mocked tool tests for the selected contract without accessing real private data.
- **Behavior:**

  > A user signed into GitHub asks Chat to read a private repository URL that works in their browser, but the fetch tool receives an anonymous-access 404. The desired experience makes authenticated GitHub context accessible through the chosen supported tool path, or explains why access is unavailable without implying the resource necessarily does not exist. Acceptance must distinguish public content, authorized private content, and content the account cannot access. If issue or PR retrieval is supported, define whether the returned context includes the discussion.
- **Trace:**

  > The Copilot FetchWebPageTool wrapper delegates to vscode_fetchWebPage_internal; the core FetchWebPageTool sends web URLs to IWebContentExtractorService.extract. NativeWebContentExtractorService creates WebPageLoader with a fresh browser partition, so GitHub sign-in is not inherited and no authenticated API translation occurs on this path. GithubRepoSemanticSearchTool provides repository code search, not issue-discussion retrieval by URL. The maintainer outlines API translation and possible discussion fetching at https://github.com/microsoft/vscode/issues/268102#issuecomment-3335915818, then leaves API retrieval versus GitHub MCP unresolved at https://github.com/microsoft/vscode/issues/268102#issuecomment-3579777524. Preserve ordinary anonymous web fetching, isolated browser sessions, and existing approval/network restrictions; do not solve this by sharing browser cookies. Inspection was read-only, with no live private-repository reproduction.
- **Open decisions:**
  - Should the built-in fetch experience support authenticated GitHub API retrieval when GitHub MCP is unavailable, or explicitly delegate private GitHub URLs to MCP and explain the limitation when it is absent?
  - If authenticated retrieval is selected, which GitHub URL kinds are supported, and should issue/PR results include the complete discussion rather than only the initial body?
