# Issue #202957 — Allow to move workspace state

[https://github.com/microsoft/vscode/issues/202957](https://github.com/microsoft/vscode/issues/202957)

## Summary

Keep this accepted, well-supported request open: current workspace identity remains path-dependent, and existing workspace-saving commands do not cover relocating a project with its state. No verified older, open canonical owns the same request; a maintainer-guided design session is warranted.

## Change summary

Provide a supported way to retain workspace state when relocating a project folder or its .code-workspace file.

## Best solution

Provide a supported relocation or state-reassociation workflow in the workspace and storage services, preserving relevant state and remapping project-relative resources without transferring trust implicitly. Decide the user-facing migration model and supported state categories before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/workspaces/node/workspaces.ts`, `src/vs/platform/storage/electron-main/storageMain.ts`, `src/vs/workbench/browser/actions/workspaceActions.ts`, `src/vs/workbench/services/workspaces/browser/abstractWorkspaceEditingService.ts`, `src/vs/workbench/services/workspaces/electron-browser/workspaceEditingService.ts`
- **Validation:** After agreeing the supported state categories, create a project with multiple open tabs, distinct cursor positions, layout state, and a saved chat session; relocate it through the chosen supported workflow and reopen it. Verify retained state refers to the new project location and survives a window reload, and separately verify that a similarly named unrelated folder does not inherit its state or trust. Cover both single-folder and saved .code-workspace cases within the agreed scope.
- **Behavior:**

  > Users need a supported way to relocate a project without manually editing internal workspace-storage files or losing access to its editor context. The issue includes opened tabs, file history, and Copilot conversations, but does not settle the exact state categories or whether migration is explicit or automatic. Acceptance should demonstrate retention of the agreed categories at the new location after reload, with project resources resolving correctly and no implicit transfer of workspace trust.
- **Trace:**

  > getWorkspaceIdentifier and getSingleFolderWorkspaceIdentifier in src/vs/platform/workspaces/node/workspaces.ts derive identity from location; WorkspaceStorageMain in src/vs/platform/storage/electron-main/storageMain.ts uses that identity to select the state database. SaveWorkspaceAsAction in src/vs/workbench/browser/actions/workspaceActions.ts reaches AbstractWorkspaceEditingService.saveAndEnterWorkspace, which rewrites the workspace configuration and enters the target; NativeWorkspaceEditingService.enterWorkspace invokes a storage switch and workspace-entry participants. These existing transitions are relevant prior art but do not establish general relocation of project resources and every state category. The remaining uncertainty is the migration contract and inventory of state owners, including state outside the database; preserve existing identity compatibility and keep trust decisions independent. https://github.com/microsoft/vscode/issues/318946 is a newer same-goal report, while https://github.com/microsoft/vscode/issues/305818 tracks narrower chat recovery.
- **Open decisions:**
  - Should the supported experience be an explicit relocation/reassociation command, an export/import workflow, or automatic recognition when a workspace is reopened at a new location?
  - Which state categories must the initial feature preserve, and does its supported scope include transfers between machines as well as relocation on the same machine?
  - When the destination already has workspace state, should migration replace it, merge supported categories, or require the user to choose which state to retain?

This is an existing in-window workspace-save transition, not a general workflow for recovering or moving all state after the project folder itself moves; it does not establish coverage of the central request.
