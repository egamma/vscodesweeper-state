# Issue #298599 — Support multi-instance supervision and 24h scheduled autonomous workflows in Copilot

[https://github.com/microsoft/vscode/issues/298599](https://github.com/microsoft/vscode/issues/298599)

## Summary

Current main already provides scheduled automations and consolidated monitoring across registered session providers, but that does not establish full coverage of supervision across independent VS Code instances or continuous 24-hour workflows. Keep this open to define the remaining coordination and execution requirements; the verified related requests cover only narrower parts.

## Change summary

Provide centralized supervision of Copilot work across multiple VS Code instances and optional scheduled or long-running autonomous workflows with safety controls and audit logs.

## Best solution

Build on the existing Agents window and Automations capabilities rather than introduce a separate supervisory surface. Establish whether provider-backed multi-project sessions satisfy the intended supervision model, and specify any remaining cross-instance coordination, continuous execution, and audit requirements.

## Plan brief

- **Likely files:** `src/vs/sessions/services/sessions/browser/sessionsManagementService.ts`, `src/vs/sessions/contrib/automations/browser/providerAutomationService.ts`, `src/vs/sessions/contrib/automations/browser/automations.contribution.ts`, `src/vs/workbench/contrib/chat/common/automations/automation.ts`, `src/vs/workbench/contrib/chat/common/automations/automationService.ts`
- **Validation:** The plan should define a runnable acceptance scenario with two repositories and the chosen supervision targets: observe both sessions centrally, run a predefined workflow on a daily schedule, cancel it, and inspect its recorded outcome. If continuous 24-hour execution is included, separately verify the agreed permission, timeout, interruption, and audit behavior over that duration.
- **Behavior:**

  > The goal is to supervise and coordinate Copilot work across multiple projects from one interface and optionally execute predefined workflows on a schedule or for an extended period. Existing recurring Automations and consolidated provider-backed monitoring should remain usable without enabling broader autonomy. Acceptance must distinguish a daily recurring run from a continuously executing 24-hour workflow and demonstrate the selected model's cancellation, safety, and audit behavior.
- **Trace:**

  > ProviderAutomationService in src/vs/sessions/contrib/automations/browser/providerAutomationService.ts combines definitions and run history across registered providers while leaving execution and persistence with those providers. SessionsManagementService._subscribeToProviders in src/vs/sessions/services/sessions/browser/sessionsManagementService.ts observes provider-owned sessions. The automation contracts in src/vs/workbench/contrib/chat/common/automations/automation.ts already model schedules, explicit targets, session templates, and lifecycle records; the contribution registers enablement and timeout settings, with a 30-minute default per run. These paths establish partial coverage but do not establish automatic discovery or control of arbitrary editor windows, continuous multi-project orchestration, or a comprehensive audit contract. Preserve provider authority and existing scheduling behavior. https://github.com/microsoft/vscode/issues/329155 concerns cross-host delegation display, and https://github.com/microsoft/vscode/issues/329209 concerns richer schedule syntax; neither owns this entire request.
- **Open decisions:**
  - Should supervision cover independently opened VS Code windows and their existing interactive sessions, or only project sessions exposed through connected Agents-window providers?
  - Does the autonomous mode mean recurring daily runs, continuously executing workflows lasting up to 24 hours, or both?
  - What coordination operations, unattended permission boundaries, and retained audit information are required beyond the existing session controls and automation run history?

## Evidence

- **Existing scheduling capability:** src/vs/workbench/contrib/chat/common/automations/automation.ts defines hourly, daily, weekdays, weekly, manual, and custom schedules, workspace targets, session templates, and run records with status, timestamps, errors, and needs-input state. src/vs/sessions/contrib/automations/browser/automations.contribution.ts registers chat.automations.enabled and chat.automations.runTimeoutMinutes. These cover recurring execution and basic run history, not necessarily continuous autonomous coordination or the requested audit guarantees.
- **Existing consolidated monitoring:** ProviderAutomationService in src/vs/sessions/contrib/automations/browser/providerAutomationService.ts aggregates automation definitions and runs across registered Sessions providers and routes operations to their owning provider. SessionsManagementService._subscribeToProviders in src/vs/sessions/services/sessions/browser/sessionsManagementService.ts subscribes to each provider's sessions and changes. This establishes multi-provider monitoring, not automatic supervision of every independently opened VS Code window.
- **Execution boundary:** src/vs/workbench/contrib/chat/common/automations/automationsEnabled.ts sets the default per-run timeout to 30 minutes. assertAutomationTargetAuthority in src/vs/workbench/contrib/chat/common/automations/automationService.ts explicitly rejects moving an automation between Agent Hosts because there is no history-preserving cross-host transfer operation. Neither recurring scheduling nor provider aggregation alone proves the requested continuous, coordinated 24-hour workflow.
