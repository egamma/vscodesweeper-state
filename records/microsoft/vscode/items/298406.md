# Issue #298406 — Add Remote Control Support to GitHub Copilot Chat

[https://github.com/microsoft/vscode/issues/298406](https://github.com/microsoft/vscode/issues/298406)

## Summary

This remains a well-supported feature request with 46 community upvotes. Current remote-tunnel and CLI capabilities do not clearly provide synchronized remote control of an existing local VS Code Copilot Chat session, and the previously cited implementation was independently refuted.

## Change summary

Allow a user to continue controlling an ongoing local VS Code Copilot Chat session from a browser, mobile device, or another machine while preserving synchronized history and context.

## Best solution

Define a secure session-handoff and synchronization model for VS Code Chat that preserves the local agent's workspace context while allowing an authenticated remote client to observe and guide the same ongoing session. The design should clarify lifecycle, permissions, connectivity, and which operations remain local before implementation begins.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat`, `src/vs/platform/agentHost`
- **Validation:** An end-to-end scenario should start a local VS Code Copilot Chat agent session, connect through an authenticated browser or mobile-capable client, exchange messages from both surfaces, and verify that history, turn ordering, session state, permissions, and disconnect/reconnect behavior remain synchronized without downgrading the local agent.
- **Behavior:**

  > A user can securely connect from another browser or device to an ongoing local VS Code Copilot Chat session and continue guiding that same session. Messages and conversation history remain ordered and synchronized on every connected surface, while workspace execution and context continue to be owned by the originating VS Code environment. Reconnection must restore the active conversation without creating an unrelated CLI session or losing prior turns.
- **Trace:**

  > The request concerns VS Code's core Copilot Chat session rather than a third-party extension or a separate Copilot CLI conversation. Commenters report that remote tunnels can expose a browser surface only in a limited CLI-agent scenario, which does not satisfy remote control of the more capable local-agent session. The relevant architecture spans the chat session lifecycle under src/vs/workbench/contrib/chat and agent-host/session transport under src/vs/platform/agentHost; the exact boundary requires design before a bounded file list can be established. Preserve the distinction between remotely viewing or controlling an existing session and starting a separate remote or CLI session. No older canonical issue with the same observable request was established, and the previously proposed fix commit is expressly refuted.
- **Open decisions:**
  - Which remote clients are supported initially: authenticated vscode.dev/browser sessions only, or GitHub Mobile as part of the public contract?
  - Which local-agent actions may a remote client authorize or invoke, particularly terminal commands, file edits, confirmations, and sensitive workspace access?
  - Does control permit multiple simultaneously active clients, and if so, what ordering and ownership semantics are visible when messages or approvals race?
  - What session behavior should users observe when the originating VS Code window disconnects, sleeps, closes, or reconnects?
