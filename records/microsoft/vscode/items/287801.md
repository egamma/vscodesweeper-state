# Issue #287801 — MCP prompt arguments cannot reliably accept binary file data

[https://github.com/microsoft/vscode/issues/287801](https://github.com/microsoft/vscode/issues/287801)

## Summary

The binary-input corruption remains directly traceable on current main: file arguments are decoded as UTF-8 without validation before being sent to the MCP server. Keep this team-authored bug open; the remaining product decision is how binary selections should be represented without breaking existing text-content arguments.

## Change summary

Prevent binary files selected as MCP prompt arguments from being silently corrupted by UTF-8 decoding.

## Best solution

Define an explicit, server-compatible contract for binary file arguments in McpPromptArgumentPick, preserving existing text-content workflows. A path-only solution must account for remote MCP servers and URI schemes that the server cannot access.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/browser/mcpPromptArgumentPick.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCompletions.ts`, `src/vs/workbench/contrib/mcp/common/mcpTypes.ts`
- **Validation:** After choosing the contract, add a browser unit test driving McpPromptArgumentPick.createArgs() with mocked file and QuickPick services and a byte sequence containing invalid UTF-8. Assert the agreed exact argument value or explicit rejection, and verify ordinary UTF-8 files, selected text, and cancellation retain their intended behavior. Manually invoke a parameterized MCP prompt with a PNG and inspect the server-received argument, including a remote-server case if paths are supported.
- **Behavior:**

  > Selecting a binary file for an MCP prompt argument currently silently replaces invalid UTF-8 bytes before the server receives the value. The completed behavior must not present a lossy string as successfully transferred binary content. Establish the binary-input contract explicitly and preserve existing text-file and selected-text workflows unless a deliberate compatibility change is approved. Acceptance must inspect the exact server-facing argument, not merely whether the picker completes.
- **Trace:**

  > McpPromptArgumentPick._fileCompletions creates action 'file' entries, and _getArg reads the selected resource and calls VSBuffer.toString() without checking whether the bytes are text. VSBuffer.toString() in src/vs/base/common/buffer.ts uses non-fatal UTF-8 decoding, conclusively explaining the reported corruption without execution. chatInputCompletions.ts passes createArgs() to prompt.resolve(), and McpPrompt.resolve in mcpServer.ts forwards the resulting strings to prompts/get. Existing text-content semantics are documented by the verification discussion at https://github.com/microsoft/vscode/issues/252045#issuecomment-3353834862. The uncertainty is the server-visible representation of binary selections, not the location of the lossy conversion. A client-local path or URI is not inherently readable by a remote server; preserve other argument sources and avoid extending this work into general chat attachment handling.
- **Open decisions:**
  - For a binary file selection, should VS Code offer a path/URI, explicitly selected base64 content, or reject the selection with an explanation, and how will the server know which representation it receives?
  - Should path/URI input be a separate explicit choice that preserves today's text-content behavior, or should selecting files change semantics for existing prompts?

## Evidence

- **Current failing path:** src/vs/workbench/contrib/mcp/browser/mcpPromptArgumentPick.ts:223-225 still handles action 'file' by calling readFile(value.uri) followed by c.value.toString(), with no binary detection, encoding choice, or warning. Selecting a PNG through file search therefore reaches the exact conversion reported in https://github.com/microsoft/vscode/issues/287801.
- **Lossy decoding:** src/vs/base/common/buffer.ts:125-132 implements VSBuffer.toString() using Buffer.toString() or a default TextDecoder. Both decode as UTF-8 with replacement of invalid sequences; the original bytes cannot be recovered from the resulting argument string. This is argument corruption, not evidence that the source file itself is modified.
