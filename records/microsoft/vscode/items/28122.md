# Issue #28122 — Activate extension with workspaceContains when a matching file is added to the workspace

[https://github.com/microsoft/vscode/issues/28122](https://github.com/microsoft/vscode/issues/28122)

## Summary

Keep open: current source checks workspaceContains at startup, when workspace folders are added, and when extensions are added, but does not monitor subsequent matching-file creation. The discussed onStartupFinished workaround activates the extension beforehand, so it does not deliver the requested conditional activation.

## Change summary

Activate an inactive extension when a file matching its workspaceContains pattern is added to an already-open workspace.

## Best solution

Provide first-party matching-file activation in the extension lifecycle without requiring each extension to activate solely to install its own watcher. Design the monitoring around startup and large-workspace performance while preserving existing activation and search semantics.

- **Fit:** aligned

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostExtensionService.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/services/extensions/common/workspaceContains.ts`, `src/vs/workbench/services/extensions/common/extensionsRegistry.ts`
- **Validation:** Use a development extension declaring only workspaceContains:**/*.md. Open a workspace without Markdown files, confirm the extension remains inactive, then create a nested Markdown file without opening it or reloading and confirm activation. Repeat with external file creation and a remote workspace; verify nonmatching additions do not activate it, additional matches do not reactivate it, and existing startup and added-folder activation still work. Assess watcher and search overhead in a large workspace before accepting the design.
- **Behavior:**

  > An extension declaring workspaceContains:**/*.md remains inactive while an open workspace has no matching file. Adding a matching file activates it without requiring a reload, opening that file, or unconditional startup activation. Nonmatching additions do not activate it, and subsequent matching additions do not activate an already-active extension again. Existing activation for matching files present at startup or in newly added workspace folders remains intact.
- **Trace:**

  > In src/vs/workbench/api/common/extHostExtensionService.ts, _handleEagerExtensions checks initial folders and subscribes to workspace-folder additions; _handleWorkspaceContainsEagerExtension delegates to checkActivateWorkspaceContainsExtension. The helper in src/vs/workbench/services/extensions/common/workspaceContains.ts performs exact-path or glob existence checks and has no persistent monitoring. AbstractExtensionService._activateAddedExtensionIfNeeded in src/vs/workbench/services/extensions/common/abstractExtensionService.ts separately handles newly added extensions, which does not cover subsequent file creation. The onStartupFinished workaround activates the extension to run its own detection, so it leaves the central activation gap intact. Preserve existing matching, cancellation, host separation, and activation idempotence; do not fold directory matching from https://github.com/microsoft/vscode/issues/2739 or extension-install behavior from https://github.com/microsoft/vscode/issues/242245 into this request. The remaining design investigation is how monitoring integrates with local, remote, and provider-backed filesystems without costly repeated workspace searches.
