# Issue #347351 — Agent Host BYOK bridge hardcodes 128-tool ceiling; no way for a provider to declare the model's real tool limit

[https://github.com/microsoft/vscode/issues/347351](https://github.com/microsoft/vscode/issues/347351)

## Summary

The provider-specific tool-limit gap remains on current main: the bridge unconditionally caps requests at 128. Numeric tool-count metadata already exists in the public API, contrary to the report, but is discarded internally; related tool-search work does not cover requests with search disabled.

## Change summary

Allow BYOK providers to declare their model's maximum tool-definition count instead of always applying the bridge's 128-tool ceiling.

## Best solution

Honor provider-declared tool limits end to end, preferably using the existing numeric capabilities.toolCalling contract, while retaining a conservative fallback for undeclared models. Coordinate with the open tool-search proposal without treating deferral as a replacement for accurate limits.

- **Behavior:**

  > A BYOK model capable of accepting more than 128 tool definitions should not lose tools solely because of the bridge's default. Provider-declared lower limits must also be respected, while undeclared models retain the existing fallback. Acceptance must include search-disabled requests, since tool-search deferral alone does not satisfy this request.
- **Trace:**

  > capBridgeTools defaults to BYOK_MAX_TOOLS = 128 in src/vs/platform/agentHost/node/copilot/byokResponsesTranslation.ts, and ByokLmProxyService invokes it without model-specific metadata. The public LanguageModelChatCapabilities.toolCalling contract in src/vscode-dts/vscode.d.ts already permits a numeric maximum, but extHostLanguageModels.ts coerces that value to boolean and ILanguageModelChatMetadata retains only that boolean. AgentHostByokLmHandler.listModels and IByokLmModelInfo also omit the ceiling. Existing proxy and translation tests pin capping and history-aware selection; preserve their ordering and continuation behavior. https://github.com/microsoft/vscode/pull/344839 separately proposes tool-search capability plumbing and cap bypass; coordinate with it rather than duplicating that work. The remaining uncertainty is the public interpretation of boolean support and how declared limits interact with tool-search-enabled requests.
- **Open decisions:**
  - Should numeric capabilities.toolCalling be the authoritative ceiling across local and Agent Host requests, with boolean true preserving the existing fallback?
  - When tool search is enabled, should a declared ceiling constrain only the tool definitions actually forwarded on each request, or should explicit tool-search support bypass that ceiling?
