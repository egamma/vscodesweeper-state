# Issue #137324 — Merge Conflict incorrectly removing conflict markers

[https://github.com/microsoft/vscode/issues/137324](https://github.com/microsoft/vscode/issues/137324)

## Summary

This is a verified duplicate of an older, open report covering the same incorrect deletions when conflict-resolution CodeLenses lag behind document edits. Consolidate on that issue while preserving this report's manual-edit trigger and Windows/WSL observations.

## Change summary

Accepting a merge conflict before CodeLenses refresh can use stale ranges and delete unrelated text or leave invalid conflict markers.

## Best solution

Track the remaining stale-range defect in https://github.com/microsoft/vscode/issues/107821 and ensure inline conflict actions cannot apply outdated conflict coordinates after earlier resolutions or manual edits.

- **Same observable symptom and trigger:** https://github.com/microsoft/vscode/issues/107821#issuecomment-723346504 identifies incorrect line deletions when accepting a subsequent conflict before the preceding conflict's gutter text disappears. https://github.com/microsoft/vscode/issues/107821#issuecomment-835052688 confirms both repeated clicks and clicking the next conflict delete unrelated lines, matching this report.
- **Current source retains stale conflict coordinates:** At checkout HEAD c3cbcba676f18ba2d0281d10d43b7ccd63db9a69, extensions/merge-conflict/src/codelensProvider.ts passes the parsed conflict object in ['known-conflict', conflict]. CommandHandler.accept in extensions/merge-conflict/src/commandHandler.ts uses that object directly without rescanning or checking its document version. DocumentMergeConflict.applyEdit in extensions/merge-conflict/src/documentMergeConflict.ts reads and replaces its stored absolute ranges against the current document; its applied guard protects only reuse of that same object, not a different conflict shifted by an earlier edit.
- **Refresh window remains:** src/vs/editor/contrib/codelens/browser/codelensController.ts retains valid CodeLens widgets after document changes and schedules provider refresh. codelensWidget.ts tracks the displayed lens position, but does not update the conflict ranges inside its command arguments. An insertion above a conflict can therefore move its displayed action while leaving its edit coordinates stale. This was established by source inspection, without executing or modifying the checkout.
- **Additional evidence to preserve:** The supplied discussion confirms the problem independently on Windows/WSL2 and adds a manual-buffer-edit trigger before clicking Accept. These are additional triggers and environments for the same stale-coordinate defect, not evidence of a separate product behavior.
