# Issue #143024 — Tabs that group editor grid layouts (Vim-style tabs)

[https://github.com/microsoft/vscode/issues/143024](https://github.com/microsoft/vscode/issues/143024)

## Summary

Keep this accepted, well-supported request open: existing working-set infrastructure restores editor grids, but does not provide independently switchable layouts within one project while retaining inactive editors. The verified older related requests do not cover the same complete behavior.

## Change summary

Allow users to name and switch between complete editor-grid layouts within one VS Code workspace.

## Best solution

Provide a lightweight, keyboard-accessible way to switch named editor-grid layouts in the same workspace. First settle whether these are live layout collections retaining inactive editors or saved snapshots, since existing working-set restoration closes editors and does not satisfy the thread's state-retention requirement.

## Plan brief

- **Likely files:** `src/vs/workbench/services/editor/common/editorGroupsService.ts`, `src/vs/workbench/browser/parts/editor/editorParts.ts`, `src/vs/workbench/browser/parts/editor/editorPart.ts`, `src/vs/workbench/services/editor/test/browser/editorGroupsService.test.ts`
- **Validation:** After agreeing on semantics, add editor-group tests for switching between two named, differently arranged grids and restoring each grid's files and active group; run scripts/test.sh --run src/vs/workbench/services/editor/test/browser/editorGroupsService.test.ts. Manually verify switching parser and lexer layouts within one workspace without changing branches or opening another window, and check inactive-editor lifetime against the chosen contract.
- **Behavior:**

  > Users need to switch complete arrangements of editor groups and files within a single workspace, rather than switch individual file tabs or independent windows. A parser layout and a lexer layout should each be selectable with one action and recover their intended split arrangement and active editor. The original request permits a save/reload interface instead of a higher-order tab bar, while later discussion explicitly asks that inactive editors remain open to avoid language-server reparsing. Acceptance must distinguish these lifetime semantics and verify that dirty edits are preserved without making ordinary editor-group navigation behave differently.
- **Trace:**

  > EditorParts.saveWorkingSet and applyWorkingSet in src/vs/workbench/browser/parts/editor/editorParts.ts already serialize and restore main and auxiliary editor state through IEditorGroupsService. EditorPart.createState serializes the grid, but doApplyState first closes non-confirming editors and disposes groups, so this path is snapshot restoration rather than retaining independent live layouts. SCMWorkingSetController in src/vs/workbench/contrib/scm/browser/workingSet.ts adopts these methods for history-reference changes; its settings do not expose arbitrary same-branch layout collections. The existing working-set test in src/vs/workbench/services/editor/test/browser/editorGroupsService.test.ts covers grid reconstruction and dirty-editor preservation. Preserve current SCM working-set behavior and normal split/tab navigation; do not assume terminal state or extension-API layout control is solved by serialization. https://github.com/microsoft/vscode/issues/9498 is related snapshot work, while https://github.com/microsoft/vscode/issues/36700 and https://github.com/microsoft/vscode/issues/100335 cover different grouping boundaries. The remaining uncertainty is the product contract for inactive layouts and their switching interface, not whether serialized grid state exists.
- **Open decisions:**
  - Should switching layouts retain inactive layouts' editors and language-server document context, or is closing and reopening saved snapshots acceptable for the first supported experience?
  - Should users switch layouts through a higher-order tab surface, or through named save/restore commands and a picker?
