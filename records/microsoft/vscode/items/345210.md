# Issue #345210 — Agents window: opt-in grouping of sessions by worktree

[https://github.com/microsoft/vscode/issues/345210](https://github.com/microsoft/vscode/issues/345210)

## Summary

The requested opt-in worktree grouping remains absent from current source. Keep this focused request open: existing grouping and manual groups do not provide automatic worktree separation, and the related cross-surface discussions do not settle this capability.

## Change summary

Allow automatic session grouping by primary working-folder identity without changing default repository-level consolidation.

## Best solution

Provide an opt-in presentation that separates sessions by primary working-folder URI, identifies each worktree and branch, and preserves existing default grouping and placement precedence. A maintainer should choose between nested worktree sections and a separate grouping mode before implementation.

- **Behavior:**

  > Users maintaining several long-lived worktrees can opt into automatic separation of their sessions by the parent's primary working folder. Sessions in the same working folder stay together, while distinct folder URIs remain separate even when their basenames match. Worktree groups show the folder name and branch. Existing default grouping remains unchanged, and a session with chats in several folders appears only once according to its parent's primary folder.
- **Trace:**

  > SessionsGrouping in src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts has four modes and no worktree mode. groupByWorkspace keys by sessionWorkspaceLabel; groupByRepository keys by GitHub owner/repository and falls back to workspace grouping. The existing tests explicitly preserve these grouping semantics, so changing workspace identity globally would alter current behavior rather than merely expose the requested option. Grouping commands live in sessionsViewActions.ts, and sessionsView.ts also exposes grouping through the mobile sheet. Preserve pins, archive and custom-group precedence, comparison ownership, and provider-neutral presentation state. https://github.com/microsoft/vscode/issues/336620 supplies cross-surface context but explicitly preserves narrower reports; https://github.com/microsoft/vscode/issues/311858 addresses broader worktree contexts. The remaining uncertainty is the user-visible grouping hierarchy and its treatment of sessions without a concrete working folder.
- **Open decisions:**
  - Should opt-in worktree separation appear as conditional sub-sections within existing Workspace/Repository sections, a separate Group by Worktree mode, or an optional change to Workspace grouping?
  - In the chosen presentation, where should sessions without a concrete primary working-folder URI appear?
