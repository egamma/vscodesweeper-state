# Issue #313681 — workspaceStorage bucket hash computed from raw path string — OneDrive Folder Backup (KFM) creates permanent duplicate storage buckets on macOS

[https://github.com/microsoft/vscode/issues/313681](https://github.com/microsoft/vscode/issues/313681)

## Summary

Keep open as a request to share workspace storage across filesystem aliases: current source confirms separate buckets, but path-based identity and identifier stability are deliberate existing contracts. No verified older canonical owns this same storage-aliasing request.

## Change summary

Allow a local workspace opened through its symlinked and resolved paths to share persistent workspace state.

## Best solution

Have the workspace/storage owners decide whether filesystem aliases should share storage independently of the visible workspace URI, with explicit compatibility and migration semantics for existing buckets. Preserve symlink paths used by tools and avoid silently discarding either bucket's existing state.

## Evidence

- **Current opening and hashing path:** src/vs/platform/windows/electron-main/windowsMainService.ts:1177–1220 normalizes the supplied path, calls fs.promises.stat, and passes URI.file(path) with that stat to getSingleFolderWorkspaceIdentifier. src/vs/platform/workspaces/node/workspaces.ts hashes folderUri.fsPath plus platform-specific metadata without resolving symlinks. On macOS, the same target birthtime does not remove the difference between the two path strings.
- **Separate storage buckets:** WorkspaceStorageMain in src/vs/platform/storage/electron-main/storageMain.ts:417–478 locates state.vscdb under workspaceStorageHome/workspace.id and creates that directory when absent. This path does not identify or reconcile an existing bucket reached through another filesystem alias.
- **Existing identity contract:** src/vs/platform/workspaces/node/workspaces.ts explicitly warns that identifiers must remain stable. src/vs/platform/workspaces/test/node/workspaces.test.ts asserts fixed hashes in 'workspace identifiers are stable'. Sharing physical-folder identity would change this contract rather than repair a missing implementation of an already-established alias-sharing guarantee.
- **Root symlink preservation is intentional:** https://github.com/microsoft/vscode/issues/18837 concerns workspace-root symlinks, not only links inside a workspace. In https://github.com/microsoft/vscode/issues/18837#issuecomment-418342604, a maintainer explicitly stopped following symbolic links for files and folders; https://github.com/microsoft/vscode/issues/18837#issuecomment-418647766 acknowledges possible state mismatches with external real paths. This supports separating any storage proposal from changes to visible workspace paths, but does not itself decline storage alias sharing.
- **Existing capability is only a workaround:** getWorkspaceIdentifier in src/vs/platform/workspaces/node/workspaces.ts bases a saved .code-workspace identity on its configuration-file path. Consistently opening one such file can provide a stable storage identity, as described in https://github.com/microsoft/vscode/issues/240172#issuecomment-2656701052, but does not make opening the two folder aliases directly share storage. Inspected workspace and workbench configuration registrations expose no matching alias-sharing setting.
- **Canonical search:** GitHub searches for symlink/storage, workspaceStorage/realpath, and workspace identity found no verified older issue with the same observable symptom. https://github.com/microsoft/vscode/issues/240172 is open but concerns changing Linux inode values at an unchanged path. https://github.com/microsoft/vscode/issues/331493 is open but describes Windows NAS history disappearance and was created after this report, so it cannot serve as a canonical under the re-review rules. https://github.com/microsoft/vscode/issues/100533 is closed and concerns duplicate editor tabs, not storage buckets.
