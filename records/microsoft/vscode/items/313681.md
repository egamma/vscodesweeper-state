# Issue #313681 — workspaceStorage bucket hash computed from raw path string — OneDrive Folder Backup (KFM) creates permanent duplicate storage buckets on macOS

[https://github.com/microsoft/vscode/issues/313681](https://github.com/microsoft/vscode/issues/313681)

## Summary

Current source confirms path-spelling-dependent workspace storage IDs, but changing this is an identity and migration decision rather than a localized bug fix. Route it to workspace/file ownership for design.

## Change summary

Use one workspace-storage bucket when symlinked and canonical paths identify the same physical folder.

## Best solution

Define a canonical storage identity or alias/migration mechanism in the workspace and storage services while preserving the user-opened workspace URI. The design must retain existing buckets and intentional symlink identities rather than silently changing stable IDs.

## Evidence

- **source behavior:** src/vs/platform/workspaces/node/workspaces.ts:getSingleFolderWorkspaceIdentifier hashes `folderUri.fsPath` plus filesystem metadata. Because `stat` follows the symlink but the raw path remains different, the two spellings produce different IDs.
- **storage mapping:** src/vs/platform/storage/electron-main/storageMain.ts constructs the workspace-storage directory from `workspaceStorageHome` and `workspace.id`, conclusively linking the differing IDs to separate buckets.
- **compatibility constraint:** Workspace identifier code and tests explicitly require identifiers to remain stable; src/vs/platform/workspaces/test/node/workspaces.test.ts snapshots the path-derived values. Directly switching to `realpath` therefore requires migration handling.
- **intentional path semantics:** https://github.com/microsoft/vscode/issues/18837 records the deliberate change to preserve symlink paths, while also acknowledging that real and symlink spellings can cause state mismatches.
- **canonical search:** https://github.com/microsoft/vscode/issues/130082 remains open but concerns canonicalizing opened editor files, not workspace-storage identity; no open issue found owns this narrower storage work.
- **existing capability:** Current source and configuration registrations contain no setting that canonicalizes workspace-storage identity independently of the displayed workspace path.
