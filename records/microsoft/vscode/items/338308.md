# Issue #338308 — Renaming a chat session from the sessions list is not persisted (renaming from the session title works)

[https://github.com/microsoft/vscode/issues/338308](https://github.com/microsoft/vscode/issues/338308)

## Summary

Well-diagnosed, reproducible bug (with jsonl storage evidence and a second corroborating commenter) in the sessions-list inline rename path, which does not reliably persist the new title, unlike renaming from the session header. I traced a plausible silent-failure path in the Agent Host local sessions provider that matches the reported symptoms, but the exact route (multiple provider implementations exist) isn't pinned down with certainty, so this needs a bit more diagnosis before an agent fix.

## Change summary

Renaming a chat session inline from the Agent Sessions list does not persist the new title (it's silently dropped), while renaming from the open chat's header title works and is saved.

## Best solution

Confirm which sessions provider path is hit for the reporter's local agent-mode session (likely src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts `renameSession`, which silently no-ops if `cached`/`connection` aren't both available) and make the failure surface or retry instead of silently dropping the rename, so it behaves consistently with the header rename path in chatServiceImpl.ts `setChatSessionTitle`.

## Evidence

- **reporter storage evidence:** Reporter shows the chatSessions/<id>.jsonl file only gets a `customTitle` entry for the header-based rename ('TEST'), never for the sessions-list rename ('test rename'), directly pointing at the sessions-list rename action failing to persist.
- **inline rename call site:** src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:1859 calls `this.sessionsManagementService.renameSession(target, title).catch(onUnexpectedError)`, which delegates to `_getProvider(session)?.renameSession(...)` in src/vs/sessions/services/sessions/browser/sessionsManagementService.ts:1376-1379.
- **candidate silent-noop path:** src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:5809-5820 `renameSession` only updates/dispatches when both `cached` and `connection` are truthy; if either is momentarily unavailable it silently does nothing (no throw), matching the second commenter's 'sometimes works, sometimes not, no error message' report.
- **contrasting path (different provider):** src/vs/sessions/contrib/providers/copilotChatSessions/browser/copilotChatSessionsProvider.ts:1548 `renameSession` unconditionally throws 'Renaming is not supported for Copilot Cloud sessions' — if this provider were hit for a local session it would throw and surface via `onUnexpectedError`, which doesn't match the reported silent failure, so the Agent Host provider path is the more likely culprit for this reporter.
- **working header path:** src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:426-439 `setChatSessionTitle` both updates the in-memory model and calls `this._chatSessionStore.setSessionTitle(...)` plus `this.saveState()`, which is why the header rename reliably persists.
