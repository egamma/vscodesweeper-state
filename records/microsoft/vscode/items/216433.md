# Issue #216433 — Make Workspace Extensions more intuitive to find and activate

[https://github.com/microsoft/vscode/issues/216433](https://github.com/microsoft/vscode/issues/216433)

## Summary

A real discoverability gap remains: current main exposes workspace extensions through Workspace Recommendations and shows already-installed workspace extensions in Installed, but offers no dedicated workspace-extension filter or other obvious activation entry point. This team-authored, Backlog-accepted request is also the canonical target for two later reports, so it must remain open.

## Change summary

Make repository-local workspace extensions easier to discover and activate without requiring users to know that they appear under Workspace Recommendations.

## Best solution

Choose a consistent Extensions-view discovery surface that distinguishes repository-local workspace extensions from ordinary recommendations and lets users activate them directly, while retaining the existing Installed representation after activation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/extensions/browser/extensionsViewlet.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsViews.ts`, `src/vs/workbench/contrib/extensions/browser/workspaceRecommendations.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsWidgets.ts`, `src/vs/workbench/contrib/extensions/test/electron-browser/extensionsViews.test.ts`
- **Validation:** Add Extensions view tests showing that an unactivated repository-local workspace extension is discoverable through the chosen surface and activation action, while an activated workspace extension remains represented in the Installed view.
- **Behavior:**

  > A user opening a workspace containing repository-local extensions can discover and activate them from an intuitive Extensions or Explorer surface without knowing to search Workspace Recommendations. Workspace extensions are clearly distinguished from Marketplace recommendations, and already-activated workspace extensions remain visible with installed extensions. Acceptance should cover both the initial unactivated state and the post-activation state.
- **Trace:**

  > WorkspaceRecommendations in src/vs/workbench/contrib/extensions/browser/workspaceRecommendations.ts discovers extension folders under .vscode/extensions and publishes them as workspace recommendations. WorkspaceRecommendedExtensionsView in src/vs/workbench/contrib/extensions/browser/extensionsViews.ts exposes those entries only through @recommended:workspace, while ExtensionsViewlet in src/vs/workbench/contrib/extensions/browser/extensionsViewlet.ts labels that section Workspace Recommendations and has no workspace-extension-specific view or filter. ExtensionsWorkbenchService.fetchInstalledExtensions already includes installed workspace-scoped extensions, and ExtensionPackCountWidget in extensionsWidgets.ts labels them Workspace Extension and can reveal their folder. Preserve Marketplace recommendation behavior, ordinary installed-extension behavior, and workspace-scoped lifecycle semantics; the unresolved boundary is the user-facing discovery surface, not extension loading.
- **Open decisions:**
  - Should the primary entry point be a dedicated Extensions view/filter, an Explorer entry, or inclusion among Installed items before activation?
  - Should repository-local items be presented as Workspace Extensions rather than Workspace Recommendations so users can distinguish them from Marketplace recommendations?

## Evidence

- **current source:** src/vs/workbench/contrib/extensions/browser/extensionsViewlet.ts registers WorkspaceRecommendedExtensionsView only under the Workspace Recommendations section; there is no dedicated workspace-extension search/view alongside the installed, enabled, disabled, and built-in views.
- **partial existing coverage:** src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts::fetchInstalledExtensions adds getInstalledWorkspaceExtensions(true) to the local installed model, while src/vs/workbench/contrib/extensions/browser/extensionsViews.ts::WorkspaceRecommendedExtensionsView uses @recommended:workspace and filters extensions already present locally. This covers the post-install state but leaves initial discovery tied to recommendations.
- **canonical reports:** Maintainers closed https://github.com/microsoft/vscode/issues/219640 and https://github.com/microsoft/vscode/issues/223511 as duplicates of this issue, carrying additional evidence that workspace extensions are difficult to notice and activate.

- **canonical search:** The older open https://github.com/microsoft/vscode/issues/347 broadly tracks support for workspace-specific extensions, but it does not report this same observable discoverability symptom and therefore does not meet the stronger duplicate bar for this re-reviewed item.
