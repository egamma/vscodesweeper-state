# Issue #209815 — Can't sign in to settings sync with GitHub if using non-default profile and `--user-data-dir`

[https://github.com/microsoft/vscode/issues/209815](https://github.com/microsoft/vscode/issues/209815)

## Summary

Keep open: current GitHub authentication mitigates the original sign-in failure by preferring a local callback server, but browser redirects can still launch the default-data instance instead of the originating instance. The portable-mode fix does not cover an ordinary installation launched with --user-data-dir.

## Change summary

GitHub sign-in should complete in the VS Code instance that initiated it, including when that instance uses a custom user-data directory and profile.

## Best solution

Complete authentication in the originating instance without opening an unrelated default-data window. Establish the remaining failure boundary between the local-server flow and protocol-handler fallback, then address custom-data instance handling while preserving normal browser sign-in.

## Evidence

- **Confirmed report and workaround:** https://github.com/microsoft/vscode/issues/209815 documents browser sign-in opening the default-data instance on Windows 11 with VS Code 1.88.0. The reporter confirmed device login works, and the maintainer attributed the failure to vscode:// routing across separate user-data instances.
- **Current authentication mitigates part of the report:** extensions/github-authentication/src/flows.ts now orders LocalServerFlow before UrlHandlerFlow. LocalServerFlow receives the OAuth code through its own LoopbackAuthServer and exchanges it in the initiating extension host, so the original inability to obtain a session is not conclusively established for today's default flow. https://github.com/microsoft/vscode/commit/31620a3decb7f5ec0d6a3c55fab89ab17906a77e made loopback authentication primary, but also introduced a subsequent redirect back to VS Code.
- **Remaining wrong-instance redirect in current source:** extensions/github-authentication/src/node/authServer.ts resolves the local OAuth result, then includes callbackUri in the success-page redirect whenever isPortable is false. extensions/github-authentication/media/index.html subsequently opens that URI through vscode.dev/redirect. A custom --user-data-dir is not the portable-mode condition, so successful loopback authentication still takes the protocol-launch path.
- **Protocol registration lacks instance identity:** src/vs/platform/url/electron-main/electronUrlListener.ts registers the Windows protocol command with --open-url --, without --user-data-dir. src/vs/platform/environment/electron-main/environmentMainService.ts derives mainIPCHandle from userDataPath, and src/vs/code/electron-main/main.ts connects to that handle during startup. Therefore the protocol invocation targets the default-data process rather than the custom-data process; a windowId added by RelayURLService cannot by itself select a different main-process IPC namespace.
- **Portable fix is narrower:** https://github.com/microsoft/vscode/pull/287063, merged as aa19df565fd19957c7ef1b844bfae729adb6c1af, suppresses protocol redirects in portable mode. Current LocalServerFlow passes env.isAppPortable to LoopbackAuthServer, not a custom-user-data indicator, so this is not a complete fix for the reported launch configuration.
- **Related issues do not supply a duplicate canonical:** https://github.com/microsoft/vscode/issues/211845 was closed as a duplicate of this issue, with a maintainer confirming the user-data-dir cause. https://github.com/microsoft/vscode/issues/236405 remains open and proposes URI-handler availability detection, but is newer than this re-reviewed report and owns an API-design question rather than being an eligible older canonical. Searches for custom-data authentication and wrong-window reports found no verified older issue owning this exact symptom.
- **Existing workaround and inspection limits:** extensions/github-authentication/package.json registers github-authentication.preferDeviceCodeFlow, and getFlows in flows.ts honors it. This provides an explicit workaround, not automatic correct-instance browser routing. Review used source and GitHub reads only; no authentication flow was executed, and local git history is shallow.
