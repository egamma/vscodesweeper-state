## Evidence

- **Concrete report and independent confirmation:** The report describes initially readable files becoming stale or combining lines after edits, plus sidebar and console output reading 'group'. Independent users confirm matching editor and sidebar symptoms at https://github.com/microsoft/vscode/issues/319725#issuecomment-5283836111 and https://github.com/microsoft/vscode/issues/319725#issuecomment-5368513061; the former supplies a three-line file and arrow-navigation reproduction.
- **Diagnosed upstream behavior:** https://github.com/microsoft/vscode/issues/319725#issuecomment-5511690655 documents incorrect AXLineForIndex and AXRangeForLine results in VS Code's Electron runtime, including reproduction in ordinary multiline text fields. This ties the wrong, stale, or blank braille lines to Chromium's macOS accessibility layer rather than an editor accessibility setting.
- **Upstream behavior-changing fix:** The merged https://github.com/electron/electron/pull/53428 carries Chromium commit 36ac8f31796a392340f7914d1018c3a885fc183f. Its patch changes accessibilityLineForIndex: in ui/accessibility/platform/browser_accessibility_cocoa.mm from lower_bound to upper_bound minus one, and removes the nonzero-line rejection in AXRangeForLine: in ui/accessibility/platform/ax_platform_node_cocoa.mm. These changes directly address the reported line-selection failure.
- **Current runtime and limits of confirmation:** The checkout's .npmrc targets Electron 43.7.7. https://github.com/microsoft/vscode/issues/319725#issuecomment-5537813733 reports the backport shipped in Electron 43.6.0 and successful physical-braille testing of a local VS Code build on Electron 44. That supports likely resolution of the principal upstream defect, but does not establish complete resolution of this report on the current checkout; no application or hardware reproduction was executed.
- **Separate sidebar improvement is not a complete fix:** https://github.com/microsoft/vscode/pull/330945 explicitly states that its virtual-list active-descendant ordering change may improve the Explorer 'group' symptom but does not fix the primary Monaco editor/braille synchronization issue. Current src/vs/base/browser/ui/list/listWidget.ts, onDidChangeActiveDescendant(), checks that the default target row is rendered before publishing its DOM ID; this is not proof that all sidebar or console braille output is correct.
- **This report already serves as a tracking point:** A maintainer closed the later matching report in favor of this issue at https://github.com/microsoft/vscode/issues/323246#issuecomment-4906117191. That closed, newer issue is not a duplicate canonical for this re-reviewed item.
- **Older canonical candidates do not absorb the full report:** Verified open https://github.com/microsoft/vscode/issues/95783 concerns typing updates and routing buttons; its latest author comment says general typing tracking improved and separates remaining cases. Verified open https://github.com/microsoft/vscode/issues/241058 concerns braille panning when moving upward from a blank line. Neither owns this report's full combination of post-edit line synchronization, sidebar names, and console output.
- **Editor source does not establish a remaining core defect:** src/vs/editor/browser/controller/editContext/native/screenReaderContentSimple.ts, SimpleScreenReaderContent.updateScreenReaderContent(), updates the accessibility text and DOM selection. Its textContent replacement is mentioned as a separate potential improvement in the upstream investigation, not the demonstrated cause; source inspection alone does not justify prescribing that change.
