# Issue #214824 — Debugger UX should show stack for current thread instead of a treeview with all threads

[https://github.com/microsoft/vscode/issues/214824](https://github.com/microsoft/vscode/issues/214824)

## Summary

This remains a distinct, accepted debug UX request: current main still renders every thread as a call-stack tree node, while the requested focused-thread stack with a thread switcher does not exist. The older concurrency issue covers large-scale logical-thread visualization rather than this conventional one-thread-at-a-time workflow.

## Change summary

Provide a debugger call-stack mode that displays only the focused thread's stack and lets users switch the focused thread separately.

## Best solution

Design a focused-thread presentation for the Call Stack view, including a lightweight thread selector and clear semantics for switching the editor and stack together, while retaining access to the existing all-threads tree.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/callStackView.ts`, `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`, `src/vs/workbench/contrib/debug/test/browser/callStack.test.ts`
- **Validation:** Add or extend debug Call Stack view tests with a multi-thread session, verifying that the chosen focused-thread mode exposes only the focused thread's frames, switching threads changes both the displayed stack and focused editor frame, and the existing all-threads presentation remains available.
- **Behavior:**

  > When debugging a session with multiple ordinary threads, users can view the focused thread's call stack without every other thread occupying the tree. Users can switch threads from that presentation, and doing so updates both the visible stack and the editor location to the selected thread. The existing all-threads view remains available for workflows that need simultaneous thread visibility.
- **Trace:**

  > CallStackDataSource.getChildren in src/vs/workbench/contrib/debug/browser/callStackView.ts currently returns the complete thread array whenever a session has multiple threads. CallStackView.updateTreeSelection tracks DebugViewModel.focusedThread but only expands and reveals that thread inside the unchanged all-threads tree. The Call Stack registration and actions are in src/vs/workbench/contrib/debug/browser/debug.contribution.ts, with existing debug-model coverage in src/vs/workbench/contrib/debug/test/browser/callStack.test.ts. The boundary is the conventional Call Stack presentation: do not fold in the paging, grouping, filtering, or DAP protocol work tracked by https://github.com/microsoft/vscode/issues/116109.
- **Open decisions:**
  - Should focused-thread presentation be the default for multi-thread sessions, an optional persistent mode, or a temporary toggle in the Call Stack view?
  - What selector interaction should expose other threads while keeping the focused stack primary, and should selecting a thread immediately navigate the editor to its top frame?

## Evidence
