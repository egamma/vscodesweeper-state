# Issue #171097 — Show timestamp on Notification UI

[https://github.com/microsoft/vscode/issues/171097](https://github.com/microsoft/vscode/issues/171097)

## Summary

Keep this accepted Backlog request open: current notifications still do not display timestamps, and its 30 upvotes demonstrate community demand. The two older reports are closed, and the canonical search found no open issue owning this work.

## Change summary

Display a local timestamp on each notification so users can distinguish stale notices and notifications generated close together.

## Best solution

Provide unobtrusive, accessible time information in the shared notification UI, with consistent semantics for updates and repeated notifications. Agree on the presentation and timestamp meaning before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/common/notifications.ts`, `src/vs/workbench/browser/parts/notifications/notificationsViewer.ts`, `src/vs/workbench/browser/parts/notifications/notificationsList.ts`, `src/vs/workbench/browser/parts/notifications/notificationsToasts.ts`, `src/vs/workbench/browser/parts/notifications/notificationAccessibleView.ts`, `src/vs/workbench/test/common/notifications.test.ts`, `src/vs/workbench/test/browser/notificationsList.test.ts`, `src/vs/workbench/test/browser/notificationAccessibleView.test.ts`
- **Validation:** Add model and notification-rendering tests using controlled times to verify the agreed timestamp semantics, including updates and deduplicated repeats, and accessible-view coverage for the displayed information. Manually generate notifications at distinct times, reopen Notification Center, and verify their age remains understandable without obscuring messages or actions.
- **Behavior:**

  > Users cannot currently tell when an individual notification originated, making stale notices and rapid sequences difficult to interpret. Notifications should expose understandable local time information without requiring changes from their producers. Acceptance should cover notices created at distinct times, later viewing in Notification Center, message or progress updates, and repeated equivalent notifications. The same information should be available to screen-reader users without unnecessarily repetitive announcements.
- **Trace:**

  > NotificationViewItem in src/vs/workbench/common/notifications.ts has no creation-time field. NotificationsModel.addNotification places new items first and closes a matching prior item during deduplication, so the meaning of time for repeated notices needs to be settled. NotificationRenderer.renderTemplate and NotificationTemplateRenderer.render in src/vs/workbench/browser/parts/notifications/notificationsViewer.ts share the visual rendering path and currently expose no timestamp. Accessible labels and content are handled separately in notificationsList.ts, notificationsToasts.ts and notificationAccessibleView.ts. The telemetry firstShown stopwatch in src/vs/workbench/common/notificationTelemetry.ts measures exposure rather than creation and is not an existing UI capability. Preserve notification ordering, filtering, action behavior and telemetry semantics; this request does not require a notification history or persistence feature. The older reports https://github.com/microsoft/vscode/issues/81608 and https://github.com/microsoft/vscode/issues/48868 are closed and supply context, not active canonical ownership.
- **Open decisions:**
  - Should notifications show an absolute local timestamp, relative age, or relative age with an exact timestamp available on demand?
  - Should time information appear in both toasts and Notification Center, and should it remain visible when a notification is collapsed?
  - Should the displayed time represent original creation or the latest update, and should a repeated equivalent notification restart that time?
