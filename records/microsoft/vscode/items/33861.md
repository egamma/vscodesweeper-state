# Issue #33861 — introduce "pathMapping" as a more powerful replacement for "remoteRoot/localRoot"

[https://github.com/microsoft/vscode/issues/33861](https://github.com/microsoft/vscode/issues/33861)

## Summary

Keep open: current JavaScript debugger options cover individual mapping scenarios, but not the requested adapter-independent capability. The discussion establishes demand beyond JavaScript; the ownership and compatibility contract still need a maintainer decision.

## Change summary

Provide multiple configurable runtime-to-workspace path mappings consistently across debug adapters, with glob-pattern support.

## Best solution

Agree on a reusable mapping contract across debuggers, including pattern matching and interaction with existing adapter-specific mappings. Preserve existing configurations and avoid applying the same mapping twice.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/common/debugUtils.ts`, `src/vs/workbench/contrib/debug/common/debugSchemas.ts`, `src/vs/workbench/api/common/extHostDebugService.ts`, `src/vs/workbench/contrib/debug/test/browser/debugUtils.test.ts`
- **Validation:** The plan should end with executable debug-path tests covering two independent mappings, the requested commit-ID wildcard case, outgoing breakpoint paths and incoming stack-frame paths, unchanged unmatched paths, and compatibility with existing adapter mappings. Manually verify a remote/container session resolves breakpoints and opens the corresponding workspace files.
- **Behavior:**

  > Users need multiple runtime-to-workspace mappings across debug adapters rather than a single localRoot/remoteRoot pair or separate adapter-specific facilities. The discussion also requests glob patterns, including a variable commit-ID segment in a runtime path. Acceptance should cover breakpoints sent toward the runtime and source locations returned to the editor, while preserving unmapped paths and existing debug configurations. The contract for adapters that already map paths must be settled before implementation.
- **Trace:**

  > In src/vs/workbench/contrib/debug/common/debugUtils.ts, convertToDAPaths and convertToVSCPaths clone protocol messages and use convertPaths to convert source paths between URI and string representations; neither accepts configurable mapping rules. src/vs/workbench/api/common/extHostDebugService.ts calls these functions in both transport directions. Current js-debug options provide browser pathMapping, sourceMapPathOverrides, and localRoot/remoteRoot, but do not establish an adapter-independent contract. The December 2022 discussion in https://github.com/microsoft/vscode/issues/33861 proposes a shared transform, while the author previously left generalized mapping for a debugger-owner decision. Preserve existing adapter behavior, source-reference handling, and URI transport semantics. https://github.com/microsoft/vscode/issues/53443 was consolidated here and adds the physical-path-to-workspace-symlink use case. The unresolved boundary is whether mappings are applied by the client or by cooperating adapters, and how that interacts with adapters that already perform substitution.
- **Open decisions:**
  - Should the common mapping contract be applied by VS Code to all adapters, or implemented through adapter participation?
  - How should common mappings interact with existing adapter-specific mapping options so existing configurations do not undergo double substitution?
  - What glob capture, precedence, and reverse-mapping behavior should users receive when mappings overlap or are not uniquely invertible?
