# Issue #337262 — Sandbox toggle not shown when using remote agent host

[https://github.com/microsoft/vscode/issues/337262](https://github.com/microsoft/vscode/issues/337262)

## Summary

Traced this to source: the chat-panel sandbox toggle is explicitly gated to the local agent-host Copilot CLI session type, so it never appears for a remote agent host session (Windows client to a macOS remote agent host), matching the report exactly.

## Change summary

The 'Sandboxing for terminal' toggle is missing from the permission/mode picker for chat sessions running on a remote agent host, even though the agent runs sandboxed there by default.

## Best solution

Extend getAgentHostSandboxSettingId (and the host-OS resolution in AgentHostChatInputPicker) to recognize remote agent-host Copilot CLI sessions, resolving the OS via the session's actual remote connection the way sessions/contrib/providers/agentHost/browser/agentHostPermissionPickerDelegate.ts already does for the Sessions window.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostChatInputPicker.ts`, `src/vs/workbench/contrib/chat/test/browser/agentSessions/agentHostChatInputPicker.test.ts`
- **Validation:** Extend agentHostChatInputPicker.test.ts's setup() with a remote agent-host Copilot CLI session type (e.g. `remote-host1-copilotcli`) and assert that `_getSandboxSettingId()` resolves a setting id and the sandbox toggle appears, reflecting the remote host's OS-specific setting the same way the existing win32/linux test at line 236 does for the local session type.
- **Behavior:**

  > When a chat session is backed by a remote agent host (any OS combination of local client / remote server), the permission/mode picker should show the 'Sandboxing for terminal' toggle exactly as it does for a local agent-host Copilot CLI session, reflecting and controlling the remote session's actual sandbox state and the remote host's OS-specific setting id. Local agent-host sessions must keep behaving exactly as today.
- **Trace:**

  > `getAgentHostSandboxSettingId` (agentHostChatInputPicker.ts:165-169) hard-codes `sessionType !== SessionType.AgentHostCopilot` as its exclusion check, so any remote agent-host session type (`remote-{authority}-copilotcli`, see platform/agentHost/common/agentHostSessionType.ts) is rejected before `getAgentHostCopilotSandboxSettingId` is even called. Separately, `_resolveHostOperatingSystem()` (same file, lines 957-973) calls `getAgentHostOperatingSystem(this._agentHostService)`, which is always the local `IAgentHostService`/`IAgentConnection`, never the session's actual remote connection. The Sessions-window equivalent, sessions/contrib/providers/agentHost/browser/agentHostPermissionPickerDelegate.ts, solves both problems already (schema-based applicability check, and connection resolution via `IAgentConnectionsService.resolveSessionResource`) — that's the reference pattern, not a prescription for the exact wiring in this file. Do not change the fully-local (non-agent-host) sandbox toggle path in permissionPickerActionItem.ts, which is unrelated and works correctly.
- **Open decisions:**
  - Should AgentHostChatInputPicker gain its own connection-resolution seam (e.g. inject IAgentConnectionsService and resolve from the session resource) mirroring agentHostPermissionPickerDelegate.ts, or is there a simpler existing way to reach the session's remote connection from this widget?
  - Should the sandbox toggle remain hidden until the remote host's OS is resolved (as today for local hosts), or should it show optimistically with a default OS assumption while resolution is pending?

## Evidence

- **explicit local-only gate:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostChatInputPicker.ts:165-169 `getAgentHostSandboxSettingId` returns undefined unless `sessionType === SessionType.AgentHostCopilot`; a remote agent host session type is `remote-{authority}-copilotcli` (see platform/agentHost/common/agentHostSessionType.ts `isRemoteAgentHostSessionType`/`parseRemoteAgentHostHarness`), so it never matches and `_getSandboxSettingId()` (line 947-955) and `_getSandboxStandaloneToggle()` (line 996-1007) always bail out for remote sessions.
- **OS resolution is local-only too:** `_resolveHostOperatingSystem()` (agentHostChatInputPicker.ts:957-973) calls `getAgentHostOperatingSystem(this._agentHostService)`, where `_agentHostService: IAgentHostService` is injected as the local singleton `IAgentConnection` — it never resolves the remote host's connection for a remote session.
- **working comparison in the Sessions window:** sessions/contrib/providers/agentHost/browser/agentHostPermissionPickerDelegate.ts:82-86 and 187-208 gate only on `sessionType === CopilotCLISessionType.id` plus the session-config schema, and resolve the OS via `this._connectionsService.resolveSessionResource(session.resource)?.connection` — that picker correctly supports remote sessions, confirming the gap is specific to the chat-panel picker.
- **existing test scaffolding:** src/vs/workbench/contrib/chat/test/browser/agentSessions/agentHostChatInputPicker.test.ts already has a `setup()` harness and an OS-specific sandbox-setting test (around line 236) that could be extended with a remote session type.
