# Issue #339226 — Saving an open file after an ancestor directory is renamed externally silently recreates the old directory tree.

[https://github.com/microsoft/vscode/issues/339226](https://github.com/microsoft/vscode/issues/339226)

## Summary

The underlying mechanism the reporter describes — VS Code recreating missing ancestor directories on save — is confirmed-intentional plumbing in fileService.writeFile, not a bug; the real ask is a new safety prompt for this specific scenario, so this is a feature request that should stay open for maintainer consideration, not an automatic close.

## Change summary

When a file's open path has an ancestor directory that was renamed/removed externally, saving silently recreates the old directory tree instead of warning the user that the original path no longer exists.

## Best solution

If pursued, add a check in the workbench save path (e.g. textFileEditorModel/textFileService) that detects the immediate or an ancestor directory is missing before delegating to fileService.writeFile, and prompts the user to confirm recreating it (or offers Save As) rather than silently recreating via the generic mkdirp-on-write fallback that all writeFile callers share.

## Evidence

- **intentional mkdirp-on-write:** src/vs/platform/files/common/fileService.ts lines 395-403: writeFile() calls validateWriteFile(); if no stat is returned (target doesn't exist), it calls `await this.mkdirp(provider, providerExtUri.dirname(resource))` before writing — this recursively creates missing ancestor directories as deliberate, generic behavior used by every save/create caller, not a bug.
- **disk provider has no separate recreate logic:** src/vs/platform/files/node/diskFileSystemProvider.ts doWriteFile()/open() just open 'w'/'r+' on the resolved path; the directory creation happens one layer up in fileService.ts, confirming this is centralized, intended plumbing rather than an accidental side effect.
- **reporter's own framing:** The issue explicitly distinguishes itself from https://github.com/microsoft/vscode/issues/20071 (following renamed folders) and accepts VS Code won't track the rename — the ask is narrowly for a warning/prompt before the silent recreate, i.e. new UX, not a claim that current behavior is unintentional.
