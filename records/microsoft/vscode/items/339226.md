# Issue #339226 — Saving an open file after an ancestor directory is renamed externally silently recreates the old directory tree.

[https://github.com/microsoft/vscode/issues/339226](https://github.com/microsoft/vscode/issues/339226)

## Summary

Confirmed in source: FileService.writeFile() unconditionally mkdirp's the parent directory whenever the target path's stat lookup fails, and StoredFileWorkingCopy.save() never consults the existing ORPHAN state before writing — so an explicit save on a working copy whose directory vanished externally silently recreates the old tree instead of warning. This stays open; the fix needs a maintainer decision on UX before implementation.

## Change summary

Saving a file whose ancestor directory was renamed/deleted outside VS Code silently recreates the old directory tree instead of failing or prompting.

## Best solution

Have StoredFileWorkingCopy.save()/doSave() consult the already-tracked ORPHAN state (currently only used for a tab decoration) before writing, and reuse the existing conflict-resolution dialog pattern (the 'fileWorkingCopy.overwrite' / Save As actions already built for FILE_MODIFIED_SINCE around storedFileWorkingCopy.ts lines 1154-1200) to ask the user whether to recreate the old path or save elsewhere, rather than silently calling mkdirp.

## Plan brief

- **Likely files:** `src/vs/platform/files/common/fileService.ts`, `src/vs/workbench/services/workingCopy/common/storedFileWorkingCopy.ts`, `src/vs/workbench/services/textfile/common/textFileEditorModel.ts`
- **Validation:** A working-copy save test asserting that saving a dirty StoredFileWorkingCopy whose path is in ORPHAN state does not call mkdirp/recreate the missing directory without some explicit user confirmation.
- **Behavior:**

  > When a working copy's underlying file is detected as orphaned (its original path's directory no longer exists because an ancestor was renamed/deleted outside VS Code), an explicit Save should not silently recreate the missing directory tree and write there. Instead, the user should see a warning/prompt (consistent with the existing save-conflict UI) offering to either recreate the original path or Save As to a new location. Saves to a path that never existed (e.g. deliberate Save As to a new file) must continue to work unchanged.
- **Trace:**

  > fileService.writeFile() (src/vs/platform/files/common/fileService.ts, ~line 395-403) calls mkdirp on the parent directory whenever validateWriteFile's stat() lookup fails, with no way to tell 'new file' apart from 'file used to exist here'. StoredFileWorkingCopy already tracks an ORPHAN state (src/vs/workbench/services/workingCopy/common/storedFileWorkingCopy.ts, StoredFileWorkingCopyState.ORPHAN) that is today used only to drive a tab decoration (src/vs/workbench/services/textfile/browser/textFileService.ts provideDecorations) — save()'s early-exit guard at lines 852-859 checks CONFLICT/ERROR but not ORPHAN, and only for auto-save reasons, so neither auto-save nor explicit save is gated on it. The boundary: do not change mkdirp/writeFile behavior for genuinely new files (Save As to a path that never existed), and do not alter the unrelated #20071 'follow renamed folder' behavior. Where the uncertainty starts: whether to gate explicit saves too (not just auto-save), what the confirmation dialog should say, and whether this needs a new setting.
- **Open decisions:**
  - Should an explicit Save on an orphaned working copy be blocked/prompted, or only auto-save (matching the existing CONFLICT/ERROR auto-save guard)?
  - What should the prompt offer — recreate at the original path, Save As to the new location, or both — and should it reuse the existing FILE_MODIFIED_SINCE conflict dialog pattern?
  - Should this be opt-in/opt-out via a setting, given it changes long-standing save behavior?

## Evidence

- **mkdirp on write:** src/vs/platform/files/common/fileService.ts writeFile(): `if (!stat) { await this.mkdirp(provider, providerExtUri.dirname(resource)); }` — when the target path's stat() fails (ENOENT, because the ancestor dir is gone), the code treats it as a brand-new file and recreates the full missing directory tree before writing (lines 395-403).
- **stat lookup swallows ENOENT:** validateWriteFile() in the same file returns `Object.create(null)` (empty stat) on any stat() error (line ~491), so there is no distinction between 'intentionally saving to a new path' and 'the file used to exist here and its directory disappeared'.
- **orphan state exists but is unused in save():** StoredFileWorkingCopyState.ORPHAN and TextFileEditorModelState.ORPHAN are tracked (storedFileWorkingCopy.ts / textFileEditorModel.ts) and drive only a tab decoration (textFileService.ts provideDecorations, 'Deleted' tooltip); StoredFileWorkingCopy.save()'s early-exit check (lines 852-859) only inspects CONFLICT/ERROR for auto-save, never ORPHAN, and explicit save bypasses it entirely — so even a correctly-detected orphan does not block or warn before the write.
- **distinguished from #20071 by reporter:** Reporter explicitly scopes this narrower than the 'follow renamed project folder' request (issue #20071), asking only for a warning/fail instead of silent recreation.
