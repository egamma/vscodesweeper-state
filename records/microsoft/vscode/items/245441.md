# Issue #245441 — Add a way to customise the "Open Recent" labels, instead of path, like using a workspace's specified "window.title"

[https://github.com/microsoft/vscode/issues/245441](https://github.com/microsoft/vscode/issues/245441)

## Summary

Keep this accepted request open: Open Recent supports stored labels internally, but the inspected user-facing configuration does not connect workspace-friendly names or window.title to those labels. With 27 upvotes and Backlog acceptance, it merits a naming-contract decision rather than a staleness close.

## Change summary

Allow user-defined friendly workspace names to appear in Open Recent instead of names derived from workspace filenames or folder paths.

## Best solution

Provide a consistent friendly-name contract for recent workspaces across the picker, menu, and welcome surface, retaining path information for disambiguation. Decide whether this name is independent workspace metadata or derived from window.title before implementing it in the workbench history and labeling paths.

- **Behavior:**

  > Users managing many projects need Open Recent to show recognizable friendly workspace names independently of directory and workspace-file names. The chosen naming contract should produce consistent names in the recent picker, menu, and welcome surface while preserving the correct open target and useful path disambiguation. Existing unnamed entries must retain their current behavior. Acceptance includes persistence across reload and correct opening of projects with identical friendly names.
- **Trace:**

  > BaseOpenRecentAction.toQuickPick in src/vs/workbench/browser/actions/windowActions.ts prefers IRecent.label and otherwise delegates to LabelService.getWorkspaceLabel, whose saved-workspace and single-folder branches derive names from filenames and URIs. MenubarControl.createOpenRecentMenuAction and the welcome getting-started recents use the same stored-label preference. The internal _workbench.addToRecentlyOpened command accepts labels, and toStoreData in src/vs/platform/workspaces/common/workspaces.ts persists non-path labels, so the data model already has a relevant primitive. window.title is independently registered as a context-dependent window-title template; no inspected connection publishes it as a recent label. The uncertainty is the user-visible naming contract, not whether labels can be stored. Preserve URI-based workspace identity, opening behavior, and ordinary file-history labels; avoid turning editor-dependent title changes into an accidental project rename. https://github.com/microsoft/vscode/issues/318366 is a separate search-ranking report, not a canonical for this work.
- **Open decisions:**
  - Should the friendly recent name be independent workspace metadata, an explicit recent-entry alias, or derived from window.title?
  - If window.title is used, how should editor-dependent variables behave when the workspace is closed: retain a snapshot or restrict the recent name to workspace-stable information?
