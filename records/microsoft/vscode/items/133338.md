# Issue #133338 — Add code lens option/alternative for native testing

[https://github.com/microsoft/vscode/issues/133338](https://github.com/microsoft/vscode/issues/133338)

## Summary

Keep open: native testing still lacks the requested optional execution code lenses. The maintainer explicitly revived this request after the earlier decline, and the related profile-feedback issue points back here rather than superseding it.

## Change summary

Offer optional native testing code lenses as an alternative or complement to gutter actions.

## Best solution

Provide an opt-in, consistent editor code-lens surface for native test actions while preserving existing gutter behavior. Settle which actions and run profiles appear inline before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/testing/common/configuration.ts`, `src/vs/workbench/contrib/testing/browser/testingDecorations.ts`
- **Validation:** With a native test controller providing located tests and multiple run profiles, enable the proposed option and verify that the agreed code lenses appear and invoke the selected test/profile. Disable the option and verify that the lenses disappear; repeat with testing.gutterEnabled both true and false, confirming existing gutter behavior remains unchanged.
- **Behavior:**

  > Users should be able to opt into editor code lenses for tests discovered through native testing, rather than relying exclusively on gutter controls. The lenses should expose the agreed test actions and execute the intended test with the appropriate profile. Existing gutter interactions must remain available with their current semantics. Acceptance includes enabling and disabling the lens surface and checking behavior with multiple applicable profiles.
- **Trace:**

  > TestingConfigKeys and testingConfiguration in src/vs/workbench/contrib/testing/common/configuration.ts expose gutter visibility and default-click behavior but no execution code-lens setting. TestingDecorationService.applyDecorations in src/vs/workbench/contrib/testing/browser/testingDecorations.ts groups located tests and creates single- or multi-test gutter decorations; the similarly named lens widgets are expected/actual diff headings, not execution controls. This establishes that the existing settings do not cover the request, but it does not settle the new lens action contract. Preserve existing gutter behavior and avoid changing test execution or profile defaults as an incidental consequence. https://github.com/microsoft/vscode/issues/203913#issuecomment-1919710393 revives this request, while https://github.com/microsoft/vscode/issues/218102#issuecomment-2189443239 supplies the related non-default-profile use case.
- **Open decisions:**
  - Should the optional lenses expose fixed Run/Debug/Coverage actions using existing profile selection, or provide direct access to applicable non-default profiles as well?
