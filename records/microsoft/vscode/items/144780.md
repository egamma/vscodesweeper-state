# Issue #144780 — Git - repository auto-detection not working for junctions on windows

[https://github.com/microsoft/vscode/issues/144780](https://github.com/microsoft/vscode/issues/144780)

## Summary

Still present on main: the git extension's workspace scan filters children with `dirent.isDirectory()`, which is false for Windows junctions (libuv reports reparse points as links), so junctioned repositories are never visited by auto-detection and only appear once a file inside them is opened. Keep open — no fix commit found and the fix needs a maintainer call on whether the scan should follow links at all.

## Change summary

Repositories reached through Windows junctions (or symlinked directories) inside a workspace folder are not auto-detected in the Source Control view until a file from them is opened.

## Best solution

Make `Model.traverseWorkspaceFolder` in extensions/git/src/model.ts also descend into link dirents that resolve to directories (with cycle/visited-realpath protection and a bounded depth), so junctioned/symlinked repositories are picked up by the initial scan exactly like plain subfolders.

Acceptance: the new traversal test covering a directory link and a link cycle passes, the existing git extension tests still pass, and a manual Windows check of the issue's steps (C:/ws/j1 -> C:/repos/r1, …) shows all repositories in Source Control immediately after the workspace loads.
- **Trace:**

  > `Model.traverseWorkspaceFolder` in extensions/git/src/model.ts (around lines 416-440) enumerates children with `fs.promises.readdir(..., { withFileTypes: true })` and keeps only `dirent.isDirectory()`; libuv reports Windows junctions and POSIX directory symlinks as link dirents, so they are dropped and `scanWorkspaceFolders` never calls `openRepository` for them — the file-open path (`Model.openRepository(path.dirname(uri.fsPath))`, ~line 560) bypasses this filter, which is why opening a file reveals exactly one repository. Post-discovery link handling already exists and should not be touched: `getRepositoryRootRealPath` (~line 731) and `getRepositoryExact` (~line 945) already realpath-match junction paths against opened repository roots. The boundary is this traversal function: do not change `openRepository`, the parent-folder/unsafe-repository prompts, or the meaning of the existing scan settings. The later comments on the issue describing 'not detected at all' plus repeated `fatal: not a git repository` in the git output could not be confirmed from source and may be a separate defect — the plan's first step should be a Windows reproduction of both symptoms. Related: https://github.com/microsoft/vscode/issues/145566.
- **Open decisions:**
  - Should the workspace scan follow directory links (junctions/symlinks) on all platforms, or only Windows junctions, given the symlink-loop and large-tree traversal risk?
  - If links are followed, should link-following be unconditional or gated behind a setting (and what is the default)?
  - Is the later-reported 'repository not detected even after opening a file' a separate bug that should be split into its own issue rather than fixed here?

## Evidence

- **root cause on main:** extensions/git/src/model.ts `traverseWorkspaceFolder` (around lines 429-435) builds the list of folders to traverse from `readdir(..., { withFileTypes: true })` and keeps only `dirent.isDirectory()` entries. On Windows, libuv reports reparse points (junctions) as `UV_DIRENT_LINK`, so `isDirectory()` is false and `isSymbolicLink()` is true — junction children are dropped before `openRepository` is ever called on them.
- **matches the reported asymmetry:** Opening a file still works because that path goes through `Model.openRepository(path.dirname(uri.fsPath))` (model.ts ~line 560), which never consults the dirent filter — exactly the behavior in the report: nothing in Source Control until a file is opened, then that one repository appears.
- **link handling exists elsewhere, not in the scan:** The model already reconciles link vs. real paths after a repository is opened — `getRepositoryRootRealPath` (model.ts ~line 731) and `getRepositoryExact` (~line 945) both call `fs.promises.realpath` — so the gap is specifically in discovery, not in matching.
- **no fix found:** No junction/symlink-related change to the scan path is present on current main; the provided checkout is a shallow shard, so commit-level history could not be inspected and no fix commit can be cited.
- **related issue:** https://github.com/microsoft/vscode/issues/145566 (Timeline view empty for files in a junction) was closed as completed, with a maintainer noting it should be fixed once this issue is — it is a symptom of the same discovery gap, not a canonical for it.
- **second symptom unconfirmed:** The later reports (https://github.com/microsoft/vscode/issues/144780#issuecomment comments from 2024/2025: 'not detected at all', `git rev-parse --show-toplevel` returning 'not a git repository') describe a possibly distinct failure that could not be confirmed from source and needs a Windows reproduction.
