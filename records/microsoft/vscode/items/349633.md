# Issue #349633 — Extension Host fails due to malformed Windows system environment variable

[https://github.com/microsoft/vscode/issues/349633](https://github.com/microsoft/vscode/issues/349633)

## Summary

Keep open: the evidence points to Electron's environment-map conversion rejecting a numeric environment key, rather than an installed extension. The report supplies a concrete trigger and a successful isolation test; removing the variable is a workaround, not a product fix.

## Change summary

Prevent an inherited numeric Windows environment-variable name from blocking Extension Host startup, and make startup failures diagnostically useful.

## Best solution

Have Electron accept numeric-looking environment names without losing their string identity, then adopt the upstream fix in VS Code. Preserve legitimate inherited variables and provide actionable Extension Host startup diagnostics rather than indiscriminately stripping unusual names.

- **Current VS Code startup path:** src/vs/workbench/services/extensions/electron-browser/localProcessExtensionHost.ts, LocalProcessExtensionHost._start, obtains the shell environment and passes it through IExtensionHostProcessOptions.env. src/vs/platform/extensions/electron-main/extensionHostStarter.ts forwards those options to the utility process.
- **Environment handling:** src/vs/platform/utilityProcess/electron-main/utilityProcess.ts, UtilityProcess.createEnv, preserves inherited keys and converts values to strings before UtilityProcess.doStart calls utilityProcess.fork. src/vs/base/common/processes.ts, removeDangerousEnvVariables, removes a named denylist, not numeric keys. Thus the reported key reaches Electron; stringifying its already-string value does not address key conversion.
