# Issue #331232 — Agents window single pane: Switched to `Changes` tab even though no changes

[https://github.com/microsoft/vscode/issues/331232](https://github.com/microsoft/vscode/issues/331232)

## Summary

Real, traceable ordering bug in the single-pane docked-tabs reconcile logic: on submit of a brand-new session with no changes yet, the Changes tab still ends up active because it's opened into an empty editor group before the Files tab, and the workbench auto-activates the first tab opened into an empty group regardless of the intended `inactive` option.

## Change summary

In the Agents window single-pane layout, submitting a first message (e.g. "hi") auto-switches focus to the empty Changes tab instead of staying on Files.

## Best solution

In `singlePaneDockedTabsCoordinator.ts`'s `_reconcileCore`, when a session transitions from not-created to created with an empty group and there are no changes yet, either open the Files tab first (extend the `openFilesFirst` condition beyond `!isCreated`) or explicitly pass an active-Files follow-up after opening Changes, so the workbench's empty-group auto-activation of the first-opened tab doesn't override the intended inactive Changes tab.

## Evidence

- **auto-activation on empty group:** Line 34-35 comment: 'Options to open the Changes tab pinned first, inactive (the workbench auto-activates it only when the group is empty).' This documents exactly the mechanism that would make Changes active even with `inactive: true` when it's the first tab opened into an empty group.
- **submit trigger:** src/vs/sessions/contrib/layout/browser/singlePane/singlePaneExistingSessionStrategy.ts:390-422: on submit (`isSubmit`), `queueReconcile(target, { openDefaultsIfEmpty: isSubmit, ensureChangesActive })` is queued with `ensureChangesActive` false (no changes yet), so the coordinator shouldn't intentionally activate Changes here — the activation is an unintended side effect of tab-open order, not the `activateChanges` path.
