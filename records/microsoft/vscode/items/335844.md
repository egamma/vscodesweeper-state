# Issue #335844 — Nitpick: Sign in button flickers during startup

[https://github.com/microsoft/vscode/issues/335844](https://github.com/microsoft/vscode/issues/335844)

## Summary

The startup flicker remains possible on current main: marketplace account discovery can temporarily publish a sign-in-required state before authentication finishes connecting. This team-authored polish request should remain open so the indeterminate state can be presented without a misleading action.

## Change summary

Avoid briefly showing the Extensions Marketplace sign-in action while marketplace authentication state is still resolving during startup.

## Best solution

Keep the Extensions view visually stable during marketplace account discovery, presenting a quiet indeterminate state until VS Code can definitively show marketplace content, access denial, or the sign-in action.

- **Behavior:**

  > Opening VS Code with a private Extensions Marketplace must not briefly show a sign-in action while authentication is still initializing. During that interval the Extensions view should remain visually stable and may show an unobtrusive indeterminate state. Once account discovery completes, eligible users see marketplace content, ineligible users see access denied, and genuinely signed-out users see the sign-in action. Existing post-startup account changes must continue updating the view.
- **Trace:**

  > WorkbenchExtensionGalleryManifestService in src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryManifestService.ts starts at Unavailable but maps both an unresolved account and an Unknown account status to RequiresSignIn in handleMarketplaceAccountAccess. ExtensionMarketplaceStatusUpdater and the marketplace access welcome in src/vs/workbench/contrib/extensions/browser/extensionsViewlet.ts react immediately to that status, producing the transient sign-in affordance. MicrosoftGalleryAccountProvider in src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryAccountService.ts resolves sessions asynchronously, and the existing test suite documents a second validation when the Microsoft authentication provider registers after startup. Preserve the stable signed-out, access-denied, eligible, account-switching, and transient-failure semantics already covered by that suite; the boundary is the unresolved startup interval, not ordinary sign-in behavior.
