# Issue #25925 — Improved search in "Go to file" panel

[https://github.com/microsoft/vscode/issues/25925](https://github.com/microsoft/vscode/issues/25925)

## Summary

Keep open: current scoring still elevates scattered filename matches over stronger directory matches unless the query contains a path separator. This accepted Backlog request has 31 upvotes and maintainer interest; the related ranking umbrella is newer and cannot be a duplicate target for this re-reviewed item.

## Change summary

Improve Quick Open relevance so strong directory and full-path matches can outrank weak, scattered filename matches without requiring slash-separated queries.

## Best solution

Establish a file-search ranking contract that compares filename and directory match quality rather than categorically privileging filename matches, while preserving large-workspace performance. Decide whether that becomes the default or an opt-in behavior, and retain this issue as the concrete requirement alongside the broader ranking tracker.

- **Behavior:**

  > Quick Open should not bury a strong directory or directory-plus-filename match beneath weak, scattered filename matches solely because the latter fit entirely within the basename. Acceptance examples include files inside archive and djangosite/urls/default.py searched with urldef or space-separated fragments, without requiring a slash workaround. Strong filename matches must remain useful, and the maintainer must settle their relative priority before acceptance assertions are finalized. Navigation responsiveness in large workspaces must not materially regress.
- **Trace:**

  > The live file-results path is AnythingQuickAccessProvider.getAdditionalPicks in src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts, which invokes compareItemsByFuzzyScore and scoreItemFuzzy. In src/vs/base/common/fuzzyScorer.ts, doScoreItemFuzzy enables filename preference for separator-free queries; doScoreItemFuzzySingle boosts and returns filename matches before trying description plus label, and the comparer preserves that tiering. prepareQuery supports independent space-separated terms, but those terms retain the same filename preference, explaining why the workaround only partially helps. Existing ranking fixtures live in src/vs/base/test/common/fuzzyScorer.test.ts. The scorer is shared infrastructure, so do not assume a global scoring change is safe for command, symbol, or extension pickers; preserve their contracts unless explicitly included in the decision. - **Open decisions:**
  - Should improved full-path relevance replace the default Quick Open ranking, or be exposed as an opt-in mode?
  - When filename and directory matches compete, should exact or prefix filename matches retain a privileged tier while weak scattered filename matches compete with full-path matches, or should all matches use one full-path relevance ordering?
