## Evidence

- **Concrete reproduction:** https://github.com/microsoft/vscode/issues/343178 supplies an extensions-disabled reproduction on macOS with VS Code 1.143.0-insider: right-click a file, open an untitled editor with Open Editors visible, then right-click the same file. Inspect Context Keys shows the untitled resource still supplying resourceScheme and isFileSystemResource; choosing a different file restores the actions.
- **Current-source defect:** src/vs/workbench/common/contextkeys.ts:261-276 returns immediately from AbstractResourceContextKey.set() when the requested URI equals the instance's cached _value, without checking whether another instance reset or rewrote the shared keys. Its reset() clears those keys independently of other instances' cached values.
- **Explorer and Open Editors path:** src/vs/workbench/contrib/files/browser/views/openEditorsView.ts:368-382 creates a ResourceContextKey and resets/sets it on list focus changes. src/vs/workbench/contrib/files/browser/views/explorerView.ts:678-682 calls its own resourceContext.set(resource), including from onContextMenu() before menu evaluation. Reusing the same file therefore encounters the cached-URI early return after the other view changed the shared keys.
- **Observable menu consequence:** src/vs/workbench/contrib/files/browser/fileActions.contribution.ts:603-614 gates the Explorer Copy Path and Copy Relative Path entries on ResourceContextKey.IsFileSystemResource. The stale false value described in the report directly hides these entries even though the clicked Explorer item is a local file.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/343179 was independently verified through the GitHub API as open with merged_at null. Its body explicitly says 'Fixes #343178', describes the same shared-context root cause, and reports regression tests for two ResourceContextKey instances sharing a real ContextKeyService. These are PR-author-reported results, not checks executed during this read-only review.
