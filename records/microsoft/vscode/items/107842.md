# Issue #107842 — onDidDispose is fired when view is moved

[https://github.com/microsoft/vscode/issues/107842](https://github.com/microsoft/vscode/issues/107842)

## Summary

Moving a webview view between containers still disposes its extension-facing view in current source. Keep this accepted, team-authored bug open: the lifecycle gap remains, and neither related closed report establishes a fix or an eligible duplicate.

## Change summary

Moving a webview view between containers unexpectedly fires WebviewView.onDidDispose and recreates the view.

## Best solution

Preserve the extension-facing webview view lifecycle across container moves while retaining disposal for explicit removal. This requires lifecycle planning across view-container ownership and webview resolution, rather than suppressing the disposal event while still destroying its underlying view.

## Plan brief

- **Likely files:** `src/vs/workbench/services/views/browser/viewDescriptorService.ts`, `src/vs/workbench/browser/parts/views/viewPaneContainer.ts`, `src/vs/workbench/contrib/webviewView/browser/webviewViewPane.ts`, `src/vs/workbench/contrib/webviewView/browser/webviewViewService.ts`, `src/vs/workbench/api/browser/mainThreadWebviewViews.ts`, `src/vs/workbench/contrib/webviewView/test/browser/webviewViewPane.test.ts`
- **Validation:** Exercise a resolved extension webview view moved from its original container into a new top-level container, then another existing container, and back. Assert that the extension-facing view is not disposed or resolved again solely because of those moves, remains usable for messaging, and reports its final visibility correctly. Explicit context-menu removal must still dispose it. Add executable browser lifecycle coverage spanning real descriptor moves and webview resolution; the current WebviewViewPane suite only covers badge activity.
- **Behavior:**

  > Moving a resolved webview view between containers currently fires onDidDispose and causes a replacement view to be resolved. Container moves should preserve the extension-facing view rather than behave like explicit removal. Acceptance covers moving into a new top-level container, moving between existing containers, and moving back, with no disposal or redundant provider resolution caused by movement. Explicit hiding through the context menu must continue to dispose the view, and normal collapse and retainContextWhenHidden behavior must remain unchanged.
- **Trace:**

  > ViewDescriptorService.moveViewsWithoutSaving removes source descriptors and adds destination descriptors. ViewPaneContainer.onDidRemoveViewDescriptors removes the source pane, whose per-item DisposableStore owns the pane itself; the destination creates another pane in onDidAddViewDescriptors. WebviewViewPane.dispose fires onDispose, which MainThreadWebviewsViews forwards to ExtHostWebviewViews.$disposeWebviewView, ultimately firing the public event. This conclusively establishes the reported path without executing code. The uncertainty is how to preserve the webview's logical lifetime across generic pane ownership changes without leaking resources or changing other view types; the other shared-container consumers have not been fully traced. Preserve explicit-removal disposal and existing hidden-context semantics. The related reports https://github.com/microsoft/vscode/issues/107827 and https://github.com/microsoft/vscode/issues/107843 corroborate the distinction between movement disposal, visibility changes, and context retention.

## Evidence

- **Confirmed trigger:** The discussion on https://github.com/microsoft/vscode/issues/107842 explicitly confirms that moving a view to a top-level container and back, or between containers, incorrectly disposes it.
- **Current container-move path:** In src/vs/workbench/services/views/browser/viewDescriptorService.ts, moveViewsWithoutSaving removes descriptors from the source container before adding them to the destination. In src/vs/workbench/browser/parts/views/viewPaneContainer.ts, onDidRemoveViewDescriptors calls removePanes; addPane registers the pane itself in the pane item's DisposableStore, and removePane disposes that store. The destination's onDidAddViewDescriptors creates a new pane.
- **Extension event propagation:** WebviewViewPane.dispose in src/vs/workbench/contrib/webviewView/browser/webviewViewPane.ts unconditionally fires _onDispose. MainThreadWebviewsViews in src/vs/workbench/api/browser/mainThreadWebviewViews.ts forwards this through $disposeWebviewView; src/vs/workbench/api/common/extHostWebviewView.ts then disposes the extension-facing object and fires onDidDispose. There is no move-specific preservation on this traced path.
- **Public lifecycle documentation:** src/vscode-dts/vscode.d.ts documents WebviewView.onDidDispose in terms of explicitly hiding a view through its context menu; container movement is not documented as a disposal trigger.
