# Issue #201842 — Cache the list of files for "Go to file" / "Quick open" / "Search files by name"

[https://github.com/microsoft/vscode/issues/201842](https://github.com/microsoft/vscode/issues/201842)

## Summary

Keep open: Quick Open already caches search results, but current source starts a fresh file-list population when the picker opens, rather than maintaining the reusable, incrementally updated inventory requested here. The remaining performance opportunity needs a design that addresses the maintainer's memory concern; existing caching alone does not establish completion.

## Change summary

Avoid repeated workspace file enumeration in Ctrl+P by retaining a file inventory and updating it as files change.

## Best solution

Evaluate longer-lived file-inventory reuse in the Quick Open/search cache lifecycle, with explicit freshness and memory bounds. Preserve search exclusions, ranking, and accurate results after file creation, deletion, and rename.

Acceptance should measure enumeration count, cold and warm picker latency, and retained memory; the reported two seconds is context, not a universal performance threshold.
- **Trace:**

  > AnythingQuickAccessProvider in src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts creates and loads a FileQueryCacheState on normal picker activation. FileQueryCacheState in src/vs/workbench/contrib/search/common/cacheState.ts allocates a new key and temporarily falls back to the previous state until replacement loading completes. SearchService in src/vs/workbench/services/search/node/rawSearchService.ts stores and filters sorted-search results by cache key, so caching already exists; the unresolved boundary is retaining and refreshing the inventory across activations without redundant enumeration. The thread at https://github.com/microsoft/vscode/issues/201842 identifies memory cost as a concern and suggests opt-in behavior, but does not settle the user-visible policy. Preserve ranking, editor history, exclusions, cancellation, and local/remote search semantics. The related remote-performance report at https://github.com/microsoft/vscode/issues/183480 also includes cached-result sorting cost and is not proof that inventory retention would solve every latency case.
- **Open decisions:**
  - Should longer-lived inventory retention be automatic and bounded, or explicitly enabled by the user?
  - What result-freshness guarantee should users receive after filesystem changes, including changes missed by watchers: temporarily stale results with background reconciliation, or a fresh inventory before presenting results?
