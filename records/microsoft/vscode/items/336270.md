# Issue #336270 — Extension host immediately closes with no logs after opening with `F5`.

[https://github.com/microsoft/vscode/issues/336270](https://github.com/microsoft/vscode/issues/336270)

## Summary

Multiple independent users (Windows, Linux, WSL) now consistently reproduce this with `trace: true` logs, satisfying connor4312's info request from 2026-09-21 — the `info-needed` state is stale and this should move to a routed bug. The core extension host times out waiting for its ready handshake in debug-launch mode, and the attached js-debug traces show the debug adapter's own attach attempt failing with `connect ECONNREFUSED ::1:<port>` right before the timeout.

## Change summary

Launching an extension via F5 (debug) intermittently or consistently fails to start the Extension Development Host, while Ctrl+F5 (run without debugging) always works.

## Best solution

Root-cause why the js-debug adapter's connection to the extension host's inspector port refuses on the IPv6 loopback (`::1`) right as the 10s startup timeout fires in localProcessExtensionHost.ts — likely an IPv6-vs-IPv4 localhost resolution mismatch between the extension host process (which forces `--dns-result-order=ipv4first`, added in src/vs/workbench/services/extensions/electron-browser/localProcessExtensionHost.ts) and how the bundled js-debug adapter (built from microsoft/vscode-js-debug) resolves 'localhost' when attaching. The fix likely needs to land in vscode-js-debug's attach logic and/or how core exposes the inspector host/port to it.

- **Behavior:**

  > Pressing F5 to debug a VS Code extension should reliably start the Extension Development Host, matching Ctrl+F5 behavior. Instead, the host frequently (sometimes always) fails to send its ready message within 10-60s and the debug session terminates with no actionable Extension Host log, while Ctrl+F5 (no debugger) works every time.
- **Trace:**

  > Core's own timeout fires in localProcessExtensionHost.ts:356 ('Extension host did not start in 10 seconds (debugBrk: ...)') when `_performHandshake`/`_establishProtocol` don't complete in time (same file, lines 412-490). The attached js-debug adapter traces (fetched and inspected) show the adapter itself throwing `connect ECONNREFUSED ::1:<port>` while trying to attach to the target process's inspector port, around the same time the host exits — i.e. the debug adapter can't unblock the `--inspect-brk`-stopped extension host, so it never gets past its first line and times out. The extension host process forces `--dns-result-order=ipv4first` (same file, ~line 284) for its own networking; the debug adapter (built from https://github.com/microsoft/vscode-js-debug, a bundled builtin per this repo's product.json) is a separate process and its own localhost/DNS resolution for the CDP attach hasn't been confirmed to use the same order — that mismatch is the lead, not a confirmed fix. Do not touch the non-debug (Ctrl+F5) startup path, which is unaffected and must keep working exactly as today.
- **Open decisions:**
  - Does the actual fix belong in this repo (e.g. exposing/forcing a consistent inspector host/IP for js-debug to connect to) or in the vscode-js-debug adapter's own attach/localhost-resolution logic (or both)?
  - If the fix is IPv6/IPv4 resolution order related, should the extension host's inspector explicitly bind to 127.0.0.1 rather than relying on DNS resolution order flags?
