# Issue #90696 — Support tmux control mode (-CC flag)

[https://github.com/microsoft/vscode/issues/90696](https://github.com/microsoft/vscode/issues/90696)

## Summary

Keep this accepted, well-supported request open: built-in terminal persistence and the tmux profile do not provide control-mode integration with native tabs and splits. The reported extension is a useful alternative, not evidence that the accepted core request is complete.

## Change summary

Support tmux control mode so persistent tmux sessions use VS Code's native terminal tabs, splits, scrolling, and selection.

## Best solution

Design an opt-in tmux control-mode integration that maps server-side panes and sessions into native terminal UI while leaving ordinary terminals unchanged. Assess the extension mentioned in the discussion as prior art before committing to the cross-layer implementation.

## Plan brief

- **Likely files:** `src/vs/platform/terminal/common/terminal.ts`, `src/vs/platform/terminal/common/terminalPlatformConfiguration.ts`, `src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts`, `src/vs/workbench/contrib/terminal/browser/terminalGroup.ts`, `src/vs/workbench/contrib/terminal/browser/terminalService.ts`
- **Validation:** On a local or SSH host with tmux, attach through the proposed control-mode entry point to a session with multiple panes; verify native tabs/splits, per-pane output and input, scrolling and selection, then close and reopen VS Code and verify attachment to the same still-running processes. Confirm ordinary non-tmux terminal behavior remains unchanged; the plan must establish automated protocol and lifecycle coverage.
- **Behavior:**

  > Users can attach VS Code's native terminal UI to a tmux control-mode session rather than operate tmux's textual pane interface. Native tabs and splits expose the attached panes, input reaches the selected pane, and normal scrolling and selection work. Closing and reopening the editor allows reattachment to surviving tmux processes without restarting them. Existing non-tmux terminals retain their behavior.
- **Trace:**

  > The built-in tmux profiles in src/vs/platform/terminal/common/terminalPlatformConfiguration.ts launch the executable without control-mode semantics. TerminalProcessManager in src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts handles the ordinary process-data stream, while TerminalGroup.split in src/vs/workbench/contrib/terminal/browser/terminalGroup.ts creates a new instance from a shell launch configuration. The persistence settings in src/vs/workbench/contrib/terminal/common/terminalConfiguration.ts distinguish reload persistence from recreating processes after shutdown; they do not establish a tmux pane/session model. Source searches found no control-mode implementation, but the trace does not yet establish the backend, reconnection, and layout contracts needed for one. Preserve ordinary terminal lifecycle behavior and do not treat shell recreation as survival of tmux processes. https://github.com/microsoft/vscode/issues/90696 records the maintainer's complexity concerns and the extension alternative; https://github.com/microsoft/vscode/issues/324350 is related orchestration work, not a duplicate canonical.
- **Open decisions:**
  - When a user closes a native tab or split attached to tmux, should that terminate the corresponding tmux pane or only detach its VS Code presentation?
  - Should attaching to an existing tmux session mirror its server-side window and pane layout, or allow an independent VS Code layout?
