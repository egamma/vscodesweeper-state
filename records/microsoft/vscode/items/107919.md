# Issue #107919 — Setting to follow to running cells in a notebook

[https://github.com/microsoft/vscode/issues/107919](https://github.com/microsoft/vscode/issues/107919)

## Summary

Keep open: ordinary Run All still lacks an opt-in mode that continuously follows the executing cell. Existing one-shot navigation and Copilot-specific auto-reveal only partially cover this accepted Backlog request.

## Change summary

Provide an option to automatically follow the currently executing cell throughout a notebook Run All operation.

## Best solution

Provide opt-in execution following for ordinary notebook runs, reusing existing reveal behavior where appropriate while preserving stationary scrolling when disabled. Settle activation and manual-scroll interruption semantics before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/notebook/browser/controller/executeActions.ts`, `src/vs/workbench/contrib/notebook/browser/notebook.contribution.ts`, `src/vs/workbench/contrib/notebook/browser/contrib/execute/executionEditorProgress.ts`, `src/vs/workbench/contrib/notebook/common/notebookExecutionStateService.ts`
- **Validation:** Run a notebook containing several cells taller than the viewport with staggered execution delays. With following enabled, verify the viewport advances to each executing cell without repeated navigation; with it disabled, verify Run All does not follow execution. Check manual scrolling according to the chosen interruption contract and preserve existing Go to Running Cell and Shift+Enter behavior.
- **Behavior:**

  > Users running all cells in a long notebook should be able to opt into following the currently executing cell as execution advances. The mode must work for ordinary Run All, not only Copilot-triggered execution. Acceptance should cover oversized cells and rapid transitions, preserve non-following behavior when disabled, and make manual-scroll interruption predictable.
- **Trace:**

  > ExecuteNotebookAction in src/vs/workbench/contrib/notebook/browser/controller/executeActions.ts delegates Run All to executeNotebookCells(); RevealRunningCellAction performs one-shot navigation. The same file's runCell helper supports command-supplied autoReveal, but reveals the first selected cell rather than subscribing to subsequent execution changes. notebook.scrolling.revealNextCellOnExecute in notebook.contribution.ts governs Execute and Select Below, while ExecutionEditorProgressController observes execution changes to update progress visibility. Copilot's follow setting and notebookServiceImpl.runCells provide related reveal plumbing but do not cover the ordinary Run All path. Preserve existing non-following execution, explicit navigation, and Shift+Enter semantics. Related design context is https://github.com/microsoft/vscode/issues/130611; agent-wide following in https://github.com/microsoft/vscode/issues/250527 is separate scope. Uncertainty begins with how users activate following and how deliberate viewport navigation interrupts it.
- **Open decisions:**
  - Should following be enabled by a persistent setting for ordinary notebook runs or a transient mode activated for the current notebook execution?
  - Should manual scrolling suspend following until explicitly resumed, or should the next executing cell bring the viewport back?
