# Issue #41574 — Can we get a few more pixels for clicking the cursor at the beginning of a line?

[https://github.com/microsoft/vscode/issues/41574](https://github.com/microsoft/vscode/issues/41574)

## Summary

The narrow click target remains on current main, and this issue is still the canonical report for the misleading boundary between text and folding controls. Newer related requests broaden the problem into configurable padding, but cannot replace this re-reviewed issue as a duplicate canonical.

## Change summary

Make the area immediately before the first character easier to click for placing the caret or starting a selection at column one, without accidentally activating folding controls.

## Best solution

Define a small, consistent editor-content hit area before column one that places the caret at the line start while preserving intentional gutter and folding interactions. The editor team should first settle whether this is an expanded hit target or visible content padding, since those alternatives produce different layout and gutter behavior.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/mouseTarget.ts`, `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/test/browser/controller`
- **Validation:** Add editor mouse-target coverage for coordinates at and immediately before `layoutInfo.contentLeft`, then manually verify that clicking and shift-dragging there starts at column one while clicking an actual folding control still toggles folding.
- **Behavior:**

  > At the left edge of a rendered line, the pointer and click behavior must agree: a text-selection pointer indicates that clicking or beginning a drag will place the caret or selection at column one. Users should not need pixel-level precision to select the first character, and a click presented as a text click must not toggle folding. Intentional clicks on folding controls and existing gutter interactions must remain available.
- **Trace:**

  > In src/vs/editor/browser/controller/mouseTarget.ts, BareHitTestRequest sets `isInMarginArea` for every coordinate left of `layoutInfo.contentLeft`; `_hitTestMargin` then assigns that coordinate to glyph, line-number, or line-decoration behavior. `_getMouseColumn` maps negative content offsets to column one, but that mapping does not turn the margin into a content target. https://github.com/microsoft/vscode/issues/127025 confirms the same I-beam/click mismatch and was explicitly consolidated into this issue. The boundary is editor hit testing and its corresponding layout contract; do not alter general line-selection semantics or folding activation outside the agreed column-one target area.
- **Open decisions:**
  - Should the extra column-one target be an invisible expansion into the existing margin, or visible content-left padding that changes editor layout?
  - How wide should the target be, and must that width be fixed by the editor or configurable by users?
  - Where should the boundary remain for folding controls so their intentional clickable area is preserved without showing a text cursor over it?

## Evidence

- **current source:** src/vs/editor/browser/controller/mouseTarget.ts classifies every horizontal coordinate before `layoutInfo.contentLeft` as margin and routes it through `_hitTestMargin`; `_getMouseColumn` only maps coordinates to column one after content-area targeting. There is no intervening content hit area on current main.
- **confirmed symptom:** https://github.com/microsoft/vscode/issues/127025 documented the same observable behavior—an I-beam over the leftmost pixels while clicks are ignored or activate folding—and a maintainer closed it as a duplicate of this issue.
- **related broader request:** https://github.com/microsoft/vscode/issues/93053 remains open and requests configurable left gutter behavior, but it was created after this issue and covers broader layout customization rather than only the misleading column-one click target.
- **newer padding proposal:** https://github.com/microsoft/vscode/issues/135114 remains open and proposes `editor.contentLeftPadding`; it was created in 2021, after this 2018 report, so it cannot be the canonical duplicate for this re-reviewed item.
- **no existing capability or fix:** Current editor options expose vertical `editor.padding.top` and `editor.padding.bottom`, but no content-left padding option; repository history contains no commit referencing #41574 or #127025.
