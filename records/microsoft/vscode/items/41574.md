# Issue #41574 — Can we get a few more pixels for clicking the cursor at the beginning of a line?

[https://github.com/microsoft/vscode/issues/41574](https://github.com/microsoft/vscode/issues/41574)

## Summary

The narrow start-of-line click target remains in current main, and this issue is the maintainer-selected canonical for that behavior. Broader padding requests are related but do not supersede this focused mouse-targeting bug.

## Change summary

Make it easier to place or begin a selection at column one without accidentally targeting the folding gutter or column two.

## Best solution

Increase the effective start-of-line mouse target while preserving deliberate gutter interactions, coordinating the behavior with the broader configurable-padding request in https://github.com/microsoft/vscode/issues/135114.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/mouseTarget.ts`, `src/vs/editor/browser/controller/mouseHandler.ts`, `src/vs/editor/browser/config/editorConfiguration.ts`, `src/vs/editor/common/config/editorOptions.ts`
- **Validation:** Add a targeted editor mouse-hit test, or an equivalent browser-level check, showing that clicks in the agreed start-of-line tolerance place the caret at column one while clicks on folding controls and line numbers retain their existing behavior.
- **Behavior:**

  > A user should be able to click or begin dragging immediately beside the first character and reliably target column one instead of the gutter or column two. Folding controls and deliberate line-number interactions must remain usable. Acceptance should cover an unindented line, an indented line, drag selection beginning at column one, and a line with a visible folding control.
- **Trace:**

  > Current hit classification is in BareHitTestRequest and MouseTargetFactory in src/vs/editor/browser/controller/mouseTarget.ts: positions left of `layoutInfo.contentLeft` are margin targets, and content columns are calculated by rounding the offset against the character width. MouseHandler._onMouseDown in src/vs/editor/browser/controller/mouseHandler.ts starts selection only for content targets or selectable line numbers and suppresses other gutter clicks. This explains the abrupt, narrow boundary confirmed by https://github.com/microsoft/vscode/issues/127025. The boundary is editor mouse targeting and layout; ordinary gutter activation, RTL behavior, horizontal scrolling, and non-mouse cursor movement must not regress. The uncertainty starts with whether the tolerance should be a fixed default hit area, visible/configurable padding coordinated with https://github.com/microsoft/vscode/issues/135114, or both.
- **Open decisions:**
  - Should the larger column-one target be an invisible fixed tolerance, visible padding, or a configurable editor option?
  - How wide should the target be by default, and should it scale with font metrics or display scaling?
  - Which parts of the folding and line-decoration gutter, if any, may yield nearby clicks to column one?

## Evidence

- **current source:** In src/vs/editor/browser/controller/mouseTarget.ts, BareHitTestRequest classifies every point left of `layoutInfo.contentLeft` as margin, while `_getMouseColumn` rounds the content offset by character width; there is no dedicated tolerance area that maps nearby clicks to column one.
- **gutter behavior:** src/vs/editor/browser/controller/mouseHandler.ts handles content targets by starting cursor selection but prevents default without focusing for gutter targets, so a small movement across the exact `contentLeft` boundary changes the interaction.
- **canonical confirmation:** A VS Code team member reproduced the narrow target in https://github.com/microsoft/vscode/issues/127025#issuecomment-944307698 and closed that report as a duplicate of this issue in https://github.com/microsoft/vscode/issues/127025#issuecomment-944413821.
- **related broader request:** https://github.com/microsoft/vscode/issues/135114 remains open in the Backlog and asks for configurable visual and clickable content padding; it covers broader customization beyond this issue's focused start-of-line hit-target defect.
