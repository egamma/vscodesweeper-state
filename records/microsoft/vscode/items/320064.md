# Issue #320064 — Tagging a new vscode release should be automated

[https://github.com/microsoft/vscode/issues/320064](https://github.com/microsoft/vscode/issues/320064)

## Summary

Keep open: the inspected release pipelines do not automate public release-tag creation, and the linked incident explicitly identifies this issue as the preventive follow-up. It is already correctly classified under engineering; no verified fix or canonical duplicate was found.

## Change summary

Automate creation of correctly named Git tags pointing to the source commit of each VS Code release.

## Best solution

Make correct public release tagging a reliable part of the release workflow, with the full released version and matching source commit, rather than a separate manual operation. Establish the stable-release integration boundary before implementation and preserve existing release approvals.

## Plan brief

- **Likely files:** `build/azure-pipelines/product-release.yml`, `build/azure-pipelines/common/releaseBuild.ts`, `build/azure-pipelines/product-publish.yml`, `build/azure-pipelines/publish-types/publish-types.yml`
- **Validation:** End the plan with a disposable-repository or mocked-GitHub check: releasing version 1.123.0 at commit C produces exactly refs/tags/1.123.0 pointing to C; retrying is harmless, a conflicting existing tag is surfaced without replacement, and unreleased builds do not receive public release tags.
- **Behavior:**

  > Release tags must use the complete released version and identify the source commit used for that release. The reported 1.123 versus 1.123.0 mismatch must not require manual correction or break downstream consumers. Acceptance should cover correct naming and commit selection, safe retries, explicit conflict handling, and exclusion of builds that have not been released.
- **Trace:**

  > build/azure-pipelines/product-release.yml delegates to main in build/azure-pipelines/common/releaseBuild.ts, which reads BUILD_SOURCEVERSION and VSCODE_QUALITY and invokes the releaseBuild stored procedure; no Git-tag creation appears in that wrapper. build/azure-pipelines/product-publish.yml obtains package.json.version for build metadata, while build/azure-pipelines/publish-types/publish-types.yml consumes tags that already exist. The maintainer's comment at https://github.com/microsoft/vscode/issues/319760#issuecomment-4629719323 establishes this as preventive work beyond the manually corrected incident. The trace stops at the release-service and stable-release orchestration boundary, whose complete behavior is not present in the inspected files. Preserve existing release approvals and type-publication behavior; do not equate artifact publication or an Azure build tag with a public Git release tag.
- **Open decisions:**
  - At what stable-release milestone must the public Git tag become visible, and should failure to create the correct tag block release completion or leave the release published with an explicit recoverable failure?
