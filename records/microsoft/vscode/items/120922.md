# Issue #120922 — The scroll bar  is not accessible through keyboard key present on the error pop-up

[https://github.com/microsoft/vscode/issues/120922](https://github.com/microsoft/vscode/issues/120922)

## Summary

The accessibility defect remains on current main: the error popup is focusable, but its overflowing content has no keyboard-scrolling path. The shared scrollbar is pointer-driven and explicitly hidden from the accessibility tree.

## Change summary

Allow keyboard users to scroll overflowing content in the error popup opened by problem navigation.

## Best solution

Provide standards-consistent keyboard scrolling when the marker-navigation popup is focused, without stealing editor navigation keys or changing mouse scrolling. A maintainer should first decide whether keyboard and ARIA semantics belong in the shared scrollbar widget or only in focusable consumers such as marker navigation.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/scrollbar/abstractScrollbar.ts`, `src/vs/base/browser/ui/scrollbar/scrollableElement.ts`, `src/vs/base/test/browser/ui/scrollbar/scrollableElement.test.ts`, `src/vs/editor/contrib/gotoError/browser/gotoErrorWidget.ts`
- **Validation:** Add browser unit coverage that focuses an overflowing scroll region, dispatches the chosen arrow-key interactions, and asserts ScrollableElement.getScrollPosition() changes; run scripts/test.sh with a grep for the new keyboard-scrolling suite. Manually verify Shift+F8, Tab into the marker popup, and horizontal and vertical keyboard scrolling.
- **Behavior:**

  > Opening a diagnostic with Shift+F8 and moving focus into an overflowing error popup must allow all hidden message content to be reached with the keyboard. Horizontal and vertical scrolling should respond to documented keys while the popup is focused. Editor cursor movement and existing mouse-wheel and pointer scrolling must remain unchanged when focus is elsewhere.
- **Trace:**

  > MarkerNavigationWidget._fillBody in src/vs/editor/contrib/gotoError/browser/gotoErrorWidget.ts gives the popup container tab focus. MessageWidget wraps diagnostic content in ScrollableElement, but no keydown path updates its scroll position. AbstractScrollbar in src/vs/base/browser/ui/scrollbar/abstractScrollbar.ts marks scrollbar DOM as presentation/aria-hidden and only wires pointer input, which conclusively leaves focused keyboard users unable to operate it. The boundary is keyboard and accessibility behavior for overflowing custom scroll regions: do not alter editor arrow-key handling, mouse scrolling, or non-overflowing popup focus behavior. The editor-hover work in https://github.com/microsoft/vscode/issues/69836 is related precedent but uses hover-specific commands and does not cover this widget.
- **Open decisions:**
  - Should keyboard and ARIA scrollbar semantics be implemented once in the shared ScrollableElement/AbstractScrollbar widgets, or should the marker-navigation popup own a focused-region scrolling handler?
  - Which standard key set and focus model should be exposed for horizontal and vertical scrolling without adding disruptive tab stops to every custom scrollbar consumer?

## Evidence

- **focus path:** src/vs/editor/contrib/gotoError/browser/gotoErrorWidget.ts makes MarkerNavigationWidget._parentContainer focusable with tabIndex 0, but neither MarkerNavigationWidget nor MessageWidget registers a keyboard handler for scrolling.
- **scroll path:** MessageWidget in src/vs/editor/contrib/gotoError/browser/gotoErrorWidget.ts renders overflowing diagnostic text through ScrollableElement and updates content position only from its onScroll event.
- **shared scrollbar behavior:** src/vs/base/browser/ui/scrollbar/abstractScrollbar.ts assigns role="presentation" and aria-hidden="true" to the scrollbar DOM node and implements pointer interaction, with no keyboard operation.
- **related issue:** https://github.com/microsoft/vscode/issues/69836 addressed keyboard scrolling for the separate editor-hover implementation; its commands live under src/vs/editor/contrib/hover and do not cover the marker-navigation popup.
- **maintainer assessment:** The maintainer response in https://github.com/microsoft/vscode/issues/120922 treats keyboard scrolling as behavior the scrollbar widget should support, confirming the reported behavior is not intentional.
