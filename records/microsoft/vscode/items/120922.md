# Issue #120922 — The scroll bar  is not accessible through keyboard key present on the error pop-up

[https://github.com/microsoft/vscode/issues/120922](https://github.com/microsoft/vscode/issues/120922)

## Summary

The keyboard-accessibility gap remains on current main: the marker popup receives focus, but neither it nor the shared scrollable widget handles arrow-key scrolling. The issue is already correctly classified and routed, so it should remain open.

## Change summary

Allow keyboard users to scroll horizontally through an overflowing error message in the marker-navigation popup.

## Best solution

Define keyboard-scrolling semantics for focused custom scrollable regions, then support horizontal arrow-key scrolling in the marker-navigation popup without disrupting editor navigation or interactive links.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/gotoError/browser/gotoErrorWidget.ts`, `src/vs/base/browser/ui/scrollbar/scrollableElement.ts`, `src/vs/base/browser/ui/scrollbar/abstractScrollbar.ts`, `src/vs/base/test/browser/ui/scrollbar/scrollableElement.test.ts`
- **Validation:** Add a targeted browser test proving that ArrowLeft and ArrowRight change horizontal scroll position while the intended scrollable region is focused, then manually verify the Shift+F8, Tab, arrow-key flow without changing editor cursor navigation or related-diagnostic link activation.
- **Behavior:**

  > When a Shift+F8 error popup contains text wider than its viewport, a keyboard user can focus the popup and scroll the hidden content horizontally with appropriate keys. The interaction must expose all diagnostic text without requiring a mouse. Editor arrow-key behavior outside the focused popup and keyboard access to links and popup actions must remain unchanged.
- **Trace:**

  > MarkerNavigationWidget._fillBody in src/vs/editor/contrib/gotoError/browser/gotoErrorWidget.ts assigns tabIndex 0 to the popup body. MessageWidget places diagnostic content in ScrollableElement, but neither class listens for keyboard scrolling. AbstractScrollbar in src/vs/base/browser/ui/scrollbar/abstractScrollbar.ts excludes its DOM node from the accessibility tree and implements pointer interactions only. The shared widget is widely consumed, so the boundary is keyboard behavior for intentionally focused scrollable regions; non-focusable scrollables and normal editor navigation must not change. The maintainer comment at https://github.com/microsoft/vscode/issues/120922#issuecomment-936108868 points toward shared scrollbar support, but does not definitively settle that scope.
- **Open decisions:**
  - Should arrow-key scrolling become a shared behavior for every intentionally focusable ScrollableElement host, or remain specific to the marker-navigation popup?

## Evidence

- **source reproduction:** src/vs/editor/contrib/gotoError/browser/gotoErrorWidget.ts makes MarkerNavigationWidget._parentContainer focusable with tabIndex 0 and embeds the message in ScrollableElement, but contains no keyboard handler that changes its scroll position.
- **scrollbar implementation:** src/vs/base/browser/ui/scrollbar/abstractScrollbar.ts marks the custom scrollbar role="presentation" and aria-hidden="true" and registers pointer handling only; no ArrowLeft or ArrowRight handling exists in the scrollbar implementation.
- **maintainer assessment:** https://github.com/microsoft/vscode/issues/120922#issuecomment-936108868 identifies this as behavior likely requiring support in the shared scrollbar widget.
- **canonical search:** https://github.com/microsoft/vscode/issues/336483 concerns exposing Sidebar scroll regions through UIAutomation and does not own marker-popup keyboard scrolling; the suggested https://github.com/microsoft/vscode/issues/116061 is closed and concerns mouse-wheel dismissal instead.
