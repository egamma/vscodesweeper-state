# Issue #241767 — Localise media paths in walkthroughs

[https://github.com/microsoft/vscode/issues/241767](https://github.com/microsoft/vscode/issues/241767)

## Summary

Keep this accepted localization request open: current walkthroughs support convention-based localized Markdown, but not locale substitution in arbitrary media paths. The linked localization issue was explicitly consolidated into this issue, and maintainers have endorsed the work.

## Change summary

Support an opt-in locale token in walkthrough media paths, including filenames, directories, and theme-specific image paths, without translating the rest of the path.

## Best solution

Provide documented locale-aware resource selection in the walkthrough contribution while preserving existing literal paths and Markdown localization. Settle locale selection and missing-resource fallback semantics before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/welcomeGettingStarted/browser/gettingStartedService.ts`, `src/vs/workbench/contrib/welcomeGettingStarted/browser/gettingStartedExtensionPoint.ts`, `src/vs/workbench/contrib/welcomeGettingStarted/browser/gettingStartedDetailsRenderer.ts`
- **Validation:** Use a development extension contributing Markdown and image media with {locale} in filenames and directories, including theme-specific image values. Switch display language between English, French, and a regional locale; verify the selected resources, approved missing-resource fallback, and unchanged literal-path and existing .nls.<language>.md behavior.
- **Behavior:**

  > Extension authors can opt into localized walkthrough resources without maintaining translated copies of each resource-path string. Locale substitution supports both filename and directory placement and object-valued image variants, while leaving non-token path text intact. Existing literal resource paths, localized titles and alt text, and convention-based localized Markdown retain their behavior. Acceptance must cover English/default language, a translated language, regional locales, and missing localized assets according to the agreed contract.
- **Trace:**

  > registerExtensionWalkthroughContributions in src/vs/workbench/contrib/welcomeGettingStarted/browser/gettingStartedService.ts converts image strings and theme variants directly to browser URIs, and Markdown/SVG strings to file URIs; no locale-token substitution exists on these paths. gettingStartedExtensionPoint.ts defines the public media contribution schema without token semantics. readContentsOfPath in gettingStartedDetailsRenderer.ts already probes .nls.<language>.md, then the generalized language, then the original resource, providing partial Markdown coverage that must remain compatible. Generic manifest localization in src/vs/platform/extensionManagement/common/extensionNls.ts substitutes whole %key% values rather than interpolating locale tokens. The reporter proposed generation-time substitution and literal-token default assets, while https://github.com/microsoft/vscode-l10n/issues/180#issuecomment-2677587936 proposes runtime display-language selection and an English default; the maintainer endorsement does not settle this contract. https://github.com/microsoft/vscode-l10n/issues/180#issuecomment-3633997684 explicitly leaves this issue owning the work. Keep the scope to walkthrough resource localization, not general translation tooling or translating text embedded in SVGs.
- **Open decisions:**
  - Should {locale} resolve at walkthrough load time from the active display language, or during localized-resource generation, and what value represents the default English locale?
  - When a regional or translated asset is absent, should tokenized paths fall back to a generalized locale, an English asset, or the literal-token default resource described in the report?
