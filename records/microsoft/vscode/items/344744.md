# Issue #344744 — Webview view: "Found unexpected null" in hookupOnLoadHandlers when options and html are set back to back

[https://github.com/microsoft/vscode/issues/344744](https://github.com/microsoft/vscode/issues/344744)

## Summary

The reported race remains in current source: deferred load setup can access an iframe after a subsequent content update removes it. An open contributor PR addresses this exact failure, so keep the issue open while that implementation is reviewed.

## Change summary

Prevent uncaught null assertions when consecutive webview content updates replace an iframe before its deferred load handlers run.

## Best solution

Review and land https://github.com/microsoft/vscode/pull/344773 after confirming that superseded frames cannot execute stale load setup or fallback callbacks, while the latest frame still renders and receives its normal events.

## Evidence

- **Consecutive content updates:** src/vs/workbench/contrib/webview/browser/webviewElement.ts:669–687 calls doUpdateContent independently from setHtml and the contentOptions setter; doUpdateContent at lines 705–729 sends a content message for each update. This matches the reporter's options-then-html trigger.
- **Current-source race:** src/vs/workbench/contrib/webview/browser/pre/index.html:1058–1061 removes the previous pending iframe. onFrameLoaded at lines 1106–1121 schedules an unguarded zero-delay callback that calls hookupOnLoadHandlers(newFrame). That function at lines 1207–1217 asserts newFrame.contentWindow without checking attachment; its 200ms fallback also asserts the frame document and window. Removing the frame between scheduling and execution therefore leaves the reported null-assertion path reachable.
- **Existing guard does not cover this path:** src/vs/workbench/contrib/webview/browser/pre/index.html:1125–1137 checks parentElement only in the Safari polling branch. The currentUpdateId check near the start of the content handler does not cancel callbacks already scheduled for a previous frame.
