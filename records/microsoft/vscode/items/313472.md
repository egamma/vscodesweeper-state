# Issue #313472 — [Agents]: Best practices for dev server port conflicts across worktree sessions

[https://github.com/microsoft/vscode/issues/313472](https://github.com/microsoft/vscode/issues/313472)

## Summary

This remains a real Agents platform gap: a maintainer confirmed that choosing an open port is currently project-owned and that VS Code has no platform solution. Keep it open under the Backlog Candidates process and classify it as under discussion while the session endpoint contract is designed.

## Change summary

Provide worktree-isolated agent sessions with conflict-free dev-server endpoints that are discoverable by users and reusable by automated tests.

## Best solution

Define one session-scoped endpoint contract that allocates or records the effective dev-server port, makes it available to commands and test processes, and surfaces the resulting URL in the session UI. The design should cover concurrent worktrees without imposing framework-specific output parsing.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/common/state/protocol/channels-terminal/commands.ts`, `src/vs/platform/agentHost/node/agentHostTerminalManager.ts`, `src/vs/platform/agentHost/node/agentService.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/stateToProgressAdapter.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts`
- **Validation:** Add targeted AgentHostTerminalManager and stateToProgressAdapter tests, then an Agent Host E2E scenario proving that two concurrent worktree sessions receive distinct usable endpoints, display the correct URL per session, and run a child test command against that same endpoint.
- **Behavior:**

  > Two concurrent worktree-isolated sessions can start the same project's dev server without binding the same local port or silently testing another checkout. Each session exposes its effective server URL prominently, and commands or test processes launched for that session can consume the same endpoint without parsing unrelated terminal output. Existing folder-isolated sessions and ordinary terminal environment behavior remain unchanged.
- **Trace:**

  > Worktree selection is resolved on first send by AgentService._resolveWorkingDirectoryBeforeSend in src/vs/platform/agentHost/node/agentService.ts and passed to provider execution as a working directory only. AgentHostTerminalManager.createTerminal in src/vs/platform/agentHost/node/agentHostTerminalManager.ts creates the PTY environment from the Agent Host process environment; CreateTerminalParams in the generated AHP protocol copy has no environment or endpoint field. Terminal tool output is adapted into chat progress by stateToProgressAdapter.ts and agentHostSessionHandler.ts, but the Agents-specific path has no dev-server URL contract. The uncertainty starts at ownership: VS Code could allocate an endpoint before launch, accept endpoint metadata from the tool/runtime, or infer it from output, and those choices have different protocol and framework-compatibility costs. Any protocol change must originate in the agent-host-protocol repository and be synchronized into the generated VS Code copy.
- **Open decisions:**
  - Should VS Code allocate a session endpoint before launching commands, or should the dev server report the endpoint it selected?
  - What session-scoped contract should expose the endpoint to both the dev command and later test processes without relying on framework-specific output parsing?
  - Should URL presentation be automatic terminal-output detection, explicit runtime metadata, or both?
  - How should endpoint lifetime, reuse, and cleanup behave when a session is archived, resumed, or run on a remote Agent Host?
