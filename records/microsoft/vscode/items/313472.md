# Issue #313472 — [Agents]: Best practices for dev server port conflicts across worktree sessions

[https://github.com/microsoft/vscode/issues/313472](https://github.com/microsoft/vscode/issues/313472)

## Summary

Keep this Backlog Candidates feature request open under the community process. A maintainer confirmed that VS Code has no platform solution yet and recommended selecting an open port as the current workaround.

## Change summary

Provide session-aware dev-server port allocation and URL discovery so isolated worktree sessions and their end-to-end tests target the correct server.

## Best solution

Define a session-scoped dev-server contract that lets run actions expose the selected URL to the Agents UI and subsequent commands or tests, while leaving port selection to the project's server tooling.

## Plan brief

- **Likely files:** `src/vs/sessions`
- **Validation:** An end-to-end Agents scenario should start servers from two isolated worktrees, allocate distinct ports, surface each session's actual URL, and make a session-launched Playwright run target its own server rather than the main workspace server.
- **Behavior:**

  > Each isolated agent worktree can run a development server without colliding with another session or silently directing validation at the wrong workspace. When a server selects a different open port, the session prominently exposes the actual URL and makes it available to subsequent session commands and end-to-end tests. Acceptance covers two concurrent worktrees, distinct URLs, and Playwright targeting the server associated with its own session.
- **Trace:**

  > The issue establishes a product gap rather than a defect: a maintainer confirmed that there is no platform solution and recommended project code select an open port. The unresolved boundary starts at how a run action reports a dynamically selected endpoint to the Agents session, how that endpoint is displayed, and whether later commands receive it through environment or structured session state. Keep port selection compatible with existing dev-server tooling; do not require VS Code to parse arbitrary process output without an explicit contract. No related canonical issue or open fixing PR is identified in the supplied timeline.
- **Open decisions:**
  - Should the public contract expose one conventional session-scoped development URL/port, or support multiple named endpoints per session?
  - Must projects explicitly publish the selected endpoint through a structured protocol, or should VS Code also infer URLs from terminal output?
  - Should the selected endpoint be injected automatically into all later session commands and tests, or only exposed for explicit project configuration?
