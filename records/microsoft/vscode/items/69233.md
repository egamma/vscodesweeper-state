# Issue #69233 — Workspace-level environment variable *definitions*

[https://github.com/microsoft/vscode/issues/69233](https://github.com/microsoft/vscode/issues/69233)

## Summary

Keep this accepted, well-supported request open: existing terminal and task environment settings do not provide one workspace-scoped definition shared with debugging and extensions. The canonical search found related requests, but none verified as an older report owning the same capability.

## Change summary

Define workspace-scoped environment variables once, including through an untracked .env file, for tasks, debug launches, integrated terminals, and extensions.

## Best solution

Design a shared workspace environment contract rather than requiring separate configuration for every consumer. Settle precedence, extension visibility, and update semantics before implementing it across workspace configuration and process-launch paths.

## Plan brief

- **Likely files:** `src/vs/workbench/services/configuration/browser/configurationService.ts`, `src/vs/workbench/services/configurationResolver/common/variableResolver.ts`, `src/vs/workbench/services/configurationResolver/electron-browser/configurationResolverService.ts`, `src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts`, `src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** After agreeing the contract, open two workspaces with conflicting NODE_ENV and DOMAIN definitions and separate gitignored .env files. Verify tasks, debugged programs, integrated terminals, and an extension-launched child process receive their own workspace values without changing the global environment or the other window. Check the agreed override precedence and reload/edit behavior.
- **Behavior:**

  > A workspace can declare an environment once, with optional values loaded from an untracked .env file, instead of repeating definitions in every consumer. Tasks, debug launches, integrated terminals, and extensions should obtain the applicable workspace environment without leaking values into other workspaces or global shell configuration. Acceptance includes two concurrently open workspaces using different values and consistent behavior across all agreed consumers. Folder-specific environments are a companion concern; this issue's central requirement remains workspace-wide definitions.
- **Trace:**

  > Terminal environment settings are registered in src/vs/workbench/contrib/terminal/common/terminalConfiguration.ts, while task command environments are separately represented in jsonSchemaCommon.ts and applied by TerminalTaskSystem in src/vs/workbench/contrib/tasks/browser/terminalTaskSystem.ts. ConfigurationResolverService obtains the shell environment, and AbstractVariableResolverService resolves environment references from that environment rather than loading workspace definitions. ExtensionContext.environmentVariableCollection in src/vscode-dts/vscode.d.ts only covers terminal environments. These inspected surfaces establish the fragmented capability, but a shared definition contract would also require tracing debug and extension-host propagation before implementation. Preserve current behavior for workspaces without definitions and keep unrelated windows isolated. Related design work exists at https://github.com/microsoft/vscode/issues/130493 and https://github.com/microsoft/vscode/issues/152806, but neither absorbs this older, broader request.
- **Open decisions:**
  - What precedence should apply among inherited process variables, workspace declarations, .env values, and consumer-specific environment overrides?
  - Should extensions receive these values through their process environment, a workspace-scoped API, or both?
  - Do edits to workspace environment definitions affect only subsequently launched processes, or require a reload or restart of existing consumers?
