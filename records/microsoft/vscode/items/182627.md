# Issue #182627 — Recent entry URL can get too large for Windows jumplist

[https://github.com/microsoft/vscode/issues/182627](https://github.com/microsoft/vscode/issues/182627)

## Summary

The issue remains necessary: current main still passes the complete dev-container URI through Electron's Windows jump-list `args`, where the confirmed OS/Electron length limit can truncate it. The merged validation fix prevents downstream URI errors but does not preserve the requested folder.

## Change summary

Long dev-container URIs are truncated in Windows jump-list entries, so selecting a recent folder cannot reopen the intended container path.

## Best solution

Resolve or formally expose the Windows/Electron argument-length constraint, then ensure VS Code never publishes an unusable recent entry—either by using a short stable handoff that preserves the destination or by safely excluding entries that exceed the supported limit.

## Evidence

- **confirmed diagnosis:** A maintainer traced the failure to Windows or Electron cropping the long `--folder-uri` argument, leaving VS Code with a remote URI whose path is missing: https://github.com/microsoft/vscode/issues/182627#issuecomment-1551069709
- **current source:** On current main, src/vs/platform/workspaces/electron-main/workspacesHistoryMainService.ts:426-445 still places `workspace.toString()` directly into each jump-list item's `args`; only the title and description are length-limited.
- **partial mitigation:** Merged https://github.com/microsoft/vscode/pull/184163 (commit 80deac05cf355ce0f7673aa60f47b348bb57bcea) normalizes an empty remote URI path to `/` in windowsMainService.ts. It does not limit jump-list arguments or restore the truncated target path.
- **workaround:** The maintainer advised avoiding the Windows jump list for dev containers and using VS Code's in-product recent menu instead: https://github.com/microsoft/vscode/issues/182627#issuecomment-1554160067
