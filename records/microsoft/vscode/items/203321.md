# Issue #203321 — Git - rescan workspace after connection to the workspace folder restored

[https://github.com/microsoft/vscode/issues/203321](https://github.com/microsoft/vscode/issues/203321)

## Summary

Keep open: current Git discovery code still has a recovery gap that explains missing nested repositories after the workspace root reopens. Neither the closed earlier report nor the newer worktree issue is a valid duplicate target.

## Change summary

Restore discovery of nested Git repositories after a network-hosted workspace becomes accessible again, without restarting VS Code or its extension host.

## Best solution

The built-in Git extension should recover repositories eligible under the existing discovery settings when workspace access returns, while preserving intentional repository closures. First establish the Windows network-drive watcher behavior so recovery does not depend on events that reconnection never emits.

## Plan brief

- **Likely files:** `extensions/git/src/model.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/commands.ts`
- **Validation:** On Windows, open a network-hosted workspace containing one root repository and three independent immediate-child repositories with git.autoRepositoryDetection=true and git.repositoryScanMaxDepth=1. Confirm all four appear, interrupt access until repositories disappear, restore access, and verify all four return exactly once without reload or extension-host restart. Capture Git trace logs and watcher behavior; repeat with an intentionally closed child and confirm it remains closed.
- **Behavior:**

  > A temporary loss of access to a network-hosted workspace must not permanently remove eligible nested repositories from Source Control. After access returns, the root and independent child repositories previously discovered at startup should reappear without restarting the window or extension host, and without duplicate entries. Existing discovery depth, ignored-path settings, and intentional repository closures must remain respected. Acceptance requires the described Windows disconnect/reconnect scenario, not merely refreshing status in an already-open repository.
- **Trace:**

  > Model.doInitialScan() in extensions/git/src/model.ts performs child traversal through scanWorkspaceFolders(), but subsequent discovery uses filtered /.git filesystem events and individual openRepository() calls. After the root opens, getOpenRepository() treats paths beneath unknown independent child repositories as belonging to that root, so the constructor's discovery filter suppresses their events. Repository.run() in extensions/git/src/repository.ts disposes repositories on NotAGitRepository, and Model.open() removes them without retaining them as intentional closures. Git refresh and reopen-closed commands in extensions/git/src/commands.ts do not repeat workspace traversal. The source explains the root-first recovery failure; uncertainty begins with which events a restored Windows network drive actually delivers and whether additional watcher recovery is needed. Preserve intentional closures and existing discovery settings; worktree metadata detection in https://github.com/microsoft/vscode/issues/320749 is separate work.

## Evidence

- **Current-source recovery gap:** In extensions/git/src/model.ts:304–307, discovery accepts only filesystem events whose paths contain /.git and for which getRepository(uri) returns nothing. getOpenRepository() at lines 956–1000 matches descendants of an open repository. Consequently, once the workspace root repository reopens, events for the reported independent nested repositories resolve to that root and are filtered out rather than discovering the nested repositories.
- **Initial discovery is not recovery discovery:** Model.doInitialScan() invokes scanWorkspaceFolders(), which traverses child directories using git.repositoryScanMaxDepth and git.scanRepositories. The only scanWorkspaceFolders() call in current model.ts is in initial scanning; the workspace-folder handler opens added roots without repeating child traversal. A root-only reconnect event therefore does not reproduce the startup scan.
- **Repository removal loses automatic recovery candidates:** extensions/git/src/repository.ts:2885–2887 sets RepositoryState.Disposed for NotAGitRepository errors. Model.open() responds by disposing and removing the repository. That disappearance path does not add it to the closed-repository manager; only explicit Model.close() does, so git.reopenClosedRepositories is not a general recovery mechanism.
- **Existing commands and settings:** extensions/git/src/commands.ts:808–810 implements git.refresh by refreshing an existing Repository; git.openRepository opens a selected path, and git.reopenClosedRepositories iterates recorded intentional closures. git.repositoryScanMaxDepth defaults to 1 and git.scanRepositories supplies additional initial scan paths, but neither provides a workspace-wide reconnect rescan.

This report concerns rediscovery of existing independent nested repositories after network reconnection. The related issue is also younger, so it fails the prior-review duplicate bar.
