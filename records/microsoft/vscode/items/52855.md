# Issue #52855 — VS Code was lost on shutdown with pending update

[https://github.com/microsoft/vscode/issues/52855](https://github.com/microsoft/vscode/issues/52855)

## Summary

Keep open: multiple users confirmed unusable Windows installations after shutdown with an update pending. Version-isolated updates have since landed, but a newer report documents the same user-visible failure under that architecture, so the existing steps warrant retesting rather than a completed close.

## Change summary

Preserve a launchable VS Code installation when Windows shuts down or restarts during a pending update.

## Best solution

Establish that interrupted Windows updates always preserve either the previous working installation or a complete replacement. Investigate the versioned-installation failure documented in https://github.com/microsoft/vscode/issues/336131 against this long-standing report before deciding whether its remaining scope is resolved.

## Plan brief

- **Likely files:** `src/vs/platform/update/electron-main/updateService.win32.ts`, `build/win32/code.iss`
- **Validation:** On a disposable Windows VM, stage a background update while VS Code remains open, then restart Windows without selecting Restart to Update. After boot, verify that the normal shortcut and code CLI launch a complete old or new installation, required resources remain present, and any deferred update can complete. Exercise user and system setup and capture setup, application-update, and inno-updater logs.
- **Behavior:**

  > Shutting down or restarting Windows with a downloaded or staged VS Code update must not leave the application missing or unable to launch. Either the update completes safely or the previous version remains usable and the update can be retried. Acceptance includes launching through the existing shortcut and code CLI after reboot without reinstalling or manually moving installation files. User settings, extensions, and workspaces must remain unchanged.
- **Trace:**

  > The historical discussion confirms files stranded in the '_' staging directory and installer deletion of application resources. Current src/vs/platform/update/electron-main/updateService.win32.ts supplies session-ending metadata and retries updating_version during postInitialize; build/win32/code.iss now stages versioned resources and skips its updater invocation during session end. https://github.com/microsoft/vscode/pull/263998 introduced the versioned-resource architecture, and https://github.com/microsoft/vscode/issues/281963 tracks its stable rollout. However, https://github.com/microsoft/vscode/issues/336131 supplies a newer setup log showing the shutdown skip alongside an unusable installation with missing versioned resources. The review did not execute a Windows reproduction or establish which installer, runtime, or cleanup operation removes those resources. Start by reproducing and correlating those operations; preserve ordinary update behavior and do not treat unrelated missing-module reports as proven instances of the same root cause.

## Evidence

- **Confirmed trigger and impact:** The discussion at https://github.com/microsoft/vscode/issues/52855 contains independent Windows 10/11 confirmations, including a September 2025 MEMBER report that Windows Update restarting while VS Code runs reproduces the problem. Several users recovered by moving staged files from the installation's '_' directory; this is installation corruption, not evidence of lost workspace edits.
- **Diagnostic evidence:** The November 18, 2025 MEMBER comment at https://github.com/microsoft/vscode/issues/52855 describes Procmon observing VSCodeSetup-x64-1.106.1.tmp delete resources/app/out/main.js during an update. This substantiates installer involvement without proving the precise interruption or rollback defect.
- **Substantial related implementation, not proof of complete resolution:** https://github.com/microsoft/vscode/pull/263998 merged on November 24, 2025 as 4c5bfb172a2d7fe6efe1d1010219f2141bd7f7ab and closed https://github.com/microsoft/vscode/issues/249239. The stable-rollout item https://github.com/microsoft/vscode/issues/281963 is also closed. These establish progress beyond the December 2025 comment, but do not establish that every shutdown-corruption path is fixed.
- **Current source safeguards:** src/vs/platform/update/electron-main/updateService.win32.ts passes a session-ending flag to the installer and postInitialize retries updates recorded in updating_version. build/win32/code.iss stages versioned updates using new_ executable names and skips inno_updater when SessionEndFileExists is true. These safeguards change the old flow, but source inspection alone does not establish interruption-safe behavior across Windows shutdown and installer cleanup.
- **Remaining reported failure after architectural change:** https://github.com/microsoft/vscode/issues/336131 is open and reports a pending background update to 1.137.0 followed by Windows restart. Its setup log explicitly skips inno_updater because the OS session is ending, yet both executables are unusable and versioned resources are missing; an in-place repair restores launchability. The precise cause remains unconfirmed.
- **Canonical search:** An open-issue search for Windows update shutdown found https://github.com/microsoft/vscode/issues/266382 and https://github.com/microsoft/vscode/issues/336131. Both are newer reports; neither establishes broader ownership than this older, extensively discussed issue. The unrelated sidebar candidate does not cover this work.
