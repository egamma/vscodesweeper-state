# Issue #9498 — Allow to save a list of opened editors in a group and switch between them

[https://github.com/microsoft/vscode/issues/9498](https://github.com/microsoft/vscode/issues/9498)

## Summary

Keep open: current VS Code supports branch-associated editor working sets, but not general, user-named snapshots that can be saved and restored without switching branches. This accepted Backlog request has 183 upvotes and remains necessary; no verified older canonical was found.

## Change summary

Allow users to save named sets of open editors and their group layout, then switch between those sets within the same project.

## Best solution

Provide an on-demand named editor-working-set experience in the workbench, independent of source-control branches, using the existing snapshot infrastructure. Settle the user-facing scope and switching semantics before implementation, preserving existing unsaved-editor protections.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/editor/editorActions.ts`, `src/vs/workbench/browser/parts/editor/editorParts.ts`, `src/vs/workbench/services/editor/common/editorGroupsService.ts`, `src/vs/workbench/services/editor/test/browser/editorGroupsService.test.ts`
- **Validation:** After choosing the product semantics, add targeted editor working-set/action tests that save sets A and B in one workspace and on one unchanged branch, switch between them, and verify editor membership, ordering, and group layout. Manually verify persistence across reload and that cancelling an unsaved-editor confirmation does not discard edits or report a successful switch. No tests were executed during this read-only review.
- **Behavior:**

  > A user can save the open editors as a named set, work with a different set in the same project, and restore the original without switching branches or opening another workspace. Restoring a set recovers its editor membership and split layout without leaving unrelated tabs cluttering the result. Acceptance should cover two independently named sets, switching on an unchanged branch, and restoration after reload. Existing protections for unsaved edits must remain effective.
- **Trace:**

  > EditorParts in src/vs/workbench/browser/parts/editor/editorParts.ts already stores named IEditorWorkingSetState entries containing main and auxiliary editor state and exposes saveWorkingSet, getWorkingSets, deleteWorkingSet, and applyWorkingSet through IEditorGroupsService. SCMWorkingSet in src/vs/workbench/contrib/scm/browser/workingSet.ts exercises capture and restore automatically on history-reference changes; scm.workingSets.enabled covers the branch-specific request documented at https://github.com/microsoft/vscode/issues/35307, not arbitrary named task contexts. The editor command registrations expose layout geometry but no general named-set save/restore surface. The existing 'working sets - create / apply state' test in src/vs/workbench/services/editor/test/browser/editorGroupsService.test.ts is a starting point for validation. Preserve SCM and agent-session behavior and avoid exposing their internally managed snapshots as user-created sets without a deliberate product decision. The remaining uncertainty is user-visible capture scope and whether saved sets are explicit snapshots or automatically updated task contexts; https://github.com/microsoft/vscode/issues/143024 is related UX discussion, not a duplicate destination.
- **Open decisions:**
  - Does a user-created set capture only the active editor group, all groups in the main window, or auxiliary editor windows as well?
  - Are saved sets immutable snapshots until explicitly saved again, or live task contexts automatically updated when switching away?
