# Issue #344037 — Chat: let tools hint how string parameters should be rendered (syntax highlighting for code, SQL, shell, etc.)

[https://github.com/microsoft/vscode/issues/344037](https://github.com/microsoft/vscode/issues/344037)

## Summary

Keep open as a feature request: current source supports a language for the entire input block, but not schema-driven rendering of individual string parameters. The discussion adds concrete use cases and compatibility concerns; no canonical owning this capability was verified.

## Change summary

Allow MCP and extension tools to annotate string parameters so Chat displays decoded, language-highlighted content alongside the remaining arguments.

## Best solution

Provide an optional, backward-compatible parameter-presentation contract shared by tool input details and confirmation surfaces, preserving exact invocation values and existing editing behavior. Settle the supported annotation vocabulary and confirmation interaction before implementation.

- **Validation:** Exercise an MCP tool and an extension-contributed tool with a multiline Python or SQL string plus a numeric argument. Verify decoded, highlighted parameter content and complete argument context in expanded input and confirmation; unknown or absent hints retain existing behavior. Verify confirmation edits reach the invoked tool unchanged, cancellation still works, and restored history remains stable after tool schema changes.
- **Behavior:**

  > Tools can optionally describe the content type of individual string arguments, allowing Chat to show real newlines and appropriate syntax highlighting while retaining the context of other parameters. Missing or unsupported hints preserve existing presentation, and display metadata does not change validation or executed argument values. Acceptance includes expanded input, confirmation, historical rendering, and compatibility with editable arguments.
- **Trace:**

  > The MCP contribution prepares rawInput and later stringifies the full argument object into IToolResultInputOutputDetails.input. That interface has inputLanguage for the whole block, and ChatInputOutputMarkdownProgressPart renders one input code part; neither provides per-property extraction. The tool schema meta-schema already accepts contentMediaType, but acceptance alone does not wire rendering. ChatToolConfirmationSubPart independently serializes rawInput into an editable JSON editor, so the confirmation path has a value-editing contract that must remain intact. The discussion at https://github.com/microsoft/vscode/issues/344037#issuecomment-6443947082 identifies persistence and provider-schema compatibility concerns that remain design considerations, not verified defects. The trace establishes the presentation gap; extension-provider propagation, persisted metadata, and the final interaction contract still need design investigation.
- **Open decisions:**
  - Should the supported public hint contract be contentMediaType alone, or also include an explicit language-ID annotation when MIME mapping is unavailable?
  - In editable confirmations, should decoded parameter blocks themselves be editable, or should editing remain in a separate authoritative JSON representation?
