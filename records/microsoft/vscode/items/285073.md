# Issue #285073 — Feature Request: Support defaultValue in l10n.t() to enable stable keys without side effects

[https://github.com/microsoft/vscode/issues/285073](https://github.com/microsoft/vscode/issues/285073)

## Summary

Keep open in l10n-platform: the current API still cannot separate a stable lookup key from its fallback message. The older default-language request is related, but does not own the full requested capability.

## Change summary

Support stable localization keys with human-readable defaults, independently of changes to the English message.

## Best solution

Have the localization API owners assess an opt-in stable-key contract that preserves existing message-based calls and the fast default-language path. Resolve whether defaults belong inline or in a default-language bundle before committing to an API.

## Evidence

- **Existing API does not cover the request:** src/vscode-dts/vscode.d.ts:18199–18277 exposes l10n.t(message, args) and an options overload containing message, args, and comment, but no independent lookup key or fallback. l10n.bundle is documented as typically undefined in the default language; it does not supply the requested default-language lookup.
- **Current runtime behavior:** src/vs/workbench/api/common/extHost.api.impl.ts:1687–1705 forwards the message to ExtHostLocalizationService.getMessage. In src/vs/workbench/api/common/extHostLocalizationService.ts, getMessage returns format2(message, args) in the default language and uses message, optionally suffixed with comment, for translated lookup. Missing translations fall back to message. initializeLocalizedMessages skips bundle loading entirely in the default language, so adding bundle.l10n.en.json alone does not solve the reporter's alternative.
- **Reporter supplied two different contracts:** https://github.com/microsoft/vscode/issues/285073 initially requests an inline defaultValue/defaultMessage, while the author's December 27 comment prefers key-only calls backed by bundles for every language, including English. Both address stable keys, but have different API and bundle-loading semantics.
- **Older related issue is not a verified duplicate:** https://github.com/microsoft/vscode/issues/168127 is open and older. Its body reports Spanish inline messages being returned when VS Code is English; discussion mentions stable keys, but the maintainer-supported direction is an extension-specific defaultLocale. That direction does not independently separate lookup keys from fallback messages, and the body does not report this item's same observable maintenance problem. It therefore does not satisfy the stronger duplicate bar for this re-reviewed item.
- **Relevant performance precedent:** https://github.com/microsoft/vscode/issues/168127#issuecomment-1338469504 explains the cost of attempting default-language bundle loads, particularly additional web requests. https://github.com/microsoft/vscode/issues/168127#issuecomment-2605948848 identifies localization extraction tooling implications. These are design constraints, not a rejection of this request.
- **Search and disposition:** Read-only searches for l10n, stable translation keys, localization keys, and defaultMessage did not identify an older open canonical that owns the complete request. Current source still lacks the capability, and the supplied Backlog milestone records accepted unscheduled work; age and one upvote do not justify a decline close.
