# Issue #333355 — Allow runSubagent model param to differentiate same-name models across BYOK groups (vendor/group/id)

[https://github.com/microsoft/vscode/issues/333355](https://github.com/microsoft/vscode/issues/333355)

## Summary

Still a real gap on current main: model references are matched by display name + vendor only, so two BYOK groups sharing the `customendpoint` vendor and a model name are indistinguishable and the first cache hit silently wins. Keep open as an aligned BYOK/subagent request; the remaining question is the public reference syntax, so it is plan-tier rather than ready to implement.

## Change summary

Let the runSubagent tool's `model` parameter (and prompt files) target an unambiguous model via vendor/group/id instead of the ambiguous "Name (Vendor)" form.

## Best solution

Extend model reference resolution so an unambiguous identifier (the existing `<vendor>/<group>/<id>` model identifier, or a `Name (vendor/group/id)` qualified form) is accepted alongside `Name (Vendor)`, and have the subagent tool resolve through it; the picker already renders provider/group/model names, so the display vocabulary exists.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/languageModels.ts`, `src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts`
- **Validation:** A languageModels unit test registering two models with identical `name` and vendor `customendpoint` in different groups, asserting that an unambiguous reference resolves to the intended identifier while the legacy `Name (Vendor)` form keeps its current behavior.
- **Behavior:**

  > When two BYOK groups expose a model with the same display name under the same vendor (e.g. GLM 5.3 Flash via a Cline group and via an openrouter group), a subagent invocation must be able to name exactly one of them and get it. Today only `Model Name (Vendor)` is accepted and the first cache match silently wins. Expected: an unambiguous reference form resolves deterministically to the intended model; the existing `Name (Vendor)` and bare-Copilot-name forms keep working unchanged; an unresolvable or still-ambiguous reference should fail or fall back visibly rather than silently picking an arbitrary copy. Acceptance: a test with two same-name models in different groups resolves each one correctly, and existing model-reference tests still pass.
- **Trace:**

  > Root cause is in `ILanguageModelChatMetadata.matchesQualifiedName`/`asQualifiedName` (src/vs/workbench/contrib/chat/common/languageModels.ts:384-393), which only compares `name` + `vendor`, combined with `LanguageModelsService.lookupLanguageModelByQualifiedName` (same file, :1297-1305), which returns the first matching `_modelCache` entry — so group membership is never considered. The consumer is the `model` parameter of the runSubagent tool (src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts:148-151, resolved in `resolveSubagentModel`). The vocabulary for the fix already exists: models carry a `modelGroup`/`group` and a service identifier `<vendor>/<group>/<id>` (languageModels.ts:327, :468), and the picker already builds a `provider/group/model` display label (:807-811). Boundary: do not change the Copilot bare-name shortcut or break the existing `Name (Vendor)` references used by prompt files and saved agent configs; this is a resolution change, not a model-identity or picker redesign. Confirmed by reading current main (3b486b1f); no fix commit found for this path.
- **Open decisions:**
  - What exact reference syntax should the tool and prompt files accept for disambiguation — the raw service identifier `<vendor>/<group>/<id>`, the reporter's `Name (vendor/group/id)` qualified form, or the picker's `provider/group/model` display label?
  - When a reference is still ambiguous (same name, same vendor, multiple groups) should the subagent invocation fail with an error listing the candidates, or keep today's first-match behavior for backward compatibility?
  - Should the disambiguated form also be what the model picker / agent configuration writes out, so copied names round-trip, or remain an accepted-input-only alternative?

## Evidence

- **ambiguity confirmed on main:** src/vs/workbench/contrib/chat/common/languageModels.ts:384-393 — `asQualifiedName()` builds `${metadata.name} (${metadata.vendor})` and `matchesQualifiedName()` compares only that string (plus a bare-name shortcut for the Copilot vendor); group is not part of the comparison.
- **first-match wins:** src/vs/workbench/contrib/chat/common/languageModels.ts:1297-1305 — `lookupLanguageModelByQualifiedName()` iterates `_modelCache` and returns the first entry that matches, so with several groups on the same vendor the winner is cache/iteration order, exactly as reported.
- **tool contract:** src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts:148-151 documents the `model` parameter as 'Format: "Model Name (Vendor)", vendor is usually "copilot"' — no group or identifier escape hatch.
- **identifier vocabulary already exists:** The same file documents the service identifier form `toModelIdentifier(vendor, group, id)` → `<vendor>/<group>/<id>` (languageModels.ts:327, :468), and the picker already composes a `provider/group/model` display label (languageModels.ts:807-811), so the requested disambiguator maps onto existing concepts.
