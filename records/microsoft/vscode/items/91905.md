## Summary

Keep open: two reporters confirmed an unresolved Terminal.processId promise that blocks extension startup. Current source establishes the delivery path, but does not establish that this Windows failure is fixed; the related reconnect report was consolidated into this issue.

## Change summary

## Plan brief

- **Likely files:** `src/vs/platform/terminal/node/terminalProcess.ts`, `src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts`, `src/vs/workbench/contrib/terminal/browser/terminalInstance.ts`, `src/vs/workbench/api/browser/mainThreadTerminalService.ts`, `src/vs/workbench/api/common/extHostTerminalService.ts`, `extensions/vscode-api-tests/src/singlefolder-tests/terminal.test.ts`
- **Validation:** On Windows with PowerShell installed, exercise an extension-host test that creates a terminal with an explicit pwsh.exe path and -NonInteractive/-NoProfile, immediately awaits terminal.processId with a bounded timeout, and asserts a positive PID. Compare with the existing default-shell PID test and repeat startup to expose intermittent delivery failures; separately check reconnected terminals if that related scenario reproduces.
- **Behavior:**

  > Creating a Windows PowerShell terminal through window.createTerminal and awaiting its processId must allow the extension's subsequent startup work to proceed once the shell process exists. The historical report instead stalls before a named-pipe connection, and changing await to .then only avoids blocking that subsequent work. First establish whether the same startup sequence still fails on a current Windows build. Acceptance should include repeated explicit-PowerShell launches with a bounded PID wait and unchanged default-shell behavior.
- **Trace:**

  > ExtHostTerminal constructs a pending PID promise in src/vs/workbench/api/common/extHostTerminalService.ts, and _setProcessId settles it when $acceptTerminalProcessId finds the corresponding terminal. MainThreadTerminalService forwards onAnyInstanceProcessIdReady notifications; TerminalProcessManager obtains the PID from the backend's onProcessReady event, and TerminalInstance exposes readiness to the terminal service. The normal delivery path is present, but source inspection did not identify the failing transition in the reported PowerShell startup sequence. The existing PID API test waits for onDidOpenTerminal and uses the default shell, so it does not exactly cover the original trigger. Preserve the public API and distinguish the indefinite promise stall from the finite ConPTY delay in https://github.com/microsoft/vscode/issues/96158. The closed reconnect report https://github.com/microsoft/vscode-internalbacklog/issues/1540 was consolidated here; do not assume its scenario and newly created PowerShell terminals require the same fix without reproduction.

## Evidence

- **Confirmed historical reproduction:** https://github.com/microsoft/vscode/issues/91905 documents Windows 10 build 19535 with VS Code 1.43.0-insider: awaiting processId after createTerminal with PowerShell and -NonInteractive/-NoProfile prevents the extension from proceeding to its named-pipe connection. The June 17, 2020 comment independently reports that the .then callback also never resolves. These confirm the historical defect, not its persistence on current main.
- **Workaround does not settle the promise:** The reporter reverted the awaited call through https://github.com/PowerShell/vscode-powershell/pull/2498. Using .then allows subsequent startup work to proceed without waiting, but does not prove PID delivery succeeds; the second reporter explicitly observed an unresolved .then callback.
- **Current API delivery path:** src/vs/workbench/api/common/extHostTerminalService.ts:115-122 constructs and exposes the PID promise; _setProcessId at lines 296-309 resolves it. MainThreadTerminalService listens for onAnyInstanceProcessIdReady and forwards defined PIDs through $acceptTerminalProcessId at lines 405-410 of src/vs/workbench/api/browser/mainThreadTerminalService.ts. This establishes the normal path, not the cause of the reported Windows stall.
- **Backend propagation:** src/vs/platform/terminal/node/terminalProcess.ts::_sendProcessId emits onProcessReady. src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts:378-385 stores e.pid in shellProcessId and forwards readiness. No execution was performed, so a missing notification or startup dependency in the reporter's environment remains unconfirmed on current main.
- **Related report consolidates here:** https://github.com/microsoft/vscode-internalbacklog/issues/1540 reports unresolved processId promises for reconnected terminals. Its discussion links this issue and ends with the maintainer's duplicate disposition at https://github.com/microsoft/vscode-internalbacklog/issues/1540#issuecomment-719153387. It is closed and is not an alternative canonical target.
- **Related ConPTY delay is not a demonstrated fix:** https://github.com/microsoft/vscode/issues/96158 concerns a 500 ms shell-task delay with ConPTY; https://github.com/microsoft/vscode/issues/96158#issuecomment-642841441 calls this issue related. That finite task delay does not establish resolution of an indefinitely pending API promise.
- **Existing coverage and search limits:** extensions/vscode-api-tests/src/singlefolder-tests/terminal.test.ts contains 'processId immediately after createTerminal should fetch the pid', but it uses the default shell and waits for onDidOpenTerminal before awaiting the PID. Searches for open terminal processId, PID-promise and process-ID hang reports did not establish a broader canonical. The checkout has shallow, single-commit history, so local history cannot establish a historical fixing commit.
