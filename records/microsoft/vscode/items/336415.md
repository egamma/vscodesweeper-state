# Issue #336415 — Agents Window: Failed to sign in to GitHub. Would you like to try again?

[https://github.com/microsoft/vscode/issues/336415](https://github.com/microsoft/vscode/issues/336415)

## Summary

Keep open: the attached logs establish a transient local extension-host startup failure that is incorrectly presented as a GitHub credential problem. This is a team-authored diagnostic issue with no referenced fix or verified duplicate.

## Change summary

Prevent an Agents Window local extension-host initialization failure from surfacing as a misleading GitHub sign-in retry dialog.

## Best solution

Distinguish authentication-provider unavailability caused by extension-host startup failure from rejected GitHub credentials, then either recover the host/provider registration or present an actionable startup/reload error without implying that the account was signed out.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/electron-browser/localProcessExtensionHost.ts`, `src/vs/workbench/services/authentication/browser/authenticationService.ts`, `src/vs/workbench/contrib/chat/browser/chatSetup/chatSetupController.ts`, `src/vs/sessions/contrib/accountMenu/browser/account.contribution.ts`
- **Validation:** Add a focused authentication/chat-setup test that simulates activation completing without registration of the GitHub provider and verifies the result is not presented as a credential sign-out; the plan should also define a deterministic check for the selected extension-host recovery behavior.
- **Behavior:**

  > When the Agents Window cannot sign in because its local extension host failed to initialize and the built-in GitHub authentication provider never registered, the UI must not imply that the user's credentials were revoked or that the account was signed out. The user should receive an actionable result appropriate to provider or extension-host unavailability, while genuine credential failures retain the existing sign-in flow. A clean launch with a registered provider must continue to authenticate normally.
- **Trace:**

  > The incident reaches the 60-second ready-message rejection in src/vs/workbench/services/extensions/electron-browser/localProcessExtensionHost.ts. The absent GitHub provider then reaches the five-second registration timeout in AuthenticationService._getProvider in src/vs/workbench/services/authentication/browser/authenticationService.ts. The Agents Window command in src/vs/sessions/contrib/accountMenu/browser/account.contribution.ts delegates to the shared chat setup action, whose signIn path in src/vs/workbench/contrib/chat/browser/chatSetup/chatSetupController.ts maps every missing default account to the same GitHub sign-in retry dialog. The uncertainty begins at ownership: whether the extension host should recover or restart, whether authentication should expose a typed provider-unavailable condition, or whether chat setup alone should distinguish this failure. Genuine rejected-credential behavior and successful provider registration must not change.
- **Open decisions:**
  - Should the primary correction recover or restart the failed local extension host, or only classify and present provider unavailability accurately?
  - Which layer should expose the distinction between missing provider registration and rejected user credentials: extension-host lifecycle, authentication service, or chat setup?
  - What retry boundary avoids another provider-registration timeout loop while preserving normal interactive sign-in?
