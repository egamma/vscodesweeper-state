# Issue #213320 — Make Tabs Multiselect Keyboard Accessible

[https://github.com/microsoft/vscode/issues/213320](https://github.com/microsoft/vscode/issues/213320)

## Summary

The accessibility gap remains on current main: editor tabs expose multi-selection state through ARIA, but only pointer handlers can add, remove, or range-select tabs. This team-authored Backlog request is the canonical tracker and should remain open.

## Change summary

Allow keyboard users to select and unselect multiple editor tabs with behavior equivalent to pointer-based Ctrl/Cmd-click and Shift-click selection.

## Best solution

Give the editor tablist a documented keyboard multi-selection model consistent with VS Code list/tree conventions, including toggle and contiguous-range selection, while preserving existing unmodified tab navigation and activation behavior.

- **Fit:** aligned
- **Reason:** Keyboard-operable tab multi-selection directly advances VS Code's durable accessibility commitment and removes a mouse-only interaction from a core workbench surface.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts`, `src/vs/workbench/test/browser/parts/editor/multiEditorTabsControl.test.ts`
- **Validation:** Add focused MultiEditorTabsControl unit tests that dispatch the chosen modifier-plus-key gestures and assert EditorGroupModel.selectedEditors and each tab's aria-selected state; run scripts/test.sh --grep "MultiEditorTabsControl".
- **Behavior:**

  > Keyboard users can add or remove individual editor tabs from the current selection and extend a contiguous selection without using a pointer. The selected tabs expose accurate aria-selected state, and actions such as Close operate on the resulting selection as they do after mouse selection. Existing unmodified arrow, Home/End, Enter, Space, and Shift+F10 behavior remains available. Acceptance includes keyboard-driven toggle and range-selection tests plus unchanged single-tab navigation.
- **Trace:**

  > MultiEditorTabsControl.registerTabListeners in src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts contains separate pointer and keyboard paths. The pointer path invokes selectEditor, unselectEditor, and selectEditorsBetween for Ctrl/Cmd-click and Shift-click, while the keyboard path only activates tabs and moves among them. The DOM already declares a multiselectable tablist and redraws aria-selected from EditorGroupModel selection state. The existing unit-test fixture is src/vs/workbench/test/browser/parts/editor/multiEditorTabsControl.test.ts; it creates a real EditorGroupModel and rendered tab DOM suitable for checking selection and ARIA state. Preserve pointer behavior, context-menu handling, editor action semantics, and ordinary keyboard navigation. The newer https://github.com/microsoft/vscode/issues/213611 is a closed duplicate of this canonical issue.
- **Open decisions:**
  - Which established multi-select keyboard contract should editor tabs expose: Ctrl/Cmd+Space for toggling and Shift+Arrow/Home/End for ranges, or another VS Code list/tree convention?
  - When extending a range by keyboard, should focus and the active editor move to the range endpoint, or should the active editor remain unchanged while only selection changes?

## Evidence

- **current source:** src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts:1070-1102 implements range and toggle selection only in the mouse/touch handler through Shift and Ctrl/Cmd modifiers.
- **keyboard gap:** src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts:1184-1215 handles Enter/Space activation and unmodified arrow/Home/End navigation, but contains no keyboard path to selectEditorsBetween, selectEditor, or unselectEditor.
- **ARIA state:** src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts:264-268 and 1873-1879 already expose aria-multiselectable on the tablist and aria-selected on each tab, so announcing selection is implemented but operating it by keyboard is not.

- **maintainer intent:** The author is a repository member and stated that tabs should apply the established list/tree ARIA selection knowledge; the Backlog milestone records this as accepted but unscheduled work.
