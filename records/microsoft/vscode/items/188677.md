# Issue #188677 — Inconsistent column number due to unicode symbols between command palette and status bar (+ inconsistent with Chrome and Firefox Devtools)

[https://github.com/microsoft/vscode/issues/188677](https://github.com/microsoft/vscode/issues/188677)

## Summary

A real semantic gap remains on current main: the status bar counts Unicode code points, while Go to Line/Column uses rendered grapheme width. The issue should remain open for a product decision on whether VS Code should expose visual columns, source/UTF-16 positions, or both.

## Change summary

Make editor column reporting internally consistent and provide positions that can be correlated with JavaScript stack traces when Unicode symbols precede the cursor.

## Best solution

Define and document distinct visual-column and source-position semantics, then make the status bar and Go to Line/Column clearly expose or consistently use them. Preserve visual navigation behavior while providing an unambiguous position compatible with JavaScript tooling.

## Plan brief

- **Likely files:** `src/vs/editor/common/core/cursorColumns.ts`, `src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts`, `src/vs/editor/contrib/quickAccess/browser/gotoLineQuickAccess.ts`, `src/vs/workbench/browser/parts/editor/editorStatus.ts`, `src/vs/editor/test/common/core/cursorColumns.test.ts`, `src/vs/editor/contrib/quickAccess/test/browser/gotoLineQuickAccess.test.ts`
- **Validation:** Extend the CursorColumns and AbstractGotoLineQuickAccessProvider unit suites with regional-indicator pairs, lone regional indicators, surrogate-pair emoji, tabs, and zero-width characters, asserting the chosen status display and round-trip Go to Line/Column semantics.
- **Behavior:**

  > For text containing tabs and Unicode grapheme clusters, every displayed position must identify whether it is a visual column or a source character offset. A position copied from the source-position surface must correlate with JavaScript stack traces, while entering the corresponding value in Go to Line/Column must land at the intended cursor boundary. Existing ASCII behavior and tab-aware visual navigation must remain stable.
- **Trace:**

  > The status item is populated in src/vs/workbench/browser/parts/editor/editorStatus.ts through CodeEditorWidget.getStatusbarColumn() in src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts. That method calls CursorColumns.toStatusbarColumn(), which counts code points and expands tabs. Go to Line/Column instead calls CursorColumns.visibleColumnFromColumn() and columnFromVisibleColumn() in src/vs/editor/contrib/quickAccess/browser/gotoLineQuickAccess.ts; those routines iterate grapheme clusters and approximate rendered width. Commit https://github.com/microsoft/vscode/commit/23897ce20c0f7647b4c2d8daa0d1ee8326db9d82 deliberately adopted visible-column semantics for Go to Line, so the uncertainty begins at the product contract rather than the implementation trace. The boundary is editor position presentation and navigation; model offsets, extension API Position semantics, cursor grapheme-boundary behavior, and non-Unicode ASCII behavior must not change inadvertently.
- **Open decisions:**
  - Should the primary status-bar column represent rendered width, Unicode code-point count, or the UTF-16 source position used by JavaScript tooling?
  - Should VS Code expose both visual column and source character position rather than replacing the established status-bar convention?
  - Should Go to Line/Column accept source positions, visual columns, or an explicit syntax or mode for each?

## Evidence

- **current status-bar path:** src/vs/workbench/browser/parts/editor/editorStatus.ts calls IEditor.getStatusbarColumn(); src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts delegates that to CursorColumns.toStatusbarColumn(), which uses CodePointIterator in src/vs/editor/common/core/cursorColumns.ts.
- **current Go to Line path:** src/vs/editor/contrib/quickAccess/browser/gotoLineQuickAccess.ts explicitly treats entered and displayed columns as visible columns through CursorColumns.visibleColumnFromColumn() and columnFromVisibleColumn(), which use GraphemeIterator and rendered-width approximations.
- **intentional recent divergence:** Commit https://github.com/microsoft/vscode/commit/23897ce20c0f7647b4c2d8daa0d1ee8326db9d82 intentionally changed Go to Line/Column to visible-column semantics for tabs, without changing the status-bar code-point semantics.
- **related design discussion:** https://github.com/microsoft/vscode/issues/167863 requests a character-position alternative for stack-trace correlation, while https://github.com/microsoft/vscode/issues/259270 documents additional Unicode widths affected by the same ambiguity; neither fully supersedes this older report.
- **maintainer precedent:** https://github.com/microsoft/vscode/issues/149933 records the established status-bar rule: tabs use rendered width, while every other Unicode code point counts as one. Changing or augmenting that convention therefore requires a deliberate product decision.
