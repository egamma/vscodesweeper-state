# Issue #188677 — Inconsistent column number due to unicode symbols between command palette and status bar (+ inconsistent with Chrome and Firefox Devtools)

[https://github.com/microsoft/vscode/issues/188677](https://github.com/microsoft/vscode/issues/188677)

## Summary

The column mismatch remains in current source: the status bar counts Unicode code points, while Go to Line/Column uses grapheme-based visual columns. Keep this with editor-core for a decision on consistent navigation semantics; the related reports do not qualify as duplicate canonicals.

## Change summary

Make Unicode column numbers consistent between the status bar and Go to Line/Column, and clarify their relationship to JavaScript stack-trace coordinates.

## Best solution

Define a consistent displayed-column and navigation contract in editor-core, so entering the status bar's column returns to the same cursor position. Explicitly settle how JavaScript UTF-16 coordinates coexist with visual columns and existing tab behavior before changing the established counting rules.

- **Validation:** Add a regression in AbstractGotoLineQuickAccessProvider tests that obtains the status-bar column at a valid position after 🇩, enters that line-column pair, and asserts navigation restores the same model position. Cover 🇩🇪, an ordinary supplementary character, CJK text, and tabs against the chosen contract; run the targeted gotoLineQuickAccess and CursorColumns suites. Manually verify the supplied JavaScript examples through the status-bar entry point.
- **Behavior:**

  > A column displayed for a cursor position must be usable in Go to Line/Column to return to that position, including positions following Unicode regional indicators. Current source violates this for the single-indicator example. The finished behavior must make the relationship between displayed columns and JavaScript stack-trace coordinates explicit. Acceptance includes Unicode round-trip checks and preservation of the agreed tab-navigation behavior.
- **Trace:**

  > EditorStatus obtains columns through CodeEditorWidget.getStatusbarColumn, which calls CursorColumns.toStatusbarColumn and counts code points with expanded tabs. AbstractGotoLineQuickAccessProvider.parsePosition instead converts user input through grapheme-based visual-column helpers, which assign regional indicators width two. At the position immediately after 🇩 in the supplied second line, these paths produce status column 25 and visual column 26; entering 25 resolves to the preceding boundary. Existing CursorColumns tests explicitly encode the differing semantics, so consistency is not merely an untested arithmetic correction. Do not change model/API coordinates, grapheme cursor boundaries, or general rendering-width calculations incidentally. Related reports https://github.com/microsoft/vscode/issues/254382 and https://github.com/microsoft/vscode/issues/259270 provide additional examples, but are newer and do not replace this issue. The remaining uncertainty is the public column contract, not the location of a helper or the structure of a test.
- **Open decisions:**
  - Should displayed and entered line-column coordinates use UTF-16 code units for JavaScript stack-trace compatibility, code points with expanded tabs, or visual columns, and how should users distinguish any retained alternative coordinate system?
