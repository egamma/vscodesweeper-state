# Issue #167514 — Implicit activation events - call out implicit activation in the logs

[https://github.com/microsoft/vscode/issues/167514](https://github.com/microsoft/vscode/issues/167514)

## Summary

The requested diagnostic distinction remains absent on current main: explicit and generated activation events are flattened before the Extension Host logs the activation reason. This team-authored Backlog request should remain open while maintainers decide how implicit-event provenance should be represented.

## Change summary

Identify implicitly generated extension activation events as implicit in the Extension Host output log.

## Best solution

Preserve or reliably derive activation-event provenance across the renderer-to-extension-host handoff, then annotate the activation log without changing extension activation behavior or telemetry semantics.

## Plan brief

- **Likely files:** `src/vs/platform/extensionManagement/common/implicitActivationEvents.ts`, `src/vs/workbench/services/extensions/common/extensions.ts`, `src/vs/workbench/services/extensions/common/extensionHostProtocol.ts`, `src/vs/workbench/api/common/extHostExtensionService.ts`, `src/vs/workbench/api/test/common/extHostExtensionActivator.test.ts`
- **Validation:** Add and run a targeted extension-host unit test proving that generated activation events are logged as implicit while explicitly declared events retain the existing log format.
- **Behavior:**

  > When an extension is activated because of an event generated from its contributions, the Extension Host log identifies that activation event as implicit. Explicitly declared activation events continue to use the existing presentation. Extension selection, activation ordering, telemetry, and activation timing must remain unchanged.
- **Trace:**

  > ImplicitActivationEventsImpl in src/vs/platform/extensionManagement/common/implicitActivationEvents.ts starts with manifest activation events and appends generated events into the same string array. ExtensionHostExtensions in src/vs/workbench/services/extensions/common/extensions.ts and AbstractExtensionService in src/vs/workbench/services/extensions/common/abstractExtensionService.ts transport only this combined map. SyncedActivationEventsReader in src/vs/workbench/api/common/extHostExtensionService.ts therefore exposes values without provenance, and `_doActivateExtension` logs only the resulting `reason.activationEvent`. The uncertainty begins at whether provenance should cross the extension-host protocol or be derived from the original manifest in the extension host. The boundary is diagnostic formatting and metadata only; activation matching and execution must not change.
- **Open decisions:**
  - Should implicit provenance be transported alongside activation events, or derived in the extension host by comparing the selected event with the manifest's explicit activation events?
  - If the same event is both explicitly declared and generated from a contribution, should the log classify it as explicit, implicit, or both?
  - How should normalized explicit events such as `onUri` be classified after their identifier-specific transformation?
