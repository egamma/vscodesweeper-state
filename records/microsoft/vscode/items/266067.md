# Issue #266067 — Chat: Invalid/failed tool calls are never shown to the user

[https://github.com/microsoft/vscode/issues/266067](https://github.com/microsoft/vscode/issues/266067)

## Summary

Keep open for design and coverage verification. Current main visibly renders tool failures that reach the workbench as `toolResultError`, but the original invalid-schema and failed-edit paths have not been shown to consistently produce that state, and no fixing commit or PR explicitly references this team-authored issue.

## Change summary

Show invalid and failed tool calls consistently in chat so users can see the agent encounter and recover from tool errors.

## Best solution

Ensure every failed or rejected tool-call path, including failures before normal execution, produces a visible invocation with an attributable error while keeping self-recovery concise. Settle the compact presentation and agent-facing error guidance with chat UX maintainers, then cover the original MCP-schema and edit-tool examples with regression tests.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatToolInvocationPart.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatToolProgressPart.ts`, `src/vs/workbench/contrib/chat/common/model/chatProgressTypes/chatToolInvocation.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/chatListRenderer.test.ts`, `extensions/copilot/src/extension/intents/node/toolCallingLoop.ts`
- **Validation:** Reproduce an MCP call rejected for invalid schema and a failed edit-file call, then add targeted chat-renderer or tool-loop tests asserting each creates one visible failed tool row with an error indication while the agent can continue to a corrected call.
- **Behavior:**

  > When the model emits an invalid tool call or a tool fails, chat visibly records that attempt instead of leaving a gap in the transcript. The row communicates failure without presenting the operation as successful, and subsequent corrected attempts remain easy to follow. Acceptance should cover the reported invalid-schema MCP call and failed edit-file call, including agent self-recovery without a redundant apology.
- **Trace:**

  > Current main already handles failures represented as `toolResultError`: ChatToolInvocation stores the error, ChatToolInvocationPart applies failure styling and an error icon, and ChatToolProgressSubPart can display the error text. ChatListRenderer tests confirm that ordinary failed internal and MCP invocations remain visible, so the uncertainty begins earlier in the pipeline: whether invalid-schema and failed-edit paths create an invocation and propagate an error at all. The Copilot tool loop in extensions/copilot/src/extension/intents/node/toolCallingLoop.ts collects model tool calls and separately filters invalid tool messages, making it a likely boundary to trace for pre-execution failures. Preserve successful tool rendering, confirmation behavior, and transcript restoration; do not turn every transient retry into a large notification. Related work includes https://github.com/microsoft/vscode/pull/298322 and https://github.com/microsoft/vscode/pull/330684.
- **Open decisions:**
  - Should a failed call remain a compact error-marked tool row by default, or automatically reveal its failure reason in the transcript?
  - For self-correctable invalid calls, should the user-facing row show the raw validation error or a concise normalized message while retaining details on expansion?
  - Should the error result sent back to the model explicitly discourage apologies and request an immediate corrected call?
