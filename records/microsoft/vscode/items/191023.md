# Issue #191023 — clean up `ISearchComplete` result field

[https://github.com/microsoft/vscode/issues/191023](https://github.com/microsoft/vscode/issues/191023)

## Summary

The cleanup remains unresolved, but current callers genuinely consume the completion results, so removing the field outright would break behavior. Keep this team-authored backlog item open pending a consumer audit and a decision on whether text-search completion should become metadata-only.

## Change summary

Review whether text search can stop returning accumulated matches through ISearchComplete.results when matches are already streamed through onProgress.

## Best solution

Establish whether text search should have a metadata-only completion contract, accounting for callers that currently consume returned matches. Preserve file-search results and synchronous open-editor results; avoid removing the shared field without providing for those uses.

## Plan brief

- **Likely files:** `src/vs/workbench/services/search/common/search.ts`, `src/vs/workbench/services/search/common/searchService.ts`, `src/vs/workbench/services/search/browser/searchService.ts`, `src/vs/workbench/contrib/search/browser/searchTreeModel/searchModel.ts`, `src/vs/workbench/contrib/chat/browser/tools/usagesTool.ts`, `src/vs/workbench/api/browser/mainThreadWorkspace.ts`
- **Validation:** The plan should end with targeted search-service and search-model tests covering streamed matches, dirty/untitled open-editor matches, completion metadata, and unchanged file-search results, plus a usages-tool check that reference previews remain populated. If a metadata-only text completion contract is chosen, verify its declared return type no longer requires accumulated matches.
- **Behavior:**

  > The proposed cleanup should eliminate redundant accumulated text-search results only where doing so preserves all existing search behavior. Streaming searches must continue delivering matches and completion metadata, synchronous open-editor results must remain available, and file search must still return file matches. Reference previews produced by the usages tool must not disappear. The current issue makes removal conditional on whether any consumers need the field, and current source contains such consumers.
- **Trace:**

  > ISearchComplete in src/vs/workbench/services/search/common/search.ts extends the existing metadata-only ISearchCompleteStats with required results. SearchService.textSearch and doSearch in common/searchService.ts aggregate completion arrays, while SearchModel.doSearch in contrib/search/browser/searchTreeModel/searchModel.ts consumes synchronous results and combines asynchronous text/notebook arrays. The usages tool in contrib/chat/browser/tools/usagesTool.ts calls textSearch without onProgress and reads returned matches for reference previews; MainThreadWorkspace.$startTextSearch instead streams matches and reads only completion metadata. The browser search provider also uses this shared completion shape for both text and file search. These establish that blanket removal is unsafe, but do not yet enumerate every provider and consumer needed for a complete contract migration. https://github.com/microsoft/vscode/pull/191002 identifies this cleanup as follow-up work; https://github.com/microsoft/vscode/issues/210692 discusses a separate public API direction and is not a duplicate canonical.
- **Open decisions:**
  - Should textSearch become a streaming-only match contract with metadata-only completion, requiring completion consumers to migrate, or should callers retain the ability to obtain accumulated matches from the returned promise?
