# Issue #259562 — Run in terminal: Leverage child process monitoring as hint for whether commands are done

[https://github.com/microsoft/vscode/issues/259562](https://github.com/microsoft/vscode/issues/259562)

## Summary

Keep open: current command-completion heuristics still do not use child-process monitoring, and the previously accepted implementation attempt was closed without merging. The existing chat-terminal routing is appropriate; no verified canonical owns this specific remaining capability.

## Change summary

Use terminal child-process activity as an additional, timeout-bounded completion hint when shell integration is unavailable.

## Best solution

Make no-shell-integration execution account for child-process activity alongside output-idle and prompt heuristics, without treating child presence as definitive proof that the submitted command is still running. Preserve a bounded fallback for pre-existing, persistent, or stale child-process state.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/noneExecuteStrategy.ts`, `src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/executeStrategy.ts`, `src/vs/workbench/contrib/terminalContrib/chatAgentTools/test/browser/noneExecuteStrategy.test.ts`, `src/vs/workbench/contrib/terminalContrib/chatAgentTools/test/browser/executeStrategy.test.ts`
- **Validation:** Add fake-timer tests in the NoneExecuteStrategy/executeStrategy suites covering output becoming idle while a newly launched child remains active, child exit followed by completion, no-child execution, pre-existing children, delayed monitoring updates, and expiration of the agreed fallback bound. Manually check a quiet long-running command with shell integration disabled; it must not be reported complete at the original idle threshold while detected child activity remains within that bound.
- **Behavior:**

  > When shell integration is unavailable, terminal output becoming idle should not alone cause premature completion while child-process activity indicates that work may still be running. Child activity is a hint rather than definitive command ownership, and waiting must remain bounded. Acceptance covers newly launched children, eventual child exit, commands without children, and terminals already containing persistent children. Existing prompt handling and alternate-buffer behavior must remain intact.
- **Trace:**

  > NoneExecuteStrategy.execute in src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/noneExecuteStrategy.ts waits through waitForIdleWithPromptHeuristics in executeStrategy.ts, which considers output idle and cursor-line prompt patterns but never child-process state. ITerminalInstance already exposes hasChildProcesses and onDidChangeHasChildProcesses; the underlying ChildProcessMonitor is input/output-triggered and sampled, so its initial value or a delayed update cannot be treated as command-specific truth. The existing fake-timer NoneExecuteStrategy tests provide a validation starting point. https://github.com/microsoft/vscode/pull/259563 contains an unmerged prior approach that the author considered reasonable; https://github.com/microsoft/vscode/issues/259562#issuecomment-3150791007 explicitly requests a timeout and raises checking the initial child state. Keep this scoped to the no-shell-integration completion path, preserving rich/basic execution, process-monitoring behavior used by confirmOnKill, and alternate-buffer handling. The remaining product uncertainty is how much child activity should extend waiting when children predate the command or never disappear.
- **Open decisions:**
  - What maximum wait should child-process activity permit, and should terminals already containing children use a different bound from initially idle terminals?
  - When children were already present before execution, should unchanged child presence extend waiting, or should extension require evidence of new activity?
