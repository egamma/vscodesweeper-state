# Issue #311318 — Agent ignored explicit single-terminal instruction and executed repeated multi-terminal Git command bursts

[https://github.com/microsoft/vscode/issues/311318](https://github.com/microsoft/vscode/issues/311318)

## Summary

A real gap remains: current terminal tooling strongly recommends synchronous execution and reuses a foreground terminal, but it has no hard session policy derived from a user's request to prohibit parallel terminal work. Route this to the Chat and Terminal owners for a product decision on serialization semantics.

## Change summary

Add a hard guard that prevents overlapping or duplicate agent terminal commands when the user explicitly requests sequential execution.

## Best solution

Define a session-scoped serialized-execution contract that permits at most one active terminal command, preserves the existing terminal lane, and prevents a timeout from triggering a duplicate execution while the original command is still running.

A command that times out or continues in the background is not automatically executed again while its original process remains active. Existing behavior for sessions that do not request serialization remains unchanged.
- **Trace:**

  > The terminal tool schema and RunInTerminalTool._resolveExecutionOptions in src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/tools/runInTerminalTool.ts currently model only sync versus async execution. RunInTerminalTool._initTerminal reuses a cached foreground terminal but intentionally creates separate background terminals for parallel execution, and active executions are tracked by generated terminal IDs rather than by a session-wide exclusion policy. The current model description strongly steers one-shot commands toward sync mode and warns against polling, but it cannot enforce the user's natural-language constraint. The issue lacks a transcript or Agent Host logs, so the plan should first reproduce the fan-out and determine whether it originated from concurrent tool calls, timeout continuation, or model retries. Preserve normal parallel/background behavior for sessions where serialization was not requested and keep the PowerShell PSReadLine rendering exception outside this change unless reproduction shows the same root cause.
- **Open decisions:**
  - Should serialized execution be inferred from natural-language instructions for one request, retained for the full chat session, or exposed as an explicit user-controlled mode?

  - Should serialized mode prohibit intentionally long-running async commands, or only prevent overlap and retries among one-shot commands?
