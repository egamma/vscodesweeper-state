# Issue #336864 — Copilot CLI plugin discovery watches unrelated runtime database writes and republishes unchanged plugins

[https://github.com/microsoft/vscode/issues/336864](https://github.com/microsoft/vscode/issues/336864)

## Summary

Team-authored, freshly filed bug with precise source citations that I independently verified against current main: the Copilot CLI plugin watcher, prompt-file change events, and the customizations debug log all lack change-detection guards, so unrelated writes under ~/.copilot can trigger cascading rediscovery and duplicate logging/CPU work. No fix exists yet, so this stays open.

## Change summary

Copilot CLI plugin discovery's non-recursive parent-directory watcher, plus downstream prompt-change and debug-log listeners, react to unrelated writes under ~/.copilot (e.g. runtime database files) and unconditionally republish/re-log even when the plugin inventory is unchanged.

## Best solution

Add equality/dedup guards at the three traced points — CopilotCliAgentPluginDiscovery's watcher callback (filter to plugin-relevant paths or debounce/compare before scheduling), AbstractAgentPluginDiscovery._refreshPlugins/_plugins.set (skip publishing when the built array is equivalent to the previous one), and PromptsService.watchPluginPromptFilesForType plus CustomizationsDebugLogContribution (compare against the last snapshot before firing/logging) — following the same unchanged-state pattern already applied for MCP servers.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/plugins/agentPluginServiceImpl.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts`, `src/vs/sessions/contrib/chat/browser/customizationsDebugLog.contribution.ts`
- **Validation:** A test asserting that scheduling a refresh with an unchanged plugin inventory does not fire onDidChangeCustomAgents/onDidChangeSlashCommands and does not produce a new debug-log snapshot; e.g. exercising CopilotCliAgentPluginDiscovery/_refreshPlugins with a synthetic unrelated file event and asserting the observable's set() call (or downstream event) is skipped when the built array is structurally equal to the prior one.
- **Behavior:**

  > When an unrelated file changes under ~/.copilot (or any watched ancestor of installed-plugins) and the resulting plugin inventory is unchanged, VS Code must not republish a new plugins array, must not fire prompt/custom-agent change events, and must not emit a duplicate customizations debug-log snapshot. Genuine plugin install/uninstall/manifest changes must still be detected and published as before.
- **Trace:**

  > Three chained, unconditional publish points were traced and confirmed on current main: (1) CopilotCliAgentPluginDiscovery's non-recursive watcher on the installed-plugins parent (e.g. ~/.copilot) schedules a refresh on any change event with no path filtering (agentPluginServiceImpl.ts, start()); (2) AbstractAgentPluginDiscovery._refreshPlugins() always calls _plugins.set() with a freshly built array even when equivalent to the previous inventory; (3) PromptsService.watchPluginPromptFilesForType() and CustomizationsDebugLogContribution both fire/log unconditionally downstream. The same unchanged-state class of bug was previously fixed for MCP servers (referenced by the reporter as #330637/#330638, not present in this checkout's history, so unverified as landed). The boundary: fixes must add change-detection/dedup, not restructure the discovery or watcher architecture, and must not suppress genuine plugin add/remove/modify events.
- **Open decisions:**
  - Should the watcher filter events by path (only react to changes under the marketplace/plugin subdirectories) or should the fix rely purely on value-equality gating downstream?
  - Should _refreshPlugins compare the built array against the previous one before calling _plugins.set(), and what equality semantics apply (reference vs. structural per-plugin comparison)?
  - Should CustomizationsDebugLogContribution dedupe by comparing the last logged snapshot content, or should the fix further upstream (PromptsService) make this unnecessary?

## Evidence
