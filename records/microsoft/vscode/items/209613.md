# Issue #209613 — Nested multi-workspaces

[https://github.com/microsoft/vscode/issues/209613](https://github.com/microsoft/vscode/issues/209613)

## Summary

Keep this accepted, well-supported request open: current workspace and Explorer code still models workspace folders as separate top-level roots. Older requests cover hierarchical presentation and nested settings, but none verified here owns the full combination of embedded projects, optional discovery, and operation without a root workspace file.

## Change summary

Support nested subprojects as independently configured workspace folders within their natural Explorer hierarchy, with optional discovery and task control without requiring a root workspace file.

## Best solution

Design embedded workspace-folder support across workspace configuration, Explorer presentation, and task discovery while preserving existing explicit multi-root workspaces. Coordinate the overlapping requests without dropping this report's automatic-discovery and workspace-file-free requirements.

- **Likely files:** `src/vs/platform/workspaces/common/workspaces.ts`, `src/vs/workbench/services/configuration/browser/configurationService.ts`, `src/vs/workbench/contrib/files/common/explorerModel.ts`, `src/vs/workbench/contrib/files/browser/views/explorerView.ts`

Verify each project appears once in its physical hierarchy, receives its intended configuration and task availability, and follows the chosen discovery and reload-persistence rules; verify existing explicit .code-workspace projects remain unchanged.
- **Behavior:**

  > Opening a monorepo should allow nested projects to retain independently scoped workspace behavior without duplicating them as additional top-level Explorer roots. Root files and the actual directory hierarchy remain visible. The request also seeks optional discovery from nested .vscode directories and control over subproject tasks without requiring a root workspace file. Acceptance must cover two independently configured subprojects, their task availability, reopening the folder, and compatibility with existing explicit multi-root workspaces.
- **Trace:**

  > IStoredWorkspaceFolder and toWorkspaceFolders in src/vs/platform/workspaces/common/workspaces.ts represent explicit path/uri entries as a flat array. ExplorerModel in src/vs/workbench/contrib/files/common/explorerModel.ts constructs one parentless root per workspace folder, and ExplorerView in src/vs/workbench/contrib/files/browser/views/explorerView.ts supplies that roots array to the multi-folder tree. Workspace configuration initialization in src/vs/workbench/services/configuration/browser/configurationService.ts obtains stored folders through toWorkspaceFolders; discovery, activation, and persistence semantics beyond this explicit model remain unsettled. Preserve existing explicit workspace configuration and unrelated file-nesting behavior. https://github.com/microsoft/vscode/issues/45470 covers the duplicate-root presentation, https://github.com/microsoft/vscode/issues/76904 covers arbitrary hierarchical grouping, and https://github.com/microsoft/vscode/issues/32693 covers nested settings; none verified here absorbs the complete request. Task discovery and activation consumers still need tracing during planning.
- **Open decisions:**
  - Should nested .vscode directories automatically become independently scoped workspace folders, or should discovery require explicit opt-in and project selection?
  - Without a root .code-workspace file, where should selected subprojects and their enabled state persist, and what should reopening the monorepo restore?
  - Does disabling a subproject affect only its tasks, or also its workspace-folder membership and configuration scope?
