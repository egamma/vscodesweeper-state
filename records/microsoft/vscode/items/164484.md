# Issue #164484 — Investigate removing cursor hit testing

[https://github.com/microsoft/vscode/issues/164484](https://github.com/microsoft/vscode/issues/164484)

## Summary

The investigation remains necessary: current main still passes cursor render geometry into mouse targeting and hard-codes its hit-test width to 2. This is also a team-authored exploratory debt item, so it must remain open without an explicit fixing reference.

## Change summary

Investigate whether the editor's cursor-specific mouse hit-testing workaround can be removed, including its stale render-data dependency and hard-coded width.

## Best solution

Determine whether current supported browsers still misidentify clicks at the painted cursor; if the workaround is obsolete, remove the cursor render-data coupling while preserving correct click targeting and drag-scrolling behavior. If it remains necessary, make its geometry accurately represent every cursor style and width.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/mouseTarget.ts`, `src/vs/editor/browser/view.ts`, `src/vs/editor/browser/viewParts/viewCursors/viewCursor.ts`, `src/vs/editor/browser/viewParts/viewCursors/viewCursors.ts`
- **Validation:** Exercise clicking directly on line, thin-line, block, and underline cursors with default and custom `editor.cursorWidth` values in supported desktop and web browser targets; verify the click resolves to the painted cursor position and that drag scrolling still computes the correct target.
- **Behavior:**

  > Clicking directly on any painted editor cursor must resolve to the cursor's actual text position without intermittent selection movement or failure to deselect. This must remain correct for line, thin-line, block, and underline cursor styles, including custom cursor widths and zoom or display scaling. Pointer targeting away from the cursor and drag scrolling must remain unchanged.
- **Trace:**

  > ViewCursor.render in src/vs/editor/browser/viewParts/viewCursors/viewCursor.ts exports cursor geometry for hit testing but always reports width 2 instead of the rendered `_renderData.width`. ViewCursors.getLastRenderData in src/vs/editor/browser/viewParts/viewCursors/viewCursors.ts retains that data, and src/vs/editor/browser/view.ts places it in PointerHandlerLastRenderData. MouseTarget._hitTestViewCursor in src/vs/editor/browser/controller/mouseTarget.ts first recognizes the cursor DOM node and then applies a geometric fallback documented as an Edge workaround; the same last-render-data bundle also reaches drag scrolling. Commit 23a3c6ec3e5cdc2f7880cb0cf477380ee38ef88e from https://github.com/microsoft/vscode/pull/159325 changed cursor positioning and padding but left this path intact. The uncertainty begins at whether supported browser engines still need the geometric fallback; preserve ordinary DOM hit testing, non-cursor mouse targeting, and drag-scrolling semantics while investigating.

## Evidence

- **current source:** src/vs/editor/browser/viewParts/viewCursors/viewCursor.ts still returns IViewCursorRenderData with `width: 2`, even though the rendered width is held in `_renderData.width` and can vary with cursor style and `editor.cursorWidth`.
- **hit-test dependency:** MouseTarget._hitTestViewCursor in src/vs/editor/browser/controller/mouseTarget.ts consumes the last cursor render data and geometrically treats points between `contentLeft` and `contentLeft + width` as cursor hits; its comment identifies this as an Edge DOM hit-testing workaround.
- **data flow:** src/vs/editor/browser/view.ts packages ViewCursors.getLastRenderData() into PointerHandlerLastRenderData, which is passed to mouse targeting from both normal pointer handling and drag scrolling.
- **referenced PR:** https://github.com/microsoft/vscode/pull/159325 merged cursor padding and positioning changes in commit 23a3c6ec3e5cdc2f7880cb0cf477380ee38ef88e, but it fixed https://github.com/microsoft/vscode/issues/156788 and did not remove the hit-test path or reference this issue as fixed.
