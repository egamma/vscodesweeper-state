# Issue #333505 — "Debug adapter process has terminated unexpectedly" after long-running debug sessions, while the adapter process is still alive

[https://github.com/microsoft/vscode/issues/333505](https://github.com/microsoft/vscode/issues/333505)

## Summary

Plausible and technically detailed report, but it depends on an unshared private debug adapter and ~1 hour of sustained output to trigger sporadically, so I can't confirm the exact defect from source alone — needs more diagnostic info before it can be routed with confidence.

## Change summary

After long, high-output debug sessions, VS Code declares the debug adapter process terminated and tears down the session, even though the adapter's OS process is still alive, leaking orphaned adapter processes.

## Best solution

Worth having a maintainer look at src/vs/workbench/contrib/debug/node/debugAdapter.ts, where ExecutableDebugAdapter treats the child process's stdout `close` event as proof the adapter died (`this.serverProcess.stdout!.on('close', () => this._onError.fire(new Error('read error')))`) without corroborating against the process's own `exit` event; if `close` can fire on Windows under heavy/long-running stdout traffic while the process is still alive, that would explain both the false 'terminated unexpectedly' notification and the leaked process. Needs a reproduction with a minimal high-output adapter (or DA protocol trace logs) to confirm before changing this logic.

## Evidence

- **suspicious code path:** src/vs/workbench/contrib/debug/node/debugAdapter.ts lines 323-325: `this.serverProcess.stdout!.on('close', () => { this._onError.fire(new Error('read error')); })` treats stdout stream close as an adapter crash, separately from the process's own `exit` handler (lines 319-321).
- **teardown vs kill:** On that error, rawDebugSession.ts (`shutdown` -> `stopAdapter`) does call `da.stopSession()`, which for ExecutableDebugAdapter uses `killTree`/`.kill()` (debugAdapter.ts lines 344-361) — so if the process truly survives, either the kill silently failed (e.g. taskkill.exe rejection swallowed) or the 'close' event fired independently of the process actually dying, which is consistent with the reporter's observation.
