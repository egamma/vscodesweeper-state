# Issue #339472 — Agent Host permission picker exposes Configure Keybinding, but command implementation is a no-op

[https://github.com/microsoft/vscode/issues/339472](https://github.com/microsoft/vscode/issues/339472)

## Summary

Confirmed from source: several Agent Host picker commands (not just Auto-Approve) register `run()` as an intentional no-op because the action view item handles the click directly, but the generic toolbar context menu still offers Configure Keybinding for them — so a user-assigned keybinding invokes a command that does nothing, even though the troubleshooting log shows it was matched and invoked.

## Change summary

Assigning and pressing a keybinding for workbench.action.chat.openAgentHostAutoApprovePicker (and sibling picker commands) does not open the picker, because the command's run() is an empty no-op by design.

## Best solution

Wire run() on these picker Action2 classes to actually open the picker (e.g. via a shared reference/event the action view item exposes), matching how the view item's click handler calls _showPicker — the same fix likely applies uniformly to OpenAgentHostModePickerAction, OpenAgentHostAutoApprovePickerAction, OpenAgentHostPermissionModePickerAction, OpenAgentHostCodexApprovalsPickerAction, and OpenAgentHostFolderPickerAction, all of which share the identical empty-run pattern.

- **Behavior:**

  > Invoking any Agent Host picker command (openAgentHostAutoApprovePicker, openAgentHostModePicker, openAgentHostPermissionModePicker, openAgentHostCodexApprovalsPicker, openAgentHostFolderPicker) via keybinding or command palette should open that picker, the same as clicking its toolbar chip. Acceptance: pressing a bound keybinding opens the picker widget; the existing click-to-open behavior is unchanged.
- **Trace:**

  > Each picker's Action2.run() in agentHostChatInputPicker.contribution.ts is an intentional empty no-op (comment: 'the action view item handles interaction'); the real logic lives in the private _showPicker in agentHostChatInputPicker.ts, invoked only from the view item's own click/render handlers. The toolbar's generic 'Configure Keybinding' menu (platform/actions/browser/toolbar.ts) is unaware of this and offers keybinding config for any action, creating the mismatch. Boundary: do not change the generic toolbar Configure Keybinding logic (it's correct in general) or the click-path behavior — the fix should let run() reach the same view item instance's _showPicker, likely via a registry/event the view item registers on creation. Where the uncertainty starts: whether to route through a shared service/event bus or a per-widget registration map, and whether the same mechanism should be reused for all five sibling actions.
- **Open decisions:**
  - Should run() resolve the currently-rendered action view item (and call its _showPicker) via a new registration mechanism, or should the toolbar's Configure Keybinding feature instead be suppressed for actions whose view item owns interaction?
  - Should this fix be applied uniformly to all five Agent Host picker actions in one pass, or fixed incrementally starting with Auto-Approve?
