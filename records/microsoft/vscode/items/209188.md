# Issue #209188 — Using a vscode:// link with ?new-window or ?reuse-window still hijacks existing window

[https://github.com/microsoft/vscode/issues/209188](https://github.com/microsoft/vscode/issues/209188)

## Summary

Keep open: a maintainer confirmed that remote protocol links replace the existing window, and current source still ignores the reported query parameters. The supported windowId=_blank parameter provides a workaround, but does not settle the maintainer's proposed alignment of default remote-link behavior.

## Change summary

Opening a remote folder through a vscode:// link replaces an active SSH workspace despite the reporter requesting a separate window.

## Best solution

Make remote protocol-link window selection predictable and preserve an unrelated active workspace when a separate window is intended. Settle whether this means changing the default remote-link behavior, supporting additional query parameters, or both, while preserving the existing windowId=_blank contract.

- **Proposed comment:**

  > Thanks for the report. To explicitly open a separate window, the supported URL parameter is `windowId=_blank`: `vscode://vscode-remote/ssh-remote+user@1.1.1.1//var/www/html/?windowId=_blank`. The `new-window` and `reuse-window` query parameters are not currently interpreted as window-selection options. Keeping this open for the confirmed window-replacement behavior and the proposed alignment of remote links with regular links.

- **Behavior:**

  > A remote-folder protocol link can currently replace an unrelated active SSH workspace, disconnecting that window from its original host. A maintainer confirmed the behavior and suggested alignment with regular URI handling. The supported windowId=_blank parameter already requests a separate window, whereas new-window and reuse-window are not interpreted as window-selection parameters. Acceptance must establish the intended default and explicit-parameter behavior, preserving the original workspace whenever a separate window is requested.
- **Trace:**

  > In src/vs/code/electron-main/app.ts, getWindowOpenableFromProtocolUrl converts the reported URL to a remote folderUri, while handleProtocolUrl sets shouldOpenInNewWindow only for windowId=_blank or the macOS no-window case. It then passes forceNewWindow to WindowsMainService.open. In src/vs/platform/windows/electron-main/windowsMainService.ts, shouldOpenNewWindow leaves folder opening eligible for reuse under default settings, and the window-opening path selects the last active window when a new window is not forced. The source supports the maintainer's reproduction at https://github.com/microsoft/vscode/issues/209188#issuecomment-3648004426; runtime behavior was not exercised. Preserve existing windowId=_blank handling, already-open workspace selection, CLI semantics, and unrelated local-link behavior. https://github.com/microsoft/vscode/issues/323880 is related conditional-reuse work, not an eligible older duplicate canonical.
- **Open decisions:**
  - Should remote-folder protocol links open a separate window by default, or continue following window.openFoldersInNewWindow unless the URL explicitly requests a new window?
  - Should new-window and reuse-window become supported URL parameters; if so, does reuse-window permit replacing an unrelated workspace or only reuse an already-matching destination?
