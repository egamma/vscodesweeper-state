# Issue #336692 — Multiple steering messages visually replace each other

[https://github.com/microsoft/vscode/issues/336692](https://github.com/microsoft/vscode/issues/336692)

## Summary

Recent, uncorroborated bug report (filed by the Copilot contributor account, no maintainer input yet) about steering-message queueing in the Agents Window; the client chat model supports multiple concurrent Steering-kind pending requests, but the agent-host protocol layer only carries a single `steeringMessage` slot, which is a plausible source of the visual-replacement symptom and needs a maintainer decision on intended design before a fix is written.

## Change summary

Sending two or more steering messages in a row only shows the latest one in the UI, even though (per the reporter) all of them are eventually delivered to the agent.

## Best solution

Decide whether the Agent Host Protocol should carry an ordered list of steering messages (mirroring the client model's multi-entry support) or whether the UI should instead visually merge/queue additional steering text into a single pending slot — then align chatModel.ts, agentHostSessionHandler.ts, and the AHP `setPendingMessages` contract accordingly.

- **Behavior:**

  > When a user sends multiple steering messages in quick succession (before the current turn completes), each queued steering message should remain visible in the chat transcript for as long as it is pending, accurately reflecting what will be sent to the agent. Currently only the most recently sent steering message stays visible; earlier ones disappear from the UI even though the reporter believes all are eventually delivered. Acceptance: after sending N steering messages back-to-back, N distinct pending steering entries are visible under the 'Steering' divider until they are sent or cleared.
- **Trace:**

  > The client-side chat model (chatModel.ts addPendingRequest, ~line 2598) and view model (chatViewModel.ts getItems, ~line 357-395) both support multiple concurrent Steering-kind pending requests and render each as a separate item. However, for Agents Window sessions backed by the agent host protocol, agent.ts:1218 defines `setPendingMessages` with a singular `steeringMessage: PendingMessage | undefined` (not an array), and agentHostSessionHandler.ts's `_syncPendingMessages`/`_applyRemotePendingMessages` (~lines 2132-2270) only ever track/project one steering message; the protocol state is authoritative and re-applied to the local model via `syncPendingRequestsFromRemote`, which is a strong candidate for why extra local steering entries vanish. The boundary: do not touch the `queuedMessages` (plural, working) side of the protocol, and do not change the semantics of a single in-flight steering injection at the CLI/agent runtime side without confirming it can actually accept more than one. No related open issues or PRs were found referencing this.
- **Open decisions:**

## Evidence
