# Issue #339088 — Tool grouping/virtual tools broken for custom endpoints

[https://github.com/microsoft/vscode/issues/339088](https://github.com/microsoft/vscode/issues/339088)

## Summary

Traced a concrete code path on main that plausibly explains this: virtual tool grouping is skipped whenever `endpoint.supportsToolSearch` is true, and for non-Anthropic BYOK/custom endpoints (OpenRouter, custom OpenAI-compatible, including DeepSeek) that flag falls back to a pure model-id/family string heuristic with no verification that the model actually implements tool search — so a custom endpoint whose model name matches the heuristic gets the full ungrouped tool list and blows past the 128-tool hard limit. The maintainer's tentative 'dupe of #322784?' doesn't hold up: that issue is a different-scope internal tracking item about carrying virtual tools over to CLI/agent-host sessions, not about this BYOK/custom-endpoint regression in the regular chat extension host.

## Change summary

Virtual tool grouping fails to kick in for custom/BYOK endpoints (OpenRouter, DeepSeek, local LLMs), causing chat to fail outright with the 128-tool hard limit error instead of grouping tools down.

## Best solution

Make the tool-search gate in getAvailableTools (extensions/copilot/src/extension/prompt/node/defaultIntentRequestHandler.ts:795) not rely solely on the model-id/family heuristic in modelSupportsToolSearch (extensions/copilot/src/platform/endpoint/common/chatModelCapabilities.ts:483) for BYOK/custom endpoints — require an explicit, verified tool_search capability (as anthropicProvider.ts already does by also checking for the CUSTOM_TOOL_SEARCH_NAME tool) before skipping virtual tool grouping, so unsupported custom endpoints always fall back to grouping.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/prompt/node/defaultIntentRequestHandler.ts`, `extensions/copilot/src/platform/endpoint/common/chatModelCapabilities.ts`, `extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts`, `extensions/copilot/src/extension/byok/vscode-node/openRouterProvider.ts`, `extensions/copilot/src/extension/byok/vscode-node/customOAIProvider.ts`
- **Validation:** A BYOK/OpenRouter-configured endpoint whose model name matches the tool-search heuristic, given >128 available tools, should trigger virtual tool grouping (toolGrouping.compute) instead of sending the raw ungrouped list — add/extend a test asserting getAvailableTools groups tools down for a custom endpoint even when modelSupportsToolSearch(id) returns true, unless the endpoint demonstrably implements server-side tool search.
- **Behavior:**

  > Starting or continuing a chat session on a custom/BYOK endpoint (OpenRouter, DeepSeek, or other OpenAI-compatible custom endpoint) whose available tool count exceeds the 128 hard limit should never fail outright with 'You may not include more than 128 tools' — virtual tool grouping should engage and trim/group tools down below the limit, the same as it does for Copilot-hosted models that don't support native tool search. Acceptance: with >128 tools and a custom endpoint, the request sent to the model contains <=128 tools (grouped), and no hard-limit error occurs.
- **Trace:**

  > `getAvailableTools` in defaultIntentRequestHandler.ts returns the tools list unmodified whenever `endpoint.supportsToolSearch` is true (line ~795), skipping `toolGrouping.compute()` entirely. For BYOK/custom endpoints built on `ChatEndpoint` (chatEndpoint.ts:274), `supportsToolSearch` falls back to `modelSupportsToolSearch(this)` (chatModelCapabilities.ts:483-508), a pure model id/family string-pattern match (e.g. 'claude-4-5+', 'gpt-5-4', 'gpt-5-5', gpt-5.6/6 families) with no verification that the specific custom provider/model actually implements the client-side tool_search mechanism Copilot relies on. Anthropic's own BYOK provider additionally gates on the presence of the `CUSTOM_TOOL_SEARCH_NAME` tool in the request (anthropicProvider.ts:147-149) before treating tool search as active, but OpenRouter/customOAIProvider have no equivalent check at the point where grouping is bypassed. Do not change the grouping algorithm itself (toolGrouping.ts/virtualToolGrouper.ts) or the heuristic's behavior for genuinely Copilot-hosted models — the boundary is specifically how/whether `supportsToolSearch` is trusted for non-Copilot-native BYOK/custom endpoints. Related: https://github.com/microsoft/vscode/issues/322784 is a separate CLI/agent-host carryover tracking issue, not a canonical for this report.
- **Open decisions:**
  - Should the tool-search gate require an endpoint-specific explicit capability flag (not just the id/family heuristic) for all non-Copilot-hosted BYOK/custom endpoints, or should the heuristic be removed entirely for those endpoint types?
  - Should custom/BYOK endpoints that incorrectly skip grouping fail gracefully by always falling back to virtual tool grouping, or should there be a user-facing capability/setting indicating whether a given custom model supports tool search?

## Evidence

- **grouping skipped on supportsToolSearch:** extensions/copilot/src/extension/prompt/node/defaultIntentRequestHandler.ts:795 — `if (this.options.invocation.endpoint.supportsToolSearch) { return tools; }` returns the full raw tool list without ever invoking `this.toolGrouping.compute(...)`.
- **heuristic-only capability flag:** extensions/copilot/src/platform/endpoint/node/chatEndpoint.ts:274 sets `this.supportsToolSearch = modelMetadata.capabilities.supports.tool_search ?? modelSupportsToolSearch(this);` — for BYOK/custom endpoints (OpenRouterEndpoint/OpenAIEndpoint, both extending the same ChatEndpoint) `capabilities.supports.tool_search` is not provided by the custom provider, so it falls through to the id/family string-matching heuristic in chatModelCapabilities.ts:483-508 (matches on 'claude', 'gpt-5-4', 'gpt-5-5', gpt-5.6/6 families) with no check that the custom endpoint actually implements server-side tool search.
- **contrast with Anthropic BYOK:** extensions/copilot/src/extension/byok/vscode-node/anthropicProvider.ts:147-149 additionally requires the CUSTOM_TOOL_SEARCH_NAME tool to be present before enabling tool search; OpenRouter/customOAIProvider have no equivalent guard, so grouping suppression relies purely on the name heuristic.
- **unverified canonical:** https://github.com/microsoft/vscode/issues/322784 (COLLABORATOR-authored, labeled agent-host) is about virtual tools not carrying over to CLI/agent-host sessions as CLI becomes default — a distinct scope from this BYOK/custom-endpoint regression in the normal chat extension host; the maintainer's comment ends in a question mark, not a confirmation.
- **corroborating report:** Comment by Slion describes hitting the same 128-tool failure with local LLMs plus many extensions, consistent with grouping not reliably engaging outside the hosted Copilot model path.
