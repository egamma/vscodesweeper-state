# Issue #339088 — Tool grouping/virtual tools broken for custom endpoints

[https://github.com/microsoft/vscode/issues/339088](https://github.com/microsoft/vscode/issues/339088)

## Summary

Likely-real bug: virtual tool grouping is supposed to keep the request under the 128-tool hard cap even without an embeddings-capable endpoint (confirmed by extensions/copilot/src/extension/tools/test/node/virtualTools/virtualToolGrouperNoEmbeddings.spec.ts), but multiple independent reporters hit the hard-limit error specifically with BYOK/custom endpoints and local models. The suggested duplicate (#322784) is a different, team-authored tracking issue about bringing virtual tools to CLI/AHP, not this symptom, so it doesn't clear the re-review duplicate bar.

## Change summary

Starting or continuing a chat session on a custom/BYOK endpoint (OpenRouter, DeepSeek, local LLMs) with enough tools/extensions/MCP servers enabled hits the "more than 128 tools" hard-cap error that virtual tool grouping is meant to prevent.

## Best solution

Trace why grouping doesn't engage (or silently fails) for BYOK/custom-endpoint sessions versus hosted Copilot models in extensions/copilot/src/extension/prompt/node/defaultIntentRequestHandler.ts and the tool grouping/categorization path (virtualToolGrouper.ts, toolGroupingService.ts), and ensure the designed no-embeddings fallback actually applies on that code path.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/prompt/node/defaultIntentRequestHandler.ts`, `extensions/copilot/src/extension/tools/common/virtualTools/virtualToolGrouper.ts`, `extensions/copilot/src/extension/tools/common/virtualTools/toolGroupingService.ts`
- **Validation:** A test asserting that, with a BYOK/custom endpoint and the embeddings model unavailable, the computed tool list passed to the model stays within HARD_TOOL_LIMIT (mirroring virtualToolGrouperNoEmbeddings.spec.ts but exercised through the BYOK/custom-endpoint request path).
- **Behavior:**

  > Starting or continuing a chat session on a custom/BYOK endpoint with more tools enabled than the hard cap should never surface the raw 'more than 128 tools' provider error — virtual tool grouping (or its no-embeddings fallback) must reduce the visible tool set below the limit exactly as it does for hosted Copilot models. Acceptance: a session with >128 available tools on a BYOK/custom endpoint sends a request with <=128 tools, and the designed no-embeddings fallback test still passes.
- **Trace:**

  > extensions/copilot/src/extension/tools/test/node/virtualTools/virtualToolGrouperNoEmbeddings.spec.ts shows the grouper is designed to stay within HARD_TOOL_LIMIT even when `IToolEmbeddingsComputer.isEmbeddingModelAvailable()` is false, so the capability to degrade gracefully exists in principle. The categorization step in virtualToolGrouper.ts calls a hardcoded Copilot endpoint ('copilot-utility-small') via IEndpointProvider rather than the user's selected endpoint, which is a candidate explanation for why grouping could be failing or short-circuiting for BYOK-only configurations, but this was not traced to a confirmed failure point — defaultIntentRequestHandler.ts's toolGrouping wiring (lines ~617-808) and how it's invoked for BYOK sessions still need to be checked to confirm whether grouping is even reached, or reached but erroring out silently. Boundary: do not change the categorization/embeddings design for hosted Copilot sessions; the fix should only affect the fallback/degradation path for endpoints lacking embeddings access. Related: https://github.com/microsoft/vscode/issues/322784 (different scope — CLI/AHP grouping support).
- **Open decisions:**
  - If embeddings/categorization is unreachable for a given endpoint, should grouping fall back to a simpler heuristic (e.g. group-by-toolset only) that still enforces the hard cap, or should the system instead surface a clearer, actionable error before the provider's 128-tool rejection?
  - Should virtual tool grouping threshold/behavior be configurable per-endpoint (so BYOK/local models get a stricter trigger point), rather than sharing one global experiment-based threshold?
