# Issue #337750 — Windows: uninstalling the User build leaves the per-extension default ProgId in HKCU\Software\Classes, so those file types still open with VS Code

[https://github.com/microsoft/vscode/issues/337750](https://github.com/microsoft/vscode/issues/337750)

## Summary

Well-diagnosed, fresh report with concrete registry evidence; the checkout confirms code.iss never writes uninstall cleanup for the extension's own `Software\Classes\.<ext>` default value (only the ProgId key and OpenWithProgids entries are cleaned up), so the leftover default is plausible, but I can't execute the Windows installer/uninstaller to fully confirm the end-to-end symptom.

## Change summary

On Windows, uninstalling VS Code (User build) with file associations enabled leaves the `.cfg`/`.json`/`.jsonc`/`.yaml` extensions' default ProgId pointing at the now-deleted `VSCode.<ext>` key, so those types still open in VS Code even though it's uninstalled.

## Best solution

Extend the Windows uninstaller (build/win32/code.iss) to also clear the extension's `Software\Classes\.<ext>` default value when it still equals the app's own `VSCode.<ext>` ProgId, mirroring the cleanup already done for the ProgId key and OpenWithProgids entries; likely needs custom uninstall Pascal Script since a blind `uninsdeletevalue` would risk clobbering a value the user later reassigned to another app.

## Plan brief

- **Likely files:** `build/win32/code.iss`
- **Validation:** Manual: install the Windows User build with associatewithfiles, uninstall, and confirm HKCU\Software\Classes\.json (Default) is removed/reset rather than left as a dangling 'VSCode.json' string.
- **Behavior:**

  > After uninstalling a Windows User-build VS Code that was installed with file associations enabled, the previously-associated extensions (.cfg, .json, .jsonc, .yaml, and any others registered the same way) should no longer resolve to VS Code — the stale `Software\Classes\.<ext>` default value pointing at the removed `VSCode.<ext>` ProgId should be cleared (or restored) rather than left dangling, so Windows falls back to a real default handler instead of silently continuing to launch VS Code via the (now-deleted) ProgId's OpenWith fallback.
- **Trace:**

  > build/win32/code.iss's [Registry] section only ever marks the `VSCode.<ext>` ProgId key (e.g. lines 722-726 for .json) and the `.ext\OpenWithProgids\VSCode.<ext>` entry (e.g. lines 128-129 for .ascx) with uninsdeletekey/uninsdeletevalue; it never touches `Software\Classes\.<ext>` itself, so its default value is never part of the declarative uninstall cleanup — consistent with the reporter's registry inspection. The boundary: do not touch `FileExts\<ext>\UserChoice` (hash-protected by Windows, not writable by any app) and don't blindly delete `Software\Classes\.<ext>`'s default for every extension — only when it still equals this app's own `VSCode.<ext>` ProgId, to avoid overwriting a default the user later picked for another editor. Reporter's related note: #118864 covers the separate ask of exposing an opt-out for associatewithfiles.
- **Open decisions:**
  - Should the uninstaller unconditionally clear `Software\Classes\.<ext>`'s default when it matches `VSCode.<ext>`, or attempt to restore the extension's pre-install default (which Inno doesn't track today)?
  - Does this cleanup belong in the generic per-extension [Registry] table (needs conditional Pascal Script per key) or in a single custom uninstall step that iterates the known extension list?

## Evidence

- **code.iss cleanup scope:** build/win32/code.iss only defines `uninsdeletekey`/`uninsdeletevalue` for `Software\Classes\{#RegValueName}.<ext>` (the ProgId key, e.g. lines 722-726 for .json) and for `Software\Classes\.<ext>\OpenWithProgids\{#RegValueName}` (e.g. lines 128-129 for .ascx) — there is no entry anywhere for `Software\Classes\.<ext>` itself, the key whose default value the reporter says is left stale.
- **reporter's own registry trace:** Reporter directly inspected HKCU\Software\Classes before/after uninstall and HKLM's uninstall-key task lists, showing OpenWithProgids/ProgId cleanup working (139→0) while the four extensions' bare `.ext` default value survived.
