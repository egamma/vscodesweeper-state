# Issue #292302 — Pull request view flickers on startup

[https://github.com/microsoft/vscode/issues/292302](https://github.com/microsoft/vscode/issues/292302)

## Summary

The startup flicker remains a valid core view-restoration bug. Maintainers confirmed the scenario and concluded that core must preserve enough view state to avoid restoring a conditional view that immediately becomes inactive.

## Change summary

Avoid briefly restoring the Active Pull Request view during startup when its pull request is no longer open.

## Best solution

Core view restoration should use the last known active/eligible state of conditional views and avoid opening an empty or soon-to-be-hidden view container while extension context keys are being recomputed. The behavior should be covered for both primary and auxiliary sidebars without changing normal restoration of containers that still have active views.

- **Behavior:**

  > When a workspace is reopened after its checked-out pull request has been merged, the conditional Active Pull Request view must not appear temporarily and then disappear. View containers that remain eligible must continue to restore normally. Acceptance should cover both the obsolete conditional-view case and an ordinary last-active view that should still be restored.
- **Trace:**

  > The confirmed trigger is restoring a workspace whose previously active pull request has since been merged. `CompositePart` in src/vs/workbench/browser/parts/compositePart.ts loads the last active composite ID from workspace storage, and the sidebar restoration path in src/vs/workbench/browser/layout.ts opens that ID without the active-view check used for auxiliary-bar restoration. `PaneCompositeBar` in src/vs/workbench/browser/parts/paneCompositeBar.ts separately caches contributed view conditions, and `ViewContainerModel` in src/vs/workbench/services/views/common/viewContainerModel.ts updates active and visible descriptors as context keys settle. The uncertainty begins at coordinating these independently persisted states across extension registration without suppressing legitimate restoration. Keep extension-owned pull-request state computation and normal restoration of eligible containers unchanged.

## Evidence

- **confirmed scenario:** The report includes a recording, and https://github.com/microsoft/vscode/issues/292302#issuecomment-3834973148 identifies the reproducible sequence: an open PR is checked out, the PR is merged, and reopening the workspace restores the obsolete view before hiding it.
- **core ownership:** The extension already initializes its controlling context keys to false and has no mechanism to suppress core restoration, as explained at https://github.com/microsoft/vscode/issues/292302#issuecomment-3834973174. A workbench maintainer consequently concluded that core needs to capture the view state: https://github.com/microsoft/vscode/issues/292302#issuecomment-3834973184.
- **current source path:** On current main, src/vs/workbench/browser/parts/compositePart.ts restores `lastActiveCompositeId` directly from workspace storage, while src/vs/workbench/browser/layout.ts reopens that last sidebar composite when the sidebar becomes visible. The sidebar path does not perform the `hasViews` eligibility check used by the auxiliary-bar restoration path.
- **cached conditional state:** src/vs/workbench/browser/parts/paneCompositeBar.ts caches contributed view `when` clauses and recomputes visibility around extension registration, while src/vs/workbench/services/views/common/viewContainerModel.ts removes active and visible descriptors when their context conditions become false. This permits a restored container to disappear after extension state settles.
- **canonical search:** No older open issue with the same reporter-observable startup view flicker was found. The mechanical candidate https://github.com/microsoft/vscode/issues/247054 concerns Wayland window borders and is unrelated.
