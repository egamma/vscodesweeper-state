# Issue #339873 — Sandbox denied domains don't work as expected

[https://github.com/microsoft/vscode/issues/339873](https://github.com/microsoft/vscode/issues/339873)

## Summary

Team-authored bug report with a concrete, first-hand repro (explicit denied-domain list plus a screenshot) showing the sandbox denylist both under- and over-blocks; this is a sandbox-policy bypass concern so it must stay open regardless of other evidence, and I couldn't fully confirm the root cause since enforcement likely happens inside the external Copilot SDK.

## Change summary

With denied domains set to `apple.com` and `*.peet.io`, `apple.com` is unexpectedly reachable while `peet.io` (the bare apex, not just subdomains) is blocked.

## Best solution

Trace the mismatch past this repo's own matching code into the actual enforcement path: `buildSandboxConfigForSdk` (src/vs/platform/agentHost/node/copilot/sandboxConfigForSdk.ts) forwards raw `deniedNetworkDomains` strings straight into `blockedHosts` for the `@github/copilot-sdk` runtime, without applying this repo's `normalizeDomainPattern`/`matchesDomainPattern` semantics (src/vs/platform/networkFilter/common/domainMatcher.ts) used elsewhere (fetch-tool filtering, command-line rewriter warnings). The discrepancy the reporter describes is consistent with the SDK's own host-matching having different (and seemingly inconsistent) wildcard/exact-match semantics than this repo's matcher — worth checking whether domains should be pre-normalized before being handed to the SDK, or whether the SDK needs a fix.
