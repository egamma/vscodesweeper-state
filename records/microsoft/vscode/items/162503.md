# Issue #162503 — Virtual F13-F19 keys is not recognised

[https://github.com/microsoft/vscode/issues/162503](https://github.com/microsoft/vscode/issues/162503)

## Summary

The failure occurs in Edge and Chrome at vscode.dev, while current VS Code source already maps F13–F19 when Chromium supplies those keyboard events. This is an upstream Chromium keyboard-event issue and should remain open as an upstream tracker.

## Change summary

Registry-remapped Windows keys targeting F13–F19 are not recognized unless AutoHotKey re-emits the virtual key.

## Best solution

Chromium should expose the registry-remapped F13–F19 key through the expected KeyboardEvent fields; VS Code can then consume it through its existing keybinding path without a product-specific workaround.

## Evidence

- **browser reproduction:** The reporter confirmed that the remapping also fails in Edge and Chrome at https://vscode.dev/ in https://github.com/microsoft/vscode/issues/162503#issuecomment-1271594377, placing the failure below VS Code's desktop-specific code.
- **current source:** src/vs/workbench/services/keybinding/browser/keybindingService.ts constructs StandardKeyboardEvent directly from the browser keydown event, and src/vs/base/browser/keyboardEvent.ts derives the key from KeyboardEvent.keyCode rather than querying a Windows-native remapping API.
- **supported key range:** src/vs/base/common/keyCodes.ts explicitly maps F13 through F19 to browser key codes 124 through 130 and Windows virtual-key names VK_F13 through VK_F19, so VS Code can handle these keys when the browser emits them correctly.
- **related upstream diagnosis:** A maintainer documented the same Chromium event boundary for registry-remapped keys in https://github.com/microsoft/vscode/issues/162629#issuecomment-1344127328; that related issue was classified upstream after also failing on vscode.dev.
