# Issue #324355 — TreeView performance degradation caused by MenuService with heavy context menus

[https://github.com/microsoft/vscode/issues/324355](https://github.com/microsoft/vscode/issues/324355)

Keep open while the linked optimization PR is reviewed. The reported menu-construction path has changed on current main, but the supplied menu contributions and profiling steps suffice to retest the remaining rendering overhead; there is no verified complete fix.

## Change summary

Heavy view/item/context contributions make extension tree scrolling and expansion slow through repeated menu processing during row rendering.

## Best solution

Review https://github.com/microsoft/vscode/pull/324358 against the current menu implementation, then profile the reporter's extension-heavy setup to establish what overhead remains. Preserve menu visibility, ordering, cross-extension contributions, and accessibility while reducing repeated work; assess contribution-point changes separately if profiling still warrants them.

## Evidence

- **Measured rendering impact:** https://github.com/microsoft/vscode/issues/324355 supplies menu definitions and scrolling traces with 100–200 ms animation frames. https://github.com/microsoft/vscode/issues/324355#issuecomment-5162135662 reports a 679.8 ms expansion frame, with 423.2 ms attributed to menu sorting, context-key collection, and menu-item retrieval.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/324358 was verified OPEN. Its body says it partially addresses this issue through reduced initialization work and caching, and reports approximately 35–40% lower average renderElement duration in the author's OSS measurements. This is not a merged or complete fix.
- **Current source differs from the original trace:** src/vs/platform/actions/common/menuService.ts:39–40 now routes getMenuActions directly through createMenuActionGroups, which filters registered items, sorts matching items, and recursively constructs submenu actions. This path does not instantiate MenuInfo or collect context keys as in the reported trace, so those historical timings cannot establish current-main performance.
- **Repeated work remains on the relevant path:** src/vs/workbench/browser/parts/views/treeView.ts calls getResourceActions for row actions around line 1495 and for accessibility labels around lines 713 and 728. TreeMenus.getActions around lines 1817–1842 calls getMenuActions using per-element context overlays, and getMenuId returns the shared MenuId.ViewItemContext. This establishes the relevant processing path, not its current measured cost.
- **Cross-extension scope and design alternatives:** https://github.com/microsoft/vscode/issues/324355#issuecomment-5168209664 corrects the earlier cross-extension experiment: removing view filters exposed effects on other extensions' trees. The reporter proposes dedicated contribution points or automatic partitioning of existing contributions; neither alternative is an accepted product decision in the supplied discussion.
