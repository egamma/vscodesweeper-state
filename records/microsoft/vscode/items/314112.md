# Issue #314112 — Unable to differentiate between browser tabs to share with the agent when the url is the same

[https://github.com/microsoft/vscode/issues/314112](https://github.com/microsoft/vscode/issues/314112)

## Summary

The sharing carousel still cannot distinguish tabs with identical titles and URLs, and accepting a tab does not reveal it. Keep this team-authored Backlog item open; the existing browser-integration and ux labels are appropriate.

## Change summary

Make identically addressed browser tabs identifiable in the agent-sharing prompt and bring the chosen tab into focus.

## Best solution

Provide a recognizable association between each sharing option and its browser editor, then reveal the tab after sharing is accepted. Settle the user-facing identification interaction before implementing it in the browser-sharing carousel.

- **Likely files:** `src/vs/workbench/contrib/browserView/electron-browser/tools/openBrowserTool.ts`, `src/vs/workbench/contrib/browserView/test/electron-browser/tools/openBrowserTool.test.ts`
- **Validation:** In the desktop workbench, open two directly shareable, unshared tabs with identical titles and URLs but distinguishable page state. Add focused OpenBrowserTool coverage for the agreed identification contract and accepted-selection reveal behavior.
- **Behavior:**

  > When multiple browser tabs have identical titles and URLs, the agent-sharing prompt must let the user determine which physical tab each option represents before sharing. Accepting sharing must bring the chosen browser tab into focus and share that tab rather than another matching tab. Declining sharing or denying consent must preserve existing non-sharing behavior. Acceptance includes exercising both matching tabs independently through the prompt.
- **Trace:**

  > OpenBrowserTool._buildShareCarousel in src/vs/workbench/contrib/browserView/electron-browser/tools/openBrowserTool.ts uses editor.id for internal identity but exposes only title and truncated URL, so identical pages produce identical visible options. _promptForUnsharedPages resolves the selected ID correctly, while _shareExistingPage updates sharing and returns a page summary without revealing the editor. BrowserViewModel.setSharedWithAgent in src/vs/workbench/contrib/browserView/common/browserView.ts also does not activate directly shareable tabs. The existing per-tab sharing button is a workaround, not carousel coverage. The original test plan at https://github.com/microsoft/vscode/issues/313813 invites UX feedback but does not settle how identical tabs should be identified. Preserve consent, sharing eligibility, network restrictions, and the existing decline/open-new-page behavior; do not broaden this into a general browser tab redesign.
- **Open decisions:**
  - What user-facing interaction should associate identical sharing options with their actual browser tabs before consent: a reveal/preview affordance, corresponding visible tab identifiers, or another identification design?
