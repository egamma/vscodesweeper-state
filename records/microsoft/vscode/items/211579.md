# Issue #211579 — Feature request: Expose API to get the width and height of the text editors

[https://github.com/microsoft/vscode/issues/211579](https://github.com/microsoft/vscode/issues/211579)

## Summary

A real extension API gap remains: extensions can observe visible ranges and editor/view-column changes, but cannot query the rendered viewport dimensions needed for accurate external-editor synchronization. The request already has the appropriate `api` and `under-discussion` labels and no verified older canonical with the same observable need is identified.

## Change summary

Expose extension APIs for obtaining the width and height of editor viewports, panels, and windows.

## Best solution

Define the narrowest stable API around text-editor viewport dimensions and dimension-change notifications, using vscode-neovim scroll synchronization as the motivating scenario; evaluate panels and windows separately because they have different ownership and lifecycle boundaries.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostTextEditors.ts`, `src/vs/workbench/api/browser/mainThreadEditors.ts`
- **Validation:** Add extension-host API tests that obtain dimensions for a visible text editor, resize its editor group, and verify both the reported dimensions and the dimension-change notification update while existing visible-range behavior remains unchanged.
- **Behavior:**

  > Extensions need a supported way to obtain the current rendered viewport dimensions of a text editor so integrations such as vscode-neovim can synchronize viewport size and scrolling without hard-coded values. The dimensions must update when the editor layout changes. The API contract should define units and behavior for hidden or not-yet-laid-out editors; panel and window dimensions should only be included if their ownership and semantics are explicitly approved.
- **Trace:**

  > The public editor API is declared in src/vscode-dts/vscode.d.ts and implemented across the extension-host editor bridge in src/vs/workbench/api/common/extHostTextEditors.ts and src/vs/workbench/api/browser/mainThreadEditors.ts. Existing visible-range and view-column data do not provide rendered viewport width or height, leaving vscode-neovim to approximate dimensions; https://github.com/vscode-neovim/vscode-neovim/pull/1335 is an external consumer attempting viewport synchronization. The boundary is a stable extension-facing layout contract: do not expose DOM objects or couple extensions to internal editor layout structures. The uncertainty starts at whether this should be editor-only or also cover panels/windows, and what unit and event semantics are stable enough for the public API.
- **Open decisions:**
  - Should the API initially expose only text-editor viewport dimensions, or also define separate contracts for panels and windows?
  - Should dimensions be reported in CSS pixels, editor columns/lines, or both?
  - What should the API return for hidden, background, or not-yet-laid-out editors, and when should dimension-change events fire?
