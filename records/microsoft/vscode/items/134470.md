# Issue #134470 — Support enabling "Open With Code" Windows Explorer integration post installation

[https://github.com/microsoft/vscode/issues/134470](https://github.com/microsoft/vscode/issues/134470)

## Summary

Keep this accepted, well-supported request open: current installer integration does not provide a discoverable in-app way to enable Open with Code after installation. This issue is already the canonical destination for a matching newer request.

## Change summary

Provide a way to enable Windows Explorer Open with Code integration after installation, including installations that offer no interactive setup options.

## Best solution

Provide a discoverable Windows-only post-installation action that enables Explorer integration and reflects its actual OS registration state. Plan the supported installation variants and interaction contract before implementation, keeping installer and runtime ownership consistent.

## Plan brief

- **Likely files:** `build/win32/code.iss`, `src/vs/workbench/electron-browser/desktop.contribution.ts`, `src/vs/platform/native/common/native.ts`, `src/vs/platform/native/electron-main/nativeHostMainService.ts`
- **Validation:** On Windows, install with both Explorer context-menu tasks omitted, invoke the agreed post-install action, and verify Open with Code opens a file and a directory. Repeat the action to check idempotence, then verify registration survives a VS Code update. Repeat for Store-installed and system-installed builds if included in the agreed support contract, and check both classic and modern Explorer menus where supported.
- **Behavior:**

  > Users who omitted Explorer integration during installation, or installed through a channel without interactive setup options, need a discoverable way to enable Open with Code afterward. Successful enablement should make the appropriate file and directory Explorer actions available and launch the installed VS Code instance. Repeating the operation should not create duplicate entries, and existing integration should remain functional across updates. Acceptance must cover the installation variants and Explorer menu styles agreed with the maintainer.
- **Trace:**

  > build/win32/code.iss owns existing integration through addcontextmenufiles/addcontextmenufolders, registry entries at lines 1275-1287, and AddAppxPackage for modern Windows menus. ShouldRepairFolderContextMenu covers only a specific update repair case, not initial post-install opt-in. Registration searches found no corresponding Windows workbench action; desktop.contribution.ts registers its existing shell-install actions only on macOS. The likely runtime boundary involves the desktop action surface and native-host service, but the operation and lifecycle ownership have not been designed. Preserve installer selections, existing update repair, and unrelated file associations; macOS integration is outside this report's central scope. https://github.com/microsoft/vscode/issues/198519 was explicitly consolidated into https://github.com/microsoft/vscode/issues/134470.
- **Open decisions:**
  - Which installation variants must the post-install action support, and should system installations enable integration only for the current user or for all users?
  - Should the user-facing capability only enable both file and directory integration, or also expose separate choices and a disable operation?
