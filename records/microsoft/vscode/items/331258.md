# Issue #331258 — Agent Host: background client auto-cancels side chat ask_user requests after 5s grace window

[https://github.com/microsoft/vscode/issues/331258](https://github.com/microsoft/vscode/issues/331258)

## Summary

Well-traced, real bug: the `ChatInput` branch of `_watchForSessionInputNeeded` checks the window-local `_renderedRequests` observable with no cross-client ownership guard, unlike the sibling `ToolClientExecution` branch — so a background client that never rendered a side chat's carousel still races to cancel it after the 5s grace window. Already labeled correctly (`bug`, `agent-host`); no action needed beyond fixing.

## Change summary

A background window with the same agent-host session open (but not that session's side chat) auto-cancels the side chat's ask_user requests ~5s after they're raised, because it can't see another window already rendered them.

## Best solution

Give `SessionChatInputRequest` cancellation the same cross-client ownership semantics as `ToolClientExecution` — either propagate a session-level 'claimed by clientId' signal all clients can observe, or have only the chat-editor-owning client run the ChatInput cancellation timer — plus surface cancellation to the model as an explicit signal rather than an empty `User responded: ` string.

- **Rationale:** The fix isn't a small local guard like the `ToolClientExecution` branch's clientId check — `SessionChatInputRequest` carries no clientId to compare against, so correctly fixing this needs a cross-client claim mechanism (e.g. a session-level 'this client is rendering it' signal other windows can observe) or protocol changes, which is more than a localized, safely-auto-fixable change.

## Evidence

- **root cause confirmed in source:** src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts lines 2273-2291: the `SessionInputRequestKind.ChatInput` branch only checks `this._renderedRequests.get().has(inputKey)` (an in-process `observableValue` local to each window, declared at line 960) before cancelling via `ChatInputCompleted`/`Cancel` after `UNOBSERVED_CLIENT_TOOL_GRACE_MS` (5000ms, line 121).
- **sibling branch has the guard this one lacks:** The `ToolClientExecution` branch at lines 2298-2300 checks `initial.clientId !== this._config.connection.clientId` and returns early ('A different client owns this call'); the `ChatInput` branch has no equivalent, and `SessionChatInputRequest`/`ChatInputRequest` (channels-session/state.ts, channels-chat/state.ts) carry no clientId field to check against, so a like-for-like guard isn't directly available.
- **affected sibling flows:** The `ToolAuthentication` (~line 2408) and confirmation-deny (~line 2427) branches use the same window-local `_renderedRequests` check with no ownership guard, so side-chat MCP auth and tool confirmations are plausibly exposed to the same race, per the issue's own note.
