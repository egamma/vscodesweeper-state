# Issue #271669 — Improve autoFix setting implementation

[https://github.com/microsoft/vscode/issues/271669](https://github.com/microsoft/vscode/issues/271669)

## Summary

Keep open: changing autoFix to default off resolved the narrower rollout question, but current main still uses the fixed per-edit diagnostics delay when the feature is enabled. This team-authored issue explicitly remains the tracker for designing a better diagnostics-delivery flow.

## Change summary

Replace autoFix's fixed delay and immediate per-edit diagnostic injection with a flow that preserves useful error feedback without slowing or diverting multi-edit agent work.

## Best solution

Choose and implement a diagnostics-delivery lifecycle that avoids waiting after every edit while still giving the model an opportunity to correct newly introduced errors before control returns to the user.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/tools/node/editFileToolResult.tsx`, `extensions/copilot/src/extension/tools/node/abstractReplaceStringTool.tsx`, `extensions/copilot/src/extension/tools/node/applyPatchTool.tsx`, `extensions/copilot/src/extension/tools/node/createFileTool.tsx`
- **Validation:** End the plan with focused tool or simulation coverage showing that a multi-edit request incurs no fixed diagnostics wait after every edit, while newly introduced diagnostics are delivered at the selected lifecycle point early enough for correction before the agent finishes.
- **Behavior:**

  > Agent requests that perform several edits should not pause for a fixed diagnostics timeout after every edit or be diverted from the requested edit sequence by transient diagnostics. Newly introduced actionable diagnostics should still reach the model at a defined lifecycle point where it can correct them before returning control to the user. Existing edit failures, notebook handling, and successful-edit reporting must remain unchanged. Acceptance requires coverage of both a multi-edit sequence with delayed diagnostics and a completed sequence containing a genuine new error.
- **Trace:**

  > EditFileResult in extensions/copilot/src/extension/tools/node/editFileToolResult.tsx gates diagnostics on ConfigKey.AutoFixDiagnostics, waits diagnosticsTimeout, compares the pushed diagnostics snapshot with existingDiagnostics, and immediately renders new warnings and errors into the tool result. AbstractReplaceStringTool, ApplyPatchTool, and CreateFileTool each supply a 2000 ms timeout for non-inline calls; inline chat disables this path with -1. The setting now defaults to false, which implements the narrower https://github.com/microsoft/vscode/issues/281483 outcome but leaves this enabled path unchanged. The uncertainty starts at the conversation lifecycle boundary: diagnostics could be surfaced after an edit batch, when the model switches away from editing, or after it attempts to finish, and those choices differ in visible latency and whether the model produces a premature summary. Keep ordinary edit result/error semantics, inline-chat behavior, and notebook exclusions outside the redesign.
- **Open decisions:**
  - At which user-observable lifecycle point should newly introduced diagnostics reach the model: after an edit batch, when it switches from editing to another action, or when it attempts to finish the turn?
  - If diagnostics arrive after the model attempts to finish, should VS Code automatically continue the agent so it can correct them, or present the errors without starting another model step?
