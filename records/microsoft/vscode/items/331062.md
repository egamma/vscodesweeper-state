# Issue #331062 — Custom Endpoint: switching an existing Chat Completions conversation to Responses API produces invalid input payload

[https://github.com/microsoft/vscode/issues/331062](https://github.com/microsoft/vscode/issues/331062)

## Summary

Still reproduces in current main: when a conversation's history is replayed to a Responses-API endpoint, assistant turns are emitted as `{ type: 'output_text', text }` with no `annotations` field, which strict validators (Azure AI Foundry's /openai/v1/responses) reject with exactly the reported error. Keep open — a maintainer already engaged in the thread, and the narrow payload defect is real regardless of the broader 1:1-translation discussion.

## Change summary

Switching an existing Chat Completions conversation to a Responses-API custom endpoint produces a request whose assistant history content parts are missing the `annotations` property, so the endpoint returns 400 invalid_payload.

## Best solution

Emit spec-compliant assistant content when converting history for the Responses API — `rawContentToResponsesAssistantContent` in extensions/copilot/src/platform/endpoint/node/responsesApi.ts should produce `output_text` parts with `annotations: []` (and must not add `annotations` to user `input_text` parts), so BYOK endpoints that validate the schema strictly accept replayed Chat Completions history.

## Evidence

- **root cause in source:** extensions/copilot/src/platform/endpoint/node/responsesApi.ts:620 `rawContentToResponsesAssistantContent` returns `Pick<OpenAI.Responses.ResponseOutputText, 'type' | 'text'>` — literally `{ type: 'output_text', text: part.text }` — deliberately dropping `annotations`. These parts are pushed as assistant `message` items in `rawMessagesToResponseAPI` (same file, ~line 428, with the comment that the SDK's ResponseOutputMessage type requires response-only fields).
- **schema expectation:** The Responses `output_text` content part carries `annotations`; the repo's own tests model it that way — extensions/copilot/src/platform/endpoint/node/test/responsesApi.spec.ts:1997+ uses `{ type: 'output_text', text: ..., annotations: [], logprobs: [] }`. That matches the reporter's error `Required property 'annotations' is missing` at `input[N].content[0].annotations` on the assistant positions (input[3], input[5], input[10], …).
- **why fresh chats work:** A first request to the Responses endpoint has no prior assistant text to replay; only replayed Chat Completions assistant turns go through the `output_text` path, which matches the reporter's control test (fresh conversation → 200, switched conversation → 400).
- **reporter's counter-test:** Adding `annotations: []` to every content part yielded `Unknown parameter: input[0].content[0].annotations` — input[0] is a user `input_text` part, where the field is not allowed. That is consistent with the fix being scoped to assistant `output_text` parts only.
- **maintainer engagement:** https://github.com/microsoft/vscode/issues/331062#issuecomment-5318085311 — a team member notes the chat-completions↔responses translation is not 1:1 and asked for the use case; the reporter replied that separate per-apiType endpoint groups still fail in a single conversation, so the payload defect stands.
- **no fix on main:** The conversion in responsesApi.ts on current main still omits `annotations`; `rg` shows line 624 is the only outgoing `output_text` construction and no post-processing adds the field.
