# Issue #327109 — Copilot Chat can invoke an MCP tool before its adapter is registered (undefined.invoke)

[https://github.com/microsoft/vscode/issues/327109](https://github.com/microsoft/vscode/issues/327109)

## Summary

Traced a genuine, still-open race in LanguageModelToolsService#invokeTool: the tool implementation is checked once, but several awaits (hook resolution, prepareToolInvocation, confirmation) intervene before it's actually invoked, and MCP's tool-sync contribution can dispose/re-register that same tool in between, leaving a stale entry whose `impl` was cleared to undefined.

## Change summary

An MCP tool call can throw `Cannot read properties of undefined (reading 'invoke')` when the tool's implementation is torn down and re-registered between the pre-invocation checks and the actual invoke call.

## Best solution

Re-fetch (or otherwise pin) the tool/impl reference from `this._tools` immediately before the `tool.impl.invoke(...)` call at languageModelToolsService.ts:723 (and the fallback path at line ~704-716), rather than trusting the object captured earlier in the function, since McpLanguageModelToolContribution's `_syncTools` can dispose and recreate a tool's registration (`existing.store.clear(); registerTool(...)`) concurrently while a call is in flight.

## Evidence

- **invoke call site:** src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts:723 calls `tool.impl.invoke(...)` using the `tool` local captured at line 575, well after the initial `!tool.impl` guard at line 580 — several `await`s (prepareToolInvocationWithHookResult, resolveAutoConfirmFromHook, dialog confirm) occur in between.
- **impl clearing on dispose:** registerToolImplementation (languageModelToolsService.ts:348-362) returns a disposer that sets `entry.impl = undefined` on the *same* entry object stored in `_tools`, without removing the map entry.
- **MCP re-registration race:** src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts:162-169: when a tool's definition changes, `existing.store.clear()` disposes the old registration (clearing impl) then `registerTool` re-registers a fresh implementation — this can race with an in-flight invokeTool call holding a stale `tool` reference.
- **reporter symptoms match:** First-chat MCP tool calls intermittently fail in the same 2ms window right after the MCP server publishes its tool list (initialize -> tools/list), consistent with a tool-sync update racing the very first invocation.
