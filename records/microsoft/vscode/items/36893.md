# Issue #36893 — Git - Support to compare with arbitrary commit instead of the current HEAD

[https://github.com/microsoft/vscode/issues/36893](https://github.com/microsoft/vscode/issues/36893)

## Summary

Keep open: current built-in comparisons do not provide persistent working-editor annotations against a selected branch, tag, or commit. The request has substantial demand, and neither the newer decoration request nor the extension API proposal is a valid canonical for this re-reviewed item.

## Change summary

Allow Git change annotations to use a user-selected reference so committed feature work remains visible while editing.

## Best solution

Provide an opt-in comparison baseline for working-editor annotations while preserving default local-change behavior. Resolve whether Explorer annotations participate, given the earlier maintainer objection to changing their working-tree status semantics.

## Plan brief

- **Likely files:** `extensions/git/src/quickDiffProvider.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/commands.ts`, `extensions/git/src/fileSystemProvider.ts`, `extensions/git/src/decorationProvider.ts`, `extensions/git/package.json`
- **Validation:** In a disposable test repository, create a base commit, branch, modify a file, and commit the modification. Select the base reference and verify that ordinary working-editor gutters still show the committed delta; make another edit and verify both committed and uncommitted changes remain represented. Return to the default comparison and verify existing local/staged annotations are unchanged. Check Explorer behavior, reference movement, and reload persistence against the maintainer-approved contract.
- **Behavior:**

  > Users working on multi-commit features should be able to view inline change annotations against a selected branch, tag, or commit while continuing to edit normal working files. Committing feature work must not erase its annotations relative to that selected baseline. Existing comparison editors are not a substitute for this editing experience. Acceptance includes committed and uncommitted deltas against the selected reference and unchanged default local/staged behavior when the comparison is disabled. Explorer participation and selection lifetime require explicit scope decisions.
- **Trace:**

  > GitQuickDiffProvider.provideOriginalResource in extensions/git/src/quickDiffProvider.ts uses an empty Git ref, and StagedResourceQuickDiffProvider uses HEAD for staged files; extensions/git/src/repository.ts registers both providers. Git reference comparisons in extensions/git/src/commands.ts instead open separate diff editors, and extensions/git/package.json exposes those commands without an arbitrary-reference annotation selector. GitFileSystemProvider in extensions/git/src/fileSystemProvider.ts reads Git resources and supplies change notifications, making baseline lifetime and refresh behavior relevant to the design. GitDecorationProvider in extensions/git/src/decorationProvider.ts derives Explorer annotations independently from Git status groups. Preserve default local/staged behavior and ordinary staging semantics; comparison annotations must not silently redefine them. The unmerged https://github.com/microsoft/vscode/pull/39117 documents objections to changing Explorer status decorations. https://github.com/microsoft/vscode/issues/169012 is a related extension-API path, while the newer https://github.com/microsoft/vscode/issues/262751 supplies additional demand rather than a canonical for this report.
- **Open decisions:**
  - Should selecting a comparison baseline affect only editor annotations, or also Explorer annotations, and how should any Explorer comparison signal remain distinguishable from working-tree status?
  - Should a selected branch or tag follow that reference as it moves, or remain pinned to the commit resolved when selected?
  - Should the comparison selection survive commits, branch switches, and window reloads, and at what repository or workspace scope?

## Evidence

- **Current annotation baseline:** extensions/git/src/quickDiffProvider.ts: GitQuickDiffProvider.provideOriginalResource returns toGitUri(uri, '', ...), while StagedResourceQuickDiffProvider returns a HEAD resource only for staged files. extensions/git/src/repository.ts registers these as the primary and secondary providers; neither accepts a user-selected branch, tag, or commit.
- **Existing capabilities are partial:** extensions/git/package.json registers git.graph.compareRef and git.timeline.compareWithSelected. In extensions/git/src/commands.ts, reference comparisons open a multi-diff editor and timeline comparisons invoke vscode.diff; they do not change the baseline of annotations in ordinary working editors. src/vs/workbench/contrib/scm/browser/scm.contribution.ts registers scm.diffDecorations and related visibility/action settings, but these control annotation presentation rather than an arbitrary Git reference.
- **Explorer scope needs a decision:** extensions/git/src/decorationProvider.ts: GitDecorationProvider.onDidRunGitStatus derives decorations from index, untracked, working-tree, and merge resource groups. In https://github.com/microsoft/vscode/pull/39117#issuecomment-347103918 the maintainer opposed changing Explorer decorations to a comparison view; https://github.com/microsoft/vscode/pull/39117#issuecomment-347220628 also identifies files absent from disk as a concern.
- **Earlier implementation did not land:** https://github.com/microsoft/vscode/pull/39117 is closed with mergedAt null. Its author removed Explorer decoration changes and the issue-closing reference in https://github.com/microsoft/vscode/pull/39117#issuecomment-347222745. The eventual closure suggested GitLens as an alternative, not a shipped implementation of this report's full scope.
