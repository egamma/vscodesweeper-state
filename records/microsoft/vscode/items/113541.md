# Issue #113541 — QuickPick API: When input value changes, first item becomes active item

[https://github.com/microsoft/vscode/issues/113541](https://github.com/microsoft/vscode/issues/113541)

## Summary

The reported focus reset remains in current source: filtering activates the first item before the extension receives the value-change event. Keep this accepted bug open; resolving the unwanted intermediate activation needs an API/behavior decision that preserves ordinary QuickPick filtering.

## Change summary

Prevent first-item activation from flashing when an extension chooses its own active QuickPick item in response to input changes.

## Best solution

Let extension-controlled QuickPicks update their active item without an intervening first-item activation, while retaining the existing default for ordinary filtered pickers. Coordinate the behavior contract with the custom-filtering API work rather than changing selection globally.

- **Behavior:**

  > An extension that controls the active QuickPick item currently sees the first item activated whenever input changes, before its onDidChangeValue listener can select the intended item. The supported extension-controlled flow should not display or emit an unwanted intermediate first-item activation. Ordinary QuickPicks must retain their default filtering and selection behavior, and value-change notifications must continue to work. Acceptance includes event-order assertions and a minimal extension demonstrating that typing no longer flashes selection onto the first item.
- **Trace:**

  > QuickPick.show() subscribes to inputBox.onDidChange and invokes doSetValue() in src/vs/platform/quickinput/browser/quickInput.ts. doSetValue() calls QuickInputList.filter(), then trySelectFirst(), before firing onDidChangeValue; the latter reaches the extension through MainThreadQuickOpen and ExtHostQuickOpen. QuickInputList.filter() in src/vs/platform/quickinput/browser/quickInputList.ts returns false only when sorting and all matching flags are disabled, so sortByLabel=false by itself does not prevent activation. The current source conclusively establishes the reset order, although its visible timing was not executed. Preserve ordinary filtering, keyboard selection, and programmatic value-change events; do not treat global removal of first-item selection as an agreed fix. The public behavior boundary remains undecided: independent activation control versus opting out of built-in filtering/selection. Related design work is https://github.com/microsoft/vscode/issues/90521 and https://github.com/microsoft/vscode/issues/83425; the maintainer discussion at https://github.com/microsoft/vscode/issues/142941#issuecomment-1054528153 prefers explicit filtering/selection control.
- **Open decisions:**
  - Should extension-controlled QuickPicks be able to retain built-in filtering and highlighting while suppressing automatic first-item activation, or should that guarantee require opting out of built-in filtering and selection together?
