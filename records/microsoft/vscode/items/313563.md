# Issue #313563 — Incremental CI/CD pipeline execution based on changed modules

[https://github.com/microsoft/vscode/issues/313563](https://github.com/microsoft/vscode/issues/313563)

## Summary

Keep open: current CI already skips some unaffected checks, but core compilation and the cross-platform test suites are not selected by affected module. This accepted Backlog request has 20 upvotes, and the broader capability remains missing.

## Change summary

Select PR build, analysis, and test work from changed files and affected dependencies while retaining necessary general validation.

## Best solution

Extend the existing conservative change-selection infrastructure incrementally, using verified dependency boundaries rather than assuming a workbench change cannot affect other areas. Preserve required-check reporting and full validation when impact cannot be determined.

- **Validation:** For an agreed first module boundary, exercise synthetic PR file lists covering isolated changes, shared dependencies, renames, and incomplete or failed lookup. Then compare representative PR check runs: only proven-unaffected work is skipped, affected checks still execute, and required statuses remain satisfied.
- **Behavior:**

  > PRs should avoid build and test work that their changes demonstrably cannot affect, reducing contributor wait time without weakening regression detection. Selection must include dependent consumers, not merely tests colocated with changed files. Shared or uncertain changes must retain broad validation, and skipped work must not leave required status checks pending.
- **Trace:**

  > The current .github/actions/detect-changes/detect.ts exports detectChanges with three path-rule outputs, consumed by selected jobs in .github/workflows/pr.yml. Core compilation and the cross-platform reusable test workflows remain outside that selection. Agent Host E2E has a separate detector demonstrating narrower suite selection and conservative fallback. The unresolved technical boundary is how to establish safe affected-consumer coverage for core modules across build, analysis, and test environments; directory isolation alone does not establish independence. Preserve existing failure fallbacks and required-check behavior, and build on the current mechanisms rather than treating the request as entirely unimplemented.
