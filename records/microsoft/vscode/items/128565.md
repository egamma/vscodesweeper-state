# Issue #128565 — [semantic highlighting] Source language suffix should be added to semantic token fallback scopes when looked up

[https://github.com/microsoft/vscode/issues/128565](https://github.com/microsoft/vscode/issues/128565)

## Summary

This team-authored Backlog request identifies a real semantic-token theming gap that remains relevant, but the proposed language-ID suffix behavior is not generally valid because language IDs and TextMate suffixes can differ. The C/C++ workaround addresses that extension's immediate need without providing the missing core mapping mechanism.

## Change summary

Allow semantic-token fallback scope resolution to match language-specific TextMate theme rules.

## Best solution

Define an explicit language-to-TextMate-suffix mapping in the `semanticTokenScopes` contribution contract, then incorporate that mapping into semantic-token fallback theme matching without changing existing generic fallback behavior.

## Plan brief

- **Likely files:** `src/vs/platform/theme/common/tokenClassificationRegistry.ts`, `src/vs/workbench/services/themes/common/colorThemeData.ts`
- **Validation:** Add semantic-token theming tests showing that an explicitly mapped suffix such as `ts` matches a language-specific TextMate rule for the `typescript` language ID, while generic fallback scopes and languages without mappings retain their current behavior.
- **Behavior:**

  > Semantic-token fallback scopes should be able to match language-specific TextMate theme rules even when the VS Code language ID differs from the TextMate suffix. Existing generic fallback matching must remain unchanged, and extensions must not need to duplicate every fallback scope for each supported language. Acceptance should cover a differing pair such as `typescript` and `ts`, an identity mapping, and a language with no mapping.
- **Trace:**

  > The issue establishes that fallback TextMate scopes currently lack a general language-suffix mapping; https://github.com/microsoft/vscode/issues/128565#issuecomment-879748331 specifically rules out blindly appending the VS Code language ID because `typescript` and `ts` differ. The likely contract surface is the semantic-token scope contribution registry in `src/vs/platform/theme/common/tokenClassificationRegistry.ts`, with matching performed by theme resolution in `src/vs/workbench/services/themes/common/colorThemeData.ts`. The C/C++ extension worked around the gap by declaring per-language scopes in https://github.com/microsoft/vscode-cpptools/pull/7829; that workaround must not be mistaken for a core fix or broken by the eventual design. The uncertainty starts at the public mapping contract and at whether mapped language-specific lookup supplements or precedes generic fallback matching.
- **Open decisions:**
  - Should the public contribution map each VS Code language ID to one TextMate suffix or permit multiple suffixes?
  - Should a mapped language-specific scope be tried before the generic fallback scope, or should both participate with existing TextMate specificity rules?
