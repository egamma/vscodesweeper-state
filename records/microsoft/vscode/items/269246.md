# Issue #269246 — [Accessibility] Expose lines numbers so that Windows 11 Voice access is able to see them for navigation

[https://github.com/microsoft/vscode/issues/269246](https://github.com/microsoft/vscode/issues/269246)

## Summary

Keep this accepted accessibility request open: current source still hides the line-number gutter from accessibility APIs, and existing Go to Line navigation does not provide directly addressable Voice Access targets. The request reached 20 upvotes and needs Windows-specific interaction design and validation, not a staleness close.

## Change summary

Expose editor line numbers so Windows 11 Voice Access users can navigate to code by line number.

## Best solution

Provide a supported, discoverable line-navigation interaction for Windows Voice Access without degrading existing screen-reader navigation or editor performance. First establish which accessibility semantics Voice Access actually recognizes and whether the interaction must reach off-screen lines.

## Plan brief

- **Likely files:** `src/vs/editor/browser/viewParts/lineNumbers/lineNumbers.ts`, `src/vs/editor/browser/viewParts/margin/margin.ts`, `src/vs/editor/browser/view/viewLayer.ts`, `src/vs/editor/browser/view/viewOverlays.ts`, `src/vs/editor/browser/view.ts`, `src/vs/workbench/contrib/codeEditor/browser/quickaccess/gotoLineQuickAccess.ts`
- **Validation:** On Windows 11 with Voice Access enabled, open a long file with absolute line numbers and inspect the editor using Accessibility Insights or Inspect.exe. Verify that the agreed voice interaction moves the caret to the requested model line, still works after scrolling and with wrapped or folded content, and does not degrade existing NVDA navigation or normal gutter interactions. Explicitly test an off-screen target if that scope is accepted.
- **Behavior:**

  > Windows 11 Voice Access users want to navigate code by line number without relying on a multi-step keyboard-driven Go to Line workflow. The accepted interaction should reliably place the caret at the requested model line and return editing focus. Line identities must remain correct after scrolling, wrapping, and folding. Existing screen-reader navigation, gutter interactions, and large-file responsiveness must remain intact; native recognition of the exact phrase 'go to line X' is not yet established.
- **Trace:**

  > LineNumbersOverlay.prepareRender in src/vs/editor/browser/viewParts/lineNumbers/lineNumbers.ts renders only the visible range and converts view positions to model line numbers. src/vs/editor/browser/view.ts nests this overlay inside MarginViewOverlays and Margin; Margin and the underlying ViewLayer both mark their DOM containers aria-hidden. Existing workbench.action.gotoLine in src/vs/workbench/contrib/codeEditor/browser/quickaccess/gotoLineQuickAccess.ts provides a separate input-based navigation path, not accessible gutter targets. These facts establish a missing exposure path but do not establish which UIA semantics Windows Voice Access will recognize or invoke. The suggestions at https://github.com/microsoft/vscode/issues/269246#issuecomment-3634093716 are untested AI advice, not a settled implementation contract. Preserve existing screen-reader behavior, line-number display modes, and editor virtualization; investigate Windows behavior before assuming that removing aria-hidden or adding a label is sufficient.
- **Open decisions:**
  - Must voice navigation reach arbitrary off-screen model lines, or is direct targeting of currently visible gutter lines sufficient for the first supported experience?
  - Is a discoverable Voice Access target such as 'click Line 50' acceptable, or does the feature require the exact phrase 'go to line 50'?
