# Issue #198451 — Editor tab tooltips for TextDocumentContentProvider schemes have backslashes on Windows and don't show the scheme

[https://github.com/microsoft/vscode/issues/198451](https://github.com/microsoft/vscode/issues/198451)

## Summary

The reported Windows formatting remains source-reproducible on current main: an unformatted custom-scheme URI is converted through `URI.fsPath`, dropping the scheme and normalizing separators as an OS path. `resourceLabelFormatters` provides an extension workaround, but the default editor-tooltip behavior remains incorrect and the existing `bug` triage rules out a judgment close.

## Change summary

Editor-tab tooltips should not display unformatted `TextDocumentContentProvider` URIs as Windows file paths with the scheme removed.

## Best solution

Define a safe default label for custom-scheme resources that preserves URI identity in editor tooltips while continuing to honor registered `resourceLabelFormatters`; first decide whether that fallback should apply only to editor long titles or consistently across all label-service consumers.

## Evidence

- **source reproduction:** The tab hover uses `editor.getTitle(Verbosity.LONG)` in `src/vs/workbench/browser/parts/editor/editorTabsControl.ts`; `AbstractResourceEditorInput.longTitle` delegates to `labelService.getUriLabel` in `src/vs/workbench/common/editor/resourceEditorInput.ts`.
- **root cause:** For a scheme without a registered formatter, `LabelService.doGetUriLabel` in `src/vs/workbench/services/label/common/labelService.ts` calls `getPathLabel`; `src/vs/base/common/labels.ts` then reads `resource.fsPath` and normalizes it with the target OS path library. On Windows this necessarily removes `my-super-scheme:` and converts `/a/b/c/file.dart` to backslash-separated path text.
- **existing workaround:** The issue discussion confirms that extensions can contribute `resourceLabelFormatters`, and the current extension point supports `${scheme}`, `${authority}`, and `${path}`. That workaround requires every provider to opt in and does not correct the default fallback reported here.
- **canonical search:** https://github.com/microsoft/vscode/issues/202678 is open but younger and concerns leading separators after an explicit formatter is registered, not this issue's unformatted editor-tooltip symptom. The older https://github.com/microsoft/vscode/issues/114234 is closed and addressed a specific built-in pseudofile scheme through formatter registration, so neither is a valid canonical duplicate under the re-review rules.
