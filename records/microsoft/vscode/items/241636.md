# Issue #241636 — Lifecycle Management VSCode snap to core24 ::  Java 21 applications crashing when run from inside VSCode

[https://github.com/microsoft/vscode/issues/241636](https://github.com/microsoft/vscode/issues/241636)

## Summary

Keep open while the linked Snap fixes are reviewed: multiple reporters confirm host applications encounter incompatible core20 libraries, and current main still packages against core20. An open PR explicitly targets this issue, but no completed fix is established.

## Change summary

Prevent applications launched from the Snap-installed VS Code integrated terminal from loading incompatible Snap runtime libraries instead of their host-system libraries.

## Best solution

Review and coordinate the existing Snap packaging PRs, then verify that Java 21 applications on Ubuntu 24.04 run and save preferences without the reported symbol lookup failure. A newer Snap base should not be treated as sufficient without checking host-library isolation on the reported launch path.

## Evidence

- **Reported trigger and independent confirmation:** https://github.com/microsoft/vscode/issues/241636 reports Java 21 launched with mvn exec:java from the integrated terminal failing during preference saving with /snap/core20/current/lib/x86_64-linux-gnu/libpthread.so.0: undefined symbol: __libc_pthread_init, version GLIBC_PRIVATE. The same application works from GNOME Terminal and the .deb installation. Comments dated 2025-03-29 and 2025-11-05 independently report related host-application failures; the former includes the same symbol error and a host libcanberra preload workaround. Reproduction status reflects the discussion, not execution in this macOS checkout.
- **Current packaging and environment handling:** resources/linux/snap/snapcraft.yaml still declares base: core20, stages libcanberra-gtk3-module, and references core20 in the crashpad RPATH and cleanup part. resources/linux/snap/electron-launch also invokes core20 GLib helpers and exports Snap-specific desktop environment variables. src/vs/platform/environment/electron-main/environmentMainService.ts already provides restoration of variables marked _VSCODE_SNAP_ORIG; these existing safeguards do not establish that the reporter's dynamically loaded library path is fixed.
- **Open fixing PR:** https://github.com/microsoft/vscode/pull/298237 was verified OPEN and its body explicitly contains Fixes #241636. It proposes upgrading the Snap base to core22 alongside launcher, process-environment, and packaging changes. This is an existing implementation candidate, not a merged fix, and precludes competing agent implementation.
- **Alternative packaging work and maintainer interest:** https://github.com/microsoft/vscode/pull/338607 was verified OPEN and proposes core24 by default with selectable core22 builds. Its description explicitly distinguishes base migration from separate terminal-environment work and notes outstanding product-build and native-install validation. In this issue's discussion, a maintainer asked whether core22 would suffice; the September 2026 reply favors core24 and links the still-open fixing PR.
- **Merged cross-reference does not fix this behavior:** https://github.com/microsoft/vscode/pull/336359 was verified MERGED with merge commit 981b8c60abe325ad32cdebfddbf1d34ace34bd72. Its scope is retrying Snap Store HTTP 429 failures before the build lifecycle; current build/azure-pipelines/linux/build-snap.sh contains that retry logic. It does not change the runtime base or the application's library-loading outcome.
- **Canonical search:** Open-issue searches for __libc_pthread_init and snap terminal core20 found https://github.com/microsoft/vscode/issues/241174 and https://github.com/microsoft/vscode/issues/180629. Their bodies describe failure to open an external terminal and a Fedora GIO/libstdc++ module-loading warning, respectively, rather than Java or other host applications terminating with the reported pthread symbol error. Neither establishes an older canonical with the same observable symptom required for this re-reviewed item.
