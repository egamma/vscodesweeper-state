# Issue #209369 — Disassembly window cannot be themed.

[https://github.com/microsoft/vscode/issues/209369](https://github.com/microsoft/vscode/issues/209369)

## Summary

This accepted Backlog request remains necessary: current main renders disassembly as un-tokenized table text, and the existing foreground setting cannot provide processor-aware syntax highlighting. With 21 community upvotes, it should remain open for design in the debug area.

## Change summary

Allow the Disassembly view to use theme-aware syntax colors, preferably through a processor-specific assembly language mode.

## Best solution

Define how a debug adapter identifies the disassembly language or architecture, then let the built-in Disassembly view render instructions using the corresponding language tokens and active color theme while preserving its debugging controls and mixed source display.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/disassemblyView.ts`, `src/vs/workbench/contrib/debug/common/debugProtocol.d.ts`
- **Validation:** Add a debug-view test using representative disassembly for at least two architectures, verifying that instruction tokens receive language/theme-specific styling while addresses, bytes, breakpoints, current-instruction highlighting, and mixed source rows retain their existing behavior.
- **Behavior:**

  > The Disassembly view should color instruction syntax using the active VS Code theme rather than rendering every instruction in one foreground color. The selected syntax must be appropriate for the target processor when that information is available. Existing addresses, instruction bytes, source interleaving, breakpoint interaction, current-instruction highlighting, and high-contrast behavior must remain usable.
- **Trace:**

  > DisassemblyView in src/vs/workbench/contrib/debug/browser/disassemblyView.ts is a WorkbenchTable rather than a Monaco editor. InstructionRenderer concatenates address, instruction bytes, and the adapter-provided instruction into one string and assigns it with `innerText`, so editor token colors and installed assembly grammars cannot participate. The DAP shapes in src/vs/workbench/contrib/debug/common/debugProtocol.d.ts provide implementation-defined instruction text but no language or architecture identifier. The boundary is the built-in disassembly presentation and any necessary adapter-facing language-selection contract; do not replace or regress breakpoint handling, paging, mixed source rendering, or stack-frame backgrounds. https://github.com/microsoft/vscode/issues/131210 is an older closed request without a fix, while https://github.com/microsoft/vscode/issues/284771 is a newer open report and should be consolidated into this older Backlog item rather than used as its canonical.
- **Open decisions:**
  - Should instruction styling use existing language grammars and token themes, dedicated disassembly theme tokens, or a defined combination of both?
  - What public contract identifies the target architecture or assembly language when a debug adapter supplies disassembly, including the fallback when it supplies none?
  - Should extensions be able to provide processor-specific tokenization for this view, and if so, which existing language-extension capabilities should apply?

## Evidence

- **current source:** In src/vs/workbench/contrib/debug/browser/disassemblyView.ts, DisassemblyView is a custom WorkbenchTable and InstructionRenderer concatenates the address, bytes, and instruction before assigning the result through `templateData.instruction.innerText`; no tokenizer or language service is involved.
- **limited existing theming:** The view uses `editorBackground` for its table and general inherited foreground text, plus debug stack-frame background colors. This confirms the maintainer comment that `foreground` works, but it does not provide syntax-level theming or satisfy the central request.
- **protocol gap:** DebugProtocol.DisassembledInstruction in src/vs/workbench/contrib/debug/common/debugProtocol.d.ts exposes implementation-defined instruction text and bytes but no architecture or language identifier, so processor-specific grammar selection requires a product and protocol/extensibility decision.

- **older related report:** https://github.com/microsoft/vscode/issues/131210 requested the same syntax-highlighting capability but was closed only by the community upvote lifecycle, without an implementation or substantive scope decision; a closed issue cannot be the duplicate canonical.
- **newer related report:** https://github.com/microsoft/vscode/issues/284771 is open and reports the same visible lack of Disassembly-view highlighting, but it was created after this re-reviewed issue and therefore cannot serve as its canonical duplicate.
