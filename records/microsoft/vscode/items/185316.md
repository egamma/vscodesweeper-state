# Issue #185316 — Command Center customization

[https://github.com/microsoft/vscode/issues/185316](https://github.com/microsoft/vscode/issues/185316)

## Summary

Keep this accepted, well-supported request open: current Command Center controls do not let users add or edit arbitrary command buttons. The older related requests concern configurable menus or a separate toolbar, rather than the same Command Center-specific behavior required for a duplicate close on re-review.

## Change summary

Allow users to add and edit icon-bearing command buttons in the Command Center beside the navigation controls.

## Best solution

Provide an opt-in way to expose selected commands beside Command Center navigation while preserving the uncluttered default title bar. Agree on the customization contract with the menus owner, using the existing configurable-menu discussion as design context rather than treating it as a proven duplicate.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/titlebar/commandCenterControl.ts`, `src/vs/workbench/browser/parts/titlebar/titlebarActions.ts`, `src/vs/workbench/browser/workbench.contribution.ts`, `src/vs/workbench/services/actions/common/menusExtensionPoint.ts`
- **Validation:** After the customization contract is agreed, configure a built-in command and an extension-contributed command with icons; verify both appear beside Command Center navigation and invoke the intended commands. Edit or remove an entry and reload to verify the agreed persistence semantics. Confirm the default title bar remains unchanged and added actions support keyboard focus and accessible labels.
- **Behavior:**

  > Users want selected built-in or extension commands available as icon-bearing buttons beside the Command Center navigation controls, without relying on memorized shortcuts or repeated Command Palette searches. The finished capability should allow adding and editing those entries and retain the existing default appearance when no customization is selected. Acceptance should cover command invocation, icon display, editing/removal, the agreed persistence behavior, and keyboard-accessible labeled actions.
- **Trace:**

  > CommandCenterControl in src/vs/workbench/browser/parts/titlebar/commandCenterControl.ts renders MenuId.CommandCenter through MenuWorkbenchToolBar and explicitly disables item hiding. Existing back/forward actions contribute to that menu in src/vs/workbench/browser/parts/editor/editorActions.ts. src/vs/workbench/browser/workbench.contribution.ts and titlebarActions.ts provide visibility controls, while editorActionsLocation relocates existing editor actions rather than supplying arbitrary Command Center entries. The public extension menu registry in src/vs/workbench/services/actions/common/menusExtensionPoint.ts does not expose CommandCenter. The remaining uncertainty is the supported user-facing customization contract, not whether the current visibility settings satisfy the request. Preserve default navigation, command launching, and title-bar layout behavior; a new standalone toolbar is outside this report's stated scope. The discussion at https://github.com/microsoft/vscode/issues/9285 is relevant design context, as noted in https://github.com/microsoft/vscode/issues/185316#issuecomment-1594471778, but does not by itself settle this surface's contract.
- **Open decisions:**
  - Should users configure Command Center entries directly through a built-in command-selection/configuration surface, or should customization be supplied through a supported extension menu contribution point?
  - Should the selected command buttons be personal configuration shared across workspaces, workspace-specific configuration for team workflows, or support both?
