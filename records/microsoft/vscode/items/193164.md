# Issue #193164 — Editor is broken when opening files with >120M lines

[https://github.com/microsoft/vscode/issues/193164](https://github.com/microsoft/vscode/issues/193164)

## Summary

The limitation remains on current main: editor scrolling still coerces dimensions to signed 32-bit integers, while no broader issue owns this specific failure. Keep it open under discussion to decide between supporting larger dimensions and rejecting such files gracefully.

## Change summary

Prevent files whose rendered height exceeds the signed 32-bit range from opening into an editor with unusable scrolling.

## Best solution

Detect this limit before the editor becomes unusable and either provide correct scrolling or fail gracefully with a clear explanation; preserve the existing fast integer path unless telemetry justifies its broader replacement.

## Plan brief

- **Likely files:** `src/vs/base/common/scrollable.ts`, `src/vs/base/test/common/scrollable.test.ts`, `src/vs/editor/common/viewLayout/viewLayout.ts`, `src/vs/editor/common/model/textModel.ts`
- **Validation:** Add a unit case in src/vs/base/test/common/scrollable.test.ts using a scrollHeight above 2^31 and an editor-level test confirming the chosen behavior is navigable or explicitly rejected rather than wrapped to a non-positive height.
- **Behavior:**

  > Opening a text file whose rendered height exceeds the signed 32-bit range must not leave the editor showing its first viewport with broken scrolling. The file should either remain navigable across its full line range or be rejected before opening with a clear explanation. Ordinary files and existing large-file optimizations must retain their current behavior and performance characteristics.
- **Trace:**

  > EditorScrollable in src/vs/editor/common/viewLayout/viewLayout.ts creates Scrollable with forceIntegerValues enabled. ScrollState in src/vs/base/common/scrollable.ts then applies bitwise `| 0` coercion to scrollHeight and scrollTop, which converts dimensions beyond the signed 32-bit range into wrapped values. TextModel in src/vs/editor/common/model/textModel.ts already classifies large models for expensive operations, but that classification does not cover rendered-height overflow. The issue's sole maintainer comment favors graceful failure plus telemetry before replacing the small-integer path. The boundary is the extreme-dimension handling: normal scrolling semantics and performance must not regress.
- **Open decisions:**
  - Should VS Code support scroll dimensions above the signed 32-bit range, or reject models whose line count and configured line height exceed it?
  - If the file is rejected, at which model/editor boundary should detection occur so the user receives a clear message before a broken editor is created?
  - What privacy-safe telemetry is needed to measure how often this threshold is encountered before reconsidering the small-integer optimization?

## Evidence

- **current source:** src/vs/editor/common/viewLayout/viewLayout.ts constructs the editor Scrollable with forceIntegerValues: true, and src/vs/base/common/scrollable.ts:65-71 still applies `| 0` to scrollHeight and the other dimensions, wrapping values above 2,147,483,647.
- **existing optimization:** src/vs/editor/common/model/textModel.ts detects large models for tokenization, synchronization, and heap operations, but it has no check for rendered height exceeding the scrollable's signed 32-bit range.
