# Issue #193164 — Editor is broken when opening files with >120M lines

[https://github.com/microsoft/vscode/issues/193164](https://github.com/microsoft/vscode/issues/193164)

## Summary

Keep open in the editor backlog: the issue identifies a concrete 32-bit overflow boundary for extremely large files, and the maintainer response favors graceful failure plus telemetry before considering a broad move away from small integers.

## Change summary

Opening files with more than roughly 120 million short lines overflows editor scroll dimensions, leaving the viewport rendered but scrolling and the scrollbar unusable.

## Best solution

Add a bounded editor-core safeguard that detects unsupported document dimensions and fails gracefully, then use privacy-compliant telemetry to measure occurrence before deciding whether the scrolling and layout stack should support dimensions beyond the signed 32-bit range.

## Plan brief

- **Likely files:** `src/vs/base/common/scrollable.ts`, `src/vs/editor/common/viewLayout/viewLayout.ts`, `src/vs/editor/browser/viewParts/scrollbar/scrollbar.ts`
- **Validation:** Create or extend editor layout/scroll tests with dimensions crossing 2,147,483,647 and verify the chosen graceful-failure behavior occurs without wrapped scroll positions or a broken scrollbar.
- **Behavior:**

  > When a document's rendered dimensions exceed the editor's supported numeric range, VS Code must not present a viewport whose scrolling and scrollbar silently wrap or become unusable. The product should expose a clear, graceful outcome for the unsupported file while ordinary and currently supported large files remain unchanged. Acceptance should include a deterministic boundary test around 2,147,483,647 rendered pixels and confirmation that no wrapped scroll state is produced.
- **Trace:**

  > The report traces the failure to 32-bit coercions such as `| 0` in the base scrolling/layout path, with the concrete trigger of 120,000,000 lines at an 18px line height. The maintainer response at https://github.com/microsoft/vscode/issues/193164#issuecomment-1721184142 explicitly favors graceful failure and telemetry before replacing small-integer coercions broadly. https://github.com/microsoft/vscode/issues/167719 is related to large text storage but does not subsume the scroll-dimension behavior. Keep the initial boundary narrow: do not globally replace every `| 0` coercion or promise full support for 120-million-line editing until measurements justify that architectural cost.
- **Open decisions:**
  - What user-visible behavior should VS Code use when the document's rendered height exceeds the supported scroll range: refuse the editor, open a constrained large-file view, or show the first viewport with an explicit unsupported-size message?
  - Should telemetry record only that the supported dimension was exceeded, or also bounded size buckets needed to evaluate broader large-file support?

## Evidence

- **confirmed diagnosis:** The issue provides the precise overflow boundary: 120,000,000 lines at an 18px line height produce a 2,160,000,000px render height, beyond signed int32 range, while editor/base scrolling code uses `| 0` coercions.
- **maintainer direction:** https://github.com/microsoft/vscode/issues/193164#issuecomment-1721184142 proposes graceful failure and telemetry to establish how often files above this scale are opened before moving away from small-integer representations.
- **related investigation:** The open https://github.com/microsoft/vscode/issues/167719 explores an ArrayBuffer backend for editor text contents, but it does not clearly own or resolve this issue's scroll-dimension overflow and graceful-failure requirement.
