# Issue #19254 — Git Diff Doesn't Show Changes in New Line Characters

[https://github.com/microsoft/vscode/issues/19254](https://github.com/microsoft/vscode/issues/19254)

## Summary

Keep open: current diff computation still omits line-ending differences, and the implementation proposal was closed without merging. This remains a well-supported Backlog request and the maintainer-designated consolidation point.

## Change summary

Make CRLF-versus-LF changes visible in the diff editor, including when ordinary line content is unchanged.

## Best solution

Provide opt-in EOL-difference visibility in the diff editor without cluttering normal Git checkout comparisons. Settle whether initial support is a file-level EOL indicator or per-line markers, and explicitly define the limits for mixed line endings.

Repeat with actual text edits, both whitespace-toggle states, and a mixed-EOL fixture according to the agreed scope; confirm viewing the diff does not alter file bytes.
- **Behavior:**

  > Users reviewing a Git change that only converts CRLF to LF, or vice versa, must be able to identify that difference without using command-line git diff. EOL visibility should be opt-in and disabled by default, following the maintainer's guidance on checkout normalization. Acceptance must cover EOL-only changes and EOL changes alongside ordinary text edits without conflating them with leading/trailing whitespace. The plan must define what is shown for mixed-EOL files and avoid implying that normalized model data preserves every original separator.
- **Trace:**

  > EditorWorker.computeDiff in src/vs/editor/common/services/editorWebWorker.ts compares separator-free getLinesContent() arrays, and _modelsAreIdentical compares line content without EOL metadata. The whitespace setting in src/vs/editor/common/config/editorConfigurationSchema.ts and the helper in src/vs/workbench/contrib/codeEditor/browser/diffEditorHelper.ts do not supply EOL visibility. Model-wide EOL comparison can distinguish uniform CRLF/LF files, but PieceTreeTextBufferFactory in src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeTextBufferBuilder.ts normally normalizes mixed separators, so exact per-line reporting reaches a different data boundary. https://github.com/microsoft/vscode/pull/274988 is a closed, unmerged implementation lead; its maintainer discussion settles the opt-in default, not the full display contract. Preserve existing checkout comparisons, ordinary whitespace handling, staging semantics, and global text-model normalization unless a separate scope decision explicitly requires more. https://github.com/microsoft/vscode/issues/127 and https://github.com/microsoft/vscode/issues/12223 are related normalization/rendering work, not duplicate owners. The encoding/BOM request consolidated from https://github.com/microsoft/vscode/issues/5118 should remain explicitly accounted for rather than being declared solved by EOL-only support.
- **Open decisions:**
  - Should initial EOL visibility identify the two model-wide line-ending styles, or mark individual changed line terminators in the diff?
  - Must initial support faithfully expose changes in mixed-EOL files, or is uniform CRLF/LF detection an explicitly limited first increment?
