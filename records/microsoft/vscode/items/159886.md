# Issue #159886 — `DebugService` has high cost

[https://github.com/microsoft/vscode/issues/159886](https://github.com/microsoft/vscode/issues/159886)

## Summary

The original optimization was intentionally partial and the issue was reopened after it merged. Current main still constructs the large DebugService dependency graph when common editor contributions access its model and view model, so the remaining startup-performance debt is still necessary.

## Change summary

Reduce the cost and critical-path timing of DebugService creation when opening an ordinary text editor.

## Best solution

Profile the current simple-editor startup path, then separate or defer DebugService collaborators that are not required before debugging while preserving early breakpoint restoration. Treat this as a measured, incremental performance refactor rather than another speculative lazy wrapper.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugService.ts`, `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`, `src/vs/workbench/contrib/debug/browser/callStackEditorContribution.ts`, `src/vs/workbench/contrib/debug/browser/breakpointEditorContribution.ts`, `src/vs/workbench/contrib/debug/browser/debugEditorContribution.ts`, `src/vs/workbench/contrib/debug/common/debug.ts`
- **Validation:** Run `scripts/code.sh --prof-startup` with a clean temporary profile while opening a simple text file with only Explorer visible; compare profiles before and after so DebugService construction is absent from the editor-creation critical path, then verify breakpoints and debug decorations are available without visible delayed initialization.
- **Behavior:**

  > Opening an ordinary text editor without starting or exposing debug UI must not synchronously construct the expensive DebugService dependency graph on the editor-creation critical path. Debug decorations, inline values, breakpoint restoration, and debug-session startup must retain their existing behavior when used. Acceptance requires a clean-profile startup trace demonstrating that DebugService construction no longer accounts for the reported editor-creation cost, without delaying visible breakpoint restoration.
- **Trace:**

  > IDebugService is registered as delayed in src/vs/workbench/contrib/debug/browser/debug.service.contribution.ts, but the editor contributions registered in src/vs/workbench/contrib/debug/browser/debug.contribution.ts invoke getModel(), getViewModel(), or getAdapterManager() during initialization. Those method calls instantiate DebugService, whose constructor in src/vs/workbench/contrib/debug/browser/debugService.ts eagerly creates the adapter/configuration managers, storage, model, telemetry, view model, and task runner. Commit 3305ea470af1f47ebfa4ec5ae7ab33b070be2e9f deferred several operations but preceded the issue's reopen and was explicitly only a first optimization. The uncertainty begins at the current profile: identify which constructor branches still dominate and define the smallest service boundary that removes them from ordinary editor creation. Preserve early breakpoint hydration and the behavior of all debug editor contributions; avoid redesigning unrelated debug-session orchestration.

## Evidence

- **partial fix and reopen:** https://github.com/microsoft/vscode/pull/162879 merged as commit 3305ea470af1f47ebfa4ec5ae7ab33b070be2e9f on 2022-10-11, closing this issue; the issue was reopened later that day because the remaining DebugService cost persisted. That pre-reopen commit cannot support an implemented-on-main close.
- **current service construction:** src/vs/workbench/contrib/debug/browser/debugService.ts still eagerly creates AdapterManager, ConfigurationManager, DebugStorage, DebugModel, DebugTelemetry, ViewModel, and DebugTaskRunner in the DebugService constructor, in addition to registering several listeners and initializing context keys.
- **current editor path:** src/vs/workbench/contrib/debug/browser/debug.contribution.ts registers three debug editor contributions for first-render/first-interaction creation. CallStackEditorContribution immediately calls debugService.getViewModel() and getModel(), while DebugEditorContribution similarly calls getViewModel() during listener registration, forcing the delayed service proxy to instantiate for a normal editor.
- **remaining lazy boundary:** src/vs/workbench/contrib/debug/browser/debugService.ts defers only the DEBUG_MEMORY_SCHEME filesystem provider through lazySetup(); the constructor's broader dependency graph remains eager once any model/view-model method is called.
- **related infrastructure:** https://github.com/microsoft/vscode/pull/162928 added delayed-service handling for direct event properties, but the current editor contributions obtain events through getModel()/getViewModel() method calls, so that optimization does not remove this construction path.
