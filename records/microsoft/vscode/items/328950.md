# Issue #328950 — Comment line rendering offset when using mixed fonts (Fira Code + Cascadia Code)

[https://github.com/microsoft/vscode/issues/328950](https://github.com/microsoft/vscode/issues/328950)

## Summary

Plausible but unconfirmed: VS Code does have a real per-token font-family/line-height customization feature (colorThemeSchema.ts `fontFamily`/`fontSize`/`lineHeight` token settings, backed by `tokenizationFontDecorationsProvider.ts`), and the CSS applied for a token-level `fontFamily` override doesn't itself adjust line height — only an explicit `lineHeight`/`fontSize` multiplier does. That's a plausible mechanism for the reported overlap, but the report doesn't include the actual settings/theme JSON used to assign Cascadia Code to comments, so it can't be verified as a genuine defect vs. a missing manual `lineHeight` compensation; asking for exact config before deciding.

## Change summary

Assigning a different font family to comment tokens (Fira Code main font, Cascadia Code for comments) causes the comment line to render with no vertical space, overlapping adjacent lines and becoming unselectable.

## Best solution

Get the reporter's exact `editor.tokenColorCustomizations`/theme rule that assigns the comment-token `fontFamily`, and confirm whether they also set a matching `lineHeight`/`fontSize` multiplier; if not, this may be `*as-designed` (per the schema, line-height auto-adjusts with `fontSize`, not bare `fontFamily`), but if a matching `lineHeight` was set and it still overlaps, that's a real editor rendering bug in the per-token font decoration path (src/vs/editor/common/model/tokens/tokenizationFontDecorationsProvider.ts / src/vs/editor/common/languages/supports/tokenization.ts) worth fixing so overlapping/unselectable lines can't occur regardless of font metric mismatch.
