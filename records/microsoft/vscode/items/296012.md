## Evidence

- **Reported trigger:** https://github.com/microsoft/vscode/issues/296012 specifies editor.foldingImportsByDefault=true, opening files, and using/import regions remaining expanded on VS Code 1.109.4. It also reports JavaScript/TypeScript failures, so attributing the entire report to the C# extensions would be premature.
- **Current editor behavior:** src/vs/editor/contrib/folding/browser/folding.ts:323-334 calls setCollapsedAllOfType(FoldingRangeKind.Imports.value, true) before updating the folding model, provided automatic import folding is enabled and _currentModelHasFoldedImports is false. This establishes the intended capability, not a reproduction of the reported failure.
- **Provider boundary:** src/vs/editor/contrib/folding/browser/syntaxRangeProvider.ts preserves each provider's range kind and accepts only ranges spanning multiple lines. extensions/typescript-language-features/src/languageFeatures/folding.ts maps TypeScript outlining spans of kind 'imports' to vscode.FoldingRangeKind.Imports. Missing or differently classified provider ranges remain a diagnostic possibility, not a proven cause.
- **State and strategy boundary:** FoldingController.restoreViewState in src/vs/editor/contrib/folding/browser/folding.ts restores state.foldedImports into _currentModelHasFoldedImports; getRangeProvider bypasses syntax providers when foldingStrategy is indentation. These paths should be distinguished from a fresh file opening before identifying a defect.
- **Canonical search:** Searches for foldingImportsByDefault and folding/import/using variants found no verified open canonical for this failure. https://github.com/microsoft/vscode/issues/40338 requests configurable initial region collapse state, while https://github.com/microsoft/vscode/issues/269857 reports unwanted collapse during error navigation; neither establishes ownership of imports failing to collapse on ordinary opening.
