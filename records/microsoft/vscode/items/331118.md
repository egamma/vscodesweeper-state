# Issue #331118 — Agent Host: first-turn config refresh leaves new chat permanently active

[https://github.com/microsoft/vscode/issues/331118](https://github.com/microsoft/vscode/issues/331118)

## Summary

Keep open: the detailed logs confirm a first-turn configuration refresh can strand an active chat, and current main retains both the destructive same-ID refresh path and a telemetry-only hang watchdog. No older issue reports the same observable symptom, and the later related reports explicitly describe different failure boundaries.

## Change summary

Prevent a first-turn customization refresh from leaving a newly materialized Agent Host chat permanently active without a response or terminal error.

## Best solution

Make first-turn configuration reconciliation preserve a usable SDK backing or terminate the turn visibly when refresh/recreation fails. Decide separately whether the existing no-progress watchdog should provide a general recovery guarantee for lost provider turns.

- **Behavior:**

  > When a new Agent Host chat's effective tools or customizations change while its first prompt is materializing, the prompt must not remain permanently active. The refresh should either complete the prompt using a valid backing session or produce one visible terminal error that clears the active state. Existing-session refreshes and successful first sends must retain their current conversation identity and behavior. Acceptance requires a deterministic test covering the first-send configuration change and proving that a terminal turn outcome is always emitted.
- **Trace:**

  > The issue's logs establish the sequence from provisional SDK-session creation through configuration divergence, destroy, failed resume, same-ID fallback creation, and a runtime disposed-handle failure with no terminal event. On current main, CopilotAgent._sendMessageOnce in src/vs/platform/agentHost/node/copilot/copilotAgent.ts computes structural restart reasons after materialization and calls _destroyLiveSession before resolving the same recorded backing. CopilotSessionLauncher.launch in src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts intentionally falls back from an empty-session resume error to createSession with the same ID. AgentHostTurnTracker._onHangWatchdogFired in src/vs/platform/agentHost/node/agentHostTurnTracker.ts reports noProgress only through telemetry. The boundary should remain the first-turn configuration-refresh lifecycle and its terminal-outcome guarantee; unrelated MCP warnings and the distinct pre-dispatch/lifecycle problems in https://github.com/microsoft/vscode/issues/332831 and https://github.com/microsoft/vscode/issues/336146 must not be folded into the fix.
- **Open decisions:**
  - When a first-turn configuration refresh cannot safely resume its newly materialized backing, should Agent Host transparently retry the prompt with a fresh backing identity, or terminate that turn with a visible error and require an explicit retry?
  - Should this issue also make the generic no-progress watchdog terminate lost provider turns after its threshold, or should the change remain limited to guaranteeing a terminal outcome in the first-turn configuration-refresh path?
