# Issue #336587 — Agent Host loses conversation context when config refresh resume falls back to createSession

[https://github.com/microsoft/vscode/issues/336587](https://github.com/microsoft/vscode/issues/336587)

## Summary

Confirmed in source: a config-driven session refresh can start `resumeSession` before the old SDK session's disconnect RPC has actually completed, because `CopilotSessionWrapper.disconnect()` races the disconnect RPC against the `session.shutdown` notification and returns on whichever settles first — matching the reporter's timeline exactly (shutdown/resume start well before the disconnect RPC and runtime-side dispose finish). This causes a spurious 'session not found' and a silent fallback to an empty `createSession` that loses the model's conversation context while the UI still shows the old transcript.

## Change summary

When Agent Host refreshes a Copilot SDK session mid-conversation (e.g. `reason=clientPluginsChanged`), resume can race the still-in-flight disconnect, land on 'session not found', and silently fall back to a fresh empty session that reconstructs zero prior turns even though the UI keeps showing the old transcript.

## Best solution

Either make the config-refresh path wait for the disconnect RPC to genuinely complete (not just the `session.shutdown` notification) before issuing `resumeSession`, and/or make the empty-session fallback rehydrate turns from the durable persisted event log (or fail visibly) instead of silently continuing with an empty model context — these are two different valid mitigations and a maintainer should pick the direction.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotSessionWrapper.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts`
- **Validation:** A resumeSession/config-refresh unit test in copilotAgent.test.ts or copilotAgentSession.test.ts that simulates a shutdown notification arriving before the disconnect RPC settles, and asserts either that resume/create no longer proceeds until the RPC truly completes, or that the fallback session's turn count still reflects the prior persisted history.
- **Behavior:**

  > When Agent Host refreshes a Copilot SDK session mid-conversation due to a config change (e.g. client-plugin change), the resulting session must not silently lose the established conversation: either resume must not be attempted until teardown has genuinely completed, or the replacement session must be rehydrated from the durable persisted event log before it is used, or the operation must fail visibly instead of continuing with an empty model context. Existing successful resume/refresh behavior (no race) must be unaffected.
- **Trace:**

  > The race lives in `CopilotSessionWrapper.disconnect()` (src/vs/platform/agentHost/node/copilot/copilotSessionWrapper.ts:84-116), which returns via `Promise.race([disconnectPromise, shutdown.p])` as soon as either the disconnect RPC or the `session.shutdown` notification settles — the runtime's own teardown (session.dispose) only completes when the RPC actually finishes, so a caller that treats the race's resolution as 'safe to resume' can start `resumeSession` too early. `_destroyLiveSession` (copilotAgent.ts:5499) and its callers (e.g. the `_resumeTurnOnce`/refresh path around copilotAgent.ts:3488-3492) await this racy disconnect before immediately resuming. `copilotSessionLauncher.ts:667-686`'s `shouldCreateEmptySessionAfterResumeError` allow-list is the point where a resume failure becomes an unconditional `createSession` fallback with no rehydration of the 304 previously-persisted events, only the new session's own 3 startup events. The boundary: do not change `disconnect()`'s behavior for ordinary dispose (where racing with shutdown is intentional to avoid hanging), only the refresh-then-resume call path; and do not remove the allow-list's safety intent (only true empty sessions should fall back) — the fix should either close the race window before resume or make the fallback safe by using persisted history. Related prior fixes for similar teardown/resume races are referenced by the reporter as issues #327125 and #328590, and issue #331118 for a related first-turn variant — I could not verify these via `gh` (unauthenticated in this environment) so their current state is unconfirmed; the maintainer should check them for precedent before choosing a design.
- **Open decisions:**
  - Should the config-refresh path wait for the disconnect RPC's true completion (not the shutdown notification) before resuming, and if so, with what timeout/fallback if the RPC never settles?
  - Should the empty-session fallback in `shouldCreateEmptySessionAfterResumeError`/`createSession` rehydrate turns from the durable persisted event log before proceeding, rather than accepting a 0-turn reconstruction as success?
  - If neither mitigation is fully reliable, should Agent Host surface a visible error/notice to the user instead of silently continuing with an empty model context, and how does that interact with the UI still showing the old transcript?

## Evidence

- **racy disconnect wait:** src/vs/platform/agentHost/node/copilot/copilotSessionWrapper.ts lines 84-116: `disconnect()` does `Promise.race([this._disconnectPromise, this._shutdown.p])`, so a caller awaiting disconnect returns as soon as the `session.shutdown` notification arrives even if the disconnect RPC (which the runtime completes teardown/dispose on) is still pending.
- **call site races resume against teardown:** src/vs/platform/agentHost/node/copilot/copilotAgent.ts `_resumeTurnOnce`/`_refreshSession`-style paths (e.g. line 3489) `await this._destroyLiveSession(entry, true)` then immediately call `_resumeSession`/`createSession` — `_destroyLiveSession` (line 5499) awaits `chatSession.destroySession()`, which bottoms out in the racy `disconnect()` above.
- **unsafe fallback:** src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts lines 667-686: on an allow-listed 'session not found'-shaped resume error, the launcher falls back to `createSession` with the same id and proceeds even though the replacement session reconstructs 0 turns from only its own 3 startup events.
- **reporter's causal timeline:** The issue's captured log shows `shutdown received` and `disconnect wait completed` at 08:38:09.529, resume starting at 08:38:09.532, but the actual `disconnect RPC completed`/runtime `session.dispose` only finishing at 08:38:09.877-878 — i.e. resume began before teardown truly finished, exactly matching the race in the source.
