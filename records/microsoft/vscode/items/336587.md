# Issue #336587 — Agent Host loses conversation context when config refresh resume falls back to createSession

[https://github.com/microsoft/vscode/issues/336587](https://github.com/microsoft/vscode/issues/336587)

## Summary

The defect is present on current main: configuration refresh can treat an early shutdown notification as completed teardown, then classify the resulting `Session not found` resume failure as proof of empty history and continue in a newly created contextless session. This team-authored, source-confirmed Agent Host bug should remain open.

## Change summary

Preserve an established Copilot conversation when a configuration-driven SDK-session refresh cannot resume its previous runtime session.

## Best solution

Separate teardown completion from permission to discard conversation context: a refresh of a known nonempty session must never use the empty-session fallback. Either restore the replacement from durable turns or fail the send visibly while retaining the transcript and a retryable backing.

Run `./scripts/test.sh --grep "config-driven session refresh|CopilotSessionLauncher resume fallback|CopilotSessionWrapper"`.
- **Behavior:**

  > When a configuration change refreshes an established Copilot conversation, the next context-dependent follow-up must retain the earlier turns. If the runtime cannot restore that context, Agent Host must surface a terminal error and keep the conversation retryable rather than sending successfully with an empty model context. Genuinely empty sessions, including the existing Start Over case, may continue using the empty-session fallback. A shutdown notification must still prevent an indefinitely pending disconnect RPC from hanging the session.
- **Trace:**

  > CopilotAgent._sendMessageOnce in src/vs/platform/agentHost/node/copilot/copilotAgent.ts destroys and resumes the same SDK backing when ActiveClient.getRestartReason reports a structural change. CopilotSessionWrapper.disconnect in src/vs/platform/agentHost/node/copilot/copilotSessionWrapper.ts resolves on either the disconnect RPC or `session.shutdown`; this behavior came from https://github.com/microsoft/vscode/issues/327125 and must not be replaced with an unbounded RPC wait. If resume then reports `Session not found`, CopilotSessionLauncher.launch in src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts treats that text as proof of absent history and creates an empty same-ID session. The issue timeline confirms that this path replaced 304 persisted events with three startup events and zero reconstructed turns. The boundary is the established-session refresh and fallback decision; preserve genuine empty-session recreation and do not redesign general chat persistence or unrelated provider lifecycles.
- **Open decisions:**
  - When refresh resume fails for a conversation known to contain prior turns, should Agent Host rehydrate a replacement SDK session from durable turns, or fail the pending send visibly and leave restoration to a later retry?

## Evidence

- **teardown race:** src/vs/platform/agentHost/node/copilot/copilotSessionWrapper.ts:83-115 implements `disconnect()` as `Promise.race([this._disconnectPromise, this._shutdown.p])`, so callers can resume the same SDK session ID while the disconnect RPC remains pending.
- **refresh path:** src/vs/platform/agentHost/node/copilot/copilotAgent.ts:4260-4270 destroys the live session and immediately resumes the same backing during `sendMessage` when client plugins or other structural configuration changes.
- **unsafe fallback:** src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:322-341 and 667-684 classify any `-32603` message containing `Session not found` as absent history and call `createSession` with the same ID, without distinguishing an established conversation from a genuinely empty session.
- **regression coverage gap:** src/vs/platform/agentHost/test/node/copilotAgentSession.test.ts:1896-1952 explicitly verifies that shutdown may complete the wrapper wait before the disconnect RPC settles, while src/vs/platform/agentHost/test/node/copilotSessionLauncher.test.ts:898 onward independently verifies that `Session not found` triggers creation; no test composes those behaviors for a nonempty refresh.
- **related precedent:** https://github.com/microsoft/vscode/issues/327125 documents why shutdown must unblock teardown when the disconnect RPC drains slowly, so merely waiting unboundedly for that RPC would regress the prior hang fix. https://github.com/microsoft/vscode/issues/331118 remains a distinct first-turn empty-session failure rather than the same observable established-history loss.
- **captured reproduction:** The supplied timeline records 304 persisted events and one reconstructed turn before refresh, followed by early shutdown, a pending disconnect RPC, `Session not found`, fallback creation, and zero reconstructed turns; the subsequent model request contained only the system message and new follow-up.
