# Issue #179235 — Menu is getting stale

[https://github.com/microsoft/vscode/issues/179235](https://github.com/microsoft/vscode/issues/179235)

## Summary

The stale native-menu state remains plausible on current main: menu enablement is rebuilt synchronously from BrowserWindow focus events, while dismissing the native modal provides no subsequent refresh if focus was sampled before the dialog closed. The newer similarly titled issue describes a different Linux custom-menu symptom and cannot be the canonical for this re-reviewed report.

## Change summary

On macOS, dismissing an extension-host failure dialog after closing Process Explorer can leave valid menu actions disabled until the window loses and regains focus.

## Best solution

Ensure the macOS application menu is refreshed with the active main window's current command enablement after the native modal is dismissed, without changing the intentional disabled-menu behavior while an auxiliary window has focus.

## Plan brief

- **Likely files:** `src/vs/platform/menubar/electron-main/menubar.ts`, `src/vs/platform/native/electron-main/nativeHostMainService.ts`, `src/vs/workbench/contrib/processExplorer/browser/processExplorer.contribution.ts`
- **Validation:** On macOS, dirty an editor backed by an extension host, open Process Explorer, terminate that extension host, close Process Explorer while the failure dialog is pending, and cancel the dialog; immediately verify that Save and other context-enabled native menu entries are enabled without cycling window focus.
- **Behavior:**

  > After an auxiliary window closes and its pending native modal is cancelled, the macOS application menu must immediately reflect the active main window's command state. A dirty editor's Save actions must remain enabled without opening another window or cycling focus. While Process Explorer or another auxiliary window actually has focus, the existing intentional restrictions on unsupported menu actions must remain unchanged.
- **Trace:**

  > Menubar.registerListeners in src/vs/platform/menubar/electron-main/menubar.ts subscribes to main-window blur/focus only. onDidChangeWindowFocus synchronously derives noActiveMainWindow from BrowserWindow.getFocusedWindow(), and setMenu disables non-fallback actions when that flag is true. NativeHostMainService in src/vs/platform/native/electron-main/nativeHostMainService.ts exposes separate main-only and main-or-auxiliary focus streams, but native-dialog cancellation provides no explicit refresh event. Process Explorer now opens through IEditorService as an always-on-top auxiliary editor in src/vs/workbench/contrib/processExplorer/browser/processExplorer.contribution.ts, so the original standalone-window implementation changed but the relevant focus ordering remains. Preserve disabled menus while an auxiliary window is genuinely active and avoid broad changes to command enablement or menu construction.

## Evidence

- **current menu path:** src/vs/platform/menubar/electron-main/menubar.ts registers only onDidBlurMainWindow/onDidFocusMainWindow for menu focus refresh, samples BrowserWindow.getFocusedWindow() in onDidChangeWindowFocus(), and disables non-fallback actions while noActiveMainWindow is true.
- **focus event boundary:** src/vs/platform/native/electron-main/nativeHostMainService.ts defines separate main-only and main-or-auxiliary focus events; Menubar consumes the main-only events, and native-dialog dismissal is not itself a menu-refresh trigger.
- **trigger remains:** src/vs/workbench/contrib/processExplorer/browser/processExplorer.contribution.ts still opens Process Explorer as an always-on-top auxiliary window, preserving the report's auxiliary-window/native-modal focus ordering even though commit 708b6aa379c2c9d12c65123c8934ca5a6a29046d converted the old standalone implementation.
