# Issue #146157 — VSCode line sorting does not use custom sort order set in System Preferences

[https://github.com/microsoft/vscode/issues/146157](https://github.com/microsoft/vscode/issues/146157)

## Summary

Keep this accepted feature request open: line sorting still uses the runtime's default collator without an explicit sorting-locale option or macOS list-sort preference integration. The request has 23 upvotes, and the older related reports do not own the same observable behavior.

## Change summary

Make Sort Lines respect the user's preferred collation, such as Chinese Pinyin sorting selected in macOS, or provide an explicit collation setting.

## Best solution

Establish how editor line sorting should select its locale and collation independently of the display language, then support the reported Pinyin ordering. Decide whether native preference integration or an explicit portable setting supplies that preference while preserving existing behavior when no preference is specified.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/linesOperations/browser/linesOperations.ts`, `src/vs/editor/contrib/linesOperations/browser/sortLinesCommand.ts`, `src/vs/editor/contrib/linesOperations/test/browser/sortLinesCommand.test.ts`
- **Validation:** On macOS configured for Chinese Pinyin list sorting, apply Sort Lines Ascending to '一 yi', '二 er', '三 san' and verify the result is '二 er', '三 san', '一 yi' under the chosen preference mechanism. Verify descending gives the reverse order, and add deterministic collation cases to the existing Editor Contrib - Sort Lines Command suite without changing selection or undo behavior.
- **Behavior:**

  > Users should be able to sort editor lines according to their preferred linguistic collation, including Chinese Pinyin. For the supplied three-line example, ascending Pinyin order is '二 er', '三 san', '一 yi'; descending reverses it. The preference mechanism must be defined before implementation, since honoring macOS preferences and offering an explicit editor setting have different observable contracts. Existing selection, whole-document sorting and undo behavior should remain unchanged.
- **Trace:**

  > AbstractSortLinesAction in src/vs/editor/contrib/linesOperations/browser/linesOperations.ts routes both commands into SortLinesCommand with selection and direction only. SortLinesCommand in src/vs/editor/contrib/linesOperations/browser/sortLinesCommand.ts uses one lazy default Intl.Collator through safeIntl.Collator(), with no explicit locale, collation or native preference input. The existing command tests in src/vs/editor/contrib/linesOperations/test/browser/sortLinesCommand.test.ts cover ascending, descending and selection behavior but not the reported collation. Source inspection establishes the absence of an explicit preference mechanism, not whether the current runtime inherits this particular macOS preference; native behavior must first be checked. Keep the scope on editor line sorting rather than Explorer ordering or the shared safeIntl helper's other consumers. https://github.com/microsoft/vscode/issues/27759 concerns Explorer sorting, and https://github.com/microsoft/vscode/issues/70920 documents default-locale sorting rather than the requested custom collation.
- **Open decisions:**
  - Should line sorting automatically honor the native OS list-sort preference, expose an explicit portable locale/collation setting, or support both?
  - If native preferences and an explicit setting are both supported, which takes precedence and what should web or unsupported-platform users observe?
