# Issue #185674 — Extension contribution point for `workbench.editor.autoLockGroups`

[https://github.com/microsoft/vscode/issues/185674](https://github.com/microsoft/vscode/issues/185674)

## Summary

A real extension API and discoverability gap remains on main. The request is already accepted into the Backlog and correctly routed, with maintainer support for exploring a webview-specific API.

## Change summary

Allow extensions to contribute named webview editor types to the `workbench.editor.autoLockGroups` checkbox list.

## Best solution

Add webview-specific contribution metadata that maps an extension-facing view type to its internal editor ID and display label, then include those declarations in the dynamically generated `workbench.editor.autoLockGroups` schema without letting extensions override the user's choice.

## Evidence

- **current source:** `src/vs/workbench/browser/parts/editor/editorConfiguration.ts` builds the setting schema only from `IEditorResolverService.getEditors()` and the hard-coded `AUTO_LOCK_EXTRA_EDITORS`; arbitrary extension webview panels are not registered for the checkbox UI.
- **webview identity:** `src/vs/workbench/api/browser/mainThreadWebviewPanels.ts` internally prefixes extension view types with `mainThreadWebview-`, and `src/vs/workbench/contrib/webviewPanel/browser/webviewEditorInput.ts` exposes that transformed value as `editorId`. This explains why using the package-facing webview name directly may have no effect.
- **existing capability is incomplete:** `src/vs/workbench/browser/parts/editor/editor.ts` accepts configured editor IDs at runtime, but the schema in `editorConfiguration.ts` sets `additionalProperties: false`; users therefore lack a supported, discoverable way to select extension webview panel types.
- **maintainer direction:** The maintainer response at https://github.com/microsoft/vscode/issues/185674#issuecomment-1602018680 says the idea makes sense and suggests considering a webview-specific API.
