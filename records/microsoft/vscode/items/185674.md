- **Same observable settings gap:** https://github.com/microsoft/vscode/issues/133229#issuecomment-921461444 explicitly asks for extension-provided webview editor types and names so the auto-lock setting can list them. https://github.com/microsoft/vscode/issues/133229#issuecomment-974538591 identifies the missing package.json contribution and discusses runtime registration as an alternative. This establishes the same settings omission, not merely a related registration concern.
- **Existing capability does not cover the request:** src/vs/workbench/browser/parts/editor/editorConfiguration.ts still builds the workbench.editor.autoLockGroups checkbox schema from IEditorResolverService.getEditors() plus AUTO_LOCK_EXTRA_EDITORS, with additionalProperties: false. The fixed extra list includes selected built-in webviews, not a general extension contribution for arbitrary webview panel types.
- **Manual workaround boundary:** src/vs/workbench/browser/parts/editor/editor.ts reads true-valued autoLockGroups entries, while editorGroupView.ts checks the opened editor's editorId only when it is newly opened as the group's first editor and multiple groups exist. mainThreadWebviewPanels.ts prefixes external panel view types with mainThreadWebview-, and webviewEditorInput.ts exposes that viewType as editorId. This explains why a raw extension view-type name is insufficient, but does not supply the missing settings discoverability.
- **Discussion to preserve:** The supplied discussion on https://github.com/microsoft/vscode/issues/185674 includes maintainer support for the idea, an unresolved question about a webview-specific API, and a second extension author's unsuccessful manual-settings attempt. These details should accompany consolidation into the canonical issue.
