# Issue #332944 — Session Forks dont appear in editor sessions list

[https://github.com/microsoft/vscode/issues/332944](https://github.com/microsoft/vscode/issues/332944)

## Summary

Team-authored (MEMBER) report describing a real gap in the multi-chat-sessions/agent-host protocol work: forked chats don't surface in the editor's sessions list. No fix commit references this issue and the author's own proposal (model chats as sessions with a parent link) is itself an open design question, so this stays open per the team-authored protection rule.

## Change summary

A forked conversation appears in the agent (chat) window but is missing from the editor's Sessions list, effectively breaking the fork feature for that surface.

## Best solution

Design how forked chats are represented across AHP-backed session providers — e.g. modeling a chat as a session with a `parent`/`type` relationship as the author sketches — so any session-list consumer (editor sessions view, Copilot app) renders forks consistently; needs a design decision before implementation.

## Plan brief

- **Trace:**

  > Fork handling today lives in the chat/agent-host layer keyed on IChat resources within a single ISession (see agentHostForkActions.test.ts, chatForkActions.js); the editor Sessions list is driven by a separate ISessionsManagementService/session provider that isn't told about the new chat as its own listable entity. The author's proposal — drop the 'chats' concept in AHP and model a fork as session2 with session2.parent = session1, session2.type = 'chat' — would change the session model contract these providers see.
- **Open decisions:**
  - Should forked chats become first-class sessions (with parent/type metadata) as proposed, or should the editor Sessions list instead be taught to unpack per-session chats?
  - Does this apply uniformly to both the editor window and the Copilot app surfaces, or can they diverge initially?
