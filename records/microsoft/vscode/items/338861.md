# Issue #338861 — Settings editor gives no indication when the Agents window overrides a setting's default (same setting shows different values in each window)

[https://github.com/microsoft/vscode/issues/338861](https://github.com/microsoft/vscode/issues/338861)

## Summary

Confirmed real gap in the current source: settings with an `agentsWindow` default override (e.g. `window.dialogStyle`, `window.menuStyle`) show no indicator distinguishing them from a plain 'Applies to all profiles' setting, even though their effective default differs between the Editor and Agents windows. A worthwhile UX fix, but the exact presentation (and whether to also unify the defaults) needs a maintainer decision.

## Change summary

The Settings editor shows no indicator when a setting's default value is overridden specifically for the Agents window, making the same unconfigured setting appear to have different values with no explanation.

## Best solution

Extend the settings indicator logic (settingsTreeModels.ts / settingsEditorSettingIndicators.ts) to surface the agentsWindow-specific default the way policy/scope overrides already are, and have a maintainer decide whether to also converge the two windows' defaults for these settings.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/preferences/browser/settingsTreeModels.ts`, `src/vs/workbench/contrib/preferences/browser/settingsEditorSettingIndicators.ts`, `src/vs/workbench/electron-browser/desktop.contribution.ts`
- **Validation:** A settings-editor model/indicator test asserting that a setting with a non-readOnly `agentsWindow` default override renders the new indicator (and correct hover text) in both the Editor and Agents window contexts when unconfigured.
- **Behavior:**

  > When a setting declares an `agentsWindow` default override (and is not `readOnly`) and the user has not configured it, the Settings editor should show an indicator (in both the Editor window and the Agents window) explaining that the effective default differs between the two windows and stating what each default is. This is distinct from the existing lock/read-only indicator, which already covers settings that cannot be changed at all in the Agents window. Acceptance: opening the Settings editor and searching for such a setting (e.g. `window.dialogStyle`) shows the new hint in both windows when unconfigured, and no hint (or the existing configured-elsewhere hint) once the user sets a value.
- **Trace:**

  > `SettingsTreeSettingElement.update` (settingsTreeModels.ts:389-397) already computes `hasAgentsWindowOverride` from `property.agentsWindow` in the config registry, but only uses it to tag the setting for the `@agentsWindow` search filter and to detect `isAgentsWindowReadOnly`. `SettingsEditorSettingIndicators.updateScopeOverrides` (settingsEditorSettingIndicators.ts:351-480) branches on `hasPolicyValue`, `isAgentsWindowReadOnly`, 'applies to all profiles', and scope overrides, in that priority order, but has no branch for a non-readOnly `agentsWindow` override — do not change the ordering or behavior of the existing branches (policy, read-only, profile-scope, cross-scope overrides) for settings that don't have this override. The relevant declarations are `window.dialogStyle` and `window.menuStyle` in desktop.contribution.ts:289,297. Do not conflate this with the unrelated `defaultOverrideIndicator` (settingsEditorSettingIndicators.ts:483-512), which handles extension-contributed default overrides via `getConfigurationDefaultsOverrides()`, a different mechanism.
- **Open decisions:**
  - Should the new indicator appear in both the Editor and Agents windows, or only where the effective value differs from the 'other' window's default?
  - Should VS Code instead converge the effective default across both windows (dropping the agentsWindow-specific default for these settings) rather than just surfacing the difference?
  - Should this reuse the existing scope-override indicator styling/slot, or introduce a new distinct indicator, and what should the exact wording/hover text be?

## Evidence
