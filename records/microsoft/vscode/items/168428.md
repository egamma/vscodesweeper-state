# Issue #168428 — Consider a sticky scroll provider API

[https://github.com/microsoft/vscode/issues/168428](https://github.com/microsoft/vscode/issues/168428)

## Summary

Keep open: the existing model setting addresses several examples in the discussion, but does not provide the requested sticky-scroll-specific extension API. With 52 upvotes and concrete language-extension requirements, this remains accepted backlog work that merits API design.

## Change summary

Allow extensions to provide sticky-scroll-specific scope ranges and displayed header information independently of document symbols and folding ranges.

## Best solution

Design a dedicated sticky scroll provider contract that lets language extensions supply meaningful headers without distorting their outline or folding data. Resolve whether the contract supports selecting existing source lines only or also supplying synthesized header text, while preserving existing behavior for languages without a provider.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/contrib/stickyScroll/browser/stickyScrollModelProvider.ts`, `src/vs/editor/contrib/stickyScroll/browser/stickyScrollElement.ts`, `src/vs/editor/contrib/stickyScroll/browser/stickyScrollProvider.ts`
- **Validation:** The plan should end with an executable extension-host API check showing that sticky-scroll-specific data can differ from document symbols and folding ranges. Cover the agreed multiline C++ header behavior and COBOL second-line program name, then verify that removing the provider restores the existing model fallback and that outline and folding outputs remain unchanged.
- **Behavior:**

  > Language extensions should be able to describe useful sticky headers independently of the information they provide for document outlines and code folding. Existing model selection helps with scope coverage but does not provide that independence. Acceptance should include the COBOL program-name example and the agreed treatment of multiline C++ declarations. Languages without a dedicated provider must retain their current sticky scroll behavior.
- **Trace:**

  > StickyModelProvider in src/vs/editor/contrib/stickyScroll/browser/stickyScrollModelProvider.ts selects among outline, syntax-folding, and indentation candidates according to editor.stickyScroll.defaultModel. Its outline candidate uses document-symbol selection ranges, and StickyRange/StickyElement in stickyScrollElement.ts carry source-line scope information rather than independent header content. StickyLineCandidateProvider in stickyScrollProvider.ts consumes that internal model; searches of src/vscode-dts found no public sticky scroll API. The discussion at https://github.com/microsoft/vscode/issues/168428 establishes demand beyond model selection, especially for C++ combined headers and a COBOL name on a later source line. The uncertainty is the public contract for displayed header content, not whether another defaultModel value exists. Preserve document-symbol and folding semantics rather than treating either provider as a sticky-scroll-only channel.
- **Open decisions:**
  - Should a sticky scroll provider select existing source lines only, or also supply synthesized text that combines multiple declaration lines into one header?
