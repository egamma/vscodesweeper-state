# Issue #339772 — Maximized editor group shows double border

[https://github.com/microsoft/vscode/issues/339772](https://github.com/microsoft/vscode/issues/339772)

## Summary

Fresh, source-confirmed visual bug in the experimental Modern UI editor-border feature: maximizing a group leaves the hidden sibling's grid separator-border painted alongside the maximized group's own card border, producing a doubled edge. No fix has landed yet.

## Change summary

After running 'View: Toggle Maximize Editor Group', the maximized group's left edge shows two stacked borders instead of one.

## Best solution

Suppress the SplitView `separator-border` (::before) pseudo-element on a view that is now filling a maximized grid node, since its own Modern UI editor-part border already provides the edge; needs a decision on whether the fix lives in the shared gridview/splitview maximize logic or is scoped to the editor part only.

## Plan brief

- **Likely files:** `src/vs/base/browser/ui/splitview/splitview.ts`, `src/vs/base/browser/ui/splitview/splitview.css`, `src/vs/base/browser/ui/grid/gridview.ts`, `src/vs/workbench/contrib/modernUI/browser/media/editorBorder.css`
- **Validation:** Manual check: with workbench.experimental.modernUI enabled, open two side-by-side editor groups, toggle maximize on one, and confirm only the group's own Modern UI card border is visible on the shared edge (no doubled line); toggling back out of maximize should restore the normal separator between groups.
- **Behavior:**

  > With the Modern UI editor border experiment enabled, toggling 'Maximize Editor Group' on a group that has a sibling group should show exactly one border on every edge of the now-fullscreen group — not a doubled line on the edge that used to be shared with the hidden sibling. Exiting maximize should restore the normal single separator between the two groups.
- **Trace:**

  > The sibling group is hidden via `setChildVisible(false)` in gridview.ts's `hideAllViewsBut`, which only toggles visibility/display and does not change DOM order. splitview.css's `.split-view-view:not(:first-child)::before` separator-border selector is purely DOM-order based, so it still applies to the maximized view, which also now gets its own full 1px card border from editorBorder.css — stacking two border lines on the same edge. The boundary: do not change how maximize hides views (sizing/restore-order logic in exitMaximizedView relies on it), and do not touch the non-maximized multi-group border rendering, which is correct today and used by other SplitView/GridView consumers (panel, sidebar) beyond the editor part.
- **Open decisions:**
  - Should the separator-border be suppressed generically in SplitView/GridView whenever a view is the sole visible (maximized) child, or should the fix be scoped narrowly to the editor part/Modern UI CSS to avoid any risk to other grid/splitview consumers (panel, sidebar, etc.)?

## Evidence

- **feature source:** src/vs/workbench/contrib/modernUI/browser/media/editorBorder.css draws a 1px border+radius on every `.part.editor` element when `.modern-ui` is enabled (gated by `workbench.experimental.modernUI`).
- **separator border mechanism:** src/vs/base/browser/ui/splitview/splitview.css line 52-59 paints a `::before` separator-border on `.split-view-view:not(:first-child)` independent of visibility; src/vs/base/browser/ui/splitview/splitview.ts lines 639-643 toggle the `separator-border` class/CSS var.
- **maximize keeps DOM order:** src/vs/base/browser/ui/grid/gridview.ts `maximizeView()`/`hideAllViewsBut()` hides sibling nodes via `setChildVisible(i, false)` (display:none) but does not remove them from the DOM, so `:not(:first-child)` still matches the maximized (now sole visible) view and its separator-border persists alongside its own Modern UI card border.
