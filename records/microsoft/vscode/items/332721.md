# Issue #332721 — TernarySearchTree.has reports true for strict prefixes of stored keys

[https://github.com/microsoft/vscode/issues/332721](https://github.com/microsoft/vscode/issues/332721)

## Summary

Confirmed bug traced directly in the source: `TernarySearchTree.has` (src/vs/base/common/ternarySearchTree.ts:505-508) reports true for strict prefixes of stored keys, disagreeing with `get`. An open PR (#332722) already fixes this, so the issue should stay open pending that PR landing.

## Change summary

TernarySearchTree.has() incorrectly returns true for keys that are only prefixes of stored keys (checking node.mid presence instead of node.value), diverging from get() and causing incorrect shortcuts in contextKeyService.ts and parcelWatcher.ts.

## Best solution

Land the existing open PR https://github.com/microsoft/vscode/pull/332722, which changes `has` to check `node?.value !== undefined` directly, matching `get`'s exact-key semantics.

## Evidence

- **buggy code:** src/vs/base/common/ternarySearchTree.ts:505-508 — `has` returns `!(node?.value === undefined && node?.mid === undefined)`, which is true whenever the node has any subtree (mid), not just when the exact key was stored.
- **reachable misuse #1:** src/vs/platform/contextkey/browser/contextKeyService.ts:569,614 use `this.overlay.has(key) ? this.overlay.get(key) : ...`, so a prefix-match `has()` true can select `get()` returning undefined instead of falling back correctly.
- **reachable misuse #2:** src/vs/platform/files/node/watcher/parcel/parcelWatcher.ts:711 uses `requestTrie.has(request.path)` to skip adding a watcher, which can wrongly treat a path as already covered when it's merely a prefix of a different stored path.
- **open fix PR:** https://github.com/microsoft/vscode/pull/332722 "Ternary search tree: make has agree with get" is open and targets exactly this defect; not yet merged (no related recent commit in `git log` for the file).
