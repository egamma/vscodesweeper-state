# Issue #180317 — Git - publish branch behave confusingly after git shallow clone

[https://github.com/microsoft/vscode/issues/180317](https://github.com/microsoft/vscode/issues/180317)

## Summary

Keep open: current source still treats an unavailable upstream as an unpublished branch, without explaining the restricted fetch configuration. The closely related upstream-detection report is newer and cannot absorb this re-reviewed issue under the duplicate rules.

## Change summary

Provide clear feedback when publishing a branch from a shallow, single-branch clone succeeds but VS Code continues offering Publish Branch.

## Best solution

Make the built-in Git publishing experience distinguish successful publication from unavailable local upstream tracking, with an actionable explanation or recovery path that preserves the user's restricted clone configuration. Coordinate the shared upstream-detection work with https://github.com/microsoft/vscode/issues/248328.

## Plan brief

- **Likely files:** `extensions/git/src/commands.ts`, `extensions/git/src/git.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/actionButton.ts`, `extensions/git/src/statusbar.ts`
- **Validation:** In a disposable fixture outside the shared checkout, clone a populated remote with --depth=1 using a file:// URL, create and commit a new branch, then run Git: Publish Branch. Verify the remote branch exists and that VS Code provides the agreed explanation or recovery instead of an unexplained repeated publish prompt. Compare with an unrestricted clone and confirm any fetch-refspec or history changes require the agreed user consent.
- **Behavior:**

  > A branch published successfully from a shallow clone with a restricted fetch refspec must not leave the user with an unexplained invitation to publish it repeatedly. The experience should make clear whether remote publication succeeded and why local upstream tracking remains unavailable. Acceptance must cover this exact successful-push case and ordinary publication from an unrestricted clone. Any recovery must preserve the user's intentional clone restrictions unless they explicitly choose otherwise.
- **Trace:**

  > Commands.publish in extensions/git/src/commands.ts calls Repository.pushTo with setUpstream=true, and git.ts executes git push -u. Repository.getBranch in git.ts obtains upstream state from for-each-ref and returns undefined upstream when Git supplies empty upstream fields; getHEADRef feeds that state into the repository model. getPublishBranchActionButton in actionButton.ts and the statusbar.ts sync control interpret absent upstream as needing publication. The same empty-field cause was independently diagnosed by maintainers in https://github.com/microsoft/vscode/issues/248328#issuecomment-3135322113; that younger report should inform coordination, not replace this older re-reviewed issue. The boundary is publication feedback and tracking state for restricted clones, not adding a general shallow-clone feature or silently downloading full history. Source inspection establishes the existing path, but the final user-visible recovery behavior is unsettled.
- **Open decisions:**
  - Should successful publication with unavailable upstream tracking provide explanation-only feedback, or offer an explicit action to add the published branch to the remote fetch configuration?
  - While upstream tracking remains unavailable, should the normal Publish Branch affordance remain with explanatory feedback, or be replaced by a distinct tracking-unavailable state?
