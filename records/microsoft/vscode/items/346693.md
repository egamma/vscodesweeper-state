# Issue #346693 — Model listed in a remote window cannot be resolved when its provider runs in the UI host

[https://github.com/microsoft/vscode/issues/346693](https://github.com/microsoft/vscode/issues/346693)

## Summary

Current source confirms the cross-extension-host cache mismatch: the workbench returns the UI provider's model identifiers, but the requesting remote extension host never receives their metadata. Keep this open separately from the remote Copilot harness BYOK issue.

## Change summary

Models supplied by a UI-host extension appear in a remote window's Local harness picker but cannot be resolved for requests.

## Best solution

Make Local harness model availability consistent with request resolution, preferably allowing the workbench broker to serve models across extension hosts. If cross-host consumption is deliberately unsupported, settle that product boundary and exclude unusable models before selection.

- **Behavior:**

  > A Remote-SSH window using the Local harness lists models from a provider installed only in the UI extension host, but every request fails as unavailable. A selectable model must be usable by that session; otherwise it must be excluded before selection. The reporter supplied complete steps, matching logs, and a same-version workspace-host control that succeeds. Preserve explicit failure for genuinely unavailable selections rather than silently switching models.
- **Trace:**

  > MainThreadLanguageModels.$selectChatModels forwards to LanguageModelsService.selectLanguageModels, which returns identifiers from the shared workbench catalog. ExtHostLanguageModels._localModels is populated only by $provideLanguageModelChatInfo in the provider's own host; selection transfers no metadata to another host. getLanguageModelByIdentifier retries discovery but still requires that host-local entry, and getLanguageModelForRequest throws before brokered dispatch. The workbench already routes sendChatRequest to the registered provider, but the consumer cannot construct its LanguageModelChat API object. Preserve authorization, cancellation, provider disposal, and same-host behavior; do not conflate this with the remote Agent Host bridge tracked at https://github.com/microsoft/vscode/issues/332085. The unresolved boundary is whether Local harness consumption must support UI-host providers or deliberately exclude them.
- **Open decisions:**
  - Should Local harness sessions consume language models across extension hosts, or should models whose provider runs in another host be excluded from those sessions' selection surface?
