# Issue #227263 — [Accessibility] Tooltips under user settings for extensions missing aria attributes.

[https://github.com/microsoft/vscode/issues/227263](https://github.com/microsoft/vscode/issues/227263)

## Summary

The settings indicator still lacks an explicit role and an association with its tooltip in current source. The tooltip itself already has role="tooltip", so the remaining work is the trigger's accessibility semantics, not adding that role again.

## Change summary

Expose the “Applies to all profiles” settings indicator and its explanatory tooltip correctly to screen readers.

## Best solution

Make the settings indicator's purpose and tooltip description discoverable to assistive technologies while preserving keyboard activation and navigation. Coordinate any shared-hover changes with the related status-bar report rather than closing this older, settings-specific issue into it.

Manually navigate to “Applies to all profiles” with a screen reader, activate its hover with Enter/Space, and verify the explanation and Escape focus restoration.
- **Behavior:**

  > In User Settings, the “Applies to all profiles” indicator is keyboard-focusable but lacks semantics connecting it to its explanatory tooltip. Assistive technologies should be able to identify the trigger and access the explanation about retaining the setting across profiles. Acceptance includes a valid descriptive relationship while the tooltip is displayed, no stale relationship after dismissal or row reuse, and unchanged toolbar navigation and keyboard activation.
- **Trace:**

  > SettingsTreeIndicatorsLabel.createScopeOverridesIndicator creates a plain span; updateScopeOverrides selects the all-profiles branch for USER_LOCAL settings when isSettingAppliedForAllProfiles returns true. That branch registers a string-content hover through HoverService.setupDelayedHover with setupKeyboardEvents enabled. The delayed-hover registration supplies mouse and Enter/Space handlers but no descriptive relationship, and the platform HoverWidget construction does not supply that relationship either. Base HoverWidget already assigns role="tooltip", so that existing behavior must be preserved. The missing attributes are established from source, but actual screen-reader announcements have not been exercised. The uncertainty is the scope of shared-hover lifecycle changes and their other consumers; https://github.com/microsoft/vscode/issues/227508 documents the related status-bar case. Preserve settings scope behavior, existing descriptions, focus restoration, and unrelated interactive-hover behavior.
