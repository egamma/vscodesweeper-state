# Issue #35350 — File extension specific settings

[https://github.com/microsoft/vscode/issues/35350](https://github.com/microsoft/vscode/issues/35350)

## Summary

This remains the accepted canonical request for file- or glob-specific configuration overrides. Current main still supports only language and workspace-folder overrides, while 182 upvotes, continuing use cases, and maintainer triage into the Backlog support keeping it open for design.

## Change summary

Allow settings to be overridden for files matching an extension, filename, path, or glob without assigning those files a different language.

## Best solution

Add resource-pattern configuration overrides with documented precedence against ordinary, workspace-folder, and language-specific settings, and expose the effective source through configuration inspection so users can understand which rule applies.

## Vision fit

- **Fit:** aligned
- **Reason:** Fine-grained, understandable configuration improves settings fidelity and supports established editor workflows without adding permanent UI.
- **Evidence:** Durable theme: Workbench and core UX includes settings fidelity; the proposal also preserves the value of simple, uniform UI interactions by expressing the behavior through the existing settings system.

## Plan brief

- **Likely files:** `src/vs/platform/configuration/common/configuration.ts`, `src/vs/platform/configuration/common/configurationModels.ts`, `src/vs/platform/configuration/common/configurationRegistry.ts`, `src/vs/editor/common/services/textResourceConfigurationService.ts`, `src/vs/platform/configuration/test/common/configurationModels.test.ts`, `src/vs/editor/test/common/services/textResourceConfigurationService.test.ts`
- **Validation:** Add configuration-model and text-resource-configuration tests covering two resources with the same language but different matching paths, asserting the chosen values and change events across user, workspace, workspace-folder, language, and file-pattern override combinations.
- **Behavior:**

  > Users can assign configuration values to files selected by extension, filename, path, or glob while retaining the files' existing language mode and language-specific settings. A matching file receives the pattern-specific values, while nonmatching files of the same language remain unchanged. Overlapping patterns and combinations with language and workspace-folder settings resolve through a documented, deterministic precedence order, and configuration inspection identifies the effective source.
- **Trace:**

  > Current settings overrides are represented by bracketed identifiers in src/vs/platform/configuration/common/configurationRegistry.ts and parsed into IOverrides by ConfigurationModel in src/vs/platform/configuration/common/configurationModels.ts. TextResourceConfigurationService in src/vs/editor/common/services/textResourceConfigurationService.ts supplies both the resource and its language, but Configuration.getConsolidatedConfigurationModelForResource uses the resource only for workspace-folder and in-memory resource selection before applying the language override. The existing model therefore has the necessary resource at lookup time but no persisted pattern selector or precedence semantics. https://github.com/microsoft/vscode/issues/1587 records the earlier decision to ship language overrides first, while https://github.com/microsoft/vscode/issues/112280#issuecomment-745867821 confirms that generalized path overrides need deliberate design. Preserve existing language-only behavior and extension-facing configuration reads; do not narrow this to formatter-specific exclusions or require synthetic language IDs.
- **Open decisions:**
  - Which public selector syntax should settings use: extension-only keys or general file globs capable of matching filenames and workspace-relative paths?
  - When file-pattern, language, workspace-folder, and ordinary settings all define the same key, what user-visible precedence order should apply, and how should overlapping file patterns be ordered?
  - Should every resource-aware setting be eligible for file-pattern overrides, or only settings with explicitly declared scopes, and how should unsupported settings be diagnosed?

## Evidence

- **current source gap:** On current main, src/vs/platform/configuration/common/configurationRegistry.ts defines OVERRIDE_PROPERTY_PATTERN solely as bracketed override identifiers and describes these entries as per-language configuration; it has no file-pattern selector.
- **configuration path:** src/vs/editor/common/services/textResourceConfigurationService.ts resolves a resource to a language and calls IConfigurationService with { resource, overrideIdentifier: language }; src/vs/platform/configuration/common/configurationModels.ts then uses the resource only to select its workspace folder and applies overrideIdentifier as a language override. No filename or glob-specific persisted model participates.
- **maintainer acceptance:** A maintainer agreed that the editor-settings case is valid in https://github.com/microsoft/vscode/issues/35350#issuecomment-335399238. Later, https://github.com/microsoft/vscode/issues/112280#issuecomment-745867821 called this a good value addition, noted that it requires deep design discussion, and placed the work in the Backlog.
- **canonical ownership:** Later requests including https://github.com/microsoft/vscode/issues/112280 and https://github.com/microsoft/vscode/issues/232954 were closed as duplicates of this issue. The older https://github.com/microsoft/vscode/issues/1587 implemented only language-specific settings and explicitly left file/glob overrides unresolved, so it is not an open canonical.
- **demand:** The issue has 182 community upvotes and recent comments continue to provide distinct examples involving formatting, linting, inlay hints, custom language associations, and path-specific source trees.
