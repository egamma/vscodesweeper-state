# Issue #332798 — huge gap appeared between window right edge and the scrollbar

[https://github.com/microsoft/vscode/issues/332798](https://github.com/microsoft/vscode/issues/332798)

## Summary

Real, repeatedly-confirmed usability regression tied to the experimental Modern UI redesign: multiple independent users report the same scrollbar-edge gap, and disabling `workbench.experimental.modernUI` fixes it for all of them, but the exact fix direction is a design call the team is still iterating on (a newer 'Density: Layout' setting didn't resolve it either) — this stays open and routed to the area, not closed.

## Change summary

With Modern UI enabled, the editor's vertical scrollbar sits noticeably inset from the true window edge, breaking the classic 'throw the mouse to the screen edge to grab the scrollbar' (Fitts'-law) interaction.

## Best solution

A maintainer should decide whether the editor part (and other window-edge-abutting parts) should render edge-flush in Modern UI to preserve the edge-grab affordance, or whether the scrollbar's effective hit target should extend to the true window edge even when the visual card is inset — then apply that consistently across `editorBorder.css` / `floatingPanels.css`.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/modernUI/browser/media/editorBorder.css`, `src/vs/workbench/browser/media/floatingPanels.css`, `src/vs/workbench/contrib/modernUI/browser/modernUI.contribution.ts`
- **Validation:** With `workbench.experimental.modernUI` enabled and a maximized window (sidebar left, no auxiliary bar), moving the mouse to the true right edge of the window and pressing/dragging should engage the vertical scrollbar, matching classic (modernUI-off) behavior.
- **Behavior:**

  > Users should be able to grab/drag the editor's vertical scrollbar by moving the mouse all the way to the true right edge of a maximized window, as in classic VS Code (an effectively infinite Fitts'-law target). With Modern UI enabled, several independent users report a real gap between the window edge and the scrollbar that requires precise horizontal aim; a subsequently-added 'Window > Density: Layout' setting did not fix it. Acceptance: with Modern UI on, edge-throwing the mouse on the window's right side engages the scrollbar, or a deliberate trade-off is documented.
- **Trace:**

  > Modern UI's Editor Border module (src/vs/workbench/contrib/modernUI/browser/media/editorBorder.css) frames the editor part as a bordered, rounded card even when it is the rightmost part touching the true window edge; the module comment claims 'no margin is added,' but combined with the shrunk 8px scrollbar (MODERN_UI_SCROLLBAR_SIZE in modernUI.contribution.ts) this is what reporters experience as a new edge gap. The sibling floating-panels module (src/vs/workbench/browser/media/floatingPanels.css) explicitly gives window-edge-facing parts (side bar, activity bar, panel) a real outer gutter (--modern-ui-floating-card-outer-margin) — the same 'inset floating card' language applied by design elsewhere — so whether the editor should follow that same intentional inset, or be special-cased edge-flush to preserve the scrollbar grab, is the open call. Do not touch unrelated Modern UI modules (tabs, activity bar rail, rounded corners on interior controls). Related, but a different symptom, not a duplicate: https://github.com/microsoft/vscode/issues/332193.
- **Open decisions:**
  - Should the editor part (and any other part abutting the true window edge) render edge-flush in Modern UI — no border/radius/inset on that edge — even at the cost of the uniform 'floating card' look, to preserve the scrollbar edge-grab?
  - Or should the scrollbar's clickable hit target be extended to the true window edge even while the visual card stays inset, so the Fitts'-law affordance survives without changing the card's look?
  - Does the answer differ between default and modern-ui-compact density, given compact already drops some floating-card margins/border-radius?

## Evidence

- **editor card framing:** src/vs/workbench/contrib/modernUI/browser/media/editorBorder.css frames the editor part with a bordered, rounded card (border-radius: var(--vscode-cornerRadius-large), overflow: hidden) even when the editor abuts the true window edge; comment states 'no margin is added' but the reduced scrollbar width doesn't preserve the classic edge-flush grab.
- **reduced scrollbar size:** MODERN_UI_SCROLLBAR_SIZE = 8 in src/vs/workbench/contrib/modernUI/browser/modernUI.contribution.ts (default is DEFAULT_SCROLLBAR_SIZE, larger), shrinking the target further.
- **adjacent 'floating card' pattern:** src/vs/workbench/browser/media/floatingPanels.css deliberately adds an outer gutter (--modern-ui-floating-card-outer-margin) between window-edge-facing parts (side bar, activity bar rail, panel) and the true window edge — the same 'card floats off the edge' design language, applied elsewhere by design.
- **multiple independent confirmations:** grego5, reserl, LWChris, and virtualcuriosities all report the identical symptom; setting `workbench.experimental.modernUI` to false fixes it for each of them (comments 1-5).
- **related but not a duplicate:** https://github.com/microsoft/vscode/issues/332193 is older but reports a different symptom (no clear way to discover/turn off Modern UI/rounded corners), not this scrollbar-edge gap — cited as related context, not canonical.
