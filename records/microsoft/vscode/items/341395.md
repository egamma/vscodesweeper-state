# Issue #341395 — Agents can't interact with Jupyter Notebooks

[https://github.com/microsoft/vscode/issues/341395](https://github.com/microsoft/vscode/issues/341395)

## Summary

Keep open: the discussion confirms notebook-tool failures in agent-host Copilot CLI sessions on 1.142.0, and current source retains both reported failure paths. This is an in-scope Copilot integration regression, not evidence of a Jupyter-extension defect.

## Change summary

Restore agents' ability to make reviewable notebook-cell edits, execute cells, and inspect their outputs without resorting to shell-based file rewrites.

## Best solution

Make the notebook tools work through the agent-host client-tool invocation path while preserving tracked edits and the selected model's identity. Address both the missing editing-stream context and execution's unnecessary dependency on resolving an external runtime model for telemetry.

- **Behavior:**

  > An agent-host Copilot CLI session must be able to edit an existing notebook through reviewable notebook changes, execute the requested cell in its notebook kernel, and consume the resulting outputs. These operations must not fail because the session uses an agent-host model identifier or lacks Copilot Chat's internal tool-loop context. Acceptance includes visible tracked edits, successful cell execution, and readable text and image outputs without shell-based notebook rewrites.
- **Trace:**

  > The October 20 reproduction on https://github.com/microsoft/vscode/issues/341395 identifies two failures retained in current source. AgentHostSessionHandler._executeClientTool invokes client tools directly, while EditNotebookTool.invoke requires a stream stored by resolveInput. RunNotebookCellTool.invoke reads options.model for telemetry before accessing the notebook; ExtHostLanguageModelTools.$invokeTool exposes a throwing getter when the explicit external-runtime model cannot resolve. Existing extension-host tests deliberately preserve rejection for tools that actually read that unresolved model, so silently substituting a default model is outside the boundary. GetNotebookCellOutputTool and RunNotebookCellTool also derive image handling from prompt context, which needs tracing before claiming the reporter's complete workflow is restored. The unresolved technical scope is how external tool invocation participates in tracked notebook edits and output handling; no product decision changing the requested behavior is needed.
