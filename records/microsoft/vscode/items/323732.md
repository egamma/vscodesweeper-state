# Issue #323732 — Allow me to fork the copilot chat conversation from the last chat

[https://github.com/microsoft/vscode/issues/323732](https://github.com/microsoft/vscode/issues/323732)

## Summary

A real UI gap remains: `/fork` can branch the complete conversation, but the visible checkpoint affordance is attached only to earlier requests, leaving no equivalent control after the final response. Keep this open under discussion rather than treating the command as complete coverage of the requested discoverable UI.

## Change summary

Expose the conversation-fork action at the end of a completed Copilot chat so the fork includes every turn.

## Best solution

Provide a discoverable end-of-conversation fork affordance that invokes the existing full-session fork path, while preserving the current intermediate checkpoint behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/actions/chatForkActions.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts`, `src/vs/workbench/contrib/chat/test/browser/actions/chatForkActions.test.ts`
- **Validation:** In a completed multi-turn chat, verify an end-of-conversation fork affordance creates a new conversation containing every completed turn; verify existing intermediate checkpoint forks still branch at their selected point. Add or extend a browser test covering the final-response invocation and run the targeted chat fork action tests.
- **Behavior:**

  > A completed chat exposes a discoverable way to fork from its end. Activating it creates a separate conversation containing every completed request and response from the source, while leaving the source unchanged. Intermediate checkpoint forks must retain their existing truncation semantics, and empty or still-running conversations must not gain an invalid action.
- **Trace:**

  > ForkConversationAction in src/vs/workbench/contrib/chat/browser/actions/chatForkActions.ts already supports a whole-session fork when invoked with a session URI: local sessions retain the full serialized request list, while contributed sessions receive an undefined request meaning "from the end." The visible action is currently contributed only to MenuId.ChatMessageCheckpoint under ChatContextKeys.isRequest and isFirstRequest.negate(), and chatListRenderer.ts constructs that checkpoint toolbar; this leaves no checkpoint after the last response. Existing action tests are in src/vs/workbench/contrib/chat/test/browser/actions/chatForkActions.test.ts. Preserve the existing `/fork` behavior and intermediate checkpoint indexing; the open product question is only how the final affordance appears.
- **Open decisions:**
  - Should the final fork control be persistently displayed after the last completed response, or appear in that response's hover/action toolbar?

## Evidence

- **current UI boundary:** src/vs/workbench/contrib/chat/browser/actions/chatForkActions.ts registers ForkConversationAction only in MenuId.ChatMessageCheckpoint with ChatContextKeys.isRequest and isFirstRequest.negate(); src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts renders that checkpoint toolbar. Consequently, the affordance depends on a following request and is absent after the final response.
- **existing full-session behavior:** ForkConversationAction.run in src/vs/workbench/contrib/chat/browser/actions/chatForkActions.ts handles a session URI from `/fork` by copying the complete serialized request list, or by passing an undefined request to a contributed session. src/vs/workbench/contrib/chat/common/chatSessionsService.ts explicitly defines undefined as forking from the end.
- **existing workaround is partial:** src/vs/workbench/contrib/chat/browser/chatSlashCommands.ts registers `/fork`, but this command does not supply the end-of-chat visual affordance requested in https://github.com/microsoft/vscode/issues/323732.
