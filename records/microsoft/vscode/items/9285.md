# Issue #9285 — User configurable menus

[https://github.com/microsoft/vscode/issues/9285](https://github.com/microsoft/vscode/issues/9285)

## Summary

Keep open: toolbar action hiding only partially addresses this accepted request; user-defined editor and Explorer context menus remain a real gap. The 291 upvotes and continued requests support planning the remaining customization contract rather than closing or consolidating into narrower menu-cleanup issues.

## Change summary

Allow users to configure menu commands and their contextual visibility, analogous to user keybindings.

## Best solution

Provide a supported user-level customization mechanism for existing menus, including editor and Explorer context menus, while preserving extension contributions and default behavior. Agree on the initial scope and override semantics before implementation; toolbar hiding is a useful foundation, not completion.

## Plan brief

- **Likely files:** `src/vs/platform/actions/common/menuService.ts`, `src/vs/platform/actions/browser/toolbar.ts`, `src/vs/platform/contextview/browser/contextMenuService.ts`, `src/vs/workbench/services/contextmenu/electron-browser/contextmenuService.ts`, `src/vs/workbench/services/actions/common/menusExtensionPoint.ts`, `src/vs/workbench/services/preferences/browser/preferencesService.ts`
- **Validation:** End the plan with executable menu-service tests for the agreed user override semantics and explicit manual checks in editor and Explorer context menus: apply customization, reload, verify persistence and contextual visibility, restore defaults, and confirm unchanged menus without customization. Cover HTML and native context-menu rendering where supported.
- **Behavior:**

  > Users want supported control over existing menus, especially editor and Explorer right-click menus, without modifying extension files or injecting CSS. The original request includes selecting commands and controlling their visibility with when expressions; later comments emphasize hiding unwanted entries as a valuable first increment. Acceptance must establish the chosen scope, persistence and reset behavior, and confirm that uncustomized menus retain their existing behavior.
- **Trace:**

  > MenuService in src/vs/platform/actions/common/menuService.ts reads MenuRegistry contributions, evaluates contributed when expressions, and attaches hide actions backed by PersistedMenuHideState. WorkbenchToolBar.setActions in src/vs/platform/actions/browser/toolbar.ts consumes that visibility metadata for primary toolbar actions. ContextMenuMenuDelegate.transform in src/vs/platform/contextview/browser/contextMenuService.ts instead retrieves and flattens registered menu actions; src/vs/workbench/services/contextmenu/electron-browser/contextmenuService.ts uses the same transformation for native menus. Extension-authored menus enter through src/vs/workbench/services/actions/common/menusExtensionPoint.ts, while the inspected preferences paths expose settings and keybindings resources, not a menus.json equivalent. These source paths establish the partial capability, not an implementation design for arbitrary user overrides. Preserve existing contributed command enablement, contextual visibility, toolbar behavior, and default menus unless the agreed product contract explicitly changes them. https://github.com/microsoft/vscode/issues/225411 and https://github.com/microsoft/vscode/issues/255626 concern default menu cleanup and must not be treated as completing user customization.
- **Open decisions:**
  - Should the first supported increment only hide existing context-menu entries, or also allow adding, reordering, and overriding when expressions as envisaged in the original request?
  - Should user configuration augment contributed menus with targeted overrides, or replace the configured menu's contents?
  - Should customization be profile-wide only, or also permit workspace-specific menu definitions?
