# Issue #300132 — The rg process uses a huge amount of CPU.

[https://github.com/microsoft/vscode/issues/300132](https://github.com/microsoft/vscode/issues/300132)

## Summary

Keep open: multiple users confirmed sustained ripgrep process storms, including a report on 1.135.0 and a repeatable bracket-path trigger. Neither a complete fixing commit nor an older canonical covering all reported discovery triggers has been established.

## Change summary

Opening workspaces can trigger excessive background ripgrep searches that consume CPU and severely degrade system responsiveness.

## Best solution

Identify the callers responsible for the repeated searches and ensure background discovery remains scoped to its intended locations without accumulating scans. Investigate the bracket-path case alongside the MCP and custom-agent searches rather than assuming they all have one cause.

Capture search queries, ripgrep cwd/arguments, parent PIDs, and process counts through startup and idle; confirm discovery completes without sustained process accumulation and retains expected customization discovery. Add an automated regression for the diagnosed path.
- **Behavior:**

  > Users report that opening several VS Code windows causes hundreds of background ripgrep processes and sustained CPU load, sometimes even with extensions disabled. Removing brackets from an ancestor path reverses the problem for one reporter; other confirmations identify MCP configuration and custom-agent discovery. Background discovery should complete without sustained process accumulation or scanning unintended ancestor trees. Acceptance should cover the bracket/no-bracket comparison and the reported customization triggers while preserving legitimate discovery.
- **Trace:**

  > PromptFilesLocator.toAbsoluteLocations passes resolved locations to resolveSearchLocation in src/vs/workbench/contrib/chat/common/promptSyntax/utils/promptFilesLocator.ts. For prompt and instruction types, resolveSearchLocation interprets paired brackets anywhere in the absolute path as glob syntax and moves searchRoot to the preceding ancestor; searchFilesInLocation then submits that root to ISearchService.fileSearch. spawnRipgrepCmd in src/vs/workbench/services/search/node/ripgrepFileSearch.ts uses the supplied root as cwd, and its argument builder follows symlinks unless explicitly disabled. This establishes a plausible search-scope defect, not the origin of every observed command or the repeated-spawn loop. CachedPromise in src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts caches computations and invalidates them on update events; the record does not establish which events or callers sustain the storm. Correlate renderer search queries with extension-host traces before choosing an implementation boundary. Preserve intentional configured globs and ordinary search behavior; do not globally disable discovery or symlink support. Older related reports are https://github.com/microsoft/vscode/issues/282852 and https://github.com/microsoft/vscode/issues/286778; the newer investigation at https://github.com/microsoft/vscode/issues/328122 illustrates why command provenance must be verified.

- **Current source supports a bracket-path investigation:** src/vs/workbench/contrib/chat/common/promptSyntax/utils/promptFilesLocator.ts:930-1046 treats paired square brackets as glob syntax. resolveSearchLocation examines the entire resolved URI path for prompt and instruction locations and selects the ancestor before the first glob-like segment as searchRoot. This can broaden a search when a literal workspace ancestor contains brackets, but does not by itself prove the reported repeated-spawn mechanism.
- **Search execution boundary:** PromptFilesLocator.searchFilesInLocation at src/vs/workbench/contrib/chat/common/promptSyntax/utils/promptFilesLocator.ts:707-735 submits a fileSearch with that folder. src/vs/workbench/services/search/node/ripgrepFileSearch.ts:17-26 uses folderQuery.folder.fsPath directly as the spawned process cwd; getRgArgs adds --follow unless ignoreSymlinks is set. The general search helper escapeGlobPattern in src/vs/workbench/services/search/common/queryBuilder.ts:683 already escapes literal brackets, so its existence alone is not evidence that discovery is fixed.
