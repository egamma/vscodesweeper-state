# Issue #342843 — Replace native dialogs with custom (in-app) dialogs

[https://github.com/microsoft/vscode/issues/342843](https://github.com/microsoft/vscode/issues/342843)

## Summary

The existing custom-dialog setting does not satisfy the request to remove native message dialogs altogether. Keep this open for design: workbench dialogs already have a custom implementation, but main-process recovery dialogs require a scope decision to preserve functionality.

## Change summary

Replace native confirmation and message dialogs with themed, DOM-accessible dialogs rather than retaining native dialogs as the default or an option.

## Best solution

Use the existing custom-dialog implementation consistently for workbench confirmations and prompts, with an explicit compatibility decision for window.dialogStyle. Define how startup and renderer-failure messages remain available when the workbench cannot display a dialog before committing to complete native-dialog removal.

## Plan brief

- **Likely files:** `src/vs/workbench/electron-browser/desktop.contribution.ts`, `src/vs/workbench/electron-browser/parts/dialogs/dialog.contribution.ts`, `src/vs/workbench/electron-browser/parts/dialogs/dialogHandler.ts`, `src/vs/workbench/browser/parts/dialogs/dialogHandler.ts`, `src/vs/platform/dialogs/electron-main/dialogMainService.ts`, `src/vs/platform/windows/electron-main/windowImpl.ts`
- **Validation:** After scope is agreed, exercise confirmation, multi-button prompt, checkbox, cancellation, and About-copy behavior in desktop editor and Agents windows, including an existing window.dialogStyle=native configuration. Check keyboard operation, screen-reader labeling, focus restoration, and background-window activation on supported desktop platforms; separately verify recovery actions remain usable after a renderer becomes unresponsive or terminates. Cover the agreed dispatch contract with targeted tests and retain the existing base Dialog tests.
- **Behavior:**

  > Ordinary VS Code confirmation and message dialogs should use the themed in-app surface without requiring users to opt in, and should remain accessible to DOM automation. Existing choices, cancellation, checkbox results, and keyboard accessibility must retain their meaning. Focus behavior should avoid unnecessary disruption while leaving each prompt reachable. The acceptance contract must also state what happens to explicit native-dialog preferences and to messages shown when no functioning workbench is available. File pickers are not part of the stated confirmation/message-dialog request.
- **Trace:**

  > DialogHandlerContribution.processDialogs in src/vs/workbench/electron-browser/parts/dialogs/dialog.contribution.ts routes confirmations, prompts, and About between BrowserDialogHandler and NativeDialogHandler; inputs already use BrowserDialogHandler exclusively. window.dialogStyle in src/vs/workbench/electron-browser/desktop.contribution.ts defaults to native for editor windows and custom for Agents windows, while the smoke-test driver forces custom dispatch. BrowserDialogHandler in src/vs/workbench/browser/parts/dialogs/dialogHandler.ts already supplies the DOM implementation. Native message boxes also originate outside this dispatcher: src/vs/platform/windows/electron-main/windowImpl.ts uses them for unresponsive and terminated renderers. Source inspection establishes the remaining capability gap, not cross-platform focus or accessibility parity. Preserve dialog result semantics and recovery availability; do not expand this into file-picker replacement. The uncertainty is the supported user-visible migration and exception policy, not which existing handler to reuse.
- **Open decisions:**
  - Does custom-only apply to workbench-owned dialogs while retaining native recovery/startup exceptions, or must those messages use a separate functioning in-app surface too?
  - When native workbench dialogs are retired, how should existing window.dialogStyle=native preferences be migrated and communicated to users?
  - When a dialog is requested by an inactive window, should it wait without activating that window, and which cases are allowed to interrupt the user's current application?

## Evidence

- **Existing capability and remaining gap:** src/vs/workbench/electron-browser/desktop.contribution.ts registers window.dialogStyle with native/custom values and a native default; only the Agents window overrides the default to custom. Opting into custom dialogs does not remove the native option or change the ordinary editor-window default.
- **Current workbench dispatch:** DialogHandlerContribution.processDialogs in src/vs/workbench/electron-browser/parts/dialogs/dialog.contribution.ts selects BrowserDialogHandler or NativeDialogHandler for confirmations, prompts, and About. Its useCustomDialog getter checks window.dialogStyle and enableSmokeTestDriver; input dialogs are already custom-only.
- **Existing custom implementation:** src/vs/workbench/browser/parts/dialogs/dialogHandler.ts implements prompt, confirm, input, and about using the DOM-based Dialog widget. The native counterpart in src/vs/workbench/electron-browser/parts/dialogs/dialogHandler.ts calls nativeHostService.showMessageBox.
- **Functionality boundary:** src/vs/platform/windows/electron-main/windowImpl.ts independently displays native message boxes for an unresponsive window and a terminated renderer. These paths cannot depend on that failed renderer's DOM, so changing workbench dispatch alone would not deliver literal removal of all native message dialogs.
- **Reported maintainer interest:** The body of https://github.com/microsoft/vscode/issues/342843 attributes the proposal to a maintainer discussion and records agreement conditional on preserving functionality. This supports a design session, but does not establish an approved migration or recovery-dialog policy.
- **Related work and implementation search:** Public GitHub searches for open issues mentioning native/custom dialogs found related but distinct requests: https://github.com/microsoft/vscode/issues/338861 concerns visibility of Agents-window default overrides, and https://github.com/microsoft/vscode/issues/340002 concerns a new extension dialog API. Neither owns wholesale replacement of native message dialogs. A search for open pull requests referencing 342843 returned no results; the supplied timeline also contains no linked implementation.
