# Issue #15106 — Option to render proper scrollbar

[https://github.com/microsoft/vscode/issues/15106](https://github.com/microsoft/vscode/issues/15106)

## Summary

Existing editor settings cover persistent visibility, larger scrollbars, and page-wise track clicks, but do not fully deliver the requested supported, traditional scrollbar experience. Keep this accepted, well-supported request open: arrow settings remain unregistered, their vertical scrolling uses wheel-sized rather than line-sized steps, and the verified related issues are newer and narrower.

## Change summary

Offer traditional vertical and horizontal scrollbars with persistent visibility, larger click targets, arrow buttons, and page-wise track clicks.

## Best solution

Reuse the existing visibility, size, and page-scroll settings, and settle a supported, discoverable contract for arrow-button scrolling. Coordinate any workbench-wide treatment with the related visibility and width requests without replacing this broader, older report.

## Plan brief

- **Likely files:** `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/browser/viewParts/editorScrollbar/editorScrollbar.ts`, `src/vs/base/browser/ui/scrollbar/verticalScrollbar.ts`, `src/vs/base/browser/ui/scrollbar/horizontalScrollbar.ts`, `src/vs/base/browser/ui/scrollbar/scrollableElement.ts`, `src/vs/platform/list/browser/listService.ts`
- **Validation:** The plan should end with checks on Windows and Linux using a long, horizontally overflowing document: configured bars remain visible at rest, configured sizes apply, track clicks advance by a page, and a vertical arrow click advances exactly one rendered line. Verify runtime-setting behavior according to the chosen contract and preserve default mouse-wheel and drag behavior; include non-editor surfaces only if they are accepted into scope.
- **Behavior:**

  > Users want an optional traditional scrollbar experience with persistent bars, larger click targets, arrow controls, and page-wise track clicks. Existing editor settings already cover visibility, size, and track clicks; the outstanding contract is supported arrow navigation, including one-line vertical steps. Acceptance should verify both axes, operation without a mouse wheel, and consistent behavior on Windows and Linux. Existing default scrolling behavior should remain unchanged unless a maintainer explicitly chooses otherwise.
- **Trace:**

  > EditorScrollbar in src/vs/editor/common/config/editorOptions.ts registers visibility, size, and scrollByPage settings, while arrow flags remain validation-only options. The editor view's EditorScrollbar passes arrow flags when constructing SmoothScrollableElement but does not update them during configuration changes. VerticalScrollbar arrow activation routes through synthetic wheel events; ScrollableElement converts those to sensitivity-dependent 50-pixel steps rather than editor-line steps. Source inspection establishes partial support, but does not resolve the thread's conflicting Windows and Ubuntu workaround reports. Related https://github.com/microsoft/vscode/issues/66000 and https://github.com/microsoft/vscode/issues/30191 concern workbench visibility and width, while https://github.com/microsoft/vscode/issues/173851#issuecomment-1424513841 favors holistic treatment. Preserve ordinary wheel scrolling, dragging, and existing independent settings; do not infer that enabling the existing internal arrow flags fulfills the requested contract.
- **Open decisions:**
  - Should supported arrow controls initially apply only to text editors, or be part of a consistent workbench-wide scrollbar treatment?
  - Should traditional scrollbar behavior remain a combination of independent settings, or also have a single discoverable preset?
  - What horizontal arrow-step behavior should accompany the explicitly requested one-line vertical step?
