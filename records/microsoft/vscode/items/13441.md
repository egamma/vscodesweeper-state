# Issue #13441 — Multiple extensions registering the 'type' command

[https://github.com/microsoft/vscode/issues/13441](https://github.com/microsoft/vscode/issues/13441)

## Summary

Keep open: the extension API still rejects duplicate command registrations, so the internal command stack does not provide the requested temporary typing handoff. This accepted API request has 55 upvotes, and no verified older canonical or completed implementation was found.

## Change summary

Allow a temporary typing handler to consume jump-mode keystrokes and then return control to another extension's typing handler.

## Best solution

Define a supported extension API for composable typing interception, with explicit consumption, delegation, and disposal semantics, so jump extensions can coexist with modal editors. Preserve existing command registration behavior unless an API-owner decision explicitly changes that contract.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostCommands.ts`, `src/vs/workbench/api/browser/mainThreadCommands.ts`, `src/vs/workbench/api/test/browser/extHostCommands.test.ts`, `src/vs/platform/commands/common/commands.ts`
- **Validation:** After choosing the API contract, add automated extension API coverage for two cooperating typing handlers: the temporary handler consumes the two jump characters exactly once, disposal restores the modal handler, and subsequent typing reaches that handler. Manually exercise the original Jumpy/VSCodeVim scenario with extensions adapted to the chosen API, and verify ordinary typing and existing duplicate-command rejection remain unchanged where promised.
- **Behavior:**

  > A modal editing extension and a temporary jump-mode extension should coexist without competing for exclusive ownership of the type command. During jump mode, its two selection characters should trigger navigation without entering the document or being interpreted by the modal extension. On completion or cancellation, subsequent typing should return to the modal extension. Acceptance must cover consumption, restoration, and compatibility with extensions using the existing command API.
- **Trace:**

  > ExtHostCommands.registerCommand in src/vs/workbench/api/common/extHostCommands.ts rejects a second registration for the same ID and stores only one callback. CommandsRegistry in src/vs/platform/commands/common/commands.ts has internal stacking, but that cannot bypass the extension-host check; MainThreadCommands.$registerCommand bridges only registrations that pass it. src/vscode-dts/vscode.d.ts explicitly promises duplicate-registration errors, while onWillType and onDidType are internal editor events rather than public extension interception hooks. The source establishes the API gap, not a runtime reproduction of the current versions of the two extensions. Keep ordinary typing fast and avoid changing unrelated command semantics without an explicit contract decision. Related performance constraints are documented in https://github.com/microsoft/vscode/issues/65876 and https://github.com/microsoft/vscode/issues/75627; neither replaces this request.
- **Open decisions:**
  - Should typing cooperation use a new dedicated interception API while preserving duplicate-command errors, or intentionally change the public registration contract for the type command?
  - What public ordering and delegation semantics should cooperating handlers have, including how a temporary mode takes precedence, consumes input, and restores the previous handler?

## Evidence

- **Requested behavior and maintainer context:** https://github.com/microsoft/vscode/issues/13441 requests that Jumpy consume two keystrokes before restoring VSCodeVim handling. The supplied 2016-10-27 maintainer comment explains that typing interception was designed for one handler, not collaboration; subsequent comments propose temporary handlers and typing events rather than establish an implemented solution.
- **Current extension-host limitation:** src/vs/workbench/api/common/extHostCommands.ts:148-170 stores one callback per command ID and throws "command '…' already exists" when that ID is registered again. This directly explains the duplicate-registration error reported in the supplied 2024-11-10 comment.
- **Public API contract:** src/vscode-dts/vscode.d.ts:10977-10990 explicitly documents that registering an existing command identifier twice causes an error. The public declaration files expose neither onWillType nor onDidType; those events exist internally in src/vs/editor/browser/editorBrowser.ts, but are not an extension interception API.
- **Internal stacking is not public coverage:** src/vs/platform/commands/common/commands.ts:69-130 maintains a linked list of registrations, allowing an internal override to be removed. However, extension registrations must first pass ExtHostCommands.registerCommand's uniqueness check before reaching src/vs/workbench/api/browser/mainThreadCommands.ts:$registerCommand. The internal stack cited in the discussion therefore does not satisfy the central ask.
- **Existing-capability check:** Inspection of public command declarations, internal typing events, and contribution registrations found no supported typing-handler priority or handoff capability. Observing document changes or executing the default typing command would not provide the requested temporary interception followed by restoration of another extension's handler.
- **Canonical search:** Read-only GitHub searches for type-command conflicts, typing interception, and multiple-extension command registration found no verified older same-symptom canonical. https://github.com/microsoft/vscode/issues/65876 and https://github.com/microsoft/vscode/issues/75627 were read and verified open; both concern typing latency, were created after this report, and do not own its handler-composition request.
- **Accepted demand:** The supplied context records the Backlog milestone, feature-request and api labels, 55 community upvotes, and independent reports involving CodeAceJumper and Emacs-style keybindings. The gap is in VS Code's extension API, not grounds to close this as caused by a third-party extension.
