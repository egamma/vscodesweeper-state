## Plan brief

- **Likely files:** `src/mainImpl.ts`, `src/vs/platform/dialogs/electron-main/dialogMainService.ts`
- **Validation:** On Ubuntu 24 LTS with the KDE portal backend, reproduce File → Open Folder on the reported stable version and current main; record the selected dialog backend and advertised FileChooser portal version. Check Ctrl+L, entering an existing absolute directory, and Enter, alongside ordinary folder selection and initial-folder navigation.
- **Behavior:**

  > The reporter expects File → Open Folder to use the desktop-configured KDE chooser, but sees GTK instead, including after updating to 1.143.1. In that GTK chooser, Ctrl+L exposes path entry but Enter reportedly no longer confirms the entered path. Establish both behaviors on the reported environment before deciding whether they share a cause. Acceptance must cover direct-path confirmation, ordinary folder selection, and preservation of initial-folder navigation.
- **Trace:**

  > src/mainImpl.ts requires FileChooser portal version 4 to preserve current_folder support. DialogMainService.pickFolder, doPick, and showOpenDialog in src/vs/platform/dialogs/electron-main/dialogMainService.ts construct folder-selection options and delegate to Electron; GTK keyboard handling is outside those functions. https://github.com/microsoft/vscode/issues/231173 documents an older desktop-native-to-GTK fallback caused by the portal requirement, while https://github.com/microsoft/vscode/issues/252497 describes a COSMIC-specific manifestation. Neither proves this installation's cause or covers its Enter-key regression conclusively. The uncertainty starts at runtime portal negotiation and native chooser behavior; do not assume that lowering the portal requirement is an acceptable fix or discard the initial-folder behavior it protects.
