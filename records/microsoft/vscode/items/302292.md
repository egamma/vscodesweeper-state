# Issue #302292 — Allow custom-guardrails for autopilot's report `task_complete`

[https://github.com/microsoft/vscode/issues/302292](https://github.com/microsoft/vscode/issues/302292)

## Summary

Current Stop hooks substantially cover deterministic completion guardrails, but the requested named pass/fail reporting remains absent. This member-authored Backlog item must stay open because no fixing commit or linked PR explicitly references https://github.com/microsoft/vscode/issues/302292.

## Change summary

Allow users to define completion guardrails such as lint, test, and build checks and report their status when Autopilot completes a task.

## Best solution

Treat Stop hooks as the enforcement mechanism, then decide whether completion should additionally expose structured, named guardrail results in the task-completion report. Any reported status should come from deterministic hook execution rather than an unchecked model assertion.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/tools/builtinTools/taskCompleteTool.ts`, `extensions/copilot/src/extension/intents/node/toolCallingLoop.ts`, `extensions/copilot/src/platform/chat/common/chatHookService.ts`, `extensions/copilot/src/extension/intents/test/node/toolCallingLoopHooks.spec.ts`
- **Validation:** Add targeted completion-flow tests showing that a failed custom guardrail prevents completion, a passing guardrail permits completion, and any approved structured status is rendered from hook results rather than an unsupported model claim.
- **Behavior:**

  > Users can define project-specific conditions such as lint, test, or build success that are evaluated when an autonomous task attempts to finish. A failed condition keeps the agent working and provides an actionable reason; successful conditions allow completion. If named statuses are included in the completion report, they accurately reflect deterministic check results rather than model-only assertions. Existing sessions without custom guardrails retain their current completion behavior.
- **Trace:**

  > The current completion tool in src/vs/workbench/contrib/chat/common/tools/builtinTools/taskCompleteTool.ts has a fixed schema containing only `summary`. The newer Stop-hook path in extensions/copilot/src/extension/intents/node/toolCallingLoop.ts executes configured hooks before stopping, collects blocking reasons, and continues the model with those reasons; extensions/copilot/src/extension/intents/test/node/toolCallingLoopHooks.spec.ts confirms test- and lint-style failures can block completion. Hook contracts are defined in extensions/copilot/src/platform/chat/common/chatHookService.ts and the lifecycle event is registered in src/vs/workbench/contrib/chat/common/promptSyntax/hookTypes.ts. The remaining uncertainty is the user-visible reporting contract, not whether deterministic enforcement is possible. Preserve ordinary `task_complete` behavior and the other hook lifecycle events.
- **Open decisions:**
  - Are Stop-hook enforcement and its displayed blocking reasons the complete intended outcome, or should the final task-completion report expose named guardrail pass/fail results?
  - If named results are exposed, must every status originate from deterministic hook output, or may the model attest to checks that have no configured verifier?

## Evidence
