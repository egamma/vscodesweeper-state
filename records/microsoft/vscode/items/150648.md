# Issue #150648 — Bracket pair colorization: op-in-flag to only colorize on focus

[https://github.com/microsoft/vscode/issues/150648](https://github.com/microsoft/vscode/issues/150648)

## Summary

Keep this accepted, 59-upvote request open: current settings do not colorize only the focused context and its descendants. The older related request covers active-pair coloring, but does not establish ownership of the additional subtree and hover behavior requested here.

## Change summary

Add opt-in bracket colorization restricted to the cursor-selected context and its descendants, with bracket-adjacent and enclosing-context modes plus optional hover activation.

## Best solution

Provide focus-scoped bracket foreground colorization while preserving ordinary syntax colors outside the selected context and retaining the existing default behavior. Coordinate with the active-pair request, but settle the subtree and hover semantics explicitly rather than treating that narrower request as full coverage.

## Plan brief

- **Likely files:** `src/vs/editor/common/config/editorOptions.ts`, `src/vs/editor/common/model/bracketPairsTextModelPart/colorizedBracketPairsDecorationProvider.ts`, `src/vs/editor/contrib/bracketMatching/browser/bracketMatching.ts`
- **Validation:** Verify in an editor containing nested and sibling bracket blocks: bracket-adjacent mode activates only at a bracket boundary; context mode activates within the enclosing block; the chosen context and descendants receive depth colors while siblings and ancestors retain ordinary syntax colors. Check optional hover activation and restoration on mouse leave, independent behavior in two editors sharing a model, and unchanged default colorization. Add automated editor-decoration coverage for the agreed semantics.
- **Behavior:**

  > Users can opt into depth-based bracket colorization for only a focused bracket context and its descendants, leaving brackets outside it at their ordinary syntax colors. The request distinguishes activation adjacent to a bracket from activation anywhere inside an enclosing context, and additionally requests optional mouse-hover activation. Acceptance should cover nested and sibling contexts, entering and leaving activation boundaries, and unchanged behavior when the option is disabled. Hover precedence and multiple-cursor behavior need explicit product decisions.
- **Trace:**

  > BracketPairColorization in src/vs/editor/common/config/editorOptions.ts exposes only enabled and independentColorPoolPerBracketType; the active guide options are a separate capability. ColorizedBracketPairsDecorationProvider.getDecorationsInRange in src/vs/editor/common/model/bracketPairsTextModelPart/colorizedBracketPairsDecorationProvider.ts is model-owned and colors every returned bracket by nesting level without cursor or hover state. BracketMatchingController in src/vs/editor/contrib/bracketMatching/browser/bracketMatching.ts already tracks editor-local cursor positions and decorates a matching pair, with editorBracketMatch.foreground overriding its foreground, but it does not color descendants. The uncertainty begins at defining activation precedence and accommodating editor-local focus when a model is shared. Preserve existing guide behavior, ordinary matching, default colorization, and responsiveness. https://github.com/microsoft/vscode/issues/136646 is related active-pair work, not verified full-scope duplicate coverage.
- **Open decisions:**
  - When hover activation is enabled, does a hovered context temporarily replace the cursor-selected context, or are both contexts colorized?
  - With multiple cursors, should colorization include every cursor's selected context or only the primary cursor's context?
