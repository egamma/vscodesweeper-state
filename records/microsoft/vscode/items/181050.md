# Issue #181050 — editor.selectionClipboard option has no effect on vscode.dev

[https://github.com/microsoft/vscode/issues/181050](https://github.com/microsoft/vscode/issues/181050)

## Summary

The issue remains necessary: a maintainer confirmed the web editor does not instantiate the workbench contribution that enforces `editor.selectionClipboard`, and suggested moving this behavior to an editor feature. The On Deck milestone is a holding bin and does not force closure, but there is no evidence that the fix has landed.

## Change summary

Make `editor.selectionClipboard: false` suppress middle-click selection paste in vscode.dev as it does in the desktop workbench.

## Best solution

Move the selection-clipboard paste-prevention behavior from the Electron-only workbench contribution into an `IEditorFeature` that is instantiated by both workbench and standalone web editors, while preserving native selection clipboard behavior when the setting is enabled.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/codeEditor/electron-sandbox/selectionClipboard.ts`, `src/vs/editor/browser/editorExtensions.ts`
- **Validation:** Add an editor browser test that configures `editor.selectionClipboard` off, dispatches the relevant middle-button paste path in a standalone editor, and verifies that no text is inserted; retain coverage showing enabled behavior is unchanged where the platform supports it.
- **Behavior:**

  > In vscode.dev on Linux/Chromium, setting `editor.selectionClipboard` to `false` must prevent a middle click from inserting the current primary selection into an editor, matching desktop VS Code. With the setting enabled, supported environments must retain their existing selection-clipboard behavior. Normal clipboard paste and unrelated middle-click interactions must remain unchanged.
- **Trace:**

  > The maintainer diagnosis in https://github.com/microsoft/vscode/issues/181050 identifies the boundary: the prevention logic lives in `src/vs/workbench/contrib/codeEditor/electron-sandbox/selectionClipboard.ts` as a workbench contribution, while vscode.dev's standalone editor does not instantiate that contribution. The suggested shared lifecycle is `IEditorFeature`, registered through editor extension infrastructure such as `src/vs/editor/browser/editorExtensions.ts`. The uncertainty starts at how the browser-side feature should detect and suppress native middle-click paste without depending on Electron-only clipboard APIs. Preserve desktop behavior and do not alter ordinary clipboard commands.
- **Open decisions:**
  - Which part of the selection-clipboard logic can be made a shared `IEditorFeature`, and which Electron-specific clipboard integration must remain in the workbench contribution?
  - What browser event or editor hook can reliably suppress native middle-click primary-selection paste without interfering with other middle-button behavior?
  - What browser-capability guard is required for platforms that do not expose an X11-style selection clipboard?
