# Issue #331926 — Integrated browser remote proxy should support remote AHP hosts in Agents window

[https://github.com/microsoft/vscode/issues/331926](https://github.com/microsoft/vscode/issues/331926)

## Summary

The current proxy path remains window/workspace-based and does not select the remote AHP host associated with an agent session. Keep this team-authored request open: the existing setting does not cover it, and the related browser umbrella does not establish a duplicate.

## Change summary

Allow integrated-browser tabs to reach remote AHP-host endpoints through their associated Agents window session while preserving isolation and showing the remote indicator.

## Best solution

Support browser routing through the selected session's remote AHP host without requiring a separate Remote Workspace connection or manual port forwarding. Establish automatic versus explicit target-selection behavior and preserve isolation between sessions connected to different hosts.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/browserView/electron-browser/browserViewWorkbenchService.ts`, `src/vs/workbench/contrib/browserView/electron-browser/features/browserRemoteFeatures.ts`, `src/vs/platform/browserView/common/browserView.ts`, `src/vs/platform/browserView/electron-main/browserViewMainService.ts`, `src/vs/platform/browserView/electron-main/browserSessionRemote.ts`
- **Validation:** Use the report's nonce-returning remote loopback server on port 43127 and open both 127.0.0.1 and localhost URLs through the associated AHP session. Confirm the remote nonce and indicator, then use two hosts serving different nonces on the same port to verify session isolation; local tabs and existing Remote Workspace proxy behavior must remain unchanged.
- **Behavior:**

  > An Agents window session connected to a remote AHP host can open HTTP/HTTPS endpoints reachable only from that host in the integrated browser, without separate port forwarding. The reported loopback URLs must reach the remote server rather than the client, and the tab must indicate remote routing. Sessions attached to different hosts must not route through one another. Existing local browsing and Remote Workspace proxy behavior must remain intact.
- **Trace:**

  > BrowserViewWorkbenchService.willUseRemoteProxy() in src/vs/workbench/contrib/browserView/electron-browser/browserViewWorkbenchService.ts checks environmentService.remoteAuthority, while IBrowserViewWindowConfiguration in src/vs/platform/browserView/common/browserView.ts carries a single window-level proxyInfo. BrowserViewMainService applies that proxy to each view's BrowserSessionRemote during creation and configuration updates. BrowserSessionRemote in src/vs/platform/browserView/electron-main/browserSessionRemote.ts configures the underlying Electron session, making storage/session sharing a routing boundary. The inspected path establishes the existing capability gap but does not establish the AHP transport integration needed to supply a host-specific proxy. Preserve existing trust, network restrictions, agent-sharing gates, and local/workspace routing behavior. https://github.com/microsoft/vscode/issues/314789 provides related browser-experience context, not a verified duplicate of this routing requirement.
- **Open decisions:**
  - Should agent-opened tabs automatically use their owning session's remote AHP host, should routing require an explicit per-tab target, or should both behaviors be available?
  - When the associated AHP host disconnects or changes, should an existing tab remain bound to its original host and stop loading, or follow the session's newly selected host?

## Evidence

- **Existing capability does not cover AHP selection:** src/vs/workbench/contrib/browserView/electron-browser/browserViewWorkbenchService.ts:221–228 makes willUseRemoteProxy() return false without environmentService.remoteAuthority. The workbench.browser.enableRemoteProxy registration in features/browserRemoteFeatures.ts explicitly describes remote-workspace connections, not session-selected AHP hosts.
- **Current proxy ownership:** src/vs/platform/browserView/common/browserView.ts:155–171 defines one proxyInfo on IBrowserViewWindowConfiguration. browserViewMainService.ts:352–366 applies that window proxy to its views, and line 422 acquires the same window-level proxy when constructing a view; these paths do not select a proxy from the owning agent session.
- **Isolation boundary:** src/vs/platform/browserView/electron-main/browserSessionRemote.ts applies proxy configuration to the Electron session, not an individual navigation.
