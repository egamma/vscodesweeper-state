# Issue #338402 — PR status doesn't show on nested session

[https://github.com/microsoft/vscode/issues/338402](https://github.com/microsoft/vscode/issues/338402)

## Summary

Fresh, first-hand report from someone testing the nested-session/worktree flow directly (with a screenshot showing the missing status), so I treat the repro as credible even though I could not pin down the exact defective code path in the time available.

## Change summary

When a nested session creates a PR from its own worktree (a different workspace than the parent session), the PR status indicator never appears anywhere in the UI.

## Best solution

Trace why a nested session's own workspace/worktree doesn't get GitHub PR info resolved and surfaced the same way a top-level session's does, then fix the resolution or wiring so `session.workspace.folders[0].gitRepository.gitHubInfo.pullRequest` (or the nested session's own workspace equivalent) populates for nested sessions in worktrees.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts`, `src/vs/sessions/services/sessions/common/session.ts`, `src/vs/sessions/contrib/github/browser/models/githubPullRequestModel.ts`
- **Validation:** A test that creates a nested session whose own workspace is a worktree with an associated PR, and asserts the nested session's `gitHubInfo.pullRequest` observable populates and the corresponding status icon/context key (`SessionHasPullRequestContext`) is set — mirroring the existing top-level session PR-status tests.
- **Behavior:**

  > When a nested (child) session creates a pull request from its own worktree/workspace — distinct from the parent session's workspace — the PR status should be shown for that nested session in the Sessions list, the same way it is shown for a top-level session whose worktree has an open PR. Currently no status/icon appears anywhere for the nested session in this scenario.
- **Trace:**

  > PR status/icon computation in sessionsList.ts (lines ~1986, ~1526, ~5199) reads `session.workspace.read(reader)?.folders[0]?.gitRepository?.gitHubInfo.read(reader)?.pullRequest` (or equivalent) to decide whether to show a status. For a nested session created inside another session's worktree, either the nested session's `workspace` observable, its `gitRepository`, or the GitHub info resolution for that repo/worktree may not get populated or wired the same way a top-level session's does — this needs to be traced against the nested-session creation/worktree-assignment code (see SESSIONS_LIST.md's 'nested-session' terminology and the worktree creation dispatcher in src/vs/sessions/contrib/chat/browser/worktreeCreatedTaskDispatcher.ts) before changing anything. Do not touch top-level session PR-status behavior, which already works.
- **Open decisions:**
  - Should a nested session resolve its own git repository/GitHub info independently (its own worktree), or inherit/derive it from the parent session's workspace when the PR was created in the nested session's own worktree?
  - Is the missing status a resolution-timing issue (info not yet fetched) or a structural gap (nested sessions never get a `gitRepository`/`gitHubInfo` wired at all)?

## Evidence
