# Issue #252011 — Allow Diagnostic providers to enrich AI-driven fix workflows with context via an optional method

[https://github.com/microsoft/vscode/issues/252011](https://github.com/microsoft/vscode/issues/252011)

## Summary

Keep open: a VS Code maintainer endorsed the concept and identified a contribution-point direction, while noting that implementation needs community help. The request remains a genuine extension API gap and has no verified older canonical issue or existing capability that fully covers it.

## Change summary

Allow diagnostic providers to supply dynamic, domain-specific context for AI-driven diagnostic fix workflows.

## Best solution

Design a generic diagnostic remediation contribution API that lets extensions associate dynamic fix guidance with diagnostic codes, then consume that guidance in the core chat fix flow without coupling the API to one model or command.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostDiagnostics.ts`, `src/vs/workbench/api/browser/mainThreadDiagnostics.ts`, `extensions/copilot`
- **Validation:** Add extension API tests proving an extension can provide asynchronous remediation context for a diagnostic and that the chat fix request receives it, while diagnostics without a provider retain existing behavior.
- **Behavior:**

  > An extension that owns a diagnostic can optionally provide dynamic remediation guidance for that diagnostic. When the user invokes the AI-driven diagnostic fix flow, the guidance is available as contextual input; diagnostics without guidance behave exactly as today. Provider failure or cancellation must not prevent the normal fix flow, and guidance must be requested only for the diagnostic being fixed.
- **Trace:**

  > The public entry point is languages.createDiagnosticCollection() in src/vscode-dts/vscode.d.ts, with diagnostic collection transport handled through the extension-host diagnostics path in src/vs/workbench/api/common/extHostDiagnostics.ts and src/vs/workbench/api/browser/mainThreadDiagnostics.ts. The consumer is the core Copilot/chat diagnostic fix workflow under extensions/copilot. The maintainer comment at https://github.com/microsoft/vscode/issues/252011#issuecomment-3083191077 points to an earlier baked-in cookbook prototype and explicitly favors a contribution point. The boundary is a generic diagnostic-remediation contract: do not expose Copilot-specific model or prompt concepts in the public API, and preserve the existing diagnostic and fix behavior for providers that do not participate. The uncertainty starts at the public API shape, matching granularity, and lifecycle semantics.
- **Open decisions:**
  - Should the public contract be a per-collection callback invoked for a specific Diagnostic, or a declarative contribution keyed by diagnostic source and code?
  - Is remediation context intended only for the explicit user-invoked AI fix action, or may other automated diagnostic-remediation workflows consume it?
  - Should the contract return opaque text, structured remediation entries such as rationale/documentation/suggestions, or both?
