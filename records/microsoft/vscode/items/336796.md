# Issue #336796 — Add telemetry for main MCP failure modes

[https://github.com/microsoft/vscode/issues/336796](https://github.com/microsoft/vscode/issues/336796)

## Summary

Keep open as MCP observability debt: current main records only a coarse startup state and successful capability discovery, with no categorized tool-call outcome telemetry. The requested taxonomy spans several lifecycle layers and needs a telemetry-contract design before implementation.

## Change summary

Add privacy-safe telemetry that categorizes MCP startup, capability-discovery, and tool-execution failures by stage, transport, recovery behavior, and ownership boundary.

## Best solution

Define a bounded, GDPR-compliant failure taxonomy shared across MCP connection and request paths, then emit outcome events at the points that still retain stage, retry, cancellation, duration, and transport context. Cover representative startup, initialization, discovery, tool-call, retry, and cancellation outcomes with telemetry-capture tests that verify no user-provided content is emitted.

- **Behavior:**

  > MCP startup and tool-call outcomes must produce privacy-safe telemetry that distinguishes the major lifecycle stage and a bounded failure category. Events must record useful categorical context and duration/retry measurements without raw errors, commands, URLs, tool arguments, results, or server content. Successful behavior and existing retry, cancellation, authentication, and elicitation semantics must remain unchanged. Acceptance requires tests for representative startup, initialization, discovery, dispatch, retry/recovery, timeout, cancellation, schema, and server-returned-error outcomes.
- **Trace:**

  > Current startup telemetry is declared and emitted in `McpServer.start` in src/vs/workbench/contrib/mcp/common/mcpServer.ts, where `mcp/serverBootState` contains only final state and elapsed time. Transport launch and protocol initialization are separate in `McpServerConnection.start` and `adoptLaunch` in src/vs/workbench/contrib/mcp/common/mcpServerConnection.ts, but their errors converge into the same connection error state. Capability discovery runs through `_populateLiveData`, `_setServerTools`, and `_setServerPrompts` in mcpServer.ts. Tool execution and retry behavior live in `McpTool._callWithProgress`, while JSON-RPC dispatch and task-backed responses live in `McpServerRequestHandler.callTool` in src/vs/workbench/contrib/mcp/common/mcpServerRequestHandler.ts. The boundary is observability only: do not change MCP protocol behavior, retry eligibility, cancellation, user-interaction handling, tool results, or catalog-refresh semantics.
- **Open decisions:**
  - Which bounded lifecycle-stage and failure-category taxonomy should become the stable telemetry contract, including how transport, SDK/runtime, server-returned, validation, cancellation, and user-interaction failures are attributed?
  - Should startup outcomes extend `mcp/serverBootState` or move to a new versioned event, and what compatibility period is required for existing dashboards?

## Evidence

- **current startup telemetry:** src/vs/workbench/contrib/mcp/common/mcpServer.ts defines `mcp/serverBootState` with only `state` and `time`, and emits it immediately after `connection.start`; it does not retain a startup stage or normalized failure category.
- **failure stages remain distinct in source:** src/vs/workbench/contrib/mcp/common/mcpServerConnection.ts separates transport launch from `McpServerRequestHandler.create` protocol initialization, but both ultimately collapse into `McpConnectionState.Kind.Error` with a raw message.
- **tool-call gap:** McpTool._callWithProgress in src/vs/workbench/contrib/mcp/common/mcpServer.ts handles dispatch, URL elicitation, retry, and terminal failure around `h.callTool`, but emits no outcome telemetry; src/vs/workbench/contrib/mcp/common/mcpServerRequestHandler.ts sends `tools/call` and handles task-backed results without telemetry.
