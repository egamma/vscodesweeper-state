# Issue #336466 — Agent Host can send a queued steering message after removal or while it is being edited

[https://github.com/microsoft/vscode/issues/336466](https://github.com/microsoft/vscode/issues/336466)

## Summary

Both races remain source-reproducible on current main: removing a steering message updates protocol state without cancelling provider delivery, and entering edit mode is not represented in the Agent Host queue state. This team-authored issue should remain open for a coordinated workbench, host, and provider fix.

## Change summary

Make removal atomically cancel queued steering delivery and prevent a steering item from being delivered while the user is editing it.

## Best solution

Make steering delivery revision-aware and cancellable at the Agent Host/provider boundary, with host-visible editing state that makes an item ineligible until editing completes. All Agent Host providers should obey the same cancellation and latest-content contract without changing ordinary queued-turn ordering.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts`, `src/vs/platform/agentHost/common/agent.ts`, `src/vs/platform/agentHost/node/chatContributions/queueDrain/queueDrainContribution.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/platform/agentHost/node/claude/claudeSdkPipeline.ts`, `src/vs/platform/agentHost/node/codex/codexAgent.ts`, `src/vs/platform/agentHost/test/node/chatContributions.test.ts`
- **Validation:** Add targeted queue lifecycle tests that hold steering delivery before provider acceptance, then verify removal prevents delivery; separately begin editing while delivery would advance, verify no delivery occurs, complete the edit, and verify exactly the final saved content is delivered. Exercise the provider-specific cancellation contract for Copilot, Claude, and Codex.
- **Behavior:**

  > Removing a pending steering message before it is consumed must prevent that message from reaching the agent; once removal is reflected in the queue, later delivery is forbidden. While a pending steering item is being edited, it remains visible but is ineligible for delivery. Completing the edit makes only the resulting stable content eligible, without sending an intermediate revision. Existing FIFO behavior for ordinary queued turns remains unchanged.
- **Trace:**

  > AgentHostSessionHandler._syncPendingMessages in src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts mirrors only pending content, kind, removal, and ordering; ChatWidget.clickedRequest keeps edit state local to the workbench. QueueDrainContribution._syncPendingMessages immediately forwards the current steering value through IAgent.setPendingMessages after every pending action. Removal therefore reaches providers as undefined, which CopilotAgent, ClaudeAgent, and CodexAgent currently treat as a no-op; their already-started steering paths have no cancellation or revision check. The uncertainty begins at the cross-client lifecycle contract: editing must become an authoritative delivery gate, and removal must not disappear from UI unless the host can guarantee it will not subsequently be accepted. Keep regular queued-turn draining, provider transcript mapping, and unrelated turn routing out of scope. https://github.com/microsoft/vscode/issues/334023 is related provider-handoff work but has a different observable symptom and does not absorb this issue.
- **Open decisions:**
  - If removal arrives after a provider has irreversibly accepted steering but before consumption is reflected, should the UI reject the removal and keep the item visible, or must the delivery protocol retain a cancellable phase until the removal window closes?
  - Should editing ownership be represented in authoritative Agent Host state so one client pauses delivery for all connected clients, or remain local with a separate host-visible eligibility signal?

## Evidence

- **removal race on main:** src/vs/platform/agentHost/node/chatContributions/queueDrain/queueDrainContribution.ts handles ChatPendingMessageRemoved by updating state and calling setPendingMessages with no steering message, but there is no acknowledgement or cancellation barrier for a delivery already started by the preceding ChatPendingMessageSet.
- **provider cancellation gap:** src/vs/platform/agentHost/node/copilot/copilotAgent.ts, src/vs/platform/agentHost/node/claude/claudeAgent.ts, and src/vs/platform/agentHost/node/codex/codexAgent.ts all ignore an undefined steering message. CopilotAgentSession.sendSteering also awaits setup and attachment conversion before SDK send without revalidating that the message remains pending.
- **editing state gap:** src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts records editing only in ChatViewModel and does not remove or suspend the pending item until the edited request is submitted. src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts synchronizes pending additions, updates, removals, and ordering, but has no editing-state signal for the host.
- **established expectation:** https://github.com/microsoft/vscode/issues/289499 explicitly requires auto-send to remain blocked while a queued item is being edited and dismissal to remove the item.
- **not a duplicate:** The older open https://github.com/microsoft/vscode/issues/334023 reports a steering message remaining queued and never reaching the provider during SDK refresh. It does not report the same observable symptom as this re-reviewed issue, where removed or actively edited content is delivered.
