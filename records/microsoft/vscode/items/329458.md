# Issue #329458 — agents window will use key bindings from disabled extension

[https://github.com/microsoft/vscode/issues/329458](https://github.com/microsoft/vscode/issues/329458)

## Summary

The defect remains traceable on current main: the Agents profile shares installed extensions but has separate profile storage for globally disabled-extension identifiers, allowing an otherwise permitted extension's keybindings to remain active. This team-authored Backlog bug should stay open for a targeted extension-enablement fix.

## Change summary

Ensure the Agents Window does not register keybindings contributed by an extension the user disabled globally.

## Best solution

Make the Agents profile inherit the default profile's global extension-enablement state while retaining its own unrelated profile and workspace state. Extension-point processing should consequently exclude disabled extensions before their keybindings reach the Agents Window resolver.

## Plan brief

- **Likely files:** `src/vs/platform/extensionManagement/common/extensionEnablementService.ts`, `src/vs/platform/userDataProfile/common/userDataProfile.ts`, `src/vs/workbench/services/extensionManagement/test/browser/extensionEnablementService.test.ts`
- **Validation:** Add a focused extension-enablement test proving that an extension disabled globally in the default profile remains disabled in an Agents Window profile that shares extensions, then run `scripts/test.sh --grep "disabled extension remains disabled in sessions window"`.
- **Behavior:**

  > When an extension is globally disabled in the user's default profile, opening or reloading the Agents Window must not register or execute that extension's contributed keybindings. This must hold for extensions otherwise permitted to run or contribute declarative keybindings in the Agents Window. Enabled supported extensions and Agents-specific workspace enablement behavior must remain unchanged. Acceptance is a focused regression test covering the default-profile-to-Agents-profile transition.
- **Trace:**

  > The Agents profile is created with `useDefaultFlags.extensions: true` in src/vs/platform/userDataProfile/common/userDataProfile.ts, so it shares the default profile's installed-extension resource, but it does not use default profile storage. `GlobalExtensionEnablementService` in src/vs/platform/extensionManagement/common/extensionEnablementService.ts stores disabled identifiers under `DISABLED_EXTENSIONS_STORAGE_PATH` at `StorageScope.PROFILE`, leaving the Agents profile with a different disabled set. `ExtensionEnablementService._getUserEnablementState` in src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts reads that set before extension-point processing, and WorkbenchKeybindingService registers bindings from the resulting enabled descriptions. Preserve separate Agents profile state generally: do not solve this by sharing all global state, and do not change keybinding precedence or the Agents Window extension-support policy. The uncertainty starts at the ownership boundary between profile-resource inheritance and profile-scoped extension-enable­ment storage.

## Evidence

- **confirmed report:** The team-authored report provides deterministic steps and a recording at https://github.com/microsoft/vscode/issues/329458#issuecomment-5207863723 showing VSCodeVim's Ctrl+F action firing after the extension was disabled.
- **profile boundary:** src/vs/platform/userDataProfile/common/userDataProfile.ts gives the Agents profile `useDefaultFlags.extensions: true`, sharing the installed-extension resource, but omits `globalState`; src/vs/platform/storage/common/storage.ts:isProfileUsingDefaultStorage therefore gives it separate profile storage.
- **root cause:** src/vs/platform/extensionManagement/common/extensionEnablementService.ts:GlobalExtensionEnablementService stores `extensionsIdentifiers/disabled` in `StorageScope.PROFILE`. The Agents profile consequently does not observe disabled identifiers recorded in the default profile.
- **observable path:** src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts computes global enablement from that profile-scoped list, while src/vs/workbench/services/keybinding/browser/keybindingService.ts registers keybindings from every extension description delivered through the keybindings extension point. An extension permitted in the Agents Window can therefore contribute its bindings despite being disabled in the default profile.
- **no landed fix:** Current main retains the separate storage behavior, and searches found no open or merged pull request referencing https://github.com/microsoft/vscode/issues/329458 and no older open canonical reporting the same observable symptom.
