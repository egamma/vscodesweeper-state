# Issue #319919 — workbench.colorTheme getting wiped when switching profiles

[https://github.com/microsoft/vscode/issues/319919](https://github.com/microsoft/vscode/issues/319919)

## Summary

The reporter supplied the requested recording, and the current source contains a profile-switch ordering path that can overwrite a profile-specific contributed theme with Dark 2026. This should remain open as a confirmed bug and be routed to the themes and user-profiles owners.

## Change summary

Switching away from and then back to the Default profile can remove its contributed `workbench.colorTheme` value and replace it with Dark 2026.

## Best solution

Preserve each profile's configured color theme while extension hosts restart during a profile switch. A temporarily unavailable contributed theme may render with a fallback, but that fallback must not be persisted over the profile's setting.

- **Validation:** Add a browser unit test that simulates switching from a profile using a profile-specific contributed theme to one without that extension, asserts the fallback does not modify the source profile's `workbench.colorTheme`, and asserts switching back restores that theme; run it with `scripts/test.sh --grep "preserves contributed color theme when switching profiles"`.
- **Behavior:**

  > When a profile uses a contributed color theme, switching to a profile where that theme extension is unavailable must not remove or replace the source profile's `workbench.colorTheme` setting. The destination profile may display its normal fallback theme. Switching back must restore the source profile's configured contributed theme. Genuine theme selection and extension-uninstall behavior outside profile switching must remain unchanged.
- **Trace:**

  > `UserDataProfileManagementService.changeCurrentProfile` stops extension hosts before `IUserDataProfileService.updateCurrentProfile`, temporarily removing profile-scoped theme contributions while the old profile remains active. The color-theme registry listener in `WorkbenchThemeService.installRegistryListeners` responds by selecting Dark 2026 through `setColorTheme(..., 'auto')`, and `ThemeConfiguration.writeConfiguration` persists that fallback into the still-current profile. The issue's installed extensions include the contributed Ayu theme, and the supplied recording demonstrates the setting loss. Keep the boundary narrow: do not make extensions global across profiles, alter normal profile configuration loading, or prevent a fallback from being displayed when a theme is genuinely unavailable.

## Evidence

- **reporter reproduction:** The reporter supplied the requested screen recording in https://github.com/microsoft/vscode/issues/319919#issuecomment-4632840664 after a maintainer could not reproduce locally.
- **profile-switch ordering:** `UserDataProfileManagementService.changeCurrentProfile` in src/vs/workbench/services/userDataProfile/browser/userDataProfileManagement.ts stops extension hosts before calling `userDataProfileService.updateCurrentProfile(profile)`, so extension-contributed themes can disappear while configuration still targets the old profile.
- **destructive fallback path:** `WorkbenchThemeService.installRegistryListeners` in src/vs/workbench/services/themes/browser/workbenchThemeService.ts handles removal of the current contributed theme by calling `setColorTheme(defaultTheme, 'auto')`; `ThemeConfiguration.writeConfiguration` in src/vs/workbench/services/themes/common/themeConfiguration.ts persists an `auto` update, allowing the Dark 2026 fallback to overwrite the old profile's setting.
