# Issue #338618 — Modern UI Status bar lacks top padding, breaking themes with a distinct status bar color

[https://github.com/microsoft/vscode/issues/338618](https://github.com/microsoft/vscode/issues/338618)

## Summary

Fresh, well-illustrated report of a real asymmetry in the experimental Modern UI status bar; source tracing finds a plausible root cause in how the floating-panels layout grows the status bar's height, but no maintainer or second reporter has weighed in yet on a same-day issue.

## Change summary

In the experimental Modern UI (floating panels), the status bar's top inset looks smaller than its bottom inset whenever `statusBar.background` differs from the surrounding chrome, making the bar look asymmetric/cramped.

## Best solution

Reconcile the item-centering padding in floatingPanels.css (`padding-top`/`padding-bottom: var(--vscode-spacing-size20)`) with the bottom-only height growth (`StatusbarPart.FLOATING_BOTTOM_PADDING`/`COMPACT_DENSITY_FLOATING_BOTTOM_PADDING` in statusbarPart.ts) so the colored bar's visible top and bottom insets read as equal regardless of theme.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/statusbar/statusbarPart.ts`, `src/vs/workbench/browser/media/floatingPanels.css`
- **Validation:** Manually verify with `workbench.experimental.modernUI` enabled, across default/compact density and with a theme where `statusBar.background` differs from the surrounding chrome, that the visible margin above the status bar's item row matches the margin below it.
- **Trace:**

  > The Modern UI status bar's rendered height is `StatusbarPart.HEIGHT` (22px) plus a bottom-only constant (`FLOATING_BOTTOM_PADDING`=6 or `COMPACT_DENSITY_FLOATING_BOTTOM_PADDING`=4, in statusbarPart.ts), while `floatingPanels.css` applies a fixed, symmetric `padding-top`/`padding-bottom: var(--vscode-spacing-size20)` (2px) that does not account for that extra bottom-only growth. The themed background is painted on the full `.part.statusbar` container (`updateStyles()` sets `container.style.backgroundColor` directly), so the extra bottom-only space appears as part of the colored bar, reading as more room below the items than above — matching the reporter's screenshots. Do not touch the window-edge outer-gutter behavior (`--modern-ui-floating-card-statusbar-margin`) or the compact/activity-bar-compact/noactivitybar variants without checking each still looks correct.
- **Open decisions:**
  - Should the extra bottom-only growth be balanced by adding equivalent space at the top (increasing overall part height further), or should the existing height be redistributed so the colored bar itself stays visually centered within its fixed footprint?
  - Is the current bottom-only growth serving double duty (item centering AND the window-edge gutter gap), and if so should those two concerns be split into separate, independently tunable values?

## Evidence

- **height growth is bottom-only:** src/vs/workbench/browser/parts/statusbar/statusbarPart.ts lines ~127-141: `minimumHeight`/`maximumHeight` = `StatusbarPart.HEIGHT` (22) + `floatingBottomPadding` (6, or 4 in compact density) — the part's total rendered height grows only via this bottom-side constant.
- **CSS padding is nominally symmetric:** src/vs/workbench/browser/media/floatingPanels.css lines 351-357: `.monaco-workbench.floating-panels .part.statusbar` sets `padding-top`/`padding-bottom: var(--vscode-spacing-size20)` (2px each per test fixtures) — equal on both sides, so it does not compensate for the extra bottom-only height added in code.
- **background paints the full grown box:** statusbarPart.ts `updateStyles()` sets `container.style.backgroundColor` directly on the `.part.statusbar` container, i.e. the themed color fills the entire height including the bottom-only growth, while nothing adds matching space above — consistent with the reporter's screenshots showing the colored bar's item row sitting closer to its top edge than its bottom edge.
- **code comment confirms centering intent:** The comment above `FLOATING_BOTTOM_PADDING` states the part 'grows by this amount and the matching padding is applied in floatingPanels.css' so items 'remain centered' — but the CSS padding is a fixed symmetric constant, not derived from `floatingBottomPadding`, so the stated intent and the actual values are not obviously reconciled.
