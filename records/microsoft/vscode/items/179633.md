# Issue #179633 — Need a UI message when an extension fails to initialize

[https://github.com/microsoft/vscode/issues/179633](https://github.com/microsoft/vscode/issues/179633)

## Summary

The gap remains on current main: ordinary activation failures in a built product are logged rather than surfaced in the Extensions UI. This team-authored, under-discussion request should remain open while maintainers decide how to provide prominent diagnostics without producing misleading notification noise.

## Change summary

Give users a visible indication when an installed extension fails during activation instead of exposing the failure only through developer diagnostics.

## Best solution

Represent activation failure prominently in the Extensions experience, with accessible error details and a clear association with the responsible extension, while avoiding repeated global notifications. The design should preserve the existing actionable handling for missing dependencies and the development-mode notification behavior.

## Plan brief

- **Likely files:** `src/vs/workbench/api/browser/mainThreadExtensionService.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/services/extensions/common/extensions.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsWidgets.ts`, `src/vs/workbench/contrib/extensions/browser/extensionFeaturesTab.ts`
- **Validation:** Add a unit test that reports an ordinary activation error in built-product mode and asserts the selected user-visible extension status or notification state, then run scripts/test.sh with a grep matching that activation-error test; manually verify that one failing extension produces one discoverable indication with its error details.
- **Behavior:**

  > When an installed extension throws from activate(), users must receive a discoverable UI indication that identifies the extension and exposes the failure details. The indication must not imply that VS Code itself failed, and repeated activation attempts must not flood global notifications. Development-mode activation errors and the existing actionable prompts for missing dependencies must remain unchanged.
- **Trace:**

  > The failure arrives at MainThreadExtensionService.$onExtensionActivationError in src/vs/workbench/api/browser/mainThreadExtensionService.ts. After specialized missing-dependency handling, built-product mode only logs the error; AbstractExtensionService._onDidActivateExtensionError in src/vs/workbench/services/extensions/common/abstractExtensionService.ts records telemetry but does not update IExtensionRuntimeStatus. The Extensions UI in extensionsWidgets.ts and extensionFeaturesTab.ts already renders runtimeErrors and messages from that status, establishing a nearby presentation path but not whether activation failures belong in those existing categories. The boundary excludes the tailored dependency prompts and development-mode notification. The uncertainty begins at the product choice among a global notification, a persistent Extensions view status, or a dedicated extension-notification surface.
- **Open decisions:**
  - Should activation failure appear only as persistent status in the Extensions UI, as a global notification, or in a dedicated extension-notification surface?
  - Should activation failures be represented as runtime errors, as status messages, or as a distinct status category with separate lifecycle semantics?
  - How should repeated failures be deduplicated, cleared after successful activation, and retained across extension-host restarts?

## Evidence

- **current activation path:** src/vs/workbench/api/browser/mainThreadExtensionService.ts::$onExtensionActivationError still calls the notification service only in development mode; for an ordinary activation failure in a built product it reaches console.error(error.message).
- **status propagation gap:** src/vs/workbench/services/extensions/common/abstractExtensionService.ts::_onDidActivateExtensionError emits telemetry but does not retain the error in extension status or fire onDidChangeExtensionsStatus; _onExtensionRuntimeError does both.
- **existing Extensions UI:** src/vs/workbench/contrib/extensions/browser/extensionsWidgets.ts and extensionFeaturesTab.ts expose runtimeErrors and status messages obtained through ExtensionsWorkbenchService.getExtensionRuntimeStatus, but activation errors are not currently added to either collection.
- **maintainer discussion:** The discussion explicitly weighs a more prominent Extensions view or future extension notification center against global error notifications that users may misattribute to VS Code; the final maintainer comment chose to wait for the new extension UI rather than declining the request.
- **no competing implementation:** No open microsoft/vscode pull request referencing issue 179633 was found, and repository history contains no commit explicitly referencing this issue.
