# Issue #179633 — Need a UI message when an extension fails to initialize

[https://github.com/microsoft/vscode/issues/179633](https://github.com/microsoft/vscode/issues/179633)

## Summary

Keep open for the extension-host UI discussion. Maintainers agreed activation failures should remain visible through extension-owned UI, potentially more prominently, but intentionally deferred the exact presentation rather than choosing global error notifications.

## Change summary

Make extension activation failures visibly discoverable in normal VS Code usage instead of leaving customers to inspect the Developer Tools console.

## Best solution

Surface activation failures prominently in the Extensions experience, clearly attributing each failure to its extension and offering access to diagnostics without flooding the global notification center.

## Plan brief

- **Likely files:** `src/vs/workbench/api/browser/mainThreadExtensionService.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsViewlet.ts`
- **Validation:** Use an extension whose activate() throws, launch it outside extension-development mode, and verify the normal Extensions UI presents a prominent extension-attributed failure with accessible diagnostics while unrelated global error notifications are not introduced.
- **Behavior:**

  > When an installed extension throws during activation, users should be able to discover the failure through normal VS Code UI without opening Developer Tools. The presentation must clearly attribute the failure to the extension rather than suggesting that VS Code itself failed. It should expose enough detail to begin troubleshooting and avoid flooding users with global notifications when multiple extensions fail.
- **Trace:**

  > The issue identifies activation-error handling in src/vs/workbench/api/browser/mainThreadExtensionService.ts and contrasts development-mode notification behavior with retail console logging. Maintainers state that activation errors are also represented in the Extensions and Running Extensions views, and that global notifications were previously avoided because users blamed VS Code; the discussion then defers to a newer extension UI. The technical trace should therefore follow the activation-error event from MainThreadExtensionService into the extension status/error rendering path and determine whether current main makes that state prominent enough. Preserve extension attribution and existing developer diagnostics; do not convert every activation failure into an undifferentiated global VS Code error notification.
- **Open decisions:**
  - Should activation failure remain an Extensions-view status made more prominent, or appear in a dedicated extension-notification surface?
  - What user action should the failure surface provide: reveal extension diagnostics, open logs, or show the activation exception inline?
