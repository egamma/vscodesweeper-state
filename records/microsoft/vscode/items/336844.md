# Issue #336844 — Agent Host: permission mode can race managed-settings resolution

[https://github.com/microsoft/vscode/issues/336844](https://github.com/microsoft/vscode/issues/336844)

## Summary

The retry mitigation already on main (`syncPermissionMode` in copilotAgentSession.ts) is a best-effort race-narrower, not the authoritative barrier the issue asks for, and the 2026-09-28 comment shows the rejection still occurring on current Insiders — matches the reopened state, so this stays open pending a real design fix.

## Change summary

Copilot Agent Host session startup can request the `allow-all` SDK permission mode before managed-settings resolution finishes, so the SDK sometimes rejects it and the turn fails with 'Copilot SDK rejected permission mode allow-all'.

## Best solution

Replace the current optimistic-set-then-retry-once-with-timeout approach in `syncPermissionMode` (copilotAgentSession.ts:5072) with an authoritative gate: don't attempt `allow-all` at turn start until `_managedSettingsResolved` has actually settled (or a policy-driven signal establishes there is no managed-settings authority to wait for), so the effective mode is clamped before the RPC call instead of raced against it.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`, `src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts`
- **Validation:** A test asserting `syncPermissionMode('turn-start')` never calls `rpc.permissions.setMode('allow-all')` before `_managedSettingsResolved` has settled (or an explicit 'no managed-settings authority' signal), including for sessions where the SDK never emits `session.managed_settings_resolved`.
- **Trace:**

  > `syncPermissionMode` (copilotAgentSession.ts:5072-5100) computes the desired SDK mode and calls `_trySetSdkPermissionMode` immediately; only on rejection does it wait up to `managedSettingsPermissionRetryTimeoutMs` (3000ms, line 860) for `_managedSettingsResolved` before one retry, then throws if still rejected. `_managedSettingsResolved` is a `DeferredPromise` (line 1186) completed only by the `onManagedSettingsResolved` handler (line 8134) — nothing settles it proactively before the first mode-set attempt. Do not touch the sandbox-policy projection path (`copilotSandboxPolicy.ts`) or the non-permission parts of `syncPermissionMode` (experimental-mode toggling).
- **Open decisions:**
  - Should turn-start block on managed-settings resolution (bounded or unbounded) before ever attempting `allow-all`, instead of attempting first and retrying on rejection?
  - For sessions/orgs with no managed-settings authority at all, how does the barrier avoid waiting indefinitely — is there an existing 'no policy applies' signal, or does one need to be added?

## Evidence

- **mitigation exists but is probabilistic:** src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:5089-5099 — `syncPermissionMode` tries `_trySetSdkPermissionMode(mode)` first, and only if that fails and managed settings weren't yet resolved does it `raceTimeout(this._managedSettingsResolved.p, managedSettingsPermissionRetryTimeoutMs)` (3000ms, line 860) before one retry; if the SDK still hasn't resolved managed settings within that window, it throws 'Copilot SDK rejected permission mode ...' — the exact reported error.
- **deferred never guaranteed to settle promptly:** `_managedSettingsResolved` (line 1186) is only completed inside `wrapper.onManagedSettingsResolved` (line 8134) when the SDK fires `session.managed_settings_resolved`; there's no proactive await of that signal before the initial mode set, so the first attempt can race it exactly as described.
- **reopened + persists on latest Insiders:** Comment from bryanchen-d (2026-09-28) on VS Code Insiders 1.140.0-insider (fee7930e) reproduced the same 'Copilot SDK rejected permission mode allow-all' error on a fresh Dev Container, then could not reliably reproduce it a second time — consistent with a narrow, not eliminated, race window.
- **related but distinct:** https://github.com/microsoft/vscode/issues/338507 covers a different symptom (harness sends allow-all despite Manual being selected) and is cited only as related, not a duplicate of this race.
