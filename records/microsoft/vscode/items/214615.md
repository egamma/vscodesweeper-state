# Issue #214615 — MSYS/Cygwin paths are not supported as terminal links

[https://github.com/microsoft/vscode/issues/214615](https://github.com/microsoft/vscode/issues/214615)

## Summary

MSYS/Cygwin drive-path translation remains missing from terminal link resolution, and maintainers explicitly welcomed a terminal-local implementation. Keep this correctly routed request open; the supported mount conventions and disambiguation behavior need a product decision.

## Change summary

Make Windows terminal links recognize MSYS/Cygwin absolute paths and open the corresponding file at the reported line without manual path editing.

## Best solution

Support MSYS/Cygwin path resolution within the terminal link subsystem while preserving displayed link text, source positions, and existing Windows/WSL behavior. Establish when translation applies and which mount conventions are supported before implementation; leave shared core path semantics unchanged.

- **Behavior:**

  > On Windows, compiler diagnostics using supported MSYS/Cygwin absolute-path notation should open the corresponding native file at the diagnostic line without requiring edits in Quick Open. The reported forms are /d/Projects/test/foo.cpp:123 and /cygdrive/d/Projects/test/foo.cpp:123. Link highlighting must continue to match the original terminal output. Existing native Windows, WSL, and remote POSIX links must retain their behavior; supported custom mounts and ambiguous paths require agreement before acceptance cases are finalized.
- **Trace:**

  > TerminalLocalLinkDetector.detect in src/vs/workbench/contrib/terminalContrib/links/browser/terminalLocalLinkDetector.ts constructs candidates and buffer ranges, then _validateLinkCandidates delegates to TerminalLinkResolver.resolveLink. In terminalLinkResolver.ts, suffix removal precedes WSL-specific translation; other slash-prefixed paths reach _preprocessPath and native normalization without MSYS/Cygwin drive conversion. Resolved URIs are separate from displayed text, so the terminal subsystem already has a boundary for differing display and destination paths. https://github.com/microsoft/vscode/pull/214435 was closed unmerged because its shared path.ts approach was too risky, while maintainers welcomed a terminal-local solution. The Windows suite in terminalLocalLinkDetector.test.ts supplies file-service resources and checks wrapped links, including WSL translation. Preserve shared core path behavior and unrelated link handling. Uncertainty starts at when Windows terminals should interpret POSIX-looking paths as MSYS/Cygwin mounts and how non-default mounts are represented.
- **Open decisions:**
  - Should initial support cover only the reporter's /<drive>/ and /cygdrive/<drive>/ conventions, or also configurable Cygwin mount prefixes?
  - Should translation apply to every local Windows terminal or only an identified MSYS/Cygwin shell, and which interpretation should win when a literal Windows path and a translated drive path both exist?

## Evidence

- **Remaining capability gap:** In src/vs/workbench/contrib/terminalContrib/links/browser/terminalLinkResolver.ts, resolveLink removes line/column suffixes and specifically translates /mnt/ WSL paths, but otherwise calls _preprocessPath. Slash-prefixed /d/Projects/test/foo.cpp and /cygdrive/d/Projects/test/foo.cpp are normalized without converting their drive component to D:. No MSYS/Cygwin translation appears in this resolver.

Existing WSL translation and file: URI support do not resolve unmodified MSYS/Cygwin compiler output.
