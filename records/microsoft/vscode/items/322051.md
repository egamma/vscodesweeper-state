# Issue #322051 — No credits spent shown when a request is stopped in Auto mode

[https://github.com/microsoft/vscode/issues/322051](https://github.com/microsoft/vscode/issues/322051)

## Summary

The model-identification portion has since improved, but current main still cannot report credits for a user-stopped request because cancellation results carry no usage data and the response stream receives credits only after a successful fetch. A maintainer explicitly reopened and retained this public issue, so it should remain open for the unresolved cancellation-accounting path.

## Change summary

Show the Auto-selected model and consumed credits in the response footer even when the user stops a chat request.

## Best solution

Preserve the resolved Auto model and final billable usage when a request is cancelled, then publish that information through the existing response usage/footer path. The client and Copilot service contract must first establish how authoritative usage is delivered after cancellation.

- **Behavior:**

  > When a user stops an Auto-mode request after routing or generation has begun, the completed response still identifies the model Auto selected and shows the credits actually consumed. The values must be authoritative rather than estimated, and stopping before any billable model call must not invent usage. Normally completed requests and fixed-model requests must retain their current footer behavior.
- **Trace:**

  > The current cancellation response union in extensions/copilot/src/platform/chat/common/commonTypes.ts has neither usage nor resolved-model fields. Cancellation branches in extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts return that reduced shape, and ToolCallingLoop in extensions/copilot/src/extension/intents/node/toolCallingLoop.ts publishes credits only from a successful fetch result. Auto model visibility now also has an inline `autoModeResolution` path in the core chat model and renderer, so the remaining uncertainty is chiefly how authoritative final usage reaches the client after cancellation. Keep the scope to stopped-request attribution; do not alter billing calculations, successful-request accounting, or unrelated cancellation behavior.
