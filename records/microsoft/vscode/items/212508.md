# Issue #212508 — After updating to version 1.89 my $HOME path is incorrect. And not able to change it.

[https://github.com/microsoft/vscode/issues/212508](https://github.com/microsoft/vscode/issues/212508)

## Summary

Still reproduces on main: `_encodeColons` only escapes `:` → `\x3a` and never backslash, while `shellIntegration-bash.sh` decodes values with `echo -e`, so a raw backslash in an env var value (e.g. produced when HOME is passed through) is reinterpreted as an escape sequence and corrupts `$HOME`. An open PR (#240614) already targets this exact root cause and names this issue, so this should stay open pending that PR, not be closed or auto-fixed separately.

## Change summary

After 1.89, Git Bash's $HOME (and other shell-integration-reported env vars) can get corrupted on Windows because backslash escape sequences in the value are misinterpreted during decoding.

## Best solution

Land/finish PR https://github.com/microsoft/vscode/pull/240614, which encodes backslashes (not just colons) before they're echoed with `echo -e` in shellIntegration-bash.sh — that closes the gap this issue reports.

## Evidence

- **current source:** src/vs/platform/terminal/common/environmentVariableCollection.ts:109-111 `_encodeColons` only replaces ':' with '\x3a'; backslashes in the value are left untouched before being embedded in the VSCODE_ENV_* string.
- **decode side:** src/vs/workbench/contrib/terminal/common/scripts/shellIntegration-bash.sh:75/85/94 decode with `VALUE="$(echo -e "$ITEM" | cut -d "=" -f 2-)"`, so any literal backslash (e.g. from a username/path segment) is interpreted as an escape sequence by `echo -e`, matching the corrupted-HOME symptom reported here.
- **open fixing PR:** https://github.com/microsoft/vscode/pull/240614 ('Fix missing encoding of backslash in terminal shell integration environment variable values') is still open, and its description explicitly lists 'May also deal with ... https://github.com/microsoft/vscode/issues/212508'.
