# Issue #343587 — Centralize customization migration availability state

[https://github.com/microsoft/vscode/issues/343587](https://github.com/microsoft/vscode/issues/343587)

## Summary

Keep open: current main still has two independent migration-availability state owners. The merged banner fix addresses same-context flicker, not the shared-controller work requested here.

## Change summary

Centralize customization migration availability and its asynchronous transitions across migration banners and the Agents navigation indicator.

## Best solution

Establish shared workbench-owned availability state consumed by both windows, with one tested transition contract and presentation-specific behavior retained in the consumers. Preserve existing telemetry, dismissal, focus, and layout semantics.

- **Validation:** Add deferred-promise transition tests covering initial discovery, retained hints during same-context refresh, empty completion, context replacement, repeated triggers, ignore/restore, disablement, dismissal, cancellation, disposal, and discovery failure. Run those with the existing ChatCustomizationMigrationNotice, Customizations toolbar, and NewChatMigrationNotice suites using scripts/test.sh with targeted selectors; verify visibility/focus callback counts and telemetry semantics. Check module layering if shared ownership introduces new imports. These checks are proposed, not executed.
- **Behavior:**

  > All migration surfaces must follow one availability contract: initial discovery is unavailable, same-context refresh retains the last completed hint, and a completed empty result removes availability. Context replacement and existing immediate-hide conditions must prevent inapplicable hints from appearing, including when obsolete requests resolve later. Ignore and restore changes must reach every applicable consumer consistently. Banner layout, keyboard behavior, focus callbacks, and hintComputed/hintShown telemetry must retain their existing semantics without refresh-induced visibility transitions.
- **Trace:**

  > ChatCustomizationMigrationNotice owns retained hints and a session/workspace/project context key, while CustomizationsNavigationState independently owns a boolean and invokes computeMigrationHint for its active session. Both implement subscriptions, cancellation, ignored-group filtering, and discovery-error handling; both currently clear their retained state on an active request's failure. NewChatMigrationNotice and ChatWidget supply different presentation contexts and dismissal/discovery behavior, so their differences must survive consolidation without introducing a Sessions dependency into workbench. The patch for https://github.com/microsoft/vscode/pull/343593 repairs banner stale-while-revalidate behavior only; current source still contains both owners. Existing deferred-promise consumer tests provide a validation starting point. The unresolved product policy is whether a failed same-context refresh should hide previously valid availability or retain it; the issue explicitly requests a documented discovery-error policy but does not choose one.
- **Open decisions:**
  - When same-context discovery fails after a successful result, should all consumers hide availability as they currently do, or retain the last completed hint until successful discovery or explicit invalidation?
