# Issue #189445 — Cursor moves to breakpoint when Debug: Focus Editor On Break is turned off

[https://github.com/microsoft/vscode/issues/189445](https://github.com/microsoft/vscode/issues/189445)

## Summary

A real behavior gap remains: disabling `debug.focusEditorOnBreak` preserves DOM focus but still opens the stopped stack frame with a selection, moving the caret. The debug owner acknowledged the distinction and left the desired setting semantics open, so this should remain the canonical request and be classified as a feature request rather than a bug.

## Change summary

Allow users to prevent breakpoint stops from moving the editor caret while retaining appropriate stopped-location reveal behavior.

## Best solution

Define separate stopped-location behaviors—likely by expanding `debug.focusEditorOnBreak` beyond a boolean—so users can independently choose whether a break reveals the source, focuses the editor, and moves the caret.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`, `src/vs/workbench/contrib/debug/browser/debugSession.ts`, `src/vs/workbench/contrib/debug/common/debugModel.ts`, `src/vs/workbench/contrib/debug/common/debugSource.ts`, `src/vs/workbench/contrib/debug/test/browser/debugSession.test.ts`, `src/vs/workbench/contrib/debug/test/browser/debugSource.test.ts`
- **Validation:** Add debug tests covering each selected stopped-location mode, including a break while editing an already-open source file; verify whether focus, active editor, reveal range, and caret selection change according to the chosen setting semantics.
- **Behavior:**

  > Users must be able to continue editing while a debug session stops without their caret unexpectedly moving to the breakpoint. VS Code must still expose the stopped location according to the selected debug-navigation behavior, including when the source is not already open. Existing default breakpoint navigation should remain unchanged unless the user selects a less disruptive mode. Acceptance checks must distinguish editor focus, source reveal, and caret movement rather than treating them as one action.
- **Trace:**

  > On a stopped event, `DebugSession` in `src/vs/workbench/contrib/debug/browser/debugSession.ts` converts the boolean `debug.focusEditorOnBreak` into `preserveFocus` and calls `DebugService.focusStackFrame`. `StackFrame.openInEditor` in `src/vs/workbench/contrib/debug/common/debugModel.ts` then passes the stopped frame range to `Source.openInEditor`; `src/vs/workbench/contrib/debug/common/debugSource.ts` always uses that range as the editor selection, so preserving focus does not preserve the caret. The setting is registered as a boolean in `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`. The boundary is automatic navigation caused by debugger stop events: explicit stack-frame selection and ordinary editor-opening behavior must not change. The uncertainty starts at the public setting contract—whether to reinterpret the existing false value or introduce multiple modes—and at what should happen when the stopped source is closed or not active. Related reports: https://github.com/microsoft/vscode/issues/139950, https://github.com/microsoft/vscode/issues/191013, and https://github.com/microsoft/vscode/issues/210811.
- **Open decisions:**
  - Should `debug.focusEditorOnBreak: false` itself stop caret movement for compatibility with user expectations, or should the setting become an enum with separate focus-and-caret modes?
  - When the stopped source is already open but not active, should the least-disruptive mode activate/reveal it without moving its saved caret, or leave the active editor unchanged?
  - When the stopped source is not open, should every mode still open it at the stopped line, or should a mode allow no editor navigation at all?

## Evidence

- **current source:** `src/vs/workbench/contrib/debug/browser/debugSession.ts` reads `debug.focusEditorOnBreak` only to set `preserveFocus` before calling `focusStackFrame`; it does not suppress stopped-frame navigation.
- **caret-moving path:** `StackFrame.openInEditor` in `src/vs/workbench/contrib/debug/common/debugModel.ts` forwards the stopped frame range to `Source.openInEditor`; `src/vs/workbench/contrib/debug/common/debugSource.ts` always supplies that range as the editor `selection`, with `CenterIfOutsideViewport`, even when focus is preserved.
- **setting contract:** `src/vs/workbench/contrib/debug/browser/debug.contribution.ts` describes `debug.focusEditorOnBreak` only as controlling editor focus, matching the current distinction between preserving focus and moving/revealing the selection.
- **maintainer direction:** The debug owner confirmed the behavior in https://github.com/microsoft/vscode/issues/189445#issuecomment-1664481163 and explicitly raised either a focused-editor-specific adjustment or expanding the setting to an enum.
- **canonical status:** The later report https://github.com/microsoft/vscode/issues/210811 was closed by the debug owner as a duplicate of this issue. The opposite-symptom report https://github.com/microsoft/vscode/issues/191013 was later closed after reporters could no longer reproduce it and does not own this request.
