# Issue #310082 — Launch VS Code with a specific Profile when opening certain file types from OS file explorer (file association / “Open with”)

[https://github.com/microsoft/vscode/issues/310082](https://github.com/microsoft/vscode/issues/310082)

## Summary

A real profiles/OS-integration gap remains: VS Code supports selecting one global new-window profile and accepts `--profile`, but its built-in file associations do not select profiles by file type or expose profile-specific Open With actions. No verified open canonical owns this request, so it should be classified and routed to profiles and OS integration.

## Change summary

Allow files opened from the operating system to launch VS Code with a selected profile, either through profile-specific file associations or configurable matching rules.

## Best solution

Design a cross-platform profile-launch association that reuses the existing `--profile` entry point while defining predictable behavior for file patterns, multiple selected files, and existing windows. The profiles and OS-integration owners should first choose between explicit profile-specific OS actions and automatic matching rules.

## Plan brief

- **Likely files:** `src/vs/platform/environment/node/argv.ts`, `src/vs/workbench/common/configuration.ts`, `src/vs/platform/userDataProfile/common/userDataProfile.ts`, `build/win32/code.iss`, `resources/linux/code.desktop`
- **Validation:** Exercise the agreed design on Windows, macOS, and Linux: opening an associated `.txt` file from the OS must select the configured profile before the window loads, while unassociated files retain the existing active/default-profile behavior; also verify multiple-file and already-running-window cases.
- **Behavior:**

  > A user can arrange for files opened through the operating system to launch in a chosen VS Code profile without manually editing registry or desktop-entry configuration. Associated files select that profile before extensions and workbench state load; files with no matching association retain current profile-selection behavior. The behavior must be predictable when multiple files are opened together and when VS Code already has active windows.
- **Trace:**

  > The existing launch primitive is `--profile` in src/vs/platform/environment/node/argv.ts. Profile fallback is exposed globally through `window.newWindowProfile` in src/vs/workbench/common/configuration.ts, while stored associations in src/vs/platform/userDataProfile/common/userDataProfile.ts are workspace-oriented. Windows installer associations in build/win32/code.iss and the Linux desktop entry in resources/linux/code.desktop launch files without profile arguments. The boundary is profile selection during OS-originated launches: existing workspace associations, ordinary CLI behavior, and unmatched-file fallback must remain compatible. https://github.com/microsoft/vscode/issues/176379 documents that the current active/default fallback is intentional; the uncertainty starts at which new user-facing association model should supplement it.
- **Open decisions:**
  - Should the supported UX expose explicit profile-specific Open With actions, automatic file/path matching rules, or both?
  - When one OS launch contains files matching different profiles, which profile should the resulting window use?
  - Should a profile-associated OS open reuse an existing window on that profile, always create a matching-profile window, or follow the existing window-reuse setting?

## Evidence

- **existing CLI capability:** src/vs/platform/environment/node/argv.ts:117 registers `--profile <profileName>` and describes profile selection and workspace association, providing a launch primitive but not first-class OS file-association configuration.
- **existing global setting:** src/vs/workbench/common/configuration.ts:241-282 registers `window.newWindowProfile`, which selects one profile for all new windows; it has no file-extension, path-pattern, or single-file matching dimension.
- **OS integration gap:** build/win32/code.iss registers file-open commands as the VS Code executable followed by `%1`, while resources/linux/code.desktop uses `Exec=@@EXEC@@ %F`; neither surface carries a selected profile or profile matching rule.
- **related precedent:** https://github.com/microsoft/vscode/issues/176379 was closed as designed because Open With falls back to the active or default profile. That decision explains current behavior but does not decide this broader request for explicit profile-specific actions or configurable file rules, and the issue is closed so it cannot be a duplicate canonical.
- **canonical search:** Searches for profile file associations, file-extension selection, and Explorer/Finder profile launching found no older open issue with the same reporter-observable request.
