# Issue #59337 — Extend tasks API to allow programmatic problem matching

[https://github.com/microsoft/vscode/issues/59337](https://github.com/microsoft/vscode/issues/59337)

## Summary

Keep open: stable APIs still do not provide task-associated output consumption or executable problem matchers while retaining VS Code-managed process execution. This issue already owns related requests consolidated by maintainers, and its 25 upvotes and On Deck milestone support retaining it for API design.

## Change summary

Allow extensions to consume task output programmatically for diagnostics and progress without taking over process execution.

## Best solution

Define a supported task-associated output or programmatic problem-matcher contract that preserves task execution, presentation, and diagnostic lifecycle management. Resolve the public API scope with the tasks/API owners rather than treating CustomExecution or proposed terminal APIs as complete coverage.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vscode-dts/vscode.proposed.taskExecutionTerminal.d.ts`, `src/vscode-dts/vscode.proposed.terminalDataWriteEvent.d.ts`, `src/vs/workbench/api/common/extHostTask.ts`, `src/vs/workbench/contrib/tasks/common/problemMatcher.ts`, `src/vs/workbench/contrib/tasks/common/problemCollectors.ts`
- **Validation:** The plan should define an extension-host integration check using a provider-supplied task that emits structured diagnostics and a readiness marker. Verify programmatic consumption while VS Code retains process execution, correct attribution across terminal reuse and concurrent tasks, and diagnostic cleanup on rerun; existing declarative matchers must retain their behavior.
- **Behavior:**

  > Extensions need to interpret task output for diagnostics and progress while VS Code continues launching and managing the task. The original report asks for reliable task/output association, and maintainers subsequently consolidated JSON parsing and dynamically supplied matcher definitions here. CustomExecution is a partial alternative because it transfers execution responsibility to the extension. Acceptance should cover structured output, concurrent executions, terminal reuse, and preservation of existing task presentation and problem-matcher behavior.
- **Trace:**

  > The stable Task API in src/vscode-dts/vscode.d.ts accepts named matchers only, and stable TaskExecution has no output or terminal member. CustomExecution supplies an extension-owned Pseudoterminal rather than observing VS Code-managed process output. extHostTask.ts serializes matcher names and separately associates a terminal with executions for the proposed taskExecutionTerminal API. problemMatcher.ts handles declarative regex matching, and problemCollectors.ts owns output-line processing and marker lifecycle. Proposed terminalDataWriteEvent exposes raw terminal data but documents a performance obstacle to stabilization; stable TerminalShellExecution.read() depends on shell integration and is not task-scoped. The uncertainty begins at the public contract: the thread supports output access but has not settled how it relates to executable matchers and managed diagnostics. Preserve existing declarative matching and task execution semantics; do not expand this into process-management convenience APIs or debug-configuration changes. Related requests were consolidated here in https://github.com/microsoft/vscode/issues/51957#issuecomment-519130273 and https://github.com/microsoft/vscode/issues/137221#issuecomment-970131825.
- **Open decisions:**
  - Should the supported API expose task-associated output for extensions to interpret, a programmatic matcher that participates in managed diagnostics, or both?
  - Must the output contract distinguish stdout from stderr, or is a combined terminal-output stream sufficient?
  - For programmatically produced diagnostics, should VS Code own clearing and background-task lifecycle semantics, or should extensions manage their own diagnostic collections?
