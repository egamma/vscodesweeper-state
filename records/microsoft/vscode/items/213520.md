# Issue #213520 — Git - VS Code Cannot Push to Git via SSH

[https://github.com/microsoft/vscode/issues/213520](https://github.com/microsoft/vscode/issues/213520)

## Summary

Move this confirmed stale-agent-socket report to the Remote-SSH tracker. Related forwarding fixes were reported there, but neither a concrete fixing commit nor coverage of this exact restart scenario has been established, so a completed close is not justified.

## Change summary

Reconnecting to a Remote-SSH workspace leaves Git and sometimes terminals using an expired SSH_AUTH_SOCK, causing SSH authentication to fail.

## Best solution

Remote-SSH should preserve working agent forwarding across reconnection and window restart for both Git operations and terminals, without requiring users to kill remote Node processes. The owning team should assess this reproduction against its existing forwarding fixes and separately account for the Git askpass exception.

## Evidence

- **confirmed reproduction:** The discussion at https://github.com/microsoft/vscode/issues/213520 contains independent confirmations: zimtkeks observed a new sshAuthSock in Remote-SSH output while the terminal retained the old, unusable SSH_AUTH_SOCK; explicitly selecting the new socket restored ssh-add. dlaflamme confirmed the same behavior on AlmaLinux 8, and lobantseff reported Git failures with a macOS client and Ubuntu remote. These are historical confirmations, not a current-main runtime reproduction.
- **ownership:** In https://github.com/microsoft/vscode/issues/213520, lszomoru explicitly referred the report to the Remote-SSH owner because that extension handles SSH_AUTH_SOCK. Remote-SSH is VS Code-team-owned and belongs in https://github.com/microsoft/vscode-remote-release; the appropriate action is transfer, not a caused-by-extension close.
- **current source boundary:** src/vs/server/node/extensionHostConnection.ts, buildUserEnvironment, merges the server process environment, resolved shell environment, and connection-provided startParamsEnv. extensions/git/src/git.ts merges process.env into Git subprocess options. These paths explain how a stale supplied socket can reach Git, but do not conclusively establish whether current Remote-SSH still supplies one.
- **reporter's linked workaround:** https://github.com/microsoft/vscode/issues/168202#issuecomment-2147925134 is the workaround linked by lobantseff: enable forwarding, disable local and exec servers, and enable remoteServerListenOnSocket. It is configuration-specific evidence, not proof that the default reconnect behavior is fixed.
- **related forwarding fixes:** https://github.com/microsoft/vscode/issues/168202 is closed; its maintainer follow-up at https://github.com/microsoft/vscode/issues/168202#issuecomment-2523905164 points to https://github.com/microsoft/vscode-remote-release/issues/10274. That issue is also closed and reports a fix in Remote-SSH pre-release 0.116.2024112219, with community validation described at https://github.com/microsoft/vscode-remote-release/issues/10274#issuecomment-2523849074. No concrete behavioral fix commit was identified, and that validation does not establish this report's complete window-close/reopen and Git-askpass scenario.
- **canonical search:** The older related https://github.com/microsoft/vscode-remote-release/issues/9662 is closed, as is https://github.com/microsoft/vscode/issues/168202, so neither is an eligible duplicate canonical. The open https://github.com/microsoft/vscode/issues/111866 concerns key filenames and hanging pushes; https://github.com/microsoft/vscode/issues/57488 concerns local Linux agent/askpass behavior; https://github.com/microsoft/vscode/issues/166132 concerns missing passphrase prompts. None establishes the same reconnect-expired-socket symptom required for this re-reviewed item. https://github.com/microsoft/vscode/issues/219570 is newer and reports a different remote-Windows hang.
- **secondary askpass failure:** The original report includes an askpass-main.js undefined.replace exception after forwarding fails. Current extensions/git/src/askpass.ts still parses prompt arguments using argv[4].replace in handleAskpass and argv[6].replace in handleSSHAskpass, but the recorded stack lacks the actual prompt arguments. This is a related diagnostic lead, not a conclusively traced current defect or evidence that fixing prompt parsing restores agent forwarding.
