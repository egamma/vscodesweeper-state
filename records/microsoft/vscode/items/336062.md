# Issue #336062 — Workspace custom agents disappear after Copilot Chat extension-host stalls; file watcher event restores them without reload

[https://github.com/microsoft/vscode/issues/336062](https://github.com/microsoft/vscode/issues/336062)

## Summary

Detailed, technically credible report (CPU profiles, exact error text, a repeatable non-reload workaround) of workspace custom agents dropping out of discovery after a Copilot Chat extension-host stall; the caching/invalidation architecture I found in core is consistent with the symptom, but the exact defect (core cache vs. extension-side data) still needs to be pinned down before implementation.

## Change summary

Workspace `.github/agents/*.agent.md` custom agents intermittently vanish from the picker/exact-name invocation after Copilot Chat's extension host stalls, and only a file-watcher event (not the extension host recovering) restores them.

## Best solution

Make the custom-agent discovery cache self-heal once the extension host becomes responsive again (e.g. retry/invalidate `CachedPromise` in promptsServiceImpl.ts on an ext-host-recovered signal) instead of relying solely on an incidental filesystem watcher event; a supported 'Refresh Custom Agents' command would be a reasonable stopgap.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/service/extensionPromptFileService.ts`, `src/vs/workbench/contrib/chat/common/promptSyntax/config/promptFileLocations.ts`
- **Validation:** Manual repro: simulate a heavy/blocking extension-host CPU task, then confirm previously-discovered workspace custom agents remain invocable by exact name in the picker without needing a `.github/agents` file-system event or window reload.
- **Behavior:**

  > A valid workspace `.github/agents/*.agent.md` custom agent must remain registered and invocable by exact name for the lifetime of the workspace. A temporary Copilot Chat extension-host CPU stall must not leave the custom-agent discovery cache stuck showing fewer agents than exist on disk. Once the extension host becomes responsive again, discovery should recover automatically — without requiring a manual file-system watcher event (the reporter's create/delete workaround) or a full window reload. Acceptance: after an artificially induced extension-host stall, previously-registered custom agents stay invocable without any workspace file change.
- **Trace:**

  > Custom-agent discovery is served through `cachedCustomAgents`, a `CachedPromise` (promptsServiceImpl.ts, class near line 1600) that only recomputes when one of a specific set of events fires (workspace prompt-file changes, config changes, trust changes) — there is no invalidation tied to the extension host regaining responsiveness. Workspace `.github/agents` files are located via `AGENTS_SOURCE_FOLDER`/`promptFileLocations.ts`, not the org-level `GitHubOrgCustomAgentProvider` (extensions/copilot), so whether the stalled extension host affects the compute function directly (e.g. a hung sub-call) or only the timing of the invalidating event is not yet confirmed — that is the open diagnosis step. Do not touch the org-agent polling provider (extensions/copilot/src/extension/agents/vscode-node/githubOrgCustomAgentProvider.ts); it is a separate feature. Related but distinct reports: https://github.com/microsoft/vscode/issues/333434 (Copilot CLI plugin nonce staleness, not workspace agent files) and https://github.com/microsoft/vscode/issues/324402 (agents lost after workspace becomes `unknown:/`, a different trigger).
- **Open decisions:**
  - Does the extension-host stall interfere with the actual compute function backing cachedCustomAgents (e.g. a hung call that needs the ext host), or only with the timing/delivery of the invalidating event that would otherwise refresh it?
  - Should recovery be automatic (tied to an 'extension host responsive again' signal) or should VS Code also expose a public 'Refresh Custom Agents' command as a user-facing fallback?
  - Is the same underlying gap present in the extension-contributed prompt/instruction caches (onDidChangeInstructions, onDidChangeSkills) or specific to custom agents?

## Evidence

- **cache mechanism:** src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts defines cachedCustomAgents as a CachedPromise (class at line ~1600) that only recomputes when an invalidation event fires (workspace file change, config change, trust change) and otherwise serves a stale in-flight/cached promise indefinitely — there is no re-check tied to extension-host responsiveness recovering.
- **discovery source:** Workspace `.github/agents` files are resolved through core file discovery (AGENTS_SOURCE_FOLDER in src/vs/workbench/contrib/chat/common/promptSyntax/config/promptFileLocations.ts), not the org-level GitHubOrgCustomAgentProvider in extensions/copilot (which is a distinct polling-based mechanism for org agents) — so the exact interaction with an extension-host stall is plausible but not yet conclusively traced.
- **report quality:** Reporter gives an exact repeatable sequence, sanitized timeline with CPU-profile percentages (github.copilot-chat ~97–99%), the literal 'Requested agent ... not found' error, and a deterministic create/delete-file workaround that restores discovery without reload.
