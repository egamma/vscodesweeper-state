# Issue #336062 — Workspace custom agents disappear after Copilot Chat extension-host stalls; file watcher event restores them without reload

[https://github.com/microsoft/vscode/issues/336062](https://github.com/microsoft/vscode/issues/336062)

## Summary

Keep open for diagnosis: the report provides a concrete mixed-root setup, exact invocation failure, and repeatable watcher-based recovery, but the stall-to-discovery failure remains unconfirmed. Harness discovery has evolved since the report; the supplied sequence is sufficient to retest without requesting another basic reproduction description.

## Change summary

Valid workspace custom agents become unavailable after extended Chat use and extension-host stalls, then return when their directory receives a file-change event.

## Best solution

Workspace-agent discovery should recover from transient failures without requiring a window reload or synthetic file changes. Diagnose the file-list and parsed-agent caches on the affected Chat path before deciding whether a public refresh command is also needed.

Once the failure mechanism is identified, add a focused discovery regression test demonstrating that subsequent successful reads restore the valid agents without a filesystem mutation or reload.
- **Behavior:**

  > Previously available, enabled workspace agents must remain discoverable and invocable by their exact names while their valid files remain present. A temporary failure must not leave agents permanently unavailable after the underlying service recovers. Validate both picker availability and named invocation without creating a temporary agent file or reloading the window. Preserve intentional exclusions and removal of genuinely deleted or disabled agents.
- **Trace:**

  > RunSubagentTool.getSubAgentByName reads PromptsService.getCustomAgents directly, linking the exact error to discovery rather than only UI state. PromptsService maintains separate cached file-location and agent-discovery promises; its file-locator event invalidates both, matching the reported workaround. PromptFilesLocator.resolveFilesAtLocation can convert a logged directory-resolution failure into an empty result, while computeAgentDiscoveryInfo retains non-cancellation parsing failures as skipped entries. These are diagnostic leads, not a confirmed stall-induced defect. Existing cancellation regression coverage predates this report and must not be treated as its fix. First establish the active harness and the cache contents during failure; preserve workspace scoping, enablement, and cancellation behavior, and do not broaden this into an extension-host performance rewrite.
- **Open decisions:**
  - Is a public Refresh Custom Agents command desired in addition to automatic recovery, or should the scope remain automatic recovery only?
