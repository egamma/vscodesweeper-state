# Issue #178392 — Cannot move a directory to its parent with the same name

[https://github.com/microsoft/vscode/issues/178392](https://github.com/microsoft/vscode/issues/178392)

## Summary

The failure remains present on current main: moving a nested same-name directory onto its parent reaches an explicit guard that rejects overwriting an ancestor. The issue should remain open while the Explorer's folder-merge semantics are designed alongside the related, but observably different, merge request.

## Change summary

Allow a nested directory to be moved out of its parent when the destination has the same name, merging its contents without deleting the parent.

## Best solution

Define consistent folder-merge behavior for cut/paste and drag-and-drop, then make this ancestor-target case move the nested contents into the existing parent while preserving unrelated contents and undo support. Coordinate the behavior with https://github.com/microsoft/vscode/issues/165706, which tracks general folder merging but reports destructive replacement rather than this operation being rejected.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/fileActions.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/contrib/files/test/browser/fileActions.test.ts`
- **Validation:** Add a targeted Explorer cut/paste test that starts with `folder/folder/file.txt`, moves the inner folder to the outer folder's parent, and asserts that `folder/file.txt` exists, the nested `folder/folder` is removed, and pre-existing outer-folder contents are preserved; include equivalent drag-and-drop coverage if both paths adopt the behavior.
- **Behavior:**

  > Moving `folder/folder` to the directory containing the outer `folder` must merge the inner folder's contents into the existing outer folder instead of failing or deleting the outer folder. Unrelated contents already in the outer folder must remain intact, and the operation must remain undoable. Conflict handling for descendants must be explicit and consistent between cut/paste and drag-and-drop.
- **Trace:**

  > The cut/paste path in src/vs/workbench/contrib/files/browser/fileActions.ts derives the destination from the source basename, producing the existing outer folder as the target. ExplorerService forwards that ResourceFileEdit to the bulk-edit machinery. FileService.doMoveCopy in src/vs/platform/files/common/fileService.ts normally implements overwrite by deleting the target first, while doValidateMoveCopy explicitly rejects this case because that target contains the source. General folder merging is discussed in https://github.com/microsoft/vscode/issues/165706, but this issue uniquely covers the ancestor-target failure. Preserve the FileService safety guard unless a lower-level merge contract is deliberately introduced; ordinary moves, file replacement, and source-inside-target protection must not regress.
- **Open decisions:**
  - Should moving a folder onto an existing folder always offer merge semantics, or should support be limited to this ancestor-target flattening case?
  - When both directory trees contain the same descendant name, should the operation prompt to replace, skip conflicts, or cancel the entire merge?
  - Must cut/paste and drag-and-drop expose identical merge prompts and conflict behavior?
