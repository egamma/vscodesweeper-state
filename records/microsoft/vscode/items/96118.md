# Issue #96118 — Allow to drag the entire panel/sidebar to move it left or right

[https://github.com/microsoft/vscode/issues/96118](https://github.com/microsoft/vscode/issues/96118)

## Summary

A real interaction gap remains: VS Code can reposition the panel and primary side bar through commands and menus, but dragging their title areas currently moves view containers rather than the entire workbench part. The Backlog milestone supports keeping this open while the drag interaction and target behavior are designed.

## Change summary

Allow users to reposition the entire panel or primary side bar by dragging it to another edge of the editor area.

## Best solution

Provide consistent direct manipulation for workbench parts: dragging an unambiguous part-level handle should expose valid edge targets and invoke the same persisted layout states as the existing panel and side-bar positioning commands, without disrupting view-container drag and drop.

## Vision fit

- **Fit:** aligned
- **Reason:** Directly manipulating major workbench regions advances the durable goal of flexible layouts while keeping the existing layout model intact.
- **Evidence:** Durable theme: “Workbench & core UX — layout flexibility.” It also supports the value of “Simple, uniform UI and UI interactions” by making repositioning consistent with other drag-based layout operations.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/paneCompositePart.ts`, `src/vs/workbench/browser/dnd.ts`, `src/vs/workbench/browser/layout.ts`, `src/vs/workbench/browser/parts/panel/panelActions.ts`, `src/vs/workbench/browser/actions/layoutActions.ts`
- **Validation:** In a development workbench, drag the panel and primary side bar to every position currently exposed by their positioning commands; verify the part moves, the position survives reload, valid drop feedback is accessible, and dragging individual views or view containers retains its existing behavior.
- **Behavior:**

  > Users can drag the entire panel between top, bottom, left, and right positions and drag the primary side bar between left and right. During the gesture, valid destinations are clearly identified, and dropping persists the same layout state as the corresponding existing command. Dragging an individual view or view-container title must continue to move that content rather than the whole part, and all existing keyboard/menu positioning commands remain available.
- **Trace:**

  > Panel positions already flow through the commands in src/vs/workbench/browser/parts/panel/panelActions.ts and `IWorkbenchLayoutService.setPanelPosition`; primary side-bar positions flow through src/vs/workbench/browser/actions/layoutActions.ts and the `workbench.sideBar.location` setting. In src/vs/workbench/browser/parts/paneCompositePart.ts, `AbstractPaneCompositePart.createTitleLabel` currently registers the title label as a `composite` drag source, while src/vs/workbench/browser/dnd.ts models only `view` and `composite` payloads. The current drop infrastructure therefore relocates contained views or view containers, not the panel/sidebar part itself. Preserve those content-level DnD semantics and the existing command-driven layout states; the uncertainty starts at which title-area region owns a whole-part gesture and how users distinguish it from moving the active composite.
- **Open decisions:**
  - Which visible region should initiate whole-part dragging so users can reliably distinguish it from dragging the active view container or interacting with title actions?
  - Should the panel expose all four existing position targets during dragging while the primary side bar exposes only left and right, or should both use a smaller common target model?

## Evidence

- **existing capability:** src/vs/workbench/browser/parts/panel/panelActions.ts registers `workbench.action.positionPanelLeft`, `workbench.action.positionPanelRight`, `workbench.action.positionPanelTop`, and `workbench.action.positionPanelBottom`; src/vs/workbench/browser/actions/layoutActions.ts similarly registers primary side-bar left/right commands.
- **remaining gap:** In src/vs/workbench/browser/parts/paneCompositePart.ts, `AbstractPaneCompositePart.createTitleLabel` marks the title label draggable, but its drag payload is the active `composite`; this moves the contained view container, not `Parts.PANEL_PART` or `Parts.SIDEBAR_PART`.
- **DnD boundary:** src/vs/workbench/browser/dnd.ts defines the shared composite drag payload around only `view` and `composite` types, with no workbench-part drag representation.
- **canonical search:** No older open issue was found that reports the same observable request. https://github.com/microsoft/vscode/issues/193154 is younger, closed, and concerns arbitrary side-bar arrangements rather than dragging a whole part between already-supported positions, so it is not a valid canonical for this re-reviewed item.
- **backlog status:** The issue is assigned to the Backlog milestone and already carries the `feature-request` and `layout` labels, indicating an accepted but unscheduled workbench-layout request.
