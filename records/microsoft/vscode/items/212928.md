# Issue #212928 — Support "Share" for tabs multiselect

[https://github.com/microsoft/vscode/issues/212928](https://github.com/microsoft/vscode/issues/212928)

## Summary

The request remains unimplemented on current main: the tab context menu explicitly hides Share for a multi-selection, and the sharing stack accepts only one resource. This team-authored Backlog item should remain open while bulk-sharing semantics are designed.

## Change summary

Allow the editor-tab Share action to operate on all selected tabs instead of disappearing for multi-selection.

## Best solution

Define consistent bulk-share behavior for mixed selected resources, provider selection, clipboard output, and partial failures, then support that behavior through the tab command context and share-provider contract.

- **Validation:** Add targeted share-service/action tests covering two selected editor resources, provider eligibility, cancellation or failure behavior, and the resulting clipboard content; manually verify that the tab context-menu Share action is keyboard-accessible for a multi-selection and that single-tab sharing is unchanged.
- **Behavior:**

  > Selecting multiple editor tabs and opening their context menu should offer Share. The chosen sharing operation must account for every selected shareable tab and present a clear result without silently falling back to only the active editor. Single-tab sharing and selections containing unsupported resources must retain well-defined behavior. Acceptance should cover provider selection, clipboard output, cancellation or partial failure, and keyboard access to the context-menu action.
- **Trace:**

  > src/vs/workbench/browser/parts/editor/editor.contribution.ts currently suppresses EditorTitleContextShare under MultipleEditorsSelectedInGroupContext. The shared command-context path in src/vs/workbench/browser/parts/editor/editorCommandsContext.ts can already resolve all selected editor inputs, but ShareAction in src/vs/workbench/contrib/share/browser/share.contribution.ts ignores command arguments and derives one active resource. IShareService and the proposed ShareProvider API in src/vs/workbench/contrib/share/common/share.ts and src/vscode-dts/vscode.proposed.shareProvider.d.ts accept one ShareableItem and return one result. https://github.com/microsoft/vscode/pull/211712 established multi-select as a foundation for later action support; https://github.com/microsoft/vscode/issues/176316 tracks the related proposed share API but not this observable tab behavior. Preserve existing single-item providers and non-tab Share entry points unless the maintainer explicitly chooses an API-contract change.
- **Open decisions:**
  - Should a provider receive the selected resources as one collection, changing the proposed provider contract, or should VS Code invoke the existing single-item provider once per selected tab?
  - What user-visible clipboard and confirmation result should multiple successful shares produce, and how should cancellation or partial provider failures be presented?
  - For a selection whose resources match different provider selectors, should Share expose only providers valid for every tab or allow per-resource provider choices?
