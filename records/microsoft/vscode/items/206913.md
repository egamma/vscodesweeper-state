# Issue #206913 — responsive GUI regarding `search.smartCase`

[https://github.com/microsoft/vscode/issues/206913](https://github.com/microsoft/vscode/issues/206913)

## Summary

Keep open: current search code still applies smart-case sensitivity without explaining it in the Match Case control or result messages. Maintainers approved an incremental message or tooltip; the broader ternary-toggle proposal remains a separate design question.

## Change summary

Make Search clearly indicate when search.smartCase automatically makes a query case-sensitive.

## Best solution

Provide a localized, accessible explanation of smart-case activation in the Search UI while preserving existing matching and manual Match Case behavior. Start with the maintainer-supported message or tooltip rather than hiding controls or introducing a ternary toggle.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/search/browser/searchView.ts`, `src/vs/workbench/contrib/search/browser/searchWidget.ts`, `src/vs/workbench/contrib/search/browser/searchAccessibilityHelp.ts`, `src/vs/workbench/contrib/search/test/browser/searchWidget.test.ts`, `src/vs/workbench/services/search/test/browser/queryBuilder.test.ts`
- **Validation:** With a workspace file containing 'example' and 'Example', enable search.smartCase and leave Match Case off. Search 'Example' and verify the chosen feedback explains automatic case sensitivity; search 'example' and verify the feedback accurately distinguishes that state. Repeat with manual Match Case enabled, smart case disabled, zero results, and settings changed while Search is open. Verify keyboard and screen-reader discoverability, and preserve the existing QueryBuilder smartCase tests.
- **Behavior:**

  > Workspace Search should explain when smart case determines effective case sensitivity, so an apparently unchecked Match Case control does not leave users guessing why uppercase queries return fewer results. The indication must remain accurate as the query, setting, and manual toggle change, including searches with no results. Preserve existing search results and manual Match Case functionality. The first increment is explanatory feedback, not a new ternary search mode, and must be discoverable to screen-reader users.
- **Trace:**

  > SearchView._onQueryChanged in src/vs/workbench/contrib/search/browser/searchView.ts passes the manual Match Case flag and search.smartCase separately to QueryBuilder.text. QueryBuilder.isCaseSensitive in src/vs/workbench/services/search/common/queryBuilder.ts resolves uppercase-driven sensitivity, including special handling of regex escapes; the smartCase tests document this contract. SearchWidget.renderSearchInput initializes the normal binary Match Case control, while SearchView.updateSearchResultCount and completion/no-results messages do not expose smart-case activation. Search accessibility help describes the setting but not current effective state. Maintainer approval for an incremental message or tooltip is recorded at https://github.com/microsoft/vscode/issues/206913#issuecomment-2147788533. Keep matching semantics, shared Find controls, and ternary-toggle redesign outside this increment; the remaining uncertainty is the user-facing presentation and whether it reports configured mode or effective activation.
- **Open decisions:**
  - Should the first increment provide visible status text near the search input/results, or an explanation available through the existing control's tooltip?
  - Should feedback report that smart case is configured, or distinguish when the current query actually activates automatic case sensitivity?
