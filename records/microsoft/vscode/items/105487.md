# Issue #105487 — [cli] specify command that runs on window open

[https://github.com/microsoft/vscode/issues/105487](https://github.com/microsoft/vscode/issues/105487)

## Summary

This remains a valid, well-supported Backlog request: current main has no CLI option for executing workbench or extension commands with arguments. This issue is the established canonical report, so the newer related issue should consolidate here rather than the reverse.

## Change summary

Add a CLI facility that executes one or more commands with arguments in the newly opened or reused VS Code window.

## Best solution

Design a public CLI contract for ordered command invocation, argument encoding, command eligibility, error reporting, and window targeting, then carry the request through the existing CLI-to-window IPC path and execute commands after the target workbench is ready.

## Plan brief

- **Likely files:** `src/vs/platform/environment/common/argv.ts`, `src/vs/platform/environment/node/argv.ts`, `src/vs/platform/environment/test/node/argv.test.ts`, `src/vs/platform/windows/electron-main/windowsMainService.ts`, `src/vs/workbench/electron-browser/window.ts`
- **Validation:** Extend the argv parser tests for repeated ordered commands and associated arguments, then add a windows/workbench integration test showing that commands execute sequentially with their arguments in both a newly opened window and a reused window after the workbench is ready.
- **Behavior:**

  > The `code` CLI can request one or more workbench or extension commands and supply arguments for each command. Commands execute sequentially after the selected window is ready; normal window-selection flags continue to determine whether a new window is opened or an existing one is reused. Arguments remain associated with the command that precedes them, and malformed invocations fail with a clear CLI error. Existing CLI launches without command requests are unchanged.
- **Trace:**

  > The supported argument contract is declared in `NativeParsedArgs` in src/vs/platform/environment/common/argv.ts and described by `OPTIONS` in src/vs/platform/environment/node/argv.ts; neither currently represents command invocations. CLI launches flow through `IOpenConfiguration.cli` in src/vs/platform/windows/electron-main/windows.ts and are routed to new or reused windows by `WindowsMainService` in src/vs/platform/windows/electron-main/windowsMainService.ts. The renderer already accepts `vscode:runAction` in src/vs/workbench/electron-browser/window.ts and calls `ICommandService.executeCommand` with positional arguments, but this IPC is currently used for trusted native actions rather than arbitrary CLI input. The design must preserve existing file, folder, URL, chat, and window-reuse behavior. https://github.com/microsoft/vscode/issues/174082 confirms this issue as the canonical request; the newer https://github.com/microsoft/vscode/issues/238786 should not replace it.
- **Open decisions:**
  - What public CLI grammar and serialization should represent multiple ordered commands and typed arguments: repeated command/argument flags, a structured JSON payload, or another stable format?
  - May the CLI invoke every registered command, or must extensions and core commands explicitly opt in to CLI invocation?
  - Should the CLI wait for command completion and report command results or failures through its exit status, or dispatch commands after window readiness and return immediately?

## Evidence

- **current source gap:** src/vs/platform/environment/common/argv.ts and src/vs/platform/environment/node/argv.ts define the current native CLI arguments, including window reuse and URL handling, but contain no run-command option or command-argument representation.
- **existing execution path:** src/vs/workbench/electron-browser/window.ts handles the internal `vscode:runAction` IPC event through `ICommandService.executeCommand`, including positional arguments, so command execution exists inside a ready workbench but is not exposed through the CLI.
- **window routing path:** src/vs/platform/windows/electron-main/windowsMainService.ts already routes CLI requests to newly opened or reused windows and uses `sendWhenReady` for requests such as chat and file opening; command requests would need equivalent lifecycle and target-window semantics.
