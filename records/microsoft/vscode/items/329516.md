# Issue #329516 — Agent plugins: auto-update permanently fails with "Cannot fast-forward to multiple branches" due to concurrent git fetch/pull in the same plugin clone

[https://github.com/microsoft/vscode/issues/329516](https://github.com/microsoft/vscode/issues/329516)

## Summary

Traced conclusively in source: `pullRepository`/`fetchRepository` in AgentPluginRepositoryService take no lock (only `ensureRepository`/clone is serialized via `_cloneSequencer`), and `updateAllPlugins` fans multiple git operations out with `Promise.all`, so concurrent `git fetch`/`git pull --ff-only` against the same clone can corrupt `FETCH_HEAD` and permanently wedge auto-update — a real, well-localized bug worth routing to the chat/plugins owner.

## Change summary

Concurrent, unsynchronized git fetch/pull against the same agent-plugin clone (from parallel update tasks, multiple windows, or the Sessions app) corrupts FETCH_HEAD and produces a permanent 'Cannot fast-forward to multiple branches' failure that the recovery path doesn't recognize.

## Best solution

In src/vs/workbench/contrib/chat/browser/agentPluginRepositoryService.ts, extend the existing `_cloneSequencer` (SequencerByKey keyed on repoDir.fsPath) to also guard `pullRepository`/`fetchRepository`, not just `ensureRepository`; additionally widen `_isFastForwardPullFailure` in src/vs/platform/git/node/localGitService.ts to match 'Cannot fast-forward to multiple branches' so the existing fetch-and-retry/hard-reset recovery in `pull()` can self-heal an already-wedged clone. A cross-process (file) lock would be needed to fully close the multi-window/Sessions-app case, but the in-process sequencer plus the widened recovery regex would fix the common case and stop the failure from being permanent.

- **Fix prompt:**

  > Two related defects were traced in source on current main. (1) In src/vs/workbench/contrib/chat/browser/agentPluginRepositoryService.ts, `ensureRepository` (line ~127) wraps its work in `this._cloneSequencer.queue(repoDir.fsPath, ...)` (a `SequencerByKey<string>` from src/vs/base/common/async.ts), but `pullRepository` (line ~146) and `fetchRepository` (line ~347) call `_pluginGit.pull`/`_pluginGit.fetchRepository` directly without going through that sequencer. Fix: wrap the bodies of `pullRepository` and `fetchRepository` in `this._cloneSequencer.queue(repoDir.fsPath, async () => { ... })` the same way `ensureRepository` does, so all git operations against a given repoDir are serialized in-process. Do not change the sequencer implementation itself or unrelated methods (clone, migration, marketplace index). (2) Separately, in src/vs/platform/git/node/localGitService.ts, `_isFastForwardPullFailure` (line ~90-97) only matches `/not possible to fast-forward|non-fast-forward/i` against the combined stderr/message, so it misses git's `Cannot fast-forward to multiple branches.` message (produced by `git pull --ff-only` when `FETCH_HEAD` has more than one non-'not-for-merge' entry — see the reporter's citation of `builtin/pull.c`). Widen this regex (e.g. add `|multiple branches` or match `cannot fast-forward` case-insensitively more broadly) so the existing fetch-and-retry / `allowHardResetOnDivergence` hard-reset recovery in `pull()` (lines ~51-83) can repair an already-corrupted clone instead of rethrowing immediately. Validate with a new unit test in src/vs/platform/git/test/node/localGitService.test.ts that feeds a fake execFile error containing 'Cannot fast-forward to multiple branches.' and asserts the retry-then-reset path is taken (it must fail before the regex change and pass after). ## Evidence

- **no lock on pull/fetch:** src/vs/workbench/contrib/chat/browser/agentPluginRepositoryService.ts:146 (pullRepository) and :347 (fetchRepository) call `_pluginGit.pull`/`_pluginGit.fetchRepository` directly with no `_cloneSequencer.queue(...)` wrap; only `ensureRepository` (line 127) is serialized.
- **concurrent fan-out:** src/vs/workbench/contrib/chat/browser/pluginInstallService.ts `updateAllPlugins` builds `gitTasks`/`independentGitTasks` arrays and awaits them via `Promise.all` (lines ~434, ~489), so multiple marketplaces/plugins can run git fetch/pull concurrently; multiple `IMarketplaceReference`s can also resolve to the same repoDir via `getRepositoryUri`.
- **narrow recovery regex:** src/vs/platform/git/node/localGitService.ts:90-97 `_isFastForwardPullFailure` only matches `/not possible to fast-forward|non-fast-forward/i`, which does not match git's `Cannot fast-forward to multiple branches.` message, so the fetch-and-retry / `allowHardResetOnDivergence` hard-reset recovery (lines 51-83) never triggers for this failure mode.
- **no cross-process lock:** The `agentPluginsHome` cache directory is shared across windows/Sessions app per userDataProfileService.currentProfile.agentPluginsHome, but the sequencer is in-process only (SequencerByKey in a single AgentPluginRepositoryService instance), consistent with the reporter's claim that a second window reproduces it reliably.
