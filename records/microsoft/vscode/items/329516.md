# Issue #329516 — Agent plugins: auto-update permanently fails with "Cannot fast-forward to multiple branches" due to concurrent git fetch/pull in the same plugin clone

[https://github.com/microsoft/vscode/issues/329516](https://github.com/microsoft/vscode/issues/329516)

## Summary

Traced the report's full causal chain in current main's source and it holds up: plugin auto-update permanently and silently breaks for a clone once two git operations race, with no repro needed since the defect is directly visible in the code.

## Change summary

Concurrent git fetch/pull on the same agent-plugin clone corrupts FETCH_HEAD, producing a 'Cannot fast-forward to multiple branches' error that the recovery path doesn't recognize, permanently breaking auto-update for that plugin.

## Best solution

In src/vs/workbench/contrib/chat/browser/agentPluginRepositoryService.ts, key a sequencer (or reuse/extend `_cloneSequencer`) on `repoDir.fsPath` for `pullRepository`/refresh, not just `ensureRepository`, and add an on-disk lock since multiple windows/the Sessions app share the same clone; in src/vs/platform/git/node/localGitService.ts, broaden `_isFastForwardPullFailure`'s regex to also match `Cannot fast-forward to multiple branches` so the existing fetch-retry/hard-reset recovery actually engages.

  > Thanks for the very thorough writeup — this traces cleanly against current main. `AgentPluginRepositoryService` only sequences clones (`_cloneSequencer` in `ensureRepository`), so `pullRepository`/refresh calls issued concurrently (e.g. from `PluginInstallService.updateAllPlugins`'s `Promise.all` fan-out, or a second window/Sessions app sharing the same `agent-plugins` clone) can race on `git fetch`/`git pull` in the same working directory. Separately, `LocalGitService._isFastForwardPullFailure` doesn't match `Cannot fast-forward to multiple branches`, so the existing fetch-retry/hard-reset recovery never kicks in once a clone gets into this state. This looks like real work for the agent-plugins area: serializing pull/fetch per repo directory (ideally with an on-disk lock, since multiple windows can be involved) and broadening the fast-forward-failure detection would fix both the root cause and the self-perpetuating failure mode.

## Evidence

- **no serialization on pull/fetch:** src/vs/workbench/contrib/chat/browser/agentPluginRepositoryService.ts: `_cloneSequencer` (a `SequencerByKey`) is only used inside `ensureRepository`; `pullRepository`/`_refreshRepository` call `this._pluginGit.pull(repoDir, ...)` with no per-repoDir lock.
- **concurrent fan-out confirmed:** src/vs/workbench/contrib/chat/browser/pluginInstallService.ts `updateAllPlugins` (~lines 395-489) pushes independent git tasks into `gitTasks`/`independentGitTasks` arrays and awaits them via `Promise.all(...)`, matching the reported concurrent fetch/pull pattern.
- **recovery regex too narrow:** src/vs/platform/git/node/localGitService.ts:90-97 `_isFastForwardPullFailure` only tests `/not possible to fast-forward|non-fast-forward/i` against stderr/message — `fatal: Cannot fast-forward to multiple branches.` matches neither, so the retry-after-fetch and hard-reset-on-divergence paths (lines 57-82) are skipped and the raw error is rethrown.
- **undiagnosable notification:** src/vs/workbench/contrib/chat/browser/pluginInstallService.ts's `updateAllFailed` notification wires its primary action to `git.showOutput` (the built-in Git extension's own output channel), unrelated to `LocalGitService`'s shared-process logging, matching the reporter's observation that Show Output is empty.
