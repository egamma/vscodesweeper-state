# Issue #178308 — Debug view: Sort "Paused on ..." threads to the top

[https://github.com/microsoft/vscode/issues/178308](https://github.com/microsoft/vscode/issues/178308)

## Summary

The requested ordering remains absent on current main, and the issue was deliberately reopened into the Backlog as an under-discussion feature request. A maintainer should first choose between stable adapter ordering, focused-stack scrolling, and an optional recently-paused sort policy.

## Change summary

Make the thread that caused a debugger pause expose more of its call stack, potentially by placing it at the top of the Call Stack view.

## Best solution

Improve focused-thread visibility while retaining the multi-thread Call Stack view. A plan should settle whether this means stronger reveal/scroll behavior or a configurable recently-paused ordering that avoids churn during stepping.

- **Behavior:**

  > When a multithreaded debug session pauses, the focused thread and a useful portion of its stack should be visible without manual scrolling. The Call Stack view must continue to expose all threads. Repeated stepping must not cause unexpected ordering churn under the chosen policy, and selecting another thread must continue to focus and reveal its stack.
- **Trace:**

  > DebugSession.getAllThreads() in src/vs/workbench/contrib/debug/browser/debugSession.ts preserves threadIds order, and CallStackDataSource.getChildren() in src/vs/workbench/contrib/debug/browser/callStackView.ts displays that order. CallStackView.updateTreeSelection() expands the focused thread and reveals the focused stack frame, so current main partially addresses visibility but does not implement the requested prioritization. The closed, unmerged https://github.com/microsoft/vscode/pull/178318 sorted threads with a stop reason first and added model-level ordering tests. The maintainer discussion at https://github.com/microsoft/vscode/issues/178308#issuecomment-1489094915 leaves the user-visible policy unresolved: preserve adapter order and improve reveal behavior, or introduce a recently-paused/configurable sort. Keep the existing multi-thread presentation and unrelated debug-adapter semantics outside the change.
- **Open decisions:**
  - Should pausing preserve the debug adapter's thread order and only reveal more of the focused stack, or should it visibly reorder threads?
