# Issue #293910 — Environment variables leak into launced program

[https://github.com/microsoft/vscode/issues/293910](https://github.com/microsoft/vscode/issues/293910)

## Summary

Keep open: the September fix stopped overriding XDG_DATA_HOME, but did not establish that launched programs receive restored XDG_DATA_DIRS or GLib module paths. The supplied C/CMake samples and outside-versus-inside comparison suffice to retest; current Ubuntu snap behavior remains unverified.

## Change summary

Prevent VS Code's snap-specific environment from leaking into launched user programs and changing their GLib module and settings-schema lookup.

## Best solution

Ensure user programs launched from the snap installation receive the original system lookup environment while VS Code retains its required snap runtime environment. Reproduce both supplied samples on Ubuntu and identify whether the remaining contamination enters through shell-environment resolution or another launch path.

## Plan brief

- **Likely files:** `resources/linux/snap/electron-launch`, `src/vs/platform/environment/electron-main/environmentMainService.ts`, `src/vs/platform/terminal/electron-main/electronPtyHostStarter.ts`, `src/vs/platform/shell/node/shellEnv.ts`, `src/vs/workbench/contrib/terminal/electron-browser/localTerminalBackend.ts`, `src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts`
- **Validation:** On Ubuntu 24.04 with the current VS Code snap, build and run both supplied C/CMake samples outside VS Code and through its terminal and relevant CMake launch action. Compare XDG_DATA_DIRS, GIO_MODULE_DIR and GSETTINGS_SCHEMA_DIR: snap-injected lookup paths must not reach the user program, and the GLib sample must read the system mouse double-click setting without the reported schema error. Repeat with VS Code launched from the desktop and from a system terminal.
- **Behavior:**

  > The reporter's C program launched from VS Code's Ubuntu snap receives snap-specific lookup paths rather than the original system environment. A GLib/GIO sample consequently loads a snap-cache module and fails to read a setting that works outside VS Code. User programs should retain the original system lookup environment unless explicitly overridden by user configuration. Acceptance compares both supplied samples inside and outside VS Code and confirms that the GLib lookup succeeds without requiring per-program environment workarounds.
- **Trace:**

  > resources/linux/snap/electron-launch still modifies XDG_DATA_DIRS, GIO_MODULE_DIR and GSETTINGS_SCHEMA_DIR after preserving their original values. EnvironmentMainService.unsetSnapExportedVariables restores those values, and ElectronPtyHostStarter._createPtyHostConfiguration already applies that restoration to the pty-host environment. However, doResolveUnixShellEnv separately inherits process.env, and LocalTerminalBackend.getShellEnvironment feeds the resulting environment into TerminalProcessManager._resolveEnvironment when useShellEnvironment is enabled. This is a plausible contamination path, not a conclusive trace of the reporter's CMake launch action; reproduce and determine the actual route first. https://github.com/microsoft/vscode/pull/292808 fixes the related XDG_DATA_HOME override but retains XDG_DATA_DIRS modifications, so its closure of https://github.com/microsoft/vscode/issues/237608 does not establish completion here. Preserve VS Code's own snap runtime requirements, explicit user environment overrides and non-snap behavior.

## Evidence

- **Concrete reproduction:** https://github.com/microsoft/vscode/issues/293910 supplies an environment-printing C program and CMake project. https://github.com/microsoft/vscode/issues/293910#issuecomment-3873591510 supplies a GLib/GIO sample that succeeds outside VS Code but fails inside it, with libdconfsettings.so loaded from the snap cache instead of the system module directory.
- **Related fix does not cover the full report:** https://github.com/microsoft/vscode/pull/292808 merged as 9dadd5ad1defcc3140bcdff44517284aeaf5bb91 on 2026-09-17 and closed https://github.com/microsoft/vscode/issues/237608. Its diff removes the XDG_DATA_HOME override but explicitly retains prepending $SNAP_USER_DATA/.local/share to XDG_DATA_DIRS; it does not change restoration of GIO_MODULE_DIR or GSETTINGS_SCHEMA_DIR for launched programs.
- **Current snap launcher:** resources/linux/snap/electron-launch preserves XDG_DATA_DIRS, GIO_MODULE_DIR and GSETTINGS_SCHEMA_DIR in _VSCODE_SNAP_ORIG variables, then prepends snap data directories and exports snap-specific module and schema paths. These match the environment contamination described by the reporter, but their presence in VS Code's own process is not sufficient to prove the child-launch defect.
- **Restoration and possible reintroduction paths:** EnvironmentMainService.unsetSnapExportedVariables in src/vs/platform/environment/electron-main/environmentMainService.ts restores original values. ElectronPtyHostStarter._createPtyHostConfiguration uses it when constructing the pty-host environment. Separately, doResolveUnixShellEnv in src/vs/platform/shell/node/shellEnv.ts spawns a login shell with process.env and does not restore snap originals; LocalTerminalBackend.getShellEnvironment and TerminalProcessManager._resolveEnvironment can use that resolved environment for terminal creation. This identifies a diagnostic lead, not a confirmed reproduction of the reporter's launch route.
- **Canonical search:** Read https://github.com/microsoft/vscode/issues/237608 and its linked fix, and searched open microsoft/vscode issues for snap environment, variables and XDG_DATA_DIRS. No verified older open canonical owning the same launched-program lookup failure was established. The closed XDG_DATA_HOME issue is neither a valid duplicate target nor proof that this report is fixed.
