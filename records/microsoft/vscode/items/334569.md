# Issue #334569 — MCP tool calls intermittently rejected "disabled by the user" while cache shows enabled and server log shows execution

[https://github.com/microsoft/vscode/issues/334569](https://github.com/microsoft/vscode/issues/334569)

## Summary

Still reproduces on current main: ask-mode MCP tool availability is still computed from a static toolReferences snapshot taken at request-parse time, exactly as the reporter traced, so tools registered after that snapshot (async server discovery) are wrongly rejected as 'disabled by the user'. Neither of the two candidate fix PRs (#334641, #334657) has landed, and both are closed, so the underlying defect remains and a maintainer still needs to pick a fix design.

## Change summary

Ask-mode MCP tool calls are intermittently rejected as 'disabled by the user' even though the tool is enabled and later executes, because tool availability is frozen at request-parse time before async MCP server/tool discovery finishes.

## Best solution

Make ask-mode MCP tool availability reflect currently-registered tools instead of a parse-time snapshot, choosing between the reporter's two proposed designs (scope to the referenced server's tools via LanguageModelToolMCPSource, vs. a looser mcp-tag-wide allow) — the former preserves the authorization boundary and is the safer default.

## Plan brief

- **Likely files:** `extensions/copilot/src/extension/intents/node/askAgentIntent.ts`, `src/vs/workbench/contrib/chat/common/requestParser/chatRequestParser.ts`
- **Validation:** A test asserting that an MCP tool registered after the toolset @-reference is parsed (simulating async server discovery completing later) is included in availableTools for the request, without exposing tools from non-referenced MCP servers.
- **Behavior:**

  > When a user @-references an MCP server (toolset) in ask mode, tools that finish registering shortly after the request is parsed (due to async server/tool discovery) should still be callable in that same turn, without erroring 'disabled by the user'. Tools belonging to MCP servers the user did NOT reference must remain unavailable. Acceptance: a test simulating late tool registration after toolset-reference parsing shows the tool as available; a parallel test with an unreferenced server's tools shows them still excluded.
- **Trace:**

  > The interception point is in the Copilot extension's tool-calling code, which throws 'disabled by the user' for any tool absent from the request's `availableTools`. In ask mode, MCP tools (tagged 'mcp') only enter `availableTools` via `request.toolReferences` (extensions/copilot/src/extension/intents/node/askAgentIntent.ts:44-52), and that reference list is built from a static toolset snapshot taken at parse time (src/vs/workbench/contrib/chat/common/requestParser/chatRequestParser.ts:191, `Array.from(toolset.getTools()).map(...)`). Because MCP server/tool discovery is asynchronous, tools that register after that snapshot moment are missing from the frozen list even though the server later executes them successfully — this is exactly what the reporter measured (14/48 tools available depending on race timing). The boundary: any fix must not widen tool exposure to MCP servers the user did not reference (see PR #334657's `LanguageModelToolMCPSource`-based scoping vs PR #334641's looser mcp-tag-wide approach, both closed unmerged) — do not touch unrelated tag-based (non-MCP) tool filtering.
- **Open decisions:**
  - Should dynamic tool inclusion be scoped strictly to the MCP server(s) the user referenced (via tool.source), or loosely to all mcp-tagged tools regardless of server — the former preserves the authorization boundary, the latter is simpler but exposes other configured servers' tools?
  - Should the toolset snapshot at request-parse time wait (with a timeout) for in-flight MCP server/tool discovery to settle before freezing, or should availability just be recomputed dynamically at call time instead?
