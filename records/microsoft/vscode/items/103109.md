# Issue #103109 — [theming] token type hierarchy to the 'Developer: Inspect Editor Tokens and Scopes' command

[https://github.com/microsoft/vscode/issues/103109](https://github.com/microsoft/vscode/issues/103109)

## Summary

A real theme-authoring gap remains, but the maintainer requested a stronger real-world example before choosing how to expose semantic-token inheritance without further crowding the inspector. The Backlog milestone and low demand do not establish a reason to close this re-reviewed request.

## Change summary

Expose the complete semantic token type hierarchy through Developer: Inspect Editor Tokens and Scopes, or an equivalent theme-authoring surface.

## Best solution

First confirm the desired presentation using a current language extension with custom inherited token types, then expose the resolved hierarchy in a discoverable semantic-token inspection surface without making the existing combined inspector harder to scan.

## Plan brief

- **Likely files:** `src/vs/editor/standalone/browser/inspectEditorTokens/inspectEditorTokens.ts`, `src/vs/platform/theme/common/tokenClassificationRegistry.ts`
- **Validation:** Add or extend an inspector test using a semantic token type with multiple inherited supertypes, then verify the complete ordered hierarchy is visible while standard token inspection remains unchanged.
- **Behavior:**

  > Theme authors inspecting a token contributed by a language extension can discover its complete semantic token type ancestry without manually reading the extension's `semanticTokenTypes` contribution. The hierarchy must include every inherited type in a clear order, not only the immediate supertype. Existing TextMate scope and semantic-token details must remain available and understandable.
- **Trace:**

  > The request concerns the Developer: Inspect Editor Tokens and Scopes surface and the semantic token type hierarchy maintained by the token classification registry. The reporter identified inherited Java token types as the concrete scenario, while the maintainer noted that the current inspector already presents substantial expert-level information. The boundary is inspection and presentation of existing contribution metadata: do not change semantic-token matching, theme fallback semantics, or extension contribution contracts. https://github.com/microsoft/vscode/issues/145312 is related to `superType` semantics but does not own this UI request.
- **Open decisions:**
  - Should hierarchy information appear in the existing combined token inspector, or should semantic-token inspection be separated from TextMate-scope inspection to control information density?
  - Should the inspector always show the full hierarchy for contributed token types, or reveal it only through a secondary expandable/detail interaction?
