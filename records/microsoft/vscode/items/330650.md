# Issue #330650 — Auxiliary window sometimes fails to restore after being maximized on multi-monitor setup

[https://github.com/microsoft/vscode/issues/330650](https://github.com/microsoft/vscode/issues/330650)

## Summary

Two independent commenters confirm the same failure pattern (maximized auxiliary window intermittently fails to restore, sometimes reopening on the wrong monitor/non-maximized), and the underlying restore logic in `applyState`/`AuxiliaryWindow.tryClaimWindow` has known timing/ordering fragility around multi-display maximize restoration — this looks real but the exact race hasn't been isolated in source, so it should go to the window-management area rather than close.

## Change summary

On multi-monitor (and even single-monitor) setups, a maximized auxiliary window sometimes fails to restore correctly on the first VS Code relaunch, only succeeding on a subsequent relaunch.

## Best solution

Have the window-management owners trace the aux-window state restore path (`AuxiliaryWindow.tryClaimWindow`/`applyState` in src/vs/platform/auxiliaryWindow/electron-main/auxiliaryWindow.ts and src/vs/platform/windows/electron-main/windowImpl.ts) for a race between `webContents`/BrowserWindow claim timing and the maximize/setBounds sequence on multi-display setups; the existing TODO comments about Electron multi-display quirks (issues 74872/146499) suggest this is a known fragile area that likely needs first-launch-vs-relaunch instrumentation to pin down.
