# Issue #337278 — Chat session rename silently lost — never persisted, reverts within seconds, no reload/sleep needed

[https://github.com/microsoft/vscode/issues/337278](https://github.com/microsoft/vscode/issues/337278)

## Summary

Well-documented, plausible bug: the reporter traced the append-only chatSessions/*.jsonl op log directly and found the rename op is never written at all, and a second reporter independently corroborates the same subsystem losing ops entirely for whole sessions. I found a concrete code path (loadRemoteSession re-applying `providedSession.title` over the in-memory customTitle) that could explain an in-memory revert racing the persisted rename, but couldn't confirm from source alone that this specific path is the trigger, so this stays open rather than closing.

## Change summary

Renaming a chat session with prior history updates the title in the UI, but the rename is never durably persisted to the session's op log and silently reverts within seconds.

## Best solution

Diagnose the race between the rename write path (ChatService.setChatSessionTitle → chatServiceImpl.ts:424, ChatSessionStore.setSessionTitle → chatSessionStore.ts:510) and whatever re-syncs/reloads session metadata in-memory afterward — a strong candidate is loadRemoteSession unconditionally calling `modelRef.object.setCustomTitle(providedSession.title)` at chatServiceImpl.ts:839 with a stale provider-side title — then make the persisted rename win over any concurrent resync.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts`, `src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts`, `src/vs/workbench/contrib/chat/common/model/chatModel.ts`
- **Validation:** A regression test that renames a loaded session, then simulates whatever resync/reload path is identified as the culprit, and asserts the persisted title (and its op-log entry) matches the rename rather than reverting.
- **Behavior:**

  > Renaming an existing chat session (one with prior history) via the sidebar must durably persist the new title: after the rename, no subsequent in-app operation should silently revert the displayed title, and the session's persisted op log must contain the `setCustomTitle` op for the new title. Acceptance: rename a session, wait several seconds without reload, and confirm both the UI title and the on-disk jsonl op log reflect the new title.
- **Trace:**

  > ChatService.setChatSessionTitle (chatServiceImpl.ts:424) sets model.setCustomTitle(title) then calls ChatSessionStore.setSessionTitle and saveState() to persist the op. The reporter's own inspection of the append-only jsonl confirms the corresponding op never lands, meaning something reverts the in-memory customTitle before the persisted write executes (the write path itself only writes what's currently in the model). One plausible culprit found by inspection: ChatService.loadRemoteSession (chatServiceImpl.ts:838-840) unconditionally calls setCustomTitle(providedSession.title) whenever a provider-backed session is (re)loaded/resynced — if that fires with stale provider data shortly after a user rename, it would silently undo the in-memory title before saveState() ever captures it. This has not been confirmed as the exact trigger; the boundary is to identify and fix the in-memory revert without touching the append-only op-log format or the general rename/save flow. Related: https://github.com/microsoft/vscode/issues/337375 (same op-log symptom, more severe: whole sessions never get any op appended).
- **Open decisions:**
  - Which subsystem re-applies a stale customTitle in-memory shortly after a rename (loadRemoteSession's providedSession.title overwrite at chatServiceImpl.ts:839, or some other periodic resync) needs to be identified via tracing/logging before the actual fix location is chosen.

## Evidence

- **reporter's own root-cause trace:** Reporter inspected the append-only chatSessions/<sessionId>.jsonl directly after reproducing and found the rename's `{"kind":1,"k":["customTitle"],"v":...}` op is absent entirely — since the log is append-only, an absent op means the write never reached persistent storage, not that it was reverted afterward.
- **corroborating related report:** https://github.com/microsoft/vscode/issues/337375 — filed same day by a different reporter (Remote-SSH instead of Remote-WSL), describing the same append-only op log losing ops entirely (0 ops appended for an entire live session) while the extension host session is still live, consistent with an in-memory resync racing persistence rather than a debounce/flush timing bug.
- **rename path:** src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:424-436 (setChatSessionTitle) calls model.setCustomTitle(title) then this._chatSessionStore.setSessionTitle(...) and this.saveState(), which is the only path that should append the customTitle op.
- **candidate overwrite path:** src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:838-840 (loadRemoteSession) unconditionally calls modelRef.object.setCustomTitle(providedSession.title) whenever a provider-backed session is (re)loaded, which would silently revert an in-memory customTitle set moments earlier by a rename if the reload uses stale provider data.
- **no fix found:** git log on chatSessionStore.ts shows only one unrelated recent commit (9c8b8c2b, an agents-session-connector UI fix); no commit addressing rename persistence or the loadRemoteSession title overwrite.
