# Issue #92736 — [themes] Allow gradients along with colors

[https://github.com/microsoft/vscode/issues/92736](https://github.com/microsoft/vscode/issues/92736)

## Summary

This remains a real, well-supported theming gap: current main accepts only hex colors, while the Backlog request has 45 community upvotes. It should stay open for design because gradient support would change the theme value contract and many consumers currently assume a concrete color.

## Change summary

Allow color themes and workbench color customizations to use CSS gradients for themeable backgrounds and borders.

## Best solution

Define a constrained, backward-compatible theme paint capability for eligible background and border roles, including accessible fallbacks, without treating arbitrary CSS as a color or weakening the existing typed color contract.

- **Reason:** Giving theme extensions a supported way to provide richer visual treatments advances the extension ecosystem while avoiding the unsupported workbench patching described in the discussion.

## Plan brief

- **Likely files:** `src/vs/platform/theme/common/colorUtils.ts`, `src/vs/platform/theme/common/themeService.ts`, `src/vs/workbench/services/themes/common/colorThemeData.ts`, `src/vs/workbench/services/themes/browser/colorThemeCss.ts`
- **Validation:** The plan should end with theme-service tests proving that an approved gradient value is accepted and emitted for every eligible background/border category, ordinary hex colors remain unchanged, ineligible foreground roles reject gradients, and high-contrast themes receive the decided fallback.
- **Behavior:**

  > Theme authors and users can assign supported CSS gradients to the background and border roles selected by the maintainers. Existing hexadecimal color values and themes continue to render unchanged, while unsupported theme roles reject gradient values with schema feedback. High-contrast behavior and fallback semantics must be explicit and testable. Acceptance requires loading both theme-file and `workbench.colorCustomizations` gradient values and observing valid generated CSS on representative eligible surfaces.
- **Trace:**

  > The workbench color schema is generated in src/vs/platform/theme/common/colorUtils.ts with `format: 'color-hex'`. ColorThemeData in src/vs/workbench/services/themes/common/colorThemeData.ts stores both theme-file and user-customized values as `Color` instances created by `Color.fromHex`, matching the `IColorTheme.getColor` return contract in src/vs/platform/theme/common/themeService.ts. generateColorThemeCSS in src/vs/workbench/services/themes/browser/colorThemeCss.ts then emits those colors as CSS custom properties, but many downstream styles consume the properties through `background-color` or border-color declarations that cannot accept gradients. The boundary is workbench theme backgrounds and borders: token foregrounds, semantic-token color maps, arbitrary CSS injection, and unrelated icon-theme rendering must remain unchanged. No open canonical issue or open PR was found; https://github.com/microsoft/vscode/issues/58709 is a closed, broader predecessor rather than a valid duplicate target.
- **Open decisions:**
  - Which registered theme roles may accept gradients: all background and border identifiers, or an explicitly declared subset based on how each CSS variable is consumed?
  - What value contract should themes expose: selected standard CSS gradient functions, a structured paint object, or another constrained representation?
  - For border roles, what observable rendering semantics should a gradient have where current consumers use border-color rather than a paint-capable property?
  - What fallback or rejection behavior is required for high-contrast themes and consumers that need a concrete `Color` for calculations rather than CSS rendering?

## Evidence

- **current source gap:** src/vs/platform/theme/common/colorUtils.ts registers every workbench color property as a `color-hex` string, and src/vs/workbench/services/themes/common/colorThemeData.ts parses theme and customization values through `Color.fromHex`; gradient expressions therefore cannot survive loading on current main.
- **typed rendering contract:** IColorTheme.getColor in src/vs/platform/theme/common/themeService.ts returns `Color | undefined`, while src/vs/workbench/services/themes/browser/colorThemeCss.ts serializes each registered value with `color.toString()`. Supporting gradients is consequently a public theme-model and consumer-contract decision, not a local parser change.
- **community demand:** https://github.com/microsoft/vscode/issues/92736 has 45 body upvotes, is assigned to the Backlog milestone, and later comments identify several widely installed extensions that patch workbench CSS to approximate the requested capability.

The older related https://github.com/microsoft/vscode/issues/58709 covered textures as well as gradients and was closed in 2018 through vote-based inbox grooming; it is neither an open duplicate canonical nor strong precedent against this now-backed Backlog item.
