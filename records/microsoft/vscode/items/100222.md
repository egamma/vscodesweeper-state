# Issue #100222 — Support reverse tunnel

[https://github.com/microsoft/vscode/issues/100222](https://github.com/microsoft/vscode/issues/100222)

## Summary

Keep open: the extension API still exposes forward tunnels, not remote-to-local connections to services such as adb. This accepted Backlog request has 144 upvotes, and both current documentation and a maintainer explicitly identify it as the reverse-tunneling discussion.

## Change summary

Allow extensions to create reverse tunnels so remote workspace processes can connect to services running on the user's local machine.

## Best solution

Design a reverse-tunneling extension API backed by the remote connection infrastructure, preserving existing forward-tunnel behavior. Use this issue to settle the supported environments and listener lifecycle before implementation; Android-specific extensions and manual SSH forwarding do not satisfy the general API request.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.proposed.tunnels.d.ts`, `src/vs/workbench/api/common/extHostTunnelService.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadTunnelService.ts`, `src/vs/platform/tunnel/common/tunnel.ts`, `src/vs/platform/tunnel/node/tunnelService.ts`
- **Validation:** In an extension development host connected to a remote workspace, start a TCP echo service on the local machine and request a reverse tunnel through the designed API. A remote process must connect to the returned remote endpoint and exchange data with that local service; disposing the tunnel must stop accepting new connections. Verify ordinary workspace.openTunnel forward connections remain unchanged and unsupported providers return the documented failure.
- **Behavior:**

  > An extension should be able to make a local TCP service reachable from a remote workspace without launching an external SSH forwarding process. This must support generic services, not only adb, and provide an endpoint and disposable lifetime that extensions can manage. Acceptance includes remote-to-local data exchange, listener cleanup on disposal, and unchanged existing forward-tunnel behavior. Supported environments and listener allocation semantics require an explicit API contract.
- **Trace:**

  > The current proposed TunnelOptions in src/vscode-dts/vscode.proposed.tunnels.d.ts describes a remote destination and suggested local port. MainThreadTunnelService.$openTunnel in src/vs/workbench/api/browser/mainThreadTunnelService.ts delegates to remoteExplorerService.forward; the platform contracts in src/vs/platform/tunnel/common/tunnel.ts expose forwardPort only. NodeRemoteTunnel in src/vs/platform/tunnel/node/tunnelService.ts listens locally and connects to a remote destination, confirming that the existing path does not implement the requested opposite direction. Current remote-extension documentation still names this gap, and https://github.com/microsoft/vscode-remote-release/issues/7182#issuecomment-1250677394 designates https://github.com/microsoft/vscode/issues/100222 as its discussion. Preserve existing forward-port semantics and avoid treating an Android-specific workaround as completion. The trace has not established the remote-side listener transport or which resolver environments could support it, so this is API and transport design rather than a bounded implementation task.
- **Open decisions:**
  - Should reverse forwarding be a direction option on workspace.openTunnel or a separate API with its own endpoint contract?
  - Which remote environments must support the initial API, and what observable result should extensions receive when a provider cannot create reverse tunnels?
  - What remote bind address, requested-port fallback behavior, and reconnect lifetime should a reverse tunnel promise?
