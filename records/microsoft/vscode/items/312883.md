- **Behavior:**

  > Opening the local home directory as a workspace must not cause sustained memory growth ending in a renderer crash after one to three minutes. Independent reports describe heat and slowness followed by JavaScript-heap exhaustion, and one commenter reports stability after changing Git detection and cloud-folder exclusions together. The diagnostic session should establish which activity drives retained renderer memory on the current build. Acceptance is a stable, responsive affected workspace under the original configuration, with normal project repository discovery preserved.
- **Trace:**

  > Model.doInitialScan and Model.scanWorkspaceFolders in extensions/git/src/model.ts are concrete starting points for the Git-detection hypothesis. The scan uses a default depth of 1, separate ignored-folder settings, and Dirent.isDirectory filtering; source inspection therefore does not confirm the comment's claim that default Git detection recursively follows the entire home tree and cloud symlinks. The same report also records expensive ripgrep enumeration, so the trace has not reached the renderer object-retention path. src/vs/platform/windows/electron-main/windowImpl.ts forwards Electron's render-process-gone details into the recovery dialog; code 5 is a symptom, not a subsystem diagnosis. Use the measured mitigation at https://github.com/microsoft/vscode/issues/312883#issuecomment-4585939219 as an A/B starting point, not a prescribed change to exclusion semantics. Preserve existing scan settings and ordinary repository discovery unless evidence identifies them as the responsible path; do not alter unrelated Remote-SSH or navigator handling.

## Evidence

- **Confirmed reproduction and memory exhaustion:** https://github.com/microsoft/vscode/issues/312883#issuecomment-4585939219 independently reports the same open-home-folder → heat/slowness → crash sequence on VS Code 1.122.1, M5 Pro, macOS 26.5. Across eight minidumps, the commenter reports a populated v8-oom-location annotation and GC logs near the approximately 4 GB JavaScript heap ceiling. This supports renderer heap exhaustion, but the proposed SCM allocation mechanism has not been independently verified.
- **Measured mitigation:** https://github.com/microsoft/vscode/issues/312883#issuecomment-4585939219 reports renderer memory falling from approximately 3,900 MB to 720 MB after jointly changing git.autoRepositoryDetection to openEditors, disabling git.autofetch, and excluding cloud-storage directories. Because several settings changed together, this is an isolation lead rather than proof that repository scanning alone owns the defect.
- **Current source limits the scanning hypothesis:** extensions/git/src/model.ts:361-447 shows Model.scanWorkspaceFolders using git.repositoryScanMaxDepth and git.repositoryScanIgnoredFolders, followed by traverseWorkspaceFolder filtering entries with Dirent.isDirectory(). extensions/git/package.json:4033-4037 defaults the depth to 1. This path does not consult files.exclude, files.watcherExclude, or search.exclude, but neither does it establish unrestricted traversal of the entire home tree or ordinary directory symlinks under default settings.
- **Original report contains another enumeration lead:** The full body at https://github.com/microsoft/vscode/issues/312883 records a home workspace with more than 21,315 files and two highly active ripgrep file-enumeration processes using --follow. The reporter's exclusions are already substantial. These observations warrant separating search/indexing activity from Git detection rather than accepting a single causal explanation.
- **Older related report is not a verified root-cause canonical:** https://github.com/microsoft/vscode/issues/267703 is currently open. Its original trigger is heavy file creation/deletion, while https://github.com/microsoft/vscode/issues/267703#issuecomment-4415717331 confirms a closely matching home-directory crash. However, that thread also includes crashes without a workspace and lacks evidence tying its original defect to the SCM/heap mechanism reported here; matching error code 5 alone does not establish common ownership.
- **Other crash signatures and workaround differ:** https://github.com/microsoft/vscode/issues/266324#issuecomment-3287193864 identifies a text-rendering allocator failure, distinct from the JavaScript-heap exhaustion reported here. The open https://github.com/microsoft/vscode/issues/316744 describes JIT-page-registration frames. The suggested workaround in https://github.com/microsoft/vscode/issues/312110 concerns a remote Node navigator migration error, whereas this report explicitly crashes its local home-folder window.
- **Additional canonical search:** Searches for home-directory crashes and CloudStorage found the open https://github.com/microsoft/vscode/issues/312925 and https://github.com/microsoft/vscode/issues/324809. Their documented triggers center on Remote-SSH with Copilot indexing or restored chat sessions, not the independently reported local home-folder/repository-detection case. Neither establishes that it owns this report's complete remaining behavior.
- **No completed fix established:** The reporter's temporary stability after downgrading to 1.115.0 is recorded at https://github.com/microsoft/vscode/issues/312883#issuecomment-4335211660, but a later reproduction exists on 1.122.1. The checkout exposes only one history commit, e3c2316227ee9a4b24449b779409e3ff4d0126a9, so no behavior-changing fix commit was established. No execution or reproduction on current main was performed.
