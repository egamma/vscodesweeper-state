# Issue #305916 — Organize issues on PROBLEMS tab by project

[https://github.com/microsoft/vscode/issues/305916](https://github.com/microsoft/vscode/issues/305916)

## Summary

A real gap remains on current main: the Problems tree groups diagnostics directly by file and has no workspace-folder/project level. The Backlog milestone bars a decline close, and no open older issue was found that meets the re-review duplicate bar, so this should remain open for a product decision.

## Change summary

Add a workspace-folder/project grouping level to the Problems tree for multi-root workspaces.

## Best solution

Let the Problems view group resource nodes beneath their containing workspace folders in multi-root workspaces, while preserving the current file-first presentation for single-folder workspaces. A maintainer should first decide whether this hierarchy is automatic or an additional selectable grouping mode.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/markers/browser/markersModel.ts`, `src/vs/workbench/contrib/markers/browser/markersView.ts`, `src/vs/workbench/contrib/markers/browser/markersTreeViewer.ts`, `src/vs/workbench/contrib/markers/test/browser/markersModel.test.ts`
- **Validation:** Add Problems model/tree tests using diagnostics from two workspace roots, asserting each file appears beneath the correct project node and that single-folder behavior remains unchanged; run the targeted markers browser unit-test suite.
- **Behavior:**

  > In a multi-root workspace, Problems tree mode should make it possible to distinguish diagnostics by workspace project before expanding individual files. Each file and diagnostic must appear exactly once beneath the correct project, with filtering, counts, navigation, and related-information children still working. Single-folder workspaces should retain a compact presentation unless the selected grouping contract explicitly says otherwise.
- **Trace:**

  > On current main, MarkersModel in src/vs/workbench/contrib/markers/browser/markersModel.ts stores a flat map of ResourceMarkers, while MarkersTree.reset in src/vs/workbench/contrib/markers/browser/markersView.ts installs every ResourceMarkers as a root child. MarkerElement, renderers, filtering, accessibility labels, identity, and tree-update logic currently know only resource, marker, and related-information nodes. Workspace folders are available to MarkersView through IWorkspaceContextService but are currently used only to resolve files.exclude expressions. The boundary is the Problems tree hierarchy: table mode, diagnostic production, severity ordering within files, and editor navigation should not change. The older same-area report https://github.com/microsoft/vscode/issues/64481 is closed and cannot own this work.
- **Open decisions:**
  - Should workspace-folder grouping become the automatic tree hierarchy for every multi-root workspace, or be an additional selectable grouping mode alongside the existing file-first tree?
  - Where should diagnostics whose resources are outside every workspace folder appear: in a dedicated group or alongside workspace-folder groups at the root?

## Evidence

- **current source:** src/vs/workbench/contrib/markers/browser/markersView.ts creates each top-level MarkersTree child directly from a ResourceMarkers instance in MarkersTree.reset; createResourceMarkersIterator then adds diagnostics beneath that file. There is no workspace-folder node.
- **current model:** src/vs/workbench/contrib/markers/browser/markersModel.ts defines MarkerElement only as ResourceMarkers | Marker | RelatedInformation and MarkersModel.resourceMarkers returns a flat, sorted collection of file resources, so the requested project hierarchy is not represented on current main.
- **existing capability check:** The Problems view consults workspace folders only for per-root files.exclude expressions in src/vs/workbench/contrib/markers/browser/markersView.ts; that filtering support does not group displayed resources by workspace folder.
- **canonical search:** https://github.com/microsoft/vscode/issues/64481 is an older related request that explicitly mentions grouping Problems by project, but it is closed by the feature-request lifecycle and therefore cannot serve as a duplicate canonical. Other inspected grouping reports concern grouping by message or Java subprojects rather than the same multi-root workspace-folder hierarchy.
