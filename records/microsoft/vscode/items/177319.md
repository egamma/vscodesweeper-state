# Issue #177319 — TimelineItem command callback values are now useless for "foreign" extensions

[https://github.com/microsoft/vscode/issues/177319](https://github.com/microsoft/vscode/issues/177319)

## Summary

A real API gap remains: current main exposes the originating TimelineItem to foreign extensions only when they have the proposed Timeline API enabled, which published Marketplace extensions generally cannot rely on. Keep this accepted Backlog request open pending Timeline API finalization.

## Change summary

Provide foreign extension commands with stable metadata identifying the selected timeline item instead of only its file URI.

## Best solution

Finalize the Timeline API with a stable command context that gives foreign extensions a clone of the public TimelineItem metadata while preserving the originating extension's live instance and private properties.

## Evidence

- **current source:** src/vs/workbench/api/common/extHostTimeline.ts processes TimelineActionContext by returning the cached TimelineItem only when the receiving extension has the `timeline` proposal enabled; otherwise it returns undefined.
- **partial implementation:** https://github.com/microsoft/vscode/commit/e47951d00e72efa8d3b1a0eddddb02f451daf3d9 expanded access from the provider extension to all proposal-enabled extensions, but did not establish a stable context for ordinary published extensions.
- **publishing constraint:** src/vs/workbench/services/extensions/common/extensionsRegistry.ts documents that `enabledApiProposals` is valid during development and extensions cannot be published with it, so the partial implementation does not cover the central Marketplace-extension scenario.
- **API prerequisite:** https://github.com/microsoft/vscode/issues/84297 remains open with `api-proposal` and tracks Timeline API finalization; its discussion confirms the API is still proposed.
- **confirmed impact:** https://github.com/microsoft/vscode/issues/178548 was confirmed by maintainers as the same Timeline item API regression and closed as a duplicate of this issue, making this the existing canonical report for the callback-context gap.
