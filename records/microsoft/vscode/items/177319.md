# Issue #177319 — TimelineItem command callback values are now useless for "foreign" extensions

[https://github.com/microsoft/vscode/issues/177319](https://github.com/microsoft/vscode/issues/177319)

## Summary

The accepted Backlog request remains necessary: current main still replaces the timeline action context with `undefined` for foreign extensions, while a maintainer explicitly planned to provide those extensions a detached public-API clone after Timeline API finalization.

## Change summary

Expose useful detached TimelineItem metadata to commands contributed by extensions other than the timeline provider.

## Best solution

Define and test a safe cross-extension command contract that gives the provider its original item and other extensions a detached representation of the public TimelineItem data. Coordinate that contract with Timeline API finalization tracked by https://github.com/microsoft/vscode/issues/84297.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostTimeline.ts`, `src/vs/workbench/contrib/timeline/browser/timelinePane.ts`, `src/vscode-dts/vscode.proposed.timeline.d.ts`
- **Validation:** Add an extension-host unit test that invokes a Timeline item action from both the provider extension and a foreign extension, asserting that the provider receives its original instance while the foreign extension receives useful detached public metadata and cannot access provider-private properties.
- **Behavior:**

  > Commands invoked from a Timeline item must receive useful item-specific context even when the command belongs to an extension other than the timeline provider. The provider may retain its original object identity and private data, but a foreign extension must receive only a detached, documented representation and must not receive `undefined`. The resource URI, source, and existing command argument ordering must remain compatible. Acceptance requires coverage for both provider-owned and foreign-extension commands.
- **Trace:**

  > TimelineActionRunner in src/vs/workbench/contrib/timeline/browser/timelinePane.ts marshals the selected item's handle, source, and URI. ExtHostTimeline's argument processor in src/vs/workbench/api/common/extHostTimeline.ts resolves the cached original only for an extension using the proposed Timeline API and returns `undefined` otherwise; this is the current source-level cause of the reported behavior. The public item shape remains proposed in src/vscode-dts/vscode.proposed.timeline.d.ts and finalization is tracked by https://github.com/microsoft/vscode/issues/84297. A maintainer stated at https://github.com/microsoft/vscode/issues/177319#issuecomment-1486662960 that foreign extensions should receive a public clone while the origin receives its instance. Preserve provider-private properties and object identity only for the originating extension; do not restore live-object sharing across extensions or broaden the change beyond Timeline action arguments.
- **Open decisions:**
  - Should useful cross-extension Timeline command context remain blocked on full Timeline API finalization, or should a detached stable context contract be exposed before the provider API itself is finalized?

## Evidence

- **current source behavior:** On current main, src/vs/workbench/contrib/timeline/browser/timelinePane.ts:1121-1137 marshals a TimelineActionContext containing the item handle, source, and URI, but src/vs/workbench/api/common/extHostTimeline.ts:43-51 resolves it only for extensions with the proposed `timeline` API enabled and otherwise returns `undefined`.
- **public metadata exists:** src/vscode-dts/vscode.proposed.timeline.d.ts defines the detachable public TimelineItem fields, including timestamp, label, id, description, tooltip, contextValue, and accessibilityInformation; current conversion in src/vs/workbench/api/common/extHostTimeline.ts:125-186 already creates a serialized internal representation of those properties.
- **maintainer direction:** https://github.com/microsoft/vscode/issues/177319#issuecomment-1486662960 states the plan: give third-party extensions a clone of the public API object while preserving the originating extension's own instance, after the Timeline API is finalized.
- **finalization dependency:** https://github.com/microsoft/vscode/issues/84297 remains open with `api-proposal` and tracks Timeline API finalization; its discussion records unresolved API scope. It is broader API tracking, not the same reporter-observable command-callback symptom required for a duplicate close on this re-reviewed issue.
- **confirmed impact:** https://github.com/microsoft/vscode/issues/178548 was confirmed by maintainers as the same Timeline action-object change and closed in favor of this issue; the GitLens and galaxy-workflows cross-references show multiple extensions lost item-specific command context.
- **no implementation candidate:** No open microsoft/vscode pull request references https://github.com/microsoft/vscode/issues/177319, and current main retains the restrictive behavior introduced by https://github.com/microsoft/vscode/pull/169621.
