# Issue #269610 — Allow granular auto-approval settings for Copilot Chat tools

[https://github.com/microsoft/vscode/issues/269610](https://github.com/microsoft/vscode/issues/269610)

## Summary

Keep open: current main provides per-tool eligibility, saved approvals, and a management UI, but these do not fully deliver unified, declarative approval rules with granular enterprise enforcement. The maintainer-supported direction remains relevant; the verified related issues are newer and cover narrower requirements.

## Change summary

Provide configurable auto-approval for selected trusted tools or tool sources, with organization-managed restrictions and an accessible management surface.

## Best solution

Provide a coherent approval configuration and management experience for selected tools and sources while preserving specialized terminal, edit, and URL rules. Enterprise restrictions should remain authoritative through the runtime managed-settings contract, rather than relying on saved UI preferences or a blanket bypass lock.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts`, `src/vs/workbench/contrib/chat/browser/tools/languageModelToolsConfirmationService.ts`, `src/vs/workbench/contrib/chat/browser/tools/languageModelToolsService.ts`, `src/vs/platform/agentHost/common/agentHostManagedSettings.ts`, `src/vs/platform/agentHost/common/agentHostPolicySupport.ts`
- **Validation:** The plan should end with runnable approval checks using two confirmation-requiring tools: a configured trusted tool runs without prompting, an unapproved tool still prompts, and an administrator-required confirmation cannot be bypassed by session mode or saved approvals. Verify distinct same-named tools from different MCP sources, persistence after reload, management UI visibility, and unchanged specialized terminal/edit/URL behavior.
- **Behavior:**

  > Users can configure selected trusted tools or tool sources for automatic approval while retaining manual confirmation for others. Administrators can enforce granular restrictions that personal preferences and saved approvals cannot override. The management surface makes configured approvals and managed restrictions understandable. Acceptance must distinguish eligibility from actual approval and preserve existing specialized terminal, edit, and URL controls.
- **Trace:**

  > The current configuration registers chat.tools.global.autoApprove as a boolean and chat.tools.eligibleForAutoApproval as a policy-capable eligibility map in chat.shared.contribution.ts. LanguageModelToolsService checks eligibility and saved approvals, and also retains an object-valued global-setting compatibility path that is not represented by the registered schema. LanguageModelToolsConfirmationService supplies per-tool and MCP-server approvals, stores them outside settings, and exposes manageConfirmationPreferences through workbench.action.chat.editToolApproval. Agent Host's contributeEligibleForAutoApprovalRestriction instead produces a session-wide bypass lock; agentHostPolicySupport marks this policy partial. These observations establish partial coverage, not a complete diagnosis of every runtime path. Preserve existing specialized approval formats and treat enterprise enforcement as runtime-owned rather than duplicating its matcher in the workbench. Coordinate the narrower enforcement work at https://github.com/microsoft/vscode/issues/337540 and MCP identity requirements at https://github.com/microsoft/vscode/issues/283422 without treating either as a canonical for this broader request.
- **Open decisions:**
  - Which selectors should the supported public rule format include: exact tools only, extension-wide groups, MCP-server groups, or a combination, and how should same-named tools from different sources be distinguished?
  - Should selected-tool rules only operate in the normal approval mode, or should users also be able to retain explicit manual-confirmation exceptions while a bypass mode is selected, independently of mandatory administrator restrictions?
