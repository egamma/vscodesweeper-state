# Issue #269610 — Allow granular auto-approval settings for Copilot Chat tools

[https://github.com/microsoft/vscode/issues/269610](https://github.com/microsoft/vscode/issues/269610)

## Summary

Keep open for product design: maintainers accepted the need for unified, granular auto-approval configuration, but the setting format must accommodate different tool kinds and finer-grained tool-specific rules. The On Deck milestone and maintainer direction rule out a decline close, while the prior claimed implementation was independently refuted.

## Change summary

Allow users and organizations to configure auto-approval for selected Copilot Chat tools or tool groups instead of enabling it globally.

## Best solution

Define one policy-manageable permission model and settings UI that can match common tool identities while allowing specialized scopes for terminal, editing, MCP, and extension-provided tools without weakening confirmation defaults.

- **Trace:**

  > The issue and Tyriar's comments establish the desired direction but leave the public configuration contract unsettled: one representation must cover built-in tools, extension-provided tools, MCP/FastMCP identifiers, and tool-specific granular formats. The likely boundary is Chat tool configuration and approval resolution in the chat contribution and language-model tool service; do not weaken the default confirmation path or collapse terminal/edit-specific permission semantics. https://github.com/microsoft/vscode/issues/293276 is a newer, narrower skill-scoped permission request and should be considered during design, not used as a duplicate target.
- **Open decisions:**
  - What stable public identifier and matching model should the setting expose for built-in, extension-provided, and MCP tools?
  - Should specialized scopes such as terminal commands and edit targets share one nested schema with tool-level approval, or remain separate settings with defined precedence?
  - When user configuration and organization policy differ, which scopes may users narrow or broaden, and how should the effective permission be presented in the UI?
