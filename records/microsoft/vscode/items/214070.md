# Issue #214070 — Standardize UI Navigation with `workbench.action.navigate`

[https://github.com/microsoft/vscode/issues/214070](https://github.com/microsoft/vscode/issues/214070)

## Summary

This remains a valid, accepted backlog request: current directional navigation stops at workbench-part boundaries and does not provide the requested navigation among sidebar panes or their internal focus regions. The older related report was closed in favor of this broader issue, confirming that this is the canonical place for the work.

## Change summary

Make the `workbench.action.navigateUp/Down/Left/Right` commands provide consistent directional keyboard navigation across workbench parts, sidebar views, and focus regions within views.

## Best solution

Define a consistent directional focus model spanning editor groups, workbench parts, view panes, and relevant controls within each pane, while preserving the existing behavior of stopping at outer boundaries rather than cycling. The design should settle whether activity/status bars participate and how individual views expose navigation between internal focus regions.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/actions/navigationActions.ts`, `src/vs/workbench/browser/parts/views/viewPaneContainer.ts`, `src/vs/workbench/browser/parts/views/viewPane.ts`, `src/vs/workbench/common/views.ts`
- **Validation:** Add workbench navigation tests covering directional movement between multiple visible sidebar panes and boundary movement between sidebar, editor, panel, and any approved activity-bar targets; manually verify the same bindings from Search and Testing input/list regions.
- **Behavior:**

  > The four `workbench.action.navigate*` commands should provide predictable directional keyboard movement throughout the visible workbench rather than stopping at the containing sidebar or panel. Users must be able to move between visible panes in a view container and, where included in the agreed scope, between distinct focus regions such as a search input and its results. Existing editor-group and cross-part navigation must remain intact, hidden regions must not be opened, and navigation should stop rather than cycle at an outer boundary.
- **Trace:**

  > BaseNavigationAction in src/vs/workbench/browser/actions/navigationActions.ts identifies only the focused workbench Part and delegates to IWorkbenchLayoutService.getVisibleNeighborPart; sidebar focus therefore has no path to a neighboring ViewPane. ViewPaneContainer in src/vs/workbench/browser/parts/views/viewPaneContainer.ts owns the ordered panes, records lastFocusedPane through onDidFocus, and can focus a pane, but it has no directional navigation contract. Individual ViewPane instances in src/vs/workbench/browser/parts/views/viewPane.ts already expose focus events and focus(). Existing commands for changing sidebar containers or focusing specific view regions remain separate and only partially cover the requested workflow. The narrower https://github.com/microsoft/vscode/issues/170200 was closed into this issue, so this issue owns pane-level navigation as well as the broader consistency question. Preserve existing directional editor-group behavior and the established rule that navigation does not reveal hidden parts or wrap at outer boundaries.
- **Open decisions:**
  - Should `workbench.action.navigate*` traverse only structural regions such as parts and ViewPane boundaries, or must each participating view expose directional transitions among internal controls such as Search and Testing inputs and result trees?
  - Which peripheral workbench regions participate in directional navigation: the activity bar requested here, the status bar as well, or neither?
  - When the next ViewPane is collapsed, should directional navigation focus its header, skip it, or expand it before focusing?

## Evidence

- **current source gap:** src/vs/workbench/browser/actions/navigationActions.ts implements BaseNavigationAction at Parts granularity: sidebar, panel, and auxiliary-bar focus each resolve only through IWorkbenchLayoutService.getVisibleNeighborPart, with no navigation among the active container's individual views or controls.
- **available pane state:** src/vs/workbench/browser/parts/views/viewPaneContainer.ts tracks panes and lastFocusedPane and its focus() method restores one pane, but it exposes no next/previous or directional pane-focus operation. src/vs/workbench/browser/parts/views/viewPane.ts provides per-pane focus tracking and focus(), so the underlying focus state exists but is not integrated with navigateUp/navigateDown.
- **canonical consolidation:** https://github.com/microsoft/vscode/issues/170200 reported the narrower observable symptom of navigateDown not moving between sidebar panes; a maintainer closed it on 2024-12-16 as a duplicate of https://github.com/microsoft/vscode/issues/214070.
- **maintainer routing:** The issue is in the Backlog and carries help wanted, accessibility, layout, and workbench-views, indicating that it has already been accepted and routed as actionable feature work.
- **existing capability is partial:** workbench.action.nextSideBarView, workbench.action.previousSideBarView, workbench.action.focusActivityBar, and view-specific focus commands cover individual transitions, but they do not satisfy the central request for one directional command family across these regions.
