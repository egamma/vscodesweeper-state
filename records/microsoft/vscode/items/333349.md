# Issue #333349 — "Window Is Not Responding" Dialog Steals Keyboard Focus and Shuts Down the Window on a Keystroke, Destroying Unsaved State

[https://github.com/microsoft/vscode/issues/333349](https://github.com/microsoft/vscode/issues/333349)

## Summary

Real, traceable defect: the 'window is not responding' dialog is a native modal that can take OS-level keyboard focus while the renderer is still busy, and its default (Enter-triggered) button is 'Reopen' — a destructive action — because windowImpl.ts never overrides the app-wide defaultId=0 convention for this specific dialog.

## Change summary

The unresponsive-window dialog can be accidentally dismissed via a stray Enter/keystroke, reopening (destroying) the window's in-memory state instead of the safer 'Keep Waiting' option.

## Best solution

Have windowImpl.ts explicitly pass `defaultId`/`cancelId` pointing at the 'Keep Waiting' button (index 2) for the UNRESPONSIVE dialog specifically, so an accidental keystroke while the dialog is stealing focus can't trigger a destructive reload — this is a small, targeted change to the onWindowError UNRESPONSIVE branch, but the exact desired UX (which button should be default, whether to delay interactivity) is a maintainer call.

## Evidence

- **default button is destructive:** src/vs/platform/windows/electron-main/windowImpl.ts:1029-1039 shows the buttons array as ['Reopen','Close','Keep Waiting'] with no explicit defaultId/cancelId passed.
- **app-wide default is button 0:** src/vs/platform/dialogs/electron-main/dialogMainUtils.ts:39 sets `let defaultId = 0; // by default the first button is default button` when the caller doesn't override it, and `cancelId` defaults to the last button (index 2, 'Keep Waiting') — so Escape is already safe but Enter is not.
- **destructive path:** windowImpl.ts:1042-1046: `if (response !== 2 /* keep waiting */) { const reopen = response === 0; ... await this.destroyWindow(reopen, checkboxChecked); }` — response 0 ('Reopen') destroys and recreates the window, discarding in-memory state not covered by hot-exit backups.
- **native modal takes OS focus:** dialogMainService.showMessageBox (src/vs/platform/dialogs/electron-main/dialogMainService.ts:150-158) calls electron.dialog.showMessageBox(window, options), a native modal that can capture OS keyboard focus even while the renderer content is still catching up, which explains why keystrokes aimed at the editor can land on the dialog instead.
