# Issue #331100 — "Add feedback" and `/act-on-feedback` go overly narrow

[https://github.com/microsoft/vscode/issues/331100](https://github.com/microsoft/vscode/issues/331100)

## Summary

The current source confirms the interaction is narrowly framed as actionable feedback even though selected-code annotations could naturally be questions. This team-authored polish issue should remain open while maintainers choose whether to generalize the workflow or expose distinct question and feedback actions.

## Change summary

Generalize the Changes annotation terminology and submission behavior so users can ask questions about selected code without implying that the agent must modify it.

## Best solution

Let selected-code comments carry either conversational questions or actionable feedback without forcing every submission through `/act-on-feedback`; preserve the focused action-and-resolution workflow when the user explicitly requests changes.

- **Behavior:**

  > Users can annotate selected code in the Changes editor to ask a question without the UI or resulting prompt implying that a code modification is required. Explicit actionable feedback must continue to tell the agent to address the comment and preserve the existing submission and resolution workflow. Labels, placeholders, and accessible names should describe the chosen distinction consistently.
- **Trace:**

  > AgentFeedbackEditorInputContribution in src/vs/sessions/contrib/agentFeedback/browser/agentFeedbackEditorInputContribution.ts presents “Add Feedback” for changed files and exposes Add / Add and Submit actions. SubmitFeedbackAction in agentFeedbackEditorActions.ts calls AgentFeedbackService.submitFeedback, whose default request in agentFeedbackService.ts is `/act-on-feedback`. The built-in skill at src/vs/sessions/skills/act-on-feedback/SKILL.md instructs the model to modify code and resolve or delete comments, which is where the informational-question intent becomes actionable. The service already accepts a custom query through ISubmitFeedbackOptions, but the ordinary UI path does not expose a general conversational mode. Keep PR-comment behavior and explicit feedback resolution semantics outside the scope of the wording/generalization change.
- **Open decisions:**
  - Should one neutral “Comment” action infer whether an annotation is a question or actionable feedback, or should the UI expose distinct question/comment and feedback actions?
  - When a submitted annotation is only a question, should it participate in the existing submitted/resolved feedback lifecycle or remain a conversational reference that does not require resolution?

## Evidence
