# Issue #108256 — resources#relativePath does not honour path casing strategy

[https://github.com/microsoft/vscode/issues/108256](https://github.com/microsoft/vscode/issues/108256)

## Summary

This remains valid URI-handling debt: maintainers agreed that `relativePath` should honor the configured casing strategy, but the attempted fix exposed non-canonical URI callers and was not merged. The Backlog milestone does not bar cleanup, but there is no fix commit or verified duplicate supporting closure.

## Change summary

Make URI relative-path calculation consistently honor the filesystem path-casing strategy without breaking callers that pass non-canonical Windows file URIs.

## Best solution

Audit callers of the case-sensitive `extUri.relativePath`, migrate operations that know filesystem capabilities to `IUriIdentityService.extUri`, and define safe compatibility behavior for generic helpers, including Windows drive-letter casing.

## Plan brief

- **Likely files:** `src/vs/base/common/resources.ts`, `src/vs/base/test/common/resources.test.ts`
- **Validation:** Extend the resources unit tests so `IExtUri.relativePath` honors both case-sensitive and case-insensitive strategies, including differently cased Windows drive letters, then run the targeted resources test suite.
- **Behavior:**

  > Relative-path calculation must honor the casing strategy supplied by the URI identity implementation. On a case-insensitive strategy, differently cased path segments and Windows drive letters should still produce the expected descendant-relative path; on a case-sensitive strategy, casing differences must remain significant. Existing URI root handling and callers of the unbiased generic helper must retain their documented semantics.
- **Trace:**

  > The report traces the inconsistency to `src/vs/base/common/resources.ts`: the historical `file`-URI branch delegates to platform path handling instead of consistently consulting `IExtUri`'s `_ignorePathCasing` strategy. The closed attempt https://github.com/microsoft/vscode/pull/108796 removed that special case but exposed callers passing non-canonical Windows URIs, especially drive letters with different casing. The discussion prefers capability-aware operations through `IUriIdentityService.extUri`, while the exported generic helper remains deliberately unbiased. The audit must bound changes to URI-relative-path semantics and affected callers; it must not broadly canonicalize every URI or alter unrelated path normalization.
- **Open decisions:**
  - Should the generic exported `resources.relativePath` remain strictly case-sensitive, become biased toward case-insensitive file behavior for compatibility, or require callers needing filesystem semantics to use `IUriIdentityService.extUri`?
  - Should Windows drive-letter comparison ignore casing independently of the configured path-casing strategy?

## Evidence

- **maintainer agreement:** In https://github.com/microsoft/vscode/issues/108256#issuecomment-707681615, a maintainer agreed that when scheme case sensitivity is known, relative-path calculation should follow it rather than use the `file` special case.
- **attempted fix:** https://github.com/microsoft/vscode/pull/108796 is closed rather than merged; its investigation exposed Windows drive-letter casing failures and callers that may supply non-canonical URIs.
- **remaining design constraint:** The issue discussion identifies the preferred direction as using canonical URIs or `IUriIdentityService.extUri`, while preserving correct behavior for generic `resources.relativePath` callers.
