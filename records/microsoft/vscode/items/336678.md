# Issue #336678 — Session fails to create worktree, but is still displayed as worktree

[https://github.com/microsoft/vscode/issues/336678](https://github.com/microsoft/vscode/issues/336678)

## Summary

Confirmed on current main: Agent Host correctly falls back to the original folder after worktree creation fails, but the Sessions provider continues presenting the session as a pending worktree. This team-authored issue should remain open for a fix.

## Change summary

A session that falls back to its original folder after worktree creation fails retains the worktree icon and pending-worktree presentation.

## Best solution

Expose the effective post-creation workspace state to the Sessions provider so a failed worktree attempt is presented as a folder session, including after reload, without changing successful or genuinely pending worktree sessions.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/agentService.ts`, `src/vs/platform/agentHost/node/shared/worktreeIsolation.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/sessions/contrib/providers/agentHost/test/browser/localAgentHostSessionsProvider.test.ts`
- **Validation:** Add a focused provider test that starts with worktree isolation, applies a failed first-send outcome with the original folder as the effective working directory, and asserts `session.worktreePending.get()` becomes false while successful and unresolved worktree cases remain true as appropriate; include a restored-session case.
- **Behavior:**

  > When creation of an isolated worktree fails and the agent continues in the original folder, the committed session must be presented as a folder session rather than as a worktree still being created. Its row icon and accessible label must stop indicating a worktree, including after the session is restored. Successfully created worktrees and worktrees genuinely awaiting first-send creation must retain their current presentation.
- **Trace:**

  > AgentService in src/vs/platform/agentHost/node/agentService.ts falls back to the picked folder after `_resolveWorktreeBeforeSend` fails, and WorktreeIsolation.resolveOnFirstSend in src/vs/platform/agentHost/node/shared/worktreeIsolation.ts clears the host-local pending marker regardless of outcome. The UI does not consume that marker: AgentHostSessionAdapter in src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts derives `worktreePending` from the selected isolation config plus absence of a worktree URI, which is also exactly the post-failure state. SessionsList then renders the worktree icon and pending ARIA text from that stale value. The uncertainty starts at the process boundary: the effective fallback outcome needs a durable representation that survives restoration without rewriting the user's original configuration choice or changing successful-worktree behavior.
- **Open decisions:**
  - Should effective isolation after first-send resolution be represented as explicit protocol/session metadata, or derived from an existing durable worktree-failure record?
  - Should the original requested isolation remain `worktree` in session configuration while presentation consumes a separate effective-workspace state?
  - What persisted state should restored sessions use to distinguish a failed worktree from one that is still pending creation?

## Evidence

- **fallback behavior:** src/vs/platform/agentHost/node/agentService.ts `_resolveWorkingDirectoryBeforeSend` falls back to `pickedFolderUri` when `_resolveWorktreeBeforeSend` returns undefined; its existing test in src/vs/platform/agentHost/test/node/agentService.test.ts confirms the failed session continues with the source directory and emits a WorktreeCreationFailure notification.
- **host pending state:** src/vs/platform/agentHost/node/shared/worktreeIsolation.ts `resolveOnFirstSend` clears its pending marker in a `finally` block, so Agent Host itself no longer considers the failed worktree pending.
- **stale UI derivation:** src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts derives `AgentHostSessionAdapter.worktreePending` from the original worktree-isolation selection and the absence of `workTreeUri`. After fallback, both conditions remain true indefinitely; `_applyWorktreeIsolation` only sets isolation to true and receives no effective failure outcome.
- **visible impact:** src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts uses `worktreePending` to select `Codicon.worktreeCompact` and to announce “creating worktree,” so the failed session remains visibly and accessibly misclassified.
