# Issue #290290 — Agent Skill: Allow users to enable/disable specific skills

[https://github.com/microsoft/vscode/issues/290290](https://github.com/microsoft/vscode/issues/290290)

## Summary

Keep open: current main exposes individual Enable/Disable actions for built-in skills, but those actions exclude workspace, user, and other extension-provided skills requested in the discussion. The linked implementation PR was closed without merging, so it does not establish completion.

## Change summary

Allow users to disable and re-enable individual installed or discovered skills without deleting their files or disabling the contributing extension.

## Best solution

Provide consistent per-skill enablement across workspace, user, built-in, and extension sources, with the selected runtime honoring the displayed state. Settle persistence and cross-harness expectations before extending the existing partial controls; extension API control and CLI synchronization are related requests, not proven existing capabilities.

Confirm files and sibling skills remain unchanged, then reload and check the agreed persistence semantics in each supported harness.
- **Behavior:**

  > Users can keep a skill installed while independently disabling and re-enabling it. Cover workspace, user, built-in, and extension-provided skills, including extension contributions with no configurable when clause. Disabled skills must not remain advertised as available to the agent, and re-enabling must restore availability without editing files or disabling the extension. Acceptance includes independent sibling state, consistent displayed and effective state, and persistence according to the agreed scope.
- **Trace:**

  > The Enable/Disable actions in src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagement.contribution.ts already call IPromptsService but are exposed only for built-in skills. PromptsServiceImpl in src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts stores disabled URIs at profile scope and filters them from slash-command discovery; promptsServiceCustomizationItemProvider.ts and aiCustomizationItemSource.ts project disabled state into customization items. This establishes partial support, not end-to-end coverage across runtimes. https://github.com/microsoft/vscode/issues/329753 documents separate disablement stores and consumer inconsistencies that the planning session must account for. https://github.com/microsoft/vscode/pull/311806 is closed and unmerged. Preserve skill files, existing extension contribution conditions, and unrelated extension functionality; disabling a skill is an availability control, not a new security sandbox.
- **Open decisions:**
  - Should individual skill disablement retain the existing profile-wide behavior, support workspace-specific choices, or offer both?
  - Should enablement be independent per harness, or should this feature share selection with Copilot CLI as requested in the discussion?
