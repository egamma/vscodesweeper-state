# Issue #333128 — Integrated Browser: Chrome DevTools remote-debugging frontend fails with `(blocked:origin)` / "Unsafe attempt to load URL ... from frame with URL chrome-error://chromewebdata/" when not using Remote-SSH/WSL port forwarding

[https://github.com/microsoft/vscode/issues/333128](https://github.com/microsoft/vscode/issues/333128)

## Summary

Well-diagnosed, technical report of a real inconsistency: the integrated browser's PNA-blocked-origin failure for manually-tunneled localhost debug ports vs. its working behavior under Remote-SSH/WSL's own port forwarding. No maintainer has weighed in and there's no fix to cite, so this stays open for area triage.

## Change summary

Chrome DevTools remote-debugging frontend fails with a Private Network Access `(blocked:origin)` error in the Integrated Browser when the target port is reached via a manually created SSH tunnel, but works when reached via VS Code's own Remote-SSH/WSL automatic port forwarding.

## Best solution

Belongs with the browserView/tunnel-proxy owners in src/vs/platform/browserView/electron-main (and the tunnel proxy in src/vs/platform/tunnel) to decide whether/how to extend the remote-forwarding path's PNA-friendly treatment to manually forwarded loopback ports — this is a security-sensitive trade-off (bypassing a Chromium security check for arbitrary localhost targets) that needs a maintainer product/security call, not an automatic fix.

## Evidence

- **tunnel proxy bypasses loopback:** src/vs/platform/browserView/electron-main/browserSessionRemote.ts _applyProxy() sets `proxyBypassRules: '<-loopback>'`, so requests to 127.0.0.1 are NOT routed through the remote tunnel proxy even when a session is 'remote' — the working Remote-SSH/WSL case must rely on VS Code's port-forwarding URL rewriting (per the browserView skill's 'Remote pages' section: 'remote URLs are rewritten to their forwarded form'), not on any PNA-specific header injection.
- **reporter's own diagnosis:** Reporter correctly attributes the failure to Chromium's Private Network Access preflight requiring `Access-Control-Allow-Private-Network: true`, which a raw --remote-debugging-port listener never sends; this matches known Chromium PNA behavior.
