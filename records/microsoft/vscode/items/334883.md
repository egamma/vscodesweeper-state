# Issue #334883 — Copilot Chat forked session posts tool-use events with the original sessionId

[https://github.com/microsoft/vscode/issues/334883](https://github.com/microsoft/vscode/issues/334883)

## Summary

Well-evidenced report: forking a Copilot Chat session gets a genuinely new sessionId in the UI/chat model (confirmed in chatForkActions.ts, which does `forkedData.sessionId = generateUuid()`), but the reporter's correlated logs show PostToolUse hook payloads for tool calls made in the fork still carry the original session's ID and transcript path — the hook/session-tracking layer in the Copilot Chat extension isn't picking up the new sessionId for the forked session.

## Change summary

After forking a Copilot Chat session, tool-use hook events (PostToolUse etc.) are still emitted with the original session's session_id/transcript_path instead of the forked session's own ID.

## Best solution

Trace how sessionId flows from the forked chat session down into extensions/copilot's toolCallingLoop.ts / defaultIntentRequestHandler.ts (which set `conversation.sessionId` from `request.sessionId`) and the SessionTranscriptService/hooks logger — likely a cached Conversation, transcript, or session-scoped service keyed off the original session that isn't refreshed when a new (forked) sessionId starts using the same underlying request stream.

## Evidence

- **core fork assigns new sessionId:** src/vs/workbench/contrib/chat/browser/actions/chatForkActions.ts sets `forkedData.sessionId = generateUuid();` before loading the forked session via `chatService.loadSessionFromData`, so the forked chat model does have its own distinct sessionId at the workbench level.
- **hook sessionId comes from conversation/request:** extensions/copilot/src/extension/prompt/node/defaultIntentRequestHandler.ts passes `this.conversation.sessionId` (derived from `this.request.sessionId` for main requests) into `chatHookService.executeHook(...)`, and toolCallingLoop.ts does the same for PreToolUse/PostToolUse hooks — so a mismatch implies the forked request/conversation object isn't carrying the new UUID through to the hook/transcript path.
- **reporter's correlated logs:** The issue includes matching toolCallId join across the original UI session file (2ddd5b6e-...), the forked UI session file (e14064d7-...), and the Hooks.log PostToolUse entries at 08:27:17 and 08:36:23 — both PostToolUse payloads show `session_id=2ddd5b6e-...` even though the second tool call (`call_iWeIUVS6...`) is only recorded in the forked session's jsonl.
