# Issue #237469 — Deleting a folder ending in a dot, actually deletes a different folder

[https://github.com/microsoft/vscode/issues/237469](https://github.com/microsoft/vscode/issues/237469)

## Summary

The Windows-specific data-loss path remains present on current main: Explorer forwards the selected trailing-dot URI into native deletion without checking whether Windows resolves it to a different sibling. The issue is already routed correctly and should remain open for a Windows-safe deletion design.

## Change summary

Deleting a Windows folder whose name ends in a dot can delete the distinct sibling whose name omits that dot.

## Best solution

Ensure every Windows deletion path fails safely or addresses the exact selected filesystem entry when its name contains a trailing dot or another Win32-ambiguous segment; it must never silently target the normalized sibling.

## Plan brief

- **Likely files:** `src/vs/platform/files/electron-main/diskFileSystemProviderServer.ts`, `src/vs/platform/files/node/diskFileSystemProvider.ts`, `src/vs/platform/files/test/node/diskFileSystemProvider.test.ts`
- **Validation:** On Windows, create sibling directories named `folder` and `folder.` through an extended-length or otherwise capable path API, delete `folder.` from the VS Code Explorer using both Recycle Bin and permanent-delete flows, and verify that `folder` and its contents remain untouched; add a provider-level regression test for the chosen handling of ambiguous paths.
- **Behavior:**

  > Selecting a filesystem entry whose Windows path ends in a dot must never delete the distinct normalized sibling. The same safety guarantee applies to Move to Recycle Bin, permanent deletion, and the fallback from a failed trash operation. The operation may either delete the exact selected entry or report that it cannot safely do so, but the undotted sibling and its contents must remain unchanged.
- **Trace:**

  > Explorer deletion starts in deleteFiles in src/vs/workbench/contrib/files/browser/fileActions.ts, which sends the selected ExplorerItem resource through ResourceFileEdit. FileService validates existence but not path identity before delegating to the provider. Trash deletion reaches DiskFileSystemProviderChannel.delete in src/vs/platform/files/electron-main/diskFileSystemProviderServer.ts, where resource.fsPath is normalized and passed to shell.trashItem; permanent deletion reaches DiskFileSystemProvider.delete in src/vs/platform/files/node/diskFileSystemProvider.ts and Promises.rm. Neither path guards a trailing-dot segment against Win32 normalization. Existing basename validation prevents creating such names through Explorer but cannot protect entries created by external tools. Keep ordinary valid-path deletion behavior and non-Windows behavior unchanged.
- **Open decisions:**
  - When a selected Windows entry has a Win32-ambiguous path, should VS Code support deleting the exact entry through an extended-path mechanism, or reject the operation with a clear safety error?

## Evidence

- **current Explorer flow:** src/vs/workbench/contrib/files/browser/fileActions.ts:214-219 constructs a ResourceFileEdit directly from the selected ExplorerItem resource and applies it without checking for Windows path aliasing.
- **current trash flow:** src/vs/platform/files/electron-main/diskFileSystemProviderServer.ts:41-53 normalizes resource.fsPath and passes it directly to Electron shell.trashItem; there is no trailing-dot or target-identity guard before the native Windows operation.
- **current permanent-delete flow:** src/vs/platform/files/node/diskFileSystemProvider.ts:653-687 converts the resource to a filesystem path and sends it to recursive removal without validating that the path identifies the selected entry rather than its Win32-normalized sibling.
- **existing validation boundary:** src/vs/base/common/extpath.ts:169-201 rejects Windows basenames ending in a dot, but that validation is used when creating or renaming Explorer items and is not applied to deletion of entries created externally.
- **related historical issue:** https://github.com/microsoft/vscode/issues/117426 fixed Explorer creation of trailing-dot names, but its discussion explicitly limited that validation to filenames being created; it does not cover deleting an externally created ambiguous path and is closed, so it is not a duplicate canonical.
- **platform confirmation pending:** https://github.com/microsoft/vscode/issues/237469#issuecomment-2583162029 records that a maintainer could not reproduce on macOS and still needed Windows verification, consistent with the Windows-only native path behavior.
