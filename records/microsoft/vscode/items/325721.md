# Issue #325721 — Agent host SSH: 'Update Server' is a silent no-op (or downgrades) while update API lags the desktop rollout — protocol-version deadlock with no recovery path

[https://github.com/microsoft/vscode/issues/325721](https://github.com/microsoft/vscode/issues/325721)

## Summary

The update-pointer deadlock and downgrade path remain in current source, although protocol compatibility and update notifications have changed since the report. Keep this open: the older mismatch report does not clearly own the additional downgrade behavior.

## Change summary

Agent-host updates must handle desktop/server rollout skew without leaving incompatible SSH sessions stranded or replacing a newer server with an older build.

## Best solution

Make CLI-managed recovery compatibility-aware and prevent rollout-pointer regression from downgrading the running host. Decide whether recovery should target a client-compatible build or explicitly explain that no compatible update is currently available.

## Plan brief

- **Likely files:** `cli/src/tunnels/agent_host.rs`, `src/vs/platform/agentHost/browser/agentHostProtocolClient.ts`, `src/vs/platform/agentHost/node/agentHostUpgradeChannel.ts`, `src/vs/platform/agentHost/common/state/protocolUpgrade.ts`, `src/vs/sessions/contrib/providers/remoteAgentHost/browser/remoteHostOptions.ts`
- **Validation:** Use controlled update-service responses to exercise two cases: an incompatible running server equal to api/latest, and a newer running server whose commit differs from the older api/latest release. Verify the first produces the agreed recovery or explicit unavailable-update result, the second never downgrades, and ordinary successful upgrades still restart and reconnect. Add supervisor and client/UI regression checks without relying on a live staged rollout.
- **Behavior:**

  > During desktop/server rollout skew, an incompatible SSH agent host must not present a no-op update as resolution of the connection failure. Recovery must either establish a compatible connection or clearly explain that a compatible update is unavailable. A manually installed newer server must not be downgraded because the update pointer still selects an older release. Normal compatible connections and successful upgrades must retain their existing behavior.
- **Trace:**

  > AgentHostManager::get_latest_release in cli/src/tunnels/agent_host.rs resolves the update-service pointer, and handle_upgrade_request compares commit inequality rather than release ordering or compatibility. The same-commit branch reports no update; the different-commit branch downloads and restarts even when the selected release is older. AgentHostProtocolClient.triggerVscodeUpgrade sends empty parameters, and requestAgentHostUpgrade forwards a bodyless management request, so the supervisor receives no client target. runServerUpgrade in remoteHostOptions.ts now displays an 'already on the latest version' notification, but that does not resolve incompatibility. Current protocol negotiation supports multiple baselines, so the original single-version symptom must be distinguished from the still-present supervisor defect. Preserve third-party-host interoperability, normal upgrade/reconnect behavior, and the test-only initial-version override; stale endpoint-registry reuse is separate work described in https://github.com/microsoft/vscode/issues/333175 and https://github.com/microsoft/vscode/issues/334296.
- **Open decisions:**
  - When the update pointer offers no compatible server, should Update Server request the desktop client's specific build, or report that a compatible update is unavailable and require a later retry?

## Evidence

- **Current update resolution:** cli/src/tunnels/agent_host.rs:643-694, AgentHostManager::get_latest_release, still resolves updates through get_latest_commit for the configured server platform and quality. The initial commit override applies only on the first lookup; subsequent upgrade requests resolve the update-service pointer.
- **Confirmed no-op and downgrade branches:** cli/src/tunnels/agent_host.rs:884-1009, handle_upgrade_request, treats running_commit != new_release.commit as upgrade_needed. If the lagging pointer equals the incompatible running build, it returns upgradeNeeded:false; if the pointer identifies an older, different build, it downloads that build and schedules kill/restart without a release-order or client-compatibility check.
