# Issue #325721 — Agent host SSH: 'Update Server' is a silent no-op (or downgrades) while update API lags the desktop rollout — protocol-version deadlock with no recovery path

[https://github.com/microsoft/vscode/issues/325721](https://github.com/microsoft/vscode/issues/325721)

## Summary

Well-diagnosed, source-confirmed bug: the CLI's upgrade endpoint compares running commit against the update API's latest commit, but during staged rollout the API lags the desktop auto-update, so the upgrade is a no-op (or downgrade). No fix has landed on main. The issue should be routed to the agent host area.

## Change summary

When the desktop client auto-updates ahead of the update API, the remote agent host's 'Update Server' button silently does nothing because the CLI resolves 'latest' from the lagging API, finds running == latest, and returns upgradeNeeded: false.

## Best solution

The client should pass its own commit hash as a desired target in the `_vscodeUpgrade` RPC (the plumbing for commit-pinned downloads already exists via `VSCODE_CLI_INITIAL_AH_VERSION`). The CLI's `handle_upgrade_request` in `cli/src/tunnels/agent_host.rs` would then use the client-supplied commit when `api/latest` matches the running version, breaking the deadlock. As a secondary defense, the upgrade check at line 723–724 should be `running < latest` (or semver-aware), not `running != latest`, to prevent downgrades.
