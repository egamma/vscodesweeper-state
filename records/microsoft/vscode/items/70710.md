# Issue #70710 — Custom Variables Support In Workspace Settings

[https://github.com/microsoft/vscode/issues/70710](https://github.com/microsoft/vscode/issues/70710)

## Summary

Custom reusable values across workspace settings remain unsupported, including the reported color-customization example. Keep this accepted Backlog request open: the older related issues do not establish a full-scope duplicate, and the closest general custom-variable request is newer.

## Change summary

Allow workspace-defined custom variables to be referenced from other settings, including theme colors and shared project paths.

## Best solution

Define a consistent contract for reusable workspace values and their substitution in supported settings, coordinated with the existing variable-resolution and theme-color requests. Settle whether substitution is general or explicitly enabled per setting before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/services/configurationResolver/common/configurationResolver.ts`, `src/vs/workbench/services/configurationResolver/common/variableResolver.ts`, `src/vs/workbench/services/themes/common/themeConfiguration.ts`, `src/vs/workbench/services/themes/common/colorThemeData.ts`, `src/vs/workbench/services/configurationResolver/test/electron-browser/configurationResolverService.test.ts`
- **Validation:** After the contract is agreed, add targeted resolver and theme tests verifying reusable workspace values, nested project-path references, workspace overrides, and explicit handling of missing or cyclic references. Verify in a VS Code window that changing one palette value updates its referencing theme-specific color settings; literal settings and existing task/terminal variable resolution must remain unchanged.
- **Behavior:**

  > Users want to define reusable workspace values once and reference them from other settings. The original acceptance case is a custom palette value used by a theme-specific tab.activeBackground override; the discussion additionally requires shared project-path values derived from existing variables. The agreed supported settings must resolve these references consistently and reflect changes to the defining value. Existing literal configuration and task/terminal variable behavior must remain compatible.
- **Trace:**

  > ThemeConfiguration.colorCustomizations reads raw configuration, and ColorThemeData.setCustomColors/overwriteCustomColors interprets strings as hexadecimal colors without invoking a resolver. AbstractVariableResolverService in src/vs/workbench/services/configurationResolver/common/variableResolver.ts already supports explicit ${config:...} resolution, including nested references covered by configurationResolverService.test.ts, but this capability is consumer-invoked rather than universal. Terminal consumers demonstrate existing opt-in use; they do not establish coverage for colors or arbitrary extension settings. The configuration service's synchronous raw-value contract is documented in https://github.com/microsoft/vscode/issues/2809#issuecomment-276606084 and must not be changed incidentally. Coordinate the design with https://github.com/microsoft/vscode/issues/2809, https://github.com/microsoft/vscode/issues/56855, and https://github.com/microsoft/vscode/issues/242153 without treating their differing scopes as proven duplicates. The trace establishes the missing color path, but does not enumerate all configuration consumers; the uncertainty starts at the intended public substitution contract.
- **Open decisions:**
  - Should custom-value substitution apply to all settings, including extension settings, or only settings that explicitly opt in?
  - Should reusable values use existing ${config:...} references to ordinary settings, or expose a dedicated workspace custom-variable namespace as requested?
  - Should settings references permit editor-dependent or interactive variables such as ${fileDirname} and task inputs, or remain limited to non-interactive configuration and workspace values?
