# Issue #70710 — Custom Variables Support In Workspace Settings

[https://github.com/microsoft/vscode/issues/70710](https://github.com/microsoft/vscode/issues/70710)

## Summary

Custom variables still do not work across workspace settings, including the reported color-customization example. Existing related issues cover narrower or different capabilities, so this accepted Backlog request should remain open while its configuration contract is designed.

## Change summary

Allow workspace-defined custom variables to be reused in settings values, including theme colors and shared project paths.

## Best solution

Define a consistent contract for reusable workspace values, coordinated with the existing settings-substitution and theme-variable requests. Decide the supported consumers and resolution semantics before implementing a cross-cutting configuration capability.

## Plan brief

- **Likely files:** `src/vs/workbench/services/configurationResolver/common/variableResolver.ts`, `src/vs/workbench/services/configurationResolver/common/configurationResolver.ts`, `src/vs/workbench/services/themes/common/themeConfiguration.ts`, `src/vs/workbench/services/themes/common/colorThemeData.ts`
- **Validation:** After agreeing the supported syntax and consumers, verify that one workspace-defined color controls a theme-specific tab.activeBackground and updates when its definition changes; verify reuse of a project-root value in the agreed path settings. Add executable tests for resolution, workspace precedence, and missing or cyclic references, while preserving existing literal-color and task/debug variable behavior.
- **Behavior:**

  > Users want to define reusable values once in workspace settings and reference them from other settings. The original example reuses a named color in a theme-specific tab background; later comments require shared project-path definitions that avoid repeating relative paths. Existing consumer-specific variable support does not satisfy general reuse. Acceptance must cover the agreed color and path consumers, updates to referenced values, and predictable handling of invalid references.
- **Trace:**

  > ThemeConfiguration.colorCustomizations in src/vs/workbench/services/themes/common/themeConfiguration.ts reads raw configuration values. ColorThemeData.setCustomColors and overwriteCustomColors in src/vs/workbench/services/themes/common/colorThemeData.ts interpret string overrides as hexadecimal colors without custom-variable substitution. AbstractVariableResolverService.resolveAsync and its config branch in src/vs/workbench/services/configurationResolver/common/variableResolver.ts provide explicit consumer-driven resolution, not a general settings contract. Related design work is tracked at https://github.com/microsoft/vscode/issues/2809 and https://github.com/microsoft/vscode/issues/56855; the former focuses on settings substitution and the latter on theme variables. https://github.com/microsoft/vscode/issues/242153 requests broader custom-setting references but is newer than this report. Preserve existing literal colors, theme-specific override precedence, synchronous configuration access, and task/debug substitution behavior; uncertainty begins at the intended public syntax, consumer scope, and dependency-resolution semantics.
- **Open decisions:**
  - Should reusable workspace values be supported across all settings, including extension settings, or only explicitly opted-in consumers?
  - Should users declare a dedicated custom-variable namespace as proposed here, or reference ordinary configuration values through existing ${config:...} syntax?
  - Which contextual variables may reusable definitions contain, and what user-visible behavior should apply when references are missing, cyclic, or depend on the active editor?
