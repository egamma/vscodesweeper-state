# Issue #234941 — Git - Built-in Git extension does not respect `includeIf` in a symbolic link directory

[https://github.com/microsoft/vscode/issues/234941](https://github.com/microsoft/vscode/issues/234941)

## Summary

Source tracing does not show a VS Code-side deviation: the extension runs git with the symlinked repository root as cwd and never sets GIT_DIR, so gitdir discovery is identical to a terminal; the only difference at commit time is `-c user.useConfigOnly=true`, which disables git's identity guessing — meaning the terminal commit may have succeeded with a guessed identity rather than the includeIf one. Asking the reporter to confirm on a current build and show whether the includeIf identity actually applies in a terminal inside the symlinked folder.

## Change summary

Committing from the Source Control view fails with "Author identity unknown" in a repository opened through a symbolic link whose `includeIf "gitdir:**/<link>/"` section supplies user.name/user.email.

## Best solution

Establish first whether git itself resolves the includeIf for the symlinked path (terminal `git config --show-origin --get user.email` inside the link); if it does not, this is git's own physical-cwd gitdir resolution and the pattern should target the real path, and only if it does should the extension's commit invocation (extensions/git/src/git.ts) be adjusted to preserve the symlinked gitdir.

## Evidence

- **no VS Code-side path rewrite for git invocations:** extensions/git/src/git.ts `Repository.exec`/`stream` pass `this.repositoryRoot` as cwd, and `Git.spawn` only sets `options.cwd = sanitizePath(cwd)`; `rg` for `GIT_DIR`/`GIT_WORK_TREE`/`--git-dir`/`-C` in extensions/git/src finds only the `rev-parse --git-dir --git-common-dir` read (git.ts:569). The extension therefore lets git discover the gitdir from the cwd, as a terminal does.
- **symlinked root is deliberately preserved:** extensions/git/src/git.ts:510-525 `getRepositoryRoot` falls back to `rev-parse --path-format=relative --show-toplevel` specifically so the symlinked path survives; the issue log confirms this worked — `[Model][openRepository] Opened repository: /home/nexus/git-includeIf-ln`. The existence of this workaround is also evidence that plain `--show-toplevel` returns the physical path, i.e. git resolves the symlink itself.
- **the real difference at commit time:** extensions/git/src/git.ts:2136-2139 prepends `-c user.useConfigOnly=true` when `git.requireGitUserConfig` is on, which stops git from guessing an identity. The reported terminal `git commit` ran without that flag, so its success does not by itself prove the includeIf section was applied — which is the missing piece of evidence.
- **reproduction not attempted:** Execution of a scratch git reproduction was not available in this environment, and the checkout must stay clean, so the includeIf/symlink matching behaviour could not be observed directly; no commenter has confirmed it either.
