# Issue #297777 — `provideChatSessionProviderOptions` only called once per window?

[https://github.com/microsoft/vscode/issues/297777](https://github.com/microsoft/vscode/issues/297777)

## Summary

Keep open for the remaining API ownership decision: the reporter confirmed the refresh workaround, but the discussion also requests core-managed inheritance of session options. The linked provider fix addresses refresh notifications, not that broader contract, and this team-authored issue should not receive a judgment close.

## Change summary

Let new chat sessions inherit the last selected permission mode and folder while preserving existing sessions' own selections.

## Best solution

Have the chat-session API owners determine whether the current per-session input-state API adequately replaces the requested persistence behavior or whether an explicit core-managed inheritance contract is still needed. Preserve existing sessions' selections and distinguish provider-managed defaults from automatic cross-session persistence.

- **Behavior:**

  > The reported workflow changes a Claude session's permission mode, sends a message, and creates a new session, where the choice unexpectedly returns to the provider default. The reporter wants new sessions to start with the last-used permission mode and folder without changing values already associated with existing sessions. The event-based workaround was confirmed to work. Acceptance for any further API work must distinguish inherited options from deliberately reset options and preserve existing-session state.
- **Trace:**

  > The legacy provideChatSessionProviderOptions contract is explicitly once-at-registration, with subsequent refreshes driven by onDidChangeChatSessionProviderOptions in src/vs/workbench/api/browser/mainThreadChatSessions.ts. https://github.com/microsoft/vscode-copilot-chat/pull/4015 added that notification to Claude option changes and references this issue, but does not establish a general persistence policy. Current main also has controller.getChatSessionInputState, reached through MainThreadChatSessionItemController.getNewChatSessionInputState and ExtHostChatSessions.$provideChatSessionInputState; the chat-sessions service requests this state for new sessions or falls back to cached type-level groups. The inspected proposed option-group API exposes selected values but no explicit cross-session inheritance declaration. The uncertainty is whether provider-managed initialization now sufficiently meets the request or whether core should own inheritance. Do not change the legacy callback lifecycle or overwrite established session values without an API-owner decision.
- **Open decisions:**
  - Should inheritance remain provider-managed through getChatSessionInputState, or should core expose and honor an explicit per-option inherit-versus-reset contract?
  - If core owns inheritance, should last-used values apply only within the current window, or persist across window reloads, and at what workspace scope?
