# Issue #131031 — Improve discoverability of available/installable output renderers for given mime types

[https://github.com/microsoft/vscode/issues/131031](https://github.com/microsoft/vscode/issues/131031)

## Summary

Current source provides renderer selection and Marketplace entry points, but still hides renderer information behind the output overflow menu when an available renderer is selected. Keep this design exploration open: the existing capabilities only partially address its two scenarios, and the older related selector issue does not cover the full request.

## Change summary

Make missing, available, and currently selected notebook output renderers easier to discover for each output.

## Best solution

Complete the notebook-output design decision for contextual renderer identification and missing-renderer discovery, reusing the existing presentation picker and Marketplace paths. Preserve compact single-line outputs and make the relationship between each output and its renderer clear without adding unnecessary permanent chrome.

- **Behavior:**

  > Users should be able to discover which renderer presents a notebook output and find available or installable alternatives without guessing that the overflow menu contains presentation controls. Missing-renderer discovery should remain meaningful when another presentation can render the output. Acceptance should cover unsupported-only output, rich output with a text fallback, unexpected selected renderers, multiple outputs, and compact single-line output. The precise visible affordance and conditions for showing a warning remain to be agreed with the maintainer.
- **Trace:**

  > CellOutputElement in src/vs/workbench/contrib/notebook/browser/view/cellParts/cellOutput.ts owns the per-output toolbar, missing-renderer message, presentation quick pick, and installation entry points. _attachToolbar places Change Presentation in secondary actions; _generateRendererInfo exposes renderer identity only inside the picker. CellOutputViewModel.resolveMimeTypes in src/vs/workbench/contrib/notebook/browser/viewModel/cellOutputViewModel.ts prefers an available trusted renderer, so a working fallback can avoid the missing-renderer message while alternatives remain unavailable. Existing configuration in notebook.contribution.ts changes MIME priority and output-action consolidation, not renderer discoverability. Preserve renderer preference, trust filtering, rendering behavior, and existing switching/install paths; this is a discovery-design task, not a renderer-selection algorithm change. https://github.com/microsoft/vscode/issues/126610 is related selector-discoverability work but does not absorb the full scope. The supplied discussion leaves the compact-output layout and visibility policy unsettled.
- **Open decisions:**
  - Should an unavailable richer presentation produce a warning when a supported fallback already renders the output, and which unavailable alternatives warrant that warning?
  - Should renderer identity and discovery appear as a per-output toolbar indicator, a labeled presentation control, or a status item, and how should the chosen affordance remain usable for single-line and multiple outputs?
