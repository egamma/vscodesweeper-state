# Issue #3742 — Add setting to automatically hide the side bar

[https://github.com/microsoft/vscode/issues/3742](https://github.com/microsoft/vscode/issues/3742)

## Summary

Keep this accepted, strongly supported request open: the inspected built-in controls offer manual visibility changes, not timed sidebar hiding or hover-revealed overlays. A maintainer-led design session should distinguish the original configurable-delay request from the floating, non-reflowing sidebar behavior requested throughout the discussion.

## Change summary

Provide an optional mode that automatically hides the primary sidebar, originally after a configurable duration, with discussion requesting hover reveal and overlay presentation.

## Best solution

Define an opt-in primary-sidebar auto-hide interaction that preserves predictable keyboard access and the existing pinned layout by default. Decide whether timed dismissal alone satisfies the request or whether transient overlay presentation without editor reflow is part of the intended capability.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/workbench.contribution.ts`, `src/vs/workbench/browser/layout.ts`, `src/vs/workbench/browser/parts/sidebar/sidebarPart.ts`, `src/vs/workbench/browser/actions/layoutActions.ts`
- **Validation:** After the interaction contract is chosen, manually check Explorer and Source Control in normal and side-by-side diff editors: enable the mode, reveal the sidebar, exercise the selected dismissal trigger and configured delay, and verify the agreed editor-reflow behavior. Check keyboard reveal, Escape/focus handling, uninterrupted interaction inside the sidebar, and unchanged Ctrl/Cmd+B behavior with the option disabled.
- **Behavior:**

  > Users want the primary sidebar available when needed without permanently consuming editor space or requiring repeated manual toggles. The original request specifies automatic hiding after a configurable duration; later discussion requests hover reveal, dismissal on leaving or clicking away, and floating presentation without shifting editor content. Acceptance must cover the chosen reveal and dismissal contract, continued keyboard access, and predictable behavior while interacting with sidebar controls. Existing pinned-sidebar behavior should remain the default.
- **Trace:**

  > ToggleSidebarVisibilityAction in src/vs/workbench/browser/actions/layoutActions.ts calls IWorkbenchLayoutService.setPartHidden for Parts.SIDEBAR_PART. Layout.setSideBarHidden in src/vs/workbench/browser/layout.ts updates persisted runtime visibility, changes workbench-grid visibility, and handles pane-composite focus and reopening. The auto-hide logic in SidebarPart and the configuration registration in workbench.contribution.ts instead concern hiding top/bottom Activity Bars based on view-container counts. These inspected capabilities do not provide the requested timed or transient-overlay sidebar interaction. The uncertainty begins at the product contract: timed hiding and a non-reflowing overlay are different experiences, and the supplied discussion does not settle which should ship. Preserve default layout, existing visibility commands, and accessible focus behavior; do not assume that related Activity Bar or terminal requests are included. Related work is discussed at https://github.com/microsoft/vscode/issues/96063 and https://github.com/microsoft/vscode/issues/10952, neither of which replaces this issue.
- **Open decisions:**
  - Should this feature deliver configurable-delay hiding within the existing grid layout, or also provide transient overlay presentation that leaves editor geometry unchanged?
  - What should trigger dismissal and restart the configured delay: sidebar inactivity, pointer departure, or focus moving back to the editor?
  - Should the hidden sidebar reveal only through existing commands and Activity Bar clicks, or also through pointer hover at the Activity Bar or window edge?
