# Issue #294640 — Feature Request: Add Optional "response_structure" Field to .agent.md Files (Custom Agents)

[https://github.com/microsoft/vscode/issues/294640](https://github.com/microsoft/vscode/issues/294640)

## Summary

This is a valid, currently unimplemented custom-agent contract request that should be routed to the chat customization owners. The older structured-handoff issue is related but does not cover provider-enforced output schemas for every custom-agent response, so the stronger re-review duplicate bar is not met.

## Change summary

Allow a custom agent to declare a machine-readable response schema in `.agent.md` frontmatter and have compatible model requests enforce it.

## Best solution

Define a provider-neutral JSON Schema contract for custom-agent responses, validate it in `.agent.md` tooling, and propagate it to model providers that support constrained output. The contract must explicitly define which invocation surfaces honor it and what users see when the selected provider cannot enforce it.

- **Validation:** Extend the prompt-syntax unit suites to validate and preserve a nested response schema, then add a request-construction test proving that a compatible custom-agent invocation carries the declared schema while an agent without it remains unchanged.
- **Behavior:**

  > A custom agent can optionally declare a machine-readable response contract in its `.agent.md` frontmatter. On invocation through a supported model provider, generated output is constrained to that contract rather than relying only on body instructions. Agents without the field retain current behavior, and unsupported-provider handling is explicit rather than silently claiming enforcement.
- **Trace:**

  > The recognized frontmatter keys originate in PromptHeaderAttributes and customAgentAttributes under src/vs/workbench/contrib/chat/common/promptSyntax; the requested key is absent. promptsServiceImpl.ts resolves only model, tools, handoffs, argument hints, agents, hooks, and body instructions into ICustomAgent, so no schema reaches request construction. The Copilot request layer already handles provider request options and recognizes `response_format`, but capability and request-shape differences across providers remain unresolved. The body-based “Output Format” convention must remain available and agents without a schema must not change. https://github.com/microsoft/vscode/issues/288719 concerns structured handoff context and is related design input, not a canonical duplicate.
- **Open decisions:**
  - Should the response contract apply to user-visible custom-agent turns, subagent return values, or both?
  - Which public schema syntax and name should `.agent.md` standardize: a provider-neutral JSON Schema contract or a provider-shaped `response_format` field?
  - When the selected model or provider cannot enforce the schema, should invocation fail visibly, continue with a warning and prompt-only guidance, or make the agent unavailable?
