# Issue #317845 — GitHub Copilot stopping GPT and resubmitting prompt shows ongoing mid-response output from previous submission.

[https://github.com/microsoft/vscode/issues/317845](https://github.com/microsoft/vscode/issues/317845)

## Summary

The cancellation/resubmission race remains plausible on current main: resend cancels the active request but immediately starts its replacement without waiting for the prior response to settle. The accepted On Deck bug should remain open for diagnosis rather than being folded into related issues with different observable symptoms.

## Change summary

Stopping a streaming GPT response and editing/resubmitting its prompt can make the replacement response continue the cancelled output mid-sentence instead of starting over.

## Best solution

Ensure an edited prompt resend cannot reuse or receive residual state or output from the cancelled turn, covering both the local request lifecycle and any provider timeline/session restoration involved in GPT requests.

- **Behavior:**

  > After the user stops a streaming response, edits that prompt, and resubmits it, the replacement response must start from the beginning as a new invocation. Output from the cancelled invocation must never be appended to or resumed in the replacement response, even when cancellation acknowledgment is delayed. Other retry, queue, and ordinary cancellation behavior must remain unchanged.
- **Trace:**

  > The edit/retry path reaches `ChatService.resendRequest` in src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts through resend actions such as src/vs/workbench/contrib/chat/browser/actions/chatTitleActions.ts. `resendRequest` calls `CancellableRequest.cancel()` and then immediately invokes `_sendRequestAsync`, while `cancelCurrentRequestForSession` separately demonstrates an established bounded wait for `responseCompletePromise`; this leaves overlapping old/new request lifetimes on the resend path. A maintainer also suspected uncleared request state during timeline restoration in https://github.com/microsoft/vscode/issues/317845#issuecomment-2962177345. The investigation must determine whether residual output is admitted by core progress handling or by the provider-backed timeline/session path before choosing the ownership boundary. Do not broaden the work to unrelated Stop-button failures or Working-state stalls tracked by https://github.com/microsoft/vscode/issues/284678 and https://github.com/microsoft/vscode/issues/285951.

## Evidence
