# Issue #333975 — Microsoft Authentication loses Settings Sync session after macOS sleep/network interruption; restarting extension host restores valid session

[https://github.com/microsoft/vscode/issues/333975](https://github.com/microsoft/vscode/issues/333975)

## Summary

Keep open: current source still collapses transient token acquisition failures into an empty session result, leaving Settings Sync unavailable without automatic recovery. The maintainer explicitly designated this issue for the authentication-layer fix; the newer Settings Sync mitigation issue does not replace it.

## Change summary

Recover Settings Sync after transient Microsoft authentication failures without requiring interactive sign-in or an extension-host restart.

## Best solution

Establish authentication-layer semantics that distinguish temporary token acquisition failures from genuinely absent or invalid sessions, allowing consumers to recover without treating a network interruption as sign-out. Coordinate the consumer recovery behavior with the separate Settings Sync mitigation decision in https://github.com/microsoft/vscode/issues/336860.

## Plan brief

- **Likely files:** `extensions/microsoft-authentication/src/node/authProvider.ts`, `src/vs/workbench/services/authentication/common/authentication.ts`, `src/vs/workbench/services/authentication/browser/authenticationService.ts`, `src/vs/workbench/api/browser/mainThreadAuthentication.ts`, `src/vs/workbench/api/common/extHostAuthentication.ts`, `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/services/userDataSync/browser/userDataSyncWorkbenchService.ts`
- **Validation:** Add automated coverage that starts with a valid persisted Microsoft session, injects an MSAL network_error during a scoped lookup, restores successful token acquisition, and verifies recovery without interactive authentication or provider restart. Cover genuinely absent, revoked and interaction-required sessions separately, and retain the reported unplugged macOS sleep/resume sequence as a manual acceptance check.
- **Behavior:**

  > An established Microsoft Settings Sync account must not become permanently stuck behind a sign-in prompt because silent token acquisition temporarily fails during sleep or network interruption. Consumers must be able to distinguish temporary authentication unavailability from an absent or invalid session, and recover when token acquisition succeeds again without interactive login or an extension-host restart. Acceptance checks must exercise transient failure followed by recovery and separately verify that genuinely revoked or interaction-required sessions still receive appropriate handling.
- **Trace:**

  > In extensions/microsoft-authentication/src/node/authProvider.ts, getAllSessionsForPca catches acquireTokenSilent failures indiscriminately and skips the affected account; it does not delete the cached account. The session-array result crosses MainThreadAuthenticationProvider.getSessions and AuthenticationService.getSessions unchanged. UserDataSyncWorkbenchService.updateCurrentAccount clears _current when that array lacks the persisted session ID, and update marks the account unavailable; initialize registers provider-change recovery but no connectivity-driven retry. This path is visible in current source and independently confirmed at https://github.com/microsoft/vscode/issues/333975#issuecomment-5737246720. The maintainer chose this issue for the authentication-layer fix and opened https://github.com/microsoft/vscode/issues/336860 for a separate consumer mitigation decision. Preserve genuine sign-out, revocation and interaction-required behavior, and do not expose an unusable token as though authentication succeeded. The unresolved boundary is how temporary failure is represented to consumers and what recovery behavior that representation guarantees.
- **Open decisions:**
  - What consumer-visible contract should distinguish temporary token acquisition failure from absent, revoked or interaction-required sessions, and does that contract extend to public authentication providers?
  - Should the authentication layer guarantee automatic recovery notification after connectivity returns, or should consumers retry after receiving an explicit temporary-unavailability result?
