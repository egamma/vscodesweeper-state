# Issue #178850 — Some way to provide an enum of suggested values, but still allow any value

[https://github.com/microsoft/vscode/issues/178850](https://github.com/microsoft/vscode/issues/178850)

## Summary

Keep open: the Settings editor still lacks a general way to offer suggested string values while accepting arbitrary input. This is an accepted, team-authored request, and the related custom-value issue was explicitly consolidated into this one.

## Change summary

Allow setting authors to provide suggested string values without restricting users to those values, including editing through the Settings editor.

## Best solution

Provide a consistent Settings editor control and configuration-schema contract for suggested-but-unrestricted strings, while preserving strict enum validation for existing settings. Settle the schema representation and custom-entry interaction before implementation.

- **Validation:** Add targeted settings model and renderer tests for the agreed schema contract: suggested values appear, an unlisted string can be entered and persisted, reopening preserves that string, and existing strict enums remain unchanged. Manually verify selection and arbitrary entry in the Settings editor and corresponding settings.json validation.
- **Behavior:**

  > A setting author can supply named string suggestions while allowing users to enter other strings. The Settings editor must expose the suggestions and permit an arbitrary value without requiring a switch to settings.json. Selecting a suggestion and entering a custom value must both persist correctly and survive reopening the editor. Existing settings declared as strict enums must retain their current restrictions.
- **Trace:**

  > The reported schema combines an unrestricted string and a string enum through anyOf. In src/vs/workbench/services/preferences/common/preferencesModels.ts, the settings model retains top-level type and enum information but does not derive suggestions from those alternatives. SettingsTreeSettingElement.initSettingValueType in src/vs/workbench/contrib/preferences/browser/settingsTreeModels.ts consequently classifies that shape as Complex; the enum renderer in src/vs/workbench/contrib/preferences/browser/settingsTree.ts offers only indexed select-box options. IJSONSchema in src/vs/base/common/jsonSchema.ts has examples and defaultSnippets, but the inspected editor path does not use them to provide unrestricted suggested-value editing. The remaining uncertainty is the author-facing schema contract and whether users receive an editable suggestion control or a separate custom-value entry. Preserve existing strict enums and unrelated object/array editing. https://github.com/microsoft/vscode/issues/183601 was explicitly folded into this request; https://github.com/microsoft/vscode/issues/128355 is a related font-specific consumer rather than a broader canonical.
- **Open decisions:**
  - Should setting authors express unrestricted suggestions through the existing anyOf shape, a supported examples annotation, or a dedicated configuration-schema property?
  - Should users enter arbitrary values directly in an editable suggestion control, or select an Other/custom option that exposes a separate text field?
