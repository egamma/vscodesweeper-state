# Issue #172056 — "Change All Occurrences" cursors get out of sync if one is moved with mouse

[https://github.com/microsoft/vscode/issues/172056](https://github.com/microsoft/vscode/issues/172056)

## Summary

The inconsistent cursor state remains source-reproducible on current main and was explicitly triaged as a bug with a reproduction video by a team member. An older identical report was closed as designed, so the intended mouse behavior needs a maintainer decision before implementation.

## Change summary

Clicking inside the primary selection after Change All Occurrences collapses only that selection while leaving the other occurrences selected, causing the next edit to affect them differently.

## Best solution

Define consistent mouse-click semantics for a multi-selection created by Change All Occurrences—either move every cursor to the corresponding offset or leave multi-cursor mode—and cover the chosen behavior without changing ordinary selection drag-and-drop.

## Plan brief

- **Likely files:** `src/vs/editor/contrib/dnd/browser/dnd.ts`, `src/vs/editor/browser/controller/mouseHandler.ts`, `src/vs/editor/test/browser/controller/cursor.test.ts`
- **Validation:** Add an editor interaction test that creates multiple selected occurrences, clicks inside the primary selection without dragging, and verifies that the resulting selections follow the chosen consistent semantics before Backspace; retain coverage for normal single-selection drag-and-drop.
- **Behavior:**

  > After Change All Occurrences creates multiple selections, clicking inside the primary occurrence must not leave one collapsed cursor alongside fully selected secondary occurrences. The next Backspace or typed character must affect occurrences consistently according to the chosen mouse semantics. Ordinary single-selection clicks and text drag-and-drop must remain unchanged.
- **Trace:**

  > MouseDownOperation.start in src/vs/editor/browser/controller/mouseHandler.ts treats a click inside the primary selection as a possible drag-and-drop operation. When no drag occurs, DragAndDropController._onEditorMouseDrop in src/vs/editor/contrib/dnd/browser/dnd.ts maps all selections, collapsing only the one containing the absolute clicked position and preserving the others. DeleteLeft then consumes those mixed selections in src/vs/editor/browser/coreCommands.ts. This source path matches the team-posted reproduction at https://github.com/microsoft/vscode/issues/172056#issuecomment-1845418869. The boundary is the no-drag click on a multi-selection; actual dragging and ordinary single-selection behavior must not change. The uncertainty begins with the intended outcome because https://github.com/microsoft/vscode/issues/85891 previously called the same behavior designed, while this newer report was explicitly labeled a bug.
- **Open decisions:**
  - Should clicking inside one selected occurrence move every cursor to the equivalent relative offset, or should it end the multi-cursor selection and retain only the clicked cursor?
  - Should the chosen behavior apply to every multi-selection or only selections created by Change All Occurrences?

## Evidence

- **source trace:** In src/vs/editor/browser/controller/mouseHandler.ts, clicking inside the primary selection enters the drag-and-drop path. DragAndDropController._onEditorMouseDrop in src/vs/editor/contrib/dnd/browser/dnd.ts maps all selections, collapses only selections containing the clicked position, and returns every other selection unchanged.
- **edit consequence:** CoreEditingCommands.DeleteLeft in src/vs/editor/browser/coreCommands.ts applies deletion operations to every remaining cursor selection, so the collapsed primary cursor deletes one character while the unchanged secondary selections are deleted in full.
- **team confirmation:** A VS Code team member applied the bug and editor-multicursor labels and posted a reproduction video on 2023-12-07: https://github.com/microsoft/vscode/issues/172056#issuecomment-1845418869.
- **prior design decision:** The same interaction was previously reported in https://github.com/microsoft/vscode/issues/85891 and closed as *as-designed in 2019, but the newer team bug classification indicates that precedent should not automatically close this report.
