# Issue #172056 — "Change All Occurrences" cursors get out of sync if one is moved with mouse

[https://github.com/microsoft/vscode/issues/172056](https://github.com/microsoft/vscode/issues/172056)

## Summary

The inconsistent edit remains explainable on current main: a no-drag click inside the primary selection collapses only that selection while preserving the other occurrence selections. The issue should remain open because a maintainer subsequently reproduced and classified this exact report as a multicursor bug.

## Change summary

After Change All Occurrences, clicking within the primary occurrence leaves the other occurrences fully selected, so the next edit applies different operations at different cursors.

## Best solution

Ensure that a no-drag click after Change All Occurrences cannot leave selection ranges out of sync: either move every occurrence cursor to the corresponding offset or end the multi-occurrence operation and retain only the clicked cursor. The editor owner should first choose which behavior should also apply to ordinary multicursor selections.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/mouseHandler.ts`, `src/vs/editor/contrib/dnd/browser/dnd.ts`
- **Validation:** Using an editor containing two occurrences of the same word, run Change All Occurrences, click in the middle of the primary occurrence without dragging, and press Backspace; verify that the edit is no longer applied as one collapsed deletion plus one full-selection deletion, while ordinary text drag-and-drop still works.
- **Behavior:**

  > After Change All Occurrences selects multiple matches, clicking within the primary match and editing must not apply structurally different edits to the occurrences. The click should either place all occurrence cursors at corresponding offsets or explicitly leave occurrence-editing mode with only the clicked cursor active. Keyboard cursor movement and actual selection drag-and-drop must remain unchanged.
- **Trace:**

  > MouseDownOperation.start in src/vs/editor/browser/controller/mouseHandler.ts enters the potential drag-and-drop path whenever a single click lands inside the non-empty primary selection. If no drag occurs, it emits a mouse-drop event. DragAndDropController._onEditorMouseDrop in src/vs/editor/contrib/dnd/browser/dnd.ts then collapses only selections containing the clicked absolute position and preserves all others, producing the reported mismatch. The normal ViewController.moveTo path instead replaces the cursor state with one selection, but this click never reaches that path. Preserve actual drag-and-drop behavior and decide explicitly whether the corrected no-drag behavior is specific to occurrence selections or applies to all multicursor selections. The same symptom was previously discussed at https://github.com/microsoft/vscode/issues/85891.
- **Open decisions:**
  - Should a click within one Change All Occurrences selection move every occurrence cursor to the corresponding character offset, or should it end the multi-occurrence operation and keep only the clicked cursor?
  - Should the chosen no-drag click behavior apply to all multiple selections, or only selections created by Change All Occurrences?

## Evidence

- **source trace:** In src/vs/editor/browser/controller/mouseHandler.ts, MouseDownOperation.start treats a single click inside the non-empty primary selection as a potential drag-and-drop operation; releasing without dragging emits onMouseDrop rather than dispatching the normal MoveTo command.
- **root cause:** In src/vs/editor/contrib/dnd/browser/dnd.ts, DragAndDropController._onEditorMouseDrop handles the no-drag path by mapping all selections, collapsing only selections that contain the clicked absolute position and returning every other selection unchanged. Occurrence selections at other locations therefore remain fully selected.
- **maintainer confirmation:** A VS Code member applied the bug and editor-multicursor labels and posted a reproduction recording on 2023-12-07: https://github.com/microsoft/vscode/issues/172056#issuecomment-1845418869.
- **older precedent:** https://github.com/microsoft/vscode/issues/85891 reported the same behavior and was closed as designed in 2019, but its final reporter comment identified this exact inconsistent-selection result; the later member triage of the current issue as a bug is stronger current evidence than that older disposition.
- **canonical search:** The open keyword candidates https://github.com/microsoft/vscode/issues/294262 and https://github.com/microsoft/vscode/issues/43046 concern different Change All Occurrences and multicursor behaviors and do not own this defect.
