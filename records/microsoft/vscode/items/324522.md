# Issue #324522 — Claude session model selection doesn't persist after restart

[https://github.com/microsoft/vscode/issues/324522](https://github.com/microsoft/vscode/issues/324522)

## Summary

Keep open: restarting a Claude agent-host session can replace the persisted model selection with the first model available during asynchronous catalog startup. The older report remains necessary because the exact corroborating issue is newer, while the older Copilot/Auto issue describes a different harness and trigger.

## Change summary

Preserve each Claude chat's selected model across a VS Code restart instead of displaying or persisting the first asynchronously loaded native model.

## Best solution

Restore the chat's persisted Claude model as an unresolved selection until the native model catalog finishes loading, then resolve it without sending a fallback selection to the agent host or overwriting session metadata.

- **Behavior:**

  > After selecting a Claude model, completing a turn, and restarting VS Code, the restored chat must continue to display and use that model. While the native model catalog is still loading, the UI may show a pending state but must not display, execute, or persist the first available model as a fallback. Other chats' selections and explicitly chosen post-restart model changes remain independent and unchanged.
- **Trace:**

  > ClaudeAgent starts with an empty model observable and queues asynchronous native enumeration through `_startModelRefresh()` and `Query.supportedModels()` in src/vs/platform/agentHost/node/claude/claudeAgent.ts. The saved selection is read from `claude.model` by ClaudeSessionMetadataStore and materialization prefers that overlay, while `_changeModel` persists every accepted UI selection. SessionModelSelection in src/vs/sessions/contrib/chat/browser/sessionModelSelection.ts already represents unresolved desired models as pending and says not to push a stand-in, so the uncertainty begins at the end-to-end restore/update ordering that still produced https://github.com/microsoft/vscode/issues/337653. Keep the boundary to restored model resolution and persistence; do not change explicit model-selection semantics, per-chat independence, or native catalog ordering.

## Evidence

- **current corroboration:** https://github.com/microsoft/vscode/issues/337653 reports the same restart symptom on VS Code 1.140.0-insider and Claude SDK 0.3.281: the picker temporarily shows the first native model while the saved selection is Opus. Later comments also document runs where that fallback reached the SDK and overwrote `session_metadata.claude.model`.
- **startup race:** src/vs/platform/agentHost/node/claude/claudeAgent.ts initializes `_models` as empty and starts `_startModelRefresh()` from a queued microtask; `_fetchNativeModels()` obtains the native catalog asynchronously through `Query.supportedModels()`.
- **persistence path:** src/vs/platform/agentHost/node/claude/claudeSessionMetadataStore.ts persists the selected model under `claude.model`, and ClaudeAgent._changeModel in src/vs/platform/agentHost/node/claude/claudeAgent.ts writes every accepted picker change back to that metadata.
- **current defensive logic:** src/vs/sessions/contrib/chat/browser/sessionModelSelection.ts now has a pending-resolution path intended to wait rather than push a stand-in model, with coverage in src/vs/sessions/contrib/chat/test/browser/sessionModelSelection.test.ts. The newer reproduction shows the end-to-end Claude restore path still needs verification against this logic before treating the issue as fixed.
