# Issue #318358 — Enable use of local agent in Agents Window

[https://github.com/microsoft/vscode/issues/318358](https://github.com/microsoft/vscode/issues/318358)

## Summary

This remains the accepted canonical backlog request for local-agent capability in the Agents Window. It has 39 upvotes, maintainers confirmed that the experience is unfinished and actively being rearchitected around Agent Host Protocol, and current main does not prove full parity with the editor's local harness.

## Change summary

Let the Agents Window use a local agent experience with the models, custom agents, tools, configuration, and session continuity available from regular VS Code Chat.

## Best solution

Complete local Agent Host/AHP parity in the Agents Window for local models, custom agents, tools, and cross-window session continuity rather than restoring the temporary extension-host harness. Preserve access for environments that cannot use external cloud CLI or SDK backends.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/providers/agentHost/browser/localAgentHost.contribution.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/localAgentHostSessionsProvider.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostChatContribution.ts`, `src/vs/sessions/contrib/providers/agentHost/test/browser/localAgentHostSessionsProvider.test.ts`
- **Validation:** Extend the local Agent Host provider tests to cover projection of supported local models and custom agents, then run an Agents Window scenario that starts a local session with both selections and confirms the same durable session can be reopened from another VS Code window.
- **Behavior:**

  > The Agents Window offers a local agent path that does not require switching to a cloud backend or a less-capable CLI workflow. Users can select supported local models and custom agents, retain the applicable tools and configuration, and reopen the same durable session across compatible VS Code windows. Acceptance should cover creating a local session, selecting a local model and custom agent before the first turn, completing a turn, and reopening that session without losing its configuration or history.
- **Trace:**

  > The current Sessions architecture registers LocalAgentHostSessionsProvider from src/vs/sessions/contrib/providers/agentHost/browser/localAgentHost.contribution.ts and derives its session types from Agent Host root state in localAgentHostSessionsProvider.ts. The specification in src/vs/sessions/contrib/providers/agentHost/AGENT_HOST_SESSIONS_PROVIDER.md establishes AHP-backed local sessions as the owning replacement architecture, while src/vs/workbench/contrib/chat/common/constants.ts keeps the legacy editor-local harness as a distinct path. Maintainer discussion in https://github.com/microsoft/vscode/issues/318358 settles the direction: close capability gaps through Agent Host rather than preserving the temporary stitched extension-host integration. The boundary is local-agent parity and durable cross-window access; do not reintroduce window-bound session ownership or redirect this work to an external extension tracker.
