# Issue #318358 — Enable use of local agent in Agents Window

[https://github.com/microsoft/vscode/issues/318358](https://github.com/microsoft/vscode/issues/318358)

## Summary

Keep this accepted feature request open: it exceeded the backlog threshold with 38 upvotes, and maintainers confirm that local-agent support remains incomplete while the Agent Host Protocol architecture is developed.

## Change summary

Restore and complete support for local agents in the Agents Window, including persistent session visibility and parity for custom agents and local models.

## Best solution

Complete the Agent Host Protocol migration so local sessions remain available across VS Code and Agents windows, while supporting custom agents and local models without relying on the temporary extension-host-bound harness.

## Plan brief

- **Likely files:** `src/vs/sessions`, `src/vs/platform/agentHost`, `extensions/copilot`
- **Validation:** In an Insiders build, create a session with a local extension-hosted agent and local model, confirm it appears and can be resumed in both the originating VS Code window and the Agents Window, reload/update the windows, and verify the session remains discoverable with its custom-agent selection intact.
- **Behavior:**

  > Users can create, discover, and resume local-agent sessions from the Agents Window without losing them across window reloads or updates. The experience supports the relevant combinations of local models and custom agents and remains usable where external cloud agent SDKs or CLI tools are unavailable. Acceptance includes cross-window access to the same session, durable session discovery, and no regression to cloud or Copilot CLI sessions.
- **Trace:**

  > The discussion identifies the current architectural boundary: the legacy Local harness executes in an extension host whose lifecycle belongs to one VS Code window, while the Agents Window needs sessions reachable from multiple clients. The intended convergence point is the Agent Host Protocol under src/vs/platform/agentHost, with the Agents Window under src/vs/sessions and provider integration in extensions/copilot. Maintainers describe the existing Local harness integration as temporary and confirm separate parity gaps for custom agents and local LLMs. The scope must preserve support for local extension-hosted runtimes needed by restricted enterprise environments; replacing them exclusively with an external cloud-dependent CLI would not satisfy the request. Related context includes https://github.com/microsoft/vscode/issues/325133 and the closed predecessor https://github.com/microsoft/vscode/issues/306921.
- **Open decisions:**
  - Must the final architecture continue supporting extension-hosted local runtimes directly, or can every compliant local runtime be adapted to the Agent Host Protocol?
  - Which combinations of custom agents, local models, and local providers are required for parity in the Agents Window?
  - What persistence and migration behavior guarantees that sessions created by the temporary Local harness remain discoverable after updates and after that harness is retired?
