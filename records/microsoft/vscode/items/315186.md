- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/316601 is verified OPEN and explicitly contains 'Closes #315186'. It proposes window.focusedTreeView and window.onDidChangeFocusedTreeView; its checklist leaves API naming, extension-only filtering, identifier versus object exposure, and unified-view scope unsettled.
- **Current API boundary:** src/vs/workbench/api/common/extHostTreeViews.ts:createTreeView exposes selection and visibility events but no view-focus property or event. Searches of src/vscode-dts and src/vs/workbench/api found no activeTreeView or focusedTreeView API. src/vs/workbench/services/views/common/viewsService.ts exposes onDidChangeFocusedView internally, but that does not provide an extension-facing solution.
- **Existing capability covers only focused items:** src/vscode-dts/vscode.proposed.treeViewActiveItem.d.ts declares TreeView.activeItem and onDidChangeActiveItem. Their implementation in src/vs/workbench/api/common/extHostTreeViews.ts is guarded by checkProposedApiEnabled(extension, 'treeViewActiveItem'); this proposed per-tree capability does not identify which of several views has focus.
- **Discussion establishes the remaining gap:** In the supplied discussion at https://github.com/microsoft/vscode/issues/315186, jrieken suggests an activeTreeView API, and alexr00 acknowledges that duplicating commands is the previous recommendation and is painful. The reporter explains why visibility, selection events, and manually configured keybinding arguments do not reliably or conveniently replace focused-view access.
- **Canonical search:** Open-issue searches for tree focus and activeTreeView surfaced https://github.com/microsoft/vscode/issues/170248 and https://github.com/microsoft/vscode/issues/3553. Both were read and verified open: the former concerns the focused item within a tree, while the latter concerns selected Explorer resources. Neither owns this report's broader focused-view identity requirement, so neither supports a duplicate close.
