# Issue #325871 — Nested mermaid diagrams do not block scroll event in chat panel

[https://github.com/microsoft/vscode/issues/325871](https://github.com/microsoft/vscode/issues/325871)

## Summary

The defect remains on current main: every wheel event from a chat output webview is unconditionally forwarded to the outer conversation, even when the Mermaid webview can scroll internally. This team-authored, confirmed bug should remain open for a wheel-routing fix.

## Change summary

Scrolling a tall Mermaid diagram with a macOS trackpad moves both the diagram and its surrounding chat conversation.

## Best solution

Make chat-output wheel routing aware of whether the embedded webview consumed the gesture: scroll the diagram while it has room, and delegate to the conversation only at the appropriate scroll boundary. Preserve outer-conversation scrolling for output webviews that have no internal vertical scroll.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/chatOutputItemRenderer.ts`, `src/vs/workbench/contrib/webview/browser/webview.ts`, `src/vs/workbench/contrib/webview/browser/webviewElement.ts`, `extensions/mermaid-markdown-features/src/chatOutputRenderer.ts`
- **Validation:** In both editor chat and the Agents window on macOS, render a Mermaid diagram taller than its 80vh viewport and verify that two-finger vertical scrolling over it moves only the diagram while internal scrolling remains possible; then verify that a non-scrollable chat output webview still delegates wheel gestures to the surrounding conversation.
- **Behavior:**

  > A vertical trackpad gesture over a Mermaid diagram that has remaining internal scroll range must move only that diagram. The surrounding chat conversation must remain stationary during that gesture. Once the embedded content cannot consume the gesture, conversation scrolling should retain the established behavior, and non-scrollable chat outputs must not trap wheel input. Validate this in both editor chat and the Agents window.
- **Trace:**

  > ChatOutputRendererService creates the embedded output webview in src/vs/workbench/contrib/chat/browser/chatOutputItemRenderer.ts. When a chat session resource is present, delegateScrollToChatWidget subscribes to IWebview.onDidWheel and forwards every event to ChatWidget.delegateScrollFromMouseWheelEvent, which reaches the outer chat list; there is no consumption or inner-scroll-boundary check. The Mermaid renderer in extensions/mermaid-markdown-features/src/chatOutputRenderer.ts supplies content whose intrinsic height can exceed the chat output's 80vh cap, creating a genuinely scrollable nested webview. Commit https://github.com/microsoft/vscode/commit/5048c16a276fe507446d3f3d6bdfdaab644bbec0 documents why unconditional forwarding originally existed, so the boundary is to preserve forwarding for non-scrollable outputs rather than disabling it globally. The uncertainty starts at the webview event contract: current onDidWheel data does not establish whether the embedded document consumed the gesture or has remaining scroll range.
