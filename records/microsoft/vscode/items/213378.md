# Issue #213378 — Cleanup/remove `interactive.transferActiveChat` 

[https://github.com/microsoft/vscode/issues/213378](https://github.com/microsoft/vscode/issues/213378)

## Summary

The proposed API still stages the last-focused chat for a later workspace opening, so the cleanup remains necessary. Keep this accepted Backlog item open for an API-owner decision on explicit session ownership and coupling transfer to opening a workspace.

## Change summary

Replace or remove the ambient interactive.transferActiveChat API in favor of an explicitly scoped transfer coupled to opening a workspace.

## Best solution

Provide a workspace-opening operation that carries an explicitly identified, caller-authorized chat session rather than whichever chat was last focused. Preserve Copilot's generated-workspace handoff while API owners decide the replacement contract and retirement of the existing proposal.

- **Behavior:**

  > The current proposed API stages whichever chat was last focused, and its effect depends on separately opening the destination workspace. The desired operation couples workspace opening with carrying an explicitly identified conversation and does not expose arbitrary active-session transfer to every proposal-enabled caller. Preserve the generated-workspace handoff used by Copilot. Acceptance must establish that the intended conversation, rather than an unrelated focused conversation, accompanies the opening operation and that ordinary folder opening remains unchanged.
- **Trace:**

  > The declaration lives in src/vscode-dts/vscode.proposed.interactive.d.ts; extHost.api.impl.ts gates only proposal availability and ExtHostChatAgents2 forwards the workspace URI. MainThreadChatAgents2.$transferActiveChatSession selects lastFocusedWidget, while ChatService.transferChatSession stages the model through ChatSessionStore for later destination startup. vscode.openFolder in workspaceCommands.ts has no chat-transfer parameter, and Copilot's newWorkspaceFollowup.ts performs the staging and opening as separate calls. These paths were read directly in the checkout and still match the concern in https://github.com/microsoft/vscode/issues/213378. Preserve ordinary folder-opening behavior and existing local Chat-view transfer constraints unless API owners explicitly expand the scope. The uncertainty begins at the public replacement contract and how it establishes the caller's right to carry a particular session; the issue's ChatResult suggestion is an example, not an approved design.
- **Open decisions:**
  - Should the replacement extend vscode.openFolder with a ChatResult-based handoff or expose a separate operation that opens a workspace with a scoped conversation?

  - Should interactive.transferActiveChat be removed immediately after migrating its built-in consumers, or retained temporarily as a deprecated proposal?
