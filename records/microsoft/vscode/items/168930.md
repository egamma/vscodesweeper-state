# Issue #168930 — Git - clone locally is not user-friendly

[https://github.com/microsoft/vscode/issues/168930](https://github.com/microsoft/vscode/issues/168930)

## Summary

Keep open: existing-clone reuse partially addresses the request, but the interactive clone flow still selects a parent folder rather than an editable, repository-derived destination. The issue is already routed to Git and accepted in Backlog.

## Change summary

Make local cloning recognize an existing checkout and offer an editable destination path derived from the repository owner and name.

## Best solution

Improve the built-in Git clone destination experience so users can distinguish an existing checkout from a parent directory and choose the complete target path. Preserve existing-clone reuse, with an explicit product decision about whether reopening a checkout should also fetch.

- **Existing-clone reuse is partial coverage:** extensions/git/src/cloneManager.ts: CloneManager.clone checks repositoryCache.get(url), and tryOpenExistingRepository can reuse an existing cached checkout. This path does not fetch, and cache-based reuse does not establish that an arbitrary destination selected by the user is recognized as the same repository.
- **Destination setting does not cover the full request:** extensions/git/package.json registers git.defaultCloneDirectory. CloneManager.cloneRepository uses it, or the home directory, as showOpenDialog.defaultUri and treats the selected folder as parentPath. It does not derive an editable full destination from the repository owner and name.
- **Nested clone behavior remains possible:** extensions/git/src/git.ts: Git.clone derives baseFolderName from the URL and constructs path.join(options.parentPath, folderName). When cache reuse does not apply, choosing ~/github.com/abcde/fg as the parent for the fg repository therefore targets ~/github.com/abcde/fg/fg, matching the reported interaction.
- **Internal capability is not interactive coverage:** extensions/git/src/commands.ts: _git.cloneRepository accepts a complete localPath and supplies targetName to Git.clone. The public git.clone command instead delegates to CloneManager's parent-folder picker, so the internal command does not satisfy the requested user-facing destination control.
