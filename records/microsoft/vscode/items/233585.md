# Issue #233585 — File comparer freezes in the background

[https://github.com/microsoft/vscode/issues/233585](https://github.com/microsoft/vscode/issues/233585)

## Summary

Keep open: current source still allows a closed comparison's computation to occupy the shared editor worker and delay subsequent comparisons. Fixing this requires planning cancellation or isolation without disrupting other worker consumers.

## Change summary

Closing an expensive file comparison should stop it from delaying subsequently opened, inexpensive comparisons.

## Best solution

Make abandoned diff computations relinquish processing capacity promptly so new comparisons remain responsive. Preserve other editor-worker operations and existing diff timeout semantics.

Verify that the small comparison completes before the abandoned computation's original timeout, rather than waiting for that timeout; also verify that another active comparison and unrelated editor-worker requests still complete correctly.
- **Behavior:**

  > A large comparison can continue consuming processing capacity after its editor is closed, delaying a subsequently opened small comparison. Closing the expensive comparison should remove that delay without requiring a window reload. Acceptance should exercise actual worker execution and show that the small comparison completes before the abandoned job's original computation budget expires. Other active comparisons and editor-worker operations must retain their results and responsiveness.
- **Trace:**

  > DiffEditorViewModel in src/vs/editor/browser/widget/diffEditor/diffEditorViewModel.ts cancels its token on disposal. WorkerBasedDocumentDiffProvider.computeDiff in src/vs/editor/browser/widget/diffEditor/diffProviderFactoryService.ts does not forward that token to IEditorWorkerService and checks cancellation only after awaiting the result. EditorWorkerService.computeDiff dispatches through a reused EditorWorkerClient, and EditorWorker.$computeDiff in src/vs/editor/common/services/editorWebWorker.ts invokes synchronous diff computation without cancellation. This establishes why closing the view cannot interrupt an active built-in diff, but it does not identify a bounded way to preempt that work safely across all shared-worker consumers. Preserve existing algorithm selection, timeout behavior, and unrelated worker requests; merely discarding the obsolete result does not satisfy the report. https://github.com/microsoft/vscode/issues/227827 supplies related large-diff performance evidence but does not establish an exact duplicate.

## Evidence

- **Reported trigger and confirmations:** https://github.com/microsoft/vscode/issues/233585 describes closing a large, substantially different file comparison and then waiting seconds to a minute for a small comparison. Two independent commenters confirm comparison stalls on Windows with VS Code 1.95.2 and 1.95.3.
- **Cancellation does not reach computation:** src/vs/editor/browser/widget/diffEditor/diffEditorViewModel.ts cancels its CancellationTokenSource on disposal and passes the token to WorkerBasedDocumentDiffProvider.computeDiff. In src/vs/editor/browser/widget/diffEditor/diffProviderFactoryService.ts, the built-in algorithm calls editorWorkerService.computeDiff without that token; cancellation is checked only after the awaited computation returns.
- **Shared synchronous worker path:** src/vs/editor/browser/services/editorWorkerService.ts:110-112 dispatches comparisons through the shared WorkerManager. WorkerManager.withWorker reuses one EditorWorkerClient. src/vs/editor/common/services/editorWebWorker.ts:124-141 invokes the diff algorithm synchronously, with no cancellation argument, so abandoning the requesting view does not interrupt an active calculation and later worker requests must wait.
- **Timeout is not disposal cancellation:** src/vs/editor/common/diff/defaultLinesDiffComputer/defaultLinesDiffComputer.ts:47 constructs a DateTimeout from maxComputationTimeMs, or an InfiniteTimeout when that value is zero. This computation budget is independent of closing the comparison; it does not resolve the missing cancellation propagation.
- **Older related issue is not a verified duplicate:** https://github.com/microsoft/vscode/issues/227827 is open and older, but reports a large comparison remaining open while loading and unrelated editor saves stalling. It does not establish the same close-large-comparison-then-open-small-comparison symptom required for a duplicate close of this re-reviewed item.
