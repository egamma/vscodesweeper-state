## Summary

The linked sample has since changed its startup sequence, so the original initialization timing also needs separating from the registration failure.

## Change summary

Semantic highlighting requires manual provider registration despite the language server advertising semantic-token support.

## Best solution

Establish whether the initialize response actually sends the protocol's lowercase semantic-token fields and inspect capabilities after client startup completes. Correct server serialization if those fields are malformed; pursue the language-client registration path only if a protocol-compliant response still fails.

## Evidence

- **Concrete reproduction material:** https://github.com/microsoft/vscode/issues/284658 supplies extension code, vscode-languageclient ^9.0.1, initialization logs, screenshots, a dynamic-registration attempt, and https://github.com/ProphetLamb/scriban-ls. There are no comments or linked closing PRs.
- **Capability casing mismatch:** The reported server log contains semanticTokensProvider with PascalCase Legend, TokenTypes, TokenModifiers, Range, and Full. The client expects lowercase legend, tokenTypes, tokenModifiers, range, and full. In https://github.com/microsoft/vscode-languageserver-node/blob/release/client/9.0.1/client/src/common/semanticTokens.ts, initialize registers capabilities.semanticTokensProvider, registerLanguageProvider checks options.full and options.range, and lines 204–212 pass options.legend to the VS Code registration APIs.
- **Logging is not a captured wire response:** https://github.com/ProphetLamb/scriban-ls/blob/HEAD/src/ScribanLanguage.Server/Controllers/LanguageServerJsonRpcController.cs logs results using JsonConvert.SerializeObject(result), separately from JSON-RPC transport serialization. This makes malformed serialization a strong lead, but the supplied log alone does not conclusively establish the bytes received by the client.
- **Initialization timing:** The original extension calls client.start() without awaiting it and immediately reads initializeResult inside its manual registration helper; an undefined result at that point does not demonstrate failed initialization. The current https://github.com/ProphetLamb/scriban-ls/blob/HEAD/src/ScribanLanguage.VSCode/src/extension.ts instead awaits startLanguageClient(), while still explicitly registering semantic tokens.
- **Current core registration path:** src/vs/workbench/api/common/extHostLanguageFeatures.ts:2580–2591 forwards registerDocumentSemanticTokensProvider to the main thread. src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts:535–542 registers the provider with the language-features service. These paths do not interpret LSP server capabilities; automatic capability handling belongs to vscode-languageclient.
