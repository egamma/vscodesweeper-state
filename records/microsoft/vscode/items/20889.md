# Issue #20889 — [Feature Request] Undo branches

[https://github.com/microsoft/vscode/issues/20889](https://github.com/microsoft/vscode/issues/20889)

## Summary

Keep this accepted Backlog request open: current undo handling still discards alternate redo futures, and Local History does not preserve every unsaved editing state. This remains the canonical request, with 330 upvotes and unresolved product/API design questions.

## Change summary

Preserve and navigate alternate editing histories when a user makes new edits after undoing.

## Best solution

Design branch-preserving editor history with an explicit way to recover alternate futures while retaining familiar undo/redo behavior. Settle the navigation surface and extension contract before changing the shared undo infrastructure; saved-file Local History is complementary, not a replacement.

## Plan brief

- **Likely files:** `src/vs/platform/undoRedo/common/undoRedo.ts`, `src/vs/platform/undoRedo/common/undoRedoService.ts`, `src/vs/editor/common/model/editStack.ts`, `src/vs/platform/undoRedo/test/common/undoRedoService.test.ts`
- **Validation:** The plan should establish executable history tests: create distinct editing states, undo, make an alternate edit, and navigate back to both futures without losing their contents. Run the targeted undoRedoService tests and agreed editor regression tests; manually verify branch navigation is keyboard-accessible and ordinary undo/redo remains familiar. No tests were executed during this read-only review.
- **Behavior:**

  > After undoing edits and making a new edit, the earlier future remains recoverable alongside the new history. Users can deliberately select and navigate alternate histories rather than reconstructing lost unsaved text from saved-file snapshots. Ordinary undo/redo should remain predictable. Acceptance must cover recovering both futures, repeated branching, and accessible navigation under the chosen product design.
- **Trace:**

  > IUndoRedoService.pushElement currently promises destruction of redo history, and ResourceEditStack.pushElement clears _future, including workspace-element invalidation. Editor typing reaches this service through EditStack._getOrCreateEditStackElement; getElements exposes only past and future arrays, not branches. Local History records saves through WorkingCopyHistoryTracker.onDidSave and cannot recover all unsaved states. The historical prototype PR https://github.com/microsoft/vscode/pull/27302 closed without merging. Maintainer discussion at https://github.com/microsoft/vscode/issues/20889#issuecomment-382380267 leaves presentation and extension interaction unresolved. Planning must enumerate shared undo consumers and grouped multi-resource behavior before treating this as a bounded editor-only change; do not conflate it with Timeline API work at https://github.com/microsoft/vscode/issues/84297.
- **Open decisions:**
  - Should alternate-history navigation use a dedicated editor surface, the Timeline, or an extension-provided surface, and should ordinary undo ever expose branch selection?
  - Should the initial capability include a public extension contract for inspecting and selecting history branches, or remain internal to the editor?
  - What user-visible retention limits and lifetime should apply to alternate branches, including whether they survive closing a document or restarting VS Code?
