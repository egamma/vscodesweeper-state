# Issue #23633 — showInputBox should have the ability to have an array of quickpick options as well

[https://github.com/microsoft/vscode/issues/23633](https://github.com/microsoft/vscode/issues/23633)

## Summary

The convenience API still lacks a combined suggestions-and-free-text input mode. Keep this accepted, well-supported request open: the documented createQuickPick workaround requires extension-managed behavior, and no verified older canonical absorbs the request.

## Change summary

Allow extensions to offer suggested values while also accepting arbitrary typed input through a convenient input API.

## Best solution

Provide an opt-in API contract for suggested values and arbitrary text acceptance, preserving existing showInputBox and showQuickPick behavior. Decide the public surface and acceptance semantics with the API owner before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostQuickOpen.ts`, `src/vs/platform/quickinput/browser/quickInput.ts`, `src/vs/platform/quickinput/test/browser/quickinput.test.ts`
- **Validation:** The plan should define API-level acceptance checks for choosing a suggestion, accepting unmatched text, and cancelling, plus a case where typed text coexists with an active suggestion. Validate the agreed widget behavior with targeted tests in src/vs/platform/quickinput/test/browser/quickinput.test.ts and verify existing input and selection-only contracts remain unchanged.
- **Behavior:**

  > Extensions should be able to present suggested values and accept a value that is not among those suggestions through a convenient input API. Users must be able to choose a suggestion or submit arbitrary typed text, with cancellation remaining distinguishable from acceptance. Acceptance checks should cover a listed value, unmatched text, cancellation, and the agreed behavior when text is entered while a suggestion remains active. Existing callers that do not opt into this capability must retain their current behavior.
- **Trace:**

  > InputBoxOptions in src/vscode-dts/vscode.d.ts has no suggestions collection, while QuickPick exposes editable filter text, mutable items, and events that support the workarounds in the issue. ExtHostQuickOpen.showQuickPick in src/vs/workbench/api/common/extHostQuickOpen.ts returns supplied items through numeric handles rather than free text; showInput delegates to a separate input-box path. QuickPick.show in src/vs/platform/quickinput/browser/quickInput.ts:896–910 promotes the active item into selectedItems before accepting, so a combined mode needs explicitly agreed text-versus-selection semantics. Related https://github.com/microsoft/vscode/issues/35785 discusses completion but is newer and includes a broader word-completion request; it is a design reference, not a duplicate target. The unresolved boundary is the public contract, not whether extensions can synthesize custom entries today. Preserve existing selection-only, cancellation, and multi-select behavior; word-level completion and multi-field dialogs are outside this request.
- **Open decisions:**
  - Should the supported convenience contract extend showInputBox with suggestions, add an opt-in free-text mode to showQuickPick, or introduce a distinct API?
  - When typed text differs from an active suggestion, does Enter accept the typed text or the suggestion, and how does the user explicitly choose the other value?
