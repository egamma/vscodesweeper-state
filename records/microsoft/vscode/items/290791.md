# Issue #290791 — Thinking UI should take up more space?

[https://github.com/microsoft/vscode/issues/290791](https://github.com/microsoft/vscode/issues/290791)

## Summary

Keep open as chat UI polish: current main retains the 200px streaming cap and supports manual full-height expansion, but a maintainer proposed revisiting that presentation and the thread has not settled whether the panel should auto-grow or use another proportion. A decline close would contradict that maintainer direction.

## Change summary

Improve the thinking panel's proportions so its fixed-height presentation does not look undersized in a large chat view.

## Best solution

Choose a responsive presentation that preserves the fixed-scrolling design's reduced layout movement while making better use of a tall chat view, without adding a user setting. The design should also keep full thinking content keyboard-accessible and preserve compact behavior in constrained layouts.

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/media/chatThinkingContent.css`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatThinkingContentPart.ts`, `src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/chatContentParts/chatThinkingContentPart.test.ts`
- **Validation:** Add or update ChatThinkingContentPart browser tests for the chosen collapsed/expanded sizing semantics and run `scripts/test.sh --grep ChatThinkingContentPart`; manually verify a long streaming response in both tall and constrained chat views, including keyboard activation of the expansion header.
- **Behavior:**

  > Long streaming thinking content should use the available chat space in a visually balanced way without causing disruptive response-list movement. Users must still be able to reveal the complete thinking content using both pointer and keyboard interaction, and constrained chat layouts must remain usable. No new configuration setting should be introduced. Acceptance should cover tall and compact chat views, active streaming, completed thinking, and collapse/expand transitions.
- **Trace:**

  > The default `fixedScrolling` mode is registered in src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts. Its viewport is capped independently in CSS at 200px and in ChatThinkingContentPart through `THINKING_SCROLL_MAX_HEIGHT`, which also drives scroll dimensions, fade indicators, auto-scroll, and whether expansion is enabled. The current expanded state removes the cap, so manual full-height expansion already exists; the unresolved question is the resting presentation and its responsiveness to available chat height. Preserve the anti-jump and secondary-content rationale recorded in https://github.com/microsoft/vscode/issues/267806, and do not add a setting because the reporter explicitly rejected that direction. Existing chat accessibility and keyboard expansion behavior must not regress.
- **Open decisions:**
  - Should streaming thinking automatically grow with available chat height, or retain a compact resting height and rely on a more discoverable manual expansion?
  - Should the visual imbalance be addressed primarily through responsive height or by narrowing the thinking surface while retaining the current height cap?
