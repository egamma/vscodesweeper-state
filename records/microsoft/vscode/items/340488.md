# Issue #340488 — Chat sessions with custom titles silently wiped (`requests: []`) and dropped from history

[https://github.com/microsoft/vscode/issues/340488](https://github.com/microsoft/vscode/issues/340488)

## Summary

Keep open: the reporter describes conversation files being destructively replaced, not merely hidden from history. Current main has separate rename, save, and serialization paths that need retesting together; the follow-up supplies a usable trigger—rename idle session B while session A is running—but the precise failure has not been confirmed.

## Change summary

Prevent renaming a chat during concurrent session activity from replacing persisted conversation contents with an empty requests array and removing it from history.

## Best solution

Establish the concurrent rename/save sequence in the core chat persistence lifecycle and ensure renaming preserves existing conversation contents and history discoverability. Distinguish incomplete model restoration from intentional conversation changes rather than treating every empty model as equivalent.

- **Behavior:**

  > A persisted multi-turn chat must retain its conversation when renamed while another chat is processing a request. Renaming should update the intended session's title without emptying either session or removing existing conversations from history. Acceptance includes reopening the renamed session after reload and verifying its complete transcript and title. Existing intentional request-removal and genuinely empty-session behavior must remain supported.
- **Trace:**

  > ChatService.setChatSessionTitle in src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts updates the live title and calls saveState after the index-title operation; saveState persists all eligible live local models, not only the renamed session. The disposal callback also stores zero-request models when they have custom titles. ChatSessionStore.writeSession in src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts can replace an existing file using serializer output; ObjectMutationLog.write produces a single kind:0 snapshot on initial write or compaction, and ChatSessionOperationLog obtains requests from the live model. These paths explain how an empty model could yield the reported artifact, but the transition from a populated session to that empty model has not been established. The investigation must first reproduce the active-A/rename-idle-B sequence and trace model restoration, identity, and disposal across the queued saves. Preserve legitimate empty-session creation and intentional history editing; a blanket ban on empty writes is not an established solution. The older reports https://github.com/microsoft/vscode/issues/331572 and https://github.com/microsoft/vscode/issues/340336 concern different observed persistence/discovery failures.
