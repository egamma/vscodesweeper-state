# Issue #157859 — Request option to not expand top-level directories

[https://github.com/microsoft/vscode/issues/157859](https://github.com/microsoft/vscode/issues/157859)

## Summary

A real gap remains on current main: when a multi-root workspace has no saved view state, the Explorer eagerly expands its first five roots, and no setting or provider API lets users suppress that initial expansion. The existing file-explorer routing is correct, but a maintainer should choose whether the control belongs to users or file-system providers.

## Change summary

Allow top-level roots supplied by a file-system provider to start collapsed so their children are not read until the user expands them.

## Best solution

Provide an opt-out from initial multi-root expansion while preserving saved view-state restoration and the existing default for ordinary workspaces. Decide whether this is a workspace/user setting or a FileSystemProvider capability before implementation because those choices expose different public contracts.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/views/explorerView.ts`, `src/vs/workbench/contrib/files/browser/files.contribution.ts`, `src/vs/workbench/contrib/files/common/files.ts`, `src/vs/workbench/contrib/files/test/browser/explorerView.test.ts`
- **Validation:** Add an ExplorerView browser test using multiple roots with no saved view state and the selected opt-out mechanism; verify that no root is expanded or resolved initially, then that expanding one root resolves only that root. Existing view-state restoration and default initial-expansion tests must remain passing.
- **Behavior:**

  > A multi-root Explorer can be configured or instructed to display new top-level roots collapsed. While collapsed, a root's children are not requested from its FileSystemProvider; expanding that root loads it normally. Existing saved expansion state continues to restore, and users who do not opt out retain the established default behavior.
- **Trace:**

  > ExplorerView.setTreeInput in src/vs/workbench/contrib/files/browser/views/explorerView.ts calls tree.setInput and, when there is no viewState, unconditionally expands Math.min(input.length, 5) roots. That directly explains why the reporter's five or six provider-backed roots invoke readDirectory immediately. explorer.expandSingleFolderWorkspaces in src/vs/workbench/contrib/files/browser/files.contribution.ts only controls the separate input.length === 1 path, so it does not cover this scenario. https://github.com/microsoft/vscode/pull/181431 limited the eager expansion count for performance but did not add an opt-out. Preserve saved view-state restoration, explicit user expansion, and ordinary auto-reveal behavior; the wrapper-directory workaround must not become required.
- **Open decisions:**
  - Should initial collapsed state be controlled by a user/workspace setting that applies to all multi-root workspaces, or by a FileSystemProvider capability through which an extension selects the initial state?

## Evidence

- **current source:** src/vs/workbench/contrib/files/browser/views/explorerView.ts, in ExplorerView.setTreeInput, explicitly expands up to the first five roots whenever no saved view state exists; this triggers child resolution for the reporter's five or six database-backed roots.
- **missing capability:** src/vs/workbench/contrib/files/browser/files.contribution.ts registers explorer.expandSingleFolderWorkspaces, but ExplorerView consults it only when input.length === 1; it does not suppress the separate loop that expands up to five roots.
- **confirmed scenario:** The reporter supplied a minimal provider reproduction in https://github.com/microsoft/vscode/issues/157859#issuecomment-1232200828, after which a maintainer applied the bug and confirmation-pending labels.
- **related fix is incomplete:** https://github.com/microsoft/vscode/pull/181431 addressed https://github.com/microsoft/vscode/issues/176226 by limiting eager expansion to five roots, but current source still eagerly expands exactly the five-or-six-root scenario reported here and provides no opt-out.
- **existing workaround:** The reporter can insert an extra wrapper directory, but that changes the exposed database hierarchy rather than controlling initial Explorer expansion.
