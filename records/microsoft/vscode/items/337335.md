# Issue #337335 — MCP: make default-off, per-workspace enablement easy to manage

[https://github.com/microsoft/vscode/issues/337335](https://github.com/microsoft/vscode/issues/337335)

## Summary

Fresh, team-authored (COLLABORATOR) feature request from today with no comments yet; the underlying gap is real — today's `chat.mcp.access` (chat.shared.contribution.ts) is a single global enum (None/Registry/All) with no first-class 'default off, opt individual workspaces in' workflow, and the allow/deny-list settings that exist are enterprise-policy-only, hidden from users. Keeping open for design input.

## Change summary

Let users keep MCP servers disabled by default globally while easily opting specific workspaces into specific servers, with workspace overrides visible/manageable and clearly distinct from session-only enablement.

## Best solution

Design a workspace-scoped override on top of the existing chat.mcp.access / per-server enablement model (src/vs/platform/mcp/common/mcpManagement.ts, src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts) with a clear place to inspect and remove per-workspace opt-ins, distinct from the existing session-only enablement flow.

## Plan brief

- **Likely files:** `src/vs/platform/mcp/common/mcpManagement.ts`, `src/vs/workbench/contrib/mcp/common/mcpConfiguration.ts`, `src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts`, `src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts`
- **Validation:** A test asserting that with the global MCP default set to off, a workspace-level override enables only the opted-in servers for that workspace, and the override is visible/removable through the chosen management surface.
- **Trace:**

  > chat.mcp.access is defined once, application-scoped, in src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts and consumed by mcpRegistry.ts / mcpDiscovery.ts / allowedMcpServersService.ts as a single global value; the only other allow/deny mechanisms (mcpAllowedServersConfig/mcpDeniedServersConfig) are enterprise-policy-only and hidden from the Settings UI. No existing code path lets a user keep the global default off while persistently opting one workspace into specific servers, distinct from ad hoc session enablement. Boundary: don't change the enterprise-policy allow/deny mechanism or the existing per-server toggle UX wholesale — the gap is the missing workspace-scoped override layer and its management surface.
- **Open decisions:**
  - Should the workspace override live as a resource-scoped variant of chat.mcp.access (or a new setting), and should it apply per-server or only as a whole-workspace toggle?
  - Where should users go to inspect and remove workspace overrides — an extension to the existing MCP servers list/editor (mcpListWidget.ts), a dedicated settings UI section, or something else?
  - How should session-only enablement (today's ad hoc allow-for-this-session flow) be distinguished in UI/state from a persistent workspace-level override so users don't confuse the two?

## Evidence

- **current setting:** chat.mcp.access (mcpAccessConfig, src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts:1096) is a flat None/Registry/All enum with no visible per-workspace scope override in the schema shown, and its enterprise-only siblings mcpAllowedServersConfig/mcpDeniedServersConfig are `included: false` (policy-only, not user-facing).
- **no workspace-override UI found:** src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts manages per-server toggling but the issue's ask — global default-off with easy, inspectable, removable per-workspace opt-in — is not represented in mcpConfiguration.ts or mcpManagement.ts.
