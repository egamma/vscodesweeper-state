# Issue #337335 — MCP: make default-off, per-workspace enablement easy to manage

[https://github.com/microsoft/vscode/issues/337335](https://github.com/microsoft/vscode/issues/337335)

## Summary

Keep open: scoped per-server enablement exists, but it does not provide the requested default-off preference and manageable workspace exceptions. The related newer request covers only workspace-origin servers, not this broader workflow.

## Change summary

Provide an optional user-level default-off preference for MCP servers with inspectable, removable workspace exceptions and clearly differentiated session enablement.

## Best solution

Extend MCP enablement and the existing customization management surface to support a configurable disabled baseline with selected workspace exceptions. Preserve the current default for other users and keep persistent workspace choices distinct from session-scoped choices.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/enablement.ts`, `src/vs/workbench/contrib/mcp/common/mcpService.ts`, `src/vs/workbench/contrib/mcp/browser/mcpCommands.ts`, `src/vs/platform/agentHost/common/customizationEnablement.ts`, `src/vs/platform/agentHost/node/agentHostCustomizationEnablementService.ts`
- **Validation:** Add local and Agent Host enablement tests covering a disabled baseline, newly discovered servers, workspace opt-in, session-only opt-in, and removal of overrides. Manually verify that workspace choices survive reopening the workspace, session choices do not affect another session, and the management UI exposes the effective scope and allows restoring inheritance.
- **Behavior:**

  > A user can choose to leave MCP servers disabled by default without manually disabling each server. Selected servers can be enabled persistently for one workspace without changing that user preference or other workspaces. Workspace exceptions are easy to inspect and remove, returning the server to its inherited state. Session-scoped enablement is visibly distinct and does not become a workspace preference. Users who do not opt into this workflow retain the existing default behavior.
- **Trace:**

  > McpService constructs the shared EnablementModel in src/vs/workbench/contrib/mcp/common/mcpService.ts; that model currently resolves absent profile decisions as enabled in src/vs/workbench/contrib/chat/common/enablement.ts. Agent Host separately resolves scoped decisions in AgentHostCustomizationEnablementService, using DEFAULT_CUSTOMIZATION_ENABLED from src/vs/platform/agentHost/common/customizationEnablement.ts. Existing per-server workspace and session actions are in src/vs/workbench/contrib/mcp/browser/mcpCommands.ts, so scope selection already has a foundation. chat.mcp.access=none suppresses registry collections, and chat.mcp.autostart only suppresses automatic startup; neither supplies the requested selectively overridable baseline. The remaining uncertainty is the complete preference propagation and override-management surface across local and host paths; the shared customization helpers also serve plugins, whose defaults must not change incidentally. https://github.com/microsoft/vscode/pull/330566 supplies prior scoped-enablement design, while https://github.com/microsoft/vscode/issues/338958 concerns a distinct origin-filtering preference.

## Evidence

- **Existing enablement foundation:** src/vs/workbench/contrib/mcp/common/mcpService.ts constructs EnablementModel('mcp.enablement'). In src/vs/workbench/contrib/chat/common/enablement.ts, readProfileEnabled falls back to true, and readEnabledWithWorkspaceKey falls back to EnabledProfile. Workspace overrides already exist, but the baseline is not a configurable default-off preference.
- **Agent Host baseline:** src/vs/platform/agentHost/common/customizationEnablement.ts defines DEFAULT_CUSTOMIZATION_ENABLED = true and resolves session > workspace > global. AgentHostCustomizationEnablementService.resolve in src/vs/platform/agentHost/node/agentHostCustomizationEnablementService.ts gathers per-customization decisions and uses that fallback; this is a foundation for scoped exceptions, not the requested blanket preference.
- **Existing settings do not cover the central ask:** src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts registers chat.mcp.access and chat.mcp.autostart. Setting access to none causes McpRegistry.collections in src/vs/workbench/contrib/mcp/common/mcpRegistry.ts to return an empty collection, rather than leaving individually enableable servers under a disabled baseline. Autostart controls automatic startup, not scoped server enablement.
- **Partial UI coverage:** src/vs/workbench/contrib/mcp/browser/mcpCommands.ts already offers distinct Enable (Workspace) and Enable (Session) actions through getAgentHostMcpServerEnablementItems. These satisfy part of the scope distinction, but do not replace the requested default-off preference or workspace-override management workflow.

It cannot absorb this older, re-reviewed request for all servers default-off.
