# Issue #127998 — Interactive Window at the bottom of the screen

[https://github.com/microsoft/vscode/issues/127998](https://github.com/microsoft/vscode/issues/127998)

## Summary

Keep open: placing the Interactive Window alongside Terminal and Debug Console remains distinct from splitting the editor downward. The request has 24 upvotes, maintainer interest, and related reports consolidated here; no verified open canonical supersedes it.

## Change summary

Allow the notebook-backed Interactive Window to occupy a bottom-panel tab alongside Terminal, Problems, Output, and Debug Console.

## Best solution

Support an Interactive Window panel location while retaining notebook execution, rich output, and editor placement. Settle the default placement and compatibility with existing extension opening calls before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/interactive/browser/interactive.contribution.ts`, `src/vs/workbench/contrib/interactive/browser/interactiveEditor.ts`, `src/vs/workbench/contrib/interactive/browser/interactiveEditorInput.ts`
- **Validation:** In a Python workspace with Jupyter, open an Interactive Window, place it in the bottom panel, switch between it and Terminal or Debug Console, and execute code from the source editor. Verify rich outputs, input history, keyboard focus, and kernel continuity; verify editor placement remains available and reload behavior matches the agreed placement contract.
- **Behavior:**

  > Users can place the notebook-backed Interactive Window in the bottom panel as a peer of Terminal and Debug Console, without creating a lower editor group. Executing Python code from the source editor continues to target that window and display rich notebook output. Switching panel tabs preserves the interactive session and input history. Editor placement remains available; the default location and restoration behavior must be agreed before implementation.
- **Trace:**

  > src/vs/workbench/contrib/interactive/browser/interactive.contribution.ts registers InteractiveEditor through EditorPaneDescriptor, and _interactive.open maps viewColumn to an editor group before calling IEditorService.openEditor. InteractiveEditor in interactiveEditor.ts derives from EditorPane and participates in editor-group layout and state; InteractiveEditorSerializer in interactive.contribution.ts serializes InteractiveEditorInput. The existing configuration block offers execution, scrolling, saving, and hint options, not panel hosting. Debug Console demonstrates a distinct panel-view registration in src/vs/workbench/contrib/debug/browser/debug.contribution.ts:426-443. https://github.com/microsoft/vscode/issues/126415#issuecomment-870721935 supports panel/sidebar placement, but does not settle the final default or compatibility contract. Preserve notebook models, kernels, rich outputs, and existing extension callers; sharing the Debug Console input widget, tracked by https://github.com/microsoft/vscode/issues/127498, is separate work. The trace establishes the hosting gap, not a bounded implementation or a complete inventory of affected consumers.
- **Open decisions:**
  - Should panel placement be opt-in while existing Interactive Window opening calls retain editor placement, or should new windows default to the panel; how should explicit viewColumn requests and restored windows behave under that choice?

## Evidence

- **Explicit panel requirement:** https://github.com/microsoft/vscode/issues/127998 requests a peer tab beside Terminal, Problems, Output, and Debug Console. The July 31, 2025 comment explicitly rejects Split Down as satisfying that requirement.
- **Existing capability does not cover the ask:** src/vs/workbench/browser/parts/editor/editor.contribution.ts registers Split Editor Down, whose command ID is workbench.action.splitEditorDown. This provides a vertically arranged editor group, not an Interactive Window tab in the panel.
- **Current opening and configuration boundary:** src/vs/workbench/contrib/interactive/browser/interactive.contribution.ts registers InteractiveEditor as an EditorPane. Its _interactive.open command resolves viewColumn through columnToEditorGroup and opens through IEditorService.openEditor; its interactiveWindow configuration registration has no panel-location option. InteractiveEditor in interactiveEditor.ts also derives from EditorPane and uses editor-group state.
- **Maintainer direction:** https://github.com/microsoft/vscode/issues/126415#issuecomment-870721935 explicitly proposes hosting the Interactive Window in the panel or sidebar, with editor placement available as for terminals. That discussion supports this request rather than an as-designed decline; the parent issue is closed and cannot serve as a duplicate canonical.
- **Related reports consolidate here:** https://github.com/microsoft/vscode-jupyter/issues/15235#issuecomment-1971411398 and https://github.com/microsoft/vscode-jupyter/issues/15925#issuecomment-2284469924 both identify this issue as their duplicate target, including the explicit request to move the Python REPL into the bottom panel.
- **Canonical search:** Searched open and closed microsoft/vscode issues using Interactive Window/panel, interactive/bottom, REPL/panel, and interactive/dock terminology. The older open https://github.com/microsoft/vscode/issues/127498 concerns sharing the input widget with Debug Console, not panel placement, so it does not own the same reporter-observable request.
- **Accepted demand and implementation boundary:** The issue is in Backlog with 24 community upvotes. The existing Debug Console panel registration in src/vs/workbench/contrib/debug/browser/debug.contribution.ts:426-443 uses ViewContainerLocation.Panel and a movable view, whereas the Interactive Window currently uses the editor registration and opening lifecycle.
