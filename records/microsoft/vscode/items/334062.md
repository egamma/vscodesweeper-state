# Issue #334062 — 1.136.0: no window on Linux when appmenu-gtk-module is loaded via gtk-modules (works in 1.134.0)

[https://github.com/microsoft/vscode/issues/334062](https://github.com/microsoft/vscode/issues/334062)

## Summary

Extremely well-diagnosed regression (bisected config, gdb backtrace) showing VS Code 1.136.0 never opens a window when `appmenu-gtk-module` is loaded via GTK's `gtk-modules=` setting — a default on Ubuntu/Kubuntu KDE Plasma installs — while 1.134.0 works fine; this needs a real engineer to confirm the exact regressing change since the checkout here has no history to trace it.

## Change summary

On Linux/X11 with the `appmenu-gtk-module` GTK module loaded (KDE Plasma default), VS Code 1.136.0's browser process SIGSEGVs inside libgio/libglib during startup and then hangs, so no window ever opens; 1.134.0 is unaffected with the identical module loaded.

## Best solution

Needs a maintainer/Electron-integration owner to bisect the exact commit or dependency change between 1.134.0 and 1.136.0 (Electron/Chromium minor bump, GTK-related command-line switch, or native module change) that causes the crash when `appmenu-gtk-module` is present; this single-commit shallow checkout has no history to do that bisection here.

## Evidence

- **reporter bisection:** Reporter isolated the trigger to a single line, `gtk-modules=appmenu-gtk-module`, in ~/.config/gtk-3.0/settings.ini via a binary search over 114 config entries, and confirmed 1.134.0 works with the identical module loaded while 1.136.0 does not.
- **traced crash path:** gdb shows a SIGSEGV in the browser process inside libgio-2.0/libglib-2.0 dispatched from g_main_context_iteration, jumping to an unmapped address, consistent with a stale/ABI-mismatched callback from the GTK module; strace shows the process then hangs writing eventfd wakeups instead of forking a renderer.
- **no VS Code-side GTK module code:** rg found no VS Code TypeScript/native code that touches gtk-modules, appmenu, or GTK module loading directly (only unrelated 'appMenu' Electron Menu API usage in src/vs/platform/menubar and src/vs/base/browser/ui/menu), so the regression is most likely in Electron's/Chromium's native Linux UI startup path rather than app-level code.
- **checkout limitation:** This checkout is a shallow single-commit clone of main (no version history), so I could not diff the .npmrc Electron target or native startup code between the 1.134.0 and 1.136.0 tags to identify the exact regressing change.
