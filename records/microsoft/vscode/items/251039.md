# Issue #251039 — Second generation profile does not inherit "Default" keybindings of parent

[https://github.com/microsoft/vscode/issues/251039](https://github.com/microsoft/vscode/issues/251039)

## Summary

The accepted Backlog bug remains present on main: duplicating a profile does not carry forward its Default-resource selection, so a second-generation profile can receive an absent keybindings file instead of the Default profile's keybindings resource.

## Change summary

Duplicating a profile whose keybindings come from Default can create a second-generation profile with a missing keybindings resource.

## Best solution

Preserve the effective Default inheritance state when duplicating Profile A into Profile B, so B resolves keybindings through the Default profile and its keybindings editor never targets a missing profile-local file.

## Evidence

- **source trace:** In src/vs/workbench/contrib/userDataProfile/browser/userDataProfilesEditorModel.ts, NewProfileElement.initialize marks every resource for copying when the source is a profile, without transferring copyFrom.useDefaultFlags; saveNewProfile consequently passes flags derived only from the new-profile radio selections.
- **failure path:** src/vs/workbench/services/userDataProfile/browser/userDataProfileImportExportService.ts exports the source keybindings and creates the target with the supplied useDefaultFlags. KeybindingsResource.getKeybindingsContent in src/vs/workbench/services/userDataProfile/browser/keybindingsResource.ts returns null when the resolved file is absent, apply then deliberately writes nothing, leaving the target's profile-local keybindingsResource missing.
- **resource semantics:** src/vs/platform/userDataProfile/common/userDataProfile.ts maps keybindingsResource to the Default profile only when useDefaultFlags.keybindings is true; the second-generation creation path does not preserve that flag automatically.
