# Issue #316769 — VSCode UI Freezes After Being Minimized While Files Are Repeatedly Created and Deleted in Opened Folder

[https://github.com/microsoft/vscode/issues/316769](https://github.com/microsoft/vscode/issues/316769)

## Summary

The supplied performance trace confirms a long renderer-main-thread stall, and current Explorer code still accumulates file-change events while its refresh scheduler is delayed. This should remain open for diagnosis of the minimized-window event backlog rather than requesting the same information again.

## Change summary

Repeated external file creation and deletion while a Windows VS Code window is minimized causes an increasingly long UI freeze when the window is restored.

## Best solution

Ensure sustained file-system churn cannot create unbounded Explorer work while renderer timers are throttled, with restoration requiring at most one bounded reconciliation of the visible tree. Confirm the ownership between Explorer event handling and Chromium's minimized-window timer behavior before choosing the implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/files/browser/explorerService.ts`, `src/vs/workbench/contrib/files/test/browser/explorerService.test.ts`
- **Validation:** Reproduce on Windows by continuously creating and deleting one file while the Explorer is visible and the window is minimized; after the eventual change, restoration must remain responsive and a performance trace must contain no restore-time renderer long task whose duration grows with the minimized interval. Add a focused ExplorerService test that exercises a large burst of alternating added/deleted notifications and verifies bounded reconciliation behavior.
- **Behavior:**

  > With the Explorer visible, sustained external creation and deletion of files while VS Code is minimized must not cause a restore-time UI freeze. Restore latency must remain bounded rather than increasing with the duration of file churn. The Explorer must still converge to the actual file-system state, and ordinary live file updates while the window is focused must remain prompt.
- **Trace:**

  > The reporter's trace at https://github.com/microsoft/vscode/issues/316769#issuecomment-4531616503 confirms a 1.56-second task on CrRendererMain, dominated by an animation-frame callback and accompanied by tree/DOM rendering activity. ExplorerService in src/vs/workbench/contrib/files/browser/explorerService.ts pushes every onDidFilesChange event into fileChangeEvents and drains the array from a 500 ms RunOnceScheduler; the same service also unconditionally refreshes when window focus returns. This provides a plausible accumulation path when Chromium throttles renderer timers for minimized windows, but the minified trace does not conclusively attribute the entire long task to ExplorerService. The plan should first correlate the restore-time task with ExplorerService event counts and refreshes on Windows. Preserve correct Explorer reconciliation and normal focused-window update latency; extension-host processing and unrelated animation-frame consumers are outside the change unless profiling identifies them as the actual owner.

## Evidence

- **performance trace:** The trace attached at https://github.com/microsoft/vscode/issues/316769#issuecomment-4531616503 records a 1.56-second renderer-main-thread task containing a 1.47-second animation-frame callback, matching the reported restore-time UI freeze; its CPU profile also contains substantial tree rendering and DOM-update work.
- **current source:** On current main, src/vs/workbench/contrib/files/browser/explorerService.ts appends every IFileService.onDidFilesChange event to fileChangeEvents, while a RunOnceScheduler processes that array after a 500 ms timer. Minimized-window timer throttling can therefore leave many events for one restore-time pass.
- **reported trigger:** The report provides explicit steps on Windows: keep the Explorer visible, repeatedly create and delete a workspace file externally, minimize for a period, then restore; the claimed freeze duration scales with time minimized.

The reporter did not provide an Extension Bisect result, but the captured renderer stall and the matching core Explorer backlog path mean there is not enough evidence for *caused-by-extension or *not-reproducible.
