# Issue #47976 — Feature: Settable "keyboard.chords.mode"

[https://github.com/microsoft/vscode/issues/47976](https://github.com/microsoft/vscode/issues/47976)

## Summary

Keep open: current source provides a terminal-specific chord setting, but not the application-wide opt-out requested for accessibility. The existing keybindings routing is appropriate, and no verified older canonical issue was found.

## Change summary

Provide a simple application-wide option to disable sequential keybinding chords without individually removing conflicting bindings.

## Best solution

Define an opt-in chord-disabled mode that preserves ordinary single-step shortcuts and leaves current behavior unchanged by default. Treat the original continuous-modifier proposal as optional design background, since the reporter explicitly accepts a simple on/off solution.

- **Likely files:** `src/vs/platform/keyboardLayout/common/keyboardConfig.ts`, `src/vs/platform/keybinding/common/keybindingResolver.ts`, `src/vs/platform/keybinding/common/abstractKeybindingService.ts`, `src/vs/workbench/services/keybinding/browser/keybindingService.ts`, `src/vs/platform/keybinding/test/common/keybindingResolver.test.ts`, `src/vs/platform/keybinding/test/common/abstractKeybindingService.test.ts`
- **Validation:** Extend the keybinding resolver and dispatch suites to cover a single-step binding sharing a prefix with a sequential binding: disabled mode must not enter chord-waiting state, the agreed single-step behavior must occur, and default mode must retain existing dispatch behavior. Include default, extension-contributed, and user-defined sequences, and verify that changing the setting takes effect without restarting.
- **Behavior:**

  > Users who find sequential chord handling inaccessible can opt out globally without editing every conflicting keybinding. Current chord behavior remains the default, and ordinary single-step shortcuts remain usable. Acceptance checks must cover shared prefixes, prefixes with no single-step command, and immediate application of a setting change. The reporter accepts an on/off option; continuous-modifier handling is not required to satisfy the central request.
- **Trace:**

  > Current keyboard configuration in src/vs/platform/keyboardLayout/common/keyboardConfig.ts covers dispatch representation and AltGr mapping, not global chord availability. KeybindingResolver.resolve selects matching bindings and reports MoreChordsNeeded for incomplete sequences; AbstractKeybindingService._doDispatch then consumes the event and enters chord mode. terminal.integrated.allowChords is handled separately by TerminalInstance and only addresses terminal event handling, so it does not cover the global request. Existing resolver and abstract service tests provide a validation surface. Preserve default resolution ordering and existing terminal settings; uncertainty begins with the public semantics of disabling sequences, not with which helper or file should implement them. https://github.com/microsoft/vscode/issues/140226 describes related prefix fallback behavior but is neither an older canonical nor equivalent work.
- **Open decisions:**
  - Should disabled mode suppress all sequential bindings, including explicitly user-defined sequences and repeated-modifier shortcuts, or permit user-defined exceptions?
  - When a disabled sequential binding shares its prefix with a lower-priority single-step binding, should that single-step command execute, or should the key be left to the focused control?
