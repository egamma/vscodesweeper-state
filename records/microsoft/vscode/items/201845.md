# Issue #201845 — Cannot reliably get editors associated with diff editor tab

[https://github.com/microsoft/vscode/issues/201845](https://github.com/microsoft/vscode/issues/201845)

## Summary

The API gap remains on current main: diff-editor child TextEditors still have no group or tab identity, so identical diffs opened in multiple groups cannot be disambiguated. The accepted Backlog bug should remain open while the public API contract is designed.

## Change summary

Extensions cannot reliably identify which visible TextEditors belong to a particular diff-editor tab when the same resources are diffed in multiple groups.

## Best solution

Expose a stable, group-aware association between a diff Tab and its original and modified TextEditors, allowing extensions to resolve the editors for the active tab even after focus moves elsewhere. The API owner should first decide whether this belongs in TextEditor.viewColumn semantics or in an explicit tab-to-editor relationship.

- **Validation:** Add an API unit test with the same original/modified URI pair open as two diff tabs in separate groups, move focus to a non-diff editor, and assert that the chosen API contract uniquely resolves the original and modified TextEditors belonging to the active diff tab.
- **Behavior:**

  > An extension can take a specific text-diff Tab and reliably identify its original and modified TextEditors, even when another group displays an identical diff and focus has moved to an output editor. The association must remain correct as groups activate, move, and close. Existing single-resource editor and tab behavior must remain compatible.
- **Trace:**

  > TabInputTextDiff in src/vscode-dts/vscode.d.ts exposes only the two resource URIs. MainThreadTextEditors._getTextEditorPositionData in src/vs/workbench/api/browser/mainThreadEditors.ts derives view columns by matching each visible IEditorPane through MainThreadTextEditor.matches; that method compares the pane control directly with a child ICodeEditor, which fails for composite diff controls. Consequently both child TextEditors retain undefined viewColumn, and URI matching cannot distinguish duplicated diff instances. The related discussion at https://github.com/microsoft/vscode/issues/15513#issuecomment-1245693792 describes the same remaining limitation. Preserve the documented treatment of unrelated embedded editors and avoid changing activeTextEditor focus semantics; uncertainty begins at the public API shape used to expose the relationship.
- **Open decisions:**
  - Should TextEditor.viewColumn report the containing editor group's column for diff-editor children, changing the documented embedded-editor behavior, or should the Tabs API expose an explicit association with the constituent TextEditors?

## Evidence

- **source reproduction:** src/vs/workbench/api/browser/mainThreadEditors.ts::_getTextEditorPositionData iterates visible editor panes and assigns a group column only when findTextEditorIdFor(editorPane) returns an editor ID.
- **root cause:** src/vs/workbench/api/browser/mainThreadEditor.ts::MainThreadTextEditor.matches compares editor.getControl() directly with the child ICodeEditor. A diff pane's control is the composite diff editor rather than either child code editor, so neither child receives position data.
- **public API limitation:** src/vscode-dts/vscode.d.ts documents TextEditor.viewColumn as undefined for embedded editors, while TabInputTextDiff exposes only original and modified URIs. Those values cannot distinguish two tabs showing the same URI pair.
- **related precedent:** https://github.com/microsoft/vscode/issues/15513 was closed after TabInputTextDiff provided URI-level detection, but https://github.com/microsoft/vscode/issues/15513#issuecomment-1245693792 explicitly identified the unresolved inability to associate a particular TextEditor with a particular diff instance.
- **no canonical or fix:** The canonical search found no open issue owning this exact observable symptom, and the current source still contains the ambiguous path.
