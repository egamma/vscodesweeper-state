# Issue #317534 — BYOK Azure Foundry /responses fails with invalid input type (input[n].type)

[https://github.com/microsoft/vscode/issues/317534](https://github.com/microsoft/vscode/issues/317534)

## Summary

Fixed on main: the Azure BYOK Entra-auth path now detects `/responses` URLs and sets `supported_endpoints` so a Responses-shaped body (`input`) is sent instead of a Chat Completions body (`messages`). The fix landed in commit 9b0c342101e (PR #322845) but has not yet shipped in a stable release.

## Change summary

BYOK Azure Foundry `/responses` endpoint fails because the Entra-auth code path sends a Chat Completions body (`messages`) instead of the Responses API body (`input`).

## Evidence

- **fix commit:** Fixed in https://github.com/microsoft/vscode/commit/9b0c342101ed0dfc07a137403c0d22c2a1242dc5 (PR https://github.com/microsoft/vscode/pull/322845), which adds `azureSupportedEndpointsForUrl()` to detect when the resolved Azure URL targets `/responses` and sets `supported_endpoints` accordingly on the Entra-auth path, so a Responses-shaped body is sent instead of the Chat Completions body that Azure Responses rejects.
- **root cause:** The `provideLanguageModelChatResponse` override in `AzureBYOKModelProvider` (Entra-auth path) constructed `modelInfo` without `supported_endpoints`, so the downstream code always sent a Chat Completions body (`messages` array). The Responses API expects `input` with typed items like `input_text`, causing the 400 error.
- **code reference:** extensions/copilot/src/extension/byok/vscode-node/azureProvider.ts — the fix adds lines 54–69 (`azureSupportedEndpointsForUrl`) and lines 148–152 (applying `supported_endpoints` in the Entra path).
- **commenter workaround:** Comment by cf-rdegregory confirms the workaround: use the Azure OpenAI endpoint (`openai.azure.com`) instead of the Foundry project endpoint (`services.ai.azure.com`), which takes the API-key path where `supported_endpoints` was already handled.
