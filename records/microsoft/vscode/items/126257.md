# Issue #126257 — function "setBreakPointsRequest" in the Debug Adapter is triggered to much

[https://github.com/microsoft/vscode/issues/126257](https://github.com/microsoft/vscode/issues/126257)

## Summary

Thanks for the report. This remains a valid debug API batching bug: one bulk `vscode.debug.removeBreakpoints()` call produces one Debug Adapter Protocol `setBreakpoints` request per removed breakpoint, causing unnecessary repeated synchronization.

## Change summary

Batch breakpoint-removal notifications so removing several breakpoints in one API call results in one `setBreakpoints` request per affected source rather than one request per breakpoint.

## Best solution

Coalesce the breakpoint model updates produced by one bulk extension API removal and synchronize each affected source once, while preserving individual breakpoint-change events and correct handling across multiple source files.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostDebugService.ts`, `src/vs/workbench/api/browser/mainThreadDebugService.ts`, `src/vs/workbench/contrib/debug/common/debugModel.ts`, `src/vs/workbench/contrib/debug/browser/debugService.ts`
- **Validation:** Add an extension-host/debug-service regression test that removes multiple breakpoints from one source in a single `vscode.debug.removeBreakpoints()` call and asserts exactly one `setBreakpoints` request for that source; also verify removals spanning two sources produce exactly one request per source.
- **Behavior:**

  > A single `vscode.debug.removeBreakpoints()` call may remove several breakpoints. The debug adapter must receive at most one resulting `setBreakpoints` request for each affected source, containing that source's final breakpoint set, rather than one intermediate request per removed breakpoint. Removing breakpoints from different source files must still synchronize each affected source, and public breakpoint-change notifications must remain correct.
- **Trace:**

  > The extension API call originates in `src/vs/workbench/api/common/extHostDebugService.ts`, crosses `src/vs/workbench/api/browser/mainThreadDebugService.ts`, updates the breakpoint model in `src/vs/workbench/contrib/debug/common/debugModel.ts`, and ultimately drives adapter synchronization through `src/vs/workbench/contrib/debug/browser/debugService.ts`. The reporter observed one adapter request per breakpoint, and the debug maintainer explicitly confirmed that one bulk API call should not behave that way in https://github.com/microsoft/vscode/issues/126257#issuecomment-860770270. The plan should trace where collection removal becomes repeated model-change notifications and establish the batching boundary without changing the Debug Adapter Protocol's per-source `setBreakpoints` replacement semantics or suppressing extension-facing breakpoint events.
