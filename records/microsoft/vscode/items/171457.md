# Issue #171457 — Allow line specific word wrap toggling

[https://github.com/microsoft/vscode/issues/171457](https://github.com/microsoft/vscode/issues/171457)

## Summary

This remains a valid backlog feature with strong community demand: current main supports only editor-wide wrapping, while the requested per-line exclusion is still missing. The related language-aware wrapping issue overlaps technically but does not cover the manual, language-independent behavior requested here.

## Change summary

Allow selected lines or ranges to remain unwrapped while word wrapping continues elsewhere in the same editor.

## Best solution

Define an editor-level per-line wrapping contract that preserves mixed horizontal scrolling and tracks selected ranges as the document changes, while coordinating the underlying projection work with https://github.com/microsoft/vscode/issues/164267.

## Plan brief

- **Likely files:** `src/vs/editor/common/modelLineProjectionData.ts`, `src/vs/editor/common/viewModel/viewModelLines.ts`, `src/vs/editor/common/viewModel/monospaceLineBreaksComputer.ts`, `src/vs/editor/browser/view/domLineBreaksComputer.ts`, `src/vs/workbench/contrib/codeEditor/browser/toggleWordWrap.ts`, `src/vs/editor/test/browser/viewModel/modelLineProjection.test.ts`
- **Validation:** Add editor view-model tests with wrapping enabled that assert an excluded line remains one view line while adjacent long lines wrap, the mixed document exposes horizontal scrolling, and the exclusion follows its content through line insertions and deletions.
- **Behavior:**

  > With word wrap enabled, users can mark selected lines as unwrapped without changing wrapping elsewhere in the document. Unwrapped lines remain horizontally scrollable, adjacent lines continue wrapping normally, and the marked range follows its content as edits move it. Existing whole-editor word-wrap settings and Toggle Word Wrap behavior remain unchanged for documents without per-line state.
- **Trace:**

  > Wrapping is currently model-wide: `ViewModelLinesFromProjectedModel.createLineBreaksComputer` in src/vs/editor/common/viewModel/viewModelLines.ts supplies one `wrappingColumn` to each factory, while `ILineBreaksComputer.addRequest` in src/vs/editor/common/modelLineProjectionData.ts carries only a line number and previous projection data. Both the monospace and DOM line-break computers therefore calculate every requested line under the same wrapping configuration. The existing command in src/vs/workbench/contrib/codeEditor/browser/toggleWordWrap.ts stores a transient whole-model override. Keep ordinary editor wrapping, diff-editor synchronization, and documents without line-specific state unchanged. https://github.com/microsoft/vscode/issues/164267 shares the projection requirement but asks for automatic language-aware behavior; https://github.com/microsoft/vscode/issues/184086 establishes this issue as the canonical tracker for selectively preserving table lines.
- **Open decisions:**
  - Should line-specific wrapping state be transient for the current model session, or persist when the document or workspace is reopened?

## Evidence

- **current source:** src/vs/editor/common/viewModel/viewModelLines.ts passes one model-wide `wrappingColumn` and `wrappingIndent` into the line-break computer; src/vs/editor/common/modelLineProjectionData.ts exposes no per-line wrapping override in `ILineBreaksComputerContext` or `addRequest`.
- **existing command:** src/vs/workbench/contrib/codeEditor/browser/toggleWordWrap.ts implements `editor.action.toggleWordWrap` by applying a transient option to the entire text model, not the selected lines.
- **community demand:** The issue has 47 upvotes and was explicitly promoted to the Backlog after exceeding the 20-upvote threshold.
- **canonical role:** https://github.com/microsoft/vscode/issues/184086 was closed by a maintainer as a duplicate of this issue for the Markdown-table case.
- **related but distinct:** https://github.com/microsoft/vscode/issues/164267 remains open for automatic language-aware wrapping, particularly hanging indentation for Markdown lists; it does not fully own this issue's manual, arbitrary line-selection behavior.
