# Issue #347405 — Spaces in ProxyCommand Break Agents

[https://github.com/microsoft/vscode/issues/347405](https://github.com/microsoft/vscode/issues/347405)

## Summary

Keep open: the merged change improves ProxyCommand failure reporting, not execution of Windows paths containing spaces. The supplied configuration and error suffice to retest; Windows connection parity remains unverified.

## Change summary

Agents Window fails to execute a Windows SSH ProxyCommand whose executable path contains spaces, although the same configuration works with Remote-SSH.

## Best solution

Preserve compatibility with working Windows OpenSSH ProxyCommands in the agent-host connection path, including executable paths containing spaces, without requiring SSH configuration edits.

- **Behavior:**

  > A Windows SSH configuration that successfully connects through OpenSSH should also connect through Agents Window when its ProxyCommand executable resides in a path containing spaces and parentheses. Acceptance requires the same configuration to launch the intended executable and complete the SSH handshake in both clients. Existing quoted commands, command arguments, token substitution, and meaningful failure diagnostics must remain functional.
- **Trace:**

  > SSHRemoteAgentHostMainService resolves the host with ssh -G, and parseSSHGOutput in common/sshConfigParsing.ts preserves the proxycommand string. The connection path passes it through expandSSHProxyCommand into SSHProxyCommand in node/sshProxyCommand.ts, whose constructor executes the command using spawn with shell: true. Literal executable paths are not normalized by the expansion function, matching the reporter's C:\Program shell error, but the precise Windows OpenSSH launch semantics have not been compared. https://github.com/microsoft/vscode/pull/349272 improves diagnostics only and must not be treated as the execution fix. Establish parity on Windows first; preserve existing command arguments, substitution protections, process cleanup, and non-Windows behavior.
