# Issue #177660 — Git - Prompt to stash or rebase uncommitted changes on checkout

[https://github.com/microsoft/vscode/issues/177660](https://github.com/microsoft/vscode/issues/177660)

## Summary

Keep this accepted Git feature request open: checkout currently offers stash/migrate choices only when local changes would be overwritten, not the proactive leave-or-bring workflow requested here. It has 22 upvotes, and no eligible older open canonical was found.

## Change summary

Offer a choice to leave uncommitted changes on the current branch or bring them to the destination when switching branches.

## Best solution

Extend the built-in Git checkout experience to support an explicit leave-or-bring choice even when Git could carry changes across without a conflict. Settle prompt defaults and branch-return restoration semantics before implementation, preserving existing checkout safeguards.

## Plan brief

- **Likely files:** `extensions/git/src/commands.ts`, `extensions/git/src/repository.ts`, `extensions/git/package.json`, `extensions/git/package.nls.json`
- **Validation:** After deciding the product contract, use a disposable Git repository with two branches and compatible uncommitted edits: switch through the branch picker, exercise both leave and bring choices, and switch back to verify the chosen restoration behavior and preservation of edits. Repeat with changes that would be overwritten, cancel the prompt, and check that clean checkouts and existing conflict safeguards remain unchanged.
- **Behavior:**

  > Users switching branches with uncommitted changes should be able to choose whether those changes remain associated with the source branch or accompany them to the destination, including when Git would otherwise complete checkout without prompting. The leave path must preserve the edits for later recovery, and the bring path must retain them on the destination without silent loss. Acceptance covers compatible edits, checkout-blocking edits, cancellation, and a return to the original branch. Prompt defaults and the return-branch recovery experience require a maintainer decision.
- **Trace:**

  > Commands._checkout in extensions/git/src/commands.ts runs CheckoutItem.run before offering any stash/migrate choice; that choice exists only in its DirtyWorkTree error handler. The existing migrate path uses _stash(repository, true), retries checkout, and invokes stashPopLatest, whereas the stash path leaves the stash unapplied. Repository.checkout in extensions/git/src/repository.ts delegates directly to the Git layer and does not provide branch-associated stash restoration. The git.autoStash registration describes pull behavior, not this workflow. Preserve ordinary clean checkout, existing overwrite protections, and unrelated pull semantics. https://github.com/microsoft/vscode/issues/86668 supplies the earlier branch-return use case but is closed; https://github.com/microsoft/vscode/issues/240571 concerns automatic stash/pop, and https://github.com/microsoft/vscode/issues/249087 concerns the explicit-treeish command path rather than this feature's full scope.
- **Open decisions:**
  - Should the leave-or-bring prompt appear by default for every branch switch with uncommitted changes, or only when the user opts into that workflow?
  - When returning to a branch whose changes were left behind, should VS Code automatically restore them or offer an explicit restore action?
