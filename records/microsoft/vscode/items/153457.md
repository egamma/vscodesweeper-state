# Issue #153457 — Profiles: Workbench startup scaffolding should take profile into account

[https://github.com/microsoft/vscode/issues/153457](https://github.com/microsoft/vscode/issues/153457)

## Summary

The defect remains source-reproducible on current main: startup scaffolding reads and writes one global splash color record even though the window configuration already identifies the active profile. The accepted Backlog bug should remain open for profile-aware splash persistence.

## Change summary

Opening a workspace with a profile whose theme differs from the previously active profile briefly renders startup scaffolding in the wrong colors.

## Best solution

Persist and retrieve startup splash colors using the effective window profile so each profile starts with its own theme colors, while retaining a safe fallback for profiles without saved splash state.

## Plan brief

- **Likely files:** `src/vs/platform/theme/electron-main/themeMainService.ts`, `src/vs/platform/theme/electron-main/themeMainServiceImpl.ts`, `src/vs/platform/native/electron-main/nativeHostMainService.ts`, `src/vs/platform/windows/electron-main/windowImpl.ts`
- **Validation:** Add coverage that saves distinct light and dark `IPartsSplash` values for two profiles and retrieves the matching value for each profile; then manually open the same workspace under alternating profiles and verify the pre-workbench scaffolding immediately uses each profile's theme colors.
- **Behavior:**

  > When a workspace opens under a profile, its startup scaffolding must use colors saved from that profile rather than colors last saved by another profile. Alternating between profiles with visibly different themes must not produce a wrong-color startup flash. A new profile without saved splash state must still receive a valid fallback, and startup behavior outside profiles must remain functional.
- **Trace:**

  > Current main stores splash data globally in `ThemeMainService.saveWindowSplash` and reads it globally in `ThemeMainService.doGetWindowSplash` within src/vs/platform/theme/electron-main/themeMainServiceImpl.ts. Startup retrieval in src/vs/platform/windows/electron-main/windowImpl.ts passes only the workspace to `getWindowSplash`, although `configuration.profiles.profile` and the window's resolved `profile` are available. The renderer-to-main save path reaches src/vs/platform/native/electron-main/nativeHostMainService.ts, where the window and its profile are also available but only the workspace is forwarded. Preserve workspace-specific layout overrides, automatic high-contrast handling, transient-profile behavior, and fallback startup colors; the reported boundary is profile-specific color selection, not a redesign of splash layout persistence.

## Evidence

- **global splash storage:** src/vs/platform/theme/electron-main/themeMainServiceImpl.ts defines the single `windowSplash` state key; `saveWindowSplash` stores every window's `IPartsSplash` under that key, and `doGetWindowSplash` reads the same global value without a profile identifier.
- **startup retrieval path:** src/vs/platform/windows/electron-main/windowImpl.ts sets `configuration.partsSplash` through `themeMainService.getWindowSplash(configuration.workspace)`. The call supplies only the workspace even though the same window configuration carries `profiles.profile`.
- **save path:** src/vs/platform/native/electron-main/nativeHostMainService.ts forwards `windowId`, `window.openedWorkspace`, and the splash to ThemeMainService, but not `window.profile`; consequently a profile's theme change overwrites the startup colors subsequently used by other profiles.
- **maintainer direction:** The issue discussion confirms that the specially stored state needs profile-aware treatment, and the issue remains accepted as `bug` in the Backlog milestone.
- **canonical search:** Repository issue searches for profile startup scaffolding, wrong startup colors, and profile base colors found no separate open issue owning this behavior; the mechanical candidate https://github.com/microsoft/vscode/issues/3130 concerns mouse shortcut customization and is unrelated.
