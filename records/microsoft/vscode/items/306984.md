# Issue #306984 — Starting from version 1.108.2 and later, the focus outline no longer appears when clicking with the mouse or when the focus is placed on "Explore."

[https://github.com/microsoft/vscode/issues/306984](https://github.com/microsoft/vscode/issues/306984)

## Summary

Current main still omits the list-container focus indicator in standard themes when the Explorer has focus but no row is focused. The issue is already accepted as a bug, and the reporter established that the change prevents keyboard users from locating focus, so it should remain open for an accessibility-conscious design decision.

## Change summary

Restore a visible indication that the Explorer has focus when focus lands on the list without a focused row.

## Best solution

Ensure keyboard- or command-initiated focus on the Explorer remains visibly identifiable in standard themes, including when no row has focus. Maintainers should decide whether pointer-acquired focus should show the same container outline or retain the cleaner mouse presentation.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/media/style.css`, `src/vs/base/browser/ui/list/listWidget.ts`
- **Validation:** Run Code OSS with default dark and light themes: focus the Explorer through its focus command when no row is focused and verify a visible focus indicator; click the list background and then navigate by keyboard to verify the maintainer-selected pointer/keyboard behavior; confirm focused rows and both high-contrast themes retain their existing indicators.
- **Behavior:**

  > When keyboard navigation or a focus command moves focus to the Explorer, users must have a visible indication of where focus resides even if no file row is focused. Focused-row styling and high-contrast behavior must remain intact. Acceptance should cover default dark and light themes, command-initiated focus with no focused row, and keyboard navigation after mouse-acquired focus.
- **Trace:**

  > Merged PR https://github.com/microsoft/vscode/pull/296799 restricted the no-focused-item list outline in src/vs/workbench/browser/media/style.css to high-contrast themes, and that restriction remains on current main. List._onFocusChange in src/vs/base/browser/ui/list/listWidget.ts toggles `element-focused` based on whether a row has focus, so a focused Explorer without a focused row depends on that now-HC-only container rule. Closed, unmerged PR https://github.com/microsoft/vscode/pull/295855 established that a plain `:focus-visible` conversion does not handle keyboard navigation following a mouse click. Keep the scope to focus indication and input modality; do not alter Explorer selection, row focus, or navigation semantics.
- **Open decisions:**
  - Should standard themes show the Explorer container indicator for every focused-without-row state, including pointer focus, or only for keyboard/programmatic focus while suppressing it for pointer-only interaction?

- **introducing change:** Merged PR https://github.com/microsoft/vscode/pull/296799 and commit https://github.com/microsoft/vscode/commit/1518251bd38143ce795e8b006f2611dd9c99e88c changed the generic `.monaco-list:not(.element-focused):not(:active):focus:before` rule to apply only under `.hc-black` and `.hc-light`, explicitly removing the container outline from standard themes.
