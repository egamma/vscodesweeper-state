# Issue #174295 — Multiple Import Organizers results in corrupted code

[https://github.com/microsoft/vscode/issues/174295](https://github.com/microsoft/vscode/issues/174295)

## Summary

Still reproduces on main: multiple code action providers for the same kind (e.g. source.organizeImports) all receive the pre-edit document state, so applying the second provider's edits against stale content corrupts the file. Author is a team member — keeping open.

## Change summary

When multiple extensions register code actions for the same kind (e.g. source.organizeImports), on-save execution fetches all actions against the initial document state and applies them sequentially, corrupting the file because later actions' edits are stale.

## Best solution

In `applyOnSaveActions` in `src/vs/workbench/contrib/codeEditor/browser/saveParticipants.ts`, after applying each code action that mutates the document (detected via `model.getVersionId()`), re-fetch remaining code actions for the same kind against the fresh document state — cascading edits rather than batching them. The same fix is needed in the notebook save participants at `src/vs/workbench/contrib/notebook/browser/contrib/saveParticipants/saveParticipants.ts`. PR https://github.com/microsoft/vscode/pull/306045 attempted this approach but was closed without merging; its design (break-and-re-evaluate on version change with a loop limit) is sound.

When multiple providers respond to the same kind (e.g. isort and ruff both providing source.organizeImports), the second provider's WorkspaceEdit was computed against the pre-first-edit document, so applying it corrupts the file. Do NOT change the outer loop over different code action kinds — only the inner loop for actions within a single kind needs cascading.
