# Issue #336878 — File list grows too eagerly when widening the main pane

[https://github.com/microsoft/vscode/issues/336878](https://github.com/microsoft/vscode/issues/336878)

## Summary

Fresh, team-authored (MEMBER) layout bug in the Agents window with a private screen recording as evidence; I traced the relevant sizing code but couldn't pin the exact mechanism causing the file list to grow prematurely, so this stays open for diagnosis rather than needs-info (team-authored hard keep-open rule applies).

## Change summary

Widening the Agents window's main editor pane also expands the file list (detail panel) too early, instead of the file list staying near its current width until the main pane is already sufficiently wide (~1000px).

## Best solution

Reproduce which layout path is responsible (single-pane docked detail panel vs. classic Grid) and adjust the width formula so the file list/auxiliary bar only grows once the main pane exceeds a reasonable threshold, consistent with the existing intent that SessionsPart/EditorPart absorb resize deltas while the auxiliary bar stays low priority.

## Plan brief

- **Likely files:** `src/vs/sessions/browser/dockedAuxiliaryBarController.ts`, `src/vs/sessions/browser/parts/editorPart.ts`, `src/vs/sessions/browser/parts/auxiliaryBarPart.ts`, `src/vs/sessions/browser/workbench.ts`

- **Behavior:**

  > When the Agents window's main pane is widened (via window resize or sash drag), the file list (detail panel / auxiliary bar showing Changes and Files) should keep its current width and only start growing once the main pane already has ample width (the reporter suggests roughly 1000px). Currently the file list starts expanding too early, competing with the main pane for newly available horizontal space. Acceptance: widening the window/sash keeps the file list width stable below the threshold and lets it grow only past it; existing resize/collapse/reset sash behavior for the detail panel is unchanged.
- **Trace:**

  > The single-pane docked detail panel's width comes from `DockedAuxiliaryBarController.getEffectiveWidth(hostWidth, editorWidth)` in src/vs/sessions/browser/dockedAuxiliaryBarController.ts, which clamps to the user's stored width (`IDockedAuxiliaryBarHost.getWidth()`) between `MIN_WIDTH`(220) and `editorWidth - EDITOR_MIN_WIDTH`(300); on paper this holds the panel width constant as editorWidth grows, so it doesn't obviously explain the report. The classic (non-single-pane) layout instead relies on `LayoutPriority` in the top-level workbench SplitView — `SessionsPart` (High, unbounded max, src/vs/sessions/browser/parts/sessionsPart.ts), `MainEditorPart` (Normal, src/vs/sessions/browser/parts/editorPart.ts, explicitly commented as intentionally NOT absorbing resize deltas), and `AuxiliaryBarPart` (Low, src/vs/sessions/browser/parts/auxiliaryBarPart.ts). `DOCK_DETAIL_PANEL_SETTING` defaults to `true` (src/vs/sessions/contrib/layout/browser/sessions.layout.contribution.ts), so the reporter is most likely on the single-pane path. First step is reproducing interactively (window resize vs. sash drag) to identify which formula/path is actually responsible before touching either; do not change the documented SessionsPart(High)/EditorPart(Normal)/AuxiliaryBar(Low) priority intent without confirming the real cause first.
- **Open decisions:**
  - Which layout mode reproduces the bug: the single-pane docked detail panel (default), the classic Grid layout, or both?
  - Is the trigger an overall window resize (distributeEmptySpace) or a specific sash drag (direct two-view resize)?
  - What should the exact width/threshold formula be (e.g. a fixed ~1000px main-pane width, or a ratio), and should it be configurable?

## Evidence

- **docked panel width formula:** src/vs/sessions/browser/dockedAuxiliaryBarController.ts `getEffectiveWidth(hostWidth, editorWidth)` clamps the panel width to the user's stored width between MIN_WIDTH(220) and editorWidth-EDITOR_MIN_WIDTH(300); as read, this should keep the panel width constant as editorWidth grows, so the reported premature growth isn't obviously explained by this path alone.
- **classic layout priorities:** src/vs/sessions/browser/parts/editorPart.ts sets `priority = LayoutPriority.Normal` with a comment that SessionsPart is the LayoutPriority.High 'flexible view' meant to absorb resize deltas, while src/vs/sessions/browser/parts/auxiliaryBarPart.ts is LayoutPriority.Low — these priorities look intended to prevent the auxiliary bar (file list) from growing on window widen, but I couldn't confirm from source alone why the reported behavior deviates.
- **default layout mode:** src/vs/sessions/contrib/layout/browser/sessions.layout.contribution.ts sets DOCK_DETAIL_PANEL_SETTING default: true (tagged experimental), so the reporter is very likely hitting the single-pane docked auxiliary bar path rather than the classic Grid layout.
