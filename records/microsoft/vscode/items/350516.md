# Issue #350516 — VSCode does not respect selected GNOME keyboard layout when using Ctrl modifier

[https://github.com/microsoft/vscode/issues/350516](https://github.com/microsoft/vscode/issues/350516)

## Summary

The supplied steps suffice to retest incorrect shortcut dispatch with GNOME's second layout selected. Current source still relies on native-keymap; the report does not establish whether the window uses Wayland or XWayland, so neither a fix nor a canonical duplicate is confirmed.

## Change summary

Ctrl-modified shortcuts use GNOME's first configured layout instead of the selected layout, while ordinary typing remains correct.

## Best solution

Ensure shortcut matching follows the active GNOME layout at startup and after switching layouts. First compare native layout data with renderer keyboard events under Wayland and XWayland to establish whether this belongs to the existing Wayland detection defect or a distinct regression.

- **Behavior:**

  > With GNOME configured for Dvorak followed by US and US selected before launch, Ctrl+Shift+P should open the Command Palette, not select highlights. Shortcut matching should remain consistent with the selected layout when switching between the two layouts. Ordinary text input and explicitly scan-code-bound shortcuts must retain their existing behavior.
- **Trace:**

  > KeyboardLayoutMainService reads the mapping and active layout from native-keymap; NativeKeyboardLayoutService transfers that data to the renderer, where KeyboardLayoutService constructs MacLinuxKeyboardMapper. The mapper resolves keyboard events by scan code, so a stale or mismatched native map can affect shortcuts independently of text input. Source inspection establishes that dependency path, not the actual failing GNOME backend. https://github.com/microsoft/vscode/issues/127932 documents the Wayland/XWayland mismatch, while https://github.com/microsoft/vscode/issues/24166 records an older startup-group defect that was fixed. Start by reproducing the supplied layout order and comparing reported layout groups and event mappings across window backends; do not assume GNOME implies a native-Wayland VS Code window. Preserve default dispatch semantics and avoid treating a keyCode workaround or dependency-version change as proof of resolution.

## Evidence

- **Complete reproduction:** https://github.com/microsoft/vscode/issues/350516 specifies VS Code 1.119.0, NixOS and GNOME versions, extensions disabled, Dvorak-first/US-second layout order, and Ctrl+Shift+P selecting highlights instead of opening the Command Palette.
- **Current native layout path:** src/vs/platform/keyboardLayout/electron-main/keyboardLayoutMainService.ts reads native-keymap.getKeyMap() and getCurrentKeyboardLayout(), refreshing them through the native layout-change callback. src/vs/workbench/services/keybinding/electron-browser/nativeKeyboardLayoutService.ts forwards those mappings to the renderer.
- **Shortcut dispatch boundary:** src/vs/workbench/services/keybinding/electron-browser/nativeKeyboardLayout.ts constructs MacLinuxKeyboardMapper from the native mapping and leaves validateCurrentKeyboardMapping() empty. src/vs/workbench/services/keybinding/common/macLinuxKeyboardMapper.ts resolves keyboard events using their scan code. This explains how typing and shortcuts can diverge, but does not conclusively reproduce the reported environment.
- **Related Wayland diagnosis:** https://github.com/microsoft/vscode/issues/127932 is open. The maintainer explanation at https://github.com/microsoft/vscode/issues/127932#issuecomment-7168773285 identifies XWayland-versus-compositor keymap mismatches and an unintegrated Wayland prototype with a first-layout limitation. This is a strong lead, not a verified duplicate without establishing this reporter's window backend.
- **Reporter-linked issue:** https://github.com/microsoft/vscode/issues/327045 remains open; https://github.com/microsoft/vscode/issues/327045#issuecomment-7175430278 connects its native-Wayland shortcut failure to the native-keymap mismatch. Unlike that report, this issue does not include a Wayland/XWayland comparison.
- **Other candidates do not establish coverage:** https://github.com/microsoft/vscode/issues/331091 requests a manual Linux layout override; https://github.com/microsoft/vscode/issues/137401 concerns Windows shortcut labels and searching; https://github.com/microsoft/vscode/issues/23991 concerns setxkbmap remappings. The matching historical startup-layout issue https://github.com/microsoft/vscode/issues/24166 is closed, so it cannot serve as a duplicate canonical or prove this current report fixed.
- **Existing workaround is not resolution:** src/vs/platform/keyboardLayout/common/keyboardConfig.ts registers keyboard.dispatch with default code and optional keyCode. That changes dispatch strategy rather than ensuring active-layout detection; the discussion in https://github.com/microsoft/vscode/issues/127932 documents layout-dependent limitations.
