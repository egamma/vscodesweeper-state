# Issue #250423 — MCP resource templates need better UI

[https://github.com/microsoft/vscode/issues/250423](https://github.com/microsoft/vscode/issues/250423)

## Summary

The resource-template workflow still collects variables through sequential QuickPick inputs; server completions do not address the requested stable editing experience. Keep this accepted Backlog request open for a maintainer-led UX decision.

## Change summary

Make filling MCP resource templates practical for everyday use, with a stable editing surface and contextual completions.

## Best solution

Provide a coherent resource-template editing experience that preserves context across variables and retains server-provided completions. Decide the interaction model before implementation; editor/snippet-based input and workspace-derived suggestions remain proposals, not settled requirements.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/mcp/browser/mcpResourceQuickAccess.ts`
- **Validation:** With a test MCP server exposing a multi-variable resource template and context-dependent completions, fill the template through the chosen interaction, revise an earlier value, and verify that subsequent suggestions use the revised context and the resolved resource opens or attaches correctly. Also check keyboard-only completion, cancellation, and optional-variable entry.
- **Behavior:**

  > Filling a multi-variable MCP resource template should retain enough visible context to be practical for repeated everyday use. Users should be able to enter and revise values while receiving server-provided suggestions informed by the other resolved variables. Acceptance should cover a GitHub-style repository/PR template, successful opening or attachment of the resolved resource, cancellation, and keyboard-only operation. The precise editing surface requires agreement before implementation.
- **Trace:**

  > McpResourcePickHelper in src/vs/workbench/contrib/mcp/browser/mcpResourceQuickAccess.ts owns both template-to-URI and template-to-attachment entry paths. _resourceTemplateToURI flattens template variables and prompts for them sequentially through one QuickPick; _promptForTemplateValue resets its contents for every variable and calls rt.complete with variablesSoFar. This confirms that existing completions do not replace the interaction criticized at https://github.com/microsoft/vscode/issues/250423. Preserve URI-template semantics, context-dependent server completions, cancellation, and resource opening/attachment behavior. The uncertainty is the desired user-facing editing model, not whether the current code already implements an editor-based flow.
- **Open decisions:**
  - Should resource templates be filled in a persistent editor/snippet surface, or should the existing QuickPick interaction be redesigned to provide revisitable fields and persistent context?
  - Should workspace-derived values be offered as explicit suggestions, or should this iteration remain limited to user-entered values and MCP-server completions?

## Evidence

- **Current resource-template flow:** src/vs/workbench/contrib/mcp/browser/mcpResourceQuickAccess.ts, McpResourcePickHelper._resourceTemplateToURI, creates a QuickPick and awaits _promptForTemplateValue separately for each template variable. _promptForTemplateValue clears the input and items for each variable and displays the partially resolved URI in its placeholder.
- **Existing capability is partial:** In the same file, _promptForTemplateValue calls rt.complete(variable.name, inputValue, variablesSoFar, token), caches results, and debounces requests by 300 ms. These completions assist the existing sequential picker; they do not supply a persistent editor or snippet-based template-filling surface. Inspection of mcp.contribution.ts found resource Quick Access registration, not an alternative template-editing setting.

The MEMBER comment acknowledges that completions help but the interaction is not necessarily optimal, and explains that previously resolved variables are passed into completion requests.
