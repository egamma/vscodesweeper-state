# Issue #326515 — Cursor doesn't follow page when scrolling with Ctrl+Arrow keys in VS Code

[https://github.com/microsoft/vscode/issues/326515](https://github.com/microsoft/vscode/issues/326515)

## Summary

Ctrl+Up/Down intentionally scrolls without moving the caret; this is not a regression. Propose closing as designed, based on the explicit command behavior and longstanding maintainer guidance for the same Visual Studio-style request.

## Change summary

Change the default Ctrl+Up/Down shortcuts so scrolling also keeps the caret inside the viewport.

## Best solution

Preserve the default scroll-only commands and the existing editorScroll option for users who prefer caret-following behavior. Use revealCursor: true to keep the caret visible when it would otherwise leave the viewport.

- **Proposed comment:**

  > Thanks for the report and the update confirmation. Ctrl+Up/Down is intentionally bound to `scrollLineUp` and `scrollLineDown`, which scroll the editor without moving the caret. The same Visual Studio-style request was previously addressed in https://github.com/microsoft/vscode/issues/111734#issuecomment-737212368.
  > 
  > For caret-following scrolling, the built-in `editorScroll` command supports `revealCursor: true`, with `to: "up"` or `"down"` and `by: "line"`. This keeps the caret inside the viewport when it would otherwise scroll out of view. I understand that you are asking to change the defaults rather than customize your bindings; the existing defaults deliberately preserve the caret position, so this is being closed as designed.

## Evidence

- **Current default is explicit:** src/vs/editor/browser/coreCommands.ts:1429–1451 and 1506–1528 register Ctrl+Up and Ctrl+Down as scrollLineUp and scrollLineDown on Windows. Both explicitly pass revealCursor: false and select: false to editorScroll, preserving the caret while scrolling.
- **Existing capability and its boundary:** src/vs/editor/browser/coreCommands.ts:1354–1374 changes cursor states only when editorScroll receives revealCursor: true, using CursorMoveCommands.findPositionInViewportIfOutside. This provides viewport-edge caret tracking through configurable keybindings, not the requested changed defaults or constant viewport-relative caret movement.
- **Maintainer statement of intent:** https://github.com/microsoft/vscode/issues/2091#issuecomment-218669447 explicitly states that the same Ctrl+Up/Down behavior is working as intended and that configurability is additional functionality rather than a bug fix. The configurable editorScroll behavior is present in current source.
- **Same Visual Studio comparison previously addressed:** https://github.com/microsoft/vscode/issues/111734#issuecomment-737212368 addresses the same request to match Visual Studio line scrolling and recommends editorScroll with revealCursor: true or the VS Keymap extension. https://github.com/microsoft/vscode/issues/59247#issuecomment-427774781 gives the same built-in command configuration.
- **Discussion and canonical search:** The reporter confirmed persistence after upgrading to 1.129.1 and later supplied an attachment; persistence is consistent with the explicit defaults. Searches for cursor-following scrolling found the prior reports above, all closed; https://github.com/microsoft/vscode/issues/3130 is open but concerns mouse shortcuts and does not own this keyboard behavior, so no duplicate close is proposed.
