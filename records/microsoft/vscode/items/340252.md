# Issue #340252 — Flaky Tests: Protocol WebSocket failures

[https://github.com/microsoft/vscode/issues/340252](https://github.com/microsoft/vscode/issues/340252)

## Summary

Team-authored flaky-test report (protected from judgment closes regardless) with concrete CI evidence — ~50% failure rate on two Protocol WebSocket multi-client tests across Linux/macOS/Windows in the same build. Real signal, no fix yet; needs investigation before any change.

## Change summary

Two multi-client integration tests ('sessionRemoved notification is broadcast to all connected clients' and 'unsubscribed client receives no actions but still gets notifications') are flaky, failing ~45-50% of runs on all three CI platforms.

## Best solution

Investigate the race in agentHostStateManager.ts's sessionRemoved broadcast path (also touched in protocolServerHandler.ts) and the test harness's connect/subscribe sequencing in multiClient.integrationTest.ts to find why the second client sometimes misses or mis-times the root/sessionRemoved notification, then stabilize the test or fix the underlying timing issue.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/test/node/protocol/multiClient.integrationTest.ts`, `src/vs/platform/agentHost/node/agentHostStateManager.ts`, `src/vs/platform/agentHost/node/protocolServerHandler.ts`
- **Validation:** Run the two named tests in a tight repeat loop (e.g. via the flaky-smoke-tests style repeat harness) locally/in CI until the failure rate is reproduced, then confirm it drops to 0/N after the fix.
- **Behavior:**

  > Both tests connect a second client (client2) after an initial session/subscription is created on client1, then trigger disposeSession on client1 and expect client2 to reliably receive a root/sessionRemoved notification — even though client2 never subscribed to the session. The notification should arrive deterministically, not ~50% of the time. Acceptance: repeated runs (e.g. 20x) of both tests pass with 0 failures on Linux, macOS, and Windows.
- **Trace:**

  > disposeSession triggers 'root/sessionRemoved' emission from agentHostStateManager.ts (lines ~1062/1125/1594 via this._onDidEmitNotification.fire), which protocolServerHandler.ts (around line 2764) routes to connected clients regardless of subscription. The CI numbers (9-10 failures out of 20, consistent across all 3 OSes) point to a timing race rather than a platform-specific issue — candidates include: client2's websocket connection/initialize handshake not being fully registered as a listener before the notification fires, or the test's waitForNotification helper missing a notification emitted before the wait is registered. Root cause not yet isolated — do not assume it's purely a test-harness bug; the actual protocolServerHandler broadcast ordering relative to a just-connected client needs tracing first. Nothing else in the multi-client test suite should change.
- **Open decisions:**
  - Is this a test-harness race (waitForNotification missing a pre-fired notification) or a genuine server-side race in registering a newly-connected client as a broadcast recipient before disposeSession fires?
  - If it's a server-side race, should the fix buffer/replay notifications for just-connected clients, or should client registration be made synchronous with the initialize handshake before any other call can proceed?
