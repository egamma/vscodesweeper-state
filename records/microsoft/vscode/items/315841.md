# Issue #315841 — Deadlock in extension host activation blocks tunnels auth

[https://github.com/microsoft/vscode/issues/315841](https://github.com/microsoft/vscode/issues/315841)

## Summary

Keep open: a team member reproduced the tunnel-connection deadlock after the linked fix merged and reopened the issue. Current main contains a likely later mitigation for initial web-worker startup, but no post-reopen commit explicitly references this team-authored issue, so it does not meet the factual-close bar.

## Change summary

Remote Tunnel authentication can remain stuck because immediate authentication activation waits for a local web-worker extension host whose initialization depends on remote extension discovery.

## Best solution

Verify the tunnel flow against current main, distinguishing initial web-worker startup from restart, and add an extension-service regression test that proves immediate authentication activation cannot wait on remote extension readiness. If the current initial-start scanning path fully resolves the reported scenario, the owning maintainer should identify and link its post-reopen change before closing.

## Plan brief

- **Likely files:** `src/vs/workbench/services/extensions/browser/extensionService.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/services/extensions/common/extensionHostManager.ts`, `src/vs/workbench/services/extensions/test/browser/extensionService.test.ts`, `src/vs/workbench/services/authentication/browser/authenticationService.ts`
- **Validation:** Extend the extension-service browser tests with a Remote Tunnel startup case where `_installedExtensionsReady` remains closed and the LocalWebWorker proxy initialization is pending; immediate authentication activation must complete through the eligible local provider without waiting for remote readiness.
- **Behavior:**

  > Connecting to a Remote Tunnel must not remain indefinitely on “connecting” while authentication extensions activate. Immediate authentication activation must allow an available local provider to register without waiting for remote extension discovery or an unrelated extension host. Acceptance should cover both initial local web-worker startup and restart, while preserving normal activation across all extension hosts after extension discovery completes.
- **Trace:**

  > The confirmed sequence starts in AbstractExtensionService.activateByEvent with ActivationKind.Immediate, continues through ExtensionHostManager._activateByEvent awaiting its proxy, and can reach WebWorkerExtensionHost initialization while `_installedExtensionsReady` is blocked on remote setup. Commit 184d76ec60143813b7cc2f20b6ca267f3f9cdb4a raced provider registration against activation in AuthenticationService.tryActivateProvider, but https://github.com/microsoft/vscode/issues/315841#issuecomment-4478826302 reproduced the problem after that commit. Current src/vs/workbench/services/extensions/browser/extensionService.ts directly scans local web extensions for initial startup but still uses `_getExtensionRegistrySnapshotWhenReady` on restart, so the exact remaining path must be established before changing behavior. Preserve normal activation ordering and remote-host participation once those hosts are ready; do not turn immediate activation into a global skip of web-worker or remote extensions. The broader timeout telemetry in https://github.com/microsoft/vscode/issues/321626 may share the activation handshake but does not prove every timeout has this deadlock.
- **Open decisions:**
  - Does current main still deadlock during initial tunnel connection, or only when the local web-worker extension host is restarting?
  - Should immediate activation wait for a not-ready LocalWebWorker at all, or should readiness filtering differ by host kind while preserving authentication providers that run in the web worker?
  - Is the remaining work specific to extension-host initialization, or should it be consolidated with the broader authentication registration handshake tracked by https://github.com/microsoft/vscode/issues/321626?
