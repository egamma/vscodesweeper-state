# Issue #334575 — Agent host: a local slash command's output is never shown, leaving an empty turn

[https://github.com/microsoft/vscode/issues/334575](https://github.com/microsoft/vscode/issues/334575)

## Summary

Confirmed by reading the source: local slash-command stdout/stderr is genuinely dropped on both the replay and live paths, leaving an empty turn even though the model correctly produced no text. This is a real, well-diagnosed defect worth fixing, but the rendering shape isn't decided yet, so it stays open for a plan pass rather than a blind implementation.

## Change summary

A local slash command's stdout/stderr is discarded instead of shown, so the workbench renders an empty assistant turn for commands like /code-review.

## Best solution

Surface <local-command-stdout>/<local-command-stderr> as a visible response part on the active turn (replay: extend ALLOWED_SYSTEM_SUBTYPES / parseSystemMessage in claudeReplayMapper.ts; live: handle the local_command subtype in claudeMapSessionEvents.ts) while still dropping the echo markers and the caveat — but decide the rendering shape and truncation policy with a maintainer first.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/claude/claudeReplayMapper.ts`, `src/vs/platform/agentHost/node/claude/claudeMapSessionEvents.ts`
- **Validation:** A replay-mapper test (alongside claudeReplayMapper.test.ts's existing compact_boundary/notification fixtures) asserting a `local_command` system entry with a `<local-command-stdout>...</local-command-stdout>` payload produces a visible response part on the turn, while a pure `<command-name>`/`<local-command-caveat>` echo is still dropped.
- **Behavior:**

  > When a local slash command (e.g. /code-review) produces output, that output must be visible to the user on the turn, both when replaying a restored session and when running live — instead of the currently empty assistant bubble. The CLI's echo markers (<command-name>, <command-message>, <command-args>) and the <local-command-caveat> preamble must continue to be hidden, since they are not user-authored content and the caveat is what keeps the model from responding to its own output.
- **Trace:**

  > Confirmed via source read (not executed): on replay, claudeReplayMapper.ts's parseSystemMessage (lines ~186-193) only keeps `system` subtypes present in ALLOWED_SYSTEM_SUBTYPES (line ~204: 'compact_boundary', 'notification'); 'local_command' is absent, so the entry carrying the actual `<local-command-stdout>` payload is dropped before it ever reaches the builder. Separately, CLI_ECHO_MARKER_PATTERN (line 222) also matches 'local-command-stdout'/'local-command-stderr' tags on `user`-typed echo envelopes — that filter is correctly dropping the CLI's echo-for-fidelity copy, not the `system`/`local_command` entry itself, so the two drops are distinct and both need addressing. On the live path, claudeMapSessionEvents.ts's mapSDKMessageToAgentSignals only routes `type: 'system'` messages to mapSubagentSystemMessage (lines 272-277), which is scoped to subagent task discrimination and returns no signal for local_command. Boundary: do not change how the CLI-echo `user` messages or the caveat are filtered — only stop dropping the `local_command` system entry itself. Where the uncertainty starts: which ResponsePartKind (SystemNotification, a new dedicated kind, or plain markdown) should carry the stdout/stderr, and whether/how very large output (the report's 13.6 KB case) should be truncated or specially formatted before display.
- **Open decisions:**
  - Should local-command stdout/stderr render as a SystemNotification-style system bubble, a plain assistant-visible text part, or a new dedicated response-part kind?
  - Should stdout and stderr be visually distinguished (e.g. stderr styled as an error/warning)?
  - Is there a size/formatting policy for large command output (the report cites 13.6 KB from a single /code-review run), or is it always shown in full?

## Evidence

- **replay drop confirmed:** src/vs/platform/agentHost/node/claude/claudeReplayMapper.ts:186-193,204-207 — parseSystemMessage only keeps subtypes in ALLOWED_SYSTEM_SUBTYPES = {'compact_boundary','notification'}; 'local_command' is not in that set, so the system entry (the actual stdout payload) is dropped entirely on replay.
- **CLI echo filter also matches stdout:** claudeReplayMapper.ts:222 CLI_ECHO_MARKER_PATTERN includes 'local-command-stdout'/'local-command-stderr' alongside the pure echo markers, confirming the issue's claim that the same filter that (correctly) drops echoes also removes the command's actual output.
- **live path also drops it:** src/vs/platform/agentHost/node/claude/claudeMapSessionEvents.ts:272-277 — the only live handling of `message.type === 'system'` is mapSubagentSystemMessage for subagent task discrimination; there is no live code path that surfaces a local_command system message as a response part, so it maps to no signal, matching the issue's description.
- **no existing part kind for this:** Only ResponsePartKind.Markdown and ResponsePartKind.SystemNotification exist as candidates (src/vs/platform/agentHost/common/state/sessionState.ts via agentHostConversationContext.ts / changesetUri.ts); neither is an obvious fit for raw command stdout, which is an open rendering decision.
