# Issue #337532 — Branch Changes status pill assumes the base remote is origin

[https://github.com/microsoft/vscode/issues/337532](https://github.com/microsoft/vscode/issues/337532)

## Summary

Confirmed on main: the Branch Changes baseline resolution hardcodes `origin` in several places with no way to honor a differently-named canonical remote, so fork-based workflows (origin=fork, another remote=upstream) compare against a stale/wrong ref and surface hundreds of unrelated files.

## Change summary

The Agent Host Git service and Branch Changes status pill assume the base/comparison remote is always named `origin`, breaking fork-based repo setups.

## Best solution

Generalize base-ref resolution in agentHostGitService.ts (getDefaultBranch, _resolveBranchMergeBaseCommit, _computeBaseBranchDivergence) to consider the actual canonical remote — e.g. the feature branch's upstream remote (already computed as `upstreamRemote` in _computeSessionGitState) or the `preferredRemote` already used for GitHub owner/repo resolution — instead of hardcoding `origin`.

## Plan brief

- **Behavior:**

  > When a repository's `origin` remote is a fork and a differently-named remote is the canonical/upstream repository, the Branch Changes status pill (and any base-branch-derived comparison) must compare against the actual base ref used to create the feature branch, not assume `origin/<base>`. Existing single-remote and origin-as-canonical setups must keep working unchanged. Acceptance: the added test demonstrates correct ref selection when origin is a fork and another remote holds the true base branch.
- **Trace:**

  > getDefaultBranch (agentHostGitService.ts:63) reads `refs/remotes/origin/HEAD` unconditionally to find the default branch and constructs `origin/<branch>` as its startPoint; _resolveBranchMergeBaseCommit (line 547) and _resolveRemoteTrackingBranch/getRemoteTrackingRef (lines 608-628, 1156-1172) likewise always build `origin/<branch>` / `refs/remotes/origin/<branch>`; _computeBaseBranchDivergence (line 1064) does the same for divergence counts. `_computeSessionGitState` (line 1006) already derives `upstreamRemote` from the feature branch's own upstream tracking ref for GitHub repo detection, and `getFetchRemoteUrls`/`parseFetchRemoteUrls` (line 759, 1644) already accept a `preferredRemote` parameter for the same purpose — neither is threaded into base-ref resolution today. The fix must not change behavior for the common single-remote-named-origin case, and should not regress the empty-repo/no-HEAD fallback path. Related: https://github.com/microsoft/vscode/issues/337420, https://github.com/microsoft/vscode/issues/321941, https://github.com/microsoft/vscode/issues/309102 (related but distinct: stale HEAD staleness and default-branch selection, not remote-name assumption), and the originating PR https://github.com/microsoft/vscode/pull/332982.
- **Open decisions:**
  - Should the canonical remote be inferred automatically (e.g. from the feature branch's own upstream remote, or from the GitHub `preferredRemote` already used for owner/repo detection), or should it be an explicit user/session setting?
  - If a remote can't be confidently inferred, should the pill fall back to the current `origin`-based behavior, or omit/disable the comparison?
