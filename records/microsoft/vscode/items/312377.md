# Issue #312377 — Show only changed/dirty Git repositories

[https://github.com/microsoft/vscode/issues/312377](https://github.com/microsoft/vscode/issues/312377)

## Summary

Keep this accepted feature request open: current repository visibility controls do not provide automatic filtering by uncommitted changes. It has 27 upvotes and was promoted to Backlog; the verified related requests address different behaviors.

## Change summary

Provide an option to show only Git repositories with uncommitted changes.

## Best solution

Offer an opt-in dirty-repository filter in the SCM repository UI that updates as repository status changes, without closing repositories or changing the default all-repository experience. Settle its interaction with repository selection and nested worktrees before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/scm/browser/scm.contribution.ts`, `src/vs/workbench/contrib/scm/browser/scmViewService.ts`, `src/vs/workbench/contrib/scm/browser/scmRepositoriesViewPane.ts`, `src/vs/workbench/contrib/scm/browser/scmViewPane.ts`
- **Validation:** In a workspace containing two Git repositories, leave one clean and create an uncommitted change in the other. Enable the agreed filter and verify only the dirty repository appears on the agreed surfaces; modify the clean repository and verify it appears, then commit or discard changes and verify the newly clean repository disappears. Disable filtering and verify both repositories return. Include staged-only, untracked-only, all-clean, and dirty-child-worktree cases.
- **Behavior:**

  > Users managing multiple Git repositories can opt to see only repositories containing uncommitted changes. Filtering responds to changes in Git status without requiring users to manually reselect repositories. Disabling the option restores the existing unfiltered experience, and hidden repositories remain available rather than being closed or ignored. Acceptance checks cover clean-to-dirty and dirty-to-clean transitions, staged and untracked changes, and an all-clean workspace; the affected surfaces and nested-repository behavior need agreement first.
- **Trace:**

  > SCMViewService.repositories and visibleRepositories in src/vs/workbench/contrib/scm/browser/scmViewService.ts currently use provider.isHidden and manual selectionIndex, with no dirty-status predicate. RepositoryTreeDataSource.getChildren in src/vs/workbench/contrib/scm/browser/scmRepositoriesViewPane.ts supplies repositories according to their parentId hierarchy. Repository settings in src/vs/workbench/contrib/scm/browser/scm.contribution.ts expose ordering, sizing, selection, and artifacts but no dirty-only option; src/vs/workbench/contrib/scm/browser/scmViewPane.ts consumes visibleRepositories for the changes surface. Git's _isHidden initialization in extensions/git/src/repository.ts serves unrelated empty-window and Copilot-worktree cases, so filtering must not repurpose those semantics or close repositories. Related requests https://github.com/microsoft/vscode/issues/180820 and https://github.com/microsoft/vscode/issues/299267 concern highlighting and active-worktree filtering respectively, not this capability. The trace establishes the missing visibility behavior, but not the desired interaction between filtering, manual selection, and nested repositories.
- **Open decisions:**
  - Should the option filter the Repositories view, the Source Control changes view, or both?
  - Should dirty-only mode display every dirty repository, or only dirty repositories within the user's existing manual selection?
  - When a clean parent contains a dirty child worktree or submodule, should the parent remain visible as a structural container, or should the dirty child appear independently?
