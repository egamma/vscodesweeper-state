# Issue #207557 — Test API: test run profiles - workspace folder scope?

[https://github.com/microsoft/vscode/issues/207557](https://github.com/microsoft/vscode/issues/207557)

## Summary

Keep open for API design discussion: tags already restrict profile eligibility, but neither explicit workspace-folder scoping nor the controller-grouping concern raised in the discussion is covered. The maintainer acknowledged the grouping tradeoff and invited ideas; the verified related issues do not own the same work.

## Change summary

Support workspace-scoped test run profiles without forcing extensions to expose separate, ungrouped controllers for every workspace folder.

## Best solution

Settle whether folder-specific profile applicability should remain tag-based or gain an explicit API, while preserving coherent extension grouping in multi-root Test Explorer trees. Retain compatibility with existing controllers and tests that have no workspace-folder association.

- **Behavior:**

  > An extension author can make profiles applicable to selected workspace folders without presenting an incoherent collection of unrelated controller roots. Inapplicable profiles should not be offered for those folders' tests, and running all tests should respect the agreed applicability semantics. Existing providers without workspace metadata must retain their behavior. Acceptance should cover two workspace folders, folder-specific profiles, and a second test provider.
- **Trace:**

  > TestRunProfile and TestController.createRunProfile in src/vscode-dts/vscode.d.ts expose tag-based applicability but no workspace-folder scope. canUseProfileWithTest in src/vs/workbench/contrib/testing/common/testProfileService.ts checks controller identity and tags, while treating controller roots as eligible; testingConfigurationUi.ts uses this helper for test-specific profile choices. The discussion at https://github.com/microsoft/vscode/issues/207557 records separate controllers as an existing alternative, but the reporter identifies the resulting extension-grouping problem and the maintainer leaves workspace metadata open for discussion. Preserve existing controller and tag semantics unless an explicit compatible contract is agreed. The uncertainty is the public workspace-scoping and grouping contract, not a confirmed defect in the current filtering implementation. https://github.com/microsoft/vscode/issues/330204 concerns profile preference, and https://github.com/microsoft/vscode/issues/141272 concerns controller ordering; neither resolves this design question.
- **Open decisions:**
  - Should workspace-folder applicability remain extension-managed through tags, or become an explicit public testing API contract?
  - Should multiple folder-specific controllers remain separate Test Explorer roots, or gain a supported grouping relationship that preserves an extension-level parent?
