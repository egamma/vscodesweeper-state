# Issue #183906 — Git - Remove all local branches which origin is deleted (Git Fetch Prune)

[https://github.com/microsoft/vscode/issues/183906](https://github.com/microsoft/vscode/issues/183906)

## Summary

Keep this accepted, well-supported request open: Fetch (Prune) still does not provide bulk cleanup of local branches whose upstreams were deleted. The previous implementation attempts were closed without merging; deletion safeguards need a maintainer decision before another implementation.

## Change summary

Provide built-in bulk cleanup of local branches whose remote upstream branches no longer exist.

## Best solution

Provide an explicit, reviewable cleanup workflow in the built-in Git extension that identifies missing upstreams and supports bulk deletion without silently discarding local work. Preserve ordinary fetch semantics and settle eligibility and confirmation behavior before implementation.

## Plan brief

- **Likely files:** `extensions/git/src/commands.ts`, `extensions/git/src/repository.ts`, `extensions/git/src/git.ts`, `extensions/git/package.json`, `extensions/git/package.nls.json`
- **Validation:** In a disposable Git repository, publish several branches, delete their upstream branches, then fetch with pruning. Verify the agreed cleanup workflow identifies and can remove eligible local branches in bulk, preserves branches with live upstreams or no configured upstream, protects branches checked out in any worktree, and handles local-only commits according to the approved policy. Confirm ordinary Fetch (Prune) and existing single-branch deletion retain their agreed behavior.
- **Behavior:**

  > Users currently retain local branches after their upstream branches are deleted and must clean them up individually or use external tools. Provide a built-in workflow for identifying and deleting these stale local branches in bulk. Acceptance must distinguish missing upstreams from branches that never tracked a remote, preserve unrelated branches, and prevent unintended loss of local-only work. The maintainer must settle whether cleanup is a separate action or an opt-in part of fetch, and what happens to branches that cannot be safely deleted.
- **Trace:**

  > The registered git.fetchPrune command calls Repository.fetchPrune in extensions/git/src/repository.ts, which delegates to git fetch --prune in extensions/git/src/git.ts without local cleanup. Commands._deleteBranch in extensions/git/src/commands.ts uses a single branch picker and retains Git's safe-delete check with an explicit force-delete prompt. getBranch in git.ts parses upstream:track but drops upstream metadata for [gone], so that API alone does not distinguish a vanished upstream from an untracked branch. Preserve ordinary fetch behavior and existing single-branch safeguards unless a maintainer explicitly approves a change. The closed, unmerged attempts at https://github.com/microsoft/vscode/pull/183955 and https://github.com/microsoft/vscode/pull/205031 are historical context, not implementations to assume correct; the latter's author subsequently requested reconsideration of behavior. Related multi-selection work at https://github.com/microsoft/vscode/issues/182640 does not cover automatic identification of vanished upstreams. The remaining uncertainty is the product contract for cleanup invocation, eligibility, and destructive confirmation.
- **Open decisions:**
  - Should cleanup be a separate explicit command, or an opt-in operation associated with Fetch (Prune)?
  - Should branches with local-only or otherwise unmerged commits be excluded, or offered for forced deletion only after explicit confirmation?
  - Should cleanup target only origin or each branch's configured upstream across remotes, and should users review a selectable candidate list before deletion?
