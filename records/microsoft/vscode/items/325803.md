# Issue #325803 — AgentHost: Support "Remote Repositories"

[https://github.com/microsoft/vscode/issues/325803](https://github.com/microsoft/vscode/issues/325803)

## Summary

Keep open: client-backed filesystem support remains missing, and the merged remote-server work explicitly excludes Remote Repositories. This team-authored request remains necessary; the newer related report does not qualify as its duplicate canonical.

## Change summary

Allow Agent Host sessions to access Remote Repositories through the client's filesystem provider, with dirty editor files as a related scenario.

## Best solution

Support client-backed filesystems across the AHP session and Copilot SDK boundary without treating virtual resources as host-local paths. Preserve existing server-backed and headless sessions, while defining client-disconnection and dirty-buffer behavior for sessions that depend on an attached editor.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts`, `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`, `src/vs/platform/agentHost/node/agentHostResourceProviders.ts`, `src/vs/workbench/services/agentHost/electron-browser/agentHostService.ts`, `src/vs/workbench/services/agentHost/browser/webAgentHostEnablementService.ts`
- **Validation:** With a Remote Repositories workspace open and no server-backed remote authority, ask an Agent Host Copilot session to read and edit a repository file; verify the operations reach the client filesystem provider and the edit appears in the editor. Exercise the agreed dirty-buffer and client-disconnection behavior, and verify ordinary local and server-backed sessions remain functional.
- **Behavior:**

  > An Agent Host Copilot session can read and edit files in a Remote Repositories workspace through the attached client's filesystem provider, without requiring a local checkout or remote server. Virtual resources must not be interpreted as unrelated host-local paths. Acceptance includes an observable repository-file edit, defined handling of client disconnection, and the agreed behavior for unsaved editor changes. Existing local, server-backed, and independently headless sessions retain their behavior.
- **Trace:**

  > CopilotSessionLauncher._createSession and _buildSessionConfig in src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts pass workingDirectory.fsPath into SDK session configuration; no SessionFsProvider integration was found in current Agent Host TypeScript sources. WorkbenchAgentHostService in src/vs/workbench/services/agentHost/electron-browser/agentHostService.ts chooses remote versus local hosting from remoteAuthority, while WebAgentHostEnablementService enables hosting only with that authority. AgentHostResourceProviders in src/vs/platform/agentHost/node/agentHostResourceProviders.ts provides host-side scheme routing, but that alone does not establish a client-filesystem bridge into SDK file tools. https://github.com/microsoft/vscode/pull/329706 explicitly excludes this request, and https://github.com/microsoft/vscode/issues/327339 corroborates the virtual-repository gap. The author has already specified client dependence for this scenario; the remaining design work is the session/filesystem contract, its lifecycle behavior, and how the related dirty-buffer scenario participates. Preserve ordinary host-backed sessions and interoperability with hosts that do not advertise this capability.
- **Open decisions:**
  - When the filesystem-owning client disconnects, should the dependent session pause for reconnection or terminate with an explicit error?
  - Should initial support include unsaved editor contents, and if so, how should agent edits interact with dirty buffers rather than only the filesystem provider's stored contents?
