# Issue #157961 — Allow to return an exit code from `--wait` invocations

[https://github.com/microsoft/vscode/issues/157961](https://github.com/microsoft/vscode/issues/157961)

## Summary

Keep open: current --wait plumbing signals editor closure, not merge success, so the requested exit-code capability remains missing. The maintainer endorsed this capability, and the related staging report was explicitly consolidated into this issue.

## Change summary

Allow waiting CLI invocations to return an exit status that distinguishes successful merge completion from abandonment or failure.

## Best solution

Define and implement a merge-outcome exit-status contract across the CLI and merge editor so external Git tools can safely trust the result. Settle compatibility with ordinary --wait editing and explicit completion with unresolved conflicts before implementation.

## Plan brief

- **Likely files:** `src/vs/code/node/cli.ts`, `src/vs/platform/environment/node/argv.ts`, `src/vs/platform/environment/node/wait.ts`, `src/vs/platform/windows/electron-main/windowsMainService.ts`, `src/vs/workbench/electron-browser/window.ts`, `src/vs/workbench/contrib/mergeEditor/browser/mergeEditorInputModel.ts`, `src/vs/workbench/contrib/mergeEditor/browser/commands/commands.ts`
- **Validation:** Run a CLI integration check using four temporary merge inputs and code --wait --merge: successful resolution and completion must return 0, while abandonment or failure must return a nonzero status under the agreed contract. Cover both an already-running window and a newly launched window, verify that the process remains waiting while the result editor is open, and check ordinary code --wait editing retains its agreed behavior.
- **Behavior:**

  > External merge tools currently cannot distinguish successful resolution from abandonment because --wait returns success after the result editor closes. A waiting merge invocation should provide a trustworthy exit status: 0 for successful completion and nonzero for abandonment or failure. Acceptance must exercise successful completion, unresolved closure, discarded changes, and explicit completion with conflicts according to the maintainer-selected contract. Ordinary waiting editor workflows must retain their agreed compatibility.
- **Trace:**

  > src/vs/code/node/cli.ts creates a wait marker, awaits its deletion or child termination, and exits 0 when main resolves. NativeWindow.trackClosedWaitFiles in src/vs/workbench/electron-browser/window.ts deletes that marker after whenEditorClosed without consuming a merge outcome. The merge editor's WorkspaceMergeEditorInputModel tracks acceptance for telemetry and supports closing with conflicts; mergeEditor.acceptMerge in commands/commands.ts also permits explicit completion with conflicts, but its successful result is not a CLI exit status. This establishes the missing transport capability without executing the application. Preserve existing merge saving, conflict warnings, and ordinary wait timing; unrelated interactive-rebase failures are outside this trace. https://github.com/microsoft/vscode/issues/162381 was consolidated into this issue, while https://github.com/microsoft/vscode/issues/159024 only changed warning preferences. The remaining uncertainty is the observable success contract and its compatibility scope, not whether the current CLI carries merge outcomes.
- **Open decisions:**
  - Should explicit Complete with Conflicts count as successful completion, or must any remaining unresolved conflict produce a nonzero CLI status?
  - Should outcome-sensitive exit codes become the default for --wait --merge, or require an opt-in CLI option to preserve existing callers?
  - Is the initial outcome contract limited to merge invocations, or should ordinary --wait editing also report abandonment and editing failures?
