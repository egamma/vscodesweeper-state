# Issue #316751 — Why does MCP require npx on the host; shouldn't it run in the devcontainer?

[https://github.com/microsoft/vscode/issues/316751](https://github.com/microsoft/vscode/issues/316751)

## Summary

Keep open as a request for remote execution of plugin-provided MCP servers. Current source selects the execution host from the plugin's location, while the separate MCP configuration flow offers remote execution; that workaround does not resolve the reported plugin-installation boundary.

## Change summary

Allow an MCP server installed through an agent plugin to run inside the connected dev container rather than requiring its runtime in the local Flatpak environment.

## Best solution

Make the execution location of plugin-provided MCP servers explicit and support choosing the connected dev container where appropriate, while preserving support for intentionally local servers. Direct remote MCP configuration provides an interim alternative, not equivalent coverage of the plugin workflow.

- **Proposed comment:**

  > Thanks for the report. MCP servers can run inside a dev container: MCP: Add Server... (`workbench.mcp.addConfiguration`) offers Remote and Workspace targets in a connected remote window. However, plugin-provided servers currently select their execution host from the plugin's location, so a locally installed plugin can still require `npx` in the local Flatpak environment. Keeping this open as a request to support an explicit remote execution choice for plugin-provided servers; configuring the server separately is an interim workaround.

## Evidence

- **Reported trigger and workaround:** https://github.com/microsoft/vscode/issues/316751 describes installing ChromeDevTools/chrome-devtools-mcp through Chat: Install Plugin from Source and enabling its tools. Installing Node tooling inside the Flatpak makes it work, but the reporter explicitly distinguishes that workaround from the desired dev-container execution.
- **Plugin execution-host selection:** src/vs/workbench/contrib/mcp/common/discovery/pluginMcpDiscovery.ts:85-100 registers plugin MCP collections with remoteAuthority taken from plugin.uri only when its scheme is vscodeRemote; otherwise it is null. src/vs/workbench/api/browser/mainThreadMcp.ts:98-105 selects an extension-host delegate whose remoteAuthority matches the collection. Opening a remote workspace therefore does not itself relocate a locally installed plugin's server.
- **Source-install location:** src/vs/workbench/contrib/chat/browser/pluginInstallService.ts:104-155 routes repository URLs through _doInstallFromSource and ensurePluginSource. src/vs/workbench/contrib/chat/browser/agentPluginRepositoryService.ts:74-80 uses the current profile's agentPluginsHome as the installation root; this path does not offer a dev-container execution-target choice.
- **Existing capability is a partial alternative:** The command workbench.mcp.addConfiguration, registered as MCP: Add Server..., offers Global, Remote, and Workspace targets in src/vs/workbench/contrib/mcp/browser/mcpCommandsAddConfiguration.ts:289-324. Remote and remote-workspace descriptions explicitly say the server runs on the remote machine. This establishes that MCP is not universally host-only, but configuring a server separately does not change the plugin-provided server's execution location.
