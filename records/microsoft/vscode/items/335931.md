# Issue #335931 — Webview widget of AI-agent extensions (Zoo Code, Cline) crashes to a blank gray panel; `[uncaught exception in main] TypeError: Titlebar overlay is not enabled` thrown from the guest-window claim path (`openGuestWindow`), Windows, 1.137.0

[https://github.com/microsoft/vscode/issues/335931](https://github.com/microsoft/vscode/issues/335931)

## Summary

The reported stack trace matches real current-main code exactly (AuxiliaryWindow.doTryClaimWindow -> BaseWindow.setWin -> updateWindowControls -> win.setTitleBarOverlay), and `updateWindowControls` calls `setTitleBarOverlay()` unconditionally whenever the global `useWindowControlsOverlay()` setting is on, without verifying the specific BrowserWindow was actually constructed with a titleBarOverlay-enabling option — plausible given the shared FIFO `pendingWindowOptionsQueue` in AuxiliaryWindowsMainService, which any about:blank guest window (including one whose opener isn't a real vscode-file:// window and is therefore never claimed via `registerWindow`) can desync. This needs a maintainer/Electron-window-team look rather than an automated fix.

## Change summary

On Windows, extension webviews that spawn `window.open()` popups (agent auth/preview windows) eventually crash to a blank gray panel because a main-process uncaught `TypeError: Titlebar overlay is not enabled` aborts guest-window initialization.

## Best solution

Have the windows/electron-main owners review `AuxiliaryWindow.doTryClaimWindow`/`BaseWindow.updateWindowControls` (src/vs/platform/windows/electron-main/windowImpl.ts, src/vs/platform/auxiliaryWindow/electron-main/auxiliaryWindow.ts, auxiliaryWindowsMainService.ts) to either guard `setTitleBarOverlay()` behind a check that the specific window was created with `titleBarOverlay` enabled, and/or fix the shared `pendingWindowOptionsQueue` so it can't desync when a guest window's `web-contents-created` opener check (`vscode-file://` prefix) causes an entry to never be shifted off.
