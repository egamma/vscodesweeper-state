# Issue #113270 — Support cancelation in getSession

[https://github.com/microsoft/vscode/issues/113270](https://github.com/microsoft/vscode/issues/113270)

## Summary

Keep open: provider-owned Cancel controls mitigate abandoned sign-ins, but current main still lacks extension-controlled getSession cancellation and provider propagation. The maintainer explicitly proposed this API work; the later Microsoft-authentication fix does not complete it.

## Change summary

Allow extensions to cancel pending authentication.getSession requests, propagate cancellation to providers, and restart an abandoned request without its original cancellation token.

## Best solution

Define an end-to-end authentication cancellation contract that lets extensions abandon pending sign-ins and retry while preserving protection against duplicate prompts. Settle how cancellation and forced restart affect callers sharing an in-flight request before implementing the public API and provider behavior.

- **Validation:** Extend the existing authentication RPC integration harness with a provider whose createSession remains pending. Verify the agreed caller-cancellation contract, provider cancellation delivery, successful retry after cancellation, unchanged deduplication without cancellation, and the chosen effect on concurrent callers. Include a manual browser-abandonment check: start sign-in, close the browser tab, cancel or restart through the agreed API, and confirm a fresh attempt can complete without reloading VS Code.
- **Behavior:**

  > An extension must be able to cancel its pending authentication.getSession request rather than wait for an abandoned browser sign-in to finish or time out. Authentication providers must receive the agreed cancellation signal, and a subsequent attempt must be able to complete without a window reload. A supported restart operation must address cases where the original cancellation token is unavailable. Repeated uncancelled requests must retain the existing protection against duplicate prompts; concurrent-caller behavior must follow the contract chosen with the maintainer.
- **Trace:**

  > The maintainer established the intended direction at https://github.com/microsoft/vscode/issues/113270#issuecomment-843507797. Current src/vscode-dts/vscode.d.ts exposes neither caller nor provider cancellation. ExtHostAuthentication.getSession in src/vs/workbench/api/common/extHostAuthentication.ts builds a request key and uses TaskSingler.getOrCreate, which retains the shared promise until settlement; MainThreadAuthentication.doGetSession forwards session creation through AuthenticationService and back to the provider without a caller token. Existing forceNewSession controls reauthentication, not cancellation of the prior request. Built-in GitHub and Microsoft providers already have locally owned progress cancellation, and https://github.com/microsoft/vscode/pull/211495 addressed the narrower Microsoft sign-in recovery problem without completing this API contract. Preserve existing session selection, access consent, and ordinary request deduplication. The unresolved boundary is cancellation ownership for shared requests and the observable scope of forced restart.
- **Open decisions:**
  - When equivalent getSession calls share a pending request, does cancelling one caller cancel only that caller's wait, or also cancel the provider operation and other waiters?
  - What is the public forced-restart contract: which pending requests may it cancel, and may it affect requests initiated by another extension?
