# Issue #258446 — Checkpoint - Undo Last Request/Redo Last Request

[https://github.com/microsoft/vscode/issues/258446](https://github.com/microsoft/vscode/issues/258446)

## Summary

Keep open: current main deliberately supports incremental undo stops within a request, while this team-authored polish issue proposes using the whole turn as the user-visible unit. The conflicting UX expectations require a maintainer decision and cannot be closed as designed under the team-authored-item rule.

## Change summary

Make chat checkpoint undo and redo operate on a consistent whole-turn unit rather than potentially stepping through subsets of a turn.

## Best solution

Choose one understandable user-visible history unit for the title-bar undo/redo actions, then align their labels, tooltips, undo behavior, and redo behavior with that decision while preserving explicit checkpoint restoration.

- **Behavior:**

  > Chat history undo and redo must expose a consistent, clearly named unit to users when one user request produces multiple internal edit checkpoints. Explicitly restoring a selected checkpoint must remain available and continue restoring both workspace edits and chat state. Acceptance should cover a request with multiple edit stops, consecutive requests, and repeated undo followed by redo, with labels and behavior matching the selected unit.
- **Trace:**

  > The top-level actions in src/vs/workbench/contrib/chat/browser/actions/chatNewActions.ts delegate to `IChatEditingSession.undoInteraction()` and `redoInteraction()`. Those reach `ChatEditingCheckpointTimelineImpl.undoToLastCheckpoint()` and `redoToNextCheckpoint()`, where `_willUndoToCheckpoint` may choose an intermediate operation checkpoint while `_willRedoToEpoch` independently selects the next checkpoint or request boundary. Explicit per-message restoration follows `restoreSnapshotWithConfirmation` in src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingActions.ts and should remain distinct. The existing timeline test suite provides the bounded validation surface. The uncertainty is product semantics, not implementation placement: the reporter wants whole-turn behavior, while a maintainer described incremental undo as intentional.
- **Open decisions:**
  - Should the title-bar undo/redo pair move by whole user turns, by user requests, or by internal edit checkpoints when a request contains multiple stops?
  - Must undo and redo always use the same unit, or is asymmetric navigation an intentional contract that should instead be made explicit in the action labels and tooltips?
