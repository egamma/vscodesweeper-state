# Issue #339409 — Agents: Peer chats disappear on refresh after chat fragment is restored as a separate session

[https://github.com/microsoft/vscode/issues/339409](https://github.com/microsoft/vscode/issues/339409)

## Summary

Team-authored (roblourens, MEMBER), freshly filed bug with a detailed root-cause trace that I confirmed against current main — `_createSessionIdentity` in agentHostConnectionsService.ts still does `sessionResource.with({ scheme: backendProvider })`, preserving the UI peer-chat `#<chat-id>` fragment, exactly as described. No fix has landed yet, so this stays open.

## Change summary

Peer chats in a multi-chat Agent Host session intermittently disappear from the sidebar on session-list refresh after a recent URI-resolution change caused a fragment-bearing phantom session to collide with and overwrite the parent's chat catalogue.

## Best solution

Fix the identity/keying collision so a fragment-bearing peer-chat URI used by session-level subscribers (WorkbenchAgentHostCustomizationService, AgentHostGenericConfigChips) is never registered or restored as a distinct top-level session that can overwrite the parent's catalogue in BaseAgentHostSessionsProvider._refreshSessions/applyChatMetadata.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/browser/agentHostConnectionsService.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/platform/agentHost/common/agent.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationService.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostGenericConfigChips.ts`
- **Validation:** A test confirming that refreshing sessions while a fragment-bearing peer-chat URI is registered does not overwrite/dispose the parent session's other peer chats, and that AgentSession.id (or the refresh keying) distinguishes a fragment-bearing phantom entry from its parent.
- **Behavior:**

  > Peer chats within a multi-chat Agent Host session must remain visible across session-list refreshes unless genuinely removed (no `session/chatRemoved`/`root/sessionRemoved`). A session-level subscription or restoration keyed off a peer-chat's fragment-bearing URI must not be treated as, or overwrite, the parent session's chat catalogue. Acceptance: repeated refreshes (e.g., on subagent turn completion) leave all real peer chats present in the sidebar; no active chat auto-switches away due to a spurious disappearance.
- **Trace:**

  > Confirmed on main: _createSessionIdentity in agentHostConnectionsService.ts (around line 181-190) builds backendSession via sessionResource.with({ scheme: backendProvider }), which keeps any UI peer-chat fragment attached. Session-level consumers (agentHostCustomizationService.ts ~L692, agentHostGenericConfigChips.ts ~L114) subscribe to that fragment-bearing URI as if it were its own session; a subscription fallback then calls restoreSession on the exact fragment-bearing URI, registering a phantom top-level session. BaseAgentHostSessionsProvider._refreshSessions keys entries via AgentSession.id (agent.ts ~L1155), which returns only the URI path, so the phantom and the real parent collide under the same cache key; whichever listSessions response arrives later (often the one-chat phantom) overwrites the parent's full catalogue, and applyChatMetadata disposes peers missing from the replacement, triggering SessionsService's active-chat fallback. Must not change: single-session restoration semantics for normal (non-peer) session URIs, or the general subscription/refresh pipeline for sessions without fragments. Where uncertainty starts: whether to fix this by stripping/preserving fragments in identity construction, by changing AgentSession.id to include the fragment for keying distinctness, or by making consumers resolve the owning parent before subscribing — these differ in session-identity contract and need a maintainer's call.
- **Open decisions:**
  - Should backendSession/identity construction strip the UI fragment entirely for session-level purposes, or should AgentSession.id be changed to incorporate the fragment so fragment-bearing and parent entries never collide in the refresh cache?
  - Should session-level subscribers (WorkbenchAgentHostCustomizationService, AgentHostGenericConfigChips) be changed to resolve and subscribe to the owning parent session instead of the fragment-bearing peer-chat URI, and is that a broader contract change affecting other consumers?
