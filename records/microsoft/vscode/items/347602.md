# Issue #347602 — Chat: "This is taking a little longer than usual" gives no indication of what the agent is stuck on

[https://github.com/microsoft/vscode/issues/347602](https://github.com/microsoft/vscode/issues/347602)

## Summary

The contextual-progress gap remains on current main: the inactivity footer still substitutes a generic message without identifying the wait or its duration. Existing diagnostic commands and foreground-tool handling only partially address the request.

## Change summary

Show the known activity and elapsed waiting time when an agent request stops producing progress.

## Best solution

Make delayed chat progress communicate the last reliably known activity and elapsed inactivity, explicitly acknowledging when the wait reason is unknown. Preserve suppression during active foreground tools and provide access to existing diagnostics without presenting an inferred cause as fact.

- **Behavior:**

  > When an agent request goes quiet long enough to show delayed progress, users should see the reliably known waiting context and elapsed inactivity rather than only a generic reassurance. Unknown causes must remain explicitly unknown, not be attributed to the model or an MCP server without evidence. New activity should update the status, and completed requests or active foreground tools must retain their existing handling.
- **Trace:**

  > ChatListRenderer constructs IChatWorkingProgress with content, progressStep, and showDelayedProgressMessage; its active branch enables the inactivity fallback when getPersistentActivityLabel returns no label. ChatWorkingProgressContentPart schedules a 90-second timer, resets it through onResponseActivity(), and resolveWorkingContent() substitutes a fixed localized sentence after expiry. showDelayedProgress() already excludes unfinished tool invocations and unsettled progress tasks. Existing debug-log actions expose a separate diagnostic surface, but no contextual wait reason or duration is passed to the delayed message. The trace establishes the presentation gap, not whether providers consistently expose trustworthy model/retry/MCP waiting states. Preserve existing foreground-tool, completion, image-generation, and accessibility behavior; https://github.com/microsoft/vscode/issues/347909 concerns a separate provider-specific hang.
- **Open decisions:**
  - Should the delayed footer show the last observed activity explicitly marked as historical when no current wait reason is available, or show an unknown-wait status with diagnostics available separately?
