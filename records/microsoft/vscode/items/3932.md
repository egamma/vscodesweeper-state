# Issue #3932 — Support Elastic Tabstops

[https://github.com/microsoft/vscode/issues/3932](https://github.com/microsoft/vscode/issues/3932)

## Summary

Keep this accepted Backlog request open: current tab rendering still uses fixed stops, while the extensions discussed do not provide buffer-preserving elastic alignment with proportional fonts and reliable cursor movement. With 256 upvotes and no verified older canonical, the remaining work warrants editor-core design rather than a cleanup close.

## Change summary

Support content-dependent tab stops that align adjacent tab-separated rows without inserting alignment spaces, including with proportional fonts.

## Best solution

Provide an opt-in elastic-tabstop capability whose rendered alignment, cursor navigation, and rectangular selection share consistent geometry without rewriting document contents. Editor-core design should establish indentation semantics and performance constraints before implementation.

## Plan brief

- **Likely files:** `src/vs/editor/common/config/editorConfigurationSchema.ts`, `src/vs/editor/common/viewLayout/viewLineRenderer.ts`, `src/vs/editor/common/core/cursorColumns.ts`, `src/vs/editor/common/cursor/cursorMoveOperations.ts`, `src/vs/editor/common/cursor/cursorColumnSelection.ts`, `src/vs/editor/browser/view/domLineBreaksComputer.ts`
- **Validation:** The plan should end with an executable editor scenario containing three adjacent rows with two literal tab-separated columns and unequal cell widths. With elastic alignment enabled, verify matching column boundaries in both monospace and proportional fonts; lengthen one cell and verify neighboring rows realign without text edits, dirty-state changes, or extra undo entries. Exercise vertical navigation, mouse placement, rectangular selection, wrapping, and split views; retain existing fixed-tab behavior when disabled and establish a large-block latency check.
- **Behavior:**

  > Adjacent tab-separated rows should align their corresponding cells using content-dependent tab stops, including with proportional fonts. Editing a cell should update the visual alignment without inserting padding into other rows or changing saved text. Cursor navigation, mouse placement, and rectangular selection should agree with the displayed layout. Acceptance must cover dynamic realignment, unchanged document contents and undo history, and unchanged existing behavior when the capability is disabled.
- **Trace:**

  > Current fixed-stop behavior is visible in _renderLine in src/vs/editor/common/viewLayout/viewLineRenderer.ts and CursorColumns.nextRenderTabStop in src/vs/editor/common/core/cursorColumns.ts. MoveOperations.vertical and ColumnSelection.columnSelect depend on the same fixed visible-column abstraction, while src/vs/editor/browser/view/domLineBreaksComputer.ts also expands tabs using modulo-based widths. The extension reports at https://github.com/microsoft/vscode/issues/3932#issuecomment-2442445991 and https://github.com/microsoft/vscode/issues/3932#issuecomment-2466699878 distinguish visual-only stretching from buffer-mutating padding and document why both remain incomplete. The linked prototype at https://github.com/microsoft/vscode/issues/115307#issuecomment-769783361 is a lead, not proof of a shipped solution. The trace establishes the central gap but does not enumerate every geometry consumer or establish a performant proportional-font design. Preserve existing fixed-tab defaults, document bytes, undo semantics, and non-Latin/bidirectional text support; the maintainer must first settle how leading indentation participates in elastic alignment.
- **Open decisions:**
  - Should leading indentation tabs remain fixed-width and indentation changes start separate alignment blocks, or should elastic column alignment extend across indentation changes?
