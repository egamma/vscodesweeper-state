# Issue #200451 — [themes] globally change saturation and contrast

[https://github.com/microsoft/vscode/issues/200451](https://github.com/microsoft/vscode/issues/200451)

## Summary

This remains a valid backlog feature request with 29 community upvotes. Current main supports individual workbench, TextMate, and semantic-token overrides but has no global saturation, brightness, or contrast adjustment; this issue is also the canonical request for the same theme-wide behavior.

## Change summary

Allow users and theme authors to adjust saturation, brightness, and contrast across an entire color theme without overriding every color individually.

## Best solution

Provide an opt-in, theme-aware global color adjustment that transforms the agreed workbench and editor color domains consistently while preserving explicit overrides and reset behavior. A maintainer should first settle the affected color domains, adjustment semantics, persistence scope, and whether the initial surface is settings-only or interactive.

## Plan brief

- **Likely files:** `src/vs/workbench/services/themes/common/themeConfiguration.ts`, `src/vs/workbench/services/themes/common/colorThemeData.ts`, `src/vs/workbench/services/themes/browser/colorThemeCss.ts`, `src/vs/workbench/services/themes/test/node/tokenStyleResolving.test.ts`
- **Validation:** Add theme-service unit tests using known input colors to verify the agreed saturation, brightness, and contrast adjustments, explicit-override precedence, theme scoping, reset behavior, and unchanged output at neutral values.
- **Behavior:**

  > Users can apply global saturation, brightness, and contrast adjustments to a selected color theme without enumerating individual color IDs. Neutral values leave the theme unchanged, and resetting the configuration restores the original theme exactly. The adjustment applies consistently to the color domains selected by the maintainer, while explicit user overrides have a documented and tested precedence. Switching themes must follow the selected persistence contract without leaking adjustments unexpectedly between themes.
- **Trace:**

  > Theme settings are registered in src/vs/workbench/services/themes/common/themeConfiguration.ts. Workbench colors resolve through ColorThemeData.getColor and explicit overrides are loaded by ColorThemeData.setCustomColors in src/vs/workbench/services/themes/common/colorThemeData.ts; TextMate and semantic-token colors use separate resolution paths in the same class. src/vs/workbench/services/themes/browser/colorThemeCss.ts serializes resolved workbench colors into CSS variables, so a CSS filter applied to the entire workbench would also affect imagery and other non-theme content and must not be assumed equivalent to transforming theme colors. Existing per-color and per-token customization behavior must remain compatible. The uncertainty starts at the public behavior boundary: which color domains participate, how adjustments compose with overrides and alpha, and whether users receive only declarative settings or an interactive control.
- **Open decisions:**
  - Should adjustments cover workbench colors, TextMate token colors, semantic-token colors, or a documented subset of these domains?
  - Do explicit user color overrides participate in the global adjustment or remain literal final colors that take precedence?
  - Are adjustment values global, scoped per named theme, or both through the existing theme-specific configuration syntax?
  - Should the initial product surface be declarative settings only, or also include an interactive preview or slider?
  - What numeric ranges and color-space semantics define saturation, brightness, and contrast, including treatment of alpha and accessibility-oriented high-contrast themes?
