# Issue #342279 — [Copilot harness] User memory is unavailable in Agent Host sessions

[https://github.com/microsoft/vscode/issues/342279](https://github.com/microsoft/vscode/issues/342279)

## Summary

Keep open: local, cross-workspace user memory remains unsupported by the Copilot harness. A maintainer explicitly identifies this issue as tracking user memory; repository-local memory does not satisfy that requirement.

## Change summary

Make locally stored personal memories available across new Copilot Agent Host sessions and workspaces without requiring cloud storage.

## Best solution

Provide optional local, file-based user memory in the Copilot harness, preserving existing personal memories and their management workflow. Coordinate with the broader memory-parity discussion without treating repository-only storage as equivalent.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts`, `src/vs/platform/agentHost/common/copilotCliConfig.ts`, `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCopilotCliSettingsContribution.ts`, `extensions/copilot/src/extension/tools/vscode-node/tools.ts`
- **Validation:** With a synthetic local personal preference visible in Chat: Show Memory Files, start fresh Copilot sessions in two different workspaces and verify that each can retrieve it without cloud memory. Verify disabled behavior, persistence after restart, and that personal memory is not written into either repository.
- **Behavior:**

  > Users should have an optional non-cloud personal-memory workflow in Copilot Agent Host sessions. A preference already stored as local user memory should be accessible in fresh sessions across workspaces, not merely visible in the memory-management UI. Acceptance includes persistence across restart and no placement of personal memories in repository files. Cloud and repository memory behavior must remain distinct.
- **Trace:**

  > The existing memory UI enumerates user files under extension global storage in extensions/copilot/src/extension/tools/vscode-node/tools.ts. CopilotSessionLauncher currently enables SDK memory and optionally selects a repository JSONL store; copilotCliConfig.ts describes that store explicitly as repository-scoped. The workbench settings contribution forwards the repository-local preference, but the traced configuration does not define access to the old personal store. Current documentation explicitly excludes user scope and reuse of Local harness files. https://github.com/microsoft/vscode/issues/344924#issuecomment-6640142116 names this issue as the user-memory tracker. The design must establish access and compatibility across the extension-storage and Agent Host boundary; do not conflate this with session-memory parity or file-edit approval behavior.
- **Open decisions:**
  - Should existing Local harness user-memory files remain the shared authoritative store, or be imported into a separate personal store with explicitly defined synchronization behavior?
  - Should local user-memory access follow the existing memory enablement setting or require a separate opt-in?
