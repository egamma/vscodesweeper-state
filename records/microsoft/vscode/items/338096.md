# Issue #338096 — Remote agent sessions do not discover host MCP servers until messaged locally

[https://github.com/microsoft/vscode/issues/338096](https://github.com/microsoft/vscode/issues/338096)

## Summary

Real, well-described bug: remote agent sessions don't pick up host-local (COPILOT_HOME) MCP servers until the same session is also messaged locally on that host. Code comments corroborate the mechanism (CopilotHome MCP servers use 'RuntimeDiscovered' delivery, discovered only by 'the window's own Copilot host on the same machine'), but the exact remote-connection lifecycle bug needs a maintainer trace before a fix lands.

## Change summary

A remote agent session started from a laptop against a dev box does not see MCP servers (e.g. Notion) configured on the dev box until the same session is first messaged locally on the dev box, after which it becomes visible remotely too.

## Best solution

Trace the remote connection/process lifecycle (sshRemoteAgentHostServiceImpl / agentHostConnectionsService / the per-machine Copilot host process cache) to find why runtime MCP discovery on the host only happens after a local message reaches it, and make host-side runtime discovery (e.g. reading ~/.copilot/mcp-config.json) happen as part of establishing the remote session rather than depending on a local trigger.

- **Trace:**

  > RuntimeDiscovered/CopilotHome MCP servers are meant to be found by the host process's own runtime scan of COPILOT_HOME/mcp-config.json rather than being forwarded by the client (agentHostLocalCustomizations.ts, agentHostMcpServerSupport.ts). The report shows this scan does not happen (or its result isn't surfaced) for a session until the same session receives a message routed through the local connection on that host. Where the uncertainty starts: which component gates this — a lazily-spawned/cached host process reused across connection types (sshRemoteAgentHostServiceImpl.ts, agentHostConnectionsService.ts), or a resync-on-message path that only refreshes runtime-discovered servers for local-origin messages. That lifecycle was not traced to a specific line in this pass.
- **Open decisions:**
  - Should host-side runtime MCP discovery run eagerly when a remote session/connection to that host is established, regardless of message origin, or should remote message handling be changed to trigger the same refresh a local message does?
  - Is there a single host process per machine shared across local and remote connections (in which case the discovery timing bug is in the resync trigger), or does the remote path spawn/attach to a distinct process that needs the same env/discovery setup as the local one?
