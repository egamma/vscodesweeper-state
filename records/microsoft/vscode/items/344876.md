# Issue #344876 — Canvases should adapt to the host app and its theme

[https://github.com/microsoft/vscode/issues/344876](https://github.com/microsoft/vscode/issues/344876)

## Summary

Keep open: existing theme propagation styles browser inspection overlays, not canvas-provider content, so the requested presentation contract remains a real gap. This team-authored request needs cross-host contract design; no verified duplicate or explicitly linked fix was found.

## Change summary

Expose presenting-app identity and live semantic theme context to canvas providers without changing canvas input or identity.

## Best solution

Define a documented, optional cross-host presentation contract that lets canvas content follow the presenting application's semantic colors and theme changes while preserving content, state, actions, and identity. Agree on compatibility and fallback semantics before implementing the VS Code bridge.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/canvases/electron-browser/canvasService.ts`, `src/vs/workbench/contrib/canvases/electron-browser/canvasView.ts`, `src/vs/workbench/contrib/browserView/electron-browser/browserViewWorkbenchService.ts`, `src/vs/platform/browserView/common/browserView.ts`, `src/vs/platform/browserView/electron-main/browserViewMainService.ts`, `src/vs/platform/browserView/electron-browser/preload-browserView.ts`, `src/vs/platform/agentHost/test/node/copilotSdkCanvas.integrationTest.ts`
- **Validation:** Use one instrumented canvas provider with identical open input in both applications and verify distinct host identities and semantic styling. In VS Code, switch dark, light, and high-contrast themes while the page remains open and confirm live updates without losing state; exercise missing presentation context and verify the documented fallback. Add contract and browser-boundary integration coverage after the delivery contract is agreed.
- **Behavior:**

  > One canvas implementation can identify its presenting application and use documented semantic presentation values without user-agent inference or caller-supplied appearance input. In VS Code, changing the active theme updates the already-open canvas without reopening it or changing its content, state, actions, or identity. Hosts without presentation support produce a documented, predictable fallback. Acceptance includes the same provider and input in both applications, live theme changes, and contract and integration coverage.
- **Trace:**

  > CanvasService creates an external browser model from the provider source URL, and CanvasView attaches the retained model to WebContentsViewHost. CanvasEditor receives IThemeService only through its EditorPane base. BrowserViewWorkbenchService already observes theme changes and sends semantic widget colors through updateWindowConfiguration, but BrowserViewMainService delivers these to the inspector and the preload applies them only to picker overlays. This existing mechanism is not evidence that providers receive presentation context. The tracked SDK integration test loads extension bootstrap assets from the bundled runtime; the generated CanvasHostContext declaration and the other application's consumer were not established in this review. Preserve canvas open input, identity, lifecycle, ordinary browser behavior, and existing inspection-overlay theming. The remaining uncertainty is the shared public contract and its delivery and compatibility semantics, not the requested user outcome.
- **Open decisions:**
  - Which host identity values and semantic theme roles form the documented cross-host contract, including high-contrast presentation?
  - What provider-visible initial-delivery and live-update guarantees does presentation context provide?
  - What exact presentation values or absence semantics should providers observe when a host lacks support or supplies only partial context?
