# Issue #156160 — Option to save panel layouts globally instead of per-workspace.

[https://github.com/microsoft/vscode/issues/156160](https://github.com/microsoft/vscode/issues/156160)

## Summary

Keep open: individual view sizes and collapsed states remain workspace-scoped, so current global layout persistence does not cover the reporter's central request. The issue has 20 upvotes, an accepted Backlog milestone, and maintainer interest; the verified related issues do not provide a duplicate target.

## Change summary

Allow a preferred arrangement of view sizes and expanded or collapsed panes to be reused across newly opened folders instead of configured separately in each workspace.

## Best solution

Provide a reusable, profile-wide default for individual view geometry and collapsed state in the view-container persistence layer. Decide whether it seeds new workspaces while preserving workspace overrides or becomes an explicitly selected shared layout mode.

## Plan brief

- **Likely files:** `src/vs/workbench/services/views/common/viewContainerModel.ts`, `src/vs/workbench/browser/parts/views/viewPaneContainer.ts`, `src/vs/workbench/browser/workbench.contribution.ts`, `src/vs/workbench/services/views/test/browser/viewContainerModel.test.ts`
- **Validation:** Extend the viewContainerModel unit suite to exercise separate workspace storage with shared profile storage and verify the selected default/override semantics. Manually arrange Source Control, Search, and Outline together in the bottom panel, resize and collapse individual panes, then open a fresh folder using the same profile and verify that the preferred arrangement is restored; also verify existing-workspace and concurrent-window behavior against the agreed contract.
- **Behavior:**

  > Users who configure individual panes in a panel or sidebar should be able to reuse their preferred sizes and expanded or collapsed states when opening new folders. The original report demonstrates Source Control, Search, and Outline returning to unwanted proportions and collapse states despite an established arrangement elsewhere. Acceptance must cover a fresh workspace, reopening an existing workspace, and multiple windows sharing a profile. The maintainer must settle whether this is a reusable initial default or an ongoing shared layout mode before implementation.
- **Trace:**

  > ViewDescriptorsState in src/vs/workbench/services/views/common/viewContainerModel.ts separates profile-level visibility/order from workspace-level size/collapsed state; initialize has no profile geometry fallback. ViewPaneContainer.saveViewSizes and restoreViewSizes in src/vs/workbench/browser/parts/views/viewPaneContainer.ts connect sash changes and first layout to that model, falling back to weighted initial sizes when no workspace size exists. Overall workbench-part dimensions already have profile storage in src/vs/workbench/browser/layout.ts, so they must not be confused with the individual view geometry requested here. Preserve unrelated view ordering, visibility, and overall layout behavior unless the agreed product contract explicitly changes them. https://github.com/microsoft/vscode/issues/153513 addressed a different workspace-view concern, and https://github.com/microsoft/vscode/issues/75017 requests workspace-specific sidebar widths rather than this shared default. The remaining uncertainty is the user-visible persistence and synchronization contract, not the existence of the current storage gap.
- **Open decisions:**
  - Should the reusable layout only initialize previously unseen workspaces, preserving later workspace-specific adjustments, or should an opt-in mode share individual view geometry across all workspaces?
  - Should the reusable layout update automatically from the most recently adjusted workspace, or only when the user explicitly saves a preferred layout?
  - If a shared layout mode is chosen, should resizing or collapsing panes update other open windows immediately, or take effect only when their layout is next restored?
