# Issue #291269 — class names aren't (internal) API

[https://github.com/microsoft/vscode/issues/291269](https://github.com/microsoft/vscode/issues/291269)

## Summary

The architectural debt remains: current BrowserOverlayManager still discovers overlays through private CSS class names, including suggest-details-container. Keep this accepted Backlog item open; the available lifecycle events do not cover the full detection contract.

## Change summary

Replace the integrated browser's dependency on incidental CSS class names with an explicit internal contract for overlay presence and layout.

## Best solution

Provide an internal overlay lifecycle and geometry contract that the browser can consume without knowing individual widgets' CSS classes. Preserve existing overlap, stacking, shadow-DOM, and native-page visibility behavior while establishing the producer coverage needed for migration.

## Evidence

- **Class-name coupling remains:** src/vs/workbench/contrib/browserView/electron-browser/overlayManager.ts defines OVERLAY_DEFINITIONS using monaco-menu-container, editor-widget, suggest-details-container, notification-toast-container, and other private class names. Its constructor builds getElementsByClassName collections; overlays() repeats the selectors inside shadow roots.
- **Existing event does not remove the dependency:** BrowserOverlayManager.onDidChangeOverlayState is generated from MutationObservers over the class-selected elements. It reports the detector's results rather than providing an independent lifecycle contract from overlay producers.
- **Live consumer:** src/vs/workbench/contrib/browserView/electron-browser/webContentsViewHost.ts subscribes to onDidChangeOverlayState and calls getOverlappingOverlays in _refreshOverlayObscured. The resulting _overlayObscured state drives native-page visibility, and notification overlays additionally control the paused message.
- **Partial lifecycle infrastructure:** src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts owns add/layout/remove operations for content and overlay widgets. src/vs/platform/contextview/browser/contextView.ts exposes context-menu show/hide events, but those events do not describe all overlay types or their geometry and do not replace the browser's current discovery mechanism.
- **Existing behavioral coverage:** src/vs/workbench/contrib/browserView/test/electron-browser/overlayManager.test.ts covers overlapping and nonoverlapping elements, modal and spotlight overlays, detached webview content, transparent context-view blockers, and notification-versus-dialog stacking. These are preservation constraints, not evidence that class-name independence has been implemented.
