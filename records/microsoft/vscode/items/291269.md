# Issue #291269 — class names aren't (internal) API

[https://github.com/microsoft/vscode/issues/291269](https://github.com/microsoft/vscode/issues/291269)

## Summary

Keep open: integrated-browser overlay detection still depends on private CSS class names, including the exact example in the report. The existing browser-integration routing is appropriate; replacing that coupling needs a cross-component lifecycle design.

## Change summary

Replace CSS-class-based integrated-browser overlay discovery with an explicit internal contract for overlay visibility and layout.

## Best solution

Provide a supported internal overlay lifecycle contract that browser obscuring can consume without knowing widget styling details. Preserve overlap detection, native-page visibility, screenshot substitution, and notification-specific pause behavior.

Preserve existing modal, notification, ancestor, shadow-root, and hit-testing behavior; verify the native visibility handoff in an Electron workbench scenario.
- **Behavior:**

  > Integrated-browser obscuring must not depend on private styling class names of workbench widgets. Showing, hiding, or moving an overlapping overlay must update browser availability through a supported internal lifecycle contract. Renaming an overlay's CSS classes must not change that behavior. Non-overlapping overlays and overlays containing the browser must not spuriously obscure it, and notification-specific pause behavior must remain unchanged.
- **Trace:**

  > BrowserOverlayManager in src/vs/workbench/contrib/browserView/electron-browser/overlayManager.ts discovers overlays from OVERLAY_DEFINITIONS via live class collections and shadow-root selectors, then observes their DOM mutations. Its onDidChangeOverlayState event therefore retains the coupling reported at https://github.com/microsoft/vscode/issues/291269. WebContentsViewHost._refreshOverlayObscured consumes that discovery result to coordinate browser visibility and notification messaging. CodeEditorWidget owns content/overlay widget add, layout, and remove operations, while menus, quick input, and dialogs expose separate lifecycle surfaces. The uncertainty begins at the complete inventory and common contract for these producers, including actual rendered layout and shadow-root coverage; editor widget events alone do not establish coverage for the whole current manager. Preserve existing geometry, stacking, focus, screenshot, and visibility semantics rather than redesigning browser behavior. https://github.com/microsoft/vscode/issues/130217 concerns z-index consistency and is related context, not a duplicate.

## Evidence

- **Debt remains on current main:** src/vs/workbench/contrib/browserView/electron-browser/overlayManager.ts:21–35 defines OVERLAY_DEFINITIONS using private classes such as suggest-details-container, editor-widget, monaco-hover, and context-view. The constructor creates getElementsByClassName collections, and overlays() repeats class-based discovery inside shadow roots.
- **Existing event does not remove the dependency:** BrowserOverlayManager.onDidChangeOverlayState is generated from structural and element MutationObservers over class-discovered elements. It exposes the heuristic's result, not an explicit lifecycle contract supplied by the widgets themselves.
- **Consumer and preservation boundary:** src/vs/workbench/contrib/browserView/electron-browser/webContentsViewHost.ts subscribes to onDidChangeOverlayState and calls getOverlappingOverlays in _refreshOverlayObscured. The result controls native-page visibility and the notification pause message; overlayManager.ts also excludes ancestor overlays and performs geometry and topmost-element checks.
- **Lifecycle design spans multiple producers:** src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts:1539–1617 owns content/overlay widget add, layout, and removal operations. Separate context-menu, quick-input, and dialog lifecycle events exist in src/vs/platform/contextview/browser/contextView.ts, src/vs/platform/quickinput/common/quickInput.ts, and src/vs/platform/dialogs/common/dialogs.ts. These separate surfaces do not currently supply the browser manager with a unified class-independent discovery contract.
