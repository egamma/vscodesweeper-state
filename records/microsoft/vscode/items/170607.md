# Issue #170607 — set decoration's opacity is not working

[https://github.com/microsoft/vscode/issues/170607](https://github.com/microsoft/vscode/issues/170607)

## Summary

The issue remains necessary: current main still applies unused-code opacity to the editor line after decoration CSS, so an extension decoration with `opacity: "1"` cannot keep its `before` content fully opaque.

## Change summary

Prevent unused-code fading from reducing the opacity of extension-provided text decoration content.

## Best solution

Adjust editor decoration styling so diagnostic fading affects the unused text without compositing extension-provided `before` or `after` content beneath the same opacity, while preserving current unused-code appearance.

## Plan brief

- **Likely files:** `src/vs/editor/browser/viewParts/decorations/decorations.ts`, `src/vs/editor/test/browser/viewParts/decorations/decorations.test.ts`
- **Validation:** Add an editor decoration rendering test covering unused-code opacity combined with a `before` decoration whose own opacity is `1`; verify the generated/rendered decoration remains opaque while the underlying unused text stays dimmed, and run the targeted editor decorations test suite.
- **Behavior:**

  > When diagnostics fade unused code, extension-provided `before` and `after` decoration content with explicit opacity must retain that opacity rather than inheriting the visual fade from the decorated text. The unused source text should remain dimmed, and ordinary decorations and diagnostic styling must remain unchanged. Acceptance requires a focused rendering test for unused text plus an opaque injected decoration.
- **Trace:**

  > Extension decoration types enter through MainThreadTextEditors in src/vs/workbench/api/browser/mainThreadEditors.ts and are converted into CSS by DecorationsOverlay in src/vs/editor/browser/viewParts/decorations/decorations.ts. The current CSS applies line/content opacity in a way that composites generated `::before`/`::after` decoration content with its parent, so a child opacity of 1 cannot restore full opacity. The defect is visible from this CSS composition path on current main; the uncertainty starts at whether unused fading should target text-only spans, use a non-compositing color treatment, or isolate injected content structurally. The boundary is editor decoration rendering: do not remove unused-code fading or change the public decoration API.
- **Open decisions:**
  - Should unused-code fading be restricted to source-text spans, or should injected decoration content be isolated from ancestor opacity through a different rendering structure?
  - Which approach preserves existing diagnostic and theme behavior without changing opacity semantics for ordinary inline and whole-line decorations?

- **current source:** On current main, src/vs/editor/browser/viewParts/decorations/decorations.ts emits injected-text `before`/`after` CSS rules first and then class-name rules; an unused-code rule that applies opacity to the decorated text container therefore also composites its generated decoration content.
- **API path:** src/vs/workbench/api/browser/mainThreadEditors.ts registers extension decoration types with the editor decoration service, and src/vs/editor/browser/viewParts/decorations/decorations.ts maps `opacity` plus `before`/`after` render options into generated CSS. The reported configuration follows this supported path.
