# Issue #245757 — Feature Request: Expose Command Trigger Source (Keyboard vs Mouse vs Menu)

[https://github.com/microsoft/vscode/issues/245757](https://github.com/microsoft/vscode/issues/245757)

## Summary

Keep this accepted API request open: command-origin information is still unavailable to extensions, and the request earned 23 upvotes and promotion to Backlog. Historical concerns about command observation require an API design review, not a decline of this subsequently accepted request.

## Change summary

Expose reliable command-invocation origin metadata to extensions for keyboard shortcuts, menus or toolbars, the command palette, and programmatic execution.

## Best solution

Design a narrowly scoped command-origin API that preserves command arguments and avoids exposing internal objects or imposing substantial per-command overhead. Resolve its observation scope and origin semantics with the API owners before implementation.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/platform/commands/common/commands.ts`, `src/vs/workbench/services/commands/common/commandService.ts`, `src/vs/platform/keybinding/common/abstractKeybindingService.ts`, `src/vs/platform/quickinput/browser/commandsQuickAccess.ts`, `src/vs/workbench/api/browser/mainThreadCommands.ts`, `src/vs/workbench/api/common/extHostCommands.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`
- **Validation:** After agreeing on the API contract, use a test extension to invoke the same contributed command through a keybinding, toolbar or context menu, command palette, and vscode.commands.executeCommand; verify the agreed origin values and unchanged arguments/results. Add targeted command-service and extension-host bridge tests for metadata propagation and nested execution, including a built-in command if global observation is approved.
- **Behavior:**

  > Extensions cannot reliably distinguish how a native or contributed command was invoked. The requested capability identifies keyboard-shortcut, menu or toolbar, command-palette, and API execution without changing existing command arguments or results. Acceptance should exercise the same command through each supported entry point and establish predictable behavior for nested or unattributable executions. The public observation scope and the distinction between input device and invoking UI surface remain to be agreed.
- **Trace:**

  > The public commands namespace in src/vscode-dts/vscode.d.ts has no onDidExecuteCommand event; the report refers to an internal or formerly proposed capability. ICommandEvent in src/vs/platform/commands/common/commands.ts and CommandService._tryExecuteCommand in src/vs/workbench/services/commands/common/commandService.ts carry only commandId and args. Keyboard dispatch and command quick access already know their entry-point source for internal telemetry, but their executeCommand calls do not propagate it as metadata. MainThreadCommands.$registerCommand forwards contributed executions to the extension host without origin information. The trace establishes the missing contract, not complete coverage of every menu or native command path. Preserve command arguments, activation behavior, and existing telemetry semantics; do not expose internal argument objects as an incidental part of this request. Historical API concerns are recorded at https://github.com/microsoft/vscode/issues/78091#issuecomment-518545491 and https://github.com/microsoft/vscode/issues/78091#issuecomment-521640092.
- **Open decisions:**
  - Should extensions receive origin metadata only for their own registered command handlers, or may they observe execution of built-in and other extensions' commands?
  - Should origin describe the invoking surface, the physical input device, or both—for example, how should a menu item or command-palette entry selected with the keyboard be classified?
  - For commands invoked programmatically by another command, should metadata report the immediate API invocation, preserve the initiating user gesture, or expose both?
