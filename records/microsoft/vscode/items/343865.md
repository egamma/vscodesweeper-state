# Issue #343865 — Voice mode can't actually interact with existing sessions

[https://github.com/microsoft/vscode/issues/343865](https://github.com/microsoft/vscode/issues/343865)

## Summary

Keep open as a request for cross-session voice interaction. Current GPT Live routing supports replies to the bound chat, but seeing other sessions does not establish that spoken instructions can target them; this collaborator-authored feedback should not be declined as intentional behavior.

## Change summary

Let voice mode answer pending inputs and send follow-up prompts directly to another existing session instead of delegating those instructions as a new coding task.

## Best solution

Define and implement an explicit cross-session targeting contract for GPT Live voice mode, with disambiguation and observable delivery outcomes. Preserve the existing safeguards that prevent ambiguous speech or stale context from answering the wrong session.

- **Validation:** Exercise GPT Live with two distinctly named existing sessions: ask it to send a follow-up to the non-active session and answer that session's pending question. Verify delivery to the intended existing session, no accidental new session or request explaining how to perform the action, and no mutation after an ambiguous target or stale pending prompt. Extend the voice routing and dispatch tests to cover the selected targeting contract.
- **Behavior:**

  > A user can ask voice mode to send a follow-up to an identifiable existing session or respond to that session's pending input without manually switching chats. The instruction must reach the intended session rather than becoming a coding task about how to interact with it. Ambiguous targets require clarification, and stale pending inputs must not be answered. Voice mode must distinguish successful delivery from failure.
- **Trace:**

  > The report arose while testing GPT Live session awareness in https://github.com/microsoft/vscode/issues/343523, whose documented scope includes status briefings about other sessions but interactions with the bound input. VoiceLiveInputRouter.captureTarget in src/vs/workbench/contrib/chat/common/voiceClient/voiceLiveInputRouter.ts captures the active session; resolve routes text and pending answers against that captured target. VoiceToolDispatchService in src/vs/workbench/contrib/chat/browser/voiceClient/voiceToolDispatchService.ts already provides explicit session resolution and guarded pending-response dispatch, so the missing capability is not the total absence of session-action primitives. The uncertainty is how GPT Live should resolve and authorize a spoken reference to a different session and whether that action changes the ongoing voice target. Preserve active-input behavior, pending-occurrence identity checks, and explicit approval requirements; do not infer authorization from session visibility alone.
- **Open decisions:**
  - Should naming another session perform a one-off action while preserving the current voice target, or switch the voice conversation's target to that session?
  - Should cross-session control cover both follow-up prompts and pending-input responses in the first increment, or initially expose only one of those capabilities?
