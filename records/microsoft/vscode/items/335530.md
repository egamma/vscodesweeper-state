# Issue #335530 — Make tokenization registries and token palettes scopeable for multi-theme fixtures

[https://github.com/microsoft/vscode/issues/335530](https://github.com/microsoft/vscode/issues/335530)

## Summary

Keep this infrastructure task open: current source still couples model tokenization and palette-dependent rendering to process-wide state. The merged fixture PR explicitly leaves scoped multi-theme ownership to this issue.

## Change summary

Make tokenization registries, TextMate factories, palettes, and rendering dependencies scope-owned so differently themed editor fixtures can coexist in one JavaScript context.

## Best solution

Establish consistent tokenization and palette ownership from text models through editor rendering, with independently disposable fixture scopes and unchanged production and standalone defaults. Plan the cross-cutting migration before implementation rather than extending the current monochrome fixture workaround.

## Plan brief

- **Likely files:** `src/vs/editor/common/languages.ts`, `src/vs/editor/common/tokenizationRegistry.ts`, `src/vs/editor/common/model/tokens/tokenizerSyntaxTokenBackend.ts`, `src/vs/editor/common/viewModel/minimapTokensColorTracker.ts`, `src/vs/editor/common/viewModel/viewContext.ts`, `src/vs/editor/common/viewModel/viewModelImpl.ts`, `src/vs/editor/browser/viewParts/minimap/minimap.ts`, `src/vs/editor/browser/controller/editContext/textArea/textAreaEditContext.ts`, `src/vs/editor/standalone/browser/standaloneThemeService.ts`, `src/vs/workbench/services/textMate/browser/textMateTokenizationFeatureImpl.ts`
- **Validation:** Add production-level tests for independent registries/model tokenization, lazy registration, palette-change notifications, and disposal isolation. Use the existing Component Explorer to mount Dark, Light, and both high-contrast editors concurrently with real TextMate grammars, inspect text/font styles and minimap colors, exercise clipboard/IME colors, then change and dispose scopes in different orders; unrelated editors must retain their tokens and colors. Preserve existing production and standalone behavior.
- **Behavior:**

  > Dark, Light, and both high-contrast editor fixtures must coexist in one JavaScript context with real TextMate syntax highlighting and matching palettes. Original language IDs, grammar injections, token-type metadata, and language features must remain intact. Theme changes or disposal in one fixture must not retokenize or recolor another fixture, including minimap, clipboard, and IME paths. Production and standalone defaults, lazy registration, and palette notifications must remain compatible; iframe isolation and semantic-highlighting changes are outside this task.
- **Trace:**

  > TokenizationRegistry is exported globally from src/vs/editor/common/languages.ts, and TokenizerSyntaxTokenBackend directly subscribes to it and retrieves supports from it. The independently constructible registry in src/vs/editor/common/tokenizationRegistry.ts therefore does not yet establish model-level scope ownership. MinimapTokensColorTracker remains a singleton, Minimap obtains it directly, and ViewModel clipboard HTML reads the global palette; ViewContext currently propagates no registry or palette dependency. TextMateTokenizationFeature._updateTheme publishes the palette globally and forwards theme changes to background tokenization. The merged https://github.com/microsoft/vscode/pull/335568 installs shared Dark TextMate support and uses monochrome non-Dark CSS in fixtureSyntaxHighlighting.ts, explicitly deferring full isolation to this issue. The trace establishes these coupling points, but the complete migration boundary across indirect consumers, background tokenization, and standalone APIs still needs to be enumerated. Preserve default global behavior for existing consumers and keep semantic highlighting separate.
