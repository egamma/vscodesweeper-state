- **Canonical discussion establishes the UX gap:** In https://github.com/microsoft/vscode/issues/193935#issuecomment-1736526892, the reporter confirms editor-based authoring works but describes the lack of specific feedback as confusing. The maintainer explains the existing git.useEditorAsCommitInput setting and why disabling the commit button is unsuitable in https://github.com/microsoft/vscode/issues/193935#issuecomment-1737592641.
- **Current source explains the apparent stall:** extensions/git/package.json registers git.useEditorAsCommitInput with default true. Commands.commitWithAnyInput in extensions/git/src/commands.ts:2576-2612 skips the message input prompt when that setting is enabled. GitEditor.handle in extensions/git/src/gitEditor.ts opens the message document and waits for its tab to close; git.commitMessageAccept closes that tab. This explains a pending commit without establishing an actual unresponsive UI.
- **Existing capability is only partial coverage:** git.useEditorAsCommitInput=false provides a 'Please provide a commit message' input prompt, and git.commitMessageAccept provides the editor's Commit action. Neither is the requested explicit guidance explaining the default editor-based workflow, so existing authoring support alone is not grounds for an as-designed close.
