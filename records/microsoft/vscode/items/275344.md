# Issue #275344 — Can't actually save prompt from `/savePrompt` with a manual save

[https://github.com/microsoft/vscode/issues/275344](https://github.com/microsoft/vscode/issues/275344)

## Summary

The bug remains source-reproducible on current main: normal Save treats the generated named untitled prompt as a filesystem path and bypasses the prompt-location picker, while Keep attempts the same save and suppresses its failure. This older issue is the canonical report and should remain open for a coordinated save-lifecycle fix.

## Change summary

Allow prompt files generated by `/savePrompt` to be persisted successfully through normal Save and the chat-edit Keep flow.

## Best solution

Generated prompt editors should save through the valid prompt-location workflow rather than attempting to write their synthetic untitled path to the filesystem. The behavior while chat edits are pending needs one explicit decision: whether Save or Keep also accepts the pending edit, or whether persistence remains a separate step.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/promptSyntax/saveAsPromptFileActions.ts`, `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedDocumentEntry.ts`, `src/vs/workbench/contrib/chat/test/browser/chatEditing/chatEditingActions.test.ts`
- **Validation:** Add focused tests covering Cmd/Ctrl+S and Keep for a generated named untitled prompt, then run `./scripts/test.sh --grep "Save As Prompt File|untitled prompt"`; both paths must avoid a root-path write and reach the agreed prompt-location behavior.
- **Behavior:**

  > A prompt generated by `/savePrompt` can be persisted with normal Cmd/Ctrl+S without attempting to write to the filesystem root. Using Keep must not silently lose or leave unsaved the generated prompt. The chosen flow must preserve the prompt filename suggestion and restrict the destination to valid user or workspace prompt locations. Existing Save and Keep behavior for ordinary files and non-prompt untitled editors must remain unchanged.
- **Trace:**

  > The generated editor has a meaningful `untitled:` path, which editorCommands.ts interprets as an associated filesystem resource. TextFileService.save() consequently skips its picker and maps that path to the default filesystem scheme, producing the reported root-path write. The prompt-specific action in saveAsPromptFileActions.ts already has the correct destination and naming flow, but it is only shown once the chat editing state is no longer Modified. ChatEditingModifiedDocumentEntry._doAccept() invokes the generic save path and suppresses its error. Keep the correction scoped to generated prompt handling; do not change generic associated-untitled save semantics for unrelated editors. The same observable symptom in https://github.com/microsoft/vscode/issues/277930 was consolidated into this issue.
- **Open decisions:**
  - When Cmd/Ctrl+S is invoked while the generated prompt still has pending chat edits, should saving implicitly Keep those edits, or should the user first resolve the edit before choosing a prompt destination?
  - Should Keep immediately open the prompt destination flow and persist the file, or should it only accept the edit and leave persistence to a subsequent Save action?

## Evidence

- **normal save path:** src/vs/workbench/contrib/files/browser/fileCommands.ts binds Cmd/Ctrl+S to `workbench.action.files.save`. In src/vs/workbench/services/textfile/browser/textFileService.ts, `save()` skips the file picker for an untitled model with `hasAssociatedFilePath` and `suggestSavePath()` converts its meaningful untitled path directly to the default filesystem scheme.
- **named untitled association:** src/vs/workbench/browser/parts/editor/editorCommands.ts treats a named `untitled:` resource as an associated filesystem resource when opening it, explaining why a generated name such as `/backportPullRequest.prompt.md` is later saved at the filesystem root.
- **prompt-specific path:** src/vs/workbench/contrib/chat/browser/promptSyntax/saveAsPromptFileActions.ts implements `workbench.action.chat.save-as-prompt` using `askForPromptSourceFolder` and `askForPromptFileName`, but exposes it only after the chat editing entry is no longer Modified and does not route normal Save through it.
- **Keep path:** ChatEditingModifiedDocumentEntry._doAccept() in src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedDocumentEntry.ts calls `ITextFileService.save()` for manual-save configurations and catches the failure without surfacing it, so Keep can leave this untitled prompt unpersisted.
