# Issue #318362 — debug configuration doesn't restore to last selected after Reload Window(Remote SSH, multi-repo .code-workspace)

[https://github.com/microsoft/vscode/issues/318362](https://github.com/microsoft/vscode/issues/318362)

## Summary

This remains a valid debug configuration restoration bug: a maintainer confirmed that restoration works locally but fails in Remote SSH, and current source still contains a startup fallback that can replace the persisted folder selection.

## Change summary

Restore the last selected debug configuration and its workspace folder after reloading a Remote SSH multi-root workspace.

## Best solution

Preserve the persisted debug configuration folder and name until remote workspace-folder launch configurations are available, then restore that exact selection without allowing the startup fallback to overwrite it.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts`, `src/vs/workbench/contrib/debug/test/browser/debugConfigurationManager.test.ts`
- **Validation:** Extend the debugConfigurationManager unit suite with two workspace folders and a persisted selection in the second folder; simulate its launch configurations becoming available after manager construction, then assert that the selected launch and configuration remain the persisted pair after the configuration-change event.
- **Behavior:**

  > In a multi-root Remote SSH workspace, reloading the window restores both the workspace folder and launch configuration selected before reload. Restoration must not switch to the first folder merely because remote launch configuration data was unavailable during early startup. Local-window restoration and ordinary first-time selection behavior remain unchanged. Acceptance is a regression test in the debug configuration manager suite covering delayed availability of the saved folder's configuration.
- **Trace:**

  > ConfigurationManager in src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts reads `debug.selectedroot` and `debug.selectedconfigname` during construction. It only uses the persisted launch when that launch already reports configuration names; otherwise `selectConfiguration(undefined, previousSelectedName)` chooses the last-active or first configured folder and stores that fallback over `debug.selectedroot`. The maintainer confirmation at https://github.com/microsoft/vscode/issues/318362 establishes the local-versus-Remote-SSH difference, but the trace has not yet established whether remote configuration initialization timing or URI/storage identity causes the saved launch to appear empty. Start by representing that remote startup ordering in src/vs/workbench/contrib/debug/test/browser/debugConfigurationManager.test.ts. Keep dynamic configurations, single-folder selection, and history-based initial selection outside the regression scope.

## Evidence

- **confirmed reproduction:** A VS Code maintainer confirmed on https://github.com/microsoft/vscode/issues/318362 that the selection restores in a local window but not through Remote SSH.
- **restore path:** src/vs/workbench/contrib/debug/browser/debugConfigurationManager.ts reads `debug.selectedroot` and `debug.selectedconfigname` during ConfigurationManager construction, but restores the saved launch only when `previousSelectedLaunch.getConfigurationNames().length` is already nonzero.
- **fallback behavior:** When the saved launch has no configurations available during initialization, ConfigurationManager calls `selectConfiguration(undefined, previousSelectedName)`. That method chooses the last-active folder or first folder with configurations and immediately stores that launch as `debug.selectedroot`, matching the reported switch to the alphabetically first repository.
- **test gap:** src/vs/workbench/contrib/debug/test/browser/debugConfigurationManager.test.ts covers configuration visibility and malformed launch entries, but has no multi-root restoration test with configurations becoming available after manager construction.
- **canonical search:** Searches for open issues involving last-selected debug configurations, Remote SSH, multi-root workspaces, and reload did not identify an older issue with the same observable symptom.
