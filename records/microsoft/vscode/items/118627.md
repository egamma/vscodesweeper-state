# Issue #118627 — Git - Apply encoding to all sides of diff

[https://github.com/microsoft/vscode/issues/118627](https://github.com/microsoft/vscode/issues/118627)

## Summary

Keep open: manually changing encoding already affects both diff sides, but automatic application of the associated file's encoding remains a separate gap. This accepted Backlog item also owns a maintainer-confirmed duplicate and has a recent Shift_JIS regression report.

## Change summary

Automatically use the appropriate file encoding when loading both committed and working-tree content in Git diffs.

## Best solution

Make Git revision content honor the associated file's applicable encoding configuration without requiring manual reopening. Establish how explicitly selected working-tree encodings carry over, while preserving cases where Git attributes intentionally give committed and working-tree bytes different encodings.

## Plan brief

- **Likely files:** `extensions/git/src/fileSystemProvider.ts`, `extensions/git/src/uri.ts`, `src/vs/workbench/services/textfile/browser/textFileService.ts`, `src/vs/editor/common/services/textResourceConfigurationService.ts`, `src/vs/workbench/browser/parts/editor/editorStatus.ts`
- **Validation:** In a multi-root workspace, configure a folder's files.encoding as gbk, commit a Chinese-text file without working-tree-encoding attributes, edit one line, and open its Git diff: both sides must display readable text and only the actual change. Repeat with language-scoped shiftjis and with a manually reopened working-tree file. Include a working-tree-encoding repository as a boundary check so differing byte encodings are not blindly treated as identical.
- **Behavior:**

  > Git diffs of legacy-encoded files should show readable committed and working-tree text without a manual encoding correction when the associated file's configuration specifies the encoding. The original report supplies a GBK save/commit/edit sequence; a later report describes the same committed-side failure with Shift_JIS. Acceptance includes folder-scoped and language-scoped settings and accurate changed-line highlighting. Repositories whose Git attributes deliberately transform encoding must remain correct rather than receiving an unconditional same-encoding rule.
- **Trace:**

  > GitFileSystemProvider.readFile in extensions/git/src/fileSystemProvider.ts supplies revision bytes, while extensions/git/src/uri.ts creates git resources retaining the associated file path. EncodingOracle in src/vs/workbench/services/textfile/browser/textFileService.ts chooses encoding using the supplied resource, and TextResourceConfigurationService in src/vs/editor/common/services/textResourceConfigurationService.ts forwards that resource into configuration resolution. The folder-configuration lookup in src/vs/platform/configuration/common/configurationModels.ts depends on workspace.getFolder(resource); the associated-file lookup gap is corroborated by https://github.com/microsoft/vscode/issues/194986#issuecomment-1875290308. Manual Change File Encoding already reaches both sides through SideBySideEditorEncodingSupport in editorStatus.ts, so manual application is not the missing capability. The trace establishes a configuration-resolution gap but does not prove the reported 1.108.2 regression's introducing change. Keep diff comparison algorithms, unrelated URI schemes, and Git attribute transformations outside the ordinary legacy-file case; https://github.com/microsoft/vscode/issues/127441 tracks the latter separately.
- **Open decisions:**
  - When the working-tree file was manually reopened with an encoding that differs from files.encoding, should a newly opened Git diff inherit that explicit selection for revision content, or use configuration and detection independently?
