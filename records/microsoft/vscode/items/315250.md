# Issue #315250 — Moving multiple tabs reverses their order

[https://github.com/microsoft/vscode/issues/315250](https://github.com/microsoft/vscode/issues/315250)

## Summary

The bug remains on current main: moving selected tabs across groups preserves the relative order of inactive tabs but always places the active selected editor first. The behavior is directly traceable in the shared multi-editor move preparation path and has no matching canonical issue or merged fix.

## Change summary

Moving multiple selected editor tabs to another group should retain their visual order instead of placing the active tab first.

## Best solution

Preserve the selected tabs' complete sequential order when moving them across groups while keeping the previously active tab active and leaving existing single-tab, sticky-tab, copy, and drag-and-drop behavior intact.

- **Behavior:**

- **Trace:**

  > The command path in src/vs/workbench/browser/parts/editor/editorCommands.ts reads `IEditorGroup.selectedEditors`, which src/vs/workbench/common/editor/editorGroupModel.ts returns in sequential order. Before moving, `prepareMoveCopyEditors` in src/vs/workbench/browser/parts/editor/editor.ts extracts the active editor, places it first, and inverse-sorts every inactive editor to accommodate side-of-active insertion. `EditorGroupView.moveEditors` then processes that sequence one editor at a time, so an empty target starts with the active editor rather than the first source tab. The helper is also consumed by editor drag/drop and auxiliary-window moves, so those consumers must preserve their existing active-editor, sticky-editor, copy, and target-placement semantics. https://github.com/microsoft/vscode/issues/236269 is related to multi-selected editor commands but does not own this ordering defect.

## Evidence

- **source reproduction:** src/vs/workbench/browser/parts/editor/editorCommands.ts:234-244 obtains `activeGroup.selectedEditors` in sequential order and sends it through `prepareMoveCopyEditors` before `sourceGroup.moveEditors` at lines 347-350.
- **root cause:** src/vs/workbench/browser/parts/editor/editor.ts:346-380 deliberately constructs the move sequence with the active editor first and the inactive editors in inverse visual order. For tabs A, B, C with B active, the empty target group consequently receives B first, matching the maintainer comment that the active editor is placed in the first position.
- **current behavior:** src/vs/workbench/browser/parts/editor/editorGroupView.ts:1388-1417 processes the prepared editors sequentially, while doMoveOrCopyEditorAcrossGroups at lines 1471-1510 opens each editor in the target before closing it in the source. No post-report change in these paths restores the original complete tab order.
- **related issue:** https://github.com/microsoft/vscode/issues/236269 is older and discusses applying move actions to selected tabs plus explicit sorting commands, but it does not report this same active-tab-first symptom and therefore does not satisfy the stronger duplicate bar for this re-reviewed issue.
