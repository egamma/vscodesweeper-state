# Issue #168676 — Extension commands do not show any status indicator while waiting for activation

[https://github.com/microsoft/vscode/issues/168676](https://github.com/microsoft/vscode/issues/168676)

## Summary

A real gap remains on current main: generic activation progress begins only after extension discovery is ready, leaving commands without feedback while startup is still pending. This team-authored, reopened Backlog request should remain open while the command-specific versus host-startup indicator design is settled.

## Change summary

Show progress while an extension command is waiting for extension discovery, host startup, or activation before it can run.

## Best solution

Provide bounded, command-aware progress from the point a user-issued command begins waiting until it can be dispatched, while retaining appropriate generic feedback for non-command activation and avoiding indefinite indicators.

## Plan brief

- **Likely files:** `src/vs/workbench/services/commands/common/commandService.ts`, `src/vs/workbench/services/commands/test/common/commandService.test.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsActivationProgress.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`
- **Validation:** Add targeted command/progress tests covering a command invoked before installed extensions are registered: progress becomes observable while registration is pending, ends when command dispatch can proceed, and remains bounded when activation never resolves.
- **Behavior:**

  > When a user invokes an extension-contributed command before the extension system is ready, VS Code provides visible progress while the command is waiting rather than appearing frozen. The indicator ends when the command can run or when the chosen bounded-progress policy expires. Commands that execute synchronously and activation that is already complete must not flash unnecessary progress.
- **Trace:**

  > CommandService.executeCommand in src/vs/workbench/services/commands/common/commandService.ts initiates `onCommand:<id>` activation and can wait for extension readiness or registration. AbstractExtensionService.activateByEvent in src/vs/workbench/services/extensions/common/abstractExtensionService.ts defers `_activateByEvent` until `_installedExtensionsReady` opens; only `_activateByEvent` emits `onWillActivateByEvent`. ExtensionActivationProgress in src/vs/workbench/contrib/extensions/browser/extensionsActivationProgress.ts listens exclusively to that later event, which explains the silent startup interval. Existing command-service tests cover activation ordering and unresolved activation but not user-visible progress. Preserve immediate execution for already-ready commands and the bounded behavior for activation promises that never settle.
- **Open decisions:**
  - Should feedback describe the specific command waiting for activation, or present a global extension-host startup indicator shared by every blocked extension operation?
  - When should the indicator become visible, and how long should it remain before timing out, so short command executions do not flash while long or unresolved activation does not leave permanent progress?
