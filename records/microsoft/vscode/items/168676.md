# Issue #168676 — Extension commands do not show any status indicator while waiting for activation

[https://github.com/microsoft/vscode/issues/168676](https://github.com/microsoft/vscode/issues/168676)

## Summary

The gap remains on current main: command activation can wait for extension discovery or host readiness before the activation-progress event is emitted, leaving no immediate feedback. This team-authored Backlog request should remain open, with a maintainer choosing between command-scoped and extension-host-startup progress.

## Change summary

Show timely progress after a user invokes an extension command that is waiting for extension-host startup or activation.

## Best solution

Provide bounded, accessible progress from command invocation through extension readiness and activation, without showing progress for commands that execute immediately. A maintainer should first decide whether this belongs to the command service or to a broader extension-host startup indicator.

## Plan brief

- **Likely files:** `src/vs/workbench/services/commands/common/commandService.ts`, `src/vs/workbench/contrib/extensions/browser/extensionsActivationProgress.ts`, `src/vs/workbench/services/extensions/common/abstractExtensionService.ts`, `src/vs/workbench/services/commands/test/common/commandService.test.ts`
- **Validation:** With extension-host startup intentionally delayed, invoke an unregistered extension command and verify that bounded progress appears after the normal progress delay but before extension readiness, clears after activation or timeout, and is announced accessibly; verify built-in and already-activated commands show no progress.
- **Behavior:**

  > Invoking an extension-contributed command while its extension host is starting must provide timely, non-blocking feedback that the command is being processed. The indicator should appear during the currently silent pre-activation wait, clear when the command can run or its bounded wait expires, and avoid flashing for commands that execute promptly. The same state must be available to screen-reader users without duplicate announcements.
- **Trace:**

  > CommandService.executeCommand in src/vs/workbench/services/commands/common/commandService.ts requests `onCommand:<id>` activation. For normal activation before extension discovery completes, AbstractExtensionService.activateByEvent in src/vs/workbench/services/extensions/common/abstractExtensionService.ts waits for _installedExtensionsReady before calling _activateByEvent, which is where onWillActivateByEvent is emitted. ExtensionActivationProgress in src/vs/workbench/contrib/extensions/browser/extensionsActivationProgress.ts observes only that later event, so the earlier wait has no status indication. Existing immediate command behavior and prompt execution for registered or already-activated commands must not regress. The issue discussion leaves the design boundary open between command-scoped progress and a generic slow-extension-host-startup indicator: https://github.com/microsoft/vscode/issues/168676#issuecomment-1361572129.
- **Open decisions:**
  - Should progress begin in CommandService for user-invoked extension commands, or should extension-host startup expose a broader progress state?
  - Should the indicator describe the pending command specifically or retain the generic "Activating Extensions..." message?
  - What timeout and accessibility announcement behavior avoids indefinite or duplicate feedback?

## Evidence

- **current source gap:** In src/vs/workbench/services/extensions/common/abstractExtensionService.ts, normal activateByEvent calls made before installed extensions are ready wait on _installedExtensionsReady before reaching _activateByEvent; only _activateByEvent fires onWillActivateByEvent.
- **progress boundary:** src/vs/workbench/contrib/extensions/browser/extensionsActivationProgress.ts listens only to onWillActivateByEvent, displays "Activating Extensions...", and caps each activation at five seconds, so it cannot cover the earlier wait identified by the report.
- **command path:** src/vs/workbench/services/commands/common/commandService.ts executes extension commands through activateByEvent(`onCommand:${id}`), preserving the uncovered pre-activation interval on current main.
- **maintainer direction:** Maintainers discussed both a command-specific indicator and a renderer status item for slow extension-host startup at https://github.com/microsoft/vscode/issues/168676#issuecomment-1361572129 and https://github.com/microsoft/vscode/issues/168676#issuecomment-1362536914.
