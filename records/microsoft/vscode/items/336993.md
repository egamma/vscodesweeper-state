# Issue #336993 — Remote agents connect/reconnect loop

[https://github.com/microsoft/vscode/issues/336993](https://github.com/microsoft/vscode/issues/336993)

## Summary

Team-authored bug report with a solid follow-up root-cause trace: two Agent Host tunnel processes can both claim the same persisted tunnel identity and repeatedly displace each other's endpoints, with the reconnect backoff resetting on each successful (but immediately stolen) connection, producing the observed connect/reconnect loop. No fix has landed on main yet, so this stays open.

## Change summary

Starting a new remote-agent tunnel while an old tunnel-host process is still running causes an endless connect/reconnect loop instead of detecting the conflict.

## Best solution

In cli/src/tunnels/dev_tunnels.rs, have start_new_launcher_tunnel detect that another live process already owns the persisted tunnel (rather than unconditionally pruning its endpoints) and surface a clear message/state instead of silently displacing it and looping forever.

## Plan brief

- **Likely files:** `cli/src/tunnels/dev_tunnels.rs`
- **Validation:** A CLI tunnel test (or manual repro with two concurrent tunnel-host processes sharing code_tunnel.json) confirming the second process surfaces a clear conflict message/state instead of silently pruning the first's endpoints and looping.
- **Trace:**

  > start_new_launcher_tunnel (cli/src/tunnels/dev_tunnels.rs, ~L538-610) loads the persisted tunnel from shared code_tunnel.json state and unconditionally deletes existing tunnel endpoints before starting its own relay, without checking whether the prior owning process is still alive. spawn_tunnel's reconnect loop (~L1128+) resets its Backoff after each successful-but-immediately-stolen connection, so two competing processes fight indefinitely, producing the observed 'Tunnel exited unexpectedly but gracefully, reconnecting' loop. Do not touch the broader tunnel relay/connection protocol — the fix should be scoped to ownership detection before endpoint deletion in start_new_launcher_tunnel/create_tunnel. Where the uncertainty starts: what mechanism should detect 'another live host process owns this tunnel' (process liveness check vs. tunnel-service state) and what the resulting user-facing behavior should be (block with a message, prompt to force-take-over, or something else).
- **Open decisions:**
  - Should the newer process detect the older one is still alive and refuse to start (showing a message), or should it still take over but only after confirming the old process has actually exited?
  - What signals a 'conflicting live owner' — a local process/PID check, a tunnel-service-side heartbeat, or something else — given both CLI invocations only share a local code_tunnel.json file?
  - If detected, should the message be surfaced only in the log, or also as a workbench/UI notification to the user starting the agent?
