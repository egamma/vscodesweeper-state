# Issue #336993 — Remote agents connect/reconnect loop

[https://github.com/microsoft/vscode/issues/336993](https://github.com/microsoft/vscode/issues/336993)

## Summary

Team-authored diagnostic report (dbaeumer) that a stale/duplicate tunnel process on the machine causes an endless silent connect/reconnect loop instead of a clear diagnostic message; author confirmed the root cause and asked for detection + messaging, so this stays open regardless of other evidence.

## Change summary

When testing remote agent tunnels, a leftover tunnel process from a prior run causes the new tunnel to loop connecting/reconnecting forever with no indication of the real cause.

## Best solution

Have the tunnel relay connection loop in cli/src/tunnels/dev_tunnels.rs detect the 'another tunnel process is already active' failure mode (the CLI already has singleton detection infrastructure in cli/src/tunnels/singleton_client.rs/singleton_server.rs) and surface an explicit message instead of retrying indefinitely.

## Plan brief

- **Likely files:** `cli/src/tunnels/dev_tunnels.rs`, `cli/src/tunnels/singleton_client.rs`, `cli/src/tunnels/singleton_server.rs`
- **Validation:** A test or manual repro where a second tunnel process is started against the same machine/tunnel id should surface a clear 'another tunnel is already running' message instead of looping through reconnect attempts.
- **Behavior:**

  > When a new tunnel process starts while an old tunnel process for the same machine/agent is still alive, the user should see a clear message identifying the conflict (e.g. 'another tunnel process is already running') rather than an unbounded silent connect/reconnect loop in the log. Acceptance: starting a tunnel with a stale conflicting process present produces a single diagnostic message and either exits or gives the user an actionable next step, instead of repeated 'Tunnel exited unexpectedly, reconnecting' log spam.
- **Trace:**

  > The reconnect loop lives in the tunnel relay connection routine in cli/src/tunnels/dev_tunnels.rs, which on any connection drop just backs off and retries indefinitely (fail!/warning! then backoff.delay().await) with no classification of *why* the tunnel dropped. Separately, cli/src/tunnels/singleton_client.rs and singleton_server.rs already implement detection of an existing tunnel process for a different CLI code path ('Connected to an existing tunnel process running on this machine.'). The gap is that the relay reconnect loop doesn't consult or share that detection when its own connection is being repeatedly rejected/dropped by the server side due to a conflicting old process. Boundary: do not change the singleton detection semantics for the already-working CLI path; the fix should be scoped to giving the relay loop a way to recognize this specific failure and message it, without altering normal reconnect/backoff behavior for transient network drops. Reported in https://github.com/microsoft/vscode/issues/336993, filed while testing https://github.com/microsoft/vscode/issues/336852.
- **Open decisions:**
  - Should conflict detection reuse/extend the existing singleton_client/singleton_server mechanism, or does the relay tunnel need a distinct signal from the server to identify 'another process already connected'?
  - Should the user-facing message be a CLI log line, a UI notification in the editor, or both?
  - Should the tunnel process exit/prompt the user to kill the stale process, or just log the message and continue retrying?

## Evidence

- **source location:** The 'Tunnel exited unexpectedly, reconnecting' / 'gracefully, reconnecting' log lines originate from cli/src/tunnels/dev_tunnels.rs (around line 1187-1189), which retries in a loop with backoff and no detection of a conflicting/stale tunnel process.
- **existing infra:** cli/src/tunnels/singleton_client.rs already implements detection of 'Connected to an existing tunnel process running on this machine.' for a different code path, suggesting a mechanism to build on but not currently wired into the relay reconnect loop.
- **author diagnosis:** Comment from dbaeumer: 'OK. AI tracked it down. There was an old tunnel process running. Would be good if we detect this and show a message instead of a connect and reconnect loop.'
