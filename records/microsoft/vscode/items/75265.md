# Issue #75265 — Global regex search with "Not matching character" doesn't match newline

[https://github.com/microsoft/vscode/issues/75265](https://github.com/microsoft/vscode/issues/75265)

## Summary

Keep open: current search still requires an explicit newline signal to enable cross-line matching, and the requested discoverable opt-in remains missing. Maintainers accepted this improvement while preserving performance-sensitive defaults; a later duplicate explicitly identifies this issue as the tracking item.

## Change summary

Provide a discoverable way to enable cross-line regex search without inserting a newline expression into an otherwise valid pattern.

## Best solution

Offer an explicit, understandable cross-line search opt-in while retaining the existing default behavior and performance safeguards. Settle the user-facing control and its persistence before implementation rather than automatically enabling multiline search for every negated character class or whitespace escape.

Cover query-mode propagation in the queryBuilder tests and verify that existing default searches and explicit-newline patterns retain their behavior.
- **Behavior:**

  > Users should be able to deliberately enable regex matches spanning lines without rewriting their regex to contain a newline token. With that opt-in, the original Promise.all expression in this issue must find the supplied multiline sample. Preserve the existing default search behavior and explicit-newline compatibility. Cross-line matching must not be confused with making dot match newline or changing anchor semantics.
- **Trace:**

  > QueryBuilder.isMultiline in src/vs/workbench/services/search/common/queryBuilder.ts recognizes an explicit pattern flag or delegates to isMultilineRegexSource in src/vs/editor/common/model/textModelSearch.ts. That helper does not recognize the reported negated character class, while a trailing \n{0} triggers it. The ripgrep argument builder in src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts already gates --multiline on the resulting flag; searchView.ts constructs the user query. Existing queryBuilder tests cover literal-newline normalization. The maintainer direction is explicit opt-in, not automatic multiline activation for all potentially newline-matching expressions: https://github.com/microsoft/vscode/issues/75265#issuecomment-511080264. The uncertainty is the discoverable user interaction and its lifetime, not whether the backend supports cross-line matching. Keep editor Find/Replace file-size behavior and unrelated regex-engine semantics outside this request.
- **Open decisions:**
  - Which user-facing interaction should expose the explicit cross-line search opt-in without overcrowding the search controls?
  - Should the explicit opt-in apply only to the current query, or persist across subsequent searches and window reloads?

## Evidence

- **Current capability and remaining gap:** src/vs/editor/common/model/textModelSearch.ts:isMultilineRegexSource recognizes literal line feeds and escaped n, r, or W, but not negated character classes or escaped s. The reported Promise.all pattern therefore does not enable multiline search, whereas appending \n{0} does. Searches of search contribution registrations found no dedicated multiline or dot-all setting/control; the workaround is not the requested discoverable opt-in.
- **Search backend boundary:** src/vs/workbench/services/search/common/queryBuilder.ts:QueryBuilder.isMultiline accepts an explicit contentPattern.isMultiline flag or the newline heuristic. src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts adds --multiline only when query.isMultiline is true. This is VS Code's search-mode selection, not evidence of an upstream ripgrep defect.
- **Maintainer-accepted improvement:** https://github.com/microsoft/vscode/issues/75265#issuecomment-502385231 calls the additional control a fair request. https://github.com/microsoft/vscode/issues/75265#issuecomment-511080264 favors explicit opt-in because of performance and unexpected-result concerns, and identifies careful UX design as the remaining obstacle.
