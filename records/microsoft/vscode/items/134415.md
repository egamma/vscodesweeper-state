# Issue #134415 — Add `!`-prefix parsing to glob util

[https://github.com/microsoft/vscode/issues/134415](https://github.com/microsoft/vscode/issues/134415)

## Summary

A real gap remains on current main: the shared glob utility treats leading `!` as a literal and combines expression entries with OR semantics. Keep this accepted On Deck request open while maintainers settle the observable precedence and ordering contract.

## Change summary

Teach the shared glob-expression utility to recognize leading `!` patterns so exclusions can contain explicit exceptions.

## Best solution

Define consistent negated-expression semantics, including precedence, ordering, and literal leading-`!` escaping, then implement them in the shared glob utility with coverage for Explorer and search consumers.

## Plan brief

- **Likely files:** `src/vs/base/common/glob.ts`, `src/vs/base/test/common/glob.test.ts`, `src/vs/workbench/contrib/files/browser/views/explorerViewer.ts`, `src/vs/workbench/services/search/common/search.ts`
- **Validation:** Add glob unit cases for positive-only, negated-exception, multiple-negation, overlapping-pattern, and literal-leading-`!` expressions, then run `scripts/test.sh --grep "Glob"`; the plan should also end with Explorer/search coverage showing the chosen semantics for `node_modules/*` plus `!node_modules/@types`.
- **Behavior:**

  > Glob expressions should recognize a leading `!` as an exception rather than a literal, allowing configurations such as excluding `node_modules/*` while retaining `node_modules/@types`. Explorer and search must apply the selected semantics consistently, and existing positive patterns, disabled entries, sibling clauses, and character-range negation must remain compatible. Acceptance must cover overlapping positive and negative patterns, multiple negations, and a documented way to match a filename that literally begins with `!`.
- **Trace:**

  > Current parsing starts in `parsePattern` and `parsedExpression` in src/vs/base/common/glob.ts; leading `!` has no special handling, while expression entries are aggregated and return on the first matching pattern. The existing expression tests are in src/vs/base/test/common/glob.test.ts. `FilesFilter.updateConfiguration` in src/vs/workbench/contrib/files/browser/views/explorerViewer.ts parses `files.exclude` directly, and search combines exclusion settings in `getExcludes` in src/vs/workbench/services/search/common/search.ts. The boundary is the shared glob-expression contract: preserve ordinary string glob behavior, sibling clauses, optimizations, and `[!...]` character ranges unless the selected public semantics require otherwise. https://github.com/microsoft/vscode/issues/869 supplies the primary user scenarios, while https://github.com/microsoft/vscode/pull/152225 demonstrates why an Explorer-only implementation is insufficient.
- **Open decisions:**
  - Should overlapping positive and leading-`!` entries use order-independent two-pass exception semantics, or ordered `.gitignore`-style last-match semantics?
  - Should leading-`!` negation apply to every `glob.IExpression` consumer, or only exclusion expressions such as `files.exclude` and `search.exclude`?
  - What public escaping syntax should preserve a literal pattern whose filename begins with `!`?

## Evidence

- **current source gap:** src/vs/base/common/glob.ts documents and implements `!` only inside `[!...]` character ranges. `parsePattern` otherwise passes a leading `!` through as a literal, so prefix negation is not implemented on current main.
- **expression semantics:** The `parsedExpression` function in src/vs/base/common/glob.ts returns immediately when any enabled parsed pattern matches, implementing OR semantics that cannot directly express positive exclusions followed by negated exceptions.
- **shared impact:** src/vs/workbench/contrib/files/browser/views/explorerViewer.ts parses `files.exclude` through `glob.parse`, while src/vs/workbench/services/search/common/search.ts merges `files.exclude` and `search.exclude` into the same `glob.IExpression` model. Prefix-negation semantics therefore affect multiple consumers.
- **unresolved contract:** Maintainer discussion in this issue distinguishes two-pass include-dominated behavior from ordered `.gitignore` behavior and identifies ambiguity when several positive and negated patterns overlap; no final contract was recorded.
- **related request:** https://github.com/microsoft/vscode/issues/869 is an older open user-facing request for exclude exceptions, but this re-reviewed item defines broader shared-utility semantics rather than reporting the same observable symptom, so it does not meet the stronger duplicate bar.
- **closed implementation attempt:** https://github.com/microsoft/vscode/pull/152225 was closed without merging after maintainers said the behavior belonged in the glob parser and redirected implementation to this issue.
