# Issue #335780 — Fireworks agent requests fail on unsupported CoT metadata

[https://github.com/microsoft/vscode/issues/335780](https://github.com/microsoft/vscode/issues/335780)

## Summary

This is a real, confirmed bug rather than a feature request: the BYOK OpenAI-compatible chat-completions path unconditionally injects CAPI-only `cot_id`/`cot_summary` fields into every assistant message, with no guard for third-party providers (like Fireworks) that strictly reject unknown JSON fields.

## Change summary

Requests to strict-schema OpenAI-compatible providers (e.g. Fireworks) fail with a 400 because the client always attaches internal `cot_id`/`cot_summary` metadata to outgoing messages.

## Best solution

In `OpenAIEndpoint.getCompletionsCallback` (extensions/copilot/src/extension/byok/node/openAIEndpoint.ts), gate emission of the CAPI-specific `cot_id`/`cot_summary` keys the same way `reasoning_content`/`reasoning` are already gated (e.g. by a capability flag or known-provider allowlist), so they are omitted for providers/models that don't tolerate unrecognized fields.

## Evidence

- **unconditional field injection:** extensions/copilot/src/extension/byok/node/openAIEndpoint.ts, `getCompletionsCallback`: whenever `data?.id` is present it always sets `out.cot_id = data.id` and `out.cot_summary = text`, regardless of the target endpoint URL/provider; only `reasoning_content`/`reasoning` are gated behind `supportsThinking`.
- **documented as intentional:** extensions/copilot/src/extension/byok/node/test/openAIEndpoint.spec.ts (e.g. the 'does not emit reasoning_content...' test around line 243) explicitly asserts cot_id/cot_summary remain present even when the model doesn't support thinking, with the comment 'CAPI-compatible keys are still emitted so the same payload also works with CAPI' — there is no branch that omits them for strict third-party validators.
- **prior related fix:** A comment references https://github.com/microsoft/vscode/issues/312746, where reasoning_content/reasoning were added for DeepSeek/Kimi/Moonshot; that fix preserved the always-on cot_id/cot_summary emission, which is exactly what this new report shows Fireworks rejecting (`messages[2].cot_id`, `messages[2].cot_summary`).
