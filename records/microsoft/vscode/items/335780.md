# Issue #335780 — Fireworks agent requests fail on unsupported CoT metadata

[https://github.com/microsoft/vscode/issues/335780](https://github.com/microsoft/vscode/issues/335780)

## Summary

Traced to a real, intentional-but-incomplete design in the BYOK OpenAI-compatible endpoint: it always stamps Azure/CAPI-style `cot_id`/`cot_summary` onto outgoing messages, which strict-schema providers like Fireworks reject as unknown fields — but the fix isn't a trivial gate since a prior regression test (issue #312746) specifically requires these fields to always be present for CAPI compatibility.

## Change summary

A BYOK 'OpenAI Compatible' custom endpoint pointed at Fireworks fails follow-up requests because the client unconditionally forwards internal `cot_id`/`cot_summary` chain-of-thought metadata that Fireworks' strict schema validation rejects with a 400, which the client then surfaces as a retried 502.

## Best solution

In `extensions/copilot/src/extension/byok/node/openAIEndpoint.ts` (`OpenAIEndpoint.getCompletionsCallback`), stop unconditionally emitting `cot_id`/`cot_summary` for every BYOK OpenAI-compatible target — gate it to endpoints that are actually CAPI/Azure-compatible (e.g. only in `AzureOpenAIEndpoint`, or behind a per-provider/model capability flag), while still emitting the provider-specific `reasoning`/`reasoning_content` fields for models where `supports.thinking` is set; needs care to not regress the existing `openAIEndpoint.spec.ts` coverage for issue #312746 (DeepSeek/Kimi/Moonshot/OpenRouter).
