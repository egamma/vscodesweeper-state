# Issue #335780 — Fireworks agent requests fail on unsupported CoT metadata

[https://github.com/microsoft/vscode/issues/335780](https://github.com/microsoft/vscode/issues/335780)

## Summary

Still present on main: the BYOK OpenAI-compatible endpoint unconditionally stamps the CAPI-proprietary `cot_id`/`cot_summary` keys onto assistant messages, which strict OpenAI-compatible providers such as Fireworks reject with a 400 — keep open; it needs a maintainer decision on how to scope those keys (and the issue is better classified as a bug than a feature request).

## Change summary

Multi-turn BYOK requests to Fireworks fail with `Extra inputs are not permitted: messages[N].cot_id / cot_summary` because VS Code forwards internal chain-of-thought metadata in the chat message.

## Best solution

Stop emitting the CAPI-only `cot_id`/`cot_summary` keys on non-CAPI OpenAI-compatible BYOK endpoints (or gate them behind a capability/allowlist), so strict providers like Fireworks accept the follow-up turn while CAPI and the DeepSeek/OpenRouter reasoning echoes keep working — the change lives in `OpenAIEndpoint.getCompletionsCallback` in extensions/copilot/src/extension/byok/node/openAIEndpoint.ts.

- **Behavior:**

  > A multi-turn BYOK conversation against a strict OpenAI-compatible provider (Fireworks, model glm-5p3-flash) must not fail with `400 invalid_request_error — Extra inputs are not permitted: messages[N].cot_id, messages[N].cot_summary` after the assistant has produced reasoning. Follow-up turns succeed on the first attempt (no 5 retries, no ~30s delay) without the user disabling reasoning. Reasoning continuity for providers that do need the echo (DeepSeek/Kimi/Moonshot/OpenRouter via `reasoning_content` / `reasoning`) and the CAPI path must be unchanged. Acceptance: the existing openAIEndpoint specs still pass, plus a new spec covering the strict-provider payload.
- **Trace:**

  > `OpenAIEndpoint.getCompletionsCallback` in extensions/copilot/src/extension/byok/node/openAIEndpoint.ts writes `out.cot_id = data.id; out.cot_summary = text;` for any thinking message with an id, with no capability or endpoint gating — only `reasoning_content`/`reasoning` are gated on `modelMetadata.capabilities.supports.thinking`. Those two keys are CAPI-internal (`ThinkingDataInMessage` in extensions/copilot/src/platform/thinking/common/thinking.ts; also scrubbed in platform/networking/common/messageTelemetry.ts) and are exactly the fields in the reporter's 400. Confirmed by reading the source on main; `git log` since 2026-09-01 shows no change to that file. The boundary: do not touch the `reasoning_content` / `reasoning` emission or the CAPI endpoint behavior — issue https://github.com/microsoft/vscode/issues/312746 depends on them — and do not change retry/error-mapping behavior as part of this. Where the uncertainty starts: extensions/copilot/src/extension/byok/node/test/openAIEndpoint.spec.ts explicitly asserts the CAPI keys for non-CAPI BYOK URLs, so the correct gating signal (endpoint family, a model capability flag, or a known-strict-provider rule) is an open call. Related: https://github.com/microsoft/vscode/issues/338819.
- **Open decisions:**
  - Should `cot_id`/`cot_summary` be omitted for all non-CAPI BYOK OpenAI-compatible endpoints, or only when a model/provider is known to validate strictly? This changes the asserted contract in openAIEndpoint.spec.ts.
  - If the keys are dropped, is any reasoning-continuity guarantee lost for BYOK gateways that proxy to CAPI (e.g. LiteLLM), and is that acceptable?
  - Should the client additionally surface the provider's underlying 400 instead of mapping it to a 502 and retrying five times, or is that a separate issue?

## Evidence

- **source trace of the reported fields:** extensions/copilot/src/extension/byok/node/openAIEndpoint.ts (getCompletionsCallback, ~lines 157–170) sets `out.cot_id = data.id; out.cot_summary = text;` for every thinking message whenever the provider returned a reasoning id — unlike `reasoning_content`/`reasoning`, this is not gated on any model capability or on the endpoint being CAPI. That is exactly the `messages[N].cot_id` / `messages[N].cot_summary` pair Fireworks rejects.
- **emission is deliberate, so the fix is a scope decision:** extensions/copilot/src/extension/byok/node/test/openAIEndpoint.spec.ts asserts the keys are present even for non-CAPI BYOK URLs (`https://openrouter.ai/...`, `https://api.example.com/...`) with the comment 'CAPI-compatible keys are still emitted so the same payload also works with CAPI'. Dropping or gating them changes an asserted contract, so a maintainer should pick the scoping rule.
- **no fix on main:** `git log` since 2026-09-01 on extensions/copilot/src/extension/byok/node/openAIEndpoint.ts shows no change to this path (checkout at 2026-10-12); the unconditional assignment is still there.
