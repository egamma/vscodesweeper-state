# Issue #251934 — Splitting primary/secondary sidebars by dragging the tool's icon is impossible in certain situations

[https://github.com/microsoft/vscode/issues/251934](https://github.com/microsoft/vscode/issues/251934)

## Summary

The state-dependent drag failure remains credible on current main: a single-view container hides its pane header, while adding another view restores visible pane headers and therefore a reliable split-drop surface. The built-in Extensions-to-Outline reproduction makes this broader than the older webview-only report.

## Change summary

Dragging a view-container icon onto a sidebar containing one view sometimes cannot split the container, although the same target becomes splittable after another view is temporarily added.

## Best solution

Make split-drop behavior consistent for single-view and multi-view containers in the shared workbench view drag-and-drop path, including built-in tree views and extension-provided webview views.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/views/viewPaneContainer.ts`, `src/vs/base/browser/ui/splitview/paneview.ts`, `src/vs/workbench/contrib/webviewView/browser/webviewViewPane.ts`
- **Validation:** In a development workbench, place Extensions and Outline in separate sidebar containers, drag one container icon over the other's sole view, and verify that split feedback appears and the drop creates two panes; repeat with two extension-provided webview containers and with an already multi-view target.
- **Behavior:**

  > A movable view-container icon can be dropped onto a sidebar container to split it regardless of whether the target currently contains one view or several. The drop indicator and resulting pane placement must be consistent for built-in tree views and extension-provided webview views. Reordering containers on the activity bar and moving a container between sidebar locations must remain unchanged.
- **Trace:**

  > ViewPaneContainer in src/vs/workbench/browser/parts/views/viewPaneContainer.ts registers composite drops on each Pane.dropTargetElement and moves all movable descriptors into the target container. Its updateViewHeaders() method hides the only pane header when the view is merged with its container; adding another pane makes headers visible, matching the issue's state-dependent behavior. Pane.dropTargetElement is the complete pane element in src/vs/base/browser/ui/splitview/paneview.ts, while webview views separately redispatch drag events in src/vs/workbench/contrib/webviewView/browser/webviewViewPane.ts. The uncertainty starts at which child surface consumes or redirects the activity-bar drag events in the single-pane state, so confirm that in a running workbench before selecting the implementation boundary. Do not change `canMoveView`, `rejectAddedViews`, activity-bar ordering, or same-container pane reordering semantics. The older https://github.com/microsoft/vscode/issues/144122 covers only the webview subset and must not be treated as canonical for the built-in tree-view case.

## Evidence

- **state-dependent reproduction:** The issue provides a video and a built-in Extensions-to-Outline reproduction with extensions disabled; the reporter subsequently confirmed the behavior remained reproducible.
- **current source path:** src/vs/workbench/browser/parts/views/viewPaneContainer.ts registers split-drop handling on each pane's `dropTargetElement`, while `updateViewHeaders()` hides the pane header whenever `isViewMergedWithContainer()` is true for a single view. Adding a second view makes the headers visible, matching the reported transition from unsplittable to splittable.
- **movability is not the blocker:** src/vs/workbench/api/browser/viewsExtensionPoint.ts sets `canMoveView` for ordinary extension-contributed views, and the composite-drop path in viewPaneContainer.ts accepts a container when all its views are movable.
- **related issue is narrower:** https://github.com/microsoft/vscode/issues/144122 remains open for the same symptom when the sole view is a webview, but it does not absorb this report's built-in tree-view reproduction.
- **no direct fix:** Repository history contains no commit referencing https://github.com/microsoft/vscode/issues/251934, and post-report changes to viewPaneContainer.ts do not alter the relevant single-view drop-target logic.
