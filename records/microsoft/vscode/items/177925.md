# Issue #177925 — Case-sensitive files/folders on Windows are not shown correctly in vscode

[https://github.com/microsoft/vscode/issues/177925](https://github.com/microsoft/vscode/issues/177925)

## Summary

The Windows-specific bug remains present on current main: the local disk provider reports case sensitivity only on Linux, causing Explorer's case-folded child map to collapse siblings such as `A` and `a`. A maintainer explicitly reopened this report because Windows per-directory case sensitivity requires different handling from the related macOS issue.

## Change summary

Explorer omits files or folders whose names differ only by case inside Windows directories enabled for case-sensitive behavior.

## Best solution

Represent Windows per-directory case sensitivity on the local filesystem path and use it consistently for Explorer child identity, lookup, rename, and file operations, while preserving case-insensitive behavior in ordinary Windows directories.

## Plan brief

- **Likely files:** `src/vs/platform/files/common/files.ts`, `src/vs/platform/files/common/fileService.ts`, `src/vs/platform/files/node/diskFileSystemProvider.ts`, `src/vs/workbench/contrib/files/common/explorerModel.ts`, `src/vs/workbench/contrib/files/test/browser/explorerModel.test.ts`, `src/vs/platform/files/test/node/diskFileService.integrationTest.ts`
- **Validation:** On Windows, add an integration or platform-gated test that enables case sensitivity for a temporary directory, creates sibling entries `A` and `a`, resolves the directory through the file service, and verifies both remain separately addressable in Explorer; retain tests proving ordinary Windows directories still use case-insensitive lookup.
- **Behavior:**

  > When a Windows directory has per-directory case sensitivity enabled, Explorer must display and separately address every sibling whose name differs only by case, including `A` and `a`. Case-only renames in that directory must update without requiring a window reload. Ordinary Windows directories must retain their existing case-insensitive behavior. Acceptance requires a Windows test covering both directory modes and an Explorer model test proving colliding case variants are not discarded.
- **Trace:**

  > DiskFileSystemProvider in src/vs/platform/files/node/diskFileSystemProvider.ts advertises PathCaseSensitive only on Linux. FileService in src/vs/platform/files/common/fileService.ts consequently selects case-insensitive URI identity for every local Windows path, and ExplorerItem.getPlatformAwareName in src/vs/workbench/contrib/files/common/explorerModel.ts lowercases child names; addChild then overwrites the first of two case-variant siblings in its Map. The Windows filesystem flag is directory-specific, but FileSystemProviderCapabilities.PathCaseSensitive in src/vs/platform/files/common/files.ts is provider-wide, so the uncertainty starts at how path-local sensitivity should flow through file-service identity consumers. Preserve current semantics for normal Windows directories and do not globally mark the Windows disk provider case-sensitive. The related macOS report https://github.com/microsoft/vscode/issues/94307 must remain separate, consistent with the maintainer's reopening comment at https://github.com/microsoft/vscode/issues/177925#issuecomment-1481535690.

## Evidence

- **source reproduction:** In src/vs/platform/files/node/diskFileSystemProvider.ts, DiskFileSystemProvider adds FileSystemProviderCapabilities.PathCaseSensitive only when `isLinux`; Windows directories carrying the per-directory `setCaseSensitiveInfo` flag therefore remain advertised as case-insensitive.
- **observable failure path:** In src/vs/workbench/contrib/files/common/explorerModel.ts, ExplorerItem.addChild stores children under getPlatformAwareName(child.name), which lowercases the name whenever the provider lacks PathCaseSensitive. Adding `A` followed by `a` therefore writes the same Map key and leaves only one visible child.
- **abstraction constraint:** FileSystemProviderCapabilities.PathCaseSensitive in src/vs/platform/files/common/files.ts and FileService.isPathCaseSensitive in src/vs/platform/files/common/fileService.ts are provider-wide, while the Windows flag is directory-specific; fixing the Explorer alone risks inconsistent identity semantics in other file operations.
- **maintainer direction:** The maintainer reopened the issue at https://github.com/microsoft/vscode/issues/177925#issuecomment-1481535690, explicitly stating that the Windows fsutil flag needs special handling rather than consolidation into the macOS report.
- **canonical search:** https://github.com/microsoft/vscode/issues/94307 is older and related, but it covers case-sensitive macOS volumes; the maintainer deliberately separated this Windows per-directory behavior, so it is not a valid duplicate canonical for this re-reviewed issue.
- **no landed or pending fix:** Repository history and GitHub searches found no commit or open pull request referencing https://github.com/microsoft/vscode/issues/177925, and the case-folding path remains unchanged on current main.
