# Issue #157096 — problemMatcher with multiple patterns doesn't work

[https://github.com/microsoft/vscode/issues/157096](https://github.com/microsoft/vscode/issues/157096)

## Summary

Keep open: current source still stops after the first successful problem matcher, suppressing the second file location in the supplied linker example. The report also combines this confirmed defect with requests for named alternative patterns and fileless diagnostics, which need separate contract decisions.

## Change summary

Allow linker output containing multiple source locations to produce all requested diagnostics without one configured problem matcher suppressing another.

## Best solution

Make the task problem-collection pipeline retain both diagnostics from the reporter's linker2/linker3 example while preserving existing multiline matching semantics. Separately settle how named alternative matchers and genuinely fileless diagnostics should be represented rather than treating a multiline pattern array as alternatives.

These checks were not executed during this read-only review.
- **Behavior:**

  > A linker output line identifying a multiple definition in one source file and its original definition in another must not lose either configured diagnostic because a different matcher already recognized the line. The supplied linker2/linker3 configuration should produce entries for both files and their respective line numbers. Existing consecutive-line pattern arrays and multiline loops must retain their documented meaning. The broader request also seeks independent patterns under one contributed name and diagnostics without a source file; their public representation needs a maintainer decision before implementation.
- **Trace:**

  > In src/vs/workbench/contrib/tasks/common/problemCollectors.ts, AbstractProblemCollector.tryMatchers returns the first successful IProblemMatch, and tryFindMarker then clears the buffered line. Both StartStopProblemCollector and WatchingProblemCollector consume this singular result, conclusively explaining why the reporter's second matcher never produces its marker. In src/vs/workbench/contrib/tasks/common/problemMatcher.ts, pattern arrays select MultiLineMatcher, whose handle method requires successive lines; they are not alternative regexes. AbstractLineMatcher.getMarkerMatch also requires a file, so kind: file is not a solution for fileless build errors. Preserve those existing multiline and resource contracts unless the maintainer explicitly approves extending them. https://github.com/microsoft/vscode/issues/149673 concerns background-task status and is related, not a verified duplicate. The uncertainty starts at the public representation and scope of the additional named-alternative and fileless capabilities, not at the demonstrated same-line suppression.
- **Open decisions:**
  - Should this issue's implementation include independently matching patterns grouped under one contributed name, or should that capability be tracked separately from the same-line diagnostic defect?
  - Should genuinely fileless build diagnostics be supported here, and if so, how should they appear and behave in the resource-oriented Problems view?
