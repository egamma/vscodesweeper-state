# Issue #200586 — vscode lock-up for ~30s if database is locked with `OSCrypt tried libsecret but couldnt initialize`

[https://github.com/microsoft/vscode/issues/200586](https://github.com/microsoft/vscode/issues/200586)

## Summary

Keep open as an upstream keychain-blocking issue: the discussion confirms lengthy libsecret initialization stalls, and current VS Code still invokes Electron's synchronous safeStorage APIs on the main process. Neither a landed fix nor an older canonical covering the same locked-database freeze was established.

## Change summary

Prevent VS Code from becoming unresponsive while a locked Linux Secret Service database awaits unlocking or times out.

## Best solution

Make keychain initialization and encryption non-blocking through Electron's supported asynchronous path, adopted by VS Code's EncryptionMainService without weakening secret-storage protection. Keep the startup freeze distinct from KeePassXC's missing-unlock-prompt defect and generic keyring-detection failures.

## Evidence

- **reported trigger and independent confirmation:** https://github.com/microsoft/vscode/issues/200586 describes starting VS Code with password-store=gnome-libsecret and a locked KeePassXC Secret Service database, causing approximately 30 seconds of unresponsiveness. The February 2024 Fedora/GNOME confirmation records about 25 seconds between selecting GNOME_LIBSECRET and reporting initialization failure; the author additionally reports blocking while the unlock prompt remains active.
- **current main-process call path:** src/vs/platform/secrets/common/secrets.ts:225-227 initializes secret storage by awaiting isEncryptionAvailable(). In src/vs/platform/encryption/electron-main/encryptionMainService.ts:65-69, that method calls safeStorage.isEncryptionAvailable() synchronously before wrapping its result in Promise.resolve; encrypt() and decrypt() likewise invoke synchronous native APIs. These Promise-shaped interfaces do not move native keychain waits off the main thread.
- **upstream blocking behavior and unadopted capability:** https://github.com/electron/electron/blob/v39.0.0/docs/api/safe-storage.md explicitly documents that keychain calls can block the current thread for user input on Linux. https://github.com/electron/electron/blob/main/docs/api/safe-storage.md now describes non-blocking asynchronous APIs, but the inspected VS Code encryption service does not call isAsyncEncryptionAvailable, encryptStringAsync, or decryptStringAsync. Upstream API availability alone therefore does not establish that this report is fixed.
- **reporter-linked upstream issue has different scope:** https://github.com/keepassxreboot/keepassxc/issues/10096 remains open and concerns an unlock prompt not reopening after dismissal through the window-decoration X. The reporter explicitly separates that prompting defect from this issue's lengthy VS Code freeze; fixing the former would not establish that waiting on an active prompt becomes non-blocking.
- **canonical search:** Searches for libsecret lock and keyring freeze found the older open https://github.com/microsoft/vscode/issues/187338. Its original report concerns failure to identify an installed keyring and encryption-unavailable errors, not the same locked-database startup freeze; it was not established as a canonical under the stronger re-review symptom requirement. The closed https://github.com/microsoft/vscode/issues/197493 has a maintainer diagnosis pointing to an unrelated workbench exception.

Its upstream guidance distinguishes identified dependency problems from issues with a clear upstream tracking link; the supplied review policy requires keeping upstream issues open. The checkout is shallow, so local history cannot establish fix provenance.
