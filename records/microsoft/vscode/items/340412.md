# Issue #340412 — NativeEditContext: Enter from a composing Android keyboard corrupts the new line

[https://github.com/microsoft/vscode/issues/340412](https://github.com/microsoft/vscode/issues/340412)

## Summary

Keep open: current source still rebases the EditContext buffer after Enter and suppresses updates when successive empty lines have identical text and offsets, matching the reported failures. The existing editor-edit-context routing is appropriate; the older suggestion-corruption report does not own this distinct Enter-triggered behavior.

## Change summary

Prevent composing Android keyboard input after Enter from overwriting existing text or consuming Backspace without removing a line break.

## Best solution

Keep the keyboard's surrounding-text coordinates consistent with editor edits across Enter and subsequent composition, including indentation and line-break deletion. Validate the complete event sequence while preserving desktop IME, textarea input, cursor movement, and undo behavior.

Ordinary caret navigation, undo, desktop IMEs and textarea input must retain their existing behavior.
- **Trace:**

  > NativeEditContext in src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts handles paragraph beforeinput through _onType, then synchronizes on cursor changes through _updateEditContext and _getNewEditContextState. The latter always constructs surrounding text from the current selection's lines; after Enter it loses the old coordinate origin, while successive empty lines produce no updateText or updateSelection call at all. _emitTypeEvent interprets subsequent keyboard ranges using this rebased state. Source establishes these mechanisms, but the complete Android event ordering and indentation interaction still require a controlled replay or device reproduction before selecting a safe design. ## Evidence

- **Complete reproduction and contrasting environment:** https://github.com/microsoft/vscode/issues/340412 supplies two concrete sequences on Android 13, Chrome 154 and Gboard 12.4.05, with extensions absent and editor.editContext enabled. Enter inside beta changes the expected second line into 'ta charlitadelta echo foxtrot', overwriting existing characters; three Enters followed by three Backspaces leave four lines. The reporter also records successful behavior with Gboard 18.4.1 on Android 16, so the affected audience should not be generalized to all Android keyboards.
- **Current-source Enter and buffer-rebasing path:** src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts handles beforeinput insertParagraph/insertLineBreak by typing '\n'. onCursorStateChanged calls _updateEditContext, whose _getNewEditContextState reads only the primary selection's lines and computes offsets from the first selected line. After the caret moves to the new line, this discards the preceding line and restarts offsets, exactly the coordinate mismatch described in the report.
- **Empty-line synchronization failure:** In NativeEditContext._updateEditContext, updateText is conditional on text differing from _previousEditContextText, and updateSelection is conditional on offsets differing from _previousEditContextSelection. Moving between empty lines leaves text '' and offsets 0 unchanged, so neither call occurs despite the model line changing. This conclusively establishes the reported missing synchronization in source; Android event delivery itself was not executed during this read-only review.
- **Cross-line replacement boundary:** NativeEditContext._emitTypeEvent translates keyboard ranges into replacePrevCharCnt/replaceNextCharCnt. In src/vs/editor/common/cursor/cursorTypeEditOperations.ts, CompositionOperation._compositionType clamps replacement to the caret's current line using Math.max(1, pos.column - replacePrevCharCnt). A request to delete the preceding line break at column 1 therefore cannot join lines through this operation. The same compositionType infrastructure is also used by the textarea input path, so changing that contract requires care.
