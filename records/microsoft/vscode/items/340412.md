# Issue #340412 — NativeEditContext: Enter from a composing Android keyboard corrupts the new line

[https://github.com/microsoft/vscode/issues/340412](https://github.com/microsoft/vscode/issues/340412)

## Summary

Thorough, well-diagnosed report with code citations that match current main exactly (`_getNewEditContextState`/`_updateEditContext` in nativeEditContext.ts) — a real, reproducible-from-source bug affecting Android composing keyboards with `NativeEditContext`. Too fresh and the fix too design-heavy to close or auto-implement yet.

## Change summary

On Android with a composing keyboard (e.g. Gboard), pressing Enter mid-word or at column 1 desyncs the browser EditContext's text/offsets from the keyboard's own copy, corrupting the new line or leaving stray line breaks that a following Backspace can't remove.

## Best solution

Route to the editor/input-method owners: the reporter's own analysis (keep the EditContext's window start line stable across keyboard-originated edits, only re-anchor on non-keyboard caret moves, and relax the `replacePrevCharCnt` clamp in `cursorTypeEditOperations.ts` for cross-line joins) is a credible direction, but distinguishing 'keyboard-driven edit' from other caret moves and interactions with composition clamping need a maintainer's design call before implementation.

## Plan brief

- **Likely files:** `src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts`, `src/vs/editor/common/cursor/cursorTypeEditOperations.ts`
- **Validation:** A manual or automated repro: type across several words with a simulated composing-keyboard Enter/textupdate sequence (or a dedicated EditContext test harness) verifying the EditContext's reported text/offsets stay consistent with what a composing keyboard would compute, and that three Enters followed by three Backspaces at column 1 restores a single empty line.
- **Behavior:**

  > After a composing-keyboard Enter is pressed inside a word, the resulting two lines must match what the keyboard itself believes it typed (no stray duplicated/overwritten characters). After N Enters at column 1 followed by N Backspaces, the file returns to its original single-line state rather than leaving extra empty lines.
- **Trace:**

  > `_getNewEditContextState`/`_updateEditContext` in nativeEditContext.ts rebuild the EditContext's text window and reset offsets to the new caret line on every caret move, including one the keyboard itself just caused via its own Enter/textupdate — but the keyboard keeps acting on its own prior copy of the text at the old offsets, causing a mismatch. Separately, `CompositionOperation._compositionType` in cursorTypeEditOperations.ts clamps replacePrevCharCnt at column 1 of the caret's line, silently dropping a keyboard-issued Backspace meant to join two lines. The fix must not touch unrelated non-keyboard caret-move handling (taps, arrow keys, undo), which should keep re-anchoring the window as today. Related: https://github.com/microsoft/vscode/issues/338890 (same file, different trigger, explicitly not a duplicate).
- **Open decisions:**
  - How should the code distinguish a caret move caused by the keyboard's own edit (window should stay anchored) from any other caret move (window should re-anchor), given both arrive as ordinary selection-change notifications?
  - Should the replacePrevCharCnt clamp in cursorTypeEditOperations.ts be relaxed generally for cross-line joins, or only in a path specific to EditContext-driven composition?

## Evidence
