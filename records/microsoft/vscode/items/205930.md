# Issue #205930 — API: allow to pass in a suggested file name to `saveAs` method

[https://github.com/microsoft/vscode/issues/205930](https://github.com/microsoft/vscode/issues/205930)

## Summary

The extension-facing save APIs still cannot accept a suggested filename or destination, despite internal support for a suggested Save As target. Keep this accepted Backlog request open for API design; the older related dialog issue does not own the same capability.

## Change summary

Allow extensions to suggest a filename and save location while retaining the normal user-confirmed save dialog.

## Best solution

Extend the workspace save API in the direction endorsed by the maintainer, allowing an optional suggested destination without bypassing user confirmation. Settle filename-only and relative-path semantics before exposing the public contract.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHost.api.impl.ts`, `src/vs/workbench/api/common/extHostWorkspace.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/browser/mainThreadWorkspace.ts`, `src/vs/workbench/services/textfile/browser/textFileService.ts`, `src/vs/workbench/api/test/browser/extHostWorkspace.test.ts`, `src/vs/workbench/api/test/browser/mainThreadWorkspace.test.ts`
- **Validation:** After agreeing the API contract, add targeted extension-host/main-thread workspace tests for suggestion forwarding and cancellation. Manually invoke the API on an untitled editor with a filename-only suggestion and a destination suggestion: the normal save dialog must prefill the agreed name/location, allow user overrides, and leave the document unsaved when cancelled; calls without a suggestion must retain existing behavior.
- **Behavior:**

  > An extension saving an open editor should be able to suggest a filename and destination without committing the save before user confirmation. The suggestion should replace the automatically derived filename in the normal save dialog, and the user must remain free to change it or cancel. Existing save calls without suggestions should behave unchanged. Acceptance checks should cover an untitled editor, an existing file saved under another name, user overrides, cancellation, and the agreed filename-only and relative-path behavior.
- **Trace:**

  > The public workspace.save and workspace.saveAs declarations in src/vscode-dts/vscode.d.ts accept only the source URI. extHost.api.impl.ts forwards that URI to ExtHostWorkspace.save/saveAs, whose RPC in extHost.protocol.ts carries only a saveAs boolean; MainThreadWorkspace.$save then invokes editorService.save without any suggested target. The internal TextFileService.saveAs already passes ITextFileSaveAsOptions.suggestedTarget through suggestSavePath to pickFileToSave, whereas its untitled save branch currently derives the suggestion directly from the source. window.showSaveDialog exposes defaultUri but does not itself save or transition the existing editor, so it is only a partial alternative. The maintainer explicitly favors the workspace APIs at https://github.com/microsoft/vscode/issues/205930#issuecomment-1960805161; preserve the normal save lifecycle and user confirmation rather than treating a suggestion as a forced target. The remaining uncertainty is the public argument contract and resolution semantics, not whether the internal dialog can accept a suggested URI.
- **Open decisions:**
  - Should the public suggestion accept only a resolved destination URI, requiring extensions to resolve filename-only and relative inputs, or also accept strings with VS Code-defined resolution semantics?
  - If filename-only or relative suggestions are accepted, which directory anchors them for untitled editors and multi-root workspaces?
  - Should suggestions be available on both workspace.save and workspace.saveAs, and should workspace.save use them only when it would already prompt for a destination?
