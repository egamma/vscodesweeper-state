# Issue #343103 — Remote SSH agent host OOM when activating Agent conversations with large untracked binary files

[https://github.com/microsoft/vscode/issues/343103](https://github.com/microsoft/vscode/issues/343103)

## Summary

Keep open: the follow-up isolates opening Changes as sufficient to crash the remote agent host, including on server 1.143.0. Current source retains the whole-file Base64 encoding path; the related encoder PR is still a draft, not a landed fix.

## Change summary

Opening Changes in an SSH-connected Agents window eagerly reads large untracked binaries and exhausts the remote agent host's heap.

## Best solution

Make Changes usable with large untracked binaries without exhausting the remote agent heap. Evaluate the existing encoder fix in https://github.com/microsoft/vscode/pull/339434 against this remote workflow and address any remaining eager-content or aggregate-transfer pressure rather than assuming encoder improvements alone resolve it.

## Evidence

- **Narrowed reproduction:** https://github.com/microsoft/vscode/issues/343103#issuecomment-6325827229 reports a stable remote process with Changes and Files closed, followed by rapid memory growth and independently logged V8 OOM/SIGABRT after opening Changes alone. No prompt, individual diff selection, debugger, or heap-limit modification was required. The remote server was verified as 1.143.0, commit 2d0b7506a36c1d6db9a466440131a8e01eab2289.
- **Allocation evidence and limitations:** https://github.com/microsoft/vscode/issues/343103#issuecomment-6306118716 records eight Base64 resource reads totaling 358,448,202 bytes, packet-capture-sized backing stores, and millions of concatenated-string nodes. Its generated-data diagnostic measured approximately 42.7 MiB additional heap for encoding 1 MiB. The instrumented run had a higher heap limit and did not itself crash; the later uninstrumented Changes reproduction separately confirms the fatal outcome.
- **Current source:** At checkout cf19b1ceff2cc6e55b02e2f9bc2ed8dfb779344e, src/vs/platform/agentHost/common/agentHostFileSystemProvider.ts AHPFileSystemProvider.readFile requests ContentEncoding.Base64. src/vs/platform/agentHost/node/resourceProviders/fileSystemResources.ts FileSystemResources.read reads the complete file and invokes encodeBase64. src/vs/base/common/buffer.ts still appends four individual characters per three input bytes. These paths match the reported allocation mechanism; the exact Changes-to-file-read sequence was not conclusively traced or executed during this review.
- **Existing implementation candidate:** https://github.com/microsoft/vscode/pull/339434 is an open draft replacing per-character Base64 string accumulation with a sized output buffer. It explicitly limits its proof to bounded encoder/resource-transfer measurements and leaves full large-file workflows and concurrent transfers unverified. The reporter already linked this candidate; it is not evidence of a completed fix.
- **Related but not a verified duplicate:** https://github.com/microsoft/vscode/issues/334892 is open and older, but reports renderer OOM during plugin synchronization, including a separate plugin-enablement concern. This report instead isolates remote agent-host OOM when opening Changes with untracked workspace binaries. Shared encoder amplification does not satisfy the same-observable-symptom duplicate bar for this re-reviewed item.
