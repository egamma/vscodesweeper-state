# Issue #171301 — the length of Command center should as same as command palette

[https://github.com/microsoft/vscode/issues/171301](https://github.com/microsoft/vscode/issues/171301)

## Summary

Keep this accepted, community-supported request open: Command Center and Command Palette still use different width rules, and the built-in settings do not provide width matching. The later comments also identify menu crowding on laptops, so the intended sizing behavior needs a maintainer design decision.

## Change summary

Make the Command Center width consistent with the Command Palette while avoiding excessive title-bar space consumption on smaller windows.

## Best solution

Agree on a coherent sizing policy for the title-bar launcher and its popup, explicitly resolving width matching versus preserving menu space. Deliver that behavior through the existing title-bar layout rather than requiring external UI modification.

## Plan brief

- **Likely files:** `src/vs/workbench/browser/parts/titlebar/media/titlebarpart.css`, `src/vs/workbench/browser/parts/titlebar/titlebarPart.ts`, `src/vs/workbench/browser/parts/titlebar/commandCenterControl.ts`, `src/vs/platform/quickinput/browser/quickInputController.ts`
- **Validation:** After agreeing on the sizing contract, measure the rendered Command Center and Command Palette bounds at narrow laptop and wide desktop window sizes, including non-default display scaling and a localized menu. Verify the agreed width relationship, menu availability, launcher interaction, and absence of overlap with title-bar controls.
- **Behavior:**

  > The reporter requests equal widths for the title-bar Command Center and Command Palette. Follow-up comments additionally ask for less launcher space consumption so laptop menus remain expanded, and describe achieving that only through Windhawk. Acceptance must define the width relationship at both narrow and wide window sizes and the expected menu-overflow behavior. Preserve access to the launcher, menus, and window controls.
- **Trace:**

  > The normal title-bar launcher width is specified by .command-center-center in src/vs/workbench/browser/parts/titlebar/media/titlebarpart.css as 38vw capped at 600px. QuickInputController.updateLayout() in src/vs/platform/quickinput/browser/quickInputController.ts normally uses 62% of its layout dimension capped at 600px, with separate anchored-popup branches that should not be assumed to follow that rule. CommandCenterControl in src/vs/workbench/browser/parts/titlebar/commandCenterControl.ts builds the launcher and hides it while top-aligned quick input is visible; titlebarPart.ts hosts it. Existing window.commandCenter and window.menuBarVisibility settings do not control width matching. The source establishes separate sizing policies, not a runtime reproduction of the laptop layout. https://github.com/microsoft/vscode/issues/156377 and https://github.com/microsoft/vscode/issues/236302 provide related responsive-layout context, but neither settles this request's contract. Preserve unrelated anchored quick inputs and existing keyboard and window-control behavior.
- **Open decisions:**
  - Should the contract require equal rendered widths between the Command Center and Command Palette, or prioritize a narrower adaptive Command Center when matching would consume space needed by the menu?
  - When space is insufficient, should the Command Center shrink before menu items overflow, and is width equality expected to yield in that case?
