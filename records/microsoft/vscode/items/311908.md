# Issue #311908 — files.watcherExclude setting does not respect relative paths and folders outside the workspace are being watched

[https://github.com/microsoft/vscode/issues/311908](https://github.com/microsoft/vscode/issues/311908)

## Summary

The defect remains on current main: a recursive watcher rooted above the workspace receives workspace-relative `files.watcherExclude` patterns unchanged, so they are interpreted relative to the broader watched root. This should be routed to the file-watcher and TypeScript owners rather than closed.

## Change summary

Make workspace-relative watcher exclusions work when the built-in TypeScript service requests a recursive watch whose root is outside or above the opened workspace.

## Best solution

Preserve support for extension-requested watches outside the workspace while resolving workspace-scoped exclusion patterns against the workspace folder they came from. The TypeScript path should also avoid consuming watches for unrelated sibling folders unless those folders are genuinely part of its project.

## Plan brief

- **Likely files:** `src/vs/workbench/api/common/extHostFileSystemEventService.ts`, `src/vs/workbench/api/test/browser/extHostFileSystemEventService.test.ts`, `extensions/typescript-language-features/src/typescriptServiceClient.ts`
- **Validation:** Add an ExtHostFileSystemEventService unit test with workspace `/repo/A`, recursive watcher base `/repo`, and `files.watcherExclude` entry `to-ignore/**`; capture `$watch` and assert the effective exclusion targets `/repo/A/to-ignore/**`. End-to-end acceptance should additionally verify that the toy repository does not allocate inotify watches for excluded paths or unrelated sibling folders under the behavior selected by the maintainer.
- **Behavior:**

  > Opening `/repo/A` must not cause a workspace-relative exclusion such as `to-ignore/**` to be interpreted relative to an extension watch rooted at `/repo`. `/repo/A/to-ignore` must remain unwatched without requiring users to know or encode the watcher's external root. The plan must also settle whether unrelated siblings such as `/repo/B` and `/repo/C` remain eligible for the TypeScript-requested watch. Absolute and globstar exclusions, multi-root workspaces, and legitimate extension watches outside the workspace must continue to behave consistently.
- **Trace:**

  > The built-in TypeScript extension receives tsserver `createDirectoryWatcher` events in extensions/typescript-language-features/src/typescriptServiceClient.ts and constructs `vscode.RelativePattern(vscode.Uri.file(fpath), '**')`. `FileSystemWatcher.ensureWatching` in src/vs/workbench/api/common/extHostFileSystemEventService.ts recognizes this as recursive, reads `files.watcherExclude`, and pushes each configured key unchanged before calling `$watch`; when `fpath` is `/repo`, `to-ignore/**` is consequently matched from `/repo` rather than workspace `/repo/A`. The reproduction repository demonstrates that root-relative `A/to-ignore/**`, `B/**`, and `C/**` work, while workspace-relative `to-ignore/**` does not. Existing tests do not cover a watcher base above the configuration's workspace folder. Keep arbitrary-folder extension watching and existing in-workspace watcher behavior intact; https://github.com/microsoft/vscode/issues/225231 concerns Git repository discovery and is related but not the same defect.
- **Open decisions:**
  - For a recursive watcher rooted above the workspace, should VS Code keep the requested external scope and apply each workspace folder's relative exclusions within that folder, or should the built-in TypeScript integration constrain the watcher so unrelated sibling folders are not watched at all?

## Evidence

- **source reproduction:** extensions/typescript-language-features/src/typescriptServiceClient.ts handles `createDirectoryWatcher` by creating a recursive `vscode.RelativePattern` rooted at the path requested by tsserver, including paths outside the workspace.
- **incorrect exclusion base:** src/vs/workbench/api/common/extHostFileSystemEventService.ts, in `FileSystemWatcher.ensureWatching`, reads `files.watcherExclude` for a recursive relative-pattern watcher and forwards each key unchanged in `excludes`. The platform watcher then interprets relative strings against the watch request path, not the workspace folder where the setting was declared.
- **concrete trigger:** The reproduction opens `/repo/A` while the TypeScript watcher covers `/repo`; the setting `to-ignore/**` therefore fails to target `/repo/A/to-ignore`, while explicit root-relative entries `A/to-ignore/**`, `B/**`, and `C/**` work.
- **current test gap:** src/vs/workbench/api/test/browser/extHostFileSystemEventService.test.ts covers relative watcher matching but has no case where a recursive watcher base is an ancestor of, or outside, the workspace folder supplying `files.watcherExclude`.
- **workaround confirms path:** A commenter reports that setting `js/ts.tsserver.watchOptions.excludeDirectories` removes the inotify watches immediately, corroborating that the built-in TypeScript watcher path is responsible.
- **related issue is not canonical:** https://github.com/microsoft/vscode/issues/225231 is older and open, but reports Git Source Control repository discovery across a broad workspace. It does not report the same observable symptom of workspace-relative `files.watcherExclude` being rebased against an external TypeScript watcher root, so it does not meet the stronger duplicate bar for this re-reviewed item.
