# Issue #190974 — env.shell API should not be the empty string on start up

[https://github.com/microsoft/vscode/issues/190974](https://github.com/microsoft/vscode/issues/190974)

## Summary

The startup race remains in current source: an early-activating extension can read an empty env.shell before asynchronous profile resolution completes. The finalized change event provides a workaround, not the initial-value fix this reopened issue tracks.

## Change summary

Make env.shell report the resolved default shell when extensions first activate in shell-capable environments.

## Best solution

Establish startup ordering that makes the correct, context-resolved default shell available to early extensions while preserving workspace-variable resolution and avoiding unnecessary extension-host startup delays. Plan the local and remote initialization dependencies before implementing.

## Plan brief

- **Likely files:** `src/vs/workbench/api/browser/mainThreadTerminalService.ts`, `src/vs/workbench/api/common/extHostTerminalService.ts`, `src/vs/workbench/api/common/extHostExtensionService.ts`, `src/vs/workbench/services/extensions/common/extensionHostProtocol.ts`, `src/vs/workbench/contrib/terminal/browser/terminalProfileResolverService.ts`
- **Validation:** Use an extension with activationEvents ['*'] that records vscode.env.shell synchronously in activate. On cold launch and reload, verify it matches the resolved configured default shell in local and remote shell-capable windows, including a profile using workspace variables; verify shell-less web environments still return ''. Retain onDidChangeShell behavior after changing the default profile and compare extension-host startup timings before and after.
- **Behavior:**

  > An extension reading vscode.env.shell synchronously during early activation can currently receive an empty string even though the environment supports a default shell. The startup value should reflect the configured, context-resolved default shell without requiring polling or waiting for onDidChangeShell. Acceptance covers cold launches and reloads, local and remote hosts, and workspace-dependent profile paths. Shell-less environments must retain their empty-string behavior, and subsequent default-shell changes must remain observable.
- **Trace:**

  > The env.shell getter in src/vs/workbench/api/common/extHost.api.impl.ts calls ExtHostTerminalService.getDefaultShell, whose undefined initial _defaultProfile produces ''. MainThreadTerminalService resolves profiles asynchronously after getEnvironment and delivers them through $acceptDefaultProfile; AbstractExtHostExtensionService._startExtensionHost has no corresponding profile-readiness dependency. TerminalProfileResolverService.getDefaultProfile also needs environment and workspace-variable resolution, so the trace does not establish a safe early-initialization boundary or enumerate all affected host-startup consumers. Preserve configured-profile semantics, remote-host correctness, shell-less behavior, and later change events; do not substitute an arbitrary OS shell merely to make the string nonempty. https://github.com/microsoft/vscode/issues/160694 and https://github.com/microsoft/vscode/pull/192886 resolved event availability rather than this startup value. The maintainer session should first establish the dependency ordering and startup-cost implications before choosing an implementation.

## Evidence

- **Current source exposes the startup race:** src/vs/workbench/api/common/extHost.api.impl.ts:435-436 delegates env.shell to getDefaultShell(false). In src/vs/workbench/api/common/extHostTerminalService.ts:427 and 511-514, _defaultProfile starts undefined and the getter returns profile?.path || ''. The constructor does not initialize that profile; $acceptDefaultProfile at 1058-1064 supplies it later.
- **Profile delivery is asynchronous and activation is not gated on it:** src/vs/workbench/api/browser/mainThreadTerminalService.ts:117-129 waits for remoteAgentService.getEnvironment(), then resolves normal and automation profiles before sending $acceptDefaultProfile. src/vs/workbench/api/common/extHostExtensionService.ts:803-820 starts eager extension activation without awaiting this delivery, and IExtensionHostInitData in src/vs/workbench/services/extensions/common/extensionHostProtocol.ts contains no initial default-shell value. These independent paths permit an activation-time read before profile delivery; no code was executed.
- **The API contract and event workaround are distinct:** src/vscode-dts/vscode.d.ts:10844-10850 describes env.shell as the detected default shell, overridden by the platform's default-profile setting, and reserves an empty string for environments without shell support. onDidChangeShell is available at 10819-10823, and $acceptDefaultProfile fires it when the initial profile arrives, but neither guarantees a populated synchronous startup read.
- **Closed related issue explicitly leaves this work here:** https://github.com/microsoft/vscode/issues/160694 is closed. Its final maintainer comment, https://github.com/microsoft/vscode/issues/160694#issuecomment-1734100237, distinguishes event finalization from the initial empty-string problem and explicitly identifies https://github.com/microsoft/vscode/issues/190974 as the remaining tracker. It is therefore not a valid duplicate target.
- **Merged PR does not fix startup initialization:** https://github.com/microsoft/vscode/pull/192886 finalized onDidChangeShell by removing the proposed-API check and moving its declaration into vscode.d.ts; its diff does not initialize the default profile or change activation ordering. It merged on 2023-09-12, before this issue reopened on 2023-09-25T16:34:50Z, so it cannot substantiate a completed close.
- **Workspace-dependent resolution remains relevant:** The author's 2023-10-23 comment explains that profile evaluation needs workspace/window context. Current src/vs/workbench/contrib/terminal/browser/terminalProfileResolverService.ts:164-165 and 310-357 still resolves the profile using environment data, the last active workspace folder, and configuration-variable resolution. Moving detection earlier alone does not establish the correct resolved API value.
