## Evidence

- **Current-source ownership leak:** In src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts, ChatService._materializeUntitledSession acquires tempRef through acquireOrLoadSession, extracts tempRef.object, and returns only the model and resources. No disposal or ownership transfer is recorded; its finally block only removes the in-flight materialization entry.
- **Diagnostic attribution:** The materialization call supplies no debugOwner. ChatService.acquireExistingSession defaults that owner to ChatService#acquireExistingSession, matching the retained holder reported at https://github.com/microsoft/vscode/issues/347346.
- **Observed impact and uncertainty:** The reporter supplies concrete first-send/switch-away steps, reference diagnostics showing one retained reference per old session and no pending edits, and surviving MCP processes with the residency limit set to zero. The reference-lifetime defect is visible in source; the complete downstream subscription-to-MCP retention chain was not independently verified.
- **Open implementation candidate:** https://github.com/microsoft/vscode/pull/347350 is open and explicitly addresses this issue by managing the temporary materialized-model reference across draft disposal and UI handoff. Its published review also identifies concurrent-send abandonment handling that needs resolution before landing.
- **Related but distinct work:** https://github.com/microsoft/vscode/issues/347352 requests configurable session residency limits; changing that policy does not repair the unowned reference identified here.
