# Issue #342870 — VS Code destroys state.vscdb.backup — the file it keeps for exactly this scenario — after a single torn page in state.vscdb

[https://github.com/microsoft/vscode/issues/342870](https://github.com/microsoft/vscode/issues/342870)

## Summary

Keep open: current source confirms that corruption discovered during the initial item read bypasses backup restoration, then shutdown can replace both the database and its backup with an incomplete session cache. This is a traced data-loss path, not an extension defect or a completed fix from the older corruption-recovery issue.

## Change summary

Restore readable pre-corruption storage from state.vscdb.backup when initial item loading fails, rather than replacing the database and backup with newly accumulated session state.

## Best solution

The storage layer should recover existing items from a healthy backup when startup encounters read-time corruption, without allowing an unsuccessfully loaded cache to destroy the recoverable state. Preserve the existing recovery behavior for databases that become corrupt after their contents have been loaded successfully.

- **Backup restoration misses initial read failures:** In src/vs/base/parts/storage/node/storage.ts, connect() restores the backup only when doConnect() rejects. doConnect() executes schema/version pragmas but does not read all ItemTable records. getItems() subsequently performs SELECT * FROM ItemTable outside that recovery branch; all() marks the connection erroneous and rejects without attempting backup restoration.
- **Incomplete cache survives initialization failure:** In src/vs/base/parts/storage/common/storage.ts, Storage.init() assigns its initially empty cache only after database.getItems() succeeds. BaseStorageMain.init() in src/vs/platform/storage/electron-main/storageMain.ts catches initialization errors and completes initialization anyway. ApplicationSharedStorageMain.doCreate() then logs the fallback storage's item count, matching the reported zero-item initialization.
- **Source-confirmed destructive shutdown path:** Storage.doClose() in src/vs/base/parts/storage/common/storage.ts passes database.close(() => this.cache), even after a flush error. SQLiteStorageDatabase.doClose() unlinks an erroneous database, creates a fresh connection, inserts that cache, and recursively closes the recovery connection. If that connection is healthy, its close immediately invokes backup(), which copies the rebuilt database over the existing .backup. Thus backup destruction can occur during the recovery shutdown itself, without waiting for another session.

Neither covers a valid opening followed by initial SELECT failure with a healthy pre-existing backup and an uninitialized cache.

Its maintainer explanation and verification explicitly accept losing old workspace state and rebuilding state accumulated during the new session.
