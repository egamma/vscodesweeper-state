# Issue #345282 — Cloud sandbox session feed: an unreadable message before the handshake is retried, after it stops the feed

[https://github.com/microsoft/vscode/issues/345282](https://github.com/microsoft/vscode/issues/345282)

## Summary

The handshake-dependent retry and telemetry asymmetry remains in current source. Keep this follow-up open while the maintainer chooses whether unreadable messages should permanently stop the feed or trigger bounded retries in both phases.

## Change summary

Make unreadable cloud sandbox feed messages produce consistent retry behavior and telemetry before and after the handshake.

## Best solution

Establish one malformed-message policy in CloudSandboxSessionFeed, apply it consistently across handshake phases, and cover both phases with outcome and retry-scheduling assertions while preserving polling fallback.

Run scripts/test.sh --run src/vs/workbench/contrib/chat/test/browser/remoteAgentHost/cloudSandboxSessionFeed.test.ts --grep CloudSandboxSessionFeed after preparing test output in a writable implementation checkout.
- **Behavior:**

  > An unreadable cloud sandbox feed frame currently causes slow retries before the handshake but permanent polling fallback after it, with different telemetry classifications. Both phases should follow the same maintainer-approved recovery policy. Acceptance checks must assert the reported outcome and whether subsequent negotiations occur for invalid JSON received in each phase. Ordinary network failures must retain their bounded recovery behavior, and discovery polling must continue while push is unavailable.
- **Trace:**

  > CloudSandboxSessionFeed._doConnect in src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxSessionFeed.ts catches parsing failures in socket.onmessage and calls disconnected(false). Before ready settles, disconnected rejects with a generic error; the surrounding catch loses the malformed-message reason, schedules retryPolicy, and emits socketFailed. After activation, the same callback clears the active connection, cancels reconnect scheduling, and emits invalidMessage. The existing CloudSandboxSessionFeed test suite covers only post-handshake malformed frames and already exposes an autoReady:false socket fixture and fake timers. Preserve ordinary socket-error recovery, unavailable-account termination, renewal behavior, polling fallback, and credential-safe diagnostics. https://github.com/microsoft/vscode/issues/345234 tracks this as an outstanding follow-up, and https://github.com/microsoft/vscode/pull/345268#discussion_r4428432048 supplies the original diagnosis. The uncertainty is the recovery policy, not the location or mechanics of the defect.
- **Open decisions:**
  - Should unreadable feed messages permanently disable push until the account or feature lifetime restarts, or permit slow bounded recovery retries, consistently before and after the handshake?
