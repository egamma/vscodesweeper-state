# Issue #251161 — Put user into restricted mode when policy error occurs

[https://github.com/microsoft/vscode/issues/251161](https://github.com/microsoft/vscode/issues/251161)

## Summary

Keep open: malformed device-policy files still do not trigger restricted mode, and the linked warning issue does not own this additional enforcement requirement. A maintainer should decide the restriction and recovery contract; the Backlog milestone and security-sensitive policy boundary rule out a decline close.

## Change summary

Consider restricting VS Code functionality while an enterprise policy cannot be loaded or applied.

## Best solution

Define which policy failures require fail-closed behavior, which capabilities must be blocked, and when normal operation resumes. Keep this separate from warning-only work and distinguish enterprise enforcement from user-controlled Workspace Trust.

## Evidence

- **Existing-capability check:** src/vs/platform/policy/common/filePolicyService.ts: FilePolicyService.read() catches JSON parsing and other read errors, logs non-FILE_NOT_FOUND failures, and returns an empty policy map. refresh() installs that map; this path does not enter restricted mode.
- **Workspace Trust is a different boundary:** src/vs/workbench/services/workspaces/common/workspaceTrust.ts: WorkspaceTrustEnablementService.isWorkspaceTrustEnabled() reads security.workspace.trust.enabled and the disable-workspace-trust flag. WorkspaceTrustManagementService.calculateWorkspaceTrust() derives trust from workspace/resource trust, not policy-file errors. Existing Restricted Mode therefore does not automatically deliver the requested enforcement.
- **Partial existing enforcement:** src/vs/workbench/services/policies/browser/accountPolicyGateContribution.ts implements fail-closed account/managed-settings gating, including restricted gate state and managed-settings refresh handling. This narrower account/AI gate is not a general restriction for malformed device-policy JSON.
