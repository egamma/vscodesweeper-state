# Issue #348742 — Settings Sync doesn't cover ~/.copilot customizations used by the Copilot agent runtime

[https://github.com/microsoft/vscode/issues/348742](https://github.com/microsoft/vscode/issues/348742)

## Summary

Keep open: migration moves personal customizations outside the directory Settings Sync watches and synchronizes. The existing skills-sync request covers only part of this regression, not migrated instructions and agents.

## Change summary

Preserve cross-machine synchronization of personal customizations after migration to the Copilot runtime.

## Best solution

Restore a supported path that both synchronizes personal customizations and makes them available to the Copilot runtime. Decide whether profile-backed customizations remain authoritative or Settings Sync gains explicit coverage of the new personal directories.

- **Behavior:**

  > Personal instructions and agents that previously synchronized must remain available across machines after migrating to the Copilot runtime. Editing an active personal customization on one machine must update the customization consumed on another synchronized machine without manual copying or repeated migration. The report also requests coverage of personal skills. Existing profile synchronization and user control over synchronization must remain intact.
- **Trace:**

  > PromptsSynchronizer in src/vs/platform/userDataSync/common/promptsSync/promptsSync.ts watches, reads, and writes profile.promptsHome only; getPromptsFileContents() enumerates immediate files with four recognized suffixes. The userDataMigrationCategory in src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationCategories.ts relocates agents and instructions because the harness ignores their original user-data location. Personal Copilot locations are defined separately in src/vs/workbench/contrib/chat/common/promptSyntax/config/promptFileLocations.ts. This establishes why edits after migration are outside the existing sync path, but does not settle the intended relationship between profile-scoped data and shared home-directory customizations. https://github.com/microsoft/vscode/issues/296414 tracks the skills subset; retain that relationship without treating it as ownership of the entire regression. Preserve existing profile isolation and conflict semantics, and do not expand synchronization to unrelated ~/.copilot content.
- **Open decisions:**
  - Should synchronized personal customizations remain profile-owned and be consumed by the Copilot runtime, or should Settings Sync synchronize the shared ~/.copilot customization directories?
  - If shared home-directory customizations are synchronized, how should their scope interact with separate VS Code profiles and the existing Prompts and Instructions sync selection?

## Evidence

- **Current sync boundary:** src/vs/platform/userDataSync/common/promptsSync/promptsSync.ts assigns PromptsSynchronizer.promptsFolder = profile.promptsHome, watches that folder, and reads only its immediate prompt/instruction/chatmode/agent files in getPromptsFileContents(). updateLocalPrompts() also writes exclusively into that folder; ~/.copilot edits do not enter this synchronization path.
- **Migration crosses the sync boundary:** src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationCategories.ts defines userDataMigrationCategory for agents and instructions. Its description explicitly says the active harness ignores user-data customizations, and its confirmation offers deleting originals after relocation. Keeping originals therefore does not synchronize subsequent destination edits.
- **Personal destination locations:** src/vs/workbench/contrib/chat/common/promptSyntax/config/promptFileLocations.ts defines ~/.copilot/agents, ~/.copilot/instructions, and ~/.copilot/skills as personal customization locations, separate from profile.promptsHome.

It requests synchronization of ~/.copilot/skills; it does not cover the loss of existing instructions/agents synchronization after migration, so it is not a full-scope duplicate canonical.
