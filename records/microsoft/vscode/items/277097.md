# Issue #277097 — Show widget when there is new entry in Copilot model list

[https://github.com/microsoft/vscode/issues/277097](https://github.com/microsoft/vscode/issues/277097)

## Summary

A real model-discoverability gap remains on current main. The newer related issue covers only the picker badge portion and cannot be the canonical duplicate for this re-reviewed, older, broader request.

## Change summary

Notify users when new Copilot models become available, including models hidden by enterprise policy, and dismiss the notification after it is viewed.

## Best solution

Use this older issue to settle the complete model-awareness experience: which surface signals a new model, how unavailable models are represented, and exactly what user action dismisses the signal. ## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerWidget.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerItems.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerItemSections.ts`, `src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerBadges.ts`, `src/vs/workbench/contrib/chat/common/languageModels.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/input/modelPicker/modelPickerItems.test.ts`
- **Validation:** Add model-picker tests that introduce a previously unseen Copilot model, verify the chosen notification and per-model affordances, verify policy-disabled models follow the decided behavior, and verify the signal remains dismissed after the specified user action.
- **Behavior:**

  > Users should receive a clear but non-persistent indication when a newly supported Copilot model becomes relevant to them, including the decided treatment for models hidden by enterprise policy. The experience must identify or lead users to the new model without treating every model as new on first use. After the agreed acknowledgement action, the indication must disappear and remain dismissed. Existing model selection, pinned models, unavailable-model messaging, and BYOK-provider behavior must remain unchanged.
- **Trace:**

  > The legacy picker path creates its static Manage Models action in createManageModelsAction and places it through buildModelPickerItems/modelPickerItemSections; the tabbed path is assembled by ModelPickerWidget.show and ModelPickerTabbedWidget. ModelPickerWidget already receives ILanguageModelsService change events, reads the control manifest, and has application-scoped IStorageService access, but current source has no previously-seen model concept or new-model badge. modelPickerBadges.ts currently ranks only retirement, promotional discount, and provider treatments. The report broadened from an unavailable enterprise model to general awareness, while https://github.com/microsoft/vscode/issues/298198 tracks the narrower "Other Models" badge. The boundary is model awareness and acknowledgement state: do not alter entitlement enforcement, enterprise model availability, BYOK discovery, or model-selection semantics.
- **Open decisions:**
  - Should the primary notification appear only inside the model picker, on the top-level model control, or through the existing chat-tip surface as well?
  - Should enterprise-disabled new models be listed visibly as unavailable, represented only by a Manage Models notification, or omitted after the notification is acknowledged?
  - What user action acknowledges a new model: opening the picker, expanding Other Models, opening Manage Models, or viewing the specific model row?
