# Issue #221343 — Packaging task has poor parallelization

[https://github.com/microsoft/vscode/issues/221343](https://github.com/microsoft/vscode/issues/221343)

## Summary

Keep open as build-performance debt: current packaging still sequences major stages, but its esbuild-based internals already perform concurrent work. The reported 45-minute, single-core behavior needs fresh measurement before identifying a safe optimization or declaring it resolved.

## Change summary

Improve multicore utilization and elapsed time for the Linux desktop build-and-package task.

## Best solution

Profile the current Linux packaging task in a comparable devcontainer, identify its critical path, and improve concurrency where artifact dependencies permit. Preserve package correctness and establish measured gains rather than assuming a 48-core machine permits a 48-fold speedup.

## Plan brief

- **Likely files:** `build/gulpfile.vscode.ts`, `build/gulpfile.extensions.ts`, `build/lib/extensions.ts`, `build/lib/esbuild.ts`, `build/next/index.ts`, `build/lib/gulp/task.ts`
- **Validation:** In a separate writable Linux devcontainer, benchmark npm run gulp -- vscode-linux-x64 on the baseline and candidate with identical CPU limits, dependencies, and cache conditions. Record stage durations, process-tree CPU utilization, wall time, and peak memory over repeated runs; verify successful packaging and launch the resulting Code OSS executable. Establish a measured improvement target from the baseline rather than treating the suggested one-minute duration as a requirement.
- **Behavior:**

  > Building and packaging the Linux x64 desktop distribution should use available resources effectively without changing the resulting application's behavior or required package contents. The report describes approximately 45 minutes with roughly one core utilized on a 48-core host; those observations must first be reassessed on the current build pipeline. Acceptance requires repeatable elapsed-time improvement against a comparable baseline, successful packaging, and a launchable result without an unacceptable memory increase.
- **Trace:**

  > The vscode-linux-x64 task is registered in build/gulpfile.vscode.ts through a series of extension compilation, media compilation, desktop bundling, and final packaging stages. build/lib/gulp/task.ts confirms these stages execute sequentially, but this alone does not identify unnecessary serialization. runEsbuildBundle in build/lib/esbuild.ts delegates to build/next/index.ts, where bundle builds entry points concurrently; build/lib/extensions.ts also launches extension-media builds and type checks concurrently. The remaining uncertainty is which stage currently dominates and whether its work is CPU-bound, I/O-bound, or constrained by container resources. Shared extension outputs, cleanup ordering, localization metadata, timestamps, and downstream package checksums are correctness boundaries that must remain intact. https://github.com/microsoft/vscode/issues/317504 documents related implicit artifact dependencies but explicitly leaves performance optimization to follow-up work; this issue remains the separate performance report.

## Evidence

The sole maintainer comment concerns ownership; it does not confirm a bottleneck or establish a fix.
- **Current orchestration:** build/gulpfile.vscode.ts:583-620 registers vscode-linux-x64 through task.series: extension preparation, non-native extension compilation, Copilot compilation, extension media, desktop bundling, then native-extension compilation and packaging. build/lib/gulp/task.ts:52-59 awaits each series member sequentially. This establishes stage ordering, not the reported CPU utilization or elapsed time.
- **Existing concurrency:** build/lib/esbuild.ts:51-82 delegates desktop bundling to build/next/index.ts. Current source therefore does not support a blanket claim that the entire build uses only one core.
