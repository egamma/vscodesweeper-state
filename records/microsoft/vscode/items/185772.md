# Issue #185772 — Support "additionalTextEdits" for _other_ files in CompletionItems

[https://github.com/microsoft/vscode/issues/185772](https://github.com/microsoft/vscode/issues/185772)

## Summary

A real extension API gap remains on current main: completion additional edits are still limited to the active document. The Backlog feature request is correctly routed and has no verified canonical duplicate.

## Change summary

Allow completion items resolved asynchronously to apply additional edits to files other than the completion document.

## Best solution

Design a workspace-scoped completion edit API and update the suggest acceptance pipeline to apply its edits with explicit version, conflict, undo, and late-resolution semantics. Coordinate any API shape with LSP completion capabilities so language servers can use it without command-based workarounds.

## Evidence

- **current public API:** src/vscode-dts/vscode.d.ts defines CompletionItem.additionalTextEdits as TextEdit[], with no URI or WorkspaceEdit support.
- **current internal model:** src/vs/editor/common/languages.ts represents completion additionalTextEdits as ISingleEditOperation[], which cannot identify another resource.
- **application path:** src/vs/editor/contrib/suggest/browser/suggestController.ts applies additional edits through the active editor's executeEdits call, so the implementation remains single-document.
- **related issue:** https://github.com/microsoft/vscode/issues/183092 remains open but concerns asynchronously resolving the primary completion text, not applying additional edits across files, so it does not absorb this request.
- **originating discussion:** https://github.com/microsoft/vscode/issues/184924 documents why commands are an unreliable and payload-heavy workaround and explicitly led to this workspace-edit proposal.
