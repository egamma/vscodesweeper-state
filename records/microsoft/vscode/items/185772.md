# Issue #185772 — Support "additionalTextEdits" for _other_ files in CompletionItems

[https://github.com/microsoft/vscode/issues/185772](https://github.com/microsoft/vscode/issues/185772)

## Summary

The cross-file completion-edit capability remains missing: current additionalTextEdits apply only to the active document, while commands do not receive the same late-resolution handling. Keep this accepted Backlog request open; the related command regression was resolved, but not this API gap.

## Change summary

Allow completion providers to resolve additional edits targeting other files, such as imports in the library containing a Dart part file.

## Best solution

Provide an editor-managed cross-document completion-edit contract that supports late resolution without delaying the primary insertion. Agree on the public API and cross-document conflict and undo semantics before implementation, preserving existing same-document completion behavior.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/editor/common/languages.ts`, `src/vs/editor/contrib/suggest/browser/suggestController.ts`, `src/vs/workbench/api/common/extHost.protocol.ts`, `src/vs/workbench/api/common/extHostLanguageFeatures.ts`, `src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts`, `src/vs/editor/contrib/suggest/test/browser/suggestController.test.ts`
- **Validation:** Use a completion provider with a deliberately delayed resolve that returns an import edit for a second document. Accept before resolve completes: the primary insertion must be immediate, and the second-document edit must subsequently follow the agreed conflict and undo contract. Cover acceptance after resolution, cancellation, target-document changes, and unchanged same-document additionalTextEdits behavior in executable regression checks.
- **Behavior:**

  > A completion accepted in one document can supply additional text edits for another document during resolution, as required when Dart imports belong in a part file's containing library. Acceptance must not wait for resolution before inserting the primary completion. Late edits should be handled by the editor under a documented conflict and undo contract, rather than relying on an arbitrary command added during resolve. Existing same-document edits and commands supplied upfront must retain their behavior.
- **Trace:**

  > CompletionItem.additionalTextEdits in src/vscode-dts/vscode.d.ts is TextEdit[], and the internal CompletionItem and ISuggestDataDto represent those edits without target resources. CompletionsAdapter in src/vs/workbench/api/common/extHostLanguageFeatures.ts serializes and forwards resolved edits through the main-thread language-feature bridge. SuggestController in src/vs/editor/contrib/suggest/browser/suggestController.ts applies both immediate and late edits to its current editor, while command execution happens during acceptance rather than after late resolution. These paths establish the missing capability without executing code. The maintainer explicitly requested this separate cross-file issue in https://github.com/microsoft/vscode/issues/184924#issuecomment-1600780612; https://github.com/microsoft/vscode/issues/183092 addresses a different primary-edit contract. Preserve immediate primary insertion and existing completion semantics; the uncertainty begins at the new public cross-document contract and its conflict and undo guarantees.
- **Open decisions:**
  - Should cross-document completion edits use a new property or extend the existing additionalTextEdits contract, and what compatibility contract should providers receive?
  - What should happen when a target document changes before late resolution completes: reject the related edit set or permit unaffected edits to apply?
  - Should late edits in other documents share the completion's undo operation or be independently undoable?
