# Issue #336736 — Custom endpoints can send unsupported sampling parameters

[https://github.com/microsoft/vscode/issues/336736](https://github.com/microsoft/vscode/issues/336736)

## Summary

Confirmed on main: `_applyConfiguredModelOptions` in `openAIEndpoint.ts` lets a per-request `temperature`/`top_p` value (the generic agent sampling defaults) override the model's own `modelOptions` values, exactly the precedence bug described — real gap in the BYOK/`customendpoint` request path.

## Change summary

A `customendpoint` model configured with fixed `modelOptions.temperature`/`top_p` still gets overridden by the agent's generic per-request sampling values, so the upstream API rejects the request.

## Best solution

Decide (with a maintainer) whether a model's configured `modelOptions.temperature`/`top_p` should always win over per-request sampling, or whether a new explicit "required/fixed" flag is needed alongside the existing default-style `modelOptions`, then apply that precedence in `_applyConfiguredModelOptions`.

- **Validation:** Add a test in openAIEndpoint.spec.ts building a request body for a model with configured modelOptions.temperature/top_p while options.requestOptions supplies different values, asserting the final decision (whichever precedence the maintainer picks) is applied; must fail against current code before the change.
- **Behavior:**

  > When a custom-endpoint model has model-specific sampling constraints declared (via modelOptions or a new constraints field), the final request body sent to the upstream API must respect those constraints even when the agent's generic per-request sampling options (options.requestOptions.temperature/top_p) differ. Models without declared constraints should continue to honor explicit per-request values unchanged. Acceptance: a new/updated test in openAIEndpoint.spec.ts confirms the configured value wins for a constrained model, and existing sampling-related tests still pass.
- **Trace:**

  > Root cause is `_applyConfiguredModelOptions` in extensions/copilot/src/extension/byok/node/openAIEndpoint.ts (lines 302-324), called from `createRequestBody` for all three API shapes (Responses, Messages, Chat Completions). It resolves `body[key]` by checking `options.requestOptions?.[key]` first, so a defined per-request value always wins over `this.modelMetadata.modelOptions[key]`. The boundary: this function is the single request-body normalization point for temperature/top_p across all customendpoint API formats — do not touch `_applyReasoningEffort` or the tool/thinking-model logic in `interceptBody`. The open question the maintainer must settle is a schema/semantics one: whether to flip precedence unconditionally for any configured modelOptions value, or introduce a distinct "required" marker so existing users relying on overridable defaults aren't broken — see extensions/copilot/src/platform/endpoint/common/endpointProvider.ts's `IChatModelRequestOptions` for where such a flag would live.
- **Open decisions:**
  - Should configured modelOptions.temperature/top_p always override per-request sampling, or only when explicitly marked as a required/fixed constraint (needing a new field on IChatModelRequestOptions)?
  - If a new 'required' concept is added, is it opt-in per field (temperature vs top_p independently) or an all-or-nothing model-level flag?
  - Does this change need to extend to other BYOK providers (Anthropic, Gemini native) that don't currently apply this reconciliation, or is it scoped to the OpenAI-compatible chat-completions/responses/messages paths only?

## Evidence
