# Issue #257621 — Simplify wrapping an npm MCP server package in VS Code Extension

[https://github.com/microsoft/vscode/issues/257621](https://github.com/microsoft/vscode/issues/257621)

## Summary

A real API gap remains: extensions must translate an npm package into a command-based MCP definition themselves. This member-authored Backlog request is protected from a judgment close, while the related newer issue was closed out-of-scope and cannot serve as a duplicate canonical.

## Change summary

Let an extension identify an npm MCP server package and have VS Code resolve and launch it without extension-specific command plumbing.

## Best solution

Decide whether the extension API should expose a generic registry-style package descriptor rather than an npm-specific type, then define VS Code's package resolution, trust, installation, and launch responsibilities before finalizing the public contract.

## Plan brief

- **Likely files:** `src/vscode-dts/vscode.d.ts`, `src/vs/workbench/api/common/extHostTypes.ts`, `src/vs/workbench/api/common/extHostMcp.ts`, `src/vs/workbench/api/common/extHostTypeConverters.ts`, `src/vs/workbench/contrib/mcp/common/mcpTypes.ts`
- **Validation:** Add extension-host MCP API tests showing that a package-based provider definition is converted into a valid launch configuration, including scoped npm package names, arguments, environment values, and resolution failures.
- **Behavior:**

  > An extension wrapping an npm-distributed MCP server can identify the package without locating its installed entry point or constructing a Node command itself. VS Code resolves the package into a launchable MCP server while preserving provider-supplied arguments, environment, working directory, and version metadata. Resolution failures must be surfaced explicitly, and existing command-based stdio and HTTP definitions must remain compatible.
- **Trace:**

  > The stable API in src/vscode-dts/vscode.d.ts currently exposes only McpStdioServerDefinition and McpHttpServerDefinition; stdio requires a concrete command and arguments. ExtHostMcpService.registerMcpConfigurationProvider in src/vs/workbench/api/common/extHostMcp.ts validates provider results and passes them through the existing conversion path, with no package-resolution layer. The concrete API classes are implemented in src/vs/workbench/api/common/extHostTypes.ts, and internal launch contracts live in src/vs/workbench/contrib/mcp/common/mcpTypes.ts. The related discussion at https://github.com/microsoft/vscode/issues/262904 established that an npm-only type would not generalize to other registry package formats, but its out-of-scope closure leaves the broader contract undecided. Preserve the existing stdio/HTTP behavior and do not conflate package resolution with silent installation or trust approval.
- **Open decisions:**
  - Should the public contract accept an npm-specific package name, or a generic registry-style package descriptor that can later represent PyPI, NuGet, Cargo, Go, and other package types?
  - Does VS Code only resolve packages bundled as extension dependencies, or may it acquire packages that are not already installed?
  - What user-visible trust or consent behavior is required before resolving or executing a package-based MCP server?

## Evidence

- **current API gap:** On current main, src/vscode-dts/vscode.d.ts defines McpStdioServerDefinition with command and args and McpServerDefinition as only stdio or HTTP; no package-name definition exists.
- **runtime path:** src/vs/workbench/api/common/extHostTypes.ts implements McpStdioServerDefinition as label, command, args, env, and version, while src/vs/workbench/api/common/extHostMcp.ts converts provider results directly into launch definitions without resolving npm package metadata.
