# Issue #50047 — Allow Code Outline in Minimap location

[https://github.com/microsoft/vscode/issues/50047](https://github.com/microsoft/vscode/issues/50047)

## Summary

Keep open: moving Outline to the secondary sidebar addresses simultaneous visibility with Explorer, but does not provide independent outlines beside each editor. The remaining request has 44 upvotes, and no verified open canonical absorbs it.

## Change summary

Allow a persistent, editor-specific code outline in the space currently occupied by the minimap.

## Best solution

Design an optional per-editor outline surface that preserves each visible editor's symbol context without changing the existing global Outline view. Resolve the narrow-editor layout concern before committing to an editor-local presentation; a general-purpose widget bar is a separate scope expansion.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/outline/browser/outlinePane.ts`, `src/vs/workbench/contrib/outline/browser/outline.contribution.ts`, `src/vs/editor/browser/viewParts/minimap/minimap.ts`, `src/vs/editor/common/config/editorOptions.ts`
- **Validation:** After agreeing on a design, open two symbol-bearing files side by side, enable the editor-local outline presentation, and verify each outline stays associated with its own editor as focus changes. Check symbol navigation, resizing to narrow editor groups, and preservation of the existing sidebar Outline and default minimap behavior.
- **Behavior:**

  > Users can keep a code outline beside each visible editor rather than choosing between Explorer and Outline or moving a single active-editor Outline across the screen. Changing focus between split editors must not replace the other editor's displayed outline. Acceptance includes correct symbol navigation for each editor and predictable behavior when an editor group becomes narrow. The existing sidebar Outline and default minimap experience remain available.
- **Trace:**

  > src/vs/workbench/contrib/outline/browser/outline.contribution.ts registers Outline as a movable workbench view. OutlinePane.renderBody in src/vs/workbench/contrib/outline/browser/outlinePane.ts listens for active-editor changes, and _handleEditorControlChanged obtains an outline through the outline service for that editor. Current minimap registrations in src/vs/editor/common/config/editorOptions.ts expose rendering and comment-section settings, not an outline replacement; the minimap renderer lives in src/vs/editor/browser/viewParts/minimap/minimap.ts. The secondary-sidebar workaround discussed in https://github.com/microsoft/vscode/issues/50047 does not remove this active-editor coupling. The trace establishes the gap but not the editor-local hosting design or its full implementation boundary. Preserve existing workbench Outline semantics and keep the later suggestion of an arbitrary widget bar outside the initial feature scope.
- **Open decisions:**
  - Should the editor-local outline replace the minimap as an alternative mode, or be a separate optional surface that can coexist with it?
  - When a split editor becomes too narrow, should its outline collapse automatically, remain visible with a minimum width, or require explicit user dismissal?

## Evidence

- **Remaining user need:** In https://github.com/microsoft/vscode/issues/50047, the June 2024 discussion explicitly distinguishes the secondary-sidebar workaround from replacing the minimap. - **Current Outline ownership:** src/vs/workbench/contrib/outline/browser/outline.contribution.ts registers one movable workbench Outline view with canMoveView: true and the outline.focus command. In outlinePane.ts, renderBody subscribes to onDidActiveEditorChange and passes activeEditorPane into _handleEditorChanged; this remains an active-editor view, not an independent outline attached to each visible editor.

These control the minimap and comment-based section headings, not a document-symbol tree replacing it.
