# Issue #221873 — Add css variables with editor font settings

[https://github.com/microsoft/vscode/issues/221873](https://github.com/microsoft/vscode/issues/221873)

## Summary

The debt remains on current main: editor font styling is still copied into individual widgets, and the editor container exposes only font size as a CSS variable. Route this to the editor area for a shared, configuration-reactive solution.

## Change summary

Expose resolved editor font properties as CSS variables so editor-adjacent UI can inherit them without imperative styling and bespoke configuration listeners.

## Best solution

Define and maintain a coherent set of editor-scoped CSS variables from resolved editor font options, then migrate UI that only needs styling to consume those variables while retaining imperative font metrics where layout calculations require them.

- **Reason:** Centralizing editor font styling improves settings fidelity and consistent UI behavior without adding new product surface.

## Plan brief

- **Likely files:** `src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts`, `src/vs/workbench/contrib/debug/browser/exceptionWidget.ts`, `src/vs/workbench/contrib/comments/browser/commentThreadWidget.ts`, `src/vs/workbench/contrib/testing/browser/testingDecorations.ts`
- **Validation:** Add an editor widget test that asserts each shared font CSS variable is initialized from resolved editor options and changes after the corresponding editor option is updated; then run the targeted editor widget test suite.
- **Behavior:**

  > Editor-adjacent UI that is intended to use the editor font should track changes to editor font family, size, weight, and line height without being recreated or maintaining its own configuration listener. Changing those editor settings must update existing rendered widgets. UI that deliberately uses a different font, and code that needs measured character widths for layout, must remain unchanged.
- **Trace:**

  > CodeEditorWidget in src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts already establishes a local precedent by setting `--editor-font-size`, but it does not expose the other resolved font properties. ExceptionWidget imperatively copies font size and line height only during `_fillContainer`; CommentThreadWidget and TestingDecorations define component-specific variables and listeners. The wider EditorOption.fontInfo search also includes metric calculations such as typical character width, which are outside the CSS migration boundary and must continue reading FontInfo. The planning pass should enumerate only styling assignments and identify an editor widget test location before implementation.

## Evidence

- **current editor surface:** src/vs/editor/browser/widget/codeEditor/codeEditorWidget.ts currently sets only `--editor-font-size` on the editor DOM element and updates it only when EditorOption.fontSize changes.
- **remaining duplication:** src/vs/workbench/contrib/debug/browser/exceptionWidget.ts reads EditorOption.fontInfo and imperatively assigns fontSize and lineHeight when the widget is created.
- **component-specific variables:** src/vs/workbench/contrib/comments/browser/commentThreadWidget.ts and src/vs/workbench/contrib/testing/browser/testingDecorations.ts still create their own editor-font CSS variables and update paths.
- **existing partial precedent:** Webview-specific `--vscode-editor-font-family`, `--vscode-editor-font-weight`, and `--vscode-editor-font-size` values are generated separately in src/vs/workbench/contrib/webview/browser/themeing.ts; they are not shared editor-container variables for workbench widgets.
