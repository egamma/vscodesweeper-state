# Issue #174905 — Add a webview/title contribution point

[https://github.com/microsoft/vscode/issues/174905](https://github.com/microsoft/vscode/issues/174905)

## Summary

Keep open: editor/title with activeWebviewPanelId supports displaying a button, but does not fully address the reporter's follow-up requirement to identify the originating WebviewPanel instance. The related open context-menu issue covers a different, narrower problem and is newer than this re-reviewed request.

## Change summary

Allow extensions to contribute webview editor title actions that can identify the particular WebviewPanel on which they were invoked.

## Best solution

Provide a supported, instance-aware command context for webview title actions while preserving existing editor/title contributions. Decide the extension-facing contract before implementation; displaying a button using activeWebviewPanelId alone does not complete this request.

## Plan brief

- **Likely files:** `src/vs/workbench/services/actions/common/menusExtensionPoint.ts`, `src/vs/workbench/browser/parts/editor/editorTabsControl.ts`, `src/vs/workbench/contrib/webviewPanel/browser/webviewEditorInput.ts`, `src/vs/workbench/api/browser/mainThreadWebviewPanels.ts`, `src/vs/workbench/api/common/extHostWebviewPanels.ts`, `src/vscode-dts/vscode.d.ts`
- **Validation:** Use an extension-host fixture that creates two WebviewPanels sharing one viewType and one contributed title command. Invoke each panel's title action with focus both on and away from that panel, and verify the command identifies the originating instance and acts only on it; existing editor/title command arguments and visibility must remain compatible.
- **Behavior:**

  > An extension can display a title action for its webview editors and determine exactly which WebviewPanel the user invoked it on. Multiple dynamically created panels may share the same viewType and contributed command. Acceptance must cover actions on both panels, including invocation when another panel has focus, without relying solely on globally active-panel state. Existing editor title contributions must continue working.
- **Trace:**

  > The discussion in https://github.com/microsoft/vscode/issues/174905 establishes that editor/title plus activeWebviewPanelId solves button visibility but leaves panel-instance identification unresolved. The context key in src/vs/workbench/contrib/webviewPanel/browser/webviewEditor.ts carries viewType only. WebviewInput.resource in src/vs/workbench/contrib/webviewPanel/browser/webviewEditorInput.ts contains an internal generated resource identity, while ExtHostWebviewPanels in src/vs/workbench/api/common/extHostWebviewPanels.ts maintains a separate private handle-to-panel map. Editor title infrastructure in src/vs/workbench/browser/parts/editor/editorTabsControl.ts carries workbench editor context, which is not itself a public WebviewPanel reference. The uncertainty is the public command-context contract and compatibility expectations, not whether a toolbar button can already be displayed. Preserve generic editor/title behavior and keep the inactive-tab menu-visibility request at https://github.com/microsoft/vscode/issues/195960 distinct.
- **Open decisions:**
  - Should webview title commands receive the originating WebviewPanel directly, or should extensions receive a supported identifier they can resolve to their panel instances?
  - Should the instance-aware contract extend existing editor/title contributions compatibly, or be exposed through a dedicated webview/title contribution point?
