# Issue #120250 — SCM - Add filter to Source Control tab to view only modified repos

[https://github.com/microsoft/vscode/issues/120250](https://github.com/microsoft/vscode/issues/120250)

## Summary

Keep this accepted SCM request open: current source supports repository selection and count badges, but not a changes-only repository filter. Related reports reinforce the demand; none verified qualifies as an older, open canonical for this re-reviewed issue.

## Change summary

Offer an optional Source Control filter that hides repositories without local changes in large multi-repository workspaces.

## Best solution

Provide an opt-in changes-only SCM view while preserving access to all repositories and existing manual selection. Settle how filtering interacts with repository selection and live change updates before implementation; staged-only filtering is optional follow-up scope.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/scm/browser/scm.contribution.ts`, `src/vs/workbench/contrib/scm/browser/scmViewService.ts`, `src/vs/workbench/contrib/scm/browser/scmRepositoriesViewPane.ts`, `src/vs/workbench/contrib/scm/browser/scmViewPane.ts`
- **Validation:** After the product decisions, exercise a workspace with clean, unstaged, staged-only, and untracked-only repositories. Enable the filter and verify qualifying repositories remain visible; change a clean repository and commit the final change in a dirty repository to verify live membership updates. Disable the filter and verify all repositories and prior manual selection remain accessible. Cover the chosen predicate and selection semantics with targeted SCM unit tests.
- **Behavior:**

  > In a workspace containing many repositories, users need an optional way to focus Source Control on repositories with local changes instead of scrolling through clean repositories. The filtered view must retain repositories with qualifying changes and provide a clear way back to the complete list. Acceptance should cover staged-only, unstaged, and untracked changes, transitions between clean and changed states, and the chosen interaction with manual repository selection. Existing behavior remains unchanged when filtering is disabled; additional status-specific filters are not required by the central request.
- **Trace:**

  > SCMViewService in src/vs/workbench/contrib/scm/browser/scmViewService.ts exposes all non-hidden repositories and derives visibleRepositories from selectionIndex, with no changes-only predicate. RepositoryTreeDataSource.getChildren in src/vs/workbench/contrib/scm/browser/scmRepositoriesViewPane.ts builds repository rows from that service using parentId; SCMViewPane.getChildren in src/vs/workbench/contrib/scm/browser/scmViewPane.ts consumes visibleRepositories, while SCMTreeFilter only suppresses empty resource groups. Configuration registrations in src/vs/workbench/contrib/scm/browser/scm.contribution.ts provide selection, sorting, sizing, and count badges but no equivalent filter. The boundary is SCM presentation: do not change repository discovery, Git status computation, or unrelated graph behavior. https://github.com/microsoft/vscode/issues/168820#issuecomment-1598508124 supports changes-only filtering, while https://github.com/microsoft/vscode/issues/33334#issuecomment-325602086 identifies live-layout instability as a UX concern. The unresolved part is which views the filter affects and whether it preserves manual selection independently of temporary visibility.
- **Open decisions:**
  - Should changes-only filtering affect the Changes view alone, or both the Changes and Source Control Repositories views?
  - Should the filter narrow the manually selected repositories, or temporarily show every changed repository while preserving the prior selection for restoration?
