# Issue #339878 — Sandboxing breaks the "share with an agent" feature

[https://github.com/microsoft/vscode/issues/339878](https://github.com/microsoft/vscode/issues/339878)

## Summary

Team-authored bug report (author is a VS Code member) describing a regression from sandboxing work in #339644; the code path matches the report exactly, so this stays open for a fix — no fixing commit exists yet.

## Change summary

When sandboxing is enabled, agents can no longer access a browser tab the user explicitly shared with them via 'Share with an Agent', because the openBrowserTool unconditionally rejects user-owned pages for sandboxed sessions.

## Best solution

Allow a sandboxed agent session to access a page the user explicitly shared (tracked via matchesBrowserViewSandboxSession/initialAudiences), rather than unconditionally requiring an isolated page — a maintainer should decide whether/how domain network restrictions still apply to that shared page.

- **Behavior:**

  > When a user shares an already-open browser tab with an agent (the 'Share with an Agent' flow) while sandboxing is enabled, the agent should be able to interact with that specific shared page, not be blocked by the generic sandbox rule requiring isolated pages. Pages the user has NOT shared must remain inaccessible/isolated as today. Acceptance: opening/using a user-shared page from a sandboxed agent session succeeds; unshared pages still get the isolated-page error.
- **Trace:**

  > openBrowserTool.ts's prepareToolInvocation/invoke paths check only `context.sandboxNetworkRestrictions?.sandboxEnabled` and unconditionally reject attaching to a user-owned page (lines ~88, ~124-127), never checking matchesBrowserViewSandboxSession/owner.initialAudiences the way screenshotBrowserTool.ts and browserViewWorkbenchService.ts already do elsewhere in this directory. The boundary: don't weaken the sandbox rule for non-shared pages, and don't change the isolated-page-creation path (_openNewPage) used when no page is shared. Open question for a maintainer: once access is allowed, should the existing allowedDomains/deniedDomains network filter still apply to the shared page, or does explicit user sharing bypass it entirely? Reported by connor4312 (VS Code team) against the sandboxing work in #339644; URL: https://github.com/microsoft/vscode/issues/339878.
- **Open decisions:**
  - Should domain-based network restrictions (allowedDomains/deniedDomains) still be enforced against a page the user explicitly shared with the agent, or does explicit sharing override the sandbox's network policy for that page?
  - Should this exception apply to all tool operations (screenshot, navigate, script execution) on the shared page, or only read-style operations?
