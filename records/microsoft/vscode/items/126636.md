# Issue #126636 — Workspace Trust - Restricted mode causes test failures

[https://github.com/microsoft/vscode/issues/126636](https://github.com/microsoft/vscode/issues/126636)

## Summary

The accepted backlog bug remains on current main: extension tests can disable Workspace Trust globally, but there is still no launch-scoped way to mark the tested workspace trusted. The existing workaround therefore cannot exercise trust-dependent extensions under realistic trusted-workspace behavior.

## Change summary

Allow extension integration tests to launch a specific workspace as trusted without changing persistent user or machine settings or disabling Workspace Trust globally.

## Best solution

Provide an explicit, launch-scoped test-host mechanism for trusting the opened workspace while retaining normal Workspace Trust enforcement elsewhere. Its persistence and URI-boundary semantics should be settled with the workspace-trust owners before implementation.

## Plan brief

- **Likely files:** `src/vs/platform/environment/common/argv.ts`, `src/vs/platform/environment/node/argv.ts`, `src/vs/workbench/services/workspaces/common/workspaceTrust.ts`, `src/vs/workbench/services/workspaces/test/common/workspaceTrust.test.ts`
- **Validation:** Add an extension-host integration scenario that launches a fresh test profile with the designated workspace trusted, asserts `vscode.workspace.isTrusted` is true and a trust-restricted test extension activates, then verifies an otherwise equivalent launch without that designation remains restricted.
- **Behavior:**

  > Extension integration tests must be able to launch a designated folder or workspace in trusted mode without editing persistent user or machine settings and without disabling Workspace Trust globally. Trust-restricted extensions should activate in that designated test workspace, while ordinary untrusted launches must remain restricted. The mechanism must be suitable for temporary CI agents and must not broaden trust outside the explicitly selected test workspace.
- **Trace:**

  > Current argument registration in src/vs/platform/environment/node/argv.ts provides only the global `--disable-workspace-trust` switch alongside extension test arguments. WorkspaceTrustEnablementService and WorkspaceTrustManagementService in src/vs/workbench/services/workspaces/common/workspaceTrust.ts have no launch-scoped trusted URI input; trust is instead disabled globally or calculated from stored URI trust. ExtensionEnablementService then uses that result to disable extensions that do not support untrusted workspaces. The existing workaround is documented at https://github.com/microsoft/vscode/issues/126636#issuecomment-878926700, while https://github.com/microsoft/vscode/issues/124182 is related but covers different Extension Development Host transition behavior. Preserve normal production trust calculation, persistent trust records, and untrusted test coverage; the uncertainty begins at the lifetime and URI scope of an explicit test-launch trust grant.
- **Open decisions:**
  - Should a test-launch trust grant be strictly process-scoped, or may it update the temporary profile's trusted-URI storage for the lifetime of that test profile?
  - Should designating a workspace trust only its exact roots and workspace file, or use the normal trusted-folder descendant semantics?

## Evidence

- **current source:** src/vs/workbench/services/workspaces/common/workspaceTrust.ts still computes trust from persisted trusted URIs through WorkspaceTrustManagementService; WorkspaceTrustEnablementService only recognizes the global `disableWorkspaceTrust` switch and has no extension-test-specific trusted-workspace input.
- **current CLI:** src/vs/platform/environment/node/argv.ts exposes `--disable-workspace-trust`, `extensionDevelopmentPath`, and `extensionTestsPath`, but no argument for temporarily trusting a specific test folder or workspace.
- **failure path:** src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts consults IWorkspaceTrustManagementService when deciding whether an extension that does not support untrusted workspaces can run, so a fresh test profile opening an untrusted folder still reaches the reported disabled-extension path.
