# Issue #336955 — Agents Window session status stays stale after continuing from another client

[https://github.com/microsoft/vscode/issues/336955](https://github.com/microsoft/vscode/issues/336955)

## Summary

Confirmed on current main: for a hydrated multi-chat session, the parent row derives status from `mainChat.status` (which prefers `_defaultChatStatusOverride`), and that override is only refreshed from a full state subscription — so an aggregate `sessionSummaryChanged` update lands in `cached.status` but never reaches the stale override until the session is reopened.

## Change summary

Agents Window rows for multi-chat sessions keep showing a stale per-chat status after a remote client changes the session's aggregate status, until the row is opened/focused locally.

## Best solution

Add a freshness signal for `_defaultChatStatusOverride` (set stale when the full state subscription is released, cleared on rehydration) and have the row-status derivation in sessionsList.ts fall back to aggregate `session.status` while stale, per the reporter's own suggested direction.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`, `src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts`
- **Validation:** Extend localAgentHostSessionsProvider.test.ts: hydrate a multi-chat session, release its state subscription, fire `fireSessionSummaryChanged(..., { status: InProgress })`, and assert the row/session status reflects InProgress without reopening the session.
- **Behavior:**

  > When a session's aggregate status changes via `root/sessionSummaryChanged` while its full per-chat state subscription is not live (e.g., continued from another client), the Agents Window row must immediately reflect the new aggregate status. Once the session is reopened/focused and per-chat state rehydrates, the existing main-chat/visible-child precedence resumes. Acceptance: a test that hydrates a multi-chat session, drops its subscription, fires an aggregate InProgress summary change, and asserts the row shows InProgress before reopening.
- **Trace:**

  > Root cause: `defaultChatStatus` in baseAgentHostSessionsProvider.ts prefers `_defaultChatStatusOverride` over `this.status` (aggregate); `_handleSessionSummaryChanged` only updates `this.status`, never the override, and the override is only refreshed via `_applyChatCatalog` from a live full-state subscription (gated by `_syncVisibleSessionStatePins`/`_ensureSessionStateSubscription`, ~L5484-5519). sessionsList.ts's `getSessionRowStatus` (deriveFromMainChat=true) reads `session.mainChat.status`, which carries the stale override. Confirmed by reading the code (no execution). Boundary: do not change precedence once state is fresh/hydrated — only the stale-state fallback path should change; don't touch single-chat sessions (survivingPeers.size === 0 already clears the override). Related prior refinements: #332931, #333999, #336445, #336613 (cited by the reporter) narrowed precedence but did not address staleness while unsubscribed.
- **Open decisions:**
  - Where should the 'per-chat state is stale/not authoritative' signal live — a new observable on the session/chat model, or an internal-only flag inside the provider — and should it be part of the public ISession/IChat contract?
  - When per-chat state is stale, should the row show the raw aggregate status verbatim, or a bounded interpretation (e.g. only escalate to InProgress, not other statuses) to avoid misattributing a peer chat's activity to the main chat?

## Evidence

- **override precedence:** src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts: `defaultChatStatus = derived(reader => this._defaultChatStatusOverride.read(reader) ?? this.status.read(reader))`, and `_applyChatCatalog` only sets `_defaultChatStatusOverride` from `state.chats` snapshots, which requires a live full subscription.
- **aggregate update path:** `_handleSessionSummaryChanged` (baseAgentHostSessionsProvider.ts ~L1188-1240) updates only `cached.status` (the aggregate), never `_defaultChatStatusOverride`.

- **subscription pinning:** `_syncVisibleSessionStatePins` (baseAgentHostSessionsProvider.ts ~L5484-5519) only pins full subscriptions for visible/open sessions, matching the reporter's claim that sidebar rows aren't kept live.
