# Issue #336955 — Agents Window session status stays stale after continuing from another client

[https://github.com/microsoft/vscode/issues/336955](https://github.com/microsoft/vscode/issues/336955)

## Summary

Confirmed on current main: `getSessionRowStatus` in sessionsList.ts returns a stale cached `mainChatStatus` whenever it is `InProgress` or `NeedsInput`, before ever considering a freshly-updated aggregate `session.status` — matching the reporter's trace exactly. This has a real milestone (1.140.0) assigned, so it stays open regardless; the fix needs design input on how to track per-chat freshness.

## Change summary

A multi-chat Agents Window session row keeps showing its stale cached main-chat status after the session is continued remotely, until the row is opened/focused locally.

## Best solution

Add a freshness signal for per-chat state (e.g. whether a live full-state subscription is currently held) and have `getSessionRowStatus` (sessionsList.ts) fall back to aggregate `session.status` when the cached main-chat status is stale, per the reporter's suggested direction; needs a maintainer's sign-off on how that freshness bit is represented/exposed since it likely touches the `ISession`/chat status contract in baseAgentHostSessionsProvider.ts as well.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts`, `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`
- **Validation:** Hydrate a multi-chat session, release its full session-state subscription, emit `SessionSummaryChanged(InProgress)`, and assert the parent row status becomes In Progress before the session is reopened (per the issue's suggested regression coverage).
- **Behavior:**

  > When a session's per-chat status cache is not currently being kept fresh (no live full-state subscription), the parent row in the Agents Window/sessions list must reflect the authoritative aggregate `session.status` the moment it changes, rather than a stale cached main-chat status. Once the session is opened/focused and per-chat state is hydrated again, the existing main-chat/visible-child precedence should resume. Acceptance: the suggested regression test (hydrate → release subscription → emit `SessionSummaryChanged(InProgress)` → row shows In Progress without reopening) passes, and existing sessionsList/baseAgentHostSessionsProvider tests still pass.
- **Trace:**

  > `getSessionRowStatus` (src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:224-237) prefers `mainChatStatus` over aggregate `sessionStatus` whenever `mainChatStatus` is `InProgress` or `NeedsInput`, with no check of whether that cached main-chat status is still fresh. `mainChatStatus` derives from `_defaultChatStatusOverride` (src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:1283, 1498), which is only refreshed by a full per-chat catalog subscription — held only for visible/open Agents grid rows (baseAgentHostSessionsProvider.ts:5484-5519 in the reporter's cited commit), not background sidebar rows. Do not change how aggregate status itself is computed, and do not blindly prefer aggregate over main-chat status once hydrated (the reporter notes aggregate activity can come from a peer chat) — the boundary is adding a freshness check before the existing precedence applies. Where uncertainty starts: how 'freshness' of per-chat state should be tracked and exposed (a boolean subscription-active flag vs. a staleness timestamp), and whether it belongs on `ISession`/`IChat` or purely inside the sessions-list presentation layer.
- **Open decisions:**
  - How should 'per-chat state is currently fresh/live' be represented and exposed — a flag on the session/chat model, or computed only in the sessions-list view layer?
  - Should the aggregate-status fallback apply the moment the subscription is released, or only once a fresher SessionSummaryChanged notification has actually arrived while unsubscribed?
