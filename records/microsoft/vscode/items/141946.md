# Issue #141946 — Extra parameter for TextEditorEdit.insert to specify not moving a selection position that's at the insertion position

[https://github.com/microsoft/vscode/issues/141946](https://github.com/microsoft/vscode/issues/141946)

## Summary

The requested insertion-boundary control remains absent from the current API. Keep this accepted Backlog request open: the documented workarounds do not cover the edit-builder workflow, and no verified open canonical owns the same request.

## Change summary

Allow TextEditorEdit.insert to preserve selection endpoints exactly at the insertion position while continuing to shift endpoints after it.

## Best solution

Consider an opt-in edit-builder API contract for insertion-boundary selection behavior, preserving existing behavior by default and applying the requested selection mapping within the edit transaction.

## Evidence

- **Current public API:** src/vscode-dts/vscode.d.ts:1400–1418 declares only insert(location: Position, value: string), with no selection-affinity option; its documentation explicitly says insertion moves the resulting selection.
- **Current implementation:** src/vs/workbench/api/common/extHostTextEditor.ts:87–104 passes forceMoveMarkers=false for replace and hardcodes true for insert. src/vs/workbench/api/browser/mainThreadEditor.ts:479–506 forwards those edits to executeEdits without an explicit final-selection argument.
- **Existing capabilities are partial workarounds:** In https://github.com/microsoft/vscode/issues/141946, jrieken acknowledges the capability is unsupported and suggests insertSnippet('$0some text', position) or resetting the selection after editor.edit. The reporter explains that post-edit resetting can race with typing and that the command uses the supplied registerTextEditorCommand edit builder. The current insertSnippet API is a separate snippet operation, not an option on that builder.
