# Issue #259109 — Jump to line

[https://github.com/microsoft/vscode/issues/259109](https://github.com/microsoft/vscode/issues/259109)

## Summary

A real gap remains: chat code-block toolbars offer copy, apply, and insert actions, but no action that opens the originating workspace location. Keep the request open for a product decision about how source provenance and exact ranges should be represented.

## Change summary

Add a chat code-block action that opens the workspace file and line range from which the displayed snippet originated.

## Best solution

When a chat code block carries trustworthy workspace provenance, expose a keyboard-accessible Open Source Location action that opens the file at the exact range; do not guess when the snippet lacks an unambiguous source.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/widget/annotations.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatCodeblockActions.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/codeBlockPart.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatMarkdownContentPart.ts`, `src/vs/workbench/contrib/chat/browser/actions/chatAccessibilityHelp.ts`, `src/vs/workbench/contrib/chat/test/browser/widget/chatContentParts/chatMarkdownContentPart.test.ts`
- **Validation:** Add targeted chat markdown/code-block tests proving that a block with explicit URI-and-range provenance exposes an action that opens the editor at that range, while a block without trustworthy provenance exposes no such action; verify keyboard and accessible-view invocation as well.
- **Behavior:**

  > A chat response code block associated with an exact workspace source location offers an Open Source Location action beside its existing actions. Invoking it opens the source file and reveals the originating range in Ask, Edit, and Agent sessions. Blocks without trustworthy source provenance must not navigate to a guessed match, and the action must be keyboard and screen-reader accessible.
- **Trace:**

  > Code-block actions are registered against MenuId.ChatCodeBlock in src/vs/workbench/contrib/chat/browser/actions/chatCodeblockActions.ts, and their context is assembled by CodeBlockPart in src/vs/workbench/contrib/chat/browser/widget/chatContentParts/codeBlockPart.ts. ChatMarkdownContentPart extracts `<vscode_codeblock_uri>` metadata, but extractCodeblockUrisFromText in src/vs/workbench/contrib/chat/common/widget/annotations.ts currently returns only a URI and flags, not a source range. Inline references elsewhere in ChatMarkdownContentPart already demonstrate opening an editor with location options. Preserve Apply in Editor and Insert at Cursor semantics, avoid text-search guessing, and update the existing chat accessibility help if a new code-block action is introduced.
- **Open decisions:**
  - Should source navigation appear only when the response carries explicit URI-and-range provenance, or may VS Code search for a matching snippet when exact provenance is absent?
  - When provenance identifies a file but not an exact range, should the action open the file without a selection or remain hidden?

## Evidence

- **current toolbar:** src/vs/workbench/contrib/chat/browser/actions/chatCodeblockActions.ts registers Copy, Apply in Editor, Insert at Cursor, and Insert into New File for MenuId.ChatCodeBlock, but no source-navigation action.
- **provenance limitation:** src/vs/workbench/contrib/chat/common/widget/annotations.ts represents a code block's source annotation as a URI through `codeblockUri`/`extractCodeblockUrisFromText`; the annotation contains no source range, so it cannot currently identify the requested exact line.
- **existing partial capability:** src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatMarkdownContentPart.ts already opens explicit inline references with editor options, but that behavior is separate from rendered code-block toolbar actions and does not cover an otherwise unlinked snippet.
- **canonical search:** Repository searches for chat code-block source navigation and jump-to-line requests found no older open issue with the same reporter-observable request; https://github.com/microsoft/vscode/issues/211516 concerns relative Ctrl+G navigation and does not own this work.
- **maintainer clarification:** The reporter confirmed in https://github.com/microsoft/vscode/issues/259109#issuecomment-2767301994 that the requested control belongs beside Apply in Editor and Insert at Cursor.
