# Issue #179146 — VSCode extension API's - some cases when "explorer/context" does not solve "resource" correctly in "when" clause

[https://github.com/microsoft/vscode/issues/179146](https://github.com/microsoft/vscode/issues/179146)

## Summary

The defect remains source-reproducible on current main: separate menu surfaces share resource context keys, while each `ResourceContextKey` instance suppresses updates based only on its own cached URI. The Explorer can therefore evaluate `resourceExtname` from the Settings editor instead of the file being right-clicked.

## Change summary

Resource-dependent extension menu entries can disappear when another workbench surface changes the shared resource context before the menu opens.

## Best solution

Ensure opening a resource-targeted menu republishes or scopes all resource context keys to that menu's target, even when the owning `ResourceContextKey` instance previously saw the same URI. Cover the cross-surface overwrite sequence in the Explorer context-menu tests without changing normal menu targeting or selection behavior.

- **Behavior:**

  > An extension command contributed to `explorer/context` with `resourceExtname == .xml` remains visible whenever an XML file is right-clicked, regardless of whether Settings or another editor/menu surface was focused immediately beforehand. Resource keys used to evaluate the menu must describe the clicked resource, not the previously active surface. Existing selection, compressed-folder targeting, background-menu, and keyboard context-menu behavior must remain unchanged.
- **Trace:**

  > `ExplorerView.onContextMenu` in src/vs/workbench/contrib/files/browser/views/explorerView.ts invokes `setContextKeys(stat)` and evaluates the menu through `this.tree.contextKeyService`. `ExplorerView.setContextKeys` delegates resource values to `ResourceContextKey.set`, whose implementation in src/vs/workbench/common/contextkeys.ts skips all writes when that instance's cached URI is unchanged. Because editor groups, editor tabs, Open Editors, and Explorer create distinct `ResourceContextKey` instances over shared/inherited context keys, another surface can replace `resourceExtname` while the Explorer instance still caches the XML URI; the next Explorer call then returns early and leaves the wrong key visible to the menu. The context-menu suite in src/vs/workbench/contrib/files/test/browser/explorerView.test.ts already supplies the relevant event and delegate harness. Keep the boundary to resource-key synchronization and menu context; do not alter command arguments, Explorer selection semantics, or unrelated when-clause parsing.

## Evidence

- **source reproduction:** `ExplorerView.onContextMenu` in src/vs/workbench/contrib/files/browser/views/explorerView.ts calls `setContextKeys(stat)` before showing `MenuId.ExplorerContext`, but its `ResourceContextKey` is backed by the shared injected context-key service.
- **root cause:** `AbstractResourceContextKey.set` in src/vs/workbench/common/contextkeys.ts returns immediately when its private cached `_value` equals the requested URI. Another `ResourceContextKey` instance can meanwhile overwrite the same `resourceExtname` key, so the Explorer instance does not restore `.xml` when the same file is right-clicked again.
- **independent confirmation:** https://github.com/microsoft/vscode/issues/179146#issuecomment-2029837071 reports the same resource-conditioned command disappearing after moving between editor content and editor-title context menus.
- **existing test surface:** src/vs/workbench/contrib/files/test/browser/explorerView.test.ts already drives Explorer mouse and keyboard context menus and captures the context-menu delegate, providing a bounded regression-test location.
- **canonical search:** Repository searches found no older open issue with the same observable cross-surface `resourceExtname` disappearance; https://github.com/microsoft/vscode/issues/204074 is newer and concerns multi-diff resource context rather than this symptom.
