# Issue #338040 — Copilot telemetry messages are truncated or lack structured content classification

[https://github.com/microsoft/vscode/issues/338040](https://github.com/microsoft/vscode/issues/338040)

## Summary

Legitimate telemetry data-quality request, but it mixes two things at different maturity: message truncation is already partly handled by an existing chunking/compression mechanism on main, while structured content-type classification for provider-specific message shapes (thinking/redacted_thinking/reasoning_text, malformed summary JSON) is a genuine, unaddressed gap that needs schema design input from the telemetry owners.

## Change summary

Copilot Chat/agent telemetry events (`engine.messages`, `conversation.messageText`, etc.) sometimes truncate message payloads and lack structured metadata distinguishing answer/summary/thinking/redacted content, with some summary-like JSON malformed.

## Best solution

Confirm whether truncation still occurs given the existing chunked/compressed property mechanism in extensions/copilot/src/platform/telemetry/common/telemetry.ts; separately, have the telemetry/prompt owners define a normalized content-type taxonomy (answer/summary/context/thinking/redacted) applied when serializing `messagesJson`/`message_text`, ensuring any embedded JSON is validated before emission.

## Plan brief

- **Likely files:** `extensions/copilot/src/platform/networking/node/chatStream.ts`, `extensions/copilot/src/platform/telemetry/common/telemetry.ts`, `extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts`
- **Validation:** A telemetry unit test asserting that serialized message content always carries a defined type/classification field and that any nested JSON payload parses successfully.
- **Behavior:**

  > Every assistant message emitted in telemetry (`messages_json`, `message_text` fields) should carry structured metadata identifying its content purpose (answer/summary/context/thinking/redacted), and any JSON embedded in a content string must be valid, parseable JSON. Large payloads should not silently truncate raw content; the existing chunk/compress mechanism should cover this, or be extended to any field that still lacks it.
- **Trace:**

  > messagesJson is built via `JSON.stringify(messages)`/`JSON.stringify(messagesWithLength)` in extensions/copilot/src/platform/networking/node/chatStream.ts (lines 94, 456), passing through whatever shape the model/provider produced without classification or JSON-validation. Truncation for oversized values is already mitigated for `messagesJson`/`diffsJSON`/`prompt` via the compressed-chunk mechanism in multiplexProperties (extensions/copilot/src/platform/telemetry/common/telemetry.ts:212-305); it's unclear whether `message_text` fields on `conversation.messageText`/`inlineConversation.messageText` go through the same path and whether any producer-side JSON validation exists before values are stringified. Boundary: do not change the chunk/compression wire format or column naming (`ALWAYS_COMPRESSED_CHUNK_KEYS`, `COMPRESSED_CHUNK_KEY_OVERRIDES`) without downstream analytics sign-off, since those names are contractual with the backend.
- **Open decisions:**
  - What normalized content-type taxonomy should be used across differing provider message shapes (thinking, redacted_thinking, reasoning_text, plain summary strings)?
  - Should malformed embedded JSON be repaired, dropped, or flagged, and who validates that decision with the analytics/backend consumers?
  - Does truncation still occur in practice given the existing chunk/compress mechanism, or is this report describing a downstream reconstruction gap rather than a producer-side one?

## Evidence

- **chunking already exists:** extensions/copilot/src/platform/telemetry/common/telemetry.ts:212-305 (`multiplexProperties`) already splits/gzip-compresses any property over 8192 chars into `<key>Chunk`/`<key>Chunk_2`... families, and `messagesJson` is in `ALWAYS_COMPRESSED_CHUNK_KEYS` so it is always emitted via the chunk family — this addresses at least part of the described truncation.
- **no content-type normalization:** extensions/copilot/src/platform/networking/node/chatStream.ts:94/456 build `messagesJson: JSON.stringify(messages)` (or `messagesWithLength`) by directly serializing whatever message shape the underlying provider returned, with no classification/normalization step or JSON-validity check — matches the reporter's issue 2 example of unclassified/malformed content.
- **related but distinct issue:** https://github.com/microsoft/vscode/issues/299952 asks to make JSON truncation *configurable*, a different ask than adding content-type classification and fixing malformed JSON; not a canonical for this report.
