# Issue #225483 — Debug view per debug session

[https://github.com/microsoft/vscode/issues/225483](https://github.com/microsoft/vscode/issues/225483)

## Summary

Keep open: built-in Variables and Watch views still follow the shared active debug context rather than supporting independent session-bound comparisons. This accepted Backlog request has 28 upvotes and maintainer interest; the verified related issues do not cover its full scope.

## Change summary

Allow concurrent, session-bound debug views so developers can compare variables and inspect multiple debug targets without switching every view together.

## Best solution

Design a coherent session-bound debug workspace that allows simultaneous inspection of multiple sessions while preserving the existing single-session experience. Resolve the proposed auxiliary-window approach versus independently pinned views with the debug maintainers before implementation.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`, `src/vs/workbench/contrib/debug/browser/variablesView.ts`, `src/vs/workbench/contrib/debug/browser/watchExpressionsView.ts`, `src/vs/workbench/contrib/debug/browser/callStackView.ts`, `src/vs/workbench/contrib/debug/browser/repl.ts`, `src/vs/workbench/contrib/debug/common/debugViewModel.ts`
- **Validation:** Launch two debug sessions with distinguishable variable values and pause both. Display their debug contexts simultaneously, switch the globally active session, and verify that each session-bound surface retains its own variables, watch evaluations, stack selection, and correctly targeted controls. Resume and end one session to verify that the other remains usable; confirm that single-session debugging retains its existing behavior.
- **Behavior:**

  > Developers debugging concurrent targets need to inspect and compare each target's debug information simultaneously. A session-bound surface must retain its session identity when another session becomes globally active, and its displayed data and actions must address the intended target. Acceptance must include two paused sessions with different variable values, independent inspection while switching global focus, and predictable behavior when one target resumes or ends. The existing single-session workflow must remain unchanged.
- **Trace:**

  > VariablesView in src/vs/workbench/contrib/debug/browser/variablesView.ts takes its tree input from the shared focusedStackFrame and updates on global frame focus changes; WatchExpressionsView also refreshes against that shared context. ViewModel in src/vs/workbench/contrib/debug/common/debugViewModel.ts stores one focused session and frame, while debug.contribution.ts registers one instance of each standard debug view. This establishes why merely relocating existing views does not provide independent comparisons, but it does not settle the architecture for separate contexts. The maintainer discussion at https://github.com/microsoft/vscode/issues/225483#issuecomment-2286710923 favors an auxiliary session-bound debug surface without accepting the reporter's per-view dropdown design. https://github.com/microsoft/vscode/issues/201772 is related console-editor work, not coverage of the whole request. Preserve ordinary active-session switching and single-session behavior; treat the reporter's disassembly discussion as separate scope. Planning must establish the chosen surface and trace all context-sensitive evaluations and controls before implementation.
- **Open decisions:**
  - Should independent debug contexts appear as complete session-bound auxiliary windows, independently pinned views in the main window, or another session-container surface?
  - Should a session-bound surface follow that session's selected stack frame, or allow its own frame selection independently of the main debug workspace?
