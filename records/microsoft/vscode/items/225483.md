# Issue #225483 — Debug view per debug session

[https://github.com/microsoft/vscode/issues/225483](https://github.com/microsoft/vscode/issues/225483)

## Summary

Keep open in the Backlog: 27 community upvotes and positive maintainer interest establish demand, while current main still exposes one globally focused debug session to the built-in views. The remaining work requires a UX decision between a session-bound auxiliary debug surface and duplicated in-workbench views.

## Change summary

Allow developers running concurrent debug sessions to display and compare built-in debug information for more than one session at a time.

## Best solution

Provide a clearly session-bound debug surface that can remain visible alongside another session's surface, while preserving the lightweight existing experience when only one session is active. The design should cover the relevant views as a coherent unit and make session identity and lifecycle explicit.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/debug/common/debugViewModel.ts`, `src/vs/workbench/contrib/debug/browser/debugViewlet.ts`, `src/vs/workbench/contrib/debug/browser/debug.contribution.ts`, `src/vs/workbench/contrib/debug/browser/callStackView.ts`, `src/vs/workbench/contrib/debug/browser/variablesView.ts`, `src/vs/workbench/contrib/debug/browser/repl.ts`, `src/vs/workbench/common/views.ts`, `src/vs/workbench/services/views/browser/viewDescriptorService.ts`
- **Validation:** End the plan with debug-view tests proving that two concurrently running sessions can retain independent selected stack frames and displayed variables, plus a manual compound-debug scenario verifying simultaneous surfaces, clear session identity, and unchanged single-session behavior.
- **Behavior:**

  > When two or more debug sessions run concurrently, a developer can keep built-in debug information for one session visible while inspecting another session. Each visible surface clearly identifies its session and keeps its displayed Call Stack, Variables, controls, and applicable console state associated with that session rather than following every global focus change. Ending a session leaves no misleading stale surface. With one session, the existing Run and Debug experience remains unchanged.
- **Trace:**

  > ViewModel in src/vs/workbench/contrib/debug/common/debugViewModel.ts owns a single focused session, thread, and stack frame. VariablesView in src/vs/workbench/contrib/debug/browser/variablesView.ts reads that global focused stack frame, while CallStackView selections call IDebugService.focusStackFrame and therefore update the shared state. The built-in views are registered once under fixed IDs in src/vs/workbench/contrib/debug/browser/debug.contribution.ts, and ViewContainerLocation has no auxiliary-window location. The existing Debug Console has some per-session selection logic in src/vs/workbench/contrib/debug/browser/repl.ts, but remains a single registered view. The boundary is the concurrent-session presentation: preserve current single-session behavior, existing debug-adapter contracts, and unrelated generic view movement. Related work at https://github.com/microsoft/vscode/issues/201772 may supply an editor/auxiliary-window pattern, but it does not settle how a complete session-bound debug surface should behave.
- **Open decisions:**
  - Should each session-bound surface be a complete auxiliary debug window, or should users be able to duplicate session-bound view containers inside the main workbench?
  - Which built-in elements form the session-bound unit: Call Stack and Variables only, or also Watch, Debug Console, and the debug toolbar?
  - Should a pinned surface persist across reloads or session restarts, or exist only for the lifetime of the selected debug session?
