# Issue #324662 — Copilot Chat history item silently fails to load when chatSessions JSONL is missing but session-store.db has transcript

[https://github.com/microsoft/vscode/issues/324662](https://github.com/microsoft/vscode/issues/324662)

## Summary

Current main still has the silent failure path: a history entry can remain indexed after both session payload files disappear, and opening it falls back to a new empty session without reporting the missing transcript. This team-authored report should remain open while recovery and stale-entry semantics are decided.

## Change summary

Handle indexed Copilot Chat sessions whose workspace JSON/JSONL payload is missing instead of silently opening an empty session despite recoverable Chronicle data.

## Best solution

Detect the missing indexed payload and provide an explicit recoverable state rather than silently replacing it with a new session. At minimum, surface a localized error and let the user remove the stale entry; use `session-store.db` recovery only if core and the Copilot extension can define a supported, lossless reconstruction contract.

- **Behavior:**

  > Selecting a non-empty Chat history entry whose workspace payload is missing must not silently open or substitute an empty session. The user must either receive the recovered transcript or a clear localized explanation with the maintainer-selected cleanup/recovery affordance. Existing valid JSONL and legacy JSON sessions must continue loading unchanged. Acceptance includes a regression case with retained metadata, absent payload files, and available Chronicle rows.
- **Trace:**

  > `ChatSessionStore.getIndex` supplies the visible history metadata independently of the payload file. In `readSessionFromLocation`, missing JSONL and legacy JSON files are logged and converted to `undefined`; `ChatService.acquireOrRestoreLocalSession` returns that value without distinguishing an indexed-but-missing session from an unknown ID. `ChatViewPane.loadSession` then calls `showModel` with no model reference, and `showModel` creates a fresh local session, bypassing the existing `chat.loadSessionFailed` notification because no exception was raised. The Copilot extension's Chronicle `SessionStoreTracker` writes a separate SQLite transcript store, but current core session restoration does not consume it. Preserve valid-session loading, cancellation behavior, and the separation between core and extension storage; the uncertainty begins at the desired recovery contract.
- **Open decisions:**
  - When an indexed session payload is missing, should VS Code attempt reconstruction from the Copilot Chronicle store, or treat that store as non-authoritative and show a recovery error?
  - If automatic reconstruction is unavailable or fails, should the stale history item remain available with an explicit remove action, or be pruned after the user is informed?
