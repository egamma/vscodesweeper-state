# Issue #338102 — Archiving a chat deletes a worktree still used by another chat

[https://github.com/microsoft/vscode/issues/338102](https://github.com/microsoft/vscode/issues/338102)

## Summary

Confirmed in source: the worktree cleanup path run on archive never checks whether another session/chat still references the same worktree before deleting it, matching the reported symptom exactly. Real gap, worth fixing, but the fix requires a product decision on how to handle the dependent session (block, warn, or cascade-archive), so it needs planning before implementation.

## Change summary

Archiving a chat whose session owns a git worktree deletes that worktree even when a second chat/session still points at the same working directory, leaving the second chat permanently broken with SessionWorkingDirectoryMissingError.

## Best solution

Before removing a worktree on archive, check whether any other non-archived session/chat metadata still references the same worktreePath, and either skip/defer deletion with a warning, or cascade the archive to dependent sessions — the exact behavior needs a maintainer decision (the issue itself proposes both options).

- **Likely files:** `src/vs/platform/agentHost/node/shared/worktreeIsolation.ts`, `extensions/copilot/src/extension/chatSessions/vscode-node/chatSessionWorktreeServiceImpl.ts`
- **Validation:** A test that creates two sessions sharing one worktreePath, archives one, and asserts the worktree is not removed (or that the second session is also archived/warned, per the chosen design) rather than left pointing at a deleted directory.
- **Trace:**

  > `_cleanupWorktreeOnArchive` in worktreeIsolation.ts reads only the archiving session's own metadata before force-removing the worktree directory; the chatSessionWorktreeServiceImpl.ts mirror has the same gap. Neither queries other sessions' stored worktree metadata to detect shared ownership. Established so far: the deletion path itself and that it is unconditional; not yet decided: which service enumerates/queries sibling sessions for a shared worktreePath, and what the user-facing behavior should be when one is found.
- **Open decisions:**
  - When another non-archived session still references the worktree, should archiving be blocked/deferred (keep the worktree, leave the archiving session orphaned from its directory) or should it cascade-archive the dependent session(s) with a warning, as the issue proposes?
  - If blocked, what warning/confirmation UI does the user see at archive time, and can they override it?
  - Does this check need to span across repositories/windows (multi-root, remote) or only sessions known to the local session store?
