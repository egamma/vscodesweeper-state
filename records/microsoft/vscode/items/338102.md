# Issue #338102 — Archiving a chat deletes a worktree still used by another chat

[https://github.com/microsoft/vscode/issues/338102](https://github.com/microsoft/vscode/issues/338102)

## Summary

Team-authored bug report (author is a repo MEMBER) describing worktree deletion on archive with no cross-chat/session reference check — the hard keep-open rule for team-authored issues applies regardless, and the trace confirms the underlying gap, so this stays open for design and a fix.

## Change summary

Archiving one chat force-deletes a worktree that a second, non-archived chat still depends on, leaving that chat permanently broken with SessionWorkingDirectoryMissingError.

## Best solution

Decide the intended contract (per the reporter's two proposals) and enforce it in src/vs/platform/agentHost/node/shared/worktreeIsolation.ts — either track cross-session/cross-chat references to a worktree path before `_cleanupWorktreeOnArchive`/`removeWorktree` run, or cascade-archive all chats/sessions sharing that worktree with an explicit warning.

## Plan brief

- **Likely files:** `src/vs/platform/agentHost/node/shared/worktreeIsolation.ts`, `src/vs/platform/agentHost/node/agentService.ts`
- **Validation:** A worktreeIsolation test creating two chats/sessions bound to the same worktree path, archiving one, and asserting the worktree either survives (if the other still needs it) or the dependent chat is cleanly archived alongside it — whichever contract is chosen.
- **Behavior:**

  > When a worktree is still referenced by a non-archived chat or session, archiving a different chat/session that shares the same worktree must not silently delete it out from under the still-active one. Either (a) the deletion is skipped/deferred while another live reference exists, or (b) all chats/sessions sharing that worktree are archived together with a clear warning to the user. Acceptance: after archiving one of two chats sharing a worktree, the other chat remains usable (or is explicitly and visibly archived too) — it must never end up pointing at a deleted directory it wasn't told about.
- **Trace:**

  > `_cleanupWorktreeOnArchive` in src/vs/platform/agentHost/node/shared/worktreeIsolation.ts (around line 1189) resolves worktree metadata solely from the archiving session's own URI via `_readWorktreeMetadata`, then unconditionally force-removes the worktree with `this._gitService.removeWorktree(...)` once branch/sync checks pass — there is no lookup of `_materializedWorktrees` or any other session/chat catalog entry that might point at the same `worktreePath`/`repositoryRoot` before deletion, confirmed via `rg` across the file. Boundary: do not touch the existing branch-presence/sync/commit safety checks for the archiving session itself; the gap is specifically the missing cross-session/cross-chat reference check. Open question is which contract to implement, per the reporter's own two alternatives in the issue body.
- **Open decisions:**
  - Should worktree deletion on archive be blocked/deferred while another chat or session still references it, or should archiving cascade to all dependent chats/sessions with an explicit warning?
  - How should 'another chat still using the worktree' be detected — is it scoped to peer chats within the same Agent Host session catalog, or must it also cover an unrelated session/window that happens to point at the same on-disk worktree path?

## Evidence

- **no reference check:** `_cleanupWorktreeOnArchive` (src/vs/platform/agentHost/node/shared/worktreeIsolation.ts:1189-1233) reads worktree metadata keyed only by the archiving session's own `sessionUri`/`sessionId`, checks branch presence and (for manual archive) commits+force-removes the worktree via `this._gitService.removeWorktree(repositoryRoot, worktreePath, { force: true })` — there is no scan across `_materializedWorktrees` or any other session/chat for a matching `worktreePath` before deletion.
- **error surfaced:** `SessionWorkingDirectoryMissingError` is thrown from src/vs/platform/agentHost/node/shared/worktreeIsolation.ts:1007/1022 when a session's working directory no longer exists on disk — consistent with the reporter's stack trace.
