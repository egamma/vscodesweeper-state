# Issue #64027 — Git - "Stage selected ranges" sometimes stages a revert of changes in the previous commit

[https://github.com/microsoft/vscode/issues/64027](https://github.com/microsoft/vscode/issues/64027)

## Summary

The stale-index staging path remains in current source, and an open PR explicitly addresses this report. Keep the issue open while that implementation is reviewed and verified.

## Change summary

Staging another selected range immediately after committing can also stage an unintended reversal of the preceding commit.

## Best solution

Review and land https://github.com/microsoft/vscode/pull/326397 if its fresh-base reads preserve range-staging behavior, encoding, and line endings. The resulting index must retain the preceding commit and contain only the newly selected changes.

- **Current source path:** extensions/git/src/commands.ts:1777–1809 routes git.stageSelectedRanges to _stageChanges. At lines 1948–1953, that method obtains the '~' Git base through workspace.openTextDocument, applies selected changes, and writes the resulting whole-file content to the index. extensions/git/src/staging.ts:35 and 55 preserve unselected content from that original document, so a stale pre-commit base reintroduces the old content outside the second selection.
- **Refresh timing:** extensions/git/src/fileSystemProvider.ts:61–109 schedules repository-change invalidation through @debounce(1100). Its readFile implementation at lines 197–231 reads repository content directly; the range command instead consumes the potentially cached TextDocument.
