# Issue #110218 — Allow extensions to contribute dynamic submenus

[https://github.com/microsoft/vscode/issues/110218](https://github.com/microsoft/vscode/issues/110218)

## Summary

Keep this accepted, well-supported API request open: current menu contributions still require predefined entries and titles, so runtime-generated submenu contents remain unsupported. The older related issues do not provide an open canonical covering this request.

## Change summary

Allow extensions to populate contributed submenus with runtime-generated items and titles rather than a fixed package.json inventory.

## Best solution

Design an extension-facing dynamic submenu contract that preserves fast, keyboard-accessible native menus and existing declarative contributions. Settle whether contents are supplied ahead of display or computed on demand, including the user-visible behavior while asynchronous results are pending.

## Plan brief

- **Likely files:** `src/vs/workbench/services/actions/common/menusExtensionPoint.ts`, `src/vs/platform/actions/common/menuService.ts`, `src/vs/workbench/api/browser/mainThreadCommands.ts`, `src/vs/workbench/api/common/extHostCommands.ts`, `src/vscode-dts/vscode.d.ts`, `src/vs/platform/actions/test/common/menuService.test.ts`
- **Validation:** Use a development extension that declares a submenu, then creates and renames items after activation. Open that submenu and verify the actual runtime names and commands appear without predeclared placeholders or a QuickPick; verify keyboard navigation and unchanged static menus. For an on-demand contract, exercise delayed results, dismissal, and provider failure. Add automated coverage for the chosen contract and affected menu-service behavior.
- **Behavior:**

  > Extensions need to display submenu choices whose number and names are unknown when package.json is authored. Runtime-created items must appear with their actual titles in the contributed submenu and invoke the corresponding commands, without requiring a separate picker. Existing static contributions and conditional visibility must retain their behavior. Acceptance includes creating and renaming choices after activation, opening the submenu, and selecting those choices with both mouse and keyboard.
- **Trace:**

  > In src/vs/workbench/services/actions/common/menusExtensionPoint.ts, submenusExtensionPoint and menusExtensionPoint consume manifest contributions and append predefined items to MenuRegistry; command references require declared contribution metadata. In src/vs/platform/actions/common/menuService.ts, createMenuActionGroups and createActionGroups synchronously read and filter registered entries, recursively constructing submenu actions. MainThreadCommands.$registerCommand in src/vs/workbench/api/browser/mainThreadCommands.ts registers executable handlers but does not contribute menu metadata, and the inspected stable/proposed declaration files expose no general dynamic submenu API. The remaining uncertainty is the public contract and menu interaction lifecycle, not whether when clauses already cover the request. Preserve static menu semantics and parent-menu responsiveness; general dynamic configuration contributions and breakpoint languages raised in the thread are outside this request. https://github.com/microsoft/vscode/issues/146184 was explicitly consolidated into this issue, while https://github.com/microsoft/vscode/issues/9827 completed static submenu support only.
- **Open decisions:**
  - Should extensions supply submenu contents ahead of display through runtime updates, compute them on demand through a provider, or support both contracts?
  - If on-demand computation is supported, when should it start, and what should users see while results are pending or computation fails?
  - Should dynamic contents be shared for the contributed submenu or vary with the specific context target, such as a TreeItem?

## Evidence

- **Existing capability and remaining gap:** src/vs/workbench/services/actions/common/menusExtensionPoint.ts:980–1170 registers submenus from manifest values, resolves menu commands through MenuRegistry.getCommand, rejects commands absent from the commands contribution, and attaches when expressions to predefined entries. Conditional visibility does not create runtime entries or titles.
- **Runtime boundary:** src/vs/workbench/api/browser/mainThreadCommands.ts:57–66 registers extension command handlers with CommandsRegistry, not menu entries. src/vs/platform/actions/common/menuService.ts:173–227 filters existing MenuRegistry entries and synchronously constructs submenu actions.
