# Issue #338626 — Placeholder text used as the only visible label for Search input field: A11y_VisualStudioCode_Labels or Instructions

[https://github.com/microsoft/vscode/issues/338626](https://github.com/microsoft/vscode/issues/338626)

## Summary

Confirmed on current main: QuickInputBox (src/vs/platform/quickinput/browser/quickInputBox.ts) constructs its FindInput with an empty visible `label: ''`, relying solely on placeholder text plus a screen-reader-only `aria-label` — matching the reported WCAG 3.3.2 gap. The prior related report (#336374) was closed by the same reporter explicitly in favor of this one, not as a duplicate to strand, so this stays the active tracking issue.

## Change summary

The quick access/search input (and other QuickInputBox-based fields) shows only placeholder text as its label, which disappears once the user types, leaving no persistent visible label for low-vision or cognitively-impaired users.

## Best solution

This needs an accessibility/UI design decision from the team (likely via the linked internal a11y triage process) on how to add a persistent visible label to the shared QuickInputBox widget without cluttering the compact quick-open UI used across command palette, go-to-file, symbol search, etc. — a change here is cross-cutting since many features share this one widget.

## Plan brief

- **Behavior:**

  > The quick input's search/filter field should show a persistent, visible text label (not just placeholder text or a hover tooltip) identifying its purpose, both before and after text entry. Placeholder text may remain as supplementary guidance. Acceptance: a visible label element exists and stays displayed regardless of input state, without needing hover or focus.
- **Trace:**

  > QuickInputBox wraps a base FindInput with an empty `label: ''` (src/vs/platform/quickinput/browser/quickInputBox.ts, constructor) and only ever manages `placeholder` and `aria-label` (screen-reader-only) via its setters — there is no visible label DOM node today. This widget backs many quick-open surfaces (command palette, go-to-symbol, go-to-file, etc.), so a change affects shared chrome, not one screen; the boundary is to preserve the compact, minimalist quick-open layout the project values while adding a persistent visible label. Where the uncertainty starts: whether the label sits inline above the input, as an adjacent element, or via some other compact affordance, and whether it applies uniformly to all QuickInputBox consumers or is opt-in per feature.
- **Open decisions:**
  - Where does the persistent visible label render relative to the compact quick-open box (inline, above, adjacent) without disrupting the existing minimalist layout?
  - Should this apply uniformly to every QuickInputBox consumer (command palette, go-to-file, go-to-symbol, etc.) or only specific ones like the search field called out in the report?
