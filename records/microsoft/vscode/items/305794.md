# Issue #305794 — agentPlugins with devcontainer story

[https://github.com/microsoft/vscode/issues/305794](https://github.com/microsoft/vscode/issues/305794)

## Summary

A real gap remains: current main can read workspace plugin recommendations, but it only prompts users to review them and does not declaratively install and enable plugins inside a dev container. The existing under-discussion and area labels correctly keep the product and trust model open for design.

## Change summary

Allow dev-container workspaces to declare agent plugin marketplaces and plugins that are provisioned inside the container without installing their dependencies on the host.

## Best solution

Define a trusted-workspace provisioning model that resolves, installs, and enables declared plugins in the remote container while leaving the host untouched, with a clear consent flow and layering rules for user-wide additional plugins.

## Plan brief

- **Likely files:** `src/vs/workbench/contrib/chat/common/plugins/workspacePluginSettingsService.ts`, `src/vs/workbench/contrib/chat/common/plugins/pluginMarketplaceService.ts`, `src/vs/workbench/contrib/chat/browser/claudePluginRecommendations.ts`, `src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts`, `src/vs/workbench/contrib/chat/test/common/plugins/workspacePluginSettingsService.test.ts`
- **Validation:** Add tests covering a trusted remote workspace declaration from discovery through the chosen consent/provisioning behavior, then manually open a dev container and verify that the plugin is usable there while no plugin files or dependencies are installed on the host.
- **Behavior:**

  > A dev-container workspace can declare its agent plugin marketplaces and required plugins. After the chosen trust or consent step, the plugins are available and enabled in that container, including plugin scripts and dependencies, without installing them on the host. User-configured additional plugins compose with the container declaration according to an explicit precedence rule. Reopening the container preserves the intended availability without unnecessary reinstalls.
- **Trace:**

  > Current main reads workspace `enabledPlugins` and `extraKnownMarketplaces` in src/vs/workbench/contrib/chat/common/plugins/workspacePluginSettingsService.ts. PluginMarketplaceService converts those entries into trusted-workspace recommendations, and AgentPluginRecommendations only displays a notification linking to `@agentPlugins @recommended`; installation remains user-driven. The application-scoped registrations in chat.shared.contribution.ts do not supply container-specific provisioning. The boundary is plugin provisioning and enablement for trusted remote workspaces: do not change unrelated extension installation semantics or allow container declarations to silently modify the host. The older https://github.com/microsoft/vscode/issues/298701 concerns broken remote installation paths rather than this declarative provisioning contract.
- **Open decisions:**
  - Should a trusted dev-container declaration install plugins automatically, or require an explicit one-time user approval before provisioning?
  - Are declared plugins enabled only for that workspace/container, or installed into the remote user profile and available to other remote workspaces?
  - How should user-level additional plugins compose with workspace declarations when the same plugin is enabled or disabled in both scopes?

## Evidence

- **current source gap:** src/vs/workbench/contrib/chat/common/plugins/workspacePluginSettingsService.ts reads `enabledPlugins` and `extraKnownMarketplaces` from `.github/copilot/settings.json` and `.claude/settings.json`, but exposes them only as workspace recommendations.
- **recommendation behavior:** src/vs/workbench/contrib/chat/browser/claudePluginRecommendations.ts checks for uninstalled recommendations after the first chat request and offers only "Show Plugins"; it does not install or enable them automatically.
- **configuration scope:** src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts still registers `chat.plugins.enabledPlugins` and `chat.plugins.marketplaces` with `ConfigurationScope.APPLICATION`, so ordinary workspace settings do not provide the requested container-specific provisioning.
- **maintainer direction:** https://github.com/microsoft/vscode/issues/305794#issuecomment-4244404249 asks whether plugin-install CLI options are planned and points to local-plugin configuration, while https://github.com/microsoft/vscode/issues/305794#issuecomment-4262265350 confirms that the suggested settings were unavailable at workspace scope.
- **canonical search:** https://github.com/microsoft/vscode/issues/298701 is older but tracks failures installing or resolving plugins in WSL/remote environments, not the same observable request for declarative per-devcontainer provisioning; it does not satisfy the stronger duplicate bar for this re-reviewed item.
