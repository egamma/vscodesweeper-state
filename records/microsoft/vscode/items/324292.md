# Issue #324292 — Prompt Caching Expiration shown in Session/Chat

[https://github.com/microsoft/vscode/issues/324292](https://github.com/microsoft/vscode/issues/324292)

## Summary

A real cache-transparency gap remains: current main reports historical cache hits but does not show when a session's prompt cache is expected to expire. This should be routed to the chat area for a provider-aware UX decision.

## Change summary

Show prompt-cache lifetime or freshness for each response, within the session, and in the sessions list so users can prioritize active sessions.

## Best solution

Expose a provider-aware cache status in the active session and sessions list, showing a countdown only when the applicable model/provider supplies a reliable TTL and otherwise avoiding false precision. Historical cached-token usage should remain available as supporting context.

## Plan brief

- **Likely files:** `src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts`, `src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts`, `src/vs/workbench/contrib/chat/common/chatUsage.ts`, `extensions/copilot/src/platform/networking/common/anthropic.ts`, `extensions/copilot/src/platform/endpoint/node/messagesApi.ts`
- **Validation:** Add sessions-list and chat-renderer tests covering a session with a known cache expiry, an expired cache, and a provider with no reliable TTL; verify that only the known case displays a countdown and existing cached-token details remain unchanged.
- **Behavior:**

  > Users managing concurrent agent sessions can see whether a session's prompt cache is still expected to be reusable and, when reliably known, how long remains. The status appears in the active session and sessions list and is updated as requests complete or the cache expires. Providers without a trustworthy expiration value must not display a fabricated countdown. Existing per-response cached-token information remains available.
- **Trace:**

  > Current response details are built by formatResponseTokenStats in src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts from historical IChatUsageModelTotal values. The cache explorer in src/vs/workbench/contrib/chat/browser/chatDebug/chatDebugCacheExplorerView.ts likewise derives hit health from completed requests, while session rows are rendered under src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts. Anthropic TTL selection occurs in extensions/copilot/src/platform/endpoint/node/messagesApi.ts through gates in extensions/copilot/src/platform/networking/common/anthropic.ts, and other providers may expose different or no TTL semantics. The boundary is cache-status presentation and the metadata required to support it; do not change provider caching policy or infer expiration solely from a previous cached-token count. The related discussion at https://github.com/microsoft/vscode/issues/321551 establishes demand for an in-chat timer but does not settle the sessions-list or unknown-provider behavior.
- **Open decisions:**
  - Should the UI show a countdown only for provider-confirmed TTLs, or may it show a clearly labeled estimate derived from the last request and known model policy?
  - When a session uses multiple models or cache entries with different lifetimes, should its sessions-list status represent the next expiry, the primary model's cache, or a non-numeric mixed state?
  - Should expired or unknown cache state remain passive metadata, or receive a stronger visual warning in the active session?

## Evidence

- **current response UI:** src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts:420-454 renders response completion time and cached input-token counts, but has no cache-expiration or remaining-lifetime field.
- **current diagnostic UI:** src/vs/workbench/contrib/chat/browser/chatDebug/chatDebugCacheExplorerView.ts:516-575 calculates historical cache-hit health from completed turns; it does not represent the future expiration time of a session's cache.
- **provider variability:** extensions/copilot/src/platform/endpoint/node/messagesApi.ts selects either the default Anthropic TTL or a 1-hour TTL, while extensions/copilot/src/platform/networking/common/anthropic.ts gates extended TTL by model and request context. A trustworthy UI therefore needs provider/model-specific semantics.
- **related older issue:** https://github.com/microsoft/vscode/issues/321551 is open and requests an in-chat warning or timer for the same cache-expiry concern, including https://github.com/microsoft/vscode/issues/321551#issuecomment-4882743876. It does not clearly own this issue's additional sessions-list status requirement, so the stronger re-review duplicate bar is not met.
- **existing mitigation:** extensions/copilot/package.json contributes github.copilot.chat.agent.longToolCallCachePreservation.enabled and maxProbes, but these experimental settings preserve caches during some long tool calls rather than telling users when each session cache expires.
